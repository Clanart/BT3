## Analysis

The external report's core broken invariant: an execution entrypoint (`receiveFlashLoan`/`onFlashLoan`) accepts and executes arbitrary attacker-supplied instructions without verifying they originated from a legitimate, bound call — becoming exploitable whenever the executing contract holds residual funds.

The direct local analog is `CallDispatcher.dispatch` in `evm/src/utils/CallDispatcher.sol`.

### Title
Permissionless `CallDispatcher.dispatch()` allows theft of any residual/unswept token balance left in the shared dispatcher singleton - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single shared, unowned utility contract (`_params.dispatcher`) used by `IntentGatewayV2` and multiple `HyperFungibleToken`/`WrappedHyperFungibleToken` variants to execute arbitrary batched calls (`Call[]`) during predispatch/postdispatch order flows and inbound-message calldata execution. Its `dispatch` function has **no access control whatsoever**: [1](#0-0) 

Anyone can call `CallDispatcher.dispatch(bytes)` directly with any `Call[]` they want, exactly mirroring the report's core issue where `receiveFlashLoan`/`onFlashLoan` executed attacker-chosen instructions with no binding to a legitimate origin — except here there isn't even a `msg.sender` restriction analogous to `_balancerVault`.

### Finding Description
`CallDispatcher` transiently holds tokens/ETH during order fulfillment. In `IntentGatewayV2.placeOrder`'s predispatch branch, after executing `order.predispatch.call`, only the exact `order.inputs` tokens are swept back to the gateway via a second `dispatch` call built from `inputsLen`: [2](#0-1) 

Likewise, in `IntentsBase._execute` (postdispatch, run after a solver fills an order), only tokens explicitly listed in `order.output.assets` are swept back as "dust": [3](#0-2) 

Any token balance that ends up in `CallDispatcher` outside of the tracked `order.inputs`/`order.output.assets` sets (e.g., a DEX swap producing an unexpected token, leftover router approvals granted to the dispatcher during predispatch calldata execution, or ETH sent via the `receive()` fallback) is never swept and persists in the contract across transactions: [4](#0-3) 

Because `dispatch()` has no `onlyOwner`/`onlyGateway` restriction and no linkage to a specific order commitment, an attacker can independently call `CallDispatcher.dispatch()` at any later time with a `Call[]` that transfers out that residual ERC20/ETH balance, or invokes any token for which `CallDispatcher` was left holding an approval by a prior predispatch swap call. This is unauthorized execution against a shared, unowned entrypoint — the same class of defect as the reported `receiveFlashLoan`, but strictly worse since there is no caller check at all.

### Impact Explanation
Unrestricted execution of arbitrary `Call[]` lets any unprivileged actor drain whatever value sits in `CallDispatcher` at a given time — token dust from swaps that don't match the tracked input/output token lists, native ETH dust, or funds obtainable via any approval left standing to the dispatcher by prior calldata execution. This is direct "stealing of funds" via unauthorized execution through a public, unauthenticated entrypoint, matching the bounty's accepted impact class.

### Likelihood Explanation
Every order that uses `predispatch`/`postdispatch` calldata (a documented, intended feature of `IntentGatewayV2`) routes value through this shared singleton `CallDispatcher`. Since sweep logic in both `placeOrder` and `_execute` only recovers tokens present in the pre-declared input/output asset lists, any deviation (a swap producing dust, over-approval to a router, unexpected token) leaves value sitting in a contract that anyone can call into with zero restriction — no relayer, prover, or privileged role is required to exploit it.

### Recommendation
Restrict `CallDispatcher.dispatch` to only be callable by the specific gateway/app that owns it (e.g., an immutable `owner`/`caller` set at construction with an `onlyCaller` modifier), and/or make `CallDispatcher` instances per-order/ephemeral rather than a shared long-lived singleton so no cross-call residual value can accumulate. Additionally, sweep *all* token balances held by the dispatcher (not just the pre-declared list) back to the gateway at the end of each predispatch/postdispatch flow, and revoke any approvals granted to the dispatcher during calldata execution.

### Proof of Concept
1. A user places an order with `predispatch.call` that swaps ETH to DAI via Uniswap, but the swap output slightly exceeds `order.inputs` due to slippage rounding, or the router leaves a nonzero DAI approval granted to `CallDispatcher` after the swap.
2. `IntentGatewayV2.placeOrder` only sweeps back the exact `order.inputs` token(s)/amount via `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`, leaving the excess DAI (or the DAI approval) sitting on `CallDispatcher`.
3. An attacker (any address) calls `CallDispatcher.dispatch(abi.encode([Call({to: DAI, value: 0, data: transfer(attacker, residualAmount)})]))` directly — no access control blocks this since `dispatch` has no caller restriction — and receives the residual DAI, or if an approval was left, calls `DAI.transferFrom(dispatcher, attacker, amount)` leveraging the standing allowance.
4. Funds that belonged to the protocol/users are extracted by an unprivileged third party through a legitimate but unauthenticated shared entrypoint. [1](#0-0)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
