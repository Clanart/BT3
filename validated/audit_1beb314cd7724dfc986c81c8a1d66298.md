### Title
Pool-leave `heightlock` is measured from the leave-signal, not from reward timing, letting a farmer pre-satisfy the wait and race the pool for pending rewards - ([File: chia/pools/plotnft_drivers.py])

### Summary
`PoolWallet`'s pool-leaving design explicitly states its purpose: *"The pool is also protected, by not allowing members to cheat by quickly leaving a pool, and claiming a block that was pledged to the pool"* via a mandatory wait (`relative_lock_height`/`heightlock`) between signaling an exit and being allowed to finish it. However, the wait is checked against the height at which the leave signal itself was submitted, not against the height of any specific reward the pool is trying to protect. A farmer can signal "leave pool" immediately (even before any reward has ever been farmed), let the short lock elapse, and then hold the fully-matured "finish leaving" transaction ready to fire the instant a new pool reward lands - stealing it from the pool with zero reaction time, exactly mirroring the reported Cosmos-style bug of pre-signaling an undelegate to defeat a cooldown meant to react to a specific future event.

### Finding Description
`PlotNFT2Wallet.leave_pool()` can be invoked at any time while `pooling` is true, with no requirement that any reward has been farmed or that a minimum farming period has elapsed: [1](#0-0) 

This creates a waiting-room coin whose only exit gate is a relative height-lock computed from that very coin's own creation height: [2](#0-1) 

and the restriction enforced while exiting is simply `Heightlock(heightlock)` plus `SendMessageBanned()` — nothing ties this lock to when a *particular* reward coin was created: [3](#0-2) 

The pool-reward destination (`p2_singleton` puzzle hash) is fixed purely by `launcher_id` and is identical across `FARMING_TO_POOL`, `LEAVING_POOL` (waiting room), and `SELF_POOLING` states: [4](#0-3) 

While `pool_config` is still set (i.e., before the second, "finish leaving" transaction lands), the pool retains a valid path to sweep any reward sent to that address via the `MofN` custody structure's pool member branch: [5](#0-4) 

Once the second transaction is confirmed, `pool_config` becomes `None` and `exiting` resets to `False`, and only the owner can call `claim_rewards`/`claim_pool_rewards` on that address: [6](#0-5) 

The legacy `PoolWallet` implementation exhibits the identical pattern: the lock check compares the current sync height against `last_height + relative_lock_height`, where `last_height` is the height of the `LEAVING_POOL` transition in spend history, again with no linkage to reward timing: [7](#0-6) [8](#0-7) 

Because the lock clock starts at the moment the farmer *chooses* to signal leaving rather than at the moment a reward the pool needs to protect is created, a farmer can:
1. Signal leave immediately after joining (or at any convenient early time), well before winning any block.
2. Wait out the `heightlock` (a pool-set value, with legacy `MINIMUM_RELATIVE_LOCK_HEIGHT` as low as 5 blocks) while it is cheap/fast — the lock is now permanently satisfied.
3. Continue farming normally (plots still pay to the same p2-singleton address, and the pool still sees them as "LEAVING_POOL", not yet aware or acting).
4. The instant a reward is farmed to that address, immediately broadcast the pre-prepared "finish leaving + self-claim" spend bundle in the same or next block, with the lock condition already trivially true and zero additional delay — racing (and typically beating) the pool's own reward-forwarding transaction which only starts after the pool observes the leave signal.

This defeats the design intent of the lock — giving the pool a genuine window, counted from signal-to-action, to react and forward each specific reward before the member exits — because the farmer can pre-purchase that window long in advance of any reward existing.

### Impact Explanation
This allows a pool member to systematically redirect block rewards that are contractually pledged to the pool into their own wallet, by racing the pool's reward-sweep transaction with a pre-satisfied exit. This is a concrete reward-redirection/theft-of-settlement issue directly reachable by any pool participant crafting their own spend bundles (no privileged access needed), matching the "reward redirection" acceptance criterion.

### Likelihood Explanation
Exploitation only requires an unprivileged wallet user who: joins a pool, immediately calls `leave_pool()`, waits the (often small, pool-configured) `heightlock`, and then submits a pre-built finish-leaving + claim transaction as soon as a reward is observed on chain. No special timing tricks beyond normal mempool submission are needed, and the race favors the farmer since their transaction can be pre-signed and broadcast the instant the reward coin is confirmed, while the pool must first detect the leave state and then react.

### Recommendation
- Short term: Tie the exit height-lock to the height of the most recently unclaimed pool reward (or require the pool to have had a minimum window since the *last farmed reward*, not since the leave signal), so that pre-signaling early cannot pre-satisfy a lock meant to protect rewards that don't exist yet. Alternatively, require the pool to have a first-refusal/forced-forward window on any reward coin created after a leave signal, independent of how long ago the signal happened.
- Long term: Audit all height/time-based cooldowns in the pooling and singleton-transition code for the same "clock starts at declared intent, not at the protected event" pattern, and ensure locks are always measured relative to the event they are meant to protect.

### Proof of Concept
1. Farmer creates a `PlotNFT2Wallet` and joins a pool with `heightlock = 5` (or any pool-set small value).
2. Immediately (before ever winning a block) call `leave_pool()`, per `chia/wallet/plotnft_wallet/plotnft_wallet.py:292-356`, creating the waiting-room coin.
3. Farm 5+ blocks so `AssertHeightRelative(height=heightlock)` in `exit_from_waiting_room_conditions()` (`chia/pools/plotnft_drivers.py:308-318`) is satisfied — this can happen in minutes, long before any real pool reward is farmed.
4. Continue farming normally to the pool; plots still pay to the fixed `reward_puzhash()` address.
5. When a pool reward coin appears at that address, immediately broadcast the pre-signed spend that (a) finishes leaving (`pool_config=None`) and (b) calls `claim_pool_rewards` for that coin, in the same or next block.
6. If this transaction confirms before the pool's own `forward_pool_reward` sweep, the farmer keeps a reward that was pledged to the pool, defeating the intended reactive protection window entirely.
