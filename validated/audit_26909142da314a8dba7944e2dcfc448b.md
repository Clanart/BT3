### Title
Deterministic reuse of a cached FROST preprocess across distinct signing rounds enables secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
CVE-2021-29266 is a stale-state bug: `vdpa` re-opened a char device with an invalid cached `config_ctx`, so a context that must be fresh per-open was reused across instantiations. The Serai analog lives in `SigningProtocol::preprocess_internal`/`share_internal`, where a FROST preprocess seed is persisted in `CachedPreprocesses` keyed only by `context` and deterministically re-expanded on every `share`/`complete` call. If the same `context` is used to sign under two different preprocess sets (different signer subsets → different binding factors and different challenge), the identical nonces `d, e` are reused across two published signature shares, which is the classic FROST/ROS nonce-reuse key-recovery condition.

### Finding Description
`preprocess_internal` derives a 32-byte ChaCha20 seed and stores it under `CachedPreprocesses::set(self.txn, &self.context, &cache)`; on every subsequent call it reloads the same seed, XOR-decrypts it, and calls `AlgorithmSignMachine::from_cache`, which deterministically re-derives the same nonces via `ChaCha20Rng::from_seed(*seed.0)` in `seeded_preprocess`. The seed is never deleted or rotated after use. The only uniqueness guard is `if CachedPreprocesses::get(...).is_none()` — i.e., a "create once" check, not a "use once" check. [1](#0-0) [2](#0-1) 

`share_internal` unconditionally calls `self.preprocess_internal(participants).0`, so each invocation of `share` and of `complete` reconstructs an `AlgorithmSignMachine` holding the same `nonces`. `DkgConfirmer::share` and `DkgConfirmer::complete` both go through `share_internal` with `context = (b"DkgConfirmer", self.attempt)` — the context does not commit to the preprocess set, only to the attempt counter. [3](#0-2) [4](#0-3) 

In `AlgorithmSignMachine::sign`, the share is a Schnorr-style linear function of the secret share: `s_i = d + e·ρ_i − λ_i·s·c`, where the binding factor `ρ_i` and challenge `c` both depend on the included signer set and the aggregate commitments (`R`). Two `share_internal` executions under the same `context` with different `serialized_preprocesses` maps (e.g., one preprocess arriving between a `share` call and a `complete` call, or a retry path re-calling `share` with a different validator subset) produce two shares over the same `d, e` with different `(ρ, c, λ)` — two independent linear equations on unknowns `e` and the interpolated secret `λ_i·s`. The code itself documents the consequence: "Reusing preprocesses would enable a third-party to recover your private key share." [5](#0-4) [6](#0-5) 

### Impact Explanation
Shares and preprocesses are broadcast over the authenticated-but-public tributary channel, so any observer (including an unprivileged counterparty whose preprocess bytes are read via `read_preprocess` and accepted into the map) that can induce or observe two distinct signing sets under one `context` collects two shares sharing the same nonce. Solving the linear system recovers the signer's interpolated secret share; combined with public threshold parameters this reduces the security of the MuSig/FROST layer to a single compromised share — a key-share-recovery analog of the kernel's stale-context UAF.

### Likelihood Explanation
The reuse is structural, not edge-case: `share()` and `complete()` are separate calls that each re-run `share_internal`, and `preprocess()` may also run beforehand. Because the cached seed is keyed only by `("DkgConfirmer", attempt)` and never consumed, any code path that evaluates `share_internal` twice with differing preprocess sets within one attempt — retries after a mid-protocol failure, or a validator's preprocess arriving after the first share was computed — deterministically reuses the nonce. A counterparty controls which serialized preprocesses are submitted, so the attacker-chosen-signing-set precondition is reachable with public inputs.

### Recommendation
Delete (or rotate) the `CachedPreprocesses` entry the first time `share_internal` uses it — i.e., enforce the documented single-use semantics — and bind the cache key to the preprocess set actually signed over (e.g., hash of the sorted `serialized_preprocesses` map plus `msg`), so that any second `share_internal` call either returns the identical share or fails rather than signing with reused nonces. `complete` should reuse the machine produced by `share` instead of re-deriving it.

### Proof of Concept
1. Attempt `a` begins; `share(preprocesses_A, kp)` runs `share_internal`, loads seed `x` under context `("DkgConfirmer", a)`, derives nonces `(d, e)`, and emits share `s_1 = d + e·ρ_A − λ_A·s·c_A`.
2. A counterparty contributes an additional/different preprocess set `preprocesses_B ≠ preprocesses_A` under the same attempt; `complete(preprocesses_B, kp, shares)` calls `share_internal` again, reloads the same seed `x`, re-derives `(d, e)`, and computes `s_2 = d + e·ρ_B − λ_B·s·c_B` with `ρ_B, c_B, λ_B` computable by anyone from the public preprocesses.
3. From `s_1, s_2`, solve the 2×2 system for `e` and `λ·s`, recovering the signer's effective secret share for the set.

I could not fully trace `coordinator/src/tributary/handle.rs` (tool budget exhausted) to confirm whether production control flow ever invokes `share`/`complete` twice with differing preprocess maps; the vulnerable mechanism in `signing_protocol.rs`/`crypto/frost/src/sign.rs` is confirmed, but the exact trigger path in the coordinator remains unverified.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
  }

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }

# Caching

modular-frost supports caching a preprocess. This is done by having all
preprocesses use a seeded RNG. Accordingly, the entire preprocess can be derived
from the RNG seed, making the cache just the seed.

Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
