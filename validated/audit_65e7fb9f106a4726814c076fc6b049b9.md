### Title
Aggregator role omitted from `check_mainnet_requirements` allows unauthenticated `InternalSendTx`/`SendMoveToVaultTx` broadcasting calls on mainnet - (File: core/src/config/mod.rs)

### Summary
`BridgeConfig::check_mainnet_requirements` only rejects `client_verification=false` for `cli::Actor::Verifier | cli::Actor::Operator`, never for `cli::Actor::Aggregator`. Since `create_grpc_server` derives both TLS client-cert enforcement and the `Interceptors::Noop` vs `OnlyAggregatorAndSelf` choice directly from `config.client_verification`, an aggregator deployed with `client_verification=false` passes the mainnet sanity check yet exposes all of its gRPC methods, including state-changing/broadcasting ones, without any peer-certificate check.

### Finding Description
The binding that should hold is: `caller_identity == aggregator_self_or_authorized_client` for every state-changing aggregator RPC, enforced via mTLS client-cert pinning (`only_aggregator_and_self` in `core/src/rpc/interceptors.rs:36-77`). This binding is installed only when `config.client_verification == true`: [1](#0-0) 

`check_mainnet_requirements` is meant to prevent unsafe mainnet configurations, but its `client_verification` check is scoped to `Verifier | Operator` only: [2](#0-1) 

`main.rs` calls `check_mainnet_requirements(cli::Actor::Aggregator)` before starting the aggregator server, and since the match arm never includes `Aggregator`, this call returns `Ok(())` even with `client_verification=false`: [3](#0-2) 

With `client_verification=false`, `create_grpc_server` (1) builds `ServerTlsConfig` without `client_ca_root` (no client cert required at all) and (2) installs `Interceptors::Noop`, which passes every request through unchecked: [4](#0-3) 

This means any unauthenticated caller can invoke `SendMoveToVaultTx` and `InternalSendTx` on the aggregator's public port: [5](#0-4) [6](#0-5) 

`internal_send_tx` performs no validation of the raw transaction content at all before queueing it for broadcast via `tx_sender.insert_try_to_send`, and `send_move_to_vault_tx` only validates output count/amounts/script-pubkeys (recomputed from the current N-of-N + security-council keys), not that the input actually carries a valid signature.

However, tracing further: neither RPC can be used to actually redirect BTC out of the vault. `send_move_to_vault_tx` recomputes and enforces the exact vault script pubkey (`nofn_script` + `security_council_script`) for output 0 and the anchor script for output 1, so an attacker cannot substitute their own destination there, and any transaction lacking a valid N-of-N witness will simply be rejected by Bitcoin consensus when the tx-sender tries to broadcast it. `internal_send_tx` similarly only queues a transaction for broadcast — it does not produce or reveal any signature, so an attacker still cannot spend a taproot UTXO protected by the N-of-N/security-council script without already possessing a valid witness. Thus the "BTC leaves a move-to-vault UTXO under attacker control" claim is not substantiated by the code: `SECP.verify_schnorr`/consensus script validation on the Bitcoin network itself still blocks any unsigned or forged spend, regardless of gRPC-layer authentication.

What *is* substantiated and real is that these are unauthenticated, state-changing, broadcasting gRPC calls reachable by anyone who can reach the aggregator's port when `client_verification=false` — which matches the rules' own "High" bucket ("an unauthenticated state-changing or broadcasting call"), not the "Critical" fund-loss bucket.

### Impact Explanation
- Impact category: High — unauthenticated state-changing/broadcasting calls (`InternalSendTx`, `SendMoveToVaultTx`) on the aggregator.
- An attacker can force the aggregator's tx-sender to queue and attempt to broadcast arbitrary attacker-chosen transactions, potentially disrupting the tx-sender queue, triggering unnecessary CPFP fee-bumping logic, or interfering with legitimate deposit/round transaction management. This is repeatable per call and does not require any bridge secret, deposit, or key share.
- It does NOT let the attacker steal a move-to-vault UTXO or forge N-of-N signatures — Bitcoin script/consensus enforcement (taproot key/script path checks on the vault output) remains intact regardless of gRPC auth, so the "Critical" impact asserted in the question is not supported by the code.

### Likelihood Explanation
- Requires a real deployment misconfiguration: mainnet paramset (`Network::Bitcoin`) with `client_verification=false` specifically on the Aggregator role. This is a documented config knob (`core/src/config/mod.rs:134-138`), not a hypothetical, and `check_mainnet_requirements` for `Aggregator` will not catch it because of the missing match arm.
- No attacker BTC/collateral is required — only network access to the aggregator's gRPC port, matching the described unprivileged attacker capabilities.
- If this misconfiguration exists in production, exploitation is trivial and repeatable (every call to `InternalSendTx`/`SendMoveToVaultTx` succeeds without any certificate).

### Recommendation
Include `cli::Actor::Aggregator` in the `client_verification` mainnet check in `core/src/config/mod.rs::check_mainnet_requirements`, i.e. change:
```rust
if matches!(actor_type, cli::Actor::Verifier | cli::Actor::Operator) && !self.client_verification {
```
to also cover `cli::Actor::Aggregator`, since the aggregator exposes equally sensitive state-changing/broadcasting RPCs that rely on the same `OnlyAggregatorAndSelf` interceptor for authorization.

use tonic::{service::Interceptor, transport::CertificateDer, Request, Status};

#[derive(Debug, Clone)]
pub enum Interceptors {
    OnlyAggregatorAndSelf {
        aggregator_cert: CertificateDer<'static>,
        our_cert: CertificateDer<'static>,
    },
    Noop,
}

fn is_internal(req: &Request<()>) -> bool {
    // This normally doesn't exist but we add it in the AddMethodMiddleware
    let Some(path) = req.metadata().get("grpc-method") else {
        // No grpc method? this should not happen
        tracing::error!("Missing grpc-method header in request");
        return false;
    };
    path.as_bytes().starts_with(b"Internal")
}

impl Interceptor for Interceptors {
    #[allow(clippy::result_large_err)]
    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {
        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
