### Title
Aggregator gRPC server ships with no client authentication by default, allowing unauthenticated callers to invoke state-changing RPCs like `GetEntityStatuses(restart_tasks=true)` - (File: core/src/servers.rs)

### Summary
`create_grpc_server` only enforces client-certificate verification and applies the `OnlyAggregatorAndSelf` interceptor when `config.client_verification == true`; otherwise it falls back to the `Noop` interceptor with no per-method authorization. `create_aggregator_grpc_server` treats `client_verification=true` as a misconfiguration (only logging a `tracing::warn!`), meaning the documented/default aggregator deployment runs with `client_verification=false` and thus `Noop`. Any network peer that can complete a plain server-authenticated TLS handshake (no client certificate required) can therefore call any RPC on `ClementineAggregatorServer`, including `GetEntityStatuses` with `restart_tasks: true`.

### Finding Description
Binding claimed: "the caller invoking `restart_tasks=true` on the aggregator" == "the aggregator operator performing authorized maintenance." This binding is broken because the RPC path enforces no such equality.

Trace:
- `create_grpc_server` (core/src/servers.rs:106-139) builds `ServerTlsConfig` with `.identity(server_identity)` only, and no `.client_ca_root(...)`, when `config.client_verification` is `false`. It also selects the interceptor: `Noop` unless `client_verification == true` [1](#0-0) .
- `create_aggregator_grpc_server` never sets `client_verification` to true for the aggregator; it only emits a warning if it happens to be true, implying the intended/default deployment is `client_verification=false` [2](#0-1) .
- The `Interceptors::Noop` variant performs no check at all and simply passes every request through: `Interceptors::Noop => Ok(req)` [3](#0-2) . Only the `OnlyAggregatorAndSelf` variant checks peer TLS client certificates against pinned aggregator/self certs [4](#0-3) .
- Consequently, with the default configuration, no gRPC method on the aggregator's public port has any authentication/authorization gate — any TCP client that completes a standard (server-only) TLS handshake can call every RPC exposed by `ClementineAggregatorServer`, including `GetEntityStatuses`.

This directly matches the rule-defined High-severity category "an unauthenticated state-changing or broadcasting call," since `GetEntityStatuses(restart_tasks: true)` is state-changing (it triggers restart of background tasks across operators/verifiers) and reachable with zero credentials.

Existing guards do not prevent this: `only_aggregator_and_self` is never invoked because the interceptor list resolves to `Noop`; there is no independent per-RPC authorization check inside the aggregator's RPC handler layer itself (`core/src/rpc/aggregator.rs`) — authorization is solely delegated to the transport-level interceptor which is bypassed by default configuration.

### Impact Explanation
An unauthenticated attacker can invoke arbitrary aggregator gRPC methods, not just `GetEntityStatuses`. For the specific method cited, triggering `restart_tasks=true` at will restarts background tasks (round tracking, tx_sender resubmission loops) on operators/verifiers at attacker-chosen times, repeatable indefinitely and applicable to every deposit/operator managed by that aggregator instance. This is an unauthenticated state-changing call over the aggregator's public interface — matching the High-severity category explicitly defined in the rules ("an unauthenticated state-changing or broadcasting call"). Broader consequences (e.g., interfering with deadline-bound Disprove/Challenge submission) depend on precise timing and task-restart behavior, which increases severity risk but the baseline unauthenticated state-changing access alone qualifies as High.

### Likelihood Explanation
Preconditions: aggregator deployed with the default/documented `client_verification=false` (the only configuration `create_aggregator_grpc_server` doesn't warn against), and its gRPC port reachable by the attacker — both stated as given in the threat model ("send requests to the aggregator's public gRPC port"). No BTC cost, no privileged credentials, no TLS interception needed — the attacker only needs a standard TLS client connecting to a public, server-authenticated endpoint. This is trivially repeatable and requires no on-chain action at all.

### Recommendation
Enforce mutual TLS / client certificate verification unconditionally on the aggregator's gRPC server, or add an explicit method-level authorization/allow-list check that does not depend solely on `config.client_verification`. At minimum, make `create_aggregator_grpc_server` refuse to start (rather than just `tracing::warn!`) when `client_verification` is disabled, or introduce a dedicated authentication mechanism (e.g., API key, mTLS always-on for the aggregator) so that `Noop` is never reachable in production.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
