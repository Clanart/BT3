Based on my investigation, this is the analogous vulnerability: `SetBooleanInBitGroups` in the slashing keeper omits the bounds check that its read counterpart `GetBooleanFromBitGroups` performs, mirroring the OCFS2 pattern of using an unvalidated size/index against a raw backing array without the same validation applied on the read path.

### Title
Missing bounds check in `SetBooleanInBitGroups` can cause an out-of-range panic/consensus halt when governance shrinks `SignedBlocksWindow` mid-slashing-window - ([File: sei-cosmos/x/slashing/keeper/signing_info.go])

### Summary
`GetBooleanFromBitGroups` validates `indexKey >= len(bitGroupArray)` before indexing, but its write counterpart `SetBooleanInBitGroups` performs the identical `indexKey := index / UINT_64_NUM_BITS` computation and indexes `bitGroupArray[indexKey]` with **no bounds check at all**. [1](#0-0)  This is structurally the same bug class as the OCFS2 report: a read path validates the derived index/size against the backing buffer, while a parallel write path skips the same validation, so an out-of-range value drives an out-of-bounds access.

### Finding Description
`HandleValidatorSignatureConcurrent` (called every block, for every validator, from `BeginBlocker`) computes `index := signInfo.IndexOffset` and, only if `missedInfo.WindowSize != window`, calls `ResizeMissedBlockArray` to reconcile the stored bit array size with the current `SignedBlocksWindow` param before calling `SetBooleanInBitGroups(missedInfo.MissedBlocks, index, missed)`. [2](#0-1) 

The resize logic explicitly resets `index = 0` when the window shrinks (`missedInfo.WindowSize > window`) [3](#0-2)  and rebuilds `newArray` sized to `window`, but the expand branch (`missedInfo.WindowSize < window`) computes `newArray := make([]bool, window)` and copies based on `index` without clamping `index` to the new array bounds in all cases, and `ParseBoolArrayToBitGroups` immediately re-derives `arrLen` from the possibly stale/inconsistent bool-array length before calling `SetBooleanInBitGroups` in a loop with no bounds check: [4](#0-3) 

Because `SetBooleanInBitGroups` unconditionally does `bitGroupArray[indexKey] |= indexMask` / `&^= indexMask` with `indexKey := index / UINT_64_NUM_BITS` and no `indexKey >= len(bitGroupArray)` guard [5](#0-4) , any code path that produces an `index` (or a boolArray length) inconsistent with the freshly-allocated `bitGroupArray` size — e.g. a stale/corrupted `IndexOffset` relative to the newly resized array after a `SignedBlocksWindow` parameter change, or state written by an older/alternate binary with different invariants — triggers a Go slice-index-out-of-range panic. Since `HandleValidatorSignatureConcurrent` is invoked unconditionally from `BeginBlocker` for every validator every block, a panic here is not recovered and crashes/halts the node executing it, and because all nodes execute `BeginBlocker` deterministically, a state condition that triggers this on one node triggers it on all validating nodes, producing a chain-wide halt rather than an isolated crash.

### Impact Explanation
If reachable, this results in a full validator-set halt: `BeginBlocker` panics are not recovered by the SDK's ante/handler recovery machinery in the same way transaction execution panics are, and a panic during `BeginBlocker` crashes the node process. Because the `SignedBlocksWindow` parameter is a governance-controlled param that any validator set upgrade/param-change proposal can adjust, and the missed-block bit array persists across param changes with the resize/reindex logic in `ResizeMissedBlockArray`, an inconsistency between `IndexOffset` and the newly-sized `MissedBlocks` array after a window-size change is a plausible trigger for `indexKey >= len(bitGroupArray)`, causing every validator node to panic simultaneously — a permanent chain halt until a coordinated patch/state-surgery.

### Likelihood Explanation
This requires a `SignedBlocksWindow` parameter change (a governance action) combined with a validator whose `IndexOffset`/missed-block array state ends up inconsistent with the resize invariants that `ResizeMissedBlockArray` assumes hold. I was not able to fully verify, within the available context, a concrete sequence of parameter changes and validator states that deterministically triggers `indexKey >= len(bitGroupArray)` (i.e., I could not rule out that `ResizeMissedBlockArray`'s invariants always keep `index` in range for every reachable window-size transition, including consecutive shrink/expand cycles or values of `index` at or beyond `missedInfo.WindowSize` at the time of resize). This uncertainty is a real gap: the missing bounds check is a genuine defensive-coding asymmetry between the get/set functions, but confirming exploitability requires tracing all call sites and historical migration paths (e.g., `migrations.go`) that could leave `IndexOffset` or array length in an unexpected relationship, which I was unable to complete in the given iterations.

### Recommendation
Add the same bounds check in `SetBooleanInBitGroups` that already exists in `GetBooleanFromBitGroups`:
```go
func (k Keeper) SetBooleanInBitGroups(bitGroupArray []uint64, index int64, missed bool) []uint64 {
    indexKey := index / UINT_64_NUM_BITS
    if indexKey < 0 || indexKey >= int64(len(bitGroupArray)) {
        return bitGroupArray // or grow/log, depending on desired semantics
    }
    ...
}
```
Additionally, audit `ResizeMissedBlockArray` and its callers to guarantee `index < window` (and thus `indexKey < len(newArray)`) is a true invariant across every parameter-change transition before removing the defensive check, and add a regression test that exercises consecutive `SignedBlocksWindow` increases/decreases interleaved with the concurrent signature-handling path.

### Proof of Concept
I was unable to construct a concrete, verified state transition (specific `IndexOffset`, `WindowSize`, and sequence of `SignedBlocksWindow` param changes) that provably drives `index` out of range within the scope of this investigation; doing so would require deeper tracing of `ResizeMissedBlockArray`'s invariants across all call sites and historical migrations than was possible here. The vulnerable code pattern itself — an unchecked array index derived from a value whose bounds are validated on the read path but not the write path — is confirmed by direct code inspection at the citations above.

```go
// Get a boolean representing whether a validator missed a block with a specific index offset
func (k Keeper) GetBooleanFromBitGroups(bitGroupArray []uint64, index int64) bool {
	// convert the index into indexKey + indexShift
	indexKey := index / UINT_64_NUM_BITS
	indexShift := index % UINT_64_NUM_BITS
	if indexKey >= int64(len(bitGroupArray)) {
		return false
	}
	// shift 1 by the indexShift value to generate bit mask (to index into the bitGroup)
	indexMask := uint64(1) << indexShift
	// apply the mask and if the value at that `indexShift` is 1 (indicating miss), then the value would be non-zero
	missed := (bitGroupArray[indexKey] & indexMask) != 0
	return missed
}

// Set the missed value for whether a validator missed a block
func (k Keeper) SetBooleanInBitGroups(bitGroupArray []uint64, index int64, missed bool) []uint64 {
	// convert the index into indexKey + indexShift
	indexKey := index / UINT_64_NUM_BITS
	indexShift := index % UINT_64_NUM_BITS
	indexMask := uint64(1) << indexShift
	if missed {
		// set bit to 1 by ORing with the specific position as 1
		bitGroupArray[indexKey] |= indexMask
	} else {
		// set bit to 0 by AND NOTing with the specific position as 1
		bitGroupArray[indexKey] &^= indexMask
	}
	// set after updating the position
	return bitGroupArray
}
```
