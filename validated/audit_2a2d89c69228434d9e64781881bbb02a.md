## Analysis

The external report's core broken invariant: a system accepts a **preliminary, still-overridable** attestation as final proof of an outcome, because the check only asks "has the current verifier/oracle answered" instead of "has the *entire* dispute/finality process actually concluded." A second, longer-lived challenge mechanism can still overturn the "answer" after the primitive already treats it as settled.

This exact pattern exists in Hyperbridge's Optimism (OP-Stack) consensus client.

### Title
Optimism fault-dispute-game client accepts unresolved (still-challengeable) L2 output roots as finalized state after only a 5-minute ISMP challenge period, well before OP's actual dispute-resolution window elapses - (File: `modules/ismp/clients/optimism/src/lib.rs`, `tesseract/consensus/op-host/src/host.rs`)

### Summary
`verify_optimism_dispute_game_proof` only checks that, at the specific L1 state root supplied by the relayer, the referenced `FaultDisputeGame`/`AggregateVerifier` proxy has *not yet* been challenged (`claimData.length == 1` / `counteredByIntermediateRootIndexPlusOne == 0`). It never checks the game's `status`/`resolvedAt`, nor whether OP's own multi-day dispute-resolution clock has actually elapsed. The resulting `IntermediateState` is then stored and becomes usable for message processing after Hyperbridge's own ISMP `challenge_period`, which for OP consensus is hardcoded to `5 * 60` seconds (5 minutes), as set in `query_initial_consensus_state`. ### Finding Description
OP's own fault-proof security model requires a claim to survive the *entire* dispute-game clock (on Superchain deployments, on the order of ~3.5 days for each side, i.e. up to ~7 days total) before it is truly final and cannot be overturned. Any bonded party may permissionlessly create a `FaultDisputeGame` with an arbitrary root claim via the `DisputeGameFactory` — this is by design in OP's fault-proof system and requires no compromised relayer, prover, or admin. [4](#0-3) 

`verify_not_challenged` merely proves that, at the moment the relayer's proof was captured, `claimData.length == 1` (no counter-move yet) — it is a snapshot check, not a finality check: [5](#0-4) 

Nothing in `verify_optimism_dispute_game_proof` verifies the game's `resolvedAt`/`status`, nor its `createdAt` age against OP's actual `maxClockDuration`. The function only binds the game type to its implementation and checks "not-yet-challenged": [6](#0-5) 

Once this proof is accepted, the `IntermediateState` is stored as a `StateCommitment` for the OP state machine on Hyperbridge. `IsmpOptimism::verify_consensus` wires this straight through, guarded only by a fisherman blacklist on the *specific proxy address* (not by dispute-resolution finality): [7](#0-6) 

Crucially, the ISMP `challenge_period` configured for this consensus client (which gates when the stored `StateCommitment` becomes usable for `handlePostRequests`/`handleGetResponses`/timeouts per `HandlerV2.sol` and `validate_state_machine` in `modules/ismp/core/src/handlers.rs`) is hardcoded to only 300 seconds: [3](#0-2) 

This mirrors the PredictDotLoan bug precisely: `_isQuestionPriceAvailable` treated a UMA answer as final even though the NegRiskAdapterOperator's overriding flag window hadn't elapsed. Here, "not yet challenged as of this L1 snapshot" is treated as equivalent to "finalized, unchallengeable state," even though OP's actual challenge/dispute window (days) vastly exceeds Hyperbridge's own 5-minute challenge period. A claim that is unchallenged in minute 1 of a multi-day dispute window is not proof that it will remain unchallenged — exactly the gap the original bug exploited between a first-pass oracle report and the second, authoritative override step.

### Impact Explanation
An attacker can permissionlessly create a `FaultDisputeGame` on L1 for the target OP chain with a **false** root claim, immediately generate the storage proofs showing "not yet challenged" (`claimData.length == 1`), and submit this to Hyperbridge's `IsmpOptimism` pallet. After Hyperbridge's 5-minute challenge period elapses — far sooner than any real OP challenger would need to detect and dispute the claim on L1 — the false state root becomes usable as canonical state on Hyperbridge. Relayers/attackers can then submit request/response/timeout proofs (`PostRequestMessage`, `GetResponseMessage`, `PostRequestTimeoutMessage`) verified against this fabricated `stateRoot`/`overlayRoot`, causing `HandlerV2` to dispatch attacker-controlled cross-chain messages, incoming request payloads, or GET responses to modules on Hyperbridge or downstream chains that were never legitimately produced on OP. This is direct false-state acceptance leading to unauthorized execution and potential fund loss/lock for any bridged assets, orders, or module state keyed to this consensus client.

### Likelihood Explanation
Creating a dispute game with an arbitrary claim is a permissionless, unprivileged, one-transaction action requiring only the bond (no relayer, prover, or governance compromise needed) — satisfying the "unprivileged attacker" requirement. The 5-minute window is short relative to the multi-day real OP dispute-resolution clock, making the race entirely plausible for an attacker who controls both the false-claim submission and the immediately-following Hyperbridge proof submission.

### Recommendation
Do not treat "not yet challenged at proof-time" as equivalent to "finalized." Either:
1. Require proof that the dispute game has actually **resolved** (`status == DEFENDER_WINS`/resolved, `resolvedAt != 0`) before accepting the claim, or
2. Set the ISMP `challenge_period` for OP consensus clients to be at least as long as OP's `maxClockDuration` (the full dispute-resolution window), so Hyperbridge's own challenge period cannot expire before OP's fault-proof game could still be legitimately challenged and overturned.

### Proof of Concept
1. Attacker calls OP's `DisputeGameFactory.create(gameType, falseRootClaim, extraData)` with the required bond, creating a new `FaultDisputeGame` proxy referencing a false L2 output root.
2. Immediately (same L1 block/height), attacker fetches: dispute-factory storage proof, dispute-game-existence proof, `gameImpls` proof, and the proxy's `claimData` storage proof (still length 1, since no one has challenged yet).
3. Attacker submits `OptimismDisputeGameProof` to `IsmpOptimism::verify_consensus` via `update_client`; `verify_optimism_dispute_game_proof` succeeds because all it checks is existence + "not challenged yet" — none of the real OP dispute-window constraints. [8](#0-7) 
4. The false `IntermediateState`/`StateCommitment` is stored; after the hardcoded `5 * 60`-second challenge period elapses, `stateMachineCommitmentUpdateTime` satisfies `delay >= challengePeriod` in `HandlerV2.handlePostRequests`/`handleGetResponses`. [9](#0-8) 
5. Attacker crafts state/merkle proofs against the false `stateRoot`/`overlayRoot` for arbitrary requests/responses and submits them to `HandlerV2`, which dispatches them as legitimate cross-chain messages — well before OP's own multi-day dispute window would have allowed a legitimate challenger to overturn the false claim on L1.

pub fn verify_optimism_dispute_game_proof<H: Keccak256 + Send + Sync>(
	payload: OptimismDisputeGameProof,
	root: H256,
	dispute_factory_address: H160,
	game_type_configs: Vec<GameTypeConfig>,
	consensus_state_id: ConsensusStateId,
) -> Result<IntermediateState, Error> {
	// Find the per-game-type configuration for this proof's game type.
	let game_config = game_type_configs
		.iter()
		.find(|c| c.game_type == payload.game_type)
		.ok_or(Error::UnsupportedGameType(payload.game_type))?
		.clone();

	let factory_storage_root =
		get_contract_account::<H>(payload.dispute_factory_proof, &dispute_factory_address.0, root)?
			.storage_root
			.0
			.into();
	let l2_block_hash = Header::from(&payload.header).hash::<H>();

	let root_claim = calculate_output_root::<H>(
		payload.version,
		payload.header.state_root,
		payload.withdrawal_storage_root,
		l2_block_hash,
	);

	let game_uuid = get_game_uuid::<H>(payload.game_type, root_claim, payload.extra_data);

	let dispute_game_key = derive_map_key::<H>(game_uuid.0.to_vec(), DISPUTE_GAMES_SLOT);

	// Does the dispute game's unique identifier exist in the _disputeGames map?
	let proof_value = match get_value_from_proof::<H>(
		dispute_game_key.0.to_vec(),
		factory_storage_root,
		payload.dispute_game_proof,
	)? {
		Some(value) => value.clone(),
		_ => Err(Error::DisputeGameIdMissing)?,
	};

	let mut encoded_game_id = <alloy_primitives::Bytes as Decodable>::decode(&mut &*proof_value)
		.map_err(|_| Error::DecodeDisputeGameId(format!("{:?}", &proof_value)))?
		.0
		.to_vec();

	let game_id = get_game_id(payload.game_type, payload.timestamp, payload.proxy);
	let game_id_bytes = game_id.to_big_endian();

	// Pad the encoded game id gotten from proof with zeros so it becomes 32 bytes long
	(0..game_id_bytes.len().saturating_sub(encoded_game_id.len()))
		.for_each(|_| encoded_game_id.insert(0, 0));

	// Derived game id must be equal to encoded game id
	if encoded_game_id != game_id_bytes {
		Err(Error::DisputeGameIdMismatch)?
	}

# Fault Dispute Games

The OpStack system finalizes L2 state commitments using fraud proofs in a permissionless manner. Any bonded party can submit an L2 output root as a fault dispute game at any time.
Invalid outputs can be challenged by anyone in a permissionless manner. The challenge process involves both the proposer (who submitted the output root) and the challenger playing a fault dispute game on-chain.
If the challenger wins, the malicious output root is discarded, and the proposer's bond acts as a reward.
Different types of dispute games, defined within the dispute factory contract, can be used for validation, with the specific game determined by the initial submission and respected game types.
Unchallenged outputs are accepted as final after a designated challenge period.
