### Title
Deserialization accepts empty aggregate signatures that verify successfully - (File: crypto/schnorr/src/aggregate.rs)

### Summary

`SchnorrAggregate::read` accepts an aggregate containing zero nonces, even though `SchnorrAggregator::complete` refuses to construct an empty aggregate. If the serialized scalar `s` is zero, `SchnorrAggregate::verify` accepts the resulting signature when supplied with an empty `keys_and_challenges` list. This creates a forged aggregate signature for an empty signer set.

### Finding Description

`SchnorrAggregate::read` reads an attacker-controlled `u32` length and accepts zero encoded `R` values, followed by a scalar `s`. [1](#0-0) 

The ordinary aggregation API explicitly returns `None` when no signatures were aggregated, so an empty `SchnorrAggregate` is not a producible protocol object. [2](#0-1) 

During verification, the code only checks that `self.Rs.len()` equals `keys_and_challenges.len()`. For an empty aggregate and empty key list, this check succeeds. [3](#0-2) 

No per-signature weights or statements are generated for the empty list, and the verifier only evaluates `(-s) * G`. When `s == 0`, that expression is the identity and verification returns `true`. [4](#0-3) 

### Impact Explanation

An attacker can submit a serialized `SchnorrAggregate` with zero `R` values and `s = 0`. Any caller that deserializes it with `SchnorrAggregate::read` and verifies it with an empty `keys_and_challenges` list will accept a signature aggregate that no honest aggregator can produce. This is a signature/proof forgery for the degenerate empty statement set and can bypass authentication or acceptance checks where an aggregate signature is interpreted as proof that the associated statements were signed.

The issue is reachable entirely through untrusted bytes: four zero bytes for the length followed by the canonical encoding of scalar zero. Canonical-scalar deserialization accepts this value through `from_repr`. [5](#0-4) 

### Likelihood Explanation

The attack requires only control over serialized aggregate-signature bytes and a verifier that permits an empty `keys_and_challenges` list. No private key, nonce reuse, malformed point encoding, or secret state is needed. The payload is constant-size and deterministic.

The issue is especially relevant because the production constructor prevents this state, but the deserialization path does not enforce the same invariant. This is analogous to unsafe deserialization admitting an object state that the normal API considers impossible.

### Recommendation

Reject zero-length aggregates during deserialization and again during verification:

- In `SchnorrAggregate::read`, return an error when `u32::from_le_bytes(len) == 0`.
- In `SchnorrAggregate::verify`, return `false` when `self.Rs.is_empty()` or `keys_and_challenges.is_empty()`.
- Consider rejecting zero `s` for empty aggregates defensively, although rejecting empty aggregates is the primary invariant.
- Add a regression test asserting that `00 00 00 00 || F::ZERO.to_repr()` fails to deserialize or verify.

### Proof of Concept

```rust
use schnorr::SchnorrAggregate;
use dalek_ff_group::Ristretto;
use ciphersuite::{Ciphersuite, group::ff::PrimeField};

// Serialized aggregate:
// - u32 little-endian length: 0
// - scalar s: canonical encoding of 0
let mut bytes = Vec::new();
bytes.extend([0u8; 4]);
bytes.extend(<Ristretto as Ciphersuite>::F::ZERO.to_repr().as_ref());

let aggregate =
  SchnorrAggregate::<Ristretto>::read::<&[u8]>(&mut bytes.as_slice()).unwrap();

// Accepted even though SchnorrAggregator::complete() cannot produce
// an aggregate containing no signatures.
assert!(aggregate.verify(b"example domain", &[]));
```
