### Title
Partial CI Check-Status Aggregation Masked as Fully-Fresh Result - ([File: app/src/lib/stores/commit-status-store.ts])

### Summary
`CommitStatusStore.refreshSubscription` aggregates two independent GitHub API sources — legacy commit statuses and modern Check Runs — into a single `ICombinedRefCheck`, and stamps the cache entry with the local fetch time (`fetchedAt: new Date()`) regardless of whether both underlying sources were actually retrieved. This is structurally the same "aggregation of stale/partial feeds masked by a fresh timestamp" pattern described in the report: a derived value is built from multiple sources of different completeness/freshness, but the output is tagged with a timestamp that implies a complete, current result.

### Finding Description
`refreshSubscription` fetches two endpoints concurrently: [1](#0-0) 

If exactly one of the two calls fails (e.g. `fetchRefCheckRuns` returns `null` due to a parse error, rate limit, or malformed/erroring response from a GitHub Enterprise Server or an intercepting proxy), the code silently continues, builds the combined status from only the surviving source, and still records the entry as freshly fetched: [2](#0-1) 

Only the *total* failure case (both `null`) is treated specially and reuses the previous cached value; a *partial* failure (one source present, one silently dropped) is indistinguishable downstream from a fully successful, complete fetch. The `entryIsEligibleForRefresh` staleness gate only looks at `fetchedAt`, not at whether the underlying combination was complete: [3](#0-2) 

`fetchRefCheckRuns` and `fetchCombinedRefStatus` independently swallow errors and return `null` on any failure to parse the response: [4](#0-3) 

Because Check Runs (Actions-based CI) and legacy commit statuses are unioned into one `checks` array before `createCombinedCheckFromChecks` computes the aggregate status/conclusion, dropping one source silently removes an entire class of checks from consideration: [5](#0-4) 

The corrupted value is the derived `ICombinedRefCheck.conclusion`/`status` exposed via `tryGetStatus`/subscription callbacks — it can read as fully "success" or "in progress" while actually representing only half of the real CI signal, and consumers have no way to detect the partial-fetch condition because `fetchedAt` is set to "now" exactly as in a fully successful fetch. [6](#0-5) 

### Impact Explanation
This value drives the PR/commit CI status badge and CI check popover shown to the user (`PullRequestBadge`, `CICheckRunPopover`), and is also consumed by the notifications store (`createCombinedCheckFromChecks` is referenced in `app/src/lib/stores/notifications-store.ts`) that surfaces "checks failed"/"checks succeeded" notifications. A repository whose GitHub Enterprise endpoint or network path is attacker-influenced (a malicious/compromised proxy or GHES instance sitting on the `git remote`/API endpoint path) can cause one of the two parallel API calls to fail while returning a benign result for the other, producing a status/notification that omits real failing Actions checks. This does not itself achieve code execution or credential exfiltration, so this analog only reaches the weaker end of the accepted impact set: it can mislead a user into believing CI is green/complete when it is not, potentially encouraging them to proceed with a merge/push decision based on incomplete information. It does not directly corrupt what is committed/pushed — Desktop does not gate commit/push on this cached value — so the concrete, hard security impact is limited to display/notification integrity rather than a stronger category (execution, exfiltration, IPC escape, or corruption of committed content).

### Likelihood Explanation
Requires the attacker to control or influence responses from one of the two check-status API endpoints for a specific ref while leaving the other endpoint intact — realistic mainly in GitHub Enterprise Server / proxied setups where an adversary controls the network path, but not for github.com itself under normal TLS. Partial failures of one endpoint while the other succeeds are plausible in practice (intermittent 5xx/rate limiting), making the masking behavior reachable through non-malicious conditions as well, but the "attacker-controlled" framing needed to call it a security vulnerability (vs. a reliability bug) requires the GHES/proxy threat model.

### Recommendation
Track partial-fetch state explicitly in `ICommitStatusCacheEntry` (e.g. `complete: boolean` reflecting whether both `statuses` and `checkRuns` were successfully retrieved) instead of only recording `fetchedAt`. When a fetch is partial, either avoid overwriting a previously complete cache entry, keep retrying more aggressively, or surface the incompleteness to UI/notification consumers so they don't treat the derived status as authoritative.

### Proof of Concept
1. Point Desktop at a GitHub Enterprise Server / intercepting proxy under attacker control.
2. For a given ref, have the proxy return a valid `IAPIRefStatus` (`state: success`) from `GET /repos/{owner}/{name}/commits/{ref}/status`, while returning a malformed/invalid body for `GET .../check-runs` so that `parsedResponse` throws inside `fetchRefCheckRuns` and it resolves to `null`. [7](#0-6) 
3. `refreshSubscription` receives `statuses !== null`, `checkRuns === null`; it pushes only the legacy status checks into `checks`, calls `createCombinedCheckFromChecks(checks)` producing a "success" combined check, and caches it with `fetchedAt: new Date()`. [8](#0-7) 
4. Any real Actions Check Run failures for that ref (only obtainable via the poisoned `check-runs` endpoint) never enter `checks`, so the UI (`PullRequestBadge`/`CICheckRunPopover`) and notifications built from this cache display a fully green, "just refreshed" status despite an incomplete/misleading picture of CI health, and this state persists for `BackgroundRefreshInterval` (3 minutes) before another chance to recover the missing data.

/**
 * Returns a value indicating whether or not the cache entry provided
 * should be considered stale enough that a refresh from the API is
 * warranted.

function entryIsEligibleForRefresh(entry: ICommitStatusCacheEntry) {
  // The age (in milliseconds) of the cache entry, i.e. how long it has
  // sat in the cache since last being fetched.
  const now = Date.now()
  const age = now - entry.fetchedAt.valueOf()

  // The GitHub API has a max-age of 60, so no need to refresh
  // any more frequently than that since Chromium would just give
  // us the cached value.
  return age > 60 * 1000
}

export function createCombinedCheckFromChecks(
  checks: ReadonlyArray<IRefCheck>
): ICombinedRefCheck | null {
  if (checks.length === 0) {
    // This case is distinct from when we fail to call the API in
    // that this means there are no checks or statuses so we should
    // clear whatever info we've got for this ref.
    return null
  }

  if (checks.length === 1) {
    // If we've got exactly one check then we can mirror its status
    // and conclusion 1-1 without having to create an aggregate status
    const { status, conclusion } = checks[0]
    return { status, conclusion, checks }
  }

  if (checks.some(isIncompleteOrFailure)) {
    return {
      status: APICheckStatus.Completed,
      conclusion: APICheckConclusion.Failure,
      checks,
    }
  } else if (checks.every(isSuccess)) {
    return {
      status: APICheckStatus.Completed,
      conclusion: APICheckConclusion.Success,
      checks,
    }
  } else {
    return { status: APICheckStatus.InProgress, conclusion: null, checks }
  }
}
