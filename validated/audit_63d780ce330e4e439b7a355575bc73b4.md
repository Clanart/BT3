### Title
UTXO Scheduler underflows `actual - expected` when amortizing branch fees, permanently dropping all queued payments - ([File: processor/src/multisigs/scheduler/utxo.rs](processor/src/multisigs/scheduler/utxo.rs))

### Summary
The Illumination bug class — comparing two amounts expressed in different units/semantic bases so a sanity check can never pass — maps onto `Scheduler::created_output` in Serai's processor. When a transaction creates a "branch" output, the scheduler is told the pre-fee amount it `expected` and the post-fee amount it `actually` received. The code then computes the fee to amortize as `actual - expected`, which is backwards: since fees are always subtracted, `actual < expected` and the subtraction underflows. Every branch output resolution either panics the processor (debug/overflow-checks builds) or silently drops every payment queued under that branch (release builds, where the wrap makes `to_amortize ≈ u64::MAX`), mirroring the "burn X, receive less, check always fails, funds non-redeemable" pattern of the report.

### Finding Description
When a plan has more payments than `N::MAX_OUTPUTS`, `Scheduler::execute` groups the excess payments and replaces them with a single payment to the multisig's own branch address, recording the queue under `queued_plans[expected]` where `expected` is the pre-fee sum of the grouped payments ( [1](#0-0) ).

When the transaction is prepared, `prepare_send` amortizes the transaction fee across payments, and for branch payments emits `PostFeeBranch { expected: initial_amount, actual: post_fee_amount }` — so `actual` is strictly less than `expected` whenever the fee is nonzero ( [2](#0-1) ). `plans_from_block` then forwards these to `scheduler.created_output(expected, actual)` ( [3](#0-2) ).

Inside `created_output`, the payments for `expected` are popped from `queued_plans`, and the fee to amortize is computed as:

```rust
let mut to_amortize = actual - expected;
```

( [4](#0-3) )

`actual` is the amount the output was *actually created with after fees*, so `actual - expected` underflows on every real branch. The subsequent guard `payments.sum() < to_amortize` then becomes trivially true (wrapped value ~`u64::MAX`) and the function `return`s, having already removed the payments from `queued_plans` ( [5](#0-4) ). Because `self.plans` is never populated at key `actual`, when the branch output is later scanned, `can_use_branch` (which checks `self.plans.contains_key(&amount)`) returns false and `add_outputs`'s `plans.get_mut(&amount)` lookup fails, so the output falls back into the generic UTXO pool while its child payments are gone forever ( [6](#0-5) [7](#0-6) ).

This is directly reachable by unprivileged users: any batch of `OutInstruction`s (burns) exceeding `MAX_OUTPUTS` forces `execute` to create branch payments, and fee amortization guarantees `actual < expected` on the created output.

### Impact Explanation
- In builds with overflow checks enabled, `actual - expected` panics inside `plans_from_block`/`prepare_send` handling, crashing the processor — a persistent liveness failure triggered by ordinary batched payouts.
- In release builds, the wrap causes an early `return` that permanently drops the queued child payments. The branch output's coins remain in the scheduler's `utxos`, but the burns they were supposed to satisfy are never executed — users' funds are stuck in vault custody, the same "funds burned but never delivered" impact as the Illuminate finding.

### Likelihood Explanation
The trigger is entirely deterministic: any nonzero fee makes `actual < expected`, and any plan with more than `MAX_OUTPUTS` payments produces a branch. High-volume payout periods (many burns in one batch) hit this on every branch resolution, not in an edge case.

### Recommendation
Compute the amortizable fee as `expected - actual` (saturating) at `processor/src/multisigs/scheduler/utxo.rs:485`:

```rust
let mut to_amortize = expected - actual;
```

Optionally use `checked_sub`/`saturating_sub` and assert `actual <= expected` to fail loudly if the invariant is ever violated. Add a regression test that calls `created_output` with `actual < expected` and verifies child payments are queued under `plans[actual]`.

### Proof of Concept
1. An unprivileged user submits `MAX_OUTPUTS + k` burn instructions for a UTXO-backed coin (e.g., Bitcoin).
2. `Scheduler::execute` drains the excess `k` payments into `queued_plans[expected]` and inserts a branch payment of `expected` sats ( [8](#0-7) ).
3. `prepare_send` amortizes `tx_fee` across payments; the branch payment is reduced, yielding `PostFeeBranch { expected, actual: Some(expected - fee_share) }` ( [2](#0-1) ).
4. `created_output(expected, actual)` computes `to_amortize = actual - expected` → underflow → panic (checked builds) or wrapped-huge value → `payments.sum() < to_amortize` → early `return` after `queued_plans` was already popped ( [9](#0-8) ).
5. The branch output lands on chain with `actual` sats; `plans` has no entry at `actual`, so `can_use_branch` is false, the output is parked as a generic UTXO, and the `k` child payments are irrecoverably dropped — burns reported complete upstream are never paid out.

Uncertainty note: whether a deployed processor build panics or silently drops payments depends on `overflow-checks` in its release profile, which was not inspectable here; under either configuration the outcome (crash vs. permanent payment loss) satisfies High severity.

```rust
  pub fn created_output<D: Db>(
    &mut self,
    txn: &mut D::Transaction<'_>,
    expected: u64,
    actual: Option<u64>,
  ) {
    log::debug!("output expected to have {} had {:?} after fees", expected, actual);

    // Get the payments this output is expected to handle
    let queued = self.queued_plans.get_mut(&expected).unwrap();
    let mut payments = queued.pop_front().unwrap();
    assert_eq!(expected, payments.iter().map(|payment| payment.balance.amount.0).sum::<u64>());
    // If this was the last set of payments at this amount, remove it
    if queued.is_empty() {
      self.queued_plans.remove(&expected);
    }

    // If we didn't actually create this output, return, dropping the child payments
    let Some(actual) = actual else { return };

    // Amortize the fee amongst all payments underneath this branch
    {
      let mut to_amortize = actual - expected;
      // If the payments are worth less than this fee we need to amortize, return, dropping them
      if payments.iter().map(|payment| payment.balance.amount.0).sum::<u64>() < to_amortize {
        return;
      }
      while to_amortize != 0 {
        let payments_len = u64::try_from(payments.len()).unwrap();
        let per_payment = to_amortize / payments_len;
        let mut overage = to_amortize % payments_len;

        for payment in &mut payments {
          let to_subtract = per_payment + overage;
          // Only subtract the overage once
          overage = 0;

          let subtractable = payment.balance.amount.0.min(to_subtract);
          to_amortize -= subtractable;
          payment.balance.amount.0 -= subtractable;
        }
      }
    }
```
