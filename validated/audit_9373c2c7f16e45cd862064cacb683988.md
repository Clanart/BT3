### Title
Silent Git remote hijack via reused `[ownerID+name]` identity in GitHubRepository upsert - ([File: app/src/lib/stores/repositories-store.ts])

### Summary
Desktop's local `GitHubRepository` records (used to auto-repair `origin`/`upstream` remote URLs) are keyed by the mutable tuple `[ownerID, name]` rather than GitHub's immutable numeric repository id. When a tracked repository is renamed away and its old `owner/name` slot is later reused by an unrelated (attacker-controlled) repository, the next background API refresh silently overwrites the stored `cloneURL` for the *old* record, and Desktop's auto-remote-repair code then rewrites the user's real git remote to point at the attacker's repository — with no user confirmation.

### Finding Description
`_upsertGitHubRepository` looks up an existing DB record purely by owner id + repo name: [1](#0-0) 
and if found, overwrites its `cloneURL`, `htmlURL`, `parentID`, etc. with whatever the API currently reports for that owner/name pair: [2](#0-1) 
Nowhere in `updatedGitHubRepo` is GitHub's immutable numeric repository id persisted or compared — only the owner id (itself derived from a login string via `putOwner`) and the repo name: [3](#0-2) 

Downstream, this record's `cloneURL` is trusted to silently rewrite the user's actual git remotes without confirmation:
- `updateRemoteUrl` auto-sets the default remote to the API's `clone_url` whenever it detects the "GitHub url changed": [4](#0-3) 
- `updateExistingUpstreamRemote`/`addUpstreamRemoteIfNeeded` set the `upstream` remote to `parent.cloneURL` from the same kind of record: [5](#0-4) [6](#0-5) 

If the tracked repository (or its fork "parent") is renamed/deleted on GitHub, and the freed `owner/name` combination is later reoccupied by a different repository (e.g. via account rename/recreation, or a different repo being created at the freed name under the same owner login string), the *next* API sync (which happens routinely as part of background repository refresh, PR loading, or fork/parent resolution) will match the stale local record by `[ownerID+name]` and overwrite its `cloneURL` with the new, unrelated repository's clone URL — with no re-validation that the underlying repository is the same one the user originally cloned. `setRemoteURL`/`updateExistingUpstreamRemote` then apply that URL directly to the local git remote: [7](#0-6) 

No guard in this path checks the GitHub API's immutable numeric repository `id` before treating the "same" owner+name as the "same" repository.

### Impact Explanation
This lets an attacker who can control (or manipulate the naming lifecycle of) a GitHub repository/GitHub API object cause Desktop to silently repoint a victim's `origin` or `upstream` remote to an attacker-owned repository. Because the user is never prompted, subsequent `git push` operations will silently push code/tags to the attacker's repository (data/IP leakage, and potential credential exposure to the attacker's remote via HTTPS auth headers), and subsequent `fetch`/`pull` will bring in attacker-controlled commits merged into the user's working tree — corrupting what the user believes they are collaborating on. This matches the "silent corruption of what the user commits or pushes" and "GitHub API object" attacker-control categories in scope.

### Likelihood Explanation
The trigger only requires an attacker to control (or race to reclaim) a `login/name` slot vacated by a legitimate rename/deletion — no local access, no malware, and no unusual user action beyond having previously added/forked the affected repository in Desktop, which then periodically refreshes GitHub metadata in the background. The window of opportunity depends on the victim (or GitHub owner) renaming/deleting a repo, which is a normal, attacker-observable GitHub event, making this moderately likely for a targeted attack against active fork/PR relationships.

### Recommendation
Persist and compare GitHub's immutable numeric repository `id` (and owner `id`) from the API response in `IDatabaseGitHubRepository`, and only reuse/overwrite an existing local record when that immutable id matches. If the id differs for the same `owner/name` key, treat it as a new repository (create a new record) rather than silently mutating the old one, and require explicit user confirmation before automatically changing `origin`/`upstream` remote URLs (similar to the existing `UpstreamAlreadyExists` confirmation dialog) whenever the underlying repository identity has changed.

### Proof of Concept
1. Victim adds/forks `github.com/alice/project` in Desktop; Desktop stores a `GitHubRepository` row keyed by `[ownerID(alice), "project"]` with `cloneURL = https://github.com/alice/project`.
2. Alice renames her GitHub account (or deletes/renames `project`), freeing the `alice/project` slot.
3. Attacker (having anticipated or triggered this) claims the `alice` login and/or creates a new repository named `project` under that reclaimed identity.
4. Victim's Desktop performs a routine background refresh (e.g., PR list load, fork parent resolution) that calls `upsertGitHubRepository`/`upsertGitHubRepositoryLight` with the API's current data for `alice/project`, which now describes the attacker's repository.
5. `_upsertGitHubRepository` matches the existing DB row by `[ownerID+name]` (`app/src/lib/stores/repositories-store.ts:613-616`) and overwrites `cloneURL` with the attacker's repo's clone URL.
6. On the next `_updateExistingUpstreamRemote` (or `updateRemoteUrl` auto-fix), Desktop calls `setRemoteURL` (`app/src/lib/git/remote.ts:56-64`) and silently repoints the victim's local `origin`/`upstream` remote at the attacker's repository, with no dialog shown to the user.

  private async putOwner(
    endpoint: string,
    login: string,
    ownerType?: GitHubAccountType
  ): Promise<Owner> {
    const key = getOwnerKey(endpoint, login)
    const existingOwner = await this.db.owners.get({ key })
    let id

    // Since we look up the owner based on a key which is the product of the
    // lowercased endpoint and login we know that we've found our match but it's
    // possible that the case differs (i.e we found `usera` but the actual login
    // is `userA`). In that case we want to update our database to persist the
    // login with the proper case.
    if (
      existingOwner === undefined ||
      existingOwner.login !== login ||
      // This is added so that we update existing owners with an undefined type.
      (ownerType !== undefined && existingOwner.type !== ownerType)
    ) {
      id = existingOwner?.id
      const existingId = id !== undefined ? { id } : {}
      id = await this.db.owners.put({
        ...existingId,
        key,
        endpoint,
        login,
        type: ownerType,
      })
    } else {
      id = forceUnwrap('Missing owner id', existingOwner.id)
    }

    return new Owner(login, endpoint, id, ownerType ?? existingOwner?.type)
  }

   * Add the upstream remote if the repository is a fork and an upstream remote
   * doesn't already exist.

  public async addUpstreamRemoteIfNeeded(): Promise<void> {
    const parent =
      this.repository.gitHubRepository &&
      this.repository.gitHubRepository.parent
    if (!parent) {
      return
    }

    const remotes = await getRemotes(this.repository)
    const upstream = findUpstreamRemote(parent, remotes)
    if (upstream) {
      return
    }

    const remoteWithUpstreamName = remotes.find(
      r => r.name === UpstreamRemoteName
    )
    if (remoteWithUpstreamName) {
      const error = new UpstreamAlreadyExistsError(
        this.repository,
        remoteWithUpstreamName
      )
      this.emitError(error)
      return
    }

    const url = forceUnwrap(
      'Parent repositories are fully loaded',
      parent.cloneURL
    )

    this._upstreamRemote =
      (await this.performFailableOperation(() =>
        addRemote(this.repository, UpstreamRemoteName, url)
      )) ?? null
  }
