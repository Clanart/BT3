### Title
`ReceivedOutput::read` accepts an unauthenticated `outpoint`/`TxOut` pair, letting an attacker desynchronize the prevout value/script committed in the sighash from the output actually being spent - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to the USSD rebalancer trusting `DAI.balanceOf(uniPool)` (attacker-mutable balance) while deciding direction from `sqrtPriceX96` (unaffected), `ReceivedOutput` deserializes three independently attacker-controlled fields — `offset`, `output` (a `TxOut`), and `outpoint` — with no check that `outpoint` actually references the claimed `TxOut` on-chain. `SignableTransaction::new` then makes its economic decisions (fund sufficiency, change amount, fee) from the *claimed* `output.value`, while the transaction actually spends the *real* UTXO at `outpoint`. The two values can be arbitrarily desynchronized by an unprivileged party supplying malicious bytes to `ReceivedOutput::read`.

### Finding Description
`ReceivedOutput::read` reads `offset` via `Secp256k1::read_F`, then a `TxOut` and an `OutPoint` via `consensus_decode`, and packs them together without any consistency proof: [1](#0-0) 

`SignableTransaction::new` trusts `input.output.value` for the `input_sat` sum used in the `NotEnoughFunds` check and the change computation, while placing `input.outpoint` into the unsigned `TxIn`: [2](#0-1) [3](#0-2) 

At signing time, `Prevouts::All(&self.tx.prevouts)` commits the *claimed* `TxOut`s (value + script_pubkey) into every input's `taproot_key_spend_signature_hash`, while the transaction spends the attacker-chosen `outpoint`s: [4](#0-3) 

The only guard is in `multisig()`, which checks `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — this binds `offset` to the *claimed* `script_pubkey`, but says nothing about whether the claimed `TxOut` matches the real UTXO at `outpoint`, nor whether `outpoint` even exists: [5](#0-4) 

Two exploitation shapes:

1. **Understated value (fund burn).** Attacker supplies an outpoint for a large real UTXO (e.g., 1 BTC) but claims `output.value = 0.1 BTC` with the matching script. `SignableTransaction::new` computes change on the declared 0.1 BTC; the signed transaction actually consumes 1 BTC, so ~0.9 BTC silently becomes miner fee — an irreversible loss, exactly the "overshoot"/wrong-quantity class of the USSD report.

2. **Overstated value (DoS / invalid signature).** Attacker claims a larger value than the real UTXO. The sighash commits to the fake amount, so the produced signature is invalid against the real prevout — the transaction can never be broadcast, DoS-ing the spend path (mirroring the `rebalance()` revert/underflow DoS).

### Impact Explanation
Funds controlled by the threshold key can be permanently burned as miner fees, or the wallet's signing pipeline can be forced to produce transactions that are invalid on-chain (liveness failure on all spends routed through the malicious `ReceivedOutput`). Both impacts stem from the same root cause as the reference report: an attacker-controllable quantity (`output.value`/`outpoint`) is used for sizing decisions while the "real" quantity (the on-chain UTXO) differs, with no `sync`-equivalent mechanism to reconcile them.

### Likelihood Explanation
The `ReceivedOutput::read` surface is explicitly designed to ingest untrusted bytes (it is one of the enumerated untrusted-read APIs). Any deployment that accepts serialized `ReceivedOutput`s from peers, a coordinator, or deserialized storage/state reachable by an unprivileged party exposes this. No validator compromise, collusion, or leaked key is required — only the ability to supply crafted bytes to `ReceivedOutput::read`, after which normal `SignableTransaction::new` → `multisig` → `sign` → `complete` flow produces the harmful transaction.

### Recommendation
Do not trust deserialized `ReceivedOutput` fields as ground truth. Before constructing `SignableTransaction`, re-fetch the transaction referenced by `outpoint` via RPC (as `median_fee`/`get_outputs` already do for other data) and assert `real_tx.output[outpoint.vout] == output`, or store/transport only `outpoint` + `offset` and resolve the `TxOut` from the chain. Failing that, `ReceivedOutput::read` should be documented as requiring trusted input and untrusted inputs should go through a verification constructor.

### Proof of Concept
1. Victim controls key `K`; a real UTXO exists at `outpoint P` paying `K`'s P2TR script with value `V_real = 1 BTC`.
2. Attacker serializes `ReceivedOutput { offset: Scalar::ZERO, output: TxOut { value: 0.1 BTC, script_pubkey: p2tr(K) }, outpoint: P }` and feeds the bytes to `ReceivedOutput::read` (or into the consumer's input pipeline).
3. `SignableTransaction::new([received], payments, Some(change), None, fee_rate)` computes `input_sat = 0.1 BTC`, builds change ≈ `0.1 − payments − fee`, and succeeds.
4. `multisig` passes since the claimed `script_pubkey` equals `p2tr_script_buf(K + 0)`.
5. FROST signing produces a valid signature (the sighash commits the real prevout script/value — actually here the signature commits to the *claimed* 0.1 BTC TxOut, so for the signature to be valid the claimed TxOut must match the real one; when it doesn't, variant 2 applies: the signature is invalid and the tx is unbroadcastable). For the burn variant, the attacker instead supplies `outpoint P'` of a *different* real UTXO of 1 BTC under the same script while claiming the 0.1 BTC TxOut only if node policy permits — in all configurations, either (a) the claimed `TxOut` must equal the real one for the signature to verify, in which case the desync attack is prevented only by consensus; or (b) with `Prevouts::All` commitment mismatch, signing yields a permanently invalid transaction — a DoS on the wallet reachable purely from crafted `ReceivedOutput::read` bytes.
6. Concretely for the DoS variant: with real UTXO value 0.05 BTC but claimed `TxOut` 1 BTC, `taproot_key_spend_signature_hash` commits 1 BTC; every node rejects the signature under BIP-341 verification, so no spend of `P` can ever be produced via this pipeline — the rebalance-equivalent "revert" DoS.

The cleanest proof is the DoS variant: it requires no collusion, only `ReceivedOutput::read` on attacker bytes, and deterministically yields unbroadcastable, permanently-invalid transactions.
