### Title
Unvalidated Mirror URL in DataLayer Enables Server-Side Request Forgery Against Nodes Subscribing to a Store - (File: chia/data_layer/download_data.py)

### Summary
DataLayer mirror URLs are attacker-controlled data published on-chain by any wallet user who owns a DataLayer singleton (via `create_new_mirror`/`dl_new_mirror`), and any other node that subscribes to that store id will have its `DataLayer` service automatically fetch data from that URL with no validation of scheme, host, or destination, allowing SSRF against the victim node's local/internal network.

### Finding Description
A DataLayer store owner can register mirror URLs for their store through the wallet RPC path (`create_new_mirror` in `chia/data_layer/data_layer_wallet.py`, exposed via `dl_new_mirror`). These URLs are committed on-chain as part of the mirror coin data and are not restricted to any particular scheme or destination — no allowlist, no rejection of loopback/link-local/private ranges, and no scheme restriction is applied anywhere in the mirror creation or storage path.

Any third-party node operator who chooses to subscribe to that store id (a normal, unprivileged DataLayer client action) will have their local `DataLayer.periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()` loop pull the subscribed store's server list via `self.data_store.get_available_servers_for_store()` [1](#0-0)  and issue outbound HTTP requests to whatever URL is stored there:

```
url = server_info.url
...
success = await insert_from_delta_file(
    ...
    server_info=server_info,
    downloader=await self.get_downloader(store_id, url),
    ...
)
``` [2](#0-1) 

When no plugin downloader claims the URL, `insert_from_delta_file` falls through to the plain HTTP path via `download_file`, which calls `http_download`, performing an unrestricted `aiohttp` GET against `server_info.url + "/" + filename` with no host/scheme validation:
```
async with session.get(
    server_info.url + "/" + filename,
    headers=headers,
    timeout=timeout,
    proxy=proxy_url,
) as resp:
``` [3](#0-2) 

The only content-level check performed is on the *response* (filename convention, hash/root verification), not on the destination itself; the request is issued before any of that validation occurs. The `.cursor/context/data-layer.md` documentation for this module explicitly confirms mirror URLs are treated as untrusted external input, only the *downloaded data* is validated against the wallet-advertised root — the destination host itself is never checked: "Mirror URLs, plugins, or static file names as trusted data sources" are called out as a "Wrong Assumption," and "Plugin and mirror URLs are external trust inputs" is listed as a fragility hotspot [4](#0-3) [5](#0-4) .

This means a store owner (an unprivileged wallet user who merely creates a DataLayer singleton and publishes a mirror record on-chain) fully controls a URL that every other node choosing to sync/subscribe to that store will contact automatically and periodically, with no restriction preventing `http://127.0.0.1:<port>/...`, `http://169.254.169.254/...`, or other internal/link-local targets.

### Impact Explanation
This is a genuine SSRF: an attacker publishes a malicious mirror URL for a public DataLayer store (something victims are encouraged to subscribe to for legitimate reasons, e.g., following a public dataset), and every subscriber's local `DataLayer` service will issue outbound HTTP requests to attacker-chosen destinations, including internal-only services (cloud metadata endpoints, other local ports, internal admin interfaces) reachable from the victim's machine/network. Because the request path constructs `server_info.url + "/" + filename`, an attacker can also influence the resulting request path/target via the URL value itself. This is a confidentiality/integrity-impacting network-reachable bug consistent with the CVE's bug class (missing input validation on a URL field feeding an outbound fetch), though it operates client-side (on nodes that voluntarily subscribe) rather than through an authenticated admin endpoint.

### Likelihood Explanation
Likelihood is moderate-to-high in normal DataLayer usage: subscribing to third-party stores is the DataLayer's core intended workflow, and the periodic sync loop (`periodically_manage_data`) will automatically and repeatedly attempt fetches from any registered mirror without operator interaction once a subscription exists. No special node privileges beyond running `chia data_layer` with an active subscription are required, and the malicious mirror publisher only needs normal DataLayer wallet-user capability to create a store and register a mirror.

### Recommendation
Validate and restrict mirror URLs at both creation time (reject malformed/dangerous schemes) and, more importantly, at fetch time in `http_download`/`download_file`/`fetch_and_validate`: enforce an allowed scheme set (e.g., `http`/`https` only, explicitly reject `file://`), and resolve/deny requests targeting loopback, link-local, and private address ranges unless explicitly opted into by the node operator (similar to typical SSRF mitigations: DNS resolution + IP-range checks before connecting, disabling redirects to disallowed destinations).

### Proof of Concept
1. As an unprivileged DataLayer/wallet user, create a DataLayer store and call `create_new_mirror` (`dl_new_mirror` RPC) with `urls=["http://127.0.0.1:8080/internal-admin"]` (or an internal/link-local address reachable from a target node's network) and push the transaction on-chain.
2. Wait for/entice a victim operator to run `chia data_layer` and subscribe to the malicious store id (`dl_track_new` / subscription flow) — a normal, expected DataLayer client action for consuming public datasets.
3. On the victim node, `periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()` reads the malicious mirror record from `get_available_servers_for_store()` [6](#0-5)  and calls `insert_from_delta_file`, which calls `download_file` → `http_download`, causing the victim's node process to issue an outbound HTTP GET to `http://127.0.0.1:8080/internal-admin/<filename>` [7](#0-6) .
4. Observe on the victim's internal service that the DataLayer process made the request, confirming SSRF against internal infrastructure triggered purely by an attacker-controlled on-chain mirror URL.
