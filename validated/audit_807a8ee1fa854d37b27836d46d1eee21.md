## Analysis: unchecked ERC-20 return value in Tron IntentGatewayV2 `withdraw()`

The external report's core defect is: a token operation returns `false` instead of reverting, the contract only checks that the low-level `call` itself didn't revert, and then permanently commits state (listing/marking as filled) as if the token movement succeeded — silently losing/locking funds.

### Local analog

The Solidity/EVM mainline of the intents system (`evm/src/apps/intentsv2/IntentsBase.sol`) correctly uses OpenZeppelin's `safeTransfer`, which decodes and checks the ERC-20 return value: [1](#0-0) 

However, the Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, reimplements this logic manually and drops the return-value check — it only verifies that the low-level `.call` succeeded, not that the ERC-20's returned boolean is `true`: [2](#0-1) 

The same unchecked pattern is repeated for `SweepDust`: [3](#0-2) 

### Finding Description

`withdraw()` is invoked from `onAccept` (for `RedeemEscrow`/`RefundEscrow` request kinds) and from `onGetResponse` for cross-chain cancellation verification. It performs, per token:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();

_orders[body.commitment][token] -= amount;
```

`success` only reflects whether the external call reverted at the EVM/TVM level — it does not decode/verify the ABI-encoded boolean that `IERC20.transfer` returns. Any token implementation that returns `false` on failure instead of reverting (a well-known pattern for a number of real-world ERC-20/TRC-20 tokens) will cause `success == true` while no tokens are actually transferred. The function nevertheless proceeds to decrement the escrow accounting (`_orders[...] -= amount`) and, at the top of the function, unconditionally marks the order as finalized: `_filled[body.commitment] = beneficiary`.

### Impact Explanation

Because `_filled` is set and escrow decremented regardless of whether the transfer actually delivered funds, the beneficiary's escrowed tokens are permanently zeroed out in accounting terms while the tokens themselves remain stuck in the `IntentGatewayV2` contract. Since `_filled[commitment]` is used elsewhere as the one-time-settlement guard, there is no way to retry or re-trigger delivery of those funds — this is a direct, unrecoverable loss of escrowed user funds, matching the bounty's "loss of funds" / "false state acceptance" impact class.

### Likelihood Explanation

This does not require a malicious peer, relayer, or admin — it is triggered purely by using (or a filler/user picking) a spec-noncompliant or non-standard ERC-20/TRC-20 token as an input/output asset, which is common in production deployments. Any ordinary `RedeemEscrow`/`RefundEscrow` settlement or dust sweep involving such a token silently loses funds.

### Recommendation

Replace the raw `token.call(...)` + `success`-only check pattern in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `safeTransfer` (as already done correctly in the EVM mainline `IntentsBase._withdraw`), which decodes and validates the boolean return value and reverts on failure, ensuring escrow accounting and the `_filled` finalization only occur once tokens are confirmed delivered.

### Proof of Concept

1. User places an order whose input/output token is an ERC-20 that returns `false` on a failed `transfer` (rather than reverting) — e.g., due to an internal blacklist/pause check that doesn't revert.
2. Order is filled/refunded, triggering `onAccept`/`onGetResponse` → `withdraw(body, isRefund)`.
3. Inside `withdraw`, `token.call(...)` succeeds at the call level (`success == true`) even though the token's internal logic returned `false` and moved no funds.
4. `_orders[body.commitment][token] -= amount` zeroes escrow accounting; `_filled[body.commitment] = beneficiary` finalizes the order.
5. Beneficiary never receives the tokens, and the escrow can never be revisited since the commitment is already marked filled — funds are permanently stuck in the gateway contract.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
