### Title
Fee and weight estimates in `SignableTransaction::new` omit the OP_RETURN data output actually included in the transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the `getlzFee()` finding (estimate computed over an encoding missing a field present in the real payload), `SignableTransaction::new` computes the transaction weight, vbytes, and therefore `needed_fee` via `calculate_weight_vbytes(tx_ins.len(), payments, ...)` using only the payment outputs. The OP_RETURN output carrying the user-supplied `data` (up to 80 bytes) is pushed onto `tx_outs` beforehand but is never included in the estimate — and is never added to `payments`, so even the `Some(&change)` recompute omits it.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` appends the OP_RETURN output to the actual transaction's output list at lines 194-202. However, the initial estimate at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds a mock transaction whose outputs are derived solely from `payments` (lines 85-93). The data output's weight (~34 + data_len bytes) is absent from `weight`, `vbytes`, and `needed_fee`. The subsequent change-branch estimate at lines 225-226 also passes `payments`, again excluding the OP_RETURN output, so `fee_with_change` and the change amount are likewise computed against an understated vsize. Finally, the `MAX_STANDARD_TX_WEIGHT` check at line 241 uses this undercounted `weight`.

### Impact Explanation
The transaction actually broadcast is larger than estimated:
- `needed_fee` is understated, so `fee()` (sum(inputs) − sum(outputs)) results in a realized fee rate below the caller-specified `fee_per_vbyte`, and possibly below `DEFAULT_MIN_RELAY_TX_FEE` in edge cases, causing the transaction to fail relay/be stuck — directly paralleling the "bridge transaction fails" consequence of the report.
- The change output absorbs the discrepancy (change = inputs − payments − fee_with_change, where fee_with_change is too small), so the wallet silently pays a lower effective rate than requested, or the min-relay check passes on a false vbytes.
- A transaction near the standardness limit can pass the `TooLargeTransaction` check while actually exceeding `MAX_STANDARD_TX_WEIGHT`, producing an unspendable/unrelayable signed transaction.

### Likelihood Explanation
Deterministic and triggered by any caller supplying `data` — e.g., every Serai Bitcoin processor transaction that attaches the required OP_RETURN metadata. No attacker sophistication needed; the estimate is wrong on every `data.is_some()` invocation.

### Recommendation
Include the OP_RETURN output in the weight estimate. Either pass the fully-constructed `tx_outs` (payments + data) into `calculate_weight_vbytes`, or add `data` as a parameter so the mock transaction includes `TxOut { value: Amount::ZERO, script_pubkey: op_return_script }` in both the no-change and with-change estimates. Recompute the change branch over outputs that include the data output.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// In SignableTransaction::new:
let data = vec![0u8; 80];
let tx = SignableTransaction::new(inputs, &payments, Some(change), Some(data.clone()), 10).unwrap();

// Actual vbytes exceeds the estimated vbytes used for needed_fee:
// tx.transaction().vsize() includes the ~91-weight-unit OP_RETURN output,
// while needed_fee was computed from payments-only vbytes (line 204).
// Therefore tx.fee() / actual_vbytes < fee_per_vbyte requested.
```
Relevant code: `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })` at `networks/bitcoin/src/wallet/send.rs:194-202`, versus the estimate `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204 and the mock output set built only from `payments` at lines 85-93.
