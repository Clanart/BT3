## Analysis

**Binding claimed broken:** `attribution_operator_xonly_pk` (stored via `update_payout_txs_and_payer_operator_xonly_pk`) is defined to equal `parse(OP_RETURN of the transaction that the honest funding operator broadcast)`. The question asks whether this equality instead resolves to `parse(OP_RETURN of whichever conflicting transaction wins the block, regardless of funder identity)`.

**Root cause: the OP_RETURN and second output are outside the signed digest.**

`create_payout_txhandler` builds input 0 as a `KeySpend` spent with the *user's* signature, while outputs 1 (anchor) and 2 (OP_RETURN with the operator's key) are added by whichever party assembles/funds the transaction: [1](#0-0) 

`Operator::withdraw` explicitly requires (and only checks) a `SIGHASH_SINGLE|ANYONECANPAY`-style signature from the user: [2](#0-1) 

`SIGHASH_SINGLE|ANYONECANPAY` commits **only** to input 0 and output 0. Outputs 1 (anchor) and 2 (OP_RETURN) — plus any additional funding inputs added via `fund_raw_transaction`'s `add_inputs: Some(true)` — are unauthenticated by that signature: [3](#0-2) 

**Attribution is derived purely from whatever transaction is observed on-chain spending the withdrawal outpoint**, with no binding back to a specific broadcaster or pre-registered txid: [4](#0-3) [5](#0-4) 

That attribution is then relied upon by `is_kickoff_malicious` to decide whether the operator submitting a kickoff is legitimate: [6](#0-5) 

**Exploit flow:** Once the honest operator broadcasts its fully-funded payout transaction (mempool-visible, or observable via Bitcoin P2P), any unprivileged party can extract input 0's witness (the reusable user signature) and output 0 (fixed by the signature), then assemble a new transaction with: the same input 0 + witness, the same output 0, but its own funding input(s) and an arbitrary/omitted OP_RETURN. Because none of the existing guards (`SECP.verify_schnorr`, `is_profitable`, `only_aggregator_and_self`, DB writes) execute on raw Bitcoin broadcasts outside Clementine's gRPC layer, nothing prevents this variant from being relayed and mined first at a higher feerate — a plain double-spend race, no RBF signal needed. Whichever variant confirms becomes the sole source `update_finalized_payouts` reads for attribution, per the join above.

**Consequence:** if the attacker's variant confirms, the real funding operator's OP_RETURN is gone; `operator_xonly_pk` in DB becomes `None` or mismatched, so `is_kickoff_malicious` returns `true` for the honest operator's later kickoff — the honest operator is treated as malicious even though it genuinely fronted the withdrawal, matching the listed Critical impacts ("an honest operator permanently unable to be reimbursed" / "an honest operator's collateral burned" via the resulting challenge path).

**Caveat on feasibility/cost:** output 0 (amount + script pubkey to the withdrawing user) is fixed by the signature and cannot be altered by the attacker, so the attacker must supply their own funding inputs covering the full withdrawal payout amount to the user's address to make their conflicting variant valid — this is not a cheap griefing attack; it requires the attacker to actually pay out the withdrawal amount themselves.

### Title
Payout attribution is bound to whichever conflicting tx confirms first, not to the honest funder, due to `SIGHASH_SINGLE|ANYONECANPAY` leaving OP_RETURN/anchor unauthenticated - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` signs the payout tx's input 0 and output 0 only (`SIGHASH_SINGLE|ANYONECANPAY`), leaving the anchor output and the attribution-critical OP_RETURN output completely unauthenticated. `update_finalized_payouts` attributes a payout to an operator purely by parsing the OP_RETURN of whatever transaction is later observed spending the withdrawal UTXO on-chain, so any party who can extract the reusable user signature (visible once the honest operator broadcasts) can craft and get confirmed a higher-fee conflicting variant with a different or missing OP_RETURN, hijacking the ATTRIBUTION binding.

### Finding Description
Binding under test: `withdrawals.payout_payer_operator_xonly_pk` (post-confirmation) == `xonly_pk committed by the honest funding operator's OP_RETURN` (`core/src/builder/transaction/operator_reimburse.rs:418`). Tracing shows this equality is not enforced: `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) simply joins on whichever `bitcoin_syncer_spent_utxos` row spent `withdrawal_utxo_txid/vout`, and `update_finalized_payouts` (`core/src/verifier.rs:2298-2343`) parses the OP_RETURN of that confirmed transaction with no check that it originated from the operator who actually funded output 0.

Because `Operator::withdraw` requires only a `SIGHASH_SINGLE|ANYONECANPAY` user signature over input 0/output 0 (`core/src/operator.rs:630-637`), any additional funding input and outputs 1–2 (anchor, OP_RETURN) added by `fund_raw_transaction`'s `add_inputs: Some(true)` (`core/src/operator.rs:652-674`) are unauthenticated. Once the honest operator's tx is visible in the mempool/P2P network, an unprivileged party can reuse input 0 + its witness + output 0 verbatim in their own transaction, attach their own higher-fee-paying input(s) covering the payout amount, and set an arbitrary/absent OP_RETURN. This is a plain conflicting-transaction race at the Bitcoin layer entirely outside Clementine's gRPC surface, so `SECP.verify_schnorr`, `is_profitable`, `only_aggregator_and_self` and DB uniqueness constraints never see or block it.

### Impact Explanation
If the attacker's variant confirms first, `payout_payer_operator_xonly_pk` becomes `None` or an unrelated key. `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1871-1890`) then flags the honest operator's legitimate kickoff as malicious, since the DB attribution no longer matches `kickoff_data.operator_xonly_pk`. This can leave the honest operator permanently unable to be reimbursed and can trigger the challenge path burning that operator's collateral — both Critical-severity outcomes. The attack is repeatable against any pending payout the attacker can observe before confirmation, across any deposit/operator.

### Likelihood Explanation
The attacker needs no protocol key, only: (1) visibility into the honest operator's broadcast payout tx (mempool or direct P2P relay), and (2) enough BTC to fund a conflicting transaction that still fully pays output 0 (the withdrawal amount) plus a higher fee than the honest tx, since output 0's amount/script are fixed by the signed digest. This makes the attack costly (attacker must front the same payout amount) but not otherwise gated by any privilege, key, or authentication — a purely economic/timing race, feasible for any well-funded party who wants to grief a specific operator or the protocol.

### Recommendation
Bind the OP_RETURN (and ideally all outputs) to the same signature that authorizes the spend, e.g., have the user (or the protocol) sign with `SIGHASH_ALL` or otherwise commit to the operator's xonly pubkey and full output set at payout-construction time, so a conflicting transaction with a different OP_RETURN cannot reuse the same witness. Alternatively, record the honest operator's intended payout txid/OP_RETURN in the DB at broadcast time (before confirmation) and reject/ignore confirmed transactions whose OP_RETURN diverges from that pre-registered commitment when attributing payouts.

### Proof of Concept
1. Set up a regtest bridge with one operator and one pending withdrawal, following the existing `full_flow.rs`/`deposit_and_withdraw_e2e.rs` harness structure.
2. Have the operator construct and sign the payout tx via `create_payout_txhandler`/`Operator::withdraw` normally (low feerate), and broadcast it (do not mine).
3. Extract input 0 (outpoint + witness containing the user's `SIGHASH_SINGLE|ANYONECANPAY` signature) and output 0 from the honest tx.
4. As the "attacker," build a new transaction reusing that input+witness and output 0 verbatim, add an attacker-funded input, and attach a different/omitted OP_RETURN; broadcast at a higher feerate.
5. Mine one block.
6. Assert: the attacker's txid, not the honest operator's, is the one recorded in `bitcoin_syncer_spent_utxos`/`withdrawals.payout_txid` after `update_finalized_payouts` runs, and assert `payout_payer_operator_xonly_pk` is `None`/mismatched, causing a subsequent `is_kickoff_malicious` check on the honest operator's real kickoff to return `true`.
