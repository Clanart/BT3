### Title
Unbounded recursive RLP decoding of `AccountKeyRoleBased` allows stack-overflow DoS via a single crafted `AccountUpdate` transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each embedded key by calling `NewAccountKeySerializer()` / `rlp.DecodeBytes` on every element without ever checking whether that element's type is itself `AccountKeyTypeRoleBased`. Because `AccountKeySerializer.DecodeRLP` simply dispatches on the declared `keyType` and blindly calls `s.Decode(serializer.key)`, an attacker can craft an `AccountKey` byte blob that nests `AccountKeyRoleBased` inside itself many thousands of times. Decoding such a blob — which happens automatically whenever any `TxTypeAccountUpdate` / `TxTypeFeeDelegatedAccountUpdate*` transaction is received via RPC, p2p, or the tx pool — recurses into `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` ... with no depth limit, exhausting the goroutine stack before any semantic validation (`CheckInstallable`, which does reject nested composite keys) ever runs.

### Finding Description
The composite-type restriction that forbids a `RoleBased` key from containing another `RoleBased` key exists only at *validation* time: [1](#0-0) 

This check (`IsCompositeType()` rejection, returning `kerrors.ErrNestedCompositeType`) is invoked from `CheckInstallable`/`CheckUpdatable`, which run only after the transaction has already been fully RLP-decoded and is being processed by the state transition / account-update logic.

However, decoding itself is unbounded and recursive: [2](#0-1) 

`AccountKeyRoleBased.DecodeRLP` reads a list of RLP-encoded key blobs, and for each one calls `NewAccountKeySerializer()` followed by `rlp.DecodeBytes(b, &serializer)`. That in turn invokes: [3](#0-2) 

`AccountKeySerializer.DecodeRLP` reads the declared `keyType`, calls `NewAccountKey(serializer.keyType)` (which for `AccountKeyTypeRoleBased` returns a fresh `*AccountKeyRoleBased`, per `blockchain/types/accountkey/account_key.go:97-114`), and then calls `s.Decode(serializer.key)` — which re-enters `AccountKeyRoleBased.DecodeRLP` if the nested type is again `RoleBased`. There is no recursion-depth counter, no nesting check, and no restriction preventing `keyType == AccountKeyTypeRoleBased` from appearing as an element inside another `AccountKeyRoleBased`'s encoded list during decode.

This decoding path is reached unconditionally whenever a `TxTypeAccountUpdate`, `TxTypeFeeDelegatedAccountUpdate`, or `TxTypeFeeDelegatedAccountUpdateWithRatio` transaction's `Key`/`KeyData` field is decoded, e.g.: [4](#0-3) 

and identically for the JSON-based ingestion path (`eth_sendRawTransaction`-adjacent RPC unmarshalling / `UnmarshalJSON`): [5](#0-4) 

This is directly analogous to the Elasticsearch `_search` API bug: a specially crafted, deeply nested input structure (there, a query DSL; here, a nested `AccountKeyRoleBased` blob) is parsed by a recursive-descent decoder with no depth limit, driving the call stack to overflow and crashing/DoS'ing the process before any semantic validation is applied.

### Impact Explanation
Any unprivileged party who can submit a transaction (via `eth_sendRawTransaction`, p2p transaction propagation, or inclusion in a block/bundle) can trigger unbounded recursion in `AccountKeyRoleBased.DecodeRLP` purely by constructing a suitably nested key blob for an `AccountUpdate`-family transaction. Because decoding happens as part of basic transaction ingestion (before mempool validation/signature checks reject it on other grounds), this can crash or exhaust the goroutine stack of any node that decodes the transaction — including full nodes relaying it and validator/CN nodes processing it — leading to a Denial of Service. Per the scan rules this is a Medium severity availability impact reachable from a single submitted transaction, matching the intent of CVE-2023-31419 (`AC:L`, `PR:L`... `A:H`, no confidentiality/integrity impact).

### Likelihood Explanation
The likelihood is high for any node that decodes the RLP or JSON of an `AccountUpdate` transaction containing a maliciously nested `AccountKeyRoleBased` key: no special privileges, prior state, or ordering are required — a single, self-contained crafted transaction payload is sufficient to reach the vulnerable decode path. The recursive dispatch (`AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `NewAccountKey`/`s.Decode`) contains no depth guard, so nesting depth is bounded only by the size of the transaction payload the attacker is willing/able to submit (subject to whatever max tx-size / RLP size limits exist elsewhere in the stack, which were not confirmed in this investigation to specifically bound `AccountKeyRoleBased` nesting depth).

### Recommendation
Add an explicit nesting/depth check in `AccountKeyRoleBased.DecodeRLP` (and in `AccountKeyRoleBased.UnmarshalJSON`, `blockchain/types/accountkey/account_key_role_based.go:150-162`, which has the same issue) that rejects any element whose decoded `keyType` is `AccountKeyTypeRoleBased` (or, more generally, `IsCompositeType()==true`) immediately upon decode, before recursing further — mirroring the existing `CheckInstallable`/`CheckUpdatable` restriction but enforced at decode time rather than only at validation time. Alternatively, introduce and enforce an explicit maximum recursion-depth parameter threaded through `DecodeRLP`/`UnmarshalJSON`.

### Proof of Concept
Conceptually (exact byte construction not verified against a live node in this investigation, since no runtime/tooling access was available):
1. Construct an `AccountKeySerializer`-encoded blob `K0` for `AccountKeyTypeNil` or another leaf key type.
2. Construct `K1 = RLP([keyType=AccountKeyTypeRoleBased, RLP([K0])])`.
3. Repeat: `Ki = RLP([keyType=AccountKeyTypeRoleBased, RLP([K(i-1)])])` for a large N (e.g., tens of thousands of levels), producing deeply nested key bytes.
4. Embed `KN` as the `Key`/`KeyData` field of a `TxTypeAccountUpdate` transaction, sign it with a valid dummy key (or intercept it before signature validation depending on which decode path is hit first), and submit via `eth_sendRawTransaction` or p2p transaction broadcast.
5. Upon RLP decoding of the transaction (`TxInternalDataAccountUpdate.fromSerializable` → `accountkey.NewAccountKeySerializer()` → `rlp.DecodeBytes` → `AccountKeyRoleBased.DecodeRLP`), the recursive chain executes N times without a depth check, exhausting the goroutine's stack and crashing/panicking the receiving node's process — occurring before `CheckInstallable`'s `IsCompositeType()` guard is ever reached.

Because tool access to execute or step through this proof of concept against the running node was unavailable, the exact minimum nesting depth required to trigger a crash (bounded by Go's default growable goroutine stack limit, typically up to ~1GB) was not empirically verified.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
