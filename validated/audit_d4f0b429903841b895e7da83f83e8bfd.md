### Title
Unlocking a portion of vlMGP forfeits and permanently burns already-earned rewards accrued while fully locked - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder._calExpireForfeit` computes the forfeiture on a user's *entire* pending reward balance using only the user's *current* lock/cool-down snapshot (`vlMGP.getRewardablePercentWAD`), rather than accounting for the state that actually existed while each portion of the reward accrued. This causes rewards honestly earned while a user was 100% locked to be retroactively and permanently forfeited to other stakers simply because the user later starts an unlock on a portion of their MGP before claiming - mirroring the Taiko bug class where a "correct" position's bond/reward is wrongly burned because reward accounting fails to account for history.

### Finding Description
Rewards accrue continuously via `rewardPerToken` and are captured into `userRewards[token][account]` whenever `_updateFor`/`updateRewards` runs [1](#0-0) . This pending balance is not tagged with when it was earned or what fraction of the user's stake was locked vs. in cool-down at each accrual point.

When the user actually claims (`getReward`/`getRewards` -> `_sendReward`), the contract forfeits a portion of the *entire* pending `userRewards` amount based solely on the account's **current** `getRewardablePercentWAD` [2](#0-1) [3](#0-2) .

`getRewardablePercentWAD` in `VLMGP.sol` computes the ratio purely from the account's present lock/cool-down slots at `block.timestamp`, with no concept of how long the accrued-but-unclaimed reward has been outstanding or what the lock state was during that period [4](#0-3) .

Concretely: a user can be fully locked for a long reward-accrual period, entitled to 100% of `userRewards`. If, before claiming, they call `startUnlock` for even a small amount of their MGP (a fully permitted, unprivileged action) [5](#0-4) , then at the moment of claim `getRewardablePercentWAD` will compute a lower "rewardable" percentage that blends the locked/cool-down ratio present *today*, and applies that reduced percentage to the *entire* historical `userRewards` balance - not just to the reward accrued after the cool-down began. The forfeited portion is not returned to the user; it is permanently redistributed into the reward pool via `_queueNewRewardsWithoutTransfer` [6](#0-5) , i.e., burned from the user's perspective and given to other stakers. The identical pattern also exists in `rewards/mWOMSVBaseRewarder.sol` (`_calExpireForfeit`/`_sendReward`).

This is the same root cause as the Taiko finding: reward/bond outcome is determined only by the *latest* observed state (current lock status) rather than the history of what was true when the reward/bond was actually earned, causing correct/honest positions to be incorrectly slashed.

### Impact Explanation
An honest, unprivileged user permanently loses a portion of rewards they legitimately and fully earned while 100% locked, purely as a side effect of initiating a partial, otherwise-permitted unlock before claiming. The lost amount is not recoverable by the user - it is redistributed to the reward pool for other stakers, constituting a permanent, protocol-level misappropriation/freezing of the user's already-earned, unclaimed yield. This can affect any staker interacting normally with `startUnlock` + delayed claim, and the magnitude scales with reward accrued and time between last claim and the unlock action.

### Likelihood Explanation
High likelihood: `startUnlock` and `getReward`/`getRewards` are ordinary, frequently used user-facing functions [5](#0-4) [7](#0-6) . Any user who does not claim immediately before starting an unlock (a very common workflow, since `startUnlock` itself triggers a `multiclaimFor` call but subsequent reward accrual before the user does another explicit claim, or reward tokens not included in that multiclaim call's rewards array, remain exposed) will suffer the loss. No special conditions, timing races, or privileged actions are required.

### Recommendation
Track forfeiture per accrual period instead of applying today's lock ratio to the entire historical pending balance. Options:
- Snapshot/checkpoint `userRewards` at the time state changes (e.g., on `startUnlock`, `cancelUnlock`, `unlock`), applying the forfeiture calculation incrementally to only the newly accrued rewards since the last checkpoint, so previously-earned rewards computed while fully locked are settled and not subject to a later lower ratio.
- Alternatively, weight the forfeiture calculation by the time-weighted average of `getRewardablePercentWAD` over the exact interval each unit of reward accrued, rather than only the snapshot at claim time.

### Proof of Concept
1. User locks MGP into `VLMGP` and remains fully locked (no unlocking) for a substantial period, accruing `userRewards[token][user]` at 100% rewardable ratio (`getRewardablePercentWAD` = 1e18 while `getUserAmountInCoolDown == 0`, see `VLMGP.sol:193-199`).
2. Before calling `getReward`, the user calls `startUnlock(smallAmount)` for a small fraction of their locked MGP (`VLMGP.sol:275-311`). This creates a cool-down slot, immediately lowering `getRewardablePercentWAD(user)` because `inCoolDown > 0` at `VLMGP.sol:193-215`.
3. The user then calls `getReward`, which computes `_sendReward` -> `_calExpireForfeit(_account, userRewards[token][account])` using the now-lower `getRewardablePercentWAD` from step 2, applied to the *entire* previously accrued `userRewards` balance (`vlMGPBaseRewarder.sol:363-376, 386-400`).
4. A portion of the reward that was earned entirely during the fully-locked period is forfeited and permanently sent to `_queueNewRewardsWithoutTransfer`, redistributing it to other stakers instead of the rightful earner - with no way for the affected user to reclaim it.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
