### Title
Odd group keys are tweaked with the negated TapTweak, making canonical Taproot outputs undetectable and unspendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`tweak_keys` applies the TapTweak scalar to an odd internal key before negating the complete result. BIP-341 requires first normalizing the internal key to its even-Y representative and then adding the tweak. For an odd group key `P`, the implementation produces `-P - tG` instead of the required `-P + tG`.

Any output sent to the canonical Taproot key for an odd `P` is not recognized by `Scanner` and cannot be signed by the corresponding `ThresholdKeys`.

### Finding Description

In `networks/bitcoin/src/wallet/mod.rs`, `tweak_keys` computes the TapTweak from the x-coordinate of `keys.group_key()`, applies it with `keys.offset(...)`, checks the parity of the already-tweaked key, and then negates the entire result if it is odd.

For an original group key `P` with odd Y:

1. BIP-341 lifts the x-only key to `P_even = -P`.
2. The correct output key is:
   `Q = P_even + TapTweakHash(x(P)) * G = -P + tG`
3. The implementation calculates:
   `Q_bad = -(P + tG) = -P - tG`

These keys differ by `2tG`. Consequently:

- `Scanner::new` and `Scanner::register_offset` index `p2tr_script_buf(Q_bad)`, not the canonical `p2tr_script_buf(Q)`.
- `SignableTransaction::multisig` rejects a canonical prevout because it requires `p2tr_script_buf(offset.group_key()) == prevout.script_pubkey`.
- The transformed threshold secret is `-(x + t)`, while the canonical output requires `-x + t`.

This affects every threshold group key whose point initially has odd Y, which occurs for approximately half of all keys.

### Impact Explanation

A Bitcoin transaction can send funds to the canonical BIP-341 Taproot output derived from Serai's group key while Serai's wallet scans for the incorrectly tweaked key. The wallet does not report the deposit as its output, and `SignableTransaction::multisig` cannot produce signatures for that prevout with the transformed keys.

This causes funds expected to be controlled by the threshold key to become undetectable and unspendable through the normal wallet path.

### Likelihood Explanation

The condition is reached whenever the generated threshold group key has odd Y. This is an ordinary, high-probability property of a randomly generated secp256k1 point rather than an exceptional edge case. An unprivileged sender can create the affected condition by paying to the canonical Taproot output derived from the published internal group key.

### Recommendation

Normalize the group key to even Y before applying the TapTweak. Conceptually, the flow should be:

1. If `group_key` is odd, scale the threshold keys by `-1`.
2. Compute the TapTweak from the normalized key's x-only encoding.
3. Apply that scalar with `offset`.
4. Ensure the final tweaked key has even Y.

The implementation should also add vectors covering both even and odd original group keys and assert equality with the BIP-341 output key.

### Proof of Concept

Let the original secret be `x`, with `P = xG` having odd Y, and let:

```text
t = TapTweakHash(x(P))
```

The implementation performs:

```rust
// networks/bitcoin/src/wallet/mod.rs
keys.offset(t).scale(-1)
```

This produces:

```text
secret_bad = -(x + t)
Q_bad      = secret_bad * G
           = -P - tG
```

BIP-341 instead requires the odd internal key to be lifted before tweaking:

```text
P_even     = -P
secret_std = -x + t
Q_std      = secret_std * G
           = -P + tG
```

For nonzero `t`:

```text
Q_bad != Q_std
```

`Scanner::new(Q_bad)` only indexes the incorrect script, while `SignableTransaction::multisig` requires the transformed key's script to equal the prevout's `script_pubkey`. A prevout paying `Q_std` therefore fails the equality check and cannot be spent by these threshold keys.
