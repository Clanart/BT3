### Title
`lockFor` in `VLMGP.sol` / `mWomSV.sol` allows locking tokens on behalf of the zero address, permanently freezing them - (File: `VLMGP.sol`, `wombat/mWomSV.sol`)

### Summary
`VLMGP.lockFor(uint256 _amount, address _for)` and `mWomSV.lockFor(uint256 _amount, address _for)` let any caller lock MGP/mWom tokens "for" an arbitrary `_for` address without validating that `_for != address(0)`. If `_for` is `address(0)`, the locked balance is permanently credited to the zero address in `MasterMagpie`, and since no one controls `address(0)`, the locked tokens can never be unlocked or withdrawn.

### Finding Description
`lockFor` forwards directly to the internal `_lock` function, pulling tokens from `msg.sender` and crediting the position to `_for` with no zero-address check: [1](#0-0) [2](#0-1) 

The same pattern exists in `mWomSV.sol`: [3](#0-2) [4](#0-3) 

Both call into `MasterMagpie.depositVlMGPFor` / `depositMWomSVFor`, which only enforce the `_onlyVlMgp` / `_onlyMWomSV` caller-restriction modifier and perform no validation of the `_for` address before crediting `UserInfo`: [5](#0-4) 

All subsequent unlock flows (`startUnlock`, `unlock`, `cancelUnlock`, `forceUnLock`) in both `VLMGP.sol` and `mWomSV.sol` operate exclusively on `msg.sender`'s slots (e.g. `userUnlockings[msg.sender]`), so no address other than `_for` itself can ever unlock a position credited to it. Since nobody holds the private key to `address(0)`, MGP/mWom locked "for" the zero address becomes permanently inaccessible.

### Impact Explanation
Any ordinary wallet calling `lockFor(_amount, address(0))` causes the transferred MGP or mWom tokens to be irrecoverably locked in the protocol, since the corresponding lock position and unlock rights are bound to `address(0)`, which cannot submit transactions. This is a permanent freezing of funds, matching the accepted impact criteria.

### Likelihood Explanation
The bug is reachable by any unprivileged wallet through a single, unrestricted external call (`lockFor`) with no special preconditions, similar to the analog report's `transferPosition` call to `address(0)`. While likely triggered accidentally (fat-fingering `_for`), it can also be triggered deliberately, and the outcome (funds stuck forever) is identical in class to the referenced finding.

### Recommendation
Add a zero-address check on `_for` in `lockFor` (and analogous `_for`-parameterized entry points such as `MasterMagpie.depositVlMGPFor`/`depositMWomSVFor`), reverting with an existing `InvalidAddress` error when `_for == address(0)`.

### Proof of Concept
1. User approves `VLMGP` (or `mWomSV`) to spend MGP (or mWom).
2. User calls `lockFor(amount, address(0))`.
3. `_lock` transfers `amount` tokens from the user into the contract and calls `MasterMagpie.depositVlMGPFor(amount, address(0))`, crediting `UserInfo[stakingToken][address(0)]`.
4. No caller can ever invoke `startUnlock`/`unlock` for `address(0)` (these operate on `msg.sender` only), so the locked tokens remain stuck in the contract permanently.
