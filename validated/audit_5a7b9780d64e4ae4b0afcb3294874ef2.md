Confirmed: this is a directly reachable, unprivileged-transaction path.

- Any tokenfactory denom creator is the denom's admin by default, and can permissionlessly call `MsgSetDenomMetadata` to change the denom's `decimals` (via `DenomUnits[].Exponent`) at any time, gated only by `authorityMetadata.Admin == msg.Sender` [1](#0-0) . There is no restriction preventing a denom's decimals from changing after the denom already has EVM integrations built on top of it.
- Any EVM caller can invoke the `pointer` precompile's `addNativePointer(token)` at address `0x100b` to (re)provision an ERC20 pointer contract for a native/tokenfactory denom, with no ownership/authorization check beyond basic call-context checks [2](#0-1) .
- When a pointer already exists for that denom, `UpsertERCPointer` does **not** create a new contract — it redeploys/overwrites the **same contract address**'s bytecode with the current metadata pulled from bank denom metadata at call time [3](#0-2) .
- This is explicitly proven by `TestUpsertERCNativePointer`, which re-upserts the same pointer denom and changes `Decimals` from `6` to `12`, with the resulting contract at the **same address** now returning `decimals() == 12` [4](#0-3) .

This is exactly the bug class from the report: a critical token property (`decimals`, analogous to `rewardToken`/its decimals in the dForce report) is mutated mid-flight, at an address that other unrelated contracts/integrations already trust and have cached/depend on, without any check that the new value is congruent with the old one, and without disabling the update path once the pointer is already in active use.

### Title
Permissionless decimals mutation of an already-integrated ERC20 native pointer via `addNativePointer` upsert - (File: x/evm/keeper/pointer_upgrade.go)

### Summary
The EVM `pointer` precompile's `addNativePointer` method allows anyone to re-invoke pointer creation for an existing native-token ERC20 pointer. Instead of failing when a pointer already exists, `Keeper.UpsertERCPointer` silently redeploys new bytecode onto the exact same contract address, using whatever `decimals`/name/symbol the tokenfactory admin currently has set in bank denom metadata. Since tokenfactory denom admins can change a denom's decimals at will via `MsgSetDenomMetadata`, and any user can then trigger the pointer's bytecode to be replaced in place via `addNativePointer`, the `decimals()` return value of a live, previously-integrated ERC20 contract can change underneath any downstream consumer (AMMs, lending markets, price oracles, off-chain integrators) without their knowledge or consent.

### Finding Description
- `PrecompileExecutor.AddNative` (the handler for `addNativePointer`) reads the denom's current bank metadata and calls `k.UpsertERCNativePointer`, with no check for whether a pointer already exists and, if so, whether its metadata is unchanged [2](#0-1) .
- `UpsertERCPointer` looks up the existing pointer address; if found, it calls `evm.GetDeploymentCode` with the *current* constructor args and overwrites the contract's code in place via `k.SetCode(writeCtx, contractAddr, ret)`, keeping the same `contractAddr` [3](#0-2) .
- Older precompile versions (e.g. `v552`, `v555`, `v562`) explicitly rejected re-registration attempts once a pointer of version ≥1 existed (`"pointer at %s with version %d exists..."`) [5](#0-4) , but this safety check was removed starting from `v575`/`v580` onward and is absent from the current `precompiles/pointer/pointer.go` and `UpsertERCPointer` [6](#0-5) .
- The metadata driving the redeploy comes from `bankKeeper.GetDenomMetaData`, which for tokenfactory denoms is entirely admin-controlled via `MsgSetDenomMetadata`, gated only by an admin check, not by any decimals-immutability rule [1](#0-0) .
- `TestUpsertERCNativePointer` proves the effect: after upserting once with `Decimals: 6`, a second upsert call with `Decimals: 12` returns the *same* contract address but the on-chain `decimals()` query now returns `12` [4](#0-3) .

### Impact Explanation
Any EVM/CosmWasm-facing protocol that integrates with a native-token pointer (lending markets computing collateral value via `10**decimals()`, AMMs normalizing reserves, price oracles caching decimals) implicitly assumes an ERC20's `decimals()` is immutable, per ERC20 conventions. A sudden decimals change at a live, already-integrated contract address can cause a 10^n-order miscalculation in any protocol that cached or assumes constant decimals, leading to under/over-valuation of collateral, incorrect swap math, or oracle price misreads — all of which can result in direct fund loss (e.g. draining an under-collateralized loan, or extracting value from an AMM pool via decimal-based mispricing), matching the fund-loss criterion for accepted findings.

### Likelihood Explanation
High. The precondition is only that: (1) the token is a tokenfactory denom whose admin controls its own metadata (a normal, common configuration, since creators are admins by default), and (2) any user calls the permissionless `addNativePointer` precompile method again after a metadata change. No governance, no validator collusion, and no special privileges are required — an ordinary denom admin plus an ordinary EVM transaction sender working together (or even the admin alone, since anyone can trigger the redeploy) is sufficient.

### Recommendation
Reinstate the "reject re-registration of an existing pointer" behavior that existed in earlier precompile versions (`v552`–`v562`), or at minimum enforce that `UpsertERCPointer` fails (rather than silently redeploying) if a pointer already exists and the new metadata's `decimals` (and ideally name/symbol) differ from those already deployed. Any legitimate metadata correction should go through a gated/governance path rather than being permissionlessly triggerable by any EVM caller who observes an admin-side metadata change.

### Proof of Concept
1. Tokenfactory admin creates denom `factory/{admin}/tok` and calls `addNativePointer("factory/{admin}/tok")` via the pointer precompile; bank metadata reports `decimals = 6`; pointer ERC20 is deployed at address `P` with `decimals() == 6`.
2. A lending protocol on Sei EVM integrates `P` as a collateral asset, reading `decimals()` once and caching `6` for value-normalization math.
3. The tokenfactory admin calls `MsgSetDenomMetadata` for `factory/{admin}/tok`, changing the `DenomUnits[].Exponent` to `18` [1](#0-0) .
4. Any user calls `addNativePointer("factory/{admin}/tok")` again on the pointer precompile. `UpsertERCPointer` finds the existing pointer at `P` and overwrites its bytecode in place using the new `decimals = 18` [7](#0-6) ; `P.decimals()` now returns `18`, exactly as demonstrated by `TestUpsertERCNativePointer` [4](#0-3) .
5. The lending protocol, still using its cached `decimals = 6` (or re-reading `decimals()` mid-transaction and getting `18`), computes collateral value off by `10**12`, enabling massive over-borrowing/drain of the protocol's other assets.

func (k *Keeper) UpsertERCPointer(
	ctx sdk.Context, evm *vm.EVM, typ string, args []interface{}, getter PointerGetter, setter PointerSetter,
) (contractAddr common.Address, err error) {
	pointee := args[0].(string)
	evmModuleAddress := k.GetEVMAddressOrDefault(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName))

	var bin []byte
	bin, err = artifacts.GetParsedABI(typ).Pack("", args...)
	if err != nil {
		panic(err)
	}
	bin = append(artifacts.GetBin(typ), bin...)
	// GetDeploymentCode / Create take EVM snapshots that Freeze() Multistore layers.
	// Exists-lookup and commits must use the live unfrozen top (sdb.Ctx): cachekv
	// forbids writing a frozen layer, and same-tx readers that skip frozen-empty
	// parents would miss those writes. The precompile Prepare `ctx` is that top at
	// Prepare time, but is frozen once this Upsert snapshots. Always attach the
	// caller's gas meter (finite precompile meter in deliver) — sdb.Ctx() alone
	// carries the infinite EVM meter.
	sdb := state.GetDBImpl(evm.StateDB)
	liveCtx := func() sdk.Context {
		if sdb == nil {
			return ctx
		}
		return sdb.Ctx().WithGasMeter(ctx.GasMeter())
	}
	existingAddr, _, exists := getter(liveCtx(), pointee)
	suppliedGas := k.getEvmGasLimitFromCtx(ctx)
	var remainingGas uint64
	if exists {
		var ret []byte
		contractAddr = existingAddr
		ret, remainingGas, err = evm.GetDeploymentCode(evmModuleAddress, bin, suppliedGas, utils.Big0, existingAddr)
		if err != nil {
			return
		}
		// Only write on success: a failed GetDeploymentCode can leave ret as nil or
		// revert data, which must not clobber live pointer bytecode (even transiently).
		writeCtx := liveCtx()
		k.SetCode(writeCtx, contractAddr, ret)
		if sdb != nil {
			sdb.RefreshCodeCache(contractAddr, ret)
		}
	} else {
		_, contractAddr, remainingGas, err = evm.Create(evmModuleAddress, bin, suppliedGas, uint256.NewInt(0))
	}
	if err != nil {
		return
	}
	ctx.GasMeter().ConsumeGas(k.GetCosmosGasLimitFromEVMGas(ctx, suppliedGas-remainingGas), "ERC pointer deployment")
	if err = setter(liveCtx(), pointee, contractAddr); err != nil {
