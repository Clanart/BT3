### Title
Untrusted `ReceivedOutput` bytes can fabricate spendable Bitcoin UTXOs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes an offset, `TxOut`, and `OutPoint` without proving that the outpoint actually contains the declared output or that the output came from `Scanner`. `SignableTransaction::new` subsequently treats that deserialized object as a spendable input, while `multisig` validates only the claimed previous output’s script against the offset-derived key. This is analogous to the ownership-loss flaw: crossing the serialization boundary reconstructs a privileged object from caller-supplied metadata rather than preserving or re-establishing its authoritative provenance.

### Finding Description
`ReceivedOutput` combines the scalar needed to derive the spending key, the presumed previous output, and the claimed outpoint. `read` parses all three fields independently and immediately returns a `ReceivedOutput`; it performs no scanner authentication or chain consistency check. The object’s `value` API then reports the attacker-controlled `TxOut` amount. When the result is passed to `SignableTransaction::new`, the claimed `OutPoint` becomes the transaction input and the claimed `TxOut` becomes the committed prevout. `SignableTransaction::multisig` checks that the supplied `TxOut` script matches the key derived from the supplied offset, but it does not and cannot check that the `OutPoint` resolves to that `TxOut`. ### Impact Explanation
An attacker who can supply serialized `ReceivedOutput` bytes can cause the caller to record or report funds as received when no corresponding spendable UTXO exists. Because the fake `TxOut` can intentionally match the offset-derived Taproot key, `SignableTransaction::multisig` accepts the input and creates a signing machine for it. The resulting Bitcoin transaction is not validly spendable if its claimed outpoint is nonexistent or resolves to a different output, despite the in-memory wallet path treating the deserialized object as owned and spendable. This maps to the accepted impact category of funds reported received that are not spendable.

### Likelihood Explanation
The attacker only needs to reach an API or persistence boundary that accepts serialized `ReceivedOutput` bytes; no validator compromise, malicious peer model, key disclosure, or collusion is required. They can choose an offset and construct a `TxOut` under the corresponding known public key, then pair it with an arbitrary `OutPoint`. The attack depends on an integrator treating `ReceivedOutput::read` as suitable for untrusted input rather than exclusively as an authenticated local serialization format.

### Recommendation
Do not expose `ReceivedOutput::read` as a way to authenticate spendable wallet state. Treat deserialized outputs as unverified hints and re-scan or query the referenced outpoint before marking funds received or constructing a `SignableTransaction`. Preferably make construction private to `Scanner`, or add an authenticated database/network boundary that preserves the scanner’s provenance. At minimum, document and enforce that callers must verify the resolved prevout equals `ReceivedOutput.output()` before use.

### Proof of Concept
Conceptually, an attacker serializes a zero or otherwise chosen scalar, a `TxOut` whose script corresponds to `base_key + G * offset`, and an arbitrary or nonexistent `OutPoint`:

```rust
// Constructed by the attacker; shown as a byte-level recipe.
let offset = Scalar::ZERO;
let fake_prevout = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: p2tr_script_buf(victim_or_controlled_key).unwrap(),
};
let fake_outpoint = OutPoint::new(nonexistent_txid, 0);

let mut bytes = offset.to_bytes().to_vec();
bytes.extend(serialize(&fake_prevout));
bytes.extend(serialize(&fake_outpoint));

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
```

The fake output satisfies the script consistency check in `SignableTransaction::multisig`, while its fake `OutPoint` is placed into the Bitcoin transaction input. The wallet therefore accepts the fabricated object as spendable even though the claimed funds may not exist on-chain.
