Stale line-index reuse in partial-commit patch generation allows attacker-controlled working-directory content to be silently committed against the user's actual review/selection - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop's partial-staging ("select individual lines to commit") feature stores the user's line selection as a set of *positional indices* (`DiffSelection`) tied to a specific rendering of the file's diff, but re-computes the diff **again**, independently, at the moment it builds the `git apply --cached` patch. Because matching is purely positional (`hunk.unifiedDiffStart + lineIndex`) rather than content-based, if the on-disk file changes between the time the user reviews/selects lines and the time Desktop stages the commit, the stale indices get silently reinterpreted against the new diff, causing the wrong lines (attacker/tool-modified content) to be included in or excluded from the commit without any warning to the user.

### Finding Description
The commit flow is:

1. User opens a file in the Changes view; Desktop computes a diff and renders hunks. The user makes a line-level selection, which `DiffSelection` stores as absolute line indices diverging from a default (all/none) selection state [1](#0-0) .
2. When the diff is reloaded while displayed, Desktop tries to keep the selection valid, but only by re-mapping *by index*, not by content: `selectableLines.add(h.unifiedDiffStart + index)` [2](#0-1) . The comment even acknowledges the limitation: "The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines."
3. When the user clicks Commit, `_commitIncludedChanges` takes the **currently cached** `WorkingDirectoryFileChange` objects (with their stored `selection`) from `state.changesState.workingDirectory.files` and passes them straight to `createCommit` [3](#0-2) .
4. `createCommit` → `stageFiles` → `applyPatchToIndex` for any partially-selected file [4](#0-3) [5](#0-4) .
5. `applyPatchToIndex` re-fetches the diff **fresh from disk at this moment** — a third, independent `git diff` invocation, unrelated to whatever the user actually looked at: `const diff = await getWorkingDirectoryDiff(repository, file)` [6](#0-5) .
6. `formatPatch` then walks this brand-new diff's hunks and decides which lines to include using `file.selection.isSelected(absoluteIndex)` — purely a positional index lookup against the stale `DiffSelection`, with no verification that line `absoluteIndex` still represents the same content the user selected [7](#0-6) .

The broken invariant: the value used to build the actual patch applied to the index (which lines get committed) is derived from **mutable, attacker/tool-influenced on-disk state re-sampled at execution time**, matched against a selection that was validated (loosely, by index only) against an earlier snapshot of that same mutable state. Nothing re-verifies that the selection is still semantically valid for the diff sampled in `apply.ts` right before staging.

### Impact Explanation
If the working-directory file is modified between the moment the user makes their line-level selection (which can be an arbitrary amount of time — while they type a commit message, review other files, etc.) and the moment they click Commit — e.g., by a file-watcher-driven build/format tool, an editor autosave, a `git` smudge/clean filter, or content written by a script/CI tool running against the checked-out repo — the positional-index selection is silently reapplied to a different diff. This can cause:
- Lines the user explicitly deselected (deliberately excluded, e.g. secrets, debug code, or malicious injected content) to be silently included in the commit, or
- Lines the user intended to include to be silently dropped,

with no re-confirmation dialog, warning, or diff re-display before the commit is finalized. This is a "silent corruption of what the user commits" scenario, matching a valid Desktop impact class, since the resulting commit content diverges from the reviewed/approved intent without any indication to the user.

### Likelihood Explanation
This requires only that the working tree be modified (by any process — editor, build tool, background formatter, or hostile content originating from a cloned/fetched repository via hooks or generated files) in the window between line-selection and commit — no elevated privileges, no local/physical access beyond normal usage, and no unnatural user steps. Given how common auto-save, on-save formatters, and background watchers are in developer environments, and that Desktop's own partial-selection UX encourages leaving files selected while composing a commit message, this window is realistically hit. The existing guard (`selectableLines` reconciliation in `app-store.ts`) only reduces (but does not eliminate) risk, and only while the diff panel is actively being viewed/reloaded — it does not run again immediately before `applyPatchToIndex` samples its own independent diff.

### Recommendation
- Capture and reuse a single diff snapshot (content-addressed, e.g., by hashing the diff or file blob) from selection-time through commit-time, instead of re-fetching a fresh diff in `applyPatchToIndex`.
- Before calling `git apply --cached`, verify that the file's current on-disk diff matches the diff the selection was built against (e.g., by comparing hunk content/hash, not just positional indices); if it has changed, abort the partial commit for that file and force the user to re-review/re-select.
- Consider matching selected lines by content-anchored identity (line text + surrounding context) rather than raw absolute index, to make the corruption failure mode fail loudly rather than silently.

### Proof of Concept
1. In Desktop, modify a tracked file with two independent regions of changes (hunk A and hunk B).
2. Select only hunk A's lines for partial commit; leave hunk B unselected.
3. While the commit message box is still open (before clicking "Commit"), have an external process (e.g., a save-on-focus-loss formatter, a script, or content controlled by a malicious `post-checkout`/`smudge` filter from a cloned repo) rewrite the file so that hunk B's added lines now occupy the same line-index range hunk A previously occupied (e.g., by inserting/removing lines earlier in the file causing a shift, or by directly editing near-identical regions).
4. Click "Commit". Observe via `git show` that the resulting commit's diff does not match what was visually selected in step 2 — content from the newly written region (positionally aligned with the old selected indices) is included instead of/along with the originally selected hunk A content, because `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-diffed the file after the external modification and `formatPatch` (`app/src/lib/patch-formatter.ts:157`) matched the stale `DiffSelection` indices against the new hunk layout.
