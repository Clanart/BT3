### Title
`SignableTransaction::new` computes weight/fee/change without the OP_RETURN data output - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` builds the transaction's outputs from `payments` plus an optional `OP_RETURN` data output, yet calculates the transaction weight, required fee, and change amount using only `payments`. This is the same bug class as the referenced finding — the wrong quantity (payment outputs instead of the actual output set) is used in an accounting update — and it causes the declared fee/change to diverge from the transaction actually signed.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202`, the `data` OP_RETURN output is pushed onto `tx_outs` (up to 80 bytes of payload, ~90 serialized bytes). However, at `send.rs:204` and `send.rs:226`, `calculate_weight_vbytes` is invoked with `payments` — not `tx_outs` — and `calculate_weight_vbytes` (lines 62-99) reconstructs the transaction solely from `payments` plus optional `change`. The OP_RETURN output is therefore excluded from `weight`/`vbytes` even though it is included in the final `Transaction` (lines 246-251).

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` undercounts by ~`90 * fee_per_vbyte` sats when `data` is present.
2. The minimum-relay-fee check at line 211 compares against an understated `vbytes`, so a transaction can pass `TooLowFee` while its true feerate is below `DEFAULT_MIN_RELAY_TX_FEE`.
3. The change output value (`input_sat - payment_sat - fee_with_change`, lines 228-230) is computed against the understated fee, so `SignableTransaction::fee()` (lines 138-141) returns a value inconsistent with the requested rate — the real fee equals the intended fee, but spread over a larger transaction, i.e., the actual sat/vbyte rate is lower than `fee_per_vbyte`.

### Impact Explanation
The threshold multisig signs and broadcasts a Bitcoin transaction whose effective feerate is strictly lower than requested whenever an OP_RETURN `data` payload is included. In the worst case the true feerate falls below the minimum relay feerate, producing a transaction that passes all of Serai's validation yet cannot be relayed or confirmed — funds committed to its inputs are unspendable until reconstructed, and any burn/settlement operation depending on it stalls. Even when relayable, the bridge systematically pays less fee than configured for data-carrying transactions, degrading confirmation reliability under fee pressure.

### Likelihood Explanation
`data` is a caller-supplied parameter to `SignableTransaction::new`; any output-creation path that attaches metadata (e.g., protocol commitments in OP_RETURN) triggers it deterministically. The miscalculation happens on every such transaction — no race or adversary timing is required.

### Recommendation
Compute `weight`/`vbytes` over the complete output set. Either move the OP_RETURN push before the weight calculation and pass the full `tx_outs` into `calculate_weight_vbytes`, or extend `calculate_weight_vbytes` to accept the data payload so both the no-change and with-change fee estimates account for it.

### Proof of Concept

```rust
// Construct a SignableTransaction with data = Some(vec![0u8; 80]) and a change script.
// - tx gains an OP_RETURN output (~90 serialized bytes) at send.rs:194-202.
// - calculate_weight_vbytes at send.rs:204/226 is given `payments`, which excludes
//   that output, so `vbytes` omits ~23 vbytes... plus payload overhead (~90 bytes total).

//   real tx requires; change absorbs the difference, so the *signed* tx's real

// With fee_per_vbyte chosen just above DEFAULT_MIN_RELAY_TX_FEE/1000, the TooLowFee
// check passes while the broadcast tx is below the relay minimum.
```

Relevant code: `send.rs:194-202` (OP_RETURN added to `tx_outs`), `send.rs:204` and `send.rs:226` (weight computed from `payments` only), `send.rs:85-93` (`calculate_weight_vbytes` uses `payments`), `send.rs:228-234` (change credited against understated fee).
