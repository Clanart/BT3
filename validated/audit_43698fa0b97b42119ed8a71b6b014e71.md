### Title
Wrong hardcoded FROST context string for Ed448 ciphersuite (`"v1"` instead of `"v11"`) - (File: crypto/frost/src/curve/ed448.rs)

### Summary
The report's bug class is a hardcoded constant that contradicts its own documented/spec value (an ETH/USD feed address labeled as BTC/USD). In Serai, the same class appears in `crypto/frost/src/curve/ed448.rs:9`, where the FROST `CONTEXT` domain separator for Ed448 is hardcoded as `b"FROST-ED448-SHAKE256-v1"`. The correct IETF ciphersuite identifier is `FROST-ED448-SHAKE256-v11` (the Ed448 suite was added at draft version 11), which is exactly what the Serai codebase itself uses in its own test vector.

### Finding Description
`Curve::CONTEXT` is prepended to every FROST hash invocation (`Curve::hash`, `hash_to_F`, `hash_msg`, `hash_commitments`, `hash_binding_factor`, `random_nonce`) at `crypto/frost/src/curve/mod.rs:49-57` and `:89-91`. Every other curve uses the correct draft-v1 identifier (`FROST-SECP256K1-SHA256-v1`, `FROST-P256-SHA256-v1`, `FROST-ED25519-SHA512-v1`, `FROST-RISTRETTO255-SHA512-v1`) at `crypto/frost/src/curve/kp256.rs:40-43` and `crypto/frost/src/curve/dalek.rs:44-47`. However, the Ed448 suite's correct identifier per the IETF FROST draft is `FROST-ED448-SHAKE256-v11`. Serai's own test vector in `crypto/ed448/src/ciphersuite.rs:86` hashes with the DST `b"FROST-ED448-SHAKE256-v11nonce"`, i.e., context `"FROST-ED448-SHAKE256-v11"` + DST `"nonce"`, confirming the intended constant is `"v11"`, while `crypto/frost/src/curve/ed448.rs:9` sets `"v1"`.

### Impact Explanation
Every domain-separated hash in the Ed448 FROST suite (binding factor `rho`, challenge `chal`, nonce derivation, `msg`/`com` hashes) is computed under a domain separator that does not match the standardized ciphersuite. Consequences:

- Ed448 signatures produced by this code will not verify under any conforming FROST-ED448-SHAKE256-v11 implementation, and vice versa — a silent interop failure on a security-critical constant, exactly like the wrong-feed-address bug.
- The transcripts collide with the (obsolete/draft) `"v1"` domain, weakening the intended domain separation guarantee that FROST relies on to prevent cross-protocol replay of preprocesses, addenda, and signatures.

### Likelihood Explanation
No attacker input is needed; the constant is wrong unconditionally whenever the `ed448` feature is used. Reachability is through any Ed448 `sign`/`verify`/`calculate_share`/`complete` path. Severity is bounded because all Serai-internal participants share the same code (internally consistent), so the practical effect is spec non-compliance and cross-version domain collision rather than an in-protocol forgery vector — hence Medium, driven entirely by a single hardcoded literal, matching the report's bug class.

### Recommendation
Change `crypto/frost/src/curve/ed448.rs:9` to:

```rust
const CONTEXT: &[u8] = b"FROST-ED448-SHAKE256-v11";
```

and add a test asserting `Ed448::CONTEXT` matches the `"FROST-ED448-SHAKE256-v11"` prefix already used by the test vector in `crypto/ed448/src/ciphersuite.rs`.

### Proof of Concept [1](#0-0) [2](#0-1) [3](#0-2) 

The test at `crypto/ed448/src/ciphersuite.rs:86` uses DST `"FROST-ED448-SHAKE256-v11nonce"`; via `Curve::hash_to_F`, the nonce DST is `"nonce"` with `CONTEXT` prepended (`crypto/frost/src/curve/mod.rs:56-57`), so the expected `CONTEXT` is `"FROST-ED448-SHAKE256-v11"`, but `curve/ed448.rs` hardcodes `"v1"`. Any conformance check against published FROST-Ed448 vectors fails, demonstrating the incorrect constant.

Note: I did not fully verify a couple of other hardcoded constants (e.g., the `DUST` value in `networks/bitcoin/src/wallet/send.rs`) within the iteration limit, so additional instances of this class may exist; the Ed448 `CONTEXT` mismatch is confirmed by the codebase's own test vector.
