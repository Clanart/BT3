### Title
OP_RETURN data output excluded from weight/vbyte and fee calculation, causing underpaid fees and potentially unbroadcastable transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the transaction weight, vbytes, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check using only the payment outputs (and optionally the change output). The OP_RETURN output carrying the caller-supplied `data` is pushed onto `tx_outs` but is never included in `calculate_weight_vbytes`, so the constructed transaction is larger and pays a lower effective fee rate than calculated.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is appended to `tx_outs` at lines 194–202. However, the weight/vbyte estimate at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds the dummy transaction solely from `payments` (lines 85–93) and an optional change output (lines 95–99). The data output is never passed in, so:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) omits the OP_RETURN output's ~11–91 vbytes (8-byte value, compactsize length, `OP_RETURN` + push opcode + up to 80 bytes of data).
- `fee_with_change` (line 227) has the same omission, so the change-amount decision at lines 228–234 is also computed on a too-small fee.
- The standardness check `weight > MAX_STANDARD_TX_WEIGHT` (line 241) uses the underestimated `weight`, so a transaction that actually exceeds the standard weight limit can be accepted as valid.

The actual fee paid is `sum(inputs) - sum(outputs)` (`fee()`, lines 137–141), which equals `needed_fee` when change is created or the exact leftover when it isn't — either way the real transaction is larger than what the fee was computed for, so the effective sat/vbyte rate is strictly below `fee_per_vbyte`.

### Impact Explanation
This is the direct analog of the `transfer()` gas-stipend bug: a fixed, insufficient resource budget attached to the fund-transfer mechanism causes the transfer to fail for the receiver.

- When `fee_per_vbyte` is at or near the minimum relay rate, the true fee rate can fall below `DEFAULT_MIN_RELAY_TX_FEE`, making the transaction non-standard/unrelayable — funds intended for recipients are never delivered even though `SignableTransaction::new` returned `Ok`.
- Near the weight boundary, the real transaction can exceed `MAX_STANDARD_TX_WEIGHT` (400,000 WU) and be rejected by all relaying nodes.
- The mis-estimation is caller-visible: `needed_fee()` and `fee()` report values inconsistent with the broadcastable transaction's actual requirements.

The minimum-relay check at line 211 validates `needed_fee` against the *underestimated* `vbytes`, so it cannot catch the underpayment.

### Likelihood Explanation
Triggering requires only that `data: Some(_)` is passed to `SignableTransaction::new` — a normal, documented use of the API (Serai attaches instruction data to Bitcoin outputs via OP_RETURN). No malicious counterparty or validator is needed; the transaction builder itself produces an invalid/underpaid transaction. Severity is medium: funds are not stolen, but outputs the wallet reports as sent may be unbroadcastable or confirm only after reconstruction at a higher fee, matching the report's "users unable to receive funds" impact class.

### Recommendation
Pass the fully assembled `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes` — e.g., compute weight/vbytes after building `tx_outs`, and include the change output in a second pass when evaluating `fee_with_change`. Alternatively, add the serialized size of the OP_RETURN output to `weight`/`vbytes` before computing `needed_fee`.

### Proof of Concept
```rust
// networks/bitcoin context; pseudo-test against SignableTransaction::new
let inputs = vec![received_output];            // a scanned ReceivedOutput
let payments = vec![(p2tr_script_buf(key).unwrap(), 1000)];
let data = Some(vec![0u8; 80]);                // maximal allowed OP_RETURN payload

let tx = SignableTransaction::new(inputs, &payments, None, data, FEE).unwrap();

// needed_fee was computed over a tx WITHOUT the OP_RETURN output:
//   vbytes_est = vbytes(inputs + payments)
// real tx additionally contains an 8-byte amount + ~83-byte OP_RETURN scriptPubKey
let real_vbytes = tx.sign_and_extract().vsize() as u64;   // after Schnorr signing
assert!(real_vbytes * FEE > tx.needed_fee());             // underpaid fee

// If FEE == DEFAULT_MIN_RELAY_TX_FEE-equivalent rate, the real feerate is
// needed_fee / real_vbytes < min relay rate -> transaction is rejected by nodes
// despite the TooLowFee check at send.rs:211 having passed.
```

Root cause is at `networks/bitcoin/src/wallet/send.rs`: OP_RETURN output added at lines 194–202, but weight computed from `payments` only at lines 204 and 225–226, with the standardness check at line 241 using the underestimated `weight`.
