Both controllers rely on the exact same HMAC scheme with no binding of context (topic, shop, endpoint) into the signed digest — directly mirroring the reported flaw where the message *type* is left out of the signed digest, allowing a signature computed for one purpose to be replayed and accepted for another.

### Title
Webhook HMAC verification omits topic/shop headers from the signed digest, enabling replay/type-confusion across webhook topics and shops - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates an incoming webhook solely by checking that `X-Shopify-Hmac-Sha256` is a valid HMAC-SHA256 of the raw POST body, using `ShopifyApp::PayloadVerification#hmac_valid?`. Neither the webhook `topic` nor the `shop_domain` — both taken from unauthenticated HTTP headers — are included in the HMAC digest that is verified. This is structurally the same flaw as the reported bug: the signed message omits the "type" (and shop context) that the receiving code uses to decide what action to take, so a signature that is valid for one message is also valid for a different, differently-interpreted message.

### Finding Description
`hmac_valid?` computes/verifies the digest purely over `data` (the raw body): [1](#0-0) 

`WebhookVerification#verify_request` calls this with only `request.raw_post`, and separately exposes `shop_domain` read straight from the `X-Shopify-Shop-Domain` header, which is never part of the HMAC computation: [2](#0-1) 

`WebhooksController#receive` forwards the raw body together with all headers (including topic and shop domain) to `ShopifyAPI::Webhooks::Registry.process`, which dispatches the job/handler based on the `x-shopify-topic` header and processes `shop_domain` from the header as well: [3](#0-2) 

Because the topic and shop-domain headers are not cryptographically bound to the signed body, a body+HMAC pair that was legitimately signed for one `(shop, topic)` combination remains a "valid" HMAC when replayed with a different `X-Shopify-Topic` or `X-Shopify-Shop-Domain` header. The verification code cannot distinguish "this body was signed to be a `carts/update` payload for shop A" from "this body is being presented as a `shop/redact` payload for shop B" — exactly the ambiguity described in the report, where the digest does not unambiguously encode the message's type/target.

The same unbound-signature pattern is duplicated in `ExtensionVerificationController`, which also verifies only `hmac_valid?(request.raw_post)` with no endpoint/type-specific context in the digest: [4](#0-3) 

### Impact Explanation
If an attacker can obtain any one legitimately-signed webhook body/HMAC pair (e.g., by being a webhook recipient for their own shop, or via a captured/leaked delivery), they can replay that same body and HMAC to the shared `WebhooksController#receive` endpoint while forging the `X-Shopify-Topic` and `X-Shopify-Shop-Domain` headers, since these are not part of the signed data. Depending on how the app's registered job classes interpret the body for the "wrong" topic (e.g., `customers/redact`, `shop/redact`, or a custom job that trusts `shop_domain`), this can cause cross-shop data exposure/mutation or trigger privileged actions (such as data-redaction jobs) against a shop the attacker doesn't operate — an accepted forged/cross-context signed request.

### Likelihood Explanation
Exploitation requires the attacker to already possess a validly-signed webhook body (trivial if they run any shop installing the app and receive webhooks for it, since HMACs are only tied to body content, not shop or topic). No secret needs to be broken — this is a pure message-confusion attack, matching the "Diﬃculty: High... but exploitable" characterization in the analogous report, though here the barrier is lower because no brute-force hash search is required — headers are simply swapped.

### Recommendation
Bind the webhook `topic` and `shop_domain` headers into the verified digest (or otherwise cryptographically tie them to the payload) so that a signature computed for one topic/shop cannot be reinterpreted as valid for another. Short term, include the `X-Shopify-Topic` and `X-Shopify-Shop-Domain` values (or their hash) alongside the raw body when computing/verifying the HMAC in `PayloadVerification#hmac_valid?`, mirroring the report's recommendation to "prefix untyped messages with the message type and include all message fields in the top-level digest." Longer term, document exactly which fields are covered by webhook/extension HMAC verification and ensure the verified digest is injective with respect to (shop, topic, body).

### Proof of Concept
1. Attacker installs the app on shop A (or otherwise legitimately receives a webhook), capturing a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair for topic `carts/update`.
2. Attacker sends a POST to the app's `WebhooksController#receive` endpoint using the same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Topic: shop/redact` and `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb:15-21`) recomputes the HMAC over `raw_body` only, which still matches, so the request passes verification.
4. `ShopifyAPI::Webhooks::Registry.process` dispatches to the `shop/redact` handler using the forged `shop_domain`, executing shop-redaction logic against `victim-shop.myshopify.com` using attacker-controlled body content, even though the signature was never generated for that shop or topic.

    def shopify_hmac

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
