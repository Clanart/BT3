## Analysis

The vLLM report's core pattern: a hardened, sanitizing "safe" API (`sanitize_message`) exists for stripping raw memory-address reprs from error strings, but a *different, unsanitized code path* re-derives a string containing a raw heap pointer and that string is attacker-observable. The failed invariant is "no raw process memory addresses ever reach an untrusted external consumer via a normal/public output path."

Protobuf has a directly analogous construct: `MessageLite::DebugString()`. [1](#0-0) 

For "lite" messages (`optimize_for = LITE_RUNTIME`, or any message whose `ClassData::is_lite` is set), `DebugString()` does not go through the redacting `TextFormat`-based `StringifyMessage` path that full `Message` uses (`Message::DebugString` → `internal::StringifyMessage` → `TextFormat::Printer` with `SetRedactDebugString(true)` and `SetRandomizeDebugString(true)`): [2](#0-1) 

Instead, `MessageLite::DebugString()` falls back to:
```cpp
return absl::StrCat("MessageLite at 0x", absl::Hex(this));
```
which is confirmed intentional/tested behavior in `LiteTest.DebugString`: [3](#0-2) 

This is wired into the generic `AbslStringify` hook, so *any* code that does `absl::StrCat(msg)`, `absl::StrFormat("%v", msg)`, `ABSL_LOG(...) << msg`, or similar with a lite message object gets this raw pointer value automatically, without the caller realizing DebugString/AbslStringify differs in redaction behavior between `Message` (full runtime, redacted) and `MessageLite` (lite runtime, raw heap address): [4](#0-3) 

### Why this is a genuine invariant miss (mirroring the vLLM CWE-532 pattern)

- Full `Message::DebugString()` was deliberately hardened against leaking sensitive/identifying data: it sets `SetRedactDebugString(true)` and `SetRandomizeDebugString(true)` on the printer specifically to prevent dependence on/leakage of unstable internal state through debug output.
- `MessageLite::DebugString()` — reachable for any application built with `optimize_for = LITE_RUNTIME` (a supported, common production configuration, e.g. Android/embedded/mobile-optimized backends) — bypasses that hardening path entirely and instead intentionally embeds the object's heap address (`this`) in the returned string.
- Just like vLLM's four/five sites that were "scope misses" from the sanitize_message fix, this is a scope miss between the `Message` redaction work and the separate `MessageLite` implementation: the redacting behavior was never extended to (or deliberately excluded from) the Lite runtime's `DebugString`/`AbslStringify` surface.

### Consuming-application exposure assumption

Protobuf itself has no RPC endpoint. The realistic exposure model (matching the analog rules) is: a service built with `optimize_for = LITE_RUNTIME` protos parses attacker-supplied bytes into a message object with a supported public API (`ParseFromString`/`MergeFrom`), and application/framework code — logging middleware, gRPC/HTTP error handlers, crash reporters, `ABSL_CHECK`/`ABSL_LOG` failure messages that stream the message via `operator<<`/`AbslStringify`, or a generic "dump object state on error" helper — includes the parsed message object in a response or log line that ultimately reaches the client (directly in an error body, or indirectly via log-based error reporting endpoints). Because `DebugString()`/`AbslStringify` is the same "safe to call for debugging" API surface developers reach for by convention (as `Message::DebugString()` trains them to expect redaction), the raw pointer leak is easy to introduce unintentionally, exactly as the vLLM secondary sites leaked `str(exc)` unintentionally.

### Severity assessment

This yields a heap-address disclosure primitive with the same ASLR-defeat value as the vLLM Stage 1 primitive — knowledge of a live heap pointer for an attacker-influenced object substantially reduces ASLR entropy for a service process. It is Medium severity, gated on the consuming application: (1) using the Lite runtime, and (2) surfacing `DebugString()`/`AbslStringify()` output of an attacker-parsed message to the attacker (log exposure, error responses, crash dumps). It requires no privileged access, malformed schema, or resource exhaustion — only a normal parse of attacker bytes into a `MessageLite`-only message type and then any ordinary debug/stringify call on it, both of which are common, intended usage patterns.

### Recommendation

- Document explicitly, at the `MessageLite::DebugString()` declaration and the `AbslStringify` friend for `MessageLite`, that Lite-runtime debug strings embed the object's raw memory address and must not be logged/returned in any context reachable by, or derived from, untrusted input in production, mirroring the guidance already given for `Message::DebugString()`.
- Consider gating the `"MessageLite at 0x..."` format behind a debug-only/opt-in build flag (analogous to `PROTOBUF_DEBUG`), or replacing the raw pointer with a redacted/opaque, non-address identifier (e.g., an incrementing counter or hashed pointer) — preserving the intended "different DebugString per instance" property (per the existing unit test comment) without exposing exploitable memory-layout information.
- Audit generated-code and internal call sites (e.g. `ByteSizeConsistencyError`, JSON debug-log paths at `json/internal/parser.cc:1391`) that log parsed messages via `DebugString()`/`AbslStringify` to confirm these are gated behind non-production debug flags (e.g., `PROTOBUF_DEBUG`) and not reachable in any code path that returns to, or is observable by, an untrusted caller.

### Proof of Concept

```cpp
// Requires a message compiled with optimize_for = LITE_RUNTIME
// (its ClassData::is_lite == true), e.g. any message deriving only
// from MessageLite (not the full Message/Reflection API).
proto2_unittest::TestAllTypesLite msg;
msg.ParseFromString(attacker_controlled_bytes);   // trusted schema, bounded payload

std::string dbg = msg.DebugString();
// dbg == "MessageLite at 0x<heap-address>"
// Confirmed format/intent at src/google/protobuf/message_lite.cc:129-137
// and asserted directly in src/google/protobuf/lite_unittest.cc:1173-1186
// (EXPECT_TRUE(absl::StartsWith(message1.DebugString(), "MessageLite at 0x")))
```
If an application logs `msg.DebugString()` (or does `ABSL_LOG(ERROR) << msg` / `absl::StrCat(msg)` via the `AbslStringify` hook) on a parse-failure or error path and that log/response is observable by the attacker (e.g. echoed error text, log-forwarding endpoint), the raw heap address of an attacker-influenced object is disclosed — the same class of ASLR-bypass primitive described in the vLLM report, transplanted to Protobuf's own "safe-looking" debug API.

std::string StringifyMessage(const Message& message, Option option,
                             FieldReporterLevel reporter_level) {
  // Indicate all scoped reflection calls are from DebugString function.
  ScopedReflectionMode scope(ReflectionMode::kDebugString);

  TextFormat::Printer printer;
  internal::FieldReporterLevel reporter = reporter_level;
  switch (option) {
    case Option::kShort:
      printer.SetSingleLineMode(true);
      break;
    case Option::kUTF8:
      printer.SetUseUtf8StringEscaping(true);
      break;
    case Option::kNone:
      break;
  }
  printer.SetExpandAny(true);
  printer.SetRedactDebugString(true);
  printer.SetRandomizeDebugString(true);
  printer.SetReportSensitiveFields(reporter);
  std::string result;
  // TODO: Remove this suppression.
  (void)printer.PrintToString(message, &result);

  if (option == Option::kShort) {
    TrimTrailingSpace(result);
  }

  return result;
}

PROTOBUF_EXPORT std::string StringifyMessage(const Message& message) {
  return StringifyMessage(message, Option::kNone,
                          FieldReporterLevel::kAbslStringify);
}
}  // namespace internal

std::string Message::DebugString() const {
  return internal::StringifyMessage(*this, internal::Option::kNone,
                                    FieldReporterLevel::kDebugString);
}

  proto2_unittest::TestAllTypesLite message1, message2;
  EXPECT_TRUE(absl::StartsWith(message1.DebugString(), "MessageLite at 0x"));
  EXPECT_TRUE(absl::StartsWith(message2.DebugString(), "MessageLite at 0x"));

  EXPECT_EQ(message1.DebugString(), message1.ShortDebugString());

  // Even identical lite protos should have different DebugString() output. Part

  // non-determinism, which should make it easier for us to change the output
  // later without breaking any code.
  EXPECT_NE(message1.DebugString(), message2.DebugString());
}
