### Title
Participant index out of range causes panic (crash) in PedPoP blame verification - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

The MariaDB advisory's bug class — a remotely triggerable hang/crash (DoS) — maps onto Serai's PedPoP blame path: `BlameMachine::blame_internal` and `calculate_share` index `self.commitments` with a `Participant` value derived from attacker-supplied bytes, and `HashMap`'s `Index` impl panics on a missing key.

### Finding Description

`blame_internal` performs `&self.commitments[&sender]` where `sender` is the accused participant supplied to `blame` / `AdditionalBlameMachine::blame` (crypto/dkg/pedpop/src/lib.rs:599). `Participant` is only validated as non-zero by `Participant::new`; nothing bounds it to `<= n`. The same unchecked-index pattern exists in `calculate_share` via `&self.commitments[&l]` (line 490), though there `validate_map` guards the keys — in `blame`/`blame_internal` no such guard exists.

In Serai's deployment shape, blame accusations arrive as tributary `InvalidDkgShare` transactions whose `accuser`/`faulty` fields are deserialized with only `Participant::new(u16)` validation (coordinator/src/tributary/transaction.rs:346-353) — any nonzero u16, e.g. `Participant(0xFFFF)`, is accepted. Feeding that into `blame` or `AdditionalBlameMachine::blame` indexes `commitments` with a key that was only ever populated for `1 ..= n` participants (see `AdditionalBlameMachine::new`, lines 656-660), so `HashMap::index` panics. Since processors run with a panic hook that terminates the process (`std::process::exit(1)`-style hooks are used across the codebase), a single crafted blame message crashes the node — a complete, repeatable DoS, matching the advisory's "hang or frequently repeatable crash" impact.

### Impact Explanation

An attacker who can submit a blame accusation (or whose message is relayed to `blame`) with a sender/recipient `Participant` index greater than `n` — or one simply absent from the commitments map — crashes the evaluating participant/coordinator. Repeated submissions keep crashing it on restart if the message is re-processed, halting DKG completion and blocking signing.

### Likelihood Explanation

The panic requires only that `blame`/`AdditionalBlameMachine::blame` be invoked with a participant index outside the committed set. The crypto library itself does not bound-check the index, and the tributary deserialization layer accepts any nonzero u16, so reachability depends only on the caller not separately validating `sender <= n`/`recipient <= n`. The cryptographic inputs needed (a malformed share message) are already expected to exist in the blame flow, since blame is precisely the path taken for invalid shares.

### Recommendation

In `blame_internal`, replace `self.commitments[&sender]` with a `get` lookup: if `sender`'s commitments are absent, return `sender` as faulty (they cannot have produced a valid committed share). Similarly bound-check `sender`/`recipient` against `params`/committed participants in `blame` and `AdditionalBlameMachine::blame`, and reject `Participant` values `> n` at the transaction-validation layer.

### Proof of Concept

```rust
// n = 3 DKG completed; commitments contains participants 1..=3
let blame_machine: AdditionalBlameMachine<Ed25519> =
    AdditionalBlameMachine::new(context, 3, commitment_msgs).unwrap();

// Crafted accusation: sender index 0xFFFF is a valid nonzero Participant
// but was never inserted into commitments.
let evil_sender = Participant::new(0xFFFF).unwrap();
// PANIC: HashMap index on missing key at pedpop/src/lib.rs:599
let _ = blame_machine.blame(evil_sender, recipient, msg, proof);
```

Caveat: I could not fully trace the coordinator-side dispatch of `InvalidDkgShare` to `blame` within this pass; the panic itself is unconditional once `blame` is reached with an out-of-set participant, but confirming end-to-end reachability requires verifying the caller doesn't bound the index.
