### Title
Permanent Loss of User Funds When Native-ERC20 IBC Refund Reconversion Fails on Timeout/ErrorAck - (File: x/erc20/keeper/ibc_callbacks.go, x/erc20/keeper/msg_server.go)

### Summary
This is the direct Cosmos EVM analog of the PawnShop/RWA report: a mandatory "unwind" step (burn/liquidate collateral in the original report; unescrow/reconvert Coins→ERC20 here) depends on an external, potentially pausable/blacklistable ERC20 contract, and the caller does not treat that dependency as atomic/recoverable. Instead of reverting the whole operation, the code silently swallows the failure and reports success, while a partial, non-atomic state mutation (escrowing the user's coins to the module account) has already been committed. The user's coins never get burned/converted back and are left parked in the `erc20` module account, while the corresponding ERC20 tokens remain in the module's EVM balance — both effectively unrecoverable by the user.

### Finding Description
When a native-ERC20 IBC transfer times out or receives an error acknowledgement, `x/erc20/ibc_middleware.go`'s `OnTimeoutPacket`/`OnAcknowledgementPacket` call into `Keeper.OnTimeoutPacket`/`Keeper.OnAcknowledgementPacket`, both of which route to `ConvertCoinToERC20FromPacket`: [1](#0-0) [2](#0-1) 

This function calls `ConvertCoinNativeERC20` to convert the sender's refunded Cosmos coin back into the native ERC20 token: [3](#0-2) 

Critically, if `ConvertCoinNativeERC20` fails, the error is swallowed and `nil` is returned — the IBC callback (and therefore the enclosing `MsgTimeout`/`MsgAcknowledgement` handled by the relayer) is reported as **successful**, so all state written up to that point is committed rather than rolled back.

Inside `ConvertCoinNativeERC20`, the sequence is:
1. `SendCoinsFromAccountToModule` — escrow the sender's coins into the `erc20` module account (this write is applied to the same `ctx`, not a discarded cache context).
2. `CallEVM(... "transfer" ...)` — the module attempts to transfer/unescrow the native ERC20 tokens from the module address to the receiver.
3. Only if step 2 succeeds does the code `BurnCoins` on the module account. [4](#0-3) 

If the underlying ERC20 contract enforces `whenNotPaused`/blacklist checks on `transfer` (a completely ordinary and expected pattern for real-world ERC20 tokens, e.g. `ERC20Pausable`/`AccessControlEnumerable` as already used in this very codebase's own `ERC20MinterBurnerDecimals.sol`), step 2 reverts and `CallEVM` returns an error. Step 1's escrow, however, was already applied to `ctx` and is never undone, since the caller (`ConvertCoinToERC20FromPacket`) intercepts the error and returns `nil`. The relayer's message therefore completes successfully and commits state, permanently:
- Debiting the user's Cosmos-coin balance (escrowed into the `erc20` module account, never burned, never refunded).
- Leaving the module's ERC20 token balance unchanged (the tokens that should have gone to the user stay in the module address).

The user ends the flow holding **neither** the ERC20 tokens **nor** the Cosmos coin representation — both are stuck under module control with no compensating mint, refund, or retry path exposed to the user. This is the same root-cause pattern as the audited report: liquidation/unwind logic assumes the paired token contract will always cooperate (no pause/blacklist), and when it doesn't, funds become permanently inaccessible — except here it is worse than "stuck"; it is unrecoverable loss because the coin leg is already destructively moved before the reciprocal ERC20 leg is confirmed.

The doc comments even acknowledge the fragility ("A user may then manually re-attempt the conversion") but this is incorrect: after the failure the user's Cosmos-coin balance has already been moved into the module account, so there is nothing left in the user's wallet to reattempt a conversion with.

### Impact Explanation
This qualifies as Critical "permanent freezing, locking, theft, or unauthorized extraction of user funds... or token-pair-backed balances": any unprivileged relayer submitting `MsgTimeout`/`MsgAcknowledgement` for a native-ERC20 token-pair IBC transfer that fails or times out, where the underlying ERC20 contract can revert on `transfer` (pause, blacklist, allowance/logic-based transfer restriction, or any other revert condition an ERC20 owner can trigger), causes irreversible loss of the user's funds. No governance/admin action of Push Chain itself is required — the pausing/blacklisting authority is the (potentially third-party) ERC20 token contract's own admin, exactly mirroring the external RWA contract's pause/blacklist role in the original report.

### Likelihood Explanation
Native ERC20 token pairs are a first-class, governance-supported use case in `x/erc20` (`RegisterERC20`, `IsNativeERC20`), and the reference minter/burner contract shipped in this repo already implements `ERC20Pausable`/`AccessControlEnumerable`, confirming pausable/permissioned ERC20s are an expected, in-scope token type. Any IBC transfer of such a token that times out (common under normal network conditions) or receives an error ack while the contract happens to be paused (or the module/receiver address is blacklisted) triggers the bug without any special privilege — a relayer's ordinary `MsgTimeout` or `MsgAcknowledgement` submission is sufficient.

### Recommendation
- Do not silently swallow errors from `ConvertCoinNativeERC20` in `ConvertCoinToERC20FromPacket`. Wrap the escrow-and-convert sequence in a `ctx.CacheContext()` (or reorder operations) so a failed ERC20 unescrow atomically rolls back the coin escrow, leaving the refunded coin in the sender's own balance (recoverable via a subsequent, user-initiated `MsgConvertCoin`).
- Alternatively, reorder `ConvertCoinNativeERC20` to attempt the EVM `transfer` first and only escrow/burn the Cosmos coin after the ERC20 leg is confirmed successful.
- Ensure the IBC callback only reports "handled" success once the user's balances are made whole in one form or another (either as coin or as ERC20), never leaving both legs under module custody.

### Proof of Concept
1. Governance registers a native ERC20 token pair for token `T` (an `ERC20Pausable`/blacklist-capable contract) via `RegisterERC20`.
2. User A converts `T` tokens to the Cosmos coin representation and initiates an IBC transfer (`MsgTransfer`) of that coin to chain B.
3. Before the packet is relayed/acknowledged, `T`'s pauser (an external token admin, not a Push Chain validator) calls `pause()` on the ERC20 contract.
4. The IBC packet times out (or chain B returns an error acknowledgement).
5. A relayer submits `MsgTimeout`/`MsgAcknowledgement`, invoking `IBCMiddleware.OnTimeoutPacket` → `Keeper.OnTimeoutPacket` → `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20`.
6. `SendCoinsFromAccountToModule` succeeds, escrowing A's coins into the `erc20` module account; the subsequent `CallEVM("transfer", ...)` reverts because `T` is paused.
7. `ConvertCoinNativeERC20` returns an error, which `ConvertCoinToERC20FromPacket` catches, emits a `EventTypeFailedConvertERC20` event, and returns `nil`.
8. The `MsgTimeout` transaction succeeds and commits. User A now holds neither `T` ERC20 tokens nor the Cosmos coin — both are stranded under `erc20` module custody, with no protocol path for A to recover them.

func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}
