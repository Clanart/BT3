### Title
Missing Timestamp Freshness Check in `AppProxyVerification` Enables Indefinite Replay of Signed App Proxy Requests - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification` verifies app-proxy requests solely by recomputing an HMAC signature over the query string and comparing it to the `signature` parameter. Although Shopify includes a `timestamp` parameter in every app proxy request (used as part of the signed data), the concern never validates that this timestamp is recent. This is the same root-cause pattern as the reported "stale price feed" bug: data that has a natural freshness/expiry (a timestamp) is treated as permanently valid because there is no explicit staleness check.

### Finding Description
`query_string_valid?` in `lib/shopify_app/controller_concerns/app_proxy_verification.rb` extracts the `signature` parameter, recomputes the expected HMAC over all the remaining query parameters (including `timestamp`), and does a secure comparison: [1](#0-0) 

The `timestamp` value is only used as an *input* to the HMAC calculation — it is never compared against the current time to reject old requests. This means any previously valid, correctly-signed app proxy URL (e.g., one that leaked via browser history, referrer headers, shared logs, proxy/CDN caches, or a man-in-the-middle capture) remains valid and accepted by `verify_proxy_request` forever, since the signature check has no expiry: [2](#0-1) 

The test suite confirms the design: a fixed, years-old `timestamp=1466106083` value with its corresponding signature is accepted as valid with no time-based rejection: [3](#0-2) 

This exactly mirrors the reported bug class: a value intended to represent freshness (block timestamp there, request timestamp here) is stored/verified without any check of how old it is, allowing stale-but-signed data to be treated as current indefinitely.

### Impact Explanation
Any controller using `ShopifyApp::AppProxyVerification` (the concern explicitly recommended for verifying app-proxy HTTP requests) will accept a captured, validly-signed app proxy request indefinitely. If a legitimate app proxy request URL is disclosed once (e.g., via logs, browser history sync, referrer leakage, or network capture), an attacker can replay it at any future time and have it accepted as authentic by the app, even though the original request context (e.g., the customer session or intent) is long gone. Depending on what the app proxy endpoint does (e.g., trigger an action tied to `shop`/`logged_in_customer_id` query params), this can enable a forged/replayed signed request being accepted well after it should have expired.

### Likelihood Explanation
Exploitation requires only capturing one previously issued, validly signed app-proxy request URL — no cryptographic secret needs to be broken, and no privileged access is required. This makes it a realistic no-privilege replay scenario applicable to any app relying on `ShopifyApp::AppProxyVerification` for authorization or trust decisions based on proxy parameters like `logged_in_customer_id`.

### Recommendation
- **Short term**: Add a freshness check in `verify_proxy_request`/`query_string_valid?` that rejects requests where `timestamp` is older than a small tolerance window (e.g., a few minutes), similar to standard replay-protection practices.
- **Long term**: Document and enforce that `AppProxyVerification` is not sufficient on its own for actions with side effects; encourage nonce/timestamp-based replay protection to be layered in for state-changing app-proxy endpoints.

### Proof of Concept
1. Capture (or reconstruct) a validly signed app proxy request, e.g. the one used in the existing test:
   `?shop=some-random-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=f5cd7233558b1c50102a6f33c0b63ad1e1072a2fc126cb58d4500f75223cefcd` [3](#0-2) 
2. Replay this exact query string against any controller including `ShopifyApp::AppProxyVerification` at any point in the future (days, months, years later).
3. `query_string_valid?` recomputes the same HMAC (since the same parameters, including the stale `timestamp`, are signed) and `verify_proxy_request` allows the request through — there is no code path that ever compares `timestamp` to `Time.now`. [4](#0-3)

```ruby
# frozen_string_literal: true

module ShopifyApp
  module AppProxyVerification
    extend ActiveSupport::Concern
    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_proxy_request
    end

    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```
