## Finding

### Title
Missing basis-points bound check on `UpdateParams`/destination fees in the Tron `IntentGatewayV2` lets governance set a 100% (or >100%) protocol fee, zeroing/underflowing user escrow - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM `IntentGatewayV2` (via `IntentsBase._validateParams`/`_updateParams`) enforces `protocolFeeBps < 10_000` and `destinationFeeBps < 10_000` on every parameter update, exactly the guard the external report recommends for `basisPoints`. The Tron port of the same contract implements its own `onAccept` handler for `RequestKind.UpdateParams` and applies `_params = update.params;` / `_destinationProtocolFees[stateMachineId] = feeBps;` directly, with **no equivalent bound check**. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`placeOrder` computes the escrowed amount as:
```
protocolFee = originalAmount * protocolFeeBps / 10_000
reducedAmount = originalAmount - protocolFee
``` [4](#0-3) 

On the mainline EVM contract, `protocolFeeBps` and any per-destination override are bound-checked to be strictly `< 10_000` both at `initialize`/`setParams` time (`_validateParams`) and on every governance `UpdateParams` (`_updateParams`), which explicitly documents the intent: "Reverts with InvalidInput if any value would brick the gateway or cause arithmetic errors in fee calculations." [5](#0-4) [6](#0-5) 

The Tron variant's `onAccept` for `RequestKind.UpdateParams`, however, decodes the `ParamsUpdate` and writes both `_params` and `_destinationProtocolFees[stateMachineId]` with **no call to any validation routine**:
```solidity
} else if (kind == RequestKind.UpdateParams) {
    ParamsUpdate memory update = abi.decode(incoming.request.body[1:], (ParamsUpdate));
    emit ParamsUpdated({previous: _params, current: update.params});
    _params = update.params;

    for (uint256 i; i < update.destinationFees.length;) {
        bytes32 stateMachineId = update.destinationFees[i].stateMachineId;
        uint256 feeBps = update.destinationFees[i].destinationFeeBps;
        _destinationProtocolFees[stateMachineId] = feeBps;
        ...
    }
}
``` [3](#0-2) 

This is the direct local analog of the reported bug class: an unchecked basis-points config value that a privileged-but-fallible actor (here, Hyperbridge governance relaying an `UpdateParams` message, gated only by `source == hyperbridge()`) can push through without any sanity bound, corrupting a downstream fee computation. [7](#0-6) 

If `protocolFeeBps` (or a destination override) is set to `10_000` (100%):
- `protocolFee = originalAmount`, `reducedAmount = 0`.
- The user's entire `originalAmount` is transferred into the gateway on `placeOrder` (`IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)`), but the escrow entry `_orders[commitment][token]` is credited with `reducedInputs[i].amount = 0`. [8](#0-7) 

Because `_orders[commitment][token] == 0` is treated everywhere as "no escrow" (`UnknownOrder` sentinel), the user's deposited funds become permanently unrecoverable dust: `withdraw`/`cancelOrder` treat the order as non-existent and revert with `UnknownOrder`, while the full deposited amount sits in the contract, indistinguishable from legitimate dust and sweepable only by governance via `SweepDust`. [9](#0-8) [10](#0-9) 

If `protocolFeeBps > 10_000` (e.g. mis-set to a value like 15000), `protocolFee > originalAmount`, and `reducedAmount = originalAmount - protocolFee` underflows and reverts under Solidity 0.8 checked arithmetic — bricking `placeOrder` entirely for that chain/destination, a denial-of-service of the order-placement path analogous to the reported `emergencyEtherRecoverWithoutOracleData` DoS.

### Impact Explanation
This breaks the "bridged assets... must move exactly once and only to the rightful beneficiary and amount" invariant: user input tokens are fully collected while the escrow record used by `withdraw`/`cancelOrder` is zeroed, causing loss/lock of 100% of the user's deposited funds with no recovery path other than a subsequent governance sweep, and/or a full DoS of `placeOrder` for any value above 100%. This is exactly the missing-bound-check bug class from the external report, reproduced in production contract code with a concrete fund-loss/DoS consequence rather than a benign revert.

### Likelihood Explanation
Requires only that Hyperbridge governance relay a single `UpdateParams` request (the same "owner mistake" precondition the original report calls medium severity) targeting the Tron `IntentGatewayV2` deployment — no relayer/prover compromise, no malicious peer, and no front-running is needed. Given the mainline EVM contract already had to add this exact guard (as shown by its dedicated `_validateParams` checks and tests such as `testRevert_UpdateParams_DestinationFeeBpsTooHigh` and `testRevert_SetParams_ProtocolFeeBpsTooHigh`), the Tron port's omission of the equivalent check is a clear regression/divergence rather than a hypothetical scenario. [11](#0-10) [12](#0-11) 

### Recommendation
Port `IntentsBase._validateParams` (and the `feeBps >= 10_000` check applied to each `DestinationFee`) into the Tron `IntentGatewayV2.onAccept` `UpdateParams` branch before assigning `_params` and `_destinationProtocolFees`, rejecting any `protocolFeeBps`/`surplusShareBps`/`destinationFeeBps` value `>= 10_000`.

### Proof of Concept
1. Deploy Tron `IntentGatewayV2` and register it with the Hyperbridge host as usual.
2. As Hyperbridge governance, dispatch a `PostRequest` with `body = RequestKind.UpdateParams || abi.encode(ParamsUpdate{params: {..., protocolFeeBps: 10_000}, destinationFees: []})` targeting the gateway; `onAccept` applies it unchecked. [13](#0-12) 
3. A user calls `placeOrder` with a USDC input of `1000e6`; `protocolFee = 1000e6`, `reducedAmount = 0`; the gateway pulls the full `1000e6` via `safeTransferFrom` but stores `_orders[commitment][usdc] = 0`. [14](#0-13) 
4. The user calls `cancelOrder`; the same-chain path checks `_orders[commitment][token]` and reverts `UnknownOrder`, permanently trapping the deposited 1000 USDC. [10](#0-9)

    /**
     * @dev Validates gateway configuration parameters. Reverts with InvalidInput if any
     * value would brick the gateway or cause arithmetic errors in fee calculations.
     *
     * @param p The parameters to validate.
     */
    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);
