### Title
Gasless swap sponsorship relies on manipulable Uniswap V2 spot price for token valuation, enabling theft of proposer-lent gas - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The `kaiax/gasless` module (KIP-247) sponsors user gas by having the block proposer lend KAIA via `LendTxGenerator`, then requires the user's `GaslessSwapTx` to repay that lent amount by swapping an ERC-20 token through a whitelisted DEX pool. The amount of token required for a given repay amount is computed on-chain via a single spot-price read (`GetAmountIn`) from a Uniswap-V2-style pool registered per-token, with no TWAP or liquidity-depth safeguard — mirroring the exact "low-liquidity AMM spot price used as oracle" bug class in the referenced report.

### Finding Description
`checkBalanceForSwap` validates the swap by querying the DEX router's instantaneous reserve-based price: [1](#0-0) 

This calls `GaslessSwapRouter.GetAmountIn(token, minAmountOut)`, which — like the Uniswap V2 `getAmountIn`/reserve math used in the project's own test harness — is a spot-price computation derived purely from the pool's current reserves: [2](#0-1) 

Tokens are onboarded to the gasless system via `AddToken(token, factory, router)` with no minimum-liquidity or TWAP requirement enforced in the reachable Go-side logic: [3](#0-2) 

The bundle constructed for execution is `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]`, built directly from the mempool without any block-level manipulation protection (e.g., requiring the swap to execute against a TWAP or checking reserve depth): [4](#0-3) 

The project's own integration test explicitly exercises this exact spot-price mechanism (`routerContract.GetAmountsOut`, Uniswap V2 style reserves) to compute `minAmountOut` for a swap that determines how much real KAIA (lent by the proposer) is repaid: [5](#0-4) 

Because `GetAmountIn`/`GetAmountsOut` in a Uniswap-V2-type pool is a deterministic function of current reserves only, any low-liquidity token pool registered via `AddToken` can have its spot price manipulated cheaply and atomically (a large swap immediately before/within the same block) to make an attacker's worthless or manipulated token appear valuable enough to satisfy `minAmountOut >= amountRepay` while contributing token value far below the KAIA that the proposer actually lent.

### Impact Explanation
An attacker who registers or targets a thinly-liquid token pool used by the gasless system can:
1. Manipulate the pool's reserve ratio (buy/sell within the pool) to inflate the apparent value of the attacker's token relative to KAIA.
2. Submit `GaslessApproveTx` + `GaslessSwapTx` with a `minAmountOut`/`amountRepay` that passes `checkBalanceForSwap`'s spot-price check but which, at true/fair market value, does not cover the KAIA lent by the block proposer.
3. Result: the block proposer's lent KAIA (real value transferred to cover the user's gas) is repaid with tokens worth substantially less, causing systematic value drain from the fee-delegation/gasless funding mechanism — a direct instance of "unauthorized value movement" / "gasless settlement theft" as called out as an acceptable impact category.

This is a High-severity issue because it allows economic extraction of real KAIA from the gasless subsidy mechanism by any unprivileged transaction sender who can influence a whitelisted pool's reserves, with no code-level defense (no TWAP, no minimum liquidity threshold, no slippage/impact cap) visible in the reachable path.

### Likelihood Explanation
Likelihood is high given: (1) `AddToken`/pool registration is on the `GaslessSwapRouter` contract level and the Go-side `checkBalanceForSwap` performs no additional liquidity or manipulation-resistance check beyond reading `GetAmountIn` once; (2) any token with shallow liquidity that gets whitelisted is exploitable trivially by a single large trade; (3) the exact bug class (spot-price AMM used for economically consequential settlement without TWAP or liquidity floor) was already flagged as high severity in the referenced external audit for a comparable design (WBGL/ETH pool). The main uncertainty is around governance/whitelisting practices for which tokens get added via `AddToken` — if operationally only deep, well-audited pools (e.g., major stablecoin pairs) are ever whitelisted, real-world exploitability is reduced, but this is an operational mitigation, not a code-enforced one.

### Recommendation
- Require a manipulation-resistant price source in `checkBalanceForSwap` (e.g., TWAP over multiple blocks, or a minimum reserve/liquidity threshold check) rather than relying solely on instantaneous `GetAmountIn`/`GetAmountsOut` reserve math.
- Add an explicit minimum-liquidity or maximum price-impact check before accepting a `GaslessSwapTx` for reimbursement of proposer-lent KAIA.
- Consider bounding the deviation between the swap's on-chain execution price and a reference/oracle price, rejecting swaps with anomalously favorable pricing for the sender.
- Restrict `AddToken` to tokens meeting a documented minimum-liquidity bar, and monitor/alert on pool reserve changes for gasless-whitelisted tokens.

### Proof of Concept
Conceptual PoC (not exploit code, since contract-level attack requires deploying/manipulating pool reserves off the scope of the Go modules under review):
1. Attacker (or colluding party) creates or targets a low-liquidity pool for `TOKEN/WKAIA` that has been added via `GaslessSwapRouter.AddToken(TOKEN, factory, router)` [3](#0-2) .
2. Attacker executes a large swap against the pool (buying WKAIA with TOKEN or vice versa) to skew reserves, making `TOKEN` appear more valuable in terms of WKAIA than its fair market price.
3. Attacker submits `GaslessApproveTx` + `GaslessSwapTx` with `amountIn` (in `TOKEN`) computed to just satisfy `GetAmountIn(TOKEN, minAmountOut)` at the manipulated price, where `minAmountOut >= amountRepay` for the KAIA gas lent by the proposer [6](#0-5) .
4. The bundle `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` executes atomically [7](#0-6) ; the proposer's lent KAIA is repaid with `TOKEN` that is, at fair value, worth less than the KAIA lent, netting the attacker the difference and draining value from the gasless subsidy pool.

func (g *GaslessModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	// there are only at most two gasless transactions in pending for a sender
	bundles := []*builder.Bundle{}
	approveTxs := map[common.Address]*types.Transaction{}
	targetTxHash := common.Hash{}
	for _, tx := range txs {
		addr, err := types.Sender(g.signer, tx)
		if err != nil {
			continue
		}
		if g.IsApproveTx(tx) {
			approveTxs[addr] = tx
		} else if g.IsSwapTx(tx) && g.IsExecutable(approveTxs[addr], tx) {
			bundleTxs := builder.NewTxOrGenList(g.GetLendTxGenerator(approveTxs[addr], tx))
			if approveTxs[addr] != nil {
				bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(approveTxs[addr]))
			}
			bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(tx))

			b := builder.NewBundle(
				bundleTxs,
				targetTxHash,
				false,
			)

			targetTxHash = tx.Hash()

			isConflict := false
			for _, prev := range append(prevBundles, bundles...) {
				if prev.IsConflict(b) {
					isConflict = true
					break
				}
			}
			if isConflict {
				// Gasless transactions will just fail even if they aren't bundled.
				continue
			}
			bundles = append(bundles, b)
		} else {
			targetTxHash = tx.Hash()
		}
	}
	return bundles
