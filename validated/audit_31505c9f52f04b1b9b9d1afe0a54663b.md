### Title
`SignableTransaction::new` excludes the OP_RETURN data output from the fee/weight calculation, producing an underfunded transaction — (File: networks/bitcoin/src/wallet/send.rs)

### Summary

Like the BT.Finance incident, where an attacker manipulated the economic inputs of a vault accounting formula to extract value, `SignableTransaction::new` computes the required fee from an incomplete transaction shape: the weight/vbytes calculation only includes `payments` and (optionally) `change`, but never the OP_RETURN output that is actually serialized into the final transaction. The signed transaction is therefore larger than the size used to derive `needed_fee`, so it pays less than the intended fee rate — potentially below the minimum relay fee — while the "change" output is simultaneously inflated by the same missing amount, masking the shortfall.

### Finding Description

In `SignableTransaction::new`, the OP_RETURN output is pushed into `tx_outs` before the weight is computed [1](#0-0) , but the weight function is invoked with `payments` only — the data output is never represented [2](#0-1) . `calculate_weight_vbytes` builds its synthetic transaction solely from `payments` plus optional `change` [3](#0-2) , so `needed_fee = fee_per_vbyte * vbytes` misses roughly `8 + 1 + (2 + 80) ≈ 91` vbytes for a maximal (80-byte) payload [4](#0-3) .

The same omission propagates: the change-amount check computes `input_sat - (payment_sat + fee_with_change)` with the underestimated `fee_with_change`, so the change output is overvalued by exactly the omitted fee and the actual on-chain fee ends up even lower than `needed_fee` [5](#0-4) . Likewise, the `TooLowFee` guard compares the underestimated fee against a minimum computed from the underestimated vbytes, so it can pass even when the real fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` [6](#0-5) .

### Impact Explanation

A caller that passes a `data` payload produces a transaction whose real fee rate is below the intended `fee_per_vbyte` and can fall below the minimum relay fee. In a threshold/FROST deployment, the resulting transaction is either non-relayable or stalls indefinitely, requiring a costly re-signing round or fee-bump; the oversized change output also misreports spendable balance downstream (`fee()` itself will report the *actual* fee, which differs from `needed_fee`, breaking fee accounting invariants such as `fee() >= needed_fee`). Funds are not stolen, but they are locked and accounting is corrupted — analogous to BT.Finance's loss via a manipulated value-transfer formula. Severity: Medium.

### Likelihood Explanation

Any integrator (or internal path) that uses the `data` parameter — the mechanism intended for `InInstruction` OP_RETURNs — triggers the miscalculation deterministically. The error grows linearly with payload size (up to ~91 vbytes × the fee rate). No adversary is needed for the bug itself; an adversary who can influence the data length (e.g., by supplying instruction bytes that get embedded) controls the magnitude of the fee shortfall.

### Recommendation

Include the OP_RETURN output in the weight calculation — e.g., pass the fully constructed `tx_outs` (or append the data output into the synthetic transaction inside `calculate_weight_vbytes`) at both call sites [7](#0-6) , so `vbytes`, `needed_fee`, the `TooLowFee` check, and the change amount all reflect the real serialized transaction.

### Proof of Concept

```rust
// networks/bitcoin: demonstrates the fee shortfall
let data = vec![0xAA; 80]; // max permitted
let tx = SignableTransaction::new(
  vec![input],                       // ReceivedOutput worth 100_000 sats
  &[(payment_script, 50_000)],
  Some(change_script.clone()),
  Some(data),
  fee_per_vbyte,                     // e.g. 1 sat/vbyte
).unwrap();

// The synthetic size excludes the ~91-vbyte OP_RETURN output
assert!(u64::try_from(tx.signable_tx_weight_vbytes().1).unwrap()
        < u64::try_from(real_signed_tx.vsize()).unwrap());
// Actual fee = inputs - outputs, reduced by change inflated by the omitted fee;
// consequently real_fee_rate < fee_per_vbyte and may be < DEFAULT_MIN_RELAY_TX_FEE
assert!(tx.fee() < tx.needed_fee() + 0); // fee() reflects the true (lower) fee
```
