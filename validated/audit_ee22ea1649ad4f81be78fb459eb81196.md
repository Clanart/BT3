### Title
Optimistic payout amount is never cross-checked against the amount Citrea recorded as owed for the withdrawal - (File: core/src/rpc/aggregator.rs)

### Finding Description
The binding that should hold is: `output_amount` (the value the N-of-N cosigns for the optimistic payout output) `==` the amount Citrea's bridge contract recorded as owed for that `deposit_id`'s withdrawal. Tracing `AggregatorServer::optimistic_payout`, `output_amount` is taken directly from the attacker-controlled gRPC request via `parser::operator::parse_withdrawal_sig_params(withdraw_params)` [1](#0-0) . The only cross-check performed against stored state is that the `input_outpoint` (withdrawal UTXO) matches the DB record fetched via `get_withdrawal_utxo_from_citrea_withdrawal`, i.e. outpoint equality only [2](#0-1) . There is no fetch of, or comparison to, any Citrea-recorded withdrawal amount anywhere in this handler — `output_amount` flows straight from the request into the `TxOut` used to build the payout tx handler [3](#0-2) , and then into the sighash that verifiers are asked to cosign nonces/partial signatures for [4](#0-3) . The remaining checks in this function are: UTXO-not-spent [5](#0-4) , output script-pubkey type validity [6](#0-5) , and a Schnorr signature check that the user (owner of the dust withdrawal UTXO) signed the constructed sighash [7](#0-6) . None of these bind `output_amount` to a Citrea-side "amount owed" figure — they only bind it to whatever value the attacker put in the request, subject only to the verifier-side upper bound (`bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT`) that the question itself already identifies.

Given that `get_withdrawal_utxo_from_citrea_withdrawal` only returns an outpoint (not an amount) and the aggregator never queries any `CitreaClientT` for the withdrawal's actual recorded amount in this path, an attacker who has: (1) made a real deposit establishing `bridge_amount`, (2) called Citrea's `withdraw()` to register *some* withdrawal_utxo outpoint (which can be a dust-value UTXO they fully control, e.g. 550 sats), and (3) constructed a valid signature over the resulting sighash, can request `output_amount` up to `bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT` regardless of what economic value the dust UTXO itself represents or what amount was actually burned/owed on the Citrea side for that withdrawal record. Verifiers will cosign because their check (per the question, mirrored by the verifier-side bound function) is also just an upper-bound sanity check against `bridge_amount`, not an equality check against the Citrea withdrawal's recorded amount.

### Impact Explanation
If confirmed end-to-end (which requires reading `Verifier::sign_optimistic_payout` and any Citrea-amount-fetching logic that I could not fully inspect within the available iterations), this would let an attacker drain nearly the full `bridge_amount` of a move-to-vault UTXO via N-of-N cosigned partial signatures for an amount that was never actually fronted/burned on Citrea in that quantity — matching the Critical category "N-of-N partial signatures for an unauthorised spend" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal." This would be repeatable per withdrawal registration and would affect the operator/vault backing that specific deposit.

### Likelihood Explanation
Based on the code inspected, the aggregator handler for `optimistic_payout` performs no amount cross-check against Citrea, only an outpoint-equality check [2](#0-1) . However, I was unable to fully verify within the available tool budget whether: (a) `Verifier::sign_optimistic_payout` in `core/src/verifier.rs` independently fetches and enforces equality between `output_amount` and a Citrea-recorded withdrawal amount, or (b) whether Citrea's `withdraw()` contract call itself locks in `output_amount` at registration time such that a mismatched value would fail elsewhere (e.g., a later on-chain verification of the withdrawal proof). These matches exist (`sign_optimistic_payout` has 3 references in `core/src/verifier.rs`) but their content was not read before the iteration budget was exhausted.

### Recommendation
Cannot be conclusively finalized without inspecting `Verifier::sign_optimistic_payout` (`core/src/verifier.rs`) and the Citrea withdrawal-amount storage/verification path to confirm whether an equality check against the Citrea-recorded withdrawal amount exists elsewhere in the flow. Given this residual uncertainty, I am not able to assert with full confidence that this is exploitable end-to-end, though the aggregator-side code inspected shows no such check.

### Proof of Concept
Not conclusively producible without confirming the verifier-side and Citrea-record-side behavior noted above; a `cargo test` proof would need to: (1) mock `CitreaClientT` to record a withdrawal for `deposit_id` with a known "amount owed" X, (2) call `optimistic_payout` gRPC with `output_amount` = `bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT` > X, using a dust-value withdrawal UTXO, and (3) assert whether verifiers still return valid partial signatures — which the aggregator.rs code path inspected suggests they would, but this could not be fully confirmed against `Verifier::sign_optimistic_payout` in the time available.
