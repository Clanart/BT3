### Title
Unauthenticated `ReceivedOutput` deserialization admits nonexistent UTXOs - ([File: `networks/bitcoin/src/wallet/mod.rs`])

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without authenticating that the referenced UTXO exists or was produced by the scanner. An unprivileged party can therefore provide serialized bytes representing an output paying to the wallet’s Taproot script while naming a nonexistent or unrelated outpoint. The resulting object reports the fabricated amount as spendable and can be used to construct and sign an invalid transaction.

### Finding Description
`ReceivedOutput` contains the three elements needed to claim and spend a Bitcoin output: an offset, a `TxOut`, and an `OutPoint`. [1](#0-0)  `ReceivedOutput::read` deserializes those fields directly and returns the object without proving that the outpoint resolves to the supplied `TxOut` or that the object came from `Scanner`. [2](#0-1) 

The legitimate construction path only creates a `ReceivedOutput` after matching a transaction output’s `script_pubkey` to a registered scanner script and binding it to the containing transaction’s actual TXID and output index. [3](#0-2)  The deserializer bypasses that provenance check entirely.

`SignableTransaction::new` subsequently trusts the deserialized `TxOut` value and `OutPoint` when calculating available funds and constructing the transaction inputs. [4](#0-3)  The signing setup checks only that the claimed `script_pubkey` equals the wallet key plus the supplied offset; it does not and cannot verify on-chain existence of the claimed prevout. [5](#0-4) 

### Impact Explanation
An attacker can fabricate a received balance that is not spendable and cause the wallet to build a transaction spending a nonexistent or mismatched UTXO. If mixed with genuine inputs, the fabricated input can also influence fee, payment, and change calculations while making the final transaction invalid. This violates the wallet invariant that a `ReceivedOutput` represents an actually received output controlled by the expected tweaked key.

### Likelihood Explanation
The attack only requires an application to pass attacker-controlled serialized bytes to `ReceivedOutput::read` and then use the result for balance tracking or transaction construction. No private key material, invalid curve point, or malformed scalar is required; a zero offset is canonical when the wallet’s base Taproot key is even, which is required by `Scanner::new` for the un-offset script. [2](#0-1) [6](#0-5) 

### Recommendation
Do not expose `ReceivedOutput::read` as a way to ingest untrusted claims about chain state. Authenticate serialized outputs before storage or revalidate every deserialized `OutPoint` against Bitcoin consensus state before treating the object as received or spendable. At minimum, transaction construction should verify that each claimed outpoint exists and that its actual on-chain `TxOut` exactly matches the deserialized `TxOut`.

### Proof of Concept
The following byte layout is sufficient to forge a received output for an even wallet key:

```rust
use bitcoin::{
  consensus::Encodable,
  hashes::{hash_newtype, Hash},
  Amount, OutPoint, TxOut, Txid,
};
use frost::curve::Secp256k1;
use bitcoin_serai::wallet::{p2tr_script_buf, ReceivedOutput};
use ciphersuite::{group::ff::PrimeField, Ciphersuite};
use k256::ProjectivePoint;

fn forged_output(group_key: ProjectivePoint, fake_value: u64) -> ReceivedOutput {
  // Scalar::ZERO leaves the wallet's base Taproot key unchanged.
  let mut bytes = Vec::new();
  bytes.extend(Secp256k1::read_F(
    &mut k256::Scalar::ZERO.to_bytes().as_slice(),
  ).unwrap().to_repr());

  // The script matches the wallet, but the outpoint below is fabricated.
  TxOut {
    value: Amount::from_sat(fake_value),
    script_pubkey: p2tr_script_buf(group_key).unwrap(),
  }
  .consensus_encode(&mut bytes)
  .unwrap();

  OutPoint {
    txid: Txid::from_raw_hash(hash_newtype!([u8; 32], [0xAA; 32]).into()),
    vout: 0,
  }
  .consensus_encode(&mut bytes)
  .unwrap();

  ReceivedOutput::read(&mut bytes.as_slice()).unwrap()
}
```

The returned object reports `fake_value` through `value()` and carries the fabricated outpoint. Passing it to `SignableTransaction::new` creates a transaction referencing that outpoint, and `multisig` accepts it when the forged `TxOut` uses the wallet’s expected `p2tr_script_buf` script.
