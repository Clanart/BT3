### Title
Rolling-window commit/push security-review rate limit can be exhausted by trivial commits, silently disabling the agentic vulnerability scan for the rest of the hour - (File: plugins/security-guidance/hooks/security_reminder_hook.py)

### Summary
The `security-guidance` plugin gates its LLM-based vulnerability review of `git commit`/`git push` on a shared, session-scoped rolling-window budget (`MAX_COMMIT_REVIEWS_PER_HOUR`, default 20 per hour). Any content that causes Claude to issue many trivial `git commit`/`git push` calls within the window — indistinguishable in cost from a "real" commit — exhausts the budget. Once exhausted, subsequent commits (including ones that actually introduce a vulnerability or secret) are silently skipped with no LLM review, mirroring the SymmStaking bug class where cheap, repeated small contributions dilute a shared resource that is supposed to protect a legitimate outcome over a bounded time window.

### Finding Description
`atomic_check_rate_limit` implements a rolling-window limiter: at most `max_per_window` calls per `window_s` seconds per `(session_id, key)`, backed by a list of timestamps pruned on every call. [1](#0-0) 

The commit-review and push-sweep handlers both draw from the *same* rate-limit key space with a shared hourly cap: [2](#0-1) 

Each time `git commit` is detected, `handle_commit_review_posttooluse` consumes one slot from this shared bucket *before* running the actual LLM security scan — the slot is spent whether or not the commit is meaningful: [3](#0-2) 

`handle_push_sweep_posttooluse` draws from the same cap: [4](#0-3) 

Once the bucket is full, the review is skipped entirely (`skip_reason=23`) and no `exit(2)`/stderr guidance is emitted, so nothing forces Claude (or the user) to notice that a commit went unreviewed — this is only visible in background telemetry, not in the transcript.

This is structurally identical to the `SymmStaking.notifyRewardAmount` dilution: the pool (reward duration in the original bug; review budget here) is meant to guarantee a service level (steady reward accrual; timely vulnerability detection) over a fixed window, but any party who can trigger the cheap operation repeatedly (dust reward deposits; trivial/empty commits) consumes the shared resource and degrades/delays the real guarantee for everyone relying on it in that window.

### Impact Explanation
Because Claude Code sessions routinely execute agent-driven or tool-chained workflows (subagents, skills, scripted commit loops, or content from an untrusted repo/PR that induces many small commits — e.g. via prompt injection instructing "commit after every tiny change"), an attacker-influenced session can cheaply burn all `MAX_COMMIT_REVIEWS_PER_HOUR` slots with throwaway commits. The next commit in that hour that actually introduces a vulnerability, hardcoded secret, or backdoor bypasses the plugin's only automated safety net (`analyze_code_security` / agentic review) without any user-visible signal, since the skip path is silent (debug log + metrics only). This directly weakens the code/secret-disclosure trust boundary the plugin exists to enforce.

### Likelihood Explanation
Reachable by any unprivileged content that influences Claude's tool-call cadence within a session (compromised repo instructions, prompt injection, or even a normal iterative "commit often" workflow) — no special privileges are required, and the hook's own re-gate logic (`_GIT_COMMIT_RE`, reflog fallback) actively counts every successful `git commit`/`git push`, including empty or trivial ones, toward the shared budget.

### Recommendation
Do not spend the review budget on low-value commits: only count a commit against `MAX_COMMIT_REVIEWS_PER_HOUR` after confirming the diff has reviewable content (i.e., after the `diff_files` non-empty check at `security_reminder_hook.py:1178`), rather than unconditionally in `atomic_check_rate_limit` before that check. Additionally, surface skip_reason=23 to the user/transcript (not only telemetry) so an exhausted review budget is visible, and consider scaling the budget or window based on commit size/frequency rather than a fixed session-lifetime-agnostic count, mirroring the original report's mitigation of enforcing a meaningful minimum contribution before it affects the shared resource.

### Proof of Concept
1. Start a Claude Code session with the `security-guidance` plugin enabled (`ENABLE_COMMIT_REVIEW=1`, default `MAX_COMMIT_REVIEWS_PER_HOUR=20`).
2. Have Claude (via prompt injection in a file it reads, or a scripted loop) run `git commit --allow-empty -m "wip"` (or trivially small real commits) 20 times within the hour — each call passes `_GIT_COMMIT_RE`/diffstat detection in `handle_commit_review_posttooluse` and consumes one `atomic_check_rate_limit("CommitReview", ...)` slot at line 1207-1209, regardless of diff size.
3. On the 21st commit within the same rolling hour, introduce an actual vulnerability/secret.
4. Observe that `_allowed` is `False` at line 1211, and the handler exits at line 1214 with `skip_reason=23` — the vulnerable commit receives no LLM review, and no stderr/exit(2) guidance is shown to the user or Claude.

def atomic_check_rate_limit(session_id, key, max_per_window, window_s):
    """Rolling-window rate limit: allow at most `max_per_window` calls per
    `window_s` seconds, per (session_id, key).

    Returns (allowed: bool, count_in_window: int). count_in_window is the
    post-decision count (i.e., includes this call if allowed) so callers can
    emit it directly as a telemetry gauge.

    Replaces session-lifetime `atomic_check_counter` for commit-review and
    push-sweep. Telemetry showed a small but persistent share of sessions hit
    the lifetime cap, and those were multi-day persistent sessions that then
    lost coverage for many subsequent commits — not burst abusers. A rolling
    hour keeps the same cost ceiling for any 1h window while letting long
    sessions regain coverage.

    State key: rate_limits: {"<key>": [ts, ts, ...]}. Timestamps are pruned
    on every call so the list is bounded by max_per_window; no migration
    needed from the old `counters` dict — different key.
    """
    import time as _time
    now = _time.time()
    cutoff = now - window_s

    def _check(state):
        buckets = state.setdefault("rate_limits", {})
        ts_list = buckets.get(key, [])
        # Prune; tolerate non-numeric junk from a corrupted state file.
        ts_list = [t for t in ts_list if isinstance(t, (int, float)) and t > cutoff]
        if len(ts_list) >= max_per_window:
            buckets[key] = ts_list
            return False, len(ts_list)
        ts_list.append(now)
        buckets[key] = ts_list
        return True, len(ts_list)

    result = with_locked_state(session_id, _check)
    # State unavailable → fail-open (same posture as atomic_check_counter).
    return result if result is not None else (True, 0)
