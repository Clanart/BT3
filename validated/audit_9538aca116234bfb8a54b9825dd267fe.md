### Title
FROST confirmation nonces reused across repeated key-pair reports: `DkgConfirmer` re-signs with a cached preprocess seed, leaking the validator's secret key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` deterministically caches a FROST preprocess seed keyed only by `context` (`CachedPreprocesses: (context) -> [u8; 32]`). For `DkgConfirmer` the context is `(b"DkgConfirmer", attempt)`. Every subsequent signing operation under that context — `share()` from `generated_key_pair`, and `share_internal` re-invoked inside `complete()` — reloads the identical seed via `AlgorithmSignMachine::from_cache`, regenerating identical FROST nonces `(d, e)` (`seeded_preprocess` → `Commitments::new(rng, original_secret_share, ...)`). There is no guard preventing a second `share` invocation under the same attempt with a different signed message, so the same nonce pair is committed to multiple Schnorr challenges, which is classic nonce reuse and allows recovery of the validator's private key from the two published shares.

### Finding Description
`preprocess_internal` writes the cached seed once per context and never deletes it after use: [1](#0-0) 

`share_internal` calls `preprocess_internal` again on every invocation, then `machine.sign(preprocesses, msg)` consumes the regenerated nonces: [2](#0-1) 

The FROST library itself only guarantees safety if each `CachedPreprocess` is used once — the seed is explicitly documented as "MUST only be used once. Reuse will enable third-party recovery of your private key share": [3](#0-2) 

Yet `DkgConfirmer::share` is invoked once per `generated_key_pair` call (which unconditionally overwrites `DkgKeyPair`/`KeyToDkgAttempt` and signs `set_keys_message(set, removed, key_pair)`), and `DkgConfirmer::complete` calls `share_internal` a second time: [4](#0-3) [5](#0-4) 

This is the analog of the vantage6 bug class (CWE-281, improper preservation of permissions): a capability tied to one context (the preprocess/nonce) is improperly preserved and reapplied when the underlying object (the `key_pair` being confirmed, or the preprocess set) is reassigned, instead of being invalidated.

### Impact Explanation
Each FROST signature share has the form `share_i = d + e·rho_i + lambda_i·s·c_i`, where `s` is the signer's secret contribution and `d, e` are the two nonce components regenerated deterministically from the cached seed (`crypto/frost/src/sign.rs` `sign()` / `nonces.drain` at lines 386–398, `Commitments::new` seeded at lines 121–144). Because the same `d` and `e` are reused, a second signing under the same attempt context with a different `msg` (different `key_pair` → different `set_keys_message`), different `removed` set, or a different contributed `confirmation_nonces`/preprocess map produces a second linear equation in the same unknowns. Two or more shares let an observer solve for `d`, `e`, and `s` — i.e., recover the validator's private signing key — from data that is published on the public tributary (`Transaction::DkgConfirmed` carries `confirmation_share`). Recovery of this key lets an attacker forge that validator's participation in subsequent MuSig/threshold operations.

### Likelihood Explanation
The trigger is a repeat of `generated_key_pair` (or `share` + `complete` diverging) under the same `attempt` context with differing inputs. Nothing in `generated_key_pair` checks whether a share was already produced for that attempt — `DkgKeyPair::set`/`KeyToDkgAttempt::set` blindly overwrite, and `preprocess_internal` unconditionally reloads the prior seed (the `is_none()` check only guards creation, never consumption or deletion). The code comments themselves acknowledge duplicated calls under timing/reboot conditions (`"this txn may not be committed with the expected timing"`, coordinator/src/tributary/handle.rs:527–528). A peer contributes `confirmation_nonces` as part of `DkgShares`, so the preprocess set fed to `sign()` is externally influenced. Any second execution path with different inputs produces publicly observable nonce reuse.

### Recommendation
- Delete (`take` rather than `get`) the `CachedPreprocesses` entry when it is consumed by `share_internal`, so a second `share` under the same context cannot reuse the seed.
- In `complete()`, do not re-run `share_internal`; persist the `AlgorithmSignatureMachine` output (or its serialized state) from the `share()` call instead of re-deriving nonces.
- Guard `generated_key_pair` with an "already signed for this attempt" check rather than overwriting `DkgKeyPair`.
- Bind the cached-preprocess context to the exact message/preprocess set it will sign (e.g., include a hash of `key_pair` and `removed` in `context`), so any reassignment forces a fresh nonce.

### Proof of Concept
1. Attempt `A` begins; `dkg_confirmation_nonces` → `preprocess_internal((b"DkgConfirmer", A))` stores seed `S` in `CachedPreprocesses`.
2. `generated_key_pair(.., key_pair_1, A)` → `share()` → `preprocess_internal` regenerates nonces `(d, e)` from `S` → `sign(preprocesses_1, set_keys_message(.., key_pair_1))` emits share `σ1`.
3. A second `generated_key_pair(.., key_pair_2, A)` (retry/re-emit path, or `complete` run with a different accumulated preprocess map) → identical `(d, e)` → `σ2` over a different `msg`/binding set.
4. With `σ1 = d + e·rho1 + λ·s·c1` and `σ2 = d + e·rho2 + λ·s·c2` (all of `rho`, `λ`, `c` publicly computable from the published preprocesses and messages), two equations in three unknowns `d, e, s`; a third share (or known `λ` structure across the participant's multiple indexes) fully determines `s` — the validator's secret key share — from on-chain data.

Note: I verified the caching/reuse mechanics and call sites in `coordinator/src/tributary/signing_protocol.rs`, `handle.rs`, and `crypto/frost/src/sign.rs`. I could not fully enumerate every caller path that can re-trigger `generated_key_pair` for the same attempt within the available search; the exploit rests on the absence of any reuse guard, which is confirmed by the code.

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
