## Analysis

Reducing the Ajna report to its core broken invariant: **a claim/withdrawal ledger entry is permanently consumed (zeroed) before the actual token transfer to the beneficiary is guaranteed to succeed, and there is no accounting to let the shortfall be reclaimed later.**

Hyperbridge's relayer fee withdrawal flow reproduces this exact pattern.

### Finding [1](#0-0) 

`Pallet::withdraw` reads the relayer's accrued `available_amount` from `Fees<T>`, then calls `dispatcher.dispatch_request(...)`. This call only **enqueues** an ISMP `PostRequest` locally on Hyperbridge (writes a request commitment and emits an event) — it performs no check that the destination chain's `HostManager`/`EvmHost` actually holds enough `feeToken` to pay out `available_amount`. [2](#0-1) 

Immediately after `dispatch_request` returns `Ok`, the pallet does `Fees::<T>::insert(dest_chain, address, U256::zero())` — the relayer's fee balance is wiped **at dispatch time**, not at confirmed-delivery time. The `amount` baked into the outbound message body is a fixed snapshot of `available_amount` taken before the zeroing.

The actual payout only happens later, when the message is delivered to the destination and `HostManager.onAccept` invokes: [3](#0-2) 

which calls into: [4](#0-3) 

`EvmHost.withdraw` uses `safeTransfer`/a raw native call that **reverts on insufficient balance** (`WithdrawalFailed`), rather than capping the transferred amount like the original Ajna bug — so on the EVM destination side there's no silent truncation. But the structural flaw is on the Hyperbridge (source) side: the `Fees` ledger entry that represents the relayer's claim is destroyed the moment the withdrawal message is dispatched, regardless of whether that message is ever successfully delivered and executed. Delivery to the destination is asynchronous and can fail for reasons unrelated to signature/nonce validity — most notably an underfunded `EvmHost`/`HostManager` fee-token balance (governance can drain protocol revenue via `withdraw`/`dispatch_withdraw`, see `evm/src/core/EvmHost.sol:651-660` and `docs/content/developers/evm/bandwidth/governance.mdx:34-55`) at the exact moment the relayer's withdrawal request lands. If that revert propagates as a non-retryable failure or the request subsequently times out, the `Fees<T>` entry is already zero — the relayer has no on-chain record left of the amount that failed to be paid, and there is no compensating "restore Fees on timeout" logic present in `withdrawal.rs`. This mirrors the Ajna `RewardsManager` defect precisely: the claim/reward ledger is finalized (zeroed) before the value transfer is confirmed, and the un-paid remainder is silently and permanently lost from the accounting.

I could not locate (within the available index) an `onPostRequestTimeout`/failure handler in `modules/pallets/relayer` that re-credits `Fees<T>` for a withdrawal whose delivery request timed out or failed on the destination — this is the one piece I was unable to fully confirm and would need direct verification in a Devin session (searching the full `pallet_ismp_relayer` `Config`/`IsmpModule` implementation for `on_timeout`/`on_post_request_timeout`).

### Title
Relayer fee ledger (`Fees<T>`) is zeroed at dispatch time, not at confirmed delivery, causing permanent loss of accrued fees if the cross-chain withdrawal message fails or times out - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` zeroes a relayer's `Fees<T>` entry as soon as the withdrawal `PostRequest` is successfully *dispatched* (queued) to the destination chain, not once the destination `HostManager`/`EvmHost` has actually paid out the funds. Because delivery is asynchronous and destination `EvmHost.withdraw` can revert (e.g., insufficient `feeToken` balance after governance drains protocol revenue) or the request can time out, the relayer's claim can be extinguished from the ledger with no compensating restoration, permanently losing the accrued reward — the same broken invariant as the referenced Ajna `RewardsManager` report (claim ledger finalized before value transfer guaranteed).

### Finding Description
`withdrawal.rs::withdraw` (lines 116-184) reads `available_amount` from `Fees<T>`, dispatches a `PostRequest` carrying that fixed amount to the destination's `host_manager`/`HYPERBRIDGE_MODULE_ID`, and on `dispatch_request` returning `Ok` immediately sets `Fees::<T>::insert(dest_chain, address, U256::zero())`. `dispatch_request` only records the outbound commitment locally; it provides no guarantee that the destination chain will ever execute the corresponding `HostManager.onAccept` → `EvmHost.withdraw` call successfully. `EvmHost.withdraw` (`evm/src/core/EvmHost.sol:651-660`) reverts if the host's `feeToken`/native balance can't cover `params.amount`. If that failure is not retried indefinitely, or the request instead times out on the destination and Hyperbridge's timeout-handling path for the relayer module does not restore `Fees<T>`, the relayer's claim is gone with no ledger of the unpaid remainder.

### Impact Explanation
This is a direct, unauthorized loss of relayer reward funds: an honest relayer that has correctly delivered messages and accrued fees can have those fees wiped from the ledger without ever receiving payment, if the destination host happens to be underfunded (a realistic operational state, since governance can drain host revenue via `withdraw`/`dispatch_withdraw`) at the moment their withdrawal is processed. This matches the required impact class "loss of funds" via a broken accounting invariant, not a peer/relayer-trust issue.

### Likelihood Explanation
Any unprivileged relayer can trigger this by calling `withdraw` when the destination `EvmHost` fee-token balance is momentarily below the relayer's accrued amount — a state reachable through normal governance revenue withdrawals or fee-token migrations, no malicious actor or admin collusion required. The zeroing-before-confirmation ordering is unconditional in the code path shown.

### Recommendation
Do not zero `Fees<T>` until delivery is confirmed (e.g., only clear/decrement it upon a callback/receipt showing the destination `withdraw` succeeded), or implement a timeout/failure handler on the relayer pallet's `IsmpModule` that re-credits `Fees<T>` with the exact `available_amount` when the withdrawal `PostRequest` times out or its delivery fails, mirroring the recommended Ajna fix of never letting the ledger "spend" more than what is actually transferred.

### Proof of Concept
1. Relayer accrues `available_amount = X` in `Fees<T>` for `dest_chain`.
2. Governance calls `EvmHost.withdraw`/`dispatch_withdraw` on the destination, draining `feeToken` balance below `X`.
3. Relayer calls `Pallet::withdraw`; `dispatch_request` succeeds (local enqueue only) and `Fees::<T>::insert(dest_chain, relayer, 0)` executes (`modules/pallets/relayer/src/withdrawal.rs:170-177`).
4. Message delivers to destination; `HostManager.onAccept` → `EvmHost.withdraw` reverts (`evm/src/core/EvmHost.sol:651-660`, insufficient balance).
5. Relayer's `Fees<T>` entry is already `0`; without a timeout/failure-handling restoration path (not found in `withdrawal.rs`), the relayer permanently loses `X` even though it was never paid.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
