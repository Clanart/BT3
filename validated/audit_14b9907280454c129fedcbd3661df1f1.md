### Title
Auctioneer bid-approval signature (`ValidateAuctioneerSig`) lacks chainId/contract domain separation, enabling cross-chain/cross-deployment signature replay - (File: `kaiax/auction/bid.go`)

### Summary
The auction module validates two signatures on a `Bid`: the searcher's signature (`ValidateSearcherSig`) and the auctioneer's approval signature (`ValidateAuctioneerSig`). While `ValidateSearcherSig` correctly binds the signed digest to `chainId` and `verifyingContract` via EIP-712 domain separation, `ValidateAuctioneerSig` signs only over the raw `SearcherSig` bytes with a bare `"\x19Ethereum Signed Message:\n"` prefix and no chain/contract/domain binding at all. This is the same class of defect as the reported `_checkSig` bug: a signature scheme that omits replay-protection fields (chain ID, verifying contract) is reusable across different chains/networks or contract redeployments.

### Finding Description
`Bid.GetEthSignedMessageHash` computes the digest the auctioneer signs: [1](#0-0) 

This digest is derived purely from `b.SearcherSig` (i.e., it commits to "I approve this particular searcher signature") with no `chainId`, no `verifyingContract`/entry-point address, and no domain separator. `ValidateAuctioneerSig` then recovers the signer from this digest and checks it equals the expected `auctioneer` address: [2](#0-1) 

Contrast this with `ValidateSearcherSig`, which explicitly requires `chainId` and `verifyingContract` and builds an EIP-712 digest bound to the auction entry-point contract and version: [3](#0-2) [4](#0-3) 

Because the auctioneer's approval signature is only bound to the `SearcherSig` bytes (which are themselves already domain-separated by `chainId`/`verifyingContract`), the auctioneer signature is technically tied only to that inner searcher signature — but there is no guarantee that the same `(chainId, verifyingContract)` context used by the auctioneer matches the network/entry-point where the bid is ultimately admitted/executed. Any deployment, testnet fork, or alternate entry-point contract instance sharing the same `AuctioneerSig`/`SearcherSig` byte values (e.g., replaying the identical `SearcherSig` on the same or a different `chainId`) will pass `ValidateAuctioneerSig` verification identically, since nothing in the auctioneer's own signed payload commits to a chain or contract identifier independently.

### Impact Explanation
Since the auction module gates block-builder bid admission and settlement on this auctioneer approval (`ValidateAuctioneerSig` is consumed for bid-pool admission per `kaiax/auction/impl/bid_pool.go`), a replayed or reused auctioneer approval could allow a bid combination valid in one network context to be accepted in another (e.g., a test network vs. mainnet, or after a contract redeployment/version bump referenced by `AuctionVersionV2`/`AuctionVersionV3`), potentially leading to acceptance of bids/approvals the auctioneer did not intend to authorize in that specific context — a form of unauthorized settlement/authorization bypass in the gasless/auction module.

### Likelihood Explanation
Exploitation requires an attacker to have or obtain a valid `(SearcherSig, AuctioneerSig)` pair from one deployment context and resubmit it to a different one sharing the same auctioneer key and expected `SearcherSig` bytes (e.g., a forked/duplicated network, or a redeployed auction entry-point at a different address reusing the same auctioneer). This is a plausible but non-trivial scenario, dependent on operational key/address reuse across environments, similar to the exploit scenario described in the original report (fork/redeploy + trusted-party account reuse).

### Recommendation
Bind `ValidateAuctioneerSig`'s digest to the same domain-separation fields already used for `ValidateSearcherSig` — i.e., include `chainId` and `verifyingContract` (and ideally the auction `version`) in the auctioneer's signed message, rather than signing only the opaque `SearcherSig` bytes. This ensures the auctioneer's approval cannot be replayed across different chains or contract deployments, mirroring the fix recommended for `_checkSig` in the original report.

### Proof of Concept
1. Auctioneer signs approval over `GetEthSignedMessageHash()` for a `Bid` whose `SearcherSig` was produced with `chainId=A`, `verifyingContract=Entrypoint_A` (per `GetHashTypedData`).
2. An attacker (or the same operator) deploys/forks a second Kaia-based network/entry-point (`chainId=B`, `verifyingContract=Entrypoint_B`) that reuses the same auctioneer address.
3. The attacker submits the identical `(SearcherSig, AuctioneerSig)` pair as a `Bid` on network B.
4. `ValidateAuctioneerSig(auctioneer)` on network B recomputes `GetEthSignedMessageHash()` — identical to network A's digest since it only depends on the `SearcherSig` bytes — and successfully recovers `auctioneer`, passing validation even though the auctioneer never intended to approve this bid in network B's context. func (b *Bid) GetEthSignedMessageHash() []byte {
	data := b.SearcherSig

	return h

func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

func (b *Bid) ValidateAuctioneerSig(auctioneer common.Address) error {
	digest := b.GetEthSignedMessageHash()

	recoveredAuctioneer, err := getSigner(b.AuctioneerSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover auctioneer sig: %v", err)
	}

	if recoveredAuctioneer != auctioneer {
		return fmt.Errorf("invalid auctioneer sig: expected %v, calculated %v", auctioneer.String(), recoveredAuctioneer.String())
	}

	return nil
}

// GetHashTypedData returns the EIP-712 digest for the bid.
// version must match the on-chain AUCTION_VERSION of the entry-point contract
// the bid targets; "0.0.2" selects the v3.0 struct typehash (with maxGasPrice),
// any other value falls back to the v2.1 typehash.
func (b *Bid) GetHashTypedData(chainId *big.Int, verifyingContract common.Address, version string) []byte {
	if chainId == nil {
		return nil
	}

	domain := EIP712Domain{
		EIP712DomainTypeHash: eip712TypeHash,
		NameHash:             auctionNameHash,
		VersionHash:          crypto.Keccak256Hash([]byte(version)),
		ChainId:              chainId,
		VerifyingContract:    verifyingContract,
	}

	domainSeparator := EncodeEIP712(domain)

	var structHash []byte
	if version == AuctionVersionV3 {
		structHash = EncodeEIP712(bidV3{b})
	} else if version == AuctionVersionV2 {
		structHash = EncodeEIP712(b)
	} else {
		// Unknown version: default to v2.1 typehash.
		structHash = EncodeEIP712(b)
	}

	return crypto.Keccak256([]byte{0x19, 0x01}, domainSeparator, structHash)
