### Title
OP_RETURN `data` output excluded from weight/fee estimation in `SignableTransaction::new`, producing transactions whose effective fee rate is below the requested rate and potentially below mempool minimum - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
Analogous to the reported bug (a fixed/insufficient gas stipend causing the intended operation to revert), `SignableTransaction::new` computes the transaction weight and required fee using only `payments` and the optional `change` output. The OP_RETURN `data` output — appended to `tx_outs` before the fee is calculated — is never included in `calculate_weight_vbytes`. The resulting `needed_fee` is a fixed stipend underestimated by the size of the data output, so the signed transaction pays a lower effective fee rate than `fee_per_vbyte`, and can fall below the node's minimum relay fee — the exact "insufficient stipend → operation reverts/is rejected" class.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is pushed onto `tx_outs` at lines 193-202 when `data` is supplied (up to 80 bytes per the check at line 171). However, the fee/weight estimation calls at lines 204 and 225-226 pass only `payments` and `change` to `calculate_weight_vbytes`, which builds the weight-estimation transaction purely from `inputs` and `payments`/`change` (lines 85-99). The data output's ~10-89 vbytes are never accounted for.

Consequences:
- When `change` is `Some`, the change output absorbs the residual: `change = input_sat - payment_sat - fee_with_change` (line 228), so the actual fee paid is exactly `needed_fee`, spread over a transaction that is actually `data` bytes larger. The effective fee rate is strictly less than `fee_per_vbyte`.
- The `TooLowFee` guard at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes` using the underestimated `vbytes`. A caller specifying the minimum viable rate produces a real transaction below the minimum relay fee; a relaying node rejects it, permanently stalling that spend (the signature commits to `Prevouts::All` and the exact outputs, so the signed TX cannot be "topped up" without a full re-signing round).
- The `NotEnoughFunds` check at line 215 uses the underestimated `needed_fee`, admitting constructions that are truly unaffordable only once the real size is considered — a marginal case, but same root cause.
- The `TooLargeTransaction` check at line 241 uses the underestimated `weight`, so a transaction legitimately at the boundary can exceed `MAX_STANDARD_TX_WEIGHT` once the data output is counted, again yielding a signed transaction that will never be accepted.

### Impact Explanation
Any caller/user able to attach `data` to a payment (the processor embeds user-supplied instruction data in outputs) causes the produced transaction to underpay relative to its size. At fee-boundary conditions the signed transaction is unrelayable: it is rejected by the network while consuming the nonce/signature ceremony, forcing re-scheduling and stalling the plan — the same "withdrawal/registration blocked because the fixed resource bound was insufficient" impact as the reference report. At the size boundary it can produce a non-standard oversize transaction that is never mineable.

### Likelihood Explanation
Requires a transaction with `data` set and a fee rate or total weight near the protocol limits. Since `data` is attacker-influenced public input (up to 80 bytes unconditionally accepted at line 171), and fee markets regularly sit at minimum relay rates, the underpriced/oversize outcome is reachable with public inputs. Severity is Medium: funds are not stolen, but a legitimate operation is blocked and must be re-created.

### Recommendation
Include the OP_RETURN `data` output in the transaction built inside `calculate_weight_vbytes` (pass it through as an additional `TxOut` alongside `payments`/`change`), for both the no-change and with-change estimations, so `needed_fee`, the `TooLowFee`, `NotEnoughFunds`, and `TooLargeTransaction` checks all reflect the real signed transaction. Alternatively, after constructing `tx_outs`, compute the weight of the final `Transaction` directly rather than a reconstruction.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs semantics
let data = vec![0u8; 80]; // passes the <= 80 check at line 171
let tx = SignableTransaction::new(
    inputs,                    // one input
    &[(script, DUST)],         // minimal payment
    Some(change_script),       // change present
    Some(data),
    1,                         // fee_per_vbyte = 1 sat/vB (minimum relay)
);
// Internally:
//  - tx_outs gains an OP_RETURN output of ~89 bytes (line 194-202)
//  - vbytes/needed_fee computed WITHOUT that output (line 204)
//  - needed_fee passes the min-relay check at line 211 against the
//    underestimated vbytes
// Result: signed tx is ~89 vbytes larger than estimated while paying
// needed_fee, so its effective rate is < 1 sat/vB and peers reject it.
```
