## Analog Analysis

The GoBGP advisory describes a decoder function (`SRv6L3ServiceAttribute.DecodeFromBytes`) that fails to validate the length/shape of attacker-supplied bytes before further processing, causing a crash (DoS). The `kaia--004` codebase has an analogous pattern in `AccountKeyRoleBased`, where RLP-decoded data can produce a slice whose length is never re-validated before an unchecked index access is performed.

### Title
Unchecked index access on empty `AccountKeyRoleBased` causes node panic during signature validation - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` decodes an arbitrary-length list of encoded keys straight from untrusted bytes without enforcing a minimum length, and `AccountKeyRoleBased.Validate` unconditionally falls back to `getDefaultKey()`, which indexes `(*a)[RoleTransaction]` (index 0) with no bounds check. [1](#0-0) [2](#0-1) 

### Finding Description
`DecodeRLP` accepts any `[][]byte` including an empty list and sets `*a = (AccountKeyRoleBased)(keys)` with `len(keys) == 0`, without ever calling `CheckInstallable` (which is the only place that rejects `len(*a) == 0`, via `kerrors.ErrZeroLength`). [3](#0-2) 

Separately, `Validate` is used to check transaction signatures against an account's key:
```go
func (a *AccountKeyRoleBased) Validate(currentBlockNumber uint64, r RoleType, recoveredKeys []*ecdsa.PublicKey, from common.Address) bool {
	if len(*a) > int(r) {
		return (*a)[r].Validate(currentBlockNumber, r, recoveredKeys, from)
	}
	return a.getDefaultKey().Validate(currentBlockNumber, r, recoveredKeys, from)
}

func (a *AccountKeyRoleBased) getDefaultKey() AccountKey {
	return (*a)[RoleTransaction]
}
```
When `len(*a) == 0`, `len(*a) > int(r)` is false for `r = RoleTransaction (0)`, so control falls through to `getDefaultKey()`, which performs `(*a)[0]` on a zero-length slice — an unrecovered Go slice-index panic.

This mirrors the GoBGP bug class: a decode routine that accepts a shape of attacker data that downstream processing logic assumes cannot occur, and that assumption violation manifests as an unhandled crash (`CWE-404`/DoS via improper resource shutdown, here process crash equivalent).

### Impact Explanation
If a zero-length `AccountKeyRoleBased` value can reach `Validate()` before `CheckInstallable()` has filtered it out, any Kaia node processing that transaction (during tx-pool admission or block execution) panics. Because Go panics in the transaction validation/execution path are typically only guarded by a top-level recover in specific goroutines (e.g., worker/miner loops), an unrecovered panic here can crash node processes handling transaction validation, denying service to the network — a concrete match for "Improper Resource Shutdown or Release" leading to availability impact (`A:L` in the CVSS vector).

### Likelihood Explanation
The likelihood hinges on whether a zero-length `AccountKeyRoleBased` can actually reach `Validate()` for an account that is otherwise valid on-chain, since `CheckInstallable` normally gates key installation for `TxTypeAccountUpdate`/`TxTypeAccountCreation`. I was not able to fully confirm, within the available tool budget, a code path where a zero-length role-based key bypasses `CheckInstallable` and is nonetheless stored/used for signature `Validate()` calls (e.g., via a state that was populated through an alternate path, or a decode call directly feeding `Validate()` without the installability check, such as via `KaiaAPI.DecodeAccountKey` returning a key object that some other caller later validates without re-checking installability). This is the residual gap in the investigation.

### Recommendation
- Add an explicit length check (`len(*a) == 0`) at the start of `AccountKeyRoleBased.Validate` and `getDefaultKey`, returning `false`/an error instead of indexing.
- Alternatively, make `DecodeRLP` reject `len(enc) == 0` directly (mirroring `CheckInstallable`'s `kerrors.ErrZeroLength`) so that no zero-length `AccountKeyRoleBased` value can ever be constructed from untrusted bytes. [1](#0-0) 

### Proof of Concept
1. Construct RLP-encoded bytes representing `AccountKeyTypeRoleBased` with an empty inner list: `rlp.Encode([]interface{}{accountkey.AccountKeyTypeRoleBased, [][]byte{}})`.
2. Feed these bytes through any path that constructs an `AccountKeyRoleBased` via `DecodeRLP` (e.g., `KaiaAPI.DecodeAccountKey`, or an account-update transaction's key field decode in `TxInternalDataAccountUpdate.fromSerializable` / `UnmarshalJSON`). [4](#0-3) 
3. If this decoded, zero-length `AccountKeyRoleBased` is subsequently passed to `.Validate(...)` (as used for signature checks) without first passing through `CheckInstallable`, the process panics at `(*a)[RoleTransaction]` due to index out of range on an empty slice.

Because I could not fully trace, within the available investigation budget, a concrete unauthorized call path that invokes `Validate()` on such a value while bypassing `CheckInstallable`, this analog should be treated as a **plausible but not fully confirmed** vulnerability requiring code-path verification (specifically whether any account-key handling route stores/validates a role-based key without first calling `CheckInstallable`).

```go
func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
```

```go
func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
```
