## Analysis

The external report's core invariant: **a single blocked/frozen token prevents a user from closing out their entire position, with no way to force closure or exclude just the blocked asset.** The Hyperbridge analog is in the Intent Gateway's escrow release path, where a single non-transferable input token can permanently lock an entire multi-token order's escrow.

### Where this lives

`_withdraw` in `IntentsBase.sol` iterates over **all** of an order's escrowed input tokens and transfers each one in a single loop, with no per-token isolation: [1](#0-0) 

This single function is the only path by which escrow is ever released, and it is called from three separate flows:

1. **Same-chain cancel** — `_cancelSameChain` in `IntrinsicIntents.sol` collects every remaining input token and calls `_withdraw` for the full set in one shot: [2](#0-1) 

2. **Cross-chain settlement/refund** — `onAccept` handles both `RedeemEscrow` and `RefundEscrow` by calling `_withdraw`/`withdraw` for all of `order.inputs`: [3](#0-2) 

3. **Source-side cancel GET response** and the Tron variant's equivalent `withdraw()`, which uses low-level `.call` + `revert TransferFailed()` on any failed transfer, again over the full token list: [4](#0-3) 

Critically, all of the cross-chain cancel/refund dispatches are sent with `timeout: 0`, meaning they **never time out** and therefore have no fallback recovery path if delivery keeps reverting: [5](#0-4) 

### Title
Single non-transferable input token permanently locks an entire order's multi-token escrow with no force/partial-withdraw path - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` (and its Tron/EVM analogs' `withdraw`) transfers every token in `body.tokens` inside one loop with no isolation or try/catch per token. If any single input token an order escrowed becomes non-transferable at redemption time — e.g., a blacklist-capable stablecoin (USDC/USDT-style `isBlacklisted`) blacklists the beneficiary or the token contract is paused/upgraded to revert transfers — the entire withdrawal reverts, blocking recovery of **every other, perfectly-transferable token** escrowed in that same order commitment. Because cross-chain cancel/refund/redeem dispatches use `timeout: 0` (no expiry), and there is no governance/self-service function to skip a single stuck token or force a partial release, the escrow becomes permanently locked with no recovery mechanism — mirroring the reported "can't force-close/repay because one token is blocked" bug class.

### Finding Description
An order's `inputs` array can contain multiple distinct ERC-20 tokens escrowed together under one `commitment`. All three withdrawal entry points — same-chain cancel, cross-chain `RedeemEscrow`/`RefundEscrow` settlement via `onAccept`, and source-side cancel via `onGetResponse` — funnel through a single all-or-nothing loop (`_withdraw`/`withdraw`) that calls `safeTransfer`/`.call` for every token in the request. There is no per-token error handling, no way to specify "skip this token," and no governance override that lets the beneficiary reclaim escrow for the tokens that *are* transferable while leaving the blocked one behind. Since `_filled[commitment]` (or the order state) is only updated as part of the same atomic transaction, a revert on one token transfer rolls back the entire withdrawal — the order remains open and unrefunded/unsettled indefinitely.

### Impact Explanation
This directly causes fund lock (a form of loss for the user/solver): all input tokens in the affected order, not just the one that becomes non-transferable, become permanently escrowed and unreachable. Because dispatches for cancellation and settlement messages use `timeout: 0`, the ISMP layer offers no automatic fallback — a reverting `onAccept`/`onGetResponse` handler simply means the relayer can keep resubmitting the same message forever without success, and the fee/escrow stays stuck. This satisfies the bounty's "stealing or loss of funds" / "bridged assets... must move exactly once and only to the rightful beneficiary" pivot, since here they move to no one at all, permanently.

### Likelihood Explanation
Multi-token orders escrowing a mix of tokens are a normal, expected usage pattern for the Intent Gateway (not a contrived edge case). Any token with owner-controlled compliance features (blacklist, pause) escrowed as one of several inputs is sufficient to trigger this — no malicious peer, relayer, or governance compromise is required, only ordinary external token-issuer behavior acting on the beneficiary address, which is a realistic, foreseeable production condition for common stablecoins.

### Recommendation
Make `_withdraw` resilient to individual token transfer failures: wrap each per-token transfer in a try/catch (or use a low-level call and record failures instead of reverting), decrement escrow and finalize the order for the tokens that succeed, and retain only the failed token's escrow in a separate "stuck" bucket that can be retried independently or swept via a dedicated recovery/force-withdraw entry point (analogous to a "force" flag) that lets the beneficiary or governance reclaim/re-attempt release of the blocked token without holding the rest of the order hostage.

### Proof of Concept
1. User places a same-chain (or cross-chain) order with `inputs = [TokenA, TokenB]`, where `TokenB` is a compliance-token (e.g., mimics USDC `blacklist`).
2. After escrow, `TokenB`'s issuer blacklists the order's beneficiary/user address (a normal, permissionless-to-Hyperbridge action by the token issuer).
3. User calls `cancelOrder` (same-chain) or the cross-chain cancel/refund path completes and dispatches the `RefundEscrow`/`RedeemEscrow` message.
4. `_withdraw`/`withdraw` iterates `[TokenA, TokenB]`; the `TokenB` transfer reverts (blacklisted recipient), reverting the whole call — `TokenA`'s otherwise-valid transfer never happens, and for the cross-chain path the ISMP message (dispatched with `timeout: 0`) can be resubmitted indefinitely by any relayer but will always fail the same way.
5. Both `TokenA` and `TokenB` remain escrowed under `_orders[commitment]` forever, with no function in `IntentsBase.sol`/`IntentGatewayV2.sol` allowing the user to force a partial withdrawal of `TokenA` alone.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
