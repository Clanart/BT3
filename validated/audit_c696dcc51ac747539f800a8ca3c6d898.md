### Title
Copilot conflict resolution silently drops unresolved merge conflicts when the model returns fewer hunk resolutions than actual conflict markers - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
Github Desktop's Copilot-assisted merge/rebase/cherry-pick conflict resolution reassembles a resolved file by splicing model-provided per-hunk resolutions into the original conflicted file, matching resolutions to conflict-marker blocks **purely by array order/index**, with no validation that the number of resolutions returned by the model equals the number of actual conflict-marker blocks present in the file. If they don't match, trailing conflict blocks are silently deleted (both "ours" and "theirs" content removed) rather than flagged as an error, and the corrupted file is written to disk and staged automatically.

### Finding Description
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` parses a conflicted file into `IConflictHunk[]` and this data is what gets sent to the model in `formatConflictContextForPrompt`. [1](#0-0) 

The model's raw response is parsed by `parseCopilotConflictResolution`, which validates only that `hunks` is a non-empty array of strings without conflict markers — it never cross-checks the count against the number of conflict blocks actually present in the file being resolved: [2](#0-1) 

`reassembleResolutions` then calls `reassembleResolvedFile(ctx.rawContent, raw.hunks)` with no length check against `ctx.hunks.length`: [3](#0-2) 

`reassembleResolvedFile` walks the raw on-disk content, and for every well-formed conflict-marker block it finds, it unconditionally skips the marker lines (`i = closingIndex + 1`) and only pushes replacement content **if** a corresponding resolution index still exists: [4](#0-3) 

If `hunkResolutions.length` is smaller than the real number of conflict blocks (e.g. the model under-counts hunks in a large/complex file, truncates its JSON output because the file has many conflicts, or is confused by attacker-crafted content that superficially looks like extra/fewer conflict regions), every conflict block beyond `hunkIndex` is dropped entirely — **both sides' code silently disappears**, with no error, warning, or fallback to leaving markers in place.

The corrupted content is then written straight to disk and staged in `_applyCopilotConflictResolutions`, with no re-diff/re-validation against the original hunk count before staging: [5](#0-4) 

The only pre-write guard is a check for whether the file's on-disk conflict status still shows unresolved markers (to avoid clobbering manual edits) — it does not detect silent hunk loss: [6](#0-5) 

Since the attacker's branch/repository is the source of the conflicting content and hunk count/complexity (files with many conflicts, deeply nested or unusual marker patterns, or content engineered to make the model miscount), an attacker who controls a branch/PR that the victim merges, rebases onto, or cherry-picks from can reliably trigger scenarios where the model's hunk count diverges from the true count, producing this silent deletion.

### Impact Explanation
This breaks the invariant that Desktop's Copilot conflict-resolution feature only ever replaces the *conflicted region* while preserving all non-conflicted code verbatim. Instead, unresolved trailing conflicts in a multi-conflict file can be silently erased — deleting code from both the "ours" and "theirs" side — and that corrupted result is written to disk, staged, and (once the user clicks "Continue Merge"/commits) becomes part of the commit history that may be pushed to a shared remote. This is exactly the "silent corruption of what the user commits or pushes" impact category: no revert, no error dialog, the user only sees the model's reasoning/summary text, not proof that every conflict block was actually resolved.

### Likelihood Explanation
Triggering this does not require any special access beyond what an attacker doing a normal PR/branch-based social engineering-free contribution already has: control over the *content* of a branch that ends up in conflict with the victim's branch during a normal merge/rebase/cherry-pick. Files with many conflict hunks (common in generated files, lockfiles-adjacent code, or large refactors) increase the chance the model under-returns hunks relative to the true count, and there is no code path that detects or prevents the mismatch — the count is never checked anywhere between generation and disk write.

### Recommendation
In `reassembleResolutions` / `reassembleResolvedFile`, validate that `raw.hunks.length === ctx.hunks.length` (the count computed by `extractConflictHunks`) before reassembly, and throw a `CopilotValidationError` (already used elsewhere for malformed responses) on mismatch instead of silently dropping unmatched conflict blocks. As defense in depth, `reassembleResolvedFile` should fail closed (leave the original conflict markers in place, or throw) rather than delete content when `hunkIndex >= hunkResolutions.length`.

### Proof of Concept
1. In a repository, create a file with 3 separate conflict-marker blocks (e.g. via a real merge conflict), each containing distinguishable content in "ours" and "theirs".
2. Trigger Desktop's "Resolve with Copilot" flow. Simulate/observe a model response (as parsed by `parseCopilotConflictResolution`) that only contains 2 entries in `hunks` for that file's `path` — this is plausible in practice if the model miscounts hunks in a complex file or its JSON output is truncated before the third hunk object.
3. `reassembleResolutions` → `reassembleResolvedFile` is invoked with `rawContent` containing 3 marker blocks but only 2 `hunkResolutions`.
4. Confirm (as shown by the existing unit tests in `app/test/unit/copilot-conflict-resolution-test.ts` covering `reassembleResolvedFile`'s splicing logic) that for the third block, `hunkIndex < hunkResolutions.length` is false, so nothing is pushed to `resultLines` — the third conflict's content (both ours and theirs) is missing entirely from the returned string, with no error raised.
5. `_applyCopilotConflictResolutions` writes this shortened content to disk via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and stages it, completing the silent corruption.
