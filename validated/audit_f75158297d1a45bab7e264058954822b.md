### Title
Daemon websocket `register_service` allows any TLS-authenticated client to impersonate any service and intercept/forward internal daemon traffic - (File: chia/daemon/server.py)

### Summary
The Chia daemon (`chia/daemon/server.py`) authenticates websocket clients only via mutual TLS against a single shared private CA, and then lets any successfully-connected client freely claim an arbitrary `service` identity via the `register_service` command. All later routing of "internal" daemon traffic (messages whose `destination` is not `"daemon"`) is dispatched purely by that self-declared string, with no binding between the TLS client-certificate identity and the claimed service name. This mirrors the Presto/Trino CVE-2020-15087 bug class: a party that is authenticated at the transport layer (able to reach the "internal" control-plane socket) can bypass authorization checks that are supposed to be tied to a specific privileged role, simply by directly invoking the internal API/registration path.

### Finding Description
`WebSocketServer` accepts any client that presents a certificate signed by the configured private CA (`ssl_context_for_server` — `verify_mode = CERT_REQUIRED`, checked only against the CA, not against a specific per-service identity): [1](#0-0) [2](#0-1) 

Once the TLS handshake succeeds, `incoming_connection()` reads JSON envelopes and dispatches them through `handle_message()`: [3](#0-2) 

`register_service` accepts the caller-supplied `service` string with no check that the connecting certificate/peer actually corresponds to that service: [4](#0-3) 

Any `destination != "daemon"` message is then forwarded verbatim to every websocket registered under that destination name, again with no verification of the sender's privilege relative to the destination service: [5](#0-4) 

The daemon's own context documentation confirms there is no peer-style authorization model here — the daemon relies solely on possessing a valid mutual-TLS cert, and treats registered service names as full routing authorities: [6](#0-5) 

Because private certs for `full_node`, `wallet`, `farmer`, `harvester`, `timelord`, `crawler`, `data_layer`, and `solver` are all signed by the *same* user private CA (per `chia/ssl/`), any local/trusted process holding one of these certs — e.g. a harvester in a remote-harvester setup, or any locally-installed lower-privilege service — can connect to the daemon socket and register itself as `"chia_wallet"`, `"wallet_ui"`, or any other higher-trust service name: [7](#0-6) 

Test code demonstrates the exact registration flow with no service-identity enforcement, confirming any client can freely (re)register under arbitrary names and receive full command routing: [8](#0-7) 

### Impact Explanation
An entity that only holds a private-CA-signed certificate for a lower-trust local service (not the actual `wallet`/`daemon` process) can register itself under the `chia_wallet`, `wallet_ui`, or other privileged service name at the daemon. Because `handle_message()` blindly forwards messages addressed to that `destination` to every socket registered under it, this lets the rogue registrant:
- Receive commands/state-change pushes intended for the real wallet/daemon-facing UI (potential information disclosure of RPC traffic, e.g. `get_blockchain_state`, keyring status notifications).
- Answer as if it were the legitimate service, letting it return forged responses to RPC callers or the GUI that trust the `destination`-routed reply, enabling downstream logic (wallet, CLI, GUI) to act on falsified data.
- Interfere with the daemon-mediated keychain/passphrase notification flow (`keyring_status_changed`) by squatting on the `wallet_ui` name.

This is an authorization-bypass on the local daemon "internal API" analogous to the Presto CWE-285 report: a lesser-privileged, already-authenticated party gains internal-API-level behavior it should not be entitled to, without any additional identity check binding the TLS cert to the claimed role.

### Likelihood Explanation
Requires the attacker to already possess a certificate trusted by the private CA (e.g., as an already-configured local service, remote harvester, or any local process that obtained daemon/private certs), which is a realistic scenario in the same class the Presto advisory addresses ("authenticated users... with secure internal communication configured" bypassing authorization on internal APIs). No additional privilege beyond basic connectivity to the daemon socket and a valid private cert is required to exploit the missing identity binding.

### Recommendation
Bind registered service identity to the connecting certificate (e.g., verify the certificate's CN/fingerprint matches an expected identity for the claimed `service` name, or require distinct per-service certs used only by their owning process) before accepting `register_service`, and reject/rate-limit destination-forwarding to sockets whose registered identity was not cryptographically validated against the certificate presented at connection.

### Proof of Concept
1. Start a local Chia daemon and a legitimate service (e.g. wallet) as normal.
2. From any other local process holding a private-CA-signed certificate (any generated private cert, e.g. a harvester's), open a websocket to `wss://127.0.0.1:{daemon_port}` using that certificate.
3. Send `register_service` with `data={"service": "wallet_ui"}` (as shown in the test harness pattern): [9](#0-8) 
4. The daemon accepts the registration without validating that the connecting certificate belongs to the real wallet UI, per `register_service()`: [10](#0-9) 
5. Subsequent daemon messages destined for `"wallet_ui"` (e.g., `keyring_status_changed` state-change pushes) are now also delivered to the rogue socket, and the rogue socket can send responses that legitimate `destination`-based routing will accept as coming from that service.

```python
def ssl_context_for_server(
    ca_cert: Path,
    ca_key: Path,
    cert_path: Path,
    key_path: Path,
    *,
    check_permissions: bool = True,
    log: logging.Logger | None = None,
) -> ssl.SSLContext:
    if check_permissions:
        verify_ssl_certs_and_keys([ca_cert, cert_path], [ca_key, key_path], log)

    ssl_context = ssl._create_unverified_context(purpose=ssl.Purpose.CLIENT_AUTH, cafile=str(ca_cert))  # ruff: ignore[suspicious-unverified-context-usage]
    ssl_context.check_hostname = False
    ssl_context.minimum_version = ssl.TLSVersion.TLSv1_3
    ssl_context.load_cert_chain(certfile=str(cert_path), keyfile=str(key_path))
    ssl_context.verify_mode = ssl.CERT_REQUIRED
    return ssl_context
```

```python
    async def register_service(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        self.log.info(f"Register service {request}")
        service = request.get("service")

            self.log.error("Service Name missing from request to 'register_service'")
            return {"success": False}
        if service not in self.connections:
            self.connections[service] = set()
        self.connections[service].add(websocket)
```

```markdown
## Wire And Routing Contracts

- Daemon messages are JSON dictionaries with `command`, `ack`, `data`,
  `request_id`, `destination`, and `origin`. `format_response()` flips
  origin/destination, preserves the request id, and sets `ack=True`.
- `destination != "daemon"` is pure service forwarding. The daemon does not
  interpret the command or payload if the destination is registered; it serializes
  the original message and sends it to all websockets registered under that
  destination.
- `register_service` adds the current websocket to `connections[service]`.
  Multiple registrations of the same websocket for the same service collapse
  through the set; one websocket may register for multiple services and
  `remove_connection()` must remove it from all of them.
- There is no peer-style protocol enum, streamable binary framing, node-type map,
  or rate limiter here. The primary gate is mutual TLS using daemon private
  certs plus local config (`self_hostname`, `daemon_port`,
  `daemon_max_message_size`, `daemon_heartbeat`).
```

```markdown
- There are two parallel trust domains. Public certs are signed by the bundled Chia CA and are used for ordinary public peer connections. Private certs are signed by the user's private CA and are used where the peer must be one of the user's trusted services.
- Private certs are generated for `full_node`, `wallet`, `farmer`, `harvester`, `timelord`, `crawler`, `data_layer`, `daemon`, and `solver`. Public certs are generated for `full_node`, `wallet`, `farmer`, `introducer`, `timelord`, `data_layer`, and `solver`.
- `ChiaServer.create()` encodes the operational matrix: harvesters use private certs as clients; harvester/farmer/wallet/data_layer servers require private-CA client certs; other peer servers use the public Chia CA. Changing generation lists or config paths without updating this matrix can silently break service startup or peer admission.
- Daemon and RPC traffic use daemon private certs with the private CA. This is a local/admin trust boundary, distinct from public peer TLS.
```
