## Title
Wallet message-signing scheme lacks domain separation for raw-signing modes, enabling blind-signature reuse to authorize unintended `AGG_SIG_UNSAFE` coin spends - (File: `chia/wallet/util/signing.py`, `chia/consensus/condition_tools.py`)

### Summary
The reported bug is that `ProxyFactory.deployProxyAndDistributeBySignature()` builds an EIP-712 `digest` without a `typeHash` and without hashing the dynamic `data` field, so the value being signed carries no structural/domain separation — a raw signature can be replayed or repurposed outside its intended context. The closest reachable analog in this codebase is Chia's generic wallet message-signing API (`sign_message`, exposed via `sign_message_by_address` / `sign_message_by_id`), which — unlike the CHIP-0002 mode — allows signing with **no structural prefix or domain separation at all** when the caller selects the raw BLS "message augmentation" signing modes. Because these modes sign with the exact same synthetic private key that also authorizes on-chain `AGG_SIG_UNSAFE` conditions, and because `AGG_SIG_UNSAFE` messages are otherwise almost unconstrained, a signature produced for an apparently harmless "sign this message" request can be repurposed as the authorization for a completely different, attacker-chosen coin spend.

### Finding Description
`chia/wallet/util/signing.py` defines `sign_message()`: [1](#0-0) 

For `SigningMode.CHIP_0002` / `CHIP_0002_HEX_INPUT`, the message is wrapped and hashed as `Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash()` — this is the CHIP-0002 equivalent of an EIP-712 "typed" hash: it binds the signed value to a well-known constant prefix ("Chia Signed Message"), providing domain separation. However, for `BLS_MESSAGE_AUGMENTATION_UTF8_INPUT` and `BLS_MESSAGE_AUGMENTATION_HEX_INPUT`, the code signs the **raw bytes of the message with no prefix, no typehash, and no domain separation whatsoever**: [2](#0-1) 

This is directly analogous to the EIP-712 bug: the "structured" (CHIP-0002) mode correctly separates the signing domain, but an alternate, reachable code path bypasses that separation and signs an unstructured payload — exactly like the reported `abi.encode(contestId, data)` digest that skips `typeHash`/`hashStruct`.

The danger is that the *same synthetic private key* used here (`convert_secret_key_to_synthetic(...)`, see `wallet_rpc_api.py`) is the key that also produces `AGG_SIG_ME`/`AGG_SIG_UNSAFE` signatures authorizing actual coin spends: [3](#0-2) 

`AGG_SIG_UNSAFE` in consensus is verified against the raw signed bytes with essentially no coin/puzzle binding — the only restriction is that the message must not *end with* one of the well-known `AGG_SIG_*_ADDITIONAL_DATA` suffixes: [4](#0-3) 

Because the raw signing modes produce `AugSchemeMPL.sign(secret_key, raw_message_bytes)` with no structural wrapper, an attacker can construct a puzzle/coin spend that requires `AGG_SIG_UNSAFE(victim_pubkey, X)` for an arbitrary byte string `X` of the attacker's choosing (as long as `X` doesn't end in the specific 32-byte additional-data constants), then social-engineer the victim into calling `sign_message_by_address`/`sign_message_by_id` with `safe_mode=False` and that exact message `X` (e.g., disguised as an "authentication" or "verification" message). The resulting signature is a fully valid `AGG_SIG_UNSAFE` witness that the attacker can insert into a spend bundle to unlock the victim's coin(s) that use `AGG_SIG_UNSAFE` with that pubkey — without any further interaction from the victim.

### Impact Explanation
If successfully exploited, this is a genuine unauthorized-coin-movement primitive: a blind-signed "message" — obtained through a client-facing feature (wallet CLI/RPC `sign_message`) explicitly intended for off-chain identity proofs — can be weaponized to satisfy an on-chain spend condition (`AGG_SIG_UNSAFE`) tied to the victim's key, letting an attacker construct and broadcast a spend bundle that moves the victim's coins. This matches the "unsigned or unauthorized coin movement" impact class.

### Likelihood Explanation
Exploitation requires social engineering (getting the victim to sign a specific raw byte string via `safe_mode=False`) and requires that some coin in the victim's wallet's control uses `AGG_SIG_UNSAFE` with the reused pubkey (which is not the default `p2_delegated_puzzle_or_hidden_puzzle` receive path but is reachable in custom puzzle/offer scenarios accepting `AGG_SIG_UNSAFE` with a wallet-controlled pubkey). This makes it Medium likelihood — it is a real, structural gap (no domain separation on non-CHIP-0002 modes) analogous to the EIP-712 finding, but it is not trivially triggerable without user interaction.

### Recommendation
- Default the `sign_message` RPC to always use the domain-separated CHIP-0002 mode; treat raw `BLS_MESSAGE_AUGMENTATION_*` (`safe_mode=False`) as a clearly labeled "danger zone" that requires explicit, unambiguous user confirmation displaying the exact raw bytes being signed.
- Consider deprecating/removing the unsafe raw-signing modes from the RPC surface reachable by less-trusted callers, or requiring that raw signed messages be constrained (e.g., minimum-length, forbidden byte patterns) so they cannot coincide with a valid `AGG_SIG_UNSAFE` condition value.
- Mirror the EIP-712 fix conceptually: always include a type/context-identifying prefix (as CHIP-0002 does) before hashing/signing, rather than allowing an unstructured raw-bytes signing path.

### Proof of Concept
1. Attacker builds a coin `C` (could be an offer, a puzzle requiring multi-party signoff, etc.) whose puzzle requires `AGG_SIG_UNSAFE(victim_pubkey, X)` for a chosen byte string `X` not ending in any `AGG_SIG_*_ADDITIONAL_DATA` constant, per the check in `condition_tools.py`.
2. Attacker convinces the victim (e.g., via a fake "verify your identity" flow) to run `chia wallet sign_message -m <hex(X)> --safe_mode false` / call `sign_message_by_address` with `safe_mode=False`, causing `sign_message()` in `chia/wallet/util/signing.py` to sign the raw bytes `X` with the victim's synthetic key.
3. Attacker takes the returned signature and inserts it into a `SpendBundle` spending coin `C`, satisfying the `AGG_SIG_UNSAFE` condition and moving the victim-controlled coin as they choose. [1](#0-0) [5](#0-4) [3](#0-2)

def sign_message(secret_key: PrivateKey, message: str, mode: SigningMode) -> SignMessageResponse:
    public_key = secret_key.get_g1()
    if mode == SigningMode.CHIP_0002_HEX_INPUT:
        hex_message: bytes = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, bytes.fromhex(message))).get_tree_hash()
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_UTF8_INPUT:
        hex_message = bytes(message, "utf-8")
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT:
        hex_message = bytes.fromhex(message)
    else:
        hex_message = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash()
    return SignMessageResponse(
        pubkey=public_key,
        signature=AugSchemeMPL.sign(secret_key, hex_message),
    )
