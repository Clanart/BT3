## Finding

### Title
Solver beneficiary is never validated before cross-chain `RedeemEscrow`, permanently locking escrowed order inputs - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
This mirrors the Ignite bug class: a beneficiary-receive check exists on some payout paths but is missing on the path that actually matters — the *asynchronous* settlement call that finalizes escrow release. In `IntentGatewayV2`/`IntentsV2`, the solver address that will receive escrowed native-token inputs is fixed at `fillOrder` time on the **destination** chain, but is never checked for its ability to receive native value on the **source** chain where the payout actually happens later via `_withdraw`.

### Finding Description
When a solver fills a cross-chain order, `msg.sender` (the solver) is embedded as the `beneficiary` of a `WithdrawalRequest` and dispatched cross-chain as a `RedeemEscrow` message: [1](#0-0) 

No validation is performed anywhere in `fillOrder` that `msg.sender` can actually receive a native-token transfer — unlike Ignite's `registerWithStake`, which explicitly probes `msg.sender.call("")` before accepting stake.

Later, on the source chain, the host delivers this `RedeemEscrow` request and the gateway processes it via `_withdraw`, which performs the actual native-token payout with a low-level call and **reverts the entire settlement on failure**: [2](#0-1) 

If the solver address cannot accept native ETH on the source chain (e.g., it is a contract address with no `receive`/payable `fallback`, or the same address resolves to different, non-payable bytecode on the source chain), `beneficiary.call{value: amount}("")` fails and `_withdraw` reverts with `InsufficientNativeToken()`. Because this call happens inside the host's terminal `onAccept` processing of the incoming `RedeemEscrow` POST request, the revert is not a soft failure — the order was already recorded/settled as filled on the destination chain (the solver already delivered the output assets and the order commitment on the destination is finalized), so the source-side cancellation path (`_cancelFromSource` → GET query of the `_filled` slot) will observe the order as filled and refuse to release escrow through that path either.

### Impact Explanation
This produces the exact "redemption not guaranteed" invariant break described in the Ignite report: value (the solver's rightfully-owed escrowed input tokens) becomes permanently unredeemable and locked in the `IntentGatewayV2`/intents contract, with no admin or retry path to redirect the payout to a different, valid address, since the beneficiary is derived immutably from `msg.sender` at fill time and baked into the cross-chain message. This is a direct loss-of-funds condition on a production settlement path (escrow release), matching the bounty's "stealing or loss of funds" impact category.

### Likelihood Explanation
No malicious relayer, prover, or governance actor is required. An ordinary, unprivileged solver — including one operating through a smart-contract wallet, multisig, or any contract account without a payable fallback — can trigger this simply by calling `fillOrder` normally. The condition is entirely a function of the solver's own address bytecode on the source chain, which the solver may not control or may not be aware of (e.g., counterfactual/undeployed contract wallets, or the same address deployed with different code on different chains). This makes the trigger conditions realistic and squarely within reach of a normal user of the intents system.

### Recommendation
- Before dispatching a `RedeemEscrow` request (or before finalizing `_withdraw`), verify that the beneficiary can accept a native-token transfer, mirroring Ignite's `registerWithStake` pattern (e.g., a zero-value `call` probe), and reject the fill early rather than after cross-chain commitment.
- Alternatively, decouple settlement finality from the native-token push: on failed native transfer, credit the beneficiary in an internal claimable balance (pull pattern) rather than reverting the entire `onAccept` handler, so a stuck beneficiary cannot block or permanently lock the underlying escrow release.
- Add a recovery/redirect mechanism allowing the recorded beneficiary to specify an alternate receiving address if the original cannot accept funds, gated by proof of ownership (e.g., signature from the original beneficiary key), instead of leaving funds irrecoverably stuck in contract storage.

### Proof of Concept
1. Solver deploys/uses a contract wallet `S` on the source chain that has no `receive()`/payable `fallback()`.
2. User places a cross-chain order on the source chain with a native-token (`address(0)`) input, per `placeOrder` (evm/src/apps/IntentGatewayV2.sol#L162 escrow logic).
3. Solver calls `fillOrder` on the destination chain from `S`, delivering the required outputs; `ExtrinsicIntents.sol` builds and dispatches a `RedeemEscrow` `WithdrawalRequest` with `beneficiary = S`.
4. The `RedeemEscrow` message is relayed and proven on the source chain; the host invokes `onAccept`, which calls `_withdraw` with `beneficiary = S` and `token = address(0)`.
5. `S.call{value: amount}("")` fails since `S` has no payable fallback; `_withdraw` reverts `InsufficientNativeToken()`, causing `onAccept` to revert.
6. The destination chain has already recorded the order as filled (solver already delivered outputs), so `_cancelFromSource`'s GET-based recovery path will see `_filled` populated on destination and refuse to release escrow via cancellation.
7. The escrowed native-token input becomes permanently locked in the source-chain gateway contract, with no code path to redirect it to a receivable address. [2](#0-1) [1](#0-0)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
