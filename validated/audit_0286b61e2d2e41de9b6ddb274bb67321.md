### Title
`ThresholdKeys::read`/`ThresholdKeys::new` performs no authorization/consistency check between the secret share, the verification shares, and the derived group key — attacker-supplied bytes define an attacker-known group key - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the missing authorization check on Klaw's `/resetMemoryCache` (an unprivileged caller invoking a state-defining operation without proving it is entitled to the resulting state), `ThresholdKeys::new` — reachable with fully attacker-controlled bytes through `ThresholdKeys::read` — accepts a `secret_share` and a `verification_shares` map and derives the group's public key solely by interpolating the first `t` verification shares, without ever checking that the bearer of these keys actually holds the corresponding secret (i.e., that `secret_share * G == verification_shares[params.i()]`), or that the shares are mutually consistent.

### Finding Description
`ThresholdKeys::new` validates only the *count* of verification shares and that participant indexes are `<= n` [1](#0-0) . It then computes `group_key` as the Lagrange/Constant interpolation over only participants `1..=t` [2](#0-1) . No statement ties `secret_share` to `verification_shares[i]`, nor the remaining `n - t` shares to the same polynomial.

`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation coefficients, the secret share, and all `n` verification shares directly from the byte stream and forwards them to `ThresholdKeys::new` [3](#0-2) . An attacker who can supply this byte stream (restore/migration/provisioned key material) therefore chooses:

- `verification_shares[1..=t]` so the interpolated `group_key` equals `x·G` for an attacker-known scalar `x`;
- `verification_shares[i]` and `secret_share` arbitrarily, e.g., `secret_share = 1`, `verification_shares[i] = G`.

Every check in `new` passes. `group_key()` now returns the attacker's key [4](#0-3) , and `view()` produces "valid-looking" `ThresholdView`s whose secret share does not correspond to the group key [5](#0-4) .

### Impact Explanation
The node treats the attacker-defined point as its own threshold group key. Any downstream use that derives receive addresses from `group_key()` (e.g., bitcoin-serai's scanner/address derivation over the validator set key) causes deposits to be attributed to and credited under a key whose discrete logarithm only the attacker knows. Funds are reported received yet are spendable only by the attacker — outright theft, not mere denial of service. Signing with the forged share produces signature shares that fail verification, so the victim cannot recover the funds through the honest signing path either.

### Likelihood Explanation
Requires the attacker to feed crafted bytes into `ThresholdKeys::read`. Per the engagement scope, `ThresholdKeys::read` is an in-scope sink for untrusted bytes (key provisioning/restore paths). No collusion, no leaked key material, and no protocol participation is needed — the entire malicious input is a single self-consistent byte string.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `read`), verify that `C::generator() * secret_share == verification_shares[&params.i()]` and, for `Interpolation::Constant`, that every verification share equals the multiexp of the coefficients evaluated at that participant index. Reject any key material that fails this self-consistency check.

### Proof of Concept
```rust
// For any Ciphersuite C with t = 2, n = 3, i = 2:
// Attacker picks x, sets:
//   verification_shares[1] = x*G - shares such that interpolation over {1,2}
//   yields x*G; simplest: set share1 = x*G * L1, share2 = x*G * L2.
//   verification_shares[3] = arbitrary valid point.
//   secret_share = F::ONE  (victim's real share is irrelevant/unknown).
// Serialize via ThresholdKeys::write format and deliver to the victim.
// Victim calls ThresholdKeys::read -> Ok(...), group_key() == x*G.
// Attacker spends anything sent to x*G with scalar x.
```
The gap is the absent check at `ThresholdKeys::new` [6](#0-5) : the constructor is the only gatekeeper for deserialized keys, and it authorizes the key set without proof the holder knows a share consistent with the derived group key — the same shape as Klaw performing a privileged reset without verifying the caller's authority over the affected state.

  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }
