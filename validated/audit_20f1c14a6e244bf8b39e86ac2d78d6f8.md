### Title
Silent `git checkout-index` exit-code masking allows discard-changes to abandon attacker-influenced files without error - ([File: app/src/lib/git/checkout-index.ts])

### Summary
GitHub Desktop's `checkoutIndex()` helper — used as the final step of the "Discard Changes" feature — whitelists exit code `1` as a success condition and never inspects `stdout`/`stderr` of the underlying `git checkout-index` invocation to confirm that every requested path was actually restored. [1](#0-0) 
This mirrors the ERC20 "unchecked return value" bug class: a call whose result can silently indicate partial/failed completion is treated as unconditional success by the caller.

### Finding Description
`checkoutIndex()` runs `git checkout-index -f -u -q --stdin -z` with `successExitCodes: new Set([0, 1])` and the `-q` flag, which explicitly suppresses errors for paths that don't exist in the index. [2](#0-1) 
The `git()` wrapper in `core.ts` only throws when the exit code is *not* in `successExitCodes` (or the parsed git error isn't in `expectedErrors`); it never validates that the operation's output/behavior matches the caller's expectations beyond the raw exit code. [3](#0-2) 

This function is the last step of `GitStore.discardChanges()`, which is documented as: move modified/new files to trash, `git reset` staged paths, then `git checkout-index` to restore the working directory to match the index/HEAD for the discarded paths. [4](#0-3) [5](#0-4) 

Because exit code `1` is accepted as success and `-q` silences path-not-found errors, if a maliciously crafted repository (e.g., a cloned/checked-out repo containing unusual index entries — conflicting stage entries, submodule/gitlink placeholders, symlink-vs-file type changes, or index corruption crafted by a remote/attacker-controlled `.git` history) causes `checkout-index` to fail for a subset of the requested paths, `checkoutIndex()` returns normally with no indication of partial failure. The caller (`GitStore.discardChanges`) treats the whole operation as successful and the UI reports the discard as complete, refreshing the repository state via `_refreshRepository`. [6](#0-5) 

The result is that files the user believed were "discarded" (restored to the last committed state) may retain content the user did not intend — most dangerously, an attacker who controls what's checked out (e.g., via a crafted fork/PR branch, a malicious submodule commit, or an index entry that trips up `checkout-index`) can cause the discard to be silently incomplete, leaving unreviewed/unexpected content in the working tree. If the user subsequently stages and commits (git add / commit all), that leftover content is committed and pushed without the user's knowledge — a silent corruption of what the user commits.

### Impact Explanation
This does not grant remote code execution, but it breaks the integrity guarantee of the "Discard Changes" action: the user is told changes were discarded, yet content can persist and later be silently included in a commit/push. This fits the "silent corruption of what the user commits or pushes" impact category, since no error surfaces to the user (`-q` plus `successExitCodes: [0,1]` swallow the specific failure).

### Likelihood Explanation
Exploitation requires a specific combination — a repository state (achievable by cloning/checking out an attacker-supplied branch, fork, or submodule) that causes `checkout-index` to exit 1 for one or more of the exact paths the user attempts to discard while other paths succeed. This is a narrower/more contrived condition than a typical ERC20 unchecked-transfer analog, and I could not find a definitive proof that `checkout-index -f -u -q` actually fails (rather than warns) for realistic attacker-controlled index states in this codebase; the `-q` flag's precise failure modes for stage-conflict or gitlink entries were not verified in the available code/tests. This uncertainty should be treated as a gap requiring further investigation (e.g., testing with conflicted index entries, submodule gitlinks, or type-changed paths) rather than a confirmed, fully reproducible finding.

### Recommendation
- Do not blanket-accept exit code `1` as success for `checkout-index`; instead parse `stderr`/`stdout` (even with `-q`, consider dropping `-q` or checking `git status`/`git diff --name-only` afterward) to confirm every requested path was actually restored.
- After `checkoutIndex()` returns, verify via `git status`/`getStatus` that no discarded path remains modified, and surface a discard-failure error to the user if any path did not revert, rather than treating a nonzero-but-whitelisted exit code as full success.

### Proof of Concept
Full reproduction was not completed within the scope of this analysis — the exact index/working-tree state needed to make `git checkout-index -f -u -q --stdin -z` exit with code `1` for only a subset of paths (while `-q` and the whitelisted `successExitCodes` mask the failure) was not empirically confirmed against this codebase's test suite. A concrete PoC would require constructing a repository with a conflicted or gitlink/type-changed index entry for one of the discard paths and confirming `checkoutIndex()` returns without error while that specific path's content is left unmodified, then verifying it gets included in a subsequent commit/push.

```typescript
 * Note that this function will not yield errors for paths that don't
 * exist in the index (-q).
 *
 * @param repository The repository in which to update the working directory
 *                   with information from the index
 *
 * @param paths      The relative paths in the working directory to update
 *                   with information from the index.
 */
export async function checkoutIndex(
  repository: Repository,
  paths: ReadonlyArray<string>
) {
  if (!paths.length) {
    return
  }

  const options = {
    successExitCodes: new Set([0, 1]),
    stdin: paths.join('\0'),
  }

  await git(
    ['checkout-index', '-f', '-u', '-q', '--stdin', '-z'],
    repository.path,
    'checkoutIndex',
    options
  )
```

```typescript
  public async _discardChanges(
    repository: Repository,
    files: ReadonlyArray<WorkingDirectoryFileChange>,
    moveToTrash: boolean = true
  ) {
    const gitStore = this.gitStoreCache.get(repository)

    const { askForConfirmationOnDiscardChangesPermanently } = this.getState()

    try {
      await gitStore.discardChanges(
        files,
        moveToTrash,
        askForConfirmationOnDiscardChangesPermanently
      )
    } catch (error) {
      if (!(error instanceof DiscardChangesError)) {
        log.error('Failed discarding changes', error)
      }

      this.emitError(error)
      return
    }

    return this._refreshRepository(repository)
  }
```
