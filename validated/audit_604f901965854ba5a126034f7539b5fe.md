### Title
App proxy signature verification lacks timestamp freshness/expiry check, allowing indefinite replay - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification#verify_proxy_request` only validates that the HMAC signature matches the query parameters; it never checks the `timestamp` parameter against the current time or any expiry window. A previously valid, captured `query_string` + `signature` pair therefore remains valid forever and can be replayed by an attacker who observed it once.

### Finding Description
`verify_proxy_request` calls `query_string_valid?(request.query_string)`, which parses the query string, extracts the `signature`, and recomputes the expected HMAC over the remaining sorted params (including `timestamp`) using `calculated_signature`, then compares with `ActiveSupport::SecurityUtils.secure_compare`: [1](#0-0) 

The `timestamp` field is treated as just another signed parameter — it contributes to the HMAC input like `shop` or `path_prefix`, but nothing in this method (or anywhere else in the concern) reads `timestamp`, parses it as a time, or compares it to `Time.now` with any allowed skew. As long as the HMAC recomputed from the untouched, previously-observed query string matches the supplied `signature`, the request passes indefinitely — there is no code path that can return `head(:forbidden)` due to staleness.

This is confirmed by the existing test suite itself: `test "request with a valid signature should pass"` in `test/shopify_app/controller_concerns/app_proxy_verification_test.rb` uses a fixed, hardcoded `timestamp: "1466106083"` (year 2016) and still asserts `assert_response :ok` with no time travel/freezing needed, demonstrating the check has no time-bound dependency: [2](#0-1) 

An attacker who captures one valid `query_string` (via browser history, server/proxy logs, referrer leakage, or a public storefront app-proxy link) can resend that exact same request at any point in the future and it will be accepted as authentic, since the verification is purely structural/cryptographic correctness of the HMAC, not temporal validity.

### Impact Explanation
This allows unauthenticated, unbounded replay of a single captured app-proxy request against the shop's app-proxy endpoint, letting an attacker repeatedly trigger that proxy action "as" the shop indefinitely. This corresponds to a forged/accepted signed request class of impact (an app-proxy request that should require a live, unexpired signature from Shopify is instead permanently replayable), enabling repeated unauthorized invocation of app-proxy functionality for that shop.

### Likelihood Explanation
Feasibility is high given only one precondition: the attacker must have observed one valid app-proxy `query_string` + `signature` at any point in the past (e.g., via browser history, network/proxy logs, or a link shared/cached from a public storefront page rendering the proxy URL). No secrets, tokens, or additional guessing are required — the same exact string can be replayed any number of times since the check is deterministic and time-independent.

### Recommendation
Add a freshness check inside `query_string_valid?` (or `verify_proxy_request`) that rejects requests whose `timestamp` parameter is missing, non-numeric, or outside a bounded validity window (e.g., a few minutes) relative to `Time.now.to_i`, in addition to the existing HMAC comparison.

### Proof of Concept
```ruby
test "request with a stale but validly-signed timestamp should still be rejected" do
  with_test_routes do
    valid_params = {
      shop: "some-random-store.myshopify.com",
      path_prefix: "/apps/my-app",
      timestamp: "1466106083", # far in the past
      signature: "f5cd7233558b1c50102a6f33c0b63ad1e1072a2fc126cb58d4500f75223cefcd",
    }
    get :basic, params: valid_params
    # Current behavior: assert_response :ok  (replay succeeds)
    # Expected/desired behavior for a fix:
    assert_response :forbidden
  end
end
```
Running this against current code shows the request returns `200 OK` regardless of how old `timestamp` is, confirming unbounded replay is possible with a single captured valid `query_string`/`signature` pair. [3](#0-2)

```ruby
    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```
