### Title
Panic in `TransactionBatchProcessor::replenish_program_cache` when a cooperatively-tracked program account disappears before load, leaving other threads permanently blocked on the ProgramCache loading-task waiter - ([File: svm/src/transaction_processor.rs])

### Summary
`replenish_program_cache` (and its sibling `prepare_one_program_for_upcoming_feature_set`) drive Agave's `ProgramCache` cooperative-loading protocol. When a thread wins the race to load a missing program, `ProgramCache::extract()` inserts a `(slot, thread_id)` marker into `loading_entries` for that program key, and the winning thread is expected to call `load_program_with_pubkey(...).expect("called load_program_with_pubkey() with nonexistent account")` and then `finish_cooperative_loading_task()` to remove the marker and `notify()` all other waiting threads (`program-runtime/src/loaded_programs.rs`, `program-runtime/src/loading_task.rs`). If `load_program_with_pubkey` returns `None` (i.e. the program account can no longer be fetched by `get_account_shared_data` at load time), the `.expect()` panics before `finish_cooperative_loading_task` runs, so the `loading_entries` marker for that key is never removed and `notify()` is never called for that completion.

This mirrors the SYMM-IO liquidation bug class: a piece of shared state (`partyBLiquidationStatus` there; `loading_entries[program_id]` here) is set to signal "operation in progress," and completion/clearing of that state depends on a downstream check succeeding. If the downstream check fails/reverts (there: expired signature; here: account no longer loadable), the state is left "stuck" with no code path to reset it, and every other party relying on that state (there: `notLiquidated`/`notLiquidatedPartyB` modifiers; here: every other thread that calls `extract()` for the same program key) is permanently blocked.

### Finding Description
- `ProgramCache::extract()` only assigns a cooperative loading task for a program id when the `loading_entries` map has a `Vacant` entry for that key: `program-runtime/src/loaded_programs.rs` lines 735-745. Once occupied, `extract()` never overwrites or expires the entry — the only way the entry is removed is via `finish_cooperative_loading_task`, called at `program-runtime/src/loaded_programs.rs` lines 764-804.
- The single caller of this contract, `TransactionBatchProcessor::replenish_program_cache` (`svm/src/transaction_processor.rs` lines 894-972), does:
  ```rust
  let (program, last_modification_slot) = load_program_with_pubkey(
      account_loader,
      program_runtime_environment_for_execution,
      &key,
      self.slot,
      execute_timings,
  )
  .expect("called load_program_with_pubkey() with nonexistent account");
  ```
  This `.expect()` is a hard panic if `load_program_with_pubkey` returns `None`, and there is a test in the repo, `test_replenish_program_cache_with_nonexistent_accounts`, that is explicitly `#[should_panic = "called load_program_with_pubkey() with nonexistent account"]` (`svm/src/transaction_processor.rs` lines 1855-1883), confirming this is a real, reachable failure mode rather than a purely theoretical `unwrap`.
- `load_program_with_pubkey` returns `None` whenever `load_program_accounts` returns `None`, which happens simply when `callbacks.get_account_shared_data(pubkey)` no longer finds the account (`svm/src/program_loader.rs` lines 34-38, 99-114). `extract()` decided a program needed loading based on an earlier check (`filter_executable_program_accounts`, `svm/src/program_loader.rs` lines 233-276) that queries account state at a different point in time/via a different call than the later `load_program_with_pubkey` call in `replenish_program_cache`. Any window in which the program account becomes unfetchable between these two points (e.g., a concurrent close, pruning, or a fork/rollback-related account view change within the same tx-batch/thread interleaving) turns "should be loadable" into `None`, hitting the panic before the marker is cleared.
- Because the marker removal and the `loading_task_waiter.notify()` call are coupled to `finish_cooperative_loading_task`, a panic on the winning thread before that call permanently orphans the `loading_entries` entry for that program id. Every other transaction-processing thread that subsequently needs that same program id will:
  1. Fail to win the cooperative-loading race (`extract()` sees the entry `Occupied` forever).
  2. Fall into the `else` branch of `replenish_program_cache`'s loop and call `task_waiter.wait(task_cookie)` (`svm/src/transaction_processor.rs` line 969), which only wakes on a *global* `notify()` from unrelated completions — the specific program will never be loaded because no thread will ever complete the associated task.
  3. Keep looping (`missing_programs` never becomes empty for that key), effectively spinning/blocking that thread's transaction processing indefinitely, analogous to the `notLiquidated`/`notLiquidatedPartyB` modifiers reverting forever in the SYMM-IO report.

### Impact Explanation
Two concrete consequences, both severe for validator liveness/availability:
1. **Immediate process crash.** The `.expect()` is a hard panic on the transaction-processing thread. This matches the "VM-triggered node crash" acceptance criterion directly — a validator process crash triggered by ordinary account-state churn during normal SVM operation, without needing a malicious payload beyond causing the program account to become unloadable at the right moment.
2. **Permanently stuck shared cache state.** Even setting the panic aside, the `loading_entries` bookkeeping has no timeout, retry, or cleanup path if the loading thread does not reach `finish_cooperative_loading_task`. This is structurally identical to the reported bug class: a critical shared "in progress" flag that can only be cleared by a downstream step succeeding, with no recovery mechanism if that step fails. Here it can block cooperative loading of a given program indefinitely for all other transaction-processing threads referencing that program id within the process's lifetime (the entry only lives in `IndexImplementation::V1::loading_entries`, an in-memory map with no expiry).

### Likelihood Explanation
The exact conditions that cause `load_program_with_pubkey` to return `None` after `extract()` already scheduled a cooperative load are not fully characterized in the code reviewed — under normal single-threaded, sequentially-locked transaction execution, account writes (including program closes via `bpf_loader_upgradeable`'s `Close` instruction, `programs/bpf_loader/src/lib.rs` lines 686-789) are protected by Agave's account write-locking (`accounts-db/src/account_locks.rs`, `accounts-db/src/accounts.rs`), which should prevent a concurrently-executing transaction from closing a program account that another transaction is simultaneously trying to load as executable. This normally-safe invariant is exactly why the maintainers' own comment in `replenish_program_cache` states "It is not possible to mock this error for SVM unit tests purposes," and the existing test only exercises the panic by constructing an inconsistent state artificially. I was not able to verify within the available context a concrete, unprivileged-user-reachable sequence that defeats account locking to produce this window in production banking/replay — for example, whether `filter_executable_program_accounts`/`extract()` and the later `load_program_with_pubkey` call in `replenish_program_cache` can observe two different account snapshots for the same locked account within one transaction-processing pass, or whether program-cache pruning/fork-rerooting concurrently with cooperative loading could remove the underlying account view without going through the write-lock path. This is a gap in my analysis given the available tools; determining exploitability with certainty would require tracing the exact bank/AccountsDB snapshot semantics used by `AccountLoader`/`TransactionProcessingCallback::get_account_shared_data` across the `filter_executable_program_accounts` → `extract()` → `load_program_with_pubkey` sequence, which is out of reach of the current code index.

### Recommendation
- Replace the `.expect("called load_program_with_pubkey() with nonexistent account")` panics in `svm/src/transaction_processor.rs` (`replenish_program_cache` and `prepare_one_program_for_upcoming_feature_set`) with a code path that still calls `finish_cooperative_loading_task` (e.g., inserting a `FailedVerification`/`Closed` tombstone entry) before returning an error to the caller, so the `loading_entries` marker is always cleared and `loading_task_waiter.notify()` is always fired regardless of whether the load succeeded.
- Add a defensive cleanup mechanism to `ProgramCache` (e.g., clearing/timing out `loading_entries` entries owned by a thread that is known to have exited or panicked, or wrapping the load-and-finish sequence in a guard/`Drop` that removes the entry and notifies on unwind) so a single panicking thread cannot permanently starve cooperative loading for other threads.
- Audit and document the account-visibility guarantees between `filter_executable_program_accounts` and the actual `load_program_with_pubkey` call to confirm whether the two can ever disagree about account existence under the current locking model, and add regression tests exercising that specific race if it is reachable.

### Proof of Concept
A precise, unprivileged-user-triggerable PoC could not be constructed with confidence given the available code index — the repository's own test (`test_replenish_program_cache_with_nonexistent_accounts`, `svm/src/transaction_processor.rs` lines 1855-1883) demonstrates the panic occurs when `load_program_with_pubkey` is called for a key that does not exist in the account store, but that test manufactures the inconsistent state directly (calling `replenish_program_cache` with a `ProgramToLoad` for a key that was never actually present) rather than showing a production sequence that defeats account write-locking to produce the same effect organically. Reproducing the "stuck forever" analog to the SYMM-IO liquidation bug would require: (1) confirming a legitimate account-visibility race between `filter_executable_program_accounts`/`extract()` and `load_program_with_pubkey`, or (2) another means to cause the winning cooperative-loading thread to panic/exit before `finish_cooperative_loading_task` runs, then observing that all subsequent lookups of that program id via `replenish_program_cache` loop forever in `task_waiter.wait(...)`. Confirming (1) or (2) needs deeper access to the AccountsDB/bank snapshotting code than is available through the current index, and this should be validated in a full Devin session with repository and test-execution access.
