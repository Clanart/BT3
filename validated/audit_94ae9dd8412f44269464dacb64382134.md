## Analysis

The TRST-H-6 bug class is: **a security-relevant gate is silently skipped (or wrongly restrictive) when the controlling storage value is left at its Solidity/Rust default of zero, until an admin explicitly initializes it.** Searching Hyperbridge's proof-verification path for this exact class of "zero-default gate," I found a real, higher-impact analog in the challenge-period enforcement, and a striking inconsistency between the two production implementations.

The Substrate side treats "not configured" as a hard failure: [1](#0-0) 
`verify_delay_passed` calls `host.challenge_period(proof_height.id)`, which returns an `Option`; if the value was never stored, it explicitly errors with `ChallengePeriodNotConfigured` rather than silently allowing the message through [2](#0-1) .

The EVM `HandlerV2` does the opposite: it reads a single global `challengePeriod` value from the host and only enforces the wait **if that value is non-zero**: [3](#0-2) [4](#0-3) [5](#0-4) 

`challengePeriod` is a governance-set field on the host (set via `HostManager`/`setHostParams`, an ISMP-authenticated governance message), analogous to `maxVotesForPool` requiring `createGauge()`/an explicit setter call. Until governance calls that setter for a given `EvmHost` deployment, `challengePeriod` reads the Solidity default of `0`, and the guard `challengePeriod != 0 && challengePeriod > delay` is unconditionally skipped — exactly mirroring the reported pattern of "only executes the requirement if the value is bigger than zero."

### Title
Zero-default `challengePeriod` silently disables the fraud-proof challenge window in `HandlerV2` - ([File: evm/src/core/HandlerV2.sol])

### Summary
`HandlerV2.handlePostRequests`, `handleGetResponses`, and `handlePostRequestTimeouts` gate on `host.challengePeriod()` with `if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();`. Because `challengePeriod` is a single governance-configured value that defaults to `0`, any `EvmHost` for which governance has not yet (or ever) called the setter accepts post requests, get-responses, and timeouts **immediately** after a consensus/state commitment update — with zero elapsed delay — instead of failing closed like the equivalent Substrate check does.

### Finding Description
The challenge period exists so that observers have a guaranteed window, after a new consensus/state commitment lands, to submit a `FraudProof` (`consensus::freeze_client`) before any request/response/timeout that depends on that commitment can be executed [6](#0-5) . Substrate's `validate_state_machine` treats a missing challenge-period configuration as a hard error (`ChallengePeriodNotConfigured`), refusing to process the message rather than defaulting to "no wait needed" [7](#0-6) .

`HandlerV2.sol` instead treats the unconfigured/default value of `challengePeriod` (`0`) as semantically identical to an intentional "challenge period disabled" setting: `if (challengePeriod != 0 && ...)`. There is no `NotConfigured`-style rejection path on the EVM side — a host whose `challengePeriod` param was never explicitly set (fresh deployment, a governance oversight, or any transient period before the parameter is pushed) permits any relayer to submit consensus updates and immediately follow up with post requests/get responses/timeouts referencing that just-landed, unchallenged state commitment.

### Impact Explanation
This directly matches the "false proof/state acceptance" and "logic attacks on challenge periods" impact categories: it removes the window during which a malicious or buggy consensus/state update could be frozen via a fraud proof before dependent cross-chain requests are dispatched to modules. An attacker (or a relayer racing to front-run the freeze) can get a request executed against state that has not survived the intended dispute window, on any `EvmHost` where this parameter has not been explicitly hardened to a non-zero value. Since `handlePostRequests`/`handleGetResponses` ultimately call `host.dispatchIncoming`, which invokes destination module logic (including token/intent settlement modules), this can translate into unauthorized execution based on state that was never actually vetted for the intended dispute period.

### Likelihood Explanation
No malicious relayer, prover, or governance actor collusion is required — an unprivileged party only needs the state variable to be at its default (unconfigured) value, which is the natural state of any freshly deployed `EvmHost` before governance explicitly sets `challengePeriod`, and remains a live risk for any deployment where that setup step is skipped or delayed. This is precisely the "never possible/never safe until setX() is called" pattern from the seed report, just manifesting as an unintended bypass of a security gate instead of an unintended revert.

### Recommendation
Mirror the Substrate behavior: distinguish "challenge period intentionally set to 0" from "challenge period never configured." Either (a) require `challengePeriod` to be explicitly initialized to a non-zero value at host deployment/params-set time and reject `0` as invalid in the `setHostParams` validation, or (b) add an explicit `configured` flag alongside `challengePeriod` in `HostParams` and have `HandlerV2` revert with a distinct error (analogous to `ChallengePeriodNotConfigured`) when it is unset, so message processing fails closed rather than open.

### Proof of Concept
1. Deploy a fresh `EvmHost` (or take one whose `HostParams.challengePeriod` was never explicitly pushed by governance) — `challengePeriod` reads `0`.
2. Submit a consensus update via `HandlerV2` that stores a new `StateMachineHeight`/commitment for the destination chain [8](#0-7) .
3. In the same or the very next block, submit `handlePostRequests` (or `handleGetResponses`/`handlePostRequestTimeouts`) with a valid Merkle-Mountain-Range proof against that fresh commitment. `delay = block.timestamp - stateMachineCommitmentUpdateTime(...)` will be small or `0`, but since `challengePeriod == 0`, the guard `challengePeriod != 0 && challengePeriod > delay` never triggers `ChallengePeriodNotElapsed`.
4. The request is dispatched to the destination module immediately, with no opportunity for anyone to have submitted a `FraudProof` against the just-landed consensus/state commitment.

Note: I was not able to fully trace every code path that sets `HostParams.challengePeriod` (e.g., whether `setHostParams` enforces a non-zero minimum) within the available index; a Devin session with full repo access would be needed to confirm whether any existing validation in `EvmHost.sol`'s params-setter already prevents `0` from being persisted in practice.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
