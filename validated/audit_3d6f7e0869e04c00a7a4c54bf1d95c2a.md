### Title
Cross-shop webhook confusion via unauthenticated `X-Shopify-Shop-Domain` header - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
The webhook verification path validates only the HMAC of the raw request body against a secret shared by the whole app, but never binds that signature to the shop the webhook claims to be from. The `shop_domain`/`shop` value used to route webhook data to a specific merchant's session is read from an unauthenticated header, so a party who can obtain one validly-signed webhook (e.g., for their own installed shop) can replay the same body with a different `X-Shopify-Shop-Domain` header and have it accepted and processed under an arbitrary other shop's identity.

### Finding Description
`hmac_valid?` computes the digest over `request.raw_post` only, using a single secret (`ShopifyApp.configuration.secret` / `old_secret`) shared across all shops that installed the app: [1](#0-0) 

`WebhookVerification#verify_request` uses this same `hmac_valid?(data)` check based purely on body bytes, and `shop_domain` is derived straight from the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header, which is not part of the signed data at all: [2](#0-1) 

Because the header carrying the destination shop is not covered by the commitment (the HMAC), the same body+HMAC pair remains "valid" no matter which shop domain header is attached. This mirrors the Nomic bug class: two logically distinct destinations (here, "shop A" vs. "shop B") share one authentication artifact with no domain separation between them, so an attacker can redirect data intended for/verified against one destination to another.

Downstream, generated webhook jobs trust this unauthenticated `shop_domain`/`shop` value to look up the `Shop` record and execute business logic in that shop's session context: [3](#0-2) 

The integration test confirms the header and body are independent inputs — the same body `"{}"` is HMAC'd, and the shop-domain header is set separately without being part of the signed payload: [4](#0-3) 

### Impact Explanation
An attacker who is a legitimate (but malicious or compromised) merchant installing the app receives genuine, correctly-HMAC'd webhooks from Shopify for their own store (since the signing secret is the app's shared secret, not a per-shop secret). By replaying that body with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain, the request still passes `hmac_valid?`, and the app processes the payload as though it originated from the victim shop. Depending on the webhook job's logic, this enables cross-shop data confusion/injection, and is especially severe for mandatory privacy webhooks (`customers/redact`, `shop/redact`, `customers/data_request`) where an attacker could trigger deletion or disclosure actions against a shop they do not own.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any shop to legitimately receive one signed webhook, and (2) POSTing that body with a forged shop-domain header to the public webhook endpoint. No secret needs to be guessed or leaked — the shared app secret is reused across all shops by design, and the shop-domain header is trivially attacker-controlled since it is never covered by the signature. This is reachable by any unrelated, otherwise-unprivileged merchant of the same app.

### Recommendation
Bind the destination shop into the authenticated commitment rather than trusting an unsigned header:
- Prefer HMAC/topic verification helpers from `shopify_api` (e.g., `ShopifyAPI::Webhooks::Registry.process`) that validate the full header set together with the body, and avoid re-deriving `shop_domain` independently from a raw header for business logic.
- If a custom controller must read `shop_domain` for the job payload, verify that it matches a shop domain associated with the given HMAC/webhook source, or at minimum use per-shop signing where feasible.
- Add regression tests that assert an otherwise-valid signed body is rejected once the `X-Shopify-Shop-Domain` header is swapped for a domain other than the one implied by the webhook source.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; capture a real webhook Shopify sends (body `B`, header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`).
2. Replay: `POST /webhooks/<topic>` with body `B`, `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb:15-21`) accepts the request because `hmac_valid?` only checks `B` against `H`.
4. `shop_domain` resolves to `victim-shop.myshopify.com` and the generated job (`lib/generators/shopify_app/add_webhook/templates/webhook_job.rb.tt:8-15`) loads and processes the victim shop's `Shop` record with attacker-supplied body data.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
