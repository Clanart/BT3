### Title
`smartConvert`'s `_minRec = _amountIn` check + no error handling in `_sendRewards` lets a manipulated wom/mWom pool revert `withdraw` - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.withdraw` unconditionally calls `_toMasterWomAndSendReward` → `_sendRewards` → `SmartWomConvert.smartConvert` whenever pending WOM rewards exist for the pool being withdrawn from. `smartConvert` enforces `convertAmount + amountRec >= _amountIn` (i.e., a strict 1:1 output requirement on the swap leg) even though the underlying router swap itself is executed with `_minAmountOut = 0`. Because there is no try/catch anywhere around this call chain, a revert inside `smartConvert` propagates all the way up and reverts the entire `withdraw()` transaction, blocking the user's principal withdrawal.

### Finding Description
The call chain is: `WombatPoolHelper.withdraw` [1](#0-0)  → `WombatStaking.withdraw` [2](#0-1)  → `_toMasterWomAndSendReward` [3](#0-2)  → `_sendRewards` [4](#0-3)  → `SmartWomConvert.smartConvert` [5](#0-4) .

In `smartConvert`, when `currentRatio()` (a single 1e18 mWom→wom quote) falls below `buybackThreshold` (90%), a buyback portion of the harvested WOM fee is swapped through the Wombat wom/mWom pool via `_convertFor`, using a fixed router call with `_minAmountOut = 0` [6](#0-5) . Immediately after, the function enforces `convertAmount + amountRec >= _minRec` where `_minRec` was passed in as the *original, full* `_amountIn` [7](#0-6) , ` [8](#0-7) `. This effectively requires the actual swap output to be at least 1:1 relative to the amount routed to swap, regardless of the small quote used to decide whether to enter the buyback branch. Because the quote (`currentRatio`, fixed 1e18 amount, mWom→wom direction) and the actual trade (variable `buybackAmount`, wom→mWom direction) hit the AMM curve differently, an attacker who skews the wom/mWom Wombat pool's cash/liability balance in the same transaction can cause the actual swap to yield less than the required 1:1 output, triggering `revert MinRecNotMatch()`.

Critically, `_sendRewards` and `_toMasterWomAndSendReward` have no try/catch anywhere in `WombatStaking.sol` — confirmed by searching the whole file for `try`/`catch`, which only exist inside `SmartWomConvert.sol` as custom error names, not exception handling. Therefore any revert in `smartConvert` bubbles up and reverts `withdraw()` in its entirety, even though the fee-conversion logic is unrelated to the user's principal being withdrawn. This affects every `deposit`, `depositLP`, `harvest`, and `withdraw` call for the affected pool whenever there is a nonzero pending WOM reward and the `isMWOM` fee is active with `smartWomConverter` set.

### Impact Explanation
An attacker (any unprivileged holder of the pool's receipt/LP tokens) can call `withdraw` via the pool helper and, by first (in the same transaction, e.g. from their own contract) pushing the wom/mWom Wombat pool off its "quoted" peg, force the fee-conversion swap to underperform 1:1, causing `MinRecNotMatch()` to revert and the whole withdrawal to fail. Since this condition can be triggered repeatedly (any time pending WOM rewards exist for a pool), it can be used to indefinitely block withdrawals and deposits for that pool, matching Immunefi's "Temporary freezing of funds for at least 24 hours" (High) impact class, since legitimate users cannot withdraw their principal while the attacker keeps the pool skewed or repeats the manipulation.

### Likelihood Explanation
Preconditions: (1) `smartWomConverter` must be configured and the `isMWOM` fee active for the pool (owner-configured, but this is the documented intended production configuration, not a misconfiguration attackers introduce); (2) there must be a nonzero pending WOM reward on withdraw (a normal, frequent condition due to Wombat's auto-harvest-on-withdraw behavior); (3) the attacker must be able to skew the wom/mWom pool's implied price/liquidity sufficiently within one transaction. Because the fee amount subject to conversion is typically small (a fee percentage of harvested rewards, not the user's principal), the swap size needed to trip the 1:1 check is also small, making the required capital modest relative to a full pool-wide price attack — though the exact capital needed depends on the wom/mWom pool's live liquidity depth at attack time, which I could not directly verify from the indexed code (Wombat pool implementation is external/interface-only in this repo). This is a repeatable griefing vector rather than a one-off exploit, and no privileged role is required — only calling `withdraw` through the pool helper and performing ordinary swaps against the public wom/mWom pool.

### Recommendation
- Do not let a revert in the fee-conversion/harvest sub-path (`_sendRewards` / `smartConvert`) block the core deposit/withdraw logic. Wrap the `smartConvert`/`IConverter` calls in `_sendRewards` in a try/catch (or a low-level call with success check) and fall back to skipping the conversion (e.g., queue raw WOM, or hold it for retry) rather than reverting the entire transaction.
- In `SmartWomConvert.smartConvert`/`_convertFor`, do not size the `_minRec` slippage check off the full `_amountIn`; instead compute an expected output based on the same trade size and direction actually executed (or apply a bounded slippage tolerance) rather than a strict 1:1 requirement decided by a separate, differently-sized quote.
- Consider decoupling the reward-harvest/fee-conversion step from the principal withdraw path entirely (e.g., make harvesting a separate, permissionless call that can independently fail without affecting `withdraw`).

### Proof of Concept
Hardhat test plan (mocking Wombat contracts and the router):
1. Deploy mocked `IMasterWombat`, `IWombatPool`, `IWombatRouter`, `IAsset`, `IMWom`, and wire up `WombatStaking`, `WombatPoolHelper`, and `SmartWomConvert` with a pool configured with `isPoolFeeFree = false` and an active `isMWOM` fee, `smartWomConverter` set.
2. Have a user deposit LP via the pool helper so pending WOM rewards will accrue on withdraw (mock `MasterWombat.withdraw` to transfer some WOM to `WombatStaking` as "harvested rewards").
3. From an attacker-controlled contract, in one transaction: (a) call the mocked `IWombatRouter`/pool state setter to make `currentRatio()` (mWom→wom, 1e18 quote) report a low ratio (<9000) while making the actual wom→mWom swap for the buyback amount return less than a 1:1 ratio (simulate asymmetric AMM slippage/skew), then (b) call `WombatPoolHelper.withdraw(_liquidity, _minAmount)` for the victim's own tokens (or trigger it as a griefing call if the function allows any pending-reward pool state to be exploited on any user's withdraw).
4. Assert that `withdraw` reverts with `MinRecNotMatch()`, that `IERC20(wom).balanceOf(address(this))` (WombatStaking) is unaffected/frozen relative to expected `totalConverted` tracked in `mWOM`, and that the victim's withdrawal transaction fails despite having sufficient principal and no fault of their own.
5. Repeat to show the block persists as long as the attacker keeps repeating the pool skew, demonstrating funds frozen beyond 24 hours.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
