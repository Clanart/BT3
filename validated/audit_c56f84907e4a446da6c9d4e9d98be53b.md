## Confirmed local analog: `order.fees` credited at nominal value while actual `feeToken` receipt can be short, corrupting the shared `TRANSACTION_FEES` escrow bucket

### Title
Unaccounted transfer-fee on `order.fees` collection causes cross-order insufficient-balance DoS/fund-loss on `IntentGatewayV2` escrow settlement - (evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder()` already contains an explicit, tested fix for fee-on-transfer (FoT) input tokens: it measures actual balances before/after `safeTransferFrom` and mutates `order.inputs[i].amount` to the real received amount before computing the commitment and crediting `_orders[commitment][token]` [1](#0-0) . However, the **fee-token collection path for `order.fees` right after that (Phase after escrow credit) has no such correction** — it pulls tokens via `safeTransferFrom` and then unconditionally stores the *nominal* `order.fees` value into `_orders[commitment][TRANSACTION_FEES]`, never checking what the contract actually received: [2](#0-1) 

This mirrors exactly the root cause of the Debita `Auction::buyNFT` bug: an accounting bucket is credited with a nominal/requested value instead of the actually-received balance for a token that can apply a transfer fee.

### Finding Description
`_orders[commitment][TRANSACTION_FEES]` is a per-commitment escrow slot, but it draws from the *same* pooled `feeToken` ERC-20 balance held by the `IntentGatewayV2` contract across **all** orders. When `_withdraw()` finalizes a fill/settlement, it reads this nominal value and calls `safeTransfer` for exactly that amount: [3](#0-2) 

If the configured host `feeToken()` is (or is ever swapped to) a fee-on-transfer / deflationary token, every `placeOrder()` call that pays `order.fees` deposits **less** than the nominal amount into the contract, yet the nominal amount is what gets credited to that order's `TRANSACTION_FEES` slot and is what all other bookkeeping (`_orders` mapping accounting, `OrderPlaced` event, and the contract's implicit solvency assumption) treats as real. This is the identical broken invariant as the Sherlock report: a pooled-token accounting ledger is built from the *requested* transfer amount rather than the *actual* balance delta, so as usage accumulates, the contract's real `feeToken` balance falls behind the sum of all outstanding `TRANSACTION_FEES` entries it has promised to pay out.

Unlike the `order.inputs[]` path — which is defended by the balance-snapshot pattern shown at lines 198-291 and is covered by dedicated fee-on-transfer regression tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`) — the `order.fees` path at line 358 has no equivalent guard, and no corresponding test exists for a FoT fee token.

### Impact Explanation
Because `TRANSACTION_FEES` deficits accumulate across *every order that pays fees in that token*, this is not a self-contained loss confined to a single order (as in a normal "user picked a bad token" scenario) — it degrades the shared solvency of the whole contract for that fee token. Eventually, whichever order's `_withdraw()`/settlement is processed once the deficit exceeds the buffer will revert with an ERC-20 transfer failure, **locking that user's/solver's legitimately-owed escrow and fee release** (a stuck, unclaimable settlement) — the same "last claimant can't be paid" failure mode described in the source report. This satisfies the "loss/lock of funds" and "logic attack on settlement accounting" criteria in the impact gate, since it is triggered purely by an unprivileged user placing an order with `order.fees > 0` in a token whose transfer semantics deduct a fee — no relayer, prover, or admin compromise required.

### Likelihood Explanation
The likelihood is limited by governance's discretion in choosing `feeToken()` on `IHost` (typically a standard stablecoin today), which is why this is a lower-severity latent defect rather than an immediately live exploit. But it is fully reachable by any user without any privileged role the moment a deflationary/FoT token is ever used as the fee token, and the codebase's own test suite explicitly demonstrates that the authors are aware fee-on-transfer tokens are a first-class integration hazard for `IntentGatewayV2` (hence the input-side balance-snapshot fix and its dedicated tests) — yet the parallel `order.fees` code path was left unpatched, making this an incomplete-fix analog to the exact bug class in the report.

### Recommendation
Apply the same balance-snapshot pattern already used for `order.inputs[]` to the `order.fees` collection branch: record `feeToken.balanceOf(address(this))` before `safeTransferFrom`, and store `_orders[commitment][TRANSACTION_FEES]` as the post-transfer delta rather than the nominal `order.fees` value, exactly mirroring lines 289-291.

### Proof of Concept
1. Governance configures a fee-on-transfer ERC-20 (1% fee) as `IDispatcher(host).feeToken()`.
2. User A calls `placeOrder()` with `order.fees = 1000`; contract actually receives 990, but `_orders[commitmentA][TRANSACTION_FEES] = 1000` is recorded (line 361).
3. Repeat with Users B, C, … N, each under-funding the pool by 1% of their nominal fee while the contract believes it holds the full nominal sum across all commitments.
4. As fills/settlements finalize and call `_withdraw()` → `safeTransfer(beneficiary, fees)` using the nominal recorded value (`IntentsBase.sol:416`), the contract's actual `feeToken` balance is short by the accumulated 1% skim across all prior orders.
5. The last order(s) to settle in that fee token revert on `safeTransfer` due to insufficient balance, permanently stranding that order's escrowed inputs and fee release (would need an explicit Foundry test analogous to `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` but targeting the `order.fees`/`TRANSACTION_FEES` branch, which does not currently exist in `evm/tests/foundry/`).
