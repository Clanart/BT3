### Title
OP_RETURN data output excluded from fee and weight accounting, yielding under-priced/oversized transactions that fail relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends the `OP_RETURN` data output to `tx_outs` (lines 194-202) but computes `weight`, `vbytes`, `needed_fee`, `fee_with_change`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check using `calculate_weight_vbytes(tx_ins.len(), payments, ...)` (lines 204, 225-226, 241), which only models the `payments` outputs and never the data output. The realized transaction is therefore larger than what was priced, mirroring the Taiko bug class where a fee is charged yet delivery fails.

### Finding Description
`calculate_weight_vbytes` (send.rs:62-127) builds a template transaction from `payments` and an optional change output. The constructor calls it before the `OP_RETURN` output is conceptually included:

- Line 204: `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);`
- Lines 225-226: same omission for the change-bearing variant.

With a `change` output specified, the change value is set to `input_sat - payment_sat - fee_with_change` (lines 228-230), so the *actual* fee paid equals `fee_with_change` exactly — priced for a transaction that does not include the up-to-80-byte `OP_RETURN` output plus its value/length overhead (~10-95 extra weight units / ~3-24 extra vbytes). The effective fee rate is therefore strictly lower than `fee_per_vbyte`, and the `TooLowFee` check at lines 211-213 validates `needed_fee` against the smaller vsize, so a transaction can pass the local minimum-relay-fee check while its true serialized fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`. Separately, the `MAX_STANDARD_TX_WEIGHT` check at line 241 uses `weight` computed without the data output, so a transaction at the boundary can exceed standardness limits without triggering `TooLargeTransaction`.

`data` reaches this function through `SignableTransaction::new`'s public `data: Option<Vec<u8>>` parameter (line 154), gated only by the 80-byte length check (line 171), and is exercised by the processor for eventualities/data-carrying transactions.

### Impact Explanation
A signed transaction containing an `OP_RETURN` output pays a fee rate lower than requested and possibly below the network minimum relay fee, or exceeds `MAX_STANDARD_TX_WEIGHT`. The transaction will not propagate or be confirmed even though all inputs are committed under `Prevouts::All` sighash signatures (send.rs:375-386); the committed inputs are effectively locked until a replacement transaction is constructed and signed, analogous to a message whose fee was consumed without successful delivery. The change output also receives more than intended (it absorbs the fee that should have paid for the data output's size), mis-accounting funds.

### Likelihood Explanation
Triggering requires a caller to supply `data` while also requesting `change`, or to construct a transaction near the standardness boundary. `data` is attacker/integrator-influenced bytes and the fee shortfall is deterministic once any `data` is present; however, the shortfall is bounded (~24 vbytes) so relay failure only occurs when `fee_per_vbyte` is already at/near the minimum. Medium-low likelihood, Medium-low impact overall: Medium severity.

### Recommendation
Include the data output in the weight/vsize template: pass the full output set (or `tx_outs`, including the `OP_RETURN` TxOut) to `calculate_weight_vbytes` for both the no-change and change fee computations, so `needed_fee`, `fee_with_change`, `TooLowFee`, and `MAX_STANDARD_TX_WEIGHT` all reflect the final transaction.

### Proof of Concept
```rust
// inputs: one ReceivedOutput of value V
// payments: [(script, P)]
// change: Some(change_script)
// data: Some(vec![0; 80])
let tx = SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0; 80]), FEE).unwrap();
// needed_fee / actual fee was computed on a template missing the OP_RETURN output.
// Actual serialized tx contains the ~90 extra bytes of the OP_RETURN output.
assert!(tx.fee() < FEE * u64::try_from(tx.transaction().vsize()).unwrap());
// i.e. realized fee rate < requested FEE; near the minimum relay boundary the TX
// passes the local TooLowFee check yet is below DEFAULT_MIN_RELAY_TX_FEE on the wire.
```
The discrepancy follows directly from send.rs:194-202 (output appended) versus send.rs:204 and 225-226 (weight computed from `payments` only), and is confirmed by the existing test asserting `needed_fee == tx.vsize() * FEE` only in the `data: None` case (tests/wallet.rs:269).
