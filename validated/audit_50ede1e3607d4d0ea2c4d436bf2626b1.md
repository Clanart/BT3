### Title
Server-Side Request Forgery (SSRF) via unvalidated DataLayer mirror URLs - ([File: chia/data_layer/download_data.py])

### Summary
Any wallet user can attach an arbitrary, attacker-controlled URL to a DataLayer store by creating a mirror coin on chain (via `add_mirror`), without owning that store. When any other node subscribes to that store for replication, `fetch_and_validate()` iterates the mirror server list and performs an unauthenticated, unvalidated outbound HTTP `GET` to the attacker-supplied URL. This is a direct analog of the reported Ghost CMS oEmbed SSRF: attacker-controlled input becomes the target of a server-initiated outbound request with no scheme/host/IP-range validation.

### Finding Description
`DataLayer.add_mirror()`/`DataLayerRpcApi.add_mirror()` accepts a list of `urls` and a `store_id` and pushes a mirror coin on chain associated with that `launcher_id` (store id) — there is no requirement that the caller own or control the target store: [1](#0-0) 

Once such a mirror is published on chain, any node that subscribes to that `store_id` will discover it via `get_available_servers_for_store()` and attempt to sync data from it in `fetch_and_validate()`: [2](#0-1) 

The actual outbound network fetch happens in `http_download()`, which builds the request directly from `server_info.url` — the attacker-supplied mirror URL — with no validation of scheme, host, or IP range (no blocking of link-local/metadata addresses, `localhost`, private ranges, etc.): [3](#0-2) 

This mirrors the root cause in the Ghost CVE-2020-8134 report: a downstream fetch function (`getOembedUrlFromHTML`/`fetchOembedData` in Ghost, `http_download`/`fetch_and_validate` here) consumes an attacker-influenced URL without any allow-list or network-destination validation, causing the server process itself to issue the request.

### Impact Explanation
Any node operator who subscribes to a third-party DataLayer store (a normal, expected DataLayer usage pattern for a "Data Layer client") can be coerced into making arbitrary outbound GET requests to attacker-chosen hosts, including internal-only services or link-local metadata endpoints (e.g., cloud instance metadata services), from the victim node's own network position. This is a blind/semi-blind SSRF: the response is not directly returned to the attacker, but the victim node performs the request (enabling internal network probing/port-scanning via timing/errors, and potential secondary exploitation if any reachable internal service accepts unauthenticated GETs with side effects). This qualifies as Medium severity, matching the CVSS class of the original report, and is reachable purely through a spend-bundle-created mirror coin plus normal subscription behavior — no malicious peer, node, or operator compromise required.

### Likelihood Explanation
Likelihood is Medium: creating a mirror coin only requires paying the mirror amount/fee via a standard spend bundle, and DataLayer subscription/sync is an ordinary, expected background process (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`) that runs automatically for any subscribed store, with no user interaction required once subscribed.

### Recommendation
Validate mirror/server URLs before use in `http_download()` and `fetch_and_validate()`/`get_downloader()`: enforce an allow-listed scheme (e.g., `https` only), resolve and reject requests to private/link-local/loopback/multicast IP ranges, and consider requiring explicit operator opt-in/allow-listing of mirror hosts rather than trusting on-chain mirror URLs implicitly.

### Proof of Concept
1. Attacker creates a mirror coin for a victim's known DataLayer `store_id` via the DataLayer RPC/CLI `add_mirror` (or the underlying wallet spend), supplying `urls=["http://169.254.169.254/latest/meta-data/"]`.
2. This is confirmed on chain as a normal mirror coin tied to the target `store_id`; the attacker does not need to own or control that store.
3. A victim node that is (or becomes) subscribed to that `store_id` runs its normal background sync loop; `get_available_servers_for_store()` returns the attacker's mirror URL as one of the `ServerInfo` entries.
4. `fetch_and_validate()` selects the malicious server and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which issues `session.get("http://169.254.169.254/latest/meta-data/" + filename, ...)` directly from the victim node process — confirming SSRF.

async def http_download(

    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
