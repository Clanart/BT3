### Title
Self-destructing a native-ERC20 token-pair contract permanently strands its Cosmos-coin liability while destroying its escrowed collateral - (File: x/erc20/keeper/msg_server.go, x/erc20/keeper/token_pairs.go)

### Summary
`ConvertERC20` and `ConvertCoin` in `x/erc20/keeper/msg_server.go` silently call `DeleteTokenPair` whenever the underlying ERC20 contract of a "native ERC20" token pair has been self-destructed, without checking whether any Cosmos bank coins of that denom are still in circulation. Because `x/vm`'s `DeleteAccount` (self-destruct handler) wipes the contract's code, storage and balance, any tokens previously escrowed at `types.ModuleAddress` for that pair are irrecoverably destroyed, while all previously-minted bank coins of `pair.Denom` remain fully spendable/transferable forever, with no way to ever redeem them back into the (now nonexistent) ERC20. This is the same class of bug as the reported Liquity issue: a per-asset accounting bucket (token-pair collateral) can be unilaterally emptied/eliminated by an ordinary user action, permanently orphaning value tied to that bucket (there, undercollateralized debt; here, an unbacked but still-circulating Cosmos coin). [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
For a "native ERC20" token pair (an ERC20 deployed on the EVM and registered via `RegisterERC20`), the accounting model is:
- `ConvertERC20` escrows the user's ERC20 tokens at `types.ModuleAddress` (inside the token contract's own storage) and mints an equal amount of the corresponding Cosmos coin (`pair.Denom`) to the user via `k.bankKeeper.MintCoins`. [5](#0-4) 
- `ConvertCoin` / `ConvertCoinNativeERC20` does the reverse: it burns the escrowed Cosmos coin and unescrows (transfers) the ERC20 tokens from the module account back to the user. [6](#0-5) 

Both entrypoints contain identical logic that checks whether the underlying contract still exists/has code, and if not, deletes the token pair outright and returns with no error:

```go
acc := k.evmKeeper.GetAccountWithoutBalance(ctx, pair.GetERC20Contract())
if acc == nil || !acc.HasCodeHash() {
    k.DeleteTokenPair(ctx, pair)
    ...
    return nil, nil
}
``` [7](#0-6) 

`DeleteTokenPair` removes the pair, its ERC20-address map, its denom map, and its allowances from state — with no check of, or accounting for, the Cosmos-coin supply that was minted against the (now-destroyed) collateral: [4](#0-3) 

Meanwhile, the EVM's self-destruct handler (`x/vm/keeper/statedb.go:DeleteAccount`) unconditionally clears the contract's balance, storage (including the escrowed-tokens balance entry that would have belonged to `types.ModuleAddress` inside the ERC20 contract's own mapping), code hash, and removes the auth account: [8](#0-7) 

Putting these together: any unprivileged user who deploys and owns an ERC20 contract, registers it as a token pair (registration is permissionless when `PermissionlessRegistration` is enabled — see `RegisterERC20`), converts some tokens into the Cosmos coin (minting `pair.Denom` 1:1 against escrowed ERC20 tokens), and then self-destructs their own contract (a legitimate EVM operation over which the token owner has full control, e.g. via a `selfdestruct` opcode reachable from an admin/owner function they wrote into their own contract) permanently and unilaterally:
1. destroys the escrowed collateral (the tokens sitting at `types.ModuleAddress` inside the contract's storage), and
2. causes the very next `ConvertERC20`/`ConvertCoin` call on that pair to delete the token-pair mapping entirely,

while the Cosmos coin (`pair.Denom`) that was already minted to the user (and potentially transferred onward to other holders, used in IBC transfers, staking, etc., since it's an ordinary bank coin) remains fully valid, spendable, and un-burnable through the normal conversion path forever (there is no longer a token pair to convert it back through, and even if a new pair were somehow created, no collateral exists to honor a real conversion). This produces a permanent, irreversible break of the 1:1 backing invariant between the native-ERC20 collateral and its Cosmos-coin representation, i.e., the coin becomes 100% "empty"/unbacked value that nonetheless remains fully usable — an outstanding-liability equivalent to the "perpetually unclaimed debt" scenario in the reported bug, except manifesting as unbacked, permanently non-redeemable circulating value rather than unclaimed debt.

The test suite acknowledges the code-deletion + pair-deletion mechanics exist (`tests/integration/x/erc20/test_msg_server.go`, `tests/integration/x/erc20/test_ibc_callback.go` "err - self-destructed contract" case) but never asserts on, or guards, what happens to already-minted, still-circulating bank coin supply of that denom. [9](#0-8) [10](#0-9) 

### Impact Explanation
This falls under "Critical permanent freezing, locking, theft, or unauthorized extraction of user funds, contract balances, escrowed assets ... or token-pair-backed balances" and "Critical ... irreversible accounting corruption of spendable user value across ... ERC20 representations." Once the token contract backing a pair is self-destructed:
- Escrowed ERC20 collateral held by the module (`types.ModuleAddress`) for that pair is irrecoverably destroyed — a permanent loss of the token-pair-backed asset.
- Outstanding Cosmos coin (`pair.Denom`) already minted against that collateral remains permanently unbacked yet permanently spendable, corrupting the accounting invariant the module's own code explicitly tries to enforce elsewhere (`types.ErrBalanceInvariance` checks in `convertERC20IntoCoinsForNativeToken`/`ConvertCoinNativeERC20`), because those invariant checks are only exercised on the happy path and are bypassed entirely by the self-destruct short-circuit.
- Any counterparties who later acquire that coin (e.g., via a market, IBC transfer, or the ERC20/WERC20 precompile) hold value that can never be redeemed for the underlying asset, and there is no mechanism to burn/reconcile it.

### Likelihood Explanation
The trigger requires only: (1) permissionless (or governance-enabled) ERC20 registration, which the codebase explicitly supports (`RegisterERC20` with `params.PermissionlessRegistration`), (2) the ability of the token deployer to self-destruct their own contract, which is standard EVM functionality entirely within an ordinary user's control for a contract they wrote, and (3) one subsequent `ConvertERC20`/`ConvertCoin` call (by anyone) to trigger the pair deletion. No privileged role, validator collusion, or governance action is needed — this is reachable purely through ordinary transactions from an unprivileged EOA operating on a contract it owns.

### Recommendation
- Before deleting a token pair due to a self-destructed/missing contract, check the current bank supply of `pair.Denom` (`bankKeeper.GetSupply`). If the supply is non-zero, do not silently delete the pair; instead, disable further conversions in a way that preserves the ability to reconcile/burn the outstanding coin, or fail the operation loudly and require a governance/registered recovery path.
- Consider explicitly documenting that self-destructing a registered native-ERC20 contract with outstanding minted coin supply is a critical action, and add an invariant/state-machine check (e.g., in the `x/erc20` module's `InvariantsRegistry`, if any) that flags/prevents this state from being reached silently.
- At minimum, emit a distinguishable, non-silent event/error when a pair with non-zero outstanding coin supply is deleted, and consider blocking `DeleteAccount` (self-destruct) at the `x/vm` layer for addresses that are currently registered as `OWNER_EXTERNAL` token-pair contracts with outstanding supply, analogous to the report's suggestion of "prevent the last trove of a given collateral type from being liquidated."

### Proof of Concept
1. Deployer deploys an ERC20 contract with a `selfdestruct`-capable admin function (using `contracts.ERC20MinterBurnerDecimalsContract` or a custom minimal ERC20) and calls `MsgRegisterERC20` (permissionless registration, or as `authtypes.NewModuleAddress(govtypes.ModuleName)`-permissioned test flow as shown in `SetupNativeErc20`). [11](#0-10) 
2. Deployer mints tokens to themselves and calls `MsgConvertERC20` to escrow `N` tokens at `types.ModuleAddress` and mint `N` `pair.Denom` coins to themselves. [12](#0-11) 
3. Deployer transfers/uses the minted `pair.Denom` coins normally (e.g., sends to another account, or IBC-transfers them) — this is ordinary bank-coin behavior with no dependency on the ERC20 contract still existing.
4. Deployer self-destructs the ERC20 contract (e.g., via `evmKeeper.DeleteAccount`/an EVM `SELFDESTRUCT` call), which wipes the contract's code, storage (including the module's escrowed balance entry) and account. [3](#0-2) 
5. Anyone calls `MsgConvertERC20` or `MsgConvertCoin` again referencing the same `pair` (or it is triggered lazily); the keeper sees `acc == nil || !acc.HasCodeHash()` and calls `DeleteTokenPair`, silently removing the token pair with no error and no check on outstanding `pair.Denom` supply. [1](#0-0) [2](#0-1) [4](#0-3) 
6. Result: the `N` `pair.Denom` coins held by the original account (and anyone who received them in step 3) remain fully valid, transferable Cosmos coins forever, but the collateral backing them is permanently gone and there is no token pair left through which to reconcile or burn them — a permanent accounting corruption / unbacked-but-spendable value bug.

Note: I was unable to fully verify within this session whether `x/erc20`'s `MintingEnabled`/pair lookup path performs any supply check before allowing this flow, or whether a bank-module invariant elsewhere in the codebase later catches and halts on this mismatch (e.g. a total-supply reconciliation invariant); the index did not surface such a guard in `x/erc20` or `x/bank` invariants for this specific pair-deletion path. This should be independently confirmed against the full module `RegisterInvariants` set before treating this as fully unmitigated.

func (k Keeper) convertERC20IntoCoinsForNativeToken(
	ctx sdk.Context,
	pair types.TokenPair,
	msg *types.MsgConvertERC20,
	receiver sdk.AccAddress,
	sender common.Address,
) (*types.MsgConvertERC20Response, error) {
	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()
	balanceCoin := k.bankKeeper.GetBalance(ctx, receiver, pair.Denom)
	balanceToken := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceToken == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow tokens on module account
	transferData, err := erc20.Pack("transfer", types.ModuleAddress, msg.Amount.BigInt())
	if err != nil {
		return nil, err
	}

	res, err := k.evmKeeper.CallEVMWithData(ctx, sender, &contract, transferData, true, nil)
	if err != nil {
		return nil, err
	}

	// Check evm call response
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return nil, err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return nil, err
		}
		if !unpackedRet.Value {
			return nil, sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute transfer")
		}
	}

	// Check expected escrow balance after transfer execution
	// NOTE: coin fields already validated in the ValidateBasic() of the message
	coins := sdk.Coins{sdk.Coin{Denom: pair.Denom, Amount: msg.Amount}}
	tokens := coins[0].Amount.BigInt()
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceTokenAfter == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	expToken := big.NewInt(0).Add(balanceToken, tokens)

	if r := balanceTokenAfter.Cmp(expToken); r != 0 {
		return nil, sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v",
			expToken, balanceTokenAfter,
		)
	}

	// Mint coins
	if err := k.bankKeeper.MintCoins(ctx, types.ModuleName, coins); err != nil {
		return nil, err
	}

	// Send minted coins to the receiver
	if err := k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, receiver, coins); err != nil {
		return nil, err
	}

// DeleteAccount handles contract's suicide call:
// - clear balance
// - remove code
// - remove states
// - remove the code hash
// - remove auth account
func (k *Keeper) DeleteAccount(ctx sdk.Context, addr common.Address) error {
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	acct := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	if acct == nil {
		return nil
	}

	// NOTE: only Ethereum contracts can be self-destructed
	if !k.IsContract(ctx, addr) {
		return errors.New("only smart contracts can be self-destructed")
	}

	// set account to a base account to set the whole balance as spendable
	baseAccount := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	k.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(cosmosAddr, baseAccount.GetPubKey(), baseAccount.GetAccountNumber(), baseAccount.GetSequence()))

	// clear balance
	if err := k.SetBalance(ctx, addr, new(uint256.Int)); err != nil {
		return err
	}

	var keys []common.Hash

	// clear storage
	k.ForEachStorage(ctx, addr, func(key, _ common.Hash) bool {
		keys = append(keys, key)
		return true
	})

	for _, key := range keys {
		k.DeleteState(ctx, addr, key)
	}

	// clear code hash
	k.DeleteCodeHash(ctx, addr)

	// remove auth account
	k.accountKeeper.RemoveAccount(ctx, acct)

	k.Logger(ctx).Debug(
		"account suicided",
		"ethereum-address", addr.Hex(),
		"cosmos-address", cosmosAddr.String(),
	)

	return nil
}

func (k Keeper) DeleteTokenPair(ctx sdk.Context, tokenPair types.TokenPair) {
	id := tokenPair.GetID()
	k.deleteTokenPair(ctx, id)
	k.deleteERC20Map(ctx, tokenPair.GetERC20Contract())
	k.deleteDenomMap(ctx, tokenPair.Denom)
	k.deleteAllowances(ctx, tokenPair.GetERC20Contract())
