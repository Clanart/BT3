### Title
Chia daemon `register_service` accepts a self-declared service name with no identity verification, allowing local clients to impersonate other services for message routing - (File: `chia/daemon/server.py`)

### Summary
The Coral Server CVE describes an SSE endpoint that fails to strongly verify that a connecting agent is actually the session participant it claims to be, permitting message injection/observation by an impersonator. The analogous gap in Chia is the local daemon's `WebSocketServer.register_service`, which binds an inbound websocket to a caller-supplied `service` string with no check that the connecting socket is the real, distinct process for that service name [1](#0-0) .

### Finding Description
Any client that completes the daemon's mutual-TLS handshake can send a `register_service` command with an arbitrary `service` value. The handler only checks that the field is present, then unconditionally adds the connecting websocket to `self.connections[service]`: [2](#0-1) 

There is no correlation between the claimed `service` string and any property of the connection (e.g., certificate subject/fingerprint, node type, or an allowlist of one-registrant-per-name). Multiple distinct sockets can register under the same destination name because `connections[service]` is a `set`, so a second registrant for `"chia_wallet"`, `"wallet_ui"`, or `"chia_full_node"` is simply added alongside the legitimate one, not rejected.

Routing then trusts this self-declared identity completely: `handle_message` looks at `message["destination"]` and, for any destination other than `"daemon"`, forwards the raw message verbatim to every websocket registered under that name: [3](#0-2) 

This is exactly the "insufficient validation of identity for [messaging] connections" bug class from the report: the daemon is a message bus keyed by unauthenticated, self-asserted names, so `destination`/`origin` fields are pure client input rather than verified identity, matching how `register_service` and `format_response`/`create_payload` construct/route envelopes purely from client-supplied strings [4](#0-3) .

Existing tests confirm the mechanics: any websocket, using nothing but a generic client TLS identity, registers under an arbitrary `service_name` string and thereafter receives responses/messages addressed to that name, including responses that actually originated from the real `chia_full_node` service: [5](#0-4) 

### Impact Explanation
Because `connections[service]` is a set and `handle_message`/`send_all_responses` fan out to every socket registered for a destination, a malicious local process holding a valid daemon private cert (the same credential class shared by wallet, full node, farmer, data layer, and GUI processes) can:
- Register under the name of a sensitive real service (e.g. `wallet_ui`, `chia_wallet`, `chia_full_node`) and passively observe traffic/state-change broadcasts meant for that consumer (message observation), including `keyring_status_changed` and other state notifications relayed by `_process_state_changed_queue`/`register_service` [6](#0-5) .
- Register under a destination name expected by a legitimate sender and receive/answer requests meant for the real service, or inject its own forged origin/destination envelopes into the routing fabric, since nothing ties `origin`/`destination` to the authenticated connection (message injection).

This breaks the trust boundary the daemon is supposed to provide between co-located Chia services and any local admin/GUI clients relaying through it, even though the underlying transport is mTLS-protected.

### Likelihood Explanation
Exploitation requires only a working daemon websocket connection (any client presenting daemon-domain cert material accepted by `ssl_context_for_server`) and a single `register_service` call with a chosen name — no race condition, no privileged host access beyond what's needed to reach the local daemon socket at all, and no server-side identity checks to bypass. This is a straightforward, deterministic misuse of a documented command.

### Recommendation
Bind `register_service` to a verified identity rather than a client-declared string: derive the allowed service name from the peer's certificate identity (or another server-side, non-spoofable attribute) instead of trusting `request["service"]` outright, and reject/replace duplicate registrations for the same canonical service name rather than silently adding to the set. At minimum, log/alert and refuse re-registration of privileged/well-known service names (`chia_wallet`, `chia_full_node`, `wallet_ui`, etc.) from a second, distinct connection.

### Proof of Concept
1. Start the daemon and a real `chia_full_node` service that registers normally (as in `test_daemon_passthru`).
2. From a second client holding daemon-domain cert material, connect to the daemon websocket and send `register_service` with `data={"service": "chia_full_node"}` (or any sensitive existing name) — the daemon accepts it and adds this socket to `connections["chia_full_node"]` alongside the real one, per [2](#0-1) .
3. Any subsequent message with `destination: "chia_full_node"` is forwarded by `handle_message` to both sockets, or the impostor's replies get mixed into responses addressed with a forged `origin` — demonstrated by the routing logic at [3](#0-2)  and exercised (for the legitimate case) in [7](#0-6) .

        if service is None:
            self.log.error("Service Name missing from request to 'register_service'")
            return {"success": False}
        if service not in self.connections:
            self.connections[service] = set()
        self.connections[service].add(websocket)
