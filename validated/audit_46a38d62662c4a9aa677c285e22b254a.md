## Analysis

The Vader `vestFor` bug class is: an **unauthenticated function accepts an arbitrary target identifier and performs a state-changing/destructive action on that identifier's behalf, with no check binding the caller to that identifier** — letting anyone act "for" a victim.

In `shopify_app`, the webhook-processing pipeline has the same shape: the code that authenticates a webhook request (HMAC check) is completely decoupled from the code that determines *which shop* the webhook applies to.

### Root cause

`ShopifyApp::PayloadVerification#hmac_valid?` only verifies the raw POST body against the shared app secret — it says nothing about which shop the request concerns: [1](#0-0) 

`ShopifyApp::WebhookVerification#shop_domain` derives the shop identity purely from the `X-Shopify-Shop-Domain` HTTP header, which is **not part of the HMAC-signed data**: [2](#0-1) 

This `shop_domain` value is exactly what the gem's own documentation tells developers to pass straight into background jobs that mutate per-shop state: [3](#0-2) 

And the generated job template built on top of this pattern uses that unverified `shop_domain` to look up and **destroy** a shop's stored record/session: [4](#0-3) 

Because every merchant who installs a public app receives webhooks signed with the *same* app-level client secret (not a per-shop secret), any attacker can install the target app on their own store, capture one genuinely HMAC-signed webhook payload, and then replay it against the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim domain. `verify_request` only checks the body's HMAC — it never checks that the claimed `shop_domain` header matches the shop that actually produced/owns that signed body. The forged request is accepted, and the enqueued job runs against the victim's shop record.

### Why this matches the analog rules

- Reachable from an anonymous/unrelated-merchant HTTP request (any account, not the victim's).
- Root cause is exact and file/method-supported: HMAC binds only `request.raw_post`; shop attribution is read from an unsigned header (`webhook_verification.rb` lines 16-25).
- Impact is concrete: cross-shop action — an attacker can cause destructive job execution (e.g. deleting a `Shop` record via `AppUninstalledJob`) attributed to a victim shop domain the attacker never controls, which is an accepted forged-signed-request / cross-shop-access class bug, not a no-impact one.

This is a real architectural weakness in the officially documented custom-webhook pattern of this gem (`docs/shopify_app/webhooks.md`, generator templates in `lib/generators/shopify_app/add_app_uninstalled_job/` and `add_declarative_webhook/`), and is the closest unprivileged analog to the "Unrestricted vestFor" report in this codebase. [5](#0-4)

### Title
Webhook shop-domain spoofing via HMAC-unverified `X-Shopify-Shop-Domain` header enables cross-shop destructive actions - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification` authenticates a webhook request solely by validating the HMAC of the raw POST body against the app's shared client secret (`PayloadVerification#hmac_valid?`). The shop the webhook is attributed to, however, is read from the `X-Shopify-Shop-Domain` request header via the `shop_domain` helper, which is not covered by the HMAC signature at all. Any actor who can obtain one validly HMAC-signed webhook body (trivially available to any merchant who installs the app on their own store, since the HMAC secret is shared app-wide, not per-shop) can replay that body to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name an arbitrary victim shop. The request passes `verify_request` unmodified, and the `shop_domain` value is handed directly to background jobs that perform per-shop mutations (per the gem's own documented pattern and generator templates), including destroying the victim's stored `Shop`/session record in `AppUninstalledJob`.

### Finding Description
- `hmac_valid?` computes/validates HMAC-SHA256 over `request.raw_post` only.
- `shop_domain` is derived from `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]`, a value entirely outside the HMAC digest.
- Docs and generators instruct developers to forward this unverified `shop_domain` into `*_job.perform_later(shop_domain: shop_domain, ...)`.
- The generated `AppUninstalledJob#perform` looks up `Shop.find_by(shopify_domain: shop_domain)` and calls `shop.destroy`, using the attacker-controlled header value with no cross-check against the signed body's own shop reference.

### Impact Explanation
An attacker (any merchant able to install the target public app) can cause the app to execute privileged, shop-mutating background jobs against a victim shop they do not control — including destroying the victim's stored access-token/session record via the standard `AppUninstalledJob`, which forces the victim to re-install/re-authorize, analogous to the "block a user" impact in the referenced report (an unrelated party forcing a costly re-authentication/lockout state onto a victim with no permission check).

### Likelihood Explanation
Moderate-to-high: exploitation only requires installing the target public app on an attacker-controlled store to obtain one genuinely signed webhook, then a single forged HTTP POST with a substituted header. No secrets, insider access, or race conditions are required beyond normal app installation, which is open to any merchant for public apps.

### Recommendation
Bind shop attribution to the signed payload rather than an unauthenticated header: derive `shop_domain` from a field inside the HMAC-verified webhook body/topic metadata (as provided by `ShopifyAPI::Webhooks::Request`/`Registry.process`), or additionally verify that the header-provided shop domain matches a shop-specific value present in the verified body before invoking any per-shop job, especially destructive ones like the uninstall handler.

### Proof of Concept
1. Attacker installs the target public app on `attacker.myshopify.com`, triggering Shopify to send a legitimately signed `app/uninstalled`-style webhook (or captures any webhook) with valid `X-Shopify-Hmac-Sha256` for that body.
2. Attacker sends a POST to the app's custom webhook endpoint (built per `docs/shopify_app/webhooks.md`'s documented pattern) reusing the captured body and valid HMAC header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which succeeds because the body/HMAC pair is genuinely valid.
4. The controller forwards `shop_domain` ("victim.myshopify.com") into `AppUninstalledJob.perform_later`, which finds and destroys `victim.myshopify.com`'s `Shop` record, even though the victim never uninstalled anything and the attacker never authenticated as that shop.

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)
```

```text
class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
```
