## Finding [1](#0-0) 

### Title
IBC callback EVM execution gas cap is silently ignored, letting a malicious callback contract exceed the user-declared gas limit - (File: x/vm/keeper/call_evm.go)

### Summary
`CallEVMWithData` accepts a `gasCap *big.Int` parameter that is meant to bound the EVM message's execution, but the function never uses it: the constructed `core.Message` hard-codes `GasLimit: config.DefaultGasCap` instead of `gasCap.Uint64()`. [2](#0-1) 
This function is invoked from `IBCReceivePacketCallback` with `remainingGas` (derived from the IBC-declared `cbData.CommitGasLimit`) explicitly intended to bound the internal `approve` call and the destination callback call. [3](#0-2) 

### Finding Description
`IBCReceivePacketCallback` computes a callback gas budget from the IBC packet memo (`cbData.CommitGasLimit`), sets an infinite gas meter with that limit on `cachedCtx`, and then calls `k.evmKeeper.CallEVM(...)` / `CallEVMWithData(...)` passing `remainingGas` as the `gasCap` argument with a comment stating "Call the EVM with the remaining gas as the maximum gas limit." [4](#0-3) [5](#0-4) 

However, inside `CallEVMWithData`, the `gasCap` parameter is dropped on the floor — the `core.Message.GasLimit` field is populated with the fixed system constant `config.DefaultGasCap` instead:
```go
msg := core.Message{
    From:       from,
    To:         contract,
    Nonce:      nonce,
    Value:      big.NewInt(0),
    GasLimit:   config.DefaultGasCap,   // <-- gasCap parameter is unused
    ...
}
``` [2](#0-1) 

This means the EVM opcode-level execution budget for the destination callback contract (which is arbitrary, attacker-supplied code specified by the IBC memo/receiver) is governed by `config.DefaultGasCap`, not by the smaller `cbData.CommitGasLimit`/`remainingGas` that the surrounding logic and code comments assume is enforced. Pure-computation EVM opcodes (loops, hashing, arithmetic) are accounted only against the EVM's internal `contract.Gas` counter derived from `msg.GasLimit`; they are not metered against the parent `ctx.GasMeter()` (the `cbData.CommitGasLimit`-limited meter) until/unless the execution touches state that goes through the Cosmos SDK KVStore gas accounting. As a result, the intended per-callback gas ceiling documented in the function ("Enforces gas limits to prevent DoS attacks") is not actually enforced for compute-heavy callback contracts. [6](#0-5) 

After the call returns, `ctx.GasMeter().ConsumeGas(res.GasUsed, "callback function")` retroactively charges the real gas used — but by then the (potentially very large, bounded only by `DefaultGasCap`) computation has already executed to completion inside the cached, isolated EVM context. [7](#0-6) 

This is the direct analog of the reported Sei `getRemainingGas` bug class: a security-critical gas value computed for one purpose (bounding untrusted execution) is silently replaced/miscalculated at the point where it is actually applied, defeating the intended gas-limiting invariant.

### Impact Explanation
Any unprivileged actor who can originate an IBC transfer packet with a destination callback memo (the standard ICS20 + IBC-callbacks flow already present in this repository, `x/ibc/callbacks`) can specify an arbitrary destination contract and a small `CommitGasLimit`. Because the callback contract's actual EVM execution is capped by `config.DefaultGasCap` rather than the declared, smaller limit, the attacker's contract can perform far more computation than the protocol's gas-accounting model assumes was possible for that callback. This breaks the documented DoS-prevention invariant of the callback processing path and can be used to inflate the actual block-processing cost of relaying/receiving IBC packets well beyond what the fee/gas model for that callback charges, creating a block-processing-time amplification vector triggerable by an ordinary user transaction (an IBC transfer with a crafted memo) — matching the "chain halt / non-determinism triggerable through ordinary transaction flow" impact category.

### Likelihood Explanation
High: no privileged relayer/validator collusion is required. Any user constructing an ICS-20 transfer with a callback memo pointing to a contract they control can trigger this path on packet receipt; the vulnerable code path (`IBCReceivePacketCallback` → `CallEVM`/`CallEVMWithData`) is on the standard, unprivileged packet-processing flow.

### Recommendation
In `CallEVMWithData` (and `CallEVM`), respect the caller-supplied `gasCap` when it is non-nil by setting `msg.GasLimit = gasCap.Uint64()` (falling back to `config.DefaultGasCap` only when `gasCap == nil`), so the IBC-callback gas budget (`cbData.CommitGasLimit`) is actually enforced on the EVM execution, consistent with the security comments in `IBCReceivePacketCallback`.

### Proof of Concept
1. Submit an ICS-20 transfer to the chain with a destination-callback memo specifying: `contractAddress = <attacker contract>` and a small `CommitGasLimit` (e.g., a few hundred thousand gas).
2. Deploy the attacker contract with an `onPacketReceive`/callback function containing a large pure-compute loop (no storage writes) sized to consume gas well above `CommitGasLimit` but below `config.DefaultGasCap`.
3. On packet receipt, `IBCReceivePacketCallback` invokes `CallEVMWithData` with `remainingGas` derived from `CommitGasLimit`, but the actual `msg.GasLimit` used for EVM execution is `config.DefaultGasCap`. [8](#0-7) 
4. The callback executes for a gas cost far above the declared `CommitGasLimit`, only being charged back to `ctx.GasMeter()` after execution completes — demonstrating the enforcement bypass.

Note: I was unable to fully confirm the exact numeric value of `config.DefaultGasCap` from the indexed content (only reference locations were found, not the constant definition), so the precise magnitude of the amplification could not be verified from the index alone; a Devin session with full file access would be needed to confirm that value.

// CallEVMWithData performs a smart contract method call using contract data.
func (k Keeper) CallEVMWithData(
	ctx sdk.Context,
	from common.Address,
	contract *common.Address,
	data []byte,
	commit bool,
	gasCap *big.Int,
) (*types.MsgEthereumTxResponse, error) {
	nonce, err := k.accountKeeper.GetSequence(ctx, from.Bytes())
	if err != nil {
		return nil, err
	}

	msg := core.Message{
		From:       from,
		To:         contract,
		Nonce:      nonce,
		Value:      big.NewInt(0),
		GasLimit:   config.DefaultGasCap,
		GasPrice:   big.NewInt(0),
		GasTipCap:  big.NewInt(0),
		GasFeeCap:  big.NewInt(0),
		Data:       data,
		AccessList: ethtypes.AccessList{},
	}

	// Use a cache context so that a reverting EVM call does not corrupt the
	// parent gas meter. On success we commit the cache and charge the actual
	// gas used; on revert we discard the cache and leave the parent meter
	// untouched (matching DerivedEVMCallWithData semantics).
	tmpCtx, commitState := ctx.CacheContext()
	res, err := k.ApplyMessage(tmpCtx, msg, nil, commit, true)
	if err != nil {
		return nil, err
	}

	if res.Failed() {
		return res, errorsmod.Wrap(types.ErrVMExecution, res.VmError)
	}

	commitState()
	ctx.GasMeter().ConsumeGas(res.GasUsed, "apply evm message")

	return res, nil
}
