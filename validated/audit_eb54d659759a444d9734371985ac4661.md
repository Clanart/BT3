### Title
Embedded-NUL truncation causes symbol-name lookup mismatch in Ruby `DescriptorPool#lookup` / `Descriptor#lookup` - (File: `ruby/ext/google/protobuf_c/defs.c`)

### Summary
Ruby protobuf's descriptor-lookup APIs (`DescriptorPool#lookup`, `Descriptor#lookup`, `Descriptor#lookup_oneof`) extract a raw C pointer from an attacker-influenced Ruby `String` via `get_str()`/`RSTRING_PTR` and pass it to strlen-based upb APIs (`upb_DefPool_FindMessageByName`, `upb_DefPool_FindExtensionByName`, `upb_DefPool_FindEnumByName`, `upb_DefPool_FindServiceByName`, `upb_DefPool_FindFileByName`, `upb_MessageDef_FindFieldByName`, `upb_MessageDef_FindOneofByName`). These wrappers compute the lookup length via `strlen(sym)` [1](#0-0) , silently truncating the logical Ruby string at its first embedded NUL byte before it reaches the exact length-aware `upb_strtable` lookup that the rest of the codebase (Python, PHP, and upb's own `WithSize` APIs) uses to defend against exactly this class of bug.

### Finding Description
This mirrors the jq CVE's core invariant failure: a string type that is allowed to carry embedded NUL bytes at the "logical" (language) level is silently reduced to a NUL-terminated C string before being resolved against a name/symbol table, creating a mismatch between the string a caller validated/observed and the string that is actually looked up.

- Ruby strings are byte-counted (`RSTRING_LEN`), not NUL-terminated semantically; `get_str()` only does `Check_Type` and returns `RSTRING_PTR(str)`, discarding the length: [2](#0-1) .
- `DescriptorPool_lookup` feeds that raw pointer into `upb_DefPool_FindMessageByName(self->symtab, name_str)` and sibling `Find*ByName` calls (not the `*WithSize` variants) [3](#0-2) .
- Those upb entry points compute `strlen(sym)` internally and forward to the size-aware primitive: [1](#0-0) [4](#0-3) .
- The exact-length variant (`*WithSize`) is the one that upb, Python's `PyUpb_DescriptorPool_FindMessageTypeByName`, and PHP's `Any::unpack` deliberately use to prevent NUL-truncation attacks — confirmed by the reflection test asserting `WithSize` respects exact length and rejects truncated prefixes [5](#0-4) , and by Python's explicit regression test crafting `normal_name + '\x00Tail.Content.Ignore'` and asserting the malicious full name raises `KeyError` rather than resolving to `normal_name` [6](#0-5) .
- Ruby's `defs.c` has no equivalent `WithSize` usage or NUL-rejection anywhere in `get_str`, `DescriptorPool_lookup`, `Descriptor_lookup`, or `Descriptor_lookup_oneof` [7](#0-6) [8](#0-7) .

The reachable failure: if application code (e.g., a JSON-derived type/field name, or a name built by concatenating attacker-controlled and trusted segments) passes a Ruby string containing an embedded NUL such as `"AllowedType\x00.EvilPayload"` into `DescriptorPool#lookup`/`Descriptor#lookup`, the call resolves to the descriptor for `"AllowedType"` — the truncated prefix — even though the full logical string differs and could have been rejected/flagged by any policy code that inspects the full Ruby string (which correctly sees the entire byte sequence, unlike the C lookup). This is precisely the jq pattern: validation/observation operates on the full logical string; native resolution operates on the truncated C-string, and the two diverge.

### Impact Explanation
Impact is bounded to symbol-name confusion within the trusted, already-loaded descriptor pool — the attacker cannot introduce new types, only cause a lookup call to silently resolve to a different (but still legitimate, already-registered) descriptor than the one an application-level check believed it was validating/requesting. This is a logic/integrity issue (type confusion in name resolution), consistent with a Medium-severity classification like the jq analog (`AV:L/AC:L/PR:L/UI:N/C:L/I:L/A:N`) rather than a memory-safety or RCE issue. It does not cause resource exhaustion, memory corruption, or crash — it is a divergence between the name that appears validated and the name actually resolved.

### Likelihood Explanation
Requires an application built on Ruby protobuf to construct descriptor names from partially attacker-controlled input and to perform any decision (allow/deny, routing, type dispatch) based on inspecting the full Ruby string rather than the object returned by `lookup`. This is a plausible but not universal pattern; still, the underlying API inconsistency (Ruby's `Find*ByName` bypassing the `WithSize` guard that Python/PHP/upb explicitly rely on) is a genuine, provable code-level defect reachable through a fully public, documented API (`DescriptorPool#lookup`, `Descriptor#lookup`).

### Recommendation
In `ruby/ext/google/protobuf_c/defs.c`, replace all `get_str()`-based calls into upb's NUL-terminated `Find*ByName` entry points with the corresponding `*WithSize` variants using `RSTRING_LEN`, mirroring Python's `PyUpb_VerifyStrData` + `*WithSize` pattern, so an embedded NUL either causes lookup failure or resolves against the caller's full byte sequence rather than a truncated prefix. This applies to `DescriptorPool_lookup`, `Descriptor_lookup`, `Descriptor_lookup_oneof`, and any other Ruby ext call sites using `get_str` feeding non-`WithSize` upb Find APIs.

### Proof of Concept
Given a descriptor pool with two independently-loaded, legitimately registered messages `Foo` and `Foo.Bar` (or any name `N1` that is a proper NUL-truncation prefix of a string `N2` also present/absent in the pool):
1. In Ruby, build `name = "Foo" + "\x00" + "EvilSuffix"` (`RSTRING_LEN(name) == 14`, contains an embedded NUL at index 3).
2. Call `Google::Protobuf::DescriptorPool.generated_pool.lookup(name)`.
3. Trace: `DescriptorPool_lookup` → `get_str(name)` returns `RSTRING_PTR` (ignores length) → `upb_DefPool_FindMessageByName(symtab, "Foo\0EvilSuffix")` → internally `strlen(sym)` yields `3`, so the call becomes equivalent to `upb_DefPool_FindMessageByNameWithSize(symtab, "Foo", 3)` — returning the `Foo` descriptor [9](#0-8) .
4. Any Ruby-side code that checked `name` (the full 14-byte string) against an allow/deny policy before calling `lookup` would see a mismatch between the string it validated and the descriptor actually resolved (`Foo`), analogous to jq resolving `"Foo\0EvilSuffix"` to the on-disk file `Foo`.

static VALUE DescriptorPool_lookup(VALUE _self, VALUE name) {
  DescriptorPool* self = ruby_to_DescriptorPool(_self);
  const char* name_str = get_str(name);
  const upb_MessageDef* msgdef;
  const upb_EnumDef* enumdef;
  const upb_FieldDef* fielddef;
  const upb_ServiceDef* servicedef;
  const upb_FileDef* filedef;

  msgdef = upb_DefPool_FindMessageByName(self->symtab, name_str);
  if (msgdef) {
    return get_msgdef_obj(_self, msgdef);
  }

  fielddef = upb_DefPool_FindExtensionByName(self->symtab, name_str);
  if (fielddef) {
    return get_fielddef_obj(_self, fielddef);
  }

  enumdef = upb_DefPool_FindEnumByName(self->symtab, name_str);
  if (enumdef) {
    return get_enumdef_obj(_self, enumdef);
  }

  servicedef = upb_DefPool_FindServiceByName(self->symtab, name_str);
  if (servicedef) {
    return get_servicedef_obj(_self, servicedef);
  }

  filedef = upb_DefPool_FindFileByName(self->symtab, name_str);
  if (filedef) {
    return get_filedef_obj(_self, filedef);
  }

  return Qnil;
}
