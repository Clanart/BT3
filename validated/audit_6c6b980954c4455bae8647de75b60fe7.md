### Title
`rewards()` view method in the distribution precompile skips the non-payable value check, permanently stranding any SEI/usei sent with the call - ([File: precompiles/distribution/distribution.go])

### Summary
The distribution precompile's `Execute` dispatcher calls `p.rewards(ctx, method, args)` for `RewardsMethod` without first validating that `value` is zero, unlike every other query/view method in the same switch statement (`params`, `validatorOutstandingRewards`, `validatorCommission`, etc., which do enforce this indirectly via `p.validateInput`/`pcommon.ValidateNonPayable`). Because `rewards()` never processes or refunds the attached value, and the precompile has no mechanism to send it back or credit it to the caller, any usei/wei value attached to a `rewards()` call is transferred into the EVM balance associated with the precompile address and left unrecoverable.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute` handles `RewardsMethod` as: [1](#0-0) 
unlike sibling query methods such as `params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, which route through `p.validateInput`, itself calling `pcommon.ValidateNonPayable(value)`: [2](#0-1) 
`ValidateNonPayable` is the guard used elsewhere in the codebase to reject any non-zero `value` sent to a non-payable/view precompile function: [3](#0-2) 

This omission is explicitly confirmed by an in-repo integration-test comment describing it as a known "guard quirk": [4](#0-3) 

Because `rewards()` never calls `HandlePaymentUsei` (the function used by payable precompile methods like `delegate`/`deposit` to refund the payer and route the coin explicitly), any value attached to the call is simply accepted by the EVM value-transfer mechanism (which moves the sender's balance to the precompile's associated Sei/EVM address as part of normal `CALL` value semantics) and never returned. Contrast this with a genuinely payable method (`deposit` in `precompiles/gov/legacy/v562/gov.go`), which explicitly requires and processes `value`: [5](#0-4) 

The distribution precompile has no withdrawal or sweep function for stray funds landing at its address — mirroring exactly the reported bug class ("payable functions exist, but no function can extract the locked funds").

### Impact Explanation
Any user (or, more importantly, any contract/aggregator/wallet automation that blindly forwards `msg.value` on a generic multicall to `distribution.rewards(address)`) that mistakenly or programmatically attaches non-zero `value` to a `rewards()` call will have those funds irreversibly locked at the precompile's associated address, since the distribution module has no code path to return or credit that balance back to any account. This is a permanent freezing of funds for the affected caller — a concrete fund-loss condition reachable by any unprivileged EVM transaction sender who calls the public precompile at `0x0000000000000000000000000000000000001007`.

### Likelihood Explanation
Reaching this is straightforward for a single unprivileged EVM transaction: any account can call `rewards(address)` on the distribution precompile with a non-zero `value` field. Because the ABI method is a "view", the natural client expectation is that misusing it is safe or that it will fail like other Sei precompile views (as the withdrawn/updated methods correctly do), which does not hold here. Wallets/tooling or contracts that route generic calldata + value through the precompile (or that generically set `value` for safety without checking method mutability) will silently strand funds instead of receiving a revert.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check for `RewardsMethod` in `precompiles/distribution/distribution.go`'s `Execute` dispatcher (and in the equivalent legacy versions `v580`, `v605`, `v606`, `v610`, `v614`, `v620`, `v630`, `v640`, `v65`, `v66`, `v67`), consistent with every other view method in the same file, so that a value-bearing call to `rewards()` reverts before any balance transfer takes effect.

### Proof of Concept
1. An account calls `distribution.rewards(delegatorAddress)` at address `0x0000000000000000000000000000000000001007` with `value: 1000000000000000000` (1 SEI) attached, e.g. via `ethers.Contract.rewards(addr, { value: ethers.parseEther("1") })`.
2. Unlike calling any other view method (e.g. `params`, `validatorOutstandingRewards`) with attached value, which reverts via `ValidateNonPayable`, this call succeeds and returns the rewards data.
3. The attached SEI is transferred as part of standard EVM `CALL` value semantics to the precompile's associated balance, but `rewards()` never processes or refunds it (no `HandlePaymentUsei` call), and there is no distribution-precompile method to sweep/withdraw stray funds from that address.
4. The sent amount is now permanently unrecoverable by the caller, confirmed directly by the codebase's own test-file annotation: [6](#0-5) .
