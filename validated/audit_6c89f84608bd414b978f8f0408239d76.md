### Title
Silent swallowing of CLVM execution errors in `Offer.__post_init__` causes incorrect offer accounting (`additions`/`hints`/`get_offered_coins`) - (File: chia/wallet/trading/offer.py)

### Summary
This maps to the reserve-protocol bug class where a value-producing function fails "softly" (returning a sentinel instead of reverting) and the caller performs downstream arithmetic without validating that the value is actually trustworthy. In `chia-blockchain`, the analog is `Offer.__post_init__`, which computes the `_additions`/`_hints` cache used throughout offer accounting (`additions()`, `get_offered_coins()`, `get_offered_amounts()`, `arbitrage()`, `is_valid()`, `get_pending_amounts()`). When a coin spend's condition execution throws a generic `Exception` (anything other than `ValidationError` or the specific "cost exceeded or below zero" `ValueError`), the loop does `continue`, silently omitting that coin's additions/hints from the cache **without raising** and **without any caller-side check** that all coin spends were successfully accounted for.

### Finding Description
`Offer.__post_init__` builds `self._additions` and `self._hints` by iterating `self._bundle.coin_spends` and calling `compute_spend_hints_and_additions(cs, max_cost=max_cost)` for each spend: [1](#0-0) 

Two of the three exception branches are safe (they either re-raise or convert to a validation error), but the final `except Exception: continue` branch swallows *any other* exception raised while running a coin's puzzle (e.g. a CLVM runtime error triggered by a maliciously or unusually constructed puzzle reveal/solution in the offer's spend bundle) and moves on without recording that coin's additions in `adds`. There is no check afterward that every `cs.coin` in the bundle got an entry in `adds`.

This cache is then relied upon, unchecked, by:
- `additions()` — flattens `self._additions.values()` [2](#0-1) 
- `_get_offered_coins()` — directly indexes `self._additions[parent_spend.coin]` (would raise `KeyError` if missing, but if for a *different* spend in the same offer the additions were dropped, other computed sets like `get_pending_amounts()`, `arbitrage()`, and `get_offered_amounts()` will be silently wrong rather than erroring) [3](#0-2) 
- `is_valid()` / `arbitrage()` — used to decide whether an offer is complete and how much "leftover" (arbitrage) is owed to whom in `to_valid_spend()` [4](#0-3) [5](#0-4) 

This is directly analogous to the Reserve Protocol finding: a value-producing function (`price()` there, `compute_spend_hints_and_additions()` here) can fail without raising a hard, propagated error in every case, and the calling code (`collateralShortfall()` there, `Offer.__post_init__`/`arbitrage()`/`to_valid_spend()` here) performs further arithmetic (shortfall / arbitrage amount) using the possibly-incomplete or wrong data, without verifying that all inputs were successfully computed.

### Impact Explanation
If an offer-taker's client builds `Offer` objects from an untrusted, attacker-supplied offer file/bech32m blob (a standard, unprivileged trust boundary — offers are exchanged between untrusted counterparties off-chain), and one of the coin spends in that bundle is crafted so that its puzzle raises a generic exception when run under `compute_spend_hints_and_additions` (as opposed to a `ValidationError` or the specific over-budget `ValueError`), that coin's real on-chain additions are dropped from `_additions` silently. Downstream:
- `arbitrage()` and `is_valid()` can compute an incorrect (understated) offered/requested balance for that asset, because `get_offered_amounts()`/`get_requested_amounts()` derive from the same caches.
- `to_valid_spend()` uses `arbitrage()` to decide how much of the "leftover" amount to send to the arbitrage puzzle hash, so understating offered/requested amounts can lead to constructing a completion spend bundle with the wrong arbitrage payment, which either fails CAT accounting (denial of service on take) or, in more subtle constructions, could misdirect value if reused elsewhere (e.g. `get_pending_amounts()`, which UI/wallet code trusts for balance/pending display and confirmation flows).
- Because the failure is swallowed silently (no exception surfaces to the caller of `Offer(...)` construction), a wallet may present users or automated exchange bots with an incorrect summary of an offer's true value, similar in spirit to the Reserve case where `collateralShortfall()` computed a bad number instead of failing loudly when a price component was unusable.

This is a Medium-severity accounting-integrity issue: it doesn't directly forge assets or bypass signature checks, but it can cause incorrect acceptance/rejection decisions and incorrect derived amounts (arbitrage payments, pending balances) based on an untrusted, attacker-influenced spend bundle, without any error being surfaced.

### Likelihood Explanation
Triggering the generic `except Exception: continue` branch requires an attacker to craft a coin spend whose puzzle raises something other than the two already-handled cases when run inside `compute_spend_hints_and_additions`/`run_with_cost`. This is plausible for any wallet or exchange service that ingests offers from arbitrary (untrusted) counterparties, since `Offer.from_bech32`/`Offer.from_bytes` will invoke `__post_init__` on attacker-controlled `coin_spends`. However, I could not exhaustively enumerate every CLVM error condition that would land in this generic branch versus the other two branches without deeper analysis of `run_with_cost`'s exception surface — so likelihood is assessed as plausible but not fully proven, and the precise exploitation path (getting a specific incorrect arbitrage/pending amount) would need concrete PoC construction, which is unconfirmed here.

### Recommendation
Do not silently `continue` on unexpected exceptions in `Offer.__post_init__`'s coin-spend loop. Either re-raise (mapped to a `ValidationError`) for any exception type, or explicitly track which `cs.coin` entries failed and refuse to construct/trust the `Offer` (or clearly flag it as "unparseable") rather than allowing downstream accounting methods (`get_offered_amounts`, `arbitrage`, `is_valid`, `get_pending_amounts`, `to_valid_spend`) to silently operate on a partial `_additions`/`_hints` cache.

### Proof of Concept
Not independently constructed/verified in this session — the vulnerable code path (`chia/wallet/trading/offer.py` lines 166-186, generic `except Exception: continue`) is confirmed by static review, but a concrete CLVM puzzle/solution that raises a *generic* (non-`ValidationError`, non-cost-exceeded) exception from `run_with_cost` inside `compute_spend_hints_and_additions` was not built or executed to confirm end-to-end exploitability of `arbitrage()`/`to_valid_spend()` miscalculation. This would need to be validated with a live spend-bundle test similar to the existing test suite patterns in `chia/_tests/wallet/test_util.py` (e.g. `test_offer_maps_clvm_cost_exceeded_value_error`) but targeting the final unguarded `except Exception` branch instead.     def _get_offered_coins(self) -> dict[bytes32 | None, list[Coin]]:
        offered_coins: dict[bytes32 | None, list[Coin]] = {}

        cost_left = INFINITE_COST
        for parent_spend in self._bundle.coin_spends:
            coins_for_this_spend: list[Coin] = []

            parent_puzzle: UnknownPuzzle = UnknownPuzzle(known_program=parent_spend.puzzle_reveal)
            parent_solution = Program.from_serialized(parent_spend.solution)
            additions: list[Coin] = self._additions[parent_spend.coin]

            puzzle_driver = match_puzzle(parent_puzzle)
            if puzzle_driver is not None:
                asset_id = create_asset_id(puzzle_driver)
                inner_puzzle: Program | None = get_inner_puzzle(puzzle_driver, parent_puzzle, parent_solution)
                inner_solution: Program | None = get_inner_solution(puzzle_driver, parent_solution)
                assert inner_puzzle is not None and inner_solution is not None

                # We're going to look at the conditions created by the inner puzzle
                puzzle_cost, conditions = inner_puzzle.run_with_cost(cost_left, inner_solution)
                assert cost_left >= puzzle_cost
                cost_left -= puzzle_cost
                expected_num_matches: int = 0
                offered_amounts: list[int] = []
                for condition in conditions.as_iter():
                    if condition.first() == 51 and condition.rest().first() == OFFER_MOD_HASH:
                        expected_num_matches += 1
                        offered_amounts.append(condition.rest().rest().first().as_int())

                # Start by filtering additions that match the amount
                matching_spend_additions = [a for a in additions if a.amount in offered_amounts]

                if len(matching_spend_additions) == expected_num_matches:
                    coins_for_this_spend.extend(matching_spend_additions)
                # We didn't quite get there so now lets narrow it down by puzzle hash
                else:
                    # If we narrowed down too much, we can't trust the amounts so start over with all additions
                    if len(matching_spend_additions) < expected_num_matches:
                        matching_spend_additions = additions
                    matching_spend_additions = [
                        a
                        for a in matching_spend_additions
                        if a.puzzle_hash == construct_puzzle(puzzle_driver, OFFER_MOD).get_tree_hash()
                    ]
                    if len(matching_spend_additions) == expected_num_matches:
                        coins_for_this_spend.extend(matching_spend_additions)
                    else:
                        raise ValueError("Could not properly guess offered coins from parent spend")
            else:
                # It's much easier if the asset is bare XCH
                asset_id = None
                coins_for_this_spend.extend([a for a in additions if a.puzzle_hash == OFFER_MOD_HASH])

            # We only care about unspent coins
            coins_for_this_spend = [c for c in coins_for_this_spend if c not in self._bundle.removals()]

            if coins_for_this_spend != []:
                offered_coins.setdefault(asset_id, [])
                offered_coins[asset_id].extend(coins_for_this_spend)
        return offered_coins

    def arbitrage(self) -> dict[bytes32 | None, int]:
        """
        Returns a dictionary of the type of each asset and amount that is involved in the trade
        With the amount being how much their offered amount within the offer
        exceeds/falls short of their requested amount.
        """
        offered_amounts: dict[bytes32 | None, int] = self.get_offered_amounts()
        requested_amounts: dict[bytes32 | None, int] = self.get_requested_amounts()

        arbitrage_dict: dict[bytes32 | None, int] = {}
        for asset_id in [*requested_amounts.keys(), *offered_amounts.keys()]:
            arbitrage_dict[asset_id] = offered_amounts.get(asset_id, 0) - requested_amounts.get(asset_id, 0)

        return arbitrage_dict

    def is_valid(self) -> bool:

    # A "valid" spend means that this bundle can be pushed to the network and will succeed
    # This differs from the `to_spend_bundle` method which deliberately creates an invalid SpendBundle
    def to_valid_spend(self, arbitrage_ph: bytes32 | None = None, solver: Solver = Solver({})) -> WalletSpendBundle:
        if not self.is_valid():
            raise ValueError("Offer is currently incomplete")

        completion_spends: list[CoinSpend] = []
        all_offered_coins: dict[bytes32 | None, list[Coin]] = self.get_offered_coins()
        total_arbitrage_amount: dict[bytes32 | None, int] = self.arbitrage()
        for asset_id, payments in self.requested_payments.items():
            offered_coins: list[Coin] = all_offered_coins[asset_id]

            # Because of CAT supply laws, we must specify a place for the leftovers to go

                assert arbitrage_ph is not None

def test_offer_maps_clvm_cost_exceeded_value_error(monkeypatch: pytest.MonkeyPatch) -> None:
    """After prior spends leave almost no CLVM budget, run_with_cost raises ValueError.

    Offer remaps that to ValidationError. Lower MAX_BLOCK_COST_CLVM so a cheap
    first spend can deplete the budget without needing huge CREATE_COIN lists.
    """
    from chia_rs import G2Element
    from chia_rs.sized_ints import uint64

    import chia.wallet.trading.offer as offer_mod
    from chia.wallet.trading.offer import Offer
    from chia.wallet.wallet_spend_bundle import WalletSpendBundle

    coin_generator = CoinGenerator()
    # Minimal first spend (~44 cost). Leave only 10 for the second so CLVM aborts
    # inside run_with_cost with ValueError("cost exceeded or below zero").
    first = make_spend(coin_generator.get().coin, Program.to(1), Program.to([]))
    _, first_cost = compute_spend_hints_and_additions(first)
    second = make_spend(
        coin_generator.get().coin,
        Program.to(1),
        Program.to([[51, bytes32.zeros, 1]]),
    )
    monkeypatch.setattr(
        offer_mod,
        "DEFAULT_CONSTANTS",
        DEFAULT_CONSTANTS.replace(MAX_BLOCK_COST_CLVM=uint64(first_cost + 10)),
    )
    with pytest.raises(ValidationError, match="compute_additions for CoinSpend"):
        Offer({}, WalletSpendBundle([first, second], G2Element()), {})
