### Title
Attacker-controlled `t`/`n` in `ThresholdKeys::read` cause quadratic Lagrange interpolation and mass point decompression, enabling a Denial of Service - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to CVE-2025-63658 (unauthenticated DoS in monkey's request parser via a crafted input), `ThresholdKeys::read` deserializes attacker-controlled `t`, `n`, and interpolation mode bytes and then performs work super-linear in those attacker-chosen values — all before `ThresholdParams::new` bounds-checks them — allowing an unprivileged party who can feed bytes to `ThresholdKeys::read` to exhaust CPU and memory.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the input stream ( [1](#0-0) ), then:

1. Allocates `Vec::with_capacity(n)` and reads `n` field elements for `Interpolation::Constant` ( [2](#0-1) ).
2. Reads `n` group elements into a `HashMap` ( [3](#0-2) ) — each `read_G` performs full point decompression/validation.
3. Only *after* this work calls `ThresholdParams::new(t, n, i)` and `ThresholdKeys::new` ( [4](#0-3) ).

The critical cost is in `ThresholdKeys::new`: it computes the group key as `Σ verification_shares[i] * interpolation_factor(i, 1..=t)` for all `i` in `1..=t` ( [5](#0-4) ). With `Interpolation::Lagrange`, `interpolation_factor` iterates over the entire `included` list per participant ( [6](#0-5) ), making group-key derivation **O(t²)** field multiplications plus `t` field inversions and `t` scalar multiplications. An attacker supplies `t = n = 0xffff` (65535) with valid Lagrange-mode bytes, forcing ~4.3 billion field multiplications and 65535 point decompressions from a ~4 MB input. The same O(len²) pattern recurs in `ThresholdView` via `view()`, which calls `interpolation_factor` once per included signer ( [7](#0-6) ).

A secondary, lower-bandwidth amplifier exists in `SchnorrAggregate::read`, which loops over an attacker-controlled u32 count performing `read_G` decompressions ( [8](#0-7) ); this is linear in input size and therefore weaker.

### Impact Explanation
Any service that calls `ThresholdKeys::read` on bytes influenced by an untrusted party (e.g., loading key material supplied through an externally reachable path, or deserializing keys in a worker/validator process) can be driven into an effectively unbounded O(t²) computation — ~10⁹ group/field operations plus tens of thousands of curve decompressions per request — by a ~4 MB crafted buffer. This matches the report class exactly: a single crafted input causes a remote Denial of Service with no authentication or privileges required. Because `ThresholdKeys` is wrapped in `Arc` and cloning is cheap, repeated reads amplify the attack across threads.

### Likelihood Explanation
Reachability requires the integrator to deserialize `ThresholdKeys` from data an unprivileged party can influence — plausible for nodes loading key material broadcast/gossiped during multisig setup or recovery. The attacker only controls public bytes (`t`, `n`, the interpolation tag, and the share encodings); no secret, no valid signature, and no protocol participation is needed, since the expensive work happens during deserialization/validation itself, before any rejection. The input must merely contain enough bytes for `n` points and (for the Constant path) `n` scalars; a Lagrange-tagged blob still forces the O(t²) `ThresholdKeys::new` group-key computation whenever the points decode successfully.

### Recommendation
- Validate `t`/`n`/`i` via `ThresholdParams::new` *before* allocating or reading the variable-length bodies, and enforce a sane upper bound on `n` (e.g., the protocol's documented maximum multisig size) at the top of `ThresholdKeys::read`.
- Bound `view()`/`interpolation_factor` work, or memoize Lagrange numerators/denominators to reduce group-key derivation to O(t) precomputation plus O(t) per participant.
- Apply the same early length validation to `SchnorrAggregate::read` (reject `len` beyond a protocol maximum before looping `read_G`).

### Proof of Concept
```rust
// Feeding crafted bytes to ThresholdKeys::read triggers O(t^2) Lagrange work.
// Construct: id_len(4) || id || t=0xffff || n=0xffff || i=1 || [1]=Lagrange ||
// secret_share || n encoded points
let mut buf = vec![];
buf.extend(&(C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&u16::MAX.to_le_bytes()); // t = 65535
buf.extend(&u16::MAX.to_le_bytes()); // n = 65535
buf.extend(&1u16.to_le_bytes());     // i = 1
buf.push(1);                          // Interpolation::Lagrange
buf.extend(C::F::ONE.to_repr().as_ref()); // secret_share
for _ in 0 .. u16::MAX {
    buf.extend(C::generator().to_bytes().as_ref()); // n valid points
}
// ThresholdKeys::<C>::read(&mut buf.as_slice()) performs ~4.3e9 field ops in
// ThresholdKeys::new -> interpolation_factor before returning.
```
With `t = n = 65535`, `ThresholdKeys::new` invokes `interpolation_factor` 65535 times, each iterating 65535 participants (`crypto/dkg/src/lib.rs:226-249`, called from `:376-378`), yielding quadratic CPU exhaustion from a single ~4 MB unauthenticated input.
