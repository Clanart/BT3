Confirmed: `placeOrder` in `evm/src/apps/IntentGatewayV2.sol` never checks that `order.inputs.length == order.output.assets.length`. Only `order.inputs.length == 0` is rejected. This absence of a matching-length check is the direct analog of the C4 bug's core defect — a fund-movement calculation keyed off *one* side's cardinality/balance (there, `usdm` balance; here, `output.assets.length`) with no validation that the paired side (there, `pool3` balance; here, `order.inputs.length`) actually has enough matching entries.

### Title
Escrow release in `_fillSameChain` indexes `order.inputs[i]` by output count, permanently locking unreleased input tokens when `inputs.length > output.assets.length` - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`placeOrder()` never enforces that `order.inputs.length == order.output.assets.length`. `_fillSameChain()` iterates `for (uint256 i; i < outputsLen; i++)` (`outputsLen = order.output.assets.length`) and uses that same index `i` to read `order.inputs[i]` to compute and release the proportional escrow. Any input index `>= outputsLen` is never touched by the release loop.

### Finding Description [1](#0-0) 
`placeOrder` only checks `order.inputs.length == 0`; it places no constraint relating `inputs.length` to `output.assets.length`. [2](#0-1) 
`_fillSameChain` sizes its escrow-tracking arrays and its loop bound off `outputsLen = order.output.assets.length`, then inside the loop reads `order.inputs[i]` using that same output-derived index. [3](#0-2) 
The escrow amount released to the solver, `escrowedAmount`, and the `WithdrawalRequest.tokens` array passed to `_withdraw` are built solely from indices `0..outputsLen-1`. When the order becomes fully filled, `_filled[commitment] = msg.sender` is set and the order is finalized — no further release path for the untouched input tokens exists. [4](#0-3) 
`_withdraw` only decrements `_orders[commitment][token]` for the tokens explicitly present in `body.tokens`. Any escrowed token whose index was never included in `escrowedInputs` keeps its full `_orders[commitment][token]` balance sitting in the contract, but with the order already finalized (`_filled` set), `_cancelSameChain`'s `Unauthorized`/state checks and the fill path make that balance unreachable by the user going forward — it is effectively bridge-custody fund loss, not a mere revert like the C4 report's DoS.

This is the structural analog of the audited bug: the C4 finding computed a liquidity amount from only one side's balance (`usdm`) without validating the paired resource (`pool3`) was sufficient, causing a broken/incomplete operation. Here, the escrow-release logic derives its working set purely from `output.assets.length` without validating that `inputs.length` matches, causing a broken/incomplete release of escrowed custody funds whenever a user (or a front-end bug, or a solver-influenced order shape via `predispatch`/`select` flows) constructs an order with more input assets than output assets.

### Impact Explanation
Any order with `order.inputs.length > order.output.assets.length` — a shape not blocked anywhere in `placeOrder`, `select`, or `fillOrder` — results in the "extra" escrowed input tokens (indices `outputsLen..inputs.length-1`) never being included in any `WithdrawalRequest.tokens` array during a same-chain fill. Once the fill completes and `isFullyFilled` is true, the order is marked filled and the remaining escrow becomes permanently stranded in `IntentGatewayV2`, unreachable by the user (cancel paths are gated on the order not yet being filled) and unreachable by the solver (the fill already "completed" per the output side). This is direct, irrecoverable loss of user-escrowed funds inside a custody contract — squarely inside the bounty's "stealing or loss of funds" / "logic attacks" category.

### Likelihood Explanation
No signature, relayer, or governance action is required — an unprivileged user calling `placeOrder` with mismatched `inputs`/`output.assets` lengths (or a compromised/buggy front-end producing such an order, or a solver front-running with a crafted multi-input single-output order if such structuring is externally reachable) triggers the stuck-fund condition on the very next same-chain fill. The condition is purely a missing invariant check in production entry-point code, not requiring any malicious peer, relayer, or off-chain assumption.

### Recommendation
In `placeOrder` (or in `_validateParams`/order-construction validation), enforce `order.inputs.length == order.output.assets.length` for orders that intend index-aligned same-chain settlement, exactly as the C4 remediation enforced that the liquidity-add amount be bounded by the minimum of both paired balances rather than one side alone. Alternatively, redesign `_fillSameChain` so escrow release is computed pro-rata across the *full* `order.inputs` set (e.g., release every input proportionally to overall order completion) rather than by reusing the output loop index to key into `order.inputs`.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [TokenA: 1000, TokenB: 1000]` and `order.output.assets = [TokenC: 1000]` (2 inputs, 1 output — no length check blocks this in `placeOrder`, `evm/src/apps/IntentGatewayV2.sol:162-163`).
2. Escrow is recorded: `_orders[commitment][TokenA] = 1000`, `_orders[commitment][TokenB] = 1000`.
3. Solver calls `fillOrder` providing `options.outputs = [TokenC: 1000]`. `_fillSameChain` runs with `outputsLen = 1`, so the loop only ever touches `order.inputs[0]` (TokenA). `escrowedInputs` array has length 1, containing only TokenA's release.
4. `_withdraw` releases 1000 TokenA to the solver and decrements `_orders[commitment][TokenA]` to 0; it never touches `_orders[commitment][TokenB]`, which stays at 1000.
5. Because `isFullyFilled` is true, `_filled[commitment] = msg.sender` is set, finalizing the order — `_cancelSameChain` will subsequently fail (`UnknownOrder`/already-filled semantics) for any attempt to recover TokenB.
6. Result: 1000 units of TokenB remain permanently locked in `IntentGatewayV2`, unrecoverable by the user who escrowed them or anyone else — direct loss of bridged/escrowed funds with no compensating custody-release path.
