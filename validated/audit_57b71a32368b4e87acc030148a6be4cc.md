### Title
Empty aggregate signature trivially verifies — zero-length signer set lets an attacker-controlled `s` pass `SchnorrAggregate::verify` - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The external bug class is: when a value that should be derived from trusted state is computed over an *empty/zero* base, attacker-supplied input is used instead, giving an unprivileged party control over the outcome. The analog in Serai is `SchnorrAggregate::verify` in `crypto/schnorr/src/aggregate.rs`: when the aggregate contains zero signatures (empty `Rs`, empty `keys_and_challenges`), the verification equation degenerates to `-s·G == 0`, so a purely attacker-chosen `s = 0` is accepted as a valid aggregate signature over any message/context.

### Finding Description
`SchnorrAggregate::verify` builds `pairs` from `keys_and_challenges` and `self.Rs`, then adds `(-self.s, C::generator())` and checks the multiexp is identity [1](#0-0) . `SchnorrAggregate::read` accepts a length-prefixed `Rs` vector of length 0 followed by any canonical scalar `s` [2](#0-1) . If `self.Rs` and `keys_and_challenges` are both empty, the only remaining term is `(-s)·G`, which is identity for `s = 0` — so the untrusted byte string `00 00 00 00 || 0x00..00` verifies as a valid aggregate signature.

The aggregation weights `z` are derived solely from a digest of the challenges (`weight()` over `digest` with only `challenge` messages appended) [3](#0-2) ; there is no commitment to the `Rs` or keys in the weight derivation, and no non-empty requirement anywhere: `SchnorrAggregator::complete` even explicitly notes "returning None if none were aggregated", but `verify` has no corresponding check [4](#0-3) .

This mirrors the reported bug exactly: with an empty "supply" (zero aggregated signatures), the prover's own input (`s`) determines the outcome rather than any bound value. The reachable consumer is `Validators::verify_aggregate` in `coordinator/tributary/src/tendermint/mod.rs`, which calls `SchnorrAggregate::read` on untrusted bytes and then `aggregate.verify(...)` with the claimed `signers` list [5](#0-4) . An empty `signers`/`Rs` pair passes both the length check and verification for any `msg`.

### Impact Explanation
Any caller that treats `verify`/`verify_aggregate` returning `true` as evidence of authorization can be handed a forged "aggregate signature" consisting of the bytes `0x00000000 || 0x00*32` (`Rs = []`, `s = 0`), which verifies for an arbitrary `dst`, arbitrary `msg`, and an empty signer set. If signature-verification success is consumed before/independently of a separate quorum-weight check (the API itself does not enforce one — it only compares lengths), unsigned artifacts can be accepted as signed by a validator set. This is an incorrect verifier formula reachable purely from public, attacker-supplied bytes via `SchnorrAggregate::read` → `verify`.

### Likelihood Explanation
Exploitation requires a caller to invoke aggregate verification with an empty signer list and not independently require quorum weight. `verify_aggregate` is a public entry point on the Tendermint `SignatureScheme` and performs no emptiness check [6](#0-5) , so the degenerate path is trivially reachable with 36 bytes of input whenever aggregate verification is exercised on attacker-influenced data. Severity Medium: concrete forged-verification primitive, but real-world impact depends on the consensus layer separately enforcing that an empty signer set has insufficient weight.

### Recommendation
Reject empty aggregates: require `self.Rs.len() == keys_and_challenges.len() != 0` in `SchnorrAggregate::verify` (and/or in `read`/`verify_aggregate`). Additionally, bind each weight to the full signature context — append `Rs[i]` and the public key to `digest` before calling `weight()` — so weights are not solely a function of attacker-influenceable challenges, matching the "use the oracle price when supply is zero" remediation pattern of deriving the degenerate case from bound, trusted values.

### Proof of Concept
```rust
// crypto/schnorr: C = e.g. Ed25519 ciphersuite
// Untrusted bytes: u32 length = 0, then a zero scalar
let mut bytes = vec![0u8; 4];
bytes.extend([0u8; 32]); // s = 0
let agg = SchnorrAggregate::<C>::read(&mut bytes.as_slice()).unwrap();

// Empty signer set — verifies true for any dst/msg context
assert!(agg.verify(b"any dst", &[]));
// In tendermint: Validators::verify_aggregate(&[], msg, &bytes) also returns true,
// since signers.len() == aggregate.Rs().len() == 0 and the challenge loop is empty.
```
Root cause lines: `verify` loop over `keys_and_challenges` produces no pairs when empty [7](#0-6) , leaving only `(-s)·G`; `read` places no lower bound on `Rs` [2](#0-1) .

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }

  /// Complete aggregation, returning None if none were aggregated.
  pub fn complete(mut self) -> Option<SchnorrAggregate<C>> {
    if self.sigs.is_empty() {
      return None;
    }

    let mut aggregate = SchnorrAggregate { Rs: Vec::with_capacity(self.sigs.len()), s: C::F::ZERO };
    for i in 0 .. self.sigs.len() {
      aggregate.Rs.push(self.sigs[i].R);
      aggregate.s += self.sigs[i].s * weight::<_, C::F>(&mut self.digest);
    }
    Some(aggregate)
  }
