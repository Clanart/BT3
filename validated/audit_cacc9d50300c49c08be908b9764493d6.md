### Title
`SchnorrAggregate::verify` vacuously accepts an empty aggregate signature (zero signers, `s == 0`) — no "at least one signer" check — (`crypto/schnorr/src/aggregate.rs`)

### Summary
The analog of CVE-2021-47521 is the missing "at least one item was set up" check: just as `ems_pcmcia_add_card()` failed to verify that at least one channel was successfully registered, `SchnorrAggregate::verify` never verifies that at least one signer/signature is present. When `keys_and_challenges` is empty and `self.Rs` is empty, the multiexp reduces to a single term `(-s) * G`, which is the identity whenever `s == 0`. An all-zero `s` scalar therefore produces a `SchnorrAggregate` that verifies as `true` for *any* message and *any* DST, with zero actual signatures.

### Finding Description
`SchnorrAggregate::verify` (crypto/schnorr/src/aggregate.rs:127-146) only checks `self.Rs.len() == keys_and_challenges.len()`, builds per-signer weighted pairs `(z, R_i)` and `(z*c_i, key_i)`, appends `(-s, G)`, and returns whether the multiexp is identity. With both lists empty, the pair list is exactly `[(-s, G)]`, so `s = 0` yields identity and `verify` returns `true`. Unlike the producer side — `SchnorrAggregator::complete` explicitly returns `None` when `self.sigs.is_empty()` (crypto/schnorr/src/aggregate.rs:175-178) — the verifier side has no non-emptiness check, and `SchnorrAggregate::read` happily deserializes `len = 0` followed by any scalar (crypto/schnorr/src/aggregate.rs:77-88). An empty `BatchVerifier` likewise verifies as `true` (crypto/multiexp/src/batch.rs:93-101), so the "zero valid elements accepted" shape exists in both primitives.

Reachability: `verify_aggregate` in `coordinator/src/tributary/signing_protocol.rs`-adjacent code (`coordinator/tributary/src/tendermint/mod.rs:201-229`) feeds attacker-supplied `AggregateSignature` bytes through `SchnorrAggregate::read` and calls `aggregate.verify(DST, ...)`; if `signers` is empty (both slices length 0 passes the `signers.len() == aggregate.Rs().len()` check), a `s = 0` aggregate verifies. The in-scope defect is the verifier formula itself accepting a forged "aggregate of nothing" for arbitrary `(dst, msg)`.

### Impact Explanation
Any caller that treats `SchnorrAggregate::verify(...) == true` as "the listed signers endorsed this message" can be handed a universally-valid forged aggregate (`len = 0`, `s = 0`) whenever its signer list can be empty — a forged signature for an arbitrary message with no signer participation, exactly the class of "verification succeeds despite nothing being verified" that the kernel fix addressed.

### Likelihood Explanation
Exploitation requires a caller to invoke `verify`/`verify_aggregate` with an empty signer list. In Tendermint usage the weight/threshold check typically rejects empty signer sets before acceptance, so end-to-end exploitability depends on the caller, but the primitive unconditionally accepts the forgery and one in-tree caller (`verify_aggregate`) forwards attacker-controlled serialized aggregates to it. Medium.

### Recommendation
Reject empty aggregates in `SchnorrAggregate::verify` (return `false` when `keys_and_challenges.is_empty()`), mirroring the `sigs.is_empty() -> None` guard in `SchnorrAggregator::complete`, and consider asserting non-emptiness in `SchnorrAggregate::read` callers. Optionally have `BatchVerifier::verify*` document/guard the empty-batch `true` result.

### Proof of Concept
```rust
// crypto/schnorr — forged "aggregate of zero signatures" accepted for any message
let mut buf = vec![];
buf.extend(0u32.to_le_bytes());        // len = 0 => Rs = []
buf.extend(<C as Ciphersuite>::F::ZERO.to_repr()); // s = 0
let forged = SchnorrAggregate::<C>::read(&mut buf.as_slice()).unwrap();
// Passes for ANY dst and ANY msg since multiexp = (-0)*G = identity
assert!(forged.verify(b"any dst", &[])); // returns true — forged signature accepted
```
Root cause: `verify` at crypto/schnorr/src/aggregate.rs:127-146 lacks the "at least one signature was set up" check that `SchnorrAggregator::complete` (lines 175-178) enforces on the production side.
