### Title
Forged `EncryptedMessage` lets an accuser frame an innocent participant in PedPoP blame arbitration - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the Mattermost bug (an inbound handler trusting an attacker-supplied object reference without verifying authorship/ownership), PedPoP's blame handler accepts an accuser-supplied `EncryptedMessage` plus a claimed `sender: Participant` and attributes fault to that sender. The message's only "authorship" evidence is a Schnorr PoP over a fresh per-message ephemeral key whose challenge embeds the `sender` index as a self-asserted transcript field — it is not bound to any long-lived key of the claimed sender. Any accuser can therefore fabricate a malformed share message "from" an arbitrary participant, produce a valid `EncryptionKeyProof` for it (the proof only binds the message to the *accuser's* own encryption key), and cause `blame_internal` to return the innocent `sender` as faulty.

### Finding Description
`pop_challenge` transcripts `sender.to_bytes()` but the signed key is `msg.key`, an ephemeral key the message author picks freely. The PoP proves only possession of that ephemeral key's discrete log; nothing ties it to the claimed participant: [1](#0-0) 

`encrypt` signs `pop_challenge(context, pub_nonce, pub_key, from, msg)` where `from` is just the local machine's own index — a claimed value, not a verifier-checked credential: [2](#0-1) 

In blame resolution, `decrypt_with_proof` verifies the PoP with the caller-supplied `from` (the *accused* index), then verifies the accuser's DLEq proof binding `proof.key` to `enc_keys[decryptor]` — i.e., only to the *accuser's* registered key, never to the sender: [3](#0-2) 

`blame_internal` then returns `sender` as faulty if the decrypted bytes aren't a canonical scalar or don't satisfy the share-verification statements against `commitments[&sender]`: [4](#0-3) 

Because a fabricated message will (by construction) decrypt under the accuser's key to bytes that either fail `from_repr` or fail verification against the victim's commitments, the arbitration deterministically blames the victim.

### Impact Explanation
`BlameMachine::blame` / `AdditionalBlameMachine::blame` is designed to be callable by anyone, including non-participants, over accuser-supplied bytes. A false `sender` verdict aborts the DKG and, in deployments like Serai's coordinator where blame maps to slashing/fatal penalties, causes an honest participant to be punished. This is an integrity failure in the blame evidence chain: the handler "modifies state" (fault attribution) for an object (share message) the submitter does not own — the same class as referencing/deleting posts owned by others.

### Likelihood Explanation
The attack needs only public inputs: the accuser calls `EncryptedMessage::read`-equivalent construction (generate `k`, set `key = k*G`, sign PoP with `sender = victim`, encrypt any garbage to their own `enc_key` via `ecdh(k, enc_pub_self)`) and supplies it to `blame()`. No collusion, no key compromise, no channel access beyond submitting the blame message is required. The only mitigation is the documented requirement that the message "must have been authenticated as actually having come from the sender" — but the whole point of blame arbitration is that the accused never broadcasts this message; the accuser relays it, so external authentication of the relay path proves nothing about authorship. The PoP exists precisely to make the message self-authenticating (per the comment about Eve reusing Alice's key `X`), yet it fails to bind authorship.

### Recommendation
Bind the PoP to the sender's registered identity: include the sender's registered encryption public key (`enc_keys[sender]`) or the round-1 `EncryptionKeyMessage`/commitment in `pop_challenge`, and/or require the per-message `key` be derived as or proven equal to a value committed under the sender's authenticated registration. Concretely, `decrypt_with_proof`/`blame_internal` should verify `msg.pop` under a challenge that also transcripts the sender's registered `enc_key` from `self.enc_keys[&from]`, so a forged message claiming `sender = victim` cannot verify without the victim's participation. Alternatively, require senders to sign each share ciphertext with a key bound to their participant index (e.g., the PoK key of their commitments), making the message non-repudiable.

### Proof of Concept
Participant `E` (index `e`), accuser, wants to frame victim `V` (index `v`):

1. `E` picks `k ← random`, sets `K = k*G` (forged `msg.key`).
2. `E` puts arbitrary non-scalar bytes `b` as the "ciphertext" plaintext, computes `ec = k * enc_pub_E` (encrypting to **itself**), sets `msg.msg = b XOR keystream(cipher(context, ec))`.
3. `E` computes `c = pop_challenge(context, R=r*G, K, sender=v, msg)` — writing `v`, the **victim's** index, into the self-asserted sender field — and sets `msg.pop = SchnorrSignature::sign(k, r, c)`.
4. `E` calls `blame(sender=v, recipient=e, msg, proof=Some(EncryptionKeyProof{ key: ec, dleq: DLEqProof::prove(transcript, [G, K], enc_key_E) }))`.
5. `decrypt_with_proof` succeeds: PoP verifies (challenge uses `from=v`, matching step 3), and the DLEq verifies because `ec = enc_key_E * K` legitimately — `E` encrypted to itself. The decrypted "share" fails `from_repr` or `share_verification_statements(v_recipient? recipient=e, commitments[v], share)` → `blame_internal` returns `v`.
6. Victim `V` is recorded faulty despite never sending anything.

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
