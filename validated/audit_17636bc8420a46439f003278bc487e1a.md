## Title
Native-fee dispatch swaps via `swapETHForExactTokens` refund excess ETH to the Host itself, not the payer, silently trapping the slippage buffer users are told to attach - (`evm/src/core/EvmHost.sol`)

## Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all convert native token payments into `feeToken` by calling `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` directly from the Host contract. [1](#0-0) [2](#0-1) 

Because `EvmHost` is the direct caller of the router, Uniswap V2's own excess-ETH refund (`if (msg.value > amounts[0]) TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`) sends the dust back to `msg.sender` as seen by the router — which is `address(EvmHost)`, not the original transaction sender/payer. `EvmHost.sol` has no logic afterward that forwards or credits that leftover ETH back to the caller.

## Finding Description
The external report's core broken invariant is: an on-chain quote/slippage value that is priced live off a manipulable AMM, combined with a swap path that has no real minimum-output/refund protection for the paying party, causes value to be misallocated during a swap executed as part of protocol logic.

The exact local analog: Hyperbridge documents and even the SDK build in the fact that the native-payment `quote()` path is "vulnerable to sandwich attacks" and must be estimated off-chain with a buffer: [3](#0-2) 

The SDK's own `HyperFungibleToken.quote()` caller explicitly adds a 1% buffer on top of the quoted amount before sending `msg.value`, precisely because the swap executes later at whatever price the pool has moved to: [4](#0-3) 

That buffered `msg.value` is sent into `dispatch{value: msg.value}(post)`, which reaches `EvmHost.dispatch()`: [1](#0-0) 

`swapETHForExactTokens` only consumes exactly `amounts[0]` (the amount needed to buy `post.fee` worth of `feeToken` at execution-time pool price) and refunds `msg.value - amounts[0]` — but to the router's caller, which is `EvmHost` itself, since `EvmHost` calls the router directly rather than forwarding `msg.sender`. No code in `dispatch()`, `dispatch(DispatchGet)`, or `fundRequest()` retransmits that refunded ETH to `_msgSender()`/`post.payer`. The refunded dust simply accumulates as native balance on the Host contract, with no on-chain accounting tying it back to the depositor.

This directly compounds the report's exact bug class: because on-chain AMM-based fee quoting is officially acknowledged to be imprecise/manipulable, every caller is forced to overpay `msg.value` as a safety margin against price movement/sandwiching — and that entire margin (as well as any user-side overestimation error) is unconditionally forfeited to the protocol contract rather than returned, on every single native-token dispatch. An attacker (or even normal price drift) can widen the gap between the buffer and the actual execution price via front-running/sandwiching the underlying Uniswap V2 pool, directly enlarging the amount of ETH permanently trapped in `EvmHost` for each victim transaction, with the loss borne entirely by the dispatching user.

## Impact Explanation
This is unauthorized, unrecoverable loss of user funds on a public, unprivileged entrypoint (`dispatch`/`fundRequest`, callable by any account, with no admin, relayer, or malicious-peer assumption required). Every native-token dispatcher permanently loses their slippage/price-movement buffer to the Host contract, and the amount lost scales with how much the pool price is pushed between quote time and execution — which an attacker can manipulate via a sandwich attack on the underlying Uniswap V2 pool to maximize the trapped ETH. There is no code path that returns this ETH to the affected user; it can only leave the contract via privileged host-management functions (if any exist), meaning ordinary users cannot recover it themselves.

## Likelihood Explanation
High: this triggers on the normal, documented, SDK-recommended flow for paying dispatch fees in native token (the SDK deliberately overpays by design because the router-side quote is admittedly imprecise). No special conditions, malicious relayer, or governance action is needed — any user dispatching with native token and any `msg.value` above the exact execution-time price loses the difference. Sandwiching the AMM (a routine, permissionless, unprivileged EVM MEV action) increases the size of the loss per transaction, but loss occurs even without an active attacker due to ordinary price drift between quote and execution.

## Recommendation
After calling `swapETHForExactTokens`, have `EvmHost` forward any residual `address(this).balance` delta (or track `msg.value - amounts[0]`) back to `_msgSender()` (or `post.payer`/the original caller for `fundRequest`) instead of retaining it. Alternatively, switch to `swapExactETHForTokens` with a caller-specified `amountOutMin`, and explicitly refund unspent input to the caller, so unpaid balance is never implicitly captured by the Host.

## Proof of Concept
1. User calls `MyApp.sendMessageWithNative{value: v}(...)` → `IDispatcher(host).dispatch{value: v}(post)` where `v` is the SDK-quoted fee plus a 1% buffer (per `hyperFungibleToken.ts:216`). [5](#0-4) 
2. `EvmHost.dispatch(DispatchPost)` executes:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [1](#0-0) 
3. Attacker front-runs the pool (sandwich) or simply the price has moved since the off-chain quote, so `amounts[0] < msg.value`.
4. Uniswap V2 Router refunds `msg.value - amounts[0]` to its caller, `EvmHost`, not to the original user.
5. `EvmHost.dispatch()` has no code to forward this refund to `_msgSender()`; the ETH stays trapped in `EvmHost`'s balance with no accounting tying it to the user who sent it.
6. Repeat for every native-fee dispatcher; the trapped balance in `EvmHost` grows monotonically at users' expense, and can be amplified by an attacker sandwiching the swap on each dispatch transaction they observe in the mempool.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
```
