Based on my investigation, I found a concrete gap between what the Aptos CLI's package `verify()` function checks and what it should check to guarantee that on-chain bytecode matches a reviewed/audited source package — this matches the required "mismatch between verified bytes, package metadata... and committed module bytes" impact category. I want to flag upfront that I was **not able to fully review** the entire `aptos-move/cli/src/stored_package.rs` file or the callers of `verify()` (e.g. the `verify-package` CLI subcommand) within my tool budget, so I cannot rule out that bytecode is compared elsewhere in that command's flow. I also explored an `object_code_deployment`/`init.move` ownership-model angle (direct `object::is_owner` used for upgrade/freeze vs. transitive `root_owner()` used for lazy self-init gating) but could not retrieve the bodies of `is_owner`/`root_owner`/`owns` in `object.move` to confirm whether they diverge in the way needed to prove an unauthorized-upgrade escalation, so I am not reporting that angle as a confirmed finding.

### Title
`stored_package::verify()` never compares actual module bytecode, only descriptive metadata — allows a "verified source" / malicious-bytecode mismatch - (File: `aptos-move/cli/src/stored_package.rs`)

### Summary
The CLI's package verification routine, used to confirm that code compiled from local sources matches what is deployed on-chain (e.g. via `aptos move verify-package`), only compares `PackageMetadata` struct fields — name, `deps`, `modules` (which are themselves just name/source-text/source-map metadata, not bytecode), `manifest`, `upgrade_policy`, `extension`, and `source_digest`. It never fetches or diffs the actual compiled module bytes stored at the on-chain address against the bytecode the CLI just built locally.

### Finding Description
`StoredPackage::verify` compares two `PackageMetadata` values field-by-field: [1](#0-0) 

`PackageMetadata.modules` is a `vector<ModuleMetadata>`, and `ModuleMetadata` only carries the module's declared `name`, optional gzipped `source` text, an optional `source_map`, and an `extension` — no bytecode hash or bytecode bytes are part of this struct: [2](#0-1) 

`BuiltPackage::extract_metadata` confirms this: when constructing `PackageMetadata` for a locally-built package it only populates `source_digest` (a hash of the *source files*, not the compiled bytecode) and per-module `source`/`source_map` (optional, and by design excludable), never anything derived from the serialized module bytes themselves: [3](#0-2) 

Because `source_digest` is a hash over sources, and `source`/`source_map` are optional and can legitimately be empty (`with_srcs`/`with_source_maps` flags), the only thing `verify()` structurally guarantees is that two `PackageMetadata` blobs are byte-identical — it does not independently prove that the bytecode on-chain was actually produced by compiling those sources, nor does it fetch/hash the on-chain `code: vector<vector<u8>>` bundle for comparison against a freshly-compiled local build.

### Impact Explanation
A malicious publisher could construct a `PackageMetadata` (name, manifest, `source_digest`, module names/sources) that appears legitimate and matches an audited/reviewed source tree, while submitting a *different* compiled module bundle (`code: vector<vector<u8>>`) in the same `publish_package_txn`/`object_code_deployment::publish` transaction — the Move VM's compatibility/verifier checks (`validate_publish_request` in `aptos_vm.rs`) only validate that module *names* in the bytecode match the `expected_modules` set derived from the metadata and that dependencies are legitimate; they do not verify that the bytecode was actually compiled from the declared `source`/`source_digest`. Anyone relying on the CLI's `verify()` path to confirm "deployed bytecode == this reviewed source package" (e.g. downstream tooling, block explorers, or auditors trusting a "verified" badge derived from this comparison) would be misled: the metadata can match while the actual executed bytecode differs, undermining code-safety guarantees for automated or human trust decisions built on top of this verification primitive.

### Likelihood Explanation
Likelihood is moderate: exploitation requires a malicious/careless package author to submit mismatched metadata and bytecode in a single publish transaction, which is entirely permissionless to do to one's own address/object, and requires a victim (tooling, explorer, or auditor) to rely on `verify()`/the metadata fields as proof of bytecode-source correspondence rather than independently comparing bytecode hashes. This is a tooling/process-level (code-safety invariant) gap, not a full remote-exploit primitive, but it directly matches the review's listed "mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" impact class.

### Recommendation
Extend `verify()` (and any downstream "verify-package"/explorer verification flow built on it) to also hash and compare the actual compiled module bytecode bundle (`code: vector<vector<u8>>`) retrieved from chain against bytecode freshly compiled from the claimed sources, rather than relying solely on the `PackageMetadata` struct (source text, source map, and source digest) as a proxy for bytecode equivalence.

### Proof of Concept
1. A malicious actor writes a legitimate-looking, auditable Move source package `S` and computes its `PackageMetadata` (via `BuiltPackage::extract_metadata`), including `source_digest` and per-module `source` text.
2. They separately compile a different, malicious module set `B'` (e.g. with an added backdoor entry function) whose module *names* match those declared in `S`'s metadata.
3. They call `code::publish_package_txn` (or `object_code_deployment::publish`) with the metadata for `S` but the bytecode `B'`. The VM's `validate_publish_request` only checks module name registration and dependency permissions, not bytecode/source correspondence: [4](#0-3) 
4. Anyone later running `StoredPackage::verify(&local_S_metadata)` against the on-chain `PackageRegistry` entry sees the metadata fields match and concludes the deployed code corresponds to source `S`, while the executing bytecode is actually `B'`.

    /// Extracts metadata, as needed for releasing a package, from the built package.
    pub fn extract_metadata(&self) -> anyhow::Result<PackageMetadata> {
        let source_digest = self
            .package
            .compiled_package_info
            .source_digest
            .map(|s| s.to_string())
            .unwrap_or_default();
        let manifest_file = self.package_path.join("Move.toml");
        let manifest = std::fs::read_to_string(manifest_file)?;
        let custom_props = extract_custom_fields(&manifest)?;
        let manifest = zip_metadata_str(&manifest)?;
        let upgrade_policy = if let Some(val) = custom_props.get(UPGRADE_POLICY_CUSTOM_FIELD) {
            str::parse::<UpgradePolicy>(val.as_ref())?
        } else {
            UpgradePolicy::compat()
        };
        let mut modules = vec![];
        for u in self.package.root_modules() {
            let name = u.unit.name().to_string();
            let source = if self.options.with_srcs {
                zip_metadata_str(&std::fs::read_to_string(&u.source_path)?)?
            } else {
                vec![]
            };
            let source_map = if self.options.with_source_maps {
                zip_metadata(&u.unit.serialize_source_map())?
            } else {
                vec![]
            };
            modules.push(ModuleMetadata {
                name,
                source,
                source_map,
                extension: None,
            })
        }
        let deps = self
            .package
            .deps_compiled_units
            .iter()
            .flat_map(|(name, unit)| match &unit.unit {
                CompiledUnit::Module(m) => {
                    let package_name = name.as_str().to_string();
                    let account = AccountAddress::new(m.address.into_bytes());

                    Some(PackageDep {
                        account,
                        package_name,
                    })
                },
                CompiledUnit::Script(_) => None,
            })
            .chain(
                self.package
                    .bytecode_deps
                    .iter()
                    .map(|(name, module)| PackageDep {
                        account: NumericalAddress::from_account_address(*module.self_addr())
                            .into_inner(),
                        package_name: name.as_str().to_string(),
                    }),
            )
            .collect::<BTreeSet<_>>()
            .into_iter()
            .collect();
        Ok(PackageMetadata {
            name: self.name().to_string(),
            upgrade_policy,
            upgrade_number: 0,
            source_digest,
            manifest,
            modules,
            deps,
            extension: None,
        })
    }
