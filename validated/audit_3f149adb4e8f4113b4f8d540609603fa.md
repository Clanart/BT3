### Title
Payout attribution (OP_RETURN operator identity) is unsigned by the withdrawing user, letting a third party hijack operator reimbursement credit for a peg-out it did not fund - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `payout_tx`'s only user-authenticated element is the withdrawal input and its matching output (index 0), signed with a `SinglePlusAnyoneCanPay` sighash. The additional funding inputs (added later via `fund_raw_transaction`/RBF) and the `OP_RETURN` output that records *which operator fronted the withdrawal* are outside that signature's coverage, so anyone who sees the pending payout transaction can rebuild it with different funding inputs and a different operator's `OP_RETURN` pubkey before it confirms. This breaks the equality `funder(payout_tx) == operator_credited_by(OP_RETURN)` that the reimbursement pipeline relies on.

### Finding Description
`create_payout_txhandler` builds the payout transaction with three outputs: the user's payout (`output_txout`, index 0), an anchor output, and an `OP_RETURN` output carrying `operator_xonly_pk` — the identity later used to attribute the withdrawal to an operator. [1](#0-0) 

The user's signature is verified to be `SinglePlusAnyoneCanPay`: [2](#0-1) 
Under `SIGHASH_SINGLE | ANYONECANPAY`, the signature commits only to the single signed input and the output at the *same index* (index 0, the user's payout output). It does **not** commit to:
- any additional inputs later attached by `fund_raw_transaction` (which is how the operator actually "fronts" the near-full withdrawal amount, since the user's original input is only a dust UTXO), and
- the anchor and `OP_RETURN` outputs (indices 1 and 2), including the operator attribution pubkey embedded in the `OP_RETURN`.

The reimbursement pipeline later determines *who gets paid back* purely by parsing this unsigned `OP_RETURN` field from whatever payout transaction actually confirms on-chain: [3](#0-2) 

That attribution then drives `PayoutCheckerTask`, which is keyed per-operator by matching this exact xonly pubkey, and triggers `handle_finalized_payout`, which consumes one of that operator's pre-signed kickoff connectors to claim the vault reimbursement: [4](#0-3) [5](#0-4) 
`validate_payer_is_operator` only checks that the attributed pubkey equals the local operator's own key — it never checks that the operator's own wallet actually supplied the funding inputs of the confirmed transaction: [6](#0-5) 

Because the funding inputs and the `OP_RETURN` are unsigned by the user, an unprivileged party observing the mempool can:
1. Take the user's signed `SinglePlusAnyoneCanPay` input/output pair (public once operator broadcasts the payout tx).
2. Build a competing transaction with the same signed input/output at index 0, but substitute their own funding inputs (fee-bumped via RBF, since `replaceable`/`add_inputs` funding is standard here) and an `OP_RETURN` naming a different operator xonly-pubkey than the one who actually intended to front the payout.
3. Get this version confirmed instead of the original operator's version.

The result: the party who supplied the BTC that actually paid the user is not the party subsequently credited and reimbursed from the vault via the kickoff/reimburse flow — the credited operator's `PayoutCheckerTask` will pick up the withdrawal as "theirs," consume a kickoff connector, and claim vault BTC for a payout it never funded.

### Impact Explanation
This breaks the custody binding "operator credited == party that fronted the withdrawal," matching the Critical category "an operator reimbursed for a payout it never funded." It also can be used adversarially against a targeted operator: forcing them to be attributed a payout they did not choose to front, consuming one of their scarce kickoff connectors for that round, potentially disrupting their normal reimbursement scheduling (`get_reimbursement_txs`/round-index bookkeeping in `handle_finalized_payout`).

### Likelihood Explanation
The precondition — RBF/fee-bumped funding via `fund_raw_transaction` with `add_inputs: true` — is the documented, intended way operators fund payouts, so unsigned funding inputs and an unsigned attribution `OP_RETURN` are the normal, not exceptional, state of every payout transaction while it sits unconfirmed in the mempool. Any network participant who can observe the mempool (no verifier/operator/watchtower privilege required) and construct a standard replacement transaction can attempt this. The main constraint is winning the fee race/RBF, which is an economic rather than a cryptographic barrier.

### Recommendation
Bind the operator attribution and the funding source to the user's authorization, e.g. by having the withdrawing user's signature (or an aggregator-countersigned commitment) cover the `OP_RETURN` operator-pubkey output as well (e.g. via `SIGHASH_ALL` for a first-party fronting commitment, or a separate pre-registration step binding withdrawal id → operator pubkey before broadcast), and/or have `validate_payer_is_operator`/`handle_finalized_payout` cross-check that the actual funding UTXOs of the confirmed payout tx trace back to the credited operator's known wallet before granting reimbursement rights.

### Proof of Concept
Not independently executable from the index alone (requires a running regtest/mempool environment to demonstrate the RBF race); the code path supporting the exploit is:
1. Operator A calls `withdraw()` → `create_payout_txhandler` produces a tx with `OP_RETURN(operator_A_xonly_pk)` at output 2, signed only over input 0 / output 0 with `SinglePlusAnyoneCanPay` [1](#0-0) , then funds it via `fund_raw_transaction` with `add_inputs: true` [7](#0-6) .
2. An observer extracts the signed input/witness for output 0, constructs a new transaction reusing it, adds their own funding inputs and a modified `OP_RETURN(operator_B_xonly_pk)`, and gets it confirmed instead (e.g., with a higher fee).
3. `update_finalized_payouts` parses the confirmed tx's `OP_RETURN` and attributes the withdrawal to operator B [3](#0-2) .
4. Operator B's `PayoutCheckerTask`/`handle_finalized_payout` claims vault reimbursement for a payout it never funded [4](#0-3) [5](#0-4) .

I was unable to fully verify within the index whether any additional signature check elsewhere (e.g., in `tx-sender`/`rbf.rs`, which also references sighash types) prevents third-party reconstruction of the payout transaction from the exposed input/witness; a Devin session with full repository and test-execution access would be needed to confirm the exploit end-to-end.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    async fn validate_payer_is_operator(
        &self,
        dbtx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
    ) -> Result<(BlockHash, Txid), BridgeError> {
        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,
        ) {
            (Some(payer_xonly_pk), Some(payout_blockhash), Some(kickoff_txid)) => {
                if payer_xonly_pk != self.signer.xonly_public_key {
                    return Err(eyre::eyre!(
                        "Payer is not own operator for deposit, payer xonly pk: {:?}, operator xonly pk: {:?}",
                        payer_xonly_pk,
                        self.signer.xonly_public_key
                    )
                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };
