### Title
ProtoJSON string serialization omits HTML/script-breakout escaping in Python, PHP, and Ruby bindings, unlike the hardened Java/C++/C# encoders - (File: `python/google/protobuf/json_format.py`, `upb/json/encode.c`)

### Summary
Protobuf's C++, Java, and C# ProtoJSON encoders deliberately escape `<`, `>`, `&`, `=`, `'` in string field values (in addition to standard JSON control-character escaping) specifically "to prevent security bugs in JavaScript" / "XSS risks" when JSON output is embedded in an HTML/`<script>` context by a consuming application. The Python `json_format.MessageToJson` path and the upb C JSON encoder used natively by the PHP and Ruby extensions do not perform this extra escaping, so a `</script>`-style payload in an attacker-controlled protobuf string field round-trips unescaped into JSON produced by these bindings.

### Finding Description
The invariant established by the Spark CVE-2017-7678 report is: attacker-controlled data that is reflected back into a page must be escaped for the context (HTML/script) it lands in before rendering; failing to do so lets an attacker break out of a script/data literal and inject markup/script that executes in a victim's browser.

Protobuf's own ProtoJSON writers already encode this exact invariant as a defense-in-depth control, independent of strict JSON-spec requirements:

- C++ (`src/google/protobuf/json/internal/writer.cc`): `MustEscape()` explicitly escapes `'<'` and `'>'` "not required by the JSON spec, but help to prevent security bugs in JavaScript" [1](#0-0) , and `WriteEscapedUtf8` treats `<`/`>` as unsafe characters requiring escaping [2](#0-1) .
- Java (`java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`): explicitly adds `<>&='` to the replacement table "to prevent XSS risks" [3](#0-2) , verified by the regression test for bug `b/73832901` (`testHtmlEscape`) [4](#0-3) .
- C# (`csharp/src/Google.Protobuf/JsonFormatter.cs`): the `CommonRepresentations` table escapes `<`/`>` for the same stated reason ("Escaping of < and > are required for HTML security") [5](#0-4) .
- The generic C++ JSON conformance test also asserts this behavior directly: `</script>` becomes `\u003c/script\u003e` [6](#0-5) .

In contrast, the upb C JSON encoder — the shared native implementation embedded in PHP (`php-upb.c`) and Ruby (`ruby-upb.c`) and also present standalone in `upb/json/encode.c` — only escapes the JSON-spec-mandated set (`\n \r \t \" \f \b \\` and control bytes < 0x20); it does not escape `<` or `>`: [7](#0-6) [8](#0-7) 

Python's `json_format.MessageToJson` builds a Python `dict`/JSON string via the standard library `json.dumps` (confirmed present in `python/google/protobuf/json_format.py`), which likewise performs only standard JSON escaping and does not escape `<`/`>`/`&` for HTML-safety, unlike the C++/Java/C# writers that were purpose-built with this extra escaping.

### Impact Explanation
This is the direct analog of the Spark advisory's failed invariant: an attacker-controlled value (a protobuf string field) is serialized to JSON by a supported public API (`MessageToJson` in Python, or the native JSON encoder invoked from generated PHP/Ruby code) and, when a consuming application embeds that JSON verbatim inside an HTML `<script>` block (a common "hydrate client state from server JSON" pattern), the missing `<`/`>` escaping allows a value like `</script><script>alert(1)</script>` to break out of the script context and execute in the victim's browser — a reflected XSS, matching CWE-79 and the CVSS vector's `UI:R`/`S:C` characteristics (victim must view a page that renders the reflected value; the impact crosses from the serializer into the browser context).

Because this same defense was intentionally added to the C++, Java, and C# encoders (with an explicit regression test citing bug `b/73832901`), its absence in the Python/PHP/Ruby encoders represents an inconsistent security control across officially supported language bindings of the same library feature (ProtoJSON serialization), not an intentional interpretation difference.

### Likelihood Explanation
Likelihood is moderate: it requires (1) an application using Python, PHP, or Ruby protobuf bindings to serialize a message containing attacker-controlled string data to ProtoJSON, and (2) that application embedding the resulting JSON directly into an HTML/script context without its own additional escaping — a known and still-common pattern for passing server-rendered data to client-side JavaScript. This mirrors the original Spark UI scenario, where the vulnerable component reflected attacker data into a web page without contextual escaping.

### Recommendation
Add the same HTML-unsafe character escaping (`<`, `>`, and ideally `&`, `=`, `'`) that C++, Java, and C# already apply to Python's `json_format.MessageToJson`/`ParseDict` string-encoding path, and to the shared upb JSON encoder (`upb/json/encode.c`, and its embedded copies in `php-upb.c`/`ruby-upb.c`), so that ProtoJSON output is consistently safe to embed in HTML/script contexts across all official language implementations. Add a cross-language conformance test analogous to the existing C++/Java `HtmlEscape`/`testHtmlEscape` tests to prevent regression.

### Proof of Concept
Conceptual reproduction (not executed in this review — flag as unverified pending a local run):
1. Define a trusted proto schema with a `string` field, e.g. `message M { string s = 1; }`.
2. In Python: `m = M(s="</script><script>alert(1)</script>")`; `json_format.MessageToJson(m)`.
   - Expected (per C++/Java/C# behavior): `s` should be escaped as `\u003c/script\u003e...`.
   - Actual (via `json.dumps`): the literal `</script><script>alert(1)</script>` is emitted unescaped in the JSON string value.
3. Compare against the equivalent C++ call `MessageToJsonString(m, &json)` or Java `JsonFormat.printer().print(m)`, which per `JsonFormatTest.testHtmlEscape` and `json_test.cc`'s `HtmlEscape` test produce `\u003c/script\u003e`.
4. The same discrepancy is expected for PHP/Ruby generated-message `serializeToJsonString()`/`to_json` calls, since they route through the same `jsonenc_put_escaped_char` in `php-upb.c`/`ruby-upb.c` shown above, which lacks the `<`/`>` case.

This proof-of-concept is a code-comparison-based demonstration; I was not able to execute the actual Python/PHP/Ruby runtime in this review to confirm the end-to-end output byte-for-byte, so this should be validated with a live run before being treated as fully confirmed.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}
