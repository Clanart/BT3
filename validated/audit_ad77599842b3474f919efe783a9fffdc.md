Interesting finding: `precompiles/common/balance_handler.go` — there's an explicit note in `evmd/tests/integration/balance_handler/balance_handler_test.go` referencing "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leads to balance desync between native bank keeper and EVM stateDB." Let me examine this more closely, since it's a concrete dual-accounting-path desync bug already flagged in the codebase (possibly fixed or still present).### Title
BalanceHandler shared `prevEventsLen` state causes StateDB/bank balance desync on nested precompile calls - (File: precompiles/common/balance_handler.go)

### Summary
`BalanceHandler` tracks bank-module events emitted during a precompile call by recording an event-log cursor (`prevEventsLen`) in `BeforeBalanceChange` and consuming events from that cursor onward in `AfterBalanceChange` to mirror `x/bank` balance changes into the EVM `StateDB`. This is structurally the same class of bug as the Convergence `ysTotal` issue in the external report: two different accounting representations of the same value (the Cosmos `x/bank`/`x/precisebank` ledger vs. the EVM `StateDB` balance) are kept in sync via a derived/tracked quantity, but the tracking state (`prevEventsLen`) is mutated non-reentrantly. When a precompile call triggers a nested/recursive precompile invocation within the same EVM call frame (contract calls precompile → precompile call executes a Cosmos message → that flow calls back into a contract → contract calls a precompile again), the inner invocation's `BeforeBalanceChange` overwrites `prevEventsLen` before the outer invocation's `AfterBalanceChange` runs, causing the outer call to consume the wrong slice of the event log — either replaying events already applied by the inner call, or skipping its own events entirely.

### Finding Description
`BalanceHandler.prevEventsLen` (`precompiles/common/balance_handler.go:38-48`) is instance state, not call-frame-scoped state:

```go
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}
``` [1](#0-0) 

`AfterBalanceChange` then slices `events[bh.prevEventsLen:]` and replays `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events into `StateDB.AddBalance`/`SubBalance`: [2](#0-1) 

If the same `BalanceHandler` instance is reused across a nested/recursive precompile call chain (a call into a precompile that, directly or via a contract callback, results in another precompile invocation before the outer call's `AfterBalanceChange` executes), the inner call's `BeforeBalanceChange` resets `prevEventsLen` to a later index. When control returns to the outer call and it invokes `AfterBalanceChange`, it uses the now-advanced cursor, which either:
- Skips the outer call's own `CoinSpent`/`CoinReceived` events (StateDB never receives the balance delta the real bank keeper already applied), or
- Double-applies the inner call's events if ordering/interleaving allows `prevEventsLen` to end up before events already consumed.

This directly diverges the EVM-visible `StateDB` balance from the real, ledger-backed `x/bank`/`x/precisebank` balance — the exact invariant break the external report describes (two different derivations of "how much a party has/owes" going out of sync, leaving spendable value under- or over-counted for at least one party).

This exact mechanism and reachability is already documented and reproduced by an existing regression test in the repo: [3](#0-2) 
which drives it end-to-end through an ordinary (non-privileged) contract call that recursively re-enters a precompile: [4](#0-3) 

### Impact Explanation
If this desync is reachable through the production precompiles that move real value (ERC20, WERC20, staking, distribution, ICS20 — all of which call `BeforeBalanceChange`/`AfterBalanceChange` around bank-mutating operations), the result is a `StateDB` balance that no longer reflects the actual `x/bank`/`x/precisebank` ledger. This is a direct instance of "irreversible accounting corruption of spendable user value across native balances, EVM balances" — an attacker-controlled contract that recurses through precompile calls (e.g., wrapping/unwrapping, transferring, or ICS20-triggered callback re-entry) can cause the EVM-visible balance to be permanently inflated (double-credited) relative to the real backing coins, or another account's legitimate credit to be silently dropped, enabling extraction of value the ledger does not actually back, or permanent loss of funds for the account whose event was skipped.

### Likelihood Explanation
The regression test in `evmd/tests/integration/balance_handler/balance_handler_test.go` shows the underlying mechanism is trivially reachable by an unprivileged user deploying a plain contract that makes a recursive/nested precompile call — no privileged keys, validators, or governance are required. However, I could not confirm from the retrieved code whether:
1. `BalanceHandler` instances are actually shared/reused across nested precompile invocations in the production precompiles (ERC20/WERC20/staking/distribution/ICS20) the same way the test's `debug` precompile demonstrates, or scoped per-call in a way that already prevents the corruption in shipped precompiles, and
2. Whether this has already been patched (the test may exist specifically to lock in a fix, i.e., assert the *correct* post-fix behavior rather than demonstrate an open bug).

I was not able to retrieve the call site(s) that construct `BalanceHandler` per precompile invocation (e.g., in the EVM precompile dispatch/`RunNativeAction` code) to confirm instance lifetime, nor the exact recursion path in the real (non-debug) precompiles. This is a material gap: without that confirmation, I cannot assert with certainty this is an *unpatched*, *exploitable* Critical bug versus a documented/mitigated edge case exercised only by the synthetic `debug` precompile used for testing.

### Recommendation
Scope `prevEventsLen` (and any other accounting cursor state) to the call frame rather than the handler instance — e.g., pass the "before" length as a value returned from `BeforeBalanceChange` and threaded explicitly into the matching `AfterBalanceChange` call (or use a stack/counter keyed by call depth), so nested/recursive precompile invocations cannot clobber an outer call's cursor. Add an invariant check (e.g., in integration tests across all value-moving precompiles, not just the debug precompile) that asserts `StateDB` balances always equal `x/bank`/`x/precisebank`-derived balances after any nested/recursive precompile call sequence, and specifically test recursion through ERC20/WERC20/ICS20/staking/distribution precompiles (not only the synthetic debug precompile) to confirm the production code paths are unaffected or need the same fix.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
```
