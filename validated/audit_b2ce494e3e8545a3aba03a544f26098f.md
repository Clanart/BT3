### Title
Stale cached FROST preprocess reused across validator sets due to insufficient context binding, causing nonce reuse and validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The analog of the reported bug class — retrieving state for "the latest/whatever is present" rather than state bound to the exact scope being operated on — exists in `SigningProtocol::preprocess_internal`. The DKG-confirmation MuSig/FROST preprocess is cached in `CachedPreprocesses` keyed only by `context = (b"DkgConfirmer", attempt)` [1](#0-0) . The key does not include the tributary `spec.genesis()`, `spec.set()`, the participant set, or the `removed` set — i.e., the equivalent of `req.Height`. `CachedPreprocesses::get` therefore returns whatever stale preprocess exists for that bare attempt number, exactly like `LastCommitInfo` returning commit info for the wrong height [2](#0-1) .

### Finding Description
`preprocess_internal` loads (or creates once) a `CachedPreprocess` seed under `(b"DkgConfirmer", self.attempt)` and rebuilds the sign machine with `AlgorithmSignMachine::from_cache` [3](#0-2) . `from_cache` calls `seeded_preprocess`, which deterministically derives all FROST nonces from `ChaCha20Rng::from_seed(*seed.0)` — the nonces depend only on the seed, not on the current `keys`, `participants`, or `msg` [4](#0-3) . The MuSig keys are rebuilt fresh each call from `musig(musig_context(self.spec.set()), key, participants)` [5](#0-4) , so the cached nonce is combined with whatever the *current* set/participants/message are — the exact inconsistency in the report.

Because `attempt` restarts at 0 for every new validator set/DKG and the `SigningProtocolDb` is a coordinator-global DB, a validator participating in a DKG confirmation for set A (attempt 0) and later set B (attempt 0) reuses the identical nonce. The confirmation signature shares (`DkgConfirmed` txs) and the resulting on-chain `set_keys` signature are public. Additionally, `DkgKeyPair::set`/`generated_key_pair` unconditionally overwrite the key pair for `(genesis, attempt)` [6](#0-5) , and `share`/`complete` each re-invoke `share_internal` with the same cached nonce [7](#0-6) , so any divergence in `key_pair` or `preprocesses` between calls produces a second share under the same nonce over a different challenge.

### Impact Explanation
Reusing a Schnorr/FROST nonce across two shares with distinct binding factors/messages lets any observer solve for the signer's secret scalar share. Here the victim is the coordinator's *validator key* (`self.key`), used both for tributary transaction signing and as a MuSig share for on-chain `set_keys`. Recovery enables forging tributary transactions as that validator and forging participation in future `set_keys` confirmations — a full validator-key compromise from publicly observable data.

### Likelihood Explanation
Every new validator set triggers a new DKG with `attempt` counting from 0, and long-lived validators keep the same `key` across sets — so cache collision on `(b"DkgConfirmer", 0)` is routine, not edge-case. The file's own header acknowledges nonce reuse leaks the private key and relies on the nonces being "context-bound" [8](#0-7) , yet the DB context does not actually bind the set. Both resulting signatures are published publicly (tributary `DkgConfirmed` and the substrate `set_keys` call) [9](#0-8) .

Caveat: if `SigningProtocolDb`'s txn is somehow partitioned per genesis (not indicated by `create_db!`, which namespaces only by label + encoded key), the cross-set path would not apply; the intra-attempt double-sign via overwritten `DkgKeyPair` still would.

### Recommendation
Bind the cache key to the full scope, like the report's "load the commit info for the exact height": use `context = (b"DkgConfirmer", spec.genesis(), self.attempt)` (or include `spec.set()` and the `removed` set), and refuse to `share`/`complete` when the loaded machine's published preprocess doesn't match the on-chain `ConfirmationNonces` entry — the file already notes this TODO [10](#0-9) . Additionally, make `generated_key_pair` reject a second `DkgKeyPair::set` for the same `(genesis, attempt)`.

### Proof of Concept
1. Validator V participates in DKG confirmation attempt 0 for tributary set A: `preprocess_internal` stores `CachedPreprocesses[("DkgConfirmer", 0)] = enc(seed_A)`, publishes nonce commitments in `DkgShares`, and publishes share `s_A = d + e·ρ_A + λ·x·c_A` via `DkgConfirmed`/`set_keys` for message `set_keys_message(set_A, …, key_pair_A)`.
2. A new validator set B is formed; V remains a validator with the same `key`. New DKG, `attempt = 0` again.
3. `preprocess_internal` finds `CachedPreprocesses[("DkgConfirmer", 0)]` already populated → `from_cache` regenerates the *identical* nonces `d, e` from `seed_A` (seed-derived, independent of keys/msg, `crypto/frost/src/sign.rs:127-133`).
4. V signs `set_keys_message(set_B, removed_B, key_pair_B)` producing share `s_B = d + e·ρ_B + λ'·x'·c_B`. With `R` identical and both `(s_A, msg_A, ρ_A)` / `(s_B, msg_B, ρ_B)` public, the nonce `d + e·ρ` cancels algebraically; solving the two linear equations yields V's secret share/key contribution. An attacker now holds V's validator signing scalar and can forge tributary txs and future confirmation shares.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
