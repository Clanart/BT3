### Title
Missing `chain_id` in EIP-712 Domain Enables Cross-Network Replay of Aggregator Withdrawal Verification Signatures — (`File: core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

`CLEMENTINE_EIP712_DOMAIN` is defined without a `chain_id` field. This domain is used to sign and verify the aggregator's ECDSA authorization signature for both the operator withdrawal flow (`OperatorWithdrawalMessage`) and the optimistic payout flow (`OptimisticPayoutMessage`). A valid signature produced on one network (e.g., testnet4) is cryptographically identical on any other network (e.g., mainnet) because the domain hash does not encode the network. An attacker who captures a legitimate aggregator-signed withdrawal authorization from testnet4 can replay it verbatim against a mainnet operator or verifier, bypassing the only application-layer authentication gate that guards the payout path.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is declared as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

The EIP-712 specification requires `chainId` in the domain separator precisely to prevent cross-chain/cross-network replay. The field is absent here.

This domain is used in `recover_address_from_ecdsa_signature`, which is the single function that verifies the aggregator's authorization for both withdrawal paths:

```rust
let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);
let address = signature.recover_address_from_prehash(&eip712_hash)...;
``` [2](#0-1) 

This recovered address is then compared to `aggregator_verification_address` in config. The check is enforced in two places:

1. **Operator withdrawal** (`core/src/rpc/operator.rs`, `withdraw` RPC): [3](#0-2) 

2. **Verifier optimistic payout** (`core/src/verifier.rs`, `sign_optimistic_payout`): [4](#0-3) 

Because the domain hash is network-agnostic, the EIP-712 hash of identical withdrawal params is identical on every network. A signature that passes verification on testnet4 will pass the same `recover_address_from_prehash` check on mainnet.

The developers are explicitly aware of the cross-network replay threat: `BatchProofMethodIdBody` in the tx-sender crate includes `chain_id: u64` with the comment *"Network identifier to prevent cross network replay attacks"*: [5](#0-4) 

The same protection was not applied to the EIP-712 domain. `citrea_chain_id` is already a first-class field in `BridgeConfig` (e.g., `62298` for regtest, `5655` in `.env.example`): [6](#0-5) 

---

### Impact Explanation

When `aggregator_verification_address` is configured (the production-intended state shown in `.env.example` line 45 and `scripts/docker/configs/regtest/.env.regtest`), the verification signature is the **only** application-layer gate that prevents an unauthorized party from triggering a payout. If the gate can be bypassed by replaying a testnet4 signature on mainnet:

- The operator's `withdraw` function proceeds to call `operator.withdraw(...)`, which constructs and broadcasts a payout transaction spending the operator's own collateral UTXO.
- The operator then initiates a kickoff and claims reimbursement from the bridge vault (the N-of-N UTXO holding deposited BTC).
- A successful replay therefore results in an unauthorized drain of the bridge vault for the replayed withdrawal amount (up to `bridge_amount` per deposit, e.g., 1 BTC in testnet4 config, 10 BTC in mainnet config).

The same replay applies to the optimistic payout path through `sign_optimistic_payout` on the verifier, which also gates on the same domain-less EIP-712 check.

---

### Likelihood Explanation

Preconditions for exploitation:

1. The same `aggregator_verification_address` / signing key is used on both testnet4 and mainnet (common operational practice — operators typically reuse keys across environments).
2. The attacker observes a valid aggregator-signed withdrawal on testnet4 (e.g., by monitoring the public gRPC endpoint or the testnet4 mempool).
3. The replayed `withdrawal_id` and `input_outpoint` must correspond to a valid, unspent withdrawal UTXO on mainnet. Because `withdrawal_id` is a sequential Citrea bridge contract counter and `input_outpoint` is a Bitcoin UTXO created by the bridge's move-to-vault transaction, these will differ between networks in the common case — but if the same deposit sequence and UTXO set exists on both networks (e.g., during a parallel testnet4/mainnet deployment with mirrored deposits), the replay is directly executable.

The likelihood is **Medium**: the key-reuse precondition is operationally common, and the UTXO-match precondition is non-trivial but achievable in a parallel-deployment scenario.

---

### Recommendation

Add `chain_id` to `CLEMENTINE_EIP712_DOMAIN`, sourced from `BridgeConfig::citrea_chain_id`:

```rust
// Make the domain non-static; construct it per-config instance
pub fn clementine_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Pass `config.citrea_chain_id as u64` wherever `CLEMENTINE_EIP712_DOMAIN` is currently used:
- `recover_address_from_ecdsa_signature` (called from `core/src/rpc/operator.rs` and `core/src/verifier.rs`)
- `sign_withdrawal_verification_signature` in `core/src/test/sign.rs`

This mirrors the pattern already used in `BatchProofMethodIdBody` and aligns with EIP-712's stated purpose for the `chainId` field.

---

### Proof of Concept

**Setup**: Two deployments share the same `aggregator_verification_address` key — one on testnet4 (`citrea_chain_id = 62298`) and one on mainnet.

**Step 1 — Capture testnet4 signature**: Aggregator signs a withdrawal on testnet4:
```
withdrawal_id = 7
input_outpoint = <txid>:<vout>   // testnet4 bridge vault UTXO
output_script_pubkey = <user_addr>
output_amount = 999_760_000 sat
```
The EIP-712 hash is computed over `CLEMENTINE_EIP712_DOMAIN` (name + version only, no chain_id). The resulting `verification_signature` = `0xABCD...`.

**Step 2 — Replay on mainnet**: Submit the identical `WithdrawParamsWithSig` to a mainnet operator's `withdraw` RPC with `verification_signature = 0xABCD...`.

**Step 3 — Verification passes**: `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` computes the same EIP-712 hash (domain is identical on both networks) and recovers the same aggregator address. The check `address_from_sig == address_in_config` passes. [7](#0-6) 

**Step 4 — Payout executes**: The operator broadcasts a payout transaction, then initiates a kickoff and claims reimbursement from the mainnet bridge vault, draining up to `bridge_amount` of real BTC.
