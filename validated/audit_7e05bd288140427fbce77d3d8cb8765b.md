### Title
Spoofed `WWW-Authenticate` `realm="GitHub"` header allows attacker-controlled host to force a trusted GitHub Enterprise sign-in flow, bypassing host verification - (File: trampoline-credential-helper.ts)

### Summary
`getEndpointKind` in [1](#0-0)  classifies a remote as `'enterprise'`, `'generic'`, or unknown based on the raw content of `wwwauth[N]` credential fields that git forwards from the HTTP response of whatever remote/proxy it is talking to. This classification is trusted *before* the actual network-based verification (`isGitHubHost(endpoint)`) is ever performed, so a value fully controlled by an unprivileged, attacker-run HTTP server (or a malicious proxy) short-circuits host trust decisions.

### Finding Description
The credential-helper git command handler (`getCredential`) calls `getEndpointKind(cred, store)` to decide how to treat the current remote. Inside it: [2](#0-1) 

Any HTTP server that git is authenticating against can return a `WWW-Authenticate` header such as `WWW-Authenticate: Basic realm="GitHub"`. Git captures this into `wwwauth[0]`/`wwwauth[1]`/... fields and passes them to the credential helper via stdin, which is parsed into the `cred` map consumed here. The code performs a plain substring match on `realm="GitHub"` with **no verification that the responding host is actually a GitHub/GHE server** — the real verification path, `isGitHubHost(endpoint)` at line 178, is only reached if the `wwwauth` loop does not already return a classification.

Once classified `'enterprise'`, `getCredential` checks whether an existing account already matches `apiEndpoint`: [3](#0-2) 

If none matches (the normal case for a brand-new attacker host), it calls `ui.promptForGitHubSignIn(endpoint)` with `endpoint` equal to the **attacker-controlled URL**. That, in turn, calls: [4](#0-3) 

Because `hostname !== 'github.com'`, this invokes `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` using the **attacker's origin**, then shows the standard "Sign in" popup labelled as a credential-helper-initiated GitHub sign-in for that endpoint. The trust decision to present this as a "GitHub Enterprise" sign-in — rather than a generic username/password prompt (`promptForGenericGitAuthentication`) — was made solely from the spoofable `realm="GitHub"` string, not from any verified property of the remote.

### Impact Explanation
An attacker who controls a git remote or an HTTP(S) proxy that git connects to (e.g., via a crafted `insteadOf`/proxy config the user is lured into using, or simply an attacker-hosted git server the user clones/adds as a remote) can force GitHub Desktop to:
1. Skip the legitimate `isGitHubHost` check that would otherwise make a real API call to confirm the host is GitHub/GHE.
2. Present the user with what looks like a trusted "Sign in to GitHub Enterprise" dialog bound to the attacker's origin.

If the user, believing this is a legitimate GitHub Desktop authentication prompt (which is an expected part of normal clone/fetch/push flows), enters an enterprise host address, a Personal Access Token, or completes an OAuth-style flow, that secret is sent directly to the attacker-controlled endpoint. This is a credential-harvesting primitive reachable purely from server response content, matching the "credential/token exfiltration" impact category in scope.

### Likelihood Explanation
Exploitation only requires the victim to interact with an attacker-controlled remote/proxy that returns a crafted `WWW-Authenticate` header during a normal git operation (clone, fetch, push) — no local access, no malware, and no unnatural steps, since being prompted to authenticate against a new remote is the expected behavior. The only user action needed is completing the resulting sign-in prompt, which is the same action they'd take for a legitimate authentication request.

### Recommendation
Do not use the `wwwauth[]` header content alone to decide trust-sensitive classification (`'enterprise'` vs `'generic'`). At minimum, gate the `realm="GitHub"` fast path behind the same `isGitHubHost()` verification (or an HTTPS-only, network-confirmed check) before routing to `promptForGitHubSignIn`, and ensure the sign-in UI clearly and unambiguously discloses the actual target host/origin so users can recognize an unexpected/untrusted enterprise endpoint before entering credentials.

### Proof of Concept
1. Attacker stands up an HTTP server implementing minimal git smart-HTTP protocol that requires auth and returns `WWW-Authenticate: Basic realm="GitHub"` on a 401 response.
2. Victim adds this server as a remote in GitHub Desktop and performs a fetch/push.
3. Git invokes the GitHub Desktop credential helper; `cred` contains `wwwauth[0] = 'Basic realm="GitHub"'`.
4. `getEndpointKind` returns `'enterprise'` without ever calling `isGitHubHost`.
5. Since no existing account matches the attacker's `apiEndpoint`, `promptForGitHubSignIn(attackerUrl)` is invoked, showing a "Sign in to GitHub Enterprise" dialog bound to the attacker's origin.
6. If the user completes the flow (e.g., enters an enterprise PAT), that credential is transmitted to the attacker's server.

Note: I could not fully verify from the indexed code how much additional validation `dispatcher.beginEnterpriseSignIn`/the `SignInStore` performs before accepting a token for an arbitrary origin (e.g., whether it independently probes `/api/v3` first) — that logic lives outside the files retrievable here, so the exact downstream guardrails (if any) should be confirmed in a full checkout before treating the phishing impact as unconditional.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
