### Title
Argument/flag injection via attacker-controlled remote name reaching `git fetch` without `--` separator - (File: `app/src/lib/git/fetch.ts`)

### Summary
`getFetchArgs` builds the argv for `git fetch` by appending the raw `remote` string as the final positional argument, with no `--` separator and no check that it doesn't start with `-`/`--`. [1](#0-0)  The value passed in is `remote.name`, taken directly from `fetch()`'s `remote: IRemote` parameter. [2](#0-1) 

### Finding Description
`IRemote[]` (including `.name`) is populated by `getRemotes()`, which runs `git remote -v` and parses the output with a permissive regex `^(.+)\t(.+)\s\(fetch\)` — it captures whatever text appears before the tab as the remote name, with no validation against a leading `-`/`--`. [3](#0-2)  That data ultimately originates from the repository's own `.git/config` `[remote "<name>"]` subsection headers, which is plain text a malicious repository author fully controls (independent of whether the name would ever pass through `git remote add`, since `git remote add` is not the only way a config can acquire a remote section — a crafted repo can ship a `.git/config` with an arbitrary subsection name).

This is unlike branch/ref names elsewhere in the codebase, which are explicitly sanitized to strip leading `-`/`+` characters before being used as git operands: `sanitizedRefName` calls `.replace(/^[-\+]*/g, '')`. [4](#0-3)  No equivalent sanitization exists for remote names in `remote.ts` or `fetch.ts`.

Consequently, if a remote name value such as `--upload-pack=<arbitrary command>` reaches `getFetchArgs`, the constructed argv becomes:
```
fetch --prune --recurse-submodules=on-demand --upload-pack=<arbitrary command>
```
Because there is no `--` before the remote operand, git's own argv parser will interpret this as the `--upload-pack` option (used by git to specify the remote-side executable for local/`file://`/ssh-style transports) rather than as a remote name, potentially causing git to execute attacker-supplied text as a program during the fetch operation.

The same argument-construction pattern (`remote.name` appended without `--`) is also present in `updateRemoteHEAD` (`git remote set-head -a`) and other remote.ts calls, though those weren't the specific target of this question. [5](#0-4) 

### Impact Explanation
If exploitable, this allows a malicious repository (cloned or opened by the victim) to have its remote metadata cause `git fetch` — invoked automatically or on user action by Desktop — to execute an attacker-chosen local process via `--upload-pack=<cmd>` (or other injectable git-fetch options), which is Critical-class remote/local code execution triggered purely by opening/fetching a hostile repository.

### Likelihood Explanation
Requires only that the victim open/clone a repository whose `.git/config` contains a remote section with a name beginning with `-`/`--`, and that Desktop subsequently calls `fetch()` for that remote (which happens routinely, including background fetches). No local access, credentials, or unusual user action beyond normal repository use is needed.

### Recommendation
- In `getFetchArgs` (and other remote-consuming git argument builders such as `updateRemoteHEAD`, `fetchRefspec`), insert a literal `'--'` separator before the `remote` operand, e.g. `['fetch', ..., '--', remote]`, so git can never interpret it as an option.
- Additionally validate/sanitize remote names the same way ref/branch names are sanitized (reject or strip leading `-`/`+`) when they are read back from `getRemotes()`/`.git/config`, not just when created through Desktop's own "add remote" UI.

### Proof of Concept
1. Craft a repository whose `.git/config` contains:
```
[remote "--upload-pack=touch /tmp/pwned;true"]
    url = file:///some/local/path
    fetch = +refs/heads/*:refs/remotes/x/*
```
2. Have the victim open/clone this repository in GitHub Desktop.
3. Desktop's `getRemotes()` parses this entry into `{ name: "--upload-pack=touch /tmp/pwned;true", url: ... }`. [6](#0-5) 
4. A subsequent fetch (manual or background) calls `fetch(repository, remote, …)` → `getFetchArgs(remote.name, …)`, producing argv `['fetch', '--prune', '--recurse-submodules=on-demand', '--upload-pack=touch /tmp/pwned;true']` with no `--` guard. [7](#0-6) 
5. git interprets `--upload-pack=...` as an option instead of a remote name, potentially executing the embedded command.

Note: I was not able to execute git directly to confirm the exact runtime behavior of `git fetch --upload-pack=<cmd>` against this specific dugite/git version bundled with the app, or to confirm empirically that a `.git/config` remote section name can be crafted outside of `git remote add`'s own name validation and still be parsed by `git remote -v`. These are standard, well-documented git behaviors, but verifying them against this exact build should be done with a live test as described in the "Fast validation" section before treating this as fully confirmed.

```typescript
export async function getRemotes(
  repository: Repository
): Promise<ReadonlyArray<IRemote>> {
  const result = await git(['remote', '-v'], repository.path, 'getRemotes', {
    expectedErrors: new Set([GitError.NotAGitRepository]),
  })

  if (result.gitError === GitError.NotAGitRepository) {
    return []
  }

  return [...result.stdout.matchAll(/^(.+)\t(.+)\s\(fetch\)/gm)].map(
    ([, name, url]) => ({ name, url })
  )
}
```
