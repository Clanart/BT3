### Title
OP_RETURN data output omitted from weight/fee accounting produces under-funded or unbroadcastable transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug class is an operand-level mistake: a computed item is never folded into the index/accounting, so work that was performed (or bytes that were added) is silently dropped. In `SignableTransaction::new`, an `OP_RETURN` output carrying up to 80 bytes of caller-supplied data is pushed onto the transaction's output list, but the weight, vbyte, and fee calculations only ever consider `payments` and `change`. The data output is "scheduled" into the transaction yet never accounted for — the same shape as `wireID` never being assigned so every item lands in `wires[0]`.

### Finding Description
`SignableTransaction::new` builds `tx_outs` from `payments` and then appends an `OP_RETURN` output when `data` is specified:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
```

However, the transaction template passed to `calculate_weight_vbytes` is built solely from `payments`:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` expands a template `Transaction` whose `output` field is derived only from `payments` plus an optional `change` output — the `data` output is never included. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` under-counts the real vsize by the size of the OP_RETURN output (roughly `9 + data_len` bytes, i.e. up to ~90 vbytes for the permitted 80-byte payload).
2. The minimum-relay check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` is evaluated against the smaller, incorrect vsize. A caller specifying `fee_per_vbyte` at the relay minimum produces a transaction whose *actual* feerate (`needed_fee / real_vsize`) falls below the 1 sat/vbyte relay floor.
3. The `input_sat < payment_sat + needed_fee` sufficiency check uses the under-counted fee, and the `weight > MAX_STANDARD_TX_WEIGHT` standardness check uses `weight` that never includes the data output (it is only ever replaced by `weight_with_change`). A transaction at the standard-weight boundary plus an OP_RETURN output can exceed 400,000 WU while passing the check.

### Impact Explanation
Any caller that attaches `data` receives a `SignableTransaction` which either (a) pays a feerate below the requested `fee_per_vbyte`, violating the documented contract that `needed_fee` is "the fee necessary for this transaction to achieve the fee rate specified at construction", or (b) at boundary conditions produces a transaction that exceeds `MAX_STANDARD_TX_WEIGHT` or falls below the minimum relay feerate and therefore cannot be broadcast. The inputs committed to such a transaction are not spendable through it — funds are locked until a corrected transaction is re-signed, directly analogous to the report's "ethers locked in a scheduled action that can never execute". Since the transaction commits to its exact output set in the sighash, the defect cannot be patched post-hoc without a new signing round.

### Likelihood Explanation
The bug triggers deterministically whenever `SignableTransaction::new` is called with `Some(data)` — the accounting omission is unconditional, not probabilistic. Whether it manifests as a failed broadcast depends on `fee_per_vbyte` and the proximity to weight/fee limits: a minimum-feerate transaction with a large data payload fails relay checks; a transaction near the weight cap with data becomes non-standard. An unprivileged party that can cause an OP_RETURN payload to be embedded in a Serai-signed Bitcoin transaction (the library explicitly supports `data` up to 80 bytes) reaches this path with public input.

### Recommendation
- Include the data output in the template transaction used by `calculate_weight_vbytes`, or compute `needed_fee`/`weight` from `tx_outs` (which already contains payments + OP_RETURN) rather than from `payments` alone.
- Re-run the `MAX_STANDARD_TX_WEIGHT` and minimum-fee checks against the final output set after the change output is decided.
- Add a unit test constructing a `SignableTransaction` with `Some(data)` asserting `tx.vsize() * fee_per_vbyte <= needed_fee` and that the weight check reflects the data output — the omission would be caught by any test that includes a data output.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs conceptual test
let tx = SignableTransaction::new(
  vec![input],                       // ReceivedOutput
  &[(payment_script, 10_000)],       // payments
  None,                              // no change
  Some(vec![0xAA; 80]),              // max-size OP_RETURN payload
  1,                                 // 1 sat/vbyte = minimum relay rate
).unwrap();

// The OP_RETURN output was pushed to tx_outs but never fed to
// calculate_weight_vbytes, so:
//   tx.transaction().vsize()  == vbytes_used + ~93
//   tx.fee() / tx.transaction().vsize()  < 1 sat/vbyte  -> rejected by relay
// and weight used in the MAX_STANDARD_TX_WEIGHT check excludes the data output.
```

Confidence note: the literal `==` vs `=` typo cannot occur in Rust (a bare `a == b;` expression statement would warn as unused), so the analog is expressed at the operand level — an item added but never included in the accounting that determines correctness. The primary caller in-scope (`processor/src/networks/bitcoin.rs::make_signable_transaction`) passes `None` for `data`, so end-to-end exposure depends on library consumers exercising the public `data` parameter; the defect itself is unconditional when they do.
