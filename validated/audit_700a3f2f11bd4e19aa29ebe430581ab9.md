### Title
Farmer-controlled `relative_lock_height` for pool "leaving" lock is enforced only client-side, allowing a self-crafted spend to bypass the anti-cheating wait period - (File: chia/pools/pool_wallet.py, chia/pools/pool_puzzles.py)

### Summary
Chia's pooling protocol has a duration parameter directly analogous to the Putty "order duration": `relative_lock_height`, which is supposed to force a farmer who leaves a pool to wait a minimum number of blocks before they can re-claim self-pooling rewards. Like the Putty bug, this minimum is only enforced by the wallet client software, not by the on-chain CLVM puzzle, so a party who controls the value being spent can set it to `0` (or bypass the check entirely) and defeat the protection the mechanism is meant to provide the counterparty (the pool).

### Finding Description
`PoolWallet.MINIMUM_RELATIVE_LOCK_HEIGHT` is set to `5`, and `_verify_pooling_state()`/`_verify_initial_target_state()` reject a `relative_lock_height` below this only inside the Python wallet code path used by `join_pool()`: [1](#0-0) [2](#0-1) [3](#0-2) 

The value is then curried directly into the on-chain `POOL_WAITING_ROOM_MOD` puzzle with no independent floor: [4](#0-3) 

The purpose of this wait, as documented directly in the source, is explicitly anti-cheating protection *for the pool, not the farmer*: [5](#0-4) 

Nothing in `create_waiting_room_inner_puzzle`, `pool_state_to_inner_puzzle`, or the singleton/travel-spend construction path enforces a minimum `relative_lock_height` at the CLVM/consensus level — the only gate is `AssertHeightRelative`/`ASSERT_HEIGHT_RELATIVE` using whatever value was curried in when the singleton was created: [6](#0-5) [7](#0-6) 

Since the launcher/travel spend is just an ordinary spend bundle submitted to the mempool, a farmer (an unprivileged wallet user acting as their own "maker" here) can construct the singleton launch/join spend directly — via `generate_launcher_spend`/`create_travel_spend`/raw CLVM — with `relative_lock_height = 0` (or any value below the client-enforced minimum of 5), completely bypassing `_verify_initial_target_state`'s check, because that check is only invoked from the `PoolWallet.join_pool()` Python method and not from consensus/mempool validation: [8](#0-7) [9](#0-8) 

### Impact Explanation
This is the direct structural analog of "[M-13] Order duration can be set to 0": a value that is supposed to bind one party (the farmer, acting as the party who fills their own "order" by joining/leaving a pool) to protect a counterparty (the pool operator) from being cheated can be set to zero (or below the intended minimum) by the same party who benefits from bypassing it, because the constraint exists only in client-side advisory code, not in the puzzle/consensus logic. A malicious farmer can pledge to a pool with `relative_lock_height = 0`, farm a block reward pledged to the pool, and immediately transition to `SELF_POOLING`/switch pools in the very next block — instantly redirecting the pledged pooling reward to themselves instead of allowing the pool time to observe/claim it, defrauding the pool of rewards it was owed under the pooling protocol's trust model. This falls under "reward redirection" from the validation checklist.

### Likelihood Explanation
Likelihood is moderate: it requires a farmer to deliberately construct a non-standard join/launch spend bundle (bypassing the reference wallet CLI/RPC, which does enforce the minimum), but this requires no privileged access, no colluding third party, and no special timing — any unprivileged wallet user with the ability to craft/sign a spend bundle for their own coin can do it. This is the same nature of "self-inflicted-looking but externally-harmful" bug class as the original Putty finding (a self-serving party sets its own parameter unfavorably to trick a counterparty into being harmed).

### Recommendation
Enforce a hard minimum `relative_lock_height` at the CLVM/consensus level inside the pooling puzzles themselves (`POOL_WAITING_ROOM_MOD`/`POOL_MEMBER_MOD`) rather than only inside `PoolWallet._verify_pooling_state()`, so that no crafted spend bundle can create a pooling singleton with a `relative_lock_height` below the protocol-mandated floor. Alternatively/additionally, have pool servers validate the `relative_lock_height` committed in the on-chain singleton state (not just what farmers self-report) before accepting partials/rewards from a given launcher ID, and refuse to credit farming rewards to singletons whose committed lock height is below the pool's advertised minimum.

### Proof of Concept
1. A farmer selects coins and calls `PoolWallet.generate_launcher_spend()` (or crafts the equivalent CLVM directly) with an `initial_target_state.relative_lock_height = 0`, bypassing `join_pool()`'s call to `PoolWallet._verify_initial_target_state()`. See [9](#0-8)  and the check that is skipped at [3](#0-2) .
2. The resulting singleton's waiting-room inner puzzle is curried with `relative_lock_height = 0` per [4](#0-3) , and this spend is broadcast to the mempool like any ordinary transaction — there is no mempool/consensus rule rejecting it.
3. The farmer farms a block while `FARMING_TO_POOL`, earning a reward paid to the pool's p2-singleton address.
4. The farmer immediately submits a travel spend to `LEAVING_POOL` then `SELF_POOLING`; because `relative_lock_height = 0`, the `ASSERT_HEIGHT_RELATIVE` condition (see test at [7](#0-6)  for the normal, protected case) is trivially satisfied in the very next block, letting the farmer claim self-pooling rewards immediately instead of after the intended waiting period, defeating the pool's anti-cheating protection.

    async def generate_launcher_spend(
        standard_wallet: Wallet,

        genesis_launcher_puz: Program = SINGLETON_LAUNCHER
        launcher_coin: Coin = Coin(launcher_parent.name(), genesis_launcher_puz.get_tree_hash(), amount)

            initial_target_state.relative_lock_height,
            initial_target_state.owner_pubkey,
            launcher_coin.name(),
            genesis_challenge,
            delay_time,
            delay_ph,
        )
        escaping_inner_puzzle_hash = escaping_inner_puzzle.get_tree_hash()

        self_pooling_inner_puzzle: Program = create_pooling_inner_puzzle(

            escaping_inner_puzzle_hash,
            initial_target_state.owner_pubkey,
            launcher_coin.name(),
            genesis_challenge,
            delay_time,
            delay_ph,
        )

        if initial_target_state.state == SELF_POOLING.value:
            puzzle = escaping_inner_puzzle
        elif initial_target_state.state == FARMING_TO_POOL.value:
            puzzle = self_pooling_inner_puzzle
        else:

        full_pooling_puzzle: Program = create_full_puzzle(puzzle, launcher_id=launcher_coin.name())

    async def join_pool(self, target_state: PoolState, fee: uint64, action_scope: WalletActionScope) -> uint64:
        if target_state.state != FARMING_TO_POOL.value:
            raise ValueError(f"join_pool must be called with target_state={FARMING_TO_POOL} (FARMING_TO_POOL)")
        if self.target_state is not None:
            raise ValueError(f"Cannot join a pool while waiting for target state: {self.target_state}")
        if await self.have_unconfirmed_transaction():
            raise ValueError(
                "Cannot join pool due to unconfirmed transaction. If this is stuck, delete the unconfirmed transaction."
            )

        current_state: PoolWalletInfo = await self.get_current_state()

        total_fee = fee
        if current_state.current == target_state:
            self.target_state = None
            msg = f"Asked to change to current state. Target = {target_state}"
            self.log.info(msg)
            raise ValueError(msg)
        elif current_state.current.state in {SELF_POOLING.value, LEAVING_POOL.value}:
            total_fee = fee
        elif current_state.current.state == FARMING_TO_POOL.value:
            total_fee = uint64(fee * 2)

        if self.target_state is not None:
            raise ValueError(
                f"Cannot change to state {target_state} when already having target state: {self.target_state}"
            )
        PoolWallet._verify_initial_target_state(target_state)
        if current_state.current.state == LEAVING_POOL.value:
            history: list[tuple[uint32, CoinSpend]] = await self.get_spend_history()
            last_height: uint32 = history[-1][0]
            if (
                await self.wallet_state_manager.blockchain.get_finished_sync_up_to()
                <= last_height + current_state.current.relative_lock_height
            ):
                raise ValueError(
                    f"Cannot join a pool until height {last_height + current_state.current.relative_lock_height}"
                )

def create_waiting_room_inner_puzzle(
    target_puzzle_hash: bytes32,
    relative_lock_height: uint32,
    owner_pubkey: G1Element,
    launcher_id: bytes32,
    genesis_challenge: bytes32,
    delay_time: uint64,
    delay_ph: bytes32,
) -> Program:
    pool_reward_prefix = bytes32(genesis_challenge[:16] + b"\x00" * 16)
    p2_singleton_puzzle_hash: bytes32 = launcher_id_to_p2_puzzle_hash(launcher_id, delay_time, delay_ph)
    return POOL_WAITING_ROOM_MOD.curry(
        target_puzzle_hash, p2_singleton_puzzle_hash, bytes(owner_pubkey), pool_reward_prefix, relative_lock_height
    )

            launcher_id,
