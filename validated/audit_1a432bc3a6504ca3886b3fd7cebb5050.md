### Title
Amend delta-review optimization in `_resolve_amend_pre_sha` permanently suppresses review of unreviewed pre-amend content - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The commit-review hook's `--amend` fast path (`_resolve_amend_pre_sha`, used at [1](#0-0) ) diffs only pre-amend..post-amend content instead of the full amended commit, based on the unchecked assumption that the pre-amend commit was already reviewed. If the original commit's review was skipped for any of the many legitimate skip paths (rate limit, API unreachable, disabled feature window, credential outage), the dangerous content it introduced is never diffed again and the resulting amended commit is subsequently treated as reviewed, permanently escaping both commit-review and push-sweep.

### Finding Description
The docstring and inline comment for `_resolve_amend_pre_sha` explicitly state the optimization's rationale: "the amend re-reviews the entire commit including code already reviewed on the original commit" [2](#0-1) . However, nothing in `_resolve_amend_pre_sha` or its caller verifies that the pre-amend SHA it resolves via reflog was actually reviewed by this plugin (e.g. via `_load_reviewed_shas`) — the function only validates reflog-subject shape and a cross-repo prefix match [3](#0-2) .

The commit-review handler frequently and legitimately skips reviewing a commit's content: rate limiting via `atomic_check_rate_limit`/`MAX_COMMIT_REVIEWS_PER_HOUR` [4](#0-3) , API unreachability (`skip_reason 24`) [5](#0-4) , missing credentials (`skip_reason 22`) [6](#0-5) , or the disabled-feature window. None of these skip paths add the commit's SHA to the reviewed-shas ledger, since no review ran.

If a commit lands during one of these skip windows and is later amended (e.g. a trivial follow-up fix, common developer/agent workflow), `_resolve_amend_pre_sha` resolves the pre-amend SHA purely from reflog shape and unconditionally switches to delta review: `git diff pre_amend_sha sha` [7](#0-6) . This diff only contains what changed between the two commits — it does NOT include the dangerous content that was already present (and never reviewed) in the pre-amend commit. That dangerous content silently rides along in the final amended commit while the review pipeline only sees the innocuous delta.

Because the review "succeeds" (non-empty delta from the trivial follow-up edit, or the empty-delta skip at `skip_reason 35` if the amend is message-only [8](#0-7) ), the resulting post-amend SHA is presumably recorded into the reviewed-shas ledger (`_append_reviewed_shas`, consumed elsewhere by push-sweep's dedup, per the module's own docstring referencing "the same file push-sweep reads — so a SHA is reviewed at most once across both surfaces" [9](#0-8) ). Push-sweep's contiguous-reviewed-prefix logic (`_compute_push_sweep_base`) then treats the entire post-amend commit — including the never-reviewed pre-amend payload — as already covered [10](#0-9) , so the push-time sweep will not re-surface it either.

Note: I was unable to directly view the exact call site of `_append_reviewed_shas` for the commit-review path (file truncated beyond line 1200), so the precise mechanics of how the amended SHA gets marked "reviewed" in the ledger is inferred from the surrounding comments and the ledger's documented cross-surface dedup purpose rather than directly confirmed in the excerpt read.

### Impact Explanation
An attacker who can influence Claude Code's session to commit dangerous code during a period where commit-review is skipped (rate-limit exhaustion via burst commits, transient `api.anthropic.com` outage, or a disabled-review window) and then have that commit amended with a trivial follow-up change, causes the plugin to never review the smuggled dangerous content — not at commit time, not at amend time (delta-only), and not at push time (ledger dedup). This breaks the stated invariant that dangerous edits/commands remain reviewable and blockable "even across retries, amends, and pushes," allowing dangerous local commands or code changes to be committed and pushed without ever triggering the Stop-hook/commit-review/push-sweep warnings that are meant to force reconsideration — consistent with "Unauthorized local command execution that bypasses Claude Code approval or deny controls" since the security-guidance layer is a review/blocking control, not a hard sandbox.

### Likelihood Explanation
This requires only ordinary, unprivileged git usage (a normal `git commit` followed later by `git commit --amend`) plus one of several commonly-occurring conditions that already legitimately cause commit-review to skip (rate limiting is explicitly designed to trigger under sustained multi-day/heavy sessions per the code comments, and API outages/credential issues are operational realities). No admin privilege, no secret leakage, and no social engineering is needed — an attacker only needs to time an amend to land after an already-unreviewed commit, which is a realistic and reproducible sequence, especially since `MAX_COMMIT_REVIEWS_PER_HOUR` is attacker/session-triggerable by issuing enough commits.

### Recommendation
Before taking the delta-review fast path in `_resolve_amend_pre_sha`'s caller, verify that the resolved pre-amend SHA is present in the reviewed-shas ledger (`_load_reviewed_shas`); if it is not, fall back to full `git show -p` review of the post-amend commit (as already happens for the other three documented guard cases). Additionally, only record a post-amend SHA into the reviewed-shas ledger when the review that ran covered its full content (full-commit review) or when its pre-amend base is independently confirmed reviewed — never mark a delta-reviewed SHA as fully reviewed if the base wasn't previously verified.

### Proof of Concept
Integration test plan for `handle_commit_review_posttooluse` / `_resolve_amend_pre_sha`:
1. Set `MAX_COMMIT_REVIEWS_PER_HOUR=1` (or mock `atomic_check_rate_limit` to return `(False, N)` on the first call) so the first commit's review is skipped with `skip_reason` indicating rate limiting.
2. In a temp git repo, create commit A introducing an obviously dangerous pattern (e.g. `eval(request.args['cmd'])`), and invoke `handle_commit_review_posttooluse` — assert it exits with `skip_reason` for rate limit and does NOT append A's SHA to reviewed-shas.
3. Reset/allow the rate limiter, then run `git commit --amend -m "fix typo"` with a trivial unrelated one-line change (dangerous code untouched), producing commit B.
4. Invoke `handle_commit_review_posttooluse` again for the amend command; assert `_resolve_amend_pre_sha` returns A's SHA and the review pipeline is invoked with `git diff A B` (delta), which does NOT include the `eval(...)` line.
5. Assert the LLM/pattern review of the delta reports no findings for the dangerous line, and that commit B's SHA is recorded as "reviewed" in the ledger despite the dangerous code never being diffed.
6. Simulate `git push` and invoke the push-sweep handler; assert `_compute_push_sweep_base` treats the range up to B as fully reviewed (`B in reviewed`) and the dangerous `eval(...)` content is never flagged by any surface — violating the "reviewable across amends and pushes" invariant.

```python
def _compute_push_sweep_base(prev_upstream, push_range, reviewed):
    """Advance the diff base past the contiguous reviewed prefix.

    Spec: review `git diff B..HEAD` where `B` is the newest commit such that
    `prev_upstream..B` is entirely in `reviewed`. Returns (B, unreviewed_tail).
    `B == None` means the whole range is reviewed (caller should skip).
    `push_range` must be oldest→newest.

    Examples (✓=reviewed, ✗=not):
      [✓1, ✗2, ✓3]  → B=1, tail=[2,3]   (cannot trim suffix; Read is at HEAD)
      [✓1, ✓2, ✓3]  → B=None            (all reviewed → skip)
      [✗1, ✓2, ✗3]  → B=prev_upstream, tail=[1,2,3]
      []            → B=None
    """
    i = 0
    while i < len(push_range) and push_range[i] in reviewed:
        i += 1
    if i == len(push_range):
        return None, []
    base = push_range[i - 1] if i > 0 else prev_upstream
    return base, push_range[i:]
```
