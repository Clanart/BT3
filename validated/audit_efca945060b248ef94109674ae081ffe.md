### Title
Unauthenticated `ReceivedOutput` deserialization accepts fabricated unspendable outputs - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput` represents a spendable Bitcoin output and exposes its offset, output, outpoint, and value as authoritative fields. [1](#0-0)  Its deserializer accepts arbitrary canonical scalar, `TxOut`, and `OutPoint` encodings without verifying that the offset derives the output’s Taproot key or that the claimed outpoint exists. [2](#0-1)  This permits an attacker who can supply serialized `ReceivedOutput` bytes to inject a fabricated spendable-output record.

### Finding Description
The valid construction path is `Scanner::scan_transaction`, which creates a `ReceivedOutput` only after matching an output’s `script_pubkey` against the scanner’s registered script map and derives its outpoint from the containing transaction. [3](#0-2)  `ReceivedOutput::read` bypasses those invariants entirely: it reads an arbitrary scalar offset, decodes any consensus-valid `TxOut`, and decodes any consensus-valid `OutPoint`, then returns the aggregate object unconditionally. [4](#0-3) 

The encoding therefore authenticates none of the semantic relationships that make the object spendable: `output.script_pubkey == p2tr_script_buf(scanned_key + G * offset)`, ownership of the referenced transaction output, or membership of the outpoint in the confirmed Bitcoin UTXO set. This is analogous to modifying a trusted state file: attacker-controlled serialized bytes can replace a scanner-derived output record with a statement that was never observed on chain.

### Impact Explanation
A forged record can report received funds that are not spendable by Serai. `value()` returns the attacker-selected `TxOut` amount, while `offset()` and `outpoint()` return attacker-selected spending metadata. [5](#0-4)  Downstream code receiving a `ReceivedOutput` from this codec has no field-level way to distinguish it from a scanner-produced output because the same type is used for both authenticated scanner results and unauthenticated deserialization results. [6](#0-5) 

Depending on the consumer, this can cause nonexistent deposits to be treated as available inputs, cause transactions to be built around inputs that cannot be spent, or poison persisted output state with entries that did not originate from a confirmed transaction.

### Likelihood Explanation
The attack requires the ability to submit or modify serialized `ReceivedOutput` bytes consumed by a component that calls `ReceivedOutput::read`. The bytes do not need to satisfy any Serai-specific ownership proof: canonical scalar encoding plus ordinary Bitcoin consensus encodings is sufficient. [4](#0-3)  No private key, validator privilege, malformed elliptic-curve encoding, or invalid Bitcoin serialization is required.

### Recommendation
Separate scanner-authenticated outputs from deserialized claims. In particular:

- Add a contextual constructor or verifier such as `ReceivedOutput::read_for_key(reader, key)` that reconstructs `p2tr_script_buf(key + GENERATOR * offset)` and rejects any `TxOut` whose `script_pubkey` does not match.
- Require callers accepting remote serialized outputs to verify the claimed outpoint against a confirmed Bitcoin block or trusted UTXO view before treating it as spendable.
- Rename or isolate the current raw deserializer so persisted trusted state cannot be confused with untrusted network input.
- Serialize an explicit domain tag/version and validate complete consumption of the input buffer to reduce cross-format and trailing-byte ambiguity.
- Persist sufficient scanner metadata, such as the expected base key and containing block identity, so reloaded records can be rechecked against the scanner relation.

### Proof of Concept
The following attacker-controlled payload contains offset zero, a Taproot output controlled by the attacker rather than the expected scanner key, and Bitcoin’s null/nonexistent outpoint. `ReceivedOutput::read` accepts it because it checks only field encodings:

```rust
use bitcoin::{
  consensus::encode::serialize,
  OutPoint, TxOut,
};
use bitcoin_serai::wallet::{p2tr_script_buf, ReceivedOutput};
use k256::ProjectivePoint;

fn forged_received_output() -> ReceivedOutput {
  let attacker_key = ProjectivePoint::GENERATOR;
  let attacker_script = p2tr_script_buf(attacker_key).unwrap();

  let mut bytes = Vec::new();
  bytes.extend([0u8; 32]); // canonical secp256k1 scalar: offset = 0
  bytes.extend(serialize(&TxOut {
    value: bitcoin::Amount::from_sat(1_000_000),
    script_pubkey: attacker_script,
  }));
  bytes.extend(serialize(&OutPoint::null()));

  ReceivedOutput::read(&mut bytes.as_slice()).unwrap()
}
```

No real transaction needs to create the claimed output. The resulting object reports `value() == 1_000_000`, `offset() == 0`, and `outpoint() == OutPoint::null()`, despite the null outpoint not identifying a spendable Bitcoin output.
