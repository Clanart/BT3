Based on my research, I found a strong native analog to the reentrancy-into-accounting-functions class of bug in the ERC20/precompile balance synchronization mechanism, though I was unable to fully verify one detail (whether nested precompile calls share the same underlying `sdk.EventManager`) due to running out of tool iterations. I'll present the finding with that caveat noted.

### Title
Balance-event double-application across recursive/nested precompile calls corrupts EVM stateDB balances - (File: precompiles/common/balance_handler.go, precompiles/common/precompile.go)

### Summary
The `BalanceHandler` mechanism that syncs Cosmos SDK bank-module balance changes into the EVM `StateDB` during precompile execution records a window of "new" events using a simple event-count offset (`prevEventsLen`) captured at the start of each precompile invocation, and replays all not-yet-seen bank events at the end of that invocation. When a precompile call recursively/re-entrantly triggers another precompile call within the same EVM transaction (e.g., a contract calling one precompile, whose native action or callback in turn invokes another precompile, or the same precompile being re-entered), each invocation gets its own `BalanceHandler` (`p.BalanceHandlerFactory.NewBalanceHandler()`), but all invocations record events against the *same* `sdk.Context`'s event manager. Because the offset is a scalar length taken at entry and the events are consumed by slicing `events[prevEventsLen:]` without ever truncating or marking events as consumed, an outer call's `AfterBalanceChange` can end up reprocessing bank events that were already applied to `stateDB` by an inner nested call's own `AfterBalanceChange`, effectively double-applying `AddBalance`/`SubBalance` deltas to the EVM `StateDB`. ### Finding Description
`RunNativeAction`/`runNativeAction` is the shared entry point for every stateful precompile (erc20, werc20, bank, staking, distribution, gov, slashing, ics20). Each invocation creates a fresh `BalanceHandler` instance and calls `BeforeBalanceChange`, which snapshots `len(ctx.EventManager().Events())` as `prevEventsLen`. [4](#0-3) 

After the native `action(ctx)` runs, `AfterBalanceChange` iterates `events[bh.prevEventsLen:]` and, for `EventTypeCoinSpent`/`EventTypeCoinReceived`/`EventTypeFractionalBalanceChange`, applies the corresponding `stateDB.SubBalance`/`AddBalance` calls. [5](#0-4) 

This design implicitly assumes that between `BeforeBalanceChange` and `AfterBalanceChange` of a given precompile call, no *other* precompile invocation observes and independently drains/applies the same event slice. If a nested precompile call occurs inside that window (e.g., a token hook, an ICS20/erc20 conversion path, or a contract calling back into a precompile from within a precompile's native action), the inner call's own `BeforeBalanceChange`/`AfterBalanceChange` pair will consume and apply the bank events generated by the inner action. When control returns to the outer call, the outer `AfterBalanceChange` computes its window from its own (earlier) `prevEventsLen` to the current event count — which still includes the inner call's already-applied events — and re-applies them to `stateDB` a second time.

The repository itself documents this exact failure mode in an integration test, whose comment states: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [6](#0-5) 

This is the direct structural analog of the audited `StrategyBase` bug: just as `sharesToUnderlyingView` can be queried mid-flight with an inconsistent shares/balance pair during a token callback, here `stateDB` balance can be mutated based on a stale/duplicated view of bank events during a nested precompile re-entry, producing a native-chain balance (bank keeper) that diverges from the EVM-visible balance (`stateDB`).

### Impact Explanation
If bank-transfer events are replayed onto `stateDB` more than once for the same underlying bank-module movement, an unprivileged user could cause `stateDB.AddBalance` to credit an EVM account with more native/EVM-token balance than the bank keeper actually holds for it (or `SubBalance` to double-debit an unrelated victim), producing a permanent desync between the Cosmos SDK bank ledger and the EVM `StateDB`. Because `StateDB` balance is what backs subsequent EVM transfers, contract calls with `value`, and gas/value checks, this is a duplication/corruption of spendable value at the EVM layer — matching the "Critical unauthorized minting/duplication ... of spendable user value across native balances, EVM balances" impact category. It also creates AppHash-divergence risk if such state is not deterministically reproduced identically across nodes (it should be deterministic here, but the double-credit itself is the core problem, not non-determinism).

### Likelihood Explanation
Reachability depends on being able to trigger a nested/recursive precompile call within the same top-level precompile invocation's event window — I could not fully confirm within the remaining budget whether this is achievable through production precompiles (e.g., erc20 transfer triggering an ICS20 or ERC20-conversion hook that itself calls into another precompile) versus only through the test-only `debug` precompile (`evmd/tests/testdata/debug/debug.go`, `contracts/solidity/DebugPrecompileCaller.sol`) used in the cited test. The `debug` precompile package lives under `evmd/tests/testdata/`, which is test-only, so if recursive precompile calls can only be produced through that test harness, this would not be reachable by an unprivileged user in production and the finding would be out of scope. Production precompiles like `erc20.transfer`/`transferFrom` (`precompiles/erc20/tx.go`) call `bank.MsgServer.Send` directly rather than invoking another precompile, so a natural recursive path (e.g., an ERC20 precompile transfer to a contract that, within the same call, calls back into another stateful precompile such as staking/distribution/werc20) would need to be confirmed as an actual attacker-reachable flow before treating this as Critical-severity in production.

### Recommendation
- Make the balance-handler event window robust to nested precompile invocations: instead of a global scalar offset into `ctx.EventManager().Events()`, track and consume events per-invocation (e.g., snapshot and truncate/mark the event slice as consumed, or use a monotonically-increasing cursor stored on the shared cache context/`StateDB` rather than per-`BalanceHandler` state) so that no event is ever applied to `stateDB` more than once.
- Add reentrancy protection at the precompile-call level (a call-depth counter, similar to `MaxPrecompileCalls` in `x/vm/statedb/statedb.go`) that specifically prevents overlapping `BeforeBalanceChange`/`AfterBalanceChange` windows, or make the event-consumption index shared/global across nested `BalanceHandler` instances within one EVM transaction.
- Add/extend integration tests to assert stateDB-vs-bank-keeper balance equality after any nested/recursive precompile call sequence (the existing `balance_handler_test.go` should be turned into a strict regression assertion, not just an event-count check).

### Proof of Concept
I was not able to fully construct or verify an end-to-end production PoC within the available tool budget. The existing repository test `TestRecursivePrecompileCallsWithDebugPrecompile` in `evmd/tests/integration/balance_handler/balance_handler_test.go` (lines 43–107) already exercises the exact recursive-call/`prevEventsLen`-desync scenario using the `debug` precompile and `DebugPrecompileCaller.sol`'s `callback` function, and its own comments describe the resulting stateDB/bank-keeper desync. [7](#0-6) 

A concrete PoC would need to identify a production (non-test-only) precompile call path that recursively invokes a second stateful precompile within the first one's native action (candidates: erc20/ics20 conversion hooks, werc20 deposit interacting with erc20 transfer logic) and then compare `bankKeeper.GetBalance` against `stateDB`-derived `eth_getBalance`/`balanceOf` results before and after the nested call to confirm double-crediting. This verification step remains outstanding.

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	initialGas := ctx.GasMeter().GasConsumed()

	defer HandleGasError(ctx, contract, initialGas, &err)()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)

	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	var balanceHandler *BalanceHandler
	if p.BalanceHandlerFactory != nil {
		balanceHandler = p.BalanceHandlerFactory.NewBalanceHandler()
	}

	if balanceHandler != nil {
		balanceHandler.BeforeBalanceChange(ctx)
	}

	bz, err = action(ctx)
	if err != nil {
		return bz, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	if balanceHandler != nil {
		if err := balanceHandler.AfterBalanceChange(ctx, stateDB); err != nil {
			return nil, err
		}
	}

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
