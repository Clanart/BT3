Found a real analog in the Tron `IntentGatewayV2.placeOrder` fee-swap path — the same class of bug as the WatchPug report (swap-based unused-token refund omitted), but here it is unused **native ETH** that is stranded rather than ERC20.

### Title
Unswapped native token change from `swapETHForExactTokens` fee swap is stranded in `IntentGatewayV2.placeOrder` (Tron variant) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron `IntentGatewayV2.placeOrder`, when a user pays `order.fees` in native token, the contract calls `swapETHForExactTokens{value: msgValue}(...)` sending the *entire remaining* `msgValue`, not just the amount needed for the fee swap. Unlike the EVM-mainline `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol`), which tracks the returned `amounts[0]` (`spent`), decrements `msgValue -= amounts[0]`, and then explicitly refunds the leftover `msgValue` to `msg.sender`, the Tron variant **discards the return value of `swapETHForExactTokens` entirely** and has **no final "refund unspent native tokens" step** after the fee block.

### Finding Description
Compare the two versions:

EVM mainline (`evm/src/apps/IntentGatewayV2.sol:345-368`):
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```

Tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol:465-482,484-497`):
```solidity
if (msgValue > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
        order.fees, path, address(this), block.timestamp
    );      // return value discarded
} else {
    IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
}

_orders[commitment][TRANSACTION_FEES] = order.fees;
}

emit OrderPlaced({...});
}   // function ends -- no post-fee "refund unspent native tokens" block
```

The underlying wrapper (`evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol:143-149`, and the equivalent V4 wrapper) does refund unspent ETH — but it sends that refund back to `msg.sender` of the *swap call*, which is the `IntentGatewayV2` contract itself, not the original user. On the EVM side, this refund lands on the gateway's balance and is then explicitly forwarded to the user via the trailing `msg.sender.call{value: msgValue}("")`. The Tron code never performs this forwarding step, so any ETH refunded by the router/wrapper back into the gateway remains permanently trapped in the `IntentGatewayV2` contract, unassigned to any escrow entry, order, or beneficiary — it is not tracked in `_orders[commitment][...]` and there is no sweep/withdraw path that would let a user reclaim it. This is structurally identical to the WatchPug finding: a swap operation leaves unused underlying value behind, and the calling contract has one refund branch (implicit success path) but omits the symmetric "return the leftover" branch.

### Impact Explanation
Any user calling `placeOrder` on the Tron gateway with `order.fees > 0` and sending `msg.value` greater than what the fee swap actually consumes (which is the normal case, since callers must overestimate `msg.value` to cover slippage on `swapETHForExactTokens`) permanently loses the difference — it becomes stuck protocol-owned ETH with no accounted claim, matching the "fund loss/lock" impact category in the bounty gate. This is triggerable by any unprivileged user through the public `placeOrder` entrypoint with normal usage patterns, not a malicious-peer or relayer scenario.

### Likelihood Explanation
High — this occurs any time a user's `msg.value` doesn't exactly equal the fee-swap's actual ETH cost, which will happen essentially every time because callers cannot predict the exact `amountIn` a Uniswap V2 exact-output swap will need at execution time (price can move between quote and execution) and must send a buffer.

### Recommendation
Mirror the EVM mainline logic in the Tron contract: capture the `uint256[] memory amounts` return value from `swapETHForExactTokens`, decrement `msgValue -= amounts[0]`, and add the same trailing refund block (`if (msgValue > 0) { (bool sent,) = msg.sender.call{value: msgValue}(""); ...}`) after the fee-escrow block in `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder{value: X}(order, graffiti)` on Tron, where `order.fees > 0` and ERC20 `order.inputs` cover the token side, so all of `X` is `msgValue` destined for the fee swap.
2. Set `X` deliberately larger than the true cost of swapping to `order.fees` fee-tokens (e.g., 5x the expected cost, matching the pattern already tested for the EVM contract in `evm/tests/foundry/IntentGatewayV2Test.sol:3461` `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`).
3. `swapETHForExactTokens{value: X}` executes, spends only `spent < X`, and refunds `X - spent` ETH back to `address(this)` (the gateway) — confirmed by the wrapper logic at `evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol:143-149`.
4. `placeOrder` returns; the user's transaction succeeds, `OrderPlaced` is emitted, but `(X - spent)` ETH sits in the `IntentGatewayV2` contract's balance with no corresponding entry in `_orders[commitment]` and no code path in `cancelOrder`/`withdraw` that returns it.
5. Repeat testing analogous to `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` but against the Tron contract and assert the user's ETH balance is *not* restored and the gateway's balance permanently retains the difference. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    /// @notice placeOrder with fee swap refunds unused ETH after swapETHForExactTokens.
    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
        assertTrue(ethSpent > 0, "User should have spent some ETH on the fee swap");
    }
