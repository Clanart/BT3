### Title
Unvalidated `PointerType` in `MsgRegisterPointer` causes an application panic in `RegisterPointer` - (File: `x/evm/keeper/msg_server.go`)

### Summary
`MsgRegisterPointer.ValidateBasic` only checks that the sender bech32 address and the `ErcAddress` hex address are well-formed; it never validates that `PointerType` is one of the known enum values. [1](#0-0)  Because `PointerType` is a plain protobuf `int32` enum, any integer value can be placed in the field by a client and will pass `ValidateBasic` unchanged. [2](#0-1)  When the message reaches `msgServer.RegisterPointer`, the handler `switch`es on `msg.PointerType` twice, and both switches fall through to `default: panic("unknown pointer type")` for any value outside `{ERC20, ERC721, ERC1155}`. [3](#0-2) [4](#0-3) 

This is the same bug class as the external report: an externally supplied, unvalidated "asset/pointer type" enum reaches privileged bookkeeping logic that assumes only well-known values are possible, and the un-handled/invalid-value case causes the code to fail hard instead of returning a graceful error.

### Finding Description
`RegisterPointer` is a standard `Msg` handler reachable by any unprivileged account via `MsgRegisterPointer` (Cosmos tx or EVM-mapped precompile flow that constructs this message). The handler trusts `msg.PointerType` to be one of the three declared enum values (`PointerType_ERC20`, `PointerType_ERC721`, `PointerType_ERC1155`) and uses `panic("unknown pointer type")` as the `default` branch of two separate `switch` statements instead of returning an error. [5](#0-4) 

Because `ValidateBasic` performs no bounds/enum check on `PointerType`, a transaction with, e.g., `PointerType: 99` will pass basic validation and antehandler checks, and only fail inside the message server via an explicit Go `panic`. [1](#0-0) 

### Impact Explanation
A `panic()` triggered from inside a message handler during transaction execution is the exact same failure mode described in the external report: a value that is supposed to be constrained to a small, known enum set is left unvalidated at the point of entry, and downstream code has no graceful handling path for out-of-range values, degrading to a hard failure instead of a rejected transaction. Depending on where in the SDK's panic-recovery pipeline this occurs (`runTx`/OCC parallel execution wrappers in `sei-cosmos/baseapp`), an uncaught or improperly-recovered panic during block execution can produce non-deterministic behavior between validators executing the same block, which is a chain-halt-class issue rather than a simple rejected transaction. I was not able to fully verify from the available index whether every code path that invokes `RegisterPointer` (including the OCC parallel-execution scheduler in `sei-cosmos/baseapp`) wraps this specific call with a recovery/error-conversion layer that safely downgrades the panic to a per-tx error without impacting block processing determinism.

### Likelihood Explanation
Very low barrier: any account can submit a plain `MsgRegisterPointer` transaction with an arbitrary `PointerType` integer value since there is no server-side or client-side enum-range enforcement in `ValidateBasic`. [1](#0-0) 

### Recommendation
Add an explicit range/enum check for `PointerType` in `MsgRegisterPointer.ValidateBasic` (reject any value not in `{ERC20, ERC721, ERC1155}`), and replace the `panic("unknown pointer type")` branches in `msgServer.RegisterPointer` with a normal `error` return (e.g., `sdkerrors.ErrInvalidRequest`) so that invalid input degrapes to a rejected transaction under all execution paths rather than relying on panic recovery. [3](#0-2) 

### Proof of Concept
1. Construct `MsgRegisterPointer{Sender: <valid bech32>, ErcAddress: <valid hex address>, PointerType: 99}` (any value outside 0–2).
2. Submit the transaction; `ValidateBasic` passes because it only checks `Sender` and `ErcAddress`. [1](#0-0) 
3. During execution, `msgServer.RegisterPointer` reaches the `switch msg.PointerType` statement, matches no case, and executes `panic("unknown pointer type")`. [6](#0-5)

func (msg *MsgRegisterPointer) ValidateBasic() error {
	_, err := sdk.AccAddressFromBech32(msg.Sender)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid sender address (%s)", err)
	}

	if !common.IsHexAddress(msg.ErcAddress) {
		return sdkerrors.ErrInvalidAddress
	}

	return nil
}

func (server msgServer) RegisterPointer(goCtx context.Context, msg *types.MsgRegisterPointer) (*types.MsgRegisterPointerResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)
	if server.GetRegisterPointerDisabled(ctx) {
		return nil, fmt.Errorf("registering CW->ERC pointers has been disabled")
	}
	var existingPointer sdk.AccAddress
	var existingVersion uint16
	var currentVersion uint16
	var exists bool
	switch msg.PointerType {
	case types.PointerType_ERC20:
		currentVersion = erc20.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW20ERC20Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	case types.PointerType_ERC721:
		currentVersion = erc721.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW721ERC721Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	case types.PointerType_ERC1155:
		currentVersion = erc1155.CurrentVersion
		existingPointer, existingVersion, exists = server.GetCW1155ERC1155Pointer(ctx, common.HexToAddress(msg.ErcAddress))
	default:
		panic("unknown pointer type")
	}
	if exists && existingVersion >= currentVersion {
		return nil, fmt.Errorf("pointer %s already registered at version %d", existingPointer.String(), existingVersion)
	}
	payload := map[string]interface{}{}
	switch msg.PointerType {
	case types.PointerType_ERC20:
		payload["erc20_address"] = msg.ErcAddress
	case types.PointerType_ERC721:
		payload["erc721_address"] = msg.ErcAddress
	case types.PointerType_ERC1155:
		payload["erc1155_address"] = msg.ErcAddress
	default:
		panic("unknown pointer type")
	}
