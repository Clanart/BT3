### Title
Unbounded, Gas-Unmetered Iteration Over EIP-7702 Authorization Lists in the EVM Ante Handlers - (File: `x/evm/ante/preprocess.go`, `app/ante/evm_checktx.go`, `app/ante/evm_delivertx.go`)

### Summary
Sei's EVM ante-handler pipeline pre-associates every EIP-7702 `SetCodeAuthorization` entry in a transaction with its true Sei address before the EVM applies delegation. This loop runs under an infinite/unmetered gas meter and performs ECDSA recovery plus KV-store reads/writes per authorization item. This mirrors the reported bug class (`runExecutionHooks`/`runValidationHooks` iterating an attacker/user-controlled collection with unbounded per-item cost): a caller can submit a single `SetCodeTx` containing many authorization entries, and the ante-handler cost of processing them is not properly capped by the fee the sender pays, because the loop executes before/outside the tx's own gas metering.

### Finding Description
`x/evm/ante/preprocess.go`'s `associateAuthorizationAuthorities` iterates `ethTx.SetCodeAuthorizations()` and, for each entry, calls `helpers.AuthorityToPreAssociate` (ECDSA signature recovery via `RecoverAddressesFromAuthorization`, nonce/chain-id/code checks, and an address-mapping lookup) and then `associateHelper.AssociateAddresses` inside a fresh `ctx.CacheContext()`: [1](#0-0) 

The same pattern exists in the legacy ABCI ante path used for both CheckTx and DeliverTx, `AssociateAuthorizationAuthorities`, which is invoked after the ante context has already been switched to an infinite gas meter: [2](#0-1) [3](#0-2) [4](#0-3) 

`RecoverAddressesFromAuthorization` does a `Keccak256` hash plus ECDSA public-key recovery for every authorization, and `AuthorityToPreAssociate` performs additional state reads (`GetCode`, `GetNonce`, `GetEVMAddress`) per entry: [5](#0-4) 

Unlike go-ethereum, which only needs to recover the authority address once per authorization for delegation, Sei's fork adds an extra address-association step with its own KV-store writes (`SetAddressMapping` touches two store keys and can create an account) per authorization, executed while the ante context uses `sdk.NewInfiniteGasMeterWithMultiplier`, so the true per-item cost is not billed to the sender in the same way normal EVM opcodes are metered: [6](#0-5) 

While the number of authorizations per transaction is nominally bounded by `intrGas <= etx.Gas() <= block.MaxGas` in `EvmStatelessChecks` (via `core.IntrinsicGas(..., etx.SetCodeAuthorizations(), ...)`), this check only exists to bound the standard EVM-side intrinsic gas cost of the tx; it does not account for the additional Sei-specific ECDSA-recovery + KV-store work performed by `AssociateAuthorizationAuthorities`/`associateAuthorizationAuthorities`, which runs on an infinite gas meter outside of `etx.Gas()` accounting: [7](#0-6) 

A search of the codebase did not surface any explicit cap on `AuthList` length independent of the intrinsic-gas-derived bound, confirming the only limiting factor is the coarse block-gas-derived bound, not a dedicated size limit as recommended by the analogous upstream report.

### Impact Explanation
Every submitted `SetCodeTx` runs this authorization loop twice per lifecycle (once in CheckTx via mempool admission, once again in DeliverTx), and the loop's per-item cost (signature recovery + several store reads/writes) is heavier than a simple map/set lookup. Because the loop executes under an infinite gas meter rather than being billed against `etx.Gas()`, an attacker can craft transactions that maximize the authorization count relative to gas paid (each authorization's *EVM-side* intrinsic cost is cheap under EIP-7702, ~a few thousand gas, while the Sei-side association work is comparatively expensive: ECDSA recovery + address bookkeeping + potential account creation). Submitting many such transactions in a block could inflate ante-handler CPU and I/O time disproportionately to the gas actually charged, risking increased block-processing latency for validators (potential contribution toward block delay) and increased mempool/CheckTx load, since the same unmetered work runs again on every CheckTx pass. This is a resource-exhaustion/DoS-style risk analogous to the reported hook-iteration issue, though bounded in practice by the block gas limit acting as an indirect (but not purpose-built) ceiling on authorization count per transaction.

### Likelihood Explanation
Likelihood is Medium: any unprivileged EVM sender can submit an EIP-7702 `SetCodeTx` with many authorization entries (each authorization's own EVM-side gas cost is small), and the ante-handler pre-association loop is reachable on both the CheckTx and DeliverTx paths without any special privilege. However, actual disruption requires crafting many such transactions and depends on how many authorizations fit within the block gas limit and mempool per-tx gas caps, which naturally throttles the attack somewhat and keeps it from being a trivial single-transaction crash.

### Recommendation
- Explicitly cap the number of EIP-7702 authorizations processed per transaction, independent of intrinsic-gas-derived bounds, so `associateAuthorizationAuthorities`/`AssociateAuthorizationAuthorities` cannot process an unbounded (or disproportionately large relative to fee paid) set of entries.
- Meter the pre-association loop's ECDSA recovery and KV-store operations against a real (non-infinite) gas meter tied to the transaction's own gas limit so the sender pays for the actual Sei-specific work performed, not just the go-ethereum intrinsic-gas approximation.
- Consider skipping the CheckTx-side pre-association pass entirely (or making it a lighter-weight check) since it is documented as best-effort/mempool-consistency-only and not required for correctness, to avoid doubling the unmetered cost per transaction.

### Proof of Concept
Not independently reproduced in this review; the analysis is based on static code inspection of the ante-handler authorization loop and its interaction with intrinsic gas accounting. A concrete PoC would need to: (1) craft an EIP-7702 `SetCodeTx` with the maximum number of authorization entries permitted under the block gas limit (each authorization signed for a fresh, previously-unassociated authority key), (2) submit many such transactions concurrently to both `CheckTx` and `DeliverTx`, and (3) measure ante-handler wall-clock time versus gas charged to confirm the cost asymmetry described above. This was not executed as part of this review; the finding is derived from code-path analysis rather than an empirical benchmark, so the actual achievable block-time impact is unverified.

func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}

func RecoverAddressesFromAuthorization(auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, error) {
	var buf bytes.Buffer
	buf.WriteByte(eip7702MagicPrefix)
	if err := rlp.Encode(&buf, []any{auth.ChainID, auth.Address, auth.Nonce}); err != nil {
		return common.Address{}, sdk.AccAddress{}, nil, err
	}
	sigHash := crypto.Keccak256Hash(buf.Bytes())
	v := new(big.Int).SetUint64(uint64(auth.V) + 27)
	return GetAddresses(v, auth.R.ToBig(), auth.S.ToBig(), sigHash)
}

// AuthorizationStateReader exposes the EVM state lookups needed to decide whether an
// EIP-7702 authorization would be applied. Both the standard and giga EVM keepers satisfy it.
type AuthorizationStateReader interface {
	ChainID(ctx sdk.Context) *big.Int
	GetCode(ctx sdk.Context, addr common.Address) []byte
	GetNonce(ctx sdk.Context, addr common.Address) uint64
	GetEVMAddress(ctx sdk.Context, seiAddr sdk.AccAddress) (common.Address, bool)
}

// AuthorityToPreAssociate returns the authority of an EIP-7702 authorization that should be
// associated with its true (pubkey-derived) Sei address before execution, or ok=false.
//
// It mirrors go-ethereum's StateTransition.validateAuthorization (chain id, nonce overflow,
// authority code, and account-nonce checks) so that pre-association happens only for
// authorizations the EVM will actually apply, and additionally skips authorities that are
// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := k.GetKVStore(ctx)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}
