### Title
Data Layer SSRF via unvalidated mirror URLs in `http_download` - (File: `chia/data_layer/download_data.py`)

### Summary
Chia's Data Layer allows any store owner to publish "mirror" server URLs on-chain for their store (via the DL wallet's mirror-coin mechanism, exposed through `add_mirror`/`get_mirrors` in `chia/data_layer/data_layer_rpc_api.py` and `chia/data_layer/data_layer_wallet.py`). Any other node that subscribes to that store will later use these attacker-supplied URLs to fetch delta/full-tree files via `http_download` in `chia/data_layer/download_data.py`, which passes the URL directly to `aiohttp.ClientSession.get` with no validation that it does not point to an internal/loopback/link-local address. This is the same bug class as CVE-2025-62615 (unfiltered outbound URL fetch causing SSRF), except the analogous "attacker-controlled URL" here is a mirror URL, and the reachable actor is any peer/client subscribing to a malicious store.

### Finding Description
`http_download` builds the request target directly from `server_info.url`: [1](#0-0) 

`server_info.url` originates from `ServerInfo` records tied to a store's mirror list. Mirror URLs are supplied by a store owner (an unprivileged Data Layer client controlling their own singleton/store) through the mirror-coin mechanism defined in `chia/data_layer/data_layer_wallet.py` and surfaced through the RPC layer (`chia/data_layer/data_layer_rpc_api.py`, `chia/cmds/data.py`). There is no scheme/host allow-listing, no rejection of loopback (`127.0.0.1`), link-local metadata addresses (`169.254.169.254`), private RFC1918 ranges, or `file://`/other unexpected schemes before the URL is handed to `aiohttp.ClientSession.get`.

Once another user's node subscribes to the malicious store (a normal, low-privilege Data Layer operation — subscribing to any store id is intentionally permissionless), that node's Data Layer service will periodically attempt to download delta/full files from every mirror URL registered for the store, causing the victim node to issue outbound HTTP requests to an attacker-chosen destination, including internal-only services reachable from the node's host/network (e.g., cloud metadata endpoints, other local RPC ports, internal admin panels).

### Impact Explanation
This satisfies the "SSRF-class" impact bar: a Data Layer client (unprivileged, since anyone can subscribe to any public store id) can be induced to make arbitrary outbound requests to attacker-chosen destinations, potentially reaching internal-only network services, cloud metadata endpoints (leading to credential theft in cloud deployments), or the node's own/other internal RPC services if firewalling is absent. This is a confidentiality/integrity issue analogous to the AutoGPT SSRF report, reachable by any subscribing peer without prior authorization.

### Likelihood Explanation
Likelihood is limited by the requirement that the victim explicitly subscribes to the malicious store id (a deliberate but unprivileged and common action for Data Layer users who want to mirror/sync third-party datasets). No signing, payment, or special access is required to publish a malicious mirror URL for one's own store, and no additional user interaction beyond a normal subscribe is needed to trigger the fetch.

### Recommendation
- Validate mirror/server URLs before use in `http_download`: enforce `https://` (or an explicit allow-listed scheme), resolve and reject loopback, link-local, and private-network addresses (defense against DNS rebinding as well), and consider disabling redirects to unvalidated hosts.
- Apply the same validation both when a mirror URL is registered (`add_mirror`) and immediately before each outbound request in `http_download`, since DNS can change between registration and download time.
- Document and optionally make this validation configurable (e.g., a `data_layer.allow_local_mirrors` flag) for legitimate testing/dev use cases.

### Proof of Concept
1. Attacker creates a Data Layer store and calls `add_mirror` with `urls=["http://169.254.169.254/latest/meta-data/"]` (or any internal address reachable from a target node, e.g. `http://127.0.0.1:8555/...`).
2. Victim runs `chia data subscribe <store_id>` (or the corresponding RPC) to mirror the attacker's public store — a normal, permissionless action.
3. Victim's Data Layer service resolves mirrors for the store and calls `http_download` in `chia/data_layer/download_data.py`, issuing `session.get("http://169.254.169.254/latest/meta-data/" + "/" + filename, ...)` from the victim's own network context.
4. The victim node performs the SSRF request; depending on deployment, the attacker can infer response behavior (timing/errors) or, in cloud contexts, potentially retrieve sensitive metadata if error handling leaks content.

Note: I could not directly view the full `add_mirror`/mirror-URL validation code path (only match counts were available for `data_layer_wallet.py`, `data_layer_rpc_api.py`, and `cmds/data.py`), so I cannot rule out that some URL filtering exists elsewhere in those files that I was unable to inspect. If a Devin session is started, the full contents of `chia/data_layer/data_layer_wallet.py::Mirror`/`add_mirror` and `chia/data_layer/data_layer_rpc_api.py` should be reviewed to confirm whether any existing validation partially mitigates this.
