### Title
`_calExpireForfeit` in `mWOMSVBaseRewarder` never applies the cooldown-based reward reduction, causing zero forfeiture always - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount = _amount - rewardableAmount` is always `0`, regardless of the account's cooldown state. This breaks the intended "forfeit reward when in partial unlock/cooldown" mechanism that is correctly implemented in the sibling contract `vlMGPBaseRewarder`, which computes `rewardableAmount` via `vlMGP.getRewardablePercentWAD(_account)`.

### Finding Description
`mWOMSVBaseRewarder` is paired with the `mWomSV` locker, whose `getRewardablePercentWAD(address _user)` function [1](#0-0)  computes the percentage of a user's `mWomSV` balance that is fully locked vs. still in cooldown, explicitly intended to reduce the rewardable share for users partially in cooldown.

However, `mWOMSVBaseRewarder._calExpireForfeit` never calls this function at all: [2](#0-1) 
It sets `rewardableAmount = _amount` on line 386, so the check `rewardableAmount > _amount` on line 387 can never trigger, and `forfeitAmount = _amount - rewardableAmount` on line 390 is always `0`.

Compare to the correct implementation in `vlMGPBaseRewarder._calExpireForfeit`, which multiplies `_amount` by `vlMGP.getRewardablePercentWAD(_account)` before computing the forfeit: [3](#0-2) 

The public view `calExpireForfeit(_account, _rewardToken)` [4](#0-3)  calls the same broken `_calExpireForfeit`, so it also always returns `0` — it does not "resolve to a nonzero value off-chain" as the question's threat premise suggests. Both the view function and the actual `getReward` -> `_sendReward` -> `_calExpireForfeit` path [5](#0-4)  consistently return `0`. There is no code path where `calExpireForfeit` returns a nonzero amount while `_sendReward` forfeits `0` — the bug affects both identically because they call the identical internal function with the same inputs.

The `ILocker` interface that `mWOMSV` is typed as in the rewarder only declares `lockFor` [6](#0-5) , so even if someone tried to fix this by calling `mWOMSV.getRewardablePercentWAD(_account)`, the interface would need updating — but that's a separate remediation detail, not part of this exploit analysis.

Regardless, the net effect is that **any** account with rewards accrued while partially in cooldown collects 100% of accrued rewards via `getReward`/`getRewards`, with the "forfeited" share (which should be redistributed to fully-locked backers via `_queueNewRewardsWithoutTransfer`) never actually being forfeited.

### Impact Explanation
This is a real fund-flow defect, but the described attack framing (observe nonzero via view function then front-run) does not hold, since the view function and the real path use the identical broken logic and both always return `0`. The actual impact is systemic and passive rather than requiring any attacker action: every account with mWomSV in cooldown, when calling `getReward`/`getRewards` (via MasterMagpie), receives the full accrued reward with no forfeiture, and the pool's other backing lockers never receive the redistributed forfeited yield they are entitled to under the documented mechanism. This constitutes a "theft or permanent freezing of unclaimed yield" class impact — value that should flow to backing (fully-locked) stakers is instead retained by cooling-down accounts, systemically across the whole `mWOMSVBaseRewarder`/`mWomSV` pool, not just for a single attacker.

### Likelihood Explanation
This requires no special capital or attacker sophistication — it is a passive, unconditional bug in `_calExpireForfeit` and triggers on the normal `getReward` call path any time an account has any `mWomSV` in cooldown while rewards are owed. It is 100% reliably reproducible (deterministic, not probabilistic) and repeatable by every user of the pool, every time.

### Recommendation
Fix `mWOMSVBaseRewarder._calExpireForfeit` to compute `rewardableAmount` using the equivalent of `getRewardablePercentWAD` on the `mWomSV` locker (mirroring `vlMGPBaseRewarder`), e.g., add `getRewardablePercentWAD` to `ILocker` (or a dedicated interface) and use it: `rewardableAmount = _amount * mWOMSV.getRewardablePercentWAD(_account) / 1e18;`.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `MasterMagpie`, and `mWOMSVBaseRewarder`; register a reward token and fund rewards via `queueNewRewards`.
2. Have account A lock the full amount (no cooldown) and account B lock then call `startUnlock` for 50% of its balance, leaving 50% in cooldown.
3. Advance the reward accrual (queue more rewards), then call `getReward` (via MasterMagpie) for account B while still in the cooldown window (`block.timestamp < endTime`).
4. Assert: `calExpireForfeit(B, rewardToken)` returns `0` before the call (confirming the view is also broken, not just the send path).
5. Assert: `ForfeitRewardAdded` event is never emitted, and B receives 100% of `userRewards[rewardToken][B]` via `RewardPaid`, whereas the expected forfeiture computed from `getRewardablePercentWAD(B)` (≈50%, since half is in active cooldown) predicts roughly half of B's reward should have been redirected to `_queueNewRewardsWithoutTransfer`.
6. Repeat across a population of partially-cooling accounts and sum `ForfeitRewardAdded` amounts vs. theoretical expected forfeiture (`sum(userReward_i * (1 - getRewardablePercentWAD_i)/1e18)`) — assert actual sum is `0` while expected sum is `> 0`, demonstrating systemic zero forfeiture.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
