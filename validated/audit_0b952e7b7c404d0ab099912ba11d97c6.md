### Title
ThresholdKeys deserialization accepts attacker-chosen verification shares without binding them to the secret share, silently installing an attacker-known group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, an interpolation method, a `secret_share`, and a `HashMap` of `verification_shares` entirely from the input bytes, then calls `ThresholdKeys::new`. `new` validates the share count, participant bounds, and interpolation applicability, but never checks that `secret_share * G == verification_shares[i]` nor that the `verification_shares` are mutually consistent with any DKG transcript. The `group_key` is then computed on the spot as the interpolation-weighted sum of `verification_shares[1..=t]` — fully derived from attacker-controlled bytes. An untrusted serialized key blob therefore silently activates an attacker-chosen key set, analogous to a GitLab project export silently activating pipeline schedules on import.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` (lines 574–632) reconstructs keys purely from serialized input: `t`, `n`, `i` at lines 591–602, interpolation at 604–616, `secret_share` at 618, and `verification_shares` for participants `1..=n` at 620–623. `ThresholdKeys::new` (lines 349–391) performs only structural checks — `verification_shares.len() == n` (355), participant indices `<= n` (361–365), and Constant-vs-Lagrange applicability (367–374) — then derives `group_key` at lines 376–378 by summing `verification_shares[i] * interpolation_factor(i, 1..=t)`. There is no cryptographic binding between `secret_share` and `verification_shares`, and no external commitment (e.g., to a DKG transcript hash) anchoring the shares.

With `Interpolation::Constant` (permitted whenever `t == n`, line 369), interpolation factors are all `1`, so `group_key = Σ verification_shares[i]` — a completely attacker-selected point with a known discrete logarithm.

### Impact Explanation
A party able to feed crafted bytes to `ThresholdKeys::read` (a listed reachable surface) causes the importer to adopt a group key whose secret the attacker fully knows: the attacker sets every `verification_shares[i] = G * s_i` for chosen `s_i`, and sets the victim's `secret_share = s_i` so that `view()` produces an interpolated share that passes `verification_share` checks during FROST signing (`crypto/dkg/src/lib.rs:500-521`). The victim then produces valid signature shares for a group key the attacker controls. Any funds the bitcoin-serai `Scanner` attributes to that group key are spendable by the attacker, and every signature authorizes messages under attacker-known key material — concrete signing under an unintended, attacker-recoverable key.

### Likelihood Explanation
Exploitation requires the victim to deserialize `ThresholdKeys` from an untrusted source. Serai serializes `ThresholdKeys` for persistence and for handoff through `dkg-promote`/`dkg-recovery` flows (`ThresholdKeys::write`/`serialize` at lines 535–571), so any path where serialized key material transits or is replaced by an untrusted party (backup restore, migration, coordinator-supplied promotion artifacts) exposes the importer. No collusion, leaked key, or malicious validator is needed — only crafted input bytes. Impact is bounded to the importing party, matching Medium severity like the GitLab original.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `read`), verify that `C::generator() * secret_share == verification_shares[&params.i()]` after interpolation consistency checks, rejecting blobs where the secret share does not match the purported verification share. Additionally, consider committing the verification-shares set (and `t`/`n`) to the group key derivation so tampering with any share changes the resulting key detectably, or transcript-bind serialized keys to the DKG session that produced them.

### Proof of Concept
For a ciphersuite `C` with `t == n` (Constant interpolation valid):

1. Attacker picks scalars `s_1 … s_n`, computes `V_i = C::generator() * s_i`. The group secret `Σ s_i` is known to the attacker.
2. Attacker crafts a serialized `ThresholdKeys` blob per the `write` format (lines 538–561): `C::ID`, `t = n`, `n`, `i`, interpolation byte `0`, `n` constant coefficients, `secret_share = s_i` for victim index `i`, then `V_1 … V_n`.
3. Victim calls `ThresholdKeys::<C>::read(&mut blob)` → `new` accepts: count/bounds checks pass, Constant interpolation allowed since `t == n` (line 369), and `group_key = Σ V_i` (lines 376–378) — attacker-known.
4. Victim calls `view(included)`; `secret_share` interpolates to `s_i` (line 495–498) which verifies against `V_i`, so FROST signing proceeds normally and produces valid signatures under the attacker's key.
5. Attacker, knowing `Σ s_i`, independently signs/spends anything the victim's `group_key` receives.

Root cause: absent share-to-secret binding in `ThresholdKeys::new`/`read` at `crypto/dkg/src/lib.rs:349-391` and `crypto/dkg/src/lib.rs:574-632`.
