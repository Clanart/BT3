### Title
`_cancelFromDest` lacks a filled-state guard, allowing order owners to double-claim escrow after a solver has already filled the order - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
The BPool bug pattern is "an operation succeeds despite a state that should have blocked it, because a critical guard is missing." The local analog is in the cross-chain Intent Gateway settlement path: `fillOrder` correctly guards against re-filling an already-filled order with `if (_filled[commitment] != address(0)) revert Filled();`, but the matching cancellation path on the destination chain, `_cancelFromDest`, has no equivalent check. This lets an order's own user cancel (and trigger a refund dispatch) an order that a solver has *already filled*, racing the solver's legitimate settlement message back to the source chain.

### Finding Description
`fillOrder` in `evm/src/apps/IntentGatewayV2.sol` enforces the filled-state invariant before allowing a fill: [1](#0-0) 

But `_cancelFromDest` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, which is reachable from the public `cancelOrder()` entrypoint, only checks the deadline and ownership — never `_filled[commitment]` — before marking the order filled locally and dispatching a `RefundEscrow` message back to the source chain: [2](#0-1) 

Because `order.deadline >= _blockNumber()` only gates *who* may call it (must be `order.user`), not *whether it was already filled*, the order's own user can call `cancelOrder()` on the destination chain **after a solver has already delivered the output tokens** via `_fillCrossChain` (which sets `_filled[commitment] = msg.sender` for the solver and dispatches `RedeemEscrow`): [3](#0-2) 

This produces two independent, unordered ISMP POST messages targeting the same source-chain commitment: the solver's `RedeemEscrow` and the user's `RefundEscrow`. Whichever arrives and is processed first by `onAccept` → `_withdraw` succeeds and zeroes the escrow; the second one reverts with `UnknownOrder` because `_withdraw` checks `escrowed == 0`: [4](#0-3) 

If the malicious user's `RefundEscrow` lands first (entirely plausible — ISMP delivery order across two independently-dispatched, independently-relayed messages is not guaranteed FIFO), the user recovers their escrowed input tokens even though the solver already paid out the required output tokens to the beneficiary on the destination chain during `_fillCrossChain`. The solver's legitimate `RedeemEscrow` then permanently reverts as `UnknownOrder`, i.e., the solver's settlement message can never be honored — the solver is on the hook for the output tokens delivered but never receives the escrowed input tokens.

### Impact Explanation
This is a double-settlement / wrong-beneficiary condition on escrowed funds: the same order commitment produces two competing on-chain settlement outcomes, and the attacker (order owner) can engineer the outcome that gives them a free refund while causing an unrecoverable loss for the solver who already delivered value in good faith. This matches the bounty's "replay/double-claim/double-settlement" and "unauthorized … logic attacks" impact categories, and directly causes loss of solver funds.

### Likelihood Explanation
The path requires no privileged role, relayer collusion, or malicious node behavior — only an unprivileged order owner racing a normal solver fill with a normal `cancelOrder()` call before the order deadline. Cross-chain message ordering between two independently dispatched POST requests is not something the protocol can rely on, so the race is realistically winnable by simply submitting the cancellation promptly after observing the fill event on the destination chain (or even submitting it proactively in the same block/near-simultaneously).

### Recommendation
Add a `_filled[commitment] == address(0)` check at the top of `_cancelFromDest` (and/or centrally in `cancelOrder()`), mirroring the guard already present in `fillOrder`, so that an order which has already been filled cannot be cancelled/refunded.

### Proof of Concept
1. User places a cross-chain order with escrowed inputs on the source chain via `placeOrder`.
2. Solver calls `fillOrder` on the destination chain before the deadline: `_fillCrossChain` sets `_filled[commitment] = solver`, transfers output tokens to the beneficiary, and dispatches `RedeemEscrow` to the source chain.
3. Immediately after, the order's `user` calls `cancelOrder` on the destination chain (still before `order.deadline`): `_cancelFromDest` does not check `_filled[commitment]`, so it overwrites it to `order.user` and dispatches a second message, `RefundEscrow`, to the source chain.
4. If the `RefundEscrow` message is delivered/processed on the source chain before the `RedeemEscrow` message, `_withdraw` succeeds, zeroing `_orders[commitment][token]` and paying the user back their original inputs.
5. When the solver's `RedeemEscrow` message is later processed, `_withdraw` reverts with `UnknownOrder` (`escrowed == 0`), permanently blocking the solver's compensation — the user has kept both the solver's delivered output tokens and their own refunded input tokens.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
