### Title
Cross-array index reuse in `fillOrder` locks escrow when `order.inputs.length != order.output.assets.length` - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents.fillOrder` iterates over `order.output.assets` using index `i` (`for (uint256 i; i < outputsLen; i++)`), but reuses that same output-loop index to read `order.inputs[i]` when computing the escrow amount tied to a fully-filled leg. This is structurally identical to the reported bug class: an index derived from array A (`moneyMarkets`) is applied unchanged to array B (`withdrawSeq`), even though the two arrays are independent and may not share the same length or ordering. Here, `order.inputs` (what the user escrows) and `order.output.assets` (what the user wants) are two independent, caller-supplied arrays with no on-chain invariant enforcing equal length.

### Finding Description
In the fill loop:
```solidity
// evm/src/apps/intentsv2/IntrinsicIntents.sol:61-120
for (uint256 i; i < outputsLen; i++) {
    bytes32 outputToken = order.output.assets[i].token;
    ...
    uint256 escrowedAmount;
    if (amountFilled == totalRequired) {
        escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
    } else {
        escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
    }
``` [1](#0-0) 

`outputsLen = order.output.assets.length` drives the loop bound, but `order.inputs[i]` is dereferenced with the same `i`. Nothing in `placeOrder` enforces `order.inputs.length == order.output.assets.length` — the only length check present in the reviewed `placeOrder` code path is `if (order.inputs.length == 0) revert InvalidInput()`. [2](#0-1) 

The SDK's own filler code confirms the protocol's implicit assumption that `inputs[i]` and `output.assets[i]` are meant to be the same "leg", explicitly warning that misaligned/compacted arrays "would mismatch and revert fillOrder": [3](#0-2) 

Because `placeOrder` (the public order-creation entrypoint) never validates that the two arrays share the same length, an order can legitimately be constructed with `output.assets.length > inputs.length`.

### Impact Explanation
When `order.output.assets.length > order.inputs.length`, `fillOrder` reverts with an out-of-bounds array access as soon as the loop index `i` reaches `inputs.length`, for every solver attempting to fill the order. The order can never be successfully filled — the user's escrowed input tokens remain locked in the gateway with no path to redemption via the normal fill flow, mirroring the original bug's impact ("withdrawals frozen for an arbitrary time... until manually restored"). Recovery is limited to the cancellation/refund path, which for cross-chain orders requires waiting past `order.deadline` and paying additional relayer fees, meaning funds are involuntarily locked for an extended, attacker/user-uncontrollable period — a direct "loss/lock of funds" outcome under the bounty's impact gate. This is reachable by any unprivileged caller through the public `placeOrder` entrypoint with no relayer, prover, or admin involvement.

### Likelihood Explanation
High: `placeOrder` performs no validation tying `inputs.length` to `output.assets.length`, and both are attacker/user-controlled calldata. Any solver-selected or open-fill order with more output legs than input legs (a plausible real-world case, e.g., a single input token being converted into multiple output tokens) triggers this deterministically on first fill attempt.

### Recommendation
In `placeOrder`, enforce `order.inputs.length == order.output.assets.length` (matching the implicit per-leg design already assumed by the SDK/filler), or, if input/output arrays are intended to be independent, rewrite `fillOrder` to resolve each output leg's associated input/escrow entry by token identity (mirroring the `for adapterAddress in withdrawSeq` fix pattern from the original report) rather than by reusing the outer loop index across two unrelated arrays.

### Proof of Concept
1. Attacker/user calls `placeOrder` with `order.inputs = [TokenA: 1000]` (single input) and `order.output.assets = [TokenB: 500, TokenC: 300]` (two outputs) — no revert occurs since only `inputs.length == 0` is checked. [4](#0-3) 
2. TokenA (1000) is escrowed under `_orders[commitment][TokenA]`.
3. A solver calls `fillOrder` supplying amounts for both output legs. The loop runs `i = 0` (`order.output.assets[0]` = TokenB, `order.inputs[0]` = TokenA — succeeds) then `i = 1` (`order.output.assets[1]` = TokenC, but `order.inputs[1]` is out of bounds) and reverts. [1](#0-0) 
4. Every subsequent fill attempt reverts identically; the escrowed 1000 TokenA is unredeemable via `fillOrder` and only reachable via the slower cancellation/refund path after `order.deadline`.
