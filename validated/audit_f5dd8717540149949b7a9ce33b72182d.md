### Title
PedPoP blame proof leaks the ECDH key for a message whose proof-of-possession was never verified — attacker recovers an honest participant's secret shares - ([File: crypto/dkg/pedpop/src/lib.rs](https://github.com/serai-dex/serai), crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to the Flowise bug (an unauthenticated request causes the server to decrypt a stored secret and return the derived secret material to the caller), `KeyMachine::calculate_share` returns an `EncryptionKeyProof` — containing the ECDH shared key `enc_key * msg.key` — for a message whose Schnorr proof-of-possession was only *queued* for batch verification and never verified. The PoP exists specifically to stop an attacker from co-opting an honest party's per-message key and tricking the victim into publishing the ECDH key that decrypts that party's message. An early `?` return on non-canonical share bytes bypasses the PoP check entirely.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs`, `calculate_share` iterates over received shares: [1](#0-0) 

`Encryption::decrypt` (crypto/dkg/pedpop/src/encryption.rs) does two things: it *queues* `msg.pop` into a `BatchVerifier` (verification is deferred), and it immediately computes the ECDH key and packages it into an `EncryptionKeyProof` (the blame proof): [2](#0-1) 

Then `calculate_share` calls `C::F::from_repr(share_bytes.0)` and, on `None`, returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` **before** `batch.verify_with_vartime_blame()` at line 493 is ever reached. The PoP — the only thing binding `msg.key` to its legitimate owner — is therefore never checked before the blame proof is emitted.

The code comments in `encryption.rs` describe exactly this attack and state the PoP prevents it: [3](#0-2) 

`pop_challenge` binds `from` (the *claimed sender index*) and the ciphertext, but not the true sender — so copying `key` verbatim and supplying a garbage `pop`/`msg` is indistinguishable at blame-emission time.

### Impact Explanation
Attack: Eve, a DKG participant, observes the honest `EncryptedMessage` Alice sent to victim Bob (the coordinator relays all share messages). Eve copies Alice's `key` field `X = x·G` into her own share slot for Bob, sets `pop` to anything and `msg` to bytes that are a non-canonical field element. Bob's `calculate_share` decrypts (garbage), hits the `from_repr` failure path, and returns `InvalidShare { blame: Some(EncryptionKeyProof { key: b·X, dleq }) }` where `b` is Bob's long-term encryption secret. Publishing that blame proof reveals `b·X` — the exact ECDH shared key for Alice's genuine message — so anyone (coordinator, all participants) can run `cipher(context, b·X)` and decrypt Alice's secret share intended for Bob.

Eve can repeat this once per victim, copying Alice's `key` from Alice's message to each victim. Alice's shares to *every* participant (n−1 ≥ t distinct evaluations of her polynomial) are thereby decrypted publicly, letting Eve fully reconstruct Alice's contributed secret/coefficient-0. This silently removes an honest party's entropy from the DKG and leaks shares that were designed to remain confidential — a direct secret-material leak reachable with purely public/attacker-supplied inputs (`EncryptedMessage::read` bytes), matching the "unauthenticated decryption oracle returns secret token" bug class. (In the processor, the blame is broadcast via `ProcessorMessage::InvalidShare`/`VerifyBlame` at processor/src/key_gen.rs:424, 504–563.)

### Likelihood Explanation
Requires only that Eve (a) participates in a key-gen session and (b) can observe routed `EncryptedMessage`s — both inherent to the coordinator-mediated DKG in `processor/src/key_gen.rs`. No collusion beyond Eve, no leaked keys, no broken primitives: the bug is a missing check ordering in Serai's own code. Eve submits one malformed share per victim; deterministic.

### Recommendation
Verify the PoP *before* emitting a blame proof, or attribute the `from_repr` failure correctly. Concretely: in `KeyMachine::calculate_share`, do not return early on `from_repr` failure — queue a sentinel share-verification statement and let `batch.verify_with_vartime_blame()` run, mapping a `BatchId::Decryption(l)` failure to `blame: None` (invalid PoP ⇒ sender fault, no key reveal). Alternatively, synchronously verify `msg.pop` inside `Encryption::decrypt` before producing `EncryptionKeyProof`, returning `None` blame on failure.
