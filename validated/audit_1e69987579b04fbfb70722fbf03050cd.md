## Title
`WrappedHyperFungibleToken.send()` locks the actual (post-fee) balance but encodes the full requested `amount` in the bridged message, letting fee-on-transfer/deflationary underlying tokens create unbacked cross-chain credit and drain the shared custody pool - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and then unconditionally builds the outgoing ISMP message with `amount: params.amount` — the *requested* amount, not what the contract actually received. For any underlying ERC20 with a transfer fee, deflationary rebase, or similar non-standard accounting, the contract's custody balance increases by less than `params.amount`, yet the destination chain mints/unlocks the full `params.amount`, and a subsequent timeout refund also pays out the full `params.amount`. This is the exact bug class from the external report ("accounting approach... not compatible with ERC-20 tokens that have a transfer fee... deflationary behavior") reproduced locally in Hyperbridge's own lock/unlock bridge contract.

### Finding Description
In `send()`: [1](#0-0) 
the contract locks tokens via `safeTransferFrom` but never measures `balanceOf(address(this))` before/after to determine the actual amount received. `_buildDispatchPost` then always encodes `params.amount`: [2](#0-1) 

Contrast this with `IntentGatewayV2.sol`, which explicitly re-measures received balances after `safeTransferFrom` specifically to defend against fee-on-transfer tokens: [3](#0-2) 
and is unit-tested for this exact scenario: [4](#0-3) 

`WrappedHyperFungibleToken` has no equivalent balance-delta check. Both the cross-chain delivery path (`onAccept`, unlocking `message.amount` on the destination — or minting via the paired `HyperFungibleToken.onAccept`) and the timeout-refund path use the same uncorrected `message.amount`: [5](#0-4) [6](#0-5) 

Since `WrappedHyperFungibleToken` is a shared-custody pool (one contract holds locked underlying for many users' outstanding cross-chain messages), any single deposit of a non-conforming underlying token creates a permanent gap between "amount promised in outstanding/refundable messages" and "amount actually held," and that gap is paid for out of *other users'* locked balance.

### Impact Explanation
This directly matches the bounty's "stealing or loss of funds" / "false state acceptance" / "wrong beneficiary or amount" categories:
- If the configured `_underlying` has any fee, deflationary, or rebasing behavior, every `send()` call under-collateralizes the pool while the dispatched message still claims the full nominal amount was locked.
- On the destination chain, `HyperFungibleToken.onAccept()`/`WrappedHyperFungibleToken.onAccept()` mints/unlocks the full nominal amount — value not actually backed by the locked custody balance.
- If the request instead times out, `onPostRequestTimeout()` refunds the full nominal `message.amount` to the original sender from the shared pool, i.e. the sender receives back more than they contributed, extracted from other depositors' locked balance in the same contract. No relayer, prover, or admin misbehavior is needed — any unprivileged user who calls the public `send()` entrypoint with such a token (or who structures a self-relay/never-relay + timeout flow, both permissionless features documented in the SDK's self-relay guide) triggers the shortfall.

### Likelihood Explanation
The precondition is that `_underlying` is a non-standard ERC20 (fee-on-transfer/deflationary/rebasing). The contract's `configure()` lets the owner set any ERC20 as `_underlying` with no validation: [7](#0-6) 
Once such a token is configured, exploitation requires no special privileges — every ordinary `send()` call is affected, and the timeout-refund extraction path is reachable by any user using the documented, permissionless self-relay flow (setting `relayerFee = 0` and letting the request time out) referenced in the SDK docs.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.sol`: measure `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom` in `send()`, and use the actual received delta (not `params.amount`) when building the `Message`/`DispatchPost`. Apply the same actual-balance accounting symmetrically wherever tokens leave custody (`onAccept`, `onPostRequestTimeout`) so promised/refunded amounts never exceed what is verifiably held.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a token that charges a 1% transfer fee (e.g. the `FeeOnTransferToken` test double already present in the repo at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2502-2547`).
2. User A calls `send({amount: 1000e18, relayerFee: 0, ...})`. Contract balance increases by only 990e18, but the dispatched `Message.amount` is 1000e18.
3. Because `relayerFee == 0`, no relayer delivers the message (self-relay documented flow); the request times out.
4. User A (or anyone submitting the timeout proof) triggers `onPostRequestTimeout`, which pays out `message.amount = 1000e18` from the shared pool — 10e18 more than was ever actually locked from User A, funded from other users' locked balances, i.e. `IERC20(_underlying).safeTransfer(refundee, message.amount)` at line 361 pays out more than was collected.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token

        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        assertEq(

        );
