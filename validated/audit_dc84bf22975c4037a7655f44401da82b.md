### Title
`kip71.gastarget` governance parameter can be voted to `0`, causing a division-by-zero panic in Magma base-fee computation on every node - ([File: params/kip71_config.go])

### Summary
The `Kip71GasTarget` governance parameter uses `noopFormatChecker`, so it can be set to `0` via a governance vote, unlike `Kip71BaseFeeDenominator` which explicitly rejects `0`. `GasTarget` is later used as a divisor in `NextMagmaBlockBaseFee`, so once the value is applied network-wide, every node computing the next block's base fee divides by zero.

### Finding Description
The parameter registry in `kaiax/gov/param.go` defines `Kip71GasTarget` with `FormatChecker: noopFormatChecker`, meaning any `uint64` value, including `0`, passes validation: [1](#0-0) 

By contrast, the neighboring `Kip71BaseFeeDenominator` parameter explicitly guards against zero (`return ok && v != 0`), showing the codebase is aware this class of parameter must not be zero, but the same guard is missing for `GasTarget`: [2](#0-1) 

A governance vote for `Kip71GasTarget` is not subject to any additional consistency check either — `checkConsistency` in `headergov/impl/header.go` only special-cases `GoverningNode`, `Kip71LowerBoundBaseFee`, `Kip71UpperBoundBaseFee`, and validator votes; `Kip71GasTarget` falls into the default "no more checks" bucket: [3](#0-2) 

Once a `GasTarget = 0` vote is accepted and takes effect, `ParamSet.ToKip71Config()` propagates the value into `KIP71Config.GasTarget`: [4](#0-3) 

`NextMagmaBlockBaseFee` uses `gasTarget` as a divisor for the base-fee delta calculation whenever `parentGasUsed != gasTarget` (i.e., in essentially every real block, since real blocks almost never have exactly `0` gas used): [5](#0-4) 

`big.Int.Div`/`Sub` operations with a zero-valued `big.Int` divisor (`new(big.Int).SetUint64(gasTarget)` where `gasTarget == 0`) panic. This function is invoked from block header validation for every processed block/transaction bundle, meaning once the parameter is live, all nodes validating any subsequent block will panic during `VerifyMagmaHeader`/`NextMagmaBlockBaseFee`.

### Impact Explanation
A single bad `GasTarget = 0` value, once activated via governance, halts block processing on every honest node computing/verifying the next base fee — effectively an unrecoverable chain halt until a hard fork or manual intervention corrects the value. This directly parallels the reported `maxLeverageFactor` bug: a numeric governance/config parameter that is implicitly assumed positive lacks a `> 0` format check, and the resulting zero value breaks a downstream arithmetic invariant (division), causing much more severe consequences here (total chain liveness failure across "governance parameters" and "block assembly" surfaces) than in the original report.

### Likelihood Explanation
Exploitation requires only that a `Kip71GasTarget` vote of `0` be accepted through the ordinary governance-vote flow (`NewVoteData`/`checkConsistency`), which the code currently permits with no format or consistency check. No cryptographic or node-compromise capability is needed beyond normal governance participation, and the format checker for this exact parameter is demonstrably weaker than its sibling `BaseFeeDenominator`, indicating this is an overlooked edge case rather than a hardened invariant.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and audit `Kip71LowerBoundBaseFee`/`Kip71MaxBlockGasUsedForBaseFee`, which also use `noopFormatChecker`) that rejects `0`, mirroring the existing `Kip71BaseFeeDenominator` check (`v != 0`). Additionally, add a defensive `gasTarget == 0` fallback in `NextMagmaBlockBaseFee` similar to the existing `baseFeeDenominator == 0` fallback, so a `0` value cannot cause a division-by-zero panic even if it slips through parameter validation.

### Proof of Concept
1. A governing-council member submits a governance vote for `kip71.gastarget = 0` (passes `NewVoteData`/`checkConsistency` since `FormatChecker` is `noopFormatChecker` and no special-case exists in `checkConsistency`).
2. The vote is included and finalized at the epoch boundary, and `GetParamSet` returns `GasTarget = 0` from that block onward, propagated via `ToKip71Config()`.
3. On the next block where `parentGasUsed != 0` (virtually guaranteed), every node's `VerifyMagmaHeader` → `NextMagmaBlockBaseFee` call executes `x.Div(x, new(big.Int).SetUint64(0))`, panicking and crashing block validation across the network.
