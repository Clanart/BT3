## Finding

### Title
Diff-selection line indices are not recalculated after hunk expansion, causing wrong lines to be staged/committed - (File: `app/src/ui/diff/text-diff-expansion.ts`, `app/src/ui/diff/side-by-side-diff.tsx`, `app/src/lib/patch-formatter.ts`)

### Summary
The external report's broken invariant is: a value (`adminFee`) is computed from a stale/incorrectly-rounded intermediate instead of being recomputed against the correct total, so the split of a shared resource (fees) silently diverges from what was intended. The Desktop analog is structurally identical but for *line selection*, not money: `DiffSelection` stores which lines a user wants to commit as a `Set<number>` of **absolute line indices** (`hunk.unifiedDiffStart + lineIndex`) [1](#0-0) . When a hunk is expanded via `expandTextDiffHunk`, the physical position of pre-existing diff lines inside a hunk shifts (new context lines are spliced in before/after the existing ones) while the *stored* selection index set is never recomputed [2](#0-1) . The component-level `expandHunk` handler only swaps local component state (`this.setState({ diff: updatedDiff })`); it never calls `onIncludeChanged` to rebuild the selection against the new hunk layout [3](#0-2) . `formatPatch`, which builds the actual `git apply`-able patch used to stage/commit, blindly trusts `file.selection.isSelected(absoluteIndex)` [4](#0-3) , so once indices are stale the wrong lines can end up included in (or excluded from) the commit.

### Finding Description
`DiffSelection.isSelected(lineIndex)` has no notion of *which line* an index refers to — it is a pure integer-keyed diff against a default state [5](#0-4) . The correctness of the whole selection model depends entirely on `unifiedDiffStart + lineIndex` staying a stable identifier for the same line across the diff's lifetime.

`expandTextDiffHunk` violates that invariant for "expand up" operations: it prepends new context lines to `hunk.lines` while keeping `hunk.unifiedDiffStart` for the modified hunk unchanged [6](#0-5) [7](#0-6) . This means a line that used to be at `unifiedDiffStart + 5` (e.g. a deliberately-deselected `+` addition) is now physically located at `unifiedDiffStart + 5 + numberOfNewDiffLines`, but the `DiffSelection`'s `divergingLines` set still contains the old index `unifiedDiffStart + 5`. The same shifting also happens for merged hunks (`mergeDiffHunks`, called when the expansion closes the gap between two hunks) which builds an entirely new header/line array while reusing `hunk1.unifiedDiffStart` [8](#0-7) , and for hunks that follow the expanded one, whose `unifiedDiffStart`/`unifiedDiffEnd` are bumped by `numberOfNewDiffLines` [9](#0-8)  — but again nothing re-derives which *old* selection entries should map to which *new* indices.

`onExpandHunk`/`expandHunk` in `side-by-side-diff.tsx` only update the component's local `diff` state; there is no call into `props.onIncludeChanged` (the callback that persists `DiffSelection` changes back to `WorkingDirectoryFileChange`/`AppStore`) [3](#0-2) . The only place the app recomputes/prunes a `DiffSelection` against a changed diff is `withSelectableLines`, invoked from `app-store.ts` when a *whole new diff* is loaded (e.g. file changed on disk) [10](#0-9)  — this path is not exercised by in-memory hunk expansion, since the diff object handed to `withSelectableLines` in that flow comes from re-reading the file, not from the expansion transform.

Consequently, `formatPatch` (used by `stageFiles`/`applyPatchToIndex` to build the real patch that is `git apply`'d to the index) evaluates `file.selection.isSelected(absoluteIndex)` against indices that no longer correspond to the same source lines once a user has expanded a hunk [11](#0-10) , [12](#0-11) .

Note: because `isSelected` is also used to render checkbox state in the diff view [13](#0-12) , the mismatch is not perfectly invisible — a diligent user re-scanning the fully expanded hunk could, in principle, notice a checkbox on the "wrong" line. I was not able to fully trace every rendering code path to confirm whether the discrepancy is always visually detectable or can be masked (e.g., if the shifted index lands on another divergent line with the same selected state, or on a context line where selection state is irrelevant to rendering but still affects `formatPatch`'s treatment of adjacent Add/Delete lines). This uncertainty affects how "silent" the corruption truly is.

### Impact Explanation
If confirmed, this allows a partially-staged commit to include a line the user explicitly excluded, or exclude a line the user explicitly included, without any error or confirmation prompt — a direct instance of "silent corruption of what the user commits." A malicious/crafted diff (e.g., in a fork a user is reviewing, or a file with hunks closely spaced within `DefaultDiffExpansionStep` (20 lines) so that GitHub Desktop's expand-up/expand-down/merge behavior is naturally invoked) could be engineered to make this misalignment likely to occur on a security-sensitive line (e.g., a line toggling a CI config, a dependency pin, or a secret) that the user intended to leave out of the commit.

### Likelihood Explanation
Exploiting this requires: (1) a diff with hunks positioned so that expanding context triggers either the "expand up" reflow or a hunk merge (both are common, ordinary user actions when reviewing partial diffs), and (2) the user making a partial-line selection before or after expanding. This does not require local/physical access, admin rights, or leaked credentials — only reviewing an untrusted diff (from a fetched branch/PR) inside Desktop's normal diff/commit workflow. However, I could not fully verify from the indexed code whether some other guard (e.g., a `componentDidUpdate` reconciliation, or a selection-clearing side effect on hunk expansion) exists elsewhere in the app that mitigates this — the search only surfaced `componentDidUpdate` resetting selection when the file or entire diff object changes wholesale, not on the targeted hunk-expansion path [14](#0-13) .

### Recommendation
Recompute (or remap) the `DiffSelection`'s diverging-line indices whenever `expandTextDiffHunk`/`mergeDiffHunks` shift line positions, analogous to how `withSelectableLines` prunes/reconciles selection state on diff reload. Concretely: after expansion, translate each `divergingLines` entry from its position in the old hunk layout to its corresponding position in the new layout (or, simpler and safer, invalidate/clear divergent selections for any hunk that was structurally modified by an expansion, forcing the user to re-select). `expandHunk` in `side-by-side-diff.tsx` should call `props.onIncludeChanged` with the remapped selection so persisted state (used later by `formatPatch`) stays consistent with what the UI displays.

### Proof of Concept
Conceptual reproduction (not run against the live app, since I only have read access to the code index):
1. Create a file with two hunks separated by fewer than `DefaultDiffExpansionStep` (20) unchanged lines, where the first hunk contains a `+` line the user wants to *exclude* from the commit.
2. In Desktop's Changes view, deselect that `+` line (`DiffSelection.withLineSelection(idx, false)`), leaving the rest of the hunk selected.
3. Click "Expand" on the hunk in a direction that either prepends lines (`expandTextDiffHunk` with `kind: 'up'`) or triggers `shouldMergeWithAdjacent` (merging with the adjacent hunk within the 20-line gap) — this is what `onExpandHunk`/`expandHunk` do [15](#0-14) .
4. Because `hunk.unifiedDiffStart` for the modified/merged hunk is not recalculated relative to inserted lines [7](#0-6) , the previously deselected `+` line now resolves to a different `absoluteIndex` than the one stored in `divergingLines`.
5. Commit the partial selection. `formatPatch` consults `file.selection.isSelected(absoluteIndex)` per line [16](#0-15)  using the now-mismatched indices, potentially including the line the user intended to exclude (or vice-versa) in the generated patch that gets `git apply`'d to the index by `applyPatchToIndex`/`stageFiles` [12](#0-11) .

I was unable to execute the app to confirm the end-to-end runtime behavior (no terminal/browser access in this mode); this assessment is based on static code-path tracing of `expandTextDiffHunk`, `DiffSelection`, and `formatPatch`. A background Devin session with repo checkout and a running Electron/test harness would be needed to write an automated unit/integration test (similar to `app/test/unit/text-diff-expansion-test.ts` and `app/test/unit/patch-formatter-test.ts`) that expands a hunk with an existing partial selection and asserts whether `formatPatch`'s output matches the user's original intended line set.

function mergeDiffHunks(hunk1: DiffHunk, hunk2: DiffHunk): DiffHunk {
  // Remove the first line in both hunks, because those are hunk header lines
  // that will be replaced by a new one for the resulting hunk.
  const allHunk1LinesButFirst = hunk1.lines.slice(1)
  const allHunk2LinesButFirst = hunk2.lines.slice(1)

  const newHunkHeader = new DiffHunkHeader(
    hunk1.header.oldStartLine,
    hunk1.header.oldLineCount + hunk2.header.oldLineCount,
    hunk1.header.newStartLine,
    hunk1.header.newLineCount + hunk2.header.newLineCount
  )

  // Create a new hunk header line for the resulting hunk
  const newFirstHunkLine = new DiffLine(
    newHunkHeader.toDiffLineRepresentation(),
    DiffLineType.Hunk,
    null,
    null,
    null,
    false
  )

  const newHunkLines = [
    newFirstHunkLine,
    ...allHunk1LinesButFirst,
    ...allHunk2LinesButFirst,
  ]

  return new DiffHunk(
    newHunkHeader,
    newHunkLines,
    hunk1.unifiedDiffStart,
    hunk1.unifiedDiffStart + newHunkLines.length - 1,
    // The expansion type of the resulting hunk will match the expansion type
    // of the first hunk:
    // - If the first hunk can be expanded up, it means it's the very first
    //   hunk, so the resulting hunk will be the first too.
    // - If the first hunk can be expanded but short, that doesn't change after
    //   merging it with the second one.
    // - If it can be expanded up and down (meaning it's a long gap), that
    //   doesn't change after merging it with the second one.
    // - It can never be expanded down exclusively, because only the last dummy
    //   hunk can do that, and that will never be the first hunk in a merge.
    hunk1.expansionType
  )
}

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

  // If we get into this state we should never have been called in the first
  // place. Someone gave us a faulty diff and/or faulty selection state.
  if (!patch.length) {
    log.debug(`formatPatch: empty path for ${file.path}`)
    throw new Error(`Could not generate a patch, no changes`)
  }

  patch = formatPatchHeaderForFile(file) + patch

  return patch
}
