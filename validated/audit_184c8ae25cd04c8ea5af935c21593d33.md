### Title
Divide-by-zero panic in KIP-71 base fee calculation via zero `governance.kip71.gastarget` vote - (File: `params/kip71_config.go`)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter without checking it is non-zero. Unlike `BaseFeeDenominator`, which has an explicit `v != 0` format check, `Kip71GasTarget` uses `noopFormatChecker`, allowing a governance vote to set `GasTarget = 0`. Once active, every subsequent block's base-fee computation performs `big.Int.Div(x, gasTarget)` with `gasTarget == 0`, which panics (Go's `big.Int.Div` calls `DivMod`, which panics on division by zero), crashing every node that processes the block header/fee history — a chain-wide denial of service and consensus-halting bug.

### Finding Description
In `params/kip71_config.go`, `NextMagmaBlockBaseFee` computes: [1](#0-0) 
`gasTarget := kc.GasTarget` is used directly, taken from `parentGasUsed > gasTarget` and `parentGasUsed < gasTarget` branches, both of which perform `x.Div(x, new(big.Int).SetUint64(gasTarget))`. [2](#0-1) 
There is no guard analogous to the `BaseFeeDenominator == 0` fallback a few lines above: [3](#0-2) 
which explicitly avoids a zero denominator, but no equivalent protection exists for `gasTarget`.

The root cause is that the governance parameter definition for `Kip71GasTarget` uses `noopFormatChecker`, which performs no validation at all, whereas the sibling parameter `Kip71BaseFeeDenominator` explicitly rejects zero: [4](#0-3) 
This `FormatChecker` is the sole gate applied when a vote value is canonicalized and accepted, both from header votes and API/governance transactions: [5](#0-4) 
and from `PartialParamSet.Add` used by governance parameter-set application: [6](#0-5) 

Once a `GasTarget = 0` vote is accepted and takes effect (governance votes take effect at epoch boundaries and are consumed by `ParamSet.Set`/`ToKip71Config`): [7](#0-6) 
every node computing the next Magma/Kip71 base fee — during block header validation (`VerifyMagmaHeader`), during block assembly, and during `eth_feeHistory` RPC serving — will panic as soon as `parentGasUsed != 0` (i.e., almost any real block), because `gasTarget=0` makes `parentGasUsed > gasTarget` true and the division by `new(big.Int).SetUint64(0)` panics. [8](#0-7) 
This same panic-prone function is also invoked by the public RPC gas-price oracle for fee history/estimation: [9](#0-8) [10](#0-9) 

### Impact Explanation
A `GasTarget = 0` governance parameter causes every honest node — proposers, followers, and RPC servers — to panic on `Div` by zero when validating or building any block with non-zero gas usage, or when serving `eth_feeHistory`/gas-price RPCs. This is a chain-halting denial of service affecting the entire network simultaneously (not just one node), matching the CVSS 5.5 "Availability: High" impact of the referenced kernel CVE's divide-by-zero class, translated to this codebase's governance/base-fee-pricing surface.

### Likelihood Explanation
Reaching this bug requires a governance vote to set `governance.kip71.gastarget` to `0` to be accepted and activated. Because the `FormatChecker` for this parameter is `noopFormatChecker` (no validation), any validator/governing entity able to submit a governance vote (via header vote or governance API) can set this value; there is no additional sanity check anywhere else in the vote-acceptance, param-set, or `ToKip71Config` pipeline. This makes the change gate purely a config/governance-process safeguard (e.g., relying on external governance council review) rather than a code-level invariant — a single successful malicious/erroneous vote is sufficient to trigger a network-wide panic on the very next non-idle block.

### Recommendation
Add an explicit non-zero check for `Kip71GasTarget`'s `FormatChecker` in `kaiax/gov/param.go` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check), and additionally add a defensive `gasTarget == 0` fallback inside `NextMagmaBlockBaseFee` (matching the existing `BaseFeeDenominator == 0` fallback) so a division by zero cannot occur even if a zero value somehow reaches the ChainConfig (e.g., through direct chain-config files or older data).

### Proof of Concept
1. Submit/accept a governance vote (or configure) `governance.kip71.gastarget = 0`. Because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, `NewVoteData`/`PartialParamSet.Add` accepts it without error.
2. Once the parameter takes effect at the next epoch, `ParamSet.GasTarget` becomes `0`, and `ToKip71Config()` propagates it into `KIP71Config.GasTarget`.
3. On the next block where `parentHeaderGasUsed != 0`, any node calling `NextMagmaBlockBaseFee` (header validation via `VerifyMagmaHeader`, block assembly, or `eth_feeHistory`/gas oracle RPC handling) executes `parentGasUsed > gasTarget` (`true` since `gasTarget=0`), then `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget=0`, which panics in Go's `math/big` package, crashing the node process — reproducible network-wide since all nodes share the same governance parameter and process the same blocks.

	}
	return nil
}

func (p PartialParamSet) Add(name string, value any) error {
	param, ok := Params[ParamName(name)]
	if !ok {
		return ErrInvalidParamName
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		return err
	}

	if !param.FormatChecker(cv) {
		return ErrInvalidParamValue
	}

	p[ParamName(name)] = cv
	return nil
}
