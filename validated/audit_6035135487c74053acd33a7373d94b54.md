### Title
Uncontrolled recursion in `AccountKeyRoleBased.DecodeRLP` allows stack-overflow DoS via nested account-key transactions - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes account keys with no nesting-depth limit, mirroring the pdfcpu CVE-2026-38970 pattern where `ParseObjectContext`/`parseArray` recurse through nested objects without a max-depth guard. An attacker can submit a single `TxTypeAccountUpdate` (or any tx type carrying an `AccountKey`, e.g. `TxTypeAccountCreation`, fee-delegated variants) whose serialized `AccountKey` blob contains many nested `AccountKeyRoleBased` levels. Decoding this structure recurses without bound and can crash the node with a stack overflow before any semantic validation (which rejects nested role-based keys) ever runs.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes an outer `[][]byte`, then for every element calls `rlp.DecodeBytes` into a fresh `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type and then calls `s.Decode(serializer.key)` on the concrete key type: [2](#0-1) 

If the encoded key type is again `AccountKeyTypeRoleBased`, this re-enters `AccountKeyRoleBased.DecodeRLP`, which again calls `rlp.DecodeBytes` on its children — a self-recursive call chain (`AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → ...) with **no depth counter or maximum-nesting check anywhere in the call path**. The only defense against nested role-based keys, `ErrNestedCompositeType`, is enforced later during semantic validation (as exercised in `TestAccountUpdateRoleBasedKeyNested`) — i.e., *after* the entire structure has already been fully and recursively decoded: [3](#0-2) 

The reachable transaction path is `Transaction.DecodeRLP` → `TxInternalDataSerializer.DecodeRLP` → concrete tx type's `DecodeRLP` (e.g. account creation/update) → `AccountCommon.DecodeRLP` / key field decode → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP`: [4](#0-3) [5](#0-4) 

Because each recursion level only requires the double-RLP-encoding overhead (a handful of bytes) of `EncodeToBytes(NewAccountKeySerializerWithAccountKey(k))` used when constructing the nested blob, an attacker can pack a very large number of nesting levels into a transaction that is still well within normal transaction size/gas limits, driving Go's goroutine stack to overflow (fatal, unrecoverable process crash — Go does not allow recovering from stack-overflow panics).

### Impact Explanation
This is reachable by any unprivileged transaction sender through the public RPC (`eth_sendRawTransaction`) or direct txpool submission, with no special privileges required. A single crafted transaction can crash a full node/validator process (denial of service) during RLP decoding, before pool admission or block processing has a chance to reject it. Because decoding happens identically on every node that receives/validates the transaction (broadcast, mempool ingestion, block re-execution), this can cause coordinated crashes across honest nodes — a network-wide DoS, consistent with the "High" severity classification of the original CVE.

### Likelihood Explanation
High likelihood: the vulnerable code is on the transaction decode path executed for every incoming transaction (`AddRemote`/`AddLocal` in the pool, and again in block validation). The construction requires only crafting a nested `AccountKeyRoleBased` RLP blob and packaging it as the account-key field of an account-creation/account-update transaction — no cryptographic material or special account state is needed beyond a validly formed transaction envelope. No existing depth guard exists anywhere in the `rlp` decoding library or in `accountkey` package to stop this.

### Recommendation
Add an explicit recursion/nesting-depth limit to `AccountKeyRoleBased.DecodeRLP` (and ideally to `AccountKeySerializer.DecodeRLP`) that rejects a role-based key whose type contains another role-based (or otherwise composite) key type before recursing, rather than only checking `IsCompositeType()` after full decode. A depth counter threaded through decode calls (or rejecting `AccountKeyTypeRoleBased` immediately upon encountering it inside `AccountKeyRoleBased.DecodeRLP`, since nesting is never valid) would close the issue, matching the already-existing semantic rule that "roleBasedKey cannot contain a roleBasedKey as a role key": [6](#0-5) 

### Proof of Concept
1. Construct nested `AccountKeyRoleBased` values recursively (`RoleBased{RoleBased{RoleBased{...}}}`) to a large depth (e.g. tens of thousands of levels), each encoded via `NewAccountKeyRoleBasedWithValues` / `EncodeRLP` as in the existing test helper: [7](#0-6) 
2. Wrap the resulting `AccountKey` in an account-update or account-creation transaction (`NewTransactionWithMap` with `TxValueKeyAccountKey`) and RLP-encode the transaction.
3. Submit it via `eth_sendRawTransaction` or directly to the txpool (`AddRemote`); decoding triggers unbounded recursion in `AccountKeyRoleBased.DecodeRLP` and crashes the process with a stack overflow before `ErrNestedCompositeType` validation (seen in `TestAccountUpdateRoleBasedKeyNested`) is ever reached, since that check only runs after decoding succeeds.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
