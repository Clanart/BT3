### Title
Silent Git Remote URL Hijack via Attacker-Controlled GitHub API `clone_url` Response - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` [1](#0-0)  rewrites the local `origin` remote to the `clone_url` value taken directly from a `fetchRepository` API response, gated only by hostname/path pattern matching (`urlMatchesRemote`) and protocol equality — not by any authenticated ownership or identity check. This function is invoked from `repositoryWithRefreshedGitHubRepository` in `app-store.ts` every time Desktop refreshes GitHub repository metadata for a repo without a current account association [2](#0-1) , meaning the trust anchor is solely "does the API return a repository whose owner/name matches a remote-derived guess."

### Finding Description
The broken invariant, mirroring the Linea report, is: *a value used to redirect a user-controlled operation (bridging tokens / pushing to a remote) is set/overwritten without verifying that it doesn't collide with or corrupt an existing, different target.*

Flow:
1. `matchGitHubRepository` in `repository-matching.ts` finds an account purely by comparing the *hostname* of the git remote to the hostname of an account's endpoint [3](#0-2)  — it does not verify the remote actually belongs to that account's namespace.
2. `matchGitHubRepository` (app-store private method) then extracts `owner`/`name` straight from `parseRemote(remote.url)` [4](#0-3) .
3. `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository(owner, name)` against that account/endpoint and, if a repository object comes back, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` [5](#0-4) .
4. `updateRemoteUrl` compares the *stored* `gitHubRepository.cloneURL` (last-known-good) against the *current* git remote to decide "has the user manually changed it," and if not, blindly writes `apiRepo.clone_url` into the git config via `gitStore.setRemoteURL` [6](#0-5) .

The `clone_url` field is entirely attacker-influenced content coming from the GitHub API (or a GitHub Enterprise Server instance, which the report's threat model of "a git remote/proxy response" directly covers). Renaming a repository, transferring ownership, or a compromised/malicious GHE server returning a crafted `clone_url` for the exact `owner/name` pair Desktop queried is sufficient — none of the guard conditions (`protocolsMatch`, `remoteUrlUnchanged`, `!urlsMatch`) validate that the new URL still points to a repository the user actually intends to push to; they only check that the *old* stored value hadn't been hand-edited and that the scheme is the same.

Just like `setCustomContract` overwrote `nativeToBridgedToken`/`bridgedToNativeToken` without checking the target was already legitimately bound elsewhere, `updateRemoteUrl` overwrites the git `origin` URL — the actual "destination" of the user's pushed commits — driven by unauthenticated, attacker-shaped API data, without confirming the new destination is the same underlying repository (e.g. by comparing GitHub repository IDs) rather than merely a same-looking owner/name string.

### Impact Explanation
If exploited, the user's future `git push` (and pulls) get silently redirected to a different remote entirely (e.g. an attacker's fork registered under a name that used to belong to, or currently resolves through the API to, the target owner/name pair), causing the exact "silent corruption of what the user commits or pushes" impact this task's Valid Impact section calls out. Because the rewrite happens transparently as part of a routine background metadata refresh (no dialog, no diff shown), the user has no visual cue that `origin` has changed before their next push.

### Likelihood Explanation
The refresh path triggers whenever Desktop doesn't already have an account association for a repository (a fairly common state — e.g., freshly cloned via URL, or after removing/re-adding an account) and successfully resolves an `owner/name` via `parseRemote`/`parseRepositoryIdentifier`. An attacker only needs control over what the `fetchRepository` endpoint returns for a specific `owner/name` combination that a victim's local remote happens to parse to — achievable via a malicious/compromised GitHub Enterprise Server (explicitly in scope per the report's "attacker controls ... a git remote/proxy response"), or via legitimate but unverified repository-transfer/rename races on GitHub.com itself. No local access, no admin rights, and no unnatural user steps are required.

### Recommendation
Before calling `gitStore.setRemoteURL`, verify that the new `clone_url` still refers to the *same* repository identity as previously recorded (e.g. compare a stable GitHub repository ID, not just owner/name strings derived from URL parsing), and require explicit user confirmation before silently changing the `origin` remote used for pushes — analogous to adding the "isNewToken" collision check the Linea fix introduced. Additionally, `matchGitHubRepository`/`findAccountForRemoteURL` should not treat a hostname match plus an API 200 response as sufficient proof of ownership/authenticity for driving a config mutation.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
