### Title
Copilot conflict resolution silently mis-splices AI-generated hunk content into the wrong conflict block, corrupting committed code - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`validateResolutionPaths` only checks that the *number* of hunks Copilot returns for a file matches the *number* of conflict-marker blocks GitHub Desktop found in that file [1](#0-0) . It never verifies that hunk *N* in the model's JSON response actually corresponds to conflict block *N* in the file. `reassembleResolvedFile` then blindly walks the raw file top-to-bottom and splices `hunkResolutions[hunkIndex]` into each conflict block strictly by positional order, with no cross-check against the original hunk content [2](#0-1) . The count-only invariant is the same class of bug as the report: two independently-computed quantities (Copilot's declared hunk ordering vs. Desktop's on-disk conflict-block ordering) are assumed to be in lockstep and only their cardinality is checked, not their correspondence.

### Finding Description
The conflict-resolution pipeline is:
1. Desktop extracts conflict hunks from the working tree file and sends them to Copilot as "Conflict 1 of N, Conflict 2 of N …" in the prompt [3](#0-2) .
2. Copilot's JSON reply is parsed into an ordered `hunks` array per file [4](#0-3) .
3. `validateResolutionPaths` gates only on `resolution.hunks.length !== expectedCount` [5](#0-4) .
4. `reassembleResolutions`/`reassembleResolvedFile` then take the *original on-disk* `rawContent` (still containing conflict markers) and splice `hunkResolutions[hunkIndex]` into the `i`‑th conflict block it finds by scanning line-by-line, purely by array position [6](#0-5) .
5. The result is written straight to disk and `git add`-ed with no further diffing against the original hunks: `_applyCopilotConflictResolutions` calls `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and stages the path [7](#0-6) .

Because correctness only depends on matching *counts*, nothing detects or rejects a response where the model (whether due to model error, or a prompt-injection payload smuggled through attacker-controlled inputs that are fed verbatim into the prompt — conflicting file content, commit messages, and PR titles/descriptions, per the system prompt's own description of its inputs [8](#0-7) ) reorders, swaps, or shuffles hunk resolutions while keeping the hunk count identical. `reassembleResolvedFile`'s own doc comment concedes the matching is "by order, not by line number" [9](#0-8) , i.e. there is no semantic binding between a hunk's `resolvedContent` and the specific conflict region it is spliced into beyond array index equality.

This is the direct analog of the audited bug: `EmissionScheduler.epochEmission` assumed `PegAirdrop`'s balance behaved like `MerkleClaim`'s on-demand minting and only checked an aggregate numeric invariant (float supply), not the actual distribution semantics — leading to silent over-issuance. Here, Desktop assumes hunk array order from an untrusted LLM response is semantically identical to on-disk conflict-block order and only checks the aggregate count, not positional correctness — leading to silent content misplacement in a user's commit.

### Impact Explanation
If hunk order is scrambled while count stays constant, Desktop writes a file to the working tree that looks fully resolved (no conflict markers) but has resolution content transplanted to the wrong logical location — e.g. a security check meant for hunk 2 gets written into hunk 1's location, or a validation removed at hunk 3 gets silently applied at hunk 1. The user sees a clean "Continue Merge" result and, per the UI code, files whose conflicts are already gone are not re-diffed against Copilot's stored content before being committed [10](#0-9) . This is silent corruption of what the user commits and (eventually) pushes — squarely in the report's valid-impact category — without requiring any local access, admin rights, or leaked credentials; the attacker only needs to influence content that ends up in the merge (a branch, PR description, or commit message that becomes part of the conflict-resolution prompt).

### Likelihood Explanation
The count-only validation is a real, permanent gap — it is not a corner case invoked only under malformed input; it is the *only* check protecting positional integrity for every single conflict resolution the model produces, including in the fully "happy path" run. The gap is exercised whenever the model reorders its `hunks` array relative to the conflicts it was shown, which large-language-model outputs are known to do under adversarial or even benign prompting conditions, especially as the number of hunks per file grows. The system prompt's own admission that it consumes commit messages and PR descriptions as model input broadens the attacker surface further, since those strings are typically supplied by unprivileged contributors to a repository/PR that a defender later merges via Desktop.

### Recommendation
Bind each hunk resolution to its source conflict block by an explicit identifier (e.g. a hunk index or stable hash of the original `oursContent`/`theirsContent`/`baseContent`) that the model must echo back, and have `reassembleResolvedFile` match on that identifier rather than pure array order. At minimum, add a semantic sanity check — comparing normalized diff similarity between each returned hunk's resolvedContent and the ours/theirs/base content of the specific hunk it will replace — and reject/retry the response if pairing looks incoherent, mirroring how `validateResolutionPaths` already rejects on count mismatch.

### Proof of Concept
1. Set up a merge/rebase/cherry-pick with a file containing two conflict hunks, A (touching a security check) and B (touching unrelated formatting).
2. Craft a commit message or PR description included in the conflict-resolution prompt context that instructs the model (via prompt injection) to "return hunk resolutions in reverse order" or similarly induce a reordering while still returning exactly 2 hunks.
3. Observe that `validateResolutionPaths` passes because `resolution.hunks.length === expectedCount (2)` [5](#0-4) .
4. `reassembleResolvedFile` splices `hunks[0]` (intended for B) into conflict block A's location and `hunks[1]` (intended for A) into block B's location, purely by index [11](#0-10) .
5. The user clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes the swapped content to disk and stages it with no further check [7](#0-6) , producing a commit whose security-relevant hunk A now silently contains the unrelated formatting resolution intended for hunk B (or vice versa).

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }
