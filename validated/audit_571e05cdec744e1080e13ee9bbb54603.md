Based on my investigation, I found a concrete Protobuf analog to the reported `cookie` crate issue. Both bugs share the same root cause: **attacker-controlled numeric text is converted through an unchecked/undersized arithmetic path with no bound on digit count, producing a silently wrong (or, in `cookie`'s case, panicking) value.**

### Title
Improper Input Validation in `TimeUtil::FromString(Duration*)` fractional-digit handling causes silent integer truncation/wraparound - (File: `src/google/protobuf/util/time_util.cc`)

### Summary
`google::protobuf::util::TimeUtil::FromString(absl::string_view, Duration*)` parses a duration string such as `"0.123456789s"` into `seconds`/`nanos` fields. It splits the fractional part into `nanos_part`, parses it with `strtoll`, and then rescales it to nanosecond precision using a helper `Pow(10, 9 - nanos_part.length())`. This function never validates that `nanos_part.length() <= 9`, unlike the equivalent upb JSON decoder which explicitly rejects `digits > 9` ("Too many digits for partial seconds"). [1](#0-0) 

### Finding Description
The scaling helper is:
```cpp
static int64_t Pow(int64_t x, int y) {
  int64_t result = 1;
  for (int i = 0; i < y; ++i) {
    result *= x;
  }
  return result;
}
``` [2](#0-1) 

and it is invoked as:
```cpp
int64_t nanos = std::strtoll(nanos_part.c_str(), &end, 10);
...
nanos = nanos * Pow(10, static_cast<int>(9 - nanos_part.length()));
``` [3](#0-2) 

If an attacker supplies more than 9 fractional digits (e.g. `"0.12345678901s"`, 11 digits), `9 - nanos_part.length()` is negative. The `for (int i = 0; i < y; ++i)` loop with negative `y` never executes, so `Pow` returns `1` instead of the intended fractional scaling (or an error). The raw, unscaled `strtoll` result — which can be an arbitrarily large integer for long digit strings — is then multiplied by `1` and passed unchanged into:
```cpp
duration->set_nanos(static_cast<int32_t>(nanos));
``` [4](#0-3) 

This is a narrowing `int64_t -> int32_t` cast with no range check. For `"0.12345678901s"`, `nanos` computes to `12345678901`, whose low 32 bits (two's-complement wraparound) is `-539222987` — a negative value fitting in the valid `int32` nanosecond range. The only remaining gate, `IsDurationValid`, checks that `nanos` falls within `[-999999999, 999999999]` and matches the sign of `seconds`: [5](#0-4) 
Since `seconds == 0` for this input, the sign-mismatch check is trivially satisfied, and the check silently accepts the corrupted value: `TimeUtil::FromString("0.12345678901s", &d)` returns `true` with `d.seconds() == 0` and `d.nanos() == -539222987`, an arithmetically incorrect Duration silently produced from malformed input that other implementations (upb JSON decoder) correctly reject. [6](#0-5) 

This mirrors the `cookie` crate flaw precisely: an attacker-controlled numeric substring is fed into arithmetic (`Duration::seconds` multiplication in `cookie`; `Pow`/narrowing cast here) without validating the value is in the range the arithmetic can safely represent, so the missing bound is silently bypassed rather than being caught by input validation.

### Impact Explanation
The impact differs from `cookie`'s crash/DoS: here the failure mode is **data integrity corruption**, not a panic — the API returns success (`true`) with a Duration object whose `seconds`/`nanos` values do not correspond to the string the caller supplied. Any application logic in a trusted schema/application layer that uses `TimeUtil::FromString` to accept externally supplied duration strings (e.g., configuration values, timeouts, rate limits) could silently compute wildly wrong durations (here, a negative fractional value from what looks like a small positive fraction), potentially leading to logic errors, incorrect timeouts, or bypassed limits downstream.

### Likelihood Explanation
Likelihood is moderate: `TimeUtil::FromString` is a public, documented utility (`google::protobuf::util::TimeUtil`) that an application can expose directly to untrusted input strings, and the malformed input (`>9` fractional digits) is trivial for a remote client to construct. It does not require special privileges, malicious schemas, or huge/unbounded payloads — a single bounded string exceeding 9 fractional digits suffices.

### Recommendation
Add an explicit check in `TimeUtil::FromString(absl::string_view, Duration*)` (and the parallel Timestamp path) rejecting `nanos_part.length() > 9` before calling `Pow`, matching the guard already present in the upb JSON decoder's `jsondec_nanos`. Additionally, replace the unchecked narrowing cast `static_cast<int32_t>(nanos)` with an explicit range check, and validate `errno`/overflow from `strtoll` for `seconds_part`/`nanos_part` before using the parsed value.

### Proof of Concept

static void jsondec_duration(jsondec* d, upb_Message* msg,
                             const upb_MessageDef* m) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  upb_MessageValue seconds;
  upb_MessageValue nanos;
  upb_StringView str = jsondec_string(d);
  const char* ptr = str.data;
  const char* end = ptr + str.size;
  const int64_t max = (uint64_t)3652500 * 86400;
  bool neg = false;

  /* "3.000000001s", "3s", etc. */
  ptr = jsondec_buftoint64(d, ptr, end, &seconds.int64_val, &neg);
  nanos.int32_val = jsondec_nanos(d, &ptr, end);

  if (end - ptr != 1 || *ptr != 's') {
    jsondec_err(d, "Malformed duration");
  }

  if (seconds.int64_val < -max || seconds.int64_val > max) {
    jsondec_err(d, "Duration out of range");
  }

  if (neg) {
    nanos.int32_val = -nanos.int32_val;
  }

  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 1),
                                   seconds, d->arena));
  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 2),
                                   nanos, d->arena));
}
