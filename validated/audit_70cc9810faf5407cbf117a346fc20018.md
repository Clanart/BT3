### Title
Missing payout-amount binding in `bridge_circuit` lets an operator claim full reimbursement for a dust-value payout - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`bridge_circuit` only asserts that the payout transaction's input spends the exact registered withdrawal outpoint (`txid`/`vout`); it never inspects `input.payout_spv.transaction.output` to verify that the value actually paid to the withdrawer matches the `bridge_amount` recorded for that withdrawal on Citrea. This lets a payout transaction that spends the correct outpoint but sends only a dust-value output to the withdrawer (with the remainder unaccounted for) still produce a valid, acceptable `journal_hash`.

### Finding Description
The binding that should hold is:
`sum(payout_tx.output[i].value where output[i] pays the withdrawer's script) == bridge_amount recorded for that withdrawal on Citrea`

What is actually checked in `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs`) is only: [1](#0-0) 

This binds `payout_spv.transaction.input[payout_input_index].previous_output` to the withdrawal outpoint (`user_wd_txid`, `vout`) obtained from `verify_storage_proofs`, but it never reads `input.payout_spv.transaction.output[..].value`. The only output the circuit inspects at all is the first OP_RETURN output, used solely to extract the operator's x-only pubkey for `deposit_constant`: [2](#0-1) 

`deposit_constant` and `journal_hash` commit `move_txid`, watchtower pubkeys digest, `operator_xonlypk`, `round_txid`, `kickoff_round_vout`, `genesis_state_hash`, `payout_tx_blockhash`, `latest_blockhash`, and `challenge_sending_watchtowers` — no payout amount or withdrawer script is ever hashed into the journal: [3](#0-2) 

`verify_storage_proofs` (`circuits-lib/src/bridge_circuit/storage_proof.rs`) only returns the withdrawal outpoint `txid`/`vout` and the move txid; it never returns or checks any expected payout amount: [4](#0-3) [5](#0-4) 

Off-chain, `Operator::withdraw` does check `Self::is_profitable(...)` before an operator constructs and funds a payout, but this is a self-check performed voluntarily by the operator over its own honest code path — it is not an on-chain or in-circuit enforced constraint, and nothing forces the operator (or whoever actually broadcasts a spend of the withdrawal outpoint) to build the payout output this way: [6](#0-5) 

Because the reimbursement/disprove machinery treats an accepted `bridge_circuit` journal as proof that "a valid payout was made", and that journal contains no commitment to the value paid to the withdrawer, any transaction that (a) spends the exact registered withdrawal `OutPoint` at `payout_input_index`, and (b) contains a first OP_RETURN output encoding the operator's x-only pubkey, will satisfy every check in `bridge_circuit` regardless of how little value actually reaches the withdrawer's script. The remaining value can be sent to fees, an anchor-style dust output, or effectively nowhere committed for the withdrawer.

### Impact Explanation
This falls squarely into the Critical category "an operator reimbursed for a payout it never funded." A withdrawal registered for `bridge_amount` (e.g., 10 BTC) can be "fulfilled" on-chain by spending the registered outpoint into a dust output plus fees, while the operator still obtains a `bridge_circuit`-accepted journal and later claims full `bridge_amount` reimbursement through the round/kickoff reimbursement path, since no verifier, watchtower, or the disprove circuit itself checks payout output value against `bridge_amount` — they all rely on the same `bridge_circuit` journal as the source of truth. This is repeatable per withdrawal and per operator, with blast radius equal to the number of withdrawals an operator processes; the value diverted per occurrence equals `bridge_amount` minus the dust actually paid, i.e., near the full withdrawal amount.

### Likelihood Explanation
No unusual preconditions beyond a normal registered withdrawal (`bridge_amount` set via Citrea `withdraw`) and control over the payout transaction that spends the withdrawal UTXO. It costs only Bitcoin transaction fees to produce the dust-value payout transaction; the OP_RETURN structure and outpoint reference are trivially reproducible from any legitimate payout template, so the discrepancy is fully deterministic and does not depend on network conditions, races, or mainnet/live Citrea state — it can be demonstrated purely via unit-testing the circuit function.

### Recommendation
Bind the payout's actual paid value to the circuit's public output. Concretely:
1. Extend `StorageProof`/`verify_storage_proofs` (or a new storage slot read) to also fetch and verify the `bridge_amount` (or minimum required payout amount) associated with the withdrawal index from Citrea storage.
2. In `bridge_circuit`, after locating `payout_input_index`, identify the output(s) of `payout_spv.transaction` that pay the withdrawer's script (e.g., an output whose `script_pubkey` matches a committed/expected script, or simply require the output at a canonical index) and assert its `value` is `>=` the required `bridge_amount` (minus allowed operator fee).
3. Commit this checked amount (or a hash including it) into `deposit_constant`/`journal_hash` so that any downstream reimbursement logic relying on the journal is bound to a payout that actually delivered the required value.

### Proof of Concept
```
cargo test -p circuits-lib bridge_circuit_dust_payout_accepted
```
Test plan:
1. Build two `BridgeCircuitInput` fixtures that are identical except for the payout transaction:
   - `full_payout_tx`: spends the registered withdrawal `OutPoint`, pays `bridge_amount` (e.g., 10 BTC minus operator fee) to the withdrawer's script, plus the required OP_RETURN operator-pubkey output.
   - `dust_payout_tx`: spends the same registered withdrawal `OutPoint` at the same `payout_input_index`, pays a dust value (e.g., 546 sats) to the withdrawer's script, sends the remainder to fees/anchor, keeps the identical OP_RETURN output.
2. Assert both `input.payout_spv.transaction.input[payout_input_index].previous_output` equal the same registered outpoint (binding under test holds on both sides).
3. Run `bridge_circuit` (or directly the relevant assertions plus `deposit_constant`/`journal_hash` computation) on both inputs with identical `hcp`, watchtower, and storage-proof data.
4. Assert `journal_hash(full_payout_tx_input) == journal_hash(dust_payout_tx_input)` — demonstrating the circuit cannot distinguish a fully funded payout from a dust payout, proving the missing amount binding.

pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant {
    // pubkeys are 32 bytes long
    let pubkey_concat = watchtower_pubkeys
        .iter()
        .flat_map(|pubkey| pubkey.to_vec())
        .collect::<Vec<u8>>();

    let watchtower_pubkeys_digest: [u8; 32] = Sha256::digest(&pubkey_concat).into();

    let pre_deposit_constant = [
        &move_txid,
        &watchtower_pubkeys_digest,
        &operator_xonlypk,
        &watchtower_challenge_connector_start_idx.to_be_bytes()[..],
        &round_txid,
        &kickoff_round_vout.to_be_bytes()[..],
        &genesis_state_hash,
    ]
    .concat();

    DepositConstant(Sha256::digest(&pre_deposit_constant).into())
}

pub fn journal_hash(
    payout_tx_blockhash: PayoutTxBlockhash,
    latest_blockhash: LatestBlockhash,
    challenge_sending_watchtowers: ChallengeSendingWatchtowers,
    deposit_constant: DepositConstant,
) -> blake3::Hash {
    let concatenated_data = [
        payout_tx_blockhash.0,
        latest_blockhash.0,
        challenge_sending_watchtowers.0,
    ]
    .concat();

    let binding = blake3::hash(&concatenated_data);
    let hash_bytes = binding.as_bytes();

    let concat_journal = [deposit_constant.0, *hash_bytes].concat();

    blake3::hash(&concat_journal)
}
