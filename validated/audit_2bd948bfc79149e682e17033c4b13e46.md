Audit Report

## Title
Missing per-client rate limiting on the JSON-RPC HTTP service allows a single client to exhaust the shared blocking-thread pool and degrade RPC service for all users - ([File: rpc/src/rpc_service.rs])

## Summary
`JsonRpcService::new` configures the `jsonrpc_http_server` with only CORS settings, a single-threaded event loop, and `max_request_body_size` — no per-IP, per-connection, or per-method rate/concurrency control is applied before requests are dispatched to expensive handlers. This is architecturally inconsistent with every other network-facing ingress in Agave (QUIC/TPU, gossip pull requests, repair), all of which enforce `TokenBucket`/`KeyedRateLimiter`-based admission control before doing expensive work.

## Finding Description
`ServerBuilder::with_meta_extractor(...).threads(1).cors(...).request_middleware(request_middleware).max_request_body_size(...)` in `rpc_service.rs` builds the HTTP server without any request-rate or concurrency admission control. The only `RequestMiddleware` installed, `RpcRequestMiddleware::on_request`, exclusively intercepts snapshot download paths, `/health`, and file-GET paths — it never inspects or throttles JSON-RPC POST method calls ( [1](#0-0) ). CPU/IO-heavy methods like `getProgramAccounts` route through `JsonRpcRequestProcessor::get_filtered_program_accounts`, which for the non-indexed (default) path explicitly performs an unbounded `bank.get_filtered_program_accounts` scan via `spawn_blocking` with the code comment "this path does not need to provide a mb limit because we only want to support secondary indexes" — meaning no byte-size limit applies in the common case either ( [2](#0-1) ). All such `spawn_blocking` calls share a single fixed-size `rpc_blocking_threads` Tokio runtime built by `service_runtime`, whose own comment documents that it deliberately serves both slow scans and latency-sensitive calls (`getMultipleAccounts`) from the same bounded pool ( [3](#0-2) ). By contrast, QUIC connection admission is gated by `ConnectionRateLimiter`/`TokenBucket` ( [4](#0-3) ), and gossip pull requests are budgeted per IP via `try_consume_pull_request_scan_budget`. No analogous mechanism exists on the JSON-RPC ingress path.

## Impact Explanation
An unprivileged, unauthenticated client with only ordinary JSON-RPC access can open a modest number of concurrent `getProgramAccounts`/`getTokenAccountsByOwner` requests against a program with many accounts. Because these scans consume `spawn_blocking` slots in the shared, fixed-size `rpc_blocking_threads` pool with no per-client admission control, a single client can occupy all blocking-thread slots and starve concurrent calls to latency-sensitive methods (`getAccountInfo`, `getMultipleAccounts`, etc.) that also depend on `spawn_blocking`. This is a non-consensus degradation/DoS of the RPC service, matching the "single-client low-rate RPC crash/degradation" impact category.

## Likelihood Explanation
Any validator/RPC node running `--full-rpc-api` with `getProgramAccounts` enabled (a standard public RPC configuration) is affected. No staking, authentication, or privileged access is required. The number of concurrent requests needed scales with the configured `rpc_blocking_threads` (default `num_cpus / 2` per the code comment), which raises but does not eliminate feasibility.

## Recommendation
Add per-IP/per-connection admission control to `rpc_service.rs`, reusing the existing `TokenBucket`/`KeyedRateLimiter` infrastructure from `streamer/src/nonblocking/connection_rate_limiter.rs`. Additionally, rate-limit or cap concurrency specifically for scan-heavy methods (`getProgramAccounts`, `getTokenAccountsByOwner`, `getTokenAccountsByDelegate`, `getLargestAccounts`) per source IP, and consider isolating these methods onto a separately bounded semaphore/thread pool distinct from the pool serving latency-sensitive calls.

## Proof of Concept
1. Start a validator with `--full-rpc-api` and default `rpc_blocking_threads`.
2. From one unauthenticated client, open N ≈ `rpc_blocking_threads` concurrent `getProgramAccounts` calls against a large, unfiltered program account set, each routed through `get_filtered_program_accounts` → `spawn_blocking` ( [5](#0-4) ).
3. From a second client, concurrently issue `getAccountInfo`/`getMultipleAccounts` calls (also `spawn_blocking`-routed).
4. Observe the second client's requests queue/stall because `rpc_service.rs` applies no admission control before dispatch ( [6](#0-5) ), demonstrating single-client degradation of the shared RPC blocking pool.

pub fn service_runtime(
    rpc_threads: usize,
    rpc_blocking_threads: usize,
    rpc_niceness_adj: i8,
) -> Arc<TokioRuntime> {
    // The jsonrpc_http_server crate supports two execution models:
    //
    // - By default, it spawns a number of threads - configured with .threads(N) - and runs a
    //   single-threaded futures executor in each thread.
    // - Alternatively when configured with .event_loop_executor(executor) and .threads(1),
    //   it executes all the tasks on the given executor, not spawning any extra internal threads.
    //
    // We use the latter configuration, using a multi threaded tokio runtime as the executor. We
    // do this so we can configure the number of worker threads, the number of blocking threads
    // and then use tokio::task::spawn_blocking() to avoid blocking the worker threads on CPU
    // bound operations like getMultipleAccounts. This results in reduced latency, since fast
    // rpc calls (the majority) are not blocked by slow CPU bound ones.
    //
    // NB: `rpc_blocking_threads` shouldn't be set too high (defaults to num_cpus / 2). Too many
    // (busy) blocking threads could compete with CPU time with other validator threads and
    // negatively impact performance.
    let rpc_threads = 1.max(rpc_threads);
    let rpc_blocking_threads = 1.max(rpc_blocking_threads);
    Arc::new(
        TokioBuilder::new_multi_thread()
            .worker_threads(rpc_threads)
            .max_blocking_threads(rpc_blocking_threads)
            .on_thread_start(move || renice_this_thread(rpc_niceness_adj).unwrap())
            .thread_name("solRpcEl")
            .enable_all()
            .build()
            .expect("Runtime"),
    )
}

    async fn get_filtered_program_accounts(
        &self,
        bank: Arc<Bank>,
        program_id: Pubkey,
        mut filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> RpcCustomResult<Vec<(Pubkey, AccountSharedData)>> {
        optimize_filters(&mut filters);
        if self
            .config
            .account_indexes
            .contains(&AccountIndex::ProgramId)
        {
            if !self.config.account_indexes.include_key(&program_id) {
                return Err(RpcCustomError::KeyExcludedFromSecondaryIndex {
                    index_key: program_id.to_string(),
                });
            }
            self.get_filtered_indexed_accounts(
                &bank,
                &IndexKey::ProgramId(program_id),
                &program_id,
                filters,
                sort_results,
            )
            .await
            .map_err(|e| RpcCustomError::ScanError {
                message: e.to_string(),
            })
        } else {
            // this path does not need to provide a mb limit because we only want to support secondary indexes
            let mut accounts = self
                .runtime
                .spawn_blocking(move || {
                    bank.get_filtered_program_accounts(
                        &program_id,
                        |account: &AccountSharedData| {
                            filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                        },
                    )
                    .map_err(|e| RpcCustomError::ScanError {
                        message: e.to_string(),
                    })
                })
                .await
                .expect("Failed to spawn blocking task")?;
            if sort_results {
                // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
                accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
            }
            Ok(accounts)
        }
    }
