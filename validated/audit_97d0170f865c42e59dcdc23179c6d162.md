### Title
Reward pool distributes queued rewards by point-in-time stake balance instead of duration-weighted stake, enabling just-in-time deposit sandwiching of `queueNewRewards()` - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool` (and the equivalent `BaseRewardPoolV2` / bribe rewarder) implement a Synthetix-style `rewardPerTokenStored` index, but unlike Synthetix's `StakingRewards`, the whole `_amountReward` passed to `queueNewRewards`/`donateRewards` is applied instantly to `rewardPerTokenStored` based on `totalStaked()` at that single block, with no `rewardRate`/`periodFinish` vesting over time [1](#0-0) . Because `earned()` only depends on a user's *current* `balanceOf` and the delta of `rewardPerTokenStored` since their last checkpoint [2](#0-1) , any staker who inflates their balance immediately before a `queueNewRewards` call and withdraws immediately after is entitled to a full pro-rata share of that reward drop for zero holding duration.

### Finding Description
`BaseRewardPool._provisionReward` (called from `queueNewRewards`) does the following on every reward injection:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / this.totalStaked();
``` [3](#0-2) 

`totalStaked()` reads the live `stakingToken` balance held by `MasterMagpie` at call time [4](#0-3) , and `balanceOf(account)` reads the user's live staked amount from `MasterMagpie.stakingInfo` [5](#0-4) . `earned()` computes:
```
balanceOf(_account) * (rewardPerToken(_rewardToken) - userRewardPerTokenPaid[_rewardToken][_account]) / 10**stakingDecimals() + userRewards[...]
``` [2](#0-1) 

`userRewardPerTokenPaid` is only checkpointed in `_updateFor`, invoked via the `updateReward` modifier on `getReward()`, which `MasterMagpie` calls on every `deposit`/`withdraw` through `_harvestBaseRewarder` inside `_deposit`/`_harvestAndUnstake` [6](#0-5) . Critically, `_deposit` harvests (checkpoints) the account *before* increasing `user.amount`/`user.available` [7](#0-6) , so the attacker's checkpoint is taken at the pre-inflation `rewardPerTokenStored`, and their `balanceOf` becomes large for the reward computation the moment `queueNewRewards` executes.

Exploit flow:
1. Attacker observes a manager's pending `queueNewRewards(amount, token)` transaction in the mempool.
2. Attacker front-runs with `MasterMagpie.deposit(stakingToken, largeAmount)`, which checkpoints `userRewardPerTokenPaid` at the pre-reward value and inflates both their `balanceOf` and the pool's `totalStaked()`.
3. Manager's `queueNewRewards` executes, increasing `rewardPerTokenStored` by `_amountReward*1e_dec / totalStaked()` — a value now diluted by attacker's inflated `totalStaked()`, but the attacker still owns a large fraction of that stake.
4. Attacker calls `MasterMagpie.withdraw(stakingToken, largeAmount)`, which triggers `getReward` → `updateReward` → `_updateFor`, computing `earned()` using the attacker's large `balanceOf` times the just-added `rewardPerToken` delta, paying out a full pro-rata share of the newly queued reward for a holding period of essentially zero (one or two blocks).

No existing modifier prevents this: `onlyManager` only gates who can call `queueNewRewards`, not when relative to deposits; `nonReentrant`/`whenNotPaused` on `MasterMagpie.deposit`/`withdraw` do not address time-weighting; there is no minimum staking duration, cooldown, or linear vesting (`rewardRate`/`periodFinish`) that would require the attacker to hold across the full reward period. The root cause is architectural: reward accrual is checkpoint/snapshot-based rather than duration/time-weighted, which the question's stated invariant ("earned reward must reflect duration-weighted stake, not point-in-time balance") does not hold in this codebase.

### Impact Explanation
This is a direct theft of yield from long-term stakers: the attacker captures reward tokens proportional to a large temporary balance, meaning honest stakers who held throughout the epoch receive a smaller share of `_amountReward` than they otherwise would have, since the denominator (`totalStaked`) is inflated by the attacker's flash stake at the exact moment of distribution, and the fixed numerator (`_amountReward`) is then split according to balances at that instant rather than duration held. This matches the Immunefi impact class "theft of unclaimed yield" and directly disadvantages other stakers' pro-rata entitlement, applicable identically to `BaseRewardPool`, `BaseRewardPoolV2`, and the bribe/vlMGP reward pools which all share this `_provisionReward`/`rewardPerToken` pattern [8](#0-7) .

### Likelihood Explanation
Feasibility depends on: (1) the attacker being able to observe `queueNewRewards` transactions before they are mined (public mempool visibility, no private relay), (2) the attacker having sufficient capital to acquire a meaningfully large fraction of `totalStaked()` for the duration of a couple of blocks (flash loans of the staking LP token could reduce capital requirements if such liquidity exists), and (3) gas/slippage costs (`deposit`+`withdraw`) being smaller than the reward captured. This is realistic on any public chain where reward-manager transactions are broadcast to a public mempool, and is fully repeatable every time `queueNewRewards`/`donateRewards` is called, requiring no privileged role.

### Recommendation
Convert the reward pool to a time-weighted/streamed distribution model (as in the standard Synthetix `StakingRewards` pattern): introduce `rewardRate`, `periodFinish`, and `lastUpdateTime`, and compute `rewardPerToken()` as an integral of `rewardRate` over elapsed time since `lastUpdateTime`, rather than instantaneously applying the full `_amountReward` against the current `totalStaked()`. Alternatively, add a minimum staking duration/cooldown before a user's stake becomes eligible for reward accrual, or checkpoint stake balances at fixed intervals so `earned()` cannot be manipulated by same-block/near-block stake inflation immediately preceding a reward injection.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `BaseRewardPool` with a stakingToken and rewardToken; register `manager` with `onlyManager` rights on the pool.
2. Have `userA` deposit `1e18` staking tokens and let time pass (simulate normal long-term staking, unrelated to any reward event yet since this pool has no time-based accrual — demonstrate that duration alone earns nothing).
3. Prepare `manager.queueNewRewards(1000e18, rewardToken)` as a pending call.
4. Before executing step 3, have `attacker` call `MasterMagpie.deposit(stakingToken, 9e18)` (9x `userA`'s stake).
5. Execute `queueNewRewards(1000e18, rewardToken)`.
6. Immediately have `attacker` call `MasterMagpie.withdraw(stakingToken, 9e18)`.
7. Assert: `attacker` receives `earned(attacker, rewardToken)` ≈ `1000e18 * 9/10 = 900e18` despite holding stake for 0 elapsed time/blocks of "real" staking, while `userA`, who staked the entire time, only receives `100e18` — i.e., an entrant who staked for a single transaction captured 9x the reward of a user who staked persistently, purely due to relative balance at the `queueNewRewards` block. Assert this contradicts a duration-weighted conservation invariant (expected `userA` reward if time-weighted would be ~100% of `1000e18` since `attacker` held 0 duration).

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);

    function _deposit(address _stakingToken, address _account, uint256 _amount, bool _isVlmgp) internal {
        updatePool(_stakingToken);

        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][_account];

        if (user.amount > 0) {
            _harvestMGP(_stakingToken, _account);

        user.amount = user.amount + _amount;
        if (!_isVlmgp) {
            user.available = user.available + _amount;

        }
        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;

        if (_amount > 0)
            if (!_isVlmgp)
                emit Deposit(_account, _stakingToken, _amount);
            else
                emit DepositNotAvailable(_account, _stakingToken, _amount);
    }

    /// @notice internal function to deal with withdraw staking token
    function _withdraw(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        _harvestAndUnstake(_stakingToken, _account, _amount, _isVlMgp);

        if (!_isVlMgp)
            IERC20(tokenToPoolInfo[_stakingToken].stakingToken).safeTransfer(address(msg.sender), _amount);
        emit Withdraw(_account, _stakingToken, _amount);
    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
