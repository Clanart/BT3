### Title
Unauthenticated key-share injection: `ThresholdKeys` only binds verification shares `1..=t` to the group key, letting arbitrary phantom participants `t+1..=n` join the signing set via attacker-supplied serialized keys — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
Analogous to CVE-2020-35209 (an Atomix node joining a cluster it was never authorized for purely by presenting configuration), `ThresholdKeys::new` derives the group key exclusively from the first `t` verification shares and performs no consistency check on the remaining `n - t` shares. Since `ThresholdKeys::read` reconstructs `ThresholdKeys` entirely from untrusted bytes (calling `ThresholdKeys::new` on attacker-chosen `t`, `n`, and `n` verification-share points), an unauthorized party can embed themselves as participant `j > t` with a self-generated verification share, and thereafter produce fully valid FROST signature shares for the victim's real group key — joining a key set they were never part of.

### Finding Description
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391), the only membership checks are `verification_shares.len() == n` and `participant <= n`. The group key is then computed as:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

Only shares `1..=t` contribute. Shares `t+1..=n` are stored verbatim and are never constrained to the polynomial implied by the group key (there is no `C::generator() * share == verification_share`-style check possible here since `ThresholdKeys` only holds our own secret share, but more importantly there is no check that `sum_{i=1..=t} vs_i * λ_i(1..=t)` equals `sum` over any other `t`-subset — i.e., that all shares are co-linear).

`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reads `t`, `n`, `i`, the interpolation variant, a secret share scalar, and `n` group elements straight from the reader and forwards them to `ThresholdKeys::new`. Nothing authenticates that the deserialized shares belong to an established key set.

Later, `view()` (crypto/dkg/src/lib.rs:463-533) happily interpolates any `included` set containing index `j`, computing `verification_share(j) = vs_j * scalar * λ_j(included)`. FROST's `verify_share` (used via `Schnorr::verify_share` in networks/bitcoin/src/crypto.rs:152-159 and the generic `algorithm.rs` path) verifies a signature share against exactly this interpolated verification share. An attacker who set `vs_j = G * x_j` for known `x_j` passes this check trivially.

### Impact Explanation
A party with no relationship to an existing threshold key set can inject themselves as a signer for that set's group key. When the attacker-controlled `ThresholdKeys` bytes are loaded (anywhere `ThresholdKeys::read` consumes externally supplied key material — backup/restore, key handoff, or config-driven provisioning, mirroring the Atomix "join via configuration" vector), the phantom participant `j` can be named in `included` signing sets and contribute cryptographically valid signature shares toward signatures under the victim's real group key. This defeats the membership guarantee of the threshold scheme: the set of effective signers is `1..=t` honest polynomial holders **plus** every phantom index `t+1..=n` the attacker defined, and signatures produced with attacker participation are indistinguishable from honest ones. This is an unauthorized-join / integrity violation comparable in severity to the reported High.

### Likelihood Explanation
Exploitation requires an attacker to get malicious `ThresholdKeys` bytes accepted via `ThresholdKeys::read` — an unprivileged, public-bytes path explicitly listed as in-scope. No honest-participant misbehavior, leaked keys, or broken BFT assumptions are needed; the crypto library itself vouches for the injected shares because it never checked them. The constraint is that a consumer must deserialize attacker-supplied keys rather than locally generated ones, which is precisely the threat model of the upstream advisory.

### Recommendation
In `ThresholdKeys::new`, verify that the committed share set is self-consistent: for Lagrange interpolation, check that every verification share lies on the degree-`t-1` polynomial defined by the group key — e.g., confirm `group_key == Σ vs_i * λ_i(S)` for an independent subset `S` containing each `i > t` (or store/check a zero-knowledge consistency proof). At minimum, `ThresholdKeys::read` should be documented and gated so deserialized shares are only accepted alongside a binding to an authenticated key set (e.g., a transcript/session commitment or the on-chain-committed group key), rather than treated as authoritative membership configuration.

### Proof of Concept
Conceptual, using `dkg` + `frost` primitives on any `Ciphersuite` `C`:

1. Honest parties run `dealer::key_gen(rng, t=2, n=3)` producing `ThresholdKeys` for participants 1..=3 with group key `Y` and verification shares `vs_1, vs_2, vs_3` on a degree-1 polynomial.
2. Attacker crafts bytes for `ThresholdKeys::<C>::read` declaring `(t=2, n=4, i=4)`, `Interpolation::Lagrange`, an arbitrary `secret_share`, and verification shares `{1: vs_1, 2: vs_2, 3: vs_3, 4: G * x}` where `x` is attacker-chosen. `read` succeeds: `len == n`, all indices `<= n`, `ThresholdKeys::new` computes `group_key = vs_1*λ_1 + vs_2*λ_2 = Y` — participant 4 never touched it.
3. Attacker runs `keys.view(vec![Participant(1), Participant(4)])`. `view` accepts (2 ≥ t), and `verification_share(4) = G*x*scalar*λ_4({1,4})`.
4. In a FROST signing session over included `{1, 4}` for the victim's group key `Y`, the attacker sets their nonce honestly, computes share `s_4 = d_4 + e_4*ρ_4 + λ_4*x*(scalar)*challenge` (using known `x`), and `verify_share(verification_share(4), nonces, s_4)` passes since `s_4*G = R_4 + c * vs_4*λ_4`. Combined with honest participant 1's share, the aggregate signature verifies under `Y` — participant 4 has joined and signed for a key set it was never authorized for, using only self-declared "configuration".
