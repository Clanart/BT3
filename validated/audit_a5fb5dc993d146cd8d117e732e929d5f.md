### Title
Second-preimage / node-type confusion in `dl_verify_proof_internal` allows forging Data Layer inclusion proofs for non-existent key/value pairs - (File: `chia/data_layer/data_layer_util.py`)

### Summary
`dl_verify_proof_internal` (the routine backing the `verify_proof` DataLayer RPC and `dl_verify_proof` wallet RPC) reconstructs a claimed leaf's node hash from attacker-supplied `key_clvm_hash`/`value_clvm_hash` using the exact same combining function, `internal_hash`, that the Merkle tree uses to combine two child node hashes into an internal node hash. Because these two roles share an identical, non-domain-separated formula at the point where the proof is checked, any internal node already present in a real DataLayer Merkle tree can be “reinterpreted” as a forged leaf whose `key_clvm_hash`/`value_clvm_hash` are simply that internal node's left/right children hashes, using that internal node's own (genuine) inclusion path as the “proof.”

### Finding Description
The correct, domain-separated hashing scheme used when building the tree is:
- `key_hash(key) = sha256(0x01 || key)`
- `leaf_hash(key, value) = sha256(0x02 || key_hash || value_hash)`
- internal nodes: `sha256(0x02 || left || right)`

as documented in `.cursor/context/data-layer.md` (Data And File Model section), and `internal_hash` is defined as: [1](#0-0) 

The `0x01` prefix (applied when hashing the *raw* key and value) is what should keep leaves distinguishable from internal nodes at verification time. However, `dl_verify_proof_internal`, which verifies the "hash-only" `DLProof`/`HashOnlyProof` structure used by `get_proof`/`verify_proof`, never sees or re-derives the raw key/value. It receives `key_clvm_hash` and `value_clvm_hash` directly from the caller and computes the presumed leaf hash by feeding them straight into `internal_hash`: [2](#0-1) 

This is identical in form to how the tree combines two *internal* child hashes into a parent (`internal_hash(left, right)`), so nothing in this verification path forces `key_clvm_hash`/`value_clvm_hash` to actually be of the form `sha256(0x01 || key)`. An attacker who controls or can query a DataLayer store can pick any real internal node in the store's Merkle tree, extract its two children hashes `L` and `R` (both already public via `get_proof`/`ProofOfInclusionLayer.other_hash`/`combined_hash` fields exposed by the RPC), and submit a `HashOnlyProof` with `key_clvm_hash = L`, `value_clvm_hash = R`, `node_hash = internal_hash(L, R)` (the internal node's real hash), and the internal node's own real sibling path as the "layers." `dl_verify_proof_internal` will:
1. Match the puzzle hash against the real, current singleton root — passes, since it's the real root.
2. Compute `leaf_hash = internal_hash(L, R)`, which equals the real internal node's hash — passes the `proof.node_hash` equality check.
3. Walk `proof.valid()` up to the root using the internal node's authentic sibling path — passes, since that path is genuinely part of the tree.

The RPC returns `success=True` claiming inclusion of a fabricated `(key_clvm_hash, value_clvm_hash)` pair that was never actually inserted as a real key/value entry.

Note this is different from the offer-settlement path (`verify_offer` in `chia/data_layer/data_layer_wallet.py`), which is not vulnerable because it is given the raw `key`/`value` and recomputes `leaf_hash(key, value)` (which applies the `0x01` domain-separation prefix before combining), so an attacker cannot supply raw preimages that collide with an internal node combination there: [3](#0-2) 

The vulnerable surface is specifically the hash-only proof path (`GetProofResponse`/`VerifyProofResponse`/`dl_verify_proof`), reachable via the local `verify_proof` DataLayer RPC endpoint and the wallet `dl_verify_proof` RPC: [4](#0-3) [5](#0-4) 

### Impact Explanation
Any Data Layer client or local RPC caller can craft a `HashOnlyProof` that `verify_proof`/`dl_verify_proof` will validate as a legitimate inclusion of an attacker-chosen `(key_clvm_hash, value_clvm_hash)` pair that never corresponds to an actual key/value entry in the store — it is merely two children hashes of a pre-existing internal Merkle node. This breaks the core guarantee of the hash-only proof format: that `success=True` means "this specific key/value hash pair is committed in the store's Merkle tree as a real leaf." Any downstream consumer that trusts `verify_proof`'s result as evidence of data authenticity (e.g., third-party verification of Data Layer-anchored claims, or any protocol/integration layer that gates an action on a successful `verify_proof` response for a specific key/value hash pair) can be misled into accepting forged "proof" of data that was never inserted. This is a forged-data/asset-identity issue rooted in the classic second-preimage node-type confusion, matching the reported bug class.

### Likelihood Explanation
Exploitation requires no privileged access: any party able to call `get_proof`/inspect a store's Merkle layers (which are meant to be publicly queryable/verifiable via `verify_proof`) can harvest internal node sibling hashes (exposed directly in `ProofOfInclusionLayer.other_hash`/`combined_hash`) and construct a forged `HashOnlyProof` locally, then submit it to any DataLayer RPC that calls `verify_proof`/`dl_verify_proof`. No signing, mempool interaction, or on-chain step is needed to trigger the false-positive verification result.

### Recommendation
Domain-separate the leaf-hash computation used for hash-only proofs from the internal-node combination function, e.g. by hashing `(key_clvm_hash, value_clvm_hash)` with a leaf-specific prefix distinct from `internal_hash`'s prefix (analogous to how `key_hash`/`value_hash` already apply the `0x01` prefix before the raw key/value are combined). Concretely, `dl_verify_proof_internal` should not derive the presumed leaf node hash via the same `internal_hash` used to combine two arbitrary child hashes; it needs its own domain-separated combination (or an explicit tag indicating "this is a leaf built from hash-only key/value" versus "this is an internal node") so that no internal node's `(left, right)` pair can be reinterpreted as a valid `(key_clvm_hash, value_clvm_hash)` leaf.

### Proof of Concept
1. Query `get_proof`/inspect any populated DataLayer store to retrieve `ProofOfInclusionLayer` entries for an existing key, exposing internal node `other_hash`/`combined_hash` values.
2. Pick any internal node hash `combined_hash = internal_hash(L, R)` where `L`/`R` are its children (or derivable from adjacent layers), and take that internal node's own remaining sibling path up to the root as the "proof layers."
3. Construct a `DLProof` containing a `HashOnlyProof` with `key_clvm_hash = L`, `value_clvm_hash = R`, `node_hash = combined_hash`, and the harvested sibling layers, plus the store's real `coin_id`/`inner_puzzle_hash`.
4. Submit this proof to `verify_proof` (`chia/data_layer/data_layer_rpc_api.py:596-600`) or wallet `dl_verify_proof`.
5. Observe `dl_verify_proof_internal` (`chia/data_layer/data_layer_util.py:898-915`) returns `success=True`, falsely certifying that `(L, R)` is an included key/value hash pair, even though `L`/`R` are just internal tree node hashes with no corresponding real key/value entry.

```python
async def dl_verify_proof(
    dlproof: DLProof,
    wallet_node: WalletNode,
    peer: WSChiaConnection,
) -> VerifyProofResponse:
    """Verify a proof of inclusion for a DL singleton"""

    coin_id = dlproof.coin_id
    coin_states = await wallet_node.get_coin_state([coin_id], peer=peer)
    if len(coin_states) == 0:
        raise ProofIntegrityError(f"Invalid Proof: No DL singleton found at coin id: {coin_id.hex()}")

    verified_keys = dl_verify_proof_internal(dlproof, coin_states[0].coin.puzzle_hash)

    response = VerifyProofResponse(
        verified_clvm_hashes=ProofResultInclusions(dlproof.store_proofs.store_id, verified_keys),
        success=True,
        current_root=coin_states[0].spent_height is None,
    )
    return response
```
