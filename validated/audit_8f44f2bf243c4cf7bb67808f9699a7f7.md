The bug-class parallel is: `ConvexRewardPoolOracle` silently assumed a fixed relationship (`token.decimals() == curveLpToken.decimals()`) between two representations of the same value, producing a wrong result whenever that unstated assumption didn't hold. GitHub Desktop's diff/patch pipeline makes an analogous unchecked, hard-coded assumption — that raw git diff bytes are UTF-8 — and that assumption feeds directly into partial-commit patch generation, where a mismatch causes bytes that the user never touched to be silently rewritten into the committed blob.

### Title
Partial-commit patch generation assumes diff output is UTF-8, silently corrupting non-UTF-8 file bytes on commit - (File: app/src/lib/git/diff.ts)

### Summary
`diffFromRawDiffOutput()` decodes the raw `git diff --patch-with-raw` buffer with a hard-coded assumption that the content is UTF-8, explicitly noted in the code as a known simplification. [1](#0-0)  This decoded, potentially mis-decoded string becomes the `DiffLine.text` used by `formatPatch()` to synthesize a partial-commit patch, which is then piped to `git apply --cached` to update the index. [2](#0-1) [3](#0-2)  If the tracked file is not actually UTF-8 (e.g. Windows-1252/Shift-JIS/legacy text, or a file crafted with invalid UTF-8 byte sequences), Node's `Buffer.toString('utf-8')` will substitute invalid sequences with U+FFFD or otherwise re-interpret multi-byte boundaries, an irreversible, lossy transformation. Because context/unselected lines are copied verbatim (`hunkBuf += `${line.text}\n``) from this already-corrupted string, applying the patch writes a blob whose "untouched" bytes differ from what is on disk — a silent corruption of the user's commit content.

### Finding Description
The correctness of Desktop's partial-staging feature relies on: 

`bytes read from git diff == bytes ultimately written into the new git blob for lines the user did not select`

This is only true if `Buffer.toString('utf-8')` is lossless for the file's actual encoding, i.e. only when the underlying tracked file is genuinely UTF-8. The code openly assumes this: 

```
// for now we just assume the diff is UTF-8, but given we have the raw buffer
// we can try and convert this into other encodings in the future
const result = output.toString('utf-8')
``` [4](#0-3) 

This decoded text is parsed into `DiffHunk`/`DiffLine` objects by `DiffParser`, which operates purely on JS strings with no byte-fidelity guarantees. [5](#0-4)  When the user performs a partial commit (selecting only some lines of a hunk), `formatPatch()` reconstructs a synthetic unified diff by re-emitting `line.text` — including all unselected/context lines — verbatim into the patch buffer:

```
if (line.type === DiffLineType.Context) {
  hunkBuf += `${line.text}\n`
  ...
} else if (file.selection.isSelected(absoluteIndex)) {
  hunkBuf += `${line.text}\n`
``` [6](#0-5) 

That patch string is then sent as `stdin` to `git apply --cached`, which writes the resulting content straight into the git index/object store: 

```
const patch = await formatPatch(file, diff)
await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })
``` [7](#0-6) 

No guard exists between the UTF-8 decode step and the patch-application step to detect or reject non-UTF-8 content — the file only needs to avoid the NUL-byte binary heuristic used elsewhere in git status/diff plumbing to be routed down this "text diff" path. There is no path-based `resolveWithin`-style validation here because the vulnerable step isn't a path traversal — it's a lossy content re-encoding that the write path (`git apply --cached`) trusts unconditionally.

### Impact Explanation
Selecting and committing only *some* lines of a file whose bytes are not valid/matching UTF-8 causes Desktop to silently rewrite the surrounding, unselected context bytes of that file when constructing the new commit — the user believes they are committing only their selected change, but the resulting blob differs from the working-tree file in ways they did not choose and were not shown (the rendered diff itself would already display the mis-decoded/`U+FFFD` characters, but users routinely don't line-by-line byte-audit unselected context). This matches the "silent corruption of what the user commits" impact category: a repository containing legacy/non-UTF-8-but-non-binary text files, when partially staged, can end up with irreversibly altered content baked into the commit history and pushed upstream.

### Likelihood Explanation
This path is reachable purely through everyday app usage on ordinary content: clone or open any repository containing a non-UTF-8 (or maliciously crafted invalid-UTF-8) tracked text file, edit it, and use Desktop's line/hunk selection to stage only part of the change (a core, heavily used Desktop feature). No admin rights, local/physical access, or social engineering is required — an attacker only needs the target to interact normally with a repository/file whose encoding they control (e.g. a shared or cloned repo). The explicit code comment acknowledging the UTF-8 assumption indicates this is a known, unaddressed limitation rather than a defended edge case.

### Recommendation
Avoid decoding the raw diff buffer as UTF-8 when reconstructing patches for partial application. Options: (1) detect the file's actual encoding and operate byte-safe (or reject partial-staging with a warning when the file is not confirmed valid UTF-8), or (2) apply patches using git's native hunk/line addressing (e.g. `git apply` with byte-range or index-based line selection) instead of re-serializing decoded JS strings, so that unselected regions are always taken from the original bytes verbatim rather than round-tripped through a lossy string decode.

### Proof of Concept
1. Create a repository with a tracked text file containing invalid UTF-8 byte sequences (or content in an 8-bit legacy encoding) that doesn't trigger Desktop's binary-file heuristic (no NUL bytes).
2. Modify the file, producing a diff with at least two hunks/lines, at least one of which is far from the byte(s) that are not valid UTF-8.
3. In Desktop's changes view, select only one hunk/line for commit (partial staging), leaving the region containing non-UTF-8 bytes as unselected context.
4. Commit; inspect the resulting blob with `git cat-file -p <blob>` and compare it byte-for-byte to the working-tree file — the context bytes around/at the non-UTF-8 sequence will differ (e.g. replaced with the UTF-8 encoding of U+FFFD, `EF BF BD`), even though the user never selected or intended to change that region.

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

  private parseHunk(
    linesConsumed: number,
    hunkIndex: number,
    previousHunk: DiffHunk | null
  ): DiffHunk {
    const headerLine = this.readLine()
    if (!headerLine) {
      throw new Error('Expected hunk header but reached end of diff')
    }

    const header = this.parseHunkHeader(headerLine)
    const lines = new Array<DiffLine>()
    lines.push(new DiffLine(headerLine, DiffLineType.Hunk, 1, null, null))

    let c: DiffLinePrefix | null

    let rollingDiffBeforeCounter = header.oldStartLine
    let rollingDiffAfterCounter = header.newStartLine

    let diffLineNumber = linesConsumed
    while ((c = this.parseLinePrefix(this.peek()))) {
      const line = this.readLine()

      if (!line) {
        throw new Error('Expected unified diff line but reached end of diff')
      }

      // A marker indicating that the last line in the original or the new file
      // is missing a trailing newline. In other words, the presence of this marker
      // means that the new and/or original file lacks a trailing newline.
      //
      // When we find it we have to look up the previous line and set the
      // noTrailingNewLine flag
      if (c === DiffPrefixNoNewline) {
        // See https://github.com/git/git/blob/21f862b498925194f8f1ebe8203b7a7df756555b/apply.c#L1725-L1732
        if (line.length < 12) {
          throw new Error(
            `Expected "no newline at end of file" marker to be at least 12 bytes long`
          )
        }

        const previousLineIndex = lines.length - 1
        const previousLine = lines[previousLineIndex]
        lines[previousLineIndex] = previousLine.withNoTrailingNewLine(true)

        continue
      }

      // We must increase `diffLineNumber` only when we're certain that the line
      // is not a "no newline" marker. Otherwise, we'll end up with a wrong
      // `diffLineNumber` for the next line. This could happen if the last line
      // in the file doesn't have a newline before the change.
      diffLineNumber++

      let diffLine: DiffLine

      if (c === DiffPrefixAdd) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Add,
          diffLineNumber,
          null,
          rollingDiffAfterCounter++
        )
      } else if (c === DiffPrefixDelete) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Delete,
          diffLineNumber,
          rollingDiffBeforeCounter++,
          null
        )
      } else if (c === DiffPrefixContext) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Context,
          diffLineNumber,
          rollingDiffBeforeCounter++,
          rollingDiffAfterCounter++
        )
      } else {
        return assertNever(c, `Unknown DiffLinePrefix: ${c}`)
      }

      lines.push(diffLine)
    }

    if (lines.length === 1) {
      throw new Error('Malformed diff, empty hunk')
    }

    return new DiffHunk(
      header,
      lines,
      linesConsumed,
      linesConsumed + lines.length - 1,
      getHunkHeaderExpansionType(hunkIndex, header, previousHunk)
    )
  }
