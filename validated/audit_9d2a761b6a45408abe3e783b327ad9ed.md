[1](#0-0) ### Title
Unrelated later Bitcoin transaction can overwrite a deposit's origin and instruction - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` accumulates matching outputs across all transactions in a block, then applies each subsequent transaction's `presumed_origin` and Serai instruction data to every previously accumulated output. An attacker who gets a transaction ordered after a victim's deposit in the same block can rewrite the victim output's refund origin or instruction without paying Serai anything. [1](#0-0) 

### Finding Description
`outputs` is initialized outside the per-transaction loop, and every scanned output from the whole block is appended to it. [2](#0-1) 

The loop only skips metadata extraction when that cumulative vector is empty, so once any earlier transaction produced a Serai output, every later transaction enters the metadata path—even if the later transaction contains no output to Serai. [3](#0-2) 

The later transaction's first input is used as `presumed_origin`, and `extract_serai_data(tx)` is read from the later transaction. [4](#0-3) 

The code then iterates over the entire accumulated `outputs` vector rather than only the outputs created by the current transaction, overwriting `data` for `External` outputs and overwriting every output's `presumed_origin`. [5](#0-4) 

During processing, `instruction_from_output` decodes the overwritten `data`, converts it to a `RefundableInInstruction`, and falls back to the overwritten `presumed_origin` as the instruction origin. [6](#0-5) 

If the injected data is absent or invalid, `instruction_from_output` returns no instruction while still returning the spoofed refund origin; the caller then builds a `PlanFromScanning::Refund` spending the victim's output to that origin. [7](#0-6) 

Those scan-generated refund plans are expanded into real scheduler plans through `refund_plan`, causing the multisig to sign a spend of the victim output. [8](#0-7) 

### Impact Explanation
This permits theft or misattribution of a confirmed Bitcoin deposit: an attacker can cause the victim's external output to be refunded to the attacker's Bitcoin address, or inject an instruction crediting the attacker's chosen Serai destination. The vulnerable association is not cryptographically bound to the deposit transaction because transaction-scoped metadata is applied to all previously scanned outputs. [5](#0-4) [7](#0-6) 

### Likelihood Explanation
An unprivileged attacker can monitor for an unconfirmed Serai deposit and broadcast a transaction designed to be mined after it in the same block. The malicious transaction does not need to pay Serai, create a matching output, or control any threshold key; it only needs a chosen first input and optional OP_RETURN/witness-embedded Serai data. Successful exploitation depends on transaction ordering within one block, but block transaction ordering is not guaranteed to preserve deposit order or isolate deposits from unrelated public transactions. [1](#0-0) 

### Recommendation
Keep the scan results transaction-scoped. For each transaction, collect its `scan_transaction` results into a local `tx_outputs` vector, skip metadata extraction when that local vector is empty, and assign `presumed_origin`/`data` only to those outputs before appending them to the block-wide result. This prevents metadata from one transaction from being attributed to outputs created by any other transaction. [9](#0-8) 

### Proof of Concept
Consider a block containing:

1. `tx_victim`, which pays the multisig's external P2TR address and contains no Serai data.
2. `tx_attacker`, ordered later in the same block, which contains no output to the multisig, has an attacker-controlled first input, and contains malformed Serai data or an attacker-controlled valid instruction.

When `get_outputs` processes `tx_victim`, it appends the victim's `External` output to `outputs`. [10](#0-9) 

When `get_outputs` processes `tx_attacker`, `outputs` is still non-empty even though `tx_attacker` contributed no matching output. [11](#0-10) 

The function derives the attacker's address from `tx_attacker.input[0]` and extracts the attacker's transaction data, then overwrites the victim output's `presumed_origin` and `data`. [12](#0-11) 

If the injected data is malformed, `instruction_from_output` returns `(Some(attacker_origin), None)`, and the caller creates a refund plan spending the victim's output to the attacker's origin. [13](#0-12) [7](#0-6) 

If the injected data instead encodes a valid refundable instruction naming the attacker's Serai destination, the rewritten instruction is pushed for processing against the victim's deposit amount. [14](#0-13) [15](#0-14)
