### Title
Cached FROST preprocess seed is reused across `share` and `complete`, enabling nonce reuse and validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug class of the external report is "use after free": an object is consumed/invalidated, then later used again. In Serai the analogous shape is the FROST `CachedPreprocess` seed, whose documentation states it "MUST only be used once" because reuse leaks the private key share. `SigningProtocol::preprocess_internal` stores the seed under `CachedPreprocesses: (context) -> [u8; 32]` keyed only by `(b"DkgConfirmer", attempt)`, reloads it on every call, and never deletes it — so every invocation of `share_internal` rebuilds an `AlgorithmSignMachine` with identical nonces via `seeded_preprocess` (`ChaCha20Rng::from_seed(*seed.0)`). `DkgConfirmer::share` and `DkgConfirmer::complete` each invoke `share_internal`, causing `AlgorithmSignMachine::sign` to be executed multiple times with the same nonce pair while the message and counterparty preprocess sets are drawn from independently-supplied arguments.

### Finding Description
`preprocess_internal` only writes `CachedPreprocesses::set` when the entry is absent; afterwards it unconditionally reads the entry back, decrypts it, and calls `AlgorithmSignMachine::from_cache`, which deterministically regenerates the same `Commitments` nonces from the same 32-byte seed [1](#0-0) [2](#0-1) . There is no `CachedPreprocesses::del` anywhere, so the seed persists after the machine produced by it has been consumed by `sign`.

The FROST library is explicit that this seed is single-use: "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" [3](#0-2) , and the spec repeats it [4](#0-3) . `sign` takes `self` by value and consumes `nonces` [5](#0-4) ; the safety invariant is that the machine is the sole holder of the seed state. Rebuilding it from the DB violates that invariant exactly like a use-after-free: the "freed" nonce state is resurrected and used again.

`DkgConfirmer::share` calls `share_internal` over attacker-influenced `preprocesses` and `key_pair` (the message is `set_keys_message(set, removed, key_pair)`), and `DkgConfirmer::complete` calls `share_internal` again with independently supplied `preprocesses` and `key_pair` [6](#0-5) . The file's own safety argument (lines 25–55) admits that nonce reuse happens if "the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" — which is precisely what the `share`/`complete` re-execution structure does whenever the two invocations observe different inputs. The code even contains an unresolved TODO acknowledging the missing check: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" and "We also need to review how we're handling Processor preprocesses" [7](#0-6) .

### Impact Explanation
With Schnorr/FROST, two signature shares produced under the same nonce but over different binding-factor/challenge values linearly reveal the signer's secret share. Here the consumed object is the validator's actual MuSig secret key (`self.key: Zeroizing<<Ristretto as Ciphersuite>::F>`), i.e., the validator's root-of-trust key used for DKG confirmation. Recovery of it lets an attacker impersonate the validator in the MuSig confirmation signature (`musig(musig_context(...), self.key.clone(), participants)`), forge validator-signed messages, and — since the same key underpins the validator's participation — compromise the validator set's signing authority. This maps directly onto the report's "Modify Memory / possible remote execution" severity: concrete secret-key recovery reachable through protocol messages an unprivileged counterparty (another validator) causes to be signed.

### Likelihood Explanation
Exploitation requires `share` and `complete` (or two `share` calls under the same attempt context) to be driven with different `preprocesses`/`key_pair` inputs. The `key_pair` argument and the preprocess map are derived from tributary/Substrate data contributed by validators rather than a single BFT-finalized value bound to the nonce, and the code provides no guard binding the cached seed to one specific message — the mitigation is a TODO. Distinct inputs can arise from a conflicting `KeyPair` proposed for the same set, a different `removed` set computed for the same attempt, or re-execution after a partial rebuild (the file's safety argument only covers *complete* rebuilds). Since context is only `(b"DkgConfirmer", attempt)`, any second `sign` under the same attempt is deterministic nonce reuse. I was not able to fully trace `handle.rs`'s call ordering in the iterations available, so the exact message sequence that forces divergent inputs is unverified; however the absence of any binding check or seed deletion is confirmed in the code, and the design comments concede the failure mode.

### Recommendation
Delete `CachedPreprocesses` once `share_internal` produces a share (e.g., `CachedPreprocesses::del` after `from_cache`, or on completion of the attempt), so `sign` can never execute twice under one seed. Additionally, implement the noted TODO: before publishing a share, verify the nonce commitments derived from the cached seed match the preprocess commitments already published on-chain for that context, and bind the context to the message (e.g., hash of `set_keys_message` inputs) so any divergence in `preprocesses`/`key_pair` aborts rather than re-signs.

### Proof of Concept
Conceptual (the vulnerable path is deterministic):

1. Coordinator calls `DkgConfirmer::preprocess()` → `preprocess_internal` stores seed `S` under `CachedPreprocesses[(b"DkgConfirmer", attempt)]` and publishes preprocess `P` with nonce commitments `C = f(S)`.
2. `DkgConfirmer::share(preprocesses_A, key_pair_A)` → `share_internal` → `preprocess_internal` reloads `S`, `from_cache` regenerates the same nonces, `sign(preprocesses_A, msg_A)` emits share `s_A = d + e_A·λ_i·share_i` (schematically).
3. `DkgConfirmer::complete(preprocesses_B, key_pair_B, shares)` is invoked with `key_pair_B ≠ key_pair_A` (or a different signing set), so `msg_B ≠ msg_A` → `share_internal` again rebuilds the machine from `S` and `sign` emits `s_B` under the *same* nonce `d` but a different challenge/binding `e_B`.
4. `d = (s_A − s_B)/(e_A − e_B)` and the validator's MuSig secret key follows from `s_A − d`.

The nonce determinism is guaranteed by `seeded_preprocess` deriving all nonces solely from `ChaCha20Rng::from_seed(*seed.0)` [8](#0-7) , and the reuse is guaranteed by `preprocess_internal` never clearing `CachedPreprocesses` [9](#0-8) .

```rust
  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
```

```markdown
Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
```
