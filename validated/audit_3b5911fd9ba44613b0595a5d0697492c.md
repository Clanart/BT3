### Title
Attacker-controlled "theirs" content with a fake `>>>>>>>`-shaped line causes Copilot conflict reassembly to mis-detect the conflict boundary, silently committing leftover raw conflict-marker text and misaligned resolutions - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` splices the model's per-hunk resolutions into the original conflicted file by scanning line-by-line for conflict marker boundaries. Its look-ahead loop stops at the *first* line matching the "theirs" marker regex, without verifying that this is the marker that actually terminates the current conflict hunk. This is analogous to the reported bug class: a loop whose boundary/skip logic is evaluated against the wrong element, silently processing (or here, mis-terminating) content that should have been treated differently, corrupting the final result.

### Finding Description
The relevant markers and loop: [1](#0-0) [2](#0-1) 

For each line matching `<{7}` (a start-of-conflict marker), the function scans forward for a `={7}` separator and then breaks at the *first* subsequent line matching `>{7}`, treating that as the closing marker (`closingIndex`). It does not verify this candidate is the marker actually inserted by git for this hunk — it only checks that a separator was seen earlier in the scan.

The "theirs" side of a merge conflict is attacker-controlled content: it comes from whatever branch/PR/remote the victim is merging into their repository (e.g. a malicious pull request). If that content contains a line that happens to match `/^>{7}(?:\s|$)/` (seven `>` characters followed by whitespace or end-of-line) — trivially achievable in a code comment, string literal, markdown snippet, or ASCII-art banner — the look-ahead loop breaks at that fake line instead of the real closing marker git actually inserted further down. This causes:

1. The conflict block to be truncated early: only the fabricated fake-marker's above content is deemed "the conflict," and Copilot's hunk resolution is spliced in for that truncated region.
2. The rest of the real "theirs" content, plus the real git-inserted `>>>>>>> branch-name` marker line, are now outside any recognized conflict block and get copied through verbatim as ordinary file content (they don't match the "ours" marker regex, so they're never revisited).
3. For files with multiple conflict hunks, `hunkIndex` is now out of sync with the actual remaining conflict blocks in the file, so subsequent hunks receive the wrong model-provided resolution content (analogous to the EigenLayer report's misaligned index after a skipped element).

There is no downstream guard against this: the model-output marker check in `parseCopilotConflictResolution` only inspects each hunk's own `resolvedContent` string for marker patterns, not the final reassembled file content, so it cannot detect that raw conflict-marker text leaked through reassembly: [3](#0-2) 

The reassembled content is then written straight to disk and staged with no further scanning for stray markers: [4](#0-3) 

### Impact Explanation
This corrupts exactly what the user ends up committing/pushing, without any error or warning surfaced to the user:
- A file can be committed that still contains a literal, unresolved git conflict marker line (`>>>>>>> branch-name`) mixed with the wrong spliced-in content, which is the classic "leftover conflict marker" defect that normally causes broken builds/behavior, except here it happens silently through an AI-assisted flow the user trusted to fully resolve conflicts.
- Because the hunk index desyncs, later legitimate hunks in the same file receive resolutions meant for different hunks, silently swapping in unrelated code into the wrong location of the committed file.
- The attacker only needs to control content on the incoming ("theirs") side of a merge/rebase/cherry-pick that the victim performs with Desktop's "Resolve with Copilot" feature — i.e., a malicious PR branch or fetched remote branch, matching the required unprivileged, remote-content-controlled threat model.

### Likelihood Explanation
The trigger condition is simple to construct: any text resembling `>>>>>>> ` (7 `>` chars + whitespace/EOL) anywhere in the attacker's branch content that ends up between the real `<<<<<<<`/`=======` and the real `>>>>>>>` of a conflicting hunk. This is easy for an attacker who controls a PR/branch to engineer deliberately (e.g., embedding it in a comment or string near code they know is likely to conflict), and it does not require any unusual local access — it only requires the victim to use the Copilot conflict-resolution feature on a merge that includes the attacker's branch.

### Recommendation
Do not rely on "first `>{7}` line after a separator" as the closing marker. Instead:
- Track markers using a strict state machine that requires the exact sequence `<<<<<<<` → (optional base marker) → `=======` → `>>>>>>>` with no interleaving `<<<<<<<`, and reject/treat-as-malformed any block where a candidate closing line is followed later by another `>{7}` or `<{7}` line that better fits git's actual structure.
- Prefer deriving hunk boundaries directly from git's own conflict-region output (e.g. reuse the same parser that already extracts hunks for the prompt context in `copilot-conflict-context.ts`) rather than re-scanning raw text independently in `reassembleResolvedFile`, so extraction and reassembly can never disagree on boundaries.
- After reassembly, scan the final `resolvedContent` for any remaining lines matching `/^<{7}|^={7}$|^>{7}/m` and refuse to write/stage the file (surface it as unresolved) if any are found, closing the gap left by the current per-hunk-only marker check.

### Proof of Concept
1. Craft a malicious branch `evil` where a file `app.ts` includes, near a change that will conflict with `main`, a comment line that is exactly `>>>>>>> `:
   ```ts
   // >>>>>>> legacy note, ignore
   function doThing() { return 2 }
   ```
2. Victim merges `evil` into `main` in Desktop; git produces a real conflict:
   ```
   <<<<<<< HEAD
   function doThing() { return 1 }
   =======
   // >>>>>>> legacy note, ignore
   function doThing() { return 2 }
   >>>>>>> evil
   ```
3. Victim clicks "Resolve with Copilot". Copilot returns one hunk resolution for this file (as validated against the file's real single-hunk conflict count).
4. `reassembleResolvedFile` scans ahead from `<<<<<<< HEAD`, sees `=======` (hasSeparator=true), then hits `// >>>>>>> legacy note, ignore` and matches it as the closing marker, setting `closingIndex` there.
5. The block is spliced with Copilot's resolution content, but `i` jumps past the fake marker line; `function doThing() { return 2 }` and the real `>>>>>>> evil` line are copied through verbatim as normal file content.
6. `_applyCopilotConflictResolutions` writes this to disk and runs `git add`; the user commits, unaware that `app.ts` now contains the literal text `>>>>>>> evil` and duplicated/incoherent function bodies.

Note: I could not fully inspect the conflict-hunk extraction logic in `app/src/lib/copilot-conflict-context.ts` (used to compute the expected hunk count sent to/validated against the model) within the available search results, so I cannot confirm whether that parser uses an equally naive marker scan (which would mean the hunk count sent to Copilot is *also* thrown off, potentially causing `validateResolutionPaths`'s hunk-count check to fail loudly instead of the fully silent corruption described above in every case). The write-path and `reassembleResolvedFile` logic themselves are directly confirmed from the code shown.
