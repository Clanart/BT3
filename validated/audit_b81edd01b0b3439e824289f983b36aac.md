### Title
Unsigned integer underflow in `jsondec_epochdays` produces silently incorrect `Timestamp` values for out-of-range month/day input - (File: `upb/json/decode.c`)

### Summary
The external report describes an unsigned/unguarded subtraction (`18 - decimals()`) that underflows when the operand exceeds the fixed constant, producing an incorrect (here: reverting) result instead of a validated computation. The closest transferable analog in this Protobuf checkout is the RFC3339 `Timestamp` JSON parsing helper `jsondec_epochdays`, which performs `uint32_t` subtraction on attacker-controlled, unvalidated month/day digits (`m - 3`) without first checking that `m`/`d` are within valid calendar ranges, mirroring the "missing bounds check before subtraction" pattern.

### Finding Description
`jsondec_timestamp` parses an RFC3339 string such as `"1972-01-01T01:00:00Z"` from untrusted ProtoJSON input via the public JSON decode API. It extracts `year`, `mon`, `day`, `hour`, `min`, `sec` using `jsondec_tsdigits`, which only parses fixed-width decimal digit groups and does **not** validate that `mon` is in `[1,12]` or `day` is in `[1,31]`: [1](#0-0) 

Those raw values are passed to `jsondec_epochdays`, which computes: [2](#0-1) 

`m_adj = m - 3` is computed in `uint32_t`. If `m` (parsed straight from user-controlled digits, e.g. `"00"`) is `0`, `1`, or `2`, the subtraction underflows and wraps to a huge value near `UINT32_MAX` (e.g. `m=0` → `m_adj = 0xFFFFFFFD`). This is directly analogous to the reported `18 - decimals()` underflow: a fixed constant minus an attacker-influenced value, computed in an unsigned type, with no prior range check.

### Impact Explanation
Unlike the original report (which caused a deployment revert — a hard failure), the underflow here does **not** crash or corrupt memory; `carry`, `adjust`, `y_adj`, `month_days`, and `leap_days` are all still bounded `uint32_t`/`int` arithmetic, and the final `int` return value is computed and used to set the `seconds` field of a `Timestamp` message via `upb_Message_SetFieldByDef`. The consequence is a **data-integrity issue**: malformed/out-of-range timestamp strings (e.g. month `"00"`) are silently accepted and converted into an arbitrary, incorrect `seconds` value instead of being rejected with `jsondec_err(d, "Malformed timestamp")`. This can let an attacker craft ProtoJSON payloads that decode to unexpected timestamp values that downstream application logic (e.g. expiry checks, ordering, cache keys) may trust as valid. This has no memory-safety or crash impact, so it does not rise to the Critical/High tier; if accepted at all, it aligns with the Medium-severity class used in the original report (functional-correctness defect, not RCE/crash/resource-exhaustion).

### Likelihood Explanation
Any ordinary client calling the public ProtoJSON parse API with a `Timestamp`-typed field can trigger this by supplying a syntactically well-formed but semantically invalid date (bad month/day) since no upstream range validation exists before the arithmetic; only the digit-count/format checks in `jsondec_tsdigits` are enforced.

### Recommendation
Validate `mon` (`1`–`12`) and `day` (`1`–`31`, further bounded per month/leap-year) immediately after parsing in `jsondec_timestamp`/`jsondec_tsdigits`, calling `jsondec_err(d, "Malformed timestamp")` before any arithmetic in `jsondec_epochdays` is performed, so invalid input is rejected rather than silently wrapped into an incorrect value.

### Proof of Concept
Feeding the ProtoJSON string `"0000-00-01T00:00:00Z"` (month `00`) into the `Timestamp` well-known-type JSON decoder reaches `jsondec_epochdays(0, 0, 1)`: [3](#0-2) 
`m_adj = 0 - 3` underflows to `4294967293` in `uint32_t`, `carry` becomes `1` (since `m_adj > (uint32_t)m`), and the subsequent `month_days`/`leap_days` computation produces an unvalidated, incorrect epoch-day count that is stored as the message's `seconds` field without any error being raised — no crash occurs, but the parsed value silently diverges from the (invalid) input, an analog of the underflow-driven incorrect-result behavior in the original report. I was not able to fully confirm within the available context whether `jsondec_err` always performs a non-local `longjmp`-style abort for every call site in this file (only partial matches were retrieved before tool access ended), so it is possible other error paths in this function do halt earlier for some malformed inputs; this should be verified against the full `jsondec_err`/`jsondec_iserror`/setjmp implementation before treating this as conclusively reachable in all code paths.

/* jsondec_epochdays(1970, 1, 1) == 1970-01-01 == 0. */
int jsondec_epochdays(int y, int m, int d) {
  const uint32_t year_base = 4800; /* Before min year, multiple of 400. */
  const uint32_t m_adj = m - 3;    /* March-based month. */
  const uint32_t carry = m_adj > (uint32_t)m ? 1 : 0;
  const uint32_t adjust = carry ? 12 : 0;
  const uint32_t y_adj = y + year_base - carry;
  const uint32_t month_days = ((m_adj + adjust) * 62719 + 769) / 2048;
  const uint32_t leap_days = y_adj / 4 - y_adj / 100 + y_adj / 400;
  return y_adj * 365 + leap_days + month_days + (d - 1) - 2472632;
}
