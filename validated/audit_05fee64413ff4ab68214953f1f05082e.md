### Title
Path-traversal via prefix-only check in `resolveWithin()` lets AI-assisted conflict resolution write files outside the repository - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is the app's single guard against writing/reading outside a repository's working directory. Its containment check is a raw string-prefix test (`realResolved.startsWith(realRoot)`) rather than a proper path/segment comparison. Any resolved path whose string representation happens to share the root path as a literal prefix — e.g. a sibling directory named `repo-evil` next to `repo` — passes the check even though it is not actually inside the repository. This guard is the only thing standing between a Copilot-generated conflict-resolution `path` (derived from repository content, including attacker-influenced commit/PR/diff text) and an on-disk `writeFile()` call.

### Finding Description
`_resolveWithin()` computes: [1](#0-0) 

`realResolved.startsWith(realRoot)` is a naive prefix comparison with no trailing-separator boundary check. If `realRoot` is `/Users/bob/repo` and `realResolved` is `/Users/bob/repo-evil/secret.txt`, the `startsWith` call returns `true`, incorrectly classifying a completely different, sibling directory as "inside" the repository. This is the well-known "path prefix without separator" containment bug — structurally the same class of flaw as the report's root cause: a boundary condition (`balance == 0` / `path == root-with-trailing-content`) that a downstream consumer treats as a valid, safe state without it actually satisfying the intended invariant ("token amount is meaningfully computed" / "path is truly inside root").

This guard is relied upon by the AI merge-conflict-resolution write path. `buildConflictContext()` gathers conflicted-file content (including surrounding code, which can contain attacker-authored strings from a hostile branch/PR) and turns it into a prompt: [2](#0-1) 

The model's structured JSON response (`copilotResolutions`, containing a `path` and `resolvedContent` per file) is later consumed without validating that `resolution.path` matches one of the actual conflicted files before writing: [3](#0-2) 

The only safety check applied to `resolution.path` before the write is `resolveWithin(repository.path, resolution.path)`. Because that function's containment test is prefix-only, a `resolution.path` such as `"../repo-secrets/x.sh"` resolves to a directory adjacent to the repository whose name merely starts with the repository directory's name, and `resolveWithin` will return a non-null absolute path outside the actual repo. `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` then writes attacker-influenced content to that location.

### Impact Explanation
A successful bypass results in a silent file write outside the intended repository boundary, driven by content that ultimately originates from a repository the attacker controls (a hostile branch/PR whose merge produces conflicts, plus prompt-injection content that steers the model's chosen resolution path). Depending on what sibling directory exists on the victim's machine (e.g., another of the user's cloned repos, a dotfiles directory, or an app-data directory whose name happens to share the prefix), this can silently corrupt files the user did not intend to touch — matching the "silent corruption of what the user commits" and "file write outside the repo" impact classes.

### Likelihood Explanation
Exploitability is conditional: it requires (a) a merge/rebase/cherry-pick conflict to occur against attacker-influenced content, (b) the Copilot conflict-resolution feature to be enabled and used, (c) the model to be steered (via prompt injection embedded in the conflicted file/PR/commit content) into emitting a `path` value with directory-traversal segments, and (d) an existing sibling directory on disk whose name has the repository directory name as a literal prefix. Condition (d) is the limiting factor — it is not guaranteed but is plausible in real developer environments (multiple related repos with prefix-sharing names, e.g. `app` and `app-internal`, `frontend` and `frontend-e2e`). No local/physical access, admin rights, or leaked credentials are required — only a repository the attacker controls that the victim opens and merges.

### Recommendation
Fix `resolveWithin()` in `app/src/lib/path.ts` to compare path containment using a segment-aware check instead of a raw string prefix, e.g.:
```ts
const rel = relative(realRoot, realResolved)
const isWithin = rel === '' || (!rel.startsWith('..') && !isAbsolute(rel))
```
Additionally, defense-in-depth: in `app-store.ts`'s Copilot-resolution acceptance flow, validate that `resolution.path` is a member of the known set of conflicted file paths (`state.changesState.workingDirectory.files`) *before* calling `resolveWithin`/`writeFile`, rather than only using that set for the "already resolved externally" check.

### Proof of Concept
```ts
import { resolveWithin } from './app/src/lib/path'
import { mkdirSync } from 'fs'

// Simulate a user with two sibling repos: "repo" and "repo-secrets"
mkdirSync('/tmp/poc/repo', { recursive: true })
mkdirSync('/tmp/poc/repo-secrets', { recursive: true })

// A Copilot-emitted resolution.path containing a traversal segment
const attackerPath = '../repo-secrets/malicious-hook.sh'

resolveWithin('/tmp/poc/repo', attackerPath).then(result => {
  // BUG: result is NOT null — it resolves to /tmp/poc/repo-secrets/malicious-hook.sh
  // even though that path is a sibling directory, not inside /tmp/poc/repo.
  console.log(result)
})
```
Running this against the current `_resolveWithin` implementation (`app/src/lib/path.ts:36-72`) returns the sibling path instead of `null`, confirming the prefix-check bypass that the conflict-resolution write path (`app/src/lib/stores/app-store.ts:7233-7258`) relies on for safety.
