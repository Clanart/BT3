### Title
Untrusted witness data injected as authoritative InInstruction lets a co-spender hijack deposits to Serai's Bitcoin external address - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
Analogous to the Xibo SQL injection (attacker-controlled input altering the interpretation of a privileged query to leak/redirect data), Serai's Bitcoin processor treats attacker-controlled witness bytes inside *any* input of a deposit transaction as the authoritative `InInstruction` governing the outputs paid to the multisig. A co-spender in a multi-input transaction (CoinJoin, batched payout, shared-UTXO spend) can inject a `Shorthand`/`RefundableInInstruction` — including an arbitrary `origin` — that is then executed against the victim's deposited funds.

### Finding Description
`Bitcoin::get_outputs` scans each non-coinbase transaction paying a registered key, then calls `extract_serai_data` to populate `output.data` for `OutputType::External` outputs [1](#0-0) . `extract_serai_data` falls back to scanning **every input's witness** when no OP_RETURN output exists: if `witness[len-1]` parses to a script starting with `OP_SHA256 <push> OP_EQUALVERIFY` (checked by `segwit_data_pattern`, which never verifies the pushed hash equals the message hash nor which input carries it), `witness[len-2]` is adopted as `data` [2](#0-1) . Any P2WSH/P2SH-P2WSH co-spender can satisfy this pattern by building a script `OP_SHA256 <sha256(msg)> OP_EQUALVERIFY <their own spend conditions>` and placing `msg` as the final witness stack item.

The injected `data` flows to `instruction_from_output`, which decodes it as `Shorthand` → `RefundableInInstruction` and, critically, lets the injected instruction's `origin` override the transaction-derived `presumed_origin` (`instruction.origin.or(presumed_origin)`) [3](#0-2) . The resulting `InInstructionWithBalance` carries the deposit's full balance (minus `2 * COST_TO_AGGREGATE`) and is dispatched for execution.

### Impact Explanation
An attacker who contributes any SegWit input to a transaction that also pays Serai's external address can fully redirect the deposit: a `transfer` instruction to an attacker Serai address, or an instruction designed to fail so the "refund" goes to the attacker-chosen `origin`. Because `presumed_origin` is taken from `tx.input[0]` only and `origin` in the injected message takes precedence, the actual funder has no protection. This is theft of unminted deposit value — concrete loss of funds via injected attacker bytes, matching the report's class (untrusted parameter injected into a trusted interpretation path → sensitive data/value exfiltration).

### Likelihood Explanation
Requires the victim's deposit transaction to (a) contain at least one attacker-controlled SegWit input, and (b) lack any OP_RETURN output (otherwise output-path wins). CoinJoins (Wasabi/JoinMarket-style), exchanges batching withdrawals, and PayJoin-style constructions routinely produce transactions where an untrusted party supplies inputs while another party's output pays a fixed address. The attacker only needs to know Serai's current external address (public on-chain) and craft a standard P2WSH input — no privileged access, no key material. The witness-script execution constraint (`OP_EQUALVERIFY` must pass) is trivially satisfied since the attacker chooses both `msg` and `sha256(msg)`.

### Recommendation
Restrict the witness-data channel to inputs provably belonging to the depositor: at minimum, only extract data when `tx.input[0]` (the input used for `presumed_origin`) carries the pattern, or require the embedding input to be the one spending to/from a verified origin. Preferably, drop the input-witness path entirely and only honor OP_RETURN data bound to the transaction's own outputs, since the input-witness heuristic cannot authenticate *who* embedded the message. Additionally, verify `sha256(witness[len-2])` equals the pushed hash inside `segwit_data_pattern`, and consider ignoring an instruction-supplied `origin` in favor of `presumed_origin` when the data path is unauthenticated.

### Proof of Concept
1. Obtain Serai's current Bitcoin external address (public P2TR script).
2. A victim constructs (or is tricked into co-signing, via CoinJoin/PayJoin/batched spend) a transaction `tx` with: an output paying `>= DUST` to Serai's external script, no OP_RETURN output, and the attacker's P2WSH input.
3. Attacker's input uses witness script `OP_SHA256 <sha256(msg)> OP_EQUALVERIFY <attacker pubkey> OP_CHECKSIG`, with witness `[sig, msg, script]` where `msg = Shorthand::Raw(RefundableInInstruction { origin: Some(attacker_addr), instruction: transfer-to-attacker })`.
4. `get_outputs` scans the block: `scan_transaction` matches the Serai output, `extract_serai_data` picks up `msg` from the attacker's input, `instruction_from_output` applies `origin = attacker_addr` and the deposit balance.
5. The injected instruction executes against the victim's deposited funds — e.g., a transfer crediting the attacker — while the victim only authorized a plain deposit.
