### Title
Cached FROST preprocess seed never invalidated — second `sign` reuses nonces under a different preprocess set, leaking the validator's secret share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug pattern is "use of a resource after its one-shot lifetime ended, because a validity flag (`PMU_F_RESERVED`) was never checked before re-reading freed buffers." Serai's `SigningProtocol` has the exact same shape: `preprocess_internal` stores a `CachedPreprocess` seed in `CachedPreprocesses` keyed by `(b"DkgConfirmer", attempt)`, and `from_cache` regenerates the identical nonces every time it runs. Nothing marks the seed as consumed after `machine.sign(...)`. `DkgConfirmer::share` and `DkgConfirmer::complete` both funnel through `share_internal` → `preprocess_internal`, so `sign` is executed more than once per attempt with the same nonces. If the `preprocesses` map passed to `complete` differs from the set used when `share` ran, the same nonce is bound into a different FROST transcript (different `included` set ⇒ different binding factors `rho` and different challenge), producing a second valid signature share that — combined with the first, both published on-chain — permits recovery of the validator's secret share.

### Finding Description
`preprocess_internal` writes the (XOR-obfuscated) ChaCha20 seed to `CachedPreprocesses` once and then reloads it on every call, building a fresh `AlgorithmSignMachine` via `from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)`, which deterministically regenerates the same `nonces` and `commitments` each time (`crypto/frost/src/sign.rs:121-144`). The cache entry is never deleted or marked used after `sign` consumes it (`coordinator/src/tributary/signing_protocol.rs:137-145`). The file's own header acknowledges the hazard: nonce reuse happens if "the received nonce commitments ... would have to be distinct and sign would have to be called again" (lines 34-35). `DkgConfirmer::complete` unconditionally re-invokes `share_internal` — i.e., calls `sign` again — using whatever `preprocesses` map the caller supplies at completion time (lines 321-326), which need not equal the map used when `share` was first invoked. Inside `AlgorithmSignMachine::sign`, the `included` set is built from `preprocesses.keys()`, so a differing set yields a different `ThresholdView`, different per-participant binding factors, and a different challenge over the same nonce commitments (`crypto/frost/src/sign.rs:290-318`).

### Impact Explanation
Two signature shares emitted under the same nonce but different transcripts let any on-chain observer solve the linear system for the signer's FROST secret share (standard nonce-reuse / ROS-style recovery). Since this protocol signs with the validators' MuSig root-of-trust keys, recovery of a sufficient subset of secret shares compromises the validator set's signing key — complete key share recovery with publicly broadcast data.

### Likelihood Explanation
The shares are published on-chain, so the resulting shares are publicly observable. The trigger is `complete` being reached with a different preprocess set than `share` — e.g., additional validators' `DkgConfirmer` preprocesses finalized after the share transaction but before completion, or a rebuilt coordinator replaying with a superset. This does not require a malicious validator; honest timing differences across blocks suffice if the preprocess set is not pinned identically between the two entry points. The gap I could not fully verify is whether the upstream handler guarantees the identical `preprocesses` map on both calls; the safety argument in the file relies on BFT-finalized messages being identical, but `complete` re-reads whatever map it is handed rather than the recorded set used at `share` time, and there is no consumed-flag enforcement analogous to `PMU_F_RESERVED`.

### Recommendation
Delete `CachedPreprocesses` (or store a consumed marker) when `share_internal` first calls `sign`, and make `preprocess_internal` fail if the seed was already consumed — the exact analog of checking `PMU_F_RESERVED` before touching the SDBs. Additionally, pin the `preprocesses`/`included` set for an attempt at first `sign` (persist it in the DB under the same context) and have `complete` reuse that recorded set rather than caller-supplied data.

### Proof of Concept
Conceptual (state machine, no code execution available):
1. Attempt `a` begins; `DkgConfirmer::share(P_A, key_pair)` stores seed `s` in `CachedPreprocesses` and produces share `σ_1 = d + b·e + λ_A·x·c_A` over included set `I_A`, broadcast on-chain.
2. `DkgConfirmer::complete(P_B, key_pair, shares)` is invoked with `P_B ⊋ P_A`; `share_internal` reloads `s`, regenerates identical `d, e`, and `sign` produces `σ_2 = d + b·e + λ_B·x·c_B` over included set `I_B ≠ I_A`, also emitted on-chain.
3. Observer computes `x = (σ_1 − σ_2) / (λ_A·c_A − λ_B·c_B)` (with `λ` and `c` publicly derivable from the transcripts), recovering the validator's secret share.
