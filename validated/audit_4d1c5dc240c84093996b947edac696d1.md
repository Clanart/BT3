### Title
Missing reverse-mapping check in EVM↔Sei address association allows overwriting an existing mapping without dropping it, orphaning state and risking a chain halt - ([File: x/evm/keeper/address.go])

### Summary
The CVE describes a class of bug where a resource holding an existing reference (`skb->_skb_refdst`) is overwritten by a "no-ref" setter (`skb_dst_set_noref`) without first dropping/checking the pre-existing reference, leaking it and corrupting invariants that downstream code assumes hold. The analogous pattern in sei-chain is `Keeper.SetAddressMapping`, which unconditionally overwrites both halves of the EVM↔Sei bidirectional address mapping without verifying (or clearing) any pre-existing reverse mapping for the EVM address being (re)associated, and its only caller-side guard checks solely the Sei-address direction.

### Finding Description
`SetAddressMapping` writes both directions of the mapping unconditionally: [1](#0-0) 

The public entrypoints that call into this (the `associate`/`associatePubKey` precompile methods) only guard against re-association from the Sei-address side: [2](#0-1) 

They never check `GetSeiAddress(ctx, evmAddr)` to see if `evmAddr` is already reverse-mapped to a *different* Sei address before calling `SetAddressMapping`. If such a stale/other reverse mapping exists, `SetAddressMapping` silently overwrites `EVMAddressToSeiAddressKey(evmAddr)` to point at the new Sei address while leaving the old Sei address's `SeiAddressToEVMAddressKey` entry dangling and pointing back at `evmAddr` — an asymmetric, orphaned mapping, exactly analogous to overwriting `skb->_skb_refdst` without dropping the previous reference.

The codebase's own comments confirm this exact bug class is known to be catastrophic when it occurs: the EIP-7702 `SetCode` authority path was specifically hardened against it in the ante handler, because "SetCode creates a mutable direct-cast EVM->Sei mapping that a later associatePubKey call can remap, orphaning any staking/distribution state created under the direct-cast identity (which can then halt the chain via the distribution validator-removal hook)": [3](#0-2) [4](#0-3) 

That fix (`AuthorityToPreAssociate` / `associateAuthorizationAuthorities`) is scoped only to EIP-7702 authorization authorities inside the ante pipeline: [5](#0-4) 

but the general-purpose, directly reachable `associate`/`associatePubKey` precompile methods (and their `AssociationHelper.AssociateAddresses` call chain, plus every legacy precompile version `v575`…`v640`) retain the same one-sided check pattern: [6](#0-5) [7](#0-6) 

### Impact Explanation
If a stale reverse mapping for an EVM address exists (created via any path prior to a legitimate `associate`/`associatePubKey` call for that same EVM address, e.g. a previously-established direct-cast/other mapping), `SetAddressMapping` will silently overwrite the forward mapping while leaving the old Sei address's mapping entry stale. This breaks the invariant relied upon elsewhere (e.g. `CanAddressReceive`, balance/state routing by associated address) and can leave state (balances, staking delegations, distribution records) permanently attached to an address that is no longer reachable through the canonical mapping — a form of fund/state freezing. Per the code's own documented failure mode, this class of asymmetric mapping can also trigger a panic in the distribution module's validator-removal hook, which would halt block production (a chain halt), matching the CVSS 7.5/High severity of the source CVE (memory/state corruption from an un-dropped stale reference leading to an assertion/crash).

### Likelihood Explanation
The precompile is public and reachable by any unprivileged EVM caller (`0x0000...1004`, methods `associate`/`associatePubKey`) — no privileged role required. The precompile checks only `GetEVMAddress(ctx, seiAddr)` and never `GetSeiAddress(ctx, evmAddr)` before calling `SetAddressMapping`, so the one-sided guard is structurally present for every `associate`/`associatePubKey` call site and every legacy version examined. Exploitability depends on the existence of a pre-existing stale reverse mapping for the target EVM address at call time; the codebase's own hardening comments confirm at least one concrete way such a mismatch already arises in practice (the direct-cast mapping created before an authoritative pubkey-based association), which was significant enough to warrant a dedicated ante-level fix for the SetCode case only.

### Recommendation
In `SetAddressMapping` (and/or in `AssociationHelper.AssociateAddresses` / the `associateAddresses` precompile handler), check `GetSeiAddress(ctx, evmAddress)` before writing; if a different Sei address is already reverse-mapped to `evmAddress`, either reject the association or explicitly clear the stale `SeiAddressToEVMAddressKey` entry for the old Sei address (and migrate/validate any state tied to it) before installing the new mapping, mirroring the already-implemented `AuthorityToPreAssociate` guard so all association entrypoints (not just the EIP-7702 ante path) enforce the same one-to-one bidirectional invariant.

### Proof of Concept
Not independently reproduced with a runnable transaction trace within the scope of this review; the finding is built on: (1) the asymmetric-overwrite code in `SetAddressMapping`, which unconditionally writes both mapping keys with no existence check on the reverse direction; (2) the one-sided guard in `associateAddresses` (`precompiles/addr/addr.go` and all `precompiles/addr/legacy/*` versions) that checks only the Sei-address-to-EVM direction; and (3) the codebase's own explicit acknowledgment, in comments and dedicated tests (`app/setcode_authority_test.go`, `x/evm/ante/preprocess_test.go`), that exactly this "overwrite without checking/dropping the existing reverse mapping" scenario is reachable and capable of orphaning staking/distribution state and halting the chain via the distribution validator-removal hook — for which a fix exists only on the narrower EIP-7702 `SetCode` authority path, not for the general `associate`/`associatePubKey` precompile entrypoints. Full confirmation of a concrete transaction sequence producing the stale reverse mapping outside the already-patched SetCode path was not completed due to tool/iteration limits; this should be verified with a live test harness before treating it as fully confirmed.

// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
