### Title
Duplicate `withdrawal_utxo` registration lets `Verifier::update_finalized_payouts` bind one real payout to two withdrawal rows, letting an operator claim reimbursement for a vault it never fronted - ([File: core/src/verifier.rs])

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` joins the `withdrawals` table to `bitcoin_syncer_spent_utxos` purely on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`. If two withdrawal rows (`idx_a`, `idx_b`, each tied to a distinct `move_to_vault_txid`/deposit) end up with the identical `withdrawal_utxo_txid`/`vout`, this join returns both `idx` values mapped to the single real `spending_txid`. `Verifier::update_finalized_payouts` then parses that one payout transaction once and calls `Database::update_payout_txs_and_payer_operator_xonly_pk` with the same `(payout_txid, operator_xonly_pk, block_hash)` for both rows, even though only one of the two vaults was actually drained by a fronted payout.

### Finding Description
The binding that should hold is: `payout_payer_operator_xonly_pk(idx_a)` is set **iff** the operator actually fronted a payout spending `idx_a`'s registered `withdrawal_utxo`, and likewise independently for `idx_b`. This binding is broken because the write path derives operator/txid/blockhash purely from the shared UTXO, not from a per-deposit fronting proof.

Code path:
1. `Database::update_withdrawal_utxo_from_citrea_withdrawal` (`core/src/database/verifier.rs:108-135`) unconditionally overwrites `withdrawal_utxo_txid`/`vout` for a given `idx` with no uniqueness constraint against other `idx` rows — the `withdrawals` schema (`core/src/database/schema.sql:269-281`) only has a primary key on `idx`, no unique constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`.
2. `Verifier::update_citrea_deposit_and_withdrawals` (`core/src/verifier.rs:2248-2262`) writes whatever `(idx, withdrawal_utxo_outpoint)` pairs `CitreaClientT::collect_withdrawal_utxos` returns from the Citrea bridge contract's `withdrawalUTXOs` mapping — an attacker fully controls the UTXO bytes for their own `withdraw()` calls, so two distinct withdrawal indices from two distinct deposits can be registered with the exact same physical outpoint (the premise from the referenced prior scenario).
3. `Database::get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) joins `withdrawals w` to `bitcoin_syncer_spent_utxos bsu` on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`. Since the UTXO can only be spent once on L1, this produces `(idx_a, txid)` and `(idx_b, txid)` — both idx rows bound to the same single real spend.
4. `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) loops over these `(idx, payout_txid)` pairs, looks up the payout tx exactly once per idx in `block_cache`, parses the same OP_RETURN operator pubkey, and pushes `(idx_a, txid, op_pk, block_hash)` and `(idx_b, txid, op_pk, block_hash)` into `payout_txs_and_payer_operator_idx`.
5. `Database::update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`) bulk-updates both rows via a `VALUES`/`FROM` join on `idx`, writing identical `payout_txid`, `payout_payer_operator_xonly_pk`, `payout_tx_blockhash` into both `idx_a` and `idx_b`.

No existing guard rejects this: `get_payout_txs_for_withdrawal_utxos` has no dedup on UTXO; `update_payout_txs_and_payer_operator_xonly_pk` has no check that a `payout_txid` isn't already assigned to another idx; `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) only checks that the OP_RETURN operator pubkey matches the kickoff's operator and that the committed blockhash matches — both of which are now identically true for `idx_a` and `idx_b` since the DB row for each carries the same (correct-looking) values.

Downstream, `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) calls `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`), which selects unhandled rows purely by `payout_payer_operator_xonly_pk` — it will surface `idx_a` and, on a subsequent poll, `idx_b`, both now attributed to the operator. For each, `Operator::handle_finalized_payout` (`core/src/operator.rs:839-885`) starts an independent kickoff/round reimbursement flow for that deposit's vault, and `send_asserts`'s check (`core/src/operator.rs:1275-1295`) that `payout_op_xonly_pk == kickoff_data.operator_xonly_pk` will pass for both, because the DB was corrupted to say so for both.

### Impact Explanation
The operator is credited and can drive full reimbursement (kickoff → round → Reimburse tx paying out of collateral/round funds) for **two** deposit vaults (`idx_a` and `idx_b`) while having fronted the withdrawal payout only **once**. This is "an operator reimbursed for a payout it never funded" (Critical) — the second reimbursement is unbacked by any real BTC fronting, effectively minting free reimbursement value at the expense of the round's collateral/other participants. The bug is mechanical (SQL join keyed only on UTXO identity) and repeats for every pair of deposits an attacker manages to register with a colliding `withdrawal_utxo`, so the blast radius scales with however many duplicate-UTXO withdrawal registrations the attacker can create across deposits/operators.

### Likelihood Explanation
Requires the precondition (from the referenced prior scenario) that two distinct Citrea withdrawal indices can be registered with an identical `withdrawal_utxo_txid`/`vout` — achievable by an unprivileged Citrea user calling `withdraw()` twice with the same UTXO bytes for two different deposits, since neither `withdrawalUTXOs` (as read by `collect_withdrawal_utxos`) nor `update_withdrawal_utxo_from_citrea_withdrawal` enforce uniqueness. Once that precondition holds, exploitation is fully automatic (no additional signatures, keys, or timing tricks needed) — the bug fires the next time the verifier processes the block containing the single real payout transaction. Any cooperating or unwitting operator (the one who fronted the single real payout) benefits without further action; the flow is deterministic and repeatable across further deposit pairs.

### Recommendation
Change `Database::get_payout_txs_for_withdrawal_utxos` / `update_payout_txs_and_payer_operator_xonly_pk` to enforce a strict 1:1 binding between a withdrawal UTXO and a single `idx`: add a uniqueness constraint (or application-level check) preventing two `withdrawals` rows from sharing the same `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, and/or make `update_payout_txs_and_payer_operator_xonly_pk` reject writes when the same `payout_txid` would be assigned to more than one `idx`. Ideally, reject the duplicate registration itself at `update_withdrawal_utxo_from_citrea_withdrawal` time so the ambiguous state can never enter the DB.

        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors

                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),

                    BlockHashDB(*block_hash),

            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

            converted_values.into_iter(),

                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

        Ok(())
    }
