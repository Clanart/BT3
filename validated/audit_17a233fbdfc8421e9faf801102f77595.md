### Title
Deep-link `branch` parameter bypasses ref-name validation and can smuggle a `git checkout` command-line flag - ([File: app/src/lib/sanitize-ref-name.ts])

### Summary
GitHub Desktop's `x-github-client://openRepo/...` deep link accepts a `branch` query parameter that is checked out automatically once the target repository is opened/cloned. The only gate applied to this attacker-controlled string is `testForInvalidChars` from `app/src/lib/sanitize-ref-name.ts`, whose regex only rejects control characters, spaces, and a handful of Git ref-format-illegal characters (`~^:?*[\|"<>`, `@{`, leading/trailing dots, `.lock` suffix, trailing slash). It does **not** reject a leading `-`/`--`, so a value such as `--upload-pack=...` or any other Git option-looking string is treated as a "valid" branch name and forwarded unmodified to the checkout code path.

### Finding Description
`parseAppURL` in `app/src/lib/parse-app-url.ts` extracts the `branch` query parameter and only rejects it when:
- it fails the `/^pr\/\d+$/` pattern (only when `pr` is also present), or
- `testForInvalidChars(branch)` returns true. [1](#0-0) 

`testForInvalidChars` uses `invalidCharacterRegex` which purposefully mirrors Git's `check-ref-format` illegal-character set — it says nothing about a leading hyphen: [2](#0-1) 

Note that the companion sanitizer `sanitizedRefName` (used elsewhere for names *generated* by the app) explicitly strips a leading `-`/`+` (`.replace(/^[-\+]*/g, '')`), which shows the maintainers are aware leading dashes are dangerous — but that stripping step is never applied to the deep-link `branch` value; only the weaker `testForInvalidChars` check gates it.

The accepted `branch` string then flows to `Dispatcher.openRepositoryFromUrl` → `openBranchNameFromUrl` → `checkoutLocalBranch`: [3](#0-2) 

Compare this to `app/src/lib/git/clone.ts`, where the maintainers deliberately insert a `--` end-of-options separator before the untrusted `url` argument specifically to prevent it from being interpreted as a Git command-line flag: [4](#0-3) 

I was unable to confirm within the remaining tool budget whether `checkoutLocalBranch`'s underlying `git checkout <branch>` invocation applies the same `--` end-of-options guard that `clone.ts` uses; if it does not, an attacker-supplied `branch` value beginning with `-`/`--` would be parsed by `git` as an option rather than a ref name (e.g. values resembling `--upload-pack=...`, `-c`, or other checkout/branch flags), corrupting the invocation with attacker-controlled option data. This is the exact broken invariant: the deep-link parser's job is to guarantee that everything reaching the git subprocess is a syntactically safe *ref name*, but its allow-list (`testForInvalidChars`) is weaker than the app's own definition of a safe ref name (`sanitizedRefName`) and does not exclude leading dashes.

### Impact Explanation
If the checkout invocation lacks a `--` separator (as `clone.ts` uses defensively), a crafted deep link clicked by a user could inject arbitrary Git command-line options into the `git checkout`/branch-resolution invocation running against the freshly opened/cloned repository — potentially altering remote-operation behavior (e.g. options affecting `upload-pack`/protocol handling) without the user's awareness, i.e. silent corruption of the operation the user believes they triggered by clicking a normal-looking "Open in Desktop" link. This matches the "attacker controls a link/deep link the user clicks" and "silent corruption" impact categories.

### Likelihood Explanation
Medium: the deep-link handler is reachable purely by getting a user to click a `x-github-client://openRepo/<url>?branch=...` link (e.g., embedded in a GitHub PR/issue comment or webpage) — no local access, credentials, or malware needed. The existing tests confirm the app already tries to filter "invalid" branch names (e.g. `%3C%3E`) but none of the test cases exercise a leading-dash value, suggesting this specific bypass is untested: [5](#0-4) 

### Recommendation
- In `app/src/lib/parse-app-url.ts`, reject (or run through `sanitizedRefName`/reject-if-different) any `branch` value that starts with `-`, in addition to the existing `testForInvalidChars` check.
- Independently, ensure every git invocation that consumes a `branch`/ref value derived from untrusted input (deep links, GitHub API PR data, etc.) uses the `--` end-of-options separator before the ref argument, the same defensive pattern already used in `app/src/lib/git/clone.ts`.

### Proof of Concept
1. Attacker crafts a link: `x-github-client://openRepo/https://github.com/some/repo?branch=--upload-pack%3Dtouch%2Ftmp%2Fpwned`
2. `parseAppURL` decodes `branch` to `--upload-pack=touch /tmp/pwned`; `testForInvalidChars` returns `false` (no character in the illegal set is present), so the value is accepted as `IOpenRepositoryFromURLAction.branch`.
3. User clicks the link; Desktop registers itself as the handler for `x-github-client://`, invokes `handleAppURL` → `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` → `checkoutLocalBranch` with the attacker-controlled string.
4. If the underlying git invocation does not prefix the ref with `--`, git parses `--upload-pack=...` as an option rather than a branch name — this is unverified beyond `parse-app-url.ts`/`sanitize-ref-name.ts` due to tool-call limits and should be confirmed by inspecting the checkout implementation reached from `app/src/ui/dispatcher/dispatcher.ts` lines 1975-1996.

```typescript
// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
```

```typescript
  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
```
