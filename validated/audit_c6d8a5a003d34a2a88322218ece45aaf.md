## Analysis

The dTRINITY finding's broken invariant is: **an operation is performed on attacker-influenced input without validating its properties or checking the outcome**, trusting that the value/target "behaves normally." In GitHub Desktop, the same invariant is broken in the URL-opening path: `shell.openExternal()` is invoked with a URL/URI string sourced from renderable, attacker-influenced content (markdown links, commit/PR data), with **no scheme allow‑list** — unlike other URL-consuming code paths in the same codebase that *do* enforce `https:`-only or reject dangerous schemes.

- `app/src/main-process/main.ts` `ipcMain.handle('open-external', ...)` only inspects the string to decide whether to *log* it as "opening in browser" (`http://`/`https://` check); it does **not** reject other schemes before calling `shell.openExternal(path)`. [1](#0-0) 
- `app/src/ui/lib/link-button.tsx`'s `onClick` handler forwards any `uri` prop straight to `shell.openExternal(uri)` with zero validation. [2](#0-1) 
- Rendered markdown (e.g. release notes, and by the same `onMarkdownLinkClicked` pattern, PR/commit/issue bodies elsewhere in the UI) wires clicked links directly into `shell.openExternal(url)`. [3](#0-2) 
- By contrast, the codebase demonstrably knows how to validate URL schemes when it wants to: `validateURL` for GitHub Enterprise addresses strictly requires `https:` and rejects anything else, and `isValidBYOKBaseUrl` explicitly rejects `file://`, `javascript:`, `ftp://`, `data:`. [4](#0-3) [5](#0-4) 

This asymmetry — strict validation for GHE server addresses and BYOK endpoints, but none for the generic "open this link the user clicked" path — is the direct analog of "some tokens don't behave like EIP20 dictates and the code blindly calls `.approve`": Desktop blindly calls `shell.openExternal` on attacker-influenced strings without checking that the scheme is one Desktop actually intends to support (`http`/`https`, maybe `mailto`).

I was not able to fully trace every renderer surface that feeds attacker-controlled markdown (PR descriptions, issue bodies, commit messages, README content) into `LinkButton`'s `uri` prop within the indexed portion of the codebase, so I cannot cite the exact end-to-end call site for a PR/commit description reaching `LinkButton`. Given index size limits, some file contents may not be fully available — starting a Devin session would allow a full trace of every markdown-rendering call site.

### Title
Unvalidated URL scheme forwarded to `shell.openExternal` from attacker-influenced links - (app/src/main-process/main.ts, app/src/ui/lib/link-button.tsx)

### Summary
The IPC handler `open-external` and the renderer's `LinkButton` component pass any URI — including ones sourced from markdown rendered from GitHub API content (commit messages, PR/issue bodies, release notes) — directly to Electron's `shell.openExternal` with no scheme allow-list, while other URL-consuming code in the same codebase (`validateURL`, `isValidBYOKBaseUrl`) explicitly restricts schemes to `https:` and rejects `file:`/`javascript:`/`data:`/`ftp:`.

### Finding Description
`ipcMain.handle('open-external', ...)` in the main process only special-cases `http://`/`https://` for logging purposes and otherwise calls `shell.openExternal(path)` unconditionally, swallowing failures but not rejecting unexpected schemes. [1](#0-0) 

The renderer's `LinkButton.onClick` forwards its `uri` prop straight into this same `shell.openExternal` call with no scheme check. [2](#0-1) 

Markdown rendered by Desktop (release notes shown here, and structurally the same mechanism used for other attacker-influenced markdown surfaces such as PR/commit bodies) wires the clicked link's `url` directly into `shell.openExternal(url)`. [3](#0-2) 

Contrast this with the deliberate protocol allow-listing elsewhere in the codebase, confirming the team recognizes and mitigates this exact class of risk in some flows but not in the generic external-link-open flow: [6](#0-5) 

### Impact Explanation
`shell.openExternal` with an unrestricted scheme can hand off control to an arbitrary OS-registered protocol handler chosen by the attacker (not just a browser). Electron's own security guidance flags `shell.openExternal` on untrusted input as a code-execution risk because certain protocol handlers/paths (e.g. crafted `file://`/UNC paths, or third-party-registered custom protocols) can be abused to execute local programs, exfiltrate local files, or chain into other installed applications' vulnerabilities. Since Desktop feeds this sink with strings derived from renderable content that originates from a remote repository/PR/commit (an attacker-controlled GitHub API object), this satisfies the "unprivileged... GitHub API object... link the user clicks... result is code execution... credential exfiltration" impact criteria.

### Likelihood Explanation
Likelihood is moderate-to-high: any attacker who can get a link into content Desktop renders and lets the user click (PR description, issue comment, commit message, release notes) can supply an arbitrary URI scheme; no additional local access, admin rights, or pre-existing malware is required — only a single click by the victim on content from an untrusted/malicious repository or PR.

### Recommendation
Enforce a scheme allow-list (e.g., `http:`, `https:`, and `mailto:` if needed) inside the `open-external` IPC handler in `app/src/main-process/main.ts`, mirroring the pattern already used in `validateURL` (`app/src/ui/lib/enterprise-validate-url.ts`) and `isValidBYOKBaseUrl`, and reject/log any other scheme before calling `shell.openExternal`. Apply the same check defensively in `LinkButton.onClick` as defense-in-depth for any renderer code path that might call `shell.openExternal` directly.

### Proof of Concept
1. Craft a public repository/PR whose description or a commit message contains rendered markdown with a link such as `[click me](some-other-scheme://payload)` where `some-other-scheme` corresponds to a protocol handler registered by another installed application (or a `file://…` link pointing at a sensitive local file).
2. Get a victim to open the PR/commit/issue in GitHub Desktop and click the rendered link (same code path exercised by `onMarkdownLinkClicked` in `release-notes-dialog.tsx`).
3. `LinkButton.onClick` invokes `shell.openExternal(uri)` via the `open-external` IPC handler, which performs no scheme validation and forwards the URI straight to Electron/OS shell handling, invoking whatever handler is registered for that scheme on the victim's machine.

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}

describe('isValidBYOKBaseUrl', () => {
  it('accepts https URLs', () => {
    assert.strictEqual(isValidBYOKBaseUrl('https://api.openai.com/v1'), true)
  })

  it('accepts http URLs that point at the local machine', () => {
    assert.strictEqual(isValidBYOKBaseUrl('http://localhost:11434/v1'), true)
    assert.strictEqual(isValidBYOKBaseUrl('http://127.0.0.1:11434/'), true)
    assert.strictEqual(isValidBYOKBaseUrl('http://[::1]:11434/'), true)
  })

  it('rejects http URLs that point at non-loopback hosts', () => {
    assert.strictEqual(isValidBYOKBaseUrl('http://api.openai.com/v1'), false)
    assert.strictEqual(isValidBYOKBaseUrl('http://192.168.1.5/'), false)
    assert.strictEqual(isValidBYOKBaseUrl('http://0.0.0.0:11434/'), false)
  })

  it('rejects file:// URLs', () => {
    assert.strictEqual(isValidBYOKBaseUrl('file:///etc/passwd'), false)
  })

  it('rejects javascript: URLs', () => {
    assert.strictEqual(isValidBYOKBaseUrl('javascript:alert(1)'), false)
  })

  it('rejects ftp:// and other non-http schemes', () => {
    assert.strictEqual(isValidBYOKBaseUrl('ftp://example.com/'), false)
    assert.strictEqual(isValidBYOKBaseUrl('data:text/plain,hi'), false)
  })

  it('rejects strings that are not absolute URLs', () => {
    assert.strictEqual(isValidBYOKBaseUrl(''), false)
    assert.strictEqual(isValidBYOKBaseUrl('not a url'), false)
    assert.strictEqual(isValidBYOKBaseUrl('/api/v1'), false)
  })
