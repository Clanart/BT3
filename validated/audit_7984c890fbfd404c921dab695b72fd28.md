## Title
Unbounded Python recursion in wallet offer/puzzle-driver matching allows a malicious offer or spend bundle to crash the wallet via stack exhaustion - (File: chia/wallet/outer_puzzles.py, chia/wallet/trading/offer.py)

### Summary
The reported Xenstore CVE-2022-42321 is a stack-exhaustion bug: recursive tree processing of attacker-controlled, arbitrarily-deep nested data with no depth limit crashes the process. The Chia wallet's outer-puzzle "driver" dispatch (`match_puzzle`/`get_inner_puzzle`/`get_inner_solution`/`construct`/`solve` in `chia/wallet/outer_puzzles.py`) walks nested puzzle layers (CAT-in-CAT, ownership-in-CAT, CR-in-CAT, singleton-in-singleton, etc.) using genuine Python function recursion with no depth bound, and this code is invoked while merely inspecting an attacker-supplied offer file (`Offer._get_offered_coins()` in `chia/wallet/trading/offer.py`).

### Finding Description
Each outer-puzzle driver (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`) implements `match()`, `get_inner_puzzle()`, and `get_inner_solution()` by recursively calling back into itself/`self._match`/`self._get_inner_puzzle`/`self._get_inner_solution` whenever a curried "also" layer is present: [1](#0-0) [2](#0-1) [3](#0-2) 

The top-level dispatcher wires these callbacks together, and each layer's `mod` is uncurried and inspected with no bound on nesting depth: [4](#0-3) 

`UnknownPuzzle` uncurries a `Program` on demand via `uncurry_puzzle`, computing `mod`/`curried_args`, so an attacker can construct a puzzle reveal that is deeply nested only in the "outer" wrapper layers (cheap to construct because currying is just cons-cell nesting, not CLVM execution): [5](#0-4) 

This recursive matching machinery is reached simply by loading/inspecting an offer: `Offer.__post_init__` and `_get_offered_coins()` call `match_puzzle`, `get_inner_puzzle`, and `get_inner_solution` directly on `parent_spend.puzzle_reveal` taken from the attacker-supplied `WalletSpendBundle` inside the offer, with no depth guard before recursing: [6](#0-5) 

By contrast, the codebase explicitly recognizes this class of bug and defends against it elsewhere — `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py` is deliberately implemented iteratively "so we don't have to worry about blowing out the python stack," and `chia/data_layer/data_store.py`'s deep-tree code has explicit `RecursionDepthExceededError` handling for the same reason. The outer-puzzle driver dispatch, however, does not have an equivalent protection: [7](#0-6) 

### Impact Explanation
A wallet user who receives or opens a maliciously crafted offer file (or an attacker who gets a wallet to process a crafted `SpendBundle`, e.g. via `get_offer_summary`/`take_offer`/`push_tx` code paths that call into `Offer`) can trigger unbounded Python recursion proportional to the number of nested asset/outer-puzzle layers the attacker chooses to curry into a single coin's puzzle reveal. Because CPython has a fixed default recursion limit, sufficiently deep nesting raises `RecursionError`, and depending on how deep and how much stack is consumed per frame, this can also raise a hard, uncatchable stack overflow (segfault) in the underlying C stack rather than a catchable Python exception. Either outcome halts wallet transaction/offer processing for that request and can crash the wallet service (a spend/offer-triggered transaction-processing halt), matching the "Accept" criteria in the report (spend-triggered transaction-processing halt).

### Likelihood Explanation
Constructing the malicious puzzle reveal is cheap for the attacker — nested currying is just building nested cons-cell structures, not running CLVM, so thousands of "also" layers can be embedded in a modestly sized offer file. No signature or on-chain state is required; only that the victim wallet inspects the offer (which normal wallet UX does automatically, e.g. to show what is offered before a user decides whether to accept). This makes the likelihood high for any wallet operator who accepts offer files from untrusted counterparties, which is the exact usage model for the Offer/Trade feature.

### Recommendation
Convert the recursive `match`/`get_inner_puzzle`/`get_inner_solution`/`construct`/`solve` traversal in `chia/wallet/outer_puzzles.py` and each outer-puzzle driver into an iterative loop (mirroring the pattern already used in `sha256_treehash`), or impose an explicit maximum nesting-depth check before recursing and reject/skip puzzle reveals that exceed it, similar to the `RecursionDepthExceededError` guard used in `chia/data_layer/data_store.py`. Apply the same depth bound wherever offer/spend-bundle puzzle reveals are parsed before any driver matching occurs (`Offer.__post_init__`, `Offer._get_offered_coins`).

### Proof of Concept
Conceptually (cannot execute code in this environment, so this is a description of the exploit construction):
1. Build an innermost puzzle `p0` (e.g. `Program.to(1)`).
2. Repeatedly wrap it N times (N in the thousands) using `construct_cat_puzzle(CAT_MOD, tail, p_i)` or `create_cr_layer`/`puzzle_for_ownership_layer`, i.e. `p_{i+1} = construct_cat_puzzle(CAT_MOD, tail, p_i)`, to create a puzzle with N nested outer-puzzle layers.
3. Place this puzzle as the `puzzle_reveal` of a single `CoinSpend` inside an `Offer`'s `WalletSpendBundle`, and serialize/export the offer file.
4. Have a victim wallet call `Offer.from_bytes(...)` (or any flow that constructs an `Offer`, e.g. `TradeManager.get_offer_summary`), which triggers `__post_init__` → `_get_offered_coins()` → `match_puzzle(parent_puzzle)`, recursing N times through `CATOuterPuzzle.match` → `self._match(...)` for each layer, exhausting the Python call stack and raising `RecursionError` or crashing the process.

def match_puzzle(puzzle: UnknownPuzzle) -> PuzzleInfo | None:
    for driver in driver_lookup.values():
        potential_info: PuzzleInfo | None = driver.match(puzzle)
        if potential_info is not None:
            return potential_info
    return None


def construct_puzzle(constructor: PuzzleInfo, inner_puzzle: Program) -> Program:
    return driver_lookup[AssetType(constructor.type())].construct(constructor, inner_puzzle)


def solve_puzzle(constructor: PuzzleInfo, solver: Solver, inner_puzzle: Program, inner_solution: Program) -> Program:
