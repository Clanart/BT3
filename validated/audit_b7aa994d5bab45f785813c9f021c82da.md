### Title
First staker of a newly deployed `PublicDelegation` vault can inflate share price and steal from subsequent stakers - (File: contracts/bindings/publicdelegation/PublicDelegation.go)

### Summary
`PublicDelegation` is an ERC4626-style share-vault deployed per Consensus Node (CN) via `CnStakingV4Factory.DeployCnStakingWithPD`, exposing `stake()`/`stakeFor()`, `convertToShares`/`convertToAssets`, `previewDeposit`/`previewRedeem`/`previewWithdraw`, `totalAssets`, and `totalSupply`, mirroring the exact ERC4626 `previewDeposit = assets.mulDivDown(supply, totalAssets())` pattern flagged in the external report. Any unprivileged staker who is first to call `stake()`/`stakeFor()` on a freshly deployed `PublicDelegation` proxy can mint a negligible number of shares and then inflate `totalAssets()` (e.g., via a direct KAIA transfer/self-destruct-less send to the contract, or a follow-up `redelegateByAssets`/`redelegateByShares` interaction that changes the underlying `CnStaking` balance accounting) to depress the shares-per-asset ratio for everyone who stakes afterward, capturing a share of their deposited principal.

### Finding Description
`PublicDelegation` exposes the full ERC4626 preview surface (`ConvertToShares`, `ConvertToAssets`, `PreviewDeposit`, `PreviewRedeem`, `PreviewWithdraw`, `TotalAssets`, `TotalSupply`) alongside payable `Stake()`/`StakeFor(_recipient)` entry points and a `Staked(user, assets, shares)` event that records the assets-to-shares conversion at deposit time.

This contract is deployed on demand and reachable by any unprivileged caller through `CnStakingV4Factory.DeployCnStakingWithPD`, which creates both the `CnStaking` proxy and its paired `PublicDelegation` share-vault proxy in one public, payable transaction. [4](#0-3) 

Because the vault follows the ERC4626 `assets.mulDivDown(supply, totalAssets())` share-pricing convention (the exact primitive described in the external report), the classic first-depositor attack applies: the first staker deposits a minimal amount (minting a minimal amount of shares), then increases `totalAssets()` out-of-band relative to `totalSupply()` (directly funding the underlying `CnStaking` balance that backs `totalAssets()`, or timing a `RedelegateByAssets`/`RedelegateByShares` call before other stakers arrive) to depress the effective share price. Every subsequent staker's `previewDeposit` then rounds their newly minted shares down, and the value lost to rounding is captured by the attacker's existing share position. [5](#0-4) 

Because the Solidity source for `PublicDelegation` is not present in this repository's indexed contents (only the Go bindings/ABI/bytecode are indexed), the exact mitigation status (e.g., whether a decimals offset, minimum-deposit floor, or virtual-shares defense analogous to OpenZeppelin's ERC4626 `_decimalsOffset()` has been added) cannot be confirmed from what is indexed here. The binding surface alone is not sufficient to prove or disprove that a fix is in place; this should be verified against the actual `PublicDelegation.sol` source before treating this as a confirmed exploitable bug versus an unconfirmed structural risk.

### Impact Explanation
If unmitigated, an attacker who is first to stake into a newly created `PublicDelegation` vault (a routine, permissionless, and cheap action available immediately after any CN's `deployCnStakingWithPD` call) can permanently skew the shares-to-assets ratio and redirect a portion of every subsequent staker's principal to themselves, exactly as described in the source report for LToken/LEther. Since `PublicDelegation` vaults are meant to let arbitrary public stakers delegate KAIA to a CN, the victim pool includes any ordinary staker choosing that CN, and losses accrue in native KAIA.

### Likelihood Explanation
Likelihood is significant for any brand-new `PublicDelegation` deployment because becoming "first staker" only requires observing the `DeployCnStakingV4`/`PublicDelegation` deployment transaction (or deploying+staking within the same block/bundle) and paying a small stake amount — well within reach of a single unprivileged transaction sender. However, this analysis is capped by not being able to inspect the actual vault Solidity implementation to confirm whether inflation-attack defenses (e.g., decimals offset, minimum liquidity lock) already exist, which is standard practice post-2023 in OpenZeppelin's ERC4626 and would neutralize this exact issue.

### Recommendation
Verify (in the actual `PublicDelegation.sol`/`ERC4626`-style base contract, not indexed here) whether:
1. A virtual-shares/virtual-assets offset (OpenZeppelin `_decimalsOffset`) is applied to `previewDeposit`/`previewMint`/`convertToShares` to make the attack economically unviable, or
2. A minimum first-deposit / minimum-liquidity lock (Uniswap V2 style) is enforced on the first stake into a freshly created vault.
If neither is present, add one of these mitigations to `previewDeposit`/`totalAssets` computation before `stake()`/`stakeFor()` accepts value, and add a regression test that deploys a fresh `PublicDelegation` via `CnStakingV4Factory.deployCnStakingWithPD`, stakes a minimal amount as the first staker, sends extra KAIA directly to the vault/backing `CnStaking`, and confirms a second staker's minted shares are not disproportionately rounded down.

### Proof of Concept
1. Call `CnStakingV4Factory.deployCnStakingWithPD(owner, pdArgs)` to deploy a fresh `CnStaking` + `PublicDelegation` pair.
2. As attacker "Mike", immediately call `PublicDelegation.stake()` (or `stakeFor`) with a minimal KAIA amount, minting a minimal number of shares while `totalSupply()` is at its lowest non-zero value.
3. Increase the vault's backing balance without minting new shares — e.g., by directly sending KAIA to the `PublicDelegation`/backing `CnStaking` contract, or by exploiting timing around `RedelegateByAssets`/`RedelegateByShares` — inflating `TotalAssets()` relative to `TotalSupply()`.
4. A legitimate staker calls `stake()` with a normal deposit; due to the depressed share price, `PreviewDeposit`/`ConvertToShares` rounds down heavily, and the `Staked(user, assets, shares)` event reflects a disproportionately small `shares` value for the `assets` paid.
5. Mike calls `Redeem`/`RedelegateByShares` to withdraw, capturing the rounding remainder that was effectively transferred from the legitimate staker's deposit.

Note: Steps 3 rely on assumptions about `TotalAssets()`'s exact balance source (backing `CnStaking` contract balance) that could not be fully confirmed from the indexed Go bindings alone; confirming the precise mechanics requires access to the `PublicDelegation.sol`/`CnStaking` source, which is not available in this repository's index.
