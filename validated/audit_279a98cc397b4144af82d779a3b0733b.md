## Title
`Stakes::sub_delegated_stake` / `VoteAccounts::sub_stake` panic on stake-cache recomputation mismatch across the `use_fixed_point_stake_math` feature boundary — validator crash (`runtime/src/stakes.rs`)

### Summary
The external report's bug class is: an unlock/decrement is computed from a *freshly recomputed "current" value* instead of the value that was actually recorded when the corresponding lock/increment happened, so if the underlying state changes between the two operations, the subtraction underflows and the code panics/reverts forever. `Stakes::sub_delegated_stake` and `VoteAccounts::sub_stake`/`do_sub_node_stake` in Agave exhibit the same pattern: instead of storing the exact stake amount attributed to a delegation when it was added, the cache recomputes `delegation_effective_stake(...)` again at removal/upsert time and subtracts that recomputed value from the aggregate, using `.expect()`/`panic!()` on any mismatch.

### Finding Description
`StakesCache::check_and_store` is invoked by ordinary (unprivileged) transaction processing whenever a stake or vote account is touched (delegate, deactivate, split, merge, withdraw, or zero-lamport removal) [1](#0-0) . It calls `Stakes::upsert_stake_delegation`/`remove_stake_delegation`, which recompute `delegation_effective_stake` for the **current** epoch/history/feature-flag state and feed that recomputed number into `sub_delegated_stake`: [2](#0-1) 

`sub_delegated_stake` asserts that the aggregate `delegated_stakes[voter]` is at least as large as the freshly recomputed value, panicking otherwise: [3](#0-2) 

The same pattern exists one layer down in `VoteAccounts`, where `sub_stake`/`do_sub_node_stake` also `.expect()`/`panic!()` on underflow of the aggregated `stake`/`staked_nodes` totals: [4](#0-3) 

The value being subtracted is **not** the value that was originally added for that delegation — it is recomputed on the fly via `delegation_effective_stake`, which is itself dispatched on the `use_fixed_point_stake_math` feature flag: [5](#0-4) 

This dispatch flag is derived from `feature_set.upgrade_bpf_stake_program_to_v5_1`, an on-chain feature that activates at a specific slot within an epoch (not necessarily an epoch boundary) [6](#0-5) . Because `check_and_store` is called per-transaction throughout the epoch (not once per epoch boundary), a stake delegation can be **added** to the cache while the flag is `false` (recorded stake computed with the legacy warmup/cooldown formula) and later **removed/updated** in a subsequent block, in the same epoch, after the feature has activated (`use_fixed_point_stake_math == true`), causing `delegation_effective_stake` to be recomputed with a different math path for the exact same `Delegation`/epoch. If the new computation yields a larger effective stake than what was originally added for that voter's aggregate (e.g., the aggregate consists of exactly one delegation, or the fixed-point rounding differs upward relative to the legacy floating computation), `current_stake.checked_sub(stake).expect(...)` in `sub_delegated_stake` fails and the validator process panics via `.expect()`.

This is structurally the same broken invariant as the Streamr `_endVote()` bug: the "amount to release" is derived from *live* recomputed state instead of the amount that was actually locked/recorded, so any divergence between add-time and remove-time state turns a normal state transition into a guaranteed panic.

### Impact Explanation
A panic inside `Stakes::sub_delegated_stake` or `VoteAccounts::sub_stake` occurs inside ordinary bank/transaction replay code, on the hot path used by every validator processing the same block (since it is triggered by normal, replicated stake-program instructions, not a local-only computation). If a specific stake-account/vote-account state sequence around a feature-activation boundary reliably reproduces the recompute mismatch, every validator that processes that block would hit the same `.expect()`/`panic!()`, i.e., a cluster-wide simultaneous crash — a consensus halt, not merely a single-node crash. This satisfies the "consensus halt" / "non-RPC remote exhaustion or crash" impact category, since the trigger is a set of unprivileged, ordinary stake instructions submitted by any account (no malicious validator/peer/admin assumption required).

### Likelihood Explanation
Likelihood is **uncertain/unconfirmed** rather than demonstrated: I was not able to fully trace, within the available tool budget, a concrete numeric example proving that `delegation_effective_stake` under `use_fixed_point_stake_math = true` can return a *strictly larger* value than under `use_fixed_point_stake_math = false` for the exact same `Delegation`/epoch/history combination (this is required to make `checked_sub` underflow rather than merely leave residual dust). The dispatch itself, and the fact that `check_and_store` recomputes effective stake independently at add-time and remove-time using the feature flag captured at call time, are both confirmed in the code. What remains unverified: (1) the exact rounding/monotonicity relationship between `stake()` and `stake_v2()` (fixed-point) implementations in `solana_stake_interface`, which are not part of the excerpts examined, and (2) whether `check_and_store`'s two call sites within the same block/epoch can actually observe different values of `use_fixed_point_stake_math` for the same delegation (i.e., whether the flag can flip mid-epoch while stake caches from before the flip are still live). Because of this, I cannot assert with confidence that this path is currently exploitable versus merely defensively fragile.

### Recommendation
Do not recompute the "current effective stake" independently at add and remove time from a feature flag that can change mid-epoch. Instead, cache/store the exact effective-stake value that was used at insertion time alongside the delegation (or pin `use_fixed_point_stake_math` per-epoch rather than per-call), and use that stored value for the corresponding removal so add/remove pairs are always symmetric regardless of feature activation timing. Additionally, replace the `.expect()`/`panic!()` underflow guards in `sub_delegated_stake`/`sub_stake`/`do_sub_node_stake` with `saturating_sub` plus a metric/log, so a rounding or math-path mismatch degrades gracefully instead of crashing the validator.

### Proof of Concept
Not fully constructible from the available code excerpts — a working PoC requires confirming the exact non-monotonic relationship between the legacy `Delegation::stake()` warmup/cooldown formula and the fixed-point `Delegation::stake_v2()` formula (in `solana-stake-interface`, not indexed here) for a delegation whose `use_fixed_point_stake_math` flag flips between the block that calls `upsert_stake_delegation`/`check_and_store` to add/update the delegation and a later block in the same epoch that calls it again (e.g., via a `Split`/`Withdraw`/`Deactivate` instruction) after `upgrade_bpf_stake_program_to_v5_1` activates. Conceptually:
1. Attacker creates a stake account and delegates it (block N, feature inactive) → cache adds `delegated_stakes[voter] += stake_legacy`.
2. `upgrade_bpf_stake_program_to_v5_1` activates at some slot within the same epoch (block N+k).
3. Attacker submits any instruction that touches the stake account (e.g., a partial withdraw/split) in block N+k+1, causing `check_and_store`→`upsert_stake_delegation`/`remove_stake_delegation` to recompute `stake_v2` instead of `stake`.
4. If `stake_v2 > stake_legacy` for that delegation/epoch and it is the sole delegation to that voter, `sub_delegated_stake` panics on `checked_sub(...).expect(...)`, crashing every validator that replays the block. [2](#0-1) [3](#0-2) [5](#0-4)

    pub fn sub_stake(&mut self, pubkey: &Pubkey, delta: u64) {
        let vote_accounts = Arc::make_mut(&mut self.vote_accounts);
        if let Some((stake, vote_account)) = vote_accounts.get_mut(pubkey) {
            *stake = stake
                .checked_sub(delta)
                .expect("subtraction value exceeds account's stake");
            let vote_account = vote_account.clone();
            self.sub_node_stake(delta, &vote_account);
        }
    }

    fn add_node_stake(&mut self, stake: u64, vote_account: &VoteAccount) {
        let Some(staked_nodes) = self.staked_nodes.get_mut() else {
            return;
        };

        VoteAccounts::do_add_node_stake(staked_nodes, stake, *vote_account.node_pubkey());
    }

    fn do_add_node_stake(
        staked_nodes: &mut Arc<HashMap<Pubkey, u64>>,
        stake: u64,
        node_pubkey: Pubkey,
    ) {
        if stake == 0u64 {
            return;
        }

        Arc::make_mut(staked_nodes)
            .entry(node_pubkey)
            .and_modify(|s| *s += stake)
            .or_insert(stake);
    }

    fn sub_node_stake(&mut self, stake: u64, vote_account: &VoteAccount) {
        let Some(staked_nodes) = self.staked_nodes.get_mut() else {
            return;
        };

        VoteAccounts::do_sub_node_stake(staked_nodes, stake, vote_account.node_pubkey());
    }

    fn do_sub_node_stake(
        staked_nodes: &mut Arc<HashMap<Pubkey, u64>>,
        stake: u64,
        node_pubkey: &Pubkey,
    ) {
        if stake == 0u64 {
            return;
        }

        let staked_nodes = Arc::make_mut(staked_nodes);
        let current_stake = staked_nodes
            .get_mut(node_pubkey)
            .expect("this should not happen");
        match (*current_stake).cmp(&stake) {
            Ordering::Less => panic!("subtraction value exceeds node's stake"),
            Ordering::Equal => {
                staked_nodes.remove(node_pubkey);
            }
            Ordering::Greater => *current_stake -= stake,
        }
    }

pub(crate) fn delegation_effective_stake<T: StakeHistoryGetEntry>(

    use_fixed_point_stake_math: bool,

        delegation.stake_v2(epoch, history, new_rate_activation_epoch)

        #[allow(deprecated)]

    }
}
