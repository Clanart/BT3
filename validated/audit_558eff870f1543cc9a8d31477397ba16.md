### Title
Identity group key accepted by `ThresholdKeys::new`/`ThresholdKeys::read` causes a reachable panic in the BIP-340 HRAm — unprivileged DoS of the signing node - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::new` computes `group_key` as the sum of the first `t` caller-supplied `verification_shares` without rejecting the point at infinity. Both `ThresholdKeys::read` (a deserialization entry point for untrusted bytes) and the DKG path feed attacker-influenced points into this constructor. Any later BIP-340/Bitcoin signing operation with those keys calls `bitcoin::crypto::Hram::hram`, which calls `x(A)` — `.expect("point at infinity")` — unconditionally aborting the process when `A = group_key` is identity. Malformed key material therefore deterministically crashes a signer mid-protocol.

### Finding Description
- `ThresholdKeys::new` builds `group_key` from `verification_shares[i] * interpolation_factor(i)` for `i in 1..=t` and stores it with no non-identity check. [1](#0-0) 
- `ThresholdKeys::read` parses `t`, `n`, `i`, the interpolation variant, `secret_share`, and then `n` group elements via `C::read_G`, and hands them straight to `ThresholdKeys::new`. `read_G` for the in-scope curves accepts the canonical encoding of the identity point (no subgroup/identity rejection of the summed result exists anywhere). [2](#0-1) 
- The Bitcoin `Schnorr` algorithm's HRAm hashes `x(R)` and `x(A)`, where `x()` returns `.expect("point at infinity")` on the identity, and `x_only`/`needs_negation` similarly assume non-infinity inputs. [3](#0-2) 
- `AlgorithmSignMachine::sign` calls `algorithm.sign_share(&view, &Rs, nonces, msg)` which invokes `Hram::hram(&R, &view.group_key(), msg)`; `A` here is the (attacker-influenced) group key. The code itself documents "If either `R` or `A` is the point at infinity, this will panic." [4](#0-3) 
- This path is reached from untrusted protocol input: `processor/src/signer.rs` runs `machines[0].read_preprocess(...)` / `machine.sign(preprocesses, &[])` on coordinator-relayed preprocess bytes, inside a `handle()` that aborts the whole node task on panic. [5](#0-4) 

Note on reachability nuance: `R` (the aggregated nonce) cannot be forced to identity by a single signer because the FROST binding factors `rho_i` commit to all preprocesses. `A` (the group key), however, is fully determined by `verification_shares`, which arrive via `ThresholdKeys::read`/`ThresholdKeys::new` and — in a DKG — via each participant's broadcast commitments; a participant who chooses its polynomial commitments so that `Σ_{i=1..t} share_i · λ_i = identity` (or who crafts a serialized `ThresholdKeys` blob with such shares) deterministically obtains an identity `group_key`. The library never validates `group_key != identity`, `secret_share` consistency, or that the shares define a non-degenerate key.

### Impact Explanation
This is a direct analog of CVE-2019-14558's "insufficient control flow management → denial of service": an untrusted input path (`read_G`-decoded points → `ThresholdKeys::new` → `Hram::hram`) reaches an `expect`/`panic` instead of a recoverable error. An unprivileged party supplying the crafted key material / DKG commitments crashes any node that attempts a Bitcoin-network FROST signature over those keys — permanently halting signing for that validator set (the key is stored, so the panic recurs on every attempt and on restart). Severity: Medium (availability only; no secret leakage).

### Likelihood Explanation
Crafting the identity-sum `verification_shares` is deterministic linear algebra over public values — the attacker needs only to make their share's contribution the negation of the honest sum, and `ThresholdKeys::new` performs no identity or key-ownership check to catch it. Every Bitcoin signing attempt then panics with certainty. The main caveat is that populating `ThresholdKeys` requires either delivering a malformed serialized blob to `ThresholdKeys::read` or winning a slot in the DKG commitment set — both are listed in-scope input surfaces, but the DKG route additionally depends on the coordinator accepting the malformed commitments (PedPoP verifies per-share Schnorr PoKs, not the aggregate group-key sum).

### Recommendation
- In `ThresholdKeys::new`, reject a `group_key` (or any `verification_shares` entry, if the protocol requires non-identity shares) that `is_identity()`, returning `DkgError` instead of storing it.
- In `bitcoin::crypto::Hram::hram` / `x` / `x_only`, return a verification-failure/`None` rather than `expect`ing non-infinity, so the panic is unreachable regardless of upstream validation.
- Defense in depth: have `C::read_G` (or the `ThresholdKeys`/`Preprocess` readers) reject identity points at deserialization boundaries where identity is never valid.

### Proof of Concept
```rust
// Networks::bitcoin scope; requires std + kp256/Secp256k1
use frost::{
  curve::{Ciphersuite, Secp256k1},
  dkg::{Participant, ThresholdParams, Interpolation, ThresholdKeys},
};
use zeroize::Zeroizing;
use std::collections::HashMap;

// t = n = 2. Choose verification_shares s.t. the interpolated group key is identity.
// With Lagrange interpolation over {1, 2}: lambda_1 = 2, lambda_2 = -1.
// group_key = 2*V1 - V2 == identity  =>  pick V1 = G*a, V2 = G*2a.
let g = Secp256k1::generator();
let a = <Secp256k1 as Ciphersuite>::F::ONE;
let mut verification_shares = HashMap::new();
verification_shares.insert(Participant::new(1).unwrap(), g * a);
verification_shares.insert(Participant::new(2).unwrap(), g * (a + a));

let keys = ThresholdKeys::<Secp256k1>::new(
  ThresholdParams::new(2, 2, Participant::new(1).unwrap()).unwrap(),
  Interpolation::Lagrange,
  Zeroizing::new(a),
  verification_shares,
).unwrap();
assert!(bool::from(keys.group_key().is_identity())); // accepted without error

// Any subsequent Bitcoin Schnorr sign with these keys reaches
// bitcoin::crypto::x(&group_key) -> expect("point at infinity") -> panic.
// Equivalently, serialize `keys` and deliver it to ThresholdKeys::read on a
// victim node; the node's first Bitcoin-network signature attempt aborts the
// processor task.
```

  #[derive(Clone, Copy, Debug)]
  pub struct Hram;
  #[allow(non_snake_case)]
  impl HramTrait<Secp256k1> for Hram {
    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
