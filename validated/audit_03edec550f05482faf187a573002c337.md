### Title
Daemon Service Identity Is Self-Asserted With No Binding to Client TLS Credential → Cross-Service RPC Hijack and Keychain Exposure - ([File: chia/daemon/server.py])

### Summary
The chia daemon (`WebSocketServer`) treats the TLS handshake purely as a yes/no admission gate and never binds a connected websocket's claimed `service` identity to any property of the credential that was actually presented. Every Chia service RPC process (`full_node`, `wallet`, `farmer`, `harvester`, `data_layer`, etc.) connects back to the daemon using the *same* shared `daemon_ssl` private cert/key pair, and then simply tells the daemon which service name it wants to be recognized as via the `register_service` command payload. Any process that can reach the daemon socket with that shared credential can therefore register — and be routed messages — under any other service's name, or invoke privileged keychain commands, without any scope check tying its asserted identity to a narrower, service-specific credential. This mirrors the OpenClaw finding where a device that was only paired (narrow scope) could skip the node-scope gate and reach host-level command execution: here, a component that should only ever legitimately identify as one low-trust service (e.g. `harvester`) can freely claim to be a high-trust service (e.g. `chia_wallet` or `chia_full_node`) and receive/forward that service's privileged RPC traffic.

### Finding Description
`RpcServer.create()` builds its daemon-connection TLS context from the single shared `daemon_ssl` private cert/key for every service type: [1](#0-0) 

That connection then self-registers using a **client-supplied string**, with no verification that the string matches any property of the presented certificate: [2](#0-1) 

On the daemon side, `register_service` accepts this string verbatim and adds the websocket to `connections[service]`: [3](#0-2) 

`handle_message()` then routes any message whose `destination` matches a registered service name to *all* websockets registered under that name, with the daemon "not interpret[ing] the command or payload if the destination is registered": [4](#0-3) 

The daemon documentation explicitly confirms there is no per-service authorization layer beyond mutual TLS with the shared daemon cert, and that "registered names become routing authorities for local clients": [5](#0-4) 

Separately, keychain commands (`add_key`, `delete_all_keys`, `get_all_private_keys`, `get_first_private_key`, etc.) are dispatched purely by command name membership in `keychain_commands`, with zero check on which service/websocket sent them: [6](#0-5) [7](#0-6) 

Because every service RPC process authenticates to the daemon with the identical shared credential, and the daemon's only notion of "which service is this" is an unauthenticated, attacker/bug-controlled string in the JSON payload, any compromised or misbehaving service process (including a harvester in a distributed farming deployment, which is architecturally the lowest-trust component allowed to hold a private cert) can:
1. Register itself as `chia_wallet` or `chia_full_node` and receive privileged messages/state-change traffic meant for those services, or
2. Directly invoke `keychain_commands` (private key extraction, key deletion, key addition) since those are gated only by TLS admission, not by caller identity/scope.

This is a direct structural analog to CWE-862/863: a component that is only supposed to be scoped to one class of operation (its own service name) can freely claim and exercise a broader scope, with no gate to prevent it — exactly the "skips node scope gate" pattern in the OpenClaw advisory, here reachable by any local RPC-capable service process rather than a remote peer.

### Impact Explanation
A compromised or malicious lower-trust service process (e.g. a harvester or plotter component, which in many production farming topologies runs on separate, less-trusted hardware than the wallet/full node) can hijack privileged daemon routing and/or directly read or delete keychain private keys via `get_all_private_keys` / `get_first_private_key` / `delete_all_keys`, and can intercept wallet-bound RPC traffic by registering under `chia_wallet`. This can lead to private key theft, unauthorized wallet-linked command execution, and denial of service against legitimate services — consistent with a High severity, host-compromise-class bug once any single service process is compromised.

### Likelihood Explanation
Reaching this requires only a working connection to the local daemon socket with the shared `daemon_ssl` credential that every installed Chia service already possesses by default (no additional secret needed beyond what a harvester/plotter/etc. process already has). No cryptographic bypass or race condition is needed — `register_service` and keychain command dispatch have no additional authorization check to defeat. The main precondition is compromise (or malicious operation) of one already-deployed lower-trust service process, matching the advisory's own "pairing/setup prerequisites" caveat for the OpenClaw finding.

### Recommendation
Bind daemon service identity to the TLS client credential rather than to an unauthenticated payload field: issue distinct per-service client certificates (or another cryptographically verifiable identity) for daemon connections, and have `register_service`/`handle_message` validate the claimed `service` name against that identity before adding routing entries or accepting privileged commands (including `keychain_commands`). At minimum, restrict which services may register under sensitive names like `chia_wallet`/`chia_full_node`/`wallet_ui`, and require keychain commands to originate only from an explicitly authorized caller identity rather than any TLS-admitted daemon client.

### Proof of Concept
1. Start the daemon and any legitimate service (e.g. a harvester) normally so it connects using the shared `daemon_ssl` private cert, as in `RpcServer.connection()`.
2. From the same or an equivalent compromised process holding that shared cert, open a raw websocket to the daemon and send:
   `register_service` with `data={"service": "chia_wallet"}` (analogous to `test_daemon_register.py`'s `test_multiple_register_different`, but using a sensitive name instead of an arbitrary test name): [8](#0-7) 
3. Any subsequent daemon message with `destination: "chia_wallet"` is now delivered to this attacker-controlled socket per `handle_message()`'s forwarding logic.
4. Independently, the same connection can send `get_all_private_keys` (a `keychain_commands` entry) and receive raw private-key material, since `handle_command()` performs no caller-identity check: [9](#0-8)

```python
    async def register_service(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        self.log.info(f"Register service {request}")
        service = request.get("service")
        if service is None:
            self.log.error("Service Name missing from request to 'register_service'")
            return {"success": False}
        if service not in self.connections:
            self.connections[service] = set()
        self.connections[service].add(websocket)

        response: dict[str, Any] = {"success": True}
        if service == service_plotter:
            response = {
                "success": True,
                "service": service,
                "queue": self.extract_plot_queue(),
            }
        elif self.ping_job is None:
            self.ping_job = create_referenced_task(self.ping_task())
        self.log.info(f"registered for service {service}")
        log.info(f"{response}")
        return response
```

```python
    async def get_all_private_keys(self, request: dict[str, Any]) -> dict[str, Any]:
        all_keys: list[dict[str, Any]] = []
        if self.get_keychain_for_request(request).is_keyring_locked():
            return {"success": False, "error": KEYCHAIN_ERR_LOCKED}

        private_keys = self.get_keychain_for_request(request).get_all_private_keys()
        for sk, entropy in private_keys:
            all_keys.append({"pk": bytes(sk.get_g1()).hex(), "entropy": entropy.hex()})

        return {"success": True, "private_keys": all_keys}
```
