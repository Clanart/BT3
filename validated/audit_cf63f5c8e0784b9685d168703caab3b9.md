### Title
`SignableTransaction::new` omits the OP_RETURN data output from the fee/weight calculation, under-paying the required fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts an optional `data` payload which is appended to the transaction as an OP_RETURN output, but the fee is derived from `calculate_weight_vbytes`, which only models the payment outputs and an optional change output. The extra output's weight is never accounted, so `needed_fee` — and the actual implicit fee `sum(inputs) - sum(outputs)` — is computed as if the transaction were up to ~90 vbytes smaller than it really is. This is the same bug class as the Burve report: a deduction (tax/fee) is computed on an amount that fails to include one of the components consuming funds/size, so the committed fee is less than required for the constructed transaction.

### Finding Description
`calculate_weight_vbytes(inputs, payments, change)` builds a mock transaction containing only `payments` (mapped to `TxOut`s) plus an optional change output, and returns its weight/vbytes (`networks/bitcoin/src/wallet/send.rs:62-127`). In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` at lines 194-202 *before* the weight is estimated, but both calls to `calculate_weight_vbytes` (lines 204 and 226) pass only `payments` and `change` — the data output is never included in the mock transaction. `data` may be up to 80 bytes (`send.rs:171-173`), which after `PushBytesBuf` encoding produces a script of up to ~82 bytes; the resulting `TxOut` adds roughly 90 vbytes (8-byte amount + varint + script + per-output overhead) that is absent from `vbytes`. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) is short by ~`90 * fee_per_vbyte` sats.
2. The minimum-relay-fee check at line 211 uses the same underestimated `vbytes`, so a transaction whose *actual* fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` still passes.
3. The `NotEnoughFunds` check (line 215) and the change computation (`input_sat - payment_sat - fee_with_change`, line 228) both use the underestimated fee, so `needed_fee()` reports a fee lower than what the built transaction requires for the requested rate — an externally observable mis-report of the committed fee.

### Impact Explanation
A transaction built with `data` commits a fee rate strictly lower than the caller-requested `fee_per_vbyte`. If the caller requests a rate at or near the relay minimum, the resulting transaction is under-priced relative to its true vsize and will be rejected by standard nodes (`min relay fee not met`) or will languish unconfirmed — a denial of service of the send path for any caller embedding data (e.g., embedding instructions/affiliate data in the OP_RETURN). `needed_fee()` and `fee()` also misreport the economics of the transaction, so downstream accounting that trusts `needed_fee` under-charges the fee. Analogous to the Burve issue, the accounting quantity (withdrawn amount / committed fee) was computed without a required component (tax / data-output weight); where Burve's bug only became fatal once a compensating double-tax was removed, here the missing component makes every data-carrying transaction under-funded on fee.

### Likelihood Explanation
The bug triggers deterministically whenever `SignableTransaction::new` is invoked with `Some(data)` — no attacker timing or adversarial conditions are needed; an unprivileged caller simply supplies up to 80 bytes of data. Whether it manifests as outright rejection depends on the requested `fee_per_vbyte` relative to the relay minimum, but the fee is mis-accounted on every such call. Callers that don't pass `data` are unaffected. Notably, the current processor code path (`processor/src/networks/bitcoin.rs:446-452`) passes `None` for data, so exploitability today depends on other consumers of this library constructing data-bearing transactions.

### Recommendation
Include the OP_RETURN output in the weight estimation: either pass the fully-constructed `tx_outs` (including the data `TxOut`) into `calculate_weight_vbytes`, or append the data output to the mock transaction inside it, so `vbytes`, `needed_fee`, the `TooLowFee` check, and the `NotEnoughFunds`/change arithmetic all reflect the transaction actually being built. As a defense-in-depth measure, after constructing `self.tx`, assert `self.fee() >= fee_per_vbyte * actual_vsize` before returning the `SignableTransaction`.

### Proof of Concept
From `networks/bitcoin/src/wallet/send.rs`:

```rust
// Lines 194-204: the data output is added to tx_outs...
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}

// ...but the fee estimate only models `payments` (and later `change`),
// never tx_outs, so the OP_RETURN's ~90 vbytes are unpriced:
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

And `calculate_weight_vbytes` (lines 85-99) builds its mock `output` vector solely from `payments` plus an optional change output — no data output exists anywhere in the estimation path.

Concretely: call `SignableTransaction::new(inputs, &payments, change, Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte` equals the minimum relay rate. The returned transaction's real vsize exceeds `vbytes` by ~90, so its effective fee rate is ~`fee_per_vbyte * vbytes / (vbytes + 90)` — below the relay minimum — yet `needed_fee()` reports the "correct" minimum fee and the `TooLowFee` check (line 211) passes because it divides by the same underestimated `vbytes`. The transaction is thus constructed, signed via `TransactionSignMachine::sign` (`Prevouts::All`, `send.rs:375-390`), and broadcast, only to be rejected by nodes — mirroring the Burve DoS where an unaccounted deduction left the operation under-funded.
