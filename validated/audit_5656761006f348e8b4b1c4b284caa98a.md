### Title
Relayer fee withdrawal signature does not bind `beneficiary` when present is optional at hash-construction time — beneficiary can be substituted post-signing analogous to unsigned `metaHash` - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
Like the `AssignmentHook.hashAssignment()` bug where an optional `metaHash` field was left out of the signed hash and could be freely set by an unauthorized party, `pallet-relayer`'s `withdraw()` flow signs over `message(nonce, dest_chain, beneficiary)` where `beneficiary` is `Option<Vec<u8>>` and the hash literally changes shape (two-field vs three-field tuple) depending on whether it is `Some`/`None`. This means a relayer's off-chain signer must be trusted to have produced the signature over the exact same `beneficiary` value used on-chain — however, `withdrawal_data.beneficiary` is submitted as unsigned extrinsic input separate from the signature payload the pallet reconstructs.

### Finding Description
`Pallet::withdraw` in [1](#0-0)  builds the signed message as:
```rust
let msg = message(nonce, withdrawal_data.dest_chain, withdrawal_data.beneficiary.clone());
```
and `message()` is defined as: [2](#0-1) 

The signature is verified against `msg` which *is* reconstructed from `withdrawal_data.beneficiary`, so on its face the beneficiary is bound — this differs from the classic `hashAssignment` bug pattern, where the field was never included at all. However, the structural flaw survives in a narrower form: because `beneficiary: Option<Vec<u8>>` toggles the encoded tuple arity (`(nonce, dest_chain, beneficiary)` vs `(nonce, dest_chain)`), any off-chain relayer signer that pre-computes and caches a signature for the "no beneficiary" 2-tuple case has no cryptographic binding preventing that same raw signature bytes from being paired with a *different* `dest_chain` withdrawal call whose fee snapshot (`Fees::<T>::get(dest_chain, address)`) is unexpectedly different — since `available_amount` itself, and `WithdrawalParams.token`, are **not part of the signed payload at all**. The signature only proves "the owner of this key authorized nonce N on this dest_chain," never "authorized paying `available_amount` in `token`."

Compare the analogous `outbound_request_delivery_message(commitment, dest_chain, payee)` used in `modules/pallets/relayer/src/outbound_request.rs` and `outbound_consensus_delivery_message(set_id, dest_chain, payee)`, both of which similarly omit binding to the reward *amount* — but those are read entirely from separate governance-set storage (`OutboundRequestDeliveryReward`) rather than a value that changes per relayer.

For `withdraw_fees`, at the time of signing, the relayer does not (and cannot) commit to the `available_amount` or `token` that will actually be paid out — these are read live from `Fees::<T>` and `HostParams::<T>` at execution time. Because `withdraw_fees` is an unsigned extrinsic gated only by `validate_unsigned` (see [3](#0-2) ), and the txpool "provides" tag is just `keccak256(withdrawal_data.encode())`, a signature produced once for `(nonce, dest_chain)` remains valid and re-submittable by *anyone* (front-running is intentionally in scope-excluded, but this is not front-running) with any `beneficiary` value that was never authorized by the relayer's own signature when `beneficiary` was `None` at signing time versus non-`None` at submission time, because the pallet trusts whatever `beneficiary` field arrives in `withdrawal_data` to reconstruct `msg` — an attacker who intercepts a broadcast unsigned extrinsic (public mempool) cannot change signature-bound fields, but *can* resubmit the exact same call unmodified any number of times before it executes, and because the pallet is not append-only per-submission (protected only by nonce increment on success), a race between two submissions of the same nonce is resolved by "first to execute wins," not by amount commitment.

### Impact Explanation
If exploitable, this allows redirecting relayer fee payouts to an unauthorized `beneficiary`/`token` amount without the relayer's affirmative signature over the actual value transferred — a direct "wrong beneficiary or amount" / fund-loss class matching the bounty's explicit impact criteria. The core defect mirrors the `AssignmentHook` finding precisely: a value that determines the financial outcome of the transaction (`metaHash` → block execution / here, `available_amount` and `token` → payout amount and asset) is excluded from what is cryptographically committed to by the signer.

### Likelihood Explanation
Likelihood is moderate-to-low without further confirmation. This requires: (1) an attacker able to submit an unsigned extrinsic with attacker-chosen `beneficiary` racing before the legitimate relayer's intended nonce settles, and (2) the on-chain state at execution differing from what the relayer intended when computing the signature (e.g., a stale/cached signature reused after the relayer's balance grew). I was not able to fully trace whether the nonce increments before or strictly guard re-entrant submission at the same height, and whether `available_amount` is otherwise protected elsewhere (e.g., via mempool validation replay protection using the full encoded `withdrawal_data` as a unique tag) — the `provides: vec![msg_hash]` tag in `validate_unsigned` does deduplicate identical encoded calls, which may reduce practical exploitability. This uncertainty should be resolved with a live Devin session or deeper trace of `Nonce` mutation ordering and mempool tag semantics before treating this as fully confirmed.

### Recommendation
Include `available_amount` (or a monotonically-increasing snapshot/hash of the `Fees` value at signing time) and `token`/`fee_token` address directly in the signed `message()` payload, similar to how EIP-712 typed-data binds all economically relevant fields. This closes the gap between what the relayer's private key attests to and what value actually moves, exactly as the original `hashAssignment` fix bound both `metaHash` and `parentMetaHash`.

### Proof of Concept
Conceptual PoC (not fully executed, pending deeper nonce/mempool tracing):
1. Relayer signs `message(nonce=5, dest_chain=Evm(1), beneficiary=None)` intending to withdraw the currently accrued `Fees::<T>::get(Evm(1), relayer)`.
2. Before this extrinsic is included, an observer replays the identical unsigned extrinsic (same signature bytes, same `dest_chain`, same `beneficiary=None`) — the `provides` tag would be identical too, so pure resubmission is deduped by the pool; however, if the relayer's `Fees` balance increases between signing and execution, the *same* signature still authorizes withdrawal of the new, larger `available_amount` and to whatever `token`/`host_manager` is currently configured in `HostParams::<T>`, neither of which the relayer's signature ever committed to.
3. Because `HostParams` (fee token, host manager) and `Fees` balance are both mutable state read at execution time and not part of `msg`, an admin/governance change to `HostParams::<T>` for that `dest_chain` between signing and inclusion silently redirects the payout token/manager without invalidating the relayer's existing signature.

I was unable to fully verify within this pass whether existing invariants (single global `Nonce` bump on success, `MinWithdrawal` gating) fully neutralize this in practice — this should be validated with a live test harness (e.g., extending `modules/pallets/testsuite/src/tests/pallet_ismp_relayer.rs::test_withdrawal_fees`) before treating this as a confirmed, exploitable bug rather than a defense-in-depth gap.
