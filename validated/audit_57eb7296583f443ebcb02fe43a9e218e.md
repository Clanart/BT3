### Title
Copilot conflict-resolution hunk splicing has no per-hunk identity check, only a count check, allowing silent corruption of committed file content - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
`ERTR-1` flags a class of bugs where a system accepts a set of externally-supplied values and stores/executes them without verifying they are semantically valid for the context they will be applied to (only superficial checks, like "non-empty", are performed). The same pattern exists in GitHub Desktop's "Resolve Conflicts with Copilot" feature: the model's per-hunk resolutions are validated only for **count** (`validateResolutionPaths`) and are then spliced into the on-disk conflicted file **positionally, by array order, with no check that resolution `i` actually corresponds to conflict block `i`'s original content**. If the model returns the right number of hunks but in the wrong order (or misattributed across near-identical conflict blocks), the wrong resolved content is silently written to disk and staged for commit — with no guard rejecting the mismatch, just like the missing token/market and non-zero validations in the report allowed invalid deposits/orders to be silently persisted.

### Finding Description
`reassembleResolvedFile` walks the raw on-disk file (which still contains `<<<<<<<`/`=======`/`>>>>>>>` markers) and replaces each conflict block with `hunkResolutions[hunkIndex]` purely by incrementing index as blocks are encountered: [1](#0-0) [2](#0-1) 

The only guard applied to the model's raw hunk array before this splicing is `validateResolutionPaths`, which checks that the **number** of hunks per file matches the number of conflict blocks found in that file — it never verifies that hunk `j` is the resolution for conflict block `j` specifically (e.g. by content anchor, `oursContent`/`theirsContent` fingerprint, or hash): [3](#0-2) 

`reassembleResolutions` then unconditionally calls `reassembleResolvedFile(ctx.rawContent, raw.hunks)` for any file whose path and hunk-count checks passed: [4](#0-3) 

Once reassembled, the result is written straight to disk and `git add`ed with no further verification that the reassembled content is coherent: [5](#0-4) 

This is the same broken invariant described in `ERTR-1`: a quantity-only check (count of hunks / non-zero amounts) stands in for a correctness check (hunk identity / token-market validity), so a value that passes validation can still be wrong for the specific slot it is applied to.

### Impact Explanation
If the wrong resolved content is spliced into the wrong conflict block, the file written to disk and staged for commit differs from what the user reviewed/intended, without any error being raised — this is silent corruption of what the user commits or pushes. Because Desktop's Copilot conflict resolution operates during merge/rebase/cherry-pick on content that originates from a remote branch (an attacker-controlled fork or branch the victim merges against), an attacker who controls one side of the conflicting branches can craft adjacent, structurally similar conflict blocks (e.g. two blocks with similar-looking markers/content) to increase the likelihood that the model's hunk-ordering is confused or that a prompt-injection-style crafted block causes the model to emit resolutions out of order. The user only sees the final reassembled file in the result dialog; there is no code path that flags a hunk being misattributed as long as the count matches.

### Likelihood Explanation
The gap is deterministic and reachable in code: `validateResolutionPaths` provably only checks path/hunk-count, and `reassembleResolvedFile` provably splices strictly by index. What is not fully verifiable from static review alone is how reliably a hostile repository can force the model to reorder or misattribute hunks (this depends on model behavior, which cannot be confirmed without running the actual Copilot conflict-resolution flow). This uncertainty should be called out explicitly: the *validation gap* is a confirmed structural fact in the code, but achieving a specific *malicious reordering* depends on influencing an LLM's output, which is probabilistic rather than a guaranteed exploit primitive.

### Recommendation
Strengthen `validateResolutionPaths` (or add a new step before `reassembleResolutions`) to verify hunk **identity**, not just count — e.g., have the model echo back a stable per-hunk anchor (a hash of `oursContent`/`theirsContent`/`contextBefore`) alongside `resolvedContent`, and reject/re-request the resolution if any anchor doesn't match the corresponding extracted hunk in `IFileConflictContext.hunks` at the same position. This closes the same class of gap the report describes: validate that the value being stored/applied is actually valid for the specific slot it is destined for, not just that superficial cardinality constraints are satisfied.

### Proof of Concept
1. Set up a repository with a branch containing two adjacent, structurally similar merge-conflict blocks in one file (e.g., two consecutive permission checks that look alike but resolve to different logic).
2. Merge/rebase against this branch in Desktop and trigger "Resolve Conflicts with Copilot" (`dispatcher.startCopilotConflictResolution`).
3. If the model's response array returns exactly 2 hunks (satisfying `validateResolutionPaths`'s count check at `app/src/lib/copilot-conflict-resolution.ts:509-520`) but in swapped order relative to the two blocks, `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) will splice hunk 0 into block 1's location and hunk 1 into block 0's location with no error.
4. Clicking "Continue Merge" calls `_applyCopilotConflictResolutions`, which writes this swapped content to disk and `git add`s it (`app/src/lib/stores/app-store.ts:7258-7268`), producing a committed file whose logic differs from what either branch intended, without any validation failure surfaced to the user. export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
