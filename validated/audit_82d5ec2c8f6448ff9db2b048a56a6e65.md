One key detail to confirm: whether the round-1 proof-of-knowledge binds the `enc_key` field of `EncryptionKeyMessage`, or only the commitments.### Title
DKG encryption keys are not bound to their participant, letting a malicious participant co-opt a victim's key so the victim (or blame observers) can decrypt all secret shares addressed to the registrant - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
In the PedPoP DKG, each participant's round-1 `EncryptionKeyMessage` carries a `Commitments` message (with a Schnorr proof of knowledge) **and** an `enc_key` point used by all other participants as the ECDH recipient for that participant's encrypted secret shares. The PoK `challenge()` binds only `context`, `participant`, `nonce`, and `cached_msg`, where `cached_msg` is the serialization of the commitment points only — `enc_key` is never transcripted or proven. A participant can therefore register another participant's `enc_key` under their own index.

### Finding Description
- `EncryptionKeyMessage { msg, enc_key }` is read in `verify_r1` and `enc_key` is stored per-participant via `self.encryption.register(l, msg)` → `Decryption::register`, which inserts `msg.enc_key` keyed by `l` with no possession check. [1](#0-0) 
- The only round-1 authentication is `msg.sig` verified against `challenge::<C>(self.context, l, msg.sig.R.to_bytes().as_ref(), &msg.cached_msg)`. [2](#0-1)  `cached_msg` is built exclusively from the `t` commitment points (`cached_msg.extend(commitments[i].to_bytes())`), and `challenge()` appends only `context`, `participant`, `nonce`, and `commitments` — `enc_key` is absent. [3](#0-2) [4](#0-3) 
- In round 2, each honest dealer encrypts participant `l`'s share with `self.decryption.enc_keys[&participant]`, i.e. ECDH against whatever point `l` registered. [5](#0-4) 
- The per-message PoP on the ciphertext binds the *sender* and ciphertext, not the intended recipient or the registered `enc_key`, so the misdelivery is undetectable. [6](#0-5) 

### Impact Explanation
Malicious participant M copies victim participant V's `enc_key` into M's own `EncryptionKeyMessage`. M's PoK still verifies (it only covers M's commitments). Every honest dealer then encrypts M's secret share under V's encryption key. Since shares are distributed as a broadcast `HashMap<Participant, EncryptedMessage>` (e.g. `ProcessorMessage::Shares` in `processor/src/key_gen.rs`), V sees the ciphertexts addressed to M and can decrypt **all** of them with its private `enc_key`, reconstructing M's entire secret share `s_M` — equivalent to stealing M's identity. V can thereafter produce valid FROST signature shares as M (`verify_share` only checks consistency with `verification_shares[M]`), so an attacker who compromised a single participant effectively controls two threshold shares, reducing the real threshold by one. Alternatively, M (unable to decrypt) files blame, and the published `EncryptionKeyProof` reveals the ECDH key to all `AdditionalBlameMachine`/`VerifyBlame` observers, publicly disclosing the share anyway. This matches the CVE class: a per-recipient credential (`enc_key`) is accepted for a party without verifying that party controls it, so restricted per-user content becomes readable by an unauthorized user.

### Likelihood Explanation
Requires one malicious DKG participant who observes other participants' round-1 messages before broadcasting their own — the messages are broadcast to all parties, so `enc_key` values are public within the session. No collusion, no broken channel assumptions, and no additional capability is needed; the attack succeeds deterministically because nothing binds `enc_key` to the participant index.

### Recommendation
Bind `enc_key` into the round-1 proof of knowledge: either include `enc_key.to_bytes()` in `cached_msg`/the `challenge()` transcript (e.g. an additional `append_message(b"encryption_key", enc_key)`), or require a separate Schnorr PoP over `enc_key` keyed to `context || participant`. `Decryption::register`/`verify_r1` must reject any registration where possession of the encryption key isn't proven under the claiming participant's index.

### Proof of Concept
1. n participants run `KeyGenMachine::generate_coefficients`. V publishes `EncryptionKeyMessage` containing `enc_key_V = G * v`.
2. M builds honest `Commitments` (valid PoK over `cached_msg` of its commitment points) but calls `registration` with `enc_key: enc_key_V` — trivially possible since `EncryptionKeyMessage { msg, enc_key }` is a public field struct and `enc_key` is not covered by `msg.sig`.
3. All parties' `verify_r1` accept M's message: the PoK verifies and `Decryption::register(Participant(M), …)` stores `enc_key_V` for `M`.
4. In `generate_secret_shares`, every dealer `d` computes `cipher(context, ecdh(k_d, enc_key_V))` for the share destined to M (`Encryption::encrypt` → `enc_keys[&M]`).
5. V reads the broadcast `EncryptedMessage` addressed to M, computes `ecdh(v, msg.key)` = the same shared key, applies `cipher`, and recovers the share. Repeating for all `d` gives V `Σ shares_d(M) = s_M`, M's full private key share — verified by `G * s_M == verification_shares[M]`.

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
