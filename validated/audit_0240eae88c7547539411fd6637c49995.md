## Title
Same-chain partial fills release the full aggregated escrow balance instead of the per-leg entitlement when duplicate input tokens back multiple order legs - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` tracks fill completion per output leg in `_partialFills[commitment][outputToken]`, but tracks escrow in an aggregated, commitment-and-token-keyed mapping `_orders[commitment][token]` that sums contributions from *all* input legs sharing that token. When a leg's output is fully satisfied, the code releases `_orders[commitment][token]` in full rather than only that leg's proportional share — exactly the same class of bug as the Amp token report, where an aggregated accounting field (`_allowed`/global balance) was used interchangeably with a per-partition value, causing state divergence.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:116-121`):

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

`_orders[commitment][token]` is populated during `placeOrder` by summing every input leg that uses that token address (see the aggregation pattern `_orders[commitment][token] += reducedInputs[i].amount;` used consistently across the gateway, e.g. `evm/tron/contracts/apps/IntentGatewayV2.sol:435,457`). It is a single scalar per `(commitment, token)`, with no per-leg partition.

`_partialFills[commitment][outputToken]`, by contrast, tracks completion **per output leg** (`evm/src/apps/intentsv2/IntentsBase.sol:148-152`).

If an order has two (or more) input legs that reference the **same token address** (`order.inputs[i].token == order.inputs[j].token`, `i != j`) — which nothing in the reviewed code paths (`placeOrder`, `_fillSameChain`) forbids — then completing leg `i`'s output (`amountFilled == totalRequired` for leg `i`) causes the withdrawal logic to release the *entire* aggregated `_orders[commitment][token]` balance, which includes escrow that was deposited for leg `j` as well. `_withdraw` then unconditionally decrements the shared entry by that full amount (`evm/src/apps/intentsv2/IntentsBase.sol:400-403`), zeroing out escrow that leg `j`'s own fill (or the user's cancellation path in `_cancelSameChain`) still needs.

This is structurally identical to the reported bug: a global/aggregated accounting field (`_orders`) is read as if it were scoped to a single partition (a single leg), when the actual authorization/completion tracking (`_partialFills`) is scoped per-partition. The mismatch lets a solver's completion of one leg silently consume escrow belonging to another leg.

### Impact Explanation
This falls squarely within "stealing or loss of funds" and "transaction manipulation" in the bounty scope. A solver who fully fills one output leg of a multi-leg order that shares an input token across legs receives (via `_withdraw`) the combined escrow of both legs instead of only their entitled proportional share. The remaining leg(s) are left with a zeroed escrow entry:
- If the user or another solver later tries to fill/cancel the remaining leg, `_withdraw` reverts with `UnknownOrder` because `_orders[commitment][token] == 0` (`IntentsBase.sol:401`), permanently locking the order in an unresolvable partially-filled state, or
- The first-completing solver receives tokens they never escrowed-equivalent value for, effectively stealing the other leg's principal.

### Likelihood Explanation
Reaching this requires only an unprivileged user placing an order whose `inputs` array contains two entries with the same `token` address (an entirely normal, unrestricted input a user or attacker controls when constructing/placing their own order or one crafted to trap a counterparty), and any solver calling the public `fillOrder`/`_fillSameChain` path with the outputs completing one leg before the other. No relayer, prover, governance, or privileged actor is needed — both the order placement and the fill are done through standard public entry points.

### Recommendation
Track escrow per-leg (e.g., keyed by `(commitment, i)` or `(commitment, outputToken)` matching `_partialFills`) instead of aggregating strictly by `(commitment, token)`, or compute `escrowedAmount` on full-leg-completion the same proportional way used for partial fills (`order.inputs[i].amount * fillAmount / totalRequired`, which on full completion is exactly `order.inputs[i].amount`) rather than reading the shared aggregated balance. This removes the redundant/ambiguous dual-accounting pattern, mirroring the Amp fix of eliminating the separate aggregate field in favor of a single source of truth scoped consistently with the completion tracking.

### Proof of Concept
1. User places a same-chain order with two input legs both using token `T`: `inputs = [{T, 100}, {T, 50}]`, and two output legs requiring different output tokens `O1`, `O2`. `_orders[commitment][T]` becomes `150` (aggregated).
2. Solver calls `fillOrder` providing only `O1`'s full required output amount (leg 0) and `0` for `O2` (leg 1) — a valid partial fill per `_fillSameChain`'s per-leg loop.
3. For leg 0, `amountFilled == totalRequired`, so `escrowedAmount = _orders[commitment][T]` = `150` (not the `100` that leg 0 actually reserved).
4. `_withdraw` transfers `150` of `T` to the solver and sets `_orders[commitment][T] = 0`.
5. Leg 1 (`O2`) is still open (`isFullyFilled = false`), but any subsequent solver attempting to fill it, or the user attempting `_cancelSameChain`, hits `_orders[commitment][T] == 0` → reverts `UnknownOrder`, permanently orphaning the remaining 50 units of `T` that were never actually paid out to anyone but were escrowed by the user.
