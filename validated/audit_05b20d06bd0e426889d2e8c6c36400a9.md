### Title
EncryptedMessage/EncryptionKeyProof lack recipient binding, letting any party frame an honest DKG sender as faulty - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2021-44225 is an access-control failure where the policy failed to restrict the *destination* of a message. The analogous shape in Serai exists in PedPoP's per-message encryption: `EncryptedMessage` cryptographically binds the **sender** (`pop_challenge` includes `sender`) but never binds the **recipient**. The intended decryptor is only supplied as an external parameter (`decryptor: Participant`) to `Decryption::decrypt_with_proof`, which then indexes `self.enc_keys[&decryptor]`. Because the ciphertext, its PoP, and the blame `EncryptionKeyProof` DLEq all omit the destination participant, a message that sender `s` honestly encrypted to participant `A` is indistinguishable, to any blame adjudicator, from a message `s` "sent" to participant `Eve`. Any unprivileged party can therefore construct a blame claim — complete with a fully valid DLEq proof for their own registered encryption key — that decrypts the relayed ciphertext to gibberish and causes `blame_internal` to return the honest `sender` as the faulty party.

### Finding Description
`EncryptedMessage` consists only of `key`, `pop`, and `msg` — no recipient field exists (crypto/dkg/pedpop/src/encryption.rs:81-93). The sender's proof-of-possession challenge `pop_challenge` binds `context`, `nonce`, `key`, `sender`, and `msg` — but not `to`/`recipient` (encryption.rs:302-324). During blame adjudication, `decrypt_with_proof` verifies that PoP (passes, since `sender` is authentic), then verifies the accuser-supplied `EncryptionKeyProof` DLEq over `[G, msg.key] → [enc_keys[decryptor], proof.key]` (encryption.rs:381-390). The accuser knows their own `enc_key` discrete log, so they can always produce a valid DLEq for `proof.key = msg.key * enc_key_priv_accuser` against *any* observed ciphertext. The resulting plaintext is unrelated garbage, so `blame_internal` (lib.rs:575-609) reports `sender` as faulty. `AdditionalBlameMachine::new` (lib.rs:649-662) is explicitly callable by anyone "regardless of if the caller was a member in the DKG protocol", and the processor's `VerifyBlame` path accepts `accuser`/`accused`/`share`/`blame` from the coordinator message (processor/src/key_gen.rs:504-519), so this is reachable with purely public, on-chain data — PedPoP share ciphertexts are broadcast/published, not kept secret between pairs.

### Impact Explanation
An incorrect verifier/adjudication formula: the blame protocol outputs the wrong faulty party. Any participant (or external observer using `AdditionalBlameMachine`) can take the public ciphertext `s→A`, claim it was addressed to themselves, attach a valid `EncryptionKeyProof`, and have all adjudicators — including on-chain blame verification via `CoordinatorMessage::VerifyBlame` — conclude honest `s` is faulty. This wrongfully attributes fault, aborts the DKG, and can drive slashing of an innocent validator. The code comment at encryption.rs:84-90 shows the designers analyzed key-reuse attacks across *senders* but did not consider that the *recipient* is equally unbound.

### Likelihood Explanation
Trivially exploitable: requires no secret knowledge beyond the attacker's own DKG encryption key, only public messages. Every DKG session publishes all participants' `EncryptedMessage`s to the shared medium for share distribution and blame arbitration, so the malicious ciphertext input is always available. The only prerequisites are participation in (or observation of) one PedPoP session.

### Recommendation
Bind the intended recipient into the message. Include `to: Participant` in `EncryptedMessage`, append it to `pop_challenge` (e.g., `transcript.append_message(b"recipient", to.to_bytes())` alongside `sender`), and verify the claimed `decryptor` matches the bound recipient in `decrypt_with_proof`/`blame_internal` before evaluating the share. This makes a relayed `s→A` ciphertext fail PoP verification when presented as `s→Eve`, correctly blaming the accuser instead of the sender.

### Proof of Concept
1. Participants 1..n run `KeyGenMachine`/`SecretShareMachine` with context C. Sender `s` produces `res[A]` = `EncryptedMessage` encrypting a valid `SecretShare` to `A`'s `enc_key`; all ciphertexts are published.
2. Attacker `Eve` (participant index `e`, with registered `enc_key_e` whose discrete log `e_priv` she knows) extracts `msg_sa` and builds:
   ```rust
   let key = Zeroizing::new(msg_sa.key * e_priv); // = ecdh(enc_key_e, msg.key)
   let dleq = DLEqProof::prove(rng, &mut encryption_key_transcript(C),
                             &[G::generator(), msg_sa.key], &e_priv);
   let proof = Some(EncryptionKeyProof { key, dleq });
   ```
3. Eve submits blame: `blame(sender: s, recipient: e, msg: msg_sa, proof)`.
4. In `blame_internal`: `msg_sa.pop.verify` passes (challenge binds `s` and the msg bytes, both authentic); `proof.dleq.verify` passes (statement `[G, msg_sa.key] → [enc_keys[e], msg_sa.key*e_priv]` is true); decryption yields gibberish which either fails `C::F::from_repr` or fails `share_verification_statements` — both branches return `sender` = `s` as faulty.
5. Result: honest `s` is blamed and the DKG aborts (potentially slashing `s`), despite `s` having sent only valid shares. Symmetric variant: a real bad share `s→Eve` can be masked by `s` claiming the adjudication should use `s→A`'s ciphertext — the ambiguity cuts both ways because the destination is never committed.
