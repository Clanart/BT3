## Finding

### Title
Shared `CallDispatcher` residual balances silently absorbed into unrelated orders' escrow due to entire-balance sweeps and partial output-only sweeping - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
This is the same bug class as the H-01 report: a contract that indiscriminately reads and consumes the *entire current balance* of a shared helper contract, instead of the delta actually produced by the current operation. In `AdapterV1.sol` this happened because unspent PSM wasn't refunded before `_addLiquidity()` read `PSM.balanceOf(address(this))`. In Hyperbridge's `IntentGatewayV2`, the analogous shared account is the singleton `CallDispatcher` (`_params.dispatcher`), which is reused across **every** order's predispatch and postdispatch calldata execution. The gateway's sweep logic reads `IERC20(token).balanceOf(dispatcher)` / `dispatcher.balance` — the dispatcher's whole balance — rather than a balance delta scoped to the current call, and the postdispatch sweep only covers the tokens declared in the *current* order's `output.assets` list.

### Finding Description
Two mechanisms combine to reproduce the "entire balance used, but not fully refunded/swept" flaw:

1. **Incomplete postdispatch sweep** — `_execute()` in `IntentsBase.sol` dispatches arbitrary, order-creator-controlled calldata (`order.output.call`) through the shared `CallDispatcher`, then sweeps back only the tokens enumerated by `outputsLen = order.output.assets.length`: [1](#0-0) 
If the arbitrary calldata touches or produces a token that is *not* listed in `order.output.assets` (e.g., an intermediate swap token from a DeFi route), that balance is never swept and remains parked in the `CallDispatcher` after the transaction completes.

2. **Entire-balance predispatch sweep in a later, unrelated order** — When any subsequent order's `placeOrder()` uses the *same* token as a `predispatch` input, `IntentGatewayV2.sol` measures "received" by transferring and reading the dispatcher's **whole** balance for that token, not a value scoped to what this order's own predispatch call produced: [2](#0-1) 
The result is compared against the *requested* amount: if it exceeds the request, the excess is merely logged as `DustCollected` (still absorbed, not returned to whoever left it); if it is less than or equal to the request, it is used directly as `order.inputs[i].amount` — i.e., it becomes this order's escrowed/committed input: [3](#0-2) 

Because the `CallDispatcher` address is fixed and public (any account can transfer tokens to it or trigger calls that leave a balance there), and because the gateway's accounting is balance-based rather than delta-based *per caller*, residue left by one order's postdispatch execution is silently folded into whatever the next order happens to compute as its own "actual received" input. This is functionally identical to the reported bug: `PSMBalance = PSM.balanceOf(address(this))` was used to size a subsequent operation instead of the amount actually produced/refunded by the immediately preceding step.

### Impact Explanation
An attacker can engineer a "donor" order whose `output.call` deliberately leaves an unlisted token balance stranded in the shared `CallDispatcher` (simply by omitting that token from `order.output.assets`, or by any calldata path that produces more of an intermediate token than the sweep loop knows about). A follow-up order using that same token as a `predispatch` asset then has that stray balance folded into its own escrow accounting at `placeOrder()` — either reducing the funder's real out-of-pocket contribution for a valid order, or being captured as "protocol dust" ahead of governance's normal `SweepDust` flow. Either outcome is an unauthorized diversion of value that should belong either to whoever left it in the dispatcher or to the protocol treasury, matching the bounty's "stealing or loss of funds" / "logic attack" impact categories.

### Likelihood Explanation
The path requires no privileged role — no relayer, prover, admin, or governance action. It only requires an ordinary user to call `placeOrder`/`fillOrder` with a specially crafted `predispatch`/`output.call`, and a subsequent unprivileged `placeOrder` call reusing the same token. The `CallDispatcher` address is a public, fixed, shared singleton by design (`_params.dispatcher`), so nothing stops an attacker from arranging both transactions themselves, or from opportunistically reading dust left over from other users' orders.

### Recommendation
Track balances relative to a `balanceBefore` snapshot taken immediately prior to each dispatcher interaction and only ever attribute the exact delta produced by *that* interaction to the current order — never the dispatcher's raw, cumulative balance. Additionally, make `_execute()`'s postdispatch sweep exhaustive (sweep every token actually touched by the calldata, not just the tokens declared in `order.output.assets`) so no residue can persist in the shared `CallDispatcher` between orders, closing off the fold-in vector described above.

### Proof of Concept
1. Attacker (as user A) places a same-chain order with `output.assets = [TokenY]` but with `output.call` crafted to swap part of the delivered `TokenY` into `TokenX` inside the `CallDispatcher` (e.g., via an approved router call embedded in `order.output.call`), without listing `TokenX` in `output.assets`.
2. Order A fills; `_fillSameChain` pays the beneficiary directly, then `_execute()` runs `order.output.call`, producing `TokenX` inside the `CallDispatcher`; the sweep loop (bounded by `outputsLen` = 1, only `TokenY`) never sweeps `TokenX`, per `evm/src/apps/intentsv2/IntentsBase.sol` lines 447-473.
3. Attacker (as user B, possibly the same address) calls `placeOrder` with `predispatch.assets` containing a small amount of `TokenX` and `predispatch.call` performing a token swap that intentionally under-produces `TokenX` relative to `order.inputs[i].amount`.
4. During Phase 1 of `placeOrder` (`evm/src/apps/IntentGatewayV2.sol` lines 236-280), `balance = IERC20(TokenX).balanceOf(dispatcher)` includes both order B's swap output *and* the stray `TokenX` left by order A; `received` is computed from this inflated balance and used directly as `order.inputs[i].amount`, letting user B fund a larger/valid escrow than their own predispatch swap actually produced — silently consuming order A's stranded residue.

        if (order.output.call.length == 0) return;

        Call[] memory sweepCalls = new Call[](outputsLen);

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {

                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
