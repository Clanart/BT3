### Title
Unauthenticated `operator_xonly_pk` in payout tx OP_RETURN lets anyone permanently freeze a deposit's move-to-vault UTXO - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The Clementine payout mechanism binds "who fronted a withdrawal" to whatever `operator_xonly_pk` value appears in the OP_RETURN output of the confirmed on-chain payout transaction [1](#0-0) . Because the user's withdrawal signature uses `SinglePlusAnyoneCanPay`, it only commits to the withdrawal input and the matching output (index 0); it does not commit to the OP_RETURN output or to which additional funding inputs are attached [2](#0-1) . Consequently, any unprivileged party who obtains this public, off-chain-shared (and in practice broadcastable/visible) withdrawal signature can construct and confirm their own payout transaction — funding the correct user output from their own wallet, but embedding an arbitrary, non-registered `operator_xonly_pk` (or garbage) in the OP_RETURN. This satisfies Citrea's payout requirement for the user, but since reimbursement bookkeeping is keyed strictly to that OP_RETURN value, no legitimate registered operator will ever discover or claim the corresponding reimbursement, permanently orphaning the deposit's move-to-vault UTXO.

### Finding Description
`create_payout_txhandler` builds the payout transaction with an operator-supplied `operator_xonly_pk` embedded in a plain OP_RETURN output, with no on-chain or witness commitment tying that value to a registered operator: [3](#0-2) 

The only signature present (the user's) is `SinglePlusAnyoneCanPay`, explicitly enforced by the parser: [4](#0-3) 

`SIGHASH_SINGLE | ANYONECANPAY` commits only to the spent input and the output at the same index (the withdrawal payout output). It does **not** cover the OP_RETURN output (containing `operator_xonly_pk`) or the anchor output, and it does not restrict which other inputs are added to fund the transaction. This is exactly the design intended to let *any* registered operator race to front a withdrawal — but the same freedom lets a completely unprivileged party do the same, since nothing validates that the embedded `operator_xonly_pk` corresponds to an actual bridge operator with existing collateral/kickoff/round infrastructure.

When the payout confirms, verifier bookkeeping records whatever key (or `None`) is found in the OP_RETURN, without validating it against the set of known operators: [5](#0-4) 

Reimbursement automation is strictly keyed to matching this exact operator xonly public key. An operator only picks up a payout for reimbursement if the recorded key equals its own signing key: [6](#0-5) 

and during kickoff, any mismatch between the payout's recorded key and the kickoff's operator is explicitly treated as a signal to challenge/reject: [7](#0-6) 

Because the deposited funds already moved into N-of-N/security-council custody at `move_to_vault_tx` time (spendable only via the presigned kickoff/reimburse chain tied to a *specific registered* operator xonly key) [8](#0-7) , if the on-chain payout's OP_RETURN key does not match any registered operator, **no** operator's automation will ever recognize this withdrawal as its own unhandled payout, so no kickoff/reimburse chain is ever initiated for that deposit's move-to-vault UTXO.

### Impact Explanation
This breaks the binding "operator credited (OP_RETURN) == party actually entitled to reimburse against the vault UTXO." An unprivileged attacker can:
1. Obtain the user's `SinglePlusAnyoneCanPay` withdrawal signature (shared off-chain to operators / visible once any operator broadcasts their own competing payout tx to the public mempool).
2. Construct a competing payout transaction reusing the same dust input and exact signed output, adding their own funding input(s) and an arbitrary (non-operator) `operator_xonly_pk` in the OP_RETURN.
3. Get this transaction confirmed first (via replace-by-fee/full-RBF or simply broadcasting before the legitimate operator).

The user still receives their withdrawal (so this is not detected as fraud by Citrea), but the deposit's move-to-vault UTXO — real BTC custodied by the bridge N-of-N/security-council script — can never be released through the normal kickoff/reimburse flow, since no legitimate operator will ever match the bogus recorded key. This matches the Critical impact category "a vault UTXO permanently frozen."

### Likelihood Explanation
The attack requires no privileged role, no key compromise, and no majority/validator collusion — only the ability to observe or obtain a user's already-shared `SinglePlusAnyoneCanPay` signature and to get a transaction confirmed before the legitimate operator's competing transaction (a normal mempool race, potentially assisted by full-RBF policies many nodes/miners run today). The economic cost to the attacker is exactly the withdrawal amount they front (which is returned to them... never, since they embed a bogus key and cannot claim reimbursement) — i.e., it is not "free" for the attacker, but it is cheap relative to the frozen custody amount for high-value deposits, and a griefer motivated purely by disruption (not profit) can execute it at the cost of the withdrawal amount.

### Recommendation
Bind the OP_RETURN `operator_xonly_pk` to the actual party fronting the payout, e.g., by requiring the additional funding input(s) to be spendable only by (or otherwise cryptographically tied to) the declared `operator_xonly_pk`, or by having verifiers validate at deposit/kickoff time that the OP_RETURN key belongs to a currently-registered operator before honoring `is_kickoff_malicious` checks, and by providing a fallback/permissionless path (not requiring security-council privilege) that allows *any* registered operator to claim reimbursement for a payout tx that correctly pays the withdrawal output, regardless of which key is in OP_RETURN, as long as they can prove they funded the qualifying output.

### Proof of Concept
Conceptual PoC (no live network available in this environment):
1. Observe a user's `WithdrawParams` (withdrawal outpoint, `SinglePlusAnyoneCanPay` signature, output script/amount) — obtainable once shared to operators or once any operator's payout tx appears in the public mempool.
2. Build a transaction via `create_payout_txhandler`-equivalent logic: input = the same withdrawal UTXO with the captured signature, output[0] = the exact signed output, output[1] = anchor, output[2] = OP_RETURN with an arbitrary 32-byte value (not any registered operator's xonly pubkey), plus attacker-funded extra input(s) to cover value/fees [9](#0-8) .
3. Broadcast with higher fee than the legitimate operator's version and get it confirmed first.
4. Confirm via `update_finalized_payouts` that `operator_xonly_pk` recorded for this withdrawal is the attacker's bogus value [10](#0-9) , and via `get_first_unhandled_payout_by_operator_xonly_pk` that no legitimate operator's automation ever surfaces this withdrawal [6](#0-5) , leaving the deposit's move-to-vault UTXO permanently unclaimed.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,

    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {

            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash

             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })

pub fn create_move_to_vault_txhandler(
    deposit_data: &mut DepositData,
    paramset: &'static ProtocolParamset,
) -> Result<TxHandler<Unsigned>, BridgeError> {
    let nofn_xonly_pk = deposit_data.get_nofn_xonly_pk()?;
    let deposit_outpoint = deposit_data.get_deposit_outpoint();
    let nofn_script = Arc::new(CheckSig::new(nofn_xonly_pk));
    let security_council_script = Arc::new(Multisig::from_security_council(
        deposit_data.security_council.clone(),
    ));

    let deposit_scripts = deposit_data.get_deposit_scripts(paramset)?;

    Ok(TxHandlerBuilder::new(TransactionType::MoveToVault)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            SpendableTxIn::from_scripts(
                deposit_outpoint,
                paramset.bridge_amount,
                deposit_scripts,
                None,
                paramset.network,
            ),
            SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_output(UnspentTxOut::from_scripts(
            paramset.bridge_amount,
            vec![nofn_script, security_council_script],
            None,
            paramset.network,
        ))
        // always use 0 sat anchor for move_tx, this will keep the amount in move to vault tx exactly the bridge amount
        .add_output(UnspentTxOut::from_partial(anchor_output(Amount::from_sat(
            0,
        ))))
        .finalize())
