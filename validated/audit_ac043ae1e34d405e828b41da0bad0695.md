### Title
`mul-div-down` truncation-to-zero in `resolve-ststx`/`resolve-ztoken` freezes zstSTX-holding positions - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`resolve-ststx` computes `(mul-div-down p ratio STSTX-RATIO-DECIMALS)` with no minimum-output floor, so when the stSTX/STX `ratio` returned by `call-ststx-ratio` is `u1` and the normalized STX price `p` is below `1000000` (i.e. below $0.01 in 8-decimal fixed point), integer division truncates the result to `0`. `resolve-callcode` for `CALLCODE-ZSTSTX` feeds this `0` into `resolve-ztoken`, whose `(* p cached-lindex)` therefore also evaluates to `0`, producing a final zstSTX price of exactly `0`. `oracle-price-legal` then rejects the resolved price and `price-resolve` aborts with `ERR-ORACLE-INVARIANT`.

### Finding Description
Tracing the price for a `CALLCODE-ZSTSTX` asset in `price-resolve`:
1. `resolve-price-feed` returns the raw normalized STX price `p` (8-decimal fixed point). [1](#0-0) 
2. `resolve-callcode` for `CALLCODE-ZSTSTX` calls `(resolve-ztoken (try! (resolve-ststx p)) stSTX)`. [2](#0-1) 
3. `resolve-ststx` computes `(mul-div-down p ratio STSTX-RATIO-DECIMALS)` where `STSTX-RATIO-DECIMALS = u1000000`, and `mul-div-down` is plain floor division `(/ (* x y) z)` with no floor/minimum-output guard. [3](#0-2) [4](#0-3)  With `ratio = u1` and `p < u1000000`, `(* p u1) = p < 1000000`, so `(/ p 1000000) = 0`.
4. This `0` is passed into `resolve-ztoken`, where `(* p cached-lindex)` becomes `(* 0 cached-lindex) = 0`, and `div-down` of `0` is `0`. [5](#0-4) 
5. Back in `price-resolve`, `oracle-price-legal` checks `(> p u0)`, which fails for `final-price = 0`, causing the `asserts!` to trip `ERR-ORACLE-INVARIANT` and abort the whole call. [6](#0-5) 

Since `price-resolve` is invoked (directly or via `price-multi-resolve`/`get-assets`) whenever any user action needs to evaluate the position's assets (withdraw, borrow, repay, liquidate), any position holding zstSTX as collateral or debt will have every such call abort as long as the STX price stays below the $0.01 normalized threshold while the ratio remains `u1`. [7](#0-6) 

No later gate recovers this: `oracle-price-legal` is precisely the check that turns the zeroed price into a hard abort rather than silently mispricing the asset, so the failure mode is a revert/freeze rather than a wrong health verdict.

### Impact Explanation
The direction of the defect is a truncation-to-zero of the resolved zstSTX price, which is caught by `oracle-price-legal` and converted into a full abort of `price-resolve`. No funds are stolen and no incorrect health verdict is produced — the gate does its job of preventing a zero/garbage price from being used in notional math. The practical effect is that every subsequent withdraw/borrow/repay/liquidate call touching a zstSTX-holding position fails with `ERR-ORACLE-INVARIANT` for as long as the extreme STX-price/ratio combination persists. This is a freezing-of-funds condition; because it is contingent on external market/vault-state conditions recovering (STX price rising back above the truncation threshold, or the ratio moving off `u1`), it is a temporary freeze rather than a provably permanent one, since the code contains no mechanism that would keep the price at exactly this pathological combination forever.

### Likelihood Explanation
Reaching this requires two conditions to hold simultaneously: (a) the normalized 8-decimal STX price feed value drops below `1000000` (below $0.01, i.e. a >99% crash from any realistic current STX price), and (b) `call-ststx-ratio` returns exactly `u1`, an extreme stSTX/STX ratio degradation. Both conditions are outside attacker control — they depend on oracle feed values and vault/stacking-protocol state, not on any action an unprivileged attacker can trigger directly. The attacker cannot manufacture either condition through ordinary calls; they can only "benefit" (in the sense of triggering the freeze) by waiting for or timing an action during such an extreme, already-existing market condition. This makes the scenario theoretically reproducible in a simnet test with fixed price/ratio mocks, but very unlikely to occur in practice given the magnitude of price/ratio degradation required.

### Recommendation
Add an explicit floor check in `resolve-ststx` (and generally in `mul-div-down` usages that feed into price resolution) so that a non-zero input price never truncates to a zero output price silently — e.g., round up when the ratio-adjusted price would otherwise floor to zero, or treat a would-be-zero result as a distinct "price degraded" state with its own error rather than relying solely on the generic `oracle-price-legal` zero-check, so operators can distinguish "market crashed, price legitimately near zero" from "truncation artifact, ratio/price combination underflowed."

### Proof of Concept
Clarinet simnet test on a local fork:
1. Mock/stub `call-ststx-ratio` to return `u1`.
2. Mock the Pyth/DIA feed for the STX identifier so `resolve-pyth`/`resolve-dia` returns a normalized price `p = u500000` (i.e. $0.005, still `> 0`).
3. Call a public function that triggers `price-resolve` for an oracle entry configured with `callcode: (some CALLCODE-ZSTSTX)` (e.g., `get-assets` on a position holding zstSTX, or directly exercise `resolve-callcode`/`resolve-ststx` if exposed for testing).
4. Assert `resolve-ststx p` returns `0` (via a read-only test wrapper or by observing the downstream abort).
5. Assert the top-level call aborts with `(err u400014)` (`ERR-ORACLE-INVARIANT`).
6. Repeat with a position holding zstSTX collateral and confirm `withdraw`/`repay`/`liquidate` calls touching that position all abort with the same error, demonstrating the freeze.
