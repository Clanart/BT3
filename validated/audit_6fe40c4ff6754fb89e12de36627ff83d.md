### Title
Taproot tweak offset is not persisted with `ThresholdKeys`, so restored keys no longer match the confirmed network key and received funds become unspendable - (File: crypto/dkg/src/lib.rs)

### Summary
The source bug class is: an operation completes (closing the Synthetix position / confirming tweaked keys) but global/persistent bookkeeping is never updated, so the assets involved become stranded and unusable. In Serai, the analogous shape is `ThresholdKeys` tweak state: `scale`/`offset` are explicitly ephemeral and are dropped by `ThresholdKeys::write`/`ThresholdKeys::read`, while the Bitcoin pipeline relies on exactly those ephemeral adjustments (`tweak_keys`) for the group key under which the multisig is confirmed on-chain and under which `Scanner`/`ReceivedOutput` spendability is defined.

### Finding Description
`ThresholdKeys` stores `scalar` and `offset` outside the persisted `ThresholdCore`: they are initialized to `ONE`/`ZERO` in `ThresholdKeys::new` and only mutated in-memory by `scale` and `offset` (`#[must_use]`, "This scalar is ephemeral and will not be included when these keys are serialized"). `serialize`/`read` confirm this: `serialize` "will not include the ephemeral scalar/offset", and `read` reconstructs via `ThresholdKeys::new`, resetting scalar/offset.

Separately, the Bitcoin wallet's `tweak_keys` applies a TapTweak offset and a conditional negation purely through `keys.offset(...)` and `keys.scale(...)` — i.e., entirely into the ephemeral fields. In the processor key-gen flow, `N::tweak_keys(&mut these_network_keys)` is invoked and the resulting keys are persisted via `GeneratedKeysDb::save_keys`. The group key committed to Substrate (asserted in `KeysDb::confirm_keys` via `key_pair.0 .0 == keys.0[0].group_key().to_bytes()`) is the *tweaked* key.

If `save_keys`/`read_keys` round-trip through `ThresholdKeys::write`/`read` (which the code strongly suggests — there is no alternate serialization path for `ThresholdKeys`), then after a processor restart the restored keys have `scalar = 1, offset = 0`, i.e., the *untweaked* group key, while the protocol's global state (the confirmed `KeyPair` on Substrate, `Scanner::key`, and every `ReceivedOutput.offset`) continues to reference the tweaked key. Just like the source bug, the "close" step (persistence) dropped the bookkeeping that makes the assets actionable.

### Impact Explanation
Any `ThresholdKeys` reload (processor reboot/crash recovery, which the codebase explicitly anticipates — see the `unwrap_or_else` rebuild paths in `processor/src/key_gen.rs` and the `CachedPreprocess`/`CommitmentsDb` recovery comments) yields keys whose `group_key()` is the pre-tweak key. Signing views (`ThresholdView`) interpolate untweaked secret shares, so produced signatures verify against the wrong group key: outputs scanned under the tweaked Taproot script (`Scanner::scan_transaction` → `ReceivedOutput`) are reported received but are not spendable by the restored signers. This is exactly the "funds reported received that are not spendable" / stranded-collateral impact of the source report.

### Likelihood Explanation
The defect triggers on any restart of a processor that has confirmed tweaked network keys — a routine operational event, no attacker action required. Severity is bounded by whether `GeneratedKeysDb::read_keys` uses `ThresholdKeys::read` (unverified; if it uses a different serialization that preserves scalar/offset, the bug does not manifest). As such, this is a Medium-severity accounting/consistency analog rather than an attacker-reachable exploit: no unprivileged party can force the reload through public `read_*`/sign inputs.

### Recommendation
Persist `scalar` and `offset` in `ThresholdKeys::write`/`read` (or persist the pre-tweak keys plus the tweak derivation and re-apply `N::tweak_keys` on load), and add a round-trip test asserting `read(write(k))` preserves `group_key()` after `tweak_keys`. If ephemeral tweaks are intentionally unpersisted, then `read_keys` must re-apply `N::tweak_keys` and `confirm_keys`'s group-key assertion must be re-validated post-restore.

```rust
// On restore:
let restored = ThresholdKeys::<Secp256k1>::read(&mut serialized.as_slice()).unwrap();
// restored.scalar == 1, restored.offset == 0
// restored.group_key() == PRE-tweak key != key_pair confirmed on Substrate
// Signatures from restored views fail for the tweaked P2TR key;
// ReceivedOutput::offset only covers HDKD offsets, not the lost base tweak.
```
Supporting code: `ThresholdKeys::new` resets scalar/offset (`crypto/dkg/src/lib.rs:380-390`), `serialize`/`read` omit them (`crypto/dkg/src/lib.rs:565-631`), `tweak_keys` relies solely on `offset`/`scale` (`networks/bitcoin/src/wallet/mod.rs:46-75`), persisted after `N::tweak_keys` (`processor/src/key_gen.rs:476-494`), confirmed under tweaked `group_key` (`processor/src/key_gen.rs:98-105`), and `Scanner`/`ReceivedOutput` key off the tweaked point (`networks/bitcoin/src/wallet/mod.rs:162-214`).

Caveat: I could not fully verify `GeneratedKeysDb::save_keys`/`read_keys` internals; if they re-apply `N::tweak_keys` on read, this analog does not hold.
