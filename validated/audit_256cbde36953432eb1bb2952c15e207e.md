## Finding Analysis

I traced the parsing logic in `listSubmodules` and confirmed the regex has a genuine ambiguity, though the practical exploitability is more limited than "arbitrary wrong path" — it depends on backtracking behavior.

### Title
Greedy/backtracking regex in `listSubmodules` can misparse `SubmoduleEntry.path` when the `git describe` output contains a crafted `" ("` sequence - (File: `app/src/lib/git/submodule.ts`)

### Summary
`listSubmodules` parses the output of `git submodule status --` with the regex: [1](#0-0) 
`/^.([^ ]+) (.+) \((.+?)\)$/gm`. The `path` group is greedy (`.+`) and the `describe` group is lazy (`.+?`), but both are ultimately resolved by backtracking from the end of the line. Because regex backtracking for a greedy quantifier reduces length from the maximum and tries the **rightmost** possible split point first, if the string wrapped in the trailing parentheses (the `git describe` output) itself contains the literal sequence `" ("`, the engine will split at that inner occurrence instead of the true boundary between the real path and the real describe text. This causes the captured `path` group to absorb extra trailing characters that belong to the describe field (e.g. `"foo/submodule (1.0"` instead of `"foo/submodule"`).

### Finding Description
Git ref names (branches/tags) permit parentheses — they are not in the set of characters disallowed by `git check-ref-format`. Since `describe` is produced by `git describe` against refs that live inside a submodule that an attacker fully controls (a malicious repository can add its own submodule with an attacker-crafted tag such as `1.0 (evil`), the attacker can make the final `git submodule status` line look like:
```
 <sha> foo/submodule (1.0 (evil) genuine)
```
For this line, the regex's greedy `path` group first attempts to match as much as possible and backtracks from the right; the **rightmost** `" ("` in the line (the one before `evil)`) is found before the correct one (the one right after `foo/submodule`), because backtracking tries the longest `path` match first. This produces:
- `path` = `"foo/submodule (1.0"` (WRONG — includes extra text that isn't part of the real on-disk directory)
- `describe` = `"evil) genuine"` (unused elsewhere)

The resulting `SubmoduleEntry.path` no longer matches the real submodule directory name recorded in `.gitmodules`/the index.

### Impact Explanation
`SubmoduleEntry.path` is consumed by `resetSubmodulePaths` (used for "discard changes" on submodules) which passes the value directly as a positional pathspec argument after `--` to `git submodule update --recursive --force -- <path>`: [2](#0-1) 
Because the `--` separator is present, this is **not** an argument-injection/flag-injection vector — a malformed path is simply an argument to git, not an option. Practically, git will fail to resolve the bogus path against any known submodule and the reset/update operation for that submodule will either error out or silently no-op, meaning any local (potentially attacker-planted) modifications to that submodule are **not reverted** when the user believes they discarded changes. I was not able to fully trace all downstream consumers of `SubmoduleEntry.path` in `app/src/lib/stores/git-store.ts` within the available tool budget, so I cannot conclusively state whether it also affects a diff-rendering sink that could produce a more severe primitive (e.g., a path traversal write). Given the `--` separator protecting `resetSubmodulePaths`, the confirmed impact is a silent failure of the discard/reset-to-recorded-commit operation for the crafted submodule, not direct code execution or file write outside the repo.

### Likelihood Explanation
Requires an attacker to control a submodule inside a cloned/fetched repository and to craft a ref name containing `" ("` such that `git describe` resolves to it — feasible since ref names permit parentheses, but the attack needs the crafted ref to actually be the "best" describe candidate for the current checkout, and needs a specific character layout to win the backtracking race. This is a real but narrow parsing bug, not a broadly reliable path-confusion primitive to an arbitrary attacker-chosen filesystem path.

### Recommendation
Replace the fragile combined regex with a two-step parse: first strip the trailing `" (…)"` block by matching from the **first** legitimate `" ("` after the fixed-width SHA field (the format is well known: 1-char status + 40-char SHA + space + path + space + `(` + describe + `)`), or better, split on the first space after the known 40-hex-char SHA to get `path` unambiguously, then treat everything from the next `" ("` to the trailing `")"` as `describe`, without relying on backtracking to disambiguate embedded parentheses.

### Proof of Concept
1. Create a repository with a submodule added at `foo/submodule`.
2. Inside the submodule, create a tag/branch such that `git describe` for its current commit resolves to a string containing `" ("`, e.g. tag it as `1.0 (evil`.
3. In the parent repo, run `git submodule status --` and observe a line like: ` <sha> foo/submodule (1.0 (evil) genuine)`.
4. Call `listSubmodules(repository)` and inspect `result[0].path` — it will equal `"foo/submodule (1.0"` instead of `"foo/submodule"`.
5. Call `resetSubmodulePaths(repository, [result[0].path])` and observe that git fails to match the pathspec / does not reset the intended submodule directory. [3](#0-2) [4](#0-3)

export async function resetSubmodulePaths(
  repository: Repository,
  paths: ReadonlyArray<string>
): Promise<void> {
  if (paths.length === 0) {
    return
  }

  await git(
    ['submodule', 'update', '--recursive', '--force', '--', ...paths],
    repository.path,
    'updateSubmodule'
  )
}
