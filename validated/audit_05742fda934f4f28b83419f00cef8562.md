### Title
Indexing panic in `Decryption::decrypt_with_proof` on unregistered participant index allows remote crash - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (a `HashMap`) without a membership check. A blame/accusation flow that feeds an attacker-controlled `EncryptedMessage` and an attacker-claimed `decryptor`/`from` participant index into this function crashes the host process when the index was never registered, even though the attacker passes the earlier PoP check trivially.

### Finding Description [1](#0-0) 

`decrypt_with_proof` performs two steps on untrusted input:

1. `msg.pop.verify(msg.key, pop_challenge(..., from, msg.msg))` — the Schnorr PoP is over the attacker-chosen `msg.key` and their chosen `from` index, so an attacker can always satisfy it by signing with their own key.
2. `proof.dleq.verify(..., &[self.enc_keys[&decryptor], *proof.key])` — `self.enc_keys` is populated only in `Decryption::register` for participants that completed commitment registration. If `decryptor` is a `Participant` index outside the registered set (e.g. `accuser`/`decryptor` values `> n`, or a participant whose commitment message was never processed), the `HashMap` index operator panics — there is no `get`/graceful-error path.

`Participant` only guarantees non-zero (`Participant::new` returns `None` for 0); any value `> n` is representable. The caller-side blame path (`VerifyBlame` → `AdditionalBlameMachine::blame` → `decrypt_with_proof`) passes the accuser-supplied indices and serialized `EncryptedMessage` bytes through to this function, so the panic is reachable from bytes an unprivileged counterparty supplies during blame verification.

### Impact Explanation
This is a availability-only crash: a single crafted accusation/blame message with an out-of-set `decryptor` index (plus a trivially valid self-signed PoP and a syntactically valid `DLEqProof` blob, or `None` proof in flows that reach the indexing line) aborts the processor thread/handles via panic. During a slash/blame round, crashing the verifying validator prevents it from adjudicating blame and can stall the key-generation recovery process — an easily repeatable hang/crash analogous to the MySQL optimizer DoS class (unauthenticated-to-low-privileged input causing complete DOS of a component).

### Likelihood Explanation
Reachable whenever a caller wires `decrypt_with_proof` to network-supplied accusation data (the Serai `VerifyBlame` handler does). The preconditions are weak: the PoP check is satisfiable with an attacker-generated ephemeral key, and the panic is deterministic on an unregistered index — no race, no probabilistic condition. The trigger requires an in-progress DKG/blame context, which exists at known protocol phases.

### Recommendation
Replace the indexing with a fallible lookup: `let decryptor_key = self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?;` before `proof.dleq.verify`. Similarly, `Encryption::encrypt`'s `self.decryption.enc_keys[&participant]` and `ThresholdView::original_verification_share`/`verification_share` (`crypto/dkg/src/lib.rs:672-682`) share the same panicking-index pattern and should be audited wherever participant indices originate from untrusted messages.

### Proof of Concept
```rust
// crypto/dkg/pedpop — conceptual PoC
// Build a Decryption registered only for participant 1 (n = 1).
let mut dec = Decryption::<Ristretto>::new(context);
dec.register(Participant::new(1).unwrap(), commitments_msg);

// Attacker crafts an EncryptedMessage with their own ephemeral key + valid PoP
// for `from = Participant(1)`, then triggers decrypt_with_proof with
// decryptor = Participant::new(2).unwrap() — never registered.
let result = dec.decrypt_with_proof::<SecretShare<_>>(
    Participant::new(1).unwrap(),   // from
    Participant::new(2).unwrap(),   // decryptor: not in enc_keys
    attacker_msg_with_valid_pop,
    Some(attacker_dleq_proof),
);
// panics at `self.enc_keys[&decryptor]` before DLEq verification completes
```

Note: I could not fully trace `AdditionalBlameMachine::blame`'s plumbing of the accuser index into `decrypt_with_proof` within the available context; the panic site itself (`self.enc_keys[&decryptor]`) is confirmed, and reachability depends on the caller passing an accusation-supplied participant index, which `processor/src/key_gen.rs`'s `VerifyBlame` path (`blame(accuser, accused, ...)`) indicates.
