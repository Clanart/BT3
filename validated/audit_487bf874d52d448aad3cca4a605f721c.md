## Finding

### Title
Duplicate input-token escrow pooling in Tron `IntentGatewayV2.placeOrder` enables disproportionate escrow release on partial/full fill - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM `IntentGatewayV2.sol` escrow-crediting loop explicitly rejects duplicate input tokens per order (`if (_orders[commitment][token] != 0) revert InvalidInput();`) before writing to the escrow map. The Tron variant of the same contract omits this guard and instead accumulates escrow with `+=`, allowing multiple `order.inputs[]` entries for the same token to be silently pooled under one storage key.

### Finding Description
In the canonical contract, escrow crediting is guarded against duplicate tokens: [1](#0-0) 

The Tron contract performs the equivalent step without any such check, using `+=` to accumulate escrow per token address regardless of how many `order.inputs[]` entries reference it: [2](#0-1) 

Downstream fill logic (in the shared same-chain fill path used across the IntentGateway family) computes the escrow amount to release per output index `i` against `order.inputs[i]`, and on a fully-completed fill for that output index releases the **entire remaining balance stored under that token's key** rather than only the portion attributable to input index `i`: [3](#0-2) 

Because the escrow key is `(commitment, token)` — not `(commitment, inputIndex)` — and the Tron variant permits multiple `inputs[]` entries with the same token address to be silently merged into that single key, a user placing an order can declare, e.g., `inputs[0] = {token: T, amount: 1}` paired with a tiny `output[0]`, and `inputs[1] = {token: T, amount: 999_900}` paired with a large `output[1]`. Both entries are summed into `_orders[commitment][T] = 999_901`. A solver who fully satisfies only `output[0]` (the negligible one) triggers the `amountFilled == totalRequired` branch, which reads and releases the **full pooled balance** `_orders[commitment][T]` — not the `1` unit that output[0]'s fill actually earned.

This is a direct structural analog of the Balancer report: the code substitutes an aggregate/pooled quantity (summed escrow across multiple positions sharing one key) for the correct per-position value, exactly as the Balancer LP valuation substituted raw `totalSupply()` for the true circulating `getActualSupply()`. In both cases a value that looks like "the total for this key" is used where "the value specific to this position" was required, producing gross over-payment.

### Impact Explanation
A solver can extract far more escrowed value than the output actually delivered, directly stealing user funds through the public `placeOrder`/`fillOrder` entrypoints — matching the bounty's "stealing or loss of funds," "transaction manipulation," and "logic attacks" categories. No relayer, prover, or admin compromise is needed; the attacker only needs to author a self-serving order (or collude as both user and solver) and call the two public functions.

### Likelihood Explanation
High for any deployment where the Tron contract is live: the missing check is in a public, unprivileged entrypoint (`placeOrder`) reachable by any user, and the exploit requires no special timing, front-running, or trusted-role compromise — just constructing an order with a repeated input token address across indices matched to mismatched output amounts.

### Recommendation
Add the same duplicate-input-token rejection used in the canonical EVM contract to the Tron `placeOrder` implementation, or, if multiple entries for the same token are intentionally supported, change escrow accounting to key by `(commitment, inputIndex)` instead of `(commitment, token)` so the fill/withdraw path can never conflate two logically distinct escrowed positions that happen to share a token address.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [{token: T, amount: 1}, {token: T, amount: 999_900}]` and matching `order.output.assets = [{token: X, amount: 1}, {token: Y, amount: large}]`.
2. Escrow crediting loop accumulates: `_orders[commitment][T] += 1` then `+= 999_900` → `_orders[commitment][T] = 999_901`, with no revert since no duplicate check exists.
3. Solver calls `fillOrder`, fully satisfying only `output[0]` (paying `1` unit of `X`).
4. Fill logic hits `amountFilled == totalRequired` for index 0 and reads `escrowedAmount = _orders[commitment][T]`, releasing the **entire 999,901** pooled balance to the solver for a fill that should have earned only `1`.

**Note on verification limits:** I confirmed the missing duplicate-token check by direct comparison of the two `placeOrder` implementations, and confirmed the "release full remaining balance on full-fill" pattern in the shared `IntrinsicIntents._fillSameChain` used by the canonical EVM gateway family. I was not able to read the Tron contract's own `fillOrder`/withdraw body in this session (ran out of tool calls) to confirm byte-for-byte that it reproduces the identical `amountFilled == totalRequired → release full key balance` branch rather than some other release formula — this should be verified directly against `evm/tron/contracts/apps/IntentGatewayV2.sol`'s fill/withdraw functions before treating the PoC amounts as exact, though the core defect (missing duplicate-input-token guard enabling escrow pooling under a shared key) is confirmed from source.
