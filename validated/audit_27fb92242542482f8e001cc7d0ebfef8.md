### Title
Wrong Argument Passed to `deposit_constant()` in Host-Side Bridge Proof Verification — (`bridge-circuit-host/src/structs.rs`)

---

### Summary

`host_deposit_constant()` in `bridge-circuit-host/src/structs.rs` passes `deposit_value_bytes` (the EIP-1186 storage-proof value, i.e. the deposit amount) as the 4th argument to `deposit_constant()`, where `move_txid` is required. The ZK circuit in `circuits-lib/src/bridge_circuit/mod.rs` correctly passes `*move_txid` at the same position. Because the two callers supply different values for the same parameter, the host-computed `DepositConstant` will never equal the circuit-committed `DepositConstant`, so every bridge-circuit proof produced by an honest operator will fail host-side verification.

---

### Finding Description

`deposit_constant()` has the following signature:

```rust
// circuits-lib/src/bridge_circuit/mod.rs  (lines 634-641)
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],          // ← 4th parameter
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant
```

**Circuit call-site (correct):**

```rust
// circuits-lib/src/bridge_circuit/mod.rs  (lines 221-229)
let deposit_constant = deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    *move_txid,          // ← move_txid  ✓
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
);
```

**Host call-site (wrong):**

```rust
// bridge-circuit-host/src/structs.rs  (lines 505-515)
let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    deposit_value_bytes,   // ← deposit amount, NOT move_txid  ✗
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
```

`deposit_value_bytes` is the 256-bit big-endian encoding of the deposit amount (in satoshis) read from the EIP-1186 storage proof. `move_txid` is the 32-byte txid of the move-to-vault Bitcoin transaction. They are semantically and numerically unrelated.

The host-computed `DepositConstant` is consumed by `SuccinctBridgeCircuitPublicInputs::new()` and then by `host_journal_hash()`:

```rust
// bridge-circuit-host/src/structs.rs  (lines 436, 455-461)
let deposit_constant = host_deposit_constant(&bridge_circuit_input)?;
...
pub fn host_journal_hash(&self) -> blake3::Hash {
    journal_hash(
        self.payout_tx_block_hash,
        self.latest_block_hash,
        self.challenge_sending_watchtowers,
        self.deposit_constant,   // ← wrong value propagates here
    )
}
```

The `host_journal_hash` is compared against the proof's public output. Because the host's `deposit_constant` is computed from the deposit amount while the circuit's is computed from `move_txid`, the two journal hashes will never match for any valid proof. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

---

### Impact Explanation

- **Operator collateral slashed**: Every honest operator that fronts a withdrawal and then tries to prove the payout via the bridge circuit will have their proof rejected by the host. Unable to submit a valid proof on-chain before the challenge window expires, the operator's collateral UTXO is burned by the disprove/timeout path.
- **Bridge liveness broken**: No withdrawal can ever be finalized through the challenge path, because the proof verification step is permanently broken for all deposits.
- **Material fund loss**: Operator collateral (bridge-controlled UTXOs) is permanently destroyed for every challenged payout.

This matches the allowed impact gate: *permanent lock or slashable exposure of operator collateral*.

---

### Likelihood Explanation

The bug is in a mandatory code path executed for every bridge-circuit proof. It requires no special attacker action — any challenger that initiates a challenge against an honest operator will trigger the broken verification. The failure is deterministic and 100% reproducible.

---

### Recommendation

In `host_deposit_constant`, derive `move_txid` from the storage proof and the payout transaction (mirroring `get_move_txid` used inside the circuit), and pass it as the 4th argument:

```rust
// bridge-circuit-host/src/structs.rs
let move_txid: [u8; 32] = get_move_txid(&input.sp, &input.payout_spv.transaction)?
    .to_byte_array();   // or however the host derives it

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    move_txid,           // ← correct
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
```

Add a unit test that constructs a `BridgeCircuitInput`, runs both the circuit-side and host-side `deposit_constant` computations, and asserts they are equal.

---

### Proof of Concept

1. Operator fronts a withdrawal and broadcasts a kickoff transaction.
2. A challenger sends the `Challenge` transaction.
3. Operator runs the bridge circuit (RISC Zero) to generate a proof. The circuit computes `deposit_constant` using `move_txid` and commits it in the proof's journal.
4. The operator's host code calls `SuccinctBridgeCircuitPublicInputs::new()`, which calls `host_deposit_constant()`. This computes `deposit_constant` using `deposit_value_bytes` (the deposit amount) instead of `move_txid`.
5. `host_journal_hash()` produces a hash that differs from the circuit's journal hash.
6. Proof verification fails. The operator cannot submit a valid proof on-chain.
7. The assert timeout expires; the disprove/timeout transaction burns the operator's collateral.
8. The operator loses their entire collateral for an honest payout. [5](#0-4) [1](#0-0) [6](#0-5)
