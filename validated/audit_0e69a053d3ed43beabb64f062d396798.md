### Title
`Scanner::register_offset` accepts arbitrary scalars with no provenance check, allowing earlier registrations to silently shift later offsets and attribute deposits to the wrong spend key - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The analog of the missing-access-control `addAsset()` report is `Scanner::register_offset` in `networks/bitcoin/src/wallet/mod.rs:180`. Like `StargateAM::addAsset`, it is a public, state-mutating registration function that inserts entries into an internal allow-map (`scripts: HashMap<ScriptBuf, Scalar>`) with no authorization or provenance check on who/what supplies the `Scalar`, and its behavior depends on registration order.

### Finding Description
`register_offset` mutates the scanner's `scripts` table for any caller-supplied scalar. Two properties combine badly:

1. **Surjective, order-dependent mapping.** If `key + offset*G` is odd (unusable under BIP-340), the offset is incremented in a loop until an even, unregistered script is found (`wallet/mod.rs:180-196`). The doc itself admits "offsets are surjective, not bijective, and the order offsets are registered in may determine the validity of future offsets."
2. **Documented security precondition unenforced.** The doc states "The offsets registered must be securely generated. Arbitrary offsets may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script (not by the signature of the key)" — yet nothing in the function enforces this; it is `pub` and takes any `Scalar`.

If an offset derived from an earlier registration collides with (or pre-occupies) the script a later legitimate offset would map to, the legitimate offset is silently bumped to `offset+N`. `scan_transaction` then returns `ReceivedOutput`s tagged with a different `offset` scalar than the one the signer/protocol expects for that deposit (`wallet/mod.rs:199-214`).

### Impact Explanation
A `ReceivedOutput` binds an `offset` to an on-chain outpoint; downstream the threshold signing applies that offset to recover the spend key. If an attacker-influenced or earlier registration forces a legitimate offset to shift (or squats its script so `None` is returned and the offset is never registered), deposits are either reported received under a mismatched scalar — producing signatures that don't correspond to the output's key, i.e. funds reported received that are not spendable — or an attacker-chosen offset introduces an arbitrary script path, letting the output be spent without the group's signature at all.

### Likelihood Explanation
Reachability requires that an unprivileged party's inputs influence the scalar passed to `register_offset` before the legitimate registration (e.g., offsets derived from deposit/refund metadata) — the caller in `processor/src/networks/bitcoin.rs` is outside the strict scope boundary and was not fully verified, which is the main uncertainty. Given that, likelihood is moderate rather than guaranteed; the primitive itself (order-dependent, unchecked registration) is confirmed in scope.

### Recommendation
- Make `register_offset` reject offsets not produced by the protocol's own deterministic derivation, or take a domain-separated commitment rather than a raw `Scalar`.
- On collision, return a distinct error instead of silently incrementing to `offset+N`, so mismatched registrations cannot be conflated with the intended spend key.
- Treat the `scripts` map as authoritative-only state: registration should require the same trust level as the key it extends.

### Proof of Concept
```rust
// Conceptual, on networks/bitcoin Scanner
let mut scanner = Scanner::new(group_key).unwrap();

// Legitimate protocol intends offset o, where key + o*G is odd.
let o = Scalar::from(1u64); // suppose p2tr_script_buf(key + o*G) == None

// An earlier registration (attacker-influenced metadata) occupies o+1's script.
scanner.register_offset(o + Scalar::ONE);

// Now the legitimate registration silently shifts to o+2 (or beyond).
let used = scanner.register_offset(o).unwrap();
assert_ne!(used, o); // deposit bound to o+2, not the expected o
```
