# UniswapIncentive-style int256 cast overflow in VWAPOracle.recordSpread

### Title
Unbounded `uint256→int256` cast on solver-controlled output amount corrupts VWAPOracle cumulative state - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
`IntentGatewayV2.fillOrder` calls `IIntentPriceOracle(_params.priceOracle).recordSpread(...)` after every fill, passing the order's escrowed `inputs` and the solver-supplied `options.outputs` directly to `VWAPOracle.recordSpread`. That function normalizes both amounts and casts them from `uint256` to `int256` with no range check, exactly the pattern the Fei report flags in `getBuyIncentive`/`getSellPenalty`: a caller-controlled amount is cast to a signed integer that can silently wrap when it exceeds `type(int256).max`. [1](#0-0) [2](#0-1) 

### Finding Description
`recordSpread` is restricted to `_intentGateway` (`restrict(_intentGateway)`), but `IntentGatewayV2.fillOrder` — a fully public, unprivileged entrypoint — forwards attacker-influenced values straight into it: [3](#0-2) 

- `outputAmountNormalized` is derived from `options.outputs[i].amount` (chosen by whoever calls `fillOrder`, i.e. the solver) and from `IERC20Metadata(outputToken).decimals()` — read directly off the token contract, with **no governance allowlist on output tokens**. `order.output.assets[i].token` is picked by whoever calls `placeOrder`, which is also unprivileged.
- Nothing in `IntentGatewayV2` (`placeOrder`/`fillOrder`/`_fillSameChain`) restricts which ERC-20 contract can be used as an output token, and a solver only needs to supply `amount >= totalRequired` (see `IntrinsicIntents._fillSameChain`, which allows arbitrarily large `solverAmount`). [4](#0-3) 

An attacker can therefore act as both the order's user and its solver: deploy a self-mintable ERC-20 with `decimals() == 0`, place a same-chain order whose output asset is that token, then fill their own order supplying a huge raw `amount` of self-minted tokens. `_normalizeAmount` scales that by `10**18` (since `decimals < 18`): [5](#0-4) 

Once `outputAmountNormalized` exceeds `type(int256).max` (~5.79e76), the explicit cast `int256(outputAmountNormalized)` wraps to a negative value — Solidity ≥0.8 only reverts on overflowing *arithmetic*, not on explicit `int↔uint` conversions. The resulting corrupted `amountDiff`/`spreadBps`/`weightedSpread` is then folded into the oracle's persistent, shared cumulative state: [6](#0-5) 

This is the same broken invariant as the Fei report: a pre/post-transfer accounting hook performs signed-integer math on an amount that was never range-checked before the cast, letting an unprivileged caller push it out of bounds.

### Impact Explanation
The corrupted value lands in `_tokenSpreads[sourceChainHash][inputToken]`, a mapping keyed by the *real, governance-recognized* source-chain input token (e.g. USDC/DAI) — so the wrap poisons the on-chain cumulative VWAP/spread data that Hyperbridge's `IIntentPriceOracle` exposes for that legitimate token going forward, for every future order that uses it as an input, regardless of which user or solver is involved. `weightedSpreadSum` and `totalVolume` can be driven to arbitrary, attacker-chosen (including wildly negative or wrapped) values with a single self-fill, since nothing bounds the magnitude of a single contribution before it's summed into permanent storage. This is a false/corrupted on-chain state-acceptance bug in the intent-settlement price-tracking surface: exactly the class of "false state acceptance" the bounty scope calls out, reached purely through the public `fillOrder`/`placeOrder` entrypoints with no relayer, prover, or governance involvement.

I could not find any additional on-chain contract in this repository that reads `IIntentPriceOracle.spread()` to directly gate a fund transfer (the only consumers I found are the getter itself and its test suite); the SDK's `FXFiller` price guard is a separate, off-chain-configured mechanism unrelated to this on-chain oracle. I flag this uncertainty explicitly: the confirmed, provable defect is corruption of the oracle's persisted state via an unchecked cast reachable by an unprivileged attacker; whether a specific downstream fund-moving consumer of this corrupted value exists elsewhere (or will be added, since the oracle is clearly built for that purpose) is not something I could verify from the indexed code.

### Likelihood Explanation
High for the state-corruption itself: no privileged role, relayer, or governance action is required — a single attacker-controlled transaction (`placeOrder` + `fillOrder` on their own order, using a self-deployed ERC-20 with `decimals()==0`) is sufficient to drive the cast out of bounds. The only cost to the attacker is gas and self-minted tokens they already control.

### Recommendation
Bound the normalized amounts before casting to `int256` in `VWAPOracle.recordSpread` — e.g. `require(outputAmountNormalized <= uint256(type(int256).max))` (and likewise for `inputAmountNormalized`) or use OpenZeppelin's `SafeCast.toInt256`, which reverts instead of silently wrapping. Additionally consider capping per-fill contribution size (`weightedSpread`) and/or an allowlist for `decimals()`-reporting output tokens, mirroring the source-side `_tokenDecimals` governance gate that already exists for input tokens.

### Proof of Concept
1. Attacker deploys `EvilToken` (ERC-20, `decimals() == 0`, unrestricted `mint`) and mints itself `2^250` raw units.
2. Attacker calls `IntentGatewayV2.placeOrder` with `order.inputs` = a small amount of a real, oracle-registered token (e.g. 1 USDC) and `order.output.assets[0].token = EvilToken`, `amount = 1` (trivially satisfiable).
3. Attacker (as solver) calls `fillOrder` with `options.outputs[0].amount = 2^250` of `EvilToken` (self-minted, self-transferred to themselves as beneficiary — no real economic cost beyond gas).
4. `_fillSameChain` accepts the fill (`solverAmount >= totalRequired`), then `IntentGatewayV2.fillOrder` calls `VWAPOracle.recordSpread(commitment, order.source, order.inputs, options.outputs)`.
5. Inside `recordSpread`, `_normalizeAmount(2^250, 0)` returns `2^250 * 1e18`, far exceeding `type(int256).max`; `int256(outputAmountNormalized)` wraps negative, corrupting `spreadBps`/`weightedSpread`, which is then summed into `_tokenSpreads[sourceChainHash][usdcAddress]` — permanently poisoning the cumulative VWAP data for the real USDC entry used by all other orders.

    function recordSpread(
        bytes32 commitment,
        bytes memory sourceChain,
        TokenInfo[] calldata inputs,
        TokenInfo[] calldata outputs
    ) external restrict(_intentGateway) {
        // Validate inputs and outputs have the same length
        if (inputs.length != outputs.length || inputs.length == 0) {
            return;
        }

        bytes32 sourceChainHash = keccak256(sourceChain);
        uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

            // Calculate spread for this token: (output - input) / input * 10000
            // Positive spread = filler provided more tokens (good for user)
            // Negative spread = filler provided fewer tokens (filler captured spread)
            int256 spreadBps = 0;
            if (inputAmountNormalized > 0) {
                int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
                spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
            }

            // Update cumulative spread data for this token (weighted by volume)
            int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
            _updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);

            // Emit event for each token
            emit SpreadRecorded(commitment, outputToken, spreadBps);
        }
    }

    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
    }
