## Finding

**Missing `--` end-of-options separator when passing attacker-controlled PR clone URLs to `git remote add` / `git remote set-url`** — (File: `app/src/lib/git/remote.ts`)

### Summary
GitHub Desktop's `git clone` invocation explicitly guards against argument injection by inserting a `--` separator before the URL and destination path, but the sibling `addRemote`/`setRemoteURL`/`removeRemote` helpers in the same module do not apply that same guard, even though they are fed attacker-controlled strings (a pull request's head clone URL, which the PR author fully controls) with no zero/empty/format validation. This mirrors the report's bug class: a protective check exists for one code path but is silently skipped for another, structurally-identical path that a remote party can reach.

### Finding Description
`clone()` treats the caller-supplied URL as untrusted and defends against it being interpreted as a Git option by terminating the option list first: [1](#0-0) 

`addRemote`, `removeRemote`, and `setRemoteURL`, however, pass their `name`/`url` arguments straight into the argv array with no `--` separator: [2](#0-1) [3](#0-2) 

These functions are reachable with values that originate entirely from a GitHub API pull-request object under the control of whoever opened the PR/fork: `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, headCloneUrl)` where `headCloneUrl` is `pullRequest.head.repo.clone_url` (or `pullRequest.head.gitHubRepository.cloneURL`) — i.e., the PR author's fork clone URL, verbatim from the API/deep link flow: [4](#0-3) [5](#0-4) 

`ensureUpstreamRemoteURL`/`updateRemoteUrl` similarly feed an API-supplied `clone_url` into `setRemoteURL` without an options separator: [6](#0-5) [7](#0-6) 

None of these call sites validate that the URL does not begin with `-` (which Git's argument parser would treat as an option rather than a positional value), unlike `clone()`, which forecloses that entirely via `--`. There is also no `GIT_ALLOW_PROTOCOL`/`GIT_PROTOCOL_FROM_USER` hardening anywhere in the codebase to constrain which transports/options Git subcommands will honor, so the only protection against this class of issue is the (inconsistently applied) `--` separator convention.

### Impact Explanation
An attacker who forks a repository and opens a pull request (or who crafts a `x-github-client://` deep link opened via `openPullRequestFromUrl`) fully controls `head.repo.clone_url`/`head.gitHubRepository.cloneURL`. If that value begins with `-`, it will be passed as a bare argument to `git remote add <name> <that-value>` / `git remote set-url <name> <that-value>` without an options terminator. Depending on which option string Git's `remote add`/`set-url` porcelain recognizes (e.g. `-f` to trigger an immediate fetch against attacker infrastructure, `-t <branch>`/`-m <branch>` to reconfigure tracking, `--mirror=fetch|push` to reconfigure the remote's semantics), this can silently corrupt the victim's remote configuration or trigger unexpected network operations against the attacker's server as a side effect of what looks like an ordinary "checkout PR" action — without the URL ever being stored as a normal remote URL. I could not fully verify within the codebase whether this specific option surface can be escalated further (e.g., to the `ext::`/`--upload-pack=` RCE primitive known for `clone`/`fetch`), since `remote add`/`set-url` accept a narrower option set than `clone`; that escalation path remains **unconfirmed** and would need to be validated against the exact Git version bundled with dugite.

### Likelihood Explanation
The vulnerable functions are reached automatically as part of normal "Open in Desktop" / "Checkout PR" flows whenever Desktop needs to add or repoint a fork/upstream remote, requiring only that a victim open a PR link or use the checkout-PR feature — no unusual user action is needed beyond the documented, expected interaction with a malicious fork's PR. The `--` fix already exists elsewhere in the same file family (`clone.ts`), showing the team is aware of the general argument-injection risk for remote URLs, but the fix was not propagated consistently to `remote.ts`.

### Recommendation
Add a `--` end-of-options separator before the positional `name`/`url` arguments in `addRemote`, `removeRemote`, and `setRemoteURL` (`app/src/lib/git/remote.ts`), matching the pattern already used in `clone()`, and reject/normalize any remote name or URL that begins with `-` before it reaches `git(...)`.

### Proof of Concept
1. Attacker forks the target repository and, via the GitHub API/UI, sets the fork's URL-adjacent field such that `pullRequest.head.repo.clone_url` (or `cloneURL`) is a string beginning with `-`, e.g. `-t=malicious-branch` or `-f`.
2. Attacker opens a PR from that fork against the victim's repository, or sends the victim an "Open in Desktop"/checkout-PR deep link referencing it.
3. Victim uses Desktop's "Checkout this PR" action, which calls `dispatcher._checkoutPullRequest` → `_findPullRequestBranch` → `addRemote(repository, forkRemoteName, headCloneUrl)`. [8](#0-7) 
4. Because `remote.ts`'s `addRemote` builds `['remote', 'add', name, url]` with no `--` separator, the crafted `headCloneUrl` is passed as a bare argv token immediately after `name`, allowing Git to parse it as an option to `git remote add` rather than a URL. [2](#0-1)

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
