### Title
OP_RETURN `data` output excluded from transaction weight/`vbytes` accounting, so `needed_fee`/`fee()` diverge from the signed transaction's real fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the `TokenLocker` report — where a value computed incrementally per-operation diverged from the value recomputed over the total, breaking an invariant — `SignableTransaction::new` computes the transaction weight and required fee over a *reconstructed* transaction that includes only `payments` (and optionally `change`), while the actual signed `Transaction` additionally carries an attacker-influenced OP_RETURN `data` output of up to 80 bytes. The two fee figures (`needed_fee`, used for the minimum-relay-fee and `NotEnoughFunds` checks, versus the effective `fee() = inputs - outputs` on the real tx) therefore disagree for any transaction carrying data. The data is untrusted input: in Serai it is populated from the depositor's `InInstruction` bytes that any Bitcoin user can cause to be emitted.

### Finding Description
`SignableTransaction::new` builds the real output vector `tx_outs` including the OP_RETURN `data` output (`send.rs:194-202`), but computes fee sizing via `calculate_weight_vbytes(tx_ins.len(), payments, None)` and `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (`send.rs:204`, `send.rs:225-227`), which constructs a throwaway `Transaction` whose `output` vector is built *only* from `payments` plus the change output (`send.rs:85-99`). The `data` output is never represented in the weight calculation. Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) is computed on `vbytes` that omits the data output (~11–91 vbytes for 0–80 bytes of data), so the transaction's *effective* sat/vbyte rate is strictly lower than `fee_per_vbyte` whenever `data` is present and a change output absorbs the remainder.
2. The minimum-relay-fee guard `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (`send.rs:211`) is checked against the understated `vbytes`, so a transaction can pass `TooLowFee` while its real fee rate is below the relay minimum.
3. The `MAX_STANDARD_TX_WEIGHT` check (`send.rs:241`) uses `weight` that also omits the data output, so a tx just under the standardness limit can exceed it once the data output is added, producing a non-standard transaction after threshold signing.

This mirrors the audit finding's "recomputed total ≠ accumulated parts" inconsistency: the invariant checked at construction (fee ≥ relay minimum, weight ≤ standard limit, inputs ≥ payments + fee) is evaluated on a different transaction than the one actually signed and broadcast.

### Impact Explanation
Any party who can influence the `data` payload (the depositor-supplied `InInstruction` data, or a change/payment script set) can cause the multisig to sign a Bitcoin transaction whose real fee rate is below the node's minimum relay fee or whose real weight exceeds `MAX_STANDARD_TX_WEIGHT`. The signed transaction is then rejected by Bitcoin Core, and the inputs — which the scanner/`SignableTransaction` pipeline treats as spent in this attempt — are effectively frozen until a new transaction is constructed and re-signed through another FROST round. This is a Medium-severity availability/funds-stuck issue reachable purely from transaction data an unprivileged party supplies.

### Likelihood Explanation
The divergence is deterministic whenever `data` is non-empty (the discrepancy is proportional to the OP_RETURN output size, up to ~91 vbytes). Whether it causes relay rejection depends on how close `fee_per_vbyte` is to the relay minimum and how close the weight is to the standardness cap; the processor uses a median-fee estimate (`median_fee` floors at 1 sat/vbyte per `processor/src/networks/bitcoin.rs:414`), so low-fee environments make the underpayment marginal but real, and the standardness bypass is deterministic. Exploitation requires no key material — only the ability to get a transaction built with a chosen `data` payload, which depositors inherently have.

### Recommendation
Include the OP_RETURN `data` output in the reconstructed `Transaction` used by `calculate_weight_vbytes` (pass the fully-formed `tx_outs`, or add the data output before computing weight), so `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check are evaluated over the exact transaction that will be signed. Alternatively, assert `needed_fee == self.fee()` consistency at construction when no change is emitted, and bound total outputs/weight including data.

### Proof of Concept
Conceptual, using the in-scope API:

```rust
// networks/bitcoin/src/wallet/send.rs
let inputs = vec![scanned_output];            // value V
let data = vec![0u8; 80];                     // max allowed attacker-supplied payload
let tx = SignableTransaction::new(
    inputs,
    &[(payment_script, V - small_margin)],    // payment sized so leftover is fee-sized
    None,                                     // no change: leftover all becomes fee
    Some(data),
    fee_per_vbyte,                            // e.g. 1 (the relay floor)
).unwrap();
```

Internally, `vbytes` is computed over a transaction with `inputs` + 1 payment output only (`send.rs:204`), omitting the ~91-vbyte OP_RETURN output pushed at `send.rs:195-202`. `needed_fee = 1 * vbytes` passes the `DEFAULT_MIN_RELAY_TX_FEE` check at `send.rs:211`. The resulting `tx.tx` is ~91 vbytes larger than measured, so its real fee rate is `needed_fee / (vbytes + 91) < 1 sat/vbyte`, below Bitcoin Core's `minrelaytxfee`, and the signed transaction is rejected from relay/mempool — despite passing all of `SignableTransaction`'s own validation. Symmetrically, a `payments` set sized to `weight` just under `MAX_STANDARD_TX_WEIGHT` passes the `send.rs:241` check while the real signed tx (including the data output) is non-standard.     inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
