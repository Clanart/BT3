### Title
DID recovery attestation binds the backup‑DID authorization only to a coin id, while the actual authorizing signature (`AGG_SIG_UNSAFE`) is left unbound to that coin id or to any chain/session identifier — ([File: chia/wallet/did_wallet/did_wallet_puzzles.py])

### Summary
The reported bug is a classic "two independent authorizers, one of which signs a message that is not bound to the specific operation/session it is meant to authorize" pattern. The closest reachable analog in this codebase is the DID recovery attestation mechanism built by `create_recovery_message_puzzle` / `create_spend_for_message` in `chia/wallet/did_wallet/did_wallet_puzzles.py:138-172`. Just like the smart-contract bug (validator vs. `enableModeSigValidator` being independent, and the enable-mode signature not being bound to `userOpHash`), DID recovery combines two independent authorizations — the backup DID's on-chain attestation coin and the new owner's `AGG_SIG_UNSAFE` signature — and only one of the two (the backup DID's spend, which creates the message coin) is bound to the specific `recovering_coin_id`. The `AGG_SIG_UNSAFE` condition itself carries no `additional_data`/chain binding and no coin-id binding in the signed message.

### Finding Description
`create_recovery_message_puzzle` builds an "attestment" puzzle for DID recovery: [1](#0-0) 

The puzzle is a quoted program `(1 conditions)` that unconditionally emits:
1. `CREATE_COIN_ANNOUNCEMENT recovering_coin_id`
2. `AGG_SIG_UNSAFE pubkey newpuz`

A backup DID (one of the `recovery_list` DIDs, `num_of_backup_ids_needed` of which are required) authorizes a specific recovery attempt by spending its own DID coin to create an ephemeral zero-value coin whose puzzle hash is `create_recovery_message_puzzle(recovering_coin_id, newpuz, pubkey).get_tree_hash()`. Anyone can then spend that ephemeral coin via `create_spend_for_message` with an empty solution: [2](#0-1) 

Two independent authorities are combined to complete the recovery, mirroring the report's "validator" / "enableModeSigValidator" split:
- The **backup DID's spend** — creates the coin locked to a puzzle hash that hardcodes `(recovering_coin_id, newpuz, pubkey)`. This is the only place `recovering_coin_id` (i.e., binding to a *specific* DID coin instance) is enforced.
- The **new owner's `AGG_SIG_UNSAFE` signature** over `newpuz` — this is the signature that must be supplied to satisfy the emitted condition, but the *signed message* is only `newpuz`. It contains **no reference to `recovering_coin_id`**, no `additional_data`/genesis-challenge binding (unlike `AGG_SIG_ME`, see `agg_sig_additional_data` in `chia/consensus/condition_tools.py:56-70`), and no binding to any particular spend bundle/session nonce.

Because the signed payload is just `newpuz`, the only thing preventing an attacker who has observed one such signature from repurposing it is whatever mechanism ties the message coin's *puzzle hash* to a specific `recovering_coin_id`. That binding lives entirely in the puzzle hash constructed off-chain by the backup DID owner's wallet code, not in the signature or in on-chain consensus rules for `AGG_SIG_UNSAFE`. `AGG_SIG_UNSAFE` conditions are explicitly documented/tested as lacking any chain- or coin-specific suffix: [3](#0-2) [4](#0-3) 

This is directly analogous to the reported issue: one authorizer's contribution (the backup DID's attestation coin, roughly analogous to the "validator" being installed) is tied to a specific recovery attempt, but the second authorizer's raw signature (`AGG_SIG_UNSAFE`, roughly analogous to `enableModeSignature`) carries no binding to that same context. It relies purely on off-chain wallet code correctly re-deriving matching puzzle hashes; it is not enforced as a consensus invariant the way `AGG_SIG_ME` enforces coin binding.

### Impact Explanation
If the `newpuz`/`pubkey` signature produced by a recovering wallet is ever observed (e.g., leaked from a partially-assembled recovery bundle, replayed by a malicious bundler/peer, or reused because the wallet signs the same `newpuz` for multiple purposes), it is not cryptographically tied to the specific `recovering_coin_id` it was meant to authorize. Anyone able to independently obtain (or forge, if the backup-DID side is somehow satisfied through unrelated means) a matching attestation coin for a *different* `recovering_coin_id` value using the same `(newpuz, pubkey)` pair could reuse the previously captured `AGG_SIG_UNSAFE` signature to complete an unauthorized recovery-style spend, since the AGG_SIG_UNSAFE message itself does nothing to prevent this. This could result in unauthorized control being asserted over a DID singleton coin — an unauthorized/forged-identity coin movement in the DID protocol.

### Likelihood Explanation
Exploitation requires:
1. Capturing a previously produced `AGG_SIG_UNSAFE(pubkey, newpuz)` signature (broadcast as part of an unconfirmed recovery spend bundle in the mempool, or otherwise leaked), and
2. Obtaining or engineering a scenario where the message-coin puzzle hash for a *different* `recovering_coin_id` still satisfies the backup DID's attestation requirement with the *same* `newpuz`/`pubkey`.

Because condition (2) is non-trivial (the backup DID must independently create a matching coin, and doing so for a different coin id requires the backup DID's own cooperation or a state where an identical DID coin exists under a different id), full exploitation in the general case is not clearly demonstrated from the code alone; the confirmed weakness is that the consensus-level `AGG_SIG_UNSAFE` primitive used here provides no cryptographic binding to `recovering_coin_id` or to chain identity, leaving the security of the whole scheme dependent entirely on wallet-side puzzle-hash construction rather than on the signature itself. This is a genuine analog to the reported class of bug, but I could not fully verify from the available indexed code (the DID inner puzzle CLVM source and the full `create_attestment`/`recovery_spend` wallet-side flow were not retrievable within the tool budget) whether any additional on-chain check (e.g., an `ASSERT_MY_COIN_ID` tying the recovery spend to `recovering_coin_id`) further narrows this gap. Given this uncertainty, I am reporting this as a **Medium** likelihood, non-critical-severity finding rather than asserting a fully proven exploit chain.

### Recommendation
Bind the `AGG_SIG_UNSAFE` message used in `create_recovery_message_puzzle` to the specific recovery context rather than to `newpuz` alone — e.g., sign over `sha256(recovering_coin_id || newpuz)` (or use `AGG_SIG_ME`-style consensus binding where feasible) so that a captured signature cannot be reinterpreted as authorizing a different `recovering_coin_id`. This mirrors the report's recommendation to include the analog of `userOpHash` in the signed payload so the signature is cryptographically tied to the specific operation it is meant to authorize, rather than relying solely on off-chain puzzle-hash construction for that binding.

### Proof of Concept
Not fully constructible from the indexed code alone: doing so requires the full DID inner puzzle CLVM logic and the complete `recovery_spend` wallet flow (not retrievable within the available tool budget) to confirm whether any on-chain assertion (e.g. `ASSERT_MY_COIN_ID`) additionally restricts reuse of a captured `(pubkey, newpuz)` `AGG_SIG_UNSAFE` signature across different `recovering_coin_id` values. The code-level weakness — that `create_recovery_message_puzzle`'s `AGG_SIG_UNSAFE` message (`newpuz`) has no coin-id or chain binding — is confirmed directly from `chia/wallet/did_wallet/did_wallet_puzzles.py:138-155` and the documented behavior of `AGG_SIG_UNSAFE` in `chia/consensus/condition_tools.py:99-123`.

def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle
```

def create_spend_for_message(
    parent_of_message: bytes32, recovering_coin: bytes32, newpuz: bytes32, pubkey: G1Element
) -> CoinSpend:
    """
    Create a CoinSpend for a atestment
    :param parent_of_message: Parent coin ID
    :param recovering_coin: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: CoinSpend
    """
    puzzle = create_recovery_message_puzzle(recovering_coin, newpuz, pubkey)
    coin = Coin(parent_of_message, puzzle.get_tree_hash(), uint64(0))
    solution = Program.to([])
    return make_spend(coin, puzzle, solution)
```

def pkm_pairs(conditions: SpendBundleConditions, additional_data: bytes) -> tuple[list[G1Element], list[bytes]]:
    ret: tuple[list[G1Element], list[bytes]] = ([], [])

    data = agg_sig_additional_data(additional_data)

    for pk, msg in conditions.agg_sig_unsafe:
        ret[0].append(pk)
        ret[1].append(msg)

    for spend in conditions.spends:
        condition_items_pairs = [
            (ConditionOpcode.AGG_SIG_PARENT, spend.agg_sig_parent),
            (ConditionOpcode.AGG_SIG_PUZZLE, spend.agg_sig_puzzle),
            (ConditionOpcode.AGG_SIG_AMOUNT, spend.agg_sig_amount),
            (ConditionOpcode.AGG_SIG_PUZZLE_AMOUNT, spend.agg_sig_puzzle_amount),
            (ConditionOpcode.AGG_SIG_PARENT_AMOUNT, spend.agg_sig_parent_amount),
            (ConditionOpcode.AGG_SIG_PARENT_PUZZLE, spend.agg_sig_parent_puzzle),
            (ConditionOpcode.AGG_SIG_ME, spend.agg_sig_me),
        ]
        for condition, items in condition_items_pairs:
            for pk, msg in items:
                ret[0].append(pk)
                ret[1].append(make_aggsig_final_message(condition, msg, spend, data))

    return ret
