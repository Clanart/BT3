### Title
Untrusted `Participant` index in blame evaluation panics on unregistered `enc_keys` entry — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The Mosquitto CVE is a NULL-pointer dereference triggered by a crafted protocol message from an authenticated peer — i.e., a remotely triggerable crash (DoS) on attacker-controlled input. The Serai analog is a `HashMap` index panic in PedPoP's blame/decryption path: `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` where `decryptor` is a `Participant` value carried in attacker-supplied blame data, with no bounds/registration check.

### Finding Description
`Decryption` holds `enc_keys: HashMap<Participant, C::G>` populated only for participants `1..=n` (via `register`, which asserts non-duplication). In `decrypt_with_proof`, when a decryption-key correctness proof is supplied, the code does:

```rust
// crypto/dkg/pedpop/src/encryption.rs:381-390
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],   // line 388: panics if decryptor unregistered
  )
```

`decrypt_with_proof` is reached from `BlameMachine`/`AdditionalBlameMachine::blame` (`blame_internal`), where `sender`, `recipient`, the `EncryptedMessage`, and the optional `EncryptionKeyProof` are all derived from a public accusation message — the same class of input as the crafted CONNACK in the CVE. `Participant` wraps a `u16` (`Participant::new` accepts any nonzero `u16`), so an accuser can set `recipient`/`decryptor` to any value `> n` (or any index that was never registered, e.g., a participant whose `EncryptionKeyMessage` was rejected/omitted). The indexing operator `enc_keys[&decryptor]` then panics, aborting blame evaluation and crashing the calling task — an unprivileged-peer-reachable denial of service, exactly the NULL-deref bug class mapped onto Rust's panic-on-missing-key shape.

The same unguarded-index pattern exists at `Encryption::encrypt` (`self.decryption.enc_keys[&participant]`, line 466), though that path is fed by internally generated maps and is not attacker-reachable; the blame path is.

### Impact Explanation
Any participant in a DKG session (or any party able to submit a blame proof for evaluation via `AdditionalBlameMachine::blame`) can deterministically panic a victim's share/blame evaluation. In the Serai validator/coordinator context this halts DKG completion or post-facto fault attribution — a crash/availability impact analogous to the Mosquitto broker crash, rated Medium.

### Likelihood Explanation
Triggering requires only that the attacker cause their accusation to be evaluated with a `decryptor` index outside the registered `enc_keys` set and a `proof` of `Some(...)` — no cryptographic work, no collusion, and no control over the victim's secrets. The PoP check on `msg.pop` runs first but is satisfiable by the attacker since they choose `key`/`pop` for the message they submit. Certainty caveat: I could not fully read `blame_internal` to confirm the `recipient` argument is passed through without an `all_participant_indexes`/`enc_keys.contains_key` check; if it validates `decryptor` against the registered set before calling `decrypt_with_proof`, this is unreachable. That check is the single gate to verify.

### Recommendation
Replace the panicking index with a checked lookup:

```rust
let Some(enc_key) = self.enc_keys.get(&decryptor) else {
  return Err(DecryptionError::InvalidProof);
};
```

and/or reject `decryptor` values outside `1..=n` in `blame_internal`/`AdditionalBlameMachine::blame` before calling `decrypt_with_proof`.

### Proof of Concept
Conceptual test (mirroring `crypto/dkg/pedpop/src/tests.rs` style): construct an `AdditionalBlameMachine` via `AdditionalBlameMachine::new(CONTEXT, n, commitment_msgs)` for `n = 5`, then call `blame(sender, recipient, msg, Some(proof))` with `recipient = Participant::new(7)` (a valid nonzero `Participant` not in `1..=5`) and a `msg`/`proof` whose `pop` signature verifies (`pop` is attacker-generated over `msg.key`). Execution reaches `decrypt_with_proof`, the `pop.verify` passes, `proof` is `Some`, and `self.enc_keys[&decryptor]` panics with "no entry found for key" instead of returning `DecryptionError`.
