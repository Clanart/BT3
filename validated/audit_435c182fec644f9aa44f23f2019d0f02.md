### Title
Untrusted `ReceivedOutput` deserialization accepts a nonexistent UTXO and causes it to be treated as spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`ReceivedOutput::read` deserializes the key offset, claimed `TxOut`, and claimed `OutPoint` directly from attacker-controlled bytes without proving that the outpoint exists, contains the claimed output, or was produced by `Scanner`. [1](#0-0)  Downstream transaction construction trusts those fields as spendable inputs, allowing serialized bytes to report arbitrary value and cause signatures to be generated for a transaction whose input may not exist. [2](#0-1) [3](#0-2) 

### Finding Description

The legitimate provenance path is `Scanner::scan_transaction`, which only constructs a `ReceivedOutput` after matching a transaction output’s `script_pubkey` to a registered script and records the actual transaction ID and output index as the `OutPoint`. [4](#0-3)  The deserialization path bypasses all of those checks and accepts an arbitrary `offset`, `output`, and `outpoint` tuple. [5](#0-4) 

`SignableTransaction::new` trusts `input.output.value` as available funding and `input.outpoint` as the UTXO being spent. [2](#0-1)  `SignableTransaction::multisig` checks only that applying the serialized offset to the signer’s key yields the serialized prevout’s `script_pubkey`; it does not check that the prevout is present on-chain or equals the outpoint’s actual output. [6](#0-5)  Signing then commits to all supplied prevouts with `Prevouts::All`, so a deserialized forged prevout is incorporated directly into the Taproot sighash. [7](#0-6) 

### Impact Explanation

An attacker can encode a `ReceivedOutput` claiming an arbitrary balance under a script derived from the victim’s group key while pointing the input at an arbitrary or nonexistent outpoint. [5](#0-4)  Any component that accepts serialized `ReceivedOutput`s as spendable wallet state can therefore report funds as received when they are not actually spendable, or construct and threshold-sign a transaction that Bitcoin consensus will reject. [2](#0-1) [3](#0-2) 

This matches the report’s core class of trusting attacker-supplied object metadata as authoritative state: here, the serialized outpoint/output pair acts as a pointer plus value assertion without authentication or resolution against the ledger. [1](#0-0) 

### Likelihood Explanation

The input is entirely public and requires no validator privilege, key material, or malformed cryptography: the attacker chooses a scalar offset, finds one for which `group_key + offset·G` has even-Y Taproot form, serializes the corresponding script and amount, and supplies an arbitrary `OutPoint`. [8](#0-7) [5](#0-4)  `multisig` accepts the forged object whenever the serialized prevout script matches the re-keyed group key, which the attacker can satisfy without knowing the group secret. [6](#0-5) 

The resulting transaction will not steal confirmed Bitcoin by itself because consensus rejects nonexistent inputs, but it defeats the spendability invariant represented by `ReceivedOutput` and can corrupt balance, scheduling, or signing decisions based on deserialized wallet state. [9](#0-8) [10](#0-9) 

### Recommendation

Treat `ReceivedOutput` as an authenticated internal type rather than a self-authenticating network encoding. [9](#0-8)  At minimum, require a provenance-authenticated constructor that resolves the `OutPoint`, verifies the resolved `TxOut` exactly equals the serialized output, and verifies the script is currently registered by `Scanner`. [4](#0-3)  If untrusted persistence or transport is supported, bind the output to a trusted scanner checkpoint or MAC/signature over the complete `offset || output || outpoint` encoding; otherwise, remove or restrict `ReceivedOutput::read` to trusted storage. [11](#0-10) 

### Proof of Concept

Conceptually, for a victim group key `K`:

1. Choose `offset = 0, 1, 2, ...` until `p2tr_script_buf(K + offset·G)` returns a script; this terminates as soon as an even-Y point is found, as documented by the registration loop. [12](#0-11) 
2. Serialize a `ReceivedOutput` containing:
   - `offset`,
   - `TxOut { value: large_amount, script_pubkey: p2tr(K + offset·G) }`,
   - an arbitrary `OutPoint` that need not exist. [5](#0-4) 
3. Pass the bytes to `ReceivedOutput::read`, then pass the result to `SignableTransaction::new`; its value is counted as spendable input and its outpoint becomes the transaction input. [2](#0-1) 
4. Call `multisig`; the script check succeeds because the crafted `offset` makes `keys.offset(offset).group_key()` produce the serialized prevout script. [6](#0-5) 
5. Run the normal preprocess/sign/complete flow; each signer commits to the forged prevout through `Prevouts::All` and `complete` returns a fully witness-populated transaction. [3](#0-2) [13](#0-12) 

A minimal malicious field tuple is therefore `offset || TxOut || OutPoint`, with no blockchain evidence required by the reader. [5](#0-4)

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =

    }
