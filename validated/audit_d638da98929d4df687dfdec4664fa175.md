### Title
Untrusted payment amounts can overflow the `payment_sat + needed_fee` sufficiency check, letting an unspendable transaction be built and signed - (networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums untrusted payment amounts and adds the fee with unchecked `u64` arithmetic. An attacker who can influence the payment list (e.g., withdrawal/request data that ends up as `(ScriptBuf, u64)` payments) can make `payment_sat` wrap past `u64::MAX`, defeating the `NotEnoughFunds` sanity check — the same bug class as Olympus's `LIMIT + ohmRemoved` overflow defeating `_canDeposit`. The resulting transaction can never be valid on-chain, yet the multisig still runs FROST signing over it, and `fee()`/`needed_fee` accounting becomes inconsistent (panic in debug, wrap in release).

### Finding Description
The constructor performs all value accounting in unchecked `u64`:

- `input_sat` is the sum of input values: `inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>()` [1](#0-0) 
- `payment_sat` is the sum of attacker-influenced payment amounts: `payments.iter().map(|payment| payment.1).sum::<u64>()` [2](#0-1) 
- The funds check is a plain addition: `if input_sat < (payment_sat + needed_fee)` [3](#0-2) 
- The fee itself is an unchecked multiply: `let mut needed_fee = fee_per_vbyte * vbytes` [4](#0-3) 

Each `payment.1` is only checked against `DUST` (546 sats); there is no upper bound and no consensus-style 21M BTC cap validation [5](#0-4) . `Amount::from_sat` accepts any `u64`. Two payments of `u64::MAX - 1000` each make `payment_sat` wrap to ~`u64::MAX - 2000` → actually wraps to a small value modulo 2^64, so `payment_sat + needed_fee` wraps to a tiny number and `input_sat < wrapped` is false — `NotEnoughFunds` is never raised for a transaction paying out far more than its inputs.

The change path then uses `input_sat.checked_sub(payment_sat + fee_with_change)` [6](#0-5) ; with `payment_sat` wrapped small, this succeeds and produces a change output worth nearly the entire (tiny) input sum's complement — i.e., a change `TxOut` whose value can exceed total inputs, guaranteeing `sum(outputs) > sum(inputs)`.

Downstream, `fee()` computes `sum(inputs) - sum(outputs)` with a bare subtraction [7](#0-6) , which panics (debug) or wraps to ~`u64::MAX` (release). Either way the constructed `SignableTransaction` proceeds to `multisig()` and `TransactionSignMachine::sign`, which runs the full FROST protocol and produces Schnorr signatures over `taproot_key_spend_signature_hash` for a transaction Bitcoin consensus can never accept [8](#0-7) .

### Impact Explanation
Mirroring the source issue's "deposits are DoSed by an overflowing sanity check," here the funds-sufficiency sanity check is defeated by wrapping arithmetic driven by untrusted payment data:

- The threshold signs a transaction that is permanently unbroadcastable (output sum exceeds input sum), wasting a signing attempt and forcing the referenced inputs to be re-planned — an availability hit on the signing pipeline caused purely by input data, with no on-chain cost to the attacker.
- In release builds, `fee()` reports a near-`u64::MAX` fee; in debug builds it panics inside fee accounting. Callers relying on `needed_fee()`/`fee()` for reconciliation observe corrupted values.
- Unlike the Olympus case, there is no admin knob (`LIMIT`) to lower — the arithmetic itself must be fixed.

### Likelihood Explanation
Reachable by any unprivileged party who can cause a withdrawal/payment request to reach `SignableTransaction::new` with attacker-chosen amounts (the payment list is exactly untrusted transaction data fed to a sign API, which the scope rules permit). It requires amounts large enough to overflow `u64` when summed — trivially satisfiable since amounts are unconstrained above `DUST`. Triggering is deterministic once such a request is constructed.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new` and `fee()`:

```rust
let input_sat = inputs.iter().try_fold(0u64, |a, i| a.checked_add(i.output.value.to_sat()))
  .ok_or(TransactionError::TooMuchData /* or new Overflow variant */)?;
let payment_sat = payments.iter().try_fold(0u64, |a, p| a.checked_add(p.1))
  .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: u64::MAX, fee: needed_fee })?;
let needed_fee = fee_per_vbyte.checked_mul(vbytes).ok_or(TransactionError::TooLowFee)?;
if input_sat < payment_sat.saturating_add(needed_fee) { ... }
```

Also reject individual payment amounts above `MAX_MONEY` (21,000,000 BTC) and make `fee()` use `checked_sub`, returning an `io::Result`/error instead of panicking.

### Proof of Concept
```rust
// Construct a SignableTransaction with one small input and two huge payments.
let input = ReceivedOutput /* value = 1_000_000 sats, any registered offset */;

let payments = vec![
  (ScriptBuf::new_p2tr_tweaked(...), u64::MAX - 100), // passes `>= DUST`
  (ScriptBuf::new_p2tr_tweaked(...), u64::MAX - 100),
];
// payment_sat wraps to u64::MAX - 200 mod 2^64 arithmetic per sum -> wraps to ~2^64 - 202
// then payment_sat + needed_fee wraps small, so `input_sat < payment_sat + needed_fee` is false.

let stx = SignableTransaction::new(vec![input], &payments, Some(change), None, 1).unwrap();
// ^ succeeds despite paying ~2^64 sats from a 1M-sat input.

// Either panics or returns ~u64::MAX:
let _fee = stx.fee();
// stx.multisig(&keys) proceeds; FROST signs a tx consensus-invalid forever.
```
