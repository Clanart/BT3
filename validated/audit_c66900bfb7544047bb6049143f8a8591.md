### Title
OP_RETURN `data` output excluded from transaction weight/fee calculation, producing under-fee or non-standard transactions that cannot be broadcast — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends the `OP_RETURN` output to `tx_outs` (lines 194–202) but computes weight, vbytes, `needed_fee`, the minimum-relay check, the change amount, and the `MAX_STANDARD_TX_WEIGHT` check using `payments`, which does not include the `OP_RETURN` output (lines 204, 211, 225–232, 241). Any transaction carrying a `data` payload is therefore built with a fee rate and weight lower than reality.

### Finding Description [1](#0-0) 

The flow is:

1. `tx_outs` is built from `payments`, then the `OP_RETURN` `TxOut` is pushed (lines 188–202). The `data` field is attacker-influenceable — it is the arbitrary data attached to an `InInstruction`/burn, capped at 80 bytes (line 171).
2. `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) constructs a template `Transaction` whose `output` list contains only `payments` — the `OP_RETURN` output that will actually appear in the signed transaction is missing.
3. `needed_fee = fee_per_vbyte * vbytes` (line 206) and the minimum-relay check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (line 211) both use this underestimated `vbytes`.
4. When a change output exists, `fee_with_change` is computed from `calculate_weight_vbytes(..., payments, Some(&change))` (line 225–227) — again without the `OP_RETURN`. The change amount is then `input_sat - payment_sat - fee_with_change` (line 228), so the leftover is added to change and the *actual* fee paid equals the underestimated `fee_with_change`.
5. The standardness check `weight > MAX_STANDARD_TX_WEIGHT` (line 241) also uses the underestimated `weight`.

An `OP_RETURN` output carrying the maximum 80 bytes of data adds roughly 91 serialized bytes (~364 WU / ~91 vbytes including the amount and script-length fields) that are never accounted for.

### Impact Explanation
The signed transaction's real virtual size exceeds the size the fee was computed for, so the effective fee rate is below `fee_per_vbyte`. When the processor requests a fee rate at or near the relay minimum, the resulting transaction falls below `DEFAULT_MIN_RELAY_TX_FEE` and is rejected by the Bitcoin P2P network — the `TooLowFee` guard cannot catch it because it evaluates the same underestimated `vbytes`. The multisig has then produced and signed a transaction spending real UTXOs that cannot be broadcast, and the change output (carrying `input_sat - payment_sat - fee_with_change`, potentially the bulk of the multisig's balance) is stranded inside an unrelayable transaction. The same omission can let a transaction silently exceed `MAX_STANDARD_TX_WEIGHT` when many inputs plus a maximal `OP_RETURN` push the true weight past the limit, again yielding a transaction no node will relay. This is funds rendered unspendable via a signed-yet-unbroadcastable transaction, reachable purely through the `data` bytes an external user causes to be embedded.

### Likelihood Explanation
Any external user submitting a burn or an `InInstruction` with an arbitrary `data` field causes the processor to construct a `SignableTransaction` via `SignableTransaction::new` with `data: Some(...)`. The miscalculation is deterministic and occurs on every such transaction; whether the fee actually dips below relay minimum depends on how close `fee_per_vbyte` is to 1 sat/vB, but the fee shortfall and the change-amount error occur unconditionally whenever `data` is present.

### Recommendation
Include the `OP_RETURN` output in the size calculation. The clean fix is to compute weight/vbytes over the actual outputs being created: build `tx_outs` (payments + OP_RETURN) first, then call `calculate_weight_vbytes(tx_ins.len(), &tx_outs-equivalent, change)` — i.e., pass the full output list (or a `&[TxOut]`/script+value list that includes the data output) instead of `payments` on lines 204 and 226. Alternatively, add a fixed `OP_RETURN`-output weight term (`Amount(8) + script len + 80-byte push`) into both the no-change and with-change calculations and into the `MAX_STANDARD_TX_WEIGHT` comparison.

// In SignableTransaction::new:
let data = vec![0u8; 80]; // max allowed, passes the <= 80 check at line 171
let tx = SignableTransaction::new(
    inputs,                        // real ReceivedOutputs
    &[(payment_script, amount)],
    Some(change_script),
    Some(data),                    // OP_RETURN output is pushed into tx_outs
    1,                             // fee_per_vbyte at the relay floor
).unwrap();

// calculate_weight_vbytes(tx_ins.len(), payments, None) built a template tx
// with only `payments` as outputs -- the OP_RETURN TxOut (≈91 bytes) is absent.
// needed_fee = 1 * vbytes(underestimated), and the min-relay check at line 211
// compares against the same underestimated vbytes, so it passes.
// The actual signed tx is ~91 vbytes larger, so its real fee rate is
// needed_fee / (vbytes + 91) < 1 sat/vB -> bitcoind rejects it from the mempool.
// All inputs' funds, including the change output, are locked in a transaction
// that cannot be relayed.
