## Analysis Summary

The external M-14 report's core broken invariant is: **external/public functions remain callable after deployment but before a required `init()`/`initialize()` call, letting an attacker corrupt state that other privileged code paths later trust.**

I traced Hyperbridge's Solidity contracts for this exact shape. Most `initialize()` entry points (`IntentGatewayV2`, `SimplexPaymaster`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleTokenUpgradeable`) use OZ's `Initializable` + `_disableInitializers()` in the constructor and are deployed atomically behind `ERC1967Proxy`, so the init-data is bound at deployment and there's no callable window [1](#0-0) . `HostManager.setIsmpHost` is also safe pre-init because its `onAccept` is gated by `restrict(_params.host)` and `host` starts as `address(0)`, which is unreachable from a normal `msg.sender` [2](#0-1) .

`EvmHost`, however, explicitly uses a **two-phase, non-atomic** deployment: the constructor sets only `admin`, and everything else (`feeToken`, `handler`, `hostManager`, `consensusClient`, `uniswapV2`) is deferred to a separate `initialize()` call for CREATE2 address-parity reasons [3](#0-2) . Between deployment and the admin's `initialize()` transaction, the contract already has code and its outbound-dispatch entry points have **no initialization gate**.

### Title
Fee-paying `dispatch()` calls before `EvmHost.initialize()` create phantom fee commitments that drain real protocol funds later - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `dispatch(DispatchGet)` are `external payable` with no check that `initialize()` has been called [4](#0-3) . Before `initialize()` runs, `_hostParams.feeToken` is `address(0)`. Calling `IERC20(address(0)).safeTransferFrom(...)` against a non-contract address is a low-level `call` that returns `success = true` with empty `returndata`, which OpenZeppelin's `SafeERC20` treats as success (no revert). This lets an attacker record a `FeeMetadata{sender: payer, fee: <arbitrary>}` entry in `_requestCommitments` without ever transferring any tokens.

### Finding Description
1. Deploy tx for `EvmHost` completes; `admin` is set but `feeToken`/`handler`/`hostManager` are still zero, and `initialize()` has not yet landed (separate tx, as documented by the contract itself) [5](#0-4) .
2. In this window, `notFrozen` passes (default `_frozen` state is neither `Outgoing` nor `All`), so anyone can call `dispatch(DispatchPost)` with `post.fee = <large value>` and `post.payer = <attacker>` [4](#0-3) .
3. Since `feeToken()` resolves to `address(0)`, the `safeTransferFrom` call silently "succeeds" against the empty account, so no tokens are actually pulled from the attacker.
4. The dispatch still records `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})` and increments the protocol nonce, exactly as if a real, fully-funded request had been made [6](#0-5) .
5. Once the admin later calls `initialize()` and sets the real `feeToken`, the host accumulates a genuine token balance from legitimate future dispatches (fees deposited by honest users).
6. When the phantom request eventually times out, the (handler-restricted) `dispatchTimeOut` path is invoked using the `meta` sourced from this same `_requestCommitments` entry, and pays out `meta.fee` in the now-real `feeToken` to `meta.sender` (the attacker) from the contract's genuine balance [7](#0-6) .

No fee was ever actually collected for this commitment, yet the contract treats it as fully backed and pays out real value.

### Impact Explanation
This is a direct, unauthorized extraction of funds from `EvmHost`'s real token balance: the attacker receives `feeToken` payouts funded by other users' legitimately collected fees, without ever depositing anything themselves. This matches the bounty's "stealing or loss of funds" and "false proof/state acceptance" categories — the corrupted value is the `_requestCommitments[commitment].fee` field, which is trusted downstream by `dispatchTimeOut`/`dispatchIncoming` without any verification that the fee was actually collected in tokens.

### Likelihood Explanation
The attack requires no privileged role, malicious relayer/prover, or governance compromise — only the ability to send a transaction to the already-deployed but not-yet-initialized `EvmHost` contract, which is directly analogous to the "Pools.sol callable before init" bug class in the source report. The only precondition is the existence of the deploy→initialize gap, which the contract's own comments confirm is a deliberate two-step process (for CREATE2 parity), not a single atomic transaction.

### Recommendation
- Gate `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` with an `_initialized` check (the flag already exists and is set in `initialize()`) so they revert until the host is fully configured.
- Alternatively, verify `feeToken().code.length > 0` before treating a `safeTransferFrom`/`safeTransfer` as authoritative, so calls against an unset (zero) fee token cannot silently "succeed."
- Consider deploying `EvmHost` via a factory/proxy pattern that combines deployment and `initialize()` into one atomic transaction, consistent with the pattern already used for `IntentGatewayV2` and `SimplexPaymaster`.

### Proof of Concept
```solidity
// 1. EvmHost is deployed (constructor only sets admin); initialize() tx not yet mined.
EvmHost host = new EvmHost(admin);

// 2. Attacker front-runs / races the admin's initialize() call.
vm.prank(attacker);
bytes32 commitment = host.dispatch(DispatchPost({
    dest: someDest,
    to: someTarget,
    body: "",
    timeout: 1,           // times out almost immediately
    fee: 1_000_000e18,    // arbitrary large "fee"
    payer: attacker
}));
// feeToken() == address(0) here, so safeTransferFrom silently "succeeds":
// attacker pays nothing, but _requestCommitments[commitment].fee = 1_000_000e18 is recorded.

// 3. admin.initialize() runs later, setting real feeToken/handler; host accrues
//    real feeToken balance from legitimate subsequent dispatches.

// 4. Handler processes the (already-expired) request as timed out:
vm.prank(handler);
host.dispatchTimeOut(timeoutStruct, FeeMetadata({sender: attacker, fee: 1_000_000e18}), commitment);
// -> IERC20(feeToken()).safeTransfer(attacker, 1_000_000e18) drains real host funds.
```
