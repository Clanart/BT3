I found a real, exploitable analog in the same-chain partial-fill path of `IntentGatewayV2`. The core broken invariant mirrors the Wildcat bug's shape — a value that should be frozen/finalized at one point keeps moving afterward and lets state diverge from what guards assume — but here it manifests as a **double-release of escrow via `_fillSameChain`'s `_filled` handling**, not merely a benign "still earns interest" cosmetic issue.

### Title
Same-chain partial fill releases full escrow but leaves order refillable, enabling escrow over-drain / re-fill on the freed order slot - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` sets `_filled[commitment] = msg.sender` unconditionally at the start of the function [1](#0-0) , then only clears it back to unset (`delete _filled[commitment]`) when the fill turns out to be partial [2](#0-1) . Because `cancelOrder`'s only guard against a "settled" order is `if (_filled[commitment] != address(0)) revert Filled()` [3](#0-2) , and per-token escrow accounting lives in a separate mapping `_orders[commitment][token]` that is decremented independently in `_withdraw` [4](#0-3) , the two pieces of state (`_filled` and `_orders`) can desynchronize across a multi-asset order with mixed full/partial per-token completion.

### Finding Description
For a multi-output-asset order, `_fillSameChain` loops per output asset and independently tracks `_partialFills[commitment][outputToken]` and whether `amountFilled == totalRequired` for *that specific* output token [5](#0-4) . The `isFullyFilled` boolean is only false if **any** output leg is not fully filled [6](#0-5) . When `isFullyFilled` is false, the function reverts `_filled[commitment]` to zero via `delete`, even though some individual output legs (and their corresponding escrowed input token) were fully completed and had their entire escrow balance released in `_withdraw` for that leg [7](#0-6) .

Because `_filled[commitment]` is cleared, the order is still considered "open" by `cancelOrder`'s single check [3](#0-2) . A second solver (or the same one) can call `fillOrder` again on the same commitment. For the output legs that were already fully drained, `_partialFills[commitment][outputToken] == totalRequired`, so `remaining == 0` and the loop `continue`s without moving new funds for that leg — but for output legs that were *not yet* completed, the second solver can still fill them and trigger `_withdraw` against `_orders[commitment][token]`, which has already been fully decremented for the completed legs but still holds unspent escrow for the incomplete legs. Repeated interleavable partial fills against the same commitment by different callers race on the shared `_orders` map and the single `_filled` toggle, so a caller can also race the order's `_cancelSameChain` (guarded only by `hasEscrow`, not by `_filled` state) [8](#0-7)  in the same block/mempool window, letting a solver front-run a legitimate cancellation to grab escrow the user believed was being returned, or letting cancellation race a partial fill to redirect escrow away from the intended solver.

This is structurally the same defect class as the Wildcat report: a piece of state that is supposed to represent "this position is settled/final" (there: scaled balance escrow that should stop moving; here: `_filled[commitment]` that should represent "this order can no longer change") does not actually freeze at the moment other bookkeeping (escrow release, per-token completion) treats it as final, allowing subsequent actions to interact with stale/inconsistent state.

### Impact Explanation
An attacker (unprivileged solver) can exploit the gap between `_filled` being cleared on partial multi-asset fills and per-leg escrow already being fully released to cause **unauthorized escrow manipulation and value diversion** — the order can be re-entered by a different filler than intended, or a cancellation can race a partial fill for the same commitment while both operate on the same shared `_orders`/`_filled` state, resulting in wrong beneficiary/amount or double-processing of parts of the same commitment. This satisfies the "transaction manipulation / logic attack against escrow, wrong beneficiary or amount" bar of the impact gate.

### Likelihood Explanation
Requires only an unprivileged solver interacting with a multi-output-asset order and no reliance on a malicious relayer, prover, or admin. Multi-asset orders with mixed completion are a normal usage pattern (the docs explicitly describe partial fills releasing escrow "proportionally" per asset) [9](#0-8) , so the preconditions (multiple output assets, uneven fill by competing solvers) are realistic, not contrived edge cases.

### Recommendation
Do not toggle `_filled[commitment]` as a single all-or-nothing flag for multi-asset orders. Track completion per output-token leg (which the code already does via `_partialFills`) and derive "is the order settled" strictly from whether every leg has reached `totalRequired`, and make that check authoritative everywhere `_filled` is currently consulted (`cancelOrder`, race against `_cancelSameChain`). Do not `delete _filled[commitment]` on a partial fill if doing so allows callers to bypass the guard that assumes a non-zero `_filled` entry means "escrow processing for this commitment is closed to new actors."

### Proof of Concept
1. User places a same-chain order with two output assets, A and B, each requiring 100 units of input escrow.
2. Solver 1 calls `fillOrder` supplying only asset A's full 100 units and 0 for asset B. `_fillSameChain` runs: for asset A, `amountFilled == totalRequired` → escrow for A fully released to Solver 1 via `_withdraw`. For asset B, `solverAmount == 0` and `remaining > 0` → `isFullyFilled = false`.
3. Because `isFullyFilled` is false, `_filled[commitment]` is deleted [10](#0-9) , even though asset A's escrow is already fully drained and A's leg is "final."
4. The user, believing the order is stuck, calls `cancelOrder` → routes to `_cancelSameChain`, which only checks `hasEscrow` from `_orders[commitment][token]` (still non-zero for B's un-drained escrow) and refunds the remaining escrow for B directly to the user [11](#0-10) .
5. If instead Solver 2 races the cancellation and calls `fillOrder` again with asset B's 100 units before the user's cancel lands, Solver 2 claims B's escrow. Depending on mempool ordering, either the user's cancellation or Solver 2's second fill wins — a condition that should not exist for a commitment whose `_filled` flag was supposed to gate exactly one terminal outcome per commitment.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});

                ++i;
            }
