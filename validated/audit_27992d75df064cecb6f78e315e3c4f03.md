### Title
Payout attribution trusts unauthenticated OP_RETURN data, letting anyone assign reimbursement credit to an operator who never funded the payout — (File: core/src/verifier.rs)

### Summary
`update_finalized_payouts` in `core/src/verifier.rs` determines which operator gets credited/reimbursed for a withdrawal purely by reading the OP_RETURN output of whichever transaction happens to spend the registered withdrawal UTXO on-chain. The OP_RETURN data is user-supplied script content with no cryptographic binding to the party who actually broadcast/funded the transaction, analogous to FrankenDAO's M-4 bug where the wrong counter (`proposalsCreated` vs `proposalsPassed`) was credited because the code trusted a signal disconnected from the actual qualifying action.

### Finding Description
The withdrawal UTXO spent by a payout transaction is a dust/user-controlled UTXO pre-signed by the withdrawing user with `SIGHASH_SINGLE|ANYONECANPAY` [9](#0-8) . Because of this sighash flag, the resulting `user_sig` authorizes only the specific output (payment to the user) and does not sign or constrain the OP_RETURN output or any other output appended to the transaction. `create_payout_txhandler` builds the OP_RETURN with whatever `operator_xonly_pk` value is passed in by the caller, with no proof that this key belongs to the entity that is fronting/funding the payment [3](#0-2) .

When the payout transaction confirms, `update_finalized_payouts` extracts the operator identity solely from this OP_RETURN field and stores it as the authoritative "payer" [4](#0-3) . `PayoutCheckerTask` then looks up "my unhandled payout" purely by matching this stored `payout_payer_operator_xonly_pk` against the local operator's own key [5](#0-4) , and immediately proceeds to allocate a kickoff connector and drive the reimbursement flow for that operator [7](#0-6) .

The binding that should hold is: `operator credited for reimbursement == operator that actually broadcast/funded the payout tx`. Because attribution is taken from unauthenticated OP_RETURN bytes rather than from proof that the credited operator's signature/broadcast produced the transaction, this binding can be broken: any party who obtains the pre-signed `user_sig` (given to operators off-chain per the withdrawal flow) can construct and broadcast the payout transaction themselves, embedding an arbitrary target operator's x-only pubkey in the OP_RETURN. Once mined, the targeted operator's own `PayoutCheckerTask`/automation will treat this as a legitimate payout they made and proceed to claim reimbursement from their own round/collateral, even though they never funded the withdrawal.

### Impact Explanation
This breaks the "operator credited versus operator that paid" binding. Reimbursement is drawn from the operator's own collateral/round funds via `create_reimburse_txhandler` [8](#0-7) , so a targeted operator's automation would consume one of their kickoff connectors and attempt a self-reimbursement for an amount they never spent — this can desynchronize their round/kickoff bookkeeping (consuming a limited kickoff slot per round) and cause `handle_finalized_payout`'s round-index invariant checks to fire internal errors (`current_round_index.next_round() != round_idx`) [10](#0-9) , potentially disrupting an honest operator's ability to process legitimate reimbursements in that round. This maps to the "operator reimbursed for a payout it never funded" / operator-collateral-integrity class of Critical impact.

### Likelihood Explanation
Exploitability depends on an attacker obtaining a valid `user_sig` for a pending withdrawal before any operator processes it, and constructing/broadcasting the payout transaction with a chosen target operator's pubkey. The report does not have full visibility into how tightly `user_sig` is scoped/distributed (it is described as "given to operators off-chain"), which is a material uncertainty — if it is only ever handed to a single operator at a time and never exposed elsewhere, the practical attack surface narrows to that operator racing/mis-tagging themselves rather than a fully unprivileged third party. This should be verified against the aggregator/off-chain distribution path before treating this as fully unauthenticated-attacker reachable.

### Recommendation
Do not trust the OP_RETURN payload as sole proof of payer identity. Require the payout transaction's kickoff to include a signature (e.g., over the payout txid) from the operator claiming credit, and validate that signature against the claimed `operator_xonly_pk` before persisting `payout_payer_operator_xonly_pk` in `update_finalized_payouts`, or otherwise cryptographically bind the OP_RETURN commitment to the funding operator (e.g., have the operator's own key co-sign/commit the OP_RETURN output rather than allowing it to be freely appended by any broadcaster of `user_sig`).

### Proof of Concept
1. Attacker obtains a valid `user_sig` for a registered withdrawal (via whatever off-chain channel operators normally receive it, e.g. by requesting/observing a `withdraw`/`WithdrawParamsWithSig` RPC exchange).
2. Attacker constructs a payout transaction using `create_payout_txhandler` logic: input = the registered `withdrawal_utxo`, output 1 = user payout (matching what the user pre-signed), output 3 = OP_RETURN containing the x-only pubkey of a target honest operator (not the attacker) [3](#0-2) .
3. Attacker funds/broadcasts this transaction on Bitcoin (CPFP anchor allows fee bumping without needing the withdrawal-side key).
4. Once finalized, `update_finalized_payouts` parses the OP_RETURN and records the target operator as `payout_payer_operator_xonly_pk` [4](#0-3) .
5. The target operator's `PayoutCheckerTask` picks this up as "their" unhandled payout and calls `handle_finalized_payout`, consuming a kickoff connector and initiating the reimbursement flow for a payment they never made [6](#0-5) , [7](#0-6) .
