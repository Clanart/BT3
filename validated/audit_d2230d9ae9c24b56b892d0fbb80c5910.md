### Title
Coinbase outputs paying a Serai multisig script are never scanned and become unspendable in practice - (File: processor/src/networks/bitcoin.rs)

### Summary
The external report concerns a contract that cannot receive funds, causing sent value to be effectively lost. The Serai analog lives in the Bitcoin output scanner: `Bitcoin::get_outputs` iterates `block.txdata[1 ..]`, unconditionally skipping the coinbase transaction. A coinbase transaction is fully able to pay arbitrary `script_pubkey`s, including Serai's P2TR deposit scripts (`External`, `Branch`, `Change`, `Forwarded`). Any miner (an unprivileged party who can craft a Bitcoin transaction) that pays a Serai-registered script inside a coinbase creates an output the processor never reports, never marks as seen, and never aggregates, permanently stranding the funds under the multisig key.

### Finding Description
`Scanner::scan_block` in `networks/bitcoin/src/wallet/mod.rs:221-227` scans *all* transactions in a block, including `txdata[0]` (the coinbase), and explicitly documents that coinbase outputs are bound by maturity and require post-processing. However, the processor-side consumer, `Bitcoin::get_outputs` in `processor/src/networks/bitcoin.rs:686-700`, does not delegate to `scan_block` with filtering; it hard-skips the coinbase:

```rust
// Skip the coinbase transaction which is burdened by maturity
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) { ... }
}
```

Coinbase outputs to a P2TR address are spendable after 100 confirmations, identically to any other key-path output once mature. The "maturity burden" is temporary, but the skip is permanent: once `Scanner::run` in `processor/src/multisigs/scanner.rs` advances `ram_scanned`/`scanned_block` past that block, the output is never revisited (blocks are scanned exactly once, and `seen`/`ram_outputs` deduplication panics rather than re-emits). There is no maturity-aware re-queueing path anywhere in `get_outputs`, `scan_block`'s consumers, or the scheduler.

### Impact Explanation
Funds sent to a Serai multisig address via a coinbase output are received on-chain (the Bitcoin network accepts them, and they become spendable after maturity) but are never emitted as `ScannerEvent::Block` outputs, never enter a `Batch`, and are never aggregated or spendable through the normal pipeline. They are effectively burned under the multisig key — the direct analog of "yield sent as ETH that the contract cannot receive". Unlike the external report's loss of *yield*, this is loss of *principal* sent to the vault.

### Likelihood Explanation
Requires a miner to place a Serai script in a coinbase output. This is unusual but entirely under an unprivileged miner's control — mining pools already pay arbitrary outputs (e.g., pool payout splits inside coinbase transactions are historically common). A confused or malicious pool operator routing a deposit address into a coinbase payout triggers silent loss. Combined with the zero-cost possibility of a miner doing it deliberately to grief the protocol, this is a low-frequency but reachable path, consistent with Medium.

### Recommendation
Do not silently drop coinbase transactions. Either:
- Scan `block.txdata[0]` and tag resulting `Output`s as immature, deferring them from `Batch` inclusion until 100 confirmations (maturity), matching the `scan_block` docstring's contract, or
- At minimum, detect coinbase outputs matching registered scripts and emit an alert/record so funds can be recovered rather than permanently stranded.

### Proof of Concept
1. On regtest (or via a miner on mainnet), construct a coinbase transaction whose output `script_pubkey` equals `p2tr_script_buf(group_key)` (the `External` script, or a `Branch`/`Forwarded` script via `Bitcoin::branch_address`/`forward_address`).
2. Mine the block so the coinbase matures (>100 blocks). The output is now a standard, spendable P2TR UTXO paying the multisig key.
3. `Scanner::run` scans the block via `Bitcoin::get_outputs`, which iterates `block.txdata[1 ..]` and returns `[]` — no `Output` is produced, `save_outputs` stores nothing, and `scanned_block` advances past the block.
4. The UTXO exists on-chain under Serai's key but is permanently invisible to the scheduler and can never be included as an input in `SignableTransaction::new`, stranding the funds.
