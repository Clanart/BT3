### Title
Unbounded out-of-range read in CLVM canonical-encoding check on attacker-supplied spend data - (File: `chia/full_node/mempool_manager.py`)

### Summary
The reported CVE describes SPICE trusting crafted "surface parameters" (length/size fields) supplied by an untrusted party and using them to index memory without validating that the indicated size actually fits inside the backing buffer, leading to out-of-bounds reads/writes. The `chia-blockchain` mempool admission path contains a structurally analogous pattern: `is_atom_canonical()` in `chia/full_node/mempool_manager.py` reads a CLVM length-prefix byte from an attacker-controlled buffer (a submitted transaction's `puzzle_reveal`/`solution`), decides how many additional prefix bytes to consume based on that byte's high bits, and then walks forward reading those bytes with no check that the buffer actually contains them.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` inspects the leading byte to pick a length-prefix format (0-5 extra bytes depending on the high bits of the atom marker) and then does: [1](#0-0) 
for each of the `prefix_len` expected continuation bytes, it increments `offset` and indexes `clvm_buffer[offset]` directly, with no bounds check that `offset < len(clvm_buffer)`.

This function is invoked from `is_clvm_canonical()`, which is itself called directly on attacker-controlled, unsigned wire data — the `puzzle_reveal` and `solution` bytes of every coin spend in a submitted `SpendBundle` — during mempool admission: [2](#0-1) 

A single submitted spend bundle whose `puzzle_reveal` or `solution` byte string ends exactly at (or a few bytes past) a multi-byte atom length-prefix marker (e.g. a trailing `0xF8`, `0xFC`, `0xE0`, etc. byte with insufficient trailing bytes) causes `is_atom_canonical` to index past the end of the buffer. In Python this raises `IndexError` rather than corrupting memory, but the effect on the reachable, unprivileged attack surface is the same class of bug as the CVE: a crafted "size/length" field is trusted to determine how far to read/index into a buffer without validating the buffer actually has that much data.

### Impact Explanation
`validate_spend_bundle()` is on the hot path for every spend bundle a wallet or peer submits to the mempool. An unhandled `IndexError` raised out of `is_clvm_canonical()`/`is_atom_canonical()` during this call would propagate out of the coroutine handling spend-bundle admission. If this exception is not caught by an enclosing handler in the call chain that invokes `validate_spend_bundle` (I was not able to fully trace every caller in the time available — this is the primary remaining uncertainty), a single crafted, low-cost, low-value spend bundle could repeatedly throw unhandled exceptions during mempool admission, denying transaction processing for the node (a spend-triggered transaction-processing halt), which is one of the accepted impact categories.

### Likelihood Explanation
Likelihood is high for triggering the underlying bounds violation: constructing a `puzzle_reveal`/`solution` byte string that ends immediately after a multi-byte-prefix atom marker requires no special privilege and no valid signature check ahead of this canonical-form check (canonical-form validation happens before/alongside dedup-eligibility processing, on every coin spend, regardless of whether the spend is otherwise valid). The uncertainty is whether an outer `try/except` around the mempool-admission call path swallows the resulting `IndexError` before it can cause a processing halt — I could not confirm this from the code visible to me.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before indexing `clvm_buffer[offset]` for each of the `prefix_len` continuation bytes (mirroring the bounds checks already present in `chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list` helpers, which raise a controlled `ValueError` instead of indexing past the buffer), and ensure `is_clvm_canonical()`/`validate_spend_bundle()` catch and convert any parsing failure into `Err.INVALID_COIN_SOLUTION` rather than letting a raw `IndexError` escape.

### Proof of Concept
Construct a `CoinSpend` whose `solution` (or `puzzle_reveal`) is a single byte `0xF8` (the 4-extra-byte length-prefix marker) with no following bytes, and submit it in a `SpendBundle`:
```python
coin_spend = make_spend(
    TEST_COIN,
    IDENTITY_PUZZLE,
    SerializedProgram.fromhex("f8"),   # atom marker claiming 4 more length bytes, buffer ends here
)
sb = SpendBundle([coin_spend], G2Element())
```
When this reaches `MempoolManager.validate_spend_bundle()`, `is_clvm_canonical(bytes(coin_spend.solution))` calls `is_atom_canonical(buf, 0)`, which reads `buf[0] == 0xF8` (prefix_len=4) and then attempts `buf[1]`, `buf[2]`, `buf[3]`, `buf[4]` on a 1-byte buffer, raising `IndexError` instead of returning a validation error.
