### Title
Unauthenticated cross-shop access-scope oracle via unverified `params[:shop]` in `ShopAccessScopesVerification` - ([File: app/controllers/concerns/shopify_app/shop_access_scopes_verification.rb])

### Summary
`ShopifyApp::ShopAccessScopesVerification#current_shopify_domain` derives shop identity solely from `params[:shop]` (sanitized, but not verified against any token/session), and feeds it into `ShopStrategy.update_access_scopes?`, which queries the stored session for that shop and compares its granted scope to the app's configured scope. An anonymous attacker who supplies a victim's `shop` param can trigger this check and observe a redirect-vs-no-redirect response difference that reveals whether the victim's stored offline session's scope differs from the app's configured scopes.

### Finding Description
`current_shopify_domain` in this concern is defined as: [1](#0-0) 
It only reads and sanitizes `params[:shop]` — there is no ID token, HMAC, or session verification anywhere in this concern's `before_action` chain: [2](#0-1) 

`scopes_mismatch?` passes this attacker-controlled value straight to `ShopifyApp.configuration.shop_access_scopes_strategy.update_access_scopes?`, which resolves to `ShopStrategy` when `reauth_on_access_scope_changes` is enabled: [3](#0-2) 

`ShopStrategy.update_access_scopes?` looks up the *victim's* stored offline session purely by the shop domain and compares its scope to the app's configured scope, with no ownership/authentication check of the caller: [4](#0-3) 

The resulting boolean directly determines whether `login_on_scope_changes` issues a redirect (`redirect_for_embedded` or `redirect_to(shop_login)`) or lets the request fall through to the action, as shown by the existing test asserting a redirect in the mismatch case and `:ok` in the match case: [5](#0-4) 

That test also demonstrates the concern can be mixed into a bare controller with no other authentication concern (`ScopesVerificationController < ActionController::Base`), so nothing inherently blocks an unauthenticated request from reaching `scopes_mismatch?`: [6](#0-5) 

No check anywhere in this path (sanitize_shop_domain, `update_access_scopes?`, or the calling before_action) verifies that the shop in `params[:shop]` corresponds to the actual authenticated caller — it is used purely as a lookup key into `SessionRepository`, breaking the invariant that shop identity must come from a verified token.

### Impact Explanation
This is a cross-shop information-disclosure oracle: an attacker who knows/guesses a victim's `myshopify.com` domain can determine, via the presence or absence of a redirect, whether that shop's stored granted OAuth scope currently differs from the app's configured scope (and, incidentally, whether the app is installed on that shop at all, since a missing session also yields a "mismatch"). No access token or secret is leaked, and no data/action access is granted — the impact is limited to a binary scope/installation-state oracle across shops, matching a low-severity information disclosure / improper authorization class of finding on Shopify's HackerOne scope.

### Likelihood Explanation
Exploitation requires only: (1) the target app to have `reauth_on_access_scope_changes` enabled (documented default recommendation) and include `ShopAccessScopesVerification` on a route reachable without prior authentication succeeding before this before_action runs, and (2) the attacker to know or guess the victim's `*.myshopify.com` domain (often guessable/enumerable from shop names). No secrets, tokens, or victim interaction are needed — a single unauthenticated GET request is sufficient, making this trivially repeatable.

### Recommendation
Derive shop identity for scope comparison from a verified source (validated ID token claim or the already-authenticated session's `shop`), not from the raw `params[:shop]`. If `ShopAccessScopesVerification` must support pre-auth contexts, it should not perform a scope-existence lookup keyed by an unverified value; instead it should only run after `EnsureHasSession`/token verification has bound `current_shopify_domain` to a verified shop, or it should use `authenticated_shopify_domain` (from the verified session) rather than `requested_shopify_domain`/`params[:shop]`.

### Proof of Concept
Using the existing test harness pattern but stubbing the real `SessionRepository` (not the strategy) to simulate a victim's stored session, to show the oracle works end-to-end without any authentication:

```ruby
class ScopesVerificationController < ActionController::Base
  include ShopifyApp::ShopAccessScopesVerification

  def index
    render(plain: "OK")
  end
end

class ShopAccessScopesOracleTest < ActionController::TestCase
  tests ScopesVerificationController

  setup do
    ShopifyApp.configuration.reauth_on_access_scope_changes = true
    ShopifyApp.configuration.shop_access_scopes = "read_products,write_products"
    @victim_domain = "victim-shop.myshopify.com"
    Rails.application.routes.draw { get "/", to: "scopes_verification#index" }
  end

  test "unauthenticated attacker learns victim's scope-mismatch state via redirect vs 200" do
    # Victim has a stored offline session with narrower scope than configured
    ShopifyApp::SessionRepository.stubs(:retrieve_shop_session_by_shopify_domain)
      .with(@victim_domain)
      .returns(ShopifyAPI::Auth::Session.new(shop: @victim_domain, scope: "read_products"))

    get :index, params: { shop: @victim_domain } # no auth header, no id token, no HMAC

    assert_redirected_to(/login/) # reveals scope mismatch for victim shop
  end

  test "same unauthenticated request with matching scope returns 200 (distinguishable oracle)" do
    ShopifyApp::SessionRepository.stubs(:retrieve_shop_session_by_shopify_domain)
      .with(@victim_domain)
      .returns(ShopifyAPI::Auth::Session.new(shop: @victim_domain, scope: "read_products,write_products"))

    get :index, params: { shop: @victim_domain }

    assert_response :ok # reveals scope match for victim shop
  end
end
```
Both requests are made with no `Authorization` header, no valid ID token, and no HMAC — only `params[:shop]` set to the victim's domain — yet the response (redirect vs 200) differs based solely on the victim's stored session state, confirming the oracle.
