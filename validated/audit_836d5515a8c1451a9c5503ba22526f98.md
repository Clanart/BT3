Based on my investigation, the claim is substantiated by the actual code in this repository.

`pending_delegator_rewards` is incremented only by `add_pending_delegator_rewards`, called from `deposit_delegator_rewards`, which is reachable via the permissionless `VoteInstruction::DepositDelegatorRewards` (requiring only the source account to sign, not any privileged authority) [1](#0-0) [2](#0-1) . The field is read every epoch by `calculate_block_reward`, which computes `stake/total_active_stake * pending_delegator_rewards` and returns it as the stake account's `block_reward` with no state change to the vote account [3](#0-2) . That `block_reward` is added directly to the stake account's lamports in `build_updated_stake_reward` [4](#0-3) .

I searched exhaustively across `programs/vote/src/vote_state/handler.rs`, `programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, and `distribution.rs` for any decrement/subtraction of `pending_delegator_rewards` (`checked_sub`, `-=`, reassignment to a reduced value, or any "consume" function) and found none — `add_pending_delegator_rewards` is confirmed as the only mutator [5](#0-4) . The `withdraw` function only reads and reserves the value; it never subtracts from it either [6](#0-5) . Capitalization accounting in `distribute_epoch_rewards_in_partition` only tracks `stake_reward_lamports_minted` and `block_reward_lamports_burned`, never a "block_reward_lamports_distributed"-driven decrease of the vote account's real balance or of `pending_delegator_rewards` [7](#0-6) . The `update_epoch_rewards_sysvar` debit of `debit_block_reward_lamports` is explicitly against the `epoch_rewards` sysvar account, not the vote account, and is noted as "since block reward lamports already existed" — meaning it's not fixing the actual root-cause bug [8](#0-7) .

I could not find any later pipeline stage that updates the vote account's `pending_delegator_rewards` field down; `store_stake_accounts_in_partition` only stores updated stake accounts, never vote accounts [9](#0-8) . This confirms the reported bug class: the pool is deposited once but paid out every epoch indefinitely, without decrement.

Audit Report

## Title
`pending_delegator_rewards` in `VoteStateV4` is never decremented after being distributed, causing indefinite re-payout of a single deposit and unbacked lamport creation - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

## Summary
Any unprivileged signer can call `VoteInstruction::DepositDelegatorRewards` to transfer lamports into a vote account and set `pending_delegator_rewards` via `add_pending_delegator_rewards`. Every subsequent epoch, `calculate_block_reward` reads this same, never-decremented field and re-computes and re-credits a proportional share of it to delegated stake accounts, meaning a single deposit is paid out repeatedly, forever, with no corresponding debit anywhere in the codebase.

## Finding Description
`deposit_delegator_rewards` transfers `deposit` lamports from any signing `source_address` into the vote account and calls `vote_state.add_pending_delegator_rewards(deposit)` [1](#0-0) , gated only by feature flags, not by any privileged authority check on the vote account itself [2](#0-1) . `add_pending_delegator_rewards` is a pure additive `checked_add` with no counterpart subtractive function anywhere in `handler.rs` [5](#0-4) .

Each epoch, `calculate_block_reward` reads `vote_state.pending_delegator_rewards()` and computes `stake/total_active_stake * pending_delegator_rewards`, clamped to `pending_delegator_rewards`, as the delegator's `block_reward` [3](#0-2) . This is invoked unconditionally (once `block_revenue_sharing` is active) inside `calculate_stake_rewards_and_commissions`, which runs for every stake delegation every epoch [10](#0-9) . The resulting `block_reward` is added straight to the stake account's lamports in `build_updated_stake_reward` [4](#0-3) , and `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition` only store updated *stake* accounts and adjust `capitalization` using `stake_reward_lamports_minted`/`block_reward_lamports_burned` — never touching the vote account or `pending_delegator_rewards` [11](#0-10) [12](#0-11) .

The `withdraw` instruction's handling of `pending_delegator_rewards` merely reserves that balance from being withdrawn by the authorized withdrawer, confirming the intended semantics of a bounded, spendable-once pool, but it never decrements the field either [6](#0-5) . The only sysvar-side accounting, `update_epoch_rewards_sysvar`, debits `debit_block_reward_lamports` from the `epoch_rewards` sysvar account (not the vote account or `pending_delegator_rewards`) and its comment explicitly notes "since block reward lamports already existed" — this is bookkeeping unrelated to fixing the source-of-truth field [13](#0-12) .

I found no decrement, no "consume" operation, and no later re-serialization of the vote account with a reduced `pending_delegator_rewards` anywhere in the reward calculation or distribution pipeline (`calculation.rs`, `distribution.rs`, `handler.rs`, `mod.rs`). The existing guard in `withdraw` only prevents extraction of the pool by the withdraw authority — it does not prevent re-payout to delegators every epoch.

## Impact Explanation
This is a fund/accounting-correctness bug in the runtime reward-distribution path (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs` and `distribution.rs`), which is consensus-critical state computed identically by every validator. A single, even tiny, `DepositDelegatorRewards` deposit causes stake accounts delegated to that vote account to receive the same proportional block reward every epoch indefinitely, without any bound on total payout versus what was actually deposited. This constitutes unbounded lamport duplication tied to stake account balances, a "false execution"/fund-creation class bug matching the target-scope category of accounting correctness in `runtime`/built-ins.

## Likelihood Explanation
The exploit path requires only an unprivileged signer with lamports to call `DepositDelegatorRewards` against any `VoteStateV4` vote account with active delegated stake — no privileged keys, no validator/peer trust assumptions, and no gossip/plugin involvement. It is gated behind `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing` (SIMD-0123/0185/0232/0291) all being active simultaneously, so it is currently not exploitable unless/until all three features are enabled on the target cluster. Given index-size limits, I could not fully rule out an unindexed decrement step existing elsewhere in the codebase, but an exhaustive search of every mutator/reader of `pending_delegator_rewards` across `programs/vote/src/vote_state/{mod,handler}.rs` and `runtime/src/bank/partitioned_epoch_rewards/{calculation,distribution,sysvar}.rs` found none.

## Recommendation
Decrement `pending_delegator_rewards` by the total `block_reward` actually distributed each epoch (summing `block_reward_lamports_distributed` computed in `store_stake_accounts_in_partition`) and persist the updated vote account state, ensuring the vote account's real lamport balance is debited by the same amount so that a single deposit cannot be paid out more than once and `capitalization` remains consistent with real total lamports in existence.

## Proof of Concept
1. Enable `block_revenue_sharing`, `custom_commission_collector`, and `commission_rate_in_basis_points`; create a `VoteStateV4` vote account with an active stake delegation.
2. Any unprivileged account calls `VoteInstruction::DepositDelegatorRewards { deposit: X }`, transferring `X` lamports into the vote account and setting `pending_delegator_rewards = X` (verified in the existing test at `programs/vote/src/vote_processor.rs` lines 5110–5140).
3. At epoch N, `calculate_block_reward` computes `stake/total_active_stake * X` and credits it to the delegated stake account via `build_updated_stake_reward`.
4. At epoch N+1 (and every epoch after, as long as the same stake remains delegated), `pending_delegator_rewards` is still `X` — no decrement path exists in `handler.rs`, `mod.rs`, `calculation.rs`, or `distribution.rs` — so `calculate_block_reward` computes and credits the same reward again, repeating indefinitely from the original single deposit. A unit test asserting `pending_delegator_rewards` remains unchanged (and equal to the total block rewards already distributed across N epochs) after `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition` runs would confirm the bug.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
