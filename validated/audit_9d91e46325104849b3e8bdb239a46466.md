Based on my investigation, the closest structural analog to the `rescheduleGame` bug — a function that updates one piece of state (`startTime`) while leaving a dependent, security-relevant piece of state (`endTime`) stale, and where downstream code only checks a coarse condition instead of full consistency — is in GitHub Desktop's Copilot merge-conflict resolution pipeline.

### Title
Stale-content conflict resolution write in `_applyCopilotConflictResolutions` can silently overwrite unresolved user edits with outdated Copilot resolutions - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When Desktop resolves merge/rebase/cherry-pick conflicts with Copilot, the resolved file content is computed once (from a snapshot of on-disk file content captured when the conflict context was built) and is only written to disk later, when the user clicks "Continue Merge." The write path guards against exactly one scenario — the file being *fully* resolved outside Desktop — but does not verify that the file's conflicted content is still the same content the resolution was computed against. As with `rescheduleGame`, only one of two logically-linked values is validated (resolution status) while the other (content identity/freshness) is not, breaking the invariant that "what the user reviewed in the diff is what gets written and committed."

### Finding Description
`buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:376-461`) reads each conflicted file once via `readFile(absolutePath, 'utf8')` and stores it as `rawContent`. Later, `reassembleResolutions` (`app/src/lib/copilot-conflict-resolution.ts:609-642`) uses that captured `rawContent` — not a fresh read — to splice the model's per-hunk resolutions back into place via `reassembleResolvedFile`, which walks the captured content line-by-line matching conflict markers "by order, not by line number" [1](#0-0) .

When the user confirms and clicks "Continue Merge," `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7169-7269`) re-reads the *current* working-directory state only to decide whether to skip a file: [2](#0-1) 

This check only catches the case where the file has *no remaining conflict markers* (i.e., the user fully resolved it externally). If the file still contains conflict markers — for example, because the repository (attacker-controlled, cloned/fetched content) legitimately contains lines that look like conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`) inside real file content (e.g., documentation, sample patches, chat transcripts, spec fixtures) interleaved with an actual conflict — `hasUnresolvedConflicts` will still report `true`, and Desktop proceeds to `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` using the stale, pre-computed resolution [3](#0-2) .

Because `reassembleResolvedFile` matches conflict-marker blocks purely by regex pattern and ordinal position rather than by git's actual stage/hunk boundaries [4](#0-3) , a repository crafted so that a file contains marker-like text outside of a true conflict region (e.g. a README documenting git conflict resolution, or a fixture `.diff`/`.patch` file) can desynchronize the hunk index counting from what the model actually reasoned about. The result is that Desktop can splice model output for one logical hunk into the wrong location in the file, or write resolved content for a hunk that no longer matches the current on-disk hunk (if the file was edited in the interim), without any re-verification against the file's current content.

The two related pieces of state — "the exact bytes the resolution was generated from" and "the exact bytes currently on disk" — are updated/checked asymmetrically: `resolvedContent` is frozen at analysis time, but the write-time guard only asks a coarse yes/no question ("are there still conflict markers?") instead of confirming the underlying content is unchanged (e.g., via a content hash comparison), exactly mirroring how `rescheduleGame` updated `startTime` without validating/recomputing the dependent `endTime`.

### Impact Explanation
This falls in-scope as "silent corruption of what the user commits or pushes": the file Desktop writes and stages (`git add`) can differ from the file the user reviewed in the Copilot conflict diff, without any error or warning, because the write path never compares the resolution's source content against the current file. A crafted upstream/attacker-controlled repository (the merge target, a malicious branch, or a PR the user pulls and merges) can trigger content that confuses the ordinal hunk-splicing logic, corrupting the committed result in a way the user does not see before confirming.

### Likelihood Explanation
This requires: (1) the user opts into and uses the Copilot conflict-resolution feature, (2) a conflicting merge/rebase against attacker-influenced content (a cloned/fetched branch or file the user merges), and (3) either a timing window where the file changes between analysis and confirmation, or file content that contains conflict-marker-like text outside the true conflict boundaries. This is a realistic but not trivial condition — it depends on the specific structure of the attacker-controlled file and the existing marker-based reassembly design, which the codebase already acknowledges as order-dependent rather than position-verified. I was not able to execute the reassembly logic to confirm a concrete crafted-file misparse in this session, so likelihood should be treated as plausible-but-unverified pending dynamic testing.

### Recommendation
At write time, re-derive `resolvedContent` from a fresh read of the file (or re-verify the captured `rawContent` still byte-for-byte matches the current on-disk content) before calling `writeFile`, and abort/refresh the resolution if they differ — mirroring the fix pattern recommended for `rescheduleGame` (recompute the dependent value rather than trusting a stale one). Additionally, `reassembleResolvedFile` should anchor hunk substitution to concrete git conflict-stage boundaries (e.g., verified via `git status`/index stage byte offsets) rather than purely textual marker scanning, to avoid marker-lookalike content in unrelated file regions desynchronizing hunk indices.

3. Before clicking "Continue Merge," modify the file's content (or have it externally modified) in a way that still leaves genuine conflict markers present (so `hasUnresolvedConflicts` remains `true`).

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
