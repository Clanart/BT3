### Title
Unauthenticated `EncryptedMessage` is decrypted and its ECDH key released as blame before the proof-of-possession is verified - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
In `KeyMachine::calculate_share`, each incoming `EncryptedMessage` is decrypted with an ECDH key derived from the recipient's static encryption key, the resulting `EncryptionKeyProof` (which *reveals* that ECDH key) is produced, and if the decrypted bytes are not a canonical scalar the function returns early — before `batch.verify_with_vartime_blame()` has verified the Schnorr proof-of-possession on the message key. An unauthenticated party can therefore inject a forged `EncryptedMessage` whose `key` field reuses the per-message key of a victim's genuine share message, obtain a blame proof containing `enc_key * X`, and thereby recover the decryption key of the victim's real secret share — the exact attack the PoP was added to prevent (`encryption.rs:84-90`).

### Finding Description
`Encryption::decrypt` queues the PoP (`msg.pop.batch_verify`) into the caller's batch verifier, but immediately applies the ChaCha20 keystream and returns the plaintext together with an `EncryptionKeyProof` containing `key = ecdh(enc_key, msg.key)` and a DLEq proof binding it to the recipient's registered encryption key (`encryption.rs:469-501`). In `calculate_share` (`lib.rs:476-482`), the result of `C::F::from_repr` on the decrypted bytes is checked inline; on failure the function returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` immediately, skipping `batch.verify_with_vartime_blame()` at `lib.rs:493` entirely. Hence a message with a completely invalid/missing PoP still causes the recipient to emit a publicly-verifiable proof revealing the ECDH shared key for the attacker-chosen `msg.key`. The ChaCha20 keystream is fixed given the ECDH point, so a forged ciphertext (e.g., all-0xFF body, per `invalidate_share_serialization`) decrypts to non-canonical bytes with high probability (~7/8 for ed25519/Ristretto), triggering the early-return path deterministically enough for repeated injection.

### Impact Explanation
The attacker frames the forged message as coming from victim sender `V`, setting `msg.key = X` where `X` is the per-message ephemeral key observed in `V`'s genuine `EncryptedMessage` to this recipient (or any key whose ECDH value the attacker wants). When the recipient errors out, it returns `EncryptionKeyProof { key: enc_key * X, dleq }`, which is broadcast as the blame object. `key` is exactly the cipher key for `V`'s real share message, so the attacker decrypts `V`'s secret share to that recipient. DKG secret shares are secret key material; across participants/attempts this undermines the confidentiality of the threshold key contribution. The library's own comments identify this exact side channel ("Bob would then use this to create a blame argument against Eve… they'd reveal bX, revealing Alice's message to Bob") as the reason the PoP exists — the early return reintroduces it. Analogous to the Odyssey flaw: unauthenticated bytes injected before authentication completes are processed and produce effects as if authentic.

### Likelihood Explanation
Reachable by any party able to deliver a share message to a DKG participant (`EncryptedMessage::read` feeds `calculate_share` via `processor/src/key_gen.rs:409-416`); no valid key share or signature is required. Construction requires only copying an observed `key` point and supplying bytes that decrypt to a non-canonical scalar, which succeeds with overwhelming probability without knowing the plaintext. The main constraint is that each abort leaks at most one share per recipient per session, and the leaked material is one polynomial evaluation rather than the full group key.

### Recommendation
Verify the PoP before performing decryption or releasing `EncryptionKeyProof`: run `msg.pop.verify(...)` (or a per-message mini-batch) at the top of `Encryption::decrypt`, and return `PedPoPError::InvalidShare { participant: l, blame: None }` for PoP failures — matching how `decrypt_with_proof` already treats `InvalidSignature` — so no ECDH key is ever published for an unauthenticated message. Alternatively, defer all `from_repr` early-returns in `calculate_share` until after `batch.verify_with_vartime_blame()` completes.

### Proof of Concept
1. Victim `V` (participant 1) sends `EncryptedMessage { key: X, pop, msg }` to recipient `R` (participant 2); attacker `E` observes `X`.
2. `E` delivers to `R` a forged message attributed to `V`: `key = X`, any `pop` (e.g., invalid), `msg` = 32 bytes of `0xFF` (`SecretShare::<C::F>` repr).
3. `R`'s `calculate_share` calls `decrypt`, computing `proof.key = enc_key_R * X` — the decryption key for `V`'s real message — queues the (failing) PoP, applies the keystream, and `C::F::from_repr(0xFF…)` fails, returning `InvalidShare { participant: V, blame: Some(proof) }` before batch verification runs.
4. `R` publishes `blame` (as in `key_gen.rs:419-425`). `E` verifies it via `decrypt_with_proof` semantics — but note the PoP check inside `blame_internal` will blame `V` regardless, while `E` already has `enc_key_R * X` from the proof and decrypts `V`'s share to `R` directly with `cipher(context, proof.key)`.
