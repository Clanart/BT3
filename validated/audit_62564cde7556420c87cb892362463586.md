## Title
Auction `SubmitBid` broadcasts the target transaction before the bid's authorization (Auctioneer/Searcher signature) checks are performed - (File: kaiax/auction/impl/api.go)

### Summary
The externally reported CVE-2020-19005 in zrlog is a broken-access-control bug: a privileged action (downloading the DB backup) executes based on a stale/global authorization state rather than validating the specific caller's permission for that specific request, so an unauthorized caller ends up performing the privileged action anyway.

The analogous flaw in this repository is in the public `auction_submitBid` RPC handler. `AuctionAPI.SubmitBid` unconditionally relays the caller-supplied `targetTxRaw` to the transaction pool/network via `api.a.Backend.SendTx(ctx, targetTx)` *before* the bid's authorization data (the `SearcherSig`/`AuctioneerSig` that prove the bid actually came from the legitimate `Auctioneer`/searcher) is checked in `bidPool.AddBid` → `validateBid` → `validateBidSigs`. Any unprivileged public-RPC caller can supply an arbitrary, unsigned/invalid bid alongside any raw transaction and have that transaction injected and gossiped, completely independent of whether the accompanying authorization proof is valid.

### Finding Description
`SubmitBid` performs the state-changing/network-affecting action first, then the authorization check second: [1](#0-0) 

Concretely:
1. `toTx(bidInput.TargetTxRaw)` decodes an attacker-supplied raw transaction with no signature/ownership requirement tying it to the caller of the RPC.
2. `api.a.Backend.SendTx(ctx, targetTx)` is called and broadcasts/pools this transaction **unconditionally** (except for hash mismatch), *before* any bid-signature validation occurs.
3. Only afterward is `ToBid(bidInput)` built and passed to `api.a.bidPool.AddBid(bid)`, which is where `validateBidSigs` actually verifies `ValidateSearcherSig`/`ValidateAuctioneerSig`: [2](#0-1) 

Because step 2 (the protected/consequential action — network transaction submission attributed to the auction flow) happens irrespective of the outcome of step 3 (the actual authorization/permission check), the authorization check is disconnected from the action it is supposed to gate — mirroring the CVE's root cause where the permission check does not actually gate the protected resource access.

The `auction` namespace API is registered with `Public: false`: [3](#0-2) 

but this only controls whether the namespace is auto-whitelisted; once an operator enables the `auction` module on an HTTP/WS endpoint (as documented, `auction_submitBid` is a plain JSON-RPC method reachable by any public-RPC caller), no per-call identity/signature check gates the `SendTx` call itself — the only real gatekeeping (`validateBidSigs`) is checked too late to prevent the transaction relay.

### Impact Explanation
An unauthenticated/unprivileged public-RPC caller can use `auction_submitBid` to force the node to call `SendTx` on an arbitrary attacker-chosen raw transaction while supplying a garbage/invalid `SearcherSig`/`AuctioneerSig`. This:
- Bypasses the intended access-control model of the auction flow (only the legitimate `Auctioneer` should be able to trigger target-tx relay tied to a winning bid).
- Allows spamming/flooding the tx-pool and gossip network with attacker-chosen transactions labeled as "auction target transactions", since the send always happens even though the bid itself is subsequently rejected as invalid (`ErrInvalidSearcherSig`/`ErrInvalidAuctioneerSig`/etc.), as shown by the test cases that still exercise the send path before failing bid validation: [4](#0-3) 

This is a state-affecting side effect (transaction relay to the network) that is not properly gated by the authorization mechanism designed to protect it, satisfying the "acceptance of an invalid/unauthorized action reaching consensus-relevant infrastructure" bar for a Medium-severity broken-access-control analog.

### Likelihood Explanation
Any node operator that enables the `auction` RPC module on a public HTTP/WS endpoint (as the KIP-249 auction module's public API is documented and intended to be reachable by searchers/bidders over the network) exposes this method to any remote caller without further authentication. Triggering the bug requires only a single crafted JSON-RPC call with any raw transaction and a syntactically-sized (not necessarily cryptographically valid) signature — no special privileges, staking, or prior state are needed.

### Recommendation
Reorder `SubmitBid` so that the authorization checks in `bidPool.validateBid`/`validateBidSigs` (searcher signature, auctioneer signature, block-number/bid-amount rules) are performed and passed **before** `api.a.Backend.SendTx` is invoked, so that no network-affecting action occurs for a bid that fails authorization. Alternatively, validate the searcher/auctioneer signatures on the `BidInput` directly at the top of `SubmitBid` prior to decoding/sending the target transaction.

### Proof of Concept
1. Enable the `auction` module on a node's public HTTP endpoint.
2. Call `auction_submitBid` with:
   - `targetTxRaw` set to any validly RLP-encoded transaction (attacker does not need to own funds tied to this tx being propagated — only its bytes need to decode and its hash needs to match `targetTxHash`).
   - `searcherSig` / `auctioneerSig` set to any well-formed-but-wrong-length-or-value signature bytes (e.g., as used in the existing `invalidSearcherSigLenBid` / `unexpectedSEarcherSigBid` test fixtures).
3. Observe that the RPC response returns a bid-validation error (`ErrInvalidSearcherSig`, etc.) as in `TestSubmitBid`, but `api.a.Backend.SendTx` was already invoked on `targetTx` in step "1. directly send target transaction" of `SubmitBid` before the error was produced — the transaction is injected into the pool/gossiped regardless of the bid's authorization outcome.

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
