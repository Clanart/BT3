### Title
`SignableTransaction::new` omits the OP_RETURN data output from fee/vsize accounting, producing signed transactions that underpay the requested fee rate and may fall below the minimum relay fee - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The vulnerability class in the external report is a multi-phase process where a value assumed fixed after phase 1 changes before phase 2, corrupting downstream accounting. In `SignableTransaction::new`, the transaction outputs are mutated (an OP_RETURN output is appended, and possibly a change output) *after* — and independently of — the fee computation, but `calculate_weight_vbytes` only ever accounts for `payments` and `change`, never the data output. The result is incorrect fee accounting: the signed transaction's actual fee rate is lower than the caller-specified `fee_per_vbyte`, and can silently drop below Bitcoin's minimum relay fee, leaving the threshold-signed transaction unbroadcastable and its inputs unspendable.

### Finding Description
`SignableTransaction::new` builds `tx_outs` from `payments`, then appends an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` (networks/bitcoin/src/wallet/send.rs:194-202). However, the weight/vsize used for `needed_fee` is computed as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204), which constructs a template transaction whose outputs are *only* `payments` (and optionally `change` at line 226). The OP_RETURN output — which adds roughly `1 (value) + 1 (script len) + ~2 (OP_RETURN pushdata header) + data.len()` bytes, up to ~84 vbytes... concretely ~11 + 80 ≈ 91 weight units / ~23 vbytes, plus output overhead ≈ ~34 vbytes total — is never included.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` undercounts by the OP_RETURN output's vsize (line 206).
- The `TooLowFee` check (lines 211-213) validates `needed_fee` against the *underestimated* `vbytes`, so a caller requesting exactly the minimum relay rate passes validation while the real transaction is below minimum.
- The change branch (lines 224-235) uses `fee_with_change` computed from the same data-less template, so change can absorb satoshis that should have paid for the OP_RETURN output's weight, pushing the *actual* fee (`sum(inputs) - sum(outputs)`, line 138-141) further below the intended rate.
- `needed_fee()` (line 133) reports the wrong value to callers.

The `data` field is attacker-influenced transaction data fed into a transaction the threshold group is caused to sign (e.g., InInstruction/bridge payloads), satisfying the reachability requirement.

### Impact Explanation
The multisig produces a fully-signed, validly-formed transaction that pays less than the requested fee rate. If the caller requested the minimum viable rate (e.g., 1 sat/vB or the checked `DEFAULT_MIN_RELAY_TX_FEE` floor), the ~23-34 vbyte omission makes the real feerate fall under the relay minimum — standard nodes reject it. The inputs are then locked in a transaction that cannot confirm: the specific `SignableTransaction`/expected `txid` can never complete on-chain, and any protocol state machine tracking that txid stalls until a corrected transaction is re-signed. Even when the tx remains relayable, the protocol silently pays a lower feerate than budgeted, degrading confirmation reliability — an accounting error directly analogous to the report's "liquidation fee computed larger than the locked LF entitles" misaccounting.

### Likelihood Explanation
Deterministic whenever `data` is non-empty. The only condition is that the requested `fee_per_vbyte` be close enough to the minimum (or to confirmation-critical levels) that the omitted ~23-34 vbytes matter — plausible precisely because the code contains an explicit `TooLowFee` guard intended to enforce the floor, which this bug bypasses. No collusion, malicious validator, or leaked key is required; only caller-supplied transaction data.

### Recommendation
Include the OP_RETURN output in the weight template: pass the fully-built `tx_outs` (or `payments` plus a synthetic data output) into `calculate_weight_vbytes` for both the no-change and with-change computations, so `vbytes`, `needed_fee`, the `TooLowFee` check, and the change-amount computation all reflect the final transaction. Alternatively, compute the weight directly from the final assembled `Transaction` before signing.

### Proof of Concept
```rust
// networks/bitcoin context; key/scanner setup as in tests/wallet.rs
let data = vec![0xaa; 80]; // maximum permitted OP_RETURN payload
let tx = SignableTransaction::new(
    vec![output.clone()],
    &payments,
    None,
    Some(data),
    1, // 1 sat/vbyte — at/near the minimum relay rate
).unwrap();

// needed_fee was computed on a template WITHOUT the OP_RETURN output
let underestimated_fee = tx.needed_fee();

// The real transaction carries the OP_RETURN output
let real_vbytes = tx.transaction().vsize() as u64; // includes the ~34 extra vbytes
// effective feerate = actual_fee / real_vbytes < 1 sat/vB
// => below DEFAULT_MIN_RELAY_TX_FEE => non-standard, rejected by relays,
// while the TooLowFee check passed because it used the smaller template vbytes.
```
The fix comparison: `calculate_weight_vbytes` is invoked with `payments` (lines 204, 226) while `tx_outs` — the value actually placed in the signed transaction — additionally contains the OP_RETURN output (lines 194-202), proving the accounting gap.
