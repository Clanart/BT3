## Title
Authorization Bypass Through Attacker-Controlled `authorized_providers` Key in CR-CAT Offer Authorization Leading to Wallet Approving Unauthorized Credential-Restricted Coin Spends - (File: `chia/wallet/vc_wallet/vc_wallet.py`)

### Summary
`VCWallet.add_vc_authorization()` is invoked automatically by `TradeManager.check_for_final_modifications()` whenever a taker's wallet processes an untrusted offer that contains a CR-CAT (Credential-Restricted CAT) leg. It selects which locally-held Verified Credential (VC) to spend/attest with purely by matching against the `authorized_providers` list that is embedded in the CR-CAT puzzle supplied by the *counterparty's* offer, and then decides whether to co-sign the CR-CAT spend using output-shape heuristics rather than verifying the coin actually belongs to, or is intended for, the local wallet. This mirrors the Kibana bug class (CWE-639, Authorization Bypass Through User-Controlled Key): an authorization credential scoped to one context (a specific provider/VC) is used to approve an action on a resource (a CR-CAT coin) whose ownership/target boundary was never actually validated, because the key used to select the authorizer (`authorized_providers`) is attacker/offer-controlled data.

### Finding Description
`add_vc_authorization` iterates over every incomplete CR-CAT spend present in an offer being taken: [1](#0-0) 

It selects `available_vcs[0]` — the first VC in the wallet's own store whose `proof_provider` happens to be present in `crcat_spend.crcat.authorized_providers`. That `authorized_providers` list is not data the wallet chose; it comes from the CR-CAT puzzle curried into the coin that is part of the **offer file supplied by the counterparty** (see `construct_cr_layer`/`match_cr_layer` in `chia/wallet/vc_wallet/cr_cat_drivers.py`). A malicious offer-maker fully controls which providers are listed for a given CR-CAT leg.

Having selected a VC purely by this attacker-influenced provider list, the code then decides whether to actually spend that VC's authorization by checking only structural properties of the CR-CAT’s own outputs — not whether the CR-CAT coin has anything to do with the local wallet's side of the trade: [2](#0-1) 

The "should we approve" branches are:
- output going to us (safe),
- output puzzle hash equal to `crcat_spend.crcat.inner_puzzle_hash` — i.e., the coin's *own current* owner, which is **not** necessarily the requesting/local wallet, it's whoever crafted the offer,
- output going to the pending-approval construct, or
- output going to the generic `OFFER_MOD` puzzle hash.

None of these actually confirm that the CR-CAT coin being approved belongs to, or was requested by, the local user's trade. As long as an offer is structured so a CR-CAT's outputs satisfy any of these shape checks (e.g., trivially returning to its own current puzzle hash, which any offer author can do at will) and its curried `authorized_providers` field happens to include a provider for which the local wallet holds *any* confirmed VC, the wallet will silently spend that VC to produce the on-chain announcement/proof-of-inclusion needed to authorize the coin's movement: [3](#0-2) 

This effectively lets an offer counterparty "borrow" the local wallet's VC-backed authority to move a CR-CAT coin that is outside the scope of what the local user actually intended to authorize in this trade — analogous to the Kibana issue where a key that scopes authorization to one context can be reused, due to insufficient binding, to act on a resource in a different context the caller was never meant to reach.

### Impact Explanation
CR-CATs are designed so that only holders of a VC issued by an `authorized_provider` can move restricted assets. If the wallet's VC-authorization logic can be tricked by a counterparty-crafted offer into attesting to spends beyond the trade the local user actually intends (because the provider-selection key and output-shape heuristics are both derived from attacker-supplied offer content rather than from a validated binding to the user's own trade), a malicious offer maker could obtain the taker's VC-backed approval/announcement for CR-CAT movements that were not part of the legitimate settlement the taker believed they were entering, undermining the credential-restriction guarantee that CR-CATs are meant to enforce for coins reachable via a single `take_offer` RPC call.

### Likelihood Explanation
This code path executes automatically and silently on every `take_offer`/`respond_to_offer` call whenever the offer contains any CR-CAT leg with an incomplete spend (`TradeManager.check_for_final_modifications` → `VCWallet.add_vc_authorization`), requiring no special privilege beyond possessing a VC from some provider that overlaps with an offer's `authorized_providers` list — a value entirely controlled by the offer author. No confirmation step or explicit user consent gates this VC selection/use.

### Recommendation
Bind VC selection and the approval decision to the specific asset/trade the local wallet actually requested or offered (e.g., cross-check the CR-CAT's asset id / launcher id against the offer's own `requested_payments`/`coins_to_offer` for this trade) rather than relying solely on (1) provider-list intersection sourced from the untrusted offer, and (2) generic output-shape heuristics such as "goes back to its own current puzzle hash." At minimum, require that a CR-CAT coin approved via this path be traceable to a coin actually referenced by the trade being accepted, and consider prompting explicit confirmation before spending a VC on behalf of a coin that is not moving to/from the local wallet.

### Proof of Concept
1. Taker's wallet holds a confirmed VC issued by provider `P`.
2. A malicious maker crafts an offer containing an incomplete CR-CAT spend for a coin unrelated to the taker's requested trade, with `authorized_providers = [P, ...]` curried into its CR layer, and structures its `CREATE_COIN` output puzzle hash to equal `crcat_spend.crcat.inner_puzzle_hash` (trivially satisfiable by any offer author).
3. Taker calls `take_offer` (`WalletRpcApi.take_offer` → `TradeManager.respond_to_offer` → `check_for_final_modifications` → `VCWallet.add_vc_authorization`).
4. `add_vc_authorization` selects the taker's VC (matching provider `P`) via `store.get_vc_records_by_providers(...)[0]`, evaluates `outputs_ok` as `True` due to the self-referential output puzzle hash, and produces the VC-backed proof-of-inclusion/announcement authorizing the unrelated CR-CAT spend as part of the taker's own transaction bundle — without the taker ever being shown that their VC was used for a coin outside their intended trade.
