### Title
Reachable process abort (`ABSL_LOG(FATAL)`/`abort()`) via unchecked-looking `CheckedAdd` overflow when merging packed repeated fields near `INT_MAX` - ([File: src/google/protobuf/parse_context.h])

### Summary
CVE-2018-10998 is a size-arithmetic overflow in Exiv2's JPEG2000 parser (`Safe::add` in `jp2image.cpp`) that was not properly guarded, causing an uncaught abort (`SIGABRT`) when a crafted file made an internal length addition overflow. The invariant that failed was "size1 + size2 must not overflow before being used to allocate/index," and the impact was an unrecoverable, uncatchable process termination triggered purely by attacker-controlled sizes.

The transferable invariant here is: *attacker-controlled length/count values must never be combined in address/size arithmetic in a way that can crash the process outside of the normal, catchable parse-failure path.* Protobuf's C++ implementation does check size additions for overflow (unlike Exiv2's original code), but the failure action for that check is not a graceful, catchable parse error — it is `ABSL_LOG(FATAL)`, which terminates the process via `abort()`. That converts a data-only condition into a hard process crash, which is exactly the externally observable effect of the Exiv2 bug (SIGABRT DoS), just reached through a "checked" instead of "unchecked" add.

### Finding Description
`internal::CheckedAdd` in `src/google/protobuf/port.h:930-963` computes `a + b` and, on overflow, calls `HandleAddOverflow(a, b)`, which is implemented in `src/google/protobuf/port.cc:185-187` as:

```
void HandleAddOverflow(absl::int128 a, absl::int128 b) {
  ABSL_LOG(FATAL) << "Integer overflow in CheckedAdd: " << a << " + " << b;
}
``` [1](#0-0) 

`ABSL_LOG(FATAL)` unconditionally aborts the process — it is not a `ParseFailed`/`InvalidProtocolBufferException`-style recoverable error; it is an uncatchable crash, structurally the same externally-observable failure mode as Exiv2's uncaught `SIGABRT`.

This helper is used directly in the packed-repeated-field wire parsing fast path, `EpsCopyInputStream::ReadPackedVarintArrayWithField` in `src/google/protobuf/parse_context.h`:

```
out.ReserveWithArena(arena, internal::CheckedAdd(out.size(), count));
...
out.ReserveWithArena(arena, internal::CheckedAdd(out.size(), count));
...
out.ReserveWithArena(arena, internal::CheckedAdd(old_size, count));
``` [2](#0-1) 

`out.size()` is the pre-existing element count of a `RepeatedField<T>` (attacker-uncontrolled in a single parse, but accumulates across repeated `MergeFrom`/`MergeFromString`/`ParseFromZeroCopyStream(..., append)` calls — a fully supported, documented public API pattern for concatenated-message streams). `count` is derived directly from the attacker-supplied packed field's byte length (`CountVarintsAssumingLargeArray(ptr, end)`), i.e. fully attacker-controlled. When `out.size() + count` exceeds `INT_MAX`, `CheckedAdd` does not return an error to the caller — it fatally aborts the whole process.

This is confirmed as an actually-reachable condition by protobuf's own regression test:

```
TEST_F(RepeatedFieldIsFullTest, RepeatedVarintOverflow) {
  ...
  msg.mutable_b()->resize(std::numeric_limits<int>::max() - 4);
  (void)msg.MergeFromString(str10);
  ...
  EXPECT_DEATH(..., HasSubstr("Integer overflow in CheckedAdd: "));
}
``` [3](#0-2) 

The test itself proves the crash is real, reproducible, and reached through the standard public `MergeFromString` entry point — the same class of API an ordinary client-facing application calls when accepting untrusted bytes.

### Impact Explanation
The effect is a hard, uncatchable process crash (denial of service) triggered by attacker-controlled length data in a packed repeated field, once the target `RepeatedField` has accumulated close to `INT_MAX` elements (e.g., via long-lived server processes that repeatedly merge/append client messages into the same in-memory message, or via processing a stream of concatenated messages with `ParseFromZeroCopyStream`/`MergeFrom`, both documented, supported patterns). This mirrors the CVE's impact tier (Medium, availability-only, `AV:N/AC:L/PR:N/UI:R/S:U/C:N/I:N/A:H`): no confidentiality/integrity compromise, no memory corruption or RCE — solely an availability/DoS impact from an aborted process, exactly analogous to Exiv2's `SIGABRT`.

### Likelihood Explanation
Reaching `INT_MAX` accumulated elements in one repeated field requires either (a) a long-running service that repeatedly merges attacker-supplied messages into a persistent in-memory message object without resetting it, or (b) processing an attacker-supplied stream close to the ~2GB single-message size ceiling with a densely packed single-byte-per-element field (e.g. packed `bool`/`enum`). Case (a) is a realistic, supported usage pattern (accumulating repeated fields across multiple `MergeFrom` calls, e.g. log aggregation or streaming APIs); case (b) is close to protobuf's own 2GB total-message-size limit, making it a boundary condition rather than something requiring an implausibly huge single input. This is a Medium-likelihood DoS bug: it needs specific pre-conditions (an already near-saturated repeated field, or an application-level merge/accumulate pattern) but does not require any application code fault, memory corruption, or elevated access — an ordinary client sending crafted packed field data through a supported public parse API can trigger it.

### Recommendation
Change the overflow-handling policy for size-add operations that are reachable from wire-format parsing (`ReadPackedVarintArrayWithField`, `RepeatedField::Reserve`-adjacent call sites) so that overflow surfaces as a normal parse failure (`return nullptr;`/`false` propagated up through `ParseContext`) instead of `ABSL_LOG(FATAL)`/`abort()`. At minimum, add an explicit pre-check (`if (count > INT_MAX - out.size()) return nullptr;`) before invoking `CheckedAdd` in the packed-array parsing path in `src/google/protobuf/parse_context.h`, so that attacker-controlled sizes can never reach the fatal path, matching the pattern already used elsewhere in `ReadSizeFallback` (`src/google/protobuf/parse_context.cc:559-564`), which correctly rejects rather than aborts on out-of-range sizes.

### Proof of Concept
The exact reproduction already exists in-tree and demonstrates the crash:
```cpp
// src/google/protobuf/repeated_field_unittest.cc:281-295
proto2_unittest::RepFieldWithBoolForFastOverflow msg;
msg.mutable_b()->resize(10);
std::string str10 = msg.SerializeAsString();

EXPECT_DEATH(
    {
      msg.mutable_b()->resize(std::numeric_limits<int>::max() - 4);
      (void)msg.MergeFromString(str10);
    },
    HasSubstr("Integer overflow in CheckedAdd: "));
``` [3](#0-2) 

Here, `msg.mutable_b()` is first grown to `INT_MAX - 4` elements (simulating an application-level state reachable by repeated attacker-controlled merges), and then `MergeFromString(str10)` — an ordinary, public, bounded parse call containing a 10-element packed bool field — is sufficient to drive `out.size() + count` (`(INT_MAX - 4) + 10`) past `INT_MAX`, hitting `CheckedAdd`'s overflow branch in `port.h` and fatally aborting the process via `HandleAddOverflow` in `port.cc:185-187`, confirmed by the `EXPECT_DEATH` assertion matching `"Integer overflow in CheckedAdd: "`.
