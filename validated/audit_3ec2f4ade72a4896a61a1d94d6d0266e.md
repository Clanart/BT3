### Title
Untrusted `.gitmodules` combined with unconditional `protocol.file.allow=always` override allows submodule-driven local file read/exfiltration during checkout - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` accepts a boolean `allowFileProtocol` flag and, when true, unconditionally injects `-c protocol.file.allow=always` into the `git submodule update --init --recursive` invocation with no validation of the submodule URLs that will actually be processed under that override. [1](#0-0) 
This mirrors the report's "settings change without restriction/validation and immediately takes effect" pattern: a security-relevant Git setting (`protocol.file.allow`) is toggled globally for the whole submodule update command based only on a caller-supplied boolean, with no inspection of the `.gitmodules` content (which is attacker-controlled data coming from a fetched/checked-out branch) before the override is applied.

### Finding Description
`protocol.file.allow` is a Git safety control introduced specifically to stop an attacker who controls a repository's `.gitmodules` from pointing a submodule at an arbitrary local path via a `file://` URL (this is the fix for the well-known "submodule file protocol" abuse class). Git's default for this setting is `user` (deny in recursive/automated contexts), which is exactly the situation `git submodule update --init --recursive` runs in after a checkout.

In Desktop, `checkoutBranch` and `checkoutCommit` both accept an `allowFileProtocol` parameter that flows straight into `updateSubmodulesAfterOperation`, which re-enables the file protocol for that submodule-update invocation with no per-URL validation: [2](#0-1) [3](#0-2) 

The `branch.name` / `commit.sha` being checked out is attacker-influenced content whenever the user checks out a branch or commit that originated from a fetched remote (fork, PR branch, any remote a user adds). If the code path that decides to pass `allowFileProtocol = true` is reached for a checkout of a branch/commit fetched from an untrusted or third-party remote, Desktop will re-arm `protocol.file.allow` and let Git process whatever submodule URLs are declared in that branch's `.gitmodules` — including `file://` URLs — without any check on whether the target path is safe, inside the repo, or belongs to the user.

The broken invariant is: *a repository-controlled file (`.gitmodules`) determines which local filesystem paths get read/cloned into the working tree, while the guard meant to prevent this (`protocol.file.allow`) is being switched off by application logic based on a simple boolean rather than on the actual content of the submodule URLs.* This is structurally identical to the Sherlock finding: an administrative/security-relevant setting is toggled with "basically no validation against the new values," and the change (re-enabling file-protocol submodules) takes effect immediately for that operation.

### Impact Explanation
If `allowFileProtocol=true` is used for a checkout that ends up processing an attacker-supplied `.gitmodules` (e.g. checking out a branch from a collaborator's fork/PR, or a remote the user does not fully control), `git submodule update --init --recursive -c protocol.file.allow=always` will clone/copy the content at an attacker-chosen local `file://` path (e.g. `file:///home/user/.ssh`, `file:///Users/x/Library/...`, or any absolute path readable by the running user) into a submodule directory inside the repository. That content becomes part of the user's working tree and, if the user is not careful, gets staged/committed/pushed — i.e., local secrets or arbitrary files outside the repo get exfiltrated to whatever remote the repo is later pushed to. This satisfies the "attacker controls a cloned/fetched repository ... and the result is file read outside the repo / credential exfiltration / silent corruption of what the user commits or pushes" criteria.

### Likelihood Explanation
Exploitability depends entirely on whether any call site passes `allowFileProtocol = true` for a checkout whose target branch/commit is not fully trusted (e.g., checking out a PR/fork branch, or a commit reached via `git log`/compare from an untrusted remote). This is plausible in Desktop workflows where users routinely check out branches from forks and PRs. I was not able to fully trace, within the remaining search budget, every call site in `app-store.ts` / `dispatcher.ts` that sets `allowFileProtocol` to confirm whether it is ever `true` for such untrusted-origin checkouts versus only for locally created/trusted repositories — this is the key open question that determines real-world severity, and it should be verified against the current values passed at each of the ~8 usages in `app-store.ts` and 6 in `dispatcher.ts`.

### Recommendation
- Never toggle `protocol.file.allow` based on a coarse boolean tied only to the operation kind; instead validate each submodule URL discovered in `.gitmodules` before allowing `file://` resolution, and only allow it for URLs that resolve to paths already known to be safe (e.g., paths under the repository itself or a previously-approved allowlist).
- If `allowFileProtocol=true` is intended only for repositories the user has explicitly created/trusted locally, gate it on repository trust state (similar to `getRepositoryType` returning `unsafe`, or the existing `addSafeDirectory`/"Trust Repository" flow) rather than on the type of Git operation being performed.
- Audit every caller of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is never `true` when the target ref originates from a remote/fork/PR the user does not control.

### Proof of Concept
1. Attacker creates/controls a remote repository (or a fork/PR branch) containing a `.gitmodules` entry such as:
   ```
   [submodule "exfil"]
       path = exfil
       url = file:///Users/victim/.ssh
   ```
2. Victim adds the attacker's remote/fork in Desktop and checks out the malicious branch.
3. If the checkout path Desktop uses reaches `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true` (per `app/src/lib/git/checkout.ts` lines 102-146, 163-207), `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive` (`app/src/lib/git/submodule.ts` lines 45-51), causing Git to copy the contents of `/Users/victim/.ssh` into the `exfil/` submodule directory of the working tree.
4. If the victim stages and pushes the resulting change (or Desktop's own workflow surfaces the new files as part of the diff and the user commits them believing they're benign submodule content), the private key material is exfiltrated to whatever remote the push targets. [4](#0-3) [2](#0-1)

/**
 * Update submodules after a git operation.
 *
 * @param repository - The repository in which to update submodules
 * @param remote - The remote for environment setup (can be null)
 * @param progressCallback - An optional function which will be invoked
 *                           with information about the current progress
 *                           of the submodule update operation.
 * @param progressKind - The kind of progress event ('checkout', 'pull', etc.)
 * @param title - The title to use for progress reporting
 * @param targetOrRemote - The target (for checkout) or remote name (for pull)
 * @param allowFileProtocol - Whether to allow file:// protocol for submodules
 */
export async function updateSubmodulesAfterOperation<T extends Progress>(
  repository: Repository,
  remote: IRemote | null,
  progressCallback: ((progress: T) => void) | undefined,
  progressKind: T['kind'],
  title: string,
  targetOrRemote: string,
  allowFileProtocol: boolean
): Promise<void> {
  const opts: IGitStringExecutionOptions = {
    env: await envForRemoteOperation(
      getFallbackUrlForProxyResolve(repository, remote)
    ),
    expectedErrors: AuthenticationErrors,
  }

  const args = [
    ...(allowFileProtocol ? ['-c', 'protocol.file.allow=always'] : []),
    'submodule',
    'update',
    '--init',
    '--recursive',
  ]

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
