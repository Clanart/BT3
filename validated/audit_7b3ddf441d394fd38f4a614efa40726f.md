### Title
Relayer fee balance is zeroed on dispatch, not on confirmed destination payout — losable on execution failure - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`Pallet::withdraw` in the relayer pallet reads the relayer's accrued `Fees` balance, dispatches a cross-chain POST instructing the destination `HostManager`/module to pay that amount out, and **immediately zeroes the `Fees` entry** — before there is any confirmation that the destination-side transfer actually succeeded. This is the same broken invariant as the Derby `savedTotalUnderlying` bug: an accounting balance is decremented based on the *requested* payout, not the *realized* one.

### Finding Description
`Pallet::withdraw` (modules/pallets/relayer/src/withdrawal.rs, lines 81-187):

```rust
let available_amount = Fees::<T>::get(withdrawal_data.dest_chain, address.clone());
...
let post = DispatchPost { dest: withdrawal_data.dest_chain, from: MODULE_ID.to_vec(), to, body, timeout: 0 };
dispatcher.dispatch_request(DispatchRequest::Post(post), FeeMetadata { payer: [0u8;32].into(), fee: Default::default() })
    .map_err(|_| Error::<T>::DispatchFailed)?;

Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());
``` [1](#0-0) 

The pallet's own doc comment acknowledges this design: *"The `Fees` entry is zeroed so the same balance cannot be withdrawn twice... The on-chain effect is just dispatching the message; the destination chain settles the payout when the ISMP request is delivered there."* [2](#0-1) 

The `timeout: 0` on the `DispatchPost` means the request never times out and can never be refunded through the normal ISMP timeout-refund path — there is no mechanism for `Fees` to be re-credited if the destination-side transfer never lands or reverts. This is structurally identical to Derby Vault's `pullFunds()`: `savedTotalUnderlying -= amountToWithdraw` was executed *before* `withdrawFromProtocol()` confirmed the actual amount realized, so any shortfall between requested and realized silently and permanently corrupted the accounting state. Here, the corrupted value is the relayer's `Fees<T>(dest_chain, address)` entry: it is unconditionally set to zero on dispatch, with no re-credit path if:
- the destination `HostManager`/module `onAccept` handler reverts (e.g., insufficient fee-token balance in the manager's treasury, a beneficiary that rejects the transfer, or any other execution failure at delivery time), or
- the relaying of that specific POST request is abandoned/never completed.

### Impact Explanation
This falls squarely under the bounty's "stealing or loss of funds" category. A relayer's entire pending fee balance for a destination chain can be irrecoverably lost the moment `withdraw()` is called, if the destination-side settlement fails for any reason unrelated to the relayer (e.g., the `HostManager`/host-manager treasury on that chain is under-funded, paused, or the withdrawal message execution otherwise fails). Unlike the source-fee dispatch path (`dispatch_request` with normal timeouts, which pallet-ismp refunds on timeout per its own documentation: *"If the dispatched request times-out, then pallet-ismp's inner subsystems will refund the fees to the sponsor of the request"* [3](#0-2) ), this withdrawal-settlement POST is dispatched with `timeout: 0`, deliberately opting out of that refund mechanism, while simultaneously debiting the internal ledger unconditionally. The net effect mirrors the accepted Derby escalation: an accounting variable is decremented by the requested/dispatched amount rather than the amount actually realized by the counterparty operation, and there is no compensating re-credit path — this is a protocol-wide fund-loss bug rather than a cosmetic accounting drift, since the debited value is exactly the relayer's claimable balance (100% loss of that withdrawal, not just drift).

### Likelihood Explanation
No malicious actor, relayer misbehavior, or governance action is required — this triggers under ordinary operating conditions any time the destination-chain settlement fails after the request is dispatched (a normal, expected failure mode for cross-chain messaging: insufficient treasury float on the destination `HostManager`, transient reverts, or misconfiguration of `HostParams`). Any relayer calling the public, unsigned-but-authenticated `withdraw` extrinsic can trigger this path; it does not require any trust assumption on the prover/relayer/operator being honest — the bug is in the pallet's own bookkeeping order, independent of who initiates the withdrawal.

### Recommendation
Do not zero `Fees<T>` at dispatch time. Instead:
1. Move the balance to a "pending withdrawal" state keyed by the dispatch commitment (similar to how `outbound_request.rs`/`OutboundRequestsClaimed` tracks claims) rather than deleting it outright, or
2. Only zero/settle `Fees` once a delivery/execution receipt (or explicit confirmation) for that specific commitment is proven back to Hyperbridge, and
3. If the destination `onAccept` execution can fail, ensure the dispatch uses a real (non-zero) timeout so pallet-ismp's existing timeout-refund path can re-credit `Fees` on failure, or add an explicit reconciliation/refund extrinsic that credits back `Fees` when a `PostRequestTimeout`/failed-execution callback is observed for the withdrawal commitment.

### Proof of Concept
Conceptual trace (no live execution possible from this static analysis; the destination-side `HostManager` failure mode could not be directly exercised here — flagging as unverified execution but structurally supported by code):
1. Relayer accrues `Fees::<T>::get(EVM-X, relayer) = 1000` via `accumulate()`.
2. Relayer calls `withdraw(dest_chain = EVM-X)`. `available_amount = 1000` is read, a `DispatchPost` with `timeout: 0` is sent to `HostParams::<T>::get(EVM-X).host_manager` carrying `WithdrawalParams { beneficiary, amount: 1000, token: fee_token }` [4](#0-3) .
3. Immediately, `Fees::<T>::insert(EVM-X, relayer, U256::zero())` — the balance is gone from Hyperbridge's perspective regardless of what happens next [5](#0-4) .
4. On EVM-X, if the `HostManager`'s fee-token balance is insufficient to cover the transfer (e.g., treasury drained by prior withdrawals, before this one lands), or the beneficiary is a contract that reverts on receiving the token, the `onAccept` execution fails.
5. Because `timeout: 0` disables the ISMP timeout-refund mechanism, there is no compensating credit back to `Fees<T>`. The relayer's 1000 units are permanently lost with no recorded on-chain trail linking the failure back to a re-creditable balance.

I was unable to directly inspect the EVM `HostManager.onAccept`/`WithdrawalParams` handling logic within available context to confirm the exact failure modes possible on the destination side (e.g., whether the manager contract has a fallback or guaranteed-success invariant); this should be verified directly in `evm/src/core/HostManager.sol` before treating the destination-side failure trigger as unconditionally reachable. The core defect — `Fees` zeroed at dispatch time rather than at confirmed settlement, with `timeout: 0` precluding any refund — is directly supported by the cited pallet code regardless of that unverified detail.

		let available_amount = Fees::<T>::get(withdrawal_data.dest_chain, address.clone());

		if available_amount <
			Self::min_withdrawal_amount(withdrawal_data.dest_chain)
				.unwrap_or(MinWithdrawal::get())
		{
			Err(Error::<T>::NotEnoughBalance)?
		}

		let dispatcher = <T as Config>::IsmpHost::default();

		Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, |value| {
			*value += 1;
			Ok::<(), ()>(())
		})
		.map_err(|_| Error::<T>::ErrorCompletingCall)?;

		let beneficiary_address = withdrawal_data.beneficiary.clone().unwrap_or(address.clone());
		let (to, body) = match withdrawal_data.dest_chain {
			s if s.is_substrate() => (
				HYPERBRIDGE_MODULE_ID.to_vec(),
				Message::WithdrawRelayerFees(WithdrawalRequest {
					amount: available_amount.low_u128(),
					account: AccountId32::try_from(&beneficiary_address[..])
						.map_err(|_| Error::<T>::InvalidPublicKey)?,
				})
				.encode(),
			),
			_ => {
				let HostParam::EvmHostParam(params) =
					HostParams::<T>::get(withdrawal_data.dest_chain)
						.ok_or_else(|| Error::<T>::MissingMangerAddress)?;

				let body = WithdrawalParams {
					beneficiary_address: beneficiary_address.clone(),
					amount: available_amount.into(),
					token: params.fee_token,
				}
				.abi_encode()
				.map_err(|_| Error::<T>::InvalidPublicKey)?;

				(params.host_manager.0.to_vec(), body)
			},
		};

		let post = DispatchPost {
			dest: withdrawal_data.dest_chain,
			from: MODULE_ID.to_vec(),
			to,
			body,
			timeout: 0,
		};

		// Account is not useful in this case
		dispatcher
			.dispatch_request(
				DispatchRequest::Post(post),
				FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
			)
			.map_err(|_| Error::<T>::DispatchFailed)?;

		Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());
