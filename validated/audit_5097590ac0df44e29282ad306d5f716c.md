### Title
`ThresholdKeys::read` / `ThresholdKeys::new` accept attacker-controlled blobs without verifying the secret share matches the verification shares or that the shares interpolate to the claimed group key - (File: crypto/dkg/src/lib.rs)

### Summary

Analogous to the Chatwoot direct-upload bug — an unauthenticated endpoint instantiating arbitrary storage blobs without validating them — `ThresholdKeys::read` instantiates an arbitrary threshold-key object from untrusted bytes without performing the semantic consistency checks required for the object to be valid. `ThresholdKeys::new` only checks the *count* and *index range* of `verification_shares`; it never verifies that `secret_share * G == verification_shares[i]` nor that the resulting `group_key` (recomputed from the first `t` verification shares) corresponds to the secret material. The FROST code itself acknowledges this hole: `AlgorithmSignatureMachine::complete` returns `InternalError("everyone had a valid share yet the signature was still invalid")` with the comment "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:492-494). A crafted blob therefore creates a "key" that participates in scanning/crediting but produces shares that can never complete a valid signature — funds reported received that are not spendable.

### Finding Description

`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reads `t`, `n`, `i`, the interpolation mode, `secret_share`, and `n` verification shares directly from the reader, then calls `ThresholdKeys::new`. `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) performs only structural checks:

- `verification_shares.len() == n` and all participant indexes `<= n` (lines 355-365),
- `t == n` for `Interpolation::Constant` (lines 367-374),

then computes `group_key` by interpolating `verification_shares[1..=t]` (lines 376-378) and returns `Ok`. There is **no check** that `C::generator() * secret_share == verification_shares[i]` — the deserialized secret share can be completely unrelated to the verification share at index `i`, and unrelated to the derived `group_key`.

Similarly, `Commitments::read` in PedPoP (crypto/dkg/pedpop/src/lib.rs:109-128) reads `t` points and a Schnorr signature but defers all semantic validation to the caller's `secret_share_machines`/context verification — but the `ThresholdKeys` case is the stronger analog since `read` itself returns a fully-formed, self-describing key object consumed by signing machines.

### Impact Explanation

An attacker who can feed crafted bytes into `ThresholdKeys::read` (deserialization is listed as an untrusted-input surface: any store/restore path of serialized `FrostKeys`) produces a `ThresholdKeys` where:

1. `secret_share` is arbitrary. When the node signs, `sign` produces a share `s_i = d_i + ρ_i·e_i·λ_i·secret_share` which will not verify against `verification_share(i)`, causing `FrostError::InvalidShare(i)` under the blame path — or, because `complete` first tries the aggregate signature, it produces `InternalError`. Worse, with `Interpolation::Constant` (t == n), an attacker can craft verification shares so that `group_key` equals a key *they* control the aggregate secret of, while honest verification shares for other indexes pass the count check — any participant loading this blob reports `group_key()` as its wallet key. Outputs scanned/credited to that `group_key` are then only spendable if the fabricated shares are actually consistent; if the attacker set `verification_shares` for other indexes inconsistently with real secret shares, the threshold can never sign, bricking the credited funds — while `group_key()` still reports a normal-looking address.

2. Because `ThresholdKeys::new` interpolates the group key from `verification_shares[1..=t]`, two different serialized blobs can yield identical `group_key` values with different `secret_share`/`i` bindings, enabling a blob-swap that silently misattributes a participant's share index (`i` is only range-checked, not bound to `verification_shares[i]`).

This is a Medium-severity integrity failure: arbitrary unvalidated object creation resulting in unspendable funds being reported as received, or in persistent signing failure/misblame, reachable purely by feeding crafted bytes to `read`.

### Likelihood Explanation

Exploitation requires an attacker to control the serialized bytes passed to `ThresholdKeys::read`. This matches the report's threat model (untrusted bytes to `ThresholdKeys::read` are explicitly in scope). Any integration that imports key material from backups, peer-synced state, or operator-supplied files — rather than only from a locally executed DKG — exposes this path. It requires no secret knowledge and no collusion; the attacker simply writes canonical-but-inconsistent encodings (all `read_F`/`read_G` calls succeed since each element is individually canonical). Once loaded, every downstream user (`ThresholdView::multisig`, `AlgorithmMachine::new`, `Scanner`/wallet code trusting `group_key()`) operates on the inconsistent object without re-validation.

### Recommendation

In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify:

1. `C::generator() * *secret_share == verification_shares[&params.i()]` — the secret share must correspond to the verification share at the claimed index.
2. For `Interpolation::Constant` (MuSig-style), recompute the binding factors or at least ensure `interpolation` length equals `n` and shares are mutually consistent; for `Lagrange`, optionally verify that interpolating all `n` verification shares is consistent with a degree `< t` polynomial (already implied by structure, but the `secret_share` check above is the critical one).
3. Reject `secret_share == 0` and identity verification shares (FROST's `Curve::read_G` already rejects identity, but `ThresholdKeys::read` uses `Ciphersuite::read_G`, which does not).

### Proof of Concept

```rust
// crypto/dkg — craft a ThresholdKeys blob for Ristretto where
// secret_share does NOT match verification_shares[i].
use dkg::{ThresholdKeys, Participant, ThresholdParams, Interpolation};
use ciphersuite::{Ciphersuite, group::{GroupEncoding, ff::{Field, PrimeField}}};
use dalek_ff_group::{Ristretto, Scalar};
use zeroize::Zeroizing;
use rand_core::OsRng;

let t: u16 = 2; let n: u16 = 3; let i: u16 = 1;
let real = Scalar::random(&mut OsRng);
let forged = Scalar::random(&mut OsRng);           // != real

let mut blob = vec![];
blob.extend(9u32.to_le_bytes());                    // len("ristretto")
blob.extend(b"ristretto");
blob.extend(t.to_le_bytes());
blob.extend(n.to_le_bytes());
blob.extend(i.to_le_bytes());
blob.push(1);                                       // Lagrange
blob.extend(forged.to_repr().as_ref());             // attacker-chosen secret_share
for l in 1 ..= n {                                  // honest shares for a DIFFERENT key
  let share = Scalar::random(&mut OsRng);
  blob.extend((Ristretto::generator() * share).to_bytes().as_ref());
}

// Succeeds: no secret_share <-> verification_shares[i] consistency check,
// so group_key() reports a key whose credited funds this node can never sign for.
let keys = ThresholdKeys::<Ristretto>::read(&mut blob.as_slice()).unwrap();
assert_ne!(
  Ristretto::generator() * *keys.original_secret_share(),
  keys.original_verification_share(Participant::new(i).unwrap()),
);
// FROST signing with these keys hits the acknowledged unreachable state:
// FrostError::InternalError("everyone had a valid share yet the signature was
// still invalid") — crypto/frost/src/sign.rs:492-494.
```
