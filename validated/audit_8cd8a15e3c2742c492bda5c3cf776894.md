### Title
`_cancelFromDest` Can Overwrite an Already-Filled Order and Redirect Escrow to the User Before the Solver's `RedeemEscrow` Settles - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`_cancelFromDest` never checks the `_filled[commitment]` flag before finalizing a cancellation, so an unprivileged caller can trigger a duplicate settlement path that races the solver's legitimate `RedeemEscrow` message and redirects escrowed input tokens to the user instead of the solver who already delivered the outputs.

### Finding Description
This mirrors the reported pattern exactly: a one-time settlement action is protected only by an incidental, insufficient guard (here, a deadline check gating *who* may call) instead of checking the actual state invariant that should block the action (whether the order is *already filled*).

`_fillCrossChain` marks an order filled on the destination chain and dispatches a `RedeemEscrow` message to the source chain to pay the solver: [1](#0-0) 

`_cancelFromDest`, also destination-side, is reachable by anyone once `order.deadline < _blockNumber()`: [2](#0-1) 

Note the guard: `if (order.deadline >= _blockNumber()) { require msg.sender == order.user }`. After the deadline it is a no-op check — *anyone* can call it. Crucially, the function never checks `_filled[commitment] != address(0)` before unconditionally writing `_filled[commitment] = order.user` and dispatching a `RefundEscrow` message to the source chain — exactly the same class of omission as `executeMigration()` checking `migrationTime`/`successMigrated` instead of the actual vote-quorum invariant.

On the source chain, both `RedeemEscrow` and `RefundEscrow` funnel through the same `onAccept` → `_withdraw` path with `finalize = true`: [3](#0-2) [4](#0-3) 

`_withdraw` only guards against *replay* on the same commitment (via `_orders[...] == 0` reverting `UnknownOrder`), it does not care about *which* message (redeem vs. refund) arrives first and finalizes the beneficiary.

### Impact Explanation
If a solver fills a cross-chain order near its deadline, the destination-side `_fillCrossChain` immediately marks `_filled[commitment] = solver` and delivers real output tokens to the beneficiary, but the corresponding `RedeemEscrow` message to the source chain must still clear the ISMP proof/challenge-period pipeline before the solver is paid from escrow. During that window, since `_cancelFromDest` performs no `_filled` check, any unprivileged address can call `cancelOrder` (destination) once `deadline` has elapsed, overwriting `_filled[commitment]` to `order.user` and racing a `RefundEscrow` message to the source chain. If `RefundEscrow` reaches the source chain and finalizes before `RedeemEscrow`, the escrowed input tokens are paid to the original user instead of the solver — even though the solver already delivered the agreed outputs. This is a direct "wrong beneficiary" fund-diversion outcome: the solver's compensation is stolen/lost, matching the bounty's "unauthorized transaction/wrong beneficiary or amount" impact class.

### Likelihood Explanation
No malicious relayer, prover, or admin is required — only ordinary cross-chain message latency (source-chain challenge period / proof availability) combined with a fill occurring close to `order.deadline`. Both `_cancelFromDest` and the resulting `RefundEscrow` dispatch are public/unsigned-caller-reachable once the deadline passes, so any address, including the user themselves, can deliberately trigger this race by filling right at the deadline boundary or delaying relay of `RedeemEscrow` while pushing `RefundEscrow` through faster (e.g., paying a higher relayer fee on the refund path). This is a realistic, unprivileged, reproducible race rather than a theoretical timing coincidence.

### Recommendation
In `_cancelFromDest` (and symmetrically wherever a finalize-type settlement is triggered), reject the action if `_filled[commitment] != address(0)`:
```solidity
function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
    if (_filled[commitment] != address(0)) revert Filled();
    if (order.deadline >= _blockNumber()) {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
    }
    ...
}
```
This makes the "already filled" invariant an explicit precondition rather than relying solely on the deadline/caller check, consistent with how `_cancelFromSource`'s GET-proof path already independently verifies non-fill state before refunding.

### Proof of Concept
1. User places a cross-chain `Order` with `deadline = D`.
2. Solver calls `fillOrder` at block `D-1`: `_fillCrossChain` sets `_filled[commitment] = solver`, sends real output tokens to beneficiary, and dispatches `RedeemEscrow` to the source chain (pending relayer delivery through the source chain's challenge period).
3. At block `D+1` (deadline passed), an unrelated address calls `cancelOrder` on the destination chain. `_cancelFromDest` executes with no authorization restriction (deadline has passed) and, without checking `_filled[commitment]` is already `solver`, overwrites it to `order.user` and dispatches `RefundEscrow` to the source chain.
4. If the `RefundEscrow` message clears the source chain's proof/challenge period before the earlier `RedeemEscrow` message does, `onAccept` → `_withdraw(body, true, true)` releases the escrowed input tokens to `order.user`.
5. When `RedeemEscrow` subsequently arrives, `_withdraw` reverts with `UnknownOrder` (escrow already zeroed) — the solver, having already paid out real tokens on the destination chain, never receives their escrowed compensation on the source chain.

**Note:** I could not locate the top-level `IntentGatewayV2.sol` `cancelOrder`/`fillOrder` public entry points that route to `_cancelFromDest`/`_fillCrossChain` (only `ExtrinsicIntents.sol`/`IntentsBase.sol`/`IntrinsicIntents.sol` were retrievable), so I could not fully confirm whether an additional `_filled` guard exists at a higher call layer that might already mitigate this. If such a layer exists, the earlier `_filled[commitment] = solver` write inside `_fillCrossChain` would still need to be checked in `_cancelFromDest` specifically, since that function is the one that lacks the check as shown above.

            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
