### Title
Permanent freezing of user funds via griefing of predictable, unowned IBC-callback isolated addresses - (File: x/ibc/callbacks/keeper/keeper.go, x/ibc/callbacks/types/keys.go)

### Summary
The external report describes a DOS where an attacker precomputes the address of a future `CREATE`-based facilitator contract and pre-fills it with 1024 NFTs, so that when the real facilitator is deployed it cannot receive its token and the whole flow reverts. The structural pattern — a helper address whose value is fully deterministic/predictable ahead of time, used transiently to hold value, and which the protocol assumes will always be "empty" when it matters — has a direct analog in this repo's `x/ibc/callbacks` module: the "isolated address" used to receive ERC20/IBC funds during a destination-chain callback.

### Finding Description
`GenerateIsolatedAddress` derives the isolated receiver deterministically and, critically, *only* from `channelID` and `sender` (the packet's sender string, which is attacker-controlled since it originates on the counterparty chain): [1](#0-0) 

This address has no private key ("no user has the ability to sign messages on behalf of this account") and is reused as the receiver for *every* callback-based IBC transfer from that same `(channelID, sender)` pair, as documented: [2](#0-1) 

In `IBCReceivePacketCallback`, the ERC20 balance is minted/escrow-released to this isolated address (outside the function, by the base transfer app, before the callback runs), then the callback: sets `approve` for the destination contract, invokes the contract, commits the cached context (`writeFn()`), and only *afterward* checks that the isolated address's ERC20 balance is exactly zero: [3](#0-2) 

Because `writeFn()` is called before this balance check, any state changes from the callback execution are already committed by the time the "no leftover balance" invariant is checked. Since the isolated address is a plain, predictable module-derived account with no signer, any residual ERC20 balance left there — whether from (a) a legitimate contract's `transferFrom` pulling less than the full packet amount, or (b) an unrelated third party directly IBC-transferring (or otherwise causing an ERC20 mint/credit of) the same denom to that address ahead of time, since the address is fully computable off-chain by anyone who knows `channelID`/`sender` — becomes **permanently unrecoverable**. There is no mechanism to sweep, retry-drain, or reassign balances stuck at an isolated address.

The mint of tokens to the isolated address happens as part of the base ICS-20 `OnRecvPacket` transfer logic prior to callback execution (per the callbacks middleware's async design, callback failures are not expected to roll back the already-successful transfer ack). This means once `IBCReceivePacketCallback` returns an error (e.g., due to the nonzero-balance check), the underlying token transfer to the isolated address has already been finalized outside the cached context used for the EVM call — leaving genuine user funds stuck at an address nobody controls.

### Impact Explanation
This satisfies the "Critical permanent freezing/locking of user funds ... escrowed assets ... token-pair-backed balances" impact class:
- Any address that knows a victim's `(channelID, sender)` pair (fully public/derivable, no secret involved — directly analogous to the report's precomputed facilitator address) can pre-poison the isolated address with a small amount of the same denom.
- Every subsequent legitimate callback-based transfer from that `(channelID, sender)` will mint additional funds to the same poisoned address; the destination contract's `transferFrom` can only ever pull the *current* packet's amount (not the pre-existing dust), so the residual-balance check at [4](#0-3)  will perpetually fail for that route, while the minted principal for that packet remains stranded at the same unowned address forever.
- Because the isolated address has no private key, none of the locked funds (attacker's dust nor victim's legitimate transferred principal) can ever be retrieved — an irreversible, unbounded-value freeze reachable by an ordinary, unprivileged IBC transfer.

### Likelihood Explanation
The address derivation function takes no per-packet randomness/nonce (no sequence number, no salt) — only `channelID` and `sender` — so it is trivially predictable by any observer, exactly like the CREATE-based facilitator address in the source report. The attack requires only sending a standard IBC transfer (no calldata/callback needed) with `receiver = isolatedAddr` for a chosen victim `(channel, sender)` pair, which is a normal, unprivileged, always-available transaction. No special access, timing races beyond "before the victim's next callback transfer," or validator/relayer collusion is required.

### Recommendation
- Include a per-packet unique component (e.g., packet sequence number, or a value derived from packet content/timeout) in the isolated-address derivation so that each callback packet gets its own single-use receiving address rather than reusing one shared, permanently predictable address per sender/channel.
- Alternatively/additionally, add a recovery/sweep path allowing the original packet sender (or a governance-gated admin) to redeem any residual balance stranded at an isolated address, rather than relying purely on the destination contract behaving correctly to keep the balance exactly zero.
- Ensure the "no leftover balance" invariant check happens (or its consequences are reconciled) atomically with the underlying mint/escrow-release, so a failing callback cannot leave real user funds committed to a state that the module itself considers unrecoverable.

### Proof of Concept
1. Attacker learns a target user's planned IBC callback route: `channelID = "channel-X"`, `sender = "cosmos1victim..."` (this is public/derivable off-chain the same way a CREATE address is; no privileged data needed).
2. Attacker computes `isolatedAddr = GenerateIsolatedAddress("channel-X", "cosmos1victim...")` using the same public logic as [1](#0-0) .
3. Attacker sends an ordinary ICS-20 transfer (no memo/callback needed) of a small amount of the same denom the victim intends to use, with `receiver = isolatedAddr`. This mints ERC20/native balance to `isolatedAddr` with no owner able to move it.
4. Victim later sends a legitimate callback-based transfer through `channel-X` from `cosmos1victim...`. The packet is validated as coming from the correct isolated address (`receiverHex == isolatedAddrHex`) per [5](#0-4) , funds are minted to `isolatedAddr`, and the contract's `transferFrom` pulls only the current packet's `amountInt`.
5. The post-check at [4](#0-3)  finds the attacker's leftover dust balance still present and returns `ErrEVMCall`, but the mint to `isolatedAddr` from step 4 has already been committed by the base transfer app prior to the callback — the victim's funds are now stuck alongside the attacker's dust at an address with no private key, permanently unrecoverable, and this repeats for every future attempt on that route.

Note: I was unable to fully trace, within the available index, the exact code path of the outer ibc-go/erc20 `OnRecvPacket`/callbacks-middleware wiring (`x/erc20/ibc_middleware.go`, `ibc/module.go`) that determines whether a callback error is allowed to roll back the preceding mint — file reads for those specific files failed due to a tool error on the final iteration. This is the one assumption in the analysis (that callback failure does not revert the already-completed transfer mint, consistent with ibc-go's documented async-callback design and with the explicit code comment "this check is here to prevent funds from getting stuck ... since they would become irretrievable"). Confirming this control-flow detail in those two files would be the first step to fully validate or refute the Critical severity before further action.

## Limitations

The receiver side callback **must** receive funds to an ephemeral address generated from the channelId and packet
sender address. Note that since this is a generated address, no user has the ability to sign messages on behalf of
this account even though it is a cross-chain representation of the packet sender.

Thus, a contract that receives the funds and calldata from the isolated receiver address **must** send the tokens
onwards to a desired address that is specified in the calldata. If tokens are deposited back into the isolated address,
they are unreachabe. If you wish to interact with a contract that does not implement functionality for sending the
tokens to a different address then you must interact with that contract through some wrapper contract interface that
can receive the funds, call the contract which deposits funds back to `msg.sender` and then the wrapper contract
can move the funds to a final desired address.
