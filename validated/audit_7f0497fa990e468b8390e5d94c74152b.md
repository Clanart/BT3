### Title
Out-of-range `Participant` index in a blame accusation panics `BlameMachine`/`AdditionalBlameMachine` — (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The buffer over-read class of CVE-2018-18827 (a crafted input driving an out-of-bounds access and denial of service) maps onto Serai as an unchecked HashMap index on an attacker-controlled `Participant` index. `BlameMachine::blame` and `AdditionalBlameMachine::blame` accept arbitrary `sender`/`recipient` `Participant` values plus an attacker-supplied `EncryptedMessage`, and index `self.commitments[&sender]` without validating that `sender` was ever registered. An unprivileged party who can submit a blame accusation (or any integrator evaluating blame over network-supplied bytes) can crash the host.

### Finding Description
`AdditionalBlameMachine::new` only registers `enc_keys`/`commitments` for participants `1..=n` (crypto/dkg/pedpop/src/lib.rs, `for i in 1 ..= n`). `blame()` forwards the caller-supplied `sender` and `recipient` to `blame_internal` with no range check:

- `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`, which only binds `sender` into the PoP challenge — it never checks `sender`/`recipient` against the registered set. `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` directly (crypto/dkg/pedpop/src/encryption.rs), panicking if `recipient` is not `1..=n`.
- If decryption succeeds, `blame_internal` evaluates `share_verification_statements(recipient, &self.commitments[&sender], ...)` — a direct `HashMap` index on `sender` that panics for any `sender` outside `1..=n` (crypto/dkg/pedpop/src/lib.rs, blame_internal → `self.commitments[&sender]`).

The PoP signature is over a challenge that *includes* `sender` but is self-signed by whoever created `msg` (`pop_challenge`/`SchnorrSignature::sign` over a fresh key in `encrypt`, crypto/dkg/pedpop/src/encryption.rs). An accuser can therefore fabricate an `EncryptedMessage` whose PoP verifies under any claimed `from` index, including `Participant::new(n + 1)`, and supply a valid `EncryptionKeyProof` for their own registered encryption key so decryption succeeds and execution reaches the panicking index.

### Impact Explanation
A single crafted blame evaluation aborts the process via a panic (`HashMap` indexing of a missing key). In deployments where blame is adjudicated on-chain/processor-side (e.g., `VerifyBlame` handling deserializing an `EncryptedMessage` and an `EncryptionKeyProof` from the accusation and calling `AdditionalBlameMachine::blame`), an unprivileged accuser controls `accused`/`sender` and the message bytes, giving a reliable remote denial of service against the node evaluating blame — the analog of the Libav crash on a crafted file.

### Likelihood Explanation
Any participant able to file an accusation, or any caller feeding unauthenticated `sender`/`recipient`/`msg`/`proof` into `AdditionalBlameMachine::blame`, triggers it deterministically. No threshold cooperation, no valid share, and no honest participant is required; the attacker only needs a self-consistent `EncryptedMessage` + `EncryptionKeyProof`, both producible from knowledge of their own encryption key.

### Recommendation
Validate `sender` and `recipient` against the registered participant set at the top of `blame`/`blame_internal` (e.g., `self.commitments.contains_key(&sender)`, `self.encryption.enc_keys.contains_key(&recipient)`) and return the accuser/caller as faulty or a dedicated `PedPoPError` instead of indexing. Replace `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with checked `.get()` lookups returning errors.

### Proof of Concept
```rust
// DKG with n participants completed; build an AdditionalBlameMachine as a
// third-party observer would (crypto/dkg/pedpop/src/lib.rs).
let mut blame = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();

// Attacker crafts a message whose PoP claims to be from a non-existent participant.
let fake_sender = Participant::new(n + 1).unwrap(); // valid Participant, not in 1..=n
// encrypt() signs pop_challenge(context, pub_nonce, pub_key, fake_sender, msg)
// with the attacker's freshly chosen key, so the PoP verifies under `from = fake_sender`.
let msg: EncryptedMessage<Ristretto, SecretShare<F>> = /* attacker-constructed, PoP valid for fake_sender */;

// Accuser (a real participant) supplies a proof for their own enc key so
// decrypt_with_proof passes the DLEq and returns the decrypted bytes.
let proof: EncryptionKeyProof<Ristretto> = /* valid proof binding accuser's enc key to msg.key */;

// Panics at `self.commitments[&sender]` (index into map keyed only over 1..=n).
let _faulty = blame.blame(fake_sender, accuser, msg, Some(proof));
```
