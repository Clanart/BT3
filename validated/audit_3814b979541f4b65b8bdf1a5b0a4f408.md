### Title
Staleness gate silently disabled for future-dated oracle timestamps, allowing stale prices to be treated as fresh - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The freshness check used by every oracle price resolution in the market contract clamps the staleness delta to `u0` whenever the reported feed timestamp is greater than the current `stacks-block-time`, instead of rejecting or bounding that case. This mirrors the CVE-2025-4947 bug class: a validation step is unconditionally skipped whenever a specific input condition holds (there, `peer->sni` being null; here, `ts > stacks-block-time`), letting a value that should be checked slip through unauthenticated.

### Finding Description
`oracle-timestamp-fresh` computes the staleness delta as: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

When the feed's reported `publish-time` (`ts`) is greater than the current block's `stacks-block-time`, `delta` is forced to `u0`. Since `u0 <= max-staleness` is always true, the `<= delta max-staleness` staleness bound is unconditionally satisfied regardless of how far in the future `ts` actually is, and the only remaining requirement is `ts >= prev` (a monotonic check that a strictly increasing sequence of future timestamps trivially satisfies). This is the same identical logic present in the non-mainnet copy of the contract: [2](#0-1) .

This value feeds directly into `price-resolve`, which is the sole gate protecting every price used by the market: [3](#0-2) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let (...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

`price-resolve`/`price-multi-resolve` back `get-assets`, which supplies collateral/debt prices to `get-notional-evaluation` used for borrow limit, health, and liquidation checks: [4](#0-3) .

The root cause is that "clock skew ahead" is treated as "not stale" instead of being independently bounded or rejected. Any legitimate condition where a feed's `publish-time` sits ahead of the market's `stacks-block-time` (e.g. normal clock/consensus-time differences between Pythnet and the Stacks chain, or `stacks-block-time` lagging behind wall-clock at the moment a transaction executes) causes the `max-staleness` bound to be bypassed entirely for that price for as long as `ts` remains ahead of `stacks-block-time`. During that window the price is accepted as "fresh" no matter how old the actual off-chain quote is, defeating the per-asset `max-staleness` gate documented as the primary staleness safety feature.

### Impact Explanation
Bypassing the staleness gate lets outdated/incorrect prices be used to compute collateral and debt notional values for borrowing, health checks, and liquidation. A user can borrow against, or avoid liquidation on, a position priced with a favorable stale value while the market believes the check passed, or conversely a liquidator/borrower can be unfairly liquidated/blocked using a stale unfavorable price — leading to under-collateralized debt, incorrect liquidations, and potential protocol insolvency (bad debt) once real prices are reconciled. This lands in the Critical bucket (protocol insolvency / theft of funds via mispriced borrowing) since it is a wrong health verdict driven by a staleness-gating bug in this code, not by malicious third-party oracle data.

### Likelihood Explanation
No attacker control of Pyth/DIA data is required — the trigger condition (`ts > stacks-block-time`) can occur through ordinary operation whenever the externally reported publish time is even slightly ahead of the Stacks block timestamp sampled during contract execution, which is plausible given cross-chain clock differences and block-production timing on Stacks. The bug is deterministic and reachable on every price resolution call, making it a systemic rather than edge-case weakness.

### Recommendation
Do not zero out `delta` when `ts > stacks-block-time`. Either reject timestamps that are ahead of the current block time (treat as invalid until the block time catches up), or compute delta as `abs(stacks-block-time - ts)` and still bound it by `max-staleness`, ensuring future-dated timestamps cannot bypass the staleness requirement.

### Proof of Concept
1. Oracle feed publishes (or naturally reports, due to clock difference) a price with `publish-time = T_future`, where `T_future` is even slightly greater than the current `stacks-block-time` at call time.
2. `resolve-pyth`/`resolve-dia` return `{ value: price, timestamp: T_future }` (`mainnet/contracts/market/v0-4-market.clar` lines 312-330).
3. `price-resolve` calls `oracle-timestamp-fresh(T_future, last-update-time, max-staleness)`; because `T_future > stacks-block-time`, `delta` is forced to `u0`, satisfying `<= delta max-staleness` regardless of the true staleness of the quote, and `T_future >= last-update-time` is trivially true.
4. The price is accepted (`ok final-price`) and used unchanged by `get-notional-evaluation` for borrow/health/liquidation math until real chain time eventually passes `T_future`, at which point the staleness math becomes correct again — but any borrow/liquidation actions taken during the bypass window are already settled on-chain with the unchecked price.

  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))

        (key { type: type, ident: ident })

        (timestamp (get timestamp resolution))

              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)

    (ok final-price)))
