### Title
SignableTransaction underpays its fee because `calculate_weight_vbytes` omits the OP_RETURN data output - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to `msg.value` not being synchronized with `_volume`, `SignableTransaction::new` computes `needed_fee` (and the standardness weight check) from a transaction shape that excludes the `OP_RETURN` data output it actually appends. The declared/committed fee rate is therefore desynchronized from the transaction's real virtual size.

### Finding Description
`SignableTransaction::new` pushes an `OP_RETURN` output into `tx_outs` when `data` is supplied:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}
```

but then estimates weight/vbytes using only `payments` (and later `change`), never the data output:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
...
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
```

`calculate_weight_vbytes` builds its template transaction exclusively from `payments` plus an optional change output; the `OP_RETURN` output (up to 80 bytes of data plus script overhead) is absent. Two desynchronized values result:

1. `needed_fee = fee_per_vbyte * vbytes` is lower than `fee_per_vbyte * actual_vsize`. The signed transaction's *effective* fee rate is below the rate the caller requested and below what `needed_fee()` reports.
2. The minimum-relay-fee guard `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` can pass for the underestimated `vbytes` while failing for the real transaction, so the produced, fully-signed transaction can be rejected by node mempool policy (`bad-txns-*`/too-low-fee) — the inputs it commits are then unspendable until a new signing round is performed.
3. The `weight > MAX_STANDARD_TX_WEIGHT` standardness check is likewise evaluated on the lighter template, slightly weakening the too-large guard when `data` is present.

### Impact Explanation
A transaction constructed with `data` pays a lower sat/vbyte rate than intended and may be built such that it fails the minimum relay fee or skates under the weight check on the wrong size. The output is a valid-looking, fully signed transaction that nodes will not relay/confirm — funds in the committed `prevouts` are reported as moved but the transaction is not usable, mirroring the original report's "funds committed but value accounting desynchronized" failure mode.

### Likelihood Explanation
Deterministic whenever `SignableTransaction::new` is invoked with `Some(data)` — the OP_RETURN output is unconditionally excluded from both `calculate_weight_vbytes` calls. Whether the fee ends up below relay minimum depends on `fee_per_vbyte` and the payments/change size, but the effective fee rate is always lower than declared.

### Recommendation
Include the data output in the template used by `calculate_weight_vbytes` (e.g., pass the finalized `tx_outs` or an `Option<&ScriptBuf>` for the OP_RETURN script) so `needed_fee`, the min-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction actually signed.

### Proof of Concept
Construct two `SignableTransaction`s identical except `data = Some(vec![0; 80])` vs `None`. `tx.fee()` / `needed_fee()` are equal, yet `tx.transaction().vsize()` for the `data` variant is ~90+ vbytes larger, so its real sat/vbyte rate is strictly below `fee_per_vbyte`, and with `fee_per_vbyte` chosen at the minimum relay boundary the `data` variant's effective rate falls under `DEFAULT_MIN_RELAY_TX_FEE`.
