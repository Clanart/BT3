### Title
Unchecked nil `*ethtypes.Transaction` from `AsTransaction()` causes RPC-node crash on decode failure - (File: evmrpc/utils.go)

### Summary
`MsgEVMTransaction.AsTransaction()` returns `(nil, nil)` whenever `UnpackTxData` fails to decode the packed `ethtx.TxData` `Any`, but at least one caller in the public JSON-RPC path dereferences the returned `*ethtypes.Transaction` immediately, without a nil check, causing a nil-pointer dereference panic — the same bug class as CVE-2018-18227 (dissector returns NULL/failure, caller doesn't check before dereferencing).

### Finding Description
`MsgEVMTransaction.AsTransaction()` unpacks `msg.Data` via `UnpackTxData` and, on error, explicitly returns `nil, nil`: [1](#0-0) 

In `evmrpc/utils.go`, `filterTransactions` (used to build block/transaction-count views served over the EVM JSON-RPC surface) calls `AsTransaction()` and immediately calls `.Hash()` and `.Nonce()` on the result without checking whether the returned pointer is nil: [2](#0-1) 

The companion helper `getTxHashesFromBlock` has the identical unchecked-dereference pattern: [3](#0-2) 

These functions iterate over transactions already included in a committed block, decoding each `MsgEVMTransaction`'s packed `Data` field again via `txConfig.TxDecoder()` and `AsTransaction()`. `UnpackTxData` itself only errors when the raw bytes fail proto.Unmarshal for every known `ethtx.TxData` variant (`LegacyTx`, `AccessListTx`, `DynamicFeeTx`, `BlobTx`, `AssociateTx`, `SetCodeTx`): [4](#0-3) 

Because `ValidateBasic()` on `MsgEVMTransaction` already calls `UnpackTxData` and would reject an undecodable payload at the mempool/ante stage, the practical path to trigger the nil-dereference is narrow: it requires a scenario where a transaction was accepted into a block (e.g., before a hard-fork removed a tx-type registration, an admission-check bypass, or an upgrade that changes decodability of a previously-valid encoding) but subsequently fails to decode when `filterTransactions`/`getTxHashesFromBlock` re-parses historical blocks for RPC queries such as `eth_getBlockByNumber`/`eth_getBlockTransactionCountByNumber`. In that scenario, unlike the Wireshark dissector case (attacker-crafted packet crashing the parser directly), the reachable crash surface here is a re-decode failure on stored/committed data, not a directly attacker-controlled payload — the code paths that would decode a freshly-submitted raw transaction (`eth_sendRawTransaction`, ante/mempool) already validate before acceptance.

### Impact Explanation
If triggered, the panic occurs inside RPC-serving goroutines (`filterTransactions`/`getTxHashesFromBlock`), which are invoked from public `eth_getBlock*` handlers. A crash here would deny block/transaction-count queries; whether it crashes the whole RPC server or is caught by a top-level recover in the RPC handler chain was not conclusively verified from the code inspected. No fund loss, supply change, or consensus-halting effect was identified — the risk is limited to node/RPC-availability degradation, contingent on an already-narrow trigger condition (a `MsgEVMTransaction` that passed `ValidateBasic` but later fails `UnpackTxData` on re-decode).

### Likelihood Explanation
Low. `ValidateBasic()` already calls `UnpackTxData` and rejects a `MsgEVMTransaction` whose `Data` cannot be unpacked into any known `ethtx.TxData` variant before it can enter a block, so an unprivileged sender cannot get an undecodable payload committed in the first place under normal operation. The vulnerable code paths only run against already-committed data during RPC-driven block replay, so a directly attacker-triggerable crash comparable to the Wireshark dissector scenario was not established with confidence.

### Recommendation
Add explicit nil checks after every `AsTransaction()` call in `evmrpc/utils.go` (`filterTransactions`, `getTxHashesFromBlock`) and skip/log the transaction instead of dereferencing, matching the defensive pattern already used elsewhere in the codebase (e.g., the nil checks in `sei-tendermint/node/fast_check_tx.go` after `msg.AsTransaction()`): [5](#0-4) 

### Proof of Concept
A conclusive, directly attacker-triggerable PoC could not be constructed from the indexed code: reaching the nil-dereference in `evmrpc/utils.go` requires a `MsgEVMTransaction` that is committed to a block despite `UnpackTxData` failing on it, and `ValidateBasic()` normally prevents that. This finding should be treated as a defensive-coding gap (missing nil check mirroring the CVE's "unhandled NULL return" root cause) rather than a proven, directly exploitable crash; a background engineering session with the ability to run the code and fuzz/replay block data would be needed to determine whether any legitimate flow can produce a `MsgEVMTransaction` in a block that fails `UnpackTxData` on re-decode.

func UnpackTxData(any *codectypes.Any) (ethtx.TxData, error) {
	if any == nil {
		return nil, errors.New("protobuf Any message cannot be nil")
	}

	txData, ok := any.GetCachedValue().(ethtx.TxData)
	if !ok {
		ltx := ethtx.LegacyTx{}
		if proto.Unmarshal(any.Value, &ltx) == nil {
			// value is a legacy tx
			return &ltx, nil
		}
		atx := ethtx.AccessListTx{}
		if proto.Unmarshal(any.Value, &atx) == nil {
			// value is a accesslist tx
			return &atx, nil
		}
		dtx := ethtx.DynamicFeeTx{}
		if proto.Unmarshal(any.Value, &dtx) == nil {
			// value is a dynamic fee tx
			return &dtx, nil
		}
		btx := ethtx.BlobTx{}
		if proto.Unmarshal(any.Value, &btx) == nil {
			// value is a blob tx
			return &btx, nil
		}
		astx := ethtx.AssociateTx{}
		if proto.Unmarshal(any.Value, &astx) == nil {
			// value is an associate tx
			return &astx, nil
		}
		stx := ethtx.SetCodeTx{}
		if proto.Unmarshal(any.Value, &stx) == nil {
			// value is a set code tx
			return &stx, nil
		}
		return nil, fmt.Errorf("cannot unpack Any into TxData %T", any)
	}
