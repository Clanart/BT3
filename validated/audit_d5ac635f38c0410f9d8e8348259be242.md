### Title
Reward double-counting bypass via mWomSV.startUnlock zeroing calDoubledCounted before repeat incentiveDeposit(mode=2) calls - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3.getRewardAmount` (lock path) computes a tier-based reward on `_amountToConvert + mWomSV.getUserTotalLocked(_account)` and subtracts `calDoubledCounted(_account)`, which itself re-reads the CURRENT `mWomSV.getUserTotalLocked(_account)` rather than a snapshot taken at the time of the prior reward calculation. Because `mWomSV.startUnlock()` immediately reduces `getUserTotalLocked` (it moves the amount into the cooldown mapping instantly, with no waiting period required for that state change to take effect), an attacker can zero out their counted balance between two `incentiveDeposit(..., 2)` calls and receive a second near-full tier reward on top of the first.

### Finding Description
`getRewardAmount` for the lock path (`_lock == true`) at [1](#0-0)  computes:
```
accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)
rewardAmount = tiered(accumulated)
mgpReward = rewardAmount/DENOMINATOR - calDoubledCounted(_account)
```
`calDoubledCounted` at [2](#0-1)  recomputes the tiered reward using the **live** `mWomSV.getUserTotalLocked(_account)`, intending to subtract the reward already attributed to the user's pre-existing locked balance so only the incremental tier reward for the new deposit is paid.

The flaw: `getUserTotalLocked` in `mWomSV` is defined as `stakingInfo - getUserAmountInCoolDown`, and `getUserAmountInCoolDown` immediately reflects any amount a user has moved into cooldown via `startUnlock`, with no delay: [3](#0-2) . `startUnlock` is a plain external function callable by any user for any amount up to their own locked balance, with no cooldown wait required before it takes effect on `getUserTotalLocked`: [4](#0-3) .

Exploit flow (unprivileged attacker, own WOM only):
1. `incentiveDeposit(A, ratio, false, 2)` — mode 2 deposits half as mWOM and locks the resulting mWOM into `mWomSV` for the attacker via `_deposit` → `mWomSV.lockFor` [5](#0-4) . Reward is computed with `getUserTotalLocked(attacker) == 0` prior to deposit, so `calDoubledCounted == 0` and attacker is paid the full tiered reward for `A` (doubled for mode 2) at [6](#0-5) .
2. Attacker immediately calls `mWomSV.startUnlock(L1)` where `L1` is (all of) their locked balance from step 1. This instantly drives `getUserTotalLocked(attacker)` toward 0 — no cooldown wait needed for this read, only for actually withdrawing the underlying mWOM later.
3. Attacker calls `incentiveDeposit(B, ratio, false, 2)` again. Now `calDoubledCounted(attacker)` reads `getUserTotalLocked ≈ 0`, so the subtraction is near-zero and the attacker is paid close to the full tiered reward on `B` again, instead of the correct incremental reward `tier(A+B) - tier(A)`.

Because reward tiers/multipliers are non-decreasing bracket-based bonuses, getting `tier(A)` and `tier(B)` computed independently (each starting from the base bracket) generally exceeds the correctly accumulated `tier(A+B)`, resulting in an overpayment of `mgp` funded from the contract's own `mgp` balance intended to reward the wider incentive program. No existing modifier (`nonReentrant`, `whenNotPaused`) prevents this since each call is a legitimate, sequential, non-reentrant transaction; the root cause is purely that the "already counted" state is derived from live, attacker-controllable data instead of a persisted historical snapshot.

### Impact Explanation
This allows an unprivileged attacker to repeatedly extract more `mgp` (locked into `vlMGP` on their behalf) from `ArbWomUp3`'s finite `mgp` balance than the tiered reward schedule intends, at the expense of other WOM depositors who rely on that same balance for their incentive rewards. This matches the "theft/permanent loss of unclaimed yield" and reward-pool insolvency impact class — the shared `mgp` reward reserve held by the contract (checked via `mgpleft` cap at [7](#0-6) ) can be drained faster and disproportionately by repeat exploiters, depriving legitimate depositors of their fair share.

### Likelihood Explanation
Feasibility is high: the attacker needs no special privileges, only WOM tokens to deposit and the ability to call `mWomSV.startUnlock` on their own position (a standard user-facing function). The attack is repeatable — each cycle costs the attacker only the WOM they deposit (which is partly retained as mWOM/mWomSV or converted, i.e., not lost), plus gas, while yielding an outsized `mgp` reward each time `incentiveDeposit` is re-invoked with `_mode == 2`. The only friction is that `startUnlock` reduces `getUserTotalLocked` used in the read, but actually withdrawing the cooled-down mWOM back requires waiting `coolDownInSecs` — however this wait is irrelevant to the exploit since the accounting bypass only depends on the instantaneous drop in `getUserTotalLocked`, not on completing the unlock.

### Recommendation
Do not compute "already counted" reward from the live `mWomSV.getUserTotalLocked`. Persist a per-account high-water-mark (e.g., `mapping(address => uint256) public accumulatedLockedForReward`) that is only ever incremented when `incentiveDeposit(..., 2)` is called, and use that stored value (rather than `mWomSV.getUserTotalLocked`) both for the `accumulated` calculation and inside `calDoubledCounted`. This ensures reward accounting is monotonic and cannot be manipulated by unlocking mWomSV/vlMGP positions between calls.

### Proof of Concept
Foundry test plan:
1. Deploy/mimic `ArbWomUp3`, `mWomSV`, `MasterMagpie`, `mWOM`, `wom`, `smartWomConvert`, `vlMGP` test doubles per existing test setup; configure `rewardTier`/`rewardMultiplier` via `setMultiplier`, fund the zapper with `mgp`.
2. As attacker, call `incentiveDeposit(A, ratio, false, 2)`; record `vlMGP` amount locked for attacker (`R1`) and `mWomSV.getUserTotalLocked(attacker)` (`L1`).
3. Call `mWomSV.startUnlock(L1)` as attacker; assert `mWomSV.getUserTotalLocked(attacker) == 0` immediately (no wait).
4. Call `incentiveDeposit(B, ratio, false, 2)` as attacker; record reward `R2`.
5. Compute expected correct reward: single call `getRewardAmount(A+B, attacker, true) * 2` performed with no intermediate unlock (i.e., against a fresh account depositing `A+B` at once) → `RExpected`.
6. Assert `R1 + R2 > RExpected`, proving the split-with-unlock path pays out more `mgp`-backed `vlMGP` reward than a single equivalent deposit, confirming the double-counting bypass.
