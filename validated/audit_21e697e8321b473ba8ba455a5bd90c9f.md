### Title
Unchecked u64 addition in `SignableTransaction::new` lets crafted payment amounts wrap the funds check and produce a signed transaction whose outputs exceed its inputs - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
CVE-2024-52559 is an integer-wraparound bug: two attacker-controlled `u32`s (`size`, `offset`) are added without an overflow check, and the wrapped sum is used as a bound. The direct analog in Serai is the satoshi accounting in `SignableTransaction::new`, where `payment_sat` is a wrapping `u64` sum of payment amounts and `payment_sat + needed_fee` is an unchecked `u64` addition used as the bound for `input_sat < ...`. Values that wrap are also fed to `input_sat.checked_sub(payment_sat + fee_with_change)` in the change calculation and to `fee()`'s wrapping subtraction.

### Finding Description
`SignableTransaction::new` computes the total of requested payments with a plain `u64` sum and compares inputs to it plus the fee:

```rust
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();
...
if input_sat < (payment_sat + needed_fee) {
  Err(TransactionError::NotEnoughFunds { ... })?;
}
``` [1](#0-0) 

Both `payment_sat` (a sum of untrusted `u64` amounts) and `payment_sat + needed_fee` can wrap modulo 2^64. The only per-payment validation is `*amount < DUST → DustPayment` [2](#0-1)  — there is no per-amount upper bound (e.g., `<= MAX_MONEY`) and no `checked_add`/`checked_sum`. Two payments of ~2^63 each satisfy `>= DUST` yet wrap `payment_sat` to a small value, defeating `NotEnoughFunds`.

The same wrapped `payment_sat` is then reused in the change path:

```rust
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
``` [3](#0-2) 

Here `payment_sat + fee_with_change` wraps again, so `checked_sub` succeeds and a change output of nearly the entire `input_sat` is appended, while the payment `TxOut`s carry the astronomically large attacker amounts (`Amount::from_sat(payment.1)`, line 190).

Finally, `fee()` performs a bare `u64` subtraction of output-sum from input-sum; after the wrap bypass the output sum exceeds the input sum, so `fee()` underflow-wraps (release) or panics (debug): [4](#0-3) 

Reachability: `payments`/`change`/`fee_per_vbyte` originate from the Plan the processor builds from out-instructions (unserialized via `Plan::read`, which reads `Payment`s from byte streams) [5](#0-4) , and the input `ReceivedOutput`s are deserialized from untrusted bytes via `ReceivedOutput::read`, where the `TxOut` value is a free `u64` from `consensus_decode` [6](#0-5) . The resulting transaction is passed to `TransactionMachine`, which produces real FROST signature shares over the malformed sighashes via `taproot_key_spend_signature_hash` [7](#0-6) .

### Impact Explanation
The `NotEnoughFunds` solvency check is the only guard preventing construction of a transaction whose declared outputs exceed its inputs. By wrapping `payment_sat + needed_fee`, an unprivileged party causes the threshold set to generate signature shares for, and `complete()` to assemble, a transaction spending more than is available — an economically nonsensical transaction that should have been rejected at construction. The same wrap corrupts `fee()` reporting (wrapping to ~2^64) and the change calculation (emitting a change output that mis-accounts the balance), and in debug builds the `sum`/`+`/`-` operations panic outright, aborting the signing session. This is a checked-arithmetic omission on attacker-influenced values gating a fund-safety invariant — structurally identical to the CVE's `size + offset` bound bypass.

### Likelihood Explanation
Triggering requires only control of the payment amounts in a plan/instruction or of a serialized `ReceivedOutput` — all reachable through untrusted bytes (`Payment::read`, `ReceivedOutput::read`) without any key material or validator status. The wrap needs no race or special timing; two large in-range `u64` amounts suffice. The resulting signed transaction is consensus-invalid, so direct theft of the inputs is not achievable — the consequence is an incorrectly-signed transaction, corrupted fee/change accounting, and a reliable abort of the signing attempt. Medium.

### Recommendation
Use checked arithmetic for all monetary aggregation in `SignableTransaction::new`: accumulate `payment_sat` and `input_sat` with `checked_add`/`try_fold` (returning `NotEnoughFunds`/`TooLargeTransaction` on overflow), reject any payment exceeding `bitcoin::Amount::MAX_MONEY.to_sat()`, compute `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`, and make `fee()` use `checked_sub`. A debug/release-safe path is required since release builds wrap silently.

### Proof of Concept
```rust
// payments under attacker control; each >= DUST so no DustPayment error
let payments: Vec<(ScriptBuf, u64)> = vec![
  (attacker_script.clone(), u64::MAX - 1000),
  (attacker_script.clone(), u64::MAX - 1000),
];
// payment_sat = (u64::MAX - 1000) * 2 wraps to a small value
// payment_sat + needed_fee wraps small again, so:
//   input_sat < (payment_sat + needed_fee)  -> false, NotEnoughFunds skipped
// change path: input_sat.checked_sub(payment_sat + fee_with_change) succeeds,
// emitting change ~= input_sat while the payment TxOuts claim ~2^64 sats
let stx = SignableTransaction::new(inputs, &payments, Some(change), None, fee_per_vbyte).unwrap();
// stx is handed to multisig()/TransactionMachine and the threshold signs
// a transaction whose outputs exceed its inputs; stx.fee() underflow-wraps
```
