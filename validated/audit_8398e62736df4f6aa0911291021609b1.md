### Title
Missing identity/non-zero check on verification shares and group key allows funds to be committed to the point at infinity (unspendable "zero address") - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) validates only the *count* and *indexes* of `verification_shares` (lines 355-365) and never checks that any share, or the resulting `group_key` computed at lines 376-378, is non-identity. `ThresholdKeys::read` (lines 574-632) reconstructs keys purely from untrusted bytes via `C::read_G`, which performs canonical-encoding checks but no identity rejection (crypto/ciphersuite/src/lib.rs:91-101), and then calls `ThresholdKeys::new` — so a byte stream carrying identity verification shares is accepted.

### Finding Description
The audit-report bug class is "constructor accepts a zero/existent-less address, causing tokens sent to it to be burned." In Serai the role of an address is played by the group key. `ThresholdKeys::new` computes `group_key` as an interpolated sum of the caller/byte-supplied verification shares: [1](#0-0) 

If all `t` shares used in the interpolation are the identity (or sum to identity), `group_key` is the point at infinity — the elliptic-curve equivalent of the zero address: a key with no usable discrete logarithm and, for Bitcoin, no representable x-only public key. No check anywhere in `new`, `view`, `scale`, or `offset` rejects this state; `scale` only rejects a zero *scalar* (lines 400-406).

### Impact Explanation
The Bitcoin wallet layer derives deposit addresses and `Scanner` scripts from this group key (`p2tr_script_buf`, `Scanner::new`, `Scanner::register_offset` in networks/bitcoin/src/wallet/mod.rs:80-196). Outputs "received" against an identity group key are permanently unspendable — there is no valid Taproot internal key and no secret key that can sign — exactly the "token burned by sending to zero address" impact. Additionally, on curves admitting a canonical identity encoding, an identity group key corresponds to secret key 0, for which `SchnorrSignature::verify` accepts any `(R = sG, s)` forgery since `R + c·identity − sG = 0` (crypto/schnorr/src/lib.rs:88-110), meaning funds are not merely burned but stealable.

### Likelihood Explanation
The input vector is in scope: `ThresholdKeys::read` is explicitly listed as an untrusted-bytes API, and it feeds attacker-controlled point encodings straight into `ThresholdKeys::new` without any non-identity validation (crypto/dkg/src/lib.rs:620-631). Reaching it requires the integrator to deserialize keys from attacker-influenced bytes — plausible for share/key-transport flows — rather than a malicious DKG peer, so it is not excluded by the malicious-peer rule. Impact severity is Medium: loss of funds/forgeability conditional on crafted key material.

### Recommendation
Reject identity points in `ThresholdKeys::new`: check each supplied verification share and the computed `group_key` with `is_identity()` and return a `DkgError`. Consider the same rejection in `C::read_G` consumers that treat decoded points as keys (e.g., `Commitments::read`, `SchnorrSignature::read` callers), and add an explicit `group_key.is_identity()` assertion after `tweak_keys` in networks/bitcoin/src/wallet/mod.rs:46-75.

### Proof of Concept
1. Build a serialized `ThresholdKeys` blob for a `PrimeGroup` suite where all `n` verification-share encodings decode to identity (for curves whose `GroupEncoding` canonically encodes identity, e.g., Ed25519 via dalek-ff-group; for secp256k1, construct `ThresholdKeys::new` directly with `ProjectivePoint::IDENTITY` shares — `new` is a public constructor with no identity check).
2. `ThresholdKeys::<C>::read(&mut blob)` / `ThresholdKeys::new(params, Interpolation::Lagrange, share, shares)` succeeds because only `len`/`index` are validated (crypto/dkg/src/lib.rs:355-365).
3. `keys.group_key()` returns `C::G::identity` (lines 376-378, 445-447).
4. On Bitcoin, `Scanner::new(group_key)`/`p2tr_script_buf` yields a deposit script for an unspendable key (or the identity key is normalized to x=0, still with no known discrete log); any output `scan_transaction` reports as received cannot be spent — funds burned, mirroring the reported zero-address constructor bug. For Ed25519-class curves, additionally present `SchnorrSignature { R: sG, s }` for arbitrary `s` to `verify(identity, c)` and it returns true.
