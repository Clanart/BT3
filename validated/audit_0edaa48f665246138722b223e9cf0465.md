Confirmed: `handle_finalized_payout` (`core/src/operator.rs:839-916`) relies entirely on the `payout_payer_operator_xonly_pk`/`payout_tx_blockhash` written by `Verifier::update_finalized_payouts`, and `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) triggers it automatically for any operator whose own `xonly_public_key` matches that DB column — with no cross-check that the operator itself ever actually broadcast or funded that payout transaction.

### Title
Unauthenticated OP_RETURN ingestion lets any withdrawing user attribute their own self-funded payout to an arbitrary operator, triggering unearned reimbursement - (File: core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` sets `withdrawals.payout_payer_operator_xonly_pk` purely from the OP_RETURN bytes of whatever transaction spends the registered `withdrawal_utxo`, with no check that the named operator actually constructed, signed, or funded that transaction. Because the withdrawal UTXO is authorized with `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:162-187`, `core/src/builder/transaction/operator_reimburse.rs:407-436`), that signature only commits to input 0 and output 0 — never to the OP_RETURN output — so any party holding that signature (in particular the withdrawing user themselves, who creates it) can fund the rest of the transaction with their own BTC and put an arbitrary operator's xonly pubkey in the OP_RETURN.

### Finding Description
Binding claimed broken: `party that can set withdrawals.payout_payer_operator_xonly_pk for withdrawal i == the operator that actually fronted (funded) withdrawal i's payout`.

Trace:
- `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:162-187`) enforces the input signature's sighash type must be `SinglePlusAnyoneCanPay`.
- `Operator::withdraw` (`core/src/operator.rs:560-692`) builds `create_payout_txhandler` with only the dust `withdrawal_utxo` as input and the user's output as output 0, verifies the SIGHASH_SINGLE|ANYONECANPAY signature only against input 0 / output 0 (`core/src/builder/transaction/txhandler.rs:210-233`, `Prevouts::One`), then calls bitcoind `fund_raw_transaction`/`sign_raw_transaction_with_wallet` to add and sign an *additional funding input from the operator's own wallet* and broadcasts.
- Nothing about this flow is enforced consensus-side. Since the signature never covers the OP_RETURN output or any additional inputs, **anyone** possessing the user's `SinglePlusAnyoneCanPay` signature over the withdrawal dust UTXO (trivially the withdrawing user, who generated it) can independently construct the same shape of transaction — dust input + user payout output + own funding input + an OP_RETURN naming *any* operator's public xonly key — sign the added funding input with their own key, and broadcast it directly to the Bitcoin network, bypassing every Clementine gRPC endpoint (`Withdraw`/`InternalWithdraw`), `Operator::is_profitable`, and the aggregator entirely.
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) scans the finalized block, finds the payout tx for withdrawal `idx`, extracts the operator xonly pk purely from `get_first_op_return_output`/`parse_op_return_data` and writes it unconditionally via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`). No signature, no gRPC interceptor, and no correlation to which entity actually funded the transaction is checked at this ingestion point.
- Downstream, `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) polls `get_first_unhandled_payout_by_operator_xonly_pk` keyed on the operator's own `signer.xonly_public_key`. If the attacker names an existing operator X in the OP_RETURN, X's own automation will match this row and call `Operator::handle_finalized_payout` (`core/src/operator.rs:839-916`), which unconditionally allocates a kickoff connector and starts the reimbursement flow for deposit `deposit_id`, believing X fronted the payout. `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) and `send_asserts`'s check (`core/src/operator.rs:1290-1295`) only verify that the OP_RETURN operator matches the kickoff's own operator — which trivially holds since X is honestly reporting its own key — not that X ever broadcast or funded the payout.

Existing guards (`SECP.verify_schnorr` in `Operator::withdraw`, `Verifier::is_deposit_valid`, `is_kickoff_malicious`, `only_aggregator_and_self`) all operate on the assumption that whoever wrote the OP_RETURN is who broadcast the transaction with real funds; none of them re-derive "who paid" from anything but the untrusted OP_RETURN bytes, so the divergence is never caught.

### Impact Explanation
An uninvolved, honest operator can be made to believe it fronted a withdrawal it never funded and will automatically execute the full kickoff/round/reimburse machinery (`Operator::handle_finalized_payout` → kickoff tx → reimburse_tx, `core/src/builder/transaction/operator_reimburse.rs:341-385`), ultimately spending the deposit's move-to-vault funds as "reimbursement" to that operator with no real payout having been fronted by them. This is exactly the Critical category "an operator reimbursed for a payout it never funded" — bridge collateral/deposit value is credited to the wrong party, and the operator additionally burns its own kickoff/round transaction fees and locks a kickoff connector for a claim it never earned. This is repeatable for every withdrawal index and every operator whose xonly pubkey is public knowledge (fetchable via `fetch_operator_keys`), so blast radius spans all deposits/withdrawals and all operators running automation.

### Likelihood Explanation
The only precondition is that the attacker is the withdrawing user (already an allowed capability: they can call Citrea's `withdraw`, choose the withdrawal UTXO bytes, choose the signature and sighash flag, and craft the OP_RETURN). No verifier, operator, or aggregator credential is needed at any point; the transaction is broadcast directly to Bitcoin. Cost is the attacker's own funding of their own output plus a normal miner fee — i.e., cost is roughly the withdrawal amount itself (which they receive back), not an added expense. Any operator running the `PayoutCheckerTask`/automation feature is automatically vulnerable without further attacker interaction.

### Recommendation
`update_finalized_payouts`/`update_payout_txs_and_payer_operator_xonly_pk` must not treat the OP_RETURN-named operator as an authenticated claim of "who funded this payout." Require that the operator's own additional funding input(s) in the payout transaction be attributable to that operator (e.g., verify the funding input's script/ownership against the operator's registered collateral/reimbursement key, or require the operator to co-sign/pre-register the payout transaction via an authenticated channel such as the aggregator/verifier signature flow before it is trusted for reimbursement purposes) before `PayoutCheckerTask` is allowed to initiate `handle_finalized_payout` for it.
