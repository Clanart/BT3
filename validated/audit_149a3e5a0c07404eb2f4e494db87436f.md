## Title
Gasless approval flow forces unrevocable unlimited ERC20 allowances to the `GaslessSwapRouter`, leaving zero-KAIA users permanently exposed if the router is compromised - (File: `kaiax/gasless/impl/getter.go`)

### Summary
The `kaiax/gasless` module (KIP-247) only recognizes an ERC20 `approve` transaction as a sponsored "GaslessApproveTx" when the approved amount is *exactly* `MaxUint256` and the spender is the currently whitelisted `GaslessSwapRouter`. There is no equivalent sponsored path to reduce or revoke that allowance (i.e., `approve(spender, 0)`), even though the whole premise of the gasless module is that these users hold **no KAIA** and therefore cannot pay gas for an ordinary revoking transaction outside the module. This mirrors the reported DODO issue: routers are granted unlimited (`type(uint256).max`) approvals with no built-in mechanism to revoke them, so a compromised or maliciously-updated router can drain every approving user's token balance.

### Finding Description
`GaslessModule.isApproveTx` enforces that a sponsored approve tx must set the allowance to `MaxUint256` for the currently registered swap router: [1](#0-0) 

The `swapRouter` address itself is not fixed - it is re-read from the KIP-149 `Registry` system contract on every block via `updateAddresses`/`getGaslessInfo`, and can be swapped by governance (or by whoever controls the `GaslessSwapRouterName` registry entry) to a different, or potentially malicious/compromised, contract address: [2](#0-1) 

Because `IsApproveTx`/`isApproveTx` only accept `amount == MaxUint256` (condition A4), the gasless flow provides no sponsored way to submit a zero/decreasing allowance to revoke a previously granted `MaxUint256` approval. The `GetCheckBalance`/`checkBalanceForSwap` logic explicitly relies on this unlimited allowance staying in place (`tx.token.allowance(sender, router) >= tx.amountIn`): [3](#0-2) 

By design, users who rely on the gasless module have zero KAIA balance (that's the entire point of the feature - the proposer lends them gas via `GetLendTxGenerator` and they repay during the swap). Consequently, once a user grants a `MaxUint256` approval to the router, they have no funded means outside the module to submit a plain `approve(router, 0)` revoke transaction, and the module itself has no support for constructing/sponsoring such a revoke. If the registered `GaslessSwapRouter` (an `Ownable` contract with `transferOwnership`) is later compromised, has its ownership hijacked, or governance points the registry to a malicious router, every prior gasless-approving user's full token balance remains permanently drainable, with no realistic self-service remedy.

### Impact Explanation
This is directly analogous to the referenced High-severity finding: unlimited router approvals that cannot be revoked lead to complete loss of the approved token balance if the router contract is later compromised. On Kaia, the affected population is specifically gasless/no-KAIA users - the very users the module targets - who structurally cannot pay for a stand-alone revoke transaction, and the protocol provides no sponsored revoke path. This constitutes a concrete unauthorized value-movement path (router-side drain of approved balances) enabled by a design gap reachable purely through normal, publicly available gasless-swap transactions.

### Likelihood Explanation
Every successful `GaslessApproveTx` inherently creates this exposure since amount is hardcoded to `MaxUint256` (A4) - there is no partial-approval alternative. The router address is also mutable via the Registry, and its `Ownable` design (`transferOwnership`, `Owner()`) means a single compromised private key or malicious governance registration is sufficient to redirect drains against all outstanding max-approvals. No attacker action is required to create the vulnerable state; it accumulates as a byproduct of normal gasless usage.

### Recommendation
Add a sponsored/gasless-compatible mechanism for zero-KAIA users to revoke or lower their token allowance to the swap router (e.g., recognize and lend gas for `approve(router, 0)` similarly to how `MaxUint256` approvals are recognized), or move to a "approve exact `amountIn` per swap" model instead of a standing `MaxUint256` allowance, so that a compromised router's blast radius is limited to funds actively in-flight rather than a user's entire token balance.

### Proof of Concept
1. User A has no KAIA balance and sends a `GaslessApproveTx` approving `GaslessSwapRouter` (`gsrAddr`) for `MaxUint256`, as validated by `isApproveTx` (A1/A3/A4) in `kaiax/gasless/impl/getter.go` lines 79-86, and executed via the lend/repay flow in `tests/gasless_test.go` lines 168-215.
2. Governance (or a hijacked registry admin key) later calls `Registry.Register(GaslessSwapRouterName, maliciousRouter, targetBlock)`, and `updateAddresses` in `kaiax/gasless/impl/getter.go` (lines 315-344) updates `g.swapRouter` to `maliciousRouter` at the target block - this is the same mechanism exercised in `kaiax/gasless/impl/execution_test.go` lines 118-142 ("update gsr address").
3. User A's ERC20 allowance was granted to the *old* `gsrAddr`, not to `maliciousRouter`; but suppose instead the *original* `gsrAddr` contract itself is later compromised (private key leak of its `Owner`, or a bug is discovered in its `swapForGas`/commission logic) - User A's allowance to `gsrAddr` is `MaxUint256` and remains valid indefinitely.
4. User A still has no KAIA and the gasless module offers no sponsored `approve(gsrAddr, 0)` transaction type (`isApproveTx` requires `Amount.Cmp(abi.MaxUint256) == 0`), so User A cannot revoke the exposed allowance.
5. The compromised/malicious router can call `transferFrom(userA, attacker, balanceOf(userA))` on the approved token at any time, draining User A's full balance, with User A structurally unable to prevent it.

// IsApproveTx checks following conditions:
// A1. tx.to is a whitelisted ERC20 token.
// A2. tx.data is `approve(spender, amount)`.
// A3. spender is a whitelisted SwapRouter contract.
// A4. amount is MaxUint.
func (g *GaslessModule) IsApproveTx(tx *types.Transaction) bool {
	args, ok := decodeApproveTx(tx, g.signer)
	return ok && g.isApproveTx(args)
}

func (g *GaslessModule) isApproveTx(args *ApproveArgs) bool {
	g.gaslessInfoMu.RLock()
	defer g.gaslessInfoMu.RUnlock()

	return g.allowedTokens[args.Token] && // A1
		g.swapRouter == args.Spender && // A3
		args.Amount.Cmp(abi.MaxUint256) == 0 // A4
}

func (g *GaslessModule) updateAddresses(header *types.Header) error {
	g.gaslessInfoMu.Lock()
	defer g.gaslessInfoMu.Unlock()

	swapRouter, tokens, err := getGaslessInfo(g.Chain, header)
	// proceed even if there is something wrong with multicall contract
	if err != nil {
		g.swapRouter = common.Address{}
		g.allowedTokens = map[common.Address]bool{}
		logger.Warn("there is something wrong with multicall contract", "err", err.Error())
		return nil
	}

	g.swapRouter = swapRouter

	g.allowedTokens = map[common.Address]bool{}
	for _, addr := range tokens {
		// all tokens are allowed if nil
		if g.GaslessConfig.AllowedTokens == nil {
			g.allowedTokens[addr] = true
		}
		for _, allowed := range g.GaslessConfig.AllowedTokens {
			if addr == allowed {
				g.allowedTokens[addr] = true
			}
		}
	}

	return nil
}
