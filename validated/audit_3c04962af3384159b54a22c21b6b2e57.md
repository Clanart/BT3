### Title
Optional `aggregator_verification_address` Bypasses Aggregator Identity Verification in Optimistic Payout and Withdrawal Flows — (File: `core/src/verifier.rs`, `core/src/rpc/operator.rs`)

---

### Summary

`BridgeConfig.aggregator_verification_address` is declared as `Option<alloy::primitives::Address>`. When the env var `AGGREGATOR_VERIFICATION_ADDRESS` is absent, the field is `None`. Both `Verifier::sign_optimistic_payout` and the `Operator::withdraw` gRPC handler gate the entire ECDSA aggregator-identity check on `if let Some(address_in_config) = self.config.aggregator_verification_address`. When the field is `None` the check is silently skipped and any caller that passes mTLS can obtain verifier partial signatures for an optimistic payout or trigger an operator withdrawal with an arbitrary output address.

---

### Finding Description

`BridgeConfig` declares the field as optional:

```rust
pub aggregator_verification_address: Option<alloy::primitives::Address>,
``` [1](#0-0) 

`BridgeConfig::from_env()` reads it with `.ok()`, so a missing env var silently produces `None`:

```rust
let aggregator_verification_address = std::env::var("AGGREGATOR_VERIFICATION_ADDRESS")
    .ok()
    .map(|addr| { ... })
    .transpose()?;
``` [2](#0-1) 

In `Verifier::sign_optimistic_payout`, the entire ECDSA check is wrapped in `if let Some(...)`:

```rust
if let Some(address_in_config) = self.config.aggregator_verification_address {
    // verify ECDSA sig ...
}
// falls through with no check when None
``` [3](#0-2) 

The identical pattern appears in the `Operator::withdraw` gRPC handler:

```rust
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    // verify ECDSA sig ...
}
``` [4](#0-3) 

Critically, `sign_optimistic_payout` accepts a caller-supplied `output_script_pubkey` and validates only that the **input** outpoint matches the DB record — the output destination is never checked against any expected value:

```rust
if withdrawal_utxo != input_outpoint {
    return Err(...);
}
// output_script_pubkey is used as-is in the payout tx
``` [5](#0-4) 

---

### Impact Explanation

When `AGGREGATOR_VERIFICATION_ADDRESS` is unset:

1. Any caller that holds a CA-signed mTLS certificate can call `NonceGen` on each verifier to obtain nonce session IDs, then call `OptimisticPayoutSign` with a valid `input_outpoint` (a real withdrawal UTXO from the DB) but an attacker-controlled `output_script_pubkey`.
2. Each verifier will produce a valid partial musig2 signature over the attacker's output address.
3. The attacker aggregates all partial signatures and broadcasts the optimistic payout transaction, redirecting the full bridge amount (up to `bridge_amount − NON_EPHEMERAL_ANCHOR_AMOUNT`) to their own address.
4. Separately, the `Operator::withdraw` gRPC endpoint will process any withdrawal without aggregator authorization, allowing unauthorized triggering of operator payout transactions.

This constitutes theft of bridged BTC and unauthorized state transitions in the withdrawal flow.

---

### Likelihood Explanation

- `AGGREGATOR_VERIFICATION_ADDRESS` is explicitly optional in `BridgeConfig::from_env()`. A deployment that omits this env var (e.g., an operator who follows the minimal required env vars) silently disables the check.
- The `BridgeConfig::default()` does include a hardcoded address, but production deployments loaded via `from_env()` or a TOML file without this field will have `None`.
- The code comment explicitly frames this as a temporary/optional guard ("to force citrea to check withdrawal params manually during some time after launch"), increasing the chance operators treat it as non-mandatory.
- The attacker only needs a CA-signed mTLS cert, which any bridge participant already holds.

---

### Recommendation

1. Make `aggregator_verification_address` a required field (`alloy::primitives::Address`, not `Option`). Return a startup error if it is absent.
2. If the field must remain optional for backward compatibility, add an explicit startup warning/error when it is `None` and the node is not in a test/regtest mode.
3. Add a guard in `sign_optimistic_payout` and `Operator::withdraw` that rejects the call when `aggregator_verification_address` is `None` in non-test builds, analogous to how `operator_withdrawal_fee_sats` is enforced:

```rust
if config.operator_withdrawal_fee_sats.is_none() {
    return Err(eyre::eyre!("Operator withdrawal fee is not set").into());
}
``` [6](#0-5) 

Apply the same pattern to `aggregator_verification_address`.

---

### Proof of Concept

**Setup:** Deploy verifiers and operators with `AGGREGATOR_VERIFICATION_ADDRESS` unset (omit the env var).

**Attack steps:**

1. Obtain a CA-signed mTLS client certificate (any bridge participant already has one).
2. For each verifier, call `NonceGen` to obtain a `nonce_session_id`.
3. For each verifier, call `OptimisticPayoutSign` with:
   - A valid `deposit_id` and `input_outpoint` (a real withdrawal UTXO visible in the bridge DB or on-chain)
   - `output_script_pubkey` = attacker's own P2TR address
   - `output_amount` = `bridge_amount − NON_EPHEMERAL_ANCHOR_AMOUNT`
   - `verification_signature` = `None` (the check is skipped when `aggregator_verification_address` is `None`)
4. Each verifier returns a `PartialSignature` without error (the `if let Some(...)` block is never entered).
5. Aggregate all partial signatures into a full musig2 signature.
6. Broadcast the optimistic payout transaction paying the full bridge amount to the attacker's address.

**Root cause:** `aggregator_verification_address` is `None` → the `if let Some(address_in_config)` guard at `core/src/verifier.rs:1602` is never entered → no ECDSA identity check is performed → the verifier signs over an attacker-supplied output address. [3](#0-2) [1](#0-0) [2](#0-1)
