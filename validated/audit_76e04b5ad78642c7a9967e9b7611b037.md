### Title
Gasless swap pricing trusts unauthenticated DEX (factory/router) pairs registered via `GaslessSwapRouter.AddToken`, allowing under-collateralized fee-delegation repayment - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
`GaslessSwapRouter.AddToken(token, factory, router)` registers an arbitrary `(factory, router)` DEX pair for a token with no on-chain verification that the `factory`/`router` were deployed by a canonical, trusted DEX factory (e.g., a known `UniswapV2Factory` bytecode/deployment), mirroring the Napier `PoolFactory.deploy()` issue where a base pool's provenance (must be deployed by `CurveTricryptoFactory`) was never checked. Kaia's CN/proposer relies on `GetAmountIn`/pricing from this unverified pair to decide how much gas fee to lend a gasless user before the swap executes, creating the same "trust an unverified pool/pair contract" root cause.

### Finding Description
The CN validates a gasless swap transaction and decides the amount of KAIA to lend the sender (to cover gas) based on the pricing returned by the registered swap-router/DEX pair: [1](#0-0) 

`GaslessModule.checkBalanceForSwap` calls `GaslessSwapRouterCaller.GetAmountIn(token, minAmountOut)` and only requires `swapArgs.AmountIn >= requiredAmountIn` reported by that router — the CN has no independent way to verify the router/factory pair backing `token` is a genuine, safe DEX deployment. This mirrors exactly the audited root cause: `getDEXInfo`/`dexAddress` return whatever `(factory, router)` was registered via `AddToken`, without checking the factory was deployed by a canonical factory contract: [2](#0-1) [3](#0-2) 

The lending/repayment amounts computed from this trust chain feed directly into the fee-delegation flow (`lendAmount`/`repayAmount`), which is the mechanism by which the CN (fee payer) is repaid after advancing gas on behalf of a gasless sender: [4](#0-3) 

If `AddToken` is ever pointed at a pair/router that is not the genuine registered DEX pair for that token (e.g., a spoofed or manipulable pair contract with the same token symbol/interface but attacker-controlled reserves or a `getAmountIn` override), the CN's balance/price check would pass while the actual `swapForGas` execution settles at a manipulated rate, producing an outcome where the CN under-collects the fee it fronted — directly analogous to "a malicious admin might use a specially crafted base pool contract to trick users/lenders."

### Impact Explanation
Because the CN's decision to advance gas (fee-delegation lending) is derived solely from `GetAmountIn` of the registered, unverified pair contract, a malicious or incorrectly-configured DEX registration can cause systematic under-collateralization of the gas advance for every gasless swap routed through that token, resulting in the CN/proposer absorbing losses on each fee-delegated gasless transaction — a concrete fee-delegation abuse/value-loss scenario, matching the Medium severity of the original finding (loss of assets for the "victim," here the fee-advancing proposer/CN).

### Likelihood Explanation
`AddToken` is owner-gated (the caller of `checkBalanceForSwap`/`swapForGas` cannot invoke it), so exploitation requires the `GaslessSwapRouter` owner/admin to register a bad pair — the same "restricted-admin" precondition the original Sherlock report explicitly carved out and still accepted as valid because the trust assumption ("must be deployed by CurveTricryptoFactory" / here, "must be a genuine DEX pair") is never enforced on-chain, and once registered, the exposure is fully reachable by any unprivileged gasless-swap sender interacting with that token, and is silently trusted by every node running the gasless module.

### Recommendation
When registering a DEX pair in `GaslessSwapRouter.addToken`, verify on-chain that `factory` is the canonical, trusted factory contract (e.g., check known factory bytecode hash or query `factory.getPair(token, WKAIA) == router`'s underlying pair matches an expected deterministic CREATE2 address derived from the canonical factory), rather than accepting an arbitrary router/factory pair by address alone. Additionally, consider having `kaiax/gasless` cross-check the router-reported pricing against an independently computed reserve-based price before trusting it for fee-delegation lending decisions.

### Proof of Concept
Not directly demonstrable from the indexed contents alone — the `GaslessSwapRouter.sol` source is not present in the indexed codebase (only the compiled Go bindings `contracts/bindings/kip247/GaslessSwapRouter.go`), so the exact internal logic of `getAmountIn`/`getDEXInfo` derivation cannot be fully confirmed here. A Devin session with full repository access would be needed to inspect the Solidity source (if present in a separate contracts repo) and confirm whether `addToken` performs any factory/pair provenance check, and to build a concrete PoC contract demonstrating the mismatch between `checkBalanceForSwap`'s price check and actual `swapForGas` settlement.

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}
