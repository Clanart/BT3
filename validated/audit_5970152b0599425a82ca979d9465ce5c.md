Based on the investigation, I found a legitimate local analog: **line-index based partial-commit selections are not invalidated when the underlying diff shape changes for files that are not the currently-viewed file**, which is the same class of bug as the report (stale ordering/positional data reused against changed underlying state, leading to incorrect security-relevant actions).

### Title
Stale line-index diff selections are silently reapplied to a reshaped diff, corrupting partial commits - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
When Desktop refreshes repository status, `updateChangedFiles` carries over each file's existing `DiffSelection` object by identity (`file.id`), regardless of whether the file's on-disk content — and therefore its diff hunk layout — has changed since the selection was made. `DiffSelection` tracks "diverging lines" purely as **absolute line indices** into a diff, with no binding to the actual line content. Only the single currently-selected file gets its selectable-line set refreshed (`updateChangesWorkingDirectoryDiff`); every other file's selection is passed through untouched. If the tracked file's content changes on disk (e.g. via a git hook, build tool, or any process that runs after clone/fetch/checkout of a repository the attacker controls) while the user has a partial selection pending on it, the old line indices get reapplied to a completely different diff at commit time, without any indication that the correspondence between "selected line #7" and its content has changed.

### Finding Description
- `updateChangedFiles` in [1](#0-0)  merges new status results with the previous working-directory files, but re-attaches the *old* `DiffSelection` object (`file.withSelection(existingFile.selection)`) to the *new* file object keyed only by file id/path — it never checks whether the diff content underlying that selection is still the same shape.
- `DiffSelection.isSelected` in [2](#0-1)  only knows about line indices (`divergingLines`), with no concept of line content — a line index is meaningful only relative to the specific diff hunks that produced it.
- `updateChangesWorkingDirectoryDiff` in [3](#0-2)  only recomputes `selectableLines` (to drop indices that no longer exist) for the **single currently-selected** file; the explicit comment there acknowledges the underlying risk: "The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines." Files that are not currently open in the Changes view never get this reconciliation at all.
- At commit time, `formatPatch` in [4](#0-3)  re-fetches the diff fresh and calls `file.selection.isSelected(absoluteIndex)` against the new hunk layout, using the stale, unvalidated indices. `stageFiles`/`applyPatchToIndex` in [5](#0-4)  and [6](#0-5)  then apply this mismatched patch to the index without any content-based validation.

This mirrors the report's broken invariant exactly: a positional ordering/selection artifact (ICR in the report, diff line index here) is computed once, cached, and later reused to drive a security/integrity-relevant operation (redemption ordering there, commit/patch staging here) after the underlying data it was derived from has changed — with no mechanism to detect or refresh it except for the one object currently being viewed.

### Impact Explanation
The result is silent corruption of what the user commits: a user could review and select specific lines to include (e.g. explicitly excluding a sensitive change), switch away from that file, and have unrelated background activity within an attacker-supplied repository (a git hook fired by clone/fetch/checkout/merge, or any tooling the repository invokes) alter that file's content between the time the selection was made and the time the commit runs. Desktop will stage whatever now sits at the previously-selected line positions — potentially including attacker-planted content the user never saw or approved — and commit/push it without any warning. This falls squarely under "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Moderate. It requires: (1) the user to have a partial (line-level) selection pending on a file, (2) that file's on-disk content to change while a different file/tab is selected (achievable via any repository-controlled hook or background process, not requiring local/physical access or credentials), and (3) the user to commit without re-opening/re-reviewing that specific file's diff. No existing guard revalidates non-visible files' selections, and the explicit code comment shows the developers are aware only the visible file's selectable lines are recomputed — non-visible files are entirely unguarded.

### Recommendation
- Bind `DiffSelection` state to a content-derived identity (e.g. a hash of the diff/hunk content) rather than purely to `file.id`, and invalidate/clear partial selections whenever the underlying diff for *any* pending file changes shape — not just the currently viewed one.
- Alternatively, re-fetch and re-validate the diff for every file with a non-`All`/`None` selection immediately before staging in `stageFiles`, rejecting or re-prompting when the recorded selectable lines no longer match reality.
- Surface a warning in the Commit flow if a file's diff has changed since its selection was last computed.

### Proof of Concept
1. Clone/open an attacker-authored repository containing a `post-checkout` (or similar) hook that, after some delay or trigger, rewrites a tracked file's content (adding/removing lines to shift hunk boundaries).
2. In Desktop, open that file's diff and select only certain lines for commit (partial `DiffSelection`), then switch focus to a different file.
3. Let the hook fire and modify the first file's content on disk; Desktop's periodic/background status refresh calls `updateChangedFiles`, which reattaches the old `DiffSelection` (by file id) to the new file object — no recomputation of selectable lines occurs because that file isn't the active selection (`updateChangesWorkingDirectoryDiff` only refreshes the currently-selected file, per [7](#0-6) ).
4. Commit. `formatPatch`/`applyPatchToIndex` apply the stale line indices to the new diff content, staging and committing lines the user never reviewed.

```typescript
export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
```
