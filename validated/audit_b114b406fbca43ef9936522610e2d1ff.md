### Title
Zero-length aggregate signature verifies as valid - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::verify` accepts an attacker-supplied aggregate encoding containing zero nonces when the claimed signer/challenge list is also empty. The resulting verification equation degenerates to `-sG == 0`, so `s = 0` verifies without any signer participating.

### Finding Description
`SchnorrAggregate::read` accepts a serialized aggregate whose nonce count is zero and then reads a scalar `s`. `SchnorrAggregate::verify` only checks that `Rs.len()` equals `keys_and_challenges.len()`; it never rejects the empty case. For empty inputs, no per-signature terms are added and the final equation is only `(-s)G`. Consequently, the 36-byte Ristretto encoding consisting of `0u32` followed by a canonical zero scalar verifies when passed an empty signer list.

This is analogous to the upstream bug class: a public dimension of zero reaches a security-sensitive calculation whose resulting expression is degenerate. The aggregation-side API recognizes that an empty aggregate is invalid—`SchnorrAggregator::complete` returns `None` if no signatures were aggregated—but deserialization and verification do not preserve that invariant. ### Impact Explanation
A caller using `SchnorrAggregate::verify` to authenticate an aggregate over a supplied signer set can accept a forged signature when that signer set is empty. The forged object cannot be produced by `SchnorrAggregator`, so accepting it through `SchnorrAggregate::read`/`verify` is an incorrect verifier acceptance condition rather than normal protocol behavior. In a call path where an empty signer list is subsequently interpreted as authorization, this permits signature forgery without knowledge of any private key.

### Likelihood Explanation
The trigger requires only untrusted bytes passed to `SchnorrAggregate::read` and verification against an empty `keys_and_challenges` list. No malformed point encodings, secret data, malicious validator, protocol breach, or cryptographic break is needed. The practical severity depends on whether a higher-level protocol treats the empty signer set as meaningful or separately enforces quorum before calling this verifier; the cryptographic verifier itself nevertheless accepts an impossible aggregate signature.

### Recommendation
Reject empty aggregate signatures consistently:

- Return an error from `SchnorrAggregate::read` when the encoded nonce count is zero, or
- Return `false` from `SchnorrAggregate::verify` when `self.Rs`/`keys_and_challenges` is empty.

Prefer enforcing the invariant in `verify` as defense in depth, since `SchnorrAggregate` can also be constructed internally. Add a regression test asserting that serialized `len = 0, s = 0` does not verify.

### Proof of Concept
For Ristretto, the forged aggregate is the four-byte little-endian count `0` followed by a canonical zero scalar:

```rust
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ristretto;
use schnorr::aggregate::SchnorrAggregate;

const DST: &[u8] = b"example";

let forged_encoding = [0u8; 36]; // u32 length 0 || zero scalar
let aggregate =
  SchnorrAggregate::<Ristretto>::read::<&[u8]>(&mut forged_encoding.as_ref()).unwrap();

assert!(aggregate.verify(DST, &[]));
```

The verification succeeds because `keys_and_challenges` is empty, no signature terms are queued, and `s = 0` makes the single remaining `(-s)G` term the identity. [4](#0-3)
