### Title
Unverified-PoP early return in `calculate_share` publishes ECDH blame key, decrypting an honest participant's secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP encryption design includes a per-message Schnorr proof-of-possession precisely so that an attacker cannot co-opt an honest sender's per-message encryption key `X` and then trigger a blame proof that reveals `enc_key_recipient * X`, which would publicly decrypt the honest message (see the threat analysis in `crypto/dkg/pedpop/src/encryption.rs:84-90`). However, in `Encryption::decrypt` the ECDH `EncryptionKeyProof` is produced unconditionally for every message, and in `KeyMachine::calculate_share` the code paths that reject a share (`from_repr` failure) return `PedPoPError::InvalidShare { blame: Some(proof) }` **before** `batch.verify_with_vartime_blame()` ever checks the queued PoP. An attacker therefore publishes a message containing a victim's public `msg.key` plus garbage ciphertext, and the victim's node emits a blame proof containing the ECDH key that decrypts the victim's real secret share. The PoP that exists to stop this is never evaluated on this path — an "incorrect access control" style flaw where sensitive data is disclosed because an authorization check (PoP verification) is skipped on an early-error path.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Encryption::decrypt` (lines 469-501) only *queues* the PoP into the `BatchVerifier` (`msg.pop.batch_verify`, line 479); it does not check it synchronously. It then computes `key = ecdh(&self.enc_key, msg.key)` (line 487) and always returns `EncryptionKeyProof { key, dleq }` (lines 489-500), where `key` is a pure function of the recipient's static `enc_key` and the attacker-controlled public point `msg.key`.

In `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:476-499`):

```rust
let (mut share_bytes, blame) =
  self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);
```

When the decrypted bytes are not a canonical scalar, `?` returns immediately — with `blame: Some(...)` — before `batch.verify_with_vartime_blame()` at line 493 is reached. The queued PoP for that sender is never verified on this path, so a forged `EncryptedMessage` whose `pop` is invalid for the claimed sender still produces a public, self-authenticating (DLEq-backed) revelation of `bob_enc_priv * msg.key`.

The blame proof is then relayed publicly: `processor/src/key_gen.rs:504-563` (`CoordinatorMessage::VerifyBlame`) verifies the `EncryptionKeyProof` via `AdditionalBlameMachine::blame` → `decrypt_with_proof` (`encryption.rs:366-397`), which accepts the DLEq for `[G, msg.key] → [enc_key_recipient, proof.key]` and blames the *sender* — while `proof.key` remains in the public blame transcript.

### Impact Explanation
The attacker picks `msg.key` equal to the per-message key `X` from victim Alice's authentic `EncryptedMessage` to Bob (`key` field is a public group element, `EncryptedMessage::read` exposes it, `encryption.rs:171-177`). When Bob's node returns the blame error, `proof.key = bob_enc_priv * X` is the exact shared secret that `cipher()` (`encryption.rs:101-133`) uses to encrypt Alice's real share. Anyone observing the public blame can recompute the ChaCha20 keystream and decrypt Alice's ciphertext, recovering Alice's secret share `f_Alice(bob)` — a direct key-share recovery / secret disclosure caused entirely by an unprivileged party feeding crafted public bytes. Note the honest variant of this attack is the one the code comments say the PoP exists to prevent; the PoP exists but is bypassed because verification is batched and the error path short-circuits.

### Likelihood Explanation
Reachability requires only that the attacker is (or impersonates, modulo external channel authentication) a DKG sender delivering an `EncryptedMessage` to a victim participant. A random garbage ciphertext decrypts to bytes that fail `C::F::from_repr` with roughly 50% probability per attempt (random 32-byte string vs. scalar modulus), and even when it parses, the attacker can simply flip ciphertext bits across protocol attempts/attempts-IDs until an early-return occurs. The cost is being blamed for that one message — a protocol fault attribution, not loss of the leaked share. The leaked share itself directly reduces the confidentiality guarantees of the DKG (each share is a secret whose exposure is an explicit acceptance criterion: key share recovery / sensitive-information disclosure).

### Recommendation
Verify the PoP synchronously (or ensure `batch.verify_with_vartime_blame()` runs and is consulted) **before** attaching `Some(blame)` to any `PedPoPError`. Concretely, in `calculate_share`, defer constructing/returning the `EncryptionKeyProof` until after batch verification confirms the PoP for that `BatchId::Decryption(l)` is valid, or perform `msg.pop.verify` inside `decrypt` and return a `None`-blame error early when it fails. Alternatively, have `decrypt` return the proof behind a flag that is only unwrapped after `batch.verify_with_vartime_blame()` succeeds for the decryption ID. This restores the invariant the PoP was added for in `encryption.rs:84-90`.

### Proof of Concept
1. Alice and Bob run `KeyMachine::new`; Alice sends Bob an `EncryptedMessage` with public `key = X`, `pop` bound to `sender = Alice`, and ciphertext `C = ChaCha(H(bob_enc*X)) ⊕ f_Alice(bob)`.
2. Attacker Eve, in the same or a subsequent DKG attempt, sends Bob an `EncryptedMessage` claiming `from = Eve` with `key = X` (copied), arbitrary/invalid `pop`, and a random ciphertext `C'`.
3. Bob's `calculate_share` calls `decrypt`, which computes `key = ecdh(bob_enc_priv, X)` — identical to Alice's shared key — decrypts `C'` to random bytes, and queues Eve's (invalid) PoP.
4. With ~50% probability the decrypted bytes fail `from_repr`; `ok_or_else` at `lib.rs:480-482` early-returns `PedPoPError::InvalidShare { participant: Eve, blame: Some(EncryptionKeyProof { key: bob_enc_priv*X, dleq }) }` — before the batch verifies Eve's PoP.
5. The blame proof is published (e.g., through `CoordinatorMessage::VerifyBlame`, `processor/src/key_gen.rs:504`); its DLEq validates because `key` is honestly derived, so `blame_internal` blames Eve — but `proof.key` is now public.
6. Anyone computes `cipher(context, bob_enc_priv*X)` and XORs it with Alice's ciphertext `C`, recovering her secret share in the clear.
