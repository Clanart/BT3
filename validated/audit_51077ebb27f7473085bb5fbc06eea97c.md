## Title
Stale working-directory snapshot lets Copilot merge-conflict resolutions silently overwrite newer file content - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`AppStore._applyCopilotConflictResolutions` writes AI-generated conflict resolutions to disk after an asynchronous Copilot session that can run for well over two minutes (tracked via `copilotConflictResolutionOver60sCount` / `copilotConflictResolutionOver120sCount`). The function's only defense against clobbering newer user edits is a single `state` snapshot fetched once at the top of the function, checked in a loop that performs multiple sequential `await`ed filesystem/git operations. Because the guard is evaluated against a point-in-time snapshot rather than the actual file content immediately before each `writeFile`, content that changes between snapshot and write is silently overwritten.

### Finding Description [1](#0-0) 

The function captures `state` once: [2](#0-1) 

and then, for every resolved path, relies on that same stale `state.changesState.workingDirectory.files` to decide whether the on-disk file was already resolved externally: [3](#0-2) 

The comment at lines 7241-7246 explicitly acknowledges the intended invariant: "If the user resolved this file externally... while the result dialog was open... Overwriting it with Copilot's stored content would silently clobber their work, so skip it." However this check is only as fresh as the single `state` object fetched at function entry — it is never re-queried against the live filesystem for each file just before `writeFile` executes. The loop resolves and stages one file at a time with multiple `await`s (`resolveWithin`, `writeFile`, and finally a batched `git add`), so the window between the "is this already resolved" check and the actual `writeFile` for later files in the list keeps growing over the entire multi-file, multi-second operation.

Since `resolution.resolvedContent` for each path is itself derived from the model's analysis of the conflict hunks — which are produced by merging in an attacker-controlled branch/fork — an attacker can craft a merge conflict (e.g., a pull request or branch designed to trigger many/large/ambiguous conflicts) that increases the AI turnaround time. During that increased window, a user who manually or partially edits a conflicted file to override an earlier AI suggestion has their edit unprotected by any live re-check, so it can be silently discarded by the delayed `writeFile` + `git add` executed with the attacker-influenced resolution content, corrupting the final commit content without the user's knowledge.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." The user believes their manual resolution (or the resolution shown correctly in the result dialog) is what gets committed, but stale-guard logic can cause Copilot's stored, attacker-influenced resolution to be written to disk and staged instead, without any error, warning, or diff shown to the user before commit.

### Likelihood Explanation
The AI session already documented as taking 60-120+ seconds establishes that this is not a hypothetical narrow race — it is a wide, application-created window during a normal, unprivileged workflow (merging/rebasing a branch that contains conflicts against attacker-controlled content). No local/physical access or elevated privileges are required beyond the ordinary act of merging a hostile branch and using the built-in "Continue Merge" Copilot flow.

### Recommendation
Re-fetch and re-check the live on-disk/`git status` state for each individual file immediately before each `writeFile` call (or use a single fresh `getStatus`/`hasUnresolvedConflicts` check right before each per-file write) instead of reusing one `state` object captured at function entry for the entire multi-file, multi-await loop.

### Proof of Concept
1. Attacker submits/prepares a branch with several large or intentionally ambiguous merge conflicts against the target repo.
2. Victim uses the Copilot conflict-resolution feature to merge that branch; resolution takes >60s per the app's own instrumentation.
3. While Copilot is still processing later files in `copilotResolutions`, the victim manually fixes an earlier-processed conflicted file in their editor, believing the "skip if externally resolved" logic (lines 7241-7256) will protect it.
4. Because the guard used the `state` snapshot taken at function start (line 7172), the loop's later iteration for that file does not see the victim's newer edit and overwrites it via `writeFile` (line 7258), silently reverting the user's fix to the Copilot/attacker-influenced content before `git add` stages it.
