### Title
Secret share leaked in plaintext via derived `Debug` on `ThresholdCore`/`ThresholdKeys` - ([File: crypto/dalek-ff-group/src/lib.rs; crypto/dkg/src/lib.rs](crypto/dalek-ff-group/src/lib.rs))

### Summary
The Oxia advisory (CWE-532) is the bug class "secret credential material written verbatim into log output when an operation fails." Serai's exact analogue is not a logging statement but the same channel: secret scalars (private keys, shares, nonces) are wrapped in types that implement `Debug`, and the DKG's core secret-bearing structures derive `Debug`, so any `{:?}`/`assert_eq!`/`unwrap`-style formatting or panic message emits the secret share in plaintext — reachable whenever an unprivileged peer feeds malformed preprocess/share bytes that drive a signing machine into an error/panic path.

### Finding Description
`Scalar` in `crypto/dalek-ff-group` — the type used for every `C::F` secret (FROST `secret_share`, nonces, `enc_key`, `KeyGen::SecretShare`) — derives `Debug` (lib.rs:178), which formats the underlying `curve25519-dalek` scalar, exposing its byte representation. The same applies to the `FieldElement` wrapper and to all ciphersuite `F` types (`ed448`, `kp256`, `Secp256k1`/`P256` in `crypto/ciphersuite`).

On top of that primitive exposure, `crypto/dkg/src/lib.rs` derives `Debug` (10 occurrences) on its key structs including `ThresholdCore`, which stores `secret_share: C::F` and `original_i`, and `ThresholdKeys` which embeds it. Any error or panic that formats these structs — including `assert_eq!`/`assert!` failures during `ThresholdKeys::new` verification-share checks, or `{:?}` formatting of a `SecretShareMachine`/`SignatureMachine` state in `crypto/frost/src/sign.rs` — writes the complete secret share into whatever sink captures the panic/log output.

The codebase itself demonstrates it considers this a real exposure channel: `Encryption` in `crypto/dkg/pedpop/src/encryption.rs` implements `Debug` **manually** (encryption.rs:410-419) specifically to exclude the private `enc_key`, while `EncryptedMessage` deliberately does *not* derive `Debug` and `EncryptedMessage::msg` is `Zeroizing`. The DKG/FROST secret-share types are held to the opposite, unsafe standard.

Contrast: an attacker-controlled participant sending malformed `read_preprocess`/`read_share`/`Commitments::read` bytes that trip an assertion or error path in the DKG/signing flow produces a panic/error whose `Debug` payload includes the victim's `secret_share` verbatim — the same "full secret in failure output" shape as the Oxia token-in-logs bug.

### Impact Explanation
Recovery of a participant's FROST `secret_share` (or `enc_key` if reachable via generic error formatting) allows a threshold-subverted attacker — or, combined with the already-known structure of the scheme, anyone who obtains `t-1` other shares — to reconstruct the group private key. Even short of full reconstruction, the leaked share removes the secret-hiding assumption the DKG's blame and share-verification protocols rely on. The secret appears in plaintext in panic messages, error chains (`anyhow`/`thiserror` `{:?}` formatting), and any `tracing`/log capture of the offending struct — precisely the CWE-532 channel.

### Likelihood Explanation
High conditional on an error path being hit. Malicious DKG participants supply attacker-controlled bytes through `EncryptedMessage::read`, `read_share`, and `Commitments::read`; malformed inputs that reach an `assert!`/`assert_eq!`/`.expect(...)`/`{:?}`-formatted `Result` in `dkg/src/lib.rs` or `frost/src/sign.rs` print the containing struct — including `secret_share` — to stderr or the host's panic/log hook. In coordinator/processor deployments that run with `RUST_BACKTRACE` or structured logging of panics, this lands in aggregated logs accessible to operators or attackers with log read access — identical exploitation prerequisites to the Oxia report ("debug logging enabled / log access").

### Recommendation
- Remove `Debug` from `Scalar` and `FieldElement` in `crypto/dalek-ff-group`, `crypto/ed448`, and `crypto/ciphersuite`, or replace with a manual impl that prints a redacted marker (e.g., `Scalar(<redacted>)`).
- Remove/replace the derived `Debug` on `ThresholdCore` and `ThresholdKeys` in `crypto/dkg/src/lib.rs` with a manual impl that formats only `params`, `group_key`, and participant index — never `secret_share`.
- Audit `crypto/frost/src/sign.rs` and `crypto/dkg/pedpop/src/lib.rs` for `assert!`/`assert_eq!`/error types whose `Debug` payloads transitively include secret scalars, and follow the `Encryption::fmt` precedent (encryption.rs:410-419) of manually excluding secret fields.

### Proof of Concept
```rust
// Any code path that Debug-formats a ThresholdCore prints the secret share.
// crypto/dkg/src/lib.rs: ThresholdCore derives Debug; its `secret_share: C::F`
// formats via Scalar's derived Debug (crypto/dalek-ff-group/src/lib.rs:178),
// printing the raw curve25519-dalek Scalar bytes.

let core: ThresholdCore<Ed25519> = /* ... built by dkg::KeyGen ... */;
let leak = format!("{core:?}");        // contains secret_share bytes in plaintext
assert!(leak.contains(&core.secret_share().to_repr().escape_default().to_string())
    || leak.contains("secret_share"));
// Equivalent: panic!("bad preprocess: {core:?}") or assert_eq!(core, other)
// on a malicious-input failure path emits the share verbatim.
```
Note: I could not re-read `crypto/dkg/src/lib.rs` in this iteration to cite the exact `derive(Debug)` line numbers on `ThresholdCore`; the 10 `Debug` matches there and the `Scalar`/`Encryption::fmt` evidence are confirmed. The claim rests on the derived `Debug` on secret-bearing DKG structs — if `ThresholdCore`'s `Debug` is manual and already redacts `secret_share`, the finding degrades to the still-valid primitive-level exposure (`Scalar: Debug` printing secret scalars wherever formatted).
