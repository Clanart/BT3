## Finding: Line-index–based partial-commit selection is silently reapplied to a diff refetched at commit time, decoupling user intent from what's staged

### Title
Selective/partial commit staging reapplies stale line-index selections to a freshly re-fetched diff, allowing silent corruption of committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only some lines of a modified file ("partial commit"), Desktop stores the user's choice as a `DiffSelection` — a set of **line indices** relative to a diff object the user was looking at in the UI. At actual commit time, `applyPatchToIndex` does **not** reuse that diff; it independently re-fetches a brand-new diff via `getWorkingDirectoryDiff` and then reapplies the old, index-based selection onto this new diff via `formatPatch`. There is no check that the new diff has the same hunk/line structure as the one the selection was made against. This is structurally the same invariant violation as the Sherlock report: a piece of state (`_lastUpdateTimestamp` / here, `DiffSelection`'s `divergingLines`) is keyed by a coarse, non-content-bound identifier (a numeric index / `${status.kind}+${path}` file id) instead of the actual content it was computed against, so a concurrent change silently invalidates the semantics of the stored state without anyone noticing.

### Finding Description
- `WorkingDirectoryFileChange.id` is computed purely from `${status.kind}+path` (and `oldPath` for renames), never from a content hash or blob OID: [1](#0-0) 
- The UI keeps a single diff per selected file in `ChangesState.selection.diff`, and validates "is this diff still relevant" only by comparing this coarse file id, not diff content: [2](#0-1) 
- The user's line selection (`DiffSelection`) is stored as index-based diverging line sets, entirely decoupled from the diff object itself: [3](#0-2) 
- At actual staging time, `applyPatchToIndex` re-fetches the diff again from git (a **second**, independent snapshot of the working tree) and blindly builds a patch by reapplying the old selection's line indices to this new diff: [4](#0-3) 
- `formatPatch` walks the (new) diff's hunks and includes/excludes lines purely based on whether their absolute index is in `selection.divergingLines`, with no verification that the new diff has the same hunk boundaries/content as the diff the user actually looked at when selecting lines: [5](#0-4) 

The broken invariant: the selection state (which lines to include/exclude from the commit) is meant to represent the user's *content-level* intent, but it is persisted and consumed as an *index into a diff object* that is not stable across the two independent git invocations (`getWorkingDirectoryDiff` for UI preview vs. `getWorkingDirectoryDiff` for staging). If the tracked file's content changes between these two diff computations — shifting hunk boundaries, adding/removing lines — the stale indices from the earlier diff get silently reapplied to the new hunk layout, exactly as `_lastUpdateTimestamp` in the Sherlock report was reused across periods it was never computed for.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A file that is continuously rewritten by an attacker-controlled mechanism embedded in a cloned/fetched repository (e.g., a `clean`/`smudge` filter defined in `.gitattributes`, a `post-checkout`/`post-merge` hook, or a build tool invoked from repository config that runs in the background) could alter tracked file content between the moment the diff is rendered in Desktop's Changes view (basis for the user's line selection) and the moment `applyPatchToIndex` re-fetches the diff for staging. Because selection is index-based and unchecked against diff identity, the user could:
- Unknowingly commit lines they explicitly deselected (excluded) in the UI.
- Unknowingly exclude lines they explicitly selected, silently dropping intended changes.
- End up creating a hunk-misaligned patch, since `git apply --cached --unidiff-zero` can succeed against nearby but shifted content.

This directly matches the impact class "silent corruption of what the user commits or pushes," with the attacker primitive being a cloned/fetched repository containing a mechanism that mutates working-tree file content asynchronously.

### Likelihood Explanation
The precondition requires the working directory file to actually change content between the two independent `git diff` invocations — the UI-preview fetch and the commit-time re-fetch in `applyPatchToIndex`. This window exists on every partial commit (it's not rare), but a *malicious* content change landing precisely in this window requires the attacker's repository-embedded mechanism (filter/hook/watcher) to race the user's click-to-commit action. This is plausible but not deterministic, making exploitation moderately reliable rather than trivial to guarantee, since I could not fully trace whether Desktop refreshes/re-validates the UI diff again immediately before invoking `applyPatchToIndex` (which could reduce, but not eliminate, the window) — this needs further verification directly in a running app or with deeper tracing through `_commitIncludedChanges`/`createCommit`.

### Recommendation
- Persist and validate partial-commit selections against a content-stable key (e.g., the diff's own hash/oid pair or hunk header signatures), not raw line indices alone.
- Before calling `applyPatchToIndex`, re-diff and compare against the diff the user's selection was made from; if they differ, abort or force the user to re-review before committing.
- Consider computing the patch to apply directly from the *same* diff object shown in the UI (pass it through instead of re-fetching), only falling back to a fresh diff with explicit re-validation of hunk structure.

### Proof of Concept
1. Attacker publishes/hosts a repository containing a `.gitattributes` `clean` filter (or a `post-checkout`/file-watcher script bundled in the repo, e.g. via `direnv`/`husky`/build tooling commonly auto-run on open) that periodically rewrites `important-file.txt` content on disk.
2. Victim clones the repository in Desktop, opens the Changes view; Desktop calls `getWorkingDirectoryDiff` and renders a diff (`app/src/lib/stores/app-store.ts:3444`).
3. Victim selects specific lines to include/exclude via the diff UI, setting `WorkingDirectoryFileChange.selection` (index-based, `app/src/models/diff/diff-selection.ts`).
4. Concurrently, the attacker-controlled mechanism rewrites `important-file.txt`, shifting hunk boundaries.
5. Victim clicks "Commit"; `stageFiles` → `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`) and calls `formatPatch(file, diff)` using the stale, index-based selection (`app/src/lib/patch-formatter.ts:129`).
6. The resulting patch, applied via `git apply --cached`, includes/excludes lines that no longer correspond to what the victim actually reviewed and intended, and the commit is created with silently corrupted content.

Note: I could not fully confirm from the indexed code whether there is an additional diff re-validation step between UI selection and `applyPatchToIndex` invocation (e.g. inside `_commitIncludedChanges`); a Devin session with full repo/terminal access would be needed to trace that call path exhaustively and build a runnable end-to-end reproduction.
