### Title
Relayer fee accumulation trusts unverified `Signature::signer()` for delivery-address attribution - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`Pallet::accumulate` credits relayer fees to whichever address `decode_receipt_relayer` extracts from the destination-chain receipt [1](#0-0) . For substrate destinations, when the stored receipt bytes decode to a `Signature`, the identity is taken via `Signature::signer()` [2](#0-1) . `signer()` simply returns the embedded `public_key`/`address` field of the enum and never checks that the accompanying `signature` bytes are cryptographically valid over any message [3](#0-2) . This is inconsistent with the other signature path in the very same pallet — `Signature::verify()` — which is used for the beneficiary-redirect check just a few lines above and does perform real ECDSA/sr25519/ed25519 verification against a bound message [4](#0-3) . The external report's bug class — two signature-verification code paths for conceptually the same authorization that behave differently, so one can be satisfied without a valid signature — has a direct local analog here.

### Finding Description
`accumulate()` derives the paid-out relayer address for a batch of request commitments from `validate_results`, which calls `Self::decode_receipt_relayer(proof.dest_proof.height.id.state_id, &encoded_receipt)` [1](#0-0) .

For substrate destination chains, `decode_receipt_relayer` decodes the receipt bytes as a `Vec<u8>`; if the length exceeds 32 bytes it is further decoded as a `crypto_utils::verification::Signature` and the delivering relayer's identity is taken from `.signer()`: [2](#0-1)

Notice it just returns the caller-declared `public_key`/`address` field embedded in the `Signature` enum — it performs no call to `sp_io::crypto::sr25519_verify`, `ed25519_verify`, or `secp256k1_ecdsa_recover`. Those cryptographic checks only happen in the sibling method `verify()` [5](#0-4) , which is the method actually used a few lines above in `accumulate()` for the optional beneficiary-redirect signature [4](#0-3) .

So within the same function, two different signature-bearing values are handled with two different trust levels:
- The beneficiary-redirect `Signature` supplied directly in the extrinsic call is cryptographically verified (`verify()`).
- The relayer-identity `Signature` recovered from the proven destination-chain receipt bytes is *not* verified — only its self-declared public key is read (`signer()`).

The destination-chain receipt bytes come from proven state (a genuine Merkle/state proof against the destination's consensus-verified state root), so the value itself is not directly forgeable by the `accumulate()` caller. However, whether that receipt slot's content is *itself* populated from a value that was cryptographically checked on the destination chain, or merely from a raw `signer` field taken at face value when the message was originally delivered/dispatched, was not able to be confirmed with the available tools in the remaining budget — that determination requires tracing the destination-chain message dispatch/receipt-writing code (e.g., in `pallet-ismp`'s message handling), which I did not have iterations left to inspect. If that destination-side write path stores the raw claimed `signer`/`Signature` bytes without independently verifying them (as appears to be the design intent given `decode_receipt_relayer`'s comment "substrate stores the signer bytes **or a signature to recover the signer from**"), then `signer()` being unauthenticated means anyone able to influence that field at delivery time can cause `decode_receipt_relayer` to attribute the fee to an arbitrary chosen public key rather than the true delivering relayer — a direct fund-redirection bug that exactly parallels the external report's "different verification strength on two sides of the same check" pattern.

### Impact Explanation
If the destination-chain receipt content is attacker-influenceable at message-delivery time (a determination I could not fully verify within the tool budget), an attacker could redirect accumulated relayer fees to an address of their choosing without ever proving control of a valid signature, causing direct loss of funds to the legitimate relayer and unauthorized fee claims. Given the sensitivity of `Signature::signer()` being unauthenticated and reused wherever `decode_receipt_relayer` is invoked (it is explicitly documented as being used by "both fee accumulation and the outbound request delivery claim" [6](#0-5) ), this pattern has a wide blast radius across the relayer reward system if the upstream data is not fully authenticated before being stored as a receipt.

### Likelihood Explanation
Moderate-to-uncertain: the vulnerability requires that the raw `signer`/`Signature` bytes committed into the destination-chain `RequestReceipts` value are not independently authenticated by the destination chain before being written (only proven to exist in state, not proven to be honestly derived). I was unable to trace that write path in the remaining time, so likelihood cannot be confirmed as exploitable end-to-end from this analysis alone — but the asymmetry between `verify()` and `signer()` inside the same trust boundary is a concrete, locally-provable code inconsistency independent of that unresolved question.

### Recommendation
- Audit every call site that writes the substrate receipt value consumed by `decode_receipt_relayer` and confirm the embedded `Signature` was authenticated (via `verify()`/`verify_and_get_sr25519_pubkey`) at write time, not merely decoded.
- If receipts can ever contain an unauthenticated `Signature`, change `decode_receipt_relayer`'s substrate branch to call a verifying method (mirroring `messaging-incentives`'s `relayer_for`, which does call `verify_and_get_sr25519_pubkey` [7](#0-6) ) instead of the non-verifying `signer()`.
- Consider removing `Signature::signer()` entirely, or renaming/gating it so it cannot be mistaken for a verified accessor, to prevent this exact class of inconsistency from recurring.

### Proof of Concept
Not able to construct a concrete end-to-end PoC within the remaining tool budget because it depends on confirming whether the destination-chain receipt-writing code path (outside the files reviewed) stores the `signer`/`Signature` bytes without prior verification. The locally provable artifact is the code-level inconsistency itself:
1. `accumulate()` verifies the beneficiary-redirect signature via `Signature::verify()` (cryptographic check) [8](#0-7) .
2. In the same function's call graph, the relayer-identity value used to actually credit fees is obtained via `Signature::signer()`, which performs no cryptographic check at all [3](#0-2) .

A background Devin session with terminal/filesystem access could trace the destination-chain `RequestReceipts` write path (in `pallet-ismp` message handling) to confirm whether attacker-controlled data reaches this field, and construct a full exploit transaction if so.

	pub fn verify(
		&self,
		msg: &[u8; 32],
		public_key_op: Option<Vec<u8>>,
	) -> Result<Vec<u8>, anyhow::Error> {
		match self {
			Signature::Evm { signature, .. } => {
				if signature.len() != 65 {
					Err(anyhow!("Invalid Signature"))?
				}

				let mut sig = [0u8; 65];
				sig.copy_from_slice(&signature);
				let pub_key = sp_io::crypto::secp256k1_ecdsa_recover(&sig, msg)
					.map_err(|_| anyhow!("Signature Verification failed"))?;
				let signer = sp_io::hashing::keccak_256(&pub_key[..])[12..].to_vec();
				Ok(signer)
			},
			Signature::Sr25519 { signature, public_key } => {
				Self::verify_sr25519(signature, public_key, msg, &public_key_op)?;
				Ok(public_key_op.unwrap_or(public_key.clone()))
			},
			Signature::Ed25519 { signature, public_key, .. } => {
				let signature =
					signature.as_slice().try_into().map_err(|_| anyhow!("Invalid Signature"))?;
				let pub_key = public_key_op
					.clone()
					.unwrap_or(public_key.clone())
					.as_slice()
					.try_into()
					.map_err(|_| anyhow!("Invalid Public Key"))?;
				if !sp_io::crypto::ed25519_verify(&signature, msg, &pub_key) {
					Err(anyhow!("Signature Verification failed"))?
				}
				Ok(public_key_op.unwrap_or(public_key.clone()))
			},
		}
	}
