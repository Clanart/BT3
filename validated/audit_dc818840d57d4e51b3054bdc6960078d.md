## Analysis

The report's bug class is: **an event listener trusts and acts on attacker-controlled input without validating/sanitizing it first.** The closest verified analog in this codebase is the deep-link (`x-github-client://…`) handler chain, where the `url` field of an `open-repository-from-url` action is parsed but never validated, unlike its sibling fields.

`parseAppURL` explicitly validates the `pr`, `branch`, and `filepath` query parameters before returning an action, but the `url` value — the actual git remote that will be cloned — is passed through completely unchecked: [1](#0-0) 

Downstream, `filepath` gets a second layer of protection (`isAbsolute` + `resolveWithin`) before being used to touch the filesystem: [2](#0-1) 

But the `url` itself flows straight into `openOrCloneRepository` → `clone()` with no scheme/protocol allowlist. `clone()` does guard against **destination path** traversal (`isClonePathSensitive`) and against **flag injection** by placing the remote after `--`: [3](#0-2) [4](#0-3) 

However, the `--` separator only stops the value from being parsed as a CLI *flag* — it does not stop git from parsing the value as a *URL scheme*. Git supports "remote helper" transports such as `ext::<command>` where the string after `ext::` is executed as a shell command by git itself as part of cloning. Since `parseAppURL` never restricts the accepted schemes (only `http(s)`/`git@`/etc. are exercised in the test suite, none of which reject other schemes), a crafted deep link can smuggle an `ext::` (or similar) URL through this exact path, causing git to execute an arbitrary command during the "clone" step, before any repository content is even inspected. [5](#0-4) 

I was not able to confirm within the available context whether `envForRemoteOperation` (referenced in `clone.ts` line 82) sets `GIT_ALLOW_PROTOCOL` to restrict transports — I could not open `app/src/lib/git/environment.ts` before running out of tool calls. If that file already restricts protocols to `http,https,ssh,git`, this specific `ext::` vector would be mitigated at the environment level; if it does not, the vector is live. This is the one open question in this analysis.

### Title
Unvalidated deep-link `url` value flows into `git clone`, enabling protocol/transport-helper injection - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` sanitizes `branch`, `pr`, and (via a later dispatcher check) `filepath` for the `open-repository-from-url` deep-link action, but never validates or restricts the scheme/format of the `url` field itself before it is used as the actual git remote to clone from.

### Finding Description
When a user clicks an `x-github-client://openRepo/<url>` link, `parseAppURL` extracts `parsedPath` directly as the `url` of an `IOpenRepositoryFromURLAction` with no scheme allowlist or format check [6](#0-5) . `Dispatcher.openRepositoryFromUrl` forwards this value into `openOrCloneRepository`, which eventually calls `clone(url, path, options)` [7](#0-6) . `clone()` protects the *destination path* and blocks *argument injection* by placing `url` after `--` [8](#0-7) , but it does not restrict which git transport/protocol strings are acceptable as the value of `url` itself. This mirrors the report's core defect: the request/message object is acted upon (dispatched to `dispatchURLAction` → `openRepositoryFromUrl` → `clone`) without a sanitize-before-use step for the most security-sensitive field.

### Impact Explanation
If the effective git-transport allowlist is not otherwise enforced, a crafted deep link can cause `git clone` to invoke an external command via a transport-helper scheme (e.g. `ext::`) as soon as the user clicks the link — resulting in arbitrary code execution in the context of the Desktop process, with no repository content ever needing to be trusted or opened.

### Likelihood Explanation
The attack requires only that the victim click a single crafted link (protocol handlers `x-github-client`, `github-mac`, `github-windows` are registered by Desktop) [9](#0-8) [10](#0-9) . No prior authentication, local access, or additional user steps beyond a normal link click are needed, which satisfies the "link/deep link the user clicks" attacker model. Likelihood is moderated only by the unresolved question of whether `envForRemoteOperation` already restricts `GIT_ALLOW_PROTOCOL`.

### Recommendation
Validate and allowlist the `url` field in `parseAppURL` (and/or immediately before `clone()` is invoked) the same way `branch`/`pr`/`filepath` are validated — reject any value that is not a well-formed `http(s)`, `git`, or `ssh`/scp-like remote, and explicitly set `GIT_ALLOW_PROTOCOL` to a safe allowlist (`http,https,ssh,git`) for all clone/fetch operations originating from deep links, regardless of whether it's already set elsewhere.

### Proof of Concept
```
x-github-client://openRepo/ext::sh -c "touch /tmp/pwned"
```
Clicking this link causes `parseAppURL` to produce `{ name: 'open-repository-from-url', url: 'ext::sh -c "touch /tmp/pwned"', branch: null, pr: null, filepath: null }`, which is passed unmodified to `clone()`'s `git clone -- <url> <path>` invocation [8](#0-7) , with the outcome depending on whether `GIT_ALLOW_PROTOCOL` is restricted elsewhere in `envForRemoteOperation` (unverified in this review).

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
