### Title
Fixed `DUST` threshold applied in satoshis ignores the payment's `script_pubkey` size, letting below-dust outputs pass `DustPayment` check - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Buffer `minFee` bug — where a fixed `1e6` threshold was denominated in one token's decimals while being compared against a fee paid in a different-denomination token — `SignableTransaction::new` applies a single hard-coded `DUST = 546` satoshi threshold to every payment, regardless of the size of that payment's `script_pubkey`. Bitcoin's dust rule is not a fixed amount: it scales with the serialized size of the output (plus the cost to spend it). A payment of ≥546 sats is only dust-free for outputs up to a certain script size; for larger scripts, the same 546+ sats is still dust and produces a non-standard output.

### Finding Description
In `SignableTransaction::new` the only validation on payment amounts is:

```rust
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
``` [1](#0-0) 

with `pub const DUST: u64 = 546` justified solely by reference to Bitcoin Core's constant for typical output sizes [2](#0-1) . Yet the code accepts an arbitrary `ScriptBuf` for each payment, and deliberately uses `payment.0.clone()` (the full script) when computing transaction weight [3](#0-2)  — acknowledging script size is variable, while the dust check denies it.

Bitcoin Core's dust rule computes `nSize = serialized_output_size + spend_cost` and requires `value >= 3 * nSize` sat/vB·bytes at the dust relay rate (≈3 sats/byte). For a P2TR output (~43 bytes) this yields 546. For an output with, e.g., a 500-byte script_pubkey, the real dust floor is ~1,600+ sats, but this function accepts 546–1,599 sats and emits the output anyway [4](#0-3) . The same fixed `DUST` gates change-output creation [5](#0-4) , which is also fed a caller-controlled `ScriptBuf`.

Like `runInitialChecks` comparing `totalFee` (in BFR's 18-decimal units) against `minFee` (1e6, calibrated for USDC's 6 decimals), the check here compares `amount` (in satoshis) against `DUST` — a constant only valid for one denomination of the measured quantity (a ~43-byte output script).

### Impact Explanation
`SignableTransaction::new` produces a transaction carrying an output below that output's true dust threshold. Such an output makes the whole transaction non-standard: Bitcoin Core nodes reject it at relay (`dust` policy failure), so the signed transaction never propagates or confirms. Any recipient whose scanner later reports the output "received" holds funds that were never spendable on-chain, and any upstream accounting (e.g., the processor's amortization logic which assumes wallet-level dust checks are authoritative) treats the payment as scheduled/spendable when the network will not accept it. This matches the accepted impact class of "funds reported received that are not spendable" and the original finding's class of a minimum-value check silently satisfied in the wrong units.

### Likelihood Explanation
The `payments` and `change` `ScriptBuf`s are externally supplied arguments to `SignableTransaction::new` — they are untrusted input to this API, not fixed internally. Any flow where a user can cause a payment to a non-P2TR/large-script output (or a caller supplies an oversized change script) with an amount in [546, real_dust) triggers it. It requires no key compromise, no collusion, and no malicious validator — only a public input (the destination script) combined with a payment amount the check wrongly deems sufficient.

### Recommendation
Compute the dust threshold per output from its serialized size instead of a global constant, e.g. `dust(payment) = 3 * (serialized_size_of_TxOut + input_spend_overhead)` per Bitcoin Core's `GetDustThreshold`/`IsDust`, and apply it to both the payments loop and the change-output branch. Reject or re-price payments whose `script_pubkey` pushes their required dust above the constant.

### Proof of Concept
```rust
// A payment whose script_pubkey is large (e.g., an oversized/nonstandard script).
let mut big_script = ScriptBuf::new();
big_script.push_slice([0u8; 500]); // ~500-byte script_pubkey

// 600 sats passes the wallet's check (600 >= DUST == 546)...
let payments = vec![(big_script, 600u64)];
let tx = SignableTransaction::new(inputs, &payments, None, None, fee_per_vbyte)
  .expect("DustPayment not raised");

// ...yet Bitcoin Core's dust floor for this output is
// ~3 * (8 + varint + 500 + spend_overhead) >> 600 sats,
// so the built transaction is non-standard and rejected at relay.
```
The defect is that `*amount < DUST` (send.rs:166) treats 546 as a universal minimum when the real minimum is a function of `payment.0`'s length — the same fixed-constant/wrong-denomination shape as `minFee = 1e6` being applied to an 18-decimal token.
