## Analog Found

### Title
Precompile signature verification loops perform unmetered, expensive cryptographic work while bypassing the compute budget - (File: `program-runtime/src/invoke_context.rs`, `precompiles/src/secp256k1.rs`, `precompiles/src/ed25519.rs`, `precompiles/src/secp256r1.rs`)

### Summary
Unlike every other instruction executed on the SVM, precompile instructions (`secp256k1`, `ed25519`, `secp256r1`) are dispatched through `InvokeContext::process_precompile`, which never touches `invoke_context.compute_meter`. The actual signature-verification loops in `precompiles/src/secp256k1.rs`, `precompiles/src/ed25519.rs`, and `precompiles/src/secp256r1.rs` iterate over a caller-controlled `num_signatures`/`count` field and perform expensive cryptographic operations (`libsecp256k1::recover`, `ed25519_dalek` strict verification, OpenSSL ECDSA verification over secp256r1) per iteration — but the cost of these operations is never deducted from the transaction's compute budget at execution time. This mirrors the reported bug class: an externally-influenced, per-iteration expensive operation performed in a loop whose real cost is not actually charged against the caller, creating an underpriced work amplification vector.

### Finding Description
`InvokeContext::process_message` special-cases precompile program IDs: [1](#0-0) 

For non-precompile instructions, `process_instruction` → `process_executable_chain` measures compute unit consumption via `self.get_remaining()` before/after execution and even asserts that builtins *must* consume compute units: [2](#0-1) 

However, `process_precompile` takes a completely different path — it pushes a stack frame, calls the `epoch_stake_callback.process_precompile(...)` (which ultimately calls the `verify()` functions in the `precompiles` crate), and pops — with **no interaction with `compute_meter` at all**: [3](#0-2) 

The actual verification loops iterate over a data-supplied count and perform real cryptographic work per iteration, with no calls to `invoke_context.compute_meter.consume_checked(...)`:
- `secp256k1`: loop up to `count` (u8, max 255) times, each doing a `libsecp256k1::recover` + Keccak hash: [4](#0-3) 
- `ed25519`: loop up to `num_signatures` (u8, max 255) times, each doing `ed25519_dalek` strict verification: [5](#0-4) 
- `secp256r1`: loop up to 8 times, each doing OpenSSL EC point parsing + ECDSA verification: [6](#0-5) 

The `cost-model` crate does compute `SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, and `SECP256R1_VERIFY_COST` per signature: [7](#0-6)  — but this is only used for block-level cost-tracking/scheduling estimates (`cost-model/src/block_cost_limits.rs`), not as an actual compute-meter deduction enforced during instruction execution inside the SVM. The runtime execution path that actually performs the CPU-intensive verification work never consumes from the transaction's declared `compute_unit_limit`.

### Impact Explanation
Because the compute meter is never charged for the real, per-signature cryptographic cost, a transaction can pack multiple precompile instructions (each with the maximum allowed signature count) and force validators to perform substantial CPU work (elliptic-curve recovery/verification) that is not reflected in, and not bounded by, the transaction's compute budget. This decouples "declared/priced compute" from "actual work performed" — exactly the underpriced/unbounded-external-work class from the report — and can be used to make transaction processing disproportionately expensive relative to what the fee/compute-budget mechanism accounts for, which is a materially underpriced compute vector.

### Likelihood Explanation
Any transaction can include `secp256k1`, `ed25519`, or `secp256r1` precompile instructions with attacker-chosen offsets, up to the per-instruction signature count limits (255 for secp256k1/ed25519, 8 for secp256r1), constrained only by the ~1232-byte transaction size limit and instruction count limits — no special privileges are required to construct and submit such a transaction.

### Recommendation
Charge `invoke_context.compute_meter` inside `process_precompile` (or inside each `verify()` implementation) proportionally to the number of signatures actually processed, using the same per-signature costs already defined in `cost-model/src/block_cost_limits.rs` (`SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST`), and enforce the `BuiltinProgramsMustConsumeComputeUnits`-style invariant for precompiles as is already done for ordinary builtins in `process_executable_chain`.

### Proof of Concept
Construct a transaction containing several `secp256k1_program`/`ed25519_program`/`secp256r1_program` instructions, each with the maximum permitted signature count and offsets crafted to point at a minimal shared signature/pubkey/message slice (to maximize count within the transaction size limit). Submit with a low `compute_unit_limit`. Observe via `program-runtime/src/invoke_context.rs`'s `process_precompile` path that no compute units are deducted for the verification work performed in `precompiles/src/secp256k1.rs`, `ed25519.rs`, and `secp256r1.rs`, despite the validator performing the full cryptographic verification workload.

            .map_err(|_| PrecompileError::InvalidSignature)?;
        let s_bignum = BigNum::from_slice(&signature[FIELD_SIZE..])
            .map_err(|_| PrecompileError::InvalidSignature)?;

        // Check that the signature is generally in range
        let within_range = r_bignum >= one
            && r_bignum <= order_minus_one
            && s_bignum >= one
            && s_bignum <= half_order;

        if !within_range {
            return Err(PrecompileError::InvalidSignature);
        }

        // Create an ECDSA signature object from the ASN.1 integers
        let ecdsa_sig = openssl::ecdsa::EcdsaSig::from_private_components(r_bignum, s_bignum)
            .and_then(|sig| sig.to_der())
            .map_err(|_| PrecompileError::InvalidSignature)?;

        let public_key_point = EcPoint::from_bytes(&group, pubkey, &mut ctx)
            .map_err(|_| PrecompileError::InvalidPublicKey)?;
        let public_key = EcKey::from_public_key(&group, &public_key_point)
            .map_err(|_| PrecompileError::InvalidPublicKey)?;

            .update(message)
            .map_err(|_| PrecompileError::InvalidSignature)?;

        if !verifier
            .verify(&ecdsa_sig)
            .map_err(|_| PrecompileError::InvalidSignature)?
        {
            return Err(PrecompileError::InvalidSignature);
        }
