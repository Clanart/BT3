### Title
Attacker-controlled `WWW-Authenticate` realm on any HTTP git remote triggers a real GitHub Enterprise sign-in flow for an untrusted host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The credential-helper trampoline classifies a remote host as GitHub-flavored based partly on the `WWW-Authenticate` header the remote server itself returns during a git HTTP auth challenge. Git forwards that header to the credential helper as `wwwauth[]` entries, and Desktop trusts the literal string content of that header (`realm="GitHub"`) to mark the endpoint as `'enterprise'`, which then causes Desktop to pop up its real GitHub Enterprise **sign-in flow** (OAuth/PAT) pointed at that attacker-controlled origin.

### Finding Description
`getEndpointKind()` iterates over the credential input looking for `wwwauth[` keys and returns `'enterprise'` purely because the header value contains the substring `realm="GitHub"`: [1](#0-0) 

This value originates entirely from the remote git server's HTTP response (a header value git forwards verbatim to the credential helper) — i.e., it is attacker-controlled whenever the user adds/clones/fetches from a malicious or compromised HTTPS remote (or is MITM'd via a malicious proxy), which is exactly the "git remote/proxy response" primitive this task allows.

When `getCredential()` sees `endpointKind !== 'generic'` and no existing account matches that endpoint, it calls `ui.promptForGitHubSignIn(endpoint)`: [2](#0-1) 

`promptForGitHubSignIn` then drives Desktop's real sign-in UI, and for any non-`github.com` hostname it calls `beginEnterpriseSignIn` and `setSignInEndpoint(origin)` using the attacker-supplied `origin` as the actual OAuth/API endpoint Desktop will talk to: [3](#0-2) 

No validation is performed that the attacker's host is actually a genuine GitHub Enterprise Server before wiring it into the enterprise sign-in flow — the only "gate" is a self-reported HTTP header from the same untrusted server. This mirrors the escrow bug's broken invariant: a sensitive, trust-establishing action (`approveAll` there; "this is a legitimate GitHub Enterprise endpoint, begin the sign-in/token flow" here) is gated only by an attacker-supplied value rather than by an independent, protocol-level trust boundary.

### Impact Explanation
This does not require any prior malware, local access, or leaked credentials — only the user pointing Desktop at (cloning/adding as remote/fetching from) an attacker-controlled or MITM'd HTTPS git server, which is entirely within the "unprivileged, attacker controls a git remote/proxy response" impact scope. The practical harm:
- The application surfaces its legitimate-looking GitHub sign-in dialog for a host chosen by the attacker, which real users routinely trust because it is presented as Desktop's own native UI, increasing the odds a user completes an OAuth/PAT flow that hands a token (their real GitHub PAT if they paste one, or an enterprise PAT/OAuth code) to the attacker's endpoint — this is "unauthorized OAuth or account binding," one of the explicitly valid impacts.
- Because `setSignInEndpoint(origin)` sets the endpoint Desktop treats as authoritative for the sign-in session, subsequent account/token handling is bound to the attacker's origin rather than a vetted GHE instance.

### Likelihood Explanation
Likelihood is moderate: the only requirement is that a git HTTP server the user connects to (any remote add/clone/fetch/push over HTTPS) returns a `WWW-Authenticate` header whose value contains `realm="GitHub"` on a 401 challenge — a single header line fully controlled by the server operator, not requiring any special git or Desktop configuration on the victim's side, and triggered automatically the first time Desktop's credential helper is invoked for that remote (`getCredential` → `getEndpointKind`).

### Recommendation
Do not use a self-reported `WWW-Authenticate` realm string as sufficient evidence that a host is a GitHub/GHE instance for the purpose of initiating the sign-in flow. Require an independent check (e.g., the existing `isGitHubHost()` API probe already used later in `getEndpointKind`) before trusting the `wwwauth[]` heuristic, or at minimum surface the actual remote hostname prominently in the sign-in popup and require explicit user confirmation that this exact untrusted host should be treated as a GitHub Enterprise endpoint, rather than silently calling `beginEnterpriseSignIn`/`setSignInEndpoint` on the raw origin.

### Proof of Concept
1. Stand up an HTTPS git server (e.g. behind `git http-backend` or a custom proxy) at `https://evil.example.com/attacker/repo.git`.
2. Configure the server to answer any git-over-HTTP request with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. In GitHub Desktop, clone or add this URL as a remote and trigger a fetch/push.
4. Git invokes Desktop's credential helper (`createCredentialHelperTrampolineHandler`); `getCredential` calls `getEndpointKind`, which sees the `wwwauth[0]` value containing `realm="GitHub"` and returns `'enterprise'`. [1](#0-0) 
5. Since no stored account matches `https://evil.example.com`, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com/...')`. [2](#0-1) 
6. `promptForGitHubSignIn` opens Desktop's real "Sign in to GitHub Enterprise" popup and calls `setSignInEndpoint('https://evil.example.com')`, wiring the attacker's origin into the enterprise OAuth/PAT sign-in flow. [4](#0-3)

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
