### Title
Unauthenticated PedPoP share keys trigger ECDH blame proofs and leak victim shares - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
`EncryptedMessage` accepts an attacker-controlled ephemeral key, Schnorr proof-of-possession, and ciphertext. [1](#0-0)  `Encryption::decrypt` only queues the proof-of-possession for batch verification, then immediately calculates the ECDH secret and returns an `EncryptionKeyProof` containing it. [2](#0-1)  `KeyMachine::calculate_share` returns that proof before batch verification if the decrypted share encoding is non-canonical. [3](#0-2) 

### Finding Description
The implementation explicitly intends the per-message PoP to stop an attacker from copying a victim message’s public key and inducing a blame proof that reveals the shared ECDH key. [4](#0-3)  The PoP challenge binds the context, claimed sender, ephemeral key, signature nonce, and ciphertext. [5](#0-4)  However, `decrypt` defers that check through `batch_verify` and still decrypts the untrusted ciphertext and constructs a proof for `enc_key * msg.key`. [2](#0-1) 

`SecretShare::read` accepts any fixed-width field representation as ciphertext, so the attacker can choose arbitrary bytes for the encrypted payload. [6](#0-5)  If decrypting those bytes produces a non-canonical scalar encoding, `calculate_share` returns `PedPoPError::InvalidShare { blame: Some(proof) }` without ever calling the batch verifier that would reject the copied PoP. [7](#0-6)  The returned proof serializes the shared ECDH point as its first field and carries a DLEq proof tying it to the recipient’s encryption key and copied message key. [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker who observes a victim’s encrypted share `X || R_v || s_v || C_v` can submit a forged share reusing `X` with an invalid PoP and arbitrary ciphertext bytes. [10](#0-9)  The victim’s node returns a proof containing `bX`, where `b` is the recipient’s registered encryption private key and `X` is the copied per-message key. [11](#0-10)  Because the message cipher is derived directly from that ECDH point, `bX` decrypts the originally observed victim ciphertext and recovers the victim’s PedPoP secret share. [12](#0-11)  This defeats the confidentiality and per-message blame isolation that the DKG encryption layer is designed to provide. [13](#0-12) 

### Likelihood Explanation
The attack only requires the ability to observe another participant’s encrypted-share message and to submit an attacker-controlled `EncryptedMessage` to `calculate_share`. [14](#0-13)  No valid proof-of-possession or knowledge of the copied key’s discrete logarithm is needed because verification is bypassed by the early non-canonical-share return. [15](#0-14) [16](#0-15)  For Ristretto’s 252-bit scalar field represented in 32 bytes, an effectively random decrypted encoding is non-canonical with probability approximately 15/16, and failed attempts can be retried across DKG attempts. [17](#0-16) 

### Recommendation
Do not release an `EncryptionKeyProof` before the message PoP has been verified. Verify `msg.pop` synchronously before ECDH/decryption, or keep the generated proof inaccessible until the batch verifier confirms that no queued `BatchId::Decryption` failed. `calculate_share` must not return `blame: Some` on a canonicalization error while an unverified PoP for the same message is pending. [2](#0-1) [18](#0-17) 

### Proof of Concept
```text
Observed victim message:
  victim = X || R_v || s_v || C_v

Forged message sent to the victim’s DKG participant:
  forged = X || R_a || s_a || C_a

where:
  X   = copied encoded ephemeral key from victim
  R_a = any valid non-identity point encoding
  s_a = any canonical scalar encoding
  C_a = arbitrary SecretShare-sized bytes
```

`EncryptedMessage::read` accepts this layout without checking whether the sender knows the discrete logarithm behind `X`. [1](#0-0)  The recipient queues, but does not immediately evaluate, the PoP and derives `K = bX`. [15](#0-14)  When `C_a XOR keystream(K)` is non-canonical, `calculate_share` returns an `InvalidShare` error containing the serialized `EncryptionKeyProof`, exposing `K`. [16](#0-15)  The attacker parses the first point from `proof.serialize()` and computes `C_v XOR keystream(K)`, yielding the victim’s original secret share. [19](#0-18) [20](#0-19)

/// without side effects.
#[derive(Clone, Zeroize)]
pub struct EncryptedMessage<C: Ciphersuite, E: Encryptable> {
  key: C::G,
  // Also include a proof-of-possession for the key.
  // If this proof-of-possession wasn't here, Eve could observe Alice encrypt to Bob with key X,
  // then send Bob a message also claiming to use X.
  // While Eve's message would fail to meaningfully decrypt, Bob would then use this to create a
  // blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob.
  // This is a massive side effect which could break some protocols, in the worst case.
  // While Eve can still reuse their own keys, causing Bob to leak all messages by revealing for
  // any single one, that's effectively Eve revealing themselves, and not considered relevant.

fn ecdh<C: Ciphersuite>(private: &Zeroizing<C::F>, public: C::G) -> Zeroizing<C::G> {
  Zeroizing::new(public * private.deref())

// Each ecdh must be distinct. Reuse of an ecdh for multiple ciphers will cause the messages to be
// leaked.
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res

  pub fn calculate_share<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
    mut shares: HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>,
  ) -> Result<BlameMachine<C>, PedPoPError<C>> {
    validate_map(
      &shares,
      &self.params.all_participant_indexes().collect::<Vec<_>>(),
      self.params.i(),
    )?;

    let mut batch = BatchVerifier::new(shares.len());
    let mut blames = HashMap::new();
    for (l, share_bytes) in shares.drain() {
      let (mut share_bytes, blame) =
        self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
      let share =
        Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
          PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
        })?);
      share_bytes.zeroize();
      *self.secret += share.deref();

      blames.insert(l, blame);
      batch.queue(
        rng,
        BatchId::Share(l),
        share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share),
      );
    }
    batch.verify_with_vartime_blame().map_err(|id| {
      let (l, blame) = match id {
        BatchId::Decryption(l) => (l, None),
        BatchId::Share(l) => (l, Some(blames.remove(&l).unwrap())),
      };
      PedPoPError::InvalidShare { participant: l, blame }
    })?;
