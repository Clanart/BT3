### Title
Unbounded caller-controlled fee rate can burn nearly all Bitcoin inputs as miner fees - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary

`SignableTransaction::new` accepts `fee_per_vbyte` without enforcing any upper bound. Although it checks that the calculated fee is at least the minimum relay rate, an arbitrarily high rate is accepted whenever the inputs can cover it. If no change output is supplied, the constructed transaction intentionally leaves every excess satoshi as a fee and the resulting transaction is passed to the threshold-signing machines.

### Finding Description

The external report’s relevant bug class is a numeric rate/configuration value being applied to funds without an absolute upper bound.

The analogous behavior exists in `SignableTransaction::new`:

- `fee_per_vbyte` is a public caller-controlled parameter. [1](#0-0) 
- The constructor only rejects zero-output transactions, dust payments, oversized data, and fees below the minimum relay rate. It never caps the maximum fee or fee rate. [2](#0-1) 
- `needed_fee` is calculated as `fee_per_vbyte * vbytes`, with no checked multiplication and no upper-bound comparison. [3](#0-2) 
- The only fund check verifies that `input_sat` covers `payment_sat + needed_fee`. [4](#0-3) 
- The API explicitly states that if no change address is provided, all leftover funds become the paid fee. [5](#0-4) 
- The resulting transaction is then committed to through Taproot sighashes using `Prevouts::All` and threshold-signed. [6](#0-5) 

Thus, an excessive `fee_per_vbyte` is not merely recorded as metadata: it directly changes the signed transaction’s output set. When `change` is `None`, `input_sat - payment_sat` becomes the effective miner fee.

The fee multiplication is also unchecked. In debug builds, an overflowing `fee_per_vbyte * vbytes` can panic; in builds without overflow checks, it can wrap and produce an incorrect `needed_fee`. A separate unchecked `payment_sat + needed_fee` can likewise overflow before the funds comparison.

### Impact Explanation

A malicious or compromised party able to supply `fee_per_vbyte` can cause the multisig to sign a transaction paying almost the entire input value as a transaction fee rather than returning it as change.

This is an unintended transaction-signing/funds-loss condition, not merely denial of service. For example, with a 1 BTC input and one minimal payment, an extreme fee rate can produce a transaction with only the payment output and no change output. The transaction is internally valid and spends approximately `1 BTC - payment_amount` to miners.

The wrapping arithmetic additionally allows the recorded `needed_fee` to differ from the transaction’s actual fee. `SignableTransaction::fee` recomputes the fee from inputs minus outputs, so the signed transaction can burn substantially more than `needed_fee`. [7](#0-6) 

### Likelihood Explanation

The condition requires the attacker to influence `fee_per_vbyte` and for the transaction construction to omit a change output. The function itself provides no defense-in-depth against either accidental or maliciously large values.

The threshold signers do not independently reconstruct or bound the fee inside `TransactionSignMachine::sign`; they sign the sighash of the already-constructed transaction. [8](#0-7) 

### Recommendation

Add explicit fee sanity and overflow checks in `SignableTransaction::new`:

1. Use `checked_mul` for `fee_per_vbyte * vbytes`.
2. Use `checked_add` for `payment_sat + needed_fee`.
3. Enforce a maximum fee rate and/or maximum absolute fee.
4. Prefer requiring a change output whenever the residual exceeds a small dust threshold.
5. Compare the actual transaction fee against `needed_fee` before returning the signable transaction, and reject excessive differences.

Conceptually:

```rust
let needed_fee = fee_per_vbyte
  .checked_mul(vbytes)
  .ok_or(TransactionError::FeeOverflow)?;

if fee_per_vbyte > MAX_REASONABLE_FEE_PER_VBYTE {
  return Err(TransactionError::TooHighFee);
}

let required = payment_sat
  .checked_add(needed_fee)
  .ok_or(TransactionError::FeeOverflow)?;

if input_sat < required {
  return Err(TransactionError::NotEnoughFunds {
    inputs: input_sat,
    payments: payment_sat,
    fee: needed_fee,
  });
}
```

### Proof of Concept

```rust
use bitcoin::ScriptBuf;
use bitcoin_serai::wallet::{SignableTransaction, ReceivedOutput};

fn excessive_fee_burns_inputs(input: ReceivedOutput, payment_script: ScriptBuf) {
  // Suppose input.value() == 100_000_000 sats.
  let payments = vec![(payment_script, 546)];

  // A wildly excessive, caller-supplied fee rate.
  // For a typical transaction of ~100-200 vbytes, this consumes millions of sats.
  let tx = SignableTransaction::new(
    vec![input],
    &payments,
    None,              // No change output
    None,
    10_000,            // sats/vbyte; no upper bound is enforced
  )
  .unwrap();

  // The transaction has only the payment output.
  assert_eq!(tx.transaction().output.len(), 1);

  // Actual fee is input value minus the payment output, not merely
  // an amount semantically validated as reasonable.
  assert!(tx.fee() > tx.needed_fee() || tx.fee() > 1_000_000);
}
```

A larger caller-supplied rate can raise the burned amount up to nearly the entire input value while still passing the current checks.
