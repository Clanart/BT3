### Title
Unvalidated on-chain DataLayer mirror URLs cause SSRF-style outbound HTTP requests from DataLayer node - (File: chia/data_layer/download_data.py)

### Summary
DataLayer mirror URLs are published entirely as attacker-controlled on-chain data (coin memos) and are later dereferenced by the local DataLayer service with a plain `aiohttp` GET/POST and no destination validation, mirroring the SSRF pattern in CVE-2020-1925 (Apache Olingo blindly following a `Location` URL).

### Finding Description
Any coin spent to the mirror puzzle hash is picked up by `DataLayerWallet.coin_added()`, which decodes `launcher_id` and `urls` straight from the spend's memos and persists them via `dl_store.add_mirror()` as long as the launcher is tracked by this node — there is no check that the spender is the store owner or that the URL is well-formed/safe: [1](#0-0) 

The DataLayer service later reads these mirror URLs verbatim from wallet RPC and feeds them into the local subscription/server list with no allow-list or scheme/host filtering: [2](#0-1) 

During sync, `fetch_and_validate()` iterates these server URLs and passes them into the download pipeline: [3](#0-2) 

Finally, `http_download()` performs an unauthenticated `aiohttp.ClientSession.get()` directly against `server_info.url`, i.e. the attacker-chosen string, with no restriction on scheme, host, or IP range (no blocking of loopback/link-local/internal ranges): [4](#0-3) 

This is functionally the same bug class as CVE-2020-1925: a value taken from an untrusted, externally-influenced channel (there, an HTTP `Location` header; here, on-chain mirror-coin memos) is used verbatim as the target of a new outbound HTTP request by the client process, without validating that the target is a legitimate/external resource.

### Impact Explanation
Any user who can create a coin with the mirror puzzle hash (which is a permissionless, cheap on-chain action — a normal wallet spend, no special DataLayer ownership required) can cause any node that subscribes to that store to issue outbound HTTP GET/POST requests to a URL of the attacker's choosing. This can be used to probe or interact with services on the DataLayer node's internal network (e.g., localhost admin endpoints, cloud metadata endpoints such as `169.254.169.254`, or other RPC ports), a classic SSRF impact. It does not directly move coins or forge assets, but it grants a remote, unauthenticated party a request-forgery primitive against the DataLayer host's network perimeter, satisfying "Medium/High" severity for a spend-triggered SSRF against an unprivileged, permissionless attack surface.

### Likelihood Explanation
Likelihood is high for any node that runs DataLayer and subscribes to third-party-created stores (the intended primary use case): mirror-coin creation requires no special permission beyond paying a small fee, and the resulting URL is dereferenced automatically by the periodic sync loop (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`) without any operator interaction or confirmation.

### Recommendation
- Validate mirror URLs before they are persisted/dereferenced: enforce `http(s)` scheme only, reject loopback/link-local/private/multicast/metadata IP ranges (and hostnames resolving to them) at request time, similarly to standard SSRF mitigations.
- Consider requiring DNS resolution and re-validating the resolved IP immediately before connecting (to avoid DNS-rebinding TOCTOU), and disabling `aiohttp` redirect-following for mirror/plugin requests unless the target is re-validated after each hop.
- Apply the same validation to `PluginRemote`/downloader/uploader URLs sourced from configuration if they can ever be influenced by external data.

### Proof of Concept
1. Attacker crafts and broadcasts a standard coin spend that creates a coin with `puzzle_hash == create_mirror_puzzle().get_tree_hash()`, using memos encoding an arbitrary `launcher_id` (any store id the target node is subscribed to) and a URL such as `http://169.254.169.254/latest/meta-data/` or `http://127.0.0.1:<internal-port>/`.
2. Once the transaction confirms, `DataLayerWallet.coin_added()` on any node tracking that `launcher_id` decodes and stores the mirror record (`chia/data_layer/data_layer_wallet.py:775-800`).
3. On the next `periodically_manage_data()` cycle, `update_subscriptions_from_wallet()` (`chia/data_layer/data_layer.py:979-985`) pulls this URL into the subscription's server list.
4. `fetch_and_validate()` (`chia/data_layer/data_layer.py:642-705`) selects this server and calls `insert_from_delta_file()` → `download_file()` → `http_download()` (`chia/data_layer/download_data.py:298-320`), causing the DataLayer node to issue an outbound HTTP request to the attacker-chosen internal/loopback URL.

Note: I was unable to fully inspect `create_mirror_puzzle`/`get_mirror_info` in `chia/wallet/db_wallet/db_wallet_puzzles.py` within the available tool budget to confirm there is no additional gating beyond puzzle-hash matching; the mirror-creation and URL-dereference flow shown above, however, is directly confirmed from `data_layer_wallet.py`, `data_layer.py`, and `download_data.py`.

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
