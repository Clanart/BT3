### Title
Unenforced 0–10,000 bps invariant on vote commission fields, deferred to a downstream consumer that doesn't clamp - ([File: programs/vote/src/vote_state/handler.rs])

### Summary
The Masset report describes a value (`colRatio`) that is supposed to satisfy an invariant (≥100%) but the setter has no validation — the invariant is only informally guaranteed by the privileged caller (the governor), while the consumer (`_redeemTo`) trusts it blindly, allowing disproportionate redemption if the invariant is violated. The Agave analog is the vote program's commission-in-basis-points fields (`inflation_rewards_commission_bps`, `block_revenue_commission_bps`), which are documented and tested as being storable outside their valid `0..=10_000` (0–100%) range, with the enforcement of the range explicitly deferred to specific downstream consumers rather than the setter.

### Finding Description
`VoteStateHandler::set_inflation_rewards_commission_bps` and `set_block_revenue_commission_bps` write the caller-supplied `u16` directly into `VoteStateV4` with no range check: [1](#0-0) 

`update_commission_bps` (invoked by the `UpdateCommissionBps` vote instruction) forwards the instruction's `commission_bps: u16` argument straight to these setters after only checking the authorized-withdrawer signature — there is no bound/clamp check on the value itself: [2](#0-1) 

This is explicitly confirmed by the unit test, which documents the design decision that out-of-range values are accepted at the storage layer and that clamping is deferred to reward calculation: [3](#0-2) 

The one consumer that is known to clamp is `commission_split`/`commission_split_preserve_lamports`, used in staking-reward distribution, which explicitly does `commission_bps.min(10_000)`: [4](#0-3) 

This mirrors the Masset bug precisely: the invariant ("commission_bps must be ≤10,000, i.e. ≤100%") is not enforced where the value is set (`update_commission_bps`/`set_*_commission_bps`), and is instead informally relied upon to be respected, with only one specific consumer (`commission_split`) adding an explicit `.min(10_000)` guard as a defensive clamp — exactly analogous to how `_redeemTo` in Masset relies on the governor never setting `colRatio` below 100% instead of validating it at the point of use.

The `block_revenue_commission_bps` field carries the same unvalidated-at-storage risk, but no downstream consumer that clamps it was found in the reachable code paths, unlike `inflation_rewards_commission_bps` which is clamped by `commission_split`. If a future or currently-unindexed consumer of `block_revenue_commission_bps` computes a split via un-clamped basis-points math (e.g. `amount * commission_bps / 10_000` without `.min(10_000)`), a withdrawer that sets `commission_bps > 10_000` could cause a commission split that exceeds 100% of the distributed amount, i.e. an over-payment/over-allocation beyond the total funds being split — the same disproportionate-payout class of bug as the Masset finding.

### Impact Explanation
If any commission-consuming code path (present or future) uses `inflation_rewards_commission_bps` or `block_revenue_commission_bps` without an explicit `.min(10_000)` clamp, an authorized withdrawer (a normal, unprivileged-at-cluster-level vote account holder — not a validator/cluster trust role) could set the commission to a value above 10,000 bps, causing the split arithmetic to allocate more than 100% of a reward/revenue amount to the commission collector. This would constitute fund misallocation. Because only one of the two commission fields (`inflation_rewards_commission_bps`) was confirmed to have a defensive clamp in the reachable code, the risk is concentrated in `block_revenue_commission_bps` consumers, which could not be located/verified in the indexed code within the search budget available.

### Likelihood Explanation
Likelihood is data-dependent: it requires (1) the authorized withdrawer setting an out-of-range commission (self-inflicted, and only harms/benefits the vote account's own collector/delegators, not third parties, unless computation feeds into cross-account transfers), and (2) a consumer that omits the clamp that `commission_split` applies. This is lower confidence than the original Masset finding because the primary reward-splitting path found (`commission_split`) does clamp correctly; the risk is only confirmed as a structural pattern (unenforced invariant at the setter, enforcement pushed to callers) rather than as a demonstrated exploitable overpayment path for `block_revenue_commission_bps`.

### Recommendation
Enforce `commission_bps <= 10_000` directly in `update_commission_bps` (or in the `set_inflation_rewards_commission_bps`/`set_block_revenue_commission_bps` setters), returning `InstructionError::InvalidInstructionData` for out-of-range values, rather than relying on individual downstream consumers to clamp. Audit every consumer of `block_revenue_commission_bps` to confirm all of them clamp to `10_000` before use, matching the guard already present in `commission_split`/`commission_split_preserve_lamports`.

### Proof of Concept
1. Withdrawer submits `VoteInstruction::UpdateCommissionBps { commission_bps: 65535, kind: CommissionKind::BlockRevenue }` on a `VoteStateV4` account with `block_revenue_sharing` feature active.
2. `update_commission_bps` accepts and stores `65535` with no bound check [5](#0-4) , consistent with the documented behavior in the unit test [6](#0-5) .
3. Any subsequent block-revenue distribution logic that computes `collector_share = amount * block_revenue_commission_bps / 10_000` without an explicit `.min(10_000)` clamp (unlike the verified `commission_split` clamp for the inflation-rewards path) would allocate `collector_share > amount`, over-allocating funds — the disproportionate-payout condition analogous to Masset's `_redeemTo`.

Note: I was unable to fully verify the internal implementation of `deposit_delegator_rewards`/the `block_revenue_commission_bps` split arithmetic within the available search iterations — the index returned only the instruction dispatch site, not the full split-computation body. This is a genuine investigative gap; the finding above is confirmed at the setter/invariant level (documented lack of validation) but the exploitability specifically for `block_revenue_commission_bps` should be verified against the full split arithmetic before treating this as fully confirmed.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
