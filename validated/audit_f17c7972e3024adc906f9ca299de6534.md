### Title
Stale Nested Oneof Message Builder Causes Field-Content/Case Desynchronization During Sequential Builder-API Parsing - ([File: src/google/protobuf/compiler/java/full/message_field.cc])

### Summary
In generated Java `Message.Builder` code for a message-typed field inside a `oneof`, the lazily-created nested `SingleFieldBuilder` (`$name$Builder_`) is cached for the lifetime of the enclosing `Builder` object and is only (re-)initialized when it is `null`. The `oneof` case tracking variable (`$oneof_name$Case_`) is updated independently, on every parse of that field's tag, inside `internalGet$capitalized_name$FieldBuilder()` and again after `input.readMessage(...)`. Because the case variable and the cached nested builder's contents are two separate pieces of state that are supposed to stay in lock-step but are synchronized by different code paths at different times, an attacker who supplies a crafted sequence of tags for the same message can cause the `oneof` case to reflect one field while the nested builder object underneath it still carries residual data written while the case pointed at a *different* field selection state. This mirrors the SMF `Profile::load()` bug class: two related state variables (`Profile::$member` data vs. `User::$me->is_owner`/case) are updated on different schedules by different call sites, and the consuming logic trusts the later-updated flag while acting on the earlier, unsynchronized data.

### Finding Description
`ImmutableMessageOneofFieldGenerator::GenerateBuilderInternalGetFieldBuilderMethod` emits: [1](#0-0) 

```java
private SingleFieldBuilder<Foo, Foo.Builder, FooOrBuilder> internalGetFooFieldBuilder() {
  if (fooBuilder_ == null) {
    if (!(oneofCase_ == FOO_NUMBER)) {
      foo_ = Foo.getDefaultInstance();
    }
    fooBuilder_ = new SingleFieldBuilder<>(foo_, getParentForChildren(), isClean());
    foo_ = null;
  }
  switch (oneofCase_) {
    default: clearFooHasBits(); // fallthrough
    case 0: oneofCase_ = FOO_NUMBER; setHasFieldBit(); // fallthrough
    case FOO_NUMBER: break;
  }
  onChanged();
  return fooBuilder_;
}
```

The wire-parsing helper for this field then does: [2](#0-1) 

```java
private void parseFoo(CodedInputStream input, ExtensionRegistryLite extensionRegistry) throws IOException {
  input.readMessage(internalGetFooFieldBuilder().getBuilder(), extensionRegistry);
  switch (oneofCase_) {
    default: clearFooHasBits(); // fallthrough
    case 0: oneofCase_ = FOO_NUMBER; setHasFieldBit(); // fallthrough
    case FOO_NUMBER: break;
  }
}
```

The invariant that should hold is: *whenever `oneofCase_` transitions away from `FOO_NUMBER` to any other oneof member and back, the nested `fooBuilder_`'s contents must be reset to reflect "not yet populated"* — exactly analogous to SMF requiring `Profile::$member` and `User::$me->is_owner` to be re-derived together on every profile load. Instead, `fooBuilder_` is guarded only by `fooBuilder_ == null`, so it survives across `oneofCase_` transitions to sibling members of the same oneof and back. `oneofCase_` is the "authorization/ownership" style flag that downstream code (`hasFoo()`, `getFoo()`, `getFooOrBuilder()`, `buildPartial()`) trusts to decide whether the data in `fooBuilder_`/`foo_` is authoritative for the current field, but the flag can be flipped by a later tag in the same input stream *after* the nested builder has already accumulated bytes belonging to an earlier occurrence — and the flip does not force a rebuild of the nested builder object.

Concretely, this is reachable purely through the public parse surface `Message.Builder.mergeFrom(CodedInputStream, ExtensionRegistryLite)` (used transitively by `parseFrom`/`Builder.mergeFrom(byte[])`) with an attacker-controlled bounded binary payload, no privileged access required, matching the "ordinary client sending bounded binary Protobuf" threat model.

### Impact Explanation
If application code relies on `oneof` "last tag wins/merges only within the same case" semantics as an implicit invariant (e.g. treating the currently active case as *the only* data source, or comparing before/after states across parse calls, similar to how SMF trusted `is_owner` derived from an earlier load while acting on `$member` from a later one), a builder object that is silently primed with attacker data from an earlier, now-inactive case can leak into the final built message once the case flips back, because `fooBuilder_.buildPartial()` is invoked unconditionally to populate `result.foo_` whenever the has-bit is set — regardless of whether the builder was freshly created for the *current* activation of that case. This is a data-integrity/consistency issue in generated code shared by every Java message with a `oneof` containing more than one message-typed field, not a memory-safety bug; severity is bounded by "unexpected merge/residue of previously-supplied bytes into the field that is ultimately reported as active," which can cause incorrect trust decisions in application logic layered on top of `oneof` semantics.

### Likelihood Explanation
The trigger requires only a single crafted binary payload with three tags: (1) the message-typed oneof field A, (2) a sibling oneof field B (any type), (3) the message-typed oneof field A again — well within normal protobuf wire-format grammar, no size limits or depth limits are implicated, and it is reachable via the standard public `Message.Builder.mergeFrom` / `parseFrom` API with a fully trusted, valid schema. This is easily reproducible and does not depend on any host-language memory corruption, making it a straightforward, deterministic sequence rather than a probabilistic race.

### Recommendation
In `internalGet$capitalized_name$FieldBuilder()`, reset (or recreate) `$name$Builder_` whenever the incoming case differs from `$number$` at the time of (re-)activation, not only when `$name$Builder_ == null`. Equivalently, `dispose()`/null out `$name$Builder_` whenever `oneofCase_` is set away from `$number$` (mirroring what `GenerateBuilderClearMethod` already does for explicit `clearFoo()` calls) so that re-entering the case via `internalGetFieldBuilder()` always constructs a fresh builder seeded from the default instance, keeping the case flag and backing builder state synchronized on every transition.

### Proof of Concept
I was unable to fully execute this against a live JVM within this session (no filesystem/JVM execution available in ask-only mode), so this is a source-level trace, not an executed test. A concrete reproduction plan:
1. Define `message M { oneof o { Foo foo = 1; Bar bar = 2; } }` where `Foo`/`Bar` are message types (trusted, valid schema).
2. Encode bytes: tag for field 1 (`Foo`) with sub-bytes `{a: 1}`, followed by tag for field 2 (`Bar`) with any content, followed by tag for field 1 (`Foo`) again with sub-bytes `{b: 2}`.
3. Call `M.newBuilder().mergeFrom(bytes)`.
4. Inspect the internal `fooBuilder_` field (or `build().getFoo()`) — the expectation under a correctly-synchronized invariant is that the second `Foo` occurrence starts from a fresh/default `Foo` builder; verify whether stale state from the first `Foo` occurrence (before the intervening `Bar`) persists in the builder that is ultimately merged into `result.foo_` in `GenerateBuildingCode`: [3](#0-2) 

This should be confirmed by a background agent with JVM access, comparing `oneofCase_`/`fooBuilder_` state transitions against `SingleFieldBuilderTest`-style assertions before concluding definitive exploitability beyond the source-level invariant violation identified above.
