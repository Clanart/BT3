Now let me read the core deserialization consumers in the in-scope crates.### Title
PedPoP deserializes an identity encryption key, collapsing ECDH to a public constant and exposing the recipient's FROST secret share - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`EncryptionKeyMessage::read` deserializes the per-participant ECDH public key (`enc_key`) with `C::read_G`, the `Ciphersuite`-level reader which enforces only canonicality — it does not reject the identity point. `Decryption::register` then stores the key with no validation and no proof-of-knowledge requirement. If a DKG participant registers `enc_key = identity`, every secret share encrypted to them is produced as `ecdh = key * identity = identity`, so the ChaCha20 cipher key is derived from the publicly known encoding of the identity point plus the public `context`. Anyone who observes the ciphertext can derive the cipher key and recover that participant's threshold secret share in the clear. This is the Serai-shaped analog of CWE-502: untrusted bytes deserialized into an object that is then used for a security-critical operation (ECDH key agreement) without semantic validation.

### Finding Description
The read path is:

1. `EncryptionKeyMessage::read` parses `enc_key` via `C::read_G` — `crypto/dkg/pedpop/src/encryption.rs:57-58`.
2. `Ciphersuite::read_G` checks `from_bytes` success and canonical re-encoding only; identity is a canonical, valid point — `crypto/ciphersuite/src/lib.rs:91-101`. Contrast with `Curve::read_G` in FROST, which explicitly rejects identity — `crypto/frost/src/curve/mod.rs:125-131`. PedPoP deliberately uses the ciphersuite-level reader, so no identity rejection exists anywhere on this path.
3. `Decryption::register` inserts the attacker-controlled `enc_key` with only a duplicate-registration assert — `crypto/dkg/pedpop/src/encryption.rs:351-362`. No PoK/PoP is required on the registration key; `EncryptionKeyProof`'s DLEq is produced by the honest *decryptor* during blame, not by the registrant.
4. In `SecretShareMachine::generate_secret_shares`, `self.encryption.encrypt(rng, l, share)` calls `encrypt(rng, context, from, enc_keys[l], msg)` → `ecdh::<C>(&key, to)` = `to * key` — `crypto/dkg/pedpop/src/encryption.rs:95-97, 154`. With `to = identity`, the shared secret is the identity point regardless of the ephemeral scalar.
5. `cipher` derives the ChaCha20 key as `transcript("DKG Encryption v0.2", context, shared_key)` — `crypto/dkg/pedpop/src/encryption.rs:101-133`. With `shared_key = identity`, the key is a deterministic function of the public session context and a constant encoding: anyone can compute it and run the keystream over the observed `msg` bytes to recover the raw `SecretShare` repr.

The result `share_l = Σ_j f_j(l)` — participant `l`'s FROST secret share — is plaintext-visible to any observer of the share ciphertexts.

### Impact Explanation
A participant's secret share must be private to that participant. When `enc_key = identity` passes deserialization, the participant's share `s_l` becomes public. Consequences:

- **Threshold reduction / signature forgery:** Anyone holding `s_l` can act as participant `l` in FROST signing — generate `l`'s preprocesses and produce signature shares that verify against `verification_shares[l] = G·s_l`. A coalition of `t−1` real participants plus the public `s_l` yields a valid group signature with only `t−1` consenting parties; honest participant `l` is framed as having signed messages they never saw. In a `t`-of-`n` custody setting this reduces the effective collusion requirement to `t−1`.
- **Secret share recovery by passive observers:** The encryption exists precisely because share messages may travel over authenticated-but-not-confidential channels; the construction silently voids that confidentiality for the malicious registrant.

This is key share recovery reachable purely from public protocol messages an unprivileged DKG participant sends.

### Likelihood Explanation
The attack requires only that one DKG participant serialize `enc_key` as the identity encoding (for Ristretto/Ed25519, the 32-byte compressed-Edwards encoding of y=1, `01 || 00…00`; for secp256k1, the SEC1 infinity encoding). The payload passes `EncryptionKeyMessage::read`, `Decryption::register`, and `verify_r1` (which checks only `commitments.len() == t` and the PoK over `commitments[0]` — unrelated to `enc_key` — `crypto/dkg/pedpop/src/lib.rs:317-329`). No honest party aborts; all `n−1` honest senders encrypt shares to the public key in round 2. Exploitation is deterministic — no grinding, no race, no collusion.

### Recommendation
Reject the identity point (and, defensively, any small-order/torsion point) in the registration path:

- In `EncryptionKeyMessage::read` or `Decryption::register`, check `enc_key.is_identity()` and error, mirroring the explicit identity rejection in `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`).
- Optionally require a proof of possession/knowledge of `enc_key`'s discrete logarithm bound to `(context, participant)` at registration time, so key validity is established before shares are encrypted to it.
- In `encrypt`, assert `ecdh` output is not identity before deriving the cipher — a cheap last-line check that a non-identity `to` can never produce anyway.

### Proof of Concept
Conceptual, for `C = Ristretto`, `t = 2`, `n = 3`, malicious participant `l = 1`:

```rust
// Participant 1's malicious EncryptionKeyMessage:
//   msg = Commitments { commitments: [G*c0, G*c1], sig: valid PoK }  // normal, valid
//   enc_key = identity encoding: bytes = [0x01, 0x00, ..., 0x00]   // 32 bytes

// Honest participants 2 and 3:
let msg = EncryptionKeyMessage::<Ristretto, Commitments<Ristretto>>::read(
    &mut bytes.as_ref(), params)?;        // succeeds — identity is canonical
machine.register(1, msg);                 // enc_keys[1] = identity

// In generate_secret_shares, for l = 1:
//   key = random_nonzero_F(rng)
//   ecdh = enc_keys[1] * key = identity * key = identity
//   cipher_key = Transcript("DKG Encryption v0.2") | context | identity.to_bytes()
//                -> "encryption_key" -> challenge("key") -> ChaCha20(static IV)
//   msg = cipher(share_bytes)   // key is fully computable by anyone knowing `context`

// Attacker (or passive observer) computes the same ChaCha20 key:
let mut t = RecommendedTranscript::new(b"DKG Encryption v0.2");
t.append_message(b"context", context);            // public session context
t.domain_separate(b"encryption_key");
t.append_message(b"shared_key", identity_encoding); // identity.to_bytes(), public
let mut key = Cc20Key::default();
key.copy_from_slice(&t.challenge(b"key")[..32]);
ChaCha20::new(&key, &iv).apply_keystream(&mut observed_msg); // -> share_1 plaintext
```

The recovered `share_1` scalar satisfies `G·share_1 == verification_shares[1]`, enabling the attacker to impersonate participant 1 in all subsequent FROST signing sessions against this group key.
