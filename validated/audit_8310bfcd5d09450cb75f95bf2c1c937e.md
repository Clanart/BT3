### Title
Boundary check in `resolveWithin` uses raw prefix `startsWith` instead of a path-separator-aware comparison, allowing sibling-directory escape when resolving attacker-controlled `filepath` from `x-github-client://openrepo` deep links - ([File: app/src/lib/path.ts])

### Summary
The GitHub Desktop analog of the Sherlock finding is a boundary-condition miscalculation, not in a Solidity `maxWithdraw` computation but in the "is this resolved path still inside the root" check performed by `_resolveWithin` in `app/src/lib/path.ts`. Just like `maxAvailable` failed to correctly bound a value, the containment check here fails to correctly bound a resolved filesystem path, because it compares string prefixes instead of path segments.

### Finding Description
`_resolveWithin` is Desktop's core "prevent path escape" primitive, used to validate paths before showing/reading files that originate from **untrusted, attacker-controlled input** (a deep-link URL or repository content). The containment decision is: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` performs a raw character-prefix comparison with **no path-separator boundary check**. This means if `realRoot` is e.g. `/Users/victim/Documents/GitHub/repo`, then `realResolved = /Users/victim/Documents/GitHub/repo-secrets/token.txt` is judged "inside" the root because the string `"repo-secrets/..."` starts with `"repo"` — even though `repo-secrets` is a completely different, sibling directory that just happens to share `repo` as a prefix. The check never verifies that the next character after the shared prefix is a path separator (or that `realResolved === realRoot`).

This function is called directly on attacker-controlled data:
1. `dispatcher.ts`'s `openRepositoryFromUrl` handler resolves the `filepath` query parameter from a `x-github-client://openrepo` deep link — fully attacker-supplied — against `repository.path`: [2](#0-1) 
2. `parse-app-url.ts` passes the `filepath` querystring value through with only an `isAbsolute` check applied by the caller, no segment sanitization at the parse layer: [3](#0-2) 
3. `copilot-conflict-context.ts` also relies on `resolveWithin` as its sole traversal/symlink guard before reading file content into an AI context: [4](#0-3) 

Desktop's own default clone layout (`~/Documents/GitHub/<name>`) makes prefix collisions realistic without any unusual user behavior: users commonly have multiple repos or repo variants co-located under the same parent directory (e.g. `repo` and `repo-secrets`, `repo` and `repo2`, `app` and `app-old`). An attacker who controls a public/forked repository name, or who crafts an `x-github-client://openrepo?url=...&filepath=..` link, can rely on such naming collisions (or even instruct the victim, via repo README, to clone a second attacker-named repo alongside the legitimate one) to make `resolveWithin(repoPath, filepath)` accept a `filepath` value that actually resolves into a sibling directory.

### Impact Explanation
Where `resolveWithin` gates `shell.showItemInFolder(resolved)` in `dispatcher.ts`, a successful bypass reveals/opens a file **outside the intended repository root** in the OS file explorer — satisfying the "file read outside the repo" criterion driven purely by a link the user clicks. Where it gates file reads for the Copilot conflict-resolution feature, a bypass could feed content of files outside the repo (potentially credential files, SSH keys, or other repos under the same parent directory that share a name prefix) into a context sent to an external AI service, which is a form of data exfiltration triggered by an attacker-influenced repository/conflict state.

### Likelihood Explanation
The `filepath` deep-link vector requires only that the victim click a crafted `x-github-client://openrepo` link and have (or create, e.g. by cloning an attacker-suggested "helper" repo) a same-prefix sibling directory next to a Desktop-managed repository — no local access, no admin rights, no pre-existing malware, and no credential leakage are required. Given Desktop's default flat clone layout under a shared parent folder, prefix collisions between repositories are a normal occurrence, making this more than a purely theoretical edge case, though it does depend on the specific directory layout on the victim's machine at the time the link is opened.

### Recommendation
Change the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to be path-segment aware rather than a raw string prefix test, e.g.:
```
return realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(with the platform-specific separator for the `win32`/`posix` variants respectively), and add regression tests mirroring the existing symlink-escape tests in `app/test/unit/path-test.ts` for the "sibling directory with root as prefix" case.

### Proof of Concept
1. Victim has two repositories cloned by Desktop under the same parent folder: `/Users/victim/Documents/GitHub/repo` (legitimate) and `/Users/victim/Documents/GitHub/repo-secrets` (any repo, could contain a sensitive file `token.txt`).
2. Attacker sends the victim a deep link:
   `x-github-client://openrepo/octocat/repo?filepath=../repo-secrets/token.txt`
3. `parse-app-url.ts` parses `filepath` unchanged. `dispatcher.ts`'s `openRepositoryFromUrl` checks `isAbsolute(filepath)` (false, it's relative) then calls `resolveWithin('/Users/victim/Documents/GitHub/repo', '../repo-secrets/token.txt')`.
4. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/Documents/GitHub/repo-secrets/token.txt`; `realResolved.startsWith(realRoot)` evaluates `"…/repo-secrets/token.txt".startsWith("…/repo")` → `true`.
5. The function returns the resolved path instead of `null`, and `shell.showItemInFolder(resolved)` opens/reveals `token.txt` from the sibling repository — a file the deep link should never have been able to reference. [5](#0-4) [6](#0-5)

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
