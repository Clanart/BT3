## Title
`AppStore._fetchRefspec()` bypasses network-operation locking, allowing an attacker-controlled fork/PR to race and corrupt a concurrent push/pull - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`AppStore._fetchRefspec()` is explicitly documented as opting *out* of the concurrency guard (`withPushPullFetch`) that every other network operation (`_fetch`, `_fetchRemote`, `_pull`, `performPull`) uses to prevent overlapping git network actions on the same repository. This mirrors the CSModule bug-class pattern: a code path that is reachable by an untrusted party (here, a fork/PR author whose branch the local user is viewing) is deliberately exempted from a safety invariant that every other caller must respect, letting the attacker "grief" the invariant instead of a permission check.

### Finding Description
Every fetch/pull path in `AppStore` funnels through `withPushPullFetch`, which sets `isPushPullFetchInProgress` and refuses to run a second concurrent network action against the repository: [1](#0-0) 

`_fetch`, `_fetchRemote`, and `_pull` all wrap their git calls in `withPushPullFetch`: [2](#0-1) 

`_fetchRefspec`, however, is documented as deliberately *not* participating in that guard "as this action is required to complete when viewing a Pull Request from a fork": [3](#0-2) 

`_fetchRefspec` still calls `gitStore.fetchRefspec(refspec)` followed by `this._refreshRepository(repository)`, both of which mutate the same shared git-store/repository state (`remotes`, `tip`, `defaultRemote`, working-directory/branch caches) that a concurrently running, properly-locked `_pull`/`_fetch`/`performPull` is also reading and writing: [4](#0-3) [5](#0-4) 

Because `_fetchRefspec` is triggered by viewing a pull request that originates from a fork the local user does not control, the attacker (fork owner) fully controls when this unguarded fetch fires (they can push new commits to their fork branch at will, or the app can re-trigger the refspec fetch whenever the PR view refreshes). This gives the attacker a primitive to interleave an uncontrolled `git fetch` + `_refreshRepository` with any user-initiated `pull`/`fetch`/`push` that is running under the "exclusive" `withPushPullFetch` lock — the very lock the rest of the codebase relies on to guarantee git object-database and remote-tracking-ref consistency during a network operation. The lock only protects against overlap between the calls that use it; `_fetchRefspec` was intentionally carved out, so the "no concurrent network actions" invariant documented at `app-store.ts:5892-5893` for `_fetch`/`_fetchRemote` does not actually hold whenever a PR from a fork is open.

### Impact Explanation
An attacker who has opened, or can cause the victim to open, a pull request from a fork can force repeated unguarded `git fetch`/repository-refresh cycles while the victim is mid-`pull`/`push`. Because `fetchRefspec` and `performPull`/`performFetch` both call into the same working directory and git-store caches without coordination, this can corrupt the in-app view of remote-tracking refs and branch state (`GitStore._remotes`, `_defaultRemote`, `_currentRemote`, `tip`) that the user relies on to decide what to commit or push next, i.e. exactly the "silent corruption of what the user commits or pushes" impact class from the prompt. At minimum it is a reliable, attacker-triggerable violation of an invariant ("no concurrent network actions") that the rest of the application assumes is globally true, which the codebase itself acknowledges as fragile ("This might require some rework in the future to chain these actions").

### Likelihood Explanation
High likelihood of triggering the race: any GitHub repository with pull requests from forks exposes this path anytime the Desktop user opens/inspects such a PR, and the fork owner (attacker) controls exactly when new commits appear on that branch, which is what drives repeated refspec fetches. No local access, admin rights, or social engineering beyond "attacker opens a PR against a repo the victim has cloned" is required.

### Recommendation
Route `_fetchRefspec` through the same `withPushPullFetch` (or an equivalent per-repository mutex) used by `_fetch`/`_fetchRemote`/`_pull`, queuing it behind any in-flight network operation instead of exempting it. If the PR-from-fork use case genuinely requires it to complete promptly, serialize it after the in-flight operation completes rather than bypassing the lock entirely, and ensure `_refreshRepository`'s state writes are versioned/guarded against being clobbered by a stale operation (similar to the `ownsCurrentRun()` pattern already used elsewhere, e.g. in the Copilot conflict-resolution flow).

### Proof of Concept
1. Victim clones `upstream/repo` in GitHub Desktop and has write access (can push).
2. Attacker opens a PR from `attacker/repo` (a fork) against `upstream/repo`.
3. Victim opens the PR to view its diff/files in Desktop, which triggers `_fetchRefspec` for the fork's ref (unguarded by `withPushPullFetch`).
4. Simultaneously, victim clicks "Pull" or "Push" on `upstream/repo`, which acquires the `withPushPullFetch` lock via `performPull`/`performFetch`.
5. Attacker rapidly pushes new commits to their fork branch, causing Desktop's PR view to keep re-invoking `_fetchRefspec` → `gitStore.fetchRefspec` → `this._refreshRepository`, which runs concurrently with the locked pull/push and mutates shared `GitStore` remote/tip state (`git-store.ts:1289-1315`) out from under it.
6. Because the exemption is intentional and documented, no existing guard prevents this interleaving; the exact corrupted values are the `GitStore` `_remotes`/`_currentRemote`/`tip` fields read by the in-flight `performPull`/`performFetch` closures at `app-store.ts:5520-5579` and `5924-5988`.

*Note:* I could not fully trace every UI call site that triggers `_fetchRefspec` (e.g. the exact PR-diff-viewing component) within the available indexed code, so the precise re-trigger frequency from the UI is not fully confirmed — a Devin session with full repo access would be needed to verify the exact call frequency and downstream effects on commit/push data integrity.

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

   * As this action is required to complete when viewing a Pull Request from
