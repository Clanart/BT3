Based on my research, I found a valid analog in the Kaia staking/reward system. I was unable to view the full Solidity source of `CnStakingV4.sol` and `MultiCallContract.sol` due to index limits — my conclusion is supported by the Go-level integration/getter tests, which explicitly demonstrate the balance-to-stake relationship in a deterministic and reproducible way. If more certainty on CnStaking's internal accounting is needed, a full Devin session with repository file access would be required to inspect the raw Solidity contracts.

### Title
Native KAIA sent directly to a CN staking contract inflates its reported stake and manipulates KIP-82 reward distribution - (File: kaiax/staking/impl/getter.go)

### Summary
The reward module attributes staking rewards to validators proportionally to their `StakingAmount`, which is derived from `GetStakingInfo` → `getFromState` → `MultiCallStakingInfo`/`MultiCallStakingInfoPermissionless`. Test fixtures show this amount equals the raw native-token *balance* of the registered CN staking contract address, not an internally tracked/authorized deposit ledger. Anyone (an unprivileged transaction sender) can send native KAIA directly to a validator's registered staking contract address to inflate that validator's counted stake, which is then used unmodified in `assignStakingRewards`/`assignStakingRewardsFlex` to redistribute the block's staking-reward budget.

### Finding Description
`StakingModule.getFromState` reads the AddressBook via the `MultiCallContract` and converts the returned amounts directly into `StakingInfo.StakingAmounts` [1](#0-0) , with the conversion simply dividing the raw wei amount by `params.KAIA` [2](#0-1) .

Unit tests confirm that this "staking amount" is literally the account's native balance in the genesis allocation, not a value produced by any deposit-accounting function: setting `Balance: 42_000_000 * KAIA` on the staking-contract address directly produces `StakingAmounts: []uint64{42_000_000, ...}` with no separate deposit bookkeeping involved [3](#0-2) . The same pattern repeats for CL staking pools, whose stake is likewise equal to their raw balance [4](#0-3) .

This `StakingAmount` (and CL amount) is then fed directly, unfiltered, into reward allocation: `assignStakingRewards` computes each validator's excess-stake share purely from `cn.StakingAmount` (+ `cn.CLStakingInfo.CLStakingAmount` after Prague) and allocates the stakers' reward budget proportionally [5](#0-4) . The Flex reward variant behaves identically, using the same balance-derived excess-over-threshold computation [6](#0-5) .

Because a CN staking contract's balance is a public, unrestricted target for native-token transfers (any account can `transfer`/`call` KAIA to any address), an attacker does not need to go through the CN staking contract's controlled staking/deposit workflow (which typically enforces admin multisig confirmation, lockup, and withdrawal-request semantics) to increase the amount counted as "staked" for reward purposes. This is structurally the same class of bug as the referenced origin-dollar `LiquidityReward` issue: the reward-relevant quantity is read from a raw balance rather than a tracked, authorization-gated ledger of legitimate deposits.

### Impact Explanation
An attacker (or a colluding validator operator wanting to boost their own or a competitor's reported reward share) can send KAIA directly to a target CN staking contract to:
- Increase that validator's `StakingAmount` above `minStake`/`stakingRewardThreshold`, causing it to receive a disproportionately large share of the "stakers" reward budget (`assignStakingRewards`/`assignStakingRewardsFlex`), diluting the rightful reward share of other, legitimately staked validators — a form of reward redirection.
- Because the excess/threshold-based split is zero-sum within the stakers' reward budget, this directly reduces the KAIA paid to other validators without any input from them.

This is a protocol-level (not merely informational) financial-value-redirection issue affecting the core staking/reward distribution flow.

### Likelihood Explanation
Likelihood is high in terms of reachability — sending native tokens to any address, including a public CN staking contract, requires only a normal value-transfer transaction from any account, with no special privileges. The main uncertainty (not fully verifiable given index limits) is whether `CnStakingV4`'s `receive()`/`fallback()` accepts unsolicited KAIA at all, or reverts/rejects bare transfers outside its controlled `stakeKaia`-like flow; if it accepts plain value transfers (common for simple payable contracts, especially older CnStaking versions), the attack is trivial and cheap (cost of one transaction plus the transferred KAIA, which is fully recoverable if the attacker's own validator is the target).

### Recommendation
Do not use the raw native balance of the CN staking contract as the authoritative `StakingAmount` for reward and validator-eligibility purposes. Instead, have `MultiCallContract`/`AddressBook` (and `parseCallResult`/`parsePermissionlessCallResult` on the Go side) source the amount from an internally tracked, access-controlled "staked amount" ledger maintained by the CN staking contract's own admin-confirmed stake/unstake functions, analogous to fixing the LiquidityReward bug by tracking valid LP deposits separately from the contract's raw balance. If the staking contract is intentionally designed so that "balance = stake" (a valid design choice for some staking architectures), then it must reject or sweep any unsolicited/direct native transfer (e.g., via a `receive()` that reverts for non-admin, non-approved deposits) so that the balance cannot be inflated by outside parties.

### Proof of Concept
1. Identify a validator's registered CN staking contract address from the AddressBook (`CN_STAKING_ADDRESS_TYPE`) as returned by `MultiCallStakingInfo` [7](#0-6) .
2. From any unprivileged EOA, send a plain KAIA transfer to that staking contract address (assuming it accepts bare native transfers).
3. At the next `GetStakingInfo` read (next block after Kaia hardfork, or next staking interval before it), the added balance is reflected in `StakingAmounts` exactly as demonstrated by the genesis-balance-driven test fixtures [3](#0-2) .
4. On the subsequent deferred-reward computation, `assignStakingRewards`/`assignStakingRewardsFlex` allocate a larger proportional share of the stakers' reward budget to that validator's reward address, at the expense of other validators' shares [8](#0-7) .

func (s *StakingModule) getFromState(header *types.Header, statedb *state.StateDB) (*staking.StakingInfo, error) {
	isForPrague := s.ChainConfig.IsPragueForkEnabled(new(big.Int).Add(header.Number, common.Big1))
	isForPermissionless := s.ChainConfig.IsPermissionlessForkEnabled(new(big.Int).Add(header.Number, common.Big1))
	num := header.Number.Uint64()

	// Bail out if AddressBook is not installed.
	// This is a common case for private nets.
	if statedb.GetCode(system.AddressBookAddr) == nil {
		logger.Trace("AddressBook not installed", "sourceNum", num)
		return emptyStakingInfo(num), nil
	}

	// Now we're safe to call the MultiCall contract.
	contract, err := system.NewMultiCallContractCaller(statedb, s.Chain, header)
	if err != nil {
		return nil, staking.ErrMultiCallCall(err)
	}

// assignStakingRewardsFlex assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}

	// Distribute the budget to the CNs based on the excess stakes.
	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(budget)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		if excessInt[cn.RewardAddr] <= 0 {
			continue
		}
		excess := new(big.Int).SetUint64(excessInt[cn.RewardAddr])

		// The KAIA unit will cancel out:
		// reward (kei) = excess (KAIA) * budget (kei) / totalExcess (KAIA)
		reward := new(big.Int).Div(new(big.Int).Mul(excess, budget), totalExcess)
		if reward.Sign() <= 0 {
			continue
		}

		// If Prague and CL is configured for this CN, split the reward between CN and CL.
		if isPrague && cn.CLStakingInfo != nil {
			cnAmount, clAmount := cn.Split(reward)
			alloc[cn.RewardAddr] = cnAmount
			alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
		} else {
			alloc[cn.RewardAddr] = reward
		}
		remaining.Sub(remaining, reward)
	}
	return alloc, remaining
}

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
