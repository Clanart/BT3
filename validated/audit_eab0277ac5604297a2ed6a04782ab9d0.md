## Title
Address Re-Association Permanently Freezes Prior Deposits/Balances Held at the Direct-Cast Sei Address, Analogous to the Boolean-Flag Transfer-Lock Bug - (File: `x/evm/keeper/address.go`)

## Summary
The reported bug is a class of "single small/incidental action permanently and irrevocably restricts an address's ability to move its own funds." The direct sei-chain analog is the dual address (cast vs. associated) model in `x/evm`: once an EVM address is explicitly associated to a *different* Sei address than the deterministic direct-cast address, the bank keeper permanently refuses to deliver any further funds to that cast address via `CanAddressReceive`, even though funds already deposited/held at that cast address (e.g., pending governance deposits) cannot be refunded back to it.

## Finding Description
`CanAddressReceive` treats a cast address as receivable only if it is unassociated or if the associated Sei address for its underlying EVM address equals the cast address itself: [1](#0-0) 

Once any account signs a Cosmos/EVM transaction (or explicitly calls Associate), `EVMPreprocessDecorator`/`AssociateAddresses` calls `SetAddressMapping`, permanently binding the EVM address to the pubkey-derived (true) Sei address: [2](#0-1) [3](#0-2) 

After this association, the direct-cast address (`sdk.AccAddress(evmAddr[:])`) is no longer the "associated" Sei address for that EVM address, so `CanAddressReceive`/`CanSendTo` permanently returns `false` for it, blocking any subsequent `SendCoins`/`SendCoinsFromModuleToAccount` to that cast address — for the lifetime of the chain, since there is no mechanism to reverse the association back to the cast address.

This is structurally the same bug class as the TITN report: a boolean/derived "association" state, once flipped by an ordinary transaction (analogous to receiving a trivial bridged-token transfer), permanently changes transfer eligibility for an address, with no path to unlock it. The codebase's own regression test explicitly demonstrates the frozen-funds outcome for module refunds: [4](#0-3) 

In this test, a depositor deposits from their cast address (`castDepositor`) before ever associating. Later, the EVM address underlying that cast address becomes associated with a *different* Sei address (which happens whenever the true owner signs any transaction and the pubkey-derived Sei address differs from the direct-cast bytes — the normal, expected outcome for most real accounts). After that: [5](#0-4) 

`CanSendTo` now returns `false` for `castDepositor`, and `RefundDeposits` can no longer deliver the deposit back to it — the deposit is left permanently pending in the gov module, unreachable by its original depositor's cast identity.

## Impact Explanation
This is a genuine, permanent value-freezing outcome reachable purely by ordinary transaction activity (no privileged access required):
- Any funds sent to, or deposited from, a not-yet-associated EVM address's cast identity become permanently unrecoverable via that cast address once the underlying EVM address is associated to a different (true, pubkey-derived) Sei address — which is the standard, expected outcome of association for virtually every real account, since the direct-cast bytes rarely equal the pubkey-derived address.
- Any Cosmos module that keeps a pending balance owed to a cast address (e.g., gov deposits, distribution withdraw addresses) can permanently fail to deliver it back, as shown by the `AfterValidatorRemoved`/`RefundDeposits` tests, which is the exact "permanent freezing" impact category accepted by the rules.
- Unlike the distribution module (which explicitly detects this and reroutes funds to the community pool as a fallback: `AfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator`), the gov module's `RefundDeposits` path has no such fallback — the deposit is simply left "pending" indefinitely. [6](#0-5) 

## Likelihood Explanation
High for occurrence, but the impact severity depends on how funds end up at a cast address before association happens. In practice: any EOA that has not yet associated (i.e., has never signed a transaction or called Associate) uses its direct-cast address as its default identity. Any counterparty (a gov depositor, a bank sender, a distribution withdraw-address target) that interacts with that cast address before the owner associates is exposed. The very next signed transaction by the address owner (an entirely ordinary action) triggers the permanent lock for that specific value — this requires no attacker at all, just normal usage patterns, making the trigger condition easy to hit unintentionally, and also triggerable adversarially by front-running an association.

## Recommendation
- Provide a governance- or module-level sweep/migration path for value stuck at a cast address after association diverges from it (similar in spirit to `MigrateCastAddressBalances`, but for value already committed into module accounts such as gov deposits).
- In `x/gov/keeper/deposit.go`'s `RefundDeposits`, mirror the fallback used by distribution's `AfterValidatorRemoved` (route unreceivable refunds to the community pool or module-locked account, with an event, rather than leaving them silently pending forever).
- Consider tracking "receivability" per amount/escrow at deposit time rather than at refund time, or disallow deposits from not-yet-associated cast addresses until association is finalized.

## Proof of Concept
Existing repository test reproduces the freeze end-to-end: [4](#0-3) 

1. `castDepositor` (an unassociated EVM address's direct-cast Sei address) deposits 40 units into a governance proposal.
2. The EVM address is subsequently associated to a different, unrelated Sei address (`SetAddressMapping`) — representing the normal outcome when the real owner of that EVM address eventually signs a transaction and their pubkey-derived Sei address differs from the direct-cast bytes.
3. `CanSendTo(ctx, castDepositor)` now returns `false`.
4. `RefundDeposits` is called; the deposit belonging to `castDepositor` remains in the store (`found == true` after refund attempt), i.e., permanently stuck and irretrievable via that identity, while the valid depositor's refund succeeds normally.

This confirms the same bug class as the TITN report — a single ordinary transaction permanently and irreversibly alters transfer eligibility for an address, freezing value that would otherwise be recoverable.

func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator(t *testing.T) {
	app := seiapp.Setup(t, false, false, false)
	ctx := app.BaseApp.NewContext(false, tmproto.Header{})

	// The validator operator is the direct-cast Sei address of an EVM address.
	evmAddr := common.HexToAddress("0x3333333333333333333333333333333333333333")
	castAddr := sdk.AccAddress(evmAddr[:])
	valAddr := sdk.ValAddress(castAddr)
	valAccAddr := sdk.AccAddress(valAddr) // == castAddr

	require.True(t, app.BankKeeper.CanSendTo(ctx, castAddr))

	// Re-associate the EVM address to a different true Sei address, mirroring
	// associatePubKey after a validator was created under the direct-cast address.
	associatedAddr := seiapp.AddTestAddrs(app, ctx, 1, sdk.NewInt(1000000000))[0]
	app.EvmKeeper.SetAddressMapping(ctx, associatedAddr, evmAddr)

	// The operator/delegator address can no longer receive funds, and the
	// withdraw-address fallback resolves back to that same unreceivable address.
	require.False(t, app.BankKeeper.CanSendTo(ctx, castAddr))
	require.Equal(t, valAccAddr.String(), app.DistrKeeper.GetDelegatorWithdrawAddr(ctx, valAccAddr).String())

	commission := sdk.DecCoins{sdk.NewDecCoin("usei", sdk.NewInt(10))}
	coins := sdk.NewCoins(sdk.NewCoin("usei", sdk.NewInt(10)))
	distrAcc := app.DistrKeeper.GetDistributionAccount(ctx)
	require.NoError(t, apptesting.FundModuleAccount(app.BankKeeper, ctx, distrAcc.GetName(), coins))
	app.AccountKeeper.SetModuleAccount(ctx, distrAcc)

	app.DistrKeeper.SetValidatorOutstandingRewards(ctx, valAddr, types.ValidatorOutstandingRewards{Rewards: commission})
	app.DistrKeeper.SetValidatorAccumulatedCommission(ctx, valAddr, types.ValidatorAccumulatedCommission{Commission: commission})

	communityBefore := app.DistrKeeper.GetFeePool(ctx).CommunityPool.AmountOf("usei")
	moduleBalanceBefore := app.BankKeeper.GetBalance(ctx, distrAcc.GetAddress(), "usei")

	require.NotPanics(t, func() {
		app.DistrKeeper.Hooks().AfterValidatorRemoved(ctx, sdk.ConsAddress{}, valAddr)
	})

	// The commission could not be paid out, so it stays in the distribution module
	// account and is accounted to the community pool. No value leaves the module and
	// the unreceivable operator address receives nothing.
	communityAfter := app.DistrKeeper.GetFeePool(ctx).CommunityPool.AmountOf("usei")
	require.Equal(t, communityBefore.Add(sdk.NewDec(10)), communityAfter)
	require.True(t, app.BankKeeper.GetBalance(ctx, castAddr, "usei").IsZero())
	require.Equal(t, moduleBalanceBefore, app.BankKeeper.GetBalance(ctx, distrAcc.GetAddress(), "usei"))
}
