### Title
OP_RETURN Data Output Excluded From Weight/Fee Calculation Allows Over-Weight or Under-Fee Transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` enforces `MAX_STANDARD_TX_WEIGHT` and the minimum relay fee using `calculate_weight_vbytes`, which reconstructs a transaction from only `payments` and `change`. The OP_RETURN `data` output — which is pushed onto `tx_outs` separately — is never included in the weight calculation. Analogous to the Notional finding (a safety bound checked against only one of several pools sharing a liquidity constraint), the transaction-size bound here is checked against only a subset of the outputs that share the transaction's weight budget.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- Lines 194–202: the OP_RETURN output is pushed into `tx_outs` (up to 80 bytes of data, checked at line 171).
- Lines 204 and 225–226: `calculate_weight_vbytes(tx_ins.len(), payments, change)` is called — it builds a `Transaction` whose `output` is derived solely from `payments` plus an optional change `TxOut` (lines 85–99). The `data`/OP_RETURN output is absent.
- Lines 211 and 241: `TooLowFee` and `TooLargeTransaction` are enforced against this underestimated `weight`/`vbytes`.

Consequences:

1. **Weight underestimation**: an OP_RETURN output costs ~8 (value) + ~1 (script len) + ~2–3 (OP_RETURN + push opcodes) + up to 80 bytes ≈ up to ~91 non-witness bytes ≈ ~364 WU (~91 vbytes). A transaction whose checked weight is just under `MAX_STANDARD_TX_WEIGHT` (400,000 WU) but whose real weight exceeds it passes `TooLargeTransaction` yet is non-standard and will not be relayed by default-policy nodes.
2. **Fee underestimation**: `needed_fee = fee_per_vbyte * vbytes` omits the OP_RETURN vbytes. If `needed_fee` sits just above `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, the *actual* fee rate falls below the minimum relay fee once the OP_RETURN size is accounted for — again producing a transaction that won't propagate.

### Impact Explanation
A `TransactionMachine` built from such a `SignableTransaction` will drive the FROST threshold signing ceremony to completion and produce a fully signed transaction that standard Bitcoin nodes reject (over-weight or under-fee). The inputs committed via `Prevouts::All` remain locked in a transaction that cannot be broadcast — funds are effectively unspendable until a new transaction is constructed, and the signing session's nonces have been consumed. This is a "signed but unbroadcastable" outcome reachable purely from the public `data` parameter supplied to `SignableTransaction::new`.

### Likelihood Explanation
Any caller can pass `data` up to the checked 80-byte limit. Triggering the over-weight path requires a transaction already near the 400k WU standardness boundary (i.e., many inputs/payments) — plausible for a consolidating vault wallet. The under-fee path triggers whenever `fee_per_vbyte` is set at or near the minimum relay rate and `data` is present, which is a routine configuration. No secret access or malicious validator is required; only untrusted/instructed transaction parameters.

### Recommendation
Include the OP_RETURN output in `calculate_weight_vbytes`. Either pass the fully-built `tx_outs` (including `data`) into the weight function, or add the `data` output explicitly when constructing the template `Transaction` at lines 68–99, so both `needed_fee` (line 206/227) and the `MAX_STANDARD_TX_WEIGHT` check (line 241) account for all outputs actually emitted.
