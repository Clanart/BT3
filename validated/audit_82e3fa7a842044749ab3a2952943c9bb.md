### Title
Multisig/Order-Independent-Multisig `signatures_required` can be set to `0`, allowing a spending condition to authenticate with zero signatures - (File: stacks-codec/src/transaction.rs)

### Summary
`MultisigSpendingCondition::verify` and `OrderIndependentMultisigSpendingCondition::verify` treat `signatures_required` as the sole threshold check, but nothing in the codec, the public constructors, or `StacksAddress::from_public_keys` prevents `signatures_required` from being `0`. When it is `0`, both `verify` functions accept a spending condition with an *empty* `fields` vector (no signatures, no public keys) as fully authenticated, exactly mirroring the Audius bug class where a threshold value that is validated to be non-zero at "creation" time can be reduced to zero and thereby allow the protected action (there: proposal execution; here: fund movement) to occur without the required proof of authorization.

### Finding Description
`OrderIndependentMultisigSpendingCondition::verify` checks: [1](#0-0) 
and `MultisigSpendingCondition::verify` checks: [2](#0-1) 

If `signatures_required == 0`, both checks are satisfied by `num_sigs == 0`, i.e. by an empty `fields` vector — no `TransactionAuthField::Signature` and no `TransactionAuthField::PublicKey` entries at all. The subsequent address-recomputation step: [3](#0-2) 
calls `StacksAddress::from_public_keys(0, hash_mode, 0, &[])`. In `from_public_keys`, the only length guard is `pubkeys.len() < num_sigs`, which for `num_sigs == 0` and an empty key list is `0 < 0`, i.e. false, so the call succeeds: [4](#0-3) 
`public_keys_to_address_hash` then deterministically hashes a fixed Bitcoin-style script (`OP_0 ... OP_0 OP_CHECKMULTISIG`) built from zero public keys: [5](#0-4) 
This hash is a fixed, publicly-computable constant — not tied to any private key. If the crafted spending condition's `signer` field is set to this fixed hash, `verify()` returns `Ok(...)` with zero cryptographic work and zero authorization material supplied.

Nothing in the codec deserializer rejects `signatures_required == 0` either — the "exactly N signatures" check for `MultisigSpendingCondition` (`num_sigs_given != signatures_required`) and the "at least N signatures" check for `OrderIndependentMultisigSpendingCondition` (`num_sigs_given < signatures_required`) are both vacuously true when `signatures_required` is `0`: [6](#0-5) [7](#0-6) 

The public constructors used throughout the codebase (including by node/wallet code) also never enforce `num_sigs >= 1`: [8](#0-7) 
so a "0-of-N" (or 0-of-0) multisig address is a first-class, reachable state, not merely a hand-crafted wire-format anomaly.

This exactly matches the bug class in the external report: a value (`votingQuorum`/`signatures_required`) that gates whether a privileged action can be executed is allowed to be `0`, which trivially satisfies the ">= threshold" check and lets the action (proposal execution / asset transfer) proceed without the intended authorization.

### Impact Explanation
Any STX, fungible, or non-fungible assets held by an address whose hash equals the fixed "0 required signatures" script hash can be spent, transferred, or have any contract-call authorized by *any* party, with no private key and no valid ECDSA signature whatsoever — the `fields` vector can be entirely empty. This breaks the core equality that a transaction's spending condition must be backed by proof of key ownership of the origin/sponsor account. This is a Critical-class impact per the classification rubric ("an asset moving without authorization"), since an attacker can author and broadcast a fully valid, network-accepted transaction that assigns itself as spender of a multisig account requiring zero signatures.

### Likelihood Explanation
The precondition is that some account uses (or is configured with) `signatures_required = 0` — whether via a misconfigured/legacy wallet using the same public constructors (`new_multisig_p2sh`, `new_multisig_p2wsh`, `new_multisig_order_independent_p2sh`, `new_multisig_order_independent_p2wsh`) with `num_sigs = 0`, or via directly hand-crafted `MultisigSpendingCondition`/`OrderIndependentMultisigSpendingCondition` structs (the fields are all `pub`). Because none of the construction, serialization, or verification code paths ever reject `signatures_required == 0`, and the resulting address is fully deterministic and can be computed in advance by anyone, this is straightforward to discover and exploit against any funds that land at that address.

### Recommendation
Add an explicit validation that `signatures_required >= 1` in:
- `MultisigSpendingCondition::verify` and `OrderIndependentMultisigSpendingCondition::verify` in `stacks-codec/src/transaction.rs`,
- their `consensus_deserialize` implementations,
- `TransactionSpendingCondition::new_multisig_p2sh` / `new_multisig_p2wsh` / `new_multisig_order_independent_p2sh` / `new_multisig_order_independent_p2wsh`, and
- `StacksAddress::from_public_keys` (reject `num_sigs == 0` for the P2SH/P2WSH multisig hash modes).

### Proof of Concept
1. Compute `Hash160` of the deterministic 0-of-0 P2SH script via `public_keys_to_address_hash(&AddressHashMode::SerializeP2SH, 0, &vec![])` — this value is a fixed constant computable offline by anyone, with no private key.
2. Construct a `MultisigSpendingCondition` (or `OrderIndependentMultisigSpendingCondition`) with:
   - `signer` = that fixed hash,
   - `signatures_required = 0`,
   - `fields = vec![]` (no signatures, no public keys),
   - arbitrary `nonce`/`tx_fee`/payload.
3. Wrap it in `TransactionAuth::Standard(...)` and build a `StacksTransaction`.
4. Call `.verify()` on the resulting spending condition: `num_sigs (0) != signatures_required (0)` is `false` (Multisig) / `num_sigs (0) < signatures_required (0)` is `false` (OrderIndependentMultisig) → check passes; `StacksAddress::from_public_keys(0, hash_mode, 0, &[])` reproduces the same fixed hash → `addr.bytes() == &self.signer` → `verify()` returns `Ok(...)`.
5. Any funds ever sent to that fixed address (e.g. mistakenly, or via a "0-of-N" wallet configuration) can now be spent by anyone submitting such a transaction, with no valid signature ever produced.

fn to_bits_p2sh<K: PublicKey>(num_sigs: usize, pubkeys: &Vec<K>) -> Hash160 {
    let mut bldr = Builder::new();
    bldr = bldr.push_int(num_sigs as i64);
    for pubk in pubkeys {
        bldr = bldr.push_slice(&pubk.to_bytes());
    }
    bldr = bldr.push_int(pubkeys.len() as i64);
    bldr = bldr.push_opcode(btc_opcodes::OP_CHECKMULTISIG);

    let script = bldr.into_script();
    Hash160::from_data(script.as_bytes())
}

/// Internally, the Stacks blockchain encodes address the same as Bitcoin
/// single-sig address over p2sh (p2h-p2wpkh)
fn to_bits_p2sh_p2wpkh<K: PublicKey>(pubk: &K) -> Hash160 {
    let key_hash = Hash160::from_data(&pubk.to_bytes());

    let bldr = Builder::new().push_int(0).push_slice(key_hash.as_bytes());

    let script = bldr.into_script();
    Hash160::from_data(script.as_bytes())
}

/// Internally, the Stacks blockchain encodes address the same as Bitcoin
/// multisig address over p2sh (p2sh-p2wsh)
fn to_bits_p2sh_p2wsh<K: PublicKey>(num_sigs: usize, pubkeys: &Vec<K>) -> Hash160 {
    let mut bldr = Builder::new();
    bldr = bldr.push_int(num_sigs as i64);
    for pubk in pubkeys {
        bldr = bldr.push_slice(&pubk.to_bytes());
    }
    bldr = bldr.push_int(pubkeys.len() as i64);
    bldr = bldr.push_opcode(btc_opcodes::OP_CHECKMULTISIG);

    let mut digest = Sha256::new();
    let mut d = [0u8; 32];

    digest.update(bldr.into_script().as_bytes());
    d.copy_from_slice(&digest.finalize());

    let ws = Builder::new().push_int(0).push_slice(&d).into_script();
    Hash160::from_data(ws.as_bytes())
}

/// Convert a number of required signatures and a list of public keys into a byte-vec to hash to an
/// address.  Validity of the hash_flag vis a vis the num_sigs and pubkeys will _NOT_ be checked.
/// This is a low-level method.  Consider using StacksAdress::from_public_keys() if you can.
pub fn public_keys_to_address_hash<K: PublicKey>(
    hash_flag: &AddressHashMode,
    num_sigs: usize,
    pubkeys: &Vec<K>,
) -> Hash160 {
    match *hash_flag {
        AddressHashMode::SerializeP2PKH => to_bits_p2pkh(&pubkeys[0]),
        AddressHashMode::SerializeP2SH => to_bits_p2sh(num_sigs, pubkeys),
        AddressHashMode::SerializeP2WPKH => to_bits_p2sh_p2wpkh(&pubkeys[0]),
        AddressHashMode::SerializeP2WSH => to_bits_p2sh_p2wsh(num_sigs, pubkeys),
    }
}
