Based on my investigation, I found a genuine local analog: the canonical EVM contracts received an explicit check-effects-interactions (CEI) fix for exactly this class of bug in `IntentGatewayV2.fillOrder`, but the parallel Tron deployment of the same contract was not patched with it.

### Title
Reentrancy in Tron `IntentGatewayV2.fillOrder` fill path allows stealing escrowed order funds (missing CEI fix present in EVM version) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The main EVM implementation of the Intent Gateway (`evm/src/apps/intentsv2/IntrinsicIntents.sol` and `ExtrinsicIntents.sol`) was patched against a `settleAuction`-style reentrancy bug by moving `_filled[commitment] = msg.sender` to the very top of `_fillSameChain`/`_fillCrossChain`, before any ETH/token transfer to the beneficiary [1](#0-0) . This fix is explicitly documented and regression-tested in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`, which describes the pre-fix vulnerability: a malicious `beneficiary` contract re-entering `fillOrder` during the ETH transfer, while `_filled[commitment]` was still unset, to drain escrowed inputs and fees [2](#0-1) .

The same `IntentGatewayV2` contract is separately maintained for Tron under `evm/tron/contracts/apps/IntentGatewayV2.sol`. A repo-wide search for the fix marker `_filled[commitment] = msg.sender` returns matches only in the EVM `intentsv2` files, not in the Tron file, while `evm/tron/contracts/apps/IntentGatewayV2.sol` otherwise mirrors the vulnerable pre-fix architecture: `withdraw()` performs `_orders[...] -= amount` and native/ERC20 `.call` transfers to the beneficiary in a loop [3](#0-2) , and `cancelOrder`'s destination-side path also transfers control externally as part of dispatch flows [4](#0-3) . Since Tron's TVM executes Solidity-compiled bytecode with the same call/reentrancy semantics as EVM, any un-migrated `fillOrder`/`_fillSameChain` logic on this fork is exposed to the identical exploit primitive that was fixed upstream: an attacker-controlled `beneficiary` re-entering `fillOrder` via the `receive()`/ERC-20 callback hook during output-token delivery, before `_filled[commitment]` is set, to claim escrowed inputs and fees more than once or divert value that should have gone to the legitimate solver.

### Impact Explanation
This is a direct fund-theft / double-settlement primitive matching the bounty's "stealing or loss of funds" and "replay/double-claim/double-settlement" categories. An unprivileged attacker who places or benefits from an order can re-enter the fill path before the settlement marker is written, draining escrowed input tokens and transaction fees from the gateway on the Tron deployment — the exact mechanism the upstream EVM fix (and this bug class, H-01 `settleAuction`) was designed to prevent.

### Likelihood Explanation
High, if the Tron contract's `fillOrder`/fill-loop logic was not updated in lockstep with the EVM CEI fix. The attack requires only a self-deployed malicious beneficiary/token contract and a normal call to the public `fillOrder` entrypoint — no relayer, prover, or admin compromise is needed, consistent with the accepted C4 finding's PoC pattern (custom token/contract re-entering during transfer).

### Recommendation
Audit `evm/tron/contracts/apps/IntentGatewayV2.sol` for the same fill functions (`fillOrder`, and any `_fillSameChain`/`_fillCrossChain` equivalents) and apply the identical CEI fix used in `evm/src/apps/intentsv2/{IntrinsicIntents,ExtrinsicIntents}.sol`: set `_filled[commitment] = msg.sender` (or the cancellation beneficiary marker) before any external token/ETH transfer, and add `nonReentrant` guards consistently across all Tron-side entrypoints that move escrowed funds, mirroring `cancelOrder`'s `nonReentrant` modifier already present in the EVM version [5](#0-4) .

### Proof of Concept
1. Attacker deploys a malicious `beneficiary` contract (or ERC-20-like token) whose `receive()`/`transfer` hook calls back into `IntentGatewayV2.fillOrder` on the Tron deployment, analogous to `ReentrantBeneficiary` in the EVM test suite [6](#0-5) .
2. Attacker (as order user) places an order with this beneficiary and a native/ETH-equivalent output, then arms the reentrant payload.
3. A legitimate solver (or the attacker itself) calls `fillOrder`; if the Tron fill implementation still sets `_filled[commitment]` only at the end (post fund transfer) — as the pre-fix EVM code did — the callback re-enters `fillOrder`/triggers a second `withdraw`-style payout before the guard is set, letting the attacker claim escrow and fees a second time.
4. Because I could not directly view the body of the Tron `fillOrder` function (only `withdraw`/`cancelOrder` sections were retrieved), this should be confirmed by a full read of that function in a Devin session; the absence of the `_filled[commitment] = msg.sender` CEI marker anywhere in `evm/tron/contracts/apps/IntentGatewayV2.sol` is the concrete local signal that the fix was not ported.
