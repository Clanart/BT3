### Title
Out-of-range `Participant` index in PedPoP blame evaluation panics via unchecked `HashMap` indexing (denial of service) - (crypto/dkg/pedpop/src/lib.rs)

### Summary
CVE-2019-19647 is a "missing validation of an attacker-controlled value leads to memory corruption / crash" bug in radare2. The analogous shape in Serai is `BlameMachine::blame` / `AdditionalBlameMachine::blame` in the in-scope `crypto/dkg/pedpop` crate: the `sender` and `recipient` `Participant` values are taken directly from the caller (deserialized from an untrusted accusation/blame message, where `Participant::new` only rejects zero), and are used to index `HashMap`s that only contain keys `1..=n`. Rust's `HashMap` `Index` implementation panics on a missing key, so any accusation naming a participant index greater than `n` crashes the evaluating party.

### Finding Description
`Participant` is "explicitly non-zero" — `Participant::new(u16)` only rejects `0`, and callers deserialize it straight from wire data (e.g. the 2-byte `accuser`/`faulty` fields in `Transaction::InvalidDkgShare` and the `accuser`/`accused` fields of `CoordinatorMessage::VerifyBlame`) with no check that the index is within `1..=n`.

In `blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609):

- It calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`, which performs `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388). `enc_keys` is only populated for `Participant(1)..=Participant(n)` via `register` (encryption.rs:351-362) / `Decryption::new` + `AdditionalBlameMachine::new` (lib.rs:654-661). A `decryptor` (the `recipient` argument) outside that range panics.
- If `msg.pop.verify` fails first, it returns `sender` without indexing — but on a well-formed message (a real, properly-signed `EncryptedMessage` copied from the wire, as the docs require) execution reaches `self.commitments[&sender]` (lib.rs:599), which likewise panics for `sender > n`.

There is no `n`-bound check on `sender` or `recipient` anywhere in `blame`, `blame_internal`, `decrypt_with_proof`, or `AdditionalBlameMachine::new`. The crate's own docs warn "Usage of invalid commitments is considered undefined behavior, and may cause everything from inaccurate blame to panics" (lib.rs:647-648), but here the commitments are all valid — the panic is driven purely by the attacker-chosen participant indexes.

### Impact Explanation
Any party able to submit an accusation/blame (in Serai this is a public tributary transaction carrying raw `u16` participant indexes, evaluated by `AdditionalBlameMachine::new(...).blame(accuser, accused, ...)` in the blame-verification path) can crash every process that evaluates it by setting `accuser` or `accused` to a non-zero index greater than `n` (e.g. `0xFFFF`). This is an unprivileged-input-triggered denial of service on the DKG accountability path — the same impact class as the CVE (crash from unvalidated input), and it also lets a faulty participant evade blame resolution by poisoning the evaluation. Medium severity: reliable crash, no secret leakage.

### Likelihood Explanation
The path is reached whenever a blame/accusation is evaluated. Crafting the input is trivial — the participant fields are just `u16`s and only `0` is rejected. The encrypted share message must be a copy of a real authenticated message from `sender`, but since `sender` itself is attacker-chosen and bogus, `decrypt_with_proof` panics on `enc_keys[&decryptor]` before message contents matter (or `commitments[&sender]` is hit for any `sender > n` once the PoP verifies). One transaction suffices to panic all evaluators.

### Recommendation
In `blame`, `blame_internal`, and `decrypt_with_proof`, validate that `sender` and `recipient` are in `1..=n` (or members of `commitments`/`enc_keys`) before indexing, and return an error or a defined "invalid accusation" outcome instead of panicking. Replace `map[&key]` indexing with `map.get(&key)` + error propagation, mirroring how `MissingParticipant`/`InvalidParticipant` errors are already handled elsewhere (`validate_map`, lib.rs:57-83). Deserializers of accusation transactions should also bound participant indexes by the session's `n`.

### Proof of Concept
```rust
// Any ciphersuite; n = 5. Construct an AdditionalBlameMachine as a blame evaluator would.
let params_n = 5u16;
let mut commitment_msgs = HashMap::new();
for i in 1 ..= params_n {
  commitment_msgs.insert(Participant::new(i).unwrap(), /* valid EncryptionKeyMessage */);
}
let machine =
  AdditionalBlameMachine::<Ristretto>::new(context, params_n, commitment_msgs).unwrap();

// `sender` is a non-zero Participant never in 1..=n — deserializable from the wire.
let evil_sender = Participant::new(0xFFFF).unwrap();
let recipient = Participant::new(1).unwrap();

// `msg` is a well-formed EncryptedMessage copied from any real share message.
// Panic 1 (if PoP verify is reached): enc_keys[&decryptor] fine, then
//   commitments[&evil_sender] -> HashMap index panic.
// Alternatively evil recipient -> enc_keys[&0xFFFF] panics inside decrypt_with_proof.
machine.blame(evil_sender, recipient, msg, proof); // thread panics
```

The panic sites are `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:599) and `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388); neither map contains keys beyond `1..=n` (populated at lib.rs:656-660 and encryption.rs:360), and `Participant::new` only rejects `0`, so the indexes are attacker-controllable through the serialized accusation.
