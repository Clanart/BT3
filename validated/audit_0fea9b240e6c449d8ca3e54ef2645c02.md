## Analysis

The seed report is about non-extensible, incomplete decimal-scaling logic. The closest real, locally-provable analog is `convert_to_balance` in `pallet-hyper-fungible-token`, which implements decimal conversion asymmetrically — it only ever *divides* by `10^(erc_decimals - local_decimals)` using `saturating_sub`, so whenever `local_decimals > erc_decimals` the required upscale never happens, and cross-chain transfers silently mis-credit beneficiaries. [1](#0-0) 

### Title
Asymmetric decimal conversion in `convert_to_balance` causes incorrect (under-)crediting on inbound HFT transfers - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`convert_to_balance` is used by `on_accept` and `on_timeout` in the `hyper-fungible-token` pallet to convert an incoming ERC-20-denominated `U256` amount into the local `Balance` type. It only implements the "erc_decimals > local_decimals" scaling direction (divide by `10^(erc_decimals - local_decimals)`); when `local_decimals > erc_decimals`, `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the function divides by `10^0 = 1` — i.e. it applies **no scaling at all**, instead of the multiply-up that correctness requires. [2](#0-1) 

### Finding Description
`on_accept` (mint/transfer path for an incoming cross-chain post request) and `on_timeout` (refund path) both compute:

```rust
let decimals = ...; // local asset/native decimals
let erc_decimals = Precisions::<T>::get(local_asset_id, source)...; // remote ERC20 decimals
let amount = convert_to_balance::<Balance>(U256::from(message.amount), erc_decimals, decimals)?;
``` [3](#0-2) [4](#0-3) 

`convert_to_balance`'s doc comment itself only describes the "divide" case ("Divides by `10^(erc_decimals - local_decimals)` to scale down from ERC20 precision") and never handles the inverse case where the local asset has *more* decimal places than the remote ERC-20 representation. This is structurally the same defect class as the reported issue: decimal handling that is written for one specific numeric relationship (like the hardcoded USDC/wBTC branches in the external report) and does not generalize — here, it silently degrades to a no-op instead of reverting or scaling correctly, for any asset pairing where `local_decimals > erc_decimals`.

Concretely: if a local asset is configured with `local_decimals = 18` (an ordinary ERC-6160-style pallet asset, as the token-gateway docs mandate: "ERC6160 assets on EVM chains should always use 18") and the remote ERC-20 side records `erc_decimals = 6` (e.g. a USDC-style token bridged in), then for an incoming amount of `1_000_000` (i.e. "1.0" token in 6-decimal units):

- Correct behavior: multiply by `10^(18-6) = 10^12` → beneficiary should receive `1_000_000 * 10^12` local base units (1.0 token at 18 decimals).
- Actual behavior: `erc_decimals.saturating_sub(local_decimals) = 6.saturating_sub(18) = 0` → divide by `10^0 = 1` → beneficiary receives `1_000_000` local base units, i.e. `0.000000000001` tokens (12 orders of magnitude short).

`convert_to_erc20` (used for the outbound teleport-style dispatch, going local→ERC) has the mirrored, complementary bug: it multiplies by `10^(erc_decimals - local_decimals)`, saturating to `10^0=1` when `erc_decimals < local_decimals`, so outbound amounts are similarly not scaled down when they should be. [5](#0-4) 

No guard exists anywhere in `on_accept`/`on_timeout` to detect or reject this decimal relationship — `Precisions::<T>::get` only checks that a precision value is *configured*, not that it is consistent with the conversion function's implicit "erc_decimals ≥ local_decimals" assumption. [6](#0-5) 

### Impact Explanation
This directly matches the bounty's "wrong beneficiary or amount" / "false state acceptance" impact class: funds that are locked/burned on the source chain are credited on the destination chain in a grossly incorrect amount whenever the local asset's configured decimals exceed the remote ERC-20's decimals. This is not a cosmetic rounding error — it is off by a full power-of-ten factor (`10^(local_decimals - erc_decimals)`), meaning users effectively lose nearly all of their bridged value while the source-chain leg has already irreversibly locked or burned the full amount. The same defective helper is reused in `on_timeout`'s refund path, so refunds after a failed cross-chain transfer would also be mis-scaled in the same direction.

### Likelihood Explanation
This is a deterministic protocol/config-driven bug, not a probabilistic one — it triggers on every single inbound message for any asset pairing where `local_decimals > erc_decimals`, which is a normal, expected configuration (e.g., an 18-decimal local pallet asset representing a 6-decimal remote stablecoin, or any local asset using more decimals than its counterpart). Because it requires no attacker action beyond a legitimate cross-chain transfer using a token pairing chosen by whoever registers the asset (via `create_erc6160_asset`/`update_asset_precision` per the token-gateway docs), the likelihood is Medium-to-High for any deployment that onboards assets with decimals lower than 18 on the EVM side while keeping 18-decimal local assets (a very plausible and even encouraged configuration, since the docs recommend ERC6160 assets use 18 decimals uniformly, but real-world bridged tokens like USDC/USDT commonly use 6).

### Recommendation
Rewrite `convert_to_balance` and `convert_to_erc20` to handle both directions symmetrically instead of relying on `saturating_sub` to silently no-op the unhandled case:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}
```

Apply the mirrored fix to `convert_to_erc20`. Add unit/integration tests exercising both `erc_decimals > local_decimals` and `erc_decimals < local_decimals` cases (the current test suite, as far as observed, does not appear to cover the latter).

### Proof of Concept
1. Register a local asset (via `create_erc6160_asset`) with `local_decimals = 18`.
2. Configure `Precisions::<T>` for that asset/remote-chain pair with `erc_decimals = 6` (mirroring a 6-decimal stablecoin on the EVM side).
3. Have the corresponding EVM contract dispatch a `Message` with `amount = 1_000_000` (representing "1.0" token at 6 decimals) to the pallet's `on_accept`.
4. Observe that `convert_to_balance(U256::from(1_000_000), 6, 18)` computes `1_000_000 / 10^(6u8.saturating_sub(18)) = 1_000_000 / 10^0 = 1_000_000`, crediting the beneficiary `1_000_000` base units of an 18-decimal asset (`0.000000000001` tokens) instead of the correct `1_000_000 * 10^12` base units (`1.0` token) — a 10^12x under-credit, while the source chain has already locked/burned the full "1.0 token" equivalent.
