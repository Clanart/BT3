### Title
ReceivedOutput deserialization never validates the offset/output binding, so arbitrary bytes are accepted as spendable received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an attacker-controlled `(offset, TxOut, OutPoint)` triple and returns a `ReceivedOutput` that downstream wallet/scheduler code treats as a confirmed, spendable output owned by the scanner's key. It performs no check that `output.script_pubkey` actually equals the Taproot script derived from `key + offset * G`, nor any sanity check on the claimed value or outpoint. This mirrors the kernel bug class: a value returned/parsed without a validity check is misinterpreted as a legitimate object (there, a positive integer as a file pointer; here, arbitrary bytes as an owned spendable output).

### Finding Description
The only construction path that is internally consistent is `Scanner::scan_transaction`, which builds a `ReceivedOutput` solely when `self.scripts.get(&output.script_pubkey)` finds a registered offset [1](#0-0) . That binding — "this output pays to `p2tr_script_buf(key + G*offset)`" — is what makes the output spendable by the threshold key via `offset()` [2](#0-1) .

`ReceivedOutput::read` drops that invariant entirely. It reads a canonical scalar, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, and returns them as a struct with no cross-validation [3](#0-2) . Unlike `read_F`/`read_G`, which reject non-canonical or invalid encodings [4](#0-3) , the decoded `TxOut`'s `script_pubkey` is never compared against `p2tr_script_buf(key + G*offset)`, and `ReceivedOutput` carries no key context to enforce this later. `ReceivedOutput::write`/`serialize` confirm the round-trip format is just the raw triple [5](#0-4) .

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (the sink is explicitly reachable in-scope) can fabricate a `ReceivedOutput` claiming ownership of any `TxOut`/`OutPoint` pair:

- Claiming funds that were never received: a forged `OutPoint`/`TxOut` with a large `value` is reported by `value()` as real balance [6](#0-5) .
- Funds reported received that are not spendable: the `script_pubkey` need not correspond to `key + offset*G`, so any code selecting this output for signing produces an input it cannot actually spend — burning a signing session and, in the worst case, a permanently unspendable input set.
- The companion `Scanner::register_offset` documentation acknowledges that arbitrary offsets can introduce spendable script paths [7](#0-6) , but `read` does not even guarantee the offset and script are related at all.

### Likelihood Explanation
The deserialization path is deterministic and requires no cryptographic work: 32 bytes of scalar plus consensus-encoded `TxOut`/`OutPoint`. Feasibility depends on a consumer reading `ReceivedOutput`s from an untrusted source rather than only from `Scanner::scan_transaction`/`scan_block` results [8](#0-7) ; where outputs are persisted or relayed between components, a malicious writer can inject forged entries. The fix cost is low; the lack of any validation is unambiguous in the code.

### Recommendation
Bind the offset to the output at the trust boundary. Either (a) make `ReceivedOutput` store the scanner key context and have `read` verify `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset) == Some(output.script_pubkey)`, rejecting mismatches with an `io::Error`; or (b) make `ReceivedOutput::read` crate-private / document it as trusted-only and expose a `read_with(&Scanner, ...)` that performs the script check. The `TxOut`/`OutPoint` fields should only ever originate from `scan_transaction`-validated data.

```rust
// Attacker-controlled bytes for ReceivedOutput::read
let mut buf = Vec::new();
// Any scalar offset
buf.extend(Scalar::ONE.to_bytes());
// A TxOut paying to ANYONE (e.g., attacker's own P2TR key, or an empty script),
// with a fabricated value
let fake_txout = TxOut {
    value: Amount::from_sat(1_000_000_000),
    script_pubkey: ScriptBuf::new_p2tr_tweaked(
        TweakedPublicKey::dangerous_assume_tweaked(attacker_x_only_key),
    ),
};
buf.extend(serialize(&fake_txout));
// An outpoint that doesn't exist / belongs to someone else
buf.extend(serialize(&OutPoint::new(Txid::from_byte_array([0x41; 32]), 0)));

// This succeeds — no binding between offset, script_pubkey, or outpoint is checked
let ro = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(ro.value(), 1_000_000_000); // reported as received funds
// Spending it via the threshold key + offset is impossible: the output's
// script_pubkey does not equal p2tr_script_buf(key + offset * G)
```

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
```
