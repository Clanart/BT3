### Title
Unchecked ERC20 return value in CW20-wraps-ERC20 pointer contract allows a non-standard ERC20 to make `transfer`/`transfer_from` appear successful while no tokens move - ([File: example/cosmwasm/cw20/src/contract.rs])

### Summary
The CosmWasm contract that exposes a CW20 interface backed by a real EVM ERC20 token (`example/cosmwasm/cw20/src/contract.rs`) issues `transferFrom`/`transfer` calls to the underlying ERC20 via an EVM delegate-call, but never inspects the ABI-encoded boolean return value of that call. It only relies on the call not reverting. Any ERC20 token that follows the (valid, pre-OpenZeppelin-SafeERC20-era) pattern of returning `false` on failure instead of reverting will cause the CW20 wrapper to treat a failed transfer as successful.

### Finding Description
`transfer()` and `transfer_from()` in the example CW20-over-ERC20 pointer contract build the ABI payload for the underlying token's `transfer`/`transferFrom` and dispatch it as an `EvmMsg::DelegateCallEvm`: [1](#0-0) [2](#0-1) 

The payload is produced purely by ABI-encoding the call (`erc20_transfer_payload`/`erc20_transfer_from_payload`), with no decoding step afterward: [3](#0-2) 

On the chain side, this `DelegateCallEvm` message is routed to `HandleInternalEVMDelegateCall`, which calls `k.CallEVM`. `CallEVM` only errors when the underlying EVM execution reverts (`res.Err != nil`); it never inspects/decodes `res.ReturnData` to confirm the ERC20's boolean success flag: [4](#0-3) 

Contrast this with the reverse-direction pointer (`CW20ERC20Pointer.sol`, which exposes an ERC20 interface backed by a CW20 token): there, `_execute` checks `success` from the delegatecall to the wasmd precompile, and CosmWasm's native message dispatch will actually raise an error/revert on a failing cw20 `transfer`/`transfer_from`, so that direction is safe: [5](#0-4) 

But for the ERC20-wrapped-as-CW20 direction, an ERC20 contract that returns `false` instead of reverting on a failed `transfer`/`transferFrom` (a non-standard-but-spec-legal ERC20, matching the exact bug class in the referenced report) will cause:
1. The EVM call to succeed with `res.Err == nil` and `ReturnData = abi.encode(false)`.
2. `CallEVM` to return that data with no error.
3. The wasm contract's `transfer`/`transfer_from` handler to complete successfully, emitting `action: transfer`/`transfer_from` attributes and a `Response` indicating success — even though no tokens were actually moved on the underlying ERC20.

### Impact Explanation
Any consumer relying on this CW20 pointer's execute-response/attributes as proof-of-transfer (e.g., a CosmWasm vault, DEX, or `Cw20ReceiveMsg`-based hook consuming `send`/`send_from` on this pointer) can be tricked into crediting a deposit or releasing funds/goods that were never actually received, because the underlying ERC20 silently failed the transfer. This is a fund-loss vector reachable by any user who can point such a wrapper at (or interact with a wrapper already pointed at) a non-standard ERC20 token that returns `false` on failure rather than reverting — no special privilege required.

### Likelihood Explanation
Likelihood is bounded by the fact that this specific contract lives under `example/cosmwasm/cw20/` rather than being unambiguously proven, from the available index, to be an unconditionally-deployed production pointer contract type (unlike `CW20ERC20Pointer.sol`, which is clearly wired into `RegisterPointer`/`PointerType_ERC20`). I was not able to conclusively confirm within the indexed code whether this exact wasm binary is the one instantiated in production for `SetERC20CW20Pointer`/reverse pointer registration (the `.wasm` artifact and its registration path were not found in the search results). If it is deployed as a live pointer type, the likelihood is high, since triggering it only requires pairing the pointer with (or the pointer already being paired with) an ERC20 implementing the non-reverting-`false` pattern and calling `transfer`/`transfer_from`.

### Recommendation
- In `example/cosmwasm/cw20/src/contract.rs`, after issuing the `DelegateCallEvm` for `transfer`/`transfer_from`, decode the returned bytes and assert the boolean result is `true` (or use a reply/submessage pattern to inspect the delegate call's `ReturnData`), erroring out otherwise — mirroring the `SafeERC20` pattern from the report.
- Alternatively/additionally, have `x/evm/keeper/evm.go`'s `CallEVM` (or a wrapper used specifically for pointer-initiated ERC20 calls) decode standard ERC20 return values and surface a business-logic error when a `transfer`/`transferFrom` call returns `false`, so pointer contracts built on top of it cannot silently treat failed transfers as successes.

### Proof of Concept
1. Deploy a non-standard ERC20 contract whose `transfer`/`transferFrom` returns `false` (does not revert) when the sender has insufficient balance/allowance.
2. Instantiate/point the `example/cosmwasm/cw20` wrapper contract at this ERC20 (`ERC20_ADDRESS` storage).
3. As an account with zero balance/allowance on the underlying ERC20, call `execute { transfer_from: { owner, recipient, amount } }` (or `transfer`) on the CW20 wrapper.
4. Observe: `HandleInternalEVMDelegateCall` → `CallEVM` returns `nil` error because the EVM call did not revert (`res.Err == nil`); the wasm contract's `transfer_from` returns a successful `Response` with `action: "transfer_from"` attributes, even though the ERC20 balance never changed (verifiable via `erc20_balance` query before/after).
5. Any downstream consumer trusting the `transfer_from`/`send_from` success (e.g., a `Cw20ReceiveMsg` hook) proceeds as if funds were received.

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

func (k *Keeper) CallEVM(ctx sdk.Context, from common.Address, to *common.Address, val *sdk.Int, data []byte) (retdata []byte, reterr error) {
	if ctx.IsEVM() && !ctx.EVMEntryViaWasmdPrecompile() {
		return nil, errors.New("sei does not support EVM->CW->EVM call pattern")
	}
	if to == nil && len(data) > params.MaxInitCodeSize {
		return nil, fmt.Errorf("%w: code size %v, limit %v", core.ErrMaxInitCodeSizeExceeded, len(data), params.MaxInitCodeSize)
	}
	if to != nil && to.Cmp(common.HexToAddress(solo.SoloAddress)) == 0 {
		return nil, errors.New("cannot call Solo precompile via CosmWasm")
	}
	value := utils.Big0
	if val != nil {
		if val.IsNegative() {
			return nil, sdkerrors.ErrInvalidCoins
		}
		value = val.BigInt()
	}
	// This call was not part of an existing StateTransition, so it should trigger one
	executionCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx)).WithEVMEntryViaWasmdPrecompile(false)
	stateDB := state.NewDBImpl(executionCtx, k, false)
	gp := k.GetGasPool()
	evmMsg := &core.Message{
		Nonce:     stateDB.GetNonce(from), // replay attack is prevented by the AccountSequence number set on the CW transaction that triggered this call
		GasLimit:  k.getEvmGasLimitFromCtx(ctx),
		GasPrice:  utils.Big0, // fees are already paid on the CW transaction
		GasFeeCap: utils.Big0,
		GasTipCap: utils.Big0,
		To:        to,
		Value:     value,
		Data:      data,
		From:      from,
	}
	// should not increment nonce since this isn't a transaction
	res, err := k.applyEVMMessage(ctx, evmMsg, stateDB, gp, false)
	if err != nil {
		return nil, err
	}
	k.consumeEvmGas(ctx, res.UsedGas)
	if res.Err != nil {
		return nil, res.Err
	}
	surplus, err := stateDB.Finalize()
	if err != nil {
		return nil, err
	}
	vmErr := ""
	if res.Err != nil {
		vmErr = res.Err.Error()
	}
	existingReceipt, err := k.GetTransientReceipt(ctx, ctx.TxSum(), uint64(ctx.TxIndex())) //nolint:gosec
	if err == nil {
		for _, l := range existingReceipt.Logs {
			stateDB.AddLog(&ethtypes.Log{
				Address: common.HexToAddress(l.Address),
				Topics:  utils.Map(l.Topics, common.HexToHash),
				Data:    l.Data,
			})
		}
		if existingReceipt.VmError != "" {
			vmErr = fmt.Sprintf("%s\n%s\n", existingReceipt.VmError, vmErr)
		}
	}
	existingDeferredInfo, found := k.GetEVMTxDeferredInfo(ctx)
	if found {
		surplus = surplus.Add(existingDeferredInfo.Surplus)
	}
	receipt, err := k.WriteReceipt(ctx, stateDB, evmMsg, ethtypes.LegacyTxType, ctx.TxSum(), res.UsedGas, vmErr, false)
	if err != nil {
		return nil, err
	}
	bloom := ethtypes.Bloom{}
	bloom.SetBytes(receipt.LogsBloom)
	k.AppendToEvmTxDeferredInfo(ctx, bloom, ctx.TxSum(), surplus)
	return res.ReturnData, nil
}
