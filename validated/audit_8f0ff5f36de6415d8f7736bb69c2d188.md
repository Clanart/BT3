## Analog Found: Unbounded Python recursion in wallet outer-puzzle driver matching (`match_puzzle`)

### Title
Unbounded recursion in wallet CAT/NFT/CR-CAT outer-puzzle `match()` drivers allows an offer/coin puzzle with deeply nested layers to crash the wallet via stack overflow - ([File: chia/wallet/outer_puzzles.py])

### Summary
The class hint is unbounded Python recursion over an attacker-controlled nested data structure with no depth limit, causing an uncaught `RecursionError`/stack overflow DoS. The same pattern exists in Chia's wallet puzzle-driver layer: `match_puzzle()` and each `*OuterPuzzle.match()` implementation recurse into the puzzle's inner layer with no depth bound, and the recursion depth is driven entirely by the untrusted puzzle reveal supplied by a coin, an offer, or a spend bundle.

### Finding Description
`chia/wallet/outer_puzzles.py` dispatches puzzle identification through `match_puzzle()`: [1](#0-0) 

Each concrete driver (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`) implements `.match()` by unwrapping one puzzle layer and then calling back into the shared `self._match` callable (which is `match_puzzle` itself) on the *inner* puzzle to build the `"also"` chain: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Each of these `match()` calls is mutually recursive through `match_puzzle()` → `driver.match()` → `self._match()` → `match_puzzle()` → ... with **no depth counter, no maximum nesting check, and no `try/except RecursionError`** anywhere in this call chain. `PuzzleInfo.also()`/`check_type()` in `chia/wallet/puzzle_drivers.py` similarly recurse over the resulting `"also"` dictionary chain without a bound: [7](#0-6) 

The depth of this recursion is controlled by how many outer-puzzle layers (`CAT_MOD`, `SINGLETON_MOD`, ownership layer, metadata layer, CR layer, etc.) are curried around the puzzle. Constructing such nested layers is computationally cheap for an attacker (e.g., `construct_cat_puzzle(CAT_MOD, tail, construct_cat_puzzle(CAT_MOD, tail, ...))`), as demonstrated by the test fixtures that already build nested/double-layer puzzles: [8](#0-7)  and NFT layering tests [9](#0-8) .

`match_puzzle` is invoked on untrusted puzzle reveals from offers and trade data — e.g. `chia/wallet/trading/offer.py` and `chia/wallet/trade_manager.py` call into this driver-matching path when parsing an incoming offer or coin puzzle reveal (both files were confirmed to call `match_puzzle`/`UnknownPuzzle(known_program=...)`). An offer counterparty fully controls the puzzle reveal bytes embedded in an offer file, and a wallet-syncing coin's puzzle reveal is likewise attacker-supplied when a malicious party sends a coin to a victim's puzzle hash.

A grep across the repository confirmed there is **no** `RecursionError` handling and **no** `sys.setrecursionlimit` adjustment anywhere in the codebase, meaning a `RecursionError` raised deep in this chain propagates uncaught to the calling wallet RPC/sync code path.

### Impact Explanation
This is directly analogous to the underscore `_.flatten`/`_.isEqual` unbounded-recursion DoS: a remote counterparty (offer taker/maker, or a peer sending a coin with a deeply layered puzzle) can craft a puzzle reveal with enough nested outer-puzzle layers to exceed Python's default recursion limit (~1000) when the victim's wallet calls `match_puzzle()` while parsing an offer or reconciling a coin's puzzle-driver info. This raises an uncaught `RecursionError`, which can abort the in-progress wallet RPC call, offer-parsing flow, or coin-state processing task — a spend/offer-triggered transaction-processing halt in the victim's wallet. Because offer files and puzzle reveals are exactly the kind of untrusted input the CWE-674/CWE-770 advisory describes, and there is no caught exception or depth guard, this satisfies the required "spend-triggered transaction-processing halt" impact class.

### Likelihood Explanation
Likelihood is Medium-to-High: constructing nested puzzle layers is cheap (pure Python/CLVM currying, no on-chain cost is paid until the fake/oversized puzzle is actually included in a real coin or offer file — and merely *parsing* an offer file or received puzzle reveal locally in the wallet does not require broadcasting a valid spend at all). An attacker only needs to get the victim wallet to call `match_puzzle`/`PuzzleInfo.also()`/`check_type()` against a maliciously deep puzzle — which happens automatically for any incoming offer file the user opens for inspection (`get_offer_summary`), or any coin puzzle the wallet attempts to classify during sync.

### Recommendation
Add an explicit depth limit/counter to `match_puzzle()`, each `*OuterPuzzle.match()` implementation, and `PuzzleInfo.also()`/`check_type()`, rejecting or returning `None` once a sane maximum nesting depth (e.g., 50–100 layers) is exceeded. Alternatively, convert the mutual recursion into an explicit iterative loop/stack (as already done for `sha256_treehash` in `chia/types/blockchain_format/tree_hash.py`), and wrap outer-puzzle matching entry points in a guard that catches `RecursionError` and treats the puzzle as unmatched/unknown rather than letting the exception escape to the caller.

### Proof of Concept
Not independently executed (index-only investigation), but the vulnerable pattern is directly demonstrated by the existing test helpers that build nested outer-puzzle layers: [8](#0-7) 
Extending this pattern to build ~2000+ nested `construct_cat_puzzle(CAT_MOD, tail, ...)` layers and calling `match_puzzle(UnknownPuzzle(known_program=deeply_nested_puzzle))` (as would happen automatically when a victim wallet inspects an offer or incoming coin containing such a puzzle) would exceed Python's recursion limit and raise an uncaught `RecursionError`, since `CATOuterPuzzle.match()` recurses through `self._match` for every layer with no bound: [2](#0-1)

                return True
            else:
                return False
        elif self.type() == types[0]:
            types.pop(0)
