### Title
Insufficient `finality_depth` Lower-Bound Allows Operator Collateral Loss via Bitcoin Reorg - (File: `crates/clementine-config/src/protocol.rs`)

### Summary

The `finality_depth` parameter governs how many Bitcoin block confirmations are required before bridge events (deposit finalization, kickoff dispatch, tx-sender finality) are treated as irreversible. The code enforces only `finality_depth >= 1`, which is trivially insecure. The shipped `.env.example` sets `FINALITY_DEPTH=1`, and the test-data `protocol_paramset.toml` also sets `finality_depth = 1`. The deployed testnet4 config sets `finality_depth = 6` — the same value the external report identifies as the original unsafe default. With `finality_depth = 1` an operator will dispatch kickoff transactions for deposits that have only one Bitcoin confirmation; a reorg of depth ≥ 2 then leaves the operator with a spent kickoff UTXO and no valid deposit to reimburse against, permanently locking their collateral.

---

### Finding Description

`ProtocolParamset.finality_depth` is the single value that controls finality across the entire bridge stack:

- `is_block_finalized()` — used by `FinalizedBlockFetcherTask` to decide when to dispatch kickoff state machines
- `fetch_new_blocks()` in `BitcoinSyncer` — halts the syncer when reorg depth exceeds `finality_depth`
- `check_if_utxo_spending_tx_is_finalized()` — gates round-tx advancement
- `sync_transaction_confirmations_via_rpc()` in tx-sender — marks bridge transactions as final

The only validation applied at load time is:

```rust
// crates/clementine-config/src/protocol.rs  line 138
if paramset.finality_depth < 1 {
    return Err(BridgeError::ConfigError(
        "Finality depth must be at least 1".to_string(),
    ));
}
```

`finality_depth = 1` passes this check. The same check is duplicated in `from_env()` and `check_general_requirements()` — all three accept 1.

The shipped example configuration explicitly sets this insecure value:

```
# .env.example  line 69
FINALITY_DEPTH=1
```

The test-data paramset file also sets `finality_depth = 1`. The `docs/usage.md` directs operators to use `.env.example` as a reference.

The deployed testnet4 config sets `finality_depth = 6`:

```toml
# scripts/docker/configs/testnet4/protocol_paramset.toml  line 20
finality_depth = 6
```

This is the same depth the external report identifies as the original unsafe default for Ethereum (where uncle blocks can appear up to depth 7, and exchanges require ≥ 10 confirmations). Testnet4 has historically exhibited reorgs at this depth.

The deposit-validation path in `verifier.rs` does not check finality depth at all — it only requires the deposit to be confirmed:

```rust
// core/src/verifier.rs  lines 712-730
let blockhash = tx_info.blockhash.ok_or_else(|| {
    BridgeError::InvalidDeposit("Deposit transaction is not confirmed".to_string())
})?;
// ... only checks block_height >= start_height, no finality check
```

With `finality_depth = 1`, `is_block_finalized(H, H+1)` evaluates to `H+1 − H + 1 = 2 ≥ 1 = true`, so block H is treated as final the moment the next block arrives. The `FinalizedBlockFetcherTask` immediately dispatches a kickoff state machine, and the operator automation sends the kickoff transaction spending a kickoff UTXO from the round tx.

---

### Impact Explanation

If a Bitcoin reorg of depth ≥ 2 occurs after the kickoff is sent:

1. The deposit UTXO no longer exists on the canonical chain.
2. The MoveToVault transaction is invalid (spends a non-existent UTXO).
3. The bridge circuit cannot verify the deposit (no valid L2 storage proof).
4. The operator cannot complete the reimbursement flow.
5. The operator's collateral (`collateral_funding_amount`, 99,000,000 sat in the regtest paramset, scaled for production) is permanently locked in the round-tx chain with no path to recovery.

The `BitcoinSyncer` halts on reorgs exceeding `finality_depth`, but the kickoff has already been broadcast and confirmed on the pre-reorg chain. The halt prevents further state updates but does not undo the already-spent kickoff UTXO.

---

### Likelihood Explanation

- Any operator who copies `.env.example` as a production template (explicitly recommended by `docs/usage.md`) will run with `finality_depth = 1`.
- The testnet4 deployment uses `finality_depth = 6`. Testnet4 has documented reorgs at this depth; the external report cites the same value as the original unsafe default.
- On mainnet, reorgs of depth 2 are rare but not impossible; the Ethereum Classic 51% attack cited in the external report reached depth > 100.
- No privileged access is required; the trigger is a natural Bitcoin reorg.

---

### Recommendation

1. **Enforce a network-appropriate minimum in `from_toml_file`, `from_env`, and `check_general_requirements`:**

```rust
let safe_min = match paramset.network {
    Network::Bitcoin  => 10,
    Network::Testnet4 => 10,
    Network::Signet   => 6,
    Network::Regtest  => 1,
    _                 => 10,
};
if paramset.finality_depth < safe_min {
    return Err(BridgeError::ConfigError(format!(
        "finality_depth {} is below the safe minimum {} for {:?}",
        paramset.finality_depth, safe_min, paramset.network
    )));
}
```

2. **Fix `.env.example`** to use a safe default (e.g., `FINALITY_DEPTH=10`) and add a comment explaining the security implications of low values.

3. **Add a finality check to `is_deposit_valid()`** in `verifier.rs` so that deposits with fewer than `finality_depth` confirmations are rejected before signing.

4. **Update the testnet4 `protocol_paramset.toml`** to use `finality_depth = 10`.
