### Title
`Scanner::scan_block` counts coinbase outputs locked by maturity as received, inflating spendable balance - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` reports any output paying to a registered script as a `ReceivedOutput`, and `Scanner::scan_block` applies it to every transaction in a block including the coinbase. Coinbase outputs are unspendable for 100 blocks by consensus. A miner (or anyone who can influence the coinbase of the block they mine — any pool participant) can pay the vault's script, and the scanner will report those funds as a normal spendable `ReceivedOutput`, even though any transaction spending them is consensus-invalid until maturity. This mirrors the reported bug class: assets that cannot actually be transferred out are included in the balance used downstream.

### Finding Description
`scan_transaction` matches solely on `output.script_pubkey` and unconditionally pushes a `ReceivedOutput` containing the output value and its outpoint (`mod.rs:199-214`). `scan_block` iterates `block.txdata` starting at index 0, i.e. including `txdata[0]` (the coinbase) (`mod.rs:221-227`). There is no check for `tx.is_coinbase()`, no maturity tracking, and no flag on `ReceivedOutput` distinguishing a locked coinbase output from a spendable one. The code comments acknowledge this ("bound by maturity... a post-processing pass is needed", `mod.rs:218-220`), but the API itself returns the locked output with no marker, so any caller summing `ReceivedOutput::value()` (as `SignableTransaction::new` does at `send.rs:175`) will treat locked coins as available inputs.

### Impact Explanation
Funds reported received that are not spendable. A `ReceivedOutput` produced from a coinbase cannot be included in a `SignableTransaction` that consensus would accept: a coinbase spend requires 100 confirmations. If the scanner output feeds balance/UTXO selection (e.g., `input_sat` in `SignableTransaction::new` at `send.rs:175`), the vault may construct and sign transactions spending immature outputs (invalid, guaranteed rejection, wasted signing rounds) or report inflated balances — the same "conversion" inaccuracy as the original finding, where locked assets poison the total used for accounting.

### Likelihood Explanation
Reachable by an unprivileged party via public inputs: any miner can add an output paying the vault's publicly known `p2tr` script in their block's coinbase at zero cost beyond the output's own (immature) value. No collusion, key access, or protocol-level privilege is required; it only requires the coinbase to exist in a scanned block, which is inherent to `scan_block`. Exploitation value is limited (the miner burns their own subsidy value for 100 blocks and only causes invalid txs/accounting inflation, not theft), so severity is Medium rather than High.

### Recommendation
In `Scanner::scan_block`, either skip `block.txdata[0]` by default or annotate `ReceivedOutput` with an `is_coinbase`/maturity flag so callers can exclude immature outputs from spendable-balance calculations. Alternatively, have `scan_transaction` take a `coinbase: bool` parameter and refuse (or mark) coinbase-matched outputs, ensuring downstream accounting in `SignableTransaction::new` never counts consensus-locked funds.

### Proof of Concept
```rust
// networks/bitcoin context
// 1. Vault key K is public; script = p2tr_script_buf(K) is publicly derivable.
// 2. Attacker mines a block whose coinbase pays `script` (or wins a pool share doing so).
// 3. Scanner::new(K).unwrap().scan_block(&block) returns a ReceivedOutput with
//    offset ZERO, outpoint = (coinbase_txid, vout), value = coinbase output value.
// 4. Caller sums ReceivedOutput::value() -> counted as spendable balance.
// 5. SignableTransaction::new(vec![that_output], ...).multisig(&keys) -> signs a tx
//    whose input is an immature coinbase output -> rejected by consensus (BIP-30/113,
//    COINBASE_MATURITY = 100), despite the balance having been reported received.
```
Root cause: `scan_block` (`mod.rs:221-227`) scans `block.txdata[0]` and `scan_transaction` (`mod.rs:199-214`) has no coinbase/maturity exclusion, so locked funds enter `ReceivedOutput` identically to spendable ones.
