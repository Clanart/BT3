Based on my research, I was not able to fully verify an unprivileged, reachable path to trigger the exact underflow before the tool budget ran out, but I did find a concrete structural analog to the reported bug class in Hyperbridge's intent-escrow accounting. I'll present it with the caveats that remain unverified.

### Title
Escrow ledger decrement in `_withdraw`/`withdraw` only guards against a zero balance, not against `amount > escrowed` - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
The Curve report's core defect is: a value is computed as a subtraction that can legitimately go negative, but the code only asserts a weaker precondition (implicitly "non-negative") before converting/using it, so the operation reverts (or worse, silently wraps) instead of being clamped. The same *shape* of guard gap exists in Hyperbridge's intent escrow bookkeeping: before decrementing a per-`(commitment, token)` escrow balance, the code checks only that the stored balance is non-zero, not that it is `>= amount` being withdrawn.

### Finding Description
`_withdraw` in `IntentsBase.sol` is the internal function that releases escrowed tokens to a beneficiary for both refunds and fills: [1](#0-0) 

The check is:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();

_orders[body.commitment][token] = escrowed - amount;
```
This only validates `escrowed != 0`; it never validates `escrowed >= amount`. The identical pattern exists, without even the partial mitigations found in the fee-token path, in the older/parallel `IntentGatewayV2.sol` (Tron) contract: [2](#0-1) 

Because Solidity ≥0.8 has built-in checked arithmetic, `escrowed - amount` does not silently wrap to a huge value the way the Vyper `convert(..., uint256)` in the report would fail on a negative `int256` — instead the whole transaction reverts. This is functionally the same failure mode as the reported issue: an assumption of non-negativity is violated, and a legitimate state transition (redeeming/refunding escrow) becomes permanently unexecutable for that commitment/token pair if any code path ever computes a per-iteration `amount` that exceeds the live `_orders[commitment][token]` balance — e.g. through duplicate-token entries in an order's `inputs`/`tokens` list, rounding drift between separately-tracked `TRANSACTION_FEES` and per-token buckets that share the same mapping namespace, or accounting drift between `order.inputs` (used to build refund `WithdrawalRequest`s) and the live escrow after partial fills.

Note: `IntrinsicIntents.sol` was already patched for the analogous rounding-dust bug (Finding #4, see `testPartialFill_RoundingDustReleasedToFinalSolver`) by using the live escrow balance directly on the final fill instead of a proportional calculation: [3](#0-2) 
That fix is *not* mirrored as an explicit `escrowed >= amount` guard in `_withdraw` itself, so any other caller (refund path, cross-chain `RedeemEscrow`/`RefundEscrow`, or a future code path) that supplies an `amount` not perfectly reconciled against the live balance will hard-revert rather than fail gracefully.

### Impact Explanation
If `amount > escrowed` is ever reached for a given `(commitment, token)` pair, the withdrawal transaction reverts unconditionally, and there is no fallback/clamped path (unlike the report's suggested "set to 0" remediation). Because `_withdraw`/`withdraw` is the *only* code path that releases escrowed funds back to a beneficiary (via `RedeemEscrow`, `RefundEscrow`, or `onGetResponse` cancellation), a permanently reverting call for a specific commitment means the escrowed tokens for that order are **irrecoverably locked** in the contract — no retry succeeds because the stored `escrowed` value never changes without going through the same reverting subtraction. This matches the bounty's "loss of funds" / fund-lock category.

### Likelihood Explanation
Low-to-moderate. Solidity's checked arithmetic prevents silent corruption (unlike the Vyper case), so exploitation requires a code path or malformed-but-hash-consistent order/withdrawal structure (e.g., duplicate token entries in `order.inputs`, or drift between the `TRANSACTION_FEES` sentinel bucket and a real token address sharing the same mapping key) that causes a legitimate `amount` to exceed the live `escrowed` balance. I could not fully confirm within the available searches whether an unprivileged user can force such a mismatch purely through `placeOrder`/`cancelOrder` inputs without relying on a malicious counterpart-chain gateway; this needs direct code review of `placeOrder`'s escrow-crediting loop and the `TRANSACTION_FEES` constant definition to close the gap with certainty.

### Recommendation
Add an explicit `if (escrowed < amount) revert InsufficientEscrow();` guard (or clamp to `min(escrowed, amount)`, consistent with the fix already applied in `IntrinsicIntents.sol` for final fills) before every escrow decrement in `_withdraw` (`IntentsBase.sol`) and the mirrored `withdraw` function in `evm/tron/contracts/apps/IntentGatewayV2.sol`. Additionally, audit all callers that construct `WithdrawalRequest.tokens` (place-order escrow crediting, partial-fill proportional calculations, and the `TRANSACTION_FEES` sentinel bucket) to guarantee the invariant `sum(all released amounts) <= amount originally escrowed` holds under duplicate-token and rounding edge cases, so no legitimate withdrawal path can ever compute `amount > escrowed`.

### Proof of Concept
Not independently reproduced in this session due to tool-call limits; a concrete PoC would need to: (1) place an order via `placeOrder` with `order.inputs` containing either a duplicate token entry or a token address colliding with the `TRANSACTION_FEES` sentinel key, (2) trigger a refund/redeem flow that builds a `WithdrawalRequest` from that input list, and (3) show the second (or fee-bucket) iteration of `_withdraw`'s loop computes `amount > _orders[commitment][token]`, causing a hard revert that permanently locks the remaining escrow for that commitment. This should be validated against `placeOrder`'s exact escrow-crediting code and the `TRANSACTION_FEES` constant before treating it as confirmed.
