### Title
Any external party (a Bitcoin miner) can cause Serai's wallet to report received funds that are not spendable, because `scan_block` has no coinbase-maturity access control — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class of the external report — a privileged-effect function reachable by any unprivileged party because no gate restricts who may invoke it — maps onto `Scanner::scan_block`. Just as `mint()` let anyone create vault shares, `scan_block` lets any external party create `ReceivedOutput` entries (i.e., funds the system counts as received) for outputs that the protocol cannot actually spend. A miner is a fully unprivileged external actor; by paying to a Serai-registered `script_pubkey` inside their coinbase transaction, they cause Serai to register funds that are consensus-unspendable for 100 blocks.

### Finding Description
`scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for any output whose `script_pubkey` is in `self.scripts` — matching on script alone, with no check of where the transaction appears in a block or whether it is a coinbase (networks/bitcoin/src/wallet/mod.rs:199-214). `scan_block` then calls `scan_transaction` on every transaction in `block.txdata`, including `block.txdata[0]`, the coinbase (networks/bitcoin/src/wallet/mod.rs:221-227).

A coinbase output cannot be spent until it has 100 confirmations (BIP-30/COINBASE_MATURITY, enforced by Bitcoin consensus). There is no maturity check, no flag on `ReceivedOutput` distinguishing a coinbase-derived output from a normal one, and the `ReceivedOutput` type itself (mod.rs:90-97) carries only `offset`, `output`, and `outpoint` — insufficient for a downstream consumer to detect immaturity without a second chain lookup keyed by `outpoint`.

The only mitigation is a doc comment on `scan_block` stating "a post-processing pass is needed" or that callers may scan `block.txdata[1 ..]` instead — but the default, natural API (`scan_block`) unconditionally returns immature outputs indistinguishable from spendable ones.

### Impact Explanation
Any external party who mines a block can register a deposit-looking output under Serai's key/offset scripts that the threshold wallet cannot spend for 100 blocks. If deposit crediting (or liquidity minting against reported receipts) acts on `scan_block` results, the miner can be credited for funds that are temporarily — and if the block is orphaned or the coinbase later conflicts, permanently — unspendable, inflating the vault's apparent balance exactly as unauthorized `mint()` inflates share supply. Impact is bounded by coinbase maturity, so it is Medium rather than High severity, assuming honest handling downstream; it becomes High if credited deposits are instantly redeemable.

### Likelihood Explanation
Requires the attacker to mine a Bitcoin block, which has a real cost — but no permission, no collusion, and no insider access. The attack surface is fully reachable with public inputs (a Bitcoin transaction the attacker causes to be mined). The footgun exists precisely because `scan_block` is the convenience API a caller reaches for; the safe path is opt-in.

### Recommendation
Make the safe behavior the default rather than documented opt-in:
- In `scan_block`, skip `block.txdata[0]` (the coinbase), or pass block context into `scan_transaction` and exclude transactions `tx.is_coinbase()` when scanning blocks at depth < COINBASE_MATURITY.
- Alternatively, add a `coinbase: bool`/maturity field to `ReceivedOutput` so downstream code can enforce spendability instead of relying on a doc comment.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs
// A miner constructs a coinbase paying to a registered Serai script.
let scanner = Scanner::new(group_key).unwrap();
let mut coinbase = Transaction {
    version: Version::TWO, lock_time: LockTime::ZERO,
    input: vec![/* coinbase input: prevout = 0x00..:0xffffffff */],
    output: vec![TxOut {
        value: Amount::from_sat(1_000_000),
        script_pubkey: p2tr_script_buf(group_key).unwrap(), // registered script
    }],
};
let block = Block { header: /* ... */, txdata: vec![coinbase] };

let outputs = scanner.scan_block(&block);
assert_eq!(outputs.len(), 1);          // reported as received...
// ...yet this OutPoint is consensus-unspendable for 100 blocks.
// ReceivedOutput exposes nothing to distinguish it from a normal deposit.
```
Root cause: `scan_block` iterates `block.txdata` including index 0 and delegates to `scan_transaction`, which matches only `output.script_pubkey` (networks/bitcoin/src/wallet/mod.rs:205-209, 221-227) — no authorization-equivalent check restricts who may mint a `ReceivedOutput` or under what transaction context.

Note: I could not fully verify whether `processor`'s scanning pipeline (e.g., `processor/src/multisigs/scanner.rs`, `processor/src/networks/bitcoin.rs`) performs the documented post-processing pass to exclude immature coinbase outputs, as I ran out of search iterations. If a downstream pass already filters coinbase outputs, this reduces to documented-misuse hardening; if not, it is a reachable Medium issue.
