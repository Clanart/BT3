### Title
PHP `GPBUtil::parseDuration` mis-signs fractional nanos for sub-second negative durations ("-0.Ns") - ([File: php/src/Google/Protobuf/Internal/GPBUtil.php])

### Summary
The external report's failed invariant is: a value is scaled/split into two related fields (whole vs. fractional units) using a sign/magnitude rule applied to only one of the derived quantities, so a caller-supplied value near a magnitude boundary (zero) causes the reconstructed pair of fields to silently take on the wrong sign — a data-integrity corruption, not a crash. The closest transferable analog in this Protobuf checkout is in the PHP ProtoJSON `Duration` parser, which reconstructs `Duration.seconds`/`Duration.nanos` from a single JSON string using the *sign of the truncated integer part* to decide the sign of the *nanos* fraction, which breaks for magnitudes between 0 and 1 second.

### Finding Description
`GPBUtil::parseDuration()` is reachable from the public ProtoJSON parsing API for any message containing a `google.protobuf.Duration` field (e.g. `Message::mergeFromJsonString()`/`mergeFromJsonArray()` for Duration-typed fields), which is a supported public parse entry point for untrusted, bounded string input. [1](#0-0) 

The vulnerable logic:
```php
$pos = strrpos($number, ".");
if ($pos !== false) {
    $seconds = substr($number, 0, $pos);
    if (bccomp($seconds, 0) < 0) {
        $nanos = bcmul("0" . substr($number, $pos), -1000000000);
    } else {
        $nanos = bcmul("0" . substr($number, $pos), 1000000000);
    }
} else {
    $seconds = $number;
    $nanos = 0;
}
$duration = new Duration();
$duration->setSeconds($seconds);
$duration->setNanos($nanos);
``` [2](#0-1) 

The sign of `nanos` is decided by `bccomp($seconds, 0) < 0`, i.e. by the *numeric value* of the truncated integer-second substring, not by whether the original input string had a leading `-`. For an attacker-supplied duration string whose magnitude is less than one second and negative, e.g. `"-0.5s"`:
- `$number` = `"-0.5"`
- `$seconds` = substr before `.` = `"-0"`
- `bccomp("-0", 0)` evaluates to `0` (bcmath treats `"-0"` as numerically equal to `0`), which is **not** `< 0`
- The `else` branch fires, so `$nanos = bcmul("0.5", 1000000000) = 500000000` (positive)
- `$duration->setSeconds("-0")` → the generated setter coerces this to the integer `0` (sign is dropped by the underlying integer cast), and `$duration->setNanos(500000000)` is stored as-is.

The resulting `Duration` object is `{seconds: 0, nanos: +500000000}` — a **positive** half-second duration — even though the attacker's input represented a **negative** half-second duration. This mirrors the report's failed invariant exactly: a quantity is decomposed into two differently-scaled/represented parts (integer seconds vs. fractional nanos derived via `* 1e9`), and the sign/scale bookkeeping used to reconstruct one part (nanos) is derived from the wrong intermediate value (`$seconds`, which lost the sign at magnitude 0) instead of the original signed input, silently corrupting the reconstructed value. This is analogous to the original bug where the mint-side scaling factor and the burn-side raw amount diverge because the code uses the wrong intermediate quantity to reverse a scale operation.

This is distinct from, and not excluded by, the "harmless depth" / "resource exhaustion" / "TextFormat-only" carve-outs in the rules: it is a binary-adjacent, supported ProtoJSON parsing path producing a value-corruption (wrong sign, not just wrong magnitude) that violates `TimeUtil`/`IsDurationValid`-style invariants (`Duration.seconds` and `Duration.nanos` must share sign per the `.proto` doc), i.e. `!(duration.seconds() <= -1 && duration.nanos() > 0)`-style consistency checks, cf. `TimeUtil::IsDurationValid` in the C++ implementation, which this PHP path bypasses entirely because no consistency check is performed after parsing. [3](#0-2) 

### Impact Explanation
An application that ingests untrusted ProtoJSON in PHP and stores/forwards the resulting `Duration` (e.g., a rate limit, TTL, retry backoff, refund/credit period, or billing adjustment expressed as a signed duration under one second) will silently receive a duration with the **wrong sign** for any input in `(-1s, 0s)`. Downstream logic that branches on sign (e.g., "negative duration ⇒ subtract time / issue a credit" vs. "positive ⇒ add time / charge") will take the wrong branch, which is a data-integrity/business-logic corruption reachable purely through parsing untrusted JSON — no privileged access or malicious schema required. Severity is bounded (only sub-one-second magnitudes near zero are affected, and it is confined to the PHP runtime's manual `Duration` JSON codec), so this is at most Medium severity, not Critical/High — it does not cause memory corruption, RCE, or unbounded resource use.

### Likelihood Explanation
High likelihood of being triggered unintentionally (any negative fractional-second duration serialized by another correct implementation and consumed by PHP will be misinterpreted), and trivially reproducible/triggerable by an attacker who controls the JSON payload (`"-0.5s"`, `"-0.000000001s"`, etc.) sent to any PHP service that parses `Duration` fields from JSON. It requires no special privileges — just a standard `mergeFromJsonString` call on a message containing a `Duration` field.

### Recommendation
Determine the sign from the original signed input string (or from whether `$number` starts with `-`), not from `bccomp($seconds, 0)`, mirroring the correct approach already used in `python/google/protobuf/internal/well_known_types.py`'s `Duration.FromJsonString` (`if value[0] == '-':`) and in `src/google/protobuf/json/internal/parser.cc`'s `ParseDuration` (`bool isNegative = (secs < 0) || absl::StartsWith(sec_digits, "-");`). Concretely:
```php
$isNegative = (strlen($number) > 0 && $number[0] === '-');
...
if ($isNegative) {
    $nanos = bcmul("0" . substr($number, $pos), -1000000000);
} else {
    $nanos = bcmul("0" . substr($number, $pos), 1000000000);
}
```
Additionally, add a post-parse consistency assertion (as C++'s `TimeUtil::IsDurationValid` does) that rejects/normalizes any `Duration` where `seconds` and `nanos` have inconsistent signs, to defend against any future regression of this class.

### Proof of Concept
Using the PHP extension/runtime (`php/src/Google/Protobuf/Internal/GPBUtil.php::parseDuration`), any message with a `google.protobuf.Duration` field parsed from:
```json
{"dur": "-0.5s"}
```
via `Message::mergeFromJsonString()` results in the stored `Duration` object having `seconds == 0` and `nanos == 500000000` (a **positive** half-second) instead of the correct `seconds == 0`, `nanos == -500000000` (a **negative** half-second), because `bccomp("-0", 0)` returns `0`, taking the `else` (positive-nanos) branch at [4](#0-3) . This can be confirmed by tracing the exact string transformations (`$number = "-0.5"`, `$seconds = "-0"`, `bccomp("-0","0") == 0`) against the code at the cited lines; I was not able to execute the PHP test suite in this environment, so this is a static-trace-verified reproduction rather than an executed one — running `php/tests/WellKnownTest.php`-style unit test with the input above would empirically confirm the sign flip.
