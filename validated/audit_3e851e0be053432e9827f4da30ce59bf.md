This confirms the exploitation path: `bindings.CallEVM` is a wasm binding message exposed to any CosmWasm contract, encoded by `EncodeCallEVM` at [1](#0-0)  into a `MsgInternalEVMCall`, which is unconditionally handled by `HandleInternalEVMCall`/`CallEVM` at [2](#0-1) . This means an ordinary CosmWasm contract instantiated/executed via the EVM `wasmd` precompile can re-enter the EVM by sending a `CallEVM` custom wasm message, and the target EVM contract can call the `wasmd` precompile again, and so on — an EVM→CW→EVM→CW… alternating recursion.

### Title
Alternating EVM↔CosmWasm re-entry (`CallEVM`/wasmd precompile) bypasses the EVM call-depth stack guard, enabling stack-overflow DoS - (File: `x/evm/keeper/evm.go`)

### Summary
The `wasmd` precompile lets an EVM contract instantiate/execute a CosmWasm contract by setting `ctx.EVMEntryViaWasmdPrecompile()=true` [3](#0-2) . That CW contract can then send the wasm-binding `CallEVM` message, which is translated to `types.MsgInternalEVMCall` and dispatched through `k.CallEVM` [1](#0-0) . `CallEVM`'s only re-entrancy guard is `if ctx.IsEVM() && !ctx.EVMEntryViaWasmdPrecompile() { return ... "EVM->CW->EVM call pattern" }` [4](#0-3) , which is satisfied (does not block) precisely because the call originated through the wasmd precompile. `CallEVM` then builds a brand-new `core.Message`/`stateDB` and calls `k.applyEVMMessage`, which constructs an entirely new `vm.EVM` instance — resetting the native go-ethereum call-depth counter (`evm.GetDepth()`) back to 0 for this new EVM instantiation [5](#0-4) . The new EVM can again call the `wasmd` precompile, which again allows the CW contract to call back into `CallEVM`, and so on.

### Finding Description
go-ethereum's normal protection against unbounded EVM call recursion is `evm.GetDepth()`, capped by `params.CallCreateDepth` (1024), enforced by the interpreter before every nested `CALL`/`DELEGATECALL`/`STATICCALL`/`CREATE`. That counter lives on a single `vm.EVM` object and is incremented per nested Go-level `Call`. Sei-chain's wasmd bridge, however, creates a *new* `vm.EVM` object every time a CosmWasm contract issues a `CallEVM` binding message (via `HandleInternalEVMCall` → `CallEVM` → `k.applyEVMMessage`), so each "hop" through CosmWasm resets the interpreter's own depth counter to zero. The only depth accounting that persists across hops is the CosmWasm-side `maxCallDepth` (default 100) tracked in `sei-wasmd/x/wasm/keeper/keeper.go`'s `checkAndIncreaseCallDepth`, via a value stored in the underlying `context.Context` [6](#0-5) .

This is structurally analogous to the reported TVM bug class: a bounded, gas-accounted "logical" recursion counter (VM call depth / continuation counter) does not correspond to the amount of native process stack consumed per logical step, because each alternation goes through many additional Go call frames — precompile dispatch (`RunAndCalculateGas`), ABI encode/decode, a new `StateDB`, `applyEVMMessage`, a new `vm.EVM`, wasmd's `contractInstance`/gas-metering plumbing, and a CGO call into the Rust `wasmvm` engine and back — before the depth counter is even incremented again. Each of the (at most 100, per `DefaultMaxCallDepth`) allowed CW-side hops therefore burns dramatically more native/Go stack than a single plain EVM `CALL` opcode, which only recurses through the interpreter's `Run`/`Call` functions. If the per-hop stack cost is large enough (CGO calls into the Rust VM push a full C stack frame, and each `Instantiate`/`Execute` in `sei-wasmd` involves substantial nested Go call chains before it can even reach the next `CallEVM`), 100 alternations of full EVM↔CW round trips can plausibly exhaust the validator node process stack even though the "logical" depth counter never exceeds 100 and gas is still available — mirroring the described CVE's "even within permissible gas limits, this nested execution exhausts the host process's stack space."

I was not able to fully verify from static inspection alone whether 100 alternating EVM↔CW hops (each involving a CGO round-trip into wasmvm) is empirically sufficient to overflow the default Go goroutine stack (which grows dynamically up to a large configurable maximum) versus simply hitting `ErrExceedMaxCallDepth` gracefully first; this depends on the actual stack cost per hop, which requires runtime profiling/fuzzing rather than code reading alone.

### Impact Explanation
If the alternating recursion does exhaust the process stack before `ErrExceedMaxCallDepth`/gas exhaustion trips, every validator executing the transaction would crash simultaneously (since EVM execution is deterministic and applied identically on every node), producing a full chain halt — a validator-halt / DoS condition, reachable by any unprivileged EVM transaction sender or contract deployer through ordinary `CALL`s into the `wasmd` precompile and the `CallEVM` wasm binding, with no special privilege required.

### Likelihood Explanation
The `wasmd` precompile and `CallEVM` wasm-binding message are both part of the standard, public CW↔EVM bridge available to any deployer, and no additional guard exists to cap the *number of native EVM↔CW round trips* independent of gas — only the pre-existing, separately-scoped `maxCallDepth` (CW-side) and `evm.GetDepth()` (per-EVM-instance) counters, neither of which accounts for the other's native stack cost. Constructing the pathological contract pair (one EVM contract that calls `wasmd.execute`, and one CW contract that immediately re-issues `CallEVM` back to the EVM contract) is straightforward and requires no unusual permissions, but confirming actual exploitability requires empirical stack-depth measurement that cannot be established through static code review alone.

### Recommendation
Track and enforce a single, shared EVM↔CW alternation counter across `CallEVM`/`applyEVMMessage`-created `vm.EVM` instances and `sei-wasmd`'s CosmWasm call-depth counter (e.g., pass through and check a combined "total native call depth" via `sdk.Context`, independent of which side incremented it, with a much lower cap than 100, and/or measure and bound the actual stack cost per hop), so that no sequence of nested EVM/CW calls can consume unbounded (or excessive) native process stack regardless of how the depth is distributed between the two subsystems. Alternatively, disallow re-entering `CallEVM` for the remainder of a call chain that already originated `evmEntryViaWasmdPrecompile`, closing the loophole in the guard at `x/evm/keeper/evm.go:80`.

### Proof of Concept
1. Deploy CW contract `B` whose `execute` handler, on receiving any message, immediately emits a `CallEVM` wasm-binding submessage back to EVM contract `A`, forwarding the same calldata (so it recurses forever until an error is thrown).
2. Deploy EVM contract `A` whose fallback/receive function calls the `wasmd` precompile's `execute` method targeting contract `B` with the same payload.
3. From an EOA, send a single EVM transaction calling `A`, providing ample gas.
4. Observe the resulting alternating `A → wasmd.execute → B.execute → CallEVM → new vm.EVM → A → …` chain; each cycle allocates a fresh `vm.EVM`/`StateDB` and a new wasmvm CGO invocation while the shared CW-side depth counter increments toward `DefaultMaxCallDepth` (100). Measure whether the validator process stack is exhausted (crash) before the 100-hop cap or gas limit is reached — this final confirmation requires instrumented runtime testing (e.g., with a reduced OS stack ulimit or stack-usage profiling) that a background engineering session should perform to conclusively establish exploitability.

func checkAndIncreaseCallDepth(ctx sdk.Context, maxCallDepth uint32) (sdk.Context, error) {
	var callDepth uint32

	if size := ctx.Context().Value(contextKeyCallDepth); size != nil {
		callDepth = size.(uint32)
	} else {
		callDepth = 0
	}

	// increase
	callDepth++

	// did we go too far?
	if callDepth > maxCallDepth {
		return sdk.Context{}, types.ErrExceedMaxCallDepth
	}

	ctx = ctx.WithContext(context.WithValue(ctx.Context(), contextKeyCallDepth, callDepth))

	// set updated stack size
	return ctx, nil
}
