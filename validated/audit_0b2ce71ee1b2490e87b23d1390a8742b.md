### Title
Same-transaction Pyth price update + borrow/withdraw enables oracle timestamp arbitrage - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The market contract lets a caller push a fresh Pyth price update and immediately use it to value collateral/debt in the very same transaction, and its staleness/monotonicity gate only requires the new timestamp to be `>=` the last recorded one, not strictly newer and not limited to one update per block. This mirrors the Stork report's bug class: a monotonic per-feed timestamp check that allows the price to be moved (and the trade to be executed) atomically, letting the caller pick both a stale-but-valid initial price and an updated final price within one call.

### Finding Description
`write-feeds`/`write-feed` accept an optional bundle of raw Pyth VAA updates and apply them via `pyth-oracle-v4 verify-and-update-price-feeds` before market logic executes [1](#0-0) . `pyth-storage-v4`'s `write-batch-entry` only rejects a price if it is *older* than the currently stored one (`is-price-update-more-recent`) and checks bounded staleness relative to `stacks-block-height`; it does not restrict how many times a feed can be updated within the same block/transaction [2](#0-1) .

Downstream, the market's own gate, `oracle-timestamp-fresh`, accepts any timestamp `ts` as long as `ts >= prev` (the last-recorded timestamp for that feed) and within `max-staleness`; it does not require the update to be new for the current block, nor does it forbid resolving the price more than once per block [3](#0-2) . `price-resolve` then updates `last-update` only if the new timestamp is strictly greater, but still returns a valid price on every call satisfying the `>=` condition [4](#0-3) , and this is the exact function used to price collateral/debt for every position via `get-notional-evaluation`/`calculate-asset-notional-value` [5](#0-4) .

Because (a) price updates can be bundled with the same call that consumes the price (via `write-feeds`), and (b) the monotonicity check permits any number of valid, monotonically non-decreasing price updates within one transaction/block, a caller can: submit an older-but-still-"newer-than-prev" VAA to push the price to a value favorable for opening/adjusting a position, perform the borrow/withdraw at that price, then submit a subsequent legitimate VAA update that restores/moves the price to its real current value — all atomically, before any other actor or liquidation bot can react.

### Impact Explanation
An attacker can borrow against, or withdraw collateral valued at, a stale-but-technically-fresh price and then immediately roll the oracle forward to the true price within the same transaction, extracting the price-gap value from the pool with no execution risk. Depending on which direction the gap runs, this results in under-collateralized debt being created against the protocol (direct theft of pooled lender funds / protocol insolvency), since the position's health is evaluated with the same manipulable snapshot used to authorize the action.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to have (or wait for) two legitimate Pyth VAA updates for the same feed with a favorable price delta and monotonically increasing timestamps, which is more likely during periods of high volatility — exactly the scenario called out in the original report. Unlike a push oracle where the "price" is chosen by a privileged relayer, here the values must be real Pythnet-signed prices, but Pyth's pull model already lets *anyone* submit any valid past-published VAA, so the attacker does not need special permissions, only correctly timed submission.

### Recommendation
Enforce a strict one-update-per-block rule for a given feed (reject or no-op resolving further updates for a feed once already updated in `stacks-block-height`), and require `price-resolve`/`oracle-timestamp-fresh` to prove the consumed price was actually updated within the current block before it is used to evaluate collateral/debt health, mirroring the reference fix suggested in the original report (track `updated-at-block` per feed and gate both the write path and the consumption path on it).

### Proof of Concept
1. Attacker observes a Pyth price feed that is about to move favorably (e.g., collateral asset price about to rise, or debt asset about to fall).
2. In a single transaction, attacker calls a market function (e.g. deposit/borrow) passing `feeds` with a legitimate but slightly stale VAA that satisfies `ts >= prev` and `max-staleness`, causing `write-feeds`/`price-resolve` to accept it and value the position favorably [1](#0-0) .
3. Still within the same transaction/block, attacker submits the true, newer VAA (also satisfying `>= prev`), updating the stored price to the real market value.
4. Attacker closes/unwinds the position at the now-correct price, having borrowed/withdrawn against the intermediate favorable valuation with zero exposure to real price risk, at the pool's expense.

  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
