### Title
Incorrect coin identity computed in `create_update_state_spend` when `new_amount` override is used - (File: chia/data_layer/data_layer_wallet.py)

### Summary
`DataLayerWallet.create_update_state_spend` accepts a `new_amount` override that is used to set the actual on-chain `CreateCoin` amount for the singleton's child coin, but every other place that needs to reflect that same child coin's amount — the new `SingletonRecord.coin_id`, its `lineage_proof.amount`, and (in the `announce_new_state` branch) the second-generation record — keeps using the stale `singleton_record.lineage_proof.amount` (the *parent* coin's amount) instead of `new_amount`. This mirrors the Arrakis `Underlying.underlying` bug class: an override parameter is honored for one computed field (the created coin's amount / the Uniswap custom price) while a dependent, derived field (the tracked coin identity / the tick) is left stale, producing an internally inconsistent result.

### Finding Description
In `create_update_state_spend`: [1](#0-0) 
the primary `CreateCoin` condition correctly uses `new_amount` when it is supplied:
```
CreateCoin(
    ... ,
    singleton_record.lineage_proof.amount if new_amount is None else new_amount,
    ...
)
```
This is the amount that will actually be committed on-chain for the child singleton coin.

However, the `new_singleton_record` that the wallet stores to track this same child coin computes its `coin_id` and `lineage_proof` using the old, un-overridden `singleton_record.lineage_proof.amount`, not `new_amount`: [2](#0-1) 

The same stale-amount pattern repeats in the `announce_new_state` branch, both for `second_coin`/`second_singleton_record` and for the final `new_singleton_record` replacement: [3](#0-2) 

Because a `Coin`'s ID is `sha256(parent_id || puzzle_hash || amount)`, when `new_amount != singleton_record.lineage_proof.amount`, the `coin_id` stored in `new_singleton_record` (computed with the old amount) will not equal the ID of the coin that is actually created on-chain (which uses `new_amount`). The wallet's `SingletonRecord`/lineage-proof bookkeeping for its own DataLayer singleton therefore diverges from the real coin set produced by the spend bundle it just built and submitted.

### Impact Explanation
This causes the wallet's local `dl_store` singleton tracking to point at a `coin_id` and `lineage_proof.amount` that do not correspond to any real coin on-chain. Subsequent calls to `get_spendable_singleton_info(launcher_id)` (used at the top of this very function, and elsewhere in the DL wallet flow to build the next spend) will use this incorrect lineage proof/amount to construct the next generation's `full_sol`/`current_coin`. That next spend will reference a parent coin amount that does not match the real unspent singleton coin, causing the wallet to either build an invalid spend (rejected by the network) or to permanently lose track of/misidentify its own singleton coin — a coin-identity/state-divergence bug reachable purely from a local wallet RPC call (`create_update_state_spend`, exposed via `dl_update_root`/related RPCs) whenever a caller supplies a `new_amount` different from the current singleton amount.

### Likelihood Explanation
Reachability requires only a local wallet-owner action that calls the DataLayer "update singleton state" RPC path with an explicit `new_amount` different from the singleton's current lineage-proof amount — no privileged, peer, or network-level access is needed. Exploitability is high whenever this optional parameter is actually exercised with a differing amount, since the bug is unconditional (no additional guard prevents the mismatch).

### Recommendation
Replace every occurrence of `singleton_record.lineage_proof.amount` used to describe the *newly created* child coin (in `new_singleton_record.coin_id`, its `LineageProof`, and the analogous `second_singleton_record`/replacement logic in the `announce_new_state` branch) with the effective new amount, i.e. `new_amount if new_amount is not None else singleton_record.lineage_proof.amount`, so the tracked coin identity always matches the amount actually placed in the `CreateCoin` condition.

### Proof of Concept
1. Call `DataLayerWallet.create_update_state_spend(launcher_id, root_hash, action_scope, new_amount=uint64(3))` on a singleton whose current `lineage_proof.amount` is `1`.
2. The generated `CreateCoin` primary uses `amount=3` (from `new_amount`), so the real on-chain child coin ID is `Coin(current_coin.name(), next_full_puz_hash, 3).name()`.
3. The `new_singleton_record.coin_id` stored via `interface.side_effects.singleton_records.append(new_singleton_record)` is computed as `Coin(current_coin.name(), next_full_puz_hash, singleton_record.lineage_proof.amount).name()` — i.e. using `amount=1` — [2](#0-1) , producing a different, non-existent coin ID.
4. Any later spend built from `get_spendable_singleton_info(launcher_id)` will use this wrong lineage proof/coin_id, causing the wallet's next singleton spend to fail or misidentify the tracked coin, demonstrating the coin-identity/state divergence caused by the stale-amount computation.
