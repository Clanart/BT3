### Title
Delimiter-injection in `extract_frontmatter` silently downgrades `action: block` rules to `warn` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` splits raw file content on the literal string `---` using `content.split('---', 2)` instead of only treating a line that is exactly `---` as a delimiter. If any frontmatter value (e.g. a `pattern` regex used to detect dangerous commands) contains the substring `---`, the split terminates early, truncating the parsed frontmatter dict before the `action: block` field is reached. `Rule.from_dict` then falls back to its default `action = "warn"`, so a rule that visually appears in the `.claude/hookify.*.local.md` file as a hard block is silently loaded and enforced as a non-blocking warning.

### Finding Description
`extract_frontmatter` in [1](#0-0)  performs `parts = content.split('---', 2)` and treats `parts[1]` as the entire frontmatter text and `parts[2]` as the message body. This is a naive string split that does not require `---` to appear alone on its own line — any occurrence of the three-character sequence anywhere in a field value (most plausibly inside a `pattern:` regex meant to match a dangerous command, e.g. `rm -rf /tmp---evil` or any pattern containing a literal `---`) is treated as the closing frontmatter delimiter.

When this happens, the custom line-based YAML-ish parser in [2](#0-1)  only ever sees the truncated `frontmatter_text`, so fields written *after* the embedded `---` — including `action: block` — end up in the discarded/misrouted "message" portion (`parts[2]`) instead of the parsed dict. `Rule.from_dict` reads `action=frontmatter.get('action', 'warn')` at [3](#0-2)  and defaults to `"warn"` when the key is absent, so the resulting `Rule.action` becomes `"warn"` even though the raw file the user/agent wrote clearly contains `action: block`.

This truncated `Rule` is then loaded via `load_rule_file`/`load_rules` [4](#0-3)  and consumed by the `PreToolUse` hook, which calls `load_rules(event=...)` and `RuleEngine.evaluate_rules` [5](#0-4) . In `RuleEngine.evaluate_rules`, a rule with `action != 'block'` is placed in `warning_rules`, which only emits a `systemMessage` and does **not** set `permissionDecision: deny`, allowing the dangerous `Bash`/`Edit` tool call to proceed [6](#0-5) . Only `blocking_rules` produce `permissionDecision: deny` for `PreToolUse`/`PostToolUse` or `decision: block` for `Stop` events [7](#0-6) .

No validation anywhere checks that the number of `---` delimiters in the raw content matches expectations, that `---` only appears as a standalone line, or that the frontmatter actually contains all fields visible in the source text before enforcement. The `if not frontmatter: return None` guard in `load_rule_file` does not catch this case because the truncated frontmatter dict is still non-empty (it contains `name`, `enabled`, `event`, `pattern`, just missing `action`).

### Impact Explanation
A rule author (user or the `/hookify` agent generating rules from conversation text) can create/believe they created a hard block rule (e.g., "block `rm -rf` with dangerous flags") that is silently enforced as warn-only due to an incidental `---` inside the pattern value. This breaks the security invariant that a deny/block rule must never be parsed into a non-blocking configuration. In practice, this means a dangerous `Bash` command, file edit, or session-stop condition that the user explicitly configured to be **blocked** will instead only display a warning message and allow execution — enabling unauthorized local command execution/file mutation that bypasses the approval/deny control the user believed was in place.

### Likelihood Explanation
The bug is deterministic and requires no special privileges: any `.claude/hookify.*.local.md` file (created by `/hookify`, hand-edited by a user, or introduced via a checked-in repository file that a victim clones/pulls) whose `pattern`, `conditions[].pattern`, or any frontmatter value happens to contain the literal substring `---` will trigger it. Patterns targeting command-line flags, ranges, or long-option syntax (e.g., `--`-style flags concatenated with other text) make this an easily and plausibly reachable condition, and it is trivially reproducible with a single crafted file — no timing or race conditions involved.

### Recommendation
Rewrite `extract_frontmatter` to only treat a line that is exactly `---` (after stripping whitespace) as a delimiter, e.g. split the content into lines, find the first line equal to `---`, then find the next line equal to `---` scanning from there, rather than using `str.split('---', 2)` on the raw text. Additionally, validate after parsing that all frontmatter keys present in the raw delimited block (verified via a real YAML parser such as `yaml.safe_load`) were actually captured, and fail closed (reject the rule / treat as invalid rather than silently defaulting `action` to `warn`) if parsing is ambiguous or incomplete.

def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules
