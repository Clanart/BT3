### Title
Bounded per-chain state-commitment queue evicts heights still needed by outstanding requests/timeouts, permanently locking relayer fees and escrowed funds - (File: `modules/pallets/ismp/src/host.rs`, `modules/pallets/ismp/src/lib.rs`)

### Summary
The Gondi bug is a fixed time buffer (`_LOAN_BUFFER_TIME`) that is not sized to the real worst-case delay before a withdrawal queue slot can safely be overwritten, so `pendingQueues` gets clobbered before the loan that depends on it finishes. Hyperbridge's pallet-ismp has the same structural flaw in its `BoundedStateCommitments`/`StateCommitmentQueue`: it is a fixed-capacity FIFO per state machine that evicts the *oldest* stored `StateCommitment` (and its update time) purely by insertion count, with no check for whether a request, timeout, or fee-accumulation proof still depends on that height.

### Finding Description
`Pallet::<T>::insert_bounded_state_commitment` (invoked from `IsmpHost::store_state_machine_commitment`) stores each new consensus-confirmed height into `BoundedStateCommitments` / `StateCommitmentQueue`, and once the configured per-chain cap (`update_commitment_caps`) is reached, the oldest entry is evicted unconditionally: [1](#0-0) 

The eviction behavior is demonstrated directly in the test suite: with a cap of 3, inserting heights 1..5 silently removes heights 1 and 2 regardless of whether anything still references them: [2](#0-1) 

Every downstream consumer of a state commitment — non-membership timeout proofs, incoming `PostRequest`/`GetResponse` delivery, and challenge-period gating — reads the commitment strictly by height and fails hard if it is missing: [3](#0-2) [4](#0-3) 

Nothing in the eviction path checks:
- whether any `RequestCommitments` entry still has `timeout_timestamp` unresolved at that height,
- whether any pending `WithdrawalProof`/fee-accumulation claim references that height as `source_proof.height` or `dest_proof.height`,
- whether the challenge period for that height has even elapsed yet.

Just like `_LOAN_BUFFER_TIME` was sized off `MaxDuration + liquidation time` but ignored the `_MIN_NO_ACTION_MARGIN` bidding-delay case, the commitment-queue cap is sized as a flat storage-bound constant with no relationship to the maximum time a request can realistically stay outstanding (arbitrary `timeout_timestamp`, or a 30-day-default fee-claim window as referenced in `create_claim_proof`): [5](#0-4) 

Any unprivileged party can submit a stream of valid `Message::Consensus` updates for a counterparty chain — this is a permissionless entry point, not a malicious relayer/prover assumption; it only requires publicly available consensus proofs for a live chain. Submitting updates faster than a legitimate relayer needs to collect a non-membership/timeout/fee proof for an older height drives `LatestStateMachineHeight` and the bounded queue forward, evicting the height the outstanding request depends on.

### Impact Explanation
Once the height a pending request/timeout/fee-claim needs is evicted:
- `host.state_machine_commitment(height)` returns `Error::StateCommitmentNotFound`, so `handle_timeouts`/`handlePostRequestTimeouts`-equivalent flows can never be completed for that specific height again.
- The associated `RequestCommitments` entry (and its escrowed `FeeMetadata.fee`, held in `RELAYER_FEE_ACCOUNT`) can no longer be resolved via that proof path, permanently locking the relayer fee that would otherwise be refunded on timeout (`on_request_timeout` refund path): [6](#0-5) 
- Any in-flight `WithdrawalProof`/`accumulate_fees` claim or `IntentGatewayV2` cross-chain cancel/fill that was waiting on a state proof at that specific evicted height loses its only route to settlement, causing fund loss/lock for the payer, relayer, or order user — matching the "loss of funds" / "fund loss/lock" impact bucket.

### Likelihood Explanation
No compromised relayer, prover, or admin is required. Submitting `Message::Consensus` updates is a normal, permissionless operation exposed to anyone holding valid consensus proofs from the counterparty chain; simply relaying them at a higher-than-normal cadence (or the counterparty chain producing/finalizing blocks quickly) is sufficient to advance the FIFO past a height that a legitimate, still-pending message depends on. The cap (`update_commitment_caps`) is a fixed governance-set constant analogous to `_LOAN_BUFFER_TIME`, with no dynamic relationship to the actual set of outstanding proof obligations.

### Recommendation
Do not evict a `StateCommitment`/`update_time` entry purely by FIFO position. Either:
- Track the set of still-unresolved heights referenced by pending `RequestCommitments` timeouts and in-flight `WithdrawalProof`s, and skip eviction of any height still referenced, or
- Size `update_commitment_caps` dynamically to bound eviction to `max(all outstanding request timeout_timestamp deltas, fee-claim window) + challenge_period`, mirroring the corrected `MaxDuration + _LOAN_BUFFER_TIME + margin` approach recommended in the Gondi report, and reject/queue new consensus updates rather than silently drop a height that a pending obligation still needs.

### Proof of Concept
1. Configure `update_commitment_caps` for a counterparty state machine to a small value `N` (as in the existing test, `N = 3`).
2. Dispatch a `PostRequest`/`DispatchGet` (e.g., an `IntentGatewayV2` cross-chain cancel-from-source query, or a relayer fee-accumulation claim) whose resolution proof must be built against height `H`.
3. Before the proof for height `H` is submitted, submit `N` additional valid `Message::Consensus` updates for that same state machine (permissionless, no privileged role needed) — this can be replayed directly from `commitment_queue_evicts_oldest_when_cap_is_reached`, substituting real heights for a live counterparty chain.
4. `BoundedStateCommitments::<T>::get(id, H)` now returns `None`; the timeout/withdrawal/refund flow that needed proof against `H` fails permanently with `StateCommitmentNotFound`, and the associated escrowed fee/asset is stuck.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
