## Analog Found

### Title
Git's built-in clone-time hook/hardlink protection is unconditionally disabled for every clone - ([File: app/src/lib/git/clone.ts])

### Summary
The OtterSec report's core pattern is: a dangerous, privileged operation (`LiquidateSolvent`) is executed without checking that the actor invoking it is the trusted/admin-controlled party — the code simply trusts whatever account is passed in as `executor`. The Desktop analog is structurally the same "missing gate" pattern, but the gate that's bypassed is Git's own built-in protection against malicious repository content, not a signer check. `clone()` in `app/src/lib/git/clone.ts` forces `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the environment for **every** `git clone --recursive` Desktop performs, unconditionally disabling that guard regardless of whether the remote URL is trusted or attacker-supplied.

### Finding Description
`clone()` builds the execution environment for every clone with: [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

This runs on `--recursive` clones (which walk into any submodules the attacker-controlled repository defines) for URLs that are directly attacker-influenced: the `url` argument reaches `clone()` from user-entered clone URLs and from the `open-repository-from-url` deep-link action parsed in `app/src/lib/parse-app-url.ts` (`parseAppURL`, lines 66-128), which is dispatched via `dispatchURLAction` in `app/src/ui/dispatcher/dispatcher.ts` (lines 2118-2120) without any additional vetting of the remote's trustworthiness. In other words, a link the user clicks (`x-github-client://openRepo/<attacker-url>`) can drive a `--recursive` clone with this protection turned off.

Desktop does separately guard against the destination path being sensitive (`isClonePathSensitive`, lines 16-47 of the same file), but that only protects the local filesystem destination — it does nothing about the trustworthiness of the remote content itself, which is exactly what `GIT_CLONE_PROTECTION_ACTIVE` is meant to gate. There is no equivalent "is this remote/operation from a trusted source" check comparable to what the report calls for (an address/allowlist constraint) before this protection is turned off.

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE` corresponds to Git's protection against malicious repository/submodule structures abusing recursive clone (case-folding/hardlink/symlink tricks that make Git treat attacker content as `.git`/hooks directories), disabling it for every clone removes a defense-in-depth barrier specifically engineered to stop a fully attacker-controlled repository from achieving code execution on the victim's machine during `clone --recursive`. This matches the "Valid Impact" bucket exactly: attacker controls a cloned repository and a link the user clicks, and the potential result is code execution outside normal repo boundaries.

### Likelihood Explanation
The path is directly reachable with no privileged preconditions: a user only needs to open a crafted `x-github-client://openRepo/...` link or paste/enter a malicious clone URL into Desktop's "Clone repository" dialog. The protection is disabled unconditionally on every single clone call, so there is no scenario where a legitimate clone benefits from the protection — it is always off.

### Recommendation
Do not blanket-disable `GIT_CLONE_PROTECTION_ACTIVE`. If it was disabled to work around a compatibility issue with a specific flow, scope that override narrowly (only for verified-safe/local operations) and leave the protection enabled by default for all clones of remote/untrusted URLs, especially those reachable via `--recursive` and deep-link-triggered `open-repository-from-url` actions.

### Proof of Concept
1. Craft a malicious Git repository designed to abuse the class of clone-time hook/hardlink vulnerabilities that `GIT_CLONE_PROTECTION_ACTIVE` is designed to block (e.g., a submodule/`--recursive` structure engineered to place executable content where Git would normally refuse to during a protected clone).
2. Host it and distribute either a direct clone URL or a deep link of the form `x-github-client://openRepo/<url-to-malicious-repo>`.
3. Victim clicks the link (or pastes the URL into "Clone a repository"), triggering `clone()` in `app/src/lib/git/clone.ts` with `--recursive` and `GIT_CLONE_PROTECTION_ACTIVE: 'false'` forced into the environment.
4. Because the protection is off, whatever Git-side check it normally performs before allowing the recursive clone to proceed is skipped for this operation.

**Caveat:** I could not access Git/dugite's internal source in this environment to confirm the exact upstream semantics of `GIT_CLONE_PROTECTION_ACTIVE` (I only have Desktop's usage site as evidence). The finding is based on the fact that this is clearly a named "protection" flag that Desktop deliberately turns off for all clones, which structurally mirrors the reported bug class (a safety/authorization gate that should restrict a dangerous action being bypassed instead of enforced). Confirming the precise upstream CVE/behavior this flag guards would require checking the `dugite`/Git changelog outside this codebase.
