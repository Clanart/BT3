### Title
Tokenfactory denom admin can front-run and retroactively block a pending transfer by mutating the denom's AllowList - (File: x/tokenfactory/keeper/msg_server.go, sei-cosmos/x/bank/keeper/send.go)

### Summary
Tokenfactory denoms can be created with an `AllowList` restricting which addresses may send the denom [1](#0-0) . The denom's admin (originally the permissionless creator) can also change this restriction later via `MsgUpdateDenom`, and `x/bank`'s `SendCoins` path enforces it against the sender at execution time, rejecting a `MsgSend` with "is not allowed to send funds" when the sender is not present in the allow list [2](#0-1) . This is structurally the same bug class as the OpenQ report: an actor who controls a mutable eligibility gate (KYC/invoice flags there, `AllowList` here) can wait for a user's transaction to be pending and front-run it with a state change that flips the gate closed, causing the user's already-in-flight, previously-eligible action to fail.

### Finding Description
Other tokenfactory admin-only actions (`Mint`, `Burn`, `ChangeAdmin`) are gated solely by `msg.Sender == authorityMetadata.GetAdmin()` with no delay, timelock, or immutability once a denom is live [3](#0-2)  and [4](#0-3) . `MsgUpdateDenom` follows the same message-service pattern and is the mechanism by which a denom's `AllowList` is changed after creation [5](#0-4) . Because the check is evaluated at `SendCoins` execution time rather than at approval/escrow time, the admin can observe a victim's pending `MsgSend` (or any composed transaction that ultimately calls `SendCoins`/`IsSendEnabledCoins` for that denom, including bank-precompile-mediated ERC20-pointer transfers of a tokenfactory-backed asset) in the mempool and submit an `UpdateDenom` transaction ahead of it that removes the sender (or, depending on enforcement point, the recipient) from the allow list, causing the victim's transaction to revert.

### Impact Explanation
This mirrors the OpenQ pattern of "front-run an eligibility-gate setter to block a pending user action, then keep/take the funds." Where this becomes concretely damaging on sei-chain is any multi-leg or composed flow where the tokenfactory transfer is only one leg of an atomic exchange (e.g., a swap, escrow release, or lending repayment built from a tokenfactory-backed pointer asset): if a counterparty leg has already committed irreversibly before the blocked leg executes, the victim can suffer real, unrecoverable loss, and the denom admin can repeat the block indefinitely, i.e., permanently withhold the asset from a specific counterparty while retaining full custody/admin rights themselves.

### Likelihood Explanation
Tokenfactory denom creation is explicitly permissionless (any account can become a denom "admin" for its own denom), and admin-gated setters here have no cooldown or dispute period, so the setup cost for an attacker to become a plausible "denom admin/attacker" is low. However, I could not directly confirm the concrete instruction/order-of-checks inside the real `UpdateDenom` handler (I only inferred it from sibling handlers), and I could not confirm a specific downstream composed flow (e.g., a lending/DEX contract on sei-chain) that would turn a simple reverted `MsgSend` into genuine fund loss rather than just a failed, gas-costing transaction. That composed-flow step is necessary to satisfy the "concrete fund loss/permanent freezing" bar and is not something I verified end-to-end in this codebase.

### Recommendation
If pursued further, a background agent should: (1) read the actual `UpdateDenom` handler in `x/tokenfactory/keeper/msg_server.go` to confirm authorization and confirm whether it can be called at any time without restriction; (2) trace exactly where in `SendCoins`/`IsSendEnabledCoins` (sei-cosmos/x/bank/keeper/send.go) the `AllowList` is checked, and whether it gates sender, recipient, or both; (3) search for any consumer of tokenfactory-backed denoms (ERC20 pointer transfers via the bank precompile, DEX/lending modules) where a `SendCoins` call is one leg of an otherwise-irreversible multi-step operation, to determine whether a blocked leg can strand funds rather than simply abort the whole transaction atomically.

### Proof of Concept
Not independently verified end-to-end; based on: `x/tokenfactory/keeper/msg_server.go` `ChangeAdmin`/`Mint`/`Burn` admin-check pattern [3](#0-2) , and `sei-cosmos/x/bank/app_test.go` `TestSendSenderNotInAllowList` demonstrating that a `MsgSend` for a tokenfactory-backed denom fails once the sender is outside the current `AllowList` [2](#0-1) .

func (server msgServer) ChangeAdmin(goCtx context.Context, msg *types.MsgChangeAdmin) (*types.MsgChangeAdminResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	// Validate new admin we change to should be different from current admin
	if msg.NewAdmin == authorityMetadata.GetAdmin() {
		return nil, types.ErrAdminAlreadyExists
	}

	err = server.setAdmin(ctx, msg.Denom, msg.NewAdmin)
	if err != nil {
		return nil, err
	}

func (k Keeper) setAdmin(ctx sdk.Context, denom string, admin string) error {

	}

	metadata.Admin = admin
