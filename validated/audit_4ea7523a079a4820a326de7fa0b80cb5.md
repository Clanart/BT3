### Title
Missing `wallet_state_manager.lock` on `PlotNFT2Wallet.claim_rewards()` allows concurrent double-selection of pool reward coins - ([File: chia/wallet/wallet_rpc_api.py])

### Summary
The external report's core theme is a Checks-Effects-Interactions inconsistency that was fixed everywhere except one function (`remove()`). The Chia analog is `WalletRpcApi.pw_absorb_rewards()`: the `PoolWallet` branch wraps the "check unspent reward coins → build spend → record transaction" sequence inside `self.service.wallet_state_manager.lock`, but the parallel `PlotNFT2Wallet` branch performs the exact same check-then-effect sequence with no lock at all.

### Finding Description
`pw_absorb_rewards` dispatches to two different pooling implementations: [1](#0-0) 

For `PoolWallet`, the entire claim (read unspent p2-singleton reward coins, build absorb spends, record the outgoing transaction) is serialized under `wallet_state_manager.lock`. For `PlotNFT2Wallet.claim_rewards()`, the same sequence — read pending rewards from `plotnft2_store.get_pool_rewards()`, build the claim spend bundle, then append the transaction record to the action scope — runs with no lock: [2](#0-1) [3](#0-2) 

Because `plotnft2_store.get_pool_rewards()` is only a read against the store (no "in-flight" marking of the coins as claimed until the resulting transaction is confirmed on chain), two overlapping local RPC calls to `pw_absorb_rewards` for the same `PlotNFT2Wallet` id can both read the identical `rewards_to_claim` set before either transaction is pushed, each building an independent `WalletSpendBundle` that spends the same reward coins and the same plotnft singleton coin. This is the "check" (are there rewards? are we within fee?) happening without the corresponding "effect" (marking those coins as claimed/locked) being atomic with the read — the classic CEI-violation pattern from the report, just manifesting as concurrent double-spend attempts on the wallet's own coin set rather than an external call.

Other `PlotNFT2Wallet` mutating operations (`join_pool`, `leave_pool`, `transfer_plotnft`, `melt_plotnft`) exhibit the same pattern relative to their `PoolWallet` counterparts, e.g. `pw_join_pool` and `pw_self_pool` do not take the lock for the `PlotNFT2Wallet` branch either: [4](#0-3) [5](#0-4) 

By contrast, `PoolWallet` methods explicitly guard against overlapping singleton-tip spends via `have_unconfirmed_transaction()` checks and the RPC-level lock, e.g. in `claim_pool_rewards`: [6](#0-5) 

`PlotNFT2Wallet.claim_rewards` has no equivalent unconfirmed-transaction guard or lock at all.

### Impact Explanation
Two rapid local `pw_absorb_rewards` (or `pw_join_pool`/`pw_self_pool`) RPC calls against the same `PlotNFT2Wallet` can each independently select the same plotnft singleton coin and reward coins and build two competing spend bundles/transaction records referencing the same removals. Both get queued as separate `TransactionRecord`s and pushed to the mempool; only one will actually be accepted on-chain (the singleton coin can only be spent once), but the wallet's local transaction/balance bookkeeping will have recorded two outgoing transactions for the same underlying coins, and the loser transaction will sit in the wallet DB as a failed/stuck TX referencing coins that no longer exist, corrupting the wallet's own accounting of claimed rewards until manually cleaned up. This is a wallet-local state-divergence bug, not a validation-bypass or a way to inflate supply or move another party's funds; it is bounded to the caller's own coins and requires the caller (or an application talking to the local unauthenticated wallet RPC) to fire overlapping requests.

### Likelihood Explanation
Requires two overlapping RPC calls to `pw_absorb_rewards`/`pw_join_pool`/`pw_self_pool` targeting the same `PlotNFT2Wallet`, which is plausible from a buggy or malicious local client/GUI issuing duplicate requests, but is not exploitable by a remote/unprivileged network peer and does not affect consensus-level coin identity or supply.

### Recommendation
Wrap the `PlotNFT2Wallet` branches of `pw_absorb_rewards`, `pw_join_pool`, and `pw_self_pool` in `wallet_state_manager.lock`, matching the `PoolWallet` branches, and/or add an unconfirmed-transaction guard inside `PlotNFT2Wallet.claim_rewards`/`join_pool`/`leave_pool` analogous to `PoolWallet.have_unconfirmed_transaction()` before selecting rewards/singleton coins for spend.

### Proof of Concept
1. Create a `PlotNFT2Wallet` with pending pool rewards recorded via `plotnft2_store.add_pool_reward`.
2. Issue two concurrent `pw_absorb_rewards` RPC calls for the same `wallet_id` (e.g. via `asyncio.gather`).
3. Both calls execute `PlotNFT2Wallet.claim_rewards` concurrently; both call `plotnft2_store.get_pool_rewards()` before either transaction is pushed, so both read the identical `rewards_to_claim` list and the identical `plotnft.coin` from `get_current_plotnft()`.
4. Both build a `WalletSpendBundle` removing the same reward coins and the same plotnft coin, and both append a `TransactionRecord` via `action_scope`.
5. Only one spend bundle can be accepted by the network; the wallet ends up with a duplicated/orphaned transaction record referencing already-spent coins, demonstrating the missing lock/guard versus the `PoolWallet` code path at `chia/wallet/wallet_rpc_api.py:3036`.
