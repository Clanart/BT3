## Title
Missing "no-newline" marker propagation on unselected deletions causes corrupted line-ending state when discarding/staging partial changes - (File: `app/src/lib/patch-formatter.ts`)

### Summary
`formatPatchToDiscardChanges()` and `formatPatch()` build synthetic unified-diff patches from a user's *partial* line selection so that `git apply` can be used to stage or discard only some of the lines in a hunk. Both functions check `line.noTrailingNewLine` **after** the per-line `if/else` branch that decides how to emit the line — but several branches `return` from the `forEach` callback before that check ever runs, silently dropping the "\ No newline at end of file" marker for the line it belonged to.

### Finding Description
In `formatPatchToDiscardChanges`, an unselected `Delete` line is treated as having "no impact on this patch" and the callback returns immediately: [1](#0-0) 

The trailing check that would emit the no-newline marker sits after this branch and is skipped whenever the `return` fires: [2](#0-1) 

The same pattern exists in `formatPatch()` for unselected `Add` lines (dropped file additions) and for any line in a new/untracked file: [3](#0-2) 

The `noTrailingNewLine` flag is set by the diff parser on the *previous* physical line whenever the raw `git diff` output contains a `\ No newline at end of file` marker: [4](#0-3) 

so this flag can legitimately be attached to the very line (add or delete) that these early-return branches skip. When that happens, the emitted synthetic hunk omits the marker even though the corresponding physical line in the repository has no trailing newline. `git apply` is then invoked against this malformed hunk: [5](#0-4) [6](#0-5) 

This is structurally the same bug class as the report's root cause: a value/flag that must be forced into a specific terminal state (here, "no trailing newline must be preserved") is silently dropped because an early-exit branch bypasses the code path that would otherwise set it, rather than the flag being explicitly and unconditionally propagated.

### Impact Explanation
When a file lacking a trailing newline is only *partially* staged or *partially* discarded (a normal, common Desktop workflow — line/hunk-level staging is a core feature), the resulting patch can misrepresent the file's final newline state. Applied via `git apply --cached` (staging) this silently changes what is recorded in the index relative to what the user intended to select, i.e. `git commit` records content the user did not actually choose — matching the "silent corruption of what the user commits or pushes" impact category. Applied via `discardChangesFromSelection`, the same defect can silently rewrite the working file's line-ending state during a destructive discard operation.

### Likelihood Explanation
Low-to-Medium. It requires a specific, but not exotic, precondition: a tracked file without a trailing newline, combined with the user performing a *partial* (line/hunk) stage or discard action that includes an unselected delete (or dropped add) line that happens to be the last line of the file. This is reachable through normal use of an attacker-influenced cloned repository (an attacker can deliberately ship a file without a trailing final newline to make this trigger more likely for contributors who commonly do partial-hunk staging), but it does not require any unnatural steps beyond Desktop's advertised line-selection feature.

### Recommendation
Compute and honor `line.noTrailingNewLine` unconditionally for every line, independent of the branch that decides whether/how the line is emitted — i.e. check the flag before any `return`, or restructure the loop so the no-newline marker is attached based on the actual last emitted line of each hunk rather than being tied to per-branch fallthrough. Add regression tests in `app/test/unit/patch-formatter-test.ts` covering unselected trailing deletions/additions on files lacking a final newline, for both `formatPatch` and `formatPatchToDiscardChanges`.

### Proof of Concept
1. Create a repository with `file.txt` whose last byte is not `\n` (no trailing newline), tracked and committed.
2. Modify the file by deleting the second-to-last line and leaving the last (no-newline) line as a `Delete` line in the diff (e.g., the file's final line changes position due to a preceding delete).
3. In Desktop, use the line-by-line diff view to select only some other hunk/line for staging, leaving the trailing `Delete` line un-selected.
4. `formatPatch`/`formatPatchToDiscardChanges` builds a hunk where the unselected `Delete` line returns early, dropping its `noTrailingNewLine` flag.
5. `applyPatchToIndex` (`git apply --cached ...`) applies the malformed patch; the resulting index entry/working file no longer matches the newline state the user actually had, without any warning or diff review reflecting the discrepancy.

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
