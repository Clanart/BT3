### Title
Scanner accepts immature coinbase outputs as spendable, reporting funds that cannot be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in `block.txdata`, including the coinbase transaction at index 0, and reports any matching outputs as ordinary `ReceivedOutput`s. Coinbase outputs are consensus-unspendable for 100 blocks (COINBASE_MATURITY). There is no maturity check anywhere in the scanning path — analogous to the BendDAO bug where staleness checks exist in form but fail to actually validate the freshness/spendability of the reported value. The code acknowledges the hazard only in a doc comment, leaving enforcement to callers.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`, `scan_transaction` matches outputs purely on `script_pubkey` membership in `self.scripts`, producing a `ReceivedOutput` with a valid `outpoint` (`tx.compute_txid()`, `vout`). `scan_block` then applies this to `&block.txdata` wholesale:

```rust
// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

The doc comment explicitly states: "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed to remove those outputs" — but no such check exists in the function, and `ReceivedOutput` carries no flag distinguishing coinbase-derived outputs. A `ReceivedOutput` produced from `block.txdata[0]` is indistinguishable from a normal one: it has a well-formed `offset`, `output`, and `outpoint`, and will pass through `read`/`write` serialization and the downstream signing pipeline (`send.rs` / scheduler) like any spendable UTXO.

This mirrors the BendDAO finding structurally: a validity invariant (price freshness there, output maturity here) is partially acknowledged but never actually enforced — the only "check" is documentation, so invalid data flows through the trusted path.

### Impact Explanation
If `scan_block` is used as the block-scanning entry point (rather than callers remembering to slice `txdata[1..]`), a coinbase output paying to the multisig's P2TR script is registered as a spendable `ReceivedOutput`. Any attempt to spend it within 100 blocks produces a transaction rejected by consensus — the scheduler builds and the threshold signature is produced over a transaction that can never confirm. Depending on downstream handling, this can cause funds to be reported received that are not spendable, or liveness failure while the signing set repeatedly tries to include an immature input. It can also enable a miner to inject a matching output that the system credits and later cannot spend, distorting accounted balance.

### Likelihood Explanation
Requires a miner to direct a coinbase output to a Serai multisig script (reachable with public inputs — the script is publicly derivable from the group key, and a miner controls coinbase contents). Whether the processor actually calls `scan_block` versus `scan_transaction` on `txdata[1..]` is not verifiable from the in-scope code I could inspect (the processor-side scanner is out of the listed scope), so exploitability hinges on the caller honoring the doc-comment contract — the exact situation the BendDAO report flagged: a critical check delegated to callers rather than enforced at the API boundary. Given the accepted impact class ("funds reported received that are not spendable") and reachable trigger, Medium is the appropriate severity if any in-tree caller uses `scan_block`.

### Recommendation
Enforce maturity at the point of scan rather than via documentation:

- In `scan_block`, skip `block.txdata[0]` (or check `tx.is_coinbase()` and skip), so `ReceivedOutput`s are only ever produced for spendable transactions.
- Alternatively, record the block height / coinbase flag on `ReceivedOutput` and require maturity before the output is accepted into the spendable set.

### Proof of Concept
```rust
// A miner crafts a block whose coinbase pays to the multisig P2TR script:
// coinbase_tx.output[0].script_pubkey == p2tr_script_buf(group_key)

let scanner = Scanner::new(group_key).unwrap();
let outputs = scanner.scan_block(&block);
// outputs[0] is a well-formed ReceivedOutput for OutPoint(coinbase_txid, 0)
// Any transaction built spending it fails consensus (immature coinbase spend,
// BIP-30 / COINBASE_MATURITY = 100 blocks), yet it was reported as received
// funds indistinguishable from a normal deposit.
```
