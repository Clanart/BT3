### Title
Permanently frozen consensus client makes both delivery and timeout-refund paths unreachable, locking escrowed relayer fees forever - ([File: modules/ismp/core/src/handlers.rs])

### Summary
The Opus/Caretaker bug is: `shut()` permanently disables `pull_redistributed_debt_and_yangs()`, so any yang that had not been pulled before shutdown becomes permanently unreachable — the "recovery" path was gated behind a check that the irreversible state transition (`shut`) also disables. Hyperbridge's ISMP core has the same structural flaw: freezing a consensus client (`freeze_client`) is **irreversible** ("Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized"), yet the exact same frozen-check gate (`is_consensus_client_frozen`) is enforced not only on the delivery path but also on the **timeout/refund path**, which is supposed to be the safety-net recovery mechanism for escrowed relayer fees.

### Finding Description
`validate_state_machine` is the shared pre-check used by both request/response delivery and timeout handling: [1](#0-0) 

It unconditionally calls `host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?`, returning `Error::FrozenConsensusClient` with no exception. This function is invoked in `timeout::handle` before verifying the non-membership proof needed to release the escrowed fee: [2](#0-1) 

Once a fraud proof successfully freezes a consensus client via `freeze_client`, the freeze is permanent by design: [3](#0-2) 

Documented explicitly: "Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead."

The corrupted/stuck value is the escrowed relayer fee held in `RequestCommitments`/`RequestMetadata` (Substrate, refunded via `RELAYER_FEE_ACCOUNT` in `on_request_timeout`) or in EVM's `_requestCommitments[commitment].fee` (`FeeMetadata`), for **any request whose proof height is anchored to the consensus_state_id that later gets frozen**. Both refund triggers — successful delivery (relayer receives fee) and timeout (payer is refunded) — require calling `validate_state_machine`/an EVM equivalent proof-verification path that checks the frozen state first. Once frozen, neither path can ever complete: `RequestVerificationFailed`/`FrozenConsensusClient` blocks delivery, and the identical frozen check inside `timeout::handle` blocks the non-membership proof needed for `delete_request_commitment` → `on_request_timeout` → refund. The escrow simply sits in `RELAYER_FEE_ACCOUNT` (or the EVM host's fee-token balance) forever, with no code path capable of moving it, mirroring the Caretaker's permanently-orphaned yang.

### Impact Explanation
Any relayer fee escrowed for in-flight requests proven against a consensus client at the time it is frozen becomes permanently unrecoverable — neither the sender (via timeout refund) nor the relayer (via delivery) can ever claim it. This is a direct, contained loss of user/application funds triggered by the protocol's own designed security response (freezing on fraud proof), matching the "false state acceptance prevention causing fund lock" bounty class rather than any malicious-actor scenario — freezing is the intended, permissionless response to a detected byzantine attack, yet its side effect permanently strands already-escrowed fees with no on-chain recovery mechanism (no `pull_when_shut()`-equivalent exists).

### Likelihood Explanation
Low-to-medium likelihood, matching the judged severity of the analog (Medium): it requires an actual consensus fault (byzantine behavior on a connected chain) to trigger `freeze_client`, which is expected to be rare but is a normal part of Hyperbridge's threat model (documented fishermen/fraud-proof mechanism). Whenever it occurs, any pending requests anchored to that consensus state at that moment have their escrowed fees permanently locked — a real, foreseeable, and unmitigated outcome of the protocol's own security mechanism.

### Recommendation
Introduce a fee-recovery path that does not depend on `is_consensus_client_frozen` succeeding once a client is permanently frozen — e.g., allow `on_frozen_client` cleanup logic (triggered by the same `FrozenClient` message result already returned by `freeze_client`) to sweep and refund all outstanding `RequestCommitments`/`_requestCommitments` entries whose proof height belongs to the frozen `consensus_state_id`, without requiring a fresh non-membership state proof from the now-untrusted/frozen source chain. Alternatively, expose an explicit governance-gated "force refund" extrinsic/function scoped to commitments tied to a frozen consensus state id, analogous to the report's suggested `pull_when_shut()`.

### Proof of Concept
1. App on chain A dispatches a `PostRequest` with a non-zero relayer fee; fee is escrowed (`RELAYER_FEE_ACCOUNT` on Substrate, or `_requestCommitments[commitment].fee` on EVM) — see `test_dispatch_fees_and_refunds`: [4](#0-3) 
2. Before the request is delivered or times out, a fisherman submits a valid `FraudProofMessage` for the consensus client backing chain A's state commitments; `freeze_client` succeeds and permanently sets `FrozenConsensusClients::<T>::insert(client, true)` with no unfreeze path: [5](#0-4) 
3. Delivery attempt: `handle_incoming_message` → `request::handle` → `validate_state_machine` → `is_consensus_client_frozen` returns `Err(FrozenConsensusClient)`. Confirmed by `frozen_consensus_client_check`: [6](#0-5) 
4. Timeout attempt (once `timeout_timestamp` elapses): `timeout::handle` also calls `validate_state_machine(host, timeout_proof.height)` first, at line 50, using the same frozen `consensus_state_id` — it fails identically before any non-membership proof is even checked: [2](#0-1) 
5. Because step 2 is irreversible (no `unfreeze` / no re-anchoring of old proof heights to a newly created client), the escrowed fee from step 1 can never be released by any code path in the repository.

/// Freeze a consensus client by providing a valid fraud proof.
pub fn freeze_client<H>(host: &H, msg: FraudProofMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host
		.consensus_client_id(msg.consensus_state_id)
		.ok_or_else(|| Error::Custom("Unknown Consensus State Id".to_string()))?;

	host.is_consensus_client_frozen(msg.consensus_state_id)?;

	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;

	consensus_client.verify_fraud_proof(host, trusted_state, msg.proof_1, msg.proof_2)?;

	host.freeze_consensus_client(msg.consensus_state_id)?;

	host.store_consensus_update_time(msg.consensus_state_id, host.timestamp())?;

	Ok(MessageResult::FrozenClient(msg.consensus_state_id))
}
