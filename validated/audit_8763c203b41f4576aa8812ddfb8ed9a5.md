## Analysis

The critical finding: the `Bid` signature scheme in `kaiax/auction` binds the searcher's EIP-712 signature (`SearcherSig`) to a struct hash computed by `Bid.EncodeData()`, which is version-dependent. The **v2.1 typehash/struct-encoding path (`AuctionVersionV2` = `"0.0.1"`, and the default/unknown-version fallback) never includes `MaxGasPrice` in the signed data**, even though `MaxGasPrice` is a first-class field of `BidData` that flows into transaction encoding, hashing, and pool admission. [1](#0-0) [2](#0-1) 

This is structurally the same bug class as the report: a cryptographic commitment/challenge (there: Fiat-Shamir challenge; here: the EIP-712 digest that the searcher signs) is computed over an **incomplete** view of the data that is later used to build and execute the actual transaction (`EncodeAuctionCallData`, which does read `bid.MaxGasPrice` when packing v3 calldata, and downstream gas-limit/settlement logic reads `bid.MaxGasPrice` from `BidData`): [3](#0-2) [4](#0-3) 

`bid.Hash()` (used for pool de-duplication/admission keying) is an RLP hash over the entire `BidData` struct including `MaxGasPrice`, so at the RLP/pool layer the field is "present," but the **searcher's authorization (signature)** never actually commits to it under the v2 typehash. `ValidateSearcherSig` only checks that the EIP-712 digest recovers to `bid.Sender`; it does not separately bind `MaxGasPrice` when version resolves to v2/default: [5](#0-4) [6](#0-5) 

Because `bp.auctionEntryPointVersion` is read from on-chain state and can equal `AuctionVersionV2` or any unrecognized string (both fall back to the un-hashed-`MaxGasPrice` path in `GetHashTypedData`), any party who can mutate `bid.MaxGasPrice` after the searcher signs — e.g. the auctioneer (who separately re-signs only `GetEthSignedMessageHash()` over the raw `SearcherSig` bytes, not over the bid content) — can submit a `Bid` with a searcher-approved signature but an attacker-chosen `MaxGasPrice`, and it will pass `validateBidSigs` unchanged. The auctioneer's own signature does not protect against this because `GetEthSignedMessageHash()` signs the *bytes of `SearcherSig`* only, not the `BidData`: [7](#0-6) [8](#0-7) 

`MaxGasPrice` is subsequently packed into the on-chain `call()` invocation for v3-encoded calldata via `EncodeAuctionCallData`, meaning the value that reaches contract execution/settlement (gas price capping enforced by the entry-point contract) can diverge from what the searcher actually authorized, without invalidating either signature — a direct parallel to "crafting fields expressions/values that a challenge doesn't cover, allowing a specific chosen value to pass verification for an otherwise-invalid statement."

I could not fully verify from the indexed code how the on-chain `AuctionEntryPointV3` contract enforces `MaxGasPrice` at settlement (i.e., whether a mismatched/omitted-from-signature `MaxGasPrice` translates into concrete fee-delegation or value-extraction, e.g. bypassing a searcher's declared price ceiling to charge them more, or letting a malicious auctioneer relay a bid with an inflated `MaxGasPrice` the searcher never agreed to). That contract source was not found in the indexed files, so the ultimate value-movement impact (fee/settlement abuse) is plausible but not independently confirmed on-chain — only the off-chain module-level signature gap is confirmed in code.

### Title
Auction Bid v2.1 EIP-712 Struct Hash Omits `MaxGasPrice`, Allowing Signature Reuse With a Tampered Gas-Price Field - (File: kaiax/auction/eip712.go)

### Summary
`Bid.GetHashTypedData` selects between a v2.1 struct encoding (`Bid.EncodeData`) and a v3.0 struct encoding (`bidV3.EncodeData`) based on the auction entry point's on-chain `AUCTION_VERSION`. Only the v3.0 encoding includes `MaxGasPrice` in the signed digest; the v2.1 encoding (and the fallback path for any unrecognized version string) excludes it entirely, even though `BidData.MaxGasPrice` is a real, independently-settable field that is later serialized into the on-chain `call()` payload by `EncodeAuctionCallData` for v3 calldata packing.

### Finding Description
The searcher signs `digest := b.GetHashTypedData(chainId, verifyingContract, version)` and this digest is verified in `Bid.ValidateSearcherSig` / `BidPool.validateBidSigs`. When `version` resolves to `AuctionVersionV2` ("0.0.1") or any unknown string, `GetHashTypedData` calls `EncodeEIP712(b)`, which uses `Bid.EncodeData()` — a function that encodes `TargetTxHash, BlockNumber, Sender, To, Nonce, Bid, CallGasLimit, keccak(Data)` but omits `MaxGasPrice` entirely. This means the searcher's cryptographic authorization does not bind to the value of `MaxGasPrice` stored in the same `BidData` struct that circulates through the bid pool and is later ABI-encoded for on-chain execution. `bp.auctionInfoMu`-protected `auctionEntryPointVersion` is read from the live chain state (`ReadAuctionVersion`) and used uniformly for all incoming bids; whenever it is `"0.0.1"` (the currently deployed/default version per tests and mocks) `MaxGasPrice` sits entirely outside the signed commitment. The auctioneer's counter-signature (`ValidateAuctioneerSig`) likewise does not remedy this, since it is computed over `GetEthSignedMessageHash()`, which hashes only the raw `SearcherSig` byte string, not the `BidData` content — so it does not bind `MaxGasPrice` either.

### Impact Explanation
This is directly analogous to the referenced weak Fiat-Shamir bug class: a value (`MaxGasPrice`) that participates in the eventual on-chain call (`EncodeAuctionCallData`, `blockchain/system/auction.go:83-119`) and in the RLP-based bid identity (`bid.Hash()`) is not covered by the cryptographic authorization the searcher actually produced. Any actor able to mutate the `BidData.MaxGasPrice` field between signing and pool submission/inclusion — most plausibly the auctioneer, RPC layer, or any intermediary relaying `SubmitBid` calls — can present a bid with the searcher's valid signature attached to a different `MaxGasPrice` than the searcher intended, without invalidating `ValidateSearcherSig`. Depending on how the on-chain `AuctionEntryPoint` enforces `maxGasPrice` as a price ceiling at settlement, this can let an auctioneer or block-builder-adjacent party settle a searcher's bid at a gas price the searcher never approved, extracting excess fee value from the searcher's designated approval — a fee/auction settlement abuse reachable purely from bid submission (single public RPC call `auction_submitBid`) with no need for any privileged or consensus role.

### Likelihood Explanation
Moderate-to-high for the module-level signature gap itself: it requires no special privilege beyond controlling or intercepting the bid-construction pipeline (the auctioneer role, or any party between searcher signing and pool submission), and is trivially reproducible by comparing `Bid.EncodeData()` vs `bidV3.EncodeData()`. It is currently gated by which on-chain `AUCTION_VERSION` string is deployed (`"0.0.1"` vs `"0.0.2"`); since v2.1 is the original/fallback version and is still supported code (`AuctionVersionV2`, and the unrecognized-version fallback both share this vulnerable path), any deployment running v2.1 auction entry points is exposed. Full exploitation confirmation additionally depends on unindexed on-chain contract logic for how `maxGasPrice` is enforced at settlement, which could not be verified here.

### Recommendation
Include `MaxGasPrice` in the v2.1 (and any fallback/unknown-version) EIP-712 struct encoding as well, or reject/require the v3.0 typehash whenever `bid.MaxGasPrice` is non-nil/non-zero, so the searcher's signature always commits to every field that participates in on-chain execution and bid identity. Alternatively, have `ValidateSearcherSig` explicitly reject bids where `MaxGasPrice` is set but the resolved signing version does not cover it, closing the gap between "fields present in `BidData`/`bid.Hash()`" and "fields actually covered by the searcher's cryptographic commitment."

### Proof of Concept
Conceptual PoC (module-level, not run against live chain):
1. Searcher signs a `Bid` with `MaxGasPrice = X` using `GetHashTypedData(chainId, verifyingContract, "0.0.1")`, producing `SearcherSig` over a digest from `Bid.EncodeData()` (no `MaxGasPrice` field).
2. An intermediary (e.g. auctioneer) changes `bid.MaxGasPrice` to `Y != X` and re-signs `AuctioneerSig` over `GetEthSignedMessageHash()` (which only hashes the unmodified `SearcherSig` bytes, unaffected by the `MaxGasPrice` change).
3. Submit via `auction_submitBid`; `BidPool.validateBidSigs` calls `ValidateSearcherSig` (digest unaffected by `MaxGasPrice`, passes) and `ValidateAuctioneerSig` (unaffected by `MaxGasPrice`, passes). [6](#0-5) 
4. The tampered `bid.MaxGasPrice = Y` is accepted into the pool and later used by `EncodeAuctionCallData` when packing calldata (for v3 ABI paths) despite never being authorized by the searcher's signature. [9](#0-8)

```go
// GetHashTypedData returns the EIP-712 digest for the bid.
// version must match the on-chain AUCTION_VERSION of the entry-point contract
// the bid targets; "0.0.2" selects the v3.0 struct typehash (with maxGasPrice),
// any other value falls back to the v2.1 typehash.
func (b *Bid) GetHashTypedData(chainId *big.Int, verifyingContract common.Address, version string) []byte {
	if chainId == nil {
		return nil
	}

	domain := EIP712Domain{
		EIP712DomainTypeHash: eip712TypeHash,
		NameHash:             auctionNameHash,
		VersionHash:          crypto.Keccak256Hash([]byte(version)),
		ChainId:              chainId,
		VerifyingContract:    verifyingContract,
	}

	domainSeparator := EncodeEIP712(domain)

	var structHash []byte
	if version == AuctionVersionV3 {
		structHash = EncodeEIP712(bidV3{b})
	} else if version == AuctionVersionV2 {
		structHash = EncodeEIP712(b)
	} else {
		// Unknown version: default to v2.1 typehash.
		structHash = EncodeEIP712(b)
	}

	return crypto.Keccak256([]byte{0x19, 0x01}, domainSeparator, structHash)
```

```go
func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}
```

```go
func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
```
