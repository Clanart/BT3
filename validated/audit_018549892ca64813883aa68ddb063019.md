### Title
LCP Fetch Failure in `PayoutCheckerTask::run_once` and `get_next_txs_to_send` Blocks Kickoff Initiation, Stalling Operator Reimbursement — (`core/src/task/payout_checker.rs`, `core/src/operator.rs`)

---

### Summary

`PayoutCheckerTask::run_once` and `get_next_txs_to_send` both call `fetch_validate_and_store_lcp` as a **preparatory** step (the LCP is only needed later, if the operator is challenged). Both call sites propagate the error with `?`, so any transient failure of the Citrea light client prover rolls back the entire database transaction, leaves the payout permanently marked as "unhandled", and prevents the kickoff transaction from ever being queued or returned. The operator, who has already fronted the withdrawal from their own funds, is blocked from initiating reimbursement for as long as the prover is unavailable.

---

### Finding Description

**`PayoutCheckerTask::run_once` — `core/src/task/payout_checker.rs:39-111`**

The task:
1. Opens a single `dbtx`.
2. Calls `handle_finalized_payout` (assigns a kickoff connector, signs txs, writes to DB — all inside `dbtx`).
3. Calls `fetch_validate_and_store_lcp` with `await?` at line 99.
4. If step 3 returns `Err`, the `?` propagates, `dbtx` is dropped (rolled back), `mark_payout_handled` is never called, and the payout row stays `is_payout_handled = FALSE`.

The code comment at line 81 explicitly acknowledges this is a preparatory step:

> `// fetch and save the LCP for if we get challenged and need to provide proof of payout later`

The LCP is not required to broadcast the kickoff transaction. It is only required if the operator is subsequently challenged and must post assert transactions. Tying the kickoff initiation to LCP availability violates the same invariant as the original report: a critical bridge operation (kickoff) must not be blocked by an optional preparatory sub-call. [1](#0-0) 

**`get_next_txs_to_send` — `core/src/operator.rs:1811-1835`**

The same pattern appears in the manual reimbursement path. When the kickoff tx is not yet on-chain, `fetch_validate_and_store_lcp` is called with `await?` before the kickoff tx is pushed to `txs_to_send`. A failure here returns an error from `get_next_txs_to_send`, so `get_reimbursement_txs` also fails, blocking the operator's manual reimbursement path. [2](#0-1) 

**`fetch_validate_and_store_lcp` failure modes — `core/src/citrea.rs:326-361`**

The function returns `Err` when:
- `get_light_client_proof_by_l1_height` returns `None` (prover has not yet processed the block).
- The HTTP call to the light client prover times out or returns a network error.
- Proof deserialization or verification fails. [3](#0-2) 

---

### Impact Explanation

The operator has already spent their own BTC to front the withdrawal (payout transaction on Bitcoin). Until `mark_payout_handled` is called and the kickoff tx is queued, the operator cannot begin the reimbursement sequence (Kickoff → ChallengeTimeout → ReadyToReimburse → Reimburse). Both the automated path (`PayoutCheckerTask`, polling every 60 s in production) and the manual path (`get_reimbursement_txs` RPC) are blocked by the same failure. The operator's fronted BTC and locked collateral remain unreimbursed for the entire duration of the prover outage. [4](#0-3) [5](#0-4) 

---

### Likelihood Explanation

The Citrea light client prover is an external HTTP service. Transient unavailability (network partition, rolling restart, block-processing lag) is a realistic operational condition. The prover may also simply not have generated the proof for the payout block height yet at the moment the task first runs. Because the task retries every 60 seconds, a short outage is self-healing, but a sustained outage (hours to days) directly delays or prevents operator reimbursement with no in-protocol fallback. [6](#0-5) 

---

### Recommendation

Decouple the LCP prefetch from the kickoff initiation. The kickoff should be queued and `mark_payout_handled` called regardless of LCP availability. The LCP fetch should be retried independently (e.g., a dedicated background task) and must succeed before `send_asserts` is invoked. Concretely:

1. In `PayoutCheckerTask::run_once`, remove the `fetch_validate_and_store_lcp` call (or wrap it so its error is logged and ignored, not propagated).
2. In `get_next_txs_to_send`, similarly decouple the LCP fetch from the kickoff tx return path.
3. Add a separate background task (or retry loop inside `send_asserts`) that ensures the LCP is present before assert transactions are constructed.

This mirrors the recommended fix in the original report: return the old/cached value instead of reverting, so the critical operation (kickoff / liquidation) always proceeds.

---

### Proof of Concept

1. Operator calls `withdraw` and fronts a BTC withdrawal on Bitcoin.
2. `PayoutCheckerTask` detects the unhandled payout and calls `handle_finalized_payout` (succeeds, assigns kickoff connector inside `dbtx`).
3. `fetch_validate_and_store_lcp` is called; the Citrea light client prover returns an error (e.g., proof not yet available for the payout block height).
4. `?` propagates the error; `dbtx` is dropped and rolled back.
5. `mark_payout_handled` is never called; the payout row remains `is_payout_handled = FALSE`.
6. The operator also calls `get_reimbursement_txs` manually; `get_next_txs_to_send` hits the same `fetch_validate_and_store_lcp` call at `operator.rs:1826` and returns an error.
7. Both automated and manual kickoff paths are blocked for the duration of the prover outage.
8. The operator's fronted BTC and collateral remain locked with no reimbursement path available. [7](#0-6) [8](#0-7)
