### Title
`lockFor` in VLMGP allows locking MGP on behalf of the zero address, permanently freezing the deposited tokens - (File: VLMGP.sol)

### Summary
`VLMGP.lockFor()` is a public, unauthenticated entry point that lets any wallet lock MGP tokens "for" an arbitrary `_for` address, with no check that `_for != address(0)`. If `_for` is the zero address, the MGP is transferred into the contract and permanently accounted to `address(0)` in `MasterMagpie`, an account that can never call `unlock()`/`startUnlock()`/`forceUnLock()` (those functions only operate on `msg.sender`, and `msg.sender` can never equal `address(0)`). This is the same bug class as the referenced Gearbox report: an `onBehalfOf`/`_for` parameter reaching internal accounting logic without a zero-address check.

### Finding Description
`lockFor` is externally callable with no access control: [1](#0-0) 

It calls `_lock`, which pulls MGP from `msg.sender` and forwards `_for` unchecked into `MasterMagpie.depositVlMGPFor`, then increases `totalAmount` (the vlMGP `totalSupply()`): [2](#0-1) 

`MasterMagpie.depositVlMGPFor` accepts any `_for`, including `address(0)`, since it is only gated by the `_onlyVlMgp` modifier (checking `msg.sender == vlmgp`), not by validating `_for`: [3](#0-2) 

This routes into `_deposit`, which records the staked amount under `userInfo[_stakingToken][address(0)]`: [4](#0-3) 

Once recorded under `address(0)`, the MGP can never be retrieved: all unlock paths in `VLMGP` (`startUnlock`, `unlock`, `cancelUnlock`, `forceUnLock`) operate strictly on `msg.sender`'s slots, and no transaction can ever originate from `msg.sender == address(0)`: [5](#0-4) 

Additionally, `_beforeTokenTransfer` unconditionally reverts, so the vlMGP "shares" credited to `address(0)` cannot be transferred out either: [6](#0-5) 

### Impact Explanation
MGP tokens locked with `_for = address(0)` become permanently and irrecoverably stuck in the `VLMGP` contract — not just for 24 hours, but forever, since there is no mechanism (owner or otherwise) to unlock or reassign a position keyed to the zero address. This satisfies "permanent freezing of funds" for any wallet that ends up (directly or via front-end/integration bug) calling `lockFor` with a zero `_for` address.

### Likelihood Explanation
The function is reachable directly by any ordinary wallet with a single unprivileged transaction — no admin, governance, or oracle interaction is required. The only precondition is a caller (user wallet, script, or integrating contract) supplying `address(0)` as `_for`, which is a plausible default/uninitialized value in many client-side integration bugs.

### Recommendation
Add an explicit check in `VLMGP.lockFor` (and defensively in `MasterMagpie.depositVlMGPFor`) that reverts when `_for == address(0)`, mirroring the recommendation from the referenced report.

### Proof of Concept
1. Caller A holds MGP and calls `VLMGP.lockFor(amount, address(0))`.
2. `_lock` pulls `amount` MGP from A into `VLMGP`, then calls `MasterMagpie.depositVlMGPFor(amount, address(0))`.
3. `MasterMagpie._deposit` credits `userInfo[address(vlmgp)][address(0)].amount += amount`; `VLMGP.totalAmount` increases accordingly.
4. No account can ever call `unlock`/`startUnlock` with `msg.sender == address(0)`, so the `amount` of MGP is permanently locked in the `VLMGP` contract with no recovery path.
