### Title
Missing `<`/`>`/JS-sensitive-character escaping in upb's ProtoJSON string encoder enables HTML/script-context injection - (File: `upb/json/encode.c`)

### Summary
CVE-2019-10067 is an OTRS agent-UI XSS where a URL-controlled value reaches a JavaScript execution context without adequate output encoding. The transferable invariant is: *any string value derived from attacker-controlled input that a component intentionally serializes for later embedding in an HTML/JS execution context must have JS-significant characters (`<`, `>`, line/paragraph separators, bidi/invisible control characters) neutralized before being handed to that context.* Protobuf's own C++, Java, and C# ProtoJSON encoders implement exactly this invariant as a deliberate defense-in-depth measure. The upb-based JSON encoder — shared natively by PHP, Ruby, Lua, and any direct upb consumer — does not, creating a genuine cross-implementation inconsistency in the public ProtoJSON serialization API.

### Finding Description
The C++ ProtoJSON writer explicitly escapes `<`, `>`, U+2028/U+2029, and several other zero-width/bidi characters specifically "to prevent security bugs in JavaScript": [1](#0-0) 

The same defense is independently re-implemented in Java's `JsonFormat`: [2](#0-1) 

and in C#'s `JsonFormatter`, again explicitly noting "Escaping of < and > are required for HTML security": [3](#0-2) 

By contrast, the upb C JSON encoder's per-character escape routine — compiled into `php-upb.c` (PHP native extension), `ruby-upb.c` (Ruby native extension), and used directly by Lua bindings and any first-party upb C consumer — only escapes JSON-spec-mandated characters (`"`, `\`, control chars `<0x20`) and passes all other bytes, including `<` and `>`, straight through: [4](#0-3) 

This same code (byte-for-byte) is embedded in both the PHP and Ruby native extensions: [5](#0-4) [6](#0-5) 

The missing check is the absence of the `<`/`>`/U+2028/U+2029/invisible-character escape cases that exist in every other first-party ProtoJSON implementation. The attacker-controlled value is any `string` field content set by a client sending trusted-schema ProtoJSON/binary through the public serialize API; no privileged access or schema/plugin control is needed — only that the consuming application later embeds the serialized JSON output inside an HTML document (e.g., inline in a `<script>` tag for client-side state bootstrapping), a pattern explicit in the very code comments and regression tests of the C++/Java/C# implementations: [7](#0-6) 

### Impact Explanation
If a consuming application built on the PHP/Ruby/Lua/direct-upb bindings follows the same "embed ProtoJSON output inline in HTML" pattern that Protobuf's own C++/Java/C# implementations were hardened to protect (as documented by their comments and regression tests), a string field value containing `</script><script>...</script>` or U+2028/U+2029 payloads will pass through upb's encoder unescaped, breaking out of the intended JSON-string literal in the embedding HTML/JS context and enabling script injection (stored/reflected XSS) in that consuming application. This mirrors the OTRS case: a value intended purely as data reaches and executes as script due to a missing output-encoding invariant. Impact is confined to XSS/script-injection in the consuming application's rendered page — no protobuf memory-safety or RCE impact — consistent with Medium severity, matching CVSS characteristics of the source CVE (network, low complexity, requires user interaction to view the affected page, confidentiality/integrity-limited).

### Likelihood Explanation
Likelihood depends entirely on application usage, not on protobuf's binary/JSON parsing itself. The trigger requires: (1) an application using the PHP or Ruby (or other upb-backed) protobuf JSON serializer, and (2) that application embedding the serialized JSON output directly/inline into an HTML page without its own additional escaping — a documented and previously-real anti-pattern that the C++/Java/C# implementations were explicitly hardened against (see the `b/73832901` regression comment). Because the escaping asymmetry exists silently across otherwise-equivalent official language bindings of the same library, developers migrating between bindings (e.g., relying on Java's documented HTML-safety behavior, then switching to PHP or Ruby) would unknowingly lose this protection.

### Recommendation
Port the `<`, `>`, U+2028, U+2029, and other JS-sensitive character escaping rules from `src/google/protobuf/json/internal/writer.cc`'s `MustEscape` (and the equivalent Java/C# tables) into upb's `jsonenc_put_escaped_char`/`jsonenc_stringbody` in `upb/json/encode.c`, so PHP, Ruby, Lua, and other upb-based bindings receive the same documented HTML/JS-safety guarantee as the C++, Java, and C# ProtoJSON encoders.

### Proof of Concept
Using the Ruby or PHP native extension (upb-backed):
1. Define a trusted schema with a `string` field, e.g. `optional_string`.
2. Set `optional_string = "</script><script>alert(1)</script>"`.
3. Call the public JSON-serialize API (`Message#to_json` in Ruby / `serializeToJsonString` in PHP), both of which route through `jsonenc_string` → `jsonenc_stringbody` → `jsonenc_put_escaped_char` in `upb/json/encode.c`/`ruby-upb.c`/`php-upb.c`.
4. Observe the output contains the literal, unescaped `</script><script>alert(1)</script>` substring (no `\u003c`/`\u003e` escaping), unlike the equivalent Java (`JsonFormat.printer().print(...)`) call on the identical field/value, which is asserted by existing test `testHtmlEscape` to produce `\u003c/script\u003e`: [8](#0-7) 

This confirms the escape-table divergence is reachable through the public, documented JSON serialization entry point of the upb-backed bindings with only a bounded, attacker-supplied string value and a trusted schema — no privileged access, hostile schema, or memory-safety bypass required.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}
