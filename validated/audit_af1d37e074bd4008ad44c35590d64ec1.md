Confirmed vulnerability found via the shared `resolveWithin`/`_resolveWithin` sandbox helper used to gate attacker-influenced paths (Copilot conflict resolution file writes, `openRepositoryFromUrl` deep-link file paths, and conflict-context reads).

### Title
Prefix-only containment check in `_resolveWithin` allows escaping the repository root to a sibling directory - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin` is GitHub Desktop's single reusable guard against path traversal/symlink escapes. It resolves the target path, `realpath`s both the root and the candidate, and then checks `realResolved.startsWith(realRoot)`. This is a raw string-prefix comparison with no trailing-separator boundary check, so any real path that merely shares the root's string prefix — not necessarily a descendant of it — is treated as "inside" the repo.

### Finding Description
`_resolveWithin` in [1](#0-0)  computes:
```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```
The intended invariant is "the resolved path must be a descendant of (or equal to) the root directory." The actual check only verifies a string prefix match. If `realRoot` is e.g. `/Users/victim/Documents/GitHub/repo`, then `/Users/victim/Documents/GitHub/repo-secrets/id_rsa` also satisfies `startsWith(realRoot)` even though it is a completely different, sibling directory outside the repository. This is exactly the same class of bug as the reported RToken issue: a check is performed against a transformed/loosely-related value ("does the string start with the root string") instead of the value that actually matters ("is this path a true descendant of the root"), so the guard silently under-enforces its own contract.

Existing tests only cover exact escape (`..`) and symlink-based escape scenarios [2](#0-1) , but there is no test for the sibling-directory-with-shared-prefix case, and the implementation provides no protection against it.

This helper gates several attacker-reachable, unprivileged flows:
- Writing Copilot-suggested conflict resolutions to disk, where `resolution.path` comes from parsed LLM/API JSON and is checked with `resolveWithin(repository.path, resolution.path)` before `writeFile` [3](#0-2) .
- Reading conflicted file contents to send to Copilot, using the same guard [4](#0-3) .
- Handling `x-github-desktop` deep links (`filepath` parameter, fully attacker-controlled via a link the user clicks) before calling `shell.showItemInFolder(resolved)` [5](#0-4) .

### Impact Explanation
If an attacker can arrange for the repository root's real path to end without a path separator right before a controllable suffix (e.g., a repo cloned/opened at a location like `.../repo`, and the attacker can get Desktop to resolve a segment such as `../repo-evil/...`), the prefix check passes even though the resulting path is outside the actual repository. Combined with the Copilot-resolution write path, this could let attacker-controlled content (a maliciously crafted conflict/LLM response referencing a sibling-prefixed path) be written outside the intended repository, or let a malicious deep link cause `shell.showItemInFolder` to reveal/act on a path outside the repo. The severity depends on what actually sits at the sibling location, but the core guarantee ("write/read is confined to the repo") is broken by design, not by an edge-case oversight.

### Likelihood Explanation
Exploitability requires the attacker to control the untrusted path segment (already true for the flagged call sites — Copilot JSON responses and deep-link `filepath` values are both attacker/API-influenced) and for the environment to have (or for the attacker to be able to create, e.g. via a cloned repo containing a sibling folder name, or a differently-named directory adjacent to the opened repo) a same-prefix sibling path. This is more constrained than a full free-form traversal bug (no `..`/symlink needed against the intended target, but the attacker needs a "prefix-colliding" real path to exist), so likelihood is moderate rather than trivial, but it is a genuine, unprivileged, no-local-access defect in the core safety primitive that every one of these call sites relies on.

### Recommendation
Fix `_resolveWithin` to require an actual path-hierarchy match rather than a string prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add a regression test asserting that a sibling directory sharing the root's string prefix (e.g. root `.../repo`, candidate real path `.../repo-evil/file`) is rejected.

### Proof of Concept
1. Create `root = /tmp/x/repo` and `sibling = /tmp/x/repo-evil`, with `sibling/secret.txt` present.
2. Call `_resolveWithin('/tmp/x/repo', ['../repo-evil/secret.txt'])`.
3. `resolve(normalizedRoot, normalizedRelative)` yields `/tmp/x/repo-evil/secret.txt`; `realpath` of both root and resolved path are computed.
4. `realResolved.startsWith(realRoot)` evaluates `'/tmp/x/repo-evil/secret.txt'.startsWith('/tmp/x/repo')` → `true`, so the function returns the resolved path even though `/tmp/x/repo-evil` is not inside `/tmp/x/repo`.
5. In the Copilot-conflict-resolution write path, an attacker-influenced `resolution.path` of `../repo-evil/secret.txt` would pass the guard at [6](#0-5)  and `writeFile` would write outside the repository.
