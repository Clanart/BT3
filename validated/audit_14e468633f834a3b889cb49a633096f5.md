### Title
Index-only (positional) line selection in partial-commit patch generation lets stale/rewritten diff content be silently staged without content validation - (File: `app/src/lib/patch-formatter.ts`)

### Summary
GitHub Desktop's partial-commit ("stage selected lines") feature tracks which diff lines the user wants to commit purely by numeric position (`absoluteIndex`), not by line identity/content. When the patch actually applied to the index is built, Desktop re-fetches a fresh diff from disk and blindly re-applies the old, position-based selection to it. This is the same class of defect as the reported `IndexedMerkleTree::update` bug: an "index" is trusted to still refer to the same logical element without validating that the element at that index still matches what the index was originally computed against.

### Finding Description
`DiffSelection` stores selected/deselected lines as a `Set<number>` of positional indices with no link to line content: [1](#0-0) 

The UI computes these indices from a diff object loaded and cached in `IChangesState.selection.diff`. When the user actually commits, `applyPatchToIndex` re-fetches the diff live from the working directory (not the cached one shown in the UI) and immediately builds the patch from it: [2](#0-1) 

`formatPatch` then walks the *freshly fetched* diff's hunks/lines and decides what to include using `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is simply `hunk.unifiedDiffStart + lineIndex` in the new diff: [3](#0-2) 

There is no check that the line at `absoluteIndex` in this newly fetched diff is the same logical line the user selected in the diff they were actually looking at. The codebase itself acknowledges this class of problem exists — `updateChangesWorkingDirectoryDiff` has a comment stating "the diff might have changed dramatically since last we loaded it" and attempts a partial mitigation by recomputing `selectableLines` and dropping selections that no longer point at an "includeable" line: [4](#0-3) 

That mitigation only prevents selecting/keeping-selected an index that has become a context line or ceased to exist. It does **not** prove the selected index still corresponds to the *same content*. If the working-copy file is rewritten between the last diff load and the commit in a way that preserves hunk shape (same number of added/deleted lines, same line types at the same offsets, e.g. a byte-for-byte reordering or a diff-shape-preserving content substitution), `selectableLines` stays identical, no line gets dropped from `divergingLines`, and `formatPatch` will happily apply the user's old selection indices to entirely different new/deleted line content — because `isSelected`/`isIncludeableLine` never inspect the line's text.

### Impact Explanation
This can cause **silent corruption of what the user commits**: the app-generated patch can stage attacker-controlled content the user never reviewed or intended to select, or drop content the user did intend to commit, while the UI shows a diff that no longer matches what is actually written into the git index/commit. This maps directly to the report's core concern ("If an element is inserted at an incorrect index... it will result in inconsistencies") — here the "tree" is the git index/commit, and the "element" is a diff line.

### Likelihood Explanation
Exploitation requires the working-copy file content to change between when Desktop last displayed/cached the diff for line-selection purposes and when `applyPatchToIndex` re-reads the diff to build the commit patch — a window that exists on every partial commit because of the deliberate double-fetch design (`app/src/lib/git/apply.ts:60` vs the UI's cached `selection.diff`). This is a timing/consistency assumption rather than a guaranteed-exploitable single input, so I rate confidence in real-world triggerability as moderate; I was not able to fully verify whether any other guard (e.g., hashing hunk content, or blocking commit if `git status`/diff changed) exists elsewhere in `update-index.ts` or the commit dispatch path, since I ran out of investigation budget before reading those files in full.

### Recommendation
- Do not key `DiffSelection` purely on positional index; associate selections with a content fingerprint of the hunk/line (e.g., hash of `oldLineNumber`/`newLineNumber` plus line text) captured at selection time.
- Before calling `formatPatch` in `applyPatchToIndex`, diff the freshly fetched hunks against the hunks that produced the current `DiffSelection` and abort/re-prompt if hunk shapes or line contents diverge, rather than assuming index stability.
- Extend the existing "selectableLines" revalidation in `app-store.ts` (`updateChangesWorkingDirectoryDiff`) to also invalidate selections when line *content* changed even if line count/type layout is unchanged.

### Proof of Concept
Conceptual reproduction (not fully verified end-to-end due to tool-call limits):
1. Open a repo in Desktop, modify a tracked file so it has an add/delete hunk, and select only some of the added lines for partial commit (`DiffSelection.withLineSelection`).
2. Before clicking "Commit", cause the working file to be rewritten with a different but diff-shape-identical set of added lines at the same offsets (same number of `+`/`-`/context lines, same positions) — e.g., through an editor auto-format, a build/watch script bundled with the cloned repository, or any process that touches the file.
3. Commit. `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff and `formatPatch` (`app/src/lib/patch-formatter.ts:143-161`) reuses the old `DiffSelection`'s numeric indices against the new hunk lines, staging content the user never actually reviewed/selected in the visible diff.
