### Title
Liquidation (and all other position-valuation flows) panics entirely if any single collateral asset in a position's mask fails oracle confidence/staleness/validity checks — (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate`, `borrow`, and `repay` all call `get-assets`, which resolves prices for every asset in the safe mask via `price-multi-resolve` and then does `unwrap-panic` on the result. If a single asset among the user's collateral fails the oracle's confidence check, staleness check, or positivity check, the whole batch resolution returns an error and the caller's `unwrap-panic` aborts the entire transaction — this includes `liquidate`, which is exactly the same failure mode the BlueBerryBank report warns about (a single unpriceable/failing token DOSing whole-position valuation and thereby blocking liquidation).

### Finding Description
`get-assets` builds the list of oracle configs for every collateral asset enabled for the user's mask and resolves all their prices in one batch call: [1](#0-0) 

`price-multi-resolve` folds over all oracle entries, calling `price-resolve` for each. If any single `price-resolve` call fails, `iter-price-multi` marks the whole accumulator invalid, and the parent asserts `valid` and returns an `Err` for the *entire batch*: [2](#0-1) 

`price-resolve` itself gates on price positivity and on timestamp freshness/monotonicity (`oracle-timestamp-fresh`), and `resolve-pyth` additionally gates on confidence via `check-confidence`: [3](#0-2) [4](#0-3) 

Because `get-assets` calls `(unwrap-panic (price-multi-resolve ...))` rather than propagating the error gracefully or skipping the failing asset, a single asset in the mask that momentarily fails confidence/staleness/positivity gating (e.g., low-confidence Pyth quote, stale feed not yet updated this block, or DIA feed lag) causes the whole `get-assets` call — and therefore the whole calling function — to abort: [5](#0-4) 

`liquidate` depends on `get-assets` to compute `total-collateral-usd`/`total-debt-usd` for the entire position before it can even reach the health check that determines liquidatability: [6](#0-5) 

So if a borrower holds even one collateral asset whose price feed is momentarily stale or low-confidence, liquidation of the *entire* position — including any other severely undercollateralized debt/collateral pair on the same account — is blocked until that one feed's confidence/staleness condition is resolved. This is structurally identical to the BlueBerryBank `getPositionValue` bug: one unpriceable/failing element inside a batch valuation reverts the whole liquidation-critical computation instead of degrading gracefully.

### Impact Explanation
Liquidations are a process that needs high uptime; a hard revert triggered by a single asset's confidence/staleness gate blocks liquidation of the position as a whole, even for accounts that are severely unhealthy based on other, correctly-priced collateral. In a fast-moving market this can allow bad debt to accumulate on the affected position while the liquidator is unable to execute, matching the "temporary freezing of funds" impact class (the collateral/liquidation processing for that user's funds is frozen until the feed recovers).

### Likelihood Explanation
Confidence and staleness failures on individual feeds are not rare edge cases — they can occur during normal oracle update lag, network congestion, or momentary abnormal price deviations reported by Pyth/DIA. Any account that holds a mix of collateral assets (which the protocol explicitly supports via the mask-based multi-asset design) is exposed: only one of the several assets it holds needs to fail gating for the entire liquidation call on that account to panic.

### Recommendation
Do not `unwrap-panic` the batch price resolution in `get-assets`. Either: (1) allow `price-multi-resolve`/`iter-price-multi` to skip an asset that fails confidence/staleness/positivity gating and treat its value as zero (or use last-known-good with an explicit staleness-aware fallback) so other assets' valuations and the liquidation decision can still proceed, or (2) restructure liquidation-critical valuation to be resilient to a single feed failure (e.g., resolve only the specific collateral/debt asset pair needed for liquidation rather than requiring successful resolution of every asset in the mask).

### Proof of Concept
1. Configure a borrower position with two collateral assets, A and B, and outstanding debt sufficient to make the position eligible for liquidation.
2. Let asset B's price feed enter a state that fails `check-confidence` (low confidence Pyth quote) or `oracle-timestamp-fresh` (feed not yet updated this block, e.g., due to update ordering) — this is a normal transient oracle condition, not an attacker-controlled data feed.
3. Call `liquidate` targeting the borrower's undercollateralized debt backed by asset A. `get-assets` at [1](#0-0)  resolves prices for the *entire mask* including asset B, causing `price-multi-resolve` to return `Err` and the `unwrap-panic` to abort the transaction.
4. Liquidation of the account fails entirely, even though asset A's price is fine and the debt backed by it is genuinely under water, until asset B's feed condition clears.

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))
