## Title
Unvalidated check-run/status `target_url` from the GitHub API is passed to `shell.openExternal` with no protocol allow-list - ([File: app/src/main-process/main.ts])

### Summary
The externally reported bug's broken invariant is: a value taken from a "legitimately obtained" but attacker-authored object (a Circle-attested CCTP message) is trusted and acted upon without validating that it actually represents what it claims. The reachable Desktop analog is structurally the same shape: a GitHub API object field (`target_url` / `html_url` on a commit status or check run) that is fully attacker-controlled content within a legitimately-fetched API response is forwarded, unsanitized and with no scheme allow-list, into `shell.openExternal`, an OS-level trust boundary. Desktop already applies strict `https://`-only validation for other externally-supplied endpoints (GitHub Enterprise sign-in URL), but does not apply the same discipline to CI status/check-run links that a repo/PR author controls.

### Finding Description
- `IAPIRefStatusItem.target_url` is a free-form string returned by the GitHub Commit Status API and is set by whoever posts the status (an unprivileged PR author posting a status to their own fork/branch, or any app/integration with `statuses` write access, is enough — no special privilege on the target repository is required to have Desktop later display and open that link when the user, e.g. a maintainer, reviews the PR's checks). [1](#0-0) 
- Desktop converts that untouched, attacker-supplied string directly into the internal `IRefCheck.htmlUrl` field with no scheme or host validation: [2](#0-1) 
- The UI "View check details" flows (both the check-run popover and the "PR checks failed" notification) take that `htmlUrl` value verbatim and hand it to `dispatcher.openInBrowser(url)`: [3](#0-2) [4](#0-3) 
- `_openInBrowser` is a bare pass-through to Electron's `shell.openExternal`: [5](#0-4) 
- The main-process IPC handler for `open-external` performs no protocol allow-list either — it only *logs* when the URL happens to be `http(s)://`, but calls `shell.openExternal(path)` unconditionally for any other scheme: [6](#0-5) 

By contrast, Desktop's own GitHub Enterprise sign-in flow enforces an explicit `https:`-only check before trusting a user/attacker-influenced URL, proving the team is aware of this class of risk but has not applied it uniformly: [7](#0-6) 

The broken invariant: Desktop treats "this URL came from a parsed GitHub API JSON response" as equivalent to "this URL is safe to hand to the OS shell," the same category of mistake as CCTP treating "this message was attested by Circle" as equivalent to "value was actually minted." In both cases, the attacker fully controls the content of a field inside an object that a trusted third party legitimately processed for an unrelated purpose (Circle attests message delivery, not fund movement; GitHub attests that a status API call was accepted, not that `target_url` is a safe URI).

### Impact Explanation
`shell.openExternal` with attacker-chosen values is a well-documented dangerous sink: on Windows it resolves through `ShellExecute`, which can invoke arbitrary OS-registered custom URI protocol handlers (installed by other software), UNC paths, or `file://`/`search-ms:`/other scheme handlers, some of which have known RCE chains when fed attacker-controlled arguments. Because Desktop places no scheme allow-list on this value, any application/protocol handler present on the victim's machine that is exploitable via URL becomes reachable purely from clicking "View check details" on a PR the attacker authored or contributed a status to.

### Likelihood Explanation
The trigger requires no special repository privilege: posting a commit status with an arbitrary `target_url` is achievable by anyone able to push to a branch/PR (including PR authors on their own forks) or by any third-party CI integration with status-write scope. The victim maintainer reviewing that PR's checks and clicking "View check details" — a completely ordinary, expected Desktop workflow — is sufficient; no unnatural steps, local access, or leaked credentials are needed.

### Recommendation
Apply the same `https:`-only (or a small explicit allow-list of `http:`/`https:`) validation used in `app/src/ui/lib/enterprise-validate-url.ts` to every URL sourced from GitHub API responses before it reaches `dispatcher.openInBrowser` / `shell.openExternal`, and enforce it centrally in the `open-external` IPC handler in `app/src/main-process/main.ts` rather than relying on renderer-side callers to have already validated the scheme.

### Proof of Concept
1. Attacker opens a PR from their own fork (or posts a status via the Status API to a branch they can push to).
2. Attacker sets a commit status with `target_url` = a malicious URI scheme string, e.g. one that resolves via `ShellExecute` on the victim's Windows machine to a locally-installed vulnerable protocol handler with attacker-controlled arguments (or any scheme registered by other software on the target machine).
3. Victim maintainer opens the PR in GitHub Desktop, opens the checks popover, and clicks "View check details" (`ci-check-run-popover.tsx: onViewCheckDetails`).
4. `checkRun.htmlUrl` (== attacker's `target_url`, unmodified) flows through `dispatcher.openInBrowser` → `AppStore._openInBrowser` → IPC `open-external` → `shell.openExternal(path)` with no scheme check, executing whatever the OS shell resolves that URI to.

export function apiStatusToRefCheck(apiStatus: IAPIRefStatusItem): IRefCheck {
  let state: APICheckStatus
  let conclusion: APICheckConclusion | null = null

  if (apiStatus.state === 'success') {
    state = APICheckStatus.Completed
    conclusion = APICheckConclusion.Success
  } else if (apiStatus.state === 'pending') {
    state = APICheckStatus.InProgress
  } else {
    state = APICheckStatus.Completed
    conclusion = APICheckConclusion.Failure
  }

  return {
    id: apiStatus.id,
    name: apiStatus.context,
    description: getCheckRunShortDescription(state, conclusion),
    status: state,
    conclusion,
    appName: '',
    checkSuiteId: null,
    htmlUrl: apiStatus.target_url,
  }

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
