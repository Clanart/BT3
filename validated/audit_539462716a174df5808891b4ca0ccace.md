## Title
Payout tx's `SinglePlusAnyoneCanPay` signature lets an unprivileged attacker hijack the withdrawal-UTXO spend and permanently misattribute it to an arbitrary/non-existent operator - ([File: core/src/builder/transaction/operator_reimburse.rs])

## Summary
`create_payout_txhandler` builds the Payout transaction with only input 0 signed by the withdrawing user under `SinglePlusAnyoneCanPay`, which commits only to input 0 and to output 0 (the user's payout output) - it leaves all other inputs and outputs, including the operator-identifying OP_RETURN, completely unauthenticated. `Verifier::update_finalized_payouts` then blindly trusts whatever OP_RETURN bytes happen to be in the transaction that ends up confirmed spending the withdrawal UTXO, with no check that the parsed key belongs to a real, currently bonded operator.

## Finding Description
The broken binding: `withdrawals.payout_payer_operator_xonly_pk` (the operator credited/blamed for fronting withdrawal `i`) should equal the xonly public key of the operator that actually funded the user's payout output for withdrawal `i`. This binding is broken because the OP_RETURN carrying that attribution is not covered by any signature.

`create_payout_txhandler` [1](#0-0)  constructs the Payout transaction with a single signed input (key-path spend of the withdrawal UTXO, witness set from `user_sig`) and three outputs: the user payout (index 0), an anchor (index 1), and the operator-identifying OP_RETURN (index 2). `Operator::withdraw` computes `sighash = payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` and verifies the user's Schnorr signature against it, explicitly documenting that the sighash type must be `SinglePlusAnyoneCanPay` [2](#0-1) . Under BIP-341 `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`, the digest commits only to: input 0's prevout/amount/script, and the single output at the *same index* as the signing input (index 0). It does **not** commit to any other input, to the OP_RETURN output, to the anchor, or to the total number of inputs/outputs.

The developers were aware only outputs/inputs beyond index 0 are unconstrained - the RBF funding code explicitly places the wallet's change output "at last index (so that SinglePlusAnyoneCanPay signatures stay valid)" [3](#0-2)  - but this only protects the operator's *own* re-funding of its own broadcast; it does nothing to stop a third party from building a competing transaction.

Exploit flow:
1. Operator A calls `withdraw`, which signs/broadcasts (via RBF-enabled `fund_raw_transaction`/tx_sender) a Payout tx spending the withdrawal UTXO at input 0, with OP_RETURN naming A at output index 2.
2. This transaction (and its witness for input 0) is visible in the public mempool before confirmation.
3. An unprivileged attacker copies input 0 (outpoint + witness) into a new transaction, keeps output 0 identical (required, since it's committed by SIGHASH_SINGLE), but supplies their own funding inputs (paid for with their own BTC) and freely chooses all other outputs, including an OP_RETURN naming an arbitrary/non-existent operator C.
4. The attacker sets a higher fee and this variant, which conflicts with A's original by spending the same input, wins standard fee-based RBF replacement in mempool policy and gets mined.
5. `Verifier::update_finalized_payouts` (core/src/verifier.rs:2283) finds the withdrawal's spending txid via `get_payout_txs_for_withdrawal_utxos` (`core/src/verifier.rs:2289`, `core/src/database/verifier.rs:170`), reads the *first* OP_RETURN output, parses it as an xonly pubkey with no validation against the actual operator set, and writes it into `withdrawals.payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk` [4](#0-3) .
6. A's original broadcast can never confirm (its input is now spent). `Operator::withdraw`'s guard `get_withdrawal_utxo_from_citrea_withdrawal` still matches the same (now-spent) outpoint [5](#0-4) , so A cannot retry with any other attribution.
7. Downstream, `send_asserts` requires `payout_op_xonly_pk == kickoff_data.operator_xonly_pk` and errors otherwise [6](#0-5) , and `PayoutCheckerTask` only picks up payouts matching its own operator's xonly key via `get_first_unhandled_payout_by_operator_xonly_pk`, so A's task never sees this withdrawal [7](#0-6) . Since C does not exist (or is not running / has no bond), no kickoff will ever be produced that matches this withdrawal, and A - who genuinely fronted the withdrawal - has no path to reimbursement.

No existing guard catches this: `SECP.verify_schnorr` only checks the user's signature over input 0/output 0, which the attacker's transaction still satisfies exactly; the database uniqueness on `withdrawals.idx` (primary key) does not prevent a wrong attribution being written for that same `idx`; and `update_finalized_payouts` does not cross-check the OP_RETURN pubkey against the list of currently bonded operators.

## Impact Explanation
An honest operator that fronted a real withdrawal becomes permanently unable to be reimbursed for that specific payout, since the on-chain attribution row is forever bound to a different (possibly non-existent) operator identity and the withdrawal outpoint is already spent. This matches the listed Critical category "an honest operator permanently unable to be reimbursed." The attack is repeatable per withdrawal - any withdrawal fronted by any operator can be targeted the moment its Payout tx appears in the mempool, prior to confirmation, so the blast radius spans all operators and all withdrawals processed through this codepath (not the optimistic-payout path, which is verifier-cosigned and not vulnerable this way).

## Likelihood Explanation
The only preconditions are: (a) an operator broadcasts a standard Payout tx (normal operation), (b) the transaction sits unconfirmed in the mempool for at least one attacker-observable interval (mempool propagation to confirmation), and (c) the Bitcoin mempool/RBF policy accepts a higher-fee conflicting transaction, which is the default behavior of Bitcoin Core and most miners. The attacker's cost is limited to Bitcoin transaction fees (no deposit, no bond, no key compromise, no majority hashrate needed) - trivially "unprivileged" per the threat model. This makes the attack cheap, fully repeatable, and does not require any race against block confirmation beyond normal mempool timing.

## Recommendation
Bind the operator-attribution output (OP_RETURN) to the same signature that authorizes spending the withdrawal UTXO, e.g., by having the user sign with `SIGHASH_ALL` (or `SIGHASH_ALL|ANYONECANPAY` restricted to a template with a fixed, pre-agreed operator identity known to the user/aggregator at signing time) instead of `SinglePlusAnyoneCanPay`, so the OP_RETURN and full output set cannot be altered post-signature. Alternatively, require the operator to additionally sign the whole Payout transaction (covering the OP_RETURN) with their own operator key, and have `update_finalized_payouts` verify that signature/commitment before trusting the OP_RETURN attribution, and reject/flag attributions to xonly keys that do not correspond to a currently bonded operator.

Test plan:
1. Set up a deposit and withdrawal as in existing e2e helpers (`core/src/test/common/clementine_utils.rs::payout_and_start_kickoff`).
2. Have operator A call `internal_withdraw`/`withdraw` to produce and broadcast the signed Payout tx (input 0 = withdrawal UTXO, output 0 = user payout, OP_RETURN = A's xonly pk) without letting it confirm.
3. Extract input 0 (outpoint + witness) from the broadcast raw tx via RPC (`get_raw_transaction`), assert its `sighash_type` byte equals `SinglePlusAnyoneCanPay`.
4. Build a new transaction reusing input 0 verbatim, output 0 identical, add attacker-funded fee input(s) and an OP_RETURN naming a fabricated xonly pubkey `C` (not belonging to any operator in the test's `TestActors`), with a higher fee than A's tx.
5. Broadcast and mine the attacker's tx; assert A's original txid is now evicted/never confirms and the attacker's tx is the one in `bitcoin_syncer_spent_utxos`.
6. Run the verifier's block sync (`update_finalized_payouts`) and assert `db.get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id` returns `Some(C)`, not `Some(A)`.
7. Call `Operator::withdraw` again for the same `withdrawal_index` from A and assert it fails (outpoint already spent / mismatched attribution), and that `PayoutCheckerTask::run_once` for A never marks this withdrawal handled, demonstrating A's front is permanently unreimbursable.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
