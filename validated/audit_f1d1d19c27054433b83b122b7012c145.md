Audit Report

## Title
Stake account mutation between epoch-reward calculation and partitioned distribution triggers unhandled `assert_eq!` panic in `build_updated_stake_reward` - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

## Summary
`calculate_stake_rewards_and_commissions` snapshots a stake account's delegation at the epoch-boundary calculation phase into a `PartitionedStakeReward` [1](#0-0) , but that cached value is redeemed later, up to many blocks afterward, against the live account fetched from `stakes_cache_accounts` in `build_updated_stake_reward` [2](#0-1) . When `relax_post_exec_min_balance_check` is inactive, the code enforces a strict `assert_eq!` between the live delegation plus the cached reward and the cached post-reward delegation, rather than reconciling the two [3](#0-2) . This assertion runs inside mandatory, deterministic block-processing code (`distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition`), so any mismatch causes every validator processing that slot to panic simultaneously.

## Finding Description
Reward calculation happens once, at the first block of the new epoch, using a stake-delegation snapshot from the end of the previous epoch [4](#0-3) . Distribution begins `REWARD_CALCULATION_NUM_BLOCKS` (currently `1`) block later and can extend over many subsequent blocks, since `get_reward_distribution_num_blocks` computes the number of partitions/blocks needed to cover all stake accounts, up to 10% of the epoch's slots [5](#0-4) [6](#0-5) . Distribution for each block's partition is driven by `distribute_partitioned_epoch_rewards`, which walks `partition_index` across the block-height range [7](#0-6) .

During the window between calculation (block N) and a given account's scheduled distribution block (block N+k, k possibly large), the account owner is fully unprivileged and can submit ordinary Stake-program instructions (`Split`, `Withdraw`, `Merge`, `Redelegate`) against their own account. I searched for any mechanism gating vote/stake program transaction processing during the active reward interval (the historical Solana `is_in_reward_interval` pattern) and found no such check in `svm/account_loader.rs`, `svm/transaction_processor.rs`, or elsewhere in this codebase — there is no code that blocks ordinary transactions from mutating a stake account while its reward distribution is pending.

At distribution time, `build_updated_stake_reward` only special-cases the account being fully removed (`AccountNotFound`) [8](#0-7) . Any partial change to `delegation.stake` — e.g. a `Split` that moves lamports/stake to a new account, or a `Withdraw` of excess balance — is not accounted for. When `relax_post_exec_min_balance_check` is inactive, the non-adjusted branch computes `expected_delegation` from the now-live `stake.delegation.stake` plus the cached `stake_reward`, and asserts it equals the cached `new_stake.delegation.stake` computed at calculation time [3](#0-2) . If the live delegation differs from the calculation-time delegation, these two values diverge and the assertion panics. This propagates from `store_stake_accounts_in_partition` [9](#0-8)  to `distribute_epoch_rewards_in_partition`, both invoked unconditionally during ordinary block processing, so the panic is hit deterministically by every validator processing that slot.

The doc-comment's claim that "further state mutation prevents by stake-program restrictions" is not supported by any guard found in the codebase; the Stake program itself has no awareness of, or restriction tied to, an account's pending reward-distribution status.

## Impact Explanation
A triggered `assert_eq!` panic inside `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition` occurs during mandatory, deterministic block processing executed by every validator for the same slot, which is a consensus-halting event rather than an isolated node crash. This matches the allowed impact category of "consensus halt" via an unprivileged runtime/accounts code path. The exact corrupted/mismatched value is the stake account's `delegation.stake` field cached in `PartitionedStakeReward.inflation.stake` versus the live on-chain `delegation.stake` in `stakes_cache_accounts`.

## Likelihood Explanation
The reachability of this path depends entirely on the activation status of the `relax_post_exec_min_balance_check` feature; when active, `adjust_delegation_for_rent` is used instead of the strict assertion and the bug does not trigger [10](#0-9) . I was unable to determine from the indexed code whether this feature is active on Agave's live networks (mainnet-beta/testnet) — this remains an open question requiring cluster feature-gate history outside the scope of this codebase search. If the feature is inactive, the exploit requires no special privileges: any staker can submit a normal `Split` or `Withdraw` transaction at a chosen block height between the epoch-boundary calculation and their account's scheduled distribution partition, and no code found in this repository blocks or reconciles such a change.

## Recommendation
Do not assert hard equality between a delegation value cached at calculation time and the live on-chain delegation at distribution time. Always recompute/clamp the delegation from current on-chain state (as `adjust_delegation_for_rent` already does) regardless of the `relax_post_exec_min_balance_check` feature flag, and treat any legitimate reduction in delegated stake between calculation and distribution as a normal data condition (similar to the existing `AccountNotFound` handling) rather than an `assert_eq!`-enforced invariant.

## Proof of Concept
1. At an epoch boundary, `calculate_stake_rewards_and_commissions` computes a `PartitionedStakeReward` for stake account `S`, caching `new_stake.delegation.stake` based on `S`'s delegation snapshot at that instant.
2. `S`'s distribution is scheduled for a later block height per `get_reward_distribution_num_blocks`/`distribute_partitioned_epoch_rewards`'s partition scheduling.
3. Before that block height, the owner of `S` submits a normal `Split` or `Withdraw` instruction that changes `S`'s on-chain `delegation.stake`, with `relax_post_exec_min_balance_check` inactive.
4. When the scheduled block is processed, `build_updated_stake_reward` reads the changed `S` from `stakes_cache_accounts`, computes `expected_delegation` from the new state, compares it to the stale cached value, and the `assert_eq!` panics, crashing every validator processing that slot.

A reproducible unit test can construct a `Bank` with a stake account, call `calculate_stake_rewards_and_commissions` to obtain a `PartitionedStakeReward`, then mutate the stake account's on-chain delegation (simulating a `Split`/`Withdraw`) before invoking `build_updated_stake_reward` with `adjust_delegations_for_rent = false`, and observe the panic.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
