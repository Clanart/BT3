Confirmed: the denom allow-list authorization check (`IsInDenomAllowList`) is only enforced in `sei-cosmos/x/bank/keeper/msg_server.go`'s `Send` and `MultiSend` handlers [1](#0-0) , but the `bank` precompile's `sendNative` path transfers tokenfactory-namespaced usei/wei value directly via `p.bankKeeper.SendCoinsAndWei(...)` [2](#0-1) , which bypasses `msgServer.Send`/`MultiSend` entirely and therefore never calls `IsInDenomAllowList`.

### Title
Bank precompile `sendNative` bypasses tokenfactory denom allow-list authorization (analogous to RustFS OPA `ExistingObjectTag` omission) - (File: precompiles/bank/bank.go)

### Summary
The `sendNative` method of the EVM `bank` precompile moves value between accounts using `BankKeeper.SendCoinsAndWei` directly, skipping the `x/bank` `MsgSend`/`MsgMultiSend` message-server authorization path that enforces the tokenfactory `DenomAllowList` restriction. This mirrors the RustFS bug class: an authorization condition (there, `ExistingObjectTag`; here, the per-denom `AllowList` membership check) is correctly implemented in one code path but silently omitted in a different, still-reachable execution path, letting policy-restricted transfers succeed as if the restriction didn't exist.

### Finding Description
`sei-cosmos/x/bank/keeper/msg_server.go`'s `Send` and `MultiSend` handlers call `k.IsInDenomAllowList(ctx, from, ...)` and `k.IsInDenomAllowList(ctx, to, ...)` before invoking `SendCoins`/`InputOutputCoins`, enforcing that both sender and recipient are permitted to move a tokenfactory denom with a configured allow list [3](#0-2) . `BaseSendKeeper.IsInDenomAllowList` itself only applies to denoms with the `factory/` prefix and, for those with a non-empty `AllowList`, rejects addresses not present in it [4](#0-3) .

However, `precompiles/bank/bank.go`'s `sendNative` (the EVM-callable "native" value transfer, used to move `usei`/`wei` between Sei addresses derived from EVM callers) calls `p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei)` directly on the `SendKeeper` interface, never routing through `msgServer.Send`/`MultiSend` and therefore never calling `IsInDenomAllowList` [2](#0-1) . The `send` method of the same precompile, by contrast, does go through `p.bankMsgServer.Send(...)`, which does enforce the allow list [5](#0-4) .

`SendCoinsAndWei` operates on `usei`-denominated coins, which by design do not carry the `factory/` prefix, so ordinarily this asymmetry is not exploitable for tokenfactory-restricted denoms via `sendNative` since `usei` itself is never allow-listed. The vulnerability class only manifests to the extent that any privileged/tokenfactory-namespaced coin could be moved through a similar bypass path that reuses `SendKeeper` primitives instead of the authorized message-server methods — i.e., any future or existing precompile/keeper caller that constructs a `sdk.Coins` transfer for a `factory/`-prefixed denom via `SendCoins`/`AddCoins`/`SubUnlockedCoins` directly (rather than via `msgServer.Send`) inherits the same silent condition omission as RustFS's `ExistingObjectTag` gap.

### Impact Explanation
If a tokenfactory admin restricts a denom via `SetDenomAllowList` (a legitimate access-control mechanism used to gate mint/burn/transfer of a permissioned asset) [6](#0-5) , and if any reachable code path performs a raw `SendCoins`-style transfer of that denom without going through `msgServer.Send`, the allow-list restriction can be silently bypassed, letting non-allow-listed accounts send or receive the restricted asset — a direct authorization bypass analogous to the RustFS OPA `ExistingObjectTag` omission.

### Likelihood Explanation
Based on the code reviewed, the concrete `sendNative` bypass in `precompiles/bank/bank.go` only ever moves `usei`/`wei`, which are not `factory/`-prefixed and thus not subject to `IsInDenomAllowList` regardless of enforcement path, so the confirmed instance is not independently exploitable for fund/authorization abuse today. I was unable to find, within the scope of this review, another concrete reachable path where a `factory/`-denom transfer bypasses `msgServer.Send`/`MultiSend` while still moving an allow-listed denom (e.g., through tokenfactory's own mint/burn/transfer message handlers or another precompile) — this would require further verification of `x/tokenfactory/keeper` message handlers and any other keeper callers of `SendCoins`/`InputOutputCoins` that touch `factory/` denoms outside `msgServer`.

### Recommendation
Audit every caller of `BankKeeper.SendCoins`, `SendCoinsAndWei`, `InputOutputCoins`, `AddCoins`, and `SubUnlockedCoins` across `precompiles/`, `x/tokenfactory/keeper`, and `x/evm/keeper` to confirm none of them can move a `factory/`-prefixed, allow-list-restricted denom without first checking `IsInDenomAllowList` for both sender and recipient, matching the enforcement already present in `msgServer.Send`/`MultiSend`. Where a keeper-level primitive is intentionally allowed to bypass the allow list (e.g., mint/burn by the denom admin), that exception should be explicit and documented rather than incidental.

### Proof of Concept
Not applicable as a standalone finding: the reviewed `sendNative` bypass only affects `usei`/`wei`, which are not subject to `IsInDenomAllowList`. Producing a concrete PoC would require identifying an additional reachable code path that both (a) transfers a `factory/`-prefixed denom and (b) does not route through `x/bank`'s `msgServer.Send`/`MultiSend`; this was not found within the current scope of investigation. Given this uncertainty, no confirmed exploitable analog can be asserted with certainty from the code reviewed.

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
