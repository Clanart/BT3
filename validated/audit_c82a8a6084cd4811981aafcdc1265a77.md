## Title
Check-effects-interactions violation in vault `deposit`/`redeem` enables state-staleness exploitation if the underlying SIP-010 token has a transfer callback - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, and identically in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`)

### Summary
Every zAsset vault's `deposit` and `redeem` functions perform the external token transfer (`receive-underlying` / `send-underlying`) before committing the corresponding accounting-state update (`var-set assets ...`). This is the same check-effects-interactions violation flagged in the referenced Hermez report: if the underlying token (`usdc`, `sbtc`, `ststx`, `ststxbtc`, `wstx`, `usdh`) has any transfer-hook/callback behavior, a reentrant call can read the stale `assets` accounting variable before it reflects the in-flight transfer, producing an incorrect share-price / redemption calculation that a caller can exploit for profit at the expense of vault solvency.

### Finding Description
In `deposit`, shares to mint (`inkind`) are computed from `convert-to-shares-preview`, which is `total-assets-preview()` divided by `total-supply-preview()` — this is effectively the exchange-rate ("price") of the zAsset share. The accounting var `assets` is only updated at the very end of the function, after the external call: [1](#0-0) 

The external call `receive-underlying` invokes `contract-call? ... transfer` on the configured underlying token contract: [2](#0-1) 

Symmetrically, `redeem` burns shares and sends underlying out via `send-underlying` (external call) before decrementing the `assets` accounting variable: [3](#0-2) 

Because the accounting variable `assets` (used by `total-assets-preview`, and therefore by `convert-to-shares-preview` / `convert-to-assets-preview`, which is the pricing function for the zAsset/underlying exchange rate) is not updated until after the external call returns, a reentrant call made from within that external call would compute share price against a stale `current-assets` value that doesn't yet reflect the in-flight deposit/withdrawal. This is structurally identical to the Hermez `addToken` finding: an external call precedes the state commit, and if the external contract has any callback path back into the vault, the stale intermediate state can be read and acted upon.

The only reentrancy guard present (`in-flashloan`) is scoped exclusively to the flashloan feature and does not protect `deposit`/`redeem` against reentrancy through the underlying token's transfer call: [4](#0-3) 

### Impact Explanation
If the underlying token used by any vault (e.g. `usdh-token-v1`, `ststx-token`, `sbtc-token`) is ever upgraded or has any post-transfer notification/callback path, an attacker could re-enter `deposit` or `redeem` mid-call and mint/redeem shares against a stale `assets`/exchange-rate snapshot, minting excess zAsset shares for less underlying than backed, or extracting more underlying than the vault's true backing supports. Since the zAsset share price is also what the oracle system consumes via the `CALLCODE-ZUSDC`/`CALLCODE-ZUSDH`/etc. transformations for collateral/health valuation in `market.clar`, an exchange-rate manipulated this way directly produces a wrong valuation for that zAsset used in liquidation/health checks, and drains real underlying backing — landing on protocol insolvency (Critical impact class).

### Likelihood Explanation
Likelihood is conditioned entirely on whether the specific underlying token contract used in production (`sbtc-token`, `ststx-token`, `usdh-token-v1`, `usdcx`, `wstx`, `ststxbtc-token-v2`) contains any transfer-triggered callback to the sender or recipient — none of these are verifiable from this repository since they are external contracts. Absent such a callback, standard SIP-010 `transfer` calls do not hand control back to the caller, and the vulnerability is not exploitable today. This mirrors the "High difficulty, contingent on token behavior" classification in the source report.

### Recommendation
- Apply check-effects-interactions ordering in all vault `deposit`/`redeem` functions (and any other function that performs `receive-underlying`/`send-underlying`): update `(var-set assets ...)` before making the external token transfer call.
- Add an explicit reentrancy guard (similar to `in-flashloan`) covering `deposit`/`redeem`/`accrue`, not just the flashloan path.
- Audit whether any of the currently integrated underlying tokens (`usdh-token-v1`, `ststx-token`, `ststxbtc-token-v2`, `sbtc-token`, `usdcx`) implement any transfer hooks/callbacks, and forbid onboarding future underlying assets that do.

### Proof of Concept
1. Assume the underlying token for a vault (e.g. `usdh-token-v1`) implements a transfer hook that calls back into `msg.sender` (or `recipient`) during `transfer`.
2. Attacker calls `deposit(amount, min-out, attackerContract)` on `v0-vault-usdh`. `current-assets`/`inkind` are snapshotted from the stale `assets` var.
3. `receive-underlying` executes `contract-call? .usdh transfer amount account current-contract none`, pulling `amount` tokens into the vault's real balance — but `(var-set assets ...)` has not yet executed.
4. The token's callback re-enters `deposit` again from `attackerContract`, computing a second `inkind` share amount using the still-stale `assets` var (which does not yet reflect the first deposit), producing a favorable/incorrect share-to-asset ratio.
5. Both calls return successfully, minting shares at an exchange rate that does not correctly reflect the vault's actual backing, diluting other depositors and/or allowing later `redeem` to be exploited symmetrically to extract more underlying than backed.

(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      (account contract-caller)
      (CAP-SUPPLY (var-get cap-supply))
      (current-assets (var-get assets))
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))

    (print {
      action: "deposit",
      caller: contract-caller,
      data: {
        depositor: account,
        recipient: recipient,
        amount: amount,
        shares-minted: inkind,
        assets: (+ current-assets amount)
      }
    })

    (ok inkind)))

(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  (let (
    (states (var-get pause-states))
    (u (try! (accrue)))
    (account contract-caller)
    (current-assets (var-get assets))
    (balance (get-balance-internal account))
    (balance-check (asserts! (>= balance amount) ERR-INSUFFICIENT-BALANCE))
    (available-assets (get-available-assets))
    (inkind (convert-to-assets-preview amount)))

  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
  (asserts! (>= available-assets inkind) ERR-INSUFFICIENT-LIQUIDITY)

  (try! (ft-burn? zft amount account))
  (try! (send-underlying inkind recipient))
  (var-set assets (- current-assets inkind))

  (print {
    action: "redeem",
    caller: contract-caller,
    data: {
      redeemer: account,
      recipient: recipient,
      shares-burned: amount,
      amount-received: inkind,
      assets: (- current-assets inkind)
    }
  })

  (ok inkind)))
