### Title
Unrecovered slice-bounds panic in the `console.log` precompile’s string/bytes decoder can crash the node on a crafted call - (File: blockchain/vm/contracts.go)

### Summary
Kaia registers a Hardhat-style `console.log` precompiled contract (`consoleLog`) that any transaction, internal call, or `eth_call` can invoke by sending calldata to its fixed address. [1](#0-0)  Its argument decoder (`consoleLog.decode`) computes offsets for dynamic `string`/`bytes` parameters directly from attacker-controlled 32-byte words converted with `big.Int.Int64()` and then slices the raw input using those offsets without validating that the resulting indices are non-negative or internally consistent. [2](#0-1) [3](#0-2) 

### Finding Description
For `StringTy`/`BytesTy` parameters, `start` is derived from `big.NewInt(0).SetBytes(params[pos:pos+registerSize]).Int64()`. [4](#0-3)  Per the Go standard library, `big.Int.Int64()` is documented as returning an *undefined* result when the underlying value cannot be represented in an `int64` — it does not error or clamp. An attacker who supplies a 32-byte word whose big-endian value is larger than `2^63` can make `start` come back as a negative `int` (or another out-of-range value). The subsequent bounds check `len(params) < start+registerSize` (and the analogous check for `size`) is written assuming `start`/`size` are non-negative, so a negative `start` trivially satisfies `len(params) < start+registerSize` (a small/negative number), skipping the intended guard. The following slice expression, e.g. `params[start : start+registerSize]`, then executes with a negative lower bound, which is a Go runtime panic (`slice bounds out of range`), not a returned `error`.

This mirrors the CVE-2019-14907 bug class: untrusted, attacker-supplied data reaches a code path that performs an unchecked conversion/interpretation of that data and, on malformed input, crashes rather than gracefully failing — in Samba's case a bad character conversion crashing a long-lived RPC process; here, an out-of-range integer conversion crashing the node's transaction/EVM-execution path. `consoleLog.Run` calls `toLogString`, which calls `decode`, and none of these functions recover from panics; only errors are propagated as `error` return values, so a panic here escapes the intended error-handling path. [5](#0-4) 

### Impact Explanation
If this panic is not caught by a `recover()` somewhere higher in the EVM call stack (e.g., in the interpreter's opcode-execution loop), it will propagate up through block/transaction processing and crash the node process handling that transaction — a straightforward unauthenticated denial-of-service reachable by any account that can submit a transaction or call targeting the `console.log` precompile address with crafted calldata. Because this is EVM execution triggered by ordinary transactions, an attacker does not need any privileged role — any unprivileged transaction sender or public-RPC `eth_call` caller can trigger it.

I was not able to confirm from the code I retrieved whether Kaia's EVM interpreter/precompile-invocation path wraps precompiled contract execution in a `recover()` (this is common in some geth-derived codebases at higher layers such as `eth_call`/`StateTransition`, but block/transaction processing loops in some EVM forks do not universally recover from precompile panics). This is the key open uncertainty: if recovery exists at the call site, the practical effect is limited to a failed/reverted call for that one transaction (low impact); if no recovery exists in the block-processing path, a single crafted transaction included in a block could crash validating/following nodes, which is a much more severe, node-crashing consensus-adjacent bug. I could not verify this within the current investigation and it should be checked directly against `blockchain/vm/evm.go`'s precompile dispatch and the top-level block-processing caller.

### Likelihood Explanation
Triggering the panic requires only constructing calldata for the `console.log` precompile with a `string`/`bytes` parameter whose length-or-offset word decodes to a value that overflows `int64`/produces a negative `start`. This requires no special privileges, no specific network conditions, and no cooperation from other parties — it is a single crafted call, matching the "single submitted transaction/RPC call" reachability bar.

### Recommendation
In `consoleLog.decode`, validate `start` and `size` explicitly before use:
- Reject if the decoded big.Int does not fit safely in a reasonable `int` range (e.g., compare against `params` length using `big.Int` comparisons, not `Int64()`).
- Reject if `start < 0` or `size < 0` after conversion.
- Perform additions with overflow checks (or keep computations in `big.Int`/`uint64` domain and bound-check against `len(params)` before ever converting to a Go slice index).
Additionally, confirm/add a `recover()` boundary around precompiled-contract execution in the EVM dispatch path so that any future decoder bug in a precompile cannot crash the node processing a block.

### Proof of Concept
1. Craft calldata for the `console.log` precompile: 4-byte selector matching a signature in `common.ConsoleLogSignatures` that includes a `string` parameter, e.g. `log(string)`. [6](#0-5) 
2. In the parameter word for the string, place a 32-byte big-endian value greater than `2^63` (e.g., `0xFFFFFFFFFFFFFFFFFFFF...`) as the "offset" word so `big.NewInt(0).SetBytes(...).Int64()` returns an undefined/negative value. [4](#0-3) 
3. Send this calldata to the `console.log` precompile address via a normal transaction (or `eth_call`), causing `consoleLog.decode` to slice `params` with the resulting negative `start`, triggering a Go runtime `slice bounds out of range` panic during EVM execution. [7](#0-6)

// Hardhat console.log accepts format string, however we don't support it.
// Instead, we just join all the parameters with a space.
func (c *consoleLog) toLogString(input []byte) (string, error) {
	if len(input) < 4 {
		return "", errors.New("input too short")
	}
	selector := binary.BigEndian.Uint32(input[:4])
	params := input[4:]

	types, ok := common.ConsoleLogSignatures[selector]
	if !ok {
		return "", errors.New("unknown selector")
	}
	decoded, err := c.decode(params, types)
	if err != nil {
		return "", err
	}

	return strings.Join(decoded, " "), nil
}
