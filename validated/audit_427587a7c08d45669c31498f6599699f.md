### Title
Spoofed `WWW-Authenticate` realm from a malicious/MITM git remote causes GitHub Desktop to initiate Enterprise sign-in against an attacker-controlled endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The bug-class from the external report is "an attacker-controlled input grows/feeds an internal decision structure with no validation, causing the app to take an unintended, unrecoverable action." The Desktop analog is `getEndpointKind()` in the credential-helper trampoline: it classifies an unknown git remote as a trusted **GitHub Enterprise** endpoint purely by inspecting the `wwwauth[]` credential field that Git forwards from the **server's own `WWW-Authenticate` response header** — a value fully controlled by whatever host (or MITM proxy) Desktop is talking to.

### Finding Description
When Git needs credentials for an HTTPS remote, it invokes Desktop's credential helper via the trampoline, passing along any `WWW-Authenticate` headers it received from the server as `wwwauth[]` fields [1](#0-0) . `getEndpointKind()` uses this attacker-supplied header as a "happy path" instead of an authenticated network check to decide whether the remote is a GitHub host:

```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } ...
``` [2](#0-1) 

Because the `Realm` string in a `WWW-Authenticate` header is entirely chosen by the remote server, any git server — a malicious remote the user adds, a compromised/forked repository's push URL, or a MITM proxy sitting between Desktop and a legitimate-looking HTTPS remote — can return `WWW-Authenticate: Basic realm="GitHub"` and be classified as `'enterprise'` with no real verification (`isGitHubHost()` is only used as a fallback and is bypassed once the header check matches) [3](#0-2) .

Once classified as `'enterprise'`, `getCredential()` checks whether an existing account matches the endpoint; since it does not for an attacker's arbitrary domain, it calls `ui.promptForGitHubSignIn(endpoint)` [4](#0-3) . That function derives `origin` directly from the attacker-controlled `endpoint` string and, since `hostname !== 'github.com'`, calls `beginEnterpriseSignIn(cb)` followed by `setSignInEndpoint(origin)`, launching Desktop's normal "Sign in to GitHub Enterprise" flow pointed at the attacker's domain:

```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
``` [5](#0-4) 

The user is shown Desktop's normal, trusted-looking GitHub sign-in dialog, but it is silently pre-configured to authenticate against the attacker's server instead of a real GitHub Enterprise instance, because the *only* signal that drove this decision was a header the attacker fully controls.

### Impact Explanation
This breaks the invariant that Desktop only treats a host as a legitimate GitHub/Enterprise endpoint after some form of verification (`isGitHubHost()`, an existing stored `Account`, or a truly trusted URL match). Instead, a single spoofed HTTP response header lets an attacker-controlled remote force Desktop's own "Sign in to GitHub Enterprise" flow to target the attacker's origin. This falls squarely into the "unauthorized OAuth or account binding / credential exfiltration" impact category: the user, believing they are completing a routine GitHub Enterprise authentication prompted by Desktop, can end up submitting credentials/PAT (for the generic/basic-auth Enterprise flow) or completing an OAuth/device-code handshake against the attacker's endpoint rather than the intended host. Existing guards (`isGitHubHost` fallback, `findGitHubTrampolineAccount` origin matching) do not prevent this because they are entirely skipped once the spoofed `realm="GitHub"` header is present — the header-based check runs first and returns early.

### Likelihood Explanation
Likelihood is moderate-to-high for the described attacker model: the only requirement is that the user adds or fetches from an attacker-controlled/compromised HTTPS remote, or that a MITM/proxy on the network path can shape the `WWW-Authenticate` response for that remote's authentication challenge — both are within the allowed "attacker controls a git remote/proxy response" scope, and require no local access, admin rights, or pre-existing malware. The user does not need to take any unnatural step beyond normal Desktop usage (fetch/push/clone triggering a credential prompt).

### Recommendation
Do not use the server-supplied `wwwauth[]` realm string as a trust signal for classifying an endpoint as GitHub/Enterprise. At minimum:
- Require a genuine `isGitHubHost()` check (or matching against an already-configured/stored Enterprise account) before treating any unknown endpoint as `'enterprise'`.
- Treat the `wwwauth[]` realm as, at most, a hint to *skip* an extra network round trip when an account for that endpoint is already known — never as sufficient evidence on its own to initiate a sign-in flow against a previously-unknown host.
- Clearly surface the actual target hostname/origin in the sign-in dialog so users can detect endpoint spoofing before entering credentials.

### Proof of Concept
1. Attacker hosts a git server (or a MITM proxy in front of any HTTPS git URL) at `https://evil.example.com/`.
2. Victim adds this URL as a remote in a repository open in GitHub Desktop (e.g., as a second remote, or clones/fetches from a repository link received from the attacker) and performs a fetch/push.
3. Git issues an authenticated request; the attacker's server responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
4. Git invokes Desktop's credential helper trampoline with `wwwauth[]=Basic realm="GitHub"` in the `fill` request stdin.
5. `getEndpointKind()` matches `realm="GitHub"` and returns `'enterprise'` without any real host verification [6](#0-5) .
6. Since no account exists for `evil.example.com`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com/...')` [7](#0-6) .
7. `promptForGitHubSignIn` opens Desktop's normal "Sign in" dialog pre-bound to `origin = https://evil.example.com`, calling `beginEnterpriseSignIn` + `setSignInEndpoint(origin)` [8](#0-7) .
8. The victim, expecting a legitimate Enterprise/GitHub authentication step (as this is a normal, expected Desktop behavior when connecting to a new host), proceeds with the flow, exposing credentials/tokens to the attacker's endpoint instead of a real GitHub host.
