### Title
Dust-deposit share hijack of queued rewards in `BaseRewardPool._provisionReward` when `totalStaked()==0` - ([File: rewards/BaseRewardPool.sol])

### Summary
When `totalStaked()==0`, `_provisionReward` accumulates incoming rewards into `rewardInfo.queuedRewards` instead of distributing them via `rewardPerTokenStored`, to avoid a division by zero. If an attacker deposits a dust amount (e.g. 1 wei) of the staking/receipt token right after such a zero-stake period and before the next `queueNewRewards`/`donateRewards` call, the entire accumulated `queuedRewards` balance plus the new reward gets folded into `rewardPerTokenStored` and divided by the attacker's dust `totalStaked()`, letting the attacker claim nearly all of it. This is a share-inflation/first-depositor style bug that results in theft of other users' historical reward accrual.

### Finding Description
In `_provisionReward` [1](#0-0) , when `this.totalStaked() == 0`, the reward is simply added to `rewardInfo.queuedRewards` with no owner attribution. On the next call to `_provisionReward` where `totalStaked() > 0`, the code does:

```solidity
if (rewardInfo.queuedRewards > 0) {
    _amountReward += rewardInfo.queuedRewards;
    rewardInfo.queuedRewards = 0;
}
rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / this.totalStaked();
```

`rewardPerTokenStored` is a single global accumulator, and reward entitlement for any account is computed purely from the account's current `balanceOf(_account)` relative to the *current* `rewardPerTokenStored` value versus what that account already had "paid" (`userRewardPerTokenPaid`) [2](#0-1) . There is no per-epoch/per-block snapshotting of who was staked when the queued rewards accrued — the whole reward amount (old queued rewards + new reward) is stamped into `rewardPerTokenStored` at the moment `totalStaked()` becomes non-zero again, and is attributed based on the staked balance that exists at that instant.

Attack flow:
1. All legitimate stakers withdraw fully, driving `totalStaked() == 0` for a given `stakingToken`/rewarder.
2. One or more `queueNewRewards`/`donateRewards` calls occur while `totalStaked()==0` (this can be routine automated harvesting via `WombatStaking`/pool helpers, or any manager operation — no malicious intent required), causing `rewardInfo.queuedRewards` to grow.
3. Attacker deposits a dust amount (as little as the smallest unit that results in `balanceOf() >= 1`) through the normal deposit path (`WombatPoolHelperV2._deposit`/`_stake` → `MasterMagpie.depositFor` [3](#0-2) ), becoming effectively the sole staker (`totalStaked()` now equals the attacker's dust balance).
4. The next `_provisionReward` call (triggered by any manager/harvest, not attacker-controlled but attacker-timed) folds `queuedRewards` into `rewardPerTokenStored`, dividing by the attacker's tiny `totalStaked()`, producing a massive `rewardPerTokenStored` increase.
5. Attacker calls `getReward`/withdraws and claims via `MasterMagpie.multiclaim` → `BaseRewardPool.getReward`, receiving nearly the entire queued reward pool despite having contributed negligible stake and negligible time. `earned()` and `getReward()` have no protections against this (no minimum stake time, no per-depositor reward-eligibility window) [4](#0-3) .

Existing modifiers (`onlyManager`, `onlyMasterMagpie`, `updateReward`) do not prevent this because they only gate *who* can call `queueNewRewards`/`getReward`, not *when* relative to `totalStaked()` state, and `updateReward`/`_updateFor` simply reads the (now-inflated) `rewardPerToken` value [5](#0-4) . This same pattern is duplicated in `BaseRewardPoolV2.sol` and `mWOMSVBaseRewarder.sol`.

### Impact Explanation
This constitutes theft of unclaimed yield belonging to previous stakers: rewards that historically accrued as "queued" (owed to whoever was staked at donation time, or intended to be fairly distributed to future stakers proportional to their stake-time) are instead captured almost entirely by an attacker holding a dust position for a brief window. This matches the Immunefi impact class "theft of unclaimed yield" / direct theft of user/protocol funds, and violates conservation of the reward accounting invariant (sum of claimable rewards should not exceed rewards actually earned proportionally to stake and duration).

### Likelihood Explanation
Preconditions: (1) `totalStaked()` for a given staking token must reach zero — realistic during low-TVL periods, pool migrations, or when a pool is being sunset, or simply because all current stakers coincide in withdrawing; (2) a `queueNewRewards`/`donateRewards`/automated harvest call must occur while stake is zero, which is a normal, non-malicious operation flow, not adversarial; (3) attacker only needs capital for a dust deposit (near-zero) and can front-run/back-run the next reward-queue transaction, which is straightforward via mempool monitoring. No privileged role is required by the attacker. Repeatability: this can occur every time a pool's `totalStaked()` transiently hits zero, making it plausible especially in newer/low-volume pools such as `wombat/ArbWomUp2.sol`-linked rewarders. Overall feasibility is moderate-to-high in low-liquidity pools but requires the zero-stake condition to actually occur, which is outside attacker control (making it opportunistic/timing-dependent rather than attacker-triggerable on demand).

### Recommendation
- When `totalStaked()==0`, either revert the `queueNewRewards`/`donateRewards` call (forcing callers to hold/retry rewards until there is real stake) instead of silently queuing, or better, attribute queued rewards fairly once staking resumes by requiring a minimum elapsed time/stake before a depositor becomes eligible for pre-existing queued rewards.
- Do not merge `queuedRewards` into `rewardPerTokenStored` immediately when a dust deposit occurs; instead, gate queued-reward distribution behind a minimum `totalStaked()` threshold or vest it over time (e.g., stream the queued rewards over a duration rather than releasing all at once against instantaneous share).
- Consider tracking a minimum stake duration/checkpoint before a user's balance is eligible to receive rewards that were queued prior to their deposit.

### Proof of Concept
Foundry test plan (`BaseRewardPool` unit test):
1. Deploy `MasterMagpie`, `BaseRewardPool` (with a mock staking token and mock reward token), register a `rewardManager`.
2. `userA` deposits `100e18` staking tokens via `MasterMagpie.deposit`.
3. `manager` calls `queueNewRewards(1000e18, rewardToken)` — verify `rewardPerTokenStored` increases and `userA.earned == ~1000e18`.
4. `userA` calls `MasterMagpie.withdraw(100e18)` fully, bringing `totalStaked() == 0`.
5. `manager` calls `queueNewRewards(500e18, rewardToken)` again — assert `rewards[rewardToken].queuedRewards == 500e18` and `rewardPerTokenStored` unchanged (division-by-zero branch taken).
6. `attacker` deposits `1 wei` staking token via `MasterMagpie.deposit` — `totalStaked() == 1`.
7. `manager` calls `queueNewRewards(1e18, rewardToken)` (or `donateRewards`) — this triggers the non-zero branch, folding `queuedRewards` (500e18) + new (1e18) into `rewardPerTokenStored`, dividing by `totalStaked()==1`.
8. `attacker` calls `MasterMagpie.multiclaim` (routes to `BaseRewardPool.getReward`) and asserts `IERC20(rewardToken).balanceOf(attacker) ~= 501e18`, i.e., attacker claimed nearly the entire queued reward despite holding only 1 wei of stake for a single block, proving disproportionate reward theft relative to `userA`'s prior 100e18 stake.

        IERC20(_rewardToken).safeTransferFrom(

            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;

            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
