### Title
Incorrect Inequality in Bridge Circuit Work Comparison Allows Equal-Work Fork to Pass — (`circuits-lib/src/bridge_circuit/mod.rs`)

### Summary

The bridge circuit uses a strict `<` comparison to check the operator's total work against the watchtower's maximum total work. The protocol specification explicitly requires the operator's work to be **strictly greater than** the watchtower's work, but the code allows the equal case to pass silently.

### Finding Description

In `bridge_circuit()`, after computing `max_total_work` from all valid watchtower challenges, the circuit checks:

```rust
// If total work is less than the max total work of watchtowers, panic
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [1](#0-0) 

When `total_work == max_total_work`, the condition is `false` and the circuit does **not** panic — it proceeds to accept the operator's proof as valid.

The protocol's own documentation and module docstring state the invariant unambiguously:

- Module docstring: *"It ensures that an operator's claimed Bitcoin chain state is valid and that it has **more** cumulative proof-of-work than any challenging watchtower."*
- Step 4 in the docstring: *"**Work Comparison:** Asserts that the operator's claimed work is **greater than** the maximum work submitted by any valid watchtower."*
- `docs/bridge-circuit.md`: *"Asserts that the Operator's `total_work` from their HCP is **greater than** the `max_total_work` from the Watchtowers."* and *"The Operator must provide a HCP with **more** work compared to the WOP with maximum Work."* [2](#0-1) [3](#0-2) 

Both `total_work` values are 16-byte (128-bit) truncated representations of the full 256-bit chain work:

```rust
let total_work: TotalWork = input.hcp.chain_state.total_work[16..32]
    .try_into()
    .expect("Cannot fail");
``` [4](#0-3) 

The `TotalWork` struct derives `PartialOrd`/`Ord` over the raw byte array, so the comparison is lexicographic over 16 bytes. [5](#0-4) 

### Impact Explanation

Bitcoin's canonical chain is defined as the chain with the **most** accumulated proof-of-work. Two chains with **equal** total work are ambiguous — neither is definitively canonical. If an operator's HCP covers a fork whose 128-bit truncated total work equals the highest valid watchtower's work, the circuit accepts the operator's proof. This allows the operator to claim reimbursement for a payout made on a non-canonical (or ambiguous) fork, which constitutes an invalid withdrawal reimbursement and a loss of bridged BTC from the bridge's collateral.

### Likelihood Explanation

Two independent Bitcoin chains accumulating exactly equal 128-bit truncated total work is extremely unlikely on mainnet under normal conditions. However:

1. The truncation to 128 bits (from 256 bits) meaningfully increases collision probability compared to the full work value.
2. In regtest or controlled test environments, this condition can be engineered deliberately.
3. A sophisticated operator could attempt to mine a competing fork to reach exact parity with the canonical chain's truncated work value.

The likelihood is low but non-zero, and the consequence is a broken bridge safety invariant.

### Recommendation

Change the comparison from strict `<` to `<=` so that equal work is also rejected:

```rust
// Operator must have STRICTLY MORE work than the best watchtower
if total_work <= max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
```

This aligns the code with the documented invariant that the operator's chain must have **strictly greater** cumulative work than any challenging watchtower.

### Proof of Concept

1. A watchtower submits a valid Work-Only Proof (WOP) with `total_work = W`.
2. An operator constructs an HCP for a fork whose 128-bit truncated total work is also exactly `W` (equal, not greater).
3. The bridge circuit computes `max_total_work = TotalWork(W)` and `total_work = TotalWork(W)`.
4. The check `total_work < max_total_work` evaluates to `W < W` → `false` → no panic.
5. The circuit proceeds to verify the SPV, LCP, and storage proofs against the operator's fork.
6. If those pass, the circuit commits a valid journal hash, allowing the operator to post valid Assert transactions and escape the disprove window — claiming reimbursement for a payout on an ambiguous or non-canonical chain.
