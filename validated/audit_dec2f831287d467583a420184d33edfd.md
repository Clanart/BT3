## Title
Unprivileged `donateRewards` lets a dust staker snipe queued rewards meant for future stakers via totalStaked-based rounding - (File: rewards/BaseRewardPool.sol / rewards/BaseRewardPoolV2.sol)

### Summary
`donateRewards` is callable by any address holding the registered reward token, with no minimum-stake or access-control check beyond `isRewardToken`, and it flows into the same `_provisionReward` reward-index update used by the privileged `queueNewRewards`. Because the reward-per-token increment is `_amountReward * 10**decimals / totalStaked()`, an attacker who is the sole staker with a dust balance (e.g. 1 wei) can call `donateRewards` at a self-chosen moment to convert `totalStaked()==1` into an outsized `rewardPerTokenStored` bump, capturing not just their own donation back but also any pre-existing `queuedRewards` (real rewards that accumulated while `totalStaked()==0`) that were meant to be shared fairly with future depositors.

### Finding Description
`_provisionReward` in `rewards/BaseRewardPool.sol` computes: [1](#0-0) 

When `totalStaked()==0`, incoming reward amounts (from a manager's `queueNewRewards` call, e.g. an automated harvester funding the pool before any user has deposited, or after all stakers have withdrawn) accumulate in `rewardInfo.queuedRewards` rather than being distributed, since there is no share denominator. The first time `_provisionReward` runs with `totalStaked() > 0`, it folds `queuedRewards` into `_amountReward` and divides the whole sum by the *current* `totalStaked()`.

`donateRewards` is unrestricted apart from the token being registered: [2](#0-1)  and the equivalent in V2: [3](#0-2) . Unlike `queueNewRewards`, which is `onlyManager`, this "flush trigger" is public.

An unprivileged attacker who is the sole (dust) staker (`balanceOf(attacker)==1`, since `totalStaked()` and `balanceOf` both derive from `MasterMagpie`'s tracked staking-token balances: [4](#0-3) ) can call `donateRewards` themselves at the exact moment they are the only staker, instead of waiting for the manager's next `queueNewRewards` call. This lets them deterministically capture the entire `queuedRewards` bucket, because `rewardPerTokenStored` is bumped by `(donation + queuedRewards) * 10**decimals / 1`, and the attacker's own `earned()` is then `1 * delta / 10**decimals == donation + queuedRewards`, redeemable via `getReward` (reachable through `MasterMagpie.multiclaim` → `_claimBaseRewarder` → `rewarder.getReward`): [5](#0-4) .

Existing checks do not stop this: `onlyManager` only gates `queueNewRewards`, not `donateRewards`; `updateReward`/`updateFor` correctly snapshot new depositors' `userRewardPerTokenPaid` at deposit time so a later legitimate staker isn't retroactively diluted for the attacker's own donation, but they do nothing to protect the `queuedRewards` bucket, which is drained in a single flush indexed only by whoever happens to hold the dust stake at trigger time.

### Impact Explanation
This is a direct theft of funds that would otherwise be distributed fairly to legitimate stakers of that pool: any real reward tokens that accumulated in `queuedRewards` while `totalStaked()==0` (e.g., a newly-added pool that received an initial reward top-up before anyone deposited, or a pool whose stakers all withdrew) can be entirely captured by an attacker who deposits a trivial dust amount and self-triggers `donateRewards`, netting them `queuedRewards` for the cost of only gas and a negligible donation. This falls under "theft or permanent freezing of unclaimed yield" / "direct theft of user funds."

### Likelihood Explanation
Requires: (1) the pool's `totalStaked()==0` at some point while a `queueNewRewards` call occurs (plausible for newly-created pools, or briefly during a full-withdrawal window on lower-TVL pools), and (2) the attacker being the first/sole depositor afterward. Capital required is minimal (1 wei of staking token + gas + the ability to hold the registered reward token for a nominal donation). The attack is fully repeatable across any pool that experiences a zero-`totalStaked()` interval with pending `queuedRewards`, and the attacker fully controls timing since `donateRewards` has no access restriction.

### Recommendation
Restrict `donateRewards` (or at least the flush of `queuedRewards`) to `onlyManager`, or require a minimum meaningful `totalStaked()` threshold before flushing `queuedRewards`, or distribute `queuedRewards` pro-rata based on stake history rather than instantaneously by whoever holds the position when the flush executes. Alternatively, decouple queued-rewards flushing from the caller-controlled donation amount so an attacker cannot choose the exact block at which the flush occurs while holding a dust position.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie` + `BaseRewardPool` for a staking token/reward token pair; register `rewardToken` via `queueNewRewards` while `totalStaked()==0` with a "real" amount `Q` from a manager (simulating protocol yield queued before any staker exists) — assert `rewards[rewardToken].queuedRewards == Q`.
2. Attacker calls `MasterMagpie.deposit(stakingToken, 1)` (1 wei), becoming the sole staker.
3. Attacker calls `rewarder.donateRewards(d, rewardToken)` directly (d small, e.g. 1), with `isRewardToken[rewardToken]==true` already satisfied.
4. Assert `rewardPerTokenStored` jumped by `(d+Q)*10**decimals`.
5. Attacker calls `MasterMagpie.multiclaim([stakingToken])`; assert attacker receives `d+Q` reward tokens — i.e., attacker recoups their donation `d` plus fully captures `Q`, the rewards that were queued for future/legitimate stakers.
6. Assert a legitimate large staker who deposits afterward and later calls `multiclaim` receives 0 for `Q` (it was already drained to the attacker), demonstrating the queued reward bucket was misappropriated rather than being distributed to genuine, larger stakers.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
