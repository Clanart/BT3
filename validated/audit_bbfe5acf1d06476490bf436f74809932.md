### Title
Silent ERC20 transfer-failure acceptance in `IntentGatewayV2.withdraw()` and `SweepDust` handling causes permanent loss of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` bypasses `SafeERC20` for escrow payouts and dust sweeps, instead issuing a raw low-level `.call()` with the `IERC20.transfer.selector` and checking only that the call did not revert, never inspecting the ABI-decoded boolean return value. This is the return-value-checking bug class from the referenced report, but manifesting as the inverse and more dangerous failure mode: a token that legitimately returns `false` (instead of reverting) on a failed transfer is treated by this code as a **successful** transfer, while escrow accounting is unconditionally decremented and the order is marked filled/redeemed.

### Finding Description
In `withdraw()`: [1](#0-0) 
each escrowed token is paid out via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
followed by unconditional accounting mutation `_orders[body.commitment][token] -= amount;` and `_filled[body.commitment] = beneficiary;` set earlier in the function. The same pattern recurs in the `SweepDust` handler: [2](#0-1) 
and again for transaction-fee redemption: [3](#0-2) 

A low-level `.call()` only reports `success = false` when the callee reverts or the call itself fails (e.g., no code at address). It does **not** validate the returned ABI-encoded boolean. Many real ERC20 implementations return `false` rather than reverting on a failed transfer (e.g., insufficient balance guarded by a `return false;` instead of `require`, blacklist checks, deflationary/rebasing tokens, or tokens with non-standard failure semantics). For such a token, `token.call(...)` succeeds (`success = true`) even though no tokens moved, so the `if (!success) revert TransferFailed();` guard never fires.

Contrast this with the rest of the codebase, which consistently uses `SafeERC20.safeTransfer`/`safeTransferFrom` for the exact same escrow-release logic on the primary EVM implementation: [4](#0-3) 
`SafeERC20` decodes and checks the return value (and handles no-return-value tokens correctly), which is precisely the protection missing from the Tron contract's `withdraw()`/`SweepDust` paths despite the file importing and even declaring `using SafeERC20 for IERC20;` at the top: [5](#0-4) 

### Impact Explanation
When a false-returning ERC20 token is escrowed and later withdrawn (via `onGetResponse` refund path or the equivalent fill/redeem POST-request path), the contract permanently marks the order `_filled` and zeroes out `_orders[commitment][token]` while the beneficiary receives nothing. The tokens remain stuck in the `IntentGatewayV2` contract with no accounting entry left to reclaim them, and the beneficiary/solver has no path to re-trigger the withdrawal because the commitment is already consumed. This is a direct loss-of-funds condition and a false-settlement-acceptance bug: the protocol's on-chain state records a successful escrow release that never actually happened.

### Likelihood Explanation
Triggering this does not require a malicious relayer, prover, or admin — any user who places or fills an order using a token whose `transfer()` can return `false` on failure (a legitimate, non-malicious ERC20 behavior found in several real-world tokens) will hit this path through ordinary protocol usage (`RedeemEscrow`, `RefundEscrow`, or `SweepDust` request kinds processed by `onAccept`/`onGetResponse`). No attacker action beyond selecting such a token for the order is needed, making this reachable in normal operation rather than requiring an adversarial actor.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `withdraw()` and the `SweepDust` branch with `IERC20(token).safeTransfer(beneficiary, amount)` from OpenZeppelin's `SafeERC20`, consistent with the rest of the codebase (`IntentsBase.sol`, `ExtrinsicIntents.sol`, `WrappedHyperFungibleToken.sol`). This ensures both no-return-value tokens (USDT-style) and false-returning tokens are handled correctly, and that escrow accounting is only mutated after a truly successful transfer.

### Proof of Concept
1. Deploy an ERC20 mock whose `transfer()` returns `false` when the internal balance check fails, instead of reverting (a valid, standards-permitted pattern):
```solidity
function transfer(address to, uint256 amount) external returns (bool) {
    if (balances[msg.sender] < amount) return false; // no revert
    balances[msg.sender] -= amount;
    balances[to] += amount;
    return true;
}
```
2. Have a user `placeOrder` escrowing this token via `IntentGatewayV2` on the Tron chain; the escrow amount is recorded in `_orders[commitment][token]`.
3. Drain or manipulate the contract's balance of that token (e.g., through fee accounting/rounding elsewhere in the same token, or simply have the token's balance mismatch due to any other legitimate flow) so that at withdrawal time the contract's balance of `token` is insufficient for the withdrawal amount but `transfer()` returns `false` rather than reverting.
4. Trigger `withdraw()` via the `RedeemEscrow`/`RefundEscrow` POST request or `onGetResponse` cancellation path: [6](#0-5) 
5. Observe: `token.call(...)` returns `success = true` (call didn't revert, just returned `false`), so `TransferFailed` is never raised; `_orders[commitment][token]` is decremented to zero and `_filled[commitment]` is set, but the beneficiary's token balance is unchanged — funds are permanently stuck with no remaining accounting trail to recover them.
