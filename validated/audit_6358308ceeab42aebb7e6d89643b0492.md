### Title
Forged `ReceivedOutput` deserialization reports unspendable Bitcoin outputs as wallet funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes an offset, `TxOut`, and `OutPoint` without validating that the offset derives the key committed to by `TxOut::script_pubkey`, or that the output was produced by `Scanner`. This lets untrusted bytes instantiate the type’s private fields directly, bypassing the invariant normally enforced by `Scanner::scan_transaction`. [1](#0-0) [2](#0-1) 

### Finding Description
`ReceivedOutput` is documented as “A spendable output,” with its `offset`, `output`, and `outpoint` fields kept private. [3](#0-2) 

The normal construction path maintains the critical invariant: `Scanner` maps each registered `ScriptBuf` to the offset used to derive it, then constructs `ReceivedOutput` only after matching `output.script_pubkey`. [4](#0-3) [5](#0-4) 

`ReceivedOutput::read` bypasses that construction path. It accepts:

1. an arbitrary scalar via `Secp256k1::read_F`;
2. an arbitrary `TxOut` via consensus decoding;
3. an arbitrary `OutPoint` via consensus decoding;

and then returns `Ok(ReceivedOutput { offset, output, outpoint })` without checking that `p2tr_script_buf(group_key + G * offset) == output.script_pubkey`. [1](#0-0) 

This mirrors the report’s write-before-validation pattern: attacker-controlled bytes establish the dangerous binding—the claimed spendable output—before the later spending path validates the offset/script relationship. `SignableTransaction::new` consumes the claimed output value, offset, and outpoint to construct transaction inputs, while the offset correctness check is deferred until `SignableTransaction::multisig`. [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who can supply serialized `ReceivedOutput` data can cause an application to report a chosen Bitcoin amount as received even though the wallet cannot spend it.

`ReceivedOutput::value()` returns the forged `TxOut` amount directly, and `SignableTransaction::new` includes that amount in `input_sat` without confirming that the corresponding `outpoint` exists or that `output` is the referenced prevout. [8](#0-7) [9](#0-8) 

The mismatch is detected only later: `multisig` applies the supplied offset and compares the derived P2TR script to the supplied `TxOut::script_pubkey`, returning `None` on mismatch. [7](#0-6)  Thus forged bytes can produce funds reported received that are not spendable—the accepted impact for this analog.

This does not appear to allow spending an unrelated victim output: if the attacker supplies a script controlled by the attacker, `multisig` rejects it unless the supplied offset derives that exact script under the threshold key. [10](#0-9)  The resulting severity is Medium rather than High.

### Likelihood Explanation
The attack is reachable wherever serialized `ReceivedOutput` values cross a trust boundary, such as peer-provided wallet data, imported state, queued scan results, or untrusted database contents. The prompt’s attack model explicitly includes untrusted bytes passed to `ReceivedOutput::read`.

No cryptographic break is required. The attacker only needs to encode a canonical scalar, a syntactically valid `TxOut`, and a syntactically valid `OutPoint`; all three fields are then trusted as a coherent wallet output. [1](#0-0) 

### Recommendation
Do not let `ReceivedOutput::read` recreate a semantically spendable output from unauthenticated bytes without context.

At minimum, replace or supplement it with a validating constructor such as:

```rust
ReceivedOutput::read_for_key(reader, group_key)
```

which deserializes the fields and rejects the object unless:

```rust
p2tr_script_buf(group_key + ProjectivePoint::GENERATOR * offset)
    == Some(output.script_pubkey.clone())
```

For registered offsets, the scanner should also verify that the decoded `script_pubkey` maps to the same offset in `Scanner::scripts`. Applications should additionally validate that `outpoint` identifies a confirmed on-chain output whose actual `TxOut` equals the serialized `TxOut` before accounting for it as spendable.

### Proof of Concept
The following conceptual Rust PoC constructs a serialized `ReceivedOutput` whose offset does not derive the supplied script. It parses successfully, reports the forged value, and is rejected only when converted into a multisig transaction.

```rust
use bitcoin::{Amount, OutPoint, ScriptBuf, TxOut};
use bitcoin::consensus::encode::serialize;
use frost::curve::Secp256k1;
use frost::Ciphersuite;
use k256::{ProjectivePoint, Scalar};

// A public group key for which a valid P2TR script can be made.
let group_key: ProjectivePoint = victim_group_key;
let real_script = p2tr_script_buf(group_key + ProjectivePoint::GENERATOR)
    .expect("derived key must have even Y");

// Lie about the offset. Scanner would have stored `1`, not `0`.
let forged_offset = Scalar::ZERO;

let forged_output = TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: real_script,
};

// Any syntactically valid outpoint suffices.
let forged_outpoint = OutPoint::null();

let mut bytes = Vec::new();
bytes.extend_from_slice(&forged_offset.to_bytes());
bytes.extend_from_slice(&serialize(&forged_output));
bytes.extend_from_slice(&serialize(&forged_outpoint));

// This succeeds despite the output not being spendable with offset 0.
let received = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(received.value(), 100_000);

// Transaction construction trusts the reported value and outpoint.
let signable = SignableTransaction::new(
    vec![received],
    &payments,
    None,
    None,
    fee_per_vbyte,
).unwrap();

// Only here is the offset/script binding checked; this returns None.
assert!(signable.multisig(&victim_threshold_keys).is_none());
```

The decisive issue is that `read` returns a supposedly spendable `ReceivedOutput` before performing the script/offset validation that the scanner’s normal construction path guarantees.
