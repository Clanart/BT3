### Malformed payment amounts can panic or wrap during transaction construction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`SignableTransaction::new` performs unchecked `u64` arithmetic over caller-supplied payment amounts and fee rates. A sufficiently large payment amount can overflow `payment_sat` or `payment_sat + needed_fee`; similarly, `fee_per_vbyte * vbytes` and `payment_sat + fee_with_change` are unchecked. In debug builds these operations panic; in release builds they wrap and can bypass the intended insufficient-funds check, producing a transaction which is semantically invalid or whose fee/change accounting is wrong.

### Finding Description

The constructor receives arbitrary `(ScriptBuf, u64)` payment pairs and a `u64` fee rate. It sums all amounts without `checked_add`, then adds the fee also without `checked_add`:

- `payment_sat` is computed with `sum::<u64>()`.
- `needed_fee` is computed with `fee_per_vbyte * vbytes`.
- `input_sat < (payment_sat + needed_fee)` is unchecked.
- The change path evaluates `input_sat.checked_sub(payment_sat + fee_with_change)`, but the inner addition is itself unchecked.

This is reachable from public transaction-construction inputs rather than requiring a malicious validator, leaked key, malformed curve implementation, or internal corruption.

### Impact Explanation

A crafted payment amount or fee rate can cause a runtime panic and halt the caller’s signing path. If wrapping arithmetic is used, the insufficient-funds check can be bypassed, yielding an invalid transaction or incorrect change/fee accounting. This is analogous to the CVE’s externally triggerable denial-of-service class: hostile transaction parameters can terminate processing before a valid signature workflow completes.

### Likelihood Explanation

The attack only requires controlling one payment amount or fee parameter supplied to `SignableTransaction::new`. No cryptographic assumptions, collisions, timing behavior, or privileged protocol role are needed. Using multiple large payments or an amount near `u64::MAX` is sufficient to hit the unchecked arithmetic.

### Recommendation

Use checked arithmetic for all monetary and fee calculations:

- Accumulate `input_sat` and `payment_sat` with `checked_add`.
- Compute `needed_fee` and `fee_with_change` with `checked_mul`.
- Compare funding using `payment_sat.checked_add(needed_fee)`.
- Compute the change subtraction using `checked_add` before `checked_sub`.
- Reject overflowing values with `TransactionError::NotEnoughFunds` or a dedicated overflow/invalid-amount error.
- Consider enforcing Bitcoin’s `MAX_MONEY` bound on every requested output amount.

### Proof of Concept

Conceptually:

```rust
let huge_payment = (script_pubkey, u64::MAX);
SignableTransaction::new(
  vec![received_output],
  &[huge_payment],
  None,
  None,
  1,
);
```
