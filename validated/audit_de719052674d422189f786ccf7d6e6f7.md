### Title
ProtoJSON parser accepts non-RFC "+" sign prefix on integer values in `JsonFormat.java` - ([File: java/util/src/main/java/com/google/protobuf/util/JsonFormat.java])

### Summary
Protobuf-java's `JsonFormat` parser converts JSON integer/string numeric values into `int32`/`int64`/`uint32`/`uint64` fields using `Integer.parseInt`, `Long.parseLong`, and `Long.parseUnsignedLong`. Since JDK 7, these methods silently accept an optional leading `+` sign (e.g. `"+123"`), which is forbidden by both the JSON number grammar (RFC 8259, `number = [ "-" ] int ...`, no leading `+`) and by Protobuf's own ProtoJSON canonical-parsing rules enforced by the C++, upb, and C# implementations. This is the same class of defect as the Mint advisory: an RFC-forbidden `+` prefix silently normalizes to a valid value in one parser while other conformant parsers in the same ecosystem reject it outright, creating a value/interpretation disagreement across implementations that consume the same ProtoJSON bytes.

### Finding Description
`JsonFormat.ParserImpl.parseInt32`/`parseInt64`/`parseUint32`/`parseUint64` in `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java` first attempt `Integer.parseInt(json.getAsString())` / `Long.parseLong(...)` / `Long.parseUnsignedLong(...)`: [1](#0-0) [2](#0-1) 

`Integer.parseInt`/`Long.parseLong`/`Long.parseUnsignedLong` all accept an optional leading `+` sign per their Javadoc contract (in effect since JDK 7). No pre-check rejects a `+` prefix before delegating to these APIs, so a ProtoJSON payload such as `{"optionalInt32": "+1"}` or `{"optionalInt32": +1}` is parsed successfully by protobuf-java, whereas the same input is explicitly required to fail by the conformance suite for every other officially-tested runtime: [3](#0-2) 

Other Protobuf language implementations explicitly guard against this. The C++ core JSON parser (`src/google/protobuf/json/internal/parser.cc`) relies on `absl::SimpleAtoi`, which — unlike `Integer.parseInt`/`Long.parseLong` — rejects a leading `+`: [4](#0-3) 

The C# runtime added an explicit, deliberate check specifically to reject `+`-prefixed numeric strings because `NumberStyles` alone cannot exclude it: [5](#0-4) 

And the C# conformance/unit tests explicitly assert `+0`/`+1` must be rejected: [6](#0-5) 

The upb-based JSON decoder (used by PHP, Ruby, Python) parses integers via `upb_BufToInt64`/`upb_BufToUint64` through a dedicated ASCII-to-integer routine (`upb/lex/atoi.c`), not the host language's generic numeric parser, and rejects the `+` sign form used in the conformance suite's `Int32FieldPlusSign` test (this test is required and only appears in the JRuby failure list, not for PHP/Ruby's core parser): [7](#0-6) 

The conformance suite explicitly documents that Java is known to diverge here: `Int32FieldPlusSign` and `Int64FieldPlusSign` (both `REQUIRED` tests under `Required.Proto2.JsonInput`/`Required.Proto3.JsonInput`) appear in `conformance/failure_list_java.txt`, confirming protobuf-java fails this REQUIRED conformance check for exactly this reason, while it is NOT similarly exempted for C++, upb-backed PHP, Python, Ruby, or C#.

**Invariant transferred from the Mint report:** the RFC/spec (RFC 8259 JSON grammar, and Protobuf's own conformance-suite-encoded JSON contract) forbids a leading `+` on a numeric token; the parser's underlying primitive (`Integer.parseInt`/`Long.parseLong`, analogous to Elixir's `Integer.parse/1`) is more permissive than the grammar it is meant to enforce, and no additional guard closes that gap. **Missing check:** absence of a leading-`+` rejection prior to calling the JDK integer parsers (present in C# via explicit `text.StartsWith("+")` guard, and structurally absent in C++/upb's custom `SimpleAtoi`/`upb_BufToInt64`).

### Impact Explanation
Impact is bounded to a parser value/acceptance differential, not memory corruption or RCE — matching the Medium-severity, integrity-only impact profile of the source advisory (CVSS `VI:L/SI:L`). A single ProtoJSON payload containing a `+`-prefixed numeric field is accepted with a concrete integer value by protobuf-java's `JsonFormat.parser()`, while the identical payload is rejected (or, per the JSON RFC, must be treated as invalid/undefined) by any other JSON/ProtoJSON consumer sharing the trust boundary — e.g., a JSON schema validator, an API gateway, or another protobuf-language service in the same request pipeline that uses the C++, upb, or C# implementation. In a multi-component pipeline where one hop validates/allows the message (or forwards it as opaque JSON) and a downstream Java service actually parses and acts on the numeric value, this cross-implementation disagreement is a values-level analog of the Mint framing disagreement: the same bytes are interpreted as "invalid" by one component and as a definite numeric value by another, which can be leveraged to smuggle data past validation logic that assumes canonical/strict JSON numeric syntax.

### Likelihood Explanation
High likelihood of the divergence being triggerable — it requires only an ordinary, bounded ProtoJSON parse call via the public `JsonFormat.parser().merge(...)` API with a trusted schema, no special privileges. The divergence is already confirmed and tracked by protobuf's own conformance suite (`Required.Proto2/Proto3.JsonInput.Int32FieldPlusSign`, `Int64FieldPlusSign` in `conformance/failure_list_java.txt`), so it is a known, currently-exempted, reproducible failure rather than a hypothetical one. Exploitability into an actual security bypass depends on a specific downstream architecture (mixed-implementation JSON validation across a trust boundary), which is an application-composition factor outside Protobuf's own control — consistent with the Medium/"requires additional deployment context" severity of the analog.

### Recommendation
Add an explicit rejection of a leading `+` character before delegating to `Integer.parseInt`/`Long.parseLong`/`Long.parseUnsignedLong`/`BigDecimal` in `JsonFormat.ParserImpl.parseInt32`, `parseInt64`, `parseUint32`, and `parseUint64` (`java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`, methods at lines 2235, 2255, 2275, 2323), mirroring the guard already present in `csharp/src/Google.Protobuf/JsonParser.cs:826-839`. Remove `Int32FieldPlusSign`/`Int64FieldPlusSign` from `conformance/failure_list_java.txt` once fixed so the REQUIRED conformance tests actually enforce this for the Java runtime going forward.

### Proof of Concept
Using protobuf-java's `JsonFormat.parser()` against any message with an `int32`/`int64`/`uint32`/`uint64` field (e.g., `TestAllTypes.optional_int32`):
```json
{"optionalInt32": "+1"}
```
or the unquoted numeric-literal form:
```json
{"optionalInt32": +1}
```
`JsonFormat.parser().merge(json, builder)` succeeds and sets `optional_int32 = 1`, whereas the C++ core parser (`ParseIntInner`/`SimpleAtoi` in `src/google/protobuf/json/internal/parser.cc:193-237`) and the C# parser (`ParseNumericString` guard in `csharp/src/Google.Protobuf/JsonParser.cs:826-839`) both reject this input with `InvalidProtocolBufferException`/parse error, and this divergence is exactly what the conformance suite's `Int32FieldPlusSign` REQUIRED test asserts (`conformance/binary_json_conformance_suite.cc:2827-2829`), with Java's known failure recorded in `conformance/failure_list_java.txt`. I did not execute this PoC in a live JVM as part of this analysis; the divergence is established from the source code of the parsing routines and the project's own conformance failure-list bookkeeping cited above, not from an executed test run.

template <typename T>
absl::StatusOr<LocationWith<T>> ParseIntInner(JsonLexer& lex, double lo,
                                              double hi) {
  absl::StatusOr<JsonLexer::Kind> kind = lex.PeekKind();
  RETURN_IF_ERROR(kind.status());

  LocationWith<T> n;
  switch (*kind) {
    case JsonLexer::kNum: {
      absl::StatusOr<LocationWith<MaybeOwnedString>> x = lex.ParseRawNumber();
      RETURN_IF_ERROR(x.status());
      n.loc = x->loc;
      if (absl::SimpleAtoi(x->value.AsView(), &n.value)) {
        break;
      }

      RETURN_IF_ERROR(ParseFloatStringAsInt<T>(*x, &n.value, lo, hi));
      break;
    }
    case JsonLexer::kStr: {
      absl::StatusOr<LocationWith<MaybeOwnedString>> str = lex.ParseUtf8();
      RETURN_IF_ERROR(str.status());

      n.loc = str->loc;

      // SimpleAtoi will ignore leading and trailing whitespace, so we need
      // to check for it ourselves.
      for (char c : str->value.AsView()) {
        if (absl::ascii_isspace(c)) {
          return lex.Invalid("non-number characters in quoted number");
        }
      }
      if (absl::SimpleAtoi(str->value.AsView(), &n.value)) {
        break;
      }

      RETURN_IF_ERROR(ParseFloatStringAsInt<T>(*str, &n.value, lo, hi));
      break;
    }
    default:
      return lex.Invalid("expected number or string");
  }

  return n;
}

static const char* jsondec_buftouint64(jsondec* d, const char* ptr,
                                       const char* end, uint64_t* val) {
  const char* out = upb_BufToUint64(ptr, end, val);
  if (!out) jsondec_err(d, "Integer overflow");
  return out;
}

static const char* jsondec_buftoint64(jsondec* d, const char* ptr,
                                      const char* end, int64_t* val,
                                      bool* is_neg) {
  const char* out = upb_BufToInt64(ptr, end, val, is_neg);
  if (!out) jsondec_err(d, "Integer overflow");
  return out;
}

static uint64_t jsondec_strtouint64(jsondec* d, upb_StringView str) {
  const char* end = str.data + str.size;
  uint64_t ret;
  if (jsondec_buftouint64(d, str.data, end, &ret) != end) {
    jsondec_err(d, "Non-number characters in quoted integer");
  }
  return ret;
}

static int64_t jsondec_strtoint64(jsondec* d, upb_StringView str) {
  const char* end = str.data + str.size;
  int64_t ret;
  if (jsondec_buftoint64(d, str.data, end, &ret, NULL) != end) {
    jsondec_err(d, "Non-number characters in quoted integer");
  }
  return ret;
}
