### Title
Direct-transfer donation of the staking/receipt token permanently dilutes `accMGPPerShare` (and bonus-reward `rewardPerTokenStored`) via `massUpdatePools()` - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie._calLpSupply()` uses `IERC20(_stakingToken).balanceOf(address(this))` as the denominator for MGP-reward accrual for every pool other than the vlMGP/mWomSV pools. Any unprivileged actor can `transfer()` the receipt/staking token directly into `MasterMagpie` (no deposit, no `UserInfo.amount` credit) and then call the fully public, unauthenticated `massUpdatePools()`/`updatePool()` to bake that inflated balance into `accMGPPerShare` for the current accrual interval, permanently reducing the MGP that is or ever will be distributable to the pool's legitimately staked `UserInfo.amount`.

### Finding Description
`updatePool()` computes the per-interval MGP increment as:
```solidity
uint256 lpSupply = _calLpSupply(_stakingToken);
...
pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
``` [1](#0-0) 

and for the general pool branch:
```solidity
return IERC20(_stakingToken).balanceOf(address(this));
``` [2](#0-1) 

`massUpdatePools()` is `public` and callable by anyone, with no role check beyond `whenNotPaused`:
```solidity
function massUpdatePools() public whenNotPaused {
    for (uint256 pid = 0; pid < registeredToken.length; ++pid) {
        updatePool(registeredToken[pid]);
    }
}
``` [3](#0-2) 

Because `lpSupply` is the raw token balance of the contract rather than the sum of `UserInfo.amount` actually credited via `_deposit`, an attacker can:
1. `transfer()` an arbitrary amount of the pool's staking/receipt token directly to `MasterMagpie` (a plain ERC20 call, no MasterMagpie function invoked, so `UserInfo.amount` is untouched).
2. Call `massUpdatePools()` (or `updatePool(_stakingToken)`, or trigger it indirectly via any `deposit`/`withdraw`/`claim` on the pool, since those all call `updatePool` first).
3. `accMGPPerShare` is incremented using the artificially inflated `lpSupply`, so `(mgpReward * 1e12) / lpSupply` under-counts the true per-share reward relative to what `sum(UserInfo.amount)` should have received for that time window.

Since `unClaimedMgp`/`_calNewMGP` and `rewardDebt` are derived purely from `accMGPPerShare * user.amount / 1e12`, the shortfall for that interval is never credited to any account and there is no mechanism to reclaim or correct it later — it is baked permanently into the monotonically increasing `accMGPPerShare` history [4](#0-3) .

The same balance-based denominator pattern is also present in the paired `BaseRewardPoolV2` bonus-reward accounting: `totalStaked()` returns `IERC20(stakingToken).balanceOf(operator)` (i.e., `MasterMagpie`'s balance) while individual `balanceOf(_account)` correctly reads `MasterMagpie.stakingInfo` (i.e., `UserInfo.amount`) [5](#0-4) . `_provisionReward()` divides `_amountReward * 10**stakingTokenDecimals` by this same inflatable `totalStaked()` [6](#0-5) , so the same donation dilutes bonus-token `rewardPerTokenStored` growth as well. No modifier, `nonReentrant` guard, or accounting reconciliation in either contract prevents this, since the root cause is the choice of denominator, not a re-entrancy or access-control gap.

Note: `BaseRewardPoolV2`'s cached `stakingTokenDecimals` (immutable, set at construction) is not itself part of the exploited mechanism — the vulnerability is fully driven by the `balanceOf`-based denominators in both `_calLpSupply` and `totalStaked()`, independent of decimals caching.

### Impact Explanation
Every interval in which the donation-inflated balance persists, the MGP (and any bonus reward token routed through `BaseRewardPoolV2`) that should have accrued to `sum(UserInfo.amount)` is permanently under-minted/under-credited: it is not paid to the attacker, and it is not recoverable by legitimate stakers because `accMGPPerShare`/`rewardPerTokenStored` only ever increase and are never reconciled against the donation. This is a permanent, quantifiable loss of unclaimed yield for every current and future staker of the affected pool, matching "High – Permanent freezing of unclaimed yield." The magnitude scales with the ratio of the donated amount to the pool's genuinely staked supply and, since the donated tokens cannot be withdrawn back out through `_withdraw` (which is `UserInfo.amount`/`available`-gated, not balance-gated), the inflation and resulting yield loss persists indefinitely with no compounding remedy in the contract.

### Likelihood Explanation
- No privileged role is required: `massUpdatePools()`/`updatePool()` have no `onlyOwner`/`_onlyPoolManager` gate, only `whenNotPaused` [7](#0-6) .
- The donation step is a standard ERC20 `transfer()` to the `MasterMagpie` address — no approval or interaction with MasterMagpie logic needed.
- Fully repeatable against any pool where `_stakingToken` is neither `vlmgp` nor `mWomSV`.
- Attack cost equals the donated token amount (which is permanently lost by the attacker as well, since it can't be withdrawn back), making it a griefing-type attack: it inflicts real, permanent yield loss on other users at the attacker's own capital expense, and is feasible for any attacker willing to sacrifice tokens to damage the protocol/competing stakers.

### Recommendation
Track staked supply internally (e.g., a `pool.totalStaked` counter incremented/decremented in `_deposit`/`_withdraw`) instead of deriving `lpSupply` from `IERC20(_stakingToken).balanceOf(address(this))` in `_calLpSupply()`. Apply the same fix to `BaseRewardPoolV2.totalStaked()` — source it from `MasterMagpie`'s internally tracked total, not `balanceOf(operator)`.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `MasterMagpie`, register a pool with a mock ERC20 `stakingToken` and a `BaseRewardPoolV2` rewarder, set `mgpPerSec` and `allocPoint`.
2. User A deposits `1000e18` staking tokens via `deposit()`; confirm `userInfo[stakingToken][A].amount == 1000e18`.
3. Advance time by `T` seconds; call `massUpdatePools()`; record `accMGPPerShare_1` and compute `expectedPending_1 = A._calNewMGP(...)`.
4. Attacker (no prior stake) sends `9000e18` staking tokens directly via `stakingToken.transfer(masterMagpie, 9000e18)` (balance now `10000e18`, but `sum(UserInfo.amount) == 1000e18`).
5. Advance time by the same `T` seconds; call `massUpdatePools()` again from an unprivileged EOA.
6. Assert `accMGPPerShare` increment for step 5 is ~10x smaller than the increment in step 3 for an identical `T` and `mgpPerSec`, even though `sum(UserInfo.amount)` is unchanged at `1000e18`.
7. Assert `A`'s claimable MGP (`_calNewMGP` + `unClaimedMgp`) for the post-donation interval is far less than `mgpReward` emitted for that interval (i.e., `pending_A < mgpPerSec * T * allocPoint / totalAllocPoint`), and that no other address (including the attacker) can claim the shortfall — confirming the yield is permanently unattributed/lost, not merely delayed.
8. Repeat steps against `BaseRewardPoolV2.queueNewRewards`/`donateRewards` to show `rewardPerTokenStored` growth is similarly diluted by the same donation via `totalStaked()`.

    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }
