## Finding

GitHub Desktop's AI ("Copilot") merge-conflict resolution feature parses git conflict-marker blocks with **two independently implemented, naive line-anchored regex scanners** that are expected to agree on hunk boundaries/count, but can desynchronize when a genuine conflict region happens to contain a line that coincidentally matches a marker regex (e.g. a stray `>>>>>>>`-looking line). This is structurally the same class of bug as the report's linked-list loop that "forgets" to advance a pointer correctly and desyncs state between iterations — here two parsers desync their notion of "where hunk N ends," causing the AI's per-hunk resolution to be spliced into the wrong place (or dropped), while raw, unreviewed conflict-marker text and one side's content is silently written into the file the user is about to commit.

### Title
Mismatched conflict-marker parsers in Copilot conflict resolution allow attacker-influenced content to desync hunk splicing, silently committing raw markers/unreviewed text - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`extractConflictHunks` (used to build the prompt sent to the model) and `reassembleResolvedFile` (used to splice the model's per-hunk resolutions back into the on-disk file before it is written/committed) are two separate hand-rolled scanners over the same conflict-marked file content, matched only "by order, not by line number" as the code itself documents. [1](#0-0) 

### Finding Description
`extractConflictHunks`'s "collect ours" phase only checks for the base marker (`|||||||`) or separator (`=======`) while scanning; it never checks for a closing marker (`>>>>>>>`): [2](#0-1) 

`reassembleResolvedFile`'s look-ahead, however, scans every line after the opening `<<<<<<<` and treats the **first** line matching the closing-marker regex as the block's end — even if no separator has been seen yet: [3](#0-2) 

If the section that sits between the real `<<<<<<<` and the real `=======` (the "ours" side) contains a line that happens to match `/^>{7}(?:\s|$)/` (a stray `>>>>>>>`-looking line — plausible in normal source, docs, ASCII dividers, or content deliberately crafted by whoever authored that side):

- `extractConflictHunks` is unaffected (its ours-loop doesn't check for closing markers) and successfully extracts the hunk, sending it to the model and receiving back a valid resolution, incrementing the expected hunk count normally: [4](#0-3) 
- `reassembleResolvedFile`'s look-ahead breaks the moment it hits the stray `>>>>>>>`-looking line, before ever reaching the real `=======`, so `hasSeparator` stays `false` and the block is classified as malformed: [5](#0-4) . In that branch, `hunkIndex` is **not** incremented, only the opening marker line is emitted, and the walk continues line-by-line — copying the real `=======`, the real "theirs" content, and the real `>>>>>>>` straight into `resultLines` as ordinary file content, because none of the intermediate lines alone re-triggers the `oursMarker` check that starts a new block: [6](#0-5) 

Because `hunkIndex` fails to advance for this block, every subsequent hunk resolution from the model is applied one slot off from where `extractConflictHunks` said it belonged — an exact structural analog of the Cairo report's `prev`/`next` pointer never being advanced, causing state to desynchronize across "iterations" of the two loops.

The only guard against markers surviving into the final file only inspects each hunk's `resolvedContent` in isolation, which never runs against this corrupted branch since it copies raw lines through `resultLines` directly rather than through a hunk resolution: [7](#0-6) 

There is no subsequent check on the fully reassembled file content for leftover `<<<<<<<`/`=======`/`>>>>>>>` markers before it's handed off as the resolved file (`IFileResolution.resolvedContent`), so this corrupted content flows straight through to whatever writes it to disk/stages it for commit.

### Impact Explanation
When this desync occurs, a user who invokes "Resolve with Copilot" on a conflicted merge/rebase/cherry-pick can end up with:
- literal, unreviewed git conflict markers and raw conflicting text (from both sides) written directly into the file content that Desktop reports as "resolved" and stages for commit, and/or
- a later, unrelated conflict hunk's marker block silently replaced with the resolution content intended for a *different* hunk (splicing the wrong merged code into the wrong location).

Either outcome is a silent corruption of what the user commits/pushes without any warning, since the feature is designed to auto-apply the model's output as the final file content.

### Likelihood Explanation
The desync depends only on ordinary file content containing a line matching `/^>{7}(?:\s|$)/` inside the "ours" span of a conflict block. During a `git pull --rebase`/cherry-pick against a remote the user doesn't fully control (a compromised or malicious upstream, matching the allowed "git remote/proxy response" attacker model), the git convention flips which side is "ours" vs "theirs," putting attacker-influenced upstream content into the very span this bug requires. No unusual local access, credentials, or social engineering beyond a normal rebase/cherry-pick against an untrusted remote and clicking Desktop's built-in AI conflict-resolution action is needed.

### Recommendation
Make `reassembleResolvedFile`'s block detection consistent with `extractConflictHunks`'s: require the base/separator marker to be found before ever testing for the closing marker (mirroring the phased loops in `extractConflictHunks`), or better, replace both hand-rolled scanners with a single shared parsing routine used by both extraction and reassembly so hunk boundaries can never diverge. Additionally, after reassembly, scan the final `resolvedContent` for residual conflict-marker lines and treat their presence as a hard failure rather than silently writing them into the committed file.

### Proof of Concept
1. Set up a rebase (or cherry-pick) where the "ours" side (per git's rebase convention, the target/upstream branch content) is attacker-influenced, e.g. by adding a remote controlled by an attacker and running `git pull --rebase` against it.
2. Craft the upstream file so the conflicting region looks like:
```
<<<<<<< HEAD
some legitimate looking line
>>>>>>> spoof
more attacker content
=======
user's real "theirs" content
>>>>>>> abcd123 (user's commit)
```
3. In `extractConflictHunks`, the ours-loop (lines 202-214) ignores the fake `>>>>>>> spoof` line (it only checks for `baseMarker`/`separatorMarker`) and keeps scanning until it reaches the real `=======`/`>>>>>>>`, successfully extracting one hunk and sending it to the model, which returns a resolution.
4. In `reassembleResolvedFile` (lines 559-579), the look-ahead loop hits `>>>>>>> spoof` first, sets `closingIndex` and breaks before ever seeing the real `=======`, so `hasSeparator` is `false` → the block is classified malformed.
5. The reassembly loop then copies through, as literal file content, the fake marker line, `more attacker content`, the real `=======`, the user's real "theirs" content, and the real `>>>>>>>` — none of which is replaced by the model's resolution — directly into the file that Desktop reports as "resolved" and stages for commit.
