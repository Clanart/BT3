## Finding

The Desktop analog to the "superfluous permissions in manifest" bug class is the renderer's Electron `webPreferences` configuration: the main application window is created with `nodeIntegration: true` and `contextIsolation: false`, even though the renderer never needs direct Node.js access — all privileged operations (file system, shell, git, IPC) are already funneled through the `ipcRenderer.invoke`/`send` proxy layer. The same overly-broad configuration is duplicated in the crash-reporter window: [2](#0-1) 

### Title
Renderer windows granted unnecessary `nodeIntegration`/disabled `contextIsolation` capabilities - (File: app/src/main-process/app-window.ts)

### Summary
Both `BrowserWindow` instances that host GitHub Desktop's renderer content (`AppWindow` and `CrashWindow`) are configured with `nodeIntegration: true` and `contextIsolation: false`. This is the Electron-app equivalent of the reported "superfluous permissions" flaw: the manifest/configuration declares far more capability (raw Node.js API access from the renderer, and no isolation boundary between the untrusted web content context and Electron internals/Node) than the renderer actually requires.

### Finding Description
Desktop already funnels every privileged action — file access, `shell.openExternal`, git operations, menu/window control — through a typed IPC proxy layer (`invokeProxy`/`sendProxy`) rather than by calling Node APIs directly from the renderer. [3](#0-2) 
This demonstrates the renderer has no functional need for direct `require`/Node global access, yet `nodeIntegration: true` and `contextIsolation: false` are still set on both windows, which:
- Exposes the full Node.js API surface (`require('fs')`, `require('child_process')`, etc.) to any script that executes in the renderer's JS context.
- Removes Electron's process-isolation boundary (`contextIsolation`) that normally prevents web content from reaching into privileged JS globals/prototypes shared with the preload/main world.

This mirrors the report's core complaint: capability is granted "just in case" rather than being scoped to what the code actually uses, which needlessly enlarges the exploitable surface for any content-injection bug (XSS) that might arise in the renderer, such as through repository names, commit messages, PR titles/bodies, or other attacker-influenced GitHub API/git object strings rendered in the UI. The one place attacker-controlled markdown *is* rendered (PR bodies/comments/Copilot conflict summaries) is properly isolated in a sandboxed iframe with DOMPurify sanitization, which shows the team is aware such content is untrusted — but the outer main-window process itself still runs with none of Electron's own defense-in-depth hardening applied. [4](#0-3) [5](#0-4) 

### Impact Explanation
With `nodeIntegration: true` and `contextIsolation: false` on the top-level app window, any future or currently-unknown script-injection primitive in the renderer (e.g. via unsanitized rendering of a cloned repo's file names, commit trailers, branch names, or a GitHub API field that bypasses React's default escaping) would convert from a scoped DOM/JS bug into full Node.js code execution in the Electron main-adjacent context — reading/writing arbitrary files, spawning processes, or exfiltrating stored credentials/OAuth tokens. Removing the unneeded flags does not eliminate a specific existing XSS, but it removes the amplification layer that turns "unprivileged content confusion" into "code execution," exactly as the original report argues for the snap's manifest.

### Likelihood Explanation
There is no direct proof-of-concept exploit chain identified in the reviewed code today (no `dangerouslySetInnerHTML` usage was found, and the primary attacker-influenced rendering path, `SandboxedMarkdown`, is iframe-isolated and DOMPurify-sanitized). The exposure is architectural rather than immediately triggerable, which is consistent with the original report's own framing (a least-privilege violation that "expands the attack surface" rather than a directly exploitable primitive by itself).

### Recommendation
Set `nodeIntegration: false` and `contextIsolation: true` on both `AppWindow` and `CrashWindow`, and expose only the minimal typed IPC surface to the renderer via a `preload` script using `contextBridge.exposeInMainWorld`, matching the existing `invokeProxy`/`sendProxy` abstraction already used in `app/src/ui/main-process-proxy.ts`. This mirrors the report's own remediation pattern of removing unused breadth of capability (`initialConnections`, `snap_dialog`, `endowment:rpc.snaps`) down to only what is actually exercised by the code.

### Proof of Concept
Not independently reproducible from the reviewed code as a standalone exploit (no existing XSS/injection sink was located); the finding documents a defense-in-depth/least-privilege gap analogous to the reported manifest issue rather than a demonstrated end-to-end RCE chain, consistent with the report's own "unnecessary permission" framing.

```typescript
export function invokeProxy<T extends keyof RequestResponseChannels>(
  channel: T,
  numArgs: ParameterCount<RequestResponseChannels[T]>
) {
  return (...args: Parameters<RequestResponseChannels[T]>) => {
    // This as any cast here may seem unsafe but it isn't since we're guaranteed
    // that numArgs will match the parameter count of the IPC declaration.
    args = args.length !== numArgs ? (args.slice(0, numArgs) as any) : args
    return ipcRenderer.invoke(channel, ...args)
  }
}
```
