### Title
ReceivedOutput deserialization accepts an offset inconsistent with the output's script, yielding funds reported as received that are not spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report describes assuming a token transfer succeeded without validating the result, leaving value accounted-for but stuck. The analog in Serai: `ReceivedOutput::read` deserializes `offset`, `output`, and `outpoint` independently and never verifies that the `offset` actually produces the `script_pubkey` contained in `output`. A `ReceivedOutput` whose `offset` does not satisfy `script_pubkey == p2tr(key + offset·G)` is accepted, reported as an external received balance, yet is unspendable — the derived signing key will not correspond to the output's taproot key, so any spend silently fails and the funds are stuck.

### Finding Description
`Scanner::register_offset` stores `script → offset` pairs where `script == p2tr_script_buf(key + offset·G)`, and `scan_transaction` produces `ReceivedOutput`s only when this invariant holds [1](#0-0) . However, `ReceivedOutput::read` reconstructs the object from untrusted bytes with no consistency check between the three fields [2](#0-1) .

The Bitcoin `Output::read` in the processor wraps `ReceivedOutput::read`, and `key()` derives the group key as `script_pubkey_key - offset·G` — again without verifying the result matches the actual multisig key [3](#0-2) . An arbitrary `offset` simply yields an arbitrary (incorrect) group key. Downstream, signing uses `group_key + offset` against the taproot-tweaked script key; with a mismatched offset the signature will not satisfy the output, so the spend is impossible while the processor still treats `output.value()` as an `ExternalBalance` credited to the protocol [4](#0-3) .

### Impact Explanation
A malformed `ReceivedOutput` causes the processor to report bitcoin as received (crediting a balance/instruction flow) that can never be spent: the signing path derives `key + offset` which does not match the output's taproot key, so the transaction cannot be signed/spent and the funds are effectively stuck — the same "value accounted but unspendable" outcome as the unchecked-transfer bug class.

### Likelihood Explanation
Reachable whenever serialized `Output`/`ReceivedOutput` bytes cross a trust boundary (network messages or DB input an attacker can influence). It requires no key compromise and produces a deterministic accounting/spendability mismatch. Severity is Medium: it misreports funds rather than stealing them.

### Recommendation
In `ReceivedOutput::read` (or `Output::read`), recompute `p2tr_script_buf(registered_key + offset·G)` and reject if it does not equal `output.script_pubkey`. Alternatively, store the expected group key in `ReceivedOutput` and verify `key()` equals it after reading.

### Proof of Concept
1. Take any honest serialized `ReceivedOutput` produced by `scan_transaction`.
2. Mutate the first 32 bytes (the `offset` scalar), e.g. `offset' = offset + 1`.
3. Feed the bytes to `ReceivedOutput::read` / `Output::read`. Deserialization succeeds.
4. `balance()` reports the output's satoshis as external funds, but `key()` returns `script_key - offset'·G`, a key unrelated to the multisig, and spending with `offset'` fails taproot verification — funds reported received, permanently unspendable.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {

      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };
