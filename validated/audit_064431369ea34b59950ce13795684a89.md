### Title
Attacker-controlled `ReceivedOutput` offset decouples the spend key from the output's `script_pubkey`, making reported funds unspendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Arrakis report — where an unprivileged donation silently skews the weights applied to subsequent depositors — any party able to feed bytes to `ReceivedOutput::read` can silently skew the *tweak parameter* (the `offset` scalar) that the wallet applies when later spending that output. `ReceivedOutput` stores `offset` as a bare `Scalar` alongside the `TxOut`/`OutPoint`, and `read` performs no check that `offset` actually satisfies `output.script_pubkey == p2tr(key + G*offset)`. The offset is later consumed blindly to re-key the signing keys for that input, so a corrupted offset produces signatures for the wrong tweaked key: the output is reported as received yet cannot be spent.

### Finding Description
`ReceivedOutput::read` deserializes three independent fields — `offset` via `Secp256k1::read_F`, then a consensus-decoded `TxOut` and `OutPoint` — with no binding between them (networks/bitcoin/src/wallet/mod.rs:120-134). The honest producer, `Scanner::scan_transaction`, only ever pairs an `offset` with an `output.script_pubkey` that `self.scripts` maps to that offset (mod.rs:199-213), so correctness depends entirely on the invariant established at scan time. Once serialized and re-read through `ReceivedOutput::read`/`serialize` (mod.rs:136-148) — a path explicitly used to persist/transport outputs (see round-trip usage in networks/bitcoin/tests/wallet.rs:72-75) — the invariant is no longer enforced.

When a `ReceivedOutput` is spent, the wallet applies `output.offset()` to derive the per-input tweaked key (the per-input re-keying is exercised in tests via `output.offset()` / `keys.clone().offset(offset)`, networks/bitcoin/tests/wallet.rs:80-98, 215-244). With a tampered `offset'`, the threshold signs under `key + G*offset'`, while the UTXO's `script_pubkey` commits to `key + G*offset`. The resulting signature cannot satisfy the script; the input is unspendable.

### Impact Explanation
An attacker who supplies or tampers with serialized `ReceivedOutput` bytes (e.g., a malicious peer/relayer feeding the spend pipeline, or corruption between the scanner and the signer components) causes funds the wallet reports as received to be unspendable: every signing attempt produces an invalid Taproot signature because the tweaked signing key no longer matches the output's committed key. If the true offset is not independently recoverable (the `Scanner`'s `scripts` map is local state, and `register_offset` is surjective/order-dependent per mod.rs:168-196), the mislabeled offset permanently desynchronizes the wallet's record from the chain state — the analog of Arrakis's "users lose yield because the propagated proportions are wrong": a locally-derived parameter (offset/weights) silently diverges from what the on-chain object (script_pubkey/vault liquidity) actually commits to, and every downstream consumer inherits the corrupted parameter. Medium: requires an untrusted-bytes channel to `read`, and the result is fund lockup rather than theft (the script_pubkey is fixed, so the attacker cannot redirect the funds to themselves).

### Likelihood Explanation
`ReceivedOutput::read` is a public deserialization API on a wallet type explicitly intended for untrusted transport (it is listed among the untrusted-byte readers). Any integration that round-trips outputs through untrusted storage, messages between mutually distrustful nodes, or coordinator-supplied spend instructions is exposed. The attacker needs only to flip or replace the leading 32-byte scalar; no cryptographic break is required.

### Recommendation
Bind the offset to the output it tweaks. Options:
- Carry the base key (or a fingerprint of it) in `ReceivedOutput` and verify `p2tr_script_buf(base_key + G*offset) == output.script_pubkey` inside `read`/a `verify` method, rejecting mismatches.
- Alternatively, stop serializing `offset` entirely and re-derive it at spend time by matching `output.script_pubkey` against the live `Scanner` script map, so the only trusted source of the offset is the same table that established the invariant at scan time.

### Proof of Concept
1. Scanner scans a deposit to the vault's external address: `out = ReceivedOutput { offset: Scalar::ZERO, output: TxOut{ script_pubkey: p2tr(key), value }, outpoint }`.
2. Attacker intercepts `out.serialize()` and replaces the first 32 bytes with `offset' = Scalar::random()`, yielding bytes that `ReceivedOutput::read` accepts without error (mod.rs:122-134).
3. The wallet schedules a spend including this input; `SignableTransaction` builds the per-input key as `keys.offset(offset')` → tweaked key `key + G*offset'`.
4. The threshold produces a BIP-340 signature valid for `key + G*offset'`, but the UTXO's script commits to `p2tr(key)` (offset ZERO). The transaction fails script verification; the reported-received funds cannot be spent. Repeating for `change`/`branch`/`forward` offsets (`hash_to_F(KEY_DST, ...)`, derivable publicly) shows no offset value lets the attacker steal the output — the mismatch strictly destroys spendability, confirming the integrity-binding failure rather than a redirection flaw.

Caveat: severity depends on whether deployments actually accept `ReceivedOutput` bytes from parties less trusted than the scanner itself; if all inputs are self-produced, the attack surface reduces to local data corruption.
