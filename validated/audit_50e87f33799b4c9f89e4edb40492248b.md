### Title
`revealInFileManager` resolves attacker-controlled repo paths without symlink/traversal validation, unlike equivalent path-handling code elsewhere - (File: `app/src/lib/app-shell.ts`)

### Summary
`revealInFileManager` builds the path it hands to the OS shell with a plain `Path.join(repository.path, path)` and never validates that the resulting path actually stays inside the repository working directory. Elsewhere in the same codebase (deep-link file opening, Copilot conflict-file reading) the exact same class of input — a repository-relative path string — is always passed through `resolveWithin()`, which performs `realpath()`-based verification specifically to defeat symlink and traversal escapes. `revealInFileManager` is the one path-consuming, shell-facing sink that skips this guard, even though it is fed `path` values that originate from git-tracked/working-directory state of a cloned or fetched repository (changed-file lists, PR diff file lists, merge-conflict file lists).

### Finding Description
`revealInFileManager` is defined as: [1](#0-0) 
```
export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}
```
`path` is joined directly with `repository.path` and passed straight to `shell.showItemInFolder`, which proxies to the Electron main process via IPC and ultimately calls `electronShell.showItemInFolder` on an arbitrary absolute path [2](#0-1) [3](#0-2) .

This function is invoked with `file.path` values sourced from data derived from the working tree/commit/diff of an opened repository — i.e., data an attacker fully controls by crafting a malicious cloned/fetched repository (a symlinked directory checked into the tree, or a crafted rename/path segment):
- Changes list context menu: [4](#0-3) 
- Pull-request file list context menu: [5](#0-4) 
- Copilot conflict resolution overflow menu: [6](#0-5) 
- Merge conflict file view (`unmerged-file.tsx`, 4 call sites, not fully inspected in this pass)

In contrast, the codebase demonstrates it is fully aware that repository-relative paths must be validated before being handed to a shell/file operation, because it applies exactly that guard in comparable code paths:
- Deep-link "open file" handler explicitly rejects absolute paths and requires `resolveWithin` to succeed before calling `shell.showItemInFolder`: [7](#0-6) 
- Copilot conflict-context file reader: "Guard against path traversal and symlink escapes (cross-platform)" via `resolveWithin`: [8](#0-7) 
- `resolveWithin` itself is implemented specifically to defeat symlink-based escapes by comparing `realpath()` of the resolved path against `realpath()` of the root: [9](#0-8) , and there is a dedicated unit test proving a symlinked directory component can otherwise be used to escape the root: [10](#0-9) 

`revealInFileManager` is the outlier: it performs the join but omits the `resolveWithin`/`realpath` check that every other path-consuming sink in this codebase applies. Because git tracks symlinks as regular blobs, a malicious repository can commit a symlink (e.g. `evil -> /` or `evil -> ../../..`) which is materialized on disk during clone/fetch/checkout. If the UI subsequently shows a "file" nested under that symlinked directory name in any of the panels above (e.g., an untracked/changed file whose relative path traverses through the symlinked entry), `Path.join(repository.path, path)` will produce a path that, once the OS resolves the symlink component, points completely outside the repository, and `revealInFileManager` will pass it straight to the main-process shell call with no re-validation.

### Impact Explanation
`showItemInFolder` opens the OS file manager focused on the resolved path. Because the check that exists everywhere else in the app to stop exactly this (`resolveWithin`) is missing here, an attacker who controls the contents of a cloned/fetched repository can cause Desktop to reveal/open a file-manager view rooted at an arbitrary location outside the repository the moment the victim right-clicks a crafted entry and selects "Reveal in Finder/Explorer" (or the app auto-triggers it in a flow such as conflict resolution). This is a file-disclosure / sandbox-escape-adjacent primitive reachable purely from repository content, matching the "read outside the repo" impact category. Depending on OS behavior (e.g., double-click-to-open following in Explorer/Finder), it can also be a stepping stone to execution of unintended binaries.

### Likelihood Explanation
Likelihood is moderate: the attacker only needs the victim to clone/fetch a repository containing a committed symlink and open the corresponding conflict/changes/PR panel and select the "Reveal in File Manager" context-menu action — no other user setup or privilege is required. This is a normal, expected user interaction (browsing changed files) rather than an unnatural workflow.

### Recommendation
Route the path through `resolveWithin(repository.path, path)` inside `revealInFileManager` (mirroring `openRepositoryFromUrl` and `buildConflictContext`) and refuse to call `shell.showItemInFolder` when it returns `null`, so all shell-reveal call sites enforce the same repo-containment/symlink-escape guard that the rest of the codebase already relies on.

### Proof of Concept
1. Attacker creates a repository containing a symlink `evil -> /` (or `../../..`) committed as a tracked blob, plus a nested path such as `evil/passwd` that appears as an untracked/changed/conflicted file once checked out.
2. Victim clones/fetches this repository in GitHub Desktop and opens the Changes list, a PR's Files Changed view, or a merge-conflict resolution view where `evil/passwd` is listed.
3. Victim right-clicks the entry and selects "Reveal in Finder"/"Show in Explorer", triggering `revealInFileManager(repository, 'evil/passwd')` at any of: [4](#0-3) , [5](#0-4) , [11](#0-10) .
4. `Path.join(repository.path, 'evil/passwd')` resolves through the on-disk symlink to `/passwd` (or another arbitrary system path), and `shell.showItemInFolder` opens the OS file manager at that location — outside the intended repository directory — with no `resolveWithin` check to stop it, unlike the equivalent deep-link and Copilot-conflict code paths.

**Note on verification limits:** I was not able to fully inspect `app/src/ui/lib/conflicts/unmerged-file.tsx` and `app/src/ui/history/selected-commits.tsx` call sites, or the exact mechanism `git status`/diff parsing uses for paths containing symlinked directory components, within the available tool budget; a Devin session with full repo/checkout access would be needed to confirm the precise git-status code path that surfaces a file nested under a symlinked directory as a distinct list entry, and to validate cross-platform (Windows/macOS) behavior of `shell.showItemInFolder` on such a resolved path.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
