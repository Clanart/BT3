### Title
`ReceivedOutput::read` accepts fully unauthenticated outpoint/TxOut/offset tuples, letting untrusted bytes mint fake spendable outputs — (`networks/bitcoin/src/wallet/mod.rs`)

### Summary
The NiFi bug class is "an alternative input path feeds a trust decision without the validation applied to the canonical path." In Serai's Bitcoin wallet the analog is `ReceivedOutput`: the type conflates "an output observed on-chain paying to the group" with a bare claimed `(offset, TxOut, outpoint)` triple. `ReceivedOutput::read` deserializes all three fields from attacker-supplied bytes and performs only encoding checks (canonical scalar, decodable `TxOut`/`OutPoint`) — it never checks that the `script_pubkey` actually corresponds to `key + offset*G`, nor that the `output`/`outpoint` pair is internally consistent. The only script/offset consistency check lives later, in `SignableTransaction::multisig`, leaving every reporting path (`Scanner` output consumers, `Output::key()` callers) trusting fabricated outputs.

### Finding Description
`ReceivedOutput::read` reads the offset scalar via `Secp256k1::read_F`, then consensus-decodes a `TxOut` and an `OutPoint`, and returns the tuple unconditionally: [1](#0-0) 

No field binds `output.script_pubkey` to `offset`, and nothing binds `output` to `outpoint`. By contrast, the spend path does validate one half of this: `SignableTransaction::multisig` rejects inputs whose `prevouts[i].script_pubkey` doesn't equal `p2tr_script_buf(keys.offset(offsets[i]).group_key())`: [2](#0-1) 

So validation exists for "does this script match the claimed offset+key" but is absent at deserialization for "is this output real / does this outpoint actually contain this TxOut" — exactly the NiFi pattern of validating `Host` while `X-Forwarded-Host` reaches the same trust decision unchecked. Any consumer that receives a serialized `ReceivedOutput` (the format is exercised through `serialize`/`read` round-trips and is re-read downstream, e.g. `Output::read` embeds `ReceivedOutput::read`) will report attacker-chosen outputs as wallet-owned funds.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` produces outputs the wallet reports as received and spendable which are not: arbitrary `TxOut`s (any value, any script) under arbitrary outpoints appear as multisig-owned balance. Forged outputs with foreign `script_pubkey` additionally cause `Output::key()`-style consumers to derive a wrong signer key or panic on `is_p2tr` assumptions, and inputs with fabricated `value` fields poison `fee()`/`input_sat` accounting in `SignableTransaction::new` (the claimed value is committed into the BIP-341 `Prevouts::All` sighash), turning fake balances into consensus-invalid signed transactions. This is "funds reported received that are not spendable" plus integrity loss of the fee/change computation — a Medium-severity impact.

### Likelihood Explanation
Exploitation requires the attacker to control the serialized `ReceivedOutput` stream — e.g., any path where scan results, DB contents, or peer-supplied data are deserialized through `read`. Within the listed trust model (untrusted bytes fed to `ReceivedOutput::read`) this is reachable with public inputs only; no key material or validator collusion is needed. The fabricated outputs cannot produce a *valid* signature stealing funds — the script/offset check in `multisig` and the BIP-341 amount commitment bound the damage to false reporting, misattributed keys, and invalid transactions — hence Medium rather than High.

### Recommendation
Make the trust boundary explicit: either (a) treat `ReceivedOutput` as constructible only by `Scanner::scan_transaction`/`scan_block` (which observed the output on-chain) and keep `read` crate-private, or (b) re-validate on deserialize — verify `output.script_pubkey == p2tr_script_buf(group_key + GENERATOR*offset)` at `read` time given a key context, matching the check `multisig` performs later. Consumers that accept serialized outputs should also confirm `outpoint` resolves on-chain to the claimed `TxOut` before reporting the funds as received.

### Proof of Concept
```rust
use bitcoin_serai::wallet::ReceivedOutput;
use bitcoin::{
  TxOut, OutPoint, ScriptBuf, Amount, Txid,
  hashes::Hash,
};
use frost::curve::Secp256k1;
use ciphersuite::Ciphersuite;
use k256::{Scalar, ProjectivePoint};

// Attacker-serialized blob: offset = 0, a TxOut paying to an ATTACKER-CONTROLLED
// p2tr key (or any script), and an arbitrary outpoint. `read` accepts it.
fn forge() -> Vec<u8> {
  let mut buf = vec![];
  buf.extend(Scalar::ZERO.to_bytes());                    // offset
  let attacker_key = XOnlyPublicKey_for_attacker();       // not key + offset*G
  let output = TxOut {
    value: Amount::from_sat(1_000_000_000),
    script_pubkey: ScriptBuf::new_p2tr_tweaked(attacker_key),
  };
  buf.extend(bitcoin::consensus::serialize(&output));
  buf.extend(bitcoin::consensus::serialize(&OutPoint::new(Txid::all_zeros(), 0)));
  buf
}

let forged = ReceivedOutput::read(&mut forge().as_slice()).unwrap(); // succeeds
// `forged` now reports 10 BTC as received; only SignableTransaction::multisig
// would later reject it — every reporting/scan path trusts it.
```
The same blob with a group-matching `script_pubkey` but fabricated `outpoint`/`value` passes even the `multisig` check and is committed into the signed sighash via `Prevouts::All`, yielding an invalid transaction that consumes a signing round.
