### Title
Unpermissioned `donateRewards` repeated small calls truncate `rewardPerTokenStored`, permanently freezing part of intended staker yield - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool.sol` (and its analogs `BaseRewardPoolV2.sol`, `mWOMSVBaseRewarder.sol`) expose a `donateRewards(uint256 _amountReward, address _rewardToken)` function that is callable by **any wallet**, with no `onlyManager`/`onlyOperator` restriction, and internally calls `_provisionReward`, which updates the global `rewardInfo.rewardPerTokenStored` accumulator using integer division:

```solidity
rewardInfo.rewardPerTokenStored =
    rewardInfo.rewardPerTokenStored +
    (_amountReward * 10**stakingDecimals()) /
    this.totalStaked();
``` [1](#0-0) 

This is structurally identical to the reported `TickLogic.sol` bug: a fixed-point division that rounds down is applied to an accumulator that is updated incrementally on every user-triggered call, rather than being computed once over the aggregate amount.

### Finding Description
`_provisionReward` computes the increase to `rewardPerTokenStored` as `(_amountReward * 10**stakingDecimals()) / totalStaked()`, rounding down [2](#0-1) . The remainder from this division (up to `totalStaked() - 1` wei of scaled precision) is discarded and never tracked anywhere — unlike the `totalStaked() == 0` branch, which correctly queues the entire amount into `queuedRewards` for later distribution [3](#0-2) . Once `totalStaked() > 0`, any truncation is permanently lost: it is not carried forward and not returned to the caller.

Because the same reward token can be donated many times, splitting one large donation `X` into `N` smaller donations of `X/N` compounds this truncation `N` times instead of once, exactly mirroring the `yieldFactor` truncation pattern in the report. The `_amountReward` tokens are still fully pulled from the caller via `safeTransferFrom` [4](#0-3) , but only the truncated, smaller `rewardPerTokenStored` delta is credited to stakers — the difference sits in the pool's token balance forever, unreachable by any staker (there is no owner/manager sweep of this dust; it is never re-queued), so it is a permanent loss of intended yield to legitimate stakers.

Any actor — the donor themself, or a third party who wants to grief the reward pool — can trigger this simply by calling the unpermissioned `donateRewards` function in a loop with dust-sized amounts, at their own gas cost, exactly as described in the report's exploit scenario (attacker splits a fixed amount into many small calls instead of one).

The identical `rewardPerTokenStored` truncation logic, guarded the same way, is repeated in `BaseRewardPoolV2.sol` (`_provisionReward`, lines 290-314) and `mWOMSVBaseRewarder.sol` (`_provisionReward`, lines 305-328) [5](#0-4) [6](#0-5) , both of which also expose an unpermissioned `donateRewards` entry point.

### Impact Explanation
This causes a permanent, unrecoverable loss ("freezing") of a fraction of reward-token yield that stakers are otherwise entitled to. While the per-call rounding error is at most `totalStaked()-1` scaled units (bounded by `10**stakingDecimals()`), it is unboundedly compoundable: a griefer or fee-sensitive integrator can split any donation into arbitrarily many small `donateRewards` calls, permanently stranding tokens that were transferred into the pool but never reflected in any user's claimable balance. This matches the report's core harm category — theft/permanent freezing of unclaimed yield belonging to legitimate stakers — since the truncated wei amounts are neither claimable by stakers nor recoverable by the protocol.

### Likelihood Explanation
Likelihood is moderate-to-low in practice: the effect per split is small relative to gas cost of extra transactions, similar to the original report's note that the exploit is only economically worthwhile at scale (hundreds of transactions) or for a griefer motivated purely by protocol disruption rather than profit. `donateRewards` requires no privilege and no owner/manager role, so the attack path is fully reachable by an ordinary wallet at any time. The truncation is deterministic and occurs on every single `_provisionReward` invocation whenever `totalStaked() > 0`, so no special preconditions are needed beyond a live reward pool.

### Recommendation
- Track truncation remainders (e.g., maintain a `pendingDust` accumulator per reward token, similar to `queuedRewards`, and roll it into the next `_provisionReward` calculation) so no precision is permanently lost regardless of how many calls are used to donate a given total.
- Alternatively, increase the internal precision of `rewardPerTokenStored` (e.g., scale by an additional large constant like `1e18` regardless of `stakingDecimals()`) to shrink the per-call truncation to negligible amounts.
- Add invariant/fuzz tests verifying that donating amount `X` via one call versus via `N` smaller calls yields the same (or negligibly different) total claimable rewards for stakers.

### Proof of Concept
1. Deploy a `BaseRewardPool` with a reward token of low decimals (e.g., 6, like USDC) and `totalStaked()` set to a value close in magnitude to typical donation amounts (so that `_amountReward * 10**stakingDecimals() / totalStaked()` has a large remainder relative to the quotient).
2. Call `donateRewards(X, token)` once with `X` = total intended reward; record resulting `rewardPerTokenStored` and thus total claimable amount across stakers.
3. Reset state (or run a parallel pool with identical `totalStaked()`), then call `donateRewards(X/N, token)` `N` times summing to the same `X`; record the resulting `rewardPerTokenStored`.
4. Compare: the `N`-call scenario's cumulative `rewardPerTokenStored` (and hence total claimable rewards) is strictly lower than the single-call scenario, with the difference proportional to `N`, even though the pool's on-chain token balance increased by the same `X` in both cases — demonstrating stranded, unclaimable tokens exactly as in the `TickLogic.sol` report.     function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
