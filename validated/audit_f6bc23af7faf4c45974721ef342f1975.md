### Title
`SolverAccount._containsFillOrder` scans only the ERC-7821 batch calldata shape, letting a standard-signature UserOp reach `fillOrder` through the single-call mode - ([File: evm/src/apps/intentsv2/SolverAccount.sol])

### Summary
`SolverAccount.validateUserOp` uses `_containsFillOrder(op.callData)` as a guard: when the UserOp is authorized with a plain 65-byte ECDSA signature (the "standard" path that skips the `select()`/session-key ceremony), any UserOp whose calldata contains a call to `IntentGatewayV2.fillOrder` must be rejected, because a publicly-known signed bid could otherwise be replayed by anyone to consume the solver's nonce and gas. The guard, however, decides whether `fillOrder` is present purely by pattern-matching the raw shape of `op.callData` — exactly the kind of context/selector-shape assumption that broke in the external Nexus report, where a hook's `preCheck`/`postCheck` misidentified a sensitive operation because it inspected `msg.data`/`msg.sender` from the wrong execution path instead of the actual operation being performed.

### Finding Description
`_containsFillOrder` only recognizes one specific encoding of ERC-7821's `execute(bytes32 mode, bytes executionData)`: [1](#0-0) 

It (1) requires the top-level selector to be `ERC7821.execute.selector`, and (2) unconditionally decodes `executionData` as `Execution[]` — i.e. it hardcodes the **batch call-type** (`CALLTYPE_BATCH`, mode byte `0x01`) encoding used in the account's own test helper: [2](#0-1) 

ERC-7821 (the standard `SolverAccount` inherits and that its own `_erc7821AuthorizedExecutor` override implements) defines more than this one shape: the mode byte also selects a **single call-type** (`CALLTYPE_SINGLE`), whose `executionData` is encoded as a single `(target, value, data)` tuple rather than an `Execution[]` array. Because `_containsFillOrder` assumes the batch encoding unconditionally, an `execute()` call built with the single-call mode targeting `IntentGatewayV2.fillOrder` directly does not decode into the expected `Execution[]` shape that the scanner is looking for, so the scanner's local view of "does this calldata call `fillOrder`" diverges from what the account's own ERC-7821 execution engine will actually do when `EntryPoint` later invokes `op.callData`. This is the same class of bug as the Nexus report: a security decision keyed off the *shape* of calldata/selector rather than off the *actual dispatched operation*, evaluated on one path (validation) while the real work happens on a structurally different path (execution) that the guard never modeled.

The intended purpose of the check (per the inline comment) is exactly to prevent someone from re-submitting a solver's publicly-signed 65-byte bid to force a `fillOrder` call outside the `select()`/session-key flow, consuming the solver's nonce/gas without their consent: [3](#0-2) 

That protection is defeated for any `execute()` call using the single-call mode, since `_containsFillOrder` never returns `true` for that shape and validation falls straight through to standard ECDSA verification.

### Impact Explanation
An unprivileged party who observes a solver's publicly broadcast, validly-signed 65-byte bid (any UserOp signed with the solver's key over a `userOpHash`) can re-encode the same `fillOrder` call using ERC-7821's single-call mode instead of the batch mode, submit it through `EntryPoint`, and have `validateUserOp` accept it without detecting the embedded `fillOrder` call. This forces execution of a state-changing call (`fillOrder`) on the solver's behalf that the account explicitly tries to forbid on this signature path, consuming the solver's UserOp nonce and gas allowance without their intended authorization — the exact griefing the guard exists to stop, now reachable via an unmodeled but standards-compliant calldata shape. Whether this also results in direct fund loss depends on `IntentGatewayV2`'s own `solverSelection` transient-storage check at `fillOrder` time (which independently reverts if `select()` was never staged); when that governance-configured protection is disabled, the bypass additionally exposes the solver's account to an unauthorized fill using its own escrowed liquidity.

### Likelihood Explanation
No privileged actor, relayer, or prover is required — a normal EntryPoint bundler or any address holding the leaked/observed calldata of a public bid can submit it. Building single-call-mode `execute()` calldata is a standard, spec-compliant ERC-7821 encoding, not a malformed or edge-case input, so bundlers will happily include it.

### Recommendation
Do not special-case one ERC-7821 encoding. Instead of re-parsing `op.callData` to guess whether `fillOrder` will be called, either (a) decode the mode byte and branch to the correct executionData layout for every ERC-7821 call type (`CALLTYPE_SINGLE`, `CALLTYPE_BATCH`, and any delegatecall variant) before scanning for `INTENT_GATEWAY_V2`/`FILL_ORDER_SELECTOR`, rejecting any unrecognized mode outright rather than treating it as "no fillOrder present," or (b) perform the fillOrder restriction at execution time (e.g., a transient-storage flag set only when the standard-ECDSA validation path is used, checked by `IntentGatewayV2.fillOrder` itself) so the guard is enforced against the operation actually dispatched rather than a static prediction of it.

### Proof of Concept
1. Solver signs and publishes a standard UserOp bid: `signature` = 65-byte ECDSA over `userOpHash`, `callData = execute(mode=CALLTYPE_BATCH, executionData=abi.encode([Execution{target: INTENT_GATEWAY_V2, data: fillOrderCalldata}]))`. Per the code's own logic, if this exact batch were submitted, `_containsFillOrder` would return `true` and `validateUserOp` would return `SIG_VALIDATION_FAILED`.
2. Attacker re-encodes the identical intent using the single-call mode instead: `callData' = execute(mode=CALLTYPE_SINGLE, executionData=abi.encode(INTENT_GATEWAY_V2, 0, fillOrderCalldata))`, keeping the same 65-byte solver signature (it covers only `userOpHash`, which is unaffected by this re-encoding choice under the account's `_rawSignatureValidation`).
3. Attacker submits `callData'` with the original signature through `EntryPoint`. `_containsFillOrder(callData')` decodes `executionData` under the hardcoded `Execution[]` assumption, fails to recognize the single-call shape, and returns `false`.
4. `validateUserOp` falls through to `super.validateUserOp`, which succeeds (signature is valid over `userOpHash`), and `EntryPoint` proceeds to execute `callData'`, which the account's ERC-7821 execution engine correctly dispatches as a single call to `fillOrder`, exactly the operation the guard was meant to block on this signature path — with the outcome bounded only by whether `IntentGatewayV2`'s own `solverSelection` transient-storage check happens to be enabled for that deployment.

    function _containsFillOrder(bytes calldata callData) private view returns (bool) {
        if (callData.length < 4 || bytes4(callData[0:4]) != EXECUTE_SELECTOR) return false;

        (, bytes memory executionData) = abi.decode(callData[4:], (bytes32, bytes));
        Execution[] memory calls = abi.decode(executionData, (Execution[]));

        for (uint256 i = 0; i < calls.length; i++) {
            bool hasFillOrder = calls[i].target == INTENT_GATEWAY_V2 && bytes4(calls[i].callData) == FILL_ORDER_SELECTOR;
            if (hasFillOrder) return true;
        }
        return false;
    }
