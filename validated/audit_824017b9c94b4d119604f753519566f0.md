### Title
`ReceivedOutput::read` accepts a spoofed `script_pubkey`, reporting funds "received" that are not spendable by the group key - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
CVE-2025-43228 is an address-bar spoofing bug: the UI presents an identity (origin) that does not match the actual destination. The analog in Serai is `ReceivedOutput`, which claims "these funds belong to group key + offset" purely by assertion. `ReceivedOutput::read` deserializes `(offset, TxOut, OutPoint)` from untrusted bytes without checking that `output.script_pubkey == p2tr_script_buf(key + G * offset)`. The claimed identity (the script that the wallet displays as "received to us") is thus decoupled from what actually controls the funds — the same spoofing primitive, mapped onto Serai's deposit-receipt shape.

### Finding Description
`ReceivedOutput` stores three independently supplied fields: a scalar `offset`, an arbitrary `TxOut`, and an arbitrary `OutPoint` (`networks/bitcoin/src/wallet/mod.rs:90-97`). The constructor path `Scanner::scan_transaction` guarantees the invariant `output.script_pubkey == p2tr_script_buf(self.key + G*offset)` via the `self.scripts` map (`mod.rs:205-211`). The deserialization path does not: `ReceivedOutput::read` calls `Secp256k1::read_F` for the offset and `consensus_decode` for `TxOut`/`OutPoint` and returns the triple verbatim (`mod.rs:122-134`). No key is even available to `read`, so no binding check is possible at that layer.

Downstream, `SignableTransaction::new` consumes `Vec<ReceivedOutput>` and trusts `input.output.value` for fee/change math and `input.offset` for key derivation (`networks/bitcoin/src/wallet/send.rs:175-176`). The only integrity check happens later in `SignableTransaction::multisig`, which merely returns `None` when `p2tr_script_buf(offset.group_key()) != prevouts[i].script_pubkey` (`send.rs:277-279`). That check proves the funds are *unspendable*, it does not undo the fact they were already recorded as received.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (an explicitly in-scope sink) constructs a receipt claiming value `V` received at `offset`, while `output.script_pubkey` pays an attacker-controlled script — or any script not derived from `key + G*offset`. Accounting layers that treat a parsed `ReceivedOutput` as evidence of deposit (as `get_outputs`/`ScannerEvent::Block` consumers do with `output.balance()`) will credit funds that the threshold group can never sign for: `multisig()` rejects the input, leaving the credited balance permanently unspendable. This is the accepted impact class "funds reported received that are not spendable", and it is the direct analog of a browser displaying a trusted origin while rendering attacker content: the receipt displays "paid to Serai key" while the UTXO pays elsewhere.

### Likelihood Explanation
Reachable by any party able to supply serialized `ReceivedOutput` bytes to a wallet/scanner consumer — the format is a plain, self-describing serialization (`mod.rs:136-148`) designed to cross process/network boundaries. Exploitation requires no key material, no threshold collusion, and no malformed-curve tricks; just inconsistent fields. Severity is Medium: it corrupts deposit accounting and bricks the reported funds rather than enabling theft or signature forgery, since `multisig()` fails closed.

### Recommendation
Make the spoofed state unrepresentable. Either (a) bind the output to the key at read time by passing the scanner's `key` into a checked constructor that verifies `p2tr_script_buf(key + G*offset) == output.script_pubkey`, or (b) add a `ReceivedOutput::verify(key)` method and require callers of `SignableTransaction::new` to run it before crediting balances. At minimum, document that `ReceivedOutput::read` output is untrusted and must not be used for accounting until `multisig()`-equivalent key-binding verification succeeds.

### Proof of Concept
```rust
// networks/bitcoin — conceptual PoC
let key = ProjectivePoint::random(&mut OsRng);           // group key
let attacker_script = ScriptBuf::new_p2pkh(&attacker_pkh); // NOT derived from key
let forged = ReceivedOutput {
  offset: Scalar::ZERO,                                  // claims "paid to group key"
  output: TxOut { value: Amount::from_sat(100_000), script_pubkey: attacker_script },
  outpoint: OutPoint::new(real_txid, 0),                 // real, attacker-funded UTXO
};
let bytes = forged.serialize();
let parsed = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// `parsed` reports 100k sats "received" at offset 0.
// SignableTransaction::new accepts it for balance/fee math;
// SignableTransaction::multisig later returns None — credited funds are unspendable.
```
The honest path `scan_transaction` can never produce this object (`mod.rs:205-211`), but `read` reconstructs it faithfully (`mod.rs:122-134`), demonstrating the missing identity-binding check analogous to the unvalidated displayed origin in CVE-2025-43228.
