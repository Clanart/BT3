### Title
`Scanner::scan_block` reports coinbase outputs as received funds that are unspendable for 100 blocks - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report describes a "fake event" class: an unprivileged caller invokes a function that emits events trusted by downstream consumers, without any check that the emitter is legitimate. The Serai analog lives in `Scanner`, the component that turns on-chain data produced by arbitrary, unprivileged Bitcoin actors into `ReceivedOutput` "you received spendable funds" events consumed by the signing pipeline.

`Scanner::scan_block` iterates `block.txdata` including index 0, the coinbase transaction, which any miner fully controls. A matching coinbase output produces a `ReceivedOutput` indistinguishable from a normal deposit, yet it is bound by Bitcoin's 100-block coinbase maturity rule and cannot be spent — any transaction spending it is consensus-invalid. The library's own downstream code (`processor`) had to special-case this by skipping `block.txdata[1 ..]` itself, and a caller using `scan_block` (the natural, documented block-scanning API) receives funds it cannot actually spend.

### Finding Description
- `Scanner::scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` is in `self.scripts`, with no notion of output maturity or spendability (`networks/bitcoin/src/wallet/mod.rs:199-214`).
- `Scanner::scan_block` feeds `block.txdata` wholesale into `scan_transaction`, so `txdata[0]` — the coinbase — is scanned identically to regular transactions (`networks/bitcoin/src/wallet/mod.rs:221-227`).
- The doc comment acknowledges the outputs are "bound by maturity" and pushes a mandatory post-processing step onto the caller (`networks/bitcoin/src/wallet/mod.rs:216-220`), but nothing in the type system or API enforces it; `scan_block` is a public API returning `Vec<ReceivedOutput>` with immature outputs mixed in silently.
- Downstream, `ReceivedOutput`s feed `SignableTransaction::new`, which builds inputs from `input.outpoint` and has the FROST group sign them (`networks/bitcoin/src/wallet/send.rs:177-185, 373-391`). A spend of a coinbase outpoint younger than 100 blocks produces a consensus-invalid transaction — the signed "payment" can never confirm.

### Impact Explanation
An unprivileged miner (any Bitcoin actor who mines a block, no Serai role required) sends a coinbase output to the scanner's key. The scanner reports it as received balance. If the consumer aggregates/spends scanned outputs without a caller-side maturity filter, it will construct and threshold-sign a transaction spending an immature coinbase outpoint. That transaction is rejected by every Bitcoin node, burning the signing round and, depending on accounting, crediting funds that do not exist as spendable UTXOs — "funds reported received that are not spendable."

### Likelihood Explanation
Requires a miner to target a known Serai deposit address, which any miner can do at no marginal cost (the coinbase output is theirs to shape). The trigger on the consumer side is using `scan_block` — the public API — rather than manually slicing `txdata[1 ..]` and calling `scan_transaction`, a footgun the API actively invites since the maturity filter is only described in a doc comment.

### Recommendation
Skip `block.txdata[0]` inside `scan_block` (returning maturity-burdened coinbase outputs via a separate, explicitly-named API if needed), or tag `ReceivedOutput` with a maturity height so consumers cannot accidentally treat immature outputs as spendable. Do not rely on every caller reimplementing the coinbase filter.

### Proof of Concept
```rust
// A miner crafts a block whose coinbase (txdata[0]) pays to the scanned key.
let block: Block = /* block with coinbase output to p2tr_script_buf(key) */;
let outputs = scanner.scan_block(&block);
// outputs[0] is a ReceivedOutput whose outpoint is the coinbase txid.
// SignableTransaction::new(vec![outputs[0].clone()], &payments, change, None, fee)
// produces a transaction that FROST-signs successfully, yet every Bitcoin node
// rejects it: coinbase outputs require 100 confirmations (BIP-30/COINBASE_MATURITY).
```
Contrast with `processor`'s network adapter, which was forced to implement the missing check itself by slicing `block.txdata[1 ..]` before scanning (`processor/src/networks/bitcoin.rs:690-692`), confirming the burden and the trap are real.
