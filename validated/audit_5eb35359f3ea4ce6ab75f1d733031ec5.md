### Title
Attacker-controlled `ReceivedOutput`/`payments` values are trusted and summed in unchecked arithmetic, letting a forged or overflowing value bypass the solvency check and report funds/fee that are not real - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` consumes `ReceivedOutput`s and `payments` which derive from untrusted bytes (`ReceivedOutput::read`, the wallet/networking input path). It computes `input_sat`, `payment_sat`, and `needed_fee` with plain `sum::<u64>()` and `*` arithmetic and then performs the only solvency check — `input_sat < payment_sat + needed_fee` — on those unchecked values, before signing. This mirrors the Perennial bug class: the guard ("collateral") is evaluated against a quantity unrelated to the value actually credited/committed at "settlement" (the signed transaction and `fee()`/`needed_fee` reported upstream). There is no bound that `output.value` corresponds to a real UTXO, nor that the sums stay within u64.

### Finding Description
- `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) deserializes `offset`, `output` (`TxOut` with an arbitrary `value`), and `outpoint` entirely from attacker-supplied bytes, with no consistency check that the outpoint exists, that `output.value` matches the on-chain UTXO, or that `offset` actually derives the script_pubkey in `output`.
- In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:175-185`), `input_sat` is summed directly from `input.output.value`, and `prevouts` (used by `fee()` at lines 138-141) are taken verbatim from the same untrusted outputs.
- `payment_sat` (line 187) and `needed_fee = fee_per_vbyte * vbytes` (line 206) are computed with plain addition/multiplication; `fee_per_vbyte` and each `payment.1` are caller-controlled u64s. In release builds these wrap, so an attacker can make `payment_sat + needed_fee` wrap to a small value and pass `input_sat < (payment_sat + needed_fee)` (line 215) — the analog of passing Perennial's collateral check with a huge `intent.price`.
- The change computation (`input_sat.checked_sub(payment_sat + fee_with_change)`, line 228) only checks the subtraction; the inner sum can wrap so that a huge "change" output is pushed to an attacker-chosen `ScriptBuf`, or conversely legitimate change is silently dropped.
- `median_fee` (`processor/src/networks/bitcoin.rs:388-414`) similarly trusts `in_value - out` per transaction — reinforcing the same class — though it additionally requires miner influence.

### Impact Explanation
An unprivileged party who supplies serialized `ReceivedOutput` bytes (or who supplies the `payments`/`fee_per_vbyte` parameters on the reachable path) can:
- Have the multisig machinery treat fabricated inputs as real, causing `fee()`/`needed_fee` to report an arbitrary "fee paid" — funds reported as received/spent that are not spendable on-chain (the exact analog of fake collateral being converted into inflated settlement PnL).
- Force signing of a transaction whose committed prevout values (Taproot `Prevouts::All` commits to each input's amount) or output totals do not correspond to real value — either producing consensus-invalid transactions that stall the withdrawal pipeline, or mis-accounting change/fees.
The threshold multisig signs exactly what is constructed here; nothing downstream re-validates the economic consistency of inputs vs. real UTXOs.

### Likelihood Explanation
Reachable wherever `ReceivedOutput`/`SignableTransaction` inputs cross a trust boundary (network deserialization, processor-supplied outputs, or external burn/withdrawal parameters). Exploitation requires no key material, no collusion, and no validator misbehavior — only control over the value/amount fields. Impact is bounded by consensus validity (inflated-input transactions cannot confirm), but the accounting discrepancy and the ability to pass the solvency check with fabricated value are real and unauthenticated.

### Recommendation
- In `ReceivedOutput::read` / at `SignableTransaction::new` entry, verify each input: recompute the script_pubkey from `key + offset*G` and compare to `output.script_pubkey`, and validate `outpoint`/`output.value` against the confirmed chain state rather than trusting the serialized bytes.
- Use `checked_add`/`checked_mul`/`checked_sum` for `input_sat`, `payment_sat`, `needed_fee`, `fee_with_change`, and the change computation; return `TransactionError` on overflow instead of relying on wrapping behavior.
- Bound `fee_per_vbyte` and each payment to sane maximums before arithmetic, analogous to bounding `intent.price` against `lastVersion.price`.

### Proof of Concept
```rust
// networks/bitcoin crate — demonstrates the unchecked-sum bypass
// Forge a ReceivedOutput with an inflated value
let mut buf = Vec::new();
buf.extend_from_slice(Scalar::ZERO.to_repr().as_ref());            // offset
let fake_txout = TxOut {
  value: Amount::from_sat(u64::MAX),                                // fabricated value
  script_pubkey: p2tr_script_buf(key).unwrap(),                     // matches scanner
};
buf.extend_from_slice(&serialize(&fake_txout));
buf.extend_from_slice(&serialize(&OutPoint::new(Txid::all_zeros(), 0)));
let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();

// Solvency check uses input_sat = u64::MAX — passes with any payment set
let payments = vec![(attacker_script.clone(), 1000u64)];
let tx = SignableTransaction::new(vec![forged], &payments, Some(change), None, 20);
// tx is Ok(...): fee() reports u64::MAX - outputs, yet no such UTXO exists.

// Overflow bypass:
let huge = u64::MAX - 100;
let payments = vec![(attacker_script.clone(), huge), (attacker_script.clone(), huge)];
// payment_sat wraps to a small value → `input_sat < payment_sat + needed_fee` fails to fire,
// and `input_sat.checked_sub(payment_sat + fee_with_change)` yields ~input_sat as change.
```
