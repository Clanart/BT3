### Title
Partial-commit line selection is applied against a freshly re-fetched diff instead of the diff the user reviewed, allowing silent inclusion of unintended/attacker-modified content in a commit - (File: `app/src/lib/git/apply.ts`)

### Summary
The bug-class in the external report is: an "index" cached at time T1 is later combined with state that has moved on to T2 without being refreshed, producing a result computed against mismatched baselines. GitHub Desktop has a structurally identical pattern in the partial-commit ("stage selected lines") flow: the user's line selection (`DiffSelection`, an index/bitset keyed to absolute line numbers of a specific diff) is computed against one diff snapshot, but at staging time the code fetches a **brand-new** diff and applies the old selection indices to it, with no revalidation that the two diffs still line up.

### Finding Description
The file's partial-commit selection state (`WorkingDirectoryFileChange.selection`) is a `DiffSelection` object that tracks selected/deselected line numbers by their **absolute position** in a specific diff (`h.unifiedDiffStart + index`), as built in `updateChangesWorkingDirectoryDiff`: [1](#0-0) 

The code comment there explicitly acknowledges the danger: "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..." — i.e. Desktop only prunes now-invalid line indices from the *previous* diff snapshot; it does not re-validate that a given index still refers to the *same content* when the diff is refreshed.

Crucially, this reconciliation only happens opportunistically when the UI proactively reloads the diff (`updateChangesWorkingDirectoryDiff`, triggered by status polling/selection changes). It is **not** re-run immediately before staging. When the user actually commits, `stageFiles` routes partially-selected files to `applyPatchToIndex`: [2](#0-1) 

`applyPatchToIndex` does not reuse the diff object the user was shown/selected against. It fetches a **new** diff via `getWorkingDirectoryDiff` at the moment of staging, then formats a patch using that new diff combined with the (older) `file.selection`: [3](#0-2) 

`formatPatch` walks the *new* diff's hunks and lines, and for each line asks `file.selection.isSelected(absoluteIndex)` — the absolute index computed against the *new* hunk layout, but the selection bitset was populated against the *previous* hunk layout: [4](#0-3) 

If the working-directory file content changes between the moment the user reviews/selects lines and the moment `applyPatchToIndex` runs (e.g. seconds later, while the commit message is being typed), hunk boundaries and `unifiedDiffStart` offsets shift. The stale `divergingLines` set (line numbers) is then applied to the new hunk geometry, so `isSelected()` can return `true`/`false` for physically different lines than what the user actually clicked. There is no hash/content check tying the `DiffSelection` to the diff it was derived from — only line numbers are stored (`app/src/models/diff/diff-selection.ts:41-120`), and `updateChangesWorkingDirectoryDiff`'s reconciliation logic only removes indices that no longer exist; it does nothing about indices that still exist but now point to different content.

### Impact Explanation
This is a "silent corruption of what the user commits" issue, matching the requested valid-impact class. A working directory file can be modified by processes the attacker (via a malicious cloned/fetched repository) can trigger without local/physical access or admin rights — most notably Git's own hook and filter machinery that a cloned repository can ship (e.g. `post-checkout`, `post-merge`, smudge/clean filters configured via `.gitattributes`/`.git/hooks` that Desktop will invoke as part of normal fetch/checkout/pull operations already exercised by `checkoutCommit` and `updateSubmodulesAfterOperation`, which explicitly set up per-operation environments and error handling for exactly this class of external process). If such a hook or filter rewrites a tracked file shortly after the diff is displayed (e.g. triggered by a background fetch, submodule update, or a race with an editor auto-format on save), the user can end up committing/pushing content they never reviewed or explicitly deselected — e.g. inadvertently including malicious lines that were hidden from the diff they approved, or excluding lines they intended to commit. Because the result silently becomes part of a real commit (and potentially a push), this can propagate unreviewed/attacker-influenced content into the project history.

### Likelihood Explanation
Low-to-medium, similar in character to the original finding ("needs some specific conditions... but technically valid"). It requires:
1. A partially-selected (not "select all") file.
2. The working tree content for that file to change between the time the diff/selection was established and the time the commit patch is generated.
3. A source of file mutation outside the user's own edits within that window — realistically a git hook, smudge filter, submodule operation, or another background Desktop refresh that overlaps with the commit action.

This is a narrow timing window but is not implausible given Desktop's asynchronous refresh cycle (`_loadStatus` → `updateChangesWorkingDirectoryDiff` runs independently of the commit action), and a hostile repository fully controls what hooks/filters it ships.

### Recommendation
- Store a content-derived identifier (e.g. hash of the diff's raw hunks, or the diff text itself) alongside `DiffSelection`, and re-fetch a fresh diff plus revalidate the selection against it immediately before building the patch in `applyPatchToIndex`, rejecting/re-prompting instead of silently proceeding if the diff has changed since the last displayed selection.
- Alternatively, always regenerate the patch from the exact diff object last shown to the user (cached in `changesState.selection.diff`) rather than re-fetching a new diff at staging time, and fail loudly if that cached diff is stale relative to current on-disk content.

### Proof of Concept
Conceptual repro (cannot be fully driven without a live Desktop instance/hooks, but the code path is deterministic):
1. Open a repository with a tracked file `foo.txt` containing 10 lines; modify a few lines so Desktop shows a diff with 3 hunks.
2. In the Changes view, partially select only specific lines to include in the commit (`DiffSelection.withLineSelection`), leaving the diff open (`changesState.selection.diff` populated, per `app-store.ts:3495-3512`).
3. Before invoking commit, have an external process (simulating a malicious repo's `post-checkout`/smudge filter) rewrite `foo.txt` so hunk boundaries shift (e.g., insert lines earlier in the file).
4. Trigger commit → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-61`) fetches a *new* diff via `getWorkingDirectoryDiff` and calls `formatPatch(file, diff)` using the *old* `file.selection` indices (`app/src/lib/patch-formatter.ts:143-171`).
5. Inspect the resulting commit: it includes/excludes lines that do not correspond to what was highlighted as "selected" in the UI before step 3, demonstrating the stale-index-vs-fresh-state mismatch.
