### Title
Attacker transaction in the same block overwrites `presumed_origin`/`data` of all previously scanned outputs, enabling deposit-instruction spoofing and refund theft - (File: processor/src/networks/bitcoin.rs)

### Summary
In `Bitcoin::get_outputs`, the `outputs` accumulator and the origin/data population loop are scoped incorrectly: for every transaction in the block after the first matching deposit, `presumed_origin` and `data` are re-derived and overwritten onto *all* previously collected outputs — including outputs produced by entirely unrelated transactions.

### Finding Description
In `get_outputs` (`processor/src/networks/bitcoin.rs:686-737`), `outputs` is declared once before iterating `block.txdata[1 ..]`. After scanning each tx, the code checks `if outputs.is_empty() { continue }` — but `outputs` is cumulative, so once any earlier tx produced an output, this check passes for every subsequent tx in the block. The subsequent block then:

- derives `presumed_origin` from `tx.input[0]`'s prevout `script_pubkey` (lines 714-728), and
- derives `data` via `Self::extract_serai_data(tx)` (line 730),

and writes both into `for output in &mut outputs` (lines 731-736) — overwriting the values belonging to the earlier deposit transaction.

So a transaction that produced **zero** Serai outputs still overwrites the origin refund address and the embedded `InInstruction` `data` of every earlier scanned output in that block. Even non-adversarially, two Serai deposits in one block cause the first deposit's instruction and refund origin to be replaced by the second deposit's.

### Impact Explanation
`presumed_origin` flows into `instruction_from_output` (`processor/src/multisigs/mod.rs:45-92`), where it becomes the refund `origin` (`instruction.origin.or(presumed_origin)`), and `output.data` is decoded as the `Shorthand`/`RefundableInInstruction` that determines what the deposited balance does (mint, swap, refund target per `spec/integrations/Instructions.md`). An unprivileged attacker who gets a transaction into the same block *after* a victim's deposit can:

- Set `data` to an attacker-crafted `Shorthand` containing `origin: <attacker address>` plus an instruction designed to fail or a `Dex` call routing proceeds to an attacker Serai address — redirecting the victim's deposited balance.
- Or leave `data` empty/invalid so the output falls back to `presumed_origin`, which they set via their `tx.input[0]` prevout address — so the refund plan (`PlanFromScanning::Refund`, `processor/src/multisigs/mod.rs:903-907`) sends the victim's coins to the attacker.

Ordering is achievable since Bitcoin only requires an attacker's tx to appear after the victim's in `txdata`; the attacker can also simply deposit-and-overwrite for anyone depositing in the same block, or exploit fee-based ordering.

### Likelihood Explanation
Requires the attacker's transaction to be ordered after the victim's deposit within the same confirmed block that the processor scans (after `CONFIRMATIONS`). This is feasible via mempool observation and fee selection, and occurs naturally whenever two deposits share a block. No collusion, no validator compromise — purely public Bitcoin transactions.

### Recommendation
Scope the population pass to the outputs produced by the current transaction: collect `tx_outputs` inside the loop, skip when `tx_outputs.is_empty()`, and only assign `presumed_origin`/`data` to `tx_outputs` before extending `outputs`. Alternatively `break`/iterate per-tx so unrelated later transactions cannot mutate earlier outputs' metadata.

### Proof of Concept
1. Victim broadcasts tx A paying to `external_address(key)` with OP_RETURN `data` encoding `Shorthand::transfer(None, victim_serai_addr)`. Confirmed in block B at index i.
2. Attacker broadcasts tx B' (index j > i in the same block) whose `input[0]` spends an attacker-owned output (attacker's `script_pubkey`) and whose `data` (via `extract_serai_data`, e.g. OP_RETURN) encodes `Shorthand::Raw(RefundableInInstruction { origin: Some(attacker_addr), instruction: <fails> })`.
3. `get_outputs`: after tx A, `outputs = [victim_output]` with correct origin/data. On tx B', `outputs.is_empty()` is false, so `victim_output.presumed_origin` is set to the attacker's address and `victim_output.data` is set to the attacker's shorthand.
4. `instruction_from_output` returns origin = attacker address; on failure the scheduler emits `PlanFromScanning::Refund(victim_output, attacker_addr)` (`processor/src/multisigs/scheduler/utxo.rs:587-605`), and the multisig signs a transaction sending the victim's deposit to the attacker.
