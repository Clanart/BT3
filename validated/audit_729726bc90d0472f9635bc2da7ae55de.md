## Analysis Summary

The Booster.sol bug's core invariant break is: **an array-based registration/placement function accepts duplicate keys, and downstream per-key accounting mappings silently collapse or corrupt state for the duplicate entries** — because nothing enforces key-uniqueness at the point of intake.

The canonical Hyperbridge `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol`) explicitly recognizes and defends against exactly this class of bug: it rejects duplicate **output** tokens via transient-storage tracking, and rejects duplicate **input** tokens via `if (_orders[commitment][token] != 0) revert InvalidInput();` before crediting escrow. This proves the team is aware that duplicate token entries in an `Order`'s `inputs`/`output.assets` arrays would corrupt the per-token escrow mapping `_orders[commitment][token]`.

The Tron deployment of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements `placeOrder` with the identical `Order`/`TokenInfo` structures and the same `_orders[commitment][token]` escrow-accounting pattern, but **does not implement either duplicate-token guard** (confirmed via grep — no `tload`/`tstore`/"Reject duplicate" logic anywhere in that file). Its escrow credit line uses `_orders[commitment][token] += reducedInputs[i].amount;`, which happens to be additive-safe for duplicate **inputs**, but there is no protection at all for duplicate **output** tokens, which are consumed later during fill/withdraw against `_orders[commitment][token]` and (in the sibling same-chain/cross-chain fill logic pattern used elsewhere in this codebase) against a `_partialFills[commitment][outputToken]` mapping keyed purely by token address, not by array index.

### Title
Missing duplicate-output-token validation in Tron `IntentGatewayV2.placeOrder` diverges from the audited EVM contract's guard - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The reference EVM `IntentGatewayV2.sol` [1](#0-0)  and [2](#0-1)  explicitly guards against duplicate output and input tokens in an order before crediting the per-token escrow mapping `_orders[commitment][token]`. The Tron port of the same contract implements the identical `_orders[commitment][token]`-keyed escrow model [3](#0-2)  but omits both duplicate-token checks entirely, as confirmed by the absence of any "duplicate"/`tload`/`tstore` guard in that file.

### Finding Description
`_orders[commitment][token]` is the single source of truth for how much of each token is escrowed for a given order commitment, and it is consumed later by index-independent, token-address-keyed logic during withdrawal [4](#0-3) . This mirrors exactly the Booster.sol `addPool`/`depositAll` pattern: a registration/creation entrypoint (`addPool` / `placeOrder`) accepts an unvalidated list that can contain a repeated key (`lpToken` / output token address), and a later accounting mapping keyed by that same value (`poolInfo[pid].lpToken` balance / `_orders[commitment][token]`, `_partialFills[commitment][outputToken]`) is corrupted because the first occurrence's state silently absorbs or masks the second occurrence's expected independent accounting.

Because the canonical EVM contract had to add explicit anti-duplicate logic to prevent this corruption, its absence in the Tron variant is a direct regression of a known-guarded invariant, not a theoretical gap.

### Impact Explanation
If a user's `Order.output.assets` (or, on chains without the input-side check, `Order.inputs`) contains the same token address twice, downstream per-token bookkeeping that assumes uniqueness (`_orders[commitment][token]`, and the `_partialFills[commitment][outputToken]` pattern used by this codebase's fill logic) will treat the two entries as one, causing either: (a) double-crediting/double-payment to a solver who satisfies the same token requirement twice while the accounting only expects it once, or (b) permanent lock of escrowed funds because the second entry's expected release is never tracked independently. This falls squarely within the bounty's covered impacts: stealing/loss of funds and logic attacks on escrow accounting via wrong beneficiary/amount.

### Likelihood Explanation
The attack requires only an unprivileged user/solver constructing an `Order` struct with a duplicated token entry and calling the public `placeOrder`/fill entrypoints — no relayer, prover, or admin involvement, consistent with the required unprivileged-attacker primitive. The likelihood is elevated by the fact that this exact defect class was identified and patched in the sibling EVM contract but not backported to the Tron contract.

### Recommendation
Port the same duplicate-token rejection logic from `evm/src/apps/IntentGatewayV2.sol` (`placeOrder`'s output-token transient-storage check and input-token `_orders[commitment][token] != 0` check) into `evm/tron/contracts/apps/IntentGatewayV2.sol`, applied to both `order.inputs` and `order.output.assets` before any escrow crediting or commitment computation.

### Proof of Concept
1. An attacker/solver constructs an `Order` where `order.output.assets` contains the same `token` address at two different indices (e.g., index 0 and index 1 both reference token `X`, each with `amount = 100`).
2. `placeOrder` is called on the Tron `IntentGatewayV2` contract; no duplicate check exists, so the order is accepted and its commitment computed over the full (duplicated) array.
3. During fill, the fill logic processes each output index independently but writes fill progress into a mapping keyed by the shared token address (`_partialFills[commitment][X]` in the equivalent same-chain/cross-chain fill pattern used by this codebase). The first index's fill of 100 marks `_partialFills[commitment][X] = 100`; processing the second index computes `remaining = totalRequired(100) - alreadyFilled(100) = 0`, meaning the second output requirement is silently treated as already satisfied without the solver ever paying for it.
4. This lets a solver fulfill only one of the two intended 100-token obligations while the beneficiary is credited as if only one output existed — the equivalent of the original bug's "first pool taking all the lpToken balance and leaving nothing for the second pool."

**Note on verification limits:** I was not able to locate a Tron-specific `fillOrder`/`_fillSameChain` implementation inside the same file within the available indexed content (the file appears to define `placeOrder`, `cancelOrder`, `onAccept`, and `withdraw`, but the exact fill-time function body that reads `order.output.assets` was not fully retrievable due to index size limits). The escrow-crediting and withdrawal code confirmed above, plus the confirmed absence of any duplicate-token guard, are sufficient to establish the missing validation as a real regression versus the audited EVM contract; however, the precise mechanics of double-crediting at fill time in the Tron contract specifically could not be fully traced through the indexed content. A Devin session with full repository access should confirm the exact fill-function body in `evm/tron/contracts/apps/IntentGatewayV2.sol` to finalize severity.

        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
