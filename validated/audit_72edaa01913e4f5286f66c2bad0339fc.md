### Title
`DkgConfirmer` signing removes the wrong map entry by confusing threshold index with MuSig index - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug-class analog to M-06 (wrong parameter passed where a specific identifier was expected) is present in `threshold_i_map_to_keys_and_musig_i_map` in `coordinator/src/tributary/signing_protocol.rs`. The function remaps a `HashMap<Participant, Vec<u8>>` keyed by threshold participant index into a new map keyed by the signer's MuSig index (`raw_i + 1`, i.e. the position in the sorted signer list). It then attempts to remove our own entry with `map.remove(&our_threshold_i)`, passing a **threshold-domain index** into a map keyed by **MuSig-domain indices**. Just as M-06 passed `rewardVault.asset()` where the Curve pool address was expected, this passes an identifier from the wrong domain, producing a panic or corrupted signer set during DKG confirmation signing.

### Finding Description
In `threshold_i_map_to_keys_and_musig_i_map`:

```rust
let our_threshold_i = spec
    .i(removed, <Ristretto as Ciphersuite>::generator() * our_key.deref())
    .expect("MuSig t-of-n signing a for a protocol we were removed from")
    .start;
assert!(map.insert(our_threshold_i, vec![]).is_none());
...
for (raw_i, (key, share)) in sorted.into_iter().enumerate() {
    let musig_i = u16::try_from(raw_i).unwrap() + 1;
    participants.push(key);
    map.insert(Participant::new(musig_i).unwrap(), share);
}

map.remove(&our_threshold_i).unwrap();
```

The rebuilt `map` is keyed by `Participant::new(musig_i)`, where `musig_i` is the signer's position (1-indexed) in the list of signers sorted by threshold index. `our_threshold_i`, however, is `spec.i(removed, our_key).start` — our index in the threshold key-share domain. These domains diverge whenever a validator controls more than one key share (`spec.i` returns a `Range<Participant>` of shares, and `MAX_KEY_SHARES_PER_SET` explicitly permits multiple shares per validator), and whenever the signer subset ordering differs from the threshold indexing.

Two concrete failure modes:

1. `our_threshold_i` is not a key in the MuSig-indexed map (its value exceeds the signer count, which happens whenever our threshold share index is greater than the number of validators). `map.remove(&our_threshold_i).unwrap()` then panics, crashing the coordinator during `share_internal`/`complete` for the DKG confirmation.

2. `our_threshold_i` collides with a *different* signer's `musig_i`. That signer's preprocess/share is silently dropped while our own entry (an empty `vec![]` placeholder inserted earlier) remains. In `share_internal`, `machine.read_preprocess(&mut vec![].as_slice())` fails on the empty bytes and the error is attributed via `.map_err(|_| participant)` to a participant index that is not ours — producing an `Err(Participant)` blaming an innocent validator, or downstream `FrostError::DuplicatedParticipant`/`MissingParticipant` mapped to `unreachable!()` panics in `share_internal`/`complete_internal`.

Additionally, the `participants` list returned is in threshold-sorted order, but the caller (`DkgConfirmer::share_internal`, `preprocess_internal`) ignores it and passes `spec.validators()` order to `musig(...)`, so the machine's `params.i` (position in validators order) and the map's `musig_i` keys (position in signer-sorted order) only coincide under lucky ordering — another instance of the same index-domain confusion.

### Impact Explanation
DKG confirmation requires this MuSig signing to succeed and correctly attribute blame. The wrong-index removal either panics the coordinator (`unwrap` on a missing key, or `unreachable!()` on `DuplicatedParticipant`/`MissingParticipant`) or returns `Err(Participant)` pointing at an innocent validator. Result: the `set_keys` confirmation signature cannot be produced — a liveness failure of key confirmation — and/or a correctly-behaving validator is flagged as having sent an invalid preprocess. Impact: Medium (protocol liveness / node crash, mirroring M-06's medium-severity "creation always fails" class).

### Likelihood Explanation
The bug triggers deterministically whenever `spec.i(removed, our_key).start` does not equal our position in the sorted signer list — i.e., whenever validators hold multiple key shares per validator (explicitly supported) or the signer subset/order diverges from threshold indexing. With a single share per validator and full participation the two index domains happen to coincide, so the bug is configuration-dependent rather than universal. Likelihood: Medium.

### Recommendation
Track our own MuSig index explicitly. When enumerating `sorted` to build the new map, record the `musig_i` assigned to our own (empty) entry — e.g. by comparing `key == our_pub_key` or by capturing the `raw_i` where the placeholder was inserted — and remove `Participant::new(our_musig_i)` instead of `our_threshold_i`. Alternatively, remove the placeholder from the threshold-indexed map *before* the remap (after sorting), so domain confusion is impossible. Also have callers use the returned `participants` list (threshold-sorted) consistently for the `musig(...)` construction so `params.i` and the map keys share one index domain.

### Proof of Concept
Consider a validator set where validators hold 2 key shares each (permitted by `MAX_KEY_SHARES_PER_SET`). Validators `V1, V2, V3` (us = `V3`) have threshold share ranges `1..=2`, `3..=4`, `5..=6`; `our_threshold_i = 5`. All three submit preprocesses; `sorted` has 3 entries, so the new map keys are `musig_i ∈ {1, 2, 3}`.

- `map.remove(&Participant::new(5)).unwrap()` → `None.unwrap()` → **panic** in `threshold_i_map_to_keys_and_musig_i_map`, aborting `DkgConfirmer::share_internal`/`complete`.

Variant with 4 validators and share ranges `1..=2`, `3..=4`, `5..=6`, `7..=8` (us = `V2`, `our_threshold_i = 3`): `map.remove(&3)` succeeds but deletes `V3`'s entry (musig_i 3), while our empty placeholder stays under musig_i 2. `share_internal` then calls `read_preprocess` on our empty `vec![]` and returns `Err(Participant(2))`, blaming the validator mapped to index 2 — a wrong-blame / failed-share outcome with no panic.

Both paths require only ordinary protocol participation (validators' preprocess/share messages and the set composition) — no malicious validator, leaked key, or broken BFT is needed to reach them.

Note: I was unable to read `TributarySpec::i`/`validators()` directly to confirm the exact share-to-validator index arithmetic; the multi-share divergence argument rests on `spec.i` returning a `Range<Participant>` and on `MAX_KEY_SHARES_PER_SET`, both evident in the code reviewed.
