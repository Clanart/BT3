### Title
Webhook shop identity spoofing via unsigned `X-Shopify-Shop-Domain` header - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` authenticates a webhook request purely by checking an HMAC over the raw POST body, using the app's single shared client secret. The shop identity that downstream code relies on (`shop_domain`) is read straight from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the HMAC computation. This is the same class of bug as the `AMPPkt.verify_origin()` issue: one field (`sender`/HMAC-over-body) is verified, but an adjacent, trust-bearing field (`previous_sender`/shop-domain header) is not bound to that verification and can be independently forged.

### Finding Description
`hmac_valid?` computes the HMAC exclusively over `request.raw_post` (the body): [1](#0-0) 

`WebhookVerification#verify_request` only checks that HMAC, and separately exposes a `shop_domain` helper that simply reads the header without any cross-check against the (HMAC-protected) body: [2](#0-1) 

Because `ShopifyApp.configuration.secret` is the app's single client secret shared across every shop that installs the app (not shop-specific), a valid HMAC only proves "this body was signed by Shopify for this app" — it does not bind the request to any particular shop. The `shop_domain` header is completely outside that signature.

The gem's own documentation instructs developers to build custom webhook controllers exactly this way, trusting `shop_domain` for job dispatch: [3](#0-2) 

And the built-in job template pattern uses the (header-derived) `shop_domain` to look up the `Shop` record and subsequently activate that shop's stored session/access token: [4](#0-3) 

By contrast, `AppProxyVerification` (the analogous HMAC-verification concern for app proxy requests) *does* include the `shop` parameter inside the signed query string, so it cannot be swapped post-signature: [5](#0-4) 

This asymmetry means webhook shop-domain trust is weaker than app-proxy shop trust, and mirrors the reported bug class: the "sender/origin" (HMAC over body) is checked, but the "previous_sender"-equivalent (shop identity) is not verified to be consistent with what was actually signed.

### Impact Explanation
Any merchant who installs the vulnerable app on their own shop (an unprivileged, unrelated-merchant actor with respect to any other installed shop) can:
1. Trigger any webhook topic the app registers (e.g., `orders/create`, `carts/update`) on their own store, which Shopify will POST to the app with a valid `X-Shopify-Hmac-Sha256` header computed over the body using the app's shared secret.
2. Capture that request (valid body + valid HMAC) and replay it to the same endpoint while substituting only the `X-Shopify-Shop-Domain` header for a different, victim shop that also has the app installed.
3. Because the signature never covered the header, `hmac_valid?` still returns true, `verify_request` passes, and the custom controller (per the gem's documented recommended pattern) dispatches a job using the attacker-controlled `shop_domain` and attacker-controlled body.
4. The job loads the victim `Shop` record and activates its session/access token, executing attacker-influenced webhook-processing logic (which reads/writes the victim shop's data) — a cross-shop access/action confusion using a replayed-but-still-signature-valid request.

This satisfies the "accepted forged signed request" / "cross-shop access" bar: the shop-domain binding that authorization/business logic depends on is not actually authenticated.

### Likelihood Explanation
Requires only that the attacker have (or can get) the app installed on some shop they control, and that the app expose at least one custom `ShopifyApp::WebhookVerification`-based controller that uses `shop_domain` for job dispatch/authorization — the exact pattern the gem's own docs recommend. No secrets need to be leaked; the attacker legitimately receives a validly signed webhook for their own shop and simply replays it with a different header value. This is a realistic, low-effort attack path for any developer following the documented guidance.

### Recommendation
- Bind shop identity to the signed payload rather than trusting the unsigned header: verify that `shop_domain` (header) matches a shop identifier that's actually inside the HMAC-covered body (Shopify includes `myshopify_domain`/shop identifiers in most webhook payloads), or
- Compute/verify the HMAC over `raw_post + shop_domain` (or otherwise incorporate the header into the signed material) before trusting it, or
- At minimum, document and enforce that consumers of `shop_domain` must independently confirm the resolved `Shop` record's domain is consistent with body contents before using it for session activation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker performs an action that triggers a registered webhook (e.g. update a cart), causing Shopify to POST to the app's webhook endpoint with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of body using app secret>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
3. Attacker intercepts/replays this exact POST body and HMAC header, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` → `hmac_valid?(request.raw_post)` still succeeds because the HMAC never covered the header. [6](#0-5) 
5. The custom controller (built as documented) calls `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)` with `shop_domain == "victim-shop.myshopify.com"` and attacker-supplied body, causing the job to load and act on `victim-shop`'s stored session/access token. [7](#0-6)

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
