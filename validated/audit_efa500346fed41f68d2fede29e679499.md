### Title
Change outputs between 546 and 10,000 sats are created but never scanned, permanently stranding multisig funds - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the referenced liquidation bug where a counterparty's owed balance (cva/pnl) is silently dropped during settlement, Serai's Bitcoin wallet creates change outputs using a dust floor of 546 sats while the processor's scanner only credits outputs worth at least 10,000 sats. A withdrawal whose leftover change falls in `[546, 10_000)` produces an on-chain output owned by the multisig that the processor will never register, so the funds are permanently unspendable — the "receiving" side of the settlement is skipped exactly like the commented-out accrual in the reference report.

### Finding Description
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` decides whether to append a change output using the wallet-level constant `DUST = 546`:

```rust

  if value >= DUST {
    tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });
    ...
  }
}

The change address itself is a valid registered scanner offset (`change_address` derives from `scanner(key)` and `OutputType::Change`), so the script is watchable — but the emitted `ReceivedOutput` is filtered out before being credited, and `get_outputs` in `processor/src/networks/bitcoin.rs` only forwards what `scanner.scan_transaction` returned. ### Impact Explanation
Whenever `input_sat - payment_sat - fee_with_change ∈ [546, 10_000)`, the signed transaction pays change to a multisig-owned address that the processor records nothing for. Those sats are locked under the multisig's change key with no corresponding `Output` in the processor's bookkeeping, so they can never be selected as inputs to a future `SignableTransaction` — a silent, permanent loss of funds from the shared pool. In the reference bug, partyA loses their rightful cva/pnl because the credit path is skipped; here, the multisig loses its rightful change because the credit path (scan filter) rejects what the settlement path (transaction builder) emitted.

### Likelihood Explanation
The window is wide: any withdrawal where the leftover after payments and fees lands in a ~9,454-sat range triggers it. The payment amount is influenced by the unprivileged withdrawer requesting a withdrawal, who can pick an amount that pushes change into the gap, causing the multisig to burn funds belonging to all participants. No privileged access is needed — only the ability to request a payment of an attacker-chosen size.

### Recommendation
Use a single dust constant across the wallet builder and the processor scanner. Either raise `networks/bitcoin/src/wallet/send.rs`'s `DUST` to `processor`'s `N::DUST` (10,000) so sub-threshold change is folded into the fee instead of emitted, or lower the scanner filter — the former is safer since it also enforces the relay-level spendability rationale documented in `processor/src/networks/bitcoin.rs`. If the two constants must differ intentionally, `SignableTransaction::new` should take the scanner's dust floor as a parameter rather than hardcoding 546.

### Proof of Concept
1. A user requests a withdrawal of amount `P` from a multisig holding an input worth `I`, such that `I - P - fee_with_change = 5,000` sats (≥ 546, < 10,000).
2. `BSignableTransaction::new` (invoked via `make_signable_transaction` in `processor/src/networks/bitcoin.rs:446`) pushes a 5,000-sat change `TxOut` to the change address, since `5_000 >= DUST (546)`.
3. The transaction is signed and broadcast; the change output is mined at the change script, which `Scanner::scan_transaction` would match (`self.scripts` contains it).
4. In `processor/src/multisigs/scanner.rs`, `output.balance().amount.0 = 5_000 < N::DUST = 10_000`, so the output is dropped and never pushed to `outputs` / never marked `seen`.
5. The 5,000 sats remain on-chain under the multisig's change key but are absent from the processor's output set, making them unspendable by any future transaction the processor constructs — a permanent loss with no error emitted at any step.
