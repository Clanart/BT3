## Finding

### Title
Aggregator's `InternalSendTx` RPC accepts and queues arbitrary transactions from any network caller without client-certificate authorization - (File: core/src/rpc/aggregator.rs)

### Summary
The `MultiDistributor.setMinimumDistribution` bug is a state-mutating method that should only be reachable by trusted participants but has no access-control check. The equivalent binding in Clementine is: *a call that mutates the tx-broadcast queue* should only be reachable by the aggregator's own operator/verifier peers or the aggregator itself, never by an arbitrary network client. `internal_send_tx` on `ClementineAggregator` breaks this binding because the aggregator, unlike the verifier and operator servers, is documented and implemented to skip client-certificate authorization entirely.

### Finding Description
Verifier and operator gRPC servers wrap their service in the `OnlyAggregatorAndSelf` interceptor, which rejects any TLS peer whose leaf certificate isn't the aggregator's or the entity's own [1](#0-0) . This binds "caller identity" to "aggregator or self" for every non-public RPC.

The aggregator, however, is explicitly documented not to enforce this: "The aggregator does not enforce client certificates but does use TLS for encryption." [2](#0-1) . This means any TCP/TLS client that can reach the aggregator's port (no client cert required) can invoke every RPC defined on `ClementineAggregator`, including `internal_send_tx`: [3](#0-2) 

The handler takes an attacker-supplied raw, already-signed Bitcoin transaction and, subject only to the compile-time `automation` feature flag (not a caller-identity check), inserts it into the aggregator's transaction-sending queue via `self.tx_sender.insert_try_to_send(...)`, which persists it in the DB for the aggregator's fee-bumping/broadcast infrastructure to relay and fund [4](#0-3) . There is no verification that the caller is the aggregator's own automation loop, a verifier, an operator, or any authorized party — the only gating in the interceptor design ("Internal*" methods require the caller's cert to equal the entity's own cert) is never applied here because the aggregator's server never installs the `OnlyAggregatorAndSelf` interceptor for its own RPC surface.

This is the direct structural analog of `setMinimumDistribution`: a state-changing entry point that the documentation says is for a specific ("Internal"/trusted) caller, but which has no code-level authorization check, unlike its sibling entry points on the verifier/operator servers.

### Impact Explanation
This falls under the report's High-impact bucket: "an unauthenticated state-changing or broadcasting call." An unauthenticated network caller can make the aggregator's transaction-sender treat any raw transaction it supplies as one to actively broadcast and fee-bump, consuming aggregator queue slots and using the aggregator's fee-paying/RBF machinery for transactions the aggregator never intended to send. This is a state mutation (durable DB insert plus subsequent network broadcast) triggered purely by network reachability, with none of the cryptographic bindings that protect other custody-critical aggregator RPCs (e.g. `withdraw`/`optimistic_payout`, which are still gated by Citrea-withdrawal-UTXO matching and, when configured, an ECDSA verification signature tied to `aggregator_verification_address`).

### Likelihood Explanation
Likelihood is high for any deployment operating exactly as documented: the aggregator's TCP port is reachable by verifiers/operators over the network, and per the docs it accepts TLS connections from any client without requiring a recognized client certificate. No key compromise, insider role, or special network position is required — only network reachability to the aggregator's listening port, which is the intended way for its RPC surface to be reached at all (this is not a misconfiguration; it is the documented aggregator authentication posture).

### Recommendation
Apply the same `OnlyAggregatorAndSelf`-style interceptor (or an aggregator-specific allow-list of verifier/operator/self certificates) to the aggregator's gRPC server, at minimum for state-changing/broadcast-affecting methods such as `internal_send_tx`, `send_move_to_vault_tx`, and other RPCs not already protected by an independent cryptographic binding (Citrea withdrawal-UTXO match, ECDSA verification signature, etc.). If the aggregator must remain reachable by external unauthenticated clients for legitimate reasons, restrict `internal_send_tx` specifically to require an authenticated/whitelisted client certificate, consistent with its "Internal" naming convention used elsewhere in the codebase.

### Proof of Concept
1. Start an aggregator per the documented/default configuration (`client_verification` semantics as implemented for the aggregator, i.e., no client-certificate check on its own RPCs) [2](#0-1) .
2. As an arbitrary network client (using only a TLS connection, no valid/whitelisted client certificate), call `ClementineAggregator/InternalSendTx` with a raw signed Bitcoin transaction and a `fee_type` [5](#0-4) .
3. The handler `internal_send_tx` deserializes the transaction and calls `insert_try_to_send`, queuing it for the aggregator's fee-bumping/broadcast pipeline [6](#0-5)  — no verification of caller identity occurs anywhere in this path.

**Uncertainty:** I was unable to fully confirm from the indexed content whether `create_aggregator_grpc_server` in `core/src/servers.rs`/`core/src/main.rs` literally always passes `Interceptors::Noop` regardless of the `client_verification` config flag, or whether it conditionally applies `OnlyAggregatorAndSelf` the same way the operator/verifier servers do (the generic TLS server-setup code shown is shared and does branch on `config.client_verification`). The `docs/usage.md` text strongly states the aggregator "does not enforce client certificates," which is what this finding relies on, but a background Devin session with full repository access should verify the exact `create_aggregator_grpc_server` construction in `core/src/servers.rs` to confirm whether this is unconditional or configuration-dependent before treating this as fully confirmed.

    #[tracing::instrument(skip(self), err(level = tracing::Level::ERROR))]
    async fn internal_send_tx(
        &self,
        request: Request<clementine::SendTxRequest>,
    ) -> Result<Response<Empty>, Status> {
        #[cfg(not(feature = "automation"))]
        {
            Err(Status::unimplemented("Automation is not enabled"))
        }
        #[cfg(feature = "automation")]
        {
            let send_tx_req = request.into_inner();
            let fee_type = send_tx_req.fee_type();
            let signed_tx: bitcoin::Transaction = send_tx_req
                .raw_tx
                .ok_or(Status::invalid_argument("Missing raw_tx"))?
                .try_into()?;
            tracing::warn!(
                "Internal send tx rpc called with feetype: {:?}, tx hex: {}",
                fee_type,
                bitcoin::consensus::encode::serialize_hex(&signed_tx)
            );

            let mut dbtx = self.db.begin_transaction().await?;
            self.tx_sender
                .insert_try_to_send(
                    &mut dbtx,
                    None,
                    &signed_tx,
                    fee_type.try_into()?,
                    None,
                    &[],
                    &[],
                    &[],
                    &[],
                )
                .await
                .map_to_status()?;
            dbtx.commit()
                .await
                .map_err(|e| Status::internal(format!("Failed to commit db transaction: {e}")))?;
            Ok(Response::new(Empty {}))
        }
    }
