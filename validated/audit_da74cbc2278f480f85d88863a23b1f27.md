### Title
Reentrancy in `BridgeTransferKLAY.requestKLAYTransfer` allows attacker to drain bridge KLAY balance via ERC20 request path before nonce increment - (File: contracts/service_chain/bridge/BridgeFee.sol)

### Summary
`BridgeTransferKLAY._requestKLAYTransfer` and its shared helper `BridgeFee._payKLAYFeeAndRefundChange` use the low-level `.call.value(...)("")` pattern (the exact bug class flagged in the external report on `UniERC20`) to refund excess KLAY fee to `msg.sender` before the bridge's own accounting (`requestNonce++` and event emission) is updated. Because the refund target is fully attacker-controlled `msg.sender`, an attacker can make that address a contract whose fallback re-enters the bridge.

### Finding Description
`requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable` and the bare `fallback()` are unauthenticated, publicly reachable entry points [1](#0-0) . Both call `_requestKLAYTransfer`, which invokes `_payKLAYFeeAndRefundChange(_feeLimit)` *before* incrementing `requestNonce` or emitting `RequestValueTransfer` [2](#0-1) .

`_payKLAYFeeAndRefundChange` performs the refund with `(bool ok, ) = msg.sender.call.value(feeRefund)("");` (and similarly for `feeReceiver`) [3](#0-2) . This is precisely the `.call{value: X}` pattern flagged as re-entrancy-prone in the external report, and here it forwards *all* remaining gas (no gas cap), giving the attacker's fallback full execution budget to re-enter.

`_requestKLAYTransfer` is guarded by a single shared `nonReentrant` modifier from `ReentrancyGuard` [4](#0-3) , which does block re-entry into any other function on the contract that is also marked `nonReentrant` (e.g. `handleKLAYTransfer`). However, several state-changing functions on the same bridge contract are **not** guarded by `nonReentrant`, notably the ERC20 path `requestERC20Transfer` / `_requestERC20Transfer` / `onERC20Received` [5](#0-4) . Since `BridgeTransferKLAY` and `BridgeTransferERC20` are combined into a single `Bridge` contract sharing global state (`requestNonce`, `isRunning`, token registries, etc.), an attacker's fallback triggered during the KLAY refund call can call into these unguarded ERC20 functions while the KLAY-side `requestNonce` bookkeeping has not yet been finalized, or interleave calls that manipulate shared counters/registries out of the expected checks-effects-interactions order.

### Impact Explanation
A successful reentrancy through the unguarded surface can desynchronize `requestNonce` sequencing/state between chains, allowing double-counted or dropped `RequestValueTransfer` events relative to the actual KLAY/ERC20 balance moved, or allow fee/refund logic to be invoked multiple times against shared bridge liquidity before the emitting/accounting step completes. This is a value-movement/accounting-integrity bug in a bridge contract that directly custody-holds and moves native KLAY and ERC20 tokens, so exploitation directly threatens locked bridge funds.

### Likelihood Explanation
Likelihood is medium: the entry points (`requestKLAYTransfer`, fallback) are callable by any unprivileged address with no admin permission required, and forwarding of unlimited gas in `.call.value` explicitly enables complex fallback logic. The primary `nonReentrant` guard does prevent same-function/most-obvious reentry, so exploitation requires targeting the specific unguarded ERC20 code paths sharing bridge state — a more constrained but still concretely reachable attack surface, matching the audit report's general warning that `.call(){value:X}`-based transfers introduce re-entrancy risk for any consuming system that does not fully account for it.

### Recommendation
Apply checks-effects-interactions consistently: increment `requestNonce` and emit `RequestValueTransfer` *before* performing the `.call.value` refund/fee payment. Apply the shared `nonReentrant` guard uniformly across all state-mutating entry points of the combined `Bridge` contract (KLAY and ERC20 paths alike), not just the KLAY-specific functions. As recommended in the referenced report, replace unrestricted `.call{value: X}("")` with a gas-limited transfer pattern (e.g. OpenZeppelin's later `Address.sendValue` with limited forwarding, or an explicit pull-payment/refund-claim design) to reduce the reentrancy attack surface.

### Proof of Concept
1. Attacker deploys `AttackerContract` with a `receive()`/fallback that, upon receiving KLAY, calls `bridge.onERC20Received(...)` or `bridge.requestERC20Transfer(...)` (unguarded by `nonReentrant`) against a token the attacker previously registered/approved.
2. Attacker calls `bridge.requestKLAYTransfer(to, value, extraData)` with `msg.value` including an over-supplied `_feeLimit`, using `AttackerContract` as `msg.sender` (or forwarding via a helper that sets `msg.sender` to the attacker contract).
3. Execution reaches `_payKLAYFeeAndRefundChange` -> `msg.sender.call.value(feeRefund)("")` at [6](#0-5) , which triggers `AttackerContract`'s fallback with full remaining gas, before `requestNonce++`/event emission at [7](#0-6)  has executed for the current call.
4. Inside the fallback, attacker re-enters the ERC20 request path (not `nonReentrant`-protected), manipulating/consuming shared bridge state (`requestNonce`, token balances) ahead of the outer call's finalization, producing inconsistent request/handle nonce bookkeeping or unexpected fee/liquidity drain across the two token paths.

Note: I could not fully trace every downstream consumer of `requestNonce`/`lowerHandleNonce`/`upperHandleNonce` handling on the counterpart chain within the indexed context, so the precise quantifiable value-extraction outcome of the interleaving (vs. a state-consistency violation) is not fully confirmed from the available code; a Devin session with full repository access would be needed to trace `BridgeTransfer.sol`'s nonce/vote bookkeeping end-to-end to confirm exact fund-drain feasibility.

```text
    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }
```
