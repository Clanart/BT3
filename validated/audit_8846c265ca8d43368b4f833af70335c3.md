### Title
Third-party OP_RETURN malleability of `payout_tx` (SIGHASH_SINGLE|ANYONECANPAY does not cover the operator-attribution output) permanently denies reimbursement to the honest operator who funded the payout - ([File: `core/src/database/verifier.rs`], [core/src/builder/transaction/operator_reimburse.rs], [core/src/operator.rs])

### Summary
`create_payout_txhandler` builds `payout_tx` with the user's withdrawal-UTXO input signed under the mandatory `SinglePlusAnyoneCanPay` sighash type, which only commits to the input and to the output at the *same index* (output 0, the user payout). The OP_RETURN output that names the reimbursing `operator_xonly_pk` (output 2) and the anchor output (output 1) are **not covered by the signature**, so anyone who observes the operator's broadcast (but unconfirmed) `payout_tx` can rebuild a fee-bumped, RBF-replacing transaction with the identical input/witness and identical user-payout output, but an attacker-chosen OP_RETURN. Whichever transaction confirms sets `payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk`, permanently and exclusively crediting that operator through `get_first_unhandled_payout_by_operator_xonly_pk` / `PayoutCheckerTask`, while the operator who actually funded the payout is left with a mismatched `payer_xonly_pk` and is either denied reimbursement or flagged malicious.

### Finding Description
The binding claimed by the protocol is: `payout_payer_operator_xonly_pk` for withdrawal `idx` == the operator whose Bitcoin funds paid the user in the transaction that spends `withdrawal_utxo` for `idx`.

Trace:
1. `Operator::withdraw` (`core/src/operator.rs:560-637`) builds `payout_txhandler` via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) with outputs: `[0] user payout, [1] anchor, [2] OP_RETURN(operator_xonly_pk)`.
2. The witness is `in_signature`, whose sighash type is enforced to `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:174-187`), and verified in `Operator::withdraw` via `calculate_sighash_txin(0, in_signature.sighash_type)` + `SECP.verify_schnorr` (`core/src/operator.rs:630-637`).
3. `SIGHASH_SINGLE|ANYONECANPAY` semantics: the signature commits only to the single spent input (outpoint/amount/script) and to the output whose index equals the input's index (output 0). Outputs 1 (anchor) and 2 (OP_RETURN operator attribution) are **unsigned/malleable** — anyone can substitute them, or add/change other inputs (ANYONECANPAY permits this, which is exactly how `fund_raw_transaction` legitimately adds fee inputs at `core/src/operator.rs:652-673`).
4. This means an attacker who sees operator A's `payout_tx` in the mempool (unconfirmed) can copy the exact input+witness, keep output 0 identical (so the user still gets paid — the signature forces this), but replace output 2's OP_RETURN with operator B's `xonly_pk` (or remove it, or point to themselves), add their own fee-paying input(s)/change output, and rebroadcast with a higher fee/feerate to win the RBF race and get mined first.
5. On confirmation, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) reads the OP_RETURN of whichever tx is in the canonical block and calls `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`), which unconditionally overwrites `payout_payer_operator_xonly_pk`/`payout_tx_blockhash` for that `idx` — there is no uniqueness or consistency check tying the credited pubkey to who actually funded the payout.
6. `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`) and `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:31-111`) then credit only the operator named in that single stored row.
7. Meanwhile, operator A (who actually spent real BTC to pay the user, if their tx happened to confirm with A's OP_RETURN preserved by luck) or, worse, whose original broadcast was replaced entirely, calls `get_reimbursement_txs` → `validate_payer_is_operator` (`core/src/operator.rs:1687-1740`), which errors out (`"Payer is not own operator for deposit"`) because `payout_payer_operator_xonly_pk` in the DB now names operator B (or nobody). Operator A can never obtain a `kickoff_tx` for this deposit and is permanently unable to be reimbursed. If A had already progressed to kickoff before the replacement is even discovered, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) will flag A's kickoff as malicious because the stored `operator_xonly_pk` no longer matches `kickoff_data.operator_xonly_pk`, risking collateral loss for the honest operator.

Existing guards do not prevent this: `SECP.verify_schnorr` only validates the signature is valid for `SinglePlusAnyoneCanPay`, which by protocol design leaves the OP_RETURN and additional inputs unsigned; `is_kickoff_malicious` checks *consistency* with the (already-corrupted) DB row, not who actually funded the payout; there is no on-chain or database mechanism binding the OP_RETURN payer identity to the actual fee-paying party.

### Impact Explanation
This is Critical: it directly matches two named Critical impact categories — "an honest operator permanently unable to be reimbursed" (operator A, having spent real BTC, is barred by `validate_payer_is_operator`) and "an operator reimbursed for a payout it never funded" (operator B, named in the attacker's malleated OP_RETURN, becomes eligible via `get_first_unhandled_payout_by_operator_xonly_pk` to kick off and be reimbursed for a payout it did not pay). It can also cascade into "an honest operator's collateral burned" if operator A had already progressed toward a kickoff that `is_kickoff_malicious` now rejects. The attack is repeatable for every withdrawal that any operator processes, requires no privileged role, and scales across all deposits/operators since it exploits a structural sighash-coverage gap common to every `payout_tx`.

### Likelihood Explanation
Preconditions: an operator must have broadcast (but not yet confirmed) a `payout_tx` for some withdrawal, which is a routine, expected event; the attacker only needs to observe the mempool (public), craft a competing transaction reusing the untouched witness/input (no signing key needed), attach their own funding input(s), and pay a higher fee to win the RBF race before the original confirms. Attacker cost is just Bitcoin transaction fees (no bridge funds put at risk by the attacker, since output 0 to the user is signature-locked and must remain unchanged). This is straightforward with mempool visibility and RBF, and is repeatable for every withdrawal processed by any operator — making it a low-cost, high-impact, and broadly exploitable bug.

### Recommendation
Extend the payout signature's coverage (or otherwise cryptographically bind) to include the OP_RETURN operator-attribution output and the anchor output, e.g. by using `SIGHASH_ALL` for the fixed portion of outputs or by having the operator co-sign/commit to the OP_RETURN content via a musig2 or additional covenant mechanism instead of leaving it as unauthenticated extra data. Alternatively, require `update_payout_txs_and_payer_operator_xonly_pk` to reconcile against an operator-specific pre-broadcast commitment (e.g., the operator's `xonly_pk` recorded off-chain/pre-committed for that `withdrawal_idx` before broadcast) rather than trusting the confirmed-tx OP_RETURN alone, and detect/react to RBF-driven mismatches instead of silently overwriting attribution.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

        Ok(())
    }

                payout_tx_blockhash = c.payout_tx_blockhash

                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );
