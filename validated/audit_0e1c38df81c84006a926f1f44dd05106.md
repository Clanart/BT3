### Title
Hardcoded zero slippage on WOM→mWom swap in `ArbWomUp3._deposit` disables `SmartWomConvert`'s built-in slippage protection - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3._deposit` (mode 2 path) calls `SmartWomConvert.convert` with `_minRec` hardcoded to `0`, disabling the slippage check that `SmartWomConvert._convertFor` is designed to enforce on the on-chain WOM→mWom swap routed through `IWombatRouter`.

### Finding Description
`SmartWomConvert._convertFor` performs a swap of a portion of the user's WOM for mWom through `IWombatRouter.swapExactTokensForTokens` and validates the outcome against a caller-supplied `_minRec` parameter: [1](#0-0) 

This slippage check is meaningful protection against sandwich attacks/MEV on the WOM/mWom pool swap. However, `ArbWomUp3._deposit`, when invoked in `_mode == 2`, calls the external `convert` function with the minimum-receive parameter hardcoded to `0`: [2](#0-1) 

Because `_minRec` is `0`, the check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` in `_convertFor` can never fail, so the swap executes and accepts whatever output the pool gives, no matter how much it has been manipulated. [3](#0-2) 

This function is reachable from an ordinary wallet via `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, _mode)` with `_mode == 2`, which is a public, unprivileged entry point: [4](#0-3) 

### Impact Explanation
Any unprivileged user calling `incentiveDeposit` with `_mode == 2` has half of their deposited WOM routed through an on-chain swap with zero minimum output enforced. A malicious actor (or naturally occurring on-chain trading activity) can sandwich this transaction, causing the user to receive significantly less mWom than fair value. Since the resulting mWom is immediately locked into `mWomSV` on the user's behalf, the loss is realized directly into a locked position the user cannot easily unwind, constituting a direct loss of user funds.

### Likelihood Explanation
The `incentiveDeposit` function is a normal user-facing entry point requiring no special privileges, and mode 2 unconditionally triggers the vulnerable swap path with zero slippage protection every time it's used, making exploitation straightforward for any MEV searcher monitoring the mempool.

### Recommendation
Add a user-supplied minimum-receive parameter to `ArbWomUp3.incentiveDeposit`/`_deposit` and forward it (instead of a hardcoded `0`) as the `_minRec` argument to `IConverter(smartWomConvert).convert(...)`, ensuring the existing `MinRecNotMatch` slippage check in `SmartWomConvert._convertFor` is actually enforced.

### Proof of Concept
1. User calls `ArbWomUp3.incentiveDeposit(amount, convertRatio, false, 2)`.
2. `_deposit` computes `toSwap = amount - amount/2` and calls `IConverter(smartWomConvert).convert(toSwap, convertRatio, 0, 0)` (`wombat/ArbWomUp3.sol:199`).
3. Inside `SmartWomConvert._convertFor`, the swap `IWombatRouter(router).swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, ...)` executes with `amountOutMin = 0` (`wombat/SmartWomConvert.sol:194-196`), and the post-swap check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` cannot trigger since `_minRec == 0` (`wombat/SmartWomConvert.sol:204-205`).
4. An attacker front-runs the swap by driving the WOM/mWom pool price against the user, and back-runs it after, extracting the difference; the victim's resulting `obtainedmWomAmount` is locked into `mWomSV` at a loss with no recourse.
