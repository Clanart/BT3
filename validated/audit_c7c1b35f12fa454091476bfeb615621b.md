### Title
Division-by-zero panic in `consolidatedNode.Split` when a zero-stake proposer has a zero-amount CL pool - (File: kaiax/staking/staking_info.go)

### Summary
`consolidatedNode.Split()` divides by `totalAmount = cnAmountBig + clAmountBig` without checking that this sum is nonzero. [2](#0-1)  This function is invoked unconditionally on the current block proposer's consolidated node inside `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` in the reward module, whenever the proposer has a registered `CLStakingInfo`. [3](#0-2)  If both the proposer's AddressBook staking amount and its consensus-liquidity (CL) pool staking amount are zero, `big.Int.Div` panics with a division-by-zero, crashing block finalization.

### Finding Description
`Split(amount)` is defined as:
```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)
	...
``` [2](#0-1) 

This is called during deferred reward finalization for the current block's proposer, guarded only by `cn.CLStakingInfo == nil` (an "early exit if there's no CL"), but with **no check that `StakingAmount + CLStakingAmount > 0`**:
```go
cns := si.ConsolidatedNodes()
for _, cn := range cns {
    if cn.RewardAddr != config.Rewardbase {
        continue
    }
    if cn.CLStakingInfo == nil {
        break
    }
    cnAmount, clAmount := cn.Split(proposer)
    ...
``` [4](#0-3) [3](#0-2) 

Separately, the `kaiax/valset` module and its own test/README explicitly document that when all council members are understaked (zero staking), they are **all still deemed qualified** and can be selected as proposer (WeightedRandom policy falls back to "if no validator meets the minimum staking requirement, all council members are qualified"). This is directly exercised by the `"zero stakes"` test case in `generateProposerListWeighted`. [5](#0-4) 

Combining these two facts: if the current block's proposer (i) has `StakingAmount == 0` in AddressBook (permitted per the valset zero-stake fallback), and (ii) has a registered `CLStakingInfo` (via the CL registry, introduced for Prague HF) with `CLStakingAmount == 0` (e.g., all consensus-liquidity withdrawn from the pool while the pool registration remains), then `Split()`'s `totalAmount` is `0`, and `clAmount.Div(clAmount, totalAmount)` panics with "division by zero" in Go's `math/big`. This panic occurs deep in `FinalizeState`/reward distribution during ordinary block processing, i.e., every honest full node processing this block would crash.

### Impact Explanation
A panic in `math/big.Div` during block finalization is unrecoverable in the normal flow and would crash (or halt) the node processing the block. Because this logic runs identically on every node validating/finalizing the block (deferred reward calculation is deterministic consensus-critical state), this constitutes a chain-halting/DoS condition triggerable by a specific but plausible validator/staking configuration (a proposer with zero effective CN stake and a CL pool drained to zero), analogous to the reported "division/modulo by zero" bug class in the GammaSwap report where an unguarded division on a value that can legitimately become zero causes an unconditional revert/crash.

### Likelihood Explanation
Reaching this state requires: (1) a council with all members understaked (falls back to "all qualified", a documented and tested scenario) so a zero-stake node can be chosen as proposer, and (2) that proposer having a registered `CLStakingInfo` whose `CLStakingAmount` has been reduced to zero (e.g., a CL pool that withdrew all consensus liquidity but remains registered in CLRegistry). Both conditions depend on governance/staking configuration and CL registry state that node operators or validators (not necessarily malicious) could reach, particularly on networks with low overall participation or during liquidity churn, rather than requiring an attacker-controlled transaction. This is a plausible but non-trivial operational configuration, giving it moderate likelihood.

### Recommendation
Add a zero-check guard in `Split()` before dividing by `totalAmount` (analogous to how `assignStakingRewards`/`assignStakingRewardsFlex` already guard their divisions by `totalExcess` being implicitly nonzero through eligibility filters) — e.g., return `(amount, big.NewInt(0))` when `totalAmount.Sign() == 0`, matching the "no meaningful split" semantics of the `CLStakingInfo == nil` branch already present in the function. [2](#0-1) 

### Proof of Concept
1. Configure a chain past the Prague hardfork with consensus liquidity enabled and `reward.minstake` set higher than any council member's actual stake, so the valset module's "all qualified when understaked" fallback applies (as exercised by the `"zero stakes"` test case). [5](#0-4) 
2. Register a `CLStakingInfo` (CL pool) for the eventual proposer's node via the CL registry, then have all liquidity withdrawn so `CLStakingAmount == 0`, while the underlying AddressBook `StakingAmount` for that node is also `0`.
3. When this node is selected as block proposer (per the documented zero-stake fallback) and the block is finalized, `specWithProposerAndFundsFlex`/`specWithProposerAndFunds` calls `cn.Split(proposer)` on this node's `consolidatedNode`, where `totalAmount = 0 + 0 = 0`. [4](#0-3) 
4. `big.Int.Div(clAmount, totalAmount)` panics with division by zero inside `Split()`, crashing the node during `FinalizeState`/reward computation for every node processing that block. [6](#0-5)
