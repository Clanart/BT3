### Title
Desktop unconditionally disables Git's clone-time exploit protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), re-enabling CVE-class RCE via malicious cloned repositories - ([File: app/src/lib/git/clone.ts])

### Summary
The bug report's abstract class is "a security mechanism that should guard the earliest, most attacker-exposed state of an object is unavailable exactly when it's needed most." The closest analog in GitHub Desktop is not a time-bootstrapping issue but a functionally identical one: Desktop's `clone()` helper explicitly forces `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` on every single `git clone --recursive` invocation, unconditionally disabling Git's upstream clone-time protections against malicious repository content — the exact protections Git added specifically to stop attacker-controlled repositories from achieving code execution during clone.

### Finding Description
`clone()` in [1](#0-0)  builds the execution environment for every clone operation and explicitly sets:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
```
and always runs `git clone --recursive ... -- <url> <path>` [2](#0-1) .

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced (as part of the 2024 multi-CVE security response covering symlinked `.git` directories, embedded/nested repositories, and malicious submodule hook/config content that can achieve code execution during a recursive clone) to detect and refuse cloning repositories crafted to smuggle executable hooks or config through submodules. By forcing this flag to `'false'` on every clone, Desktop deliberately turns that protection off for all clone operations — not just as a one-time bootstrap gap like the amAMM report, but permanently, for every user, on every clone, regardless of whether the source is untrusted.

This is reachable from multiple unprivileged, attacker-controlled entry points:
- The "Clone repository" UI flow (`clone-repository.tsx` → `cloneImpl` → `dispatcher.clone` → `appStore._clone` → `clone()`).
- The `x-github-client://openrepo` deep link / CLI `--cli-clone` handler in `main.ts`, which parses an externally supplied URL via `parseAppURL` and can route straight into a clone of an attacker-supplied repository [3](#0-2) .

None of Desktop's other clone-time safeguards address this: `isClonePathSensitive()` only checks the destination directory, not the content of the cloned repository [4](#0-3) , and the `safe.directory`/"unsafe repository" ownership check in `rev-parse.ts` and `add-existing-repository.tsx` only fires for repositories owned by a different local user — it does not apply to a repository the user just cloned themselves, and it does nothing to stop hook/config execution that can occur inline during the clone-and-checkout process that the disabled Git protection was built to catch [5](#0-4) .

### Impact Explanation
If the underlying Git binary bundled with Desktop is one where `GIT_CLONE_PROTECTION_ACTIVE` gates the fix for the clone-time embedded/symlinked-repository or malicious-submodule-hook exploits, forcing it off restores the pre-patch vulnerable behavior for every Desktop user, on every clone. A victim who clones or "Opens in Desktop" an attacker-controlled repository (including via a crafted GitHub URL or deep link) could have arbitrary commands executed on their machine during the clone, entirely outside the git-committed content the user intended to fetch — i.e., code execution, satisfying the report's valid-impact criteria for an attacker-controlled cloned/fetched repository leading to code execution.

### Likelihood Explanation
Likelihood is high for any Desktop build using a Git version where this protection matters: the disabling code path runs unconditionally on every clone with no opt-out, no user prompt, and no distinction between trusted and untrusted sources. The attacker primitive required is simply getting the victim to clone a URL they control (a normal, expected Desktop workflow), which is far less friction than the "wait 24 hours" bottleneck in the original amAMM report.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Leave Git's default (protection-enabled) behavior in place for `git clone --recursive`, and audit why this override was introduced — if it was added to work around a compatibility issue, that issue should be fixed without reintroducing a known RCE-class exposure. If a temporary suppression is unavoidable, it should be scoped as narrowly as possible and paired with independent validation that the cloned tree contains no embedded/symlinked `.git` directories or unexpected submodule hook content before the recursive clone proceeds.

### Proof of Concept
1. Craft a malicious Git repository (superproject + submodule) using the layout targeted by Git's clone-time embedded-repository/submodule-hook protections (e.g., a submodule path that resolves to a symlink or an embedded `.git` directory carrying an executable hook).
2. Host it publicly or serve it via a controlled remote/proxy.
3. Send the victim a link that triggers Desktop's clone flow — e.g., a GitHub "Open with GitHub Desktop" action, or a raw `x-github-client://openrepo/<attacker-repo-url>` deep link handled in `main.ts` [3](#0-2)  — or have the victim manually paste the URL into "Clone repository."
4. Desktop calls `clone()`, which runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` [1](#0-0) , bypassing the check that would otherwise abort the clone and surface an error to the user.
5. If the bundled Git version's protection would have blocked the malicious content, it instead proceeds, and the embedded hook/config content executes in the context of the victim's clone.

Note: full confirmation that the bundled `dugite`/Git binary version in this app still gates the specific CVE fixes behind `GIT_CLONE_PROTECTION_ACTIVE` could not be verified from the indexed code alone (the Git binary itself is external to this repo); this should be validated against the exact Git version Desktop ships before treating exploitability as fully confirmed.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
