## Title
Out-of-bounds array read / index desynchronization when parsing `--raw --numstat -z` output for a crafted commit - (File: `app/src/lib/git/log.ts`)

## Summary
`parseRawLogWithNumstat` in `app/src/lib/git/log.ts` assumes a strict 1:1, in-order correspondence between the `:mode mode sha sha status` (`--raw`) records and the `added\tdeleted\t...` (`--numstat`) records that `git log`/`git diff -z --raw --numstat` emits for a commit. This is directly analogous to the seed bug's core flaw: a value derived from untrusted/attacker-shaped input (the reward-per-token computation) is used without validating that it fits the assumption made by the consuming code (`uint96` width). Here, the assumption is that `files[numStatCount]` always exists and is aligned with the raw-entry that produced it, and this assumption is never checked before being indexed.

## Finding Description
The parser walks the NUL-separated (`-z`) token stream once, incrementing a loop index `i` for raw-diff records (lines starting with `:`) and pushing into `files`, and a **separate** counter `numStatCount` for numstat records: [1](#0-0) 

The critical desync point is:
```
} else {
  const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
  const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
  linesAdded += added === '-' ? 0 : parseInt(added, 10)
  linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

  if (isCopyOrRename(files[numStatCount].status)) {
    i += 2
  }
  numStatCount++
}
```
`files[numStatCount]` is read without any bounds check. The code relies entirely on `git`'s `--raw` and `--numstat` sections always containing the exact same number of entries, in the exact same order, for every kind of diff record (added/deleted/modified/renamed/copied/type-changed/submodule). This corresponds directly to the pattern in the seed report: the invariant "the value always fits" is assumed and never enforced by a check before it's used, so any repository content that violates it (attacker-controlled since `git log`/`diff` output is driven by the actual tree/blob contents and modes of a cloned or fetched commit) breaks a downcast-free but equally unchecked assumption.

If `numStatCount` ever exceeds `files.length - 1` — which can happen whenever the number of numstat lines emitted for a commit differs from the number of raw entries pushed into `files` (e.g. due to type changes, submodule entries, or other edge cases in git's raw/numstat pairing that a crafted commit tree can exercise) — `files[numStatCount]` evaluates to `undefined`, and `.status` on `undefined` throws a `TypeError`, crashing history/diff rendering for that commit. Historical precedent for exactly this kind of raw/numstat parsing fragility exists in the project's own changelog ("Fix 'Invalid numstat line' error when trying to preview a pull request"), confirming this parser has previously broken on real-world crafted/edge-case diffs. There is no existing guard equivalent to the report's recommended "store the full-width value / validate before consuming" — the code goes straight from `parseInt`/regex match to array indexing with no length check.

## Impact Explanation
This function is reached from `getChangedFiles`, `getBranchMergeBaseChangedFiles`, `getCommitRangeChangedFiles`, and `getStashedFiles` (all in `app/src/lib/git/diff.ts` and `app/src/lib/git/stash.ts`) — i.e., any time Desktop lists the files changed in a commit from a repository the user has cloned, fetched, or is browsing (including PR previews and comparisons), so the attacker only needs to control the tree/commit content of a repository the victim opens with Desktop. A crafted commit that desynchronizes the raw/numstat pairing causes an uncaught exception while rendering history/diff for that commit. Impact is capped at a crash/functional-denial of the changes/history view for the affected commit (i.e., a rendering DoS), not memory corruption, code execution, or credential exposure — I could not establish a path from this desync to actual data corruption of what the user commits/pushes (the parsed data isn't fed back into `git commit`/`git push` argument construction), only to what's *displayed*.

## Likelihood Explanation
Reaching this code only requires opening/browsing a commit's diff or history in a repository under attacker influence — a very natural, unprompted user action (viewing history after cloning or fetching a repo, or previewing a PR). No special local access or social engineering beyond "clone/open the repo" is needed. However, constructing a concrete git tree that reliably desynchronizes `--raw`/`--numstat` output (rather than just hitting the already-known "Invalid numstat line" `forceUnwrap` crash on `match`) is not verified in this codebase snapshot — I was not able to trace the exact git-internal condition (e.g., certain submodule/type-change combinations) that produces mismatched raw vs. numstat record counts, only that the code has no defense against it and has broken this way before per the changelog.

## Recommendation
Bound-check `numStatCount` against `files.length` before indexing (`files[numStatCount] === undefined` → skip or throw a descriptive parse error instead of an uncaught `TypeError`), and prefer pairing raw and numstat entries by parsing both streams into aligned arrays first and then zipping them by matching path rather than by independently incremented counters, so any git-version/edge-case divergence fails safely (a caught, descriptive error) instead of an unchecked array access.

```typescript
export function parseRawLogWithNumstat(
  stdout: string,
  sha: string,
  parentCommitish: string
) {
  const files = new Array<CommittedFileChange>()
  let linesAdded = 0
  let linesDeleted = 0
  let numStatCount = 0
  const lines = stdout.split('\0')

  for (let i = 0; i < lines.length - 1; i++) {
    const line = lines[i]
    if (line.startsWith(':')) {
      const lineComponents = line.split(' ')
      const srcMode = forceUnwrap(
        'Invalid log output (srcMode)',
        lineComponents[0]?.replace(':', '')
      )
      const dstMode = forceUnwrap(
        'Invalid log output (dstMode)',
        lineComponents[1]
      )
      const status = forceUnwrap(
        'Invalid log output (status)',
        lineComponents.at(-1)
      )
      const oldPath = /^R|C/.test(status)
        ? forceUnwrap('Missing old path', lines.at(++i))
        : undefined

      const path = forceUnwrap('Missing path', lines.at(++i))

      files.push(
        new CommittedFileChange(
          path,
          mapStatus(status, oldPath, srcMode, dstMode),
          sha,
          parentCommitish
        )
      )
    } else {
      const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
      const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
      linesAdded += added === '-' ? 0 : parseInt(added, 10)
      linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

      // If this entry denotes a rename or copy the old and new paths are on
      // two separate fields (separated by \0). Otherwise they're on the same
      // line as the added and deleted lines.
      if (isCopyOrRename(files[numStatCount].status)) {
        i += 2
      }
      numStatCount++
    }
  }

  return { files, linesAdded, linesDeleted }
}
```
