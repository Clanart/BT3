### Title
Non-linear HEAD rewrite (`git commit --amend --no-edit` onto a different parent, `git reset`+recommit, rebase, or divergent checkout) causes `compute_v2_review_set` to drop already-committed dangerous changes from Stop-hook review - (File: `plugins/security-guidance/hooks/diffstate.py`)

### Summary
`compute_v2_review_set` (which consumes `load_baseline_sha`'s value) only widens the reviewed file set with `head_at_capture..HEAD` names when `_is_ancestor(head_at_capture, current_head)` is true, i.e. only when HEAD advanced *linearly*. If, during a turn, git history is rewritten non-linearly (rebase, `reset --hard`+commit, cherry-pick onto a detached/divergent ref, or an amend whose new parent differs from `head_at_capture`), the modified file is (a) no longer "dirty" in the working tree (it's committed) and (b) not covered by the ancestor-gated `head_at_capture..HEAD` diff, so it is silently excluded from `dirty_now`, and therefore from `review_set = dirty_now & changed_since` — even though its content differs from the turn-start baseline.

### Finding Description
`load_baseline_sha`/`consume_stop_state` supply `baseline_sha` and `head_at_capture`, captured once at `UserPromptSubmit` via `capture_git_baseline`/`_git_rev_parse_head`. [1](#0-0)  The Stop hook then calls `compute_v2_review_set(cwd, baseline_sha, head_at_capture, ...)` to determine which files get reviewed. [2](#0-1) 

Inside `compute_v2_review_set`, `dirty_now` is the union of the current working-tree status (`_git_status_porcelain`) and, *only if* `head_at_capture` is an ancestor of the current HEAD, the names changed in `head_at_capture..HEAD`: [3](#0-2)  The final `review_set` is `dirty_now & changed_since` (or `dirty_now` alone if `changed_since` is unavailable): [4](#0-3) 

The ancestry check (`_is_ancestor`) explicitly only recognizes "HEAD moved forward via commit/merge, not sideways via checkout": [5](#0-4)  Any non-linear history change during the same turn (interactive rebase, `git reset --hard <ref>` followed by a new commit, cherry-pick from a detached HEAD, or an amend that changes the parent) makes `head_at_capture` no longer an ancestor of the new HEAD. Once the dangerous edit is *committed* under such a history rewrite, the working tree becomes clean, so `_git_status_porcelain` reports it as not-dirty, and the ancestor-gated `head_at_capture..HEAD` widening does not fire either. The file is therefore absent from `dirty_now`, and the intersection with `changed_since` (`dirty_now & changed_since`) cannot resurrect it — a missing element from `dirty_now` zeros it out regardless of `changed_since` content. The dangerous, turn-authored change is silently excluded from `review_paths`, bypasses `get_git_diff`/`parse_diff_into_files`/`analyze_code_security`, and the Stop hook proceeds to `_skip(9, ...)` (empty review set) as if no reviewable changes existed. [6](#0-5) 

None of the existing guards (empty-review skip, `MAX_DIFF_FILES` cap, `filter_preexisting_from_diff`) address this: they operate strictly on whatever `review_paths` computed, and the bug is upstream of that in the `dirty_now` construction. The docstring even acknowledges the design intentionally trades off recall for stability against "checkout/pull ballooning," but doesn't account for legitimate git operations (rebase/amend/reset) an agent or a repository-embedded automation script might run mid-turn that create the same non-ancestor topology. [7](#0-6) 

### Impact Explanation
A dangerous code change (e.g. a backdoor, hardcoded secret, or injection sink introduced by Claude or by a repo-embedded instruction that drives git operations) that gets committed via a non-linear git rewrite during the same turn is never sent to the Haiku security reviewer, never triggers the exit(2) remediation loop, and the baseline silently rolls forward past it on the next `UserPromptSubmit`/Stop cycle — permanently removing it from review. This directly breaks the stated invariant that "the review set must stay bound to the right repo, baseline, and touched paths," and can lead to sensitive/dangerous code shipping unreviewed, matching the "Sensitive code disclosure to an unintended... sink" impact class (the vulnerable code itself becomes the unreviewed exfiltration/backdoor vector).

### Likelihood Explanation
The trigger is a normal, unprivileged git sequence performable by any actor who can influence what git commands run in the cloned repo during a turn (Claude itself following repo-embedded instructions, or a Bash tool invocation) — no admin privilege, leaked keys, or social engineering required. Rebase/amend/reset are common, unremarkable developer operations, making this readily reproducible and not a corner case requiring unusual timing.

### Recommendation
Replace the strict `_is_ancestor` ancestor-gate with a topology-agnostic detection of "did HEAD change since capture, and if so, what files differ." Concretely: whenever `current_head != head_at_capture` (regardless of ancestry direction), union `dirty_now` with the merge-base diff (`git diff --name-only $(git merge-base head_at_capture HEAD) HEAD`) or, more robustly, always include `_git_name_only(repo, head_at_capture)` (a straight two-dot diff against the pre-turn HEAD) unconditionally when `head_at_capture` still resolves, instead of gating it behind linear ancestry. This preserves protection against unrelated "checkout/pull ballooning" (which the ancestry check was meant to avoid) by still requiring HEAD to have changed, while ensuring committed changes are never dropped purely because history was rewritten non-linearly.

### Proof of Concept
Integration test in the vein of the existing Stop-hook test suite:
1. Init a git repo, commit an initial safe file, capture `head_at_capture = H0` via `capture_git_baseline`/`_git_rev_parse_head` (simulating UPS).
2. Simulate a turn: edit a file to introduce a dangerous pattern (e.g. `eval(user_input)`), `git add`, `git commit -m "wip"` → `HEAD=C1` (linear child of `H0`, sanity case — assert `compute_v2_review_set` DOES include it).
3. Repeat from `H0`, but instead run `git reset --hard H0` then re-apply the dangerous edit and `git commit -m "wip2"` producing `C1'` — a sibling of `C1`, not a descendant reachable only via `H0` being an ancestor of `C1'` is actually still true here (parent unchanged), so use a stronger repro: `git checkout -b other H0`, cherry-pick/commit the dangerous change there to produce `C2` whose only path back to `H0` goes through a merge, or explicitly `git rebase --onto <unrelated-commit> H0 HEAD` so `merge-base --is-ancestor H0 <new HEAD>` returns non-zero.
4. Call `compute_v2_review_set(cwd, baseline_sha=<stash-sha-from-step1>, head_at_capture=H0, {})` and assert: **expected (bug)** — the dangerous file is absent from `review_paths` even though its content differs from baseline; **desired (fixed)** — `review_paths` still contains the dangerous file's absolute path.
5. Add a fuzz/invariant test: for randomized sequences of {edit, commit, amend, reset --hard <earlier>, rebase --onto} ending with the dangerous file committed and content differing from `baseline_sha`, assert the dangerous file's path is always present in the returned `review_paths` list from `compute_v2_review_set`.

def _is_ancestor(cwd, maybe_ancestor, descendant):
    """True if `maybe_ancestor` is reachable from `descendant` (i.e. HEAD
    moved forward via commit/merge, not sideways via checkout)."""
    try:
        result = subprocess.run(
            [*GIT_CMD, "merge-base", "--is-ancestor", maybe_ancestor, descendant],
            cwd=cwd, capture_output=True, text=True, timeout=5,
        )
        return result.returncode == 0
    except (subprocess.TimeoutExpired, FileNotFoundError, OSError):
        return False
