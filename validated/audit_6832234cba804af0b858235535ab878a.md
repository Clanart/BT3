### Title
Identity/weak ECDH encryption key in PedPoP registration makes secret shares publicly decryptable - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2023-25758 is a man-in-the-middle extraction of seed material over an unauthenticated channel. The analog in Serai is the PedPoP DKG's share-encryption layer: each participant submits an `EncryptionKeyMessage` carrying an `enc_key` (their ECDH public key) which is stored verbatim by `Decryption::register` and used as the ECDH peer point in `encrypt`. Neither `C::read_G`, `EncryptionKeyMessage::read`, `Decryption::register`, nor `encrypt` rejects the identity point (or otherwise validates the key). A participant who registers `enc_key = identity` causes every secret share encrypted to them to use `ecdh = identity * k = identity`, a publicly known value, so the ChaCha20 keystream is derivable by anyone. The ciphertext alone then reveals the plaintext share to any passive observer — no authenticated-channel position needed.

### Finding Description
- `EncryptionKeyMessage::read` reads `enc_key` via `C::read_G` [1](#0-0) , which only enforces canonical encoding and explicitly accepts the identity point [2](#0-1) .
- `Decryption::register` stores the supplied `enc_key` with no validity check [3](#0-2) .
- `Encryption::encrypt` computes the shared secret as `ecdh::<C>(&key, to)` = `to * key` where `to` is the registered key [4](#0-3) , [5](#0-4) .
- `cipher` derives the ChaCha20 key solely from `context || ecdh.to_bytes()` with a fixed IV `b"DKG IV v0.2\0"` [6](#0-5) . With `ecdh = identity`, the keystream input is constant and public, so `apply_keystream` is trivially reversible by any observer [7](#0-6) .
- The per-message PoP only proves knowledge of the *sender's* ephemeral key [8](#0-7) ; nothing binds `enc_key` to the registrant's commitments or checks it is non-identity, and the round-1 PoK covers only `cached_msg` (the commitments), not `enc_key` [9](#0-8) .

### Impact Explanation
Every honest participant encrypts their Pedersen share for the malicious registrant against `identity`, so all shares directed at that participant decrypt to plaintext for anyone who sees the wire bytes. This recovers the victim-slot's aggregated secret share (sum of all per-dealer shares for that index) — a key-share disclosure to unprivileged parties that the ECDH layer exists specifically to prevent [10](#0-9) . Beyond leaking the share, an observer who also obtains `t-1` further shares through any other weakness reaches threshold key recovery, and the leaked share is verifiable against the public commitments via `share_verification_statements` [11](#0-10) , so the attacker can confirm correctness offline.

### Likelihood Explanation
Requires only a single malicious DKG participant supplying crafted `EncryptionKeyMessage` bytes — exactly the untrusted-input surface in scope (`EncryptionKeyMessage::read` → `C::read_G`). No collusion, no network MITM, and no authenticated-channel violation is needed since the ciphertext itself becomes public. Exploitation is deterministic; the only mitigation is that share messages might not be broadcast.

### Recommendation
Reject the identity point (and any non-prime-order/torsion point, where applicable) for `enc_key` in `Decryption::register` or `EncryptionKeyMessage::read` — e.g., `if bool::from(msg.enc_key.is_identity()) { Err(...) }`. Additionally consider binding `enc_key` into the round-1 Schnorr PoK transcript (`challenge`/`cached_msg`) so the encryption key is authenticated under the same proof as the commitments.

### Proof of Concept
1. Attacker runs `KeyGenMachine::generate_coefficients`, then mutates their `EncryptionKeyMessage` so `enc_key` serializes to the canonical identity encoding (all-zero/`0x01..00` per curve) before broadcast — `C::read_G` accepts it.
2. Honest participants call `generate_secret_shares`; `self.encryption.encrypt(rng, l, share_bytes)` for `l` = attacker computes `ecdh = identity * key = identity`, then `cipher(context, identity)` produces a keystream every observer can recompute from the fixed transcript `"DKG Encryption v0.2"`, the public `context`, the identity encoding, and IV `"DKG IV v0.2\0"`.
3. Observer XORs the attacker's `EncryptedMessage.msg` bytes with that keystream and recovers each sender's `SecretShare` plaintext for the attacker index; the share verifies against the sender's public `commitments` via `share_verification_statements`.

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
