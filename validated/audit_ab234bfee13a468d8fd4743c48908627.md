### Title
Unbounded per-call `debug_trace*` timeout accepted from RPC caller without validation against server-configured maximum - ([File: evmrpc/block_trace_profiled.go])

### Summary
`profiledTraceTx` in `evmrpc/block_trace_profiled.go` reads the caller-supplied `TraceConfig.Timeout` string and passes it straight into `time.ParseDuration` and then `context.WithTimeout`, with no upper bound check against the node operator's configured `trace_timeout`/`api.traceTimeout`. This mirrors the Apache Olingo CVE-2019-17555 bug class: an externally-supplied duration value is consumed by a blocking/timing primitive without validation, allowing a caller to force an arbitrarily long wait.

### Finding Description
In the profiled block/tx tracing path, the timeout used to bound tracer execution is derived from the request itself: [1](#0-0) 

Specifically:
```go
timeout = profiledDefaultTraceTimeout
...
if config.Timeout != nil {
    if timeout, err = time.ParseDuration(*config.Timeout); err != nil {
        return nil, err
    }
}
deadlineCtx, cancel := context.WithTimeout(ctx, timeout)
``` [2](#0-1) 

There is no clamp comparing the parsed `timeout` to `profiledDefaultTraceTimeout` or to the operator-configured `evm.trace_timeout` value that other trace paths enforce via `prepareTraceContext`: [3](#0-2) 

By contrast, the non-profiled trace entry point (`TraceTransaction`) always wraps the context with the server-side `api.traceTimeout`, ignoring the caller's `config.Timeout` for bounding purposes: [4](#0-3) 

But the profiled block-trace path (`profiledTraceBlock` → `profiledTraceBlockSequential`/`profiledTraceBlockParallel` → `profiledTraceTx`) does not appear to go through `prepareTraceContext`/`api.traceTimeout` before reaching `profiledTraceTx`; instead it independently derives its own timeout from the untrusted `config.Timeout` field, which is fully attacker-controlled via the JSON-RPC request body (e.g. `debug_traceBlockByNumber`/`debug_traceBlockByHash` with `{"timeout": "999999h"}`).

Since the outer `ctx` passed into `profiledTraceTx` is the request context (not itself bounded to `api.traceTimeout` on this code path, as evidenced by the parallel/sequential callers only threading `ctx` from the top-level entry functions without an intervening `context.WithTimeout(ctx, api.traceTimeout)`), a caller-supplied huge duration is not capped, and `context.WithTimeout(ctx, timeout)` will not shorten the effective deadline below what the caller requested.

### Impact Explanation
A public RPC client can send a `debug_traceBlockByNumber`/`debug_traceBlockByHash` request with an extreme `timeout` value (e.g. "87600h"). This causes the profiled tracer's deadline goroutine and worker threads (up to `maxProfiledTraceWorkers` = 16 per block) to remain committed to the trace for as long as execution takes, defeating the intended timeout safety valve that exists specifically to bound resource consumption of tracing calls. Combined with concurrent requests, this can tie up trace worker capacity and node resources for extended, attacker-chosen periods, degrading or denying the public RPC service (resource-exhaustion DoS on the RPC node), which matches the "crash/DoS of default-configuration RPC nodes" impact class in scope.

### Likelihood Explanation
The `timeout` field of `TraceConfig` is a documented, ordinary JSON-RPC parameter (as shown being exercised in tests with values like `"1ns"` and `"60s"`) [5](#0-4) [6](#0-5) , so any unprivileged RPC client can trivially set it to an arbitrarily large duration string with no authentication, gas cost, or fee required, and no special node configuration needed (the profiled trace path is enabled via `enable_parallelized_block_trace`, a documented, non-default-off-by-necessity config option) [7](#0-6) .

### Recommendation
Clamp the parsed `config.Timeout` in `profiledTraceTx` (and any other profiled-trace timeout derivation) to the operator-configured maximum (`api.traceTimeout` / `evm.trace_timeout`), the same way the non-profiled `TraceTransaction`/`prepareTraceContext` path already enforces a server-side ceiling. Concretely, after parsing `config.Timeout`, take `min(timeout, api.traceTimeout)` before calling `context.WithTimeout`, and/or wrap the top-level `ctx` passed into the profiled block trace entry points with the same `api.traceTimeout`-bounded context used by `prepareTraceContext`.

### Proof of Concept
1. Enable the profiled block trace path (`enable_parallelized_block_trace = true`) on a public RPC node.
2. Send:
```json
{"jsonrpc":"2.0","method":"debug_traceBlockByNumber","params":["0x2", {"timeout": "999999h"}],"id":1}
```
3. Observe that `profiledTraceTx`'s `context.WithTimeout(ctx, timeout)` is created with the caller-supplied 999999-hour duration rather than being capped to the server's configured `trace_timeout`, so the trace goroutine and worker are held for far longer than intended by node operators, allowing repeated requests to exhaust the profiled trace worker pool (`maxProfiledTraceWorkers`) and hold RPC resources indefinitely relative to configuration expectations. (Full confirmation that the outer request context is never separately bounded by `api.traceTimeout` on this specific code path was not completely verifiable from the available snippets alone — the exact call chain from the JSON-RPC handler into `profiledTraceBlockByNumber`/`profiledTraceBlockByHash` was not fully traced due to index/tool limits, so this should be verified against the full source, e.g. via a Devin session with full repository access, before treating this as conclusively exploitable.)

// prepareTraceContext creates the trace timeout context and acquires a trace slot if one
// is immediately available, returning a cleanup function for acquired resources.
func (api *DebugAPI) prepareTraceContext(ctx context.Context) (context.Context, func(), error) {
	traceCtx, cancel := context.WithTimeout(ctx, api.traceTimeout)
	release, err := api.acquireTraceSemaphore(traceCtx)
	if err != nil {
		cancel()
		return nil, nil, err
	}
	return traceCtx, func() {
		release()
		cancel()
	}, nil
}

func (api *DebugAPI) TraceTransaction(ctx context.Context, hash common.Hash, config *tracers.TraceConfig) (result interface{}, returnErr error) {
	startTime := time.Now()
	defer func() {
		recordMetricsWithError(ctx, "debug_traceTransaction", api.connectionType, startTime, returnErr, recover())
	}()

	if returnErr = api.validateTraceTracer(config); returnErr != nil {
		return nil, returnErr
	}
	if returnErr = api.guardHistoricalDebugTraceByTxHash(ctx, "debug_traceTransaction", hash); returnErr != nil {
		return nil, returnErr
	}

	if cached, ok := api.tryTraceCache(hash, config); ok {
		return cached, nil
	}

	ctx, done, err := api.prepareTraceContext(ctx)
	if err != nil {
		return nil, err
	}
	defer done()

	if config == nil {
		config = &tracers.TraceConfig{}
	}
	api.clampDefaultStructLogLimit(config)
	traced, err := api.tracersAPI.TraceTransaction(ctx, hash, config)
	return resultUnlessExpired(ctx, traced, err)
}
