### Title
OP_RETURN data output excluded from weight/fee calculation permits non-standard or under-funded transactions that cannot relay, stranding inputs - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output carrying up to 80 bytes of caller-supplied data to the transaction, but computes the transaction weight, vbytes, `needed_fee`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` standardness check using only `payments` — the data output is never included in the size estimate. A transaction that embeds data can therefore be built (and signed) while actually exceeding the standard weight limit or paying an effective feerate below the relay minimum, causing nodes to reject it while the inputs remain committed to that exact transaction shape.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- Lines 194–202 push the `OP_RETURN` output onto `tx_outs` when `data` is `Some`, before any size estimation occurs.
- Line 204 computes `(weight, vbytes)` via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds a dummy transaction containing only the payment outputs (lines 85–94). The `OP_RETURN` output is not modeled.
- The change-recalculation path at lines 225–227 also passes `payments` without the data output, so `weight`/`needed_fee` are never corrected even when change is added.
- The relay-fee gate at lines 206–213 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) uses the underestimated `vbytes`, so it can pass while the real transaction is below the minimum feerate.
- The standardness gate at lines 241–243 (`weight > MAX_STANDARD_TX_WEIGHT`) uses `weight` that omits the ~92-byte (368 weight-unit) data output, so a boundary transaction can pass the check and still exceed `MAX_STANDARD_TX_WEIGHT` on the wire.

Because every input uses `sequence: Sequence::MAX` (line 182), the resulting transaction does not signal BIP-125 replaceability; a rejected or non-propagating transaction cannot be fee-bumped, and the FROST signature in `TransactionSignMachine::sign` (lines 383–391) binds `Prevouts::All` to this exact transaction, so the signature cannot be reused for a corrected transaction.

### Impact Explanation
A caller (in Serai's architecture, an unprivileged user whose dispatch creates a `Payment`/data-bearing out-transaction) can cause the multisig to produce a Bitcoin transaction that standard Bitcoin nodes will not relay or accept — either because its real weight exceeds `MAX_STANDARD_TX_WEIGHT` or because its effective feerate is below `DEFAULT_MIN_RELAY_TX_FEE` despite the `TooLowFee` guard. This is the direct analog of the report class: the consensus-level "message" (the signed transaction) cannot be completed/accepted on the destination layer, and there is no fallback — the signed transaction is un-broadcastable and non-replaceable, so the consumed inputs are stranded until an entirely new signing round produces a different transaction, exactly mirroring "L1 succeeded, L2 fails, no refund path."

### Likelihood Explanation
Any transaction built with `data: Some` is affected. Whether it actually fails depends on boundary conditions (payments near the weight cap, or fee-per-vbyte at/near the minimum), so it is not guaranteed for every data transaction, but it is deterministically reachable with public inputs — the data bytes are attacker/user-controlled up to 80 bytes — and requires no key material, collusion, or validator misbehavior.

### Recommendation
Include the `OP_RETURN` output in `calculate_weight_vbytes` (e.g., pass the full intended output list, or add the data output to the dummy transaction) so that `vbytes`, `needed_fee`, the relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check reflect the real transaction. Additionally, consider checking the final `tx`'s actual `weight()` directly rather than the estimate, and/or setting `sequence` to an RBF-signaling value so under-fee transactions can be bumped without a new signing round.

### Proof of Concept
Conceptual construction: create `payments` and `inputs` such that `calculate_weight_vbytes(inputs, payments, None)` yields `weight` just under `MAX_STANDARD_TX_WEIGHT` (or `needed_fee` exactly equal to `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`). Then call `SignableTransaction::new(inputs, &payments, None, Some(vec![0u8; 80]), fee_per_vbyte)`. The constructor returns `Ok`, but the resulting `tx` (line 246–251) contains an extra `OP_RETURN` output (~368 weight units / ~92 vbytes) never accounted for: `tx.weight()` exceeds `MAX_STANDARD_TX_WEIGHT` (or its true fee rate falls below the relay minimum), so Bitcoin nodes reject it, while `needed_fee()` and the internal checks all reported it valid.
