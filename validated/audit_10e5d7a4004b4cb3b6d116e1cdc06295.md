### Title
Missing Beneficiary Address Validation in `IntentGatewayV2.withdraw()` Permanently Locks Escrowed Order Funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core defect is a **transfer path that moves custody funds to an attacker/user-supplied destination without validating that the destination can actually receive/use them**, permanently locking the funds. The same defect pattern exists in `IntentGatewayV2.withdraw()`, which decodes a `beneficiary` address directly from an untrusted `bytes32` field and immediately releases escrowed order funds (native + ERC20 + fee-token) to it — with no zero-address or well-formedness check — before permanently marking the order as filled/claimed.

### Finding Description
`withdraw()` decodes the beneficiary straight from the message body and uses it for every fund movement in the function: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }
    _orders[body.commitment][token] -= amount;
    ...
}
```

There is no check that `beneficiary != address(0)` (or otherwise unusable) before:
1. Writing `_filled[body.commitment] = beneficiary`, which permanently marks the commitment as settled — there is no re-withdraw or recovery path once this is set.
2. Pushing native ETH via `.call{value: amount}("")` (which trivially "succeeds" against `address(0)`) and ERC20 tokens via `.transfer(beneficiary, amount)` (most ERC20s permit transfers to the zero address, effectively burning them).

This mirrors the `BeraBitcoin.transfer()` bug exactly in structure: a value-moving function accepts a destination address without validating it is capable of receiving/using the funds, so once the transfer executes the tokens become permanently stuck (here, burned to `address(0)` or sent to an inert/precompile address) and the settlement bookkeeping (`_filled`) is already finalized, so there is no way to reclaim them.

The `beneficiary` in `WithdrawalRequest` arrives via a cross-chain `RedeemEscrow`/`RefundEscrow` POST request body, decoded in `onAccept` and forwarded to `withdraw()`. Because this value is only ABI-decoded from `bytes32` (`address(uint160(uint256(body.beneficiary)))`), any zero/garbage upper-96-bit-cleared value, whether from a benign encoding bug on the counter-party chain, an integer/casting error in message construction, or a maliciously crafted commitment on the source side, results in `beneficiary == address(0)` (or another inert precompile address) without the transaction reverting.

### Impact Explanation
Escrowed order funds — the core custody assets of the intents settlement system — are moved to an unusable address and the corresponding commitment is simultaneously marked filled in `_filled`, permanently foreclosing any retry, refund, or recovery. This is a direct, permanent loss of bridged/escrowed funds, matching the bounty's "stealing or loss of funds" and "false/incorrect settlement to the wrong beneficiary" categories.

### Likelihood Explanation
The path is reached through the ordinary `RedeemEscrow`/`RefundEscrow` message flow processed in `onAccept` for every cross-chain intent settlement; no privileged actor, malicious relayer, or governance action is required — only that the beneficiary field decode to the zero address (e.g., through a legitimate cross-chain message whose `beneficiary` bytes32 happens to have all lower 20 bytes zero, or through a caller-controlled commitment that encodes such a value). Given there is no guard anywhere in `withdraw()` or its caller against this, the likelihood of it being triggered — intentionally or accidentally — is non-trivial for a public, always-reachable settlement entrypoint.

### Recommendation
Add an explicit `require(beneficiary != address(0))` (and reject any other well-known burn/precompile addresses if desired) at the start of `withdraw()`, reverting the whole settlement rather than silently finalizing `_filled` and destroying funds. If revert-on-invalid-beneficiary is undesirable given cross-chain message delivery guarantees, escrow the funds under a recoverable holding account instead of directly to the unvalidated `beneficiary`.

### Proof of Concept
1. A cross-chain settlement message triggers `onAccept` with `RequestKind.RedeemEscrow` (or `RefundEscrow`), carrying a `WithdrawalRequest.beneficiary` value whose lower 20 bytes are all zero (e.g. `bytes32(0)` or any value where `uint160(uint256(beneficiary)) == 0`).
2. `withdraw()` decodes `beneficiary = address(0)`, sets `_filled[commitment] = address(0)`.
3. For native token legs, `address(0).call{value: amount}("")` succeeds trivially (any external call with value to a non-contract address succeeds), and for ERC20 legs, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, address(0), amount))` succeeds for tokens that don't explicitly block zero-address transfers.
4. The escrowed `amount` is now unrecoverable (burned or sent to an address with no owner), while `_orders[commitment][token]` is decremented and `_filled[commitment]` is already set, permanently foreclosing recovery via cancellation/refund paths.
