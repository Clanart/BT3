### Title
Anyone can construct `ThresholdKeys` with fully attacker-chosen parameters and verification shares, producing an arbitrary group key the attacker secretly controls - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::new` (and its public deserialization path `ThresholdKeys::read`) validates only the *shape* of the supplied parameters — share count, participant index range, and the `Constant`-interpolation `t == n` rule — but never verifies that the claimed `secret_share` is consistent with `verification_shares[params.i()]` (`generator() * secret_share == verification_shares[i]`), nor that the verification shares represent any real key-generation protocol output. Analogous to the unguarded `RoundFactory::create`, any party can feed arbitrary bytes to `ThresholdKeys::read` and instantiate a fully "valid" `ThresholdKeys` object carrying a group key of their own choosing.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, `i`, an interpolation method, a `secret_share` scalar, and `n` verification shares, then calls `ThresholdKeys::new`, which computes `group_key` by interpolating `verification_shares[1..=t]` and returns `Ok` without any proof or consistency check that these values came from an authorized DKG or are internally consistent:

```rust
// crypto/dkg/src/lib.rs:355-378
if verification_shares.len() != usize::from(params.n()) { ... }
for participant in verification_shares.keys().copied() {
  if u16::from(participant) > params.n() { ... }
}
// no check: C::generator() * secret_share == verification_shares[&params.i()]
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

Two distinct consequences follow:

1. **Attacker-controlled group key.** The attacker picks `n` scalars `x_1..x_n`, sets `verification_shares[j] = G * x_j`, picks any `i`, `t`, `secret_share`, and serializes. Because the attacker knows every `x_j`, they know the discrete log of the interpolated `group_key`. Any system that ingests attacker-supplied serialized `ThresholdKeys` (key import, backup restore, handoff of DKG output) will derive a group key/address the attacker fully controls, while `params.i()` may point at a victim participant index.

2. **Inconsistent self-share → false blame / silent corruption.** If instead `secret_share` does not match `verification_shares[i]`, every downstream use (`view()` → FROST `AlgorithmSignMachine::sign` → `verify_share`/`BatchVerifier`) produces a signature share that fails verification and is blamed on the holder (`FrostError::InvalidShare(i)`), or, for the aggregate path in `SignatureMachine::complete`, reaches `InternalError("everyone had a valid share yet the signature was still invalid")` — which the code itself attributes to "deserialize a semantically invalid FrostKeys".

Notably, `dkg/recovery::recover_key` *does* check `C::generator() * res == group_key` (crypto/dkg/recovery/src/lib.rs:80), showing the codebase recognizes the need for consistency verification — `ThresholdKeys::new` just lacks it. Contrast also with `Curve::read_G` in crypto/frost, which rejects identity points, while `ThresholdKeys::new` accepts arbitrary (including identity/attacker-known-dlog) verification shares.

### Impact Explanation
An unprivileged party able to get serialized key material accepted produces a `ThresholdKeys` whose `group_key()` — the value networks derive deposit addresses/validator keys from — is either fully attacker-controlled (they know the underlying secret via known `x_j`s), or whose shares can never produce valid signatures, bricking the key. In the first case this is effective key theft: any funds associated with the imported group key are spendable by the attacker, and any signature emitted is a signature under a key the attacker owns, regardless of the claimed participant index.

### Likelihood Explanation
The exploit path requires an attacker to supply the serialized `ThresholdKeys` bytes — e.g., a malicious peer or service providing "recovered"/"exported" key material, or a compromised storage layer serving key blobs to a node on startup. `ThresholdKeys::read` is a public API accepting arbitrary reader input; nothing in the type proves provenance. Deterministically reachable with trivially crafted bytes — no probabilistic or timing requirement.

### Recommendation
In `ThresholdKeys::new`, after computing `group_key`, verify the local share is consistent: `C::generator() * secret_share == verification_shares[&params.i()]` (returning a new `DkgError` variant on failure). This rejects mismatched self-shares but cannot prove the other `n-1` shares correspond to a real sharing — so additionally, callers importing key material should treat deserialized `ThresholdKeys` as unauthenticated and require an attestation/proof of protocol provenance (e.g., the PedPoP `BlameMachine`-attested result, or a signed key commitment), rather than accepting raw bytes. Optionally also reject identity/zero verification shares.
