### Title
Missing `_filled` state check lets a permissionless destination-chain cancellation race and override a genuine solver fill, diverting escrowed input tokens away from the solver - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
Like the Linea `finalizeCompressedBlocksWithProof` bug — where the contract finalized a caller-supplied `finalBlockNumber` without checking it against the actual last submitted block, letting the prover silently skip data — `ExtrinsicIntents._cancelFromDest` and `_fillCrossChain` both write to the `_filled[commitment]` mapping and dispatch a cross-chain settlement message (`RedeemEscrow` / `RefundEscrow`) without first checking the *existing* value of `_filled[commitment]`. Neither function verifies that the order hasn't already been finalized by the other path before proceeding, so a genuine solver fill and a permissionless post-deadline cancellation can race independently over Hyperbridge, and whichever message reaches the source chain first is the one that gets settled — irrespective of what actually happened on the destination chain.

### Finding Description
`_fillCrossChain` (evm/src/apps/intentsv2/ExtrinsicIntents.sol, lines 89-171) unconditionally sets: [1](#0-0) 
with no guard such as `if (_filled[commitment] != address(0)) revert Filled();` before the solver pays out real output tokens and a `RedeemEscrow` message is dispatched to the source chain.

`_cancelFromDest` (same file, lines 240-267) is **permissionless once `order.deadline` has passed** (`if (order.deadline >= _blockNumber())` only gates the pre-deadline case), and it also unconditionally overwrites the same mapping: [2](#0-1) 

Neither function checks the prior value of `_filled[commitment]` before mutating it and dispatching a settlement message. This is the exact analog of the audited bug: a contract state transition (finalization of an order/escrow) is committed on the basis of caller-supplied data without validating it against the *actual* recorded prior state (`finalBlockNumber` vs. the real last submitted block; here, `_filled[commitment]` vs. whether the order was already filled).

On the source chain, `onAccept` (lines 289-309) routes both `RedeemEscrow` and `RefundEscrow` requests to the same `_withdraw` function: [3](#0-2) 
`_withdraw` (evm/src/apps/intentsv2/IntentsBase.sol, lines 390-425) decrements `_orders[commitment][token]` and reverts only if the escrow entry is already zero: [4](#0-3) 

Because both `RedeemEscrow` (from a real fill) and `RefundEscrow` (from an unguarded cancel) are independent Hyperbridge messages dispatched separately and delivered by whichever relayer/proof arrives first, **the destination-side fill does not causally block or invalidate a concurrently-dispatched cancel**, and vice versa. The `_orders` ledger only prevents *double*-spending the escrow (second message reverts with `UnknownOrder`); it does not ensure the *correct* message (the one matching what genuinely happened on the destination chain) is the one that wins the race.

### Impact Explanation
A solver can fill an order on the destination chain — transferring real output tokens to the beneficiary out of its own funds — and dispatch `RedeemEscrow`. Before that message is delivered and settled on the source chain, any unprivileged caller can invoke the destination-chain cancel path once `order.deadline` has passed, which calls `_cancelFromDest` and dispatches a competing `RefundEscrow` message to the source chain, without any check that `_filled[commitment]` was already set by the solver's fill. If the `RefundEscrow` message reaches the source chain first (a routine race condition in independent cross-chain message delivery, not requiring a malicious relayer), the escrowed input tokens are released back to the original user instead of to the solver who already paid out on the destination chain. The solver permanently loses the value it fronted — direct loss of funds to an unprivileged party (the solver), triggered purely by public, permissionless entrypoints and normal message-delivery timing, matching the bounty's "stealing or loss of funds" / "logic attacks" / "wrong beneficiary or amount" criteria.

### Likelihood Explanation
Both entrypoints (`fillOrder`-style dispatch of `_fillCrossChain`, and the cancel path invoking `_cancelFromDest`) are public/permissionless once the order deadline passes, and no relayer collusion, admin action, or leaked key is required — only ordinary asynchronous message delivery over Hyperbridge, which can vary in timing between independent dispatches. Any solver who fills an order close to its deadline is exposed to this race whenever a third party (or the user itself) submits the cancellation once the deadline is reached.

### Recommendation
In `_fillCrossChain`, revert if `_filled[commitment] != address(0)` before marking the order filled and dispatching `RedeemEscrow`. In `_cancelFromDest` (and `_cancelFromSource`'s downstream `onGetResponse` finalize path), revert if `_filled[commitment] != address(0)` before marking the order cancelled/refunded and dispatching `RefundEscrow`. This mirrors the Linea fix pattern of validating the finalization value against the actual last recorded state before allowing settlement, ensuring only the first genuine state transition (fill XOR cancel) can dispatch a settlement message, and the second attempt fails at the source of truth rather than racing on delivery order.

### Proof of Concept
1. User places a cross-chain order with a short-ish deadline; the source-chain gateway escrows `order.inputs`.
2. Near the deadline, a solver calls the fill entrypoint on the destination chain, which invokes `_fillCrossChain`: solver transfers output tokens to `beneficiary`, sets `_filled[commitment] = solver`, and dispatches `RedeemEscrow` to the source chain [5](#0-4) .
3. Immediately after the deadline elapses, any third party calls the cancel entrypoint on the destination chain, which invokes `_cancelFromDest` (no `msg.sender` restriction post-deadline, no check of `_filled[commitment]`): it overwrites `_filled[commitment] = order.user` and dispatches `RefundEscrow` to the source chain [6](#0-5) .
4. Both `RedeemEscrow` and `RefundEscrow` messages are independently relayed to the source chain. If the `RefundEscrow` message is delivered and processed first, `onAccept` → `_withdraw` releases the escrowed input tokens to `order.user` and zeroes `_orders[commitment][token]` [7](#0-6) .
5. When the solver's `RedeemEscrow` message later arrives, `_withdraw` sees `escrowed == 0` and reverts with `UnknownOrder`, permanently denying the solver the escrowed compensation it was owed for tokens it already delivered on the destination chain.

I was not able to inspect the public wrapper function(s) that call `_cancelFromDest`/`_fillCrossChain` (e.g., in `IntentGatewayV2.sol`) to confirm there is no additional guard added at that layer; this should be verified in a live session, but based on the code paths in `ExtrinsicIntents.sol` and `IntentsBase.sol` shown here, no such guard exists in the reachable internal logic.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        if (options.nativeDispatchFee > 0 && msgValue >= options.nativeDispatchFee) {
            IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request);
            msgValue -= options.nativeDispatchFee;
        } else {
            dispatchWithFeeToken(request);
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
