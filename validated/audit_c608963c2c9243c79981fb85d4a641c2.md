### Title
Missing slippage protection combined with attacker-forceable full-buyback routing in `SmartWomConvert.smartConvert` allows value extraction from `womMWomPool` LPs - (File: wombat/SmartWomConvert.sol)

### Summary
`smartConvert` computes `convertRatio` from `maxSwapAmount()`, which reads `IAsset(womAsset).cash()`/`liability()` from an external Wombat pool the attacker can skew with an ordinary, unprivileged deposit/withdraw. This lets an attacker force nearly all of `_amountIn` through the "buyback" branch of `_convertFor`, which swaps WOM→mWom via `IWombatRouter.swapExactTokensForTokens(... , 0, ...)` with **zero slippage protection**. Combined with a self-sandwich of `womMWomPool`'s price, the attacker can extract more mWom than the WOM contributed, at the expense of that pool's liquidity providers.

### Finding Description
`maxSwapAmount()` throttles how much of a conversion can go through the discretionary buyback swap path: [1](#0-0) 
This value is derived purely from `womAsset.cash()`/`liability()`, values on an external Wombat pool that any unprivileged actor can move by performing ordinary (self-funded) deposit/withdraw calls against that pool, since Wombat's constant-sum/coverage-ratio AMM design ties the deposit/withdraw haircut and liability-minting formula to the current coverage ratio, allowing temporary skew of `cash` vs `liability`.

`smartConvert` then uses this manipulable value to size the swap: [2](#0-1) 
By inflating `(liability - cash)`, an attacker can drive `maxSwap >= _amountIn`, forcing `convertRatio` to `0` — i.e., routing 100% of `_amountIn` into the swap branch of `_convertFor` rather than the safe 1:1 mint branch.

Critically, that swap branch has no per-call slippage protection: [3](#0-2) 
`swapExactTokensForTokens` is called with `minAmountOut = 0`. The only downstream check is the aggregate floor: [4](#0-3) 
and in `smartConvert` this floor is hardcoded to `_minRec = _amountIn` — it only guarantees the caller doesn't lose principal, it does not cap the upside the caller can extract from the pool at manipulated prices.

Exploit flow: attacker (1) skews `womMWomPool`'s price so mWom is artificially cheap (a swap into the pool), (2) skews `womAsset`'s cash/liability via deposit/withdraw so `maxSwapAmount()` forces `convertRatio → 0` (full buyback) for their `_amountIn`, (3) calls `smartConvert(_amountIn, _mode)`, which executes the unprotected router swap at the manipulated favorable price, yielding `amountRec > _amountIn` beyond what would occur at the true market rate, (4) reverses both manipulations in the same block/transaction, paying only ordinary swap/haircut fees. The attacker walks away with `obtainedmWomAmount - _amountIn` extracted value beyond normal arbitrage margins, funded by `womMWomPool`'s LPs (and indirectly by `mWom`'s backing integrity if `womMWomPool` reserves are treated as backing).

Existing checks that fail to prevent this: `_minRec` only floors the caller's own loss, not the pool's loss; there is no `minAmountOut` on the internal swap; `maxSwapAmount()`'s inputs are read live from an externally-influenceable pool state with no TWAP or manipulation resistance; there is no reentrancy or same-block guard preventing the attacker from bracketing the call with pool-skewing transactions.

### Impact Explanation
This is a direct value-extraction bug: an unprivileged actor can repeatedly drain value from `womMWomPool` liquidity providers by forcing oversized, unprotected buyback swaps at self-manipulated prices, netting more mWom per WOM contributed than fair market rate. Depending on how `womMWomPool` reserves relate to overall mWom backing, this also degrades the WOM-backing invariant of `mWom`, matching an Immunefi "theft of funds / protocol insolvency (partial)" impact class.

### Likelihood Explanation
The attack requires only self-funded capital (no privileged role), can be executed atomically within one transaction/block (flash-loanable), and is repeatable indefinitely as long as the attacker can afford the round-trip fees/haircuts on `womMWomPool` and `womAsset`'s deposit/withdraw. The main friction is the swap/haircut fees paid during the skew-and-restore cycle, which must be smaller than the extracted mWom surplus — feasible when pool liquidity is shallow relative to attacker capital or when `ratio`/`buybackThreshold` settings make the throttle bypass valuable.

### Recommendation
- Add a real `minAmountOut` to the internal `swapExactTokensForTokens` call in `_convertFor`, computed from a TWAP or oracle-independent fair-value bound, not `0`.
- Derive `maxSwapAmount()` from a time-weighted or otherwise manipulation-resistant measure of pool imbalance instead of instantaneous `cash()`/`liability()`.
- Consider requiring `_minRec` to be caller-supplied (not hardcoded to `_amountIn`) with an upper/lower band check, or splitting risk by capping buyback swap size independent of a single spot read.

### Proof of Concept
Foundry fork test outline:
1. Fork a network with live Wombat `womMWomPool`/`womAsset` and deployed `SmartWomConvert`.
2. As attacker EOA: (a) swap a large amount of mWom→WOM in `womMWomPool` to depress mWom price; (b) deposit/withdraw WOM in the pool backing `womAsset` to push `liability - cash` upward so `maxSwapAmount() >= _amountIn`.
3. Approve and call `smartConvert(_amountIn, 0)`.
4. Reverse steps (a)/(b) (swap back, withdraw/redeposit) to restore pool state.
5. Assert `obtainedmWomAmount - _amountIn` (from `mWomConverted` event or `mWom.balanceOf(attacker)` delta) is strictly greater than the amount achievable from an unmanipulated baseline call under identical `_amountIn`/`_mode`, beyond the pool's stated swap fee, demonstrating extraction from `womMWomPool` LPs.

```text
    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
```
