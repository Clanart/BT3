### Title
Divergent conflict-marker parsers in Copilot merge-conflict resolution cause silent misassignment of resolved content, corrupting files before they are committed/pushed - (File: app/src/lib/copilot-conflict-context.ts, app/src/lib/copilot-conflict-resolution.ts)

### Summary
The Copilot AI conflict-resolution feature extracts conflict hunks from a file with one line-scanning parser (`extractConflictHunks`) to build the prompt sent to the model, and later splices the model's per-hunk resolutions back into the *same raw file content* with a second, independently-written line-scanning parser (`reassembleResolvedFile`). The two parsers handle malformed/unbalanced conflict-marker sequences differently. A file that contains such a sequence — trivially plantable by anyone who can influence content merged into the working tree (e.g., a collaborator's branch, a fetched remote, or content copied from another repo) — causes the two parsers to disagree about where hunk boundaries are. Because the only sanity check performed (`validateResolutionPaths`) compares hunk *counts*, not hunk *positions*, a coincidental count match lets resolved content for one conflict get spliced into a different location in the file, silently corrupting the file that the user then stages, commits, and pushes.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-260`) walks the file looking for `<<<<<<<` markers. When it fails to find a matching `>>>>>>>` before EOF, it treats the *whole remaining file* as consumed by the "theirs" section and drops that hunk entirely: [1](#0-0) 

Because the inner `while (i < lines.length)` loop that gathers `theirsLines` has no early bail-out on encountering a *new* `<<<<<<<`/`=======`/`>>>>>>>` sequence, any subsequent, well-formed conflict block located after a malformed one is silently swallowed and never becomes part of the model's input, and never counted as an expected hunk.

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`), which is run later against the exact same raw file content to splice the model's resolutions back in, handles the same malformed case very differently: it copies only the single unmatched `<<<<<<<` line through as ordinary content and continues scanning line-by-line from the very next line: [2](#0-1) 

This means content that `extractConflictHunks` swallowed (and never exposed to the model) can still be re-parsed by `reassembleResolvedFile` as one or more *new* conflict blocks (its `=======`/`>>>>>>>` remnants can pair up with markers that were never part of a hunk the model resolved).

The only guard against this divergence, `validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`), enforces that the model returned exactly as many hunks per file as `extractConflictHunks` originally counted: [3](#0-2) 

This check only compares counts — it has no way to detect that `reassembleResolvedFile` will walk a different set of marker boundaries in the same raw content. If the counts happen to match (e.g., the swallowed trailing block plus a legitimate leftover marker produces the same total number of `hunkIndex` increments as the model was asked to resolve), `reassembleResolvedFile` will splice `hunkResolutions[k]` (intended for logical conflict *k*) into a *different* structural position in the file than where the model's context said conflict *k* was.

### Impact Explanation
This breaks the invariant that "all non-conflicted code is preserved exactly, and the model's output is only responsible for the small resolved sections" (as stated in the function's own doc comment). Since Desktop's Copilot conflict-resolution flow writes `resolvedContent` back to disk and stages it for the user's next commit, a resolution silently applied to the wrong code region — potentially deleting unrelated code, duplicating a wrong branch's content, or inserting text into an unintended location — corrupts what the user commits and subsequently pushes, without any error, warning, or diff-count mismatch surfaced to the user. This lands squarely in the requested impact category of "silent corruption of what the user commits or pushes," triggered purely by content in a merged/fetched branch that the attacker controls (no local access, no credentials, no social engineering needed beyond having the victim merge/rebase against attacker-influenced content and use the AI-assisted resolution feature).

### Likelihood Explanation
Triggering the divergence requires crafting a file containing an unbalanced/malformed conflict-marker-like sequence (e.g., embedding literal `<<<<<<<`/`=======`/`>>>>>>>`-shaped text such as documentation showing example Git conflicts, or a nested/aborted merge artifact) positioned before a real, legitimate conflict block in the same file, in a way that produces a hunk-count collision. This is a genuinely reachable but somewhat narrow condition (requires knowledge of the exact parsing quirks and careful crafting to make counts collide), and depends on the victim opting into the Copilot AI merge-conflict-resolution feature and accepting its output without manually re-verifying the diff. It's plausible but not trivially guaranteed to succeed on the first attempt — it likely requires some experimentation to reliably produce a matching hunk count while causing the desired misalignment.

### Recommendation
Unify the conflict-marker parsing logic used by `extractConflictHunks` and `reassembleResolvedFile` into a single shared parser so both stages agree exactly on hunk boundaries for the same raw content. Additionally, `reassembleResolvedFile` should record markers/anchors (e.g., a hash or the original marker line index) alongside each extracted hunk in `IConflictHunk`, and `reassembleResolvedFile`/`validateResolutionPaths` should verify positional/structural correspondence — not just counts — before splicing, rejecting the resolution with a `CopilotValidationError` if the reconstructed marker positions don't match what was sent to the model.

### Proof of Concept
1. Create a file `example.md` containing, before any real conflict, a malformed/unclosed marker sequence such as:
```
<<<<<<< some-doc-example
(no closing marker; EOF reached inside extractConflictHunks' theirs-collection loop for a merge that touches this file elsewhere)
```
2. Ensure the same file, further down, has an actual git-generated conflict block from a real three-way merge (`<<<<<<< HEAD ... ======= ... >>>>>>> feature`).
3. Trigger a merge/rebase in Desktop against a branch containing this content (e.g., fetched from an attacker-controlled remote/fork) and invoke the Copilot conflict-resolution feature.
4. Because `extractConflictHunks` swallows everything from the first unclosed `<<<<<<<` to EOF (dropping the real trailing conflict from the model's context and expected-hunk count), while `reassembleResolvedFile` treats the same malformed line as ordinary content and continues scanning line-by-line, the two functions can end up agreeing on a hunk *count* while disagreeing on hunk *location*. The resulting `resolvedContent` written to disk splices the model's resolution into the wrong region of the file.
5. Confirming the exact minimal marker sequence that produces a count collision (rather than a mismatch caught by `validateResolutionPaths`) would require local experimentation against `extractConflictHunks` and `reassembleResolvedFile`, which was not runnable in this read-only analysis — this is noted as an area needing hands-on verification with a Devin session that can execute the code and unit tests in `app/test/unit/copilot-conflict-resolution-test.ts` and `app/test/unit/copilot-conflict-context-test.ts`.
