## Analysis Summary

The H-16 core invariant break is: **a contract in the custody chain performs an operation on behalf of "whoever calls it," with no check that the caller is the authorized orchestrator**, letting an attacker trigger an accounting/asset-moving operation the balance-tracking logic assumes only the legitimate flow can invoke. In Hyperbridge, the closest exact local analog is `CallDispatcher.dispatch()` — a permissionless, unauthenticated relay contract that `IntentGatewayV2.placeOrder`'s predispatch flow uses to temporarily hold and forward escrowed tokens, but which any address can call directly to move whatever balance the dispatcher currently holds.

### Title
Unauthenticated `CallDispatcher.dispatch()` allows theft of any token/ETH balance temporarily held by the shared dispatcher during `placeOrder` predispatch - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared, stateless contract used by `IntentGatewayV2.placeOrder` to route "predispatch" calls (e.g. unwrapping LP tokens before escrow). Its `dispatch(bytes)` function is `external` with **no caller restriction whatsoever** — it will execute any `Call[]` (arbitrary `to`, `value`, `data`) sent by any address, and those inner calls run with `msg.sender == dispatcher`. During `placeOrder`'s predispatch path, real user funds are transferred onto `dispatcher` and briefly sit there between two separate `dispatch()` invocations while the predispatch swap/call executes and before the resulting balance is swept back into the gateway. [1](#0-0) 

### Finding Description
`placeOrder`'s predispatch branch:
1. Transfers `order.predispatch.assets` tokens/ETH to `dispatcher`.
2. Calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — an arbitrary, user-supplied call executed *as* the dispatcher (e.g., a Uniswap unwrap/swap).
3. Reads `IERC20(token).balanceOf(dispatcher)` for each `order.inputs[i].token` and builds a second `Call[]` that instructs the dispatcher to `transfer` its *entire current balance* of that token back to the gateway.
4. Calls `dispatch()` again to execute the sweep. [2](#0-1) 

Two structural problems combine into a fund-loss path:

- **`dispatch()` has no access control** — any external account, not just `IntentGatewayV2`, can call it and instruct the dispatcher to move out any token/ETH it is currently holding, to any destination. There is no `onlyGateway`, no reentrancy guard, and no notion of "whose funds these are."
- **The sweep in `placeOrder` only sweeps balances of `order.inputs` tokens**, not the original `predispatch.assets` token. If the user-supplied `order.predispatch.call` (e.g., an LP-unwrap or swap) does not fully consume the deposited `predispatch.assets` — leaving residual pre-swap token dust, or leaving any token not listed in `order.inputs` — that residue is left sitting on the shared `dispatcher` contract after `placeOrder` completes, because nothing ever sweeps it out.

Because `dispatcher` is a single global singleton reused across every `placeOrder` call from every user, this residue accumulates as unswept custody balance on a contract whose only movement primitive (`dispatch`) is fully public. Any attacker can then call `CallDispatcher.dispatch()` directly with a `Call` targeting the residual ERC20 token's `transfer(attacker, amount)` (or a raw ETH transfer via `call.value`), draining funds that came from other users' escrowed orders — with `msg.sender` for that ERC20 transfer being the dispatcher itself, so no allowance or ownership check on the token side stops it.

This mirrors H-16's structural flaw exactly: `_claimRewards`/`getReward` assumed only the legitimate caller could move the balance being accounted for, but the underlying primitive was actually callable by anyone, letting an outsider manipulate the balance the trusted accounting logic relied on. Here, `dispatch()` is the "public getReward-equivalent" that anyone can invoke to move balances the escrow accounting (`balanceOf(dispatcher)` reads in `placeOrder`) assumes are exclusively under `IntentGatewayV2`'s control.

### Impact Explanation
Funds temporarily custodied by `CallDispatcher` — which include real user escrow deposits and any unswept dust left by imperfect predispatch swaps — can be stolen outright by any unprivileged address calling `dispatch()` directly. This is a direct loss-of-funds / unauthorized-execution vector matching the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories, requiring no malicious relayer, prover, or admin — just a plain EOA watching the mempool or scanning `dispatcher`'s token balances.

### Likelihood Explanation
High. `dispatch()` is a public, stateless entrypoint with zero access control — exploitation requires no special timing, no governance, and no compromised infrastructure. Any residual balance on `dispatcher` (from a predispatch swap that doesn't perfectly zero out its input token, from a user's own predispatch call leaving dust, or from a partially-consumed multi-hop swap) is immediately and permanently at risk until drained by whoever notices first.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the intended orchestrator (e.g., `onlyGateway`/an allowlist of trusted callers), or make dispatcher instances per-order/ephemeral (e.g., deployed via CREATE2 per commitment and self-destructed/swept fully at the end of `placeOrder`) so no shared, publicly-drainable balance can ever persist between transactions. Additionally, `placeOrder`'s predispatch sweep should sweep *all* tokens the predispatch call could plausibly touch (or explicitly document/require that `order.predispatch.call` fully zero out its input balances), rather than only sweeping `order.inputs` tokens, to avoid leaving custodial dust on a contract that must remain public.

### Proof of Concept
1. A user calls `IntentGatewayV2.placeOrder` with a `predispatch` block whose `call` performs a Uniswap swap that consumes only 99% of the deposited `predispatch.assets` token (routine slippage/rounding), leaving 1% as residual balance on `CallDispatcher`.
2. `placeOrder` sweeps only `order.inputs` tokens (the swap's output token) back to the gateway; the leftover input-side token dust remains on `CallDispatcher`.
3. An attacker, observing `CallDispatcher`'s ERC20 balance via `balanceOf`, calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: transfer(attacker, residualAmount)})]))` directly.
4. Since `dispatch()` performs no caller check, the call succeeds; the ERC20 `transfer` executes with `msg.sender == dispatcher`, moving the residual balance to the attacker.
5. Repeating this across many `placeOrder` calls (each leaving small dust on the same shared dispatcher) lets the attacker continuously drain funds that were never accounted for as protocol dust nor returned to any user, with no dependency on relayers, provers, or governance. [1](#0-0) [3](#0-2)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
