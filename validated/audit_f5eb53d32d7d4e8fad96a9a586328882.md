### Title
Refundable outputs with undetectable `presumed_origin` are permanently locked with no refund plan created - (File: processor/src/networks/bitcoin.rs)

### Summary
Serai's refund path for malformed/unusable `External` deposits on Bitcoin derives the refund destination (`presumed_origin`) solely from `tx.input[0].previous_output`'s `script_pubkey`. When that script cannot be converted into a `serai` `Address` — or when the first input does not belong to the actual depositor — the processor silently drops the output and creates **no** refund `Plan`. The coins remain under multisig control forever with no path back to the user: the exact "funds locked, no withdrawal route" shape of the referenced Vault bug.

### Finding Description
`Bitcoin::get_outputs` sets `presumed_origin` by fetching the first input's prevout and calling `Address::new(spent_output.script_pubkey)` [1](#0-0) .

`instruction_from_output` returns `(presumed_origin, None)` whenever the embedded data exceeds `MAX_DATA_LEN`, fails `Shorthand::decode`, or fails `RefundableInInstruction::try_from` [2](#0-1) .

The caller then only creates a `PlanFromScanning::Refund` if `refund_to` is `Some` and converts via `try_into()`; otherwise it simply `continue`s — the scanned output is dropped, never scheduled, never refunded [3](#0-2) . The same dead-end exists in the `ForwardFromExisting` rotation step [4](#0-3) .

Any unprivileged sender can construct a deposit whose first input spends a prevout whose `script_pubkey` is not a standard address type (e.g. bare multisig, non-standard/OP_RETURN scripts, or PayJoin/coinjoin-style transactions where `input[0]` is contributed by a third party). Once confirmed, the output is recognized as belonging to the multisig (matched by `script_pubkey` in `Scanner::scan_transaction` [5](#0-4) ) yet receives no refund plan and no instruction, so the funds are unspendable-by-anyone-else and unrecoverable by the depositor.

### Impact Explanation
Funds are permanently locked in the threshold multisig: the user loses the entire deposit. Unlike the audited finding (withdrawal gated on epoch timing), here there is no code path at all to recover the output — the scanner emitted it, the processor discarded it, and no `Eventuality`/`Plan` will ever reference it.

### Likelihood Explanation
Requires a deposit transaction that (a) carries a `RefundableInInstruction` that is malformed/oversized **and** (b) has `tx.input[0]` spending a non-addressable prevout, or a transaction assembled by third-party tooling (PayJoin, batched payouts) where `input[0]` is not the depositor's. Both conditions are reachable with ordinary Bitcoin transactions an unprivileged party broadcasts; the second alone also causes refunds to be issued to an unrelated party.

### Recommendation
In `Bitcoin::get_outputs`, choose `presumed_origin` from the depositor-relevant input (or all inputs) rather than unconditionally `tx.input[0]`, and when `Address::new` fails, either synthesize a refund address from an alternate input or explicitly account for the orphaned output (e.g. emit an error event / route to a governance-recoverable plan) instead of silently dropping it.

### Proof of Concept
1. An unprivileged user crafts a funding transaction with output `script_pubkey = p2tr(multisig_key)` (External offset `Scalar::ZERO`), embedded data that is larger than `MAX_DATA_LEN` or fails `Shorthand::decode`, and makes `input[0]` spend a prevout whose `script_pubkey` is a bare multisig/`OP_RETURN` script (or participates via PayJoin so `input[0]` belongs to a counterparty).
2. `get_outputs` matches the output by `script_pubkey` and returns it as an `External` `Output` with `presumed_origin = None` (or an unrelated party's address) [6](#0-5) .
3. `instruction_from_output` returns `(None, None)` [7](#0-6) .
4. `scanner_event_to_multisig_event` hits `let Some(instruction) = ... else { ... continue }` — no refund plan is pushed since `refund_to` is `None` [3](#0-2) .
5. The output never enters any `Plan`, `Batch`, or `Eventuality`; the depositor's coins are locked in the multisig with no withdrawal or refund path.
