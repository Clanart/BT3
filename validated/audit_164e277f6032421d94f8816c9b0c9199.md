### Title
Missing minting-balance check before unsigned subtraction in mempool fee computation causes unhandled exception on malicious spend bundle submission - ([File: chia/full_node/mempool_manager.py])

### Summary
`MempoolManager.validate_spend_bundle` computes the transaction fee as `fees = uint64(removal_amount - addition_amount)` without first verifying that `addition_amount <= removal_amount`. [1](#0-0)  Unlike the equivalent block-body validation path, which explicitly checks `if removed < added: return Err.MINTING_COIN` before subtracting, the mempool path has no such guard. [2](#0-1)  This mirrors the underlying bug class of CVE-2018-20989: a missing/omitted underflow check before an arithmetic operation on an unsigned/bounded type, relying on the caller to have already validated the values.

### Finding Description
`addition_amount` is accumulated directly from `create_coin` conditions reported for each coin spend in the submitted bundle, with no upper bound relative to `removal_amount` enforced anywhere earlier in `validate_spend_bundle`. [3](#0-2)  `removal_amount` is accumulated from the actual coin records being spent. [4](#0-3)  If an attacker crafts a spend bundle whose `CREATE_COIN` conditions sum to more than the value of the coins being spent (i.e., attempts to mint value out of thin air within a single spend bundle), `removal_amount - addition_amount` is negative. Passing a negative Python `int` into the `uint64()` constructor raises a `ValueError` rather than silently wrapping, as demonstrated by the project's own tests confirming this exact failure mode for `uint64` conversions of negative sums. [5](#0-4) 

Because the balance check (`MINTING_COIN`) that exists in `block_body_validation.py` is absent from the earlier, per-transaction `validate_spend_bundle` path in the mempool, the code reaches the unguarded subtraction/conversion at line 814 instead of returning a controlled `Err` result. [6](#0-5)  This is the exact class of defect the CVE describes: an underflow-prone computation performed without the caller (the mempool tx-validation logic) checking bounds first, expecting that value never occurs.

### Impact Explanation
`validate_spend_bundle` is invoked for every spend bundle submitted from any untrusted source — wallet RPC, `push_tx`, or a peer relaying a transaction — as part of standard mempool admission. [7](#0-6)  A single unprivileged submitter can trigger this code path with one spend bundle whose declared `CREATE_COIN` outputs exceed the value of the coins spent, causing an unhandled `ValueError` at the fee-computation step instead of the intended, gracefully-handled `Err.MINTING_COIN`/rejection outcome. Depending on how far up the call chain (transaction-processing / RPC handler) this raw exception is caught, this results in improper error handling for a spend-triggered code path in transaction processing — the same "improper error handling around an underflow" bug class as the CVE, applied to mempool admission rather than ASN.1 parsing.

### Likelihood Explanation
Likelihood is straightforward to trigger: an attacker only needs to construct one spend bundle where the sum of `CREATE_COIN` amounts exceeds the sum of the coin amounts being spent, and submit it through any normal transaction-submission path (RPC `push_tx`, wallet, or peer gossip); it requires no privileges beyond being able to submit a spend bundle. No signature validity is required to reach this code because the balance-only check happens (or fails to happen) during condition-derived fee computation, ahead of/alongside more expensive validation steps.

### Recommendation
Add an explicit balance check before the subtraction/`uint64()` conversion in `validate_spend_bundle`, mirroring the one already present in `block_body_validation.py`:
```python
if addition_amount > removal_amount:
    return Err.MINTING_COIN, None, []
fees = uint64(removal_amount - addition_amount)
```
This restores the same fail-safe behavior as the consensus-level check and avoids relying on `uint64()`'s exception as an implicit, unhandled bounds check.

### Proof of Concept
1. Create/select a coin of amount `N`.
2. Construct a `CoinSpend` for that coin whose puzzle/solution emits a `CREATE_COIN` condition with amount `> N` (e.g., `N + 1`), so that `addition_amount > removal_amount` for the resulting `SpendBundle`.
3. Submit the spend bundle via `push_tx`/RPC so it flows into `MempoolManager.validate_spend_bundle`.
4. Observe that instead of a controlled `Err.MINTING_COIN`-style rejection, the call raises a `ValueError` at `fees = uint64(removal_amount - addition_amount)` (as confirmed by the negative-sum behavior demonstrated in `test_compute_block_fee`), because no minting-balance guard exists ahead of this line in the mempool validation path.
