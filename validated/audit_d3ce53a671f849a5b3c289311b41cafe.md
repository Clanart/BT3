### Title
`ReceivedOutput::read` accepts an offset/script pair the scan path would never produce, reporting unspendable outputs as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external bug class is inconsistent authorization: a restriction enforced on one code path (`Perm.Download` on direct raw download) is skipped on an alternate path to the same capability (`/api/public/dl/<hash>` only checks share permissions). The Serai analog is the two paths that produce a `ReceivedOutput`: `Scanner::scan_transaction`/`scan_block` cryptographically binds each `offset` to the output's `script_pubkey`, while `ReceivedOutput::read` (the deserialization path fed by untrusted bytes) performs no such binding and will construct a `ReceivedOutput` for any (offset, TxOut, OutPoint) triple.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` mapping each expected P2TR script to the scalar offset that derives its key (`key + G*offset`), populated by `Scanner::new` and `register_offset` at `networks/bitcoin/src/wallet/mod.rs:162-196`. `scan_transaction` only emits a `ReceivedOutput` when `output.script_pubkey` is present in that map, so the returned `offset` is guaranteed to satisfy `p2tr_script_buf(key + G*offset) == output.script_pubkey` (`mod.rs:199-214`).

`ReceivedOutput::read` (`mod.rs:122-134`) reads `offset` via `Secp256k1::read_F`, then consensus-decodes `TxOut` and `OutPoint` — but never checks that `offset` corresponds to the script in `output`. There is no key-check field at all: a `ReceivedOutput` carries only `{ offset, output, outpoint }`, so the consistency invariant enforced by the scan path is unenforced on the read path. Downstream spending (`SignableTransaction` / per-input commitment re-keying in `networks/bitcoin/src/wallet`) applies `output.offset()` to the threshold keys; with a mismatched offset the resulting signature is for `key + offset` rather than the key committed in `script_pubkey`, producing an invalid transaction. The same asymmetric-checks shape exists because `ReceivedOutput` deliberately omits the scanning key, so `read` cannot recheck it — just as the public share handler omits the owner's `Perm.Download`.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (it is explicitly a public-input reader, used by `Output::read` in `processor/src/networks/bitcoin.rs:156` and any storage/network deserialization of received outputs) can cause funds to be reported as received that are not spendable: any attacker-influenced `TxOut` with an arbitrary `offset` deserializes successfully and is treated identically to a scanner-produced output. This meets the "funds reported received that are not spendable" acceptance criterion — the wallet/scheduler will attempt to sign for `key + offset` which does not match the output's P2TR key, so the spend fails (or, where the mismatched offset silently maps to a different registered kind per `processor/src/networks/bitcoin.rs:324-344` semantics, funds get misclassified).

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ReceivedOutput::read`. In-process scan outputs are always consistent, so exploitation requires a deserialization surface carrying untrusted data (e.g., externally supplied output records or corrupted/malicious upstream data). Impact is limited to misattribution/failed spends rather than direct theft, matching a Medium severity.

### Recommendation
Either include the derived script's key binding in `ReceivedOutput` (store the expected `ScriptBuf` key or the base key so `read` can recompute `p2tr_script_buf(key + G*offset)` and compare against `output.script_pubkey`), or document and enforce at every deserialization call site that `ReceivedOutput::read` must only be applied to scanner-produced bytes. The minimal fix is to have `read` verify the offset against the script when a base key is available, mirroring how the scan path enforces the invariant.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs context
// Scanner::scan_transaction only yields outputs where
// p2tr_script_buf(key + G*offset) == output.script_pubkey (mod.rs:185-211).

// ReceivedOutput::read performs no such check (mod.rs:122-134):
let offset = Secp256k1::read_F(r)?;            // arbitrary scalar accepted
output = TxOut::consensus_decode(&mut buf_r)?; // arbitrary script_pubkey accepted
outpoint = OutPoint::consensus_decode(&mut buf_r)?;
// => ReceivedOutput { offset, output, outpoint } with offset unrelated to script key
```

1. Take a valid serialized `ReceivedOutput` from `scan_transaction` for offset `o`, script `s`.
2. Mutate the `offset` field to `o' != o` (canonical scalar), or replace the `TxOut` with a different `script_pubkey` while keeping `offset`.
3. `ReceivedOutput::read` succeeds, returning an output that `Scanner::scan_transaction` could never have emitted.
4. Spending it re-keys the threshold signature by `o'`, yielding a signature under a key that does not match the output's P2TR script — the "received" funds are not spendable.
