## Title
`CW20ERC20Pointer#transferFrom` always spends CW20 allowance even when `from == msg.sender`, breaking self-pull compatibility with standard DeFi contracts - (File: `contracts/src/CW20ERC20Pointer.sol`)

### Summary
`CW20ERC20Pointer.transferFrom` unconditionally dispatches a CosmWasm `transfer_from` execute message to the underlying CW20 contract, without special-casing the situation where `from == msg.sender`. This mirrors the Sherlock Surge `Pool.transferFrom` finding: a large class of protocols invoke `transferFrom(msg.sender, ..., amount)` (self-pull) or `transferFrom(address(this), recipient, amount)` (self-push on withdraw) expecting no allowance to be required in that case, since the caller already owns the tokens.

### Finding Description
`CW20ERC20Pointer.sol` wraps a native CW20 token as an ERC20-compatible contract reachable by any EVM caller. `transfer()` and `transferFrom()` both delegatecall into the wasmd precompile to execute CW20 messages: [1](#0-0) 

Unlike its sibling `CW1155ERC1155Pointer.sol`, which explicitly short-circuits the approval requirement when the caller is the owner (`msg.sender == from || isApprovedForAll(...)`), the ERC20 pointer's `transferFrom` has no such check: [2](#0-1) 

Because the underlying CW20 `transfer_from` message (see `execute_transfer_from`/`transfer_from` in the example CW20 contract) always deducts from the `owner`→`spender` allowance regardless of whether `owner == spender`, calling `CW20ERC20Pointer.transferFrom(from, to, amount)` where `from == msg.sender` will always require the caller to have previously approved themselves, and otherwise reverts with `"CosmWasm execute failed"`: [3](#0-2) 

### Impact Explanation
Many third-party, already-deployed and immutable smart contracts use the common "self-pull" pattern — `token.transferFrom(msg.sender, address(this), amount)` for deposits, or `token.transferFrom(address(this), recipient, amount)` for withdrawals — relying on the ERC20 convention that no allowance check is needed when the caller already owns the funds. Because the pointer contract has no such special case, any pointer-token balance held by, or routed through, such a contract will permanently fail to move via this call path (the contract never calls `approve(itself, amount)`), since that would require code the immutable protocol does not have. This can permanently strand pointer-token balances already deposited in such integrated protocols, exactly matching the "stranded/unusable tokens" impact described in the referenced report.

### Likelihood Explanation
Any user or protocol only needs to hold or interact with a `CW20ERC20Pointer`-derived token and integrate it with an off-the-shelf, pull-based DeFi contract (a very common integration pattern) to trigger this. No special privilege is required — a normal EVM transaction sender or a permissionless CW20→ERC20 pointer creation is sufficient to reach this code path.

### Recommendation
In `CW20ERC20Pointer.transferFrom`, skip the CW20 `transfer_from` allowance-consuming path when `from == msg.sender` and instead issue a plain CW20 `transfer` message (mirroring the `msg.sender == from` bypass already implemented in `CW1155ERC1155Pointer.safeTransferFrom`), e.g.:
```solidity
function transferFrom(address from, address to, uint256 amount) public override returns (bool) {
    require(to != address(0), "ERC20: transfer to the zero address");
    if (from == msg.sender) {
        return transfer(to, amount);
    }
    ... existing transfer_from logic ...
}
```

### Proof of Concept
1. Deploy/obtain a `CW20ERC20Pointer` for an existing CW20 token, associated to EVM address `A`.
2. Deploy a minimal immutable "vault" contract `V` implementing `withdraw()` as `token.transferFrom(address(this), msg.sender, amount)` (a standard self-pull withdrawal pattern).
3. Have user `A` transfer/deposit pointer tokens into `V` via `token.transfer(address(V), amount)`.
4. Call `V.withdraw()`; internally it calls `pointer.transferFrom(address(V), A, amount)`. Since `V` never called `approve(address(V), amount)` on itself, and the pointer contract has no `from == msg.sender` bypass, the underlying CW20 `transfer_from` message reverts due to zero allowance — the call reverts with `"CosmWasm execute failed"` (see `contracts/src/CW20ERC20Pointer.sol` lines 88-96), and `V`'s tokens can never be withdrawn through this path.

    function transferFrom(address from, address to, uint256 amount) public override returns (bool) {
        require(to != address(0), "ERC20: transfer to the zero address");
        string memory sender = _formatPayload("owner", _doubleQuotes(AddrPrecompile.getSeiAddr(from)));
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount)));
        string memory req = _curlyBrace(_formatPayload("transfer_from", _curlyBrace(_join(_join(sender, recipient, ","), amt, ","))));
        _execute(bytes(req));
        return true;
    }
