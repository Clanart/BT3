### Title
Permissionless `WombatPoolHelperV2.depositFor()` hardcodes zero slippage protection, exposing depositors to loss of funds from pool imbalance - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.deposit()` correctly forwards a user-supplied `_minimumLiquidity` parameter to `WombatStaking.deposit()` for slippage protection, but the sibling function `depositFor()` hardcodes this value to `0`, meaning any unprivileged caller using this entry point receives no minimum-liquidity guarantee, regardless of how imbalanced the underlying Wombat pool is at execution time.

### Finding Description
`WombatStaking.deposit()` forwards `_minimumLiquidity` straight into the underlying Wombat pool's `deposit()` call, which uses a StableSwap-style invariant (the same class of `getD()`-based curve referenced in the external report) where LP/asset tokens minted per unit deposited depend on the current pool reserve ratio and can be materially less than 1:1 when the pool is imbalanced. [1](#0-0) 

`WombatPoolHelperV2.deposit()` exposes `_minimumLiquidity` to the caller so users can protect themselves against this slippage: [2](#0-1) 

However, `depositFor()` — which is `external` with no access-control modifier, callable by any wallet for any `_for` address — always passes `0` as the minimum liquidity, completely disabling slippage protection for this path: [3](#0-2) 

This is functionally the same defect described in the source report: a deposit-into-pool function lacking a way to bound the acceptable minimum output, so the actual number of shares/receipt tokens minted is dependent on the pool's live reserve state and can be significantly lower than expected if the pool is imbalanced at execution time (e.g., right after a large swap/cross-chain transfer, before arbitrage bots rebalance it).

### Impact Explanation
Any user calling `depositFor()` on an imbalanced Wombat pool will receive fewer `stakingToken`/receipt tokens (and correspondingly less underlying value) than the deposited amount is worth, with no way to bound or reject the slippage. This is a direct, unprivileged loss of user funds — same impact class as the referenced report — and requires no admin or governance action to occur.

### Likelihood Explanation
Likelihood is moderate-to-high: `depositFor()` is fully public and can be triggered any time the pool is imbalanced (e.g. immediately following a large swap or cross-chain transfer, before arbitrage restores the peg), a condition the source report explicitly notes is common and not instantaneous to correct.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor()` (as already exists for `deposit()`/`depositNative()`) and forward the caller-supplied value through to `WombatStaking.deposit()` instead of hardcoding `0`.

### Proof of Concept
1. Wombat pool becomes imbalanced (e.g., X=1800, Y=200, similar to Scenario 3 in the source report).
2. A user calls `WombatPoolHelperV2.depositFor(100e18, userAddress)`.
3. `_deposit(100e18, 0, userAddress, address(this))` is invoked internally, forwarding `_minimumLiquidity = 0` to `WombatStaking.deposit()`.
4. `WombatStaking.deposit()` calls the underlying Wombat pool's `deposit()` with `_minimumLiquidity = 0`, so the transaction cannot revert regardless of how few LP tokens are minted.
5. The user receives materially fewer receipt/staking tokens than a balanced-pool deposit would yield (e.g., ~96 tokens per 100 deposited, per the report's simulation), with no recourse. [3](#0-2) [1](#0-0)
