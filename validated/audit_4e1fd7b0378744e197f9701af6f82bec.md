### Title
OP_RETURN data output omitted from weight/vbytes calculation, undercharging the fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Aloe report describes a boundary case where a proportional calculation collapses to zero (`fee * shares / balance` with `shares == balance`), letting a user escape a fee they should pay. The same bug class — a component of what should be paid for being silently dropped from the fee computation — exists in `SignableTransaction::new`, where an `OP_RETURN` output carrying up to 80 bytes of attacker-controlled data is appended to the transaction but is never included in the weight/vbytes measurement used to price the fee.

### Finding Description
`SignableTransaction::new` builds `tx_outs` from `payments`, then pushes an `OP_RETURN` output when `data` is present:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` constructs a dummy transaction whose outputs come **only** from `payments` (plus an optional change output) — it never sees `data`. The OP_RETURN output costs `8 (value) + 1+ (scriptPubKey len) + 9 + 80` ≈ 90+ vbytes for max-size data, none of which is priced into `needed_fee`. The change-output path has the same flaw: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` still omits the data output.

### Impact Explanation
Any transaction including `data` pays a fee computed as if the OP_RETURN output did not exist. With 80 bytes of data the effective fee rate is materially lower than the requested `fee_per_vbyte` (a ~90-vbyte shortfall on a transaction whose base size may only be ~150–250 vbytes). The transaction is still consensus-valid — excess input value still becomes fee — but the multisig systematically underpays relative to its own fee-rate target whenever data is attached, risking stuck transactions and requiring replacement/urgent handling. Like the Aloe issue, a party causes a transfer of value/size that escapes the proportional accounting.

### Likelihood Explanation
`data` is an untrusted, user-supplied field (up to the 80-byte check at line 171), so any caller attaching an OP_RETURN triggers this deterministically — no edge-case alignment needed.

### Recommendation
Pass the data output into the size estimation, e.g. build `calculate_weight_vbytes` over the final `tx_outs` (or append an `OP_RETURN` output of the real script length to the dummy transaction) so `needed_fee` covers every output actually serialized.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, None, Some(vec![0u8; 80]), fee_per_vbyte)`. `needed_fee` equals `fee_per_vbyte * vbytes` where `vbytes` reflects a transaction with no OP_RETURN output, while `tx.output` contains one ~98-byte extra output. `fee()` / actual vsize therefore yields an effective sat/vbyte strictly below `fee_per_vbyte`, and can even dip below the relay minimum the `TooLowFee` check was meant to enforce, since that check uses the same undercounted `vbytes`.
