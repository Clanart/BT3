### Title
Untrusted `ThresholdKeys` bytes with a short `Interpolation::Constant` vector cause an out-of-bounds panic in `interpolation_factor` - (File: crypto/dkg/src/lib.rs)

### Summary
The analog of CVE-2020-1939 (NULL pointer dereference on attacker-influenced state) in Serai's Rust codebase is an uncontrolled panic reachable through a `read` API that consumes untrusted bytes. `ThresholdKeys::read` deserializes an attacker-supplied `Interpolation::Constant(Vec<F>)` whose length is read verbatim from the input as `n` scalars are consumed — but nothing ties the vector's logical meaning to the participant indexes later used against it. `Interpolation::interpolation_factor` then indexes that vector with `c[usize::from(u16::from(i) - 1)]` for any participant `i` in the signing set.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, then for interpolation tag `0` pushes exactly `n` scalars into `Interpolation::Constant` and calls `ThresholdKeys::new(ThresholdParams::new(t, n, i)?, interpolation, secret_share, verification_shares)` [1](#0-0) . `ThresholdParams::new` only validates `t`, `n`, and `i` against each other — it has no visibility into the interpolation vector [2](#0-1) .

Later, whenever a signing view is computed, `interpolation_factor` performs a direct, unchecked index into the attacker-controlled vector: `Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)]` [3](#0-2) . `AlgorithmSignMachine::sign` calls `self.params.keys.view(included.clone()).unwrap()` after validating only that indexes are in `1..=n` and unique — it does not validate the deserialized key material [4](#0-3) . The `complete` path itself acknowledges this class of input: "The only known way to cause this... is to deserialize a semantically invalid FrostKeys" [5](#0-4) , confirming `ThresholdKeys::new` does not fully canonicalize what `read` accepts.

### Impact Explanation
A `Constant` vector whose contents are inconsistent (e.g., a keys blob crafted/desynced so the coefficient list doesn't match the `verification_shares`/`i` domain) yields either an out-of-bounds index panic — aborting the signing task/process — or, at minimum, wrong interpolation factors. The panic occurs inside FROST `sign` on the hot path for every signature attempt, giving a persistent denial of service of the signing service keyed by the corrupted input. This is the direct Rust analogue of the ftpd NULL dereference: malformed serialized state drives an unconditional crash in library code documented as "expected not to panic" [6](#0-5) .

### Likelihood Explanation
`ThresholdKeys::read` is an explicitly in-scope untrusted-bytes sink. Whether the panic is reachable depends on whether `ThresholdKeys::new` validates `Constant` length/consistency against `n` — I could not confirm that check (body of `ThresholdKeys::new` at crypto/dkg/src/lib.rs beyond line 300 was not fully read in available iterations). If it does not, any caller that round-trips keys through `serialize`/`read` (reshare/recovery flows, DB restore of tampered bytes, or the `promote`/`recovery` modules that re-key `ThresholdKeys`) exposes the crash to whoever supplies the blob. Severity capped at Medium/High: impact is availability only, no secret leakage.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs), reject `Interpolation::Constant(c)` unless `c.len() == usize::from(params.n())`, and make `interpolation_factor` return `Option`/`Result` instead of indexing — mirroring how `ThresholdParams::new` already validates its scalars. Failing that, `ThresholdKeys::read` should enforce the length/domain invariant at deserialization time so a malformed blob is an `io::Error`, not a later panic.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
