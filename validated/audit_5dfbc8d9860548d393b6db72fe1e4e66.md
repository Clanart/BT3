### Title
Dust-forgiveness threshold in `_calExpireForfeit` allows splitting claims to avoid forfeiture - ([File: rewards/vlMGPBaseRewarder.sol])

### Finding Description
`_calExpireForfeit` computes `forfeitAmount = _amount - rewardableAmount` and forgives it entirely (`forfeitAmount = 0`) whenever `forfeitAmount < _amount / 1000` [1](#0-0) . This function is invoked from `queueMGP` (per-call MGP harvest into the vlMGP rewarder) and from `_sendReward` (per reward-token claim) [2](#0-1) [3](#0-2) .

The threshold is evaluated independently on each call's `_amount`, not on an aggregate/session basis. Since `forfeitAmount` scales linearly with `_amount` (it equals `_amount * (1 - rewardablePercentWAD/1e18)`), the *ratio* `forfeitAmount / _amount` is constant regardless of how `_amount` is split — it depends only on `rewardablePercentWAD`, which is a per-account property (presumably tied to lock/unlock schedule in `VLMGP`), not on claim size. Therefore splitting a claim of size `A` into `N` claims of size `A/N` does **not** change whether `forfeitAmount/_amount < 1/1000` for each sub-claim: if the ratio is below 0.1%, a single large claim would also round to zero; if it's above 0.1%, splitting into smaller pieces does not reduce the ratio either, since it's amount-independent.

Consequently, an attacker cannot manufacture the "always just under 0.1%" scenario by splitting amounts — the forfeit ratio is fixed by `rewardablePercentWAD` for that account/timestamp, not manipulable via call granularity. Only whether the *fraction* forfeited is close to zero (i.e., near end of expiry/vesting when `rewardablePercentWAD` is close to `1e18`) determines whether the dust-forgiveness branch triggers, and it triggers identically whether checked once on the full amount or repeated proportionally on split amounts, because `_amount` and the computed `forfeitAmount` both scale by the same factor `1/N` in each sub-call, preserving the ratio and hence the same rounding-to-zero/non-zero outcome under integer division in the aggregate (aside from negligible integer-rounding drift on the order of at most a few wei per split, not a "systematic theft" of a materially larger forfeiture).

### Impact Explanation
No exploitable impact: the claimed rounding-arbitrage does not exist because the forfeit calculation is amount-proportional, not amount-thresholded in a way splitting can circumvent. Any difference between one lump claim and N split claims is bounded by integer-division rounding of at most `~N` wei total, which is not a materially exploitable "systematic theft of aggregate forfeiture."

### Likelihood Explanation
Not applicable — the described attack vector requires a rounding threshold that behaves non-linearly with amount, which is not the case here since both `_amount` and `forfeitAmount` are linear scalings of the same underlying `rewardablePercentWAD` ratio.

### Recommendation
No fix required for this specific vector. (If defense-in-depth is desired, forfeiture accounting could be tracked cumulatively per-account across claims rather than per-call, but this is not required to prevent the exploit alleged in the question.)

### Proof of Concept
Not applicable — a Foundry test splitting `queueMGP`/`getReward` calls into small increments vs. one lump claim would show forfeited totals differing only by negligible integer-rounding dust (bounded by number of splits, in wei), not a material "systematic theft," because `rewardablePercentWAD` (and thus the forfeit ratio) is independent of `_amount`.

        return true;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
