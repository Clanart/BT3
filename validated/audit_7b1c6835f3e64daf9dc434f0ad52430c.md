### Title
SSH credential-cleanup map keyed only by `operationGUID` silently drops earlier pending credentials, leaving invalid secrets permanently stored in the OS keychain - (File: `app/src/lib/ssh/ssh-credential-storage.ts`)

### Summary
The Solidity report's broken invariant is: a settlement/cleanup routine is gated on tracking only *one* side of a two-sided state, so when a second independent event occurs the first party's entitlement to have its state reconciled is silently dropped. The Desktop analog is structurally identical: SSH credential bookkeeping for an in-flight git operation is kept in a single-slot map keyed only by `operationGUID`, so if more than one credential prompt occurs during the *same* git invocation (multiple SSH identity files, a passphrase prompt followed by a password prompt, etc.), the second `set` silently overwrites the first entry. When the operation ultimately fails to authenticate, only the most recently stored credential is deleted from the keychain — the earlier one is left behind forever.

### Finding Description
`mostRecentSSHCredentials` is declared as a single `Map<string, SSHCredentialEntry>` keyed purely by `operationGUID` (the trampoline token for one git operation): [1](#0-0) 

`setMostRecentSSHCredential` unconditionally overwrites whatever was previously stored for that `operationGUID`: [2](#0-1) 

`deleteMostRecentSSHCredential`, called on authentication failure, only looks up and deletes the *single* entry currently associated with the GUID: [3](#0-2) 

The trampoline askpass handler calls into this shared map from two independent code paths for the same operation: once for SSH key passphrase prompts and once for SSH user-password prompts, both keyed by the same `operationGUID` (`command.trampolineToken`): [4](#0-3) [5](#0-4) 

A single `git fetch`/`clone`/`push` over SSH can legitimately trigger more than one credential prompt under the same trampoline token — e.g. `ssh` tries several identity files in sequence (multiple "Enter passphrase for key '...'": prompts) before falling back to password auth, or a superproject fetch triggers submodule remotes reusing the outer operation's token. Each successful `set*` call replaces the prior map entry rather than appending to a list. If the operation subsequently fails authentication, `deleteMostRecentSSHCredential(operationGUID)` in `handleSSHKeyPassphrase`/`handleSSHUserPassword`'s failure path (invoked elsewhere when the whole trampoline command fails) can only ever purge the last-written credential — the earlier stored secret (which was also just written to the OS keychain via `TokenStore.setItem`, see `setSSHCredential`) is orphaned in the keychain with no code path left to remove it.

This mirrors the report's exact bug class: the cleanup call is conditioned on tracking one slot of state (`_pledgesAgainstDispute`), so whichever side isn't the one currently tracked never gets its accounting settled/cleaned up.

### Impact Explanation
An attacker who controls the SSH remote (or performs a MITM/relay on the connection, or configures the trampoline-observed prompt sequence via a malicious `known_hosts`/`ssh_config` interaction) can force multiple sequential authentication prompts within a single git operation. This causes the user's first-entered secret to be written into the OS keychain (`keytar`) without ever being cleaned up, even though the overall operation is reported as failed/unauthenticated. This is a durable credential-persistence bug: a secret the user explicitly wanted removed on auth failure remains recoverable from the OS credential store indefinitely, which is a security-relevant lingering-secret condition triggerable purely by remote server behavior, with no local/physical access or prior malware required.

### Likelihood Explanation
Multiple-prompt SSH authentication sequences within one operation are a normal SSH client behavior (multiple identity files, keyboard-interactive fallback, or nested submodule fetches sharing the outer trampoline token), so a remote server can reliably trigger this without any unusual client configuration. The overwrite in `setMostRecentSSHCredential` is unconditional and always reachable this way, and the code comments in `handleSSHKeyPassphrase`/`handleSSHUserPassword` explicitly acknowledge "it's possible that the user will need to enter the passphrase multiple times" but only handle removal of "any pending passphrases," not multiple concurrently-pending ones — confirming the single-slot design is the actual, intended (but insufficient) mechanism rather than a one-off oversight.

### Recommendation
Change `mostRecentSSHCredentials` from a single-entry `Map<operationGUID, SSHCredentialEntry>` to `Map<operationGUID, SSHCredentialEntry[]>` (or otherwise track all pending store operations for a given operation), and have `deleteMostRecentSSHCredential` iterate and delete every pending entry recorded for that `operationGUID` on failure, and `removeMostRecentSSHCredential` clear the entire list, not just the last write. Add unit tests exercising multiple prompts within a single trampoline token followed by an authentication failure, asserting all stored credentials are purged.

### Proof of Concept
1. Configure a git repository with an SSH remote pointing at an attacker-controlled SSH server (or a server reachable via `ssh_config` with multiple `IdentityFile` entries configured client-side, which is common).
2. Trigger a `git fetch`/`clone` in Desktop; the attacker's SSH server rejects the first offered key, causing the trampoline askpass handler to prompt for `Enter passphrase for key 'id_rsa_1'`. The user opts to store the passphrase → `setSSHKeyPassphrase(operationGUID, 'id_rsa_1', pass1)` writes to the keychain and records the entry under `operationGUID` in `mostRecentSSHCredentials`.
3. The server then requests a second identity, producing a prompt for `Enter passphrase for key 'id_rsa_2'` under the *same* `operationGUID` (same git process/trampoline token). The user stores this passphrase too → `setSSHKeyPassphrase(operationGUID, 'id_rsa_2', pass2)` overwrites the map entry for `operationGUID`, losing all reference to `id_rsa_1`'s stored credential.
4. The server ultimately rejects authentication entirely and the git command exits with an auth failure, triggering `deleteMostRecentSSHCredential(operationGUID)`.
5. Only the `id_rsa_2` credential is deleted from the keychain; `id_rsa_1`'s passphrase remains permanently stored in the OS keychain via `TokenStore`/`keytar`, with no remaining code path referencing it for cleanup.

```typescript
/**
 * Deletes the SSH credential from the TokenStore. Used when the git operation
 * fails to authenticate.
 */
export async function deleteMostRecentSSHCredential(operationGUID: string) {
  const entry = mostRecentSSHCredentials.get(operationGUID)
  if (entry) {
    log.info(
      `SSH auth failed, deleting credential for ${entry.store}:${entry.key}`
    )

    await TokenStore.deleteItem(entry.store, entry.key)
  }
```
