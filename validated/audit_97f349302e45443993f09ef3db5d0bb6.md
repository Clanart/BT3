### Title
Unchecked zero-stake denominator in Alpenglow validator/leader reward calculation can panic bank replay - (`runtime/src/block_component_processor/vote_reward.rs`)

### Summary
`calculate_reward()`, used by `RewardState::calculate_reward()` to pay out per-slot validator and leader emissions under Alpenglow, divides by `total_stake_lamports` (the epoch's total delegated stake, `denominator = slots_per_epoch * total_stake_lamports`) with no check that the value is non-zero, unlike the sibling denominator-based reward function `calculate_alpenglow_points()` in `runtime/src/inflation_rewards/points.rs`, which explicitly filters `*stake != 0` and returns an error before dividing. This mirrors the TRST-M-1 pattern: an unchecked `veSupply[weekCursor]` denominator that can freeze claims if it is ever zero.

### Finding Description
`calculate_reward()` computes: [1](#0-0) 
`total_stake_lamports` is supplied unchecked from `RewardState.total_stake`, which is set directly from `epoch_stakes.total_stake()` at `RewardState::try_new()` with no validation: [2](#0-1) 
`calculate_reward()` (the private method) then calls the division helper directly for every rewarded validator, once per bank during reward crediting: [3](#0-2) 

By contrast, the points-based (Tower/migration) reward path in `runtime/src/inflation_rewards/points.rs::calculate_alpenglow_points()` explicitly guards the analogous `total_stake` denominator: [4](#0-3) 

This shows the codebase is aware zero-stake denominators are a real hazard for reward math (mirroring the external report's root cause), yet the Alpenglow validator/leader reward path in `vote_reward.rs` was not given the same defensive check. If `epoch_stakes.total_stake()` for the reward epoch is ever `0` — e.g., due to a data/logic bug in epoch stake bookkeeping, an empty/degenerate `EpochStakes` snapshot for that slot, or a reward/final cert referencing a slot whose epoch stakes were never populated with any delegated stake — the division in `calculate_reward()` will panic (integer division by zero), aborting bank replay for every node processing that reward certificate.

### Impact Explanation
A panic inside `calc_vote_rewards_update_vote_states()` occurs during block/bank processing (called for every validator being credited a reward in that slot's cert), not from a malicious remote input a normal user controls, but it is a validator/runtime-internal code path executed unprivileged on every node during normal Alpenglow reward accounting. If it panics, replay of that slot fails on all validators simultaneously (since the same reward cert and epoch stakes are used deterministically), which is a consensus-halting event, not merely a local process crash. This matches the highest-severity outcome class (consensus halt / false rejection of execution) rather than an isolated RPC crash.

### Likelihood Explanation
Likelihood is low under normal operation because `total_stake` is meant to reflect nonzero aggregate delegated stake for a live epoch — a cluster with zero total stake could not function at all. However, unlike the points-based reward code, there is no explicit invariant enforcement, no `NonZero<u64>` typing, and no defensive `checked_div`/zero-guard at this specific call site, so any bug in epoch-stakes computation, migration-epoch bookkeeping, or a corrupted/edge-case `EpochStakes` entry for a given reward slot would translate directly into a division-by-zero panic with no graceful degradation, exactly the failure mode described in the external report.

### Recommendation
Mirror the guard already used in `calculate_alpenglow_points()`: before calling `calculate_reward()`, validate that `total_stake_lamports` (and `slots_per_epoch`) is non-zero, and if zero, skip/record the error via `RewardStateError` instead of dividing, or change `RewardState.total_stake` to `NonZero<u64>` so the invariant is enforced at construction time rather than left implicit at the point of division.

### Proof of Concept
1. Reach a state where `epoch_stakes.total_stake()` returns `0` for `reward_slot`'s epoch (e.g., via a bug in stake aggregation, or by constructing/replaying a bank whose `EpochStakes` for that epoch has an empty/zero-sum `VoteAccounts` map — this "reachability" itself is the assumption requiring further static/dynamic analysis of `EpochStakes` population code, which could not be fully traced here).
2. Have a `ValidatedRewardCert` reference that slot as `reward_slot`.
3. `calc_vote_rewards_update_vote_states()` → `RewardState::try_new()` sets `total_stake = 0` → `update_account()` → `calculate_reward()` (method) → `calculate_reward()` (free function) computes `denominator = slots_per_epoch * 0 = 0` and divides, causing an integer-division panic that aborts bank replay for every node processing this slot.

Note: I was not able to fully confirm within the available context whether `epoch_stakes.total_stake()` can *legitimately* reach zero under any reachable runtime state (this would require deeper tracing through `EpochStakes` construction, which was not indexed in enough depth here); this uncertainty affects the likelihood assessment and should be verified further, e.g. via a Devin session with full repository access, before treating this as fully exploitable rather than a defense-in-depth gap.

    fn calculate_reward(
        &self,
        validator: Pubkey,
        accumulating_leader_reward: &mut u64,
    ) -> Result<u64, RewardStateError> {
        let (reward_slot_validator_stake, _) =
            self.accounts
                .get(&validator)
                .ok_or(RewardStateError::MissingRewardSlotValidator {
                    pubkey: validator,
                    reward_slot: self.reward_slot,
                    bank_slot: self.bank_slot,
                })?;
        let (validator_reward, leader_reward) = calculate_reward(
            &self.epoch_inflation_state,
            self.total_stake,
            *reward_slot_validator_stake,
        );
        *accumulating_leader_reward = accumulating_leader_reward.saturating_add(leader_reward);
        Ok(validator_reward)
    }
