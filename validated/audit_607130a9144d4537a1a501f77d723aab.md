### Title
Unprivileged bandwidth-purchase spam can evict a victim app's paid allowance via `pallet-bandwidth`'s unconditional FIFO eviction - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth::push_subscription` evicts the oldest subscription in an `(app_chain, app)` FIFO list whenever the list is at its 1024-entry cap, with no regard to the evicted entry's remaining bytes or expiry. Because the credit target `(app_chain, app)` in a `BandwidthPurchaseMsg` is **not** required to match the purchasing source chain (documented "sponsorship" feature), any unprivileged actor holding funds for a registered `BandwidthManager` on *any* chain can direct 1024 cheap purchases at a victim's `(app_chain, app)` key and force-evict the victim's legitimately paid, unexpired, high-value bandwidth allowance.

### Finding Description
`push_subscription` implements the eviction unconditionally on list length, not on value: [1](#0-0) 

The purchase path that reaches this function keys the credited list by `(app_chain, app)` taken from the *message body*, independent of `request.source` — this is explicitly documented as the "sponsorship" model that lets "a buyer on Ethereum credit an app on Base": [2](#0-1) [3](#0-2) 

The docs themselves acknowledge the eviction mechanism but only anticipate it firing under "pathological repeat-buy behavior" by the app's own operator, not under an adversarial third party deliberately targeting another app's key: [4](#0-3) 

Because any caller of `purchase()` on any registered `BandwidthManager` can set an arbitrary `(app, chain)` pair in the dispatched `BandwidthPurchaseMsg`, and `on_accept`'s only gating checks are that `request.from` matches the registered manager and the tier is configured (not that the caller has any relationship to the target app), an attacker can:
1. Buy the cheapest configured tier (e.g. `TierOne`) 1024 times, each specifying the victim's `(app_chain, app)` as the credit target.
2. Each purchase appends a tiny subscription to the victim's FIFO list.
3. Once the list hits the 1024 cap, each further purchase evicts the oldest entry — eventually evicting the victim's real, large, unexpired subscription(s) that were paid for at a much higher price and are far from expiry.

The victim's paid-for byte allowance is permanently destroyed (an `Event::SubscriptionEvicted` fires, but there is no way to recover the lost bytes), and their app becomes unable to send messages through the `BandwidthGate` until it repurchases — this is a direct loss of paid value with no privileged actor, relayer, prover, or governance action required.

### Impact Explanation
This is a fund-loss / logic attack on a production bridge resource-accounting mechanism: an unprivileged attacker permanently destroys another party's already-paid-for prepaid bandwidth allowance by exploiting the combination of (a) attacker-controlled sponsorship target and (b) unconditional oldest-first eviction with no value/expiry check. The victim app is forced to either re-pay for bandwidth or is denied service on Hyperbridge (`BandwidthGate::try_consume` returns `NoAllowance`/`Insufficient` once their credited allowance is gone), constituting "loss of funds" / "logic attack" per the bounty's accepted impact categories.

### Likelihood Explanation
Likelihood is medium: the attack requires the attacker to fund 1024 purchase transactions at the cheapest configured tier price on some registered `BandwidthManager` deployment (cost is nonzero but fixed and independent of how much value is destroyed on the victim's side — an attacker can wipe out a `$1000`/8MB subscription by spending roughly `1024 × $50` in the worst case, or far less if a cheaper tier exists or if the victim's list is already partially filled). No relayer collusion, governance action, or malicious node is required — only calling `purchase()` on a manager contract that is registered by governance for some source chain, which per the docs is intended to be permissionlessly callable by any buyer.

### Recommendation
Do not evict purely by FIFO position when the list is full from a credit whose payer/source differs from the app's own registered/expected chain, or add a per-source or per-payer cap/reservation so a single unrelated payer cannot fill an app's entire 1024-slot list. Alternatively, weight eviction by `remaining_bytes`/`expires_at` (e.g. evict the entry with the least remaining value or soonest expiry rather than strictly the oldest), and/or require that credits targeting a given `(app_chain, app)` only be created by that app's registered owner/deployer, keeping the sponsorship feature but gating it via an explicit allow-list of permitted sponsors per app.

### Proof of Concept
1. Governance registers `BandwidthManager` on chain `A` (attacker's cheap/low-fee chain) and configures `TierOne` with the smallest available price/byte allowance.
2. Victim app `V` on chain `B` buys a large tier (e.g. `TierFour`, 8MB) via `BandwidthManager` on chain `B`, landing one `Subscription` entry in `Allowance::<T>::get(B, V)`.
3. Attacker calls `manager.purchase({app: V, tier: TierOne, months: 1, chain: B})` on chain `A`'s manager 1024 times (paying the small `TierOne` price each time), each dispatching a `BandwidthPurchaseMsg{app: V, chain: B, ...}` to `pallet-bandwidth`.
4. Each message's `on_accept` calls `push_subscription(&B, &V, TierOne, ...)`; once the list length reaches `MAX_SUBSCRIPTIONS` (1024), `push_subscription` evicts `list.remove(0)` — which, after enough attacker purchases queue ahead of it in FIFO order relative to when the eviction pointer reaches it, becomes the victim's original `TierFour` subscription — permanently destroying `V`'s paid-for 8MB allowance, confirmed on-chain by an `Event::SubscriptionEvicted{ app_chain: B, app: V, tier: TierFour, lost_bytes: 8_000_000 }`.
5. `V`'s subsequent dispatches on chain `B` are rejected by `BandwidthGate::try_consume` with `GateError::NoAllowance`/`Insufficient` despite having paid for bandwidth that was never used.

## Sponsoring Another Chain

The `chain` argument is **not validated against the source chain** — see [Overview → Sponsorship](/developers/evm/bandwidth/overview#sponsorship) for the model. A buyer on Ethereum credits an app on Base by passing the credit chain id in `chain`:

```solidity
manager.purchase({
    app:    abi.encodePacked(appAddressOnBase),
    tier:   2,
    months: 6,
    chain:  bytes("EVM-8453")
});
```

The pallet keys allowance storage on `(msg.chain, msg.app)`, so the credit lands on Base regardless of which chain sent the payment. The recommended pattern for teams running a central treasury is to deploy `BandwidthManager` on one low-fee chain and sponsor bandwidth for app instances elsewhere.
```

### Eviction

Pushing onto a full list (1024 entries) evicts the **oldest** entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain. In practice this only happens under pathological repeat-buy behavior — at the default of one purchase per cycle, 1024 buys is years of headroom.
```

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```
