### Title
`ThresholdKeys::read` / `ThresholdKeys::new` never verify the secret share against the verification shares, allowing semantically invalid key material from untrusted bytes - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation method, the `secret_share`, and all `verification_shares` from an untrusted byte stream, then calls `ThresholdKeys::new`. `ThresholdKeys::new` validates only structural fields — the count of verification shares, that participant indexes are `<= n`, and that `Constant` interpolation is only used when `t == n` — but never checks the privileged field: that `C::generator() * secret_share == verification_shares[&i]` (crypto/dkg/src/lib.rs:349-391). This mirrors the LiteLLM flaw: the deserializer restricts *which object* is being updated (params/participant bounds) but not *which fields* may be set inconsistently.

### Finding Description
- `ThresholdKeys::new` checks `verification_shares.len() == n` and participant bounds, then computes `group_key` from `verification_shares[1..=t]` — it never relates `secret_share` to `verification_shares[i]` (crypto/dkg/src/lib.rs:355-378).
- `ThresholdKeys::read` passes fully attacker-controlled `secret_share` and `verification_shares` into `new` (crypto/dkg/src/lib.rs:574-632). `Constant` interpolation coefficients are also read unchecked (crypto/dkg/src/lib.rs:604-616).
- The inconsistency is silently carried into signing: `view()` derives the signer's share purely from `secret_share` (crypto/dkg/src/lib.rs:494-520), and the FROST layer itself acknowledges this hole — the `InternalError` comment in `complete` states the only known way to reach "everyone had a valid share yet the signature was still invalid" is "to deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:491-494).

### Impact Explanation
An attacker who can feed crafted bytes to `ThresholdKeys::read` (key backup/restore, key transport, or any channel supplying serialized `ThresholdKeys`) can install key material where the holder's `secret_share` does not match `verification_shares[i]` for the declared `group_key`. Every FROST signature share the victim produces then fails `verify_share`, so `complete` returns `FrostError::InvalidShare(victim_i)` — i.e., the honest victim is deterministically blamed as faulty (crypto/frost/src/sign.rs:475-489). In a deployment with blame-based removal/slashing this converts a key-file write into forced ejection of a specific participant, and any signing session the victim joins is sabotaged with the blame pinned on them rather than the corrupted data.

### Likelihood Explanation
Reachability is conditional: it requires an attacker to control or corrupt the serialized `ThresholdKeys` consumed by `ThresholdKeys::read`, which is plausible for backups, migration, or provisioned key blobs but not for keys generated purely in-process via `key_gen`/PedPoP (which produce consistent material). The inconsistency is never detected at load time, so a single corrupted restore persistently poisons the participant — no race or collusion needed.

### Recommendation
In `ThresholdKeys::new` (and thereby `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject the input otherwise. Optionally also sanity-check that `group_key` derived from shares `1..=t` is non-identity.

### Proof of Concept
```rust
// Serialize a victim's legitimate keys, then flip bytes within the
// secret_share field (or write secret_share = 0 / a random scalar),
// leaving params, interpolation, and all verification_shares intact.
let mut bytes = keys.serialize().to_vec();
// secret_share begins right after ID || t || n || i || interpolation tag
// (see ThresholdKeys::read, crypto/dkg/src/lib.rs:591-618).
// Overwrite it with an arbitrary scalar:
let forged = C::F::random(rng);
bytes[SECRET_SHARE_OFFSET..SECRET_SHARE_OFFSET + 32]
    .copy_from_slice(forged.to_repr().as_ref());

// Succeeds: params, share count, and participant bounds all validate.
let corrupted = ThresholdKeys::<C>::read(&mut bytes.as_slice()).unwrap();
// group_key() is unchanged, but secret_share no longer matches it.
// Any sign() with `corrupted` produces a share that fails verify_share,
// and complete() blames this participant via FrostError::InvalidShare.
```

Confidence caveat: I could not fully trace every `ThresholdKeys::read` call site in the deployment path; the finding stands on the missing field-consistency check itself, which the FROST `InternalError` comment explicitly acknowledges as reachable only via malformed deserialization.
