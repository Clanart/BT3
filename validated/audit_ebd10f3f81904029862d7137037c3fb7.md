## Analog Found: Rounding‑truncation causes a solver to deliver real output tokens but be released zero escrowed input tokens

### Title
Rounding truncation in same-chain partial-fill escrow release can zero out a solver's proportional input reward - (`evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` computes the proportional escrow released to a partial-fill solver with integer division: `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` [1](#0-0) . Exactly like the Notional `StrategyUtils._convertBPTClaimToStrategyTokens` bug (numerator precision smaller than denominator causing truncation to zero), when `order.inputs[i].amount * fillAmount` is smaller than `totalRequired`, `escrowedAmount` rounds down to `0`. The function has no check that a non-zero `fillAmount` produces a non-zero `escrowedAmount` before transferring the solver's real output tokens to the beneficiary.

### Finding Description
`fillOrder` (public, unprivileged entrypoint) routes to `_fillSameChain`, which lets any solver partially fill an order's output leg for any `fillAmount` up to `remaining` [2](#0-1) . The solver immediately pays `beneficiaryTotal` (real ERC20/native tokens) to the order's beneficiary [3](#0-2) , and only afterward the code computes what input tokens the solver is entitled to receive back via the proportional formula at line 120. Because `order.inputs[i].amount` (fixed at order placement) and `fillAmount` (chosen by the solver, potentially tiny relative to `totalRequired`) are multiplied before dividing by `totalRequired`, a small enough `fillAmount` yields `escrowedAmount = 0` — the solver transfers real value to the beneficiary and is credited zero escrowed input in `escrowedInputs[i]`, which then flows unchanged into `_withdraw` [4](#0-3) .

This mirrors the reported invariant break precisely: "deposit assets (real output tokens paid to beneficiary), receive zero token (escrowed input) in return." Existing test coverage (`testPartialFill_RoundingDustReleasedToFinalSolver*`, labeled "Finding #4") only fixes the aggregate dust-locking problem for the *final* completing solver by using the exact stored balance on full completion [5](#0-4) ; it does not address or guard against an *intermediate* partial fill whose `fillAmount` truncates to zero escrow at line 120 — no `require(escrowedAmount != 0)` guard exists anywhere in `_fillSameChain`.

### Impact Explanation
A solver calling `fillOrder` with a `fillAmount` that is small relative to `totalRequired` and `order.inputs[i].amount` pays real output tokens to the beneficiary but is released `escrowedAmount == 0` input tokens — a direct, unrecoverable loss of funds for that fill, matching the bounty's "loss of funds" / "unauthorized... wrong beneficiary or amount" category. Repeated small fills by naive or scripted solvers (e.g., automated fillers probing liquidity in small increments) systematically forfeit value with no recourse, since `_partialFills[commitment][outputToken]` is incremented regardless of whether real escrow was released, permanently recording that portion as "filled" without paying it out to anyone.

### Likelihood Explanation
The path is reachable by any unprivileged solver through the standard public `fillOrder` entrypoint with no special preconditions (no malicious relayer/prover, no admin, no front-running required). It is triggered whenever `order.inputs[i].amount * fillAmount < totalRequired`, which is common for orders whose input token has few decimals (e.g., 6-decimal USDC) paired with a high-precision output (18-decimal token) and a solver attempting a small partial fill — the exact decimal-mismatch scenario (1e8 vs 1e18-class precision mismatch) that produced the original Notional finding.

### Recommendation
Add an explicit guard in `_fillSameChain` after computing `escrowedAmount` for the proportional (non-full) branch, reverting if it rounds to zero:
```solidity
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
    require(escrowedAmount != 0, "zero escrow released");
}
```
Alternatively, enforce a minimum `fillAmount` per leg (e.g., a minimum fill ratio) so that `order.inputs[i].amount * fillAmount / totalRequired` can never round to zero, consistent with the recommendation in the referenced report to revert on zero-token minting/release.

### Proof of Concept
1. User places a same-chain order: `inputs[0].amount = 100 * 1e6` (USDC), `output.assets[0].amount = 3 * 1e18` (DAI, `totalRequired`).
2. Solver calls `fillOrder` with `outputs[0].amount = 1` (1 wei DAI) as `fillAmount`.
3. `escrowedAmount = (100_000_000 * 1) / 3_000_000_000_000_000_000 = 0` (integer division truncates to zero) — computed at [6](#0-5) .
4. The solver has already transferred `beneficiaryTotal = 1 wei DAI` to the beneficiary at line 107, but `escrowedInputs[0].amount = 0` is passed to `_withdraw`, so the solver receives no USDC for this fill while `_partialFills[commitment][outputToken]` is nonetheless advanced by 1 wei DAI equivalent, permanently marking that increment as filled without any corresponding escrow payout.

    /*//////////////////////////////////////////////////////////////
                    ROUNDING DUST IN PARTIAL FILLS (Finding #4)
    //////////////////////////////////////////////////////////////*/

    /// @notice Verifies that rounding dust from integer division in partial fills
    /// is not permanently locked. The final solver completing the order should
    /// receive the full remaining escrow balance rather than a truncated amount.
    function testPartialFill_RoundingDustReleasedToFinalSolver() public {
        // Choose amounts that produce rounding truncation:
        // input = 100 USDC (100e6), output = 3 DAI (3e18)
        // Each of 3 solvers fills 1 DAI. Proportional release per fill:
        //   100e6 * 1e18 / 3e18 = 33333333 (truncated from 33333333.33...)
        // Without fix: 3 * 33333333 = 99999999, leaving 1 unit locked.
        // With fix: final solver gets remaining balance = 100e6 - 2*33333333 = 33333334
        uint256 inputAmount = 100 * 1e6; // 100 USDC
        uint256 outputAmount = 3 * 1e18; // 3 DAI

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        uint256 fillPerSolver = 1e18; // Each solver fills 1 DAI
        uint256 truncatedRelease = (inputAmount * fillPerSolver) / outputAmount; // 33333333

        // --- Solver 1 fills 1 DAI ---
        address solver1 = makeAddr("solver1");
        vm.deal(solver1, 1 ether);
        deal(address(dai), solver1, 10 * 1e18);
        uint256 solver1UsdcBefore = usdc.balanceOf(solver1);

        vm.startPrank(solver1);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out1 = new TokenInfo[](1);
        out1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out1}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver1),
            solver1UsdcBefore + truncatedRelease,
            "Solver1 should receive truncated proportional USDC"
        );

        // --- Solver 2 fills 1 DAI ---
        address solver2 = makeAddr("solver2");
        vm.deal(solver2, 1 ether);
        deal(address(dai), solver2, 10 * 1e18);
        uint256 solver2UsdcBefore = usdc.balanceOf(solver2);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out2 = new TokenInfo[](1);
        out2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out2}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver2),
            solver2UsdcBefore + truncatedRelease,
            "Solver2 should receive truncated proportional USDC"
        );

        // --- Solver 3 fills final 1 DAI (completes the order) ---
        address solver3 = makeAddr("solver3");
        vm.deal(solver3, 1 ether);
        deal(address(dai), solver3, 10 * 1e18);
        uint256 solver3UsdcBefore = usdc.balanceOf(solver3);

        vm.startPrank(solver3);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out3 = new TokenInfo[](1);
        out3[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out3}));
        vm.stopPrank();

        // Final solver should receive the remaining balance (truncatedRelease + 1 rounding unit)
        uint256 expectedFinalRelease = inputAmount - (2 * truncatedRelease); // 33333334
        assertEq(
            usdc.balanceOf(solver3),
            solver3UsdcBefore + expectedFinalRelease,
            "Final solver should receive remaining escrow including rounding dust"
        );
        assertGt(expectedFinalRelease, truncatedRelease, "Final release should be larger due to rounding dust");

        // Gateway should have zero USDC — no dust locked
        assertEq(usdc.balanceOf(address(intentGateway)), 0, "Gateway should have zero USDC - no rounding dust locked");
    }
