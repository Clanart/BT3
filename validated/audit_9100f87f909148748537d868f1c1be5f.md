### Title
Unverified `operator_xonly_pk` in `SetOperatorKeys` Allows BitVM Key Poisoning for Any Deposit - (`File: core/src/verifier.rs`)

### Summary

`Verifier::set_operator_keys` accepts an `operator_xonly_pk` field from the `OperatorKeysWithDeposit` RPC message and uses it directly to store BitVM winternitz keys and challenge-ACK hashes in the DB, without ever verifying that this key is actually one of the operators listed in the accompanying `deposit_data`. This is the direct Clementine analog of the `_burn()` bug: a top-level validity check passes (deposit validation), but the identity used in all subsequent state-mutating calls is taken from the caller-supplied field rather than from the authoritative source (`deposit_data.get_operators()`).

`is_deposit_valid` (lines 603-731) checks that every operator in the DB with usable collateral appears in `deposit_data`, and vice versa, but it **never checks that the `operator_xonly_pk` parameter is a member of `deposit_data.get_operators()`**. [4](#0-3) 

The aggregator correctly sets `operator_xonly_pk` from `deposit_data.get_operators()` when building the `OperatorKeysWithDeposit` message:

```rust

``` [5](#0-4) 

But the verifier never enforces this invariant itself.

---

### Impact Explanation

A caller who can reach the `SetOperatorKeys` gRPC endpoint can supply a valid deposit (passing `is_deposit_valid`) while setting `operator_xonly_pk` to any other registered operator's key. The verifier will then:

1. Store the attacker-supplied challenge-ACK hashes in `operators_challenge_ack_hashes` under the victim operator's identity for this deposit.
2. Compute and store wrong `assert_tx_addrs` and `root_hash` in `bitvm_setups` (built from the attacker's winternitz keys but attributed to the victim operator). [6](#0-5) 

Downstream consequences:

- **Watchtower challenge path broken**: when a watchtower challenges the victim operator's kickoff, the verifier looks up the stored challenge-ACK hashes and BitVM scripts for that `(operator_xonly_pk, deposit_id)` pair. With poisoned values, a valid disprove transaction from the victim operator will be rejected (wrong taproot leaf hashes), and the challenge-ACK verification will use the wrong preimage hashes. This can render the victim operator's kickoff unchallengeable, allowing a fraudulent withdrawal to finalize and bridge BTC to be stolen.
- **Operator collateral at risk**: if the victim operator's assert transactions are rejected because the stored `assert_tx_addrs` do not match, the operator cannot complete reimbursement, causing permanent loss of their collateral.

---

### Likelihood Explanation

The `SetOperatorKeys` endpoint is part of `ClementineVerifier` and is intended to be called only by the aggregator. Exploitability depends on whether the verifier's gRPC port enforces mTLS. No explicit mTLS enforcement was found in the RPC handler code reviewed. If the port is reachable without mTLS, any network peer can trigger this. Even with mTLS, a compromised or malicious aggregator can exploit it trivially. [7](#0-6) 

---

### Recommendation

Add a membership check at the top of `set_operator_keys` (or inside `parse_op_keys_with_deposit`) before any DB writes:

```rust
pub async fn set_operator_keys(
    &self,
    mut deposit_data: DepositData,
    keys: OperatorKeys,
    operator_xonly_pk: XOnlyPublicKey,
) -> Result<(), BridgeError> {
    // NEW: verify operator_xonly_pk is actually in this deposit
    if !deposit_data.get_operators().contains(&operator_xonly_pk) {
        return Err(eyre::eyre!(
            "operator_xonly_pk {:?} is not listed in deposit_data operators",
            operator_xonly_pk
        ).into());
    }
    ...
```

This mirrors the fix in the `_burn()` analog: use the authoritative identity (`deposit_data.get_operators()`) rather than trusting the caller-supplied field.

### Proof of Concept

1. Attacker controls operator A (registered in the system).
2. A deposit is created that includes both operator A and operator B.
3. Attacker calls `SetOperatorKeys` on a verifier directly with:
   - `deposit_params`: the real deposit params (passes `is_deposit_valid`)
   - `operator_xonly_pk`: operator B's key
   - `operator_keys`: attacker-generated BitVM winternitz keys and challenge-ACK hashes
4. `is_deposit_valid` passes — the deposit is real and operator B is in the DB.
5. `get_operator(operator_B_pk)` succeeds — operator B exists.
6. Attacker's keys are stored in `bitvm_setups` and `operators_challenge_ack_hashes` under operator B's identity for this deposit.
7. Operator B later sends a kickoff. A watchtower challenges it.
8. The verifier fetches the poisoned `assert_tx_addrs` / `root_hash` for `(operator_B_pk, deposit_id)`.
9. Operator B's legitimate assert transactions do not match the poisoned taproot addresses; the disprove fails.
10. The fraudulent kickoff finalizes; bridged BTC is stolen.

pub fn parse_op_keys_with_deposit(

    )?;

    Ok((deposit_data, op_keys, operator_xonly_pk))
}
