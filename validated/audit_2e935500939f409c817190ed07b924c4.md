### Title
Attacker-controlled FROST preprocess forces an infinity aggregate nonce and panics Bitcoin transaction signing - (File: `crypto/frost/src/sign.rs`)

### Summary

A malicious signing participant can submit a syntactically valid preprocess whose nonce commitments make the aggregate Schnorr nonce the point at infinity. The FROST code accepts the resulting `Rs` without an identity check, then Bitcoin’s BIP-340 HRAM unconditionally extracts the nonce’s x-coordinate, which panics on infinity.

### Finding Description

`TransactionSignMachine::read_preprocess` accepts remote preprocesses and `AlgorithmSignMachine::sign` converts them into aggregate nonce points through `B.nonces(&nonces)`. [1](#0-0) [2](#0-1)  For every participant and generator, the bound commitment is `D + rho * E`, with both group elements supplied directly by that participant. [3](#0-2)  Because `C::read_G` validates canonical point encoding but does not reject the identity element, a participant can encode `E` as identity and choose `D` as the negation of the other participants’ already-known aggregate nonce contribution. [4](#0-3)  The resulting aggregate nonce becomes identity, after which `Schnorr::sign_share` passes `nonce_sums[0][0]` to `H::hram`. [5](#0-4)  Bitcoin’s HRAM passes that point to `x`, whose implementation calls `expect("point at infinity")`, causing an uncaught panic rather than a `FrostError`. [6](#0-5) [7](#0-6) 

### Impact Explanation

An unprivileged signer in a Bitcoin threshold-signing session can crash the node process when its preprocess is used for signing. This matches the reported bug class: a protocol message reaches an unchecked exceptional state and terminates the process instead of producing an error. A crashed signer can halt threshold signing and delay or prevent transaction production.

### Likelihood Explanation

Exploitation requires the attacker to be an accepted participant in the signing set and to know or predict the other participants’ nonce commitments. In broadcast-based FROST operation, a malicious participant can wait for the other preprocesses before publishing its own, making the required negation deterministic because setting `E` to identity removes the unknown binding-factor term. No private keys, invalid encodings, malformed Bitcoin transactions, colluding validators, or underlying cryptographic failure are required.

### Recommendation

Reject identity aggregate nonces before invoking algorithm-specific `sign_share`, ideally returning `FrostError::InvalidPreprocess` or `FrostError::InvalidSigningSet` instead of panicking. The identity check should cover every element produced by `B.nonces`, not only deserialized `D` and `E`, because malicious combinations can create identity even when individual commitments are nonzero. Bitcoin’s `x` helper should also avoid panicking in protocol paths, or the HRAM API should propagate failure so the signing state machine can report a normal error.

### Proof of Concept

Conceptually, for one Schnorr nonce and one malicious signer among the included participants:

1. Let `P` be the sum of all other participants’ bound nonce commitments for the first nonce.
2. Submit a canonical preprocess whose first commitment pair is `D = -P` and `E = identity`.
3. `D + rho * E` evaluates to `-P`, so the session aggregate nonce evaluates to `P + (-P) = identity`.
4. `AlgorithmSignMachine::sign` reaches `Schnorr::sign_share`, which calls Bitcoin `Hram::hram` with the identity nonce.
5. `x(R)` calls `expect("point at infinity")` and aborts the process. [3](#0-2) [2](#0-1) [5](#0-4) [6](#0-5)
