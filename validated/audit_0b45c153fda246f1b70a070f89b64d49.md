### Title
Unvalidated `sender`/`recipient` participant indexes in PedPoP blame evaluation cause a panic (DoS) - ([File: crypto/dkg/pedpop/src/encryption.rs, crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
Analogous to CL-2020-06 (missing validation of attacker-controlled fields leading to a crash), Serai's PedPoP DKG blame path performs unchecked `HashMap` indexing on `Participant` values supplied as call arguments. `BlameMachine::blame` / `AdditionalBlameMachine::blame` accept arbitrary `sender` and `recipient` indexes, and `blame_internal` indexes `self.enc_keys[&decryptor]` and `self.commitments[&sender]` without first checking that these participants were ever registered. Passing any index outside the DKG set (any non-zero `u16` not in `1..=n`) triggers a panic, crashing the evaluating party.

### Finding Description
`AdditionalBlameMachine` is explicitly designed to evaluate blame for non-participants ("capable of handling an arbitrary amount of additional blame proofs... regardless of if the caller was a member in the DKG protocol"), so its inputs — `sender`, `recipient`, `msg`, `proof` — are all attacker-controlled data.

In `blame_internal` (crypto/dkg/pedpop/src/lib.rs):

```rust
let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
```

`decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:366-397) verifies the message's Schnorr PoP and then, when a `proof` is supplied, does:

```rust
&[self.enc_keys[&decryptor], *proof.key],
```

`enc_keys` only contains keys for participants registered in `Decryption::register` (indexes `1..=n`). If `decryptor` (`recipient`) is any other `Participant` (e.g. `Participant::new(n + 1)`), this `HashMap` index operation panics — `HashMap`'s `Index` impl panics on missing keys.

If the PoP signature check fails, `blame_internal` returns early; if it passes but `proof` is `None`, it returns `recipient` as faulty without indexing. But an attacker can trivially construct an `EncryptedMessage` with a *valid* PoP (`SchnorrSignature::sign` over `pop_challenge`, since they choose the key) plus any `EncryptionKeyProof`, then cause a blame evaluation with `recipient` out of range → panic.

Even reaching the `self.commitments[&sender]` lookup (lib.rs ~line 599) panics when `sender` was not in the commitments map (e.g. in `AdditionalBlameMachine::new` where the map only covers `1..=n`).

The only guard on `Participant` is that it is non-zero (`Participant::new` rejects 0); there is no `<= n` bound check anywhere on the blame path.

### Impact Explanation
An unprivileged party who submits a blame accusation (or causes a node/coordinator to evaluate one) with an out-of-range `sender` or `recipient` index crashes the evaluating process. In a deployment where validators or coordinators process blame proofs from peers (the documented purpose of `AdditionalBlameMachine`), this is a remote, unauthenticated panic/DoS of a consensus-adjacent component — the same impact class as the original discv5 report (malformed input → crash via missing field validation).

### Likelihood Explanation
All inputs to `blame`/`blame_internal` are externally supplied: the `Participant` arguments are bare `u16`s, and the `EncryptedMessage`/`EncryptionKeyProof` are byte-deserializable (`EncryptedMessage::read`, `EncryptionKeyProof::read`) with no restriction to known indexes. The PoP check is not an obstacle — the attacker simply signs a PoP for their own chosen `key`. Any flow that feeds peer-provided blame statements into `AdditionalBlameMachine::blame` or `BlameMachine::blame` reaches the panic with a single crafted argument set.

### Recommendation
Validate `sender` and `recipient` at the top of `blame` / `blame_internal` (and inside `decrypt_with_proof`): return `Err`/a defined fault instead of indexing. Concretely, replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get(...)` returning an error for unknown participants, or check membership against `1..=n` before use.

### Proof of Concept
```rust
// Build an observer machine for a DKG with n participants.
let mut machine = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();

// Attacker crafts an EncryptedMessage with a *valid* PoP for their own key:
//   key = random scalar k; msg.key = G*k; msg.pop = SchnorrSignature::sign(k, r, pop_challenge(...))
// and an arbitrary EncryptionKeyProof.
let msg: EncryptedMessage<Ristretto, SecretShare<_>> = attacker_crafted_msg_with_valid_pop();
let proof = Some(attacker_dleq_proof());

// recipient is any non-zero index never registered (n + 1 ..= u16::MAX)
let bad_recipient = Participant::new(n + 1).unwrap();

// Inside blame_internal -> decrypt_with_proof:
//   msg.pop.verify(...) passes (attacker signed it correctly)
//   proof is Some -> evaluates `self.enc_keys[&decryptor]` -> PANIC (missing key)
machine.blame(sender, bad_recipient, msg, proof);
```

The panic occurs at the `enc_keys[&decryptor]` index expression in `decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs, inside the `if let Some(proof)` branch around lines 381–390), and equivalently at `self.commitments[&sender]` in `blame_internal` (crypto/dkg/pedpop/src/lib.rs ~line 599) when `sender` is out of range.

Uncertainty note: whether an in-tree production callsite actually forwards peer-controlled `sender`/`recipient`/`msg` into `blame` could not be fully verified (the coordinator code appears to be out of the indexed scope); the panic itself is confirmed in the in-scope library code, and `AdditionalBlameMachine`'s documented purpose is evaluating blame statements provided by third parties.
