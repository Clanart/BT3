### Title
Empty serialized aggregate signatures verify as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` accepts an aggregate containing zero signatures, and `SchnorrAggregate::verify` returns true for that value when the caller supplies an empty `keys_and_challenges` list. Although `SchnorrAggregator::complete` refuses to create an empty aggregate, the public deserializer permits an unauthenticated party to create the same state directly from bytes.

### Finding Description
`SchnorrAggregate::read` reads an attacker-controlled `u32` count and allows it to be zero, then reads zero `R` values followed by the scalar `s` at `crypto/schnorr/src/aggregate.rs:77-88`.

`SchnorrAggregate::verify` only checks that `self.Rs.len() == keys_and_challenges.len()` at `crypto/schnorr/src/aggregate.rs:127-130`. For two empty lists, it queues no weighted signature statements and appends only `(-self.s, C::generator())` at `crypto/schnorr/src/aggregate.rs:138-145`. If the attacker encodes `s = 0`, the resulting multiexp is the identity and verification succeeds.

The generating path explicitly treats an empty aggregation as invalid: `SchnorrAggregator::complete` returns `None` when `self.sigs.is_empty()` at `crypto/schnorr/src/aggregate.rs:174-178`. The deserialization path bypasses that invariant.

### Impact Explanation
An unauthenticated party can submit the serialized encoding:

```text
00000000 || 00...00
```

where the first four bytes are the little-endian `Rs` length `0`, followed by the canonical encoding of scalar zero. A verifier that calls:

```rust
let sig = SchnorrAggregate::<C>::read(&mut bytes)?;
assert!(sig.verify(dst, &[]));
```

will accept a signature aggregate that was never produced by any signer. For an empty expected signature set, this is a forged aggregate signature and bypasses whatever authorization decision was delegated to aggregate verification.

### Likelihood Explanation
The attack requires only control of serialized bytes supplied to `SchnorrAggregate::read` and a verification call with an empty `keys_and_challenges` list. It does not require a private key, nonce, participating signer, malformed encoding, or malicious validator. The verifier must accept an empty aggregate as a meaningful input domain; the API currently permits that input rather than rejecting it.

### Recommendation
Reject `Rs.len() == 0` in both `SchnorrAggregate::read` and `SchnorrAggregate::verify`. `verify` should additionally require `keys_and_challenges` to be non-empty before checking length equality. A regression test should deserialize `u32(0) || scalar(0)` and assert that either deserialization fails or verification returns false.
