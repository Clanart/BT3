### Title
`incentiveDeposit` doubles the mode-2 reward after `getRewardAmount` has already capped it to the contract's MGP balance - (File: wombat/ArbWomUp3.sol)

### Summary
`getRewardAmount()` clamps `mgpReward` to `IERC20(mgp).balanceOf(address(this))` before returning it, but `incentiveDeposit` then multiplies that already-capped value by two when `_mode == 2`, so `rewardToSend` can end up exceeding the MGP the contract actually holds. This value is then approved and passed straight to `vlMGP.lockFor(rewardToSend, msg.sender)`.

### Finding Description
In `incentiveDeposit`:
```solidity
uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender, _mode == 2);
if (_mode == 2)
    rewardToSend = rewardToSend * 2;
...
IERC20(mgp).safeApprove(address(vlMGP), rewardToSend);
vlMGP.lockFor(rewardToSend, msg.sender);
``` [2](#0-1) 

`getRewardAmount` computes the tier-based reward and returns `min(mgpReward, mgpleft)`, where `mgpleft = IERC20(mgp).balanceOf(address(this))`. [3](#0-2) 

Because the balance-cap check happens inside `getRewardAmount` and the ×2 bonus is applied afterward in `incentiveDeposit`, the balance check is bypassed for the doubled portion: the invariant "bonus multiplier applied before the solvency check" is violated. Any unprivileged caller choosing `_mode == 2` (mWomSV lock mode) with a sufficiently large `_amount`/`_convertRatio` combination relative to the current MGP balance can trigger `rewardToSend` values greater than `mgpleft`.

### Impact Explanation
This is a genuine ordering/logic defect matching the "Critical - Protocol insolvency" pattern in principle: the function attempts to lock more MGP for a user than the contract holds. Whether this results in actual fund-level insolvency depends on the downstream behavior of `vlMGP.lockFor` (i.e., whether it performs a real `transferFrom` of `rewardToSend` MGP from `ArbWomUp3`). I was unable to retrieve the implementation of `lockFor` in `VLMGP.sol` through the indexed codebase (the file content returned was empty/truncated), so I cannot confirm whether:
- `lockFor` pulls tokens via `transferFrom`, in which case the ERC20 balance check would cause the entire `incentiveDeposit` transaction to revert once `rewardToSend` exceeds the contract's actual balance (this would degrade to a denial-of-service on mode-2 deposits rather than fund theft), or
- `lockFor` credits a locked balance to the user independent of an enforced token transfer, in which case the doubling bug would directly create unbacked locked MGP claims (true insolvency).

Given the index size limits, the full contents of `VLMGP.sol`'s `lockFor` were not available to verify this distinction with certainty; a Devin session with full filesystem access would be needed to confirm the exact downstream mechanics.

### Likelihood Explanation
No privileged role is required — any EOA holding WOM tokens can call `incentiveDeposit` with `_mode == 2`. The precondition is simply that the reward computed for the caller's tier/lock amount, before doubling, is close to or at the current MGP balance cap (e.g., due to a residual/low MGP balance in the contract), which is a plausible, externally observable state (MGP balance is a public ERC20 balance) rather than an attacker-controlled precondition.

### Recommendation
Move the balance cap to after all bonus multipliers are applied, e.g., compute the tier-based `mgpReward` and the mode-2 doubling first, then clamp the final `rewardToSend` to `IERC20(mgp).balanceOf(address(this))` immediately before approving/calling `vlMGP.lockFor`. Alternatively, pass the multiplier information into `getRewardAmount` so the cap is calculated on the final, post-bonus amount.

### Proof of Concept

1. Deploy `ArbWomUp3`, set `rewardMultiplier`/`rewardTier` such that a user's tier reward is close to `mgp.balanceOf(ArbWomUp3)`.
2. Fund the contract with a modest MGP balance (e.g., `X` MGP).
3. Attacker (unprivileged EOA) calls `incentiveDeposit(_amount, _convertRatio, false, 2)` with an `_amount` sized so `getRewardAmount` returns a value close to `X` (i.e., capped at `mgpleft = X`).
4. Assert that `rewardToSend` computed in the call (via emitted `VLMGPRewarded` event) equals `2 * X`, i.e., exceeds the contract's actual MGP balance `X`.
5. Inspect whether the transaction reverts inside `vlMGP.lockFor` (confirming only a DoS) or succeeds and credits `2 * X` locked MGP to the attacker while the contract only ever held `X` (confirming insolvency) — this step requires the `VLMGP.sol` `lockFor` source, which should be obtained via a full repository checkout to complete verification.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
