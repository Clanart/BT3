Found it: `AccountKeyRoleBased.ValidateMember` at `blockchain/types/accountkey/account_key_role_based.go:72-79` checks whether a recovered public key belongs to **any** of the role sub-keys, without scoping the check to the specific role being authorized for the operation in question — the exact bug class described in the Grafana advisory (a permission check that is not scoped to the specific resource, satisfied instead by unrelated access).

### Title
Role-based AccountKey membership check is not scoped to the requested role, allowing a key from one role to be accepted as a member of another - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.ValidateMember` (lines 72-79) iterates over **all** role sub-keys (`RoleTransaction`, `RoleAccountUpdate`, `RoleFeePayer`) and returns `true` if the recovered public key matches *any* of them, regardless of which specific role the caller is asking about:

```go
func (a *AccountKeyRoleBased) ValidateMember(recoveredKey *ecdsa.PublicKey, from common.Address) bool {
	for _, rk := range *a {
		if rk.ValidateMember(recoveredKey, from) {
			return true
		}
	}
	return false
}
``` [1](#0-0) 

This mirrors the Grafana CVE-2024-6322 pattern: the access decision ("is this signer authorized?") checks for authorization against the wrong/broader resource set (any role) instead of the specific one relevant to the action (the role required for the given transaction operation), because `ValidateMember` — unlike `Validate` — takes no `RoleType` parameter and cannot scope the check.

### Finding Description
`AccountKeyRoleBased` supports up to three independently-purposed keys per the documented role semantics: `RoleTransaction` for value transfers, `RoleAccountUpdate` for updating the account's key, and `RoleFeePayer` strictly for paying transaction fees as a fee payer [2](#0-1) . The role-scoped `Validate` method correctly indexes into the specific role slot `(*a)[r]` [3](#0-2) , which is used by the core transaction/fee-payer validation paths in `Transaction.ValidateSender` and `Transaction.ValidateFeePayer` via `accountkey.ValidateAccountKey` [4](#0-3) [5](#0-4) .

However, `ValidateMember` deliberately drops the role parameter and loops across every sub-key, accepting a signer that only holds, e.g., the `RoleFeePayer` key as a valid "member" for a check that conceptually should be scoped to a specific role (e.g., `RoleAccountUpdate` membership, used for multisig-style member checks). This is the same class of defect as the reported Grafana bug: the authorization primitive checks "does this key have access to *any* role-scoped resource of this account" instead of "does this key have access to *this* role-scoped resource," and any caller that (a) needs a role-specific membership check but (b) calls `ValidateMember` instead of `Validate` will silently accept members of the wrong role.

### Impact Explanation
If `ValidateMember` is relied upon anywhere in the codebase to gate a role-specific privilege (e.g., checking whether a signature belongs to the `RoleAccountUpdate` key set before permitting an account-key update, or checking `RoleFeePayer` membership before allowing fee-delegation), a signer holding only the unrelated `RoleTransaction` (or any other role) key would incorrectly pass the check. That could let a key that should only be able to send value transfers also authorize account-key changes or fee-payer duties, an unauthorized-value/control-plane escalation. Given the rules scope (fee delegation, AccountKey authorization reachable by a single submitted transaction), a wrong-role key being accepted as a fee payer or account-key authorizer would allow unauthorized state changes or fee obligations to be imposed via a legitimately signed but wrongly-scoped key.

### Likelihood Explanation
Exploitability is contingent on there being a live call site that invokes `AccountKeyRoleBased.ValidateMember` for a role-specific decision instead of `Validate`. I was not able to conclusively confirm within the indexed portion of the codebase which callers use `ValidateMember` versus `Validate` for role-based accounts under consensus-critical or transaction-admission code paths (the interface is implemented uniformly across all `AccountKey` types) [6](#0-5) . Given the size limits on the codebase index, some call sites of `ValidateMember` may not have been surfaced by search. **This should be verified with a full repository checkout (e.g., via a Devin session) to confirm whether any consensus-relevant caller uses `ValidateMember` on a `AccountKeyRoleBased` value in a way that requires role scoping** before treating this as a confirmed, exploitable vulnerability rather than a latent API footgun.

### Recommendation
Add a `RoleType` parameter to `AccountKeyRoleBased.ValidateMember` (mirroring `Validate`) so membership checks are scoped to the specific role relevant to the calling context, and audit all call sites of `ValidateMember` across account key types to ensure role-specific decisions cannot be satisfied by an unrelated role's key.

### Proof of Concept
Conceptual PoC (pending confirmation of a concrete role-scoped call site):
1. Create an account with `AccountKeyRoleBased` containing distinct keys for `RoleTransaction`, `RoleAccountUpdate`, and `RoleFeePayer`.
2. Sign a message with only the `RoleTransaction` private key.
3. Call `ValidateMember(recoveredKey, from)` on the account's `AccountKeyRoleBased` from a code path that intends to verify `RoleAccountUpdate` (or `RoleFeePayer`) membership.
4. Observe that the check returns `true` even though the signer only controls the `RoleTransaction` key — confirming the missing role-scoping — mirroring the Grafana ReqActions-not-scoped-to-datasource flaw.

Note: I was unable to identify, within the indexed code, a definitive consensus-critical caller that invokes `ValidateMember` in a role-specific context (as opposed to `Validate`, which is properly scoped and used by `Transaction.ValidateSender`/`ValidateFeePayer`). This gap should be closed with full-repository access before treating the finding as a confirmed exploitable vulnerability rather than a defect in an unused/underused API.
