## Finding

### Title
`aptos move verify-package` reports success without ever comparing on-chain module bytecode to the locally compiled bytecode - (File: `aptos-move/cli/src/stored_package.rs`)

### Summary
The Aptos CLI's `verify-package` command is the tool operators, auditors, and downstream integrators use to confirm that bytecode published on-chain under an address actually corresponds to a given source tree. In `VerifyPackage::execute`, the on-chain `PackageRegistry` is fetched **without bytecode** (`with_bytecode = false`), and the resulting `CachedPackageMetadata::verify()` only diffs `PackageMetadata` struct fields (name, deps, module names/gzipped source/source_map, manifest, upgrade policy, extension, source digest). No step ever fetches the actual on-chain module bytecode and byte-compares it against the bytecode compiled from the local source. Yet on success the command prints "Successfully verified source of package" [1](#0-0) , which is a claim the code never actually substantiates.

### Finding Description
`VerifyPackage::execute` builds the package locally, extracts its `PackageMetadata`, and calls `CachedPackageRegistry::create(client, self.account, false)` — the trailing `false` is the `with_bytecode` flag: [2](#0-1) 

Inside `CachedPackageRegistry::create`, bytecode is only fetched from the chain "if with_bytecode": [3](#0-2) 

Since `verify-package` passes `false`, `self.bytecode` remains empty, and `get_bytecode()` is never exercised on this path. `CachedPackageMetadata::verify()` — the only correctness check invoked by `VerifyPackage::execute` — compares purely metadata fields (`name`, `deps`, `modules` [which includes only gzipped `source`/`source_map`, not compiled bytecode], `manifest`, `upgrade_policy`, `extension`, `source_digest`); it never touches `self.bytecode` or the module bytes returned by `code::publish_package`'s `code: vector<vector<u8>>` parameter: [4](#0-3) 

Because `PackageMetadata.modules[i].source` is attacker-supplied, gzipped source text embedded at publish time (`extract_metadata` simply reads and zips whatever is on disk when the package was built) [5](#0-4) , it is trivially possible to publish a package where the declared metadata (name, deps, `source_digest`, `source` text, manifest) matches a legitimate, "audited-looking" source tree while the actual bytecode blob supplied to `code::publish_package_txn`'s `code: vector<vector<u8>>` argument is a different, maliciously modified module. The Move bytecode verifier and dependency checks in `code.move`/`aptos_vm.rs::validate_publish_request` [6](#0-5)  validate structural/dependency/compatibility properties of the bundle, but they do not (and cannot) prove that the bytecode was actually compiled from the source text embedded in `ModuleMetadata.source`. `verify-package` is precisely the tool meant to close that gap for a human/auditor, but it skips the one step (byte comparison) that would do so.

### Impact Explanation
This produces "success without action" analogous to the referenced report: the tool asserts an invariant ("on-chain bytecode matches source") that it never actually checked, giving a false sense of security to anyone relying on `verify-package` output before interacting with, depending on, or approving a package (e.g. governance reviewers verifying a framework/package upgrade, or third parties auditing a DeFi contract before granting it `AllowedDep` trust or before users approve capital to it). A malicious or compromised publisher can pass `verify-package` while running bytecode that diverges from its claimed, reviewed source — for example smuggling an admin backdoor, altered arithmetic, or a different friend/visibility surface — undetected by the very tool designed to catch it. This directly matches the required impact class "Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes."

### Likelihood Explanation
High likelihood of triggering: any package publisher can freely control the `source`/`source_map` embedded in `PackageMetadata` at publish time (it is just gzipped text bundled into the transaction, not independently derived from the actual bytecode by the VM), and any user of `aptos move verify-package` will unconditionally get the false "Successfully verified" message as long as metadata fields line up, since no code path in this command ever downloads or diffs actual bytecode. This requires no special privilege beyond being able to publish a package (permissionless) and does not depend on any of the excluded categories (no governance/admin trust assumption, no leaked keys, no consensus/DAG/keyless/AA involvement).

### Recommendation
`VerifyPackage::execute` should call `CachedPackageRegistry::create(client, self.account, true)` to fetch on-chain bytecode, then extend `CachedPackageMetadata::verify()` (or add a new step) that recompiles/extracts the local bytecode via `pack.extract_code()` and byte-compares each module against `registry.get_bytecode(module_name)`, failing verification on any mismatch. Only after this succeeds should the tool print a "verified" success message.

### Proof of Concept
1. Author package `P` with legitimate-looking source `m.move` implementing `public fun withdraw(...)` with a safety check.
2. Before submission, patch the compiled bytecode blob (e.g., via `PackageBuilder`/patcher helpers similar to `publish_package_with_patcher` used in existing tests [7](#0-6) ) to remove the safety check, while leaving `PackageMetadata.modules[0].source` unchanged (still the "safe" source text) and recomputing `source_digest` consistently from the same (unchanged) source files.
3. Publish this package on-chain via `code::publish_package_txn` with the tampered bytecode but honest-looking metadata.
4. Run `aptos move verify-package --account <addr>` against the original, safe local source tree.
5. Observe `verify()` succeeds and the CLI prints "Successfully verified source of package," even though the deployed bytecode's actual logic differs from the verified source — because bytecode was never fetched (`with_bytecode=false`) or compared.

                package_metadata.name,
                self_metadata.name

            bail!(
                "Dependencies don't match {:?} : {:?}",

            bail!(

                self_metadata.modules

            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
