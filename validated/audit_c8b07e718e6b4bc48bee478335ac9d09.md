### Title
Unbounded recursive RLP/JSON decoding of nested `AccountKeyRoleBased` account keys causes stack overflow before nesting validation runs - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` and `AccountKeyRoleBased.UnmarshalJSON` recursively decode each role's sub-key by delegating to `AccountKeySerializer`, which in turn dispatches back into `AccountKeyRoleBased.DecodeRLP`/`UnmarshalJSON` if the sub-key's declared type is again `AccountKeyTypeRoleBased`. The only defense against nested `RoleBased` keys (`ErrNestedCompositeType` / `roleBasedKey cannot contains a roleBasedKey as a role key`) is enforced *after* decoding completes, in `CheckInstallable`/`CheckUpdatable`/`checkAccountKeyZeroValues`. An attacker can therefore submit a transaction (or call a public RPC) containing an `AccountKey` payload that nests `AccountKeyRoleBased` inside itself thousands of times, causing unbounded Go-stack recursion purely during decoding, crashing the node with a stack overflow — directly analogous to the wasmd CWA-2024-005 stack-overflow-via-unbounded-recursive-parsing bug class (CWE-121).

### Finding Description
- `AccountKeyRoleBased.DecodeRLP` decodes a list of RLP-encoded sub-keys and, for every element, calls `rlp.DecodeBytes(b, &serializer)` where `serializer` is an `AccountKeySerializer`: [1](#0-0) 
- `AccountKeySerializer.DecodeRLP` reads the key type and then calls `NewAccountKey` followed by `s.Decode(serializer.key)`. If the declared type is `AccountKeyTypeRoleBased` again, this invokes `AccountKeyRoleBased.DecodeRLP` recursively with no depth check: [2](#0-1) 
- The same unbounded recursion exists in the JSON path: `AccountKeySerializer.UnmarshalJSON` unmarshals into `serializer.key` (which can be `*AccountKeyRoleBased`), whose `UnmarshalJSON` in turn unmarshals a list of nested `*AccountKeySerializer`: [3](#0-2) [4](#0-3) 
- The nesting rejection only happens after decode succeeds, inside validation routines such as `CheckInstallable`: [5](#0-4) 
and the RPC-facing helper `checkAccountKeyZeroValues`, which explicitly documents that nested RoleBased keys are rejected only via an `isNested` flag checked *after* the key object already exists: [6](#0-5) 

This mirrors the wasmd CWA-2024-005 bug class: recursive decode/parse of attacker-controlled nested structures with no depth limit, where the depth check (if any) is applied only after the vulnerable recursive parsing has already occurred.

### Impact Explanation
An attacker-supplied, deeply nested `AccountKeyRoleBased` payload triggers unbounded native-stack recursion during RLP or JSON decoding of an `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction's `AccountKey` field, or via the public `kaia_decodeAccountKey`/`kaia_encodeAccountKey` RPC endpoints. This crashes the goroutine (and potentially the node process) with a stack overflow, a memory-safety violation classified CWE-121, matching CVSS High Availability impact (`A:H`) with no privileges required and no user interaction — the same severity profile as the referenced wasmd advisory.

### Likelihood Explanation
Likely: crafting a deeply nested RLP or JSON `AccountKeyRoleBased` structure requires no special privileges, funds beyond minimal gas, or coordination with other actors, and can be delivered as a standalone transaction to the transaction pool (decoded on ingestion before signature/logic validation) or via a public RPC call.

### Recommendation
Enforce a strict recursion/nesting depth limit inside `AccountKeyRoleBased.DecodeRLP` and `AccountKeyRoleBased.UnmarshalJSON` (and generally in `AccountKeySerializer.DecodeRLP`/`UnmarshalJSON`) that rejects any nested `AccountKeyTypeRoleBased` sub-key immediately during decode, rather than deferring the check to `CheckInstallable`/`CheckUpdatable`/`checkAccountKeyZeroValues`. This mirrors how upstream wasmd fixed CWA-2024-005 by bounding recursive message depth before performing recursive work.

### Proof of Concept
1. Construct an `AccountKeyRoleBased` value `X0 = AccountKeyRoleBased{legacyKey}`.
2. Iteratively wrap: `Xi = AccountKeyRoleBased{Xi-1}` for `i = 1..N` with large `N` (e.g., tens of thousands), each level re-declaring `AccountKeyTypeRoleBased` as its type via `AccountKeySerializer`.
3. RLP-encode `XN` via `NewAccountKeySerializerWithAccountKey(XN)` / `rlp.EncodeToBytes` (mirroring `EncodeAccountKey` in `api/api_kaia.go`).
4. Submit the encoded bytes either as the `AccountKey` field of a `TxTypeAccountUpdate` transaction to the mempool, or directly to the `kaia_decodeAccountKey` RPC (`api/api_kaia.go` `DecodeAccountKey`, calling `rlp.DecodeBytes(encodedAccKey, &dec)`).
5. Decoding recurses `N` times through `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` before any nesting check executes, exhausting the goroutine stack and crashing the process.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
}
