### Title
`BandwidthManager.purchase()` assumes the host's `feeToken` is worth exactly $1, letting fee-token depeg silently drain protocol bandwidth revenue - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
`BandwidthManager` prices bandwidth tiers in "18-decimal units" that governance intends to represent a fixed USD cost, then converts that number into the host's configured `feeToken` purely by rescaling decimals — with **no price oracle and no exchange-rate check**. This is the same broken invariant as the RAACNFT report: a token is silently assumed to always be worth $1, when nothing in the code enforces that peg.

### Finding Description
`Tier.price` and `tierPrice[tier]` are documented as "Price in 18-decimal units; scaled at purchase time to fee-token decimals": [1](#0-0) 

`purchase()` performs that "scaling" as a pure decimal-shift, never consulting any USD/feeToken exchange rate: [2](#0-1) 

The `feeToken` itself is **not a hardcoded stablecoin** — it is an arbitrary, governance-configurable address read at call time from the host (`IDispatcher(_host).feeToken()`), documented as "typically a stablecoin" but not guaranteed to hold peg or even be a stable asset: [3](#0-2) [4](#0-3) 

The docs confirm this rescaling is the entire pricing model — no FX/oracle logic exists anywhere in the purchase path: [5](#0-4) 

This mirrors the RAACNFT `crvUSD == 1 USD` bug exactly: a governance-set "dollar" price is converted into a specific ERC-20 token 1:1 by decimals only, with the implicit assumption that 1 unit of that token is worth 1 USD. If `feeToken` depegs from its intended dollar value (temporarily, e.g. during a stablecoin depeg event, or permanently if governance later repoints `feeToken` to a different asset via `EvmHostParamUpdate.fee_token` without a corresponding `SetTiers` repricing), the amount pulled from `msg.sender` in `IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount)` no longer reflects the tier's intended dollar cost.

### Impact Explanation
When `feeToken`'s real market value drops below the $1 implicitly assumed at tier-setting time, every buyer of bandwidth pays the *nominal* scaled amount but delivers *less real value* than the tier price was calibrated for — a direct, protocol-wide underpayment/loss-of-funds condition for the treasury that holds and later withdraws these fee-token balances (`Withdraw` action, lines 213-221). Because `chain` is explicitly unvalidated against the source chain (sponsorship is a documented feature), an attacker can exploit any transient depeg window across any chain where a `BandwidthManager` is deployed to buy bandwidth at a steep discount versus its intended dollar cost, at scale, with no privileged access required — this is a pure unprivileged-attacker "logic attack" against the price assumption, not a relayer/prover/admin compromise.

### Likelihood Explanation
Likelihood is elevated by two facts already visible in the code/docs: (1) `feeToken` is explicitly designed to be swappable by governance ("we allow it to be configurable to prevent future regrets" — `EvmHost.sol` line 43-44) without any coupling to `BandwidthManager`'s `tierPrice` table, so a governance-driven fee-token migration alone can desynchronize pricing from the new token's real value until someone remembers to re-run `SetTiers`; and (2) even without a fee-token change, any real-world stablecoin depeg event (the exact scenario the original crvUSD report documents as commonplace) immediately breaks the 1:1 assumption for every purchase made during that window, with no code path detecting or rejecting it.

### Recommendation
Add a price oracle (e.g., a Chainlink `feeToken`/USD feed with staleness checks, matching the pattern already used in `SimplexPaymaster.sol`'s `_getOraclePrice`) and use it to convert the governance-set USD tier price into `feeToken` units at purchase time, instead of a bare decimal rescale. At minimum, add a governance-enforced invariant that any `fee_token` change is atomically paired with a `SetTiers` repricing based on the new token's actual USD value, and consider bounding tier purchases with a max-staleness/deviation guard against a reference price.

### Proof of Concept
1. Host governance configures `feeToken` = a stablecoin `X` and sets `tierPrice[1] = 100e18` (intended: $100/tier-month), via `SetTiers` (`BandwidthManager.sol` lines 207-212).
2. `X` depegs to $0.50 (real historical behavior for various stablecoins, per the original report's exact bug class).
3. Attacker calls `purchase(app, tier=1, months=1, chain)`; `total18d = 100e18`, `amount = 100e18 / 10**(18-dec)` — the nominal token amount is transferred at face value regardless of `X`'s real market price: [6](#0-5) 
4. The attacker receives the full tier's bandwidth credit (dispatched unconditionally to `pallet-bandwidth`) while having paid only $50 of real value instead of the intended $100 — a 50% discount extracted purely from the code's unchecked 1:1 price assumption, repeatable at scale for the duration of the depeg.

Two implications:

1. **Fee tokens with `decimals > 18` would underflow `(18 - dec)`.** This is not a concern in practice — the supported fee tokens are all `≤ 18` decimals.
2. **Tier prices must be representable at the local fee-token's decimals after multiplication by `months`.** A tier priced at `10**12` (a hypothetical sub-penny SKU) and a 6-decimal fee token would revert with `PriceNotRepresentable()` because the 18-decimal value doesn't divide cleanly. Set tier prices to multiples of `10**12` to keep them clean on 6-decimal fee tokens.

The fee token comes from `IDispatcher(_host).feeToken()` — the same token used for relayer fees elsewhere in the protocol. Your dapp should always read it from the host rather than hardcoding an address.
