### Title
Unvalidated CLVM atom length-prefix parsing in `is_atom_canonical`/`is_clvm_canonical` allows a crafted spend bundle to crash mempool admission - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `mempool_manager.py` parse the raw CLVM byte serialization of a coin spend's puzzle reveal and solution to check for canonical (shortest-form) atom encoding. Neither function validates that the multi-byte length-prefix or the computed atom length actually fits within the remaining buffer before indexing into it, mirroring the CVE-2017-6319 pattern where `dex_parse_debug_item` read variable-length fields from a crafted file without bounds checks.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads `clvm_buffer[offset]` to get the tag byte, then for `prefix_len` (up to 5) additional bytes does: [1](#0-0) 
There is no check that `offset + prefix_len < len(clvm_buffer)` before these reads. If a crafted atom header (e.g. `0xFC` prefix indicating a 6-byte-long length prefix) appears near the end of a puzzle-reveal or solution buffer with insufficient trailing bytes, indexing `clvm_buffer[offset]` past the end of the `bytes` object raises an unhandled `IndexError`.

The caller, `is_clvm_canonical()`, also indexes `clvm_buffer[offset]` at the top of its parse loop without bounds checking, and advances `offset` by `atom_len` (an attacker-controlled value from the length prefix) without ever confirming `atom_len` bytes actually remain in the buffer: [2](#0-1) 

Both functions are invoked unconditionally on every coin spend of every incoming `SpendBundle`, on both `puzzle_reveal` and `solution`, inside `MempoolManager.validate_spend_bundle()`: [3](#0-2) 
This is on the main mempool-admission path (`add_spend_bundle()` → `validate_spend_bundle()`), reachable directly by any unprivileged peer or RPC caller submitting a spend bundle. No prior signature verification or coin-record lookup happens before this canonical-form check runs, so a syntactically well-formed-but-truncated CLVM atom header is sufficient to trigger it.

### Impact Explanation
An uncaught `IndexError` raised deep inside CLVM byte parsing during spend-bundle validation is not a `ValueError`/`Err` return the mempool admission pipeline is designed to handle gracefully (the pipeline's documented failure modes are `Err` enum values, not raw Python exceptions). Depending on how far up the call stack this propagates, this can abort the transaction-processing task/coroutine handling `RespondTransaction`/`new_transaction` (or `push_tx` RPC), effectively a spend-triggered halt of transaction processing for that request path — matching the "spend-triggered transaction-processing halt" impact class explicitly in scope.

### Likelihood Explanation
High reachability: any unprivileged spend-bundle submitter (via P2P `new_transaction`/`respond_transaction` or the `push_tx` RPC) can trigger this by constructing a `CoinSpend` whose `puzzle_reveal` or `solution` bytes end with a multi-byte atom length-prefix tag that lacks the required trailing length bytes. No fee payment success, coin ownership, or signature validity is required to reach this parsing step, since it runs before/alongside conditions/cost checks in `validate_spend_bundle()`.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before reading each length-prefix byte (`if offset + prefix_len >= len(clvm_buffer): return <safe/non-canonical result>`), and in `is_clvm_canonical()` validate that `atom_len` does not exceed the remaining buffer length before advancing `offset`, returning `False` (not canonical / malformed) instead of allowing an `IndexError` to escape. Additionally wrap the canonical-check call site in `validate_spend_bundle()` to translate any parsing exception into the existing `Err.INVALID_COIN_SOLUTION` return path so malformed encodings are handled the same way as other invalid-solution errors rather than propagating an unhandled exception.

### Proof of Concept
1. Construct a `CoinSpend` whose `solution` (or `puzzle_reveal`) SerializedProgram bytes end with, e.g., the single byte `0xFC` (indicating a 6-byte atom length prefix per `is_atom_canonical`) with zero or fewer than 5 trailing bytes, e.g. `bytes.fromhex("80fc")` (a valid leading atom `0x80` followed by a truncated long-prefix atom tag).
2. Build a `SpendBundle` containing this `CoinSpend` and submit it via `push_tx` RPC or the P2P `new_transaction`/`respond_transaction` flow to a full node.
3. When `MempoolManager.validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.solution))` at [3](#0-2) , execution reaches `is_atom_canonical()`, which indexes past the end of the truncated buffer and raises `IndexError`, since the check at [1](#0-0)  never verifies `offset` stays within `len(clvm_buffer)`.
