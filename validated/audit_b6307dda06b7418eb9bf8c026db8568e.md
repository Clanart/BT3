### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` causes stack-consumption DoS during transaction pool admission - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
The RLP decoder for `AccountKeyRoleBased` recursively decodes each sub-key through a generic `AccountKeySerializer`, which itself can construct and decode another `AccountKeyRoleBased`. There is no recursion-depth limit anywhere in this decode path or in the underlying `rlp` package, so a single crafted `TxTypeAccountUpdate` (or `TxTypeFeeDelegatedAccountUpdate*`) transaction with a deeply self-nested `RoleBased` account key can drive unbounded Go-stack recursion during RLP decoding, before any semantic validation (`CheckInstallable`/`CheckUpdatable`, which reject nested composite types) ever runs. This mirrors the CVE-2017-11624 bug class: a parser that recurses on nested/self-referential structures without a depth bound, causing stack exhaustion ("infinite loop"/stack overflow) from a single malicious input.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes an RLP list of byte-strings, and for every element constructs a fresh `AccountKeySerializer` and calls `rlp.DecodeBytes` on it: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads a `keyType`, instantiates the corresponding `AccountKey` via `NewAccountKey`, and then calls `s.Decode(serializer.key)` — which, if `keyType` is `AccountKeyTypeRoleBased`, re-enters `AccountKeyRoleBased.DecodeRLP`: [2](#0-1) [3](#0-2) 

Nothing in this chain enforces a maximum nesting depth; the `rlp` package itself has no recursion/nesting-depth guard (`rlp/decode.go`'s `Stream.List`/`ListEnd` only track byte-length accounting via a `stack []uint64`, not a depth cap): [4](#0-3) [5](#0-4) 

The only defense against nested `RoleBased` keys — `CheckInstallable`/`CheckUpdatable`, which return `kerrors.ErrNestedCompositeType` — runs *after* the full recursive RLP decode has already completed: [6](#0-5) [7](#0-6) 

This is confirmed by the existing regression test, which shows the rejection happening only at `txpool.AddRemote` / `applyTransaction` time via `ErrNestedCompositeType`, i.e., strictly after decoding: [8](#0-7) 

`TxInternalDataAccountUpdate.Key` is an `accountkey.AccountKey` interface field decoded straight from the wire-format transaction bytes, so simply receiving/decoding the raw transaction (e.g. via `eth_sendRawTransaction`/p2p tx propagation into the pool) triggers the vulnerable decode path: [9](#0-8) 

### Impact Explanation
An attacker can construct a single RLP-encoded `AccountUpdate` (or fee-delegated variant) transaction whose `Key` field is an `AccountKeyRoleBased` containing another `AccountKeyRoleBased` containing another, nested to a depth sufficient to exhaust the goroutine stack during decode. Because decoding happens as soon as the transaction bytes are parsed — before signature checks or `CheckInstallable`/`CheckUpdatable` validation — this can crash or panic the node process (denial of service) that attempts to decode the transaction, whether during pool admission, RPC decode, or block processing. This matches the "acceptance of an invalid transaction / crash causing state divergence between honest nodes" impact category, since a node that panics on a specific transaction while others reject it gracefully (or vice versa, depending on Go recover semantics in the surrounding stack frame) can diverge in availability/behavior.

### Likelihood Explanation
Likelihood is limited by two factors that I could not fully verify given tool constraints:
1. Whether an outer `recover()` in the RPC/pool goroutine converts a Go stack overflow into a graceful error rather than a full process crash. Go's runtime typically treats true stack overflow as a fatal, non-recoverable error (`runtime: goroutine stack exceeds ... - fatal error: stack overflow`), which `recover()` cannot catch, making this a hard crash rather than a normal panic.
2. Whether an upstream RLP size limit (e.g., max transaction size in bytes, imposed by the p2p or RPC layer) caps how many nesting levels are actually reachable before the byte budget for the whole transaction is exhausted. Each nesting level does consume RLP list/string overhead bytes, so the maximum depth is bounded by max-tx-size / per-level-overhead, but I was not able to locate an explicit tx-size cap check in this session to confirm the achievable depth is insufficient to exhaust the stack.

Given no explicit recursion-depth guard exists in the account-key decode path, and no explicit protection was found in the `rlp` package, the primary uncertainty is whether the maximum transaction size still permits enough nesting levels to exhaust the stack in practice.

### Recommendation
Add an explicit recursion-depth limit inside `AccountKeyRoleBased.DecodeRLP` (and generally in `AccountKeySerializer.DecodeRLP`), e.g. by threading a depth counter through decode context and rejecting decode once depth exceeds a small constant (1, since nested `RoleBased` keys are never semantically valid). Enforce this check *during* decode, not only in the later `CheckInstallable`/`CheckUpdatable` validation, so that a hostile transaction cannot cause unbounded recursion before any semantic checks occur.

### Proof of Concept
Conceptual encoding (not run against the live code in this session):
1. Build an `AccountKeyRoleBased` value `k0 = RoleBased([Legacy])`.
2. Build `k1 = RoleBased([Serializer(RoleBasedType, RLP(k0))])`.
3. Repeat, wrapping `k_{i} = RoleBased([Serializer(RoleBasedType, RLP(k_{i-1}))])` for N iterations (N large enough, e.g. tens of thousands, while still fitting under the tx size cap since each level's overhead is small).
4. Encode a `TxTypeAccountUpdate` transaction with `Key = k_N` (or use raw RLP crafting bypassing the Go struct, directly building nested RLP lists of `[keyType=RoleBased, [ [keyType=RoleBased, [...]] ] ]`).
5. Submit the raw transaction bytes to `eth_sendRawTransaction` or inject into `txpool.AddRemote`.
6. Expected: `rlp.DecodeBytes` recurses through `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` N times, consuming stack until Go's runtime stack limit is hit, causing `fatal error: stack overflow` and crashing the node process before `CheckInstallable`/`ErrNestedCompositeType` validation is ever reached.

I could not execute this PoC in this session (no code execution/tooling available); the depth required to trigger an actual crash and its interaction with any max-tx-size limit remains unverified.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (a *AccountKeyRoleBased) CheckUpdatable(newKey AccountKey, currentBlockNumber uint64) error {
	if newKey, ok := newKey.(*AccountKeyRoleBased); ok {
		lenOldKey := len(*a)
		lenNewKey := len(*newKey)
		// If no key is to be replaced, it is regarded as a fail.
		if lenNewKey == 0 {
			return kerrors.ErrZeroLength
		}
		// Do not allow undefined roles.
		if lenNewKey > (int)(RoleLast) {
			return kerrors.ErrLengthTooLong
		}
		for i := range lenNewKey {
			switch {
			// A composite key is not allowed.
			case (*newKey)[i].IsCompositeType():
				return kerrors.ErrNestedCompositeType
			// If newKey is longer than oldKey, init the new attributes.
			case i >= lenOldKey:
				if err := (*newKey)[i].CheckInstallable(currentBlockNumber); err != nil {
					return err
				}
			// Do nothing for AccountKeyTypeNil
			case (*newKey)[i].Type() == AccountKeyTypeNil:

			// Check whether the newKey is replacable or not
			default:
				if err := CheckReplacable((*a)[i], (*newKey)[i], currentBlockNumber); err != nil {
					return err
				}
			}
		}
		return nil
	}
	// Update is not possible if the type is different.
	return kerrors.ErrDifferentAccountKeyType
}

func (s *Stream) List() (size uint64, err error) {
	kind, size, err := s.Kind()
	if err != nil {
		return 0, err
	}
	if kind != List {
		return 0, ErrExpectedList
	}

	// Remove size of inner list from outer list before pushing the new size
	// onto the stack. This ensures that the remaining outer list size will
	// be correct after the matching call to ListEnd.
	if inList, limit := s.listLimit(); inList {
		s.stack[len(s.stack)-1] = limit - size
	}
	s.stack = append(s.stack, size)
	s.kind = -1
	s.size = 0
	return size, nil
}
