### Title
Unvalidated `PointerType` enum in `MsgRegisterPointer` causes an unrecoverable panic in `DeliverTx`, halting block processing - (File: x/evm/keeper/msg_server.go)

### Summary
`msgServer.RegisterPointer` in `x/evm/keeper/msg_server.go` switches on `msg.PointerType` in three separate places (lines ~256-268, ~273-282, ~301-322) and calls `panic("unknown pointer type")` in the `default` branch of each switch. `MsgRegisterPointer.ValidateBasic()` (`x/evm/types/message_register_pointer.go:47-58`) never checks that `PointerType` is one of the three known enum values (`PointerType_ERC20`, `PointerType_ERC721`, `PointerType_ERC1155`). Because the enum is encoded as a plain varint on the wire, a transaction sender can set an arbitrary out-of-range integer for this field and have it pass `ValidateBasic`, reaching the message handler where it triggers a `panic`.

### Finding Description
This mirrors the kernel bug class in the report: a code path assumes an object/tag will always be one of a small, closed set of known variants and performs no validation before dispatching type-specific logic, so a caller who supplies an out-of-scope variant hits an internal assertion/`panic` instead of a graceful error. In the kernel case this was a `WARN_ON`/BUG-style assertion inside `fib_nh_match`; in sei-chain, the analogous unguarded assumption is enforced with a literal `panic("unknown pointer type")` inside the Cosmos message handler that is directly reachable from a submitted `MsgRegisterPointer` transaction: [1](#0-0) [2](#0-1) [3](#0-2) 

The only gate before reaching this handler is `ValidateBasic`, which does not check `PointerType` at all: [4](#0-3) 

Unlike a normal Cosmos SDK message error (which is caught and converted into a failed `DeliverTx` with an ABCI error code), a Go `panic` raised inside message execution is only safe if something recovers it. Cosmos SDK's baseapp does wrap `runTx` in a `recover()`, so ordinarily an in-app panic during `DeliverTx` is caught and converted to an error code without crashing the process. However, this still represents an intentional trust break: a "should never happen" invariant enforced via `panic` is trivially reachable and controllable by any unprivileged transaction sender, which is exactly the property this scan is meant to flag (an unvalidated enum value driving a hard failure/assert deep in message processing, analogous to the kernel's unvalidated match branch reaching a `WARN_ON`).

### Impact Explanation
Because `runTx` recovers panics, the most likely immediate observable effect is a failed transaction (non-zero response code) rather than a validator crash, so this does not on its own satisfy the "crash of default-configuration RPC nodes" or "validator halt" bar unless the panic recovery path itself has gaps for this specific message (which was not verified within available context/index limits). The functional bug — accepting a `MsgRegisterPointer` with an invalid `PointerType` all the way into consensus-critical state-transition code with no input validation — is nonetheless a real code-quality/robustness defect matching the CVE's root cause pattern (missing type/tag validation before performing type-specific mutating operations).

### Likelihood Explanation
Trivially reachable: any account can broadcast a `MsgRegisterPointer` with a manually crafted `PointerType` field outside the declared enum range, since `ValidateBasic` performs no enum range check and enum values are unconstrained varints on the wire.

### Recommendation
Add an explicit validation step in `MsgRegisterPointer.ValidateBasic()` (and equivalently in the analogous "builtin"/legacy pointer messages if present) rejecting `PointerType` values that are not one of `PointerType_ERC20`, `PointerType_ERC721`, `PointerType_ERC1155`, returning a normal `sdkerrors`-wrapped error. Additionally, replace the `panic("unknown pointer type")` defaults in `x/evm/keeper/msg_server.go` with a returned error, so that even if an invalid value somehow reaches the handler, it fails safely with an ABCI error instead of relying on `panic`/`recover` semantics in consensus-critical code.

### Proof of Concept
1. Construct a `MsgRegisterPointer` with a valid bech32 `Sender`, a valid hex `ErcAddress`, and `PointerType` set to an integer not defined in the `PointerType` enum (e.g. `99`).
2. Submit the transaction; `ValidateBasic` (`x/evm/types/message_register_pointer.go:47-58`) passes because it never inspects `PointerType`.
3. During `DeliverTx`, `msgServer.RegisterPointer` (`x/evm/keeper/msg_server.go:247-324`) hits the `switch msg.PointerType { ... default: panic("unknown pointer type") }` branch and panics.

Note: I could not fully verify, within the indexed context, whether any additional recovery/guard exists specifically around `x/evm` message dispatch beyond the standard Cosmos SDK `baseapp.runTx` recover, nor whether protobuf-level enum decoding rejects out-of-range values before `ValidateBasic` is invoked (this would need to be confirmed with a live build/test, e.g. via a Devin session, since the index does not include the full protobuf-generated decoding path for this message).

func (msg *MsgRegisterPointer) ValidateBasic() error {
	_, err := sdk.AccAddressFromBech32(msg.Sender)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid sender address (%s)", err)
	}

	if !common.IsHexAddress(msg.ErcAddress) {
		return sdkerrors.ErrInvalidAddress
	}

	return nil
}
