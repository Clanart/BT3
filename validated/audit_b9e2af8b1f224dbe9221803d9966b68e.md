## Title
Malicious submodule reference silently strands a stashed working-directory changes during branch checkout - (File: `app/src/lib/git/checkout.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
`checkoutBranch` performs the actual `git checkout` and then, as a *separate*, unguarded follow-up step, runs `git submodule update --init --recursive` via `updateSubmodulesAfterOperation`. If a target branch contains a submodule entry crafted to always fail this step (unreachable/invalid URL, blocked `file://` protocol, bad SHA, etc.), the function throws *after* the branch switch has already succeeded. `checkoutAndBringChanges` in `AppStore`, which stashes the user's local changes before retrying checkout and pops the stash afterward, has no exception handling around this second checkout call — so when it throws, `popStashEntry` is never reached and the user's changes remain orphaned in a stash while the branch has already moved to the attacker-controlled target.

### Finding Description
`checkoutBranch` executes the real state-changing Git operation first, then a second, independently-failable operation: [1](#0-0) 

`updateSubmodulesAfterOperation` unconditionally invokes `git submodule update --init --recursive` and lets any failure (e.g. `SubmoduleRepositoryDoesNotExist`, `InvalidSubmoduleSHA`, or protocol restrictions) propagate as an exception: [2](#0-1) 

These exact failure modes are recognized and surfaced by Desktop's own error mapping, confirming they are expected, attacker-triggerable outcomes rather than edge cases: [3](#0-2) 

`AppStore._checkoutBranch`'s "bring changes along" strategy (`checkoutAndBringChanges`) stashes uncommitted changes, retries the checkout, and only pops the stash if that retry succeeds — with no `try/finally` protecting the stash-pop step: [4](#0-3) 

Because `checkoutBranch`'s `git checkout` call already completed (moving HEAD/working tree to the malicious branch) before `updateSubmodulesAfterOperation` throws, the thrown error from the *second* `checkoutIgnoringChanges` call inside the `catch` block escapes `checkoutAndBringChanges` entirely, so `popStashEntry(repository, stash.stashSha)` is skipped. The stash created moments earlier is never restored. Upstream, `_checkoutBranch` only wraps the whole chain in a generic `.catch` that raises a `CheckoutError` banner — it has no special handling to detect or recover the now-orphaned stash: [5](#0-4) 

This is the same broken invariant as the EigenLayer report: a single failing sub-component processed as part of a larger batched/composite operation (a strategy in `completeQueuedWithdrawal`, here a submodule in `checkout`) causes the whole operation to report failure via exception, even though the primary state mutation it depends on (`_removeShares`/delegated-shares accounting there, `git checkout` HEAD move here) already succeeded — leaving an associated asset (queued shares there, the user's uncommitted work here) detached from the normal completion path and only recoverable via a manual, non-obvious workaround.

### Impact Explanation
A user who clones or fetches a repository (or checks out a branch from one) that embeds an intentionally-broken submodule reference in `.gitmodules`/index for the branch they're switching to will have their local uncommitted changes stashed and effectively stranded: the branch switch itself succeeds, but the app throws a generic checkout error and never runs `popStashEntry`. The user sees an error dialog implying the checkout failed, with no indication that their working-directory edits were moved into an anonymous stash. Their changes are not lost outright (`git stash list` would still show them), but from the normal Desktop UI flow they silently disappear from the Changes tab, and users unaware of the underlying stash mechanism may believe their uncommitted work is gone or may create new work that conflicts, effectively corrupting/losing what they intended to commit unless they know to inspect stashes manually.

### Likelihood Explanation
This requires no admin rights, no prior host compromise, and no unnatural user steps: any user who clones/fetches a third-party repository and switches to a branch with an attacker-crafted submodule entry, while having uncommitted local changes and Desktop's "bring changes to new branch" strategy active (a default/common preference), will trigger this path. Submodule URLs/paths/SHAs are attacker-controlled content that ships with the repository, matching the "attacker controls a cloned/fetched repository" criterion directly.

### Recommendation
Wrap the second `checkoutIgnoringChanges` call and its subsequent `popStashEntry` in a `try/finally` (or explicit error handling) so that a submodule-update failure after a successful `git checkout` does not prevent the stash from being restored; alternatively, decouple submodule updates from the checkout success path so a submodule failure doesn't abort the whole checkout flow (mirroring the "skip malicious entries" pattern from the original report), and surface a specific error/banner that tells the user their changes were stashed and how to recover them if the submodule step fails.

### Proof of Concept
1. Attacker publishes/pushes a repository with a branch `evil` whose `.gitmodules` references a submodule pointing to an unreachable or disallowed URL (e.g. `file:///nonexistent` or an SSH host that always rejects).
2. Victim clones the repo in GitHub Desktop, makes local uncommitted changes on `main`, and uses "bring my changes to `evil`" when switching branches (default `UncommittedChangesStrategy` behavior routed through `checkoutAndBringChanges`).
3. `checkoutIgnoringChanges` → `checkoutBranch` runs `git checkout evil` (succeeds, HEAD moves) then `updateSubmodulesAfterOperation` runs `git submodule update --init --recursive`, which fails and throws (`checkout.ts:122-127`, `submodule.ts:44-55`).
4. Because this throw happens inside the retry call at `app-store.ts:4729`, `popStashEntry` at `app-store.ts:4730` never executes.
5. Desktop shows a checkout error; the victim's uncommitted changes are stuck in an unnamed stash not surfaced anywhere in the UI, while the working directory now reflects the attacker's branch.

  private async checkoutAndBringChanges(
    repository: Repository,
    branch: Branch,
    currentRemote: IRemote | null
  ) {
    try {
      await this.checkoutIgnoringChanges(repository, branch, currentRemote)
    } catch (checkoutError) {
      if (!isLocalChangesOverwrittenError(checkoutError)) {
        throw checkoutError
      }

      const stash = (await this.createStashEntry(repository, branch))
        ? await getLastDesktopStashEntryForBranch(repository, branch)
        : null

      // Failing to stash the changes when we know that there are changes
      // preventing a checkout is very likely due to assume-unchanged or
      // skip-worktree. So instead of showing a "could not create stash" error
      // we'll show the checkout error to the user and let them figure it out.
      if (stash === null) {
        throw checkoutError
      }

      await this.checkoutIgnoringChanges(repository, branch, currentRemote)
      await popStashEntry(repository, stash.stashSha)

      this.statsStore.increment('changesTakenToNewBranchCount')
    }
  }
