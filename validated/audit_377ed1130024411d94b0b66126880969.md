### Title
`totalStaked()` reads raw `stakingToken.balanceOf(operator)` instead of tracked stake accounting, allowing griefing/dilution of `BaseRewardPool._provisionReward` reward math - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`)

### Summary
`BaseRewardPool.totalStaked()` returns `IERC20(stakingToken).balanceOf(operator)` [1](#0-0)  rather than the internally tracked sum of user deposits held in `MasterMagpie.userInfo`. Because `MasterMagpie._deposit`/`_withdraw` only update `user.amount`/`user.available` and move tokens via `safeTransferFrom`/`safeTransfer` [2](#0-1) , any unprivileged actor can inflate the raw balance read by `totalStaked()` simply by sending `stakingToken` directly to the `MasterMagpie` contract with a plain ERC20 `transfer`, without depositing or being credited any stake.

### Finding Description
`_provisionReward` (called from the permissionless `donateRewards` and from `queueNewRewards`) computes the reward-per-token increment as `(_amountReward * 10**decimals) / this.totalStaked()` [3](#0-2) . `totalStaked()` is a live ERC20 balance check, not a snapshot of the sum of `user.amount` recorded in `MasterMagpie` [4](#0-3) . An attacker can:
1. Acquire `stakingToken` on the open market.
2. Raw-transfer it directly to the `MasterMagpie` contract address (`operator`), bypassing `deposit()`/`depositFor()` entirely — this increases `IERC20(stakingToken).balanceOf(operator)` without incrementing any `userInfo[...].amount`.
3. Trigger (or wait for) any subsequent `_provisionReward` call — either their own permissionless `donateRewards` call [5](#0-4)  or a legitimate `queueNewRewards` call by the reward manager.
4. The divisor `totalStaked()` is now artificially inflated, so the `rewardPerTokenStored` increment for that call is smaller than it should be relative to the reward tokens actually transferred in, permanently under-crediting stakers for that provisioning event. `historicalRewards` still records the full amount, but the cumulative `rewardPerTokenStored * (sum of real user shares)` will forever be less than `historicalRewards`, breaking the backing invariant.

There is no reconciliation mechanism: once `rewardPerTokenStored` is incremented using the inflated divisor, it is never corrected retroactively.

Important caveat found during investigation: I could not find any `emergencyWithdraw`/sweep function in `MasterMagpie` that lets an attacker later recover the raw-transferred "dust" tokens based on actual balance rather than tracked `userInfo` [6](#0-5) . Withdrawals are gated on `user.available`/`user.amount`, not on raw contract balance, so the donated tokens cannot be withdrawn back out by the attacker. This means the described "withdraw the donated dust separately" step in the question is not achievable with the code paths found — the attacker cannot recoup the raw-transferred tokens, so this is a permanent self-funded griefing attack, not a theft-for-profit exploit. It still causes a genuine, permanent misallocation/dilution of legitimately-donated yield for real stakers, satisfying the "permanent freezing of unclaimed yield" impact class, but with no direct financial upside for the attacker.

### Impact Explanation
Each time `_provisionReward` runs while `totalStaked()` is inflated by a raw transfer, a fraction of the reward tokens transferred into the pool during that call becomes permanently unaccounted for in `rewardPerTokenStored`, i.e. unclaimable by any staker under normal reward math — a quantifiable violation of the backing invariant (`historicalRewards` vs. `rewardPerTokenStored * totalStaked`). This matches "permanent freezing of unclaimed yield." However, because the attacker cannot recover the raw-transferred stakingToken (no sweep/skim path was found), the attack costs the attacker capital proportional to the desired dilution ratio, with no direct profit — it is a griefing vector against protocol reward accounting rather than a fund-theft exploit.

### Likelihood Explanation
Feasible in principle (no privileged role required, `donateRewards` is fully permissionless, raw ERC20 transfer requires no special access), but capital-intensive: to meaningfully dilute `totalStaked()` the attacker must transfer an amount of `stakingToken` comparable to the existing total staked amount, and that capital is permanently lost with no way to recover it. This significantly limits real-world incentive and repeatability, since the attacker bears an unrecoverable cost roughly proportional to the damage caused, and gains nothing from the pool's own reward distribution being diluted (they receive the same proportional share as everyone else on their own actual stake, if any).

### Recommendation
Change `totalStaked()` in `BaseRewardPool`/`BaseRewardPoolV2` to return the internally tracked total (e.g., a running total updated in `MasterMagpie._deposit`/`_withdraw`, or `sizeOfPool`/pool-level accounting already computed via `_calLpSupply`) rather than the raw `IERC20(stakingToken).balanceOf(operator)`, so it cannot be influenced by unsolicited direct token transfers.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie` + `BaseRewardPool` with a mock ERC20 `stakingToken` and mock reward token; register the reward token via `queueNewRewards` once so `isRewardToken` is true.
2. User A deposits `1000e18` `stakingToken` via `MasterMagpie.deposit`.
3. Baseline: reward manager calls `queueNewRewards(100e18, rewardToken)`; record `rewardPerTokenStored` (call it `R1`).
4. Reset state (or use a second scenario): before an equivalent `queueNewRewards(100e18, rewardToken)` call, have an attacker EOA call `stakingToken.transfer(address(masterMagpie), 9000e18)` directly (no `deposit()`).
5. Call `queueNewRewards(100e18, rewardToken)` again; record `rewardPerTokenStored` (call it `R2`).
6. Assert `R2 < R1` (same reward amount produces a smaller reward-per-token increment purely due to the raw transfer).
7. Assert `rewards[rewardToken].historicalRewards` grows correctly in both cases, but `rewardPerTokenStored * (User A's tracked balanceOf) < historicalRewards`, demonstrating the backing invariant violation.
8. Attempt to have the attacker withdraw the `9000e18` dust via `MasterMagpie.withdraw`/`emergencyWithdraw` and assert it reverts or returns 0, confirming the tokens are permanently stuck (no profit path for the attacker).
