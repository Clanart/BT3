### Title
`host_deposit_constant` passes `deposit_value_bytes` instead of `move_txid` to `deposit_constant`, causing permanent journal hash mismatch and operator proof generation failure — (`bridge-circuit-host/src/structs.rs`)

---

### Summary

The `host_deposit_constant` function in `bridge-circuit-host/src/structs.rs` passes `deposit_value_bytes` (the deposit amount from the EVM storage proof) as the 4th argument to `deposit_constant`, where `move_txid` (the move transaction ID) is expected. The circuit and the verifier both correctly pass `move_txid`. Because both values are `[u8; 32]`, Rust's type system does not catch the mismatch. The result is that the host's `deposit_constant` always differs from the circuit's, causing the journal hash check in `prove_bridge_circuit` to always fail, permanently preventing any operator from generating a valid bridge circuit proof to defend against a challenge.

---

### Finding Description

The `deposit_constant` function is defined in `circuits-lib/src/bridge_circuit/mod.rs`:

```rust
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],        // 4th param: move transaction ID
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant
``` [1](#0-0) 

The docstring explicitly states the 4th parameter is `move_txid`: "A 32-byte array representing the transaction ID of the move transaction."

**In the circuit** (`circuits-lib/src/bridge_circuit/mod.rs`), the correct value is passed:

```rust
let (user_wd_outpoint, vout, move_txid) =
    verify_storage_proofs(&input.sp, light_client_circuit_output.l2_state_root);
...
let deposit_constant = deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    *move_txid,   // ✓ correct: move transaction ID from storage proof
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
);
``` [2](#0-1) 

**In the verifier** (`core/src/verifier.rs`), the correct value is also passed:

```rust
let deposit_constant = deposit_constant(
    kickoff_data.operator_xonly_pk.serialize(),
    watchtower_challenge_start_idx,
    &watchtower_pubkeys,
    move_txid,   // ✓ correct
    round_txid,
    vout,
    self.config.protocol_paramset.genesis_chain_state_hash,
);
``` [3](#0-2) 

**In the host** (`bridge-circuit-host/src/structs.rs`), the wrong value is passed:

```rust
let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    deposit_value_bytes,   // ✗ WRONG: deposit amount, not move_txid
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
``` [4](#0-3) 

The host's `deposit_constant` feeds into `host_journal_hash()`: [5](#0-4) 

Which is then compared against the circuit's committed journal hash in `prove_bridge_circuit`:

```rust
if *journal_hash.as_bytes() != succinct_receipt_journal {
    return Err(eyre!("Journal hash mismatch"));
}
``` [6](#0-5) 

Since `deposit_value_bytes` (a 32-byte big-endian encoding of the deposit amount in wei) is structurally different from `move_txid` (a 32-byte Bitcoin transaction ID), the two `deposit_constant` values will always differ, and the journal hash check will always fail.

---

### Impact Explanation

`prove_bridge_circuit` is the operator's sole mechanism to generate a Groth16 proof to defend against a BitVM2 challenge. Because the host always computes the wrong `deposit_constant`, this function always returns an error. Any operator who is challenged cannot produce a valid proof, cannot spend the disprove connector in their favor, and will have their collateral (bridged BTC) slashed by the challenger. This breaks the bridge's safety guarantee: an honest operator who correctly fronted a withdrawal is indistinguishable from a malicious one because neither can produce a proof that passes the host's journal hash check.

The `deposit_constant` also propagates into `BridgeCircuitBitvmInputs`, which is used for on-chain BitVM2 verification: [7](#0-6) 

Even if the journal hash check were bypassed, the wrong `deposit_constant` would cause the Groth16 public input scalar to be wrong, making on-chain proof verification fail.

---

### Likelihood Explanation

The bug is unconditional: every call to `prove_bridge_circuit` on any network will compute the wrong `deposit_constant` in the host. Any challenger can challenge any operator knowing the operator can never produce a valid proof. No special conditions, privileged access, or race conditions are required.

---

### Recommendation

In `bridge-circuit-host/src/structs.rs`, `host_deposit_constant` must extract the move transaction ID from the storage proof (mirroring what `verify_storage_proofs` does in the circuit) and pass it as the 4th argument to `deposit_constant` instead of `deposit_value_bytes`. The deposit value bytes, if needed for other purposes, should be passed separately or not at all in this call.

---

### Proof of Concept

1. Operator fronts a withdrawal and broadcasts a kickoff transaction.
2. A challenger sends the challenge transaction.
3. Operator calls `prove_bridge_circuit` to generate a Groth16 proof.
4. Host calls `host_deposit_constant`, which computes `deposit_constant` using `deposit_value_bytes` (e.g., `0x0000...0de0b6b3a7640000` for 1 ETH) instead of `move_txid` (e.g., `0xabcd...ef01`).
5. Circuit commits journal hash using `deposit_constant(move_txid, ...)`.
6. Host computes journal hash using `deposit_constant(deposit_value_bytes, ...)`.
7. Check `if *journal_hash.as_bytes() != succinct_receipt_journal` triggers.
8. `prove_bridge_circuit` returns `Err("Journal hash mismatch")`.
9. Operator cannot produce any proof; challenger spends the disprove connector and burns operator collateral. [8](#0-7)

    tracing::info!("Starting bridge circuit proof generation");
    let bridge_circuit_input = bridge_circuit_host_params

    // Header chain verification

        bitcoin::Network::Signet => SIGNET_HEADER_CHAIN_METHOD_ID,
