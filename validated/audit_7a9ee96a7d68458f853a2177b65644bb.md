### Title
Slice-bounds panic in `consoleLog.decode` from attacker-controlled offset in precompile input — ([File: blockchain/vm/contracts.go])

### Summary
The `consoleLog` precompiled contract (address `0x000000000000000000636F6E736F6C652E6C6F67`) decodes `string`/`bytes` parameters from raw call `input` without validating that the attacker-supplied 32-byte "offset" word is non-negative before using it as a Go slice index, mirroring the `loona-hpack` class of bug (decoding untrusted input causes an unrecoverable panic rather than a graceful error).

### Finding Description
`consoleLog.Run` calls `toLogString`, which parses the 4-byte selector and hands the remaining `params` bytes to `c.decode` along with the fixed parameter-type list resolved from `common.ConsoleLogSignatures`: [1](#0-0) 

Inside `decode`, for `StringTy`/`BytesTy` parameters, the "offset" word is read directly from attacker-controlled `params` and converted to a Go `int` via `big.Int.Int64()`, with only an upper-bound check (`len(params) < start+registerSize`) — there is no check that `start >= 0`: [2](#0-1) [3](#0-2) 

`big.Int.Int64()` is documented to return an undefined/truncated result if the value doesn't fit in an `int64`. Since the offset word is a full 32-byte big-endian value taken straight from the call data, an attacker can craft a value (e.g. all `0xFF` bytes) whose `Int64()` result is negative, making `start` a negative `int`. The subsequent bound check `len(params) < start+registerSize` becomes trivially satisfied for a negative `start`, and the code proceeds to slice `params[start : start+registerSize]` with a negative lower bound, which panics with "slice bounds out of range" in Go — an unrecoverable runtime panic rather than a decode error, exactly analogous to the `loona_hpack`/`hpack-rs` issue referenced in the report (index computed from untrusted input used without a lower-bound sanity check).

### Impact Explanation
A panic inside `PrecompiledContract.Run`, invoked from EVM execution, propagates as a Go runtime panic. Depending on whether callers of the interpreter loop recover panics uniformly, this can crash the node process executing/validating the block (denial of service) or, if only some nodes crash while others recover differently, could cause a state/consensus divergence between nodes running with `--vm.use-console-log`/`UseConsoleLog` enabled versus those without. Because the precompile is added to the EVM's active precompile map only when the node operator explicitly enables console.log for local/test networks, mainnet exploitability is contingent on that opt-in configuration; on any deployment where it is enabled it is reachable by any contract deployer/caller who can trigger a `CALL` to the console.log address with crafted calldata — no special privilege is required beyond deploying/calling a contract, satisfying "unprivileged transaction sender" reachability.

### Likelihood Explanation
Exploitation requires a single crafted transaction/call whose `input` targets the console.log precompile address with a selector matching `StringTy`/`BytesTy` and a poisoned offset word; this is trivial to construct and fully deterministic. The only precondition is that `Config.UseConsoleLog` be true for the executing node (a config flag, not runtime-negotiated), which limits blast radius to networks/nodes that opt into this debugging feature (commonly local/dev/test networks) rather than default mainnet nodes.

### Recommendation
In `consoleLog.decode` (`blockchain/vm/contracts.go`), validate that computed offsets and sizes are non-negative and within `len(params)` before slicing — e.g., check `start < 0 || size < 0` explicitly, and prefer using `uint64`/bounds-checked arithmetic instead of `int64`/`int` conversions from raw big-endian words, matching the fix pattern used by `hpack-patched` (validate decoded length/offset before use).

### Proof of Concept
```go
// Selector for {StringTy} e.g. 0x41304fac (see common.ConsoleLogSignatures)
selector := []byte{0x41, 0x30, 0x4f, 0xac}
params := make([]byte, 64)
// offset word: all 0xFF -> big.Int.Int64() returns -1
for i := 0; i < 32; i++ {
    params[i] = 0xFF
}
input := append(selector, params...)

c := &consoleLog{}
_, _ = c.toLogString(input) // panics: slice bounds out of range [-1:31]
```
This mirrors the PoC pattern in the report (`Decoder.decode(&[0x3f])` panicking on malformed length) — an attacker-controlled length/offset field is trusted without a lower-bound check before being used to index into a byte slice.

func (c *consoleLog) toLogString(input []byte) (string, error) {
	if len(input) < 4 {
		return "", errors.New("input too short")
	}
	selector := binary.BigEndian.Uint32(input[:4])
	params := input[4:]

	types, ok := common.ConsoleLogSignatures[selector]
	if !ok {
		return "", errors.New("unknown selector")
	}
	decoded, err := c.decode(params, types)
	if err != nil {
		return "", err
	}

	return strings.Join(decoded, " "), nil
}
