### Title
WSEI `withdraw()` uses `.transfer()` with a fixed 2300 gas stipend, allowing permanent freezing of wrapped SEI for contract holders - (File: contracts/src/WSEI.sol)

### Summary
The genesis-deployed WSEI ("Wrapped Sei") contract's `withdraw()` function sends native value back to the caller using Solidity's `.transfer()`, which hardcodes a 2300 gas stipend. This is the exact bug class described in the external report (fixed 2300 gas ETH send), and it is present verbatim in sei-chain's own wrapped-native-token contract, which is deployed via CLI/genesis artifacts and reachable by any unprivileged EVM user.

### Finding Description
`WSEI.withdraw()` deducts the caller's balance and then relays native SEI to `msg.sender` via `payable(msg.sender).transfer(wad)`: [1](#0-0) 

`.transfer()` in Solidity forwards only a fixed 2300 gas stipend to the recipient. If `msg.sender` is a smart contract (rather than an EOA) whose `receive()`/`fallback()` performs any state-changing logic (e.g., an SLOAD due to EIP-1884 repricing, emitting an event, or any nontrivial computation), the call will run out of gas and revert. Because the balance decrement (`balanceOf[msg.sender] -= wad;`) happens before the `.transfer()` call but is rolled back together with the whole transaction on revert, the net effect is not loss of the internal `balanceOf` state, but rather permanent inability for that contract to ever withdraw its wrapped SEI through this path — the transaction always reverts, regardless of gas limit supplied by the caller, because the stipend is hardcoded by the EVM opcode semantics that `.transfer()` compiles to, not by the caller-specified gas limit.

This is the same root cause identified in the referenced Lido `Lido.sol` report: reliance on a fixed low-gas stipend for an outbound native-value transfer, which can silently fail whenever the recipient requires more gas than 2300 (which can happen due to gas-cost repricing of opcodes, or simply because the recipient is a contract with any receive-logic).

WSEI is compiled into `x/evm/artifacts/wsei/artifacts.go` (embedding `WSEI.bin`/`WSEI.abi`) and referenced from `x/evm/client/cli/tx.go`, indicating it is a first-class, chain-provided ERC20-wrapper for native SEI (analogous to WETH) rather than an example/test-only contract. [2](#0-1) 

### Impact Explanation
Any smart contract (e.g., a DEX router, vault, multisig, or any composable DeFi contract) that deposits SEI into WSEI and later needs to withdraw it will have its withdrawal permanently blocked if its `receive()`/`fallback()` logic costs more than 2300 gas to execute — a routine situation for contracts with even simple bookkeeping in their fallback (event emission plus an SLOAD already exceeds 2300 gas after EIP-1884 costs). This results in the wrapped SEI balance being permanently unwithdrawable/locked for that contract despite it holding a legitimate, correctly-accounted `balanceOf` entry, i.e., a permanent freezing of funds condition. Given WSEI is the canonical wrapped-native contract used throughout the EVM ecosystem for SEI (analogous to WETH's central role on Ethereum-compatible chains), the blast radius includes any DeFi protocol built to interact with WSEI as a contract counterparty.

### Likelihood Explanation
No special privilege is required to trigger this: any contract account can call `deposit()` and then `withdraw()`. The condition depends only on the gas cost of the caller-contract's fallback/receive logic exceeding 2300 gas, which is common for non-trivial contracts and is exactly the scenario the referenced report warns about (opcode gas repricing making the fixed stipend insufficient). This is a deterministic, caller-triggerable condition rather than a probabilistic or adversarial-timing bug.

### Recommendation
Replace the hardcoded-stipend `.transfer()` call in `withdraw()` with a low-level `call` that forwards the available gas and checks the return value, e.g.:
```solidity
(bool success, ) = msg.sender.call{value: wad}("");
require(success, "WSEI: ETH_TRANSFER_FAILED");
```
This mirrors the pattern already used safely elsewhere in the codebase's own `TransferHelper.safeTransferETH` [3](#0-2) , and should be applied consistently to `WSEI.sol`'s `withdraw()` function.

### Proof of Concept
1. Deploy a helper contract `Sink` whose `receive() external payable { someMapping[msg.sender] = block.timestamp; }` (any state write costing >2300 gas).
2. From `Sink`, call `WSEI.deposit()` with `value = X` (via a `call` forwarding value, since `Sink` needs to be `msg.sender` of the deposit to later withdraw).
3. From `Sink`, call `WSEI.withdraw(X)`.
4. Observe the transaction reverts inside `.transfer()`'s forwarded-2300-gas execution of `Sink.receive()`, regardless of the outer transaction's gas limit — `Sink`'s WSEI balance (`X`) remains stuck in the WSEI contract forever, since every future `withdraw()` call from `Sink` will hit the same 2300-gas ceiling. // SPDX-License-Identifier: MIT
```text
pragma solidity ^0.8.0;

contract WSEI {
    string public name     = "Wrapped Sei";
    string public symbol   = "WSEI";
    uint8  public decimals = 18;

    event  Approval(address indexed src, address indexed guy, uint wad);
    event  Transfer(address indexed src, address indexed dst, uint wad);
    event  Deposit(address indexed dst, uint wad);
    event  Withdrawal(address indexed src, uint wad);

    mapping (address => uint)                       public  balanceOf;
    mapping (address => mapping (address => uint))  public  allowance;

    fallback() external payable {
        deposit();
    }
    receive() external payable {
        deposit();
    }
    function deposit() public payable {
        balanceOf[msg.sender] += msg.value;
        emit Deposit(msg.sender, msg.value);
    }
    function withdraw(uint wad) public {
        require(balanceOf[msg.sender] >= wad);
        balanceOf[msg.sender] -= wad;
        payable(msg.sender).transfer(wad);
        emit Withdrawal(msg.sender, wad);
    }
```
