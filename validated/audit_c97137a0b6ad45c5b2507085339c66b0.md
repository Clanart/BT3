## Finding: SSH credential "most recent" tracking map is silently overwritten per trampoline operation, defeating the rollback safety-net

### Title
Overwritten `mostRecentSSHCredentials` entry lets stale/invalid SSH secrets survive a failed git operation - (File: `app/src/lib/ssh/ssh-credential-storage.ts`)

### Summary
This is the same bug class as the QuailFinance report: a state map is keyed by an identifier (there: `potCreator`/round; here: `operationGUID`, the trampoline token for one git operation) and a later `.set()` call unconditionally overwrites the map entry with no check for a pre-existing value. In QuailFinance this destroyed an unclaimed reward; in Desktop it destroys the bookkeeping needed to roll back a previously-persisted SSH secret, so a credential that should never have survived a failed authentication is left permanently in the OS keychain.

### Finding Description
`mostRecentSSHCredentials` is a single `Map<string, SSHCredentialEntry>` keyed by `operationGUID` (== the trampoline token for the whole git invocation): [1](#0-0) 

The docstring states the explicit invariant: a credential must not be persisted "until we know the git operation finished successfully." In practice, `setSSHCredential` writes to the OS keychain immediately and only *tracks* the entry for possible rollback: [2](#0-1) 

Tracking is done with an unconditional overwrite, with no check whether an entry for that `operationGUID` already exists: [3](#0-2) 

Rollback on failure only ever looks at (and deletes) that single, most-recently-set entry: [4](#0-3) 

The askpass handler calls this tracking/store logic once per prompt, and a single git operation (one `operationGUID`/trampoline token, minted once per `git` invocation) can legitimately receive *multiple* prompts — e.g. a passphrase prompt for one SSH key, then another passphrase prompt for a second identity file, and/or a username/password prompt — all sharing the same `operationGUID`: [5](#0-4) [6](#0-5) 

If the overall operation ultimately fails with an SSH auth error, `withTrampolineEnv` calls `deleteMostRecentSSHCredential(token)` exactly once: [7](#0-6) 

Because `mostRecentSSHCredentials.set()` overwrote earlier entries for the same `operationGUID`, this only removes the *last* credential written to the keychain during that operation. Any earlier credential(s) written to the keychain in the same operation (e.g., the passphrase for the first SSH key tried) are never rolled back, even though the operation as a whole failed — silently violating the "only persist on success" guarantee the code comments claim to provide.

### Impact Explanation
An SSH server/remote that an unprivileged attacker controls (the exact "attacker controls ... a git remote/proxy response" primitive) can cause the local `ssh` client to attempt multiple identity files in sequence before ultimately rejecting authentication (standard OpenSSH client behavior: try each configured/offered identity, prompting for each encrypted key's passphrase via `SSH_ASKPASS`, then fail if none are accepted). Within Desktop, all of these prompts occur under the same trampoline `operationGUID`. If the user opts to "remember" more than one of these passphrases, only the last one is cleaned up when the operation is finally reported as failed — the earlier passphrase(s) remain permanently stored in the OS keychain, even though Desktop's own logic states they should be discarded because the operation didn't succeed. This is a silent, unintended persistence of a secret that the guard mechanism was explicitly built to prevent, caused entirely by remote-controlled prompt sequencing that a malicious/misconfigured server can trigger.

### Likelihood Explanation
No local access, admin rights, or social engineering is required beyond normal use of Desktop against an attacker-influenced SSH remote (e.g. a compromised/rogue server presenting several key challenges, or a proxy manipulating the SSH negotiation). Multiple sequential askpass prompts within one git command are a normal, easily reproducible SSH client behavior, so triggering the overwrite path only requires the user to have more than one relevant SSH identity configured and to check "remember" more than once during a single failing operation — a realistic scenario for anyone managing multiple SSH keys.

### Recommendation
Track pending-to-be-persisted SSH credentials per `operationGUID` as a **collection** (e.g. `Map<string, SSHCredentialEntry[]>`) rather than a single overwritten value, and on failure iterate and delete all entries recorded for that operation instead of only the most recent one — mirroring the report's own recommendation to check existing state (`pot.hasWon`) before overwriting it.

### Proof of Concept
1. Configure two SSH private keys for a host (e.g. `id_rsa_primary`, `id_rsa_secondary`), both passphrase-protected, offered in that order by the SSH client/agent.
2. Point the remote at (or MITM) a server that always rejects the offered public keys (attacker-controlled SSH endpoint).
3. Run a Desktop git operation (e.g. `git fetch`) against that remote.
4. When prompted "Enter passphrase for key 'id_rsa_primary'", enter the correct passphrase and check "Remember passphrase" → `setSSHKeyPassphrase(token, ...)` writes it to the keychain and calls `mostRecentSSHCredentials.set(token, {...primary})`.
5. SSH then tries `id_rsa_secondary`; Desktop prompts again for its passphrase with the **same** trampoline token. Enter it and again check "Remember" → `mostRecentSSHCredentials.set(token, {...secondary})` overwrites the map entry for `token`, losing the reference to the primary key's entry.
6. The server rejects both keys; `git` exits with `SSHAuthenticationFailed`; `withTrampolineEnv`'s catch block calls `deleteMostRecentSSHCredential(token)`, which deletes only the `secondary` key's keychain entry.
7. Inspect the OS keychain: the `primary` key's passphrase entry (`GitHub Desktop - SSH key passphrases` / `id_rsa_primary` hash) remains permanently stored, despite the git operation having failed — contradicting the documented "only persist on success" invariant.

/**
 * Deletes the SSH credential from the TokenStore. Used when the git operation
 * fails to authenticate.
 */
export async function deleteMostRecentSSHCredential(operationGUID: string) {
  const entry = mostRecentSSHCredentials.get(operationGUID)
  if (entry) {
    log.info(
      `SSH auth failed, deleting credential for ${entry.store}:${entry.key}`
    )

    await TokenStore.deleteItem(entry.store, entry.key)
  }
}
