### Title
Stale-state OAuth completion callback allows cross-session account/token binding in `SignInStore.resolveOAuthRequest()` - (File: app/src/lib/stores/sign-in-store.ts)

### Summary
`SignInStore.authenticateWithBrowser()` and `SignInStore.resolveOAuthRequest()` implement a check-then-act pattern around a mutable single `this.state` field. The CSRF/state check is performed once, before two `await`ed network calls (`requestOAuthToken`, `fetchUser`); but the eventual completion (`onAuthCompleted`) is invoked against whatever `this.state.oauthState` happens to be *at resolution time*, not the state that was validated before the awaits. If a second OAuth/sign-in session is started while the first is still awaiting its network round trip, the first flow's resolved account can be delivered into the second flow's promise, analogous to the reported reentrancy bug where a value is checked before an external call but consumed after it, once the external call has mutated the guarding state.

### Finding Description
In `authenticateWithBrowser()`, each call creates a new `csrfToken` and calls `this.setState(...)` overwriting `this.state.oauthState`, unconditionally replacing any previous in-flight `oauthState` (including its `resolve`/`reject` for a still-pending promise) [3](#0-2) .

In `resolveOAuthRequest(action)`, the CSRF check `this.state.oauthState.state !== action.state` is done up front, but the token is then fetched asynchronously, and completion is delivered via `this.state.oauthState.onAuthCompleted(account)` — re-reading the *live* `this.state` property rather than a value captured at validation time:

```ts
const { endpoint } = this.state
const token = await requestOAuthToken(endpoint, action.code)

if (token) {
  const account = await fetchUser(endpoint, token)
  this.state.oauthState.onAuthCompleted(account)   // <-- re-reads this.state after awaits
}
``` [4](#0-3) 

If, during the two `await`s, a new sign-in session is started (e.g. another `authenticateWithBrowser()` call for a *different* endpoint, overwriting `this.state.oauthState` with a new `csrfToken`/`resolve`/`reject`), the still-pending call resumes and invokes `this.state.oauthState.onAuthCompleted(account)` on the *new* oauthState object — resolving the second session's promise with the first session's authenticated account, without ever re-validating that `action.state` matches the currently-active `oauthState.state`.

The `.then()` handler that consumes the resolved account in `authenticateWithBrowser()` only checks that `this.state.kind === SignInStep.Authentication` (i.e. that some sign-in flow is still active) — it does **not** check that the resolved account corresponds to *this* invocation's `csrfToken`/`endpoint`:
```ts
.then(account => {
  if (!this.state || this.state.kind !== SignInStep.Authentication) {
    return
  }
  this.emitAuthenticate(account)     // account may belong to a *different* session
  this.setState({ kind: SignInStep.Success, resultCallback: this.state.resultCallback })
})
``` [5](#0-4) 

Only the `.catch()` branch re-validates `this.state.oauthState?.state === csrfToken` [6](#0-5)  — the success path has no equivalent guard, exactly the asymmetry described in the report ("no check to make sure X before the action is committed").

### Impact Explanation
The corrupted value is the pairing between an OAuth-authenticated `Account` and the `resultCallback`/`endpoint` context of the session that is ultimately notified of success. A malicious repository/organization can force GitHub Desktop to display the SAML re-auth flow (`samlReauthRequired` handler, driven entirely by attacker-controlled `remote:` stderr text from a git server/proxy) [7](#0-6) . If the user has two such flows race (e.g., two different remotes triggering SAML re-auth in quick succession, or a legitimate manual sign-in overlapping with an attacker-triggered SAML popup), the account resolved for one endpoint can be delivered to the `resultCallback`/`retryAction` context of another. Because `SAMLReauthRequiredDialog.onSignIn` immediately triggers `dispatcher.performRetry(this.props.retryAction)` upon a `'success'` result [2](#0-1) , this can lead to a `RetryAction` (e.g., a push) being retried under the impression that reauthorization for organization/endpoint B succeeded, while in fact the credentials used originate from an unrelated flow — i.e. unauthorized OAuth/account binding across sessions.

### Likelihood Explanation
This requires two concurrent sign-in/OAuth flows to be in flight in the renderer at the same time — a narrow window, but reachable without local access, admin rights, or prior compromise: the SAML-reauth trigger is fully attacker-controlled via crafted `remote:` error text on a git server the user pushes/fetches to, and the OAuth completion path itself already anticipates concurrent/duplicate deep-link deliveries (its comment references "browser reloading the callback URL"), showing that overlapping OAuth completions are an anticipated real-world occurrence in this exact code, not merely theoretical.

### Recommendation
Capture the validated `oauthState`/`csrfToken` object into a local variable at validation time and use that captured reference (not `this.state`) when calling `onAuthCompleted`/`onAuthError`. Additionally, in `authenticateWithBrowser()`'s `.then()` success handler, re-validate that `this.state.oauthState?.state === csrfToken` (mirroring the existing `.catch()` check) before calling `emitAuthenticate()` and transitioning to `SignInStep.Success`, so a stale/foreign session's resolution can never be attributed to the currently active flow.

### Proof of Concept
1. User's Desktop session pushes to attacker-controlled org A; Desktop shows `SAMLReauthRequiredDialog` for org A (triggered purely by `remote:` stderr crafted per `samlReauthErrorMessageRe`) and the user clicks "Continue in Browser" → `authenticateWithBrowser()` sets `oauthState.state = csrfTokenA` and opens the browser.
2. Before the user finishes in the browser, a second git operation against a different attacker/legit org B also fails with a SAML re-auth error, and the user (or an automated retry) triggers a second `authenticateWithBrowser()` call for endpoint B; `this.state.oauthState` is overwritten with `csrfTokenB`.
3. The user completes the browser flow for A; the deep link fires `resolveOAuthRequest({ code, state: csrfTokenA })`. The state check at the top of `resolveOAuthRequest` fails if `this.state.oauthState.state` is already `csrfTokenB`, so this particular ordering is blocked — but if `resolveOAuthRequest` for A begins ("this.state.oauthState.state === csrfTokenA") and only then, mid-await inside `requestOAuthToken`/`fetchUser`, session B's `authenticateWithBrowser()` overwrites `this.state.oauthState` to `csrfTokenB`, the subsequent `this.state.oauthState.onAuthCompleted(accountA)` call resolves session B's promise with `accountA`.
4. Session B's `.then()` handler only checks `this.state.kind === SignInStep.Authentication` (true) and calls `emitAuthenticate(accountA)` and `resultCallback({ kind: 'success', account: accountA })`, which is consumed by `SAMLReauthRequiredDialog` for org B, causing `dispatcher.performRetry(retryActionB)` to run believing reauthorization for org B succeeded, when the account actually came from org A's flow.

Note: exploiting this precisely requires winning a race between two concurrent sign-in flows within the renderer process; I was not able to fully verify from static analysis alone whether other application-level guards (e.g., disabling concurrent SAML dialogs) prevent two `authenticateWithBrowser()` calls from being in flight simultaneously in the current UI — this would need dynamic/runtime verification beyond what the indexed code confirms.

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {

    }

    if (!this.state.oauthState) {
      return
    }

    const { endpoint } = this.state

      this.state.oauthState.onAuthCompleted(account)
