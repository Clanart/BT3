### Title
Silent origin-remote rewrite via GitHub API `clone_url` in `updateRemoteUrl` — attacker-controlled repository object can hijack a user's push/fetch destination - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The reported LI.FI bug is a "trust it once, trust it again" invariant break: an attacker-controlled value (`underlying()`) is fetched, validated, and then re-fetched later expecting the same value, but the second fetch silently returns something different, causing funds to be routed to an attacker address. `GitHubDesktop`'s `updateRemoteUrl` function has the same broken invariant applied to `git remote` URLs instead of token addresses: it fetches an owner/name pair from the local `origin` remote, later re-resolves that owner/name against the live GitHub API, and if the API's `clone_url` for that owner/name doesn't match what's stored locally, Desktop **automatically rewrites `origin`'s URL** to whatever the API returned — with no ownership/identity re-verification beyond "same owner/name string, same protocol".

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` derives `owner`/`name` purely from parsing the local git remote URL string via `matchGitHubRepository` (`app/src/lib/stores/app-store.ts:4964-4977`, backed by `app/src/lib/repository-matching.ts:29-46`), then calls `api.fetchRepository(owner, name)` (`app/src/lib/stores/app-store.ts:4890`) and passes the resulting `apiRepo` straight into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then does: [2](#0-1) 

The corrupted value is `gitStore.defaultRemote`'s URL (`origin`), which is silently overwritten to `apiRepo.clone_url` whenever:
1. `protocolsMatch` — the new URL's scheme (http/https) equals the old one (a trivially satisfiable condition since an attacker fully controls the scheme of a URL they own),
2. `remoteUrlUnchanged` — the *previously cached* `gitHubRepository.cloneURL` (from an earlier successful API resolution, e.g., before a repo was deleted/renamed/transferred) still matches the current git remote, and
3. `!urlsMatch` — the *new* API-provided `clone_url` differs from the current remote.

The owner/name identity used to look up the "fresh" API repository is nothing more than a string match on `owner` + `name` parsed out of the URL (`parseRemote` in `app/src/lib/remote-parsing.ts:55-64`). GitHub allows repository owners/organizations to be renamed, and previously-used `owner/name` slugs to be re-claimed by a different account after the original repository is deleted, renamed away, or an organization is disbanded ("repo-jacking"/"namespace-squatting"). Because `GitHubDesktop`'s only remaining anchor of trust is this string, the second (later) `fetchRepository(owner, name)` call can return a *completely different* GitHub repository object controlled by an attacker who has since claimed that identical `owner/name` slug — exactly mirroring the AnyswapFacet pattern where `IAnyswapToken(_anyswapData.token).underlying()` was trusted to return the same value on both calls, but an attacker made the second call return something else.

No additional check (repository ID, commit graph relationship, user confirmation) is performed before `gitStore.setRemoteURL(...)` (`app/src/lib/git/remote.ts:57-64`) is invoked, so the rewrite happens fully silently in the background (this code path runs during routine background refreshes such as `_fetch`, `_pull`, and repository selection via `withRefreshedGitHubRepository` / `repositoryWithRefreshedGitHubRepository`, not just on explicit user action).

### Impact Explanation
Once `origin` is silently repointed to the attacker's repository:
- Subsequent user-initiated `git push` operations in Desktop (`app/src/lib/git/push.ts`) will push the user's code and history to the attacker-controlled repository, exfiltrating source code and, with `envForRemoteOperation`/credential helpers, causing the trampoline to authenticate against the attacker's endpoint using the account's credentials over an HTTPS remote the attacker controls (credential/token exposure risk if the attacker's endpoint is designed to harvest Basic Auth headers, since the URL's host is fully attacker-chosen as long as it's a valid parseable GitHub-URL shape resolvable to some account's configured endpoint).
- Subsequent `git fetch`/`git pull` will merge in attacker-supplied history into the user's working repository — a silent corruption of what the user later commits/builds on top of, satisfying the "silent corruption of what the user commits or pushes" impact category.
- All of this happens without any prompt; the user only sees the remote continue to say "origin" with no explicit re-authorization step.

### Likelihood Explanation
This requires no local access, no malware, and no direct compromise of the user's machine — only that a GitHub `owner/name` pair the user's `origin` currently points at becomes re-claimable and is claimed by an attacker (e.g., original org/user renamed or repo deleted, which happens commonly in the OSS ecosystem — repo-jacking is a well-documented real-world attack pattern). The vulnerable code path (`repositoryWithRefreshedGitHubRepository`) runs automatically during background repository refresh, `_fetch`, and `_pull` (`app/src/lib/stores/app-store.ts:5895-5915`), so no unusual user action is required beyond normal Desktop usage.

### Recommendation
- Do not silently rewrite `origin`'s URL based solely on owner/name string equality against a freshly fetched API repository. At minimum, compare the GitHub repository's stable numeric `id` (already partially tracked, see `IDatabaseGitHubRepository`/`owner.id` in `app/src/lib/stores/repositories-store.ts`) between the previously stored `GitHubRepository` and the new `apiRepo` before treating them as "the same repository that simply moved."
- If the `id` differs (repository was deleted/recreated/transferred to a different owner), require explicit user confirmation before updating the remote, rather than auto-updating via `gitStore.setRemoteURL`.
- Consider surfacing a warning banner when a tracked GitHub repository's identity (`id`) changes underneath an existing local clone.

### Proof of Concept
1. User clones `https://github.com/some-org/some-repo` in `GitHub Desktop`; the app stores `gitHubRepository.cloneURL` and the local `origin` remote both pointing to `some-org/some-repo`.
2. `some-org` is later deleted/renamed (a common, legitimate GitHub event), freeing the `some-org/some-repo` namespace.
3. Attacker re-registers `some-org` (or creates a repo at the identical freed slug) and sets `clone_url` to an attacker-controlled HTTPS repository at that exact `owner/name`.
4. On the user's next background refresh/fetch/pull (`repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`), `matchGitHubRepository` still parses the same `owner`/`name` out of the local `origin` URL, `api.fetchRepository(owner, name)` now resolves to the attacker's repository, `protocolsMatch` is true (attacker uses https), `remoteUrlUnchanged` is true (nothing local changed), `!urlsMatch` is true (new clone_url differs at the DNS/path level from the exact-format the API happened to previously report, e.g. case or redirect differences) — the condition in `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:42-44`) fires and `origin` is silently rewritten to the attacker's URL.
5. The user's next `git push`/`git pull` in Desktop silently interacts with the attacker's repository. [2](#0-1) [3](#0-2) [1](#0-0)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
