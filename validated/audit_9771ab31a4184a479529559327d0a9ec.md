### Title
Attacker-controlled `n` field in `ThresholdKeys::read` triggers large up-front heap allocations from a handful of input bytes (unbounded memory-size check bypass) - (File: crypto/dkg/src/lib.rs)

### Summary
The DRF advisory's bug class is a high-level API that consumes attacker-controlled input without enforcing the deployment's configured size limit, letting a small request cause disproportionate resource consumption. The analog in Serai is `ThresholdKeys::<C>::read`, an explicitly-listed untrusted-bytes entry point. It reads a 2-byte `n` field and immediately performs `Vec::with_capacity(usize::from(n))` plus loops that populate a `HashMap` of `n` verification shares — all before any consistency check on `n` occurs. A few dozen bytes of input therefore compel allocation of up to ~64 Ki scalar slots (~2–4 MiB plus HashMap overhead) per call, with no bound checked against the actual input length.

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs`), the deserializer reads `t`, `n`, and `i` as raw `u16`s, then reads an interpolation selector. For `Interpolation::Constant` it executes:

```rust
let mut res = Vec::with_capacity(usize::from(n));
for _ in 0 .. n {
  res.push(C::read_F(reader)?);
}
``` [1](#0-0) 

`with_capacity` commits the full allocation up front — `n` up to 65535 means a multi-megabyte allocation from an input that may be only ~20 bytes (curve ID + `t`,`n`,`i` + selector). Even for `Interpolation::Lagrange` (which skips that alloc), the subsequent loop inserts `n` entries into `verification_shares`: [2](#0-1) 

Only after all reads complete does `ThresholdParams::new` validate `t`/`n`/`i` consistency — there is no check relating declared `n` to remaining input length, mirroring how DRF handed the raw stream to parsers before size validation. Similarly, `SchnorrAggregate::read` reads a `u32` element count and iterates `C::read_G` up to ~4 billion times with no bound beyond EOF: [3](#0-2) 

That variant has no pre-allocation but allows a caller to drive near-unbounded parsing work. Contrast with `call.read` in `networks/ethereum/src/machine.rs` (out of scope but demonstrating the intended pattern), which explicitly chunks reads to avoid a "claim a 4 GB data is present for only 4 bytes" DoS: [4](#0-3) 

### Impact Explanation
An unprivileged party who can feed serialized bytes to `ThresholdKeys::read` (the recovery/backup import path, or any RPC that accepts serialized key material) causes repeated multi-megabyte allocations with tiny requests — a CPU/memory amplification factor of roughly three orders of magnitude per call. Repeated calls can exhaust process memory or tank allocator performance. `SchnorrAggregate::read` similarly lets a tiny 4-byte length prefix drive up to ~4 billion point-deserialization attempts (each fixed-size read fails fast on EOF, but a fully padded input enables unbounded parsing work with no size gate). This is an availability/resource-exhaustion issue (CWE-400/CWE-770), analogous in class to the DRF report — no key recovery or forgery, so Medium.

### Likelihood Explanation
Reachability requires an integration that calls `ThresholdKeys::read` on bytes an unprivileged party controls. That path exists for key recovery/import; whether a deployment exposes it to untrusted input is configuration-dependent. Within a hostile-input model the trigger is trivial: ~20 bytes with `n = 0xFFFF` and interpolation byte `0`. Likelihood is moderate — the allocation is real but each call's amplification is bounded at ~2–4 MiB, requiring repeated invocations for meaningful exhaustion.

### Recommendation
Validate declared counts against remaining input before allocating. In `crypto/dkg/src/lib.rs` `ThresholdKeys::read`: (a) check `n <= t`-consistent bounds and protocol-max participant counts before `Vec::with_capacity`, or use `Vec::new` and `push` so allocation tracks actually-present data; (b) cap `n` to a protocol maximum (e.g., `MAX_KEY_SHARES_PER_SET`-style bound as `coordinator/src/tributary/transaction.rs` does for slash reports). In `crypto/schnorr/src/aggregate.rs` `SchnorrAggregate::read`, enforce a maximum aggregate count before iterating. The chunked-read pattern in `networks/ethereum/src/machine.rs` is the established mitigation in this codebase.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use frost::curve::Ristretto;
use dkg::ThresholdKeys;

// Minimal input: curve ID len+ID, t=1, n=0xFFFF, i=1, interpolation=0 (Constant)
let mut buf = vec![];
buf.extend((Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(1u16.to_le_bytes());        // t
buf.extend(u16::MAX.to_le_bytes());    // n = 65535
buf.extend(1u16.to_le_bytes());        // i
buf.push(0u8);                         // Interpolation::Constant
// No scalar bytes follow at all.
let res: io::Result<ThresholdKeys<Ristretto>> =
    ThresholdKeys::read(&mut buf.as_slice());
// With ~15 bytes of input, Vec::with_capacity(65535) has already
// committed ~2+ MiB before the first read_F fails on EOF.
assert!(res.is_err());
```
Invoked in a loop (e.g., repeated recovery/import requests), each iteration pins megabytes briefly; under concurrency this yields memory-pressure DoS from negligible bandwidth.
