### Title
Unauthorized forced address association and fund migration via replayed off-chain signature - (File: `app/ante/evm_checktx.go`, `x/evm/types/ethtx/associate_tx.go`, `precompiles/addr/addr.go`)

### Summary
The Sei<->EVM `AssociateTx` (and the equivalent `addr` precompile `associate` method) recover an EVM/Sei address pair from an arbitrary, attacker-supplied `(V,R,S, CustomMessage)` tuple and then force-link that recovered EVM address to the recovered Sei address, migrating any funds sitting at the "cast" address. No domain separation (chain ID, contract/purpose tag, nonce) is enforced on the signed payload, so any previously produced ECDSA signature of a victim over any message can be replayed to trigger association, even though the sender of the wrapping transaction can be a completely unrelated third party.

### Finding Description
`HandleAssociateTx` recovers the EVM/Sei address pair purely from the raw signature values and an unrestricted `CustomMessage` string: [1](#0-0) 

The hash that is actually verified is just `keccak256(CustomMessage)` — there is no binding to Sei's chain ID, to a "Sei association" domain tag, or to any nonce: [2](#0-1) 

The recovery helper (`helpers.GetAddresses`/`RecoverPubkey`) simply ECDSA-recovers the public key from `(V,R,S)` over whatever hash it is given, with no context check: [3](#0-2) 

The project's own code explicitly documents the danger of exactly this pattern for the *related* EIP-7702 SetCode-authorization path, and had to add chain-ID / nonce / authority binding checks specifically because "a publicly-visible authorization a user signed for another chain... could be replayed... to force-associate them — migrating their direct-cast balance and orphaning staking/distribution state": [4](#0-3) 

That same class of protection (chain binding, purpose binding) is missing from `AssociateTx`/precompile `associate`. The test suite even demonstrates the accepted format is a bare EIP-191 `personal_sign`-style message (`"\x19Ethereum Signed Message:\n" + len + data`) with no Sei-specific content requirement: [5](#0-4) 

Critically, the wrapping message that carries the `(V,R,S,CustomMessage)` payload, `MsgAssociate`, is signed/submitted by an entirely different account (`msg.Sender`) than the account whose signature is embedded inside it — the "signer" of the association proof and the "signer/fee-payer" of the outer transaction are unrelated: [6](#0-5) 

Once the address pair is recovered, `AssociateAddresses`/`MigrateBalance` unconditionally move any `usei`/wei balance and coins sitting at the "cast" address (`sdk.AccAddress(evmAddr[:])`) to the newly bound Sei bech32 address, and delete the cast account: [7](#0-6) 

The only gate is a minimal balance check (as low as 1 usei or 1 wei at either address): [8](#0-7) 

Because signature-over-arbitrary-message reuse is endemic in the wider EVM ecosystem (personal-sign "Sign-In with X" flows, off-chain voting/attestation systems, wallet-connect auth, etc. all produce publicly retrievable `(message, signature)` pairs bound to a user's EVM key), an attacker who has ever observed such a pair for a victim can submit it as a Sei `MsgAssociate`/`AssociateTx` (or call the `addr` precompile's `associate` method from any account), forcing an association the victim never intended for Sei and triggering an immediate, irreversible transfer of any balance already sitting at their EVM-derived Sei address into the newly bound account. This mirrors the underlying flaw of GHSA-h77f-xxx7-4858/CVE-2021-39177: a cryptographic credential/token is accepted and acted upon as proof of identity/consent for a specific action without being scoped to that action's context, enabling one party to act (here, force account linkage + fund transfer) on behalf of another without their authorization for that specific chain/action.

### Impact Explanation
This can cause unauthorized transfer of funds: any usei/wei balance held at the victim's EVM-cast Sei address is moved to the forcibly-associated address as a direct side effect of `MigrateBalance`, without the victim submitting or approving a Sei transaction. It also permanently and irreversibly writes an EVM<->Sei address mapping the victim did not consent to for Sei specifically (association cannot be undone/rebound, per the "account already has association set" check), which can corrupt downstream expectations for that account (e.g., wallets, staking/distribution assumptions), matching the "orphaning staking/distribution state" risk the codebase's own comments call out for the sibling SetCode-authorization vulnerability class it already patched.

### Likelihood Explanation
Exploitability requires the attacker to possess a valid `(message, V, R, S)` signature produced by the victim's private key. Because the accepted digest is unconstrained (any UTF-8 string, verified with the standard `personal_sign`-style flow shown in the test fixtures), and because off-chain signing to "prove wallet ownership" or vote/attest is extremely common across web3 (and often results in public, retrievable signatures), such material is realistically obtainable for many active EVM users without any cooperation from Sei itself. The submitting account can be any unprivileged third party — `MsgAssociate.Sender` need not match, and need not have any relationship to, the account whose credential is embedded.

### Recommendation
Bind the association proof to a Sei-specific, chain-scoped, purpose-scoped domain the way `AuthorityToPreAssociate`/`RecoverAddressesFromAuthorization` now do for SetCode authorizations: require the signed message to include the Sei chain ID (and ideally the target Sei address or a monotonic nonce) so that signatures produced for other applications/chains cannot be replayed as a Sei association. At minimum, prefix/require the `CustomMessage` to embed the chain ID and a fixed "Sei address association" domain tag, and validate that prefix on-chain in `HandleAssociateTx`/`PreprocessUnpacked` and in every `addr` precompile `associate`/legacy `associate` implementation before recovering and acting on the address pair.

### Proof of Concept
1. Obtain any publicly available `(message, v, r, s)` ECDSA signature produced by a victim's EVM private key for an unrelated purpose (e.g., a "Sign-In with Ethereum" login message, a Snapshot governance vote, or any `personal_sign` attestation whose plaintext and signature are disclosed).
2. Craft `ethtx.AssociateTx{V, R, S, CustomMessage: <victim's exact signed plaintext>}` (as shown in `x/evm/ante/preprocess_test.go:233-250`) or call the `addr` precompile's `associate(v, r, s, customMessage)` method with the same values from any unprivileged account.
3. Submit it as `MsgAssociate`/wrap it as an EVM transaction from an attacker-controlled fee payer account (the signer of the outer message need not be the victim, per `x/evm/types/message_associate.go:14-32`).
4. `HandleAssociateTx` (`app/ante/evm_checktx.go:182-204`) recovers the victim's true `evmAddr`/`seiAddr` pair from the reused signature, passes the minimal balance check if the victim's EVM-cast address holds any usei/wei, and calls `AssociateAddress` → `AssociateAddresses`/`MigrateBalance` (`utils/helpers/associate.go:34-83`), forcibly associating the addresses and transferring the victim's cast-address balance to the new Sei account — all without the victim ever interacting with Sei.

func GetAddressesFromPubkeyBytes(pubkey []byte) (common.Address, sdk.AccAddress, cryptotypes.PubKey, error) {
	evmAddr, err := PubkeyToEVMAddress(pubkey)
	if err != nil {
		return common.Address{}, sdk.AccAddress{}, nil, err
	}
	seiPubkey := PubkeyBytesToSeiPubKey(pubkey)
	seiAddr := sdk.AccAddress(seiPubkey.Address())
	return evmAddr, seiAddr, &seiPubkey, nil
}

// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
