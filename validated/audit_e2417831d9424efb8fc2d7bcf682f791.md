## Title
Manual conflict resolution choices (`manualResolutions`) are not reset when a new merge/rebase begins, causing stale "ours"/"theirs" decisions to be silently re-applied to different, attacker-influenced content - (File: `app/src/lib/stores/updates/changes-state.ts`)

## Summary
This is the closest verifiable analog to the Sherlock bug class: a per-entity status/counter (`reviewsByStatus`) that should be reset whenever the entity is "re-registered" but instead persists and is silently reused to make an authorization/state decision on the new entity. In Desktop, the analogous state is the `manualResolutions: Map<string, ManualConflictResolution>` that records a user's per-file "keep ours" / "keep theirs" conflict-resolution choice. `updateConflictState` in [1](#0-0)  carries this map forward across state transitions as long as the *category* of conflict (merge-like or rebase-like) stays the same — it does not check whether the underlying merge target/tip/branch is actually the same conflict session.

## Finding Description
`updateConflictState` computes the next `ConflictState` and decides whether to keep `manualResolutions`: [1](#0-0) 

The carry-over condition only checks `isMergeConflictState` / `isRebaseConflictState` (i.e. "is this still a merge" / "is this still a rebase"), not whether `currentBranch`/`currentTip`/`targetBranch` match the previous conflict. This is confirmed by the existing unit test that documents the exact scenario: manual resolutions survive even when `currentBranch` changes between the previous and new conflict state (which happens when the prior merge is aborted and a new one is started against a different branch): [2](#0-1) 

and the "same-session" preservation test right above it, which shows the map is passed through unchanged into the new `ConflictState`: [3](#0-2) 

The per-file resolution (`ours`/`theirs`) is later used to decide which side's content is applied for a given path, and to drive the diff shown to the user in the Copilot/manual conflict UI without necessarily forcing a fresh choice: [4](#0-3) [5](#0-4) 

This mirrors the original bug precisely: `reviewsByStatus[recipientId][recipientStatus]` was carried across a recipient's re-registration and could push the *new* application straight to `Accepted` with fewer votes than `reviewThreshold`. Here, a resolution choice recorded for `path` in one merge/rebase (e.g. "always take theirs for `config.json`") is carried into a brand-new merge/rebase against a different, attacker-influenced branch/remote for the same path, without the user re-confirming that choice for the new content.

## Impact Explanation
If a user has previously resolved a conflict on a given file with "keep theirs" and later starts a new merge (e.g. after fetching updates from a remote, or merging a different/attacker-supplied branch) that has a conflict at the same path, the stale resolution is reused. Because `theirs` in the new merge now points at attacker-controlled content (the newly fetched branch tip), the file content that ends up staged/committed for that path is chosen without the user reviewing or approving the specific new diff — this is a form of "silent corruption of what the user commits or pushes," one of the explicitly valid impact classes, and the attacker-controlled input is exactly a fetched/merged branch tip from a git remote.

## Likelihood Explanation
Requires: (1) the user has previously resolved a merge/rebase conflict for a specific path using the manual "ours/theirs" mechanism, (2) a later merge/rebase conflicts on the same path, and (3) the "theirs" side of that later conflict is attacker-influenced (e.g., a malicious branch on a shared remote, or the result of a `git pull`/fetch from a compromised or attacker-served remote). This is plausible in team workflows with repeated merges/rebases against long-lived feature branches or forks, but requires a fairly specific alignment of file path and conflict recurrence, so likelihood is moderate rather than trivial.

## Recommendation
Scope `manualResolutions` to the specific conflict session rather than just its category. `updateConflictState` should clear `manualResolutions` whenever the identifying attributes of the conflict change (e.g. `currentTip`/`targetBranch` for rebase, `currentBranch`/`currentTip` for merge, `targetBranchName` for cherry-pick), not just when the conflict `kind` changes between merge/rebase/cherry-pick.

## Proof of Concept
1. Start a merge that conflicts on `config.json`; resolve it manually by choosing "theirs" (`ManualConflictResolution.theirs`) via `dispatcher.updateManualConflictResolution`.
2. Abort that merge (branch/tip changes, but conflict `kind` remains `'merge'`).
3. Fetch from a remote controlled or influenced by an attacker and start a new merge that also conflicts on `config.json`, where "theirs" now refers to the attacker's branch content.
4. Because `updateConflictState` only checks `isMergeConflictState(prevConflictState) && isMergeConflictState(newConflictState)` (as demonstrated in the existing test at [2](#0-1) ), the stale `theirs` resolution for `config.json` is carried into the new conflict state without any additional user confirmation, causing the attacker's version of `config.json` to be silently applied when the merge is continued.

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

export function getResolutionChoiceForFile(
  path: string,
  manualResolutions: Map<string, ManualConflictResolution>
): CopilotFileResolutionChoice {
  const manual = manualResolutions.get(path)
  if (manual === ManualConflictResolution.ours) {
    return 'ours'
  }
  if (manual === ManualConflictResolution.theirs) {
    return 'theirs'
  }
  return 'copilot'
}

  private async loadDiffForFile(file: CommittedFileChange) {
    const requestId = ++this.diffRequestId
    const choice = getResolutionChoiceForFile(
      file.path,
      this.props.manualResolutions
    )

    if (choice === 'ours' || choice === 'theirs') {
      this.setState({
        diff: null,
        fileContents: null,
        noResolution: false,
        diffError: false,
      })
      try {
        const result = await getResolutionDiff(
          this.props.repository,
          file.path,
          { stage: choice },
          this.state.hideWhitespaceInDiff
        )

        if (this.mounted && requestId === this.diffRequestId) {
          this.setState({
            diff: result.diff,
            fileContents: this.buildFileContents(file, result),
          })
        }
      } catch (e) {
        log.error('Failed to compute resolution diff', e)
        if (this.mounted && requestId === this.diffRequestId) {
          this.setState({ diff: null, fileContents: null, diffError: true })
        }
      }
      return
    }
