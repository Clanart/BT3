### Title
`donateRewards` credits the requested amount instead of the actual balance received, allowing fee-on-transfer/rebasing reward tokens to inflate the reward index and cause protocol insolvency - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`BaseRewardPoolV2.donateRewards()` is a permissionless function that forwards any amount to `_provisionReward()`, which credits `_amountReward` (the value requested by the caller) to `historicalRewards` and to the `rewardPerTokenStored` increment, rather than measuring the actual balance delta received after `safeTransferFrom`. If the registered reward token is fee-on-transfer or rebasing and delivers less than `_amountReward` to the pool, the index and `historicalRewards` become permanently inflated relative to the pool's real token balance.

### Finding Description
`_provisionReward()` performs: [1](#0-0) 

It calls `safeTransferFrom(msg.sender, address(this), _amountReward)` and then unconditionally adds `_amountReward` to `rewardInfo.historicalRewards` and uses it to compute the `rewardPerTokenStored` increment (`_amountReward * 10**decimals / totalStaked()`), without ever reading `IERC20(_rewardToken).balanceOf(address(this))` before/after the transfer to determine the actual amount received.

`donateRewards()` is callable by anyone as long as the token is already registered (`isRewardToken[_rewardToken]` is true): [2](#0-1) 

Given a registered reward token with fee-on-transfer or rebasing semantics, any unprivileged EOA can call `donateRewards(_amountReward, _rewardToken)` with `_amountReward` approved/held, and the pool will credit the full nominal `_amountReward` to the index even though it only received `balanceBefore - balanceAfter < _amountReward` tokens. This breaks the invariant that the sum of all stakers' claimable amounts (driven by `rewardPerTokenStored` and `historicalRewards`) must be backed by the pool's actual token balance. Once the index is inflated, later claimants (via `getReward`/`getRewards` in the same file) will be entitled to more tokens than the pool holds, and the last claimants will have their `safeTransfer` calls fail or partially fail, permanently freezing/loss for at least one staker — i.e., protocol insolvency for that reward token.

Neither `onlyManager` nor `onlyMasterMagpie` guards this path — `donateRewards` intentionally has no access control besides the token being registered, and no code path verifies balance-delta accounting.

### Impact Explanation
This causes protocol insolvency scoped to whichever reward token is fee-on-transfer/rebasing and already registered in the pool: the sum of promised rewards (`rewardPerTokenStored * totalStaked / 10**decimals` across all users) exceeds `IERC20(_rewardToken).balanceOf(address(this))`. This matches "Critical – Protocol insolvency" since honest, unclaimed yield of other stakers becomes uncollectible/frozen once the shortfall is realized, and it can be repeated with `_amountReward` as low as one wei on any transfer that incurs even minimal fee/rebase loss.

### Likelihood Explanation
The precondition is a registered reward token with fee-on-transfer or negative-rebase behavior on `transferFrom`. This is not attacker-controlled (the attacker does not choose which tokens are registered — that requires `queueNewRewards`, which is `onlyManager`), but the flaw exists in `_provisionReward()` for any registered token that exhibits such behavior, and the attack itself (calling `donateRewards`) requires only an unprivileged EOA holding some of that token, no capital beyond dust amounts, and is trivially repeatable each time the pool holds such a token.

### Recommendation
Measure the actual balance delta in `_provisionReward()`: read `IERC20(_rewardToken).balanceOf(address(this))` before and after `safeTransferFrom`, and use `balanceAfter - balanceBefore` (not the caller-supplied `_amountReward`) for both `historicalRewards` accumulation and the `rewardPerTokenStored` increment computation.

### Proof of Concept
1. Deploy `BaseRewardPoolV2` with a mock fee-on-transfer ERC20 (e.g., burns 10% on `transferFrom`) as the registered `_rewardToken`, and a mock `MasterMagpie`/staking token with `totalStaked() > 0`.
2. Have a staker account with nonzero `balanceOf` stake so `totalStaked() != 0`.
3. From an unprivileged EOA, approve and call `donateRewards(1000, feeToken)`.
4. Assert `IERC20(feeToken).balanceOf(pool)` increased by only 900 (fee-on-transfer), but `rewards[feeToken].historicalRewards` increased by the full 1000, and `rewardPerTokenStored` was computed using 1000 instead of 900.
5. Have the staker call `getReward`, and demonstrate that the sum of `earned()` across all stakers exceeds `IERC20(feeToken).balanceOf(pool)`, i.e., not all stakers can be paid in full — reproducing the insolvency.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
