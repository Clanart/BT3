## Title
Incomplete credential-value sanitization in `formatCredential` (missing bare `\r` check) permits credential-protocol line injection into external credential helper stdin — (File: `app/src/lib/git/credential.ts`)

### Summary
`formatCredential` is meant to guarantee that a credential `Map` can be safely serialized into the newline-delimited `key=value` wire format used by git's credential-helper protocol. It only rejects values containing `\n` or `\0`, but not a bare `\r`. Several external credential-manager implementations (e.g. Git Credential Manager, which is a .NET application) read stdin line-by-line using APIs that treat `\r`, `\n`, and `\r\n` all as line terminators. This mismatch between what Desktop considers a "line break" (`\n` only) and what the receiving helper considers a "line break" (`\r` or `\n`) allows a single credential field to be split into two protocol lines from the helper's point of view.

### Finding Description
`formatCredential` builds the stdin payload sent to `git credential <cmd>` (configured with `credential.helper=manager`, i.e. an external, real credential manager binary) purely by joining `key=value\n` lines: [1](#0-0) 

The forbidden-character guard only checks for `\n` and `\0`: [2](#0-1) 

Notably, the app's own `parseCredential` treats `\r\n` as an equivalent line terminator to `\n` (via the `/\r?\n/` split), showing the intended threat model already accounts for `\r`-involved line endings, yet the sanitizer in `formatCredential` fails to reject a **bare** `\r`: [3](#0-2) 

The credential `Map` fed into `formatCredential` (via `fillCredential`/`approveCredential`/`rejectCredential`) originates from `parseCredential(command.stdin)` — i.e., from the payload real `git` forwards to Desktop's trampoline credential helper, which includes `wwwauth[]` entries mirroring the WWW-Authenticate header(s) returned by the remote/API server: [4](#0-3) [5](#0-4) [6](#0-5) 

If Desktop is configured to use the external credential helper (`useExternalCredentialHelper()`), that credential map (still containing the attacker-influenced `wwwauth[...]` value) is passed to `fillCredential`/`approveCredential`, which call `exec()` → `formatCredential(cred)` → written as stdin to the real external helper process: [7](#0-6) 

Because `formatCredential` only blocks `\n`/`\0`, a value containing a lone `\r` (e.g. `evil\rurl=https://attacker.example`) passes the check unmodified and is serialized as `key=evil\rurl=https://attacker.example\n`. External helpers that split stdin on any of `\r`, `\n`, `\r\n` (a common behavior for line-oriented I/O in .NET/managed runtimes, which Git Credential Manager is built on) would interpret the embedded `\r` as ending the current line and starting a new `url=...` (or `host=`, `path=`, etc.) line — letting an attacker-controlled field smuggle an additional protocol field into the request sent to the helper.

### Impact Explanation
If an injected line can override fields such as `url`/`host`/`path` in the request sent to the external credential manager, it can influence which credential entry is looked up (`fill`) or under which host/path a token gets stored/overwritten (`approve`), corrupting the association between the stored token and the true target host. This is a credential/token-scoping integrity issue rather than immediate code execution, but it can lead to leaking a token intended for one host being returned for another, or a legitimate token being persisted under an attacker-chosen `url`.

### Likelihood Explanation
Exploitability depends on: (1) the user having enabled the external credential helper path (`useExternalCredentialHelper()`), and (2) the concrete line-splitting behavior of the specific external helper (this repo does not include GCM's source, so the exact stdin-parsing semantics could not be verified from within this codebase — the reasoning about `\r`-as-terminator is based on typical managed-runtime line reading, not on code reviewed here). Also, delivering a raw, unpaired `\r` byte through an HTTP `WWW-Authenticate` header value requires a server/proxy under attacker control that emits non-strictly-conformant header bytes, since compliant HTTP header parsing normally terminates lines at the exact `\r\n` sequence — an unpaired `\r` inside the value is unusual but not universally rejected by HTTP clients. Given these two unverified/circumstantial preconditions, likelihood is moderate rather than confirmed.

### Recommendation
Extend the forbidden-character check in `formatCredential` to reject or escape any `\r` in addition to `\n` and `\0`:
```ts
if (v.includes('\n') || v.includes('\r') || v.includes('\0')) {
  throw new Error(`forbidden characters in credential value: ${k}`)
}
```
This aligns the serializer's notion of "line break" with `parseCredential`'s `/\r?\n/` splitting logic and closes the gap regardless of the specific external helper's line-parsing behavior.

### Proof of Concept
```ts
import { formatCredential } from 'app/src/lib/git/credential'

const cred = new Map([
  ['url', 'https://good.example'],
  ['wwwauth[0]', 'evil\rurl=https://attacker.example'],
])

const out = formatCredential(cred) // does NOT throw
console.log(out)
// -> "url=https://good.example\nwwwauth[]=evil\rurl=https://attacker.example\n"
```
No exception is thrown, and the resulting string contains an embedded `\r` that a line-oriented external reader (splitting on `\r`/`\n`/`\r\n`) would interpret as two separate protocol lines, the second being an attacker-controlled `url=...` field. [8](#0-7)

```typescript
export const formatCredential = (credential: Map<string, string>) => {
  const lines = []
  for (const [k, v] of credential) {
    if (v.includes('\n') || v.includes('\0')) {
      throw new Error(`forbidden characters in credential value: ${k}`)
    }
    lines.push(`${k.replace(/\[\d+\]$/, '[]')}=${v}\n`)
  }

  return lines.join('')
}
```
