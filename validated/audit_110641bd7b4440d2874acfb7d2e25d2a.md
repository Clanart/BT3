The coordinator crate is out of scope; the analog must live in `crypto/*` or `networks/bitcoin/src`. Let me check the Bitcoin scanner/key-offset code, where "one credential authenticates all contexts" maps to outputs being accepted/credited without binding to the right key/context.### Title
`ReceivedOutput::read` accepts an unverified offset/output pairing, letting forged scan results claim outputs that are not spendable under the asserted offset - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The NiceGUI bug is a scoping failure: authentication established for one session was implicitly trusted for every session, because the server stored a single shared authenticated state instead of binding it to the client it was proven for. The analog in Serai's in-scope code is `Scanner`/`ReceivedOutput` in `networks/bitcoin/src/wallet/mod.rs`: ownership is *proven once* by `Scanner` (which internally derives `script = p2tr(key + offset·G)`), but the deserialization path `ReceivedOutput::read` reconstructs the claimed pairing `(offset, output)` directly from untrusted bytes with no re-verification that the asserted offset actually yields the output's `script_pubkey`. A claim authenticated in one context (a genuinely scanned output) is accepted for an arbitrary context (any `TxOut`/`OutPoint` with any offset) — the same "one proof, global acceptance" shape as GHSA-v6jv-p6r8-j78w.

### Finding Description
`Scanner::scan_transaction` correctly establishes the binding between a script and its offset: it only emits a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` returns the offset that was registered for that exact script via `register_offset` (`mod.rs:199-214`, `180-196`). That binding is the "authentication" step.

`ReceivedOutput::read` (`mod.rs:122-134`) deserializes `offset` via `Secp256k1::read_F`, then consensus-decodes a `TxOut` and an `OutPoint`, and returns the triple as fact. There is no `key` stored on `ReceivedOutput` and no check that `p2tr_script_buf(scanner_key + offset·G) == output.script_pubkey` — the function signature doesn't even take the scanner key. Any downstream consumer that receives a serialized `ReceivedOutput` over an untrusted channel therefore trusts an `offset` claim that was never proven for those bytes: a relayed/forged blob can pair a real scanner-owned output with a wrong offset (making the credited funds unspendable under the reported key) or pair an arbitrary `OutPoint`/`TxOut` with a valid offset (crediting an output that was never received). This matches the external report's pattern only as a bug class: a validity predicate established in one place is reused as blanket authentication elsewhere without re-binding it to the object it was proven for.

### Impact Explanation
`ReceivedOutput` is the wallet's representation of spendable funds (`offset` is documented as "the scalar offset to obtain the key usable to spend this output", `mod.rs:91`). A forged or tampered serialization causes funds to be reported received that are not spendable with the stated offset — one of the accepted impact classes. An attacker able to inject bytes on the path that feeds `ReceivedOutput::read` (the prompt explicitly lists `ReceivedOutput::read` as reachable with untrusted bytes) can cause a consumer to build spends against `offset`-derived keys that do not control the output, or to credit phantom outputs, corrupting balance/UTXO accounting and potentially locking funds in an invalid transaction plan.

### Likelihood Explanation
Reachability requires an attacker-controlled serialized `ReceivedOutput` to reach `read`, which is plausible wherever scan results are relayed between components rather than produced in-process by `Scanner`. It does not require key knowledge, collusion, or validator misbehavior. Impact is bounded to accounting integrity/availability of funds rather than direct theft, since the scripts themselves still require valid threshold signatures to spend — hence Medium, not High.

### Recommendation
Bind the claim to the object at trust boundaries: either store the scanner's public key on `ReceivedOutput` and have `read`/`scan` re-derive `p2tr_script_buf(key + offset·G)` and compare against `output.script_pubkey` (returning an error on mismatch), or make `ReceivedOutput` construction private to `Scanner` and authenticate serialized scan results at the transport layer (MAC/signature by the scanning party). Document that serialized `ReceivedOutput`s are only as trustworthy as the channel that carried them if re-verification is deemed out of scope.

### Proof of Concept
1. Instantiate `Scanner::new(key)` and `register_offset(o)`, obtaining a legitimately scanned `ReceivedOutput { offset: o, output: paying to p2tr(key+o·G), outpoint }`.
2. Construct a forged buffer: serialize `offset = o` but pair it with a `TxOut` paying to an unrelated script (e.g., `p2tr(key + o'·G)` for some `o' ≠ o`) and an arbitrary `OutPoint`.
3. `ReceivedOutput::read` accepts it and returns `offset() == o`; a consumer deriving the spend key as `key + o·G` obtains a key that does not control the output — the funds are reported received yet are unspendable with the reported offset.

*Uncertainty note: I could not inspect the consumers of `ReceivedOutput::read` within the allowed iterations, so the exact blast radius (which component trusts serialized outputs) is unverified; the claim stands on the fact that `read` performs no offset↔script re-verification and is listed as reachable with untrusted bytes.*
