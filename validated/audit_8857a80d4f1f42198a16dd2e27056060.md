### Title
Binary-file diff viewer's "Open file in external program" bypasses the `.exe/.cmd/.bat/.sh` execution guard - (File: app/src/ui/diff/binary-file.tsx)

### Summary
The bug pattern in the report is a security check (`checkPoolCap`) that is enforced on one entry point (`deposit`) but omitted on a functionally equivalent entry point (`swapIntoFromRouter`) that mutates the same guarded state. GitHub Desktop has the same class of bug: the `isSafeFileExtension` guard that blocks Desktop from launching `.exe`, `.cmd`, `.bat`, `.sh` files via "Open with Default Program" is enforced only in the changed-files/history context menus, but the separate binary-diff "Open file in external program" action reaches the exact same `openFile`/`shell.openExternal` sink with no extension check at all.

### Finding Description
`isSafeFileExtension` is defined once and is meant to be the guard against launching dangerous executables from inside Desktop: [1](#0-0) 

It is only consulted when building the "Open with Default Program" menu item in the changes list, commit history file list, and PR files-changed list, where it sets the menu item's `enabled` flag: [2](#0-1) [3](#0-2) 

The actual opening call, `openFile()`, performs no extension validation whatsoever — it unconditionally hands the path to the OS via `shell.openExternal`: [4](#0-3) 

Crucially, there is a second, independent path to this exact same sink that never passes through `isSafeFileExtension` at all: when Desktop renders a file as a binary diff (any file git classifies as binary, including a `.exe`, `.cmd`, `.bat`, or `.sh` that has non-text content), it shows a `BinaryFile` component with an "Open file in external program" link that calls `onOpenBinaryFile(fullPath)` directly, with no extension check anywhere in the component: [5](#0-4) 

This prop is threaded straight through `Diff`/`SeamlessDiffSwitcher` without any additional gating: [6](#0-5) [7](#0-6) 

This is structurally identical to the report: the invariant "don't let the app open dangerous file extensions" is a modifier-style check attached to one call site (`getDefaultContextMenu`/`getRebaseContextMenu`'s "Open with Default Program" item) but the underlying sink (`openFile`) is reachable through a second, attacker-influenced path (the binary-diff viewer) that never applies it — exactly as `checkPoolCap` guards `deposit` but not `swapIntoFromRouter`, even though both funnel into the same pool-asset balance.

### Impact Explanation
An attacker who controls a cloned/fetched repository can commit a file with a `.exe`, `.cmd`, `.bat`, or `.sh` extension whose contents are binary (or simply not detected as text), so Desktop renders it via the `BinaryFile` panel rather than the normal changes list rows. A user who clicks "Open file in external program" on that diff has the file launched via `shell.openExternal('file://...')` with the OS default handler for that extension — on Windows this typically means direct execution for `.exe`/`.cmd`/`.bat` — with none of the protection that the same action would receive if reached via the context menu on a non-binary file. This is a guard/enforcement inconsistency that leads to code execution originating from attacker-controlled repository content, matching the valid-impact criteria (attacker controls a cloned/fetched repo, result is code execution).

### Likelihood Explanation
Likelihood is Medium: it requires the user to open the binary diff for the specific attacker-crafted file and click the "Open file in external program" link — a single, plausible interaction that Desktop's own UI explicitly offers for binary files (e.g., inspecting an unfamiliar executable/script committed by a collaborator or in a forked PR). No admin rights, local access, or unnatural steps are required beyond normal repository browsing.

### Recommendation
Apply `isSafeFileExtension` (or an equivalent check) inside `openFile()` in `app/src/ui/lib/open-file.ts` itself — or at minimum in `BinaryFile`'s open handler in `app/src/ui/diff/binary-file.tsx` — so that the extension restriction is enforced centrally at the sink rather than being replicated (and forgotten) at each individual call site/menu item.

### Proof of Concept
1. In a repository, create a file `payload.exe` containing binary/non-text bytes (e.g. a small PE stub) and commit it, or produce it as part of a fetched branch/PR from an untrusted remote.
2. Have the victim open that commit/PR diff in GitHub Desktop; because the content isn't text, Desktop renders the `BinaryFile` panel instead of a normal diff row (bypassing the changes-list/PR-files-changed context menu code path that would have disabled "Open with Default Program" for `.exe`).
3. Victim clicks "Open file in external program" in the binary panel.
4. `onOpenBinaryFile(fullPath)` → `openFile(fullPath, dispatcher)` → `shell.openExternal('file://' + fullPath)` executes the attacker-supplied binary without any extension check, unlike the equivalent action in the normal changes list which would have been disabled by `isSafeFileExtension`.

Note: I was unable to trace the exact `onOpenBinaryFile` handler implementation wired in `app/src/ui/repository.tsx` / `app/src/ui/changes/changes.tsx` due to the tool-call limit, so I could not directly confirm the final call reaches `shell.openExternal` verbatim in every consumer (vs. e.g. an editor-launch path with its own checks). The `open-file.ts` sink itself is confirmed to have no extension check, and `BinaryFile`/`Diff`/`SeamlessDiffSwitcher` are confirmed to pass the path through unchecked; a Devin session with full repo access should verify the concrete `onOpenBinaryFile` prop assignment in `repository.tsx`/`changes.tsx`/`stash-diff-viewer.tsx` before treating this as fully confirmed.

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
