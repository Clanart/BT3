Based on my investigation, I found a concrete analog: the automatic remote-URL rewriting logic in `updateRemoteUrl`, which silently repoints a user's `origin` remote based on unvalidated data from the GitHub API — directly matching the seed bug's pattern of a value being propagated into the wrong/unvalidated destination and permanently corrupting state that the user relies on (in this case, *where the user's future commits get pushed*), without the safety checks the surrounding code appears to assume.

### Title
Unvalidated GitHub API `clone_url` silently rewrites the user's git remote, redirecting future pushes - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
### Finding Description
`updateRemoteUrl` [1](#0-0)  automatically rewrites the local `origin` remote URL whenever it detects that the API's `clone_url` for a `GitHubRepository` no longer matches the local remote, as long as the *previously cached* `gitHubRepository.cloneURL` still matches the current remote and the protocol hasn't changed: [2](#0-1) 

The only validation performed is `urlMatchesRemote`/`protocolsMatch`, which compare the *old* cached clone URL against the *current* remote — there is no check that the *new* `updatedRemoteUrl` (`apiRepo.clone_url`, taken verbatim from the GitHub API response) points to the same host, owner, or even the same GitHub instance as before. `urlMatchesRemote` is only used to detect drift, not to validate the destination: [3](#0-2) .

Once the mismatch and staleness conditions are true, `gitStore.setRemoteURL(...)` is called unconditionally with the API-provided value, silently overwriting the actual git config's remote — the value that determines where `git push` sends the user's commits. This is the same bug class as the seed report: an unguarded assignment of an attacker-influenced value into a state variable that downstream logic implicitly trusts (`typeVotes`/`typeWeights` mixup → `origin` remote silently repointed by unvalidated API data), producing invisible, persistent corruption of the invariant "the repository's remote matches what the user configured/expects."

### Impact Explanation
The `IAPIRepository.clone_url` field is populated from the GitHub REST API response for a given repository. This is exactly the "attacker controls a GitHub API object" primitive the task calls out: a malicious or compromised repository owner (e.g., of a public repo the victim has cloned/forked), or a compromised/MITM'd GitHub Enterprise Server response, can set an arbitrary `clone_url` on a repo entry Desktop tracks. Once Desktop refreshes that repository's metadata, `updateRemoteUrl` will rewrite the victim's `origin` remote to that attacker-chosen URL — with no re-validation of the new destination. Subsequent user actions ("push", "sync") from `_push`/`performPush` in `app-store.ts` will then push the user's code to the attacker's server instead of the intended one, all without any visible warning, since the remote change happens silently as part of a routine repository refresh, not a user-initiated action. [4](#0-3)  shows the deliberate scrutiny given to keeping `remote.name`/`branch.remote` consistent for the *existing* remote, underscoring that the remote's *URL* being silently swappable by API data is inconsistent with how carefully push destinations are otherwise guarded elsewhere in the same file.

### Likelihood Explanation
Any user who has cloned or added a public GitHub repository they don't own is affected — no special git configuration is required, and the update happens automatically as part of normal repository refresh cycles (this function is invoked from `app-store.ts` during `withRefreshedGitHubRepository`-style flows), not gated behind a user prompt. The attacker's only requirement is control over the repository's metadata as observed via the GitHub API (achievable by any repo owner, or in Enterprise environments, by a MITM/compromised GHES instance), satisfying the "unprivileged" bar in the reported impact criteria.

### Recommendation
Before calling `gitStore.setRemoteURL`, validate that `updatedRemoteUrl` and the *original* remote share the same hostname (and ideally require user confirmation for any owner/name change, similar to how force-push and branch-protection changes are surfaced). At minimum, restrict automatic rewriting to same-hostname changes and surface a UI prompt when the target host differs, rather than silently trusting `apiRepo.clone_url` end-to-end.

### Proof of Concept
1. Victim adds/clones a public repository `https://github.com/attacker/legit-repo.git` in Desktop; Desktop stores `gitHubRepository.cloneURL` accordingly.
2. Attacker (owner of `attacker/legit-repo`) changes the repository in a way that causes the GitHub API's `clone_url` field for that repo id to report a different URL (e.g., via a transfer/rename sequence, or a compromised GHES instance simply returning a different `clone_url` in the API response).
3. Desktop's background refresh calls `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)`, and since `remoteUrlUnchanged` and `protocolsMatch` hold true while `urlsMatch` is false, `gitStore.setRemoteURL('origin', apiRepo.clone_url)` executes silently: [5](#0-4) .
4. Victim performs a normal "Push" from the Changes/History view; `git push` now sends the victim's commits to the attacker-controlled destination in `apiRepo.clone_url` with no warning shown.

**Uncertainty**: I could not fully trace, within the given tool budget, the exact call sites in `app-store.ts` that invoke `updateRemoteUrl` (only found via grep, not read in full) or confirm whether any additional UI confirmation step exists elsewhere in the app-store refresh flow that might mitigate this before `setRemoteURL` executes. I recommend a follow-up read of `app-store.ts`'s three references to `updateRemoteUrl` to confirm there is no gating confirmation dialog before this path is exploitable in practice.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
