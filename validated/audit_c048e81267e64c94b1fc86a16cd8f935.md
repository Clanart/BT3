### Title
Stale conflict snapshot is blindly re-applied to disk when accepting Copilot merge-conflict resolutions - (File: app/src/lib/stores/app-store.ts)

### Summary
The report's broken invariant is: a security-relevant computation is derived from a *raw, unvalidated snapshot of attacker-influenced state*, and that stale/derived value is later used to perform a destructive action (a token transfer that reverts) without re-checking that the snapshot still matches reality. The same invariant is broken in GitHub Desktop's Copilot merge-conflict-resolution flow: the file content used to build the AI resolution (`rawContent`) is captured once, sent through an async round-trip to the Copilot backend, and the resulting `resolvedContent` is later written straight to disk with only a coarse status-kind check — not a content-identity check against the *current* on-disk state, which is derived from git status output that reflects the state of a checked-out branch/merge that can be entirely attacker-authored (a malicious PR/branch being merged, exactly the "attacker controls a fetched/cloned repository" precondition).

### Finding Description
`buildConflictContext` reads each conflicted file's full content into `rawContent` and extracts `hunks` with a naive line-based parser: [1](#0-0) 

The comment on `IFileConflictContext.rawContent` states this snapshot is later used to "reassemble the resolved file by splicing per-hunk resolutions into the original content": [2](#0-1) 

The hunk parser itself only looks for the *first* line matching `^={7}$` / `^>{7}` to close a hunk, with no protection against a conflicting side containing content that incidentally matches these marker patterns (fully attacker-controlled, since "theirs"/"ours" content comes directly from the branch/commit being merged): [3](#0-2) 

When the user accepts the AI-proposed resolutions, `app-store.ts` resolves the path and writes `resolution.resolvedContent` to disk. The only re-validation performed before the write is a check that the file's *status kind* still shows unresolved conflicts — not that the on-disk bytes still match the `rawContent` snapshot that was used to compute `resolvedContent`: [4](#0-3) 

The comment at lines 7241-7246 explicitly acknowledges a TOCTOU class of bug ("If the user resolved this file externally ... git status will report it with no remaining conflict markers. Overwriting it with Copilot's stored content would silently clobber their work") and defends against exactly one instance of it (fully-externally-resolved files), but the guard is a coarse `isConflictedFileStatus`/`hasUnresolvedConflicts` check on cached `state.changesState.workingDirectory.files`, not a comparison of current file bytes against the `rawContent` that the resolution was computed from. Any other change to the file between context-gathering and write-back — partial user edits inside the markers, a background git operation, or content whose marker-like lines confused `extractConflictHunks` into computing wrong hunk boundaries in the first place — is not detected, and `writeFile` unconditionally overwrites the file with content derived from the stale/incorrectly-parsed snapshot.

### Impact Explanation
This maps to "silent corruption of what the user commits or pushes," an explicitly in-scope impact category. Because the "theirs" side of a merge/rebase/cherry-pick conflict is attacker-controlled content (a malicious branch or PR the victim merges), the attacker can shape file content to desynchronize the hunk boundaries the naive parser computes from the boundaries assumed at reassembly time, or simply rely on the async Copilot round-trip window to make the accepted resolution stale relative to the file the user is actually looking at. The end result is that Desktop writes content to the working tree that the user did not actually author or review, which then gets `git add`'d and can be committed/pushed without the corruption being visible.

### Likelihood Explanation
Medium. It requires the file to be part of a merge/rebase/cherry-pick with conflicts against attacker-authored content, and requires the Copilot conflict-resolution feature to be in use — a normal, expected workflow, not privileged access or local compromise. No credentials, admin rights, or unnatural user steps are needed; the user just merges a branch and accepts the AI-proposed resolution, which is the intended product flow.

### Recommendation
Before writing `resolution.resolvedContent` in `_acceptCopilotResolutions`, re-read the current on-disk file and verify its content still matches (or is a strict superset compatible with) the `rawContent`/hunk boundaries the resolution was computed from — not merely that its status kind is still "conflicted." Additionally, harden `extractConflictHunks` so that lines matching `=======`/`>>>>>>>` patterns that occur inside content the attacker controls cannot be conflated with actual git conflict markers (e.g., by validating marker counts/nesting against the git-reported conflict state rather than purely lexical scanning).

### Proof of Concept
A full end-to-end PoC would require driving the Copilot conflict dialog with a mocked backend and is not verifiable purely from static code, but the reachable path is:
1. Attacker's branch introduces a merge conflict where the "theirs" hunk content contains a line that is exactly 7 `=` characters (e.g., a code comment divider), which `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:208-214`) will treat as the conflict separator, truncating the real hunk early.
2. `buildConflictContext` still returns this mis-parsed hunk plus the full `rawContent`, and the resolution is generated against this desynchronized data.
3. `_acceptCopilotResolutions` (`app/src/lib/stores/app-store.ts:7233-7259`) checks only `isConflictedFileStatus`/`hasUnresolvedConflicts` on the cached status, then calls `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` unconditionally, splicing the mis-bounded resolution into the file and staging it for commit.

I could not fully verify the exact splice/reconstruction logic in `app/src/lib/copilot-conflict-resolution.ts`, since I ran out of tool calls before reading it — that file should be reviewed directly (via a Devin session with full repo access) to confirm whether the splice step re-validates hunk positions against fresh content or trusts the original line offsets, which would determine the precise corruption mechanics.

      i++

    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator

        if (separatorMarker.test(lines[i])) {
          i++
          break

        baseLines.push(lines[i])
        i++
      }
    }

        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }
