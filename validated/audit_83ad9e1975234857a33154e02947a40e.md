### Title
Scanner treats any output paying to a deterministic internal offset script as an internally-created output, letting an attacker forge "internal" (Branch/Change/Forwarded) outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` decides ownership/kind solely by matching `output.script_pubkey` against the registered script map, never validating the output's *provenance* — the analog of validating a tar member's own path while never checking where its symlink actually points. The internal scripts are reachable by anyone because the offsets are deterministic and publicly derivable.

### Finding Description
`Scanner::register_offset` maps `script_pubkey -> offset`, and `scan_transaction` accepts any output whose `script_pubkey` collides with a registered script (`networks/bitcoin/src/wallet/mod.rs:199-214`). The processor registers `Branch`, `Change`, and `Forwarded` offsets computed as `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch"|"change"|"forward")` (`processor/src/networks/bitcoin.rs:308-344`), then classifies each scanned output purely by `kinds[offset_repr]` (`processor/src/networks/bitcoin.rs:686-700`).

The check validates *where the output pays* (the member's path) but not *who created it or which transaction context it belongs to* (the symlink target). Since the offsets are deterministic hashes of fixed public strings over the publicly known group key, any Bitcoin user can compute `key + offset*G`, derive the identical P2TR script, and broadcast a transaction paying to it. `get_outputs` then reports that attacker-created output as `OutputType::Branch`, `OutputType::Change`, or `OutputType::Forwarded` — classifications intended only for outputs produced by Serai's own `SignableTransaction` plans.

### Impact Explanation
Outputs classified as internal kinds bypass the `OutputType::External` path — the only path on which the protocol expects arbitrary senders and requires the embedded `InInstruction` data (`presumed_origin`/data population at `bitcoin.rs:706-736` only treats `External` outputs as foreign). A forged internal output:

- Can be reported as the expected internal output of a pending plan (change consolidation, branch/forwarding rotation), satisfying completion checks with an output the protocol did not create, at a block/value/timing of the attacker's choosing.
- Skips external-deposit handling, misattributing funds in the processor's accounting and potentially triggering downstream scheduling (e.g., the scanner's `ack_block`/eventuality flow) for an operation that never happened.
- Since internal outputs are treated as protocol-owned liquidity, an attacker can inject small fake "internal" outputs to corrupt the assumed UTXO set used for plan construction.

This is "funds reported received under an internal classification that no protocol action produced," reachable with public inputs (anyone can send a Bitcoin transaction). The outputs are technically spendable (the script commits to `key + offset*G`), so the damage is misclassification/provenance forgery rather than unspendability.

### Likelihood Explanation
The attacker needs only the group key (public on the Serai chain / in previous transactions) and the fixed DST strings to recompute all internal scripts. No threshold compromise, no collusion — a single unprivileged Bitcoin sender suffices, at the cost of a dust-sized output. Medium: impact is bounded to internal-accounting/plan-state confusion rather than direct key compromise, and the exact downstream effect depends on scheduler handling of unexpected internal outputs, which I could not fully trace within the in-scope files.

### Recommendation
Bind scanned outputs to provenance, not just script. Options:

- For `Branch`/`Change`/`Forwarded` outputs, only accept them when they appear in transactions the multisig itself signed (check `tx.compute_txid()` against pending signed plans), or when they are at expected vout positions within a recognized plan transaction.
- Alternatively, treat unexpected outputs paying to internal scripts as `External` (or drop them) rather than classifying by script alone.
- Keep `kinds` lookups from being authoritative for kind assignment on unsolicited transactions.

### Proof of Concept
```rust
// Attacker side, given the Serai multisig group key `key` (public):
let branch_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch");
let mut offset = branch_offset;
// mimic register_offset's evenness bumping:
while p2tr_script_buf(key + (ProjectivePoint::GENERATOR * offset)).is_none() {
    offset += Scalar::ONE;
}
let forged_script = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * offset)).unwrap();

// Attacker broadcasts any tx with TxOut { value: dust_or_more, script_pubkey: forged_script }
// Once mined, Bitcoin::get_outputs -> scanner.scan_transaction (wallet/mod.rs:199-214)
// matches `forged_script` in self.scripts and reports the output; processor then sets
// kind = kinds[offset_repr] == OutputType::Branch (networks/bitcoin.rs:693-699),
// even though no Serai plan ever created it.
```

The forged output requires no key knowledge, no preprocess participation, and no validator misbehavior — only a standard Bitcoin payment to a publicly recomputable script.
