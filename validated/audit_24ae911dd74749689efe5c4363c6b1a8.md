### Title
Division-by-zero panic in `KIP71Config.NextMagmaBlockBaseFee` when `kip71.gastarget` governance parameter is set to zero, halting all nodes - (File: params/kip71_config.go)

### Summary
`kaiax/gov/param.go` registers the `kip71.gastarget` governance parameter with `FormatChecker: noopFormatChecker`, which always returns `true` regardless of the value, unlike other numeric KIP-71 parameters. This allows `GasTarget` to be set to `0` via a governance vote. `params.KIP71Config.NextMagmaBlockBaseFee` unconditionally divides by `gasTarget` (`x.Div(x, new(big.Int).SetUint64(gasTarget))`) whenever `parentGasUsed != gasTarget`, with no zero-guard analogous to the existing `BaseFeeDenominator == 0` guard in the same function. If `gasTarget == 0` and any block uses gas (`parentGasUsed > 0`), `big.Int.Div` panics on division by zero.

### Finding Description
`kaiax/gov/param.go` defines the parameter table for governance-controlled values. For most numeric KIP-71 fields a real `FormatChecker` is used (e.g. bound checks are enforced elsewhere in `checkConsistency` for `LowerBoundBaseFee`/`UpperBoundBaseFee`), but `Kip71GasTarget` uses: [1](#0-0) 

`noopFormatChecker` unconditionally returns `true`: [2](#0-1) 

The vote-format tests confirm that `kip71.gastarget` votes of `uint64(0)` are not tested as bad votes at all (only `"30000"`, `3000`, `false`, `true` are rejected), and existing tests explicitly exercise `gastarget=15000000`/`30000000` as valid, but no rejection of `0` exists: [3](#0-2) [4](#0-3) 

`checkConsistency` in header governance only special-cases `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` and `GovernanceGoverningNode`; `Kip71GasTarget` falls into the catch-all case that returns `nil` (no additional validation): [5](#0-4) 

Once `GasTarget = 0` becomes effective, every node computing the next block's base fee via `NextMagmaBlockBaseFee` divides by it as soon as a block uses any gas (`parentGasUsed > gasTarget`, i.e. `parentGasUsed > 0`): [6](#0-5) 

Note the function already contains a defensive zero-check for `BaseFeeDenominator`: [7](#0-6) 

but no equivalent guard exists for `gasTarget`, confirming this is a missing safeguard rather than an intentional invariant. `math/big.Int.Div` panics at runtime when the divisor is zero (Go's `big.Int` division does not return an error, it calls `panic("division by zero")`), unlike EVM arithmetic which silently returns 0.

`NextMagmaBlockBaseFee`/`VerifyMagmaHeader` are invoked in core, consensus-critical paths that run on every node processing/validating a block, including `blockchain/block_validator.go`, `blockchain/chain_makers.go`, `blockchain/tx_pool.go`, `work/worker.go`, and the `node/cn/gasprice` fee oracle: [8](#0-7) 

### Impact Explanation
Since `NextMagmaBlockBaseFee` runs deterministically on **every full node and validator** (in `BlockValidator.ValidateHeader`, block assembly in `work/worker.go`, and RPC/fee-estimation code paths), once `GasTarget = 0` is voted in and any subsequent block has nonzero gas usage, every node attempting to compute or verify the next block's base fee will panic and crash simultaneously. This is a hard, network-wide denial of service: block production and validation halt across the entire chain until a coordinated patch/hard fork restores a nonzero `GasTarget`. This mirrors the referenced bug class exactly — a governance-adjustable numeric parameter reaching zero causes an unguarded division that (a) can be reached from a normal path (governance parameter propagation into consensus-critical header/base-fee computation) and (b) results in irrecoverable, chain-wide blocking, which is a materially worse outcome than the original `CvgRewards` issue (which only locked one contract's cycle progression) because here it can crash node processes outright.

### Likelihood Explanation
Reaching this state requires a governance vote setting `kip71.gastarget = 0` to pass and take effect (in `single` governance mode, only the governing node can vote; in other modes, it may require validator/council approval), so it is not exploitable by an arbitrary unprivileged EOA in one transaction — this matches the acknowledged "governance parameter" reachable category, and mirrors the original Sherlock finding's own caveat ("unlikely to occur in reality... nevertheless valid and acknowledged as Medium"). The complete absence of a format check (`noopFormatChecker`) and absence of any consistency check in `checkConsistency`, contrasted with the deliberate zero-guard present for `BaseFeeDenominator` in the very same function, indicates this is an unintentional gap rather than a deliberately accepted risk, and a single misconfigured or malicious governance vote (human error, compromised governing-node key, or contract-governance misconfiguration) is sufficient to trigger it network-wide on the very next block with gas usage.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally a `checkConsistency` case) that rejects `0`, mirroring the existing pattern used for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`. Additionally, add a defensive zero-guard in `NextMagmaBlockBaseFee` analogous to the existing `BaseFeeDenominator == 0` fallback, e.g.:
```go
gasTarget := kc.GasTarget
if gasTarget == 0 {
    gasTarget = DefaultGasTarget // or another safe fallback
}
```
so a zero value can never reach the `big.Int.Div` calls even if it slips through governance validation.

### Proof of Concept
1. In `single` governance mode, the governing node (or via contract governance / council vote in other modes) submits a governance vote for `kip71.gastarget` with value `uint64(0)`.
2. `NewVoteData` accepts it because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` (`kaiax/gov/param.go:324-334`, `kaiax/gov/param.go:160-162`).
3. `checkConsistency` performs no extra validation for `Kip71GasTarget` (`kaiax/gov/headergov/impl/header.go:214-220`), so the vote is accepted and becomes effective in `GetParamSet`.
4. `ParamSet.ToKip71Config()` propagates `GasTarget: 0` into `params.KIP71Config` used by consensus code (`kaiax/gov/paramset.go:199-207`).
5. On the next block after the change takes effect, if `parentGasUsed > 0` (any transaction included), `NextMagmaBlockBaseFee` computes `parentGasUsed > gasTarget` (`0 > 0`? no—true if `parentGasUsed>0`), enters the increase branch, and executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0` (`params/kip71_config.go:100-102`), causing a `panic: division by zero` in every node calling `ValidateHeader`/`NextMagmaBlockBaseFee` (block validators, block producers, tx pool, fee oracle), crashing the chain.
