### Title
Attacker can steal another user's stranded predispatch tokens by sweeping the shared `CallDispatcher`'s full token balance - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder()`'s predispatch path computes the amount of tokens a user "received" by sweeping the **entire current balance** of `_params.dispatcher` (a single, persistent `CallDispatcher` contract shared by every order placed through the gateway) rather than tracking only the amount that this specific caller's predispatch call moved there. This mirrors the reported bug class: deriving a caller-attributable amount from a global/shared balance read instead of an isolated, per-caller delta, which lets balance contributed by someone else be misattributed to the current caller.

### Finding Description
In `placeOrder`, when an order has a non-empty `predispatch`, the flow is:

1. The caller's `predispatch.assets` are transferred to `dispatcher` and `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` is invoked. [1](#0-0) 

2. For each `order.inputs[i]`, the code reads `IERC20(token).balanceOf(dispatcher)` (the **entire** balance the dispatcher currently holds for that token) and builds a sweep call that transfers that whole balance to the gateway: [2](#0-1) 

3. The delta (`balanceOf(this) - balancesBefore[i]`) is treated as "received" and, if it exceeds the declared `order.inputs[i].amount`, the excess is only logged as `DustCollected` — the tokens have already been pulled into the gateway, and the surplus is not returned to anyone: [3](#0-2) 

`CallDispatcher` itself is a stateless pass-through contract with no ownership or per-order accounting — it just executes whatever `Call[]` it is given via `dispatch()`: [4](#0-3) 

The `dispatcher` address comes from `_params.dispatcher`, set once at `initialize()` and shared by **every** order routed through this gateway instance — it is not an ephemeral, per-order contract. [5](#0-4) 

If a user's `predispatch.call` unwraps or produces a token that is **not** listed in that user's own `order.inputs` (e.g., an LP unwrap that yields two tokens but the order only escrows one of them), that token remains stranded on the shared `dispatcher` contract after the transaction completes, since the sweep loop only pulls balances for tokens present in `order.inputs`. Because the dispatcher is shared across all orders, any subsequent unprivileged caller can place a trivial follow-up order (empty predispatch `call`, as demonstrated by the project's own `testPlaceOrder_FeeOnTransferToken_Predispatch` pattern) that lists the stranded token as an input with a `predispatch.assets` entry of arbitrary value (even a negligible amount they actually own). The sweep step then reads `balanceOf(dispatcher)` for that token — which now includes the earlier victim's stranded balance — and pulls the **entire** amount into the gateway, crediting it to the attacker's own order commitment up to `order.inputs[i].amount`, i.e., the attacker's escrow is funded, in whole or in part, by another user's tokens.

### Impact Explanation
This is a direct fund-theft path reachable by any ordinary, unprivileged user — no malicious relayer, prover, or governance actor is required. It results in tokens legitimately belonging to one user being credited to a different user's escrowed order, i.e., "stealing or loss of funds" and "wrong beneficiary" as defined in the bounty scope. The shared, non-isolated balance read (`IERC20(token).balanceOf(dispatcher)`) is the exact corrupted value — analogous to the Umbrella report's `IERC20(aToken).balanceOf(address(this))` after `safeTransferFrom`, which conflates the caller's contribution with whatever else happens to sit in the same account.

### Likelihood Explanation
Requires (a) at least one order whose `predispatch.call` produces or leaves a token balance on the dispatcher that is not swept back out (a realistic byproduct of any multi-token unwrap/predispatch logic that only lists a subset of resulting tokens as `order.inputs`), and (b) an attacker who notices the stranded balance and places a matching order. Both steps are achievable by a normal caller with no special privileges, and the vulnerable code path (`balanceOf(dispatcher)` full-balance sweep) is unconditionally exercised whenever `predispatch` is used.

### Recommendation
Do not sweep the dispatcher's total token balance. Instead, have the `CallDispatcher` (or the gateway) track and return only the amount attributable to the current `dispatch()` invocation — e.g., require predispatch calls to transfer exact amounts directly to the gateway, or have `CallDispatcher.dispatch` return/report per-call outputs so the gateway can compute a delta scoped strictly to the current order's calls, never a raw `balanceOf` read on a contract shared by other callers. Any genuinely unattributable residual balance should be sweepable only by protocol governance, not implicitly absorbed into the next caller's order.

### Proof of Concept
1. User A calls `placeOrder` with a `predispatch.call` that unwraps an LP token into Token A and Token B, but lists only Token A in `order.inputs`. Token B (say, 1,000 units) is transferred to `dispatcher` via the predispatch call but is never included in the sweep loop for A's order, so it is left stranded on `dispatcher` after A's transaction completes. [6](#0-5) 
2. Attacker calls `placeOrder` with a trivial predispatch (`predispatch.call` = an empty `Call[]` no-op, as used in the repo's own `testPlaceOrder_FeeOnTransferToken_Predispatch` test) and `predispatch.assets`/`order.inputs` listing Token B with a small `requiredAmount` (e.g., 1 unit) that they legitimately fund themselves. [7](#0-6) 
3. The sweep step for Token B reads `IERC20(TokenB).balanceOf(dispatcher)`, which equals attacker's small deposit **plus** User A's stranded 1,000 units, and transfers that entire balance to the gateway. [8](#0-7) 
4. `received` (the full swept amount) exceeds attacker's declared `order.inputs[i].amount`; the excess is emitted as `DustCollected` but the tokens are already inside the gateway and effectively unattributed/available for the attacker's order economics — User A's 1,000 units of Token B are gone from the pool they were stranded in and are not returned to User A. [3](#0-2)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
