### Title
Missing post-recovery consistency check in `recoverPolynomialCoeffs` allows redundant/inconsistent cell sets to silently recover a divergent polynomial - (File: api_eip7594.go)

### Summary
`Context.RecoverCellsAndComputeKZGProofs` calls `recoverPolynomialCoeffs`, which builds `extendedBlob` from the caller-supplied `cellIDs`/`cells` and passes it straight to `ctx.dataRecovery.RecoverPolynomialCoefficients` without ever re-checking that the recovered polynomial reproduces the supplied cell values at the supplied indices <cite repo="blackvul/go-eth-kzg--010" path="api_eip7594.go" start="128-146" />. When a caller supplies more cells than the minimum required for reconstruction (`ctx.dataRecovery.NumBlocksNeededToReconstruct()`), and those extra cells are crafted to be mutually inconsistent (not lying on one degree-`ScalarsPerBlob` polynomial), the erasure-decoding math produces an intermediate polynomial of degree up to `len(cellIDs)*scalarsPerCell - 1`, which must be truncated to degree `< ScalarsPerBlob` to be returned as blob coefficients; nothing in `api_eip7594.go` verifies that this truncation is lossless (i.e., that the discarded high-order coefficients are zero) or that `recovered[cellIDs[i]] == cells[i]` afterward.

### Finding Description
The equality claimed to be broken is: for every supplied `cellIDs[i]`, `recovered[cellIDs[i]]` (re-derived from `polyCoeff` via `computeCellsFromPolyCoeff`) must equal the originally supplied `cells[i]`.

Tracing the call path:
1. `Context.RecoverCellsAndComputeKZGProofs(cellIDs, cells, numGoRoutines)` <cite repo="blackvul/go-eth-kzg--010" path="api_eip7594.go" start="148-165" /> calls `ctx.recoverPolynomialCoeffs(cellIDs, cells)`.
2. `recoverPolynomialCoeffs` validates shape (`ErrNumCellIDsNotEqualNumCells`), ordering (`isAscending`), per-ID bounds (`ErrFoundInvalidCellID`), and a minimum-count threshold (`ErrNotEnoughCellsForReconstruction`) — but it never checks the *upper* bound relationship between the number of supplied cells and internal consistency of their values <cite repo="blackvul/go-eth-kzg--010" path="api_eip7594.go" start="97-117" />.
3. It deserializes each cell and places it directly into `extendedBlob` at `cellID*scalarsPerCell`, then calls `ctx.dataRecovery.RecoverPolynomialCoefficients(extendedBlob, missingCellIds)` <cite repo="blackvul/go-eth-kzg--010" path="api_eip7594.go" start="128-145" />.
4. The recovered coefficients (`polyCoeff`) are returned to `RecoverCellsAndComputeKZGProofs`, which re-derives `recoveredCells` via `ctx.computeCellsFromPolyCoeff(polyCoeff, ...)` and returns them — with no comparison back against the caller's original `cells` <cite repo="blackvul/go-eth-kzg--010" path="api_eip7594.go" start="154-164" />.

Mathematically, when a caller supplies exactly the minimum threshold number of cells, Lagrange interpolation through exactly that many points uniquely and always reproduces those points, so no divergence is possible. However, when a caller supplies *more* than the minimum threshold (redundant cells), the underlying erasure-decoding algorithm (vanishing-polynomial/FFT-based division) produces an intermediate polynomial whose degree can be as large as `(number of supplied points) - 1`. Only the low-order `ScalarsPerBlob` coefficients are kept as the "recovered" blob polynomial. If the supplied redundant cells are inconsistent with any single degree-`<ScalarsPerBlob` polynomial, the coefficients above index `ScalarsPerBlob-1` are non-zero and get silently discarded by the truncation, so the returned `polyCoeff`, and the cells re-derived from it, will not equal the cells originally supplied by the attacker at those cellIDs. None of the existing guards (`isAscending`, `ErrFoundInvalidCellID`, `NumBlocksNeededToReconstruct` lower-bound check) detect or reject this case, because they only bound the count from below, never validate self-consistency of the supplied values, and there is no assertion comparing `recovered[cellIDs[i]]` to `cells[i]` before returning.

### Impact Explanation
If the reference consensus-spec / c-kzg implementation performs (or effectively guarantees via a stricter algorithm) a check that rejects such inconsistent, over-determined cell sets while go-eth-kzg silently accepts them and emits a different (mismatched) set of recovered cells/proofs, this is a client-implementation divergence on the same input — matching the "High" severity category (disagreement on accept/reject or on emitted recovered data for the same input). A node using go-eth-kzg could accept and propagate reconstructed cell/proof data that does not match what its peers using c-kzg would produce or accept, causing chain-data disagreements in the data-availability-sampling protocol.

### Likelihood Explanation
Exploitation requires the attacker to submit more cells than the strict minimum (`NumBlocksNeededToReconstruct()`) into `RecoverCellsAndComputeKZGProofs`, with the redundant cells crafted to be inconsistent with a single low-degree polynomial. This is fully within an unprivileged caller's control (only `cellIDs` and `cells` byte arguments), requires no privileged state, and is repeatable per call. Feasibility depends on whether such inconsistent-but-valid-looking cell encodings can be constructed without failing `deserializeCell`'s canonicity checks — this was not fully verified due to not inspecting `deserializeCell` and the internal `erasure_code.go` implementation (`RecoverPolynomialCoefficients`) in this session.

### Recommendation
After computing `polyCoeff` in `recoverPolynomialCoeffs` (or immediately after in `RecoverCellsAndComputeKZGProofs`), re-derive the cells at the supplied `cellIDs` from `polyCoeff` and assert `recovered[cellIDs[i]] == cells[i]` for every supplied index, returning an error (e.g., a new `ErrInconsistentCellRecovery`) on mismatch. Additionally/alternatively, verify inside `RecoverPolynomialCoefficients` that any coefficients above `ScalarsPerBlob-1` produced during erasure decoding are exactly zero before truncating.
