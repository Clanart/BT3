### Title
`clone()` explicitly disables Git's clone-time symlink/case-collision protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) during `--recursive` clones, re-opening a CVE-2024-32002-class RCE path - (File: `app/src/lib/git/clone.ts`)

### Summary
Git 2.45.1 introduced runtime protections against a class of remote-code-execution bugs (CVE‑2024‑32002 and related CVEs) where a maliciously crafted repository — using case-insensitive/symlink-confusable submodule names that collide with `.git` — can trick `git clone --recursive` into writing files (including hook scripts) into the `.git/` directory of the superproject instead of the working tree, resulting in an executable hook file being planted and later auto-executed. The fix is enforced via an internal signal that Git itself sets/reads (`GIT_CLONE_PROTECTION_ACTIVE`) to keep the protection active across the recursive submodule-clone sub-processes it spawns.

GitHub Desktop's `clone()` function explicitly sets this variable to `'false'` on every clone, while still passing `--recursive`: [1](#0-0) 

This means every repository cloned through Desktop's "Clone repository" or "Open in Desktop" flow runs with the very protection Git added to stop this attack class turned off, for a `--recursive` clone that will process attacker-supplied submodule paths/names from the remote.

### Finding Description
`clone()` builds the environment for the `git clone` invocation like this: [1](#0-0) 

and always invokes clone with `--recursive`: [2](#0-1) 

`GIT_CLONE_PROTECTION_ACTIVE` is not a user-facing Desktop feature flag — it is the internal environment variable Git uses to indicate that clone-time protections against symlink/case-insensitive-filesystem `.git` directory confusion (the class of bugs fixed by CVE‑2024‑32002, CVE‑2024‑32004, and the accompanying submodule hardening) should remain active through nested/recursive submodule clones. By force-setting it to `'false'` for every clone, Desktop tells the embedded Git binary to skip that check even when cloning an attacker-controlled remote with `--recursive`, which is precisely the vector the check exists to catch (a crafted submodule whose name/path collides with `.git` on case-insensitive or symlink-tolerant filesystems, letting a subsequent recursive submodule checkout write a hook file, e.g. `post-checkout`, into the superproject's real `.git/hooks`).

The other defenses present in the codebase do not cover this gap:
- `isClonePathSensitive()` only validates the *destination* directory chosen by the user (home dir, `.ssh`, `.gnupg`, etc.) — it says nothing about the *contents* the remote can write once cloning begins. [3](#0-2) 
- `sanitizeCloneName()` / `parseRepositoryIdentifier()` only sanitize the top-level folder name derived from the clone URL, not paths inside `.gitmodules` or nested submodule trees. [4](#0-3) 
- The "repository appears to be owned by another user"/unsafe-directory warning in `add-existing-repository.tsx` and `missing-repository.tsx` is a `safe.directory` check that applies to *opening* an already-existing local repository, not to files written mid-clone by a hostile remote. [5](#0-4) 

None of these guards inspect or restrict what a remote server can cause `git clone --recursive` to write on disk — that is exactly the job of the upstream Git protection that this code disables.

### Impact Explanation
If exploitable against the embedded/bundled Git version, a victim who clones (or does "Open in Desktop" on) a malicious public repository would have Git write a file into their own `.git/hooks` (or another sensitive location inside `.git/`) during the recursive submodule clone, with the attacker fully controlling its content. Git hooks execute local commands automatically on subsequent, ordinary Git operations (checkout, commit, merge, etc.) performed inside Desktop — this is arbitrary code execution on the victim's machine triggered purely by cloning an attacker-supplied URL, with no other user action beyond the normal "Clone repository" flow. This matches the report's "attacker controls a cloned/fetched repository … resulting in code execution" impact class.

### Likelihood Explanation
Likelihood depends on whether the bundled Git binary is new enough that the underlying filesystem-level fixes (which do not solely rely on the env var) fully close the hole regardless of `GIT_CLONE_PROTECTION_ACTIVE`, and whether the target filesystem is case-insensitive/symlink-confusable (default on Windows and macOS, the two most common Desktop platforms). Given that Desktop deliberately overrides the protection flag to `'false'` rather than leaving Git's default (`true`) in place, and that the flow is reachable simply by cloning any attacker-hosted URL — no local access, no admin rights, no prior compromise — this is a directly reachable, unprivileged attacker-controlled-repository path. I could not confirm from the indexed code alone which exact Git/dugite version is bundled or whether all underlying protections (beyond the env var) are still enforced independently; this would need to be validated by testing against the actual shipped Git binary.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (or set it to `'true'`/leave it unset so Git's own default applies) so that the CVE‑2024‑32002-class clone-time protections remain active for `--recursive` clones of untrusted remotes. If the override was added to work around a specific compatibility issue, gate it narrowly and document why it is safe, and add a regression test asserting that a crafted submodule whose name collides with `.git` cannot cause a file to be written into `.git/hooks` during `clone()`.

### Proof of Concept
1. Host a malicious Git repository whose `.gitmodules` defines a submodule with a name/path designed to case-insensitively or symlink-collide with `.git` (the same submodule-name-confusion technique used to demonstrate CVE‑2024‑32002), where the submodule content contains a hook script such as `post-checkout`.
2. In GitHub Desktop, use "Clone repository" (or "Open in Desktop" from a crafted deep link) pointing at that URL.
3. `clone()` runs `git … clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set, per `app/src/lib/git/clone.ts:81-93,119-125`.
4. On a case-insensitive/symlink-tolerant filesystem, the recursive submodule clone step writes the attacker's hook file into the superproject's `.git/hooks` directory instead of the intended submodule working tree, because the protection that would normally reject/guard this write was explicitly disabled.
5. The planted hook (e.g., `post-checkout`) executes automatically the next time Desktop performs a checkout/pull inside that repository, achieving code execution on the victim's machine.

I was unable to fully verify step 3–4 execution against the specific bundled Git/dugite binary version in this environment (no shell access), so this should be validated by a Devin session with terminal access to the built app before treating it as a confirmed, reproduced RCE rather than a design-level analog of the CEI-violation-class bug (a protective "state"/flag being deliberately bypassed before untrusted, attacker-controlled write operations occur).

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
