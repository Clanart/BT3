### Title
`_withdraw()`'s per-token hard revert bricks intent order settlement across all exit paths - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()` is the single internal function that releases or refunds escrowed order funds for every IntentGateway exit path — same-chain fill (`IntrinsicIntents._fillSameChain`), same-chain cancel (`_cancelSameChain`), cross-chain redeem (`onAccept` → `RedeemEscrow`), cross-chain refund (`onAccept` → `RefundEscrow`, and `onGetResponse`). It loops over the tokens in a `WithdrawalRequest` and unconditionally reverts the *entire* call with `UnknownOrder()` if the live escrow for any single token entry is `0` while a non-zero amount is requested: [1](#0-0) 

This mirrors exactly the Notional bug class: a loop that assumes a per-item invariant ("escrow for this token can never be less than what the message requests") always holds, and hard-reverts the whole batch when that assumption is violated — with no partial-success fallback.

### Finding Description
The bug report's root cause is that `getWithdrawRequestValue()` assumes an exit balance can never be zero, and `require(hasRequest)` reverts the *entire* value computation if that assumption fails for even one token, bricking `price()` and freezing the account permanently since `price()` sits on every critical path (exit, repay, withdraw, liquidation).

The structural analog in Hyperbridge is `_withdraw()`:
- It is invoked from `onAccept` cross-chain `RedeemEscrow`/`RefundEscrow` message delivery and from `onGetResponse`, which are the *only* finalization paths for a cross-chain order — there is no alternate retry mechanism that recomputes amounts from live storage. Contrast this with same-chain cancel (`_cancelSameChain`), which explicitly reads the *live* `_orders[commitment][token]` balance to build the withdrawal request: [2](#0-1) 

- Cross-chain redeem/refund messages, by contrast, carry token amounts fixed at *dispatch time* (`order.inputs`/`escrowedInputs`), which are checked against the *live, independently-decremented* `_orders` mapping at *delivery time*: [3](#0-2) [4](#0-3) 

Because the escrow is a mutable shared value (`_orders[commitment][token]`) rather than a value snapshotted and passed atomically with the settlement message, any divergence between the amount encoded in the in-flight ISMP message and the escrow balance still on-chain when that message is delivered (e.g. from message reordering/redelivery at the ISMP layer, or from a same-chain path having already partially drained one of the tokens in a multi-token order) causes `_withdraw()` to revert on the *first* affected token — reverting the whole release/refund for *every other, otherwise-valid token* in the same order. Since `onAccept`/`onGetResponse` are `onlyHost`-gated one-shot execution points for that specific message, and the message body's requested amounts are immutable once dispatched, there is no way to re-drive settlement with corrected amounts: the order's escrow becomes permanently unreachable, exactly matching the "position stuck forever" impact of the seed bug.

### Impact Explanation
If triggered, the affected order's escrowed input tokens (real user/solver funds custodied by `IntentGatewayV2`) become permanently locked: `EscrowReleased`/`EscrowRefunded` can never fire for that commitment because the sole delivery path for the cross-chain settlement message always reverts, and `_filled` is never durably set (the revert unwinds the storage write made earlier in the same function). This is a direct "loss/lock of bridged funds" impact matching the Hyperbridge Impact Gate (stealing or loss of funds via a broken settlement path), reachable through the unprivileged, permissionless `fillOrder`/`cancelOrder` intent flow rather than via a malicious relayer, prover, or admin.

### Likelihood Explanation
Likelihood is moderate and conditioned on the escrow-vs-message-amount divergence actually occurring in production — I was not able to fully trace `_fillCrossChain`'s cross-chain fill accounting within the available investigation budget to confirm a concrete unprivileged sequence that produces `escrowed < requested` for one token while other tokens in the same multi-input order remain valid. The structural weakness (message-encoded amounts vs. mutable live escrow, combined with an unconditional whole-batch revert) is confirmed and directly present in shipped code; determining the exact reachable trigger (e.g., message replay/duplicate delivery semantics enforced elsewhere in the ISMP host, or partial-fill interaction with multi-token cross-chain orders) requires further review of `_fillCrossChain` and the ISMP receipt/replay-protection logic, which should be verified before triage.

### Recommendation
- In `_withdraw()`, avoid all-or-nothing reversion across independent token entries: process each token's release/refund defensively (e.g. `amount = min(amount, escrowed)`), or explicitly separate "how much can be settled now" from "how much was requested," emitting a partial-settlement event rather than reverting the entire batch.
- For cross-chain redeem/refund paths, ensure the settlement amount is derived from state that is guaranteed consistent at delivery time (e.g., re-deriving from live escrow the same way `_cancelSameChain` does) rather than trusting a value fixed at dispatch time.
- Add regression tests simulating message redelivery / out-of-order delivery of `RedeemEscrow`/`RefundEscrow` against an order whose escrow has already been partially or fully drained by a race with another finalization path.

### Proof of Concept
Not independently reproduced — this submission documents a structural code-level analog identified via static review of `IntentsBase._withdraw()`, `IntrinsicIntents`, and `ExtrinsicIntents`. A full PoC requires exercising `_fillCrossChain` end-to-end (not fully available in the indexed context) to confirm a concrete unprivileged transaction sequence that leaves `_orders[commitment][token] == 0` for one token in a multi-input order before the corresponding cross-chain settlement message is delivered.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));

            (address newImpl, bytes memory initData) = abi.decode(incoming.request.body[1:], (address, bytes));
