### Title
`is_deposit_valid` accepts a self-funded ReplacementDeposit outpoint without verifying it actually spends `old_move_txid`'s `DepositInMove` output via the security-council/nofn path - (File: `core/src/verifier.rs`)

### Summary
For `DepositType::ReplacementDeposit`, `Verifier::is_deposit_valid` only checks that the *new* `deposit_outpoint` on-chain UTXO has the expected script pubkey (built from `ReplacementDepositScript(new_nofn_xonly_pk, old_move_txid)` + `Multisig::from_security_council`), the expected `bridge_amount` value, and a block height above `start_height`. It never verifies that this specific UTXO was produced by an actual spend of `old_move_txid:DepositInMove` authorized by `CheckSig(old_nofn)` or `Multisig::from_security_council`. Since the script merely *commits to* `old_move_txid` as a data push (not as a consensus-enforced input reference), an attacker can self-fund an arbitrary fresh UTXO with the matching taproot script/amount and register it as a "replacement" for any legitimate deposit's move-to-vault txid.

### Finding Description
The claimed binding is: `deposit_outpoint` (the UTXO given in a `ReplacementDeposit` request) == an output of a transaction whose input actually spent `old_move_txid:UtxoVout::DepositInMove` via the `CheckSig(old_nofn_xonly_pk)` OR `Multisig::from_security_council(...)` spend path (as constructed in `create_replacement_deposit_txhandler`, `core/src/builder/transaction/mod.rs:404-446`).

`Verifier::is_deposit_valid` (`core/src/verifier.rs:541-732`) only checks, for the given `deposit_outpoint`:
- security council config match, watchtower/operator counts, uniqueness (lines 543-601);
- that `deposit_outpoint`'s scriptPubKey equals `create_taproot_address(deposit_scripts, ...)` where `deposit_scripts` for `ReplacementDeposit` is `[ReplacementDepositScript::new(nofn_xonly_pk, old_move_txid), Multisig::from_security_council(security_council)]` [1](#0-0) ;
- that the value equals `bridge_amount` and the block height is `>= start_height` [2](#0-1) .

None of these checks trace back to `old_move_txid`'s actual output being spent. The `ReplacementDepositScript` only embeds `old_move_txid` as an `OP_IF ... push_slice(citrea_replace) push_slice(old_move_txid) OP_ENDIF` data commitment inside the script [3](#0-2)  — it is not a consensus-level input reference. Because Bitcoin script has no way to reference a specific external outpoint being spent, the "real" enforcement of "this replacement genuinely re-vaults `old_move_txid`'s coin" is supposed to come from Clementine itself constructing/verifying the replacement transaction's *input* (`create_replacement_deposit_txhandler` uses `input_outpoint = old_move_txid:DepositInMove` with a `CheckSig(old_nofn)`/`Multisig(security_council)` spend path, requiring council/nofn signatures) [4](#0-3) . But `is_deposit_valid` never fetches or inspects the funding transaction of `deposit_outpoint` to confirm its input actually is `old_move_txid:DepositInMove`.

Exploit flow: an attacker (unprivileged, able to broadcast Bitcoin transactions) creates and funds, with their own coins, a P2TR output using scripts `[ReplacementDepositScript(current_nofn_xonly_pk, old_move_txid), Multisig::from_security_council(current_council)]` for `bridge_amount`, where `old_move_txid` is picked to be *any* legitimate, previously-created move-to-vault txid (belonging to some other user's deposit) that they have simply observed on-chain. They then call the public `Aggregator::new_deposit` gRPC with `deposit_outpoint` = their self-funded UTXO and `deposit_data = ReplacementDeposit{ old_move_txid }`. Every verifier's `is_deposit_valid` (called from `deposit_sign`/`deposit_finalize`, `core/src/verifier.rs:866-994`) passes because script/value/height all match, without ever confirming that `old_move_txid`'s vault output was spent by the council/nofn.

### Impact Explanation
If verifiers sign, this produces a fully valid new N-of-N move-to-vault transaction spending the attacker's self-funded coin, and (per the `register_replacement_deposit_to_citrea`/`replaceDeposit` flow observed in tests, `core/src/test/common/citrea/mod.rs:495-595`) that new move-to-vault txid can be registered on the Citrea bridge contract as the replacement `move_txid` for an *existing* `deposit_id`. This would decouple Citrea's bookkeeping (which vault UTXO backs a given deposit_id's minted tokens/withdrawal rights) from the actual original move-to-vault UTXO holding the legitimate user's BTC — the original, real vault becomes untracked by the protocol (its coins are no longer the ones referenced for that deposit's withdrawal/payout machinery), i.e. a move-to-vault UTXO becomes permanently orphaned/frozen relative to the bridge's accounting, matching the "move-to-vault UTXO permanently frozen" Critical category. This is repeatable against any deposit whose `move_txid` an attacker can observe on-chain (all of them, since move-to-vault txids are public), and the coin the attacker must post is their own `bridge_amount`, only locked under nofn/council control, not directly stolen — but it silently rewires the mapping without security-council authorization, since that authorization is only encoded implicitly in `is_deposit_valid`'s missing check, not enforced elsewhere on the verifier side.

I could not fully confirm from the indexed code the exact Citrea-side `replaceDeposit` Solidity logic (it is out of scope / not present in this repo's indexed contents) that determines whether this L1-side gap actually translates into a fund-diverting L2 state change, so the ultimate consensus-breaking impact depends on unverified Citrea contract behavior.

### Likelihood Explanation
Preconditions: default deployment configuration where the ReplacementDeposit path is enabled (it is a normal supported `DepositData::ReplacementDeposit` code path reachable via the public `new_deposit` gRPC on the aggregator, which routes to every verifier's `deposit_sign`/`deposit_finalize`). Attacker cost is exactly one `bridge_amount` self-funded UTXO plus fees to construct the correct taproot script (public information: `nofn_xonly_pk`, `security_council`, and any observed `old_move_txid`). No signature forgery, no key compromise, and no majority-hashrate is required — purely a missing on-chain linkage check in `is_deposit_valid`. This is repeatable for every distinct legitimate move-to-vault txid on the network.

### Recommendation
In `Verifier::is_deposit_valid` (for `DepositType::ReplacementDeposit`), fetch the transaction that funds `deposit_outpoint`, verify it has exactly one input, that this input's `previous_output` equals `old_move_txid:UtxoVout::DepositInMove::get_vout()`, and that the witness for that input satisfies the `CheckSig(old_nofn_xonly_pk)` or `Multisig::from_security_council(security_council)` script-path of the old move-to-vault taproot output (i.e., re-derive the old vault's taproot address/script from the recorded old deposit data and confirm the spend is consistent with it). Reject the deposit if `old_move_txid`'s `DepositInMove` output is not proven spent by this exact transaction.

/// Struct for deposit script that replaces an old move tx with a replacement deposit (to update bridge design on chain)
/// It commits to the old move txid inside the script.
#[derive(Debug, Clone)]
pub struct ReplacementDepositScript(pub(crate) XOnlyPublicKey, Txid);

impl SpendableScript for ReplacementDepositScript {
    fn as_any(&self) -> &dyn Any {
        self
    }

    fn kind(&self) -> ScriptKind {
        ScriptKind::ReplacementDepositScript(self)
    }

    fn to_script_buf(&self) -> ScriptBuf {
        let citrea_replace: [u8; 13] = "citreaReplace".as_bytes().try_into().expect("length == 13");

        Builder::new()
            .push_x_only_key(&self.0)
            .push_opcode(OP_CHECKSIG)
            .push_opcode(OP_FALSE)
            .push_opcode(OP_IF)
            .push_slice(citrea_replace)
            .push_slice(self.1.as_byte_array())
            .push_opcode(OP_ENDIF)
            .into_script()
    }
}

pub fn create_replacement_deposit_txhandler(
    old_move_txid: Txid,
    input_outpoint: OutPoint,
    old_nofn_xonly_pk: XOnlyPublicKey,
    new_nofn_xonly_pk: XOnlyPublicKey,
    paramset: &'static ProtocolParamset,
    security_council: SecurityCouncil,
) -> Result<TxHandler, BridgeError> {
    Ok(TxHandlerBuilder::new(TransactionType::ReplacementDeposit)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NoSignature,
            SpendableTxIn::from_scripts(
                input_outpoint,
                paramset.bridge_amount,
                vec![
                    Arc::new(CheckSig::new(old_nofn_xonly_pk)),
                    Arc::new(Multisig::from_security_council(security_council.clone())),
                ],
                None,
                paramset.network,
            ),
            crate::builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_output(UnspentTxOut::from_scripts(
            paramset.bridge_amount,
            vec![
                Arc::new(ReplacementDepositScript::new(
                    new_nofn_xonly_pk,
                    old_move_txid,
                )),
                Arc::new(Multisig::from_security_council(security_council)),
            ],
            None,
            paramset.network,
        ))
        // always use 0 sat anchor for replacement deposit tx, this will keep the amount in replacement deposit tx exactly the bridge amount
        .add_output(UnspentTxOut::from_partial(anchor_output(Amount::from_sat(
            0,
        ))))
        .finalize())
}
