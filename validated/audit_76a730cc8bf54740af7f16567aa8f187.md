### Title
Unvalidated Data Layer mirror URLs enable blind SSRF against subscribing nodes - (File: chia/data_layer/download_data.py)

### Summary
Data Layer mirror coins can be created by any wallet for any store's `launcher_id`, embedding arbitrary URLs. Nodes that subscribe to that store fetch these attacker-supplied URLs via unauthenticated outbound HTTP requests with no restriction on target address space (localhost, RFC1918/link-local ranges, cloud metadata endpoints, etc.), mirroring the GitLab blind-SSRF bug class (CVE-2022-0249).

### Finding Description
Mirror coins use `create_mirror_puzzle()` = `P2_PARENT.curry(Program.to(1))` [1](#0-0)  and `get_mirror_info()` extracts the `launcher_id` and URL list straight from the coin's memos without validating that the spender owns/controls that `launcher_id`'s singleton [2](#0-1) . Any wallet user can create a mirror coin for any store id with attacker-chosen URLs.

Once such a mirror exists on-chain, `DataLayer.get_mirrors()` / `update_subscriptions_from_wallet()` pull these URLs from `wallet_rpc.dl_get_mirrors()` and persist them as subscription server URLs [3](#0-2) . During the periodic sync loop, `fetch_and_validate()` iterates these server URLs and calls `insert_from_delta_file()`/`download_file()` [4](#0-3) , which performs an unauthenticated `aiohttp` GET directly to the attacker-controlled URL with no address-space allow-listing: `session.get(server_info.url + "/" + filename, ...)` [5](#0-4) . There is no check preventing `server_info.url` from pointing to `http://127.0.0.1/...`, `http://169.254.169.254/...`, internal RPC ports, or other shared/local address space — exactly the bug class described in the GitLab SSRF advisory (requests to shared address space not blocked).

Downloader plugin URLs (`PluginRemote`) follow the identical unrestricted-fetch pattern in `download_file()`'s plugin branch [6](#0-5) , but those are locally configured by the operator, whereas mirror URLs are attacker-supplied on-chain data reachable by an unprivileged Data Layer participant.

### Impact Explanation
A malicious Data Layer participant can force any node that subscribes to a targeted store (including nodes that auto-subscribe to owned/tracked stores) to issue outbound HTTP requests to arbitrary internal or loopback addresses at intervals defined by `manage_data_interval`. This can be used to probe/interact with internal services (local RPC ports, cloud metadata service, other LAN hosts) blindly, and can also be leveraged for resource exhaustion or triggering unexpected internal side effects if an internal HTTP endpoint reacts to GET requests with attacker-chosen paths (`filename` is also attacker-influenced through generation/root data). This satisfies the "Data Layer roots and proofs" reachable-path allowance and represents a genuine SSRF impact class, though it does not directly cause coin-state divergence or asset forgery.

### Likelihood Explanation
High likelihood of reachability: creating a mirror coin requires only a standard wallet transaction (no special permission, no proof of store ownership) and subscribing to a store id is a normal, unprivileged Data Layer RPC action (`subscribe`) [7](#0-6) . The periodic sync loop automatically acts on mirror URLs pulled from chain state without operator review.

### Recommendation
- In `get_mirror_info()`/mirror creation validation, verify that the mirror coin's spender authority is tied to the actual singleton owner for `launcher_id` (e.g., require a signature or coin lineage proof back to the store's owner key) before trusting the URL.
- In `download_data.py`'s `http_download()` and `data_layer.py`'s mirror/downloader URL handling, resolve and validate target hosts against a deny-list of loopback/link-local/private/multicast address ranges before issuing requests (equivalent to blocking "shared address space" per the GitLab fix), and support only http(s) schemes with an explicit port allow-list.
- Consider requiring the local operator to explicitly approve/allow-list server URLs used for a subscription rather than trusting URLs sourced entirely from chain data controlled by third parties.

### Proof of Concept
1. Attacker creates a mirror coin using `dl_new_mirror` (or manually crafts a `P2_PARENT`-locked coin) specifying an arbitrary victim `launcher_id` (a store id the victim already tracks) and URL `http://127.0.0.1:<victim-internal-port>/` in the memo — no ownership of that `launcher_id`'s singleton is required due to the ACS-style mirror puzzle.
2. Victim node's periodic `update_subscription()` calls `update_subscriptions_from_wallet()`, which pulls this mirror via `dl_get_mirrors` and adds `http://127.0.0.1:<port>` to the store's subscription server list [3](#0-2) .
3. `fetch_and_validate()` selects this server and calls `http_download()`, which issues `session.get("http://127.0.0.1:<port>/" + filename, ...)` from the victim node with no address restriction [8](#0-7) , completing a blind SSRF against the victim's local/internal network.

Note: I was unable to fully trace the exact spend-authorization path for `dl_new_mirror` inside `data_layer_wallet.py` within the remaining iteration budget, so the precise on-chain authorization requirements for creating a mirror coin targeting an arbitrary `launcher_id` should be independently re-verified (e.g., whether the wallet CLI/RPC restricts `launcher_id` to stores you own, even though the underlying puzzle itself imposes no such restriction) before treating this as fully confirmed.

```python
def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```
