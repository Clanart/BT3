## Title
Division-by-zero panic in `consolidatedNode.Split` when computing proposer's block reward split between CN self-stake and consensus liquidity (CL) - ([File: kaiax/staking/staking_info.go])

### Summary
`consolidatedNode.Split()` unconditionally divides by `totalAmount = cn.StakingAmount + cn.CLStakingInfo.CLStakingAmount` whenever `CLStakingInfo` is non-nil, with no check that this sum is non-zero. Unlike the staking-reward distribution paths (`assignStakingRewards`/`assignStakingRewardsFlex`), which only invoke `Split` after confirming a validator's combined stake exceeds `minStake`/`threshold`, the **proposer** reward path (`specWithProposerAndFunds` / `specWithProposerAndFundsFlex`) calls `cn.Split(proposer)` for the block's own proposer with no such guard. This is directly analogous to the CVE-2021-37684 TFLite pooling bug class (CWE-369): a divisor derived from external/user-controllable inputs is used without a zero check, causing a crash (FPE/panic).

### Finding Description
`Split` is defined as: [1](#0-0) 

It divides `clAmount` by `totalAmount`, which is the sum of the CN's own `StakingAmount` and its `CLStakingInfo.CLStakingAmount`, with no `totalAmount.Sign() == 0` guard.

`StakingAmount` is derived from the AddressBook staking-contract balance and is truncated to whole KAIA via integer division: [2](#0-1) 

Any staking-contract balance below 1 KAIA (`params.KAIA` = 1e18 kei) rounds down to `StakingAmount = 0`. `CLStakingAmount` is likewise a `uint64` populated directly from the CL registry's reported amount, without a non-zero filter: [3](#0-2) 

Consensus liquidity (CL) deposits/withdrawals into a validator's CL pool are performed by unprivileged stakers; a staker can withdraw all liquidity from a specific validator's CL pool, driving that validator's `CLStakingAmount` to 0. If that same validator's own `StakingAmount` also rounds to 0 (a plausible edge value, or the CN having a sub-1-KAIA balance), the `consolidatedNode` for that validator has `StakingAmount = 0` and `CLStakingInfo.CLStakingAmount = 0`, but `CLStakingInfo` itself remains non-nil.

The reward-distribution code paths that call `Split` on this validator's own excess-stake allocation guard against this via `minStake`/`threshold` checks before ever computing `Split`: [4](#0-3) [5](#0-4) 

However, the **proposer's own reward** is split unconditionally, with no such precondition: [6](#0-5) [7](#0-6) 

If the block proposer's `consolidatedNode` has `CLStakingInfo != nil` but `StakingAmount + CLStakingAmount == 0`, `cn.Split(proposer)` computes `totalAmount = 0` and calls `big.Int.Div(clAmount, totalAmount)`, which panics at runtime (Go's `math/big` division by zero is a fatal panic, not an error return).

### Impact Explanation
This code path executes inside `FinalizeState()` (deferred reward distribution) on every full/honest node processing the block, since reward computation is part of block finalization. A panic here would crash the node process for all nodes processing that block, causing a consensus-wide chain halt/DoS rather than a localized failure — a High-impact availability issue reachable without any privileged access, matching the "state divergence between honest nodes" / crash criteria in scope.

### Likelihood Explanation
Reaching the exact zero-sum condition requires two independently-controllable conditions to coincide for the specific validator that becomes proposer of a given block:
1. The validator's own CNStaking balance rounds down to 0 KAIA (sub-1-KAIA balance), and
2. All consensus liquidity in that validator's CL pool has been withdrawn by CL depositors (unprivileged stakers), leaving `CLStakingAmount = 0`.

Both are achievable by unprivileged actors (the validator's own low self-stake, and staker(s) withdrawing all CL), but require the validator to simultaneously be selected as the block proposer in the round where the imbalance exists. This makes the likelihood **Medium** — plausible but requiring specific validator/staking conditions rather than trivial single-transaction exploitation.

### Recommendation
In `consolidatedNode.Split`, check `totalAmount.Sign() == 0` before dividing and return `(amount, big.NewInt(0))` (or an explicit error) in that case, mirroring the safety pattern already used in `assignStakingRewards`/`assignStakingRewardsFlex`. Additionally, consider validating in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` that a CN's combined self+CL stake is non-zero before calling `Split`.

### Proof of Concept
1. A validator `V` (proposer candidate) maintains a CNStaking contract balance under 1 KAIA, so `StakingAmount` (computed via integer division by `params.KAIA`) resolves to `0`.
2. `V` has a registered CL pool with `CLStakingInfo != nil`. Any staker(s) that deposited into `V`'s CL pool submit ordinary withdrawal transactions to fully drain the pool, driving `CLStakingAmount` to `0`.
3. Both conditions occur before/at the block where `V` is selected as proposer (post-Prague, `IsPrague == true`).
4. At `FinalizeState()`, `specWithProposerAndFunds` (or the flex variant) locates `V`'s `consolidatedNode` by `RewardAddr == config.Rewardbase`, sees `CLStakingInfo != nil`, and calls `cn.Split(proposer)`.
5. Inside `Split`, `totalAmount = big.NewInt(0).Add(0, 0) = 0`; `clAmount.Div(clAmount, totalAmount)` panics, crashing every node finalizing that block.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
