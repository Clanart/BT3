### Title
SignableTransaction fee calculation omits the OP_RETURN data output, causing underpriced transactions that fail relay and lock received funds - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` builds `tx_outs` including an OP_RETURN output carrying `data`, but computes the transaction weight/vbytes — and therefore `needed_fee` — over only `payments` and the optional `change` output. The same wrong-field pattern as the reference bug (checking `market.longToken` while debiting `initialLongToken`): the fee is priced against a different set of outputs than the transaction actually contains. The result is a signed transaction whose real fee rate is lower than the caller-specified `fee_per_vbyte`, potentially below the node's minimum relay fee.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the weight is calculated: [1](#0-0) 

but `calculate_weight_vbytes` is invoked with `payments`, not `tx_outs`, so the OP_RETURN output's bytes (~9 + len(data), up to ~89 bytes ≈ 23+ vbytes) are never counted: [2](#0-1) 

The identical omission exists in the change path: [3](#0-2) 

Consequently `needed_fee` and the minimum-relay-fee guard are computed against a smaller transaction than the one actually signed: [4](#0-3) 

The signed transaction is then broadcast as-is; `fee()` (actual `inputs − outputs`) equals `needed_fee`, which covers only `vbytes_without_data`, so the effective fee rate is `needed_fee / actual_vbytes < fee_per_vbyte`.

### Impact Explanation
An OP_RETURN output adds roughly 11 + len(data) bytes (~23 vbytes worst case at 80 bytes of data). For low `fee_per_vbyte` values near the relay minimum, the true fee rate can drop below `DEFAULT_MIN_RELAY_TX_FEE`, making `send_raw_transaction` reject the transaction. Any scanner-observed outputs intended to be spent via that transaction become unspendable until reconstructed — funds reported received that are not spendable. Even when relay succeeds, every data-carrying transaction pays a fee rate systematically lower than requested. This is reachable purely through public inputs: `data` and `fee_per_vbyte` are supplied to `SignableTransaction::new` by the caller.

### Likelihood Explanation
Any `SignableTransaction::new` call with `data.is_some()` triggers the miscalculation deterministically. Serai embeds InInstruction data in Bitcoin transactions via OP_RETURN, so the path is exercised whenever a data-bearing payment is constructed. Whether the transaction is actually rejected depends on how close `fee_per_vbyte` is to the relay minimum and the data length; the underpricing itself is unconditional.

### Recommendation
Pass the fully constructed `tx_outs` (including the OP_RETURN output) into the weight calculation rather than `payments`. Concretely, change `calculate_weight_vbytes` to accept `&[TxOut]` and call it with the `tx_outs` vector (with a placeholder zero-value change output for the change variant), so `needed_fee` is priced over the exact output set that will be signed.

### Proof of Concept
```rust
// networks/bitcoin: construct a SignableTransaction with near-maximal data
// and the minimum viable fee rate.
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
  vec![received_output],            // a scanned ReceivedOutput
  &[(payment_script, 1000)],
  None,
  Some(data),
  1,                                // fee_per_vbyte at relay minimum
).unwrap();

// tx.needed_fee() was computed over vbytes that exclude the ~89-byte
// OP_RETURN output now present in tx.transaction().output.
let actual_vbytes = tx.transaction().vsize() as u64;
assert!(tx.fee() < actual_vbytes * 1); // effective rate < requested rate
// A node enforcing DEFAULT_MIN_RELAY_TX_FEE rejects the signed TX,
// leaving the inputs unspendable via this transaction.
```
Root cause: `calculate_weight_vbytes(tx_ins.len(), payments, …)` at send.rs:204 and send.rs:226 prices `payments` while the real output vector `tx_outs` (built at send.rs:188–201) additionally contains the OP_RETURN output — the wrong-field/wrong-set analog of the `market.longToken` vs `initialLongToken` confusion.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
