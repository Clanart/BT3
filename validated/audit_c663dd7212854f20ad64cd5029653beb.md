## Analysis

The Sherlock report describes a `payable` entry point (`flash`) that the caller isn’t supposed to send ETH to, with no mechanism to return or account for stray value, leading to permanent loss/theft of funds. The `sei-chain` analog of this bug class is the **distribution precompile’s `rewards()` method**, which is the one query/view method that lacks the `ValidateNonPayable` guard present on every sibling method.

### Root Cause

In every version of `precompiles/distribution/distribution.go`, `Execute()` dispatches every state-changing method (`SetWithdrawAddress`, `WithdrawDelegationRewards`, etc.) with an explicit `readOnly` guard, and dispatches `WithdrawValidatorCommissionMethod` with an explicit `pcommon.ValidateNonPayable(value)` check [1](#0-0) . However, `RewardsMethod` is dispatched directly with no non-payable check and no readOnly guard at all: [2](#0-1) 

The `rewards()` implementation itself only queries `DelegationTotalRewards` and packs a response — it never inspects, refunds, or otherwise accounts for `value`: [3](#0-2) 

This same gap exists across every historical version of the precompile (`v580`, `v605`, `v606`, `v610`, `v614`, `v620`, `v630`, `v640`, `v65`, `v66`, `v67`), confirming it is a long-standing, unpatched pattern rather than an isolated regression [4](#0-3) .

The test-suite authors were aware of this and explicitly documented it as intentional/known rather than fixed: [5](#0-4) [6](#0-5) 

Other precompile methods that legitimately accept `usei` value (e.g. `wasmd.execute`) explicitly call `pcommon.HandlePaymentUsei`, which either forwards the coins into the CosmWasm execution's `Funds` or refunds the payer [7](#0-6) . `rewards()` has no analogous handling — the EVM's normal `CALL`-with-value semantics move the `usei`/`wei` balance from the caller to the precompile's associated Sei account before `Execute` even runs, and nothing in `rewards()` ever moves that balance back out.

### Title
Distribution precompile's `rewards()` view method accepts `value` without a non-payable check, permanently stranding sent funds - ([File: precompiles/distribution/distribution.go])

### Summary
The distribution precompile at `0x...1007` validates non-payability on all its state-mutating methods (and even one specific view, `WithdrawValidatorCommission`), but its `rewards(address)` query method omits the `pcommon.ValidateNonPayable(value)` check present everywhere else. Any transaction (not staticcall) that calls `rewards()` with non-zero `msg.value` succeeds, the EVM's value-transfer semantics move the sent `usei`/`wei` into the precompile's associated bank account, and `rewards()` neither uses nor refunds that value.

### Finding Description
`Execute()` in `precompiles/distribution/distribution.go` dispatches to `p.rewards(ctx, method, args)` for `RewardsMethod` with no call to `pcommon.ValidateNonPayable(value)`, unlike every other switch case in the same function [8](#0-7) . Because `rewards` is a plain query that only calls `p.distrKeeper.DelegationTotalRewards` and packs the ABI output [3](#0-2) , any value attached to the call is silently absorbed by the EVM's standard value-transfer mechanics (credited to the precompile's own Sei-side account) with no code path to reclaim or forward it, exactly mirroring the Sherlock report's "payable function not meant to receive funds" bug class.

### Impact Explanation
Any user/contract mistakenly (or through a malicious front-end/router) sending value alongside a `rewards(address)` call on the distribution precompile permanently loses that `usei`/`wei` — it accrues to the precompile's own address with no withdrawal path, constituting a permanent freezing/loss of user funds. This matches the accepted High-severity impact criteria (permanent fund freezing).

### Likelihood Explanation
Likelihood is moderate: exploitation requires a caller to send value with a `rewards()` call rather than a plain `eth_call`/staticcall (the common usage pattern), but nothing in the ABI or precompile prevents it, and no other precompile method in the same contract has this gap — making it an easy, unintentional trap for integrators building custom router/aggregator contracts.

### Recommendation
Add `if err = pcommon.ValidateNonPayable(value); err != nil { return nil, 0, err }` to the `RewardsMethod` case in `Execute()` in `precompiles/distribution/distribution.go` (and all still-supported legacy versions), matching the guard already used for `WithdrawValidatorCommissionMethod` and the other view methods that should reject value.

### Proof of Concept
1. Call the distribution precompile (`0x0000000000000000000000000000000000001007`) function `rewards(address delegator)` via a normal (non-static) EVM transaction with `msg.value > 0`.
2. The EVM performs the standard value transfer from caller to the precompile address before executing `Run`/`Execute`.
3. `Execute()` dispatches straight to `rewards()` without calling `ValidateNonPayable`, so the call succeeds and returns the query result.
4. The transferred `usei`/`wei` now resides in the distribution precompile's associated Sei account with no code path in `rewards()` (or any sibling method) to return it to the sender — the funds are permanently stuck.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
