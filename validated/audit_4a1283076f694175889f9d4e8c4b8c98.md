Found a concrete analog in the auction bid signature scheme, structurally identical in root cause to the reported RewardPool issue: a signature that is not bound to the specific action/version it authorizes.

### Title
Auctioneer signature is not bound to the bid content or AUCTION_VERSION, enabling cross-version bid/field tampering - ([File: kaiax/auction/bid.go])

### Summary
`RewardPool`'s `burn()`/`move()` bug stems from two near-identical, differently-consequential operations being distinguished only by an implicit runtime value (separate nonces) rather than an explicit, signed indicator of *which* operation is authorized. The same bug class exists in Kaia's auction module: the auctioneer's co-signature over a searcher's bid is computed **only over the raw `SearcherSig` bytes**, not over the bid's actual content, the `AUCTION_VERSION`, chain ID, or verifying contract. Meanwhile, the protocol supports two structurally different, version-selected signing/encoding schemes (v2.1 without `MaxGasPrice`, v3.0 with `MaxGasPrice`) that are also selected only by an implicit, node-read runtime value (`AUCTION_VERSION`) rather than by anything present in the auctioneer's own signature.

### Finding Description
`Bid.GetEthSignedMessageHash()` builds the digest that the auctioneer signs as simply `keccak256("\x19Ethereum Signed Message:\n" + len(SearcherSig) + SearcherSig)`: [1](#0-0) 

`ValidateAuctioneerSig` then only checks that this digest was signed by the expected `auctioneer`: [2](#0-1) 

Compare this with `ValidateSearcherSig`, which binds the searcher's authorization to `chainId`, `verifyingContract`, and `version` via full EIP-712 typed data: [3](#0-2) 

The two EIP-712 struct encodings differ only in whether `MaxGasPrice` is part of the hashed struct: [4](#0-3) 

`BidData.MaxGasPrice` is a `json:"omitempty"` field carried separately in the RLP/JSON payload: [5](#0-4) 

The `version` used to validate a bid's `SearcherSig` and to encode the eventual on-chain call is not chosen by the searcher or embedded in any signature — it is read live from the chain by the node via `ReadAuctionVersion` and cached in `bidPool.auctionEntryPointVersion`: [6](#0-5) [7](#0-6) 

Because:
1. The auctioneer's signature never covers the bid's actual fields (target tx hash, sender, `to`, nonce, bid amount, `MaxGasPrice`, call gas limit, data) — only the opaque `SearcherSig` bytes — and
2. `MaxGasPrice` is entirely excluded from what the searcher signs under the v2.1 typehash,

an RPC caller submitting a bid via `SubmitBid` can set an arbitrary `BidInput.MaxGasPrice` value that is neither signed by the searcher (under v2.1) nor bound by the auctioneer's signature (which only attests to the `SearcherSig` blob, regardless of contract version or field content): [8](#0-7) 

If the network's active `AUCTION_VERSION` transitions from v2.1 to v3.0 (or a node's cached `auctionEntryPointVersion` becomes stale/inconsistent relative to another node's), a bid whose `SearcherSig` was produced and accepted under the v2.1 typehash (which never committed to `MaxGasPrice`) can be re-encoded and executed via the v3.0 ABI, which **does** include `MaxGasPrice` in the on-chain call — using a value the searcher never actually authorized: [9](#0-8) 

This is the same root cause pattern as the reported issue: two "almost identical" authorized operations (v2.1 call vs v3.0 call, analogous to `burn()` vs `move()`) are distinguished only by an out-of-band, mutable value (on-chain `AUCTION_VERSION` / cached module state, analogous to `BurnNonce`/`MoveNonce` alignment) instead of the signature itself explicitly committing to the operation/version/field-set being authorized.

### Impact Explanation
An attacker-controlled `MaxGasPrice` that bypasses both searcher and auctioneer authorization can be used to manipulate auction settlement economics (e.g., inflating the gas price cap used in bid execution/refund accounting on the v3.0 entry point) despite neither party's signature actually covering that value under the version in effect when the signature was produced. This constitutes unauthorized manipulation of auction/bid settlement terms reachable by any bidder submitting a bid over the public `auction_submitBid` RPC, without requiring any privileged access, satisfying the "auction bidder" and "public-RPC caller" reachability requirement.

### Likelihood Explanation
Exploitation requires a window where the signature-validation version and the execution/encoding version diverge (e.g., during a version migration of the `AuctionEntryPoint` contract, or bid-pool cache staleness relative to another validating node), which is a narrower condition than a fully general, always-exploitable bug. However, unlike `RewardPool`'s nonce-alignment reliance (which the client already deemed fragile), this auction design has **no defense at all** tying the auctioneer's approval to bid content/version — the gap is structural, not merely a fragile secondary control, making it likely to manifest whenever a version transition or multi-binary/version-mismatch scenario occurs across the network's nodes.

### Recommendation
Bind the auctioneer's signature to the full bid content and to an explicit, version/selector-committing value, mirroring the report's recommendation to include the function selector in the signed data:
- Compute `AuctioneerSig` over a digest that includes the same EIP-712 typed struct hash (or at minimum, all `BidData` fields including `MaxGasPrice`), the `chainId`, `verifyingContract`, and the `AUCTION_VERSION` string used to construct the `SearcherSig`, not merely the raw `SearcherSig` bytes.
- Ensure the same explicit version tag used for `SearcherSig` validation is also authenticated and unambiguously carried through to `EncodeAuctionCallData`, so a bid validated under one version's typehash can never be re-encoded/executed under a different version's ABI.

### Proof of Concept
1. Node's cached `auctionEntryPointVersion` is `AuctionVersionV2` (`"0.0.1"`) at the time a searcher submits a bid via `auction_submitBid` with `BidInput.MaxGasPrice = X` (attacker-chosen, e.g. an extreme value).
2. `ValidateSearcherSig` is computed against the v2.1 typehash via `GetHashTypedData(..., AuctionVersionV2)`, whose `EncodeData()` never includes `MaxGasPrice`, so the signature is valid regardless of `X`: [10](#0-9) 
3. `ValidateAuctioneerSig` only checks that `AuctioneerSig` recovers to the auctioneer over `keccak256(EthPrefix + SearcherSig)` — it never inspects `MaxGasPrice`, `X`, or the bid's other fields at all: [2](#0-1) 
4. The bid, `SearcherSig`, and `AuctioneerSig` pass `validateBidSigs` and are accepted into the pool: [7](#0-6) 
5. If the entry point subsequently reports (or is read as) `AuctionVersionV3` when the bid is executed/encoded, `EncodeAuctionCallData` will include `bid.MaxGasPrice = X` in the on-chain `call(...)` payload to the v3.0 contract, applying an unauthorized value neither the searcher nor auctioneer actually committed to under the signature scheme in force at signing time: [11](#0-10) 

Note: I was not able to fully trace how `bid.MaxGasPrice` is consumed inside the v3.0 `AuctionEntryPoint` on-chain contract's settlement/refund logic (only the mock in `contracts/testing/system_contracts/AuctionEntryPointMock.sol` was available in the index, and it has the bid-taking/refund logic commented out), so the precise on-chain financial impact of an unauthorized `MaxGasPrice` could not be fully confirmed from the indexed code; a background Devin session with full repo access would be needed to inspect the production `AuctionEntryPoint`/`Kip249V3` contract source to confirm exact fund-impact severity.

func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

// EncodeEIP712 encodes any EIP712Encoder according to EIP-712 specification
func EncodeEIP712(encoder EIP712Encoder) []byte {
	encoded := make([]byte, 0)
	encoded = append(encoded, encoder.EncodeType()...)
	encoded = append(encoded, encoder.EncodeData()...)
	return crypto.Keccak256Hash(encoded).Bytes()
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
