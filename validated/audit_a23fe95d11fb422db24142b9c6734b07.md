### Title
Unbounded recursion-depth/limit leak on decode error in `UntypedMessage::DecodeDelimited` - ([File: src/google/protobuf/json/internal/untyped_message.cc])

### Summary
The libceph CVE's failed invariant is: a stateful decoder tracks partial progress (sparse-read state, recursion/limit bookkeeping) that is *not reset* when the read fails/aborts, so the next attempt to use the same stateful object misinterprets it, and can enter an unrecoverable loop. The closest structural analog I could substantiate in this checkout is in `UntypedMessage::DecodeDelimited` in `src/google/protobuf/json/internal/untyped_message.cc:461-532`, which is used by the ProtoJSON `Any`/type-resolution machinery to decode a length-delimited field off a shared `io::CodedInputStream`. I was not able to fully trace every caller of this function within the remaining time, so I cannot conclusively prove the "reused stream after failure" precondition; this should be treated as a plausible but not fully confirmed analog.

### Finding Description
`DecodeDelimited` increments the stream's recursion depth and pushes a limit at the top: [1](#0-0) 

It then dispatches on field kind. For `TYPE_STRING`/`TYPE_BYTES` and packed scalar fields it uses `RETURN_IF_ERROR`/early `return` on failure: [2](#0-1) 

Only on the successful fall-through path does it call the balancing cleanup: [3](#0-2) 

Every early return above (`MakeUnexpectedEofError()`, `MakeProto3Utf8Error()`, `RETURN_IF_ERROR(...)`, `MakeInvalidLengthDelimType(...)`) skips the trailing `stream.DecrementRecursionDepthAndPopLimit(limit)` call. This means:
- The recursion-depth counter that was incremented at line 463 is never decremented on any of these failure paths.
- The byte-limit pushed by `ReadLengthAndPushLimit()` at line 466 is never popped on failure.

This is structurally the same defect class as the libceph bug: a piece of decode state (recursion counters / length limits, analogous to the sparse-read state machine) is mutated at the start of an operation but only unwound on the success path; failure leaves the shared `CodedInputStream` object's bookkeeping desynchronized from where the bytes actually are.

### Impact Explanation
`google::protobuf::io::CodedInputStream`'s own documented contract states plainly: *"if any method throws an exception... it can desynchronize the instance and leave its internal state unspecified. The instance should not be used further and must be discarded"* (see class comment, `src/google/protobuf/io/coded_stream.h:142-150`): [4](#0-3) 

If the caller of `DecodeDelimited` (in `UntypedMessage::ParseFromStream`/the `Any`-resolution decode loop) treats a field-level decode failure as *recoverable* — e.g., logging it and continuing to decode sibling fields or subsequent top-level messages on the same `CodedInputStream` — then the leaked recursion-depth increment and un-popped limit would corrupt all further reads through that stream: subsequent legitimate, bounded fields could spuriously trip `RecursionLimitExceeded`, or `BytesUntilLimit()`/limit-based length checks would be computed against a stale limit, producing spurious `TruncatedMessage`/`RecursionLimitExceeded` errors on data that is otherwise well-formed. That matches the CVSS profile of the libceph bug (`C:N/I:N/A:H`): no confidentiality/integrity break, but a denial-of-service style failure loop confined to the consuming application's use of that decode path.

However, I was unable to confirm within the available searches whether `UntypedMessage::ParseFromStream`'s field-decode loop actually swallows per-field decode errors and continues (which would be required for exploitability), or whether it treats any `DecodeDelimited` failure as fatal and aborts/discards the whole `CodedInputStream` (in which case the leaked state is harmless, matching the documented single-use contract). This is the critical unresolved question.

### Likelihood Explanation
Medium-low confidence. The trigger requires only a bounded, malformed length-delimited field (e.g., a `TYPE_STRING` field with invalid UTF-8, per `MakeProto3Utf8Error()` at line 481, or a truncated packed scalar) inside an `Any`-typed value being converted through the type-resolver/JSON path — reachable from an ordinary client sending bounded ProtoJSON/`Any` payloads through a public parse/serialize API, assuming that surface uses `UntypedMessage`. But because I could not verify the calling convention/error-handling of `ParseFromStream` (only one reference was found, in `unparser.cc`, and I did not have iterations left to inspect it), I cannot state with confidence that the leaked state actually escapes into a second, independent parse attempt rather than immediately terminating the whole conversion.

### Recommendation
Regardless of exploitability confirmation, `DecodeDelimited` should use an RAII/cleanup guard (e.g. `absl::Cleanup`) to guarantee `stream.DecrementRecursionDepthAndPopLimit(limit)` (or the appropriate error-path equivalent) runs on every exit path, mirroring the pattern already used elsewhere in the codebase (e.g. `absl::MakeCleanup` in `src/google/protobuf/compiler/parser.cc:1149` and `text_format.cc:529`). This closes the state-leak regardless of whether the current callers happen to discard the stream on error — defense in depth against future callers that might retry/reuse the stream, which is exactly the class of bug the libceph fix addresses (reset stateful bookkeeping in the fault/error path rather than relying on every caller to do the right thing).

### Proof of Concept
I could not run code in this environment. A concrete reproduction would require:
1. Constructing a `Field` of `TYPE_STRING` (or a packed scalar) with a length-delimited payload containing invalid UTF-8 (to hit `MakeProto3Utf8Error()`) or a truncated packed value (to hit the `DecodeVarint`/`Decode32Bit`/`Decode64Bit` failure paths), inside a serialized `Any`.
2. Feeding this through the public ProtoJSON conversion API path that constructs an `UntypedMessage` from a `CodedInputStream` (via `ParseFromStream`), while reusing/continuing to use the same `CodedInputStream` for subsequent field or message decoding.
3. Asserting, via a debug build with recursion-depth/limit assertions, that `stream.recursion_budget_` and the current limit are inconsistent with the number of bytes actually consumed after the failed `DecodeDelimited` call returns.

Because I could not confirm step 2 (whether any caller actually reuses the stream past a `DecodeDelimited` failure) within the remaining tool budget, I am not able to assert this as a proven, exploitable vulnerability — only as a real code defect (missing cleanup on error paths) that structurally mirrors the CVE's failed invariant. If a background engineering investigation confirms `ParseFromStream`'s loop does not abort the whole `CodedInputStream` on a `DecodeDelimited` failure, this finding should be upgraded to Medium/High DoS; otherwise it remains a defensive-coding gap rather than a directly exploitable vulnerability.
