## Analog Found: Protocol-fee rounding-to-zero in `IntentGatewayV2.placeOrder`

The exact bug class from the report — repeatedly executing small transfers so `amount * feeBps / 10_000` truncates to `0`, letting the payer dodge the fee entirely — has a direct analog in Hyperbridge's `IntentGatewayV2` protocol-fee deduction.

### Title
Protocol fee can be rounded to zero by splitting orders into small amounts - (evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` computes the protocol fee taken from each escrowed input with plain integer division that truncates toward zero, exactly like `HoneyQueen::computeFees`. An order-placer can split a large transfer into many orders each below the rounding threshold and pay `protocolFee == 0` on every one of them, permanently avoiding the fee that legitimate single large orders pay.

### Finding Description
In `placeOrder`, the protocol fee is computed as:
```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
...
if (protocolFee > 0) emit DustCollected(token, protocolFee);
``` [1](#0-0) 

The same computation and truncation exist in `fillOrder`'s phase-2 fee computation and in the Tron fork of the same contract. [2](#0-1) 

`protocolFeeBps` is set as low as 5 bps in current deployments per the documented placement flow. [3](#0-2) 

With `protocolFeeBps = 5`, any `originalAmount < 2000` (in the token's smallest unit) satisfies `amount * 5 / 10_000 == 0`, so `protocolFee` is exactly zero and no fee is ever deducted or emitted as `DustCollected`. There is no minimum-fee floor and no "round up" branch anywhere in the fee computation — unlike the neighboring rounding-dust fix already applied for partial fills (see `testPartialFill_RoundingDustReleasedToFinalSolver`), which explicitly guards against truncation loss elsewhere in the same contract. [4](#0-3) 

An attacker (any ordinary order-placer, no privileged role needed) can therefore place N small orders instead of one large order and pay zero protocol fee on the entire notional amount, whereas a single order of the same aggregate size would have paid `originalAmount * protocolFeeBps / 10_000` to the protocol (collected as `DustCollected`).

### Impact Explanation
This is a direct, unprivileged, repeatable mechanism for permanently avoiding protocol revenue on `IntentGatewayV2`, the production intent-settlement entrypoint used for both same-chain and cross-chain order placement. For high-value/low-decimal tokens (e.g., 8-decimal wrapped BTC or other high-unit-value assets), the per-order threshold (`10_000/protocolFeeBps` units) can represent a meaningful notional value, making the split-and-avoid strategy profitable relative to gas costs, exactly as the original report notes for `HoneyLocker`.

### Likelihood Explanation
Likelihood is Medium: it requires no special privileges, no relayer/prover cooperation, and no race condition — just placing multiple orders. It is bounded by gas cost per extra `placeOrder` call and only becomes profitable for tokens where the rounding threshold's value exceeds the marginal gas cost of splitting, similar to the "high-value, low-decimal" caveat in the original report.

### Recommendation
Round the protocol fee up (ceiling division) as already done in `sdk/packages/sdk/src/protocols/intents/quote/shared.ts`'s `divCeil`/`grossUpForProtocolFee` helpers used for quoting, or enforce a minimum non-zero fee once `protocolFeeBps > 0` and `originalAmount > 0`, mirroring the ceiling-rounding pattern the SDK already uses off-chain for quotes but which the on-chain `placeOrder`/`fillOrder` fee deduction does not apply. [5](#0-4) 

### Proof of Concept
1. Gateway configured with `protocolFeeBps = 5` (current mainnet setting per docs).
2. Attacker wants to move 1,000,000 units of a token through the gateway.
3. Instead of one `placeOrder` with `amount = 1,000,000` (fee = `1,000,000*5/10_000 = 500`), attacker issues 500+ separate `placeOrder` calls each with `amount = 1999` (fee = `1999*5/10_000 = 0`, truncated).
4. Each call passes with `protocolFee == 0`, `reducedAmount == originalAmount`, and no `DustCollected` event.
5. Aggregate notional moved equals the same 1,000,000 units, but total protocol fee collected is `0` instead of `500`, confirmed by inspecting `_orders[commitment][token]` balances and the absence of `DustCollected` emissions across all calls.

```text
### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.
```

/** Mirrors the gateway's floored fee deduction. */
export function deductProtocolFee(amount: bigint, protocolFeeBps: bigint): bigint {
	if (protocolFeeBps <= 0n) return amount
	const fee = (amount * protocolFeeBps) / BPS_DENOMINATOR
	return amount - fee
}

/** Conservatively grosses a net amount up so protocol-fee deduction cannot leave it short. */
export function grossUpForProtocolFee(netAmount: bigint, protocolFeeBps: bigint): bigint {
	if (protocolFeeBps <= 0n) return netAmount
	if (protocolFeeBps >= BPS_DENOMINATOR) throw new Error("protocolFeeBps must be less than 10,000")
	return divCeil(netAmount * BPS_DENOMINATOR, BPS_DENOMINATOR - protocolFeeBps)
}
```
