This is the key finding: `FileChange.id` is computed purely from **path + status kind** (and `oldPath` for renames/copies), not from any content hash, blob OID, or the actual diff content. [1](#0-0) 

This identity is then used throughout the app as the sole "has this changed" check that gates diff reuse and re-fetch decisions — exactly analogous to the CVE's flaw of trusting a partial identifier (`txid`, which excludes auth data) as proof that the full object is unchanged/verified.

### Where the partial identity is trusted as "unchanged"
- `updateChangedFiles` reuses the previously-loaded `diff` object for the working directory selection if the selected file `id` is unchanged, without ever comparing blob content/oid: [2](#0-1) 
- `updateChangesWorkingDirectoryDiff` guards against "a different file was selected" purely via `selectedFileIDs` equality, not content identity: [3](#0-2) 
- `_changeFileSelection` (committed-file diff loading) similarly re-checks only `shas`/`file.id` after the async diff load, never the actual content hash of the loaded diff versus current file state: [4](#0-3) 
- The `SeamlessDiffSwitcher` in the diff viewer also gates re-fetching file contents on `isSameFile`/`isSameDiff`, reusing previously loaded content when the `id`/diff-structural-equality says "same": [5](#0-4) 

### Why this matters for commit/discard integrity
The `diff` object cached under this weak identity is exactly what gets converted into a real `git apply` patch when the user stages partial changes or discards a selection:
- `formatPatch` builds a real unified diff from the (possibly stale) `diff.hunks` and the `file.selection`, which is then applied to the index via `git apply --cached`: [6](#0-5) 
- `discardChangesFromSelection` does the same for discarding, applying a patch derived from a cached `diff` object directly to the working tree via `git apply`: [7](#0-6) 

If a file's on-disk/blob content changes (e.g. because a fetch/checkout/submodule update, or a background git operation triggered by opening an attacker-crafted repository, alters file content) while `path` and `status.kind` remain identical, the `FileChange.id` does not change. Consequently Desktop's UI-level guards (`selectedFileIDs` equality, `isSameFile`) will treat the old, now-stale `diff` as still valid and reuse it, or race conditions in `updateChangesWorkingDirectoryDiff`/`_changeFileSelection` will not catch a content swap that happens to preserve `path`+`status.kind`. The stale hunks are then fed into `git apply` to build the next commit or to discard changes — silently committing/discarding content that does not correspond to what is actually visible/intended, without the "existing guards" (which only compare `id`, an identifier that structurally excludes content) ever detecting the mismatch.

This is a plausible but not confirmed exploitable path — I could not find, within the indexed portion of the codebase, a concrete trigger (e.g., a background refresh, submodule checkout, or LFS smudge) that mutates file content between the time a diff is cached and the time `git apply`/discard is invoked while keeping `path`+`status.kind` identical. Given the size limits on the indexed codebase, some relevant files (e.g., background status-refresh scheduling, submodule checkout code paths) may not be fully available to verify a concrete, reliable trigger sequence. A full Devin session with complete repository access would be needed to trace the exact interleaving (refresh timers, submodule update, or LFS pointer resolution) that could realistically desynchronize `diff` content from `file.id` before `git apply` runs.

### Title
Weak path+status-only `FileChange.id` allows stale diff/patch reuse across content changes, risking silent commit/discard corruption - (File: `app/src/models/status.ts`)

### Summary
`FileChange.id` (and its `WorkingDirectoryFileChange`/`CommittedFileChange` subclasses) is derived only from `path` and `status.kind` (+`oldPath` for renames), never from blob content. This identity is the sole check multiple stores/components use to decide whether a previously fetched `diff` can be reused instead of re-fetched, and that same `diff` is later turned into a real patch applied via `git apply` for partial-commit staging and for discarding changes.

### Finding Description
Analogous to the Zebra CVE where a `txid` that excludes authorization data was treated as proof of full-transaction identity, Desktop's `FileChange.id` excludes content (blob oid/size/hash) entirely and is treated as proof that a cached `diff` still matches the file's current content, in `changes-state.ts`, `app-store.ts`, and `seamless-diff-switcher.tsx`.

### Impact Explanation
If content underlying a `WorkingDirectoryFileChange` changes without altering `path`/`status.kind`, cached/stale diff hunks can be reused and fed into `git apply` (`applyPatchToIndex`, `discardChangesFromSelection`), potentially causing the committed content or the discard operation to not match what the user actually intended/reviewed — a silent corruption of what is committed/discarded.

### Likelihood Explanation
Likelihood is uncertain/low-to-moderate: it requires a race where content changes while `path`+`status.kind` stay identical, which is not something ordinary user editing typically produces, and I could not confirm a concrete attacker-triggerable sequence (e.g., background refresh + submodule/LFS content swap) within the available index.

### Recommendation
Incorporate a content-derived component (e.g., blob OID, mtime+size, or diff hash) into the reuse/staleness checks in `updateChangedFiles`, `updateChangesWorkingDirectoryDiff`, `_changeFileSelection`, and `SeamlessDiffSwitcher.isSameFile`/`isSameDiff`, so cached diffs are invalidated whenever underlying content changes even if `path`/`status.kind` remain the same.

### Proof of Concept
Not independently reproduced; conceptual PoC requires: (1) select a working directory file to load and cache its `diff`, (2) mutate the file's underlying content via a background operation that preserves `path` and `status.kind` (candidate: submodule commit change, LFS smudge re-resolution, or an external git process racing with Desktop's status refresh) before the diff-reuse checks re-run, (3) trigger partial stage or discard, and (4) observe that `git apply` uses stale hunks from step 1 against the new content. This last step could not be verified against actual trigger code within the indexed files.

        return

export async function discardChangesFromSelection(

  diff: ITextDiff,
