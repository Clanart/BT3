## Finding

### Title
Unchecked low-level `token.call()` in `IntentGatewayV2.withdraw()`/`onAccept` (Tron) silently "succeeds" against code-less tokens, enabling the classic honeypot false-settlement pattern — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The bug report's core invariant break is: *a token transfer library that reports success without checking that the target address actually has contract code*, letting escrow bookkeeping advance while no value moves. The Tron build of `IntentGatewayV2` reproduces exactly this pattern in its outbound settlement path, `withdraw()`, and in the `SweepDust` handler inside `onAccept`, whereas the canonical EVM contracts (`evm/src/apps/intentsv2/IntentsBase.sol`) use OpenZeppelin's `SafeERC20.safeTransfer`, which explicitly checks `address(token).code.length > 0` before trusting an empty return value as success.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, all *outbound* ERC20 transfers use a raw low-level call instead of `SafeERC20`: [1](#0-0) 

and identically in the dust-sweep branch of `onAccept`: [2](#0-1) 

A low-level `address.call(data)` against an address with no deployed code always returns `success = true` with empty return data — it is indistinguishable from a real ERC20 `transfer` that returned nothing meaningful, because the EVM/TVM never executes any code. `withdraw()` treats that fabricated `success` as proof of a real transfer, then unconditionally decrements the escrow bookkeeping and marks the order as settled: [3](#0-2) 

By contrast, escrow deposits on the *inbound* side of the very same file use OpenZeppelin's `SafeERC20` (`using SafeERC20 for IERC20;`), which internally checks contract-code existence when the low-level call returns empty data — the same fix the original report recommends: [4](#0-3) [5](#0-4) 

So the inbound escrow-funding path is protected, but the outbound settlement path (`withdraw`, called from `onAccept` for both `RedeemEscrow`/`RefundEscrow`) and `SweepDust` are not. The canonical EVM `IntentsBase._withdraw` demonstrates what the protected version looks like — it uses `safeTransfer`, which reverts on a code-less token: [6](#0-5) 

### Impact Explanation
An order placer fully controls `order.inputs[i].token` (validated with `SafeERC20.safeTransferFrom` only at *placement* time, when the token must have code to succeed). If that address's code is later removed — e.g. the placer deploys a malicious token contract that behaves like a normal ERC20 during escrow, then `SELFDESTRUCT`s itself (TVM does not carry EVM's Cancun-era `SELFDESTRUCT` restriction, so this is fully available on Tron) before the order is filled/cancelled — then at settlement time `withdraw()`'s raw `.call()` against the now-code-less address trivially reports success. The contract:
- decrements `_orders[commitment][token]` as if the transfer happened,
- sets `_filled[commitment] = beneficiary`,
- emits `EscrowReleased`/`EscrowRefunded`,

while the beneficiary (the solver who already delivered real output tokens to the user, or the user awaiting a refund) receives **nothing**. This is a false-settlement/loss-of-funds primitive reachable by an unprivileged order placer with no relayer, prover, or admin collusion — matching the bounty's "false state acceptance" and "loss of funds" categories, and it is the direct structural analog of the Solmate honeypot bug (transfer library trusting a call to a non-existent contract as success).

### Likelihood Explanation
Exploitability depends only on the attacker's ability to deploy a self-destructible token contract and time the destruction between order placement and fill/cancellation — both fully within an unprivileged user's control on Tron/TVM. No relayer or governance action is required; the vulnerable code path (`withdraw`) executes automatically whenever `onAccept` processes a `RedeemEscrow`/`RefundEscrow` message. The one constraint is that the beneficiary of the corrupted settlement must be someone the attacker controls (e.g., the attacker is both the order's original user and, via `select`, effectively arranges to be paid) — which is achievable since the order placer chooses their own beneficiary/refund path.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept` with OpenZeppelin's `SafeERC20.safeTransfer` (already imported and used elsewhere in the same file), which reverts when the target has no code and the call returns empty data. Alternatively, explicitly guard every low-level token call with an `require(token.code.length > 0)` check before dispatching, mirroring the mitigation already applied on the inbound `safeTransferFrom` path.

### Proof of Concept
1. Attacker (as `order.user`) deploys `EvilToken`, a fully-compliant ERC20 with an owner-gated `kill()` that calls `selfdestruct`.
2. Attacker calls `placeOrder` with `order.inputs[0].token = EvilToken`, escrow succeeds via `SafeERC20.safeTransferFrom` (token has code) — `_orders[commitment][EvilToken] = amount`.
3. A solver fills the cross-chain order on the destination chain, delivering real output assets to the attacker/beneficiary, and Hyperbridge dispatches `RedeemEscrow` back to the source chain naming the solver as beneficiary.
4. Before the `RedeemEscrow` message is processed, attacker calls `EvilToken.kill()`, removing its code.
5. `onAccept` → `withdraw()` runs: `token.call(transfer(solver, amount))` against the now-code-less `EvilToken` address returns `success = true` trivially; `_orders[commitment][EvilToken] -= amount` proceeds; `EscrowReleased` is emitted.
6. The solver, who already paid out real output tokens, receives zero input tokens — funds are lost and the protocol's on-chain record falsely shows the order as successfully settled.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
