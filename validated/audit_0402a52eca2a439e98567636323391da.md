### Title
Unbounded / cycle-unsafe loop in `object::root_owner()` lets a self-owned code object permanently DoS `code::publish_package` upgrades and `init::internal_maybe_initialize` self-init gating - ([File: aptos-move/framework/aptos-framework/sources/object.move])

### Summary
`object::root_owner()` walks an object's ownership chain with a plain `while (is_object(obj_owner)) { ... }` loop that has **no depth bound and no cycle detection**, unlike its sibling traversal functions `owns()` and `verify_ungated_and_descendant()`, which both enforce `MAXIMUM_OBJECT_NESTING` (8). Since the object model provably allows a self-owned (cyclic) object to be created via `object::transfer`, calling `root_owner()` on such an object loops forever (until gas is exhausted). This function is exactly the one used by the publish/ownership-gating logic in `code::publish_package` and `init::assert_may_self_initialize` to determine code-object ownership for upgrade/self-init authorization, so a cyclic object used as a code object turns those protected-state-mutation paths into a guaranteed-revert DoS.

### Finding Description
`object::root_owner()`:
```move
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
``` [1](#0-0) 

Compare this to `owns()` and `verify_ungated_and_descendant()`, which are the *only* other functions that walk the ownership chain, and both explicitly bound the walk and abort on cycles:
```move
let count = 0;
while (owner != current_address) {
    count += 1;
    assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
    ...
};
``` [2](#0-1) 

The framework's own test suite proves a cyclic (self-owned) object is a reachable, valid on-chain state: the first self-transfer succeeds and only the *second* attempt aborts (because `verify_ungated_and_descendant`'s bounded walk detects the loop):
```move
fun test_cyclic_ownership_transfer_should_fail(creator: &signer) {
    let obj1 = create_simple_object(creator, b"1");
    // This creates a cycle (self-loop) in ownership.
    transfer(creator, obj1, obj1.object_address());
    // This should fails as the ownership is cyclic.
    transfer(creator, obj1, obj1.object_address());
}
``` [3](#0-2) 

`transfer_raw` only verifies that the *destination* is currently, transitively owned by the caller (`verify_ungated_and_descendant(owner_address, object)`) before flipping `ObjectCore.owner`; it never checks whether the *transferred object itself* would become part of a cycle: [4](#0-3) 

So an object owner can legally set `ObjectCore.owner == self` (or a longer cycle through several objects they control) in one transaction, since at that moment the check only requires the destination to already resolve back to the signer, which is trivially true for a self-transfer.

`root_owner()` is exactly what the newly added lazy-module-initialization / code-object-ownership guard relies on:
- In `code::publish_package`, on every (re)publish to an object address, it records `root_owner()` as the authorized owner for self-init:
```move
if (features::is_lazy_module_initialization_enabled() && object::is_object(addr)) {
    let owner = object::address_to_object<object::ObjectCore>(addr).root_owner();
    module_names.for_each_ref(|name| {
        init::record_deploy_owner(addr, *name.bytes(), owner);
    });
};
``` [5](#0-4) 

- In `init::assert_may_self_initialize`, invoked from `init::internal_maybe_initialize` on essentially every call into a module that uses lazy self-init, it re-derives `root_owner()` and compares it to the recorded value:
```move
fun assert_may_self_initialize(addr: address, module_id: ModuleId) {
    let recorded = recorded_deploy_owner(addr, module_id);
    let ok = if (recorded.is_some()) {
        object::is_object(addr)
            && recorded.destroy_some() == object::address_to_object<ObjectCore>(addr).root_owner()
    } else {
        !object::is_object(addr)
    };
    assert!(ok, error::permission_denied(EOWNER_CHANGED_SINCE_DEPLOY));
}
``` [6](#0-5) 
called from `internal_maybe_initialize`: [7](#0-6) 

If an object anywhere in the ownership chain of a deployed code object (the code object itself, or any ancestor object still reachable via `is_object`) is turned into a self-referencing/cyclic owner, both of these code paths hit an unbounded loop:
- `code::publish_package` (i.e. any future upgrade attempt through `object_code_deployment::upgrade` / `large_packages::upgrade_object_code`) will spin in `root_owner()` until gas runs out, so the package can never be upgraded or frozen again.
- Any entry function on that module that calls `init::internal_maybe_initialize` (used by essentially any module opting into lazy self-init, including on ordinary user calls, not just owner calls) will likewise burn gas without terminating, denying service to every caller of that entry point, not just the object owner.

### Impact Explanation
This breaks a code-safety invariant central to Aptos's object-based code-object publish model: `root_owner()` is the sole primitive used to decide (a) who is authorized to complete self-initialization of freshly-deployed/upgraded module code, and (b) what owner value is durably recorded to gate that self-init across future upgrades. An unbounded loop in this primitive converts a legal, framework-acknowledged on-chain state (cyclic object ownership, already demonstrated by the framework's own unit test) into a guaranteed out-of-gas failure for:
- The upgrade/publish path (`code::publish_package`) for any code object whose (or whose ancestor's) ownership becomes cyclic — permanently bricking upgrade/freeze capability for that on-chain code object.
- The lazily-initialized module's self-init gate (`init::internal_maybe_initialize`), which runs on ordinary entry-function calls from arbitrary users, not only the object owner — a denial of service against any consumer of that module.

Because this sits directly in the object-code-deployment / init gating machinery that decides code ownership and upgrade authority (explicitly called out in the "Publish Pivots" as an area requiring loader/object ownership correctness), and it can permanently and irreversibly disable upgrade/freeze/init on a mainnet-relevant contract, this is a high-severity denial-of-service against protected publish-path state.

### Likelihood Explanation
Triggering the state is straightforward and requires only ordinary permissions: any account that owns an object (including one it intends to, or already did, use for code-object deployment via `object_code_deployment::publish`) can call the public entry function `object::transfer` (or `transfer_to_object`) with `to` equal to the object's own address, which is proven to succeed by the framework's own `test_cyclic_ownership_transfer_should_fail` test (the first self-transfer call in that test succeeds without abort). No governance or privileged role is required; a single unprivileged transaction creates the hazard, after which any subsequent upgrade or lazily-initializing call against that object permanently fails.

### Recommendation
Add the same bounded/cycle-safe traversal used in `owns()`/`verify_ungated_and_descendant()` to `root_owner()`:
```move
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    let count = 0;
    while (is_object(obj_owner)) {
        count += 1;
        assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```
Additionally, consider rejecting self-referential/cyclic transfers outright in `transfer_raw`/`verify_ungated_and_descendant` (e.g., disallow `to == object` and detect that the object being moved does not already appear in its own new ownership chain), rather than only detecting the cycle on a subsequent transfer attempt.

### Proof of Concept
1. Deploy a code object via `object_code_deployment::publish` with the `LAZY_MODULE_INITIALIZATION` feature enabled, so `code::publish_package` records `deploy_owner` via `root_owner()` [5](#0-4) .
2. As the object owner, call `object::transfer(owner, code_object, code_object_address)` (self-transfer). This succeeds, per the framework's own test [3](#0-2) , setting `ObjectCore.owner == code_object_address` (self-cycle).
3. Any subsequent call to `object_code_deployment::upgrade` (which calls `code::publish_package_txn` → `root_owner()`) or any user call into the module's entry function that calls `init::internal_maybe_initialize` → `assert_may_self_initialize` → `root_owner()` [6](#0-5)  now loops on `while (is_object(obj_owner))` forever, since `obj_owner` never changes and `is_object` remains true, exhausting gas and aborting every such transaction — permanently denying upgrade and self-init for that code object.
