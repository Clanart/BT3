### Title
Division-by-zero panic in KIP-71 base fee calculation when governance sets `kip71.gastarget` to 0 - (File: `params/kip71_config.go`)

### Summary
`NextMagmaBlockBaseFee` computes the dynamic base fee using `kc.GasTarget` as a divisor in two branches (gas used above/below target), but unlike `BaseFeeDenominator`, there is no zero-value fallback for `GasTarget`. The corresponding governance parameter `Kip71GasTarget` uses a `noopFormatChecker` that accepts any `uint64` value, including `0`.

### Finding Description
`NextMagmaBlockBaseFee` in `params/kip71_config.go` divides by `gasTarget` twice: once when `parentGasUsed > gasTarget` (line 102: `y := x.Div(x, new(big.Int).SetUint64(gasTarget))`) and once when `parentGasUsed < gasTarget` (line 120, same pattern) [3](#0-2) . The code explicitly guards against a zero `BaseFeeDenominator` with a fallback value of `64` ("To avoid panic, set the fluctuation range small") [2](#0-1) , but applies no equivalent guard for `GasTarget`.

The governance parameter registry entry for `Kip71GasTarget` uses `noopFormatChecker`, in contrast to `Kip71BaseFeeDenominator`, which explicitly requires `v != 0` [1](#0-0) . This means a governance vote (submitted as a normal governance transaction/header vote, reachable by the governing node/council per the chain's governance mode) can set `governance.kip71.gastarget` to `0`, which will be canonicalized to `uint64(0)` and accepted without rejection.

Once such a value takes effect at the next epoch, every block header's `BaseFee` is computed via `NextMagmaBlockBaseFee`, which is invoked both when generating the block (worker/miner) and when verifying it (`VerifyMagmaHeader`) [4](#0-3) . If `parentGasUsed != gasTarget` (which will be true for essentially any block since `gasTarget == 0` almost never equals actual usage), the code proceeds into the `Div` call with `gasTarget = 0`, causing a `runtime panic: division by zero` inside Go's `math/big` package.

### Impact Explanation
A panic during block production or block header verification crashes/halts the node process performing that operation. Since `NextMagmaBlockBaseFee` is deterministic and consensus-critical (used both to propose a block's `BaseFee` and to verify it), a governance vote lowering `GasTarget` to `0` would cause **all nodes** on the network to panic when processing the block after the parameter activates, effectively halting the chain. This is a severe availability/liveness impact reachable through a normal governance parameter update.

### Likelihood Explanation
Likelihood depends on governance being willing/able to submit a `governance.kip71.gastarget = 0` vote (or a similar chain of validator votes under `ballot` mode). Because the format checker performs no validation (`noopFormatChecker`), there's no automatic rejection at proposal, submission, or activation time — a single successful vote (accidental misconfiguration or malicious governance action) is sufficient to trigger the fault chain-wide once it activates.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`/`Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` where relevant) in `kaiax/gov/param.go` that rejects `0`, mirroring the `Kip71BaseFeeDenominator` check [5](#0-4) . Additionally, add a defensive zero-check inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` analogous to the existing `BaseFeeDenominator` fallback, so that even if a zero value slips through, the node degrades gracefully instead of panicking.

### Proof of Concept
1. Under `ballot`/governing-node governance mode, submit and pass a governance vote setting `kip71.gastarget` (`governance.GasTarget`) to `0`.
2. Once the vote activates at the next epoch, propose or verify any block where `parentGasUsed != 0` (virtually guaranteed).
3. `NextMagmaBlockBaseFee` executes `gasUsedDelta := ... ; x := new(big.Int).Mul(parentBaseFee, gasUsedDelta); y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0` [3](#0-2) , causing `math/big.(*Int).Div` to panic with a division-by-zero error, crashing the node process during block assembly/verification for every CN on the network.

	}
	return nil
}
