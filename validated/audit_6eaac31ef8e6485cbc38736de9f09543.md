### Title
Unconditional `UPDATE withdrawals SET withdrawal_utxo_txid, withdrawal_utxo_vout WHERE idx=$1` allows the same withdrawal outpoint to be bound to multiple `idx` rows - (File: `core/src/database/verifier.rs`)

### Summary
`Database::update_withdrawal_utxo_from_citrea_withdrawal` writes an attacker-controlled `OutPoint` into the `withdrawals` row for a given Citrea `idx` with no check that the outpoint is already bound to a different `idx`. Since the withdrawal UTXO bytes are fully attacker-controlled (the attacker calls Citrea `withdraw` and chooses the outpoint), an attacker can register the same outpoint for two distinct withdrawal indices, breaking the intended 1:1 binding between a fronted UTXO and a reimbursable index.

### Finding Description
The binding that must hold is: for outpoint `O`, `count({ idx : withdrawals.idx bound to O })` must equal `1` (the number of times `O` was actually fronted). The write path is: [1](#0-0) 

This `UPDATE ... WHERE idx = $1` query has no `WHERE NOT EXISTS (SELECT 1 FROM withdrawals WHERE withdrawal_utxo_txid=$2 AND withdrawal_utxo_vout=$3)` guard, no `RETURNING` check against pre-existing rows holding the same outpoint, and there is no unique index/constraint enforced at the query layer on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`. Calling it twice with distinct `idx` values (`i`, `j`) and the identical `OutPoint` succeeds silently both times, leaving two rows in `withdrawals` pointing at the same UTXO.

This function is invoked from `Verifier::update_citrea_deposit_and_withdrawals` for each new Citrea withdrawal event ingested; the attacker fully controls "the bytes of a withdrawal UTXO" per the threat model, so they can call Citrea's `withdraw` with `withdrawal_id=j` and reuse the outpoint bytes already registered under `withdrawal_id=i`.

The consequence is directly observable in the same file: `get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` purely on `(txid, vout)`: [2](#0-1) 

Because the join key is the outpoint and not a unique claim relationship, a single real Bitcoin spend of `O` will match every `idx` row bound to `O`, and `update_payout_txs_and_payer_operator_xonly_pk` will then mark all of those `idx` rows as paid out from a single physical payout: [3](#0-2) 

No guard in `Verifier::is_deposit_valid`, `SECP.verify_schnorr`, `verify_storage_proofs`, or any presigned-transaction check inspects cross-index outpoint uniqueness — those checks operate on deposit scripts/signatures, not on withdrawal-outpoint uniqueness across `idx`.

### Impact Explanation
Once one outpoint is bound to two indices, a single fronted withdrawal payout can later be attributed to two reimbursable indices (the downstream mechanism, per the linked join-bug question, is `get_payout_txs_for_withdrawal_utxos`/`update_payout_txs_and_payer_operator_xonly_pk` shown above). This lets an operator (or two operators) claim reimbursement for a move-to-vault UTXO that was never independently fronted for that specific index, matching the Critical category "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" / "an operator reimbursed for a payout it never funded." The blast radius is per-outpoint and repeatable across any number of withdrawal indices the attacker chooses to collide, and is not limited to one deposit/operator.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to have caused (via a legitimate first withdrawal) an outpoint `O` to be registered at `idx=i`, then call Citrea's `withdraw` again with a new `withdrawal_id=j` reusing the same outpoint bytes before any payout is finalized. This requires no verifier/operator/aggregator privilege, only the ability to call the public Citrea bridge contract `withdraw` function, which is explicitly within the attacker's granted capabilities. Cost is limited to whatever Citrea-side fee/deposit is required to register a withdrawal, no Bitcoin fees are needed for this specific write since it is only a Citrea event ingestion into the verifier's local database.

### Recommendation
Add a database-level uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table (excluding NULLs), and/or change `update_withdrawal_utxo_from_citrea_withdrawal` to a conditional write (e.g. `WHERE idx = $1 AND NOT EXISTS (SELECT 1 FROM withdrawals w2 WHERE w2.withdrawal_utxo_txid = $2 AND w2.withdrawal_utxo_vout = $3 AND w2.idx <> $1)`) and return an explicit error when the outpoint is already claimed by a different `idx`.

### Proof of Concept
```rust
#[tokio::test]
async fn duplicate_withdrawal_utxo_across_two_indices_is_accepted() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();
    let mut dbtx = db.begin_transaction().await.unwrap();

    let idx_i = 1u32;
    let idx_j = 2u32;
    let shared_outpoint = bitcoin::OutPoint {
        txid: bitcoin::Txid::from_byte_array([0xAA; 32]),
        vout: 0,
    };

    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_i, &bitcoin::Txid::from_byte_array([0x01; 32])).await.unwrap();
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_j, &bitcoin::Txid::from_byte_array([0x02; 32])).await.unwrap();

    // First registration: idx_i bound to shared_outpoint
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_i, shared_outpoint, 0).await.unwrap();

    // Attacker re-registers the SAME outpoint for a different idx_j
    let result = db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_j, shared_outpoint, 0).await;

    // Currently succeeds with no error/dedup — this is the bug.
    assert!(result.is_ok());

    let utxo_i = db.get_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_i).await.unwrap();
    let utxo_j = db.get_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_j).await.unwrap();

    // Binding violated: two distinct idx rows are bound to the same outpoint.
    assert_eq!(utxo_i, shared_outpoint);
    assert_eq!(utxo_j, shared_outpoint);
    assert_eq!(utxo_i, utxo_j); // demonstrates the many-to-one mapping
}
```
A fixed implementation should make the second `update_withdrawal_utxo_from_citrea_withdrawal` call return `Err(...)` (uniqueness violation), causing this test's `assert!(result.is_ok())` to fail instead.

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
