## Title
App Proxy signed requests have no timestamp/staleness check, enabling indefinite replay of captured proxy URLs - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` verifies only that the HMAC `signature` parameter matches the recomputed signature over the query string. The query string always contains a `timestamp` parameter (per Shopify's app proxy signing scheme), but that value is included only as signed *data* — it is never compared against the current time to reject old requests. This mirrors the reported oracle bug class: a timestamp field exists in the verified payload, but the code never uses it to bound the acceptable age of the data/signature, so a validly-signed-but-stale artifact is accepted forever.

### Finding Description
`query_string_valid?` deletes the `signature` key, recomputes the HMAC over the remaining sorted parameters (including `timestamp`), and does a secure comparison against the request-provided signature: [1](#0-0) 

Nowhere in this concern — or in `verify_proxy_request` which gates all app-proxy actions — is `timestamp` checked against `Time.now` or any acceptable drift window: [2](#0-1) 

Since the signature is computed purely from the query parameters (shop, path_prefix, timestamp, etc.) with the merchant's shared secret, any URL that was ever validly generated by Shopify for this app proxy remains valid forever as far as this code is concerned — there is no expiry, nonce, or freshness enforcement. This is confirmed by the test suite, which only asserts correctness of the HMAC comparison logic and never exercises an "expired timestamp" rejection path: [3](#0-2) 

The check is structurally identical to the reported bug: a timestamp is present in the verified data, but the code treats "signature matches" as sufficient, without validating "was this recent enough."

### Impact Explanation
An app-proxy URL/query string that leaks (browser history, server access logs, Referer headers, shared screenshots, proxy/CDN logs, or a compromised intermediate) can be replayed by any anonymous requester indefinitely to invoke the app proxy endpoint as if it were a fresh, legitimate Shopify-forwarded storefront request. If the proxy action has any side effects tied to the (shop, path_prefix) pair, or if downstream code trusts the "verified" request as freshly originated from Shopify, this enables unauthorized replay against an unrelated request context long after the original request should have expired.

### Likelihood Explanation
Exploitation requires only capturing one previously-valid, signed app-proxy query string (no secret compromise, no privileged access) — a realistic bar for logs/referrers/history — and no mitigation exists in-repo to detect staleness. Likelihood is Medium because impact depends on what the specific app's proxy action does with the (unbounded) replay.

### Recommendation
Reject requests where `timestamp` is missing or older than an acceptable window (analogous to the bug report's recommendation to check `block.timestamp - updatedAt` against an asset/endpoint-specific heartbeat), e.g.:
```ruby
def query_string_valid?(query_string)
  query_hash = Rack::Utils.parse_query(query_string)
  signature = query_hash.delete("signature")
  return false if signature.nil?
  timestamp = query_hash["timestamp"].to_i
  return false if timestamp.zero? || (Time.now.to_i - timestamp) > MAX_ALLOWED_DRIFT

  ActiveSupport::SecurityUtils.secure_compare(calculated_signature(query_hash), signature)
end
```

### Proof of Concept
1. Capture any legitimately-signed app proxy query string once (e.g., `shop=store.myshopify.com&path_prefix=/apps/my-app&timestamp=1466106083&signature=...`), as demonstrated by the existing valid-signature test fixture: [3](#0-2) 
2. Replay the exact same query string against the app's proxy endpoint at any later time (days, months, years later).
3. `query_string_valid?` recomputes the same HMAC and returns `true` because `timestamp` is never compared to the current time — `verify_proxy_request` allows the request through with no staleness rejection: [4](#0-3)
