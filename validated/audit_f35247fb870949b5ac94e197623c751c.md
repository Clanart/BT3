### Title
`ThresholdKeys::read` deserializes attacker-controlled shares/verification-shares without ever checking their consistency, letting a crafted "backup" import install a group key the rightful participants cannot spend (or that the importer controls) - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` is the restore/import path for threshold key material. It reads `t`, `n`, `i`, the interpolation mode (including arbitrary `Interpolation::Constant` coefficients), the scalar `secret_share`, and all `n` `verification_shares` straight from the byte stream, then passes them to `ThresholdKeys::new`. `new` only checks *structural* invariants — share count equals `n`, participant indexes `<= n`, `t == n` for `Constant` — and derives `group_key` as `sum_{i=1..=t} V_i * factor(i)`. It never checks the fundamental DKG invariant that `secret_share * G == verification_shares[i]`, nor that the `Constant` coefficients are the actual MuSig binding factors. This is exactly the LXD bug class: an import path applies fields that the normal generation path establishes via protocol verification, without re-validating them. The FROST crate itself acknowledges this gap: `crypto/frost/src/sign.rs:492-494` comments that "the only known way to cause this... is to deserialize a semantically invalid FrostKeys". ### Finding Description
The serialization in `write` (crypto/dkg/src/lib.rs:538-562) emits every field verbatim with no checksum, no proof, and no binding between `secret_share` and `verification_shares[i]`. `read` then:
- reads `secret_share` via `C::read_F` — canonical encoding checked, but never its correspondence to `verification_shares[i]` (lib.rs:618);
- reads `n` arbitrary points into `verification_shares` (lib.rs:620-623);
- for `Interpolation::Constant`, reads `n` arbitrary scalar coefficients with no check that they equal the MuSig `binding_factor` values computed in `musig_key_multiexp` (lib.rs:607-613; crypto/dkg/musig/src/lib.rs:139-151);
- computes `group_key` solely from `verification_shares[1..=t]` (lib.rs:376-378).

The `view()` path then interpolates `secret_share` and offsets `included[0]` with no further consistency check (lib.rs:463-533), so an inconsistent secret share is only discovered at signature-aggregation time — after group key/address commitments have already been made. Downstream, `GeneratedKeysDb::read_keys` (processor/src/key_gen.rs:50-63) feeds stored bytes directly into `ThresholdKeys::read` and uses `group_key()` to index the keys (key_gen.rs:79-80), so a crafted blob becomes the node's live wallet key set. ### Impact Explanation
An attacker who supplies the serialized blob can fully dictate `group_key` while presenting `i`, `t`, `n` that pass all checks:
- Set `verification_shares[1..=t]` to attacker-known points (e.g., `G * a_i` with chosen `a_i`) so `group_key` has a discrete log known to the attacker. Deposits sent to the resulting address are spendable by the attacker, not by the threshold — "funds reported received that are not spendable" by the rightful set.
- Set `secret_share` to an attacker-chosen scalar unrelated to `verification_shares[i]` (e.g., for MuSig/`Constant` keys). The victim produces signature shares that fail `verify_share`, causing the victim's own share to be blamed in `complete()` (sign.rs:476-488) and making the key unusable.
Both outcomes require no protocol participation: every check in `new`/`read` passes because consistency between fields is simply never validated.

### Likelihood Explanation
Reachability depends on the attacker controlling bytes fed to `ThresholdKeys::read` — the same threat model as the LXD report (a crafted backup/snapshot blob imported by a privileged-but-restricted operator). Unlike the creation path (`PedPoP::calculate_share`, `musig`), which cryptographically verifies every share against commitments, the restore path trusts the blob. Any import/restore/migration flow or tampered key store reaches it.

### Recommendation
In `ThresholdKeys::read` (or `new`), verify `C::generator() * secret_share == verification_shares[&params.i()]`. For `Interpolation::Constant`, either document that coefficients are trusted state or recompute them from `(context, keys)` where available; at minimum hash the serialized blob or store a MAC/commitment (e.g., hash of `group_key || secret_share`) so a tampered restore is detected before keys are indexed by `group_key()`.

### Proof of Concept
```rust
// Any curve, e.g. Ristretto / kp256 curve used by ThresholdKeys<C>
// Attacker crafts a serialized ThresholdKeys blob where the group key
// is fully attacker-controlled and all structural checks pass.

// t = 2, n = 3, Lagrange. Attacker picks scalars a1, a2 and sets
// V1 = G*a1, V2 = G*a2, V3 = anything. Then:
//   group_key = V1*λ1 + V2*λ2  (over included = {1,2})
// Lagrange factors for {1,2}: λ1 = 2, λ2 = -1
// => group_key = 2*V1 - V2 = G*(2*a1 - a2)  <- attacker knows the log.

let a1 = C::random_nonzero_F(&mut rng);
let a2 = C::random_nonzero_F(&mut rng);
let attacker_secret = F::from(2u64) * a1 - a2; // attacker knows discrete log of group_key

let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(2u16.to_le_bytes());              // t
blob.extend(3u16.to_le_bytes());              // n
blob.extend(1u16.to_le_bytes());              // i = participant 1
blob.push(1);                                 // Interpolation::Lagrange
blob.extend(a1.to_repr().as_ref());           // secret_share = a1 (consistent with V1)
for v in [
  C::generator() * a1,                        // V1
  C::generator() * a2,                        // V2
  C::generator() * C::random_nonzero_F(&mut rng), // V3
] {
  blob.extend(v.to_bytes().as_ref());
}

// Import: passes ThresholdParams::new and all ThresholdKeys::new checks
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
assert_eq!(keys.group_key(), C::generator() * attacker_secret);
// The resulting group_key is registered/used as the multisig address
// (GeneratedKeysDb::read_keys keys the DB by group_key), yet the
// threshold of honest participants does not control it — the attacker does.
```

```rust
      let mut id_len = [0; 4];

      if u32::try_from(C::ID.len()).unwrap().to_le_bytes() != id_len {
        Err(different())?;
      }

      let mut id = vec![0; C::ID.len()];
      reader.read_exact(&mut id)?;
      if id != C::ID {
        Err(different())?;
      }
    }

    let (t, n, i) = {
      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
    let interpolation = match interpolation[0] {
      0 => Interpolation::Constant({
        let mut res = Vec::with_capacity(usize::from(n));
        for _ in 0 .. n {
          res.push(C::read_F(reader)?);
        }
        res
      }),
      1 => Interpolation::Lagrange,
      _ => Err(io::Error::other("invalid interpolation method"))?,
    };

    let secret_share = Zeroizing::new(C::read_F(reader)?);

    let mut verification_shares = HashMap::new();

      verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
    }

    ThresholdKeys::new(
      ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
      interpolation,
      secret_share,
      verification_shares,
    )
    .map_err(io::Error::other)
```
