### Title
Concurrent index side-effect operations (AI commit-message generation vs. commit) can silently corrupt the committed diff - ([File: app/src/lib/git/diff.ts])

### Summary
The `vyperlang/vyper` advisory describes a class of bug where an operation performs multiple side-effecting sub-steps that another concurrent/dependent operation relies on, and when the order of those side effects is wrong, the final on-chain state doesn't match what the code appeared to compute. In GitHub Desktop, the closest analog is a git-index race: `getFilesDiffText` (used to build the diff sent to Copilot for commit-message generation) and `createCommit` (used to actually commit) both perform the *same* multi-step sequence of side effects against the shared git index (`unstageAll` → `stageFiles` → git command → optionally `unstageAll` again), but the two call paths are protected by two **independent, non-overlapping** mutex flags (`isGeneratingCommitMessage` and `isCommitting`). Nothing prevents both flows from running concurrently, so their index-mutating steps can interleave in an order the code never intended, corrupting what actually gets staged/committed.

### Finding Description
`getFilesDiffText` mutates the shared git index as a side effect of computing a diff to feed to Copilot: [1](#0-0) 

It does: `unstageAll(repository)` → `stageFiles(repository, files)` → `git diff --staged` → `unstageAll(repository)` again — leaving the index in a "clean" state when done.

`createCommit` performs the analogous sequence for an actual commit: [2](#0-1) 

`await unstageAll(repository)` then `await stageFiles(repository, files)`, followed by `git commit`.

`_generateCommitMessage` (invoked when the user clicks "Generate Commit Message with Copilot") calls `getFilesDiffText` and is guarded only by its own flag: [3](#0-2) 

`_commitIncludedChanges` (invoked when the user clicks "Commit") calls `createCommit` and is guarded only by a *different* flag: [4](#0-3) [5](#0-4) 

`withIsCommitting` only rejects a second call if `state.isCommitting` is already `true`; it says nothing about `isGeneratingCommitMessage`, and vice versa. Because these are two separate boolean flags in `repositoryStateCache`, the app has **no single mutex covering all git-index-mutating working-directory operations**. If a user selects files, clicks "Generate Commit Message with Copilot" and then — before that async chain (which spans a Copilot API network round trip and several `await`s) finishes — clicks "Commit" (possible because the commit button’s enabled state is derived from render-time props/state and the flag transitions happen asynchronously across `await` boundaries, not synchronously with the click), both async chains proceed to call `unstageAll`/`stageFiles` on the same repository’s index without coordination.

The UI-level `enabled` check for the "Generate commit message" menu item only inspects `isCommitting`/`isGeneratingCommitMessage` at render time: [6](#0-5) 

but the underlying `_generateCommitMessage`/`_commitIncludedChanges` calls in `app-store.ts` do not re-validate against each other's flag before touching the index — each only checks its own. This is the same broken invariant as the report: multiple steps with observable side effects (staging/unstaging the index) are assumed to execute in a fixed, non-interleaved order, but nothing in the code enforces that across the two independent operations.

### Impact Explanation
`stageFiles`/`unstageAll` operate on the shared `.git/index` for the whole repository, not a private, isolated copy. If the commit-message-generation flow's `unstageAll`/`stageFiles(files selected for the diff)` interleaves with the commit flow's `unstageAll`/`stageFiles(selectedFiles)`/`git commit`, the final index state at the moment `git commit` runs can reflect a partial or entirely different set of staged files than what the user selected in the Changes list — i.e., the commit created can silently include files/changes the user did not intend to commit (or omit ones they did), because the two flows' `unstageAll` calls can wipe out staging performed by the other flow between its `stageFiles` and its final git invocation. This is a "silent corruption of what the user commits" — the exact class of harm the report focuses on (a downstream consumer of an operation depending on side effects that happened in the wrong order/interleaving).

### Likelihood Explanation
Likelihood is limited by timing: both flows are asynchronous chains with multiple `await` points (network calls, multiple git invocations), which is exactly the kind of window that makes races like this practically triggerable — a user or a scripted UI-automation sequence rapidly invoking "Generate Commit Message" then "Commit" (or vice versa) within that window is plausible without any special privileges. It does not require an attacker to control the repository content, only ordinary user interaction with the existing feature set (working directory + Copilot commit-message generation), which is within the intended usage of Desktop. I could not verify from static inspection alone whether there's an additional guard elsewhere (e.g., disabling both buttons app-wide during either operation) that fully closes this window — the code inspected only shows two independent flags with no cross-check, but a live/dynamic test would be needed to confirm the race is reliably triggerable in the shipped UI.

### Recommendation
- Merge `isCommitting` and `isGeneratingCommitMessage` (and any other flow that mutates the shared index, e.g. `getFilesDiffText` callers) into a single per-repository mutex (e.g., `isWorkingDirectoryBusy`) so that starting one index-mutating operation is rejected while another is in flight, regardless of which specific operation set the flag.
- Alternatively, make `getFilesDiffText` non-destructive to the shared index (e.g., use a temporary index file via `GIT_INDEX_FILE`, or `git diff` against a constructed tree object) so it never needs to call `unstageAll`/`stageFiles` against the repository's real index at all.
- Add an explicit check in `_commitIncludedChanges` (and `_generateCommitMessage`) that rejects/queues the operation if the other flag is set, rather than only checking its own flag.

### Proof of Concept
1. Open a repository with an authenticated Copilot-enabled account and several changed files in the Changes list.
2. Select a subset of files to commit.
3. Click "Generate commit message with Copilot" — this starts `_generateCommitMessage` → `getFilesDiffText`, which begins `unstageAll` then `stageFiles(filesSelected)`.
4. Immediately (within the async window before `isGeneratingCommitMessage` transitions are reflected and before the diff round-trip to Copilot completes) trigger "Commit" — this starts `_commitIncludedChanges` → `createCommit`, which independently calls `unstageAll` then `stageFiles(selectedFiles)` then `git commit`.
5. Because neither flow checks the other's busy flag, their `unstageAll`/`stageFiles` calls interleave on the shared index; depending on scheduling, `createCommit`'s final `git commit` can run right after `getFilesDiffText`'s trailing `unstageAll`, producing an empty or partial commit relative to what the user selected — or `getFilesDiffText`'s `stageFiles` can leave unintended files staged that get swept into the commit.

Note: I was not able to execute this scenario live (no runtime/browser access in this environment); the analysis is based on static review of the two independent mutex flags and the shared, mutating `stageFiles`/`unstageAll` calls in both code paths. A Devin session with full repo/runtime access would be needed to confirm the exact interleaving and reproduce a corrupted commit end-to-end.

export async function getFilesDiffText(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  commitish?: string
): Promise<string> {
  // Clear the staging area, our diffs reflect the difference between the
  // working directory and the last commit (if any) so our commits should
  // do the same thing.
  await unstageAll(repository)

  await stageFiles(repository, files)

  // `--no-ext-diff` should be provided wherever we invoke `git diff` so that any
  // diff.external program configured by the user is ignored
  const args = [
    'diff',
    '--no-ext-diff',
    '--patch-with-raw',
    '--no-color',
    '--staged',
    ...(commitish ? [commitish] : []),
  ]
  const successExitCodes = new Set([0])

  const { stdout } = await git(args, repository.path, 'getFilesDiffText', {
    successExitCodes,
    encoding: 'buffer',
  })

  await unstageAll(repository)

  private async withIsCommitting(
    repository: Repository,
    fn: () => Promise<boolean>
  ): Promise<boolean> {
    const state = this.repositoryStateCache.get(repository)
    // ensure the user doesn't try and commit again
    if (state.isCommitting) {
      return false
    }

    this.repositoryStateCache.update(repository, () => ({
      isCommitting: true,
      hookProgress: null,
      subscribeToCommitOutput: null,
    }))
    this.emitUpdate()

    try {
      return await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isCommitting: false,
        hookProgress: null,
        subscribeToCommitOutput: null,
      }))
      this.emitUpdate()
    }
  }

  private async withIsGeneratingCommitMessage(
    repository: Repository,
    fn: (signal: AbortSignal) => Promise<boolean>
  ): Promise<boolean> {
    const state = this.repositoryStateCache.get(repository)
    // ensure the user doesn't try and commit again
    if (state.isGeneratingCommitMessage) {
      return false
    }

    const abortController = new AbortController()

    this.repositoryStateCache.update(repository, () => ({
      isGeneratingCommitMessage: true,
      commitMessageGenerationAbortController: abortController,
    }))
    this.emitUpdate()

    try {
      return await fn(abortController.signal)
    } finally {
      const currentState = this.repositoryStateCache.get(repository)
      if (
        currentState.commitMessageGenerationAbortController === abortController
      ) {
        this.repositoryStateCache.update(repository, () => ({
          isGeneratingCommitMessage: false,
          commitMessageGenerationAbortController: null,
        }))
        this.emitUpdate()
      }
    }
  }
