## Title
Arbitrary `(app_chain, app)` targeting in `pallet-bandwidth::on_accept` lets an unprivileged purchaser evict another app's already-paid bandwidth via FIFO cap eviction - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
The external report's core primitive is: an attacker cheaply and repeatedly allocates entries in a bounded resource that only gets deallocated through specific paths the attacker can avoid, exhausting the resource for legitimate users. In Hyperbridge's `pallet-bandwidth`, the FIFO subscription list per `(app_chain, app)` is capped at `MAX_SUBSCRIPTIONS` (1024) and evicts the *oldest* entry once full [1](#0-0) . Because the `app_chain`/`app` key that a purchase credits is taken entirely from the attacker-supplied purchase message body rather than from any caller-owned identity, any party able to call the legitimate `BandwidthManager.purchase()` can target a victim app's bucket directly and force-evict its unexpired, already-paid-for subscription.

### Finding Description
`on_accept` authenticates only that the POST request's `from` matches the registered `BandwidthManager` contract for the source chain — it does not authenticate or restrict which `(chain, app)` bucket the purchase credits: [2](#0-1) 

The `msg.chain` and `msg.app` fields are decoded straight from the purchase body and passed into `push_subscription`, which is documented (by design, for the "sponsorship" feature) to key storage by the payload's `app_chain`, not by `request.source`: [3](#0-2) 

`push_subscription` appends unconditionally to the FIFO `Allowance` list, and when the list is already at the 1024 cap it evicts index 0 — the oldest surviving entry — regardless of who purchased it or how much of its `remaining_bytes` is unused: [1](#0-0) 

Because there is no per-purchaser restriction tying a credit to the app being credited (this is intentional to support cross-chain sponsorship), an attacker only needs enough fee-token funds to buy the cheapest configured tier (`TierOne`, potentially `months = 1`) repeatedly, targeting a victim's `(app_chain, app)` key 1024 times, to push out the victim's real, unexpired, previously-paid subscription — destroying funds/bandwidth the victim already paid for. This directly satisfies `SubscriptionEvicted { lost_bytes }`, which the pallet's own docs describe as bytes "the user paid for and won't get to use" [4](#0-3) .

The existing guards — `UnknownManager`/`request.from` check, tier configuration checks — only validate that the *purchase* itself is legitimate; none of them constrain *whose* bucket a legitimate purchase can target, so they do not stop this path.

### Impact Explanation
This is a "loss of funds" / "wrong beneficiary" style bug rather than a generic DoS: a paying app can have its already-purchased, unexpired bandwidth silently destroyed by a third party who never interacted with that app, at a cost proportional only to the cheapest tier × the small number of purchases needed to reach the 1024-entry cap (much smaller if the victim's queue already has entries). The victim then experiences message rejection (`GateError::NoAllowance`/`Insufficient`) despite having paid, which can halt their cross-chain message flow.

### Likelihood Explanation
Any unprivileged account with fee tokens can call the public, permissionless `BandwidthManager.purchase()` on the legitimate manager contract and freely choose the `app`/`chain` target in the payload — no admin, relayer, or prover compromise is required. The FIFO cap of 1024 with pure oldest-first eviction, combined with the tiered pricing (cheapest tier is explicitly cheaper per byte), makes this an economically realistic griefing/theft vector against any actively-used app that keeps a modest queue of subscriptions.

### Recommendation
Bind purchase eligibility to the target so an attacker cannot cheaply out-evict a victim's real subscriptions: e.g., require the crediting purchase's payer/source to match (or be authorized by) the `app` being credited except through a governance-gated sponsorship allowlist, or switch eviction policy to protect entries with meaningfully remaining `remaining_bytes`/`expires_at` rather than pure FIFO oldest-first, or scale the cap / add a minimum-value threshold per evictable entry so cheap tier-one purchases cannot displace larger paid allowances.

### Proof of Concept
1. Victim app `A` on chain `X` has, say, 5 active subscriptions purchased over time via `BandwidthManager.purchase()`, each with significant `remaining_bytes` and a future `expires_at`.
2. Attacker, with no relationship to app `A`, calls the same legitimate `BandwidthManager.purchase()` contract 1024 times (or enough times to exceed remaining headroom in `A`'s queue), each time setting the purchase payload's `chain`/`app` fields to `A`'s `(app_chain, app)` key and using the cheapest configured tier with `months = 1`.
3. Each purchase message is routed to `pallet-bandwidth::on_accept`, which only checks `request.from == registered manager` [5](#0-4)  and then calls `push_subscription(&msg.chain, &key, ...)` using the attacker-chosen `msg.chain`/`key` [6](#0-5) .
4. Once `A`'s FIFO list hits 1024 entries, each subsequent attacker purchase evicts the oldest entry in `A`'s list [7](#0-6)  — eventually evicting `A`'s legitimately purchased, unexpired, unused subscriptions, emitting `SubscriptionEvicted { lost_bytes }` for funds `A` paid for and never consumed.

Note: I was unable to fully inspect `evm/src/apps/BandwidthManager.sol`'s `purchase()` signature within the available tool budget to directly quote the Solidity-side parameter that lets the caller set `app`/`chain`; this is inferred from the pallet-side decode logic and the project's own documentation explicitly describing "sponsorship" (payer chain differs from credited `app_chain`) as an intended, unauthenticated-by-target feature. A Devin session with full repo access could confirm the exact Solidity `purchase()` parameters to close this gap.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

### Purchase messages skip the gate

The router uses `Pallet::is_purchase_message(request)` to identify a purchase from a registered manager (`request.source` is managed _and_ `request.from` matches the registered manager address). Purchase messages bypass the gate — otherwise a depleted app couldn't ever recharge.

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
