### Title
Copilot-model-supplied file path in AI conflict resolution is not restricted to the actual conflicted file set, allowing PR/commit-message prompt injection to silently overwrite arbitrary in-repo files - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes AI-generated content to disk for every entry in `copilotResolutions`, using `resolveWithin(repository.path, resolution.path)` to keep the write inside the repository, but never validates that `resolution.path` is one of the files that were actually part of the merge conflict. The `path` value originates from JSON parsed out of the Copilot model's own text response (`parseCopilotConflictResolution`), and the model's prompt includes attacker-influenceable data — PR titles/bodies and commit summaries from both sides of the merge (`formatConflictContextForPrompt` / `appendPullRequest`) — gathered from a repository the user is merging with (a fetched branch, a PR, or a cloned fork). [1](#0-0) 

### Finding Description
The Copilot merge/rebase/cherry-pick conflict-resolution feature:
1. Gathers conflict context including PR titles/bodies and commit messages from both sides of the operation, which can be attacker-authored content in a malicious PR or a specially crafted commit on a branch the user fetches/merges. [2](#0-1) [3](#0-2) 
2. Sends this untrusted text to the model as part of the user prompt, instructing it to respond only with JSON containing a `resolutions` array of `{ path, hunks/action, reasoning }`. [4](#0-3) 
3. Parses the model's JSON response and validates only structural shape of each entry (`path` non-empty string, `hunks` array, no leftover conflict markers) — never checks the path against the actual list of files known to be in conflict. [5](#0-4) 
4. When the user clicks "Continue Merge", `_applyCopilotConflictResolutions` iterates every resolution and, for non delete/modify entries, only checks `resolveWithin(repository.path, resolution.path)` (containment-only path-traversal guard) before writing: `await writeFile(absolutePath, resolution.resolvedContent, 'utf8')`, followed by `git add` to stage it. [1](#0-0) 
5. The only place `resolution.path` is cross-checked against the working directory's file list (`onDiskFile`) is to decide whether to *skip* writing (because the user already resolved it externally). If `onDiskFile` is `undefined` — i.e., the path is not one of the originally-conflicted files — that skip condition is false and the code proceeds to write anyway. [6](#0-5) 

`resolveWithin` (`app/src/lib/path.ts`) is a purely structural/containment guard — it resolves the path, calls `realpath`, and checks the result starts with the repo's real root; it has no concept of "must be one of the conflicted files" and therefore does not stop the model from targeting any other file that exists (or resolves) inside the repository tree. [7](#0-6) 

The broken invariant: the app implicitly assumes the model's `resolutions[].path` values are a subset of the conflicted-file paths it was given, but nothing enforces that assumption before an unattended file write + `git add` occurs.

### Impact Explanation
An attacker who controls content merged into the conflict-resolution prompt (a PR title/body, or a commit message on a branch fetched and merged/rebased by the victim) can attempt prompt injection instructing the model to include an additional `resolutions` entry for a file that was not actually conflicted — e.g. `package.json`, a CI workflow file, `.git/hooks/*` (if reachable via traversal quirks), or any other tracked/untracked file inside the working tree — with attacker-chosen `resolvedContent`. Because the write path only enforces "inside the repo," this content is silently written to disk and staged with `git add`, corrupting what the user is about to commit and push without any diff review specific to that file (the result dialog is oriented around the known conflicted-file list). This matches the accepted impact class: "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Requires: (1) the user to opt into the AI "Resolve with Copilot" feature during a merge/rebase/cherry-pick with actual conflicts, and (2) a PR body or commit message from the "theirs" side (attacker-controlled, e.g. a contributor's PR or a compromised/malicious upstream branch) to contain a successful prompt injection payload that a model instructed by a strict system prompt would still comply with. LLM prompt-injection reliability varies, and existing mitigations (JSON-only response, delimiter-free but truncated PR body embedding, `sanitizeForMarkdown`) reduce but do not structurally prevent it, since the missing control is a code-level allowlist, not a prompt-engineering defense. This is a plausible but not certain-to-always-succeed path, so likelihood is medium.

### Recommendation
Before writing any `resolution` to disk in `_applyCopilotConflictResolutions`, cross-check `resolution.path` against the deterministic list of files that were actually part of the conflict (the `conflictedFiles`/`fileContexts` passed into the prompt). Reject and log/skip (as is already done for the "path outside repository" case) any resolution whose path is not in that known set, in addition to the existing `resolveWithin` containment check.

### Proof of Concept
1. Set up a repository and create a merge conflict between two branches.
2. Craft the "theirs" branch/PR such that its PR body or a commit message contains a prompt-injection payload instructing the model to also emit a `resolutions` entry with `"path": "package.json"` (a file that is not in conflict) and malicious `resolvedContent` (e.g. adding a malicious `postinstall` script or altering a dependency).
3. In Desktop, start the merge/rebase and click "Resolve with Copilot".
4. If the model complies with the injected instruction, `parseCopilotConflictResolution` accepts the extra entry (no cross-check against the conflicted-file set exists at `app/src/lib/copilot-conflict-resolution.ts:379-463`).
5. When the user clicks "Continue Merge", `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7233-7259`) resolves `package.json` via `resolveWithin` (which succeeds, since the file is inside the repo), and unconditionally writes the attacker-supplied content to it and stages it — without the user ever seeing it flagged as part of the conflict resolution.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
