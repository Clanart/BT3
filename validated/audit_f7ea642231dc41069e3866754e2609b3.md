### Title
Cross-shop session confusion via user_id-based session lookup in `current_shopify_session` / `should_exchange_expired_token?` - ([File: lib/shopify_app/controller_concerns/token_exchange.rb])

### Summary
`current_shopify_session_id` is derived from the verified id token's own claims (shop + user_id) via `ShopifyAPI::Utils::SessionUtils.session_id_from_shopify_id_token`, but `ShopifyApp::SessionRepository.load_session` discards the shop portion of that id for online sessions and looks the session up purely by `shopify_user_id`. Neither `should_exchange_expired_token?` nor `current_shopify_session` re-validate that the retrieved session's `shop` actually matches the id token's verified `dest`/shop claim before the session is used and later activated.

### Finding Description
`current_shopify_session_id` calls `ShopifyAPI::Utils::SessionUtils.session_id_from_shopify_id_token(id_token: shopify_id_token, online: online_token_configured?)` [1](#0-0) , producing an id that encodes both the shop and the user_id from the id token's own (verified) claims. That id is passed to `ShopifyApp::SessionRepository.load_session`, which for non-offline ids does:

```
user = id.split("_").last
retrieve_user_session_by_shopify_user_id(user)
``` [2](#0-1) 

This completely discards the shop component of the id and resolves the session solely from `user_storage.retrieve_by_shopify_user_id(user_id)` (e.g. `InMemoryUserSessionStore#retrieve_by_shopify_user_id` at [3](#0-2)  or `UserSessionStorage.retrieve_by_shopify_user_id` at [4](#0-3) ). If the store already contains a record for that `shopify_user_id` pointing to a different shop (a pre-existing collision, e.g. from `store` unconditionally doing `find_or_initialize_by(shopify_user_id: user.id)` and overwriting `shopify_domain`/`shopify_token` — [5](#0-4) ), `current_shopify_session` returns the wrong shop's session object.

Downstream, `should_exchange_expired_token?` calls `current_shopify_session.expired?` on whatever session was returned, with no shop check [6](#0-5) . `current_shopify_session` itself performs no comparison against `jwt_shopify_domain` (the verified shop claim from `WithShopifyIdToken`) [7](#0-6) [8](#0-7) .

The only guard in `activate_shopify_session` is `reject_mismatched_requested_shopify_domain`, which compares `authenticated_shopify_domain_from_token` (`current_shopify_session&.shop || jwt_shopify_domain`, i.e. the *wrong* session's shop) against `requested_shopify_domain` (`sanitized_shop_name`, an attacker-supplied `shop`/`host` query param) [9](#0-8) . This check: (a) short-circuits (`return false`) when no `shop` param is present, providing no protection at all for non-embedded/API requests, and (b) can be trivially satisfied when a `shop` param is present by simply setting it to the colliding shop's domain, since it never compares against the verified `jwt_shopify_domain`. There is no assertion anywhere that `current_shopify_session.shop == jwt_shopify_domain`.

As a result, once a collision exists in the user-keyed session store, `ShopifyAPI::Context.activate_session(current_shopify_session)` [10](#0-9)  activates the colliding shop's session/access token for a request carrying a validly-signed id token for a different shop.

### Impact Explanation
Concrete impact is cross-shop session confusion / unauthorized access to another shop's access token and scopes: the app's subsequent API calls under `ShopifyAPI::Context.activate_session` use shop B's access token even though the request was authenticated (correctly, signature-wise) for shop A. This matches Shopify's "Cross-shop/cross-account session confusion, unauthorized data/action on another shop" impact class. The blast radius is bounded by the precondition (a collision must already exist for the specific `shopify_user_id` involved).

### Likelihood Explanation
This requires a pre-existing collision in the online-session store, keyed only by `shopify_user_id` and not scoped by shop — a design property of `UserSessionStorage`/`InMemoryUserSessionStore` (`store` unconditionally rewrites `shopify_domain`/`shopify_token` for a given user id) rather than something the attacker fabricates in a single request. Given that precondition (established by the referenced prior test/finding), the exploitation step here — sending a valid id token and having `load_session`/`current_shopify_session`/`should_exchange_expired_token?` resolve and operate on the wrong shop's session with no shop-binding check — is deterministic and fully reproducible.

### Recommendation
In `ShopifyApp::TokenExchange#current_shopify_session` (and/or in `SessionRepository.load_session`), after loading the session, assert that `session.shop == jwt_shopify_domain` (the verified id token's own shop claim) before returning/using it, and treat a mismatch as an invalid session (force re-exchange or respond unauthorized). Additionally, `SessionRepository.load_session`/online session storage should key/lookup online sessions by `(shop, shopify_user_id)` rather than `shopify_user_id` alone, so that the same physical user across multiple shops cannot overwrite or shadow each other's stored sessions.

### Proof of Concept
```ruby
test "current_shopify_session returns colliding shop's session when store is keyed only by user_id" do
  # Precondition: collision already exists (per prior finding) - same shopify_user_id
  # was stored for both shop-a and shop-b, last write (shop-b) wins in the user-keyed store.
  ShopifyApp::SessionRepository.user_storage = ShopifyApp::InMemoryUserSessionStore
  shop_b_session = ShopifyAPI::Auth::Session.new(
    shop: "shop-b.myshopify.com", access_token: "shop-b-token",
    associated_user: ShopifyAPI::Auth::AssociatedUser.new(id: 123, first_name: "", last_name: "",
      email: "", email_verified: false, account_owner: false, locale: "", collaborator: false),
  )
  ShopifyApp::InMemoryUserSessionStore.store(shop_b_session, OpenStruct.new(id: 123))

  # Attacker: valid id token for shop-a, sub/user_id = 123 (collided id)
  id_token = build_id_token(dest: "https://shop-a.myshopify.com", sub: "123")
  @controller.request.headers["HTTP_AUTHORIZATION"] = "Bearer #{id_token}"

  get :shop_context # no shop/host param -> reject_mismatched_requested_shopify_domain short-circuits

  # Expected (secure) behavior: session for shop-a is used, or request is rejected.
  # Actual (vulnerable) behavior: ShopifyAPI::Context.activate_session is called with
  # a session whose .shop == "shop-b.myshopify.com" and access_token == "shop-b-token",
  # even though the id token's own dest claim is shop-a.
end
```
Expected assertion for the vulnerability: `ShopifyAPI::Context.activate_session` is invoked with a session object whose `shop` differs from `jwt_shopify_domain` derived from the attacker's own valid id token, confirming the session-binding is not exact.
