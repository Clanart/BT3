### Title
Malformed compressed offer input can raise an unhandled `zlib.error` and crash the wallet RPC / API process - (File: `chia/wallet/util/puzzle_compression.py`)

### Summary
`Offer.from_bech32()` decodes an attacker-supplied bech32 offer string and feeds the raw bytes into `Offer.try_offer_decompression()`, which calls `decompress_object_with_puzzles()` → `zlib.decompressobj().decompress()`. The only exception this code path anticipates is `TypeError`; any malformed/corrupted compressed blob raises `zlib.error` instead, which propagates unhandled.

### Finding Description
`decompress_with_zdict()` calls `zlib.decompressobj(zdict=zdict).decompress(blob, max_length=...)` directly on attacker-controlled bytes with no validation of the compressed stream's structure: [1](#0-0) 

`Offer.try_offer_decompression()` is the entry point that any wallet user or offer counterparty reaches when supplying an offer string/file (e.g. via `take_offer`, `get_offer_summary`, CLI, or bech32-encoded offer files). It only guards against `TypeError`, not `zlib.error`: [2](#0-1) 

`Offer.from_bech32()` decodes the bech32 payload and forwards it straight into `try_offer_decompression()` without any additional validation of the compressed body: [3](#0-2) 

A truncated, bit-flipped, or otherwise corrupted zlib stream (e.g., invalid header bytes, bad checksum, or a stream that is valid zlib but decompresses to garbage that later fails elsewhere) causes `zlib.decompress`/`decompressobj().decompress` to raise `zlib.error: Error -3 while decompressing data: incorrect header check` (or similar). Because only `TypeError` is caught, this exception is not converted into a handled `ValueError`/`CompressionVersionError` and instead bubbles up through the offer-parsing call chain. This is directly analogous to the reported gRPC-js bug class: an incoming malformed *compressed* payload is decompressed without robust error handling, causing a crash/DoS in the receiving process. Here the "network peer" is replaced by an unprivileged wallet RPC caller or offer counterparty who supplies a bech32 offer string.

### Impact Explanation
Any caller of the wallet RPC endpoints that parse offer strings (e.g. `take_offer`, `get_offer_summary`, or CLI `chia wallet take_offer`) can pass a corrupted bech32 offer. If the RPC handler / CLI command does not itself wrap the parse call in a broad `try/except`, the unhandled `zlib.error` will propagate and can crash or degrade the wallet process/RPC worker handling that request — a spend/offer-triggered denial-of-service against the wallet, matching the CWE-248 (uncaught exception) / CWE-400 (uncontrolled resource consumption / crash) classification of the source advisory. This is reachable by any unprivileged party who can hand a wallet user an offer file/string (a normal, expected trust boundary in the offers flow).

### Likelihood Explanation
High likelihood of triggering the crash path: constructing a bech32 string with valid checksum but a corrupted/truncated zlib payload is trivial and requires no cryptographic material or privileged access — any offer counterparty or wallet-RPC caller can produce one. The only uncertainty (not verifiable from the indexed code alone) is whether the top-level RPC/CLI call sites wrap `Offer.from_bech32`/`try_offer_decompression` in a sufficiently broad exception handler that would prevent a full process crash and only return an RPC error instead; this could not be fully confirmed from the available `wallet_rpc_api.py`/`wallet_request_types.py` excerpts within the tool budget.

### Recommendation
In `decompress_with_zdict()` (or in `try_offer_decompression()`), catch `zlib.error` explicitly and re-raise as the same domain-specific exception used elsewhere (e.g. `CompressionVersionError` or a new `ValueError`), so malformed compressed offer data is turned into a normal, handled parse failure rather than an unhandled low-level exception. Additionally verify that all RPC/CLI entry points that call `Offer.from_bech32`/`try_offer_decompression` catch this error and return a clean error response rather than letting the process crash.

### Proof of Concept
1. Take any valid offer bech32 string (or synthesize one): compute `to_bech32()` output.
2. Corrupt a few bytes in the middle of the underlying compressed payload (post version-prefix bytes) before bech32-encoding, keeping the bech32 checksum valid by re-encoding with `bech32_encode`.
3. Submit the corrupted string to a wallet RPC call that parses offers (or directly call `Offer.from_bech32(corrupted_str)`).
4. Observe `decompress_with_zdict()` raising `zlib.error`, which is not caught by `try_offer_decompression()`'s `except TypeError` clause, propagating as an unhandled exception in the wallet process.

def decompress_with_zdict(blob: bytes, zdict: bytes) -> bytes:
    do = zlib.decompressobj(zdict=zdict)
    return do.decompress(blob, max_length=6 * 1024 * 1024)  # Limit output size


def decompress_object_with_puzzles(compressed_object_blob: bytes) -> bytes:
    version = int.from_bytes(compressed_object_blob[0:2], "big")
    if version > len(ZDICT):
        raise CompressionVersionError(version)
    zdict = zdict_for_version(version)
    object_bytes = decompress_with_zdict(compressed_object_blob[2:], zdict)
    return object_bytes
