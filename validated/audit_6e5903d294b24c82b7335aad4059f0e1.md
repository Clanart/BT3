### Title
Git server can spoof itself as "GitHub Enterprise" via a forged `WWW-Authenticate` header to trigger unauthorized GitHub sign-in prompts against an attacker-controlled host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind()` classifies a git remote as `'enterprise'` (i.e., a trusted GitHub Enterprise host) purely based on a self-reported `WWW-Authenticate` header value forwarded by git during authentication, without any cryptographic or out-of-band verification that the host is actually a GitHub product. This is analogous to the Axelar bug: an identity is "validated" solely because the *claimant itself* asserts that identity, rather than through an independently verifiable, non-spoofable channel.

### Finding Description
When Desktop's git credential trampoline handles a `get` request, it calls `getEndpointKind()`: [1](#0-0) 

Any host, GitHub-owned or not, that a user clones/fetches/pushes to can respond to an authenticated git HTTP request with a header such as `WWW-Authenticate: Basic realm="GitHub"`. Git forwards this header verbatim to the credential helper as a `wwwauth[...]` credential field, and Desktop trusts it at face value to classify the remote as `'enterprise'` — a full trust tier reserved for real GitHub Enterprise Server instances.

This classification then drives `getCredential()`: [2](#0-1) 

Because no existing account matches the attacker's `apiEndpoint`, Desktop calls `ui.promptForGitHubSignIn(endpoint)` — presenting the user with what looks like a legitimate "Sign in to GitHub Enterprise" flow, but directed at the attacker's arbitrary hostname, purely because that hostname's server *claimed* to be GitHub via an HTTP response header it fully controls.

The same self-asserted classification is also used to gate credential storage/erasure (`storeCredential`/`eraseCredential`), meaning a spoofed classification can also suppress normal generic-credential-helper storage behavior for that host.

### Impact Explanation
A malicious or MITM'd git remote/proxy (a party the report's threat model explicitly allows: "attacker controls ... a git remote/proxy response") can silently escalate its trust classification from "generic git host" to "GitHub Enterprise" simply by returning a crafted `WWW-Authenticate` header on a normal, user-initiated `git fetch`/`clone`/`push`. This:
- Triggers an unsolicited GitHub-Enterprise sign-in UI flow bound to the attacker's host, which can be used to phish/harvest PATs or OAuth codes the user believes are being sent to a legitimate GitHub product (unauthorized OAuth/account-binding, credential exfiltration).
- Alters credential-handling behavior (bypassing the generic external/native credential helper path) for that host, silently changing how the user's git credentials for that remote are managed.

No local access, admin rights, or pre-existing malware is required — only a repository/remote under attacker control that the user clones or interacts with, matching the report's allowed impact categories.

### Likelihood Explanation
Any attacker who can stand up a git-over-HTTPS server (or MITM an HTTP git proxy) can add this header trivially; the check in `getEndpointKind` is a simple substring match (`v.includes('realm="GitHub"')`) with no additional verification (no TLS certificate check, no `x-github-request-id` confirmation as used elsewhere via `isGitHubHost`). This is a much cheaper "happy path" bypass than the `isGitHubHost()` network probe used later in the same function, and it fires for every git credential negotiation against that remote.

### Recommendation
Do not use the `WWW-Authenticate` realm header alone as sufficient evidence of a GitHub identity. At minimum:
- Require corroboration via the existing `isGitHubHost()` probe (which checks for the `x-github-request-id` response header) before elevating trust based on the `wwwauth[...]` realm hint, rather than treating the realm string as a standalone happy path.
- Scope any "GitHub Enterprise" trust elevation strictly to hosts that have been explicitly added as GHE accounts by the user, mirroring the Axelar fix's recommendation to require explicit allow-listing rather than trusting a self-asserted identity claim.

### Proof of Concept
1. Attacker hosts a git-over-HTTPS repository at `https://evil.example.com/repo.git`.
2. User adds this as a remote in a Desktop-managed repo and performs a `fetch`/`push`.
3. Attacker's server responds to the authenticated git request with `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this to Desktop's credential trampoline; `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`) returns `'enterprise'` for `evil.example.com`.
5. `getCredential` finds no existing account for `evil.example.com` and invokes `ui.promptForGitHubSignIn('https://evil.example.com')`, presenting a "Sign in to GitHub Enterprise" prompt for the attacker's domain.
6. A user who trusts the prompt (believing Desktop only shows this for genuine GitHub products) enters a PAT or completes an OAuth flow scoped to the attacker's endpoint, exfiltrating credentials.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
