### Title
Stale `totalBoostFactor` denominator (missing `updateTotalFactor` on `unlock`/`cancelUnlock`/`forceUnLock`) enables inflated referral boost payouts - (File: rewards/ReferralStorage.sol, VLMGP.sol)

### Summary
`updateTotalFactor()` is only invoked from `VLMGP._lock` and `VLMGP.startUnlock`, never from `unlock`, `cancelUnlock`, or `forceUnLock` [1](#0-0) [2](#0-1) . Because `cancelUnlock` moves an amount back from cool-down into active locked status (increasing `getUserTotalLocked`) without recomputing `factor`/`totalBoostFactor`, the shared denominator `totalBoostFactor` can be made to permanently understate the true sum of all users' factors. This drift skews `_calBoosted` for every referrer, not just the manipulating account.

### Finding Description
`updateTotalFactor` recomputes a user's `factor = sqrt(getUserTotalLocked(_account))` and adjusts the global `totalBoostFactor` accordingly [3](#0-2) . It is wired into only two of the five state-changing lock paths in `VLMGP.sol`:
- `_lock` (used by `lock`/`lockFor`) calls it [2](#0-1) .
- `startUnlock` calls it [4](#0-3) .
- `unlock`, `cancelUnlock`, and `forceUnLock` do **not** call it [5](#0-4) [6](#0-5) .

For `unlock` and `forceUnLock`, this omission is largely harmless because `getUserTotalLocked` already excludes cool-down amounts, so the factor was already correctly reduced when `startUnlock` ran. The dangerous path is `cancelUnlock`: it sets `slot.amountInCoolDown = 0` and decrements `totalAmountInCoolDown`, which causes `getUserTotalLocked` (== `amountInMasterMagpie - amountInCoolDown`) to jump back up to the pre-`startUnlock` value, effectively "re-locking" the tokens — but `userInfo.factor` and `totalBoostFactor` are never refreshed to reflect this increase [6](#0-5) [7](#0-6) .

The consequence: `totalBoostFactor` (the shared denominator in `_calBoosted`) ends up permanently smaller than the true sum of all registered users' `sqrt(lockedAmount)` values [8](#0-7) . Since `boostesd = BoostPoint * userInfos[_account].factor / totalBoostFactor` has no bound guaranteeing the sum of shares stays ≤ `BoostPoint`, an artificially low `totalBoostFactor` inflates `boostesd` for **every** account with a registered code, including other addresses the attacker controls as referrers. `trigger()` then uses `basic + boostesd` directly as a percentage against `DENOMINATOR` to compute `refererAmount`/`refereeAmount` paid out of the shared MGP reward pool that `claimReward()` draws from [9](#0-8) [10](#0-9) .

Note: the specific mechanism described in the prompt ("`myReferer[account]` diverging from `userInfos[account].codeIUsed` by splitting a lock across many addresses that each register a code") is not the actual causal path — `myReferer`/`codeIUsed` are set independently in `useCode`/`registerCode` and are unrelated to `totalBoostFactor` bookkeeping [11](#0-10) . The real root cause is the missing `updateTotalFactor` call specifically on the `cancelUnlock` re-lock path.

### Impact Explanation
An attacker who owns a "sacrifice" account (lock → `startUnlock` full amount → `cancelUnlock` to re-lock without refreshing factor) can permanently deflate the shared `totalBoostFactor` denominator. This inflates `boostesd` for all accounts with a registered referral code, including attacker-controlled referrer accounts that receive `trigger()` payouts from referee reward claims. Over repeated cycles this results in the protocol paying out referral rebates larger than the intended `BoostPoint`-bounded budget, draining MGP tokens meant to fund `claimReward()` — a form of theft/over-extraction of unclaimed yield from the shared reward pool. The effect is systemic (benefits all referrers, not exclusively the attacker) which somewhat dilutes the "clean single-attacker theft" narrative, but the attacker can still direct disproportionate gain to accounts they control.

### Likelihood Explanation
The attack requires no privileged role: `lock`/`lockFor`, `startUnlock`, and `cancelUnlock` are all permissionless entrypoints on `VLMGP.sol` [12](#0-11) [6](#0-5) . It requires capital to lock MGP (which is returned to the attacker via `cancelUnlock`, i.e. no permanent capital loss) and a code registered via `registerCode` [13](#0-12) . It is repeatable and does not depend on any admin/governance action.

### Recommendation
Call `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)` at the end of `unlock`, `cancelUnlock`, and `forceUnLock` in `VLMGP.sol`, mirroring the call already present in `_lock` and `startUnlock`, so `totalBoostFactor` is refreshed on every path that changes `getUserTotalLocked`. Additionally, consider bounding `_calBoosted` so the sum of `boostesd` values cannot exceed `BoostPoint` regardless of transient denominator staleness (e.g., cap `boostesd` or recompute `totalBoostFactor` lazily from live data rather than incrementally maintained state).

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `ReferralStorage`; register codes for `attackerA` (sacrifice account) and `attackerB` (beneficiary referrer).
2. Have `victimC` register a code and lock a normal amount, and have `victimD` use `victimC`'s code as referee — record baseline `boostesd`/`totalBoostFactor`.
3. `attackerA` locks a large amount via `lock()` (factor and `totalBoostFactor` update correctly), then calls `startUnlock(fullAmount)` (factor drops to ~0, `totalBoostFactor` decreases correctly), then calls `cancelUnlock(slotIndex)` before cool-down ends (re-locks tokens, but `totalBoostFactor` stays deflated — assert via `totalBoostFactor` view/getter that it did not increase back).
4. Assert `getUserTotalLocked(attackerA)` is back to the pre-`startUnlock` value while `totalBoostFactor` remains at the post-`startUnlock` (deflated) level — confirming the drift.
5. Have `attackerB`'s referee claim a reward via `masterMagpie` triggering `ReferralStorage.trigger()`; assert `refererAmount` credited to `attackerB` is measurably higher than the amount computed with a correctly-refreshed `totalBoostFactor` (compare against a control run where `updateTotalFactor` is manually invoked after `cancelUnlock`).
6. Assert the sum of `basic + boostesd` across active referrers can exceed the value it would have with a correctly maintained `totalBoostFactor`, demonstrating over-payout from the shared MGP reward pool.
