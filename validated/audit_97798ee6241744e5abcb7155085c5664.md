### Title
Unbounded RPC filter creation allows memory/goroutine exhaustion DoS - ([File: node/cn/filters/api_kaia_filter.go])

### Summary
Any public RPC caller can repeatedly invoke `eth_newFilter` / `klay_newFilter`, `eth_newBlockFilter` / `klay_newBlockFilter`, and `eth_newPendingTransactionFilter` / `klay_newPendingTransactionFilter` without any cap on the number of filters that can be created. Each call inserts a new entry into the shared `api.filters` map and spawns a dedicated goroutine and event subscription that persist until either an explicit `uninstallFilter` call or a 5-minute idle deadline. This mirrors the Mattermost `getSessions` flaw (CWE-400/770): an authenticated-but-unprivileged caller can flood an unbounded, session-like table until the node runs out of memory or goroutines.

### Finding Description
`FilterAPI` keeps all active filters in a single unbounded map: [1](#0-0) 

`NewFilter`, `NewBlockFilter`, and `NewPendingTransactionFilter` each add an entry to `api.filters` and start a new goroutine + subscription with no check on how many filters already exist (globally or per caller/IP): [2](#0-1) [3](#0-2) [4](#0-3) 

The only cleanup mechanism is a 5-minute idle timeout that sweeps stale filters: [5](#0-4) [6](#0-5) 

An attacker only needs to create new filters faster than the 5-minute reaper, or simply poll each filter (via `getFilterChanges`) to reset its deadline timer, keeping unbounded numbers of filters, goroutines, and subscriptions alive indefinitely. Unlike the tx pool (`ExecSlotsAccount`/`NonExecSlotsAll` in `blockchain/tx_pool.go`), the gasless bundle queue (`MaxBundleTxsInQueue` in `kaiax/gasless/config.go`), the bid pool (`MaxBidPoolSize`), and the p2p request tracker (`maxTrackedPackets`), which all enforce hard caps on unbounded growth from repeated external requests, the RPC filter subsystem has no equivalent per-caller or global cap.

### Impact Explanation
Each filter holds an open channel, a background goroutine, and a live subscription to the node's log/head/pending-tx event feeds. Unbounded accumulation of these consumes heap memory and goroutine stack space and adds load to the event-dispatch loops that fan out logs/heads/pending-tx notifications to every registered subscriber. A single unauthenticated/unprivileged RPC caller can degrade or crash the node process (CWE-400: Uncontrolled Resource Consumption; CWE-770: Allocation of Resources Without Limits or Throttling), directly analogous to the Mattermost session-table flood that crashed the server via unbounded session growth.

### Likelihood Explanation
`eth_newFilter`/`klay_newFilter` and friends are standard, publicly exposed JSON-RPC methods (marked `Public: true` in `node/cn/backend.go`), reachable by any RPC client with no special privileges, no gas cost, and no rate limiting specific to filter creation (the existing `RPCConcurrencyLimit`/batch limits throttle concurrent *requests*, not the number of persistent filter objects that accumulate over time). This makes the attack trivially and repeatedly exploitable over a long-lived connection or many short ones.

### Recommendation
Enforce a maximum number of concurrently active filters, either globally or per client/IP/connection, in `FilterAPI` (e.g., reject `NewFilter`/`NewBlockFilter`/`NewPendingTransactionFilter` once `len(api.filters)` exceeds a configurable threshold), and/or shorten the idle deadline and rate-limit filter creation per connection, mirroring the caps already applied to the tx pool (`ExecSlotsAccount`, `NonExecSlotsAll`) and the gasless bundle queue (`MaxBundleTxsInQueue`).

### Proof of Concept
1. Connect to the node's public JSON-RPC endpoint (HTTP or WS).
2. In a loop, call `eth_newFilter` (or `klay_newBlockFilter`/`eth_newPendingTransactionFilter`) with a fresh filter criteria each time, without ever calling `uninstallFilter`.
3. Periodically call `eth_getFilterChanges` on each created filter ID to reset its 5-minute idle deadline, or simply create filters faster than the 5-minute reaper interval.
4. Observe unbounded growth of `api.filters`, goroutine count, and memory usage on the node until resource exhaustion causes degraded performance or crash — with no built-in defense in `node/cn/filters/api_kaia_filter.go`.

// timeoutLoop runs every 5 minutes and deletes filters that have not been recently used.
// It is started when the api is created.
func (api *FilterAPI) timeoutLoop() {
	var toUninstall []*Subscription
	ticker := time.NewTicker(api.timeout)
	defer ticker.Stop()
	for {
		<-ticker.C
		api.filtersMu.Lock()
		for id, f := range api.filters {
			select {
			case <-f.deadline.C:
				toUninstall = append(toUninstall, f.s)
				delete(api.filters, id)
			default:
				continue
			}
		}
		api.filtersMu.Unlock()

		// Unsubscribes are processed outside the lock to avoid the following scenario:
		// event loop attempts broadcasting events to still active filters while
		// Unsubscribe is waiting for it to process the uninstall request.
		for _, s := range toUninstall {
			s.Unsubscribe()
		}
		toUninstall = nil
	}

func (api *KaiaFilterAPI) NewPendingTransactionFilter() rpc.ID {
	var (
		pendingTxs   = make(chan []*types.Transaction)
		pendingTxSub = api.events.SubscribePendingTxs(pendingTxs)
	)

	api.filtersMu.Lock()
	api.filters[pendingTxSub.ID] = &filter{typ: PendingTransactionsSubscription, deadline: time.NewTimer(api.timeout), txs: make([]*types.Transaction, 0), s: pendingTxSub}
	api.filtersMu.Unlock()

	go func() {
		defer pendingTxSub.Unsubscribe()
		for {
			select {
			case pTx := <-pendingTxs:
				api.filtersMu.Lock()
				if f, found := api.filters[pendingTxSub.ID]; found {
					f.txs = append(f.txs, pTx...)
				}
				api.filtersMu.Unlock()
			case <-pendingTxSub.Err():
				api.filtersMu.Lock()
				delete(api.filters, pendingTxSub.ID)
				api.filtersMu.Unlock()
				return
			}
		}
	}()

	return pendingTxSub.ID
}
