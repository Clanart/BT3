### Title
Distribution precompile `rewards()` view accepts and permanently strands attached `value` due to missing non-payable check - (File: `precompiles/distribution/distribution.go`)

### Summary
The `rewards()` view method of the distribution precompile (address `0x...1007`) can be invoked with a non-zero `value` (usei/wei) attached to the EVM call. Unlike all other query methods in the same dispatcher, it lacks the `pcommon.ValidateNonPayable(value)` guard, so the call succeeds instead of reverting, and the attached value is never refunded or otherwise processed, permanently stranding it at the precompile's address.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute()` dispatches to `p.rewards(ctx, method, args)` for `RewardsMethod` without any value validation: [1](#0-0) 

Contrast this with the sibling query methods that all invoke `p.validateInput(value, args, n)`, which internally calls `pcommon.ValidateNonPayable(value)`: [2](#0-1) [3](#0-2) 

The `rewards()` implementation itself only validates argument length and never inspects `value` at all: [4](#0-3) 

For "payable" precompile transaction methods (e.g. `delegate` in the staking precompile), any usei sent as `value` is explicitly re-credited to the caller via `pcommon.HandlePaymentUsei`, whose comment makes clear this refund step is required because the EVM's own value-transfer mechanics already move the balance to the precompile address before precompile logic runs: [5](#0-4) 

Because `rewards()` neither rejects nonzero `value` (like `ValidateNonPayable` does for other views, causing a revert and rollback of the EVM value transfer) nor consumes/refunds it (like `HandlePaymentUsei` does for payable methods), any usei/wei sent alongside a `rewards()` call is accepted by the EVM as a successful, non-reverting transaction and left stuck in the precompile's associated balance with no code path that ever moves it back out. This is architecturally identical to the Alchemix `RewardsDistributor.claim()` bug: a function that is reachable with `msg.value > 0`, takes an early/short-circuit code path that omits the value check present on its sibling code paths, and the value is subsequently unrecoverable.

This exact gap is independently confirmed and documented in the repository's own integration test suite comment: [6](#0-5) 

The dispatcher's own code comment on `!p.IsTransaction(method.Name)` confirms `rewards` is treated purely as a query/view method, reinforcing that non-zero value was never an intended input for it: [7](#0-6) 

### Impact Explanation
Any unprivileged EVM transaction sender who calls `rewards(address)` on the distribution precompile at `0x0000000000000000000000000000000000001007` with a nonzero `value` field will have that usei/wei amount irrecoverably locked. This is a direct, permanent freezing-of-funds bug reachable by any public JSON-RPC client or contract that composes with the precompile (e.g., a wrapper/aggregator contract that forwards `msg.value` when querying rewards), matching the "permanent freezing of funds" impact class.

### Likelihood Explanation
Likelihood is comparable to (or higher than) the original Alchemix report: unlike the Alchemix case which requires a specific stuck-transaction retry scenario, here a single, ordinary call to `rewards()` with any attached value is sufficient to trigger the loss — no double-send/race condition is required. The main mitigating factor is that most legitimate callers do not attach value to a "view" style call (`rewards` is a `view`/non-mutating query semantically), so this typically only manifests due to caller error, an integrating contract's bug, or a wallet/tooling mistake that attaches value unconditionally. This aligns with medium severity as in the original report.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check at the top of `rewards()` (or in the `RewardsMethod` case of `Execute()`), matching the guard already present on every sibling read-only method (`validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`): [1](#0-0) 

### Proof of Concept
1. Associate an EVM address with a Sei account.
2. Call `distribution.rewards(delegatorAddress)` at `0x0000000000000000000000000000000000001007` with `{ value: ethers.parseEther("1") }` (or any nonzero usei-denominated wei amount) as a transaction (not a static call).
3. Observe the transaction succeeds (`status == 1`) and returns the rewards data.
4. Observe the caller's EVM balance decreased by the sent value, and that no compensating `bankKeeper.SendCoins` back to the caller ever occurs (no `HandlePaymentUsei` invocation exists on this code path) — the value is now stuck at the precompile's associated account, exactly as flagged by the existing test-suite comment: [8](#0-7)
