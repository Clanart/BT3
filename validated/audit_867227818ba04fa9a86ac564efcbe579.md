### Title
BIP-340 algorithm never normalizes group-key parity, producing invalid signatures for odd-Y threshold keys (funds unspendable) - (File: networks/bitcoin/src/crypto.rs)

### Summary
The `Hram`/`Schnorr` BIP-340 adapter corrects only the parity of the nonce commitment `R` (by negating the challenge when `R` is odd, and negating `s` on output). It never normalizes the parity of the x-only group key `A`. BIP-340 requires verification against the even-Y lift of `x(A)`; when the threshold `group_key` has odd Y (probability ~1/2 for any DKG output), the aggregate signature passes Serai's internal Schnorr verification yet is invalid under BIP-340 consensus rules.

### Finding Description
`Hram::hram` hashes `x(R)`, `x(A)`, `m` and conditionally negates the challenge `c` solely on `needs_negation(R)`; there is no handling of `needs_negation(A)` [1](#0-0) . `Schnorr::verify` runs `FrostSchnorr::verify` (which checks `s·G == R + c·P` against the unnormalized point `P`), then negates `s` if `sig.R` is odd and serializes the x-only signature [2](#0-1) . The inner `sign_share`/`verify` use `params.group_key()` directly, with no key negation [3](#0-2) . Since `Hram` negates `c` for odd `R`, the produced scalar is `s = r − c_B·x`; after the output negation, external verifiers compute `-s·G = -R + c_B·P`, whereas BIP-340 requires `R_even + c_B·P_even`. If `P` is odd, `P_even = -P`, so the equation holds only if `P` is even. No code path negates the secret share / applies `scale(-1)` when the group key is odd, and `ThresholdKeys::group_key()`/`offset()`/`scale()` are applied verbatim [4](#0-3) . Because `verify` uses the same unnormalized `P`, the internal "integrity check" in `AlgorithmSignatureMachine::complete` passes and emits the consensus-invalid signature [5](#0-4) .

### Impact Explanation
For any threshold group key whose point has odd Y (~50% of keys, an unprivileged party triggering signing cannot fix this from the outside), every emitted "valid" BIP-340 signature fails consensus verification. For the Bitcoin network integration this translates into Taproot outputs whose key-path spend is impossible: funds reported received are not spendable via the produced signatures — a permanent loss-of-funds/liveness failure that the internal signature check cannot detect. This mirrors the memory-corruption class of CVE-2023-6212 mapped onto Serai's real shape: a correctness defect in verification math producing signatures the ecosystem rejects.

### Likelihood Explanation
Triggering requires only that `needs_negation(group_key)` hold, which occurs for half of all uniformly distributed DKG outputs — no malicious participant, no crafted input required, and any requester who causes a message to be signed receives an invalid signature. The defect is deterministic given key parity, so affected keys fail on every signature.

### Recommendation
In `Schnorr`'s FROST wiring, normalize the group key to even-Y before signing/verifying: if `needs_negation(view.group_key())`, sign with the negated secret share (equivalently, have callers apply `ThresholdKeys::scale(-1)` / negate `view.secret_share()` and the interpolated verification shares) so that `s·G == R + c·P_even`. The cleanest fix is in `sign_share`/`verify_share`/`verify` of the bitcoin `Schnorr` algorithm: detect `needs_negation(group_key)` once, negate `params.secret_share()` and each `verification_share` accordingly, and hash `x(A)` as today. Add a regression test asserting the emitted `[u8; 64]` verifies under `secp256k1`/`bitcoin`'s BIP-340 `verify` for an odd-Y group key.

### Proof of Concept
1. Run `dkg_dealer::key_gen::<_, Secp256k1>(rng, t, n)` until `bool::from(needs_negation(&keys[1].group_key()))` (reject sampling, ~1 iteration on average).
2. Execute a full `Schnorr::new()` FROST signing round over any `msg` via `AlgorithmMachine::preprocess`/`sign`/`complete`; `complete` returns `Ok(sig)` because `FrostSchnorr::verify` checks against the odd point.
3. Parse `sig` as a BIP-340 signature with `XOnlyPublicKey::from_slice(&x(&group_key))` and call `secp256k1::schnorr::Signature::verify` — it fails, since verification uses the even-Y lift `-group_key` while `s` encodes `±(r − c·x)` for `x` of the odd point. For an even-Y key the same test passes, confirming the defect is the missing key-parity normalization in `crypto.rs`.

Confidence note: I could not inspect all of `networks/bitcoin/src` wallet/scanner code, so an offset applied elsewhere that forces even-Y keys cannot be fully excluded; nothing in `crypto.rs`, `frost/algorithm.rs`, or `dkg` shown above performs such normalization.

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }

    fn verify(
      &self,
      group_key: ProjectivePoint,
      nonces: &[Vec<ProjectivePoint>],
      sum: Scalar,
    ) -> Option<Self::Signature> {
      self.0.verify(group_key, nonces, sum).map(|mut sig| {
        sig.s = <_>::conditional_select(&sum, &-sum, needs_negation(&sig.R));
        // Convert to a Bitcoin signature by dropping the byte for the point's sign bit
        sig.serialize()[1 ..].try_into().unwrap()
      })
    }
