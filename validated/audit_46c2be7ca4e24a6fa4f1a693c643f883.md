Let me check the `blame`/`decrypt_with_proof` semantics and the `VerifyBlame` call site more closely, plus a few other spots where a caller-supplied index mutates another party's state.### Title
Swapped `sender`/`recipient` arguments in `VerifyBlame` blame evaluation let an accuser convict an innocent participant and shield the actual faulty sender — (File: processor/src/key_gen.rs)

### Summary
`CoordinatorMessage::VerifyBlame` in `processor/src/key_gen.rs:504-564` evaluates a DKG blame accusation by calling `AdditionalBlameMachine::blame` / `BlameMachine::blame`. Those functions take `(sender, recipient, msg, proof)` where, per their documentation, the *accused* is the sender of the secret share and the *accuser* is its recipient. The processor instead calls `.blame(accuser, accused, share, blame)`, placing the accuser in the `sender` slot and the accused in the `recipient` slot — the same bug class as `claimFees` writing `feeRecipientToTokenToAmount[to]` for an attacker-chosen `to` instead of the authenticated caller: the verdict is applied to the wrong party.

### Finding Description
`blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-609`) calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`. In `Decryption::decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:366-397`):

1. `msg.pop` is verified against `pop_challenge(context, R, msg.key, from, msg)` — `from` is the `sender` argument, and `pop_challenge` appends `sender.to_bytes()` into the challenge (`encryption.rs:317`). A legitimate PoP therefore binds the *real* encryptor's `Participant` index.
2. If a `proof` is supplied, its DLEq is verified against `self.enc_keys[&decryptor]` — i.e., the proof must be the ECDH shared key derivable only by the `recipient` (`encryption.rs:381-390`).
3. Outcomes: `InvalidSignature` → returns `sender`; `InvalidProof` (including `proof == None`) → returns `recipient`; invalid scalar/share → returns `sender`; valid share → returns `recipient`.

In `VerifyBlame`, the processor calls `.blame(accuser, accused, substrate_share, substrate_blame)` and the same for the network share (`key_gen.rs:543-556`), then slashes `accused` iff either call returns `accused` (`key_gen.rs:558-563`).

Two consequences follow from the swap:

- **Honest accusations backfire.** A real accuser holds a share whose PoP binds the real sender (the accused). Because the code verifies the PoP with `from = accuser`, the signature check fails → `InvalidSignature` → returns `sender` (= accuser), so `Blame { participant: accuser }` is emitted. The honest reporter is blamed and the malicious share-sender is never convicted.
- **Framing an innocent victim.** The attacker controls the `share` bytes (`EncryptedMessage::read`, `key_gen.rs:508-519`) and the `blame` bytes (`EncryptionKeyProof::read`, `key_gen.rs:538-541`). The attacker crafts a fresh `EncryptedMessage` with a self-generated per-message key, whose PoP is bound to `from = accuser` (themselves) and whose payload is encrypted to the victim's published encryption key — all computable from public `EncryptionKeyMessage`s. Submitting `blame: None` then takes the `InvalidProof` branch → returns `recipient` (= accused = victim). `VerifyBlame` sees `blame == accused` and emits `Blame { participant: victim }`, convicting an honest participant with zero proof. Even a fabricated-but-validly-signed message suffices; no ECDH key, no valid share, and no misbehavior by the victim is required.

The PedPoP tests confirm the intended argument order: `machine.blame(ONE, TWO, msg, blame)` blames `ONE` where `ONE` is the malicious *sender* of the mutated share to recipient `TWO` (`crypto/dkg/pedpop/src/tests.rs:156-170`). `VerifyBlame` inverts this.

### Impact Explanation
DKG blame is the accountability mechanism that fatally penalizes (slashes) faulty validators. With the arguments swapped, any participant can emit an `InvalidShare` accusation naming an arbitrary victim, supply a self-crafted `EncryptedMessage` and an empty/missing `EncryptionKeyProof`, and cause the coordinator-side verification to blame the victim — an unearned fatal fault on an honest validator. Simultaneously, a genuinely malicious participant who distributes invalid shares can never be convicted through `VerifyBlame`, since valid accusations resolve to the accuser. This inverts the protocol's incentive structure and makes the blame system unusable or actively harmful. Severity: High.

### Likelihood Explanation
Reachable by an unprivileged DKG participant using only public inputs: the commitment messages (which contain every participant's `enc_key`), attacker-chosen `share`/`blame` byte strings parsed via the public `EncryptedMessage::read` / `EncryptionKeyProof::read` deserializers, and the `VerifyBlame` message path. The attacker needs only to author a Schnorr PoP for a key they generated — trivial. One caveat I could not fully verify within the available context: the exact mechanism by which the coordinator selects `accuser`/`accused` for `VerifyBlame` (in `coordinator/src/tributary/handle.rs`). If the coordinator accepts the self-reported `faulty` field from the accusing validator's `ProcessorMessage::InvalidShare`, the framing attack is fully attacker-driven; even under a more restrictive coordinator, the "honest accusation blames the accuser" failure mode is unconditional.

### Recommendation
Swap the arguments at `key_gen.rs:549` and `key_gen.rs:556` to `.blame(accused, accuser, share, blame)` so the accused occupies the `sender` slot and the accuser the `recipient` slot, matching `blame`'s documented contract ("a copy of the encrypted secret share from the accused sender to the accusing recipient", `crypto/dkg/pedpop/src/lib.rs:611-617`). Additionally, consider rejecting `proof: None` blame verdicts against the recipient in `decrypt_with_proof` only when the PoP itself is invalid (i.e., require an `EncryptionKeyProof` before blame can fall on the `recipient`), so a missing decryption key can never convict anyone.
