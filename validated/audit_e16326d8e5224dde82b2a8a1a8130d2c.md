### Title
Autocreator visibility side effect committed before parse success is verified in `-[GPBMessage mergeFromData:extensionRegistry:error:]` - (File: objectivec/GPBMessage.m)

### Summary
`mergeFromData:extensionRegistry:error:` calls `GPBBecomeVisibleToAutocreator(self)` unconditionally at the top of the method, before the actual parse (`mergeFromCodedInputStream:`) has run and before the try/catch that determines whether the parse succeeded. This mirrors the Sturdy `LidoVault._withdrawFromYieldPool` bug class: an irreversible state-mutating action is performed first, and the correctness check (parse success/failure) is only evaluated afterward — but the mutation is never rolled back when the check later reports failure.

### Finding Description [1](#0-0) 

```objc
- (BOOL)mergeFromData:(NSData *)data
    extensionRegistry:(nullable id<GPBExtensionRegistry>)extensionRegistry
                error:(NSError **)errorPtr {
  GPBBecomeVisibleToAutocreator(self);
  GPBCodedInputStream *input = [[GPBCodedInputStream alloc] initWithData:data];
  @try {
    [self mergeFromCodedInputStream:input extensionRegistry:extensionRegistry endingTag:0];
    [input checkLastTagWas:0];
    if (errorPtr) { *errorPtr = nil; }
  } @catch (NSException *exception) {
    [input release];
    if (errorPtr) { *errorPtr = ErrorFromException(exception); }
    return NO;
  }
  [input release];
  return YES;
}
```

`GPBBecomeVisibleToAutocreator` permanently walks up the autocreated-message parent chain and marks each ancestor as "real" (i.e., converts an autocreated placeholder message into a message that will actually be retained/serialized by its parent), as seen in its many call sites in `objectivec/GPBUtilities.m` and `objectivec/GPBMessage.m`. This call happens with attacker-controlled binary Protobuf input (`data` is the parameter that will be parsed) before any of that input has been validated. If parsing subsequently throws (malformed tag, truncated buffer, bad wire type, `checkLastTagWas:0` failure indicating trailing/unconsumed bytes, etc.), the method returns `NO` — but `GPBBecomeVisibleToAutocreator(self)` has already executed and is not undone in the `@catch` block.

This is the same "check performed after the state-changing action has already committed and been returned/exposed" pattern as the external report: in `LidoVault`, funds were transferred (and the function had effectively already "returned" by the time the `require(sent, ...)` check ran) so a failed transfer could not be caught. Here, the visibility mutation (`GPBBecomeVisibleToAutocreator`) is the analog of the fund transfer, and the parse-success check (the `@try`/`@catch` around `mergeFromCodedInputStream:`) is the analog of the `require(sent, ...)` check that is too late to prevent the side effect.

### Impact Explanation
For an ordinary client feeding bounded, otherwise-valid-looking but ultimately malformed/truncated binary Protobuf into the public `parseFromData:`/`mergeFromData:` API (which internally allocates the message via autocreation from a parent, then calls this method), a parse failure will leave the autocreated parent object graph permanently mutated to treat the (empty/partially-populated) submessage as "set" even though the caller receives an error/`nil`. Application code that relies on `hasX`/presence semantics of the parent message (a very common Protobuf idiom to distinguish "field not set" vs "field set to default") can be misled into believing a field is present when the actual content failed to parse, since the parent's has-bit / container state was already flipped by the autocreator visibility walk before the error was surfaced. This is a logic/integrity issue in consumption of parsed Objective-C messages, not a memory-safety or RCE issue, and is scoped to Objective-C generated message trees (this API is a supported public parse surface, and the bytes are fully attacker-controlled/bounded).

### Likelihood Explanation
Likelihood is moderate: it requires (a) the target submessage object to have been reached via Objective-C's lazy "autocreation" mechanism (i.e., accessed as a nested/child message property before being explicitly set — the standard way generated ObjC accessors work), and (b) the attacker-supplied bytes for that submessage to be malformed enough to throw inside `mergeFromCodedInputStream:` or fail `checkLastTagWas:0` (e.g. truncated varint, invalid wire type, or trailing garbage after top-level fields) while still reaching the call to `mergeFromData:` on that submessage. Both conditions are easily satisfiable by any external caller submitting arbitrary malformed but well-formed-looking wire bytes to a public Protobuf parse entry point, and no privileged access or hostile schema is required.

### Recommendation
Move `GPBBecomeVisibleToAutocreator(self)` to after the parse has been confirmed successful (i.e., after the `@try` block completes without throwing and `checkLastTagWas:0` succeeds), mirroring the general LidoVault-class fix of "check success before performing/finalizing the observable effect." If visibility must be established before parsing for correctness reasons (e.g., to support self-referential parsing), the mutation should instead be reverted/rolled back in the `@catch` block on failure so that a failed merge leaves the autocreated ancestor chain unaffected.

### Proof of Concept
1. In an Objective-C generated message `Parent` with an unset submessage field `child` of message type `Child`, access `parent.child` without setting it (this returns an autocreated placeholder `Child` per generated accessor semantics documented via `GPBBecomeVisibleToAutocreator` usage throughout `objectivec/GPBUtilities.m`).
2. Call `[parent.child mergeFromData:malformedChildBytes error:&err]` where `malformedChildBytes` is a truncated/invalid protobuf payload designed to make `mergeFromCodedInputStream:` throw (e.g., a length-delimited field whose declared length exceeds the remaining buffer) — this reaches the code at [1](#0-0)  and executes `GPBBecomeVisibleToAutocreator(self)` before the `@try` block runs.
3. Observe the method returns `NO` with `err` populated (parse failure reported correctly), but `parent.hasChild` is now `YES` (or `parent`'s serialization now includes an empty/partial `Child` submessage) because the autocreator-visibility side effect from step 2 was never reverted.
4. This demonstrates the state mutation "leaking through" despite the reported failure, analogous to funds being withdrawn (state already changed) even though the success check later fails in the LidoVault report.
