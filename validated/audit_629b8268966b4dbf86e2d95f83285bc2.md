## Analysis Result [1](#0-0) 

### Title
Signed integer overflow (UB) when negating `Duration.nanos == INT32_MIN` during ProtoJSON encoding - (File: `upb/json/encode.c`)

### Summary
`jsondec`/`jsonenc` in upb's JSON codec encode a parsed `google.protobuf.Duration` message by flipping the sign of `seconds` and `nanos` when they are negative, using the pattern `nanos = -nanos;` on a plain `int32_t`. Unlike `seconds`, whose magnitude is range-checked before negation, `nanos` is never bounds-checked against `INT32_MIN`, so an attacker-controlled `Duration.nanos` field set to `-2147483648` triggers undefined-behavior signed overflow on negation, exactly mirroring the reported GMX pattern of naively negating a signed value that may equal the type's minimum.

### Finding Description
`jsonenc_duration()` reads the wire-format `int32 nanos` field directly off the message with no bound enforcement other than a sign-consistency check against `seconds`: [2](#0-1) 

The guard clause only rejects `seconds` outside `[-315576000000, 315576000000]` and rejects a *sign mismatch* between `seconds` and `nanos` when both are non-zero. It never validates that `|nanos| < 1e9`, and — critically — never guards against `nanos == INT32_MIN`. When `seconds == 0` (so the sign-mismatch branch is not taken) and `nanos == INT32_MIN`, execution reaches `nanos = -nanos;`, which is signed-integer overflow, i.e. undefined behavior in C.

This is the identical bug class from the external report: a value coming from attacker-controlled data is unconditionally negated via `-x` and assigned back to a same-width signed type without checking for the type's minimum value first (the report's recommended fix, `SignedMath.abs()`/unsigned-negate-then-cast idiom, is exactly what would be needed here).

`Duration.nanos` is an ordinary `int32` field (not `sint32`), so any 32-bit value including `INT32_MIN` can be legally wire-encoded as a 10-byte varint and delivered to any consumer that: (1) parses the bytes into a `Duration` message via a public binary-parse API, and (2) subsequently serializes that message to ProtoJSON via `upb_JsonEncode`/`ToJson` — both fully public, unprivileged, bounded operations reachable by an ordinary client.

### Impact Explanation
Negating `INT32_MIN` is undefined behavior in C. In practice on two's-complement platforms this typically wraps back to `INT32_MIN` itself, which is then fed to `jsonenc_nanos()`/printf-style formatting expecting a small positive fractional value — producing corrupted/incorrect JSON output (a `nanos` component that is still negative or wildly out of the expected `[0, 999999999]` range) rather than a crash in the common case, but the behavior is compiler/optimization-level dependent and is a genuine UB defect that sanitizers (UBSan) will flag, and which can manifest as different results across compilers/optimization levels. This affects data integrity of the JSON serialization output for any application relying on ToJson round-tripping of `Duration` messages built from untrusted binary/ProtoJSON input.

### Likelihood Explanation
High reachability: `Duration.nanos = INT32_MIN` is a trivially constructible, fully valid (from a wire-format perspective) binary protobuf payload; the only requirement is that the consuming application first accepts an attacker-supplied `Duration` (or a message embedding one, e.g., via `Any`) through a standard `ParseFrom*` call and then serializes it back to JSON — a common, supported round-trip pattern (e.g., proxies/gateways translating binary to JSON).

### Recommendation
Before negating, check for the boundary value explicitly (mirroring the `SignedMath.abs()`-style fix recommended in the original report), e.g.:
```c
if (nanos < 0) {
  negative = true;
  if (nanos == INT32_MIN) {
    jsonenc_err(e, "bad duration");
  } else {
    nanos = -nanos;
  }
}
```
Additionally, add an explicit magnitude check (`nanos <= -1000000000 || nanos >= 1000000000` is invalid) alongside the existing sign-consistency check, so malformed `Duration` values are rejected outright rather than silently mis-encoded. Apply the same fix to the duplicated copies of this logic in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`, which contain byte-identical `jsonenc_duration`/`jsondec_duration` code. ### Proof of Concept
1. Construct a binary-encoded `google.protobuf.Duration` message with field 1 (`seconds`) unset/0 and field 2 (`nanos`) encoded as the varint for `-2147483648` (`INT32_MIN`), i.e. the 10-byte varint `80 80 80 80 f8 ff ff ff ff 01` for tag `0x10` (field 2, varint).
2. Parse it with any public API, e.g. `Duration::ParseFromString(bytes)` / `upb_Decode`, which will succeed since `int32` accepts the full 32-bit range.
3. Call the ProtoJSON encoder (`upb_JsonEncode` / `MessageToJson`) on the resulting message.
4. Execution reaches `upb/json/encode.c:197` (`nanos = -nanos;`) with `nanos == INT32_MIN`, causing signed-integer overflow (UB), detectable with `-fsanitize=undefined`, and producing an incorrect/garbage `nanos` component in the emitted JSON string instead of a properly range-validated error.

static void jsonenc_duration(jsonenc* e, const upb_Message* msg,
                             const upb_MessageDef* m) {
  const upb_FieldDef* seconds_f = upb_MessageDef_FindFieldByNumber(m, 1);
  const upb_FieldDef* nanos_f = upb_MessageDef_FindFieldByNumber(m, 2);
  int64_t seconds = upb_Message_GetFieldByDef(msg, seconds_f).int64_val;
  int32_t nanos = upb_Message_GetFieldByDef(msg, nanos_f).int32_val;
  bool negative = false;

  if (seconds > 315576000000 || seconds < -315576000000 ||
      (seconds != 0 && nanos != 0 && (seconds < 0) != (nanos < 0))) {
    jsonenc_err(e, "bad duration");
  }

  if (seconds < 0) {
    negative = true;
    seconds = -seconds;
  }
  if (nanos < 0) {
    negative = true;
    nanos = -nanos;
  }

  jsonenc_putstr(e, "\"");
  if (negative) {
    jsonenc_putstr(e, "-");
  }
  jsonenc_printf(e, "%" PRId64, seconds);
  jsonenc_nanos(e, nanos);
  jsonenc_putstr(e, "s\"");
}

static void jsondec_duration(jsondec* d, upb_Message* msg,
                             const upb_MessageDef* m) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  upb_MessageValue seconds;
  upb_MessageValue nanos;
  upb_StringView str = jsondec_string(d);
  const char* ptr = str.data;
  const char* end = ptr + str.size;
  const int64_t max = (uint64_t)3652500 * 86400;
  bool neg = false;

  /* "3.000000001s", "3s", etc. */
  ptr = jsondec_buftoint64(d, ptr, end, &seconds.int64_val, &neg);
  nanos.int32_val = jsondec_nanos(d, &ptr, end);

  if (end - ptr != 1 || *ptr != 's') {
    jsondec_err(d, "Malformed duration");
  }

  if (seconds.int64_val < -max || seconds.int64_val > max) {
    jsondec_err(d, "Duration out of range");
  }

  if (neg) {
    nanos.int32_val = -nanos.int32_val;
  }

  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 1),
                                   seconds, d->arena));
  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 2),
                                   nanos, d->arena));
}
