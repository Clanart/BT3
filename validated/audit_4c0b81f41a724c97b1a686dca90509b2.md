### Title
Cached FROST preprocess seed reused across messages leaks the MuSig secret share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to `setFlowLimit` changing a parameter without refreshing dependent state, `SigningProtocol::preprocess_internal` caches the FROST preprocess seed keyed only by `context` and never invalidates or rotates it when the message being signed changes. Because the nonces are derived deterministically from the cached seed alone, signing two different messages under the same context reuses identical nonces, enabling recovery of the validator's MuSig secret share.

### Finding Description
`preprocess_internal` stores a `CachedPreprocess` seed in `CachedPreprocesses` keyed by `context` (e.g., `(b"DkgConfirmer", attempt)`) and, on every subsequent call, rebuilds an `AlgorithmSignMachine` via `from_cache` with that same seed [1](#0-0) . In `seeded_preprocess`, the FROST nonces are generated solely from `ChaCha20Rng::from_seed(*seed.0)` — they do not depend on the message, so rebuilding the machine yields the exact same nonces and commitments [2](#0-1) .

`share_internal` calls `preprocess_internal` again to construct a fresh machine and then calls `sign` on it [3](#0-2) . Both `DkgConfirmer::share` and `DkgConfirmer::complete` invoke `share_internal`, and `complete` explicitly calls `share_internal` a second time, each time producing a signature share from the same cached seed [4](#0-3) . The signed message is `set_keys_message(&self.spec.set(), &removed, key_pair)`, which varies with the `key_pair` argument [5](#0-4) . The seed is never deleted from `CachedPreprocesses` after a share is produced, so nothing binds the cached nonce material to a single message — the exact "parameter changed but dependent state not updated" defect from the reference report.

### Impact Explanation
A Schnorr/FROST signature share has the form `z = d + b·ρ + λ·s·e`. If the same `(d, b)` nonces sign two distinct messages, the shares differ only in the challenge `e`; an observer with both shares solves for `λ·s` and recovers the validator's MuSig secret share. This is the documented catastrophic outcome of preprocess reuse: "Reuse will enable third-party recovery of your private key share" [6](#0-5) . Recovery of a validator's key share undermines the threshold signing set securing the DKG confirmation flow.

### Likelihood Explanation
The share messages are broadcast over the tributary protocol to all participants, so any participant in the signing set observes both shares. If `share` and `complete` are invoked with differing `key_pair` values for the same `(b"DkgConfirmer", attempt)` context — e.g., a competing or corrected `set_keys` proposal for the same attempt — the second `share_internal` call deterministically regenerates identical nonces and signs a different message. No caching delete or per-message keying exists in `preprocess_internal` to prevent this; the only guard is the implicit assumption that the same context always signs the same message, which is not enforced anywhere in the code.

### Recommendation
Include the message (or a binding commitment to it, such as the `key_pair`/message hash) in the `CachedPreprocesses` key, or delete the cached preprocess once a share is produced so a subsequent `share_internal` under the same context generates fresh nonces. Alternatively, make `share`/`complete` carry the constructed `AlgorithmSignMachine` forward (e.g., persist and reuse the same in-flight machine) rather than rebuilding it from the seed for each call.

### Proof of Concept
1. For a given attempt, the coordinator calls `DkgConfirmer::share(preprocesses, key_pair_A)`. `preprocess_internal` stores/loads seed `S` under context `(b"DkgConfirmer", attempt)`, `from_cache` → `seeded_preprocess` derives nonces `(d, b)` from `ChaCha20Rng::from_seed(S)`, and `sign` emits share `z_A = d + b·ρ_A + λ·s·e_A` for `msg_A = set_keys_message(set, removed, key_pair_A)`.
2. The coordinator then calls `DkgConfirmer::complete(preprocesses, key_pair_B, shares)` with `key_pair_B != key_pair_A`. `share_internal` again loads seed `S`, regenerates identical `(d, b)`, and emits `z_B = d + b·ρ_B + λ·s·e_B` for `msg_B`.
3. Both shares reference the same published preprocess (commitments for `d` and `b`), so `ρ` values are computable. An observer computes `s = (z_A - z_B - (b·ρ_A - b·ρ_B)) / (λ·(e_A - e_B))`, recovering the secret share.
4. Root cause: `CachedPreprocesses::set` is performed once per `context` and never invalidated; `from_cache` at `signing_protocol.rs:144-145` regenerates identical nonces while `share`/`complete` at lines 288-327 may bind different `key_pair`/message values.

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();

      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
