### Title
Missing non-zero participant check lets an attacker inject index 0 into the signing set, panicking the signer or binding shares to the group key - (File: crypto/frost/src/sign.rs)

### Summary
CVE-2017-15115 is a "missing context/namespace check" bug: `sctp_do_peeloff` failed to verify the object belonged to the intended namespace before operating on it. The Serai analog lives in `AlgorithmSignMachine::sign`: the signing set `included` is built entirely from attacker-controlled `HashMap` keys (the preprocesses' claimed `Participant` IDs), and the only bounds check enforced is the upper bound (`<= n`). The lower bound (`participant > 0`) — explicitly documented in `FrostError::InvalidParticipant`'s own message ("0 < participant <= {0}") — is never enforced, so an unprivileged counterparty can join the signing set under index `0`.

### Finding Description
In `crypto/frost/src/sign.rs:290-312`, `included` is assembled from `multisig_params.i()` plus every key of the externally supplied `preprocesses` map, then sorted. The code checks `included[last] > n` (line 302) and checks for duplicates (lines 306-310), but never checks `included[0] >= 1`. `Participant(0)` therefore passes validation and is fed into `self.params.keys.view(included.clone()).unwrap()` (line 312).

Participant index 0 is cryptographically special in threshold schemes: the group secret is the constant term `f(0)` of the shared polynomial, so evaluating the Lagrange coefficient / verification-share polynomial at `0` yields a coefficient of `1` and resolves to the group key itself rather than a per-participant share. Two reachable outcomes:

- If `ThresholdKeys::view`/`ThresholdView` rejects index 0 (the documented valid domain is `1..=n`), the `.unwrap()` at line 312 panics, crashing the honest signer's process from a single untrusted preprocess message — a direct analog of the CVE's system crash.
- If `view` accepts it, the attacker-claimed participant 0 is transcripted into `B`, gets binding factor `rho_0`, and `verify_share`/`verification_share(0)` in `complete` (sign.rs:476-477) validates their share against the group key rather than a real share — an incorrect verifier binding that also displaces any scalar offset applied to `included[0]`, aborting every signing session the attacker joins while appearing as a "valid" participant.

### Impact Explanation
An unprivileged party who can send a preprocess message (the exact input class the rules scope to `read_preprocess`/`sign`) can claim `Participant(0)`. In the worst verified path this panics `sign()` via `unwrap()` on `keys.view(...)`, crashing the signer. Otherwise it forces every co-signed session to abort and binds share verification to the group key under an incorrect formula. Either way a single malicious message deterministically kills the honest participant's signing operation — the same impact class (local denial of service / crash from a crafted input) as the kernel bug.

### Likelihood Explanation
Triggering requires only sending a preprocess keyed under index 0 to a coordinator/signer that keys its `preprocesses` map by the sender's claimed participant index — the natural way to build that map from received messages. No threshold collusion, no leaked keys, and no special privileges are needed; it works against any `AlgorithmMachine`/`AlgorithmSignMachine` user.

### Recommendation
Add the missing lower-bound check alongside the existing upper-bound check in `sign()`:

```rust
// crypto/frost/src/sign.rs, after line 295
if u16::from(included[0]) == 0 {
  Err(FrostError::InvalidParticipant(multisig_params.n(), included[0]))?;
}
```

Equivalently, validate `0 < p <= n` for every `p` in `included` (or inside `validate_map` in `crypto/frost/src/lib.rs:50`), and enforce the same domain inside `ThresholdKeys::view`/`ThresholdView` so the `.unwrap()` cannot panic on adversarial input.
