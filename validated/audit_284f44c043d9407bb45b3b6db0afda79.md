### Title
Silent swallowing of exceptions when computing offer coin additions causes a hard `KeyError` crash on attacker-supplied offers - (File: chia/wallet/trading/offer.py)

### Summary
The Apache Traffic Server CVE-2022-37392 is a CWE-754 "Improper Check for Unusual or Exceptional Conditions" bug: an exceptional/malformed condition while reading a client-supplied request is not properly checked, leading to a crash. The analogous pattern exists in Chia's offer-handling code, where an unexpected exception raised while parsing an untrusted, attacker-supplied `SpendBundle`/offer is silently swallowed instead of being safely rejected, leaving the object in an inconsistent state that a later code path dereferences unconditionally.

### Finding Description
`Offer.__post_init__` iterates over every `CoinSpend` in the (attacker-controlled, since offers are exchanged between untrusted counterparties) `_bundle` and calls `compute_spend_hints_and_additions` for each one to populate the `_additions` cache: [1](#0-0) 

Any exception other than `ValidationError` or the specific `"cost exceeded or below zero"` `ValueError` is caught by a bare `except Exception: continue` — the loop simply moves on without adding an entry to `adds` for that `cs.coin`. This means `self._additions` can end up **missing keys** for some of the coin spends in the bundle whenever the puzzle/solution triggers any other kind of exception during hint/addition computation (e.g. malformed CLVM structure, unexpected condition arguments, type errors while destructuring conditions in `compute_spend_hints_and_additions`).

Later, `_get_offered_coins()` — which is used to derive what asset is actually being offered when inspecting/accepting an offer — unconditionally indexes into that same dict for **every** coin spend in the bundle: [2](#0-1) 

If `parent_spend.coin` is one of the coins whose addition computation was silently skipped in `__post_init__`, `self._additions[parent_spend.coin]` raises an uncaught `KeyError` instead of a handled `ValidationError`. Because `Offer.__post_init__`'s broad exception net does not verify/re-raise the exceptional condition it caught, the object contract ("`_additions` has an entry for every coin spend") is silently violated, and the invariant is broken well before it is observed.

### Impact Explanation
A wallet user who receives/inspects a crafted offer (`.offer` file) from an untrupted counterparty can trigger this state mismatch: the puzzle reveal/solution for one spend is constructed so that `compute_spend_hints_and_additions` raises some exception that isn't the two explicitly handled cases (e.g. an `IndexError`/`TypeError`/`AssertionError` from unexpected CLVM shapes). This makes `Offer` object construction succeed with an incomplete `_additions` cache, and a subsequent, otherwise-routine call to summarize or accept the offer (`_get_offered_coins`, which feeds `get_offered_coins()`/summary/trade-manager acceptance flow) throws an unhandled `KeyError`. This matches the "spend-triggered transaction-processing halt" impact class: a malicious but syntactically valid spend bundle (delivered as an offer) can abort the wallet's offer-processing/acceptance path.

### Likelihood Explanation
Likelihood is limited by how easy it is to craft a coin spend whose puzzle/solution causes `compute_spend_hints_and_additions` to throw something other than the two explicitly anticipated exception types. This requires deeper knowledge of `compute_spend_hints_and_additions`'s internals (not fully inspected here due to index truncation) to construct a concrete puzzle/solution pair that reaches the generic `except Exception` branch. I was not able to fully trace `compute_spend_hints_and_additions` in `chia/wallet/util/compute_hints.py` within this investigation to confirm every code path that raises non-`ValueError`/non-`ValidationError` exceptions, so the exact trigger condition remains unverified.

### Recommendation
Replace the bare `except Exception: continue` in `Offer.__post_init__` with an approach that either (a) re-raises any exception not explicitly expected as a `ValidationError` so the `Offer` object is never constructed in an inconsistent state, or (b) explicitly excludes/skip-marks the coin from all downstream consumption (including `_get_offered_coins`) rather than silently omitting it from `_additions` while other code assumes full coverage. At minimum, `_get_offered_coins` should use `self._additions.get(parent_spend.coin, [])` defensively, and the underlying unexpected exception should be logged and surfaced as a rejected offer rather than swallowed.

### Proof of Concept
Not able to construct a concrete triggering puzzle/solution within this investigation, since it requires exercising an as-yet-unverified exception path inside `compute_spend_hints_and_additions` (in `chia/wallet/util/compute_hints.py`) that is not one of the two explicitly handled cases (`ValidationError`, or `ValueError("cost exceeded or below zero")`). This would need to be validated in a live environment/Devin session with the ability to run the wallet code to confirm a concrete crafted spend triggers the generic `except Exception` branch and subsequently the `KeyError` in `_get_offered_coins`.
