### Title
gh.sh flag-value `skip_next` bypass allows arbitrary flag injection (e.g. `--repo`) breaking repo-scoping guarantee - ([File: scripts/gh.sh])

### Summary
`scripts/gh.sh` is a wrapper that Claude Code agents invoke (via `allowed-tools: Bash(./scripts/gh.sh:*)` in `.claude/commands/triage-issue.md` and `.claude/commands/dedupe.md`) to interact with the `gh` CLI, with the explicit security guarantee that "All commands are scoped to the current repository via GH_REPO". The flag-parsing loop's `skip_next` mechanism trusts the token following any `FLAGS_WITH_VALUES` flag unconditionally, letting an attacker smuggle a disallowed flag (e.g. `--repo=attacker/x`) into `FLAGS[]` without any validation, which is then passed straight to `gh`, overriding `GH_REPO` and breaking the repo-scoping boundary.

### Finding Description
In the argument loop [1](#0-0) , once a flag such as `--state`, `--limit`, or `--label` is matched against `ALLOWED_FLAGS`/`FLAGS_WITH_VALUES` without `=` syntax, `skip_next` is set `true`, and on the very next iteration the code does:
```
if [[ "$skip_next" == true ]]; then
  FLAGS+=("$arg")
  skip_next=false
```
This unconditionally appends `$arg` to `FLAGS[]` with no check that `$arg` doesn't itself start with `-` and no re-validation against `ALLOWED_FLAGS`. An input sequence like `--state --repo=attacker/x` causes `--state` to set `skip_next=true`, then `--repo=attacker/x` is blindly appended as the "value" of `--state`, bypassing the `ALLOWED_FLAGS` allowlist entirely at line 51-60.

The resulting `FLAGS` array is passed directly to `gh` at lines 83/89/95, e.g. `gh issue list --state --repo=attacker/x`. Since `gh` CLI's `--repo` flag on the command line takes precedence over the `GH_REPO` environment variable exported at line 21, this overrides the intended repository scoping. The `search issues` query-text check for `repo:`/`org:`/`user:` qualifiers (lines 76-82) only inspects the positional search string, not injected flags, so it does not block this path.

The attacker-controlled surface is issue/PR body/title/comment text, which is fed to the Claude agent as untrusted context (`$ARGUMENTS` in `triage-issue.md`, issue content read via `gh.sh issue view`/`search issues` in `dedupe.md`). Via prompt injection in that content, an attacker can induce the agent (which has `allowed-tools: Bash(./scripts/gh.sh:*)`, i.e. no per-argument approval) to invoke `./scripts/gh.sh issue list --state --repo=<attacker-controlled-or-private-repo>` or `search issues "x" --limit --repo=<repo>`, exploiting the `skip_next` gap to escape the intended single-repo scope.

### Impact Explanation
This breaks the trust boundary the wrapper exists to enforce: "commands are scoped to the current repository." A successful injection lets the agent's `gh` invocation (running with whatever token/scopes the automation has) query, list, or search issues/labels in a different repository than the one the workflow is authorized for — potential information disclosure across repos accessible to the automation's credentials, and repo-scope confusion in automated triage/dedupe decisions. This matches "trust-boundary bypass / unauthorized cross-scope action" impact categories.

### Likelihood Explanation
Feasibility is high: the bug requires no privilege beyond being able to place text in an issue/PR/comment (ordinary repository content) that the Claude agent later reads and is convinced (via prompt injection) to act on with `./scripts/gh.sh`. Since `allowed-tools` grants blanket `Bash(./scripts/gh.sh:*)` access with no per-call human approval, and the flag/value logic itself is deterministic and always vulnerable to this pattern, this is reliably repeatable whenever the agent can be steered into emitting `<value-taking-flag> --repo=...` (or any other disallowed flag) as adjacent tokens.

### Recommendation
In the `skip_next` branch, validate that `$arg` does not match `^-` (or specifically re-run it through the allowlist logic) before appending it as a flag value; reject the argument list if a flag-expecting-a-value is immediately followed by another `-*` token instead of silently trusting it. Additionally, explicitly pass `--repo "$REPO"` last / hard-code it after `${FLAGS[@]}` so any injected `--repo` cannot override the trusted value (or strip `--repo`/`--repo=*` from `FLAGS[]` unconditionally regardless of allowlist logic bugs).

### Proof of Concept
Add a bash unit test invoking the script (with `gh` stubbed to just echo its argv) exercising:
```
GITHUB_REPOSITORY=owner/safe-repo ./scripts/gh.sh issue list --state --repo=attacker/evil
```
Expected (buggy) behavior: stub `gh` receives `issue list --state --repo=attacker/evil`, i.e. `--repo=attacker/evil` ends up in the argv despite not being in `ALLOWED_FLAGS`, and `gh`'s effective repo becomes `attacker/evil` instead of `owner/safe-repo`.
Expected (fixed) behavior: the script should either error out (`Error: only --comments, --state, --limit, --label flags are allowed`) or `--repo` should never reach `gh`'s effective resolution ahead of the enforced `GH_REPO`/explicit `--repo "$REPO"`.   if [[ "$skip_next" == true ]]; then
    FLAGS+=("$arg")
    skip_next=false

      if [[ "$flag" == "$allowed" ]]; then
        matched=true
        break
      fi
    done
