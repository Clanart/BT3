### Title
Partial line-selection state is silently reapplied against a changed diff, corrupting what the user commits - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
`updateChangedFiles` in [1](#0-0)  reuses a file's previous `DiffSelection` object (which encodes selected/deselected lines by absolute index via `divergingLines`) whenever a background `git status` refresh finds a file with the same ID, without re-validating that the line indices still map to the same content. This is analogous to the EsEMBR.sol bug class: a value that determines what gets "included" (rewards / committed lines) is carried forward across an underlying state change (balance burn / working-tree content change) without being recomputed, so the user acts on stale state.

### Finding Description
`DiffSelection` tracks selection purely as a set of numeric line indices (`divergingLines`) relative to a specific diff's hunk layout [2](#0-1) . Every time `git status` is refreshed (on file-watcher events, focus regain, after fetch/pull/checkout, background indicator refresh, etc.), `_loadStatus` calls `updateChangedFiles`, which — for every file that still exists by ID — blindly does `file.withSelection(existingFile.selection)` [3](#0-2) , copying the old, index-based selection onto the new `WorkingDirectoryFileChange`, regardless of whether the file's on-disk content (and thus its diff/hunk shape) has changed since the selection was made.

The only place that re-validates line indices against a fresh diff is `updateChangesWorkingDirectoryDiff`, and it does so **only for the single currently-selected/open file**, by calling `withSelectableLines` after loading a new diff [4](#0-3) . Files that are not the one currently open in the diff viewer never get this reconciliation — their stale `divergingLines` set (indices into the *old* diff) is carried forward untouched into the working-directory file list that is used at commit time.

At commit time, `_commitIncludedChanges` selects files purely by `file.selection.getSelectionType() !== DiffSelectionType.None` [5](#0-4)  and passes those files straight to `createCommit`. The patch text is then built by `formatPatch`, which decides per-line inclusion via `file.selection.isSelected(absoluteIndex)` computed against the **current** diff’s hunks [6](#0-5) . Because `absoluteIndex` is only a positional index (`hunk.unifiedDiffStart + lineIndex`), if the file's content shifted (lines added/removed) between when the user made a partial selection and when the background status refresh re-applied that same `DiffSelection` object to the newer file entry, the indices in `divergingLines` no longer correspond to the same logical lines. The patch generator will happily select/deselect lines by position, not by content identity.

### Impact Explanation
This breaks the invariant "what the user visually selected for commit is what actually gets committed" for any file the user is not actively viewing in the diff pane. A file's working-tree content can change out from under a stale selection through several unprivileged, attacker-influenced paths:
- Files rewritten by post-checkout/post-merge/post-commit hooks that ship inside an attacker-controlled cloned/fetched repository [7](#0-6) , triggered automatically during `pull`/`fetch`/`checkout` flows that Desktop performs (e.g. `fastForwardBranches`, `performFetch`) which are always followed by `_refreshRepository` → `_loadStatus` [8](#0-7) [9](#0-8) .
- Any external process/editor rewriting a tracked file while a status refresh happens to race with it (file watcher-driven refreshes are frequent and automatic).

Because the corrupted selection is silent (no UI indication that indices are now misaligned) and directly affects `formatPatch`'s line-inclusion logic, the practical outcomes are: unintended content silently included in a commit (e.g. lines the user explicitly deselected reappear because their old index now points at different, newly-inserted content), or intended content silently dropped from the commit. Either way this is "silent corruption of what the user commits or pushes," matching the stated valid-impact class.

### Likelihood Explanation
Medium. The trigger conditions (a background status refresh happening while a non-active file retains a partial/line-level selection, combined with that file's content changing underneath, e.g., via hook execution during fetch/pull/checkout) are realistic in normal Desktop usage without any local/admin access or social engineering — they only require the user to have partially staged a file and for a routine, automatic refresh to occur, which the app performs constantly (file-watcher events, focus regain, after every push/pull/fetch) [10](#0-9) . It requires precise timing/content shifts to produce a specific desired corruption, which somewhat limits reliable weaponization, but the underlying missing-invalidation is verifiably always active — no code path revalidates non-active files' `divergingLines` against the new diff shape, as confirmed by `updateChangedFiles`'s unconditional `file.withSelection(existingFile.selection)`.

### Recommendation
In `updateChangedFiles` (or in `updateConflictState`/wherever the merged file list is built), do not reuse a stale `DiffSelection` as-is when the file's content/diff shape may have changed. At minimum:
- Track a content fingerprint (e.g., the file's `blob`/`oid` or a hash of the diff) alongside the selection, and drop/reset partial selections (falling back to `withIncludeAll`/full selection or requiring re-review) whenever that fingerprint differs from the one recorded when the selection was made — not only for the actively-viewed file.
- Alternatively, invalidate (`withSelectableLines` reconciliation or full reset to “all”/“none”) partial selections for *all* files on every status refresh, not just the currently open one, whenever `clearPartialState` isn't already forcing it.
- Surface a warning in the UI when a file's underlying diff changed after a partial selection was made, forcing explicit user re-confirmation before it is included in a commit.

### Proof of Concept
1. In Desktop, open a repository and modify `fileA.txt`, staging only some lines (partial selection) via the line-level diff gutter, without leaving `fileA.txt` as the currently-open diff.
2. Simulate the effect of hooks/an attacker-controlled remote: while `fileA.txt`'s partial selection is retained in state, externally rewrite `fileA.txt` on disk in a way that shifts line positions (e.g., insert a line above the previously-selected block) — this can be triggered by a `post-checkout`/`post-merge` hook shipped in a maliciously crafted repository that Desktop fetches/pulls/checks out.
3. Trigger any background status refresh (file-watcher event, regain focus, or an automatic `_refreshRepository` following the fetch/pull) so that `updateChangedFiles` runs and reapplies the old `DiffSelection` object onto the updated `fileA.txt` entry (verified in `app/src/lib/stores/updates/changes-state.ts:43-60`, which is unconditional/unvalidated for non-active files).
4. Commit — `_commitIncludedChanges`/`formatPatch` will include/exclude lines by the stale absolute indices against the new diff (`app/src/lib/patch-formatter.ts:143-171`), producing a commit whose content differs from what the user last visually reviewed/selected, with no warning shown.

export function updateChangedFiles(
  state: IChangesState,
  status: IStatusResult,
  clearPartialState: boolean
): ChangedFilesResult {
  // Populate a map for all files in the current working directory state
  const filesByID = new Map<string, WorkingDirectoryFileChange>()
  state.workingDirectory.files.forEach(f => filesByID.set(f.id, f))

  // Attempt to preserve the selection state for each file in the new
  // working directory state by looking at the current files
  const mergedFiles = status.workingDirectory.files

            DiffSelectionType.Partial
          ) {
            return file.withIncludeAll(false)
          }
        }

        return file.withSelection(existingFile.selection)

        return file
      }
