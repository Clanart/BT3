### Title
Deadline parameter passed to underlying Wombat Pool swaps is always `block.timestamp` at execution time, providing no expiration/staleness protection - (File: wombat/WombatStaking.sol, wombat/SmartWomConvert.sol)

### Summary
`WombatStaking.deposit()`/`withdraw()` and `SmartWomConvert._convertFor()` are reachable from any unprivileged wallet (via `WombatPoolHelper`/`AnkrBNBPoolHelper` for staking, or directly for conversion), and each forwards a deadline value to the underlying Wombat AMM (`IWombatPool.deposit/withdraw`, `IWombatRouter.swapExactTokensForTokens`) that is hardcoded to `block.timestamp` at the moment of execution, not a user-supplied expiry. This mirrors the exact bug class in the referenced report ([M-06] Missing deadline check for AfEth actions): a "deadline" mechanism that can never actually expire, offering zero protection against stale/pending transactions being executed later at a bad, MEV-exploitable rate.

### Finding Description
`WombatStaking.deposit()` transfers user's deposit token and calls the pool with `block.timestamp` as the deadline: [1](#0-0) 

Similarly `WombatStaking.withdraw()` passes `block.timestamp` to `IWombatPool.withdraw`: [2](#0-1) 

Both entrypoints are reachable by any ordinary wallet through `WombatPoolHelper.deposit()`/`withdraw()` (and `depositNative`), which simply forward to `WombatStaking`: [3](#0-2) [4](#0-3) 

The same pattern exists in `SmartWomConvert._convertFor`, which is directly external via `convert()`/`convertFor()`, and swaps WOM for mWOM on the Wombat router using `block.timestamp` as the deadline argument: [5](#0-4) [6](#0-5) 

Because `block.timestamp` is evaluated inside the same transaction that performs the swap, the "deadline" check inside the pool/router (`deadline` must be `>= block.timestamp`) is trivially always satisfied no matter how long the transaction sits in the mempool. This is functionally equivalent to having no deadline at all — the exact root cause identified in the referenced report for AfEth's `deposit()`/`withdraw()`, where lack of a real (user-supplied, pre-committed) deadline lets a transaction be executed at an arbitrary later time under a stale, no-longer-representative price.

### Impact Explanation
A user's deposit/withdraw/convert transaction submitted with a `_minimumLiquidity`/`_minAmount`/`_minRec` slippage bound computed against the current pool state can remain pending in the mempool (e.g., during network congestion or through validator/searcher manipulation) and later be executed once market/pool conditions have shifted unfavorably. Since the slippage bound was computed for stale conditions, the transaction still satisfies the (now outdated) minimum-out check but executes at a worse effective rate than the user intended, and the swap can be sandwiched by MEV actors for a guaranteed profit at the user's expense. Because `WombatStaking` and `SmartWomConvert` directly custody and swap significant user funds (LP deposits/withdrawals and mWOM conversions), this results in a direct theft of user funds via MEV extraction on unprivileged, high-value user transactions.

### Likelihood Explanation
Likelihood is moderate-to-high: no privileged role is required, any user calling `deposit`, `withdraw`, `convert`/`convertFor`, or `smartConvert` is exposed whenever their transaction is delayed in the mempool (congestion, low gas price, or intentional delay by a searcher), which is a common occurrence on public networks. The exploit only requires observing a pending transaction and either delaying it or sandwiching it — both are routine, well-known MEV techniques (as referenced in the original report).

### Recommendation
Add a user-supplied `deadline` parameter to `WombatStaking.deposit()`, `WombatStaking.withdraw()`, `SmartWomConvert.convert()`/`convertFor()`/`smartConvert()` (and their `PoolHelper` wrappers), and revert if `block.timestamp > deadline`. Then forward that same deadline (not `block.timestamp`) to the underlying `IWombatPool`/`IWombatRouter` calls so that a stale transaction cannot be executed after the user's intended validity window has passed.

### Proof of Concept
1. User calls `WombatPoolHelper.deposit(amount, minimumLiquidity)` with `minimumLiquidity` computed from the current WOM/asset exchange rate; this reaches `WombatStaking.deposit()`.
2. The transaction is broadcast but remains pending (e.g., low gas price, network congestion, or deliberately held by a searcher who observes it in the mempool).
3. Pool price for the deposit asset moves unfavorably for the user (or a searcher sandwiches the trade around it).
4. The transaction is eventually mined; because `WombatStaking.deposit()` passes `block.timestamp` (evaluated at mining time) as the deadline to `IWombatPool.deposit`, the pool's deadline check trivially passes.
5. `minimumLiquidity` is still satisfied (since it was computed loosely or the sandwich is calibrated to sit just above it), so the deposit executes, but the user receives materially fewer LP/receipt tokens than they would have at submission time — the difference is captured by the delaying/sandwiching party.
