### Title
Missing fee-metadata invalidation in `dispatchIncoming(GetResponse)` allows the same relayer fee to be paid twice (relayer payout + later timeout refund) - (File: evm/src/core/EvmHost.sol)

### Summary
The external report's core invariant is: "a fee is transferred out immediately/irrevocably while the accounting record that guards it is never cleared, so the same fee can later be paid out a second time to a different party." The local analog is in `EvmHost`'s GET-request fee lifecycle: when a `GetResponse` is successfully delivered, the relayer fee is paid out of `_requestCommitments[commitment]` but that mapping entry is never deleted, unlike the equivalent timeout paths which explicitly delete it for "replay protection." This leaves the door open for the same fee to be paid again via the GET-timeout path.

### Finding Description
`EvmHost.dispatchIncoming(GetResponse memory response, address relayer)` pays the relayer fee directly from `_requestCommitments[commitment].fee` after a successful `onGetResponse` callback, but does not delete/zero the entry afterward: [1](#0-0) 

Contrast this with `dispatchTimeOut` for `GetRequestTimeout`/`PostRequestTimeout`, where `_requestCommitments[commitment]` is explicitly deleted first ("replay protection") and only re-inserted if the module callback fails: [2](#0-1) 

The `HandlerV2` entrypoints that drive these two paths use different, unrelated replay guards:
- `handleGetResponses` blocks duplicates via `host.responseReceipts(...).relayer != address(0)`.
- `handleGetRequestTimeouts` blocks a timeout submission only via a *non-membership proof* of the response receipt in Hyperbridge's own state trie at an admin/relayer-chosen historical height `message.height`, and a local timestamp comparison `request.timeout() > state.timestamp`: [3](#0-2) 

Because `_stateCommitments` entries for old heights are never removed as new heights arrive (only a governance "veto" clears one), any state height that was finalized *before* Hyperbridge actually recorded/committed the response receipt remains permanently available and provably valid for a non-membership proof — even after the response has since been delivered and paid out on the source host. `dispatchTimeOut(GetRequestTimeout, meta, commitment)` re-reads `meta.fee` from `host.requestCommitments(commitment)` — which is untouched by the earlier successful response delivery — and refunds it to `meta.sender`: [4](#0-3) 

Since GET requests are explicitly documented as skipping timeout validation at the point of response delivery ("don't check for timeouts because it's checked on Hyperbridge"), a response can be legitimately delivered and paid to a relayer close to or slightly after the nominal timeout window, while an older, already-finalized state height (predating the response's inclusion in Hyperbridge's trie) is still available on the host for constructing a valid non-membership proof for the timeout path.

### Impact Explanation
This is a direct fund-loss/double-settlement bug on the fee escrow held by `EvmHost`: the same relayer fee amount is paid out twice from the host's `feeToken` balance — once to the relayer (`dispatchIncoming(GetResponse,...)`), and once refunded to the original payer (`dispatchTimeOut(GetRequestTimeout,...)`) — draining host-held fee token reserves that back other users' pending requests. This matches the bounty's "duplicate settlement/double-claim" and "unauthorized transaction/fund loss" categories, executed entirely through permissionless, public entrypoints (`handleGetResponses` and `handleGetRequestTimeouts`), requiring no malicious relayer, prover, or admin — any caller holding legitimate proofs from two different (but both valid) historical Hyperbridge state heights can trigger it.

### Likelihood Explanation
Exploitation requires only that: (1) a GET request's response is delivered at or slightly past its nominal timeout, and (2) an older already-finalized state height on the host — one whose timestamp already exceeds the request's `timeoutTimestamp` but whose ISMP trie predates the response's inclusion — is still queryable. Both conditions arise naturally from the host's own retention of all historical `_stateCommitments` and the explicit design choice to skip timeout checks during response delivery, making this a realistic, low-cost timing window rather than requiring any protocol violation or compromised actor.

### Recommendation
In `dispatchIncoming(GetResponse memory response, address relayer)`, delete (or zero out) `_requestCommitments[commitment]` immediately after the fee is paid to the relayer, mirroring the "replay protection" pattern already used in the timeout dispatch functions. Additionally, `handleGetRequestTimeouts` should reject non-membership proofs taken from a state height that predates the height at which the response could plausibly have been recorded, or the host should track a definitive "responded" flag consulted by both code paths instead of relying solely on non-membership proofs against arbitrary historical heights.

### Proof of Concept
1. App dispatches a `GetRequest` via `EvmHost.dispatch(DispatchGet)` with a nonzero `fee`; `_requestCommitments[commitment] = {sender: payer, fee: F}` is recorded (`evm/src/core/EvmHost.sol:974-1013`).
2. Shortly after (at or slightly past) the request's `timeoutTimestamp`, a relayer submits a valid `GetResponseMessage` via `HandlerV2.handleGetResponses` for a recent Hyperbridge state height; this succeeds since no timeout check is performed here (`evm/src/core/HandlerV2.sol:217-247`), and `EvmHost.dispatchIncoming(GetResponse,...)` pays fee `F` to the relayer without clearing `_requestCommitments[commitment]` (`evm/src/core/EvmHost.sol:824-847`).
3. The attacker then submits `HandlerV2.handleGetRequestTimeouts` using an older state height `h` that the host still has recorded in `_stateCommitments`, where `state[h].timestamp >= request.timeout()` and the response receipt is (truthfully) absent from Hyperbridge's trie at that historical height (`evm/src/core/HandlerV2.sol:293-321`).
4. `EvmHost.dispatchTimeOut(GetRequestTimeout,...)` re-reads `meta.fee = F` (still present because step 2 never cleared it), calls `onGetTimeout` on the module, and on success refunds `F` again to `payer` (`evm/src/core/EvmHost.sol:856-877`).
5. Net result: fee `F` has been paid out twice from the host's fee-token balance for a single request — once to the relayer, once to the payer.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;

            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
    }
