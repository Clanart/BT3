## Analysis

The Flayer/UniswapV4 bug's core invariant: **when a user supplies native token for a swap/liquidity operation, any un-consumed portion must be returned to the original payer — otherwise it becomes permanently trapped in the intermediary contract.** Hyperbridge's `IntentGatewayV2`/`IntentsBase` contracts explicitly guard against this pattern everywhere they touch native tokens (`placeOrder`, `fillOrder`, `_fillSameChain` all refund `msgValue` leftovers, per [1](#0-0) , [2](#0-1) ). However, `EvmHost.sol` — the core ISMP host contract that every app dispatches through — has the exact unguarded analog.

## Title
Native-token overpayment on `EvmHost.dispatch()`/`fundRequest()` is permanently locked in the host contract instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and swap it for an exact amount of `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`. This is an exact-output swap: any ETH beyond what's needed to buy the requested fee amount is refunded by the Uniswap router — but to `msg.sender` of the swap call, which is `EvmHost` itself, not the original caller (`_msgSender()`) who sent the `msg.value`. Unlike `IntentGatewayV2`, `EvmHost` never forwards this leftover native balance back to the caller, and no sweep/withdraw path exists for it.

### Finding Description
In all three functions:
```solidity
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [3](#0-2) [4](#0-3) [5](#0-4) 

`swapETHForExactTokens` only spends the ETH necessary to produce `post.fee`/`get.fee`/`amount` output tokens and refunds the rest — to `msg.sender`, i.e. `address(this)` (`EvmHost`), because `EvmHost` is the account that called the router with `{value: msg.value}`. There is no subsequent code in any of these three functions that forwards this refunded excess back to `_msgSender()`. Because relayer-fee pricing is denominated in an ERC20 `feeToken` while payment is optionally in native token, and the exact ETH cost of an exact-output swap fluctuates with pool price at execution time, callers cannot pre-compute the exact `msg.value` needed — some overpayment margin is the normal, expected usage pattern (this is exactly analogous to `IntentGatewayV2.placeOrder`'s fee-swap path, which the docs explicitly warn about and which is why that function refunds unspent `msgValue`, see [6](#0-5) ). `EvmHost` has no equivalent refund logic and, per the code searched, no governance/admin sweep function for a stray native balance accumulated this way.

### Impact Explanation
Any unprivileged app, user, or contract calling `dispatch()`/`fundRequest()` with native-token payment and even minimal overpayment (unavoidable given price movement between quote and execution) permanently loses the excess ETH into `EvmHost`. This is direct, unrecoverable fund loss for ordinary protocol users — matching the bounty's "stealing or loss of funds" category — with no malicious relayer, prover, or admin involved; it is triggered purely by normal usage of a public entrypoint.

### Likelihood Explanation
High. Any caller sending native ETH to pay Hyperbridge dispatch fees via the local AMM swap will almost always overpay by some margin (to guard against price movement/slippage between quote time and execution), and 100% of that margin is lost every single time these functions are used with `msg.value` payment. This is not an edge case — it is the default/expected usage pattern for native-fee payment as documented.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, check `address(this).balance` (or track ETH balance before/after) and refund any leftover native balance to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`/`fillOrder`.

### Proof of Concept
1. Call `EvmHost.dispatch(DispatchPost{... fee: 10e6 feeToken units ...})` with `msg.value = 1 ether`, where the router only needs `0.3 ether` worth of ETH to produce `10e6` feeToken via `swapETHForExactTokens`.
2. `swapETHForExactTokens` consumes `0.3 ether` and refunds `0.7 ether` back to `msg.sender` of the swap call — `EvmHost`.
3. `EvmHost`'s ETH balance increases by `0.7 ether` and the function returns without forwarding any of it to the original caller.
4. Repeat for any number of callers/transactions; the excess ETH accumulates in `EvmHost` with no code path to reclaim it for the payers, and no admin/governance sweep function was found for this balance in the reviewed contract.

            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
