## Title
Silent commit corruption via stale line-selection indices reused against a re-fetched diff (TOCTOU) - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
The DODO bug is a class of "state not re-synchronized with a changed accounting record": `liquidate()` computes and stores an updated per-loan `record.amount` but never re-derives the pool-wide `totalBorrows` from the same event, so a stale aggregate silently diverges from the true state and corrupts the exchange rate used by every other user. The GitHub Desktop analog is the same invariant break applied to partial-commit staging: a `DiffSelection` (a set of *line indices*) is computed against one snapshot of a file's diff, but is later replayed against a **freshly re-fetched diff** of the same file at commit time, with no check that the line indices still refer to the same content. If the working-directory file changes between the two diff computations (which a malicious repository can trigger via a `post-checkout`/`post-merge` hook, a smudge/clean filter, or any script the cloned repo runs), the wrong lines get staged and committed, silently, with no error, no confirmation, and no visual mismatch to the user.

### Finding Description
`DiffSelection` stores selection state purely as a set of "diverging" absolute line indices, with no binding to file content or a diff version/hash: [1](#0-0) 

When the Changes view loads a diff for display, GitHub Desktop is aware that the diff can shift underneath a stale selection and only partially compensates by re-deriving `selectableLines` — explicitly noting the limitation in its own comment: [2](#0-1) 

That mitigation only prunes lines that no longer exist; it does nothing to guarantee that the *content* at a given absolute index in the new diff is the same content the user actually reviewed and selected earlier.

The real corruption path is at commit time. `_commitIncludedChanges` takes the `WorkingDirectoryFileChange` objects (with their `DiffSelection`, built against whatever diff was last rendered in the UI) straight from `repositoryStateCache` and hands them to `createCommit`: [3](#0-2) 

`createCommit` → `stageFiles` routes any partially-selected file to `applyPatchToIndex`: [4](#0-3) 

`applyPatchToIndex` does **not** reuse the diff the user looked at — it independently re-fetches a brand-new diff of the file right before staging: [5](#0-4) 

That fresh diff is then formatted using `formatPatch`, which walks the **new** diff's hunks and, for every non-context line, asks the stale `file.selection.isSelected(absoluteIndex)` whether that absolute index (computed from the new diff) was selected: [6](#0-5) 

`DiffSelection.isSelected` has no way to know the diff changed — it just answers "was line index N in my divergingLines set", regardless of what content now lives at index N: [7](#0-6) 

**The corrupted value**: the set of line indices considered "selected" for staging (`DiffSelection.divergingLines`), when interpreted against a diff computed at a different point in time than the one that produced those indices. There is no diff identity/hash comparison, no re-validation of selection content, and no user-visible warning anywhere between diff-load and `git apply --cached`.

**Why existing guards don't stop it**: `updateChangesWorkingDirectoryDiff` only prunes indices that fall outside the new set of `selectableLines`; it does not detect that surviving indices might now point at *different* lines because of insertions/deletions elsewhere in the file. `_commitIncludedChanges` performs no re-diff/re-validation before staging — it trusts the state-cache snapshot. `applyPatchToIndex` deliberately re-fetches the diff (for a legitimate reason — to reflect the very latest working tree — see the code comment about "the index knows of the removed file") but this reintroduces the exact same mismatch the app-store code was aware of, without the compensating `selectableLines` pruning step.

### Impact Explanation
If a cloned repository ships a hook or tooling (e.g. `post-checkout`, `post-merge`, or any script triggered while the app is open and the user is reviewing/selecting partial diff hunks) that rewrites a tracked file's content — e.g. adding/removing lines above the hunk the user is inspecting — the user's line selection silently shifts onto unrelated lines when they click Commit. This is exactly "silent corruption of what the user commits or pushes": the user believes they staged line X, but `git apply --cached` stages whatever line now occupies that absolute index in the newly-fetched diff. Depending on content, this can exfiltrate/commit secrets the user explicitly deselected, revert unrelated fixes, or inject attacker content into a commit the user then pushes upstream — all without any error dialog, since `git apply` succeeds as long as the patch is structurally valid.

### Likelihood Explanation
Exploitation requires precise timing (the file must change between the time the user's diff/selection state was computed and the moment they click Commit) and depends on the attacker's ability to trigger file mutation from within the repository itself (hooks/filters/build scripts) while the app is focused on that file. This is plausible but non-trivial to reliably weaponize, and the window is normally short — this places it as a real but moderate-likelihood race rather than a trivially reproducible bug on every commit.

### Recommendation
- Bind each `DiffSelection` to an identity/hash of the diff it was computed against (e.g., diff content hash or `unifiedDiffStart`/hunk signature), and refuse to stage (or force a full re-diff + re-render + explicit re-confirmation) if the diff used by `applyPatchToIndex` doesn't match the one the user's selection was computed from.
- Alternatively, have `applyPatchToIndex` reuse the exact diff object last rendered/validated in the UI rather than independently re-fetching, and only re-fetch defensively when it can prove equivalence (e.g. by comparing blob OIDs) with the previously-approved diff.
- Surface a hard error/warning to the user ("file changed since you reviewed it — re-review before committing") instead of silently applying a patch computed against outdated line semantics.

### Proof of Concept
1. Clone a malicious repository containing a `post-checkout` (or similarly triggerable) hook script that appends/removes lines to a tracked file it knows the victim is likely to review (e.g., a config file), timed to fire a few seconds after checkout/open.
2. In GitHub Desktop, open the Changes view, select the file, and manually deselect a specific sensitive hunk/line via `_changeFileLineSelection` (recorded as `divergingLines` in `DiffSelection`) — see `app/src/lib/stores/app-store.ts:3887-3894` and `app/src/models/diff/diff-selection.ts:41-84`.
3. While the user is composing the commit message, the malicious script (already running from step 1, or triggered by another repo-controlled event) inserts/removes lines earlier in the same file, shifting absolute line indices.
4. The user clicks Commit. `_commitIncludedChanges` (`app-store.ts:3681`) stages the file via `stageFiles`→`applyPatchToIndex` (`apply.ts:52-81`), which re-fetches the diff fresh and calls `formatPatch` (`patch-formatter.ts:143-171`), applying the stale `DiffSelection` indices to the new hunk layout.
5. Result: the actual staged/committed content differs from what the user selected and reviewed, with no warning — confirming silent corruption of what is committed.

/**
 * An immutable, efficient, storage object for tracking selections of indexable
 * lines. While general purpose by design this is currently used exclusively for
 * tracking selected lines in modified files in the working directory.
 *
 * This class starts out with an initial (or default) selection state, ie
 * either all lines are selected by default or no lines are selected by default.
 *
 * The selection can then be transformed by marking a line or a range of lines
 * as selected or not selected. Internally the class maintains a list of lines
 * whose selection state has diverged from the default selection state.
 */
export class DiffSelection {
  /**
   * Initialize a new selection instance where either all lines are selected by default
   * or not lines are selected by default.
   */
  public static fromInitialSelection(
    initialSelection: DiffSelectionType.All | DiffSelectionType.None
  ): DiffSelection {
    if (
      initialSelection !== DiffSelectionType.All &&
      initialSelection !== DiffSelectionType.None
    ) {
      return assertNever(
        initialSelection,
        'Can only instantiate a DiffSelection with All or None as the initial selection'
      )
    }

    return new DiffSelection(initialSelection, null, null)
  }

  /**
   * @param divergingLines Any line numbers where the selection differs from the default state.
   * @param selectableLines Optional set of line numbers which can be selected.
   */
  private constructor(
    private readonly defaultSelectionType:
      | DiffSelectionType.All
      | DiffSelectionType.None,
    private readonly divergingLines: Set<number> | null = null,
    private readonly selectableLines: Set<number> | null = null
  ) {}
