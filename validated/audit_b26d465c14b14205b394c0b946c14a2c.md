## Title
Stale line-index selection is silently re-applied to a fresh working-directory diff at commit time, causing unreviewed content to be staged and committed - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop tracks a partial commit selection as a set of purely positional line indices (`DiffSelection`, keyed by `divergingLines`/`selectableLines`), decoupled from the actual line content of the diff the user reviewed. This selection is only re-validated against a fresh diff when that specific file's diff is actively being *displayed* in the UI. When the commit is created, `applyPatchToIndex` re-fetches a brand-new working-directory diff and blindly re-applies the old, positional selection to it, with no re-validation and no comparison to the diff the user actually looked at.

### Finding Description
`DiffSelection.isSelected(lineIndex)` and `isSelectable(lineIndex)` operate purely on line-index numbers (`divergingLines: Set<number>`), with no binding to line content or hunk identity [1](#0-0) . The only place this positional selection is reconciled against a newly loaded diff is `updateSelectionAfterDiffLoad` in `app-store.ts`, which recomputes `selectableLines` — but only for the file that is *currently selected/displayed* in the Changes view [2](#0-1) . The code comment there explicitly acknowledges this is best-effort and not content-aware: "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..." [3](#0-2) .

When the working directory status refreshes for *any other reason* (file watcher event, `_loadStatus`, background refresh), `updateChangedFiles` simply carries the old selection object forward unchanged as long as the file ID still matches, with no re-validation against a new diff: `return file.withSelection(existingFile.selection)` [4](#0-3) . This means a file's selection can become stale relative to its on-disk content for as long as its diff panel isn't actively open, which is the normal case for every file except the one the user is currently viewing.

At commit time, `_commitIncludedChanges` passes the (possibly stale) `WorkingDirectoryFileChange.selection` straight into `createCommit`/`stageFiles`/`applyPatchToIndex` [5](#0-4) . Critically, `applyPatchToIndex` does **not** reuse the diff the user reviewed; it calls `getWorkingDirectoryDiff` again, fetching a fresh diff of the current on-disk content, and then builds the patch by testing `file.selection.isSelected(absoluteIndex)` against the *new* diff's hunk/line layout [6](#0-5) , [7](#0-6) . If the file's content shifted between the time the user made their line selection and the time of the commit (e.g. new lines inserted earlier in the file by a formatter, linter, build tool, IDE auto-save, or any other process writing into the working tree — none of which requires local/physical access, since these can be entirely automated background tooling the user already has running), the "same" line indices now point at different, unreviewed lines.

This is directly analogous to the WJLP bug: an operation (`unwrap`/withdraw of tokens) proceeds on the caller's *current* state while relying on a stale, un-refreshed accounting value (`_userUpdate` never called) from before the state change. Here, `applyPatchToIndex` proceeds against the *current* diff while relying on a stale, un-refreshed selection (line indices) computed against the diff as it existed before the state change (file edit) — the guard that exists (`updateSelectionAfterDiffLoad`) only fires for the actively-viewed file, not universally before every commit.

### Impact Explanation
This can silently corrupt what the user commits and subsequently pushes: content the user never reviewed or intentionally selected can be staged and committed, while content they did intend to include can be silently dropped, without any warning dialog (the "hidden changes" filter warning only covers file-list filtering, not selection/diff drift — see `isCommittingFileHiddenByFilter` usage in `filter-changes-list.tsx`, which is a separate, unrelated safeguard) [8](#0-7) . In an adversarial supply-chain scenario (e.g. a repository pulling in a pre-commit/build/watch tool, editor extension, or `postinstall` script that touches source files after the user has visually reviewed and partially staged a diff but before they click "Commit"), this can be leveraged to smuggle attacker-influenced lines into a commit the developer believes only contains the lines they explicitly reviewed and clicked to select.

### Likelihood Explanation
Moderately likely in practice: any auto-formatter, linter-on-save, live-reload/build watcher, or slow background script writing to a file between "user reviews and partially selects lines" and "user clicks Commit" will shift line offsets. The window is the entire time the Changes tab isn't showing that file's diff, which is common when a developer stages several files in sequence before committing. No special privileges or local file-system access beyond what any dev-tooling already has is required — this fits the "attacker controls ... a git remote/proxy response" / build-tooling class of untrusted input reaching the working tree, and results in "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories.

### Recommendation
Before applying a partial patch (`applyPatchToIndex`) or immediately before commit, re-run `updateSelectionAfterDiffLoad`-style reconciliation (or an equivalent content-aware diff) for every file with a `Partial` selection, not just the currently displayed one, and abort/re-prompt the user if the underlying diff has changed since the selection was made. Consider binding selection state to line content hashes or hunk identifiers rather than raw positional indices so that content drift is detected rather than silently re-mapped.

### Proof of Concept
1. Modify `file.md` and open its diff in Desktop; use "Discard"/line selection to select only a subset of lines (creating a `DiffSelectionType.Partial` `WorkingDirectoryFileChange`).
2. Without switching the Changes selection back to `file.md` (e.g., select a different file in the sidebar), have an external process append/insert lines earlier in `file.md` (simulating an auto-formatter/build tool), shifting hunk offsets.
3. Return to the Changes list, keep the same partial selection (no diff view of `file.md` is reopened, so `updateSelectionAfterDiffLoad` never runs for it), and commit.
4. Inspect the resulting commit via `getChangedFiles`: because `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`) and applies the old positional `divergingLines` to the new hunk layout, the committed content does not correspond to the lines originally selected/reviewed by the user, and can include lines never seen or intended for commit — matching the "existing selectable-lines reconciliation" logic acknowledged as incomplete in `app-store.ts:3480-3486`.
