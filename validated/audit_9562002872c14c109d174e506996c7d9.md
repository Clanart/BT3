### Title
CR-CAT "pending approval" payments can be permanently locked with no escape hatch if no authorized VC provider ever approves them - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
When a Credential-Restricted CAT (CR-CAT) payment is sent to a recipient who cannot yet prove they hold a Verified Credential (VC) from one of the CR-CAT's `authorized_providers`, the coin is routed into an intermediate "pending approval" puzzle hash (`construct_pending_approval_state`) instead of the recipient's own inner puzzle. The only code path that can ever move this coin out of the pending-approval state (`CRCATWallet.claim_pending_approval_balance`) hard-requires a `VerifiedCredential` issued by one of the `authorized_providers`. There is no time-based or otherwise permissionless fallback path allowing the recipient to reclaim the coin if no provider ever issues (or re-issues) them a valid VC.

### Finding Description
`check_for_requested_payment_modifications` in `chia/wallet/trade_manager.py:1021-1069` rewrites CR-CAT offer payments so that funds destined for a recipient without a currently provable VC go to `construct_pending_approval_state(payment.puzzle_hash, payment.amount)` [1](#0-0) , which curries the target puzzle hash into an announcement-gated puzzle: [2](#0-1) .

The wallet tracks such coins as `CoinType.CRCAT_PENDING` and reports them in `get_pending_approval_balance()` [3](#0-2) .

The *only* function that can spend a `CRCAT_PENDING` coin into the recipient's spendable balance is `claim_pending_approval_balance`. It unconditionally looks up a VC from an authorized provider and aborts if none exists: [4](#0-3) 

That VC must in turn be produced by a `DIDWallet` whose DID matches one of the `authorized_providers` on the CR-CAT (`add_vc_authorization` similarly requires a VC from an authorized provider for on-chain movement, see `chia/wallet/vc_wallet/vc_wallet.py:439-484`). The underlying CLVM puzzle (`CREDENTIAL_RESTRICTION`, curried via `construct_cr_layer`) is solved with `solve_cr_layer`, which always requires `proof_of_inclusions`, `provider_id`, `vc_launcher_id`, and `vc_inner_puzhash` — i.e., cryptographic proof tied to a specific authorized provider's live, unrevoked VC singleton [5](#0-4) . There is no relative/absolute timelock condition or alternate spend branch in this flow that lets the coin owner reclaim the coin without provider cooperation.

This mirrors the Opyn/Sherlock M-3 pattern precisely: a user's coin sits in a state where the *only* forward path depends on a privileged third party (here, an "authorized provider"/DID operator, analogous to the Opyn `owner`) performing an action (issuing/renewing a VC with valid, non-expired/non-revoked proofs). If that provider:
- never issues the recipient a VC in the first place,
- lets the VC's proofs expire without reissuing an inclusion proof against a fresh Merkle root,
- revokes the VC via `activate_backdoor()` (`chia/wallet/vc_wallet/vc_drivers.py:757-799`), or
- loses its DID signing key / becomes unresponsive or malicious,

then the recipient's CR-CAT funds sitting in `CoinType.CRCAT_PENDING` are permanently unspendable, with no code path (timeout, escape hatch, or alternative claim) that lets the coin owner recover the value.

### Impact Explanation
Funds legitimately paid to a user (e.g., the taker side of an offer, or any CR-CAT transfer to a not-yet-verified recipient) can become permanently locked if the credential-issuing authority never cooperates. This is a direct "unauthorized/impossible coin movement" condition — value is provably created on-chain (the pending-approval coin exists and is owned by the recipient's committed puzzle hash) but can never be spent by that recipient absent third-party action, with no time-bound recourse. This matches the "spend-triggered transaction-processing halt" / "coin permanently unspendable" impact category (funds frozen indefinitely), which is a Medium/High-severity denial-of-access issue for any wallet user or offer counterparty who ends up on the receiving side of a CR-CAT trade without (or who later loses) an approving VC.

### Likelihood Explanation
This is reachable by any ordinary wallet user who is the taker/recipient of a CR-CAT offer or transfer and does not (yet, or ever) hold a matching VC — a state explicitly built into the normal offer-taking flow (`check_for_requested_payment_modifications`), not an edge case requiring a malicious peer. The dependency on a specific `authorized_providers` DID cooperating is entirely analogous to the Sherlock M-3 admin-dependency pattern: it requires no attacker action beyond the provider becoming unavailable, unwilling, or compromised, which is a realistic operational risk for any credential-restricted asset with third-party KYC/AML providers.

### Recommendation
Introduce a time-bound, permissionless escape path for coins sitting in the CR-CAT "pending approval" state, analogous to the clawback puzzle's `ASSERT_SECONDS_RELATIVE` timelock (`chia/wallet/puzzles/clawback/drivers.py:70-135`) or the pool protocol's `pay_to_singleton_or_delay_puzzle` delayed-claim mechanism (`chia/wallet/puzzles/singleton_top_layer.py:267-301`). For example, after a configurable timelock has elapsed without a valid VC-authorized claim, the recipient (or original sender) should be able to reclaim the coin's value directly to a plain puzzle hash without needing any `authorized_providers` VC proof, ensuring credential-provider unavailability or malice cannot permanently freeze user funds.

### Proof of Concept
1. Wallet A creates a CR-CAT (CAT with `authorized_providers = [DID_X]`) and offers/sends it to Wallet B.
2. Wallet B has no VC issued by `DID_X` (or its previously issued VC's proofs have expired/been revoked via `activate_backdoor`).
3. `check_for_requested_payment_modifications` (chia/wallet/trade_manager.py:1047-1056) routes the payment to `construct_pending_approval_state(B_puzzle_hash, amount)`; the coin is recorded as `CoinType.CRCAT_PENDING` in Wallet B (`add_crcat_coin`, chia/wallet/vc_wallet/cr_cat_wallet.py:244-277).
4. Wallet B calls `crcat_approve_pending` / `claim_pending_approval_balance` to try to claim the funds.
5. `vc_wallet.get_vc_with_provider_in_and_proofs(self.info.authorized_providers, ...)` returns `None` because `DID_X` never issued (or revoked) a VC to B, causing `RuntimeError(f"No VC exists that can approve spends for CR-CAT wallet {self.id()}")` (chia/wallet/vc_wallet/cr_cat_wallet.py:717-718).
6. No other function in the codebase can move a `CoinType.CRCAT_PENDING` coin to a spendable state; Wallet B's funds remain locked indefinitely regardless of elapsed time, as long as `DID_X` does not cooperate.

```python
def construct_pending_approval_state(puzzle_hash: bytes32, amount: uint64) -> Program:
    return PENDING_VC_ANNOUNCEMENT.curry(Program.to([[51, puzzle_hash, amount, [puzzle_hash]]]))
```

```python
    async def get_pending_approval_balance(self, record_list: set[WalletCoinRecord] | None = None) -> uint128:
        if record_list is None:
            record_list = await self.wallet_state_manager.coin_store.get_unspent_coins_for_wallet(
                self.id(), CoinType.CRCAT_PENDING
            )
        amount: uint128 = uint128(0)
        for record in record_list:
            crcat: CRCAT = self.coin_record_to_crcat(record)
            if not crcat.lineage_proof.is_none():
                amount = uint128(amount + record.coin.amount)

        self.log.info(f"Pending approval balance for cat wallet {self.id()} is {amount}")
        return uint128(amount)
```
