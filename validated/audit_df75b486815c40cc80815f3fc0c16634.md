`RewardMintingAmount` (`reward.mintingamount`) is the closest analog to the reported `setApys` issue: it directly controls token inflation ("tokenomics"), yet its `FormatChecker` is `noopFormatChecker`, meaning no bound is enforced (not even non-negativity), unlike `RewardMinimumStake`, which explicitly checks `v.Sign() >= 0`.

### Title
Missing bounds/sign validation on `reward.mintingamount` governance parameter enables unbounded token-inflation manipulation - ([File: kaiax/gov/param.go])

### Summary
The `RewardMintingAmount` governance parameter, which determines the per-block minting reward (the primary inflation source of the KAIA token economy), is registered with `FormatChecker: noopFormatChecker`, i.e., no validation is performed on the value at all. Every other numeric tokenomics-relevant parameter (e.g. `RewardMinimumStake`, `RewardRatio`, `RewardKip82Ratio`) has an explicit `FormatChecker` enforcing non-negativity or the correct percentage-sum, but `RewardMintingAmount` does not.

### Finding Description
`gov.Params[RewardMintingAmount]` is defined with `Canonicalizer: bigIntCanonicalizer` and `FormatChecker: noopFormatChecker`, which always returns `true`: [1](#0-0) 

`noopFormatChecker` unconditionally accepts any canonical value: [2](#0-1) 

By contrast, the structurally similar `RewardMinimumStake` parameter enforces `v.Sign() >= 0`, and `RewardRatio`/`RewardKip82Ratio` enforce percentage-sum invariants, showing that the codebase's own convention is to validate these tokenomics-affecting parameters: [3](#0-2) 

`bigIntCanonicalizer` itself performs no sign or magnitude check — it merely parses the string/bytes into a `*big.Int`: [4](#0-3) 

The parameter value is stored via `ParamSet.Set()` without any additional validation and is consumed directly by the reward engine to compute the per-block minting reward, which is split among validators and funds: [5](#0-4) [6](#0-5) 

This value flows through header-vote governance (`checkConsistency` explicitly passes `RewardMintingAmount` through with no extra checks beyond format) or through the on-chain `GovParam` contract's `setParamIn`, both of which rely solely on `Params[name].FormatChecker` for value sanity: [7](#0-6) 

### Impact Explanation
Since `reward.mintingamount` directly determines `MintingReward` split among validators/funds every block, the absence of a sanity check (e.g., disallowing negative values, zero, or absurdly large values) means a governance actor able to submit this parameter can either halt/corrupt reward computation (negative amounts propagating into `big.Int` arithmetic used for reward splitting) or set an arbitrarily large inflation amount, directly inflating token supply beyond intended economic parameters — the same "impact to tokenomics" class described in the reported `setApys` issue.

### Likelihood Explanation
The governance parameter path (header-vote `GovernanceGoverningNode`/single-mode voting, or `GovParam.setParamIn` contract call) is one of the explicitly in-scope reachable paths (governance parameters) per the analog rules. Because `noopFormatChecker` performs zero validation, any successful vote/contract call setting this parameter—regardless of how privileged the submission mechanism is—will be accepted without a value sanity check, unlike its sibling parameters which do enforce checks. This mirrors exactly the "no validation of new value" bug class from the reported issue.

### Recommendation
Add a `FormatChecker` for `RewardMintingAmount` analogous to `RewardMinimumStake`'s, e.g. reject nil/negative values and optionally enforce a sane upper bound (e.g., relative to current default or previous value) to prevent uncontrolled tokenomics manipulation:
```go
FormatChecker: func(cv any) bool {
    v, ok := cv.(*big.Int)
    if !ok {
        return false
    }
    return v.Sign() >= 0
},
```

### Proof of Concept
1. A governing node (single-mode governance) or an actor with `GovParam` contract write access submits a vote/`setParamIn` call for `reward.mintingamount` with value `"-1"` or an extremely large integer (e.g. `2^256-1`).
2. `bigIntCanonicalizer` parses the string into a `*big.Int` without any sign check.
3. `noopFormatChecker` returns `true` unconditionally, so `NewVoteData`/`setParamIn` accepts the value.
4. `checkConsistency()` in `header.go` also does not add any bound check for `RewardMintingAmount`, letting the vote pass verification.
5. Once activated, `NewRewardConfig()` reads this value into `rc.MintingAmount` and `RewardRatio.Split`/`SplitFlex` uses it directly in `big.Int` multiplication to compute minting rewards for validators and funds each block, propagating the unvalidated value directly into the token supply calculation.
