### Title
Unhandled `StopIteration` crash when parsing malformed CLVM output conditions in wallet coin-spend processing - ([File: chia/wallet/util/compute_additions.py])

### Summary
`compute_additions_with_cost()` (and the structurally identical `compute_spend_hints_and_additions()`) iterate over the output conditions produced by running an untrusted puzzle reveal + solution, and blindly call `next()` on a per-condition iterator without guarding against an empty/malformed condition entry. This mirrors the CVE-2021-33446 pattern: `mjs_next()` dereferenced state produced by an iterator without validating that a "next" element actually existed, causing a NULL pointer crash. Here, `next(atoms)` on an exhausted/empty iterator raises an uncaught `StopIteration`, crashing the wallet code path that is processing a coin spend whose puzzle output is attacker-influenced (e.g., an offer counterparty's puzzle, or a CAT/NFT/DID/singleton coin spend being synced).

`cond` here is one element of the CLVM output list produced by running `cs.puzzle_reveal` against `cs.solution` — both of which are attacker-controlled data embedded in a `CoinSpend` (e.g. inside an offer, an NFT/DID/CAT/singleton spend being parsed by the wallet, or a coin spend received while syncing). If the output program yields a condition entry that is `()` (an empty/atom "nil"), `cond.as_iter()` returns an empty iterator. The first `next(atoms)` call then raises `StopIteration` instead of returning a value, and nothing in this function catches it.

The identical unguarded pattern exists in `chia/wallet/util/compute_hints.py`: [2](#0-1) 

Both helpers are consumed throughout wallet code that must process spends whose puzzle/solution content is not fully trusted by the local wallet — e.g. `chia/wallet/trading/offer.py`, `chia/wallet/trade_manager.py`, `chia/wallet/cat_wallet/cat_wallet.py`, `chia/wallet/nft_wallet/nft_wallet.py`, `chia/wallet/did_wallet/did_wallet.py`, `chia/wallet/vc_wallet/vc_drivers.py`, `chia/wallet/vc_wallet/cr_cat_wallet.py`, `chia/pools/pool_wallet.py`, `chia/wallet/singleton.py`, `chia/data_layer/data_layer_wallet.py`, and `chia/wallet/wallet_state_manager.py`. [3](#0-2) 

Unlike full-node consensus condition parsing (`chia/consensus/condition_tools.py:parse_sexp_to_condition`), which explicitly checks `first is None` / `op is None` and raises a `ConsensusError`, these wallet-side helper functions perform no such defensive checks before consuming the iterator via `next()`. [4](#0-3) 

### Impact Explanation
A malicious offer counterparty or a coin whose puzzle output is crafted to emit a degenerate (empty/nil) condition entry can cause `StopIteration` to propagate uncaught out of `compute_additions_with_cost`/`compute_spend_hints_and_additions`. Depending on the call site, this halts wallet-side processing of that trade/spend/sync operation (a spend-triggered transaction-processing halt for the affected wallet), potentially blocking legitimate progress (e.g., inability to evaluate/accept an offer, or a crash during coin-state syncing for CAT/NFT/DID/singleton/VC coins) until the code is patched or the offending spend is otherwise avoided.

### Likelihood Explanation
Reaching this requires only crafting a puzzle/solution pair (fully within the attacker's control, e.g. as the maker of a Chia offer, or the owner of a coin whose spend is being synced/inspected by the victim's wallet) whose CLVM output includes a nil ("()") entry in the top-level condition list. No signature or special permissions are needed beyond normal offer/coin-spend interaction, so likelihood is reasonably high for a determined counterparty.

### Recommendation
Harden `compute_additions_with_cost()` and `compute_spend_hints_and_additions()` to validate that each condition entry is a non-empty list (i.e., `cond.pair is not None` / has an atom `first`) before calling `next()`, mirroring the defensive `first is None` / `op is None` checks already used in `chia/consensus/condition_tools.py:parse_sexp_to_condition`. Malformed/empty condition entries should be skipped or raise a handled `ValidationError` rather than allowing an unguarded `StopIteration`/`AttributeError` to propagate.

### Proof of Concept
1. Construct a `CoinSpend` whose `puzzle_reveal`, when run against `solution`, returns a CLVM list containing at least one `()` (nil) entry as a top-level "condition", e.g. a puzzle equivalent to `(mod (solution) (c () (list_of_other_conditions)))`.
2. Feed this `CoinSpend` into any wallet flow that calls `compute_additions`/`compute_additions_with_cost` or `compute_spend_hints_and_additions` on it — e.g., present it as part of an offer (`chia/wallet/trading/offer.py`) or as a coin spend encountered while the wallet syncs/parses a CAT/NFT/DID/singleton coin.
3. When the vulnerable function iterates that condition (`atoms = cond.as_iter(); op = next(atoms).atom`), `cond.as_iter()` yields nothing, and `next(atoms)` raises an uncaught `StopIteration`, crashing/aborting the calling wallet operation.

def parse_sexp_to_condition(sexp: Program) -> ConditionWithArgs:
    """
    Takes a ChiaLisp sexp and returns a ConditionWithArgs.
    Raises an ConsensusError if it fails.
    """
    first = sexp.pair
    if first is None:
        raise ConsensusError(Err.INVALID_CONDITION, ["first is None"])
    op = first[0].atom
    if op is None or len(op) != 1:
        raise ConsensusError(Err.INVALID_CONDITION, ["invalid op"])

    # since the ConditionWithArgs only has atoms as the args, we can't parse
    # hints and memos with this function. We just exit the loop if we encounter
    # a pair instead of an atom
    vars: list[bytes] = []
    for arg in Program(first[1]).as_iter():
        a = arg.atom
        if a is None:
            break
        vars.append(a)
        # no condition (currently) has more than 3 arguments. Additional
        # arguments are allowed but ignored
        if len(vars) > 3:
            break

    return ConditionWithArgs(ConditionOpcode(op), vars)
