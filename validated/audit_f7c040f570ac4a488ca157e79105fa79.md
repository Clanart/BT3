### Title
`SignableTransaction::new` does not include the `OP_RETURN` output in the fee/weight calculation, so user-supplied `data` produces an under-priced transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The audit-issue bug class is "a caller accepts a payload but fails to pass it to the inner consumer" (Allo.sol failing to forward `msg.value` to `strategy.registerRecipient`). In `bitcoin-serai`, `SignableTransaction::new` accepts an optional `data` payload, appends a real `OP_RETURN` `TxOut` to the transaction's outputs, but never passes that output into `calculate_weight_vbytes` — the function that determines the vbytes the fee is computed from. The `data` is "received" by the constructor but not "passed on" to the fee accounting.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`):

- Lines 194-202 push the `OP_RETURN` output into `tx_outs` when `data` is `Some` — this output is part of the real, signed transaction.
- Lines 204 and 225-226 call `calculate_weight_vbytes(tx_ins.len(), payments, ...)` — only `payments` (and optionally `change`) are used to build the synthetic transaction whose `tx.weight()` is measured (lines 68-99). The `OP_RETURN` output is absent from that synthetic transaction.
- `needed_fee = fee_per_vbyte * vbytes` (lines 206, 227) therefore prices a transaction that is smaller than the one actually constructed.

When a `change` address is provided, the change output's value is set to `input_sat - payment_sat - fee_with_change` (line 228-230), so the effective fee is exactly `fee_with_change` — a fee computed for a transaction missing up to ~91 bytes (80-byte push + output overhead). The finalized transaction is strictly larger than the priced transaction, so its actual fee rate is strictly below the caller-specified `fee_per_vbyte`.

The minimum-fee check at line 211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) is also computed against the under-counted `vbytes`, so a caller that requests the minimum viable fee rate produces a signed transaction whose true fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` and will not relay.

### Impact Explanation
An unprivileged user can supply instruction data that flows into `SignableTransaction::new` as `data` (up to the 80-byte limit enforced at line 171). Combined with a `change` output and a fee rate near the relay minimum, the resulting transaction — which the threshold group signs via `TransactionSignMachine::sign` (lines 355-398) — has an actual fee rate below the minimum relay fee and will be rejected or sit unconfirmed in mempools. The transaction is validly signed, so the inputs are committed to this under-priced transaction; recovering requires coordinating an entirely new signing round for a replacement. This is "funds sent but effectively stuck" analogous to value trapped in the Allo contract instead of reaching the strategy. Severity: Medium — no permanent loss, but a reachable path to producing an unpropagatable signed transaction and an incorrect fee formula.

### Likelihood Explanation
- `data` is attacker/user-influenced (arbitrary bytes up to 80 bytes).
- `change` is routinely present in the wallet flow.
- Any `fee_per_vbyte` chosen near the minimum relay boundary makes the signed output non-relayable; higher requested fee rates merely produce a fee rate silently lower than requested, degrading confirmation reliability.
- No collusion, malicious validator, or leaked key is required — only control of the `data` field.

### Recommendation
Include the `OP_RETURN` output in the weight calculation. Either pass the full set of outputs (payments + `OP_RETURN` + change) into `calculate_weight_vbytes`, or add the serialized size of the `OP_RETURN` `TxOut` (8-byte value + compact-size script length + script bytes) to the computed weight before deriving `needed_fee`. Also re-run the minimum-relay check against the true final vbytes.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Construct a SignableTransaction with data and a change output:

let payments = &[(recipient_script, 100_000u64)];
let data = Some(vec![0xAA; 80]); // max permitted by the len check
let tx = SignableTransaction::new(
    inputs,                 // prevouts summing > 100_000 + fee
    payments,
    Some(change_script),    // change present -> effective fee = needed_fee
    data,
    1,                      // 1 sat/vbyte, at the relay-minimum boundary
).unwrap();

// The signed transaction serializes larger than the measured one:
assert!(tx.transaction().weight().to_wu() >
        // weight priced by calculate_weight_vbytes, which never saw the
        // OP_RETURN output pushed at lines 194-202
        /* weight of synthetic tx built from `payments` + `change` only */);

// Actual fee rate = needed_fee / actual_vbytes < 1 sat/vbyte,
// i.e. below bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE, so the signed
// transaction will not relay, despite passing the check at line 211.
```

The root cause is exactly the audited bug class: `new` accepts `data`, commits it to the real output set, but fails to forward it to `calculate_weight_vbytes`, leaving the computed fee stale relative to the transaction that is actually signed.

Caveat: I verified the code path in `send.rs` directly; I did not trace the coordinator path that populates `data` from user instructions end-to-end, so the "unprivileged user controls `data`" claim rests on the documented OutInstruction data flow rather than a full call-chain read.
