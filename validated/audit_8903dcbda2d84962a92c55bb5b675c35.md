## Title
Missing reentrancy protection in `IntentGatewayV2.placeOrder` (Tron variant) enables ERC777-style over-crediting of escrow — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder()` has **no reentrancy guard** at all, unlike the mainline EVM contract at `evm/src/apps/IntentGatewayV2.sol:162`, which is explicitly protected with `nonReentrant` (`ReentrancyGuardTransient`). [1](#0-0)  The Tron contract's `placeOrder` is declared `public payable` with no modifier at all: [2](#0-1)  and the file never imports or inherits `ReentrancyGuard`/`ReentrancyGuardTransient`. [3](#0-2) 

### Finding Description
This is the same broken invariant as the PolygonZkEvmBridge ERC777 report: a token-callback hook (ERC777 `tokensToSend`, or an ERC20/ERC1363-style callback token on Tron/TRC20 equivalents) fires during `safeTransferFrom`, before the transfer/escrow bookkeeping for the outer call completes, and is used to re-enter the escrow entry-point.

In the Tron `placeOrder`, escrow accounting is accumulative: after computing `reducedInputs` and `commitment`, each input token amount is added into a persistent per-commitment/per-token map:

```
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
``` [4](#0-3) 

Because `_orders[commitment][token]` is credited unconditionally after each `safeTransferFrom` call, and there is no reentrancy lock, an attacker using a callback-enabled token can register a transfer hook and re-enter `placeOrder` from within the token's `transferFrom` call. Each nested/reentrant `placeOrder` invocation stamps a **new, unique commitment** (via `order.nonce = _nonce++` and `commitment = keccak256(abi.encode(order))`), so the attacker is not amplifying a single order the way the original report amplified a single deposit leaf — instead the attacker can interleave multiple `placeOrder` calls whose token-pull side effects overlap in time due to the callback firing mid-transfer. Since the escrow credit (`_orders[...] += amount`) is applied per call based on the *reduced amount requested*, not on a verified post-transfer balance delta, and there is no `nonReentrant` guard preventing overlapping in-flight `placeOrder` executions, the actual amount of tokens pulled into the contract can diverge from the sum of amounts credited to `_orders`, exactly mirroring the ERC777 balance-diff exploit primitive (state committed based on an assumption that does not hold under reentrant call-hook execution).

Notably the predispatch branch of the *mainline* EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol:198-298`) explicitly documents awareness of this exact class of bug ("For fee-on-transfer tokens, the gateway receives less than the requested amount... to reflect actual received so the commitment and escrow are consistent") and is guarded by `nonReentrant`. [5](#0-4)  The Tron contract implements the equivalent escrow logic but omits both the reentrancy guard and, in its non-predispatch path, the received-balance verification, relying purely on `safeTransferFrom` succeeding for the nominal amount. [4](#0-3) 

### Impact Explanation
If exploitable with a TRC20/callback token accepted by the gateway, this allows an attacker to create escrow credits (`_orders[commitment][token]`) that are later redeemable via `RedeemEscrow`/fill/cancel flows without a matching real balance backing them in the contract — a direct fund-loss/insolvency vector against the shared custody pool, draining tokens deposited by other legitimate order-placers. This matches the bounty's "stealing or loss of funds" and "false state acceptance" (escrow state not reflecting real custody) categories.

### Likelihood Explanation
The precondition — a token with a transfer-time callback hook usable by the token holder (`from`) being accepted by the gateway — is plausible since the gateway accepts arbitrary ERC20-shaped tokens by address with no allowlist visible in the reviewed code, and the vulnerability requires only an unprivileged attacker interacting with public `placeOrder`, no relayer/prover/admin compromise. However, I could not confirm within this review whether Tron's TRC20 standard or the specific token contracts intended for use with this gateway actually support ERC777-style `tokensToSend`/transfer hooks, nor whether the sibling functions (`fillOrder`, `cancelOrder`) in the same Tron file carry their own guards that would block the attack downstream (redemption side). This uncertainty affects confidence in end-to-end exploitability versus code-level absence of the defense that the primary EVM contract deliberately implements.

### Recommendation
Add `nonReentrant` (or an equivalent lock) to `IntentGatewayV2.placeOrder`, `fillOrder`, and `cancelOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, matching the protection already present in `evm/src/apps/IntentGatewayV2.sol`. Additionally, replace the unconditional `_orders[commitment][token] += reducedInputs[i].amount` credit with a received-balance-delta check (`balanceOf(this)` before/after `safeTransferFrom`) as already done in the non-predispatch branch of the mainline contract, so escrow bookkeeping can never diverge from actual custodied balance regardless of callback-token behavior.

### Proof of Concept
Conceptual PoC (not executed against a live deployment — no test harness for the Tron contract was found in this review):
1. Attacker registers/uses a transfer-hook-enabled token accepted by the Tron `IntentGateway`.
2. Attacker calls `placeOrder(orderA, ...)` with `inputs[0].amount = A` for that token.
3. During the internal `safeTransferFrom(msg.sender, address(this), A)`, the token's transfer hook fires and re-enters `placeOrder(orderB, ...)` (unique nonce/commitment) before `orderA`'s `_orders[commitment][token] += reducedInputs[i].amount` write and/or before the real token balance change is finalized.
4. Both `orderA` and `orderB` are credited in `_orders` mapping based on nominal requested amounts rather than a verified balance delta, while the actual net tokens pulled from the attacker can be made less than the sum credited (e.g., by having the reentrant call use `amount=0`/partial transfers before the outer transfer completes), producing over-credited escrow redeemable later via the `RedeemEscrow` request path — draining the shared token pool.         // Validate that order has inputs
        if (order.inputs.length == 0) revert InvalidInput();

        address hostAddr = host();
        // fill out the order preludes
        order.user = bytes32(uint256(uint160(msg.sender)));
        order.source = IDispatcher(hostAddr).host();
        order.nonce = _nonce++;

        // Calculate reduced inputs (after protocol fees) for commitment and escrow
        uint256 inputsLen = order.inputs.length;
        // Use destination-specific protocol fee, fallback to source chain fee if zero
        bytes32 destinationHash = keccak256(order.destination);
        uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
        if (protocolFeeBps == 0) {
            protocolFeeBps = _params.protocolFeeBps;
        }
        TokenInfo[] memory reducedInputs;
        bytes32 commitment;

        if (protocolFeeBps > 0) {
            reducedInputs = new TokenInfo[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                uint256 originalAmount = order.inputs[i].amount;
                uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
                uint256 reducedAmount = originalAmount - protocolFee;
                address token = address(uint160(uint256(order.inputs[i].token)));

                // Emit DustCollected for protocol fee if non-zero
                if (protocolFee > 0) emit DustCollected(token, protocolFee);

                reducedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: reducedAmount});
                unchecked {
                    ++i;
                }
            }

            // Temporarily swap inputs to calculate commitment with reduced amounts
            TokenInfo[] memory originalInputs = order.inputs;
            order.inputs = reducedInputs;
            commitment = keccak256(abi.encode(order));
            order.inputs = originalInputs;
        } else {
            // No protocol fees, use order.inputs directly
            reducedInputs = order.inputs;
            commitment = keccak256(abi.encode(order));
        }

        // escrow tokens
        uint256 msgValue = msg.value;
        if (order.predispatch.call.length > 0 && order.predispatch.assets.length > 0) {
            address dispatcher = _params.dispatcher;

            // Transfer all predispatch assets to the call dispatcher
            uint256 assetsLen = order.predispatch.assets.length;
            for (uint256 i; i < assetsLen;) {
                address token = address(uint160(uint256(order.predispatch.assets[i].token)));
                uint256 amount = order.predispatch.assets[i].amount;

                if (token == address(0)) {

            ICallDispatcher(dispatcher).dispatch(order.predispatch.call);

            // Transfer tokens from call dispatcher back to IntentGateway
            Call[] memory transferCalls = new Call[](inputsLen);

                uint256 balance;

                if (token == address(0)) {
