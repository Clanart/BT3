### Title
Nil-pointer dereference on unpacked EVM transaction in `filterTransactions` crashes public RPC nodes - ([File: evmrpc/utils.go])

### Summary
`filterTransactions` in `evmrpc/utils.go` calls `m.AsTransaction()` on a decoded `*types.MsgEVMTransaction` and immediately dereferences the result with `ethtx.Hash()` without checking for `nil`. Elsewhere in the same package, the identical call is explicitly guarded because the authors document that `AsTransaction()` "may return nil if it fails to unpack the tx data." This is the same bug class as CVE-2022-50388: a code path assumes a field/return value is always populated and dereferences it unconditionally, while a sibling code path in the same codebase proves the value can legitimately be `nil` under conditions the first path doesn't defend against.

### Finding Description
`filterTransactions` iterates the messages of every transaction in a block and, for `*types.MsgEVMTransaction` entries that are not "associate" transactions, does:

```go
case *types.MsgEVMTransaction:
    if m.IsAssociateTx() {
        continue
    }
    ethtx, _ := m.AsTransaction()
    hash := ethtx.Hash()
``` [1](#0-0) 

`AsTransaction()`'s error is discarded and `ethtx` is dereferenced unconditionally via `.Hash()`.

Contrast this with `Backend.BlockByNumber`, which handles the exact same `AsTransaction()` call defensively:
```go
ethtx, _ := m.AsTransaction()
if ethtx == nil {
    // AsTransaction may return nil if it fails to unpack the tx data.
    continue
}
``` [2](#0-1) 

The comment is direct, first-party evidence from the codebase that `AsTransaction()` returning `nil` is a real, expected outcome (analogous to the flush request's `nil` `bio` in the kernel report), yet `filterTransactions` — a much more widely used helper — has no such guard.

`filterTransactions` is not a leaf function: it backs core public JSON-RPC handlers, including transaction/receipt/block enumeration paths in `evmrpc/tx.go` and `evmrpc/block.go`, as well as `evmrpc/simulate.go`'s block construction: [3](#0-2) 

Any externally-submitted `MsgEVMTransaction` whose `AsTransaction()` fails to unpack (returns a `nil` transaction with a non-nil error) and still lands in a finalized block will cause every RPC call that reaches `filterTransactions` for that block — `eth_getBlockByNumber`, `eth_getBlockByHash`, `eth_getTransactionByBlockNumberAndIndex`, `debug_traceBlockByNumber`, etc. — to panic on `ethtx.Hash()` with a nil-pointer dereference.

### Impact Explanation
A nil-pointer dereference in `filterTransactions` crashes the goroutine servicing the RPC call; because this is invoked from many hot public JSON-RPC endpoints (block/tx listing, tracing) that any unauthenticated RPC client can call for any historical or new block, a single malformed message that made it into a block turns basic block/tx RPC queries against a default-configuration full/RPC node into a permanent, repeatable crash trigger for that block (and any subsequent RPC request touching it), i.e., a crash of default-configuration RPC nodes.

### Likelihood Explanation
The likelihood hinges on whether a `MsgEVMTransaction` that fails `AsTransaction()` unpacking can actually be included in a finalized block. This is uncertain from the index alone: normal ante-handler processing typically requires a message to unpack successfully before proceeding, and I could not fully trace all ante-handler / message-validation code paths within the available context to confirm whether such a message can bypass that check (e.g., via a synthetic/wasm-bridge message, a future/incompatible tx-type encoding, or an associate-tx-adjacent code path) and still be committed. The presence of the explicit defensive `nil` check and its comment in `evmrpc/simulate.go` strongly suggests the authors encountered or anticipated this exact scenario in production, which is why I flag it as Medium rather than dismiss it, but full confirmation would require tracing `MsgEVMTransaction` validation in the ante handler and message-decode path end to end.

### Recommendation
Add the same `nil` check used in `evmrpc/simulate.go`'s `BlockByNumber` to `filterTransactions` in `evmrpc/utils.go`:
```go
ethtx, _ := m.AsTransaction()
if ethtx == nil {
    continue
}
hash := ethtx.Hash()
```
Audit all other call sites of `AsTransaction()` across `evmrpc/` and `x/evm/keeper/` for the same missing-guard pattern, and add a regression test that feeds `filterTransactions` an `MsgEVMTransaction` whose payload cannot be unpacked into an `ethtypes.Transaction`.

### Proof of Concept
1. Construct/observe a block containing a `MsgEVMTransaction` (not an associate tx) whose embedded transaction payload cannot be unmarshalled by `AsTransaction()` (returns `nil, err`).
2. Call any public RPC method that resolves through `filterTransactions` for that block, e.g. `eth_getBlockByNumber` with `fullTx=true`, or `debug_traceBlockByNumber`.
3. Execution reaches `evmrpc/utils.go`'s `filterTransactions`, `ethtx, _ := m.AsTransaction()` returns `nil`, and the subsequent `ethtx.Hash()` call panics with a nil-pointer dereference, crashing the RPC-serving goroutine/node for every future request touching that block. [1](#0-0)
