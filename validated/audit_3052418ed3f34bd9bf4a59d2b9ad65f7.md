### Title
Quadratic CPU exhaustion in `ThresholdKeys::read` via attacker-controlled participant count and Lagrange interpolation - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t` and `n` as untrusted `u16` fields and then calls `ThresholdKeys::new`, which computes the group key as a sum over `t` participants where each term invokes `Interpolation::interpolation_factor`. For `Interpolation::Lagrange`, `interpolation_factor` is itself `O(t)`, making group-key derivation `O(t²)` in field multiplications — roughly 4.3 billion field ops for `t = n = 65535` — triggered by ~2 MB of attacker-supplied bytes.

### Finding Description
- `ThresholdKeys::read` reads `t`, `n`, `i` from the stream, reads `n` scalars (if `Interpolation::Constant`) or nothing (if `Lagrange`), then reads `n` group elements via `C::read_G`, and finally calls `ThresholdKeys::new` [1](#0-0) .
- `ThresholdKeys::new` builds `t = (1..=params.t())` and computes `group_key` by mapping each participant to `verification_shares[i] * interpolation.interpolation_factor(*i, &t)` and summing [2](#0-1) .
- For `Interpolation::Lagrange`, `interpolation_factor` iterates over the entire `included` list (length `t`), performing two field multiplications per element, plus an inversion [3](#0-2) . Since it is called once per included participant, the total cost is `O(t²)` field multiplications plus `t` point-scalar multiplications.
- `t` and `n` are unbounded `u16`s from the input: `ThresholdParams::new` only enforces `t <= n` and `i <= n` [4](#0-3) . There is no cap on `n`, and no work bound before the quadratic interpolation runs.
- The same quadratic pattern exists in `ThresholdKeys::view`, which calls `interpolation_factor` per included participant over the full `included` list [5](#0-4)  — but `read` alone is sufficient to trigger it.

### Impact Explanation
This mirrors CVE-2026-62326's class: a small untrusted input causes disproportionate, unbounded CPU consumption with no timeout or early bound check. An attacker who can cause a node to deserialize a `ThresholdKeys` blob (e.g., via any protocol message, DB restore path, or API accepting serialized keys) supplies `n = 65535` verification shares (≈2 MB of point encodings for Ristretto/ed25519) with `t = n`. The resulting `O(t²)` interpolation — ~4·10⁹ field multiplications plus 65535 scalar-point multiplications — pins a CPU core, denying service to the calling process. Any retry/mulitplexed handling amplifies this to sustained denial of service.

### Likelihood Explanation
Reachable wherever `ThresholdKeys::read` consumes bytes influenced by an untrusted party — the audit rules explicitly designate `ThresholdKeys::read` as an untrusted-input sink. `n` is a 2-byte field the attacker fully controls; each required verification share is only ~32 bytes, so the amplification factor (compute per input byte) is enormous. No cryptographic validity is required — the points only need to deserialize, and the quadratic loop runs before any validity check could fail.

### Recommendation
- Cap `n` (and hence `t`) to a protocol-meaningful maximum (e.g., `MAX_KEY_SHARES_PER_SET`-style bound) inside `ThresholdKeys::read`/`ThresholdKeys::new` before interpolation.
- Replace the naive per-participant `O(t)` Lagrange evaluation with an `O(t)` total algorithm (prefix/suffix products of `(x_j - x_i)` denominators with a single batched inversion), eliminating the quadratic blowup for legitimate large sets.
- Apply the same bound/fix to `ThresholdKeys::view` and to `KeyMachine::calculate_share` in pedpop, which is `O(n·t)` in `share_verification_statements`/`exponential` [6](#0-5) .

fn exponential<C: Ciphersuite>(i: Participant, values: &[C::G]) -> Vec<(C::F, C::G)> {
  let i = C::F::from(u16::from(i).into());
  let mut res = Vec::with_capacity(values.len());
  (0 .. values.len()).fold(C::F::ONE, |exp, l| {
    res.push((exp, values[l]));
    exp * i
  });
  res
}
