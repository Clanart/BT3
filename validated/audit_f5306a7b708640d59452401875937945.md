### Title
`SignableTransaction::new` undercounts transaction size for the OP_RETURN data output, producing an under-funded fee and an unchecked oversize transaction - (crypto → networks/bitcoin/src/wallet/send.rs)

### Summary
The kernel fix (`accel/amdxdna: Adjust size for copy_to_user()`) is about a size-accounting mismatch: the amount of data must be bounded by the size of the buffer it is reported/copied into, rather than silently mismatching the caller's expectation. The same class exists in `SignableTransaction::new`: an OP_RETURN output carrying attacker-influenced `data` is appended to the transaction, but the weight/vbyte calculation used for the fee, the minimum-relay-fee check, and the maximum-standard-weight check is computed from `payments` only, which does not include that data output.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), the optional `data` payload is converted into an OP_RETURN output and pushed into `tx_outs` before any size accounting happens: [1](#0-0) 

The subsequent call computes the transaction weight from `tx_ins.len()` and `payments` — *not* `tx_outs` — so the OP_RETURN output is excluded: [2](#0-1) 

`calculate_weight_vbytes` only materializes outputs for `payments` and an optional `change` script, confirming the data output is never part of the measured transaction: [3](#0-2) 

Consequences propagate to three checks:
1. `needed_fee = fee_per_vbyte * vbytes` uses the smaller vbytes, so the fee committed (`sum(inputs) - sum(outputs)`, which equals `needed_fee` since the OP_RETURN carries 0 value) corresponds to a lower effective sat/vbyte rate than requested.
2. The minimum relay fee check at line 211 passes against the undercounted vbytes while the true transaction may be below `DEFAULT_MIN_RELAY_TX_FEE` for its real size, making it non-relayable.
3. The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses `weight` computed without the OP_RETURN, so a transaction that actually exceeds standard weight passes validation and gets signed. [4](#0-3) 

### Impact Explanation
The produced transaction's actual fee rate is lower than the `fee_per_vbyte` requested, and it may fall below the network minimum relay fee or exceed `MAX_STANDARD_TX_WEIGHT` once the real OP_RETURN-bearing size is measured. The multisig will still produce valid signatures for it (each input signs the real sighash via `taproot_key_spend_signature_hash` at line 386), so the protocol emits a fully-signed transaction that peers will reject. Funds are not stolen, but a spend whose data payload was supplied as part of the payment request produces a transaction that cannot be broadcast/confirmed — funds remain locked pending a new signing round, and in a deployment where signed transactions are assumed broadcastable this is an integrity failure of the "amount reported vs. amount that fits" variety. Severity: Medium.

### Likelihood Explanation
`data` is an externally influenced field (`Option<Vec<u8>>`, up to 80 bytes) attached to payment requests. Any requester who supplies an OP_RETURN payload alongside a near-boundary fee rate or a near-max-weight transaction deterministically triggers the undercount — no collusion or privileged position is needed. The miscount is unconditional whenever `data.is_some()`.

### Recommendation
Include the OP_RETURN output in the size accounting: either push the data output into the `payments`-equivalent list passed to `calculate_weight_vbytes` (with its zero value), or add the serialized `TxOut` size to `weight`/`vbytes` before computing `needed_fee` and performing the `MAX_STANDARD_TX_WEIGHT` check. Conceptually: bound the reported size by the full buffer actually written, not just the payment subset.

### Proof of Concept
Conceptual reproduction: call `SignableTransaction::new` with one input of, say, 10,000 sats, `payments = [(script, 9_000)]`, `change = None`, `data = Some(vec![0xAA; 80])`, `fee_per_vbyte = 1`. The returned `SignableTransaction` has `needed_fee` computed for vbytes that exclude the ~90-byte OP_RETURN output, while `tx.output` contains it; `tx.weight()` on `st.transaction()` exceeds the `weight` used internally, and the effective fee rate is below 1 sat/vbyte. With `payments`/`inputs` sized so that `weight + OP_RETURN > MAX_STANDARD_TX_WEIGHT` but `weight <= MAX_STANDARD_TX_WEIGHT`, the constructor returns `Ok` for a transaction Bitcoin Core will reject as non-standard — a signed transaction that cannot spend its inputs.
