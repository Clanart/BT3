### Title
`internal_withdraw` RPC Bypasses Aggregator ECDSA Authorization Check Present in `withdraw` — (File: `core/src/rpc/operator.rs`)

### Summary

The `ClementineOperator` gRPC service exposes two withdrawal endpoints: `withdraw` and `internal_withdraw`. The `withdraw` endpoint enforces an ECDSA verification-signature check (guarded by `aggregator_verification_address`) that ensures only the authorized aggregator can trigger operator payouts. The `internal_withdraw` endpoint calls the identical underlying `operator.withdraw()` logic but omits this authorization check entirely, allowing any mTLS-authenticated caller to trigger operator payout transactions without the aggregator's ECDSA approval.

---

### Finding Description

`core/src/rpc/operator.rs` implements two RPC handlers for the `ClementineOperator` service:

**`withdraw` (lines 193–257)** — the standard path called by the aggregator:

`internal_withdraw` calls the same `operator.withdraw()` core function but **never checks `aggregator_verification_address`**. The check is not delegated to `operator.withdraw()` either — it lives exclusively in the `withdraw` RPC handler. [3](#0-2) 

Both endpoints are registered as live gRPC methods on the `ClementineOperator` service (confirmed by four references in `core/src/rpc/clementine.rs` and one in `core/src/bin/cli.rs`).

---

### Impact Explanation

`aggregator_verification_address` is the operator's defense-in-depth mechanism: even if an adversary obtains mTLS credentials to reach the operator's gRPC port, they still cannot authorize a payout without the aggregator's ECDSA key. `internal_withdraw` nullifies this layer entirely.

A caller with mTLS access to the operator can:
1. Construct a valid `WithdrawParams` for any Citrea-registered withdrawal UTXO.
2. Call `internal_withdraw` directly, bypassing the aggregator ECDSA gate.
3. Cause the operator to broadcast a payout transaction and spend its own BTC liquidity without the aggregator's knowledge or approval.

The operator's BTC liquidity (used to front withdrawals) is a bridge-controlled balance. Unauthorized spending of it constitutes a material fund impact and fits the "authentication or authorization bypass in gRPC… that grants privileged bridge actions to the wrong party" criterion. [4](#0-3) 

---

### Likelihood Explanation

- The `aggregator_verification_address` config field is optional; operators who do not set it are unaffected.
- Operators who **do** set it (the security-conscious deployment) are fully exposed via `internal_withdraw`.
- The attacker surface is any party holding a valid mTLS client certificate for the operator's gRPC port — this includes the aggregator itself acting maliciously, a compromised aggregator host, or any other service sharing the same mTLS CA.
- No special on-chain state or cryptographic material beyond a valid Citrea withdrawal UTXO is required.

---

### Recommendation

Add the identical `aggregator_verification_address` ECDSA check to `internal_withdraw`, or — if `internal_withdraw` is intended only for trusted internal/CLI use — remove it from the live gRPC service definition and restrict it to a non-networked code path.

### Proof of Concept

1. Operator is configured with `aggregator_verification_address = <aggregator_ecdsa_addr>`.
2. Attacker holds a valid mTLS client certificate for the operator's gRPC port (e.g., a compromised aggregator host or a second service sharing the same CA).
3. Attacker observes a pending Citrea withdrawal UTXO (`withdrawal_id`, `input_outpoint`) and constructs a `WithdrawParams` with a valid user taproot signature over the payout output.
4. Attacker calls `ClementineOperator::internal_withdraw` with these params — **no `verification_signature` field is required**.
5. The operator's `withdraw()` core function validates the Citrea state and profitability check, then enqueues a payout transaction via TxSender, spending the operator's BTC liquidity without the aggregator's ECDSA authorization. [5](#0-4) [6](#0-5)

            parser::operator::parse_withdrawal_sig_params(withdraw_params)?;

        );

        // if verification address is set in config, check if verification signature is valid
        if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
            let verification_signature = params
                .verification_signature
                .map(|sig| {
                    PrimitiveSignature::from_str(&sig).map_err(|e| {
                        Status::invalid_argument(format!("Invalid verification signature: {e}"))
                    })
                })
                .transpose()?;
            // check if verification signature is provided by aggregator
            if let Some(verification_signature) = verification_signature {
                let address_from_sig =
                    recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>(

                        input_outpoint,
                        output_script_pubkey.clone(),
                        output_amount,
                        verification_signature,
                    )?;

                if address_from_sig != address_in_config {
                    return Err(BridgeError::InvalidECDSAVerificationSignature).map_to_status();
                }
            } else {
                // if verification signature is not provided, but verification address is set in config, return error
                return Err(BridgeError::ECDSAVerificationSignatureMissing).map_to_status();
            }
        }

            .operator
            .withdraw(
                withdrawal_id,
                input_signature,
                input_outpoint,
                output_script_pubkey,
                output_amount,
            )
            .await?;

        tracing::info!(
            "Withdraw rpc completed successfully for withdrawal id: {:?}",
            withdrawal_id
        );
