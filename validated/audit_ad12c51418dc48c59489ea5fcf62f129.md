### Title
Partial-commit line selection is applied against a re-fetched diff, letting working-tree content that changes between diff-render and commit silently determine what actually gets committed - (File: app/src/lib/git/apply.ts)

### Summary
This is a business/data-consistency analog to the Sablier bug: in Sablier, a value that is *supposed to be fixed at the time the underlying state (debt) was created* (the fee rate) is instead read and applied at the time of the later action (withdrawal), so the current value silently overrides the historical one. In GitHub Desktop, `DiffSelection` line indices are computed against the diff that was rendered to the user, but `applyPatchToIndex` re-fetches the working-directory diff at commit time and re-applies the *old* selection bitmap against that *new* diff, rather than binding the selection to the exact content the user reviewed.

### Finding Description
When a user partially stages a file, Desktop keeps a `DiffSelection` bitmap keyed by absolute line index into the diff that was rendered in the UI. When the commit is actually executed, `applyPatchToIndex` does not reuse that already-rendered diff; it calls `getWorkingDirectoryDiff` again to get a fresh diff of the file and then calls `formatPatch(file, diff)`, which walks the *new* diff and asks `file.selection.isSelected(absoluteIndex)` for each line using indices computed against the *new* hunk layout: [1](#0-0) 

`formatPatch` itself has no way to verify that the line at a given absolute index is the same line content the user actually selected - it purely trusts the index: [2](#0-1) 

The codebase is aware that the diff "might have changed dramatically since last we loaded it" and attempts to prune indices that no longer exist or turned into context lines, but explicitly only fixes up *selectable* lines - it does not re-validate that previously-selected indices still map to the same textual content: [3](#0-2) 

If the file's on-disk content shifts between the moment the diff is displayed/selected in the UI and the moment `applyPatchToIndex` re-diffs and commits (e.g. content mutated by a `clean`/`smudge` filter, a checkout-triggered hook, an external tool, or any other process touching the working tree while the Changes view is open), the hunk boundaries and line offsets can differ from what the user visually reviewed. The stale bitmap is then applied to the new hunk structure, so the line at "index N" that gets included in the generated patch may no longer be the line the user actually clicked to select.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes": the user visually reviews and selects specific lines in the diff view, but the code path that turns that selection into an actual git patch does not guarantee the same line content is committed - it only guarantees the same *index* is honored against a diff that can have changed shape. A user could unknowingly commit/push content they never selected (or omit content they did select), without any warning, because the mismatch is entirely silent - `formatPatch` throws only if the resulting patch is completely empty, not if the content mapped to the indices differs from what was originally rendered.

### Likelihood Explanation
The window is real but narrow: it requires the working-tree file to change between diff render and the (usually fast) commit action. This can happen via git clean/smudge filters (attacker-controlled `.gitattributes` in a cloned/fetched repository can register a smudge filter that rewrites file content on `git add`/checkout operations triggered by Desktop in the background), background repository refreshes, or external processes. The app-store.ts comment shows the Desktop team already identified diff staleness as a real, recurring condition worth handling, but the handling is partial (pruning selectable lines) rather than a full content-based re-validation, so the residual risk of index/content mismatch after that partial fix-up is not eliminated.

### Recommendation
Bind the selection to actual line content (e.g., hash or store the line text alongside the index) rather than pure positional indices, or force a synchronous re-diff-and-reconcile-selection step immediately before `applyPatchToIndex` generates the patch, rejecting/re-prompting the user if the diff used for patch generation differs from the diff the selection was computed against.

### Proof of Concept
Conceptual reproduction (cannot be fully executed without a live Desktop session):
1. Open a modified file with several hunks in Desktop's Changes view; select a subset of added/removed lines via `DiffSelection`.
2. Before clicking "Commit", trigger a change to the same file's on-disk content that alters hunk boundaries but keeps the file "modified" (e.g., a background process, an editor auto-format, or a `.gitattributes` clean/smudge filter from the cloned repository firing on a subsequent `git` invocation).
3. Click "Commit". `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff via `getWorkingDirectoryDiff`, then `formatPatch` (`app/src/lib/patch-formatter.ts:143-161`) applies the old selection bitmap's absolute indices against the new hunk layout.
4. Inspect the resulting commit content: it can differ from what was visually selected in step 1, without any user-facing warning.
