### Title
Stale in-memory working-directory snapshot used to gate Copilot conflict-resolution writes can let sequential writes overwrite files the user has already resolved themselves - (File: app/src/lib/stores/app-store.ts)

### Summary
The routine that applies AI-generated (Copilot) merge-conflict resolutions captures a single `repositoryStateCache` snapshot at the start of the batch operation and then loops over every conflicted file, `await`-ing a `writeFile()` per file [1](#0-0) . Before writing each file it checks whether the file is still conflicted using that *same, unchanging* snapshot rather than re-reading current on-disk/status state at the moment of the write [2](#0-1) .

### Finding Description
The guard is explicitly designed to avoid clobbering a file the user resolved manually outside Desktop while the Copilot resolution dialog was open: [3](#0-2) 
```
      // If the user resolved this file externally (e.g. in their editor) while
      // the result dialog was open, git status will report it with no remaining
      // conflict markers. Overwriting it with Copilot's stored content would
      // silently clobber their work, so skip it and let their resolution stand.
      ...
      const onDiskFile = state.changesState.workingDirectory.files.find(
        f => f.path === resolution.path
      )
      if (
        onDiskFile !== undefined &&
        isConflictedFileStatus(onDiskFile.status) &&
        !hasUnresolvedConflicts(onDiskFile.status)
      ) {
        continue
      }
```
The `state` object used in this check is fetched once, before the loop begins, at the top of the function: [4](#0-3) 
This is structurally the same inconsistency as the AMO report: a validation is performed against one data source (a cached/frozen balance/status) while the actual mutating operation depends on a different, live, and potentially more up-to-date source of truth. In the AMO case, `stakedBalance()` was checked while `withdrawAndUnwrap()` actually consulted both staked and contract-held balances. Here, `hasUnresolvedConflicts(onDiskFile.status)` is checked against a `workingDirectory.files` array captured once before the multi-file `await writeFile()` loop runs, while the actual write happens later, per-file, without re-verifying the live git status for that specific file at write time.

### Impact Explanation
If the user resolves a conflicted file manually (in an external editor) *after* the initial `state` snapshot is taken but *before* that file's turn comes up in the `for` loop (which can take time across many files, each doing an async filesystem write and, at the end, a `git add`), the stale `onDiskFile.status` will still show it as conflicted, and the loop will proceed to `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`, silently overwriting the user's own manual resolution with Copilot's suggested content [5](#0-4) . This is exactly the "silent corruption of what the user commits" impact category: the user believes their manually resolved content will be committed, but Desktop transparently replaces it, and the file is subsequently staged via `git add` [6](#0-5) .

### Likelihood Explanation
This requires an unprivileged, entirely plausible user workflow: a merge/rebase/cherry-pick produces multiple conflicted files, Copilot conflict resolution runs across all of them, and the user edits one of the later files in the list in their own editor while the batch is still processing the earlier files (a normal and expected interaction pattern for the multi-file conflict resolution feature). Because the check is per-loop-iteration but the snapshot is per-invocation, the race window scales with the number of conflicted files and the time each `writeFile`/git call takes — it is not a contrived corner case.

### Recommendation
Re-fetch the live working-directory status (or at minimum the specific file's conflict status) immediately before each `writeFile()` call rather than relying on the `state` snapshot taken once at function entry, so the "already resolved externally" guard reflects the state at the moment of the write, not the moment the function began.

### Proof of Concept
1. Trigger a merge/rebase with several conflicted files and open the Copilot conflict resolution flow.
2. Accept the resolutions; the batch loop begins iterating and calls `writeFile` for the first files.
3. While the loop is still running (before it reaches file N), manually resolve file N's conflict in an external editor and save it.
4. When the loop reaches file N, `onDiskFile.status` still reflects the stale, pre-edit conflicted state captured in the initial `state` snapshot, so the `continue` skip branch is not taken, and `writeFile` overwrites the user's manual resolution with Copilot's stored content.
