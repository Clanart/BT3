### Title
`CallDispatcher.dispatch()` has no access control — anyone can execute arbitrary calls as the shared dispatcher identity and steal any funds/allowances it holds - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
The reported `swapLiquidity` bug allowed an attacker to make a trusted contract perform an arbitrary external call to an attacker-chosen address, then sweep whatever balance that address held — draining allowances/funds that belonged to other, unrelated parties who had trusted the calling contract's identity. The core broken invariant is: *a shared trusted execution identity can be driven by an untrusted, attacker-controlled entry point*. `CallDispatcher.dispatch()` reproduces this exact primitive: it is a public, unauthenticated function that executes arbitrary `(to, value, data)` calls with the `CallDispatcher` contract itself as `msg.sender`, and it is used as a single shared singleton (`_params.dispatcher`) across every order, every user, and every app (`IntentGatewayV2`, `ExtrinsicIntents`, `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata flows) on the chain.

### Finding Description
`CallDispatcher.sol` exposes: [1](#0-0) 

There is no modifier restricting the caller to `IntentGatewayV2` or any other trusted app — `dispatch(bytes memory encoded)` is `external` with zero access control. Any address can call it directly, at any time, with any `Call[]` of its choosing, and the executed calls run with `msg.sender == CallDispatcher`.

`CallDispatcher` is a single, persistent, shared address wired into gateway configuration (`_params.dispatcher`) and reused across **all** orders from **all** users, in both predispatch and postdispatch (fill) flows: [2](#0-1) [3](#0-2) 

These flows deliberately route tokens/ETH into the dispatcher and then execute arbitrary, caller-supplied calldata (`order.predispatch.call` / `order.output.call`) through it before sweeping the *expected* input/output tokens back to the gateway. The sweep logic only recovers the specific tokens listed in `order.inputs` / `order.output.assets` — any other token balance, native dust, or ERC20 allowance the dispatcher ends up holding as a side effect of executing a swap (partial fills, unconsumed router approvals, intermediate swap-path tokens, native ETH remainders below `requiredAmount` checks, etc.) is not accounted for by the gateway's dust logic and is left sitting on the shared `CallDispatcher` contract.

Because `dispatch()` has no caller restriction, this residual value (and any standing ERC20 allowance ever granted to the `CallDispatcher` address by any user's predispatch/postdispatch calldata, e.g. `approve(dispatcher, amount)` calls staged as part of a composable swap route) is directly drainable by **anyone**, without going through `IntentGatewayV2.placeOrder`/`fillOrder` at all. An attacker simply calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: transferFrom(victim, attacker, allowance)})]))` or `Call({to: attacker, value: dispatcher.balance, data: ""})` directly.

This is structurally identical to the `swapLiquidity` bug: a contract intended to act only on behalf of a trusted caller (`LendingPool` / `IntentGatewayV2`) exposes an unauthenticated entry point (`ISwapAdapter(receiverAddress).executeOperation` / `CallDispatcher.dispatch`) that lets an attacker redirect the trusted identity's execution and balance to themselves.

### Impact Explanation
Any ERC20 dust, native ETH remainder, or standing allowance ever accumulated on the shared `CallDispatcher` — across every order placed by every user on the chain — can be stolen by an unprivileged attacker with a single direct call, bypassing the gateway's dust-accounting and `DustCollected` bookkeeping entirely. This is a direct "stealing or loss of funds" / "unauthorized transaction or execution" impact against a bridge/intents contract holding user funds in transit.

### Likelihood Explanation
No privileged role, relayer, prover, or governance actor is required — any EOA can call `CallDispatcher.dispatch` directly since it is a public external function with no modifier. The dispatcher is guaranteed to be non-empty in practice, since it is actively used to route native ETH and ERC20 balances through Uniswap swaps as part of normal predispatch/postdispatch flows (per the documented "swap-then-escrow" and "fill-then-act" patterns), and slippage/partial-fill scenarios and multi-hop swap byproducts routinely leave value or approvals on intermediate holders like this contract.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the registered gateway/app contracts (e.g., an `onlyAuthorizedCaller` modifier checked against a whitelist set by governance), or make the dispatcher single-use/ephemeral per order (e.g., deploy a fresh minimal-proxy dispatcher per order via CREATE2, as is done for other per-order isolation in this codebase) so no cross-user shared custody exists. Additionally, ensure sweep logic accounts for *all* token balances present on the dispatcher after execution, not only the tokens explicitly listed in `order.inputs`/`order.output.assets`, and revoke any approvals granted during predispatch/postdispatch execution before returning control.

### Proof of Concept
1. Observe (via events/onchain state) that `CallDispatcher` holds a non-zero ERC20 balance or has been granted an ERC20 allowance as a byproduct of a legitimate user's predispatch/postdispatch swap execution (e.g., a Uniswap multi-hop swap leaves intermediate token dust, or a user's calldata included an `approve()` to the dispatcher itself that wasn't fully consumed).
2. Attacker, with no special privileges, directly calls:
```solidity
CallDispatcher(dispatcherAddr).dispatch(
    abi.encode([
        Call({
            to: token,
            value: 0,
            data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(token).balanceOf(dispatcherAddr))
        })
    ])
);
```
3. The call succeeds because `dispatch` has no access control — `msg.sender` inside the executed call is `CallDispatcher`, and the token balance/allowance transfers to `attacker`, entirely outside of any `IntentGatewayV2` order, escrow, or dust-accounting flow. [1](#0-0)

            Call memory call = calls[i];

            }

                revert NotContract(to);
            }

            if (!success) revert CallFailed(to, result);
        }
