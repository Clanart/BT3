I found a strong analog: a hunk-counting/index-alignment mismatch between two independently-written parsers of the same attacker-influenced content, whose divergence is silently "forgotten" rather than surfaced — the exact bug class in the GMX report (a computed correction that should carry over an excess/shortfall is instead dropped, corrupting downstream state).

### Title
Diff-3/diff-3-less-strict conflict-marker miscount causes AI conflict resolution to silently splice content into the wrong location and commit corrupted code - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
`extractConflictHunks` (used to tell the model how many conflicts exist and to build the per-hunk prompt) and `reassembleResolvedFile` (used to splice the model's per-hunk resolutions back into the on-disk file) are two independently written scanners over the same raw file content. They use near-identical but not identical regexes/parsing rules for what counts as a well-formed `<<<<<<<`/`=======`/`>>>>>>>` block, and diff3 (`|||||||`) markers are handled by one but not checked at all in the other's "malformed block" detection. Neither function cross-validates that they agree on how many marker blocks exist and in which positions. `reassembleResolvedFile` matches `hunkResolutions[hunkIndex]` "by order, not by line number" [1](#0-0) , so any divergence between the two parsers' hunk counts is never detected — it just silently shifts every subsequent splice by one position, exactly like the GMX `collateralDelta = 0` case where a shortfall is silently absorbed instead of raised.

### Finding Description
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` recognizes diff3 markers via `baseMarker = /^\|{7}(?:\s|$)/` and treats a hunk with `hasBase` as valid [2](#0-1) . `reassembleResolvedFile`'s well-formedness check in `app/src/lib/copilot-conflict-resolution.ts` only checks for a `=======` separator and `>>>>>>>` closer — it has no `|||||||` awareness at all [3](#0-2) . This is not fatal by itself (the separator regex would still eventually be found), but it demonstrates the two parsers are maintained independently and can drift.

The concrete corrupting scenario: an attacker who controls content the user merges/rebases against (a git remote, a branch, or a file introduced by a malicious PR) can craft a file whose *non-conflicted* body legitimately contains lines matching `^<{7}(?:\s|$)`, `^={7}$`, or `^>{7}(?:\s|$)` (e.g. example git-conflict text in documentation, a diff/patch fixture, ASCII banners, or ‑ as literally exists in this very repository's own test fixtures such as `app/test/unit/copilot-conflict-resolution-test.ts` and `diff-parser-test.ts` content). If such a look-alike sequence appears anywhere in the file *in addition to* real conflict markers, both `extractConflictHunks` and `reassembleResolvedFile` will happily treat it as a legitimate, well-formed hunk (their look-ahead only requires the three sigils in order somewhere before EOF — it does not validate branch-name suffixes, marker balance, or that markers are not nested inside a real hunk's ours/theirs content). Because ours/theirs content is collected without checking for a nested `<<<<<<<`, a look-alike block embedded inside a real conflict's "ours" or "theirs" side will be consumed as its own hunk by `extractConflictHunks`, shifting the hunk index used to build the prompt (`### Conflict N of M` in `app/src/lib/copilot-conflict-context.ts` lines 560-590) relative to what `reassembleResolvedFile` will do when it re-scans the same raw content, since `reassembleResolvedFile` never receives the model's understanding of "N of M" — it just walks the file counting well-formed blocks in isolation and re-splices `hunkResolutions[hunkIndex]` [4](#0-3) . If a look-alike block that the extractor treats as skippable/rejected (e.g. because the extractor's inner loop for base/separator disagrees) is instead accepted by the reassembler's looser check (or vice versa), the two functions disagree on the total hunk count for the same file, and every hunk resolution after the point of disagreement is spliced into the wrong marker block. `validateResolutionPaths` only compares the model's *returned* hunk count against `expectedFiles` hunk count — both of which come from the same `extractConflictHunks` call — so this check cannot detect a divergence against `reassembleResolvedFile`'s independent count [5](#0-4) .

### Impact Explanation
When the counters diverge, `reassembleResolvedFile` silently writes the model's resolution for conflict K into the marker block at a different file position than the one the model was shown and reasoned about. Because the function returns a plain string and the caller writes it straight to disk as the "fully resolved file" with all markers presumably removed, this results in **silent corruption of what the user commits**: wrong code merged in place of the wrong hunk, or a legitimate hunk's content dropped when `hunkIndex` runs past `hunkResolutions.length` (line 585's `if (hunkIndex < hunkResolutions.length)` silently no-ops, permanently losing that block's replacement, mirroring the GMX `collateralDelta = 0` "forgotten debt" pattern) [6](#0-5) . The user sees an AI-authored merge result they're implicitly trusting; nothing in the UI or write path re-verifies that the reassembled file no longer contains conflict markers or that the splice count matched.

### Likelihood Explanation
This requires an attacker to control content that ends up in a real merge/rebase conflict the user resolves with the Copilot conflict-resolution feature, and to plant look-alike marker sequences that coincide with or are adjacent to a genuine conflict in the same file — a git remote/branch/PR content scenario within the stated valid-impact scope. It is a narrow, content-crafting-dependent condition (not trivial to hit accidentally), similar to the "very unlikely case with minimal impact" categorization the GMX team gave TRST-M-11, but here the consequence is silent commit corruption rather than a self-correcting leverage window.

### Recommendation
Make `reassembleResolvedFile` consume the exact same parser/output as `extractConflictHunks` (e.g. have `extractConflictHunks` return marker byte/line offsets and have reassembly splice by those offsets, not by an independent re-scan), and have it assert that the number of well-formed blocks it finds equals `hunkResolutions.length`, throwing `CopilotValidationError` on any mismatch instead of silently truncating or misaligning splices.

### Proof of Concept
1. Set up a repo where `file.md` contains, interleaved with a real merge conflict, a documentation/example block that itself matches the marker regexes, e.g.:
```
real code line
<<<<<<< HEAD
ours change
=======
theirs change
>>>>>>> feature
Here is an example of a conflict marker for documentation purposes:
<<<<<<< example
foo
=======
bar
>>>>>>> example
more real code
```
2. Trigger a real merge that produces exactly one genuine conflict in this file, and invoke the Copilot conflict-resolution feature.
3. `extractConflictHunks` will report **two** hunks for this file (the real one and the "example" one), so the model is prompted with `### Conflict 1 of 2` / `### Conflict 2 of 2` and returns two `hunks[]` entries.
4. `reassembleResolvedFile` independently re-scans the same content and also finds two well-formed blocks — in this simple case it "accidentally" agrees, but any variation where one of the two parsers rejects a block the other accepts (e.g. a base/diff3 marker present in one block, a marker missing whitespace after the sigils in a way one regex tolerates differently under multi-line vs. single-pass scanning, or a marker nested inside another hunk's ours/theirs content that `extractConflictHunks`'s inner collection loop does not check for) causes the two hunk counts to differ, and `resultLines` in `reassembleResolvedFile` end up splicing the wrong `resolvedContent` into the wrong block or dropping a resolution entirely once `hunkIndex >= hunkResolutions.length`.

**Uncertainty**: I was not able to execute this against the live Copilot pipeline to produce a concrete counter-example where the two regex-based scanners diverge in count (this would require enumerating edge cases like marker lines with trailing whitespace, marker lines that are prefixes of longer marker runs, e.g. 8+ `<` characters, or markers embedded in ours/theirs text) — a background engineering session with test execution would be needed to confirm a specific divergent input rather than the structural mismatch identified here from static review.

  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }

const baseMarker = /^\|{7}(?:\s|$)/
const separatorMarker = /^={7}$/
const theirsMarker = /^>{7}(?:\s|$)/

 * Absolute upper bound (in bytes) on a conflicted file we'll read into memory.
 *
 * This is a memory-safety guard only, not a resolvability heuristic — we only
 * ever send the *conflict hunks* to the model, never the whole file, so a large
 * file with a small conflict is still perfectly resolvable. Files above this
 * size are skipped before reading to avoid loading pathological blobs (e.g. a
 * multi-megabyte generated lockfile) into a string.
 */
const MAX_CONFLICT_FILE_READ_SIZE = 10_485_760 // 10MB

/**
 * Maximum length (in characters) of any single line within a conflict hunk.
 *
 * Mirrors the diff renderer's `MaxCharactersPerLine`. Conflicts containing a
 * line longer than this are almost always minified/generated content where a
 * line-oriented resolution is meaningless, so we skip them rather than sending
 * an enormous single line to the model.
 */
const MAX_CONFLICT_LINE_LENGTH = 5000

/**
 * Maximum combined size (in characters) of the actual conflict content in a
 * single file — the sum of the ours/base/theirs text across every hunk.
 *
 * Unlike a whole-file cap, this measures what we actually send to the model, so
 * it protects prompt size and output quality (truncation/malformed JSON)
 * without penalising large files whose conflicts are small.
 */
const MAX_CONFLICT_CONTENT_SIZE = 262_144 // 256KB

function isConflictMarker(line: string): boolean {
  return (
    oursMarker.test(line) ||
    baseMarker.test(line) ||
    separatorMarker.test(line) ||
    theirsMarker.test(line)
  )
}

 * Parse a file's text content and extract all conflict hunks.

 * Handles both standard two-way conflict markers (`<<<<<<<`, `=======`,

 * section for the merge base content.

 * @param contextLines - Number of surrounding unchanged lines to include

  fileContent: string,
  contextLines: number = 3

      i++
      continue
