### Title
Tokenfactory `DenomAllowList` restriction can be bypassed by routing sends through a CosmWasm contract's `BankMsg::Send` - (File: `sei-wasmd/x/wasm/keeper/keeper.go`)

### Summary
The bank module's native `MsgSend`/`MsgMultiSend` handlers enforce a tokenfactory `DenomAllowList` restriction, but the CosmWasm bank-message dispatch path (`BankCoinTransferrer.TransferCoins`), which is used whenever a contract's execution result contains a `BankMsg::Send`, omits this check. An unprivileged wasm user can therefore move an allow-listed tokenfactory denom to/from addresses that are not on the denom's allow list simply by routing the transfer through any CosmWasm contract, exactly analogous to the reported issue where a restriction enforced only at the "front door" (the Router/MsgServer) can be bypassed by reaching the underlying primitive (ArrakisV2/`SendCoins`) through another path.

### Finding Description
`x/bank`'s `msgServer.Send` and `msgServer.MultiSend` explicitly call `IsInDenomAllowList` for both the sender and the receiver before calling the low-level `SendCoins`/`InputOutputCoins` keeper functions: [1](#0-0) 

`IsInDenomAllowList` is the gate that restricts transfers of tokenfactory denoms (`factory/<creator>/<subdenom>`) with a configured allow list to only the addresses in that list: [2](#0-1) 

However, the `x/wasm` module dispatches `BankMsg::Send` messages returned by CosmWasm contracts through a separate `BankCoinTransferrer.TransferCoins` path, which replicates only the `IsSendEnabledCoins` and `BlockedAddr` checks from the SDK's message server — it never calls `IsInDenomAllowList`: [3](#0-2) 

This is the same class of bug as the report: the protective check (`whenNotPaused` in the report, `IsInDenomAllowList` here) is implemented only in one caller (`ArrakisV2Router` / `bank.msgServer.Send`) and not in the shared underlying primitive (`ArrakisV2.mint/burn` / `bank.keeper.SendCoins`). Any other caller that reaches the primitive directly — here, the wasm module's bank-message dispatcher — bypasses the restriction entirely.

### Impact Explanation
Tokenfactory denom creators use `DenomAllowList` to restrict which accounts may hold/transfer a given denom (e.g. compliance/KYC-gated tokens, permissioned assets). Bypassing this via a CosmWasm contract allows unauthorized transfer of a restricted token to or from disallowed addresses, defeating the issuer's access-control guarantee and enabling movement of funds that were intended to be frozen/restricted to specific parties. This is a concrete authorization bypass leading to unauthorized transfer of tokenfactory-governed assets.

### Likelihood Explanation
Any unprivileged user can instantiate or call an existing CosmWasm contract and have it emit a `BankMsg::Send` carrying the restricted denom; no special privileges, validator cooperation, or race condition are required — the wasm dispatcher unconditionally uses `BankCoinTransferrer.TransferCoins` for all `BankMsg::Send` submessages. This makes the bypass trivially and repeatably reachable from ordinary CosmWasm execute transactions.

### Recommendation
Add the same `IsInDenomAllowList` check (for both the sender and receiver, matching `msgServer.Send`/`MultiSend`) into `BankCoinTransferrer.TransferCoins` in `sei-wasmd/x/wasm/keeper/keeper.go`, or move the allow-list enforcement into `BaseSendKeeper.SendCoins`/`InputOutputCoins` itself so every caller (native bank messages, CosmWasm bank dispatch, precompiles, IBC, etc.) is consistently gated regardless of entry point.

### Proof of Concept
1. A tokenfactory denom creator calls `SetDenomAllowList` (via governance/authority flow) to restrict `factory/<creator>/<subdenom>` transfers to a specific set of addresses.
2. An attacker who is not on the allow list deploys or calls an arbitrary CosmWasm contract (e.g. a simple "forwarder" contract) whose `execute` entry point returns `Response::new().add_message(BankMsg::Send { to_address: attacker, amount: [restricted_denom] })`, using funds sent to the contract as part of the `Execute` message (or funds already held by the contract).
3. `x/wasm` dispatches this returned `BankMsg::Send` through `BankCoinTransferrer.TransferCoins`, which only checks `IsSendEnabledCoins`/`BlockedAddr` and calls `SendCoins` directly — never checking `IsInDenomAllowList`.
4. The transfer succeeds even though the attacker's address is not on `factory/<creator>/<subdenom>`'s allow list, whereas the same transfer attempted via a native `MsgSend` transaction would be rejected with `"is not allowed to send/receive funds"`.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

	err = k.SendCoins(ctx, from, to, msg.Amount)

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

// BankCoinTransferrer replicates the cosmos-sdk behaviour as in
// https://github.com/cosmos/cosmos-sdk/blob/v0.41.4/x/bank/keeper/msg_server.go#L26
type BankCoinTransferrer struct {
	keeper types.BankKeeper
}

func NewBankCoinTransferrer(keeper types.BankKeeper) BankCoinTransferrer {
	return BankCoinTransferrer{
		keeper: keeper,
	}
}

// TransferCoins transfers coins from source to destination account when coin send was enabled for them and the recipient
// is not in the blocked address list.
func (c BankCoinTransferrer) TransferCoins(parentCtx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amount sdk.Coins) error {
	em := sdk.NewEventManager()
	ctx := parentCtx.WithEventManager(em)
	if err := c.keeper.IsSendEnabledCoins(ctx, amount...); err != nil {
		return err
	}
	if c.keeper.BlockedAddr(toAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", toAddr.String())
	}

	sdkerr := c.keeper.SendCoins(ctx, fromAddr, toAddr, amount)
	if sdkerr != nil {
		return sdkerr
	}
	for _, e := range em.Events() {
		if e.Type == sdk.EventTypeMessage { // skip messages as we talk to the keeper directly
			continue
		}
		parentCtx.EventManager().EmitEvent(e)
	}
	return nil
}
