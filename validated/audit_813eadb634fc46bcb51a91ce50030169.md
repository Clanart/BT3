## Title
Missing `<`/`>` (and related XSS-mitigation) escaping in upb JSON encoder used by Python/Ruby/PHP `MessageToJson` — (`upb/json/encode.c`)

## Summary
The upstream external report (CVE-2020-36827) describes XAO::Web mishandling `<`/`>` characters when producing JSON that is later embedded (`json-embed`) into an HTML/JS context, allowing script injection. Protobuf itself defines a public JSON-serialization API (`MessageToJson` / `encode_json` / `JsonFormat.print`) whose documented purpose includes safe embedding of proto-derived data into web responses. The C++, Java, and C# implementations of this API deliberately escape `<`, `>` (plus a handful of other characters) specifically to avoid this exact class of bug when the resulting JSON is placed into `<script>` blocks. The shared `upb` C JSON encoder — which backs the default Python binding, and the native Ruby and PHP extensions — omits this defense-in-depth escaping, reproducing the same failed invariant as CVE-2020-36827 for those language bindings.

## Finding Description
Protobuf's JSON writer invariant, as implemented in the canonical C++ backend, is: "characters that are syntactically legal in JSON but dangerous if the JSON is later parsed/embedded as JavaScript/HTML (`<`, `>`, plus zero-width/bidi control characters) must be `\u`-escaped." This is explicit in:

- C++: `MustEscape()` explicitly escapes `<` and `>` "to prevent security bugs in JavaScript" [1](#0-0) , and `WriteEscapedUtf8` treats `<`/`>` as unsafe characters requiring the slow escaping path [2](#0-1) .
- Java: `JsonFormat` explicitly adds `<>&='` to the replacement table "to prevent XSS risks" [3](#0-2) , with an explicit regression test tied to bug b/73832901 confirming `</script>` is escaped to `\u003c/script\u003e` [4](#0-3) .
- C#: `JsonFormatter.WriteString` likewise HTML/JS-escapes special characters via the `CommonRepresentations` table, explicitly modeled on `json_escaping.cc`'s behavior [5](#0-4) .

In contrast, the shared `upb` C JSON encoder's per-byte escaper only handles the characters required by strict JSON syntax (`\n \r \t \" \f \b \\` and ASCII control bytes `<0x20`) and otherwise copies raw bytes through unescaped, with no handling of `<`/`>`/zero-width/bidi characters at all: [6](#0-5) 

This `jsonenc_stringbody`/`jsonenc_string` path is invoked for every string-typed field value via `jsonenc_scalar` [7](#0-6) , and it is the exact code that is directly wired to the public per-language JSON APIs:

- Ruby's `Message.encode_json` calls `upb_JsonEncode` directly on the message and returns the raw string [8](#0-7) .
- The identical unescaped-`<`/`>` encoder is duplicated verbatim into PHP's `php-upb.c` [9](#0-8)  and Ruby's bundled `ruby-upb.c` [10](#0-9) .
- Python's default backend (since protobuf 4.21, and now the priority-ordered default) is the `upb`-based extension [11](#0-10) , which uses the same `upb_JsonEncode` machinery.

## Impact Explanation
An ordinary client can set an arbitrary string field (e.g., via a bounded, valid binary Protobuf parse of a trusted schema) to a payload containing `</script><script>...</script>` or similar. If the consuming application (as in the original CVE's `json-embed` scenario) serializes that message with `MessageToJson`/`encode_json` in Python (upb backend), Ruby, or PHP and embeds the resulting JSON text directly into an HTML page (a common "hydrate a JS object from server-rendered JSON" pattern), the `<`/`>` sequence passes through unescaped and can break out of a `<script>` context, causing reflected XSS in the consuming web application. This is a content-integrity/output-encoding failure in a public, documented serialization API, not a memory-safety bug — consistent with a Medium severity classification, matching the CVE-2020-36827 analog.

## Likelihood Explanation
High likelihood of reachability: any attacker-controlled string field reaching `MessageToJson` (Python upb backend, which is default) or `Message#to_json`/`encode_json` (Ruby) or `PHP`'s serializer produces this unescaped output with no configuration needed. The bug requires no malformed input, no privileged access, and no unusual API usage — just a string field value containing `<`/`>`, which is entirely valid UTF-8/JSON content.

## Recommendation
Update `jsonenc_put_escaped_char`/`jsonenc_stringbody` in `upb/json/encode.c` (and its copies embedded in `php-upb.c` and `ruby-upb.c`, which are presumably regenerated from the same source) to escape `<`, `>`, and ideally the same additional characters (`&`, `=`, `'`, zero-width/bidi control code points) that the C++, Java, and C# JSON writers already escape, so that all supported language bindings share the same XSS-hardening invariant for JSON output.

## Proof of Concept
Given a trusted `.proto` schema with a `string` field `s`, and a Ruby/PHP/Python(upb) message set to:
```
s = "</script><script>alert(1)</script>"
```
Calling `Message.encode_json(msg)` (Ruby) — which forwards directly into `upb_JsonEncode` → `jsonenc_string` → `jsonenc_stringbody` [12](#0-11) [13](#0-12)  — yields:
```json
{"s":"</script><script>alert(1)</script>"}
```
with `<`/`>` left completely unescaped, in contrast to the equivalent Java call on the same field value, which is verified by existing test code to produce `\u003c`/`\u003e` escapes instead: [14](#0-13)

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}

    ret = rb_str_new(buf2, size);

# Implementation backends

There are three separate implementations of Python Protobuf. All of them offer
the same API and are thus functionally the same, though they have very different
performance characteristics.

The runtime library contains a switching layer that can choose between these
backends at runtime. Normally it will choose between them automatically, using
priority-ordered list, and skipping any backends that are not available. However
you can request a specific backend by setting the
`PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION` environment variable to one of the
following values:

1.  **upb**: Built on the
    [upb C library](https://github.com/protocolbuffers/protobuf/tree/main/upb),
    this is a new extension module
    [released in 4.21.0](https://protobuf.dev/news/2022-05-06/). It offers
    better performance than any of the previous backends, and it is now the
    default. It is distributed in our PyPI packages, and requires no special
    installation. The code for this module lives in this directory.
1.  **cpp**: This extension module wraps the C++ protobuf library. It is
    deprecated and is no longer released in our PyPI packages, however it is
    still used in some legacy cases where apps want to perform zero-copy message
    sharing between Python and C++. It must be installed separately before it
    can be used. The code for this module lives in
    [google/protobuf/pyext](https://github.com/protocolbuffers/protobuf/tree/main/python/google/protobuf/pyext).
1.  **python**: The pure-Python backend, this does not require any extension
    module to be present on the system. The code for the pure-Python backend
    lives in [google/protobuf/internal](google/protobuf/internal)

The order given above is the general priority order, with `upb` being preferred
the most and the `python` backend preferred the least. However this ordering can
be overridden by the presence of a
`google.protobuf.internal._api_implementation` module. See the logic in
[api_implementation.py](https://github.com/protocolbuffers/protobuf/blob/main/python/google/protobuf/internal/api_implementation.py)
for details.

You can check which backend you are using with the following snippet:
