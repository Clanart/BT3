## Bandwidth subscription queue can be griefed to evict a victim's unused, prepaid allowance

### Title
Unbounded FIFO eviction in pallet-bandwidth lets any buyer permanently destroy another app's prepaid bandwidth - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` stores prepaid bandwidth as a FIFO list of `Subscription` entries per `(app_chain, app)`, capped at 1024 slots [1](#0-0) . Every successful purchase message unconditionally appends a new subscription and, once the list is at capacity, silently deletes ("evicts") the single oldest entry regardless of how many bytes remain on it [2](#0-1) . Because the credited `(app_chain, app)` key is taken from the purchase message body itself — not from the caller's identity — and any address on any registered source chain can call `BandwidthManager.purchase()` to target an arbitrary app's bucket for sponsorship purposes [3](#0-2) , an attacker can flood a victim app's queue with minimum-tier purchases until the victim's still-unused, high-value subscription is pushed out and permanently lost, exactly mirroring the reported bug class: prepaid value becomes unclaimable with no recovery path.

### Finding Description
`on_accept` decodes any inbound purchase message and calls `push_subscription` keyed by `msg.chain` and the app name in the message body — fields fully controlled by whoever calls `purchase()` on the registered `BandwidthManager` for that source chain [4](#0-3) . The only check performed is that `request.from` matches the registered manager address for `request.source`; there is no check that the caller has any relationship to the app being credited [5](#0-4) .

`push_subscription` then does:
```
let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
    let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
        Some(list.remove(0))
    } else { None };
    let _ = list.try_push(new_sub);
    evicted
});
``` [6](#0-5) 

Eviction is purely FIFO-by-age, independent of `remaining_bytes` — a fresh 1-byte purchase can evict a nearly-untouched multi-month, high-tier subscription simply by being pushed after it once the list is saturated. The design documentation confirms this is deliberate but treats it as a benign edge case ("in practice this only happens under pathological repeat-buy behavior") [7](#0-6) , without accounting for an adversarial third-party buyer deliberately targeting someone else's bucket.

This is the direct analog of the `clearExtraRewards` bug: a data structure holding value owed to a specific beneficiary gets wiped by an action that (a) requires no permission from that beneficiary and (b) has no accompanying settlement/refund step. The only difference is that here the "clearer" is not a privileged `rewardManager` but any unprivileged purchaser, since the pallet exposes no restriction on who may credit — or, by extension via the FIFO cap, evict — an app's bucket.

### Impact Explanation
A victim app that has legitimately prepaid for a large/long bandwidth tier can have that unused allowance permanently destroyed by a third party spamming minimum-cost purchases against the same `(app_chain, app)` key. There is no sweep, refund, or reversal mechanism — the pallet only emits `SubscriptionEvicted { lost_bytes }` for audit purposes, matching the judge's observation in the referenced report that "there doesn't seem to be any sweep function… the admin [here: no one] to take the reward tokens" — the paid-for allowance is gone forever, and the app that paid for it can no longer dispatch messages through the gate up to that amount, which is a direct loss of prepaid funds/value with no way for anyone to reclaim it.

### Likelihood Explanation
Reaching the vulnerable path requires no privileged role, no malicious relayer, and no compromised prover — it only requires calling the public `purchase()` entrypoint on any registered `BandwidthManager` contract with the target's `(app_chain, app)` encoded in the purchase body, which is explicitly supported by the sponsorship feature [3](#0-2) . The attacker's cost scales with the cheapest configured tier price times however many pushes are needed to walk the FIFO cap past the victim's entry, which is bounded by 1024 total slots per bucket — an economically meaningful but not infeasible cost for griefing a specific high-value target, and the attack requires zero cooperation from any other party.

### Recommendation
Do not evict purely by age. Options: (1) reject new purchases (or refund/redirect them) once a bucket is at capacity instead of silently evicting the oldest entry, (2) evict only expired or fully-drained entries and hard-fail (or force the purchaser to pick a different tier/app) if no evictable entry exists, or (3) restrict who may credit a given `(app_chain, app)` bucket (e.g., an allowlist of authorized sponsors per app) so an unrelated third party cannot unilaterally grow another app's queue. At minimum, the eviction choice should account for `remaining_bytes`/value, not just insertion order, so a large unused subscription can never be destroyed by a stream of dust purchases.

### Proof of Concept
1. Victim app `A` on `app_chain = X` purchases `TierFour` for many months, crediting a subscription with a very large `remaining_bytes` and long `expires_at`, appended to `Allowance::<T>::get(X, A)`.
2. Attacker, using any `BandwidthManager` registered for some source chain (does not need to be `X`, since `msg.chain` is independent of `request.source`), repeatedly calls `purchase()` with `chain = X`, `app = A`, `tier = TierOne`, `months = 1` — the cheapest possible SKU.
3. Each purchase message reaches `on_accept` and calls `push_subscription(&X, &A, TierOne, ...)` [8](#0-7) , appending to the same FIFO list as the victim's subscription.
4. Once the list for `(X, A)` reaches 1024 entries, every further attacker purchase evicts the oldest entry via `list.remove(0)` [6](#0-5) . The attacker continues purchasing until the victim's still-mostly-unused `TierFour` subscription reaches the front of the queue and gets evicted, emitting `SubscriptionEvicted { lost_bytes: <victim's remaining balance> }`.
5. Victim `A` has now lost the bytes it paid for with no way to reclaim them — `Pallet::remaining(X, A)` no longer reflects the evicted subscription, and no refund or recovery call exists anywhere in the pallet.

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",

			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}

### Eviction

Pushing onto a full list (1024 entries) evicts the **oldest** entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain. In practice this only happens under pathological repeat-buy behavior — at the default of one purchase per cycle, 1024 buys is years of headroom.

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
