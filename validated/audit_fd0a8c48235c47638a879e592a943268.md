### Title
PedPoP encryption key registration accepts the identity point, making encrypted secret shares publicly decryptable - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary

Analogous to CVE-2023-52874 — where a register that was supposed to be cleared was left carrying an attacker-influenced value — `Decryption::register` accepts a participant-supplied `enc_key` with no identity check, so the ECDH "shared secret" collapses to a fixed public value (the identity point) instead of a secret. The stream cipher keyed off that value can then be derived by any observer, leaking every secret share encrypted to that participant.

### Finding Description

`EncryptionKeyMessage::read` parses `enc_key` with `C::read_G`, which is `<C as Ciphersuite>::read_G` — the base trait method. The FROST crate explicitly layers an identity rejection on top of this method in `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`), which demonstrates that `Ciphersuite::read_G` itself does **not** reject the identity point. PedPoP never adds that check:

- `EncryptionKeyMessage::read` reads `enc_key` via `C::read_G` with no identity/validity check (`crypto/dkg/pedpop/src/encryption.rs:57-59`).
- `Decryption::register` stores it unconditionally (`crypto/dkg/pedpop/src/encryption.rs:351-362`); there is no proof-of-possession on the *registered* key (the Schnorr PoP only covers the per-message ephemeral `msg.key` in `EncryptedMessage`).
- During `generate_secret_shares`, each participant calls `encrypt(..., self.decryption.enc_keys[&participant], share_bytes)` (`crypto/dkg/pedpop/src/encryption.rs:466`, `crypto/dkg/pedpop/src/lib.rs:369`).
- `encrypt` computes `ecdh::<C>(&key, to)` = `to * key` (`crypto/dkg/pedpop/src/encryption.rs:95-97,153-154`). If `to` is the identity, the ECDH result is the identity point regardless of the fresh random `key`.
- `cipher::<C>(context, &ecdh)` transcripts `identity.to_bytes()` as the `shared_key` and derives the ChaCha20 key from it with a static IV (`crypto/dkg/pedpop/src/encryption.rs:101-133`). Since the identity encoding, context, and IV are all public constants/inputs, the keystream is computable by anyone.

The same gap exists for `EncryptedMessage::read`'s `key` field (`encryption.rs:171-177`), but `decrypt` computes `ecdh = msg.key * self.enc_key` where `self.enc_key` is an honest nonzero scalar — a malicious sender choosing `key = identity` only produces a public keystream for their *own* message. The reachable and harmful direction is the registered `enc_key`, which controls decryption of messages *others* send to the malicious participant.

### Impact Explanation

Encrypted secret shares are distributed through the coordinator/tributary data path (`processor/src/key_gen.rs:403-413` reads `EncryptedMessage`s per participant; `coordinator/src/tributary/handle.rs:347-363` stores `DkgShare` data per sender/recipient), i.e., over an authenticated channel that is not confidential — messages are observable by third parties. A participant who registers `enc_key = identity` causes every honest participant's `SecretShare` encrypted to them to be XORed with a publicly derivable ChaCha20 keystream. Any observer — not just the malicious participant — recovers the plaintext shares, and the sum of those shares is that participant's final PedPoP secret share (`*self.secret += share` in `calculate_share`, `crypto/dkg/pedpop/src/lib.rs:484`).

The result is recovery of a threshold key share by an unprivileged observer, degrading the effective security of the resulting `ThresholdKeys` by one share; combined with compromise of `t-1` other shares the group key is fully recoverable. This is not detectable: the identity key produces well-formed ciphertext and passes all PoP/share-verification checks, so no blame is attributable.

### Likelihood Explanation

Any DKG participant can include `enc_key = identity` (canonical zero encoding for Ristretto/ed25519) in their round-1 `EncryptionKeyMessage`. This requires only sending crafted public bytes — no collusion and no protocol violation that the code detects. The residual uncertainty is whether the share-distribution channel is truly readable by unprivileged third parties; the design doc explicitly assumes only an *authenticated* channel (`spec/cryptography/Distributed Key Generation.md:30-35`), and tributary data is published on-chain, so this assumption holds in the deployed configuration. Given per-participant (not group-key) share exposure, severity is Medium–High.

### Recommendation

Reject the identity point when registering encryption keys, e.g., apply the same check `Curve::read_G` performs: in `EncryptionKeyMessage::read` and/or `Decryption::register` (`crypto/dkg/pedpop/src/encryption.rs:58` and `351-362`), error if `enc_key.is_identity()`. Defense in depth: also reject identity `msg.key` in `EncryptedMessage::read`/`decrypt`, and consider requiring a PoP on the registered `enc_key` so a participant cannot register keys whose discrete log they don't know.

### Proof of Concept

```rust
// Attacker is DKG participant j. In round 1 they publish:
let mut msg_bytes = commitments.serialize(); // their Commitments<C>
msg_bytes.extend(<C::G as GroupEncoding>::Repr::default().as_ref()); // enc_key = identity
let key_msg = EncryptionKeyMessage::<C, Commitments<C>>::read(
    &mut msg_bytes.as_slice(), params
).unwrap(); // accepted — no identity check

// Every honest participant i then computes, in generate_secret_shares ->
// Encryption::encrypt -> encrypt():
//   ecdh = enc_keys[j] * random_key = identity * k = identity
//   cipher = ChaCha20::new(H(transcript(context, identity.to_bytes())), b"DKG IV v0.2\0")
// and broadcasts  ciphertext_i = share_i->j XOR keystream

// Observer O recomputes the identical keystream from public constants:
let ecdh_point = C::G::identity();
let mut pub_transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
pub_transcript.append_message(b"context", context);
pub_transcript.domain_separate(b"encryption_key");
pub_transcript.append_message(b"shared_key", ecdh_point.to_bytes().as_ref());
// -> ChaCha20 key = challenge(b"key")[..32], IV = b"DKG IV v0.2\0"
// O XORs each observed ciphertext to recover share_i->j for all i,
// then sums them to obtain participant j's full PedPoP secret share.
```

Note: I did not fully verify whether `Ciphersuite::read_G` for `dalek-ff-group`/`kp256` rejects identity encodings internally; the explicit identity check added in `Curve::read_G` strongly suggests it does not, but confirming that implementation would remove the residual uncertainty.
