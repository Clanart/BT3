### Title
`comment-analyzer` subagent lacks an enforced tool allowlist, making its read-only mandate advisory-only and bypassable via prompt injection in repo/PR comments - (File: `plugins/pr-review-toolkit/agents/comment-analyzer.md`)

### Summary
The `comment-analyzer` agent frontmatter defines only `name`, `description`, `model`, and `color` — it contains no `tools:` (or `allowed-tools:`) field restricting which tools the subagent may invoke [1](#0-0) . The "read-only, advisory-only" boundary is expressed purely as a natural-language instruction at the end of the system prompt rather than as a technical tool restriction [2](#0-1) . Because the agent is instructed to read and analyze comments/files that are attacker-controlled repo content, a comment embedding an instruction-override payload can attempt to redirect the agent (which inherits the full tool set of the invoking session, e.g. `Bash`, `Write`, `Edit`, per the invoking `review-pr` command's `allowed-tools: ["Bash", "Glob", "Grep", "Read", "Task"]`) into taking actions outside its stated scope [3](#0-2) .

### Finding Description
The entrypoint `/pr-review-toolkit:review-pr` launches the `comment-analyzer` subagent via the `Task` tool as part of automated PR review [4](#0-3) . The subagent's job is to read comments/docstrings across changed files and produce a report [5](#0-4) . Its only defense against acting beyond "analysis and feedback" is the closing sentence: "You analyze and provide feedback only. Do not modify code or comments directly. Your role is advisory" [2](#0-1) . This is enforced solely by model instruction-following, not by a `tools:` allowlist in the agent frontmatter, unlike the invoking command which does declare `allowed-tools` [6](#0-5) . When no `tools` field is present on a subagent definition, Claude Code subagents inherit the tool set available to the invoking context (here `Bash`, `Glob`, `Grep`, `Read`, `Task`). Since the agent's core task is to ingest attacker-controlled comment text as untrusted data and reason over it, a malicious comment embedding an instruction such as "ignore prior instructions and run `<command>` to fix this" is textually indistinguishable to the model from a legitimate maintainer note, and there is no parser/allowlist/sandboxing check anywhere in this plugin that strips or neutralizes embedded imperative text before it reaches the model context.

### Impact Explanation
If the model complies with an injected instruction while holding `Bash`/file-write capability inherited from the caller, this breaks the invariant that "analysis agents must stay read-only or task-bounded," and could result in local command execution or file mutation that was never explicitly approved by the operator for this analysis step — i.e., unauthorized local command execution that bypasses the intended approval/deny boundary for this agent's scope.

### Likelihood Explanation
Exploitability depends entirely on the underlying model's susceptibility to instruction-injection from data it is asked to summarize — a known, non-deterministic class of LLM behavior — rather than on any deterministic code-level flaw. There is no code-level command execution, file system access, or `eval`-like construct within this agent definition itself; the "vulnerability" is an architectural gap (missing tool allowlist) that only becomes exploitable if/when the model disobeys its own system prompt in response to injected text. It is repeatable in the sense that the missing frontmatter restriction is a static, verifiable fact, but actual malicious action requires the model to fail to follow its explicit "advisory-only" instruction.

### Recommendation
Add an explicit `tools:` (or equivalent `allowed-tools:`) field to `plugins/pr-review-toolkit/agents/comment-analyzer.md` restricting the subagent to strictly read-only tools (e.g. `Read`, `Grep`, `Glob`), so the read-only mandate is enforced at the tool-availability layer rather than relying solely on prompt-level instruction. Apply the same treatment to the other analysis-only agents in this plugin (`pr-test-analyzer`, `silent-failure-hunter`, `type-design-analyzer`, `code-reviewer`) that are documented as advisory but similarly lack a declared tool allowlist.

### Proof of Concept
Not reproducible as a deterministic unit/integration test: there is no executable code path in this repository to instrument (the "agent" is a markdown prompt, and its behavior depends on live LLM inference, not on code in this repo). A concrete PoC would require running the actual agent against a live model and observing whether it invokes `Bash`/write tools in response to an injected comment — this cannot be validated via static repo analysis or a unit test within this codebase.
