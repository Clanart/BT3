### Title
Cross-transaction contamination of output metadata in `Bitcoin::get_outputs` causes deposits to be reported with attacker-controlled data and origin - (File: processor/src/networks/bitcoin.rs)

### Summary
Analogous to the Tokensoft report (an unrestricted function lets an outsider overwrite/amplify state that should have been bound to a single initialization), `get_outputs` accumulates `outputs` across all transactions in a block but then overwrites **every** previously collected output's `presumed_origin` and `data` with the *current* transaction's values. Any unprivileged Bitcoin user can include a transaction later in the same block to corrupt the metadata of an earlier, unrelated deposit.

### Finding Description
In `Bitcoin::get_outputs`, `outputs` is declared once outside the per-transaction loop:

```rust
let mut outputs = vec![];
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) { ... outputs.push(output); }
  if outputs.is_empty() { continue; }
  // populate the outputs with the origin and data
  let presumed_origin = ... tx.input[0] ...;
  let data = Self::extract_serai_data(tx);
  for output in &mut outputs { ... }   // mutates outputs from ALL prior txs
}
```

The `outputs.is_empty()` guard only skips the *first* empty stretch. Once any transaction produces a Serai output, every subsequent transaction in the block that also produces an output re-populates **all** accumulated outputs with its own `presumed_origin` and its own extracted `data` (`extract_serai_data` reads the OP_RETURN push or the witness-embedded `SHA256 PUSH MSG_HASH OP_EQUALVERIFY` pattern — both fully attacker-controlled).

Concretely, for `OutputType::External` outputs, `output.data` is set from the *last* output-producing transaction in the block, not the transaction that actually created the deposit. `presumed_origin` is similarly overwritten for all outputs (external, branch, change, forwarded).

### Impact Explanation
The `data` field of a `ReceivedOutput`/`Output` carries the Serai instruction/memo bound to a deposit (who it is credited to / what it does). An attacker who observes a victim deposit to a Serai external address in the mempool can craft their own transaction paying any dust-to-anything with a malicious OP_RETURN/witness payload, get it mined in the same block after the victim's tx, and cause the victim's deposit to be reported with the attacker's `data` and `presumed_origin`. Depending on how the processor consumes `data`, this can redirect credit, attach a forged instruction to someone else's funds, or misattribute the origin address — a deposit-relevant manipulation reachable entirely with public, unprivileged transactions. This mirrors the report's class: state belonging to one record is mutated by an unrelated party's call, with no check binding the mutation to the record that produced it.

### Likelihood Explanation
High reachability: requires only that the attacker's transaction lands in the same block as a Serai-bound transaction and itself produces a scanned output (or, for the origin/data write to fire, `outputs` is non-empty — which the victim's deposit already satisfies; note the attacker doesn't even need their own output, since the write triggers whenever any output exists and this tx produced ≥0... the write only runs if the current tx produced an output, so the attacker does need one scanned output, e.g. paying dust to a Serai address or even an unrelated matching script is not needed — they need `scan_transaction(tx)` to return ≥1 output, i.e. they must pay a Serai address, which is public knowledge). Cost is one transaction fee. Ordering within a block is achievable via fees/mining.

### Recommendation
Scope `outputs` (and the origin/data population) per transaction: declare the per-tx vector inside the loop, or index the population loop to only the outputs produced by `tx`. Alternatively, return `(tx, output)` pairs from scanning and populate each output's metadata from the transaction that created it. Also consider binding `data` only to outputs actually created by the tx carrying it.

### Proof of Concept

// Block with two txs paying the multisig's external address:
//   txA: victim deposit, output[0] -> external_addr, OP_RETURN = b"victim-memo"
//   txB: attacker tx,     output[0] -> external_addr, OP_RETURN = b"attacker-memo"

let outputs = bitcoin.get_outputs(&block, key).await;

// outputs[0] is the victim's outpoint (txA:0) — correct id/amount —
// but outputs[0].data == b"attacker-memo" and
// outputs[0].presumed_origin == attacker address,
