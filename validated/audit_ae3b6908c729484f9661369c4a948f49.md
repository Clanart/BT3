### Title
Symlinked tracked directory in a malicious repository allows Discard Changes to delete/overwrite files outside the repository - ([File: app/src/lib/stores/git-store.ts])

### Summary
This is the same bug class as the Remora report: a value is computed once from an initial state and then used later without being re-validated after conditions that should invalidate it. In `TokenBank::buy`, `feeValue` is computed from `stablecoinValue` before the discount mutates `stablecoinValue`, so the stale value is used. In GitHub Desktop's `GitStore.discardChanges`, the on-disk path to operate on is computed with a plain, non-symlink-aware join (`Path.resolve`/`Path.join`) even though the codebase has an explicit, dedicated primitive — `resolveWithin` in `app/src/lib/path.ts` — created specifically to "guard against path traversal and symlink escapes." `discardChanges` never uses it, so a `file.path` that traverses through a tracked symlink is resolved to a filesystem location outside the repository and then deleted/overwritten.

### Finding Description
`GitStore.discardChanges` builds destination paths directly from repository-relative `file.path` values returned by `git status`: [1](#0-0) 

Two branches are affected:
- `this.shell.moveItemToTrash(Path.resolve(this.repository.path, file.path))` at [2](#0-1) 
- `rm(Path.join(this.repository.path, file.path))` fallback paths at [3](#0-2) 

`Path.resolve`/`Path.join` only perform lexical joining; they never inspect the real filesystem, so if any path component is a symlink, the resulting path string is textually inside the repo but the OS will dereference the symlink at access time and operate on whatever it points to.

The codebase already has a fix for exactly this class of bug — `resolveWithin` — which resolves the path and then calls `realpath` on both root and target to verify the *real* location is still inside the root, explicitly to defend against symlink escapes: [4](#0-3) 

This primitive is already used to hedge the same risk in a newer feature, Copilot conflict resolution, which explicitly comments that it's "Guard[ing] against path traversal and symlink escapes (cross-platform)": [5](#0-4) 
and again when writing resolved content back to disk: [6](#0-5) 

`discardChanges`, however, predates this fix and was never migrated to it (confirmed by the doc describing the flow, which never mentions symlink/path validation): [7](#0-6) 

`file.path` values come straight from parsing `git status --porcelain=2 -z` output, including for untracked entries, with no filtering for paths that traverse through symlinked directories: [8](#0-7) [9](#0-8) 

**Attacker primitive / broken invariant:** A cloned/fetched repository can commit a tracked symlinked directory (e.g. `link -> /`, or `link -> ~/Library/Application Support`, or `link -> ~/.ssh`) plus an untracked/modified file underneath that symlink path (e.g. `link/authorized_keys`, reported by git status as an untracked path `link/authorized_keys`). When the user reviews Changes in Desktop and clicks "Discard Changes" on that entry (a completely ordinary, unprompted action a user takes to clean up unwanted changes), Desktop computes `Path.resolve(repoPath, "link/authorized_keys")` — a string that looks safely inside the repo — and passes it to `shell.moveItemToTrash` (or `fs.rm`). The OS resolves `link` through the symlink and moves/deletes the *real* target file, which lives outside the repository.

### Impact Explanation
This allows an attacker-controlled repository to cause Desktop to delete or move arbitrary files outside the repository working directory that the OS user has permission to modify (e.g. SSH keys, shell profiles, other project files), triggered purely by the victim performing a normal "Discard Changes" action inside Desktop. This matches the "file write [or destructive modification] outside the repo" impact category — the corrupted value is the resolved filesystem path used for deletion/trash, which is computed without symlink-aware validation despite equivalent, already-existing tooling (`resolveWithin`) in the same codebase.

### Likelihood Explanation
Discarding changes is one of the most common actions in Desktop, requires only that the user open a hostile/compromised repository and click "Discard changes" on a listed file/directory — no unusual steps, no elevated privileges, no pre-existing local compromise. Git natively supports tracking symlinks (mode `120000`), so a malicious repository can trivially include one. The existing `resolveWithin` guard is proof the maintainers recognize this exact risk class but it was not applied consistently to `discardChanges`.

### Recommendation
In `GitStore.discardChanges` (and its `rm(...)` fallback branches), resolve `file.path` through `resolveWithin(this.repository.path, file.path)` (or `resolveWithinPosix`/`resolveWithinWin32` as appropriate) before calling `moveItemToTrash` or `rm`, and skip/reject any entry that resolves outside the repository root, mirroring the pattern already used in `copilot-conflict-context.ts` and `app-store.ts`.

### Proof of Concept
1. Create a malicious repository containing a tracked symlink `evil -> /Users/victim/.ssh` (or `evil -> /` on a case where broader access is desired), committed with mode `120000`.
2. Victim clones this repository with Desktop.
3. Attacker's repo (or a subsequent fetch/PR branch) also includes an untracked/modified file physically materialized at `evil/id_rsa` in the working tree (git will show it as an untracked path `evil/id_rsa` per `git status --porcelain=2`).
4. Victim opens the Changes list in Desktop, sees `evil/id_rsa`, and clicks "Discard Changes" (a completely normal cleanup action).
5. `GitStore.discardChanges` computes `Path.resolve(repoPath, "evil/id_rsa")` and calls `shell.moveItemToTrash` on it; because `evil` is a symlink to `~/.ssh`, the OS moves the victim's real `~/.ssh/id_rsa` to the trash (or, with the non-trash fallback path, permanently deletes it via `fs.rm`) — a file entirely outside the cloned repository.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
