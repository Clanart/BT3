## Title
Whole-file changes default to "included" and are silently committed while the diff content is hidden from review when a hunk line exceeds the render threshold - ([File: app/src/lib/git/diff.ts], [File: app/src/lib/patch-formatter.ts])

## Summary
The report's core defect is a **split-brain computation**: one code path (`getVotes`, shown to the UI) computes a value the user reviews, while a *different* path (`getPastVotes`, used for the actual consequential action) computes the value that is actually acted upon — and the two can diverge, so what the user is shown is not what actually happens. The GitHub Desktop analog of this "shown value ≠ acted-upon value" invariant break is in the diff/commit pipeline: the value the user *reviews* (the rendered diff) and the value that is *actually staged and committed* (`file.selection` applied via `formatPatch`) are computed from two different representations of the same hunk data, and Desktop's own size gate (`isDiffTooLarge`/`isBufferTooLarge` in `app/src/lib/git/diff.ts`) can suppress the reviewed representation while leaving the acted-upon representation fully intact and defaulted to "select all."

## Finding Description
When Desktop computes a diff for a working-directory file, `buildDiff` in `app/src/lib/git/diff.ts` checks whether the diff is renderable: [1](#0-0) 

If any single line exceeds `MaxCharactersPerLine`, or the raw buffer exceeds `MaxReasonableDiffSize`, the diff is downgraded to `DiffType.LargeText` — the hunks/lines are still fully present in the returned object (`hunks: diff.hunks`), but the UI does not render them by default: [2](#0-1) 

The user is shown only a placeholder ("The diff is too large to be displayed by default…") with a "Show Diff" button they may never click. Meanwhile, the file's `DiffSelection` for new/modified working-directory files defaults to "select all" (`DiffSelectionType.All`) in `app/src/lib/git/status.ts`, and when the user commits, `formatPatch` in `app/src/lib/patch-formatter.ts` walks the *same underlying hunk lines* — independent of whether they were ever rendered — and stages every selected line verbatim: [3](#0-2) 

This patch is fed directly to `git apply --cached` in `applyPatchToIndex`: [4](#0-3) 

So the invariant broken is: **"what the user visually reviewed" and "what gets written into the git index/commit" must be the same bytes.** Desktop's size-based rendering gate (`isDiffTooLarge`) decouples these two: the *review* surface is suppressed while the *action* surface (patch generation from `hunk.lines` + `file.selection`) is unaffected. A single crafted long line (or an otherwise-innocuous-looking file with one attacker-controlled line that exceeds `MaxCharactersPerLine`) is enough to hide arbitrary added content from the diff viewer while it is still auto-included in the next commit the user makes to that file, because selection defaults to "all" and is not tied to whether the content was ever displayed.

Existing guards don't stop this: `hasHiddenBidiChars` detection (`HiddenBidiCharsRegex` in `app/src/lib/diff-parser.ts`) only flags bidirectional Unicode control characters, not oversized/hidden lines, and it is a separate, narrower check that does not gate committing — it only drives a UI warning banner. The `isDiffTooLarge`/`isBufferTooLarge` gate exists purely for UX/performance and has no corresponding effect on `DiffSelection` defaults or on `formatPatch`.

## Impact Explanation
An attacker who controls a fetched/cloned repository (e.g. via a PR branch checked out in Desktop, or a file modified by a malicious pre-existing branch) can plant a change containing one very long line (exceeding the render threshold) that is not shown in the diff UI by default. If the user only glances at the file list and commits without clicking "Show Diff," the long/hidden line is silently included in the commit, corrupting what the user actually commits or pushes without their informed review — directly matching the accepted impact category "silent corruption of what the user commits or pushes." This is distinct from a UI cosmetic issue because the actual git object written to the index/commit is derived from unreviewed content.

## Likelihood Explanation
Likely to trigger unintentionally on large generated files, minified assets, or long JSON/lock-file lines, and trivially craftable by an attacker who can influence file content the victim will later edit/commit (common in shared branches, generated files, or merge conflict resolution flows). No local access, admin rights, or social engineering beyond normal collaboration is required — the victim performs an ordinary "stage and commit" action in the standard UI flow.

## Recommendation
- Tie the default `DiffSelection` state to whether the diff was actually rendered/reviewed: for `LargeText`/`Unrenderable` diffs, default to *not* auto-including lines that exceed the render threshold, or force an explicit confirmation before staging unreviewed hunks.
- Alternatively, block `formatPatch`/`applyPatchToIndex` from operating on hunks that were never rendered to the user, requiring an explicit "I reviewed this large diff" acknowledgment recorded per-file before commit.
- Extend the existing hidden-content warning mechanism (`hasHiddenBidiChars`) to also flag `isDiffTooLarge` conditions before allowing commit of files with unrendered content, rather than only offering a passive "Show Diff" button.

## Proof of Concept
1. In a working repository, create/modify a text file so that one line's length exceeds `MaxCharactersPerLine` (e.g. a single line with >5000 characters containing an embedded secondary payload later in the line), while keeping the rest of the file diff visually small.
2. Open GitHub Desktop's Changes view for this file. `buildDiff` classifies the diff as `DiffType.LargeText` due to `isDiffTooLarge`, and `app/src/ui/diff/index.tsx`'s `renderLargeTextDiff` shows only the "too large to display" placeholder — the actual added/changed content, including anything embedded later in the long line, is never shown.
3. Without clicking "Show Diff," commit the file normally (default selection is "all").
4. Inspect the resulting commit (`git show`) and confirm the entire long line — including content never rendered to the user — is present in the commit, produced by `formatPatch` iterating `hunk.lines` and `file.selection.isSelected(absoluteIndex)` independent of what the UI displayed.
