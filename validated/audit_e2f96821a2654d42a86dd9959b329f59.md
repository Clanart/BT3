### Title
`SignableTransaction::new` computes vbytes/fee over an output set that omits the OP_RETURN `data` output, so the signed transaction's real fee rate and weight are miscalculated - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report's bug class is an exchange-rate calculation that uses the wrong scaling factor, producing a systematically incorrect rate feeding a security-critical mechanism. The Serai analog lives in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`: the "fee rate" is `needed_fee / vbytes`, and the `vbytes` denominator is computed by `calculate_weight_vbytes` over a transaction that does not include the OP_RETURN `data` output, even though that output is included in the signed transaction. Every fee and weight check therefore runs against an understated size, and the resulting transaction - once signed by the FROST multisig - has a lower effective fee rate than the caller specified and may exceed `MAX_STANDARD_TX_WEIGHT`.

### Finding Description
`SignableTransaction::new` builds `tx_outs` including a zero-value OP_RETURN output when `data` is supplied (`send.rs:194-202`). It then computes the transaction's weight/vbytes via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (`send.rs:204`), which only builds `TxOut`s from `payments` - the OP_RETURN output is never represented in the sizing transaction.

Consequences:

- `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) is understated by `fee_per_vbyte * ~91` vbytes for a full 80-byte payload (8-byte value + compact-size length + OP_RETURN pushdata overhead + 80 bytes of data).
- The change branch repeats the same miscalculation: `fee_with_change = fee_per_vbyte * vbytes_with_change` (`send.rs:226-233`) also omits the OP_RETURN output, so the change value is inflated by the missing fee and the actual paid fee equals the understated `fee_with_change` exactly (since the leftover after payments + OP_RETURN(0) + change is precisely `fee_with_change`).
- The minimum-relay check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (`send.rs:211`) validates against the understated vbytes, so a caller-specified `fee_per_vbyte` that should pass the relay minimum can produce a transaction whose actual sat/vbyte rate falls below it.
- The standardness check `weight > MAX_STANDARD_TX_WEIGHT` (`send.rs:241`) is evaluated against a weight missing the OP_RETURN output, allowing a transaction that is actually non-standard to be approved.

The mistake is structurally identical to the external report: a ratio (fee rate) whose denominator (vbytes) is computed over the wrong quantity, invalidating every downstream decision derived from it, in code whose output feeds a threshold-signing mechanism (`TransactionMachine`/`TransactionSignMachine`, `send.rs:273-398`).

### Impact Explanation
The OP_RETURN `data` is attacker/caller-influenced transaction data fed into `SignableTransaction::new`, which an unprivileged party causes the multisig to sign (the transaction is completed via the public `preprocess`/`sign`/`complete` flow at `send.rs:302-428`). The signed result is a transaction that either:

- pays a real fee rate below the intended `fee_per_vbyte` and potentially below `DEFAULT_MIN_RELAY_TX_FEE`, so it will not relay or confirm - the intended spend fails while the FROST signing session was consumed, or
- exceeds `MAX_STANDARD_TX_WEIGHT`, producing a transaction no standard node will accept, i.e. funds that appear spent by the produced transaction are not actually movable via it.

### Likelihood Explanation
Triggered deterministically whenever `data` is non-empty (any OP_RETURN-bearing send). No adversarial collusion or validator misbehavior is required; the miscalculation is purely a function of public transaction inputs.

### Recommendation
Include the OP_RETURN `data` output when computing weight/vbytes in `SignableTransaction::new` (both the no-change call at `send.rs:204` and the `Some(&change)` call at `send.rs:226`). The cleanest fix is to perform the size calculation over the final `tx_outs` vector (which already includes payments, OP_RETURN, and, when applicable, a placeholder change output) rather than reconstructing the output list from `payments` alone inside `calculate_weight_vbytes`.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// L193-202: data output appended to tx_outs
tx_outs.push(TxOut {
  value: Amount::ZERO,
  script_pubkey: ScriptBuf::new_op_return(
    PushBytesBuf::try_from(data).expect("data didn't fit into PushBytes..."),
  ),
});

// L204: vbytes computed WITHOUT the data output
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes; // understates the real fee requirement

// L226-233: same omission in the change branch
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
let fee_with_change = fee_per_vbyte * vbytes_with_change;
```
Construct a `SignableTransaction::new` with `data = vec![0xAA; 80]`, one input, a payment, and a change output. `fee()` (`send.rs:138-141`) returns exactly `fee_with_change`, while `tx.weight()` / real vsize is ~91 vbytes larger than `vbytes_with_change`, so the effective fee rate is `fee_per_vbyte * vbytes_with_change / (vbytes_with_change + 91)` - strictly below the rate the caller requested and possibly below the relay minimum, with the transaction still passing all internal checks and being signed.
