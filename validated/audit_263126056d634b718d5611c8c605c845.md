### Title
Unchecked `u64` arithmetic on payment amounts and fees lets an unbounded user-supplied amount wrap the funds check, producing a permanently unconfirmable transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` never bounds the per-payment amounts an attacker can request. The total of all payments (`payment_sat`) and the adequacy check `input_sat < (payment_sat + needed_fee)` are computed with wrapping `u64` arithmetic, so a sufficiently large payment amount wraps the sum back to a small value, defeats the `NotEnoughFunds` check, and emits a transaction whose output values exceed its inputs — a transaction that can be signed but can never be confirmed, leaving the plan (and the vault's funds) stuck.

### Finding Description
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs), each payment's amount is only checked against the dust floor:

```rust
for (_, amount) in payments {
  if *amount < DUST { Err(TransactionError::DustPayment)?; }
}
```

There is no upper bound, and no check that a payment amount is a valid/attainable Bitcoin value (`<= 21e6 * 1e8`). The amounts are then summed and combined with the fee via plain `u64` operators, which wrap on overflow in release builds:

```rust
let input_sat = inputs.iter().map(|i| i.output.value.to_sat()).sum::<u64>();
let payment_sat = payments.iter().map(|p| p.1).sum::<u64>();
...
if input_sat < (payment_sat + needed_fee) {
  Err(TransactionError::NotEnoughFunds { .. })?;
}
```

`payment_sat` can overflow during the `.sum()`, and `payment_sat + needed_fee` (and later `payment_sat + fee_with_change` at the change computation) can overflow again. After wrapping to a small value, the `NotEnoughFunds` guard passes, and the change path computes `input_sat.checked_sub(payment_sat + fee_with_change)`, successfully pushing a change `TxOut`.

The resulting `SignableTransaction` then contains `TxOut`s with `Amount::from_sat(payment.1)` equal to the attacker's huge declared amounts — outputs summing far above `input_sat`. This is the same shape as the referenced Y2K bug: a fee/amount parameter accepted at creation time without an upper bound whose downstream arithmetic produces a value larger than the available funds, making resolution impossible.

Upstream, the amounts originate from user burns of `sriBTC` (each `payment.balance.amount.0` is a `u64` set by the burner) and are passed through `Bitcoin::make_signable_transaction` in processor/src/networks/bitcoin.rs directly into `BSignableTransaction::new`, so the value is public-input-controlled.

### Impact Explanation
- If `payment_sat` wraps to a value `<= input_sat - needed_fee`, the transaction is constructed and handed to the FROST signing machines. The multisig will sign it — the signature itself is valid — but the transaction is consensus-invalid (outputs exceed inputs), so no Bitcoin node will ever relay or confirm it.
- Since the plan's Eventuality is keyed on this txid (`Eventuality(signable.txid())`), the plan can never be confirmed complete and the vault's UTXOs allocated to it remain stuck — the direct analog of "epoch cannot be resolved, user funds stuck forever."
- Additionally, `fee()` computes `sum(inputs) - sum(outputs)` with a plain subtraction; once the invalid transaction exists, calling `fee()` underflows and panics.

### Likelihood Explanation
The attacker must be able to burn `sriBTC` for a large declared amount (up to `u64` range) — the amount is bounded only by what the Substrate side accepts, and `Amount`/`SubstrateAmount` are raw `u64` with no coin-supply-range check at this layer. Two payments near `2^64/2` (or one `u64::MAX` payment combined with the fee) suffice to wrap `payment_sat`/`payment_sat + needed_fee`. No validator collusion, malformed curve input, or internal access is needed — just burn instructions carrying large amounts. Severity is Medium: it requires large burn amounts and produces a stuck-plan DoS rather than direct theft.

### Recommendation
- Bound each payment amount to the maximum spendable BTC value (`21_000_000 * 100_000_000` sats) and reject anything larger.
- Use `checked_add`/`checked_sum` for `payment_sat`, `payment_sat + needed_fee`, and `payment_sat + fee_with_change`, returning `TransactionError::NotEnoughFunds` on overflow.
- Use `checked_sub` inside `fee()` (or an explicit `debug_assert`/`Err`) so a malformed transaction fails with an error instead of a panic.

### Proof of Concept
```rust
// Two payments whose amounts sum > u64::MAX.
let huge = u64::MAX - 10_000;
let payments = vec![(addr(), huge), (addr(), huge)];

// input_sat is a realistic vault balance, e.g. 1 BTC = 100_000_000 sats.
let tx = SignableTransaction::new(inputs, &payments, Some(change_addr), None, FEE);
// payment_sat wraps to ~u64::MAX - 20_000 - 2^64 → small; NotEnoughFunds never fires.
// `tx` is Ok(...) and contains TxOuts of `huge` sats each — consensus-invalid forever.
// tx.fee() additionally underflows: sum(inputs) - sum(outputs) < 0 → panic.
```
