## Local Analog Found

### Title
Order fill "last-leg sweep" in `_fillSameChain` releases the entire pooled per-token escrow to whichever solver completes an output leg first, when an order has multiple output legs sharing the same input token - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
The external report's core broken invariant is: a shared, cumulative resource pool (voting power) is allocated **entirely** to whoever triggers a state-changing action last, instead of proportionally to that actor's actual contribution. The local analog is the escrow-release branch in `IntrinsicIntents._fillSameChain`, where completing any single output leg of a same-chain intent order sweeps the **entire remaining `_orders[commitment][token]` balance** for that input token — not just the proportional share belonging to that leg — because escrow is keyed only by `(commitment, token)`, not by output-leg index.

### Finding Description
`_fillSameChain` loops over `order.output.assets[i]` / `order.inputs[i]` pairs by index `i`. For each leg it computes:

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [1](#0-0) 

When a leg is fully satisfied (`amountFilled == totalRequired`), the code deliberately reads and releases the **whole current balance** of `_orders[commitment][token]` for that token, rather than the exact amount owed for leg `i`. This was introduced intentionally to sweep rounding dust for a single-leg order (see the dedicated regression test `testPartialFill_RoundingDustReleasedToFinalSolver`) [2](#0-1) .

The escrow ledger itself is keyed only by `(commitment, token)` — there is no per-leg (`i`) sub-accounting: `_orders[commitment][token] = escrowed - amount;` in the shared `_withdraw` helper [3](#0-2) . If an order has two or more output legs (`order.output.assets[i]`) whose corresponding input legs (`order.inputs[i]`) reference the **same** input token address, completing the first such leg will read and drain the pooled escrow that still backs the *other*, not-yet-filled leg(s) for that same token — because the code has no way to distinguish "the balance owed to leg 0" from "the balance owed to leg 1" once they collapse into the same mapping key.

### Impact Explanation
An attacker (any solver, unprivileged) can construct or select an order with multiple output legs sharing an input token, then choose to fully satisfy the *cheapest* leg first. On that leg's completion, `escrowedAmount = _orders[commitment][token]` returns the sum of escrow meant for **all** legs on that token, and the full amount is transferred to that solver via `_withdraw`. The remaining, still-unfilled leg(s) are left with `_orders[commitment][token] == 0`, so:
- A later solver attempting to fill the remaining leg gets `escrowed == 0` and the transfer reverts with `UnknownOrder()` (fund lock for the user), or
- If it doesn't revert first, the accounting is simply wrong and the first solver receives escrow value it was never entitled to (fund theft from the pool meant for subsequent legs).

This matches the bounty's "stealing or loss of funds" / "transaction manipulation" impact class — a corrupted value (`_orders[commitment][token]`) is read and drained based on completion of leg `i` alone, when it actually represents pooled principal for multiple legs.

### Likelihood Explanation
Reachable via the fully public `fillOrder` entrypoint with no privileged role, prover, or relayer involved — any solver can pick which leg to fill first when a same-chain order happens to have (or is crafted to have) two legs on the same input token. This is plausible because `Order.inputs`/`Order.output.assets` are arbitrary arrays supplied at `placeOrder` time; nothing in the visible code path prevents two entries from sharing a token address. Likelihood is somewhat conditioned on whether such orders are commonly placed by users/UIs (multi-leg-same-token orders may be rare in practice), which lowers confidence versus a guaranteed trigger, but the code path itself contains no defensive check against this configuration.

### Recommendation
Track escrow release per `(commitment, i)` (leg index) rather than aggregating strictly by `(commitment, token)`, or compute the dust-sweep amount as `min(_orders[commitment][token], proportional_share_for_this_leg + leftover_dust_attributable_to_this_leg)` instead of unconditionally taking the whole pooled balance. At minimum, reject orders where multiple `output.assets`/`inputs` entries reuse the same input token address, or track a per-leg escrow sub-balance.

### Proof of Concept
1. User places a same-chain order with two output legs, both requiring DAI, and both legs' `order.inputs[i].token == USDC` (i.e., two legs pulling from the same escrowed USDC pool), `inputAmount = 1000 USDC` split conceptually as 500/500 across two output legs of 500 DAI each.
2. Solver A fully fills leg `i=0` (500 DAI) in one `fillOrder` call. Inside the loop, `amountFilled == totalRequired` for leg 0, so `escrowedAmount = _orders[commitment][USDC]`, which at this point still equals the **full 1000 USDC** (nothing withdrawn yet) — Solver A receives all 1000 USDC instead of the 500 USDC proportional to leg 0.
3. `_orders[commitment][USDC]` is now 0.
4. Solver B attempts to fill leg `i=1` (500 DAI) — `_withdraw` reads `escrowed = _orders[commitment][USDC] == 0` and reverts with `UnknownOrder()`, permanently locking Solver B out and leaving the user's second leg unfulfillable while Solver A walked away with escrow that should have been split between both legs.     function _fillSameChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        bool isFullyFilled = true;

        TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                uint256 dust = solverAmount - totalRequired;
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            } else {
                fillAmount = solverAmount > remaining ? remaining : solverAmount;
            }

            uint256 amountFilled = alreadyFilled + fillAmount;
            _partialFills[commitment][outputToken] = amountFilled;
            uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

            if (token == address(0)) {
                if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }

            if (totalRequired > amountFilled) isFullyFilled = false;
            if (protocolShare > 0) emit DustCollected(token, protocolShare);

            uint256 escrowedAmount;
            if (amountFilled == totalRequired) {
                escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
            } else {
                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
            }
            escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
            outputFills[i] = TokenInfo({token: outputToken, amount: fillAmount});
        }
