### Title
Out-of-range participant index in a DKG blame transaction panics the node via `HashMap` indexing in `blame_internal` - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP DKG blame-evaluation path indexes participant-keyed `HashMap`s with `sender`/`recipient` values that are only validated as non-zero `u16`, not as members of the set `1..=n`. An unprivileged participant can broadcast a blame transaction naming a `Participant` greater than `n` (or one never registered), causing a panic (`HashMap` index on a missing key) rather than a clean `Err`, crashing the validator process — the analog of the reported "oversized/unvalidated input → DoS" class.

### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` accept attacker-controlled `sender` and `recipient` `Participant` values and pass them to `blame_internal`, which performs unchecked indexing:

```rust
// crypto/dkg/pedpop/src/lib.rs
proof.dleq.verify(..., &[self.enc_keys[&decryptor], *proof.key], ...)  // line ~388
...
&self.commitments[&sender]                                            // line ~599
```

`self.commitments` is populated only for `1..=n` (in `calculate_share` from `all_participant_indexes`, and in `AdditionalBlameMachine::new` for `i in 1..=n`), and `self.enc_keys` only for registered participants. The `Participant` constructor rejects only `0` (`crypto/dkg/src/lib.rs`, `Participant::new`); nothing in `blame`/`blame_internal` bounds the value to `n`. On the coordinator side, the serialized `InvalidDkgShare` transaction reads `accuser`/`faulty` as `Participant::new(u16)` with no upper bound either (`coordinator/src/tributary/transaction.rs` lines ~346–353), so wire bytes directly control the index.

### Impact Explanation
A single crafted blame/accusation message containing `Participant` = `n+1` (or any unregistered index up to 65535) reaches `self.commitments[&sender]` or `self.enc_keys[&decryptor]` and panics the thread executing blame evaluation. This is a remotely triggerable denial of service of the validator/blame-arbitration path, and repeated messages can keep the process down, stalling DKG completion and any dependent signing.

### Likelihood Explanation
Blame messages are a normal, expected part of the DKG protocol and are carried as on-tributary transactions whose fields are deserialized from arbitrary bytes. Producing an out-of-range `Participant` requires only flipping two bytes in an otherwise well-formed transaction — no key material or collusion needed. The panic requires the node to evaluate blame for that sender/recipient pair, which is exactly the flow these APIs exist for. Caveat: I could not fully verify the coordinator call site that dispatches `Transaction::InvalidDkgShare` into `blame`; if it independently bounds accuser/faulty to `1..=n` before calling, reachability is reduced — but the in-scope pedpop API itself enforces no such bound and documents indexing as panic-capable ("may cause everything from inaccurate blame to panics" only under *invalid commitments*, not invalid indexes).

### Recommendation
In `blame_internal`, replace `self.commitments[&sender]` / `self.enc_keys[&decryptor]` with `.get(...)` and return a defined fault outcome (or an explicit `Err`) when the participant is not in the set. Additionally, validate `sender`/`recipient` against `1..=n` at the `blame`/`AdditionalBlameMachine::blame` boundary, and bound `accuser`/`faulty` to the set size when decoding `Transaction::InvalidDkgShare`.

### Proof of Concept
```rust
// Setup: n-of-t PedPoP DKG completed, producing BlameMachine for participant i.
// Attacker submits an InvalidDkgShare transaction with:
//   faulty  = Participant::new(n + 1).unwrap()   // valid non-zero u16, out of set
//   accuser = <any valid participant>
// When evaluated:
blame_machine.blame(
    Participant::new(n + 1).unwrap(), // sender: not in commitments
    accuser,
    msg,
    proof,
);
// => panic at `self.commitments[&sender]` (HashMap index: key not found)
// Alternatively, with proof = Some(...), `self.enc_keys[&decryptor]` panics
// for any decryptor index never registered.
```
