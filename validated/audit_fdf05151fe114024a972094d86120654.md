Based on my investigation into `app/src/lib/copilot-conflict-resolution.ts` and `app/src/lib/stores/app-store.ts`, I found a genuine analog to the reported invariant-violation bug class: a missing membership/validity check that lets an untrusted, attacker-influenced value (here, a Copilot-generated file path) be trusted and applied without re-validating it against the original trusted input set.

### Title
Unvalidated Copilot-resolution file paths allow writing arbitrary files inside the repository (including `.git/hooks`) via prompt-injected conflict content - ([File: app/src/lib/stores/app-store.ts])

### Summary
When Desktop's AI-assisted merge-conflict resolution feature applies Copilot's suggested resolutions, it iterates over `copilotResolutions` and writes `resolution.resolvedContent` to `resolveWithin(repository.path, resolution.path)` for every entry, but it never verifies that `resolution.path` is actually one of the file paths that were sent to the model as part of `buildConflictContext`'s `files` list.

### Finding Description
`buildConflictContext` in `app/src/lib/copilot-conflict-context.ts` reads the raw content of each conflicted file (including full file text with conflict markers) and sends it to the Copilot SDK as prompt context [1](#0-0) . The SDK's response — a list of per-file resolutions — is stored as `copilotResolutions` and later applied in `app-store.ts`:

```
const absolutePath = await resolveWithin(repository.path, resolution.path)
...
const onDiskFile = state.changesState.workingDirectory.files.find(f => f.path === resolution.path)
if (onDiskFile !== undefined && isConflictedFileStatus(onDiskFile.status) && !hasUnresolvedConflicts(onDiskFile.status)) {
  continue
}
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
``` [2](#0-1) 

Note that the "already resolved externally" guard only fires when `onDiskFile !== undefined`. If `resolution.path` refers to a path that is **not** in `state.changesState.workingDirectory.files` (i.e., not a tracked/conflicted working-directory change — such as `.git/hooks/post-checkout`, `.git/config`, or any file inside `.git/`), that guard is skipped entirely and the code proceeds straight to `writeFile`. The only path-safety check applied is `resolveWithin(repository.path, resolution.path)`, defined in `app/src/lib/path.ts` [3](#0-2) , which only guarantees the resolved path stays *inside* `repository.path` — it does not exclude `.git/` internals or restrict to the original conflict-file set. There is no check anywhere in this flow that `resolution.path` is a member of the `files` array originally passed into `buildConflictContext`/sent to the model.

This mirrors the reported bug's core pattern: an invariant assumed by the surrounding system ("resolutions only ever touch the exact set of files we asked about") is not actually enforced by the code that consumes the (partially attacker-influenced) output, allowing state to be corrupted outside the intended bounds — analogous to `totalSupply` being altered outside its assumed cap because `burn()` wasn't constrained by the same invariant as `mint()`.

### Impact Explanation
Since the entire raw content of conflicted files — attacker-controlled if the user is resolving a merge/rebase/cherry-pick against a maliciously crafted branch or fork — is fed verbatim into the model's prompt [4](#0-3) , an attacker who controls the conflicting content can attempt prompt injection to make the model emit an out-of-scope "resolution" with a `path` such as `.git/hooks/post-checkout` and `resolvedContent` containing a malicious shell script. Because the write path is only checked for containment inside `repository.path` (which includes `.git/`) and not membership in the original conflicted-file set, this could result in a git hook being silently written to disk. The next git operation that triggers that hook (checkout, commit, merge) would execute attacker-controlled code — a serious code-execution primitive that also silently corrupts what the user believes they are committing/pushing, matching the "silent corruption of what the user commits or pushes" and "code execution" criteria.

### Likelihood Explanation
Likelihood depends on whether the Copilot model can reliably be steered by injected file content to emit a resolution path outside the file list it was given — this is a prompt-injection dependent condition I could not fully verify from static code alone (I don't have visibility into the exact system prompt/schema constraints imposed on the SDK response, if any, beyond what's shown in `copilot-conflict-resolution.ts`). However, the code-level guard that *should* prevent this regardless of model behavior — validating `resolution.path` against the known conflicted-files list — is verifiably absent from the write loop shown above.

### Recommendation
Before writing, verify `resolution.path` exists in the original `files` list passed to `buildConflictContext` (or equivalently, that it corresponds to a currently conflicted file per `state.changesState.workingDirectory.files`) regardless of whether `onDiskFile` is `undefined`; reject/skip any resolution whose path isn't in that trusted set, and explicitly reject any path that resolves inside `.git/`.

### Proof of Concept
1. Set up a repository and initiate a merge/rebase where the "theirs" side contains a conflicted file whose content includes a prompt-injection payload instructing the assistant to also emit a resolution object for `.git/hooks/post-checkout` with a malicious script body.
2. Trigger Desktop's Copilot-assisted conflict resolution flow (`gatherCommitContext`/`buildConflictContext` → Copilot SDK → `copilotResolutions`).
3. If the model complies and returns an extra resolution entry for `.git/hooks/post-checkout`, the apply loop at `app/src/lib/stores/app-store.ts:7233-7259` finds no matching entry in `state.changesState.workingDirectory.files` (since `.git/hooks/post-checkout` isn't a working-directory change), skips the "already resolved" check, and calls `writeFile` unconditionally, writing the attacker's script into the hooks directory.
4. On the next `git checkout`, the hook executes with the user's privileges.

Note: I was unable to fully inspect `app/src/lib/copilot-conflict-resolution.ts` (the module that parses/validates the raw SDK response into `copilotResolutions`) within this session, so it's possible some schema-level validation exists there that constrains `path` to the requested file set — if so, this would materially reduce or eliminate the vulnerability. I recommend confirming this directly in that file before treating this as fully validated.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
