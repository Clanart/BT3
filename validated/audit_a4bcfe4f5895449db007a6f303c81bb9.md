### Title
Unchecked `u64` fee arithmetic wraps to a near-zero fee, producing an unconfirmable transaction that locks multisig UTXOs - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
CVE-2016-4472 is an overflow-check failure: bounds/overflow guards that were supposed to fire were silently removed, letting attacker-shaped input drive arithmetic past its limits. The direct analog in Serai is the fee computation in `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), which performs unchecked `u64` multiplication and addition on the externally influenced `fee_per_vbyte` and on the sum of payment amounts. In release builds this arithmetic wraps instead of erroring, so the overflow protection is effectively absent — the same bug class as the advisory.

### Finding Description
`SignableTransaction::new` computes:

- `let mut needed_fee = fee_per_vbyte * vbytes;` — unchecked multiplication (`send.rs:206`)
- `let fee_with_change = fee_per_vbyte * vbytes_with_change;` (`send.rs:227`)
- `if input_sat < (payment_sat + needed_fee)` — unchecked addition (`send.rs:215`)
- `input_sat.checked_sub(payment_sat + fee_with_change)` — `checked_sub` guards the subtraction, but the inner `payment_sat + fee_with_change` can itself overflow before the check (`send.rs:228`)
- `fee()` returns `sum(inputs) - sum(outputs)` with a plain subtraction (`send.rs:139`)
- `payment_sat = payments.iter().map(|p| p.1).sum::<u64>()` — unchecked `sum` (`send.rs:187`)

`fee_per_vbyte` is not a fixed constant. In production it is produced by `Bitcoin::median_fee`, which averages the fee rate of every transaction in a block (`processor/src/networks/bitcoin.rs:388–415`). Any unprivileged party who gets Bitcoin transactions mined — i.e., anyone who pays fees on their own transactions — directly influences `fee.0`, which is passed verbatim as `fee_per_vbyte` into `BSignableTransaction::new` (`processor/src/networks/bitcoin.rs:446–452`).

If `fee_per_vbyte * vbytes` exceeds `u64::MAX` (~1.8e19), the product wraps modulo 2^64 in release builds. `needed_fee` then becomes a small garbage value:

- The `NotEnoughFunds` check at `send.rs:215` passes because `payment_sat + needed_fee` is small.
- `checked_sub(payment_sat + fee_with_change)` at `send.rs:228` returns a large change amount because the wrapped `fee_with_change` is small.
- The constructed transaction pays only the wrapped (tiny) remainder as its actual fee: `fee = input_sat - payment_sat - change ≈ wrapped_value`.

The resulting transaction has a fee far below any relay minimum and will never confirm, yet `SignableTransaction`/`TransactionSignMachine` treats it as valid and drives the FROST signers to sign it (`send.rs:373–397`). The spent inputs are Serai multisig UTXOs; the transaction consumes them while being unconfirmable, and `Eventuality`/plan tracking records it as in-progress.

In debug builds, or wherever overflow checks are enabled, the same path panics — a remotely triggerable crash of the processor during `signable_transaction`/`needed_fee`.

### Impact Explanation
An attacker who can push `median_fee` high enough (by broadcasting transactions paying extreme fee rates — costly but a pure on-chain action requiring no privilege) causes the coordinator-selected processors to construct and sign a Bitcoin transaction whose fee wraps to near zero. That transaction will never confirm, while it commits the multisig's UTXOs as spent inputs under `Prevouts::All` (`send.rs:375`). Funds routed through that plan are locked: reported as processed by the scheduler yet not spendable on-chain. Additionally, any overflow-checked build suffers a hard panic — a remote DoS on the signing path. These map to the advisory's "denial of service (crash) or possibly execute arbitrary code" class, instantiated here as fund-locking and crash rather than memory corruption.

### Likelihood Explanation
Triggering the wrap requires `fee_per_vbyte * vbytes > u64::MAX`; with vbytes in the hundreds, `fee_per_vbyte` needs to be on the order of 10^16–10^17 sats/vbyte — i.e., transactions paying ~10^17+ sats of fee in a small tx, and enough of them to control the block median. This is economically expensive and requires influencing `median_fee`'s sampling of a specific block (`processor/src/networks/bitcoin.rs:388–415`), so it is not a casual attack. However, the wrap needs only `fee_per_vbyte` to be attacker-influenced, which it is by design. Medium likelihood-adjusted severity; the missing `checked_mul`/`checked_add` is the concrete defect regardless.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new` and `fee()`:

- Replace `fee_per_vbyte * vbytes` with `fee_per_vbyte.checked_mul(vbytes)` and return `TooLowFee`/`NotEnoughFunds` or a dedicated `FeeOverflow` error on `None`.
- Replace `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`, rejecting on overflow before the `checked_sub`.
- Use `checked_sub` in `fee()` (or compute the difference with `saturating`/explicit error).
- Use `try_fold`/`checked_add` for `sum::<u64>()` over payment amounts.
- Clamp `median_fee`'s per-transaction fee rate to a sane bound (e.g., `u64::MAX / MAX_STANDARD_TX_WEIGHT`) before returning it.
