### Title
Stale manual conflict resolutions are silently reapplied to unrelated content in multi-commit rebase/cherry-pick operations - (File: `app/src/lib/git/rebase.ts`, `app/src/lib/git/cherry-pick.ts`, `app/src/lib/stores/updates/changes-state.ts`)

### Summary
GitHub Desktop stores a user's manual conflict resolutions ("ours"/"theirs" for unmergeable files) in a `Map<string, ManualConflictResolution>` keyed **only by file path**, and this map is carried forward across every commit of the same multi-commit `rebase`/`cherry-pick`/`reorder`/`squash` operation, not reset per-commit. When the *same path* conflicts again on a later commit in the sequence — with entirely different content, because a malicious or crafted upstream/target branch touches that path repeatedly — Desktop automatically re-applies the earlier, now-irrelevant resolution to the new conflict without prompting the user again.

### Finding Description
The conflict state carrying the resolutions map is produced by `getConflictState` in `app/src/lib/stores/updates/changes-state.ts`: [1](#0-0) 

`updateConflictState` decides whether to keep the previous `manualResolutions` based only on whether the conflict `kind` (merge vs rebase) is the same — it does not check whether the conflict is for the same commit or the same blob/oid: [2](#0-1) 

When the user clicks "Continue", `continueRebase` (and the analogous `continueCherryPick`) walks every entry of `manualResolutions` and matches it to the *current* conflicted file **purely by path string**, then stages that resolution automatically — files with a stored resolution are explicitly excluded from `otherFiles` (i.e., excluded from requiring fresh user staging/review): [3](#0-2) [4](#0-3) 

Because a rebase/cherry-pick/reorder can touch the same path across multiple commits in the sequence (this is normal and demonstrated in Desktop's own tests, e.g. `second.md` conflicting twice in sequence), the stored resolution from the *first* conflict on that path is blindly reused for the *second, unrelated* conflict on that path, with no re-diff shown to the user and no re-confirmation prompt: [5](#0-4) 

### Impact Explanation
This breaks the invariant that a "resolve conflict" decision reflects the specific content the user reviewed. An attacker who controls the branch/commits being rebased onto or cherry-picked (e.g., a malicious `git remote`/fork the victim pulls and rebases against) can engineer multiple sequential commits that all touch the same file path with conflicting hunks. Once the user resolves the *first* conflict with "theirs" (accepting the attacker's version) for that path, every *subsequent*, differently-content conflict on that same path in the operation is silently resolved the same way and staged into the final commit/history without ever being shown to the user — resulting in silent corruption of what the user ultimately commits and pushes, potentially injecting attacker-controlled content that the user never reviewed or approved for later commits in the sequence.

### Likelihood Explanation
This requires a normal, unprivileged Desktop workflow — rebasing, cherry-picking, or reordering commits against/from a branch/fork controlled by an attacker — with no admin rights, local access, or prior malware needed. It requires the attacker to craft multiple commits that conflict on the same path (a realistic and easily engineered condition), and it requires the victim to hit conflicts on that path more than once during a single operation and choose a manual "ours/theirs" resolution the first time. This is a plausible but not trivial-to-hit scenario (moderate likelihood), since it depends on user interaction with the conflict UI and reuse of the same path across commits.

### Recommendation
Scope `manualResolutions` per-conflict-instance rather than per-path for the lifetime of the whole multi-commit operation — e.g., key resolutions by `(path, current conflicted blob OIDs)` or simply clear/re-derive the resolutions map every time `continueRebase`/`continueCherryPick` succeeds and a new conflict is detected for a subsequent commit in the sequence, forcing the user to re-confirm the resolution whenever the underlying conflicting content changes.

### Proof of Concept
1. Attacker crafts a branch `evil` with three sequential commits, each modifying the same file `shared.md` with content that will conflict with the victim's `feature` branch at that same path.
2. Victim runs `git rebase evil` (or reorders/cherry-picks similarly) from Desktop; the first commit conflicts on `shared.md`. Victim manually resolves it as "Use Their Version" (attacker's version) via Desktop's conflict UI, which stores `manualResolutions.set('shared.md', theirs)` in the multi-commit-operation conflict state (see `updateMultiCommitOperationStateAfterManualResolution`, `app/src/lib/stores/app-store.ts:8830-8862`).
3. Victim clicks "Continue"; `continueRebase` applies the stored resolution and moves to the next commit, which also conflicts on `shared.md` with entirely different content designed by the attacker.
4. Because `manualResolutions` still has `shared.md → theirs` and is not cleared, `continueRebase`/`continueCherryPick` silently stages the attacker's newest version of `shared.md` for this new conflict without ever showing it to the user or a conflict-resolution prompt, per `app/src/lib/git/rebase.ts:449-462`.
5. The victim completes the rebase believing they only approved one conflict resolution, while multiple different attacker-controlled versions of `shared.md` have been silently committed into their history and will be pushed.

  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

export async function continueCherryPick(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  manualResolutions: ReadonlyMap<string, ManualConflictResolution> = new Map(),
  progressCallback?: (progress: IMultiCommitOperationProgress) => void
): Promise<CherryPickResult> {
  // only stage files related to cherry pick
  const trackedFiles = files.filter(f => {
    return f.status.kind !== AppFileStatusKind.Untracked
  })

  // apply conflict resolutions
  for (const [path, resolution] of manualResolutions) {
    const file = files.find(f => f.path === path)
    if (file === undefined) {
      log.error(
        `[continueCherryPick] couldn't find file ${path} even though there's a manual resolution for it`
      )
      continue
    }
    await stageManualConflictResolution(repository, file, resolution)
  }

  const otherFiles = trackedFiles.filter(f => !manualResolutions.has(f.path))
  await stageFiles(repository, otherFiles)
