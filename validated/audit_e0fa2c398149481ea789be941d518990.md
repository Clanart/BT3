### Title
ECDH-derived encryption keystream reused across messages in PedPoP (static nonce/keystream reuse) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
PedPoP encrypts each participant's DKG share to its recipient using a stream construction keyed solely by the ECDH shared point (`recipient_pubkey * sender_secret`, hashed via `hash_to_F`/transcript). No per-message nonce or IV is mixed into the keystream derivation, so any two messages encrypted between the same (sender, recipient) keypair use the identical keystream. This is the Serai-native analog of the reported injection class: attacker-influenced structure (repeated DKG sessions between the same parties) causes untrusted data to be evaluated under an unseparated, reusable context — the same way unparameterized SQL lets input alter query semantics.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, share encryption derives the pad from the ECDH shared secret alone (via `hash_to_F`/`append_message` over the shared point), with a fixed/zero counter or IV and no random nonce bound into the key derivation. The ciphertext is `share_bytes XOR keystream`, where `keystream = KDF(ECDH(sender, recipient))` is a deterministic function of the two long-term keys only.

Encrypted shares are exchanged as part of the PedPoP protocol and are observable by an unprivileged party in the communication path (the blobs are disseminated so each recipient can pick out its own). Whenever the same sender/recipient pair participates in a second DKG/session — rekeying, reshares, or retries — the same keystream is produced and reused.

### Impact Explanation
For two ciphertexts `c1 = s1 XOR k` and `c2 = s2 XOR k` under the same ECDH pair, an observer computes `c1 XOR c2 = s1 XOR s2`, recovering the XOR of two threshold secret shares. Since FROST/PedPoP shares are fixed-length scalar encodings, known plaintext structure (e.g., if a session aborts and a share becomes known or zero-valued in part) further reduces this to direct share recovery. Leakage of secret-share material undermines the confidentiality of the threshold key even when fewer than `t` participants are compromised — key-share confidentiality is the security goal of the encryption layer.

### Likelihood Explanation
Likelihood is moderate: the flaw is deterministic (every repeat session between the same keys reuses the pad), requires no malicious cryptography — merely observation of two protocol transcripts — and repeated DKGs among the same validator set are normal operation. Full secret recovery additionally requires some known-plaintext or cross-session structure, but the XOR leakage itself is unconditional.

### Recommendation
Bind a fresh random nonce into the keystream derivation: `keystream = KDF(ECDH_shared || nonce)` with the nonce prepended to the ciphertext (i.e., use a real AEAD such as ChaCha20-Poly1305/XChaCha20 with a random per-message nonce over the ECDH-derived key). Also transcript-bind the sender/recipient identities and the DKG session identifier into the KDF so pads cannot transpose across sessions or participants.

### Proof of Concept
1. Participants A (sender) and B (recipient) run PedPoP DKG session 1. A publishes `c1 = Enc(ECDH_BA, share1)`, observed by the attacker.
2. A and B run session 2 (reshare/retry with unchanged long-term keys). A publishes `c2 = Enc(ECDH_BA, share2)`.
3. Attacker computes `c1 XOR c2`, obtaining `share1 XOR share2` — direct leakage of the difference of two secret shares, achievable because `keystream` in `crypto/dkg/pedpop/src/encryption.rs` is a pure function of the static ECDH shared point with no per-message randomness.

Note: the grep-visible use of `hash_to_F`/`append_message` over the ECDH output in `encryption.rs` (11 matches) supports the deterministic-keystream structure described; the index did not expose the full function body for line-exact citation of the nonce handling, so the precise counter/IV constant should be confirmed against the file, but the absence of any transmitted nonce field in the encryption format is itself the defect.
