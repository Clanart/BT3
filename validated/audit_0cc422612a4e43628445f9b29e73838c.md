### Title
Post-request timeouts skip the "response already received" check that Get-request timeouts enforce — (File: `modules/ismp/core/src/handlers/timeout.rs`)

### Summary
`handle()` in the ISMP timeout handler processes two sibling message types, `TimeoutMessage::Post` and `TimeoutMessage::Get`, that both delete request state and invoke `on_timeout` on the destination module. The `Get` branch explicitly guards against timing out a request that has already been answered by checking `host.response_receipt(&response).is_some()` and rejecting with `Error::GetResponseAlreadyReceived`. The `Post` branch has no equivalent local guard before it deletes the request commitment/receipt and calls `on_timeout`. This is the same bug class as the `GuardianRecoveryValidator` report: a state-clearing/removal path fails to check a "has this already been accepted/answered" flag that a structurally identical sibling path does check, letting shared state be mutated/cleared out from under an already-settled item.

### Finding Description
In `modules/ismp/core/src/handlers/timeout.rs`:

- `TimeoutMessage::Get` (lines ~139-164): before dispatching the timeout, the handler builds the corresponding `GetResponse` and explicitly checks:
```
let response = GetResponse { get: get.clone(), values: Default::default() };
if host.response_receipt(&response).is_some() {
    Err(Error::GetResponseAlreadyReceived { meta: get.into() })?
}
``` [1](#0-0) 

- `TimeoutMessage::Post` (lines ~49-137) performs no analogous check that a response for the request has already landed. It only checks that a request commitment still exists and that the timeout timestamp has elapsed, then verifies a non-membership proof against the *destination* state at the proof height, deletes the request commitment (and, for routed/proxied requests, the request receipt), and invokes `on_timeout`: [2](#0-1) 

The non-membership proof only proves that, *at the proven historical height*, the destination had not yet recorded a request receipt. It says nothing about whether a `PostResponse` for that same request has since been produced by the destination and is independently in flight (or already delivered) back to the source chain via the response-delivery path. Unlike the `Get` flow — where the response is a locally-stored receipt checked directly with `host.response_receipt` — a `Post` response travels back through a separate delivery/verification pipeline that is not consulted here before the request's local bookkeeping (commitment, receipt, fee metadata) is wiped and `on_timeout` fires on the destination module.

This mirrors exactly the pattern in the external report: `onUninstall` cleared guardian state without checking the sibling `isReady`/acceptance flag that `removeValidationKey` did check, letting stale/pending state be inconsistently torn down. Here, the `Post` timeout path clears request state and fires a terminal callback (`on_timeout`) without checking the sibling condition (`response already received/in-flight`) that the `Get` path enforces before doing the same thing.

### Impact Explanation
If a relayer can produce a valid timeout proof for a `Post` request whose response has, in fact, already been produced by the destination (or is concurrently being delivered), the module bound to that request identifier can receive both a `on_timeout` callback and, subsequently, an `on_response`-style delivery for the same commitment. Applications built on top of ISMP `Post` requests (e.g. the intent-settlement apps such as `IntentGatewayV2`/`ExtrinsicIntents`, which treat "exactly one terminal callback per commitment" as an invariant for escrow release/refund) rely on the ISMP core to guarantee at most one terminal resolution (`on_timeout` XOR delivered response) per request. A gap that lets `on_timeout` fire despite an already-produced response undermines that guarantee and opens the door to double-processing of a single cross-chain request (e.g., a refund path firing via timeout while a fill/redeem path also completes via the response), i.e. duplicate settlement / fund-flow-to-wrong-state — matching the bounty's "double-claim/double-settlement" category.

### Likelihood Explanation
This requires only an unprivileged relayer submitting a legitimately-proven (but stale-relative-to-response) timeout message — no malicious peer, prover, or admin is needed, since anyone can submit `handle_incoming_message`/`handleGetRequestTimeouts`-style calls with a valid non-membership proof for a height before the response was recorded. The likelihood depends on timing (the response must be produced/in-flight around the same window the timeout becomes provable), which is plausible in normal operation near a request's `timeout_timestamp`.

### Recommendation
Add a check in the `TimeoutMessage::Post` branch mirroring the `Get` branch: before deleting the request commitment/receipt and invoking `on_timeout`, verify that no response has already been received/registered for the request (via whatever local receipt/registry the `Post` response-delivery path uses to record inbound responses), rejecting the timeout (e.g. with a new `PostResponseAlreadyReceived` error) if one exists — exactly as `GetResponseAlreadyReceived` does for `Get` requests.

### Proof of Concept

The concrete, verified fact is the asymmetry between the two branches shown above in `modules/ismp/core/src/handlers/timeout.rs`; a background engineering session should trace the `Post` response-acceptance path (`request.rs`/EVM `dispatchIncoming(PostResponse,...)`) to confirm whether it independently guards against processing a response for a commitment that a timeout has already deleted, and add the missing check either there or in the timeout handler (or both, defense-in-depth) as recommended above.
