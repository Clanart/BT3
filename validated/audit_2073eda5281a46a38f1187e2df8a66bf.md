### Title
Attacker-injected `Participant` indexes cause unchecked HashMap indexing panic (DoS) in PedPoP blame path - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to prototype pollution — where an attacker injects keys into an object/map that the program later trusts — PedPoP's blame machinery accepts an attacker-chosen `sender`/`recipient` `Participant` and uses it directly as a `HashMap` index. `blame_internal` performs `self.commitments[&sender]` and `Decryption::decrypt_with_proof` performs `self.enc_keys[&decryptor]`, both panicking when the supplied index is not one of the registered participants `1..=n`. An unprivileged party can therefore crash any node evaluating blame with a crafted accusation.

### Finding Description
`Participant` is a non-zero `u16` newtype; it is not bounded by `n` at construction (`Participant::new` only rejects 0). `AdditionalBlameMachine::new` populates `commitments` and `encryption.enc_keys` strictly for indexes `1..=n` (`crypto/dkg/pedpop/src/lib.rs:656-660`). However:

- `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`) — panic if `decryptor ∉ 1..=n`.
- `blame_internal` indexes `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`) — panic if `sender ∉ 1..=n`.

Both `BlameMachine::blame` (`lib.rs:623`) and `AdditionalBlameMachine::blame` (`lib.rs:674`) take `sender`/`recipient` as free parameters with no bounds check against `params.n()`. The in-repo consumer confirms reachability: `CoordinatorMessage::VerifyBlame { accuser, accused, share, blame }` flows into `.blame(accuser, accused, substrate_share, substrate_blame)` after deserializing attacker bytes via `EncryptedMessage::read` (`processor/src/key_gen.rs:504-549`).

To reach the panic at `lib.rs:599`, the attacker needs a message that survives `decrypt_with_proof`: a valid Schnorr PoP over `msg.key` and, when a proof is supplied, a valid DLEq binding `msg.key` to `enc_keys[accused]`. Both are producible by anyone who performed the ECDH encryption themselves (they know the ephemeral scalar), since `encrypt` signs the PoP with the ephemeral key (`encryption.rs:153-167`). For `sender ∉ 1..=n`, the pop/DLEq still verify because `pop_challenge` merely commits to `from` bytes — a `Participant` value like 200 serializes fine and is not range-checked.

### Impact Explanation
A single malformed blame accusation — carryable in `EncryptedMessage`/`EncryptionKeyProof` bytes plus two attacker-chosen `Participant` indexes — panics the evaluating node. In a validator/processor context (`VerifyBlame` handler), this is a remotely triggerable crash (denial of service), halting key generation, signing, or blame adjudication. It also lets an actually-faulty DKG participant abort blame evaluation against themselves by embedding an out-of-range index, degrading the accountability mechanism.

### Likelihood Explanation
Reachable with purely public inputs: the attacker supplies `sender`/`recipient` indexes and an `EncryptedMessage` they encrypted themselves (giving them the ephemeral scalar needed for a valid PoP and `EncryptionKeyProof` DLEq). No collusion, key material, or trusted position is required; any party able to submit or relay blame data triggers the panic. Mitigating factor: impact is a crash/abort (DoS), not key compromise, keeping this at Medium severity.

### Recommendation
In `blame_internal` and `Decryption::decrypt_with_proof`, replace indexing (`self.commitments[&sender]`, `self.enc_keys[&decryptor]`) with fallible lookups (`get`), and reject `sender`/`recipient` values outside `1..=n` before evaluation — e.g., validate both against `ThresholdParams`/`all_participant_indexes` at the top of `BlameMachine::blame` and `AdditionalBlameMachine::blame`, returning a defined `PedPoPError`/blame result rather than panicking.

### Proof of Concept
```rust
// Context: a completed/failed PedPoP session with n = 5 participants.
// `commitment_msgs` are the public round-1 messages (broadcast, attacker-known).
let mut machine = AdditionalBlameMachine::<Ristretto>::new(context, 5, commitment_msgs).unwrap();

// Attacker (or relay) crafts an EncryptedMessage honestly encrypted to victim
// participant 3's enc_key — they know the ephemeral scalar, so they can also
// build a valid EncryptionKeyProof (DLEq between msg.key and enc_keys[3]).
let msg: EncryptedMessage<Ristretto, SecretShare<_>> = /* attacker-built, valid PoP */;
let proof: Option<EncryptionKeyProof<Ristretto>> = /* valid DLEq */;

// Inject an out-of-range Participant index as `sender` — Participant::new only
// rejects 0, so Participant(200) is accepted by the type system.
let sender = Participant::new(200).unwrap();
let recipient = Participant::new(3).unwrap();

// decrypt_with_proof succeeds (valid pop + valid proof),
// then `self.commitments[&sender]` at pedpop/src/lib.rs:599 indexes a key
// that was never inserted -> panic, crashing the node.
machine.blame(sender, recipient, msg, proof);
```

Equally, passing `recipient = Participant::new(200)` panics earlier at `self.enc_keys[&decryptor]` in `crypto/dkg/pedpop/src/encryption.rs:388` whenever a proof is supplied.
