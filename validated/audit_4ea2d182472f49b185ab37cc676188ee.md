### Title
Scanner reports immature coinbase outputs as spendable funds, locking scheduled payments - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the JPEG'd finding where `pool.lpToken.balanceOf(address(this))` counted untracked tokens as distributable supply (locking rewards), `Scanner::scan_block` counts outputs from the coinbase transaction (`block.txdata[0]`) as ordinary received funds, even though coinbase outputs are unspendable for 100 blocks (COINBASE_MATURITY). The reported "balance" includes funds that are not actually spendable, exactly the "measured balance != usable balance" class of bug.

### Finding Description
`Scanner::scan_transaction` matches outputs purely by `script_pubkey` against the registered script set, and `scan_block` iterates over `block.txdata` including index 0, the coinbase transaction (`networks/bitcoin/src/wallet/mod.rs:199-227`). A `ReceivedOutput` produced from a coinbase carries a valid `offset` (e.g. `Scalar::ZERO` for the base key) and the full coinbase `value`, so it is indistinguishable from a normal deposit.

Downstream, `SignableTransaction::new` sums `inputs.iter().map(|input| input.output.value.to_sat())` as `input_sat` (`networks/bitcoin/src/wallet/send.rs:175`) and builds a `TxIn` for every supplied `outpoint` (`send.rs:177-185`) without any maturity check. The FROST `TransactionSignMachine::sign` then produces BIP-341 key-path signatures over `Prevouts::All` (`send.rs:373-397`), and `TransactionSignatureMachine::complete` returns a fully signed `Transaction` (`send.rs:413-428`) that is consensus-invalid — every node rejects a spend of a coinbase output younger than 100 blocks.

The doc comment on `scan_block` acknowledges the issue ("This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed"), but no such pass exists in this crate and `scan_block` is the exposed API.

### Impact Explanation
Any coinbase output paying a registered Serai script (multisig external/change/branch/forward address) is reported as a confirmed, spendable `ReceivedOutput`. The scheduler can select it to fund payments; the resulting signed transaction can never be mined while the coinbase is immature, so the associated payment plan stalls and the other UTXOs committed as inputs to that plan are effectively locked behind an unbroadcastable transaction until it is rebuilt. This is "funds reported received that are not spendable" and a direct analog of rewards locked by counting unowned tokens in the pool denominator.

### Likelihood Explanation
Requires a Bitcoin miner to direct coinbase payouts to a Serai-controlled P2TR script. Mining is permissionless and pool operators routinely set custom coinbase outputs; an attacker who obtains (or guesses) an active multisig address can attempt this whenever they mine a block. The trigger needs a mined block rather than a normal transaction, which lowers frequency versus a plain transfer, but it is fully reachable by an unprivileged party and repeatable.

### Recommendation
In `Scanner::scan_block`, skip `block.txdata[0]` or filter its results, mirroring the suggested `scan_transaction(&block.txdata[1 ..])` usage in the doc comment. Alternatively, tag `ReceivedOutput` with a coinbase flag (detectable via `tx.is_coinbase()`) so callers/scheduler can defer it until maturity.

### Proof of Concept
```rust
// networks/bitcoin/tests/wallet.rs already demonstrates the path:
// send_and_get_output mines a block paying p2tr_script_buf(key) via the
// coinbase ("generatetoaddress"), then:
let outputs = scanner.scan_block(&block);
assert_eq!(outputs, scanner.scan_transaction(&block.txdata[0])); // coinbase output returned
// outputs[0] is a ReceivedOutput with offset ZERO and the full coinbase value,
// yet it is unspendable for 100 blocks.
// Feeding it into SignableTransaction::new(...) and signing via
// TransactionMachine produces a tx rejected by all nodes (immature coinbase spend),
// locking the plan and its co-inputs.
```

Note: severity is bounded (Medium) — the issue self-heals after maturity and the doc comment partially discloses the caveat, but no in-crate guard exists and the exposure is real.
