### Title
Missing Length Validation on `Bid.SearcherSig`/`AuctioneerSig` Causes Out-of-Bounds Panic in `getSigner()` - (File: `kaiax/auction/bid.go`)

### Summary
`kaiax/auction/bid.go`'s `getSigner()` function indexes into a caller-supplied signature byte slice (`sig[crypto.RecoveryIDOffset]`, `sig[0:32]`, `sig[32:64]`) without first validating that the slice is at least 65 bytes long. Both `BidData.SearcherSig` and `BidData.AuctioneerSig` are attacker-controlled fields deserialized directly from an RLP-encoded `Bid` (via `Bid.DecodeRLP`) submitted by any auction bidder/searcher. A short or empty signature field causes an unrecovered index-out-of-range panic.

### Finding Description
`getSigner` is the shared helper used by both `Bid.ValidateSearcherSig()` and `Bid.ValidateAuctioneerSig()`: [1](#0-0) 

Unlike every other signature-handling path in the codebase — e.g. `crypto.Ecrecover`/`sigToPub` which explicitly check `len(sig) != SignatureLength` before touching `sig[RecoveryIDOffset]` — [2](#0-1)  and `secp256k1.checkSignature` [3](#0-2) , `getSigner()` performs no length check on `sig` before:
- reading `copiedSig[crypto.RecoveryIDOffset]` (index 64),
- slicing `copiedSig[0:32]` and `copiedSig[32:64]`.

`BidData` (containing `SearcherSig []byte` and `AuctioneerSig []byte`) is decoded straight from untrusted RLP input via `Bid.DecodeRLP`: [4](#0-3) 

There is no RLP-level or upstream field-length validation enforcing these byte slices to be exactly 65 bytes before `getSigner` is invoked from `ValidateSearcherSig`/`ValidateAuctioneerSig`: [5](#0-4) 

This mirrors the reported bug class in iccDEV (`CIccTagXmlSegmentedCurve::ToXml()`): user-controllable input is unsafely incorporated into a structured data buffer without a bounds check before indexing/slicing, leading to an out-of-bounds access. In Go this manifests as a runtime panic (index out of range) rather than a C-style heap overflow, but the root cause — missing length validation on attacker-supplied binary blob prior to fixed-offset access — is the same.

### Impact Explanation
Any unprivileged auction searcher/bidder submitting a `Bid` (e.g., via the auction module's bid submission RPC) with a `SearcherSig` or `AuctioneerSig` shorter than 65 bytes (including a 0-length slice) triggers an unrecovered panic inside `getSigner`. If this validation path runs on the node's bid-processing/auction-settlement goroutine without panic recovery, it can crash or otherwise disrupt the node's auction module, denying bid processing/settlement for that node (and potentially causing divergence in auction outcomes between nodes that do/don't crash or recover differently). This affects the auction bid-validation flow used to select the winning bid/searcher for block building, so it can directly impact auction settlement integrity/availability — a Medium/High-severity issue depending on whether this runs in a recoverable goroutine.

### Likelihood Explanation
High likelihood of reachability: the `Bid` structure's signature fields are directly attacker-supplied and RLP-decoded with no field-size enforcement before being passed into `getSigner`. Triggering the panic requires only submitting a `Bid` with a malformed/short signature — no privileged access, special key material, or race condition needed.

### Recommendation
Add an explicit length check at the start of `getSigner()` (mirroring `crypto.Ecrecover`/`checkSignature`): 
```go
func getSigner(sig, digest []byte) (common.Address, error) {
    if len(sig) != crypto.SignatureLength {
        return common.Address{}, ErrInvalidSignature
    }
    ...
}
```
Additionally, consider validating `SearcherSig`/`AuctioneerSig` length immediately upon `Bid` decode/ingestion (e.g., in `DecodeRLP` or the bid pool admission check) to reject malformed bids early, and ensure any bid-validation goroutine has panic recovery as defense in depth.

### Proof of Concept
1. Craft a `BidData` with `SearcherSig = []byte{}` (or any slice shorter than 65 bytes) and valid/arbitrary values for other fields.
2. RLP-encode the `BidData` and submit it as a `Bid` through the auction module's bid ingestion path (which calls `Bid.DecodeRLP` then eventually `ValidateSearcherSig`).
3. `ValidateSearcherSig` calls `getSigner(b.SearcherSig, digest)`.
4. Inside `getSigner`, `copiedSig[crypto.RecoveryIDOffset]` (index 64) is accessed on a slice of length 0 (or < 65), causing:
```
panic: runtime error: index out of range [64] with length 0
```
5. The same applies to `ValidateAuctioneerSig` with a malformed `AuctioneerSig`.

Note: I could not fully trace whether the bid RPC/pool ingestion path wraps bid validation in panic-recovery middleware — this would determine whether the impact is a per-goroutine crash (recovered, DoS-limited) or a full node crash. A Devin session with full repo/runtime access would be needed to confirm the exact blast radius of this panic within the auction module's goroutine structure.

```go
func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

func (b *Bid) ValidateAuctioneerSig(auctioneer common.Address) error {
	digest := b.GetEthSignedMessageHash()

	recoveredAuctioneer, err := getSigner(b.AuctioneerSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover auctioneer sig: %v", err)
	}

	if recoveredAuctioneer != auctioneer {
		return fmt.Errorf("invalid auctioneer sig: expected %v, calculated %v", auctioneer.String(), recoveredAuctioneer.String())
	}

	return nil
}
```

```go
func getSigner(sig, digest []byte) (common.Address, error) {
	// Manually convert V from 27/28 to 0/1
	copiedSig := slices.Clone(sig)
	if copiedSig[crypto.RecoveryIDOffset] == 27 || copiedSig[crypto.RecoveryIDOffset] == 28 {
		copiedSig[crypto.RecoveryIDOffset] -= 27
	}

	v := copiedSig[crypto.RecoveryIDOffset]
	r := new(big.Int).SetBytes(copiedSig[0:32])
	s := new(big.Int).SetBytes(copiedSig[32:64])
	if !crypto.ValidateSignatureValues(v, r, s, true) {
		return common.Address{}, ErrInvalidSignature
	}
```
