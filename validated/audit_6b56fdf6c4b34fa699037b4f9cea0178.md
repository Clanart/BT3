## Title
Inconsistent JS/HTML-safety escaping in ProtoJSON string serialization — missing `'` and `&` escapes in C++, C#, and upb-based (Python/Ruby/PHP) JSON writers - (File: `src/google/protobuf/json/internal/writer.cc`)

## Summary
The NocoDB bug is a classic "partial escaping" failure: the EJS template HTML-entity-encoded a fixed character set but omitted the two characters (`'` and `\`) needed to safely place attacker-controlled data inside a JS string literal, so the token broke out of its quoting context. Protobuf's ProtoJSON encoders exhibit the identical bug class: several official Protobuf language runtimes intentionally escape `<`/`>` (and, in one case, `&`/`'`/`=`) beyond what the JSON spec requires, explicitly to prevent the serialized JSON from breaking out of an HTML/`<script>` context when embedded by a consuming application — but the character sets escaped are inconsistent, and most non-Java backends omit `&` and `'` entirely.

## Finding Description
Protobuf's own code comments establish the invariant that ProtoJSON string encoding must escape certain characters "to prevent security bugs in JavaScript," even though the JSON spec doesn't require it:

- Java's `JsonFormat` explicitly escapes `<>&='` for exactly this reason: [1](#0-0) 
- The C++ core JSON writer's `MustEscape` only escapes `<` and `>` (plus a list of Unicode zero-width/bidi characters) under the same rationale, but has no case for `&` or `'`: [2](#0-1) 
- The fast-path `kUnsafeChars` set used to skip escaping for runs of "safe" bytes is `"\"\\<>"` — again omitting `&` and `'`: [3](#0-2) 
- The C# `JsonFormatter.CommonRepresentations` table escapes `<` (0x3c) and `>` (0x3e) but leaves `&` (0x26) and `'` (0x27) as empty (unescaped) entries, and the `WriteString` switch that follows only adds handling for surrogate pairs and a list of Unicode bidi/zero-width code points — never `&` or `'`: [4](#0-3) [5](#0-4) 
- The shared upb JSON encoder — used natively by Python, Ruby, and PHP bindings — only escapes the JSON-spec-mandated characters (`\n \r \t \" \f \b \\` and control chars `< 0x20`) and has no handling at all for `<`, `>`, `&`, or `'`: [6](#0-5)  (identical copies exist at [7](#0-6)  and [8](#0-7) )

Java's own regression test confirms the intended, security-motivated invariant that `<>&='` must all be escaped in ProtoJSON output: [9](#0-8) 

Consuming-application exposure assumption: a downstream web application takes an attacker-controlled string field (e.g., a user-supplied name, comment, or token forwarded through a protobuf message) and calls the library's public ProtoJSON serialization API, then embeds the resulting JSON text directly into an HTML document — most commonly an inline `<script>` block for SSR/hydration (e.g., `var data = <ProtoJSON output>;`) — trusting that the serializer already neutralizes JS-breaking characters, exactly the pattern Java's own escaping and comments advertise as protection ("to prevent security bugs in JavaScript").

## Impact Explanation
If the consuming application relies on ProtoJSON's advertised JS-safety guarantee (present in Java, and partially in C++/C#) but uses the C++, C#, Python, Ruby, or PHP/upb backends, an attacker-controlled string containing a single quote, ampersand, or (for upb-based backends) `<`/`>` can break out of a quoted JS string or attribute context embedded in the page, in the same way the NocoDB token broke out of `token: '<%= token %>'`. This is a reflected/DOM-XSS-class outcome, contingent on the consuming application's embedding pattern — matching CWE-79 and the Medium severity of the source advisory.

## Likelihood Explanation
Embedding protobuf-serialized JSON directly into inline `<script>` tags for SSR hydration is a common and realistic integration pattern, and the presence of explicit "prevent security bugs in JavaScript" escaping in two of the language backends (Java fully, C++ partially) demonstrates this is a known, anticipated risk within the Protobuf project itself — yet the protection is inconsistently and incompletely implemented across backends (C++/C# omit `&`/`'`; upb-based Python/Ruby/PHP omit all of `<`/`>`/`&`/`'`).

## Recommendation
Align all ProtoJSON string writers (C++ `MustEscape`/`kUnsafeChars`, C# `CommonRepresentations`/`WriteString`, and the shared upb `jsonenc_put_escaped_char`) with Java's `JsonFormat` character set, escaping `<`, `>`, `&`, `=`, and `'` consistently, or explicitly document that ProtoJSON output is not safe for direct HTML/script embedding without additional context-aware escaping by the caller, so backends don't provide inconsistent implicit guarantees.

## Proof of Concept
Using the C++ (or Python/Ruby/PHP via upb) JSON writer, serialize a message with a string field set to `it's & <fine>`:
- Java `JsonFormat.printer().print(msg)` → escapes to `it\u0027s \u0026 \u003cfine\u003e` (safe).
- C++ `MessageToJsonString` (via `writer.cc` `MustEscape`) → produces `"it's & \u003cfine\u003e"` — `'` and `&` pass through unescaped: [2](#0-1) 
- upb-based Python/Ruby/PHP `MessageToJson` → produces `"it's & <fine>"` — none of `<`,`>`,`&`,`'` are escaped: [6](#0-5) 

If this output is embedded as `var msg = <output>;` inside a `<script>` block, the unescaped `'` terminates the JS string literal early, allowing injected script — the same mechanic as the NocoDB advisory's `token: '<%= token %>'` break-out.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}
