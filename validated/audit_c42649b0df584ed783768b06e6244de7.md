## Title
SSH askpass trampoline auto-answers keyboard-interactive password prompts with cached credentials keyed only by a server-supplied username, with no binding to the actual remote host - (File: `app/src/lib/trampoline/trampoline-askpass-handler.ts`)

### Summary
`handleSSHUserPassword` in the trampoline askpass handler matches any SSH prompt of the form `<username>'s password: ` and, if a password is already cached for that exact `username` string, returns it automatically without asking the user. [1](#0-0)  The `username` value is taken directly from the prompt text via a regex, not from Desktop's own knowledge of which remote/host the git operation is actually talking to. [2](#0-1)  The stored credential is looked up purely by that username string. [3](#0-2) 

### Finding Description
For `keyboard-interactive` SSH authentication, the *prompt text itself* is supplied by the SSH server, not generated purely by the local OpenSSH client. Desktop's askpass trampoline treats OpenSSH's stdout/stderr prompts as trusted input and dispatches on simple prefix/suffix/regex matching:

- `firstParameter.endsWith("'s password: ")` → `handleSSHUserPassword` [4](#0-3) 
- Inside it, `promptRegex = /^(.+@.+)'s password: $/` extracts an arbitrary `username` capture group with no validation against the actual remote hostname of the current git operation. [5](#0-4) 
- That `username` is used verbatim as the lookup key into `TokenStore` via `getSSHUserPassword(username)`. [3](#0-2) 
- If a match is found, the cached secret is returned immediately to the SSH subprocess/server — **no UI prompt is shown to the user in that case.** [6](#0-5) 

There is no check that `username` corresponds to the host or account actually being connected to for the current git operation (`trampolineEnvironmentPath`/`operationGUID` carry no host binding — see `trampoline-environment.ts`, which tracks only path and background-task flags per token, not the target hostname). This is exactly the class of bug described in the seed report: a value that flows into a trust/security decision (there, seed/password length in wallet derivation; here, the identity string used to key a secret lookup) is accepted from an untrusted source without any length/format/origin validation that would bind it to the legitimate context.

The similarly-structured `handleSSHHostAuthenticity` function does perform a strict equality check against a hardcoded GitHub fingerprint before auto-accepting a host key, which is the correct pattern. [7](#0-6)  `handleSSHUserPassword` has no equivalent binding check — it silently trusts any username string that happens to match a previously-cached entry.

### Impact Explanation
An attacker who controls an SSH remote that the user's Desktop client connects to (e.g. a malicious/compromised git server added as a remote, or a server reached via cloning a URL from an untrusted source) can use keyboard-interactive authentication to send a crafted prompt string such as `git@github.com's password: `. If the user previously stored an SSH password/passphrase under that exact username key (e.g. from a legitimate `git@github.com` interaction), Desktop's askpass handler will match the regex, look up the cached secret keyed only on that username, and return it straight to the SSH subprocess talking to the attacker's server — resulting in credential exfiltration to a party the user never intended to authenticate with, without any additional user interaction or visible prompt.

### Likelihood Explanation
Requires (1) the user to have previously chosen "remember" for an SSH password/passphrase under some `user@host`-shaped identifier, and (2) the user to connect (clone/fetch/push) to an attacker-controlled or MITM'd SSH endpoint that supports keyboard-interactive auth with attacker-chosen prompt strings. Both conditions are plausible in the threat model this class of report targets (attacker controls a git remote/proxy response the user interacts with) but require the victim to have SSH password-based auth in active use with stored credentials, which somewhat limits the population of exploitable users versus HTTPS/token-based auth flows.

### Recommendation
Bind the stored/looked-up SSH user-password credential to the actual remote/host of the current git operation (e.g. compare the host portion of the captured `username` against the trampoline environment's known target host for `operationGUID`) before returning a cached secret automatically, rather than trusting the server-supplied prompt string's username in isolation. At minimum, reject or prompt the user instead of auto-returning when the prompt-derived host does not match the git operation's actual remote host.

### Proof of Concept
1. User connects once to `git@github.com` via SSH password auth and checks "remember" (stored under key `"git@github.com"` in `SSHUserPasswordTokenStoreKey`).
2. Attacker sets up a git remote (e.g. `ssh://attacker.example.com/repo.git`) that the user is lured/social-engineered-free into fetching from (e.g. via a legitimately-added remote that later points to attacker infra, or a compromised mirror).
3. Attacker's SSH server offers keyboard-interactive auth and sends the prompt string `git@github.com's password: ` regardless of the actual target host.
4. Desktop's `createAskpassTrampolineHandler` matches `endsWith("'s password: ")`, calls `handleSSHUserPassword`, regex-extracts `git@github.com`, finds the cached credential, and returns it directly to the attacker's server via the trampoline response — exfiltrating the previously-stored GitHub SSH password without any dialog being shown.

Note: I was not able to fully verify from local index contents alone that OpenSSH's keyboard-interactive prompt text is passed through unmodified end-to-end by the bundled `desktop-trampoline`/`ssh-wrapper` binaries versus the OS OpenSSH client version bundled in Electron; this is an assumption based on standard SSH `keyboard-interactive` protocol behavior (RFC 4256) where prompt strings are server-supplied. Confirming the exact wrapper behavior would require inspecting `vendor/desktop-trampoline` more fully or running a live test, which is beyond what the indexed code excerpts confirm.

```typescript
async function handleSSHUserPassword(operationGUID: string, prompt: string) {
  const promptRegex = /^(.+@.+)'s password: $/

  const matches = promptRegex.exec(prompt)
  if (matches === null || matches.length < 2) {
    return undefined
  }

  const username = matches[1]

  const storedPassword = await getSSHUserPassword(username)
  if (storedPassword !== null) {
    // Keep this stored password around in case it's not valid and we need to
    // delete it if the git operation fails to authenticate.
    setMostRecentSSHUserPassword(operationGUID, username)
    return storedPassword
  }
```

```typescript
/** Retrieves the password for the given SSH username. */
export async function getSSHUserPassword(username: string) {
  try {
    return TokenStore.getItem(SSHUserPasswordTokenStoreKey, username)
  } catch (e) {
    log.error('Could not retrieve passphrase for SSH key:', e)
    return null
  }
}
```
