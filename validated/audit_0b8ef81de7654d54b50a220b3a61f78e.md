### Title
`SignableTransaction::new` omits the OP_RETURN data output from fee/weight estimation, causing underpayment of the promised fee rate and bypass of the standard-weight check — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The transaction builder enumerates every component contributing to transaction weight — inputs, payments, change — but the size/fee calculation in `calculate_weight_vbytes` is invoked with only `payments` and `change`, after the caller-supplied OP_RETURN `data` output has already been appended to `tx_outs`. The enumeration of dangerous/weight-bearing outputs is incomplete: the OP_RETURN output is never counted. This mirrors the Fickling bug class — a safety check built over an incomplete list of items lets a dangerous case pass.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed to `tx_outs` at lines 194–202, but `calculate_weight_vbytes` at line 204 is called as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — it builds its template `Transaction` from `payments` only, never seeing `data`. Consequences, all in `networks/bitcoin/src/wallet/send.rs`:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed on a vsize that excludes the OP_RETURN output. The final transaction does pay `needed_fee` (since fee = inputs − outputs and outputs are fixed), so the *effective* feerate is strictly lower than the caller-specified `fee_per_vbyte`.
- The `TooLowFee` minimum-relay-fee check (line 211) uses the same underestimated `vbytes`, so a transaction whose true size pushes it below `DEFAULT_MIN_RELAY_TX_FEE` per vbyte is accepted and signed.
- The `MAX_STANDARD_TX_WEIGHT` check (line 241) uses the underestimated `weight`, so a transaction that is actually non-standard (>400,000 WU) can be constructed and signed.
- The same omission occurs in the change branch: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (line 226) also ignores `data`, so `fee_with_change` is underestimated and the `value >= DUST` leftover calculation (line 228–230) can produce a change output absorbing funds that should have covered the real fee.

An unprivileged party reaches this through the "transaction data they cause to be signed" surface: the `data` parameter is attacker-influenced (e.g., a user's deposit/burn memo routed into the OP_RETURN by the integrator path), and the signed result is broadcast expecting `fee_per_vbyte` to hold.

### Impact Explanation
The multisig signs and broadcasts a transaction whose real feerate is below the requested rate and potentially below the minimum relay fee, so it is silently dropped or never confirmed — funds committed as payments/change are effectively locked until reconstruction. In the worst case the transaction exceeds `MAX_STANDARD_TX_WEIGHT` and is unrelayable entirely, while `SignableTransaction::new` reported success. This is a correctness/safety-check bypass on a value-bearing path, not merely a DoS: the invariant "the signed TX pays `fee_per_vbyte`" is broken by attacker-controllable input size.

### Likelihood Explanation
Any `data` of non-trivial length (up to the 80-byte cap checked at line 171) inflates the real vsize by ~10–90+ vbytes versus the estimate. When `fee_per_vbyte` is near the relay minimum, or the transaction is near the standardness weight cap, the check bypass is deterministic. It requires an integrator path that forwards user-controlled `data` into `SignableTransaction::new`, which is the documented purpose of the OP_RETURN parameter.

### Recommendation
Include the OP_RETURN output in the template transaction inside `SignableTransaction::new` — e.g., build the output list passed to `calculate_weight_vbytes` from the already-constructed `tx_outs` (or add a `data: Option<&[u8]>` parameter so its push-opcode and payload length are counted) before computing `vbytes`, `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check. Apply the same fix to the change-branch estimate at line 226.

### Proof of Concept
```rust
// SignableTransaction::new(inputs, &[(payment_script, 10_000)], None,
//   Some(vec![0xAA; 80]), fee_per_vbyte)
//
// tx_outs ends up with [payment, OP_RETURN(80 bytes)], but
// calculate_weight_vbytes(tx_ins.len(), payments, None) builds a template
// containing ONLY the payment output. The returned `vbytes` omits the
// ~90-byte OP_RETURN output, so needed_fee = fee_per_vbyte * vbytes
// underpays relative to the real serialized size. With
// fee_per_vbyte = 1 and a real size near the min-relay cutoff, or a
// payment set pushing real weight over MAX_STANDARD_TX_WEIGHT, the
// signed transaction is produced yet is non-standard/unrelayable.
// Assert: tx.weight() (signed result) > the `weight` value validated
// at line 241 whenever data.is_some().
```
