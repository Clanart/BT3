### Title
`optimistic_payout()` never validates `verification_signature`, letting an unauthenticated caller broadcast withdrawal payouts before Citrea's mandated manual-verification window - (File: `core/src/rpc/aggregator.rs`)

### Summary
The `ClementineAggregator::optimistic_payout` RPC handler accepts an `OptimisticWithdrawParams` message that carries a `verification_signature` field, whose entire purpose (per `BridgeConfig::aggregator_verification_address`) is to prove that Citrea/aggregator manually re-verified the withdrawal before a real Bitcoin payout transaction is signed and broadcast. The handler reads and logs this field but never verifies it against `aggregator_verification_address`, and the aggregator's gRPC service is documented to not enforce client certificates at all. This mirrors the report's bug class: a state-changing operation that is supposed to be gated by a specific authority's authorization silently skips that authorization check.

### Finding Description
`BridgeConfig` documents the intended control: [1](#0-0) 

which states the ECDSA address is used "for an extra verification of aggregator's identity and to force citrea to check withdrawal params manually during some time after launch."

In `ClementineAggregator::optimistic_payout`, the request is parsed and `opt_withdraw_params.verification_signature` is only referenced in a `tracing::info!` log call; it is never checked against `self.config.aggregator_verification_address`: [2](#0-1) 

The rest of the function only validates: the UTXO is unspent, the output script pubkey type, that a deposit exists for the withdrawal, and that the user's own Schnorr signature (`SECP.verify_schnorr`) matches the withdrawal's prevout pubkey: [3](#0-2) 

Once those checks pass, the aggregator collects verifier partial signatures, aggregates a final signature, and — under the `automation` feature — pushes the fully signed optimistic-payout transaction directly into the tx-sender broadcast queue: [4](#0-3) 

Separately, the project's own documentation states that the aggregator's gRPC endpoints are not protected by mTLS client-certificate checks the way verifier/operator endpoints are: [5](#0-4) 

confirmed by the interceptor code, which only guards verifier/operator servers via `OnlyAggregatorAndSelf`; there is no equivalent interceptor wired for the aggregator server in `core/src/servers.rs`.

### Impact Explanation
This breaks the binding: "a message signed by the required authority (Citrea/aggregator verification address) versus the withdrawal payout actually fronted." The config's own comment states this signature is meant "to force citrea to check withdrawal params manually during some time after launch" — i.e., it is a mandatory circuit-breaker on early optimistic payouts. Since the aggregator server accepts calls without client-certificate authentication and the handler never checks `verification_signature`, any network caller who can produce a syntactically valid `OptimisticWithdrawParams` (including a legitimately-obtained user withdrawal signature, which is not secret once a withdrawal is initiated on Citrea) can trigger the verifiers to co-sign and have the aggregator broadcast a real BTC payout transaction — bypassing the intended manual-verification safety window entirely. This is an unauthenticated caller reaching a state-changing/broadcasting method that was designed to require a specific authority's signature, matching the High-impact bucket "an unauthenticated state-changing or broadcasting call."

### Likelihood Explanation
High. The aggregator RPC surface is, per the project's own documentation, reachable without any client certificate. The missing check is a simple omission — `verification_signature` is parsed into `opt_withdraw_params` and logged, but no branch in `optimistic_payout` ever calls a signature-recovery/verification routine against `aggregator_verification_address`, so the bypass requires no special conditions beyond calling the RPC with an otherwise-valid withdrawal payload.

### Recommendation
In `core/src/rpc/aggregator.rs::optimistic_payout`, before proceeding to collect verifier signatures or queue the transaction for broadcast, recover the ECDSA signer address from `opt_withdraw_params.verification_signature` over the withdrawal parameters and require it to equal `self.config.aggregator_verification_address` (when configured/required), returning `Status::unauthenticated`/`Status::invalid_argument` otherwise. Additionally, consider adding an authentication layer (mTLS or equivalent) to the aggregator's public RPC surface to close the broader unauthenticated-access gap noted in `docs/usage.md`.

### Proof of Concept
Not directly executable from static review alone (would require a running aggregator + verifier set); this is stated as an unconfirmed gap. Conceptually:
1. Deploy/observe a live Clementine aggregator (no client cert required per `docs/usage.md`).
2. Obtain a valid user withdrawal signature (`in_signature`) for an existing Citrea withdrawal (available once the user initiates withdrawal on Citrea, as required data for `parse_withdrawal_sig_params`).
3. Call `optimistic_payout` directly with any (or no) `verification_signature` value.
4. Observe that `optimistic_payout` in `core/src/rpc/aggregator.rs` (lines 1010-1267) proceeds unconditionally to collect verifier co-signatures and, with the `automation` feature, enqueues the signed transaction for broadcast (lines 1237-1259) — with no check ever performed on `verification_signature`.

## RPC Authentication

Clementine uses mutual TLS (mTLS) to secure gRPC communications between entities
and to authenticate clients. Client certificates are verified and filtered by
the verifier/operator to ensure that:

1. Verifier/Operator methods can only be called by the aggregator (using
   aggregator's client certificate `aggregator_cert_path`)
2. Internal methods can only be called by the entity's own client certificate
   (using the entity's client certificate `client_cert_path`)

The aggregator does not enforce client certificates but does use TLS for encryption.
