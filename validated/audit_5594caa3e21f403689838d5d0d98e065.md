### Title
`SignableTransaction::new` computes weight/vsize and fee on a payment set that omits the OP_RETURN `data` output, producing a systematically under-priced (and potentially non-relayable) transaction - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
The external report describes a function returning the *requested* amount (10e18) rather than the *actual received* amount (10e18-1), which then causes a downstream transfer of the requested amount to revert, DoSing `deposit`. The Serai analog in `networks/bitcoin/src/wallet/send.rs` is that `SignableTransaction::new` computes the transaction's weight, vbytes, required fee, dust-threshold change, and the max-standard-weight check from an *assumed* transaction layout (`payments` only) that differs from the *actual* transaction it builds (which additionally contains the OP_RETURN `data` output). The signed transaction therefore has a larger real vsize than the one priced, exactly mirroring "assumed amount != actual amount" with a consensus-level DoS consequence.

### Finding Description
`SignableTransaction::new` builds `tx_outs` including an OP_RETURN output when `data` is supplied (send.rs lines 193-202), but then computes the transaction weight and vbytes via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — passing `payments`, which does not include the data output (send.rs line 204). The same omission occurs when computing `fee_with_change` via `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs lines 225-227).

Consequences within `new`:

1. `needed_fee = fee_per_vbyte * vbytes` prices an undersized transaction (line 206). The minimum-relay-fee check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (line 211) also uses the undersized `vbytes`, so it validates against a rate the final transaction does not achieve.
2. The change amount `input_sat - (payment_sat + fee_with_change)` (line 228) is likewise computed with an under-priced fee.
3. The standardness guard `weight > MAX_STANDARD_TX_WEIGHT` (line 241) uses the weight of the transaction *without* the data output, so a transaction near the limit can pass this check yet exceed `MAX_STANDARD_TX_WEIGHT` once the OP_RETURN output is included.

The signed output of `TransactionSignatureMachine::complete` (lines 413-428) is the real transaction containing the OP_RETURN output, i.e., the "actual received" object differs from the "assumed" object used for all accounting — the exact structural defect from the report (return/use the requested figure, act on a different actual figure).

### Impact Explanation
The actual fee paid is `sum(inputs) - sum(outputs)`, which equals the computed `needed_fee`, but the real virtual size is roughly `vbytes + (9 + push overhead + data.len())` (up to ~90 vbytes for the permitted 80-byte payload). For any `fee_per_vbyte` at or near the minimum relay rate, the effective fee rate of the broadcast transaction drops below `DEFAULT_MIN_RELAY_TX_FEE`, so Bitcoin Core rejects it at mempool acceptance. The multisig then produces signatures for a transaction that cannot be relayed, and because the signature commits to the exact transaction (sighash over all prevouts/outputs), the entire signing session is wasted — a denial of service of the spend path directly analogous to the deposit DoS in the report. In the boundary case, a transaction passing the `MAX_STANDARD_TX_WEIGHT` check can also be rejected as non-standard, locking those inputs until a new plan is constructed. Additionally, even where the transaction remains relayable, the protocol pays a lower fee rate than requested, degrading confirmation reliability.

### Likelihood Explanation
`data` flows from the instructions being encoded into the transaction (the OP_RETURN branch exists precisely for instruction data). Any spend plan that embeds data triggers the under-estimate deterministically — no rounding luck is needed, unlike the report's 1-wei condition. The severity is Medium: it requires a data-carrying transaction priced near the minimum relay rate (or near the standard weight cap) to cause outright rejection; otherwise it silently degrades the fee rate.

### Recommendation
In `SignableTransaction::new`, compute weight/vbytes over the *actual* output set. Either:

- Extend `calculate_weight_vbytes` to take the already-built `tx_outs` (including the OP_RETURN output and, when applicable, change), or
- Add the data output's size to `payments` before calling `calculate_weight_vbytes` — e.g., construct a `(script_pubkey, value)` entry for the OP_RETURN `TxOut` and include it in the slices passed at lines 204 and 226.

Apply the same fix to both the no-change and with-change calls, so `needed_fee`, `fee_with_change`, the min-relay check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the final transaction.

### Proof of Concept
Conceptual, at the `bitcoin_serai` crate level:

```rust
// One input, one payment, 80 bytes of OP_RETURN data, fee rate of 1 sat/vbyte
let data = vec![0xaa; 80];
let stx = SignableTransaction::new(
    vec![input],                    // a ReceivedOutput with sufficient value
    &[(payment_script, DUST)],      // minimal payment
    None,                           // no change
    Some(data),                     // OP_RETURN output
    1,                              // fee_per_vbyte = min relay rate
).unwrap();

// needed_fee passed the check: needed_fee >= 1000 * vbytes_est / 1000
// where vbytes_est EXCLUDES the OP_RETURN output (~90 extra vbytes).
// The final signed tx's actual vsize = vbytes_est + ~90,
// so its effective rate = needed_fee / actual_vsize < 1 sat/vbyte
// -> rejected by Bitcoin Core mempool (min relay fee not met),
// DoSing the spend and wasting the FROST signing session.
```

The divergence is visible directly: `tx_outs` (used for the real transaction at lines 246-251) contains the OP_RETURN `TxOut`, while every `calculate_weight_vbytes` call operates on `payments`, which does not.
