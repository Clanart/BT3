### Title
Malicious FROST preprocess forces aggregate nonce `R` to the point at infinity, panicking honest signers in `Hram::hram` - ([File: networks/bitcoin/src/crypto.rs])

### Summary
The CVE class (untrusted input → NULL deref / crash) maps onto Rust as an attacker-reachable panic. In `bitcoin-serai`'s BIP-340 `Hram`, `x(R)` calls `.expect("point at infinity")` on the aggregated nonce point. The FROST binding factor `rho` is a public, deterministic hash over the whole preprocess set, so a malicious cosigner who sends their preprocess last can choose commitments `(D, E)` such that `D + rho_i * E` exactly cancels the sum of the other signers' contributions, driving the aggregate `R` to infinity. Every honest signer then panics inside `sign_share`/`verify` instead of returning a `FrostError` — a deterministic, remotely-triggered denial of service of the signing session.

### Finding Description
`x()` in `networks/bitcoin/src/crypto.rs:13-16` panics on the point at infinity, and `Hram::hram` (`networks/bitcoin/src/crypto.rs:59-73`) feeds it the aggregated nonce `R`. `R` is built in `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:383`, via `B.nonces`) as the sum over participants of `D_l + rho_l * E_l`. `rho_l` is computed by `B.calculate_binding_factors` (`crypto/frost/src/sign.rs:371`) from `rho_transcript`, which commits to `group_key`, `hash_msg(msg)`, and a hash of the entire transcript of preprocesses (`crypto/frost/src/sign.rs:362-368`). All of this is public to the attacker before they submit their preprocess. `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) only rejects identity for each individual commitment point — it does not (and cannot) prevent a pair of valid non-identity points whose bound sum is infinity. The doc comment on `Schnorr` (`networks/bitcoin/src/crypto.rs:78-80`) claims infinity has "a negligible probability ... even with malicious participants present"; that assumption is incorrect because `rho` is deterministic and known to the attacker, making the infinity result deterministic, not probabilistic.

### Impact Explanation
A single malicious signing-set participant deterministically crashes every honest cosigner that calls `TransactionSignMachine::sign` / `AlgorithmSignMachine::sign` (and again at `complete`/`verify_share`), aborting the Bitcoin signing session. For a threshold Bitcoin wallet this is a liveness/DoS failure of fund movement, triggered purely by untrusted bytes delivered through `read_preprocess` — the exact impact class (crash via crafted input) as CVE-2020-27819. Panics can also poison larger consensus-adjacent processes that don't isolate the signing call.

### Likelihood Explanation
The attack is cheap and deterministic: the attacker waits for all other preprocesses (or goes last in a simultaneous broadcast, e.g. as coordinator-ordered last), computes the honest partial sum `S`, solves `E = -(S + D)/rho_i` for arbitrary `D`, and broadcasts `(D, E)` — both valid non-identity secp256k1 points that pass `read_preprocess`. Any cosigner can do this; no collusion or special privilege is required. Reachability is through the documented public-input surface (`read_preprocess` → `sign`).

### Recommendation
In `AlgorithmSignMachine::sign` (and/or `AlgorithmSignatureMachine::complete`), check each aggregated `R` for `is_identity()` after `B.nonces(&nonces)` and return `FrostError` identifying/blaming the responsible participant instead of letting the value reach `Hram::hram`. Alternatively, have `x()`/`x_only()` return `Option` and propagate an error. The misleading "negligible probability" comment on `Schnorr` should be corrected — the condition is attacker-determinable, not random.

### Proof of Concept
1. Attacker `i` participates in a `TransactionSignMachine` signing set for a Bitcoin spend.
2. Attacker collects all other participants' preprocesses `(D_l, E_l)` via `read_preprocess`.
3. Attacker reconstructs `rho_transcript` exactly as `sign` does (group key, `hash_msg(msg)`, `hash_commitments` of the transcript over preprocesses), computing their own binding factor `rho_i` and the honest aggregate `S = Σ_{l≠i} (D_l + rho_l·E_l)`.
4. Attacker picks `D_i` as any non-identity point and sets `E_i = -(S + D_i) · rho_i⁻¹`, serializes `(D_i, E_i)` as their `Preprocess` commitments. Both points are non-identity and pass `Secp256k1::read_G`.
5. Each honest signer computes `R = S + (D_i + rho_i·E_i) = infinity`, then `IetfSchnorr::sign_share` → `Hram::hram(&R, …)` → `x(R)` → `expect("point at infinity")` panics, crashing the signer.
