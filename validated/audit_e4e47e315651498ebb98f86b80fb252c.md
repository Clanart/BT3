### Title
Unauthenticated PedPoP ciphertexts can extract ECDH blame keys and decrypt another participant’s share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

**Severity: High.** `KeyMachine::calculate_share` returns an `EncryptionKeyProof` for a ciphertext whose proof-of-possession has only been queued for batch verification, not verified. An invalid decrypted scalar causes an early return containing that proof before the batch verifier can reject the proof-of-possession, allowing a participant to obtain the ECDH key for a copied per-message public key. [1](#0-0) [2](#0-1) 

### Finding Description

`EncryptedMessage::read` accepts an attacker-controlled public key, Schnorr proof-of-possession, and ciphertext. [3](#0-2)  During `Encryption::decrypt`, the PoP is merely queued in `BatchVerifier`; the function then computes `ecdh = msg.key * recipient_secret` and returns an `EncryptionKeyProof` containing that shared point. [2](#0-1) 

`calculate_share` immediately deserializes the decrypted bytes and, if they are not a canonical scalar, returns `InvalidShare` with `Some(blame)`. [4](#0-3)  This bypasses the later `batch.verify_with_vartime_blame()` call that would classify the invalid PoP as `BatchId::Decryption` and suppress the blame proof. [5](#0-4) 

The same ChaCha20 keystream can then be reconstructed from the disclosed ECDH point and public DKG context. [6](#0-5) 

### Impact Explanation

An attacker can copy the per-message public key from another participant’s encrypted share addressed to a victim, submit it in the attacker’s own `EncryptedMessage`, use an invalid PoP, and choose ciphertext bytes that decrypt to a non-canonical scalar. The victim returns a blame proof containing `copied_key * victim_encryption_secret`, which is also the decryption key for the captured legitimate ciphertext. [7](#0-6) [8](#0-7) 

The processor serializes that proof into an `InvalidShare` message, making the ECDH key available beyond the local DKG machine. [9](#0-8)  Repeating the attack against multiple recipients lets an attacker decrypt one sender’s secret-share messages to those recipients and recover that sender’s distributed share material, defeating PedPoP’s share confidentiality boundary.

### Likelihood Explanation

The attack is reachable by an unprivileged DKG participant supplying untrusted `EncryptedMessage` bytes to `calculate_share`. For Ristretto, a random 32-byte decrypted buffer is non-canonical with high probability, so a ciphertext such as all-zero bytes will usually trigger the vulnerable early return; when it does not, the invalid PoP is later rejected without revealing the proof. [10](#0-9) 

### Recommendation

Do not create or expose `EncryptionKeyProof` until the message PoP has been verified. The safest fix is to synchronously verify `msg.pop` before computing `ecdh` or generating the proof in `Encryption::decrypt`. Alternatively, restructure `calculate_share` so all PoP verifications complete successfully before scalar decoding, share verification, or returning any blame proof.

### Proof of Concept

1. Alice sends Bob a legitimate `EncryptedMessage` containing ephemeral public key `X` and ciphertext `C`.
2. Malicious participant Eve submits to Bob an `EncryptedMessage` under Eve’s participant index with:
   - `key = X`;
   - `pop` equal to a canonically encoded but invalid Schnorr signature;
   - `msg` equal to a 32-byte ciphertext that decrypts to a non-canonical scalar, such as zero bytes for Ristretto.
3. Bob calls `calculate_share`; `Encryption::decrypt` queues the invalid PoP, calculates `K = X * bob_secret`, decrypts the supplied ciphertext, and creates an `EncryptionKeyProof` containing `K`. [2](#0-1) 
4. Because the decrypted bytes fail `C::F::from_repr`, `calculate_share` returns `InvalidShare` with `Some(blame)` before checking the queued PoP. [11](#0-10) 
5. Eve reads `K` from the emitted blame proof and applies the same `cipher(context, K)` keystream to Alice’s original ciphertext `C`, recovering Alice’s `SecretShare` intended for Bob. [6](#0-5)

  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
