## Analysis

The reported bug class is a **checks-effects-interactions violation**: a security check is computed against one piece of state, but the actual sensitive effect (asset transfer) is executed later using a *different, unguarded* read of that state, so the two are inconsistent and the guard can be bypassed. Reentrancy itself (calling back into the same contract) doesn't map to an Electron/git app, but the underlying pattern — "the same trust boundary is enforced in one code path but not in the sibling code path that performs the actual sensitive operation" — has a direct analog in the Copilot merge-conflict resolution feature.

`buildConflictContext` (the function that gathers conflicted-file content to send to the AI resolution service) explicitly guards every file read against path/symlink escape: [1](#0-0) 

But the sibling function that actually renders the on-disk diff for the same conflicted files, `getResolutionDiff`, reads the file directly with `Path.join` and no `resolveWithin` check at all: [2](#0-1) 

`resolveWithin` (with its symlink-aware `realpath` check) exists precisely to stop this class of bug and is proven to catch symlink escapes in tests: [3](#0-2) [4](#0-3) 

### Title
Missing path/symlink-escape guard in `getResolutionDiff` allows reading files outside the repository during merge-conflict resolution - (File: `app/src/lib/git/diff.ts`)

### Summary
`getResolutionDiff` is used by the merge-conflict UI/Copilot-resolution flow to render a diff for a conflicted file's "current"/"incoming"/AI-resolved content versus the on-disk working-tree version. Unlike `buildConflictContext`, which validates every conflicted file path with `resolveWithin` before reading it from disk, `getResolutionDiff` builds the on-disk path with a bare `Path.join(repository.path, filePath)` and reads it directly, with no traversal or symlink-escape check.

### Finding Description
The invariant "a conflicted file path must resolve to a location inside the repository working directory" is enforced in `buildConflictContext` [1](#0-0)  but not in `getResolutionDiff`, which is reached from the same merge-conflict UI (`copilot-conflicts-changes.tsx`) for the same set of conflicted paths. Because git's own filename rules do not prevent a tracked path from residing under a tracked *symlinked directory* (a repo can commit a symlink `linked -> /home/user/.ssh` and a file `linked/id_rsa` on a conflicting branch), an attacker who controls a branch/repository the victim merges can cause `repository.path/linked/id_rsa` to resolve, via the symlink, to a file entirely outside the repository. `getResolutionDiff`'s `readFile(Path.join(repository.path, filePath), 'utf8')` will happily read that off-repo target and hand its contents to the diff renderer as `baseContent`.

This mirrors the report's core defect: the same conceptual check ("is this within bounds?") exists but is computed and enforced against one code path while the actual sensitive operation is carried out via a different path that skips it — exactly the kind of check/effect mismatch the report describes, just realized as a path-validation gap instead of a reentrancy guard reset.

### Impact Explanation
A successful escape lets the diff view (and, depending on downstream consumers of `IResolutionDiff`, any UI surface built on it) display the contents of arbitrary files outside the repository that are readable by the Desktop process — e.g. SSH private keys, `.netrc`, or other credential material — merely because the victim merged/checked out a branch containing a symlinked path. This satisfies the "file read outside the repo" and potential "credential exfiltration" impact classes, driven entirely by attacker-controlled repository content (a crafted branch/commit), with no local access or social engineering beyond a normal merge operation.

### Likelihood Explanation
The trigger requires only that the victim have a merge/rebase conflict against a branch that contains a symlinked directory + a conflicting file under it — a scenario fully achievable from a remote/forked branch the attacker controls, and it is directly reachable from the Copilot conflict-resolution dialog which calls `getResolutionDiff` for each conflicted file. The fact that the adjacent, functionally similar `buildConflictContext` already had to add an explicit `resolveWithin` guard (with accompanying symlink tests) indicates the maintainers are aware this exact escape vector is realistic for this feature; `getResolutionDiff` was simply not updated to match.

### Recommendation
Route `getResolutionDiff`'s on-disk path resolution through `resolveWithin(repository.path, filePath)` (the same helper `buildConflictContext` uses), rejecting or safely handling a `null` result (outside-repo / symlink escape) before calling `readFile`, so the same trust-boundary invariant is enforced consistently across every code path that reads conflicted-file content from disk.

### Proof of Concept
1. Attacker publishes a branch that adds a symlink `evil -> ../../../../home/victim/.ssh` (or an absolute-path equivalent reachable via a relative symlink) and a file `evil/id_rsa` with placeholder content, in a way that produces a merge conflict with the victim's local file at the same relative path.
2. Victim fetches the branch in Desktop and starts a merge/rebase, encountering a conflict on `evil/id_rsa`.
3. Victim opens the conflict resolution dialog (e.g. Copilot conflict resolution UI), which calls `getResolutionDiff(repository, 'evil/id_rsa', ...)`.
4. `getResolutionDiff` executes `readFile(Path.join(repository.path, 'evil/id_rsa'), 'utf8')`, which — because `evil` is a symlink pointing outside the repo — actually reads `/home/victim/.ssh/id_rsa` and renders its content in the diff UI, unlike `buildConflictContext`, which would have rejected the same path via `resolveWithin`.

**Note on confidence:** I was not able to fully inspect `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-changes.tsx` in this session to confirm there is no earlier filtering step that discards symlink-escaping paths before calling `getResolutionDiff`; based on the grep results it does call `getResolutionDiff` three times but I could not verify its exact pre-conditions. If a stronger filter exists there, the exploitability would be reduced. If you need certainty on that call site's guard, that file's full contents should be reviewed.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
