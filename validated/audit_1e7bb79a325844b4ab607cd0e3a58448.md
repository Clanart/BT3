### Title
Unvalidated/identity DKG encryption key makes the ECDH shared secret public, exposing encrypted secret shares to any observer - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
In the PedPoP DKG, each participant broadcasts an `EncryptionKeyMessage` containing `enc_key`, which other participants use as the ECDH receiver key when encrypting secret shares (`crypto/dkg/pedpop/src/encryption.rs:466`, `153-154`). `Decryption::register` inserts this attacker-controlled point with no validation: no proof of possession and no rejection of the identity point (`encryption.rs:351-362`). `C::read_G` only enforces canonical encoding, and the identity point is a canonical, valid group element (`crypto/ciphersuite/src/lib.rs:91-101`). A malicious participant (or an observer who obtains the ciphertext) therefore gains a share whose "encryption" uses a publicly computable key.

### Finding Description
`encrypt` computes `cipher(context, ecdh(key, to))` where `to` is the recipient's registered `enc_key` and the ephemeral private `key` is discarded (`encryption.rs:153-154`). If a participant registers `enc_key = identity`, then `ecdh = identity * k = identity` for every message sent to them, so the ChaCha20 key is `transcript(context, identity.to_bytes())` — fully determined by public data (the context and the constant identity encoding). The static IV (`encryption.rs:124-126`) is irrelevant here; the keystream itself is world-computable.

More generally, since there is no proof of possession on `enc_key`, a participant can register any point whose discrete log makes the ECDH result predictable (e.g., identity, or a low-order/torsion point on cofactored ciphersuites such as ed448). Unlike `EncryptedMessage`, which carries a Schnorr PoP to prevent key co-option (`encryption.rs:84-91`), the long-lived registration key has no equivalent check — the exact asymmetric gap the in-code commentary identifies for per-message keys but never applies to registration keys.

### Impact Explanation
Any party who obtains the `EncryptedMessage<C, SecretShare<C::F>>` ciphertext addressed to the malicious participant can recompute `cipher(context, identity)` and recover the secret share plaintext. This leaks a DKG secret share — secret key material — to parties who were never meant to possess it, weakening the threshold: combined with t-1 other shares (or a corrupt participant's own dealings), it enables key/share recovery outside the intended recipient. This is a confidentiality break on threshold key material reachable purely through attacker-chosen public bytes (`enc_key` in the `EncryptionKeyMessage`) fed to `EncryptionKeyMessage::read` → `register` → `encrypt`.

### Likelihood Explanation
The attacker only needs to include the identity encoding as `enc_key` in their round-1 commitments message — an unprivileged public input accepted by `EncryptionKeyMessage::read` and `register` with no checks. Every share subsequently encrypted to them is trivially decryptable. The attack requires seeing the ciphertext, which any relaying/coordinating party or malicious co-participant in a share-forwarding flow can have; within the processor's model (`processor/src/key_gen.rs`), shares transit through the coordinator. Likelihood is bounded by needing ciphertext access and by the share being the attacker's "own" slot (the leaked share belongs to the malicious registrant's index, but its exposure to third parties who shouldn't hold it still breaks the DKG's secrecy assumptions).

### Recommendation
- In `Decryption::register` / `Encryption::register`, reject the identity point and any non-prime-order point for `enc_key`.
- Require a proof of possession for the registration encryption key (e.g., a Schnorr signature over `context || participant || enc_key`, bound by the same `pop_challenge` machinery already used per-message).
- Optionally hash the recipient's claimed `enc_key` into the cipher transcript so a key-substitution cannot silently redirect decryption capability.

### Proof of Concept
1. Malicious participant `M` runs `KeyGenMachine::generate_coefficients`, but crafts their `EncryptionKeyMessage` with `enc_key = C::G::identity()` (valid canonical encoding, passes `C::read_G` and `register`).
2. An honest participant `H` calls `generate_secret_shares`; for `l = M`, `encrypt` computes `ecdh = M.enc_key * k = identity` (`encryption.rs:154`), so `cipher` derives the ChaCha20 key from `transcript("DKG Encryption v0.2" | context | identity_bytes)` with IV `"DKG IV v0.2\0"` — all public constants.
3. Anyone who obtains `EncryptedMessage` for `M` recomputes the same keystream and XORs `msg` to recover `SecretShare<F::Repr>` → the DKG share for index `M`, without knowing any private key.
