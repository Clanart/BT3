## Analysis

This maps directly onto the report's bug class: a governance-settable numeric parameter is missing a non-zero/consistency check, and that missing check causes a downstream division-by-zero / functional breakage — exactly like the `OptionsConfig` min/max and "greater than 0" checks that were missing and caused `getMaxUtilization`/period checks to revert or brick trading.

### Title
Missing non-zero validation on `kip71.gastarget` governance parameter causes division-by-zero panic in KIP-71 base fee calculation - (File: `params/kip71_config.go`, `kaiax/gov/param.go`)

### Summary
The governance parameter `Kip71GasTarget` (`kip71.gastarget`) can be set to `0` through the standard governance voting mechanism because its `FormatChecker` is `noopFormatChecker`, unlike the sibling parameter `Kip71BaseFeeDenominator`, which explicitly rejects zero. A `GasTarget` value of `0` causes an unconditional division by zero in `KIP71Config.NextMagmaBlockBaseFee`, which is called by every node computing/validating the Magma dynamic base fee.

### Finding Description
`Kip71GasTarget`'s parameter definition uses `noopFormatChecker`, which accepts any `uint64` value including `0`: [1](#0-0) 

By contrast, the neighboring `Kip71BaseFeeDenominator` parameter explicitly guards against a zero value (`return ok && v != 0`), and `NextMagmaBlockBaseFee` itself falls back to a hardcoded `64` when `BaseFeeDenominator == 0` "to avoid panic": [2](#0-1) [3](#0-2) 

No equivalent guard exists for `GasTarget`. When a vote sets `kip71.gastarget` to `0`, `headergov`'s `checkConsistency` performs no special validation for it — it falls into the generic "no more checks" case: [4](#0-3) 

Once `GasTarget == 0` is active, every call to `NextMagmaBlockBaseFee` with any non-zero `parentGasUsed` (i.e., essentially every real block) takes the `parentGasUsed > gasTarget` (or `<`) branch and divides by `gasTarget`: [5](#0-4) 

`x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0` panics (division by zero) in Go's `big.Int.Div`.

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked both by block producers computing the next base fee and by every validating node in `VerifyMagmaHeader` during block validation: [6](#0-5) 

Once the governance change activates, all nodes on the network panic when processing the very next block with nonzero gas usage — this is a chain-halting, network-wide denial of service directly analogous to the reported bug's "not possible to initiate new trades" outcome, but at the consensus/base-fee layer instead of an options market.

### Likelihood Explanation
Setting governance parameters requires a governance vote (via `headergov` or `contractgov`), so this requires governing-node/council-level access rather than an arbitrary unprivileged transaction. This falls squarely within the explicitly allowed "governance parameters" analog category. Because the format checker performs no validation and the value flows straight from vote to consensus-critical arithmetic, a single mistaken or malicious vote is sufficient to trigger the crash for the entire network — there is no additional condition needed beyond the parameter being activated and a block containing any gas usage being processed.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check), and add a defensive fallback (or explicit rejection) inside `NextMagmaBlockBaseFee` similar to the existing `BaseFeeDenominator == 0` guard, so that `gasTarget == 0` cannot reach the `Div` calls.

### Proof of Concept
1. A governing/council node submits a governance vote setting `kip71.gastarget` to `0` via `headerGovAPI.Vote("kip71.gastarget", 0)`; this passes `NewVoteData`'s format check (`noopFormatChecker`) and `checkConsistency` (no special-case handling for this parameter). [4](#0-3) 
2. The vote is included and activates at the governance epoch boundary; `GetParamSet` now returns `GasTarget = 0`, which is converted via `ToKip71Config()`: [7](#0-6) 
3. On the next block where `parentHeaderGasUsed != 0` (virtually guaranteed), every node calling `NextMagmaBlockBaseFee` (both proposer computing the base fee and validators verifying it) executes `x.Div(x, new(big.Int).SetUint64(0))`, which panics. [8](#0-7) 
4. All nodes on the network crash/halt when processing this block, producing a full chain outage from a single governance vote.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
