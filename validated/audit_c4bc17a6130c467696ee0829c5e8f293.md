### Title
IBC ERC20-conversion middleware can trigger an error acknowledgement *after* the underlying ICS20 transfer has already committed the mint/unescrow, causing duplicated (double-spent) cross-chain value - (File: `x/erc20/ibc_middleware.go`, `x/erc20/keeper/ibc_callbacks.go`)

### Summary
This is the Cosmos EVM analog of the TOFT `multiHopSellCollateral()` bug class: a cross-chain flow performs an irreversible state change on the destination chain and *then* executes a second, separately-fallible step whose failure is reported back to the source chain as if nothing had happened on the destination — causing funds to be duplicated/locked rather than atomically reverted or completed.

### Finding Description
The ERC20 IBC middleware (`x/erc20/ibc_middleware.go`) wraps the standard ICS20 transfer `OnRecvPacket` call with an additional ERC20-conversion/registration step: [1](#0-0) 

`im.Module.OnRecvPacket(ctx, ...)` is the underlying ICS20 transfer app, which — using the **same, non-cached `sdk.Context`** — mints new voucher coins or unescrows previously-escrowed native coins to the recipient's bank balance as soon as it returns success. Only *after* that state change is committed does the erc20 keeper's own `OnRecvPacket` run: [2](#0-1) 

If this subsequent step fails — e.g. `RegisterERC20Extension` (Case 1, brand-new IBC denom) at [3](#0-2)  or `MintingEnabled`/`ConvertCoinNativeERC20` (Case 2, native-ERC20 round trip) at [4](#0-3)  — the middleware returns `channeltypes.NewErrorAcknowledgement(err)`. That error acknowledgement propagates up as the *final* acknowledgement for the packet.

Critically, nothing rolls back the bank mint/unescrow that `im.Module.OnRecvPacket` already performed on the receiving chain's `ctx`, because — unlike the sibling `x/ibc/callbacks` module, which explicitly wraps EVM callback execution in `ctx.CacheContext()`/`writeFn()` so that failures roll back state (see the documented invariant "the recv packet application state changes are reverted and an error acknowledgement is returned") — the erc20 auto-conversion middleware performs no such caching: [5](#0-4) [6](#0-5) 

Meanwhile, an error acknowledgement written on the receiving chain causes the **sending chain** to run its own `OnAcknowledgementPacket`, which refunds the original sender (re-mints/unescrows on the source side): [7](#0-6) 

The net effect:
- Case 1 (new IBC denom): the receiving chain's recipient already holds newly-minted voucher coins that were credited by the underlying transfer app, while the source chain independently refunds the sender the same amount — creating value that exists in two places from a single transfer (duplication/unauthorized minting of spendable value).
- Case 2 (returning native-ERC20 token): the receiving chain releases real escrowed value to the recipient (a legitimate unescrow), but the source chain (the last hop that sent this specific packet) also refunds its own sender by re-minting/re-crediting a voucher — leaving the source-chain voucher unbacked by any remaining escrow, an insolvency/duplication of claims on the same underlying collateral.

### Impact Explanation
This breaks the fundamental 1:1 accounting invariant between native coins, IBC escrows and ERC20 representations that the erc20/ibc-callbacks modules are supposed to preserve. An unprivileged relayer/user simply needs to cause the ERC20 registration or conversion step to fail after a legitimate IBC transfer is received (e.g. a token pair name/metadata collision, disabled precompile registration path, or any keeper-level error in `CreateNewTokenPair`/`EnableDynamicPrecompile`/`ConvertCoinNativeERC20`) to produce duplicated spendable value across two chains — a Critical unauthorized-duplication/accounting-corruption impact.

### Likelihood Explanation
Likelihood depends on the practical reachability of a failure in `RegisterERC20Extension` or `ConvertCoinNativeERC20` for an otherwise-successful ICS20 receive. I was not able to fully enumerate every failure branch of `CreateNewTokenPair`/`EnableDynamicPrecompile`/`ConvertCoinNativeERC20` within the available context (index truncation), so I cannot confirm a concrete unprivileged trigger (e.g., a denom/metadata collision, a disabled `EnableErc20` param toggled mid-flight, or an EVM-level revert in `approve`/`mint`) with full certainty. The architecture itself, however, demonstrably lacks the same cache/rollback protection that the neighboring `x/ibc/callbacks` module explicitly implements for the identical class of "do a real transfer, then a second fallible step" problem, which strongly suggests this is a genuine gap rather than a deliberately-accepted design tradeoff.

### Recommendation
Wrap the entire receive-and-convert sequence in `x/erc20/ibc_middleware.go`'s `OnRecvPacket` (and the v2 variant) in a `ctx.CacheContext()`, calling both `im.Module.OnRecvPacket` and `k.keeper.OnRecvPacket` against the cached context, and only invoke `writeFn()` if the final acknowledgement is successful. If the ERC20 conversion/registration step fails, the entire packet-receive state change (mint/unescrow to the recipient) must be discarded before returning the error acknowledgement, mirroring the pattern already used in `x/ibc/callbacks/keeper/keeper.go`.

### Proof of Concept
Conceptual reproduction (exact failing precondition for `RegisterERC20Extension`/`ConvertCoinNativeERC20` not fully verified against all code paths due to index limits):
1. A user initiates a legitimate ICS20 transfer of a new denom (or a returning native-ERC20 denom) to the Cosmos EVM chain.
2. Core IBC executes `IBCMiddleware.OnRecvPacket`, which calls the underlying transfer app's `OnRecvPacket` — crediting/unescrowing the coin to the recipient's bank balance on `ctx`. [8](#0-7) 
3. The erc20 keeper's `OnRecvPacket` then attempts `RegisterERC20Extension`/`ConvertCoinNativeERC20`, which fails for any keeper-level reason, returning an error acknowledgement. [9](#0-8) 
4. The bank credit from step 2 is never reverted (no cached context/writeFn), so the recipient keeps the coins.
5. The error acknowledgement is relayed to the sending chain, which independently refunds the original sender via `OnAcknowledgementPacket`.
6. Both the recipient (destination chain) and the sender (refunded on source chain) now hold spendable value derived from a single transfer — duplicating value / leaving an unbacked voucher, depending on the case.

I recommend a Devin session start a full trace of `CreateNewTokenPair`, `EnableDynamicPrecompile`, and `ConvertCoinNativeERC20` failure paths, plus verification of how `ChannelKeeper.WriteAcknowledgement` consumes the returned acknowledgement, to conclusively confirm an unprivileged, deterministic trigger before filing this as a final report.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
