### Title
MuSig key list accepts the identity point, letting a listed "signer" bypass private-key possession and produce valid FROST shares - (File: crypto/dkg/musig/src/lib.rs)

### Summary
The external report concerns an allowlist/verification check that fails to reject an unauthorized party (Gate One's origins check). The Serai analog is `check_keys` in `crypto/dkg/musig/src/lib.rs`: it validates the signer key list for emptiness, length, and duplicates, but never rejects the identity point. Because `C::read_G` (the base `Ciphersuite` reader, distinct from `Curve::read_G` which does reject identity at crypto/frost/src/curve/mod.rs:125-131) can supply the identity, an attacker can register `identity` as their public key. They then occupy a slot in the n-of-n MuSig key set — the analog of the "origins list" — while controlling no secret, and can still emit fully valid FROST signature shares for that index.

### Finding Description
`check_keys` only checks `keys.is_empty()`, `u16::try_from(keys.len())`, and duplicate `to_bytes` (crypto/dkg/musig/src/lib.rs:46-63). There is no `key.is_identity()` rejection and no subgroup/DL possession check. `musig_key_multiexp` then computes `group_key = Σ ρ_i·K_i` (lines 87-98); an identity `K_i` contributes `ρ_i·0 = 0`, so the group key is computed normally. `musig` (lines 116-162) inserts each key verbatim into `verification_shares`, so the identity-keyed participant's verification share is the identity point.

During FROST signing (`crypto/frost/src/sign.rs` and `crypto/frost/src/algorithm.rs:219-230`), share verification checks `R_l + c·Y_l − s_l·G = 0`. With `Y_l = identity`, the `c·Y_l` term vanishes, so a share `s_l = d_l + e_l·ρ_l` — computable purely from public binding factors and self-chosen nonce commitments — verifies with no secret key. The slot's "authorization" implied by the keys list is therefore bypassed: anyone can act as that participant index.

### Impact Explanation
The MuSig keys list is the authorization roster for the aggregated group key (in validator-sets usage, the signer set that authorizes set-key/slash messages). An attacker who injects an identity key into the roster obtains a signer slot that requires no secret, weakening the effective security of the n-of-n: that index's signature share can be produced by anyone, defeating the purpose of listing that party as a required signer. This is a forged-participation / verification-bypass of the key-possession check implicit in key aggregation.

### Likelihood Explanation
Exploitation requires the attacker's identity key to be present in the `keys` list supplied to `musig`/`musig_key` — i.e., they must be able to register a key into the signer set, which is exactly the public-input surface this class covers (keys are attacker-supplied `C::G` bytes read via `C::read_G`, which does not enforce non-identity). Wherever key registration is permissionless or the list is assembled from untrusted registrations, the attack is straightforward; where a trusted party curates the list it is not reachable.

### Recommendation
In `check_keys`, reject `key.is_identity()` (and ideally require non-torsion/canonical keys per the ciphersuite's guarantees) before building the binding-factor transcript, matching the identity rejection already performed by `Curve::read_G` in crypto/frost/src/curve/mod.rs:125-131.

### Proof of Concept
```rust
// In-scope crates: crypto/dkg/musig, crypto/frost
// Setup: legitimate keys K1..K_{n-1}; attacker appends K_n = identity
let keys = vec![k1, k2, C::G::identity()];

// check_keys passes: no duplicates, non-empty, len <= u16::MAX
let group_key = musig_key::<C>(context, &keys).unwrap();
// group_key = Σ rho_i * K_i; the identity term contributes 0

// Attacker instantiates their "share" with secret 0:
// our_pub_key = G * 0 = identity, found at index n
let keys_n = musig::<C>(context, Zeroizing::new(C::F::ZERO), &keys).unwrap();

// In AlgorithmSignMachine::sign (crypto/frost/src/sign.rs), the attacker
// publishes normal preprocess commitments (D_l, E_l). Their share:
//   s_l = d_l + e_l * rho_l + c * secret_share(=0)
// verifies since verify_share checks R_l + c*Y_l - s_l*G == 0
// and Y_l = identity makes c*Y_l vanish — no private key was ever needed.
```

Caveat: I verified `check_keys`, `musig_key_multiexp`, `musig`, and the share-verification formula, but could not re-confirm within the iteration budget whether every in-scope `Ciphersuite::read_G` implementation admits the identity encoding (e.g., `dalek-ff-group`/`kp256` read paths) — the finding depends on the identity point being expressible as a `C::G`, which holds for the API surface regardless of encoding strictness since callers can construct `C::G::identity()` or supply its encoding where accepted.
