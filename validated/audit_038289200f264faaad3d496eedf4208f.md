### Title
Unbounded attacker-controlled allocation in `EncryptedMessage::read` enables remote memory exhaustion - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`EncryptedMessage::read` in `crypto/dkg/pedpop/src/encryption.rs` deserializes the encrypted DKG share payload by reading a length prefix from the input stream and immediately allocating a `Vec` of that size (`vec![0; usize::try_from(u32::from_le_bytes(len))]`-style allocation) before the bytes are actually read or validated. This is a direct analog of CVE-2019-19070: a memory-consumption denial of service triggered purely by declaring a large length in untrusted input. Unlike the kernel CVE (which required the system to already be near OOM), this variant needs nothing pre-existing — the sender alone controls the allocation size, up to ~4 GiB per message.

### Finding Description
Within the in-scope PedPoP DKG flow, participants exchange `EncryptedMessage` payloads whose bytes are deserialized via `EncryptedMessage::read`. The reader parses a `u32` length field and allocates a buffer of that declared length with no bound check against a maximum message size and no chunked/incremental reading. A malicious or even merely faulty DKG participant (or any party able to feed bytes to `EncryptedMessage::read`, which the threat model explicitly permits as untrusted input) can send a 4-byte header claiming a multi-gigabyte body. The host allocates the full declared amount before `read_exact` discovers the stream is short — so a tiny crafted message forces a giant allocation. Repeated messages can compound the exhaustion. The codebase itself acknowledges this bug class elsewhere: `networks/ethereum/src/machine.rs:51-60` explicitly comments "A valid DoS would be to claim a 4 GB data is present for only 4 bytes" and reads in 1 KB chunks to bound the damage — the PedPoP reader applies no such mitigation.

### Impact Explanation
Memory exhaustion / denial of service against any node processing DKG traffic. A stalled DKG blocks key generation for a validator set; if hit during resharing or rotation it can halt multisig availability, delaying or preventing signing of Bitcoin transactions.

### Likelihood Explanation
The attacker only needs to deliver bytes to `EncryptedMessage::read` — one of the explicitly in-scope untrusted-input surfaces. No signature validity, threshold collusion, or honest-party cooperation is required; the allocation happens before any cryptographic verification of the ciphertext. Exploitation cost is a handful of bytes per gigabyte forced.

### Recommendation
Cap the declared length before allocating (e.g., reject lengths exceeding the maximum legitimate serialized `EncryptedMessage` size for the known participant count), or adopt the chunked-read pattern already used in `Call::read` at `networks/ethereum/src/machine.rs:53-60` so allocation is bounded by bytes actually present.

### Proof of Concept
```rust
// A peer (or any party able to feed bytes to EncryptedMessage::read) sends:
let mut malicious = vec![];
malicious.extend(u32::MAX.to_le_bytes()); // declared ciphertext length ~4 GiB
malicious.extend([0u8; 8]);               // negligible actual body
// EncryptedMessage::read(&mut malicious.as_slice()) allocates ~4 GiB
// before read_exact fails on the short stream. Repeat to exhaust memory.
```
