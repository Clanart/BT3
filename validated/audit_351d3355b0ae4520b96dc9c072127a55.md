### Title
SignableTransaction omits the OP_RETURN data output from weight/vbytes, so the enforced fee and size checks don't match the signed transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes the caller-supplied `data` OP_RETURN output onto `tx_outs`, but then estimates the transaction weight and virtual size via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which builds its dummy transaction only from `payments` (plus optional change). The OP_RETURN output is invisible to the estimate, so `needed_fee`, the `TooLowFee` minimum-relay-fee check, the dust-margin change check, and the `TooLargeTransaction` check are all evaluated against a transaction smaller than the one actually signed and broadcast.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:193-202`, an OP_RETURN `TxOut` (up to 80 bytes of data + ~3-10 bytes overhead) is appended to `tx_outs`. Then:

- Line 204: `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` — uses `payments`, not `tx_outs`, so `vbytes` excludes the data output.
- Line 206: `needed_fee = fee_per_vbyte * vbytes` — underestimates the fee for the achieved rate.
- Line 211: the `TooLowFee` check compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` — passes for a tx whose real size is larger.
- Lines 224-235: `calculate_weight_vbytes(..., payments, Some(&change))` again omits the data output, so `fee_with_change` is underestimated and change is over-credited (`change = input_sat - payment_sat - fee_with_change`).
- Line 241: `weight > MAX_STANDARD_TX_WEIGHT` uses the weight that excludes the data output.

The result: the constructed `tx` (which does include the OP_RETURN output at line 250) is signed with `actual_fee = needed_fee` fixed, giving an actual fee rate strictly below `fee_per_vbyte`, and potentially below the relay minimum — and in edge cases a real weight exceeding `MAX_STANDARD_TX_WEIGHT` despite the check passing.

### Impact Explanation
An unprivileged caller controls `data` (checked only to be ≤ 80 bytes) and `fee_per_vbyte`. Two reachable outcomes:

1. **Fee-rate violation**: the signed transaction pays `needed_fee` computed for a smaller tx; its true sat/vbyte is lower than requested and can fall under `DEFAULT_MIN_RELAY_TX_FEE`, producing a transaction Bitcoin nodes will not relay — funds are committed to an unpropagating/unspendable state until resigned.
2. **Standardness bypass**: when `payments` + inputs + change are already near `MAX_STANDARD_TX_WEIGHT`, adding the uncounted OP_RETURN output pushes the real weight past the limit while `TooLargeTransaction` never fires, yielding a non-standard transaction the multisig signs believing it is valid.

This is the same bug class as the reference report: a pre-flight check (`needed_fee`, `TooLowFee`, `TooLargeTransaction`, change sufficiency) is computed from quantities that omit a deduction/output the final object actually includes, so the check passes while the executed result differs.

### Likelihood Explanation
Requires only that a transaction be constructed with `data.is_some()` — a public input path (OP_RETURN data is explicitly supported, capped at 80 bytes). The fee discrepancy occurs deterministically on every such transaction; the non-standard-weight outcome additionally requires being within ~90 bytes of the weight cap, which is rare but does occur when batching many inputs/outputs (the code supports up to ~520 of each).

### Recommendation
Pass the fully-assembled output list (or at least `payments` + the OP_RETURN `TxOut`) into `calculate_weight_vbytes`, e.g. change its signature to take `&[TxOut]` built from `tx_outs`, so `needed_fee`, `fee_with_change`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all account for the data output. Alternatively, move the data-output append after the fee computation and add its serialized size to `vbytes`/`weight` manually.
