## Analysis

Reducing the Aerodrome report to its core primitive: a value-accounting step trusts a **raw, unauthenticated `balanceOf`/reserve read on a shared contract** as ground truth, rather than a delta strictly attributable to the current operation. Anyone who can push tokens into that shared contract before the read can inflate the accounted value for free.

The local analog is `IntentGatewayV2.placeOrder`'s predispatch-swap accounting, which sweeps and prices tokens based on the **total balance of the shared `_params.dispatcher` (`CallDispatcher`)**, not a delta strictly tied to the caller's own predispatch swap. [1](#0-0) 

### Title
Shared `CallDispatcher` balance used as accounting ground truth in `placeOrder` predispatch flow — donation/residue inflates escrowed order value - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`_params.dispatcher` is a single, protocol-wide `CallDispatcher` instance [2](#0-1)  reused by every `placeOrder` call that uses the predispatch swap path. During that path, the gateway reads `IERC20(token).balanceOf(dispatcher)` / `dispatcher.balance` as the amount available to sweep into escrow, rather than measuring only what the just-executed `order.predispatch.call` produced: [3](#0-2) 

### Finding Description
`CallDispatcher.dispatch` is a generic call forwarder with no access control on `to`/`data` and no restriction on who can trigger it [4](#0-3) . It also has a bare `receive()` [5](#0-4) , so any address can push ETH/ERC-20 into it at any time, outside of any `placeOrder` transaction.

In `placeOrder`, the balance-check-then-sweep sequence:
1. Computes `balance = IERC20(token).balanceOf(dispatcher)` (or `dispatcher.balance` for native) — the *entire* current balance of the shared contract, not a delta scoped to this call.
2. Only requires `balance >= requiredAmount` [6](#0-5) .
3. Sweeps the *whole* balance out via a `transfer(this, balance)` call routed back through `dispatcher.dispatch(...)` [7](#0-6) .
4. Measures `received = balanceOf(this) - balancesBefore[i]` and, crucially, when `received > order.inputs[i].amount` the **excess is silently treated as dust and order.inputs[i].amount is left unchanged**, while when `received` is smaller the order amount is reduced to the actual figure [8](#0-7) .

Because the check and the sweep operate on the dispatcher's *raw balance* rather than a value strictly attributable to `order.predispatch.call`'s own effect, any token balance already resident in the shared `dispatcher` at call time (from a stray/failed prior partial flow, a direct donation transfer, or any other interaction that leaves a token balance behind on that well-known address) is silently absorbed into whichever `placeOrder` call happens to run next and race the sweep. The requiredAmount check does not verify provenance of the swept funds — it only asserts a floor, exactly mirroring the Aerodrome bug's core defect: reserves/balances are trusted as accounting inputs without verifying they were legitimately produced by the operation being priced.

This differs from the Aerodrome case in that a **single** `placeOrder` call is atomic and typically only the caller's own predispatch swap funds the dispatcher moments before the sweep — so in the common case an attacker is "donating" only to their own order (no protocol harm). The exploitable edge is the shared, persistent, permissionless nature of the `dispatcher` address: it is not scoped per-order or per-caller, so **any residual balance left in it by any other actor's interaction (successful or not) is up for grabs by the next caller's sweep, with no ownership check tying the swept balance back to that caller's own predispatch inputs.**

### Impact Explanation
If any token balance is ever resident at the shared `dispatcher` address between transactions (e.g., an operator error, a partially-completed governance/migration flow, a user or third party mistakenly sending tokens to the well-known `dispatcher` address, or dust left by an edge case in another code path that touches `dispatcher`), the **next arbitrary caller's `placeOrder` predispatch sweep silently captures it**, crediting it toward that caller's own order inputs or, above the requested amount, redirecting it to protocol dust — in either case diverting funds away from their rightful owner without their consent. This is a fund-diversion / wrong-beneficiary primitive matching the bounty's "false state acceptance" / "wrong beneficiary or amount" categories, reachable by any unprivileged `placeOrder` caller with no special role.

### Likelihood Explanation
Likelihood is **conditional but non-trivial**: it requires the shared `dispatcher` to be holding a stray balance at the moment some other unrelated `placeOrder` sweep runs. Given `dispatcher` is a single fixed, publicly-known address reused for the entire IntentGatewayV2 deployment (not ephemeral per order), and `receive()`/arbitrary `dispatch()` calls make it trivial for anyone to send tokens to it, the precondition ("dispatcher holds a nonzero balance for a given token right before someone else's predispatch sweep") is directly attacker-inducible: an attacker can send dust to `dispatcher`, then immediately front-run/race their own no-op-swap `placeOrder` transaction to claim it, or — if any other legitimate flow briefly parks funds there — race that window. This is a public-entrypoint, unprivileged-attacker path with no dependency on a malicious relayer, prover, or admin.

### Recommendation
Replace the "read total balance of `dispatcher`" pattern with a strict delta measured only around the specific `order.predispatch.call` execution: snapshot `balanceOf(dispatcher)` immediately before invoking `dispatch(order.predispatch.call)` and require the *sweep amount* to equal `balanceOf(dispatcher) - preCallBalance` (clamped to the actual amount produced), rejecting/reverting on any balance already present before the predispatch call runs, or explicitly sweeping only the newly-added portion rather than the full current balance. Alternatively, use a fresh, single-use/ephemeral dispatcher (e.g., a minimal proxy deployed per-order via `CREATE2` and self-destructed/never reused) so no other flow can ever leave residual balance for a subsequent unrelated caller to inherit.

### Proof of Concept
1. Attacker (or anyone) sends `X` tokens of `TOKEN_A` directly to the known `_params.dispatcher` address via a plain `IERC20.transfer`, outside of any `placeOrder` call — this succeeds because `CallDispatcher` has no restriction on incoming transfers.
2. Separately, another user (Victim) submits a `placeOrder` with a predispatch swap for `TOKEN_A` whose real swap only produces `Y < requiredAmount` of `TOKEN_A` at the dispatcher.
3. Because the check at [9](#0-8)  reads `balanceOf(dispatcher)` (which now equals `X + Y`, satisfying `balance >= requiredAmount` even though the user's own swap under-delivered), the order proceeds and sweeps `X + Y` into escrow, crediting Victim's order with tokens `X` never actually attributable to Victim's own predispatch call.
4. Depending on timing/race, the beneficiary of the swept `X` can be manipulated: an attacker who front-runs their own low-value predispatch call after donating `X` captures `X` toward their own order for free, or a completely unrelated actor's donated dust gets silently absorbed into whichever `placeOrder` call races the sweep next — in both cases the balance-based accounting fails to verify provenance, mirroring the Aerodrome `sync()` donation bug's "trust the raw balance, not what this operation actually produced" root cause.

*Note: full exploitation economics (net attacker profit vs. gas/predispatch cost) and whether any other code path realistically leaves the shared `dispatcher` with a non-zero balance between transactions could not be fully confirmed from the available indexed code — this would need direct testing against a deployed instance to establish concrete conditions under which stray balance accumulates at `dispatcher` outside of a single atomic `placeOrder` call.*

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
