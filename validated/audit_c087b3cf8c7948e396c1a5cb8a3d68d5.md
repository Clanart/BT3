### Title
Swapped old/new line-number arguments in `formatHunkHeader()` call inside `formatPatchToDiscardChanges()` corrupts "Discard Changes" patch hunk headers - (File: app/src/lib/patch-formatter.ts)

### Summary
`formatHunkHeader()` is defined with the parameter order `(oldStartLine, oldLineCount, newStartLine, newLineCount, sectionHeading?)` [1](#0-0) . Every correct call site passes the arguments in that exact order — e.g. `formatPatch()` calls it as `formatHunkHeader(hunk.header.oldStartLine, oldCount, hunk.header.newStartLine, newCount)` [2](#0-1) . However, `formatPatchToDiscardChanges()` — the function that builds the reverse patch used to discard the user's local changes — calls the same function with the old/new pair swapped: `formatHunkHeader(hunk.header.newStartLine, newCount, hunk.header.oldStartLine, oldCount)` [3](#0-2) . This is the exact bug class from H-18: two same-typed value pairs transposed at a call site relative to the callee's declared signature.

### Finding Description
`formatHunkHeader()` builds the `@@ -oldStart,oldCount +newStart,newCount @@` header for a unified diff hunk, which `git apply` uses to locate and validate the region of the file being patched [4](#0-3) .

In `formatPatchToDiscardChanges()`, the body of the hunk is built by *inverting* each selected line (an `Add` becomes a `-` line and increments `newCount`; a `Delete` becomes a `+` line and increments `oldCount`) so the resulting patch, when applied, reverses the change [5](#0-4) . This inversion is intentional and correct for the hunk *body*. But the header line at the end of the loop should still describe the *actual* pre-image (working directory) and post-image (discarded state) using the tracked `oldCount`/`newCount` in the same `(old, new)` order that `formatHunkHeader` expects. Instead the call swaps which SHA-adjacent tracked count/start goes into which parameter slot: `hunk.header.newStartLine`/`newCount` are passed into the `oldStartLine`/`oldLineCount` parameters, and `hunk.header.oldStartLine`/`oldCount` into the `newStartLine`/`newLineCount` parameters [3](#0-2) .

This mirrors H-18 precisely: `MarketUtils.updateTotalBorrowing` expected `(prevSizeInUsd, prevBorrowingFactor, ...)` but `PositionUtils.sol` passed `(borrowingFactor(), sizeInUsd(), ...)` — two positionally-similar values transposed against the callee's declared order, producing internally inconsistent state without any type system or runtime check catching it (both are `uint256`/`number`, so no compiler error is possible).

The resulting malformed patch is fed directly to `git apply` via `discardChangesFromSelection()` [6](#0-5) , which is the exact same sink used by the "Discard changes" / "Discard selected changes" UI feature.

### Impact Explanation
This corrupts the artifact of a core user-invoked write action: discarding (partially or fully) local changes to a file. A mismatched `@@ -l,s +l,s @@` line-count header can cause `git apply` to:
- Reject the patch outright (denial of the discard action, less severe), or
- With `--unidiff-zero` (0-context hunks are permitted here, see `args` in `discardChangesFromSelection`) apply the hunk using the wrong length/starting-line accounting, silently discarding the wrong lines, leaving unintended content in the working tree, or corrupting the file beyond what the user selected.

Because "discard changes" is destructive and typically has no diff-preview per invocation of the internal patch, a corrupted result is silently written back to the user's working directory — matching the "silent corruption of what the user commits" impact class from the seed report, since discarded/kept lines feed directly into what is subsequently staged and committed.

### Likelihood Explanation
This code path executes on every "Discard changes" or "Discard selected lines" action for a `Modified`/`Conflicted` text file with more than one hunk or with counts that differ between old/new (e.g. any hunk containing a mix of additions and deletions) — a very common, everyday Desktop operation, not requiring any attacker interaction beyond producing a file with such a diff (which any cloned/fetched repository's working tree naturally contains). No privileged access or unusual steps are needed; it is triggered by ordinary UI use once a repository with mixed-count hunks is opened.

### Recommendation
Fix the call to `formatHunkHeader()` inside `formatPatchToDiscardChanges()` so the arguments align with the declared parameter order, matching the correct call in `formatPatch()`:
```ts
patch += formatHunkHeader(
  hunk.header.oldStartLine,
  oldCount,
  hunk.header.newStartLine,
  newCount
)
```
at [3](#0-2) .

### Proof of Concept
1. Open a repository containing a tracked file with a hunk that has an unequal number of additions and deletions (e.g. delete 3 lines, add 1 line) so that `oldCount !== newCount` and `hunk.header.oldStartLine !== hunk.header.newStartLine`.
2. In Desktop's Changes view, select only some of the lines in that hunk and invoke "Discard changes" (routes through `discard-changes-dialog.tsx` → `discardChangesFromSelection` → `formatPatchToDiscardChanges` → `git apply`) [7](#0-6) .
3. Because the generated hunk header reports `@@ -newStart,newCount +oldStart,oldCount @@` instead of `@@ -oldStart,oldCount +newStart,newCount @@`, `git apply` either fails validation (visible as an unexplained discard failure) or, under `--unidiff-zero`'s relaxed context checking, applies the reversal patch against the wrong line range/length, leaving the working copy in a state that does not match what the user intended to discard/keep — demonstrable by diffing the file content before and after the discard action and comparing to the expected result from manually reverting the selected lines.

function formatHunkHeader(
  oldStartLine: number,
  oldLineCount: number,
  newStartLine: number,
  newLineCount: number,
  sectionHeading?: string | null
) {
  // > @@ -l,s +l,s @@ optional section heading
  // >
  // > The hunk range information contains two hunk ranges. The range for the hunk of the original
  // > file is preceded by a minus symbol, and the range for the new file is preceded by a plus
  // > symbol. Each hunk range is of the format l,s where l is the starting line number and s is
  // > the number of lines the change hunk applies to for each respective file.
  // >
  // > In many versions of GNU diff, each range can omit the comma and trailing value s,
  // > in which case s defaults to 1
  const lineInfoBefore =
    oldLineCount === 1 ? `${oldStartLine}` : `${oldStartLine},${oldLineCount}`

  const lineInfoAfter =
    newLineCount === 1 ? `${newStartLine}` : `${newStartLine},${newLineCount}`

  sectionHeading = sectionHeading ? ` ${sectionHeading}` : ''

  return `@@ -${lineInfoBefore} +${lineInfoAfter} @@${sectionHeading}\n`
}

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
