### Title
Unbounded recursion when parsing nested `MofN` custody memos crashes wallet/pool clients — ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs an on-chain custody puzzle structure from an untrusted `memo`/hint `Program` attached to a coin. When the memo encodes an `MofN` component, the method recurses into itself once per member, with no limit on nesting depth. A coin creator fully controls the memo bytes attached to any coin they create, so they can craft a coin whose memo encodes a deeply nested chain of `MofN` wrappers. Any wallet or pool-related client code that calls `from_memo()` on that coin's memo will recurse until the Python interpreter's recursion limit is hit (`RecursionError`), which is the same "no folder/level count validation causes uncontrolled recursion depth" bug class as the reported `node-tar` DoS.

### Finding Description
`PuzzleWithRestrictions.from_memo()` is the "sync unknown custody puzzle from chain" contract: [1](#0-0) 

Key issue: when `further_branching` is true (i.e., the memo declares an `MofN` node), the code does:
```python
m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
puzzle: MIPSComponent = MofN(
    m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
)
```
each element of `member_memos` is itself parsed recursively via `PuzzleWithRestrictions.from_memo`, with `MofNHint.from_program` allowing an arbitrary list of nested member memos (`member_memos=list(member_memos.as_iter())`): [2](#0-1) 

There is no check on nesting depth, number of members, or total structure size before recursing. This mirrors the reported `node-tar` issue: parsing untrusted nested structure with no bound on recursion depth.

This function is reachable from at least one concrete production call site: `PlotNFT.get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` directly on the memo of a `CREATE_COIN` condition parsed out of a coin spend's puzzle/solution, in order to reconstruct plotNFT state when it cannot otherwise recognize the puzzle: [3](#0-2) 

`memo_blob` originates from a `CreateCoin` condition emitted by an arbitrary singleton inner-puzzle spend — content fully controlled by whoever creates that spend/coin. A plotnft-tracking wallet/pool client that walks singleton lineage and calls `get_next_from_coin_spend()` on an attacker-crafted spend with a deeply nested `MofN` memo will trigger unbounded Python recursion.

Separately, `PuzzleWithRestrictions.unknown_puzzles` (used by general wallet custody-puzzle recognition to discover puzzle hashes it needs to fill in) recurses over `self.puzzle.members` with the same unbounded depth once a `PuzzleWithRestrictions` object has been constructed via `from_memo()`: [4](#0-3) 

### Impact Explanation
A wallet/pool client processing a coin (via plotNFT lineage tracking, or any future consumer of `PuzzleWithRestrictions.from_memo()`/`unknown_puzzles` for CHIP-0043 custody puzzle recognition) can be made to raise a Python `RecursionError` by an attacker who creates a coin with a maliciously deep `MofN` memo nesting. Depending on how the exception propagates, this can crash or hang the wallet sync/plotNFT tracking task, denying service to the local wallet/pool user processing that coin — a transaction/coin-processing halt triggered by attacker-supplied data, consistent with CWE-400 resource exhaustion via unbounded recursion.

### Likelihood Explanation
Likelihood is moderate: the vulnerable path is currently reachable through `PlotNFT.get_next_from_coin_spend()`, which is exercised when reconstructing plotNFT/pool state from chain data and can be fed an arbitrary attacker-controlled coin spend's `CREATE_COIN` memo. An attacker only needs to create a coin (a normal, unprivileged action) with a crafted memo to trigger the deep-recursion parse path in any client that calls this code on that coin.

### Recommendation
Add an explicit maximum recursion/nesting depth (and a maximum total member count) check in `PuzzleWithRestrictions.from_memo()` and `MofNHint.from_program()`, raising a `ValueError` early instead of recursing arbitrarily deep. Alternatively, convert the recursive descent into an iterative, explicit-stack implementation (as already done for `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py`) so that deeply nested but otherwise well-formed memos cannot exhaust the Python call stack. The same bound should be applied to `unknown_puzzles`/`fill_in_unknown_puzzles`, which walk the same recursive `MofN` structure.

### Proof of Concept
1. Construct a `CREATE_COIN` condition whose memo is `PuzzleWithRestrictions.spec_namespace` followed by an `MofN` hint (`further_branching=1`) whose single member's memo is itself another `MofN`-branching memo, repeated N times (e.g., N = 5,000–100,000, well beyond Python's default recursion limit of ~1000).
2. Spend/create a coin carrying that memo on-chain (an ordinary, unprivileged coin creation).
3. Have a client call `PlotNFT.get_next_from_coin_spend(coin_spend=...)` (or any future caller of `PuzzleWithRestrictions.from_memo()`) on that coin's spend, as shown in [3](#0-2) .
4. `from_memo()` recurses once per nesting level with no depth check, as in [5](#0-4) , raising `RecursionError` and halting/crashing the processing task.

    @classmethod
    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
            puzzle=puzzle,
