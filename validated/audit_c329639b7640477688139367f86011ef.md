### Title
Stale `manualResolutions` conflict-resolution choices are silently reapplied across merge-state changes, allowing an attacker-controlled remote to corrupt what a user commits - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState` in `app/src/lib/stores/updates/changes-state.ts` keys a user's manual conflict resolution choices (`ManualConflictResolution.ours`/`theirs`) by file path in a `Map<string, ManualConflictResolution>` and carries that map forward across status refreshes as long as the conflict `kind` (`'merge'`) stays the same - even when `currentTip`/`currentBranch` (i.e., the actual commit being merged in) has changed underneath the user. When the merge is later finished, `createMergeCommit` (`app/src/lib/git/commit.ts:82-97`) blindly applies the stored resolution to whatever content is currently present for that path, without re-validating that the resolution was made against the same content the user reviewed.

### Finding Description
`getConflictState`/`updateConflictState` (`app/src/lib/stores/updates/changes-state.ts:118-176, 263-311`) build the `ConflictState` from `IStatusResult` on every status refresh. The `manualResolutions` are preserved unconditionally: [1](#0-0) 

`performEffectsForMergeStateChange`/`performEffectsForRebaseStateChange` only use branch/tip name comparisons to record analytics ("aborted"/"success" counters) - they never invalidate `manualResolutions` even when `currentTip` (the incoming merge head) changes while `currentBranch` stays the same, e.g. because the remote branch being merged was force-pushed to a new SHA between the time the user made a manual "theirs" choice and the time they click "Commit merge": [2](#0-1) 

When the user finally continues, the stale `manualResolutions` map flows straight through `dispatcher.finishConflictedMerge` → `_finishConflictedMerge` → `createMergeCommit`, which applies the resolution by path against whatever `status.entry.them`/`us` currently is, with no SHA/content binding check: [3](#0-2) [4](#0-3) 

The "us"/"them" chosen content is derived purely from the live `status.entry` at commit time, not from the content that existed when the choice was made: [5](#0-4) 

There is no code path anywhere in `updateConflictState` that clears or re-validates `manualResolutions` when `currentTip` changes but `currentBranch`/`kind` remain identical - the only invalidation trigger is a full `branchNameChanged`, and even that only affects stats, not the resolutions themselves.

### Impact Explanation
This mirrors the reported bug-class exactly: a state value the user "earned" (their reviewed, deliberate `theirs`/`ours` choice) is silently carried over and reapplied in a context it was never validated for, because the invalidation key (file path only, not content/SHA) is too coarse. In Desktop's case, the corrupted value is the content that gets committed into the user's repository history. If a collaborator (or attacker with push access to the branch being merged, e.g. a malicious PR branch) force-pushes new content to the same path after the user marked "theirs" but before the user hits "commit merge", Desktop will silently stage the new (potentially malicious) content without prompting the user to re-review it - directly matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitability depends on a race between the user reviewing conflicts and a force-push happening on the remote branch, combined with Desktop re-running status/fetch during that window (background fetch, refocus, manual fetch, etc.) while the merge remains unresolved and of the same `kind`. This is a real, unprivileged, attacker-controlled-remote scenario, but I could not fully trace (within the available index) whether `currentTip` in `IStatusResult` for a merge in progress is actually driven by `MERGE_HEAD`'s live SHA on every refresh, or is cached once and not re-read until the merge is aborted/restarted - `app/src/lib/status.ts` was not retrievable in the indexed content, so I cannot confirm with certainty how often `MERGE_HEAD` is re-parsed during an in-progress conflict. This uncertainty means the exact refresh cadence and thus the practical likelihood of the race window opening should be verified against the full source before treating this as confirmed-exploitable.

### Recommendation
Bind manual conflict resolutions to the specific conflict instance (e.g., include `currentTip`/`MERGE_HEAD` SHA alongside the file path as the map key, or hash the conflicted blob SHAs for "ours"/"theirs") so that any change to the incoming content invalidates prior resolutions and forces the user to re-review, rather than silently carrying stale choices from `prevConflictState.manualResolutions` into `newConflictState` whenever `currentTip` differs from what it was when the resolution was recorded.

### Proof of Concept
1. Attacker with push access to `feature-branch` opens a PR with a conflicting file `config.yml` containing benign content C1.
2. Victim in Desktop starts merging `feature-branch`, sees a conflict on `config.yml`, and manually resolves it as "theirs" (accepting C1).
3. Before the victim clicks "Commit merge", the attacker force-pushes `feature-branch` so `config.yml`'s "their" content becomes malicious content C2 (same path, new SHA).
4. Desktop's background fetch/refresh re-runs `_loadStatus`, which calls `updateConflictState`; since `currentBranch` is unchanged and conflict `kind` is still `'merge'`, `manualResolutions` (`config.yml -> theirs`) is carried over unchanged into the new state, per `app/src/lib/stores/updates/changes-state.ts:270-291`.
5. Victim clicks "Commit merge" without re-reviewing (UI still shows conflict as already resolved). `createMergeCommit` stages `status.entry.them`, which is now C2, and commits it - the malicious content is silently incorporated into the victim's history and can subsequently be pushed to the shared repository.

function performEffectsForRebaseStateChange(
  prevConflictState: RebaseConflictState | null,
  newConflictState: RebaseConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
) {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.targetBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.targetBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the rebase must have been aborted
  if (branchNameChanged) {
    statsStore.increment('rebaseAbortedAfterConflictsCount')
    return
  }

  const { currentTip, currentBranch } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null &&
    currentBranch != null
  ) {
    const previousTip = prevConflictState.originalBranchTip

    const previousTipChanged =
      previousTip !== currentTip &&
      currentBranch === prevConflictState.targetBranch

    if (!previousTipChanged) {
      statsStore.increment('rebaseAbortedAfterConflictsCount')
    }
  }

  return
}

  public async _finishConflictedMerge(
    repository: Repository,
    workingDirectory: WorkingDirectoryStatus,
    manualResolutions: Map<string, ManualConflictResolution>
  ): Promise<string | undefined> {
    /**
     *  The assumption made here is that all other files that were part of this merge
     *  have already been staged by git automatically (or manually by the user via CLI).
     *  When the user executes a merge and there are conflicts,
     *  git stages all files that are part of the merge that _don't_ have conflicts
     *  This means that we only need to stage the conflicted files
     *  (whether they are manual or markered) to get all changes related to
     *  this merge staged. This also means that any uncommitted changes in the index
     *  that were in place before the merge was started will _not_ be included, unless
     *  the user stages them manually via CLI.
     *
     *  Its also worth noting this method only used in the Merge Conflicts dialog flow, not committing a conflicted merge via the "Changes" pane.
     *
     *  *TLDR we only stage conflicts here because git will have already staged the rest of the changes related to this merge.*
     */
    const conflictedFiles = workingDirectory.files.filter(f => {
      return f.status.kind === AppFileStatusKind.Conflicted
    })
    const gitStore = this.gitStoreCache.get(repository)
    return await gitStore.performFailableOperation(() =>
      createMergeCommit(repository, conflictedFiles, manualResolutions)
    )

export async function createMergeCommit(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  manualResolutions: ReadonlyMap<string, ManualConflictResolution> = new Map()
): Promise<string> {
  // apply manual conflict resolutions
  for (const [path, resolution] of manualResolutions) {
    const file = files.find(f => f.path === path)
    if (file !== undefined) {
      await stageManualConflictResolution(repository, file, resolution)
    } else {
      log.error(
        `couldn't find file ${path} even though there's a manual resolution for it`
      )
    }
  }

  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
