### Title
Unprivileged stake `Split`/`Merge`/top-up during the epoch-reward distribution window can violate a hard `assert_eq!` invariant in `build_updated_stake_reward`, panicking every validator - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The C4 report describes a single misbehaving collateral asset making a *global*, unconditional pass (`AssetRegistry.refresh()`) revert for everyone, permanently freezing the whole system because the failure path has no fallback and cannot be worked around by governance. The Agave analog is the two-phase, multi-block **partitioned epoch-reward** pipeline: rewards are *calculated* once at the epoch boundary from a stake-account snapshot, then *distributed* over many subsequent blocks by re-reading the *live* `StakesCache`. `build_updated_stake_reward` [1](#0-0)  hard-asserts that the live account's delegation is exactly consistent with the value computed at calculation time. Any unprivileged, ordinary stake-account instruction (e.g. `Split`) that changes the account's lamports/delegation in the interim — while the legacy (`adjust_delegations_for_rent == false`) code path is active — trips the `assert_eq!` and panics the whole validator process, deterministically, for every node replaying that slot.

### Finding Description
`distribute_partitioned_epoch_rewards` runs unconditionally on every block inside the distribution window [2](#0-1) , calling `store_stake_accounts_in_partition` [3](#0-2) , which in turn calls `build_updated_stake_reward` for every stake pubkey scheduled in that partition. That function fetches the account's **current** state from `stakes_cache_accounts` (live, post block-processing state) [4](#0-3) , then compares it against `partitioned_stake_reward`, a value that was frozen at reward-**calculation** time, potentially thousands of blocks earlier [5](#0-4) .

When the `relax_post_exec_min_balance_check` feature is inactive (`adjust_delegations_for_rent == false`), the code takes the legacy branch:
```
let expected_delegation = stake.delegation.stake.saturating_add(partitioned_stake_reward.inflation.stake_reward);
assert_eq!(expected_delegation, new_stake.delegation.stake, "stake reward delegation must be consistent with the updated stake account lamport balance");
``` [6](#0-5) 

`stake` here is the account's *live* delegation at distribution time, while `new_stake.delegation.stake` is `old_delegation_at_calculation_time + reward`. Nothing prevents an unprivileged staker from issuing an ordinary `Split`, `Merge`, or an extra lamport transfer against their own stake account between the calculation block and the (many-block) distribution window — this is a completely normal, permission-less user operation, not a "malicious validator/node" action. Doing so changes the live `delegation.stake`/lamports so that `stake.delegation.stake + reward != new_stake.delegation.stake`, and the `assert_eq!` panics.

Because block processing (including `distribute_partitioned_epoch_rewards`) is executed identically by every validator replaying/producing that slot, this panic is not confined to one node's local state — it fires deterministically across the whole cluster, exactly like the report's "single bad collateral makes `AssetRegistry.refresh()` revert for everyone" scenario. There is no governance/administrative unregister-style recovery: the reward distribution loop has no try/catch around this assertion (unlike the sibling error paths in the same function that are properly caught, e.g. `AccountNotFound`, `ArithmeticOverflow`, `UnableToSetState`, all returned as `Result` and handled by burning the reward instead of panicking) [7](#0-6) [8](#0-7) .

The report's underlying finding that this branch is real and reachable is corroborated by the existence of a regression test that specifically exercises "lamports transferred into a stake account before distribution" (`test_delegation_adjustment_at_distribution`) [9](#0-8) , which only passes because the *new* (`adjust_delegations_for_rent == true`) branch was added to tolerate this exact scenario — proving that the legacy `assert_eq!` branch would have failed under the very same conditions before that fix landed, and remains live for any cluster/environment where `relax_post_exec_min_balance_check` has not yet activated.

### Impact Explanation
A hit of the `assert_eq!` in `build_updated_stake_reward` causes a Rust panic during ordinary block-execution/replay, executed by every validator applying that slot. Since it is deterministic given the same chain state, this is not a "single node crash" but a synchronized panic across the network at the same point, i.e. a consensus/liveness halt. Under the "Valid Impact" categories this maps to *consensus halt* / *non-RPC remote exhaustion/crash*, achieved purely by an unprivileged staker performing ordinary account maintenance (splitting/merging their own stake) — no malicious validator, leaked key, or trusted process is required.

### Likelihood Explanation
The trigger requires only:
1. A cluster/epoch-boundary where `relax_post_exec_min_balance_check` is not active (this is a feature-gated legacy path — its exact current mainnet activation status could not be conclusively confirmed with the available tools, so this should be treated as **uncertain/needs verification** rather than an unconditionally exploitable bug on current mainnet).
2. Any staker issuing a `Split`, `Merge`, or lamport top-up on their own delegated stake account during the (multi-block) reward-distribution window that follows the epoch boundary — an everyday, permission-less action any user can perform on their own account.

Given how ordinary the triggering action is (stake splitting/merging is a normal wallet/exchange operation), likelihood is high wherever the legacy branch is still reachable; likelihood is effectively zero on any cluster where the feature has been permanently activated and the flag can never regress.

### Recommendation
- Remove the hard `assert_eq!` invariant entirely (or convert it into the same `Result`/`DistributionError` pattern already used for the other failure modes in this function), so that a stale/inconsistent delegation observed at distribution time degrades gracefully (e.g., burn/skip that reward and log, exactly as done for `AccountNotFound`/`ArithmeticOverflow`) instead of panicking the whole validator.
- Ensure the rent-adjustment code path (`adjust_delegations_for_rent == true`) is the only path, i.e. confirm `relax_post_exec_min_balance_check` is permanently active on all supported clusters, and delete the legacy branch instead of leaving a live panic path in the codebase.
- Add a fuzz/property test that performs `Split`/`Merge`/lamport transfers on a delegated stake account between the calculation and every block of the distribution window, verifying that `distribute_partitioned_epoch_rewards` never panics under either feature configuration.

### Proof of Concept
1. Create a stake account and delegate it in epoch N; let epoch-boundary reward *calculation* run for epoch N (this snapshots `partitioned_stake_reward.inflation.stake` from the current delegation).
2. Before the distribution partition containing this stake account's index is processed (distribution can span up to 10% of the epoch's slots, see `get_reward_distribution_num_blocks` [10](#0-9) ), submit an ordinary `Split` (or `Merge`, or a plain lamport transfer as shown in the existing test) against that same stake account, changing its live delegation/lamports.
3. On the block that processes that partition, `store_stake_accounts_in_partition` → `build_updated_stake_reward` is invoked with the now-stale `partitioned_stake_reward` versus the live, mutated `stake` account state [11](#0-10) .
4. With `adjust_delegations_for_rent == false`, `expected_delegation != new_stake.delegation.stake`, and the `assert_eq!` panics for every validator processing that block — the network halts at that slot.
5. Compare with `test_delegation_adjustment_at_distribution` [9](#0-8) , which demonstrates the identical "extra lamports added before distribution" scenario and only avoids the panic because it exercises the newer `adjust_delegations_for_rent == true` branch.

    fn build_updated_stake_reward(
        distribution_epoch: u64,
        stake_history: &StakeHistory,
        new_warmup_cooldown_rate_epoch: Option<Epoch>,
        stakes_cache_accounts: &imbl::HashMap<Pubkey, StakeAccount<Delegation>>,
        partitioned_stake_reward: &PartitionedStakeReward,
        rent: &Rent,
        adjust_delegations_for_rent: bool,
        use_fixed_point_stake_math: bool,
    ) -> Result<StakeReward, DistributionError> {
        let stake_account = stakes_cache_accounts
            .get(&partitioned_stake_reward.stake_pubkey)
            .ok_or(DistributionError::AccountNotFound)?
            .clone();

        let (mut account, stake_state): (AccountSharedData, StakeStateV2) = stake_account.into();
        let StakeStateV2::Stake(meta, stake, flags) = stake_state else {
            // StakesCache only stores accounts where StakeStateV2::delegation().is_some()
            unreachable!(
                "StakesCache entry {:?} failed StakeStateV2 deserialization",
                partitioned_stake_reward.stake_pubkey
            )
        };
        account
            .checked_add_lamports(partitioned_stake_reward.inflation.stake_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;
        account
            .checked_add_lamports(partitioned_stake_reward.block_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;

        let mut new_stake = partitioned_stake_reward.inflation.stake;
        if adjust_delegations_for_rent {
            let minimum_balance = rent.minimum_balance(account.data().len());
            // The rewarded epoch is right before the distribution epoch
            let rewarded_epoch = distribution_epoch.saturating_sub(1);
            // The entry in `partitioned_stake_reward` contains the rewards,
            // calculated during the calculation phase
            let delegation_with_rewards = new_stake.delegation.stake;
            adjust_delegation_for_rent(
                &mut new_stake.delegation,
                rewarded_epoch,
                delegation_with_rewards,
                account.lamports(),
                minimum_balance,
            );
        } else {
            let expected_delegation = stake
                .delegation
                .stake
                .saturating_add(partitioned_stake_reward.inflation.stake_reward);
            assert_eq!(
                expected_delegation, new_stake.delegation.stake,
                "stake reward delegation must be consistent with the updated stake account \
                 lamport balance"
            );
        }
        account
            .set_state(&StakeStateV2::Stake(meta, new_stake, flags))
            .map_err(|_| DistributionError::UnableToSetState)?;

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
