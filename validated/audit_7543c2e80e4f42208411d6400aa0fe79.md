This confirms the key facts needed for the analog finding:

- `RegisterERC20` is permissionless by default (`PermissionlessRegistration` param), so any unprivileged user can register an arbitrary, attacker-controlled ERC20 contract address as a token pair. [1](#0-0) 
- `GenerateIsolatedAddress` derives a **deterministic** address purely from `channelID` + `sender` string, so the same isolated address is reused across every IBC packet from that sender/channel. [2](#0-1) 
- `IBCReceivePacketCallback` issues a raw `approve(contractAddr, amountInt)` EVM call against `tokenPair.GetERC20Contract()` — an address that can be *any* registered ERC20 contract, not necessarily the module's own minter-burner bytecode — and only checks that the call didn't revert and returned `true`. [3](#0-2) 
- The docs explicitly acknowledge that funds deposited to the isolated address are unrecoverable if not forwarded by the callback contract, since no one holds its private key. [4](#0-3) 

### Title
Non-zero-to-non-zero `approve()` on isolated address in IBC receive-callback permanently locks user funds for USDT-style ERC20 tokens - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
`IBCReceivePacketCallback` performs a raw `IERC20(token).approve(contract, amount)` call (mirroring the exact bug class from the Arrakis USDT report) against an arbitrary, permissionlessly-registered ERC20 contract, using a deterministic, reused "isolated address" that holds no private key. If that ERC20 contract enforces the well-known USDT-style invariant (`approve` reverts when going from a non-zero to a non-zero allowance without first resetting to zero), a second callback-triggering IBC transfer from the same sender/channel pair will make the `approve` call revert permanently, while the underlying token transfer to the isolated address has already been committed and cannot be reversed or retried by any user (no key controls that address).

### Finding Description
`IBCReceivePacketCallback` builds the isolated receiver deterministically from `(destChannel, sender)`: [2](#0-1) 

This same address is used every time the given sender sends a callback-carrying packet over that channel. On every such packet, the keeper issues a plain `approve` call — not `increaseAllowance`, not zero-then-set, not `forceApprove` — for the entire `amountInt` from the isolated address to `contractAddr`: [3](#0-2) 

`tokenPair.GetERC20Contract()` is not restricted to module-controlled minter-burner bytecode; `RegisterERC20` is permissionless by default and lets any user register an arbitrary externally-deployed contract as a token pair (`OWNER_EXTERNAL`): [1](#0-0) 

An attacker can register a token contract that implements the exact behavior described in the referenced report — `require(amount == 0 || allowance[owner][spender] == 0)` before allowing a new non-zero approval (USDT's real mainnet behavior). Then:
1. Attacker sends an IBC transfer with a `dest_callback` memo pointing at a benign-looking callback contract that (accidentally or maliciously) does not consume the full approved allowance via `transferFrom` (e.g., only partially pulls tokens, or the underlying token has extra fee-on-transfer/rounding behavior). Because the balance-invariant check that would normally catch this happens *after* `writeFn()` commits the cached context, the residual nonzero allowance and the partial token balance left on the isolated address are permanently persisted to state even though the whole `IBCReceivePacketCallback` call ultimately returns an error: [5](#0-4) 
2. On the *next* packet from the same sender/channel, the isolated address is reused, and `approve(contractAddr, newAmount)` is invoked again while the previous allowance is still non-zero. Because the token contract requires zero-approval-first, this call reverts.
3. Since the isolated address's private key does not exist, no one can call `approve(contractAddr, 0)` first to reset it. Every subsequent IBC receive callback for that sender/channel pair permanently fails at the allowance step, and the tokens already delivered to the isolated address by the (already-finalized) underlying IBC transfer become permanently unrecoverable — exactly the scenario the module's own README calls out as "unreachable" funds.

### Impact Explanation
This matches the Critical "permanent freezing/locking of user funds" impact gate: an unprivileged attacker (or even an honest user interacting with a slightly non-standard, permissionlessly-registered token) can cause user IBC-transferred value to become permanently and irrecoverably stuck in a keyless isolated address, with no admin or governance recovery path exposed in this code. Because the trigger only requires normal IBC-transfer and permissionless ERC20-registration flows, this is reachable by unprivileged users, matching the required Critical unauthorized-lock/freeze impact.

### Likelihood Explanation
Likelihood is moderate-to-high: permissionless registration of arbitrary ERC20 contracts is enabled by default (`PermissionlessRegistration`), and USDT-style zero-reset-required approve semantics are common/well known (real production tokens like USDT itself, or any similarly-coded custom token). An attacker fully controls the registered contract's approve/transferFrom logic and thus can deterministically engineer the residual-allowance condition, or simply register a straightforward "safe-approve-required" token and rely on ordinary usage to trigger the lock on a second transfer.

### Recommendation
- Replace the raw `approve` call with a "reset-then-set" pattern: call `approve(contractAddr, 0)` before `approve(contractAddr, amount)`, or use a `safeApprove`/`forceApprove`-equivalent EVM call sequence.
- Perform the post-execution allowance/balance sanity check (and any state writes) atomically with the `approve`+callback execution, so that partial completions are never persisted via `writeFn()` when the final invariant check fails.
- Consider explicitly zeroing/revoking the allowance for `contractAddr` at the end of `IBCReceivePacketCallback` (success or failure) so that no non-zero residual allowance from the isolated address can persist across packets.

### Proof of Concept
1. Attacker calls `MsgRegisterERC20` (permissionless) to register a custom ERC20 contract `T` whose `approve()` implementation reverts if `allowance[owner][spender] != 0 && amount != 0` (standard USDT-style guard).
2. Attacker sends an IBC transfer of `T` (or the ERC20 representation of a coin registered to `T`) with a `dest_callback` memo pointing at a contract `C` that only partially consumes the approved allowance in `transferFrom` (attacker deploys `C` themselves, or leverages any contract with rounding/fee logic).
3. `IBCReceivePacketCallback` runs: `approve(C, amount)` succeeds (previous allowance was 0), `CallEVMWithData` executes `C`'s calldata which only pulls part of `amount`, `writeFn()` commits state, then the final `receiverTokenBalance != 0` check fails and the function returns an error — but the non-zero allowance and partial balance are already committed on-chain.
4. Attacker sends a second IBC transfer from the same sender over the same channel (same isolated address). `IBCReceivePacketCallback` calls `approve(C, newAmount)` again; because current allowance is still non-zero, `T.approve()` reverts, and this failure is permanent (no key exists for the isolated address to reset the allowance).
5. All tokens delivered to the isolated address (from both packets) are now permanently unrecoverable.

## Limitations

The receiver side callback **must** receive funds to an ephemeral address generated from the channelId and packet
sender address. Note that since this is a generated address, no user has the ability to sign messages on behalf of
this account even though it is a cross-chain representation of the packet sender.

tokens to a different address then you must interact with that contract through some wrapper contract interface that
can receive the funds, call the contract which deposits funds back to `msg.sender` and then the wrapper contract
can move the funds to a final desired address.
