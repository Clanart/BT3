### Title
`ReceivedOutput::read` accepts non-existent UTXOs and reports them as spendable - (networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` is documented as “a spendable output,” but its deserializer accepts an attacker-supplied scalar offset, `TxOut`, and `OutPoint` without proving that the referenced UTXO exists on-chain or contains the encoded script and amount. The wallet subsequently trusts these fields to calculate available funds, construct inputs, and sign Taproot spends.

### Finding Description
`ReceivedOutput::read` only performs syntax-level deserialization: it reads a canonical scalar, consensus-decodes a `TxOut`, and consensus-decodes an `OutPoint`, then returns `Ok(ReceivedOutput)` without validating the UTXO against blockchain state. [1](#0-0) 

`SignableTransaction::new` trusts the decoded `output.value` as available input value and inserts the decoded `outpoint` into the transaction inputs. [2](#0-1)  Before signing, `multisig` verifies only that the encoded `script_pubkey` corresponds to the threshold key plus the supplied offset; it does not verify that the `OutPoint` exists or that the encoded `TxOut` is the UTXO actually stored at that `OutPoint`. [3](#0-2)  The signing code then commits to all supplied prevouts through `Prevouts::All`, producing signatures over the attacker-defined claim. [4](#0-3) 

### Impact Explanation
An attacker who can provide bytes to `ReceivedOutput::read` can cause an arbitrary non-existent outpoint, amount, and wallet-controlled Taproot script to be represented as a spendable received output. This can cause funds to be reported received when they are not spendable, and can cause the threshold wallet to produce a fully signed transaction that Bitcoin consensus rejects because the referenced input does not exist or does not match the encoded prevout.

### Likelihood Explanation
The malicious input is entirely public data: a scalar encoding, consensus-encoded `TxOut`, and consensus-encoded `OutPoint`. Exploitation requires an integration path where serialized `ReceivedOutput`s are accepted from an untrusted peer rather than exclusively from trusted local storage. The attack does not require validator compromise, key compromise, malformed curve points, or invalid consensus encodings.

### Recommendation
Do not treat `ReceivedOutput::read` as proof of UTXO existence or spendability. Before accounting for or signing against a deserialized output, verify the `OutPoint` against trusted blockchain state and compare the chain-returned `TxOut` exactly against the encoded `TxOut`. Alternatively, restrict this deserializer to trusted persistence and expose a separately validated input type for spend construction.

### Proof of Concept
1. Let `key` be the wallet’s even Taproot group key and obtain `script = p2tr_script_buf(key).unwrap()`.
2. Construct untrusted bytes equivalent to:
   - `Scalar::ZERO.to_bytes()`
   - consensus encoding of `TxOut { value: Amount::from_sat(100_000), script_pubkey: script }`
   - consensus encoding of `OutPoint { txid: <unmined/nonexistent txid>, vout: 0 }`
3. Feed those bytes to `ReceivedOutput::read`. The function returns `Ok` despite the UTXO not existing. [5](#0-4) 
4. Pass the returned object to `SignableTransaction::new`. Its claimed `100_000` sats are included in `input_sat`, and the fake `OutPoint` is placed in a transaction input. [2](#0-1) 
5. Call `multisig` with keys whose `p2tr_script_buf(group_key)` equals the encoded script. The key/offset check succeeds because it validates only the script, not chain existence. [6](#0-5) 
6. Complete the normal preprocess/sign/complete flow. `complete` returns a signed `Transaction`, but Bitcoin nodes reject it because its input references a non-existent UTXO. [7](#0-6)
