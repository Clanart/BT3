### Title
Check-then-act race on `CachedPreprocesses` allows two signing machines to share one nonce seed, enabling FROST secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` guards nonce creation with a non-atomic `get → is_none → generate → set → get` sequence on the `CachedPreprocesses` DB table keyed by `context`. This is the same bug class as CVE-2024-50654 (a "claim a limited resource under concurrency" flaw): two executions for the same context can interleave so that both obtain the same cached seed — or one execution's `set` is overwritten after the other already generated its machine — producing two `AlgorithmSignMachine`s derived from a single `CachedPreprocess` seed. Since the seed deterministically drives `ChaCha20Rng` nonce generation, the two machines reuse identical FROST nonces, and two distinct shares under the same nonce reveal the signer's secret share.

### Finding Description
In `preprocess_internal`, the code first checks `CachedPreprocesses::get(self.txn, &self.context).is_none()`, generates a fresh preprocess with `OsRng`, caches `machine.cache()` (the seed), and then re-reads the key to build the signing machine via `AlgorithmSignMachine::from_cache` [1](#0-0) . There is no atomicity between the check, the write, and the re-read. If two invocations for the same `context` interleave (e.g., invocation A `set`s seed₁, invocation B observes `is_none` or overwrites with seed₂, then both `get`), both can resolve to the same stored seed, or A can build its machine from a seed that B later overwrites while A's published preprocess no longer matches the stored record.

The seed fully determines the nonces: `from_cache` calls `seeded_preprocess`, which feeds the seed into `ChaCha20Rng::from_seed` and generates both nonce scalars via `Commitments::new` / `C::random_nonce` [2](#0-1) [3](#0-2) . The file's own documentation acknowledges the danger: "it is explicitly unsafe to reuse nonces across signing sessions" and safety relies on BFT-finalized inputs [4](#0-3) . The FROST spec doc likewise warns that reusing a cached preprocess "will presumably cause the signer to leak their secret share" [5](#0-4) .

The concrete trigger: `share_internal` calls `preprocess_internal` on every signing attempt [6](#0-5) . If `share_internal` is invoked twice for the same context with different `serialized_preprocesses` / `msg` (the caller explicitly contemplates being called again — "In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again"), and the two calls race on the `get/set/get` sequence, each produces a deterministic machine from the same seed but signs a different binding-factor set or message. `sign` then computes `actual = base + rho * nonce` from the drained nonces and emits a `SignatureShare` [7](#0-6) .

### Impact Explanation
Two signature shares produced from the same underlying nonce `(d, e)` but different effective nonces `d + ρ₁e` vs `d + ρ₂e` (different binding factors from different preprocess sets) or different challenges yield two linear equations in the share secret. The code's own comments state the consequence directly: reuse "will enable third-party recovery of your private key share" [8](#0-7) . Recovery of a validator's MuSig/FROST secret share reduces the threshold security of the coordinator's DKG-confirmation signing protocol and can be combined with shares from Byzantine participants to forge validator-set key confirmations — a loss of integrity comparable to the CVE's integrity-only CVSS rating.

### Likelihood Explanation
The window is narrow but real: the vulnerability only requires two executions of `share_internal`/`preprocess_internal` for the same `context` within one DB transaction lifetime or across overlapping transactions. The code's own TODO notes the incomplete guard: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" and "we also need to review how we're handling Processor preprocesses" [9](#0-8) , meaning the second layer of defense against this exact replay does not yet exist. Any re-execution, retry, or rebuild path that reaches `share_internal` with the same context while the cached row state diverges triggers nonce reuse.

### Recommendation
Make the nonce-seed claim atomic and single-use: perform a transactional `get`-for-update / insert-if-absent on `CachedPreprocesses` and record a "consumed" marker once a machine has signed, rejecting a second `share_internal` for the same context unless the inputs (commitment set hash, message hash) are identical. Additionally, before publishing shares, verify on-chain that the preprocess commitments match the presumed cached preprocess (the already-noted TODO), which converts any residual reuse into a detectable abort rather than a key-leaking second signature.

### Proof of Concept
```rust
// Conceptual PoC against SigningProtocol::preprocess_internal

// Invocation A and B, same `context`, racing:
//   A: get(context) -> None
//   B: get(context) -> None
//   A: generate machine_A, set(context, seed_A)
//   B: generate machine_B, set(context, seed_B)   // overwrites seed_A
//   A: get(context) -> seed_B  -> machine_A' built from seed_B
//   B: get(context) -> seed_B  -> machine_B' built from seed_B
//
// Both A' and B' derive identical FROST nonces (d, e) via
// ChaCha20Rng::from_seed(seed_B) -> Commitments::new -> random_nonce.
// A' signs with preprocess set S1 / msg m1, B' with S2 / msg m2.
// Shares: s1 = d + rho1*e - c1*lambda*share,  s2 = d + rho2*e - c2*lambda*share
// => attacker solving the two equations recovers the secret share,
//    since (rho1, c1, rho2, c2) are public and (d + rho*e) collide modulo rho.
```

Key support: deterministic nonce derivation [10](#0-9) , nonce combination formula [11](#0-10) , and the non-atomic cache sequence [1](#0-0) .

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
