### Title
Shared, unrestricted `CallDispatcher.dispatch()` lets any order's `predispatch`/`postdispatch` calldata drain unrelated users' token allowances — ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`IntentGatewayV2` and `IntentsBase` route every order's `predispatch.call` and `output.call` (postdispatch) payloads through a single, globally shared `CallDispatcher` contract (`_params.dispatcher`), the same instance used by *every* user and *every* order of the gateway. `CallDispatcher.dispatch()` performs completely unrestricted `to.call(data)` execution with no allowlist on `to` and no binding to the order that triggered it. This is the same broken invariant as the Caviar `PrivatePool.execute()` finding: a permissionlessly-reachable, shared, arbitrary-execution primitive that can call `ERC20.transferFrom(victim, attacker, amount)` against any address that has ever left an allowance to that shared executor contract.

### Finding Description
`placeOrder()` funds the dispatcher with the *order's own* escrowed assets and then calls the dispatcher with attacker-supplied (order-creator-supplied) calldata: [1](#0-0) 

The same pattern exists for `output.call` (postdispatch, executed after a fill): [2](#0-1) 

Both call sites use `_params.dispatcher` — a single address stored in the gateway's `Params` struct and reused for all orders from all users: [3](#0-2) 

`CallDispatcher.dispatch()` itself enforces no restriction whatsoever on the call target or on whose tokens the call may move — it only checks that `to` has code, then blindly executes: [4](#0-3) 

`order.predispatch.call` and `order.output.call` are fields of the `Order` struct fully controlled by whoever calls `placeOrder`/`fillOrder` — there is no allowlist of callable targets and no restriction preventing `to` from being an arbitrary ERC20 token contract with a `transferFrom(victim, attacker, amount)` payload. The project's own documentation acknowledges the exact risk this creates but does not enforce it on-chain:

> "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution."

This is advisory only — nothing in `CallDispatcher.sol` or `IntentGatewayV2.sol`/`IntentsBase.sol` prevents an unprivileged order-placer from pointing `Call.to` at any ERC20 token and `Call.data` at `transferFrom(victim, attacker, amount)`. If **any** user of the gateway (following the documented approve-then-swap examples, e.g. approving a spender for a subsequent step, or leaving unconsumed allowance due to slippage/partial execution) has ever granted an allowance to the shared `CallDispatcher` address rather than an exact, single-use amount, that allowance is not scoped to their own order — it is a standing allowance against the *shared* dispatcher contract, exploitable by any subsequent, unrelated order.

### Impact Explanation
This directly matches the Hyperbridge bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories. An unprivileged attacker calling the public, permissionless `placeOrder()` (or `fillOrder()` for postdispatch) can craft `Call[]` entries that transfer any ERC20 balance from any address that has left a standing allowance to the CallDispatcher, to an address of the attacker's choosing — with no interaction from the victim required beyond a prior approval that the docs themselves warn is dangerous but that nothing prevents.

### Likelihood Explanation
Likelihood is elevated because: (1) `placeOrder`/`fillOrder` are fully public entry points requiring no privilege, relayer, or governance action; (2) the dispatcher is a single shared contract per gateway deployment, so allowance exposure accumulates across the entire user base over time, not just a single pool as in the original Caviar case; (3) the documented usage patterns (approve-then-swap) actively encourage granting allowances to the dispatcher address, and only a comment — not code — discourages unlimited allowances.

### Recommendation
Mirror the Caviar mitigation pattern adapted to this architecture:
- Deploy a fresh, single-use `CallDispatcher` (or an ephemeral proxy/minimal-clone) per order/fill, so no allowance or balance from one order can ever be reachable by another order's calldata, or
- Restrict `CallDispatcher.dispatch()` (or add a check in `IntentGatewayV2`/`IntentsBase`) to disallow `Call.to` targeting arbitrary ERC20 contracts unless the token is part of the order's own declared `predispatch.assets`/`output.assets`, and
- Never allow a dispatcher instance to persist standing allowances across orders/users — sweep and revoke leftover allowances at the end of every dispatch instead of only sweeping token balances.

### Proof of Concept
1. User `Victim` uses the documented approve-then-swap example for `predispatch`/postdispatch calldata and, contrary to the doc's advisory note, approves the shared `CallDispatcher` address for an unlimited amount of `TokenX` (or leaves residual allowance after a partial swap).
2. `Attacker` calls `IntentGatewayV2.placeOrder(order, graffiti)` with `order.predispatch.call` (or, for an existing filled order, `output.call` via `fillOrder`) ABI-encoded as a `Call[]` where:
   - `to = address(TokenX)`
   - `value = 0`
   - `data = abi.encodeWithSelector(IERC20.transferFrom.selector, Victim, Attacker, TokenX.allowance(Victim, dispatcher))`
3. `placeOrder` calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, which executes the crafted call verbatim: [5](#0-4) 
4. `TokenX.transferFrom` succeeds because `msg.sender` (from `TokenX`'s perspective) is the shared `CallDispatcher`, and `Victim` had granted it an allowance in an unrelated prior transaction. `Victim`'s tokens land in `Attacker`'s wallet with no further checks, since `dispatch()` has no allowlist on `to` or `data`.
