### Title
`_calExpireForfeit()` never actually forfeits unclaimed mWOMSV rewards, permanently denying honest lockers their entitled reward redistribution - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder` is meant to penalize accounts whose mWOMSV lock has expired (or is otherwise not "rewardable") by forfeiting a portion of their accrued reward and redistributing it back into the pool for stakers who remain properly locked. The forfeit calculation is implemented as a tautology that can never produce a non-zero result, so the forfeit mechanism is permanently disabled, and the yield share that should flow back to compliant, still-locked stakers is never distributed to them.

### Finding Description
`_sendReward()` computes a `forfeitAmount` for every payout via `_calExpireForfeit()` and re-queues that forfeited portion to the pool for other stakers using `_queueNewRewardsWithoutTransfer()`: [1](#0-0) 

However, `_calExpireForfeit()` sets `rewardableAmount = _amount` unconditionally, then checks `if (rewardableAmount > _amount) revert(...)` — a condition that can never be true since the two values are always equal — and finally computes `forfeitAmount = _amount - rewardableAmount`, which is always `0`: [2](#0-1) 

There is no logic anywhere in this function that references lock-expiry state, timestamps, or any other condition that would make `rewardableAmount` differ from `_amount`. The function is dead code that always returns `0`, structurally analogous to the FluxToken.sol issue where the reward formula was implemented incorrectly (wrong terms/constants used) so that the calculated value diverges from the intended economic design — here, instead of computing a *forfeited* proportion, the formula collapses to always yielding zero forfeiture regardless of the account's actual lock/expiry state.

Because `forfeitAmount` is always `0`:
- `_queueNewRewardsWithoutTransfer()` in `_sendReward()` is never invoked with a positive amount, so the reward "pot" that should be redistributed to remaining, properly-locked mWOMSV holders is never funded: [3](#0-2) 
- Every account, regardless of whether it should be subject to expiry forfeiture, receives 100% of its accrued `userRewards`, permanently bypassing the intended redistribution to honest, still-locked stakers.

### Impact Explanation
This is reachable by any ordinary wallet holding mWOMSV/vlMGP positions and calling `getReward`/`getRewards` (routed through `MasterMagpie`), i.e., no privileged role is required. The bug permanently and irrecoverably denies the class of "properly-locked" stakers the redistributed yield they are entitled to receive under the protocol's reward-forfeiture design — this is a permanent freezing/loss of unclaimed yield for those users, since the forfeited amount that should have accrued to `rewardPerTokenStored` for their benefit is never captured. There is no code path or admin function that can recover the amount that should have been forfeited on each claim, since the miscalculation happens silently at the time of `_sendReward` and the "lost" forfeiture share simply never comes into existence.

### Likelihood Explanation
This will occur on essentially every call to `getReward`/`getRewards` when a `mWOMSVBaseRewarder` is in use, since `_calExpireForfeit` is deterministically broken (not dependent on any special preconditions or attacker actions). No malicious actor is needed — the flawed formula executes on the default/expected code path for any regular user claiming rewards.

### Recommendation
Implement `_calExpireForfeit()` so that `rewardableAmount` is actually derived from the account's real lock/expiry state (e.g., mirroring the intended design referenced by `calExpireForfeit`/`ILocker` lock-slot data), rather than being hardcoded equal to `_amount`. The guard condition should be removed or corrected so it reflects a genuine invariant, and unit tests should assert that `forfeitAmount > 0` for accounts whose lock has expired, and that the forfeited amount is correctly re-distributed via `_queueNewRewardsWithoutTransfer`.

### Proof of Concept
1. Any two accounts, A and B, stake mWOMSV and accrue `userRewards` in `mWOMSVBaseRewarder`.
2. Let account A's lock expire (whatever the intended "not rewardable" condition is meant to be).
3. Account A calls `getReward(A, A)`, which invokes `_sendReward` → `_calExpireForfeit(A, userRewards[token][A])`.
4. Trace the calculation: `rewardableAmount = _amount`; `rewardableAmount > _amount` is `false`; `forfeitAmount = _amount - rewardableAmount = 0`.
5. Account A receives 100% of `userRewards[token][A]` regardless of lock expiry, and `_queueNewRewardsWithoutTransfer` is never called with a nonzero amount, so account B (who kept their lock active) never receives the redistributed share it should have been entitled to. [2](#0-1)

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
