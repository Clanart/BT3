### Title
ReceivedOutput deserialization never validates offset/script consistency — untrusted bytes produce "received" outputs that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report's bug class is *value delivered without the required receive-side validation/notification, leaving assets trapped*. The analog in Serai is `ReceivedOutput::read`: it deserializes the three fields that define a spendable received output — the scalar `offset`, the `TxOut`, and the `OutPoint` — entirely independently, with no check that the claimed `offset` actually corresponds to `output.script_pubkey`. `ReceivedOutput::read` is explicitly in the set of untrusted-byte entry points. The only place the offset↔script binding is ever established is inside `Scanner::scan_transaction`, which looks up `self.scripts.get(&output.script_pubkey)` — and that binding is immediately discarded when the output is serialized and re-read.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` mapping each registered P2TR script (for `key`, `key + offset·G`, etc.) to the offset needed to spend it (`networks/bitcoin/src/wallet/mod.rs:153-196`). `scan_transaction` emits a `ReceivedOutput` whose `offset` is correct *by construction* (lines 199-214). However, `ReceivedOutput::read` (lines 122-134) parses `offset`, `output`, and `outpoint` as independent fields:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)?;
outpoint = OutPoint::consensus_decode(&mut buf_r)?;
Ok(ReceivedOutput { offset, output, outpoint })
```

There is no re-derivation of `p2tr_script_buf(key + offset·G)` and no comparison against `output.script_pubkey` — the received-side "callback" that would confirm the delivered asset is actually usable. Any consumer that accepts a serialized `ReceivedOutput` (the type provides `serialize`/`read`/`write` precisely so it can cross trust boundaries, e.g., scheduler/processor hand-off of scanned outputs) will treat the output as received and spendable under `offset`, when the true spending key is `group_key + actual_offset·G` (with the even-Y parity condition enforced by `p2tr_script_buf`, lines 80-86). The downstream `SignableTransaction` re-keys each input by `output.offset()`, so a mismatch yields signatures for the wrong BIP-340 key — an invalid, unbroadcastable spend, i.e., funds reported received that are not spendable.

A second reachable instance of the same class exists in `Scanner::register_offset` (lines 180-196): offsets are *surjective, not bijective* — the function silently increments `offset` until `key + offset·G` is even. If a caller registers offset `o` and then constructs/communicates an address from `o` rather than the returned `o + k`, funds sent there land on a script the scanner never registered (or registered for a different offset), and `scan_transaction` will never report them — value delivered with no notification, permanently invisible to the wallet.

### Impact Explanation
An unprivileged party able to supply serialized `ReceivedOutput` bytes (or influence which offset a counterparty pays to) causes the processor to account for and attempt to spend outputs under an incorrect key offset. The resulting transaction fails BIP-340 verification on the Bitcoin network, so accounted funds cannot be moved — a direct "assets delivered but trapped" impact matching the report class. Where the offset maps to a *different registered* script, the spend can also be misattributed (e.g., change vs. external `OutputType` via `kinds[offset_repr_ref]` in `processor/src/networks/bitcoin.rs:693-695`).

### Likelihood Explanation
Reachable wherever serialized `ReceivedOutput`s cross a trust boundary rather than staying within a single `Scanner` instance; the `read` API exists precisely for that. The `register_offset` increment behavior is deterministic and triggered with ~50% probability per registration, making offset confusion a routine rather than edge-case event for any caller that ignores the return value.

### Recommendation
- In `ReceivedOutput::read`, or at the point of use, re-derive the expected script for the claimed offset (`p2tr_script_buf(group_key + offset·G)`) and reject bytes where it does not equal `output.script_pubkey`; alternatively carry the group key/registered-script set into validation.
- Make `register_offset` failures unambiguous: have callers commit to the returned offset only, and surface `None` results as errors rather than allowing address derivation from the un-adjusted scalar.

### Proof of Concept
1. Scanner registers offset `o`; `key + o·G` is odd, so `register_offset` returns `o+1` and stores script `S` for `key + (o+1)·G`.
2. Attacker (or confused counterparty) pays to the P2TR address derived from `key + o·G`'s x-coordinate with an odd-Y or differently-tweaked construction, or submits `ReceivedOutput::read` bytes `{offset: o, output: TxOut{script_pubkey: S}, outpoint: real}` — parse succeeds with no error.
3. The output is queued for spending; `SignableTransaction` re-keys input by `o`, producing a signature under `group_key + o` which does not control `S`. The spend is invalid; the accounted balance is unspendable — the delivered asset is trapped exactly as in the ERC721 report.
