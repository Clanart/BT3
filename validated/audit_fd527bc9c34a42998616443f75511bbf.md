### Title
`recoverPolynomialCoeffs`/`RecoverCellsAndComputeKZGProofs` silently produce recovered cells that diverge from attacker-supplied cells when more than the minimum number of cells is provided - (File: `api_eip7594.go`)

### Summary
`ctx.recoverPolynomialCoeffs` only enforces a *lower* bound on the number of supplied cells (`len(cellIDs) >= NumBlocksNeededToReconstruct()`), never an upper bound or a value-consistency check. When an attacker supplies strictly more than the minimum required cells with values that are not mutually consistent with a single low-degree polynomial, the erasure-decoding math (`DataRecovery.RecoverPolynomialCoefficients`) computes a quotient polynomial of degree that can exceed the truncation cutoff `dr.numScalarsInDataWord`, silently discarding real coefficients. `RecoverCellsAndComputeKZGProofs` returns `nil` error even though `recoveredCells[cellIDs[i]] != cells[i]` for the discarded positions.

### Finding Description
The broken equality is: for every `i`, `recoveredCells[cellIDs[i]] == cells[i]` after a successful (`err == nil`) call to `ctx.RecoverCellsAndComputeKZGProofs(cellIDs, cells, ...)`.

Path: `RecoverCellsAndComputeKZGProofs` → `recoverPolynomialCoeffs` → `ctx.dataRecovery.RecoverPolynomialCoefficients` → `computeCellsFromPolyCoeff` → `ctx.fk20.ComputeExtendedPolynomial`.

`recoverPolynomialCoeffs` in [1](#0-0)  checks only `isAscending(cellIDs)`, cell-ID range (`< CellsPerExtBlob`), and `len(cellIDs) < ctx.dataRecovery.NumBlocksNeededToReconstruct()` (lower bound). There is no upper bound and no check that the supplied `cells` values are actually consistent with a degree `< numScalarsInDataWord` polynomial.

The reconstruction algorithm in `DataRecovery.RecoverPolynomialCoefficients` ( [2](#0-1) ) works by:
1. Building the vanishing polynomial `Z(x)` whose degree equals `numMissing*blockErasureSize`, where `numMissing = totalNumBlocks - len(cellIDs)`.
2. Computing `Dz(X) = IFFT(data .* Z-evaluations)`, which by construction vanishes exactly at the missing roots, so `Z(X)` exactly divides `Dz(X)` — this is a pure algebraic fact, true for *any* `data`, consistent or not.
3. Computing `Q(X) = Dz(X)/Z(X)` via a coset FFT, which is guaranteed to satisfy `Q(root_i) == data[i]` at every *known* root — again, regardless of whether the known values are self-consistent — **provided `deg(Q) < numScalarsInDataWord`**, since only the first `numScalarsInDataWord` coefficients are kept ( [3](#0-2) ).

`deg(Q) <= N-1-numMissing*blockErasureSize`. The lossless-truncation bound `deg(Q) < numScalarsInDataWord` only holds when `numMissing == NumBlocksNeededToReconstruct` (the boundary/minimum case). If `len(cellIDs) > NumBlocksNeededToReconstruct` (i.e., `numMissing` is smaller than the design minimum) and the attacker's per-cell values are mutually inconsistent (not evaluations of one low-degree polynomial), `deg(Q)` can exceed `numScalarsInDataWord - 1`. The line `polyCoeff := cosetQuotientEval[:dr.numScalarsInDataWord]` then silently truncates real, non-zero high-degree coefficients of `Q`. The truncated `polyCoeff` no longer equals `Q`, so `computeCellsFromPolyCoeff(polyCoeff, ...)` (which calls `ctx.fk20.ComputeExtendedPolynomial(polyCoeff)`, [4](#0-3) ) evaluates a different polynomial than the one that matched the supplied cells, breaking `recoveredCells[cellIDs[i]] == cells[i]` for potentially many `i`, with `RecoverCellsAndComputeKZGProofs` still returning `nil` error.

Concretely, with EIP-7594 parameters (`CellsPerExtBlob = 128`, `NumBlocksNeededToReconstruct() = 64`), an attacker can call `RecoverCellsAndComputeKZGProofs` with, e.g., 100 ascending, in-range, distinct `cellIDs` (well above the minimum 64) and 100 `Cell` byte blobs whose field-element contents are not jointly consistent with any single degree-4096 polynomial (e.g., real cells for most blocks but a handful of blocks with arbitrarily flipped scalars). None of `isAscending`, the range check, or `NumBlocksNeededToReconstruct` catch this, because none of them validate value-consistency, only index shape.

### Impact Explanation
`RecoverCellsAndComputeKZGProofs` can silently return a `recoveredCells`/`proofs` pair that does not preserve the input cells the caller believed were being recovered, with no error signaled. This is a High-severity output-divergence issue: for the exact same (crafted, unprivileged) input, this library's public API can emit `recoveredCells` different from what any correct/consistent implementation performing the c-kzg-style unique-decoding recovery would produce for a "properly-sized" (== minimum) cell set, and it does so with `nil` error, meaning API-level output cannot be trusted to actually incorporate the caller's supplied cell values whenever more than the minimum count is passed with inconsistent data. It affects consumers of `RecoverCellsAndComputeKZGProofs` (e.g. any data-availability-sampling recovery path) built on the assumption that a successful recovery reproduces the input cells exactly at their claimed indices.

### Likelihood Explanation
The attacker needs no privileges: `RecoverCellsAndComputeKZGProofs` is a fully public method and the attacker fully controls both `cellIDs` (ascending, in-range, count anywhere from `NumBlocksNeededToReconstruct()` to `CellsPerExtBlob`) and `cells` byte contents (only individually validated for field-element canonicity by `deserializeCell`, not for cross-cell polynomial consistency). Supplying strictly more than the minimum count with any inconsistent (non-single-polynomial) cell content reliably triggers divergence; this is repeatable on every call with such inputs and requires no special setup beyond the embedded trusted setup.

### Recommendation
Either (a) restrict `recoverPolynomialCoeffs`/`RecoverCellsAndComputeKZGProofs` to accept exactly `NumBlocksNeededToReconstruct()` cells (discarding/ignoring extras before calling the erasure decoder), matching the boundary where the algebraic truncation is provably lossless, or (b) after recovery, explicitly re-verify that `computeCellsFromPolyCoeff(polyCoeff, ...)` reproduces every originally supplied `cells[i]` at `cellIDs[i]` and return an error (e.g. a new `ErrRecoveredCellMismatch`) if not.

```go
func (ctx *Context) recoverPolynomialCoeffs(cellIDs []uint64, cells []*Cell) ([]fr.Element, error) {
	if len(cellIDs) != len(cells) {
		return nil, ErrNumCellIDsNotEqualNumCells
	}

	// Check that the cell Ids are ordered (ascending)
	if !isAscending(cellIDs) {
		return nil, ErrCellIDsNotOrdered
	}

	// Check that each CellId is less than CellsPerExtBlob
	for _, cellID := range cellIDs {
		if cellID >= CellsPerExtBlob {
			return nil, ErrFoundInvalidCellID
		}
	}

	// Check that we have enough cells to perform reconstruction
	if len(cellIDs) < ctx.dataRecovery.NumBlocksNeededToReconstruct() {
		return nil, ErrNotEnoughCellsForReconstruction
	}

	// Find the missing cell IDs and bit reverse them
	// So that they are in normal order
	missingCellIds := make([]uint64, 0, CellsPerExtBlob)
	for cellID := uint64(0); cellID < CellsPerExtBlob; cellID++ {
		if !slices.Contains(cellIDs, cellID) {
			missingCellIds = append(missingCellIds, (domain.BitReverseInt(cellID, CellsPerExtBlob)))
		}
	}

	// Convert Cells to field elements
	extendedBlob := make([]fr.Element, scalarsPerExtBlob)
	// for each cellId, we get the corresponding cell in cells
	// then use the cellId to place the cell in the correct position in the data(extendedBlob) array
	for i, cellID := range cellIDs {
		cell := cells[i]
		// Deserialize the cell
		cellEvals, err := deserializeCell(cell)
		if err != nil {
			return nil, err
		}
		// Place the cell in the correct position in the data array
		copy(extendedBlob[cellID*scalarsPerCell:], cellEvals)
	}
	// Bit reverse the extendedBlob so that it is in normal order
	domain.BitReverse(extendedBlob)

	return ctx.dataRecovery.RecoverPolynomialCoefficients(extendedBlob, missingCellIds)
```

```go
func (dr *DataRecovery) RecoverPolynomialCoefficients(data []fr.Element, missingIndices []BlockErasureIndex) ([]fr.Element, error) {
	zX := dr.constructVanishingPolyOnIndices(missingIndices)

	// Compute zX evaluations without mutating zX since we need zX later for a coset FFT
	zXForEval := make([]fr.Element, len(zX))
	copy(zXForEval, zX)
	dr.domainExtended.FftFr(zXForEval)
	zXEval := zXForEval

	if len(zXEval) != len(data) {
		return nil, errors.New("length of data and zXEval should be equal")
	}

	eZEval := make([]fr.Element, len(data))
	for i := 0; i < len(data); i++ {
		eZEval[i].Mul(&data[i], &zXEval[i])
	}

	dr.domainExtended.IfftFr(eZEval)
	dzPoly := eZEval

	dr.domainExtendedCoset.CosetFFtFr(zX)
	cosetZxEval := zX
	dr.domainExtendedCoset.CosetFFtFr(dzPoly)
	cosetDzEVal := dzPoly

	cosetQuotientEval := make([]fr.Element, len(cosetZxEval))
	cosetZxEval = fr.BatchInvert(cosetZxEval)

	for i := 0; i < len(cosetZxEval); i++ {
		cosetQuotientEval[i].Mul(&cosetDzEVal[i], &cosetZxEval[i])
	}

	dr.domainExtendedCoset.CosetIFFtFr(cosetQuotientEval)

	// Truncate the polynomial coefficients to the number of scalars in the data word
	polyCoeff := cosetQuotientEval[:dr.numScalarsInDataWord]
	return polyCoeff, nil
}
```
