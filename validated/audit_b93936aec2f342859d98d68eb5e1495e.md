### Title
Instant (non-streamed) reward-per-token accounting in `BribeRewardPool`/`BaseRewardPoolV2` lets an unprivileged voter flash-stake vlMGP votes immediately before `castVotes()` and withdraw immediately after, capturing a disproportionate share of just-harvested Wombat bribes - (File: `wombat/WombatBribeManager.sol`, `rewards/BribeRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`)

### Summary
`WombatBribeManager.vote()`/`castVotes()` route stake changes into `BribeRewardPool.stakeFor`/`withdrawFor`, which use the Synthetix-style `updateRewards` modifier from `BaseRewardPoolV2`. Rewards are added via `_provisionReward`, which bumps `rewardPerTokenStored` instantly and in full, proportionally to `totalStaked()` at that exact block — there is no time-weighted/streamed distribution (`rewardsDuration`/`rewardRate`). Because `castVotes()` is a public, permissionless function that triggers `wombatStaking.vote()` (which harvests pending Wombat bribes and calls `queueNewRewards()`), any address that stakes into a pool's rewarder immediately before `castVotes()` and withdraws immediately after captures a full pro-rata share of the harvested bribe despite zero time-weighted exposure.

### Finding Description
- `WombatBribeManager.vote()` [1](#0-0)  lets any user with unused vlMGP lock (`getUserVotable`) call `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta))` for a positive delta, and `withdrawFor(...)` for a negative delta, with no cooldown or minimum holding period between calls.
- `castVotes()` [2](#0-1)  is `public` with no access modifier, so anyone can trigger it (e.g. by calling `voteAndCast` themselves in one transaction). It calls `wombatStaking.vote(...)` which harvests Wombat bribes and (per the described flow) calls `IBaseRewardPool.queueNewRewards()` on each pool's rewarder.
- `BribeRewardPool.stakeFor`/`withdrawFor` are gated by `updateRewards(_for, rewardTokens)` [3](#0-2) , which snapshots `userRewardPerTokenPaid` at the current `rewardPerToken` value before/after balance change.
- The core flaw is in `BaseRewardPoolV2._provisionReward` [4](#0-3) : when new rewards are queued, `rewardPerTokenStored` is increased **immediately and entirely** by `(_amountReward * 10**decimals) / totalStaked()`, using whatever `totalStaked()` is at that exact instant — there is no per-second drip. This means every token staked at the moment `queueNewRewards()` executes earns a full pro-rata share of the entire harvested bribe, regardless of whether it was staked for the whole accrual period or for a single block.
- `_earned`/`earned` compute rewards purely as `balance * (rewardPerToken - userRewardPerTokenPaid)` [5](#0-4) , with no time-weighting component, so a flash-stake sandwiched around the harvest captures its full share exactly as described in the question.
- No `nonReentrant`, cooldown, or minimum-stake-duration check exists on `vote`, `unvote`, `stakeFor`, or `withdrawFor` to prevent this. The `onlyOperator` modifier on `stakeFor`/`withdrawFor` only restricts direct external callers to the bribe manager — it does not stop `WombatBribeManager.vote()` (callable by any EOA) from invoking them on the attacker's behalf.

### Impact Explanation
This is theft of unclaimed yield from long-term voters. Legitimate voters who kept their vlMGP votes staked on a pool for the entire epoch see their share of `rewardPerTokenStored` diluted at the exact harvest instant by the attacker's flash-added `totalSupply`, while the attacker withdraws immediately after collecting an unearned pro-rata claim on `earned()`. This matches the Immunefi "theft of unclaimed yield" impact class and is a violation of the reward-accrual conservation invariant (rewards should track time-weighted stake, not point-in-time stake).

### Likelihood Explanation
- The attacker only needs an already-unlocked/unused portion of vlMGP (`getUserVotable`) — no flash loan of vlMGP itself is required since it is locked/vested, but the vlMGP does not need to be freshly acquired per attack; the same locked balance can be reused for every future `castVotes()` call to repeatedly snipe bribes across many pools/epochs.
- The attacker can execute the whole sandwich atomically within a single transaction by calling `voteAndCast(lps, [+X], false)` themselves (which internally calls `vote()` then `castVotes()`), then a follow-up `vote(lps, [-X])`/`unvote()` transaction to exit, making the attack fully permissionless, repeatable, and requiring no special timing beyond ordinary transaction sequencing.
- The only limiting factor is the size of the attacker's vlMGP lock relative to the pool's existing stake, and the size of pending bribes — both attacker-observable on-chain before acting, making the attack highly feasible and cheap to repeat every time bribes accumulate.

### Recommendation
Replace the instantaneous `rewardPerTokenStored` bump in `BaseRewardPoolV2._provisionReward` with a time-weighted/streamed reward release model (e.g., Synthetix `rewardRate`/`periodFinish`/`lastUpdateTime` pattern), so that rewards accrue continuously over an epoch rather than being fully realizable by whoever holds stake at the exact block `queueNewRewards()` is called. Additionally, consider adding a minimum stake-duration or a cooldown between `vote()` increases and decreases on the same pool to prevent same-block/immediate sandwiching, and disallow `withdrawFor`/`unvote` on a pool within the same block/transaction as a `stakeFor` for that pool.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, a `BribeRewardPool` for a mock Wombat LP pool, and mock `IWombatStaking`/`IWombatVoter`/`IVeWom` such that `wombatStaking.vote()` harvests a fixed bribe amount and calls `queueNewRewards(amount, rewardToken)` on the pool's rewarder.
2. Set up two vlMGP holders: `victim` (locks X vlMGP and calls `vote(lp, +X)` at epoch start, holds it for the whole epoch) and `attacker` (locks Y vlMGP, does nothing until just before harvest).
3. Simulate epoch passing (no time-based accrual exists in the contract, but advance `block.timestamp` to reflect the intended epoch duration for narrative purposes).
4. Attacker calls `voteAndCast(lp, +Y, false)` (or `vote` then `castVotes`) in one transaction, triggering the bribe harvest with both `victim` and `attacker` staked.
5. Assert `rewardPerToken(rewardToken)` jumps by `bribeAmount * 1e18 / (X + Y)` in that single call, i.e., attacker's `Y` shares immediately in the full bribe despite zero holding time.
6. Attacker calls `vote(lp, -Y)` (or `unvote`) to withdraw, then `claimBribe([lp])`, and assert `earned(attacker, rewardToken) == Y * bribeAmount / (X + Y)` (nonzero and disproportionate to the attacker's near-zero holding duration).
7. Compare `victim`'s realized share (`X * bribeAmount / (X+Y)`) against the fair, fully time-weighted expectation (`bribeAmount` since victim held the vote for the entire period) — showing the victim was diluted by the attacker's flash stake, confirming the reward-conservation invariant violation.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
