## Title
Stale working-directory snapshot lets Copilot conflict-resolution silently overwrite a user's manual conflict fix - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`AppStore._applyCopilotConflictResolutions` writes Copilot's AI-generated conflict-resolution content to disk and stages it when the user clicks "Continue Merge." It guards against clobbering a file the user already resolved externally, but that guard is checked against a single `state` snapshot captured once at the top of the function, before a `for` loop that performs multiple `await`-ing operations per file. This mirrors the Balancer `_setPoolRecoveryMode` bug class: a mutating operation reads/derives from state that can go stale across intervening asynchronous steps, and by the time the destructive write happens, the guard no longer reflects reality, silently losing/overwriting a value that should have been preserved.

### Finding Description
`_applyCopilotConflictResolutions` fetches `state` once: [1](#0-0) 

It then iterates every file Copilot resolved, doing an `await resolveWithin(...)` per file, and — critically — checks whether the user already fixed the conflict themselves using the *same, function-entry* `state` object rather than re-reading `this.repositoryStateCache.get(repository)`: [2](#0-1) 

The comment at lines 7241-7246 explicitly states the intent of this check: if the user resolved a file externally while the result dialog was open, Desktop should skip overwriting it, "since overwriting it with Copilot's stored content would silently clobber their work." [3](#0-2) 

However, the check uses `state.changesState.workingDirectory.files` captured before the loop began, not a value re-fetched after each `await`. In a multi-file conflict (a very common real-world case with Copilot resolving several files at once), each iteration performs an async `resolveWithin` call and (on the write path) an `await writeFile`. Any of these await points yields the event loop, during which:
- the repository's `changesState`/`workingDirectory` in `repositoryStateCache` can be updated by an unrelated status refresh (e.g. triggered by Desktop's own `git add`/write activity, another dispatcher call, or the user editing a different conflicted file in their external editor while the "Continue Merge" operation is running), and
- that update is invisible to the loop, because it keeps referencing the original `state` local variable instead of re-querying `repositoryStateCache`.

This is exactly the order-of-operations flaw in the report's bug class: a piece of derived/staged data (`state.changesState.workingDirectory.files`) is computed once, then used later to gate a destructive write, after the underlying source of truth has already moved on. In the Balancer case the stale flag caused fees to be silently deducted without being credited anywhere; here the stale snapshot causes the user's own manually-resolved file content to be silently overwritten by Copilot's stored resolution without any error, warning, or opportunity to notice, because the "already resolved externally" guard fails to catch changes that happen *during* the loop's own execution window.

Other call sites in the same file demonstrate the pattern the code *should* follow — capturing a "before" snapshot and then explicitly re-fetching an "after" snapshot post-`await` to detect staleness before committing a state update, e.g. `updateChangesWorkingDirectoryDiff` and `_changeFileSelection`: [4](#0-3) [5](#0-4) 
`_applyCopilotConflictResolutions` is missing this re-validation entirely, despite doing the exact same kind of "check-then-act-across-an-await" sequence for every file in the loop, not just once.

### Impact Explanation
The corrupted value is the on-disk content of a conflicted file that the user believed they had personally resolved (e.g., by editing it in their external editor while the Copilot result dialog was open). Because the repository's conflict markers are attacker-influenced (a malicious/compromised remote can craft merge/rebase/cherry-pick conflicts, including content intended to manipulate what Copilot proposes as the "resolution"), an attacker-controlled repository can indirectly control `resolution.resolvedContent` for a given path. Combined with the stale-snapshot bug, Desktop can silently write and `git add` that attacker-influenced content over the user's genuine fix for files processed later in the loop, without any indication to the user that their edit was discarded. The result is silent corruption of what the user ultimately commits and pushes — the report's exact "Valid Impact" category.

### Likelihood Explanation
Triggering this requires: (1) a conflict spanning multiple files that Copilot resolves in one pass (a routine, expected usage pattern — not an unnatural user step), and (2) the user editing/resolving one of the not-yet-processed files while the multi-file write/stage loop is executing. Because the loop performs sequential `await`s (`resolveWithin` + `writeFile` per file, plus a batched `git add`), the window in which a background status refresh can race ahead of the stale `state` variable is non-trivial, especially in larger merges/rebases with many conflicted files. No admin rights, local access, or prior malware are needed — only a hostile repository/remote and normal use of the Copilot conflict-resolution feature.

### Recommendation
- Re-fetch `this.repositoryStateCache.get(repository)` immediately before the "already resolved externally" check on every loop iteration (not just once before the loop), mirroring the before/after snapshot pattern already used in `updateChangesWorkingDirectoryDiff` and `_changeFileSelection`.
- Alternatively, re-run `getStatusOrThrow`/an explicit conflict-marker check on the file immediately before `writeFile`, rather than trusting an in-memory snapshot that predates the loop's own asynchronous side effects.
- Add a regression test that: starts a multi-file Copilot resolution, mutates `repositoryStateCache` (simulating an external edit or background refresh) mid-loop after the first file is processed, and asserts that the second file is not overwritten when it now shows no unresolved conflicts.

### Proof of Concept
1. Set up a repository with two conflicted files, `a.txt` and `b.txt`, and run Copilot conflict resolution, producing `copilotResolutions` for both.
2. Simulate a race: after the first iteration's `await resolveWithin(...)` for `a.txt` returns, but before the loop evaluates `b.txt`, have another code path update `repositoryStateCache` for the repository (e.g., invoke `_loadStatus`/`updateChangesState` as would happen from a real filesystem-driven status refresh) to reflect that the user has manually fixed `b.txt`'s conflict markers on disk.
3. Because `_applyCopilotConflictResolutions` never re-reads `repositoryStateCache` inside the loop, its check at lines 7247-7256 still evaluates against the pre-loop `state`, where `b.txt` still appears conflicted — so the loop proceeds to `writeFile(absolutePathForB, resolution.resolvedContent, 'utf8')`, overwriting the user's manual fix with Copilot's resolution, then stages it via `git add`.
4. The user, who resolved `b.txt` themselves and expects that resolution to stand, unknowingly commits/pushes Copilot's overwritten content instead.

Note: I could not find a file-watcher/background-refresh implementation in the indexed portion of the codebase to pin down the exact trigger that updates `repositoryStateCache` mid-loop in production (e.g., `useFSEvents`/chokidar-based watcher), so the precise timing of the race in real usage is inferred from the async structure of the function rather than directly observed; a Devin session with full repo access could confirm the exact refresh trigger.
