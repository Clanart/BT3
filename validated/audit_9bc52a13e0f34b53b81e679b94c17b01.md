### Title
Attacker-controlled deposits to deterministic change/branch/forward scripts are misclassified and silently dropped by the output scanner — ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
Analogous to CVE-2016-10728 — where an attacker-chosen first packet causes the flow to be looked up under the wrong rule group and inspection proceeds with the wrong (missed-detection) result — Serai's Bitcoin scanner classifies every received output solely by which deterministic offset script it pays to. The `Branch`, `Change`, and `Forwarded` offsets are publicly derivable (`hash_to_F(KEY_DST, ...)` over the group key), so any unprivileged sender can craft a transaction whose output lands on a non-`External` script. The scanner then assigns the wrong `OutputType`, and the multisig event handler discards the output, producing a missed detection of real received funds.

### Finding Description
`scanner()` in `processor/src/networks/bitcoin.rs` builds a `Scanner` keyed by `script_pubkey -> Scalar offset`, registering deterministic offsets for `OutputType::Branch`, `OutputType::Change`, and `OutputType::Forwarded` via `Secp256k1::hash_to_F(KEY_DST, b"branch" | b"change" | b"forward")`. `get_outputs` scans each non-coinbase transaction with `scanner.scan_transaction(tx)` and maps `output.offset()` through the `kinds` table to assign `OutputType`. `scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` matches purely on `output.script_pubkey`, iterating all outputs.

The resulting `kind` is the security-relevant routing decision: in `processor/src/multisigs/mod.rs`, `scanner_event_to_multisig_event` retains only `OutputType::External` outputs before emitting `InInstruction`s — `outputs.retain(|output| output.kind() == OutputType::External)` — and `Forwarded` outputs are consumed only if a matching `ForwardedOutputDb` entry exists. A deposit sent to the change, branch, or forward script is therefore never converted into an instruction, never credited, and never entered into a plan.

Because the offsets are deterministic functions of public data (`KEY_DST = b"Serai Bitcoin Output Offset"`, fixed labels, and the public group key), anyone can compute the change/branch/forward `p2tr` script for a multisig and pay to it directly — no collusion, validator access, or leaked keys required.

### Impact Explanation
An attacker (or mistaken user) sending BTC to the multisig's derived change/branch/forward address produces an on-chain output the scanner *sees* but classifies as internal traffic. The output is filtered out of the `External` set and dropped, so no `InInstruction`/batch is emitted: the deposit is never credited on Serai, and the funds sit at a script the processor never schedules a spend for through the deposit flow. This is a direct missed-detection analog to the Suricata bug: attacker-chosen "direction" (which script bucket the first — and only — relevant output falls into) causes the wrong lookup result and silently skips the intended handling path.

### Likelihood Explanation
Reachable by any unprivileged Bitcoin sender: they only need the multisig group key (public) to recompute `register_offset`-derived scripts and broadcast a transaction paying to one. Exploitation requires no timing, no threshold of malicious signers, and no protocol violation — just sending funds to a valid script. Impact is limited to miscrediting/missed reporting of that specific deposit rather than key compromise, fitting a Medium severity.

### Recommendation
- Do not rely on script-bucket `kind` alone to decide whether an output is a user deposit; treat any output to a registered script that does not correspond to an in-flight change/forward/branch plan as `External`, or at least emit a refund/instruction for it.
- Track expected internal outputs (change created by `prepare_send`, forwarded outputs) explicitly and reconcile scanned `Change`/`Forwarded` outputs against them rather than unconditionally dropping them in `scanner_event_to_multisig_event`.
- Alternatively, refuse to classify outputs as `Change`/`Branch`/`Forwarded` unless they appear in a transaction the multisig itself constructed, recording expected outpoints when plans are executed.

### Proof of Concept
1. Obtain the multisig's secp256k1 group key `K` (public).
2. Compute `offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change")` (incrementing per `register_offset` semantics until `K + G*offset` yields an even-y point), then `script = p2tr_script_buf(K + G*offset)`.
3. Broadcast a Bitcoin transaction paying `script` an amount ≥ `DUST`, with any ordinary input.
4. When the block is finalized and scanned, `scan_transaction` matches the `script_pubkey`, `get_outputs` labels it `OutputType::Change`, and `scanner_event_to_multisig_event` drops it via the `retain(... == External)` filter.
5. Result: funds confirmed on-chain under the multisig's control, yet no `InInstruction` is emitted — the deposit is missed, mirroring the CVE's "continue with the wrong rule group → missed detection" shape.
