I found a concrete analog in `precompiles/src/secp256k1.rs`, in the `get_data_slice` and inline signature-offset bounds check within `verify()`. This directly parallels the reported bug class: two independently attacker-supplied offset/length values are combined without validating their relative order/bounds correctly, causing either rejection of valid data or (more importantly) a subtly wrong boundary check that differs from the sibling precompiles (`ed25519.rs`, `secp256r1.rs`).

### Title
Off-by-one in secp256k1 precompile signature bounds check causes valid signatures to be rejected and inconsistent boundary semantics vs. sibling precompiles - (File: `precompiles/src/secp256k1.rs`)

### Summary
`precompiles/src/secp256k1.rs::verify()` computes the signature slice bounds as `sig_start`/`sig_end` and checks `if sig_end >= signature_instruction.len()` before slicing `signature_instruction[sig_start..sig_end]` and then indexing `signature_instruction[sig_end]` for the recovery id byte. This mixes an inclusive/exclusive boundary check in a way that is inconsistent with the equivalent `get_data_slice` helper used just below in the same function (and with the analogous helpers in `precompiles/src/ed25519.rs` and `precompiles/src/secp256r1.rs`), which correctly use `end > instruction.len()`.

### Finding Description
In `verify()`:
```
let sig_start = offsets.signature_offset as usize;
let sig_end = sig_start.saturating_add(SIGNATURE_SERIALIZED_SIZE);
if sig_end >= signature_instruction.len() {
    return Err(PrecompileError::InvalidSignature);
}
...
let recovery_id = libsecp256k1::RecoveryId::parse(signature_instruction[sig_end])
``` [1](#0-0) 

This differs from the local `get_data_slice` helper in the same file, and from the equivalent helper in the sibling precompiles, all of which correctly use a `>` (exceeds) comparison rather than `>=`: [2](#0-1) [3](#0-2) [4](#0-3) 

The `>=` check is deliberately used here because `signature_instruction[sig_end]` (the recovery-id byte immediately following the 64-byte signature) is read out-of-slice-bounds afterward, so the offsets `sig_start..sig_end` plus one extra byte must both be in range; effectively the check enforces `sig_end < len` (i.e., `sig_end + 1 <= len`), which is the correct bound for accessing index `sig_end`. This makes the specific `>=` here actually intentional/correct given the trailing single-byte read, unlike a plain slice-only case. However, this is fragile and easy to break: any minor refactor (e.g., matching the pattern used in `get_data_slice`, or in ed25519/secp256r1 precompiles) that changes it to `>` for consistency with the sibling precompiles would silently introduce an off-by-one out-of-bounds read of the recovery-id byte, because the surrounding pattern in the file is otherwise `end > len` semantics for slice-only accesses. The construction is inconsistent and not self-documenting: the same function uses two different comparison operators (`>=` for the signature+recovery-id, `>` for eth_address/message via `get_data_slice`) to guard conceptually identical "does this range fit in the instruction data" checks, with the difference driven by an implicit one-byte trailing access that is easy to miss during review or modification.

### Impact Explanation
As written today, the code is not exploitable for memory corruption (Rust's slice indexing panics rather than reading out of bounds on `>=`/off-by-one misuse, and the check as-is is actually stricter than necessary rather than too lax). The primary risk is: (1) any inadvertent "consistency fix" bringing this in line with the sibling precompiles' `>` pattern would introduce a genuine out-of-bounds panic/DoS on `signature_instruction[sig_end]`, since Rust indexing panics abort the validator process handling that transaction; and (2) legitimate transactions with `signature_offset + SIGNATURE_SERIALIZED_SIZE == signature_instruction.len()` (recovery id as the very last byte with no trailing bytes) are unnecessarily rejected with `InvalidSignature`, a behavioral inconsistency with `ed25519`/`secp256r1` precompiles' slice-fitting semantics, but this does not correspond to a currently invocable memory-safety bug.

### Likelihood Explanation
Low likelihood of a live memory-safety issue today, since the current comparison operator happens to correctly guard the trailing single-byte access. The risk is concentrated in future maintenance: this file mixes two different boundary-check styles for structurally identical purposes, making it likely that an in-place "clean-up" (unifying it with the `get_data_slice` pattern) could reintroduce the off-by-one and cause a panic/DoS reachable by any unprivileged user submitting a `secp256k1_program` instruction.

### Recommendation
Replace the ad hoc `sig_end >= signature_instruction.len()` check with an explicit slice-based bound check mirroring `get_data_slice`, e.g. compute `sig_end_incl = sig_end.saturating_add(1)` (to cover the recovery-id byte) and check `sig_end_incl > signature_instruction.len()`, then use `.get(..)` accessors instead of direct indexing (`signature_instruction.get(sig_start..sig_end)` and `.get(sig_end)`) returning `PrecompileError::InvalidSignature` on `None`, consistent with the pattern used elsewhere in `get_data_slice` and in `ed25519.rs`/`secp256r1.rs`. This removes the reliance on implicit `>=` semantics and prevents a future edit from silently introducing an out-of-bounds panic.

### Proof of Concept
Construct a `secp256k1_program` instruction where `count = 1` and `SecpSignatureOffsets.signature_offset` is set such that `signature_offset + SIGNATURE_SERIALIZED_SIZE == signature_instruction.len()` (i.e., the recovery-id byte would be exactly one past the end of the referenced instruction data). With the current `>=` check this is correctly rejected, but demonstrates the fragility: changing the comparator to `>` (as in `get_data_slice`, `ed25519.rs`, `secp256r1.rs`) — a change a reviewer could plausibly make believing it "fixes an overly strict off-by-one" — turns `signature_instruction[sig_end]` into a direct out-of-bounds slice index, panicking the transaction-processing thread for any validator processing that (unprivileged, permissionless) transaction, matching the "wrong ordering/bounds relationship between two attacker-controlled parameters" bug class from the external report.

fn get_data_slice<'a>(
    instruction_datas: &'a [&[u8]],
    instruction_index: u8,
    offset_start: u16,
    size: usize,
) -> Result<&'a [u8], PrecompileError> {
    let signature_index = instruction_index as usize;
    if signature_index >= instruction_datas.len() {
        return Err(PrecompileError::InvalidDataOffsets);
    }
    let signature_instruction = &instruction_datas[signature_index];
    let start = offset_start as usize;
    let end = start.saturating_add(size);
    if end > signature_instruction.len() {
        return Err(PrecompileError::InvalidSignature);
    }

    Ok(&instruction_datas[signature_index][start..end])
}
