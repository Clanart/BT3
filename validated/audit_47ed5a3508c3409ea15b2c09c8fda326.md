### Title
Line-selection index reuse against a re-fetched diff lets a stale patch silently commit different content than the user reviewed - (File: `app/src/lib/git/apply.ts`)

### Summary
`applyPatchToIndex()` builds the patch that will actually be staged and committed by calling `getWorkingDirectoryDiff()` *fresh* at apply time and then filtering hunk lines using `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is a positional index into hunk lines [1](#0-0) . The `file.selection` object, however, is the `DiffSelection` state the user built by clicking lines against a diff that was loaded earlier in the UI (`updateChangesWorkingDirectoryDiff`), and Desktop's own code acknowledges that this selection is only partially reconciled when the diff changes: "the diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines" [2](#0-1) . Selection state is keyed purely by numeric line index (`isSelected(lineIndex)`, `withRangeSelection(from, length, selected)`) with no line-content binding [3](#0-2) .

### Finding Description
The accounting invariant that's supposed to hold is: "the lines a user visually selected in the diff panel are the same lines that end up in the commit." That invariant is enforced entirely through numeric line indices, not content hashes. If the working tree file changes between the time the UI diff was loaded (and the user made a line selection) and the time `createCommit` → `stageFiles` → `applyPatchToIndex` runs, `formatPatch()` re-fetches the diff and reapplies the *old* `DiffSelection`'s index set to the *new* hunk structure [4](#0-3) , [5](#0-4) .

Content that can change the working tree between diff-load and commit-time under attacker control includes:
- A clean/smudge or merge driver defined in a cloned repository's `.gitattributes`/`.git/config` that rewrites file contents on checkout/merge.
- A repository-defined Git hook (`post-checkout`, `post-merge`) which Desktop now executes via its hooks proxy (`app/src/lib/hooks/hooks-proxy.ts`, `app/src/lib/hooks/with-hooks-env.ts`) [6](#0-5) , and can rewrite tracked files after Desktop displayed the diff but before the user clicks Commit.
- Any background filesystem write triggered by opening the malicious repository (build tooling, IDE, watcher) that the repo's tooling configuration launches.

Because `DiffSelection` tracks only integer line offsets and Desktop's own comment admits the reconciliation on diff refresh is best-effort ("for now") [2](#0-1) , a shifted or content-altered diff can cause the previously-selected indices to now correspond to unrelated/attacker-inserted lines. `formatPatch` will happily build a patch out of whatever lines fall at those indices in the new diff, and `git apply --cached` will stage that — with no re-confirmation shown to the user before `git commit` runs.

### Impact Explanation
This causes **silent corruption of what the user commits and subsequently pushes**: the visual diff the user reviewed and approved no longer matches the bytes that get written into the commit object. This can be leveraged by a malicious repository (via checkout/merge hooks or content filters) to have Desktop users unknowingly commit and push attacker-chosen content (e.g. reintroducing a backdoor line the user thought they excluded, or including secrets/lines the user explicitly deselected) while the UI still shows the old, reviewed diff. This matches the report's core bug class: an internal "accounting" structure (selection state / delayedRewards) becomes stale relative to reality, and the operation meant to reconcile it (`claimRewards()` / partial-diff reconciliation) is either bypassable or incomplete, and downstream code proceeds to act on the stale state without re-validation.

### Likelihood Explanation
The window is real but narrow — it requires the working-tree file to be modified (via a filter, hook, or other repo-triggered process) in between the diff being loaded into the UI and the moment the user clicks "Commit." Desktop's own recently-added hooks execution feature (`interceptHooks` for `post-checkout`/`post-merge`, `pre-commit` etc., see `app/src/lib/hooks/*`) [7](#0-6)  materially increases the number of repository-controlled trigger points that can run arbitrary user-shell commands around checkout/merge/commit, making this more reachable than a purely theoretical TOCTOU. It is not exploitable via a single click and doesn't need local/admin access — only cloning/opening or checking out a crafted repository and performing a normal commit — but it does require some coincidental timing or an attacker-controlled hook that specifically targets the currently-open file, which lowers overall likelihood to moderate rather than high.

### Recommendation
Bind `DiffSelection` state to the actual line *content* it was computed against (e.g., store a hash/fingerprint per selectable line, or diff the previously-shown hunks against freshly-fetched hunks and refuse to reuse an index whose surrounding context text differs) rather than trusting raw positional indices. Before staging in `applyPatchToIndex`/`stageFiles`, re-verify that the file's diff has not changed since the last time it was shown to the user; if it has, force the user to re-review the diff and re-confirm their selection before allowing `createCommit` to proceed, instead of silently regenerating the patch from a diff loaded moments before the commit.

### Proof of Concept
Not independently executable from static analysis alone (requires reproducing timing between hook execution and Desktop's commit flow), but the exploitable path is fully supported by local code:
1. Attacker publishes a repository containing a `post-checkout` (or `post-merge`) hook that appends/edits a line in a tracked file whenever it fires.
2. Victim clones/opens the repository in Desktop with hooks enabled (`getHooksEnvEnabled()` true, a default Desktop is moving toward per changelog "Enable hooks support by default") [8](#0-7) .
3. Victim edits the file, Desktop loads a diff and the victim deselects certain lines in the Changes view (`updateChangesWorkingDirectoryDiff` stores a `DiffSelection` keyed by index) [9](#0-8) .
4. Something triggers the repo-controlled hook again (e.g. a stash/merge/checkout side effect during the same session) which rewrites lines in that file.
5. Victim clicks Commit: `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff and reapplies the stale index-based `DiffSelection` [1](#0-0) , producing a patch/commit whose content differs from what the victim last visually approved, which is then available to `git push`.
