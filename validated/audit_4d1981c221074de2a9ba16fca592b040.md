### Title
`unlock()` permanently reverts and freezes user principal if any queued reward-token transfer inside `multiclaimFor` fails - ([File: VLMGP.sol])

### Summary
`VLMGP.unlock()` unconditionally calls `IMasterMagpie(masterMagpie).multiclaimFor(...)` before releasing the user's principal, and that call performs a `safeTransfer` for every registered reward token in the vlMGP reward pool with no try/catch. If any single reward token (e.g. a paused/blacklisting stablecoin, or a reward pool that reverts on transfer due to insufficient balance) reverts, the whole `unlock()` transaction reverts, so users cannot withdraw already-cooled-down principal.

### Finding Description
`unlock()` first validates the cooldown slot, then executes: [1](#0-0) 
`IMasterMagpie(masterMagpie).multiclaimFor` routes to `_multiClaim`, which for the vlMGP staking token calls `_claimBaseRewarder` → `rewarder.getReward(_account, _receiver)`: [2](#0-1) 
`getReward` iterates over **all** registered `rewardTokens` for the pool and performs `IERC20(rewardToken).safeTransfer(_receiver, reward)` for each one that has a nonzero pending reward: [3](#0-2) 

There is no try/catch anywhere in this call chain (`unlock` → `multiclaimFor` → `_multiClaim` → `_claimBaseRewarder` → `getReward`). If any reward token in the vlMGP reward pool reverts on transfer (e.g., a paused ERC20, a token that blacklists the vlMGP/rewarder or the recipient, or a token whose balance in the rewarder is insufficient causing the underlying transfer to revert), the entire `getReward` call reverts, bubbling all the way up and reverting `unlock()`. Because `slot.amountInCoolDown` is only zeroed and `MGP` is only transferred *after* the `multiclaimFor` call succeeds, the user's already fully-vested principal in that slot can never be extracted while any queued reward token keeps reverting — there is no way to skip or bypass the claim step from `unlock()`.

### Impact Explanation
This causes permanent/prolonged freezing of a user's principal MGP for a fully-vested cooldown slot (`endTime` has passed) as long as any reward token registered in the vlMGP rewarder keeps reverting on transfer. Since `unlock()` and reward harvesting are non-severable in a single transaction, and a single malfunctioning/paused/blacklisting reward token affects **every** user's `unlock()` call (not just one), this can freeze funds for the entire vlMGP user base — matching the Immunefi "permanent or prolonged freezing of user funds" impact category. This qualifies as ≥24h freezing whenever the problematic reward-token condition (pause, blacklist, insufficient rewarder balance) persists for that long, which is plausible for common stablecoin pause/freeze events or reward accounting shortfalls.

### Likelihood Explanation
No privileged role is needed to trigger the underlying condition — it only requires a reward token registered in the vlMGP `BaseRewardPool`/`BaseRewardPoolV2` to enter a state where `safeTransfer` reverts (paused, blacklisted recipient/holder, or reward pool insolvency due to accounting drift/rounding across multiple reward tokens). Because `queueNewRewards`/`donateRewards` allow arbitrary reward tokens to be registered over time, and any one bad token permanently blocks `unlock()` for all users, the likelihood is that the design flaw itself (tight coupling of unrelated operations) is the exploitable root cause rather than a specific attacker action — it is a systemic, easily reproducible condition, not a one-off edge case.

### Recommendation
Decouple principal withdrawal from reward harvesting in `unlock()`/`startUnlock()`. Options: (1) wrap the `multiclaimFor` call in a try/catch so a reward-claim failure does not block principal withdrawal, (2) add a per-reward-token try/catch inside `getReward`/`getRewards` so one bad token cannot block payout of others and callers, or (3) allow users to opt out of auto-claiming rewards when calling `unlock()`, letting them claim rewards separately once the problematic token is fixed/removed.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `VLMGP`, and a `BaseRewardPoolV2` for the vlMGP pool with two reward tokens: a normal ERC20 and a `RevertingERC20` mock whose `transfer`/`transferFrom` always reverts (simulating a paused/blacklisted token).
2. User locks MGP via `VLMGP.lock()`, then calls `startUnlock()` to move an amount into a cooldown slot.
3. Queue rewards for both tokens via `queueNewRewards` so `userRewards[revertingToken][user] > 0` at claim time.
4. Fast-forward past `coolDownInSecs` so `slot.endTime <= block.timestamp`.
5. Call `VLMGP.unlock(slotIndex)` and assert it reverts (propagated from `RevertingERC20.transfer`), verifying via `vm.expectRevert()`.
6. Assert `userUnlockings[user][slotIndex].amountInCoolDown` is unchanged (nonzero) and the user's `MGP` balance did not increase, demonstrating principal remains permanently locked despite `endTime` having passed, until the reverting reward token issue is resolved.

    /// calculate reward token amount
    function _claimBaseRewarder(address _stakingToken, address _account, address _receiver, address[] memory _rewardTokens) internal {
        IBaseRewardPool rewarder = IBaseRewardPool(tokenToPoolInfo[_stakingToken].rewarder);
        if (address(rewarder) != address(0)) {
            if (_rewardTokens.length > 0)
                rewarder.getRewards(_account, _receiver, _rewardTokens);
            else
                // if not specifiying any reward token, just claim them all
                rewarder.getReward(_account, _receiver);
        }
    }

        override
        public

        uint256 length = rewardTokens.length;
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier
            if (reward > 0) {
                userRewards[rewardToken][_account] = 0;
                IERC20(rewardToken).safeTransfer(_receiver, reward);
                emit RewardPaid(_account, _receiver, reward, rewardToken);
            }
        }

        return true;
    }
