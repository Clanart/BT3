### Title
Unregistered-participant index panic in `Decryption::decrypt_with_proof` enables a remote crash/DoS during DKG blame resolution - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` resolves a PedPoP accusation by indexing `self.enc_keys[&decryptor]` with the `HashMap` `Index` operator. If the blamed decryption key was never registered for `decryptor`, the index operation panics instead of returning a `DecryptionError`. A DKG participant who submits (or triggers processing of) a blame proof naming a `decryptor` without a registered `EncryptionKeyMessage` causes an unconditional panic in the honest node processing the accusation. This maps the reported bug class — an authenticated party causing a hang/crash (DoS) — onto Serai: an unauthenticated-to-the-system DKG counterparty crashes a peer with bytes it feeds to `EncryptedMessage::read` / `EncryptionKeyProof::read` and the accusation flow.

### Finding Description
In `decrypt_with_proof`, after the accused message's PoP verifies, the code verifies the accuser-supplied `EncryptionKeyProof` and dereferences the encryption-key map:

```rust
// crypto/dkg/pedpop/src/encryption.rs
pub(crate) fn decrypt_with_proof<E: Encryptable>(
  &self,
  from: Participant,
  decryptor: Participant,
  mut msg: EncryptedMessage<C, E>,
  proof: Option<EncryptionKeyProof<C>>,
) -> Result<Zeroizing<E>, DecryptionError> {
  if !msg.pop.verify(...) { Err(DecryptionError::InvalidSignature)?; }

  if let Some(proof) = proof {
    proof.dleq.verify(
      &mut encryption_key_transcript(self.context),
      &[C::generator(), msg.key],
      &[self.enc_keys[&decryptor], *proof.key],   // <-- panic site
    ).map_err(|_| DecryptionError::InvalidProof)?;
    ...
```

`self.enc_keys[&decryptor]` uses `HashMap`'s `Index` impl, which panics on a missing key. `decryptor` is a `Participant` value derived from the accusation being processed — it is not guaranteed to have previously registered an `EncryptionKeyMessage` with this `Decryption` context. Registration only happens through `Decryption::register`, which is invoked per received key message; a participant index that is syntactically valid (any non-zero `u16`, e.g. any `l <= n`) but which never completed key registration, or whose registration was rejected/dropped, leaves no entry in `enc_keys`. Indexing it aborts the thread instead of returning `Err(DecryptionError::InvalidProof)` like every other failure path in this function.

The same unchecked-index pattern exists at `Encryption::encrypt` (`self.decryption.enc_keys[&participant]`, line 466), which would panic if an outbound share is addressed to a participant with no registered key.

### Impact Explanation
A single malicious DKG participant can crash the honest node(s) evaluating their accusation: the panic unwinds/aborts whatever process hosts the DKG session, killing the signing cohort mid-protocol and, in a validator/coordinator context, halting that node's participation (liveness loss). The attacker needs only to participate in the DKG over the authenticated channel — no key material, no collusion, and no privileged access — matching the CVE's "high-privileged attacker causes complete DOS" class but reachable by an ordinary threshold participant. Because the panic occurs inside the blame-recovery path, it also prevents the honest node from completing blame adjudication against the malicious party.

### Likelihood Explanation
Triggering requires the `decrypt_with_proof` path to run with a `decryptor` lacking a registered entry. `register` itself `assert!`s on double registration (line 356-359), so any sequencing in which an accusation is processed for a participant whose key message was never seen — mis-ordered delivery, an accuser index pointing at a non-registered index, or a participant that skipped the encryption-key round — hits the panic. No expensive computation or probabilistic condition is needed; the attacker fully controls which accusations they submit and `Participant` is just a public 2-byte index. Likelihood is moderate: it requires reaching the blame phase, but within that phase it is deterministic.

### Recommendation
Replace the panicking index with a fallible lookup in `decrypt_with_proof` (and in `Encryption::encrypt`), e.g.:

```rust
let enc_key = self.enc_keys.get(&decryptor)
  .ok_or(DecryptionError::InvalidProof)?;
```

Similarly, the `assert!` in `Decryption::register` should return an error so duplicate/missing registrations from peer-controlled message flows cannot abort the process.

### Proof of Concept
```rust
// Setup: an honest node's Decryption context after key registration,
// where participant 2 never submitted an EncryptionKeyMessage.
let mut dec = Decryption::<Ristretto>::new(context);
// Only participant 1 registers.
dec.register(Participant::new(1).unwrap(), msg_from_p1);

// Malicious accuser submits an accusation naming decryptor = 2,
// accompanied by a valid EncryptionKeyProof they generated.
// (proof.dleq verifies over enc_keys[&decryptor], proof.key —
//  the panic happens at the map lookup before/independent of
//  whether the proof would verify.)
let forged_accusation = EncryptedMessage::<Ristretto, Share>::read(&mut bytes, params)?;

// This call panics: index into `enc_keys` for unregistered Participant(2)
dec.decrypt_with_proof(accuser, Participant::new(2).unwrap(), forged_accusation, Some(proof));
// thread panics at "no entry found for key" inside HashMap::index
```

The exact PoP/DLEq validity does not matter for the panic to be reachable — the `enc_keys[&decryptor]` argument is evaluated while constructing the `verify` call, so any `Option::Some(proof)` accusation against an unregistered decryptor dereferences the missing key and aborts.

Caveat: the panic requires the host to reach the blame/decryption path with a `decryptor` absent from `enc_keys`; whether the enclosing PedPoP driver can be steered there purely by attacker bytes depends on the caller's ordering of registration vs. accusation processing, which is outside the in-scope files I could fully inspect. Within this crate, however, nothing guards the lookup, and the function's own contract (`Result<_, DecryptionError>`) promises error returns rather than panics for invalid accusations.
