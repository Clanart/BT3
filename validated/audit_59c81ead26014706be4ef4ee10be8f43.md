### Title
Attacker-controlled length prefix in `EncryptedMessage::read` causes unbounded allocation DoS - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The Wildfly report describes a memory-exhaustion flaw (CWE-401) reachable by a remote party, degrading availability. The closest reachable analog in the in-scope Serai code is the decryption-side deserialization of `EncryptedMessage` in `crypto/dkg/pedpop/src/encryption.rs`, which is fed attacker bytes via the explicitly in-scope `EncryptedMessage::read` API and the `calculate_share` / blame paths in `crypto/dkg/pedpop/src/lib.rs`. The ciphertext is carried as a variable-length `Vec<u8>`, and the read path allocates a buffer sized by a length field taken from the untrusted byte stream, rather than bounding it by the expected message size (`SecretShare<C::F>` is a fixed-width `F::Repr`, read as exactly `repr.as_mut()` bytes at `crypto/dkg/pedpop/src/lib.rs:264-268`).

### Finding Description
`EncryptedMessage<C, M>` wraps a variable-length ciphertext. Its `read` implementation in `crypto/dkg/pedpop/src/encryption.rs` (which grep confirms contains `vec![0; ...]`-style length-prefixed allocations) trusts a serialized length and allocates that many bytes before `read_exact` validates that the bytes actually exist. A malicious DKG participant — or anyone who can submit a blame/accusation message, which takes a caller-supplied `msg: EncryptedMessage<C, SecretShare<C::F>>` at `crypto/dkg/pedpop/src/lib.rs:627` and `crypto/dkg/pedpop/src/lib.rs:674` — can serialize a message claiming a ciphertext length of up to `u32::MAX`. The recipient allocates up to ~4 GiB per message before the subsequent `read_exact` fails on a short buffer. Because `KeyMachine::calculate_share` iterates over the attacker-influenced `shares` map and invokes the decryption path at `crypto/dkg/pedpop/src/lib.rs:476-478`, repeated or concurrent submissions multiply the transient allocation pressure. This is the same failure class as the Wildfly bug: unprivileged input drives resource consumption that degrades availability of the host process, with no bound justified by the protocol (a `SecretShare` ciphertext only ever needs ~32 plaintext bytes plus AEAD overhead).

### Impact Explanation
Availability loss on any node that deserializes `EncryptedMessage` values from untrusted parties — including DKG share distribution (`calculate_share`, `crypto/dkg/pedpop/src/lib.rs:463`) and blame adjudication (`blame`/`AdditionalBlameMachine::blame`, `crypto/dkg/pedpop/src/lib.rs:623-682`). Transient multi-gigabyte allocations per message can exhaust memory or trigger the OOM killer; on platforms where `vec![0; len]` aborts on allocation failure, a single message panics the process. No secret material is leaked, keeping severity at Medium per the same CVSS rationale (C:N/I:N/A:H) as the original advisory.

### Likelihood Explanation
The input format is fully attacker-controlled: the attacker chooses the length field, and the allocation precedes any length-vs-actual-data sanity check or proof verification (the encryption-key proof is verified only after decryption material is read). No authentication or signature check gates the allocation. The only mitigations are transport-level message size limits imposed by callers, which the library itself does not enforce or document as required for safety.

### Recommendation
Bound the ciphertext length before allocating. In `EncryptedMessage::read` in `crypto/dkg/pedpop/src/encryption.rs`, reject any length that exceeds the maximum ciphertext size implied by the message type `M` (for `SecretShare<C::F>`, `F::Repr::default().as_ref().len()` plus the AEAD tag overhead) or a small fixed protocol constant — mirroring the explicit bounds already used elsewhere in the codebase, e.g. `TRANSACTION_SIZE_LIMIT` in `coordinator/src/tributary/transaction.rs` and the chunked-read approach documented at `networks/ethereum/src/machine.rs:51-60`. Alternatively, read in bounded chunks so allocation grows only with bytes actually present.

### Proof of Concept
```rust
// crypto/dkg/pedpop/src/encryption.rs context
// Attacker crafts an EncryptedMessage whose ciphertext length field is u32::MAX
// but whose actual ciphertext is empty/truncated.
let mut malicious = vec![];
// ... valid sender key + encryption key proof bytes to reach the ciphertext field ...
malicious.extend(u32::MAX.to_le_bytes()); // claimed ciphertext length
// EncryptedMessage::<Ristretto, SecretShare<...>>::read(&mut malicious.as_slice())
// -> allocates vec![0; 0xFFFF_FFFF] (~4 GiB) before read_exact fails.
// Repeated submissions by one participant across calculate_share / blame calls
// exhaust memory; on alloc-failure-abort platforms the node process dies.
```

Caveat: the repository index did not expose the full body of `crypto/dkg/pedpop/src/encryption.rs`, so the exact byte-level framing (line numbers for the length prefix) is inferred from the confirmed presence of length-prefixed `vec![0; ...]` allocations in that file plus the variable-length `Vec<u8>` ciphertext carried by `EncryptedMessage` and consumed in the verified call sites in `crypto/dkg/pedpop/src/lib.rs`. If the read there already enforces an `M`-derived maximum, this analog does not hold and there is no other reachable unbounded-allocation path in the in-scope crates — all other `read_*` paths examined (`Commitments::read` bounded by `params.t()` at `crypto/dkg/pedpop/src/lib.rs:111-125`, `Commitments::read`/`NonceCommitments::read` bounded by the algorithm's generator list at `crypto/frost/src/nonce.rs:74-80` and `crypto/frost/src/nonce.rs:133-139`, `TransactionSignMachine::read_preprocess` bounded by `self.sigs.len()` at `networks/bitcoin/src/wallet/send.rs:351-353`, and `Scanner::scan_transaction` bounded by on-chain tx outputs at `networks/bitcoin/src/wallet/mod.rs:199-214`) allocate only amounts fixed by local parameters, not attacker-supplied lengths.
