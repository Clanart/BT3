### Title
GitHub Desktop disables Git's built-in clone protection against malicious submodules (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: `app/src/lib/git/clone.ts`)

### Summary
GitHub Desktop's `clone()` helper unconditionally sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` on every clone operation, while also passing `--recursive` to automatically initialize and clone all submodules. [1](#0-0) 

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is a real, upstream Git environment variable introduced specifically to harden `git clone --recursive` against maliciously-crafted repositories that abuse case-insensitive/case-folding filesystems (and similar tricks) to smuggle a `.git` directory structure inside a submodule path that can overwrite or plant hook files (e.g. `.git/hooks/post-checkout`) which then get executed during the recursive checkout. This is the class of vulnerability fixed upstream by Git (CVE-2024-32002-style clone-protection). Desktop explicitly opts out of this protection for every single clone: [2](#0-1) 

Immediately above this, Desktop does add its own guard, `isClonePathSensitive`, but that only checks whether the *top-level destination path* resolves to a sensitive system directory (home, `.ssh`, `.gnupg`, `.config`, `APPDATA`) — it says nothing about what a malicious submodule inside the cloned tree can write to during the recursive clone/checkout itself. [3](#0-2) 

The broken invariant is: "cloning a repository should never let its content control what gets executed or written outside the intended working directory." By forcing `GIT_CLONE_PROTECTION_ACTIVE=false`, Desktop removes the one guard Git itself ships to enforce that invariant for recursive clones, and none of Desktop's own checks (`isClonePathSensitive`) cover the internal submodule-hook-planting attack path. This mirrors the reported bug class exactly: an attacker-controlled object (a malicious repository/VAA-analog) is processed through a path where a safety check that is supposed to gate the dangerous side effect has been silently defeated, so the dangerous effect (arbitrary file write / hook execution) can occur even though the higher-level operation appears to "succeed" normally.

### Impact Explanation
If exploitable end-to-end, this could allow a malicious GitHub repository (the attacker-controlled object explicitly called out as valid impact: "attacker controls a cloned/fetched repository") to achieve arbitrary code execution or file writes outside the intended clone directory the moment a user clones it in GitHub Desktop, via a crafted submodule structure exploited during the `--recursive` clone. This is executed with the privileges of the Desktop application/user, satisfying the "code execution / file write outside the repo" impact bar.

### Likelihood Explanation
Likelihood is high for exposure (every clone in Desktop goes through this function with the protection disabled) but depends on whether the specific upstream case-insensitive-filesystem submodule trick still has a viable payload against the installed Git version's other defenses (Git has layered additional hardening beyond this single toggle in newer releases). No git-version gating or comment justifying the override is present in this code path, so there's no compensating control visible in the repository. [4](#0-3) 

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override (or set it to `'true'`/leave unset) so Git's built-in recursive-clone protection remains active. If the override was added to work around a compatibility issue, gate it behind a verified-safe condition (e.g., confirmed patched Git version and additional Desktop-side validation of submodule paths for path traversal / case-folding collisions) rather than disabling it unconditionally for every clone.

### Proof of Concept
1. Publish a malicious public repository containing a submodule whose configuration exploits a case-insensitive/case-folding filesystem collision to plant a hook file (e.g., `post-checkout`) at a location Git's clone-protection is designed to block.
2. Have a victim clone the repository in GitHub Desktop (uses `clone()` in `app/src/lib/git/clone.ts` with `--recursive`).
3. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'`, Git's internal defense against this class of attack is bypassed during submodule initialization/checkout, and the planted hook executes.
4. Verifying full exploitability requires confirming the target Git version doesn't have other layered mitigations in place; that verification is outside what can be confirmed from the Desktop source alone.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
