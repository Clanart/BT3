### Title
Unvalidated attacker-controlled interpolation type tag and coefficients in `ThresholdKeys::read` let a crafted byte stream instantiate keys under an arbitrary group key - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to XStream unmarshalling attacker-chosen type tags to instantiate unintended objects, `ThresholdKeys::<C>::read` trusts a serialized tag byte to select `Interpolation::Constant` vs `Interpolation::Lagrange`, and in the `Constant` case reads `n` attacker-controlled scalars as the interpolation coefficients — while `ThresholdKeys::new` never verifies that `secret_share` corresponds to `verification_shares[i]`, nor that the coefficients/shares are consistent with any DKG the node actually performed. The group key is then *computed* from these untrusted bytes, so the deserializer fully controls which group key the resulting `ThresholdKeys` claims and can produce internally consistent keys under an attacker-chosen group key.

### Finding Description
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632), after checking the curve ID, the reader consumes `t`, `n`, `i`, then a single tag byte selecting the interpolation variant:

- Tag `0` → `Interpolation::Constant`, followed by `n` scalars read via `C::read_F` — these are constant coefficients, one per participant (crypto/dkg/src/lib.rs:604-616).
- Tag `1` → `Interpolation::Lagrange`.

`Interpolation::Constant(c)` means `interpolation_factor(i, _)` simply returns `c[i-1]` (crypto/dkg/src/lib.rs:226-229): the byte supplier dictates the entire multiplicative map from each participant's share to the group key.

`ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) validates only:
1. `verification_shares.len() == n` and indexes `<= n`,
2. `Constant` is only used when `t == n`,

then computes `group_key = Σ_{i ∈ 1..=t} verification_shares[i] * interpolation_factor(i, 1..=t)`. It never checks:

- `C::generator() * secret_share == verification_shares[i]` (the loaded secret share is not bound to the loaded verification shares), and
- for `Constant`, that the coefficients actually reconstruct the intended polynomial — they are arbitrary scalars.

So the whole object — params, interpolation variant, coefficients, secret share, and all `n` verification shares — is attacker-supplied, and every consistency relation between them is derived (not checked) inside `new`. This mirrors the XStream flaw: the stream's embedded "type information" (tag byte + coefficient list) drives construction of an object the receiver never authorized, with no whitelist binding the deserialized state to previously agreed state.

### Impact Explanation
An attacker who supplies bytes to `ThresholdKeys::read` (e.g., during key restoration/import or any path feeding untrusted bytes into this sink) makes the victim node adopt `ThresholdKeys` whose `group_key` is attacker-chosen:

1. Set `t == n`, tag `0` (Constant), any coefficients `c`, `verification_shares[j] = c[j]⁻¹ · Y_j` for attacker `Y_j`, and `secret_share = s` with `verification_shares[i] = G·s` so the node's own shares self-verify in `view()`.
2. The node's `group_key()` returns `G·x` for `x = Σ s_j`, a key whose discrete log the attacker knows.

Every subsequent `view()`/`sign()` produces valid FROST signature shares *under the attacker's group key*, and since the attacker controls all verification-share relations, the signature shares pass verification — the node concretely signs messages for a threshold key it never generated through a legitimate DKG. Conversely, flipping a legitimately serialized `Lagrange` blob to `Constant` (or vice versa) silently mutates the reconstructed `group_key` and every interpolation factor, making the node compute shares for the wrong group key (funds/signing-equipment divergence).

### Likelihood Explanation
`ThresholdKeys::read` is an explicitly permitted deserialization sink for untrusted bytes. Unlike the FROST preprocess/share readers — where malformed bytes are caught by share verification — the corruption here happens *before* signing: the keys themselves are a forgery. No check anywhere in the read path binds the blob to a prior transcript, session ID, or on-chain group key commitment; the first consistency check that could catch it (`key != expected`) lives entirely in the caller, and the struct offers `original_group_key()` as if it were authentic.

### Recommendation
In `ThresholdKeys::read` (or `ThresholdKeys::new`), require:
- `C::generator() * secret_share == verification_shares[&i]` — reject otherwise;
- for `Interpolation::Constant(c)`, `c.len() == n` *and* document/enforce that callers only accept the interpolation variant they negotiated;
- expose/require an expected `group_key` parameter so deserialization is bound to a previously committed key rather than deriving authority from the blob itself.

### Proof of Concept
```rust
// Attacker builds a ThresholdKeys blob for group key X = G*x that they fully own.
let x = random_scalar();
let attacker_shares: Vec<Scalar> = (1..=n).map(|_| random_scalar()).collect();
// choose x = sum(attacker_shares) by fixing the last share
let s_i = attacker_shares[i-1];                    // node's "secret share" (attacker-chosen)
let c = vec![Scalar::ONE; n];                      // Constant coefficients
let verification_shares[j] = G * attacker_shares[j];

// serialize: ID || t || n || i || tag=0 || c[0..n] || s_i || vs[0..n]
let keys = ThresholdKeys::<C>::read(&mut blob).unwrap(); // succeeds
assert_eq!(keys.group_key(), G * x);               // attacker-chosen key accepted

// Node now signs; its share verifies against verification_shares[i] = G*s_i
let view = keys.view(included).unwrap();
// produce a share — valid FROST share for group key G*x the attacker controls
```
