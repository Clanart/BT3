### Title
Unbounded stake-account fan-out via near-zero minimum delegation forces unbounded per-epoch reward-calculation cost on every validator - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The Autonolas `liquidity_lockbox` bug is that `deposit()` has no minimum-size floor, letting an attacker mass-create minimal positions that some other party must expensively unwind one-by-one. Agave has a structurally identical primitive: `stake_instruction::split` lets any stakeholder split a stake account into a new delegated stake account whose only floor is `rent_exempt_reserve + get_minimum_delegation(...)`, and pre-v5-stake-program activation that minimum delegation is **1 lamport**. Every epoch, `Bank::calculate_stake_rewards_and_commissions` iterates and processes *every single stake delegation in the whole stakes cache* to compute rewards — this is mandatory, unprivileged-triggerable, consensus-relevant work performed by every validator, not just one griefed counterparty.

### Finding Description
`get_minimum_delegation` returns `1` lamport unless the `upgrade_bpf_stake_program_to_v5` feature is active, in which case it returns `1 * LAMPORTS_PER_SOL`: [1](#0-0) 

The CLI's own split-stake flow shows the actual on-chain economic floor for a new split stake account is just the rent-exempt reserve for `StakeStateV2::size_of()` plus this minimum delegation — nothing else: [2](#0-1) 

Any unprivileged staker with a delegated stake account can therefore call `split` (or `split_with_seed`) repeatedly, at the mere cost of one rent-exempt reserve (~0.00227 SOL, fully recoverable by later merging/withdrawing) per new account, to create an arbitrarily large number of delegated stake accounts with negligible (1-lamport) delegated stake each.

Every epoch boundary, `Bank::process_new_epoch` → `compute_new_epoch_caches_and_rewards` → `calculate_rewards` → `calculate_rewards_for_partitioning` → `calculate_stake_rewards_and_commissions` pulls the **entire** `stake_delegations_vec()` from the stakes cache and does per-delegation reward redemption work over all of them: [3](#0-2) 

The code's own comment acknowledges this is expected to scale into the millions and is a known hot path: [4](#0-3) 

This same `stake_delegations` snapshot also drives `calculate_activated_stake` and is later re-walked account-by-account in `store_stake_accounts_in_partition` for every produced reward, since rewards must still be stored/distributed for zero-value entries (comment: "even if staker's reward is 0, the stake account still needs to be stored because credits observed has changed"): [5](#0-4) [6](#0-5) 

Unlike the lockbox griefing scenario (where only a single unlucky counterparty pays the closing cost), here the cost of processing every one of the attacker's dust stake accounts is paid by **every validator, every epoch, forever** as part of consensus-critical reward computation — there is no way for a validator to opt out, skip, or batch-ignore small delegations, and no per-epoch mechanism to prune or merge them automatically.

### Impact Explanation
This is a non-RPC, cluster-wide resource-exhaustion vector, not a single-node RPC nuisance: the attacker forces O(N) additional work (reward computation, additional store operations, additional entries in `imbl::HashMap<Pubkey, StakeAccount<Delegation>>`) onto every validator's mandatory per-epoch bank-processing path for the price of N rent-exempt reserves (fully attacker-recoverable via `merge`/`withdraw` later, i.e., near-zero net cost). At sufficient scale this degrades epoch-boundary processing time cluster-wide, which is on the critical path for block production and can push validators toward missing their leader slots — i.e., availability degradation across the network, matching the "non-RPC remote exhaustion" impact category.

### Likelihood Explanation
The attack requires only an ordinary, unprivileged wallet with a delegated stake account and enough SOL to cover `N` rent-exempt reserves — no special permissions, no malicious validator/peer assumption, no trusted plugin. It uses only the documented, standard `split`/`split_with_seed` instruction path exercised routinely by the CLI and `stake-accounts`/`tokens` distribution tooling shown in-repo: [7](#0-6) 
Likelihood is bounded mainly by the attacker's capital for N rent-exempt reserves, which is recoverable, making sustained/repeated griefing economically cheap.

### Recommendation
Enforce a materially larger, protocol-level minimum for any *new* stake delegation created via `split` (not just the already-planned `stake_raise_minimum_delegation_to_1_sol` proposal, which is still only a feature id/proposal in this codebase and not confirmed active) — e.g., always require the 1-SOL-class minimum delegation regardless of the `upgrade_bpf_stake_program_to_v5` feature gate. Additionally, consider bounding or rate-limiting the number of stake accounts a single delegator can maintain below some materialized total-stake threshold, and/or introducing epoch-boundary consolidation/pruning of sub-threshold delegations so the per-epoch reward-calculation cost cannot be inflated by attacker-controlled dust accounts at near-zero net cost.

### Proof of Concept
1. Attacker creates one delegated stake account and delegates real stake (`stake_instruction::create_account_and_delegate_stake`).
2. Attacker repeatedly calls `stake_instruction::split_with_seed` (as used by `rebase_stake_account`/`move_stake_account` in `stake-accounts/src/stake_accounts.rs`), each time only funding the new split account with `rent_exempt_reserve` (paid via `system_instruction::transfer`, as shown in `process_split_stake`) plus 1 lamport of delegated stake — well under any warning threshold since the CLI only prints a *warning*, not a hard failure, when below `minimum_total_lamports`: [8](#0-7) 
3. Repeat step 2 thousands of times to create thousands of near-empty delegated stake accounts, all counted in the stakes cache.
4. At the next epoch boundary, every validator's `compute_new_epoch_caches_and_rewards` must include all of these delegations in `stake_delegations_vec()`, iterate them in `calculate_stake_rewards_and_commissions`, and store per-account reward updates in `store_stake_accounts_in_partition`, inflating epoch-boundary bank processing time cluster-wide.
5. Attacker later calls `merge` (not shown here, but present in stake CLI as `MergeStake`) to reclaim rent-exempt reserves, repeating the cycle at near-zero net cost.

fn rebase_stake_account(
    stake_account_address: &Pubkey,
    new_base_pubkey: &Pubkey,
    i: usize,
    fee_payer_pubkey: &Pubkey,
    stake_authority_pubkey: &Pubkey,
    lamports: u64,
) -> Option<Message> {
    if lamports == 0 {
        return None;
    }
    let new_stake_account_address = derive_stake_account_address(new_base_pubkey, i);
    let instructions = stake_instruction::split_with_seed(
        stake_account_address,
        stake_authority_pubkey,
        lamports,
        &new_stake_account_address,
        new_base_pubkey,
        &i.to_string(),
    );
    let message = Message::new(&instructions, Some(fee_payer_pubkey));
    Some(message)
}
