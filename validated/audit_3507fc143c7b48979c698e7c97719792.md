## Title
Stale line-selection indices used against a freshly re-read diff can silently commit unreviewed content - (`app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user review a rendered diff and select only specific lines/hunks to include in a commit. That selection is stored as a set of *line-index* offsets (`DiffSelection`), not as content. When the commit is actually created, `applyPatchToIndex` re-reads the working-directory diff from disk a second time and blindly reapplies the old index-based selection to whatever hunks/line-offsets the *new* diff produces. If the on-disk file changes between the moment the user reviewed/selected lines and the moment the commit patch is built (e.g. an editor autosave, a build/watch tool, a git `clean`/`smudge` filter invoked on checkout, or any other background process touching the file — all of which can be triggered by content coming from a cloned/fetched repository, e.g. `.gitattributes` filters or LFS/build hooks), the same index numbers can now point at completely different lines. This mirrors the reported LP-issuer bug class: an action approved by the user (their "expected" balanced amounts / their expected diff selection) is executed against state that can shift underneath it, and the code never re-verifies that the actually-produced result matches what was approved.

### Finding Description
The relevant flow:

1. The UI computes a diff and lets the user toggle inclusion of individual lines; this is persisted purely as line-index sets in `DiffSelection` (`app/src/models/diff/diff-selection.ts`).
2. `app-store.ts`'s `updateChangesWorkingDirectoryDiff` explicitly acknowledges that a diff can change dramatically between renders and only prunes now-nonexistent selectable line indices — it does **not** verify that the *content* originally selected by the user is what remains selected: [1](#0-0) 
3. When the user finally commits, `stageFiles` → `applyPatchToIndex` is invoked per partially-selected file. Critically, this function fetches yet another fresh diff at apply-time via `getWorkingDirectoryDiff` and builds the commit patch from that fresh diff using the file's `selection.isSelected(absoluteIndex)` checks — the same stored index numbers, now matched against whatever hunk layout the newest diff happens to have: [2](#0-1) 
4. `formatPatch` (`app/src/lib/patch-formatter.ts`) trusts `file.selection.isSelected(absoluteIndex)` unconditionally against the hunks of whatever diff it's handed: [3](#0-2) 

There is no check anywhere in this path that the diff used to build the final patch is the same diff (by hash/content) that the user actually reviewed and selected lines against — only a best-effort pruning of indices that no longer exist. Unlike the `LPIssuer.deposit` bug's proposed fix (accept an expected/minimum outcome and verify it before committing to the trade), Desktop has no analogous "does the resulting patch match what I approved" check before calling `git apply --cached` and creating the commit.

### Impact Explanation
If the working tree changes between the user's line-selection review and the actual commit (a window that is arbitrarily long since staging is not atomic with review), the user can silently commit and push content they never reviewed or explicitly approved — lines they intended to exclude can be included, and vice versa. This is exactly the "silent corruption of what the user commits or pushes" impact category: the commit that lands on the remote does not correspond to what the UI showed as "selected" when the user clicked "Commit". Because a git `clean`/`smudge` filter, LFS pointer rewrite, or any tool watching the working directory (which can be configured by a cloned/fetched repository's own `.gitattributes`/hooks) can perform such modifications, an attacker-controlled repository can increase the likelihood/window of this mismatch without any unusual user action beyond opening/using the repository normally.

### Likelihood Explanation
This requires a real race between the diff-render/selection step and the commit step, which in an interactive GUI application is normal (users take time to select lines and write a message before committing). The window is non-trivial and grows with commit-message-writing time, making an accidental race plausible on its own; a malicious repository shipping filters/hooks that touch tracked files during normal operations increases the odds of triggering it deterministically. That said, exploiting it *reliably and remotely* (rather than as a plausible but hard-to-precisely-time corruption bug) would need more investigation into exactly which git attributes/hooks Desktop actually invokes automatically without user consent — I could not verify from the indexed code whether Desktop executes arbitrary repo-supplied filters unprompted, so likelihood should be treated as "plausible, but the precise attacker-triggerable timing primitive is not fully confirmed from local code alone."

### Recommendation
Before applying `formatPatch`'s output to the index (`applyPatchToIndex`) or before finalizing `createCommit`, verify the diff being staged is unchanged from the diff the user's `DiffSelection` was computed against (e.g., compare a hash/fingerprint of the diff, or re-derive `selectableLines` and reject/re-prompt if the file's content changed since the last selection snapshot) instead of only pruning indices that ceased to exist. At minimum, surface a warning/confirmation to the user if the file was modified externally between diff render and commit, analogous to adding a "verify actual result matches expected outcome" check.

### Proof of Concept
1. Modify a tracked file, open Desktop, and view the diff for that file in the Changes list.
2. Deselect some lines (e.g., unselect a specific added line) via the diff gutter — this stores `DiffSelection` with divergent line indices for the *current* hunk layout.
3. Before clicking "Commit", have another process (editor autosave, background formatter, or a git filter triggered by a fetch/checkout) rewrite the file so hunk boundaries shift (e.g., add/remove lines earlier in the file).
4. Click "Commit". `applyPatchToIndex` re-reads the diff (now with shifted hunks) and applies the stale line-index selection against it via `formatPatch`, producing a patch whose actual included/excluded lines no longer match what the user saw and approved in step 2.
5. Inspect the resulting commit: it contains different line inclusions than what was visually selected, with no error or warning shown to the user. [2](#0-1) [4](#0-3) [5](#0-4)
