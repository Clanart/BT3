### Title
Multi-token escrow release reverts atomically on a single blocked transfer, permanently locking the entire order's escrow - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw()` is the single code path that releases an `Order`'s escrowed input tokens, whether via `RedeemEscrow` (solver payout after a cross-chain fill) or `RefundEscrow` (user refund after cancellation). It loops over `body.tokens` and calls `IERC20.safeTransfer` (or a raw native-token `.call`) for each token in the same order, with no per-token isolation and no fallback if one transfer fails. [1](#0-0) 

Just as the Lido `requestWithdraw` bug locked funds because a downstream, uncontrollable protocol limitation (`MIN`/`MAX_STETH_WITHDRAWAL_AMOUNT`) was never checked at the point the withdraw was initiated, here the gateway never checks — at order placement or at fill/cancel time — that every escrowed token/beneficiary pair can actually be transferred. If any single token in a multi-input order becomes untransferable to the beneficiary (e.g. a supported stablecoin such as USDC/USDT blacklists the beneficiary address, or the beneficiary is a contract that reverts on receiving native ETH), the `safeTransfer`/`.call` for that one token reverts and unwinds the *entire* `_withdraw` call — including the release of every other, otherwise-transferable token in the same order.

### Finding Description
`_withdraw` is invoked exclusively from `onAccept()` when Hyperbridge delivers a `RedeemEscrow` or `RefundEscrow` POST request: [2](#0-1) 

There is no alternate on-chain path to pull the escrowed balances out of `_orders[commitment][token]` once this cross-chain message exists — `onAccept` is `onlyHost`, and the escrow accounting (`_orders`) is only ever decremented inside `_withdraw`. If `_withdraw` reverts, the ISMP message delivery for that commitment fails; because there is nothing to prevent the exact same body from being resubmitted, the destination-side message can be replayed forever and will revert every single time, exactly mirroring the Lido case where `triggerExtraStep` "will always revert... tokens... will never be claimed."

The critical difference from a normal single-token DoS is the loop structure: `body.tokens` in a `WithdrawalRequest` can (per `Order.inputs: TokenInfo[]`) contain multiple distinct ERC-20s escrowed for one order. Because the loop has no try/catch and no per-token accounting checkpointing, one poisoned token (blacklist, pausable token, non-standard revert-on-transfer token, or a beneficiary contract without a payable fallback for the native-token branch) blocks release of every other token that was otherwise perfectly redeemable. There is no way to salvage the healthy tokens or to reroute the poisoned one to an alternate address, since `beneficiary` is fixed by the incoming message (`order.user` for refunds, `solver` for fills) and cannot be renegotiated once the message is dispatched.

This is a structural amplification of the Lido bug class: instead of "some withdraw amounts near a threshold revert," here *any* one of N escrowed assets becoming untransferable to a fixed, unauthenticated-by-user beneficiary permanently freezes N-1 unrelated assets as well.

### Impact Explanation
Escrowed user or protocol funds for an order become permanently locked with no recovery mechanism:
- For `RedeemEscrow`: a solver who has already delivered output tokens on the destination chain can be permanently denied their input-token payout on the source chain if any single input token transfer to them reverts (e.g. the solver's address is later blacklisted on one of the escrowed stablecoins, or was mistakenly blacklisted before the fill settles).
- For `RefundEscrow`: a user who cancels an order can have their entire multi-token refund permanently stuck if a single escrowed token cannot be transferred back to them, even though the rest of their tokens are perfectly redeemable.

This matches the accepted Sherlock severity rationale directly: a downstream, protocol/token-level restriction not accounted for at the point of committing the withdrawal path causes a permanent, unrecoverable loss of funds for the rightful beneficiary — "high" severity because it can hit any order with a blacklistable stablecoin among its inputs, not merely an edge case.

### Likelihood Explanation
No malicious relayer, prover, governance actor, or leaked key is required. The trigger conditions are realistic and externally controllable:
- Stablecoins with issuer-controlled blacklists (USDC, USDT) are the archetypal fee/settlement tokens bridges support, and addresses can be blacklisted after order placement but before settlement completes.
- A beneficiary set to a smart-contract wallet without a payable `receive()`/`fallback()` will always revert the native-token branch (`beneficiary.call{value: amount}("")`), a common and unprivileged self-inflicted or adversarial griefing condition (an attacker can construct an order/fill whose beneficiary is such a contract).
- Since `onAccept` is called by the trusted host as part of normal, permissionless message delivery, this is a public execution path reachable by any legitimate cross-chain settlement, not a contrived edge case.

### Recommendation
Do not let one token's failed transfer block release of the others in the same `WithdrawalRequest`:
- Isolate each token transfer with `try/catch` (for ERC-20) or a bounded low-level call, and on failure route that specific amount into a per-beneficiary "claimable" escrow bucket that the beneficiary (or anyone, to that beneficiary) can retry/pull independently, rather than reverting the whole `_withdraw`.
- Decrement `_orders[commitment][token]` and mark `finalize`/event emission independent of any single token's transfer success, so a stuck token cannot resurrect the entire settlement.
- For the native-token branch, consider wrapping to WETH-equivalent on failed `.call` transfer instead of reverting, so ETH cannot be permanently locked by a non-payable beneficiary.

### Proof of Concept
1. User places a cross-chain `Order` with two escrowed input tokens: `TokenA` (a normal ERC-20) and `TokenB` (a blacklist-capable stablecoin such as USDC).
2. Before the order settles, `TokenB`'s issuer blacklists the `beneficiary` address that will ultimately receive the refund/payout (either the solver, in the fill case, or `order.user`, in the cancel case) — a routine, externally-triggerable, non-privileged-to-Hyperbridge event.
3. The corresponding `RedeemEscrow`/`RefundEscrow` message is delivered via Hyperbridge and reaches `onAccept()` → `_withdraw()`.
4. In the loop at `evm/src/apps/intentsv2/IntentsBase.sol:395-409`, the transfer of `TokenB` via `IERC20(token).safeTransfer(beneficiary, amount)` reverts because the beneficiary is blacklisted.
5. The revert unwinds the entire `_withdraw` call, including the otherwise-successful transfer of `TokenA` and the fee release, and `_filled[commitment]` is never set.
6. The message can be resubmitted indefinitely by any relayer, but will revert identically every time (the blacklist is external and permanent), permanently freezing both `TokenA` and `TokenB` escrow for that commitment with no alternative extraction path — the same "always revert / permanent lock" pattern the Lido report describes for Kelp's `triggerExtraStep`.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
