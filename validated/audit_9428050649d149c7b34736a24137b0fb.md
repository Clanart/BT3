### Title
Stale line-based diff selection is silently replayed against a freshly re-fetched diff during commit, allowing a repository-controlled `post-merge`/`post-checkout` hook to corrupt what gets committed - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop's partial-commit flow stores the user's line selections as *absolute line indices* into a diff that was fetched at some earlier point (when the user viewed/edited the Changes list), but keeps that stale diff/selection cached across background refreshes as long as the same file id stays selected. When the user actually commits, `applyPatchToIndex` re-fetches a brand-new diff from disk and blindly re-applies the old, stale, index-based selection to it. If the tracked file's on-disk content changes between the time the selection was made and the time of the commit (which a hostile remote can trigger via a `post-merge`/`post-checkout` hook run automatically during `pull`), the line offsets no longer correspond to the same hunks, and `formatPatch` will silently stage/commit different content than what the user selected in the UI - with no error and no invariant check to catch the mismatch.

### Finding Description
Line selection state (`DiffSelection`) is index-based, generated from a diff fetched once via `getWorkingDirectoryDiff` [1](#0-0) . This diff/selection is cached in `ChangesWorkingDirectorySelection.diff` and reused across background status refreshes purely by comparing the selected file's `id`, without validating that the underlying diff content is unchanged: [2](#0-1) 

Selection state (`existingFile.selection`) is likewise carried over verbatim onto the new `WorkingDirectoryFileChange` produced from a fresh `git status`: [3](#0-2) 

The only place that attempts to reconcile a changed diff with existing selection is `updateChangesWorkingDirectoryDiff`, which explicitly acknowledges the diff "might have changed dramatically since last we loaded it" and only prunes now-invalid *selectable* lines - it does not re-validate that previously selected line indices still map to the same content: [4](#0-3) 

At commit time, `_commitIncludedChanges` takes the files/selection straight from the cached `workingDirectory.files` state [5](#0-4)  and calls `createCommit`, which calls `stageFiles`, which for any partially-selected file calls `applyPatchToIndex`: [6](#0-5) 

`applyPatchToIndex` **re-fetches a brand-new diff from disk** right before staging, rather than reusing the diff the selection was computed from: [7](#0-6) 

`formatPatch` then applies the (potentially stale) `file.selection.isSelected(absoluteIndex)` against this **new** diff's hunks purely by numeric line index, with no verification that the hunk content at that index is what the user actually saw when selecting it: [8](#0-7) 

This is structurally identical to the reported bug class: a value (share-to-asset rate / here, line-index-to-content mapping) is computed at time T1, an action is taken (burn / here, staging) using state assumed to still equal T1, but the actual redemption/patch-application happens against state at T2, and no atomic transaction or invariant check exists to detect the drift.

**Attacker primitive**: a git repository the user has cloned/added as a remote can ship a `post-merge` or `post-checkout` hook. `pull()` only intercepts a fixed allowlist of hooks (`pre-merge-commit`, `prepare-commit-msg`, `commit-msg`, `post-merge`, `pre-rebase`, `pre-commit`, `post-rewrite`) [9](#0-8)  - note `post-checkout` is in the recognized hook set [10](#0-9)  but is *not* intercepted during `pull`/checkout flows, so a real, unmodified `post-checkout`/`post-merge` script can run and rewrite tracked file contents on disk after a fetch/merge/checkout completes and before the user finalizes their staged line selection and clicks Commit.

### Impact Explanation
If the working tree content changes underneath a partially-selected file between selection and commit, `applyPatchToIndex`/`formatPatch` can produce a patch that stages the wrong hunks - including content the user never selected, or omitting content they intended to commit - and this happens **silently**, with no error surfaced to the user (unlike the invariant check in the report's SY token example, there is no supply/asset check here at all). This is a direct "silent corruption of what the user commits" as called out in the valid-impact criteria: a user could unknowingly commit and push attacker-influenced content, or fail to commit content they believed they selected, from a hostile but functionally normal-looking repository.

### Likelihood Explanation
Requires: (1) the user has partially selected lines of a file for commit, (2) a repository-provided `post-merge`/`post-checkout` hook (or any concurrent legitimate operation such as build tooling, format-on-save, or another async Desktop refresh) modifies the same file's content in the window between diff/selection load and commit execution, and (3) the diff/selection cache is not invalidated in between (`updateChangedFiles` only compares file `id`, not content hash, so the stale diff/selection survives a background refresh triggered by the very hook-modifying operation). This is a realistic sequence in normal Desktop usage (pull → background status refresh reusing cached diff → user commits) and does not require local/physical access, admin rights, or pre-existing malware - only a repository the user has cloned or pulled from.

### Recommendation
- Invalidate the cached diff and any partial line selection whenever the underlying file's content/hash changes, not just when the selected file `id` changes, in `updateChangedFiles` (`app/src/lib/stores/updates/changes-state.ts`).
- Reuse the same diff object that the selection was built against when calling `applyPatchToIndex`/`stageFiles`, instead of re-fetching a new diff from disk at commit time in `app/src/lib/git/apply.ts`.
- Add a final consistency check before invoking `git commit`: re-diff and compare against the diff used to build the patch; if they differ, abort the commit and force the user to re-review the selection, analogous to performing the burn-and-redeem atomically in the original report.

### Proof of Concept
1. Clone a hostile repository that ships a `post-merge` hook (`.git/hooks/post-merge`, installed e.g. via a first `git clone` setup step or a template) which appends/edits lines in a tracked file, e.g. `shared.txt`, whenever a merge/pull completes.
2. In Desktop, open the repo, select `shared.txt` in the Changes list, and select only specific lines (partial selection) for the next commit.
3. Trigger `Pull` (or let Desktop's background fetch/refresh run) - the `post-merge` hook executes and rewrites `shared.txt`'s content/line layout on disk. Desktop's background `_refreshRepository`/`updateChangedFiles` refresh keeps the previously-selected file `id` selected, so the stale diff and stale line-index selection is preserved (`app/src/lib/stores/updates/changes-state.ts:90-95`).
4. Click Commit. `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches a fresh diff of the now-hook-modified file and `formatPatch` applies the old index-based selection to it, producing a patch that does not correspond to what the user saw/selected.
5. Inspect the resulting commit: it contains different hunks/lines than what was visually selected in the UI before the pull, with no warning shown to the user.

I was not able to fully verify (given index/time constraints) whether Desktop's async status-refresh cadence guarantees the hook always fires strictly between selection-load and commit-click in every configuration, so the exact timing window should be confirmed with a live reproduction in a background agent session.
