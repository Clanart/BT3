### Title
Data Layer mirror URLs are attacker-controlled and trigger automatic outbound requests (SSRF-class) — ([File: chia/data_layer/data_layer_wallet.py])

### Summary
Any wallet holder can create an on-chain "mirror" coin that attaches an arbitrary list of URL strings to *any* DataLayer store's `launcher_id`, without owning that store. Any node running a DataLayer service that tracks/subscribes to that `launcher_id` will ingest those URLs from wallet state and automatically issue outbound HTTP requests to them on a periodic background loop, with no validation of scheme, host, or destination (including private/link-local addresses).

### Finding Description
`DataLayerWallet.create_new_mirror()` builds a standard coin spend to `create_mirror_puzzle()` and encodes `launcher_id` plus an arbitrary list of `urls` into the coin memo — there is no check that the caller owns or controls that `launcher_id`: [1](#0-0) 

When any node's wallet syncs and sees a coin whose puzzle hash matches the mirror puzzle, `DataLayerWallet.coin_added()` extracts `launcher_id, urls` from the spend and, as long as that `launcher_id` is a *tracked* singleton (i.e., the local DataLayer service subscribes to or owns that store), it unconditionally records the mirror and its URLs — again with no check on who created the coin or whether the amount/sender is trusted: [2](#0-1) 

The DataLayer service periodically calls `update_subscriptions_from_wallet()`, which fetches these wallet-tracked mirror URLs verbatim and merges them into the local subscription server list for that store: [3](#0-2) 

`fetch_and_validate()` then iterates the subscription's `servers_info` (which now includes attacker-supplied URLs) and attempts to download delta files from each one: [4](#0-3) 

The actual outbound request is made by `http_download()`, which performs an `aiohttp` `GET` to `server_info.url + "/" + filename` with no restriction on scheme/host (no blocklist for loopback, link-local/metadata addresses, or private ranges): [5](#0-4) 

This chain matches the CVE-2019-9174 bug class: a low-privilege actor supplies a URL that is not validated, and the server-side component (here, any DataLayer node tracking the targeted store) is coerced into making an outbound request to an attacker-chosen destination — enabling internal network/port probing, cloud metadata endpoint access (e.g., `169.254.169.254`), or interaction with local-only services (including the node's own RPC ports) from every DataLayer node that follows the targeted store.

### Impact Explanation
Any wallet user who can afford the mirror coin creation fee can force every DataLayer node subscribed to a given store to make repeated outbound HTTP requests to arbitrary attacker-chosen URLs/hosts/ports, on a recurring background schedule (`periodically_manage_data`). This is a genuine SSRF primitive reachable purely through a submitted spend bundle (the mirror coin), impacting any Data Layer client that tracks the targeted store — it can be used for internal network reconnaissance, hitting cloud metadata services, or probing/attacking other local services reachable from the DataLayer host. It does not directly cause coin-set divergence or fund theft, but it is a concrete unauthorized network-request primitive triggered by an unprivileged spend, satisfying the "Data Layer client" reachability class in scope.

### Likelihood Explanation
High reachability: creating a mirror requires only `dl_new_mirror` (`chia/wallet/wallet_rpc_api.py`) which any wallet with funds can call for a `launcher_id` it does not own, and the resulting coin need only be confirmed on-chain — no cooperation from the store owner or the DataLayer node operator is required. The vulnerable node merely needs to be tracking/subscribed to the targeted `launcher_id`, which is a normal, common DataLayer operating mode (subscribing to other people's public stores).

### Recommendation
- In `DataLayerWallet.coin_added()`/mirror ingestion, validate/sanitize mirror URLs before they are used as network fetch targets (restrict scheme to `http(s)`, reject loopback/link-local/private/metadata IP ranges, or require operator opt-in per host).
- In `http_download()` / `download_file()` (`chia/data_layer/download_data.py`), enforce an allowlist or at least block requests to private/link-local/metadata address ranges by default, and make outbound mirror fetching to unvetted third-party URLs an explicit opt-in configuration.
- Consider requiring DataLayer service operators to explicitly approve new mirror URLs discovered via `update_subscriptions_from_wallet()` rather than auto-merging them into the active fetch list.

### Proof of Concept
1. Attacker (any funded wallet, does not need to own the target store) calls `dl_new_mirror` for a `launcher_id` belonging to a store that is well-known/subscribed to by many DataLayer nodes, with `urls=["http://169.254.169.254/latest/meta-data/", "http://<attacker-selected-internal-host>:<port>/"]` (`chia/wallet/wallet_rpc_api.py` `dl_new_mirror` → `DataLayerWallet.create_new_mirror`).
2. Once confirmed on-chain, any node tracking that `launcher_id` ingests the mirror via `coin_added()` (`chia/data_layer/data_layer_wallet.py:775-800`).
3. On the next `periodically_manage_data()` cycle, `update_subscriptions_from_wallet()` merges the malicious URLs into the store's subscription server list (`chia/data_layer/data_layer.py:979-985`), and `fetch_and_validate()` → `http_download()` issues outbound GET requests to those attacker-chosen hosts (`chia/data_layer/data_layer.py:642-705`, `chia/data_layer/download_data.py:298-324`), repeating on every sync cycle.

**Note on verification limits:** I was unable to fully confirm within available context whether any additional filtering exists elsewhere in the URL-parsing/validation pipeline (e.g., in `Mirror.decode_urls` or the RPC layer) that might restrict scheme/host before storage — I found no such validation in the code paths reviewed (`chia/data_layer/data_layer_wallet.py`, `chia/data_layer/data_layer.py`, `chia/data_layer/download_data.py`), but a full pass by a Devin session with complete file access would be needed to rule this out definitively.

            )[0]
            parent_spend = await fetch_coin_spend(height, parent_state.coin, peer)

                    Mirror(
                        coin.name(),
                        launcher_id,
                        uint64(coin.amount),
                        Mirror.decode_urls(urls),
                        ours,
                        height,
                    )
                )

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
