### Title
CW1155 ERC1155 pointer performs the CosmWasm token-balance state transition before invoking the untrusted `onERC1155Received`/`onERC1155BatchReceived` callback, violating checks-effects-interactions - (File: `contracts/src/CW1155ERC1155Pointer.sol`)

### Summary
The external report flags Sandclock's `Vault.deposit()` for updating protocol state and then minting NFTs (triggering attacker-controlled callbacks) before finishing execution, allowing reentrancy. The closest reachable analog in sei-chain is `CW1155ERC1155Pointer.safeTransferFrom`/`safeBatchTransferFrom`, which calls `_execute()` to perform the CW1155 `send`/`send_batch` message against the underlying CosmWasm contract (the actual state-changing action) and only afterward calls the attacker-controlled recipient's `onERC1155Received`/`onERC1155BatchReceived` hook, with no reentrancy guard.

### Finding Description
`safeTransferFrom` in `contracts/src/CW1155ERC1155Pointer.sol` performs the CosmWasm `send` execute message via `_execute(bytes(req))` (line 63), which delegatecalls into the wasmd precompile and moves the token balance in the CW1155 contract, and only then invokes the external, attacker-controlled `to` contract's `onERC1155Received` (lines 64-75). The batch variant follows the identical pattern (`_execute` at line 116, then `onERC1155BatchReceived` at lines 117-128). [1](#0-0) [2](#0-1) 

Both functions rely solely on `_execute`, which is a bare `delegatecall` into the wasmd precompile with no `nonReentrant` modifier or any lock around the pointer's transaction functions (`safeTransferFrom`, `safeBatchTransferFrom`, `setApprovalForAll`, `burn`, `burnBatch`): [3](#0-2) 

Because `to` can be any EVM contract, an attacker can make `to` a malicious contract whose `onERC1155Received`/`onERC1155BatchReceived` re-enters the pointer contract (e.g., calling `setApprovalForAll`, `burn`/`burnBatch`, or another `safeTransferFrom`) while the outer transfer call is still on the stack, before the pointer's transaction completes.

### Impact Explanation
Unlike the Sandclock `Vault`, this pointer contract keeps essentially no local Solidity ledger for balances/ownership — `balanceOf`, `balanceOfBatch`, and `isApprovedForAll` are live queries against the CosmWasm contract via the wasmd precompile rather than cached storage. This significantly reduces (though I could not fully rule out) the classic double-spend impact of the reported bug class, since a reentrant call would observe the already-updated CW1155 balance rather than stale state. I was not able to fully trace whether the wasmd precompile's `execute` path (`precompiles/wasmd/legacy/v6xx/wasmd.go`) enforces any call-depth or reentrancy restrictions when invoked recursively through a callback originating from its own `execute` call, nor whether nested precompile invocations within the same EVM message could cause double-application of the underlying Cosmos `MsgExecuteContract`, inconsistent gas accounting, or unintended state interleaving with other pointer functions like `burn`/`setApprovalForAll` that also call `_execute` without any guard. Because I cannot confirm concrete fund loss, unauthorized transfer, or supply inflation resulting from this specific reentrancy path with the evidence gathered, I cannot assert this rises to a validated Medium/High/Critical finding under the strict acceptance criteria (concrete fund loss, freezing, unauthorized transfer, or supply inflation).

### Likelihood Explanation
Reachability is high: any EVM contract can be the `to` address in `safeTransferFrom`/`safeBatchTransferFrom` on a permissionlessly-deployed CW1155→ERC1155 pointer, and CosmWasm/ERC token pointers are a public, unprivileged, user-reachable surface. However, likelihood of a *concrete, provable* fund-loss exploit is uncertain given the live-query balance design described above.

### Recommendation
Add a `nonReentrant`-style guard (e.g., an EIP-1167/OpenZeppelin `ReentrancyGuard` or a simple state-lock modifier) across all state-changing pointer functions (`safeTransferFrom`, `safeBatchTransferFrom`, `setApprovalForAll`, `burn`, `burnBatch`) in both `CW1155ERC1155Pointer.sol` and `CW721ERC721Pointer.sol`, and audit the wasmd precompile's `execute`/`executeBatch` handlers for reentrant-call protections (e.g., disallowing nested `execute` calls triggered from within an ERC-receiver callback of the same pointer instance) to close any residual cross-function reentrancy surface, even though the live-query balance design limits the immediate double-spend risk.

### Proof of Concept
Could not be fully constructed/verified within the available tool budget: a definitive PoC would require deploying a malicious `IERC1155Receiver` contract as `to`, tracing the wasmd precompile's execute path (`precompiles/wasmd/legacy/*/wasmd.go`) to confirm whether a reentrant `execute` call from within `onERC1155Received` is permitted or blocked, and whether such reentrancy can manipulate balances, approvals, or bypass the "insufficient balance" checks in `safeBatchTransferFrom`'s pre-computed `balances` array (lines 91-98) versus the balance state after the first `_execute` call completes. This gap should be validated with a Devin session that has access to the wasmd precompile execution/depth-limiting code and can run the Foundry pointer tests (`contracts/test/CW1155ERC1155PointerTest.t.sol`) with a malicious receiver mock.
