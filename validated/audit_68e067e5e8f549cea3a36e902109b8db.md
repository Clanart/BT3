### Title
Uncontrolled recursion in Chia's outer-puzzle driver matching (`match_puzzle`/`get_inner_puzzle`) allows stack exhaustion when processing untrusted offer/spend puzzle reveals - ([File: chia/wallet/outer_puzzles.py])

### Summary
Analogous to the Faraday `NestedParamsEncoder`/`dehash` bug (CWE-674, unbounded recursion over attacker-controlled nested input), Chia's wallet-side "outer puzzle" driver system recursively unwraps curried puzzle layers (CAT, singleton, ownership, CR, metadata) with no depth limit. The recursion depth is controlled entirely by how many puzzle layers an attacker curries into a `puzzle_reveal`, which is trivially cheap to make arbitrarily deep. A malicious offer or spend bundle containing a puzzle reveal with thousands of nested layers will drive the wallet's Python call stack past its limit, raising an uncaught `RecursionError`/`SystemStackError`-equivalent and crashing the offer/spend processing path.

### Finding Description
`match_puzzle()` in `chia/wallet/outer_puzzles.py` dispatches to each registered driver's `.match()` method: [1](#0-0) 

Each driver's `match`, `get_inner_puzzle`, `get_inner_solution`, `construct`, and `solve` implementations recurse into `self._match(...)`/`self._get_inner_puzzle(...)`/`self._construct(...)` when an `also` (nested inner layer) is present, with no bound on recursion depth. For example, `SingletonOuterPuzzle.match()` and `.get_inner_puzzle()`: [2](#0-1) 

and `OwnershipOuterPuzzle`, and `CATOuterPuzzle.construct`/`.get_inner_solution`, and `CROuterPuzzle.get_inner_puzzle`, all follow the same unbounded pattern: [3](#0-2) [4](#0-3) 

`PuzzleInfo.also()`/`.check_type()` in `chia/wallet/puzzle_drivers.py` is likewise recursive without a depth guard, and is called whenever a `PuzzleInfo` built from an untrusted puzzle reveal is inspected (e.g. `check_for_special_offer_making`): [5](#0-4) [6](#0-5) 

Because CLVM curry layers (`(a (q . MOD) (c (q . ARGS) 1))`) can be nested extremely deeply for negligible extra bytes/cost (no execution is required to *construct* a puzzle reveal — only to run it), a counterparty can hand a wallet an `Offer`/`SpendBundle` whose `puzzle_reveal` is wrapped in an arbitrarily deep chain of CAT/singleton/ownership/CR layers. When the receiving wallet inspects that puzzle reveal via `match_puzzle`/`get_inner_puzzle`/`PuzzleInfo.also()` (part of normal offer-taking/validation flow, e.g. `TradeManager.respond_to_offer` → `check_for_special_offer_making`/`_create_offer_for_ids`, or NFT/CAT/DL wallet driver construction), the unbounded Python recursion walks the entire nesting depth and can exhaust the interpreter stack.

This differs from the `sha256_treehash` tree-hashing code, which the codebase explicitly documents as "deliberately iterative to avoid Python recursion limits on deeply nested CLVM" — the outer-puzzle driver code does not have this protection.

### Impact Explanation
An unprivileged offer counterparty (or any spend bundle submitter whose puzzle reveal is inspected by another party's wallet, e.g. during offer validation/trade acceptance) can craft a deeply layered puzzle reveal that, when the victim wallet processes it, exhausts the Python call stack and crashes/hangs the wallet's request-handling task. This is a spend/offer-triggered transaction-processing halt (denial of service) rather than a fund-theft or consensus-divergence bug, but it fits the "spend-triggered transaction-processing halt" acceptance criterion.

### Likelihood Explanation
Building a deeply curried puzzle reveal is cheap (each layer adds only a constant handful of CLVM atoms) and does not require running the puzzle, so an attacker can reach very large nesting depths with a small `puzzle_reveal` blob. The trigger path (`Offer`/`SpendBundle` handling → `match_puzzle`/`get_inner_puzzle`/`PuzzleInfo.also()`) is exercised during normal wallet-to-wallet offer exchange, making this readily reachable by any wallet user or offer counterparty without special privileges.

### Recommendation
Add an explicit maximum recursion/nesting depth to `match_puzzle`, `get_inner_puzzle`, `get_inner_solution`, `construct`, and `solve` in the outer-puzzle driver classes (`chia/wallet/outer_puzzles.py`, `cat_outer_puzzle.py`, `singleton_outer_puzzle.py`, `ownership_outer_puzzle.py`, `cr_outer_puzzle.py`, `metadata_outer_puzzle.py`), and to `PuzzleInfo.also()`/`check_type()` in `chia/wallet/puzzle_drivers.py`. Convert the recursive traversal to an iterative loop with a bounded layer count (or raise `sys.setrecursionlimit`-independent explicit errors once a sane maximum nesting depth, e.g. 32–64 layers, is exceeded), similar to the iterative approach already used for `sha256_treehash`.

### Proof of Concept
Conceptually (cannot be fully executed without live wallet infra, but the mechanism is directly derivable from the code):
1. Construct a puzzle `P0 = ACS` (accept-any inner puzzle).
2. Repeatedly wrap it thousands of times using any of the outer-puzzle constructors that support `also`, e.g. `construct_cat_puzzle(CAT_MOD, tail, P_{i})` or `puzzle_for_ownership_layer(owner, transfer_program, P_{i})`, to build `P_{i+1}`, for N ≈ 10,000+ iterations (this is analogous to the "double CAT puzzle" pattern already exercised in `chia/_tests/wallet/cat_wallet/test_cat_outer_puzzle.py`).
3. Place `P_N` as the `puzzle_reveal` of a coin spend inside a `SpendBundle`/`Offer` sent to a victim wallet.
4. When the victim wallet calls `match_puzzle(UnknownPuzzle(known_program=P_N))` (or `get_inner_puzzle`) during offer validation/acceptance, the recursive `.match()`/`.get_inner_puzzle()` chain recurses N times, exhausting the Python stack and crashing/hanging that processing task. [7](#0-6)

def test_cat_outer_puzzle() -> None:
