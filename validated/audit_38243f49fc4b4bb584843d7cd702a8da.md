### Title
Reachable assertion (uncaught `AssertionError`) when computing offer/spend hints from an untrusted `CREATE_COIN` condition - (File: `chia/wallet/util/compute_hints.py`)

### Summary
`compute_spend_hints_and_additions()` parses `CREATE_COIN` conditions produced by running an untrusted `puzzle_reveal`/`solution` pair, and asserts that the puzzle-hash argument is an atom without first validating its shape, exactly mirroring the TensorFlow advisory's pattern of missing input validation before a `CHECK`/assert that aborts the process.

### Finding Description
`compute_spend_hints_and_additions` runs a coin spend's CLVM (`run_with_cost(cs.puzzle_reveal, max_cost, cs.solution)`) and iterates the resulting conditions. For any `CREATE_COIN` condition it does: [1](#0-0) 

```
if op != ConditionOpcode.CREATE_COIN.value:
    continue
cost += ConditionCost.CREATE_COIN.value

rf = condition.at("rf").atom
assert rf is not None

coin: Coin = Coin(cs.coin.name(), bytes32(rf), uint64(condition.at("rrf").as_int()))
``` [2](#0-1) 

The code assumes the first argument of `CREATE_COIN` (`rf`) is always an atom, but nothing prevents a CLVM program from returning `(51 (a . b) amount ...)` where the first argument is a cons pair instead of an atom. In that case `condition.at("rf").atom` is `None` and the bare `assert rf is not None` raises an uncaught `AssertionError` (CWE-617, reachable assertion), rather than returning a graceful `ValidationError`/`Err` as is done everywhere else in this same function (e.g., the `Err.BLOCK_COST_EXCEEDS_MAX` case a few lines above). This is a direct analog of the TensorFlow `rfft2d`/`rfft3d` CVE-2022-29213: missing shape/type validation of attacker-influenced data before a hard assertion that terminates execution (CWE-20 + CWE-617).

This function is invoked on untrusted, unconfirmed spend data. In particular, `TradeManager.calculate_tx_records_for_offer()` calls it against every coin spend of a counterparty-supplied `Offer`'s `to_valid_spend()` bundle, before the offer has ever been validated by a full node: [3](#0-2) 

Because `Offer` objects (and their embedded puzzle reveals/solutions) are received directly from an offer counterparty (e.g., via an offer file), a wallet user who inspects, previews, or attempts to take a malicious offer will execute the counterparty's puzzle and hit this code path.

### Impact Explanation
An attacker can craft a spend bundle/offer whose puzzle returns a `CREATE_COIN` condition with a non-atom first argument. When a wallet processes that offer (e.g., `take_offer`, `get_offer_summary`, or trade-record calculation), the wallet process raises an unhandled `AssertionError`, crashing wallet transaction processing for that request — a spend-triggered denial-of-service condition against the wallet's offer/trade handling, without requiring any confirmed on-chain spend or privileged access.

### Likelihood Explanation
The condition is trivially reachable: any offer counterparty can construct a puzzle that returns a `CREATE_COIN` condition whose first argument is a pair (e.g., `(51 (1 . 2) 100)`), which is valid, well-formed CLVM output and requires no special puzzle complexity. A user merely inspecting/accepting an untrusted offer triggers the crash.

### Recommendation
Replace the bare `assert rf is not None` with explicit, non-assertion validation that raises a handled error (e.g., `ValidationError(Err.INVALID_CONDITION, ...)`) when the `CREATE_COIN` puzzle-hash argument is missing or not an atom, consistent with the `Err.BLOCK_COST_EXCEEDS_MAX` handling already present in the same function. Apply the same defensive check to `condition.at("rrf")`/`condition.at("rrrff")` accesses that assume atom shape.

### Proof of Concept
1. Construct a CoinSpend whose `puzzle_reveal`, when run against `solution`, returns:
   `((51 (1 . 2) 100))` — i.e. a `CREATE_COIN` condition whose first argument is a cons pair rather than an atom puzzle hash.
2. Wrap it into an `Offer` (or any spend bundle) and have a victim wallet call `TradeManager.calculate_tx_records_for_offer()` (e.g., via `take_offer`/`get_offer_summary`) on it.
3. `compute_spend_hints_and_additions()` executes `condition.at("rf").atom`, which returns `None` since the first argument is a pair, and the subsequent `assert rf is not None` raises an unhandled `AssertionError`, crashing the offer-processing call.
