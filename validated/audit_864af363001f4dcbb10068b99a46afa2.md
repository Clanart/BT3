### Title
`ThresholdKeys::read` deserializes a `secret_share` never bound to the attacker-supplied `verification_shares`/`group_key`, yielding a signing key whose own share is inconsistent with the key it signs under - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` is the deserialization entry point for threshold key material. It reads `t`, `n`, `i`, an interpolation method, a `secret_share` scalar, and `n` verification shares, then constructs `ThresholdKeys` via `ThresholdKeys::new`. `ThresholdKeys::new` computes `group_key` solely from the first `t` verification shares (`verification_shares[i] * interpolation_factor(i, 1..=t)`) and never verifies that `generator() * secret_share == verification_shares[i]` nor that the verification shares lie on a consistent polynomial of degree `t-1`. The result is a `ThresholdKeys` object fully formed from untrusted bytes in which the deserialized secret share is not actually a share of the deserialized group key.

### Finding Description
The bug class (trusted types reconstructed from untrusted bytes without validation, as in the XStream deserialization CVE) maps onto `ThresholdKeys::read` at crypto/dkg/src/lib.rs:574-632:

```rust
let secret_share = Zeroizing::new(C::read_F(reader)?);          // line 618
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);  // 621-623
}
ThresholdKeys::new(
  ThresholdParams::new(t, n, i)...,
  interpolation, secret_share, verification_shares,
)
```

`ThresholdKeys::new` (lines 349-391) only checks:
- `verification_shares.len() == n` and every index `<= n`,
- `t == n` when `Interpolation::Constant` is used.

It then derives `group_key = Σ_{i∈1..=t} verification_shares[i] * interpolation_factor(i, {1..=t})` (line 376-378). Nothing ties `secret_share` to `verification_shares[i]` (the caller's own share). Compare with honest construction paths: `dealer::key_gen` derives `verification_shares` as `G * secret_share` (crypto/dkg/dealer/src/lib.rs:53), and `pedpop` verifies each share against the sender's commitments before building keys (crypto/dkg/pedpop/src/lib.rs:487-491). The deserialization path skips all of this.

Downstream, `ThresholdView`/`SignMachine` use `group_key` for the signature's `R + cA` relation and `verification_shares` for per-share blame. A crafted blob where `verification_shares[1..=t]` define group key `Y` while `secret_share = s'` with `G*s' ≠ verification_shares[i]` produces a "valid" `ThresholdKeys` that signs shares inconsistent with `Y` — or, worse, an attacker can set `verification_shares[i] = G*s'` so this node's share verifies against an attacker-chosen group key while `recover_key`/`complete` behavior diverges across nodes fed different blobs.

### Impact Explanation
An unprivileged party who can cause a `ThresholdKeys` blob to be deserialized (the wire/storage format accepts all fields) can inject keys whose group key, share consistency, and interpolation are entirely attacker-controlled. Consequences include: a node signing under a group key that no honest quorum agreed to; per-participant views of `group_key()` differing across nodes fed distinct serializations of "the same" key set (breaking consensus on the multisig address and enabling funds to be reported received under a key nobody can reconstruct); and `recover_key`/`Interpolation::Constant` paths operating on incoherent shares. This is a concrete integrity failure of the deserialized object, not merely a panic.

### Likelihood Explanation
Exploitation requires an attacker to supply or corrupt a serialized `ThresholdKeys` blob read by a participant (e.g., key material exchanged/persisted outside the PedPoP verification path). The `read` API is a public deserialization entry point explicitly exposed for loading key material, and it performs structural validation (curve ID, canonical encodings, parameter bounds) that implies it is meant to be robust against untrusted input — yet omits the one cryptographic invariant that defines the object. Likelihood is moderate: the input format is fully attacker-malleable where reachable, but reachability depends on an integrator deserializing keys from a non-trusted channel.

### Recommendation
In `ThresholdKeys::new` (or in `ThresholdKeys::read`), additionally verify:
1. `C::generator() * secret_share == verification_shares[&params.i()]` — the deserialized share must match the deserialized verification share for this participant.
2. Optionally, that `verification_shares` interpolate consistently (e.g., `group_key` computed from any `t`-subset agrees), to ensure the shares lie on one polynomial.

### Proof of Concept
```rust
// t = n = 1, i = 1, Lagrange interpolation.
// Provide secret_share = a (attacker-chosen scalar),
// verification_shares = { 1: G*b } with b != a.
// Layout: id_len || C::ID || t=1 || n=1 || i=1 || interp=1 || a || G*b
let mut blob = vec![];
blob.extend(4u32.to_le_bytes());
blob.extend(C::ID);
blob.extend(1u16.to_le_bytes()); // t
blob.extend(1u16.to_le_bytes()); // n
blob.extend(1u16.to_le_bytes()); // i
blob.push(1);                    // Interpolation::Lagrange
blob.extend(a.to_repr().as_ref());
blob.extend((C::generator() * b).to_bytes().as_ref());

let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
// keys.group_key() == G*b, yet original_secret_share() == a, G*a != G*b
assert_ne!(C::generator() * *keys.original_secret_share(), keys.group_key());
```
`read` succeeds and returns a `ThresholdKeys` whose secret share does not correspond to its group key — an object no honest DKG path can produce.
