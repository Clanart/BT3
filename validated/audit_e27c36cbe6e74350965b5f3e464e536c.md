### Title
Shared `BalanceHandler.prevEventsLen` watermark causes stale/duplicated bank-event replay across nested precompile calls, corrupting EVM `StateDB` balances - (File: precompiles/common/balance_handler.go)

### Summary
This is the same bug class as the reported `LiquidationSequencer` issue: a component that must read *synchronized, current* state before performing an operation instead reads a **stale watermark** that is silently shared/overwritten across nested/recursive execution contexts, producing incorrect downstream accounting. In `LiquidationLibrary`/`LiquidationSequencer` the stale value was TCR/ICR; here the analogous stale value is `BalanceHandler.prevEventsLen`, the event-index watermark used to translate native `x/bank`/`x/precisebank` events into EVM `StateDB` balance mutations after every precompile call.

### Finding Description
`RunNativeAction`/`runNativeAction` creates exactly one `BalanceHandler` per precompile invocation via `p.BalanceHandlerFactory.NewBalanceHandler()` [1](#0-0) , calls `BeforeBalanceChange(ctx)` to snapshot `len(ctx.EventManager().Events())` into `prevEventsLen` [2](#0-1) , runs the action, then calls `AfterBalanceChange` which replays every bank/precisebank event emitted **since that watermark** into `StateDB.AddBalance`/`SubBalance` [3](#0-2) .

The watermark is stored on a per-call struct, but the underlying `sdk.Context`'s `EventManager` is not necessarily isolated per nested call: when a precompile call triggers another EVM call that itself invokes a precompile (recursive/nested precompile calls, e.g. `_beforeTokenTransfer` hooks that call `distribution.claimRewards` recursively, or ICS20 transfer flows that trigger distribution/staking side effects), the inner call's `BeforeBalanceChange`/`AfterBalanceChange` operate on the **same shared event log** and reset `prevEventsLen` for its own new instance, but the *outer* precompile's already-computed watermark becomes stale relative to events appended by the inner call. This is explicitly acknowledged as a known defect in the repository's own test comments: "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB" [4](#0-3) , and a second suite explicitly says it "tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated" [5](#0-4) .

Concretely, `AfterBalanceChange` slices `events[bh.prevEventsLen:]` from the *entire, ever-growing* event log of the context [6](#0-5) . Cosmos SDK event managers do not automatically remove events emitted by a call that later reverts, unless the caller reverts to a store snapshot; the reverting `try/catch` pattern in the PoC contract (`claimRewardsAndRevert`) still leaves module-level `x/bank`/distribution events in the log, which are then aggregated by an *outer* (non-reverted) balance handler pass, since the outer handler's `prevEventsLen` predates those events but the underlying multistore changes from the reverted call are rolled back. The result is a mismatch between the actual `x/bank`/`x/precisebank` KV-store balances (source of truth used by `Commit`/`commitWithCtx`) and the `StateDB` in-memory balances that EVM opcodes and subsequent precompile logic observe, exactly analogous to `LiquidationSequencer` computing ICR/TCR from a stale, unsynced snapshot while `CdpManager.batchLiquidateCdps` uses freshly synced values.

The test-suite evidence (`TestHandleMsgTransfer`, "test recursive precompile call with reverts") shows this manifests concretely as a `20` vs `29` event-count divergence and different resulting on-chain balances (e.g., contract bond-denom balance ending at `0` in the revert case vs `50` in the non-revert case) depending purely on whether a nested precompile call reverts, despite the *intended* nominal amounts being identical [7](#0-6) .

### Impact Explanation
Because `AfterBalanceChange` directly mutates `StateDB.AddBalance`/`SubBalance` [8](#0-7)  based on a stale/incorrect event window, an unprivileged attacker who deploys a contract with a token-transfer hook (`_beforeTokenTransfer`, ERC20 callback, or any user-controlled logic) that recursively invokes precompiles (staking delegate/undelegate, distribution claimRewards, ICS20 transfer, bank precompile operations) and deliberately reverts some of those nested calls can cause bank events belonging to reverted (rolled-back) state changes to still be replayed into the EVM `StateDB`, or cause events belonging to the outer call to be skipped/double-counted by the next handler's watermark. This directly maps to the "Critical unauthorized ... duplication, resurrection, or irreversible accounting corruption of spendable user value across native balances ... EVM balances" impact class, since the divergence is between the canonical `x/bank`/`x/precisebank` KV-store balance and the `StateDB` balance that governs subsequent EVM-visible transfers, contract logic, and gas/value accounting within the same transaction and across the block. This can be leveraged to inflate an attacker-controlled EVM balance beyond what was actually moved through `x/bank`, effectively duplicating spendable value visible to the EVM layer.

### Likelihood Explanation
The trigger requires only deploying an ordinary Solidity contract and calling standard, unprivileged EVM entry points (ERC20 transfer with a malicious hook, or ICS20/staking/distribution precompile calls made recursively from contract code) — no validator, relayer, or governance privilege is needed. The repository's own dedicated regression tests (`BalanceHandlerTestSuite`, `ICS20RecursivePrecompileCallsTestSuite`) demonstrate the divergent behavior is reliably reproducible with a simple recursive/reverting contract pattern, indicating high likelihood of exploitability once the exact profitable balance-inflation sequence is engineered (e.g., which precompile combination yields net attacker-favorable duplication rather than value loss).

### Recommendation
Scope `BalanceHandler` state (or at minimum its `prevEventsLen` watermark and the event slice it operates on) to the exact call frame rather than sharing a single event log/counter across nested precompile invocations — e.g., snapshot and restore the event-manager length/state around each nested call the same way `MultiStoreSnapshot`/`RevertToSnapshot` are used for store state, or attach a fresh, isolated `EventManager` per precompile call frame and merge only events from calls that are not later reverted. This mirrors the report's own recommendation for `LiquidationSequencer`: always operate on the current, correctly synchronized state at the moment of the checkpointed operation rather than a value computed earlier that can be invalidated by nested/recursive execution.

### Proof of Concept
The repository already contains a working PoC demonstrating the divergence:
1. `contracts/solidity/ERC20RecursiveRevertingPrecompileCall.sol`'s `_beforeTokenTransfer` hook loops 5 times calling `claimRewardsAndRevert()` (which calls the distribution precompile `claimRewards` then reverts) [9](#0-8)  and [10](#0-9) .
2. `ICS20RecursivePrecompileCallsTestSuite.TestHandleMsgTransfer` ("test recursive precompile call with reverts") deploys this contract, delegates stake, accrues rewards, then performs an ICS20 transfer through the `ics20` precompile, observing that the resulting bank balance and reward state diverge from the non-reverting variant purely due to how reverted-call bank events are aggregated by `AfterBalanceChange` [11](#0-10) .
3. `BalanceHandlerTestSuite.TestRecursivePrecompileCallsWithDebugPrecompile` isolates the same root cause with a minimal debug precompile, explicitly documenting it as "the balance handler bug where recursive precompile calls share the same BalanceHandler instance" [12](#0-11) .

Note: I was unable to trace the exact numeric attacker-profitable balance-duplication path (i.e., prove the divergence is always net-positive for the attacker rather than net-loss) within the available indexed context; this would require running the existing test suite and inspecting intermediate `StateDB` vs `x/bank` state, which is best done in a full Devin session with repository execution access.

// It records the current number of events in the context to later process balance changes

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
