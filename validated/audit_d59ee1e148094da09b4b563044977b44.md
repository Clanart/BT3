### Title
Errored EVM transactions skip sweeping their per-tx coinbase fee balance to the fee collector, stranding paid fees - (File: x/evm/keeper/abci.go)

### Summary
In `x/evm/keeper/abci.go`, `EndBlock` iterates over each transaction's deferred info to sweep the gas fee that was collected into a deterministic, per-transaction-index "coinbase" account (`state.GetCoinbaseAddress(idx)`) into the real fee collector/coinbase address. This mirrors the Sherlock report's pattern: a conditional branch that should only skip *one* piece of bookkeeping instead skips *all* bookkeeping for that code path, so a value the user is owed/expected to be forwarded (their paid gas fee surplus) never reaches its destination and is left sitting in an intermediate holding account instead.

### Finding Description
`EndBlock` processes `evmTxDeferredInfoList` like this: [1](#0-0) 

For every deferred info entry with a non-empty `Error` (meaning the tx failed somewhere in the ante/msg-server pipeline after fees were already bought via `BuyGas`), the loop does `continue` immediately after (optionally) writing a failed receipt — it never reaches the block below that reads `coinbaseAddress := state.GetCoinbaseAddress(idx)` and sweeps `useiBalance`/`weiBalance` from that per-tx coinbase account to the block's `coinbase` (fee collector) via `SendCoinsAndWei`. It also skips `surplus = surplus.Add(deferredInfo.Surplus)`.

The fee itself was already charged and deposited into that same deterministic `coinbaseAddress` earlier in `EvmDeliverChargeFees` → `EvmCheckAndChargeFees` → `st.BuyGas()` (ante pipeline), independent of whether the transaction later errors. In go-ethereum-derived logic, `BuyGas` unconditionally debits the sender and credits the block's fee-collection address before any later validation/logic runs; Sei's `state.NewDBImpl`-backed `stateDB.Finalize()` in `EvmDeliverChargeFees` then persists this transfer: [2](#0-1) 

So the sequence is: fee is bought and lands in `GetCoinbaseAddress(idx)` → a later ante/msg-server step fails and marks `deferredInfo.Error != ""` → `EndBlock`'s early `continue` for the error branch means the funds sitting at `GetCoinbaseAddress(idx)` are never swept out during that block. Unlike the Sherlock bug (where funds are permanently stuck because the crediting statement is skipped by a combined if/else), here the funds are not necessarily lost forever — the same deterministic address will be reused by whatever transaction occupies that same `idx` in a *future* block, and its balance will be swept together with that future transaction's proceeds. But this conflates unrelated transactions' funds, delays the sweep indefinitely (it is only swept whenever some future tx happens to reuse that exact index and succeed), and permanently corrupts total-supply/fee-collector accounting in the interim, exactly the kind of "fee/refund accounting" bug this scan targets.

Notably, this exact bug class is independently corroborated by the repository itself: `x/evm/migrations/fix_total_supply.go` is a one-time migration explicitly written to correct "total supply mismatch caused by mishandled ante surplus": [3](#0-2) 

This confirms that mis-accounted ante/fee surplus (funds not routed to where the protocol's own accounting expects them) has previously caused real total-supply corruption in this exact subsystem, which is the same root-cause category as the reported vault bug: a conditional branch omits a required fund-movement step.

### Impact Explanation
Any errored EVM transaction after fee-charging leaves its already-paid fee stranded at an intermediate, per-index coinbase account rather than being swept into the fee collector during that block's `EndBlock`. This breaks the invariant that all bought gas fees for a block are collected each block, causing:
- Fee-collector under-crediting for the block in which the error occurred (fee revenue effectively "frozen" at an unswept address until happenstance reuse).
- Total-supply accounting drift between `BankKeeper` balances and the EVM module's expected supply, the very class of bug the `FixTotalSupply` migration was created to patch.
- If the specific `idx` is never reused by a later successful transaction (e.g., end of chain life, upgrade, or simply low future traffic at that index), the usei/wei balance at that `GetCoinbaseAddress(idx)` account is permanently unswept and effectively frozen, unreachable through the normal EndBlock flow.

This satisfies the "fee or refund abuse" / permanent freezing acceptance criteria for this scan.

### Likelihood Explanation
Any unprivileged EVM transaction sender can trigger this by submitting a transaction that passes the fee-charging ante decorator (`EVMFeeCheckDecorator.AnteHandle` → `BuyGas`) but fails later in the ante chain or during message-server execution (e.g., nonce race, signature-derived failures processed after fee buy, or panics recovered in `msgServer.EVMTransaction`), producing a `deferredInfo.Error != ""` entry with `TxHash != ethtypes.EmptyTxsHash` and a bumped nonce (`GetNonceBumped`) so it isn't filtered out entirely. No special privileges, governance, or validator collusion is required — an ordinary submitted transaction is sufficient to place funds into this skipped-sweep code path.

### Recommendation
Decouple "recording the failure receipt" from "sweeping the per-tx coinbase balance." In the `deferredInfo.Error != ""` branch, still compute `coinbaseAddress := state.GetCoinbaseAddress(idx)` and perform the same `SendCoinsAndWei` sweep (and `surplus.Add`) that the success path performs, before or after writing the failed receipt, so that every transaction index's coinbase balance is swept every block regardless of whether the transaction ultimately succeeded.

### Proof of Concept
Conceptual repro (cannot be executed in this read-only review, but derivable from the code paths cited above):
1. Craft an EVM transaction whose `GasFeeCap`/`GasTipCap` pass `EVMFeeCheckDecorator.AnteHandle`, so `st.BuyGas()` succeeds and deposits fee funds into `state.GetCoinbaseAddress(idx)` for this tx's index in the block.
2. Arrange for a later ante or msg-server step to fail/panic after fee-buy but still bump the nonce (so `GetNonceBumped` returns true and the entry is not filtered out of `GetAllEVMTxDeferredInfo`), producing a `types.DeferredInfo{TxIndex: idx, TxHash: <hash>, Error: <log>}`.
3. In `EndBlock`, this entry hits the `if deferredInfo.Error != "" && txHash.Cmp(ethtypes.EmptyTxsHash) != 0` branch, writes a failed receipt, and `continue`s — skipping the `SendCoinsAndWei` sweep of `GetCoinbaseAddress(idx)`'s balance into `coinbase`.
4. Query `BankKeeper().GetBalance`/`GetWeiBalance` for `state.GetCoinbaseAddress(idx)` after the block commits: the bought fee remains there instead of at the `fee_collector`/coinbase, and `k.GetAnteSurplusSum` / fee-collector totals under-report the true fee revenue for that block, matching the discrepancy that `FixTotalSupply` was built to fix.

var logger = seilog.NewLogger("x", "evm", "migrations")

// This migration is to fix total supply mismatch caused by mishandled
// ante surplus
func FixTotalSupply(ctx sdk.Context, k *keeper.Keeper) error {
	balances := k.BankKeeper().GetAccountsBalances(ctx)
	correctSupply := sdk.ZeroInt()
	for _, balance := range balances {
		correctSupply = correctSupply.Add(balance.Coins.AmountOf(sdk.MustGetBaseDenom()))
	}
