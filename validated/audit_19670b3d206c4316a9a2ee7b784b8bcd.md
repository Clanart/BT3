### Title
Gasless swap admission check relies on manipulable spot AMM price instead of a stale-price-protected oracle, enabling sandwich-style value extraction from the fee-delegation flow - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The `GaslessModule.checkBalanceForSwap` function validates a user's `SwapForGas` transaction by querying the whitelisted `GaslessSwapRouter`'s `getAmountIn(token, minAmountOut)`, which is a standard UniswapV2-style spot-price read from live pool reserves. This is structurally the same root cause flagged in TRST-H-1: a user-controlled `minAmountOut`/slippage parameter is validated (and, at execution, honored) against an on-chain AMM price with no oracle, no staleness check, and no manipulation resistance, letting a single caller manipulate the reference pool and extract value in one transaction/bundle.

### Finding Description
The gasless flow allows an unprivileged tx sender to pair an `approve()` tx with a `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` tx [1](#0-0) . Before admitting the swap tx into the pool, `checkBalanceForSwap` enforces `tx.amountIn >= gsr.getAmountIn(minAmountOut)` by directly calling the whitelisted router contract with the *current* chain state: [2](#0-1) 

`getAmountIn` is the same style of DEX quoting function shown in the router bindings (`GaslessSwapRouter.GetAmountIn`), which is backed by the underlying AMM pool's reserves via `dexAddress(token)` [3](#0-2) . Unlike the vault's `ChainlinkInterface.getMinReceived` (the report's remediation), there is no Chainlink price feed, no staleness bound, and no sequencer-uptime check backing this admission logic — the check is purely a spot-price read of a swappable pool, exactly the pattern the external report identifies as exploitable via reserve manipulation within a single transaction/bundle.

Because `amountRepay` (funds owed back to the fee-advancing proposer) is only required to be `<= minAmountOut` [4](#0-3) , and `minAmountOut` itself is only validated against a manipulable spot price rather than a robust oracle-derived fair value, a sender can transiently skew the whitelisted pool's reserves (e.g., via an adjacent transaction in the same block/bundle, which the auction/bid module explicitly supports by allowing a bundle `[BidTx]` to execute immediately after a target tx [5](#0-4) ) to make `getAmountIn` return an artificially low quote. This lets a `swapForGas` call pass admission and execute with a `minAmountOut`/`amountIn` ratio that does not reflect fair market value, mirroring the vault's `receiveAmtMin=0`-style drain: the safety parameter is present but derived from a price source the caller can move.

### Impact Explanation
The gasless/fee-delegation mechanism exists specifically to let a token-holder without KAIA pay for gas by swapping tokens through a trusted router; the `amountRepay` value is what makes the proposer/relayer whole for advancing gas. If the swap's fairness check can be defeated by pool manipulation, the value distributed at swap completion (`SwappedForGas(proposer, amountRepaid, user, finalUserAmount, commission)` [6](#0-5) ) can be skewed to shortchange either the repaying proposer or the protocol commission, i.e., direct fee-delegation/gasless-settlement value abuse, which falls squarely in the "gasless and auction modules" abuse category called out as in-scope.

### Likelihood Explanation
The whitelisted DEX pools backing `GaslessSwapRouter` are ordinary AMM pools (UniswapV2-style, as used in `tests/gasless_test.go` with `UniswapV2Router02`/`UniswapV2Factory` [7](#0-6) ), which are generally shallow/permissionless and can be manipulated with a flashloan or large swap in the same block, especially when combined with the auction module's guaranteed same-block bundle execution right after a target transaction. No special privilege is required — only a wallet capable of sending an approve+swap pair and a way to move the pool (a normal DEX swap).

### Recommendation
Apply the same mitigation the vault adopted: back `minAmountOut`/`amountIn` validation for gasless swaps with an oracle-derived fair-value bound (with staleness and, if run on L2, sequencer-uptime checks) rather than relying solely on the whitelisted router's live spot-price quote, or otherwise bound the allowed deviation between `getAmountIn`'s quote and a TWAP/oracle reference before admitting/executing `swapForGas`.

### Proof of Concept
1. Attacker holds token `T` whitelisted in `GaslessModule` and has a large capital position (or flashloan access) able to swap heavily against the whitelisted `T`/KAIA pool used by `GaslessSwapRouter`.
2. In the same block (optionally using the auction module's bundle mechanism to guarantee ordering), attacker skews the pool reserves to depress `getAmountIn(T, minAmountOut)`'s quoted requirement.
3. Attacker submits `approve` + `swapForGas(T, amountIn, minAmountOut, amountRepay, deadline)` where `amountIn` and `minAmountOut` are set to just satisfy `checkBalanceForSwap`'s `amountIn >= getAmountIn(minAmountOut)` and `minAmountOut >= amountRepay` checks under the manipulated price [8](#0-7) .
4. Attacker reverses the pool manipulation later in the same block, having obtained a swap outcome inconsistent with fair market value, at the expense of the proposer/commission pool that relied on `minAmountOut` as a fairness bound.
