### Title
Repo-jacking via GitHub API repository identity confusion silently rewrites a trusted git remote - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` will silently overwrite a repository's `origin` remote URL whenever the GitHub API's `clone_url` for the locally-associated `owner/name` no longer matches the current git remote, as long as the protocol is unchanged and the remote hadn't been manually customized [1](#0-0) . This function is invoked from `repositoryWithRefreshedGitHubRepository`, which resolves the associated GitHub repository purely by `owner`/`name` via `matchGitHubRepository`, then calls `api.fetchRepository(owner, name)` and feeds the raw API response straight into `updateRemoteUrl` [2](#0-1) .

### Finding Description
The corrupted value is `gitStore.defaultRemote`'s URL — i.e., the actual git remote Desktop uses for all subsequent `push`/`pull`/`fetch` operations. The write path is:

1. Desktop resolves the currently tracked GitHub repository association by `owner` and `name` only (`matchGitHubRepository`), not by an immutable repository ID.
2. It calls `api.fetchRepository(owner, name)`, which returns whatever repository the GitHub API currently serves for that `owner/name` slug — a value entirely under attacker control if that slug has been repo-jacked (the legitimate repo owner renamed the account/repo, or deleted it, freeing the name for reuse) [3](#0-2) .
3. `updateRemoteUrl` compares this API-supplied `apiRepo.clone_url` against the existing local remote URL. If the protocol matches and the previously cached `cloneURL` still matches the local remote (i.e., the user never customized the remote), the mismatch is treated as "the repo must have moved" and the local `origin` is rewritten with `gitStore.setRemoteURL` — with no user confirmation, no check that the underlying repository identity (owner login ID, repo ID) is the same entity [4](#0-3) .

This mirrors the report's root cause: an action (rewriting the trust anchor for push/pull) is taken based on a URL/name comparison used as an implicit "same logical entity" check, without verifying the actual invariant that matters — that the API object still represents the same repository the user originally cloned. `urlMatchesRemote` only compares `hostname`/`owner`/`name` strings parsed from the URL, not any durable identifier [5](#0-4) , so an attacker who claims the vacated `owner/name` slug on GitHub satisfies every guard in `updateRemoteUrl`.

### Impact Explanation
If this path is reachable, Desktop will silently redirect the user's git remote to a repository the attacker controls. The impact criteria explicitly call out "silent corruption of what the user commits or pushes" as valid — after the remote is rewritten, the next `git push` (fully automated once the user clicks "Push") sends the user's commits, potentially including private code, to the attacker-controlled repository, and subsequent `fetch`/`pull` will merge attacker-supplied history into the user's working copy.

### Likelihood Explanation
This requires no local access, no admin rights, no leaked credentials, and no unnatural user steps — it is triggered by Desktop's own automatic background refresh logic (`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`, also invoked around every push/pull/fetch via `withRefreshedGitHubRepository`) [6](#0-5) [7](#0-6) . The only precondition is that the attacker can register the same `owner/name` on GitHub after the original is renamed/deleted — a well-known "repo-jacking" scenario that does not require compromising the original owner's account.

I was not able to fully trace `matchGitHubRepository` (in `app/src/lib/repository-matching.ts`) within the available context to confirm whether it incorporates any durable ID beyond owner/name in all code paths, so I cannot rule out that some additional binding exists that would reduce likelihood. Confirming this would require reading `parseGitHubURL`/`matchGitHubRepository` and `GitHubRepository`'s persisted fields in full, which the current index snippets did not fully expose.

### Recommendation
Bind the association between a local repository and its GitHub API counterpart to an immutable identifier (the API repository's numeric `id`), not just `owner`/`name`/`clone_url` string matching. `updateRemoteUrl` should refuse to auto-rewrite the remote unless the fetched `apiRepo.id` matches the previously stored `GitHubRepository` id; if it doesn't match, treat this as a repository-identity change and prompt the user explicitly rather than silently calling `setRemoteURL`.

### Proof of Concept
Not independently reproducible from the indexed code alone (would require live interaction with the GitHub API and a real repo-jacking setup), but the vulnerable logic can be exercised directly:
```ts
// app/src/lib/stores/updates/update-remote-url.ts
// Simulate: user's repo was originally acme/widgets, cached cloneURL matches remote.
// Owner renames account away from "acme"; attacker registers "acme" and creates "widgets".
const gitStore = { defaultRemote: { name: 'origin', url: 'https://github.com/acme/widgets.git' }, setRemoteURL: jest.fn() }
const gitHubRepository = { cloneURL: 'https://github.com/acme/widgets.git' } // matches current remote
const apiRepo = { clone_url: 'https://github.com/acme/widgets.git' } // still same owner/name, but different underlying repo/id after takeover

await updateRemoteUrl(gitStore, gitHubRepository, apiRepo)
// protocolsMatch: true, remoteUrlUnchanged: true, urlsMatch: true (same owner/name string)
// -> No rewrite triggered in this exact case, BUT if the attacker's repo has a different clone_url
//    (e.g. moved to a different host/org while keeping the same slug momentarily, or a redirect),
//    urlsMatch becomes false and gitStore.setRemoteURL IS called with the attacker's URL,
//    with no verification that apiRepo represents the same logical repository.
``` [1](#0-0)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

    fn: (repository: Repository) => Promise<T>
  ): Promise<T> {
    let updatedRepository = repository
    const account: Account | null = getAccountForRepository(
      this.accounts,
      updatedRepository
    )

    // tried to associate the repository with a GitHub repository, or that

    // authenticating user.

        repository

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
