### Title
Unbounded recursion parsing untrusted on-chain custody memos causes wallet stack-consumption DoS - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
CVE-2019-9903 is a stack-consumption bug caused by Poppler recursively marking/traversing an attacker-controlled nested PDF `Dict` structure without a depth bound, exhausting the process stack. The analogous bug class in this codebase is unbounded, depth-unlimited Python recursion while reconstructing an attacker/coin-creator-controlled nested puzzle "memo" structure that a wallet parses when syncing an unknown custody puzzle from chain, in `PuzzleWithRestrictions.from_memo()`.

### Finding Description
`PuzzleWithRestrictions.from_memo()` reconstructs a `PuzzleWithRestrictions` tree from a CLVM `Program` memo that was read from on-chain data (this is explicitly documented as reconstructing "unknown members/restrictions, including recursive MofN, so later wallet code can fill known puzzle implementations by puzzle hash" — see `.cursor/context/testing/clvm.md:63`). [1](#0-0) 

The method decodes `further_branching_prog`/`puzzle_hint_prog` and, when the memo encodes a nested `MofN` structure, calls `MofNHint.from_program()` and then recurses by calling `PuzzleWithRestrictions.from_memo(memo)` once per member:

```
if further_branching:
    m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
    puzzle: MIPSComponent = MofN(
        m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
    )
```

There is no depth check, no iteration limit, and no bound on how many times a `MofN` member can itself be a nested `MofN`. `MofNHint.from_program()` places no restriction on `member_memos` content either: [2](#0-1) 

This directly parallels the CVE's root cause: `Dict::find()`/`markObject` recursed into attacker-nested dictionaries without a recursion cap. Here, `from_memo` recurses into attacker-nested `MofN` memos without a recursion cap. The codebase elsewhere is explicitly careful about this exact class of bug — `sha256_treehash` in `chia/types/blockchain_format/tree_hash.py:1-7` states it is deliberately implemented non-recursively "so we don't have to worry about blowing out the python stack," and the Data Layer's Rust `MerkleBlob` insertion path raises a dedicated `chia_rs.datalayer.RecursionDepthExceededError` for deeply nested untrusted trees (`chia/_tests/core/data_layer/test_data_store.py:1764`). `from_memo()` has no equivalent protection.

### Impact Explanation
A coin's custody memo (used by `PuzzleWithRestrictions.memo()`/`from_memo()` for CHIP-0043 custody puzzle sync, referenced from `chia/pools/plotnft_drivers.py`) is attacker-controlled content that any spend-bundle submitter can embed in a coin. A wallet or pool-participant client that later syncs and reconstructs an unknown inner puzzle by calling `from_memo()` on a deeply nested `MofN` memo (e.g., thousands of levels of `MofN(members=[MofN(members=[...])])`) will recurse once per nesting level in pure Python, exhausting the interpreter's call stack and crashing the wallet process (`RecursionError`) or, depending on platform stack limits, causing a native stack overflow. This is a spend-triggered transaction-processing halt on the wallet-sync path — a legitimate Medium-severity DoS analog of CVE-2019-9903, reachable purely by submitting/propagating a coin with a maliciously crafted memo that an unprivileged wallet later chooses to inspect.

### Likelihood Explanation
Likelihood is moderate: constructing a deeply nested `MofN`/`RestrictionHint` memo program is straightforward CLVM construction requiring no special privileges, and the memo need only be attached to a coin that a wallet subsequently attempts to sync as an "unknown" custody puzzle (a normal wallet behavior per the custody-architecture design). No signature or on-chain acceptance of a spend is strictly required to deliver the malicious memo to the parsing code path if any client-side tooling ingests attacker-supplied puzzle-hint data before submission/acceptance; at minimum it is reachable once such a coin is created and observed on chain.

### Recommendation
Add an explicit recursion/depth limit (or convert `from_memo`/the `MofN` reconstruction to an iterative, stack-based traversal similar to `sha256_treehash`) before recursing into nested member memos, and reject memos whose nesting exceeds a sane bound (e.g., mirroring the `RecursionDepthExceededError` bound used in `chia_rs.datalayer` for Merkle trees).

### Proof of Concept
1. Construct a `PuzzleWithRestrictions` whose `puzzle` field is a deeply nested `MofN` (e.g., `MofN(m=1, members=[PuzzleWithRestrictions(..., puzzle=MofN(m=1, members=[...]))])`) recursed to a depth in the tens of thousands, mirroring the pattern already exercised (at small depth) in `chia/_tests/clvm/test_custody_architecture.py:83-116`.
2. Call `.memo()` to obtain the corresponding CLVM `Program` memo bytes.
3. Attach/broadcast that memo as coin hint data associated with a coin puzzle hash.
4. Have a wallet client that reconstructs unknown custody puzzles call `PuzzleWithRestrictions.from_memo(memo)` on the retrieved program; the recursive member reconstruction loop will exhaust the Python call stack and raise `RecursionError`, halting wallet processing of that sync path.

@dataclass(kw_only=True, frozen=True)
class MofNHint:
    m: int
    member_memos: list[Program]

    def to_program(self) -> Program:
        return Program.to([self.m, self.member_memos])

    @classmethod
    def from_program(cls, prog: Program) -> MofNHint:
        m, member_memos = prog.as_iter()
        return MofNHint(
            m=m.as_int(),
            member_memos=list(member_memos.as_iter()),
