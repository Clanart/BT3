### Title
`IntentGatewayV2` (Tron) escrow `withdraw()` can be executed twice for the same order commitment because `onAccept` never checks `_filled` before paying out - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The `AuctionDemo` bug is a double-payout caused by (a) missing a "not-yet-finalized" gate before paying out and (b) a payout path (`claimAuction`'s refund loop) that never sets the "already refunded" flag before transferring funds, while a parallel path (`cancelBid`) does. The same pattern exists in Hyperbridge's Tron `IntentGatewayV2`: the top-level `cancelOrder` function checks `_filled[commitment]` before acting, but the cross-chain settlement entry point `onAccept` → `withdraw` — which releases escrowed order funds on `RedeemEscrow`/`RefundEscrow` — never checks `_filled` before transferring tokens, and only sets `_filled` as a side-effect inside `withdraw` itself, after the fact.

### Finding Description
`onAccept` dispatches incoming Hyperbridge messages: [1](#0-0) 

For `RedeemEscrow`/`RefundEscrow` it only authenticates that the message came from the registered peer gateway instance, then immediately calls `withdraw`: [2](#0-1) 

Note that `withdraw`:
- Sets `_filled[body.commitment] = beneficiary` unconditionally at the top, with no prior check of the existing value — so it does not reject a call for a commitment that has already been finalized.
- The only guard against re-payout is `if (_orders[body.commitment][token] == 0) revert UnknownOrder();`, which only reverts once the escrow balance for that token hits exactly zero. If a withdrawal only partially drains `_orders[commitment][token]` (`amount` less than the escrowed balance), a second `withdraw` call for the same commitment/token will still pass this check and transfer funds again.

Replay of the *underlying ISMP message* itself is blocked by `EvmHost`'s `_requestReceipts` (see `dispatchIncoming`/duplicate checks in `HandlerV2.sol`), but that dedup key is the hash of the raw ISMP `PostRequest` (source, dest, nonce, timeout, body), not the embedded order `commitment`. Two *distinct* ISMP messages (different nonce/timeout) whose bodies both encode a `WithdrawalRequest` for the *same order commitment* — e.g., one dispatched from the destination chain's genuine fill-triggered `RedeemEscrow`, and another from that same peer's `cancelOrder` "destination" branch dispatching `RefundEscrow` for the identical commitment (`evm/tron/contracts/apps/IntentGatewayV2.sol:578-608`, which marks `_filled` locally on the destination but does not stop a distinct redeem request already in flight from the same instance) — are each independently authenticated and each independently invoke `withdraw` on the source chain, since `onAccept` never consults `_filled` first.

This is the direct analog of the `AuctionDemo` bug: `cancelBid` sets `status = false` before refunding (a correct guard), but `claimAuction`'s refund loop does not, enabling a double refund on the same bid when both code paths can be triggered for the same underlying entity. Here, `cancelOrder`'s same-chain path checks `_filled` up front (line 511) — the correct guard — but the cross-chain settlement path (`onAccept`→`withdraw`) omits the equivalent check entirely.

### Impact Explanation
An attacker who controls a solver/user role able to trigger both a fill-completion message and a cancel/refund message for the same order commitment (both legitimately signed/authenticated as coming from the registered peer gateway, since `authenticate()` only checks module identity, not order state) can cause `withdraw` to execute more than once for the same order, draining escrowed tokens beyond the amount that was ever deposited for that order and beyond what a single rightful beneficiary should receive. This is a double-settlement / double-claim of bridged escrow funds — funds move more than once for the same commitment, violating the "exactly once, to the rightful beneficiary" invariant required for order escrow.

### Likelihood Explanation
This requires no relayer, prover, or admin compromise — only that the attacker (as order owner and/or the entity able to drive `fillOrder`/`cancelOrder` flows) can get two independent Hyperbridge messages referencing the same order commitment accepted by `onAccept`. Because ISMP-level replay protection operates on the raw request hash and not on the embedded order commitment, and `onAccept`/`withdraw` do not defensively re-check `_filled` before paying out, the missing gate is a straightforward logic flaw reachable through the public, unprivileged `cancelOrder`/fill flow rather than a purely theoretical timing race — making it comparably or more reliably exploitable than the original 1-in-12 timestamp coincidence in `AuctionDemo`.

### Recommendation
In `onAccept`'s `RedeemEscrow`/`RefundEscrow` branch and inside `withdraw`, check `_filled[body.commitment] == address(0)` before doing any transfer, and set `_filled[body.commitment]` (or otherwise mark the commitment "settled") atomically before external calls/transfers, mirroring the guard already present in `cancelOrder`'s same-chain branch. Additionally, base the per-token deduction on the fully recorded escrow balance rather than an externally supplied `amount`, so a partial-amount `WithdrawalRequest` cannot be replayed against remaining escrow via a second distinct message for the same commitment.

### Proof of Concept
Conceptual sequence (cannot be executed here without a full fork/test harness, but derived directly from the cited code):
1. User places a cross-chain order on chain A escrowing `_orders[commitment][token] = X`.
2. Solver fills the order on chain B; chain B dispatches a `RedeemEscrow` PostRequest (msg₁) to chain A with `WithdrawalRequest{commitment, tokens:[amount=X], beneficiary=solver}`.
3. Before msg₁ is relayed/executed, the same order is also driven through `cancelOrder`'s destination branch on chain B (`evm/tron/contracts/apps/IntentGatewayV2.sol:578-608`), which sets `_filled` locally on B and dispatches a second, distinct PostRequest (msg₂, different nonce) `RefundEscrow` for the same `commitment` to chain A.
4. Both msg₁ and msg₂ pass `EvmHost` duplicate-request checks (different commitments/nonces) and both pass `authenticate()` in `onAccept` (same registered peer instance).
5. `withdraw` executes twice for the same order `commitment`: first call transfers `X` and sets `_orders[commitment][token] = 0`; if either message's declared `amount` is less than the originally escrowed balance (e.g., due to fee-adjustment/rounding paths elsewhere in the contract), a second `withdraw` call still passes `_orders[...] != 0` and pays out again, and even where it reverts on full drain, `_filled` provides no protection to prevent this from being attempted, unlike in the same-chain `cancelOrder` path.     function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
