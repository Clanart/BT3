### Title
Recursive precompile calls share a single `BalanceHandler` instance, corrupting EVM `StateDB` balances relative to the native bank ledger - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
`Precompile.RunNativeAction` / `runNativeAction` creates a `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()` and uses `bh.prevEventsLen` (an event-index watermark) to slice out the bank events emitted during that specific call so they can be replayed onto the EVM `StateDB` (`AddBalance`/`SubBalance`). When a precompile call re-enters the EVM and triggers another call into the *same* precompile address (recursion/callback, e.g. via `CallEVMWithData` back into a contract that calls the precompile again, or nested calls between precompiles/contracts), the inner call's `BeforeBalanceChange` overwrites the shared `prevEventsLen` watermark before the outer call's `AfterBalanceChange` runs, causing the outer call to slice the wrong (too-short or too-long) event range. This produces desynchronization between the bank keeper's actual balances and the EVM `StateDB`'s cached balances.

This is the direct Cosmos-EVM analog of the "stale factors" bug class: a value (`prevEventsLen`) computed at one point in time is consumed later by a different execution context in a call graph without being aware that the value has since been mutated by a nested/recursive invocation, causing incorrect derived state (here, `StateDB` balances rather than a rebalance target amount).

### Impact Explanation
`StateDB.AddBalance`/`SubBalance` directly determines the EVM-visible native balance of every account for the remainder of the transaction (and, upon `Commit()`, is written back via `commitWithCtx`, see `x/vm/statedb/statedb.go:713-745`). If the sliced event window is wrong:
- Events can be double-counted (processed by both the inner and outer `AfterBalanceChange` due to overlapping windows), causing `AddBalance`/`SubBalance` to apply the same bank transfer twice to `StateDB` — i.e. duplication/unauthorized creation of spendable EVM balance without a corresponding bank-side movement.
- Events can be skipped entirely (window advanced past them by the inner call), causing `StateDB` to never reflect a real balance decrease/increase, permanently desynchronizing EVM-visible balances from the canonical bank ledger and enabling accounting corruption that can manifest as free balance credit to an attacker-controlled contract or permanent loss/freezing of the counterparty's expected balance.

Both outcomes match the required Critical impact class: "unauthorized minting, burning, duplication, ... or irreversible accounting corruption of spendable user value across native balances, EVM balances ... or precompile-mediated assets," since `StateDB.Commit()` persists the corrupted balance back to the account keeper.

### Likelihood Explanation
The trigger is a normal, unprivileged EVM transaction: any contract that recursively/nestedly invokes a stateful precompile (directly or through a callback pattern) reaches this code path. The repository's own test (`TestRecursivePrecompileCallsWithDebugPrecompile`) demonstrates the recursive-call scenario succeeds without reverting and produces an event count inconsistent with expectations, confirming the code path is reachable via ordinary transaction execution and is not gated by any privileged role. Any production precompile built on `cmn.Precompile.RunNativeAction` (staking, distribution, gov, slashing, erc20, ics20 — all wired via `BalanceHandlerFactory`, see grep of `BalanceHandler` usage across `precompiles/distribution/distribution.go`, `precompiles/erc20/erc20.go`, `precompiles/gov/gov.go`, `precompiles/ics20/ics20.go`, `precompiles/slashing/slashing.go`, `precompiles/staking/staking.go`) is exposed if a contract can force nested/recursive precompile invocation during its execution (e.g., precompile call triggers a bank send whose recipient is a contract with a fallback that re-enters the same or another precompile, or ICS20 transfer triggering IBC callbacks that re-enter precompiles).

I could not fully verify from the index alone whether every production precompile path can be driven into true reentrancy (vs. only the debug precompile used for the PoC) or whether `MaxPrecompileCalls`/journal-based reverts fully mask the corrupted balances in all cases — that would require running the referenced test suites and tracing specific production precompile call graphs (e.g., ERC20 `transfer` triggering a contract recipient hook, or ICS20 callbacks) end-to-end, which needs execution rather than static reading.

### Recommendation
Make the balance-event watermark and replay scoped per call-frame rather than shared mutable state on the handler:
- Push/pop `prevEventsLen` on a stack (or pass it as a return value from `BeforeBalanceChange` that the caller threads through explicitly) so that a nested call's `BeforeBalanceChange`/`AfterBalanceChange` pair cannot overwrite the watermark of an outer, still-in-flight call.
- Alternatively, snapshot the event slice length locally within `runNativeAction` (not on the shared handler struct) and pass it explicitly to `AfterBalanceChange`, eliminating the shared mutable field entirely.
- Add invariant checks that total balance-changing events processed across nested precompile calls in a transaction reconcile exactly once against the bank keeper's final balances before `StateDB.Commit()`.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.4;

contract DebugPrecompileCaller {
    address constant debugPrecompile = 0x0000000000000000000000000000000000000799;
    error CallFailed(bytes data);
    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }
        }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));
        if (!result) {
            revert CallFailed(data);
        }
    }
}
