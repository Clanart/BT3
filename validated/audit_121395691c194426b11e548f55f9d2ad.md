## Title
Copilot conflict-resolution writes/stages attacker-influenced file content for paths that were never part of the conflict - (File: `app/src/lib/stores/app-store.ts`)

## Summary
`_applyCopilotConflictResolutions` iterates the AI-generated `copilotResolutions` list and, for every entry that is not a delete-vs-modify case, only checks that the target path resolves *inside the repository* before writing it to disk and staging it. It never checks that `resolution.path` actually corresponds to one of the files that were part of the current merge/cherry-pick/rebase conflict set. This mirrors the `BlockhashRegistry.recreateBlockheaders` flaw: the function trusts an externally supplied list without validating that its members are legitimate inputs for the state-changing operation it performs, so it silently writes/commits data the user never reviewed.

## Finding Description
`_startCopilotConflictResolution` sends the repository's conflicted files to an AI conflict-resolution backend and stores whatever `resolutions` array comes back in `copilotResolutions` [1](#0-0) . When the user clicks "Continue Merge", `_applyCopilotConflictResolutions` writes each resolution to disk: [2](#0-1) 

The only gate before `writeFile` is `resolveWithin(repository.path, resolution.path)`, which merely prevents path traversal outside the repo — it does not verify that `resolution.path` names a file that is actually a member of `conflictState`/the conflicted `workingDirectory.files`. The subsequent `onDiskFile` lookup is used exclusively to detect the case where a *conflicted* file was externally resolved (`isConflictedFileStatus` / `hasUnresolvedConflicts`); if `onDiskFile` is `undefined` (i.e., the path isn't even a changed/conflicted file at all), that guard is simply skipped and the function proceeds straight to `writeFile` + staging via `git add`.

This is structurally identical to the reported bug: `recreateBlockheaders` trusted `_blockheaders` to be well-formed and non-empty and proceeded to write `blockhashMapping` and emit an event without validating the input actually represented a legitimate change. Here, `copilotResolutions` (content ultimately derived from AI-model output that itself processes attacker-controlled repository content — e.g. conflict markers/file contents from a malicious fork or branch) is trusted to only reference files that are part of the conflict, and the function writes to disk and stages for commit without re-validating that invariant.

## Impact Explanation
Because `resolveWithin` only enforces "inside the repo," and the resolution set is not cross-checked against the actual conflicted-file list, a manipulated/hallucinated resolution entry can:
- Silently overwrite the content of an unrelated tracked file in the repository (not shown to the user as part of the conflict UI, since the result dialog only lists the files GitHub Desktop asked Copilot to resolve) and stage it — i.e. silent corruption of what the user is about to commit/push, matching the "Valid Impact" criteria explicitly.
- If the AI backend's output path lands on a sensitive tracked path within the working tree, the write could alter files the user did not intend to modify at all, with no diff review step for that path before staging (`git add -- <path>` happens automatically once `pathsToStage` is non-empty) [3](#0-2) .

I could not confirm within the available index whether `resolveWithin` additionally special-cases `.git/` internals (e.g., hooks) or symlinked paths, so I cannot assert whether this escalates to code execution via git hooks — that would need to be verified against the implementation of `resolveWithin` (not found in the indexed portions I could inspect) in a full checkout.

## Likelihood Explanation
The attack surface is realistic under the report's threat model: an attacker who controls a cloned/fetched repository can craft conflict content (including prompt-injection-style text in the conflicting hunks) that influences the AI resolution output, since the resolution set for a given conflict is not re-validated against the actual set of conflicted files before being written to disk. The existing delete-vs-modify branch does perform a `workingDirectory.files.find` membership check [4](#0-3) , showing the developers intended such validation for one code path but omitted the equivalent "is this actually a conflicted file" check for the main content-write path.

## Recommendation
Before writing any `resolution.resolvedContent` to disk, verify `resolution.path` is a member of the set of files that were actually part of the current conflict (`conflictState`/`workingDirectory.files` conflicted entries), not merely that the path resolves inside the repository. Reject and log/skip any resolution whose path was not part of the original conflict set, mirroring the membership check already used in the delete-vs-modify branch.

## Proof of Concept
1. Attacker sets up a repository/branch such that merging/rebasing it produces a conflict, embedding manipulative content in the conflicting hunks intended to influence the Copilot resolution model.
2. Victim uses Desktop's "Resolve with Copilot" flow; `_startCopilotConflictResolution` stores whatever `resolutions` the backend returns in `copilotResolutions`.
3. Victim clicks "Continue Merge" → `_applyCopilotConflictResolutions` runs; for a resolution entry whose `path` is not one of the conflicted files (but still resolves inside the repo), the `onDiskFile` lookup returns `undefined`, the "already resolved" skip is bypassed, and `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` executes, followed by `git add` staging that content [5](#0-4) .
4. The victim commits, believing only the shown conflicted files were touched, while an unreviewed file's content has been silently altered and included in the commit/push.
