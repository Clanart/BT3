### Title
Duplicate-token input legs let a solver drain another leg's escrow on partial-fill completion - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntrinsicIntents._fillSameChain` computes the escrow amount to release for a completed output leg by reading the *entire* current `_orders[commitment][token]` balance instead of the amount specifically allotted to that leg (`order.inputs[i].amount`). This mirrors the GNTDeposit `batchTransfer` flaw: a shared bucket (there, `balances[msg.sender]`; here, `_orders[commitment][token]`) is written/read as if it belonged to a single loop iteration, when in fact multiple entries (legs) can alias the same key.

### Finding Description
In `_fillSameChain` [1](#0-0) , when a leg's fill amount reaches `totalRequired` (i.e. `amountFilled == totalRequired`), the code does:

```
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

`_orders[commitment][token]` is a single mapping bucket keyed only by `(commitment, token)`, populated during `placeOrder` by summing every input entry that references that token: `_orders[commitment][token] += reducedInputs[i].amount;` for each `i` in `order.inputs`. If an order legitimately has two output legs whose corresponding input entries reference the **same token** (e.g. `order.inputs[0].token == order.inputs[2].token == DAI`, escrowed 100 and 50 respectively), the placement step stores `_orders[commitment][DAI] = 150` — a combined figure with no per-leg attribution.

When a solver fully fills leg 0 (single fill, `alreadyFilled == 0`, `solverAmount >= totalRequired`), the "fully filled" fast path reads the *whole* `_orders[commitment][DAI]` value (150) as the escrow to release for that leg, rather than the 100 that was actually earmarked for leg 0. `_withdraw`/`withdraw()` in `IntentsBase.sol` then decrements `_orders[commitment][DAI]` by that full amount and transfers it to the solver: [2](#0-1) . This zeroes out the bucket before leg 2 (which shares the DAI token) can ever be filled — the second leg's fill attempt hits `if (escrowed == 0) revert UnknownOrder();` and reverts, but by then the first solver has already been paid the DAI meant for leg 2 as well.

The existing "insufficient balance" guard (`escrowed == 0` / Solidity 0.8 checked-subtraction underflow) only prevents a raw double-spend of the *same* leg; it does not stop one leg's completion from mis-attributing and draining a co-located token bucket that belongs to a sibling leg.

### Impact Explanation
A single solver who completes just one leg of a multi-leg, same-chain order can receive escrowed input tokens that were reserved for a *different* leg, as long as the two legs' `order.inputs[i].token` values coincide. This is a direct loss/misdirection of escrowed user funds: the user's DAI meant to pay a different filler for a different output leg is instead paid out to the solver who only delivered one leg's output, and the sibling leg becomes permanently unfillable (its escrow was already drained), which is effectively a stuck/lost order for any solver expecting to fill it. This matches the bounty's "stealing or loss of funds" and "wrong beneficiary or amount" categories in the Hyperbridge Impact Gate.

### Likelihood Explanation
No privileged actor, relayer, or governance action is required — any user placing an order (their own choice, not attacker-forced) with two output legs whose input entries share a token triggers the aliasing at placement time, and any solver (unprivileged, permissionless) fully filling the first such leg triggers the over-release. Nothing in `placeOrder` or `fillOrder` rejects duplicate `order.inputs[i].token` values across legs, so the precondition is fully attacker/solver-reachable through the public `placeOrder`/`fillOrder` entrypoints. The scenario requires a specific order shape (duplicate input token across legs) but no exotic timing, malicious peer, or trusted-role assumption — matching the report's own "high difficulty, single-actor-triggerable" profile.

### Recommendation
Attribute escrow per-leg instead of per-token-bucket: track `_orders[commitment][token]` releases against the specific `order.inputs[i].amount` for that leg (e.g., maintain a per-`(commitment, i)` remaining-escrow accounting, or subtract `order.inputs[i].amount - alreadyReleased[i]` rather than reading the whole shared mapping value), or alternatively reject orders at `placeOrder` time whose `inputs[].token` values are not distinct across output legs — analogous to adding `require(addr != msg.sender)` in the original report, i.e., add an explicit uniqueness/ownership check before allowing the aggregated bucket to be treated as a single leg's balance.

### Proof of Concept
1. User calls `placeOrder` with two output legs and matching `order.inputs`:
   - `order.inputs[0] = {token: DAI, amount: 100}`, `order.output.assets[0] = {token: X, amount: A}`
   - `order.inputs[1] = {token: DAI, amount: 50}`, `order.output.assets[1] = {token: Y, amount: B}`
   - Placement stores `_orders[commitment][DAI] = 150` via the summing `+=` loop [3](#0-2) .
2. Solver S1 calls `fillOrder` supplying only enough output token `X` to satisfy leg 0 in full (`solverAmount >= A`), and 0 (or a non-satisfying amount) for leg 1.
3. In `_fillSameChain`, leg 0 hits `amountFilled == totalRequired`, so `escrowedAmount = _orders[commitment][DAI] = 150` (not 100).
4. `_withdraw` pays S1 the full 150 DAI and zeroes `_orders[commitment][DAI]`.
5. Any subsequent solver S2 attempting to fill leg 1 for output token `Y` calls `fillOrder`; when it reaches the escrow-release step for `DAI`, `_orders[commitment][DAI] == 0`, causing `withdraw()`/`_withdraw` to revert with `UnknownOrder()` — leg 1 can never be filled, and the 50 DAI meant for it has already left the contract to S1.
