## Analysis

The reported bug pattern is a **narrow validation invariant that assumes only one specific "shape" of untrusted output, but the guard's logic (`&&` combining two independent conditions) lets a partially-malformed variant slip through**, leading to a state the code never intended to allow. The closest analog in this codebase is in the AI-assisted merge-conflict resolution feature (`app/src/lib/copilot-conflict-resolution.ts`), where a similarly narrow guard is meant to reject any leftover conflict markers in the LLM's output before it is spliced verbatim into a file that the user is about to commit.

### The broken invariant

`parseCopilotConflictResolution` is supposed to reject any hunk resolution that still contains unresolved conflict markers before it gets spliced into the working file:

```ts
const rc = hunkObj.resolvedContent
if (/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)) {
  throw new CopilotValidationError(...)
}
``` [1](#0-0) 

This check only throws when **both** an opening marker (`<<<<<<<`) *and* a separator (`=======`) line are present in the same `resolvedContent` string. Content containing only a stray `<<<<<<<` line, only a stray `=======`, or only a stray `>>>>>>>` (the closing marker isn't checked at all) passes validation untouched.

The validated content is then spliced directly into the file on disk with no further sanitization:

```ts
if (hunkIndex < hunkResolutions.length) {
  const resolved = hunkResolutions[hunkIndex].resolvedContent
  if (resolved.length > 0) {
    resultLines.push(...resolved.split(/\r?\n/))
  }
}
``` [2](#0-1) 

The reassembled content becomes the file's final committed/written state — this is the write path that both the resolution dialog and the eventual commit consume (`IFileResolution.resolvedContent` in `reassembleResolutions`). [3](#0-2) 

### Why this matters for the "valid impact" criteria

The conflict content that drives the LLM's output is built entirely from repository data an attacker can influence — the "ours"/"theirs" hunks of a merge, rebase, or cherry-pick, pulled straight from the working tree via `extractConflictHunks` and fed into the prompt with fenced code blocks: [4](#0-3) 

An attacker who controls one side of a merge (a malicious branch/PR the user merges, or a crafted upstream commit) can shape file content and comments to increase the likelihood the model echoes back a stray marker-like line (e.g. quoting example conflict-marker text, or being confused by adversarial content designed to look like an unresolved nested conflict). Because the guard only rejects the paired ours+separator case, a resolution containing a lone stray marker line is accepted and written into the file that ultimately gets shown as "resolved" and committed/pushed by the user — without any warning. This is a case of **silent corruption of what the user commits**, since the UI and commit flow treat the file as fully resolved.

### Why existing guards don't stop it

- `validateResolutionPaths` only checks file paths and hunk *counts*, never hunk *content*. [5](#0-4) 
- The only content-level guard is the `&&` check described above, which requires both marker types to co-occur in the same hunk string.
- `reassembleResolvedFile`'s own marker detection is only applied to the *original* raw file content to find splice points — it is never re-run on the model's replacement text, so a marker fragment left in `resolvedContent` is not caught a second time.

### Recommendation

- Replace the paired `&&` check with independent checks for each marker type (`<{7}`, `={7}`, `>{7}` each on their own, using the same `oursMarker`/`separatorMarker`/`theirsMarker` regexes already defined in `copilot-conflict-context.ts`) so that any single stray marker line causes rejection/retry.
- Re-validate the fully reassembled file (not just each hunk in isolation) for leftover conflict markers before it is offered to the user as "resolved," since markers could also be introduced by mismatched hunk splicing.
- Treat conflict-resolution failures as blocking (surface an error requiring manual resolution) rather than silently writing content that could contain corrupted markers.

### Proof of Concept (conceptual)

1. Attacker crafts a branch that, when merged, produces a conflict whose "theirs" hunk contains adversarial text (e.g., an embedded example that says "resolve by keeping content starting with `<<<<<<< ours`" without a paired `=======`).
2. User triggers Copilot-assisted conflict resolution on the merge.
3. The model, influenced by the adversarial content, returns a hunk `resolvedContent` containing a single stray `<<<<<<<` (or `>>>>>>>`) line with no paired `=======`.
4. `parseCopilotConflictResolution`'s `&&` check does not fire (only one marker type present), so the hunk is accepted.
5. `reassembleResolvedFile` splices this content directly into the file, which is presented to the user as fully resolved.
6. The user commits/pushes a file containing a corrupted/broken conflict marker fragment without any warning — silent corruption of the committed source.

**Confidence note:** This finding depends on inducing specific LLM output behavior (prompt-injection-style influence) rather than a fully deterministic parser bug, so likelihood is lower than a pure parsing flaw; however, the validation logic itself is objectively insufficient (an `&&` where an independent per-marker check is required), and the write path applies no secondary sanitization, which is a concrete, verifiable code defect regardless of how reliably an attacker can trigger the specific model output.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
