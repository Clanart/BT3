### Title
`WombatBribeManager::removePool` never deactivates the pool, allowing votes to be permanently orphaned and old voters to game bribe rewards at the expense of new voters - (File: `wombat/WombatBribeManager.sol`)

### Summary
`WombatBribeManager::removePool` only pops the target LP address out of the `pools` array used by `castVotes`, but never sets `poolInfos[_lp].isActive = false` or clears the pool's recorded votes/stakes. This is the direct analog of the reported Maia issue: an admin "removes" a gauge/pool, but the pool is not actually deactivated in the downstream voting/staking bookkeeping, so it keeps behaving as if it were live for anyone who interacts with it directly, while `castVotes` silently stops covering it going forward.

### Finding Description
`Pool.isActive` gates both `vote()` and `unvote()`: [1](#0-0) [2](#0-1) 

`isActive` is only ever set to `true`, in `addPool`: [3](#0-2) 

`removePool` — the only admin function meant to retire a pool — never touches `poolInfos[_lp]` at all; it just removes the LP from the `pools` array that `castVotes` iterates over: [4](#0-3) 

Because `poolInfos[_lp].isActive` stays `true` forever:
- Ordinary users can still call `vote()` on the "removed" pool after `removePool` runs, since `vote()` only checks `poolInfos[_lps[i]].isActive`, not membership in `pools`. This calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, ...)` and increases `userTotalVotedInVlmgp`/`totalVlMgpInVote`, permanently consuming part of the user's votable vlMGP budget on a pool that will never again be included in `castVotes`. [5](#0-4) 
- `castVotes()` only loops over the `pools` array, so once an LP is popped out, its previously-cast vote weight at the real Wombat voter (`usedVote`) is never reduced back to zero — there is no mechanism analogous to the reported `afterCreateRemoved` callback to unwind the already-cast Wombat vote. [6](#0-5) 
- `harvestSinglePool()` takes an arbitrary `_lps` array and does not check `pools` membership or `isActive` at all, so bribes tied to the removed pool's rewarder can still be triggered/harvested and distributed to whoever is staked in `IBribeRewardPool(pool.rewarder)` — i.e., users who voted before removal (and even after, via the `vote()` bypass) keep collecting bribes tied to stale vote weight that Wombat itself is no longer actually recasting. [7](#0-6) 

This is functionally identical to the reported bug class: removing a pool/gauge at the factory/manager layer does not propagate deactivation to the staking/reward layer (`IBribeRewardPool` here, `UniswapV3Staker` in the original), so stale participants keep earning while new participants unknowingly lock value into a dead pool, and the underlying voting allocation becomes permanently stuck.

### Impact Explanation
- Permanent freezing of protocol voting power: votes already cast to the real Wombat voter for a removed pool can never be reduced to zero again through `castVotes`, permanently locking part of `usedVote()`/`totalVotes()` capacity that should be reallocatable to active pools — this reduces `remainingVotes()` for the whole protocol indefinitely.
- Users who vote for the "removed" pool via the un-gated `vote()` path (because `isActive` never flips to `false`) get their `userTotalVotedInVlmgp` reduced (a real, ongoing opportunity cost) while receiving no corresponding Wombat-side voting benefit or new bribe growth, since the pool is silently skipped by `castVotes`.
- Old voters who staked in the pool's `IBribeRewardPool` before removal can keep extracting bribes via `harvestSinglePool`/`claimBribe` even though the pool is meant to be retired, at the expense of protocol funds meant for active pools.

This satisfies the "permanent freezing of funds" / "theft or permanent freezing of unclaimed yield" impact bar, reachable purely through ordinary wallet calls (`vote`, `unvote`, `harvestSinglePool`, `claimBribe`) with `removePool` acting only as a normal (non-malicious) trigger, exactly mirroring the original report's structure where `removeGauge` was a legitimate admin action.

### Likelihood Explanation
`removePool` is a normal, expected lifecycle operation (pools get deprecated/replaced regularly in AMM-adjacent voting systems). Once called, any ordinary user can immediately exploit the missed deactivation by calling `vote()` on the stale pool address (still present in `poolInfos`) with no special privileges required. No attacker coordination or governance compromise is needed — only knowledge of the now-removed LP address, which remains public/discoverable via prior `AddPool` events.

### Recommendation
1. In `removePool`, explicitly set `poolInfos[_lp].isActive = false` (and consider deleting sensitive fields) so `vote()` reverts with `PoolNotActive()` for the removed pool.
2. Before/at removal, force-unwind existing votes for that pool (cast a zero target vote to Wombat for it one last time, or otherwise decrement `usedVote` at the Wombat voter) so removed pools do not permanently lock protocol voting capacity.
3. Gate `harvestSinglePool` (and any other function accepting arbitrary `_lps`) on `poolInfos[_lp].isActive` or `pools` membership, so removed pools cannot continue to trigger bribe harvesting/distribution.
4. Add an explicit `unvote`-only-when-inactive path (or a dedicated `emergencyWithdraw`) so users who already staked in a pool prior to removal can cleanly exit without being blocked by the `isActive` check in `unvote`.

### Proof of Concept
1. Owner calls `addPool(lpA, rewarderA, "PoolA")` — `poolInfos[lpA].isActive = true`, `lpA` pushed to `pools`. [3](#0-2) 
2. User1 calls `vote([lpA], [+100e18])` — stakes 100 vlMGP-equivalent weight into `rewarderA`. [8](#0-7) 
3. Owner calls `castVotes(...)`, forwarding User1's vote weight to the real Wombat voter (increasing `usedVote()` there). [9](#0-8) 
4. Owner calls `removePool(indexOfLpA)` — `lpA` is removed from `pools`, but `poolInfos[lpA].isActive` remains `true` and User1's stake/vote records are untouched. [4](#0-3) 
5. User2 (unaware the pool was retired) calls `vote([lpA], [+50e18])` — succeeds because `poolInfos[lpA].isActive` is still `true`, locking part of User2's vlMGP votable budget into `rewarderA`. [10](#0-9) 
6. Subsequent `castVotes()` calls never iterate `lpA` again (it's not in `pools`), so User1's original vote weight remains permanently cast at the real Wombat voter with no way to reduce it, and User2's new vote is likewise never forwarded — both users' vlMGP allocations are stuck while User1 (and anyone with a residual stake) can still call `harvestSinglePool([lpA])`/`claimBribe([lpA])` to pull any bribes still routed to `rewarderA`. [7](#0-6)

        if (_lps.length != _deltas.length)
            revert LengthMismatch();

        uint256 length = _lps.length;
        int256 totalUserVote;

        for (uint256 i; i < length; i++) {
            Pool storage pool = poolInfos[_lps[i]];
            if (!pool.isActive)
                revert PoolNotActive();
            int256 delta = _deltas[i];
            totalUserVote += delta;
            if (delta != 0) {
                if (delta > 0) {
                    pool.totalVoteInVlmgp += uint256(delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] += uint256(delta);
                    IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta));
                } else {
                    pool.totalVoteInVlmgp -= uint256(-delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] -= uint256(-delta);
                    IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(-delta), false);
                }
            }
        }

        if (msg.sender != delegatedPool) {
            if (totalUserVote > 0) {
                userTotalVotedInVlmgp[msg.sender] += uint256(totalUserVote);
                totalVlMgpInVote += uint256(totalUserVote);

                userTotalVotedInVlmgp[msg.sender] -= uint256(-totalUserVote);
                totalVlMgpInVote -= uint256(-totalUserVote);
            }
        }

        if (userTotalVotedInVlmgp[msg.sender] > getUserVotable(msg.sender))
            revert NotEnoughVote();
    }
