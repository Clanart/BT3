### Title
Prefix-only path-containment check in `resolveWithin()` allows sibling-directory escape via malicious deep link - ([File: app/src/lib/path.ts])

### Summary
`resolveWithin()` is the app's central guard against path traversal/symlink escapes, and it validates containment with `realResolved.startsWith(realRoot)`, a plain string-prefix comparison with no path-separator boundary check. This mirrors the reported bug class: an "invariant" check whose comparison logic doesn't actually enforce the property it's supposed to guarantee. Here the flaw is in the opposite direction from the smart-contract report (too permissive instead of too strict), but it is the same root cause: the guard's arithmetic/string comparison silently fails to enforce the boundary it claims to enforce.

### Finding Description
`resolveWithin()` is meant to guarantee that a resolved path is at, or underneath, `rootPath`: [1](#0-0) 

The containment check is:
```
return realResolved.startsWith(realRoot) ? resolved : null
```
This is a naive string-prefix test. If `realRoot` is `/Users/victim/Documents/GitHub/myrepo` (no trailing separator) and an attacker supplies a relative segment such as `../myrepo-secrets/creds.txt`, `path.resolve` produces `/Users/victim/Documents/GitHub/myrepo-secrets/creds.txt`. That string legitimately *starts with* `/Users/victim/Documents/GitHub/myrepo`, so the check passes even though `myrepo-secrets` is a completely different, sibling directory — not a descendant of `myrepo` at all. The existing symlink/null-byte checks in the same function do not protect against this, because the bypass happens purely through the final string comparison, not through symlinks.

One reachable, attacker-influenced caller of this function is the "Open Repository from URL" deep-link handler: [2](#0-1) 

Here `filepath` comes directly from a parsed `x-github-client://` deep link (see `app/src/lib/parse-app-url.ts`, which builds the `IOpenRepositoryFromURLAction` including `filepath`) that a user clicks. The only other check is `isAbsolute(filepath)`, which a relative-with-`..` payload trivially avoids. If `resolveWithin` incorrectly returns a path outside the repository (as shown above), `shell.showItemInFolder(resolved)` is called on a location that is not actually inside the repository.

### Impact Explanation
This breaks the confinement invariant that every other caller of `resolveWithin` (Copilot conflict-resolution context building/file-write in `app-store.ts` and `copilot-conflict-context.ts`) relies on to keep file reads/writes scoped to the repository. In the deep-link path, a successful bypass causes GitHub Desktop to reveal/open a file-manager window pointed at an attacker-chosen sibling path outside the cloned repository — an unauthorized filesystem disclosure triggered purely by the victim clicking a crafted link, matching the "file read outside the repo" impact category. Because the same flawed primitive underlies the sandboxing used for the Copilot AI-assisted conflict-resolution file writes, the same class of prefix-collision (e.g., a workspace whose parent directory contains a similarly-prefixed sibling folder) could, in principle, weaken the write-path guard as well, though the write path is further constrained by `validateResolutionPaths` matching against real on-disk conflicted files, limiting practical exploitability there.

### Likelihood Explanation
Exploitation requires only that the victim click a link (no local access, no credentials, no admin rights) — the `x-github-client://openRepo?...&filepath=...` deep-link flow is normal, unprivileged application functionality. The precondition (a sibling directory/file whose name has the repository's directory name as a string prefix, e.g. `myrepo` vs `myrepo-secrets` or `myrepo` vs `myrepo.bak`) is a realistic real-world naming pattern, especially for cloned/backup/fork directories developers commonly keep side-by-side. No cryptographic or race-condition tricks are needed; it's a straightforward string-comparison bug.

### Recommendation
Fix `resolveWithin()` to require an exact path-boundary match instead of a raw prefix test, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests specifically for sibling-directory names that share a prefix (e.g., root `.../myrepo` vs resolved `.../myrepo-secrets`) to the existing `path-test.ts` suite, alongside the current symlink/null-byte cases.

### Proof of Concept
1. Have a GitHub Desktop repository open at `/Users/victim/Documents/GitHub/myrepo`, and a sibling directory `/Users/victim/Documents/GitHub/myrepo-secrets/creds.txt` existing on disk (e.g. an old backup or unrelated project).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/owner/myrepo?filepath=../myrepo-secrets/creds.txt`.
3. Victim clicks the link; Desktop parses it via `parse-app-url.ts` into an `IOpenRepositoryFromURLAction` with `filepath = '../myrepo-secrets/creds.txt'`.
4. `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts` calls `resolveWithin(repository.path, filepath)`.
5. Because `realResolved.startsWith(realRoot)` treats `.../myrepo-secrets/creds.txt` as "starting with" `.../myrepo` (string-prefix collision, not a real subdirectory relationship), the guard returns a non-null path instead of `null`.
6. `shell.showItemInFolder(resolved)` opens the file manager at the sibling directory outside the intended repository, disclosing its location/contents to the flow triggered entirely by the deep link click.

Note: I was unable to execute this against a live build to confirm end-to-end OS-level behavior (index-only analysis); the logic trace above is based on the source shown in `app/src/lib/path.ts`, `app/src/ui/dispatcher/dispatcher.ts`, and `app/src/lib/parse-app-url.ts`.

```typescript
  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }
```
