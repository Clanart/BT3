## Analog Found

**Bug-class reduction from the report:** removing an entry from a "supported/registered" set used by both the outbound (escrow/burn) and inbound/timeout (redeem/refund) code paths permanently blocks completion of already-escrowed obligations that reference the removed entry, because the guard check is asset/registration-existence based rather than a permanent "ever registered" set.

### Title
`update_token`'s `remove_chains` deletes routing state needed by `on_timeout`, permanently bricking in-flight refunds - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
In the `hyper-fungible-token` pallet, `send()` locks or burns a user's asset and dispatches a cross-chain `PostRequest` keyed on `(destination chain, asset_id)` configuration read from `TokenContracts` and `Precisions`. [1](#0-0)  If the request is never delivered and times out, `on_timeout` refunds the original sender, but it must first re-derive the asset and decimals from `ContractToAsset` and `Precisions`, keyed on the destination chain and contract address embedded in the original message. [2](#0-1) 

`update_token`'s `remove_chains` branch unconditionally deletes `TokenContracts`, `ContractToAsset`, and `Precisions` entries for a chain, with no check for in-flight (already dispatched, not-yet-timed-out) transfers to that chain. [3](#0-2) 

### Finding Description
The flow:
1. A user calls `send()`, which escrows/burns their tokens and dispatches a `DispatchPost` to `params.destination` using the `token_contract` and `erc_decimals` looked up at that moment. [4](#0-3) 
2. Before the request is delivered or times out, `CreateOrigin` calls `update_token` with that chain in `remove_chains` (e.g. routine maintenance, re-pointing the token contract, or deprecating a chain) — this removes the `ContractToAsset` reverse mapping and the `Precisions` entry for `(asset_id, chain)`. [3](#0-2) 
3. When the original request eventually times out, `pallet-ismp` invokes `on_timeout`, which calls `ContractToAsset::<T>::get(dest, &to).ok_or(HftError::UnknownContractOnTimeout)?` and then `Precisions::<T>::get(local_asset_id, dest).ok_or(HftError::DecimalsNotConfigured(dest))?`. [5](#0-4)  Both lookups now fail because step 2 deleted them, so `on_timeout` returns an error instead of crediting the refund.

This is the direct structural analog of the LevelMinting issue: a single mutable "supported" registry is used both to gate new operations and to satisfy previously-created obligations, so removing an entry silently breaks completion of pending obligations tied to it, with no separate "was ever valid" record preserved (unlike the recommended fix's `_redeemableAssets` set).

### Impact Explanation
The escrowed/burned funds from `send()` become permanently unrecoverable: `on_timeout` errors out (propagated by `pallet-ismp` as a failed timeout handler), so the pallet's escrow account or burn accounting is never reversed, and there is no other extrinsic in this pallet to force a refund for an orphaned commitment. This is a direct loss-of-funds condition for the ordinary end user who called `send()`, triggered by an entirely routine and non-malicious governance action (updating chain configuration), which is exactly the class of "loss of funds" impact the bounty accepts — it does not require a malicious admin, relayer, or prover; the admin action itself is legitimate protocol maintenance, and the victim is an unprivileged user with no recourse.

### Likelihood Explanation
`update_token` is a normal, expected maintenance operation (e.g., re-pointing a token's EVM contract per the pallet's own doc: "Add or remove chains from an existing token's configuration"). [6](#0-5)  Any window between an in-flight `send()` (locked funds, dispatched post) and its timeout — which can be arbitrarily long, since `params.timeout` is caller-supplied — is enough to trigger the bug if `update_token(remove_chains)` executes in that window. No attacker collusion, malicious relayer, or malformed proof is required; it is a pure ordering/config-lifecycle bug.

### Recommendation
Do not delete `ContractToAsset`/`Precisions` entries outright on `remove_chains`, or maintain a secondary "historical" record (analogous to the report's `_redeemableAssets` set) that `on_timeout` can consult even after a chain/asset mapping has been removed from the "currently supported" set used by `send()`. Alternatively, require `update_token(remove_chains)` to first drain/settle all in-flight commitments for that `(asset, chain)` pair (e.g., via a pending-request counter) before allowing removal.

### Proof of Concept
1. Governance calls `register_token` registering asset `A` for `StateMachine::Evm(X)` with a token contract and decimals. [7](#0-6) 
2. A user calls `send(params)` with `asset_id = A`, `destination = Evm(X)`, and a long `timeout`; this escrows/burns their tokens and dispatches a `DispatchPost` via `pallet-ismp`. [8](#0-7) 
3. Before delivery/timeout, governance calls `update_token` with `remove_chains = [Evm(X)]`, deleting `TokenContracts`, `ContractToAsset`, and `Precisions` entries for `(A, Evm(X))`. [3](#0-2) 
4. The dispatched request is never delivered (network partition, relayer inactivity, or destination contract issue) and eventually times out; `pallet-ismp` calls `Pallet::on_timeout`.
5. `on_timeout` executes `ContractToAsset::<T>::get(dest, &to).ok_or(HftError::UnknownContractOnTimeout)?` which now returns `None` and errors out, so the user's escrowed/burned funds are never refunded. [9](#0-8)

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}

					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal

					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}
