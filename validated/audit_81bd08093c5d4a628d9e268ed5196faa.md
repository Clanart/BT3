### Title
Payout Attribution via Unauthenticated OP_RETURN Allows Framing Honest Operators for Reimbursement They Never Funded - (File: core/src/operator.rs, core/src/verifier.rs)

### Summary
`send_asserts` and `Verifier::is_kickoff_malicious` both determine "who funded this withdrawal" solely from the `payout_payer_operator_xonly_pk` DB column, which `update_finalized_payouts` populates purely by parsing the OP_RETURN of whatever transaction is found on-chain spending the withdrawal UTXO. Because the user's authorizing signature for that UTXO uses `SinglePlusAnyoneCanPay` (which commits only to input 0 and the matching output 0), the withdrawing user fully controls all other inputs/outputs of the payout transaction — including the OP_RETURN — and can self-fund the withdrawal while stamping an arbitrary, unrelated operator's x-only pubkey into it.

### Finding Description
The broken binding is: `withdrawals.payout_payer_operator_xonly_pk == the operator who actually broadcast/funded payout_tx`. In practice the column only reflects `withdrawals.payout_payer_operator_xonly_pk == whatever XOnlyPublicKey bytes appear in payout_tx's OP_RETURN output`, with no signature or proof tying that key's owner to the transaction's funding inputs.

- `create_payout_txhandler` builds output 2 as an unauthenticated OP_RETURN containing `operator_xonly_pk.serialize()` [1](#0-0) .
- The single input (the withdrawal UTXO) is authorized by the user with `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params` [2](#0-1) . `SinglePlusAnyoneCanPay` only commits to input 0 and the output at index 0 (`Prevouts::One`), as implemented in `calculate_pubkey_spend_sighash` [3](#0-2) . It leaves the anchor output and the OP_RETURN output completely unconstrained.
- `update_finalized_payouts` trusts this OP_RETURN at face value from the mined block, with no check that the funding inputs belong to the named operator: it just extracts and stores whatever xonly pubkey parses from the first OP_RETURN output [4](#0-3) .
- `send_asserts` fetches this DB value and only compares it against `kickoff_data.operator_xonly_pk`, never re-deriving it independently from the actual payout transaction at assert time beyond this same DB-trusting comparison [5](#0-4) .
- `Verifier::is_kickoff_malicious` performs the identical DB-trusting comparison as its sole authenticity check [6](#0-5) .
- Automation is fully self-triggering: `PayoutCheckerTask` polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and, upon any match, automatically calls `handle_finalized_payout` to create and eventually confirm a kickoff/reimburse for that operator [7](#0-6) .

Exploit flow: the attacker (as the withdrawing user) owns the withdrawal UTXO's private key and signs a `SinglePlusAnyoneCanPay` signature over it, per `withdraw`'s signature verification [8](#0-7) . Because ANYONECANPAY/SINGLE leaves everything but input/output 0 unsigned, the attacker can independently build their own payout transaction: input 0 = the same withdrawal UTXO with their own valid signature, output 0 = the exact committed user payout (matching what Citrea registered), additional funding input(s) from the attacker's own wallet to cover the payout amount, and an OP_RETURN naming a real, permissioned, uninvolved operator X's public key (public knowledge, since operators are known/whitelisted per `is_deposit_valid`'s operator collateral checks [9](#0-8) ). The attacker broadcasts and confirms this self-funded transaction before X (or instead of X) ever creates a payout. `update_finalized_payouts` then records operator X as the payer. X's own automation (unaware it never made this payout) subsequently drives the kickoff → asserts → Reimburse pipeline to completion, using X's own collateral and round slot, ultimately releasing the deposit's move-to-vault BTC to X's reimbursement address for a withdrawal X never funded.

Existing guards do not catch this: `Verifier::is_kickoff_malicious` re-uses the same poisoned DB column instead of independently verifying that operator X's own signed inputs fund the payout; `SPV::verify` and the light-client proof pipeline in `send_asserts` only prove that *a* payout transaction with the claimed txid/blockhash exists and pays the correct user output — they never verify which party's funds moved through that transaction.

### Impact Explanation
The bridge's move-to-vault deposit BTC for the targeted deposit is released via `Reimburse` to an operator (X) who never personally funded the corresponding withdrawal — matching the listed Critical category "an operator reimbursed for a payout it never funded." This is fully attacker-repeatable across any deposit/withdrawal for which the attacker is willing to front the withdrawal amount themselves, and across any currently-registered operator whose public key is known (all operator keys are public/discoverable). It also forces the framed honest operator to consume a kickoff/round slot and collateral risk (challenge exposure) for a payout it never authorized, which the operator did not choose to make.

### Likelihood Explanation
No privileged role is required: the attacker only needs to be a normal withdrawing user with control over the dust withdrawal UTXO's private key and enough BTC to self-fund the payout amount (which returns to the attacker as the withdrawal recipient, so the net attacker cost is limited to Bitcoin transaction fees plus locking up capital briefly). No collusion with the framed operator, no majority hashrate, and no privileged gRPC access are needed — the attacker simply needs to win the race to have their self-crafted transaction confirmed for the corresponding withdrawal UTXO, which is entirely under their control since they hold that UTXO's key.

### Recommendation
Do not derive payer attribution purely from OP_RETURN content parsed from chain data. Either (a) require the additional funding inputs of `payout_tx` to be cryptographically tied to the named operator (e.g., verify a signature from `operator_xonly_pk` over the full transaction, or require the OP_RETURN output itself to be committed under `SIGHASH_ALL`/`SIGHASH_DEFAULT` covering all outputs together with an operator-specific input), or (b) have `send_asserts`/`is_kickoff_malicious` independently verify that at least one input of `payout_tx` is spendable only by `kickoff_data.operator_xonly_pk` (e.g., matches the operator's registered collateral/wallet key) rather than trusting the unauthenticated OP_RETURN tag alone.
