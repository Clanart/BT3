### Title
Incomplete conflict-marker validation lets Copilot AI conflict resolution silently commit content with unresolved git conflict markers - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The `bHermes`/`ERC4626DepositOnly` report is about a missing output check: the contract accepts whatever `shares`/`assets` value comes out of a computation without validating it against the caller's expectation, so bad output silently reaches the user. The same broken-invariant class exists in GitHub Desktop's Copilot-based merge/rebase/cherry-pick conflict resolution feature: the code that validates the LLM's per-hunk resolution before splicing it into the file on disk only rejects a resolution when it contains **both** an "ours" marker line **and** a separator marker line — it does not reject a resolution that still contains just one dangling conflict-marker artifact. The check is a coarse heuristic, not a real "did the model actually resolve this" gate, so an under-resolved or manipulated model response can be accepted and written straight into the file that ends up staged/committed.

### Finding Description
`parseCopilotConflictResolution` is the only gate between the raw LLM JSON response and the content that gets spliced into a user's working tree via `reassembleResolvedFile`/`reassembleResolutions`. Its only defense against markers surviving into the final file is: [1](#0-0) 

```
if (typeof hunkObj.resolvedContent !== 'string') { ... }
const rc = hunkObj.resolvedContent
if (/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)) {
  throw new CopilotValidationError(
    `... hunk ${j} of file "${path}" still contains conflict markers`
  )
}
```

This requires **both** the `<<<<<<<` pattern **and** a `=======` line to be present in the *same* `resolvedContent` string before it is rejected. It never checks for the closing `>>>>>>>` marker at all, and it never rejects a `resolvedContent` that contains only one of the marker types (e.g. a stray `<<<<<<<` line with no matching `=======`, or a lone `>>>>>>>` copied verbatim from context). Once validated, the content is spliced verbatim into the on-disk file: [2](#0-1) 

There is no second-layer check downstream (e.g. re-scanning the fully reassembled file for `isConflictMarker`-style patterns before it is presented to the user as "resolved"). The system prompt tells the model to never leave markers in, but the model is fed attacker-influenceable repository content — PR titles/bodies and commit summaries pulled from the fetched history are placed directly into the prompt: [3](#0-2) 

An attacker who controls a PR description or commit message that will end up in a real merge conflict (i.e., a repository the victim clones/fetches and later merges/rebases) can attempt to bias or destabilize the model's output via prompt injection so that a hunk's `resolvedContent` ships with a lone marker line that this incomplete regex does not catch. Because the model output is trusted content only checked by this weak heuristic, the corrupted text is written to the file as if it were a clean resolution — analogous to the ERC4626 report's core problem: an output value is accepted without validating it actually matches the caller's expectation ("fully resolved, marker-free content").

### Impact Explanation
If a resolvedContent value carrying a partial/stray conflict marker is spliced in, the resulting file silently contains invalid/broken syntax (or, worse, a marker line that changes program semantics, e.g. inside a string literal it wouldn't even error) that the user is expected to have received as "conflicts fully resolved." Because the write path performs no downstream re-validation, this can lead to a corrupted commit being made and pushed without the user noticing — matching the accepted impact category "silent corruption of what the user commits or pushes." In the worst case for compiled/interpreted languages, an unnoticed stray marker breaks the build only after push, and in data files (lockfiles, configs, YAML) it can silently produce a different value than intended without even causing a visible error.

### Likelihood Explanation
The feature batches up to `SinglePromptFileLimit` (20) files per prompt across up to `MaxConcurrentChunks` (5) concurrent LLM calls, so on any moderately-sized merge conflict the user is unlikely to manually re-diff every hunk before accepting the AI-generated resolution — the whole point of the feature is to let the user trust the summary/reasoning UI rather than read every line. This makes the "user doesn't catch it because the app said it was resolved" pathway realistic. Reaching the specific incomplete-regex bypass requires influencing the model's output through prompt content pulled from a real repository (commit messages / PR descriptions), which is plausible but not guaranteed to succeed reliably given LLM non-determinism — hence likelihood is speculative/moderate rather than certain, since I could not execute the model to confirm bypass reliability.

### Recommendation
Tighten the guard in `parseCopilotConflictResolution` to reject `resolvedContent` containing **any** of the three marker patterns individually (`<{7}`, `={7}`, `>{7}`), not just the conjunction of two. Additionally, add a defense-in-depth re-scan of the fully reassembled file content in `reassembleResolutions`/`reassembleResolvedFile` (using the same `isConflictMarker` check already defined in `copilot-conflict-context.ts`) before it is surfaced to the UI as a completed resolution, so a partially-resolved or adversarially-influenced hunk cannot reach the write path even if the per-hunk check is bypassed.

### Proof of Concept
1. Set up a merge conflict where the incoming PR body/commit message is attacker-authored (e.g., a public fork PR that will later be merged) and crafted to prompt-inject the resolution model.
2. Trigger Copilot conflict resolution on the merge.
3. Get the model to return, for one hunk, `resolvedContent` equal to e.g. `"some code\n<<<<<<< leftover\nmore code"` (a lone `<<<<<<<` without a matching `=======` in that same string).
4. `parseCopilotConflictResolution`'s check `/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)` evaluates to `false && ...` = `false`, so no `CopilotValidationError` is thrown.
5. `reassembleResolvedFile` splices this content in place of the real conflict block; the file on disk now contains a stray, unresolved-looking marker line inside what the UI reports as a clean, fully-resolved file, and the user may stage/commit it without noticing. [4](#0-3)

/** Maximum number of characters of a PR body to include in the prompt. */
const MAX_PR_BODY_LENGTH = 4000

/** Append a single pull request's title and (truncated) body to the prompt. */
function appendPullRequest(
  parts: Array<string>,
  pr: IConflictContextPullRequest
): void {
  parts.push(`PR #${pr.number}: ${pr.title}`)
  if (pr.body) {
    parts.push('Description:')
    parts.push(makeFencedBlock(truncateBody(pr.body)))
  }
  parts.push('')
}

/** Truncate an over-long PR body so a single PR can't dominate the prompt. */
function truncateBody(body: string): string {
  if (body.length <= MAX_PR_BODY_LENGTH) {
    return body
  }
  return `${body.slice(0, MAX_PR_BODY_LENGTH)}\n…(truncated)`
}
