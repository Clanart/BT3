Based on my research, I found a structurally analogous pattern in Agave, though with an important caveat about verifiability that I'll explain.

### Title
Unchecked assumption that a V1 transaction always has a populated `transaction_config()` causes `.expect()` panic on attacker-supplied packets - (File: runtime-transaction/src/runtime_transaction/transaction_view.rs)

### Summary
The TON bug is a classic "sum-type variant assumed present" panic: code accesses `TrPhaseComputeVm` without checking whether the actual variant is `TrPhaseComputeSkipped`, and attacker-controlled low-value messages can force the skipped variant, panicking observer threads. The Agave analog is in `RuntimeTransaction<ResolvedTransactionView<D>>::to_versioned_transaction()`, which unconditionally calls `.expect("V1 must have config_view")` on `self.transaction_config()` whenever `self.version()` reports `TransactionVersion::V1` [1](#0-0) .

### Finding Description
`to_versioned_transaction()` branches on `self.version()`, and for the `V1` arm it does:
```rust
let config_view = self.transaction_config().expect("V1 must have config_view");
``` [2](#0-1) 

This mirrors the TON pattern exactly: `version()`/`shred_variant`/`ComputePh.SumType` is one tag, and a *separate* optional field (`transaction_config()` / `TrPhaseComputeVm`) is assumed to be populated whenever that tag has a specific value, with no fallback branch — just a hard `.expect()`/panic. A sibling function, `from_sanitized_transaction_view()`, treats this same relationship as fallible by using `if let Some(transaction_config_view) = transaction.transaction_config()` with a `LegacyAndV0` fallback branch instead of assuming presence [3](#0-2) , which shows the codebase itself does not treat "V1 implies config_view present" as an unconditionally-safe invariant elsewhere — yet `to_versioned_transaction()` does.

The presence check ultimately depends on the external `agave-transaction-view` crate's wire-format parser (not vendored in this repository, so I could not directly verify its invariants). The in-repo code's own comment acknowledges the risk: "NOTE: only txv1 has `transaction_config_view`, which must have been validated for `SanitizedTransactionView`" [4](#0-3) . This is exactly the kind of documented-but-unenforced-in-this-call-path invariant that caused the TON panic: the guarantee lives in a different layer than the code doing the unchecked `.expect()`.

### Impact Explanation
`as_sanitized_transaction()`/`to_versioned_transaction()` is called from `runtime/src/bank.rs`, `runtime/src/transaction_execution.rs`, and `core/src/banking_stage/committer.rs` — i.e., in the transaction execution and commit hot path that runs for every ordinary transaction processed by a validator, reachable by any unprivileged client sending TPU/QUIC transactions [5](#0-4) . If a malicious sender can produce a packet that the `agave-transaction-view` parser classifies as `TransactionVersion::V1` without populating the config view (e.g., through a parser edge case analogous to TON's "compute skipped" variant), the `.expect()` panic would crash the banking/execution thread — a non-RPC remote crash from a single malformed transaction, which matches the "non-RPC remote exhaustion/crash" impact class.

### Likelihood Explanation
Likelihood is uncertain and cannot be fully confirmed from this repository alone: the actual guarantee that "any TransactionVersion::V1 has a config_view" is enforced (or not) inside `agave-transaction-view`'s `SanitizedTransactionView::try_new_sanitized()`, which is an external crate not present in this codebase, so I could not inspect its parsing/validation logic to confirm whether a bypass exists. What I can confirm is that the call site itself provides no defensive fallback — unlike the analogous `from_sanitized_transaction_view()` function which does handle the `None` case gracefully. This is architecturally the same defect class as the TON bug (an assumed-always-present sub-field of a tagged union, accessed via `.expect()`/panic instead of a checked `if let`/`match`), but confirming actual exploitability requires access to the transaction-view parser's source, which is outside this index's coverage.

### Recommendation
Replace the `.expect("V1 must have config_view")` in `to_versioned_transaction()` with a graceful `Result`-based error path (mirroring `from_sanitized_transaction_view()`'s `if let Some(...) else` fallback), so that a transaction which is tagged `V1` but lacks a populated config view is rejected as a sanitize failure rather than panicking the caller thread.

### Proof of Concept
Not independently constructible without access to the `agave-transaction-view` crate's source to determine whether a wire-format packet can be crafted that parses to `TransactionVersion::V1` while `transaction_config()` returns `None`. I recommend a Devin session start a full-repo/dependency checkout (including the `agave-transaction-view` crate) to determine whether such a packet can be crafted, and if so, build a concrete PoC transaction and confirm the panic in `to_versioned_transaction()`.
