## Analog Found: Stale Gateway Instance Causes Permanent Escrow Lock After `NewDeployment` Update

### Title
Redeploying an IntentGateway instance via `NewDeployment` permanently strands in-flight escrows authenticated against the old instance address - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The original report's core defect: a single mutable address record (the Locker) is overwritten without regard to in-flight state that was created under the old address, and cross-message authentication is later checked strictly against the *current* record — so funds tied to the superseded address become permanently unclaimable. Hyperbridge's `IntentGatewayV2` (via `IntentsBase`/`ExtrinsicIntents`) has the exact same pattern with its `_instances` mapping, which records the counterpart gateway address per remote state machine and is used both to route outgoing settlement messages and to authenticate incoming ones.

### Finding Description
`_instances[keccak256(stateMachineId)]` stores the trusted gateway address for each remote chain [1](#0-0) . This value is written by `_addDeployment`, invoked only in response to a `NewDeployment` message from Hyperbridge itself [2](#0-1) , and it unconditionally overwrites the prior entry with no history retained for the address it replaces.

Every cross-chain settlement message that releases escrowed funds is gated by `_authenticate`, which strictly compares the incoming message's `from` field against the *current* value of `_instances[source]`: [3](#0-2) 

Both `RedeemEscrow` (solver claiming input tokens after filling an order) and `RefundEscrow` (user reclaiming input tokens after cancellation) route through this same `_authenticate` check before `_withdraw` releases funds [4](#0-3) .

The attack/failure sequence:
1. A solver fills a cross-chain order on the destination chain while `_instances[destinationChain]` on the source gateway still points to the destination gateway's address, `GatewayOld`. The solver pays out the order's output tokens to the beneficiary immediately, then the destination gateway dispatches a `RedeemEscrow` POST back to the source chain with `from = GatewayOld` [5](#0-4) .
2. Before that message is delivered (i.e., while it is in flight across Hyperbridge — a window of at least one challenge period), Hyperbridge issues a routine `NewDeployment` update to the source gateway that migrates the destination's registered instance to `GatewayNew` [6](#0-5) , overwriting `_instances[destinationChain]` with no preservation of `GatewayOld`.
3. When the `RedeemEscrow` message from `GatewayOld` finally arrives, `_authenticate` compares `request.from` (`GatewayOld`) against the now-updated `_instance(source)` (`GatewayNew`) and reverts with `Unauthorized` [3](#0-2) .
4. The escrowed input tokens in `_orders[commitment][token]` remain locked in the source gateway forever — the solver already delivered the output tokens on the destination chain and has no other path to claim the escrow, and `_cancelFromSource`/`_cancelFromDest` cannot help because `_filled[commitment]` was already set to the solver's address by the fill, so a subsequent cancel attempt fails the "not yet filled" precondition baked into the redeem/cancel flow.

This is structurally identical to the reported bug: the AirdropFactory's locker address update is reflected only in the factory (analogous here to Hyperbridge's canonical routing table), but the dependent contract (`Airdrop.sol`, analogous here to the *other side's* `IntentGatewayV2` instance) keeps checking against a single overwritten value instead of accepting/tracking the value that was valid at the time the in-flight action was initiated.

### Impact Explanation
Legitimate solver funds (input-token escrow) become permanently unclaimable, and the solver has already irrevocably paid out the corresponding output tokens on the destination chain — this is a direct, unrecoverable loss of funds triggered by an ordinary, non-malicious protocol-migration operation (gateway redeployment), not requiring any admin/relayer misbehavior, matching the bounty's "stealing or loss of funds" and "false state acceptance / unauthorized rejection preventing rightful settlement" categories.

### Likelihood Explanation
`NewDeployment` events occur whenever a gateway is redeployed/upgraded on any connected chain — a routine operational event, not a rare edge case. Any order in flight (filled but not yet settled) at the moment of such a migration is affected; the longer the settlement message's transit/challenge-period latency, the larger the window of orders at risk. No attacker action is required — the failure is deterministic given the normal migration + concurrent in-flight order combination.

### Recommendation
Do not authenticate solely against the single current `_instances[source]` value. Options:
- Retain a set/history of previously valid gateway addresses per state machine (e.g., `mapping(bytes32 => mapping(address => bool)) _validInstances`) and accept messages from any address that was valid, rather than overwriting a single slot.
- Alternatively, snapshot the expected settlement counterpart address into the order/commitment itself at order-placement time, and authenticate against that stored value rather than the live, mutable `_instances` mapping.
- At minimum, gate `NewDeployment` migrations with a drain/quiescence period that first ensures no orders are in-flight against the old instance before the mapping is overwritten.

### Proof of Concept
1. Source chain gateway `G_src` has `_instances[dst] = GatewayOld`.
2. Solver calls `fillOrder`/cross-chain fill path on destination; `_fillCrossChain` sets `_filled[commitment] = solver`, pays beneficiary, and dispatches `RedeemEscrow` from `GatewayOld` to `G_src` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:139-155`).
3. Before the message lands on `G_src`, Hyperbridge dispatches a `NewDeployment` request updating `G_src._instances[dst] = GatewayNew` via `_addDeployment` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:299-300`).
4. The `RedeemEscrow` message arrives at `G_src.onAccept`; `_authenticate` computes `module = GatewayOld` and compares to `_instance(dst) == GatewayNew` → reverts `Unauthorized` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:63-67`).
5. `_orders[commitment][inputToken]` remains non-zero forever; solver cannot re-trigger settlement (no retry entrypoint exists for a reverted `onAccept` handled request from Hyperbridge's perspective as "delivered"), and cancellation paths are blocked because `_filled[commitment]` is already set. Funds are permanently stuck.
