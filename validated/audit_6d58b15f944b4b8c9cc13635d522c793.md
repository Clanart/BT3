### Title
Untrusted `ReceivedOutput` amounts produce signatures committing to fabricated prevout values, making received funds unspendable - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the report (where the fee/amount is computed at approval time but recomputed under changed parameters at execution), `SignableTransaction` computes its payment/fee math from the `TxOut` value embedded in each `ReceivedOutput`, while the BIP-341 signature later commits to those same attacker-controlled prevout values via `Prevouts::All`. `ReceivedOutput::read` deserializes the `offset`, `TxOut` (including `value`), and `OutPoint` from untrusted bytes with no validation that the `TxOut` matches the actual on-chain UTXO referenced by the `OutPoint`.

### Finding Description
`ReceivedOutput::read` (wallet/mod.rs:122-133) accepts arbitrary bytes specifying an `output: TxOut` — whose `value` is wholly attacker-chosen — paired with an arbitrary `outpoint`. `SignableTransaction::new` then:

- Sums `input.output.value` to compute `input_sat` (send.rs:175) and derives `needed_fee` / change / `NotEnoughFunds` decisions from it (send.rs:206-234).
- Stores the fabricated `TxOut`s into `prevouts` (send.rs:253).

At signing time, `TransactionSignMachine::sign` uses `Prevouts::All(&self.tx.prevouts)` (send.rs:375) so each `taproot_key_spend_signature_hash` commits to those fabricated amounts. Because `SighashType::Default` (i.e. `SIGHASH_DEFAULT`, equivalent to ALL) commits to all input prevout amounts, the signature is only valid if the prevout values are the real on-chain values. Any discrepancy produces a transaction the network rejects as invalid (BIP-341 verifies amounts during sighash evaluation), even though `scan_transaction`/`ReceivedOutput` caused the funds to be treated as received and spendable.

There is no check anywhere that `output.value` equals the true UTXO amount — `multisig` only verifies the derived key's `script_pubkey` matches `prevouts[i].script_pubkey` (send.rs:277), which the attacker satisfies trivially since they control the whole `TxOut`.

### Impact Explanation
A party supplying `ReceivedOutput` bytes (e.g. a coordinator distributing outputs to sign for) can craft a `TxOut` with an inflated or deflated `value`:

- **Inflated value:** `input_sat` is overstated, so change outputs and fee checks pass; the signed tx is consensus/policy-invalid because the sighash commits to amounts that exceed the real input values. The funds are effectively locked — the threshold signed a transaction that can never be broadcast.
- **Deflated value:** `input_sat` is understated → spurious `NotEnoughFunds`, or with a change output, `input_sat - payment_sat - fee_with_change` yields a wrong change amount; again the committed prevout values are wrong → invalid tx.
- Additionally, since actual fee = `sum(inputs) - sum(outputs)` (send.rs:139), a mismatch silently converts arbitrary amounts into fee in the constructed tx — though the invalid sighash prevents broadcast, the threshold session and funds are burned.

This is "funds reported received that are not spendable": the scanner/`ReceivedOutput` flow treats the output as spendable, yet the produced transaction can never confirm.

### Likelihood Explanation
Requires a party able to feed crafted bytes to `ReceivedOutput::read` — squarely within the untrusted-bytes surface. No collusion or key compromise needed; a single malicious coordinator/relayer crafting the serialized `ReceivedOutput` suffices. The resulting failure is deterministic, not probabilistic.

### Recommendation
Bind `ReceivedOutput` to the real UTXO. Options:

- Fetch and verify the prevout `TxOut` from the chain/RPC for each `outpoint` when constructing `SignableTransaction`, rather than trusting the deserialized value.
- At minimum, cross-check that `output` is the exact `TxOut` at `outpoint` (e.g. require the caller to supply the full prev transaction or a merkle/UTXO proof), and reject on mismatch.
- Alternatively use `TapSighashType::AllPlusAnyoneCanPay`-style flows only where amounts are verified; failing that, sign each input with `Prevouts::One` won't help — the correct fix is authenticating the prevout data before it ever reaches the sighash.

### Proof of Concept
```rust
// Attacker crafts bytes: valid offset scalar, TxOut{value: 1_000_000_000, script_pubkey: <real p2tr script>},
// OutPoint pointing at a real UTXO actually worth 100_000 sats.
let bytes = attacker_serialized_received_output();
let ro = ReceivedOutput::read(&mut &bytes[..]).unwrap();          // accepted, no validation

let tx = SignableTransaction::new(
  vec![ro],
  &[(payment_script, 500_000)],
  Some(change_script),
  None,
  10,
).unwrap();                                                       // fee/change math on fake 1 BTC

let machine = tx.multisig(&keys).unwrap();                        // script_pubkey check passes
let (sign_machine, preprocess) = machine.preprocess(&mut rng);
// ... FROST signing ...
let signed = sig_machine.complete(shares).unwrap();
// signed.input[0] witness commits via Prevouts::All to value=1_000_000_000
// Broadcasting fails: real UTXO is 100_000 sats -> sighash mismatch -> invalid tx.
// Funds are treated as received but permanently unspendable by this signature.
```
