## Finding: Unauthenticated cross-account crediting lets anyone force-evict a victim app's paid bandwidth subscriptions in `pallet-bandwidth`

### Title
Arbitrary `app` field in `BandwidthPurchaseMsg` allows unauthorized parties to spam-credit and evict a victim's paid bandwidth allowance - (File: `modules/pallets/bandwidth/src/lib.rs`, `evm/src/apps/BandwidthManager.sol`)

### Summary
The external report's core broken invariant is: a public, unprivileged entrypoint lets an attacker cheaply saturate a hard-capped, shared resource list keyed by a *victim-controlled identity* (the delegatee), causing legitimate entries/actions for that victim to be evicted or blocked. The local analog is `pallet-bandwidth`'s FIFO subscription list, capped at `MAX_SUBSCRIPTIONS = 1024` per `(app_chain, app)`, combined with `BandwidthManager.sol::purchase()` taking an attacker-supplied `app` parameter with zero ownership binding to `msg.sender`.

### Finding Description
`BandwidthManager.sol::purchase()` accepts an arbitrary `bytes calldata app` and dispatches a `BandwidthPurchaseMsg{app, tier, months, chain}` to `pallet-bandwidth` with no check that `msg.sender` corresponds to `app`: [1](#0-0) 

On Hyperbridge's `on_accept`, the pallet only authenticates the *manager contract* (`request.from == manager`), never the `app` identity embedded in the message body, then calls `push_subscription` keyed purely by `(msg.chain, msg.app)`: [2](#0-1) 

`push_subscription` enforces a hard cap of `MAX_SUBSCRIPTIONS = 1024` and, once full, evicts the oldest (FIFO head) entry unconditionally to make room for the new one: [3](#0-2) [4](#0-3) 

Because `app` is fully attacker-controlled and unauthenticated, any account on a registered source chain can repeatedly call `purchase()` targeting a victim's `app` identifier with the cheapest configured tier, pushing 1024 low-value subscriptions into the victim's queue and evicting the victim's legitimately purchased (larger/longer-duration) subscriptions before they are consumed — the exact same "saturate the capped list with minimal-value entries to displace/deny legitimate participants" primitive as the `VotingEscrow::MAX_DELEGATES` bug.

### Impact Explanation
Each eviction destroys real, already-paid-for byte allowance and is explicitly acknowledged as an auditable loss (`SubscriptionEvicted{ lost_bytes }`): [5](#0-4) 

This is a genuine loss-of-funds / logic-attack path: the victim paid the manager contract in fee tokens for a byte allowance, but an unrelated, unprivileged third party can force that paid allowance to be discarded before use, simply by knowing the victim's `app` byte-string (a public value — the recipient address) and being willing to spend on cheap tier purchases. No relayer/prover/admin compromise, no front-running assumption, and no malicious peer is required — it is a fully permissionless, public-entrypoint state-corruption path against the `Allowance` storage map.

### Likelihood Explanation
- `purchase()` is a public function with no allowlist or ownership check on `app`.
- `on_accept` never validates that the purchaser is authorized to credit `app`; it only checks the manager's address, which is fixed and public per chain.
- The eviction logic in `push_subscription` is unconditional once the 1024 cap is hit — there is no per-purchaser sub-limit, no minimum-value protection for older/larger subscriptions, and no distinction between "self-purchase" and "third-party purchase."
- The attack requires no privileged role and works against any app on any registered source chain, using the cheapest configured tier to minimize attacker cost while maximizing the number of evictable slots consumed.

### Recommendation
- Bind `app` in `BandwidthPurchaseMsg` to `msg.sender` (or require an explicit authorization/allowlist from the app before third-party crediting is accepted), removing the ability for arbitrary accounts to write into another app's subscription queue.
- If third-party/sponsor crediting must remain supported (per the "Sponsorship" design intent), separate the queue by payer or enforce a per-payer sub-cap within the 1024-entry list so no single unrelated payer can evict another payer's entries.
- Consider protecting high `remaining_bytes`/long-`expires_at` entries from eviction by low-value new entries (e.g., evict smallest-value entry instead of strictly-oldest, or require the new subscription's value to exceed some fraction of the evicted one).

### Proof of Concept
1. Victim `V` calls `purchase()` on `BandwidthManager.sol` for `app = V_APP`, buying `TierFour` ($1000 / 8MB / 30 days) intended to cover a month of traffic. This credits one `Subscription` into `Allowance::(app_chain, V_APP)`. [6](#0-5) 
2. Attacker `A`, with no relation to `V_APP`, repeatedly calls `purchase(app = V_APP, tier = TierOne, months = 1, chain = app_chain)` from their own account, paying only the (cheapest) `TierOne` price each time.
3. Each call reaches `on_accept`, which authenticates only the manager contract, decodes `msg.app = V_APP`, and calls `push_subscription(app_chain, V_APP, ...)`: [7](#0-6) 
4. After 1024 attacker-issued purchases, the queue is full; the 1025th attacker purchase evicts the oldest entry — which is `V`'s legitimately purchased, still largely unconsumed `TierFour` subscription — emitting `SubscriptionEvicted{ lost_bytes: <V's remaining bytes> }`.
5. `V`'s paid-for bandwidth allowance is destroyed without `V`'s consent or any action from `V`; `V` must repurchase to regain service, while the attacker never needed access to `V`'s account, keys, or any privileged role.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
