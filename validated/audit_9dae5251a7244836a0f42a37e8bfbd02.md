### Title
Stateful global regex in `testForInvalidChars` can allow a malicious deep-link branch name to bypass ref-name validation - ([File: app/src/lib/sanitize-ref-name.ts])

### Summary
The report's underlying pattern is a validation invariant that is assumed to hold consistently across the codebase but is not actually enforced the way callers expect, causing an attacker-influenced value to be accepted when it should be rejected. In GitHub Desktop, the ref-name validation function used to gate branch names coming from an `x-github-client://openRepo/...` deep link shares a single module-level regular expression object declared with the global (`g`) flag, and validates untrusted input using `RegExp.prototype.test()`.

### Finding Description
`invalidCharacterRegex` is defined once at module scope with the `g` flag and is used by two different exported functions: `sanitizedRefName()` (via `.replace()`) and `testForInvalidChars()` (via `.test()`): [1](#0-0) 

`RegExp.prototype.test()` on a global regex is stateful: it mutates the shared `lastIndex` property of the regex object and resumes scanning from that offset on the next call, only resetting to 0 after a call that returns `false`. Because `invalidCharacterRegex` is a single shared, module-scoped object, any prior `.test()` call (or interleaved `.replace()` call elsewhere in the process) can leave `lastIndex` at a non-zero offset. A subsequent `testForInvalidChars(branch)` call on a new, attacker-controlled `branch` string then begins scanning past the start of the string, so illegal/control characters located before the current `lastIndex` offset are silently skipped and the function can incorrectly report `false` (no invalid characters found) even though the string does contain characters that `git check-ref-format` would reject.

This function directly gates the `branch` parameter parsed out of an "Open in Desktop" / CLI clone deep link: [2](#0-1) 

If validation is bypassed, the raw, attacker-supplied `branch` string flows unmodified through `parseAppURL` → `dispatchCLIAction`/`openRepositoryFromUrl` → `openBranchNameFromUrl` → `checkoutLocalBranch`, which ultimately invokes a `git checkout`/branch-creation git command with that string as an argument: [3](#0-2) [4](#0-3) 

This is the same class of "the enforced check does not match what other code paths assume" bug described in the source report: the report flags that `InfraredBERAConstants`/`InfraredBERADepositor.execute()` enforce a value that is not actually in sync with what `BeaconDeposit` enforces, causing an invariant mismatch. Here, `sanitizedRefName` (the "sanitizer" used elsewhere, e.g. in the ref-name text box UI) and `testForInvalidChars` (the "validator" used to gate deep-link input) are supposed to police the exact same invalid-character set, but because they share one stateful global-flag `RegExp` instance, the validator's actual behavior silently drifts from its specification depending on prior calls — an in-flux/inconsistent enforcement path exactly analogous to the report's root cause.

### Impact Explanation
An attacker who can get a victim to click a crafted `x-github-client://openRepo/...` (or platform-legacy `github-mac://`/`github-windows://`) deep link controls the `branch` query parameter that GitHub Desktop passes to `git checkout`/branch creation without shell-quoting concerns handled elsewhere. If the character-class check that is supposed to strip out control characters, `~^:?*[\|"<>`, `@{`, leading dashes, `..`, and `.lock` suffixes is bypassed due to the stale `lastIndex`, a value containing a leading `-` or other git-significant characters could reach the underlying git invocation, resulting in unexpected git argument/option injection during checkout, or a ref name that corrupts local repository state (silent corruption of what the user later commits/pushes on that branch). This matches the "Valid Impact" category of a link/deep-link the user clicks resulting in silent corruption of git operations.

### Likelihood Explanation
Low-to-Medium. Exploitation requires: (1) getting the app to invoke `testForInvalidChars` in a state where `lastIndex` is non-zero from a prior call (e.g., a previous deep link, or another code path reusing the same imported module-level regex object during the same process lifetime), and (2) crafting a `branch` string whose invalid characters occur before the resumed scan offset. Because the regex is a shared singleton imported across the app process (not re-created per call), this is plausible in a long-running Electron process handling repeated deep links, but is timing/state dependent rather than deterministic on the very first call.

### Recommendation
1. Never call `.test()` (or `.exec()`) on a regex with the global (`g`) flag when it needs to be stateless; either remove the `g` flag from a dedicated validation-only regex, or reset `lastIndex = 0` before/after every `.test()` call.
2. Use two distinct `RegExp` instances (or clone the pattern) for `sanitizedRefName` (replace, global) and `testForInvalidChars` (test, non-global) so the two "specifications" cannot drift from each other via shared mutable state.
3. Add a regression test that calls `testForInvalidChars` multiple times in a row with different malicious inputs to confirm each call is evaluated independently.

### Proof of Concept
```ts
import { testForInvalidChars } from 'app/src/lib/sanitize-ref-name'

// First call consumes/advances the shared global regex's lastIndex
// past the invalid character it matched.
testForInvalidChars('a\x00'.padEnd(50, 'x')) // true, lastIndex now > 0

// Second call, with a NEW attacker-controlled string that has an
// invalid character located before the current lastIndex offset,
// can incorrectly return false because .test() resumes scanning
// from the stale lastIndex instead of position 0.
testForInvalidChars('\x00malicious-branch-name') // may incorrectly report false
```
This mirrors how `parseAppURL` invokes `testForInvalidChars(branch)` once per deep-link event on a long-lived, shared module instance [5](#0-4) , so state left over from handling one deep link/CLI action can affect validation of a subsequently processed one, letting an unsanitized branch string reach `checkoutLocalBranch` [6](#0-5) .

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
