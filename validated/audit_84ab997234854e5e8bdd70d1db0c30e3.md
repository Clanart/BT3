### Title
Missing ref/URL sanitization on PR-checkout path lets a malicious fork PR inject unsanitized `head.ref`/`clone_url` into git operations - ([File: app/src/ui/dispatcher/dispatcher.ts])

### Summary
GitHub Desktop validates a branch name against `testForInvalidChars()` when it originates from a `x-github-client://openRepo` deep link, but the sibling code path that checks out a pull request's head branch — where the ref name and remote URL are taken directly from the GitHub API's PR object (attacker-controlled if the PR is from a fork) — never applies that same validation. This is the same broken-invariant pattern as the USDKG report: a security check (`notBlackListed`/`testForInvalidChars`) is enforced on one caller of a sensitive operation but omitted on a second caller that reaches the exact same sink.

### Finding Description
`app/src/lib/parse-app-url.ts` validates `branch` coming from a deep link before it's ever used: [1](#0-0) 

That validated `branch` flows into `Dispatcher.openBranchNameFromUrl`, which eventually calls `checkoutLocalBranch`: [2](#0-1) 

However, the pull-request path in the very same file builds its checkout target entirely from the GitHub API response — `pullRequest.head.repo.owner.login`, `pullRequest.head.repo.clone_url`, and `pullRequest.head.ref` — and passes them straight into `_checkoutPullRequest` with **no** call to `testForInvalidChars`/`sanitizedRefName` (compare to `app/src/lib/sanitize-ref-name.ts`, which exists precisely to strip git-unsafe characters such as leading `-`/`+`, `~^:?*[\|<>`, and other ref-format-breaking sequences): [3](#0-2) [4](#0-3) 

All three of these values (`owner.login`, `clone_url`, `head.ref`) are attacker-controlled when the pull request is opened from a fork the attacker controls: the fork owner name, the fork's clone URL, and the head branch name are all fields the PR author sets, and Desktop consumes them unvalidated once a user opens/views that PR in Desktop (`openPullRequestFromUrl` is reachable via the `openrepo?pr=` URL action as well as normal PR checkout flows).

### Impact Explanation
`sanitizedRefName`/`testForInvalidChars` exist specifically because branch names are eventually interpolated into git command invocations, and a ref beginning with `-` (e.g. `--upload-pack=...`, `--exec=...`) or containing control characters can be interpreted as a command-line flag rather than a literal ref by git subcommands — the classic "git argument injection" class. Because the PR-checkout path skips this check, a hostile fork PR can supply a `head.ref` or a `clone_url` that was never meant to be treated as an option, and this could be interpreted as a flag by whatever git command (`fetch`, `checkout`, `remote add`) ultimately consumes it. In the report's terms, the "spender" (the PR/API path) is missing the exact guard that the "sender" (the URL path) has, letting an attacker corrupt or hijack the git operation the user believes is a normal branch checkout.

### Likelihood Explanation
Exploitation requires only that a victim open (or Desktop auto-selects) a pull request from an attacker-controlled fork — no local access, no elevated privileges, and no unusual user action beyond viewing/checking-out a PR, which is core, expected Desktop functionality. The asymmetry is directly visible in code: one call site sanitizes, the sibling call site to the same underlying checkout logic does not.

### Recommendation
Apply the same validation used in `parse-app-url.ts` (`testForInvalidChars`/`sanitizedRefName`) to `pullRequest.head.ref`, `pullRequest.head.repo.owner.login`, and `pullRequest.head.repo.clone_url` before they are passed to `_checkoutPullRequest` in `app/src/ui/dispatcher/dispatcher.ts`. Reject or sanitize any PR-derived ref/URL that fails the check, mirroring how the deep-link path already refuses unsafe branch input.

### Proof of Concept
1. Attacker forks a public repo and creates a branch named `--upload-pack=/tmp/evil` (or another `-`-prefixed value permitted by `git check-ref-format` edge cases/GitHub API) in their fork.
2. Attacker opens a pull request from that branch against the upstream repo.
3. Victim, using GitHub Desktop, opens/checks out that pull request (via the PR list or via an `x-github-client://openrepo?...&pr=<n>` deep link).
4. `openPullRequestFromUrl` fetches the PR object and calls `_checkoutPullRequest` with the raw, unsanitized `pullRequest.head.ref` — unlike the equivalent `openBranchNameFromUrl` path, no `testForInvalidChars` check runs first, so the malicious value reaches the git invocation unchecked.

Note: I was not able to fully trace the exact dugite/git invocation inside `_checkoutPullRequest` in `app/src/lib/stores/app-store.ts` within the available search budget (index limits), so I cannot confirm with certainty whether the underlying git call uses an argument array with a `--` separator that would neutralize a leading-dash ref. This missing confirmation is the main uncertainty in this analog; the asymmetry in validation between the two call sites in `dispatcher.ts`, however, is directly confirmed in code.

**File:** app/src/lib/sanitize-ref-name.ts (L1-16)
```typescript
// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
```
