### Title
Operator reimbursement is attributed purely from OP_RETURN bytes in the Payout tx, letting an attacker who controls the registered withdrawal UTXO self-fund a payout and frame a real operator into claiming reimbursement it never funded - (core/src/verifier.rs)

### Summary
`create_payout_txhandler` builds the Payout tx's withdrawal input with `SpendableTxIn::new_partial`, which carries no cryptographic or economic link to any operator, and the withdrawer's `SinglePlusAnyoneCanPay` signature only commits to input#0/output#0, leaving the OP_RETURN output (which names the "paying" operator) completely unsigned and attacker-controllable. `update_finalized_payouts` then attributes reimbursement eligibility to whichever xonly_pk appears in that unsigned OP_RETURN, with no check that the named operator actually funded the transaction, and `PayoutCheckerTask` automatically consumes this attribution to trigger a real kickoff/reimbursement claim against the deposit's move-to-vault UTXO.

### Finding Description
The binding claimed to hold is:
`operator_xonly_pk` parsed from the Payout tx's OP_RETURN (`core/src/verifier.rs:2319-2321`) == the xonly_pk of the entity whose funds actually paid `output_txout.value` to the withdrawer in that same Payout tx.

Tracing the code shows this binding does not exist anywhere:

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the withdrawal input via `SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout)` (`core/src/builder/transaction/input.rs:45-47`), which stores only an `OutPoint`/`TxOut` — no key, script commitment, or link to any operator identity.
- The withdrawer's signature uses `TapSighashType::SinglePlusAnyoneCanPay` (see the test helper at `core/src/test/common/setup_utils.rs:499-543`, which mirrors production usage). `SIGHASH_SINGLE|ANYONECANPAY` only commits input#0 to output#0; it commits nothing to the anchor output or the OP_RETURN output, and it does not prevent the signer (who owns the withdrawal UTXO) from adding extra inputs to fund fees/output value themselves.
- Because a withdrawer who is also the depositor/attacker holds the private key of the withdrawal dust UTXO, they can sign this input for ANY output configuration they like, fund `output_txout` entirely from their own separate UTXO(s) (ANYONECANPAY permits attaching arbitrary extra inputs), and freely choose the OP_RETURN bytes to be any operator's `xonly_pk` — including one they don't control at all.
- The attacker registers this dust UTXO as the withdrawal UTXO themselves by calling Citrea's `withdraw` (attacker capability, explicitly allowed), so `get_withdrawal_utxo_from_citrea_withdrawal` (`core/src/database/verifier.rs:139-166`) matches it once Citrea syncs.
- Attacker broadcasts this self-funded, self-signed Payout tx directly to Bitcoin, bypassing `Operator::withdraw`'s `is_profitable` check entirely (`core/src/operator.rs:560-627`), since that check only runs when an operator itself calls the RPC — it is never invoked for transactions broadcast directly to the network.
- When the tx confirms, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) finds it via `get_payout_txs_for_withdrawal_utxos` (matches purely by which tx spent the registered withdrawal UTXO, `core/src/database/verifier.rs:170-196`), extracts `operator_xonly_pk` purely from the OP_RETURN bytes (`core/src/verifier.rs:2319-2321`), and writes it into `withdrawals.payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`) — with zero verification that this xonly_pk's owner funded anything in the transaction.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) automatically polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` (`core/src/database/verifier.rs:282-313`) and, upon match, automatically calls `Operator::handle_finalized_payout` (`core/src/operator.rs:839-916`), which allocates a kickoff connector and constructs/signs a real Kickoff tx — with no validation that the operator actually funded the underlying Payout tx.
- Later, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) only checks that the OP_RETURN xonly_pk equals `kickoff_data.operator_xonly_pk` (same DB-sourced value) and that a committed blockhash matches — it never checks the actual Bitcoin-level source of funds in the Payout tx.
- The eventual `Reimburse` tx (`core/src/builder/transaction/operator_reimburse.rs:341-385`) pays out the full deposited `DepositInMove` value to the named operator's reimbursement address, completing the drain of the vault UTXO without any equivalent value having actually been fronted by that operator.

No existing guard (`is_profitable`, `SECP.verify_schnorr`, `is_kickoff_malicious`, storage proof verification, SPV, or database uniqueness) checks that the funding source of the Payout tx matches the OP_RETURN-named operator; they only check that IDs/hashes are internally consistent with what was already recorded from the OP_RETURN itself.

### Impact Explanation
Value leaves a move-to-vault UTXO (the deposit's collateral) via a Reimburse tx crediting an operator that never funded the actual withdrawal payout — matching the Critical category "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" / "an operator reimbursed for a payout it never funded." The attacker forces the bridge's bookkeeping to record an arbitrary operator as payer using bytes they fully control and never sign meaningfully. This is repeatable for every deposit/withdrawal pair the attacker controls and can target any operator xonly_pk they choose to name, since the OP_RETURN is unauthenticated.

### Likelihood Explanation
The only preconditions are attacker capabilities explicitly granted: making a deposit, calling Citrea `withdraw` with a self-chosen UTXO, signing with a chosen sighash flag, and broadcasting a Bitcoin transaction with an arbitrary OP_RETURN — all listed as in-scope attacker abilities. No verifier/operator/aggregator privilege, TLS cert, or key compromise is needed. Cost is only Bitcoin fees plus the dust amount funding their own withdrawal output. This is fully reproducible without mainnet or live Citrea using the existing regtest/mock-Citrea test harness (`core/src/test/deposit_and_withdraw_e2e.rs`, `core/src/test/manual_reimbursement.rs`).

### Recommendation
Bind the OP_RETURN operator attribution to a cryptographic commitment: require the withdrawer's signature (or a separate signature) to cover the OP_RETURN output (e.g. use `SIGHASH_ALL` for the operator-fronted flow, or have the operator co-sign/attach a signature over the whole payout tx), and/or require `update_finalized_payouts` to verify that the claimed operator's key actually authorized/funded an input or output in the transaction before recording `payout_payer_operator_xonly_pk`. Additionally, require `handle_finalized_payout`/`PayoutCheckerTask` to independently verify the Payout tx's structure (amount funded, source of extra inputs) matches an expected profitable-withdrawal shape rather than trusting DB-recorded OP_RETURN bytes alone.
