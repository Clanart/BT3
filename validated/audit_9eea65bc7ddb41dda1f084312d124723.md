### Title
Missing zero-address validation on `_to` in `BridgeTransferKLAY.requestKLAYTransfer` permits unrecoverable burning of user-locked KLAY - (File: contracts/service_chain/bridge/BridgeTransferKLAY.sol)

### Summary
`BridgeTransferKLAY.requestKLAYTransfer` and its internal helper `_requestKLAYTransfer` accept an arbitrary `_to` address and lock the user's KLAY in the bridge contract without validating that `_to != address(0)`. If a user (or a front-end/relayer acting on a malformed input) submits `_to = address(0)`, the request is accepted, KLAY is locked in the bridge, and the corresponding `RequestValueTransfer` event is emitted with a zero destination. When an operator later processes this on the counterpart chain via `handleKLAYTransfer`, the contract executes `_to.call.value(_value)("")` to the zero address, which succeeds silently (a plain value-transfer call to `address(0)` does not revert) and the funds become permanently unrecoverable.

### Finding Description
The permissionless entry point: [1](#0-0) 
calls the internal transfer logic: [2](#0-1) 
Neither function checks `_to != address(0)`. The corresponding `handleKLAYTransfer`, which any operator executes on the counterpart chain to release the locked value, performs a raw low-level call to `_to` with the transferred value and only checks that the call succeeded: [3](#0-2) 
A `.call.value(...)("")` targeting `address(0)` succeeds (there is no revert for sending value to the zero address in Solidity 0.5.x), so `ok` is `true` and the transaction completes normally while the KLAY is effectively burned/lost forever, with no way to recover the corresponding locked funds on the source chain.

This mirrors the pattern in the referenced Sherlock report: a value-transfer function accepting a `receiver`/`_to` parameter without a zero-address check, allowing funds to be irrecoverably destroyed instead of delivered.

### Impact Explanation
Any unprivileged, unauthenticated caller can invoke `requestKLAYTransfer(address(0), value, extraData)` directly (it is an `external payable` function with no access control other than `unlockedKLAY`/`isRunning`). This causes:
- Permanent loss of the transferred KLAY once the counterpart-chain operator processes the request (loss of user funds).
- No revert or on-chain signal preventing this outcome — the bug can be triggered accidentally (fat-fingered zero address) or maliciously (e.g., an attacker griefing a victim's UI/integration by tricking it into submitting a zero `_to`, or a compromised/malfunctioning relayer/front-end defaulting to a zero address).
- Because `_to` also appears in the `RequestValueTransfer`/`HandleValueTransfer` events and is entirely attacker/user-controlled, there is no compensating validation elsewhere in the bridge stack (`BridgeTransfer.sol`, `BridgeFee.sol`) that rejects a zero destination.

This satisfies the "concrete unauthorized value movement" / fund-loss bar, reachable purely via a single submitted transaction from an unprivileged sender.

### Likelihood Explanation
Likelihood is moderate: exploitation requires either (a) a user or integrating dApp mistakenly passing `address(0)` as `_to` (common bug class in bridge/relayer software when an unresolved or default address gets passed through), or (b) deliberate griefing where an attacker crafts/relays a transaction with `_to = address(0)` on behalf of a victim's approved flow. Since `requestKLAYTransfer` has no allowlist or restriction on `_to`, and the function is fully public, the precondition (a permissionless call with a zero address) is trivially satisfiable in a single transaction.

### Recommendation
Add an explicit zero-address check in `_requestKLAYTransfer` (and analogously in the ERC20/ERC721 request-transfer counterparts in `BridgeTransferERC20.sol`/`BridgeTransferERC721.sol` if they exhibit the same gap) before accepting funds:
```solidity
function _requestKLAYTransfer(address _to, uint256 _feeLimit, bytes memory _extraData)
    internal
    unlockedKLAY
    nonReentrant
{
    require(_to != address(0), "receiver is the zero address");
    require(isRunning, "stopped bridge");
    require(msg.value > _feeLimit, "insufficient amount");
    ...
}
```
Additionally, consider adding a defensive `require(_to != address(0), ...)` in `handleKLAYTransfer` as a second line of defense, in case a legitimate zero-address request somehow reaches the handle stage.

### Proof of Concept
1. An unprivileged user calls `bridge.requestKLAYTransfer(address(0), value, "0x")` with `msg.value = value + feeLimit`.
2. `_requestKLAYTransfer` executes without any revert since there is no zero-address check; KLAY is locked in the bridge contract and a `RequestValueTransfer` event with `_to = address(0)` is emitted.
3. An operator later observes this event (per the off-chain bridge_manager flow shown in `node/sc/bridge_manager.go`'s `handleRequestValueTransferEvent`, which forwards `to` unchanged) and calls `handleKLAYTransfer(txHash, from, address(0), value, nonce, blockNum, extraData)` on the counterpart chain.
4. `handleKLAYTransfer` executes `(bool ok, ) = address(0).call.value(_value)("")`, which returns `ok = true` (no revert), so the funds are sent to `address(0)` and permanently lost, while the bridge marks the request as successfully handled. [4](#0-3)
