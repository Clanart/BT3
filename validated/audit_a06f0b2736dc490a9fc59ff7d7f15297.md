### Title
LP receipt tokens minted from requested amount instead of actually-received amount in `depositLP` - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.deposit()` correctly derives the amount to mint/stake by measuring the LP-token balance delta before/after the external deposit call, protecting against fee-on-transfer/deflationary behavior. `WombatStaking.depositLP()`, however, does not use this pattern: it pulls tokens with `safeTransferFrom` and then mints receipt tokens and stakes to Master Wombat using the caller-supplied `_lpAmount` directly, without verifying the amount actually received.

### Finding Description
In `deposit()`, the actually-received LP amount is computed explicitly: [1](#0-0) 

In `depositLP()`, by contrast, the requested `_lpAmount` is used verbatim for both staking accounting and receipt-token minting, with no balance-delta check against what `safeTransferFrom` actually delivered: [2](#0-1) 

This function is reachable by an ordinary wallet through the pool helper, which itself does not correct for this discrepancy — it only measures the balance change of the *receipt* token it receives from `WombatStaking`, not of the underlying LP token consumed inside `WombatStaking.depositLP`: [3](#0-2) 

If `poolInfo.lpAddress` were ever a fee-on-transfer/deflationary token, `IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount)` would deliver less than `_lpAmount` to `WombatStaking`, while `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` mints the full requested amount and `_toMasterWomAndSendReward(_lpAddress, _lpAmount, true)` attempts to stake/report the full requested amount as well — a mismatch between real custody and the claims (receipt tokens) issued against it.

### Impact Explanation
This maps to the "restrict deflationary tokens" bug class from the report: receiving fewer real tokens than accounted for while incrementing user-facing balances 1:1 breaks the internal accounting invariant, potentially causing protocol insolvency (receipt-token supply exceeds actual LP custody) or reverts that freeze the deposit path for that pool.

### Likelihood Explanation
Likelihood depends entirely on whether `poolInfo.lpAddress` (the Wombat Asset/LP token registered per pool) is ever a fee-on-transfer/rebasing token. Based on the reviewed code, LP tokens registered via `registerPool` are standard Wombat Asset tokens external to this codebase, and I found no evidence within this repo that any registered LP token is deflationary — this determination depends on the specific token contracts deployed for each pool, which are out of scope for this repo. I cannot confirm with certainty from the available code whether this is exploitable in the current production deployment, only that the code pattern itself lacks the same protection that `deposit()` has.

### Recommendation
Mirror the `deposit()` pattern in `depositLP()`: measure `IERC20(poolInfo.lpAddress).balanceOf(address(this))` before and after the `safeTransferFrom`/staking step, and use the actual delta for both `_toMasterWomAndSendReward` and the receipt-token `mint` amount, or explicitly document/enforce that only non-fee-on-transfer LP tokens may be registered via `registerPool`.

### Proof of Concept
1. Owner registers a pool whose `lpAddress` is a fee-on-transfer token (via `registerPool`).
2. A user calls the pool helper's `depositLP(_lpAmount)`, which calls `WombatStaking.depositLP(lpToken, _lpAmount, msg.sender)`.
3. `safeTransferFrom(_for, address(this), _lpAmount)` transfers `_lpAmount * (1 - fee)` actual tokens to `WombatStaking`.
4. `receiptToken.mint(msg.sender, _lpAmount)` mints the full `_lpAmount`, and `_toMasterWomAndSendReward` operates on the same over-stated `_lpAmount`, creating a mismatch between minted receipt-token supply and real LP custody in the contract.
