### Title
Monotonic per-feed oracle timestamp check causes single-block DoS for time-sensitive market actions - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`price-resolve` in the Zest market contract enforces a non-decreasing per-feed timestamp via `oracle-timestamp-fresh`, requiring the fetched oracle timestamp to be `>=` the last stored timestamp for that feed. Because prices are pulled live per-call rather than pinned by the caller, any transaction that fetches a slightly older (but still valid/fresh) Pyth/DIA price than one already recorded for that feed in a prior transaction will revert, exactly mirroring the RedStone report's root cause (a non-decreasing/monotonic oracle-timestamp validation applied to time-sensitive actions).

### Finding Description
`price-resolve` fetches a feed's price and timestamp, then asserts freshness and monotonicity before accepting it: [1](#0-0) [2](#0-1) 

The predicate `oracle-timestamp-fresh` requires `(>= ts prev)`, where `prev` is `oracle-last-update key` — the last timestamp seen for that `{type, ident}` feed, stored in a per-feed map and updated whenever a strictly newer timestamp is observed: [3](#0-2) 

For Pyth-sourced feeds, `resolve-pyth` reads `publish-time` directly from the on-chain `pyth-storage-v4` mapping populated by push-based relayer updates, and for DIA it converts the stored millisecond timestamp: [4](#0-3) 

Since prices are read from these on-chain storage contracts at call time rather than embedded per-transaction like RedStone calldata, the direct analog is slightly different in mechanics but identical in the bug class: `last-update` is a shared, feed-level (not user-scoped) monotonic timestamp gate. Any transaction that reads the feed after a relayer has already pushed a newer `publish-time` for that same feed (which any other unrelated market action, or even another user's transaction, can trigger) will find `oracle-last-update` already advanced past what is momentarily available, and any subsequent read that observes a timestamp older than the already-recorded `last-update` (e.g., due to relayer/indexer propagation delays, or a temporarily rolled-back/older cached price feed value) is unconditionally rejected via `ERR-ORACLE-INVARIANT`, regardless of whether that price is otherwise fresh and legitimate per `max-staleness`.

### Impact Explanation
`price-resolve`/`price-multi-resolve` are invoked by all account-health-dependent actions (borrow, withdraw, liquidation checks) since `oracle-price-legal`/`oracle-timestamp-fresh` gate every price lookup with `ERR-ORACLE-INVARIANT`. A revert here blocks time-sensitive operations — most notably liquidations and borrows against fluctuating collateral — for the duration that the shared `last-update` value for a feed remains ahead of what the reverting transaction observes. This is a temporary freezing-of-funds/operations condition (a single-block-scoped DoS on time-sensitive functions), matching the accepted Sherlock precedent that graded the equivalent RedStone case as Medium because it can block time-critical liquidation/borrow calls.

### Likelihood Explanation
No malicious action is strictly required — normal relayer/oracle update cadence, or divergent read timing on multiple market calls in the same block, can cause `oracle-last-update` for a feed to advance ahead of a later-arriving but valid price observation, causing that action to revert with `ERR-ORACLE-INVARIANT`. An attacker could also intentionally spam price-refreshing calls to keep `last-update` maximally advanced, deterministically griefing others' borrow/liquidate transactions that read a marginally older (but valid) price in the same block.

### Recommendation
Remove or relax the `(>= ts prev)` monotonicity requirement in `oracle-timestamp-fresh` at [1](#0-0) , and rely solely on the `max-staleness` freshness check (delta between `stacks-block-time` and the feed's own `publish-time`) to validate price validity, consistent with how the underlying Pyth/DIA storage contracts already enforce their own staleness and update-ordering guarantees.

### Proof of Concept
1. Feed `X` has `last-update[X] = T2` after a relayer push or a market call that observed `publish-time = T2`.
2. A separate transaction (e.g., a borrow or liquidation call) calls `price-resolve` for feed `X` and, due to read timing or a temporarily observed older cached price, obtains `publish-time = T1 < T2` while still within `max-staleness` of `stacks-block-time`.
3. `oracle-timestamp-fresh` evaluates `(>= T1 T2)` as `false`, so `price-resolve` returns `ERR-ORACLE-INVARIANT` at [5](#0-4) , reverting the borrow/liquidation call even though the price is otherwise valid and fresh, causing exactly the DoS pattern described in the referenced report.

  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
