## Title
Division-before-multiplication in NFT royalty computation truncates royalty payments to NFT creators - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`compute_royalty_amount()` computes the royalty owed to an NFT's royalty address when it is requested/offered as part of a trade offer. The formula performs an integer division by `royalty_split` **before** multiplying by `percentage`, then divides again by `MAX_ROYALTY_BASIS_POINTS`. This double-floor arithmetic systematically truncates the royalty amount below its mathematically correct value, and any wallet user constructing an NFT offer controls the inputs (`offered_amount`, `royalty_split`) that determine how much value is lost.

### Finding Description
The vulnerable code is: [1](#0-0) 

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    ...
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    ...
    return royalty
```

The mathematically correct royalty is `abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`, i.e. multiplication should happen before any division. Instead, the code divides by `royalty_split` first (`abs(offered_amount) // royalty_split`), discarding the remainder, and only then multiplies by `percentage` and divides by `MAX_ROYALTY_BASIS_POINTS`. This compounds two floor operations instead of one, which is exactly the "division before multiplication" pattern described in the reference report — it strictly under-computes the amount owed relative to the correct single-floor calculation.

This function is called from `NFTWallet.make_nft1_offer()`, a path reachable by any wallet user building an offer that trades fungible assets for one or more royalty-enabled NFTs: [2](#0-1) 

```python
        royalty_payments: dict[bytes32 | None, list[tuple[bytes32, CreateCoin]]] = {}
        for asset, amount in fungible_asset_dict.items():  # offered fungible items
            if amount < 0 and request_side_royalty_split > 0:
                payment_list: list[tuple[bytes32, CreateCoin]] = []
                for launcher_id, address, percentage in required_royalty_info:
                    extra_royalty_amount = compute_royalty_amount(amount, request_side_royalty_split, percentage)
                    payment_list.append((launcher_id, CreateCoin(address, extra_royalty_amount, [address])))
                royalty_payments[asset] = payment_list
```

The same double-floor pattern also appears independently in the royalty-preview helper used by the RPC/CLI to show users how much royalty an offer will pay: [3](#0-2) 

```python
            for name, amount in fungible_asset_dict.items():
                summary_dict[id].append(
                    {
                        "asset": name,
                        "address": address,
                        "amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
                    }
                )
```

Because `royalty_split` (the number of royalty-NFTs requested on one side of the trade) and `offered_amount` are both parameters an offer-creating wallet chooses, an offerer can pick values (e.g. `offered_amount` not evenly divisible by `royalty_split`) to maximize the truncation and pay the royalty-address (the NFT creator/beneficiary) strictly less than the intended `percentage` of the traded value.

### Impact Explanation
Royalty payments are a core economic guarantee of NFT1 royalty-enabled offers in Chia's offer protocol — the royalty recipient is supposed to receive `percentage` of the traded value split evenly among the requested royalty NFTs. Due to the double-floor bug, royalty recipients receive systematically less than entitled, and the loss is compounded and offerer-influenced (choice of amounts and NFT counts controls the magnitude of the shortfall). This is a concrete instance of offer-settlement value diversion away from the intended royalty beneficiary, reachable by any wallet user constructing an NFT offer — no privileged access required.

### Likelihood Explanation
This triggers on every offer that trades a fungible asset against more than one royalty-enabled NFT (or any offer where `abs(offered_amount)` is not exactly divisible by `royalty_split`), which is a normal, commonly used offer pattern (`make_nft1_offer`). No special conditions or race are needed — the bug fires deterministically based on chosen offer amounts.

### Recommendation
Reorder the arithmetic to multiply before dividing, doing a single floor division at the end, matching the reference fix pattern:

```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```

Apply the same fix to the preview calculation in `royalty_calculation()`:
```python
"amount": abs(amount) * percentage // (len(royalty_assets_dict) * MAX_ROYALTY_BASIS_POINTS),
```

### Proof of Concept
Using `compute_royalty_amount` directly (as tested in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py`):
```python
# offered_amount = -1000, royalty_split = 3, percentage = 500 (5%)
# Correct:  1000 * 500 // (3 * 10000) = 16
# Buggy:    1000 // 3 * 500 // 10000  = 333 * 500 // 10000 = 16 (equal here, but for less friendly numbers:)

# offered_amount = -999, royalty_split = 3, percentage = 500
# Correct:  999 * 500 // (3 * 10000) = 16
# Buggy:    999 // 3 * 500 // 10000  = 333 * 500 // 10000 = 16

# offered_amount = -100, royalty_split = 3, percentage = 9900 (near-max allowed)
# Correct:  100 * 9900 // (3 * 10000) = 33
# Buggy:    100 // 3 * 9900 // 10000 = 33 * 9900 // 10000 = 32   <-- truncated, loses 1 unit (~3%)
```
As `offered_amount`, `royalty_split`, and `percentage` scale up (real coin amounts are mojos, up to 2^63), the absolute truncated value scales proportionally, letting an offerer systematically underpay royalty-entitled NFT creators on every multi-NFT royalty offer they construct.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
