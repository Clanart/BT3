## Analysis

The Renzo bug's broken invariant is: **a security guard is applied inconsistently across structurally identical call paths**, so the guard protects one path while an equivalent, equally-reachable path is left exposed to the exact primitive the guard was meant to stop (in Renzo's case, a legitimate nested call blocked by `nonReentrant` on one path but expected elsewhere in the same flow). The Desktop analog to search for is a validation/guard applied to one file-path-opening flow but omitted from a structurally identical one.

I found this pattern in the file-path-traversal guard `resolveWithin` (`app/src/lib/path.ts`). It's correctly applied to the deep-link ("Open in Desktop") file-open flow, but is missing from several other flows that open/reveal file paths sourced directly from git status/diff/commit content — content that is fully attacker-controlled when the user opens a malicious cloned/fetched repository.

### Title
Path-traversal guard (`resolveWithin`) is applied to deep-link file opens but missing from Changes/History file context-menu actions, allowing a malicious repository to open/reveal files outside the repo - (File: `app/src/lib/app-shell.ts`)

### Summary
`app/src/ui/dispatcher/dispatcher.ts`'s `openRepositoryFromUrl` explicitly resolves a URL-supplied `filepath` with `resolveWithin(repository.path, filepath)` and refuses to proceed if the result escapes the repository root, logging "Prevented attempt to open path outside of the repository root". [1](#0-0) 

However, the same class of operation — opening or revealing a file identified by a path that comes from the repository's own tracked/working-directory content (`WorkingDirectoryFileChange`/`CommittedFileChange.path`) — is performed elsewhere using a raw `Path.join(repository.path, path)` with **no** `resolveWithin` check:

- `revealInFileManager` in `app/src/lib/app-shell.ts` [2](#0-1) 
- `onOpenItem` in the Changes sidebar [3](#0-2) 
- `onOpenItem`/`onContextMenu` in the commit history file list [4](#0-3) 
- `open()` in `BinaryFile` diff view [5](#0-4) 
- `onOverflowMenuClick` in the Copilot conflict resolution dialog [6](#0-5) 
- `onOpenInExternalEditor` in `app.tsx` [7](#0-6) 

Notably, the codebase already contains an explicit, dedicated test proving the team is aware that a tracked path can be turned into an escape via a symlinked directory component, and that `resolveWithin` is the fix: `resolveWithin` fails when a symlink is used to traverse outside the root. [8](#0-7) 

### Finding Description
`path`/`file.path` values displayed in the Changes list and History view originate from `git status`/`git diff`/`git show` output, parsed in `app/src/lib/status-parser.ts`, which performs no traversal or symlink sanitization on the raw path strings it extracts. [9](#0-8) 

Git's working tree can legitimately contain a file whose relative path passes through a symlinked directory (e.g., a tracked or untracked directory-name entry that is a symlink pointing outside the repository, created by a previous checkout of the same or a different branch, or shipped as a tracked symlink itself). When the user clicks "Reveal in Finder/Explorer," "Open with Default Program," or "Open in External Editor" for such an entry, Desktop computes the target path as `Path.join(repository.path, path)` and passes it directly to `shell.showItemInFolder`, `shell.openExternal`, or an external editor spawn — all without ever calling `resolveWithin` to confirm the resolved path still lies inside the repository. This is exactly the risk the deep-link code path already treats as a vulnerability worth guarding against (see the `resolveWithin` call and the "Prevented attempt to open path outside of the repository root" log line). [10](#0-9) 

The existing guard exists in only one of several equivalent sinks, so the fix does not stop the path through the Changes/History context menus.

### Impact Explanation
A malicious/attacker-controlled cloned or fetched repository can cause GitHub Desktop to reveal, open (with the OS default handler), or launch in an external editor a file located outside the repository's working directory, once the user interacts with a normal, expected UI affordance (context menu on a changed/committed file). This matches the "file write/read outside the repo" impact category driven purely by attacker-controlled repository content — no local/physical access, admin rights, or unnatural user steps are required beyond browsing a malicious repo's Changes/History tab, which is core, expected Desktop usage.

### Likelihood Explanation
Medium: it requires the user to open (clone/fetch) an attacker-supplied repository and interact with the file list (a very common action, e.g. reviewing a PR or examining commit contents), and it requires the underlying working tree to contain a symlinked path component or another mechanism git allows for placing a path that resolves outside the repo root. The engineering team's own `resolveWithin` symlink test demonstrates this escape technique is a recognized, real construction, not a hypothetical one. [8](#0-7) 

### Recommendation
Route every file path derived from repository content (`WorkingDirectoryFileChange.path`, `CommittedFileChange.path`) through `resolveWithin(repository.path, path)` before it is used in `revealInFileManager`, `onOpenItem`, `onContextMenu`, `BinaryFile.open`, the Copilot conflict dialog's overflow menu, and `onOpenInExternalEditor` — mirroring the check already performed in `dispatcher.ts`'s `openRepositoryFromUrl`. Treat a `null` result (path resolves outside the repo) the same way: refuse the action and log/warn instead of silently operating on the resolved path.

### Proof of Concept
1. Attacker publishes a repository whose working tree contains a symlinked directory component (or a tracked symlink) such that a reported changed/committed file path, when joined with the repository root, actually resolves (once the OS/shell follows the symlink) to a location outside the repository — analogous to the escape the project's own test constructs in `app/test/unit/path-test.ts` (`symlink(resolve(tempDir, '..', '..'), symlinkPath)`).
2. Victim clones/fetches this repository in GitHub Desktop and opens the Changes tab or Commit History for the affected commit.
3. Victim right-clicks the file and selects "Reveal in Finder/Explorer" or "Open with Default Program" (or opens a binary diff and clicks "Open file in external program").
4. Desktop computes `Path.join(repository.path, file.path)` in `app-shell.ts`/`sidebar.tsx`/`selected-commits.tsx`/`binary-file.tsx` and passes it straight to `shell.showItemInFolder` / `shell.openExternal` / the external editor launcher, without the `resolveWithin` containment check that the deep-link flow performs, revealing/opening the out-of-repo target. [2](#0-1)
