### Title
Payout output value/type is never validated by `bridge_circuit`, letting a withdrawer burn a payout to `OP_RETURN` while still tagging an operator as payer - ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
`bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:137-245`) only checks that the payout tx's spent input matches the withdrawal outpoint (`user_wd_txid`/`vout` equality, lines 190-204) and that *some* output is an `OP_RETURN` carrying an operator pubkey (`get_first_op_return_output`, line 206). It never inspects the `script_pubkey` type or `value` of any non-OP_RETURN output, so nothing in the circuit enforces that a spendable, non-zero-value payment was actually delivered to the withdrawer.

### Finding Description
The binding the system is supposed to enforce is:
`value(spendable output paid to withdrawer in payout_tx) == withdrawal_amount registered on Citrea`

Tracing `bridge_circuit`:
- Input equality is checked: `user_wd_txid == input[payout_input_index].previous_output.txid` and `vout == ...previous_output.vout` [1](#0-0) .
- `get_first_op_return_output` is used only to extract the operator's x-only pubkey for `deposit_constant`, and is documented merely as "Retrieves the first output of a transaction that is an OP_RETURN script" [2](#0-1) [3](#0-2) .
- No code path in `bridge_circuit` reads or asserts the value or `script_pubkey` kind of any other output (e.g. output index 0, the intended "user payout output" per `create_payout_txhandler`'s own doc comment) [4](#0-3) .

Because the withdrawal UTXO is spent via key-path (Taproot) with a user-controlled signature, whoever controls that private key (i.e., the withdrawer themselves, who is an in-scope unprivileged attacker able to register their own withdrawal and choose the signature/sighash flag) can construct and broadcast a payout tx directly to Bitcoin — bypassing the operator's `withdraw()` RPC entirely (which does enforce `SinglePlusAnyoneCanPay`/output binding via `SECP.verify_schnorr` at `core/src/operator.rs:630-637`, but that check only exists inside the operator's own RPC handler, not on-chain or in the circuit). The attacker-controlled payout tx can have:
- input spending the registered withdrawal outpoint (any sighash type, since the attacker owns the key),
- output 0: `OP_RETURN` carrying a target operator's x-only pubkey,
- output 1: `OP_RETURN`/zero-value junk,
- no spendable output paying the withdrawer anything.

Once this transaction confirms, the verifier's on-chain scanner blindly derives the "payer" purely from OP_RETURN content: `update_finalized_payouts` sets `payout_payer_operator_xonly_pk` to whatever pubkey is parsed from the first OP_RETURN, with no check that the operator actually funded/broadcast the tx [5](#0-4) . The `PayoutCheckerTask` for that operator then automatically picks up this "unhandled payout" purely by matching its own pubkey (`get_first_unhandled_payout_by_operator_xonly_pk`), and drives it into the kickoff/reimbursement flow [6](#0-5) . `is_kickoff_malicious` (the guard that would flag a bogus kickoff) only checks operator-pubkey match and the committed payout blockhash — never the paid amount or output script type [7](#0-6) . And even if a watchtower disputes the kickoff and forces a `bridge_circuit` proof, the circuit itself — as shown above — has no assertion that would catch the missing payment, so the dispute path cannot disprove it either.

### Impact Explanation
An attacker who is the withdrawer of their own registered withdrawal can, at zero cost to any operator, tag an arbitrary operator's x-only pubkey onto a payout tx that delivers no real value, forcing that operator's automation into the reimbursement pipeline for a payout it never made or funded. If the reimbursement completes (default optimistic round/kickoff-timeout path, since neither the on-chain bookkeeping nor `bridge_circuit`'s dispute path checks payment value), bridge collateral is paid out to an operator that funded nothing — draining the shared collateral pool. Independently, and irrespective of the "wrong operator" angle, this also confirms that even a genuinely complicit operator could use this same gap to front a payout with `OP_RETURN` outputs and still pass `bridge_circuit`, since no output value/type binding exists anywhere in the circuit's checked invariants. This matches the Critical category "an operator reimbursed for a payout it never funded," and is repeatable across any withdrawal/operator pairing since the check (or lack thereof) is systemic, not per-instance.

### Likelihood Explanation
Preconditions are minimal and within the stated attacker capability set: the attacker needs a registered withdrawal (achievable by depositing and calling `withdraw` on the Citrea Bridge contract themselves) and the ability to sign/broadcast a Bitcoin transaction spending their own withdrawal UTXO with an arbitrary sighash flag — something the attacker fully controls since it is a key-path spend of their own key. No operator, verifier, or aggregator cooperation, key compromise, or majority hashrate is required. Cost is limited to transaction fees plus the (dust-level, e.g. 550 sats per test fixtures) value of the withdrawal UTXO itself; the attacker forfeits nothing of value since no real payment is being delivered. The exploit is repeatable for every deposit/withdrawal instance and does not depend on any particular paramset.

### Recommendation
`bridge_circuit` should independently validate that the actual payout output paid to the withdrawer (identified deterministically, e.g. by requiring it be output index 0, matching `create_payout_txhandler`'s convention) has a `script_pubkey` matching a spendable standard type (not `OP_RETURN`/`OP_FALSE OP_RETURN`) and a `value` at least equal to the withdrawal amount recorded via the storage proof (`verify_storage_proofs`)/Citrea state. This binding needs to be enforced inside `bridge_circuit` itself (not merely at the operator's optional RPC-layer check), since that RPC check can be trivially bypassed by anyone who controls the withdrawal UTXO's private key and broadcasts directly to Bitcoin.
