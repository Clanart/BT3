Based on my investigation, I have found a valid analog to the Astaria M-10 bug in the Clementine codebase.

---

### Title
`InternalWithdraw` gRPC Handler Bypasses `aggregator_verification_address` ECDSA Guard, Accessible to Any Peer When `client_verification=false` — (`core/src/rpc/operator.rs`)

### Summary

The `ClementineOperator` gRPC service exposes two withdrawal entry points: `Withdraw` and `InternalWithdraw`. The `Withdraw` handler enforces an ECDSA verification-signature check (the `aggregator_verification_address` guard) when the operator is configured to require it. The `InternalWithdraw` handler calls the same underlying `operator.withdraw()` function but **omits this check entirely**. The only protection for `InternalWithdraw` is the mTLS interceptor, which is conditional on `client_verification = true`. When `client_verification = false` — a supported production configuration — the interceptor degrades to a `Noop` and any network peer can invoke `InternalWithdraw`, bypassing the aggregator ECDSA authorization gate and forcing the operator to front a payout without the required manual verification.

### Finding Description

**The guarded path — `Withdraw`:**

`Withdraw` (called by the aggregator on behalf of a user) checks `aggregator_verification_address` when it is set in config. If the ECDSA verification signature is absent or signed by the wrong key, the call is rejected. [1](#0-0) 

**The unguarded path — `InternalWithdraw`:**

`InternalWithdraw` is documented as "intended for operator's own use" and calls the identical `operator.withdraw()` function, but contains **no** `aggregator_verification_address` check. [2](#0-1) 

**The conditional mTLS guard:**

The interceptor restricts methods whose `grpc-method` header starts with `"Internal"` to self-only (the operator's own client certificate). However, this protection is only active when `client_verification = true`. [3](#0-2) 

When `client_verification = false`, the server installs a `Noop` interceptor instead: [4](#0-3) 

This means `InternalWithdraw` has **no application-level authorization guard** of its own; it relies entirely on the mTLS layer, which can be disabled.

**The `aggregator_verification_address` field is optional in config:** [5](#0-4) 

When set, it is the ECDSA address that must co-sign every withdrawal request. The `.env.example` shows it populated in a reference deployment: [6](#0-5) 

**Proto definition confirms `InternalWithdraw` is a live production RPC (not test-only):** [7](#0-6) 

Compare with `InternalFinalizedPayout`, which has an explicit `cfg!(test)` guard in its handler — `InternalWithdraw` has no such guard. [8](#0-7) 

### Impact Explanation

When `client_verification = false` and `aggregator_verification_address` is configured:

1. Any network peer that can reach the operator's gRPC port calls `InternalWithdraw` with a valid `withdrawal_id` and a user-provided Schnorr signature (which users broadcast to operators as part of the withdrawal flow).
2. The operator's `withdraw()` logic runs: it verifies the Schnorr signature, checks Citrea registration, and broadcasts a payout transaction — all without the aggregator's ECDSA co-authorization.
3. The operator fronts BTC to the user without the manual verification step that `aggregator_verification_address` is designed to enforce, defeating the purpose of that guard during the post-launch manual-review period.
4. The operator's collateral is committed to the kickoff/reimbursement cycle for a payout that was never authorized by the aggregator, exposing operator funds to the full reimbursement flow under potentially unverified conditions.

### Likelihood Explanation

- `client_verification = false` is a first-class supported configuration (the `Noop` branch is production code, not a test stub).
- The user's Schnorr signature is distributed to operators as part of the normal withdrawal flow; an attacker who observes or intercepts it can replay it to `InternalWithdraw`.
- No additional secret or privilege is required beyond network access to the operator's gRPC port.
- The `aggregator_verification_address` guard exists precisely because the protocol designers recognized that unverified withdrawals are a risk; `InternalWithdraw` silently nullifies that guard.

### Recommendation

Add an explicit application-level check inside `internal_withdraw` that rejects calls when `aggregator_verification_address` is configured, mirroring the guard in `withdraw`:

```rust
async fn internal_withdraw(
    &self,
    request: Request<WithdrawParams>,
) -> Result<Response<RawSignedTx>, Status> {
    // Reject if aggregator verification is required — callers must use Withdraw
    if self.operator.config.aggregator_verification_address.is_some() {
        return Err(Status::permission_denied(
            "aggregator_verification_address is set; use the Withdraw RPC with a verification signature",
        ));
    }
    // ... existing logic
}
```

Alternatively, add a `cfg!(test)` guard to `internal_withdraw` (as done for `internal_finalized_payout`) if the method is not needed in production outside of self-automation.

### Proof of Concept

1. Deploy an operator with `client_verification = false` and `aggregator_verification_address` set to a non-null address.
2. Observe that `Withdraw` rejects calls without a valid ECDSA verification signature.
3. Obtain a valid `withdrawal_id` (registered in Citrea) and the corresponding user Schnorr signature (intercepted from the normal withdrawal broadcast).
4. Call `InternalWithdraw` directly on the operator's gRPC port with those parameters and no verification signature.
5. Observe that the operator accepts the call, creates, and broadcasts a payout transaction — bypassing the `aggregator_verification_address` guard entirely. [2](#0-1) [9](#0-8) [10](#0-9)

fn is_internal(req: &Request<()>) -> bool {
    // This normally doesn't exist but we add it in the AddMethodMiddleware
    let Some(path) = req.metadata().get("grpc-method") else {
        // No grpc method? this should not happen
        tracing::error!("Missing grpc-method header in request");
        return false;
    };
    path.as_bytes().starts_with(b"Internal")
}

impl Interceptor for Interceptors {
    #[allow(clippy::result_large_err)]
    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {
        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
}

#[allow(clippy::result_large_err)]
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
