Based on the investigation, I could not substantiate a valid Protobuf analog to this libmspack `kwajd_read_headers` bug.

The CVE's failed invariant is: an attacker-controlled short length/type field in a file header is used to compute a write offset into a fixed-size buffer without a correct bounds check, causing a 1–2 byte overwrite past the buffer end.

I searched the equivalent Protobuf surfaces for this exact pattern — fixed/stack buffers sized from attacker-controlled length fields during binary/ProtoJSON parsing:

- `upb`'s JSON string/unicode decoder (`upb/json/decode.c` `jsondec_string`/`jsondec_unicode`, mirrored in `ruby-upb.c`/`php-upb.c`) resizes its output buffer and re-checks `buf_end - end < 4` immediately before writing up to 4 UTF-8 bytes, so the write is always preceded by a correct capacity check. [1](#0-0) 
- C++ `MicroString::SetInChunks` and `SetImpl` gate every write path (`inline`, `MicroRep`, `LargeRep`) with `ABSL_DCHECK_LE(size, capacity)` before `memcpy`, and dispatch to a larger representation when the size doesn't fit. [2](#0-1) 
- `EpsCopyInputStream::ReadSize`/`ReadSizeFallback` explicitly rejects sizes that would overflow `int32_t` or come within `kSlopBytes` of `INT_MAX`, preventing the length field itself from being weaponized into a bad pointer arithmetic offset.
