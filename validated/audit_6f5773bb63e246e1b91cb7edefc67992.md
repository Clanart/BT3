### Title
Delegated PoX-4/PoX-5 lock-increase silently unrecorded in `AssetMap`, letting a `Staking` post-condition be bypassed — (File: `pox-locking/src/pox_4.rs`)

### Summary
This is a real analog of the recall report's bug class: a state-tracking structure that is supposed to mirror an actual balance/weight change is only updated for one code path and silently skipped for a functionally-equivalent path, breaking the equality between "real locked STX" and "STX the post-condition machinery believes moved."

### Finding Description
`handle_stack_lockup_pox_v4`, `handle_stack_lockup_extension_pox_v4`, and `handle_stack_lockup_increase_pox_v4` in `pox-locking/src/pox_4.rs` each call `pox_lock_v4` / `pox_lock_extend_v4` / `pox_lock_increase_v4` unconditionally for `stack-stx`/`delegate-stack-stx`, `stack-extend`/`delegate-stack-extend`, and `stack-increase`/`delegate-stack-increase` respectively — these functions always mutate the *real* STX balance snapshot for `stacker` (the account whose STX gets locked), regardless of whether the call came from the direct path or the delegate path: [1](#0-0) [2](#0-1) [3](#0-2) 

But `global_context.log_stacking(&stacker, ...)` — the call that records the change into `AssetMap.stacking_map`, which `check_transaction_postconditions` later reads via `asset_map.get_stacking(&account_principal)` / `asset_map.get_all_stacking()` — is only invoked when `function_name == "stack-stx"`, `"stack-extend"`, or `"stack-increase"`. For the delegate variants (`delegate-stack-stx`, `delegate-stack-extend`, `delegate-stack-increase`), the real lock is applied but `log_stacking` is never called for `stacker`, so the increase is invisible to the `AssetMap`: [4](#0-3) 

`check_transaction_postconditions` (`crates/stacks-transactions/src/lib.rs`) relies entirely on `asset_map.get_stacking(&account_principal)` and `asset_map.get_all_stacking()` to verify a `TransactionPostCondition::Staking` condition and to enforce that every principal whose stacking changed is covered by a condition when the mode requires it: [5](#0-4) [6](#0-5) 

Because delegated increases never populate `stacking_map` for `stacker`, `get_stacking(stacker)` returns `None`/`0` even though `stacker`'s real locked balance rose by `new_total_locked - old_locked`. This breaks the intended equality "STX actually stacked by principal == STX the post-condition machinery observed as stacked by principal."

### Impact Explanation
This is the "asset moving past its post-conditions" class explicitly listed as Critical. A delegator (pool operator, who is the tx-sender/origin for `delegate-stack-increase`) can drive up a stacker's locked STX with no corresponding entry in the `AssetMap`. Any transaction (whether built by the stacker themselves to constrain a contract they call, or by a wallet auto-generating a `Staking` post-condition to bound how much of the stacker's balance a call is allowed to lock) that relies on a `Staking` post-condition to cap or gate this exact state change is defeated: the check unconditionally reports `amount_staked = 0`, so any `condition_code.check(...)` against the real threshold is evaluated against the wrong (zero) value and passes when it should fail. In `Deny`/`Originator` mode, the "every stacked amount must be covered" enforcement loop also can't catch this since the delegated increase never appears in `get_all_stacking()`.

### Likelihood Explanation
Medium-high: `delegate-stack-increase` is a normal, reachable PoX-4/PoX-5 contract call available to any registered pool operator with delegation rights over the stacker; no privileged role beyond a standard delegate-pool relationship is needed, and the asymmetry (`if function_name == "stack-increase"` vs. the omitted `delegate-stack-increase` branch) is visible directly in the source, not a subtle timing race.

### Recommendation
Call `global_context.log_stacking(&stacker, ...)` for the delegate variants as well (`delegate-stack-stx`, `delegate-stack-extend`, `delegate-stack-increase`), recording the change against the `stacker` principal whose real balance changed, so `AssetMap` always reflects the true locked amount regardless of which contract entry point produced it. Add regression tests analogous to `log_stacking_sums_within_frame_in_epoch_4` and `handle_contract_call_logs_pox_action_even_on_error` that assert `get_stacking(&stacker)` reflects the post-increase locked amount after a `delegate-stack-increase` call.

### Proof of Concept
1. Stacker `S` delegates stacking rights to pool operator `O` via `delegate-stx`, and is already locked via `stack-stx` (200,000 uSTX).
2. `O` builds and signs a transaction calling `delegate-stack-increase` for `S`, raising `S`'s total locked to 400,000 uSTX, and (as the tx author) attaches `TransactionPostCondition::Staking(S, SentLe, 200_000)` in `Deny`/`Originator` mode intending to bound the increase (or a monitoring wallet auto-generates this).
3. `pox_lock_increase_v4` succeeds and really locks 400,000 uSTX for `S` (`snapshot.save()` persists the new locked balance) — confirmed by `handle_stack_lockup_increase_pox_v4` unconditionally calling `pox_lock_increase_v4`: [7](#0-6) 
4. Because `function_name == "delegate-stack-increase"` (not `"stack-increase"`), `log_stacking` is skipped, so `AssetMap.stacking_map` for `S` remains unset.
5. `check_transaction_postconditions` evaluates the `Staking` condition using `asset_map.get_stacking(&S).unwrap_or(0)` = `0`, which trivially satisfies `SentLe 200_000`, so the transaction is accepted as if no over-increase occurred — even though `S`'s real locked balance is now 400,000 uSTX, double the intended cap.
