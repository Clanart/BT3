### Title
Incomplete conflict-marker detection allows AI conflict-resolution output to splice a partial/unbalanced conflict marker into the file that gets written and committed - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The Ironbank bug is a class of "trust an external/adversarial value without validating it against the invariant that actually matters," letting corrupted data flow into a decision that affects funds. The closest reachable analog in GitHub Desktop is `parseCopilotConflictResolution` / `reassembleResolvedFile` in [1](#0-0) , which validates Copilot's (LLM's) per-hunk `resolvedContent` before it is spliced verbatim into the user's file and ultimately staged/committed. The check that is supposed to guarantee "no leftover conflict markers" is incomplete, so malformed/partial marker text can pass validation and be silently written into the reassembled file that Desktop treats as fully resolved.

### Finding Description
`parseCopilotConflictResolution` validates each hunk's `resolvedContent` with:

```js
const rc = hunkObj.resolvedContent
if (/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)) {
  throw new CopilotValidationError(...)
}
``` [2](#0-1) 

This mirrors the PriceOracle pattern exactly: instead of rejecting *any* value outside the safe invariant, it only rejects when **both** an opening marker (`<<<<<<<`) **and** a separator (`=======`) are present in the *same* hunk string. It never checks for a bare `>>>>>>>` closing marker at all, and it requires both of the other two together rather than either alone. A model output containing only `>>>>>>> theirs` (no `<<<<<<<`/`=======`), or only a stray `<<<<<<< ` line without a matching `=======`, passes this guard untouched.

That content then flows through `validateResolutionPaths` (path/hunk-count only — no content re-check) at [3](#0-2)  and into `reassembleResolvedFile`, which splices `hunkResolutions[hunkIndex].resolvedContent` directly into the reconstructed file:

```js
if (hunkIndex < hunkResolutions.length) {
  const resolved = hunkResolutions[hunkIndex].resolvedContent
  if (resolved.length > 0) {
    resultLines.push(...resolved.split(/\r?\n/))
  }
}
``` [4](#0-3) 

Crucially, `reassembleResolvedFile`'s own marker scanner (used to find the *original* conflict block boundaries) treats a stray `<<<<<<<` that is not followed by both a separator and closing marker as **regular content** and copies it through unchanged:

```js
if (!hasSeparator || closingIndex === -1) {
  // Malformed marker — copy through as regular content
  resultLines.push(lines[i])
  ...
}
``` [5](#0-4) 

So a leftover partial marker injected by the model's `resolvedContent` on a *subsequent* pass, or one embedded directly in the reassembled output, is not caught as an unresolved conflict — it's treated as legitimate file content. The end result is a file the UI and the rest of the app believe is "fully resolved" (`IFileResolution.resolvedContent`) that in fact silently contains corrupted/leftover marker text, and this is what gets written to disk and can be committed/pushed by the user believing the conflict was cleanly resolved. This satisfies the stated valid-impact category of "silent corruption of what the user commits or pushes," driven by an untrusted external object (the Copilot/LLM response, itself influenced by attacker-controlled repository content — conflicting file text, commit messages, and PR title/description that are fed into the prompt as context) that is not validated against the actual safety invariant ("no marker fragments of any kind").

### Impact Explanation
If this path fires, the committed file can contain a stray `<<<<<<<`, `=======`, or `>>>>>>>` line that silently corrupts source code (breaking a build, or worse, changing program semantics if e.g. a bare `>>>>>>>` happens to be valid-looking token soup in some language, or truncates/duplicates logic around it) without any warning to the user, who is told the conflict was resolved. Since conflict resolution is specifically the feature used when merging/rebasing potentially attacker-influenced branches or PRs, an attacker who can shape the conflicting content or the PR/commit metadata fed into the LLM prompt has a lever to increase the odds of this malformed output slipping through undetected. This is a silent-corruption issue on the write/commit path, matching the accepted impact category, though the severity is bounded by needing the LLM to actually emit non-fully-valid output past its own quality bar (i.e., likelihood is the primary limiter, not exploitability of the code path itself).

### Likelihood Explanation
Moderate-to-low. This requires: (1) the user to invoke Copilot-assisted conflict resolution, (2) the model to emit a hunk whose `resolvedContent` contains a marker fragment that fails only one of the two required regex conditions (e.g., a bare `>>>>>>>`, or `<<<<<<<` without `=======`, or vice versa within the same hunk) — a case the code comments make clear the authors *intended* to guard against ("hunk ... still contains conflict markers") but implemented incompletely. Prompt-injected or adversarially crafted repository/commit/PR content that is included in the LLM prompt as untrusted context increases the chance of eliciting such degenerate output, but this is inherently probabilistic since it depends on model behavior rather than a deterministic attacker-controlled trigger.

### Recommendation
Fix the marker-detection guard to reject `resolvedContent` containing **any** conflict marker line independently, not just the conjunction of two specific markers:

```js
const hasAnyMarker =
  /^<{7}(?:\s|$)/m.test(rc) ||
  /^={7}$/m.test(rc) ||
  /^>{7}(?:\s|$)/m.test(rc)
if (hasAnyMarker) {
  throw new CopilotValidationError(
    `... hunk ${j} of file "${path}" still contains conflict markers`
  )
}
```
Additionally, re-validate the fully reassembled file content (post-splice) for any leftover marker lines before it is surfaced to the user as "resolved" or written to disk, since `reassembleResolvedFile`'s marker scanner is designed to find *original* conflict boundaries, not to catch new markers introduced by the model's own output.

### Proof of Concept
1. Trigger a merge/rebase conflict resolution via Copilot on a file with one conflict hunk.
2. Have (or simulate, in a test calling `parseCopilotConflictResolution` directly) the model return:
```json
{
  "resolutions": [{
    "path": "src/foo.ts",
    "hunks": [{ "resolvedContent": "someCode();\n>>>>>>> theirs\nmoreCode();" }],
    "reasoning": "merged both sides"
  }],
  "summary": null,
  "references": []
}
```
3. `parseCopilotConflictResolution` evaluates `/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)` — both are `false`/absent, so the AND short-circuits to `false` and no `CopilotValidationError` is thrown, even though `resolvedContent` still contains a raw `>>>>>>> theirs` marker line [1](#0-0) .
4. `reassembleResolutions` → `reassembleResolvedFile` splices this string verbatim into the reconstructed file [4](#0-3) , producing a file with an orphan `>>>>>>> theirs` line that is presented to the user as the final resolved content and can be committed unmodified.
