### Title
Attacker-controlled FROST preprocess can force an identity (point-at-infinity) aggregate nonce, panicking BIP-340 signing via `x()`/`Hram` — ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
CVE-2018-7335 is a dissector crash caused by accepting inputs that are "too small" / malformed at the edge instead of being rejected up front. The analog in Serai is a crash on a degenerate value accepted at the deserialization edge: `Ciphersuite::read_G` accepts the canonical encoding of the identity point (`crypto/ciphersuite/src/lib.rs:91-101`), and neither `GeneratorCommitments::read` nor `NonceCommitments::read` nor `Commitments::read` perform any identity/non-degenerate check on the committed nonce points (`crypto/frost/src/nonce.rs:34-36`, `crypto/frost/src/nonce.rs:74-80`, `crypto/frost/src/nonce.rs:133-139`). These points flow into `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:283-318`), and for Bitcoin's `Schnorr` algorithm the challenge is computed by `Hram::hram`, which calls `x(R)` — a function that panics with `.expect("point at infinity")` when `R` is the identity (`networks/bitcoin/src/crypto.rs:13-16`, `crypto.rs:59-66`).

### Finding Description
A participant in a Bitcoin FROST signing session supplies preprocess bytes parsed by `read_preprocess` (`crypto/frost/src/sign.rs:276-281`). Each preprocess contributes nonce commitments (D, E) per generator, and the aggregate nonce point `R` is a linear combination `sum_i (D_i + rho_i * E_i)` over all included signers. Because `read_G` admits the identity encoding and the nonce-commitment readers impose no identity rejection, a rushing signer who observes the other participants' preprocesses before submitting their own (the preprocesses are gossiped/collected before `sign` is invoked) can choose `D_i, E_i` such that their contribution cancels the remaining sum, driving the effective aggregate nonce `R` to the point at infinity. When `sign_share`/`verify` computes `Hram::hram(R, A, msg)`, `x(R)` calls `to_encoded_point(true).x()` on infinity, which returns `None`, and `.expect("point at infinity")` aborts the process (`crypto.rs:14-15`).

The code itself acknowledges this panic path: the `Schnorr` doc comment states it "MAY panic" on nonces/group keys that are the point at infinity, dismissing it as having "a negligible probability ... even with malicious participants present" (`crypto.rs:78-80`). That dismissal is incorrect — it is negligible only for *random* nonces; a malicious co-signer choosing their commitment points last can make `R = identity` deterministically, turning a documented panic into a remotely triggerable crash. The correct fix mirrors the Wireshark patch ("reject lengths that are too small"): reject identity commitments in `read_G`/`Commitments::read` or in `sign` before the nonce sum is used.

### Impact Explanation
An unprivileged co-signer (any participant able to submit a preprocess to the signing session, e.g., via the coordinator's `SignData`/preprocess flow that reaches `read_preprocess` in `processor/src/batch_signer.rs:241-247` and `processor/src/cosigner.rs:161-169`) can deterministically panic the processor/coordinator binary handling Bitcoin signing. Rather than receiving a `FrostError::InvalidPreprocess`, the process aborts, halting all in-flight signing work — the same availability impact class as the Wireshark dissector crash. Because the panic happens inside the machine rather than returning a blameable error, the attacker can also repeat it across attempts without the preprocess being cleanly attributed as faulty.

### Likelihood Explanation
Requires a slot in the signing set (a participant index whose preprocess is included) and the ability to order their preprocess after observing others (a rushing adversary — feasible in any asynchronous collection of preprocesses, and trivially if preprocesses can be resubmitted per-attempt). No key material or collusion is needed. The panic path is explicitly documented in the code, so exploitability does not depend on probabilistic events.

### Recommendation
Reject the point at infinity for all nonce commitments: either inside `GeneratorCommitments::read`/`NonceCommitments::read` (`crypto/frost/src/nonce.rs`) or as a validation step in `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs`) on each participant's effective commitment `D_i + rho_i * E_i` and on the aggregate nonce sum, returning `FrostError::InvalidPreprocess(i)` so the faulty participant is blamed. Additionally, make `Hram::hram`/`x`/`x_only` return `Option`/`Result` rather than panicking (`networks/bitcoin/src/crypto.rs:13-23`, `59-73`).

### Proof of Concept
1. Attacker joins a Bitcoin `Schnorr` signing session as participant `i`.
2. Honest participants broadcast preprocesses with commitments `(D_j, E_j)`; these reach the attacker through `read_preprocess`.
3. Attacker computes the `rho` binding factors (all public: group key, `hash_msg`, the `preprocesses` transcript) and chooses `E_i = identity`, `D_i = -(sum over others of D_j + rho_j * E_j)` — or, more simply for the PoC, arranges the effective sum to be identity by submitting commitments that cancel the aggregate. The identity is canonically encodable (32 zero-ish bytes per `GroupEncoding`), so `read_G` accepts it.
4. The victim calls `machine.sign(preprocesses, msg)`. The aggregate `R` is infinity; `Hram::hram` → `x(R)` → `to_encoded_point(true).x()` is `None` → `.expect("point at infinity")` panics, aborting the process instead of returning `FrostError::InvalidPreprocess`.

Caveat: I verified that `read_G` accepts identity (`ciphersuite/src/lib.rs:91-101`), that the nonce-commitment readers do no filtering (`nonce.rs:34-80`), and that `x()`/`hram` panic on infinity (`crypto.rs:13-16`, `54-56`, `78-83`). I did not confirm the exact point in `crypto/frost/src/sign.rs` past line ~319 where the nonce sum is formed and where `hram` is invoked, nor whether an existing identity check on the summed `R` exists there — if such a check exists, this reduces to the still-incorrect documented panic being unreachable via this specific path, and the analog should be re-scoped.
