### Title
Missing cross-vote consistency check in `headerGovModule::checkConsistency` for KIP-71 `LowerBoundBaseFee`/`UpperBoundBaseFee` allows inverted base-fee bounds - (File: `kaiax/gov/headergov/impl/header.go`)

### Summary
`checkConsistency` in `kaiax/gov/headergov/impl/header.go` validates a `Kip71LowerBoundBaseFee` vote by comparing it to the *currently committed* `UpperBoundBaseFee`, and a `Kip71UpperBoundBaseFee` vote by comparing it to the *currently committed* `LowerBoundBaseFee`. Because both checks are evaluated against the old, pre-epoch parameter set rather than against each other's proposed new values, two votes submitted by the governing/council voter within the same epoch can each pass validation individually while producing a final combined state where `LowerBoundBaseFee > UpperBoundBaseFee` — the same class of bug as the reported `FlatcoinVault::setExecutabilityAge()` missing `min < max` check.

### Finding Description
`VerifyVote` calls `checkConsistency(blockNum, vote)` for every vote embedded in a block header [5](#0-4) . For KIP-71 bound votes, the check is:

```go
case gov.Kip71LowerBoundBaseFee:
    params := h.GetParamSet(blockNum)
    if vote.Value().(uint64) > params.UpperBoundBaseFee {
        return ErrLowerBoundBaseFee
    }
...
case gov.Kip71UpperBoundBaseFee:
    params := h.GetParamSet(blockNum)
    if vote.Value().(uint64) < params.LowerBoundBaseFee {
        return ErrUpperBoundBaseFee
    }
``` [1](#0-0) 

`params` is fetched fresh at each vote's block via `h.GetParamSet(blockNum)`, which reflects only what has already been *finalized* (committed at a previous epoch boundary), not any other vote proposed earlier in the same, still-open epoch. Votes accumulated in an epoch are later merged wholesale by `getExpectedGovernance`, which simply calls `govs.Add(...)` for every vote name/value pair with no re-validation of the combined result [2](#0-1) .

Concretely: with the default bounds `LowerBoundBaseFee = 25e9`, `UpperBoundBaseFee = 750e9` [6](#0-5) :
1. Vote A (earlier block in epoch N): set `UpperBoundBaseFee = 100e9`. Check: `100e9 < 25e9`? No → accepted.
2. Vote B (later block, same epoch N): set `LowerBoundBaseFee = 200e9`. Check: `200e9 > 750e9` (the *old*, still-unmodified upper bound)? No → accepted.
3. At the epoch boundary, both votes are merged into the header's `Governance` field and applied together, yielding `LowerBoundBaseFee = 200e9 > UpperBoundBaseFee = 100e9`.

This is analogous to the reported `FlatcoinVault::setExecutabilityAge()` bug: individually-valid inputs combine into an invalid, inverted range because there is no atomic/combined-state validation, only pairwise validation against stale state.

### Impact Explanation
`NextMagmaBlockBaseFee` in `params/kip71_config.go` assumes `lowerBoundBaseFee <= upperBoundBaseFee`; it clamps `parentBaseFee` by first checking `>= upperBoundBaseFee` and then `<= lowerBoundBaseFee` [7](#0-6) . When the bounds are inverted, the clamping and delta-adjustment logic can no longer guarantee `lowerBoundBaseFee <= nextBaseFee <= upperBoundBaseFee` in the way intended (indeed, the existing test `TestEvenBaseFee` explicitly checks `even.Cmp(lowerBound) >= 0` and `even.Cmp(upperBound) <= 0` as invariants [8](#0-7) , which is exactly the invariant this bug breaks for on-chain, governance-set values). This can force an incorrect/inverted `expectedBaseFee` computed by `VerifyMagmaHeader`, causing legitimate blocks to be rejected as invalid (or an unintended too-low/too-high base fee to be locked in for all subsequent blocks), impacting fee computation for every transaction on the network — a network-wide gas pricing malfunction, not merely a griefing of a single order like in the original Flatcoin report.

### Likelihood Explanation
Triggering this requires the ability to cast governance votes, which under `GovernanceMode == "single"` is restricted to the `GoverningNode`, and under multi-voter mode is open to any council/validator member [9](#0-8) . This fits the allowed "governance parameters" category. It requires only submitting two ordinary votes within the same epoch (a routine governance operation, not requiring any privileged network access), so likelihood is moderate — it needs either a malicious/compromised governing node or a colluding subset of council voters, but no consensus-level or off-chain compromise.

### Recommendation
When validating `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` votes in `checkConsistency`, account for any other pending vote for the counterpart parameter already accepted within the same open epoch (not just the last-committed `ParamSet`), or re-validate the fully merged `PartialParamSet` for internal consistency (`LowerBoundBaseFee <= UpperBoundBaseFee`) inside `getExpectedGovernance` before it is written into `header.Governance`, rejecting/dropping the whole epoch's aggregate governance change if the combined values are inconsistent.

### Proof of Concept
1. Start from default `LowerBoundBaseFee = 25_000_000_000`, `UpperBoundBaseFee = 750_000_000_000`.
2. As governing node, submit vote for block N (early in epoch): `Kip71UpperBoundBaseFee = 100_000_000_000`. `checkConsistency` compares `100e9 < 25e9` → false → vote accepted.
3. Submit a second vote for block N+k (later, same epoch): `Kip71LowerBoundBaseFee = 200_000_000_000`. `checkConsistency` compares `200e9 > 750e9` (still the old, uncommitted upper bound) → false → vote accepted.
4. At the epoch boundary, `getExpectedGovernance` merges both votes into `header.Governance` without cross-checking them against each other, producing a final state where `LowerBoundBaseFee (200e9) > UpperBoundBaseFee (100e9)`.
5. Subsequent `NextMagmaBlockBaseFee` calls operate on this inverted configuration, violating the bound invariants asserted by `TestEvenBaseFee`, and can cause disagreement/rejection in `VerifyMagmaHeader`'s base-fee validation for all future blocks.

func (h *headerGovModule) getExpectedGovernance(blockNum uint64) headergov.GovData {
	prevEpochIdx := calcEpochIdx(blockNum, h.epoch) - 1
	prevEpochVotes := h.getVotesInEpoch(prevEpochIdx)
	govs := make(gov.PartialParamSet)

	sortedVoteBlocks := slices.Collect(maps.Keys(prevEpochVotes))
	slices.Sort(sortedVoteBlocks)

	for _, voteBlock := range sortedVoteBlocks {
		vote := prevEpochVotes[voteBlock]
		govs.Add(string(vote.Name()), vote.Value())
	}

	// assert(len(headergov.NewGovData(govs).Items()) == len(govs))
	return headergov.NewGovData(govs)
}
