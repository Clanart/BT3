### Title
`clone()` disables Git's clone-time hook-execution protection for every recursive clone - ([File: app/src/lib/git/clone.ts])

### Summary
Reducing the ERC777 report to its broken invariant: **a trust/accounting state is finalized while an attacker-controlled callback path that should have been blocked is still reachable**. The Desktop analog: `clone()` performs `git clone --recursive` (auto-initializing every submodule the remote repository declares) while explicitly forcing the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`, on every single clone, regardless of whether the URL/remote is trusted. [1](#0-0) 

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is a Git internal safety flag (introduced as part of the upstream Git hardening work for the "arbitrary hook execution via crafted repository content during clone/recursive-submodule-checkout" class of issues, e.g. CVE-2024-32004/32020/32021/32465). When Git performs a clone — especially a recursive one that has to `init`/`update` submodules and thereby runs `checkout`/`hook` machinery against content that came from the (potentially malicious) remote — it uses this flag internally to suppress execution of repository-supplied hooks until the clone is known-safe. Git sets/consults this flag itself; a caller is not supposed to need to force it.

Desktop's `clone()` explicitly overrides this to `'false'`:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
...
args.push('--', url, path)
await git(args, __dirname, 'clone', opts)
``` [2](#0-1) 

The only other check applied before the clone is `isClonePathSensitive(path)`, which only validates the local destination path (e.g. rejecting system directories) — it has no bearing on the *content* of the remote repository being cloned. [3](#0-2) 

This is structurally identical to the reentrancy report's flaw: the report's `_deposit()` performed the trust-sensitive `transferFrom()` (which can invoke attacker code) *after* accounting state had already been finalized, and the fix was to reorder/guard that external call. Here, Desktop reorders/guards nothing — it actively disables the guard Git itself would otherwise apply around exactly the external, attacker-influenced code path (`--recursive` submodule checkout/hook execution) triggered by cloning a URL that is, by definition, attacker-supplied content the user has not yet vetted.

Note: I could not find any local test, comment, or commit history in this repo explaining *why* protection is disabled (the repository history only shows a single "Initial commit" for this file), so the intent behind this override could not be verified locally — but the code as written unconditionally disables the protection for every clone. [4](#0-3) 

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE=false` indeed suppresses Git's clone-time hook-suppression safeguard as its name and upstream origin imply, then cloning a malicious or compromised repository/remote through Desktop (the exact "attacker controls a cloned/fetched repository" primitive named in the Valid Impact scope) can result in arbitrary code execution on the user's machine during the clone itself, before the user has had any chance to inspect the repository contents. This satisfies the "code execution" impact bar directly, and requires no elevated privileges, no pre-existing malware, and no unnatural user steps beyond the completely ordinary act of cloning a repository URL in Desktop (Clone Repository dialog / "Open in Desktop" deep link / File > Clone repository).

### Likelihood Explanation
Likelihood is high for the trigger conditions: every clone Desktop performs uses `--recursive` and this same disabled-protection environment unconditionally — there is no opt-in/opt-out, no allow-list, and no repository-trust check comparable to the "unsafe repository" ownership check Desktop already applies elsewhere for locally-added repos. [5](#0-4) [6](#0-5) 
That existing "unsafe repository" flow shows Desktop is clearly aware of, and already mitigates, "adding untrusted repositories may automatically execute files in the repository" for *local* repos added by path — but the clone path bypasses an analogous Git-native protection instead of relying on it. What remains unverified from local code alone is the exact current semantics of `GIT_CLONE_PROTECTION_ACTIVE` in the specific bundled Git/dugite version Desktop ships (version-dependent behavior of this flag could not be checked from this repository), which is the main residual uncertainty.

### Recommendation
- Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Remove the override so Git's default (protection-active) behavior applies during clone, matching upstream Git's intended defense-in-depth for recursive/submodule clones of untrusted content.
- If the override exists to work around a specific breakage (e.g., legitimate submodule hooks needed at clone time), scope it narrowly (e.g., only for repositories the user has explicitly marked as trusted, mirroring the existing "unsafe repository" trust flow) rather than applying it unconditionally to every clone.
- Add a regression/unit test asserting that `clone()` does not disable this protection env var, and document in code why any exception is safe if one is ever reintroduced.

### Proof of Concept
1. Craft a public/attacker-controlled Git remote whose repository declares a submodule (`.gitmodules`) and includes hook content designed to execute during submodule checkout (the same content pattern addressed by the upstream Git CVEs this protection flag was created for).
2. Have the victim clone that URL via GitHub Desktop's Clone dialog (or via a `x-github-client://openRepo`/`github-desktop://` deep link that pre-fills the clone URL) — an entirely ordinary, unprivileged user action.
3. Desktop calls `clone()`, which runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` injected into the process environment. [2](#0-1) 
4. Because the clone-time hook-suppression safeguard is disabled, the malicious submodule/hook content executes with the current user's privileges during the clone, before the user has viewed a single file — achieving code execution purely from an attacker-controlled cloned repository, matching the "Valid Impact" criteria of this task.
