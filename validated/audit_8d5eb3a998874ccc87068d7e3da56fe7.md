### Title
Silent cross-chain dispatch failure in `add_deployment` permanently desyncs `_instances` across IntentGatewayV2 deployments - (File: modules/pallets/intents-coprocessor/src/lib.rs)

### Summary
`add_deployment` registers a new `IntentGatewayV2` deployment on Hyperbridge and is supposed to propagate that registration to every other already-registered gateway instance via an ISMP `AddDeployment` cross-chain POST. The propagation call's result is explicitly discarded with `let _ = Self::dispatch(...)`, so a failed dispatch (insufficient fee-token liquidity in the coprocessor's dispatch path, a `DispatchError` from `pallet-ismp`, host misconfiguration, etc.) is swallowed. Hyperbridge's own bookkeeping (`Gateways::<T>::insert`) reflects the new deployment as if the notification had succeeded, while the peer `IntentGatewayV2` contract's `_instances[keccak256(chain)]` mapping never receives the corresponding `NewDeployment` message and stays uninitialized for the new chain.

### Finding Description
`add_deployment` in `modules/pallets/intents-coprocessor/src/lib.rs:369-407` iterates every existing gateway and dispatches an `AddDeployment` request to notify it of the newly registered chain: [1](#0-0) 

The dispatch result is discarded (`let _ = Self::dispatch(...)`) rather than propagated as an error, unlike the sibling extrinsic `update_params`, which uses `Self::dispatch(...)?` and reverts the whole call (including the local storage mutation) on failure: [2](#0-1) 

On the EVM side, a gateway only learns about a new peer chain through the `NewDeployment` message handled in `onAccept`, which populates `_instances[keccak256(body.chain)]`: [3](#0-2) [4](#0-3) 

Because `Self::dispatch` errors are swallowed in the loop, `add_deployment` always succeeds and always emits `GatewayDeploymentAdded`, regardless of whether any peer actually received the `AddDeployment` notification. This means Hyperbridge's own `Gateways` storage and the emitted event both assert that state is synced across the network when, for one or more existing gateways, it silently is not. The affected gateway's `_instances` mapping for the new chain stays at the zero address, so any subsequent cross-chain fill/cancel/dispatch calls targeting that (from the affected gateway's perspective, "unknown") chain hit `_instance()`'s `UnknownInstance` revert in `IntentsBase.sol`, and cross-chain messages arriving from that chain fail `_authenticate` (`_instance(request.source) != module`), causing `RedeemEscrow`/`RefundEscrow` deliveries to permanently revert. There is no retry mechanism, no on-chain flag indicating which gateways failed to receive the notification, and the same commitment cannot be re-dispatched because `add_deployment` for that state machine has already run and inserted into `Gateways`. Escrowed input tokens on the omitted gateway's chain, and destined for solvers/users via that dropped notification path, become permanently unroutable/stuck — mirroring the original bug's "state on the destination side never syncs, and a strict equality/authorization check on the destination locks funds forever."

### Impact Explanation
This falls squarely within the accepted impact class of loss/lock of bridged funds: solvers who fill cross-chain orders targeting (or originating from) the newly added chain rely on the affected peer gateway recognizing that chain via `_instances`. If the notification silently failed, the gateway rejects the incoming settlement message (`_authenticate` reverts with `Unauthorized`) or the outbound dispatch reverts with `UnknownInstance`, permanently blocking `RedeemEscrow`/`RefundEscrow` delivery and leaving escrowed tokens unredeemable through the intended protocol path. This is a real production runtime effect (governance-triggered onboarding of new intent-gateway chains), not a testnet-only or node-operator-only concern.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: `add_deployment` fires `N-1` independent cross-chain dispatches every time governance onboards a new chain (as intent-gateway coverage grows this fan-out increases), and there is no on-chain guarantee (fee-token balance, dispatcher configuration, per-destination host params) that every one of those dispatches succeeds. Any single failure among them is silently absorbed, and nothing in the pallet's storage or events distinguishes a fully-synced rollout from a partially-synced one, so operators have no signal to manually retry.

### Recommendation
Do not discard the dispatch result. Either: (a) propagate the error and abort the whole `add_deployment` call transactionally (as `update_params` already does with `?`), forcing governance to retry until every notification succeeds before `Gateways` is updated; or (b) if partial rollout must be tolerated, persist per-`(state_machine, existing_state_machine)` pending/failed notification state and expose a permissionless or governance-gated `retry_deployment_notification` extrinsic so a failed `AddDeployment` message can be re-dispatched without needing to re-run the full `add_deployment` flow.

### Proof of Concept
1. Governance has two existing `IntentGatewayV2` deployments registered in `Gateways`: chain A (gateway_A) and chain B (gateway_B), each already aware of the other via prior `NewDeployment` messages.
2. Governance calls `add_deployment(state_machine_C, gateway_C, params)`.
3. `add_deployment` iterates existing gateways and dispatches `AddDeployment` to both A and B. Suppose the dispatch to gateway_B fails (e.g., `IsmpDispatcher::dispatch_request` returns `Err` due to a transient fee/dispatcher configuration issue on chain B) — the error is discarded via `let _ = Self::dispatch(...)`.
4. The call still succeeds: `Gateways::<T>::insert(state_machine_C, ...)` runs, and `GatewayDeploymentAdded` is emitted, with no on-chain trace that gateway_B never got notified.
5. A user later places a cross-chain order with `source = chain C`, `destination = chain B`. A solver fills it on gateway_B and gateway_B dispatches `RedeemEscrow` back to gateway_C's `IntentGatewayV2` — this direction is unaffected because gateway_C was initialized with knowledge of chain B via `initialize`'s `peerChains`, or a symmetric add_deployment call.
6. Conversely, a user places an order with `source = chain B`, `destination = chain C`, fills on gateway_C, and gateway_C attempts `RedeemEscrow` back to gateway_B. Because gateway_B's `_instances[keccak256(chain C)]` was never set (step 3 dropped the notification), `_authenticate` in `ExtrinsicIntents.sol` computes `_instance(request.source)` for chain C on gateway_B, which reverts `UnknownInstance` — `onAccept` reverts, the settlement message can never be delivered, and the solver's escrowed input on chain C from the user's original order is permanently stuck (no automatic timeout/refund path exists once the intended redemption path is broken this way, since the message was accepted by ISMP as a receipt but application-level `onAccept` reverts on every retry with the same authentication failure).
