### Title

Bitcoin Schnorr aggregation signs an unintended Taproot signature when the aggregated nonce is odd - ([File: networks/bitcoin/src/crypto.rs])

### Summary

The Bitcoin FROST algorithm mishandles BIP-340 nonce parity. `Hram::hram` negates the challenge when the aggregate nonce `R` is odd, and `verify` later negates the final `s` when `sig.R` is odd. This produces `s' = -r + h*x` for an odd `R`, which is a valid BIP-340 signature for `-R` and the x-only group key, but it is not a valid share-transcript signature under the FROST algorithm’s own verification equation because `verify_share` still checks each share against the un-negated `c` relationship.

More importantly, this transform is applied at the aggregate signature layer rather than by re-keying each participant’s nonce share. For an odd combined `R`, each participant produced `s_i = r_i - h*x_i`, while the final signature is emitted as `-sum(s_i)`. The resulting transaction signature commits to `-R`, not the `R` that was bound into the FROST preprocess/commitment transcript. This breaks the intended binding between the nonce commitments exchanged by signers and the signature emitted for the Bitcoin transaction.

### Finding Description

`Hram::hram` computes the BIP-340 challenge from `x(R)`, `x(A)`, and the message, then conditionally negates the challenge if `R` is odd. [1](#0-0) 

`Schnorr::verify` then verifies the ordinary Schnorr equation using the original `group_key`, `nonces[0][0]`, and `sum`, and only afterward conditionally negates `sig.s` if `sig.R` is odd. [2](#0-1) 

Share verification is delegated back to the generic Schnorr verifier using the stored challenge and the participant’s bound nonce, without any equivalent BIP-340 parity correction to the verification-share formula. [3](#0-2) 

The generic Schnorr share formula is `R + cA - sG == 0`. [4](#0-3) 

For odd aggregate `R`, `Hram` makes `c = -h`, so each valid signer creates `s_i = r_i - h*x_i`. The aggregate `sum = r - h*x` satisfies the generic equation against `R + (-h)A`. `verify` then emits `s' = -sum`, which satisfies Bitcoin’s equation for `R' = -R`. The emitted transaction therefore uses a different nonce point than the one committed to in the FROST nonce transcript.

### Impact Explanation

An attacker who can influence the aggregate nonce commitments can cause the signer to emit a Bitcoin transaction signature whose effective nonce `-R` differs from the committed aggregate nonce `R`. This is a signature-equivalence/binding break in the FROST-to-BIP340 adapter: the bytes authorized through the FROST commitment transcript are not the same nonce value that appears in the final transaction signature.

This can also cause valid local share verification and transaction completion to diverge from the externally visible BIP-340 signature semantics. In a threshold signing flow, that weakens the fundamental guarantee that all participants are signing the exact committed nonce and message relation.

### Likelihood Explanation

The condition is probabilistic and reachable: an odd aggregate `R` occurs with approximately 50% probability from public nonce commitments. A participant capable of supplying preprocess commitments can also try nonce choices until the resulting aggregate `R` has the desired parity. The flawed path is entirely contained in `networks/bitcoin/src/crypto.rs` and is exercised whenever Bitcoin Taproot key-path signatures are produced.

### Recommendation

Normalize the nonce before challenge generation instead of negating the challenge. For each signer, derive the effective nonce scalar as `-nonce` when the aggregate nonce parity requires negation, and ensure the verification-share equation uses the same normalized nonce and public-key parity rules as BIP-340. Alternatively, reject sessions whose aggregate nonce does not satisfy the required parity and restart with fresh preprocesses.

### Proof of Concept

A concrete PoC can be built by generating a two-signer FROST session over `Secp256k1` with `Schnorr::new`, choosing one participant’s preprocess nonce until the aggregate `R` is odd, then calling `sign` and `complete`. The resulting transaction signature is valid for BIP-340’s even lift of `R`, while the internal share equation was generated with `c = -h`. This demonstrates the signed nonce is not the same `R` committed to by the preprocess transcript.

      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
