### Title
Open redirect via backslash-normalized `return_to`/Referer path bypassing Ruby-URI-based safety checks in `redirect_to_login`/`return_to_url`/`login_url_params` - (File: lib/shopify_app/controller_concerns/login_protection.rb)

### Summary
`redirect_to_login` derives the value stored in `session[:return_to]` from `request.path` on GET requests, but from the attacker-controlled **Referer header** on non-GET requests [1](#0-0) . That value is later used verbatim by `return_address`/`base_return_address` as a live redirect target, and is only validated with Ruby's RFC3986 `URI` parser (`RedirectSafely.make_safe`, `URI()`), which does not treat `\` as a path/authority delimiter the way browsers' WHATWG URL parser does [2](#0-1) . This parser differential lets a value such as `/\attacker.com` pass every "is this relative/same-origin" check on the server while a real browser normalizes it to `//attacker.com`, a protocol-relative absolute URL to the attacker's host.

### Finding Description
Path:
1. An unauthenticated attacker sends a **non-GET** request to a protected action (any action wrapped by `activate_shopify_session`) with `Referer: http://x/\attacker.com`.
2. `activate_shopify_session` finds no session and calls `redirect_to_login` [3](#0-2) .
3. Because the request is not a GET, `redirect_to_login` builds `path` from `URI(request.referer).path`, not from the actual route [4](#0-3) . Ruby's `URI` parser does not special-case `\`, so `path` becomes the literal string `"/\attacker.com"`.
4. `session[:return_to] = return_to_url(path, query)` stores this value, `return_to_url` does a plain string concatenation with no host/backslash validation [5](#0-4) .
5. Later (e.g. an error path or the un-embedded branch of the callback flow), `base_return_address`/`return_address` return this raw string as the actual redirect target: `session.delete(:return_to) || ShopifyApp.configuration.root_url` [6](#0-5) , and it is passed straight into `redirect_to(...)`.
6. The only sanitization applied anywhere in this pipeline (`RedirectSafely.make_safe`, `URI()`, Rails' own `redirect_to` open-redirect protection) relies on Ruby's `URI` host-detection, which reports `host.nil? == true` for `"/\attacker.com"` because `\` is not an authority delimiter in RFC3986. A real browser's WHATWG URL parser, however, treats `\` as equivalent to `/` for special schemes (http/https), turning the relative path into `//attacker.com` — a network-path reference that changes the authority to `attacker.com`.
7. For **embedded apps**, `callback_controller#redirect_to_app` mitigates this specific case by prepending a trusted `decoded_host` before the stored `return_to` unless `fully_formed_url?` (Addressable-based) already flags it as absolute [7](#0-6) , so the exploit is neutralized there. For **non-embedded apps**, `redirect_to_app` calls `redirect_to(return_address)` directly with no host prefix, and other call sites (e.g. `SessionsController#render_invalid_shop_error`) also call `redirect_to(return_address)` unconditionally — none of these add a trusted host prefix, so the raw attacker-influenced value reaches the `Location` header unmodified.

### Impact Explanation
On a non-embedded app configuration, this results in an open redirect: the app issues `Location: /\attacker.com...`, which a real browser resolves to `https://attacker.com/...`. Combined with the app's normal flow of appending `id_token`/`host`/session-bearing query parameters on the way back from Shopify's login, this can be leveraged to exfiltrate those values to an attacker-controlled origin on the follow-up navigation, matching the "open redirect leading to token/host theft" impact class.

### Likelihood Explanation
Requires: (a) app configured as non-embedded (or a call path that reaches `return_address`/`base_return_address` without the embedded `decoded_host` prefix), (b) attacker able to send a non-GET request to any protected action while unauthenticated with a crafted `Referer` header, and (c) session persistence between that request and the later request that reads `session[:return_to]` back out. All of these are attacker-reachable without any privileged credentials — Referer headers are fully attacker-controlled in cross-site link/form scenarios, and the affected endpoints are exactly the ones this class of concern targets (protected actions behind `activate_shopify_session`). The embedded-app code path is already mitigated by `decoded_host` prefixing, narrowing but not eliminating exploitability.

### Recommendation
Normalize `\` to `/` (or reject any return_to/path containing `\`) before treating a value as "relative/safe" in `return_to_url`, `RedirectSafely.make_safe` usage, and `base_return_address`/`return_address`. Alternatively, always resolve `return_to` against a trusted, known-good host (as already done in the embedded branch of `redirect_to_app`) rather than trusting a bare leading `/` as proof of same-origin-ness, and validate using a WHATWG-URL-compatible parser (or explicitly `gsub("\\", "/")` before validation) so the server's notion of "relative" matches the browser's.

### Proof of Concept
```ruby
# test/shopify_app/controller_concerns/login_protection_test.rb (illustrative)
test "redirect_to_login stores a backslash-prefixed referer path that a browser would treat as protocol-relative" do
  request.headers["Referer"] = "http://example.com/\\attacker.com"
  post :protected_action # unauthenticated, non-GET, triggers activate_shopify_session -> redirect_to_login

  # server-side value considered "safe" (no host, per Ruby URI):
  assert_equal "/\\attacker.com", session[:return_to].split("?").first

  # simulate a later call site that redirects using this value:
  get :some_action_calling_return_address
  # EXPECTED (bug): Location header is "/\\attacker.com..." verbatim (no trusted host prefix, no rejection)
  # A real browser resolves this Location to "//attacker.com/...' -> https://attacker.com/...
  assert_match %r{\A/\\attacker\.com}, response.location
end
```
Fast validation approach: add a property test that feeds `return_to_url`/`base_return_address` values containing `\`, `%5C`, mixed-case `HtTpS:\/\/`, and confirm the sanitizer rejects/normalizes all of them to a value that cannot be reinterpreted as `//host` by a WHATWG-compliant parser.
