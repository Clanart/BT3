### Title
Sending native value to `distribution` precompile's `rewards()` view method permanently strands the funds — (File: `precompiles/distribution/distribution.go`)

### Summary
The `rewards` view method of the `distribution` precompile (address `0x0000000000000000000000000000000000001007`) is the only transaction/view entrypoint in that precompile that does not call `pcommon.ValidateNonPayable(value)` and does not refund any attached `msg.value`. Any unprivileged caller can invoke it with a real `CALL` (not `STATICCALL`) carrying non-zero wei, and that wei is silently absorbed with no mechanism to recover it — mirroring the reported Footium issue where a payable entrypoint accepts arbitrary value without enforcing or accounting for a correct amount.

### Finding Description
The distribution precompile's dispatcher explicitly enforces `ValidateNonPayable(value)` for `WithdrawValidatorCommissionMethod`, and other value-bearing methods (`setWithdrawAddress`, `withdrawDelegationRewards`, etc.) go through `HandlePaymentUsei`, which refunds any usei-equivalent value sent along with the call back to the payer. `RewardsMethod`, however, is dispatched directly without any payability guard: [1](#0-0) 

and the executor itself never inspects or refunds `value` at all: [2](#0-1) 

This is a known, documented quirk in the repo's own integration test suite: [3](#0-2) 

and again summarized in the precompile testing README: [4](#0-3) 

Because the EVM's `CALL` opcode moves `msg.value` from the caller's balance to the callee address's balance in the StateDB *before* the precompile logic executes (this happens generically for any address, precompiled or not), calling `rewards(address)` with attached wei via a normal transaction (not `eth_call`/`staticcall`) transfers that wei into the precompile's own account balance in the usei/wei StateDB bridge. Unlike every other payable precompile method, there is no `HandlePaymentUsei`-style refund and no later usage of that balance, so the funds become permanently unreachable — the precompile address is not a real controllable Cosmos account that any user or module can sweep.

### Impact Explanation
Any transaction sender can cause permanent loss of their own or an attacker-directed victim's funds by inducing (or being tricked into) a `CALL` to `rewards()` with non-zero value — e.g., a malicious dApp front-end could construct a transaction that silently attaches value to this call. This satisfies the "permanent freezing of funds" impact category: wei sent this way cannot be recovered by the sender, the chain, or governance through any existing withdrawal path.

### Likelihood Explanation
Likelihood is moderate: this requires a real mined transaction (not `eth_call`) invoking `rewards()` with `value > 0`, which any EOA or contract can trigger with a single crafted transaction — no special privileges, precompile allowlisting, or validator cooperation needed. The main mitigating factor is that well-behaved wallets/dApps calling a "view" method wouldn't normally attach value, but nothing in the precompile enforces this, and a malicious or buggy integration can trivially do so.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to the `RewardsMethod` case in `Execute` (and its legacy precompile versions) exactly as is already done for `WithdrawValidatorCommissionMethod`, so a value-bearing call to `rewards()` reverts instead of silently stranding funds. Alternatively, if payability is intentional, route any received value through `HandlePaymentUsei` to refund the caller.

### Proof of Concept
1. Deploy/hold an EOA with a Sei-EVM association.
2. Send a real transaction (mined, not `eth_call`) to the distribution precompile address `0x...1007` calling `rewards(delegatorAddress)` with `value: 1 (or more) wei/usei-equivalent` and sufficient gas.
3. Observe: the call succeeds and returns reward data as normal, exactly as documented in the test comment. [5](#0-4) 
4. Query the sender's on-chain usei/wei balance before and after: the attached value is deducted from the sender and is not present anywhere reclaimable (no refund event, no corresponding bank transfer), unlike calls to `withdrawDelegationRewards`/`setWithdrawAddress`, which use `pcommon.HandlePaymentUsei` to return unused value. func HandlePaymentUsei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Coin, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	if !wei.IsZero() {
		return sdk.Coin{}, fmt.Errorf("selected precompile function does not allow payment with non-zero wei remainder: received %s", value)
	}
	coin := sdk.NewCoin(sdk.MustGetBaseDenom(), usei)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoins(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, sdk.NewCoins(coin)); err != nil {
		return sdk.Coin{}, err
	}
	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
		if hooks.OnEnter != nil {
			hooks.OnEnter(depth+1, byte(vm.CALL), evmKeeper.GetEVMAddressOrDefault(newCtx, precompileAddr), evmKeeper.GetEVMAddressOrDefault(newCtx, payer), []byte{}, GetRemainingGas(newCtx, evmKeeper), value)
		}
		if hooks.OnExit != nil {
			hooks.OnExit(depth+1, []byte{}, 0, nil, false)
		}
	}
	return coin, nil
}
