### Title
Rewards can be permanently frozen in `WomUp` by repeatedly staking dust amounts to keep `rewardPerToken()` rounding to zero - (File: wombat/WomUp.sol)

### Summary
`WomUp.sol` implements a classic Synthetix-style, time-weighted reward accumulator (`rewardPerTokenStored`, `lastUpdateTime`, `rewardRate`). Because `rewardPerToken()` uses integer division and any call to the public, unprivileged `stake()`/`withdraw()` functions resets `lastUpdateTime` to the current block timestamp, a user can keep `timeSinceLastUpdated` low enough (by staking a dust amount of `wom` on a tight cadence) that `(lastTimeRewardApplicable() - lastUpdateTime) * rewardRate * 1e18 / totalSupply()` truncates to zero on every update. Since the truncated remainder is discarded (not carried forward) each time `lastUpdateTime` advances, `rewardPerTokenStored` can be kept from ever increasing for the whole `duration` (7 days) of the reward period, permanently freezing the yield owed to all other stakers for that epoch.

### Finding Description
`rewardPerToken()` computes the newly accrued reward per token since the last checkpoint: [1](#0-0) 

This is checkpointed via the `updateReward` modifier, which is triggered on every `stake()`/`withdraw()`/`migrate()`/`getReward()` call by *any* address, and which unconditionally advances `lastUpdateTime` to `lastTimeRewardApplicable()` regardless of whether `rewardPerTokenStored` actually changed: [2](#0-1) 

`stake()` is a fully public, unprivileged entry point that only requires `_amount != 0`, so it can be called with the smallest possible unit (`1 wei` of `wom`): [3](#0-2) 

Because Solidity division truncates, whenever `(lastTimeRewardApplicable() - lastUpdateTime) * rewardRate * 1e18 < totalSupply()`, the increment to `rewardPerTokenStored` is `0`, and the fractional/rounded-down reward for that interval is lost forever (not accumulated for the next call) because `lastUpdateTime` has already advanced past that interval. A user (attacker, or simply organic frequent staking/unstaking activity from many users) can keep re-triggering `updateReward` at a high frequency (e.g., every block by staking/withdrawing `1 wei`), keeping `timeSinceLastUpdated` minimal on every checkpoint and thus keeping the increment truncated to zero indefinitely — for as long as `rewardRate * 1e18 * timeSinceLastUpdated < totalSupply()` holds, which is controlled by the pre-set `rewardRate` (derived from `initializeRewards()`, based on however much `mgp` happens to be funded) versus the pool's `totalSupply()` of staked WOM.

This mirrors the reported bug class exactly: the accumulator (`rewardPerTokenStored`) can be kept flat while the time tracker (`lastUpdateTime`) keeps moving forward, permanently eating the rounding dust and starving legitimate stakers of their share of rewards for the active `duration`.

### Impact Explanation
If exploited (or triggered organically by normal high-frequency stake/unstake activity), all `mgp` rewards allocated for the active 7-day period (`duration = 7 days`) become permanently unclaimable by legitimate stakers — `rewardPerTokenStored` never advances, so `earned()` stays at (or near) zero for everyone despite the reward budget being consumed by the fixed `periodFinish` window. This is a permanent freeze of already-funded, unclaimed yield for a period well in excess of 24 hours (the entire `duration`), reachable purely through the unprivileged `stake()`/`withdraw()` functions.

### Likelihood Explanation
Exploitability depends on the ratio between `rewardRate` (set by `initializeRewards()` from the funded `mgp` balance divided by `duration`) and `totalSupply()` (total WOM staked in the pool). Whenever this ratio is low enough that `rewardRate * 1e18 * 1 second < totalSupply()`, a griefer can trivially keep the checkpoint interval near 1 second by repeatedly calling `stake(1)` (dust amount, reversible economically since WOM/mWom is retained, only gas is spent), sustaining the zero-increment condition for the whole reward epoch. This does not require any privileged role and can also occur unintentionally from ordinary high-frequency user activity, exactly as described in the referenced report.

### Recommendation
Avoid resetting `lastUpdateTime` when the computed increment to `rewardPerTokenStored` truncates to zero, or accumulate un-flushed remainder time/reward instead of discarding it, e.g. track a running "undistributed" remainder to be added into the next calculation instead of overwriting `lastUpdateTime` unconditionally in the `updateReward` modifier. Alternatively, scale `rewardPerTokenStored` up further (e.g., 1e30 instead of 1e18) or restrict/rate-limit dust-sized `stake`/`withdraw` calls so an attacker cannot cheaply force sub-second checkpoint granularity.

### Proof of Concept
1. Owner calls `initializeRewards()` funding the pool with `mgp`, setting `rewardRate = rewardsAvailable / duration` and `periodFinish = block.timestamp + duration` (7 days), per [4](#0-3) .
2. A user (attacker) calls `stake(1)` (1 wei of `wom`) as the sole/dominant interacting party, or simply piggybacks on natural high-frequency activity from many users, every block/second for the full 7-day duration.
3. On each call, `updateReward(msg.sender)` computes `rewardPerToken()`; because `timeSinceLastUpdated` is ~1 second each time and `rewardRate * 1e18 * 1 < totalSupply()`, the added term truncates to `0`, so `rewardPerTokenStored` never increases, and `lastUpdateTime` is advanced anyway per [2](#0-1) .
4. After `periodFinish` is reached, `lastTimeRewardApplicable()` caps at `periodFinish`, but `rewardPerTokenStored` has remained effectively at its initial value throughout — all legitimate stakers' `earned()` values stay ~0, and the entire `mgp` reward budget for that period is unclaimable/lost to rounding, despite having been fully funded.

    function rewardPerToken() public view returns (uint256) {
        if (totalSupply() == 0) {
            return rewardPerTokenStored;
        }
        return
            rewardPerTokenStored + (
                (lastTimeRewardApplicable() - (lastUpdateTime)) * rewardRate * (1e18) / (totalSupply())

    }

    function initializeRewards() external onlyOwner returns (bool) {
        if(rewardRate > 0) revert MustZero();

        uint256 rewardsAvailable = IERC20(mgp).balanceOf(address(this));
        if(rewardsAvailable == 0) revert MustNotZero();

        rewardRate = rewardsAvailable / (duration);

        lastUpdateTime = block.timestamp;
        periodFinish = block.timestamp + (duration);

        emit RewardAdded(rewardsAvailable);

        return true;
    }
