## Analysis

The external report's core invariant: **escrow accounting must be based on actual balance increase, not the nominal transfer amount**, because ERC-20 transfers can silently deliver less than requested (fee-on-transfer tokens, deflationary tokens, etc.).

`IntentGatewayV2.placeOrder` in this repo already implements the *exact* recommended mitigation for order input tokens — it snapshots the balance before `safeTransferFrom` and updates `order.inputs[i].amount` to the actual balance delta: [1](#0-0) 

However, the very same function, a few lines later, escrows the **solver fee** (`order.fees`) using the *nominal requested amount* instead of the verified balance increase — the pre-fix pattern the report describes: [2](#0-1) 

This `_orders[commitment][TRANSACTION_FEES] = order.fees` write assumes `safeTransferFrom` delivered exactly `order.fees` of `feeToken` to the contract, with no balance check. All escrowed fee tokens across every order commitment sit in one shared `feeToken` balance, so if the actual increase is ever less than `order.fees` (fee-on-transfer/deflationary token, or a proxy/upgradeable token later swapped in by governance to a fee-charging variant), the recorded escrow for that commitment exceeds what was actually deposited. When settlement runs, `withdraw()`/`_withdraw()` unconditionally transfers the *recorded* `fees` value out of the pool to the beneficiary/solver: [3](#0-2) 

Because escrow is not isolated per-commitment at the token level (it's bookkeeping against one shared balance), any order whose fee escrow was under-collected will, upon settlement, be paid out of tokens actually escrowed by *other* orders — a direct protocol/user fund leakage, identical in kind to the report's finding but reintroduced in a code path the fix wasn't applied to.

### Title
Order fee escrow trusts nominal `order.fees` instead of verified balance increase, enabling fee-token accounting drift and cross-order fund leakage - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` correctly reconciles input-token escrow against the actual post-transfer balance delta (mitigating fee-on-transfer/deflationary token risk), but the solver-fee escrow branch immediately below it skips this check and records `order.fees` verbatim.

### Finding Description
In the `order.fees > 0` branch of `placeOrder`, when `msgValue == 0`, the contract calls `IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees)` and then unconditionally sets `_orders[commitment][TRANSACTION_FEES] = order.fees`, with no balance-before/balance-after verification — unlike the input-token loop just above it (lines 282-297) which explicitly guards against this exact scenario: [4](#0-3) 
If `feeToken` (set via `IDispatcher(hostAddr).feeToken()`, a governance-controlled parameter) ever behaves as a fee-on-transfer/rebasing token, or any ERC-20 quirk causes actual receipt to be less than `order.fees`, the escrow ledger for that commitment is overstated relative to the tokens genuinely held for it. Since all fee escrow lives in one shared `feeToken` balance across all commitments, on settlement `_withdraw`/`withdraw` pays out the recorded (overstated) `fees` value: [3](#0-2) 
That payout is drawn from the shared pool, which includes fee tokens escrowed by unrelated, still-pending orders — leaking their funds.

### Impact Explanation
This is a fund-loss/leakage bug matching the bounty's "stealing or loss of funds" and "logic attacks" categories: value escrowed for one order can be paid out on settlement of another due to an accounting-vs-actual-balance mismatch, exactly the class of bug the source report describes, reproduced in the fee-escrow path that the main input-escrow path was already hardened against.

### Likelihood Explanation
Trigger requires only that `feeToken` (governance-settable via host parameters) is or becomes a token with any transfer-amount deviation. No malicious relayer, prover, or peer is needed — a normal user places an order paying fees in such a token and the mismatch is created entirely through the public `placeOrder` entrypoint.

### Recommendation
Apply the same balance-before/balance-after pattern already used for `order.inputs` to the fee-token transfer: snapshot `IERC20(feeToken).balanceOf(address(this))` before `safeTransferFrom`, and set `_orders[commitment][TRANSACTION_FEES]` to the actual balance delta rather than `order.fees`.

### Proof of Concept
1. Governance configures `feeToken` as (or it is later upgraded to behave as) a deflationary/fee-on-transfer ERC-20.
2. User A calls `placeOrder` with `order.fees = 100`; actual tokens received by the contract are only 98, but `_orders[commitmentA][TRANSACTION_FEES] = 100` is recorded.
3. User B places a separate order also paying fees in the same token, correctly funding the pool.
4. On settlement of order A, `withdraw()` transfers `100` out of the shared `feeToken` balance — 2 units more than order A actually contributed, sourced from order B's escrowed fee balance.
5. Repeated across orders, this drains the shared fee pool below what remaining orders are entitled to, causing later legitimate fee withdrawals to under-pay or revert due to insufficient contract balance.
