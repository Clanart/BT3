## Valid Vulnerability Confirmed

### Title
Relayer reward transfer is unconditionally executed while the `LastRewardedHeight` watermark update is skipped on `ReputationAsset::mint_into` failure, allowing repeated/duplicate treasury payouts for the same block span - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`Pallet::<T>::process_message` performs the `T::Currency::transfer` from the Treasury to the relayer **before** calling `T::ReputationAsset::mint_into`, and only advances the `LastRewardedHeight` watermark **after** the mint succeeds. If `mint_into` fails, the function returns `Err(Error::ReputationMintFailed)` after the funds have already been transferred, but before the watermark is advanced.

### Finding Description
In `process_message`:
1. The reward is computed from `LastRewardedHeight` as baseline vs. `latest_commitment_height` (`calculate_reward`). [1](#0-0) 
2. The Treasury→relayer transfer executes and the `RelayerRewarded` event fires. [2](#0-1) 
3. `T::ReputationAsset::mint_into` is called; if it errors (e.g., relayer account stays below the reputation asset's existential deposit), the function returns early with `Error::ReputationMintFailed` **before** reaching the watermark update. [3](#0-2) 
4. The caller `on_executed` discards the `Result` entirely via `let _ = Self::process_message(...)`, so the failure is silently swallowed and has no other side effect. [4](#0-3) 

Because `LastRewardedHeight` is never advanced when the mint fails, every subsequent successful `on_executed` invocation for that `state_machine_id` recomputes the reward using the *same stale baseline*, causing the span between the original baseline and the new `latest_height` to be paid out again (fully or overlapping with prior payouts), each time actually moving Treasury funds via `T::Currency::transfer`, regardless of whether the mint keeps failing. This breaks the documented invariant that "the watermark only moves forward, so a height... is not paid for a second time." [5](#0-4) 

### Impact Explanation
This allows repeated draining of the Treasury reward balance for a relayer whose reputation-asset account is deliberately kept unmintable (e.g., below the reputation asset's existential deposit), for the same or overlapping block spans, with no bound other than the attacker's ability to keep triggering `on_executed` for that state machine. This is a direct loss-of-funds / duplicate-settlement bug in production reward accounting.

### Likelihood Explanation
The precondition (an account for which `mint_into` deterministically fails, e.g. an unfunded/sub-ED account) is attacker-controlled and requires no privileged access — the attacker only needs to control the relayer account identity recovered from the consensus message signature. No proof forgery or protocol-level compromise is needed; this is a pure ordering/error-handling bug in `process_message`.

### Recommendation
Advance `LastRewardedHeight` (and/or gate the `T::Currency::transfer`) independently of `T::ReputationAsset::mint_into` outcome — e.g., update the watermark immediately after computing the reward and before/regardless of the mint call, or make the mint failure non-fatal to bookkeeping (log/skip minting reputation without reverting the watermark update), so the "paid once per span" invariant holds even when the reputation mint fails.

### Proof of Concept
1. Configure `StateMachinesCostPerBlock` for a target `state_machine_id`.
2. Use a mock `T::ReputationAsset` whose `mint_into` always returns `Err` (or use a real `pallet-assets` reputation asset with the relayer account balance kept below the asset's `min_balance`).
3. Drive `on_executed` with a `StateMachineUpdated` event for that `state_machine_id`/height signed by the attacker-controlled relayer key — observe: Treasury is debited, `RelayerRewarded` event fires, but `LastRewardedHeight` is *not* updated (because `process_message` returns early on `ReputationMintFailed`).
4. Drive `on_executed` again (e.g., for a subsequent, or even the same, `latest_height`) — `calculate_reward` recomputes using the stale baseline, and Treasury is debited a second time for a span that should have already been "watermarked" as paid.
5. Assert: Treasury balance decreases by more than one reward-span amount across the two calls, violating "reward paid at most once per block-span."
