### Title
Cached FROST preprocess deterministically reuses nonces across sign calls under a single context, enabling private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::share_internal` derives its `AlgorithmSignMachine` via `preprocess_internal`, which stores a single `CachedPreprocess` seed keyed only by `context` and re-derives identical FROST nonces from that seed on every invocation. If `share_internal` is ever executed more than once for the same context (e.g., a reattempt, a second cosign/slash-report under the same tributary context, or any code path that re-enters share production), the same `(d, e)` nonces are reused to sign different binding-factor/message combinations, leaking the validator's secret share — recoverable entirely from data published on the public tributary. (See citations below; I was unable to fully trace every call site of `share_internal` before the iteration limit, so the exact triggering path is the residual uncertainty.)

### Finding Description
`preprocess_internal` creates the seed once per context, XOR-encrypts it, persists it via `CachedPreprocesses::set`, and on every later call reloads the same seed and reconstructs the machine with `AlgorithmSignMachine::from_cache` [1](#0-0) . `from_cache` routes to `seeded_preprocess`, which seeds `ChaCha20Rng` with the stored 32 bytes and regenerates `Commitments::new` — so the same seed always yields the same nonce pair `(d, e)` and the same published preprocess [2](#0-1) . `share_internal` unconditionally calls `preprocess_internal` each time it produces a share [3](#0-2) .

In `AlgorithmSignMachine::sign`, the effective nonce is `base + rho * actual` where `rho` is bound to `group_key`, `hash_msg(msg)` and the preprocesses challenge [4](#0-3) . Two shares produced from the same nonces over different messages (or different participant sets, giving different `rho`) yield two linear equations `s = d + e·ρ + λ·share·c` in the two unknowns `d, e` plus the share term — standard FROST nonce reuse, from which the private key share is solved directly from the two published `SignatureShare`s and public preprocesses. The FROST spec itself acknowledges that reuse of a cached preprocess "will enable third-party recovery of your private key share" [5](#0-4) .

This mirrors the reported bug class: the seed is committed to storage once (the analog of the early `set(..., 0)` write), and every subsequent legitimate signing operation within the same context window silently reuses the consumed secret material instead of drawing fresh nonces — the "premature finalization" of state that should have been regenerated per use.

### Impact Explanation
Any party reading the tributary (unprivileged observer) who sees two `Label::Share`/`Transaction::Sign` shares emitted under the same context with distinct signed payloads obtains the validator's Ristretto secret share, enabling reconstruction/forgery contribution to the MuSig2/FROST group key for that validator set — i.e., concrete key share recovery.

### Likelihood Explanation
The vulnerability fires whenever more than one share-producing operation shares a `context`. The coordinator deliberately caches preprocesses so that reboots/re-deliveries regenerate the *same* preprocess (intended for idempotent redelivery), but the same mechanism applies to genuinely distinct sign calls: `share_internal` is invoked per share-collection round with no nonce freshness check and no deletion/rotation of `CachedPreprocesses` after a successful `machine.sign` [3](#0-2) . If the context does not embed `attempt`/message identity (it is a fixed `C: Encode` per `SigningProtocol`), any second `sign` in that context triggers reuse. Likelihood is conditional on whether higher layers ever issue two distinct messages under one context; the code places no guard preventing it.

### Recommendation
Key the cached preprocess by `(context, message/nonce-session)` or delete `CachedPreprocesses[context]` after the first successful `machine.sign`, storing a tombstone that forces re-`preprocess` (fresh `OsRng` seed) on any subsequent share attempt — so that, as with the fixed epoch check, a consumed one-time value can never be reused within its still-valid window. At minimum, assert in `share_internal` that the exact `msg`/participant set matches the one the cache was created for.

### Proof of Concept
1. From `coordinator/src/tributary/signing_protocol.rs`: `preprocess_internal` persists `CachedPreprocess` keyed solely by `self.context.encode()` and rebuilds the machine from that seed on every call; `share_internal` calls it each time.
2. From `crypto/frost/src/sign.rs`: `seeded_preprocess` deterministically regenerates `nonces`/`commitments` from `ChaCha20Rng::from_seed(*seed.0)`; `sign` forms the effective nonce `base + rho·actual` and emits `SignatureShare(share)` where `share` is affine in `d, e` and the secret share.
3. Two shares `(s1, msg1)` and `(s2, msg2)` under one context: identical `(d, e)`, published identical preprocess commitments, differing `c` (signature challenge over msg) and/or `ρ` — solve the 2×2 linear system to recover `d, e`, then the private key share. All inputs (preprocesses, shares, messages) are public tributary transactions.

Residual uncertainty: I did not enumerate all `share_internal` call sites to confirm a same-context second `sign` is produced by unprivileged-reachable flow (vs. only on validator-triggered messages); if contexts are strictly per-message this degrades to a latent reuse hazard rather than a live trigger.

```rust
  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
```

```rust
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
```

**File:** spec/cryptography/FROST.md (L51-62)
```markdown
Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
```
