This confirms `timeout: 0` in `withdrawal.rs`'s `DispatchPost` becomes `timeout_timestamp: 0`, which per `dispatcher.rs` (lines 118-124, 135-141) is the literal encoding for "never times out." That closes off the one recovery path (timeout-triggered refund) that exists elsewhere in the codebase (as shown by `EvmHost.dispatchTimeOut` and `pallet_ismp` `on_request_timeout`, which do refund the fee payer). Combined with `docs/outbound-request-incentivization.md`'s explicit admission that hyperbridge-originated system dispatches — explicitly including "the relayer pallet's withdrawal request" — carry `FeeMetadata { payer: [0u8;32], fee: Default::default() }`, i.e. zero relayer incentive, this gives a concrete, locally-provable analog to the Rubicon bug.

### Title
Relayer fee withdrawal zeroes accrued balance before settlement is guaranteed, permanently stranding funds - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` treats "dispatching the payout message" as equivalent to "having paid the relayer," zeroing the relayer's `Fees` entry immediately, atomically, in the same call that only *initiates* an ISMP POST to the destination chain. The actual value transfer happens later and only if a third party relayer delivers that message. Two facts in this codebase mean that delivery is not guaranteed and, once it fails to happen, the funds can never be recovered: the withdrawal POST is dispatched with `timeout: 0` (no timeout, ever) and it carries zero relayer fee, so no economically-rational relayer is incentivized to deliver it.

### Finding Description
`Pallet::withdraw` in [1](#0-0)  reads `available_amount = Fees::<T>::get(...)`, dispatches a `DispatchPost` with `timeout: 0` carrying a `WithdrawalParams`/`WithdrawRelayerFees` payload to the destination chain's host manager, and then unconditionally zeroes the source-side accounting with `Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero())` in the same extrinsic — before any confirmation that the message was ever delivered.

The dispatch path in [2](#0-1)  converts `timeout: 0` into `timeout_timestamp: 0` for both GET and POST requests. Elsewhere in the same file, the module doc explicitly states the *only* recovery mechanism for a stuck dispatched request is the timeout-refund path: "If the dispatched request times-out, then pallet-ismp's inner subsystems will refund the fees to the sponsor of the request" ( [3](#0-2) ). A `timeout_timestamp` of `0` means this request can never time out, so this refund path is structurally unreachable for the withdrawal message.

Separately, `docs/outbound-request-incentivization.md` documents that this exact withdrawal dispatch (referencing `modules/pallets/relayer/src/lib.rs:638`, i.e. this same withdrawal flow) is dispatched with `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }` — zero fee, zero payer — meaning ordinary, non-malicious, profit-driven relayers "have no economic reason to pick them up," with the fix for this being an entirely separate, not-yet-implemented reward pallet (`OutboundRequestDeliveryReward`) ( [4](#0-3) ).

The corrupted/lost value is the relayer's `Fees::<T>::get(dest_chain, address)` entry: it is destroyed (set to `U256::zero()`) at `withdraw()` time on the mere assumption that the dispatched POST will eventually be delivered and settled by `HyperbridgeWithdrawalModule::on_accept` (source-chain substrate destinations, [5](#0-4) ) or the EVM host-manager's withdrawal handler — but nothing in the codebase re-credits `Fees` if that delivery never happens.

This is structurally identical to the Rubicon `closePosition` bug: an operation clears/commits accounting state for an amount that depends on a second, external, not-guaranteed-to-succeed step (there: `_repay`'s swap+transferFrom of the full debt; here: third-party relayer delivery of the payout message), and if that second step fails to complete, the actor is left with no ability to retry or recover, because the internal bookkeeping has already been irreversibly zeroed/consumed.

### Impact Explanation
This falls under "stealing or loss of funds" from the Impact Gate: a legitimate relayer's rightfully-earned fee balance (`Fees::<T>`) is deleted from source-chain accounting without a guarantee that the corresponding payout is or will ever be delivered on the destination chain, and with the one general-purpose recovery mechanism in this codebase (timeout refund) structurally disabled for this specific message (`timeout_timestamp: 0`). No malicious peer, relayer, or prover is required — ordinary economically-rational relayer behavior (not delivering a zero-fee message) is sufficient to trigger permanent fund loss for the withdrawing relayer.

### Likelihood Explanation
High for realization, though the actor causing loss is simply passive/absent (not malicious): any relayer calling `withdraw_fees` on a destination chain where no operator happens to self-relay or otherwise deliver the zero-fee `WithdrawRelayerFees`/`WithdrawalParams` message will have that balance permanently stuck. The project's own documentation (`docs/outbound-request-incentivization.md`) confirms this is a known, currently-unaddressed gap for exactly this dispatch site.

### Recommendation
Do not zero `Fees::<T>` until destination-side settlement is confirmed (e.g., only decrement on a delivery-receipt callback/ack from the destination, mirroring how `accumulate_fees` credits fees only after verifying a destination delivery proof), or attach a real timeout and a compensating on-timeout re-credit path for the withdrawal dispatch, and/or fund withdrawal dispatches with a non-zero relayer incentive (as proposed in `docs/outbound-request-incentivization.md`) so delivery is actually guaranteed before the source-side balance is destroyed.

### Proof of Concept
1. A relayer accrues `Fees::<T>::get(dest_chain, relayer) = N` via `accumulate()`.
2. Relayer calls `withdraw_fees` (`Pallet::withdraw`) for `dest_chain`. This dispatches a `DispatchPost{ timeout: 0, fee: Default::default(), ... }` and, in the same transaction, sets `Fees::<T>::insert(dest_chain, relayer, U256::zero())` ( [6](#0-5) ).
3. Because the dispatched request carries zero fee, no independent relayer has an economic incentive to relay it to `dest_chain` (per `docs/outbound-request-incentivization.md`).
4. Because `timeout_timestamp` is permanently `0` ( [7](#0-6) ), the message can never time out, so the standard "refund the sponsor on timeout" path documented in the dispatcher never fires.
5. The relayer's `N` units are unrecoverable: `Fees` is already zero, so a repeat `withdraw_fees` call fails `NotEnoughBalance`, and there is no other call path in `withdrawal.rs` or `accumulate.rs` that restores a previously-zeroed `Fees` entry.

**Caveat:** I was not able to fully trace the destination-side EVM `host_manager`/`WithdrawalParams` handler and the substrate `HostParams`/`HYPERBRIDGE_MODULE_ID` delivery path to confirm there is truly zero automatic redelivery/retry infrastructure outside of tesseract's off-chain relayer economics; if a production deployment guarantees self-relay of protocol-originated messages, the practical severity would be lower than described. Given index size limits, some destination-chain host-manager contract internals may not be fully represented here — a Devin session with full repo access could confirm this end to end.

```markdown
A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.

## The shape of the solution

The issue creator's preferred shape ([comment 4428807013](https://github.com/polytope-labs/hyperbridge/issues/532#issuecomment-4428807013)): use `pallet-relayer` to pay BRIDGE to whoever proves they delivered a hyperbridge-originated request. The messaging task in the tesseract relayer submits the claim.

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.

This is structurally identical to the existing `claim_outbound_consensus_delivery_reward` (see `modules/pallets/relayer/src/outbound_consensus.rs`) on the consensus side. The request claim lives in its own `modules/pallets/relayer/src/outbound_request.rs` module that mirrors it: swap "consensus rotation delivered" for "request delivered," key the reward storage by `module_id`, and have the relayer ship the full `PostRequest` in the claim so the pallet can hash it on chain.

No changes to pallet-hyperbridge or to any of the system-message dispatch sites. The reward is decoupled from the dispatch path and paid out at claim time against a destination state proof.
```
