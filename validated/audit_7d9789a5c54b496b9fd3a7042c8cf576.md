### Title
Self-Referral via Sybil Wallets Drains the Shared Referral Reward Pool - ([File: rewards/ReferralStorage.sol])

### Summary
`ReferralStorage::registerCode()` is fully permissionless and `ReferralStorage::useCode()` only blocks a wallet from linking a code it owns *itself* [1](#0-0) . Because any address can register a code with no eligibility gating [2](#0-1) , a single real user can register a code from a secondary wallet and apply it from their primary wallet, becoming both the "referrer" and "referee" of their own MasterMagpie reward claims and farming a shared, finite MGP reward pool.

### Finding Description
`MasterMagpie` calls `IReferralStorage(referral).trigger(_user, totalReward)` every time a user harvests MGP rewards [3](#0-2) . Inside `trigger()`, both a referer share and a referee share of the claimed amount are credited into `rewardAmount` for the referrer and referee addresses respectively, based on a tier percentage plus a vlMGP-lock-based "boost" factor [4](#0-3) . These `rewardAmount` balances are later paid out via `claimReward()`, which transfers MGP directly out of the `ReferralStorage` contract's own token balance — there is no per-trigger minting or transfer-in from `MasterMagpie` [5](#0-4) .

The only self-referral guard is `if (codeOwners[_code] == msg.sender) revert Circled();` in `useCode()` [1](#0-0) , which is the exact same weak check flagged in the external report (address-equality check bypassable via Sybil wallets). Since `registerCode()` has no access control or minimum-activity requirement [2](#0-1) , a user simply:
1. Registers a code from wallet B (`registerCode`).
2. Calls `useCode()` from wallet A (their real trading/staking wallet) to link A→B as referee→referrer.
3. Locks MGP into `vlMGP` from wallet B to raise `userInfos[B].factor` via `updateTotalFactor()` [6](#0-5) , boosting the referer reward rate through `_calBoosted()` [7](#0-6) .
4. Repeatedly harvests MGP rewards from wallet A in `MasterMagpie`, triggering `refererAmount` credit to B and `refereeAmount` credit to A on every claim — both ultimately controlled by the same actor.

### Impact Explanation
Because `claimReward()` pays out of `ReferralStorage`'s pre-funded MGP balance rather than newly minted/escrowed-per-trigger tokens, `rewardAmount` credited to Sybil-linked wallets represents a real, finite claim against that shared balance intended to reward genuine referrer/referee relationships. Unrestricted self-referral via Sybil wallets lets any single actor capture both the referrer and referee share on every single reward claim they make, disproportionately draining the pool relative to actual referral activity across the protocol. This can exhaust the contract's MGP balance, causing other legitimate referrers'/referees' `claimReward()` calls to revert on `safeTransfer` due to insufficient balance — a protocol-level insolvency/permanent freezing of other users' already-accrued (unclaimed) referral yield.

### Likelihood Explanation
This requires no privileged role, governance action, or oracle manipulation — only two ordinary EOAs and normal MGP locking/staking activity, all at the cost of gas. Given the referral system is designed to reward real user activity, any active trader has direct incentive to farm the extra reward with zero marginal cost beyond deploying a second wallet.

### Recommendation
Do not rely solely on `codeOwners[_code] == msg.sender` to prevent self-referral. Options include: gating `registerCode()` behind a minimum verified/eligible activity threshold (as suggested in the original report), tracking and capping total referral-boost reward emitted per unique locked-MGP source, or funding referral rewards proportionally per genuine trigger event (e.g., transferring exactly the reward amount from `MasterMagpie` at trigger time) rather than drawing down a shared pre-funded pool that can be gamed by Sybil relationships.

### Proof of Concept
1. Attacker controls wallet A (main) and wallet B (Sybil).
2. From B: call `registerCode(codeB)` — succeeds, no eligibility check [2](#0-1) .
3. From A: call `useCode(codeB)` — passes since `codeOwners[codeB] == B != A` [1](#0-0) .
4. From B: lock MGP in `vlMGP`, triggering `updateTotalFactor(B)` to raise B's boost factor [6](#0-5) .
5. From A: stake/claim in `MasterMagpie` repeatedly; each claim invokes `trigger(A, totalReward)`, crediting `rewardAmount` to both B (referer) and A (referee) [4](#0-3) .
6. Both A and B call `claimReward()` to withdraw MGP directly from the shared contract balance [5](#0-4) , extracting more MGP than a non-Sybil user ever could, at the expense of the shared pool available to genuine participants.

    function trigger(address _referee, uint256 _amount) external _onlyMasterMagpie {
        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }

        totalBoostFactor -= userInfo.factor;
        uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);
        userInfo.factor = DSMath.sqrt(vlMGPLockedAmoubnt);

        totalBoostFactor += userInfo.factor;
