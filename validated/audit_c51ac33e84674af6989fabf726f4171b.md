### Title
Deauthorized AccountKey Silently Reverts to AccountKeyLegacy After State Object Deletion, Reviving Old Private-Key Control Over an Account - (File: blockchain/state/statedb.go)

### Summary
Kaia's `AccountUpdate` transaction type lets an account owner replace its original ECDSA key (the implicit "legacy" key derived from the address) with a `AccountKeyPublic`, `AccountKeyWeightedMultiSig`, `AccountKeyRoleBased`, or even `AccountKeyFail` key, explicitly revoking the ability of the original private key to authorize transactions. However, if the underlying state object for that address is later removed from the state trie (e.g., via `deleteStateObject` after self-destruct or EIP-161-style emptiness pruning) and the account subsequently becomes non-empty again, `StateDB.GetKey` falls back to a fresh `AccountKeyLegacy`, silently restoring authority to the original, previously-revoked private key.

### Finding Description
`StateDB.GetKey` is the canonical accessor used throughout transaction validation (`Transaction.ValidateSender`, `TxPool.validateTx`, `Transaction.Validate`) to fetch the `AccountKey` that governs signature verification for an address: [1](#0-0) 

When no live `stateObject` exists for the address (i.e., it was deleted from the trie via `deleteStateObject`, or a new one hasn't been instantiated), the function does **not** return an error or "no key configured" state — it returns a brand-new `accountkey.NewAccountKeyLegacy()`: [2](#0-1) 

This is the exact same fallback used for a freshly-created, never-before-used account: [3](#0-2) 

`AccountKeyLegacy.Validate`/`ValidateMember` authorizes any signature whose recovered public key hashes to the account address — i.e., it re-enables the original private key associated with that address: [4](#0-3) 

This mirrors GHSA-6gjf-7w99-j7x7's bug class: a credential that was explicitly revoked (the October admin's deleted account / here, the pre-`AccountUpdate` private key) regains standing to authenticate/authorize once the record holding the revocation (the account's custom `AccountKey`, analogous to the admin DB row) is purged and the identity is "recreated" from a bare state. The state-transition machinery treats "account not present in trie" as equivalent to "account with default legacy key," rather than as "no signature is valid for this address," which loses the security intent of `AccountUpdate`/`AccountKeyFail` once the address round-trips through deletion.

The signature check itself is used pervasively for authorizing value movement and account-key updates: [5](#0-4) [6](#0-5) 

### Impact Explanation
If an account address that previously moved off the legacy key (via `AccountUpdate`, to protect itself from an original private key that may have been compromised, is a multisig-controlled treasury, or is a smart-contract account hardened with `AccountKeyFail` to block EOA-style signature draining) is later reduced to an "empty"/self-destructed state and its trie entry removed, then re-funded, the account reverts to `AccountKeyLegacy`. Anyone holding the original address's private key — precisely the credential the owner tried to invalidate — can once again sign `TxTypeValueTransfer`, `TxTypeAccountUpdate`, and other transactions and take control of/drain funds sent to that address afterward. For `AccountKeyFail`-protected smart contract accounts specifically, the whole design intent ("prevent smart contract accounts from withdrawing tokens from themselves with a public key recovery mechanism") is documented directly in the code: [7](#0-6) 

Losing that guarantee after a delete/recreate cycle is an unauthorized-value-movement vector consistent with a High-severity authentication bypass, matching the CVSS profile of the reference advisory (network-reachable, no special privilege beyond controlling the original private key, high confidentiality/integrity/availability impact on the affected account's funds).

### Likelihood Explanation
Exploitation requires: (1) an address whose `AccountKey` was updated away from Legacy, (2) that address's state object being deleted from the trie (self-destruct for a contract account, or full balance/nonce/code emptying for an EOA under state-clearing semantics), and (3) the address later receiving value again so a fresh `stateObject`/`AccountCommon` is instantiated with the default Legacy key. Steps 1 and 3 are fully reachable by ordinary unprivileged transaction senders (any RoleTransaction/RoleAccountUpdate signer can trigger `AccountUpdate`, self-destruct, or a plain value transfer to refund an address). Step 2 (deletion) depends on Kaia's precise state-clearing/self-destruct condition, which the search results in this environment could not fully confirm (e.g., the exact "is-empty" predicate and whether `AccountUpdate`-tagged EOAs with balance are ever fully pruned mid-chain). This uncertainty means the finding should be treated as a credible architectural risk requiring confirmation of the specific deletion/state-clearing path rather than a proven, ready-to-exploit chain.

### Recommendation
Do not treat "no state object present" as equivalent to a legitimate `AccountKeyLegacy` account. Options:
1. Persist a tombstone/marker (or non-Legacy sentinel key, e.g. reuse `AccountKeyFail`) for any address that ever executed a non-Legacy `AccountUpdate`, so that re-creation via later funding does not silently restore legacy-key authority.
2. When a `stateObject` is deleted (self-destruct or emptiness pruning) for an account with a non-Legacy `AccountKey`, forbid recreation with the default Legacy key, or require an explicit `AccountUpdate` again before any legacy-style signature is accepted.
3. Audit all self-destruct/state-clearing code paths against accounts holding custom `AccountKey`s and add regression tests asserting that AccountKey semantics survive a delete → refund cycle.

### Proof of Concept
Conceptual reproduction (given confirmation of the underlying deletion trigger):
1. Address `A` starts with default `AccountKeyLegacy` (private key `k`).
2. `A` submits `TxTypeAccountUpdate` switching to `AccountKeyPublic`/`AccountKeyFail`, revoking `k`'s signing authority — verified via `accountkey.ValidateAccountKey` in `Transaction.ValidateSender`, `blockchain/types/transaction.go:930`.
3. `A`'s state object is deleted from the trie (self-destruct, or emptied to zero balance/nonce/no-code and pruned) via `deleteStateObject`, `blockchain/state/statedb.go:683-691`.
4. A third party sends value to `A` again, causing a fresh `stateObject`/`AccountCommon` to be created with the default `key: accountkey.NewAccountKeyLegacy()` (`blockchain/types/account/account_common.go:56-64`).
5. The holder of `k` signs a new `TxTypeValueTransfer` from `A`. `StateDB.GetKey(A)` returns `AccountKeyLegacy` (`blockchain/state/statedb.go:455-461`), `ValidateMember`/`Validate` succeeds because the recovered pubkey hashes to `A` (`blockchain/types/accountkey/account_key_legacy.go:53-71`), and the transaction is accepted by both `TxPool.validateTx` and block-level `Transaction.Validate`, despite `k` having been explicitly deauthorized in step 2.

// ValidateSender finds a sender from both legacy and new types of transactions.
// It returns the senders address and gas used for the tx validation.
func (tx *Transaction) ValidateSender(signer Signer, p AccountKeyPicker, currentBlockNumber uint64) (uint64, error) {
	if tx.IsEthereumTransaction() {
		addr, err := Sender(signer, tx)
		// Legacy transaction cannot be executed unless the account has a legacy key.
		if p.GetKey(addr).Type().IsLegacyAccountKey() == false {
			return 0, kerrors.ErrLegacyTransactionMustBeWithLegacyKey
		}
		tx.mu.Lock()
		if tx.validatedSender == (common.Address{}) {
			tx.validatedSender = addr
			tx.validatedFeePayer = addr
		}
		tx.mu.Unlock()
		return 0, err
	}

	pubkey, err := SenderPubkey(signer, tx)
	if err != nil {
		return 0, err
	}
	txfrom, ok := tx.data.(TxInternalDataFrom)
	if !ok {
		return 0, errNotTxInternalDataFrom
	}
	from := txfrom.GetFrom()
	accKey := p.GetKey(from)

	gasKey, err := accKey.SigValidationGas(currentBlockNumber, GetRoleTypeForValidation(tx.Type()), len(pubkey))
	if err != nil {
		return 0, err
	}

	if err := accountkey.ValidateAccountKey(currentBlockNumber, from, accKey, pubkey, GetRoleTypeForValidation(tx.Type())); err != nil {
		return 0, ErrInvalidAccountKey
	}

	tx.mu.Lock()
	if tx.validatedSender == (common.Address{}) {
		tx.validatedSender = from
		tx.validatedFeePayer = from
	}
	tx.mu.Unlock()

	return gasKey, nil
}
