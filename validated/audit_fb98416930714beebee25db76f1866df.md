## Title
`reassembleResolvedFile` splices Copilot hunk resolutions by conflict-marker order, not by hunk identity, allowing an attacker-crafted repository to cause silent misapplication (content-swap) of merge resolutions - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) reassembles the final file that gets written to disk and staged for commit by walking the raw on-disk file text and replacing the *Nth* conflict-marker block it encounters with the *Nth* entry of `hunkResolutions`, matched purely by encounter order, never by any content or identity check. [1](#0-0) 

The only safety net upstream, `validateResolutionPaths`, checks file paths and *hunk counts* per file, but never validates that each hunk's resolved content corresponds to the correct conflict region, nor that hunk order is preserved end-to-end. [2](#0-1) 

### Finding Description
The broken invariant is: "the Nth resolution the model returns for a file is assumed to correspond to the Nth conflict-marker block found on disk." This assumption is enforced nowhere except by construction of the prompt (`ConflictResolutionSystemPrompt`, `app/src/lib/copilot-conflict-resolution.ts:190-254`) which merely *asks* the model to return hunks "matching the … order from the input." There is no cross-check tying a returned hunk back to the original ours/theirs content it was supposed to resolve.

This is structurally identical to the `Lock`/`BondNFT` bug class: a downstream consumer (`BondNFT.distribute` / here, `reassembleResolvedFile`) trusts an upstream signal (asset totalShares / here, hunk ordering) without validating it against the actual state, and the failure is *silent* — no exception, no user-visible error — while it corrupts the value that ultimately gets persisted (transferred governance fees / here, the file content that gets `writeFile`'d and `git add`'d into the user's commit). [3](#0-2) 

The attacker-controlled input is the repository content itself: the conflicted file's on-disk marker layout (which the attacker fully controls by crafting a branch that will later be merged) combined with the LLM's non-deterministic hunk ordering in its JSON response. Because git conflict marker parsing is purely positional (`extractConflictHunks`, `app/src/lib/copilot-conflict-context.ts:179-279`) and reassembly is purely positional too, any mismatch between the number/order the model "sees" versus emits — e.g. a chunk of hunks dropped, reordered, or a hunk silently merged/split by the model when handling a repo the attacker constructed with many nested/adjacent conflict blocks, unusual encodings, or lines crafted to look like conflict markers to a model without them being real markers on disk — results in resolution content for conflict A being spliced into the position of conflict B.

Because `validateResolutionPaths` only checks `resolution.hunks.length !== expectedCount` per path and never checks that each hunk's content is consistent with the original ours/theirs pair it claims to resolve, an off-by-position swap that happens to preserve total hunk count for a file passes validation cleanly and reaches `reassembleResolvedFile`, which then writes the mismatched content to disk with no error at all. [4](#0-3) 

### Impact Explanation
The result is silent corruption of what the user commits/pushes: the "Copilot resolved conflicts" result dialog will show the user a resolution (and a `summary`/`reasoning` describing what was intended), but the code actually spliced onto disk and staged via `git add` (`app/src/lib/stores/app-store.ts:7258-7268`) can contain the wrong hunk's content for a given conflict location — e.g., merging in unrelated logic, silently dropping a security-relevant change from one side, or duplicating/misplacing code — without the write path, the validation, or the reassembly logic raising any error. This falls squarely within the requested impact category of "silent corruption of what the user commits or pushes," driven by attacker-controlled repository content (a maliciously structured conflicting branch/PR) that the local repo owner would merge and then trust to Copilot-based conflict resolution.

### Likelihood Explanation
Requires only an attacker's branch/PR containing crafted conflict-marker content to be present when the local user performs a merge/rebase/cherry-pick and chooses "Resolve with Copilot" — no local/physical access, no admin rights, no leaked credentials, and no unnatural user steps beyond the feature's own intended usage flow. Because the ordering/counting invariant is never explicitly enforced by code (it's an implicit LLM-prompt contract, `hunks: An ordered array with one entry per conflict … matching the "Conflict 1 of N" … order`), any imperfection in the model's hunk ordering for adversarially-crafted or unusually structured conflicts is sufficient to trigger this, making the likelihood non-trivial though dependent on model behavior rather than deterministic attacker control. [5](#0-4) 

### Recommendation
Strengthen `validateResolutionPaths`/`reassembleResolutions` to bind each returned hunk to the specific conflict region it resolves rather than trusting positional order alone — e.g., include a stable identifier or a snippet/hash of the original `oursContent`/`theirsContent` in each hunk request/response and verify it in `reassembleResolvedFile` before splicing, rejecting (not silently applying) the resolution when a mismatch is detected. Additionally, surface a hard failure (not a silent pass-through) whenever hunk content cannot be confidently matched to its source conflict block, forcing a fallback to manual resolution rather than writing unverified content into the user's working tree and stage.

### Proof of Concept
1. Attacker crafts a branch with a file containing multiple conflict blocks structured so that, once merged locally, the on-disk conflict markers are unusual/nested/adjacent enough (or include marker-look-alike lines) that the LLM is likely to reorder, merge, or split hunks relative to `extractConflictHunks`'s positional enumeration (`app/src/lib/copilot-conflict-context.ts:179-279`).
2. Victim merges this branch locally in GitHub Desktop and clicks "Resolve with Copilot" (`_startCopilotConflictResolution`, `app/src/lib/stores/app-store.ts:6912`).
3. The model returns a `resolutions[].hunks` array whose length matches `expectedHunkCounts` (passing `validateResolutionPaths`, `app/src/lib/copilot-conflict-resolution.ts:509-520`) but whose per-hunk order does not correspond 1:1 to the actual on-disk conflict-block order.
4. `reassembleResolutions` → `reassembleResolvedFile` splices hunk `i`'s content into conflict-block `i` positionally (`app/src/lib/copilot-conflict-resolution.ts:585-591`), producing a file where resolution content is attached to the wrong conflict.
5. User clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes this content to disk and stages it via `git add` with no error surfaced (`app/src/lib/stores/app-store.ts:7258-7268`), and the corrupted merge is committed and can be pushed.

*Note: this analysis is based on statically reading `copilot-conflict-resolution.ts`, `copilot-conflict-context.ts`, and `app-store.ts` in the index; I did not have the ability to run the Copilot SDK model live to empirically confirm how frequently ordering mismatches occur in practice, so the likelihood is model-behavior-dependent and not deterministically provable from static code alone.*

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
