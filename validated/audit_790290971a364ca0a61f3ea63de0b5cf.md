### Title
GitHub host spoofing via forged `WWW-Authenticate: realm="GitHub"` header bypasses HTTPS-only safeguard in credential helper - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind` classifies a git remote endpoint as `'enterprise'`, `'github.com'`, or `'generic'` in order to decide whether GitHub Desktop should treat the remote as a GitHub host (and thus prompt the user to sign in with a GitHub/Enterprise account, potentially handing over stored account tokens) or as a plain generic git host. The classification trusts an attacker-controlled `WWW-Authenticate` header value before it ever checks the URL scheme.

### Finding Description
`getEndpointKind` inspects the credential map's `wwwauth[...]` entries — which are populated directly from the `WWW-Authenticate` response header that Git forwards from the remote server to the credential helper: [1](#0-0) 

If the header contains `realm="GitHub"`, the function immediately returns `'enterprise'`. This check happens **before** the explicit HTTPS-only guard further down in the same function: [2](#0-1) 

The comment at line 172 states the app's intended invariant — "All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can assume that this is not a GitHub host" — but the `wwwauth[...]` branch returns early and never reaches this check, so a plain-`http://` remote can still be classified as `'enterprise'` simply by returning a spoofed header.

In `getCredential`, once `endpointKind !== 'generic'` and no stored account matches the endpoint, GitHub Desktop calls `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`promptForGitHubSignIn` then wires the Enterprise sign-in flow directly to the attacker's origin, via `setSignInEndpoint(origin)` and `credentialHelperUrl: endpoint`: [4](#0-3) 

If the user completes that sign-in (entering a PAT/OAuth token, or via device flow tied to that origin), the resulting `Account`'s token is merged into the credential (`credWithAccount`) and returned to Git as the password for that request: [5](#0-4) 

Because the endpoint's scheme was never verified to be HTTPS, this can result in the resulting Basic-Auth credential being sent by Git in cleartext to `http://` — an attacker who is only on-path or who merely stands up a plain HTTP server that responds `401` with a forged `WWW-Authenticate: Basic realm="GitHub"` header can trigger this flow.

### Impact Explanation
This lets an unauthorized, attacker-controlled git remote/proxy response impersonate a "GitHub Enterprise" endpoint purely by spoofing a response header, causing GitHub Desktop to:
1. Display a GitHub Enterprise sign-in dialog bound to the attacker's chosen origin (`setSignInEndpoint(origin)`), which is a form of endpoint/account-binding confusion the user did not authorize.
2. Potentially transmit the resulting account token to that same attacker's host in cleartext over `http://`, since the HTTPS-only check (which was specifically designed to prevent this class of host misclassification) is bypassed for the `wwwauth[]` code path.

This matches the described threat class: a credential/token normally scoped to GitHub.com/GHE being funneled to an attacker-controlled host that the user never authorized, via the trampoline credential helper.

### Likelihood Explanation
Exploitation requires the user to interact with a malicious or compromised git remote (adding/cloning/fetching from an attacker-controlled server) that returns a crafted `401` response with a forged `WWW-Authenticate` header — this is squarely within scope ("git remote/proxy response"). No admin rights, local access, or leaked credentials are needed. However, actual credential exfiltration additionally requires the user to proceed through the resulting sign-in prompt, which somewhat lowers the practical likelihood compared to a fully silent exfiltration, but the host-classification/HTTPS-bypass itself is a clear, unconditional logic flaw independent of user action, since the classification result is wrong before any user prompt occurs.

### Recommendation
Move the HTTPS-scheme check (`credentialUrl.protocol !== 'https:'`) to run *before* the `wwwauth[...]` realm-sniffing loop, so a non-HTTPS endpoint can never be classified as `'enterprise'`/`'github.com'` regardless of what `WWW-Authenticate` header value it presents. Consider also validating that the `realm="GitHub"` heuristic is only trusted when combined with other corroborating signals (e.g., a following `isGitHubHost` network check) rather than treated as sufficient by itself.

### Proof of Concept
1. Stand up an HTTP (not HTTPS) git server at `http://attacker.example/repo.git` that, when Git attempts an authenticated request, responds `401 Unauthorized` with header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, add this URL as a remote and attempt to fetch/clone.
3. Git invokes the `desktop` credential helper (trampoline) with the captured header forwarded as a `wwwauth[...]` credential field, per [1](#0-0) .
4. `getEndpointKind` returns `'enterprise'` without ever checking that the URL is `http:` rather than `https:`.
5. Since no stored account matches `attacker.example`, GitHub Desktop shows "Sign in to GitHub Enterprise" bound to `http://attacker.example`, per [6](#0-5) .
6. If the user completes sign-in, the resulting token is merged into the credential returned to Git and used to authenticate the plaintext HTTP request to the attacker's server.

Note: I could not fully trace how Git populates the `wwwauth[...]` credential fields end-to-end inside this repo (it is a Git core client-side behavior invoked via `dugite`, not implemented in this codebase), so the exact wire format/timing of that forwarding could not be independently verified from source; this is standard documented Git credential-helper behavior (`git credential-cache`/`GCM` `wwwauth[N]` capability) but the confirmation of the full request/response cycle here relies on that external Git behavior rather than code in this repository.

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
