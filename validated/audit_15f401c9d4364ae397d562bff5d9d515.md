## Title
`fillOrder` records arbitrary, unpaid solver-declared output amounts into `VWAPOracle`, letting any solver poison the price/spread oracle - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
This is a direct analog of the `calculateSetupRate()`/`calculateUpDownRate()` bug: a value that feeds into persistent, presumably trusted protocol accounting (`collectedFee` in the report; `_tokenSpreads`/VWAP in Hyperbridge) is derived from **caller-supplied numbers that are never fully reconciled against the tokens actually moved**. In `IntentGatewayV2.fillOrder`, the solver-declared `options.outputs` array is forwarded unmodified to `VWAPOracle.recordSpread`, even though the actual on-chain token movement can be capped to a smaller amount (partial fills). Any solver can therefore inflate the recorded spread/VWAP data without paying for the inflated amount.

### Finding Description
`fillOrder` computes and executes the fill, then unconditionally reports the oracle using the *raw, attacker-supplied* `options.outputs`, not the amount that was actually transferred: [1](#0-0) 

For same-chain **partial** fills, `IntrinsicIntents._fillSameChain` caps the actually-transferred amount to `remaining` when a subsequent partial fill's `solverAmount` exceeds what's left to fill: [2](#0-1) 

The transfer size (`beneficiaryTotal`, `protocolShare`) is derived from the *capped* `fillAmount`, not from the solver's declared `solverAmount`. Nothing in the code path re-derives an "actual outputs" array using `fillAmount`/`outputFills` for the oracle call — `fillOrder` still passes the original, uncapped `options.outputs` straight through to `recordSpread`.

`VWAPOracle.recordSpread` is guarded only by a `restrict(_intentGateway)` modifier that checks `msg.sender == _intentGateway` — it fully trusts whatever `inputs`/`outputs` the gateway forwards, with no revalidation against actual transferred token amounts: [3](#0-2) 

Because `recordSpread` computes `spreadBps` from `(outputAmountNormalized - inputAmountNormalized) / inputAmountNormalized` and folds it into the volume-weighted cumulative average (`_updateCumulativeSpread`), a solver who declares an inflated `options.outputs[i].amount` on a partial-fill call — while only being forced to actually transfer the smaller, capped `fillAmount` — gets the inflated (favorable) spread recorded at zero extra cost.

This exactly mirrors the reported bug class: a function reachable by any unprivileged caller lets attacker-chosen numbers (`lostTeamTotal`/`wonTeamTotal` in the original report; `options.outputs` here) flow directly into a persistent global accounting variable (`collectedFee` there; `_tokenSpreads` VWAP data here) without being checked against the real economic event that is supposed to back it.

### Impact Explanation
`VWAPOracle` is explicitly documented as tracking "cumulative weighted average spreads for same-token swaps" — i.e., a price-reference used to gauge fill quality/protocol economics. If any downstream logic (governance decisions, fee-tier tuning, solver reputation, dispute/slashing heuristics, or a future on-chain guard rejecting bad fills) relies on `spread()`, an attacker can cheaply and repeatedly bias that state without paying the tokens the recorded numbers imply. This is a false-state-acceptance / accounting-manipulation issue matching the bounty's "logic attacks" and "false proof/state acceptance" categories — the on-chain accounting no longer reflects real economic activity, and it is reachable by any ordinary, unprivileged solver through the public `fillOrder` entrypoint.

### Likelihood Explanation
High. `fillOrder` is a completely public, permissionless function; no relayer, prover, or admin compromise is required. All a solver needs to do is choose a partial fill scenario (`alreadyFilled > 0` and `solverAmount > remaining`) and declare an oversized `options.outputs[i].amount`, which the contract silently caps for the token transfer but still forwards uncapped to the oracle. This requires no special conditions beyond normal partial-fill usage of the same-chain intents flow.

### Recommendation
In `IntentGatewayV2.fillOrder`, pass to `IIntentPriceOracle.recordSpread` the amounts that were actually transferred (i.e., the same `outputFills`/`fillAmount`-derived array emitted in `OrderFilled`/`PartialFill`), not the raw `options.outputs`. `_fillSameChain`/`_fillCrossChain` already compute `outputFills` for the event; that same array (or an equivalent "amount actually paid") should be threaded back to the oracle call instead of `options.outputs`.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `_params.priceOracle = VWAPOracle` and `solverSelection = false`.
2. User places a same-chain order requiring 1000 DAI output for 1000 USDC input.
3. Solver A partially fills 500 DAI (`solverAmount = 500e18`), which is `<= remaining`, so `fillAmount = 500e18`; `_partialFills` = 500e18; oracle gets `options.outputs[i].amount = 500e18` — correct so far since `solverAmount == fillAmount` here.
4. Solver B (attacker) then calls `fillOrder` for the same order with `options.outputs[i].amount = 10_000_000e18` (`remaining` is only 500e18). Per `IntrinsicIntents._fillSameChain` (`fillAmount = solverAmount > remaining ? remaining : solverAmount`), the actual transfer/escrow release is capped at `fillAmount = 500e18`, and the solver only needs to approve/pay for `beneficiaryTotal = 500e18` (no surplus branch taken because `alreadyFilled != 0`).
5. `fillOrder` still calls `recordSpread(commitment, order.source, order.inputs, options.outputs)` with the attacker's uncapped `options.outputs[i].amount = 10_000_000e18` against `order.inputs[i].amount = 1000e6` (USDC), producing a wildly inflated positive `spreadBps` and skewing `_tokenSpreads[sourceChainHash][DAI]`'s weighted average — for a real cost of only 500 DAI instead of the ~10,000,000 DAI the recorded data implies.

    /**
     * @inheritdoc IIntentPriceOracle
     */
    function recordSpread(
        bytes32 commitment,
        bytes memory sourceChain,
        TokenInfo[] calldata inputs,
        TokenInfo[] calldata outputs
    ) external restrict(_intentGateway) {
        // Validate inputs and outputs have the same length
        if (inputs.length != outputs.length || inputs.length == 0) {
            return;
        }

        bytes32 sourceChainHash = keccak256(sourceChain);
        uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

            // Calculate spread for this token: (output - input) / input * 10000
            // Positive spread = filler provided more tokens (good for user)
            // Negative spread = filler provided fewer tokens (filler captured spread)
            int256 spreadBps = 0;
            if (inputAmountNormalized > 0) {
                int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
                spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
            }

            // Update cumulative spread data for this token (weighted by volume)
            int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
            _updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);

            // Emit event for each token
            emit SpreadRecorded(commitment, outputToken, spreadBps);
        }
    }
