## Finding [1](#0-0) 

The `Teleportation` bug is a "free, low-cost action that exhausts a shared, fixed-size resource budget and locks out all other users for an extended period." Chia's mempool block-builder has a directly analogous mechanism: `PRIORITY_TX_THRESHOLD`.

### Root cause

`PRIORITY_TX_THRESHOLD = 3` and `MAX_SKIPPED_ITEMS = 10` are hard-coded constants used in both block-building code paths (`Mempool.create_bundle_from_mempool_items()` and `Mempool.create_block_generator2()`). [2](#0-1) [3](#0-2) 

Mempool items are iterated in `priority DESC, seq ASC` order, where `priority` is `fee_per_virtual_cost` set at admission time [4](#0-3) . Once the number of "skipped" items (items/batches that don't fit the remaining block budget) reaches `PRIORITY_TX_THRESHOLD` (only 3), the code takes an unconditional shortcut: **any** subsequent mempool item that is fast-forward (FF) or dedup (DEDUP) eligible — i.e. any singleton spend (NFT, DID, vault, etc.) or any duplicated-solution CAT/offer spend — is skipped without even being checked for fit, purely to save block-building time: [5](#0-4) 

An unprivileged mempool submitter can pay a modest, competitive `fee_per_cost` (no need for the transaction to ever confirm — fees are only paid on inclusion, so an attacker whose transactions never get included pays **nothing**) and craft 3+ transactions that are ordered ahead of legitimate FF/DEDUP spenders and that don't fit into the remaining block space. This flips the `skipped_items >= PRIORITY_TX_THRESHOLD` shortcut, and every other user's fast-forward eligible (singleton/NFT/DID) or dedup-eligible (CAT/offer) spend bundle already in the mempool is skipped from every subsequent block-building attempt, for as long as the attacker's 3 blocking items remain in the mempool (they can be refreshed/replaced before eviction or expiry).

This mirrors the report's pattern precisely: a cheap, fee-optional, unprivileged action exhausts a small fixed counter (`PRIORITY_TX_THRESHOLD` analogous to `maxTransferAmountPerDay`) and blocks all other users relying on that code path (here, every NFT/DID/vault singleton spend and every dedup/offer-settlement spend) from having their transactions processed — a spend-triggered transaction-processing halt.

### Impact

* All singleton-owning users (NFT transfers, DID updates, vault/CR-CAT operations relying on FF) and all dedup-eligible spenders (e.g. multiple parties claiming the same offer, CAT ring spends) can be locked out of block inclusion indefinitely while the attacker maintains 3 cheap blocking entries in the mempool.
* The attack costs the attacker nothing in fees, since unconfirmed transactions never pay a fee; only the (temporary) illusion of committed coin value is required for the transactions to gain high mempool priority.

### Recommendation
Do not apply the FF/DEDUP-skip shortcut based purely on a global `skipped_items` counter that any low-fee/no-cost transaction can inflate. Instead, scope the skip counter per priority class, require the "skipping" transactions to have actually paid a real fee (not merely claimed one), or bound the shortcut by cumulative wasted cost/time rather than a raw item count of 3.

### Proof of Concept (conceptual)
1. Attacker submits 3 (or more) spend bundles to the mempool with a `fee_per_cost` higher than that of pending NFT/DID/dedup transactions, and with a `cost` sized so each fails to fit in the remaining block space once earlier batches are committed — see `if block_cost + item.conds.cost - cost_saving > constants.MAX_BLOCK_COST_CLVM:` at [6](#0-5) .
2. These transactions are never included on-chain (so no fee is ever actually charged), but they raise `skipped_items` to `PRIORITY_TX_THRESHOLD` (3).
3. From that point on, every FF/DEDUP-eligible mempool item is skipped unconditionally at [5](#0-4) , blocking all NFT/DID/offer/dedup transactions from every subsequent block, as long as the attacker keeps re-submitting equivalent blocking items before they expire/get evicted.
