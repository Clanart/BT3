### Title
Divergent duplicate sanitizer (`safeDirectoryName`) lets a malicious PR head-ref name traverse the worktree destination path - (File: app/src/ui/lib/repository-path.tsx)

### Summary
GitHub Desktop has at least three independent, non-canonical reimplementations of "make a name filesystem-safe": `sanitizeCloneName()` [1](#0-0) , `sanitizedRefName()` [2](#0-1) , and `safeDirectoryName()` inside `RepositoryPath` [3](#0-2) . Unlike the other two, `safeDirectoryName()` explicitly does **not** strip `/` or `\`, and does nothing at all on macOS/Linux, by design ("we don't sanitize `\` or `/` here since we use `Path.join`… letting users type something like OrgA\RepoB").

### Finding Description
`RepositoryPath.getFullPath()` builds the destination directory as `Path.join(path, safeDirectoryName(name))` [4](#0-3) . The `name` field is seeded from `initialName`, which for the "Add Worktree" flow is populated from `initialWorktreeName`/`initialBranchName`.

For the "Checkout PR in new worktree" entry point, `initialWorktreeName` is built directly from the PR number (safe) but `initialBranchName` is taken verbatim from `pullRequest.head.ref` — a value fully controlled by whoever opened the pull request on the attacker's fork: [5](#0-4) 

`AddWorktreeDialog` passes `initialWorktreeName ?? initialBranchName` straight into `RepositoryPath`'s `initialName`: [6](#0-5) 

Because `safeDirectoryName()` only strips `<>:"|?*` and trailing whitespace on Windows, and does nothing on POSIX, a PR head ref containing path separators and `..` segments (e.g. `../../../../.ssh`) is *not* neutralized here the way it would be by `sanitizeCloneName()` (used for `git clone`) or `sanitizedRefName()` (used to validate ref/branch names elsewhere, e.g. `testForInvalidChars` in `app/src/lib/parse-app-url.ts`). `Path.join(path, "../../../../.ssh")` resolves outside the intended base directory, so the worktree name field is pre-filled with a value capable of escaping the chosen parent folder.

### Impact Explanation
If the user does not notice/edit the pre-filled "Worktree Name" field and hits "Create Worktree", `git worktree add <fullPath> ...` is invoked with a path computed via `Path.join(basePath, attackerControlledRef)` that can traverse outside the intended target directory [7](#0-6) , writing repository files (a working tree checkout, including a `.git` file pointer) into an arbitrary, attacker-influenced sibling/parent directory such as `~/.ssh`. This is a real git ref name (git allows `/` freely, and this pathological ref would need to actually exist as `pullRequest.head.ref` on the fork — git does reject refs containing literal `..` as a path component per `git-check-ref-format`, which somewhat limits exploitability, but the divergence in sanitization logic between `safeDirectoryName` and the codebase's other two purpose-built sanitizers is the actual defect: the "canonical" traversal-safe helpers (`sanitizeCloneName`, ref validation with `testForInvalidChars`) exist and are used elsewhere, but this particular duplicate implementation of the same conceptual operation was never reconciled with them, so a code change to the canonical helper won't propagate here).

### Likelihood Explanation
Moderate-low: `git-check-ref-format` blocks literal `..` path components in real branch names, which constrains but does not eliminate the traversal surface (e.g. ref components using other filesystem-significant sequences, or Windows-only differences in `Path.join` normalization). The likelihood is limited primarily by git's own ref-name validation rather than by any guard inside GitHub Desktop's `safeDirectoryName()`/`RepositoryPath` code path itself — the app-level defense that protects the clone flow (`sanitizeCloneName`, `isClonePathSensitive` in `app/src/lib/git/clone.ts`) is simply absent from this worktree-naming code path.

### Recommendation
Route `safeDirectoryName()` (or the worktree "Name" field generally) through the same canonical, traversal-safe helper already used for clone destinations (`sanitizeCloneName()`) instead of maintaining a third, independently-scoped sanitizer, and reject/collapse `..`/absolute-path segments before calling `Path.join()`, consistent with the "use the canonical function, don't reimplement it" recommendation from the original report.

### Proof of Concept
1. Attacker forks a target repo and creates a branch/PR whose head ref name is a git-legal but filesystem-hazardous string (subject to `git-check-ref-format` constraints), or exploits any other flow that flows `pullRequest.head.ref`/`branch.name` into `AddWorktreeDialog`'s `initialBranchName` unsanitized.
2. Victim opens "Checkout PR in new worktree" from `branch-dropdown.tsx`'s `onCheckoutPRInNewWorktree`, which pre-fills the worktree name from `pullRequest.head.ref` [5](#0-4) .
3. `RepositoryPath.getFullPath()` computes `Path.join(basePath, safeDirectoryName(name))` without traversal filtering [4](#0-3) .
4. Victim clicks "Create Worktree"; `addWorktree()` runs `git worktree add <fullPath> ...` [7](#0-6) , writing outside the intended directory if the resolved path escapes it.

Note: I was not able to fully verify within this session whether `git-check-ref-format` (invoked implicitly by git when the PR branch was created) would successfully reject every traversal-relevant ref string before it ever reaches Desktop — this affects the practical likelihood and would need confirmation with a live PoC against real git ref validation rules.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

export async function addWorktree(
  repository: Repository,
  path: string,
  options: {
    /** Branch name used with -b (create new branch) */
    readonly createBranch?: string
    /** Commit-ish to check out (branch name, ref, or SHA) */
    readonly commitish?: string
  } = {}
): Promise<void> {
  const args = ['worktree', 'add']

  if (options.createBranch) {
    args.push('-b', options.createBranch)
  }

  args.push(path)

  if (options.commitish) {
    args.push(options.commitish)
  }

  await git(args, repository.path, 'addWorktree')
}
