### Title
Payout OP_RETURN operator xonly-pk is unsigned, letting the withdrawing user self-attribute a payout to any operator - ([File: core/src/verifier.rs])

### Summary
`Verifier::update_finalized_payouts` attributes a Citrea withdrawal's payout to whichever xonly pubkey happens to appear in the first OP_RETURN output of *any* transaction that spends the tracked `withdrawal_utxo` — with no signature or membership check binding that pubkey to the entity that actually funded the payout. Because the `withdrawal_utxo`'s spending key belongs to the withdrawing user (the attacker) rather than to any operator, the attacker can self-broadcast a payout-shaped transaction that pays themselves and stamps an arbitrary (real, honest) operator's xonly pubkey into the OP_RETURN, causing that operator to be falsely credited as payer and later reimbursed from the deposit's move-to-vault UTXO for a payout it never made.

### Finding Description
The claimed binding is:
`operator_xonly_pk recorded in DB for withdrawal idx == xonly_pk of the party that funded payout_tx`

Trace:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) writes the fronting operator's key into the payout tx's OP_RETURN via `op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()))`, and this operator key comes from `self.signer.xonly_public_key` inside `Operator::withdraw` (`core/src/operator.rs:620-626`) — i.e. legitimately it can only be the calling operator's own key. **However**, this construction path is only exercised when an operator itself services the withdrawal through its own RPC.
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) does not care which code path produced the confirmed transaction. It simply takes whatever txid `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) returns — a pure SQL join on `bitcoin_syncer_spent_utxos` keyed by `(withdrawal_utxo_txid, withdrawal_utxo_vout)` — reads its first OP_RETURN via `get_first_op_return_output`/`parse_op_return_data`, and writes whatever 32 bytes are found there into `payout_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`). No signature over the OP_RETURN, no check that the OP_RETURN key corresponds to whoever actually supplied the funding inputs of the transaction.
- The `withdrawal_utxo` tracked for a Citrea withdrawal index is populated from the Citrea bridge contract's `withdrawalUTXOs` mapping (`core/src/citrea.rs:458-496`), i.e. it is the L1 UTXO the *withdrawing user* nominates and controls the private key for (as evidenced by `Operator::withdraw` verifying the *user's* Schnorr signature over this input with `SIGHASH_SINGLE|ANYONECANPAY`, `core/src/operator.rs:614-637`). The user, not any operator, owns the key that can spend this UTXO.
- Because the private key of `withdrawal_utxo` belongs to the attacker, the attacker can construct and broadcast their *own* transaction spending this UTXO (adding whatever extra inputs/outputs they like since `SIGHASH_SINGLE|ANYONECANPAY` only commits the signature to input index 0 and the same-index output), with an OP_RETURN output containing any operator's real, public xonly pubkey. No operator RPC, no operator funds, and no operator signature are involved in producing this transaction.
- Once this transaction confirms and finalizes, `update_finalized_payouts` will faithfully record `payout_payer_operator_xonly_pk = <victim operator pubkey>` for that withdrawal index.
- The victim operator's own automated `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and will pick up this spoofed record as its own unhandled payout, then call `handle_finalized_payout`, which proceeds to `end_round` and drives the honest operator into the kickoff/reimbursement flow for a payout it never made.
- The later cross-check `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) only compares `operator_xonly_pk` from the DB (the attacker-spoofed value) against `kickoff_data.operator_xonly_pk` (the same victim operator's own key, since it is the victim who legitimately issues the kickoff believing it fronted the payout) — these match by construction, so this guard does not catch the fraud. It also checks the committed payout blockhash, which is honest chain data and thus also matches.

No existing guard (`is_kickoff_malicious`, `is_profitable`, `SECP.verify_schnorr`, storage-proof checks) verifies that the entity named in the OP_RETURN is the entity whose wallet actually supplied the payout's value-bearing inputs; `Operator::withdraw`'s `is_profitable` check is bypassed entirely because the attacker never calls that RPC.

### Impact Explanation
The victim operator ends up completing a kickoff and reimbursement cycle (`create_reimburse_txhandler`, spending the move-to-vault UTXO of the deposit) for a withdrawal it never funded — this is explicitly listed as a Critical impact category ("an operator reimbursed for a payout it never funded"). The deposit's collateralized BTC is drained to the falsely-credited operator without a corresponding real payout ever having been made by that operator, breaking the accounting invariant between fronted payouts and reimbursements. This is repeatable for every withdrawal index and against any operator whose xonly pubkey is public (all operators' pubkeys are public/known), and requires no operator or verifier collusion, only the attacker's own withdrawal-UTXO signing key and normal Bitcoin broadcast capability.

### Likelihood Explanation
The precondition is minimal: the attacker just needs to be a normal withdrawing user (register a withdrawal on the Citrea bridge contract, own the L1 UTXO nominated as `withdrawal_utxo`) and be able to construct/broadcast an ordinary Bitcoin transaction with an OP_RETURN output — capabilities explicitly granted to the unprivileged attacker in this exercise. Cost is only normal transaction fees plus whatever amount the attacker chooses to pay themselves in output 0 (their own money). No key compromise, no majority hashrate, no operator or verifier cooperation is required, and the attack can be repeated for each withdrawal the attacker registers.

### Recommendation
Bind the OP_RETURN operator pubkey to actual proof of funding rather than trusting unsigned bytes: e.g., require the payout transaction's *additional* funding inputs to be provably controlled by (or presigned/committed to) the claimed operator, or have the operator co-sign a commitment (e.g., via a musig2/N-of-N signature or a Winternitz/other commitment scheme already used for kickoff data) that binds the operator identity to the specific `withdrawal_utxo`/payout amount pair before `update_finalized_payouts` accepts it. Alternatively, validate in `update_finalized_payouts` that the operator claimed in the OP_RETURN is one of the parties whose UTXOs were spent as additional inputs of the payout transaction (i.e., trace input ownership rather than trusting an unauthenticated OP_RETURN field).

#[tokio::test]
async fn test_op_return_spoof_diverges_from_real_funder() {
    // 1. Set up a withdrawal_utxo owned solely by an attacker-controlled keypair
    //    (simulating a Citrea-registered withdrawal UTXO).
    // 2. Construct payout_tx spending withdrawal_utxo with:
    //    - input[0]: attacker's withdrawal_utxo (signed with attacker's own key,
    //      SIGHASH_SINGLE|ANYONECANPAY)
    //    - output[0]: pays the attacker themselves
    //    - OP_RETURN output: contains an arbitrary/victim operator's real xonly pubkey
    //      (NOT the attacker's key, and the victim operator never signed or funded
    //      any input of this tx)
    // 3. Feed this into the block_cache path exercised by update_finalized_payouts
    //    (insert_spent_utxo etc. as in
    //    core/src/database/verifier.rs::update_get_payout_txs_from_citrea_withdrawal test).
    // 4. Assert:
    let stored_pk = db.get_payout_info_from_move_txid(...).await.unwrap().unwrap().0;
    assert_eq!(stored_pk, Some(victim_operator_xonly_pk)); // DB believes victim funded it
    assert_ne!(stored_pk, Some(actual_funder_xonly_pk));   // but the actual wallet that
                                                            // funded payout_tx's input was
                                                            // the attacker's, not the victim's
    // This demonstrates the binding
    //   operator_xonly_pk in DB == xonly_pk of party that funded payout_tx
    // is violated: the two diverge because nothing signs the OP_RETURN.
}
