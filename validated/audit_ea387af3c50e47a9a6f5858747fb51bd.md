### Title
Tokenfactory denom allow-list restriction is enforced only in `MsgSend`/`MsgMultiSend`, not in `BankKeeper.SendCoins`, allowing other transfer paths to bypass it — ([File: sei-cosmos/x/bank/keeper/send.go])

### Summary
The tokenfactory allow-list ("softly restricted" analog to `FULL_RESTRICTED_STAKER_ROLE`) is only checked at the `x/bank` message-server entry points for `MsgSend` and `MsgMultiSend`. The actual balance-moving primitive, `BaseSendKeeper.SendCoins`/`SendCoinsWithoutAccCreation`/`InputOutputCoins`, never calls `IsInDenomAllowList` itself. Any code path that invokes the bank keeper's `SendCoins` (or related transfer methods) directly, instead of going through the `MsgSend` handler, bypasses the allow-list restriction entirely — exactly analogous to the Ethena bug where the restriction check lived only in one entry function (`_withdraw`) and not in the lower-level state-mutating logic, letting other entry points (`approve`+`transferFrom`) bypass it.

### Finding Description
`IsInDenomAllowList` is defined on `BaseSendKeeper` and is documented as gating token-factory-denom transfers to/from an allow list [3](#0-2) . It is invoked explicitly inside the `Send` and `MultiSend` msg-server handlers before calling `SendCoins`/`InputOutputCoins`: [4](#0-3) 

However, `SendCoins` itself performs no such check — it only calls `SendCoinsWithoutAccCreation` and handles account creation: [5](#0-4) 

This means the restriction is enforced by convention at the message-handler layer rather than at the keeper layer where the actual transfer happens. Any caller with a reference to the `BankKeeper` interface that calls `SendCoins` (or `SendCoinsAndWei`, `InputOutputCoins` outside the `MsgMultiSend` handler) directly bypasses the allow-list, the same class of bug as the Ethena report where `_withdraw`/`_beforeTokenTransfer` checked `caller`/`receiver` but the true state-mutation path could be reached via a different entry (`approve` + third-party `redeem`) that skipped the restriction.

Concretely, the EVM `bank` precompile's `sendNative` method calls `p.bankKeeper.SendCoinsAndWei` directly rather than going through the msg server [6](#0-5) . While `sendNative` only moves `usei`/`wei` (not tokenfactory denoms, since it hardcodes the native bond denom split), this confirms the general pattern that precompiles and other internal callers use `bankKeeper.SendCoins*` directly, so any restricted tokenfactory denom whose flow could reach `SendCoins` outside the `MsgSend`/`MsgMultiSend` handlers (e.g. via `x/wasm` bank-send bindings, IBC transfer hooks, or future precompiles that call `SendCoins` for arbitrary denoms) would silently skip the allow-list enforcement.

### Impact Explanation
If a tokenfactory admin relies on `DenomAllowList` for legal/compliance restriction of a denom (e.g., KYC-gated token), any component that transfers that denom via the bank keeper's `SendCoins`/`InputOutputCoins` without going through `MsgSend`/`MsgMultiSend` bypasses the restriction, letting a disallowed address send or receive funds directly. This maps to "unauthorized transfer via precompile or pointer" since the restriction-bypass surface is precisely the keeper layer used by precompiles and other modules.

### Likelihood Explanation
Currently the only in-repo direct caller of `SendCoins`/`SendCoinsAndWei` reachable from unprivileged EVM users is the bank precompile's `sendNative`, which is restricted to `usei`, so today's concrete exploitability against a tokenfactory-allow-listed denom could not be confirmed within the scope of files reviewed. The risk is architectural: the enforcement point is decoupled from the actual transfer primitive, so any new or existing internal caller of `SendCoins` for a tokenfactory denom (module-to-account transfers are explicitly exempted, but any account-to-account keeper call bypasses it) has no allow-list protection, making this a latent/systemic bypass rather than an immediately reachable end-to-end unprivileged exploit that could be fully verified with the tools available.

### Recommendation
Move the `IsInDenomAllowList` check into `BaseSendKeeper.SendCoins`/`SendCoinsWithoutAccCreation` (and `InputOutputCoins`) themselves, so the restriction is enforced at the point where balances are actually moved, rather than duplicated at each message handler. Alternatively, audit every direct caller of `SendCoins`/`SendCoinsAndWei`/`InputOutputCoins` in the codebase (precompiles, `x/wasm` bindings, IBC) to ensure they replicate the allow-list check identically to `msgServer.Send`.

### Proof of Concept
Not independently reproducible with the tools available in this session — a live proof of concept would require exercising a code path that calls `BankKeeper.SendCoins` for a tokenfactory-restricted denom outside `MsgSend`/`MsgMultiSend` (e.g., via CosmWasm `BankMsg::Send` bindings or a custom precompile) and confirming the restriction is skipped; this could not be fully traced through `x/wasm`'s bank bindings within the current investigation.

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
