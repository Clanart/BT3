### Title
Direct staking-token transfers to MasterMagpie/BaseRewardPool inflate `totalStaked()` and permanently dilute reward accounting - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`BaseRewardPoolV2` computes `rewardPerTokenStored` using `totalStaked()`, which is defined as `IERC20(stakingToken).balanceOf(operator)` (the MasterMagpie contract), rather than an internally tracked sum of user deposits. Because any wallet can transfer the staking token directly to the MasterMagpie address without going through `deposit()`/`depositFor()`, an attacker can inflate this balance-based denominator, causing every subsequent `queueNewRewards`/`donateRewards` call to under-credit `rewardPerTokenStored` to legitimate stakers. The shortfall corresponds to no staker and is never claimable, permanently freezing part of every future reward distribution — the same "manipulate `balanceOf` used as an accounting denominator" root cause described in the external `convertToShares`/GVault report.

### Finding Description
`totalStaked()` in `BaseRewardPoolV2` reads the staking token's raw ERC20 balance held by the `operator` (MasterMagpie), instead of an internally maintained supply counter: [1](#0-0) 

This value is used directly as the divisor when new rewards are queued or donated: [2](#0-1) 

`donateRewards` is a fully permissionless entry point that anyone can call to trigger `_provisionReward`, and it is exactly this function whose math is diluted: [3](#0-2) 

Because `totalStaked()` is derived from `balanceOf(operator)` rather than the sum of `userInfo[...].amount` tracked in `MasterMagpie`, any unprivileged wallet can send the corresponding staking token (e.g., a WombatStaking receipt token minted 1:1 on deposit/depositLP) directly to the MasterMagpie contract address: [4](#0-3) 

This is a plain ERC20 `transfer`, bypassing MasterMagpie's `_deposit` bookkeeping (`user.amount`, `user.available`) entirely: [5](#0-4) 

As a result, `totalStaked()` in the associated `BaseRewardPoolV2` becomes larger than the true amount of tokens attributable to real stakers. Every subsequent `_provisionReward` call divides new rewards by this inflated denominator, so `rewardPerTokenStored` increases by less than it should. The "missing" portion of rewards is never distributed to any account — it corresponds to a phantom balance no user is tracked as owning — and remains permanently stuck as unclaimable tokens in the reward pool contract.

### Impact Explanation
Every reward distribution (both `queueNewRewards`, called by managers for pool-specific bonus tokens, and the permissionless `donateRewards`) after the attacker's donation is permanently diluted. This is a direct, protocol-wide, permanent freezing of a fraction of unclaimed yield for every current and future staker of the affected pool, satisfying the "permanent freezing of ... unclaimed yield" impact bar. Unlike the GVault report's DoS-on-deposit angle, here the practical, lasting consequence is loss/lock of reward funds rather than blocking deposits, but the underlying flaw (using `balanceOf` as a manipulable accounting denominator instead of an internal ledger) is identical.

### Likelihood Explanation
The attack requires only acquiring a small amount of the relevant staking token (receipt token, LP token, or similar ERC20 minted by `WombatStaking`) and sending a plain `transfer` to the `MasterMagpie` contract address — no privileged role, governance action, or oracle manipulation is needed. This can be done by any unprivileged wallet immediately after a pool is created or at any later point to degrade reward accuracy further, making likelihood high once discovered.

### Recommendation
Replace `balanceOf(operator)`-based `totalStaked()` in `BaseRewardPoolV2` with an internally tracked total-staked counter that is only updated inside `_deposit`/`_withdraw` in `MasterMagpie` (mirroring the report's recommendation to track `assetBalance` explicitly rather than relying on `balanceOf`). Ensure `MasterMagpie`'s own MGP emission accounting (`_calLpSupply`, used in `updatePool`) is similarly backed by internal state rather than raw token balances, so unsolicited direct transfers cannot influence reward-per-token math.

### Proof of Concept
1. A pool is registered in `MasterMagpie` with staking token `T` and rewarder `R` (a `BaseRewardPoolV2`).
2. Legitimate users deposit a total of 1000 `T` via `MasterMagpie.deposit`, so `userInfo[T][*].amount` sums to 1000 and `T.balanceOf(MasterMagpie) == 1000`.
3. Attacker acquires 9000 `T` tokens (e.g., by minting/buying a WombatStaking receipt token) and calls `T.transfer(MasterMagpie, 9000)` directly — no MasterMagpie function is invoked, so no `userInfo` entry is created for the attacker.
4. `R.totalStaked()` now returns `10000` (`T.balanceOf(MasterMagpie)`), even though only 1000 is attributable to real stakers [6](#0-5) .
5. A manager calls `queueNewRewards(1000e18, rewardToken)` (or anyone calls `donateRewards`). `_provisionReward` computes `rewardPerTokenStored += 1000e18 * 10**decimals / 10000` instead of dividing by `1000`, an 10x under-credit [7](#0-6) .
6. Legitimate stakers can only ever claim proportionally to the diluted `rewardPerTokenStored`; the remaining ~90% of the donated reward tokens sit in the `BaseRewardPoolV2` contract permanently unclaimable by anyone, since no account is tracked as owning the attacker's phantom 9000 `T` balance.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
