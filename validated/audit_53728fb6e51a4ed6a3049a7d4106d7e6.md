### Title
OP_RETURN data output omitted from transaction weight/vsize calculation causes systematic fee underpayment - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to CVE-2024-42259 — where a mapped-region size was computed as `min(requested, actual)` without accounting for the start offset, producing a wrong boundary — `SignableTransaction::new` computes the transaction's virtual size from only the `payments` slice, while the actual transaction's output set (`tx_outs`) additionally contains an attacker-influenced OP_RETURN data output. The size/boundary of what is being measured (the serialized transaction) is thus calculated with a component offset into the output vector omitted, so `vbytes`/`weight` underestimate the real transaction size and the required fee is undercharged.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` when `data` is present: [1](#0-0) 

However, both calls that size the transaction pass `payments` — not `tx_outs` — so the OP_RETURN output's weight is never counted: [2](#0-1) [3](#0-2) 

`calculate_weight_vbytes` builds its template transaction only from `payments` plus optional change, so a data output of up to 80 bytes (`TooMuchData` check at line 171) adds roughly `8 (value) + 1–3 (script len) + 1 (OP_RETURN) + 1 (push) + len(data)` ≈ up to ~93 non-witness bytes (~93 vbytes) that are never priced. `needed_fee = fee_per_vbyte * vbytes` is therefore short by `fee_per_vbyte * ~93` sats at maximum, and the minimum-relay-fee check at line 211 is evaluated against the same underestimated `vbytes`.

### Impact Explanation
The resulting transaction broadcasts with a lower effective feerate than `fee_per_vbyte` requested — the difference scales with the caller-supplied `data` length. When the true feerate falls below relay/mempool policy, the transaction is dropped or stalls, leaving inputs (Serai multisig funds backing user withdrawals) unconfirmed and effectively unspendable until re-signed, and `needed_fee()` reports a fee that does not correspond to the transaction actually produced. This is an incorrect size/boundary calculation in the same class as the kernel bug: a region's extent was measured without one of its constituent components.

### Likelihood Explanation
Triggering requires a plan/payment path that supplies `data` to `SignableTransaction::new` (OP_RETURN metadata); the miscalculation is deterministic whenever `data.is_some()`. Whether it causes a dropped transaction depends on margin between the requested feerate and relay minimums — at 1 sat/vb the shortfall is up to ~93 sats, enough to push a borderline transaction under policy. Impact is fund availability (stuck/underpriced TX), not theft; severity Medium.

### Recommendation
Pass the fully-constructed `tx_outs` (or a combined `payments + OP_RETURN` list) into `calculate_weight_vbytes`, or compute weight directly from the final `Transaction` after all outputs — including the data output — are pushed, so both the no-change and with-change fee computations (lines 204 and 226) price the real serialized size.

### Proof of Concept
```rust
// Conceptual: construct a SignableTransaction with an OP_RETURN payload
let data = Some(vec![0xAA; 80]); // max permitted by the TooMuchData check
let stx = SignableTransaction::new(inputs, payments, change, data.clone(), fee_per_vbyte)?;

// The real transaction contains the OP_RETURN output...
assert!(stx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));

// ...but needed_fee was computed on a template without it, so:
//   actual_vbytes(stx.transaction()) > vbytes_used_internally
//   => effective feerate = stx.fee() / actual_vbytes < fee_per_vbyte
```
Concretely, replicate `calculate_weight_vbytes` on `payments` only versus on the final `stx.transaction()`; the difference equals the OP_RETURN output's serialized size (~93 vbytes for 80 bytes of data), which `fee_per_vbyte` never pays for.
