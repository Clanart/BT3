### Title
Missing recipient binding in PedPoP blame lets an accuser convict an arbitrary participant - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2024-33118 is an arbitrary-read: an attacker-controlled parameter selects which resource is returned. The Serai analog lives in the PedPoP blame path: `Decryption::decrypt_with_proof` takes an attacker-chosen `decryptor: Participant` and an `Option<EncryptionKeyProof>`, and `blame_internal` returns `recipient` (the accused) as faulty whenever the supplied proof is `None` or fails verification — even for a well-formed message. The PoP transcript binds the sender and message but never the intended recipient, so an accuser can replay/craft any `EncryptedMessage` and select an arbitrary victim to be marked faulty, exactly like the attacker-selected file path in the original bug.

### Finding Description
`EncryptedMessage::read` accepts attacker-supplied bytes for `key`, `pop`, and `msg` (encryption.rs:171-177). The proof of possession `pop_challenge` binds `context`, `nonce`, `key`, `sender`, and `msg` — but not the decryptor/recipient (encryption.rs:302-324). In `blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609), the accuser chooses both `sender` and `recipient`; when `proof` is `None`, `decrypt_with_proof` (encryption.rs:381-396) returns `DecryptionError::InvalidProof`, and blame resolves to `recipient`. Because the accuser controls `recipient`, they name an arbitrary participant as faulty. When `proof` is `Some`, the DLEq must tie `proof.key` to `enc_keys[decryptor]`, but since `decryptor` is also attacker-chosen and the message is attacker-crafted, an accuser can always force the `InvalidProof` branch against any victim. This is reachable at the coordinator's `VerifyBlame` handler (processor/src/key_gen.rs:504-563) which calls `AdditionalBlameMachine::blame(accuser, accused, share, blame)` and fatally slashes whichever participant is returned.

### Impact Explanation
An accuser can cause an arbitrary honest participant to be reported as the faulty party (`ProcessorMessage::Blame { participant: accused }`), leading to fatal slashing of an innocent validator and aborting/framing DKG sessions. This is the "arbitrary read" analog: attacker-selected input (`recipient`/`decryptor` index plus a `None` proof) selects an arbitrary victim rather than an arbitrary file, with the blame output being the attacker-serving result.

### Likelihood Explanation
Submitting a blame/accusation requires only public DKG transcript data plus a self-consistent `EncryptedMessage` the accuser constructs (they know the per-message key, so they produce a valid `pop` under `from = accuser`). No secret knowledge of the victim's keys is needed to reach the `InvalidProof → recipient` branch. The only prerequisite is the ability to lodge a `VerifyBlame` accusation, which any DKG participant can trigger.

### Recommendation
In `decrypt_with_proof`/`blame_internal`, require a `Some(proof)` with a valid DLEq before the `recipient` can be convicted — a `None` proof on a signature-valid message should convict the accuser (`sender` side / whoever submitted), not the accused. Additionally, bind the intended recipient into `pop_challenge` (append `transcript.append_message(b"recipient", ...)` or the recipient's `enc_key`), so a message cannot be re-aimed at an arbitrary `decryptor` index.

### Proof of Concept
1. Accuser A wants to blame honest participant V.
2. A calls `Encryption::encrypt` (or hand-builds) an `EncryptedMessage` addressed to A's own `enc_key`, producing valid `key`, `pop` (with `from = A`), and ciphertext.
3. A submits `blame(sender = A, recipient = V, msg, proof = None)` to `AdditionalBlameMachine::blame` (or via `VerifyBlame` with `accuser = A`, `accused = V`).
4. `decrypt_with_proof` verifies `pop` successfully, then hits the `None` arm and returns `DecryptionError::InvalidProof`; `blame_internal` returns `recipient` = V.
5. V — who did nothing wrong — is returned as the faulty participant and slashed.
