### Title
Missing null-check on `@type` value in Any JSON parsing causes out-of-bounds pointer walk-back - ([File: upb/json/decode.c])

### Summary
The external report describes a Go RPC client (`gethclient`) crashing with a nil-pointer dereference because it read an attacker/server-controlled JSON field (`RestoredBalance`) without checking for `null` before dereferencing it — an untrusted, "should always be present" field that was blindly trusted. The transferable invariant is: **a value taken from untrusted JSON input, assumed to be structurally well-formed/present, is used to compute a pointer/offset without validating that the assumption holds**, leading to memory-unsafe access and a crash (DoS) on a public parsing path. I looked for the strongest Protobuf analog of that exact failure pattern — an untrusted JSON payload driving an unchecked pointer computation in a public parse API — and found one in upb's JSON `Any` decoder.

### Finding Description
In `upb`'s JSON decoder (used transitively by the Ruby, PHP, and core upb bindings; the same code appears verbatim in `upb/json/decode.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`, and `php/ext/google/protobuf/php-upb.c`), the function `jsondec_any` scans a JSON object for the special `"@type"` key, which can appear anywhere in the object, not necessarily first: [1](#0-0) 

```c
while (!any_m && jsondec_objnext(d)) {
    const char* start = d->ptr;
    upb_StringView name = jsondec_string(d);
    jsondec_entrysep(d);
    if (jsondec_streql(name, "@type")) {
      any_m = jsondec_typeurl(d, msg, m);
      if (pre_type_data) {
        pre_type_end = start;
        while (*pre_type_end != ',') pre_type_end--;
      }
    } else {
      if (!pre_type_data) pre_type_data = start;
      jsondec_skipval(d);
    }
}
```

When fields precede `"@type"` in the object (i.e. `pre_type_data` was set by an earlier, non-`@type` field), the code walks `pre_type_end` backwards from the current parse position looking for a `,` character to find the boundary of the buffered "pre-type" JSON fragment. This walk-back **assumes** a comma will be found before the pointer runs past the start of the buffer/input — an assumption inherited from trusting the *shape* of attacker-supplied JSON. There is no bounds check against the start of the input buffer (`d->ptr`/original buffer start) in this loop.

This mirrors the `gethclient` bug precisely: an externally supplied value (here, the byte layout of the JSON preceding `@type`) is trusted to have a particular structural property (a preceding `,`) without validating it, and the code performs a raw pointer walk (analogous to an unchecked dereference) based on that untrusted assumption.

### Impact Explanation
If an attacker crafts a JSON payload for a `google.protobuf.Any` field where the bytes immediately preceding the first occurrence of the literal `"@type"` key do not actually contain a comma delimiter reachable before the start of the buffer (which can be engineered via nested/embedded `Any` parsing, or by controlling exactly what appears before `@type` at the outer message level), `pre_type_end--` walks backward past the beginning of the allocated input buffer. This is an out-of-bounds read that can under sufficient adversarial control corrupt adjacent heap/stack memory reads and, depending on allocator layout, crash the process (`SIGSEGV`) — a Denial of Service against any consuming application that calls the public `upb_JsonDecode`/`Any`-parsing entry points (exposed via Ruby's `JSON.parse` on protobuf messages, PHP's JSON deserialization, and any upb-based binding) on untrusted input. This is directly analogous in severity/class to the reported nil-pointer dereference DoS: a crash reachable through a public parse API fed with attacker-controlled JSON.

### Likelihood Explanation
Reaching this code requires only: (1) a message containing an `Any` field, (2) JSON input for that `Any` where the `@type` key is not the first key in the object (fully attacker-controlled, since JSON key order is not required to be sorted and this "any @type-anywhere" support is explicitly designed into `jsondec_any`), and (3) crafting the preceding field content so that the backward scan does not find a `,` within the buffer before running off its start. Since the loop only starts its backward scan when `pre_type_data` is non-null (meaning at least one prior field was seen) this is a normal, reachable input shape for the parser and requires no privileged access — just a bounded JSON document sent through a supported public parse API (`upb_JsonDecode` / language bindings' `parseJson`/`decode_json` equivalents).

### Recommendation
Add an explicit bound to the backward scan in `jsondec_any`, e.g., clamp `pre_type_end` against a known lower bound (the start of `pre_type_data` or the object's opening `{`) before dereferencing/decrementing, and treat "no comma found within bounds" as a parse error rather than continuing to walk the pointer. Concretely:
```c
pre_type_end = start;
while (pre_type_end > pre_type_data && *pre_type_end != ',') pre_type_end--;
if (pre_type_end == pre_type_data) {
  jsondec_err(d, "malformed Any: could not find field delimiter before @type");
}
```
This preserves the existing legacy-nonconformant "type-anywhere" behavior while eliminating the unchecked pointer walk.

### Proof of Concept
A minimal reproduction sketch (conceptual, since I could not execute code in this environment) would be: construct a message with an `Any`-typed field, and set its JSON value to an object where a non-`@type` field appears first with content engineered so that scanning backward from the point right before the literal `@type` never encounters a `,` before crossing the start of the parser's input buffer, e.g. a JSON document where `Any`'s JSON representation begins exactly at buffer start with `{"x":1"@type":"type.googleapis.com/foo.Bar"}` — malformed enough to skip the normal comma insertion, or more realistically nested inside a larger buffer where the preceding `,` legitimately lies before the *start of the field being scanned* due to how `pre_type_data`/`start` are computed relative to `d->ptr`'s original allocation start, feeding this through `upb_JsonDecode` (or the Ruby/PHP JSON parse entry points that wrap it) and observing whether the process crashes/reads out-of-bounds under AddressSanitizer.
