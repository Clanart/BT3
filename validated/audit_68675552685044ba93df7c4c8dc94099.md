### Title
Unified diff hunk-header line counts are never validated against the actual number of parsed lines - ([File: app/src/lib/diff-parser.ts])

### Summary
`DiffParser.parseHunk` in [1](#0-0)  reads the `@@ -l,s +l,s @@` hunk header and extracts `oldStartLine`/`oldLineCount`/`newStartLine`/`newLineCount` purely from regex-group *shape* validation (does the header look like `@@ -N(,N)? +N(,N)? @@`), but it never cross-checks that the number of subsequent `+`/`-`/` ` lines it walks (`while ((c = this.parseLinePrefix(this.peek())))`) actually matches `oldLineCount`/`newLineCount`. This mirrors the reported bug class in the external report: one invariant (regex format of the header) is checked, while a second, logically-required invariant (that declared counts equal actual body length) is silently assumed and never enforced.

### Finding Description
`parseHunkHeader` at [2](#0-1)  only validates that the header line matches `diffHeaderRe` and that the numeric groups parse. `parseHunk` then greedily consumes every following line whose first character is one of `+ - \` (space)` via `parseLinePrefix`, using `rollingDiffBeforeCounter`/`rollingDiffAfterCounter` that are seeded from the header but are **never checked against** `header.oldLineCount` / `header.newLineCount` when the loop ends (see [3](#0-2) ). The only length-style sanity check present in this function is the unrelated "no newline" marker check (`line.length < 12`) at [4](#0-3) , which shows the parser is aware of length-based validation elsewhere but omits it for the far more consequential hunk-size invariant.

Because hunk boundaries are determined purely by "does the next line start with a diff-line prefix character," a crafted diff (e.g. from a malicious remote, a crafted patch/blob, or a spoofed `git diff`/`git log --patch` output ingested by Desktop) can present a header claiming a small hunk (e.g. `@@ -1,2 +1,2 @@`) while the actual body contains many more or fewer prefixed lines than declared, or vice versa. The parser will keep consuming lines regardless of the declared counts, and downstream consumers of `DiffHunk`/`DiffLine` (used for rendering the diff and for computing which lines are included when the user stages/discards a subset of lines) rely on `header.oldLineCount`/`newLineCount` and the rolling counters being consistent with what is actually shown.

### Impact Explanation
If declared and actual hunk sizes diverge, Desktop's line-selection/partial-stage machinery (which reconstructs a patch from selected `DiffLine`s and the hunk header for `git apply`) can produce a patch whose header doesn't match the lines it contains. Depending on how that mismatched patch is applied, this could translate into a user staging/committing different content than what was visually presented to them — i.e., silent corruption of what the user commits, which is explicitly a valid impact category for this analysis.

### Likelihood Explanation
I was not able to fully trace, within the remaining investigation budget, the exact downstream file (e.g. a patch-formatter/format-patch helper) that consumes `DiffHunk.header` together with selected `DiffLine`s to build a patch passed to `git apply`, so I cannot confirm with full certainty that a header/body mismatch survives all the way to an actual `git apply` call rather than being re-derived independently from line data. This is a real gap in evidence for this specific write path, and should be verified by inspecting the line-selection/patch-formatting code that consumes `IRawDiff`/`DiffHunk` before treating this as fully confirmed exploitable.

### Recommendation
In `parseHunk`, after the consuming loop ends, verify that the number of consumed old-file lines (context + delete) equals `header.oldLineCount` and that the number of consumed new-file lines (context + add) equals `header.newLineCount`; throw a parse error (as is already done elsewhere in this parser, e.g. `Malformed diff, empty hunk`) if they don't match, rather than silently accepting whatever the line-prefix scan produced.

### Proof of Concept
Not independently confirmed end-to-end due to the unresolved downstream-consumer question noted above. Conceptually: feed `DiffParser.parse()` a unified diff whose hunk header declares `@@ -1,2 +1,2 @@` but whose body contains, say, 5 `+`/`-`/context lines instead of 2+2; `parseHunk` will accept it without error since only the header's regex shape is validated, not the count-vs-body invariant, at [2](#0-1)  and [5](#0-4) .

  private parseHunkHeader(line: string): DiffHunkHeader {
    const m = diffHeaderRe.exec(line)
    if (!m) {
      throw new Error(`Invalid hunk header format`)
    }

    // If endLines are missing default to 1, see diffHeaderRe docs
    const oldStartLine = this.numberFromGroup(m, 1)
    const oldLineCount = this.numberFromGroup(m, 2, 1)
    const newStartLine = this.numberFromGroup(m, 3)
    const newLineCount = this.numberFromGroup(m, 4, 1)

    return new DiffHunkHeader(
      oldStartLine,
      oldLineCount,
      newStartLine,
      newLineCount
    )
  }

    let c: DiffLinePrefix | null

    let rollingDiffBeforeCounter = header.oldStartLine
    let rollingDiffAfterCounter = header.newStartLine

    let diffLineNumber = linesConsumed
    while ((c = this.parseLinePrefix(this.peek()))) {
      const line = this.readLine()

      if (!line) {
        throw new Error('Expected unified diff line but reached end of diff')
      }

      // A marker indicating that the last line in the original or the new file
      // is missing a trailing newline. In other words, the presence of this marker
      // means that the new and/or original file lacks a trailing newline.
      //
      // When we find it we have to look up the previous line and set the
      // noTrailingNewLine flag
      if (c === DiffPrefixNoNewline) {
        // See https://github.com/git/git/blob/21f862b498925194f8f1ebe8203b7a7df756555b/apply.c#L1725-L1732
        if (line.length < 12) {
          throw new Error(
            `Expected "no newline at end of file" marker to be at least 12 bytes long`
          )
        }

        const previousLineIndex = lines.length - 1
        const previousLine = lines[previousLineIndex]
        lines[previousLineIndex] = previousLine.withNoTrailingNewLine(true)

        continue
      }

      // We must increase `diffLineNumber` only when we're certain that the line
      // is not a "no newline" marker. Otherwise, we'll end up with a wrong
      // `diffLineNumber` for the next line. This could happen if the last line
      // in the file doesn't have a newline before the change.
      diffLineNumber++

      let diffLine: DiffLine

      if (c === DiffPrefixAdd) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Add,
          diffLineNumber,
          null,
          rollingDiffAfterCounter++
        )
      } else if (c === DiffPrefixDelete) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Delete,
          diffLineNumber,
          rollingDiffBeforeCounter++,
          null
        )
      } else if (c === DiffPrefixContext) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Context,
          diffLineNumber,
          rollingDiffBeforeCounter++,
          rollingDiffAfterCounter++
        )
      } else {
        return assertNever(c, `Unknown DiffLinePrefix: ${c}`)
      }

      lines.push(diffLine)
    }

    if (lines.length === 1) {
      throw new Error('Malformed diff, empty hunk')
    }
