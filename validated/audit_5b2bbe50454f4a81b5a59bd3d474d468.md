### Title
`ThresholdKeys::read`/`new` accept identity (zero) verification shares and an inconsistent secret share, silently corrupting `group_key` and breaking signing with a non-blameable `InternalError` - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the LensHub report — where a whitelisted zero address was accepted as a `collectModule`, was only dereferenced later, and then broke collects/mirrors while misreporting the publication type — `ThresholdKeys` accepts semantically invalid "zero" values at construction/deserialization, and only fails deep inside FROST signing, with the wrong error (`InternalError` instead of `InvalidShare` blame).

### Finding Description
`ThresholdKeys::read` deserializes `n` verification shares via `C::read_G` and passes them to `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:620-632`). `read_G` only enforces canonical encoding — for Ristretto, the identity point is a canonical, torsion-free encoding of 32 zero bytes, and `Ciphersuite` requires `PrimeGroup`, so identity is accepted (`crypto/ciphersuite/src/lib.rs:91-101`). `ThresholdKeys::new` only checks the *count* of verification shares and that indexes are `<= n`; it never rejects identity shares, and it never verifies `C::generator() * secret_share == verification_shares[i]` (`crypto/dkg/src/lib.rs:355-365`). The `group_key` is then computed as the interpolated sum over `verification_shares[1..=t]` (`crypto/dkg/src/lib.rs:376-378`), so an identity share silently contributes zero, producing a group key that does not correspond to the secret shares.

### Impact Explanation
Downstream, `view()` interpolates shares against this map (`crypto/dkg/src/lib.rs:500-507`), and `AlgorithmSignatureMachine::complete` first tries aggregate signature verification, then falls back to per-share blame via `verify_share` (`crypto/frost/src/sign.rs:465-489`). With an identity interpolated verification share, the per-share statement reduces to `R - sG == 0`, so any share satisfying `sG = R` passes blame even though it does not match the real key share — while the aggregate signature still fails. The result is the code's own "should never happen" path: `FrostError::InternalError("everyone had a valid share yet the signature was still invalid")` (`crypto/frost/src/sign.rs:491-494`). As in the Lens bug, a value that should have been rejected at whitelist/construction time propagates and then (a) breaks the primary function (signing) and (b) misreports the failure mode (an un-blameable internal error instead of participant blame), and the group key reported by `group_key()` is wrong relative to the held shares.

### Likelihood Explanation
Reachable only where `ThresholdKeys::read` consumes untrusted bytes (listed as an untrusted-input surface); an honest DKG never produces this. Impact is Medium-grade: no key recovery or forgery — a forged signature still requires knowledge of the group secret — but availability is broken without attributable blame, and a corrupted `group_key` can be reported/used consistently across honest callers of the same corrupted keys.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391), reject identity verification shares and verify `C::generator() * secret_share == verification_shares[&params.i()]` so a `ThresholdKeys` object is guaranteed self-consistent; equivalently enforce this in `ThresholdKeys::read`.

### Proof of Concept
Deserialize a `ThresholdKeys<Ristretto>` (via `ThresholdKeys::read`) where `verification_shares[k]` for some `k <= t` is the 32-byte identity encoding. `read` succeeds; `group_key()` omits that share's contribution; `view()`/`complete` then return `InternalError` rather than `InvalidShare(k)` when signing with participant `k`.
