### Title
Pointer precompile (`0x100b`) allows CW→ERC pointer registration even when the admin has disabled it via `RegisterPointerDisabled` - (File: precompiles/pointer/pointer.go)

### Summary
The `x/evm` module exposes an admin-controlled parameter, `RegisterPointerDisabled`, intended to globally disable creation of new CW→ERC pointer contracts. This restriction is enforced in the Cosmos message path (`MsgRegisterPointer`) but the equivalent EVM precompile entry points (`addCW20Pointer`, `addCW721Pointer`, `addCW1155Pointer`, `addNativePointer` on the pointer precompile at `0x100b`) never check this parameter, letting any EVM caller bypass the admin's restriction — the same bug class as Publify's guest self-registration being enforced only on the front-end and not on the actual mutation path.

### Finding Description
The `x/evm` keeper defines a chain param `RegisterPointerDisabled` that is meant to be the single on/off switch for creating new CW→ERC pointer contracts (used, e.g., during migrations or when the admin wants to freeze pointer creation): [1](#0-0) 

The Cosmos message handler `RegisterPointer` (invoked via `MsgRegisterPointer`) correctly gates on this parameter before allowing any pointer creation: [2](#0-1) 

This is confirmed by the dedicated test `TestRegisterPointerDisabled`, which asserts that `MsgRegisterPointer` fails for ERC20/ERC721/ERC1155 pointer types once `RegisterPointerDisabled` is set: [3](#0-2) 

However, the same functionality is also reachable directly from EVM transactions/contracts through the `pointer` precompile at address `0x100b`, whose `Execute` dispatcher routes `addCW20Pointer`, `addCW721Pointer`, `addCW1155Pointer`, and `addNativePointer` to their respective handlers: [4](#0-3) 

None of these precompile handlers (in the current version or in any of the many legacy precompile snapshots inspected: v552, v555, v562, v580, v606, etc.) call `GetRegisterPointerDisabled` before creating a pointer. For example, `AddCW20` directly instantiates the pointer contract and persists the mapping with no param check: [5](#0-4) 

A grep across the entire `precompiles/pointer` directory tree (current and every legacy version folder) for `RegisterPointerDisabled`/`GetRegisterPointerDisabled` returns zero matches, confirming the check exists nowhere in the precompile code path, while it is present and tested in the Cosmos `MsgRegisterPointer` path.

### Impact Explanation
When an operator sets `RegisterPointerDisabled = true` (as is done by the on-chain migration `MigrateDisableRegisterPointer`) intending to prevent any new CW↔EVM pointer contracts from being created chain-wide — for example during a migration window where pointer registration is unsafe, or to freeze the pointer registry pending a governance-controlled process — any EVM user can still call the pointer precompile directly to instantiate new CW20/CW721/CW1155/native pointer contracts and register them in the same global pointer registry that the admin intended to freeze. This is a genuine improper-access-control gap: the restriction is enforced on one code path (Cosmos msg) but not on the functionally identical EVM precompile path that reaches the exact same keeper state (`SetCW20ERC20Pointer`, etc.), mirroring the reported bug class where a restriction was only enforced in one interface layer and bypassable through another. [6](#0-5) 

### Likelihood Explanation
The pointer precompile is a standard, publicly documented precompile at a fixed address (`0x100b`) reachable by any EVM transaction sender with no special privilege, gas payment, or pointer-to-pointer restriction beyond what's already checked inside `AddCW20`/`AddCW721`/etc. (e.g., not-already-a-pointer checks). Bypassing `RegisterPointerDisabled` requires nothing more than calling `addCW20Pointer(cwAddr)` (or the CW721/CW1155/native variants) on the precompile from a normal transaction — no privileged role, contract compromise, or unusual conditions are needed.

### Recommendation
Add the same `if server.GetRegisterPointerDisabled(ctx) { return error }` guard used in `x/evm/keeper/msg_server.go`'s `RegisterPointer` to each of the pointer-precompile handlers (`AddCW20`, `AddCW721`, `AddCW1155`, `AddNative`) in `precompiles/pointer/pointer.go`, so the admin-controlled kill switch applies uniformly to both the Cosmos message and EVM precompile entry points.

### Proof of Concept
1. Chain admin/governance sets `RegisterPointerDisabled = true` via a param update or an upgrade migration such as `MigrateDisableRegisterPointer`.
2. Confirm the intended restriction works: submitting `MsgRegisterPointer` for a CW20 contract fails with `"registering CW->ERC pointers has been disabled"` (as shown by `TestRegisterPointerDisabled`).
3. From any EVM account, send a transaction calling `addCW20Pointer(cwAddr)` on the pointer precompile at `0x100b` (ABI in `precompiles/pointer/abi.json`) for an existing CW20 contract.
4. Observe the call succeeds: a new ERC20 pointer contract is deployed and `SetERC20CW20Pointer`/`SetCW20ERC20Pointer` is recorded in the pointer registry, despite `RegisterPointerDisabled == true` — demonstrating the admin's restriction is bypassed entirely via the precompile path.

func NewPrecompile(keepers putils.Keepers) (*pcommon.DynamicGasPrecompile, error) {
	newAbi := pcommon.MustGetABI(f, "abi.json")

	p := &PrecompileExecutor{
		evmKeeper:   keepers.EVMK(),

		wasmdKeeper: keepers.WasmdVK(),

		switch name {
		case AddNativePointer:
			p.AddNativePointerID = m.ID
		case AddCW20Pointer:
			p.AddCW20PointerID = m.ID
		case AddCW721Pointer:
			p.AddCW721PointerID = m.ID
		case AddCW1155Pointer:
			p.AddCW1155PointerID = m.ID
		}
	}

	return pcommon.NewDynamicGasPrecompile(newAbi, p, common.HexToAddress(PointerAddress), PrecompileName), nil
}
