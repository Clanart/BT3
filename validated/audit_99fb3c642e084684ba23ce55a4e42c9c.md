### Title
Tron `IntentGatewayV2.withdraw()` treats a low-level `.call` success as proof of transfer without checking the ERC20 return value, permanently locking escrowed funds for tokens that return `false` on failure - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary

### Finding Description
The Tron variant of `IntentGatewayV2` imports OpenZeppelin's `SafeERC20` and uses it correctly in `placeOrder`/`fillOrder` paths (`safeTransferFrom`), but in the escrow-release path `withdraw()` (and in the `SweepDust` handler inside `onAccept`) it instead performs a raw low-level call and only checks that the call did not revert, never decoding the returned boolean: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

The same unchecked pattern appears for fee redemption and for `SweepDust`: [2](#0-1) [3](#0-2) 

This is exactly the bug class from the seed report: tokens like Tether Gold (and other non-standard ERC20s) can return `false` from `transfer()` on failure instead of reverting. A raw `.call(...)` only fails (`success == false`) when the callee reverts or the call itself is malformed; if the token contract executes normally and simply returns `abi.encode(false)`, `success` is `true` and the check `if (!success) revert TransferFailed();` never fires.

Because the code does not decode/verify the boolean return data (the way `SafeERC20.safeTransfer` does), the contract believes the transfer succeeded and immediately decrements the escrow accounting: `_orders[body.commitment][token] -= amount;` and, on the finalize path, marks the order filled via `_filled[body.commitment] = beneficiary;` This happens inside `onAccept`, which is invoked by the trusted Host when a `RedeemEscrow`/`RefundEscrow` request or `SweepDust` request is delivered - i.e., through the normal, unprivileged cross-chain settlement flow, not requiring any malicious relayer/prover/admin. Compare this to the canonical `IntentsBase.sol` implementation used elsewhere in the repo, which correctly uses `SafeERC20.safeTransfer`: [4](#0-3) 

### Impact Explanation
For any token whose `transfer()`/`transferFrom()` implementation can return `false` instead of reverting on failure (e.g., paused/frozen accounts, blacklists, or non-standard ERC20s like Tether Gold-style tokens), a legitimate beneficiary's withdrawal will silently fail to deliver funds while the protocol still:
- decrements `_orders[commitment][token]`, permanently zeroing out the escrow record for that token, and
- on `finalize`, marks `_filled[commitment] = beneficiary`, closing out the order as fulfilled.

The net effect is loss/lock of escrowed user funds: the tokens remain stuck in the `IntentGatewayV2` contract balance, unassigned to any recoverable order state, while the on-chain settlement records the withdrawal/refund as complete. This matches the bounty's "stealing or loss of funds" and "false state acceptance" impact classes, since the contract accepts an incomplete/failed transfer as a successful settlement.

### Likelihood Explanation
Likelihood depends on the specific token used as an order's input/fee asset. It requires the deployment to accept a non-standard ERC20 with false-on-failure semantics as a valid order token, and requires a transfer condition to actually fail (e.g., blacklist, pause) at the exact moment of withdrawal — this is a plausible, unprivileged runtime condition rather than an attacker-controlled exploit, but it depends on token choice by the deployer/market, so is best characterized as medium likelihood, contingent on token support decisions.

### Recommendation
Use `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported via `using SafeERC20 for IERC20;` in this same file) consistently in `withdraw()`, the fee-redemption block, and the `SweepDust` handler in `onAccept`, instead of raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` with only a call-success check. This ensures both revert-on-failure and return-false-on-failure token behaviors are caught before escrow accounting is mutated.

### Proof of Concept
1. Deploy (or configure) `IntentGatewayV2` (Tron variant) with a token `T` whose `transfer(to, amount)` returns `false` (without reverting) when `to` is blacklisted or paused — mirroring Tether Gold-style behavior.
2. User places an order with `T` as an input token via `placeOrder`, escrowing `amount` into `_orders[commitment][T]` (uses `safeTransferFrom`, so deposit works fine).
3. Solver fills the order on the destination chain; the source-chain `IntentGatewayV2.onAccept` receives a `RedeemEscrow` request and calls internal `withdraw(body, false)`.
4. At the moment of withdrawal, beneficiary address happens to be blacklisted/paused on `T` (or `T`'s admin toggles this state) — `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes without reverting but returns `false`.
5. `success == true` from the low-level call perspective, so `if (!success) revert TransferFailed();` does not trigger.
6. `_orders[body.commitment][token] -= amount;` executes, zeroing the escrow record, and `_filled[body.commitment] = beneficiary;` marks the order filled — yet the beneficiary never received the `T` tokens, which remain stuck in the `IntentGatewayV2` contract with no accounting path to recover them.     function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
