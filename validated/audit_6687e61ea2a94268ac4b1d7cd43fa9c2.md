### Title
Silent Git remote hijack via unvalidated `clone_url` from GitHub API response - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
When Desktop refreshes the GitHub metadata for a tracked repository, it compares the locally configured `origin` remote against the `clone_url` returned by the GitHub API and, under certain conditions, silently rewrites the local remote to that API-provided URL. The only safety check performed is that the URL **protocol** matches (`http`/`https`/`ssh`) — the **hostname** of the new URL is never validated against the existing remote's hostname or the account's expected endpoint. A GitHub API response (or a malicious/compromised endpoint masquerading as the GitHub/GHES API, or a MITM'd API response) that returns a `clone_url` pointing at an attacker-controlled host with a matching protocol will cause Desktop to silently repoint the user's `origin` remote to that host.

### Finding Description
`repositoryWithRefreshedGitHubRepository` fetches the repository object from the API for the owner/name matched from the local remote, and if a `GitHubRepository` is already associated, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [1](#0-0) 

`updateRemoteUrl` then decides whether to overwrite the local `origin` URL with `apiRepo.clone_url`: [2](#0-1) 

The gating logic is:
- `protocolsMatch`: only compares `URL.parse(url).protocol` for the current remote vs. the new `clone_url` — i.e. `https:` === `https:`. It does **not** compare hostnames.
- `remoteUrlUnchanged`: confirms the user hasn't manually repointed `origin` away from the previously cached `gitHubRepository.cloneURL` (structural comparison via `urlMatchesRemote`, which does check hostname/owner/name — but only against the *old, cached* GitHub repository record, not the new one).
- `!urlsMatch`: the new `clone_url` differs (by hostname/owner/name) from the current remote.

If all three hold, `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` is called, directly rewriting `origin` to whatever `apiRepo.clone_url` says — with no verification that the new hostname belongs to the same GitHub/GHES endpoint the repository is associated with: [3](#0-2) 

The `apiRepo` value originates from `api.fetchRepository(owner, name)`, i.e. directly from the trust boundary of the GitHub API response for that account/endpoint: [4](#0-3) 

Any actor that can influence that HTTP response body — a compromised/malicious GHES instance the user has added as an account, a network-level MITM of the API traffic, or a compromised GitHub API response — can set `clone_url` to `https://attacker.example/x/y.git` (same scheme as the existing remote) and Desktop will accept it as the new `origin` without ever checking that the hostname is consistent with the account's endpoint or the previous remote.

### Impact Explanation
This directly matches the "silent corruption of what the user commits or pushes" impact category. Once `origin` is silently repointed:
- The next `git push` (via `app/src/lib/git/push.ts`, using `envForRemoteOperation(remote.url)` for auth/proxy resolution) sends the user's code, and potentially credentials/tokens resolved for that remote, to the attacker's host instead of the legitimate GitHub repository. [5](#0-4) 
- Subsequent fetches (`app/src/lib/git/fetch.ts`) would then pull refs/objects from the attacker's server, allowing injection of malicious commits into the user's local history under the guise of the "same" repository. [6](#0-5) 
- The change happens with no user prompt or visible diff — the user continues to believe they are pushing/pulling to/from the original GitHub repository.

### Likelihood Explanation
This path only triggers under an attacker model where the GitHub/GHES API response itself is attacker-influenced (matching the explicitly allowed "attacker controls...a GitHub API object" primitive in scope). It requires the user to already have that endpoint/account configured (e.g. a GHES instance later compromised, or a MITM position on API traffic), and it silently fires during routine background metadata refresh (`repositoryWithRefreshedGitHubRepository`, invoked e.g. on account changes) — no unusual user action is needed once the malicious API response is delivered.

### Recommendation
In `updateRemoteUrl`, validate that the new `clone_url`'s **hostname** matches the hostname of the account/endpoint associated with `gitHubRepository` (or at minimum matches the existing remote's hostname) before calling `setRemoteURL`, rather than only comparing protocol. Any hostname change should require explicit user confirmation rather than silent rewriting.

### Proof of Concept
1. Add a GitHub Enterprise Server account in Desktop and track a repository from it (or otherwise get into a state where the API endpoint returning repo metadata for `owner/name` can be influenced/MITM'd).
2. When Desktop calls `repositoryWithRefreshedGitHubRepository` (e.g., triggered by `refreshSelectedRepositoryAfterAccountChange` on sign-in/out), have the compromised/malicious API endpoint return a repository object whose `clone_url` is `https://attacker.example/owner/name.git` — same scheme (`https:`) as the user's current `origin`, but different hostname.
3. `updateRemoteUrl` computes `protocolsMatch = true`, `remoteUrlUnchanged = true` (cached GH repo still matches original remote), `urlsMatch = false` (hostname differs) → calls `gitStore.setRemoteURL('origin', 'https://attacker.example/owner/name.git')`.
4. `origin` is now silently repointed. The next push/fetch operation in the app transmits/receives data to/from `attacker.example` with no user-visible warning.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
