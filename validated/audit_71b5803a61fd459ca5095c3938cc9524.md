### Title
Shared `BalanceHandler.prevEventsLen` corrupted by recursive/nested precompile calls causes StateDB/bank balance desync - ([File: precompiles/common/balance_handler.go])

### Summary
The external "flash loan wrong balance check" bug is a `before/after` balance-diff invariant that is computed incorrectly because the "before" snapshot is captured at the wrong point relative to nested state changes, causing an inflated/incorrect delta. The direct Cosmos EVM analog is `BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` in [1](#0-0) , which records `prevEventsLen = len(ctx.EventManager().Events())` as the "before" marker and later slices `events[bh.prevEventsLen:]` as the "after" diff to translate bank `CoinSpent`/`CoinReceived` events into `StateDB.AddBalance`/`SubBalance` calls. The repository itself contains a dedicated regression test, `BalanceHandlerTestSuite`, whose doc-comment states this handler has a known bug: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB"* [2](#0-1) .

### Finding Description
Per-precompile instances (bank, distribution, erc20, gov, ics20, slashing, staking) hold a single `BalanceHandler` via `GetBalanceHandler()` rather than allocating a fresh one per call, as shown by the reference implementation in the debug precompile [3](#0-2) , where `p.GetBalanceHandler().BeforeBalanceChange(ctx)` is invoked immediately before executing the precompile method and `p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB)` afterward. `BeforeBalanceChange` just stores an event-count offset (`prevEventsLen`) on the shared handler instance [4](#0-3) .

When a contract makes a nested/recursive call into the same stateful precompile (e.g., precompile A calls out to a contract that calls back into precompile A, or a caller contract triggers multiple sequential precompile invocations that share the same precompile object), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` on the shared handler. When the inner call finishes and its `AfterBalanceChange` runs, it correctly slices from the inner offset. But when control returns to the *outer* call and its own `AfterBalanceChange` executes, `prevEventsLen` has already been mutated by the inner call, so the outer call's event slice window is wrong — it can double count events already applied by the inner call, or skip events, corrupting the delta computed between the "before" and "after" markers. This is structurally identical to the flash-loan bug pattern: a shared/reused "before" reference point that gets invalidated by an intervening state change, producing a wrong sum/diff used to drive balance mutation (`stateDB.AddBalance`/`SubBalance`) [5](#0-4) .

Because `AddBalance`/`SubBalance` calls made from `AfterBalanceChange` write directly to `StateDB` balances that are independent of the underlying bank-keeper multi-store changes made by the precompile's native action (which are separately snapshotted/reverted via `precompileCallChange`/`AddPrecompileFn` in the journal [6](#0-5) ), a miscomputed event window means the EVM-visible balance (`StateDB`) diverges from the actual bank-module balance for the same account. This divergence is exactly the class of "accounting corruption between EVM balances and native balances" called out in the required-impact gate.

### Impact Explanation
If `prevEventsLen` is corrupted by nested/recursive precompile calls, an attacker-crafted contract can arrange precompile call sequences (e.g., calling a precompile like `bank`, `erc20`, `distribution`, or `ics20` recursively or interleaved through intermediate contract calls) such that the outer call's `AfterBalanceChange` either:
- re-applies bank events already consumed by the inner call, double-crediting `StateDB` balance for an account beyond what was actually moved in the bank keeper (state duplication of spendable value), or
- skips events that should have updated `StateDB`, leaving EVM balance out of sync with the bank balance (freezing/loss of usable value from the EVM's perspective, or the inverse — an unearned balance increase usable to pass subsequent `balanceOf`/`transfer` checks in the EVM).

Either direction breaks the 1:1 accounting invariant between native bank balances and EVM-visible balances that the repo's own required-impact gate treats as Critical (unauthorized duplication/corruption of spendable value across native and EVM balances). The repository's own `NestedEVMExtensionCallSuite`/`test_flash_loan_exploit.go` tests explicitly exercise this "flash loan exploit" pattern of nested EVM extension (precompile) calls plus intervening reverts [7](#0-6) , underscoring that this call shape (nested precompile + external contract call) is a recognized attack surface in this codebase.

### Likelihood Explanation
Likelihood is High for triggering the code path (unprivileged users can freely deploy contracts that call precompiles recursively/sequentially — no privileged setup required), but I could not fully verify from the available index whether every stateful precompile's `GetBalanceHandler()` returns a genuinely shared/singleton handler across nested calls versus a fresh one is allocated per top-level `Run`/`RunNativeAction` invocation. The `runNativeAction` path in `precompiles/common/precompile.go` creates a **new** `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()` [8](#0-7) , which would NOT exhibit this bug — only the `debug` precompile's `Run` method uses `p.GetBalanceHandler()` (a field on the precompile struct, reused across calls) [9](#0-8) . Since the debug precompile is explicitly a test/demo precompile and the regression test (`TestRecursivePrecompileCallsWithDebugPrecompile`) only exercises it against the debug precompile [10](#0-9) , I could not confirm from the index that production precompiles (bank, erc20, staking, distribution, gov, slashing, ics20) actually share a persistent `BalanceHandler` instance across nested/recursive calls in the same way, versus using the factory pattern that allocates fresh handlers per call. This determines whether the bug is reachable in production precompiles or is confined to the test-only `debug` precompile.

### Recommendation
Confirm whether any production (non-test) precompile holds a persistent `BalanceHandler` via `GetBalanceHandler()` rather than obtaining a fresh instance per call through `BalanceHandlerFactory.NewBalanceHandler()`. If so, either (a) always allocate a new `BalanceHandler` per precompile invocation (matching the `runNativeAction` pattern) so `prevEventsLen` cannot be clobbered by nested calls, or (b) make `BeforeBalanceChange`/`AfterBalanceChange` stack-based (push/pop event-window boundaries) instead of storing a single scalar offset, so nested calls cannot corrupt an outer call's window.

### Proof of Concept
The repository already contains a reproduction: `BalanceHandlerTestSuite.TestRecursivePrecompileCallsWithDebugPrecompile` deploys a caller contract that recursively invokes the debug precompile (`callback(0)`) and asserts on the resulting event/balance counts [11](#0-10) . I was unable to fully verify — due to index/tool-call limits — whether this reproduction path is confined to the test-only `debug` precompile or is also reachable through any shipped production precompile; a Devin session with full repository access (to trace `GetBalanceHandler()` call sites in `precompiles/bank`, `precompiles/erc20`, `precompiles/staking`, `precompiles/distribution`, `precompiles/gov`, `precompiles/slashing`, `precompiles/ics20`) would be needed to confirm production reachability before treating this as a confirmed Critical finding rather than a test-only artifact.

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

func (p Precompile) Run(evm *vm.EVM, contract *vm.Contract, readonly bool) ([]byte, error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.Wrap(errors2.ErrUnauthorized, "could not create statedb in debug precompile")
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	err = stateDB.AddPrecompileFn(p.Address(), snapshot, events)
	if err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	// Start the balance change handler before executing the precompile.
	p.GetBalanceHandler().BeforeBalanceChange(ctx)

	initialGas := ctx.GasMeter().GasConsumed()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)
	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	// This handles any out of gas errors that may occur during the execution of a precompile tx or query.
	// It avoids panics and returns the out of gas error so the EVM can continue gracefully.
	defer cmn.HandleGasError(ctx, contract, initialGas, &err)()

	res, err := p.Execute(ctx, stateDB, contract, readonly)
	if err != nil {
		return nil, err
	}

	if err != nil {
		return nil, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	// Process the native balance changes after the method execution.
	if err := p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB); err != nil {
		return nil, err
	}

	return res, nil
}

// AddPrecompileFn adds a precompileCall journal entry
// with a snapshot of the multi-store and events previous
// to the precompile call.
func (s *StateDB) AddPrecompileFn(snapshot int, events sdk.Events) error {
	s.journal.append(precompileCallChange{
		snapshot: snapshot,
		events:   events,
	})
	s.precompileCallsCounter++
	if s.precompileCallsCounter > types.MaxPrecompileCalls {
		return fmt.Errorf("max calls to precompiles (%d) reached", types.MaxPrecompileCalls)
	}
	return nil
}
