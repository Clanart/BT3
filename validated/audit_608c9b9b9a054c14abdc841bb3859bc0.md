Based on the evidence gathered, here is the strongest locally-provable analog to the reported PDA-constraint bug.

### Title
Missing-instance fallback in `instance()`/`authenticate()` lets an attacker forge a trusted `IntentGateway` sender identity for unregistered chains, enabling unauthorized `RedeemEscrow`/`RefundEscrow` withdrawals - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirrored pattern in `evm/src/apps/intentsv2/IntentsBase.sol` / `ExtrinsicIntents.sol`)

### Summary
The original report's core broken invariant is: *an account/identity that is supposed to be constraint-checked (PDA derivation) is instead accepted implicitly/by default, so an attacker-supplied account can pass as legitimate.* The direct Hyperbridge analog is `IntentGatewayV2.instance()` / `authenticate()`, which is supposed to enforce that an incoming cross-chain settlement message (`RedeemEscrow`/`RefundEscrow`) truly originates from the registered `IntentGateway` instance on the source chain. Instead of failing closed when no instance is registered for a given `stateMachineId`, it **falls back to `address(this)`**, silently trusting any sender that happens to match the local gateway's own address.

### Finding Description
`instance()` resolves the expected sender module for a given source `stateMachineId`: [1](#0-0) 

```
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

`authenticate()` is invoked in `onAccept()` for `RedeemEscrow`/`RefundEscrow`, which then calls `withdraw()` to release escrowed funds: [2](#0-1) 

For state machines that have never been explicitly registered via `NewDeployment` (`_instances[keccak256(stateMachineId)] == 0`), `instance()` returns `address(this)` instead of reverting or requiring an explicit allow-list entry. This means `authenticate()` will accept a `PostRequest` whose `request.from` equals the gateway's own address on this chain, coming from *any* `request.source` that has no registered mapping. Because ISMP's `PostRequest.from` is populated by the dispatching contract on the source chain (attacker-controlled, not the destination host), an attacker can:

1. Choose (or spin up, e.g., on an EVM-compatible chain) a state machine ID that Hyperbridge governance has not yet registered an `IntentGateway` instance for.
2. Deploy any contract at the same address as this destination gateway's address on that source chain (achievable via deterministic `CREATE2`/matching nonce+deployer, a standard technique, not a "malicious relayer/prover" precondition — it's purely local contract deployment by the attacker).
3. From that contract, dispatch a `PostRequest` with `to = <destination IntentGateway>`, `from = <that same address>`, and a `body` encoding `RequestKind.RedeemEscrow` / `RefundEscrow` with an arbitrary existing `commitment`, arbitrary `tokens`, and `beneficiary = attacker`.
4. Once relayed with a valid state/consensus proof for that (unregistered but real) chain, `onAccept()` → `authenticate()` passes because `instance(request.source) == address(this) == module`, and `withdraw()` transfers the escrowed tokens for that commitment straight to the attacker.

This is the exact structural analog of the audit's PDA finding: a value that should be strictly derived/verified against an expected, whitelisted identity (`redemption_offer`/`redemption_request` PDA there; the registered gateway `instance` here) is instead accepted via an implicit default, letting a wrong (attacker-controlled) account satisfy the check. `withdraw()` performs no further verification that the escrow's `commitment` was ever meant to be settled from that particular source chain — it only checks `_orders[commitment][token] != 0`: [3](#0-2) 

### Impact Explanation
This allows unauthorized transaction/execution and outright theft of escrowed bridge funds: an unregistered/attacker-reachable chain path is treated as an authenticated `IntentGateway` peer, letting an attacker redeem or redirect another user's escrowed order inputs to a beneficiary of their choosing (`RedeemEscrow`/`RefundEscrow` both call the same `withdraw()` with attacker-supplied `beneficiary`). This is a direct fund-loss / wrong-beneficiary bridge-custody violation matching the bounty's "stealing or loss of funds" and "false proof/state acceptance" categories, since the attacker effectively forges the identity that state-proof verification is meant to bind.

### Likelihood Explanation
The path is reachable by any unprivileged actor able to deploy a contract on a source chain and get a valid message relayed with correct state proofs (permissionless relaying is by design in ISMP) — no malicious relayer, prover, or governance actor is required, only that at least one state machine remains without an explicitly registered `_instances` entry, which is the default/expected state for any newly supported or not-yet-configured chain. Achieving an identical contract address across chains via deterministic deployment (`CREATE2`, same deployer nonce, factory patterns) is a well-known, low-effort technique, making this practically exploitable rather than theoretical.

### Recommendation
Change `instance()` to fail closed: if `_instances[keccak256(stateMachineId)] == 0`, `authenticate()` must revert (e.g., `revert UnknownInstance()`), rather than defaulting to `address(this)`. Only the chain this contract is itself deployed on (matched via `request.source == host().host()`, if that self-referential case is ever legitimate) should be allowed to bypass the explicit instance mapping, and that should be an explicit, intentional check rather than an implicit fallback for *every* unregistered chain. Apply the same fail-closed audit to the equivalent `_instance()`/`_authenticate()` logic in `evm/src/apps/intentsv2/IntentsBase.sol` and `ExtrinsicIntents.sol` used by the non-Tron `IntentGatewayV2`.

### Proof of Concept
1. On any source state machine not present in destination `_instances` mapping, deploy `Attacker` contract at address `X` such that `X == <destinationGatewayAddress>` (via `CREATE2` with a chosen salt/deployer replicated across chains).
2. From `Attacker`, call the source-chain ISMP host's `dispatch()` with a `PostRequest{ from: X, to: destinationGatewayBytes, source: sourceChainId, dest: destChainId, body: abi.encodePacked(RequestKind.RedeemEscrow, abi.encode(WithdrawalRequest{commitment: knownVictimCommitment, tokens: victimInputs, beneficiary: attackerAddress})) }`.
3. Have a (permissionless) relayer submit this request with a valid state proof for `sourceChainId` to the destination `HandlerV2`.
4. `IntentGatewayV2.onAccept()` → `authenticate(request)` computes `instance(sourceChainId)`; since unregistered, returns `address(this)` == `X` == `request.from`, so the check passes.
5. `withdraw()` executes, transferring the victim's escrowed tokens for `knownVictimCommitment` to `attackerAddress`.

Note: I was unable to fully re-confirm whether the primary (non-Tron) `IntentsBase.sol` `_instance()` implementation contains the identical `address(this)` fallback, since a follow-up `read_file` call failed due to a missing parameter and no further tool iterations were available; this should be verified directly in a full session, but `ExtrinsicIntents.sol`'s `_authenticate()`/`_instance()` calling pattern mirrors the vulnerable Tron contract exactly, indicating the same class of bug is very likely present there as well.
