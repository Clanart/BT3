## Analysis

The Cork bug's core pattern: an amount is escrowed under one accounting bucket, but a later "release" path operates on a *different* (larger) amount than what was actually recorded, so the accounting either underflows or leaves value permanently unreachable. I found a direct structural analog in the Tron variant of `IntentGatewayV2`.

### Title
Same-chain order cancellation always reverts and permanently locks escrowed principal when a protocol fee is configured — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`placeOrder` escrows the **fee-reduced** input amount (`reducedInputs[i].amount = originalAmount - protocolFee`) into `_orders[commitment][token]`, while the full, pre-fee `order.inputs[i].amount` remains part of the contract's token balance (the fee portion is only *emitted* as `DustCollected`, not separately accounted). When a same-chain order is cancelled, `cancelOrder` builds the refund request using the **original, unreduced** `order.inputs`, not the reduced escrow amount, and passes it to `withdraw()`, which decrements `_orders[commitment][token]` by that unreduced amount — permanently reverting whenever a protocol fee applies.

### Finding Description
In `placeOrder`, the escrow bookkeeping uses the fee-adjusted amount: [1](#0-0) [2](#0-1) 

Note `_orders[commitment][token] += reducedInputs[i].amount;` — this is strictly less than `order.inputs[i].amount` whenever `protocolFeeBps > 0`.

In `cancelOrder`'s same-chain branch, however, the withdrawal request is built directly from the **original** `order.inputs`, not from the actual escrowed (reduced) amount: [3](#0-2) 

`withdraw()` then attempts to transfer that unreduced amount and subtract it from the smaller escrowed balance: [4](#0-3) 

`amount = body.tokens[i].amount` is the full pre-fee amount; `_orders[body.commitment][token]` only ever held the reduced amount. The line `_orders[body.commitment][token] -= amount;` underflows under Solidity `^0.8.24`'s default checked arithmetic (it is outside the `unchecked { ++i; }` block), causing the whole transaction — including the token/ETH transfer that preceded it in the same call frame — to revert.

The guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` only checks for a non-zero escrow, not for sufficiency against `amount`, so it does not prevent this path from being reached.

### Impact Explanation
Whenever `_params.protocolFeeBps` (or a destination-specific override) is non-zero, **every same-chain `cancelOrder` call reverts unconditionally**. This is the direct analog of the Cork `Pa` value that is "stored... but never dealt with again": the user's escrowed principal is deposited under the reduced-amount accounting, but the only cancellation code path assumes the unreduced amount, so the release path can never succeed. Since no other function decrements `_orders[commitment][token]` for a same-chain order except a solver's `fillOrder`/`withdraw` on a full/partial fill, a user who places an order with a nonzero protocol fee and finds no solver willing to fill it has **no way to ever recover their escrowed tokens** — the funds are permanently locked in the contract, exactly matching the "stuck and never redeemed" impact class from the seed report.

### Likelihood Explanation
This is trivially triggerable by any ordinary user: place a same-chain order while `protocolFeeBps > 0` (a normal governance-configured, non-zero value is the expected production configuration for fee-generating routes), then call `cancelOrder`. No relayer, prover, or privileged actor is required — it is a pure function of governance-configured fee parameters and standard user actions on public entrypoints.

### Recommendation
In the same-chain `cancelOrder` branch, build the `WithdrawalRequest.tokens` list from the actual escrowed balances (`_orders[commitment][token]`), matching the pattern used by the main EVM `IntentsBase._cancelSameChain`, instead of `order.inputs`. Additionally, harden `withdraw()` to validate `amount <= _orders[body.commitment][token]` before transferring, and to update state before performing the external transfer (checks-effects-interactions) to avoid combining an underflow-revert with an already-executed external call.

### Proof of Concept
1. Governance sets `_params.protocolFeeBps = 100` (1%).
2. User calls `placeOrder` with `order.inputs = [{token: USDC, amount: 1000e6}]`, `order.destination = order.source` (same-chain). `reducedInputs[0].amount = 990e6` is credited to `_orders[commitment][USDC]`; `1000e6` USDC total sits in the contract balance (990e6 escrow + 10e6 fee dust).
3. No solver fills the order.
4. User calls `cancelOrder(order, options)`. `cancelOrder` builds `body.tokens = order.inputs = [{USDC, 1000e6}]` and calls `withdraw(body, true)`.
5. `withdraw()` transfers `1000e6` USDC to the user, then executes `_orders[commitment][USDC] -= 1000e6` where `_orders[commitment][USDC] == 990e6` — this underflows and reverts under Solidity 0.8 checked arithmetic, rolling back the whole transaction.
6. Every subsequent `cancelOrder` call for this commitment reverts identically; the user's `990e6` USDC (plus the `10e6` fee) remains locked in the contract indefinitely with no path to recovery.
