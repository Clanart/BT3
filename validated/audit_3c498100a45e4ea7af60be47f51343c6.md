### Title
Attacker-controlled deposits to reserved internal offsets are misclassified as internal `Branch`/`Change`/`Forwarded` outputs - (File: processor/src/networks/bitcoin.rs)

### Summary
CVE-2020-12103's bug class is "an attacker-controlled locator lets an operation create objects outside its intended scope, in the same flat namespace." In Serai's Bitcoin processor, the flat namespace is the `Scanner`'s `scripts` map keyed by `script_pubkey`, and the reserved "directories" are the deterministic offsets `Branch`, `Change`, and `Forwarded` registered for every monitored key. `Bitcoin::get_outputs` classifies every scanned output purely by which registered offset its script maps to, with no check that non-`External` outputs were actually created by the protocol. An external party can compute these reserved scripts and pay to them, causing the processor to emit internally-classified outputs it never created.

### Finding Description
`Scanner::register_offset` deterministically maps `key + G*offset` to a P2TR script and stores it in `self.scripts`. `scan_transaction` then matches on `output.script_pubkey` alone, returning the stored offset for any matching output regardless of who created the containing transaction (`networks/bitcoin/src/wallet/mod.rs:180-213`).

The processor registers three reserved offsets with a public, deterministic derivation (`Secp256k1::hash_to_F(KEY_DST, b"branch"|"change"|"forward")`) and builds a `kinds` map from offset-repr to `OutputType` (`processor/src/networks/bitcoin.rs:308-347`).

In `get_outputs`, each scanned output's kind is assigned solely via `kinds[offset_repr]` (`processor/src/networks/bitcoin.rs:686-700`). Only `External` outputs are validated against the transaction's `InInstruction` data and origin (`processor/src/networks/bitcoin.rs:730-736`); `Branch`, `Change`, and `Forwarded` outputs are accepted with empty `data` and a `presumed_origin` cloned from `tx.input[0]`'s spent output — an attacker-chosen value.

Because `BRANCH_OFFSET`/`CHANGE_OFFSET`/`FORWARD_OFFSET` are derived from a public DST and the group key is public, any unprivileged party can compute `p2tr_script_buf(key + G*offset)` for the reserved offsets and broadcast a transaction paying to them. The processor will report these as `Output { kind: OutputType::Branch | Change | Forwarded, ... }`, indistinguishable from outputs the wallet itself produced.

This mirrors the CVE exactly: attacker-supplied input reaches a flat namespace and creates an object (here, an internal-type `Output`) outside the intended scope (protocol-generated transactions), because no provenance/scope check exists for the internal classifications.

### Impact Explanation
Internally-typed outputs carry protocol meaning. `Branch` outputs signal key-rotation branches and `Change` outputs are treated as the wallet's own change; downstream schedulers consume `outputs` from `ScannerEvent::Block` and build `Plan`s around their `kind`. An attacker can:

- Inject fabricated `Branch` outputs, making the processor believe a rotation/branch output exists that it never created, corrupting scheduling decisions.
- Inject `Change`/`Forwarded` outputs that are booked as internal movements rather than external deposits — the attached `data` (which only `External` outputs get) is dropped, so any associated `InInstruction` semantics are silently lost while `presumed_origin` is attacker-controlled.

While the funds remain technically spendable under the same offset key, the processor's accounting and plan construction treat them as internally-originated, enabling balance misattribution and disruption of multisig rotation flows — reachable entirely from an unmined attacker transaction.

### Likelihood Explanation
Reachability is high: computing the reserved scripts requires only the public group key and the hardcoded `KEY_DST`/labels; paying to them costs a standard Bitcoin transaction. Exploitation impact depends on how schedulers consume misclassified outputs, and there is a documented expectation that internal outputs originate from the wallet — hence Medium rather than High.

### Recommendation
For non-`External` outputs, verify provenance before classification: e.g., require that `Change`/`Forwarded` outputs appear in transactions spending inputs owned by the same key (check `tx.input` prevouts resolve to scanner-owned outpoints), or bind internal classifications to outputs the wallet itself constructed (record expected change/branch outpoints when signing). Alternatively, include the `OutputType` expectation in the registration so externally-originated transactions paying to reserved scripts are either rejected or downgraded to `External` with their `data`/origin populated accordingly.

### Proof of Concept
```rust
// Attacker knows the public group key `key` and the public DST.
let branch_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch");
let mut branch = branch_offset;
// reproduce register_offset's increment-until-even behavior
while !is_even(key + ProjectivePoint::GENERATOR * branch) { branch += Scalar::ONE; }
let script = p2tr_script_buf(key + ProjectivePoint::GENERATOR * branch).unwrap();

// Attacker broadcasts a tx paying `script`.
// In Bitcoin::get_outputs, scanner.scan_transaction returns offset == branch,
// so `kinds[branch_repr]` yields OutputType::Branch and the output is emitted as:
//   Output { kind: Branch, presumed_origin: <attacker-chosen input[0] origin>,
//            output: <attacker tx output>, data: [] }
// — identical in shape to a protocol-created branch output.
```
