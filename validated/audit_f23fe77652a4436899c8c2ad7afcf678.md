### Title
Missing HTML-unsafe character escaping (`<`, `>`) in upb's native JSON encoder allows unescaped script-delimiter sequences in ProtoJSON output - ([File: upb/json/encode.c])

### Summary
The CVE-2021-32608 report describes a stored-XSS class defect: a Razor view (`_ForumPost.cshtml`) renders user-controlled forum-post text without calling `HtmlUtils.SanitizeHtml`, so an attacker-controlled string reaches an HTML sink unescaped. The transferable invariant is: *"a string value that is fully attacker-controlled and will later be rendered/consumed in an HTML/JS context must have HTML/JS-significant characters (`<`, `>`, etc.) neutralized before it leaves the trusted component."* Protobuf's JSON serializers implement exactly this invariant as a deliberate, documented hardening measure — but the native `upb` JSON encoder used by the PHP, Ruby, and Python (upb-backend) bindings omits it, while every other language implementation (C++, Java, C#) implements it consistently.

### Finding Description
Protobuf's `ProtoJSON` string-encoding routines intentionally escape `<` and `>` (and in some cases `&`, `=`, `'`) even though the JSON spec does not require it, explicitly to prevent a JSON payload from being unsafely interpreted if later embedded in an HTML/`<script>` context by a consuming application:

- C++ `JsonWriter::WriteEscapedUtf8` explicitly escapes `<` and `>` as part of `kUnsafeChars`/`MustEscape`, with the comment "help to prevent security bugs in JavaScript." [1](#0-0) [2](#0-1) 
- Java `JsonFormat.printStringEscapedAndQuoted` explicitly escapes `<`, `>`, `&`, `=`, `'` "to prevent XSS risks," with a regression test (`testHtmlEscape`, for b/73832901) asserting `</script>` is rendered as `\u003c/script\u003e`. [3](#0-2) [4](#0-3) 
- C# `JsonFormatter.WriteString` likewise escapes `<`/`>` "required for HTML security." [5](#0-4) 
- The C++ `JsonFormat` behavior is covered by `JsonTest.HtmlEscape`, confirming `</script>` → `\u003c/script\u003e` is the expected, tested contract across bindings that use this path. [6](#0-5) 

In contrast, the native `upb` C JSON encoder — the backend used by PHP (`php-upb.c`), Ruby (`ruby-upb.c`), and the upb-based Python C extension — implements string escaping in `jsonenc_put_escaped_char`, but its default branch only escapes ASCII control characters (`< 0x20`) and passes all other bytes (including `<`, 0x3C, and `>`, 0x3E) straight through unescaped: [7](#0-6) 

This means a message with `string_value = "</script><script>alert(1)</script>"` serialized via `MessageToJson` on the upb backend emits the raw `<`/`>` characters verbatim, whereas the same message serialized via the C++/Java/C# backends emits `\u003c`/`\u003e`. The identical PHP wire-format encoder path also does not apply this escaping at the byte level. [8](#0-7) 

### Impact Explanation
This is a real behavioral inconsistency between Protobuf's own JSON-encoder implementations, and it removes a documented defense-in-depth hardening that other backends provide. However, it does **not** independently transfer the CVE's impact. Protobuf itself has no HTML-rendering sink; the escaping in `JsonFormat`/`JsonWriter`/`JsonFormatter` is explicitly a best-practice mitigation for consuming applications that might naively embed ProtoJSON output into HTML/`<script>` contexts without doing their own context-aware output encoding — it is not a substitute for that encoding, and the JSON is still syntactically valid and semantically identical whether or not `<`/`>` are escaped (per the code comment: "consumers should never do any manual unescape to round trip the intended value"). A consuming application that correctly HTML/JS-encodes output before embedding remains unaffected regardless of which Protobuf backend it uses. This is best classified as an **engineering inconsistency / missing hardening** in `upb`'s encoder rather than a confirmed, directly exploitable vulnerability in Protobuf itself, since exploitation still requires a downstream consumer to skip its own output encoding — the same precondition needed for the original CVE, but one layer further removed.

### Likelihood Explanation
Reachability is straightforward: any attacker-controlled string field, serialized to ProtoJSON via a PHP/Ruby/upb-Python binding and later reflected into an HTML/JS context by an application that relies on Protobuf's escaping (rather than its own), would be exposed. This requires a specific, non-default consuming-application behavior (skipping proper contextual encoding while trusting ProtoJSON's incidental escaping), which is speculative and not verified in this repository — no consuming application code is in scope.

### Recommendation
Align `upb`'s `jsonenc_put_escaped_char` (and the amalgamated `php-upb.c`/`ruby-upb.c` copies) with the C++/Java/C# JSON writers by escaping `<` and `>` (and ideally the same extended set: `&`, `=`, `'`, and the Unicode ranges already handled in `src/google/protobuf/json/internal/writer.cc`), so behavior is consistent across all officially supported Protobuf language bindings.

### Proof of Concept
Source-level comparison (no execution available in this environment):
- upb encoder: `jsonenc_put_escaped_char('<')` falls to the `default` branch, `(uint8_t)'<' == 0x3C` is not `< 0x20`, so it is written raw via `jsonenc_putbytes`. [9](#0-8) 
- C++ encoder: `MustEscape('<', ...)` returns `true` via the explicit `case '<':` branch, and `WriteEscapedUtf8` emits the `\u003c` escape instead. [10](#0-9) 
- Confirmed expected/tested output for the C++/Java code paths is `\u003c/script\u003e` for input `</script>`. [6](#0-5) 

No test exists in this checkout exercising `upb/json/encode.c`'s `</script>` behavior to confirm the discrepancy at the binding level (PHP/Ruby/upb-Python); this is a source-level argument, not an executed reproduction.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}
