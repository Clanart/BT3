### Title
Reward-per-token is credited in a lump-sum jump on `harvest()`, allowing an unprivileged attacker to sandwich `WombatStaking.harvest()` and steal freshly-harvested WOM/bonus rewards from long-term stakers - ([File: rewards/BaseRewardPoolV2.sol], [File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.harvest()` is a fully permissionless, unprivileged-callable function that pulls WOM/bonus rewards from the external Wombat protocol and injects them into `BaseRewardPool`/`BaseRewardPoolV2` via `queueNewRewards()`, which immediately bumps `rewardPerTokenStored` in one discrete step based on `totalStaked()` at that instant. [1](#0-0) [2](#0-1) [3](#0-2)  This is the same root-cause pattern as the reported `Oracle.updateExchangeRate()` sandwich in `afiVault`: a value used to compute a user's share of pooled value jumps discretely in a single transaction, and deposits/withdrawals around that transaction have no cooldown, so anyone watching the mempool can capture value that should accrue only to stakers who were present for the whole earning period.

### Finding Description
`MasterMagpie.deposit`/`withdraw` (reachable by any wallet, or via `WombatPoolHelper.deposit`/`withdraw`) have no minimum holding period, and `_deposit`/`_withdraw` immediately harvest whatever `rewardPerTokenStored` currently is. [4](#0-3)  `BaseRewardPoolV2._provisionReward` (invoked by the permissionless `harvest()` -> `_toMasterWomAndSendReward` -> `_sendRewards` -> `queueNewRewards` chain) computes:

```
rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked();
``` [3](#0-2) 

This means the entire freshly harvested reward for a whole epoch is divided by *whatever* `totalStaked()` happens to be at the exact block the harvest lands, rather than by time-weighted stake. Since `harvest(address _lpToken)` in `WombatStaking.sol` can be called by anyone (only gated by `whenNotPaused` and `_onlyActivePool`, not by role) [1](#0-0) , an attacker can watch the mempool (or simply call `harvest()` themselves right after depositing) and:
1. Front-run/deposit a large stake into the pool via `MasterMagpie.deposit`/`WombatPoolHelper.deposit` right before `harvest()` executes.
2. Let `harvest()` execute, injecting the full accumulated WOM/bonus reward and instantly increasing `rewardPerTokenStored` proportional to the now-inflated `totalStaked()`.
3. Immediately call `getReward`/`multiclaim` to claim their share of `rewardPerTokenStored`, then `withdraw` in the same or next block—no cooldown blocks this.

This dilutes/steals rewards that should have accrued to users who were staked for the entire period between harvests, exactly analogous to Alice's sandwich of `Oracle.updateExchangeRate()` in the report.

### Impact Explanation
This is a direct theft of unclaimed yield from genuine stakers: value that should be distributed pro-rata over the elapsed staking period is instead captured almost entirely by an attacker who stakes for a single block around the `harvest()` call, permanently diluting `rewardPerTokenStored` gains available to long-term LPs. This matches the "theft or permanent freezing of unclaimed yield" acceptance criterion.

### Likelihood Explanation
`harvest()` is unauthenticated and can be triggered by anyone at will (also auto-triggered on every deposit/withdraw via `_toMasterWomAndSendReward`), and `MasterMagpie` deposit/withdraw have no cooldown or minimum holding time, so the attack is executable purely by an ordinary wallet with capital, without needing to compromise any privileged role.

### Recommendation
- Stream harvested rewards linearly over time (e.g., a `rewardRate`/`periodFinish` model like Synthetix `StakingRewards`) instead of crediting the entire harvested amount to `rewardPerTokenStored` in one atomic step based on instantaneous `totalStaked()`.
- Alternatively/additionally, enforce a minimum staking duration before a user's deposit is eligible to earn from a newly queued reward batch, or block reward-token claims from within the same block as a deposit.
- Consider disallowing deposit and withdrawal (or deposit and reward claim) in the same block/transaction as `harvest()`/`queueNewRewards()` for the same pool.

### Proof of Concept
1. Suppose pool has 100 staked tokens and 0 pending rewards; `WombatStaking.harvest(lpToken)` is about to be called (visible in mempool or callable by anyone at any time) and will bring in 1,000 WOM in rewards.
2. Attacker calls `MasterMagpie.deposit(stakingToken, 900)` (or via `WombatPoolHelper.deposit`), bringing `totalStaked()` to 1,000. [5](#0-4) 
3. `harvest()` executes: `_provisionReward` computes `rewardPerTokenStored += 1000e18 / 1000 = 1e18` (per-token units), i.e., 1 WOM per staked token, credited across the current `totalStaked()` of 1,000. [6](#0-5) 
4. Attacker immediately calls `getReward`/`multiclaim`/`withdraw`, claiming 900 WOM (90% of the harvested reward) despite having staked for effectively zero time, while the original 100 long-term stakers only receive 100 WOM combined instead of the full 1,000. [7](#0-6)

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
