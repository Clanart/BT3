I'll examine the Bitcoin `SignableTransaction` fee calculation — the "pending additions not reflected in the base measurement" is a plausible analog there.### Title
SignableTransaction underpays fees by excluding the OP_RETURN data output from the weight/vbytes calculation - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check using `calculate_weight_vbytes`, which builds a mock transaction containing only `payments` (and optionally `change`). The OP_RETURN output carrying `data` (up to 80 bytes) is pushed to `tx_outs` but is never included in the weight estimate. This mirrors the reported bug class: a component added to the object before its "settlement" (the data output minted into the TX, like protocol fees minted into totalSupply) is missing from the denominator used for pricing, so the paid fee is systematically less than the requested `fee_per_vbyte` whenever `data` is present.

### Finding Description
In `SignableTransaction::new` (send.rs:150), the fee-relevant size is computed at line 204:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

and, when change is considered, at line 226:

```rust
let (weight_with_change, vbytes_with_change) =
    Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
```

Inside `calculate_weight_vbytes` (send.rs:62-127), the mock `Transaction` only contains `payments` and the optional `change` output — its `output` vector never receives the OP_RETURN output. Yet in `new`, the `data` output is pushed onto `tx_outs` at lines 194-202 *before* the weight is measured, and becomes part of the real transaction returned by `complete` (send.rs:417-427).

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` undercounts actual vsize by the serialized size of the OP_RETURN output (~9 + data_len bytes, up to ~90 bytes ≈ 90 vbytes with `data` capped at 80 bytes).
- The `TooLowFee` minimum-relay check at line 211 is evaluated against this underestimated `vbytes`, so it can pass while the *effective* fee rate (`needed_fee / actual_vsize`) falls below `DEFAULT_MIN_RELAY_TX_FEE`.
- The `TooLargeTransaction` check at line 241 uses `weight`, which likewise omits the data output's weight.

The data output is attacker/unprivileged-user reachable: `data` flows from Bitcoin transactions carrying Serai InInstructions (`extract_serai_data` in processor/src/networks/bitcoin.rs) into the outputs the validator set later spends, and into `SignableTransaction::new(..., data, fee_per_vbyte)`.

### Impact Explanation
Any Bitcoin transaction Serai constructs that includes an InInstruction OP_RETURN pays a strictly lower fee rate than requested — proportionally worse for small transactions where ~90 vbytes is a large fraction of total size. The produced (validly threshold-signed) transaction can be below the mempool's minimum relay fee and never propagate or confirm, stalling the corresponding out-instruction indefinitely even though `SignableTransaction::new` returned `Ok`. This is a concrete denial-of-spendability of funds the system believes it is moving, reachable purely from public on-chain input (an 80-byte InInstruction payload).

### Likelihood Explanation
Triggered whenever `data.is_some()` in `SignableTransaction::new`, i.e., every Bitcoin out-flow carrying an InInstruction payload. No special timing or privileged position is needed — any user who embeds the maximum-sized data payload maximizes the discrepancy between the estimated and true virtual size.

### Recommendation
Include the OP_RETURN output in the size estimate: pass the fully-formed `tx_outs` (or append a `TxOut` with `ScriptBuf::new_op_return(...)` of the correct length) to `calculate_weight_vbytes` before computing `vbytes`/`weight`, both in the no-change and with-change calls, so `needed_fee`, the `TooLowFee` check, and the `TooLargeTransaction` check reflect the final transaction.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs context
// In SignableTransaction::new:

// 1. OP_RETURN output is added to the real outputs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

// 2. But the fee estimate is built ONLY from `payments` (+ optional change)
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
// `calculate_weight_vbytes` constructs `output` from `payments`/`change` only;
// the `data` output's bytes are never measured.

// 3. Effective fee rate = needed_fee / actual_vsize < fee_per_vbyte,
//    and the min-relay check uses the underestimated `vbytes`:
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;   // can pass while actual fee rate is too low
}
```
A transaction built with `data = vec![0; 80]` and `fee_per_vbyte` at the minimum relay boundary produces a signed transaction whose real vsize exceeds `vbytes` by ~90 bytes, yielding an effective fee rate below the relay minimum — the signed TX is valid yet non-relayable.
