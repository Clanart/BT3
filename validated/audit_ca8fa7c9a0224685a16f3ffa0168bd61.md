Based on my investigation, I found a concrete analog to the STON.fi confused-deputy bug class within GitHub Desktop's pull-request/fork handling code.

### Title
Attacker-controlled fork clone URL from GitHub API is passed unvalidated into `git remote add`, allowing an `ext::`/local-path transport to be registered and later fetched by Desktop - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_findPullRequestBranch` in `app-store.ts` [1](#0-0)  takes `headCloneUrl` straight from a pull request's `head.repo.clone_url` — a value that originates from the GitHub API and is fully controlled by whoever owns the fork that opened the PR (an unprivileged, unauthenticated-relative-to-victim attacker) — and passes it directly to `addRemote`, which shells out to `git remote add name url` with no protocol allow-list [2](#0-1) . Immediately after, Desktop calls `_fetchRemote` → `fetch()` on that exact remote [3](#0-2) [4](#0-3) .

### Finding Description
This mirrors the STON.fi report's broken invariant: a value that is supposed to represent a validated, benign identifier (there: the LP-account owner address; here: a repository clone URL) is instead attacker-supplied data coming through a "trusted-looking" channel (there: a `pay_to` message from the pool contract; here: a PR object served by the GitHub API for a fork PR) and is used directly to drive a privileged operation (there: minting LP tokens against someone else's balance; here: registering and fetching an arbitrary git transport in the victim's local repository).

Git supports remote helper transports beyond `http(s)`/`ssh`, notably `ext::<command>`, which spawns `<command>` as a subprocess to service the fetch, and local filesystem paths, which can be used to reach files/objects outside the intended remote. `remote-parsing.ts`'s `remoteRegexes` only recognizes `https`/`ssh`-shaped URLs for the purpose of *matching/parsing* known GitHub hosts [5](#0-4) , but this classification is not used as a gate before `addRemote`/`fetch` are invoked in `_findPullRequestBranch` — there is no check that `headCloneUrl` starts with `https://` or `git@`/`ssh://` before it reaches `git remote add` and `git fetch`. Contrast this with `checkout.ts`, which explicitly threads an `allowFileProtocol` flag through submodule handling [6](#0-5) , showing the project is aware that non-standard git protocols/paths are a risk surface elsewhere, but that same discipline is absent for PR-fork clone URLs.

### Impact Explanation
If Desktop actually fetches a crafted `ext::sh -c '...'`-style (or similar transport-helper) URL taken from a forked PR's `head.repo.clone_url`, `git fetch` would execute the attacker's command locally on the victim's machine merely because the victim opened/viewed a pull request from that fork in Desktop — i.e., "code execution triggered by an attacker-controlled GitHub API object," matching the accepted impact categories in the task (code execution via a GitHub API object).

### Likelihood Explanation
The `clone_url` field of `head.repo` in the GitHub API pull request payload is fully attacker-controlled if GitHub itself permits registering repositories whose reported clone URL can be manipulated (e.g., via API responses for non-standard/self-hosted or crafted repository metadata), and Desktop's call path performs no protocol/scheme validation before use. However, I could not fully verify within the indexed code whether GitHub's REST API server-side sanitizes `clone_url` to always be `https://github.com/...` for repositories it hosts (which would make the field effectively trusted and this path unreachable in practice for github.com, though potentially reachable for GitHub Enterprise instances with different validation). This uncertainty affects whether the untrusted input can realistically contain `ext::` or a local path, and I was not able to resolve it with the available tools — a background agent with the actual GitHub API contract for `clone_url` should verify this before treating the finding as fully exploitable.

### Recommendation
Before calling `addRemote`/`fetch` in `_findPullRequestBranch` (and any other place that ingests `head.repo.clone_url`/similar fields from PR API objects), validate that the URL's scheme is restricted to `https:`, `http:`, `ssh:`, or `git:` (reusing/extending the existing `remoteRegexes` validation in `remote-parsing.ts`), and reject anything else (in particular `ext::`, `fd::`, or bare filesystem paths) rather than passing the raw string through to `git remote add`/`git fetch`.

### Proof of Concept
Conceptual PoC (unverified end-to-end due to the API-contract uncertainty noted above):
1. Attacker forks a target repository and opens a pull request whose `head.repo.clone_url` (as returned by the API/consumed by Desktop) is set to a transport string such as `ext::sh -c "touch /tmp/pwned"` instead of a normal `https://` URL.
2. Victim, using GitHub Desktop, opens or interacts with that pull request (e.g., via "Open PR from Desktop" deep link or the PR list), triggering `_findPullRequestBranch` with `headCloneUrl` set to the attacker's string.
3. `addRemote(repository, forkRemoteName, headCloneUrl)` registers the malicious remote unchanged [2](#0-1) .
4. `_fetchRemote` invokes `fetch(repository, remote, ...)`, which runs `git fetch <remote-name>` [7](#0-6) ; git resolves the `ext::` helper for that remote and executes the attacker's command on the victim's machine.

export async function fetch(
  repository: Repository,
  remote: IRemote,
  progressCallback?: (progress: IFetchProgress) => void,
  isBackgroundTask = false
): Promise<void> {
  let opts: IGitStringExecutionOptions = {
    successExitCodes: new Set([0]),
    env: await envForRemoteOperation(remote.url),
  }

  if (progressCallback) {
    const title = `Fetching ${remote.name}`
    const kind = 'fetch'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true, isBackgroundTask },
      new FetchProgressParser(),
      progress => {
        // In addition to progress output from the remote end and from
        // git itself, the stderr output from pull contains information
        // about ref updates. We don't need to bring those into the progress
        // stream so we'll just punt on anything we don't know about for now.
        if (progress.kind === 'context') {
          if (!progress.text.startsWith('remote: Counting objects')) {
            return
          }
        }

        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({
          kind,
          title,
          description,
          value,
          remote: remote.name,
        })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0, remote: remote.name })
  }

  const args = await getFetchArgs(remote.name, progressCallback)

  await git(args, repository.path, 'fetch', opts)
