## Analysis

I traced the WETH/ETH “stale total-balance instead of delta” bug class to a real, directly comparable defect in Hyperbridge's own Tron deployment of the Intent Gateway. The canonical EVM contract already contains the fix pattern; the Tron variant of the *same* contract was never updated to match it, and — more importantly — also dropped the reentrancy guard that the canonical version relies on to make that accounting safe.

### Title
Missing reentrancy guard + un-snapshotted dispatcher balance accounting in `placeOrder` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM `IntentGatewayV2.sol::placeOrder` snapshots gateway balances immediately before sweeping the dispatcher (`balancesBefore[i]`) and derives the actually-received amount as a **delta** (`balance_after - balance_before`), then updates `order.inputs[i].amount` and the escrow/commitment from that delta [1](#0-0) . The Tron fork of the identical function computes escrow credit from the pre-computed `reducedInputs[i].amount` (locked in *before* the predispatch swap even runs) and reads the dispatcher's **absolute total balance** rather than a delta to decide how much is “dust” [2](#0-1) . Critically, the Tron `placeOrder` is also missing the `nonReentrant` modifier that the canonical version carries [3](#0-2)  versus [4](#0-3) .

### Finding Description
`placeOrder` computes `commitment` from `reducedInputs` (fee-adjusted, attacker-declared `order.inputs[i].amount`) *before* executing the attacker-supplied `order.predispatch.call` through the shared, singleton `CallDispatcher` at `_params.dispatcher` [5](#0-4) . That dispatch is an arbitrary external call executed on the attacker's behalf, with no reentrancy lock protecting the function. Inside that call, an attacker can reenter `placeOrder` (or `cancelOrder`/`fillOrder` if the shared dispatcher/host allow it), interleaving another order's escrow bookkeeping with the current one before `_orders[commitment][token] += reducedInputs[i].amount` for the original call has committed [6](#0-5) .

Compounding this, the escrow credit for the *current* order is decoupled from what is actually transferred out of the dispatcher: `balance = IERC20(token).balanceOf(dispatcher)` reads the dispatcher's total current balance (not a before/after delta), and the *entire* balance is swept to the gateway while only the fixed `reducedInputs[i].amount` is recorded as this order's escrow debt [7](#0-6) . Because `dispatcher` is a shared singleton used by every order's predispatch/postdispatch calls, any balance left in it by a reentrant, concurrently-in-flight, or interrupted call is silently absorbed into whichever `placeOrder` invocation happens to read it next — exactly the same “ambient balance corrupts a per-call accounting check” root cause as the ParticleExchange ETH/WETH bug, except here it is compounded by the absence of a reentrancy guard, escalating it from a false-revert DoS into a state-corruption/fund-accounting primitive.

### Impact Explanation
An attacker who controls `order.predispatch.call` (fully attacker-supplied calldata, per the contract's own design intent for “swap-then-escrow” patterns) can use the dispatch call as a reentrancy point into a function with no lock, while critical escrow (`_orders[commitment][token]`) and nonce (`_nonce++`) state for the outer call is still uncommitted or in an inconsistent intermediate state. Combined with the balance-not-delta dust computation, this allows manipulation of which tokens get credited to which order's escrow commitment, enabling incorrect escrow accounting, dust misattribution, or duplicate/interleaved order bookkeeping — a direct violation of the “bridged assets and order escrow must move exactly once and only to the rightful beneficiary and amount” invariant.

### Likelihood Explanation
This requires no privileged actor: any unprivileged user can call `placeOrder` with a predispatch call and a target `Order`, since the `predispatch.call`/`predispatch.assets` fields are fully user-controlled by design (documented as supporting arbitrary DeFi composition, e.g., Uniswap swaps) . The only missing guard is the `nonReentrant` modifier already present on the sibling EVM contract, so this is a straightforward regression rather than a theoretical construct — it's directly diffable against the patched canonical implementation in the same repository.

### Recommendation
Add `nonReentrant` to `placeOrder` (and any other externally-callable function that dispatches attacker-controlled calldata through the shared `CallDispatcher`) in `evm/tron/contracts/apps/IntentGatewayV2.sol`, and port the before/after balance-delta accounting from the canonical `evm/src/apps/IntentGatewayV2.sol::placeOrder` so that escrow credit and dust are derived from actual balance movement rather than an absolute dispatcher balance snapshot taken after an arbitrary reentrant-capable call.

### Proof of Concept
1. Attacker crafts an `Order` whose `predispatch.call` is a `Call[]` that re-enters `IntentGatewayV2.placeOrder` (or another state-mutating entry point reachable via the shared dispatcher/host) mid-execution of the outer `placeOrder` call, before the outer call's `_orders[commitment][token] += reducedInputs[i].amount` line executes [8](#0-7) .
2. Because `placeOrder` lacks `nonReentrant`, the reentrant call succeeds and mutates shared state (`_nonce`, dispatcher token balances) while the outer call's escrow bookkeeping is still pending.
3. The outer call resumes, reads `IERC20(token).balanceOf(dispatcher)` — now reflecting balances influenced by the reentrant call rather than only the outer call's own predispatch swap — and sweeps that entire balance to the gateway while crediting only the pre-computed `reducedInputs[i].amount` to `_orders[commitment][token]`, corrupting the relationship between physically-held gateway funds and per-order escrow liabilities [7](#0-6) .
