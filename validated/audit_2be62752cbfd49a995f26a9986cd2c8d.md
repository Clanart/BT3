### Title
Symlink-based arbitrary file disclosure via image-diff rendering (`getWorkingDirectoryImage` does not use the repository's path-containment guard) - (File: `app/src/lib/git/diff.ts`)

### Summary
The reported Vader bug is a "broken invariant" class issue: a value (the exchange-rate scaling factor) is computed without applying the safety transformation (`10 ** decimals`) that every other similar computation in the codebase applies, silently producing a corrupted result that downstream code trusts. Looking for the same *broken-invariant* pattern in GitHub Desktop — a place where a security-relevant path value is used *without* the containment/symlink guard that parallel code paths in the same codebase already apply — leads to `getWorkingDirectoryImage` in `app/src/lib/git/diff.ts`.

### Finding Description
GitHub Desktop has a dedicated, well-tested path-containment primitive, `resolveWithin()` in `app/src/lib/path.ts`, which resolves symlinks and rejects any path that escapes a given root directory. It is deliberately used in security-sensitive spots such as `buildConflictContext` and `openRepositoryFromUrl`: [1](#0-0) [2](#0-1) 

However, `getWorkingDirectoryImage`, which is called whenever the UI renders an image diff for a working-directory file, resolves the file path with a plain `Path.join` and reads it directly, with no call to `resolveWithin` and no symlink check: [3](#0-2) 

This function is invoked from `getImageDiff` for any working-directory file that is not deleted or conflicted, based purely on the file's extension being recognized as an image type: [4](#0-3) 

Git tracks symlinks as blobs whose content is the link target string; when checked out, the OS creates a real symlink on disk. If a cloned/fetched repository contains (or a crafted commit introduces) a symlink such as `logo.png -> ../../../../.ssh/id_rsa` (or any path outside the repository, including sensitive files like SSH keys, browser cookie stores, etc.), and that entry appears as a new/modified/untracked "image" file in the Changes list, `getWorkingDirectoryImage` will follow the symlink via `readFile(Path.join(repository.path, file.path))`, read the *target* file's bytes, base64-encode them, and hand them to the renderer as a `data:` URI to display "the image."

Unlike `resolveWithin`, which explicitly resolves symlinks and verifies the final real path is still inside root (and has a dedicated test for exactly this attack: "fails for paths that use a symlink to traverse outside of the root" in `app/test/unit/path-test.ts`), the image-diff path never performs this check.

### Impact Explanation
This lets an attacker who controls a cloned/fetched repository (or a branch/commit an unsuspecting user checks out or whose diff they merely view) exfiltrate the contents of arbitrary files readable by the user's OS account — SSH private keys, cloud credential files, other repositories' contents, etc. — into the Desktop renderer process. Content displayed as a data URI is present in the DOM/renderer memory and can be inspected (e.g., via DevTools, or extracted through any additional renderer-side primitive), constituting file read outside the repository and potential credential exfiltration purely from viewing a diff of a malicious repository — no local/physical access, admin rights, or prior compromise needed, satisfying the "attacker controls a cloned/fetched repository" impact criterion.

### Likelihood Explanation
The attack requires only that a victim clone/fetch a repository containing a symlinked "image" file and open the Changes/History view to preview that file — an ordinary, expected user action in Desktop, not an "unnatural" step. The codebase's own test suite proves the team is aware that symlink-based root escape is a real risk for the `resolveWithin` helper, but that guard simply was not applied to this particular file-reading code path, making the gap a straightforward oversight rather than a defense-in-depth omission.

### Recommendation
Route `getWorkingDirectoryImage` (and any other direct `fs.readFile`/`Path.join` access to working-directory file paths derived from git status, e.g. `getLargeFilePaths`) through `resolveWithin(repository.path, file.path)` before reading, refusing to render/read when the resolved path is `null` (outside the repository) — mirroring the pattern already used in `buildConflictContext` and `openRepositoryFromUrl`.

### Proof of Concept
1. Create a malicious repository containing a symlink entry named e.g. `cute.png` pointing to `../../../../../../.ssh/id_rsa` (or, on the victim's machine, to any absolute/relative path outside the repo that the OS symlink permits).
2. Have the victim clone this repository, or add it as a remote and fetch/checkout a branch containing this file, with the git config allowing symlinks (default in most setups).
3. In GitHub Desktop, open the repository and view the Changes tab; select the `cute.png` entry, which is treated as an untracked/new "image" file.
4. `getImageDiff` → `getWorkingDirectoryImage` (`app/src/lib/git/diff.ts` lines 926-937) resolves `Path.join(repository.path, 'cute.png')`, and Node's `fs.readFile` follows the OS-level symlink, reading the target file (e.g., `id_rsa`) instead of an image.
5. The bytes are base64-encoded and returned as an `Image`, rendered into the diff view as a `data:` URI — the private key content is now present in the renderer's DOM, retrievable via DevTools or any script with renderer access.

Note: I was unable to execute this end-to-end in a live Desktop instance to confirm exact UI rendering behavior (e.g., whether malformed "image" data throws before completing the read, or whether git's `core.symlinks`/checkout settings on the victim's platform would block symlink creation on Windows by default). This should be validated experimentally by a Devin session with terminal access; the code-level absence of the `resolveWithin` guard on this specific path, however, is confirmed directly from the source.

/**
 * Retrieve the binary contents of a blob from the working directory
 *
 * Returns an image object containing the base64 encoded string,
 * as <img> tags support the data URI scheme instead of
 * needing to reference a file:// URI
 *
 * https://en.wikipedia.org/wiki/Data_URI_scheme
 */
export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}
