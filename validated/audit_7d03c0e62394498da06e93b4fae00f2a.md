Based on my research, I found a valid analog. The VC (Verified Credential) revocation mechanism mirrors the `StakingModule.slash` front-running pattern: a privileged provider (holding the associated DID) is meant to be able to revoke a user's VC via the backdoor, but the VC coin remains freely spendable by its holder at any time (transfer, proof update, or self-revoke), so the holder can consume the coin before the provider's revocation spend confirms, invalidating it.

### Title
Users can front-run VC (Verified Credential) provider revocation by spending the VC coin first - ([File: chia/wallet/vc_wallet/vc_wallet.py], [File: chia/wallet/vc_wallet/vc_drivers.py])

### Summary
`VCWallet.revoke_vc` lets a provider's DID revoke a user's Verified Credential (VC) by spending the VC's singleton coin through the `activate_backdoor` "hidden puzzle" path [1](#0-0) . The VC coin, however, is a normal singleton coin fully controllable by its holder via `VCWallet.generate_signed_transaction`, which supports transferring the VC, updating its proof hash, or self-revoking it at will [2](#0-1) . Because there is no on-chain lock preventing the VC holder from spending the coin, the holder can observe a pending provider-issued revoke transaction in the mempool and submit a competing spend of the same VC coin, causing the provider's revoke spend to be rejected as a double-spend once the holder's spend confirms first — exactly analogous to a staking user calling `fullClaimAndExit` to front-run `StakingModule.slash`.

### Finding Description
The VC's puzzle stack curries a `REVOCATION_LAYER` ("backdoor") beneath the singleton/EML layers, giving the `proof_provider` DID the ability to spend the coin through `activate_backdoor()` and effectively revoke the credential [3](#0-2) . The revocation is implemented purely as an alternative valid spend path on the *same* coin, not as a state that freezes the coin against holder-initiated spends [4](#0-3) .

`VCWallet.revoke_vc` fetches the current on-chain VC coin state, builds the DID-authorized backdoor spend, and pushes it as an "extra spend" alongside a DID message spend [5](#0-4) . Meanwhile, the holder's own `generate_signed_transaction` path (used for normal transfers, proof updates, or `self_revoke`) can spend the identical coin at any time with no cooldown, timelock, or "pending revocation" gating [6](#0-5) . Since Chia's mempool/consensus model resolves conflicting spends of the same coin by first-confirmed-wins, a VC holder who becomes aware that a provider intends to revoke (or who simply front-runs proactively, since it costs them nothing to always beat a slow provider transaction) can submit their own spend of the VC coin with a higher fee to ensure it confirms first, permanently invalidating the provider's pending revocation transaction.

This mirrors the `StakingModule.slash` issue: a privileged party (SLASHER_ROLE / VC provider) has an authorized penalizing/administrative action against a user's asset, but the user retains unrestricted, un-timelocked ability to spend/exit that asset, allowing preemptive front-running that permanently defeats the authority's action.

### Impact Explanation
A VC's entire security model (used to gate CR-CAT participation, KYC/whitelisting, etc.) depends on providers being able to revoke a credential when a condition changes (e.g., a user is removed from an approved list). If a malicious or simply attentive VC holder can always front-run revocation, the provider's revocation right is effectively unenforceable on-chain, undermining the trust guarantees CR-CATs and other VC-gated flows rely on. This is a medium-severity design/logic issue rather than a direct fund-theft bug, since it affects the enforceability of an authorization mechanism rather than causing unauthorized coin movement directly.

### Likelihood Explanation
Any user who is the target of revocation is economically motivated to front-run it, and doing so requires no special access — only monitoring the mempool/network for the provider's revoke transaction (or preemptively racing it) and submitting a normal, unprivileged spend of their own VC coin with sufficient fee priority. This is trivially executable by any wallet user holding a VC.

### Recommendation
Introduce a mechanism to prevent the VC holder from unilaterally spending the credential once revocation is initiated, or restructure revocation to not depend on winning a spend race — for example, by giving the provider's backdoor spend guaranteed precedence (e.g., via an announcement/assertion the holder's normal spend path must also satisfy), or by requiring a relative-timelock "notice period" during which only the provider can spend the coin, analogous to how pool-leaving enforces a `relative_lock_height` before self-pooling can resume (see `chia/pools/pool_wallet.py`).

### Proof of Concept
1. Provider DID mints a VC to a user via `vc_mint`.
2. Provider observes the need to revoke and calls `client.vc_revoke(...)`, which builds a spend using `VerifiedCredential.activate_backdoor()` [7](#0-6)  and broadcasts it.
3. Before the provider's transaction confirms, the user (or an automated bot watching the mempool for provider-initiated spends of their VC coin) submits their own transaction via `generate_signed_transaction` (e.g., a proof update or `self_revoke`) spending the same VC coin, with a higher fee.
4. The user's transaction confirms first; the provider's revoke transaction is rejected by the mempool as a double-spend of an already-spent coin, and the VC remains valid/under the user's control despite the provider's intended revocation.

def create_revocation_layer(hidden_puzzle_hash: bytes32, inner_puzzle_hash: bytes32) -> Program:
    return REVOCATION_LAYER.curry(
        REVOCATION_LAYER_HASH,
        hidden_puzzle_hash,
        inner_puzzle_hash,
    )


def match_revocation_layer(uncurried_puzzle: UnknownPuzzle) -> tuple[bytes32, bytes32] | None:
    if uncurried_puzzle.mod == REVOCATION_LAYER and uncurried_puzzle.curried_args is not None:
        return (
            bytes32(uncurried_puzzle.curried_args[1].as_atom()),
            bytes32(uncurried_puzzle.curried_args[2].as_atom()),
        )
    else:
        return None  # pragma: no cover


def solve_revocation_layer(puzzle_reveal: Program, inner_solution: Program, hidden: bool = False) -> Program:
    solution: Program = Program.to(
        [
            hidden,
            puzzle_reveal,
            inner_solution,
        ]
    )
    return solution

    def activate_backdoor(
        self, provider_innerpuzhash: bytes32, announcement_nonce: bytes32 | None = None
    ) -> tuple[CreatePuzzleAnnouncement, CoinSpend]:
        """
        Activates the backdoor in the VC to revoke the credentials and remove the provider's DID.

        Returns the announcement we expect from the provider's DID authorizing this, and the spend of the VC.
        Sync attempts by this class on spends generated by this method are expected to fail. This could be improved in
        the future with a separate type/state of VC that is revoked, but perfectly useful as a singleton.
        """
        vc_solution: Program = solution_for_singleton(
            self.singleton_lineage_proof,
            uint64(self.coin.amount),
            Program.to(
                [  # solve EML
                    solve_revocation_layer(
                        self.hidden_puzzle(),
                        solve_std_vc_backdoor(
                            self.launcher_id,
                            Program.to((self.proof_provider, self.proof_hash)).get_tree_hash(),
                            self.construct_transfer_program().get_tree_hash(),
                            self.inner_puzzle_hash,
                            uint64(self.coin.amount),
                            self.eml_lineage_proof,
                            provider_innerpuzhash,
                            self.coin.name(),
                            announcement_nonce,
                        ),
                        hidden=True,
                    ),
                ]
            ),
        )

        expected_announcement: CreatePuzzleAnnouncement = CreatePuzzleAnnouncement(
            std_hash(self.coin.name() + Program.NIL.get_tree_hash() + ACS_TRANSFER_PROGRAM.get_tree_hash())
        )

        return (
            expected_announcement,
            make_spend(self.coin, self.construct_puzzle(), vc_solution),
        )
