### Title
Schnorr aggregate verification recomputes weights over a different transcript state than aggregation - (crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregator::complete` derives each aggregation weight immediately after only that signature’s challenge has been appended to the digest, while `SchnorrAggregate::verify` first appends every challenge and only then derives all weights. The producer and verifier therefore use different `z_i` values for the same aggregate, analogous to evaluating a check with a value from the wrong scale/domain. The result is an incorrect verifier formula for aggregates containing more than one signature.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `SchnorrAggregator::aggregate` appends each challenge to `self.digest` before the next signature is processed. `SchnorrAggregator::complete` then calls `weight(&mut self.digest)` once per signature, so `weight_0` is derived from `H(challenge_0)`, `weight_1` from `H(challenge_0 || challenge_1)`, etc. In `SchnorrAggregate::verify`, the verifier appends all challenges into a fresh digest before entering the weight loop, so every `z_i` is derived from a transcript already containing `challenge_0 .. challenge_n`. For `i = 0`, producer weight excludes later challenges while verifier weight includes them; for all later `i`, the transcript states still diverge from the producer’s incremental states.

### Impact Explanation
Honestly produced aggregates with at least two signatures are rejected by the matching verifier, creating an availability failure for any protocol path that relies on half-aggregation. It also splits the definition of “valid aggregate”: bytes produced by `SchnorrAggregator` are not the bytes accepted by `SchnorrAggregate::verify`, so an external peer can cause disagreement by submitting multi-signature aggregates to verification. This is an incorrect verifier formula rather than a pure style issue, but I did not find a standalone key-recovery or universal-forgery primitive inside this function alone.

### Likelihood Explanation
Reachable whenever two or more Schnorr signatures are aggregated through `SchnorrAggregator::aggregate`/`complete` and later checked with `SchnorrAggregate::verify` over `keys_and_challenges`. Single-signature aggregates remain unaffected because there are no later challenges to contaminate the first weight.

### Recommendation
Make production and verification derive weights from identical transcript states. Either buffer all `(R, s, challenge)` values during aggregation and compute weights only after all challenges are appended, or change verification to mirror the producer’s incremental transcript exactly. Add a vector test aggregating two valid signatures and asserting `verify` succeeds.

### Proof of Concept
1. Create two valid `SchnorrSignature<C>` values under distinct public keys/challenges.
2. Feed them in order to `SchnorrAggregator::new(dst)` via `aggregate(challenge_i, sig_i)`, then call `complete` to obtain `SchnorrAggregate { Rs, s }`.
3. Call `SchnorrAggregate::verify(dst, &[(A0, c0), (A1, c1)])`.
4. The check fails for otherwise valid inputs because verification computed `z_0` and `z_1` after both `c0` and `c1` were appended, while aggregation computed `z_0` after only `c0` and `z_1` after `c0 || c1`.
