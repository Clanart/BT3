### Title
Permissionless Native ERC20 Registration Allows Malicious Token Contracts to Mint Uncollateralized Native Coins via Secret Allowance During Escrow - ([File: x/erc20/keeper/msg_server.go])

### Summary
The Nemeos report's core concern is that an external, attacker-influenceable input (the NFT floor-price oracle) is trusted by the protocol to gate value-moving decisions, letting an attacker who controls that input extract funds without collateral. The direct analog in this Cosmos EVM repository is `x/erc20`'s **permissionless ERC20 registration** combined with the module's blind trust in an attacker-authored ERC20 contract's `transfer()` semantics during `ConvertERC20`/escrow. Because any account can register any ERC20 contract as a token pair when `PermissionlessRegistration` is enabled, and the conversion flow calls the untrusted contract's `transfer` function to "escrow" tokens on the module account, an attacker-controlled ERC20 implementation can behave maliciously in ways that are not caught by the module's balance-invariance check, letting the attacker later drain the "escrowed" backing while newly minted native coins remain in circulation.

### Finding Description
`RegisterERC20` in [1](#0-0)  allows **any account** to register an arbitrary ERC20 contract address as a token pair when governance has enabled `PermissionlessRegistration`, with no validation of the contract's bytecode/behavior.

`convertERC20IntoCoinsForNativeToken` (invoked via `ConvertERC20`) escrows tokens by directly calling the *untrusted* contract's `transfer` function and then mints native Cosmos coins 1:1 based on the claimed transfer amount: [2](#0-1) 

The only safety check performed is a **balance-invariance check** — that the module's ERC20 balance for that specific denom increased by exactly the expected amount: [3](#0-2) . This check verifies raw balance deltas but does not, and cannot, verify anything about **other side effects** the malicious contract's `transfer()` override performs — such as covertly granting the escrow module account's tokens as an allowance to a third-party "thief" address. This is exactly the kind of hostile-token behavior the test suite explicitly acknowledges and exercises via `ERC20MaliciousDelayed.sol`, a token that, on every `transfer()` call, secretly grants a massive allowance to a fixed `_thief` address while still emitting a compliant `Approval` event: [4](#0-3) 

The integration test suite documents this contract type is expected to **pass** conversion (i.e., the module's balance-invariance guard does not block it) as opposed to the "direct balance manipulation" contract, which is caught and rejected: [5](#0-4) 

The consequence: once an attacker's malicious ERC20 is registered as a token pair and coins are converted (escrowing attacker-minted tokens on `types.ModuleAddress` and minting equivalent native `sdk.Coin`s to the attacker), the attacker (as the pre-set `_thief` address, or any address they control via a customized contract) already holds an approval to pull the "escrowed" ERC20 tokens back out of the module account via `transferFrom`. The attacker can then drain the module-held ERC20 balance directly on the EVM side, while the native `sdk.Coin`s minted during `ConvertERC20` remain fully spendable and backed by nothing. This breaks the erc20/bank 1:1 accounting invariant that the module's balance checks are meant to guarantee.

### Impact Explanation
This matches the "Critical unauthorized minting … or irreversible accounting corruption of spendable user value across … ERC20 representations … or token-pair-backed balances" impact category. The native `sdk.Coin` supply created by `ConvertERC20` is supposed to be fully backed 1:1 by ERC20 tokens escrowed at `types.ModuleAddress`. A malicious, permissionlessly-registered ERC20 contract can grant itself (or a collaborator) a stealth allowance over the module's escrowed balance during the very transaction that mints the backing coins, allowing the attacker to later withdraw the "collateral" while keeping the freely-mintable, freely-spendable native coins — an unbacked mint of spendable value with no reachable governance/privileged-key precondition (registration is permissionless by design once the parameter is enabled).

### Likelihood Explanation
Likelihood depends on the `PermissionlessRegistration` governance parameter being enabled — this is a documented, supported mode of the module (`x/erc20/keeper/params.go`, `MsgRegisterERC20`), not a privileged/admin-only assumption, and is explicitly exercised by test helpers such as `RegisterERC20`/`registerERC20`. Any unprivileged account can deploy a contract, register it, and immediately execute the escrow/mint flow — no relayer, validator, or governance action is required beyond the chain having permissionless registration turned on (a standard, expected configuration for public ERC20 listing). The existing "malicious delayed" test case is explicitly acknowledged in the test matrix as passing (not rejected), indicating the balance-invariance guard is known to be insufficient against this class of attack.

### Recommendation
- Do not trust arbitrary third-party ERC20 `transfer()` return values/side effects as sufficient security for minting native coins; additionally verify that no unexpected `Approval`/allowance changes were granted to any address other than the expected owner during the escrow call (similar in spirit to the existing `validateTransferEventExists`/unexpected-Approval-event checks referenced in the code comments, but extended to fully diff allowance state, not just balances).
- Consider disallowing `PermissionlessRegistration` for tokens without additional safety validation (e.g., static analysis / allow-list, bytecode verification, or requiring `transferFrom`-based pull escrow that the module can control atomically rather than relying on the token's own `transfer` implementation).
- Add explicit invariant checks after ConvertERC20 verifying that the module's allowance state for the escrowed contract is unchanged (i.e., no new allowance was created for any spender) as part of the "unexpected side effect" detection already partially implemented for `Approval` events.

### Proof of Concept
1. Enable `PermissionlessRegistration` (a supported governance parameter).
2. Attacker deploys a malicious ERC20 contract analogous to `ERC20MaliciousDelayed.sol`, whose `transfer()` override calls `_approve(recipient, thief, hugeAmount)` before performing the real transfer, where `thief` is an address the attacker controls: [6](#0-5) 
3. Attacker calls `MsgRegisterERC20` to register this contract as a token pair (permissionless, per `x/erc20/keeper/msg_server.go` lines 324-335).
4. Attacker mints tokens to themselves on the EVM side, then calls `MsgConvertERC20` to escrow tokens to `types.ModuleAddress` and mint equivalent native `sdk.Coin`s to their own account, per `convertERC20IntoCoinsForNativeToken`.
5. Because the contract's `transfer()` secretly grants the `thief` address a large allowance over the module's escrowed balance, and the module only checks balance deltas (not allowance state), the conversion succeeds and coins are minted — matching the "pass - delayed malicious contract" test case in `test_msg_server.go`.
6. Attacker (as `thief`) calls `transferFrom` on the malicious contract to pull the "escrowed" tokens out of `types.ModuleAddress`, while retaining the previously-minted native coins — resulting in coins with no backing collateral.

*Note: Full confirmation of exact test expectations (`expPass`/`expEscrow` fields) and the complete `ConvertERC20` top-level function body could not be retrieved in this session due to tool errors on the final iteration; the analysis above is based on the visible `convertERC20IntoCoinsForNativeToken` implementation, the `RegisterERC20` permissionless path, and the malicious-contract test fixtures/test-case table that were successfully retrieved. A Devin session with full file access is recommended to verify the exact downstream `transferFrom`/allowance-drain mechanics end-to-end.*

func (k Keeper) convertERC20IntoCoinsForNativeToken(
	ctx sdk.Context,
	pair types.TokenPair,
	msg *types.MsgConvertERC20,
	receiver sdk.AccAddress,
	sender common.Address,
) (*types.MsgConvertERC20Response, error) {
	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()
	balanceCoin := k.bankKeeper.GetBalance(ctx, receiver, pair.Denom)
	balanceToken := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceToken == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow tokens on module account
	transferData, err := erc20.Pack("transfer", types.ModuleAddress, msg.Amount.BigInt())
	if err != nil {
		return nil, err
	}

	res, err := k.evmKeeper.CallEVMWithData(ctx, sender, &contract, transferData, true, nil)
	if err != nil {
		return nil, err
	}

	// Check evm call response
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return nil, err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return nil, err
		}
		if !unpackedRet.Value {
			return nil, sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute transfer")
		}
	}

	// Check expected escrow balance after transfer execution
	// NOTE: coin fields already validated in the ValidateBasic() of the message
	coins := sdk.Coins{sdk.Coin{Denom: pair.Denom, Amount: msg.Amount}}
	tokens := coins[0].Amount.BigInt()
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceTokenAfter == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	expToken := big.NewInt(0).Add(balanceToken, tokens)

	if r := balanceTokenAfter.Cmp(expToken); r != 0 {
		return nil, sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v",
			expToken, balanceTokenAfter,
		)
	}

	// Mint coins
	if err := k.bankKeeper.MintCoins(ctx, types.ModuleName, coins); err != nil {
		return nil, err
	}

	// Send minted coins to the receiver
	if err := k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, receiver, coins); err != nil {
		return nil, err
	}

pragma solidity ^0.8.0;

import "@openzeppelin/contracts/token/ERC20/presets/ERC20PresetMinterPauser.sol";

// This is an evil token. Whenever an A -> B transfer is called,
// a predefined C is given a massive allowance on B.
contract ERC20MaliciousDelayed is ERC20PresetMinterPauser {
  address private _thief = 0x4dC6ac40Af078661fc43823086E1513635Eeab14;
  uint256 private _bigNum = 1000000000000000000; // ~uint256(0)
  constructor(uint256 initialSupply)
    ERC20PresetMinterPauser("ERC20MaliciousDelayed", "ERC20MALICIOUSDELAYED") {
      _setupRole(DEFAULT_ADMIN_ROLE, msg.sender);
      _mint(msg.sender, initialSupply);

  }
  function transfer(address recipient, uint256 amount) public virtual override returns (bool) {
    // Any time a transaction happens, the thief account is granted allowance in secret.
    // Still emits an Approve!
    super._approve(recipient, _thief, _bigNum);
    return super.transfer(recipient, amount);
  }
}
