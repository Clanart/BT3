### Title
Stack overflow via unbounded recursive RLP decoding of nested `AccountKeyRoleBased` account keys - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each sub-key of a role-based account key by calling `rlp.DecodeBytes` on attacker-controlled byte strings, and this recursion has no depth limit. Since the "no nested composite key" rule is only enforced after decoding (in `blockchain/state_transition.go`), an attacker can submit a crafted raw transaction (e.g. a `TxTypeAccountUpdate`) whose `Key` field contains many levels of nested `AccountKeyRoleBased` values, causing unbounded Go-stack recursion during RLP decoding and crashing the node (fatal stack overflow, not a recoverable panic) before any semantic validation occurs.

### Finding Description
`AccountKeyRoleBased` is encoded/decoded as a list of RLP-encoded sub-keys: [1](#0-0) 

`DecodeRLP` reads `[][]byte` and then, for each element, calls `rlp.DecodeBytes(b, &serializer)` where `serializer` is an `AccountKeySerializer`. `AccountKeySerializer.DecodeRLP` reads a key type tag and then decodes the key value using `NewAccountKey(...)` + `s.Decode(serializer.key)`: [2](#0-1) 

If the nested key type is again `AccountKeyTypeRoleBased`, this re-enters `AccountKeyRoleBased.DecodeRLP`, which again recurses into `AccountKeySerializer.DecodeRLP`, and so on — the recursion depth is entirely controlled by the attacker's raw bytes with no limit on nesting depth checked before or during decoding.

The check that is supposed to forbid this ("nested composite type not allowed") is only performed **after** decoding completes, in `blockchain/state_transition.go` (confirmed by `ErrNestedCompositeType` usage there and in the account-key files themselves), and is exercised at the txpool/state-transition validation layer as shown by the existing regression test: [3](#0-2) 

That test only verifies a single level of nesting is rejected; it does not address that the decode itself has already fully recursed (and would recurse further for deeper nesting) before the rejection check runs. Because `IsCompositeType`/`ErrNestedCompositeType` validation happens post-decode, an attacker who crafts many nested levels forces the Go RLP decoder (and the mutually recursive `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` pair) to recurse until the goroutine stack is exhausted, which in Go is a fatal, unrecoverable process crash — this is the same bug class as the referenced jsonxx CVE-2022-23460 (recursive descent parser without a depth limit).

This path is reachable from a single unprivileged transaction: any `TxTypeAccountUpdate` transaction carries an `AccountKeySerializer`-encoded `Key` field which is RLP-decoded during general transaction decoding (`blockchain/types/tx_internal_data_account_update.go`), i.e. before signature/nonce/balance checks can reject the transaction. Both `eth_sendRawTransaction`/public RPC ingestion and `txpool.AddRemote` must RLP-decode the transaction (and thus the nested account key) to even determine its type/hash, so the stack-overflow trigger fires before pool admission or state-transition validation can reject it.

### Impact Explanation
A successful stack overflow is a fatal runtime crash of the Go process (not a recoverable panic), causing denial of service for any Kaia node that decodes the malicious raw transaction — including nodes in the p2p tx-broadcast path and validators processing the transaction pool. Because the trigger occurs during RLP decode (prior to nonce/balance/signature checks), the attacker does not need funds, a valid signature, or txpool acceptance to reach the vulnerable code — a bare RLP blob submitted via `eth_sendRawTransaction` or gossiped as a pending transaction is sufficient to crash any node that decodes it, which can cause node crashes across the network and disrupt consensus liveness.

### Likelihood Explanation
High: constructing a deeply nested `AccountKeyRoleBased` blob is a purely off-chain, unauthenticated operation involving repeated RLP encoding of type-tag + byte-string pairs; no cryptographic material or special privileges are required to build the payload. The only requirement is that the resulting envelope be well-formed RLP for a `TxTypeAccountUpdate` transaction, which is fully attacker-controlled.

### Recommendation
Enforce a maximum recursion/nesting depth for account-key decoding before or during `AccountKeyRoleBased.DecodeRLP` (e.g., pass a decode-depth counter through `AccountKeySerializer.DecodeRLP` and reject with `ErrNestedCompositeType` as soon as depth > 1, instead of only after full decode). Alternatively, disallow decoding an `AccountKeyTypeRoleBased` tag when already inside a `RoleBased`/composite decode context, failing fast on the first nested occurrence rather than after unbounded recursion.

### Proof of Concept
Conceptually:
1. Build an `AccountKeySerializer` whose `keyType = AccountKeyTypeRoleBased` and whose `key` bytes are themselves an RLP-encoded `AccountKeyRoleBased` list containing another such serializer, and repeat this nesting N times (N large, e.g. tens of thousands).
2. Wrap the resulting bytes as the `Key` field of a `TxTypeAccountUpdate` transaction (`blockchain/types/tx_internal_data_account_update.go`), RLP-encode the full transaction envelope.
3. Submit the raw transaction via `eth_sendRawTransaction` (or inject via p2p gossip / `txpool.AddRemote`).
4. When the node RLP-decodes the transaction to determine its type/hash, `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recurse N times, exhausting the goroutine stack and crashing the process before `ErrNestedCompositeType` validation in `blockchain/state_transition.go` is ever reached. func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
```go
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
```

```go
func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
```
