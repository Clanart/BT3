### Title
Auctioneer signature does not bind bid content; `MaxGasPrice` can be forged when EIP-712 struct version excludes it - ([File: kaiax/auction/bid.go])

### Summary
The Kaia auction module (KIP-249) requires two independent signatures on a `Bid`: a **searcher signature** over an EIP-712 typed digest of the bid content, and an **auctioneer signature**. Analogous to the passport-wsfed-saml2 flaw (a "signature exists" check that does not verify the signature actually covers the data being trusted), the auctioneer signature in `ValidateAuctioneerSig` never signs over any bid field — it only signs over the raw bytes of the searcher's signature. Combined with the version-dependent EIP-712 struct definition that omits `MaxGasPrice` from the "v2.1"/default typehash, the `MaxGasPrice` field can be attached to (or altered in) a bid without invalidating either signature, and later be honored on-chain via the v3.0 ABI encoding path.

### Finding Description
`Bid.ValidateAuctioneerSig` computes its digest from `GetEthSignedMessageHash`, which hashes **only** `b.SearcherSig` bytes, not any bid parameter: [1](#0-0) [2](#0-1) 

This design relies entirely on the searcher's own EIP-712 signature to bind the bid content. However, the EIP-712 struct encoding is version-dependent, and the "v2.1" / default (unrecognized-version) struct hash explicitly excludes the `MaxGasPrice` field: [3](#0-2) [4](#0-3) 

Yet `BidData.MaxGasPrice` is a normal, independently mutable field of the wire/API structure that is not restricted based on version: [5](#0-4) [6](#0-5) 

The bid-pool validation logic (`validateBidSigs`) verifies signature validity using whatever `auctionEntryPointVersion` is currently cached from on-chain state: [7](#0-6) 

Separately, at block-building time, `GetBidTxGenerator` independently re-reads the current version and re-encodes the bid — including `MaxGasPrice` — for submission to the on-chain `AuctionEntryPoint` contract if that version is v3.0: [8](#0-7) [9](#0-8) 

If the entry-point contract's reported `AUCTION_VERSION` differs between the moment the bid's signatures were validated (v2.1, excluding `MaxGasPrice` from the digest) and the moment the bid transaction calldata is generated (v3.0, including `MaxGasPrice`), an attacker can set or modify `MaxGasPrice` on a bid whose two signatures were computed/validated without that field ever being part of either signed digest. Both `ValidateSearcherSig` and `ValidateAuctioneerSig` will still pass because neither digest depends on `MaxGasPrice` under the v2.1 typehash, and the auctioneer signature never covers bid fields directly in the first place. The module does state it clears the bid pool on detected version changes, which is a mitigation for the specific TOCTOU window, but the underlying signature architecture is still structurally unsound: the auctioneer's attestation is over an opaque signature blob rather than the actual economic terms of the bid (`MaxGasPrice`, `To`, `CallGasLimit`, `Data`), so any future addition of unsigned-in-some-version fields (as already happened with `MaxGasPrice`) reintroduces the same class of bug without any additional code review catching it, since the auctioneer signature check offers no defense-in-depth on its own.

### Impact Explanation
`MaxGasPrice` is intended to be an economic guarantee negotiated between searcher and auctioneer (analogous to a max-fee cap the searcher authorizes). If it can be attached/altered outside of what either signature actually attests to, it enables fee/settlement abuse in the auction flow: a party could cause a bid to be executed on-chain against a `MaxGasPrice` value the searcher never actually signed, potentially forcing higher-than-agreed gas costs on the searcher or allowing manipulation of settlement economics enforced by the v3.0 `AuctionEntryPoint` contract. This falls under "gasless or auction settlement theft / fee abuse" within the accepted impact categories.

### Likelihood Explanation
Exploitation requires a narrow timing window around an on-chain `AuctionEntryPoint` contract version upgrade from v2.1 to v3.0 (or a transient/erroneous version read), which the module partially mitigates by clearing the bid pool on detected version/address changes. I was not able to fully verify the atomicity of that clearing relative to the version reads used in `validateBidSigs` versus `GetBidTxGenerator` within the available context, so likelihood is best assessed as **conditional/moderate**: the structural flaw (auctioneer signature not binding to bid content) is unconditionally present, but full exploitation depends on the version-transition race actually being reachable in practice.

### Recommendation
Have `ValidateAuctioneerSig` sign over (or otherwise cryptographically bind to) the full `BidData` content — including `MaxGasPrice` — rather than merely the raw `SearcherSig` bytes, so the auctioneer's attestation does not depend transitively and incompletely on the searcher's EIP-712 typehash for a specific contract version. Additionally, ensure the same, single version value is used consistently for both signature validation and calldata generation for a given bid (e.g., pin the version at bid-submission time and reject/re-validate bids if the on-chain version changes before inclusion), rather than reading it independently at two different points in the pipeline.

### Proof of Concept
1. At time T1, `AuctionEntryPoint.AUCTION_VERSION()` returns `"0.0.1"` (v2.1).
2. A searcher signs a `Bid` with `MaxGasPrice = X` set; `GetHashTypedData(..., "0.0.1")` computes a digest via `Bid.EncodeData()`, which does not include `MaxGasPrice` (`kaiax/auction/eip712.go:75-86`). The digest is therefore identical regardless of the value of `X`.
3. The auctioneer signs `GetEthSignedMessageHash()`, which only hashes the `SearcherSig` bytes (`kaiax/auction/bid.go:52-55`), so it too is agnostic to `MaxGasPrice`.
4. `bp.validateBidSigs` accepts the bid at T1 under version v2.1 — both signatures are valid regardless of `X`'s value; an attacker (or the searcher's own relay) can therefore freely change `MaxGasPrice` to any value `Y` without invalidating either signature, as long as the version stays "0.0.1" at validation time.
5. If, by the time `GetBidTxGenerator`/`EncodeAuctionCallData` runs, `a.bidPool.GetAuctionEntryPointVersion()` returns `"0.0.2"` (v3.0) — e.g., due to a version upgrade between validation and block-building, or if the module's pool-clearing-on-change logic has any gap — `EncodeAuctionCallData(bid, "0.0.2")` will now include the attacker-controlled `MaxGasPrice = Y` in the on-chain `call()` payload (`blockchain/system/auction.go:83-103`), even though neither the searcher nor the auctioneer ever signed over that value.

func (b *Bid) ValidateAuctioneerSig(auctioneer common.Address) error {
	digest := b.GetEthSignedMessageHash()

	recoveredAuctioneer, err := getSigner(b.AuctioneerSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover auctioneer sig: %v", err)
	}

	if recoveredAuctioneer != auctioneer {
		return fmt.Errorf("invalid auctioneer sig: expected %v, calculated %v", auctioneer.String(), recoveredAuctioneer.String())
	}

	return nil

func (b *Bid) EncodeData() []byte {
	encoded := make([]byte, 0)
	encoded = append(encoded, b.TargetTxHash.Bytes()...)
	encoded = append(encoded, common.LeftPadBytes(common.Int64ToByteBigEndian(b.BlockNumber), 32)...)
	encoded = append(encoded, common.LeftPadBytes(b.Sender.Bytes(), 32)...)
	encoded = append(encoded, common.LeftPadBytes(b.To.Bytes(), 32)...)
	encoded = append(encoded, common.LeftPadBytes(common.Int64ToByteBigEndian(b.Nonce), 32)...)
	encoded = append(encoded, common.LeftPadBytes(b.Bid.Bytes(), 32)...)
	encoded = append(encoded, common.LeftPadBytes(common.Int64ToByteBigEndian(b.CallGasLimit), 32)...)
	encoded = append(encoded, crypto.Keccak256Hash(b.Data).Bytes()...)
	return encoded
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}

func EncodeAuctionCallData(bid *auction.Bid, version string) ([]byte, error) {
