### Title
`SweepDust` transfers protocol dust from a shared token pool with no on-chain ledger separating it from unfilled users' escrowed order funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
This is a direct analog of the GLX `LimitOrderRegistry.withdrawNative` bug: an authorized maintenance/sweep function drains a token balance that is *shared* between collected protocol fees ("dust") and still-outstanding user assets, because the contract never maintains a dedicated on-chain accounting variable for "collected dust" separate from the escrow ledger (`_orders`). The sweep transfers whatever amount is specified in the request directly out of the contract's raw balance, with no invariant check against total outstanding escrow.

### Finding Description
`IntentGatewayV2`/`IntentsBase` accumulates protocol "dust" from three sources into the *same* contract balance that also holds users' escrowed order inputs:
- protocol-fee deduction at `placeOrder` time [1](#0-0) 
- solver overpayment ("surplus") sent to the protocol at fill time [2](#0-1) 
- residual calldata-execution dust swept back from the `CallDispatcher` [3](#0-2) 

None of these events increment a dedicated state variable tracking "collected dust." The only accounting the contract maintains is `_orders[commitment][token]`, which tracks *per-order escrow*, decremented only when that specific order is filled, refunded, or cancelled [4](#0-3) .

When Hyperbridge governance sweeps the accumulated dust, `_sweepDust` simply transfers an arbitrary caller-specified amount straight from the contract's balance to a beneficiary, with zero on-chain validation that this amount does not exceed the actual "dust" (i.e., `contract balance − sum of all outstanding `_orders` escrow`):

```solidity
function _sweepDust(SweepDust memory req) internal {
    uint256 outputsLen = req.outputs.length;
    for (uint256 i; i < outputsLen;) {
        TokenInfo memory info = req.outputs[i];
        address token = address(uint160(uint256(info.token)));
        uint256 amount = info.amount;
        if (token == address(0)) {
            (bool sent,) = req.beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            IERC20(token).safeTransfer(req.beneficiary, amount);
        }
        ...
    }
}

Just like the original H-1 report, the "fee"/dust amount is computed *off-chain* (by whichever process constructs the `SweepDust` payload) from an observed balance snapshot, then blindly executed on-chain against a pool that also contains funds belonging to users whose orders are pending fill/refund. There is no on-chain guard such as `amount <= IERC20(token).balanceOf(address(this)) - totalEscrowed[token]`. Because escrow deposits (`placeOrder`) happen continuously and asynchronously relative to when a `SweepDust` message is computed off-chain and later delivered on-chain (subject to cross-chain relay delay), the executed sweep amount can, at execution time, exceed the token's true "dust" portion and consume tokens that are still recorded as `_orders[commitment][token]` escrow for an unfilled or uncancelled order. When the affected order is later filled/cancelled, `_withdraw`'s `IERC20(token).safeTransfer(beneficiary, amount)` or native `.call{value: amount}("")` will fail for lack of funds, reverting withdrawal and leaving the user's escrowed principal (or worse, a solver's already-delivered assets in a fill scenario) unrecoverable — an irreversible loss of user/solver funds, exactly mirroring the GLX scenario where fee-withdrawal wiped out a claimable order.

### Impact Explanation
This breaks the "bridged assets/order escrow must move exactly once and only to the rightful beneficiary and amount" invariant. A pool meant to hold both segregated user escrow and protocol fees has no on-chain ledger enforcing the separation, so a legitimate, authorized administrative operation (sweeping protocol dust to treasury) can — due to timing/off-chain miscalculation, exactly as in the original report — transfer tokens still owed to users/solvers out of the contract, causing their subsequent `withdraw`/`cancelOrder`/`fillOrder` settlement calls to revert and their escrowed funds to become permanently unrecoverable.

### Likelihood Explanation
The condition does not require any malicious relayer, prover, or compromised key — it requires only ordinary operational timing: dust is computed from an off-chain balance observation, and any new `placeOrder`/`fillOrder` activity that adds to the shared pool between that snapshot and the on-chain execution of the sweep (subject to ISMP cross-chain delivery latency) is enough to make the sweep touch funds that are still legitimately escrowed. As protocol usage grows and dust-sweep frequency increases, this window recurs regularly, making this a systemic, structural gap rather than a one-off edge case.

### Recommendation
Introduce a dedicated on-chain running-total for collected protocol dust per token (incremented at each of the three dust-generating sites: protocol-fee deduction, surplus split, and calldata-dust sweep), and have `_sweepDust`/`onAccept(SweepDust)` validate and decrement against that ledger rather than transferring an arbitrary amount from the raw contract balance. This mirrors "Solution 2" from the referenced report — segregating fee/dust accounting from user-asset accounting so a sweep can never draw on funds still tracked in `_orders`.

### Proof of Concept
1. User A calls `placeOrder`, escrowing input tokens; `_orders[commitmentA][token]` is credited, and the contract's raw token balance now includes both A's escrow and any previously accumulated dust.
2. Off-chain governance tooling observes the contract's total token balance minus a stale/previous dust estimate and constructs a `SweepDust` payload for what it believes is purely accumulated fee dust, then dispatches it via the ISMP `UpdateParams`/`SweepDust` flow (`evm/src/apps/intentsv2/IntentsBase.sol` `RequestKind.SweepDust`, `onAccept`).
3. Before this cross-chain message is delivered and executed on the destination gateway, User A's order is filled/partially processed, or another user's `placeOrder`/solver's surplus payment increases the shared balance such that the true "dust" portion shrinks relative to the snapshot used to build the payload — or conversely the sweep is executed while A's order is still outstanding and the previously computed dust figure already double-counts a portion of A's escrow due to no ledger cross-check.
4. `onAccept` executes `SweepDust` unconditionally, calling `IERC20(token).safeTransfer(beneficiary, amount)` (evm) / low-level `token.call(...)` (tron) for the specified `amount`, draining tokens from the shared pool that include User A's still-escrowed balance.
5. User A later attempts to fill/cancel their order; `_withdraw` computes `escrowed - amount` correctly in storage, but the subsequent `IERC20(token).safeTransfer(beneficiary, amount)` reverts (or, on the tron contract's unchecked low-level call path, may silently fail while storage is already decremented) because the contract's actual token balance is now insufficient — resulting in a stuck/lost order with no recovery path, since `SweepDust` funds have already left the contract to the treasury beneficiary.

Note: I was unable to fully trace the off-chain/pallet-side logic in `modules/pallets/intents-coprocessor` that constructs the `SweepDust` amount (tool budget exhausted before reading `types.rs`/`lib.rs` sweep-dispatch code in full), so I cannot confirm whether any additional off-chain safeguard exists there; the on-chain contract code, however, demonstrably contains no such check, which is the exploitable local analog.
