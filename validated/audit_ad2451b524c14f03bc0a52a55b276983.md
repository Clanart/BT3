### Title
Staked-stream load EMA can be kept artificially suppressed by drip-feeding calls just under the smoothing interval, defeating QUIC/TPU staked-stream throttling - (`streamer/src/nonblocking/stream_throttle.rs`)

### Summary
The Sherlock report's root cause is a "discretize-by-truncated-division, then advance the checkpoint to the exact current time instead of the truncated boundary" pattern: work performed for a period is credited only in whole intervals (floor division), while the remainder time is silently thrown away because the stored checkpoint jumps to `now` rather than to `checkpoint + intervals*interval_length`. This lets an attacker who calls the function often (always leaving < 1 interval of remainder) permanently erase part of the real elapsed time from the calculation, corrupting an accrual/rate value in their favor.

Agave's staked-stream load EMA in `StakedStreamLoadEMA::update_ema_if_needed`/`update_ema` follows the same structural pattern: it truncates elapsed time into whole `STREAM_LOAD_EMA_INTERVAL_MS` catch-up steps via integer division, but then unconditionally sets the checkpoint to `Instant::now()` instead of to the truncated interval boundary.

### Finding Description
`update_ema_if_needed` gates on a fixed `EMA_DURATION` (`STREAM_LOAD_EMA_INTERVAL_MS` = 5ms) and, when triggered, snapshots `since_last_update` and then stores `*last_update_w = Instant::now()`: [1](#0-0) 

`update_ema` then converts that raw elapsed duration into a *floored* count of extra 5ms steps: [2](#0-1) 

and it drains the accumulated `load_in_recent_interval` counter in a single `swap(0, ...)`: [3](#0-2) 

The bug: any fractional part of `since_last_update_ms` beyond whole 5ms multiples is discarded from the interval accounting (only used to decide how many *zero-load* catch-up steps to fold in), yet the checkpoint is reset to the *actual* wall-clock `now`, not to `last_update + num_intervals*5ms`. Each time `increment_load` → `update_ema_if_needed` fires just past the 5ms boundary (e.g. at 5.9ms), the "used" interval is treated as exactly one 5ms tick, and the leftover ~0.9ms is permanently dropped from the elapsed-time accounting — mirroring the Isomorph `threeMinuteDelta` truncation exactly: `virtualPrice`/`lastUpdateTime` there vs. `current_load_ema`/`last_update` here.

Unlike `net_utils::token_bucket::TokenBucket::update_state`, which explicitly preserves the unused remainder in `credit_time_us` for the next caller (the correct fix pattern recommended in the Isomorph report), `StakedStreamLoadEMA` has no such remainder-preservation mechanism: [4](#0-3) 

### Impact Explanation
`current_load_ema` gates `staked_throttling_enabled`, which in turn controls `available_load_capacity_in_throttling_duration` — the QoS mechanism that limits how many streams a staked peer may open on the validator's QUIC/TPU ingestion path: [5](#0-4) 

Because `increment_load` is invoked on every new stream from any (unprivileged, remote) connected peer and calls `update_ema_if_needed` inline: [6](#0-5) 

an attacker-influenced access pattern to this shared per-validator EMA state can suppress how quickly `current_load_ema` rises toward `staked_throttling_on_load_threshold`, delaying or preventing `staked_throttling_enabled` from turning on. This weakens the QUIC/TPU stream throttling defense that exists specifically to prevent load-based denial of service, falling into the "non-RPC remote exhaustion/crash" impact category — it degrades a control meant to protect validator stream-processing resources from being overwhelmed.

### Likelihood Explanation
The EMA update path is on the hot path of every incoming QUIC stream (`increment_load`), so triggering `update_ema_if_needed` at a chosen cadence merely requires sending many streams at network-observable timing — no special privilege, leader status, or trusted role is needed, only being a connected (potentially staked) client sending TPU traffic. However, because the effect only shaves fractional milliseconds per 5ms window off of the accounting rather than eliminating them, this is a matter of degree (a load-smoothing/QoS bypass under sustained high-rate stream submission), not an outright silent disablement, and its practical exploitability depends on how easily an attacker can align the timing of stream submissions with the 5ms boundary at scale across many concurrent streams from potentially multiple threads (the lock-based double-check in `update_ema_if_needed` also serializes updates, which somewhat limits how much drift can accumulate).

### Recommendation
Truncate the checkpoint to the interval boundary consumed, instead of resetting it to `Instant::now()`:
```rust
let elapsed_ms = since_last_update.as_millis();
let intervals_consumed = elapsed_ms / u128::from(STREAM_LOAD_EMA_INTERVAL_MS);
*last_update_w += Duration::from_millis((intervals_consumed as u64) * STREAM_LOAD_EMA_INTERVAL_MS);
self.update_ema(elapsed_ms);
```
Or, following the `TokenBucket::update_state` pattern already present in this codebase, preserve the truncated remainder for the next call instead of discarding it (e.g. an accumulator similar to `credit_time_us`).

### Proof of Concept
1. Attacker opens a staked QUIC connection and repeatedly submits streams timed so that each call to `increment_load` → `update_ema_if_needed` lands just after crossing the 5ms `EMA_DURATION` boundary (e.g., at 5.9ms, 11.8ms, 17.7ms, ...).
2. Each call: `since_last_update` ≈ 5.9ms; `update_ema` computes `num_extra_updates = (5900-1)/5000 = 0` (with `STREAM_LOAD_EMA_INTERVAL_MS` in the internal unit used), applying exactly one EMA update cycle for what is actually a ~5.9ms window, then `last_update_w` is set to the exact call time.
3. Repeating this pattern across many stream submissions accumulates fractional-millisecond loss on every update; over a sustained burst the tracked `current_load_ema` under-represents the true submission rate.
4. As long as `current_load_ema` stays below `staked_throttling_on_load_threshold`, `staked_throttling_enabled` remains false, and `available_load_capacity_in_throttling_duration` continues returning `self.max_staked_load_in_throttling_window` (the full, unthrottled capacity) for this peer's stake weight, letting it push more streams through the QUIC/TPU ingestion pipeline than the QoS design intends.

**Uncertainty**: I could not load `streamer/src/nonblocking/swqos.rs` (tool call failed on the final iteration) to confirm the exact call sites and locking granularity around `available_load_capacity_in_throttling_duration`, and I have not run a live timing experiment to quantify how much cumulative EMA suppression is achievable under realistic QUIC stream-submission jitter/lock contention. A Devin session with full repo/terminal access would be needed to trace `swqos.rs` completely and to empirically validate the magnitude of this drift under load.

    pub(crate) fn update_ema_if_needed(&self) {
        const EMA_DURATION: Duration = Duration::from_millis(STREAM_LOAD_EMA_INTERVAL_MS);
        // Read lock enables multiple connection handlers to run in parallel if interval is not expired
        if Instant::now().duration_since(*self.last_update.read().unwrap()) >= EMA_DURATION {
            let mut last_update_w = self.last_update.write().unwrap();
            // Recheck as some other thread might have updated the ema since this thread tried to acquire the write lock.
            let since_last_update = Instant::now().duration_since(*last_update_w);
            if since_last_update >= EMA_DURATION {
                *last_update_w = Instant::now();
                self.update_ema(since_last_update.as_millis());
            }
        }
    }

    pub(crate) fn increment_load(&self, peer_type: ConnectionPeerType) {
        if peer_type.is_staked() {
            self.load_in_recent_interval.fetch_add(1, Ordering::Relaxed);
        }
        self.update_ema_if_needed();
    }

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }

    /// Updates internal state of the bucket by
    /// depositing new tokens (if appropriate)
    fn update_state(&self, now: u64) {
        // fetch last update time
        let last = self.last_update.load(Ordering::SeqCst);

        // If time has not advanced, nothing to do.
        if now <= last {
            return;
        }

        // Try to claim the interval [last, now].
        // If we can not claim it, someone else will claim [last..some other time] when they
        // touch the bucket.
        // If we can claim interval [last, now], no other thread can credit tokens for it anymore.
        // If [last, now] is too short to mint any tokens, spare time will be preserved in credit_time_us.
        match self.last_update.compare_exchange(
            last,
            now,
            Ordering::AcqRel,  // winner publishes new timestamp
            Ordering::Acquire, // loser observes updates
        ) {
            Ok(_) => {
                // This thread won the race and is responsible for minting tokens
                let elapsed = now.saturating_sub(last);

                // also add leftovers from previous conversion attempts.
                // we do not care about who uses the spare_time_us, so relaxed is ok here.
                let elapsed =
                    elapsed.saturating_add(self.credit_time_us.swap(0, Ordering::Relaxed));

                let new_tokens_f64 = elapsed as f64 * self.new_tokens_per_us;

                // amount of full tokens to be minted
                let new_tokens = new_tokens_f64.floor() as u64;

                let time_to_return = if new_tokens >= 1 {
                    // Credit tokens, saturating at max_tokens
                    self.add_tokens(new_tokens);
                    // Fractional remainder of elapsed time (not enough to mint a whole token)
                    // that will be credited to other minters
                    (new_tokens_f64.fract() / self.new_tokens_per_us) as u64
                } else {
                    // No whole tokens minted → return whole interval
                    elapsed
                };
                // Save unused elapsed time for other threads
                self.credit_time_us
                    .fetch_add(time_to_return, Ordering::Relaxed);
            }
            Err(_) => {
                // Another thread advanced last_update first → nothing we can do now.
            }
        }
