### Title
Uncaught `ValueError` on unrecognized condition opcode crashes wallet signing/offer-processing paths - (File: `chia/consensus/condition_tools.py`)

### Summary
`parse_sexp_to_condition()` builds a `ConditionWithArgs` by directly constructing `ConditionOpcode(op)` from an attacker-controlled byte returned by CLVM execution of a puzzle/solution. `ConditionOpcode` is a strict `bytes, enum.Enum` with a fixed, sparse set of valid single-byte values (e.g. no member for byte value `2`, `10`, `91-255`, etc.) [1](#0-0) . If a puzzle emits a condition whose opcode atom is exactly one byte long but does not match any enum member, `ConditionOpcode(op)` raises a plain `ValueError`, not a `Program.EvalError` [2](#0-1) .

The only caller that wraps this parsing, `conditions_for_solution()`, catches only `Program.EvalError` and converts it into a `ConsensusError`; it does **not** catch `ValueError` [3](#0-2) . As a result, an unrecognized-but-well-formed opcode atom escapes as an unhandled `ValueError` all the way up through `conditions_dict_for_solution()` [4](#0-3)  into every caller that does not itself guard against generic exceptions.

### Finding Description
Two wallet-facing call chains use `conditions_dict_for_solution` on puzzle/solution pairs that originate from **untrusted, attacker-supplied data** (an offer file or a coin spend supplied over RPC), with no exception handling for anything other than the CLVM run itself:

1. `chia/wallet/wallet_signer.py` `WalletSigner.gather_signing_info()` calls `conditions_dict_for_solution(coin_spend.puzzle_reveal, coin_spend.solution, self.max_block_cost_clvm)` directly on each `Spend` derived from a `CoinSpend` [5](#0-4) . This is reachable from `gather_signing_info_for_trades(offers)` → `gather_signing_info_for_bundles([offer._bundle for offer in offers])` [6](#0-5) , i.e. from processing an **offer received from a counterparty** during wallet signing/take-offer flows exposed via the wallet RPC.

2. `chia/wallet/util/debug_spend_bundle.py` `debug_spend_bundle()` calls `conditions_dict_for_solution(puzzle_reveal, solution, INFINITE_COST)` on every coin spend of an arbitrary `SpendBundle` with no surrounding try/except at all [7](#0-6) .

Because a malicious offer counterparty (or any spend-bundle-adjacent puzzle author) fully controls the puzzle reveal/solution and hence the CLVM output list of conditions, they can trivially construct a puzzle that outputs `(2)` — a one-byte atom with value `2`, which is syntactically identical to a real condition list entry, has no NIL/list issue, and is not one of the ~35 enum members. This causes `ConditionOpcode(op)` to raise `ValueError: 2 is not a valid ConditionOpcode`, which is uncaught in the `conditions_for_solution` try/except (only `Program.EvalError` is trapped) and propagates as an unhandled exception to the calling wallet code.

This mirrors the CVE-2021-36754 bug class: a value that is syntactically valid at the wire/opcode level but outside the range the code's dispatch table anticipates (there, DNS QTYPE 65535; here, a condition-opcode byte with no enum mapping) triggers an unhandled exception/out-of-range fault instead of a graceful error path, halting request/transaction processing for that caller.

### Impact Explanation
An untrusted counterparty who sends an offer (or any spend bundle a wallet is asked to sign/debug) containing a puzzle that emits a bogus single-byte opcode can cause an unhandled `ValueError` in the victim wallet process during `take_offer`/signing flows (`gather_signing_info_for_trades`) or in tooling that calls `debug_spend_bundle`. This is a spend/offer-triggered processing halt reachable purely through data the attacker controls (puzzle output), without needing any privileged access — matching the "spend-triggered transaction-processing halt" impact class explicitly in scope.

### Likelihood Explanation
Likelihood is high for the mechanics (trivial to construct a puzzle that emits `(2 ...)` as a condition), but the blast radius is bounded to the wallet-side signing/debug utility paths rather than full-node mempool admission or block validation — full-node consensus paths use the Rust (`chia_rs`) condition parser via `run_block_generator`, not this Python `parse_sexp_to_conditions`. The exposure is therefore real but limited to wallet RPC callers that route through `WalletSigner.gather_signing_info` (e.g. offer taking/signing) or explicitly call `debug_spend_bundle`.

### Recommendation
In `parse_sexp_to_condition()` (chia/consensus/condition_tools.py), catch `ValueError` from `ConditionOpcode(op)` and raise `ConsensusError(Err.INVALID_CONDITION, ...)` instead, or widen the `try/except` in `conditions_for_solution()` to also catch `ValueError`/`KeyError` from opcode construction and convert them into `ConsensusError`. Additionally, harden `WalletSigner.gather_signing_info()` and `debug_spend_bundle()` to catch and handle unexpected exceptions per-coin-spend rather than allowing a single malformed spend to abort the whole signing/debug operation.

### Proof of Concept
1. Craft a CoinSpend whose puzzle, when run with its solution, outputs a condition list containing an atom `(2)` (or any single byte not in `ConditionOpcode`), e.g. CLVM: `(q (2))`.
2. Package this coin spend as part of a `WalletSpendBundle`/`Offer` and have the wallet process it via `Offer.conditions()`/`WalletSigner.gather_signing_info_for_trades` (e.g. `take_offer` RPC) or pass it to `debug_spend_bundle`.
3. Observe `ConditionOpcode(op)` raise `ValueError: b'\x02' is not a valid ConditionOpcode` inside `parse_sexp_to_condition`, uncaught by `conditions_for_solution`'s `except Program.EvalError`, propagating out of `conditions_dict_for_solution` and aborting the calling wallet operation.

```python
def parse_sexp_to_condition(sexp: Program) -> ConditionWithArgs:
    """
    Takes a ChiaLisp sexp and returns a ConditionWithArgs.
    Raises an ConsensusError if it fails.
    """
    first = sexp.pair
    if first is None:
        raise ConsensusError(Err.INVALID_CONDITION, ["first is None"])
    op = first[0].atom
    if op is None or len(op) != 1:
        raise ConsensusError(Err.INVALID_CONDITION, ["invalid op"])

    # since the ConditionWithArgs only has atoms as the args, we can't parse
    # hints and memos with this function. We just exit the loop if we encounter
    # a pair instead of an atom
    vars: list[bytes] = []
    for arg in Program(first[1]).as_iter():
        a = arg.atom
        if a is None:
            break
        vars.append(a)
        # no condition (currently) has more than 3 arguments. Additional
        # arguments are allowed but ignored
        if len(vars) > 3:
            break

    return ConditionWithArgs(ConditionOpcode(op), vars)
```

```python
def conditions_dict_for_solution(
    puzzle_reveal: Program | SerializedProgram, solution: Program | SerializedProgram, max_cost: int
) -> dict[ConditionOpcode, list[ConditionWithArgs]]:
    conditions_dict: dict[ConditionOpcode, list[ConditionWithArgs]] = {}
    for cvp in conditions_for_solution(puzzle_reveal, solution, max_cost):
        conditions_dict.setdefault(cvp.opcode, list()).append(cvp)
    return conditions_dict
```

```python
    async def gather_signing_info_for_bundles(self, bundles: list[WalletSpendBundle]) -> list[UnsignedTransaction]:
        utxs: list[UnsignedTransaction] = []
        for bundle in bundles:
            signer_protocol_spends: list[Spend] = [Spend.from_coin_spend(spend) for spend in bundle.coin_spends]
            utxs.append(
                UnsignedTransaction(
                    TransactionInfo(signer_protocol_spends),
                    await self.gather_signing_info(signer_protocol_spends),
                )
            )

        return utxs

    async def gather_signing_info_for_txs(self, txs: list[TransactionRecord]) -> list[UnsignedTransaction]:
        return await self.gather_signing_info_for_bundles(
            [tx.spend_bundle for tx in txs if tx.spend_bundle is not None]
        )

    async def gather_signing_info_for_trades(self, offers: list[Offer]) -> list[UnsignedTransaction]:
        return await self.gather_signing_info_for_bundles([offer._bundle for offer in offers])
```
