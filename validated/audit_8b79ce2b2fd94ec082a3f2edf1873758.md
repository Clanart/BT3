Based on my research, the strongest analog to the reported bug class (an unauthenticated, attacker-supplied value being trusted to drive a privileged state transition without validation, mirroring how `settleAuction` trusted attacker-supplied `inputTokens`/timing to lower `tokensNeeded`) is in GitHub Desktop's Git credential-helper trampoline, where a remote server's own self-declared `WWW-Authenticate` header is used, unverified, to decide whether an arbitrary endpoint is treated as a trusted GitHub host.

### Title
Credential-helper trusts attacker-controlled `WWW-Authenticate` realm header to classify arbitrary hosts as GitHub, triggering GitHub sign-in flow for untrusted endpoints - (`app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind()` in the credential-helper trampoline handler determines whether a Git remote endpoint should be treated as `'github.com'`, `'enterprise'`, or `'generic'`. Part of this classification logic reads the `wwwauth[]` fields that Git forwards from the remote server's HTTP response and, if the header content contains `realm="GitHub"`, unconditionally classifies the endpoint as `'enterprise'` [1](#0-0) . This value is fully attacker-controlled: any Git server (or a MITM proxy sitting between Desktop and any HTTPS remote) can emit that header on an authentication challenge for any URL, regardless of whether it is actually a GitHub/GHE server.

### Finding Description
The broken invariant is: *"is this a GitHub host"* should be derived from a validated identity check (matching a known account's endpoint, or an actual API probe like `isGitHubHost`), not from a self-asserted string the remote itself supplies during the handshake. In `getEndpointKind`, the `wwwauth[]` heuristic is checked and returns `'enterprise'` *before* falling through to the safer checks (`findGitHubTrampolineAccount`, protocol check, or the network-based `isGitHubHost` probe) [2](#0-1) . Once classified as `'enterprise'`, `getCredential()` skips the generic/external credential-helper path entirely and, if no existing account matches that endpoint, calls `ui.promptForGitHubSignIn(endpoint)` using the attacker-controlled endpoint string [3](#0-2) . This is analogous to the audit finding's core issue: a value computed from attacker-influenced input (`newRatio`) is trusted directly in a security-relevant decision (`tokensNeeded`) without an independent, tamper-resistant check.

No existing guard stops this path: `findGitHubTrampolineAccount` matching real account origins runs earlier only for the fast-path of *finding a stored token* (so it doesn't leak a token for a different origin) [4](#0-3) , but it does not prevent the `wwwauth[]`-driven misclassification from later firing the GitHub-Enterprise sign-in UI branch for a host that has no relationship to GitHub at all.

### Impact Explanation
Any Git server the user fetches/clones/pushes to over HTTPS — or any network intermediary capable of injecting/modifying the HTTP auth challenge for a non-GitHub remote — can force Desktop to present its "Sign in to GitHub Enterprise" flow against an arbitrary attacker-chosen endpoint string. Because the endpoint is taken from `getCredentialUrl(cred)`, which itself is built from the `host`/`protocol`/`path` fields Git derived from the actual request URL, the user is led into what looks like a legitimate GHE authentication prompt for a server that is not one. Depending on what `promptForGitHubSignIn` does with that endpoint (device/OAuth flow initiation), this creates a real risk of binding an OAuth/account flow to attacker infrastructure — falling under the "unauthorized OAuth or account binding" impact category. I was not able to fully trace `promptForGitHubSignIn`'s downstream OAuth implementation before running out of tool budget, so the exact blast radius (whether it merely records a false GHE account locally vs. actually exchanges an OAuth token with the attacker endpoint) should be verified directly in `app/src/lib/trampoline/trampoline-ui-helper.ts` and the sign-in store it delegates to.

### Likelihood Explanation
The trigger requires only that the user perform a normal fetch/clone/push against a repository the attacker controls (satisfies "attacker controls ... a git remote/proxy response"), or that traffic to any HTTPS remote passes through a compromised/malicious proxy that can inject the `WWW-Authenticate` header on a 401 challenge. No local access, no prior credentials, and no unnatural user steps beyond routine Desktop usage are needed — the classification happens automatically inside the credential-helper handler during a normal authentication challenge.

### Recommendation
Do not trust the `wwwauth[]` realm string alone to classify a host as GitHub/Enterprise. Require it to be corroborated by an actual endpoint match (`findGitHubTrampolineAccount`) or a network-verified check (`isGitHubHost`) before routing to the GitHub-Enterprise sign-in branch, and never surface a GitHub sign-in dialog for a host that hasn't been positively confirmed as a GitHub API endpoint.

### Proof of Concept
1. Stand up an HTTPS Git server (or a MITM/compromised proxy in front of any HTTPS remote) that responds to the credential-helper's authentication attempt with a header such as `WWW-Authenticate: Basic realm="GitHub"`.
2. Add this remote in GitHub Desktop and perform a `fetch`/`clone`/`push`.
3. Git forwards the header to Desktop's credential-helper trampoline as a `wwwauth[N]` field in the credential protocol payload.
4. `getEndpointKind()` matches `realm="GitHub"` and returns `'enterprise'` for the attacker's endpoint [5](#0-4) .
5. Since no existing account matches this arbitrary endpoint, `getCredential()` invokes `ui.promptForGitHubSignIn(endpoint)` for the attacker-controlled URL [6](#0-5) , presenting a GitHub-Enterprise sign-in dialog for a non-GitHub host.

Note: I could not verify within the available budget whether `promptForGitHubSignIn` performs a real OAuth exchange bound to the attacker endpoint or simply records a local account association; this should be confirmed against `app/src/lib/trampoline/trampoline-ui-helper.ts` and the underlying sign-in store before treating the OAuth-binding impact as fully proven.

```typescript
const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
```

```typescript
export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
```
