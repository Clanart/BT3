### Title
Balance desync between bank keeper and EVM StateDB via recursive precompile calls sharing a single `BalanceHandler` instance - (File: precompiles/common/balance_handler.go, precompiles/common/precompile.go)

### Summary
There is a test explicitly named for this bug class already present in the repository (`evmd/tests/integration/balance_handler/balance_handler_test.go`), which documents: "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."

### Finding Description
`RunNativeAction` in `precompiles/common/precompile.go` creates a `BalanceHandler` via `p.BalanceHandlerFactory.NewBalanceHandler()` for each precompile call, calling `BeforeBalanceChange(ctx)` prior to executing the native action and `AfterBalanceChange(ctx, stateDB)` afterward to reconcile bank-module balance changes into the EVM `StateDB`. The `BalanceHandler` tracks the length of previously-seen bank balance-change events (`prevEventsLen`) to compute the delta caused by the current action. This exactly parallels the `FullRangeHook`/`TickMath` bug pattern: a piece of state (an "expected boundary" — here, the count of already-processed events) is assumed to reflect a single linear scope of execution, but if a precompile call recursively invokes another precompile call (e.g., an ERC20 precompile invoked from within another precompile, or a callback), a second `BalanceHandler` may be created and operate over the *same* underlying event stream/context, corrupting the `prevEventsLen` bookkeeping for the outer handler. This is analogous to how the `FullRangeHook`'s liquidity math assumed price always stays within `[MIN_TICK, MAX_TICK]`, but recursive/adversarial input (a swap moving price outside that range) broke the invariant and caused wildly incorrect liquidity calculations while consuming the same input amounts.

### Impact Explanation
If the accounting of the delta of bank balance changes to reflect into the `StateDB` becomes wrong due to corrupted `prevEventsLen`, this can result in the EVM view of an account's balance permanently diverging from the actual bank-module balance — i.e., either double-counting a balance increase (unauthorized value creation, in scope as "unauthorized minting/duplication of spendable user value") or dropping a balance change entirely (permanent freezing/loss of user funds). Both outcomes are explicitly listed critical impacts (balance/accounting corruption across native/EVM balances via precompile-mediated flows).

### Likelihood Explanation
The repository already contains a dedicated regression test (`BalanceHandlerTestSuite`) built specifically to reproduce this scenario via recursive precompile calls, which strongly suggests the underlying root cause was previously identified as reachable through unprivileged, ordinary contract-to-precompile-to-precompile call chains (e.g., a contract calling one precompile that internally triggers another precompile call, such as ICS20 callbacks invoking ERC20 precompile transfers). This is a reachable, unprivileged trigger path (any user deploying/calling a contract that chains precompile calls).

### Recommendation
Ensure `BalanceHandler` instances are properly scoped per call-depth (e.g., using a stack or reference-counted nesting mechanism instead of a single shared instance/counter), so that `prevEventsLen` accounting for an outer precompile call is not clobbered by an inner, recursively-invoked precompile's `BalanceHandler`. Add explicit invariant checks (e.g., assert bank-keeper balance equals `StateDB` view after each top-level EVM message) to fail closed instead of silently drifting.
