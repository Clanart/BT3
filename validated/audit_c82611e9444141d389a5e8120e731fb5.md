### Title
OP_RETURN `data` output omitted from weight/vbyte estimate, so `SignableTransaction` under-prices the fee and over-credits change - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The M-6 report concerns functions that consume a quote but cannot attach the required value (the 0x protocol fee), so the operation silently executes under the wrong economic terms. The analogous flaw in Serai is in `SignableTransaction::new`: the fee ("the value that must be attached") is computed from a reconstructed transaction that omits the OP_RETURN `data` output, so `needed_fee` is systematically too low whenever `data` is supplied.

### Finding Description
`SignableTransaction::new` builds `tx_outs` by pushing the OP_RETURN output when `data` is `Some` (lines 194–202). However, the weight/vbyte estimate used to derive `needed_fee` is computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204), and `calculate_weight_vbytes` reconstructs the transaction outputs *only* from `payments` (lines 85–93) — it never sees the OP_RETURN output. The same omission occurs in the with-change estimate at lines 225–227.

Consequences, all derived from a `needed_fee` that is ~`(9 + data.len()) * fee_per_vbyte` sats too small:

1. The `NotEnoughFunds` check at line 215 (`input_sat < payment_sat + needed_fee`) can pass when the real required fee does not fit.
2. When `change` is `Some`, the change output is set to `input_sat - payment_sat - fee_with_change` (lines 228–230), an over-credited value. The actual fee paid (`sum(inputs) - sum(outputs)`, line 139) then equals the underestimated `needed_fee`, i.e. below the caller-specified `fee_per_vbyte` and potentially below `DEFAULT_MIN_RELAY_TX_FEE` — the check at line 211 uses the same underestimated value, so it does not catch this.
3. `needed_fee()` (line 133) reports a value lower than what the caller's requested fee rate implies, so downstream fee amortization (e.g. `Network::needed_fee`/`prepare_send` logic that subtracts `needed_fee` from payments/change) mis-accounts the cost.

### Impact Explanation
A caller that attaches `data` produces a transaction paying a lower effective fee rate than requested. In the worst case (change present, underestimated fee below the minimum relay fee) the signed transaction is unrelayable/non-standard, leaving the spend stuck; more generally the change output is inflated at the expense of the fee, so the transaction confirms at a worse rate than intended — the same "wrong economic terms" impact as the original finding (wasted gas / bad rates), here manifesting as under-paid fees and over-credited change.

### Likelihood Explanation
Reachable by any unprivileged party able to invoke `SignableTransaction::new` with `data: Some(..)` (public transaction data), which is within the stated scope (`networks/bitcoin/src/wallet/`). It triggers deterministically on every call with `Some(data)`; severity scales with `data` length (up to 80 bytes) and `fee_per_vbyte`.

### Recommendation
Pass the fully-built output set into the weight estimate rather than `payments`. E.g., compute `calculate_weight_vbytes` over `tx_outs` (including the OP_RETURN output and, when applicable, the change output), or change the signature to accept the real `Vec<TxOut>` so the estimate cannot diverge from the transaction actually constructed.

### Proof of Concept
- `tx_outs` gains the OP_RETURN output: `send.rs` lines 194–202.
- The estimate ignores it, using `payments` only: `send.rs` line 204 and lines 225–227, with `calculate_weight_vbytes` building outputs solely from `payments` at lines 85–93.
- Under-checked fund sufficiency: line 215 (`input_sat < payment_sat + needed_fee`).
- Over-credited change and under-paid fee: lines 228–230 vs. the true fee definition at lines 138–141.
- Min-relay-fee check applies to the wrong (underestimated) value: lines 206–213.

Reproduce conceptually: call `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0; 80]), fee_per_vbyte)`. Compare `signable.needed_fee()` with `fee_per_vbyte * actual_vbytes_of_final_tx` (the final tx includes the ~93-byte OP_RETURN output); `needed_fee` is short by roughly `fee_per_vbyte * (11 + 80)` vbytes-worth, and `signable.fee()` equals the underestimated `needed_fee` rather than the caller's intended rate.
