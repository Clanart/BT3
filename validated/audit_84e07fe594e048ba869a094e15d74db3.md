### Title
Unchecked u64 addition in `SignableTransaction::new` fund check wraps, allowing a transaction paying out more than its inputs to be signed - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The external report describes an integer overflow reachable only through a specific parse path (`XML_ParseBuffer`) because a bounds check present in the sibling path (`XML_Parse`) was missing. The same shape exists in `networks/bitcoin/src/wallet/send.rs`: the solvency check `input_sat < (payment_sat + needed_fee)` uses unchecked `u64` addition, while the analogous change-calculation path directly below it correctly uses `checked_sub`. The unchecked sum can wrap, defeating the not-enough-funds check and producing a `SignableTransaction` whose outputs exceed its inputs, which the FROST machines then sign.

### Finding Description
`SignableTransaction::new` sums the requested payments and adds the required fee with plain `u64` arithmetic:

- `payment_sat` is `payments.iter().map(|payment| payment.1).sum::<u64>()` — the sum itself can wrap.
- The solvency gate is `if input_sat < (payment_sat + needed_fee)` — another unchecked addition.
- `needed_fee = fee_per_vbyte * vbytes` — unchecked multiplication.

Each individual payment is only lower-bound-checked (`*amount < DUST` → `DustPayment`); there is no upper bound and no per-payment or sum overflow check. Two payments of roughly `u64::MAX / 2` sat each make `payment_sat` wrap to a small value, so `input_sat < (payment_sat + needed_fee)` is false even though the declared outputs vastly exceed the inputs.

The parallel path one branch below is written correctly: the change calculation uses `input_sat.checked_sub(payment_sat + fee_with_change)` (which silently overflows internally the same way, but `checked_sub` at least rejects when the wrapped `payment_sat + fee_with_change` exceeds `input_sat`). The asymmetry — checked arithmetic in one path, unchecked in the other — is exactly the expat bug class. When `change` is `None` (or when the wrapped sum happens to be smaller than `input_sat`, letting `checked_sub` "succeed"), the function returns `Ok(SignableTransaction)` with `tx_outs` whose total value exceeds `input_sat`. `TransactionMachine`/`TransactionSignMachine` then runs the full FROST protocol and produces threshold signatures over `taproot_key_spend_signature_hash` for this transaction.

### Impact Explanation
The multisig produces valid BIP-340 threshold signatures for a transaction that is consensus-invalid (outputs > inputs, i.e., a negative real fee). Additionally, `SignableTransaction::fee()` computes `sum(inputs) - sum(outputs)` with plain subtraction, so calling `fee()` on the resulting object underflows and returns a garbage wrapped `u64` (or panics in debug builds), corrupting any downstream accounting/reporting that consumes it. This is concrete signing of an unintended message: the threshold group signs a spend no honest participant intended — a TX claiming to pay sums the wallet does not hold — plus incorrect fee reporting. Even though Bitcoin consensus rejects the signed TX, the signature bytes are produced and published, and the wrapped `fee()`/`needed_fee` values feed external balance tracking.

### Likelihood Explanation
Reachability depends on whether payment amounts reaching `SignableTransaction::new` can be attacker-influenced. Withdrawal/payment amounts originate from protocol plans; if any path forwards a user-requested amount without capping it to plausible Bitcoin values (< 21M BTC = 2.1e15 sat), a single request for e.g. `u64::MAX - 1000` sat combined with one more payment wraps `payment_sat`. `fee_per_vbyte` multiplication overflow additionally requires an absurd fee rate. Since `input_sat` cannot realistically exceed ~2.1e15 sat, the `payment_sat + needed_fee` wrap must land below that to bypass the check, which is straightforward to arrange. This requires large-value payment fields to reach the function unvalidated — plausible for a library API but not guaranteed by the upstream pipeline, keeping this at Medium rather than higher.

### Recommendation
Use checked arithmetic consistently in `SignableTransaction::new`:

- Replace `payments.iter().map(|p| p.1).sum::<u64>()` with a checked fold returning `TransactionError::NotEnoughFunds`/`TooMuchData` on overflow.
- Replace `input_sat < (payment_sat + needed_fee)` with `input_sat.checked_sub(payment_sat).and_then(|r| r.checked_sub(needed_fee)).is_none()` or equivalent.
- Use `checked_mul` for `fee_per_vbyte * vbytes` and `fee_with_change`.
- Bound payment amounts to `MAX_MONEY` (21e14 sat) per payment.
- Make `fee()` return `Option<u64>`/`u64` via `checked_sub` so an invalid transaction cannot silently wrap the reported fee.
