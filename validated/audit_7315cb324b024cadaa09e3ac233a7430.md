### Title
EVM transaction sender spoofing via client-supplied `Derived` metadata bypasses ECDSA signature recovery - ([File: x/evm/ante/preprocess.go])

### Summary
`MsgEVMTransaction` carries an optional, wire-serializable `derived` field (`proto/evm/tx.proto:20-23`) that is meant to cache the ECDSA-recovered sender identity (`SenderEVMAddr`, `SenderSeiAddr`, `PubKey`) after the ante pipeline validates a transaction's signature. However, this field is a normal protobuf field that a client can populate directly when constructing the raw transaction bytes submitted via `broadcast_tx`/RPC. The preprocessing and delivery-time signer-resolution code trusts this attacker-supplied field whenever it is already non-nil and has a non-nil `PubKey`, skipping ECDSA signature recovery entirely and using the client-declared `SenderEVMAddr`/`SenderSeiAddr` as the transaction's true signer.

### Finding Description
`x/evm/types/message_evm_transaction.go` `ValidateBasic()` and `app/ante/evm_checktx.go` `EvmStatelessChecks()` only reject a client-supplied `Derived` when its `PubKey` is `nil`: [1](#0-0) [2](#0-1) 

The core signer-recovery routine, `PreprocessUnpacked`, short-circuits with "already preprocessed" as soon as `Derived != nil` and `Derived.PubKey != nil`, without ever recovering the sender from the embedded Ethereum transaction's ECDSA signature: [3](#0-2) 

`EvmDeliverHandleSignatures` (used on the deliver-tx path) has the identical trust pattern — if `msg.Derived != nil` with a non-nil `PubKey`, it takes `msg.Derived.SenderEVMAddr`/`SenderSeiAddr` as-is and associates them, instead of calling `CheckAndDecodeSignature` to derive the real signer from the tx bytes: [4](#0-3) 

The `derived` field is a standard serialized protobuf field (field #2) with no separate authentication, so it is fully attacker-controlled at decode time: [5](#0-4) [6](#0-5) 

This is the same bug class as the Mattermost advisory (CWE-346, Origin Validation Error): a piece of metadata that is supposed to be derived/verified server-side from an authenticated source (in Mattermost, permalink post metadata computed from the referenced post; here, the EVM sender identity computed from the transaction's ECDSA signature) is instead accepted as client-supplied input without independent verification, allowing an attacker to make the system believe an action originated from someone else.

### Impact Explanation
An attacker can craft a `MsgEVMTransaction` where:
- `Data` contains an arbitrary embedded Ethereum transaction (e.g., a token transfer or contract call the attacker wants executed),
- `Derived.SenderEVMAddr` / `Derived.SenderSeiAddr` are set to a victim's addresses,
- `Derived.PubKey` is any well-formed public key (does not need to correspond to the victim at all).

Because `PreprocessUnpacked` and `EvmDeliverHandleSignatures` treat a populated `Derived` as already-verified, the downstream ante pipeline and EVM execution proceed using the victim's addresses as the transaction sender — without ever validating that the embedded transaction was actually signed by the victim's private key. Downstream stages (`x/evm/ante/basic.go` `BasicDecorator`, fee/gas decorators, and eventual EVM execution) consume `msg.Derived.SenderEVMAddr`/`SenderSeiAddr` as the authoritative sender: [7](#0-6) [8](#0-7) 

This can result in unauthorized transfer of a victim's funds/tokens or unauthorized contract interactions performed as the victim — a direct fund-loss / impersonation scenario, reachable by any unprivileged party who can submit a raw transaction to a public RPC endpoint.

### Likelihood Explanation
High. No special privileges, validator collusion, or private keys are required — only the ability to hand-construct a protobuf `MsgEVMTransaction` and submit it through the normal `broadcast_tx` RPC path, which is the same capability every ordinary EVM/Cosmos transaction sender already has.

### Recommendation
Never trust a client-populated `Derived` field. The signer identity (`SenderEVMAddr`, `SenderSeiAddr`, `PubKey`) must always be (re)computed server-side from the actual ECDSA signature over the canonical transaction bytes, regardless of whether `Derived` arrives pre-populated on the wire. Concretely:
- Strip/ignore any `Derived` value present in the raw decoded transaction before ante processing (only allow it to be set internally, after this ante chain performs its own recovery), or
- Always re-verify that `Derived.PubKey` cryptographically corresponds to `SenderEVMAddr`/`SenderSeiAddr` and to a valid signature over `msg.Data`, rejecting the transaction if any mismatch is found, in both `PreprocessUnpacked` (`x/evm/ante/preprocess.go`) and `EvmDeliverHandleSignatures` (`app/ante/evm_delivertx.go`).

### Proof of Concept
1. Construct an `ethtx` payload (e.g., an ERC-20 `transfer` call or native value transfer) with arbitrary/garbage signature bytes — signature validity of this payload is never re-checked once `Derived` is set.
2. Marshal a `MsgEVMTransaction` with:
   - `data`: the above payload wrapped in an `Any`,
   - `derived`: a `derived.Derived` struct with `SenderEVMAddr`/`SenderSeiAddr` set to the victim's addresses and any valid `PubKey` (e.g., the attacker's own public key).
3. Wrap the message in a standard Cosmos `Tx` envelope (per `x/evm/AGENTS.md`, EVM txs bypass normal Cosmos signature checks via the EVM ante router) and submit via `broadcast_tx_sync`/`broadcast_tx_commit`.
4. Observe that `EvmStatelessChecks`/`ValidateBasic` accept the message (since `Derived.PubKey != nil`), `PreprocessUnpacked` short-circuits without ECDSA recovery, and the transaction executes with the victim's address as sender — moving the victim's funds or invoking contracts on their behalf without their signature ever being validated.

func (p *EVMPreprocessDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	msg := evmtypes.MustGetEVMTransactionMessage(tx)
	if err := Preprocess(ctx, msg, p.evmKeeper.ChainID(ctx), p.evmKeeper.EthBlockTestConfig.Enabled); err != nil {
		return ctx, err
	}

	// use infinite gas meter for EVM transaction because EVM handles gas checking from within
	ctx = ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))

	derived := msg.Derived
	seiAddr := derived.SenderSeiAddr
	evmAddr := derived.SenderEVMAddr
	ctx.EventManager().EmitEvent(sdk.NewEvent(evmtypes.EventTypeSigner,
		sdk.NewAttribute(evmtypes.AttributeKeyEvmAddress, evmAddr.Hex()),
		sdk.NewAttribute(evmtypes.AttributeKeySeiAddress, seiAddr.String())))
	pubkey := derived.PubKey
	isAssociateTx := derived.IsAssociate
	associateHelper := helpers.NewAssociationHelper(p.evmKeeper, p.evmKeeper.BankKeeper(), p.accountKeeper)
	_, isAssociated := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if isAssociateTx && isAssociated {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInvalidRequest, "account already has association set")
	} else if isAssociateTx {
		// check if the account has enough balance (without charging)
		if !p.IsAccountBalancePositive(ctx, seiAddr, evmAddr) {
			assocErr := evmtypes.NewAssociationMissingErr(seiAddr.String())
			evmAnteMetrics.associationError.Add(ctx.Context(), 1, otelmetric.WithAttributes(attribute.String("scenario", "associate_tx_insufficient_funds"), attribute.String("type", assocErr.AddressType())))
			return ctx, sdkerrors.Wrap(sdkerrors.ErrInsufficientFunds, "account needs to have at least 1 wei to force association")
		}
		if err := associateHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false); err != nil {
			return ctx, err
		}

		return ctx.WithPriority(antedecorators.EVMAssociatePriority), nil // short-circuit without calling next
	} else if isAssociated {
		// noop; for readability
	} else {
		// not associatedTx and not already associated
		if err := associateHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false); err != nil {
			return ctx, err
		}
		if p.evmKeeper.EthReplayConfig.Enabled {
			p.evmKeeper.PrepareReplayedAddr(ctx, evmAddr)
		}
	}

	// EIP-7702 authorization authorities are distinct accounts from the tx sender, so the
	// sender association above does not cover them. Associate each authority to its true
	// (pubkey-derived) Sei address before EVM execution installs delegation code for it.
	// Otherwise SetCode creates a mutable direct-cast EVM->Sei mapping that a later
	// associatePubKey call can remap, orphaning any staking/distribution state created
	// under the direct-cast identity (which can then halt the chain via the distribution
	// validator-removal hook).
	p.associateAuthorizationAuthorities(ctx, msg, associateHelper)

	return next(ctx, tx, simulate)

// cherrypicked from go-ethereum:txpool:ValidateTransaction
func (gl BasicDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	msg := evmtypes.MustGetEVMTransactionMessage(tx)
	etx, _ := msg.AsTransaction()

	if msg.Derived != nil && !gl.k.EthReplayConfig.Enabled && !gl.k.EthBlockTestConfig.Enabled {
		startingNonce := gl.k.GetNonce(ctx, msg.Derived.SenderEVMAddr)
		txNonce := etx.Nonce()
		if !ctx.IsCheckTx() && !ctx.IsReCheckTx() && startingNonce == txNonce {
			ctx = ctx.WithDeliverTxCallback(func(callCtx sdk.Context) {
				// bump nonce if it is for some reason not incremented (e.g. ante failure)
				if gl.k.GetNonce(callCtx, msg.Derived.SenderEVMAddr) == startingNonce {
					gl.k.SetNonce(callCtx, msg.Derived.SenderEVMAddr, startingNonce+1)
					gl.k.SetNonceBumped(callCtx)
				}
			})
		}
	}
