### Title
Non-canonical Ed25519 point encodings accepted by `read_G` / `GroupEncoding::from_bytes`, bypassing the intended canonical-encoding filter - (File: crypto/dalek-ff-group/src/lib.rs)

### Summary
The `serve` path traversal advisory is a filter-bypass class bug: inputs that were meant to be excluded (paths outside the served root / ignored folders) are reachable through an alternate representation (`../`, relative paths) that the normalization layer accepts as equivalent. The analog in Serai is in the Ed25519 group wrapper: `EdwardsPoint::from_bytes` (reached by `C::read_G`, used in `Commitments::read`, `SchnorrSignature::read`, `DLEqProof::read`, `ReceivedOutput` key handling, and every FROST/Schnorr/DLEq verification path on the `Ed25519` ciphersuite) accepts non-canonical encodings of a point, so byte-strings that a canonical-decoding implementation would reject are "reachable" — they decode to valid in-group points. This is the same shape: an exclusion ("only canonical encodings are valid") is bypassed via an alternate representation of the same object.

### Finding Description
`GroupEncoding for EdwardsPoint` is implemented at `crypto/dalek-ff-group/src/lib.rs` (lines 426-446, instantiated at 470-478) as:

```rust
fn from_bytes(bytes: &Self::Repr) -> CtOption<Self> {
  let decompressed = $DCompressed(*bytes).decompress();
  let point = decompressed.unwrap_or($DPoint::identity());
  CtOption::new(
    $Point(point),
    choice(black_box(decompressed).is_some()) & choice($torsion_free(point)),
  )
}
```

For `EdwardsPoint`, this calls `dalek::edwards::CompressedEdwardsY::decompress()`. That decompressor recovers `x` from `y` and the sign bit by field arithmetic modulo `p` — it does **not** check that the encoded `y` coordinate is a canonical field element (`y < p`). Encodings with `y ≥ p` (non-canonical field elements) are reduced modulo `p` and accepted, and the "negative zero" form (`y = 0` or `y = -1` with the sign bit set, i.e., `x = -0 ≡ 0`) is likewise accepted. The only post-filter applied is `is_torsion_free()`; there is no canonicality check and no rejection of the `-0` encoding.

The contrast with the sibling ciphersuite makes the gap clear: `RistrettoPoint` uses `CompressedRistretto::decompress()`, which enforces canonical, strictly-in-subgroup encodings by construction (the `|_| true` torsion predicate at line 489 is safe precisely because Ristretto encodings are canonical-by-design). `EdwardsPoint` exposes the raw Edwards encoding where canonicality must be enforced explicitly — and isn't.

Reachability: `C::read_G` in `crypto/ciphersuite` reads a 32-byte `Repr` and calls `from_bytes`. Every untrusted-byte entry point enumerated in scope — `Commitments::read` (FROST preprocesses), `EncryptedMessage::read` (PedPoP), `DLEqProof::read`, `SchnorrSignature::read`, `ThresholdKeys::read` — routes through this on the `Ed25519` ciphersuite, and none of them re-check that the bytes they consumed were canonical.

### Impact Explanation
An unprivileged party can submit any point in two (or more) distinct wire encodings — the canonical encoding and a non-canonical `y + p` (or `-0`) encoding — and both are accepted as the same group element. Consequences:

- **Signature/proof malleability on Ed25519**: a valid `SchnorrSignature` or `DLEqProof` whose `R`/`A`/`s`-adjacent points are re-encoded non-canonically still verifies, producing a distinct byte-level artifact for an identical statement. Any downstream system that deduplicates, indexes, or blocklists by raw proof/signature bytes (rather than decoded points) can be bypassed — the direct analog of "explicitly ignored content reachable via relative paths".
- **FROST preprocess/commitment malleability**: `Commitments::read` accepts a non-canonical encoding of a nonce commitment. A participant can rebroadcast a byte-distinct but point-identical preprocess; any preprocess-seen cache keyed on raw bytes (the documented defense against preprocess reuse leading to share recovery) is evaded at the encoding layer, while `commitments.transcript()` re-encodes canonically via `to_bytes()`, so both encodings produce identical binding factors — i.e., the same effective commitment slips past a byte-equality filter.

Severity is Medium: there is no direct key/share recovery or forgery, but it is a real, attacker-reachable canonicality bypass creating malleable artifacts in every Ed25519 verification path.

### Likelihood Explanation
Any party that can feed bytes to `read_G` on Ed25519 — preprocess broadcasts, signature shares, PedPoP messages, DLEq proofs, or Bitcoin-adjacent key material — can produce the alternate encoding by adding `p` to the `y` coordinate (or setting the sign bit on an `x = 0` encoding). It requires no key material and no collusion. Impact is bounded because Serai's internal dedup (HashMaps keyed on `Participant`, transcript commitment via canonical `to_bytes()`) operates on decoded points, so the practical harm is malleability/byte-level filter bypass rather than a break of the signature schemes.

### Recommendation
Enforce canonical decoding in `EdwardsPoint::from_bytes` before decompressing:

1. Reject encodings where `y` is not canonical: compare `bytes` against `decompressed.to_bytes()` and require equality (`point.to_bytes().ct_eq(bytes)`), or check `y < p` explicitly before decompression.
2. Reject the negative-zero form: when `y` decodes with `x = 0`, require the sign bit to be clear (dalek's `decompress` does not do this).
3. Add a regression test asserting `EdwardsPoint::from_bytes` rejects `canonical_encoding` with `y + p` and the `-0` variant, matching Ristretto's behavior.

### Proof of Concept
```rust
use group::GroupEncoding;
use dalek_ff_group::EdwardsPoint;

// Take any valid point, e.g. the generator
let P = EdwardsPoint::generator();
let canonical = P.to_bytes();

// p = 2^255 - 19; set y' = y + p (clearing sign bit manipulation)
// Concretely: the encoding of identity with sign bit set, or:
//   y_bytes canonical | add 0xED... per p reduction.
// Simplest demonstration: identity encoded with x sign bit = 1 ("negative zero").
let mut neg_zero_identity = [0u8; 32];
neg_zero_identity[0] = 1;                    // y = 1  (identity is (0,1))
neg_zero_identity[31] |= 0x80;               // sign bit set -> x = -0
// Both decode to the identity point:
assert_eq!(
  EdwardsPoint::from_bytes(&[1,0,0,.. /* y=1, sign=0 */]).unwrap(),
  EdwardsPoint::from_bytes(&neg_zero_identity).unwrap()   // accepted, same point
);
// And for any point, y + p produces a byte-distinct encoding that
// decompress() reduces mod p and accepts, where a canonical decoder rejects.
```
(The exact `-0`/`y+p` acceptance is inherited from `curve25519-dalek`'s `CompressedEdwardsY::decompress`, which performs field reduction without a canonicality check; Serai's wrapper adds only the torsion filter and does not compensate.)

Caveat: I was unable to fully verify whether any in-scope caller performs byte-level (rather than point-level) deduplication/blocklisting that this bypass concretely defeats; the malleability itself is confirmed by the missing canonicality check, but the severity rests on downstream byte-keyed filters. If none exist in the deployment, this degrades to signature/proof malleability only.
