### Title
Division-by-zero panic in KIP-71 base fee calculation via ungated `Kip71GasTarget=0` governance parameter - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `kc.GasTarget` when the parent block's gas usage differs from the target, but the governance parameter `Kip71GasTarget` has no non-zero format checker (unlike its sibling `Kip71BaseFeeDenominator`, which explicitly rejects zero). If `reward.kip71.gastarget` (or `governance.kip71.gastarget`) is ever set to `0` via a governance vote, every node computing the next Magma/KIP-71 base fee — during header verification, `FeeHistory`/gas-price RPC, and block preparation — divides a `big.Int` by zero, which panics in Go's `math/big` package.

### Finding Description
`NextMagmaBlockBaseFee` reads `gasTarget := kc.GasTarget` directly from the KIP-71 config without any zero-guard: [1](#0-0) 

Compare this to `baseFeeDenominator`, which is defensively defaulted to `64` if zero to "avoid panic": [2](#0-1) 

No equivalent guard exists for `gasTarget`. When `parentGasUsed != gasTarget`, the code computes: [3](#0-2) 
and, symmetrically, for the decreasing-gas-usage branch: [4](#0-3) 

Both branches call `x.Div(x, new(big.Int).SetUint64(gasTarget))`. If `gasTarget == 0`, this is a division by zero, which in Go's `math/big.Int.Div` causes a runtime panic (`division by zero`), not a benign error return — directly analogous to the C-level undefined behavior in ImageMagick's `WaveImage()` from CVE-2021-20309 that this scan is checking for.

The root cause is that the governance parameter definition for `Kip71GasTarget` uses `noopFormatChecker` (i.e., no validation at all), whereas the sibling `Kip71BaseFeeDenominator` explicitly requires `v != 0`: [5](#0-4) 

This means the governance module (`kaiax/gov`) will happily accept and canonicalize a governance vote setting `kip71.gastarget` to `0`, and once such a vote is finalized, the resulting `ParamSet.GasTarget` value of `0` propagates unguarded into `KIP71Config.GasTarget` via `ToKip71Config()`: [6](#0-5) 

`NextMagmaBlockBaseFee` is invoked on the hot path of consensus-critical logic reachable by ordinary block processing (header base-fee verification) and by public RPC (`eth_feeHistory`): [7](#0-6) [8](#0-7) 

### Impact Explanation
Once a `gastarget=0` value is enacted (e.g., via an errant or malicious governance vote passed by the governing node/council), every full node computing the next block's base fee — during block header verification (`VerifyMagmaHeader`), block preparation by the proposer, and any RPC caller invoking `eth_feeHistory`/gas price estimation — hits the same unguarded division and panics identically. Because this triggers deterministically and identically on all nodes processing the same chain state, it functions as a network-wide denial-of-service / consensus halt: nodes crash rather than diverge, but the practical effect is a full chain stop until the software is patched and/or the parameter is manually corrected, satisfying "system availability" impact matching the CVSS 7.5 characterization of the CVE. It also creates a crash-loop risk for public RPC nodes serving `eth_feeHistory` calls if the panic is not recovered at that call site.

### Likelihood Explanation
Reaching this requires that `reward.kip71.gastarget` be set to exactly `0` through the standard governance-vote mechanism. This is a legitimate, in-scope governance parameter (explicitly listed as reachable in the assessment scope) rather than a validator/peer/network attack, and unlike every other numeric KIP-71 parameter that has protective bounds (`Kip71BaseFeeDenominator` explicitly checks `!= 0`), `Kip71GasTarget` has zero validation (`noopFormatChecker`), so nothing in the governance pipeline prevents this value from being proposed and finalized. Because the check is missing entirely (not merely bypassable), likelihood of triggering this bug, whether accidentally through a misconfigured governance proposal or deliberately, is realistic and requires no cryptographic or node-compromise prerequisites.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0`, mirroring the existing checker for `Kip71BaseFeeDenominator`. Additionally, as defense in depth, guard `gasTarget` inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` with the same zero-fallback pattern already used for `baseFeeDenominator`, so that even a pre-existing/legacy misconfigured genesis or config cannot crash node processes.

### Proof of Concept
1. Deploy/govern a Kaia network where `governance.governancemode` allows the governing node to update `reward.kip71.gastarget`.
2. Submit and finalize a governance vote setting `kip71.gastarget` to `0` (currently accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, per `kaiax/gov/param.go` lines 324-334).
3. Once the parameter takes effect at the next epoch, any block with `parentGasUsed != 0` (virtually always true) causes `KIP71Config.NextMagmaBlockBaseFee()` to execute `x.Div(x, new(big.Int).SetUint64(0))` in either the "gas used > target" or "gas used < target" branch (`params/kip71_config.go` lines 99-103 and 118-121).
4. This call panics with `"division by zero"` inside every node's header verification (`VerifyMagmaHeader`) and in the block proposer's header preparation, as well as any public RPC node servicing `eth_feeHistory`, halting block production/verification network-wide.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
