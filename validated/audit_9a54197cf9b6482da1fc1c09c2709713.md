Confirmed: `mapStatus` in `app/src/lib/status-parser.ts` has no explicit `if` branch for `'MM'` or `'MD'` status codes, only a generic fallback at the end that returns `{ kind: 'ordinary', type: 'modified', submoduleStatus }` for any unrecognized code.

### Title
Staged-then-further-changed files (`MM`/`MD` porcelain status codes) are misclassified, causing silent omission of unstaged deletions from the Changes view - ([File: app/src/lib/status-parser.ts])

### Summary
`git status --porcelain=v2 -z` reports a two-character `XY` code where `X` is the index (staged) state and `Y` is the worktree state. `mapStatus` in `app/src/lib/status-parser.ts` explicitly handles a limited set of `XY` combinations (`.M`, `M.`, `.A`, `A.`, `.D`, `D.`, `R.`, `.R`, `C.`, `.C`, `AD`, `AM`, `RM`, `RD`, `DD`, `AU`, `UD`, `UA`, `DU`, `AA`, `UU`), but is missing the extremely common `MM` (staged-modified, then further modified in worktree) and `MD` (staged-modified, then deleted in worktree) combinations. Any unmatched code falls through to a hardcoded fallback that always reports the entry as a plain, non-submodule `modified` file with no index/worktree distinction: [1](#0-0) 

### Finding Description
`mapStatus` is a chain of explicit `if (statusCode === ...)` checks covering only a subset of Git's documented `XY` porcelain codes for ordinary changes: [2](#0-1) [3](#0-2) 

`MM` and `MD` are not among the handled combinations — the code jumps straight to the fallback branch: [1](#0-0) 

`MD` occurs whenever a user stages a modification (`git add`) and subsequently deletes the same file from the working directory before committing — a routine editing sequence (edit → stage → delete/rename via external tool → commit in Desktop). Because the fallback discards the real `index`/`workingTree` distinction and always reports `type: 'modified'`, the entry is passed to `convertToAppStatus` in `app/src/lib/git/status.ts` as `AppFileStatusKind.Modified` instead of reflecting that the working tree copy is gone: [4](#0-3) 

This differs qualitatively from the already-handled `AD` case (added-then-deleted), which the code explicitly special-cases in `buildStatusMap` to be skipped from the changes list entirely because "the file won't be part of the commit": [5](#0-4) 

No equivalent special-casing exists for `MD`, so Desktop's Changes list will show the file as an ordinary "Modified" entry (diffed against the stale on-disk/staged blob) rather than surfacing that the file has actually been deleted from disk. The invariant broken here is: *the Changes list must accurately reflect the true combined index+worktree state so a "Commit" action stages exactly what the user intends*.

### Impact Explanation
If a user stages a change, then a file gets deleted from the worktree (e.g., by an external tool, an IDE auto-format-and-move, a build script, or a git-aware extension), Desktop's UI will report the file as "Modified" rather than as a pending deletion. A user reviewing the Changes list and choosing "Commit All" would then commit based on Desktop's (incorrect) belief about the file's state, which can silently diverge from what the user actually intended to commit/push — the "silent corruption of what the user commits" category. Because Desktop drives the actual `git add`/`git commit` invocation based on this classification, this is not merely a cosmetic UI bug; it can affect what content ends up staged in the resulting commit.

### Likelihood Explanation
`MM`/`MD` are common real-world states — staging a file and then editing or deleting it again before committing is a normal workflow, not a contrived edge case. No attacker interaction is strictly required for the base case, but the report's threat model also covers a controlled remote/tooling scenario: a malicious or compromised pre-existing tool/hook in a cloned repository (e.g., a `post-checkout`/editor plugin invoked as part of normal use) could intentionally leave a tracked file in an `MD` state to make Desktop misreport a deletion as an unrelated "modification," nudging the user toward committing/pushing unintended state. This fits squarely in the allowed threat model (attacker-influenced repository content/tooling causing silent corruption of what the user commits), without requiring local/admin access or social engineering beyond normal repository use.

### Recommendation
Add explicit handling for `MM` and `MD` (and audit for `CM`/`CD` as well) in `mapStatus`, mirroring the pattern already used for `AM`/`AD`/`RM`/`RD`, e.g.:
```ts
if (statusCode === 'MM') {
  return { kind: 'ordinary', type: 'modified', index: GitStatusEntry.Modified, workingTree: GitStatusEntry.Modified, submoduleStatus }
}
if (statusCode === 'MD') {
  return { kind: 'ordinary', type: 'deleted', index: GitStatusEntry.Modified, workingTree: GitStatusEntry.Deleted, submoduleStatus }
}
```
Additionally, replace the silent fallback at the end of `mapStatus` with a hard failure (`fatalError`/thrown exception, as is already done in the sibling `getIndexStatus` function in `app/src/lib/git/diff-index.ts`) so any future unhandled code is caught in testing rather than silently misreported to the user.

### Proof of Concept
1. In a Desktop-managed repository, modify `foo.txt` and stage it (`git add foo.txt`), producing index state `M`.
2. Without committing, delete `foo.txt` from the working directory (`rm foo.txt`), producing worktree state `D`. `git status --porcelain=v2` now reports `MD foo.txt`.
3. Open the repository in GitHub Desktop and view the Changes list — the file is expected to show as "Deleted" (or a clear staged-modified/worktree-deleted combined state) but, per the code path traced above, falls through to the generic fallback in `mapStatus` (`app/src/lib/status-parser.ts:420-426`) and is reported as `AppFileStatusKind.Modified`.
4. Selecting "Commit All" commits based on this incorrect classification, silently diverging from the actual intended working-directory state (the deletion is not properly reflected in what gets committed). [6](#0-5) [7](#0-6)

function convertToAppStatus(
  path: string,
  entry: FileEntry,
  conflictDetails: ConflictFilesDetails,
  oldPath?: string
): AppFileStatus {
  if (entry.kind === 'ordinary') {
    switch (entry.type) {
      case 'added':
        return {
          kind: AppFileStatusKind.New,
          submoduleStatus: entry.submoduleStatus,
        }
      case 'modified':
        return {
          kind: AppFileStatusKind.Modified,
          submoduleStatus: entry.submoduleStatus,
        }
      case 'deleted':
        return {
          kind: AppFileStatusKind.Deleted,

function buildStatusMap(
  files: Map<string, WorkingDirectoryFileChange>,
  entry: IStatusEntry,
  conflictDetails: ConflictFilesDetails
): Map<string, WorkingDirectoryFileChange> {
  const status = mapStatus(
    entry.statusCode,
    entry.submoduleStatusCode,
    entry.renameOrCopyScore
  )

  if (status.kind === 'ordinary') {
    // when a file is added in the index but then removed in the working
    // directory, the file won't be part of the commit, so we can skip
    // displaying this entry in the changes list
    if (
      status.index === GitStatusEntry.Added &&
      status.workingTree === GitStatusEntry.Deleted
    ) {
      return files
    }
  }

  if (status.kind === 'untracked') {
    // when a delete has been staged, but an untracked file exists with the
    // same path, we should ensure that we only draw one entry in the
    // changes list - see if an entry already exists for this path and
    // remove it if found
    files.delete(entry.path)
  }

  // for now we just poke at the existing summary
  const appStatus = convertToAppStatus(
    entry.path,
    status,
    conflictDetails,
    entry.oldPath
  )

  const initialSelectionType =
    appStatus.kind === AppFileStatusKind.Modified &&
    appStatus.submoduleStatus !== undefined &&
    !appStatus.submoduleStatus.commitChanged
      ? DiffSelectionType.None
      : DiffSelectionType.All

  const selection = DiffSelection.fromInitialSelection(initialSelectionType)

  files.set(
    entry.path,
    new WorkingDirectoryFileChange(entry.path, appStatus, selection)
  )
  return files
}
