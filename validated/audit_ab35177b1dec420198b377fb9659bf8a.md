Based on the evidence gathered, the closest verifiable Desktop analog concerns insufficiently-gated re-enablement of Git's `file://` submodule protocol, which mirrors the CometBFT bug class (missing validation of an attacker-influenceable parameter that controls a sensitive protocol/consensus path).

### Title
Submodule checkout re-enables `protocol.file.allow=always`, letting an attacker-controlled `.gitmodules` pull arbitrary local paths into the working tree - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` accepts a boolean `allowFileProtocol` flag that, when true, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation, unconditionally overriding Git's own hardening (the `protocol.file.allow=user`/disabled-by-default behavior shipped after CVE-2022-39253) for every submodule declared in that repository's `.gitmodules`, regardless of what URL scheme each individual submodule uses.

### Finding Description
`.gitmodules` (and therefore each submodule's `url`) is repository content — fully attacker-controlled once a user clones or checks out a branch/PR from an untrusted source. Git upstream deliberately disabled `file://`/bare local-path submodule URLs by default specifically because a malicious `.gitmodules` could otherwise be used to have Git read/copy arbitrary local paths into the working tree during `submodule update --init`. GitHub Desktop's `updateSubmodulesAfterOperation` re-enables this exact capability wholesale via `protocol.file.allow=always`: [1](#0-0) 
This flag is threaded through `checkoutBranch` and `checkoutCommit` as a plain boolean parameter defaulting to `false`, with no validation that ties the decision to allow `file://` protocol to the actual content of the `.gitmodules` file being processed: [2](#0-1) [3](#0-2) 
Because the flag is applied at the whole-command level (`-c protocol.file.allow=always` for the entire `submodule update --init --recursive` invocation) rather than scoped per-submodule-URL, any code path that sets `allowFileProtocol = true` for a legitimate reason (e.g., the parent repository itself was cloned via a local/file path) will also silently authorize *every other* submodule entry in `.gitmodules` to use `file://`/local-path URLs — including ones injected by a malicious branch or fork the user checks out. This is structurally the same class of flaw as GHSA-qr8r-m495-7hc4: a security-relevant parameter (there, consensus params like block size bounds; here, allowed submodule transport) is derived/gated too coarsely and applied to untrusted, attacker-supplied structured data without per-field validation.

### Impact Explanation
If `allowFileProtocol` is true during any checkout/pull that runs `updateSubmodulesAfterOperation` on a repository whose `.gitmodules` was supplied or modified by an untrusted party (fork, PR branch, or spoofed remote content), Git will happily "clone" a submodule from a local filesystem path such as the user's home directory, `AppData`, or any other path the Desktop process can read — copying that data into the repository's working tree. This creates disk content outside what the legitimate remote intended, which the user may then stage, commit, and push (exfiltrating local files to whatever remote they push to), satisfying the "file read outside the repo" / "silent corruption of what the user commits or pushes" impact criteria.

### Likelihood Explanation
Exploitability depends entirely on when the app actually sets `allowFileProtocol = true` for `checkoutBranch`/`checkoutCommit` on a repository containing untrusted `.gitmodules` content (e.g., after checking out a PR/fork branch). I was not able to trace all call sites in `app/src/lib/stores/app-store.ts` and `app/src/ui/dispatcher/dispatcher.ts` within the available investigation to confirm the exact gating condition used to decide `allowFileProtocol`, so I cannot confirm with certainty whether existing UI/store logic already restricts this to safe cases (e.g., only enabling it when the parent remote itself is a local/file path that the user explicitly trusts). This is a material gap in my analysis — it should be resolved by inspecting those call sites directly.

### Recommendation
- Scope `protocol.file.allow` decisions per submodule URL (parse `.gitmodules`/`submodule.<name>.url` and only allow `file://`/local paths for submodules whose URL was not introduced by untrusted content), rather than toggling a single command-wide flag.
- Audit all callers of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is never derived from or applied to content that originates from an untrusted fork/PR/remote.
- Consider defaulting to Git's native protections (leave `protocol.file.allow` unset) and only opt in with an explicit user confirmation dialog naming the specific local path Git intends to access.

### Proof of Concept
Conceptual (not fully verified against caller gating logic, see Likelihood Explanation):
1. Attacker publishes a fork/branch whose `.gitmodules` contains `url = file:///Users/victim/Documents/secret` (or `C:\Users\victim\AppData\...` on Windows).
2. Victim, using GitHub Desktop, checks out this branch/PR in a context where `allowFileProtocol` ends up `true` for the checkout (exact trigger unconfirmed).
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, causing Git to copy the contents of `/Users/victim/Documents/secret` into the submodule directory inside the repository working tree.
4. The victim's local, sensitive files now appear as new/added content in Desktop's changes view, and if committed and pushed, are exfiltrated to whatever remote the victim pushes to. [4](#0-3)

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
