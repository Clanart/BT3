### Title
`register()` full-overwrite resets `claimed` to zero, letting a beneficiary front-run re-registration to double-claim vested tokens - (File: `rewards/MGPRelease.sol`)

### Summary
`MGPRelease.register()` unconditionally overwrites `beneficiaries[_addresses[i]]` with a fresh `Vesting` struct that resets `claimed` to `0`, without ever accounting for tokens already paid out to that address. Any already-registered beneficiary can watch the mempool for a legitimate re-registration transaction targeting their own address (e.g. an allocation top-up/correction, a normal operational action, not requiring malicious intent) and sandwich it with `claim()` calls to be paid twice for the same vested period from the shared `tokenToRelease` balance.

### Finding Description
`register()` writes:
```solidity
beneficiaries[_addresses[i]] = Vesting({
    totalAlloced: _amounts[i],
    claimed: 0,
    revoked: false
});
``` [1](#0-0) 
This is a full struct overwrite, so any prior `claimed` value tracked from that address's earlier `claim()` calls is discarded, regardless of how many tokens were already transferred out via `IERC20(tokenToRelease).safeTransfer(msg.sender, claimable)` in `claim()`. [2](#0-1) 

Exploit flow for a beneficiary who is already registered and expects a future re-registration (e.g. a top-up):
1. Beneficiary observes a pending `register()` transaction in the mempool that will re-register their address (a normal admin action to add/adjust allocation, not an admin attack).
2. Beneficiary front-runs it with `claim()`, receiving `claimable` tokens computed from `getClaimable()` against the *old* `totalAlloced`, and `vesting.claimed` is incremented accordingly. [3](#0-2) 
3. The pending `register()` transaction executes, resetting `claimed` to `0` while setting a new `totalAlloced`.
4. Beneficiary immediately calls `claim()` again. Since `claimed` is now `0`, `getClaimable()` recomputes the full vested-to-date amount (linear vesting based on elapsed time from `startTimestamp`) with no deduction for the tokens already paid in step 2, and transfers that amount again.

The `nonReentrant` modifier on `claim()` prevents reentrancy within a single call but does nothing to stop this two-transaction, cross-block (or same-block ordering) sequence of legitimate calls. There is no check in `register()` that preserves or nets out previously distributed amounts.

### Impact Explanation
Each time the owner performs a routine re-registration (e.g., correcting or increasing an allocation) for an address that has already claimed, that beneficiary can double-claim their previously vested tranche. This drains `tokenToRelease` balance held by the contract beyond what is owed, directly causing **protocol insolvency**: other legitimate beneficiaries may later find `withdrawDust`/their own `claim()` calls under-funded because tokens meant for their vesting schedule were already drained by the double-claimer. This is a direct, quantifiable loss of principal from the shared token pool.

### Likelihood Explanation
This requires no privileged role from the attacker — they only need to be a beneficiary already holding a nonzero `claimed` balance and to react to a publicly visible pending `register()` transaction (mempool front-running), which is a well-established, cheap, repeatable technique. It does not depend on the owner being malicious — routine re-registration (e.g. adjusting/topping up allocations for the same set of addresses) is a foreseeable normal operational flow given `register()` has no guard against being called twice for the same address. The bug is purely in the contract's accounting logic, triggerable opportunistically by any registered address.

### Recommendation
Change `register()` to not blindly reset `claimed`: either (a) disallow re-registration of an address that already has a nonzero `claimed`/`totalAlloced` unless explicitly intended, or (b) when updating an existing beneficiary, only update `totalAlloced` while preserving the existing `claimed` value, e.g.:
```solidity
Vesting storage v = beneficiaries[_addresses[i]];
v.totalAlloced = _amounts[i];
// keep v.claimed as-is
```
Add invariant checks (e.g., new `totalAlloced` must be >= existing `claimed`) so vesting math cannot go negative or allow re-claim of already-paid amounts.

### Proof of Concept
Hardhat test plan:
1. Deploy `MGPRelease` with `startTimestamp = now`, `endTimestamp = now + 1000`, `initialUnlockPercentage = 0`, mint/transfer sufficient `tokenToRelease` to the contract.
2. Owner calls `register([alice], [1000e18])`.
3. Advance time to `startTimestamp + 500` (50% vested). Alice calls `claim()` and receives `500e18`; assert `beneficiaries[alice].claimed == 500e18` and Alice's token balance increased by `500e18`.
4. Owner submits `register([alice], [2000e18])` (simulating a legitimate top-up) — in the test, simply call it directly to demonstrate the reset (mempool front-run timing is simulated by ordering calls in the same test).
5. Immediately after, Alice calls `claim()` again at the same timestamp. Assert `getClaimable()` now returns `1000e18` (50% of new `totalAlloced` minus `claimed=0`), and Alice's cumulative received tokens are `500e18 + 1000e18 = 1500e18`, exceeding the `500e18` she should have net-received relative to a correctly-updated allocation that accounts for prior claims.
6. Assert contract's `tokenToRelease` balance is reduced by the double-claimed amount beyond what a correct accounting model would allow, demonstrating insolvency risk for other beneficiaries sharing the same token pool.

    function getClaimable(address _account) public view returns (uint256 claimable) {
        Vesting storage vesting = beneficiaries[_account];
        uint256 initialUnlockedAmount = vesting.totalAlloced * initialUnlockPercentage / denominator;

        if (block.timestamp <= startTimestamp)
            return  initialUnlockedAmount - vesting.claimed;

        if (block.timestamp >= endTimestamp)
            return vesting.totalAlloced - vesting.claimed;

        uint256 needVesting = vesting.totalAlloced - initialUnlockedAmount;
        uint256 vested = (((block.timestamp - startTimestamp) * needVesting) / (endTimestamp - startTimestamp));

        claimable = (initialUnlockedAmount + vested - vesting.claimed);
    }    
```

        Vesting storage vesting = beneficiaries[msg.sender];
        if (vesting.revoked)
            revert AccountRevoked();

        IERC20(tokenToRelease).safeTransfer(msg.sender, claimable);

    }
