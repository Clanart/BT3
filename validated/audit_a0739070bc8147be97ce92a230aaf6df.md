## Title
Truncating CW bech32 address strings to 20 bytes for the EVM pointer reverse-registry key allows cross-pointer collisions and pointer-registration state confusion - (File: x/evm/keeper/pointer.go)

### Summary
The Angular advisory describes a class of bug where semantically distinct request inputs are serialized into identical cache-key material, causing one entity's data to be silently substituted for another's. The closest reachable analog in sei-chain is in the CW↔EVM pointer registry: when registering a CW20/CW721/CW1155 pointer for an ERC20/721/1155 contract, the reverse-lookup key is derived by truncating the bech32 **string** representation of the CW address down to `common.Address`'s 20 bytes via `common.BytesToAddress([]byte(addr))`, rather than using the canonical 20-byte `AccAddress` payload.

### Finding Description
`SetCW20ERC20PointerWithVersion`, `SetCW721ERC721PointerWithVersion`, and `SetCW1155ERC1155PointerWithVersion` store the reverse pointer mapping keyed by: [1](#0-0) 
`common.BytesToAddress([]byte(addr))`, where `addr` is the CW contract's bech32 **address string** (e.g. `"sei1..."`, typically ~44 ASCII bytes), not the raw 20-byte account payload. Go-ethereum's `common.BytesToAddress` right-aligns and truncates its input to the last 20 bytes when the input is longer, so this operation discards most of the string and keeps only its last 20 ASCII characters as the "address" used for the reverse-registry key: [2](#0-1) 
`cwAddressIsPointer` and `evmAddressIsPointer` gate `ErrorPointerToPointerNotAllowed` using this same truncated/derived key: [3](#0-2) 
Because the key space collapses a full bech32 string (which is unique per contract, checksummed, and effectively unbounded in information content relative to 20 bytes) down to only its last 20 ASCII bytes, two different, syntactically-valid CW contract addresses (owned/controlled by different, unrelated wasm contracts deployed by any user) can end up mapping to the same `PointerReverseRegistryKey`. This mirrors the Angular bug class: distinct, semantically different inputs are reduced to identical "key material," so one entity's reverse-pointer record can be read, overwritten, or spoofed as if it belonged to another.

### Impact Explanation
If an attacker (any CosmWasm user, since they fully control the salt/instantiate parameters that determine a wasm contract's resulting bech32 address) can find or influence a CW20/CW721/CW1155 contract address whose last 20 ASCII bytes match those of a victim CW address already registered as a pointer, they can:
- Trigger `ErrorPointerToPointerNotAllowed` false positives/negatives, blocking or permitting pointer registration in unintended ways.
- Overwrite the reverse-registry entry for the victim's pointer, corrupting `evmAddressIsPointer`/`cwAddressIsPointer` checks used elsewhere in the EVM/pointer bridge to gate pointer-to-pointer creation and possibly other pointer/pointee resolution logic (`GetCW20Pointee`, `GetERC20Pointee`, etc., in the same file), which are reachable via the public `RegisterPointer` EVM precompile message path.
- This is a `x/evm` module (bank/pointer bridge) state-poisoning class of bug affecting CW↔EVM pointer bookkeeping reachable by any user submitting a `MsgRegisterPointer` or the pointer precompile's `AddCW20`/`AddCW721`/`AddCW1155` calls.

### Likelihood Explanation
Exploitability is bounded by the difficulty of generating a CosmWasm contract address whose **bech32 string's last 20 ASCII bytes** collide with a target's. Bech32 addresses are checksummed, so finding an exact 20-ASCII-byte tail collision for an arbitrary target is a non-trivial (though not cryptographically infeasible — 20 bytes of ASCII, i.e. a birthday-bound search over a printable/bech32-charset alphabet) search problem; a user can grind wasm instantiate salts to influence the resulting contract address until the tail matches. This makes the issue realistically exploitable with computational effort by a motivated, unprivileged CosmWasm user, but not trivial to trigger accidentally.

### Recommendation
Use the canonical 20-byte `AccAddress.Bytes()` payload (or a full, unambiguous encoding, e.g. length-prefixed) rather than truncating the bech32 string representation when constructing `PointerReverseRegistryKey` for CW-address-keyed pointer types. Ensure `SetCW20ERC20Pointer`, `SetCW721ERC721Pointer`, `SetCW1155ERC1155Pointer`, `DeleteCW20ERC20Pointer`, `DeleteCW721ERC721Pointer`, `DeleteCW1155ERC1155Pointer`, `cwAddressIsPointer`, and any other caller passing a CW address string into `common.BytesToAddress` are updated consistently, and add a regression test asserting that two distinct valid bech32 addresses sharing the same last-20-byte ASCII tail cannot collide in the reverse registry.

### Proof of Concept
Conceptual (cannot be fully executed without live chain access):
1. Deploy/instantiate a CosmWasm CW20 contract `A` at bech32 address `sei1AAAA...XYZ01234567890123456789` and register it as an ERC20 pointer via `MsgRegisterPointer`/`AddCW20`, populating `PointerReverseRegistryKey(common.BytesToAddress([]byte("sei1AAAA...XYZ01234567890123456789")))`.
2. Grind wasm instantiate `salt`/`admin` parameters (or brute force redeploy attempts) to obtain a second, unrelated CW20 contract `B` whose bech32 address string shares the same last 20 ASCII characters as `A`'s address string (`common.BytesToAddress` truncates to those last 20 bytes).
3. Register `B` as a pointer; observe that `PointerReverseRegistryKey` for `B` collides with `A`'s entry, causing `evmAddressIsPointer`/`cwAddressIsPointer` and pointee-resolution calls (`GetCW20Pointee`) to return `A`'s data for `B` or vice versa, or causing `ErrorPointerToPointerNotAllowed` to incorrectly fire/not fire.

Note: I was not able to fully verify computational feasibility of the collision search or confirm downstream consumers of `evmAddressIsPointer`/`GetCW20Pointee` beyond what's shown in `x/evm/keeper/pointer.go`; a Devin session with full repository and test-execution access would be needed to construct and run a concrete end-to-end PoC and assess exact severity of downstream consumers.

func (k *Keeper) SetCW20ERC20PointerWithVersion(ctx sdk.Context, erc20Address common.Address, addr string, version uint16) error {
	if k.evmAddressIsPointer(ctx, erc20Address) {
		return ErrorPointerToPointerNotAllowed
	}
	err := k.setPointerInfo(ctx, types.PointerCW20ERC20Key(erc20Address), []byte(addr), version)
	if err != nil {
		return err
	}
	return k.setPointerInfo(ctx, types.PointerReverseRegistryKey(common.BytesToAddress([]byte(addr))), erc20Address[:], version)
}
