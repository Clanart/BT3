## Analysis

The Sherlock report's underlying pattern is: **a security-critical protection can be silently disabled/bypassed, allowing an attacker-supplied object (there: an ERC20 approval; here: a cloned repository) to cause unauthorized state changes**. Translating "attacker controls the operand that a security check is supposed to gate" into GitHub Desktop, the strongest local-code analog is the explicit disabling of Git's own clone-time symlink/embedded-repo protection. [1](#0-0) 

### Title
Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard is explicitly disabled during clone, re-exposing local-clone symlink file write/read outside the destination repo - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` in [2](#0-1)  builds the environment for every `git clone` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. This is the internal Git environment variable used by Git's `clone.c` protections that were added to remediate local (file:// / same-filesystem) clone vulnerabilities such as CVE-2022-39253, where a maliciously crafted repository can contain symlinks (or nested `.git` directories/hardlinks) that, when followed during a local clone, cause Git to read or write files outside of the intended destination directory. Forcing this protection off means Desktop's clone path is not merely "unpatched" — it actively re-enables the vulnerable behavior on every clone, regardless of the installed Git version's default posture.

### Finding Description
Desktop constructs the clone environment by merging `envForRemoteOperation(url)` with a hard override: [1](#0-0) 
No other git operation file in the codebase (`fetch.ts`, `pull.ts`, `push.ts`, `checkout.ts`, `branch.ts`, `remote.ts`, `revert.ts`, `submodule.ts`, `tag.ts`) sets this variable — it is unique to `clone.ts`, confirming it is a deliberate override rather than a shared default.

The function does add a defense against a different attack (clone destination path traversal) via `isClonePathSensitive()` [3](#0-2) , but that check only inspects the *destination* path argument supplied by Desktop's own UI — it does nothing to prevent a malicious *source* repository's contents (symlinks placed inside the repo being cloned) from escaping the destination directory once Git's own protection is turned off.

This directly matches the "attacker controls a cloned/fetched repository" primitive called out as valid impact: an attacker who can get a user to clone or open a crafted repository (e.g. via the `open-repository-from-url` deep-link action handled in `dispatcher.openOrCloneRepository`, itself reachable via `parseAppURL`/`dispatchURLAction` [4](#0-3) ) can embed symlinks that, once the built-in Git guard is disabled, let the clone operation write or overwrite files outside the intended repository working directory.

### Impact Explanation
If the disabled protection is exploitable on the user's Git version, cloning a malicious repository (via the normal "Clone repository" URL, drag-and-drop, or an `x-github-client://openRepo/...` deep link) can result in file writes or reads outside the clone destination — potentially clobbering files elsewhere on disk or exfiltrating file contents through crafted symlinks, without any unusual user action beyond cloning a repository or clicking a link, both explicitly listed as legitimate Desktop attack surfaces.

### Likelihood Explanation
The unsafe path directly opposes the effort Git upstream took to guard against this class of bug by default; Desktop actively re-enables the vulnerable behavior on every single clone call, so the likelihood of triggering the unsafe code path is 100% whenever a clone happens — the only open variable is whether the currently bundled/system Git version still contains the underlying symlink-following behavior that the flag was designed to suppress, which I could not verify from the indexed files alone (Git version pinning/bundling config was not found in the reachable code).

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in [1](#0-0)  (or set it to `'true'`/leave it unset) so Git's built-in clone-time symlink/embedded-repository protections remain active, and add a regression test asserting the clone environment never disables this flag.

### Proof of Concept
1. Craft a malicious Git repository whose tree contains a symlink (e.g. `evil -> ../../../../.ssh`) positioned so that, when locally cloned with the built-in Git protection active, Git would normally refuse/neutralize the checkout of that entry.
2. Host this repository and have the victim clone it in Desktop, either directly through the "Clone repository" dialog or via an `x-github-client://openRepo/<repo-url>` deep link handled by `parseAppURL`/`dispatchURLAction`.
3. Desktop invokes `clone()` [5](#0-4) , which sets `GIT_CLONE_PROTECTION_ACTIVE=false` in the child process environment, disabling Git's guard for this specific clone.
4. Depending on the installed Git version's underlying symlink handling, the crafted entry follows the symlink outside the destination directory during checkout, resulting in file read/write outside the cloned repo path — exactly the "attacker controls a cloned repository → file write/read outside the repo" impact class.

I was not able to fully confirm from the indexed source alone which Git version ships with Desktop or whether that version's default (non-overridden) behavior would actually be exploitable without this override; a Devin session with full repository/checkout access would be needed to verify the bundled Git version and reproduce the symlink escape end-to-end.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
