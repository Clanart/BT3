## Title
Silent, Unconfirmed Remote URL Rewrite From GitHub API Data Can Redirect Pushes/Credentials to an Attacker-Controlled Endpoint - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a repository's `origin` remote URL using data fetched from the GitHub API, with no user confirmation and with a validation check (`protocolsMatch`) that only compares URL *scheme*, not host/owner/name. This mirrors the seed report's broken invariant: a value that controls where "value" (funds in the C4 report, git operations/credentials in Desktop) flows is mutated based on an externally-sourced input without a bound/allow-list check, and the change is applied silently.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` every time GitHub Desktop refreshes a repository's association with the GitHub API (repository selection, background fetch, account-change refresh, etc.): [1](#0-0) 

The function itself: [2](#0-1) 

The gating logic is:
- `remoteUrlUnchanged`: the *current* local remote still matches the *previously cached* `gitHubRepository.cloneURL` (via `urlMatchesRemote`, which does check hostname/owner/name) — this is meant to ensure the user hasn't manually customized the remote.
- `protocolsMatch`: only compares `https:` vs `ssh:`/`https:` scheme strings, **not** hostname, owner, or repo name.
- `!urlsMatch`: the new `apiRepo.clone_url` differs from the current remote.

If all three hold, `gitStore.setRemoteURL()` is called immediately, with no dialog, confirmation, or diff shown to the user — this directly performs `git remote set-url origin <url>`: [3](#0-2) 

Because `apiRepo` comes from `api.fetchRepository(owner, name)` — live data from GitHub for whatever repository the local `owner/name` currently resolves to — any legitimate scenario that changes what `owner/name` points to at the API level (e.g., a repository/account rename or transfer) will cause the local `origin` to be silently repointed to whatever `clone_url` the API now returns, on an arbitrary host, with no cross-check that the new remote is even related to the same GitHub host/owner the user originally trusted. This is the direct analog of `RoyaltyVault.setPlatformFee`: a privileged/automatic write path exists, the bound check (`platformFee < MAX_FEE` in the seed / hostname+owner equality here) is missing, and the corrupted value (`platformFee` → local `origin` remote URL) silently redirects where "value" goes.

### Impact Explanation
Once `origin` is silently repointed:
- Future `git push` operations sent by the user go to the attacker/unexpected endpoint instead of the URL the user believes they're pushing to — this is "silent corruption of what the user commits or pushes."
- Because credential resolution in Desktop's trampoline is endpoint-based (`getCredentialUrl`/`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts`), a remote pointed at a different host can also change which credential/account gets offered for authentication, and for a generic (non-GitHub) endpoint, this can route Basic Auth/token material to the attacker's host via `getExternalCredential`/`getGenericCredential`.
- The rewrite happens automatically during routine background refreshes without any explicit user action being required, satisfying the "unprivileged, no local access" requirement.

### Likelihood Explanation
`repositoryWithRefreshedGitHubRepository` runs opportunistically and frequently (repository selection, background fetch cycles, account changes), so the window for this to fire is large. The only precondition is that the GitHub API begins returning a different `clone_url` for the `owner/name` pair Desktop still associates with the repository — which is not equivalent to local/physical access, admin rights, or leaked credentials, and doesn't require unnatural user interaction.

### Recommendation
- Do not silently call `setRemoteURL`; require explicit user confirmation (a popup similar to other destructive/consequential Desktop actions) before changing an existing remote's URL based on API data.
- Strengthen the check from scheme-only `protocolsMatch` to a full identity check (hostname at minimum, ideally reusing `urlMatchesRemote`-style hostname compare) between the old and new URL before ever considering an automatic rewrite, and only allow automatic updates when the hostname is unchanged (i.e., only owner/name changed on the same GitHub endpoint).
- Log/telemetry and surface a visible notification whenever this kind of remote URL change happens so users can detect unexpected redirection.

### Proof of Concept
1. User has repository `X` cloned with `origin = https://github.com/owner/repo.git`, and Desktop's DB has `gitHubRepository.cloneURL = https://github.com/owner/repo.git`.
2. Through an account/repo-level change on GitHub (e.g., owner renames their account after the app's cached mapping was set up, or the repo is transferred), `api.fetchRepository('owner', 'repo')` starts returning `clone_url: https://github.com/attacker-controlled/repo.git` for that same owner/name lookup.
3. On next `repositoryWithRefreshedGitHubRepository` call (background fetch, or simply reselecting the repo tab):
   - `remoteUrlUnchanged` is true (local remote still matches cached `cloneURL`).
   - `protocolsMatch` is true (`https:` === `https:`), regardless of host/owner differing.
   - `!urlsMatch` is true (the new URL differs).
   - `gitStore.setRemoteURL('origin', 'https://github.com/attacker-controlled/repo.git')` executes with zero user confirmation.
4. All subsequent pushes/fetches for `origin` now target the attacker-controlled repository/host. [4](#0-3)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export async function setRemoteURL(

  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
