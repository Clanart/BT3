## Analog Identified: `order.fees` (solver/settlement fee) is charged in full at placement but never refunded on cancellation, despite being escrowed in `_orders[commitment][TRANSACTION_FEES]`

### Title
Solver/settlement fee (`order.fees`) is permanently forfeited on order cancellation instead of being refunded - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
This is the same bug class as the Sablier report: a fee is collected in full, upfront, at creation time, and is not returned/pro-rated when the position is cancelled before completion. In `IntentGatewayV2.placeOrder`, the full `order.fees` amount is pulled from the user immediately and recorded under the sentinel key `TRANSACTION_FEES` in the `_orders[commitment]` mapping. [1](#0-0)  When the order is later cancelled, the cancel paths (`_cancelSameChain` and the destination cancel handler in `ExtrinsicIntents.sol`) build the `WithdrawalRequest.tokens` array from `order.inputs` only — the `TRANSACTION_FEES` entry is never included, so it is never returned to the user.

### Finding Description
`placeOrder` collects `order.fees` in the fee token (or swaps native for it) and stores it under the reserved `TRANSACTION_FEES` slot inside the same per-commitment escrow map used for the order's real input tokens: [1](#0-0) 

When a same-chain order is cancelled, `_cancelSameChain` iterates only over `order.inputs` to build the refund list: [2](#0-1) 

`TRANSACTION_FEES` is a separate key in the same `_orders[commitment]` mapping and is not part of `order.inputs`, so it is excluded from `remainingTokens` and from the `WithdrawalRequest` passed to `_withdraw`. The same pattern occurs in the cross-chain destination cancel path, which also builds its `WithdrawalRequest` strictly from `order.tokens`/`order.inputs`: [3](#0-2) 

The project's own documentation states the intended behavior is that `order.fees` **is** refunded on cancellation ("`order.fees` solver/settlement fee | Refunded to `order.user` when the refund finalizes on the source chain"), distinguishing it from the protocol fee/dust, which is explicitly documented as non-refundable. [4](#0-3)  The on-chain cancel logic does not implement this: the fee remains locked in `_orders[commitment][TRANSACTION_FEES]` with no code path (visible in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`) that clears or returns it during cancellation, matching exactly the Sablier pattern of an upfront, non-refundable fee charge that becomes especially harmful on early/immediate cancellation (e.g., a user cancelling right after placement due to a mistaken parameter).

### Impact Explanation
This causes a guaranteed, permanent loss of user funds equal to `order.fees` on every cancelled order (same-chain or cross-chain), even though the protocol advertises this amount as refundable. Unlike the protocol fee (explicitly documented "dust," intentionally non-refundable), this fee is meant to go to the solver only upon a successful fill; on cancellation there is no fill, so retaining it is an unintended value transfer away from the rightful beneficiary (the user) with no beneficiary receiving it (it becomes stuck/unaccounted-for balance in the gateway contract). This matches the bounty's "loss of funds" / "wrong beneficiary or amount" impact class.

### Likelihood Explanation
High likelihood: this triggers on the default, unprivileged cancellation flow available to any order owner (`_cancelSameChain` requires only `order.user == msg.sender`; the cross-chain destination path is user-callable before deadline and public after). No malicious relayer, prover, or governance actor is required — any user who places an order with `order.fees > 0` and then cancels it (for any reason, including immediately after placement) loses the fee permanently.

### Recommendation
Include the `TRANSACTION_FEES` escrow entry in the `WithdrawalRequest.tokens` array (using the fee token address) for both `_cancelSameChain` and the cross-chain cancel paths (`_cancelFromDest`, and the corresponding source-side refund flow), and clear `_orders[commitment][TRANSACTION_FEES]` after refunding, mirroring how `order.inputs` escrow is refunded. Alternatively, explicitly document and clearly disclose (front-end warnings, SDK guards) that `order.fees` is forfeited on cancellation, and reconcile the documentation in `cancelling-orders.mdx` with actual contract behavior.

### Proof of Concept
1. User calls `placeOrder` with `order.fees = X` (feeToken), and `msg.value = 0`; `X` is transferred from the user and stored at `_orders[commitment][TRANSACTION_FEES] = X`. [1](#0-0) 
2. Before any solver fills the order, the user calls `cancelOrder` (same-chain path) — this routes to `_cancelSameChain`. [5](#0-4) 
3. `_cancelSameChain` computes `remainingTokens` strictly from `order.inputs`, omitting the `TRANSACTION_FEES` slot, and calls `_withdraw` with only those tokens. [2](#0-1) 
4. The user's escrowed input tokens are refunded, but the `X` fee tokens remain locked in the contract at `_orders[commitment][TRANSACTION_FEES]` indefinitely, with no subsequent function shown in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol` that sweeps or returns it to the user.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
