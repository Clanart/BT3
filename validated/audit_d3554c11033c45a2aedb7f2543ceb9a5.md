## Finding [1](#0-0) 

### Title
Path-containment check in `resolveWithin` accepts sibling directories via string-prefix matching, allowing deep-link/conflict-path escape from the intended repository root - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin` (and its POSIX/Win32 variants) is the single guard GitHub Desktop uses to validate that an attacker- or repository-supplied relative path stays inside a trusted root directory before it is used to read a file or reveal it in the OS shell. The final containment check compares the resolved real path against the root using plain string `startsWith`, without requiring a path separator boundary. This lets a path escape into a *sibling* directory whose name merely starts with the root directory's name, defeating the guard the exact same way the original report's `_update` override defeated the intended invariant with incomplete logic.

### Finding Description
The containment check is:

```
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`realResolved.startsWith(realRoot)` treats `realRoot` as a literal string prefix, not a directory boundary. If the repository root is `/Users/victim/Documents/GitHub/app` and a resolved path is `/Users/victim/Documents/GitHub/app-secrets/config.json`, the check returns `true` even though `app-secrets` is a completely different directory — because `"…/app-secrets/config.json".startsWith("…/app")` is true in plain string comparison. The existing unit tests only exercise "go up and come back into the exact same root" and "go up entirely" cases; they never test the sibling-prefix scenario, so this gap is unverified by the test suite:

```
it('fails for paths outside of the root', async () => {
  assert((await resolveWithin(root, join('..'))) === null)
  assert((await resolveWithin(root, join('..', '..'))) === null)
})
``` [3](#0-2) 

This helper is the *only* guard used in two attacker-reachable call sites:

1. **Deep link handling** — `openRepositoryFromUrl` in the dispatcher trusts `filepath` from a parsed `x-github-client://openRepo/...?filepath=...` URL (fully attacker controlled, delivered as a link the user clicks) and only rejects absolute paths before calling `resolveWithin`:
```
if (isAbsolute(filepath)) { ... return }
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
}
``` [4](#0-3) 

2. **Copilot conflict context** — `buildConflictContext` reads file content from disk and forwards it to the Copilot SDK after the same `resolveWithin` check:
```
absolutePath = await resolveWithin(workingDirectory, file.path)
...
content = await readFile(absolutePath, 'utf8')
``` [5](#0-4) 

Because `resolveWithin`'s final check does not enforce that `realResolved` equals `realRoot` or starts with `realRoot + path.sep`, a relative path such as `../app-secrets/id_rsa` (where the working repo is checked out as `.../GitHub/app`) resolves to a sibling directory and is incorrectly accepted as "inside" the repository.

### Impact Explanation
An attacker who controls a deep link (`x-github-client://openRepo/...?filepath=...`) that a user clicks, or content in a repository that produces a crafted conflicted-file path, can cause Desktop to treat a path in a sibling directory as if it were inside the trusted repository root. Depending on the call site this can:
- Reveal (via `shell.showItemInFolder`) the location/existence of files outside the repository, including sensitive sibling clone directories.
- Cause the contents of a file outside the intended repository (e.g. from a similarly-named sibling clone containing secrets) to be read and transmitted to the Copilot backend as part of conflict-resolution context, i.e. exfiltration of out-of-repo file content to a third-party service.

This matches the accepted impact classes: "the result is code execution, file write or read outside the repo... or silent corruption... " triggered purely via a clicked deep link or crafted repository state, with no local/physical access or prior compromise required.

### Likelihood Explanation
Exploitation requires only that the victim clicks a crafted `x-github-client://` deep link (a normal, expected Desktop feature) and that a sibling directory whose name is a superstring of the repository's directory name exists on disk. GitHub Desktop's default clone location is a shared parent folder (e.g. `~/Documents/GitHub/<repo>`), where users commonly keep multiple repositories with related, prefix-sharing names (`app`, `app-secrets`, `app-old`, forks, backups, etc.), making the collision realistic rather than contrived. The guard function itself is unit-tested but the tests never cover this exact boundary condition, indicating the gap was not caught by existing safeguards.

### Recommendation
Fix the containment check in `_resolveWithin` to require an exact match or a proper separator boundary, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests specifically for sibling directories whose names share a prefix with the root (e.g. `root = /tmp/app`, escape target `/tmp/app-secret/file`) to prevent regressions of this exact class of bug.

### Proof of Concept
1. Victim has two repositories cloned side by side: `~/Documents/GitHub/app` (currently open in Desktop) and `~/Documents/GitHub/app-secrets` (contains sensitive files).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/owner/app?filepath=../app-secrets/credentials.json`
3. `parseAppURL` parses this into an `IOpenRepositoryFromURLAction` with `filepath = "../app-secrets/credentials.json"` [6](#0-5) .
4. `openRepositoryFromUrl` passes this to `resolveWithin(repository.path, filepath)` where `repository.path` is `.../GitHub/app`. The resolved path `.../GitHub/app-secrets/credentials.json` passes the flawed `startsWith` check and is passed to `shell.showItemInFolder`, revealing the sibling repository's sensitive file location outside the intended repo boundary [4](#0-3) .

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
