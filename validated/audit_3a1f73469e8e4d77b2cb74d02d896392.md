### Title
Scanner accepts zero-value/below-dust outputs as received funds which cannot be economically spent - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner::scan_transaction` returns any `TxOut` whose `script_pubkey` matches a registered script as a `ReceivedOutput`, with no check on `output.value`. An unprivileged party can send a Bitcoin transaction paying a zero-value (or below-dust) output to a Serai multisig's P2TR script, causing the wallet layer to report it as a spendable received output. Analogous to the Cooler report where `rollable` defaults to `true` even when `interest == 0` (making `roll()` free), here the implicit "this output is worth spending" assumption holds by default even when the value parameter is zero, so the "cost" of the output (the fee to spend its ~57-vbyte input) exceeds its value.

### Finding Description
`Scanner::scan_transaction` matches outputs purely on `script_pubkey`:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```
(networks/bitcoin/src/wallet/mod.rs:205-211)

`ReceivedOutput::read` also deserializes `TxOut::consensus_decode` without any value check (mod.rs:122-134), so a zero-value `ReceivedOutput` can additionally be fed to any downstream consumer as untrusted bytes.

On the spend side, `SignableTransaction::new` enforces `DUST` only on *payments* (send.rs:165-169). Inputs are summed and weighed unconditionally (send.rs:175-204): every matched output adds ~57 vbytes of Taproot input weight to `needed_fee` while contributing `output.value` to `input_sat`. A value-0 or sub-dust input therefore reduces `input_sat - (payment_sat + needed_fee)`, i.e. it burns fee budget rather than funding anything. There is no `input.value < DUST` rejection anywhere in `SignableTransaction::new` or in `scan_transaction`.

### Impact Explanation
An attacker who knows a multisig's P2TR address (public on-chain) can create zero-value or dust outputs to it at essentially the cost of the funding input's fee — the output itself carries 0 sats. Each such output:
- is reported by `Scanner::scan_block`/`scan_transaction` as a received output, indistinguishable in kind from real funds (the accounting value comes out as ~0 but it occupies the output set);
- if later selected as an input to `SignableTransaction::new`, adds fee weight with no value, so spending it is strictly net-negative — the funds are "received" but not economically spendable, directly matching the accepted impact category of funds reported received that are not spendable;
- is unbounded in quantity: unlike `roll()` which the reporter showed is costless when `interest == 0`, here the cost parameter (`output.value`) is zero for the *recipient's* benefit while the sender only pays a marginal output-serialization cost.

### Likelihood Explanation
Reachable by any unprivileged party sending a public Bitcoin transaction — no validator collusion, no leaked keys, no malicious-RPC assumption. The only mitigating factor is that a downstream integrator (e.g. the processor's `>= N::DUST` filter in `processor/src/multisigs/scanner.rs:564`) must select the dust output as a spend input for direct loss; the library itself provides no such guard, and `ReceivedOutput::read` lets these outputs be reintroduced via deserialization even if a caller filtered at scan time.

### Recommendation
Mirror the report's fix ("rollable=false when interest=0"): gate the default acceptance on the zero-valued parameter. In `Scanner::scan_transaction`, skip outputs with `output.value.to_sat() < DUST` (using the `DUST` constant already defined in `wallet/send.rs`), and reject `output.value == 0` in `ReceivedOutput::read`. Additionally, in `SignableTransaction::new`, reject or prune inputs whose value is below the marginal fee they add (`fee_per_vbyte * 57`), so a dust input can never be net-negative.

### Proof of Concept
1. Obtain a Serai multisig's P2TR `script_pubkey` (public from any prior deposit on-chain).
2. Broadcast a transaction containing `TxOut { value: Amount::ZERO, script_pubkey: serai_script }` (a zero-value output is consensus-valid; relay can be achieved via direct miner submission or by using 1–545 sats, still below `DUST = 546`).
3. `Scanner::scan_block` returns a `ReceivedOutput` for it (`scripts.get` matches), value 0.
4. That `ReceivedOutput` round-trips through `serialize`/`read` unfiltered and, when passed in `inputs` to `SignableTransaction::new`, increases `needed_fee` by `fee_per_vbyte * 57` while contributing 0 to `input_sat` — funds reported received which are not spendable without loss.
