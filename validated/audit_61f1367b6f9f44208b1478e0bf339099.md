## Answer

Confirmed vulnerability — attacker-supplied ref names can reach `addWorktree`'s `commitish` argument and be parsed as a `git worktree add` option, because no `--` separator is used to end option parsing.

### Title
Argument injection via unescaped commit-ish in `addWorktree` (missing `--` option terminator) — (File: `app/src/lib/git/worktree.ts`)

### Summary
`addWorktree` builds the `git worktree add` argv by pushing `path` and then, optionally, `options.commitish` directly onto the args array with no `--` terminator: [1](#0-0) 

`options.commitish` is populated from `Branch.ref` / `Branch.name`, which are derived from `%(refname)` / `%(refname:short)` produced by `git for-each-ref` over `refs/heads` and `refs/remotes` — i.e., from ref names that can originate from a fetched remote: [2](#0-1) 

That value flows to `addWorktree` from the Add Worktree dialog when the user picks a (possibly remote) branch: [3](#0-2) 

Git's `check-ref-format` rules (leading `.`, `..`, control chars, `~^:?*[\`, trailing `/`/`.lock`, `@{`, bare `@`) do **not** forbid a ref component from beginning with `-`, so a remote can legitimately push/advertise a branch such as `refs/heads/--orphan` or `refs/heads/--reason=x`, which Desktop will happily list as a `Branch`. This is exactly the class of bug the codebase is aware of and defends against elsewhere: `checkout.ts`'s `getBranchCheckoutArgs` deliberately appends a trailing `'--'` after the branch name specifically to stop it from being parsed as an option: [4](#0-3) 

and the ref-sanitization helper explicitly documents/tests that a leading `-` must be stripped when Desktop invents ref names itself: [5](#0-4) 

`addWorktree` has no equivalent protection — `path` and `commitish` are appended with no `--`, so a commit-ish beginning with `-` will be parsed by git's `parse_options` as a flag to `worktree add` rather than a positional commit-ish.

### Impact Explanation
This is genuine argument injection, but the *reachable* impact is bounded by `git worktree add`'s own option surface (`-f`/`--force`, `--detach`, `--checkout`/`--no-checkout`, `--lock`, `--reason=<string>`, `-b`/`-B`/`--orphan`, `-q`/`--quiet`) — there is no `-c <config>` or `--upload-pack=<cmd>`-style flag reachable at this argv position, and dugite/git spawns the process without a shell, so the proof-of-concept's `$(touch pwn)` shell substitution would **not** execute; it would simply become part of a literal option string (e.g. a `--reason` value). The realistic impact is corruption of worktree-creation semantics — e.g. forcing `--orphan` so the new worktree is checked out on an unrelated unborn branch instead of the intended commit-ish, or forcing `--lock`/`--force`/`--detach` — which can silently produce a worktree that does not correspond to what the UI told the user was being checked out (falls under "silent corruption of what the user commits" rather than code execution/file write outside the repo).

### Likelihood Explanation
Requires the victim to have fetched a remote containing a maliciously named branch and to then pick that branch (by typing/autocompleting its name) in the Add Worktree dialog — a normal, expected user action once the branch is present locally, not an "unnatural" step.

### Recommendation
Mirror the existing mitigation used in `checkout.ts`: append a `'--'` terminator before the positional `path`/`commitish` arguments in `addWorktree`, e.g. `args.push('--', path); if (options.commitish) args.push(options.commitish)`, so no attacker-controlled ref value can ever be interpreted as an option to `git worktree add`.

### Proof of Concept
1. On a malicious remote, create/advertise a branch whose name is `--orphan` (or `--reason=x`), e.g. `refs/heads/--orphan`.
2. Victim adds/fetches this remote in GitHub Desktop; the branch appears in `allBranches`.
3. Victim opens "Add Worktree", types/selects the branch named `--orphan` as the branch to check out.
4. `addWorktree` builds argv `['worktree','add', <path>, '--orphan']` with no `--` separator; git parses `--orphan` as a flag rather than a commit-ish, and the new worktree is created as an orphan branch instead of checking out the branch the UI claimed to check out — demonstrating the argument-injection primitive (note: this does **not** achieve shell command execution, since git args are not shell-interpreted).
