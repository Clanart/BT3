### Title
Silent corruption of partial commits when working-directory content changes between diff review and commit staging - ([File: app/src/lib/patch-formatter.ts])

### Summary
The Angle Protocol bug is a class of "index/order does not imply identity" bug: a caller supplies a selection (`minAmountsOut`) that is matched positionally against an array (`ts.collateralList`) that can silently change between when the selection was formed and when it is consumed, so the wrong element gets matched to the wrong selection entry. GitHub Desktop has the same invariant in its partial-commit ("stage selected lines") feature: `DiffSelection` records *positional* line indices from a previously rendered diff, and `formatPatch` / `formatPatchToDiscardChanges` blindly reapply those indices against whatever diff is supplied at staging time, with no check that the line at that index is still the same content the user actually reviewed and selected.

### Finding Description
`DiffSelection` stores which lines are included in a commit purely as a set of numeric `absoluteIndex` values (`divergingLines`), computed relative to a diff snapshot rendered in the UI: [1](#0-0) 

When the app builds the patch to stage, `formatPatch` walks a (potentially different/fresher) `diff.hunks` and asks `file.selection.isSelected(absoluteIndex)` — purely a positional lookup, with no comparison of the line's text/type against what was originally selected: [2](#0-1) 

The only place that reconciles a changed diff against a stale selection is `updateChangesWorkingDirectoryDiff`, and it only recomputes which indices are *selectable* (to drop lines that turned into context or disappeared) — it never verifies that a line which is still "selectable" at the same index still has the *same content*: [3](#0-2) 

`stageFiles`/`update-index.ts` then applies this same `file.selection` object via `applyPatchToIndex` for every file with a partial selection, independent of when the diff underlying that selection was generated: [4](#0-3) 

This mirrors the unmitigated Angle finding exactly: the "index" (line number in the diff) is treated as a stable identity key across two different snapshots of the same conceptual list (the diff hunks), when in fact the content behind that index can shift (lines added/removed elsewhere in the file, hunk re-numbering, or the file being rewritten by an external process/tool/build step while Desktop is open) between the time the user selects lines and the time Desktop turns that selection into a patch and stages it.

### Impact Explanation
If the working tree file is modified out from under Desktop after the user has made a partial line selection but before the commit is finalized (e.g., a build tool, formatter, git hook, git smudge/clean filter, or any other process touching the file, which is a very common occurrence in real repos, especially ones with automated tooling or malicious/compromised pre-commit tooling shipped in the repo), `formatPatch` will silently include/exclude lines that the user never reviewed at all, because the same absolute index now refers to different text. The result is a commit whose content differs from what the user believed they approved and, if pushed, corrupts the published history without any error or warning — this is precisely the "silent corruption of what the user commits or pushes" impact category, driven by content the attacker (via a malicious repo, hook, or filter) can influence.

### Likelihood Explanation
Requires a window between diff rendering/selection and commit staging where the underlying file content changes without Desktop re-diffing and clearing the stale selection — plausible via repo-controlled mechanisms like clean/smudge filters, `post-checkout`/background tooling, or any file watcher triggered by the repo's own build config, none of which require local/physical access or leaked credentials. It's a race/staleness condition rather than a guaranteed trigger, so likelihood is moderate; severity of a silently wrong commit is what elevates it.

### Recommendation
Do not treat `absoluteIndex` as a stable identity key across diff regenerations. Before staging, re-validate that the diff used to build the patch is the same diff (by content hash, or by verifying that each selected line's text/type still matches what was originally captured) as the one the user's `DiffSelection` was created against; if it differs, force a full re-diff/re-selection instead of silently reapplying possibly-mismatched indices, analogous to checking token identity rather than array position in the original Angle mitigation.

### Proof of Concept
1. Open a modified file with multiple hunks in the Changes view and select only a subset of lines for the commit (populates `DiffSelection.divergingLines` with absolute indices tied to the current diff).
2. Before clicking "Commit", have an external process (e.g., a repo-configured git `clean`/`smudge` filter, a build watcher, or any tool) rewrite the file so that lines shift (insert/remove lines above the hunk) without Desktop's Changes view re-rendering/re-diffing in time.
3. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` regenerates the diff and calls `formatPatch`, which reapplies the old `DiffSelection` indices positionally against the new hunks [5](#0-4) .
4. The resulting commit includes/excludes lines the user never actually reviewed, differing from what was shown and approved in the UI.
