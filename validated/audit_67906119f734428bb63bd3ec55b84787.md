## Title
Self-reported `unstable` compilation metadata can be stripped from a module to bypass `reject_unstable_bytecode`'s mainnet check with no independent bytecode-level verification - (File: `aptos-move/aptos-vm/src/aptos_vm.rs`)

### Summary
`AptosVM::reject_unstable_bytecode` (and its script counterpart `reject_unstable_bytecode_for_script`) only inspects the optional `CompilationMetadata` entry embedded by the Move compiler in a module's metadata table. If that metadata entry is present but reports `unstable: true`, publishing is rejected on mainnet. However, if the metadata entry is absent entirely, the loop silently returns `Ok(())` for that module - there is no independent, structural signal in the bytecode itself that a module was produced by an "unstable" compiler version.

### Finding Description
`reject_unstable_bytecode` iterates modules and only rejects when `get_compilation_metadata` returns `Some(metadata)` with `metadata.unstable == true`: [1](#0-0) 

`get_compilation_metadata` simply looks up the `COMPILATION_METADATA_KEY` entry in the module's metadata vector and returns `None` if it is not found: [2](#0-1) 

Nothing in the publish path enforces that this metadata entry must be present. `check_metadata_format`, which does validate metadata format/duplication, treats the compilation-metadata key as just another optional, well-formed entry - it does not require it to exist: [3](#0-2) 

`verify_module_metadata_for_module_publishing`, called from `validate_publish_request` right after `reject_unstable_bytecode`, also does not require compilation metadata to be present - it only validates `RuntimeModuleMetadataV1` (a separate, unrelated key) and returns `Ok(())` immediately if that is missing: [4](#0-3) [5](#0-4) 

The `unstable` tag corresponds to the compiler version being marked unstable (currently `CompilerVersion::V2_1`), a property of the *toolchain*, not necessarily of specific opcodes: [6](#0-5) 

Separately, genuinely new *bytecode format* features (enums, function values, closures, signed integers, etc.) are independently gated by binary-format version checks in the deserializer and by verifier/feature-flag configuration (`aptos_prod_verifier_config`, `get_max_binary_format_version`), regardless of the compilation-metadata `unstable` flag: [7](#0-6) [8](#0-7) 

Those independent gates only stop modules that actually *use* new opcodes/format versions. They do not stop a module that was compiled by an unstable compiler but happens to only emit opcodes already legal in the currently-enabled bytecode version - the only signal for that class of code is the self-reported `unstable` metadata flag, which is entirely attacker-controlled at serialization time since nothing enforces its presence or correctness.

### Impact Explanation
An attacker who compiles a module with the unstable compiler, then hand-edits the serialized module to drop the `COMPILATION_METADATA_KEY` metadata entry, can publish that module to mainnet even though the intended invariant ("unstable bytecode never lands on mainnet") is violated. Since the check is metadata-driven rather than bytecode-behavior-driven, and metadata is not mandatory, `reject_unstable_bytecode`/`reject_unstable_bytecode_for_script` provide no protection once the attacker controls the raw module bytes of the publish payload (which is normal for any publisher of a standard publish transaction).

That said, this only affects the attacker's own published modules under their own account - it does not let them publish, upgrade, freeze, or take over code they do not own, and does not defeat compatibility/upgrade-policy/dependency checks, which remain independently enforced.

### Likelihood Explanation
High for any user willing to post-process their compiled module bytes before submission, since no code ownership, permission, or additional capability is required beyond a standard publish transaction. Low impact severity, however, because the affected invariant is a compiler-toolchain safety net (guarding against compiler bugs/experimental codegen for the publisher's own modules), not a code-ownership or authority boundary.

### Recommendation
If the mainnet "no unstable bytecode" invariant is intended to be an adversarially-robust security property rather than a developer-ergonomics guard, `reject_unstable_bytecode` should not treat an absent compilation-metadata entry as implicitly stable. Options include: requiring the compilation-metadata entry to be present for the "known" compiler versions and rejecting modules lacking it when a stricter policy is desired, or (preferably) deriving stability from actual on-chain re-verification of code guarantees rather than solely from compiler-emitted, strippable metadata.

### Proof of Concept
1. Compile a Move package that intentionally triggers the compiler's unstable-version path (e.g. forcing `CompilerVersion::V2_1`), producing a `CompiledModule` whose metadata table contains a `COMPILATION_METADATA_KEY` entry with `unstable: true`, as exercised by `test_compilation_metadata_internal(true, true)`: [9](#0-8) 
2. Deserialize the produced module bytes, remove the metadata entry whose key equals `COMPILATION_METADATA_KEY`, and re-serialize.
3. Submit a standard publish transaction with the modified module bytes on a mainnet `chain_id`.
4. Observe that `validate_publish_request` -> `reject_unstable_bytecode` returns `Ok(())` for this module (since `get_compilation_metadata` returns `None`), and no other check in `validate_publish_request` (native validation, allowed-deps, `verify_module_metadata_for_module_publishing`, resource-group/event validation) rejects it, so the publish succeeds despite being compiled by the unstable compiler - contrary to the invariant demonstrated by the original `UNSTABLE_BYTECODE_REJECTED` behavior in `test_compilation_metadata`.

/// Check if the metadata has unknown key/data types
fn check_metadata_format(module: &CompiledModule) -> Result<(), MalformedError> {
    let mut exist = false;
    let mut compilation_key_exist = false;
    for data in module.metadata.iter() {
        if data.key == *APTOS_METADATA_KEY || data.key == *APTOS_METADATA_KEY_V1 {
            if exist {
                return Err(MalformedError::DuplicateKey);
            }
            exist = true;

            if data.key == *APTOS_METADATA_KEY {
                bcs::from_bytes::<RuntimeModuleMetadata>(&data.value)
                    .map_err(|e| MalformedError::DeserializedError(data.key.clone(), e))?;
            } else if data.key == *APTOS_METADATA_KEY_V1 {
                bcs::from_bytes::<RuntimeModuleMetadataV1>(&data.value)
                    .map_err(|e| MalformedError::DeserializedError(data.key.clone(), e))?;
            }
        } else if data.key == *COMPILATION_METADATA_KEY {
            if compilation_key_exist {
                return Err(MalformedError::DuplicateKey);
            }
            compilation_key_exist = true;
            bcs::from_bytes::<CompilationMetadata>(&data.value)
                .map_err(|e| MalformedError::DeserializedError(data.key.clone(), e))?;
        } else {
            return Err(MalformedError::UnknownKey(data.key.clone()));
        }
    }

    Ok(())
}
