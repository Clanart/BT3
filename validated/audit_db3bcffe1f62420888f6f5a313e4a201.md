Now I have concrete evidence in `python/google/protobuf/json_format.py` (the pure-Python `_Parser._ConvertFieldValuePair` implementation).### Title
Silent last-write-wins field resolution when a JSON key resolves to a proto field via two different aliases in the pure-Python `_ConvertFieldValuePair` parser - ([File: python/google/protobuf/json_format.py])

### Summary
The GitLab advisory (CVE-2025-12506) describes a Git-reference-resolution flaw: a name lookup ("ref") can resolve differently depending on which resolution path is used, so the content shown differs from the content actually retrieved — an "incorrectly-resolved name/reference" bug. The closest structural analog in this protobuf checkout is in the pure-Python ProtoJSON parser: `_Parser._ConvertFieldValuePair` resolves each incoming JSON key to a `FieldDescriptor` through two independent alias tables (`json_name` and the raw proto `name`), but its duplicate-key detector only tracks the *literal JSON key string*, not the resolved field identity. Two differently-spelled keys that resolve to the **same field** are treated as distinct, so the second write silently overwrites the first with no error — an authenticated/ordinary client can submit a payload whose displayed/validated key set looks non-conflicting while the actually-populated field state depends on key order, i.e., a resolution mismatch between "the set of names that appear valid" and "the field that is actually written."

### Finding Description
`_ConvertFieldValuePair` builds two lookup tables to resolve a JSON key `name` to a `FieldDescriptor`: [1](#0-0) 
For each key it first tries the `json_name` alias table, then falls back to the raw declared-name table: [2](#0-1) 
The duplicate-field guard that is supposed to reject "multiple fields for the same target" only compares the **literal string** `name` against a list of previously-seen literal strings, not the resolved `field` object: [3](#0-2) 
Because a single proto field can be reached through more than one literal string (its declared `snake_case` name and its `json_name`/camelCase alias, and, for proto2 messages that were compiled without the `deprecated_legacy_json_field_conflicts` uniqueness check, potentially other declared fields that alias to the same `json_name`), the `name in names` check never fires when the two occurrences use different spellings for the same field. The second occurrence's `_SetFieldOrExtension`/`_ConvertAndSetScalar` call simply overwrites the value set by the first occurrence, exactly like the upstream repo's own test acknowledges: [4](#0-3) 
This is the invariant failure that transfers from the GitLab report: the parser resolves the *same* underlying target (a Git ref / a proto field) through two different name-lookup paths, and the code that is supposed to detect and reject that overlap only compares the raw untranslated key, not the resolved identity — so "what looks like two independent, non-conflicting entries" silently collapse into a single write whose winning value is determined by JSON key ordering, not by validation.

The C++/upb JSON parser (`src/google/protobuf/json/internal/parser.cc`) does perform duplicate detection against the *resolved field* via `Traits::RecordAsSeen(*field, msg)`, so this specific incorrectly-scoped check is confined to the pure-Python fallback implementation: [5](#0-4) 

### Impact Explanation
An ordinary client submitting a bounded ProtoJSON payload to any application that uses the pure-Python `json_format.Parse`/`ParseDict` can smuggle two spellings of the same field (`"int32Value"` and `"int32_value"`, or a map field's two spellings) into one object. Downstream code that inspects the raw JSON for validation/auditing (e.g., "no field X appears twice", or logs the first occurrence as authoritative) will observe a different value than what ends up actually stored in the parsed protobuf message, because the second occurrence silently wins. This is a data-integrity/consuming-application-trust issue (the same class as "content displayed differs from content actually used") rather than memory corruption; severity is bounded by the fact that it requires proto2/legacy schemas or dual-alias `json_name` field maps and only affects the pure-Python parser path, not the C++/upb accelerated path used by most production Python installs.

### Likelihood Explanation
Likelihood is Medium: exploitation only requires an ordinary client to send a crafted ProtoJSON body containing the same field under two textual spellings; no privileged access or malicious schema is needed. However, the vulnerable code path is limited to the pure-Python `_Parser` implementation (used when the C-extension/upb backend is unavailable or explicitly disabled), which reduces real-world exposure since most production deployments use the upb-accelerated JSON parser that resolves duplicates against the field object rather than the string.

### Recommendation
In `_ConvertFieldValuePair` (python/google/protobuf/json_format.py), change the duplicate-detection state from a list of literal JSON key strings (`names`) to a set keyed by the resolved `FieldDescriptor` (or its `full_name`/field number), so that any two JSON keys that resolve to the same field are correctly flagged as a duplicate regardless of which alias (`json_name` vs. declared `name`) was used, mirroring the resolved-field-based duplicate check already used in the C++/upb JSON parser (`Traits::RecordAsSeen`).

### Proof of Concept
Using the pure-Python parser directly (forcing the pure-Python implementation, bypassing the upb/C++ accelerated backend), the existing repository test already demonstrates the exact behavior and confirms it is an acknowledged, unfixed oversight: [4](#0-3) 
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2 as pb2

msg = pb2.TestMessage()
json_format.Parse('{"int32Value": 1,"int32_value":2}', msg)
assert msg.int32_value == 2   # first write ("int32Value"->1) silently overwritten
```
No `ParseError` is raised despite the same field being set twice under two different literal key spellings — the duplicate check in `_ConvertFieldValuePair` (lines 663-670) never triggers because it compares raw strings, not the resolved `FieldDescriptor`.
