Audit Report

## Title
Early `break` on retry-pool overflow silently drops and under-reports already-broadcast transactions mid-batch - (File: send-transaction-service/src/send_transaction_service.rs)

## Summary
In `receive_txn_thread`, once a batch of transactions has been sent to the TPU via `tpu_sender.send_transactions_in_batch(...)`, the code attempts to move each transaction into the shared `retry_transactions` pool by iterating `transactions.drain()`. When the pool reaches `retry_pool_max_size`, the loop does `break`, but because `HashMap::drain()`'s iterator empties the source map on drop regardless of how many items were actually consumed, all not-yet-processed entries in `transactions` are discarded rather than skipped. These transactions were already broadcast over TPU but are never inserted into `retry_transactions` and never counted beyond the single triggering entry in `stats.retry_queue_overflow`.

## Finding Description
The relevant flow is in `receive_txn_thread`: [1](#0-0) 

1. `stats.sent_transactions` is incremented for the whole batch and `tpu_sender.send_transactions_in_batch(...)` broadcasts all buffered transactions before any retry-pool bookkeeping occurs: [2](#0-1) 
2. The code then locks `retry_transactions` and iterates `transactions.drain()`, incrementing `transactions_to_retry` for each entry and checking `retry_len >= retry_pool_max_size`, breaking on overflow: [3](#0-2) 
3. `HashMap::drain()` returns a `Drain` iterator whose `Drop` implementation unconditionally empties the source map of all not-yet-yielded elements once the iterator itself is dropped — this is a documented guarantee of `drain()`, independent of whether the loop consumed the iterator fully. Breaking out of the `for` loop causes the implicit `Drain` iterator to be dropped at the end of that block, silently discarding every remaining entry in `transactions`.
4. Consequently, any transaction ordered after the one that triggers the overflow `break` is lost: it is not inserted into `retry_transactions` (so `retry_thread` never retries it) and it is not counted, since `transactions_to_retry`/`transactions_added_to_retry` bookkeeping stops at the break point: [4](#0-3) 

Existing guards are insufficient: the overflow accounting (`retry_queue_overflow`) only reflects the delta between `transactions_to_retry` and `transactions_added_to_retry` computed up to the break point, not the actual number of entries silently dropped by `Drain::drop`.

## Impact Explanation
This affects the built-in `SendTransactionService` used for the `sendTransaction` RPC path. Transactions from any client sharing a batch window with a retry-pool-overflow event are broadcast once via TPU but then silently dropped from future retry — they are absent from `retry_transactions` and unaccounted for in stats. Since a client cannot control what else lands in the same `transactions` batch, this causes degradation for other, unrelated low-rate clients whose transactions may never land if the single broadcast attempt fails (no retry occurs), consistent with "single-client low-rate RPC crash/degradation" of the RPC scope.

## Likelihood Explanation
Triggering it only requires the shared `retry_transactions` pool to be at or near `retry_pool_max_size` (default `MAX_TRANSACTION_RETRY_POOL_SIZE`) when a batch is drained, and for that batch to contain more than one new transaction past the boundary. An unprivileged client can keep the retry pool near-saturated (e.g., submitting many transactions with high `max_retries` that never confirm) using only public RPC inputs, repeatedly straddling this boundary and causing collateral drops of other clients' transactions in the same batch window.

## Recommendation
Replace `break` with `continue` in the loop (while still accounting for skipped items in overflow bookkeeping), or avoid `break`ing while iterating a `drain()` iterator — e.g., collect remaining entries into a `Vec` first, or check pool capacity before entering the loop and stop consuming further elements without discarding them (e.g., via `retain`/explicit removal instead of `drain()` + `break`).

## Proof of Concept
1. Configure `retry_pool_max_size` to a small value (e.g., 3) via `--rpc-send-transaction-retry-pool-max-size`.
2. Pre-fill `retry_transactions` to `retry_pool_max_size - 1` with unconfirmed transactions that remain in the retry pool.
3. Submit a batch (within one `batch_send_rate_ms` window) containing several new distinct transactions such that the first fills the last retry-pool slot while others remain pending in the same `transactions.drain()` iteration.
4. Observe `stats.sent_transactions` counts the whole batch, but `stats.retry_queue_overflow` increments only by 1, while the remaining broadcast transactions are neither in `retry_transactions` nor reflected in any stat — they are silently lost and will never be retried, verifiable via a unit test asserting `retry_transactions.len()` and `retry_queue_overflow` after constructing this scenario.
