### Title
`SignableTransaction::new` computes the transaction weight/fee without the OP_RETURN data output, undercharging the real transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external finding is a two-step function where the first step's amounts are computed on the live value but the second step's amount is computed on a stale, pre-update value (`reserve` instead of `balance`). The Serai analog is `SignableTransaction::new`: the OP_RETURN `data` output is pushed onto `tx_outs` (the "balance") *before* the weight and fee are derived, yet `calculate_weight_vbytes` is invoked with only `payments` (the "reserve"), so every fee/change figure the constructor commits to is computed on a transaction that is one output short of the transaction actually signed and broadcast.

### Finding Description
In `SignableTransaction::new`, the outputs are assembled in two stages. First `tx_outs` is built from `payments`, then the OP_RETURN output is appended to `tx_outs` when `data.is_some()`. However, the subsequent calls to `calculate_weight_vbytes` are passed `payments`, not `tx_outs`:

- `calculate_weight_vbytes(tx_ins.len(), payments, None)` at `send.rs:204` — computes `vbytes` used for `needed_fee` and for the `TooLowFee` minimum-relay check.
- `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at `send.rs:225-226` — computes `vbytes_with_change` used for `fee_with_change`, which determines the change output's value.

Inside `calculate_weight_vbytes` (`send.rs:85-94`), the dummy `Transaction` is built exclusively from `payments`; the OP_RETURN output (up to `80` bytes of data plus ~`11` bytes of output overhead, i.e. ~`91` extra vbytes) is never included. The code even re-verifies at `send.rs:171-173` that `data.len() <= 80`, so the omission is systematic for every in-range `data`.

The result: `needed_fee`/`fee_with_change` are computed on a smaller transaction than the one placed in `self.tx` (`send.rs:245-251`), and the change amount `input_sat - payment_sat - fee_with_change` (`send.rs:228-230`) is inflated by exactly the missing fee. This mirrors the report's structure: the first quantity (outputs committed to the tx) reflects the updated set, while the second quantity (the fee/change math) is computed on the pre-update set.

### Impact Explanation
- The actual fee paid (`fee()` at `send.rs:138-141`, `sum(prevouts) - sum(outputs)`) equals `needed_fee`, which corresponds to a lower sat/vbyte rate than the caller's `fee_per_vbyte`. The transaction therefore pays strictly less than requested — up to ~`91 * fee_per_vbyte` sat less.
- The `TooLowFee` minimum-relay check at `send.rs:211` is evaluated against the understated `vbytes`. If the caller sets `fee_per_vbyte` at (or near) the relay minimum and includes a `data` payload, the signed transaction's real feerate can fall below `DEFAULT_MIN_RELAY_TX_FEE`, making it non-relayable. For a threshold wallet this burns a signing round and can leave the spend stuck until re-signed.
- The change output is credited more sat than it should be (the shortfall is quietly absorbed as an effective overpayment to change), which skews downstream accounting such as the processor's `on_chain_expected_change`/dust operating-cost logic in `processor/src/networks/mod.rs:580-592`.

### Likelihood Explanation
`data` is a public caller-controlled parameter of `SignableTransaction::new` (used for Serai `Shorthand`/instruction OP_RETURNs), so the bug triggers deterministically whenever `data.is_some()` — no adversarial timing or validator misbehavior required. It is reachable purely through public transaction-construction inputs. Impact is capped at an incorrect fee/change split and potential non-relayability (funds recoverable via re-signing), so this is Medium.

### Recommendation
Base the weight calculation on the actual output set that will appear in the transaction, not on `payments`. Concretely, change `calculate_weight_vbytes` to accept the already-assembled `tx_outs` (or pass `data` through and push the OP_RETURN `TxOut` inside the function, mirroring `send.rs:193-202`), so that both the no-change call (`send.rs:204`) and the with-change call (`send.rs:225-226`) measure the same transaction that is stored in `self.tx`. This keeps `needed_fee`, `fee()`, and the change amount consistent with the real vsize — analogous to the report's fix of using `balance` instead of `reserve`.
