### Title
Unbounded recursion during outer-puzzle driver matching allows a wallet-processing halt from a single crafted coin puzzle - (File: `chia/wallet/outer_puzzles.py`)

### Summary
The ReportPortal advisory describes a DoS caused by unbounded recursive nesting in a stored structure (`test_item.path`) with no depth limit, which destabilizes processing once nesting exceeds an implicit engine limit. The analogous pattern in this codebase is the wallet's outer-puzzle "driver" matching/traversal mechanism, which recursively unwraps nested CLVM puzzle layers (CAT, singleton, metadata, ownership, credential-restricted, etc.) with no depth bound, driven entirely by attacker-controlled puzzle structure.

### Finding Description
`match_puzzle()` in `chia/wallet/outer_puzzles.py:49-54` iterates over `driver_lookup` and calls each driver's `.match()` on an `UnknownPuzzle`. Each concrete driver's `match()` — e.g. `CATOuterPuzzle.match()` (`chia/wallet/cat_wallet/cat_outer_puzzle.py:33-45`), `MetadataOuterPuzzle.match()` (`chia/wallet/nft_wallet/metadata_outer_puzzle.py:39-53`), `OwnershipOuterPuzzle.match()` (`chia/wallet/nft_wallet/ownership_outer_puzzle.py:39-55`), `SingletonOuterPuzzle.match()` (`chia/wallet/nft_wallet/singleton_outer_puzzle.py:32-54`) — recursively calls `self._match(UnknownPuzzle(known_program=inner_puzzle))` (which is `match_puzzle` itself) on whatever inner puzzle it uncurries, with **no depth limit and no cost accounting**. The same unbounded recursive pattern exists in `get_inner_puzzle()`/`get_inner_solution()`/`construct()`/`solve()` on each driver, and in the CLVM-level `curry`/`uncurry` recursion used by `calculate_hash_of_curried_parameters` (`chia/wallet/puzzles/curry.clib:62-67`) and `recursive_uncurry_dump` (`chia/wallet/util/debug_spend_bundle.py:44-56`).

This recursive matcher is invoked directly on puzzle reveals sourced from the network/peers during wallet sync — for example `WalletStateManager.determine_coin_type()` (`chia/wallet/wallet_state_manager.py:915-1025`) builds an `UnknownPuzzle` from `coin_spend.puzzle_reveal` fetched from an untrusted/semi-trusted peer and calls `match_cat_puzzle`, `UncurriedNFT.uncurry`, `match_did_puzzle`, etc. — all of which uncurry nested layers recursively without depth limits. Similarly, `CATOuterPuzzle`/`OwnershipOuterPuzzle`/`MetadataOuterPuzzle` chains are exercised when a wallet parses an incoming **offer** (`Offer` decompression → driver dict construction) supplied by an untrusted offer counterparty, and when constructing/solving spends for CAT-in-CAT-style compound assets (as demonstrated by the existing test `chia/_tests/wallet/cat_wallet/test_cat_outer_puzzle.py` which builds a `double_cat_puzzle` — a CAT curried with another CAT as its inner puzzle — showing the "also" nesting mechanism is a first-class, attacker-reachable feature).

Because CLVM puzzle nesting depth is bounded only by CLVM execution *cost* at the interpreter level, not by any Python-side recursion guard in these driver/uncurry code paths, a party can construct a coin (or an offer, or a spend bundle observed on the network) whose puzzle reveal is nested deeply enough (tens of thousands of curry layers, still well within CLVM cost limits since currying/uncurrying such nesting is comparatively cheap per layer) to drive Python's call stack past its recursion limit when a wallet or full node attempts to identify/match it. This mirrors the ReportPortal bug class exactly: no explicit cap on recursively nested elements before the underlying engine (Python interpreter stack vs. Postgres `ltree` depth) becomes unstable.

By contrast, the codebase's DataLayer Merkle-tree code has already been hardened against exactly this class of issue: `chia/data_layer/data_store.py` explicitly documents (`sha256_treehash` in `chia/types/blockchain_format/tree_hash.py`) that treehash computation was made iterative "so we don't have to worry about blowing out the python stack," and `insert_into_data_store_from_file()` relies on the Rust `chia_rs.datalayer.MerkleBlob`, which raises `RecursionDepthExceededError`/`CycleFoundError` for excessively deep or cyclic externally-supplied trees (see `chia/_tests/core/data_layer/test_data_store.py:1726-1789`). No equivalent recursion-depth guard exists for the wallet's outer-puzzle driver matching/uncurrying code paths.

### Impact Explanation
A crafted coin puzzle reveal (deliverable via a network coin spend a wallet must sync, or via an offer file/bech32 blob a user is asked to inspect/accept) can trigger unbounded Python-level recursion in `match_puzzle()`/driver `.match()`/`.get_inner_puzzle()` chains. Hitting Python's recursion limit raises `RecursionError`, which is not always caught cleanly around these driver call sites, and can crash or hang the wallet's sync loop or offer-parsing thread — a spend-triggered transaction-processing halt for a wallet/light client, consistent with CWE-770 resource exhaustion. This does not directly forge value, but it can deny service to a targeted wallet user or interrupt a full node's coin-type identification/notification pipeline that shares this code.

### Likelihood Explanation
Likelihood is moderate: constructing a deeply nested but still `uncurry()`-parseable puzzle (e.g., CAT-wrapping-CAT-wrapping-CAT... or singleton/metadata/ownership layering repeated) is cheap for an attacker to build off-chain and does not require expensive CLVM execution cost, only a large but still-bounded number of nested `curry` applications — well within `MAX_BLOCK_COST_CLVM`. It can be delivered without needing to be mined/confirmed at all in the offer-parsing case (a wallet user opening a hostile offer file), and in the sync case a peer only needs to serve a `CoinSpend` with such a puzzle reveal for a coin the wallet is asked to identify. The main uncertainty is the exact practical recursion depth needed to exceed Python's default limit (~1000 frames, multiplied by the multiple recursive calls per layer across `match`, `get_inner_puzzle`, `get_inner_solution`, `construct`), which is easily reachable with a few hundred to low-thousands of nested layers.

### Recommendation
Add explicit recursion/iteration-depth limits (and/or convert to iterative traversal, following the precedent already set in `sha256_treehash`) to `match_puzzle()`, each outer-puzzle driver's `match`/`get_inner_puzzle`/`get_inner_solution`/`construct`/`solve` implementations in `chia/wallet/outer_puzzles.py` and the driver files under `chia/wallet/cat_wallet/`, `chia/wallet/nft_wallet/`, and `chia/wallet/vc_wallet/`, and to `UncurriedNFT.uncurry()`. Reject puzzle reveals whose nested-layer depth exceeds a sane bound (e.g., a few dozen) before recursive matching/uncurrying begins, and ensure any `RecursionError` raised is caught and treated as "unrecognized puzzle" rather than propagating and killing the sync/offer-processing task.

### Proof of Concept
Conceptual PoC (not executed): using the pattern already present in `chia/_tests/wallet/cat_wallet/test_cat_outer_puzzle.py`, repeatedly nest `construct_cat_puzzle(CAT_MOD, tail, construct_cat_puzzle(CAT_MOD, tail, ...))` (or repeatedly wrap `NFT_STATE_LAYER_MOD`/`NFT_OWNERSHIP_LAYER`/singleton layers) N times, for N in the low thousands, to build a single puzzle reveal. Attach this puzzle reveal to a `CoinSpend`/offer and feed it to `match_puzzle(UnknownPuzzle(known_program=nested_puzzle))` or to `WalletStateManager.determine_coin_type()`'s uncurry path; the recursive `.match()`/`.get_inner_puzzle()` chain calls itself once per nesting layer, and sufficiently large N is expected to raise a Python `RecursionError`, halting the calling task/thread. Exact required depth and whether the exception is caught upstream were not empirically verified in this review and should be confirmed with a running instance. @pytest.mark.anyio
@pytest.mark.parametrize("depth", [1000, 100_000])
async def test_insert_into_data_store_from_file_line_graph_depth(
    data_store: DataStore,
    store_id: bytes32,
    tmp_path: Path,
    depth: int,
) -> None:
    # Binary "line graph":
    #   1 -> leaf_1, 2
    #   2 -> leaf_2, 3
    #   ...
    #   depth -> leaf_depth, leaf_end
    #
    # This stresses depth/stack handling while staying strictly binary.
    #
    # Node IDs:
    # - internal nodes: 1..depth
    # - per-level leaf nodes: (depth+1)..(2*depth)
    # - final leaf: (2*depth+1)
    internal_first = 1
    internal_last = depth
    leaf_base = internal_last + 1
    leaf_end = (2 * depth) + 1

    edges: list[tuple[int, int]] = []
    for i in range(internal_first, internal_last):
        # Order matters: first edge is left child, second edge is right child.
        edges.append((i, leaf_base + (i - internal_first)))  # unique leaf for this internal node
        edges.append((i, i + 1))  # next internal node

    # last internal points to its leaf and a final leaf
    edges.append((internal_last, leaf_base + (internal_last - internal_first)))
    edges.append((internal_last, leaf_end))

    filename = tmp_path / f"line_graph_depth_{depth}.dat"
    root_hash = create_graph_util(filename, edges)

    with pytest.raises(chia_rs.datalayer.RecursionDepthExceededError):
        await data_store.insert_into_data_store_from_file(store_id, root_hash, filename)
