### Title
Unchecked u32 subtraction in Bitcoin difficulty-retarget calculation can flip the direction of a difficulty adjustment - ([File: circuits-lib/src/header_chain/mod.rs])

### Summary
`calculate_new_difficulty` computes `actual_timespan = last_timestamp - epoch_start_time` as a plain, unchecked `u32` subtraction on attacker-influenced block-header timestamps. Bitcoin's median-time-past (MTP) rule only requires a block's timestamp to be greater than the median of the previous 11 timestamps, not greater than every earlier timestamp, so `last_timestamp` can legitimately be numerically smaller than `epoch_start_time` (2015 blocks earlier) while still passing `validate_timestamp`. When that happens the subtraction wraps to a value near `u32::MAX` instead of representing a negative timespan.

### Finding Description
`calculate_new_difficulty` (circuits-lib/src/header_chain/mod.rs:635-656) is called from `apply_block_headers` (circuits-lib/src/header_chain/mod.rs:499-506) at every 2016-block epoch boundary in the header-chain circuit, using `self.epoch_start_time` (set from the first block's timestamp of the epoch, line 490) and `block_header.time` (the last block's timestamp of the epoch).

```
circuits-lib/src/header_chain/mod.rs:640
let mut actual_timespan = last_timestamp - epoch_start_time;
```

Timestamp validation only enforces `block_time > median(prev_11_timestamps)` (`validate_timestamp`, lines 546-549); it does not enforce monotonicity relative to blocks more than 11 back. A chain of headers under attacker control (an operator/watchtower crafting an alternative header sequence fed to the header-chain circuit as input) can therefore have the epoch's last block timestamp be less than the epoch's first block timestamp while still satisfying every per-block MTP check.

In real Bitcoin Core, `nActualTimespan` is computed with signed 64-bit arithmetic, so a negative timespan is clamped to the *minimum* (`EXPECTED_EPOCH_TIMESPAN/4`), which *increases* difficulty (makes future blocks harder). In this codebase, the unsigned wraparound instead produces a value near `u32::MAX`, which is far above `EXPECTED_EPOCH_TIMESPAN*4`, so it gets clamped to the *maximum* (`EXPECTED_EPOCH_TIMESPAN*4`), which *decreases* difficulty (makes future blocks easier). This is the opposite consensus outcome from real Bitcoin and diverges from canonical chain rules that the header-chain circuit is supposed to faithfully re-implement.

### Impact Explanation
The header-chain proof's `chain_state.total_work` and its implied difficulty schedule are relied on by the bridge circuit to decide who has "more cumulative proof-of-work" (circuits-lib/src/bridge_circuit/mod.rs:148-160, `total_work < max_total_work` check). By exploiting this bug, a party constructing an alternative header sequence (which only needs internally-consistent PoW satisfying the circuit's own — now artificially lowered — target, not the real Bitcoin network's actual historical target) can grind blocks with less real work than the target implies, while still causing the circuit to accept an inflated/incorrect total-work value or an easier target for subsequent epochs. This can allow a false circuit claim to be proved (the header-chain proof accepting a chain state that would not be canonical under real Bitcoin consensus rules), which underpins the bridge's PoW-based dispute resolution (watchtower vs. operator total-work comparison, and ultimately the Disprove path described in `docs/bridge-circuit.md`). This maps to the specified Critical impact category "a false circuit claim proved or a true one made unprovable."

### Likelihood Explanation
Triggering this requires the attacker to construct a full set of block headers (crossing an epoch boundary) that: (1) chains correctly via `prev_block_hash`, (2) satisfies the difficulty target the circuit computes at each step, and (3) has the epoch's final timestamp numerically less than the epoch's start timestamp while every individual header still exceeds the median of its preceding 11 timestamps. Because headers are supplied as circuit input rather than validated against the real Bitcoin network inside this code path, an attacker generating their own header chain (with grinding power sufficient to satisfy whatever, possibly circuit-lowered, target results) controls all these values. This is a purely arithmetic/logic issue, not requiring any privileged role, key, or majority hashpower over the real Bitcoin network — only the ability to mine/grind an internally valid alternate header sequence against the circuit's own (self-referential, exploitable) targets.

### Recommendation
Compute the epoch timespan using a signed or checked operation that mirrors Bitcoin Core's semantics, e.g.:
```rust
let actual_timespan = (last_timestamp as i64) - (epoch_start_time as i64);
let mut actual_timespan = actual_timespan.clamp(
    (EXPECTED_EPOCH_TIMESPAN / 4) as i64,
    (EXPECTED_EPOCH_TIMESPAN * 4) as i64,
) as u32;
```
or use `last_timestamp.checked_sub(epoch_start_time)`, and if it underflows, clamp explicitly to `EXPECTED_EPOCH_TIMESPAN / 4` (the same treatment Bitcoin Core gives a negative timespan) rather than letting it wrap to a large unsigned value that gets clamped to the maximum.

### Proof of Concept
1. An attacker builds an alternate header chain for the header-chain circuit's input, choosing timestamps for 2016 consecutive headers such that each header's timestamp is greater than the median of the previous 11 timestamps (satisfying `validate_timestamp`) but the very last header's timestamp in the epoch is smaller than the epoch's first header's timestamp (`self.epoch_start_time`), e.g. oscillating timestamps that decrease overall while locally satisfying the median rule.
2. At the epoch boundary (`block_height % BLOCKS_PER_EPOCH == BLOCKS_PER_EPOCH - 1`), `calculate_new_difficulty(epoch_start_time, last_timestamp, current_target_bits)` executes `last_timestamp - epoch_start_time`, which underflows and wraps to a value close to `u32::MAX`.
3. This value exceeds `EXPECTED_EPOCH_TIMESPAN * 4`, so it is clamped to `EXPECTED_EPOCH_TIMESPAN * 4`, causing the new target to increase (difficulty to drop) by the maximum factor — the opposite of the difficulty increase that real Bitcoin consensus would apply for a negative timespan.
4. The attacker continues mining subsequent epochs against this artificially lowered target, accumulating a `chain_state.total_work` value in the header-chain proof that does not correspond to the real amount of work Bitcoin consensus rules would require, which can then be leveraged in the bridge circuit's total-work comparison (circuits-lib/src/bridge_circuit/mod.rs:148-160). fn calculate_new_difficulty(
```rust
    epoch_start_time: u32,
    last_timestamp: u32,
    current_target: u32,
) -> [u8; 32] {
    let mut actual_timespan = last_timestamp - epoch_start_time;
    if actual_timespan < EXPECTED_EPOCH_TIMESPAN / 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN / 4;
    } else if actual_timespan > EXPECTED_EPOCH_TIMESPAN * 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN * 4;
    }

    let current_target_bytes = bits_to_target(current_target);
    let mut new_target = U256::from_be_bytes(current_target_bytes)
        .wrapping_mul(&U256::from(actual_timespan))
        .wrapping_div(&U256::from(EXPECTED_EPOCH_TIMESPAN));

    if new_target > NETWORK_CONSTANTS.max_target {
        new_target = NETWORK_CONSTANTS.max_target;
    }
    new_target.to_be_bytes()
}
```
