### Title
Missing zero-address check in `VLMGP.lockFor` permanently freezes locked MGP tokens - (File: VLMGP.sol)

### Summary
`VLMGP.lockFor(uint256 _amount, address _for)` lets any wallet lock MGP tokens on behalf of a `_for` address, but performs no validation that `_for != address(0)`. If a user mistypes or passes `address(0)` (directly, or through any integrating contract that forwards a `_for`/recipient parameter without its own check), the MGP is pulled from the caller and permanently credited to the zero address, with no way to ever unlock or recover it.

### Finding Description
`lockFor` calls the internal `_lock` helper directly with the caller-supplied `_for` address, with no zero-address guard: [1](#0-0) 

`_lock` transfers MGP from `spender` (the caller) into the contract and then calls `MasterMagpie.depositVlMGPFor(_amount, _for)`: [2](#0-1) 

`depositVlMGPFor` is restricted to be called only by `VLMGP` (`_onlyVlMgp`) and forwards straight into `_deposit(address(vlmgp), _for, _amount, true)` without any zero-address check either: [3](#0-2) [4](#0-3) 

The resulting `UserInfo` is stored under `userInfo[vlmgp][address(0)]`. Because every unlock/withdraw path in `VLMGP` (`startUnlock`, `_unlock`, `_checkIdexInBoundary`, `_checkInCoolDown`, etc.) is keyed off `msg.sender`, and no external account can ever originate a transaction with `msg.sender == address(0)`, the locked MGP recorded against `address(0)` can never be unlocked, withdrawn, or otherwise recovered by anyone. The `MGP.safeTransferFrom(spender, address(this), _amount)` already succeeded, so the tokens leave the caller's wallet before the flawed `_for` value is used.

This matches the report's bug class (missing zero-address check causing user fund loss from a simple mistake/typo) but manifests specifically in the vlMGP lock accounting path rather than `IonPool.withdraw`.

### Impact Explanation
Any ordinary wallet that calls `lockFor(_amount, address(0))` — whether directly or via any front-end/integration bug that passes a bad recipient — permanently loses the locked MGP with no recovery mechanism. This is a direct, permanent freezing of user funds, satisfying the "permanent freezing of funds" impact criterion.

### Likelihood Explanation
`lockFor` is a fully public, unprivileged function intended for normal use (e.g., contracts or scripts locking MGP on behalf of another user, as seen in `rewards/Airdrop2.sol`'s `vlmgp.lockFor(claimable, msg.sender)` and `wombat/ArbWomUp3.sol`'s `vlMGP.lockFor(mgpAmountToLcok, _account)`). Any caller-side bug, integration error, or accidental use of an uninitialized/zeroed address variable as `_for` triggers permanent loss, and there is no on-chain guard preventing it. [5](#0-4) [6](#0-5) 

### Recommendation
Add a zero-address check in `VLMGP.lockFor` (and defensively in `_lock`, and in `MasterMagpie.depositVlMGPFor`/`_deposit`) that reverts if `_for == address(0)`.

### Proof of Concept
1. A wallet holds MGP and calls `VLMGP.lockFor(amount, address(0))` directly, or an integrating contract forwards a zero address due to an uninitialized variable/typo.
2. `_lock` executes `MGP.safeTransferFrom(msg.sender, address(this), amount)`, pulling the tokens out of the caller's wallet.
3. `IMasterMagpie(masterMagpie).depositVlMGPFor(amount, address(0))` is called, which credits `userInfo[vlmgp][address(0)].amount += amount` in `MasterMagpie`.
4. No account can ever call any `VLMGP` unlock function with `msg.sender == address(0)`, so the locked amount is unrecoverable forever, and `totalAmount`/`totalAllocPoint` accounting in `MasterMagpie` also permanently reflects phantom locked supply attributable to no real user.
