### Title
Missing HTML/JS-unsafe character escaping (`<`, `>`, `&`, `=`, `'`) in upb's JSON encoder used by PHP/Ruby bindings, enabling reflected XSS when protobuf JSON output is embedded in HTML - (File: `upb/json/encode.c`)

### Summary
Protobuf's JSON serialization intentionally escapes characters that are legal in JSON but dangerous if the JSON is later embedded verbatim into an HTML/`<script>` context (`<`, `>`, `&`, `=`, `'`, plus several Unicode "invisible"/bidi characters). This defense is implemented consistently in the C++ (`src/google/protobuf/json/internal/writer.cc`), Java (`java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`), and C# (`csharp/src/Google.Protobuf/JsonFormatter.cs`) JSON writers, but the upb JSON encoder (`upb/json/encode.c`), which backs the PHP and Ruby native extensions (compiled in as `php-upb.c` / `ruby-upb.c`), does not implement this escaping at all.

### Finding Description
The failed invariant in the hibernate-validator report is: user-controlled string content must be neutralized before it can be interpreted as executable markup by a browser; `SafeHtmlValidator` failed to fully neutralize a crafted tag, allowing HTML/script injection.

Protobuf has an almost identical invariant for JSON output: string field values are attacker-controlled (client-supplied via `ParseFrom*`/message setters through a trusted schema) and are serialized into JSON that downstream consumers frequently embed directly into HTML pages or `<script>` blocks (this is exactly why protobuf's own regression test exists: "Make sure html tags are escaped", `java/util/src/test/java/com/google/protobuf/util/JsonFormatTest.java:2016-2035`).

The C++ writer explicitly escapes `<`, `>` and a list of Unicode confusables "to prevent security bugs in JavaScript": [1](#0-0) 
and the string-writing loop actively treats `<`/`>` as unsafe characters requiring escaping: [2](#0-1) 

Java's `JsonFormat` mirrors this, explicitly escaping `<>&='` "to prevent XSS risks": [3](#0-2) 

C#'s `JsonFormatter` does the same, escaping `<` and `>` as `\u003c`/`\u003e` "for HTML security": [4](#0-3) 

In contrast, upb's `jsonenc_put_escaped_char`, which is the single per-character escaping routine for all JSON string output in upb, only escapes JSON-spec-mandated characters (`\n`, `\r`, `\t`, `"`, `\f`, `\b`, `\\`) and raw control bytes `< 0x20`. It has no case for `<`, `>`, `&`, `=`, `'`, or any of the Unicode bidi/invisible characters that the other implementations treat as unsafe: [5](#0-4) 
The identical code is compiled into the PHP C extension (`php-upb.c`) and the Ruby C extension (`ruby-upb.c`), both of which invoke `upb_JsonEncode` from their respective `message.c` implementations for the public `serializeToJsonString`/`to_json` API surface, meaning the same unescaped-output behavior reaches end users of the PHP and Ruby bindings.

### Impact Explanation
Consuming-application exposure assumption: many applications take the protobuf-generated JSON string and embed it directly into an HTML response (e.g., inline `<script>var data = <json>;</script>` bootstrapping, or server-rendered templates) without additional HTML-context escaping, trusting protobuf's JSON writer to have already neutralized HTML-unsafe characters — which is precisely the behavior the C++/Java/C# writers guarantee and document via their explicit "prevent XSS"/"HTML security" comments and regression tests. For PHP and Ruby applications using the upb-backed native extension, a string field value containing `</script><script>alert(1)</script>` or similar would be serialized byte-for-byte into the JSON output (only `"` and `\` are escaped), so if that JSON is interpolated into an HTML/script context, the payload executes — a classic reflected/stored XSS, matching CWE-79 and the same class of failure as the hibernate-validator advisory (attacker-controlled string reaches a rendering context without complete neutralization).

### Likelihood Explanation
Reachability is high and requires no privileged access: any client-controlled string field passed through the normal, public `Message#to_json` (Ruby) or `serializeToJsonString()` (PHP) API on the upb backend will pass through `upb_JsonEncode` → `jsonenc_string` → `jsonenc_put_escaped_char`, which never escapes `<`/`>`. No malformed schema, native API misuse, or privileged access is needed — only that the resulting JSON is later embedded in an HTML/JS context by the consuming application, which is a common and protobuf-documented usage pattern (evidenced by the dedicated C++/Java regression tests for exactly this scenario).

### Recommendation
Add the same HTML/JS-unsafe character escaping present in `src/google/protobuf/json/internal/writer.cc`'s `MustEscape` (escaping `<`, `>`, and the same Unicode confusable ranges) into `upb/json/encode.c`'s `jsonenc_put_escaped_char`/`jsonenc_stringbody`, so that PHP, Ruby, and any other upb-backed language binding produce JSON consistent with the C++/Java/C# writers. Add a regression test in `upb/json/encode_test.cc` mirroring `testHtmlEscape` in `JsonFormatTest.java` and `HtmlEscape` in `json_test.cc` to lock in the fix.

### Proof of Concept
Using the Ruby or PHP native extension (upb backend):
1. Set a string field to `</script><script>alert(1)</script>`.
2. Call `to_json` (Ruby) / `serializeToJsonString()` (PHP).
3. Observe the output contains the raw substring `</script><script>alert(1)</script>` verbatim, whereas the equivalent C++ (`ToJson`, tested in `src/google/protobuf/json/json_test.cc:1583-1589`) or Java (`JsonFormat.printer().print(...)`, tested in `JsonFormatTest.java:2016-2035`) call on the same message would emit `\u003c/script\u003e\u003cscript\u003ealert(1)\u003c/script\u003e`.
This confirms the escaping gap is specific to the upb encoder path (`upb/json/encode.c`) and is exploitable whenever the resulting JSON is embedded in an HTML/script context by the consuming application. [6](#0-5) [1](#0-0) [3](#0-2) [7](#0-6) [8](#0-7)

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}
