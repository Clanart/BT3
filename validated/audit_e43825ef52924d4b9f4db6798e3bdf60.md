## Analysis

The Initia report's core broken invariant is: **a threshold/quorum check sums voting power per submitted vote without deduplicating by validator identity**, letting one validator's vote be effectively counted more than once (or unauthenticated duplicate entries inflate the tally) to cross a `2/3+1` supermajority bar.

Hyperbridge has the exact same threshold-counting pattern in its BEEFY consensus client, and — critically — sibling consensus verifiers in this same repo explicitly guard against this class of bug while the BEEFY verifier does not.

### Title
BEEFY consensus proof supermajority check counts raw vote/signature count without deduplicating authority index, unlike every other verifier in the repo - (File: `evm/src/consensus/EcdsaBeefy.sol`, `modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` and its Rust counterpart `verify_mmr_update_proof` derive the supermajority participation count directly from `votes.length` / `signatures.len()` and feed each vote's `authorityIndex`/`sig.index` into a merkle multi-proof of membership, but never check that the set of `authorityIndex` values submitted is unique before comparing the count against the `2/3+1` threshold [1](#0-0) . Every other consensus verifier in this repository explicitly rejects duplicated voter/validator identities before doing the same supermajority arithmetic: Tendermint's `ensure_unique_addresses` [2](#0-1) , Pharos's `verify_validator_membership` returning `Error::DuplicateParticipant` [3](#0-2) , and BSC's bitmap-based vote set which is structurally unable to double-count a bit [4](#0-3) . BEEFY is the outlier that has no such guard.

### Finding Description
In `verifyMmrUpdateProof`, `sigLen = relayProof.signedCommitment.votes.length` is computed straight from the caller-supplied `votes` array, and this raw length is what's passed into `checkParticipationThreshold(sigLen, authoritySet.len)` [5](#0-4) . The loop that follows recovers a signer address per vote and constructs a `MerkleMultiProof.Leaf` keyed by `vote.authorityIndex` for membership verification [6](#0-5) . Nowhere is `vote.authorityIndex` (or the recovered `authority` address) checked for uniqueness across the `votes` array before `sigLen` is compared to the threshold, and `checkParticipationThreshold` itself does pure arithmetic on the count with no identity awareness [7](#0-6) .

The Rust BEEFY verifier has the identical structure: `signatures_length = mmr.signed_commitment.signatures.len()` feeds `check_participation_threshold`, and the loop over `mmr.signed_commitment.signatures` pushes `sig.index` into `authority_indices` with no dedup check before the merkle proof and threshold checks [8](#0-7) [9](#0-8) .

By contrast, GRANDPA's justification verifier explicitly rejects `num_duplicated_precommits() > 0` [10](#0-9) , and Pharos has a dedicated test (`test_duplicate_participant_keys_rejected`) proving the guard is load-bearing [11](#0-10) . This shows the project is aware that duplicate voter entries must be excluded from quorum counts, yet the guard was omitted specifically in the BEEFY path (both Solidity and Rust implementations), which is the consensus client actually used to bridge relay-chain/parachain state into Hyperbridge (per `IConsensusV2.verify`) [12](#0-11) .

### Impact Explanation
If duplicate `authorityIndex`/`sig.index` entries (each with a valid signature from the same real authority, recoverable/verifiable trivially since the authority's own signature over the commitment is by definition valid) are accepted as separate "votes" toward `sigLen`/`signatures_length`, an attacker who controls or replays a much smaller number of real signatures than `2/3+1` of the authority set could pad `votes`/`signatures` with repeats of the same authority index to clear the threshold check. This directly enables **false state acceptance**: `verifyMmrUpdateProof`/`verify_mmr_update_proof` would accept an MMR root/authority-set rotation and finalized parachain headers that were never actually finalized by consensus, letting forged state commitments (and therefore forged cross-chain messages relying on those commitments) be treated as trusted by Hyperbridge — a direct violation of the "consensus proofs ... must never let false remote state become trusted" pivot.

### Likelihood Explanation
This does not require a malicious relayer, prover, or admin — any unprivileged party constructing the `BeefyConsensusProof`/`ConsensusMessage` calldata submitted to `IConsensusV2.verify` can supply an arbitrary `votes`/`signatures` array. The only prerequisite is obtaining a small number of genuine authority signatures over a commitment (which is public data broadcast by the relay chain in normal operation), then repeating those entries under distinct array slots. Whether this fully succeeds end-to-end depends on how the external `MerkleMultiProof`/`rs_merkle` multi-proof verification libraries handle duplicate index entries in the leaf set (these libraries are not vendored in this repo, so their exact duplicate-index handling could not be directly inspected here) — but the local `sigLen`/`signatures_length` computation itself performs no deduplication regardless of library behavior, which is the same class of gap the Initia report flagged as medium/high severity.

### Recommendation
Mirror the pattern already used elsewhere in this repository: before computing `sigLen`/`signatures_length` and comparing against the participation threshold, deduplicate on `authorityIndex`/`sig.index` (e.g., a `BTreeSet`/mapping check as in `ensure_unique_addresses` and `verify_validator_membership`) and revert/error on any duplicate, exactly as recommended in the Initia report's mitigation for `ValidateVoteExtensions`.

### Proof of Concept
1. Obtain `t` genuine ECDSA signatures from `t` real BEEFY authorities over a commitment, where `t < (2/3 * authoritySet.len) + 1`.
2. Build `relayProof.signedCommitment.votes` with more than `t` entries by repeating one or more of the genuine `(authorityIndex, signature)` pairs, so `votes.length >= (2/3 * authoritySet.len) + 1`.
3. Call `EcdsaBeefy.verify(previousState, proof)`. `sigLen = votes.length` passes `checkParticipationThreshold`, and each repeated `Vote` recovers to a valid authority address which is a legitimate merkle leaf, so `MerkleMultiProof.VerifyProof` is presented with a leaf set drawn from genuinely valid (but duplicated) authority memberships.
4. If the underlying multi-proof verification does not itself reject duplicate index entries, the forged commitment (and any MMR/parachain-header state bundled with it) is accepted as finalized despite only `t` real signers having actually attested to it — never reaching the true `2/3+1` supermajority.

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
