### Title
ERC721→CW721 pointer's `transfer_nft` uses raw `transferFrom` instead of `safeTransferFrom`, permanently locking underlying ERC721 tokens - (File: `example/cosmwasm/cw721/src/contract.rs`)

### Summary
The `ERC721toCW721` pointer contract (a CosmWasm contract that represents a native EVM ERC721 collection on the Cosmos/CW721 side) moves the real, underlying ERC721 token via a raw `transferFrom` call instead of `safeTransferFrom` whenever a CW721 `transfer_nft`/`send_nft` message is executed. This is the same bug class as the reported `FuelERC721Gateway.finalizeWithdrawal()` issue: an intermediary/gateway contract moves a real ERC721 token to an arbitrary recipient address using `transferFrom`, with no check that the recipient can handle the token, risking permanent loss.

### Finding Description
The pointer's `transfer_nft` handler builds the underlying-ERC721 transfer payload and dispatches it as a delegatecall to the real ERC721 contract: [1](#0-0) 

The payload itself is built by `HandleERC721TransferPayload`, which ABI-encodes a call to `transferFrom` (function selector `0x23b872dd`), not `safeTransferFrom`: [2](#0-1) 

The resulting `EvmMsg::DelegateCallEvm` executes this `transferFrom` payload against the real ERC721 contract on behalf of the pointer contract, so the pointer contract's own address is used as `msg.sender` for the delegatecall, moving actual ERC721 ownership from the current owner to `recipient` (an EVM address derived from the Sei address supplied in the CW721 message). The `IERC721.transferFrom` interface used never triggers `onERC721Received`, so if `recipient` resolves to a contract that is not ERC721-aware, the transfer succeeds but the token becomes inaccessible to that contract.

This mirrors the `IERC721Upgradeable(tokenAddress).transferFrom(address(this), to, tokenId)` pattern flagged in the Fuel report: a bridge/pointer contract forwards a real NFT to an externally-supplied recipient using the unsafe `transferFrom` variant.

### Impact Explanation
Any user who can execute a `transfer_nft` (or `send_nft`) message against an ERC721→CW721 pointer contract — reachable by any wasm message sender, including via `MsgExecuteContract` from a plain Cosmos account or from another contract — can send the real, underlying ERC721 token to any EVM address, including ones belonging to smart contracts that have no support for holding/moving ERC721 tokens (no `onERC721Received`, and no logic to call `transferFrom`/`approve` on themselves as an owner). Because the transfer uses `transferFrom` rather than `safeTransferFrom`, there is no revert or receiver-capability check, and the token can end up permanently stuck at that address, i.e. permanent freezing/loss of the NFT — a concrete impact matching the "Accept" criteria (permanent freezing of funds/assets).

### Likelihood Explanation
This is reachable purely through wasm message submission — no privileged role, validator, or node-operator access is required. A user only needs to `execute` the pointer's `transfer_nft`/`send_nft` message with a `recipient` that decodes (via `AddrPrecompile`/EVM-Sei address association) to a smart-contract address lacking ERC721-receiver support. Given ERC721↔CW721 pointers are a core, user-facing bridging feature (`registerPointerForERC721`, `deployErc721PointerForCw721`), and recipients are freely specifiable strings, the likelihood of an accidental or malicious transfer to a non-receiving contract is realistic — the bug does not require any unusual preconditions.

### Recommendation
Change `HandleERC721TransferPayload` in `x/evm/client/wasm/query.go` to ABI-pack `safeTransferFrom(address,address,uint256)` instead of `transferFrom`, and update the `transfer_nft` flow in `example/cosmwasm/cw721/src/contract.rs` accordingly, so that the underlying ERC721 contract enforces `onERC721Received` semantics when the recipient is a contract, causing the transfer to revert rather than silently locking the token.

### Proof of Concept
1. Deploy a native ERC721 collection and register an ERC721→CW721 pointer via `registerPointerForERC721`/`deployErc721PointerForCw721` (as exercised in `contracts/test/ERC721toCW721PointerTest.js`).
2. Deploy an arbitrary EVM contract (e.g., a simple vault) that does **not** implement `IERC721Receiver`, and associate/derive a Sei address for it (any EVM contract has an implicit Sei-side address mapping).
3. As the owner of a token on the pointer's CW721 side, execute `{"transfer_nft": {"recipient": "<sei-address-of-the-non-receiving-contract>", "token_id": "<id>"}}`.
4. Observe that `transfer_nft` (`example/cosmwasm/cw721/src/contract.rs#L175-192`) succeeds because it calls `erc721_transfer_payload`, which encodes a plain `transferFrom` (`x/evm/client/wasm/query.go#L202-225`), so no `onERC721Received` check is performed.
5. The underlying ERC721 token is now owned by the non-receiving contract; since that contract has no logic to call `transferFrom`/`approve` on itself, the NFT is permanently locked.

```rust
fn transfer_nft(
    deps: DepsMut<EvmQueryWrapper>,
    info: &MessageInfo,
    recipient: &str,
    token_id: &str,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(recipient)?;

    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let owner = querier.erc721_owner(info.sender.to_string(), erc_addr.to_string(), token_id.to_string())?.owner;
    let payload = querier.erc721_transfer_payload(owner, recipient.to_string(), token_id.to_string())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new().add_message(msg);

    Ok(res)
}
```

```go
func (h *EVMQueryHandler) HandleERC721TransferPayload(ctx sdk.Context, from string, recipient string, tokenId string) ([]byte, error) {
	abi, err := cw721.Cw721MetaData.GetAbi()
	if err != nil {
		return nil, err
	}
	fromEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(from))
	if !found {
		return nil, types.NewAssociationMissingErr(from)
	}
	toEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(recipient))
	if !found {
		return nil, types.NewAssociationMissingErr(recipient)
	}
	t, ok := sdk.NewIntFromString(tokenId)
	if !ok {
		return nil, errors.New("invalid token ID for ERC721, must be a big Int")
	}
	bz, err := abi.Pack("transferFrom", fromEvmAddr, toEvmAddr, t.BigInt())
	if err != nil {
		return nil, err
	}
	res := bindings.ERCPayloadResponse{EncodedPayload: base64.StdEncoding.EncodeToString(bz)}
	return json.Marshal(res)
}
```
