### Title
GitHub Enterprise sign-in flow can be spoofed to an attacker-controlled host via forged `WWW-Authenticate` realm - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The 0x report describes a case where a trust classification ("delegated" vs "direct" stake, which controls reward weighting) can be forged by an external contract that misrepresents its true nature to gain a more favorable trust level. The GitHub Desktop analog is `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts`, which classifies an unknown Git remote host as `'enterprise'` (i.e., a trusted GitHub Enterprise server) based on an attacker-controllable signal — the `WWW-Authenticate` realm string returned by the remote server during a Git HTTP authentication handshake — rather than any cryptographically verified property.

### Finding Description
When Git needs credentials for a remote, Desktop's trampoline credential helper is invoked to decide how to authenticate. `getEndpointKind` determines the "kind" of endpoint (`'github.com'`, `'ghe.com'`, `'enterprise'`, or `'generic'`), and this classification changes trust behavior: [1](#0-0) 

Crucially, when the host is neither `github.com` nor a known `.ghe.com` domain, the code falls back to trusting a `WWW-Authenticate` header value forwarded by Git from the remote HTTP server: if it contains `realm="GitHub"`, the endpoint is classified as `'enterprise'`: [2](#0-1) 

This header is fully attacker-controlled — any HTTP server the user's Git client talks to (including a malicious/compromised remote, or a machine-in-the-middle proxy on an unauthenticated HTTP transport, or simply an attacker-hosted `http(s)://` remote the victim was tricked into adding/cloning) can respond to the unauthenticated probe with `WWW-Authenticate: Basic realm="GitHub"` and force this classification, without needing to match any real GitHub domain pattern or TLS/certificate property.

Once classified as `'enterprise'` and no existing account matches that endpoint, `getCredential` proceeds to invoke the GitHub sign-in UI directly against the attacker's endpoint: [3](#0-2) 

`ui.promptForGitHubSignIn(endpoint)` then reads the hostname/origin straight from the attacker-controlled URL and kicks off `dispatcher.beginEnterpriseSignIn` / `setSignInEndpoint(origin)` using that origin as the actual GHE server to authenticate against: [4](#0-3) 

This presents the user with what looks like a legitimate "Sign in to GitHub Enterprise" dialog, but the enterprise API/OAuth endpoint being contacted is the attacker's server — chosen entirely by the attacker via the spoofed header, not by anything the user configured as a trusted GHE instance.

### Impact Explanation
If the user completes the sign-in flow believing it is a normal Desktop authentication prompt, their GitHub Enterprise credentials, OAuth authorization, or resulting token exchange will be conducted against the attacker's server, resulting in credential/token exfiltration and an unauthorized "account binding" to an attacker-controlled endpoint — this matches the "unauthorized OAuth or account binding" / "credential exfiltration" impact classes explicitly called out as valid. Unlike the legitimate GHE detection paths (`isDotCom`, `isGHE`, direct `.github.` hostname pattern match, or an authenticated `isGitHubHost` meta-endpoint probe with a real `x-github-request-id` response header), the `wwwauth[...]` fallback trusts an easily forged string with no verification of the actual server identity.

### Likelihood Explanation
The attacker primitive required is exactly the sanctioned scope: control of a git remote/proxy response. Getting a victim to add or clone from an attacker-controlled HTTP(S) remote (e.g., via a malicious fork URL, a "helpful" clone link, or a MITM proxy on plain HTTP) is a normal, low-friction Desktop workflow (paste a URL into Clone/Add Remote), not a contrived local-access or malware scenario. The only additional condition is that the user must not already have an account entry matching that endpoint and must proceed through the resulting sign-in prompt — the same level of user interaction expected in normal credential-prompt flows, not "unnatural user steps."

### Recommendation
Do not use the `WWW-Authenticate` realm string as a basis for classifying an endpoint as a trusted GitHub Enterprise server. Restrict the `'enterprise'` classification to endpoints that either match a hostname pattern already trusted for other reasons, or that are confirmed via the existing authenticated `isGitHubHost` request path (checking `x-github-request-id`) before presenting the sign-in UI. If the header hint is retained as a fast path, it should only be used as a hint to *offer* a "this looks like a GitHub server, verify?" affordance rather than being sufficient by itself to launch the enterprise OAuth/sign-in flow against the attacker-chosen origin.

### Proof of Concept
1. Attacker stands up an HTTP(S) server (or a MITM proxy in front of one) at `https://evil.example.com/some/repo.git`.
2. Server responds to Git's unauthenticated request with `WWW-Authenticate: Basic realm="GitHub"`.
3. Victim adds this URL as a remote in Desktop (e.g., via Clone or "Add Existing Repository" + fetch), triggering a credential helper `get` call.
4. In `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`), the header match returns `'enterprise'`.
5. Since no account exists for `evil.example.com`, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com')` (lines 109-125), which starts the Enterprise sign-in flow pointed at `evil.example.com` via `trampoline-ui-helper.ts:87-93`.
6. Victim, believing this is a legitimate Desktop GHE sign-in prompt, authenticates — their credentials/OAuth flow are conducted with the attacker's server.

```typescript
const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
```
