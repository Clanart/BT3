## Analysis Summary

The strongest analog to the Deneb tree-height bug is a **structural-ambiguity parsing bug** in `parseRawLogWithNumstat()` in `app/src/lib/git/log.ts`. Both bugs share the same root cause: a parser assumes a fixed, unambiguous shape for a data stream, but an attacker can craft a "leaf" value that is indistinguishable from a structural "header" token, causing the parser's state machine to desynchronize.### Title
Ambiguous `-z --raw --numstat` parser lets an attacker-named file be mis-parsed as a diff header, corrupting the file/diff mapping shown to reviewers - (File: `app/src/lib/git/log.ts`)

### Summary
`BeaconChainProofs.verifyWithdrawal()` assumed a fixed, unchanging tree structure (constant height 4) and therefore could not tell a legitimate leaf from an attacker-crafted "leaf" that actually collides with an internal node's encoding (a second-preimage style confusion). The GitHub Desktop analog is in `parseRawLogWithNumstat()` (`app/src/lib/git/log.ts:276-334`), which parses `git log/diff -z --raw --numstat` output using a state machine that assumes every NUL-delimited token is *either* a diff-header line (identified solely by `line.startsWith(':')`) *or* a path/numstat line — never both. A file path is untrusted, attacker-controlled data (it comes from a cloned/fetched repository), and nothing prevents a path from itself starting with `:`, which makes it visually and structurally indistinguishable from a real header token to this parser. This is the same class of bug: an assumption about fixed/unambiguous structure that breaks when the attacker controls the "leaf" content.

### Finding Description
`parseRawLogWithNumstat` is fed the buffered stdout of `git log ... --raw --numstat -z` (used by `getChangedFiles`, `app/src/lib/git/log.ts:219-245`) and `git diff --raw --numstat -z` (used by `getBranchMergeBaseChangedFiles` and `getCommitRangeChangedFiles`, `app/src/lib/git/diff.ts:252-335`), as well as `git stash show --raw --numstat -z` (`getStashedFiles`, `app/src/lib/git/stash.ts:279-297`).

The function splits the buffer on `\0` and walks the tokens with a single discriminator: [1](#0-0) 

If the token starts with `:` it is treated as a new raw-diff header (`:<srcMode> <dstMode> <srcSha> <dstSha> <status>`), and the following one or two tokens are consumed as `oldPath`/`path`: [2](#0-1) 

Otherwise the token is assumed to be a numstat line, and the code advances `numStatCount` in lock-step with `files[]`, using `files[numStatCount].status` to decide whether to additionally skip 2 tokens for renamed/copied entries: [3](#0-2) 

Nothing validates that a "path" token is actually a path and not a header look-alike. A file whose name simply begins with `:` (e.g. `:pwn`, or fully mimicking the header shape `:100644 100644 aaaa bbbb M`) is a legal filename on Linux/macOS and can be created via ordinary `git add`/`git commit` or low-level plumbing (`git hash-object`, `git update-index`, `git commit-tree`) by anyone crafting a repository to be cloned or fetched by a victim. When such a path token is encountered where the parser expects a *value* (a "leaf"), the `if (line.startsWith(':'))` branch fires instead, and the state machine misinterprets it as a new diff header. This desynchronizes the `files[]` array from the numstat section for every subsequent entry in the same commit's diff output — exactly the "leaf posing as an intermediate node" failure mode described in the original report, except here it corrupts an index correlation instead of a Merkle proof.

Consequences of the desync:
- `files[numStatCount]` can point to the wrong `CommittedFileChange`, so a numstat line's added/deleted counts, and the copy/rename-skip logic (`isCopyOrRename(files[numStatCount].status)`), are applied to the wrong file.
- Subsequent iterations consume the wrong number of tokens (`i += 2` fired incorrectly, or not fired when it should have been), shifting alignment for every file that follows in that diff.
- `forceUnwrap` calls (`'Invalid log output (srcMode)'`, `'Missing path'`, `'Invalid numstat line'`) can throw once misalignment causes a token to fail to match the expected shape, but more importantly the corruption can also succeed silently, associating the wrong file path with a completely different status/diff.

Existing guards do not stop this path: there is no filename sanitization, no escaping of the `:` character, and no structural marker distinguishing "this token is a path" from "this token is a header" beyond the leading-colon heuristic that user-controlled paths can trivially satisfy. `git`'s own machine-readable `-z` format guarantees NUL-delimited fields, but it does not (and cannot) guarantee that a path's *first character* differs from the header sigil — Desktop's parser relies on an assumption `git` does not enforce.

### Impact Explanation
The parsed `CommittedFileChange[]` (path + status) drives the Changes/History file list and, downstream, `getCommitDiff`/`getWorkingDirectoryDiff` type flows that fetch and render the diff for "the selected file" using `file.path` and `file.status`. If an attacker's crafted repository (cloned or fetched by the victim) desynchronizes this list, a reviewer in Desktop's History or PR-review UI can be shown:
- an incorrect file name/status pairing (e.g., a large/malicious change attributed to what looks like a trivial rename), or
- a thrown exception that aborts loading the correct changed-files list for a commit.

This falls squarely in the requested impact category of "silent corruption of what the user commits or pushes": the user's mental model of what a commit/PR actually changes can be misrepresented before they act on it (approve, merge, cherry-pick, or push), because the file/diff association itself — not just cosmetic rendering — is computed from the corrupted array.

### Likelihood Explanation
The trigger condition is trivial to construct: any file path beginning with the ASCII colon character (`:`) in a commit that is diffed by Desktop is sufficient to enter the wrong branch of the parser. No unusual git configuration, network position, or elevated privileges are required — only that the victim clone/fetch a repository containing such a commit and view that commit's changed files (a completely ordinary Desktop workflow: browsing History, viewing a PR's changed files, or comparing branches via `getBranchMergeBaseChangedFiles`/`getCommitRangeChangedFiles`). This matches the requested threat model of "attacker controls a cloned/fetched repository."

I was not able to execute the parser in a live environment to confirm the exact downstream rendering behavior (whether the UI silently shows a wrong diff versus throwing and blocking the view) since this is a static code review; that would need to be validated empirically before assigning a final severity, but the code path and the ambiguity itself are directly evidenced in `app/src/lib/git/log.ts`.

### Recommendation
Do not use a positional/heuristic discriminator (`line.startsWith(':')`) to distinguish structural header tokens from path/leaf values in NUL-delimited git output. Options:
1. Use a numstat/raw parsing strategy where the number of tokens per record is deterministically known ahead of time from the `git` invocation flags (similar to `createLogParser`'s fixed key-count scheme), rather than inferred from content that includes attacker-controlled paths.
2. When consuming `--raw` output, use `-z` combined with an unambiguous encoding, or invoke `git diff-tree`/`git diff --raw` and `--numstat` in separate, independently-parsed invocations, so a path value's content can never be confused with a header line.
3. At minimum, validate that a "path" token has the exact shape expected by counting remaining fields per commit and asserting a fixed record layout, rather than branching solely on the leading character.

### Proof of Concept
1. Create a repository containing a commit that adds a file literally named `:pwn.txt` (or, for full ambiguity, `:100644 100644 aaaaaaa0 bbbbbbb0 M`) alongside at least one other normal file, e.g.:
   ```
   git init poc
   cd poc
   printf 'a' > normal.txt
   printf 'b' > ':pwn.txt'
   git add normal.txt ':pwn.txt'
   git commit -m 'poc'
   ```
2. Have the victim clone this repository in GitHub Desktop and open the commit in History (which invokes `getChangedFiles` → `parseRawLogWithNumstat`, `app/src/lib/git/log.ts:219-245, 276-334`).
3. Observe that the numstat token for `normal.txt` is consumed as if it were a new diff header/path pair because it does not start with `:`... conversely, the `:pwn.txt` numstat/raw line is misclassified due to `startsWith(':')`, offsetting `files[]`/`numStatCount` correlation for the remainder of the commit's file list, producing either a `forceUnwrap` exception ("Invalid numstat line" / "Missing path") or a wrong path-to-status/diff pairing in the resulting `IChangesetData`.
