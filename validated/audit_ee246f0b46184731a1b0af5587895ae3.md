### Title
Reward forfeiture bypass via `cancelUnlock` state manipulation before `multiclaimFor` - ([File: VLMGP.sol / rewards/vlMGPBaseRewarder.sol])

### Summary
An attacker who has locked MGP into `VLMGP` can start a cooldown (`startUnlock`), let the MGP staking reward accrue in `MasterMagpie` while a large share of their balance sits in cooldown (which should reduce `getRewardablePercentWAD`), then call `cancelUnlock` immediately before `multiclaimFor` to reset their rewardable percent back to ~100% without any forced harvest. This makes `vlMGPBaseRewarder._calExpireForfeit` compute `forfeitAmount = 0` on the full pending MGP even though most of the accrual period should have resulted in a forfeiture that is redistributed to other, fully-locked stakers.

### Finding Description
`getRewardablePercentWAD` in `VLMGP.sol` computes a percent based on the user's *current* split between "fully locked" and "in cooldown" MGP: [1](#0-0) 

This percent is used at the moment of reward claim, in `vlMGPBaseRewarder._calExpireForfeit`, to determine how much of the pending, previously-accrued MGP the account forfeits: [2](#0-1) 

The forfeited amount is queued back into the rewarder as bonus rewards for other lockers via `_queueNewRewardsWithoutTransfer`/`queueMGP`, so forfeiture is meant to punish accounts that reduce lock commitment during the accrual window: [3](#0-2) 

Crucially, the base MGP staking reward stream in `MasterMagpie` accrues purely on `user.amount` for the `vlmgp` staking token, which is **not reduced** when the user starts a cooldown (only the VLMGP-level split between "locked" and "in cooldown" changes, tracked separately in `userUnlockings`): [4](#0-3) [5](#0-4) 

`unlock()` and `startUnlock()` both correctly call `multiclaimFor` **before** mutating cooldown state, forcing a harvest at the "before" percent: [6](#0-5) [7](#0-6) 

However, `cancelUnlock()` does **not** follow this pattern — it directly zeroes `slot.amountInCoolDown` and decrements `totalAmountInCoolDown` with no preceding `multiclaimFor`/harvest call and no `nonReentrant` guard: [8](#0-7) 

Exploit flow:
1. Attacker locks MGP into `VLMGP`, accruing MGP staking rewards in `MasterMagpie` for the `vlmgp` pool.
2. Attacker calls `startUnlock(largeAmount)` to move most of their balance into cooldown. This forces a harvest first (at 100% percent, so no loss yet), then the state moves a large fraction to cooldown, dropping `getRewardablePercentWAD` for future harvests.
3. Time passes; MGP reward continues to accrue in `MasterMagpie` on the full `user.amount` (cooldown status is irrelevant to base emission).
4. Immediately before harvesting, attacker calls `cancelUnlock(slotIndex)` — no cooldown period wait required, no harvest triggered — instantly restoring `getUserTotalLocked` to the full amount and `getRewardablePercentWAD` to ~100%.
5. Attacker calls `multiclaimFor([vlmgp], _rewardTokens, attacker)` → `MasterMagpie._sendMGPForVlMGPPool` → `vlMGPRewarder.queueMGP` → `_calExpireForfeit` now sees 100% rewardable, so `forfeitAmount = 0` and the attacker receives the entire pending MGP, none of which is redirected to the forfeit pool for other lockers.
6. Attacker can immediately re-enter cooldown (`startUnlock` again, which harvests first at the just-reset 100% baseline) and repeat, indefinitely avoiding forfeiture while enjoying full staking-reward accrual and optionality to eventually withdraw.

Existing checks (`whenNotPaused`, `_checkInCoolDown`, `_checkIdexInBoundary`) do not prevent this because they only validate the unlock slot exists and is currently in cooldown — they do not force a reward harvest before allowing the state (and thus `getRewardablePercentWAD`) to be reset.

### Impact Explanation
This allows an unprivileged staker to permanently avoid the reward-forfeiture mechanism that funds the bonus reward pool for fully-committed lockers, diverting yield that should be redistributed to other vlMGP holders to themselves instead. This is a theft of unclaimed yield belonging to other stakers (Immunefi: "Theft of unclaimed yield"), executed repeatedly at negligible cost (gas only).

### Likelihood Explanation
Preconditions are minimal: any user who has locked MGP into `VLMGP` (no special role required) can trigger `startUnlock`/`cancelUnlock`/`multiclaimFor` freely. The exploit is fully repeatable each cooldown cycle and requires no flash loans or front-running — the attacker fully controls the transaction ordering (`cancelUnlock` then `multiclaimFor` can even be done via a single external call to a helper contract or bundled by the attacker themselves without needing atomicity from anyone else).

### Recommendation
Make `cancelUnlock` symmetric with `unlock`/`startUnlock`: force a `multiclaimFor`/harvest of the vlMGP pool for `msg.sender` at the pre-cancellation `getRewardablePercentWAD` **before** mutating `slot.amountInCoolDown`/`totalAmountInCoolDown`, and add `nonReentrant`. Alternatively, redesign forfeiture accounting to be time-weighted over the accrual period (e.g., checkpoint rewardable percent whenever it changes and integrate it, rather than applying only the percent at claim time to the entire pending balance).

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `VLMGP`, `vlMGPBaseRewarder` per existing test harness; register `vlmgp` pool with MGP emission.
2. Attacker locks `1000 MGP` via `VLMGP.lock`.
3. Advance time, call `startUnlock(900e18)` to put 90% into cooldown (this internally harvests once at 100% baseline — assert `forfeitAmount == 0` for this initial harvest).
4. Advance time further (e.g. half the cooldown period) so pending MGP reward accrues while `getRewardablePercentWAD(attacker)` ≈ 10%.
5. Record `expectedForfeit = pendingMGP * (1e18 - rewardablePercentWAD) / 1e18` computed at this point (what should be forfeited if harvested now).
6. Call `VLMGP.cancelUnlock(slotIndex)` (no harvest triggered, no cooldown wait needed).
7. Call `MasterMagpie.multiclaimFor([vlmgp], [[]], attacker)`.
8. Assert: attacker receives full `pendingMGP` with `forfeitAmount == 0` (via `MGPHarvested` event or querying vlMGPBaseRewarder `rewards[MGP].queuedRewards`/`historicalRewards` unchanged), proving `expectedForfeit` (step 5) was never captured for the bonus pool, unlike the case where the same flow is run without calling `cancelUnlock` first (control test showing correct forfeiture applied).

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
