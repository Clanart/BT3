### Title
Deserialized `ThresholdKeys` can carry an identity/attacker-controlled group key because `ThresholdKeys::new` never checks the secret share against the verification shares — (File: crypto/dkg/src/lib.rs)

### Summary
The external report describes a system left without an operator/admin: the privileged role becomes vacant, so critical actions become impossible (or belong to no one). The analog in Serai is a threshold key set whose "operator capability" — the group key — is vacant. `ThresholdKeys::read` accepts untrusted bytes and calls `ThresholdKeys::new`, which validates only the count and participant-index bounds of `verification_shares` (crypto/dkg/src/lib.rs:355-365). It never checks:

1. that `C::generator() * secret_share == verification_shares[i]` (self-consistency), or
2. that the derived `group_key` (computed as the Lagrange/Constant-interpolated sum of the first `t` verification shares, lines 376-378) is non-identity / well-formed.

An attacker can therefore craft a `ThresholdKeys` blob — e.g. `t = 1`, `verification_shares[1] = identity`, arbitrary `secret_share` — that deserializes successfully and yields `group_key() == identity`.

### Finding Description
`ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) builds `group_key` purely from the supplied `verification_shares`:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

With `t = 1` and `Interpolation::Lagrange`, the interpolation factor for the single included participant is `1`, so `group_key == verification_shares[1]` verbatim. Neither `new` nor `read` (lines 574-632) rejects identity `C::G` values in `verification_shares`, nor does anything verify `C::generator() * secret_share == verification_shares[params.i()]`. `view()` then interpolates `secret_share` without any consistency check against `group_key` (lines 463-533), and `sign`/`complete` flows in crypto/frost produce signatures over whatever `group_key()` returns.

This is the "lost role" analog: a key container that parses successfully, is treated as authoritative for who may sign, yet corresponds to a secret (`0`, or an attacker-chosen value) held by no legitimate participant — or equivalently held by everyone, since `identity` is the public key of the secret `0`.

### Impact Explanation
Any downstream verifier that trusts `keys.group_key()` (or `original_group_key()`) as the signature-verification public key will accept trivially forged signatures. A Schnorr/FROST signature `(R, s)` under a group key `P = identity` verifies iff `s·G == R + c·P = R`, i.e. any `(s·G, s)` pair is a valid forgery with no secret knowledge. For bitcoin-serai this maps to outputs "owned" by an identity/tweaked key: funds reported received under such a key are spendable by anyone (or unspendable). Additionally, an attacker can set `verification_shares[1]` equal to an honest victim's public key while supplying `secret_share = 0`, producing a key set that claims authority under the victim's identity while containing no valid share.

### Likelihood Explanation
The rules of engagement explicitly count untrusted bytes fed to `ThresholdKeys::read` as attacker-reachable. Any component that loads `ThresholdKeys` from a channel an unprivileged party can influence (network transport, shared storage, peer-supplied backup/recovery blobs) is exposed. No threshold of colluding validators, leaked keys, or malicious node is required — only the ability to supply bytes to the deserialization path.

### Recommendation
In `ThresholdKeys::new` (or `read`), enforce:

- `verification_shares[&params.i()] == C::generator() * secret_share` (self-share consistency),
- `group_key` is non-identity,
- all `verification_shares` values are non-identity (rejecting identity early also prevents trivial interpolation collapse).

### Proof of Concept
Conceptual byte-level PoC (Ristretto):

1. Serialize: `C::ID`, `t = 1`, `n = 1`, `i = 1`, `Interpolation::Lagrange` (byte `1`), `secret_share = 0` (or arbitrary), `verification_shares[1] = identity` (all-zero compressed point).
2. `ThresholdKeys::<Ristretto>::read(&mut bytes)` returns `Ok`.
3. `keys.group_key()` returns `Ristretto::identity()`.
4. For any message `m`, compute `c = H(R || P || m)` as the verifier would; publish `(R = s·G, s)` for arbitrary `s`. Verification `s·G == R + c·P` holds since `P = identity` — a forged signature with no private input.

The root cause is the absence of the share↔verification consistency check in `ThresholdKeys::new` / `read` (crypto/dkg/src/lib.rs:349-391, 574-632).
