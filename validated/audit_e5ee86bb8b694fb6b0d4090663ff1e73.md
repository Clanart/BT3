### Title
`ThresholdKeys::read` accepts attacker-crafted key material with identity verification shares, yielding a `group_key` of identity (private key 0) - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes `t`, `n`, `i`, the interpolation method, `secret_share`, and `n` verification shares entirely from the byte stream. `ThresholdKeys::new` validates counts, indexes, and `t <= n`, but never rejects identity verification shares (it uses `Ciphersuite::read_G`, not `Curve::read_G`, so identity is permitted), never checks `verification_shares[i] == generator() * secret_share`, and never rejects an identity `group_key`. An attacker who can feed crafted bytes to `ThresholdKeys::read` can therefore instantiate keys whose group key is the identity point — i.e. a group private key of `0` known to everyone.

### Finding Description
- Deserialization path: `ThresholdKeys::read` reads `n` verification shares with `<C as Ciphersuite>::read_G(reader)` — canonical but identity-permitting — then calls `ThresholdKeys::new`.
- `ThresholdKeys::new` computes `group_key` as the interpolated sum of `verification_shares[1..=t]` with no identity check on inputs or result:
```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```
- With `Interpolation::Lagrange`, `t = 1`, `n = 1`, `i = 1`: the factor for participant 1 in the set `[1]` is `1`, so `group_key = verification_shares[1]`. Supplying the identity encoding sets `group_key` to identity.
- Additionally, nothing binds `secret_share` to `verification_shares[i]`: `new` accepts a `secret_share` inconsistent with the verification-share polynomial. This is the deserialization-gadget analog of CVE-2020-36188 — attacker-controlled bytes construct an internally-inconsistent object that later cryptographic consumers treat as valid.

### Impact Explanation
A key whose `group_key()` is the identity point corresponds to group secret `0`. Any FROST signature produced (or forged) under these keys verifies against public key `identity + offset` — a key whose discrete log the attacker knows. Any funds controlled by such a key are spendable by anyone, and any "threshold" security property is void: there is effectively no secret. Alternatively, a mismatched `secret_share`/`verification_shares[i]` pair lets an attacker plant keys that sign with one share while verifying against another, corrupting the signing set the node believes it belongs to.

### Likelihood Explanation
Reachable wherever serialized `ThresholdKeys` cross a trust boundary (restored key material, imported shares, bytes read via `ThresholdKeys::read` from a peer-controlled source). The input is fully attacker-controlled public bytes; no collusion or privileged position is needed — the rules explicitly list `ThresholdKeys::read` as an in-scope untrusted input. Exploitation requires only encoding identity points and arbitrary scalars, which `Ciphersuite::read_G`/`read_F` accept.

### Recommendation
In `ThresholdKeys::read`/`ThresholdKeys::new`:
- Use `Curve`-style `read_G` or explicitly reject `is_identity()` verification shares.
- Verify `verification_shares[params.i()] == C::generator() * secret_share` on construction/deserialization.
- Reject a computed `group_key` that is identity.

### Proof of Concept
```rust
// For a Ciphersuite C with 32-byte encodings (e.g. Ristretto):
let mut buf = vec![];
buf.extend(&(C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&1u16.to_le_bytes()); // t = 1
buf.extend(&1u16.to_le_bytes()); // n = 1
buf.extend(&1u16.to_le_bytes()); // i = 1
buf.push(1);                     // Interpolation::Lagrange
buf.extend(C::F::ONE.to_repr().as_ref());            // secret_share (arbitrary)
buf.extend(C::G::identity().to_bytes().as_ref());    // verification_shares[1] = identity

let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap(); // accepted
assert!(bool::from(keys.group_key().is_identity())); // group secret is 0
// keys.view(vec![Participant::new(1).unwrap()]) now signs under public key = identity,
// a private key (0) known to the attacker.
```
The analogous malleability applies to any `t`/`n` when all verification shares in `1..=t` are identity.
