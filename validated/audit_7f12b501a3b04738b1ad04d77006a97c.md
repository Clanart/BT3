### Title
SignableTransaction fee calculation omits the OP_RETURN output, undercharging fees for transactions carrying data - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the transaction's weight/vbytes — and therefore `needed_fee` and the change-output decision — using only `payments`, which never includes the OP_RETURN data output that was already pushed into `tx_outs`. Any transaction built with `data = Some(_)` undercounts its real size by up to ~83 vbytes, pays a fee below the requested `fee_per_vbyte`, and can fall below the relay minimum despite passing the `TooLowFee` check.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` appends an OP_RETURN output to `tx_outs` when `data` is supplied (lines 194-202). However, the size used for fee accounting is computed as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204), where `payments` is the caller's `(ScriptBuf, u64)` slice — it does not include the data output. The same omission occurs in the change-path calculation at line 225-226 (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`).

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed on a smaller transaction than the one actually serialized into `tx` (lines 246-251), so the true fee rate is strictly less than `fee_per_vbyte`.
- The `TooLowFee` check (lines 211-213) validates the undercounted `needed_fee` against the undercounted `vbytes`, so a transaction whose *real* fee falls below `DEFAULT_MIN_RELAY_TX_FEE` still passes.
- The change decision (`input_sat.checked_sub(payment_sat + fee_with_change)` and `value >= DUST`, lines 228-234) uses the underestimated `fee_with_change`, and the change value `input_sat - payment_sat - fee_with_change` does not account for the OP_RETURN output's real cost — the transaction ends up paying `inputs - outputs`, which is correct in total but means the effective fee rate is lower than requested, and the change-vs-dust boundary is computed against the wrong fee.

This mirrors the report's class: fee accounting inconsistent with the value actually moved. Here the transaction "reports" a fee (`needed_fee`) that does not match the fee required for its real size, so funds are committed to a transaction that may not relay at the intended rate.

### Impact Explanation
A caller supplying `data` produces a transaction whose actual sat/vbyte is below `fee_per_vbyte` and potentially below the Bitcoin relay minimum. The signed transaction can be rejected or stuck in mempools, delaying spends of threshold-controlled UTXOs and requiring a new signing round to fix. The delta is bounded (~83 vbytes × fee rate), so the impact is a liveness/relaying failure and fee-rate misaccounting rather than direct theft — Medium.

### Likelihood Explanation
The bug triggers deterministically whenever `data` is `Some`, which is the standard path for embedding protocol data into bridge transactions. Any nonzero `fee_per_vbyte` is affected; transactions near the relay floor fail outright.

### Recommendation
Include the OP_RETURN output in the size estimate. Compute weight/vbytes over the final `tx_outs` (payments + data, and change where applicable) rather than over `payments` alone — e.g., change `calculate_weight_vbytes` to accept the full `Vec<TxOut>` being constructed, or add the serialized OP_RETURN output's weight to the estimate before computing `needed_fee` and the change threshold.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, None, Some(vec![0u8; 80]), fee_per_vbyte)`. The internal `vbytes` at line 204 reflects a transaction with only the payment outputs; the produced `tx` additionally contains an ~83-byte OP_RETURN output. `tx.fee()` (lines 138-141, `sum(inputs) - sum(outputs)`) equals `input_sat - payment_sat` while the true vsize is larger than `vbytes`, so `fee() / tx.vsize() < fee_per_vbyte`, and can be `< DEFAULT_MIN_RELAY_TX_FEE / 1000` even though `TooLowFee` was not raised.
