## Finding [1](#0-0) [2](#0-1) 

### Title
Stale bank events from a reverted nested precompile call are incorrectly re-aggregated into a sibling call's `BalanceHandler` window, desynchronizing EVM `StateDB` balances from real bank balances - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
`BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` reconstruct EVM `StateDB` balance deltas by diffing the Cosmos SDK `ctx.EventManager()` event slice against a recorded `prevEventsLen` index, rather than by directly reading canonical bank state. This design assumes the event-manager slice observed between "before" and "after" markers for a given precompile invocation exactly corresponds to that invocation's own bank effects. Two test suites already present in this repository — `evmd/tests/integration/balance_handler/balance_handler_test.go` and `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` — are explicitly written to exercise "the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated" and "recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten," leading to "balance desync between native bank keeper and EVM stateDB." This is the same invariant-violation class as the Curve V2 report: an oracle/accounting mechanism trusts an *assumption* about which state changes belong to which caller/scope, and that assumption breaks under nested/recursive execution, corrupting a downstream value used to move user funds.

### Finding Description
`BalanceHandler` (in `precompiles/common/balance_handler.go`) records `prevEventsLen = len(ctx.EventManager().Events())` before executing a precompile method, then on completion re-scans `events[prevEventsLen:]` for `EventTypeCoinSpent`/`EventTypeCoinReceived`/`EventTypeFractionalBalanceChange` and applies matching `StateDB.AddBalance`/`SubBalance` calls [3](#0-2) . This is invoked around every stateful precompile execution via `Precompile.runNativeAction` in `precompiles/common/precompile.go`, which snapshots the multistore, commits a cache context, and wraps the actual precompile logic between `BeforeBalanceChange`/`AfterBalanceChange` [4](#0-3) .

The correctness of this mechanism depends on the SDK `EventManager`'s event slice growing monotonically and *only* with events that are causally attributable to, and permanently committed by, the enclosing precompile call. That assumption fails once precompiles call back into the EVM (staking/distribution/ICS20/erc20/gov/slashing precompiles can trigger nested EVM/precompile execution, and Cosmos EVM explicitly supports and tests such recursive precompile-call patterns, e.g. `StakingReverter` and `ics20_recursive_precompile_calls_test.go`):
- If an inner precompile call reverts, the Cosmos SDK `EventManager`'s already-emitted events are not necessarily rolled back with the same granularity as the KV multistore snapshot/revert used for state (`stateDB.MultiStoreSnapshot()` / `AddPrecompileFn`), so events emitted by a reverted call can persist in the shared event log.
- A subsequent, unrelated call (sibling or outer scope) that begins its own `BeforeBalanceChange`/`AfterBalanceChange` window can then have those stale, already-discarded bank events fall inside its `events[prevEventsLen:]` window, or conversely have inner events double-counted across two overlapping windows (outer window `[N:]` still contains the inner call's own already-processed `[M:]` sub-range).
- Either way, a `CoinSpent`/`CoinReceived` event that is not backed by a corresponding, currently-valid state change in `x/bank` gets translated into a `StateDB.AddBalance`/`SubBalance` call, permanently crediting or debiting EVM-visible balances that do not match the actual bank ledger.

This is a native analog of the Curve V2 oracle bug: instead of an oracle wrongly assuming "only pools with the sentinel ETH address are reenterable," Cosmos EVM's balance-sync mechanism wrongly assumes "the event slice observed within a precompile's execution window belongs exclusively and completely to that call." Nested/recursive execution — reachable by any unprivileged contract calling into the staking, distribution, gov, slashing, erc20, ICS20, or debug-style precompiles, several of which explicitly support calling back into the EVM — breaks that assumption.

### Impact Explanation
If stale or double-counted bank events get replayed into `StateDB.AddBalance`, an attacker-controlled contract can cause the EVM `StateDB` to reflect a native-token balance increase (or decrease of another account) that is not backed by an equivalent real change in `x/bank`/`x/precisebank` state. Because `StateDB` balances are what back subsequent EVM transfers, `CALL` value movement, and are eventually committed back via `stateDB.Commit()`, this is a duplication/unauthorized-minting-class bug on spendable value across native and EVM-visible balances — directly matching the "Critical unauthorized minting, burning, duplication ... of spendable user value across native balances, EVM balances" impact category. Because the affected precompiles (staking, distribution, gov, slashing, erc20, ICS20) are triggerable by any ordinary user-owned contract, no privileged access is required.

### Likelihood Explanation
The likelihood is high in terms of reachability: recursive/nested precompile invocation is a first-class, explicitly tested pattern in this codebase (`StakingReverter.sol`, `nestedTryCatchDelegations`, `ics20_recursive_precompile_calls_test.go`, `BalanceHandlerTestSuite`), meaning the trigger path (contract A calls precompile P, which calls back into the EVM invoking precompile Q or P again, with an intervening `revert`) is a normal, unprivileged usage pattern rather than an edge case requiring special access. The presence of dedicated regression tests with names and comments explicitly describing "the native balance handler bug" and "balance desync between native bank keeper and EVM stateDB" indicates the maintainers are aware this exact class of bug can occur in this exact mechanism; whether the current `precompile.go`/`balance_handler.go` state fully closes every recursive/revert-interleaving path (versus only the specific case captured by the existing tests) could not be conclusively confirmed from static review alone, since the correctness depends on the Cosmos SDK `EventManager`'s exact revert semantics across cached contexts, which was not fully traceable within the available index.

### Recommendation
- Do not rely on `ctx.EventManager()` event slicing (`events[prevEventsLen:]`) as the source of truth for balance deltas across nested/recursive precompile calls. Instead, snapshot and diff actual `x/bank`/`x/precisebank` account balances (or use a per-call isolated event manager that is created and discarded strictly within each precompile invocation, and is explicitly rolled back together with the multistore snapshot on revert).
- Ensure that when a nested precompile call reverts (multistore snapshot restored via `AddPrecompileFn`/journal), any events it emitted are also excised from `ctx.EventManager()`, or that the balance-handler event window for the parent call cannot re-observe or double-count events already consumed by a child call.
- Add explicit regression tests that combine (a) nested precompile calls performing real bank-affecting operations (not just custom no-op events like the `debug_precompile` event), and (b) a revert in an inner call, then assert `StateDB` balances exactly equal `x/bank` balances after the transaction — the existing tests using a debug precompile that only emits non-bank events would not detect a real duplication of `CoinSpent`/`CoinReceived` handling.

### Proof of Concept
A concrete, minimal PoC was not fully constructable from the available index (the exact revert/event-manager semantics of `stateDB.GetCacheContext()`/`CommitWithCacheCtx()` across nested calls need runtime verification). The reachable skeleton, based on code already in the repository, is:
1. Deploy a contract that calls a value-moving precompile (e.g. `DISTRIBUTION_CONTRACT.withdrawDelegatorRewards`) inside a `try/catch` that is expected to revert, similar to `StakingReverter.performDelegation` [5](#0-4) , but structured so the inner call emits `CoinSpent`/`CoinReceived` bank events before reverting.
2. Immediately follow with a second, successful precompile call (e.g. `STAKING_CONTRACT.delegate`) in the same transaction.
3. Inspect whether the second call's `BalanceHandler.AfterBalanceChange` window incorporates the first (reverted) call's leftover bank events, causing `StateDB.AddBalance`/`SubBalance` to apply balance deltas that have no corresponding committed state in `x/bank`.
4. Compare final `StateDB` balances (via `eth_getBalance`) against the ground-truth bank balance to confirm divergence.

This mirrors the exact scenario already anticipated by the maintainers' own test file naming and comments (`evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`, `evmd/tests/integration/balance_handler/balance_handler_test.go`), which should be consulted/extended to confirm exploitability with a bank-event-emitting precompile rather than the no-op debug precompile currently used.
