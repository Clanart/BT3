### Title
`ThresholdKeys::read` accepts identity verification shares, enabling deserialization of a key set with an identity (unownable / universally-forgeable) group key — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` deserializes each participant's verification share with `<C as Ciphersuite>::read_G`, which only checks canonicality and accepts the identity point (`crypto/ciphersuite/src/lib.rs:91-100`). The FROST `Curve` trait overrides `read_G` to explicitly reject identity (`crypto/frost/src/curve/mod.rs:125-131`), but `ThresholdKeys::read` deliberately uses the ciphersuite-level reader. `ThresholdKeys::new` then computes the group key as the interpolated sum of the first `t` verification shares without any identity or consistency check (`crypto/dkg/src/lib.rs:376-378`). Consequently, attacker-controlled bytes fed to `ThresholdKeys::read` can install verification shares whose interpolated group key is the identity point — the discrete-log-equivalent of transferring ownership to `address(0)`.

### Finding Description
The deserialization path is:

1. `ThresholdKeys::read` reads `n` verification shares via `<C as Ciphersuite>::read_G(reader)` (`crypto/dkg/src/lib.rs:620-623`).
2. `Ciphersuite::read_G` validates canonicality but explicitly permits the identity point; only `Curve::read_G` adds `is_identity` rejection (`crypto/frost/src/curve/mod.rs:123-131`), and it is not used here.
3. `ThresholdKeys::new` checks only share count and participant indices (`crypto/dkg/src/lib.rs:355-365`), then sets `group_key = Σ verification_shares[i] * interpolation_factor(i, 1..=t)` (`crypto/dkg/src/lib.rs:376-378`) with no check that any share, or the resulting group key, is non-identity.
4. Similarly, `secret_share` is read via `C::read_F` (`crypto/dkg/src/lib.rs:618`), which accepts zero, and `Interpolation::Constant` coefficients are read via `C::read_F` (`crypto/dkg/src/lib.rs:607-612`) without non-zero checks.

With `Interpolation::Constant` (used by MuSig via `musig` in `crypto/dkg/musig/src/lib.rs:155-160`), the attacker fully controls every coefficient, so `group_key` is an arbitrary linear combination of attacker-chosen points — trivially made identity (e.g., all shares identity, or shares cancelling under the supplied coefficients).

### Impact Explanation
A `ThresholdKeys` whose `group_key` is the identity point is the threshold analogue of a contract owned by `address(0)`:

- The identity has the publicly known discrete logarithm `0`, so Schnorr signatures under it are forgeable by anyone: for any nonce `r`, `s = r` satisfies `s·G = R + c·identity = R`. Any externally observable signature/verification path keyed by this group key is unauthenticated.
- Conversely, if downstream consumers treat the key as unspendable-by-design (no holder of the "real" discrete log), any funds or authority bound to `group_key()` are permanently inaccessible — exactly the "contract unownable, core functionality inaccessible" impact of the source report.
- Since `secret_share` and verification shares are never cross-validated (`ThresholdKeys::new` does not check `G·secret_share == verification_shares[i]`), the corrupted key material is accepted and later used by FROST `view`/`sign`/`complete` without detecting the inconsistency; `AlgorithmSignatureMachine::complete` even notes "deserialize a semantically invalid FrostKeys" as the only way to reach its internal-error path (`crypto/frost/src/sign.rs:491-494`).

### Likelihood Explanation
`ThresholdKeys::read` is the canonical loader for threshold key material, and untrusted-byte deserialization is reachable wherever serialized `ThresholdKeys` are transported or restored rather than locally generated. The exploit requires only crafting a byte stream — setting verification-share encodings to the canonical identity encoding (all-zero bytes for Ristretto/ed25519 compressed identity) — and requires no computational work, collusion, or protocol participation. Any consumer that accepts serialized key sets from an unprivileged source (key rotation, backup restore, cross-process handoff) is exposed. Rated Medium: high impact when triggered, but requires the attacker to control the serialized input rather than breaking honestly-generated keys.

### Recommendation
In `ThresholdKeys::read` (or `ThresholdKeys::new`), reject identity verification shares and a zero `secret_share`, e.g., use `Curve`-style `is_identity` checks after `read_G`, and verify consistency: `C::generator() * secret_share == verification_shares[params.i()]` and `!group_key.is_identity()`. For `Interpolation::Constant`, also reject zero coefficients where they would null a share's contribution.

### Proof of Concept
```rust
// For C = Ristretto. Construct a serialized ThresholdKeys blob:
//   id_len || C::ID || t=1 || n=1 || i=1 || interpolation=1 (Lagrange)
//   || secret_share = 0 || verification_shares[1] = identity encoding
let mut buf = vec![];
buf.extend((Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(1u16.to_le_bytes()); // t
buf.extend(1u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes()); // i
buf.push(1);                    // Interpolation::Lagrange
buf.extend(<Ristretto as Ciphersuite>::F::ZERO.to_repr());      // secret_share = 0
buf.extend(<Ristretto as Ciphersuite>::G::identity().to_bytes()); // identity share

let keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity())); // unownable group key accepted
```
