## Analysis

`saveGitIgnore` builds its target path as: [1](#0-0) 

`repository.path` is the local working-tree root that Desktop itself resolved when the repository was added/cloned (it is not attacker-controlled data from inside the repo tree), and the appended segment is the **hardcoded literal** `'.gitignore'` — not a value derived from repo content. Because the string passed to `Path.join` never contains attacker-supplied path segments, there is no `..`-based traversal possible through this function: the resulting `ignorePath` is always `<repo-root>/.gitignore` as a string.

However, that string is then used directly as the target of a filesystem write: [2](#0-1) 

`writeFile` (from `fs/promises`) opens the target with the default `'w'` flag, which **follows symlinks** at the final path component (no `O_NOFOLLOW`/`wx` exclusive-create flag, and no `lstat`/`isSymbolicLink()` check beforehand). Git supports committing symlinks as blobs, and on macOS/Linux (where `core.symlinks` defaults to `true`) a checked-out repository can legitimately contain a file literally named `.gitignore` at the working-tree root that is actually a symlink pointing to an arbitrary absolute path outside the repository (e.g. `~/.ssh/authorized_keys`, `~/.bashrc`, another project's file, etc.). The same pattern also applies to the read path: [3](#0-2) 

and to `FS.unlink`, although `unlink` removes the symlink itself rather than its target, so that path is not exploitable for escape.

### Title
Symlink-following write in `saveGitIgnore` breaks working-tree containment - (File: app/src/lib/git/gitignore.ts)

### Summary
`saveGitIgnore` (and `readGitIgnoreAtRoot`) resolve the fixed path `<repository.path>/.gitignore` and then call Node's `writeFile`/`FS.readFile` without checking whether that path is a symlink. A malicious repository can ship a `.gitignore` entry checked in as a symlink pointing outside the working tree; on checkout this becomes a real symlink on disk (on platforms/configs where `core.symlinks` is enabled). Note: unlike the "`..`-laden path" phrasing in the question, the path itself cannot be manipulated via `..` because the joined segment is a hardcoded literal, not attacker data — the actual escape vector is symlink-following, not path traversal.

### Finding Description
`Path.join(repository.path, '.gitignore')` always yields a fixed relative filename under the trusted root, so string-based traversal (`../../..`) is not possible here [4](#0-3) . But `writeFile(ignorePath, fileContents)` opens that path with default flags, which follow a terminal symlink instead of failing or operating on the link itself [2](#0-1) . If the attacker's repository contains a symlink named `.gitignore` at the root pointing to an absolute path outside the repo, subsequent writes via this function are redirected to that external target, breaking the "stays inside the repo working tree" invariant.

### Impact Explanation
A successful exploitation lets an attacker cause Desktop to write to an arbitrary file the symlink targets (subject to OS filesystem permissions of the Desktop process/user), e.g. overwriting shell rc files, SSH config, or other sensitive user files, when the victim performs a routine action like saving repository settings or ignoring a file. This does not grant fully attacker-controlled file *contents* (the written content is the gitignore text the user/app composed), but the write *destination* is attacker-controlled, which can still corrupt or hijack files outside the repo.

### Likelihood Explanation
Requires: (1) the victim clones/opens a malicious repo containing a committed symlink named `.gitignore`, on a platform/config where symlink checkout is honored, and (2) the victim performs an action that calls `saveGitIgnore`/`appendIgnoreRule` (e.g., opening Repository Settings → Ignored Files and saving, or using "ignore file" from the Changes sidebar context menu). This requires some ordinary user interaction with a feature that many users do use, but it is not fully automatic on clone/checkout alone — I could not confirm within available context whether any call path invokes `saveGitIgnore`/`appendIgnoreRule` without explicit user action.

### Recommendation
Before writing, `lstat` the target path and refuse (or unlink-and-recreate) if it is a symlink; alternatively open with flags that disable symlink-following (e.g., write to a temp file inside the repo and atomically rename, or use `O_NOFOLLOW` where supported) for both `saveGitIgnore` and `readGitIgnoreAtRoot`.

### Proof of Concept
1. Create a repository containing a symlink named `.gitignore` at the root pointing to `/home/victim/.bashrc` (`ln -s /home/victim/.bashrc .gitignore`, commit as a symlink blob).
2. Victim clones the repo with GitHub Desktop; checkout creates the real symlink on disk.
3. Victim opens Repository Settings → Ignored Files and clicks Save (or right-clicks an untracked file → "Ignore file").
4. `saveGitIgnore` calls `writeFile(ignorePath, fileContents)`, following the symlink and overwriting `/home/victim/.bashrc` with gitignore content instead of the intended `.gitignore` file in the repo.

export async function readGitIgnoreAtRoot(
  repository: Repository
): Promise<string | null> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  return new Promise<string | null>((resolve, reject) => {
    FS.readFile(ignorePath, 'utf8', (err, data) => {
      if (err) {
        if (err.code === 'ENOENT') {
          resolve(null)
        } else {
          reject(err)
        }
      } else {
        resolve(data)
      }
    })
  })
}
