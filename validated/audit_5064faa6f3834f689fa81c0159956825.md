### Title
Uncontrolled panic in `GeneratorPromotion::complete` on attacker-controlled proof map - (File: crypto/dkg/promote/src/lib.rs)

### Summary
The buffer-overflow class of CVE-2017-14265 (out-of-bounds access driven by unvalidated input structure) maps onto Serai's Rust code as an unchecked indexing/`unwrap` reachable with attacker-supplied data. `GeneratorPromotion::complete` iterates `1 ..= params.n()` and unconditionally calls `proofs.get(&i).unwrap()`, after only checking `proofs.len() == n - 1` and that every key is `<= n`. A map containing the callee's own participant index (or any in-range duplicate-free set that omits one index in `1..=n`) satisfies both checks but leaves one `get()` returning `None`, causing an `unwrap` panic — a remotely triggerable crash, the memory-safety-class analog in safe Rust.

### Finding Description
`complete` performs two validations on the untrusted `proofs: &HashMap<Participant, GeneratorProof<C1>>`:
- `proofs.len() != n - 1` → error (crypto/dkg/promote/src/lib.rs:125)
- each key `u16::from(i) > params.n()` → error (lines 132–136)

It then indexes the map for every participant other than the callee (`proofs.get(&i).unwrap()` at line 146). `HashMap` keys are unique, so an attacker supplies `n - 1` entries keyed by valid `Participant` indexes where one of them is the victim's own `params.i()` — a key that is never checked for exclusion. Because `proofs.len() == n - 1` and all keys are in `1..=n`, both checks pass, yet some `i` in `1..=n` other than `params.i()` has no entry, and `unwrap()` panics.

### Impact Explanation
An unprivileged counterparty in a generator-promotion session sends a crafted set of `GeneratorProof` messages (reachable as untrusted bytes via `DLEqProof::read` / serialized `GeneratorProof`s fed into `complete`). The victim node crashes mid-protocol via panic rather than returning `PromotionError`, denying service at the exact point proofs are consumed — the same availability impact class as the referenced stack overflow, realized as a memory-safety violation (indexing a missing key) in Rust.

### Likelihood Explanation
Triggering requires only controlling the key set of the `proofs` map passed to `complete`, which any participant in the promotion protocol supplies. No valid proofs, signature forgeries, or threshold compromise are needed; the panic occurs before `proof.proof.verify(...)` for the missing index is ever reached.

### Recommendation
Replace the `unwrap()` with an existence check returning `PromotionError::InvalidParticipant`/a new missing-proof error, e.g. `let Some(proof) = proofs.get(&i) else { Err(...) }?`, and/or explicitly reject `proofs.contains_key(&params.i())` up front.

### Proof of Concept
```
// params: n = 3, params.i() = Participant(2)
// Attacker sends proofs keyed {2, 3} instead of {1, 3}:
//   proofs.len() == 2 == n - 1                 -> passes
//   all keys <= n                              -> passes
//   loop i = 1: proofs.get(&Participant(1))    -> None.unwrap() -> panic
let mut proofs = HashMap::new();
proofs.insert(Participant::new(2).unwrap(), attacker_proof_a); // victim's own index
proofs.insert(Participant::new(3).unwrap(), attacker_proof_b); // index 1 omitted
promotion.complete(&proofs); // panics at proofs.get(&i).unwrap()
```
