### Title
Symlink-based arbitrary file read via `.claude/hookify.*.local.md` rule loading - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`load_rules()` locates rule files with `glob.glob(os.path.join('.claude', 'hookify.*.local.md'))` and passes every matched path to `load_rule_file()`, which opens it with plain `open(file_path, 'r')` [1](#0-0) [2](#0-1) . Neither function checks `os.path.islink()`, resolves/validates the path with `os.path.realpath()` against the repo root, or otherwise enforces that the file physically resides inside `.claude/`. Both `glob.glob` and Python's `open()` transparently dereference symlinks, so if an attacker commits a symlink named e.g. `.claude/hookify.evil.local.md` pointing to a file outside the workspace (a path predictable across machines, such as `~/.ssh/id_rsa`, `~/.aws/credentials`, or a relative `../` path to a sibling project's `.env`), the loader will happily follow the link and read that file's real contents. The content is parsed by `extract_frontmatter()` and turned into a `Rule` via `Rule.from_dict()`, with the body stored as `rule.message` [3](#0-2) . This rule is then evaluated by `RuleEngine` and, on match, its message text is surfaced back to the user/Claude through the hook's `systemMessage` output, e.g. in `plugins/hookify/hooks/userpromptsubmit.py` which calls `load_rules(event='prompt')` and prints the engine result as JSON to stdout [4](#0-3) . None of the three hook executors (`userpromptsubmit.py`, `pretooluse.py`, `posttooluse.py`, `stop.py`) add any path/symlink validation before calling `load_rules()`, so there is no compensating control anywhere in the call chain from attacker-controlled repository content to file disclosure.

### Impact Explanation
An attacker who can get a victim to check out a repository/branch/PR containing such a symlink (a completely ordinary, unprivileged git operation — no admin/maintainer rights needed) can exfiltrate the contents of arbitrary files outside the project workspace into a message that Claude Code surfaces as a `systemMessage` on the very next prompt submission, tool call, or session stop. This is a workspace-confinement escape and secret-disclosure vulnerability: SSH keys, cloud credentials, or another project's `.env` secrets could be leaked into the conversation transcript, which may then be logged, displayed, or even acted upon by the agent.

### Likelihood Explanation
Exploitation only requires: (1) the attacker can add a file to a repository the victim will clone/checkout (public repo, fork, malicious PR branch, or a compromised dependency), and (2) the hookify plugin is installed and active (it installs generic hooks on PreToolUse/PostToolUse/Stop/UserPromptSubmit). No secrets, elevated privileges, or social engineering beyond "get victim to open/checkout this repo" are needed. The main limiting factor is that the attacker must guess a plausible target path (home-directory-relative paths like `~/.ssh/id_rsa` are OS-symlink-target strings and are not expanded to a per-user path unless the attacker knows the username, but `../`-relative traversal to sibling directories in common monorepo/checkout layouts is fully attacker-controlled and reliable), which lowers but does not eliminate feasibility.

### Recommendation
In `load_rule_file()` (and/or `load_rules()`), reject any candidate file that is a symlink or whose resolved real path escapes the `.claude/` directory: e.g. `if os.path.islink(file_path): skip/reject`, and additionally verify `os.path.commonpath([os.path.realpath(file_path), os.path.realpath('.claude')]) == os.path.realpath('.claude')` before opening. Apply the same guard to any other plugin code that globs and opens `.claude/*.local.md`-style files.

### Proof of Concept
Unit test sketch for `plugins/hookify/core/config_loader.py`:
1. Create a temp "secret" file `secret.txt` outside the fixture repo containing:
   ```
   ---
   name: x
   enabled: true
   event: prompt
   pattern: y
   ---
   TOP-SECRET-CONTENT
   ```
2. In a fixture repo directory, create `.claude/hookify.evil.local.md` as a symlink (`os.symlink`) pointing to `secret.txt`.
3. `chdir` into the fixture repo and call `load_rules(event='prompt')`.
4. Assert the returned list contains a `Rule` whose `message == "TOP-SECRET-CONTENT"` and `enabled is True`, proving the secret file outside the repo was read and surfaced.
5. Extend the test to run `plugins/hookify/hooks/userpromptsubmit.py` with a matching prompt on stdin and assert the printed JSON's `systemMessage`/hookSpecificOutput contains `TOP-SECRET-CONTENT`, confirming end-to-end disclosure via the hook output channel.
