Confirmed: the `CLARITY_NAME_REGEX_STRING` pattern `^[-+=/*]$|^[<>]=?$` explicitly allows a single-character identifier of exactly `*` (among `-+=/*`) as a valid `ClarityName` [1](#0-0) . This means a Clarity contract can legally define a fungible or non-fungible token literally named `*` (e.g. `(define-fungible-token * ...)`), and `AssetIdentifier { contract_identifier, asset_name: "*" }` is a real, distinct, addressable asset.

### Title
Wildcard asset-name collision lets `with-ft`/`with-nft` allowances scoped to a literal asset named `*` be silently reinterpreted as "all fungible/non-fungible tokens in the contract" - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
`restrict-assets?` and `as-contract?` let a contract scope outbound asset movement to a bounded `Allowance` list (`with-stx`, `with-ft`, `with-nft`, ...). `check_allowances` implements a "wildcard" convenience: an allowance declared for asset-name `"*"` under a given contract is treated as covering *every* fungible/non-fungible token under that contract, not just a token literally named `*`. Because `ClarityName` explicitly permits the single character `*` as a valid identifier [1](#0-0) , a contract that defines a real token named `*` and an allowance-writer that specifies `(with-ft .contract "*" amt)` intending to bound only that one token, instead unintentionally authorizes movement of *every* other fungible/non-fungible token defined in that contract, up to `amt`/its own bound, breaking the equality between "assets requested to be movable" and "assets actually authorized to move."

### Finding Description
`check_allowances` builds `ft_allowances`/`nft_allowances` keyed by `AssetIdentifier` (which is `{contract_identifier, asset_name}`), then for every FT/NFT actually moved by `owner` in the resulting asset map, it looks up both the exact match and a synthetic wildcard key built as `AssetIdentifier { contract_identifier: asset.contract_identifier.clone(), asset_name: ClarityName::from_literal("*") }`, merging any entries found under either key [2](#0-1) [3](#0-2) .

This lookup is asset-name-blind by design: any allowance whose `asset.asset_name == "*"` is folded into the `merged` list for *every other differently-named asset in the same contract* that the owner moves, regardless of whether that allowance was meant as a genuine wildcard or as a specific bound on a token that happens to be named `*`. Since `"*"` is accepted by `CLARITY_NAME_REGEX_STRING` as a standalone `ClarityName` [1](#0-0) , a contract can define `ft-token` named literally `*`, and `eval_allowance`'s `AllowanceWithFt`/`AllowanceWithNft` handlers will happily construct an `AssetIdentifier{asset_name: "*"}` from that literal string with no special-casing [4](#0-3) [5](#0-4) .

The equality broken: the sender/contract author declares "I authorize movement of token `*` up to amount X" (a narrow, specific grant), but the enforcement logic treats it as "I authorize movement of *all* fungible/non-fungible tokens in this contract up to amount X" (an unbounded, broad grant covering assets never named in the allowance list) — exactly the Keystone pattern of requesting a scoped permission and unintentionally being granted every related permission.

### Impact Explanation
Inside `restrict-assets?`/`as-contract?`, this can let a contract call (e.g., through `as-contract?` invoking another contract on behalf of the calling contract) move/burn other fungible or non-fungible tokens defined in the same contract as the `*`-named token, past what the allowance list was intended to authorize, and still pass the post-condition check that is supposed to gate and roll back unauthorized asset movement (`evaluate_body_with_allowance_check`, lines 405-420). This is an asset moving past its declared post-conditions/allowances within the meaning of the "High/Critical" impact bucket (post-condition-scoped asset movement exceeding the declared allowance).

### Likelihood Explanation
Requires a contract author (not a privileged party — any Clarity contract deployer) to (a) name a token `*` — legal per the `ClarityName` grammar, and (b) write a `restrict-assets?`/`as-contract?` allowance list intending to scope only that token. This is a narrow but concrete authoring mistake rather than a malicious-miner/node assumption; it's reachable by an ordinary unprivileged contract deployer/caller through the standard Clarity execution path, no signer/admin/miner privileges needed.

### Recommendation
Reject `"*"` as a valid `asset_name` argument to `with-ft`/`with-nft` at allowance-construction time (`eval_allowance`), or use a dedicated non-collidable sentinel/variant for "all fungible tokens in this contract" (as is already done via the distinct `Allowance::All` variant for "all assets") instead of overloading the literal string `"*"`, so an asset genuinely named `*` can never be aliased into a blanket allowance.

### Proof of Concept
1. Deploy a contract defining two fungible tokens: `(define-fungible-token * u1000000)` and `(define-fungible-token real-token u1000000)`, minting balances of both to the contract itself.
2. From within the contract, call:
   ```
   (as-contract?
     ((with-ft .this-contract "*" u10))
     (ft-transfer? real-token u999999 tx-sender 'SP...RECIPIENT))
   ```
3. Despite `real-token` never being named in any allowance and the allowance for `"*"` capping only `u10`, `check_allowances` merges the `"*"` allowance into `real-token`'s check via the wildcard lookup at [6](#0-5) , and since `u999999 > u10` fails **that** entry it would be flagged — however, if the `*` allowance amount is instead set to `u1000000` (intending only to authorize the token literally named `*`), the transfer of `real-token` for the full `u999999` silently passes even though `real-token` was never explicitly authorized, demonstrating the allowance scoped to one asset (`*`) is being applied to an entirely different asset (`real-token`) in the same contract.

    if let Some(ft_moved) = assets.get_all_fungible_tokens(owner) {
        for (asset, amount_moved) in ft_moved {
            // Build merged allowance list: exact-match entries + wildcard entries for the same contract
            let mut merged: Vec<(usize, u128)> = Vec::new();

            if let Some(allowance_vec) = ft_allowances.get(asset) {
                merged.extend(allowance_vec.iter().cloned());
            }

            if let Some(wildcard_vec) = ft_allowances.get(&AssetIdentifier {
                contract_identifier: asset.contract_identifier.clone(),
                asset_name: ClarityName::from_literal("*"),
            }) {
                merged.extend(wildcard_vec.iter().cloned());
            }

            if merged.is_empty() {
                // No allowance for this asset, any movement is a violation
                record_violation(&mut earliest_violation, MAX_ALLOWANCES as u128);
                continue;
            }

            for (index, allowance) in merged {
                if *amount_moved > allowance {
                    record_violation(&mut earliest_violation, index as u128);
                }
            }
        }
    }
