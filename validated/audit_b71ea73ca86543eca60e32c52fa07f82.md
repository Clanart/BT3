## Analysis Result

This is a valid, demonstrable vulnerability rooted in the join logic of `get_payout_txs_for_withdrawal_utxos` combined with the missing uniqueness constraint on `withdrawal_utxo_txid`/`withdrawal_utxo_vout` in the `withdrawals` table.

### Title
One Bitcoin payout transaction credited to two withdrawal indices via a shared `withdrawal_utxo`, causing double reimbursement - (`core/src/database/verifier.rs`, `core/src/verifier.rs`)

### Summary
The `withdrawals` table has no uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` [1](#0-0) , and `get_payout_txs_for_withdrawal_utxos` joins purely on those UTXO bytes rather than a per-withdrawal identifier [2](#0-1) . An attacker who registers the same Bitcoin outpoint bytes as the `withdrawal_utxo` for two different Citrea withdrawal indices `i` and `j` causes a single honestly-funded payout transaction to be attributed to both indices, letting the funding operator be marked eligible for reimbursement twice for one real BTC outflow.

### Finding Description
The broken binding is: `payout_payer_operator_xonly_pk` for withdrawal `i` AND for withdrawal `j` must equal exactly the operator that funded exactly one Bitcoin payout — but nothing enforces `withdrawal_utxo` to be unique per withdrawal index.

- `update_withdrawal_utxo_from_citrea_withdrawal` simply `UPDATE`s `withdrawals` by `idx`, storing whatever `(txid, vout)` bytes came from Citrea's `collect_withdrawal_utxos`/`withdrawalUTXOs(idx)` [3](#0-2) , with no check against other rows.
- `get_payout_txs_for_withdrawal_utxos` joins `withdrawals w` to `bitcoin_syncer_spent_utxos bsu` purely `ON bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout` [4](#0-3) . If two rows (`idx=i`, `idx=j`) share the same outpoint, this query returns **two** `(idx, spending_txid)` rows for one real spend.
- `Verifier::update_finalized_payouts` loops over these pairs, computing `operator_xonly_pk` once from the payout tx's OP_RETURN, and pushes `(idx, payout_txid, operator_xonly_pk, block_hash)` for both `i` and `j` [5](#0-4) .
- `update_payout_txs_and_payer_operator_xonly_pk` then updates **both** withdrawal rows with the same `payout_txid`/`payout_payer_operator_xonly_pk`/`payout_tx_blockhash` [6](#0-5) .
- `get_first_unhandled_payout_by_operator_xonly_pk` and `PayoutCheckerTask` then process each row independently by `idx`, each invoking `handle_finalized_payout` for its own `move_to_vault_txid`/deposit, and each marks itself handled separately [7](#0-6) . Nothing deduplicates by `payout_txid`.

**Why existing guards fail:** `is_kickoff_malicious` checks `payout_payer_operator_xonly_pk`/`payout_tx_blockhash` against the same corrupted `withdrawals` table row [8](#0-7) , so all verifiers deterministically derive the same (incorrect) attribution from the same Bitcoin block — the "malicious kickoff" check cannot detect this because the corruption is consensus-consistent across all nodes' independently-synced state.

**Exploit flow:** Attacker deposits into the bridge for two deposits A (idx `i`) and B (idx `j`). Attacker calls Citrea's `withdraw()` for both indices, providing the *same* real outpoint `X` (owned/spendable by attacker) as `withdrawal_utxo` bytes for both `i` and `j` — nothing in this repo's sync/registration logic rejects a duplicate. The attacker only ever requests the operator's `withdraw` gRPC for index `i`, providing a valid signature over `X`. The honest operator funds one real payout transaction spending `X`, with an OP_RETURN naming its own `xonly_pk`. Once finalized, the join above manufactures a spurious `(j, that same payout_txid)` entry, causing withdrawal `j` (deposit B) to be marked as "paid by the operator" though no output was ever sent for B's registered `output_script_pubkey`/`output_amount`. The operator (or its automated `PayoutCheckerTask`) subsequently proceeds through `handle_finalized_payout`/kickoff/Reimburse for deposit B as well, draining B's move-to-vault UTXO for a payout that was never made.

### Impact Explanation
BTC leaves deposit B's move-to-vault UTXO via a Reimburse flow with no matching fronted withdrawal for B — exactly the Critical category "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal / an operator reimbursed for a payout it never funded." The blast radius scales with however many deposit/withdrawal indices the attacker can link to one real outpoint (not limited to two), and is repeatable across any set of deposits the attacker controls (or, if the Citrea contract itself permitted registering an already-used-by-someone-else outpoint, across other users' deposits too — out of scope to verify contract-side, but this repo places no defense of its own).

### Likelihood Explanation
Preconditions: attacker must own/control two bridge deposits and be able to register identical `withdrawal_utxo` bytes for both indices via Citrea's `withdraw()` (a capability explicitly granted to the unprivileged attacker in this audit's ruleset) and must possess a real Bitcoin UTXO with a signature satisfying the operator's payout construction for one of the two. Cost is limited to two bridge deposits' worth of BTC plus normal transaction fees — no privileged role, key compromise, or majority hashrate needed. This is fully repeatable per attacker-controlled deposit pair.

### Recommendation
Enforce uniqueness of `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table (reject/ignore duplicate registrations at `update_withdrawal_utxo_from_citrea_withdrawal` time), and additionally make `get_payout_txs_for_withdrawal_utxos` and `update_payout_txs_and_payer_operator_xonly_pk` bind the payout attribution 1:1 to a single `idx` per physical `(spending_txid)`/outpoint pair (e.g., add a DB constraint so a given `payout_txid` can satisfy at most one unhandled withdrawal, and validate that the payout's actual output amount/script matches the specific withdrawal `idx`'s registered `output_script_pubkey`/`output_amount` before crediting it).

// core/src/database/verifier.rs (test module) — extend existing
// update_get_payout_txs_from_citrea_withdrawal-style test:
#[tokio::test]
async fn duplicate_withdrawal_utxo_double_credits_operator() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();
    let mut dbtx = db.begin_transaction().await.unwrap();

    let shared_utxo = bitcoin::OutPoint {
        txid: bitcoin::Txid::from_byte_array([0x45; 32]),
        vout: 0,
    };
    let payout_txid = Txid::from_byte_array([0x99; 32]);
    let operator_xonly_pk = generate_random_xonly_pk();
    let block_hash = BlockHash::all_zeros();

    let block_id = db.insert_block_info(Some(&mut dbtx), &block_hash, &BlockHash::all_zeros(), 0).await.unwrap();
    db.insert_txid_to_block(&mut dbtx, block_id, &payout_txid).await.unwrap();
    db.insert_spent_utxo(&mut dbtx, block_id, &payout_txid, &shared_utxo.txid, shared_utxo.vout.into()).await.unwrap();

    // Deposit A (idx=0) and Deposit B (idx=1) both register the SAME withdrawal_utxo
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), 0, &Txid::from_byte_array([0xAA; 32])).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), 0, shared_utxo, block_id).await.unwrap();

    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), 1, &Txid::from_byte_array([0xBB; 32])).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), 1, shared_utxo, block_id).await.unwrap();

    // Simulate update_finalized_payouts' resulting query + write
    let joined = db.get_payout_txs_for_withdrawal_utxos(Some(&mut dbtx), block_id).await.unwrap();
    assert_eq!(joined.len(), 2, "BINDING BROKEN: one payout tx credited to two withdrawal idxs");

    let updates: Vec<_> = joined.into_iter()
        .map(|(idx, txid)| (idx, txid, Some(operator_xonly_pk), block_hash))
        .collect();
    db.update_payout_txs_and_payer_operator_xonly_pk(Some(&mut dbtx), updates).await.unwrap();

    // Assert both withdrawal rows now falsely show as paid by the same operator
    let (op0, _, txid0, _) = db.get_payout_info_from_move_txid(Some(&mut dbtx), Txid::from_byte_array([0xAA; 32])).await.unwrap().unwrap();
    let (op1, _, txid1, _) = db.get_payout_info_from_move_txid(Some(&mut dbtx), Txid::from_byte_array([0xBB; 32])).await.unwrap().unwrap();
    assert_eq!(op0, Some(operator_xonly_pk));
    assert_eq!(op1, Some(operator_xonly_pk)); // BUG: B credited despite no real payout for B
    assert_eq!(txid0, txid1); // same physical BTC spend counted for both

    // get_first_unhandled_payout_by_operator_xonly_pk should return only ONE entry per real spend,
    // but returns idx 0 first; after marking it handled, it will ALSO return idx 1 — proving double credit:
    let first = db.get_first_unhandled_payout_by_operator_xonly_pk(Some(&mut dbtx), operator_xonly_pk).await.unwrap();
    assert!(first.is_some());
    db.mark_payout_handled(Some(&mut dbtx), first.unwrap().0, Txid::from_byte_array([0xCC; 32])).await.unwrap();
    let second = db.get_first_unhandled_payout_by_operator_xonly_pk(Some(&mut dbtx), operator_xonly_pk).await.unwrap();
    assert!(second.is_some(), "operator gets a SECOND unhandled payout credit for the same funded tx");
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
