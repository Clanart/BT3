### Title
`ReceivedOutput::read` performs no consistency validation between the offset, script_pubkey, and outpoint — crafted bytes yield outputs reported as received and spendable that are not ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to the NiFi validation-bypass class (structured input accepted because validation is insufficient), `ReceivedOutput::read` deserializes three attacker-controlled fields — a scalar `offset`, a `TxOut` (value + `script_pubkey`), and an `OutPoint` — but only checks scalar canonicity and consensus-decodability. It never verifies the tuple is internally consistent: that `p2tr_script_buf(scanner_key + G * offset)` actually equals `output.script_pubkey`, nor that the output carries a sane value/outpoint. A genuine output produced by `Scanner::scan_transaction` always satisfies this relation (`offset` is looked up from `self.scripts[script_pubkey]`), but the deserialization path accepts arbitrary combinations.

### Finding Description
- `ReceivedOutput::read` reads `offset` via `Secp256k1::read_F`, then consensus-decodes `output` and `outpoint` with no further checks (networks/bitcoin/src/wallet/mod.rs:122-134).
- The legitimate producer `Scanner::scan_transaction` guarantees `output.script_pubkey == p2tr(script_key + G*offset)` by construction (mod.rs:205-211), and `Scanner::register_offset` documents that arbitrary offsets "may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script" (mod.rs:177-179). `ReceivedOutput::read` enforces none of this.
- Consumers treat the fields as authoritative: `SignableTransaction::new` sums `input.output.value` for balance/fee accounting and uses `input.offset` to derive the per-input signing key and `input.outpoint` as the prevout (wallet/send.rs:175-185). The transaction machine then signs per-input with keys re-keyed by each `offset` (send.rs:321-397).

An attacker who supplies `ReceivedOutput` bytes can therefore inject an output whose `script_pubkey` is not derivable from the wallet key plus the declared `offset` (e.g., a script the attacker controls, or a phantom outpoint), and the wallet will treat it as owned, spendable balance.

### Impact Explanation
- **Funds reported received that are not spendable**: a crafted `ReceivedOutput` (script_pubkey not matching `key + G*offset`, or a nonexistent outpoint) is accepted as wallet funds. Coin selection counts its `value` toward `input_sat`, but the resulting transaction is unspendable — either the prevout doesn't exist or the produced BIP-340 signature (for the tweaked Serai key) won't satisfy the attacker's script. Withdrawal transactions built over such inputs are invalid and stuck.
- If `offset` is chosen so `key + G*offset` maps to a script with an attacker-known script path (the exact hazard `register_offset` warns about for untrusted offsets), the deserialized output can encode a spendable-by-attacker output that the wallet believes is key-spend-only.

### Likelihood Explanation
Requires feeding crafted bytes to `ReceivedOutput::read` — reachable wherever serialized outputs cross a trust boundary (DB restore, network-provided data, or an attacker-controlled input list passed to `SignableTransaction::new`). No threshold collusion or key material needed. Impact is integrity/availability of the wallet's reported funds rather than direct key recovery, consistent with a Medium.

### Recommendation
Bind the offset to the output at deserialization, or validate before use: reconstruct the expected `script_pubkey` from the wallet base key and `offset` (mirroring `Scanner`'s `scripts` map check, including the even-Y increment loop from `register_offset`) and reject outputs where it doesn't match. At minimum, `SignableTransaction::new` should re-verify `p2tr_script_buf(key + G*offset) == output.script_pubkey` for every input before signing.

### Proof of Concept

```rust
let offset = Secp256k1::read_F(r)?;              // any canonical scalar
let output = TxOut::consensus_decode(&mut buf_r) // attacker-chosen script_pubkey/value
let outpoint = OutPoint::consensus_decode(...)   // arbitrary/possibly nonexistent prevout
// No check that p2tr_script_buf(scanner.key + G*offset) == output.script_pubkey
// => ReceivedOutput accepted; counted as spendable balance by SignableTransaction::new,
//    producing a transaction whose input cannot be unlocked (or is spendable via an

```

Caveat: reachability depends on untrusted bytes reaching `ReceivedOutput::read`; within this repo the enumerated sink is allowed, but the ultimate exploitability hinges on the processor trusting deserialized outputs without re-scanning on-chain data — that call path could not be fully traced within available iterations.
