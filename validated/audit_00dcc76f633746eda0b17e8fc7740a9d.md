### Title
Duplicate/misplaced `proofs` entry causes a panic (`unwrap` on absent key) in `GeneratorPromotion::complete` — ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary
The NFS bug class is "dereference of an object assumed valid in a given context (a positive dentry), which can actually be negative" — an Oops caused by trusting a container-level assumption rather than validating the specific element. The analog in Serai is in `GeneratorPromotion::complete`, which assumes the attacker-influenced `proofs` map contains one entry per other participant after only checking the map's *length* and each key's *upper bound*. A map that satisfies both checks yet lacks a required participant — e.g., because it contains the completer's own index — makes `proofs.get(&i).unwrap()` panic, aborting the promotion with a crash instead of an error.

### Finding Description
`complete` validates `proofs` with two checks:

- `proofs.len() == n - 1` (line 125)
- `u16::from(i) <= n` for every key (lines 132–136)

Neither check ensures the keys are exactly the set `{1..=n} \ {params.i()}`. The subsequent loop iterates `i` over `1..=n`, skips `params.i()`, and unconditionally unwraps:

```rust
// crypto/dkg/promote/src/lib.rs:146
let proof = proofs.get(&i).unwrap();
```

A `proofs` map of length `n - 1` that includes `params.i()` (a "self" entry) and omits some other participant `j` passes both checks, then panics at `proofs.get(&j).unwrap()`. Likewise, any map missing a required participant while containing a stray-but-in-range entry triggers the same panic.

This mirrors the kernel fix's shape exactly: the code indexes a container (`proofs`) under the assumption that prior aggregate checks (count, range) guarantee membership, when the specific entry can be "negative" (absent). The correct behavior — like deriving `nfs_server` from the dentry itself — is to derive presence per-index and return `PromotionError` rather than panic, e.g. `proofs.get(&i).ok_or(PromotionError::IncorrectAmountOfParticipants{..})` or an explicit "missing participant" error.

`proofs` is a `HashMap<Participant, GeneratorProof<C1>>` supplied by the caller aggregating per-participant proofs; in the DKG-promotion protocol these originate from the other participants' broadcast `GeneratorProof`s, which an unprivileged protocol participant controls (it chooses which participant index to attach its proof to / whether to omit itself or target another index).

### Impact Explanation
A single participant can crash the promotion process for a victim completing `GeneratorPromotion::complete` — an availability failure during a key-generation/promotion round, the same class of impact (unprivileged-triggered crash/Oops, `A:H` scope) as the reference CVE. In a validator rotation/promotion, repeatedly aborting the round via a panic (rather than a catchable error that could trigger blame/exclusion logic) prevents the set from completing the generator promotion cleanly and can be used to stall the ceremony.

### Likelihood Explanation
Triggering requires only that a participant in the promotion round publish/submit their `GeneratorProof` under the completer's own participant index (or omit the index of another participant and substitute a self-entry). No collusion, leaked keys, or broken BFT assumptions are needed — the panic is reachable purely from the contents of the `proofs` map, which is assembled from per-participant protocol messages. Note: if the caller builds `proofs` by keyed participant ID and malicious duplicates can't override an honest index, reachability depends on the aggregator accepting attacker-labeled indices; in the minimal library-level contract shown here, `complete` itself performs no such sanitization.

### Recommendation
Replace the length/range checks with an exact-membership check: verify that `proofs.keys().collect::<BTreeSet<_>>()` equals `{1..=n} \ {params.i()}`, returning `PromotionError::IncorrectAmountOfParticipants` (or a new `MissingParticipant`/`SelfProofProvided` variant) otherwise. Alternatively, change line 146 to `let proof = proofs.get(&i).ok_or(PromotionError::InvalidParticipant { n: params.n(), participant: i })?;` so an absent entry is a protocol error, not a panic.

### Proof of Concept
```rust
// Conceptual: C1 = C2 = Ristretto-backed ciphersuite with n = 3, we are participant 1.
let (promotion, _our_proof) = GeneratorPromotion::<C1, C2>::promote(&mut rng, base_keys);

let mut proofs = HashMap::new();
// Attacker-controlled map: n - 1 = 2 entries, all keys <= n, but contains
// the completer's own index and omits participant 2.
proofs.insert(Participant::new(1).unwrap(), forged_or_replayed_proof_a);
proofs.insert(Participant::new(3).unwrap(), proof_from_3);

// Passes len check (2 == n-1) and range check (all <= 3), then
// panics at proofs.get(&Participant(2)).unwrap()
let _ = promotion.complete(&proofs);
```

The panic occurs at `crypto/dkg/promote/src/lib.rs:146` because `proofs` has length `n - 1` with all keys `<= n`, satisfying both guards, while the required entry for participant 2 is absent.

Caveats: this conclusion is based on `complete`'s own validation (lines 124–156). If an outer caller pre-filters `proofs` to guarantee exact-set membership before calling `complete`, reachability would be reduced to a library-misuse panic rather than a protocol-reachable crash; the in-scope source I inspected contains no such guarantee inside `complete` itself.
