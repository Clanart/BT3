### Title
Attacker-controlled FROST nonce sum of point-at-infinity panics BIP-340 `hram`, crashing Bitcoin sign/verify - ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
The ezXML CVE-2019-20006 class — a crash (invalid free/segfault) triggered by attacker-supplied structured data — maps onto Serai as a panic reachable via untrusted signing inputs. In `networks/bitcoin/src/crypto.rs`, the helper `x()` calls `key.to_encoded_point(true)` and then `.expect("point at infinity")` on the x-coordinate [1](#0-0) . The BIP-340 challenge function `Hram::hram` invokes `x(R)` and `x(A)` on the aggregate nonce point `R` and group key `A` supplied by the caller [2](#0-1) . `hram` is reached from `Schnorr::verify`/`sign_share`, which wrap `FrostSchnorr::ietf()` over Secp256k1 [3](#0-2) . The aggregate `R` is a sum of per-participant nonce commitments, which come from preprocess messages read with `read_G` — bytes an unprivileged cosigner fully controls [4](#0-3) .

### Finding Description
A malicious participant in a threshold signing session can choose nonce commitments such that the summed nonce `R = Σ (D_l + rho_l * E_l)` is the point at infinity. Each individual point is a validly encoded Secp256k1 point, so deserialization accepts them; only their linear combination degenerates. When `verify`/`hram` then calls `x(R)` to compute the BIP-340 challenge, `to_encoded_point(...)` returns no x-coordinate for infinity and `.expect("point at infinity")` panics [1](#0-0) . Because `rho` binding values are computed over all included preprocesses, an attacker who sees honest participants' preprocesses before publishing their own (standard non-simultaneous broadcast) can solve for a commitment that cancels the sum. The same panic exists in `x_only` [5](#0-4)  and propagates through `tweak_keys`-adjacent paths; `Schnorr`'s own docs admit it "MAY panic" on infinity nonces [6](#0-5) .

### Impact Explanation
An unprivileged cosigner in any Bitcoin FROST signing session can deterministically panic every honest node evaluating `hram` on the poisoned aggregate nonce, aborting the signing attempt and crashing any caller that does not catch panics (a DoS identical in effect to the CVE's segfault). It does not leak key material. Uncertainty: I could not fully verify whether `crypto/frost/src` rejects identity nonce sums before `hram` is evaluated (the `is_identity` hits in `curve/mod.rs`/`nonce.rs` were not inspected); if such a guard exists before challenge computation, reachability drops.

### Likelihood Explanation
Requires the attacker to be a participant in the signing set (they must submit a preprocess), and to observe peers' commitments before publishing theirs — realistic in non-synchronized broadcast. The commitment that forces the sum to infinity is a solvable linear condition over public data, so it is reliable, not probabilistic.

### Recommendation
Return an error instead of panicking: have `x()`/`x_only()` return `Option`/`io::Result` and have `hram`/`verify`/`sign_share` reject identity `R`/`A`. Preferably, reject nonce sums equal to identity in the FROST aggregation layer itself so no algorithm variant can reach this state.

### Proof of Concept
```rust
// In a 2-of-n signing session over Secp256k1 (bitcoin-serai Schnorr):
// 1. Honest peer broadcasts nonce commitments (D_h, E_h).
// 2. Attacker computes rho for each included participant from the
//    preprocesses transcript (public), then chooses commitments
//    (D_a, E_a) such that:
//      (D_h + rho_h * E_h) + (D_a + rho_a * E_a) == ProjectivePoint::IDENTITY
//    e.g. pick E_a = G, solve D_a = -(R_h) - rho_a * G where R_h is the
//    honest partial sum.
// 3. All encodings are valid SEC1 compressed points, so read_G accepts.
// 4. Honest node calls Schnorr::verify -> FrostSchnorr::verify -> Hram::hram
//    -> x(R) -> to_encoded_point(true).x() == None for infinity
//    -> .expect("point at infinity") panics.
```
