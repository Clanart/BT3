### Title
Division by zero panic in `consolidatedNode.Split` halts block finalization when a proposer's CN+CL staking amount is both zero - (File: kaiax/staking/staking_info.go)

### Summary
`consolidatedNode.Split` divides the proposer's minting/fee reward by `totalAmount = StakingAmount + CLStakingInfo.CLStakingAmount` with no zero-check. This mirrors the reported `slashIndex == 0` division-by-zero bug class: an edge-case value of exactly zero in a state-derived variable is never guarded before being used as a divisor, and the call sites that invoke `Split()` for the block proposer do not gate on any minimum-stake condition, unlike other staking reward paths in the same file.

### Finding Description
`consolidatedNode.Split` is defined as: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)   // <-- panics if totalAmount == 0
	...
}
```
`math/big.Int.Div` panics unconditionally when the divisor is zero, exactly analogous to `divWadDown` reverting on zero denominator in the reported bug.

This `Split` is invoked unconditionally (no minimum-stake gate) whenever the current block's proposer has a registered `CLStakingInfo`, in both the Kore and Flex reward paths: [2](#0-1) [3](#0-2) 

Contrast this with `assignStakingRewards`/`assignStakingRewardsFlex`, which only call `Split` after verifying `cnTotalStakingAmount > minStake` (i.e., division is protected): [4](#0-3) 

No such guard exists for the *proposer's own* reward split. `StakingAmount` (CN-only stake) and `CLStakingInfo.CLStakingAmount` (consensus-liquidity pool stake) are read straight from on-chain state each epoch/block: [5](#0-4) 

Crucially, validator "qualification" for RoundRobin and Sticky proposer policies does **not** require any minimum stake — every council member is eligible to propose regardless of stake amount: [6](#0-5) 

So a council member can withdraw its entire CN stake (a normal, permissionless staking-contract withdrawal transaction) down to `StakingAmount == 0`, while its registered consensus-liquidity pool (`CLStakingInfo`) also currently has `CLStakingAmount == 0` (e.g., freshly registered, or fully withdrawn by CL depositors). This validator remains in the council and, under RoundRobin/Sticky policy, remains fully eligible to be selected `Proposer(N,R)`. When it is selected proposer and Prague is active with `CLStakingInfos != nil`, `FinalizeState` reaches `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` → `consolidatedNode.Split(proposer)` with `totalAmount == 0`, causing a Go panic inside deterministic state-transition code.

### Impact Explanation
Because the panic occurs inside deterministic block finalization logic (`FinalizeState`) that every full node executes identically, this is not a single node's local failure — every honest node processing that block hits the same panic. This is a consensus-liveness-breaking condition (block finalization halts network-wide) rooted in reward/staking accounting, directly in the "staking and reward distribution" and "state transition" scope. It matches the severity class of the source report: an unguarded division that turns an achievable, low-cost state condition (zero-value denominator) into a systemic failure rather than a contained error.

### Likelihood Explanation
Reaching `StakingAmount == 0` for a council member requires only ordinary CN-staking withdrawal transactions, which are permissionless operations available to any staker. Reaching `CLStakingAmount == 0` for the same node's registered CL pool similarly requires only that no one (or nobody currently) has deposited into that specific CL pool, or that all CL depositors withdraw — also permissionless. Both conditions coinciding is plausible especially right after a validator registers a new CL pool (default balance 0) while intentionally or incidentally holding zero CN stake, and under RoundRobin/Sticky proposer policy (used by many private/permissioned networks and reachable by governance parameter configuration) there is no staking-based exclusion preventing this validator from being chosen proposer.

### Recommendation
Guard `consolidatedNode.Split` against a zero denominator, mirroring the safe pattern already used in `assignStakingRewards`/`assignStakingRewardsFlex`:
```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	totalAmount := c.StakingAmount + c.CLStakingInfo.CLStakingAmount
	if totalAmount == 0 {
		return amount, big.NewInt(0) // or explicit fallback policy
	}
	...
}
```
Additionally, apply the same minimum-stake style guard at the two proposer-reward call sites (`specWithProposerAndFunds`, `specWithProposerAndFundsFlex`) so proposer reward splitting is never attempted when both CN and CL stakes are zero.

### Proof of Concept
1. Deploy/operate a Kaia network with `istanbul.policy` = RoundRobin or Sticky and Prague hardfork active, with a `CLRegistry`/CL pool contract installed.
2. A council-member validator `V` registers a `CLStakingInfo` for a new/empty CL pool (`CLStakingAmount == 0` at that block).
3. `V` withdraws its entire CNStaking balance via the standard staking-contract withdrawal function, bringing `StakingAmount` to `0` while `V` remains in the council (RoundRobin/Sticky does not evict on zero stake).
4. When round-robin/sticky rotation selects `V` as `Proposer(N,R)`, `FinalizeState` computes the deferred reward and calls `specWithProposerAndFunds(Flex)` → `consolidatedNode.Split(proposer)` for `V`'s consolidated node, where `totalAmount = 0 + 0 = 0`.
5. `big.Int.Div` panics inside block finalization; every honest node processing block `N` panics identically, halting chain progress.
