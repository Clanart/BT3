Based on the investigation, I found a plausible Agave analog to the Timeless `Gate.sol` bug, but I want to be upfront: I was not able to fully verify whether `pending_delegator_rewards` is decremented somewhere in the reward-calculation pipeline I didn't get to inspect (e.g., inside `calculate_rewards`/`compute_new_epoch_caches_and_rewards`, which I only partially reviewed). My targeted greps for any subtraction/reset of `pending_delegator_rewards` in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` and `calculation.rs` returned no matches, which is the basis for this finding, but this is not a complete proof of absence given the size of `vote_state/mod.rs` and `vote_processor.rs` that I couldn't fully read line-by-line within budget.

### Title
Potential re-distribution of stale `pending_delegator_rewards` in block-revenue-sharing epoch rewards - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The external report's root cause is that a "yield pool" value (accrued yield per token) is read to compute a recipient's share of rewards, but the source account balance is mutated before the pool value is correctly consumed/finalized for that recipient, causing an over-distribution of yield. The closest Agave analog is `calculate_block_reward` [1](#0-0) , which reads the full accumulated `pending_delegator_rewards` value from a vote account's state every epoch and distributes a proportional share of that *entire* pool to each delegator's stake account, without any code path I could locate that decrements or zeroes `pending_delegator_rewards` on the vote account after distribution.

### Finding Description
`pending_delegator_rewards` is a field on `VoteStateV4` that accumulates lamports deposited via `deposit_delegator_rewards` (SIMD-0123): [2](#0-1) . This function only ever adds to the field via `add_pending_delegator_rewards` [3](#0-2) .

Each epoch, when block-revenue-sharing is active, `calculate_block_reward` reads this same accumulated total and computes each delegator's block reward as `pending_delegator_rewards * stake / total_active_stake`, capped at `pending_delegator_rewards`: [4](#0-3) . This reward is then minted directly onto the *stake* account's lamport balance in `build_updated_stake_reward`, via `account.checked_add_lamports(partitioned_stake_reward.block_reward)`: [5](#0-4) .

I searched `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` and `calculation.rs` for any write/decrement of `pending_delegator_rewards` and found none — the only writes to that field that I could locate are the `add_pending_delegator_rewards` call in the deposit path and test-only direct assignments used to simulate withdraw-instruction state in `vote_processor.rs` test code. If there is truly no step that reduces the vote account's `pending_delegator_rewards` by the amount already distributed as block reward (or that snapshots/moves the "distributable" portion out of the field at the start of the epoch-rewards cycle), then every subsequent epoch's `calculate_block_reward` call would again use the *undiminished* total `pending_delegator_rewards`, re-distributing the same "pool" to stake accounts every epoch — effectively minting stake rewards not backed by any actual reduction in the vote account's tracked pending-rewards liability.

### Impact Explanation
If confirmed, this would be a fund-creation/inflation bug: stake accounts delegated to a vote account with nonzero `pending_delegator_rewards` would receive a block-revenue-sharing reward every epoch computed off the same undecremented pool, rather than only once. Since `build_updated_stake_reward` mints lamports directly onto stake accounts (`checked_add_lamports`) using this value, and the corresponding capitalization/sysvar accounting (`stake_reward_lamports_minted`, `block_reward_lamports_distributed`) tracks amounts distributed in that specific epoch's partition rather than draining the vote account's `pending_delegator_rewards` field itself, this could cause validators to be paid the same delegator-deposited reward pool repeatedly, corrupting global lamport supply invariants — a "false execution/acceptance" class issue affecting consensus-relevant state (stake balances feed into future consensus weight).

### Likelihood Explanation
Moderate-to-low confidence — I was unable to fully trace the entire epoch-rewards calculation pipeline (`calculate_rewards`, `compute_new_epoch_caches_and_rewards`) end-to-end within the available search budget to rule out a decrement/consumption step that I simply didn't locate (e.g., it's plausible `pending_delegator_rewards` is snapshotted and zeroed elsewhere as part of `update_epoch_stakes` or a related VAT/epoch-boundary routine referenced in comments about "VAT burns in `update_epoch_stakes`"). This needs direct code confirmation before being treated as a confirmed vulnerability.

### Recommendation
Verify whether `pending_delegator_rewards` is reduced/zeroed by the exact amount distributed as block reward at the point calculation happens (ideally atomically with the read in `calculate_block_reward`, or at epoch-boundary snapshot time before computing `total_active_stake`-proportional shares). If no such decrement exists, `calculate_block_reward` and/or the epoch-boundary snapshot logic (`compute_new_epoch_caches_and_rewards`) needs to consume/zero the distributed portion of `pending_delegator_rewards` on the vote account so the same pool cannot be redistributed in subsequent epochs.

### Proof of Concept
Not able to construct with full confidence without confirming the missing decrement step; would require:
1. Delegate stake to a vote account.
2. Call `deposit_delegator_rewards` to set `pending_delegator_rewards = N`.
3. Let two consecutive epochs elapse with `calculate_block_reward` invoked each epoch.
4. Confirm whether the stake account receives a reward proportional to `N` in *both* epochs (bug) or only once with the field reduced accordingly (no bug).

Given the residual uncertainty about the missing decrement step, this should be treated as a lead requiring direct code confirmation in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`'s `calculate_rewards`/`compute_new_epoch_caches_and_rewards` and any VAT/epoch-stakes-update logic mentioned in comments, rather than a fully confirmed finding.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
