## Analysis: Asymmetric path-containment validation in file-open/reveal actions

The report's underlying pattern is: **a security invariant (state/whitelist validation) is enforced on one code path but is silently missing on a structurally identical path that handles the same kind of value**, letting an attacker (or unlucky sequence of events) slip past the guard through the unchecked path. The same anti-pattern exists in GitHub Desktop's file-path handling.

### The guarded path (exists)
When Desktop resolves a file path that arrived from an untrusted, attacker-influenced source — the `x-github-client://openRepo/...?filepath=...` deep link — it explicitly guards against path traversal: [1](#0-0) 

It rejects absolute paths and calls `resolveWithin(repository.path, filepath)`, which normalizes, resolves symlinks via `realpath`, and rejects anything not underneath the repository root: [2](#0-1) 

### The unguarded, structurally identical paths (missing)
Multiple other UI entry points build essentially the same "repository root + attacker/PR-controlled relative path" value, but use a raw `Path.join` with **no containment check at all**, then hand it to `shell.showItemInFolder`, `openFile`, or the external editor launcher: [3](#0-2) 

Callers that feed attacker/API-controlled `file.path` values into this unguarded join include the pull-request file list (populated from the GitHub API's PR file data, which is attacker-controlled by whoever authored the fork/PR): [4](#0-3) 

and the commit history file viewer / changes list, which do the same `Path.join(repository.path, file.path)` pattern without ever calling `resolveWithin`: [5](#0-4) [6](#0-5) 

Notably, `IAppShell.showItemInFolder`'s own doc comment even flags this exact requirement ("Do not use this method with non-validated paths") — the invariant is documented but not enforced at these call sites, mirroring the missing `TokenState.InOut` check on the Synthesis side of the original report: [7](#0-6) 

### Why this matters
The codebase has already hardened an almost identical class of attack for clone destinations — a backslash-based traversal payload (`x..\..\..\..\foo`) that escapes the intended base directory on Windows because `\` is a path separator there but not rejected by naive component checks: [8](#0-7) [9](#0-8) 

That same backslash trick is not blocked by Git's own tree-entry validation (a single tree/path component only needs to avoid being *literally* `..`; a component like `evil..\..\..\ssh\id_rsa` is a legal single git path component containing embedded backslashes) and is not re-checked anywhere in the PR-file / commit-file "reveal" and "open" code paths, unlike the deep-link handler.

### Impact
A malicious fork/PR author can craft a committed filename containing a Windows-style backslash traversal sequence. When a victim on Windows opens that PR in Desktop (`checkoutPullRequest` → `PullRequestFilesChanged`) or views it in the commit history, and right-clicks "Reveal in Explorer" / "Open with Default Program" / "Open in External Editor", `Path.join(repository.path, file.path)` resolves outside the repository to an attacker-chosen location on the victim's disk (e.g. `%USERPROFILE%\.ssh\id_rsa` or another sensitive file), which is then revealed in Explorer or opened by the OS default handler / configured editor — disclosing the existence/contents of files outside the repository, entirely from opening an untrusted PR/diff, with no local access or extra user steps beyond normal PR review.

### Title
Path traversal via unvalidated `file.path` in PR/commit "Reveal in File Manager" / "Open" actions - (File: `app/src/lib/app-shell.ts`)

### Summary
`revealInFileManager` and the various `onFileContextMenu`/`openFile` handlers join `repository.path` with an attacker-influenced relative `file.path` (sourced from PR diffs/commits) using plain `Path.join`, with no equivalent of the `resolveWithin` containment check that Desktop already applies to deep-link-provided file paths.

### Finding Description
`dispatcher.ts`'s `openRepositoryFromUrl` treats externally-supplied filepaths as untrusted and validates containment via `resolveWithin` before calling `shell.showItemInFolder`. The same repository-root-plus-relative-path construction is repeated in `pull-request-files-changed.tsx`, `selected-commits.tsx`, `filter-changes-list.tsx`, and conflict-resolution UI, all using a bare `Path.join` and no traversal check, even though `IAppShell`'s own documentation states these shell APIs must not be used with "non-validated paths." Filenames displayed here originate from PR file lists / diffs, which are ultimately attacker-controlled content (the PR author's fork). A crafted filename using backslash-based traversal (the exact class already mitigated for clone destinations in `clone.ts`/`remote-parsing.ts`) is not rejected by Git tree validation and is not re-validated in these UI paths.

### Impact Explanation
Successful exploitation lets a malicious PR/fork author cause a victim's Desktop client to reveal or open a file located outside the repository working directory (e.g., SSH keys, config files) via normal "Reveal in File Manager"/"Open" context-menu actions — an unprompted, natural review workflow. This is a read/exposure-outside-repo primitive attributable to attacker-controlled GitHub API/diff content, satisfying the impact bar (file read/exposure outside the repo boundary via a GitHub API/PR object).

### Likelihood Explanation
Requires the victim to view an attacker's PR/fork in Desktop and use a context-menu "Reveal"/"Open" action on the malicious file — a normal, expected reviewer workflow, not a contrived local-access scenario. Windows-specific due to reliance on `\` as a path separator, but Desktop explicitly supports Windows and the maintainers have already had to patch an identical primitive elsewhere (`clone-path-safety-test.ts`), indicating real-world plausibility.

### Recommendation
Route every `repository.path` + `file.path` join used for `revealInFileManager`, `openFile`, and external-editor launches through `resolveWithin` (or `resolveWithinWin32` platform-appropriately), rejecting/aborting the action when the resolved path escapes the repository root, exactly as already done in `dispatcher.ts`'s `openRepositoryFromUrl`.

### Proof of Concept
1. Attacker creates a fork/branch and commits a file whose path is a single git tree component containing a Windows traversal payload, e.g. `evil..\..\..\..\Users\victim\.ssh\id_rsa` (git only forbids a component literally equal to `..`, not embedded `\..\` sequences), and opens a PR against the victim's repo.
2. Victim opens the PR in GitHub Desktop (`Open in Desktop` → `PullRequestFilesChanged`).
3. Victim right-clicks the suspicious-looking file entry and selects "Show in Explorer" / "Open with Default Program".
4. `Path.join(repository.path, file.path)` resolves outside the repository (interpreted by Windows as a `..` traversal), and `shell.showItemInFolder`/`openFile` operate on the out-of-repo target without any `resolveWithin` containment check, unlike the equivalent deep-link code path in `dispatcher.ts`.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
