### Title
Malicious participant can crash the FROST/Bitcoin signer by submitting identity (point-at-infinity) nonce commitments — (File: networks/bitcoin/src/crypto.rs)

### Summary
The Serai codebase contains a reachable panic on untrusted input analogous to CVE-2017-15121 (unprivileged input triggering a system crash). In `networks/bitcoin/src/crypto.rs`, `Hram::hram` calls `x(R)`/`x(A)`, and `x` unconditionally calls `key.to_encoded_point(true).x().expect("point at infinity")`. A participant in a FROST signing session supplies nonce commitments (D, E) via `read_preprocess`/`Commitments::read`, which accept any canonically encoded point — including the identity. If the binding sum `R = D + rho * E` ends up as the point at infinity (trivially achieved by sending identity commitments), the `expect` panics inside `sign`, crashing the signer process mid-session.

### Finding Description
`Commitments::read` (crypto/frost/src/nonce.rs, `GeneratorCommitments::read` lines 34–36 / `NonceCommitments::read` lines 74–80) deserializes attacker-controlled generator commitments with `C::read_G`, which enforces canonical encoding but does not reject the identity point. The FROST `sign` path (crypto/frost/src/sign.rs, `AlgorithmSignMachine::sign` ~line 283) computes aggregate nonce sums and invokes the algorithm's `Hram`. For Bitcoin signing, `Schnorr` wraps `FrostSchnorr<Secp256k1, Hram>` where `hram` (networks/bitcoin/src/crypto.rs lines 59–73) calls `x(R)` and `x(A)`; `x` (lines 13–16) does `encoded.x().expect("point at infinity")`, documented as "Panics on invalid input". The docstring on `Schnorr` (lines 78–83) claims infinity inputs have "a negligible probability... even with malicious participants present" — that reasoning is wrong: a malicious participant can *choose* identity commitments deterministically, no grinding required.

### Impact Explanation
A single faulty participant in any Bitcoin `TransactionSignMachine::sign` (networks/bitcoin/src/wallet/send.rs lines 355–398) or generic `AlgorithmSignMachine` session can crash the processor node with a panic at the moment shares are computed. This is availability loss of the threshold signer — a signing node taken down by public preprocess bytes. It matches the original bug class (unprivileged input reaches a boundary case — here the identity "hole" in the point set — causing a crash) and is reachable entirely through `read_preprocess` bytes.

### Likelihood Explanation
Any participant index able to send a preprocess can submit encodings of the identity point for both nonce commitments (D = E = infinity ⇒ R = infinity for every generator). No collusion, no race, no computational work is needed. Triggering requires only participation in a signing session.

### Recommendation
Reject the identity point in `read_G` for nonce commitments (or explicitly in `GeneratorCommitments::read`/`NonceCommitments::read`), consistent with the FROST spec's requirement that nonce commitments be non-identity. Additionally, make `x()`/`x_only()`/`Hram::hram` return `Option`/errors instead of panicking, or have `AlgorithmSignMachine::sign` detect an identity aggregate nonce and return `FrostError::InvalidPreprocess(l)` identifying the faulty participant.

### Proof of Concept
1. Join a signing session as any participant `l`.
2. In the preprocess message, encode `NonceCommitments` where every `GeneratorCommitments` pair is two canonical encodings of the secp256k1 identity (for k256, `0x00` SEC1 encoding).
3. The victim's `read_preprocess` accepts the bytes (canonical, so `read_G` passes).
4. During `sign`, the binding factor `rho` is computed; `R = D + rho*E = infinity`.
5. `Hram::hram` calls `x(&R)` → `encoded.x().expect("point at infinity")` → panic, crashing the signer thread/process.

Note on uncertainty: I confirmed the panic site and the deserialization path, and saw no identity rejection in the shown `sign`/`Commitments::read` code; if an upstream caller filters identity commitments before `sign`, reachability would depend on that filter, which I could not fully verify within scope.
