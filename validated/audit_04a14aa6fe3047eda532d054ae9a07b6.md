## Finding: Permanent fund loss on timeout refund when `update_token` removes a chain while a `send()` is in-flight — (File: `modules/pallets/hyper-fungible-token/src/module.rs` / `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
The original report's broken invariant is: a token's registration/whitelist status can change on one side of a bridge operation between the time funds are locked/burned and the time the counter-leg validates that status, causing the counter-leg to revert and the already-spent side's funds/fee to be stranded. The same invariant is broken in `pallet-hyper-fungible-token`: the mapping the pallet uses to identify *which local asset* an in-flight cross-chain request belongs to (`ContractToAsset`) is a mutable, admin-controlled map keyed by `(StateMachine, contract_address)`, and it is consulted identically by both the success path (`on_accept`) and the refund path (`on_timeout`). If this mapping is changed after a `send()` has already escrowed/burned the user's tokens but before the corresponding request resolves, the refund path can no longer resolve the asset and permanently fails — unlike the reported bug (fee-only loss), this leaves the user's **principal** unrecoverable.

### Finding Description
`send()` escrows or burns the sender's tokens immediately and only afterwards dispatches the ISMP `PostRequest`: [1](#0-0) [2](#0-1) 

The corresponding refund logic in `on_timeout` re-derives the local asset purely from the *current* state of `ContractToAsset`, keyed by `(dest, to)` where `to` is the destination contract address recorded in the original request body: [3](#0-2) 

`ContractToAsset` and `Precisions` are mutated by `update_token`'s `remove_chains` branch, which unconditionally clears the very entries `on_timeout` (and `on_accept`) depend on: [4](#0-3) 

Because the pallet keeps no per-request snapshot of the asset/decimals used at send time, any `send()` whose request is still outstanding (not yet accepted, not yet timed out) when a `remove_chains` (or `add_chains` with an old-contract removal, see line 408-411) update runs against the same `(dest, asset)` pair will hit `HftError::UnknownContractOnTimeout` or `HftError::DecimalsNotConfigured` on timeout. Since `on_timeout` returns `Err`, the refund transfer/mint back to the sender never executes, so the escrowed or burned tokens are gone — the sender neither receives the cross-chain credit (destination changed) nor the local refund (source lookup now empty).

### Impact Explanation
This produces genuine loss/lock of user principal, not just a relayer fee, for the exact same class of bug the report describes (a mid-flight change to token-status/registration state that a later verification step relies on). Any legitimate token-maintenance action, such as migrating a destination contract address or removing chain support with `update_token`, silently strands every in-flight `send()` for that `(dest, asset)` pair issued before the update but not yet resolved — with no on-chain recovery path.

### Likelihood Explanation
`update_token` is expected to be used routinely for legitimate maintenance (contract redeploys, decimal corrections, deprecating a destination chain). There is no coordination between in-flight requests and this call, and no pending-request snapshot mechanism, so the race window exists on every `update_token` call, not just adversarial ones — increasing the odds of unintentional but real fund loss for ordinary users mid-transfer.

### Recommendation
Snapshot the asset id, decimals, and native/non-native classification into the dispatched request body (or a per-commitment storage entry keyed by the ISMP commitment) at `send()` time, and have `on_accept`/`on_timeout` resolve against that snapshot instead of re-reading the live, admin-mutable `ContractToAsset`/`Precisions`/`NativeAssets` maps. Alternatively, disallow `remove_chains`/contract changes for a chain while requests dispatched against the old contract address are still outstanding (e.g. track pending commitments per `(chain, asset)`).

### Proof of Concept
1. Admin registers asset `X` for `StateMachine::Evm(1)` with contract `C1` via `register_token`.
2. User calls `send()` for asset `X` to `Evm(1)`; tokens are burned/escrowed; `DispatchPost` is sent with `to = C1`.
3. Before the request is delivered/times out, admin calls `update_token` with `remove_chains = [Evm(1)]` (e.g., because `C1` is being deprecated in favor of `C2`), which executes `ContractToAsset::remove(Evm(1), C1)` and `Precisions::remove(X, Evm(1))`.
4. If delivery to `C1` fails or is never relayed and the request times out, `on_timeout` calls `ContractToAsset::<T>::get(dest, &to)` with `to = C1`, which now returns `None`, raising `HftError::UnknownContractOnTimeout`.
5. The refund transfer never executes; the user's escrowed/burned tokens are permanently unrecoverable. [5](#0-4) [6](#0-5)

		match request {
			Request::Post(PostRequest { body, to, dest, .. }) => {
				let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

				// Refund the original sender
				let from_bytes = message.from.as_ref();
				let mut sender_bytes = [0u8; 32];
				if from_bytes.len() == 32 {
					sender_bytes.copy_from_slice(from_bytes);
				} else if from_bytes.len() == 20 {
					sender_bytes[12..].copy_from_slice(from_bytes);
				} else {
					Err(HftError::InvalidSenderLength(from_bytes.len()))?
