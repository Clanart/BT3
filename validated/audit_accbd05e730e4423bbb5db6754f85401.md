## Title
Clawback auto-claim batches multiple independent coins into one atomic spend bundle, letting an attacker-controlled coin invalidate the whole batch (DoS to `auto_claim_coins`) - (File: `chia/wallet/clawback_manager.py`)

### Summary
`ClawbackManager.auto_claim_coins()` groups up to `auto_claim_batch_size` unrelated clawback merkle coins (which can originate from different, mutually untrusted senders) and hands them to `spend_clawback_coins()`, which aggregates all of their individual `CoinSpend`s into a single `WalletSpendBundle` and pushes it as one atomic transaction [1](#0-0) . This mirrors the reported Y2K `mintRollovers()` bug class: independent, per-item state (in Y2K, share ownership; here, whether a clawback coin is still unspent) is not re-verified at the moment the shared batch is finally submitted, so if any single item in the batch becomes stale, the entire combined operation fails and blocks the legitimate items bundled with it.

### Finding Description
`auto_claim_coins` selects unspent clawback coins whose timelock has elapsed and accumulates them into a dict, flushing to `spend_clawback_coins` once `auto_claim_batch_size` is reached (or at the end of the loop) [2](#0-1) . Inside `spend_clawback_coins`, each coin's `CoinSpend` is built inside a `try/except` that only guards against local bookkeeping problems (e.g. the coin's incoming tx already being "sent") [3](#0-2) ; it does not re-check that the coin is still unspent on-chain at build/push time. All successfully built `CoinSpend`s are then combined into a single `WalletSpendBundle`, wrapped in one `TransactionRecord`, and queued for push [4](#0-3) .

Because clawback lets the **sender** revert their own coin at any time (independent of the recipient's timelock), a malicious sender can send several small clawback payments to a victim recipient, wait until the recipient's `auto_claim_coins` batches these coins together with other, unrelated legitimate claims (e.g. from other senders) into a single pending batch, then race the recipient by clawing back (spending) their own coin just before the batch's aggregated spend bundle is submitted. When the combined bundle reaches the mempool, the one already-spent coin causes `check_removals()`/mempool validation to reject the whole bundle as a double spend, since it evaluates all `bundle_coin_spends` in the item together [5](#0-4) . This causes every other legitimately-claimable coin bundled in that same transaction to also fail to be claimed, even though only the attacker's own coin was stale.

The user-facing RPC path `spend_clawback_coins` has the same structure: it chunks `coin_ids` into `batch_size` groups and calls `clawback_manager.spend_clawback_coins` per chunk, again combining each chunk's spends into one bundle [6](#0-5) , so the same batching hazard applies whenever multiple coin owners' claims (or a user's own coins alongside a maliciously-raced counterparty coin) are chunked together.

### Impact Explanation
An unprivileged clawback counterparty (the sender side of a clawback transaction, who fully controls when to revert their own coin) can repeatedly grief a victim's automated claiming process: by timing their own coin's revert to coincide with the recipient's batched auto-claim submission, they can cause the atomic push to fail for the whole batch, denying/delaying the claim of other, unrelated clawback coins that happen to be batched together. This is a spend-triggered transaction-processing halt for the victim's claim flow — no funds are directly stolen, but service (timely claiming of one's own funds) is denied to honest parties whose coins are bundled with the attacker's.

### Likelihood Explanation
This requires no special privilege — any wallet that is a clawback *sender* can trigger the race by broadcasting a clawback-revert spend for its own already-clawback-payment coin at the moment the recipient's periodic `auto_claim_coins` (or a `spend_clawback_coins` RPC batch) is about to submit. The batching behavior (aggregating multiple independent coins into one spend bundle without a final on-chain re-check) is deterministic and reproducible; the main variable is timing the race against the recipient's periodic auto-claim cadence or RPC batch call.

### Recommendation
Before combining coin spends into the final aggregate bundle in `spend_clawback_coins`, re-verify each coin's on-chain spent status (or at minimum split failures per-coin and retry the batch without the stale coin instead of submitting one bundle atomically), so that one stale/attacker-controlled coin cannot block the processing of unrelated coins bundled in the same transaction.

### Proof of Concept
1. Attacker (sender) sends several small XCH transfers with clawback to victim, timelock T.
2. Victim's wallet accumulates multiple claimable clawback coins (from attacker and other honest senders) and batches them together in `auto_claim_coins` once `auto_claim_batch_size` is reached.
3. Right before/while the victim's wallet pushes the combined `spend_bundle` (containing all batched coins' `CoinSpend`s), attacker submits a clawback-revert spend for their own coin, spending it first.
4. The victim's combined spend bundle now references an already-spent coin; mempool validation via `check_removals` rejects the whole bundle as `DOUBLE_SPEND` [7](#0-6) , so none of the other honest senders' coins in that batch get claimed in this round, even though they remained valid and unspent.

    async def auto_claim_coins(self, action_scope: WalletActionScope) -> None:
        # Get unspent clawback coin
        current_timestamp = self.blockchain.get_latest_timestamp()
        clawback_coins: dict[Coin, ClawbackMetadata] = {}
        unspent_coins = await self.coin_store.get_coin_records(
            coin_type=CoinType.CLAWBACK,
            wallet_type=WalletType.STANDARD_WALLET,
            spent_range=UInt32Range(stop=uint32(0)),
            amount_range=UInt64Range(
                start=action_scope.config.tx_config.coin_selection_config.min_coin_amount,
                stop=action_scope.config.tx_config.coin_selection_config.max_coin_amount,
            ),
        )

        for coin in unspent_coins.records:
            try:
                metadata = coin.parsed_metadata()
                assert isinstance(metadata, ClawbackMetadata)
                if await metadata.is_recipient(self.puzzle_store):
                    coin_timestamp = await self.timestamp_for_height(coin.confirmed_block_height)
                    if current_timestamp - coin_timestamp >= metadata.time_lock:
                        clawback_coins[coin.coin] = metadata
                        if len(clawback_coins) >= self.auto_claim_batch_size:
                            await self.spend_clawback_coins(clawback_coins, self.auto_claim_tx_fee, action_scope)
                            clawback_coins = {}
            except Exception as e:
                self.log.error(f"Failed to claim clawback coin {coin.coin.name().hex()}: %s", e)
        if len(clawback_coins) > 0:
            await self.spend_clawback_coins(clawback_coins, self.auto_claim_tx_fee, action_scope)
