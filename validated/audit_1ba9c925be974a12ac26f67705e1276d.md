### Title
Trampoline server trusts any local caller holding a live token, letting a repo-controlled Git subprocess (hook/filter) request the signed-in GitHub credential for an arbitrary host - (File: `app/src/lib/trampoline/trampoline-server.ts`)

### Summary
GitHub Desktop's "trampoline" mechanism is the local analog of the report's off-chain relayer: Desktop spawns `git` with `GIT_ASKPASS`/`credential.helper=desktop` pointed at a small trampoline binary, and passes it `DESKTOP_PORT` + `DESKTOP_TRAMPOLINE_TOKEN` via environment variables so the binary can call back into the Desktop process over a local TCP socket [1](#0-0) . Just like the Gelato relay case, the receiving side (`TrampolineServer`) can only check "did this caller present a currently-valid token" — it has no way to verify that the caller is actually the specific `git` child process performing the specific fetch/clone/checkout for which the token was minted [2](#0-1) . The token itself is a bare, unscoped UUID stored in a global `Set` [3](#0-2) , valid for the whole duration of that git operation, and any of git's own subprocesses (hooks, smudge/clean filters, credential helpers invoked transitively) inherit the same environment variables as the top-level `git` process, so they can also speak the trampoline protocol.

### Finding Description
The broken invariant is: "a request received by the trampoline server for the get-credential command actually corresponds to the outstanding, singular git remote authentication attempt Desktop is expecting for a given account/endpoint." Desktop instead accepts *any* request carrying a valid, unexpired token and answers it with the real GitHub account credential if the requested `endpoint` origin matches a signed-in account:

- `createCredentialHelperTrampolineHandler` -> `getCredential` -> `getGitHubCredential` looks up the account purely by comparing `getCredentialUrl(cred)` origin to a signed-in account's endpoint, and if found, returns the account's real `login`/`token` [4](#0-3) .
- The `host`/`url` fields used to build that credential URL come straight from attacker-controllable input passed to the trampoline binary (git's credential-helper protocol), not something Desktop independently derives from the remote it's actually operating on [5](#0-4) .
- Nothing in `processCommand` binds the command to the git subcommand/remote that the token was minted for; it only checks token validity and dispatches by `identifier` [6](#0-5) .

Because a cloned/fetched repository can supply a Git hook (e.g. `post-checkout`, `post-merge`) or a clean/smudge filter (configured via `.gitattributes`/LFS) that executes as a child of the `git` process Desktop invoked, that hook inherits `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` from its environment. During the window that token is valid (for the whole operation, see `withTrampolineToken`) [7](#0-6) , that hook process can independently connect to `127.0.0.1:<DESKTOP_PORT>` and speak the `CREDENTIALHELPER get` protocol for `host=github.com`, causing Desktop to hand back the signed-in user's real GitHub token — a value having nothing to do with the fetch/clone operation the hook was spawned from.

### Impact Explanation
This is a credential-exfiltration primitive fully attacker-controlled through repository content: an attacker who gets a victim to clone or fetch their repository (or a repo containing a malicious submodule / LFS filter / hook shipped via `.git/hooks` through some vector, or more directly a build/filter script executed during checkout) can obtain the victim's live GitHub OAuth token without any additional user interaction, matching the "credential/token exfiltration" impact bucket explicitly called out as valid.

### Likelihood Explanation
The attacker fully controls the repository content and thus what hooks/filters run as children of the `git` process Desktop spawns; environment variable inheritance to child processes is default OS behavior, so no special privilege or host compromise is required beyond the victim performing a normal clone/fetch/checkout of the attacker's repository within Desktop. The remaining uncertainty is which specific hook types Desktop allows to execute unmodified during its automated git operations (some Git operations run with hooks disabled) — this could not be fully confirmed from the indexed code, so this should be validated by actually tracing whether `core.hooksPath`/`--no-verify` or similar restrictions are applied by Desktop's `git()` wrapper before treating this as confirmed-exploitable versus a hardening gap.

### Recommendation
Scope trampoline tokens to the specific operation and the specific expected remote host(s) rather than accepting any request bearing a live token; validate that the `host`/`url` in a `get` credential request matches the remote(s) actually configured for the repository/operation associated with that token before returning real account credentials, and consider binding the token to the originating process (e.g., via a per-connection handshake secret proven only by the direct child, not inheritable by grandchildren) so hook/filter subprocesses cannot silently reuse the parent's trampoline session.

### Proof of Concept
Conceptual PoC (not run, derived from code reading):
1. Attacker publishes a public repo with a `post-checkout` hook (or LFS smudge filter) script that reads `process.env.DESKTOP_PORT` / `DESKTOP_TRAMPOLINE_TOKEN`.
2. Victim clones the repo in GitHub Desktop; Desktop's `git clone` runs with `GIT_CONFIG_PARAMETERS=... credential.helper=desktop` and `DESKTOP_TRAMPOLINE_TOKEN=<token>` in its environment [8](#0-7) .
3. The hook, running as a child of `git`, opens a TCP socket to `127.0.0.1:<DESKTOP_PORT>` and sends a `CREDENTIALHELPER` `get` command with `host=github.com\n` using the inherited token, following the same wire protocol the desktop-trampoline binary uses.
4. `TrampolineServer.processCommand` accepts it because `isValidTrampolineToken(token)` is true [2](#0-1) , and `getGitHubCredential` returns the victim's real `login`/`token` for their GitHub.com account [4](#0-3) .
5. The hook exfiltrates the credential over any outbound network channel available to it.

Note: I was not able to fully verify within the indexed code whether Desktop's git wrapper disables hooks (`-c core.hooksPath=/dev/null` or similar) for clone/fetch operations, which would materially affect exploitability; this should be checked directly in `app/src/lib/git/` before treating the PoC as fully validated. Given the size limits on the indexed codebase, some relevant files (e.g. the full `git/core.ts` wrapper and hook-disabling logic) may not have been fully retrievable — a Devin session with full repo access would be able to confirm this definitively.

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}

const trampolineTokens = new Set<string>()

function requestTrampolineToken() {
  const token = crypto.randomUUID()
  trampolineTokens.add(token)
  return token
}

function revokeTrampolineToken(token: string) {
  trampolineTokens.delete(token)
}

/** Checks if a given trampoline token is valid. */
export function isValidTrampolineToken(token: string) {
  return trampolineTokens.has(token)
}

export async function withTrampolineToken<T>(
  fn: (token: string) => Promise<T>
): Promise<T> {
  const token = requestTrampolineToken()
  let result

  try {
    result = await fn(token)
  } finally {
    revokeTrampolineToken(token)
  }

  return result
}
