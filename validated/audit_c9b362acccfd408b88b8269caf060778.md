### Title
Cached FROST/MuSig preprocess seeds keyed by `(name, attempt)` only — nonce reuse across distinct confirmation contexts enables validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Vyper bug class is "named resources that should isolate distinct use sites are allocated/incorrectly keyed, causing cross-context interference." The direct analog in Serai is `CachedPreprocesses`, the DB table that persists the deterministic ChaCha20 seed from which a signing session's FROST nonces are derived. The cache key is `context.encode()`, and for the DKG-confirmer MuSig protocol the context is only `(b"DkgConfirmer", attempt)`. The validator set, the `spec` (genesis/set identity), the `removed` list, and the message being signed are *not* part of the key. Any two confirmation signing flows that share an `attempt` value but differ in the participant set or signed message will therefore reuse the same nonce seed — the exact precondition for Schnorr nonce-reuse private key recovery, which the code itself warns about.

### Finding Description
`preprocess_internal` generates a random seed, XOR-encrypts it under `Blake2s256("Cached Preprocess Encryption Key" || context || key)`, stores it via `CachedPreprocesses::set(txn, &self.context, &cache.0)`, and on subsequent calls *reuses* the stored seed via `from_cache`/`seeded_preprocess`, which feeds it to `ChaCha20Rng::from_seed` to derive the FROST nonces deterministically. [1](#0-0) [2](#0-1) 

The context for the only consumer, `DkgConfirmer`, is `(b"DkgConfirmer", self.attempt)`. [3](#0-2)  Yet the *signing statement* varies independently of that key:

- `musig(musig_context(spec.set()), key, participants)` binds the MuSig aggregate to `spec.set()` and the concrete `participants` vector — neither is in the context key. [4](#0-3) 
- `share_internal` signs `set_keys_message(&spec.set(), &removed, key_pair)`, which depends on the `removed` set read live from `removed_as_of_dkg_attempt`, plus `key_pair` — again none are in the context key. [5](#0-4) 

Consequently, if the same `attempt` is ever signed under two different binding contexts — e.g., the `removed` list changes mid-attempt (a removal transaction is confirmed while a DKG confirmation attempt is still open, changing the effective participants via `spec.i(removed, ...)`), or a second `TributarySpec`/rebuilt tributary re-runs the same attempt numbers against the same persistent DB — the same nonce `k` is committed under two different aggregate challenges `e`, `e'` (different participant sets and different messages produce different binding factors and different MuSig challenges). Two shares `s = k + e·a·x`, `s' = k + e'·a'·x` leak `x`, the validator's Ristretto MuSig key share. The file's own safety argument acknowledges nonce reuse is fatal and relies entirely on the decided nonces being context-bound under BFT finality — but that argument only covers *messages received within one BFT execution*; it does not cover the persistent cross-context collision in the `CachedPreprocesses` key itself. [6](#0-5) 

### Impact Explanation
The coordinator's MuSig key is the root of trust for confirming DKG results on-chain. Recovery of a validator's `key` share lets an attacker forge that validator's contribution to `set_keys` confirmations, and (because `key` is the validator's signing key, not an ephemeral share) potentially impersonate it in other contexts using the same key. Both shares and the final aggregated signature are published/observable on-chain and in tributary messages, so the two nonce-reuse shares are recoverable by an unprivileged observer of public data. This satisfies "key share recovery / signing an unintended message" from public inputs.

### Likelihood Explanation
The vulnerability requires `context` to collide across two *semantically distinct* sessions. `attempt` is a `u32` scoped to a DKG attempt, and `removed` is evaluated per-call at `DkgConfirmer::new` via `removed_as_of_dkg_attempt` — so a removal confirmed mid-attempt (the protocol explicitly supports evolving `removed` sets) changes participants and the signed message while the cache key stays fixed. Additionally, the DB is persistent across restarts and the context contains no `spec`/`genesis` binding, so a re-genesis or a new tributary instance reusing attempt numbering collides with stale entries. The `removed`-mutation path is the more reachable trigger and is driven by on-chain data an unprivileged party can cause (validator removals are submitted via normal transactions). I could not fully trace every `DkgConfirmer::new` call site in `handle.rs` within the available iterations, so the exact frequency of the `removed`-changes-mid-attempt window is uncertain, but the keying defect itself is unconditional: the nonce seed is provably not bound to the participants or message it is used to sign under.

### Recommendation
Include every parameter that can vary the signing statement in the cache key: extend the context to something like `(b"DkgConfirmer", spec.genesis(), spec.set(), removed_hash, attempt)` — or store the cached seed together with a commitment to the participants/message it was generated for, and refuse to `from_cache` when the current participants/message commitment differs. At minimum, bind `musig_context(spec.set())` and `removed` into `context` so `CachedPreprocesses::get` can only return a seed whose reuse is provably safe.

```rust
// Same validator key, same attempt, but the removed set (hence participants
// and msg = set_keys_message(set, removed, key_pair)) differs between calls.

let mut confirmer_a =
  DkgConfirmer::new(&key, &spec, &mut txn, attempt).unwrap(); // removed = []
let (machine_a, _pre_a) = confirmer_a.signing_protocol()
  .preprocess_internal(&participants_a);  // generates + caches seed S under ("DkgConfirmer", attempt)
let (sig_machine_a, share_a) = confirmer_a
  .share_internal(preprocesses, &key_pair).unwrap(); // s_a = k + e_a * a_a * x

// A removal is confirmed mid-attempt (or a second spec reuses `attempt`):
let mut confirmer_b =
  DkgConfirmer::new(&key, &spec, &mut txn, attempt).unwrap(); // removed = [v]
// CachedPreprocesses::get hits the same key -> same ChaCha20 seed S -> same nonces k.
let (sig_machine_b, share_b) = confirmer_b
  .share_internal(preprocesses_b, &key_pair_b).unwrap(); // s_b = k + e_b * a_b * x

// Observers of share_a and share_b solve:
//   x = (s_a - s_b) / (e_a*a_a - e_b*a_b)
// recovering the validator's MuSig secret share, forging future confirmations.
```
The root cause is that `seeded_preprocess` derives nonces solely from `CachedPreprocess` [7](#0-6)  while `CachedPreprocesses` is indexed only by the caller-supplied `context`, which omits the participant set and message. [8](#0-7)

```rust
  As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from
  the nonces being context-bound under a BFT protocol. The flow is as follows:

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  Additionally, to ensure a rebuilt service isn't flagged as malicious, we have to check the
  commitments generated from the decided nonces are in fact its commitments on-chain (TODO).
```

```rust
  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
```
