### Title
SchnorrAggregate::verify accepts an attacker-crafted "aggregate" signature over zero signers (s = 0, Rs = []) - (File: crypto/schnorr/src/aggregate.rs)

### Summary

`SchnorrAggregate::verify` computes `sum_i z_i*R_i + sum_i z_i*c_i*A_i - s*G == 0` via `multiexp_vartime`. When the aggregate contains zero nonces (`Rs.len() == 0`) and `keys_and_challenges` is empty, the only remaining statement is `(-s, G)`. With `s = 0`, the multiexp returns the identity point and `verify` returns `true`. `SchnorrAggregate::read` imposes no minimum length, so the 4-byte encoding `00000000 || repr(0)` deserializes cleanly and verifies as a valid aggregate signature for the empty signer set — a signature no private key holder ever produced. The producer side cannot generate this value honestly: `SchnorrAggregator::complete` returns `None` when nothing was aggregated (aggregate.rs:175-178), so the encoding is only reachable through attacker-supplied bytes, mirroring the Janssen bug where an unsigned JWE request object was accepted once the signed payload was absent.

### Finding Description

- `crypto/schnorr/src/aggregate.rs` `SchnorrAggregate::read` (lines 77-88) reads a `u32` count and that many nonces, then `s`. `count = 0` is accepted.
- `SchnorrAggregate::verify` (lines 127-146) only checks `Rs.len() == keys_and_challenges.len()`, builds `pairs` of length `2n + 1`, and calls `multiexp_vartime`.
- `crypto/multiexp/src/lib.rs` `algorithm(1)` selects `Algorithm::Single`, evaluating `pairs[0].1 * pairs[0].0` = `G * (-0)` = identity, so `verify` returns `true`.
- The reachable in-scope consumer is `Validators::verify_aggregate` in `coordinator/tributary/src/tendermint/mod.rs` (lines 201-229): it reads the aggregate, requires `signers.len() == aggregate.Rs().len()` (satisfied by `0 == 0`), iterates zero signers, and calls `aggregate.verify(DST, &[])`, which returns `true` for the crafted bytes. No check that `signers` is non-empty or carries quorum weight exists inside `verify_aggregate`/`SchnorrAggregate::verify` itself.

### Impact Explanation

The primitive's contract — "verify an aggregate signature for the list of signers" — is violated: an unprivileged party produces a byte string (`[0,0,0,0]` followed by 32 zero bytes) that is accepted as a valid aggregate signature without knowledge of any private key. Any downstream logic that treats `verify_aggregate`/`SchnorrAggregate::verify == true` as proof of authorization (e.g., a Tendermint commit or any batch-verification caller) and does not independently require the signer list to be non-empty and carry sufficient weight accepts a forged "signature". This is the same failure shape as CVE-2026-45795: the absence of a signed payload causes the verifier to accept an unsigned object.

### Likelihood Explanation

The attack requires no cryptographic work — four zero bytes plus a zero scalar. It is exploitable wherever a caller passes an empty (or attacker-controlled) `signers`/`keys_and_challenges` list into the verifier and relies on its boolean result for authorization. In the Tendermint consumer, acceptance additionally depends on whether commit processing independently enforces a quorum-weighted signer set before or after `verify_aggregate`; that weight check lives outside the in-scope crypto code, so within the audited surface the primitive unconditionally returns `true` for the forgery. Severity is bounded by the vacuous-signer-set nature of the forgery, hence Medium rather than High.

### Recommendation

Reject empty aggregates in both `SchnorrAggregate::read`/`verify` and `SchnorrAggregate::verify` (return `Err`/`false` when `Rs.is_empty()`), and in `Validators::verify_aggregate` reject `signers.is_empty()` before verification. Alternatively, require `s != 0` is insufficient — the emptiness check is the correct invariant, matching `SchnorrAggregator::complete`'s refusal to produce empty aggregates.

### Proof of Concept

```rust
// crypto/schnorr, with feature = "aggregate"
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ristretto;
use schnorr::aggregate::SchnorrAggregate;

// Attacker-crafted aggregate: zero nonces, s = 0
let mut bytes = vec![0u8; 4];            // len = 0
bytes.extend([0u8; 32]);                 // s = 0 (canonical scalar zero)
let agg = SchnorrAggregate::<Ristretto>::read(&mut bytes.as_slice()).unwrap();

// Verifies as valid for the empty signer set, under any DST
assert!(agg.verify(b"any domain separator", &[]));
```

`verify` reaches `multiexp_vartime(&[(-0, G)])`, which via `Algorithm::Single` yields the identity point, and `is_identity()` makes `verify` return `true`. The corresponding on-path consumer `Validators::verify_aggregate` in `coordinator/tributary/src/tendermint/mod.rs` returns `true` when called with `signers = &[]` and these bytes, since `signers.len() == aggregate.Rs().len()` holds trivially and the per-signer loop is empty.
