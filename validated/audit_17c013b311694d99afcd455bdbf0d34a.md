I need to look at the FROST signing path, where participant-supplied preprocesses/commitments are keyed by index — the closest analog to an unvalidated cross-scope reference.### Title
PedPoP `EncryptionKeyMessage.enc_key` is unauthenticated: swapping a victim's registered encryption key redirects their secret shares to an attacker-controlled ECDH key - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The bug class is an unvalidated cross-scope reference: a message carries a field pointing at a resource that is used under the victim's name without being bound to the victim's authenticated data. In PedPoP, each participant broadcasts `EncryptionKeyMessage { msg: Commitments, enc_key }`. The only proof of possession signs `cached_msg` (the serialized commitments) via `challenge(context, l, nonce, cached_msg)` in `verify_r1` (`crypto/dkg/pedpop/src/lib.rs:323-329`), while `enc_key` — the ECDH key under which *all* of that participant's secret shares will be encrypted — is outside the signed/transcripted material entirely. `Decryption::register` inserts `msg.enc_key` verbatim with no proof of possession (`crypto/dkg/pedpop/src/encryption.rs:351-361`).

### Finding Description
`EncryptionKeyMessage::read` accepts untrusted bytes (`msg` then `enc_key`, `encryption.rs:57-59`). In `SecretShareMachine::verify_r1`, the Schnorr PoK is verified over `msg.cached_msg`, which `generate_coefficients` builds solely from the commitment points (`lib.rs:163-184`); `enc_key` is appended by `Encryption::registration` *outside* the signed `Commitments` (`lib.rs:190-191`, `encryption.rs:448-449`). Consequently a party who relays, re-encodes, or republishes a victim's round-1 message can substitute `enc_key` with a point `k*G` whose discrete log they know, while the PoK still verifies. Every other participant then calls `Encryption::encrypt(rng, l, share)`, which resolves `self.decryption.enc_keys[&participant]` — the attacker-controlled key — as the ECDH recipient (`encryption.rs:460-467`), and produces `cipher(context, ecdh(key, enc_key))` (`encryption.rs:153-154`). The victim's actual key is never used.

### Impact Explanation
All `t-... n-1` secret shares intended for participant `l` are encrypted to the attacker's ECDH key. Since PedPoP share messages are transported as data other parties can observe (and `EncryptedMessage::read` is a listed untrusted input), the attacker runs `cipher(context, ecdh(their_k, msg.key))` and recovers the victim's complete secret share `s_l`. The attacker now controls two share indexes (`s_l` and their own `s_i`); for `t = 2` this alone interpolates to the full group private key, and for general `t` it reduces the effective collusion threshold by one per hijacked participant. This is key share recovery reachable purely with untrusted message bytes — the direct analog of a function executing inside another tenant's environment because the environment reference was never checked.

### Likelihood Explanation
Any party able to present a modified round-1 message under the victim's index (relay, coordinator, or any transport where the whole `EncryptionKeyMessage` is not additionally authenticated — which the library explicitly does not require, since it relies on the PoK for authenticity) can perform the swap. The swap is undetectable: the PoK verifies, commitments are valid, and decryption failures at `calculate_share` are indistinguishable from a faulty sender — and even trigger the blame path rather than revealing the substitution.

### Recommendation
Bind `enc_key` into the authenticated transcript: extend `Commitments`/the PoK `challenge` input in `generate_coefficients`/`verify_r1` to include `enc_key.to_bytes()`, or add a Schnorr proof-of-possession for `enc_key` verified in `Decryption::register`/`Encryption::register`, mirroring the per-message `pop` already required on `EncryptedMessage` (`encryption.rs:80-93`).

### Proof of Concept
1. Victim `l` produces `(SecretShareMachine, EncryptionKeyMessage { Commitments{commitments, cached_msg, sig}, enc_key = e*G })`.
2. Attacker reads it via `EncryptionKeyMessage::read`, replaces `enc_key` with `a*G` (known `a`), re-serializes, and delivers it as `l`'s message. `sig` still verifies because `cached_msg` does not cover `enc_key` (`lib.rs:183`, `encryption.rs:57-64`).
3. All participants `register(l, msg)` storing `a*G`, then `encrypt` each `share_l` with `ecdh(r_j, a*G)` (`encryption.rs:466`, `lib.rs:369`).
4. Observing any published `EncryptedMessage{key: r_j*G, msg}` addressed to `l`, the attacker computes `ecdh(a, r_j*G)`, derives `cipher(context, ...)` (`encryption.rs:101-133`), and XOR-decrypts `SecretShare` → obtains `s_l`. With `t=2`, interpolate `(l, s_l)` and `(i_attacker, s_i)` to recover the group secret key.
