## Title
Order-of-operations rounding error in `compute_royalty_amount` truncates NFT royalty payments - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`compute_royalty_amount` in `chia/wallet/nft_wallet/nft_wallet.py` divides by `royalty_split` *before* multiplying by the royalty `percentage`, instead of multiplying first and dividing last. This is the same rounding-error bug class as the referenced USSD `calculateMint` report: performing integer division before multiplication causes unnecessary truncation, so the on-chain royalty payment created during an NFT offer settlement can be smaller than the mathematically correct amount — in some cases truncated all the way to zero when it should be nonzero. [1](#0-0) 

### Finding Description
```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(...)
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
``` [1](#0-0) 

The expression `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS` performs the integer division by `royalty_split` first (an early, avoidable truncation), then multiplies by `percentage`, then divides by `10000`. Mathematically the correct floor computation is `abs(offered_amount) * percentage // royalty_split // MAX_ROYALTY_BASIS_POINTS` (multiply first, then divide), which always yields a result greater than or equal to the current implementation for the same inputs (dividing early can only lose precision, never gain it).

`compute_royalty_amount` is called directly inside `NFTWallet.make_nft1_offer` — the function that constructs the actual on-chain `CreateCoin` payment to the NFT royalty address as part of settling an offer/trade:
```python
extra_royalty_amount = compute_royalty_amount(amount, request_side_royalty_split, percentage)
payment_list.append((launcher_id, CreateCoin(address, extra_royalty_amount, [address])))
``` [2](#0-1) 

`make_nft1_offer` is reachable by any wallet user creating or taking an NFT offer (any offer counterparty), i.e. unprivileged local RPC/wallet action — this is exactly the "offers and trades" and "NFT/DID ownership" attack surface listed as in scope.

### Impact Explanation
Because the division by `royalty_split` happens before the multiplication by `percentage`, the computed royalty amount is systematically rounded down more aggressively than necessary. In the worst case (e.g. small `offered_amount`, `royalty_split > 1`, and a `percentage` that is not a large fraction of 10000), the truncation can zero out a royalty payment that should have been nonzero, directly reducing the funds paid to the NFT royalty recipient. This is a loss-of-funds bug for royalty-holders/NFT creators participating in offers with multiple royalty-bearing NFTs (`royalty_split > 1`), reachable by any user who creates or takes such an offer — no privileged access required.

### Likelihood Explanation
This triggers deterministically whenever an offer involves `royalty_split > 1` (i.e., multiple royalty-enabled NFTs on one side of a trade) with a fungible payment amount and percentage combination where premature division changes the floor result. This is a normal, unprivileged usage path (any wallet user creating a complex NFT offer via `make_nft1_offer`), so likelihood of occurrence is directly tied to normal usage of multi-NFT offers, not to any adversarial or privileged condition.

### Recommendation
Reorder the arithmetic to multiply before dividing, matching the fix pattern recommended in the referenced report:
```python
amount = abs(offered_amount) * percentage // royalty_split // MAX_ROYALTY_BASIS_POINTS
```
This preserves precision by deferring both divisions until after the multiplication, minimizing truncation loss while keeping the same overflow/validation checks.

### Proof of Concept
Using `compute_royalty_amount` as implemented:
```python
# offered_amount = -5 mojos, royalty_split = 3 (three royalty NFTs sharing the offer),
# percentage = 6000 basis points (60%)
compute_royalty_amount(offered_amount=-5, royalty_split=3, percentage=6000)
# Current code: abs(-5)//3 = 1 ; 1*6000 = 6000 ; 6000//10000 = 0  -> royalty paid = 0

# Correct order (multiply-then-divide):
# abs(-5)*6000 = 30000 ; 30000//3 = 10000 ; 10000//10000 = 1 -> royalty should be 1
```
The existing test file `chia/_tests/wallet/nft_wallet/test_nft_royalty.py` exercises `compute_royalty_amount` (e.g. `test_royalty_split_across_multiple_nfts`, `test_small_amount_truncates_to_zero`) confirming the current divide-then-multiply behavior, which can be shown to under-pay relative to a multiply-then-divide computation for the same inputs.
