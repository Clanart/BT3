### Title
Submodule `protocol.file.allow=always` override lets a malicious repo's `.gitmodules` read/exfiltrate arbitrary local files during checkout/pull - (File: app/src/lib/git/submodule.ts)

### Summary
Git disabled the `file://` transport for submodules by default (git ≥2.38, following the 2022 `.gitmodules` arbitrary-file-read fixes) precisely because a hostile repository can declare a submodule whose URL points at an attacker-chosen local path (`file:///…` or a relative path that walks out of the repo with `../../..`). GitHub Desktop's submodule-update helper explicitly reintroduces this dangerous surface via an `allowFileProtocol` flag that appends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation.

### Finding Description
`updateSubmodulesAfterOperation` builds its argument list as: [1](#0-0) 

When `allowFileProtocol` is `true`, Desktop unconditionally re-enables `protocol.file.allow=always` for the whole `git submodule update` invocation, not scoped to any particular submodule or origin check. The only thing the caller is expected to validate is *whether* to pass this flag at all — analogous to the ENS bug's "only the nodehash is checked, the rest of the call is trusted" pattern: once the flag is set, git will honor *any* `file://` (or bare local path) URL declared in the untrusted repository's `.gitmodules`, with no further validation of where that path points.

A cloned or fetched repository is fully attacker-controlled content (this is exactly the "attacker controls a cloned/fetched repository" trust boundary called out in scope). An attacker can commit a `.gitmodules` entry such as:
```
[submodule "x"]
  path = pwned
  url = ../../../../../../etc
```
or an absolute `file:///Users/victim/.ssh` path. If Desktop performs a checkout/pull that reaches `updateSubmodulesAfterOperation` with `allowFileProtocol = true`, git will happily "clone" that local directory into the submodule path inside the working tree.

### Impact Explanation
If reachable with attacker control over the submodule URL, this results in local files being copied into the tracked working directory of a repo the victim did not intend to expose — e.g., SSH keys, config files, or other sensitive local paths. Because the copied content lands as ordinary tracked files, a subsequent `git add`/commit/push by the victim would silently exfiltrate those files to whatever remote the attacker/victim then pushes to, which matches the "silent corruption of what the user commits or pushes" / "file read outside the repo" impact categories in scope.

### Likelihood Explanation
I could not confirm, within the remaining tool budget, which call sites pass `allowFileProtocol: true` versus `false`, nor whether Desktop restricts this to first-party/local-clone scenarios (e.g., only when cloning a repo the user just created locally) versus arbitrary fetched/cloned third-party repositories. This is the critical open question: if `allowFileProtocol` is only ever `true` for trusted, locally-authored repositories, the finding is not exploitable by a remote attacker and should be downgraded or dismissed. Given the parameter name and doc comment ("Whether to allow file:// protocol for submodules") [2](#0-1) , the intent appears scoped, but I do not have direct evidence (from the checkout/pull/clone call sites) of the exact gating condition, so likelihood cannot be finalized with confidence.

### Recommendation
- Trace every caller of `updateSubmodulesAfterOperation` (checkout, pull, clone flows) and confirm `allowFileProtocol` is only ever `true` in contexts where the repository's submodule declarations are already trusted (i.e., never for repos obtained via clone-from-URL, fetch, or deep-link/PR checkout of attacker-supplied content).
- If `file://` submodule support is required, restrict it per-submodule (e.g., require the path to resolve within an allow-listed set of local repos) rather than globally toggling `protocol.file.allow=always` for the whole operation.
- Add a regression test asserting that a repository containing a `.gitmodules` entry with a `file://`/relative-traversal URL fails to initialize when reached through the untrusted clone/fetch/PR-checkout code paths.

### Proof of Concept
Not fully constructible without confirming the exact caller/flag wiring (see Likelihood Explanation). The conceptual PoC:
1. Attacker publishes/forks a public repo with `.gitmodules` containing a submodule whose `url` is `file:///absolute/path/to/target` or a `..`-traversal relative path.
2. Victim clones/fetches this repo in Desktop and performs an action that triggers `updateSubmodulesAfterOperation` with `allowFileProtocol: true`.
3. Git initializes the submodule from the local path, copying its contents into the working tree, where they become trackable/stageable by the victim.
