### Title
Single non-transferable escrowed token permanently locks all of an order's escrow in `_withdraw`/`withdraw` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2` orders can escrow multiple `TokenInfo` inputs (`order.inputs[]`), chosen by the user at order-creation time. When escrow is released — either to a solver on `RedeemEscrow` or to the user on `RefundEscrow`/cancellation — `_withdraw` (and the Tron `withdraw`) iterates over *every* token in the order and transfers each one in a single atomic loop. If any single token in that list reverts on transfer (paused/blacklistable/broken ERC-20, or an ERC-20 whose `transfer` starts reverting after the order was created), the entire withdrawal transaction reverts — including the transfers for all the *other*, perfectly good, escrowed tokens in the same order, and including the transaction-fee payout. This is the same broken invariant as the NFTX `distribute` bug: one bad element in a batch/loop unconditionally blocks the whole batch, but here the impact is permanent loss/lock of legitimately escrowed cross-chain funds rather than fee-distribution DoS.

### Finding Description
`_withdraw` in `IntentsBase.sol` loops over `body.tokens` (which mirrors `order.inputs`) and, for each token, either calls `IERC20(token).safeTransfer(beneficiary, amount)` or does a raw native-token `.call{value: amount}("")`, reverting (`InsufficientNativeToken()`) if it fails: [1](#0-0) 

The equivalent Tron/EVM-clone path does the same thing with a raw low-level `.call` and an explicit `revert TransferFailed()` on any single failed transfer: [2](#0-1) 

`onAccept` invokes this unconditionally for `RedeemEscrow`/`RefundEscrow` requests once the ISMP message is authenticated — there is no per-token isolation, `try/catch`, or "best effort" handling: [3](#0-2) 

Because the loop is atomic, a single misbehaving token among the order's `inputs[]` — e.g., a USDC-style token whose issuer later blacklists the beneficiary address, or a token that gets paused/rug-paused/deprecated between order placement and settlement, or one deliberately chosen by an adversarial order creator — causes the whole `_withdraw` call to revert every time it is attempted. Since the failing token is a permanent, unchangeable part of the order's `inputs[]` array, this DoS is not transient: it recurs on every retry, deterministically preventing:
- the solver from ever collecting the escrowed inputs it is owed after having already delivered outputs to the user, and
- the user from ever getting a refund on cancellation if the same faulty token is present.

This differs from the classic "malicious peer" pattern excluded by the impact gate: the attacker here is simply the order's own creator (an ordinary unprivileged user) choosing the set of input tokens, or an external token issuer's ordinary compliance action (blacklist/pause) — no relayer, prover, or admin collusion is required. The existing guards (`safeTransfer`, `TransferFailed()` revert) actively make the DoS worse by ensuring the entire batch fails atomically instead of degrading gracefully, mirroring exactly the pattern the NFTX report flagged: a single bad element in a distribution/settlement loop breaks the whole operation for every other party.

### Impact Explanation
This falls under "loss of funds" / "logic attack" on cross-chain escrow settlement, matching the pivot: "Bridged assets, order escrow, refunds... must move exactly once and only to the rightful beneficiary and amount." Here they move zero times, permanently: solver capital fronted on the destination chain is unrecoverable, and/or user-escrowed funds on the source chain become permanently frozen, with no admin recovery path shown in `onAccept`/`_withdraw` (no per-token retry, no partial release, no sweep-around for the affected commitment).

### Likelihood Explanation
Likely to be reachable by any unprivileged user: they can select arbitrary ERC-20 tokens as `order.inputs` when placing an order (no allowlist enforcement visible in the reviewed paths), and many real-world stablecoins/tokens support blacklisting or pausing that can be triggered independently of Hyperbridge. No relayer/prover/governance collusion is required — only ordinary token behavior or an order composed to include such a token.

### Recommendation
Make per-token transfer failures non-fatal to the rest of the batch: wrap each token transfer in a `try/catch` (or low-level call whose failure is recorded rather than reverting the whole function), track undelivered amounts per `(commitment, token)`, and expose a separate recovery/retry entrypoint for the stuck token so the other tokens in the same order still settle. Alternatively, disallow multi-token orders from being blocked atomically by validating transferability of each input token at order placement, and/or add a governance/beneficiary-triggered "skip and sweep" path for a specifically failing token similar to the `SweepDust` flow.

### Proof of Concept
1. User creates a cross-chain order via `_fillCrossChain`/order placement with `order.inputs = [GoodToken, BadToken]`, where `BadToken` is a standard ERC-20 that later blacklists the intended beneficiary (or is paused).
2. Solver fills the order on the destination chain, delivering outputs to the user; a `RedeemEscrow` `PostRequest` is dispatched back to the source chain.
3. Hyperbridge delivers the request; `onAccept` calls `_withdraw(body, false, true)` [4](#0-3) .
4. Inside `_withdraw`'s loop, the transfer of `GoodToken` succeeds, but `IERC20(BadToken).safeTransfer(beneficiary, amount)` reverts because `beneficiary` is blacklisted [5](#0-4) .
5. The entire `onAccept` transaction reverts. The solver never receives `GoodToken` (which had no issue) nor `BadToken`. Every retry of message delivery reproduces the same revert indefinitely, since `beneficiary`/token state does not change — permanently locking both escrowed tokens for that commitment.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
