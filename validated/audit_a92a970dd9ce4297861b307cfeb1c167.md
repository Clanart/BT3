## Title
Arbitrary file read via symlink-following in `getWorkingDirectoryImage` (no path-containment check) - (`app/src/lib/git/diff.ts`)

## Summary
`getWorkingDirectoryImage` builds the path to a working-tree image file solely with `Path.join(repository.path, file.path)` and passes it straight to `readFile`. Unlike other parts of the codebase that read repository-relative files, it does not use the project's own containment helper, `resolveWithin` (`app/src/lib/path.ts`), which explicitly detects and blocks symlink-based root escapes. A cloned/fetched repository containing a symlink whose target resolves outside `repository.path` will therefore have its target file read, base64-encoded, and rendered by `NewImageDiff`/`ModifiedImageDiff`.

## Finding Description
`getWorkingDirectoryImage` is the sink for the "current" image when diffing a working-directory file whose status is not `Deleted`: [1](#0-0) 

Node's `fs.promises.readFile` follows symlinks by default, and there is no `lstat`/`realpath`/containment check before the call. Contrast this with the codebase's own symlink-escape guard, `resolveWithin`, which explicitly walks `realpath()` on both the root and the resolved path to detect symlink traversal outside the root: [2](#0-1) 

That helper is already used elsewhere for exactly this class of risk, e.g. in the Copilot conflict-context builder (`buildConflictContext`, which explicitly comments "Guard against path traversal and symlink escapes (cross-platform)") and in `dispatcher.ts`'s `openRepositoryFromUrl` for deep-link file paths: [3](#0-2) [4](#0-3) 

`getWorkingDirectoryImage`, however, has no such guard, so a symlinked path in the working tree (e.g. an untracked/new file whose git status is picked up by `AppFileStatusKind.New`) that points outside the repo will be dereferenced and its target bytes read, base64-encoded, and returned as an `Image`: [5](#0-4) 

The result is consumed by the UI's `renderImage`, which picks `NewImageDiff` for `AppFileStatusKind.New`/`Untracked` files, and `ImageContainer` turns the base64 payload into a `data:` URI `<img src>`: [6](#0-5) [7](#0-6) 

I did not find any evidence supporting the additional claim that this content is attached to error reports or Copilot context. `reportError`/`sendErrorWithContext` only transmit error name/message/stack and small UI-state metadata, not file/diff contents ( [8](#0-7) [9](#0-8) ), and the Copilot conflict-context path (`buildConflictContext`) uses `resolveWithin` and thus is not vulnerable to this specific symlink-escape technique.

## Impact Explanation
An attacker who controls a cloned/fetched repository (a valid, unprivileged attack surface per scope) can commit a symlink pointing to an arbitrary path on the victim's filesystem (e.g. `~/.ssh/id_rsa`, browser profile files, etc.). When the victim opens the repository in GitHub Desktop and that symlink appears as a new/untracked "image" candidate in the Changes view, `getWorkingDirectoryImage` will read and base64-encode the target file's bytes and hand them to the renderer, where they become visible (rendered as an `<img>` if a valid image, or at minimum present as a base64 string in the renderer's DOM/state, inspectable via devtools) — an out-of-repo file read triggered purely by opening/viewing a malicious repository, matching the "file write or read outside the repo" valid-impact category.

## Likelihood Explanation
Requires only that the victim clone/fetch a malicious repository (or add it as a remote and pull) and open it in GitHub Desktop's Changes/history view where the symlinked path is classified as an image-eligible file (`AppFileStatusKind.New`/`Untracked`/`Modified`, non-conflicted). No special user interaction beyond normal repository browsing (which the app does automatically when displaying diffs) is required, making this readily reachable.

## Recommendation
Route `getWorkingDirectoryImage` (and any similar working-tree file readers that build paths via `Path.join(repository.path, file.path)`) through the existing `resolveWithin` helper before calling `readFile`, mirroring the protection already applied in `buildConflictContext` and `openRepositoryFromUrl`. If `resolveWithin` returns `null`, the file should be treated as unreadable/unrenderable rather than attempting the read.

## Proof of Concept
1. Create a fixture repository. On POSIX, add a symlink e.g. `evil.png -> /etc/passwd` (or any absolute/relative path resolving outside the repo root) and commit or leave it as untracked.
2. Open the repository in GitHub Desktop / call `getWorkingDirectoryImage(repository, file)` directly (as in the existing test suite pattern at `app/test/unit/git/diff-test.ts:50-69`) with `file.path = 'evil.png'`.
3. Observe that `current.contents` (base64) decodes to the contents of `/etc/passwd` rather than failing or being blocked, confirming the symlink is followed without containment enforcement.

```typescript
export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}
```

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
