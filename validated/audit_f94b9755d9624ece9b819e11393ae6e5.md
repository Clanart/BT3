### Title
Attacker-controlled input script hijacks the `data`/InInstruction and `presumed_origin` of another party's deposit in the same transaction - (File: `processor/src/networks/bitcoin.rs`)

### Summary
In `Bitcoin::get_outputs`, when a transaction contains *any* output paying a registered Serai key, the processor extracts the `InInstruction` payload from the transaction's inputs via `extract_serai_data(tx)` and derives `presumed_origin` from `tx.input[0]` — then stamps those values onto **every** `External` output of that transaction. There is no binding between the input carrying the instruction and the output it is meant to annotate. An unprivileged attacker who co-authors a transaction (e.g., a coinjoin round) in which a victim pays Serai's external address can embed their own InInstruction in their input, causing the victim's deposit to be credited/executed per the attacker's instruction.

### Finding Description
`get_outputs` scans every non-coinbase transaction with the key's `Scanner` (which matches only `script_pubkey`). Once `outputs` is non-empty, it computes `presumed_origin` solely from `tx.input[0]`'s previous output and calls `Self::extract_serai_data(tx)` to pull a Serai `InInstruction` from the transaction's input scripts, then applies `data` to all `OutputType::External` outputs and `presumed_origin` to all outputs [1](#0-0) . The scanner itself (`scan_transaction`) does not verify any input–output correspondence — it matches only the output script [2](#0-1) . The InInstruction embedding mechanism is input-based: a witness/script such as `OP_SHA256 <hash> OP_EQUALVERIFY ...` in a P2WSH input, proven by the protocol's own test [3](#0-2) . Nothing checks that the party authorizing the instruction is the same party funding the Serai output.

### Impact Explanation
The attached `data` is the `InInstruction` that tells Serai what to do with the deposited funds (e.g., `Shorthand::transfer` to a Serai address). By embedding `transfer(…, attacker_serai_address)` in an input the attacker controls, the victim's BTC output to the Serai deposit address is processed as though the attacker deposited it — the minted/routed value goes to the attacker. `presumed_origin` (used downstream in `processor/src/multisigs/mod.rs` for refunds/attribution) is equally spoofable via control of `tx.input[0]`, misdirecting any refund path. This mirrors CVE-2020-8903's shape: an attacker-supplied ancillary value is trusted by a privileged component to make an authorization/attribution decision, because the binding between the value's source and the resource it annotates is absent.

### Likelihood Explanation
Serai's external deposit address for an active multisig key is public and static. Collaborative-transaction protocols (coinjoin rounds, payjoin, batched exchange withdrawals, shared-funding transactions) routinely place outputs from multiple unaffiliated parties in one transaction. The attacker only needs to be a co-signer of a transaction in which some other participant's output pays Serai's external address — a condition the attacker can check for before signing and actively arrange (or opportunistically exploit). No validator, peer, or colluding-threshold assumption is required; the reachability is a standard on-chain transaction the attacker sends.

### Recommendation
Bind instructions to outputs rather than transactions: e.g., require the InInstruction-committing input to be funded/authorized by the same key paying the deposit, or switch to an output-bound scheme (instruction commitment in the deposit output's script/offset derivation, or an `OP_RETURN` keyed to the specific output index). At minimum, reject transactions where an `External` output has `data` unless the tx structure proves depositor–instructor correspondence (single depositor, or explicit per-output commitment), and do not derive `presumed_origin` from `tx.input[0]` for multi-party transactions — derive it per-depositor or leave it unset when ambiguous.

### Proof of Concept
1. Attacker learns Serai's external address `addr` (derived from the active group key via `external_address`/`p2tr_script_buf`).
2. Attacker participates in a collaborative transaction (e.g., a Wasabi/coinjoin round or a payjoin they initiate with a victim service) and confirms — before signing — that the transaction contains an output paying `addr` funded by a victim participant.
3. Attacker contributes an input embedding an InInstruction script in the established form: `OP_SHA256 <sha256(Shorthand::transfer(None, attacker_serai_addr).encode())> OP_EQUALVERIFY <attacker_spend_script>` (P2WSH), exactly as constructed in `tests/literal/mod.rs:94-102,142-162`.
4. When the block is processed, `get_outputs` runs `scan_transaction`, finds the victim's output (script matches `addr`), sets `kind = External`, sets `output.data` to the attacker's `transfer` instruction via `extract_serai_data(tx)`, and sets `presumed_origin` from `tx.input[0]` [4](#0-3) .
5. Serai's processor executes the attacker's `transfer` instruction against the victim's deposit value, crediting `attacker_serai_addr`. The victim's deposit is consumed but attributed to the attacker — funds are effectively stolen through transaction-level (not output-level) instruction binding.

  async fn get_outputs(&self, block: &Self::Block, key: ProjectivePoint) -> Vec<Output> {
    let (scanner, _, kinds) = scanner(key);

    let mut outputs = vec![];
    // Skip the coinbase transaction which is burdened by maturity
    for tx in &block.txdata[1 ..] {
      for output in scanner.scan_transaction(tx) {
        let offset_repr = output.offset().to_repr();
        let offset_repr_ref: &[u8] = offset_repr.as_ref();
        let kind = kinds[offset_repr_ref];

        let output = Output { kind, presumed_origin: None, output, data: vec![] };
        assert_eq!(output.tx_id(), tx.id());
        outputs.push(output);
      }

      if outputs.is_empty() {
        continue;
      }

      // populate the outputs with the origin and data
      let presumed_origin = {
        // This may identify the P2WSH output *embedding the InInstruction* as the origin, which
        // would be a bit trickier to spend that a traditional output...
        // There's no risk of the InInstruction going missing as it'd already be on-chain though
        // We *could* parse out the script *without the InInstruction prefix* and declare that the
        // origin
        // TODO
        let spent_output = {
          let input = &tx.input[0];
          let mut spent_tx = input.previous_output.txid.as_raw_hash().to_byte_array();
          spent_tx.reverse();
          let mut tx;
          while {
            tx = self.rpc.get_transaction(&spent_tx).await;
            tx.is_err()
          } {
            log::error!("couldn't get transaction from bitcoin node: {tx:?}");
            sleep(Duration::from_secs(5)).await;
          }
          tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
        };
        Address::new(spent_output.script_pubkey)
      };
      let data = Self::extract_serai_data(tx);
      for output in &mut outputs {
        if output.kind == OutputType::External {
          output.data.clone_from(&data);
        }
        output.presumed_origin.clone_from(&presumed_origin);
      }
    }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
