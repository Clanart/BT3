### Title
Governance-only IntentGatewayV2 requests (`UpgradeContract`, `SweepDust`, `UpdateParams`, `NewDeployment`) are authenticated only by source chain, not by sender module — ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`ExtrinsicIntents.onAccept` applies two different authentication strengths to the two classes of incoming ISMP requests it handles. `RedeemEscrow`/`RefundEscrow` are authenticated with `_authenticate()`, which checks both the source chain *and* that `request.from` matches the specific registered `IntentGatewayV2` instance for that chain. The governance branch (`NewDeployment`, `UpdateParams`, `SweepDust`, `UpgradeContract`) checks only that `request.source` equals the Hyperbridge nexus state machine — it never inspects `request.from` to confirm the request was dispatched by the specific authorized governance module. This is the same class of bug as the sdeUSD report: a privileged action is gated by a coarser check (chain-level) than the one used elsewhere in the same function (module-level), letting any entity able to dispatch a POST from the Hyperbridge chain masquerade as governance.

### Finding Description
`_authenticate` performs strict per-module authentication: [1](#0-0) 

But the governance dispatch path in `onAccept` only checks the chain id of the source, never `request.from`: [2](#0-1) 

`RequestKind.UpgradeContract` calls `ERC1967Utils.upgradeToAndCall(newImpl, initData)` directly — full contract takeover — and `RequestKind.SweepDust` transfers accumulated protocol dust to an attacker-controlled beneficiary, and `UpdateParams`/`NewDeployment` rewrite gateway configuration and registered destination instances. All four of these are reachable by *any* module on the Hyperbridge/nexus chain that can dispatch an ISMP `PostRequest` whose `to` targets this gateway's address, as long as `request.source` correctly resolves to the Hyperbridge state machine — there is no check that `request.from` equals a specific, restricted admin/governance module id.

Per `docs/outbound-request-incentivization.md`, several independent pallets on the Hyperbridge/nexus chain already originate ISMP requests through the generic `IsmpDispatcher::dispatch_request` (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path), each setting their own `from` to their own module id. `onAccept`'s governance branch does not distinguish between these — it will accept a `NewDeployment`/`UpdateParams`/`SweepDust`/`UpgradeContract` body from *any* of them (or any future dispatcher added to the runtime), not just the one pallet meant to administer `IntentGatewayV2`.

This exactly mirrors the sdeUSD finding's root cause: the code checks a coarser predicate (chain identity / "soft restriction" equivalent) in place of the specific predicate (module identity / "full restriction" equivalent) that is enforced elsewhere in the same contract for a structurally similar operation (`_authenticate`).

### Impact Explanation
If any non-privileged or unrelated Hyperbridge-native pallet/dispatcher can produce a `PostRequest` with `source == hyperbridge()` and an arbitrary body/`from`, an attacker or a compromised/buggy adjacent pallet could:
- Upgrade the `IntentGatewayV2` proxy to an attacker-controlled implementation (`UpgradeContract`), leading to complete loss of all escrowed user funds.
- Sweep protocol dust to an arbitrary beneficiary (`SweepDust`).
- Rewrite fee parameters, solver-selection flags, or destination-fee tables (`UpdateParams`), enabling economic manipulation of future fills.
- Register a forged gateway instance for a state machine (`NewDeployment`), which would then be trusted for authenticating future `RedeemEscrow`/`RefundEscrow` messages from that chain — opening a path to double-settlement of escrow.

This meets the bounty's "unauthorized transaction or execution" / "false state acceptance" / "loss of funds" categories, without requiring a malicious relayer, prover, or governance key — only requiring that some non-admin dispatcher on the source chain can originate a message routed to this contract's address.

### Likelihood Explanation
Likelihood depends on runtime composition: exploitability requires that some pallet/actor other than the intended intents-governance module can cause a `PostRequest` with attacker-influenced `to`/`body` to be dispatched from the Hyperbridge chain. Given the documented pattern that dispatch is available to multiple system pallets (and potentially any future pallet added to the runtime) via the shared `IsmpDispatcher` interface, the check being purely chain-scoped rather than module-scoped is an architectural gap regardless of whether a concrete misuse path exists today — it is inconsistent with the far stricter authentication (`_authenticate`) used for economically-sensitive escrow release just a few lines above in the same function, which is itself evidence the module-level check was intended but omitted for the admin branch.

### Recommendation
Require `onAccept`'s governance branch to also verify `request.from` against a specifically configured/allow-listed admin module id (analogous to `_instances[...]` used by `_authenticate`), rather than accepting any request whose `source` merely resolves to the Hyperbridge state machine. This closes the gap between the "soft" (chain-level) and "full" (module-level) authentication paths in the same handler.

### Proof of Concept
Conceptual PoC (cannot be executed without a live nexus/EVM environment, but the code path is directly inspectable):
1. Any pallet `P` on the Hyperbridge nexus chain other than the intended `IntentGatewayV2` admin module calls `IsmpDispatcher::dispatch_request` with:
   - `dest` = the EVM chain hosting the target `IntentGatewayV2`
   - `to` = the target `IntentGatewayV2` contract address
   - `body` = `bytes1(uint8(RequestKind.UpgradeContract)) || abi.encode(maliciousImpl, initData)`
2. The relayer delivers this request; `IntentGatewayV2.onAccept` is invoked with `incoming.request.source == host_state_machine()` (true, since `P` is a pallet on the Hyperbridge chain) and `kind == RequestKind.UpgradeContract`.
3. `onAccept` at [3](#0-2)  passes because it only checks `request.source`, never `request.from`.
4. `ERC1967Utils.upgradeToAndCall(maliciousImpl, initData)` executes, replacing the gateway's logic contract and giving the attacker (via `P`) full control of all escrowed funds.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.UpgradeContract) {
            (address newImpl, bytes memory initData) = abi.decode(incoming.request.body[1:], (address, bytes));
            ERC1967Utils.upgradeToAndCall(newImpl, initData);
        }
    }
