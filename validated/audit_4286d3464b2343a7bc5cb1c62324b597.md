### Title
`ReceivedOutput::read` doesn't verify the scalar offset actually derives the output's `script_pubkey` — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to `migrate()` failing to check the new strategy's base token, `ReceivedOutput::read` deserializes the three components of a spendable output — the scalar `offset`, the `TxOut` (containing the `script_pubkey`), and the `OutPoint` — without verifying they are mutually consistent. A `ReceivedOutput` whose `offset` does not satisfy `p2tr_script_buf(key + G*offset) == output.script_pubkey` is accepted and treated as a spendable received output, even though no key derived via that offset can ever spend it.

### Finding Description
`Scanner::scan_transaction` produces `ReceivedOutput`s where `offset` is guaranteed correct because it is looked up from `self.scripts`, a map keyed by `script_pubkey` built by `register_offset` (networks/bitcoin/src/wallet/mod.rs:199-214). However, `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) reconstructs the struct directly from raw bytes:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...
outpoint = OutPoint::consensus_decode(&mut buf_r)...
Ok(ReceivedOutput { offset, output, outpoint })
```

There is no check that `offset` corresponds to `output.script_pubkey`. Any consumer reading `ReceivedOutput`s from serialized data (the structure is passed between the scanner/processor components in serialized form) will trust an attacker-controlled offset. When such an output is later spent, `SignableTransaction::multisig` does perform a consistency check (`p2tr_script_buf(offset.group_key()) != self.prevouts[i].script_pubkey` → `None`, send.rs:273-281), but that check rejects the *entire* transaction construction rather than the bad output — so the malformed input silently poisons the spend path.

The parallel to the original bug is exact: in prePO, the controller receives tokens under a base token it doesn't track, so the funds are present but unspendable/lost; here, the wallet records an output under an offset that doesn't derive its locking script, so the funds are reported received but are not spendable.

### Impact Explanation
An unprivileged party able to feed crafted bytes into `ReceivedOutput::read` can cause the system to register an output as spendable when the stored `offset` yields a group key whose P2TR script does not equal `output.script_pubkey`. Consequences:

- Funds counted toward spendable balance that can never be signed for: `SignableTransaction::multisig` returns `None` ("wrong keys") when it reaches the mismatched input (send.rs:277-279), causing transaction construction to fail or, if the bad output is bundled with real inputs, blocking a legitimate spend.
- A `ReceivedOutput` can also carry a `script_pubkey` for a *different* offset/key than registered (e.g., an output actually locked to an unrelated key), inflating perceived received funds that are provably unspendable.

This matches the "funds reported received that are not spendable" acceptance criterion.

### Likelihood Explanation
`ReceivedOutput::read` consumes length-delimited untrusted bytes: a `Secp256k1` scalar, a consensus-encoded `TxOut`, and an `OutPoint`. Any deserialization boundary where these bytes originate outside the local `Scanner` (IPC between coordinator/processor components, DB re-reads, or peer-supplied data) is an injection point. No secret is required to craft the input — the fields are all public-shaped data — so the attack needs only control of the byte stream, not key material or validator collusion. Exploitation requires an inconsistent `(offset, script_pubkey)` pair, which the attacker constructs trivially by pairing a valid script with an arbitrary scalar.

### Recommendation
Bind the offset to the output at deserialization or first use. Since `ReceivedOutput::read` doesn't know the base `key`, the cleanest analog of `require(_baseToken == _newStrategy.getBaseToken())` is to have the caller verify consistency immediately after reading: `p2tr_script_buf(key + (GENERATOR * offset)) == Some(output.script_pubkey.clone())`, mirroring the check already present in `SignableTransaction::multisig` but failing early per-output so a malformed input cannot poison the spend of unrelated valid inputs. Alternatively, re-serialize the `script_pubkey` as the authority: derive the offset lookup from the registered `scripts` map (keyed by script) rather than trusting a serialized scalar, making `offset` a pure function of `script_pubkey` as it is in `scan_transaction`.

### Proof of Concept
1. A legitimate deposit produces an output with `script_pubkey = p2tr_script_buf(key + G*o)` for some registered offset `o` (mod.rs:180-196, 205-211).
2. An attacker supplies bytes to `ReceivedOutput::read`: `offset = o' ≠ o` (or any scalar), `output` = the real `TxOut`, `outpoint` = the real outpoint (mod.rs:122-134). The read succeeds — no consistency check exists.
3. The wallet registers the output's value as spendable funds.
4. Later, `SignableTransaction::new` collects `offsets` from the inputs (send.rs:176) and `multisig` computes `p2tr_script_buf(keys.offset(o').group_key())`, which does not equal `prevouts[i].script_pubkey`, returning `None` (send.rs:276-279). The "received" funds cannot be spent — the wallet believes it controls tokens it effectively does not, identical in effect to the controller holding tokens of the wrong base token.
