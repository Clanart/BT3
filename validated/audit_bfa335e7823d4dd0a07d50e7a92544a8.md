### Title
`ReceivedOutput::read` deserializes an arbitrary `script_pubkey`/offset pair without verifying the output is actually spendable by the scanner's key hierarchy - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` reconstructs a "spendable output" purely from attacker-supplied bytes: an arbitrary `Scalar` offset, an arbitrary `TxOut` (including its `script_pubkey`), and an arbitrary `OutPoint` (networks/bitcoin/src/wallet/mod.rs:122-134). No check ties the declared `script_pubkey` to the multisig key plus the declared offset — the analog of the missing `isTokenAllowed` check: an item read from untrusted input is accepted into the set of assets the system believes it controls, even though it was never produced by `Scanner::scan_transaction` (which is the only code path that legitimately binds `script_pubkey` → `offset`, networks/bitcoin/src/wallet/mod.rs:199-214).

### Finding Description
In Sentiment, controller functions returned tokens that were added to an account's asset list without an allowlist check. Here, `Scanner` maintains a `scripts: HashMap<ScriptBuf, Scalar>` allowlist and `scan_transaction` only emits a `ReceivedOutput` when `output.script_pubkey` is in that map — i.e., only when the output provably pays to `key + offset·G` with a registered, parity-corrected offset. `ReceivedOutput::read` bypasses that allowlist entirely: the caller deserializes `offset`, `output`, and `outpoint` verbatim with no reference to the `Scanner`'s script set and no re-derivation that `p2tr_script_buf(key + offset·G) == output.script_pubkey`.

A malicious `ReceivedOutput` therefore claims:
- any `value` (inflating reported balances / `value()`),
- any `script_pubkey` — e.g. an output paying to the *attacker's* own key, or to a P2TR script whose internal key is unrelated to the multisig,
- any `offset`, causing downstream `keys.clone().offset(offset)` to derive the wrong signing key.

Notably, nothing downstream fully recovers the check. `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256) copies `input.offset` and `input.output` into `offsets`/`prevouts` without validating that the prevout's `script_pubkey` corresponds to the multisig key under that offset. The only binding check is in `SignableTransaction::multisig` (send.rs:273-285), which merely returns `None` — after the forged output has already been recorded as received funds and counted in `input_sat`.

### Impact Explanation
An unprivileged party who can feed crafted bytes to `ReceivedOutput::read` can cause funds to be reported as received that are not spendable by the protocol: the declared `script_pubkey` pays to a key the multisig does not control (or controls under a different offset than claimed), while `value()` reports the attacker's chosen amount. This directly mirrors the audit finding — an unvetted "asset" enters the books. Consequences: inflated accounted balance, and any spend attempt either aborts (`multisig` → `None`) or produces a transaction that cannot confirm, permanently stranding the plan's other co-spent inputs in scheduling logic and burning fee budget on retries.

### Likelihood Explanation
Reachable wherever serialized `ReceivedOutput`s cross a trust boundary (gossiped output claims, DB rows reconstructed from external input, `Output::read` in processor code which delegates to `ReceivedOutput::read`, processor/src/networks/bitcoin.rs:156). The forgery requires only choosing a scalar and a TxOut — no key knowledge needed. Impact is capped at false-balance/stall rather than direct theft, matching Medium.

### Recommendation
Bind deserialization to the scanner: either make `ReceivedOutput::read` a method on `Scanner` that rejects any `output.script_pubkey` not present in `self.scripts` (rejecting also if `self.scripts[script] != offset`), or verify inside `read` consumers that `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey`. At minimum, `SignableTransaction::new` should reject inputs whose `prevout.script_pubkey` is not P2TR for the expected key+offset, so the failure surfaces at input-acceptance time, not at `multisig`.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ReceivedOutput::read
let forged = {
  let mut buf = vec![];
  // arbitrary offset — never registered with the victim's Scanner
  buf.extend(Scalar::from(1337u64).to_bytes());
  // a TxOut paying to the ATTACKER's own P2TR key, claiming 21 BTC
  let attacker_script = p2tr_script_buf(attacker_even_key).unwrap();
  buf.extend(serialize(&TxOut {
    value: Amount::from_sat(2_100_000_000),
    script_pubkey: attacker_script,
  }));
  buf.extend(serialize(&OutPoint::new(real_txid, 0)));
  buf
};
let output = ReceivedOutput::read(&mut forged.as_slice()).unwrap();
// Accepted: reports 21 BTC "received"
assert_eq!(output.value(), 2_100_000_000);
// Scanner::scan_transaction would NEVER have emitted this: attacker_script
// is not in scanner.scripts. Yet downstream, SignableTransaction::new
// counts it in input_sat, and SignableTransaction::multisig returns None
// (or signs an unspendable input) — funds reported, not spendable.
```
