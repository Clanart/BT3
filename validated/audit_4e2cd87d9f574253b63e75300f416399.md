Unbounded raw balance-delta arithmetic in staking precompile `undelegate`/`redelegate` can panic on unexpected fee/side-effect deductions from the withdraw address — (File: `precompiles/staking/staking.go`)

### Summary
The Uniswap-hooks bug pattern — using a raw returned balance delta that can include an unaccounted-for component and flip sign, then feeding that signed delta into an operation that assumes a fixed sign — has a direct analog in Sei's staking precompile. `delegate`/`delegateFor` explicitly guard against a sign flip in the before/after balance delta (`rewardsAmount.IsNegative()` check with compensation), but the sibling functions `undelegate`, `undelegateFor`, `redelegate`, and `redelegateFor` compute the same kind of before/after balance delta using **unsigned `sdk.Coin.Sub`**, with no negative-value guard at all.

### Finding Description
In `precompiles/staking/staking.go`, `delegateFor` explicitly documents and handles the case where the raw balance delta around a staking operation can go negative (because the withdraw address == delegator and the delegated principal is also debited from the same balance during the same operation): [1](#0-0) 

By contrast, `undelegateFor` and `redelegateFor` (and the non-authorization entry points `undelegate`/`redelegate`) compute the analogous "rewards withdrawn" delta with plain `sdk.Coin` subtraction and no sign check: [2](#0-1) [3](#0-2) 

`sdk.Coin.Sub` panics if the result would be negative (Cosmos SDK's `Coin` type does not permit negative amounts). This is the exact same class of bug as the reported issue: the code assumes `withdrawAddressBalanceAfter >= withdrawAddressBalanceBefore` (i.e., that the only balance movement at the withdraw address between the "before" and "after" snapshots is a non-negative rewards credit), but nothing in `Undelegate`/`BeginRedelegate` guarantees this. If any other balance-decreasing effect touches the withdraw address in between the two `GetBalance` calls — e.g. the withdraw address coincides with an account that is simultaneously debited by another effect in the same message execution (analogous to the `delegate` case that required explicit compensation), or a future/alternate code path in the staking/distribution keepers moves funds out of the withdraw address as part of executing `Undelegate`/`BeginRedelegate` — the delta computed by `Sub` goes negative and the call panics instead of returning a clean error.

This mirrors the report precisely: a raw delta is used to infer a quantity ("rewards withdrawn") that is implicitly assumed non-negative, but the delta actually mixes multiple balance-affecting components whose net sign is not provable in all cases, and the code path that would need a sign check (as already implemented one function over, in `delegateFor`) is missing it.

### Impact Explanation
A panic inside a Cosmos precompile invoked from an EVM `CALL` is not necessarily contained: unlike `withdrawDelegationRewardsFor` in the distribution precompile, which wraps its logic in a `defer recover()`, `undelegateFor`/`redelegateFor` in the staking precompile (and their non-authorization counterparts `undelegate`/`redelegate`) have no such recovery. A panic that escapes precompile execution surfaces as an unhandled runtime panic during EVM transaction processing, which — depending on how deeply it propagates through the ABCI transaction-execution call stack — can degrade to a failed/reverted transaction in the best case or an unrecoverable node panic in the worst case, since Cosmos SDK message handling for panics inside precompiles run through the EVM's genuinely different execution path than ordinary message dispatch (which normally converts panics to errors via ante/msg-service recover wrappers, but that guarantee is not visible here for this code path). This is reachable by any EVM caller (including from a smart contract) that invokes `undelegate`/`redelegate`/`undelegateWithAuthorization`/`redelegateWithAuthorization` on the staking precompile at `0x0000000000000000000000000000000000001005`.

### Likelihood Explanation
Under the current, narrowly-tested execution paths (delegator's own withdraw address, no concurrent slashing/other debits within the same message), the delta is very likely always non-negative in practice, which is presumably why this has not yet been observed. However, this is precisely the same "usually true, but not provably true" assumption that caused the reported Uniswap-hooks bug, and the codebase's own comment on the sibling `delegate` function ("Use Int arithmetic ... which can make balanceAfter < balanceBefore. We compensate for that.") demonstrates that Sei's own developers recognize this balance-delta pattern is unsafe in the general case — they simply didn't apply the same defensive fix to `undelegate`/`redelegate`. This makes it a legitimate latent-defect analog rather than a purely theoretical one; the trigger condition depends on how withdraw-address balance side effects interact with `Undelegate`/`BeginRedelegate`, which is plausible for custom or delegated withdraw addresses (e.g., withdraw address set to a contract-controlled address that has other balance movements batched in the same block/tx, or future keeper changes that touch the withdraw address balance as part of unbonding).

### Recommendation
Apply the same defensive pattern already used in `delegateFor` to `undelegateFor`, `redelegateFor` (and the legacy/`v6xx` duplicates): compute the delta using `sdk.Int` arithmetic (which allows negative intermediate values) rather than `sdk.Coin.Sub`, and explicitly check for and reject (return a clean error rather than panic) an unexpected negative result. Additionally, wrap `undelegateFor`/`redelegateFor` (and `undelegate`/`redelegate`) in the same `defer recover()` pattern used by `withdrawDelegationRewardsFor` so that any unexpected panic degrades to a returned error instead of an unhandled panic during EVM transaction execution.

### Proof of Concept
A full PoC requires constructing a scenario where the delegator's distribution withdraw address balance decreases (rather than only increases) between the pre- and post- `GetBalance` snapshots surrounding the `Undelegate`/`BeginRedelegate` keeper call in `undelegateFor`/`redelegateFor`. This was not reproducible from static analysis alone within the scope of this review; verifying it requires exercising the staking/distribution keeper's `Undelegate`/`BeginRedelegate` code paths with a custom withdraw address (set via `setWithdrawAddress`) that has additional debits applied in the same context, which should be validated in a running devnet/integration test (e.g., extending `precompiles/staking/staking_events_test.go`'s pattern to set a withdraw address with a competing debit and observe whether `rewardsWithdrawn := withdrawAddressBalanceAfter.Sub(withdrawAddressBalanceBefore)` panics).
