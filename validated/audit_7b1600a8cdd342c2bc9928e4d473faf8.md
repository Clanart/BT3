## Title
Divide-by-zero panic in `consolidatedNode.Split` halts block finalization when a proposer has zero CN + CL stake - (File: `kaiax/staking/staking_info.go`)

### Summary
`TribalChief.updatePool` reverting at `totalAllocPoint == 0` is the report's bug class: an unguarded denominator that can legitimately become zero, breaking reward distribution. The Kaia analog is worse than a revert — it is an unguarded `big.Int` division in `consolidatedNode.Split` that can **panic** the Go process during consensus-critical block finalization, when a validator's combined CN-staking amount and consensus-liquidity (CL) staking amount are both zero.

### Finding Description
`consolidatedNode.Split` computes `totalAmount = cnAmountBig + clAmountBig` and then divides by it without checking for zero: [1](#0-0) 

`cn.StakingAmount` (CN stake) can legitimately be `0` while the node is still a qualified validator/proposer candidate — the valset test suite explicitly documents this: *"validators can be qualified with zero stakes, if all are understaked"*, and demonstrates a proposer list built entirely from validators with `amounts: []uint64{0,0,0,0}`: [2](#0-1) [3](#0-2) 

`CLStakingInfo.CLStakingAmount` is populated independently from the CLRegistry/CL pool balance and can also be `0` (e.g., a freshly registered CL pool with no deposits yet): [4](#0-3) 

These two independent zero-able quantities are combined into `consolidatedNode` during `consolidateNodes()`, with no validation that their sum is nonzero: [5](#0-4) 

Crucially, when the block proposer's `RewardAddr` maps to a `consolidatedNode` that has `CLStakingInfo != nil`, `specWithProposerAndFundsFlex` (and the analogous non-flex `specWithProposerAndFunds`) unconditionally calls `cn.Split(proposer)` — with no check that `cn.StakingAmount + cn.CLStakingInfo.CLStakingAmount > 0`: [6](#0-5) 

This is reached from `FinalizeState`, which runs on **every full node** for every block under deferred-fee/Kore+ configurations (Kaia Mainnet/Kairos use deferred fees): [7](#0-6) 

In Go, `big.Int.Div`/`.Quo` on a zero divisor panics (unlike Solidity's revert). A panic inside `FinalizeState` during block processing is not a contained, recoverable error like a Solidity `revert` — it crashes the node process that processes the block, i.e., every honest full node processing that block.

### Impact Explanation
This is strictly more severe than the reported TribalChief issue: instead of a single contract call reverting (temporarily blocking `updatePool`), a legitimate on-chain state (a proposer with zero combined CN+CL stake) causes an unrecoverable panic in the reward-distribution code path executed by every node finalizing that block. This halts the entire network's block processing (chain-wide denial of service / consensus halt) rather than merely reverting one transaction, and is reachable purely through normal validator/staking/CL-registration operations without any privileged access.

### Likelihood Explanation
Reaching the trigger condition requires: (1) a validator whose CN-staking amount is 0 (possible and explicitly supported — "all validators can be qualified with zero stake if all are understaked", or a validator that withdraws its CN stake to 0 after being registered), (2) that same validator having a `CLStakingInfo` entry with `CLStakingAmount == 0` (e.g., registered a CL pool via CLRegistry but no one has deposited into it yet), and (3) that validator being selected as block proposer. None of these require special privilege beyond normal staking/CL-pool registration and normal proposer rotation (including the "if no validator meets minimum staking, all council members are qualified" fallback), making this feasible under ordinary operational conditions, particularly on low-stake or newly-Prague-upgraded networks.

### Recommendation
Guard `consolidatedNode.Split` against a zero denominator (`totalAmount.Sign() == 0`), returning the whole amount to the CN (or 0/0) in that case, mirroring the recommended `totalAllocPoint > 0` guard from the source report. Additionally, add defensive checks anywhere `cn.Split` is invoked in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` and `assignStakingRewards`/`assignStakingRewardsFlex` in `kaiax/reward/impl/getter.go` so that a zero-stake CL-registered proposer cannot trigger a division by zero.

### Proof of Concept
1. Deploy/enable CLRegistry (Prague HF active) and register a CL pool for validator `V` with `CLStakingAmount = 0` (no deposits yet).
2. Ensure `V`'s CN-staking contract balance is 0 KAIA (e.g., withdraw all CN stake, or the validator never staked into CNStaking).
3. Since no validator meets `reward.minstake`, all council members (including `V`) become qualified per the WeightedRandom fallback rule; `V` is eventually selected as block proposer (or via RoundRobin/Sticky policy where all council members are always qualified).
4. When `V` proposes a block and `FinalizeState` is invoked, `getDeferredRewardFullFlex`/`getDeferredRewardFullKore` → `specWithProposerAndFundsFlex`/`specWithProposerAndFunds` finds `cn.RewardAddr == config.Rewardbase` with `cn.CLStakingInfo != nil`, and calls `cn.Split(proposer)`.
5. Inside `Split`, `totalAmount = 0 (StakingAmount) + 0 (CLStakingAmount) = 0`; `new(big.Int).Div(clAmount, totalAmount)` panics with "division by zero," crashing every node processing that block.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

func (r *RewardModule) FinalizeState(header *types.Header, state *state.StateDB, txs []*types.Transaction, receipts []*types.Receipt) error {
	if r.GovModule.GetParamSet(header.Number.Uint64()).ProposerPolicy == uint64(istanbul.WeightedRandom) && common.EmptyHash(header.Root) {
		qualified, err := r.ValsetModule.GetQualifiedValidators(header.Number.Uint64())
		if err != nil {
			return err
		}
		useRewardAddress := valset.NewAddressSet(qualified).Contains(r.NodeAddress)

		if rewardAddr := r.GetRewardAddress(header.Number.Uint64(), r.NodeAddress); useRewardAddress && rewardAddr != (common.Address{}) {
			header.Rewardbase = rewardAddr
			logger.Trace("Use reward address for nodeValidator", "header.Number", header.Number.Uint64(), "nodeAddress", r.NodeAddress, "rewardbase", header.Rewardbase)
		} else {
			logger.Trace("No reward address for nodeValidator. Use node's rewardbase.", "header.Number", header.Number.Uint64(), "nodeAddress", r.NodeAddress, "rewardbase", header.Rewardbase)
		}
	}

	spec, err := r.GetDeferredReward(header, txs, receipts)
	if err != nil {
		return err
	}
	if err := spec.Validate(); err != nil {
		return err
	}
	for addr, amount := range spec.Rewards {
		state.AddBalance(addr, amount)
	}
	return nil
}
