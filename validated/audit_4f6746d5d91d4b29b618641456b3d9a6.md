### Title
Discard Changes leaves working directory permanently corrupted when a mid-batch git operation fails after files have already been moved to Trash - (File: `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore.discardChanges` performs the "discard" flow in two separate phases: first it moves every selected file to the OS Trash (or deletes it, if the user opted out of Trash), and only afterwards does it run the git-level restore (`resetSubmodulePaths`/`resetPaths`/`checkoutIndex`) wrapped in a single `performFailableOperation` call. [1](#0-0) [2](#0-1)  If that batched git step throws for any reason, the files that were already removed from the working directory are never restored, leaving Desktop's view of the repository (and the actual working tree) permanently out of sync — mirroring the sentiment `AccountManager` bug where a single failing sub-step (one asset transfer / one file's git command) aborts the whole multi-item operation and leaves state stuck rather than rolling back or skipping just the failing item.

### Finding Description
`discardChanges` iterates over the user-selected `files` and, for each one, calls `this.shell.moveItemToTrash(...)` (or removes it directly) inside a per-file `try/catch`. [3](#0-2)  This is the destructive step: content is taken out of the working directory immediately, one file at a time, and any per-file trash failures are individually handled.

The restorative step, however, is not done per-file. All remaining paths are batched into a single call sequence — `resetSubmodulePaths`, `resetPaths`, `checkoutIndex` — executed inside one `performFailableOperation`: [2](#0-1) 

Because these three git invocations operate on the *entire* path list at once (not one file at a time with individual catch/skip logic), any single failure anywhere in that git sequence — a submodule path that git refuses to reset, a path containing characters or a state that trips `checkout-index -f -u -q --stdin -z`, an unexpected non-zero/non-1 exit code, or any other git error not already tolerated by `successExitCodes` — throws and aborts the whole batch. This is exactly the same broken invariant as the Sherlock report: a per-item loop where the destructive action (transfer / Trash-move) has already partially or fully completed, but the compensating/completing action (asset accounting / index-restore + checkout) is done as one atomic-looking batch that has no per-item error isolation.

Since the files were already trashed *before* the git step ran, a failure in the git step means:
- The files no longer exist in the working directory (already trashed/removed).
- Git's index/HEAD state was never reset for those paths, so Desktop's status computation and the user's mental model ("discard restores HEAD's copy") no longer match reality.
- There is no retry or rollback: the `catch` around `gitStore.discardChanges` in `AppStore._discardChanges` only logs and surfaces an error dialog, then still calls `_refreshRepository`; it does not restore trashed files or reconcile state. [4](#0-3) 

Note: I was not able to load the definition of `performFailableOperation` before running out of tool calls, so I cannot confirm every internal detail of its error-swallowing behavior (e.g., whether it silently no-ops on some Git errors). This is a gap in verification, but the sequencing bug — trash-then-batch-git-restore with no per-file compensation — is confirmed directly from the code shown above.

### Impact Explanation
A repository whose contents are attacker-influenced (a maliciously crafted cloned/fetched repo, e.g. one containing a submodule entry that is broken/malformed, or files whose paths interact badly with `checkout-index`/`reset` in a way that makes the batched git command fail) can cause a user's legitimate "Discard Changes" action to silently and permanently delete/trash local file content without restoring it from HEAD. This is a silent corruption of the user's working directory contract ("discard means go back to last commit"), potentially affecting many files in one action (batch discard, "Discard All Changes"). It does not require local/physical access, admin rights, or any credential — only that the user open/clone the crafted repository and click "Discard Changes."

### Likelihood Explanation
Moderate. The trigger requires the batched restore call (`resetSubmodulePaths`/`resetPaths`/`checkoutIndex`) to fail for at least one path in the selected set while the destructive Trash step for that (or another) file has already succeeded. Submodule paths are the most plausible trigger vector since they are filtered and handled specially and passed to a dedicated `resetSubmodulePaths` call whose git behavior is less predictable across submodule states (uninitialized, deleted, or conflicting `.gitmodules` entries) — all of which can be shaped by the content of a cloned/fetched repository. Because "Discard Changes" is a common and unprompted user action for any repo, no unnatural user steps are needed beyond normal usage.

### Recommendation
Perform the Trash-move and the corresponding git restore per-file (or per-safe-batch) with matching error handling, so that if the git-level restore fails for a subset of paths, those specific files are either (a) not trashed in the first place, or (b) restored from Trash automatically, rather than leaving a partial, silently-inconsistent state. At minimum, catch and report which specific paths failed to be reset/checked-out after files were already moved to Trash, and surface this to the user distinctly from a generic "Failed discarding changes" error so they know their files are recoverable only from Trash and were not restored to HEAD's copy.

### Proof of Concept

2. In Desktop, select the modified files + the submodule path and choose "Discard Changes" (or "Discard All Changes").
3. `discardChanges` in `app/src/lib/stores/git-store.ts` (lines 1555–1601) moves the regular files to Trash successfully.
4. The subsequent `performFailableOperation` block (lines 1636–1648) throws when `resetSubmodulePaths` (or `resetPaths`/`checkoutIndex`) errors on the submodule path.
5. `AppStore._discardChanges` (lines 5705–5720) catches the error, logs it, shows an error to the user, and calls `_refreshRepository` — but the already-trashed regular files are never restored from HEAD, and there is no code path that reconciles this. [5](#0-4) [6](#0-5)

  public async discardChanges(
    files: ReadonlyArray<WorkingDirectoryFileChange>,
    moveToTrash: boolean = true,
    askForConfirmationOnDiscardChangesPermanently: boolean = false
  ): Promise<void> {
    const pathsToCheckout = new Array<string>()
    const pathsToReset = new Array<string>()

    const submodules = await listSubmodules(this.repository)

    for (const file of files) {
      const foundSubmodule = submodules.some(s => s.path === file.path)

      if (file.status.kind !== AppFileStatusKind.Deleted && !foundSubmodule) {
        if (moveToTrash) {
          try {
            await this.shell.moveItemToTrash(
              Path.resolve(this.repository.path, file.path)
            )
          } catch (e) {
            if (askForConfirmationOnDiscardChangesPermanently) {
              throw new DiscardChangesError(e, this.repository, files)
            }

            // The user has received the confirmation dialog in past and has
            // chosen to always discard the changes permanently if trash failes.
            // We need to remove the file manually.
            if (file.status.kind === AppFileStatusKind.Untracked) {
              await rm(Path.join(this.repository.path, file.path))
            }
          }
        } else if (moveToTrash === false) {
          // The user has received the confirmation dialog and has chosen to
          // discard the changes permanently. We need to remove the file
          // manually.
          if (file.status.kind === AppFileStatusKind.Untracked) {
            await rm(Path.join(this.repository.path, file.path))
          }
        }
      }

      if (
        file.status.kind === AppFileStatusKind.Copied ||
        file.status.kind === AppFileStatusKind.Renamed
      ) {
        // file.path is the "destination" or "new" file in a copy or rename.
        // we've already deleted it so all we need to do is make sure the
        // index forgets about it.
        pathsToReset.push(file.path)

        // checkout the old path too
        pathsToCheckout.push(file.status.oldPath)
        pathsToReset.push(file.status.oldPath)
      } else {
        pathsToCheckout.push(file.path)
        pathsToReset.push(file.path)
      }
    }

    // Check the index to see which files actually have changes there as compared to HEAD
    const changedFilesInIndex = await getIndexChanges(this.repository)

    // Only reset paths if they have changes in the index
    const necessaryPathsToReset = pathsToReset.filter(x =>
      changedFilesInIndex.has(x)
    )

    const submodulePaths = pathsToCheckout.filter(p =>
      submodules.find(s => s.path === p)
    )

    // Don't attempt to checkout files that are submodules or don't exist in the index after our reset
    const necessaryPathsToCheckout = pathsToCheckout.filter(
      x =>
        submodulePaths.indexOf(x) === -1 ||
        changedFilesInIndex.get(x) !== IndexStatus.Added
    )

    // We're trying to not invoke git linearly with the number of files to discard
    // so we're doing our discards in three conceptual steps.
    //
    // 1. Figure out what the index thinks has changed as compared to the previous
    //    commit. For users who exclusive interact with Git using Desktop this will
    //    almost always empty which, as it turns out, is great for us.
    //
    // 2. Figure out if any of the files that we've been asked to discard are changed
    //    in the index and if so, reset them such that the index is set up just as
    //    the previous commit for the paths we're discarding.
    //
    // 3. Checkout all the files that we've discarded that existed in the previous
    //    commit from the index.
    await this.performFailableOperation(async () => {
      if (submodulePaths.length > 0) {
        await resetSubmodulePaths(this.repository, submodulePaths)
      }

      await resetPaths(
        this.repository,
        GitResetMode.Mixed,
        'HEAD',
        necessaryPathsToReset
      )
      await checkoutIndex(this.repository, necessaryPathsToCheckout)
    })
  }

  public async _discardChanges(
    repository: Repository,
    files: ReadonlyArray<WorkingDirectoryFileChange>,
    moveToTrash: boolean = true
  ) {
    const gitStore = this.gitStoreCache.get(repository)

    const { askForConfirmationOnDiscardChangesPermanently } = this.getState()

    try {
      await gitStore.discardChanges(
        files,
        moveToTrash,
        askForConfirmationOnDiscardChangesPermanently
      )
    } catch (error) {
      if (!(error instanceof DiscardChangesError)) {
        log.error('Failed discarding changes', error)
      }

      this.emitError(error)
      return
    }

    return this._refreshRepository(repository)
  }
