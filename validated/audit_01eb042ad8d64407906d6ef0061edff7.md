### Title
Coinbase outputs are reported as spendable before maturity - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_block` scans every transaction in a block, including the coinbase transaction, and returns matching coinbase outputs as ordinary `ReceivedOutput` values [1](#0-0) . A `ReceivedOutput` is explicitly modeled as “a spendable output,” but a coinbase output cannot be spent until it reaches Bitcoin’s coinbase maturity rule [2](#0-1) . The implementation relies on callers to perform an additional filtering pass rather than enforcing that invariant in the scanner [3](#0-2) .

### Finding Description
`scan_block` iterates over all `block.txdata`, where `txdata[0]` is the coinbase transaction, and calls `scan_transaction` for it [1](#0-0) . `scan_transaction` creates a `ReceivedOutput` solely because the output’s `script_pubkey` matches a registered scanner script [4](#0-3) . The resulting object carries only the spend offset, `TxOut`, and outpoint; it does not carry coinbase status, confirmation height, or maturity metadata [2](#0-1) . `SignableTransaction::new` then accepts those outputs as inputs and preserves their `TxOut` values as prevouts without checking whether they are mature coinbase outputs [5](#0-4) . The multisig construction validates only that the offset group key matches the previous output’s script, not that the referenced output is currently spendable [6](#0-5) .

### Impact Explanation
A miner can direct a coinbase output to a Serai-scanned Taproot script, causing the wallet scanner to report funds as received even though Bitcoin consensus forbids spending them for 100 blocks [3](#0-2) . Downstream wallet or scheduler logic that treats `ReceivedOutput` according to its documented contract may construct and threshold-sign a transaction that is guaranteed to fail relay and confirmation until maturity [7](#0-6) . This can cause temporarily unavailable accounting, stuck plans, rejected transactions, or repeated signing attempts for an output that the interface already classified as spendable [8](#0-7) . The impact is bounded to the maturity window, so it does not permit permanent theft or forging of signatures [3](#0-2) .

### Likelihood Explanation
An external miner can create the triggering condition with public transaction data by paying the scanned P2TR script in the block’s coinbase output [4](#0-3) . No malformed encoding, private key access, malicious validator, or protocol modification is required: the scanner itself explicitly acknowledges that it scans the maturity-bound coinbase transaction [3](#0-2) . The issue is conditional on a consumer using `scan_block` instead of manually skipping `block.txdata[0]`, but that use is directly exposed by the API [1](#0-0) .

### Recommendation
Make the spendability invariant part of the API instead of relying on caller-side filtering. `Scanner::scan_block` should skip `block.txdata[0]`, return a distinct immature-output type, or include sufficient block/coinbase metadata for callers to reject immature outputs before constructing `SignableTransaction` [9](#0-8) . If immature outputs must remain visible for accounting, rename or extend `ReceivedOutput` so that it cannot be passed to `SignableTransaction::new` until matured [10](#0-9) .

### Proof of Concept
1. Construct an even Taproot group key and initialize `Scanner::new(key)`, which registers the matching P2TR script with offset zero [11](#0-10) .
2. Create a regtest block whose coinbase transaction has an output paying `p2tr_script_buf(key)`.
3. Call `Scanner::scan_block(&block)`; the scanner returns a `ReceivedOutput` for the coinbase outpoint because it matches the registered script [12](#0-11) .
4. Pass that `ReceivedOutput` to `SignableTransaction::new`; the constructor accepts it as an input and records its `TxOut` as a prevout [5](#0-4) .
5. `multisig` succeeds because the offset key produces the same P2TR script, and `sign` produces a Taproot key-spend signature over `Prevouts::All` [6](#0-5) [7](#0-6) .
6. Broadcasting the signed transaction before coinbase maturity is rejected by Bitcoin consensus despite the scanner having classified the output as spendable [2](#0-1) .

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
