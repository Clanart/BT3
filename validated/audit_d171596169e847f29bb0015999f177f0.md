### Title
Missing Ownership Check in DataLayerWallet.create_new_mirror Allows Anyone to Register Malicious Mirror URLs for Any Data Layer Singleton - ([File: chia/data_layer/data_layer_wallet.py])

### Summary
`DataLayerWallet.create_new_mirror()` lets any wallet create an on-chain "mirror" record (a coin with a specific mirror puzzle hash) that associates an arbitrary `launcher_id` with arbitrary URLs, with no check that the caller actually owns the singleton identified by that `launcher_id`. This is the direct analog of the `addUniV3Pools` bug: a function that should be restricted to the entity that controls the trusted resource (the pool/singleton owner) is instead callable by anyone, letting an attacker register spoofed trust metadata (mirror server URLs) that downstream clients rely on.

### Finding Description
`create_new_mirror` builds a standard coin spend to the public `create_mirror_puzzle()` puzzle hash and simply memoizes the caller-supplied `launcher_id` and `urls` — it performs no lookup or verification that the spending wallet actually owns or controls the singleton identified by `launcher_id`: [1](#0-0) 

Contrast this with the sibling function `delete_mirror`, which explicitly checks that the wallet has a derivation record for the mirror's parent puzzle hash before allowing removal, and raises a permission error otherwise: [2](#0-1) 

The asymmetry shows that ownership verification was clearly intended as a security boundary for mirror management, but it was omitted on the *creation* path — the path that actually injects trust data into the system. Any user can spend their own XCH to the `create_mirror_puzzle()` puzzle hash with a memo of `[launcher_id, *urls]` for **any** `launcher_id`, including one they do not own, and the resulting mirror coin is indistinguishable on-chain from a legitimate mirror registered by the real singleton owner. This is exposed through the wallet RPC `dl_new_mirror` endpoint, which passes the caller-supplied `launcher_id` straight through to `create_new_mirror` without any ownership check either: [3](#0-2) 

Mirrors recorded this way are queried by `dl_get_mirrors`/`DLGetMirrors` and by Data Layer client tooling to discover which hosts serve the root/proof data for a given store (`launcher_id`): [4](#0-3) 

Because the association between `launcher_id` and mirror URL is only a memo on a freely-spendable coin — not a cryptographic proof of singleton ownership — an unprivileged attacker can flood the mirror list for someone else's Data Layer store with attacker-controlled URLs.

### Impact Explanation
A local/remote Data Layer client that resolves mirrors for a target store id to fetch the store's root/proof data (analogous to an oracle price feed) can be redirected to attacker-controlled endpoints. This enables serving of malicious or stale root/proof data to any Data Layer client that trusts the mirror list, which can mislead consumers of a store's data (a data-integrity/trust manipulation analogous to poisoning the Uniswap pool list used for pricing). It does not directly move funds, but it corrupts the trust/discovery layer that off-chain Data Layer clients depend on for a given `launcher_id`, and pollutes on-chain mirror state for singletons the attacker does not own.

### Likelihood Explanation
High reachability: any wallet user (an "unprivileged... Data Layer client" per the reachable-actor list) can call `dl_new_mirror` via the wallet RPC, or directly construct the standard-wallet spend, for any `launcher_id` they choose — no special key, signature over the target singleton, or prior relationship with that singleton is required. The only cost is the mirror-coin amount and fee.

### Recommendation
Before creating a mirror, `create_new_mirror` (and the `dl_new_mirror` RPC handler) should verify that the calling wallet actually owns/tracks the specified `launcher_id`, mirroring the same ownership check already used in `delete_mirror` (i.e., resolve the singleton's current inner puzzle hash and confirm a matching derivation record exists in `puzzle_store`) before allowing the mirror registration to proceed. Alternatively, bind the mirror puzzle itself to require a signature/announcement from the singleton's current inner puzzle so a mirror cannot be created for a `launcher_id` without the owner's cooperation.

### Proof of Concept
1. Attacker identifies a target Data Layer store's `launcher_id` (public on-chain data, not secret).
2. Attacker calls the wallet RPC `dl_new_mirror` (`DLNewMirror`) with that `launcher_id` and `urls=["http://attacker.example/malicious-store"]`, using their own unrelated wallet/funds — no ownership of the store is required: [3](#0-2) 
3. The resulting transaction is accepted by full nodes because `create_new_mirror` performs no ownership check and simply generates a signed transaction to the public mirror puzzle hash with the attacker's chosen memo: [1](#0-0) 
4. Once confirmed, `dl_get_mirrors`/`DLGetMirrors` for that `launcher_id` now includes the attacker's malicious URL alongside (or instead of) legitimate mirrors, and any Data Layer client resolving mirrors for that store may fetch data from the attacker-controlled host.

Note: I could not fully trace, within the indexing limits of this pass, the exact downstream Data Layer client code path that fetches/validates root data from a mirror URL (e.g., whether hash/proof verification later rejects tampered content) — a Devin session with full repository access should verify whether `chia/data_layer/data_layer.py`'s mirror-consumption logic cryptographically validates fetched content against the store's proven root before deciding final exploit severity (data poisoning vs. detected-and-rejected forgery).

        """Get all of the mirrors for a specific singleton"""
        if self.service.wallet_state_manager is None:
            raise ValueError("The wallet service is not currently initialized")

        wallet = await self.service.wallet_state_manager.get_dl_wallet()
        return DLGetMirrorsResponse(mirrors=await wallet.get_mirrors_for_launcher(request.launcher_id))

    async def dl_new_mirror(
        self,
        request: DLNewMirror,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> DLNewMirrorResponse:
        """Add a new on chain message for a specific singleton"""
        if self.service.wallet_state_manager is None:
            raise ValueError("The wallet service is not currently initialized")

        dl_wallet = await self.service.wallet_state_manager.get_dl_wallet()
        async with self.service.wallet_state_manager.lock:
            await dl_wallet.create_new_mirror(
                request.launcher_id,
                request.amount,
                Mirror.encode_urls(request.urls),
                action_scope,
                fee=request.fee,
                extra_conditions=extra_conditions,
            )

        # tx_endpoint will take care of default values here
        return DLNewMirrorResponse(unsigned_transactions=[], transactions=[])
