### Title
Operator can be auto-credited for a payout it never fronted via unauthenticated OP_RETURN pubkey - ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
`bridge_circuit()` derives `operator_xonlypk` for `deposit_constant()` purely from `parse_op_return_data(&first_op_return_output.script_pubkey)`, an unsigned 32-byte push in the payout transaction's OP_RETURN. Every downstream consumer of this value (`update_finalized_payouts`, `is_kickoff_malicious`, `PayoutCheckerTask`) trusts these bytes as proof of who fronted the withdrawal, with no check that the party who actually funded/broadcast the payout transaction controls the private key for that xonly pubkey.

### Finding Description
The claimed binding is: `deposit_constant.operator_xonlypk == xonly_pubkey_of_party_that_actually_fronted_the_payout`.

Trace:
1. `create_payout_txhandler` writes `operator_xonly_pk.serialize()` into an OP_RETURN output with **no signature over it** [1](#0-0) . Anyone who can build a valid keypath spend of the withdrawal input (the attacker, per the rules, chooses the withdrawal UTXO, signature and sighash flag) can construct their own payout transaction and put **any** 32 bytes — including a real operator's public xonly key — into that OP_RETURN.
2. `bridge_circuit()` reads those bytes with `parse_op_return_data` and feeds them straight into `deposit_constant()` with no signature check binding them to a funder [2](#0-1) ; `parse_op_return_data` itself only extracts a push-data blob, performing zero cryptographic validation [3](#0-2) .
3. On the verifier/operator side, chain-sync (`update_finalized_payouts`) does the same unauthenticated parse and stores it as `payout_payer_operator_xonly_pk` in the DB [4](#0-3) .
4. Each operator's `PayoutCheckerTask` queries `get_first_unhandled_payout_by_operator_xonly_pk` filtered by **its own** signer key [5](#0-4) [6](#0-5) . If a match is found it automatically calls `handle_finalized_payout`, which allocates a kickoff connector and starts the reimbursement flow [7](#0-6) .
5. `is_kickoff_malicious` (the only cross-check verifiers run) merely re-checks `operator_xonly_pk (from OP_RETURN) == kickoff_data.operator_xonly_pk (the kickoff tx signer)` [8](#0-7) . Since the attacker deliberately chose the OP_RETURN bytes to equal the targeted operator's real public key, this check trivially passes even though that operator never funded, signed, or broadcast the payout transaction.

Exploit flow: the attacker crafts a payout transaction spending a withdrawal UTXO they can authorize (self-funding it or otherwise bypassing the operator), sets the OP_RETURN to a real, known operator's xonly public key, and mines it. The targeted operator's own automation (`PayoutCheckerTask`) picks it up as "its" payout and proceeds through kickoff → assert → reimburse, ultimately releasing bridge value to that operator's `Reimburse` output for a withdrawal it never fronted. No component — not `bridge_circuit`, not `is_kickoff_malicious`, not `update_finalized_payouts` — ever verifies a Schnorr signature binding the OP_RETURN pubkey to whoever actually funded the payout output.

### Impact Explanation
This lets an attacker force bridge (vault) value to be paid out to an operator's `Reimburse` transaction for a withdrawal that operator never fronted with its own funds — matching the Critical category "an operator reimbursed for a payout it never funded" (and correspondingly, "BTC leaving a move-to-vault UTXO/collateral without a matching fronted withdrawal"). It is repeatable across every deposit/withdrawal pair and against any operator whose xonly pubkey is public knowledge (all operator keys are public protocol participants), so the blast radius spans the whole operator set and every processed deposit.

### Likelihood Explanation
Preconditions: a real deposit exists and a withdrawal UTXO/registration exists on the Citrea side that the attacker can spend via keypath (the attacker is explicitly granted control of the withdrawal UTXO, signature, and sighash flag per the threat model). The attacker pays only Bitcoin transaction fees to broadcast their crafted payout transaction; no privileged role, key compromise, or majority hashrate is required. This is fully deterministic and repeatable — it does not depend on network races or timing beyond normal block confirmation.

### Recommendation
Bind the OP_RETURN `operator_xonlypk` cryptographically to the actual funder: require the payout transaction (or a companion witness/signature) to carry a Schnorr signature under the claimed operator key over the payout transaction (e.g., sighash of the payout tx), and verify that signature inside `bridge_circuit` (and in `is_kickoff_malicious`/`update_finalized_payouts`) before trusting the OP_RETURN bytes as attribution, instead of treating an unauthenticated 32-byte push as proof of funding.

### Proof of Concept

Add a test in `circuits-lib/src/bridge_circuit/mod.rs`:
1. Construct a `BridgeCircuitInput` with a real deposit/withdrawal storage proof and a `payout_spv.transaction` whose OP_RETURN contains `victim_operator_xonlypk` (32 bytes), but whose input keypath witness/signature is authored by an unrelated `attacker_key` (i.e., the actual funder of the payout output).
2. Call the internal logic equivalent to `bridge_circuit`'s deposit-constant computation, asserting `operator_xonlypk == victim_operator_xonlypk` succeeds (proving the circuit accepts it) while separately proving `victim_operator_xonlypk` never signed/authorized the payout output (no signature check exists against `attacker_key`).
3. Compute `deposit_constant` once using `victim_operator_xonlypk` (from the forged OP_RETURN) and once using the true funder's key (`attacker_key`); assert they differ, demonstrating that `bridge_circuit` commits a `journal_hash` that credits `victim_operator_xonlypk` despite no signature from that key ever being verified anywhere in the call chain (`parse_op_return_data` → `deposit_constant` → `journal_hash`).

```rust
/// Parses the OP_RETURN data from a Bitcoin script. It retrieves the first data push after an OP_RETURN.
pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}
```

```rust
    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
```
