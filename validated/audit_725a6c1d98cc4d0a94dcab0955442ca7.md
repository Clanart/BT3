### Title
Escrow accounting is finalized even when the underlying ERC20 `transfer` call returns `false` on the Tron `IntentGatewayV2.withdraw`/`sweepDust` paths - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw` (the internal function invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow`) and the `SweepDust` branch of `onAccept` move escrowed ERC20 tokens using a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the *call itself* did not revert (`success`), never decoding the returned boolean. Any ERC20/TRC20 that returns `false` on a failed transfer instead of reverting (e.g. a blacklist-capable stablecoin) will pass this check while moving zero tokens, yet the contract still permanently zeroes out the escrow accounting and emits a "released"/"swept" event, permanently trapping the tokens.

### Finding Description
In `withdraw`, escrow is decremented unconditionally after the `.call` "succeeds": [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

The same pattern appears for the transaction-fee redemption immediately after, and in the `SweepDust` branch of `onAccept`: [2](#0-1) 

`success` here is `true` whenever the callee contract executes without reverting — it says nothing about the ABI-encoded boolean return value. Standards-compliant-but-non-reverting tokens (blacklist-gated stablecoins are the canonical example, and are especially relevant on Tron where TRC20 USDT-style tokens commonly implement blacklisting) return `false` from `transfer` for a disallowed recipient rather than reverting. In that case `success == true`, the `if (!success) revert TransferFailed();` guard never fires, and execution falls through to `_orders[body.commitment][token] -= amount;`, which unconditionally marks the escrow as settled even though no tokens actually left the contract.

Notably the same file already imports and uses `SafeERC20` for other transfers (`safeTransferFrom` at deposit time), so the inconsistency is local to the withdrawal/sweep paths, not a project-wide choice.

This is the direct local analog of the external Talos `collectProtocolFees` finding: a non-reverting `false`-returning ERC20 transfer causes escrow/protocol-fee bookkeeping to update as if the transfer succeeded, silently trapping funds in the contract.

### Impact Explanation
Once `_orders[body.commitment][token]` is decremented (or `_filled[commitment]` is set) without the tokens actually moving, the beneficiary/solver has no way to redeem those tokens again — the commitment is treated as fulfilled/refunded, and there is no retry or reclaim path for the escrowed balance. This is a direct, permanent loss/lock of bridged/escrowed funds for the affected order, which matches the bounty's "stealing or loss of funds" impact class. It requires no malicious relayer, prover, or governance actor — only a token whose `transfer` can return `false` for the beneficiary in question (e.g. a blacklisted address on a TRC20 stablecoin), which is an ordinary, non-adversarial token property already accounted for elsewhere in the same contract via `SafeERC20`.

### Likelihood Explanation
This contract is specifically the Tron deployment (`evm/tron/contracts/apps/IntentGatewayV2.sol`), where TRC20 tokens with blacklist/pausable transfer semantics that return `false` instead of reverting are commonplace (this is the same token-behavior class OpenZeppelin's SafeERC20 docs warn about, and is exactly why the rest of the contract uses `safeTransferFrom`). Any order whose input/output token is such a token, and whose beneficiary later becomes blacklisted (or intentionally is a contract that returns `false` deliberately) before the `RedeemEscrow`/`RefundEscrow`/`SweepDust` request is delivered, hits this path deterministically and without any special privileges.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only checks in `withdraw` (both the token loop and the transaction-fee redemption) and in the `SweepDust` branch of `onAccept` with `SafeERC20.safeTransfer`, consistent with the rest of the contract's `safeTransferFrom` usage. `SafeERC20` reverts on both a call-level revert and a `false` return value, preventing the escrow state from ever being finalized without the tokens actually moving.

### Proof of Concept
1. Deploy (or use) a TRC20/ERC20 token whose `transfer` returns `false` for a blacklisted recipient instead of reverting (standard pattern for many stablecoins deployed on Tron).
2. Place a same-chain or cross-chain order whose output/input token is this token, with `beneficiary` set to an address that the token issuer can later blacklist.
3. Get `beneficiary` blacklisted by the token contract before the `RedeemEscrow` (or `RefundEscrow`) request is delivered to `IntentGatewayV2.onAccept`.
4. When `withdraw` executes:
   - `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (call executes, no revert) but transfers 0 tokens (token-internal `transfer` returned `false`).
   - `_orders[body.commitment][token] -= amount;` executes, and `EscrowReleased`/`EscrowRefunded` is emitted.
5. The tokens remain in the `IntentGatewayV2` contract balance, but the commitment's escrow entry is now zero/settled, so there is no code path left to reclaim them — the funds are permanently stuck. [3](#0-2)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
