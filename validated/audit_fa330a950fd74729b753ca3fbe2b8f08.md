## Title
Withdraw-then-decrement ordering in `IntentGatewayV2.withdraw()` violates checks-effects-interactions, enabling escrow over-drain via a malicious order-input token - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of the Intent Gateway settles escrow withdrawals by performing the external token transfer **before** decrementing the internal escrow accounting, the same "pay first, update ledger second" defect that caused the Connext `withdrawAdminFees()` bug (fees transferred without zeroing `adminFees[i]` first, permitting repeat withdrawal of the same balance).

### Finding Description
In `withdraw()`:
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    ...
}
_orders[body.commitment][token] -= amount;
``` [1](#0-0) 
and for the fee sweep:
```solidity
uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
if (fees > 0) {
    ...
    (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
    ...
    delete _orders[body.commitment][TRANSACTION_FEES];
}
``` [2](#0-1) 
the escrow ledger (`_orders[commitment][token]`) is only decremented **after** the external `token.call` returns, exactly mirroring the reported pattern where `self.adminFees[i]` was read and transferred but not zeroed until after (in that case, never). The token address in `order.inputs[i].token` is fully attacker-controlled at order-creation time via `placeOrder()` [3](#0-2) , so an order creator can escrow a custom malicious ERC20 whose `transfer()` implementation re-enters the gateway before the ledger write lands.

By contrast, the canonical (non-Tron) implementation in `IntentsBase.sol` performs the accounting update **before** the transfer for both the token loop and the fee sweep:
```solidity
_orders[body.commitment][token] = escrowed - amount;
...
IERC20(token).safeTransfer(beneficiary, amount);
``` [4](#0-3) 
```solidity
if (fees > 0) {
    delete _orders[body.commitment][TRANSACTION_FEES];
    IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
}
``` [5](#0-4) 
This confirms the Tron contract's ordering is a regression from the safe pattern used elsewhere in the same protocol, and it is the exact bug class targeted by the report: value moved out before the corresponding internal balance is reset.

The only reachable unprivileged entrypoint into `withdraw()` is `cancelOrder()` for same-chain orders:
```solidity
if (isSameChain) {
    if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
    ...
    withdraw(body, true);
}
``` [6](#0-5) 
`withdraw()` does set `_filled[body.commitment] = beneficiary` at the top, before the loop [7](#0-6) , which blocks a **second top-level call** into `cancelOrder`/`onAccept` for the same commitment. I was not able to fully verify, within the remaining investigation budget, whether a malicious token's `transfer()` callback can reach another code path (e.g. `placeOrder`, `fillOrder`, or a different order's `cancelOrder`) that reads/writes the *same* `_orders[commitment][token]` slot before the decrement lands — this is the residual uncertainty in turning the CEI violation into a concrete drain, and it should be treated as unverified rather than confirmed exploitable end-to-end.

### Impact Explanation
If a reachable reentrant path exists, an attacker-supplied malicious ERC20 used as an order input could cause the gateway to pay out escrowed value more than once against the same `_orders[commitment][token]` balance, directly stealing bridge-custodied funds — matching the required impact class ("stealing or loss of funds", "double-claim/double-settlement"). Even absent a full double-spend, this is a clear checks-effects-interactions violation in fund-custody code that differs from the audited/safe pattern used in `IntentsBase.sol`, and should be fixed defensively regardless of whether a concrete reentrant caller was proven in this pass.

### Likelihood Explanation
Medium: the vulnerable code path is reachable by any unprivileged order creator (no relayer, prover, or admin needed) since they choose the escrowed token in `placeOrder()`, and `cancelOrder()`/`withdraw()` are public, unprivileged entrypoints. The `_filled` guard mitigates the most direct re-entry via `cancelOrder`, so likelihood is capped at "medium" pending confirmation of an alternate reentry path (not established here).

### Recommendation
In `IntentGatewayV2.sol::withdraw()`, apply checks-effects-interactions consistently: decrement `_orders[body.commitment][token]` (and `delete` the `TRANSACTION_FEES` entry) **before** issuing the external `token.call`/`beneficiary.call`, matching the ordering already used in `IntentsBase.sol`. Additionally consider a reentrancy guard on all public entrypoints that ultimately call `withdraw()` (`cancelOrder`, `onAccept`, `onGetResponse`) as defense in depth.

### Proof of Concept
Conceptual (not runtime-verified against a live reentrant call path):
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer()` callback attempts to re-enter the gateway.
2. Attacker calls `placeOrder()` with `order.inputs = [{token: EvilToken, amount: X}]`, escrowing `X` `EvilToken` into `_orders[commitment][EvilToken] = X`. [8](#0-7) 
3. Attacker calls `cancelOrder()` (same-chain path) once expired/eligible, triggering `withdraw(body, true)`.
4. Inside the token loop, `token.call(transfer(beneficiary, X))` executes before `_orders[commitment][token] -= X`; if `EvilToken.transfer` can re-enter a code path that still observes `_orders[commitment][EvilToken] == X` (unconfirmed which path, since direct `cancelOrder` re-entry is blocked by the `_filled` set at function entry), the escrow could be drained beyond the single deposited `X`.

This PoC establishes the CEI violation with certainty; the full double-spend exploit chain requires further investigation into cross-function reentrancy paths, which could not be completed within this session — recommend a Devin session with local test execution to confirm/deny exploitability empirically before triage.
