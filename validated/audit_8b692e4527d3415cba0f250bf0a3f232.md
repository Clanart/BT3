### Title
Bitcoin Scanner credits outputs of any value, including uneconomical dust outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes swaps executed without a minimum-output bound (`minAmountOut == 0`), letting a counterparty/MEV bot satisfy the trade with arbitrarily little value. The analog in Serai's in-scope code is `Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs`: it credits any on-chain output whose `script_pubkey` matches a registered script with **no minimum value bound**. Any unprivileged party can send a transaction paying dust (e.g., 1 satoshi) to the multisig's Taproot script, and the scanner reports it as a `ReceivedOutput` — a "received" output whose spending cost exceeds its value, so the reported funds are effectively unspendable.

### Finding Description
`scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) iterates transaction outputs and pushes a `ReceivedOutput` for every output matching a registered script:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

There is no check on `output.value`. The same is true of `scan_block` (lines 221-227), which delegates to `scan_transaction` for every transaction including the coinbase.

The codebase *does* recognize that outputs below a threshold are worthless: `Bitcoin::DUST = 10_000` sats (`processor/src/networks/bitcoin.rs:638`) is defined precisely because spending an output costs ~285+ sats of fee and relay policy demands outputs be worth more than their spend fee. `SignableTransaction::new` rejects `DustPayment` outputs and drops sub-dust change (send.rs:165-169, 228-234). But that protection only applies on the *send* side. On the *receive* side, the scanner — the only path by which externally-sent Bitcoin becomes a `ReceivedOutput` — applies no bound at all, exactly mirroring `minAmountOut == 0`: the protocol accepts whatever output the sender gives it.

### Impact Explanation
An attacker sends a Bitcoin transaction with an output of 1-294 satoshis to the Serai multisig's P2TR script (or to a registered offset script). `scan_transaction`/`scan_block` return it as a valid `ReceivedOutput`, and downstream code (`processor` scheduler/`SignableTransaction`) treats it as spendable input. Because the ~57-vbyte Taproot input it contributes costs more in fees than its value, including it in a transaction is a net loss (`input_sat` grows by less than `needed_fee` grows), and omitting it leaves the credited balance permanently unrecoverable. This produces funds reported received that are not economically spendable, and forces honest scheduling code to absorb a loss (or wedge on `NotEnoughFunds`) proportional to the dust received. Repeated dust deposits compound the discrepancy between tracked balance and recoverable balance.

### Likelihood Explanation
The attack requires only that the attacker broadcast a normal Bitcoin transaction paying to the multisig's publicly known script — no validator collusion, no leaked keys, no malformed cryptography. The script pubkey is necessarily public (it is the deposit address), and `register_offset`-derived scripts are likewise observable on-chain. Cost to the attacker is the dust itself plus a normal transaction fee. The only mitigating factor is that each dust output's damage is bounded by its spend fee, keeping this at Medium rather than higher severity.

### Recommendation
Apply the same minimum-bound philosophy used for payments to received outputs: filter `scan_transaction`/`scan_block` results to outputs with `value >= DUST` (the `10_000` sat threshold already defined for the Bitcoin network), or push the check into `scan_transaction` itself so sub-dust outputs are never surfaced as `ReceivedOutput`. Equivalently, treat the network `DUST` constant as the `amountOutMin` for inbound outputs.

### Proof of Concept
Conceptual, on regtest/signet:

1. Obtain the multisig's P2TR `ScriptBuf` (the deposit address) via `Scanner::new(key)` / `p2tr_script_buf`, or observe any registered offset script on-chain.
2. Broadcast a transaction with `TxOut { value: Amount::from_sat(1), script_pubkey: multisig_script }`.
3. Call `Scanner::scan_block(&block_containing_tx)` — it returns `vec![ReceivedOutput { value: 1, ... }]` with no rejection path (mod.rs:199-214).
4. Attempt to spend it via `SignableTransaction::new` (send.rs:150-256): the input adds 1 sat to `input_sat` but ~57 vbytes × `fee_per_vbyte` to `needed_fee`, so it can never be profitably spent — the credited sat is unspendable, and at realistic fee rates including it forces `NotEnoughFunds` or burns other inputs' value.

No minimum-value check exists anywhere between `output.script_pubkey` matching (mod.rs:205) and `ReceivedOutput` construction (mod.rs:206-210), confirming the missing bound.
