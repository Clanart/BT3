## Analysis

The bug-class in the report is: a value-tracking write silently diverges from real fund movement (burn accounted but balance not deducted → user gets more than entitled). The closest real analog in this repo is in the **Tron build of `IntentGatewayV2`**, where escrow accounting is deducted and the order is marked settled even when the underlying ERC-20 transfer silently failed.

`evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()` releases escrow using a raw low-level `.call`, checking only that the call didn't revert — not the boolean return value the ERC-20 standard requires for `transfer()`: [1](#0-0) 

Compare this to the canonical EVM implementation, which correctly uses `SafeERC20.safeTransfer`, reverting the whole withdrawal if the transfer fails or returns `false`: [2](#0-1) 

The same unchecked-`.call` pattern recurs for `SweepDust` and transaction-fee payout in the Tron contract: [3](#0-2) [4](#0-3) 

`withdraw()` is invoked from `onAccept` (guarded by `onlyHost`, but reachable by any valid `RedeemEscrow`/`RefundEscrow` ISMP message once authenticated) and from `onGetResponse`: [5](#0-4) [6](#0-5) 

### Title
Escrow marked settled and decremented even when the ERC-20 transfer fails — silent fund loss/lock in Tron `IntentGatewayV2.withdraw()` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` releases escrowed tokens via a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks whether the *call itself* reverted, not the ERC-20 `transfer` return value. Any legacy/non-standard ERC-20 that returns `false` on failure instead of reverting (insufficient contract balance, paused token, blacklisted recipient, etc.) will cause `success == true` while no tokens actually move. The function proceeds to decrement `_orders[commitment][token]`, mark `_filled[commitment]`, forward fees, and emit `EscrowReleased`/`EscrowRefunded` — permanently closing out the order's accounting although the beneficiary received nothing.

### Finding Description
`withdraw()` sets `_filled[body.commitment] = beneficiary` up front, then for each token performs the transfer and unconditionally decrements `_orders[body.commitment][token] -= amount` immediately after, based solely on `success` from the low-level `.call` [7](#0-6) . A low-level `.call` to a contract only returns `success = false` when the callee *reverts*; if the ERC-20 implementation instead returns `false` (a pattern SafeERC20 exists specifically to guard against), `success` stays `true` and the code treats the withdrawal as fully successful.

This directly parallels the report's core defect: a value-transfer function whose bookkeeping (`_orders[...]`, `_filled[...]`) is unconditionally updated as if the transfer of value happened, without verifying that it actually did — analogous to `burnFlashGovernanceAsset()` updating a user's state to reflect a burn that may not correctly reflect what was actually deducted.

### Impact Explanation
Once `_orders[commitment][token]` is decremented and `_filled[commitment]` is set, the escrowed tokens can never be claimed again through any path (`onAccept` rejects re-processing via the `UnknownOrder` check on a zeroed balance, and `cancelOrder` is blocked by `_filled` being non-zero). The tokens remain physically inside the contract but are permanently unreachable by the rightful beneficiary — a direct loss/lock of user or solver funds, matching the bounty's "stealing or loss of funds" / "false state acceptance" categories.

### Likelihood Explanation
Exploitability depends only on the input/output token used in an order being a non-standard ERC-20 that returns `false` rather than reverting on failure (a well-documented class of real-world tokens), or on that token entering a failure state (paused, blacklist, insufficient balance) between escrow and settlement — none of which requires a malicious relayer, prover, or governance actor. The order originator or solver picks the token address at `placeOrder`/`fillOrder` time, so this is reachable by an ordinary unprivileged user of the Tron deployment.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in this file with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, exactly as done in the canonical `evm/src/apps/intentsv2/IntentsBase.sol` implementation, so a failed/false-returning transfer reverts the entire withdrawal instead of silently finalizing escrow accounting.

### Proof of Concept
1. User places an order on the Tron `IntentGatewayV2` with an input token `T` that implements `transfer()` to return `false` on failure instead of reverting (or whose balance becomes insufficient before settlement, e.g. due to a prior partial sweep).
2. A cross-chain `RedeemEscrow`/`RefundEscrow` message reaches `onAccept`, which calls `withdraw(body, ...)`.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call didn't revert) even though `T.transfer` internally returned `false` and moved zero tokens.
4. `_orders[commitment][T] -= amount` executes, `_filled[commitment]` is already set, and `EscrowReleased`/`EscrowRefunded` fires.
5. The beneficiary's on-chain balance of `T` is unchanged, but the order is permanently marked settled — the escrowed `T` tokens are now unrecoverable through any contract entry point.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
