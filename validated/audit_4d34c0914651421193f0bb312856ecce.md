Based on my research, the strongest local analog to the reported bug (unchecked/uninitialized array indexing causing an out-of-bounds condition) is in the IntentGateway's `onGetResponse` handler, which indexes into a GET response's `values` array without validating its length before use.

### Title
Unchecked `values[0]` indexing in `IntentGatewayV2.onGetResponse` can permanently lock escrowed order funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`onGetResponse` blindly accesses `incoming.response.values[0]` to decide whether a source-chain order cancellation should proceed, with no check that the `values` array actually contains an element.

### Finding Description
The cancel-from-source flow dispatches a `DispatchGet` storage-read request to check whether `_filled[commitment]` is set on the destination chain, then relies on the returned `values` array to determine order status: [1](#0-0) 

```solidity
function onGetResponse(IncomingGetResponse calldata incoming) external override onlyHost {
    if (incoming.response.values[0].value.length != 0) revert Filled();
    WithdrawalRequest memory body = abi.decode(incoming.response.request.context, (WithdrawalRequest));
    withdraw(body, true);
}
```

This mirrors the audited `createPools` bug class: a return/response array whose length is assumed rather than validated before indexing. On the ISMP GET-response construction path, the destination state machine's `verify_state_proof` produces a `values` vector keyed to the requested storage slots; the coprocessor pallet then maps that result into `StorageValue` entries: [2](#0-1) 

If the underlying trie proof verification treats a genuinely-absent key (i.e., the exact "unfilled order" case this code path exists to prove) as "no value returned" rather than "one entry with an empty byte value," the resulting `values` array delivered to `onGetResponse` would have zero elements instead of one empty element. `values[0]` would then revert with an array-index-out-of-bounds panic instead of the intended `Filled()` semantics.

### Impact Explanation
If this path is hit, every source-chain cancellation attempt for that order reverts unconditionally — the escrowed input tokens can never be refunded via the source-cancel route, and the ISMP GET response commitment for this order is permanently consumed (each new attempt requires a fresh dispatch/fee). This is a fund-lock condition on user escrow, distinct from a generic gas/DoS issue, because it removes the only mechanism defined for unfilled orders to recover funds from the source chain once the destination-side proof of non-fill is produced.

### Likelihood Explanation
This depends on whether the destination state machine's proof-verification path omits entries for non-existent storage slots versus returning them as zero-length values. I could not fully confirm the exact behavior of `verify_state_proof` for the EVM destination state machine within the available index, so I cannot certify this triggers in all cases — this is the main uncertainty in this finding. What is certain and locally verifiable is the missing bounds check itself: `onGetResponse` never validates `incoming.response.values.length > 0` before indexing, so any code path (current or introduced later) that can return a shorter values array than expected will cause this panic on the legitimate refund path.

### Recommendation
Add an explicit length check before indexing, e.g.:
```solidity
if (incoming.response.values.length == 0 || incoming.response.values[0].value.length != 0) revert Filled();
```
or more precisely, require `values.length == 1` and revert with a distinct error (e.g., `InvalidResponse()`) if not, so a malformed/empty response cannot silently brick the cancellation path. This should also be verified against the actual `verify_state_proof` semantics to determine whether empty-value entries are guaranteed to be present for non-existent keys.

### Proof of Concept
Not independently reproducible from the indexed code alone — the trigger condition requires confirming that `verify_state_proof` (destination EVM state machine) can return a `values` vector with fewer entries than requested `keys` for absent storage slots. Given the missing bounds check is confirmed in `onGetResponse`, the recommended fix should be applied regardless of whether this exact non-existence path currently drops entries or not, since it removes an unguarded assumption on trusted cross-chain response data feeding directly into fund-custody logic.
