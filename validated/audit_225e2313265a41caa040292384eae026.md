### Title
Reentrancy via `onERC1155Received`/`onERC1155BatchReceived` callback in CW1155ERC1155Pointer allows balance-check bypass across nested transfers - (File: `contracts/src/CW1155ERC1155Pointer.sol`)

### Summary
`CW1155ERC1155Pointer.safeTransferFrom` and `safeBatchTransferFrom` execute the underlying CW1155 `send`/`send_batch` message via `_execute` (a `delegatecall` into the wasmd precompile that immediately mutates the CosmWasm contract's balance state) and only afterward invoke the external `onERC1155Received`/`onERC1155BatchReceived` callback on the recipient contract, per [3](#0-2)  and [4](#0-3) . Since the "check" (`balanceOf`) is a live external query into wasm state rather than a locally cached balance, and the wasm state has already been mutated by the time the callback fires, a malicious recipient contract can re-enter the pointer (e.g., call `safeTransferFrom` again, or interact with another pointer/EVM contract that reads this balance) during the callback while the sender's balance reflects the post-transfer, not pre-transfer, state, unlike a canonical OpenZeppelin ERC1155 which updates internal state before external calls and does not re-query external systems mid-transfer.

### Finding Description
The `_execute` helper performs a `delegatecall` to the wasmd precompile at `0x1002` to run the CW1155 contract's `send` message, which debits/credits balances in Cosmos (wasm) state [2](#0-1) . This external state mutation happens strictly before the `IERC1155Receiver` callback is invoked in both `safeTransferFrom` and `safeBatchTransferFrom` [5](#0-4) [6](#0-5) . Because `balanceOf` here is not a local mapping but a fresh cross-VM query into CosmWasm state via `WasmdPrecompile.query` [7](#0-6) , any code that re-enters and reads the sender's/receiver's balance mid-callback observes the already-updated (post-transfer) balance rather than a protected/locked value. This differs from the canonical CEI pattern (and from OpenZeppelin's own `_update`-then-callback ordering) in that the "effect" here is a real, externally-visible, cross-module state change (Cosmos wasm store) rather than an in-EVM-storage write that could be trivially reverted on failure — and there is no reentrancy guard anywhere in this contract or the wasmd precompile `execute` path.

### Impact Explanation
A malicious ERC1155/ERC1155Receiver contract acting as `to` can implement `onERC1155Received` to re-enter `safeTransferFrom`/`safeBatchTransferFrom` (or a `transferFrom`-driven flow in a composed protocol built atop the pointer, e.g., marketplace/escrow contracts that trust `balanceOf`/`transferFrom` return values or check pre/post balances) and exploit the fact that the token has already left the sender's account in wasm state. Depending on how downstream contracts (marketplaces, lending/escrow contracts built on top of the pointer) use these callbacks or balance checks, this can enable double-spending style transfers, unauthorized draining, or bypass of balance/collateral checks that assume atomicity — i.e., real fund loss or unauthorized transfer via the pointer, which is in-scope impact for "unauthorized transfer via precompile or pointer."

### Likelihood Explanation
Any unprivileged EVM contract deployer can create a contract implementing `IERC1155Receiver` and receive tokens through this pointer, then call back into the pointer (or any other reachable contract) during the callback — no special privilege is required. The vulnerability is reachable purely through a standard `safeTransferFrom`/`safeBatchTransferFrom` call from a public RPC-submitted transaction, satisfying the "unprivileged transaction sender/contract deployer... CW/pointer user" reachability requirement.

### Recommendation
Follow checks-effects-interactions: cache the pre-transfer balance check, perform the wasmd `_execute` state mutation, and only invoke the `IERC1155Receiver` callback last while guarding the whole function with a reentrancy lock (e.g., OpenZeppelin's `ReentrancyGuard`), or restructure so the callback is invoked with a "reserved"/"pending" state that blocks concurrent re-entrant transfers on the same `(owner, id)` pair until the outer transfer completes.

### Proof of Concept
1. Deploy `AttackerReceiver` implementing `onERC1155Received` that, upon receiving tokens, immediately calls `CW1155ERC1155Pointer.safeTransferFrom(attackerReceiverAddr, victimOrSelf, id, amount, "")` again (or interacts with a third-party contract that trusts the pointer's `balanceOf`).
2. Attacker calls `pointer.safeTransferFrom(attacker, AttackerReceiver, id, amount, data)`.
3. Inside `_execute`, the CW1155 `send` message is applied, debiting `attacker`'s and crediting `AttackerReceiver`'s wasm balance [8](#0-7) .
4. Before returning, `onERC1155Received` is invoked on `AttackerReceiver` [9](#0-8) , which re-enters the pointer to transfer the just-received balance elsewhere while any composed protocol still believes the original outer transfer is mid-flight / has not finalized checks that depend on the sender's or receiver's balance being stable across the call.
