### Title
Unchecked `removal_amount - addition_amount` subtraction in mempool fee computation can crash spend-bundle validation - ([File: chia/full_node/mempool_manager.py])

### Summary
`MempoolManager.validate_spend_bundle()` computes the transaction fee as `fees = uint64(removal_amount - addition_amount)` without first verifying that the sum of created coin amounts (`addition_amount`) does not exceed the sum of spent coin amounts (`removal_amount`). This mirrors the reported `VestingEscrow.recoverERC20()` bug class: an unchecked subtraction of two attacker-influenced values that can go negative.

### Finding Description
In `chia/full_node/mempool_manager.py`, `addition_amount` is accumulated directly from `CREATE_COIN` conditions revealed inside the submitted spend bundle's own puzzle solutions: [1](#0-0) 

`removal_amount` is accumulated from the amounts of the coins being spent: [2](#0-1) 

The fee is then computed with no preceding "additions cannot exceed removals" guard: [3](#0-2) 

Contrast this with the equivalent full-block validation path, `validate_block_body()`, which explicitly checks for this condition **before** performing the subtraction: [4](#0-3) 

No such `if removal_amount < addition_amount: return Err.MINTING_COIN`-style guard exists in `validate_spend_bundle()` prior to the `uint64()` cast. Because `uint64()` (from `chia_rs.sized_ints`) raises `ValueError: ... does not fit into uint64` for negative inputs rather than silently wrapping (confirmed by `chia/_tests/core/consensus/test_block_creation.py:11-23`, which expects `pytest.raises(ValueError, match="does not fit into uint64")` when `sum(removals) - sum(additions) < 0`), a spend bundle whose total `CREATE_COIN` output exceeds its total input value will cause `uint64(removal_amount - addition_amount)` to throw an uncaught `ValueError` inside `validate_spend_bundle()`. No `try/except` wraps this line or the surrounding block in `mempool_manager.py`.

This differs from the Solidity original (which silently wraps to a huge value), but the root cause is analogous: an arithmetic operation on adversary-controlled inputs performed without a prior bounds/ordering check. In Chia's case the practical consequence is not silent fund miscalculation (Python ints don't wrap) but an unhandled exception during spend-bundle admission — i.e., a spend-bundle-triggered fault in the mempool item-processing pipeline, one of the accepted impact categories ("a spend-triggered transaction-processing halt").

### Impact Explanation
A single unprivileged spend-bundle submitter can construct a spend bundle (e.g., via RPC `push_tx`) whose puzzle solutions declare `CREATE_COIN` outputs summing to more than the total amount of coins being spent (attempting to "mint" coins, which is invalid but not filtered out before this line). This is trivial to construct because a spend bundle need not be internally solvent to reach this code path — solvency is exactly what this line is (mis)computing. The resulting unhandled `ValueError` propagates out of `validate_spend_bundle()`, disrupting mempool admission processing for that call path rather than gracefully returning `Err.MINTING_COIN` as intended by consensus semantics.

### Likelihood Explanation
High reachability: any wallet/RPC caller or spend-bundle submitter can trivially craft a spend bundle with a `CREATE_COIN` condition whose declared amount exceeds the coin being spent — no special privileges, signatures matching real value, or network position are required, since `addition_amount` is derived purely from attacker-supplied condition data before value legitimacy is otherwise checked at this point in the function.

### Recommendation
Add an explicit guard mirroring `block_body_validation.py`'s logic before computing fees in `validate_spend_bundle()`:
```python
if removal_amount < addition_amount:
    return Err.MINTING_COIN, None, []
fees = uint64(removal_amount - addition_amount)
```
This makes mempool admission consistent with consensus block-validation semantics and prevents the uncaught `ValueError` from an adversarial/malformed spend bundle.

### Proof of Concept
1. Construct a coin spend for an owned coin of amount `X`.
2. Craft its solution/puzzle so the CLVM output contains a `CREATE_COIN` condition (or several) whose total amount `Y > X` (i.e., attempt to fabricate value beyond what's being spent).
3. Submit the resulting `SpendBundle` via the wallet/full node RPC (`push_tx` or mempool submission).
4. In `validate_spend_bundle()`, `addition_amount` (sum of `CREATE_COIN` amounts) will exceed `removal_amount` (sum of spent coin amounts), and `fees = uint64(removal_amount - addition_amount)` at [3](#0-2)  raises an unhandled `ValueError`, since no minting check precedes it, unlike the analogous safeguard in `validate_block_body()` at [4](#0-3) .
