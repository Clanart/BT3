### Title
Raw base58-encoded private keys accepted directly as CLI arguments in `solana-keygen recover` and generic signer parsing, exposing keys to shell history and process lists - (File: `clap-v3-utils/src/input_parsers/signer.rs`)

### Summary
The Agave CLI signer-parsing infrastructure auto-detects a raw base58-encoded 64-byte secret key typed directly as a command-line argument and treats it as a valid signing source (`SignerSourceKind::Base58Keypair`), the same bug class described in the external report (private key material passed as a CLI argument gets recorded in the shell's history file / visible via `ps`).

### Finding Description
`SignerSource::parse` in `clap-v3-utils/src/input_parsers/signer.rs` inspects every string given as a signer/keypair CLI argument and, before any other interpretation, attempts to base58-decode it into 64 bytes and verify it is a valid ed25519 keypair: [1](#0-0) 

If this succeeds, the raw secret key string is preserved verbatim in `SignerSourceKind::Base58Keypair(source)`, which is later turned directly into a `Keypair` via `Keypair::from_base58_string`: [2](#0-1) 

This capability is explicitly wired into `SignerSourceParserBuilder` via `allow_base58_keypair()`/`allow_all()`: [3](#0-2) 

and is used by `solana-keygen recover`'s positional `prompt_signer` argument, which explicitly documents that a "base58-encoded keypair string" may be supplied as a bare command-line token: [4](#0-3) 

`is_valid_pubkey`/`is_valid_signer` and `allow_all()` builders are also referenced generically for `--keypair`-style arguments used throughout the CLI utilities: [5](#0-4) 

The broken invariant: nowhere in this code path is there any warning, confirmation, or restriction preventing a user (or a script/wrapper invoking these binaries) from passing the *full 64-byte secret key material* as a literal shell argument. Once passed this way, on any POSIX shell with default history settings, the private key is persisted verbatim to `~/.bash_history` (or equivalent), and is also transiently visible to any other local user via `ps aux`/`/proc/<pid>/cmdline` while the process is running. This is the exact bug class from the external report — sensitive key material logged/exposed via shell history/process listing due to CLI-argument based secret input — now demonstrated as a real, reachable path in Agave's own CLI signer-parsing code rather than a hypothetical script.

Existing guards do not stop this: the other signer sources (`prompt:`, `ASK`, `stdin:`, `usb:`, keypair file path) are designed specifically to avoid ever putting the secret on the command line, but the `Base58Keypair` branch is auto-detected ahead of file-path/URI parsing and is deliberately exposed as an allowed, documented option in at least one shipped binary (`solana-keygen recover`), and via `allow_all()` in the generic builder that other CLI tools (e.g., `solana-cli`, and any wallet/tool crate that constructs its keypair argument with `SignerSourceParserBuilder::default().allow_all()...`) can opt into for the same argument used for `--keypair`, `--fee-payer`, `--from`, etc.

### Impact Explanation
If a private key is ever supplied this way — which the code explicitly documents and supports rather than merely tolerates — an attacker with any form of local access to the machine (another user, a compromised unrelated process reading `.bash_history`, backup/sync tools that capture home-directory dotfiles, or a monitoring/logging agent capturing `ps`) can recover the full signing key and drain or hijack the associated Solana account. This matches "fund theft/loss" impact for the operator/holder of that CLI. It does not require a malicious peer, validator, or trusted plugin — only normal local multi-tenant or defense-in-depth exposure, consistent with the report's own risk framing (Impact 3, Likelihood 3).

### Likelihood Explanation
The likelihood is non-trivial: `solana-keygen recover` explicitly advertises "base58-encoded keypair string" as a valid direct positional argument in its own `--help` text, meaning an unaware operator (or an automation script generated by an LLM/tutorial, similar to the original bash-history HTLC report) is likely to invoke it as `solana-keygen recover <secret-key-base58>` or wire a similar pattern into any downstream tool using `allow_all()`/`allow_base58_keypair()`. No warning is printed when this source type is used.

### Recommendation
- Remove or gate `SignerSourceKind::Base58Keypair` auto-detection behind an explicit, opt-in flag (e.g. `--unsafe-raw-keypair`) rather than making it a silently auto-detected first branch of `SignerSource::parse`.
- Emit a loud stderr warning whenever a `Base58Keypair` source is used, recommending `prompt:`/`ASK`/file-based sources instead.
- Update `solana-keygen recover --help` and related CLI docs to not advertise raw base58 secret entry as a normal usage pattern.
- Where feasible, actively scrub such arguments from process argv (e.g., by immediately re-executing with a masked argv) to reduce `ps`/`/proc` exposure, in addition to the shell-history mitigations from the original report.

import base64,subprocess

KEY_B58=$(python3 - <<'PY'
import json, base58  # illustrative; real code path uses Keypair::to_base58_string
data = json.load(open('/tmp/id.json'))
print(base58.b58encode(bytes(data)).decode())
PY

pub struct SignerSourceParserBuilder {
    allow_prompt: bool,
    allow_file_path: bool,
    allow_usb: bool,
    allow_stdin: bool,
    allow_pubkey: bool,
    allow_base58_keypair: bool,
    allow_legacy: bool,

impl SignerSourceParserBuilder {
    pub fn allow_all(mut self) -> Self {
        self.allow_prompt = true;
        self.allow_file_path = true;
        self.allow_usb = true;

        self.allow_pubkey = true;
        self.allow_legacy = true;

    pub fn allow_pubkey(mut self) -> Self {
        self.allow_pubkey = true;
        self
    }

    pub fn allow_legacy(mut self) -> Self {
        self.allow_legacy = true;
        self
    }

    pub fn allow_base58_keypair(mut self) -> Self {
        self.allow_base58_keypair = true;
        self
    }

    pub fn build(self) -> ValueParser {
        ValueParser::from(
            move |arg: &str| -> Result<SignerSource, SignerSourceError> {
                let signer_source = SignerSource::parse(arg)?;
                if !self.allow_legacy && signer_source.legacy {
                    return Err(SignerSourceError::UnsupportedSource);
                }
                match signer_source.kind {
                    SignerSourceKind::Prompt if self.allow_prompt => Ok(signer_source),
                    SignerSourceKind::Filepath(_) if self.allow_file_path => Ok(signer_source),
                    SignerSourceKind::Usb(_) if self.allow_usb => Ok(signer_source),
                    SignerSourceKind::Stdin if self.allow_stdin => Ok(signer_source),
                    SignerSourceKind::Pubkey(_) if self.allow_pubkey => Ok(signer_source),
                    SignerSourceKind::Base58Keypair(_) if self.allow_base58_keypair => {
                        Ok(signer_source)
                    }
                    _ => Err(SignerSourceError::UnsupportedSource),
                }
            },
        )
    }
}

// Return an error if string cannot be parsed as a pubkey string, or a valid Signer that can
// produce a pubkey()
#[deprecated(
    since = "1.18.0",
    note = "please use `SignerSourceParserBuilder::default().allow_all().build()` instead"
)]
#[allow(deprecated)]
pub fn is_valid_pubkey<T>(string: T) -> Result<(), String>
where
    T: AsRef<str> + Display,
{
    match SignerSource::parse(string.as_ref())
        .map_err(|err| format!("{err}"))?
        .kind
    {
        SignerSourceKind::Filepath(path) => is_keypair(path),
        _ => Ok(()),
    }
}

// Return an error if string cannot be parsed as a valid Signer. This is an alias of
// `is_valid_pubkey`, and does accept pubkey strings, even though a Pubkey is not by itself
// sufficient to sign a transaction.
//
// In the current offline-signing implementation, a pubkey is the valid input for a signer field
// when paired with an offline `--signer` argument to provide a Presigner (pubkey + signature).
// Clap validators can't check multiple fields at once, so the verification that a `--signer` is
// also provided and correct happens in parsing, not in validation.
#[deprecated(
    since = "1.18.0",
    note = "please use `SignerSourceParserBuilder::default().allow_all().build()` instead"
)]
#[allow(deprecated)]
pub fn is_valid_signer<T>(string: T) -> Result<(), String>
where
    T: AsRef<str> + Display,
{
    is_valid_pubkey(string)
}
