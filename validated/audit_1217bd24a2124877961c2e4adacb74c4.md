### Title
Partial-commit patch generation for renamed files diffs against the index (not HEAD), silently including previously staged content the user never reviewed or selected - (File: `app/src/lib/git/diff.ts`)

### Summary
The Seaport report's broken invariant is: what the fulfiller is shown/allowed to validate (a `CriteriaResolver`) does not correspond to what actually gets executed for contract offers, because the itemType/identifier used for execution can silently diverge from the one the user reviewed. GitHub Desktop has a structurally identical invariant violation for partial (line-by-line) commits of renamed files: the diff a user reviews and selects lines from is not guaranteed to be the diff that is actually applied to the index and committed, because `getWorkingDirectoryDiff` intentionally computes a different base for renamed files than the one used elsewhere in the app.

### Finding Description
`getWorkingDirectoryDiff` in `app/src/lib/git/diff.ts` builds the diff shown in the Changes view. For most files it diffs against `HEAD`: [1](#0-0) 

For `AppFileStatusKind.Renamed` files, it explicitly diffs against the index instead of `HEAD`, and the code comment self-documents the deviation: [1](#0-0) 

This means: "In order to show exactly what will end up in the commit we should perform a diff between the new file and the old file as it appears in HEAD. By diffing against the index we won't show any changes already staged to the renamed file which differs from our other diffs." In other words, any content that is already staged in the index for the renamed file (but not yet in HEAD) is silently excluded from the diff shown to the user - the user only sees changes made after the last `git add`.

This same, already-narrowed diff is what `applyPatchToIndex` (`app/src/lib/git/apply.ts`) uses to construct the partial-commit patch via `formatPatch`: [2](#0-1) 

Crucially, `applyPatchToIndex` resets the rename in the index by recreating it from the blob at `HEAD` (`ls-tree HEAD` + `update-index --add --cacheinfo`) and then applies the patch built only from the (index-relative) diff: [3](#0-2) 

The invariant that should hold - "the diff the user selected lines from is exactly the diff that ends up in the final commit" - is broken here in the same way the Seaport report describes: the component computing what to show/validate (`getWorkingDirectoryDiff`) and the component performing the actual state transition (index recreation + patch application in `applyPatchToIndex`) operate on different underlying bases (index vs. HEAD), and nothing reconciles the two. Existing guards (`isDiffTooLarge`, `isValidBuffer`, binary/submodule checks in `applyPatchToIndex`) only guard against size/type issues - they do nothing to ensure the diff base used for display matches the diff base needed for a correct, review-accurate commit.

### Impact Explanation
Because staged-but-not-yet-shown content on a renamed file is excluded from the reviewed diff, a user who partially selects lines to include in a commit can end up committing (and subsequently pushing) content they never saw and never explicitly selected. This is a silent corruption of what the user commits, matching the "Valid Impact" criterion for this exercise. A hostile scenario is plausible where a repository, tooling, or a script bundled with the cloned repo (e.g. a build step, git hook, or IDE integration the user is told to run) stages content into the index on a renamed path before the user opens Desktop's Changes view; the user then reviews only the unstaged delta, unaware that the previously staged content will also be committed by any commit action (full or partial) they take, because Git's commit operation itself always includes the full index, not just the working-directory diff that Desktop rendered.

### Likelihood Explanation
This path requires: (1) a file rename plus (2) content already staged in the index for that renamed file prior to Desktop computing its working-directory diff. Renames combined with partially-staged content are a common workflow when using external tools/CLI alongside Desktop (`git mv`, editors that auto-stage, IDE Git integrations), so the pre-condition is realistic without requiring local/physical access, admin rights, or social engineering beyond a user running Desktop against a repository/tooling combination they already trust. The deviation is also explicitly acknowledged as "the best kind of incorrect" in the code itself, indicating the developers were aware the two views of the diff could diverge but did not add a reconciliation or warning path.

### Recommendation
Ensure the diff base used for partial-commit patch construction always matches the diff base used for rendering, or vice versa: for renamed files, either (a) diff against `HEAD` consistently (matching the "should" behavior noted in the code comment) so any already-staged content is visible and selectable/deselectable by the user, or (b) if diffing against the index is kept for rename-recreation reasons, surface a warning in the UI when the index differs from HEAD for a renamed file, and refuse "partial" (line-level) commits in that state, forcing the user to review the full set of changes. In all cases, add an integration test asserting that the resulting commit content, for a renamed file with pre-staged content, exactly equals what the diff view displayed and the user selected.

### Proof of Concept
1. In an empty repo, create `foo` with `line1\n`, `add`+`commit`.
2. `git mv foo bar`.
3. Manually stage a change to `bar` outside of Desktop, e.g. `echo maliciousline >> bar && git add bar`.
4. Now further modify `bar` on disk (e.g. append a benign `line2`), without staging it.
5. Open Desktop: the Changes view calls `getWorkingDirectoryDiff` for the renamed `bar`, which diffs against the index — showing only the unstaged `line2` addition, not `maliciousline`.
6. The user reviews and selects only `line2` for partial commit.
7. `createCommit` → `applyPatchToIndex` recreates the rename from `HEAD` and applies the patch built from the same index-relative diff, but crucially the underlying `git commit` operation commits the full index, which already contains `maliciousline` from step 3.
8. Result: the commit (and any subsequent push) contains `maliciousline`, content the user never saw in the diff and never explicitly selected, confirming the diff-shown ≠ diff-committed mismatch analogous to the Seaport criteria-resolver bug.

Note: I was not able to run this repository's test suite/build in this environment to empirically confirm the exact resulting commit content, so this PoC is derived from static analysis of `getWorkingDirectoryDiff`, `applyPatchToIndex`, and `formatPatch` and their documented behavior; a Devin session with terminal access would be needed to execute and confirm it end-to-end.
