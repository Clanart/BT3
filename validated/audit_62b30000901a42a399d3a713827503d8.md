### Title
Unbounded EIP-7702 authorization-list loop runs under an infinite gas meter in the EVM ante handler - ([File: x/evm/ante/preprocess.go])

### Summary
`EVMPreprocessDecorator.AnteHandle` installs an infinite gas meter for EVM transactions and then calls `associateAuthorizationAuthorities`, which iterates over every entry in a `SetCodeTx`'s (EIP-7702) authorization list, performing signature recovery and a KV read/write per entry, with no bound on the number of authorizations and no gas charged for the work.

### Finding Description
In `x/evm/ante/preprocess.go`, `EVMPreprocessDecorator.AnteHandle` first calls `Preprocess`, then immediately replaces the gas meter with an infinite one: [1](#0-0) 

with the comment that "EVM handles gas checking from within." It then unconditionally calls `p.associateAuthorizationAuthorities(ctx, msg, associateHelper)` before handing off to `next` (which is where `NewBasicDecorator`—responsible for intrinsic-gas/size validation—runs): [2](#0-1) 

`associateAuthorizationAuthorities` unpacks the tx data, and if it is a `SetCodeTx`, loops over `ethTx.SetCodeAuthorizations()` with no cap on the number of tuples processed. For each authorization it calls `helpers.AuthorityToPreAssociate` (which recovers the authority's address/pubkey from its ECDSA signature — a `chainId`/`nonce`/state-based check per the comment, meaning it performs real signature recovery for every tuple) and then does a `ctx.CacheContext()` + `AssociateAddresses` (state reads/writes) per matching entry: [3](#0-2) 

Because this loop executes:
1. under the infinite gas meter installed at line 65 (so none of this CPU/storage work is priced or capped by gas), and
2. before `NewBasicDecorator`'s intrinsic-gas/size checks run (`EVMPreprocessDecorator` precedes `NewBasicDecorator` in the EVM ante chain in `app/ante.go`),

an attacker can submit a single `SetCodeTx` (EIP-7702) with an authorization list sized up to whatever the node's transaction-size limit allows, and every node that runs the ante handler (in `CheckTx` and `DeliverTx`, for every validator and full node) is forced to perform an unbounded amount of uncharged ECDSA-recovery and KV-store work before the transaction can even be rejected for insufficient gas or oversized intrinsic gas.

This is the sei-chain analog of the reported bug class ("functions can reach block gas-limit via unbounded operations… inadequate size validation of arrays… loops iterating over dynamic data structures"): here the unbounded per-item loop is not just costly to the sender, it runs completely unmetered (infinite gas meter) and ahead of the size/gas validation step, so the cost is imposed on every node in the network for free.

### Impact Explanation
A single crafted EVM transaction can force ante-handler processing (executed on `CheckTx` for every node's mempool admission and again on `DeliverTx`/block validation for every validator) to perform an unbounded number of secp256k1 signature-recovery operations and state reads/writes, with zero gas charged for this work because it happens under `sdk.NewInfiniteGasMeterWithMultiplier`. This can materially delay ante-handler processing across the validator set for a single (or repeated) transaction, risking block-processing delay beyond the 2.5-second threshold, at negligible cost to the attacker (the tx can ultimately be rejected for insufficient intrinsic gas after the expensive work has already been performed).

### Likelihood Explanation
Reachable by any unprivileged EVM transaction sender: constructing a `SetCodeTx` with EIP-7702 authorizations is a standard, public-RPC-reachable operation, requiring only that the attacker sign a large number of authorization tuples (which do not need to be otherwise valid/exploitable — `AuthorityToPreAssociate` simply needs to be reachable per entry, and even entries that fail the match are still scanned in the loop, and matching entries additionally trigger `AssociateAddresses`). The exact number of authorizations that fit in one transaction depends on the chain's configured maximum transaction size, which was not directly confirmed in this pass; this bounds but does not eliminate the issue.

### Recommendation
- Bound the number of authorization tuples processed in `associateAuthorizationAuthorities` (e.g., cap at a small constant, mirroring the `maxNestedMsgs` pattern used in `app/antedecorators/authz_nested_message.go`), rejecting or truncating transactions whose authorization list exceeds the cap.
- Move `associateAuthorizationAuthorities` (or at minimum the size/intrinsic-gas validation currently in `NewBasicDecorator`) to run before the infinite gas meter is installed and before any expensive per-authorization work, so oversized lists are rejected cheaply.
- Charge gas (from a real, non-infinite meter) for the ECDSA-recovery and store operations performed per authorization tuple, consistent with how go-ethereum's `IntrinsicGas` already accounts for `PerEmptyAccountCost`/`PerAuthBaseCost` per authorization.

### Proof of Concept
1. Craft a `MsgEVMTransaction` wrapping an EIP-7702 `SetCodeTx` whose `AuthorizationList` contains the maximum number of authorization tuples that fit within the node's transaction-size limit (each tuple is only a chain ID, address, nonce, and `v/r/s` — tens of bytes), each with a valid signature that recovers a distinct authority (they do not need to reference real/funded accounts).
2. Submit the transaction via the public EVM JSON-RPC (`eth_sendRawTransaction`).
3. Observe that `EVMPreprocessDecorator.AnteHandle` installs an infinite gas meter (`x/evm/ante/preprocess.go:65`) and then calls `associateAuthorizationAuthorities`, which loops over every authorization performing signature recovery via `helpers.AuthorityToPreAssociate` and, for matches, a `ctx.CacheContext()`/`AssociateAddresses` round trip — all before `NewBasicDecorator`'s intrinsic-gas check (which would otherwise reject the oversized tx) is reached, and all unmetered.
4. Repeat/batch such transactions to amplify per-block ante-handler CPU cost across the validator set at effectively zero gas cost to the attacker.

func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}
