### Title
Stale line-selection reused against a freshly re-fetched diff allows silent corruption of committed content - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop lets a user select individual diff lines (via a bit-vector `DiffSelection`, indexed by absolute line position within a specific `IDiff` snapshot) to build a partial commit. That selection is computed against the diff object that was rendered in the UI at some earlier point in time. When the commit is actually created, `applyPatchToIndex` does **not** reuse that same diff object — it independently re-fetches a brand-new diff from the working directory and applies the old selection indices to the new hunk structure. If the tracked file's content changes on disk between the time the diff was shown/selected and the time the commit executes, the index-based selection silently maps onto different lines in the new diff, producing a commit that does not match what the user reviewed and approved. This mirrors the reported bug class: two logically-coupled pieces of state (`diff` and `selection`) that are supposed to stay synchronized can diverge, and the divergence window is silently trusted rather than validated.

### Finding Description
- The UI computes and caches a diff for the selected file, and the user toggles inclusion of lines via `DiffSelection`, which stores selection as a bit-vector keyed by absolute line index within that diff's hunks: [1](#0-0) 
- When the diff is refreshed (e.g., a periodic repository refresh, or any background diff reload), the code recomputes the set of selectable lines and calls `withSelectableLines`, which preserves the existing selection state for indices that are still selectable — but it does not verify that the *content* at a given index is the same as when it was originally selected, only that the position is still a valid diff line: [2](#0-1) 
- At commit time, `stageFiles` calls `applyPatchToIndex` for every partially-selected file: [3](#0-2) 
- Critically, `applyPatchToIndex` re-fetches the diff **again**, from scratch, immediately before formatting the patch — this is a second, independent read of the working directory that is not guaranteed to be identical to the diff the user actually saw/selected against: [4](#0-3) 
- `formatPatch` then walks the hunks of this freshly-fetched diff and decides whether each line is included based on `file.selection.isSelected(absoluteIndex)` — i.e., it trusts that the index positions in the new diff still correspond to the same logical lines the user selected in the old diff: [5](#0-4) 
- `createCommit` orchestrates this whole flow (`unstageAll` → `stageFiles` → `git commit`) without any check that the working tree content is unchanged since the diff was last displayed to the user: [6](#0-5) 

The invariant that is supposed to hold — "the diff object backing the user's line selection is the same diff object used to build the committed patch" — is not enforced. `getWorkingDirectoryDiff` is called at two different times (UI render time and commit time) against a mutable working directory, and the intervening `DiffSelection` bit-vector is blindly reapplied to whatever hunks come back the second time.

### Impact Explanation
This directly matches the "silent corruption of what the user commits or pushes" impact category. A user who carefully reviews a diff, deliberately excludes certain lines from a commit (e.g., excluding a secret, a debug statement, or an unwanted change), can end up committing and pushing content they never intended to include — or omitting content they meant to include — without any warning, if the file on disk changes between diff-display time and commit time. Because Desktop applies the patch with `git apply --cached` and then commits directly, there is no secondary diff-review step immediately before the actual `git commit` invocation to catch the mismatch.

### Likelihood Explanation
The file content is not required to be attacker-modified through "local/physical access" in the excluded sense — the working directory of a cloned/fetched repository is exactly the kind of attacker-influenced surface this analysis targets. Any mechanism that mutates tracked files between the diff render and the commit click is sufficient: git smudge/clean filters, `.gitattributes`-driven filters, LFS pointers being resolved, submodule/worktree operations, or any other content-mutating hook wired into the repository and triggered by routine Desktop operations (checkout, pull, branch switch, background refresh) that a malicious repository can configure. Because Desktop performs periodic background refreshes (`_refreshRepository`) and diff reloads while the Changes view stays open, the race window between diff snapshot and commit is realistically reachable during normal use, not a contrived edge case.

### Recommendation
- Have `applyPatchToIndex` (and `stageFiles`/`createCommit`) reuse the exact `IDiff` object the selection was made against (already available on `WorkingDirectoryFileChange`/`changesState.selection.diff`) instead of independently re-fetching a new diff from disk immediately before applying the patch.
- If a fresh diff must be fetched at commit time for correctness (e.g., to avoid staging stale content), compare it against the diff used for the selection (e.g., by hash of `diff.text` or of the underlying blob) and, on mismatch, abort staging that file and force the user to re-review the diff before committing rather than silently reapplying old line indices to new hunk positions.

### Proof of Concept
1. Open a repository in GitHub Desktop and modify `file.txt`, producing a diff with hunks A and B.
2. In the Changes view, select only the lines belonging to hunk A for inclusion (leave hunk B unselected). Do not commit yet.
3. While the commit message box is open (before clicking "Commit"), have an external process (e.g., a git clean/smudge filter, LFS filter, or any script triggered by a repository-configured hook while Desktop performs a background refresh) rewrite `file.txt` so that the line offsets/hunks shift (e.g., insert new lines above hunk A).
4. Click "Commit". `applyPatchToIndex` re-fetches the diff (now with shifted hunks) and calls `formatPatch` using the stale `DiffSelection` bit-vector computed against the old hunk layout.
5. Inspect the resulting commit: the staged/committed lines no longer correspond to the lines the user actually selected in the UI (e.g., unrelated lines get included, or the intended exclusion no longer applies), demonstrating silent corruption of the commit contents without any warning presented to the user.
