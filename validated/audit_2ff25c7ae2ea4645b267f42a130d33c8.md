### Title
Symlink escape in working-directory image/text preview bypasses the `resolveWithin` sandbox used elsewhere - ([File: app/src/lib/git/diff.ts])

### Summary
GitHub Desktop added a `resolveWithin()` helper (`app/src/lib/path.ts`) specifically to stop path-traversal/symlink escapes when repository-relative paths from attacker-controlled repo content are turned into filesystem operations. It is correctly used in `buildConflictContext()` (`app/src/lib/copilot-conflict-context.ts:390-407`) before reading conflicted files. However, two other code paths that read working-directory file contents by joining `repository.path` with an attacker-supplied `file.path` do **not** use this guard: `getWorkingDirectoryImage()` in `app/src/lib/git/diff.ts:926-937` and `getNewFileContent()` in `app/src/ui/diff/syntax-highlighting/index.ts:81-105`. This is the same class of bug as the report's seed issue: one code path got the correct fix/guard, a sibling code path performing the analogous operation on attacker-influenced input did not.

### Finding Description
`getWorkingDirectoryImage()`:
```ts
export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  ...
``` [1](#0-0) 

and `getNewFileContent()`:
```ts
if (file instanceof WorkingDirectoryFileChange) {
    return readPartialFile(
      Path.join(repository.path, file.path),
      0,
      MaxHighlightContentLength - 1
    )
``` [2](#0-1) 

both build the on-disk path with a plain `Path.join()` and read it directly, with no traversal/symlink check. `file.path` is a repository-relative path taken from `git status` (`WorkingDirectoryFileChange`), which is fully attacker-controlled when the user clones or checks out a hostile repository: git tracks symlinks (mode `120000`), so a repo can contain a tracked or untracked entry, e.g. `notes.png`, that is actually a relative symlink such as `../../../../.ssh/id_rsa` or `../../../../AppData/Roaming/…`. When materialized in the working directory this symlink resolves outside the repository root.

Compare this to the guarded path in `buildConflictContext()`, which explicitly calls `resolveWithin(workingDirectory, file.path)` and rejects the read if the resolved path escapes the repo root:
```ts
absolutePath = await resolveWithin(workingDirectory, file.path)
...
if (absolutePath === null) { ... skippedReason: 'File path is outside the repository' }
``` [3](#0-2) 

`resolveWithin()` itself is implemented specifically to defeat this exact symlink-escape scenario, as its own unit tests demonstrate:
```ts
it('fails for paths that use a symlink to traverse outside of the root', async () => {
  ...
  await symlink(resolve(tempDir, '..', '..'), symlinkPath)
  assert((await resolveWithin(tempDir, symlinkName)) === null)
``` [4](#0-3) 

Because `getWorkingDirectoryImage` and `getNewFileContent` never call `resolveWithin`, `readFile`/`readPartialFile` will transparently follow the symlink to whatever path it points at (subject to normal OS filesystem permissions of the running user), and the resulting bytes are treated as image/text content and rendered in the Changes/History diff viewer.

### Impact Explanation
An attacker who gets a victim to clone or fetch a repository (a fully unprivileged, remote-content-only primitive) can plant a symlinked "file" in the working tree that points at a sensitive file outside the repository (SSH keys, cloud credential files, other local documents). Simply selecting that file in the Changes list (to preview the image diff or text diff/syntax highlighting) causes Desktop to read the target file's bytes off disk and display them in the UI — a file read outside the repository boundary, i.e. disclosure of local file contents the user never intended to expose, driven entirely by content the attacker controls in the untrusted repo. This matches the "file … read outside the repo" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high for any user who opens a cloned/fetched malicious repository in Desktop and looks at its Changes/diff view for a new/untracked file — a completely normal workflow, no unusual steps required. The only precondition is that the relative symlink target, once resolved from the file's location in the working tree, escapes the repo root (trivial to craft, e.g. `../../../../.ssh/id_rsa`), and that the OS/user permissions allow reading the target (true for the user's own files).

### Recommendation
Route both `getWorkingDirectoryImage()` (`app/src/lib/git/diff.ts:926-937`) and the working-directory branch of `getNewFileContent()` (`app/src/ui/diff/syntax-highlighting/index.ts:89-94`) through the same `resolveWithin()`/`resolveWithinPosix`/`resolveWithinWin32` helper already used in `buildConflictContext()`, rejecting (or treating as "cannot be read") any resolved path that lands outside `repository.path`, exactly as done for Copilot conflict resolution.

### Proof of Concept
1. Attacker creates a repository containing an untracked/new entry `preview.png` that is actually a symlink: `ln -s ../../../../.ssh/id_rsa preview.png` (relative depth chosen so that, once the repo is cloned into a typical location such as `~/Documents/GitHub/<repo>/preview.png`, the target resolves to `~/.ssh/id_rsa`).
2. Victim clones the repository with GitHub Desktop and opens the Changes list; `preview.png` appears as a new file.
3. Victim clicks the file to preview it. Desktop calls `getWorkingDirectoryImage(repository, file)`, which executes `readFile(Path.join(repository.path, 'preview.png'))` — the OS follows the symlink and returns the contents of `~/.ssh/id_rsa`, which Desktop then attempts to render as an image (or, for a text file target, `getNewFileContent` would feed the private key content straight into the syntax-highlighted diff view).
4. No `resolveWithin` check exists on this path (unlike `buildConflictContext`), so the read succeeds and the sensitive file's bytes are exposed inside the Desktop UI, confirming the missing guard.

(Note: I was not able to fully inspect the implementation of `readPartialFile` in `app/src/lib/file-system.ts` within the available search results, so I cannot confirm whether it independently applies any additional safety check beyond a straightforward partial read; based on `getNewFileContent`'s call site and the absence of any `resolveWithin` call around it, no such check appears to exist.)
