Based on my investigation, I found a strong analog to the CVE-2022-21741 division-by-zero bug class in Kaia's KIP-71 base fee calculation.

### Title
Division by zero in `NextMagmaBlockBaseFee` when governance `GasTarget` is set to 0 - (File: params/kip71_config.go)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter without checking that it is non-zero, mirroring the TFLite pattern where a user/governance-controlled divisor is used in a division without a zero-check.

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee using `gasTarget := kc.GasTarget` taken directly from `KIP71Config` [1](#0-0) . In both the "gas used above target" and "gas used below target" branches, the code performs `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` [2](#0-1)  and an analogous division in the decrease branch [3](#0-2) . Unlike `BaseFeeDenominator`, which has an explicit zero-guard that substitutes a fallback value of 64 [4](#0-3) , `GasTarget` has no such guard. `math/big.Int.Div` with a zero divisor triggers a Go runtime panic (division by zero), unlike normal integer division which the language itself would catch at compile time only for constants.

The `GasTarget` value is a governance parameter (`reward.kip71.gastarget` / `Kip71GasTarget`) that can be modified by an on-chain governance vote, and it also appears in the governance parameter table used to validate/canonicalize votes [5](#0-4) . I was unable to fully confirm the `FormatChecker` enforced for `Kip71GasTarget` in `kaiax/gov/param.go` (my last tool call to inspect it failed due to a regex/tool error and there were no further iterations available), so I cannot conclusively state whether governance vote validation currently rejects a `GasTarget = 0` proposal. If the format checker does not explicitly reject zero (unlike `Kip71BaseFeeDenominator`, which explicitly requires `v != 0` per its checker [6](#0-5) ), then a governance vote setting `GasTarget` to `0` would be accepted and would cause every node computing `NextMagmaBlockBaseFee` for the following block to panic.

### Impact Explanation
If reachable (i.e., if the governance vote pathway does not reject `GasTarget = 0`), the impact is severe: `NextMagmaBlockBaseFee` is called during header construction (`makeHeader`) and during Magma header verification for every single block once the Magma hardfork is active [7](#0-6) , and again by RPC fee-history/gas-price estimation logic [8](#0-7) . A panic here would crash block production and/or block validation across all full nodes and consensus nodes simultaneously — a chain-halting denial of service, which is more severe than the original TFLite CVE (a compute-node DoS) because it can render every honest node unable to progress the chain.

### Likelihood Explanation
The likelihood of reachability depends entirely on the governance parameter validation that I could not fully verify in the time available. If the `Kip71GasTarget` `FormatChecker` in `kaiax/gov/param.go` allows zero (unlike the `BaseFeeDenominator` checker, which explicitly rejects zero), then any governance-authorized voter (typically the governing node or CN committee, depending on `GovernanceMode`) could trigger this by voting to set `reward.kip71.gastarget = 0`. This requires governance/validator-level authorization rather than an arbitrary unprivileged transaction sender, which somewhat limits likelihood, but it is still a plausible "acceptance of a chain-breaking governance parameter" scenario in scope (governance parameters are explicitly listed as an in-scope area).

### Recommendation
Add an explicit zero-check/fallback for `GasTarget` in `NextMagmaBlockBaseFee`, mirroring the existing fallback logic already used for `BaseFeeDenominator` [4](#0-3) , and/or ensure the `Kip71GasTarget` governance parameter's `FormatChecker` explicitly rejects `0` the same way `Kip71BaseFeeDenominator`'s checker does [6](#0-5) .

### Proof of Concept
1. Confirm (this step requires code access I could not complete) whether `Kip71GasTarget`'s `FormatChecker` in `kaiax/gov/param.go` permits a value of `0`.
2. If permitted, submit and pass a governance vote (via the applicable `GovernanceMode`) setting `reward.kip71.gastarget = 0`.
3. Once the vote takes effect at the target block, any subsequent block header construction calls `chain.Config().Governance.KIP71.NextMagmaBlockBaseFee(parent.Number(), parent.Header().BaseFee, parent.GasUsed())` [7](#0-6) . With `GasTarget = 0` and any nonzero `parentGasUsed`, the code enters the "above target" branch and executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0` [2](#0-1) , causing a runtime panic in every node computing the header, halting block production/validation network-wide.

**Note on completeness:** I was unable to verify the `Kip71GasTarget` `FormatChecker` implementation before running out of tool iterations. This is the single missing piece needed to fully confirm exploitability — if that checker already rejects `v == 0` (as the `BaseFeeDenominator` checker does), this analog would not be practically reachable and this finding should be downgraded or dismissed accordingly.
