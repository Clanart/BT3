### Title
EVM native-token transfers bypass `x/bank`'s `SendEnabled`/`BlockedAddr` gating enforced only at the `MsgSend` layer - (File: `x/evm/state/balance.go`)

### Summary
The Arrakis report shows that a pause/permission gate enforced only at the `ArrakisV2Router` layer (`pause()`) is meaningless because the underlying vault's `mint()`/`burn()` can be called directly, bypassing the gate entirely. Sei-chain has the analogous structural flaw: `x/bank`'s `SendEnabled` and `BlockedAddr` restrictions are enforced only in the "router"-equivalent entry points (`MsgSend`/`MultiSend`/`SendCoinsFromModuleToAccount`), while the EVM's native-value transfer path calls the low-level "vault"-equivalent primitives (`AddCoins`, `SubUnlockedCoins`, `AddWei`, `SubWei`) directly, with no such checks.

### Finding Description
`x/bank`'s public message handlers gate transfers through `IsSendEnabledCoins` and `BlockedAddr`: [1](#0-0) [2](#0-1) 

These checks exist specifically to prevent funds from reaching module/blocked accounts outside expected state-machine rules, because doing so can break invariants and halt the chain, as the module's own spec documents: [3](#0-2) 

However, every EVM native-value transfer (a plain `msg.value` transfer, or any opcode that moves ether-equivalent balance) goes through `DBImpl.SubBalance`/`DBImpl.AddBalance`, which call the low-level bank primitives `SubUnlockedCoins`/`AddCoins` and `SubWei`/`AddWei` directly — bypassing `IsSendEnabledCoins` and `BlockedAddr` entirely: [4](#0-3) 

The only "blocked" check inside the EVM balance bridge is a narrow special case for the coinbase address prefix, not a general `BlockedAddr`/`SendEnabled` check: [5](#0-4) 

This is structurally identical to the Arrakis bug: `MsgSend`/`MultiSend` act as the "Router" enforcing `pause`-like restrictions (`SendEnabled=false`, `BlockedAddr`), while the EVM state-transfer bridge is the "vault" whose `mint()`/`burn()`-equivalent primitives (`AddCoins`/`SubUnlockedCoins`/`AddWei`/`SubWei`) have no restriction checks of their own, so any EVM transaction moving native value bypasses the restriction.

### Impact Explanation
If governance disables `SendEnabled` for the base denom (`usei`) — the closest on-chain equivalent of "pausing" transfers — or if `BlockedAddr` is configured to protect a sensitive module account, those protections only take effect for Cosmos-native `MsgSend`/`MsgMultiSend`/`SendCoinsFromModuleToAccount` calls. An EVM transaction that simply transfers value (`msg.value`) to the EVM address mapped to a blocked/module account will still succeed, because `AddBalance`/`SubBalance` call `AddCoins`/`SubUnlockedCoins`/`AddWei`/`SubWei` directly without any `IsSendEnabledCoins` or `BlockedAddr` check. As the bank module's own documentation states, funds reaching blocked accounts outside expected rules can break state-machine invariants and halt the network — this satisfies the "permanent chain split / validator halt" impact bar.

### Likelihood Explanation
Any unprivileged EVM transaction sender can trigger this by sending a normal value transfer to an EVM address that resolves (via `GetSeiAddressOrDefault`) to a blocked or module Sei address, or simply by relying on ordinary EVM value transfers continuing to work while governance believes `SendEnabled=false` halts all `usei` movement. No special privileges, precompile access, or malicious infrastructure are required — a single crafted/ordinary EVM transaction is sufficient.

### Recommendation
Enforce `IsSendEnabledCoins` and `BlockedAddr` checks (or an equivalent EVM-aware variant) inside the EVM balance bridge (`DBImpl.SubBalance`/`AddBalance` and the `send`/`SetBalance` helpers in `x/evm/state/balance.go`), or route native-value EVM transfers through the same bank keeper entry points (`SendCoins`/`SendCoinsFromModuleToAccount`) that already apply these restrictions, so that a chain-level pause/blocklist cannot be bypassed simply by moving value through the EVM.

### Proof of Concept
1. Governance sets `x/bank` params so `SendEnabled` is `false` for `usei` (intending to halt all native-token movement), or configures `BlockedAddr` to protect a module account's Sei address.
2. A user attempts `bank.MsgSend` (or the `bank` precompile's `send`, which goes through `bankMsgServer.Send`) to move `usei` — this correctly fails with `ErrSendDisabled`/`ErrUnauthorized`. [6](#0-5) 
3. The same user instead sends a plain EVM transaction with non-zero `value` to the EVM address associated with the target Sei address (module/blocked account) or simply performs a normal value transfer.
4. `DBImpl.SubBalance`/`AddBalance` execute the transfer via `SubUnlockedCoins`/`AddCoins` and `SubWei`/`AddWei`, none of which check `IsSendEnabledCoins` or `BlockedAddr`, so the transfer succeeds despite the pause/blocklist. [7](#0-6)

	ctx sdk.Context, senderModule string, recipientAddr sdk.AccAddress, amt sdk.Coins,

	senderAddr := k.ak.GetModuleAddress(senderModule)
	if senderAddr == nil {
		panic(sdkerrors.Wrapf(sdkerrors.ErrUnknownAddress, "module account %s does not exist", senderModule))

	if k.BlockedAddr(recipientAddr) {

	}

## Blocklisting Addresses

The `x/bank` module accepts a map of addresses that are considered blocklisted
from directly and explicitly receiving funds through means such as `MsgSend` and
`MsgMultiSend` and direct API calls like `SendCoinsFromModuleToAccount`.

Typically, these addresses are module accounts. If these addresses receive funds
outside the expected rules of the state machine, invariants are likely to be
broken and could result in a halted network.

By providing the `x/bank` module with a blocklisted set of addresses, an error occurs for the operation if a user or client attempts to directly or indirectly send funds to a blocklisted account, for example, by using [IBC](http://docs.cosmos.network/master/ibc/).

func (s *DBImpl) SubBalance(evmAddr common.Address, amtUint256 *uint256.Int, reason tracing.BalanceChangeReason) uint256.Int {
	s.k.PrepareReplayedAddr(s.ctx, evmAddr)
	amt := amtUint256.ToBig()
	if amt.Sign() == 0 {
		return *ZeroInt
	}
	if amt.Sign() < 0 {
		return s.AddBalance(evmAddr, new(uint256.Int).Neg(amtUint256), reason)
	}

	ctx := s.ctx
	var oldBalance *uint256.Int
	if s.logger != nil && s.logger.OnBalanceChange != nil {
		oldBalance = s.GetBalance(evmAddr)
	}

	// this avoids emitting cosmos events for ephemeral bookkeeping transfers like send_native
	if s.eventsSuppressed {
		ctx = ctx.WithEventManager(sdk.NewEventManager())
	}

	// Hook for mock balances (no-op in production builds)
	s.ensureSufficientBalance(evmAddr, amt)

	usei, wei := SplitUseiWeiAmount(amt)
	addr := s.getSeiAddress(evmAddr)
	err := s.k.BankKeeper().SubUnlockedCoins(ctx, addr, sdk.NewCoins(sdk.NewCoin(s.k.GetBaseDenom(s.ctx), usei)), true)
	if err != nil {
		s.err = err
		return *ZeroInt
	}
	err = s.k.BankKeeper().SubWei(ctx, addr, wei)
	if err != nil {
		s.err = err
		return *ZeroInt
	}

	if s.logger != nil && s.logger.OnBalanceChange != nil && oldBalance != nil {
		newBalance := s.GetBalance(evmAddr).ToBig()
		oldBalance := new(big.Int).Add(newBalance, amt)
		s.logger.OnBalanceChange(evmAddr, oldBalance, newBalance, reason)
	}

	surplus := sdk.NewIntFromBigInt(amt)
	s.tempState.surplus = s.tempState.surplus.Add(surplus)
	s.journal = append(s.journal, &surplusChange{delta: surplus})
	return *ZeroInt
}

func (s *DBImpl) AddBalance(evmAddr common.Address, amtUint256 *uint256.Int, reason tracing.BalanceChangeReason) uint256.Int {
	s.k.PrepareReplayedAddr(s.ctx, evmAddr)
	amt := amtUint256.ToBig()
	if amt.Sign() == 0 {
		return *ZeroInt
	}
	if amt.Sign() < 0 {
		return s.SubBalance(evmAddr, new(uint256.Int).Neg(amtUint256), reason)
	}

	ctx := s.ctx

	if s.logger != nil && s.logger.OnBalanceChange != nil {
		oldBalance = s.GetBalance(evmAddr)

// IsSendEnabledCoins checks the coins provide and returns an ErrSendDisabled if
// any of the coins are not configured for sending.  Returns nil if sending is enabled
// for all provided coin
func (k BaseSendKeeper) IsSendEnabledCoins(ctx sdk.Context, coins ...sdk.Coin) error {
	for _, coin := range coins {
		if !k.IsSendEnabledCoin(ctx, coin) {
			return sdkerrors.Wrapf(types.ErrSendDisabled, "%s transfers are currently disabled", coin.Denom)
		}
	}
	return nil
}

// BlockedAddr checks if a given address is restricted from
// receiving funds.
func (k BaseSendKeeper) BlockedAddr(addr sdk.AccAddress) bool {
	if len(addr) == len(CoinbaseAddressPrefix)+8 {
		if bytes.Equal(CoinbaseAddressPrefix, addr[:len(CoinbaseAddressPrefix)]) {
			return true
		}
	}
	return k.blockedAddrs[addr.String()]
}
