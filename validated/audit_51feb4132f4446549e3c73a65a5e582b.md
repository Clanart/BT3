### Title
Quadratic Lagrange interpolation complexity on attacker-controlled threshold parameters - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts the `t`/`n` fields of an untrusted serialization and, via `ThresholdKeys::new`, performs Lagrange `interpolation_factor` for each participant `1..=t`, where each factor computation is itself `O(t)`. This produces `O(t²)` field multiplications plus `t` inversions on data derived from attacker-controlled bytes — the Serai analog of the CVE-2021-43854 (ReDoS/CWE-400) class: superlinear work triggered by a modest public input.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` as raw `u16`s, then reads exactly `n` verification-share points, and calls `ThresholdKeys::new` [1](#0-0) .

`ThresholdKeys::new` computes the group key by summing `verification_shares[i] * interpolation_factor(i, t_set)` for every participant in `t = 1..=params.t()` [2](#0-1) .

`Interpolation::interpolation_factor` for `Lagrange` iterates the entire `included` vector (length `t`) per call, performing field multiplications and one inversion [3](#0-2) . There is no memoization: each of the `t` outer iterations recomputes an `O(t)` numerator/denominator product and a fresh inversion of attacker-influenced denominators, for `O(t²)` multiplications and `O(t)` inversions total.

The same quadratic shape exists in `ThresholdKeys::view`, which calls `interpolation_factor` once per included signer [4](#0-3) , but `read`/`new` is the cleaner attacker entry point since it requires no prior key material.

`ThresholdKeys::read` is explicitly on the list of deserialization APIs reachable with untrusted bytes, so an unprivileged party supplying crafted key bytes sets the loop bounds.

### Impact Explanation
With `t = n = u16::MAX` (65535), deserialization requires `n` group elements (~32 bytes each for Ristretto/Ed25519; ~2–4 MB total input) and then executes ~4.3×10⁹ scalar multiplications plus 65535 field inversions before returning. Each inversion is itself ~256 squarings/multiplications. A sub-4MB input therefore stalls a single-threaded caller for an extended period — quadratic/exponential work relative to input size, matching CWE-400. A service that deserializes `ThresholdKeys` from peer- or user-supplied data (key import, recovery material upload, processor-side `VerifyBlame`-style paths that `read` prior-round messages) can be denied service without any secret leakage, collusion, or protocol role.

### Likelihood Explanation
Reachability depends on an integration feeding unauthenticated bytes to `ThresholdKeys::read` (or constructing `ThresholdKeys::new` with remote `t`/`n`/`verification_shares`, e.g., after receiving `n` points). The input cost to the attacker is small (a few MB), the work induced is `O(n²)`, and no cryptographic validity is needed — invalid shares still drive the full loop before `ThresholdKeys::new` returns. Because `t`/`n` are capped at `u16`, the blowup is bounded rather than truly unbounded, which tempers severity relative to the NLTK regex case; this is a Medium DoS analog, not High.

### Recommendation
- Precompute the Lagrange denominator/numerator products once per `included` set (or use an `O(t)` prefix/suffix product construction) instead of recomputing `interpolation_factor` per participant in `ThresholdKeys::new` and `ThresholdKeys::view`.
- Alternatively/ additionally, bound or rate-limit `t`/`n` at the `read` boundary, and perform share-count/size validation before any interpolation work.

### Proof of Concept
```rust
use std::io;
use std::time::Instant;

// On any Ciphersuite C in-scope (e.g., Ristretto, Ed25519):
// Craft a serialized ThresholdKeys claiming t = n = u16::MAX with Lagrange interpolation.
let n: u16 = u16::MAX;
let mut buf = vec![];
// C::ID
buf.extend_from_slice(&(C::ID.len() as u32).to_le_bytes());
buf.extend_from_slice(C::ID);
// t, n, i
buf.extend_from_slice(&n.to_le_bytes());      // t = 65535
buf.extend_from_slice(&n.to_le_bytes());      // n = 65535
buf.extend_from_slice(&1u16.to_le_bytes());   // i = 1
buf.push(1); // Interpolation::Lagrange
// secret_share
buf.extend_from_slice(C::F::ZERO.to_repr().as_ref());
// n verification shares (any validly encoded points, e.g., generator)
for _ in 0 .. n {
  buf.extend_from_slice(C::generator().to_bytes().as_ref());
}

let start = Instant::now();
// ~4.3e9 field multiplications + 65535 inversions for a ~2-4 MB input
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
println!("elapsed: {:?}", start.elapsed());
```

Contrast with `Interpolation::Constant` or small `t`, where the same code is linear. Nothing in `ThresholdKeys::new` short-circuits the per-participant `O(t)` interpolation loop regardless of share validity.
