### Title
Unvalidated `Participant` index in PedPoP blame path causes a panic (remote DoS) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` take an attacker-influenced `sender: Participant` and use it as a raw `HashMap` index (`self.commitments[&sender]`) without checking membership. `Participant` is any non-zero `u16` (`1..=65535`), while the `commitments` map only contains entries for the `1..=n` participants whose `Commitments` messages were received. Passing a participant index absent from the map panics via implicit `Index` on `HashMap`, crashing the calling process. This mirrors CVE-2024-33667: an unsanitized, externally supplied selector is dispatched into a fatal code path instead of being validated against an allowlist.

### Finding Description
`Participant::new` accepts any non-zero `u16` (`crypto/dkg/src/lib.rs:29-35`), so indices greater than `n` are representable. `BlameMachine` is constructed from a `HashMap<Participant, Vec<C::G>>` of commitments (`crypto/dkg/pedpop/src/lib.rs:536-540`). During blame resolution, `blame_internal` first attempts `decrypt_with_proof`, then — for the share-verification branch — indexes the map directly: [1](#0-0) 

`self.commitments[&sender]` panics when `sender` is not a key of the map. The earlier `InvalidSignature`/`InvalidProof` returns (lines 584-587) blame `sender`/`recipient` gracefully only when decryption fails first; if the supplied `msg`/`proof` verify (or decrypt reaches share verification), the unchecked indexing is hit. Note `blame` takes `self` and re-wraps as `AdditionalBlameMachine` (`crypto/dkg/pedpop/src/lib.rs:623-632`), so the same unchecked index is reachable on every subsequent `AdditionalBlameMachine::blame` call.

The only validation present is in `polynomial` (`assert!(l != F::ZERO)`, `crypto/dkg/pedpop/src/lib.rs:211`), which is guaranteed by `Participant` being non-zero and does not bound the index against `n` or the commitments map.

### Impact Explanation
The panic unwinds/aborts the host task processing the blame protocol. In a threshold-network deployment, key-gen and blame handling run inside the node's message loop, so a crash takes down the participant process — a remote denial of service on an availability-critical signing component, matching the CVE's `A:H` impact. Because `blame` consumes `self` and forces protocol abort on any fault, a panic here also destroys the ability to complete or attribute blame correctly.

### Likelihood Explanation
The accusing/`accused` participant index in a blame flow originates from a protocol message (e.g., a `VerifyBlame`-style request), i.e., public input an unprivileged or minimally-privileged party controls. Nothing in `blame`, `blame_internal`, or `AdditionalBlameMachine` checks `u16::from(sender) <= n` or `commitments.contains_key(&sender)` before indexing. A malicious or malformed accusation naming a non-existent participant index (e.g., `Participant(n+1)`, or a participant whose `Commitments` were never delivered) deterministically hits the panic whenever the code path reaches share verification. It does not require collusion, a threshold of malicious parties, or leaked key material — only the ability to trigger a blame evaluation with an out-of-map index.

### Recommendation
In `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-609`), validate `sender`/`recipient` against `self.commitments` before indexing: return a defined fault result (or a dedicated error variant) when `self.commitments.get(&sender)` is `None`, rather than indexing with `[]`. The same check should be applied in `AdditionalBlameMachine::blame`/`new`, and `AdditionalBlameMachine::new` should reject commitment maps missing expected participant indexes. The analogous hardening in the CVE was an allowlist on dispatched method names; here the allowlist is the set of committed participants.
