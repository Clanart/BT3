### Title
GitHub API `clone_url` is silently trusted to rewrite the local `origin` remote before every push, allowing a compromised/malicious GitHub Enterprise endpoint to redirect the user's push destination and credentials - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`compound_xinit_pool_rewards` in the Cabal report mutates protocol-internal accounting (`m_store.staked_amounts`) from an external signal (claimed rewards) without ever re-validating that internal state against the real, authoritative source (`pool_router::get_real_total_stakes`), letting an attacker-influenced external event (slashing) silently desynchronize state that later governs a security-relevant calculation (mint ratio). The Desktop analog is `updateRemoteUrl`, which mutates the security-relevant local git configuration (the `origin` remote URL that later `git push`/`git fetch` operations, and credential-helper lookups, are based on) purely from an external signal — the GitHub API's `clone_url` field — without any independent verification or user confirmation, and this happens automatically on every push.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` [1](#0-0) , which is called unconditionally at the start of every push via `_push` → `withRefreshedGitHubRepository` [2](#0-1) . The function fetches the repository object from the GitHub API (`api.fetchRepository(owner, name)`) and, if the returned `apiRepo.clone_url` differs from the currently configured local remote while "looking like" a legitimate rename (same protocol, and the *previously cached* `gitHubRepository.cloneURL` still matches the local remote), calls `gitStore.setRemoteURL(...)` to rewrite `origin` on disk with **no user confirmation dialog**: [3](#0-2) 

The only safety checks are:
1. `protocolsMatch` — compares URL *scheme* only, not host/owner/name.
2. `remoteUrlUnchanged` — compares the *cached* `gitHubRepository.cloneURL` (itself derived from a prior, equally-unverified API response) against the current remote.
3. `!urlsMatch` — the new API value differs from the current remote.

None of these checks independently verify that the entity behind `owner/name` is the same trusted repository the user originally cloned — they only check "did the API's opinion of the URL change," which is exactly the kind of unverified external state Cabal's bug pattern warns about (updating an internal value based on an external claim instead of syncing against ground truth). For GitHub Enterprise Server accounts, the "external claim" is whatever that self-hosted `/repos/{owner}/{name}` endpoint returns, and Desktop applies it directly to `git remote set-url` without asking the user. This is the same root cause: internal state that gates a downstream security-relevant computation is refreshed from an unauthenticated/lightly-validated external signal instead of the true ground truth (in git terms, the ground truth would be "the remote configured explicitly by the user"), and no confirmation gate exists.

### Impact Explanation
Because `updateRemoteUrl` runs immediately before `performPush` on every push, and `performPush` derives the actual push target from `repositoryStateCache`'s `remote` (fed by `gitStore.currentRemote`) [4](#0-3) , a manipulated `clone_url` from a compromised/MITM'd GHES instance (or any scenario where an attacker can influence what the configured API endpoint returns for the tracked `owner/name`) causes Desktop to silently repoint `origin` and then push the user's commits — and authenticate against that new remote using the stored credential/OAuth token — to an attacker-controlled git host. This matches the "attacker controls ... a git remote/proxy response" and "silent corruption of what the user commits or pushes" categories: the corrupted value is the local git remote URL (`origin`), and the guard rails (`protocolsMatch`, cached-URL comparison) only validate superficial properties of the untrusted API response, not its trustworthiness.

### Likelihood Explanation
Exploitation requires the attacker to control or tamper with the API response for the repository's `owner/name` on the account's configured endpoint (realistic for compromised/malicious GHES deployments, or MITM against a GHES without proper TLS validation) — no local access, no leaked credentials, and no unusual user action beyond a normal `git push` from Desktop, which happens routinely. This keeps it within the allowed "unprivileged... GitHub API object" attacker model even though it depends on a non-dotcom API trust boundary, which somewhat limits likelihood versus a github.com-only attack.

### Recommendation
Never silently rewrite `origin` from API data. At minimum:
- Require explicit user confirmation before calling `gitStore.setRemoteURL` when the GitHub API's `clone_url` diverges from the configured remote.
- Verify repository identity via a stable identifier (e.g., the numeric GitHub repository `id`) rather than trusting `owner/name`/`clone_url` string comparisons, mirroring the report's recommendation to "sync with reality" via an authoritative source rather than accumulating unverified external state.

### Proof of Concept
1. User adds a GitHub Enterprise Server account in Desktop and has a repository cloned from `https://ghes.internal/org/repo.git`.
2. Attacker compromises the GHES instance (or performs a MITM against it) and makes `GET /api/v3/repos/org/repo` return a crafted `clone_url` such as `https://ghes.internal/org/repo-fork.git` pointing at an attacker-controlled repository with the same protocol/host but different owner/name path, or a wholly attacker-hosted URL sharing the scheme.
3. User clicks "Push" in Desktop. `_push` → `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository` fetches the tampered `apiRepo` [5](#0-4)  and calls `updateRemoteUrl`, which finds `protocolsMatch = true`, `remoteUrlUnchanged = true` (cached value still matches local remote), `urlsMatch = false`, and silently executes `gitStore.setRemoteURL(...)` [6](#0-5) .
4. `performPush` immediately pushes to the newly rewritten remote using the stored credentials [7](#0-6) , exfiltrating source code and authenticating with the user's token/credential against the attacker-controlled destination — with no dialog ever shown to the user.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
