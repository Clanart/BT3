### Title
Stale line-index selection silently reapplied to a re-fetched diff causes wrong content to be committed - (File: `app/src/lib/git/apply.ts`)

### Summary
The reported bug is a class of "frozen accounting value applied against a later, different state without re-validation": `freezeBuckets` locks an amount computed at repay-time, but a later withdrawal changes the pool balance without updating the locked amount, so a stale value is used against fresh state, causing incorrect results. GitHub Desktop has a structurally identical pattern in its partial-commit staging path: the user's line selection (`DiffSelection`, a set of absolute line indices) is computed against the diff shown at selection time, but `applyPatchToIndex` independently re-fetches the diff from disk at commit time and blindly reapplies the old index-based selection to it.

### Finding Description
When a user partially selects lines/hunks of a modified file to include in a commit, GitHub Desktop stores the selection as a `DiffSelection` keyed by absolute line index into a specific diff snapshot [3](#0-2) . The app's own code acknowledges that this index-based state can become invalid if the diff changes, and only partially remediates it by recomputing `selectableLines` when the UI reactively reloads a diff for the *currently selected* file [4](#0-3) .

However, this reconciliation only happens opportunistically as part of `updateChangesWorkingDirectoryDiff`, triggered on selection changes — it is not guaranteed to run before every commit. When the user actually commits, `createCommit` → `stageFiles` → `applyPatchToIndex` independently calls `getWorkingDirectoryDiff(repository, file)` again [5](#0-4) , fetching a brand-new diff of the file's current on-disk state. This new diff is then fed into `formatPatch`, which walks the new diff's hunks and checks `file.selection.isSelected(absoluteIndex)` for each line, using the index positions from the *old* diff snapshot the user actually reviewed [2](#0-1) .

If the file's on-disk content changes between the moment the user reviews/selects lines and the moment `git commit` actually runs (e.g., hunks shift because lines were added/removed elsewhere in the file by a background process, an editor autosave, a merge/rebase side effect, or content rewritten via a `clean`/`smudge` filter driven by a cloned repository's `.gitattributes`), the absolute line indices no longer correspond to the same logical lines. `formatPatch` will silently include or exclude lines that the user never reviewed, since there is no check that the diff used for staging is the same diff the selection was computed against — no hash/oid/text comparison guards this reapplication, unlike the analogous `updateChangesWorkingDirectoryDiff` staleness bail-outs for stash diffs at [6](#0-5) .

### Impact Explanation
This breaks the invariant that "what the user selected to commit is what gets committed." The corrupted value is the mapping between `DiffSelection`'s absolute line indices and the diff actually used to build the patch in `applyPatchToIndex`. A mismatch here causes silent corruption of what the user commits (and subsequently pushes), which is explicitly listed as a valid impact category — the user can unknowingly commit/push unreviewed content, or exclude content they intended to include, without any error being surfaced (`formatPatch` only throws if the resulting patch is completely empty, not if it diverges from the reviewed selection) [7](#0-6) .

### Likelihood Explanation
The comment left in the codebase directly documents the maintainers' own awareness that "the diff might have changed dramatically since last we loaded it" and that the fix implemented ("just updating the selectable lines") is a partial mitigation, not a full validation of selection correctness [8](#0-7) . The race window exists on every partial commit where the working tree file is touched by anything other than the exact `getWorkingDirectoryDiff` call the UI diff pane last used — a plausible occurrence when repository content is attacker-influenced (e.g., via `.gitattributes` clean/smudge filters, or files simultaneously touched by a build tool/editor while the user is reviewing a diff before clicking Commit).

### Recommendation
Before applying the stale `DiffSelection` to a freshly fetched diff in `applyPatchToIndex`, validate that the diff hasn't changed since the selection was computed (e.g., compare against a content hash/oid captured at selection time, or re-derive the patch from the same diff object used to render the UI instead of re-fetching). At minimum, abort the partial-stage operation and surface an error to the user rather than silently reapplying indices from a different diff.

### Proof of Concept
1. Modify a tracked file so it has multiple hunks; open it in GitHub Desktop's Changes view.
2. Select only specific lines within one hunk (leaving others unselected) — this computes a `DiffSelection` against the diff currently rendered.
3. Before clicking "Commit", cause the file's content to shift (e.g., an external process/editor inserts or removes lines elsewhere in the file, or a `.gitattributes`-driven clean filter rewrites content) without Desktop reloading the diff pane.
4. Click "Commit". `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` [5](#0-4)  and `formatPatch` reapplies the old absolute-index selection to the new hunks [2](#0-1) , producing a patch that stages/commits different lines than what the user actually reviewed and selected.
