### Title
Governance-settable `GasTarget = 0` causes division-by-zero panic in KIP-71 base fee calculation, halting block validation, tx pool acceptance, and block production - ([File: params/kip71_config.go])

### Summary
This is a direct analog of the reported bug class: an arithmetic formula that assumes a governance/config parameter is always non-zero/well-formed, but the input validation for that parameter does not enforce that assumption, causing the formula to trap/revert (here: Go's `big.Int.Div` panics on division by zero, equivalent to Solidity's underflow revert) and brick the affected functionality across the whole node.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` computes the Magma dynamic base fee using the formula (when `parentGasUsed > gasTarget`):
```
gasUsedDelta := parentGasUsed - gasTarget
x := parentBaseFee * gasUsedDelta
y := x.Div(x, gasTarget)          // <-- divide by gasTarget
baseFeeDelta := max(x.Div(y, baseFeeDenominator), 1)
``` [1](#0-0) 

The `gasTarget` value comes directly from the governance parameter `Kip71GasTarget` with no non-zero enforcement: [2](#0-1) 

Contrast this with the adjacent `Kip71BaseFeeDenominator` parameter, which explicitly rejects zero in its `FormatChecker`: [3](#0-2) 

`GasTarget` uses `noopFormatChecker`, so a governance vote (in `single` governance mode, submitted by the `GoverningNode` via a governance-vote transaction/header) can set `GasTarget` to `0` with no rejection.

Once `GasTarget == 0` is active and any block has `parentGasUsed > 0`, the "gas used above target" branch executes: `gasUsedDelta = parentGasUsed - 0`, then `x.Div(x, gasTarget)` where `gasTarget` is a `big.Int` set to `0`. `big.Int.Div` panics with "division by zero" in this case — this is the functional equivalent of the referenced report's Solidity underflow revert, except here it is a fatal Go panic rather than a caught `revert`.

This function is on the critical consensus and mempool path:
- Called during block header validation via `KIP71Config.VerifyMagmaHeader` in `blockchain/block_validator.go`.
- Called during block assembly/mining in `work/worker.go`.
- Called during transaction pool gas-price/base-fee bookkeeping in `blockchain/tx_pool.go`.
- Called by the fee-history/gas-price RPC oracle in `node/cn/gasprice/feehistory.go` (`processBlock`) and `node/cn/gasprice/gasprice.go`. [4](#0-3) 

Because this touches block validation and block production, once `GasTarget` is set to `0`, essentially every node that processes the very next block with nonzero gas usage panics, causing a chain-wide halt — a far more severe outcome than the referenced report's single-contract brick.

### Impact Explanation
A single governance parameter update setting `Kip71GasTarget = 0` will cause every full node (validators, RPC nodes) to panic/crash when validating or building the next block that uses gas above the target of 0 (i.e., essentially any block with transactions), because `NextMagmaBlockBaseFee` performs an unguarded `big.Int` division by `gasTarget`. This is a chain-halting denial of service affecting the entire network's consensus and RPC layer, not merely one contract as in the original report.

### Likelihood Explanation
Governance parameters in `single` mode are set by the `GoverningNode` via governance vote transactions/headers, and the format checker for `Kip71GasTarget` is a no-op (`noopFormatChecker`), unlike the sibling parameter `Kip71BaseFeeDenominator` which explicitly guards against zero. This asymmetry strongly suggests the zero-check was simply omitted for `GasTarget`, making this reachable by any actor capable of successfully casting/enacting a governance vote for this parameter (the standard reachable path for KIP-71 pricing parameter changes), with no additional preconditions once the vote is enacted.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check), and/or add a defensive `gasTarget == 0` guard inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` that returns a safe fallback (e.g., treats it like the existing `baseFeeDenominator == 0` fallback) instead of performing an unchecked division.

### Proof of Concept
1. Governance (in `single` mode, via the `GoverningNode`) submits a parameter vote setting `Kip71GasTarget = 0`, which is accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`: [2](#0-1) 
2. The vote is enacted into `ParamSet` and converted via `ToKip71Config()`: [5](#0-4) 
3. On the next block where `header.GasUsed > 0` (trivially satisfied by any transaction), `KIP71Config.NextMagmaBlockBaseFee` is invoked from block validation (`blockchain/block_validator.go`) with `kc.GasTarget = 0`. Since `parentGasUsed (>0) > gasTarget (0)`, execution reaches:
```go
y := x.Div(x, new(big.Int).SetUint64(gasTarget))  // gasTarget = 0
``` [6](#0-5) 
which panics with "division by zero" in Go's `math/big` package, crashing the validating node's process during consensus-critical block processing — analogous to how the original report's underflow made `getPrice` (and everything depending on it) permanently revert, but here causing a full node crash/chain halt instead of a single-contract revert.
