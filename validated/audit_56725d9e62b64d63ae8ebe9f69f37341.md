### Title
Deposits confirmed before a multisig key's activation block are permanently skipped by the Scanner — attacker can burn/devalue a deposit by front-running key registration - (File: processor/src/multisigs/scanner.rs)

### Summary
The external report describes a "pre-start" accounting asymmetry: deposits made before the vault starts accrue value that is silently withdrawn by an attacker, and the victim joining on the other side is left holding an unfair position. The Serai analog lives in the processor's block scanner: every registered multisig key carries an `activation_number`, and the scan loop iterates forward from the last scanned block, skipping a key for any block lower than its activation. The external deposit address (`p2tr_script_buf` of the group key) is deterministic and publicly derivable, so any unprivileged Bitcoin sender can broadcast a deposit to a not-yet-activated (or rotated-out) key and have it confirm in a block below `activation_number`. That output is spendable by the threshold key yet is never emitted as a `ScannerEvent::Block` output, so it is never credited nor scheduled — effectively burned, exactly mirroring "pre-start funds don't count" with the ordering manipulated by an outside party.

### Finding Description
`ScannerDb::register_key` persists each key with an `activation_number` supplied by the caller (the current latest block number at registration time, e.g. `network.get_latest_block_number()` as in `processor/src/tests/wallet.rs:56`). In `Scanner::run`, for each `block_being_scanned` the loop iterates `scanner.keys` and skips keys not yet active:

- `processor/src/multisigs/scanner.rs:550-553`: `if activation_number > block_being_scanned { continue; }`
- `processor/src/multisigs/scanner.rs:562-566`: only `network.get_outputs(&block, key)` results from the current block are collected.

The scan is strictly forward-only over `(ram_scanned + 1) ..= latest_block_to_scan` (`scanner.rs:492`), and once a block number is passed, no later pass revisits it for a newly activated key. The deposit address is deterministic: `Scanner::new` / `processor/src/networks/bitcoin.rs:314-347` derive `p2tr_script_buf(key)` plus fixed `hash_to_F("Serai Bitcoin Output Offset", …)` offsets for Branch/Change/Forwarded, all computable by anyone who knows the group key (which is public after keygen). `Bitcoin::get_outputs` (`processor/src/networks/bitcoin.rs:686-700`) only matches `tx.output[*].script_pubkey` via `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`), so a pre-activation payment produces a valid `ReceivedOutput` on-chain that the processor simply never sees.

### Impact Explanation
Funds are received by the threshold-controlled Taproot output but are never reported to the scheduler/attestation flow: no `ScannerEvent::Block` entry, no `save_outputs`, no credit. Because the output genuinely belongs to the multisig key, the BTC is recoverable only through out-of-band coordination; within protocol logic it is burned. An attacker who can observe a pending key registration (e.g., a new validator set / key rotation being scheduled) can race a deposit into an earlier block than `activation_number`, or trick a depositor into using a stale/pre-activation address, causing a guaranteed loss of credited funds — the same "deposit before start is worth nothing while appearing valid" shape as the honeypot report.

### Likelihood Explanation
Reachable by any unprivileged party sending a normal Bitcoin transaction: no mempool manipulation beyond ordinary broadcast timing, no collusion, no privileged access. The group key and hence the deposit script are publicly computable, so an attacker can pre-position or grief deposits whenever key activation is delayed or when a deposit address is published before its activation block is finalized. The window is narrow (a few blocks around activation/rotation), and impact is limited to funds sent in that window, keeping this at Medium rather than High.

### Recommendation
When a key is registered, scan deterministically from the block in which the key was *generated* (or from the earliest block that could contain the first published address), not from the registration-time block — or record `activation_number` as a lower bound with a bounded look-back rescan. At minimum, document that the deposit address must not be published or used before the activation block has passed and that pre-activation sends are unrecoverable, since the code itself cannot distinguish them after the fact.

### Proof of Concept
```text
1. Keygen completes; group key K is known. External address = p2tr_script_buf(K),
   computable by anyone via Scanner::new(K) (networks/bitcoin/src/wallet/mod.rs:162-166).
2. At block N-1, attacker (or a misinformed depositor) broadcasts a tx paying to that
   script_pubkey; it confirms in block N.
3. At block N, the processor calls register_key(txn, N, K) — activation_number = N.
   (Equal-height case also skipped only if activation recorded as N+1; for N-1 deposits
   the skip is unconditional.)
4. Scanner::run processes block N: activation_number == N, so key is scanned from N
   onward — but the deposit confirmed at block N-1 is in (ram_scanned+1)..=N only if
   ram_scanned < N-1; since scanning starts at the registration block, block N-1
   is never revisited (scanner.rs:492, 550-553).
5. The output satisfies scan_transaction's script match and would yield a valid
   ReceivedOutput with offset ZERO (mod.rs:199-214), yet no ScannerEvent::Block is
   emitted for it and save_outputs never stores it. The BTC sits at an address the
   multisig can sign for but the protocol never credits or schedules.
```
