Notably, `IntentGatewayV2` even imports `SafeERC20` and declares `using SafeERC20 for IERC20;` at the top of the Tron variant, yet its `withdraw()` function deliberately bypasses `safeTransfer` and uses a raw low-level `.call` with `abi.encodeWithSelector(IERC20.transfer.selector, ...)`, only checking that the *call itself* succeeded — not that the token's boolean return value was `true`.

### Title
Escrow withdrawal accepts non-reverting `transfer()` failures as success, permanently burning settlement accounting without moving funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` on the Tron deployment settles filled/refunded intents by decrementing escrow accounting and pushing tokens to the beneficiary via a raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`, checking only `success` (call did not revert) rather than validating the ABI-decoded boolean return value, unlike the sibling `IntentsBase._release`-style paths and the same file's own imports which use `SafeERC20.safeTransfer` elsewhere. [1](#0-0) [2](#0-1) 

### Finding Description
`withdraw()` is invoked from `onGetResponse` after a proof-verified query result, and settles escrowed order tokens to `beneficiary`: it marks `_filled[body.commitment] = beneficiary`, decrements `_orders[body.commitment][token]`, and for ERC20 tokens does:
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

This only guards against calls that revert. Any ERC20-like token that returns `false` on failure instead of reverting (a well-documented pattern, and the exact class of "does-not-behave-as-expected-recipient" risk the external report is about — a transfer target that cannot properly complete the expected token semantics) will make `success == true` while no tokens actually moved. The function will still emit `EscrowReleased`/`EscrowRefunded` and has already zeroed/decremented the escrow ledger and set `_filled[commitment]`, so the commitment is marked as permanently settled. The tokens remain trapped in the contract with no accounting entry pointing to them, and the rightful beneficiary receives nothing, with no retry path since `_filled` is now non-zero and further calls to `withdraw`/`fillOrder` for that commitment are rejected. The identical `SweepDust` branch in the same contract has the same unchecked-boolean pattern. [4](#0-3) 

By contrast, the canonical EVM `IntentsBase.sol` implementation of the same withdrawal logic uses `IERC20(token).safeTransfer(beneficiary, amount)`, which reverts the whole settlement atomically if the token returns `false`, preserving the escrow accounting and beneficiary's claim to the funds. [5](#0-4)  The Tron variant, despite importing and declaring `using SafeERC20 for IERC20`, does not apply it in this settlement path. [6](#0-5) 

### Impact Explanation
This is a direct fund-loss / double-settlement risk within the intent-settlement/bridge-custody surface called out in the impact gate: escrowed order tokens can be irreversibly marked as released/refunded (`_filled` set, escrow ledger zeroed) while the actual ERC20 transfer silently fails, leaving funds stuck in the `IntentGatewayV2` contract and unrecoverable by the beneficiary — a genuine "funds move to nobody" loss condition triggered purely by unprivileged, permissionless calls into `onGetResponse`/`withdraw` once a proof is delivered, with no reliance on a malicious relayer, prover, or admin.

### Likelihood Explanation
Likelihood depends on at least one settlement token used with the Tron `IntentGatewayV2` deployment implementing non-reverting failure semantics (return `false` instead of reverting) — a real and known ERC20 behavior class (older/legacy tokens, custom fee/pausable tokens, or partially-compliant Tron TRC20 tokens). Given the code was already set up to use `SafeERC20` elsewhere in the same contract, the raw `.call` bypass in `withdraw`/`SweepDust` appears to be an inconsistency rather than an intentional design choice, and is directly reachable through the normal fill/refund flow.

### Recommendation
Replace the raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with `IERC20(token).safeTransfer(beneficiary, amount)` (already imported and used via `using SafeERC20 for IERC20`), so that non-reverting `false`-returning tokens cause the entire settlement to revert instead of silently finalizing without moving funds.

### Proof of Concept
1. Deploy a mock TRC20/ERC20 token whose `transfer()` returns `false` on failure (e.g., insufficient allowance internally tracked, or simply a token designed to return `false` instead of reverting on any transfer past a cap) and fund the `IntentGatewayV2` escrow for an order with that token via the normal fill/order flow. [3](#0-2) 
2. Trigger the cross-chain refund/withdraw path (`onGetResponse` → `withdraw(body, true)`) for that commitment. [7](#0-6) 
3. Inside `withdraw`, the token's `transfer()` call returns `(true, abi.encode(false))` (call succeeds, but the encoded boolean is `false`); the code only inspects `success` from `.call`, so it passes the check, decrements `_orders[...]`, sets `_filled[commitment] = beneficiary`, and emits `EscrowRefunded`. [8](#0-7) 
4. Verify on-chain that the beneficiary's token balance did not increase, while `_filled[commitment]` is now permanently set and `_orders[commitment][token]` is zero — the tokens are stuck in the `IntentGatewayV2` contract with no code path left to claim them for that beneficiary/commitment.
