### Title
`reward.proposerupdateinterval` governance parameter accepts unbounded/zero values with no relation to `istanbul.epoch`, causing divide-by-zero style interval misuse in proposer scheduling - ([File: kaiax/gov/param.go], [File: kaiax/valset/impl/getter_proposers.go])

### Summary
The Sherlock finding shows that `BondBaseSDA.sol` derives `debtDecayInterval` from a user-supplied `depositInterval` (`* 5`) with **no upper-bound check against the total market duration** (`secondsToConclusion`), so the derived interval can exceed the window it is meant to operate within, breaking downstream ratio-scaling assumptions. The analogous Kaia pattern is the governance parameter `reward.proposerupdateinterval` (`RewardProposerUpdateInterval`), which is consumed as a divisor/step size in `getProposerList` to compute the proposer-schedule update boundary, yet its `FormatChecker` performs no validation whatsoever.

### Finding Description
`RewardProposerUpdateInterval` is defined with `FormatChecker: noopFormatChecker`, meaning any `uint64` value — including `0` or a value far larger than `istanbul.epoch` — passes format validation and can become the active governance value: [1](#0-0) 

This value flows into `ParamSet.ProposerUpdateInterval` and is directly used as the modulus/step for computing the proposer-list update block: [2](#0-1) 
and again to bound the vote-scanning window: [3](#0-2) 

`checkConsistency` in header governance explicitly whitelists `RewardProposerUpdateInterval` as a vote that "passes as long as it passes the format checks in `NewVoteData()`" — i.e., no additional cross-parameter consistency check (e.g., against `istanbul.epoch`) is performed: [4](#0-3) 

This is structurally identical to the reported bug class: an interval-like governance/economic parameter is accepted without validating it against the other bound it must respect (here, `istanbul.epoch`/total interval window, there, `secondsToConclusion`). Notably, the sibling parameter `RewardStakingUpdateInterval` is defended against the zero case only at genesis-time module `Init` (`staking.ErrZeroStakingInterval`), not for live governance updates: [5](#0-4) 
which shows the project is aware zero/degenerate intervals are dangerous, yet the mutable governance-vote path (`RewardProposerUpdateInterval`, and possibly `RewardStakingUpdateInterval` post-genesis) bypasses this safeguard entirely.

### Impact Explanation
If `ProposerUpdateInterval` is set to `0` (or to a pathological value) via a governance vote, `roundDown(c.num-1, uint64(c.pset.ProposerUpdateInterval))` in `getProposerList` operates on a zero/invalid interval. Depending on the exact implementation of `roundDown` (not directly inspected in this pass), this can cause a division/modulo-by-zero panic in the block-processing path used by every consensus node to compute the proposer schedule, or produce a schedule that diverges from what other clients compute if the interval interacts inconsistently with `istanbul.epoch`. Either outcome — a crash during header/block processing, or a proposer-schedule computation that differs between nodes — falls squarely into "state divergence between honest nodes" or "acceptance of an invalid block," since `getProposerList` output feeds into the committee/proposer verification consensus performed on every node.

### Likelihood Explanation
Reaching this requires a `reward.proposerupdateinterval` governance vote to be accepted and take effect, which in "single" governance mode is restricted to the governing node, and post-Kore can route through contract-based governance. This is a privileged rather than a fully public/unprivileged path, so likelihood is lower than a plain user-facing bug, but governance parameters are explicitly called out as an in-scope component, and the complete absence of a `FormatChecker` (unlike siblings such as `Kip71BaseFeeDenominator`, which enforces non-zero) indicates the validation gap is a genuine oversight rather than an intentional design choice.

### Recommendation
Add a non-zero (and reasonably bounded, e.g., must divide evenly into or be no larger than `istanbul.epoch`) `FormatChecker` for `RewardProposerUpdateInterval` (and reconsider `RewardStakingUpdateInterval`) analogous to the `Kip71BaseFeeDenominator` non-zero check, and add a `checkConsistency` case in `kaiax/gov/headergov/impl/header.go` that rejects votes setting `RewardProposerUpdateInterval` to `0` or to a value inconsistent with `istanbul.epoch`, mirroring the recommended `require(debtDecayInterval <= secondsToConclusion, ...)` pattern from the original report.

### Proof of Concept
1. In single governance mode, have the governing node (or, post-Kore, the authorized contract-governance path) submit a vote setting `reward.proposerupdateinterval` to `0`.
2. Once the vote is accepted (passing only the no-op `FormatChecker`), the new `ParamSet.ProposerUpdateInterval` becomes `0` for subsequent blocks.
3. On the next block whose proposer list must be (re)computed, `getProposerList` calls `roundDown(c.num-1, uint64(c.pset.ProposerUpdateInterval))` with `ProposerUpdateInterval == 0`, and `getRemoveVotesInInterval`/`scanBlocks` iterate `for i := pUpdateNum; i < pUpdateNum+0; i++` (a no-op range) while `roundDown` with a zero divisor is the primary risk point.
4. Exact runtime behavior of `roundDown` when passed `0` was not directly confirmed in this pass (source not retrieved) — this should be verified by a background engineer to confirm whether it panics (crash/DoS across all nodes) or silently returns an incorrect value (schedule divergence), and the two documented citations above establish the reachable, unvalidated parameter path either way.
