Looking at `app/src/lib/patch-formatter.ts`, I traced the hunk-line accounting logic in `formatPatch()`/`formatPatchToDiscardChanges()` — both manually recompute `oldCount`/`newCount` and manually emit `\ No newline at end of file` markers, mirroring the report's pattern of two independently-computed values (fee-controller vs. `ProtocolFees`) that must stay consistent. I found a real divergence in how the "no trailing newline" marker is attached vs. dropped.### Title
Partial-commit patch generation drops the "no trailing newline" marker when an unstaged trailing line is excluded, corrupting/failing selective commits - (File: `app/src/lib/patch-formatter.ts`)

### Summary
`formatPatch()` and `formatPatchToDiscardChanges()` in `app/src/lib/patch-formatter.ts` independently recompute hunk metadata (`oldCount`/`newCount` and the `\ No newline at end of file` marker) from the raw diff line-by-line, the same way `RubiconFeeController` and `ProtocolFees` independently recomputed a fee amount that had to agree exactly. When a user excludes ("unselects") the very last added line of a hunk that itself carries the `noTrailingNewLine` flag, the line — and the newline-state information attached to it — is dropped entirely before the check that would normally re-emit the `\ No newline at end of file` marker ever runs, because the loop body returns early.

### Finding Description
`formatPatch` iterates `hunk.lines` and, for **unselected** lines, has this control flow (`app/src/lib/patch-formatter.ts:171-206`): [1](#0-0) 

```
// An unselected added line has no impact on this patch, pretend
// it was never added to the old file by dropping it.
if (line.type === DiffLineType.Add) {
  return
}
```

This `return` exits the `forEach` callback for that line **before** reaching: [2](#0-1) 

```
if (line.noTrailingNewLine) {
  hunkBuf += '\\ No newline at end of file\n'
}
```

`noTrailingNewLine` is set by `DiffParser.parseHunk()` on the specific `DiffLine` that is literally the last line of the old and/or new version of the file (see `app/src/lib/diff-parser.ts:319-338`). If the user, via the interactive per-line staging UI (`Changes`/`SeamlessDiffSwitcher`, wired through `changeFileLineSelection` → `file.selection.isSelected`), deselects exactly that trailing added line, the emitted patch:
- Silently loses all information that the resulting staged content has no trailing newline, and
- Leaves whatever line now becomes the new logical "last line" in the hunk (a context line or a converted delete→context line) without any no-newline marker, even though its neighbor in the real file may or may not have one.

The two computations that must agree — "what the real file's last-line/newline state is" (embodied in the dropped `DiffLine.noTrailingNewLine`) and "what the emitted patch claims" (embodied in the `hunkBuf` marker logic) — diverge exactly like the `RubiconFeeController` (`mulDivUp`) vs `ProtocolFees` (`mulDivDown`) mismatch in the seed report: one code path computes a value one way, a second path validates/consumes it another way, and nothing reconciles them.

The generated patch is then piped straight to `git apply --cached --unidiff-zero --whitespace=nowarn -` in `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-81`), with no post-generation sanity check that the patch's newline expectations match the actual working-tree bytes.

### Impact Explanation
- If `git apply --cached` detects the mismatch between the patch's implied trailing-newline state and the real blob, it fails, blocking the user's ability to commit that file at all until they stage everything (a DoS on the partial-commit feature, directly analogous to "Fee Controller Can DOS Trading Activity" in the seed report).
- If `git apply --cached` does not reject the patch (unified diffs without an explicit conflicting marker are often accepted), the index ends up staged with content whose trailing-newline state differs from what the user selected/reviewed in the diff view — i.e. **silent corruption of what the user commits**, one of the explicitly in-scope impact categories.
- The trigger condition (a tracked file with no trailing final newline) is trivial for a repository author to set up deliberately and ship in a cloned/fetched repo; the only remaining step is the victim's normal, expected use of GitHub Desktop's line-level partial staging on that file.

### Likelihood Explanation
Missing-final-newline files are common and easy for a repo author to guarantee. Partial line/hunk staging is a core, frequently used GitHub Desktop feature. The only requirement is that the user deselects the final line of such a file during interactive staging — a very ordinary interaction, not a contrived edge case, making this reachable without any unnatural user steps. I was not able to execute `git apply` in this environment to confirm which specific failure mode (hard reject vs. silent divergence) occurs on a given Git version; this should be validated with a concrete reproduction in a full dev/test environment.

### Recommendation
When dropping a `DiffLine` that carries `noTrailingNewLine` (both the "unselected added line" path and the equivalent path in `formatPatchToDiscardChanges`), propagate the newline-state onto whichever line becomes the new last emitted line of the hunk instead of silently discarding it, and add a regression test (extending `app/test/unit/git/apply-test.ts`) covering partial staging/discarding of a file lacking a trailing newline where the trailing line itself is deselected.

### Proof of Concept
1. Create a repository containing `file.txt` with content `line1\nline2` (no trailing newline after `line2`) and commit it — trivially doable by any repo author/attacker.
2. Victim clones the repo, edits the file to `line1\nline2\nline3` (again no trailing newline), and opens GitHub Desktop's Changes view.
3. In the interactive diff, the victim selects `line1`/context but **deselects** the newly added `line3` (the line for which `DiffLine.noTrailingNewLine` is `true`), intending to stage only the `line2` portion.
4. GitHub Desktop calls `_commitIncludedChanges` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`) → `formatPatch` (`app/src/lib/patch-formatter.ts:129-232`).
5. In `formatPatch`, the `line3` `DiffLine` hits the `if (line.type === DiffLineType.Add) { return }` branch at line 187 and is dropped before its `noTrailingNewLine` flag is ever consulted, so no `\ No newline at end of file` marker is emitted for the resulting hunk even though the real file on disk still lacks a final newline.
6. The malformed patch is piped to `git apply --cached ...`, which either rejects it (blocking the commit) or applies it, staging index content whose newline state does not match the working tree/what was shown to the user in the diff view.
