Audit Report

## Title
Unbounded per-origin `nodes` map in `ReceivedCacheEntry::record` via unauthenticated `Protocol::PushMessage` `from` field enables gossip-thread CPU exhaustion - (File: gossip/src/received_cache.rs)

## Summary
`ReceivedCacheEntry::record` only caps `self.nodes.len()` at `CAPACITY = 50` on the "stale/duplicate" path, not on the "timely" (`num_dups < NUM_DUPS_THRESHOLD`) path, which inserts unconditionally. Because the `from` pubkey in `Protocol::PushMessage(from, data)` is never authenticated against the sender's real identity or address, an attacker can drive unbounded growth of a single origin's `nodes` map, making the later `sorted_unstable_by_key` call in `ReceivedCacheEntry::prune` an `O(n log n)` operation on attacker-controlled `n`, run synchronously on the gossip-processing thread while holding the `received_cache` mutex.

## Finding Description
`record()` in `gossip/src/received_cache.rs` (lines 72-87) inserts into `self.nodes: HashMap<Pubkey, usize>` unconditionally when `num_dups < NUM_DUPS_THRESHOLD` (i.e., for timely/new or first-duplicate messages), and only checks `self.nodes.len() < Self::CAPACITY` in the `else` branch for older duplicates. `prune()` (lines 89-120) later performs `self.nodes.into_iter()....sorted_unstable_by_key(...)` over the entire map. This is called from `CrdsGossipPush::process_push_message` and `CrdsGossipPush::prune_received_cache` in `gossip/src/crds_gossip_push.rs`, both invoked synchronously from `ClusterInfo::handle_batch_batch_push_messages`/`process_packets` in `gossip/src/cluster_info.rs` on the gossip thread. The `node` key passed to `record` is the outer `from` pubkey of `Protocol::PushMessage(Pubkey, Vec<CrdsValue>)`, which `Protocol::verify` (`gossip/src/protocol.rs`, lines 135-147) never authenticates — it only verifies signatures on inner `CrdsValue`s. `process_packets` in `cluster_info.rs` (lines 2113-2124) takes this `from` at face value into `push_messages.push((from, data))` with no check against the packet's actual `from_addr` or any verified contact info.

## Impact Explanation
If exploitable to the degree described, this would allow an unprivileged remote party to cause CPU exhaustion on the gossip thread via the `O(n log n)` sort inside `ReceivedCacheEntry::prune`, degrading gossip participation — a non-RPC remote resource-exhaustion effect consistent with the target scope. However, I was unable to independently confirm within this review the achievable growth rate of `nodes` for a fixed origin (i.e., how many distinct `record(origin, from, 0)` calls with different spoofed `from` an attacker can realistically drive per unit time, given `crds.insert` upsert/wallclock-window semantics and any other rate limiting in the packet-processing pipeline), so the practical severity of the CPU-exhaustion effect is not fully substantiated by direct evidence beyond the code paths cited.

## Likelihood Explanation
The described attack requires only an unprivileged gossip endpoint, an attacker-owned keypair as `origin`, and the ability to send small UDP packets with distinct, unauthenticated `from` fields wrapping validly-signed CrdsValues — no stake or trust relationship is required, consistent with the code reviewed. The exact achievable packet/insert rate and hence real-world severity were not independently benchmarked or fully traced through `crds.rs`'s insert/upsert logic in this session.

## Recommendation
Cap `self.nodes.len()` unconditionally at `CAPACITY` in `ReceivedCacheEntry::record`, including in the `num_dups < NUM_DUPS_THRESHOLD` branch, and/or authenticate or otherwise bind the `from` field of `Protocol::PushMessage` to a verified peer identity before using it as a `ReceivedCache` key.

## Proof of Concept
As described in the finding: repeatedly call `CrdsGossipPush::process_push_message` with a fixed attacker-controlled `origin` and successive fresh, wallclock-valid `CrdsValue`s that cause `crds.insert` to return `Ok(())`, while varying `from` to a new random `Pubkey` on each call; then measure the cost of `CrdsGossipPush::prune_received_cache`/`ReceivedCacheEntry::prune` as `nodes.len()` grows well beyond `CAPACITY = 50`. Concrete timing/throughput numbers were not produced in this review and would require running the actual test/benchmark in the crate.
