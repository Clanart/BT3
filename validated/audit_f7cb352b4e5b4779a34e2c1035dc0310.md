Based on my research, I found a concrete analog: **unsanitized attacker-controlled ref names flowing into `git` command argument lists without an "options-terminator" boundary**, which mirrors the seed bug's core pattern (an untrusted, attacker-influenced value bypasses the validation boundary that protects a security-relevant operation).

### Title
Attacker-controlled remote branch names bypass Desktop's ref-name sanitization and are injected as leading git-command arguments during merge/checkout - (File: `app/src/lib/git/merge.ts`, `app/src/lib/git/checkout.ts`)

### Summary
Desktop maintains a dedicated sanitizer, `sanitizedRefName` [1](#0-0) , that strips leading `-`/`+` characters specifically because a ref name beginning with `-` can be misinterpreted by `git` as a command-line flag rather than a positional argument. This sanitizer, however, is only applied to **user-typed** branch names in the UI (e.g. `app/src/ui/worktrees/add-worktree-dialog.tsx`). Branch names that originate from a `git fetch`/`git clone` of a remote — i.e., the `Branch` model's `nameWithoutRemote`/`name` derived straight from ref data [2](#0-1)  — are never passed through this sanitizer before being placed as bare positional arguments in `git merge`/`git checkout` invocations.

### Finding Description
The broken invariant is the same shape as the vault bug: a value that should only be trusted/consumed after being "initialized"/validated through one code path (`sanitizedRefName`, applied to Desktop-created branches) is instead consumed via a second, uninitialized/unvalidated path (ref names learned from an untrusted remote) that reaches the same sensitive sink.

Concretely:
- `merge()` builds `const args = ['merge']`, optionally pushes `--squash`/`--no-verify`, then does `args.push(branch)` with the raw branch string as the final positional argument — no `--` terminator precedes it [3](#0-2) .
- `checkoutBranch()`'s `getBranchCheckoutArgs()` places `branch.name` (and `-b`/`branch.nameWithoutRemote` for remote branches) ahead of the `'--'` terminator, which is appended only at the very end of the argument list [4](#0-3) .
- `renameBranch()` similarly passes `branch.nameWithoutRemote` as a positional operand to `git branch -m/-M` [5](#0-4) .

A malicious remote can create refs with names git's low-level plumbing accepts (e.g. via `git update-ref`/hand-edited `packed-refs`, bypassing the higher-level `git branch`/`git tag` porcelain check that normally forbids a leading `-`). When the victim clones/fetches such a repository in Desktop and the resulting remote-tracking branch is auto-materialized into a local branch during checkout (`-b <nameWithoutRemote>`, unsanitized) or is later selected as a merge/rename target, git receives an argument beginning with `-` at a position where it is parsed as an option rather than a ref name, because none of these call sites places the value after a `--` terminator that precedes it.

### Impact Explanation
At minimum this allows an attacker-controlled repository to silently alter the semantics of a `git merge`/`git checkout`/`git branch -m` operation the victim believes they are running against a specific branch — e.g., injecting flags such as `-X<strategy-option>`, `--squash`, `--no-ff`/`--ff-only`, or `--no-commit` — which fits the accepted impact class of "silent corruption of what the user commits or pushes." Because the user only sees a friendly branch label in the Desktop UI, they have no visibility into the fact that the underlying ref name is being interpreted as a flag by the invoked `git` process. I could not fully verify from static review alone whether any specific injectable flag on these particular subcommands (`merge`, `checkout`, `branch -m`) escalates to arbitrary code execution (as opposed to strategy/behavior confusion or a parse error) — that would require actually invoking `dugite`/`git` with a crafted ref to observe real argument-parsing behavior, which is outside what I can confirm via the indexed source alone.

### Likelihood Explanation
Exploitation requires: (1) the victim adds/clones/fetches an attacker-controlled remote, which is within the accepted attacker model ("attacker controls a cloned/fetched repository ... or a git remote"), and (2) the victim subsequently interacts with the malicious branch (checks it out, merges it, or renames it) through Desktop's normal UI flows — no unnatural steps are required beyond routine use of a hostile repository. The likelihood is tempered by the need for the attacker to construct a ref name outside git's normal `branch`/`tag` porcelain (a one-time setup cost on the attacker's own repository, not on the victim's machine).

### Recommendation
Apply the same defense already used for user-typed names to ref/branch values sourced from remotes:
- Pass `'--'` immediately before any branch/ref-derived argument in `merge()`, `getBranchCheckoutArgs()`, and `renameBranch()`, mirroring the existing pattern already used in `resetPaths`/`getCommits` (`app/src/lib/git/reset.ts`, `app/src/lib/git/log.ts`) where a `--` terminator is placed ahead of user/remote-controlled values.
- Alternatively/additionally, reject or sanitize (rather than silently accept) any local/remote ref whose short name begins with `-` when parsing `for-each-ref` output into `Branch` objects, consistent with `sanitizedRefName`'s existing rule set [6](#0-5) .

### Proof of Concept
1. Attacker creates a repository and, using `git update-ref refs/heads/-Xtheirs abc123` (bypassing `git branch`'s own leading-dash rejection), publishes a branch that Desktop's `for-each-ref` parsing will read as name `-Xtheirs`.
2. Victim adds this remote in Desktop and fetches; the branch shows up as `origin/-Xtheirs` in the branch list (`app/src/lib/git/branch.ts` `getBranchNames`, `app/src/models/branch.ts`).
3. Victim selects "Merge into current branch" for `origin/-Xtheirs`. `merge()` builds `git merge origin/-Xtheirs` — because the value is prefixed by the remote name it is not directly exploitable at this hop, but if the victim first checks out the branch (auto-creating a local branch literally named `-Xtheirs` via the unsanitized `-b nameWithoutRemote` in `getBranchCheckoutArgs`) and later merges/renames that local branch, subsequent calls (`merge()`, `renameBranch()`) pass the bare string `-Xtheirs` as a positional argument with no preceding `--`, letting `git` interpret it as the `-X` merge-strategy-option flag instead of a branch name.
4. Because I was not able to execute `dugite`/`git` in this environment, I can confirm the code path (missing `--` terminator, unsanitized value) with certainty, but not the exact resulting git behavior (flag-parse error vs. semantic change vs. code execution) for each specific subcommand — this should be validated by a Devin session capable of running the actual `git` binary against a crafted ref.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}
