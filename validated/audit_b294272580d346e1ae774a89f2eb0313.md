### Title
Stale `deleteConflictAction` resolution silently overrides externally-resolved conflicts before commit - ([File: app/src/lib/stores/app-store.ts])

### Summary
`applyCopilotConflictResolutions()` applies AI-generated conflict resolutions to disk before a merge/rebase/cherry-pick continues. For ordinary text conflicts it guards against clobbering a conflict the user already resolved outside the dialog (e.g. in their editor), but the parallel code path for delete-vs-modify conflicts has no equivalent guard, so it can silently re-apply a stale Copilot decision over whatever the user or the working tree actually resolved to.

### Finding Description
`applyCopilotConflictResolutions` snapshots `state = this.repositoryStateCache.get(repository)` once at the top of the function [1](#0-0) , then iterates over `copilotResolutions` produced earlier by the AI.

For normal text-conflict resolutions, before overwriting the file it explicitly re-checks the live conflict status and skips if the user already resolved it themselves: [2](#0-1) 

For `deleteConflictAction` resolutions (one side deleted the file, the other modified it), no such re-validation exists. The code looks up the file from the same stale `state` snapshot, derives `deletedSide` from it, and unconditionally calls `_updateManualConflictResolution` to force `ManualConflictResolution.ours`/`theirs`: [3](#0-2) 

That manual resolution is authoritative at commit time: `stageManualConflictResolution` uses it to run `git checkout --ours/--theirs` and stage the chosen side, overriding whatever is currently on disk or already staged [4](#0-3) . Because the delete-vs-modify branch is missing the "already resolved externally, don't clobber" check that exists for the text-conflict branch, a decision computed from stale conflict-content context (which itself derives from repository/remote-supplied file content, `oursContent`/`theirsContent`, fed to the AI in `copilot-conflict-context.ts`) can be re-applied after the user has already taken a different resolution action, silently overwriting the user's intended commit contents with the (attacker-influenceable, since the conflicting content originates from the fetched remote branch) AI-derived choice.

This is structurally the same bug class as the report: a safety/consistency check that is enforced on one branch of a symmetric decision (positive PnL / text-conflict path) is omitted on the other branch (negative PnL / delete-conflict path), letting stale or attacker-influenced state be committed without the intended reconciliation.

### Impact Explanation
If triggered, this could cause Desktop to silently stage and later commit the wrong side of a delete-vs-modify conflict — e.g. keeping a file the user intended to delete, or deleting a file the user had manually restored — without further confirmation. This is a silent corruption of what the user commits/pushes, which meets the stated valid-impact bar (unprivileged, attacker-influenced repository content flowing through Copilot's conflict-resolution context, ending in unintended, unreviewed changes to the committed tree).

### Likelihood Explanation
Requires a delete-vs-modify conflict during a Copilot-assisted merge/rebase/cherry-pick, and a timing window where the on-disk/manual resolution state changes between when the AI resolution is computed and when `applyCopilotConflictResolutions` runs (e.g. user manually resolves via editor/CLI while the result dialog is open, or intervening file changes). This is a narrower window than the acknowledged smart-contract report's always-reachable code path, so likelihood is lower — it depends on a race/staleness condition rather than a straightforward always-applicable computation gap. I was not able to fully trace every caller of `applyCopilotConflictResolutions` or confirm how large the staleness window can realistically be in the UI flow, so this should be treated as a plausible but not fully proven-exploitable path.

### Recommendation
Apply the same "resolved externally, don't clobber" check used for text conflicts (`isConflictedFileStatus` + `hasUnresolvedConflicts`, or re-reading current status just before applying) to the `deleteConflictAction` branch before calling `_updateManualConflictResolution`, so stale AI resolutions can never override a resolution the user has already made through another path.

### Proof of Concept
1. Start a merge/rebase where a file is deleted on one side and modified on the other (delete-vs-modify conflict), with the "modified" content coming from a remote branch under attacker control.
2. Trigger Copilot conflict resolution; it decides `action: "keep"` (or `"delete"`) based on `getDeletedSideFromStatus`/AI reasoning.
3. Before continuing, the user manually resolves the conflict differently (e.g., via external editor/CLI) so the working tree/index no longer reflects the AI's assumed state.
4. Click "Continue" — `applyCopilotConflictResolutions` runs; because the delete-conflict branch never re-validates against current status (unlike the text-conflict branch), it calls `_updateManualConflictResolution` with the stale `deletedSide`/choice, which `stageManualConflictResolution` then applies via `git checkout --ours/--theirs`, silently overwriting the user's manual resolution in the resulting commit.

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
    default:
      assertNever(chosen, 'unaccounted for git status entry possibility')
  }
