## Title
Missing Cross-Spend Binding in `dl_update_multiple` Enables BLS Signature Subtraction to Split Atomic DataLayer Root Updates - (File: chia/wallet/wallet_rpc_api.py)

### Summary
The ScadaBR advisory describes a missing-authentication-for-critical-function flaw where an attacker can inject arbitrary state without the originator's consent. The closest reachable analog in this codebase is `WalletRpcApi.dl_update_multiple`, which builds several independent DataLayer singleton update spends into a single spend bundle without cryptographically linking them together, and the code explicitly flags this gap.

### Finding Description
`dl_update_multiple` iterates over `request.updates.launcher_root_pairs` and calls `wallet.create_update_state_spend()` once per launcher, accumulating all spends (and one aggregate fee) inside the same `action_scope`/spend bundle: [1](#0-0) 

The method's own TODO states the missing safeguard: [2](#0-1) 

`create_update_state_spend()` only emits the linking announcement/assertion pair when the caller explicitly passes `announce_new_state=True`; by default the per-launcher singleton spends are signed together but not bound to one another via `AssertCoinAnnouncement`/`CreateCoinAnnouncement` conditions: [3](#0-2) 

Because BLS signatures used by Chia (`AugSchemeMPL`) aggregate linearly, an aggregate signature over multiple independent messages can have any subset's contribution subtracted out by a third party who knows the individual message/signature relationship structure (a classic "signature subtraction" issue): `Sig_total - Sig_i` remains a valid aggregate signature for the spend bundle with coin-spend `i` removed. Since none of the individual singleton updates assert that the others are present (no shared announcement), removing one spend from `dl_update_multiple`'s bundle still produces a fully valid, independently acceptable transaction for the remaining launchers.

`DataLayer.multistore_batch_update()` in the service layer builds exactly this kind of multi-launcher `dl_update_multiple` call from `DataLayerRpcApi.multistore_batch_update`, so any local RPC caller (or offer/trade flow) that batches multiple store root publications together is exposed to this gap: [4](#0-3) 

### Impact Explanation
An attacker who can observe a `dl_update_multiple` spend bundle in the mempool before it confirms (or who receives it as an intermediary, e.g. in an offer-relay or multi-party workflow) can strip the signature/spend contribution belonging to one or more launcher updates and resubmit the remainder as an independently valid spend bundle. This breaks the intended atomicity of `multistore_batch_update`/`dl_update_multiple`: some DataLayer singleton roots get published while others silently do not, even though a fee spend or other conditions were meant to make the whole set an all-or-nothing update. This is a coin-set divergence / invalid-partial-acceptance issue directly analogous to unauthenticated data injection: unauthorized parties can force only part of a caller-authorized state transition onto the chain.

### Likelihood Explanation
Exploitation requires the batch to actually contain more than one launcher update signed together (a supported and documented RPC flow), and requires the attacker to see the spend bundle before confirmation (mempool visibility, which is the normal untrusted-peer threat model already assumed elsewhere in the RPC boundary docs). No key compromise is needed — this is a structural signature-aggregation issue, not a leaked-key scenario, so it is not excluded by the leaked-key exclusion rule.

### Recommendation
Always emit the linking `AssertCoinAnnouncement`/`CreatePuzzleAnnouncement` conditions between every singleton spend included in a multi-launcher update (i.e., force `announce_new_state=True` semantics, or add an explicit shared announcement chain) whenever `dl_update_multiple`/`multistore_batch_update` combines more than one `create_update_state_spend` call, so that any subtraction of one spend from the aggregate signature invalidates the announcement assertions of the remaining spends.

### Proof of Concept
1. Wallet user calls `dl_update_multiple` (or `multistore_batch_update` via DataLayer RPC) with two launcher/root pairs and a shared fee, producing one spend bundle with an aggregate BLS signature covering both singleton spends.
2. Bundle is broadcast and sits in the mempool.
3. A third party captures the bundle, computes the per-spend `AGG_SIG_ME` message for singleton B, and subtracts the corresponding signature share from the aggregate signature (`Sig_total - Sig_B`), producing a new bundle containing only singleton A's spend with a still-valid aggregate signature.
4. The stripped bundle is submitted and accepted by the mempool/full node since singleton A's spend has no announcement dependency on singleton B's spend.
5. Result: singleton A's root update is published while singleton B's is silently dropped, contrary to the original caller's intended atomic multi-store update.

    async def dl_update_multiple(
        self,
        request: DLUpdateMultiple,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> DLUpdateMultipleResponse:
        """Update multiple singletons with new merkle roots"""
        if self.service.wallet_state_manager is None:
            raise RuntimeError("not initialized")

        wallet = await self.service.wallet_state_manager.get_dl_wallet()
        async with self.service.wallet_state_manager.lock:
            # TODO: This method should optionally link the singletons with announcements.
            #       Otherwise spends are vulnerable to signature subtraction.
            # TODO: This method should natively support spending many and attaching one fee
            fee_per_launcher = uint64(request.fee // len(request.updates.launcher_root_pairs))
            for launcher_root_pair in request.updates.launcher_root_pairs:
                await wallet.create_update_state_spend(
                    launcher_root_pair.launcher_id,
                    launcher_root_pair.new_root,
                    action_scope,
                    fee=fee_per_launcher,
                    extra_conditions=extra_conditions,
                )

            # tx_endpoint will take care of default values here
            return DLUpdateMultipleResponse(unsigned_transactions=[], transactions=[])

    async def multistore_batch_update(
        self,
        store_updates: list[dict[str, Any]],
        fee: uint64,
        submit_on_chain: bool = True,
    ) -> list[TransactionRecord]:
        store_ids: set[bytes32] = set()
        for update in store_updates:
            store_id = update["store_id"]
            changelist = update["changelist"]

            if store_id in store_ids:
                raise Exception(f"Store id {store_id.hex()} must appear in a single update")
            store_ids.add(store_id)

            status = Status.PENDING if submit_on_chain else Status.PENDING_BATCH
            await self.batch_insert(store_id=store_id, changelist=changelist, status=status)

        if submit_on_chain:
            updates: list[LauncherRootPair] = []
            for store_id in store_ids:
                await self._update_confirmation_status(store_id=store_id)
                root_hash = await self._get_publishable_root_hash(store_id=store_id)
                updates.append(LauncherRootPair(launcher_id=store_id, new_root=root_hash))
            response = await self.wallet_rpc.dl_update_multiple(
                DLUpdateMultiple(updates=DLUpdateMultipleUpdates(launcher_root_pairs=updates), fee=fee),
                DEFAULT_TX_CONFIG,
            )
            return response.transactions
