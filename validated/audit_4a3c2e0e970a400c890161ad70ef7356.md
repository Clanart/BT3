## Finding: BandwidthManager.purchase() debits the buyer in full but dispatches with zero relayer fee and zero timeout, with no refund path if the request is never delivered

### Title
Bandwidth purchase funds can be permanently stranded — payment is pulled up-front but the ISMP dispatch carries no relayer fee, no timeout, and no timeout-refund handler - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`BandwidthManager.purchase()` immediately pulls the full fee-token payment from the caller via `safeTransferFrom`, then dispatches a `PostRequest` to hyperbridge's `pallet-bandwidth` with `fee: 0` and `timeout: 0`, and the contract implements no `onPostRequestTimeout` handler. This breaks the "funds move exactly once and only to the rightful beneficiary" invariant: an unprivileged caller's payment is debited unconditionally, but nothing in the protocol guarantees the corresponding bandwidth credit is ever delivered, and there is no automated path back to the payer if it is not.

### Finding Description
`purchase()` computes the scaled price and pulls it from `msg.sender` before doing anything else: [1](#0-0) 

It then dispatches the credit message to hyperbridge with the fee explicitly zeroed and `payer` set to the contract itself rather than the buyer: [2](#0-1) 

`docs/outbound-request-incentivization.md` documents this exact pattern (`FeeMetadata { payer: [0u8;32], fee: Default::default() }`) as the known cause of relayers having "no economic reason to pick them up," calling the result "altruism"-dependent delivery: [3](#0-2) 

That doc's fix only covers *hyperbridge-originated* system messages (host-executive, intents-coprocessor, token-governor, relayer withdrawal) via a new `pallet-relayer` reward keyed by `module_id`. `BandwidthManager`'s dispatch is a *user-originated* EVM→hyperbridge request, which is a different leg entirely (normally covered by the standard `accumulate_fees`/`WithdrawalProof` flow in `modules/pallets/relayer/src/accumulate.rs`, which requires a non-zero source-chain fee to reward the relaying party). Because `fee: 0` here, that flow has nothing to pay out either — no incentive exists anywhere in the pipeline for a relayer to deliver this specific request.

Compounding this, `purchase()` sets `timeout: 0`. The standard ISMP timeout-refund path only ever returns `meta.fee` (already zero) to `meta.sender`/`payer` — it never refunds the price the buyer paid into `BandwidthManager`'s balance, and `BandwidthManager` implements no `onPostRequestTimeout` override to add such logic: [4](#0-3) 

The only way funds already sitting in the contract move out again is the governance-only `Withdraw` action, which must originate from hyperbridge itself (`request.source` must equal hyperbridge) and sends funds to an arbitrary `beneficiary` chosen by governance — not automatically back to the original buyer: [5](#0-4) 

### Impact Explanation
Any unprivileged user calling `purchase()` has their fee-token payment debited unconditionally and irreversibly at call time. If the resulting zero-fee message is never relayed to hyperbridge (which the project's own documentation confirms is the expected outcome for zero-fee/zero-payer dispatches, absent an operator acting altruistically), the buyer receives no bandwidth credit and has no protocol-level way to recover the payment — it sits in `BandwidthManager` until/unless governance discovers it and manually issues a `Withdraw`, at which point governance (not the buyer) chooses the beneficiary. This is a direct loss-of-funds condition triggerable through a normal, unprivileged, public entry point, matching the bounty's "stealing or loss of funds" category without requiring a malicious relayer, prover, or admin — the loss occurs precisely because no honest relayer is economically motivated to act.

### Likelihood Explanation
The trigger condition is simply calling `purchase()` under normal operating conditions where no relayer chooses to deliver a fee-free message — a condition the project's own `outbound-request-incentivization.md` explicitly acknowledges happens for zero-fee dispatches elsewhere in the same codebase. No attacker action, race, or compromised party is needed; the vulnerable state is reachable by every ordinary purchase. I could not fully verify from the indexed content how the ISMP core treats a request with `timeout: 0` (whether it is "never expires" or is effectively unenforceable/malformed) — that detail affects whether a timeout-based partial mitigation could ever fire, but it does not change the core finding, since even a successful timeout only refunds the (zero) protocol fee, not the buyer's purchase amount.

### Recommendation
- Have `purchase()` attach a real, non-zero relayer fee (pulled from the buyer in addition to the tier price, or carved out of it) and set `payer` to the actual buyer so the standard `accumulate_fees`/`WithdrawalProof` relayer-reward path (`modules/pallets/relayer/src/accumulate.rs`) applies and creates a real economic incentive to deliver.
- Set a real, finite `timeout` for the dispatch.
- Implement `onPostRequestTimeout` in `BandwidthManager` to refund the buyer's originally paid `amount` (not just the zero protocol fee) when the request times out, tracking per-commitment payer/amount so the refund goes to the correct rightful beneficiary.

### Proof of Concept
1. User calls `BandwidthManager.purchase(app, tier, months, chain)`; `amount` of fee-token is pulled from the user via `safeTransferFrom` at line 163.
2. The dispatched `DispatchPost` carries `fee: 0`, `payer: address(this)`, `timeout: 0` (lines 172-181).
3. No relayer is economically incentivized to deliver this message (per the project's documented behavior for zero-fee dispatches in `docs/outbound-request-incentivization.md:9-11`), so the request is never relayed to hyperbridge and `pallet-bandwidth` never credits the tier bucket.
4. The user's `amount` remains locked in `BandwidthManager`'s token balance; `onAccept` only exposes a governance-triggered `Withdraw` (line 213-221) that can send the stuck funds to any `beneficiary` governance names — not automatically back to the original buyer. The buyer has permanently lost their payment with no on-chain recourse.

    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }

**File:** docs/outbound-request-incentivization.md (L9-11)
```markdown
A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.
```
