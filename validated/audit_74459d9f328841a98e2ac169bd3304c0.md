### Title
`unvote()` decrements `totalVlMgpInVote` for votes cast while `msg.sender` was the old `delegatedPool`, corrupting the proportional vote denominator - (File: wombat/WombatBribeManager.sol)

### Summary
`vote()` skips the `totalVlMgpInVote`/`userTotalVotedInVlmgp` increment when `msg.sender == delegatedPool` at the time of voting [1](#0-0) , but `unvote()` only checks `msg.sender != delegatedPool` against the *current* value of `delegatedPool` when deciding whether to decrement [2](#0-1) . If the owner changes `delegatedPool` between the `vote()` and `unvote()` calls (a routine admin lifecycle action via `setDelegatedPool`) [3](#0-2) , the address that used to be `delegatedPool` can call `unvote()` and decrement `totalVlMgpInVote` for an amount that was never added to it, corrupting the global counter used as the denominator in `castVotes()`.

### Finding Description
`vote()` and `unvote()` maintain two related but distinct sets of state:
- Per-pool per-user state: `pool.totalVoteInVlmgp`, `userVotedForPoolInVlmgp[msg.sender][pool]` — always updated regardless of `delegatedPool` status.
- Aggregate state: `userTotalVotedInVlmgp[msg.sender]`, `totalVlMgpInVote` — updated only when `msg.sender != delegatedPool`, i.e., excluded for the currently designated delegated pool [1](#0-0) .

`unvote()` re-reads `userVotedForPoolInVlmgp[msg.sender][pool.poolAddress]` (the per-pool amount, always accurate) and unconditionally subtracts it from `pool.totalVoteInVlmgp` and `userTotalVotedInVlmgp[msg.sender]`, then separately gates the `totalVlMgpInVote` decrement on the *current* `delegatedPool` value:
```solidity
pool.totalVoteInVlmgp -= uint256(currentVote);
userTotalVotedInVlmgp[msg.sender] -= uint256(currentVote);
userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] = 0;
if (msg.sender != delegatedPool) {
    totalVlMgpInVote -= currentVote;
}
``` [4](#0-3) 

Because the exclusion condition is evaluated against the *live* `delegatedPool` at unvote-time rather than the value that was in effect when the vote was originally cast, the following sequence desynchronizes `totalVlMgpInVote` from the true sum of contributions:

1. Owner sets `delegatedPool = X` (via `setDelegatedPool`, normal admin action).
2. `X` calls `vote([lp], [+V])`. `pool.totalVoteInVlmgp` and `userVotedForPoolInVlmgp[X][lp]` increase by `V`, but since `msg.sender == delegatedPool`, `totalVlMgpInVote` is **not** incremented [5](#0-4) .
3. Owner later changes `delegatedPool` to a different address `Y` (routine lifecycle change, e.g. migrating the delegate reward pool contract).
4. `X` (now an ordinary, unprivileged caller no longer equal to `delegatedPool`) calls `unvote(lp)`. The per-pool state correctly zeroes out, but the check `msg.sender != delegatedPool` is now true, so `totalVlMgpInVote -= V` executes even though `V` was never added in step 2.

This either underflows and reverts (denial of unvote for the caller, self-inflicted) or, more importantly in aggregate scenarios with concurrent votes from other users, drives `totalVlMgpInVote` below the true sum of all non-delegated users' contributions. Since `castVotes()` uses `totalVlMgpInVote` as the shared denominator for every pool's proportional allocation:
```solidity
targetVote = targetVoteInLMGP * totalVotes() / totalVlMgpInVote;
``` [6](#0-5) 
an artificially shrunk `totalVlMgpInVote` inflates `targetVote` for every pool, distorting the relative Wombat gauge weight allocation for all remaining voters — a governance/voting-integrity break, not merely a self-DoS.

No modifier or reentrancy guard mitigates this; `unvote()` has no access control beyond `pool.isActive`, and the mismatch stems purely from the asymmetric time-of-check (vote-time delegatedPool) vs time-of-check (current delegatedpool) between the two functions.

### Impact Explanation
This corrupts the aggregate `totalVlMgpInVote` invariant (it should equal the sum of all non-delegated users' active allocations). Since `castVotes()` divides by this value to compute each pool's proportional vote weight sent to the real Wombat `voter.vote()` call, an incorrect (too small) denominator inflates every pool's computed `targetVote`, distorting Wombat gauge allocations for every current voter — this matches the "governance voting result manipulation" impact class. In the extreme case (large delegated votes unvoted after a delegatedPool swap), `totalVlMgpInVote` can underflow entirely, reverting and breaking `unvote()`/`castVotes()` for the whole system until manually recovered by the owner.

### Likelihood Explanation
The only precondition is that `delegatedPool` is reassigned by the owner between a `vote()` and later `unvote()` call for the same address — an ordinary, expected admin operation (e.g., replacing/upgrading the delegate vote reward pool contract), not a malicious or compromised admin action. Once that ordinary reassignment happens, the former `delegatedPool` address (or anyone who voted while temporarily set as `delegatedPool`) can call `unvote()` permissionlessly at zero cost, requiring no capital, flash loans, or special privileges. The bug is deterministic and repeatable every time `delegatedPool` is rotated while it still holds an active vote.

### Recommendation
Track, per user (or per vote record), whether that user's contribution was excluded from `totalVlMgpInVote` at vote-time (e.g., a `mapping(address => bool) wasDelegatedAtVote` snapshot, or simply persist the address that was `delegatedPool` at the time of each vote), and use that stored flag in `unvote()` instead of re-checking the live `delegatedPool`. Alternatively, before changing `delegatedPool`, force a full reconciliation/unvote of the old delegated pool's positions so no aggregate-excluded votes are left outstanding when the address changes.

### Proof of Concept
Foundry test outline:
1. Deploy `WombatBribeManager`, add an active pool `lp` with a mock rewarder.
2. As owner, call `setDelegatedPool(attacker)`.
3. `vm.prank(attacker)`; call `vote([lp], [+1000e18])`. Assert `totalVlMgpInVote == 0` (excluded) while `userVotedForPoolInVlmgp[attacker][lp] == 1000e18`.
4. Have a second, normal user `bob` (not delegated) call `vote([lp], [+500e18])`. Assert `totalVlMgpInVote == 500e18`.
5. As owner, call `setDelegatedPool(newAddr)` (simulating routine delegate-pool rotation).
6. `vm.prank(attacker)`; call `unvote(lp)`.
7. Assert either (a) the call reverts with an arithmetic underflow (since `totalVlMgpInVote` (500e18) < `currentVote` (1000e18)), demonstrating the unconditional/erroneous decrement, or, using a scenario where `totalVlMgpInVote` is large enough not to underflow, assert `totalVlMgpInVote` ends up strictly less than the true remaining sum `userTotalVotedInVlmgp[bob]`, proving the invariant "`totalVlMgpInVote` == sum of all non-delegated users' contributions" is broken.
8. Call `castVotes()` and show the computed `targetVote` for `lp` no longer matches the expected proportional share based on real outstanding votes, confirming downstream governance-weight distortion.
