## Analog Found

### Title
Unrecognized two-character git status codes are silently coerced to "modified", corrupting the represented file state used for commit/diff decisions - (File: `app/src/lib/status-parser.ts`)

### Summary
`mapStatus` in `app/src/lib/status-parser.ts` decodes the two-character `XY` status code Git emits for `git status --porcelain=2` into a `FileEntry` discriminated union that later drives what Desktop shows, stages, and diffs for a file. The function enumerates roughly twenty specific two-character combinations, and for anything else falls through to a final unconditional branch: [1](#0-0) 

This is the structural analog of the Fedimint bug: an externally-influenced discriminant (there, a consensus item variant; here, the git status code pulled from `git status` output) is decoded leniently, and the decoder treats "unrecognized" the same as a known, well-understood state instead of surfacing an error. The Fedimint fix rejected unknown items; here the code goes the opposite direction and silently *accepts* the unknown value as if it were `modified`, which is worse for correctness because it never even logs a warning.

### Finding Description
The regex that captures the status code accepts any two characters from the class `[MADRCUTX?!.]`, i.e. 49 possible combinations: [2](#0-1) 

`mapStatus` only special-cases about 20 of those combinations (`.M`, `M.`, `.A`, `A.`, `.D`, `D.`, `R.`, `.R`, `C.`, `.C`, `AD`, `AM`, `RM`, `RD`, `DD`, `AU`, `UD`, `UA`, `DU`, `AA`, `UU`) — see the full chain of `if (statusCode === ...)` checks from lines 208–418. Anything not on that list — for example `T.`, `.T`, `TM`, `MT`, `CM`, `MC`, `CD`, `XA`, or any combination involving the type-change code `T` (used when a file changes kind, e.g. regular file ↔ symlink, which git legitimately reports) — falls into the final fallback: [1](#0-0) 

This returns an `OrdinaryEntry` with `type: 'modified'` and **no `index`/`workingTree` fields at all**, even though those fields are declared optional specifically to allow such omission: [3](#0-2) 

That `FileEntry` then flows straight into `buildStatusMap`, which branches on `status.kind === 'ordinary'` to decide whether to *skip* displaying an entry (when index=Added & workingTree=Deleted) and otherwise hands it to `convertToAppStatus` to build the `AppFileStatus` shown in the Changes list and used to build commit patches: [4](#0-3) 

Because the fallback entry carries no `index`/`workingTree` values, the "skip if added-then-deleted" guard at lines 312–317 can never fire for an unrecognized code, and the file is always surfaced and always treated as a plain "Modified" file regardless of what actually happened (e.g., a type change from a regular file to a symlink, or a symlink to a regular file, or a git 2.9+ new porcelain code not yet enumerated here). `T` (typechange) is part of the porcelain v2 XY alphabet per Git's own documentation, and Desktop's regex explicitly whitelists it as a valid character in the status field, yet `mapStatus` has no branch for any code containing `T`.

### Impact Explanation
Git's typechange status (`T`) is the mechanism a maliciously crafted repository can use to swap a tracked regular file for a symlink (or vice versa) between the index and the working tree. When that transition is reported as `.T`/`T.`/`TM`/etc., Desktop's `mapStatus` silently classifies it as an ordinary "Modified" file rather than surfacing the actual index/working-tree kind change. Since the "ordinary added-then-deleted" suppression logic depends on `index`/`workingTree` being populated (lines 312–317 of `status.ts`), and the fallback never populates them, a crafted status transition can also slip past that de-duplication guard, causing entries that should have been hidden or represented differently to instead be shown and committed as an innocuous "Modified" change. This is a silent corruption of what the user believes they are committing: the file list, diff, and patch generation all treat the change as a normal content modification when the underlying git-level operation (a type change, e.g. regular-file → symlink) is materially different and can be used to disguise a malicious payload swap as an unremarkable one-line diff. This satisfies the "silent corruption of what the user commits or pushes" impact category, driven by an attacker-controlled input (a crafted repository whose working tree/index produces an uncommon status transition).

### Likelihood Explanation
The attacker does not need local/physical access or elevated privileges — they only need to craft a repository (or a set of commits/working-tree states within a repository the victim clones or checks out) that produces one of the ~29 unhandled `XY` combinations, most plausibly involving Git's `T` (typechange) code, which is a legitimate and reachable status Git can emit. The victim only needs to open that repository in Desktop, which calls `getStatus` → `parsePorcelainStatus` → `mapStatus` as part of ordinary repository-open/refresh flow: [5](#0-4) 

No unusual user action beyond viewing/committing changes in a crafted repo is required, and no existing guard rejects or even logs the unmapped code — it is a bare `if`/`if`/`if` chain with no `default: throw` or `assertNever`, unlike the analogous exhaustive-enum patterns elsewhere in the codebase (e.g., `assertNever` usage in `app/src/lib/status.ts:42-43` or `app/src/lib/diff-parser.ts:372-373`) that would have caught this at compile time or runtime.

### Recommendation
Add explicit handling (or at minimum a `log.error`/telemetry event plus a distinct `AppFileStatusKind` such as "Unknown"/"TypeChanged") for status codes containing `T`, and replace the silent fallback at the end of `mapStatus` with a code path that surfaces the real index/workingTree characters instead of defaulting to `'modified'` with no `index`/`workingTree`. At minimum, log the unrecognized `statusCode` so type-change and other uncommon transitions are not misrepresented, and ensure the "hide added-then-deleted" and similar heuristics in `buildStatusMap` are not silently bypassed for entries with unpopulated `index`/`workingTree`.

### Proof of Concept
1. Prepare a repository where a tracked file `foo` is a symlink in the index but has been replaced with a regular file in the working tree (or vice versa), which git reports via a status code containing `T` (e.g., `.T` or `T.`) under `git status --porcelain=2`.
2. Have the victim clone/open this repository in GitHub Desktop and view the Changes list; `getStatus` → `parsePorcelainStatus` → `mapStatus` is invoked as shown in `app/src/lib/git/status.ts:221-235` and `app/src/lib/status-parser.ts:201-426`.
3. Observe that `mapStatus` falls through to the final `return { kind: 'ordinary', type: 'modified', submoduleStatus }` branch (lines 420-425) instead of reflecting the actual type-change, and Desktop's UI/patch generation treats the entry as an ordinary content modification.
4. Confirm via `app/src/lib/git/status.ts:308-318` that the `index`/`workingTree` fields being `undefined` prevents the "added-in-index-but-removed-in-working-tree" suppression logic from ever engaging for this class of status code, meaning any such transition is always surfaced/committed as a plain "Modified" file with no indication of the underlying type change.

(Note: I was not able to fully read the body of `convertToAppStatus` in `app/src/lib/git/status.ts` due to tool-call limits; while its call site and its consumption of the `OrdinaryEntry`'s `type` field are confirmed at lines 302-334 and 128-139, the exact final mapping from `type: 'modified'` to `AppFileStatusKind.Modified` should be verified in the full function body before implementing a fix.)

  const match = changedEntryRe.exec(field)

  if (!match) {
    log.debug(`parseChangedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for changed entry`)

    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    path: match[8],

function buildStatusMap(
  files: Map<string, WorkingDirectoryFileChange>,
  entry: IStatusEntry,
  conflictDetails: ConflictFilesDetails
): Map<string, WorkingDirectoryFileChange> {
  const status = mapStatus(
    entry.statusCode,
    entry.submoduleStatusCode,
    entry.renameOrCopyScore
  )

  if (status.kind === 'ordinary') {
    // when a file is added in the index but then removed in the working
    // directory, the file won't be part of the commit, so we can skip
    // displaying this entry in the changes list
    if (
      status.index === GitStatusEntry.Added &&
      status.workingTree === GitStatusEntry.Deleted
    ) {
      return files
    }
  }

  if (status.kind === 'untracked') {
    // when a delete has been staged, but an untracked file exists with the
    // same path, we should ensure that we only draw one entry in the
    // changes list - see if an entry already exists for this path and
    // remove it if found
    files.delete(entry.path)
  }

  // for now we just poke at the existing summary
  const appStatus = convertToAppStatus(
    entry.path,
    status,
    conflictDetails,
    entry.oldPath
  )

  const initialSelectionType =
    appStatus.kind === AppFileStatusKind.Modified &&
    appStatus.submoduleStatus !== undefined &&
    !appStatus.submoduleStatus.commitChanged
      ? DiffSelectionType.None
      : DiffSelectionType.All

  const selection = DiffSelection.fromInitialSelection(initialSelectionType)

  files.set(
    entry.path,
    new WorkingDirectoryFileChange(entry.path, appStatus, selection)
  )
  return files
