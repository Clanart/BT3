### Title
Missing `updateTotalFactor` call in `cancelUnlock` desynchronizes `totalBoostFactor` from real locked balances - (File: VLMGP.sol)

### Summary
`cancelUnlock(uint256 _slotIndex)` restores a user's effective locked balance (via `totalAmountInCoolDown -= slot.amountInCoolDown`) but never calls `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)`, unlike `startUnlock`, which does call it. Because `ReferralStorage.updateTotalFactor` recomputes `userInfo.factor = sqrt(getUserTotalLocked(_account))` and adjusts the shared `totalBoostFactor` accordingly, skipping it on `cancelUnlock` leaves both the caller's `factor` and the global `totalBoostFactor` permanently stale (lower than the true locked-weight), breaking the invariant `totalBoostFactor == sum(userInfo.factor)`.

### Finding Description
The relevant code path is: [1](#0-0) 

Compare with `startUnlock`, which does keep the invariant consistent by calling the referral hook: [2](#0-1) 

`ReferralStorage.updateTotalFactor` computes the boost factor purely from `IVLMGP(vlMGP).getUserTotalLocked(_account)`: [3](#0-2) 

`getUserTotalLocked` is directly a function of `getUserAmountInCoolDown`, which sums `amountInCoolDown` across a user's slots: [4](#0-3) 

Exploit flow for a user who has registered a referral code (`registerCode`, so `userInfo.myCode != 0` and the account is tracked in `totalBoostFactor`):
1. User has locked amount `L`; `userInfo.factor = sqrt(L)` is folded into `totalBoostFactor`.
2. User calls `startUnlock(X)`. `getUserTotalLocked` drops to `L - X`; `updateTotalFactor` is invoked, correctly setting `factor = sqrt(L - X)` and adjusting `totalBoostFactor` down by `sqrt(L) - sqrt(L - X)`. Invariant still holds.
3. User calls `cancelUnlock(_slotIndex)`. `slot.amountInCoolDown` is zeroed and `totalAmountInCoolDown` is decremented, so `getUserTotalLocked` immediately jumps back to `L` — but `updateTotalFactor` is never called. `userInfo.factor` stays at the stale `sqrt(L - X)`, and `totalBoostFactor` is never restored, remaining understated by `sqrt(L) - sqrt(L - X)`.

Because `totalBoostFactor` is a single global denominator shared by every referrer, this understatement inflates `_calBoosted` for every account with a nonzero `factor`: [5](#0-4) 

That inflated boost feeds directly into `trigger()`'s percentage math, over-allocating `refererAmount`/`refereeAmount` out of `_amount` on every subsequent referral-triggered reward: [6](#0-5) 

No modifier, reentrancy guard, or accounting check prevents this — `cancelUnlock` is only gated by `whenNotPaused` and slot-boundary/cooldown checks, both of which are satisfied by an ordinary unprivileged user performing `startUnlock` then `cancelUnlock` on their own slot.

### Impact Explanation
The bug permanently desynchronizes `totalBoostFactor` from the sum of live `userInfo.factor` values, understating the shared denominator used to compute every referrer's boosted reward share. Any referrer (including the attacker via a second registered account, or any existing referrer) subsequently receives a larger `boosted` percentage than the protocol design intends whenever `trigger()` runs, which increases `refererAmount + refereeAmount` paid out of the reward pool. This is a repeatable, low-cost mechanism to inflate referral-reward payouts (unclaimed yield) at the expense of the reward pool/other participants, matching a High - Theft of unclaimed yield class, though the realized loss magnitude scales with `sqrt(L) - sqrt(L-X)` and the number/weight of concurrent referrers sharing `totalBoostFactor`.

### Likelihood Explanation
Highly feasible: it only requires a normal unprivileged account with any locked MGP and a registered referral code (`registerCode`) to call `startUnlock` followed immediately by `cancelUnlock` on the same slot — both are plain external user actions with no special role. It can be repeated across multiple slots/accounts to accumulate an arbitrarily large permanent gap between `totalBoostFactor` and the true sum of factors, since nothing ever resyncs the value except another `startUnlock` call by the same specific account (which only fixes that one account's own factor, not the accumulated global drift already handed out via `trigger()` in the interim).

### Recommendation
Call `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)` inside `cancelUnlock` (and `unlock`/`forceUnLock`, which have the same gap) right after mutating `totalAmountInCoolDown`/`slot.amountInCoolDown`, so `userInfo.factor` and `totalBoostFactor` are re-derived from the post-mutation `getUserTotalLocked` value every time locked balance changes, preserving the `totalBoostFactor == sum(factor)` invariant at all state-changing entry points.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `ReferralStorage`, and a mock `MasterMagpie`/staking backend; wire `referralStorage` into `VLMGP`.
2. Attacker locks `L` MGP via `lock`, then calls `registerCode(code)` on `ReferralStorage` to activate factor tracking; assert `totalBoostFactor == sqrt(L)`.
3. Attacker calls `startUnlock(X)`; assert `totalBoostFactor == sqrt(L - X)` (invariant holds).
4. Attacker calls `cancelUnlock(slotIndex)`; assert `getUserTotalLocked(attacker) == L` (restored) but `totalBoostFactor` still equals `sqrt(L - X)` — i.e., `totalBoostFactor != sum(all userInfo.factor)`, proving the invariant break.
5. Have `masterMagpie` call `trigger(referee, amount)` for a second referrer/referee pair and confirm `_calBoosted` (via the public `boosted()` getter) returns a larger value than it would if `totalBoostFactor` had been correctly resynced to `sqrt(L)`, and that `refererAmount + refereeAmount` paid out exceeds the protocol-intended share of `amount`.
