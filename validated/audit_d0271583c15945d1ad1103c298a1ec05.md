### Title
PedPoP round-1 encryption key is not bound by the commitments proof-of-knowledge, allowing a relaying attacker to redirect a victim's secret shares - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
Like CVE-2021-23222 (a MITM injecting false responses to a client's first queries despite transport authentication), the first PedPoP DKG message authenticates only the polynomial commitments — not the `enc_key` field carried in the same `EncryptionKeyMessage`. An unprivileged party who relays round-1 messages can substitute the victim's encryption public key with one they control. Every dealer then encrypts the victim's secret shares to the attacker's key, and the attacker recovers the victim's full secret key share.

### Finding Description
`KeyGenMachine::generate_coefficients` computes the round-1 proof of knowledge as `SchnorrSignature::sign(&coefficients[0], r, challenge::<C>(context, i, nonce, &cached_msg))`, where `cached_msg` is built solely from the serialized commitments (`cached_msg.extend(commitments[i].to_bytes())`) [1](#0-0) . The message actually broadcast is `EncryptionKeyMessage { msg: Commitments { commitments, cached_msg, sig }, enc_key }` [2](#0-1) . `enc_key` never enters the challenge.

On receipt, `verify_r1` calls `self.encryption.register(l, msg)` which stores `msg.enc_key()` into `decryption.enc_keys[l]` before the PoK is batch-verified — and the verification challenge again covers only `context, l, sig.R, cached_msg` [3](#0-2) . Nothing cryptographically ties `enc_key` to participant `l` or to the commitments.

In round 2, each dealer encrypts `share_bytes` to `self.decryption.enc_keys[&participant]` via `encrypt()` → `ecdh(key, to)` [4](#0-3) . If `enc_keys[victim]` is the attacker's key, the attacker computes the same ECDH shared point and runs `cipher(context, &ecdh).apply_keystream` to decrypt every `f_i(victim)` share [5](#0-4) .

The shares still satisfy the Pedersen verification (`share_verification_statements` checks against the real commitments), so the victim's `calculate_share` — which the attacker cannot decrypt-forward since the shares were encrypted to the wrong key — simply fails with blame, while the attacker holds `Σ_i f_i(victim) = s_victim` [6](#0-5) .

### Impact Explanation
The attacker recovers one participant's FROST secret key share `s_victim`. Since the victim's verification share `Y_victim = s_victim·G` is public in `ThresholdKeys`, the attacker can produce valid signature shares for that participant index (`verify_share` only checks `s·G = R_l + λ_l·c·Y_l`), letting them impersonate the victim in every future signing session for that group key. Because the swapped key causes the victim to abort (undecryptable shares), the practical result is a repeat-until-success attack on groups where the attacker is also a participant, or share theft combined with selective completion. This is an unauthorized key share recovery reachable entirely by tampering with relayed round-1 bytes.

### Likelihood Explanation
Requires the ability to rewrite `EncryptionKeyMessage` bytes in transit between a participant and the message relay (e.g., a coordinator or gossip layer that forwards `Commitments` messages without re-binding them to the sender's authenticated session — exactly the "false early responses despite channel authentication" shape of the CVE). The library documents an authenticated channel requirement, but authentication of origin does not protect an unsigned field inside the payload; the PoK's existence invites exactly this assumption of coverage. No collusion, no validator compromise, and no broken primitives are needed. Medium likelihood, Medium+ impact → Medium overall.

### Recommendation
Include `enc_key` in the round-1 proof-of-knowledge: append `self.encryption.registration(...)`'s `enc_key.to_bytes()` (or the full serialized `EncryptionKeyMessage`) to `cached_msg` before calling `challenge::<C>` in `generate_coefficients`, and mirror the same byte layout when recomputing the challenge in `verify_r1`. Alternatively, transcript `enc_key` into `challenge()` as a separate `append_message` so the signature covers `(context, participant, nonce, commitments, enc_key)`.
