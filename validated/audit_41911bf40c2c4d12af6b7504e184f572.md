### Title
Stale line-selection indices combined with `--unidiff-zero` allow silent corruption of partially-staged commits - ([File: app/src/lib/git/apply.ts])

### Summary
The VotingEscrow bug is caused by trusting a caller-supplied amount instead of the value actually observed after the external transfer. The analogous invariant break in GitHub Desktop is in `applyPatchToIndex`, which stages a partial commit by combining a `WorkingDirectoryFileChange.selection` (a set of line *indices* computed against the diff that was rendered earlier in the UI) with a **freshly re-fetched** diff, and then applies the resulting patch with `git apply --cached --unidiff-zero`, a flag that explicitly disables Git's normal context-based fuzz matching.

### Finding Description
When a user reviews a diff in the Changes view and selects individual lines/hunks to commit, the selection is stored as an index-based `DiffSelection` tied to the specific diff object shown at that time (`app/src/lib/stores/app-store.ts` `updateChangesWorkingDirectoryDiff`, lines ~3478‑3497, builds `selectableLines` from `hunk.unifiedDiffStart + index` for the diff loaded at that moment). [1](#0-0) 

When the commit is actually created, `applyPatchToIndex` does **not** reuse that same diff object — it re-fetches the diff from disk again immediately before formatting the patch: [2](#0-1) 

`formatPatch` then walks the (newly fetched) `diff.hunks`, and for each line calls `file.selection.isSelected(absoluteIndex)` using the *old* index scheme to decide what to include, drop, or convert to context: [3](#0-2) 

Finally the generated patch is applied with `--unidiff-zero`, a flag that is specifically documented to allow patches with zero lines of context to apply — this removes Git's normal safety net of verifying that the surrounding context in the hunk still matches the file before writing: [4](#0-3) 

If the underlying working-tree file changes between the moment the UI diff was rendered/selected and the moment `applyPatchToIndex` runs — e.g. because a `clean`/`smudge` filter defined via `.gitattributes` in a cloned/fetched repository rewrites the file on checkout, a background fetch/checkout triggered elsewhere in Desktop updates the file, or an external editor/process modifies it — the line counts and offsets recorded in the newly-formatted hunk header (`oldCount`/`newCount` in `formatPatch`) no longer correspond to what the user actually selected. Because `--unidiff-zero` disables context verification, `git apply --cached` will not reject a hunk whose surrounding lines don't match; it applies strictly by line offset. The result is that the index (and subsequently the commit that gets pushed) can silently contain different content than what the user reviewed and intended to stage — a direct parallel to VotingEscrow crediting a `locked` amount that doesn't match what was actually received.

### Impact Explanation
This can silently corrupt what the user commits and pushes: content the user never reviewed or explicitly opted into can end up in a commit, or content the user selected can be silently dropped/misplaced, without any error surfaced by `git apply` because context checking is disabled via `--unidiff-zero`. Since attacker-controlled repository content (e.g. `.gitattributes`-driven smudge/clean filters, or other checkout-time mutation vectors reachable from a cloned/fetched repository) can trigger working-tree mutation between diff-render time and stage time, this fits the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitability depends on winning a race between diff-render and stage/commit, and on the attacker's repository content being able to trigger a working-tree mutation in that window (e.g., via filter/hook side effects, background refreshes, or other file-changing operations Desktop performs concurrently). I was not able to fully verify, within the available tooling, an exact attacker-triggerable trigger point that mutates the working tree in that specific window (e.g., whether a smudge filter re-runs on an already-checked-out file, or whether another Desktop background operation like a fetch/prune can touch working-tree file content while a commit UI session is open). This is a plausible but not fully proven end-to-end trigger, so likelihood should be treated as uncertain/lower until that mutation vector is concretely demonstrated.

### Recommendation
- Re-validate the file's diff immediately before formatting the patch and reject/re-prompt if the diff has changed since the user's selection was made, rather than blindly reusing stale line-selection indices against a freshly fetched diff.
- Avoid `--unidiff-zero` where possible, or add an explicit content/hash check (e.g., compare a hash of the file content at selection time vs. staging time) before calling `git apply --cached`, refusing to stage if they differ.
- Surface an error to the user instead of silently applying a patch whose context can no longer be verified.

### Proof of Concept
Conceptual reproduction (not independently executed against a live Desktop build due to tool limitations):
1. Clone/open a repository containing a `.gitattributes` clean/smudge filter (or otherwise arrange for the working-tree file to be rewritten by a background process) for a tracked text file.
2. In Desktop's Changes view, open the diff for that file and select a subset of lines/hunks to commit (partial selection), leaving the tab open.
3. Trigger the filter/background process (e.g., via a checkout, LFS smudge re-run, or another Desktop operation) to mutate the file's line count/content without the user re-reviewing the diff.
4. Click "Commit" — `applyPatchToIndex` (`app/src/lib/git/apply.ts` lines 52-61) re-fetches the diff, but `formatPatch` (`app/src/lib/patch-formatter.ts` lines 143-171) still maps the old selection indices onto the new hunk lines, and `git apply --cached --unidiff-zero` (line 55 in `apply.ts`) applies the resulting patch without validating context.
5. Inspect the resulting commit: it can contain content that differs from what was displayed/selected in the UI at selection time, silently corrupting what gets committed and subsequently pushed.
