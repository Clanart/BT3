This confirms the mechanism: `is_kickoff_malicious` in `core/src/verifier.rs` explicitly compares `operator_xonly_pk != kickoff_data.operator_xonly_pk` from the OP_RETURN against whichever operator sends a kickoff, and treats a mismatch (or a missing/unparseable OP_RETURN) as malicious — this is exactly the mechanism that would permanently block the honest operator's kickoff/reimbursement if the confirmed payout's OP_RETURN doesn't match their key.### Title
Unauthenticated OP_RETURN attribution in `create_payout_txhandler` allows payout-credit hijacking via SIGHASH_SINGLE|ANYONECANPAY replay - (`core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The withdrawer's Taproot signature is checked only against input 0's sighash with `SinglePlusAnyoneCanPay` enforced, which cryptographically commits solely to the spent outpoint and output[0] (the user's payout). The anchor output and the OP_RETURN output carrying `operator_xonly_pk` — the only field used later to decide who gets reimbursement credit — are unauthenticated by the user, so anyone who observes a broadcast-but-unconfirmed payout transaction can rebuild a conflicting transaction with the same signature, the same output[0], but a different OP_RETURN, and race it to confirmation.

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk (DB, from OP_RETURN of the confirmed payout tx) == operator_who_actually_funded_output[0]`.

- `parse_withdrawal_sig_params` enforces `TapSighashType::SinglePlusAnyoneCanPay` on the user signature [1](#0-0) .
- `Operator::withdraw` verifies this signature only against `payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` [2](#0-1) .
- `calculate_pubkey_spend_sighash` uses `Prevouts::One` for the `*PlusAnyoneCanPay` types, meaning only input 0's own prevout is committed, and `SIGHASH_SINGLE` semantics only bind output[0] [3](#0-2) .
- `create_payout_txhandler` builds output[0] (payout), output[1] (anchor), output[2] (OP_RETURN with `operator_xonly_pk`) [4](#0-3) . The OP_RETURN output is never covered by the user's signature.
- Once a tx is broadcast, its full witness (including the user's schnorr signature and sighash byte) is public in the mempool. An attacker can therefore build a *new*, conflicting transaction spending the same `in_outpoint`, reproducing output[0] byte-for-byte (required to keep the signature valid), but with a different OP_RETURN payload and its own arbitrary funding inputs/outputs (unconstrained by `ANYONECANPAY`), then get it confirmed instead (ordinary fee-based mempool/miner selection on a double-spent input — not reliant on malicious peers or hashrate).
- `Verifier::update_finalized_payouts` blindly parses whichever OP_RETURN ends up in the confirmed tx and stores it as `payout_payer_operator_xonly_pk`, with no check that the named key actually funded the payment [5](#0-4) .
- `Verifier::is_kickoff_malicious` later compares this DB value against `kickoff_data.operator_xonly_pk` from the real funding operator's kickoff, and treats any mismatch (or missing key) as malicious, permanently blocking that operator's kickoff/reimbursement path [6](#0-5) .

No existing guard re-validates that the OP_RETURN's `operator_xonly_pk` corresponds to whoever supplied the additional funding inputs of the confirmed transaction; the sighash scope simply never covers it.

### Impact Explanation
Once the attacker's competing transaction confirms with a different (or bogus/non-operator) `operator_xonly_pk` in the OP_RETURN, the withdrawal UTXO is irrevocably spent, so the honest operator who actually fronted the withdrawal can never re-submit their own payout tx for that withdrawal, and `is_kickoff_malicious` will flag their kickoff as malicious because the DB's recorded payer key won't match theirs. This matches the Critical category "an honest operator permanently unable to be reimbursed" — the deposited bridge amount's reimbursement leg becomes unclaimable by any legitimate registered operator, even though the user's withdrawal itself was satisfied. The attack is repeatable across any withdrawal an operator has already broadcast but not yet confirmed.

### Likelihood Explanation
The attacker needs: (1) to observe a broadcast-but-unconfirmed payout transaction in the mempool (trivial, public data), (2) to supply their own funding inputs covering the exact same output[0] amount, and (3) to get their conflicting transaction confirmed instead (feasible via a higher fee, standard replace-by-fee behavior, not requiring malicious nodes or majority hashrate). The main cost is that the attacker must front capital equal to the withdrawal amount to construct the competing output[0], which limits casual exploitation but does not prevent a well-funded griefer (e.g., a rival wanting to sabotage a competing operator) from executing it repeatably across withdrawals.

### Recommendation
Bind the operator identity to the user's signature scope. Options: require the sighash type to cover all outputs (e.g., use `SIGHASH_ALL|ANYONECANPAY` semantics restricted to the payout output plus OP_RETURN), or have the withdrawer additionally commit to a specific chosen `operator_xonly_pk` as part of the signed message/off-chain protocol so a substituted OP_RETURN invalidates the signature, and/or require `update_finalized_payouts` to cross-check the OP_RETURN pubkey against the actual funding inputs' provenance (e.g., verify against a registered operator whose collateral/withdrawal-fee wallet funded the transaction) rather than trusting unauthenticated OP_RETURN bytes.

### Proof of Concept
In a `cargo test` (regtest, no mainnet/live Citrea) under `core/src/test/deposit_and_withdraw_e2e.rs`-style harness:
1. Register a deposit and withdrawal; obtain `in_signature`/`in_outpoint`/`output_txout` via `generate_withdrawal_transaction_and_signature`.
2. Call `Operator::withdraw` for operator A, capture the resulting funded, signed `payout_txhandler` transaction (do not mine it — leave it in mempool).
3. Independently call `builder::transaction::create_payout_txhandler` with the same `input_utxo`, identical `output_txout`, the same `user_sig`, but a different `operator_xonly_pk` (operator B's or an arbitrary keypair), then fund it with a second wallet's UTXOs at a higher fee rate and broadcast it.
4. Assert `txhandler.set_p2tr_key_spend_witness` succeeds and `SECP.verify_schnorr` passes for the second transaction (proving the same user signature is valid for a different OP_RETURN).
5. Mine to confirm the second (attacker) transaction, and assert operator A's original transaction is evicted/rejected by the node (double-spend).
6. Run `Verifier::update_finalized_payouts` and assert `get_payout_info_from_move_txid` returns operator B's (or the arbitrary) `xonly_pk`, not operator A's.
7. Attempt operator A's kickoff flow and assert `is_kickoff_malicious` returns `true` (or the kickoff-vs-payout mismatch check fails), proving operator A — who funded the payout — cannot be reimbursed.

pub fn create_payout_txhandler(

    output_txout: TxOut,

    _network: bitcoin::Network,

    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
