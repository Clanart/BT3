### Title
Legacy `bank` precompile `send` versions (v5.5.2–v6.4.0) transfer tokenfactory coins via `bankKeeper.SendCoins` directly, bypassing the `DenomAllowList` restriction enforced by the `MsgSend` message server - (File: precompiles/bank/legacy/v552/bank.go)

### Summary
The bank precompile is versioned (`precompiles/bank/setup.go`), and each historical version remains compiled into the binary and dispatched for its corresponding upgrade window via `utils.VersionedPrecompiles` [1](#0-0) . The current/latest `send` implementation routes the transfer through `p.bankMsgServer.Send(...)`, which enforces the tokenfactory `DenomAllowList` restriction on both sender and receiver before moving funds [2](#0-1) . However, every legacy implementation (`v552`, `v580`, `v600`, `v620`, `v630`, `v640`, etc.) instead calls `p.bankKeeper.SendCoins(...)` directly [3](#0-2) [4](#0-3) , and `BaseSendKeeper.SendCoins`/`sendCoinsWithoutAccCreation` never calls `IsInDenomAllowList` — that check exists only in the `msgServer.Send`/`MultiSend` handlers [5](#0-4) [6](#0-5) .

### Finding Description
The tokenfactory `AllowList` is a permission mechanism analogous to the "restricted" policy in the referenced advisory: a denom admin sets `DenomAllowList` intending to restrict which addresses may send or receive a `factory/...` denom (`x/tokenfactory` `MsgUpdateDenom`/`AllowList`, enforced in `BaseSendKeeper.IsInDenomAllowList` [7](#0-6) ). The enforcement, however, was implemented only at the Cosmos `msgServer.Send`/`MultiSend` layer, not inside the lower-level `SendCoins` keeper method that actually moves balances. Any code path that calls `bankKeeper.SendCoins` directly instead of going through the message server bypasses the allow-list check entirely — exactly the kind of "restriction exists on paper but the enforced primitive doesn't apply it" gap described in the Rancher PSP advisory.

The EVM `bank` precompile is one such caller. Its current version was fixed to route through `bankMsgServer.Send` (which does check the allow list), but the legacy precompile implementations that remain compiled and dispatched for older upgrade heights (`v552`, `v555`? note v562/v580/v600/v601/v603/v605/v606/v610/v614/v620/v630/v640) call `bankKeeper.SendCoins` directly, e.g.: [8](#0-7) 

These versions are still present in `utils.VersionedPrecompiles` and selected based on the upgrade name associated with the historical chain height being replayed [1](#0-0) .

### Impact Explanation
If a tokenfactory denom admin relies on `DenomAllowList` to restrict transfers of a compliance-sensitive or restricted asset (e.g., a KYC-gated stablecoin, or a denom meant to be non-transferable outside an allow-listed set of addresses), a caller can bypass that restriction entirely by invoking the EVM bank precompile's `send`/`sendNative` method through the pointer/EVM address associated with that denom, provided the call is dispatched to one of the legacy precompile versions. This allows unauthorized transfer of a restricted token to/from addresses that were deliberately excluded from the allow list, defeating the token issuer's access-control guarantee — a direct "unauthorized transfer via precompile" outcome matching the required impact criteria.

### Likelihood Explanation
Reachability requires that a transaction be processed/replayed under one of the older upgrade names for which the vulnerable legacy bank-precompile implementation is still wired into `VersionedPrecompiles`, and that the caller be the ERC20 native pointer contract for a tokenfactory denom that has an active `DenomAllowList` (only "pointer" contracts are authorized to invoke `send`, per the `pointer.Cmp(caller)` check [9](#0-8) ). Any unprivileged EVM user holding/controlling such an ERC20 pointer contract for a restricted tokenfactory denom can trigger this bypass, since the "unauthorized transfer" is fully realizable from a single submitted EVM transaction with no special privilege beyond calling the ERC20 pointer's `transfer`.

### Recommendation
Enforce `IsInDenomAllowList` (and `BlockedAddr`) checks directly inside `BaseSendKeeper.SendCoins`/`SendCoinsWithoutAccCreation` in `sei-cosmos/x/bank/keeper/send.go`, rather than only in the `msgServer.Send`/`MultiSend` handlers, so that every caller of the low-level keeper — including all historical/legacy precompile code paths that must remain byte-for-byte reproducible for replay — is subject to the same restriction. Alternatively, patch each legacy bank-precompile `send` implementation to route through `bankMsgServer.Send` instead of calling `bankKeeper.SendCoins` directly.

### Proof of Concept
1. Tokenfactory denom admin creates `factory/{admin}/restricted` and calls `MsgUpdateDenom` with an `AllowList` containing only a small set of approved Sei addresses.
2. An ERC20 native pointer is created for the denom via the `pointer` precompile's `AddNativePointer`.
3. A holder of the restricted token whose EVM-associated Sei address is NOT in the `AllowList` calls `transfer(to, amount)` on the ERC20 pointer contract for a block/replay path dispatched to one of the legacy `bank` precompile versions (e.g., `v6.2.0`/`v6.3.0`/`v6.4.0`), which internally invokes the `bank` precompile's `send` method.
4. The legacy `send` implementation calls `p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, coins)` directly (see `precompiles/bank/legacy/v640/bank.go:145-156`), which succeeds because `SendCoins`/`sendCoinsWithoutAccCreation` never checks `IsInDenomAllowList`.
5. The restricted transfer completes despite neither the sender nor receiver being on the `AllowList`, whereas the same `MsgSend` submitted through the native Cosmos tx path would have been rejected with `"... is not allowed to send/receive funds"`.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
