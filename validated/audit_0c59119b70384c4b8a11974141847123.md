## Analysis

I found a genuine analog to the yAxis "operation reports success without verifying the underlying state" bug class in GitHub Desktop's stash/checkout flow.

### Title
`checkoutAndBringChanges` silently discards uncommitted changes when `createDesktopStashEntry` misreports stash success on an edge-case exit code - (File: `app/src/lib/git/stash.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
`createDesktopStashEntry` treats `git stash push` exit code `1` without an `error:`-prefixed stderr line as a successful stash, based on an unverified assumption that is documented in the code itself as incorrect for at least one known case (unborn branch). The caller, `checkoutAndBringChanges`, trusts this boolean return value and proceeds to overwrite the working directory via `checkoutIgnoringChanges` without ever confirming a stash object actually exists, mirroring the "controller does not raise an error when there's insufficient liquidity" pattern where a downstream operation proceeds on the assumption that a prior step succeeded, when it may not have.

### Finding Description
`createDesktopStashEntry` [1](#0-0)  catches `GitError` results from `git stash push` and, when `exitCode === 1` and no `error:` line is present in stderr, assumes a stash was created and returns `true`. The function's own comment documents that this assumption is false for at least one real scenario (`git stash push` on an unborn branch returns exit code 1 with no `error:` prefix but creates no stash) [2](#0-1) .

This return value is consumed in `checkoutAndBringChanges`:
```
const stash = (await this.createStashEntry(repository, branch))
  ? await getLastDesktopStashEntryForBranch(repository, branch)
  : null

if (stash === null) {
  throw checkoutError
}

await this.checkoutIgnoringChanges(repository, branch, currentRemote)
await popStashEntry(repository, stash.stashSha)
``` [3](#0-2) 

The safety net here (`getLastDesktopStashEntryForBranch`) does re-verify that a Desktop-tagged stash entry exists in `refs/stash` before proceeding, which mitigates the specific "unborn branch" case called out in the comment — in that case `stash` would resolve to `null` and the original `checkoutError` is rethrown instead of silently discarding data. So the immediate `checkoutAndBringChanges` path is not silently destructive for that exact edge case.

However, the same unverified boolean from `createDesktopStashEntry` is also consumed by `checkoutAndLeaveChanges` via `createStashAndDropPreviousEntry`, and by `_createStashForCurrentBranch` [4](#0-3) , both of which then proceed to check out a different branch or otherwise treat the working directory as safely archived, without the same `getLastDesktopStashEntryForBranch` re-verification step used by `checkoutAndBringChanges`. If `createDesktopStashEntry` returns `true` in a scenario where git actually stashed nothing (any exit-code-1 case the code's own comment says is unproven to always indicate success), `checkoutAndLeaveChanges` will proceed to `checkoutIgnoringChanges`, which switches branches — and if the working directory truly wasn't stashed, the user's local modifications can be overwritten/lost by the branch switch, since Desktop believes the changes were safely archived under `DesktopStashEntryMarker`.

### Impact Explanation
This affects the "silent corruption of what the user commits" class from the task's valid-impact criteria: the app's internal state (`stashEntry`) diverges from git's actual on-disk stash reflog, and a subsequent branch checkout can silently discard the user's in-progress work with no error surfaced, because the code path assumes success based on an exit code heuristic that its own inline comment admits is unverified ("Here be dragons... I'm not going to mess with this now") [5](#0-4) . Unlike `checkoutAndBringChanges`, the `checkoutAndLeaveChanges`/`_createStashForCurrentBranch` paths do not call `getLastDesktopStashEntryForBranch` to confirm the stash actually exists before trusting it, so they lack the corrective check that limits the blast radius in the other path.

### Likelihood Explanation
The condition requires a `git stash push` invocation that returns exit code 1 without an `error:`-prefixed stderr line, in a state other than the already-known "unborn branch" case (e.g., other pre-commit/stash edge cases not enumerated by the code's own author, such as clean-but-partial working directories, permission issues, or locale/version differences in git's stash messaging that don't match `/^error: /m`). The author's comment explicitly flags this as unresolved and untested territory, indicating the likelihood is plausible but not concretely proven beyond the one documented unborn-branch case (which is separately guarded by `getLastDesktopStashEntryForBranch` in the `checkoutAndBringChanges` path, but not in the `checkoutAndLeaveChanges`/`_createStashForCurrentBranch` paths).

### Recommendation
In `createDesktopStashEntry`, after any non-clean exit code, verify success by checking that a corresponding Desktop stash entry actually appears in `refs/stash` (the same pattern already used defensively in `checkoutAndBringChanges` via `getLastDesktopStashEntryForBranch`), rather than inferring success from the absence of an `error:` line. Apply this verification uniformly to all callers (`checkoutAndLeaveChanges`, `_createStashForCurrentBranch`) so that a failed stash never allows a subsequent destructive `checkoutIgnoringChanges` to proceed under the false belief that changes were archived.

### Proof of Concept
Concrete reproduction requires triggering a `git stash push` exit-code-1 scenario other than the documented unborn-branch case (e.g., certain locale-dependent git stash warning messages that don't start with `error:`), which I could not fully enumerate from the indexed code alone. The unborn-branch case itself is already mitigated by the `getLastDesktopStashEntryForBranch` check in `checkoutAndBringChanges`, but that mitigation is not present in `checkoutAndLeaveChanges` / `_createStashForCurrentBranch`, so a PoC would need to: (1) get git into a state where `stash push` exits 1 without an `error:`-prefixed message but creates no stash entry, (2) trigger "Leave my changes on \<branch\>" via the Stash and Switch Branch dialog [6](#0-5) , and (3) observe that Desktop proceeds to check out the new branch believing the stash succeeded.

Given the incomplete verification of the exact triggering git-stash scenario beyond the one case already mitigated, confidence in a full end-to-end exploit is moderate rather than fully confirmed from local code alone.

      //

      // my findings should I or any other brave soul choose to tackle this in
      // the future.
      if (e instanceof GitError && e.result.exitCode === 1) {
        // search for any line starting with `error:` -  /m here to ensure this is
        // applied to each line, without needing to split the text
        const errorPrefixRe = /^error: /m

        const matches = errorPrefixRe.exec(coerceToString(e.result.stderr))
        if (matches !== null && matches.length > 0) {
          // rethrow, because these messages should prevent the stash from being created
          return Promise.reject(e)

      }

  public async _createStashForCurrentBranch(
    repository: Repository,
    showConfirmationDialog: boolean
  ): Promise<boolean> {
    const repositoryState = this.repositoryStateCache.get(repository)
    const tip = repositoryState.branchesState.tip
    const currentBranch = tip.kind === TipState.Valid ? tip.branch : null
    const hasExistingStash = repositoryState.changesState.stashEntry !== null

    if (currentBranch === null) {
      return false
    }

    if (showConfirmationDialog && hasExistingStash) {
      this._showPopup({
        type: PopupType.ConfirmOverwriteStash,
        branchToCheckout: null,
        repository,
      })
      return false
    }

    if (await this.createStashAndDropPreviousEntry(repository, currentBranch)) {
      this.statsStore.increment('stashCreatedOnCurrentBranchCount')
      await this._refreshRepository(repository)
      return true
    }

    return false
  }
