## Finding: Confirmed — No Host-Match Check or Confirmation Prompt Before `openExternal`

### Title
Unvalidated check-run/job-step URL from Actions API metadata is passed directly to `shell.openExternal` with no host/scheme allow-listing - (File: `app/src/ui/check-runs/ci-check-run-actions-job-step-list.tsx`)

### Summary
Tracing the click path from `CICheckRunActionsJobStepListItem.onViewJobStepExternally` through to the Electron main process confirms there is **no confirmation dialog and no host-match assertion** against `repository.gitHubRepository.endpoint` anywhere on this path before `shell.openExternal` is invoked.

### Finding Description
The click handler chain is:

1. `CICheckRunActionsJobStepListItem` renders a button whose `onClick` fires `onViewJobStepExternally`, which simply forwards `this.props.step` up to the parent callback with no validation: [1](#0-0) 

2. `CICheckRunActionsJobStepList` passes the callback straight through as `onViewJobStep`: [2](#0-1) 

3. Two consumers wire this up: `ci-check-run-popover.tsx` and `pull-request-checks-failed.tsx`. Both build the URL with `getCheckRunStepURL`, which concatenates `checkRun.htmlUrl` (an Actions API-supplied field, e.g. a check run's `details_url`) with the step number, with **no scheme or host check**: [3](#0-2) [4](#0-3) [5](#0-4) 

4. The URL then flows straight into `dispatcher.openInBrowser(url)` → `AppStore._openInBrowser` → `shell.openExternal(url)`, with no comparison to `repository.gitHubRepository.endpoint` anywhere in this chain: [6](#0-5) 

5. Finally, in the main process, the IPC handler for `open-external` only *logs* when the URL begins with `http://`/`https://` — it does **not** block or validate any other scheme (e.g. `file://`, `javascript:`, custom/UNC handlers), and unconditionally calls `shell.openExternal(path)`: [7](#0-6) 

At no point in this call chain — click handler, `getCheckRunStepURL`, `dispatcher.openInBrowser`, `AppStore._openInBrowser`, or the `open-external` IPC handler — is `checkRun.htmlUrl` validated against `repository.gitHubRepository.endpoint` or restricted to `http(s)` schemes. The value `checkRun.htmlUrl` originates from the Checks API `details_url` field, which is set by whichever GitHub App/CI integration created the check run — this is attacker-influenced data if a malicious/compromised CI integration is installed on the repository, not a Desktop-generated URL.

### Impact Explanation
Because the destination URL is unvalidated and attacker-influenced, a malicious check-run provider could set `details_url` to something other than an `https://github.com/...` link — e.g. a `file://` or UNC path, or a URL leading to credential-phishing pages that spoof GitHub login. Depending on OS/Electron/Chromium handling of `shell.openExternal`, such URLs can be used for local file access disclosure, NTLM credential leakage via UNC-path elicitation, or launching of other locally registered custom URI-scheme handlers — all without any confirmation step warning the user that the destination is not GitHub.com.

### Likelihood Explanation
Likelihood is moderate: it requires either a malicious/compromised third-party CI/Checks integration installed on the target repository, or an attacker able to control the `details_url` metadata returned in the Checks API response for a repository the victim has cloned/is tracking in Desktop. This is a reasonably attainable position (repository owners frequently grant third-party Actions/Apps check-run creation rights), which fits the "repository content / API object" attacker model in scope.

### Recommendation
Before calling `dispatcher.openInBrowser`/`shell.openExternal` with a URL sourced from Checks API metadata (`checkRun.htmlUrl`, `step` data), validate that the URL's origin matches `repository.gitHubRepository.endpoint` (or is restricted to `https:` scheme and a known GitHub host allowlist), consistent with how other GitHub Desktop link-opening surfaces (e.g., markdown link click handling) should be hardened. Reject or prompt the user for confirmation when the URL host doesn't match the expected GitHub endpoint.

### Proof of Concept
1. Register/compromise a check-run-creating GitHub App on a public test repository.
2. Set the check run's `details_url` to a non-GitHub value (e.g., a UNC path or a credential-phishing URL) instead of a github.com URL.
3. In GitHub Desktop, open the PR/branch check-run popover or the "checks failed" notification for that check run and click the job step's "View on GitHub" external-link icon (`CICheckRunActionsJobStepListItem`).
4. Observe that `getCheckRunStepURL` builds the URL directly from the malicious `details_url` and `dispatcher.openInBrowser` invokes `shell.openExternal` on it with no confirmation dialog or host check, confirming the missing validation traced above. [8](#0-7)

```typescript
export function getCheckRunStepURL(
  checkRun: IRefCheck,
  step: IAPIWorkflowJobStep,
  repository: GitHubRepository,
  pullRequestNumber: number
): string | null {
  if (checkRun.htmlUrl === null && repository.htmlURL === null) {
    // A check run may not have a url depending on how it is setup.
    // However, the repository should have one; Thus, we shouldn't hit this
    return null
  }

  const url =
    checkRun.htmlUrl !== null
      ? `${checkRun.htmlUrl}/#step:${step.number}:1`
      : `${repository.htmlURL}/pull/${pullRequestNumber}`

  return url
}
```
