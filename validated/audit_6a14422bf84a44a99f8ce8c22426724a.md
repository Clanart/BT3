## Title
App Proxy request signature verification omits timestamp freshness check, permitting indefinite replay of captured signed requests - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` validates only that the `signature` query parameter matches an HMAC computed over the other query parameters (including `timestamp`). It never checks that the `timestamp` value is recent, so any previously captured, validly signed app-proxy URL remains fully valid forever and can be replayed by anyone who obtains it.

### Finding Description
`query_string_valid?` extracts `signature` from the query string, recomputes the HMAC over the remaining parameters (which include `timestamp`), and compares it with `ActiveSupport::SecurityUtils.secure_compare`: [1](#0-0) 

`timestamp` is treated purely as opaque signed data — like `latestRoundData`'s `timeStamp` in the referenced oracle bug, it is present in the payload but the value itself is never validated for staleness. There is no check equivalent to "timestamp must not be older than N minutes/hours"; the only guard is the HMAC signature integrity check, not a freshness check.

This is the same bug class as the reported oracle issue: a timestamp field exists and is nominally covered by an integrity mechanism, but the consuming code performs no bound/freshness check on it, so stale (here, arbitrarily old) signed data is accepted as valid indefinitely.

Contrast this with the webhook and OAuth-callback signed inputs in this gem, where HMAC validity is the only defense as well, but Shopify's webhook delivery model relies on delivery-time freshness guarantees outside the app; the app-proxy signature, by contrast, is generated once per storefront request and can be captured (via browser history, shared/bookmarked URLs, proxy/CDN logs, Referer headers leaking to third-party resources, etc.) and replayed by an unrelated party at any later time, since `verify_proxy_request` accepts it unconditionally as long as the signature matches: [2](#0-1) 

### Impact Explanation
Any controller that includes `ShopifyApp::AppProxyVerification` (the gem's generated `AppProxyController` and any custom app-proxy controllers) will accept a captured, previously-valid signed request at any point in the future — there is no expiry window enforced on `timestamp`. Depending on what the app-proxy endpoint does (e.g., issuing discounts, reading/mutating shop or customer data, triggering an app action tied to a specific storefront visit), an attacker who captures one signed proxy URL (from logs, history, or a leaked link) can replay it indefinitely to repeat that specific action, even long after the shop/session context that generated it is no longer valid. This is a genuine "accepted forged/stale signed request" condition reachable from any unauthenticated actor who obtains the URL, since the endpoint itself is reachable by an anonymous storefront visitor.

### Likelihood Explanation
Medium: it requires the attacker to obtain a previously issued signed app-proxy URL (e.g., via Referer leakage, browser history, shared/bookmarked links, logs), which is a realistic capture vector for storefront-triggered requests, but it is not a zero-interaction bypass since some prior legitimate request must have been generated and captured.

### Recommendation
Add a freshness check on the `timestamp` query parameter in addition to the HMAC check, rejecting requests whose `timestamp` is older than a defined window (e.g., a few minutes), mirroring Shopify's own guidance for app-proxy request verification:

```ruby
def query_string_valid?(query_string)
  query_hash = Rack::Utils.parse_query(query_string)

  signature = query_hash.delete("signature")
  return false if signature.nil?

  timestamp = query_hash["timestamp"].to_i
  return false if timestamp.zero? || (Time.now.to_i - timestamp) > MAX_ALLOWED_SKEW

  ActiveSupport::SecurityUtils.secure_compare(
    calculated_signature(query_hash),
    signature,
  )
end
```

### Proof of Concept
1. A storefront visitor loads a page that triggers an app-proxy request, e.g. `GET /apps/my-app?shop=some-shop.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid_hmac>`.
2. The URL (with its valid signature) is captured by an unrelated party (e.g., via `Referer` header leakage to a third-party resource loaded on the same page, shared link, or proxy/CDN access log).
3. At any later time, the captured party replays the exact same URL to the app-proxy endpoint.
4. `ShopifyApp::AppProxyVerification#verify_proxy_request` recomputes the HMAC over the same parameters and it still matches, so the request is accepted with no check that `timestamp=1466106083` corresponds to "now" as demonstrated by the existing passing test using a fixed historical timestamp: [3](#0-2) .
