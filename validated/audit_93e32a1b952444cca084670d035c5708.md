### Title
Reward sniping in `BaseRewardPool` due to lump-sum, non-time-weighted `rewardPerTokenStored` accounting - (File: `rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool.rewardPerToken()` simply returns `rewards[_rewardToken].rewardPerTokenStored` [1](#0-0) , and this value is only updated in one place: `_provisionReward()`, which is invoked whenever new rewards are queued (`queueNewRewards`) or donated (`donateRewards`) to the pool [2](#0-1) . The update is a single lump-sum credit computed from the pool's `totalStaked()` **at the instant the reward arrives**, with no time-weighting of how long any given staker's balance has been present: [3](#0-2) 

This is the exact same root-cause class as the `LendingLedger` finding: a user's share of a reward is determined by a balance snapshot rather than by the duration the balance was actually held during the period the reward accrued over.

### Finding Description
Unlike a Synthetix-style `rewardRate`/`periodFinish` streaming model, `BaseRewardPool` credits the entire incoming reward amount to `rewardPerTokenStored` in one shot, based on whatever `totalStaked()` (i.e. `IERC20(stakingToken).balanceOf(operator)` in `MasterMagpie`) happens to be at that exact moment [4](#0-3) . A user's `earned()` amount is `balanceOf(_account) * (rewardPerToken - userRewardPerTokenPaid) / 10**decimals + userRewards`, meaning the moment `rewardPerTokenStored` jumps up, every currently-staked wallet's proportional share of that increase is fixed, regardless of whether they staked one second earlier or one week earlier [5](#0-4) .

An ordinary wallet can call `MasterMagpie.deposit(_stakingToken, _amount)` immediately before a `queueNewRewards`/`donateRewards` call lands (or in the same transaction sequence, e.g., front-running a harvest that eventually pushes rewards into the rewarder), then call `MasterMagpie.withdraw(_stakingToken, _amount)` right after, and still capture their full proportional share of that reward injection — exactly mirroring the `LendingLedger` bug where depositing at 23:59 and withdrawing at 00:00 captured a full week's reward. Here the "epoch" is effectively a single block/transaction instead of a week, but the underlying defect (reward entitlement based on an instantaneous balance snapshot rather than time-weighted presence) is identical.

### Impact Explanation
This allows unprivileged wallets to systematically dilute honest long-term stakers' rewards by timing deposits around reward injections, extracting yield they did not economically earn. This is a theft/dilution of unclaimed yield belonging to legitimate long-term stakers in every pool that uses `BaseRewardPool` (and its `BaseRewardPoolV2`/`mWOMSVBaseRewarder` variants, which share the identical `_provisionReward` pattern) [6](#0-5) [7](#0-6) .

### Likelihood Explanation
Reachable by any ordinary wallet with no privileged role: it only requires normal `deposit`/`withdraw` calls into `MasterMagpie` timed around a permissionless or foreseeable reward injection (e.g., a public harvest routine that eventually calls `queueNewRewards`). Repeated across every reward distribution, this is a persistent, exploitable pattern rather than a one-off edge case.

### Recommendation
Replace the lump-sum `rewardPerTokenStored` update in `_provisionReward` with a time-weighted streaming model (rewardRate over a fixed duration, à la Synthetix `StakingRewards`), or otherwise require a minimum bonding/holding period before a deposit is eligible to receive a share of newly queued rewards, so that reward entitlement reflects actual duration of stake rather than an instantaneous balance snapshot.

### Proof of Concept
1. Attacker observes (or front-runs) a pending `BaseRewardPool.queueNewRewards()`/`donateRewards()` call (e.g., triggered via `WombatStaking` harvest).
2. Attacker calls `MasterMagpie.deposit(_stakingToken, largeAmount)` in the block/transaction immediately preceding the reward provisioning.
3. `_provisionReward` executes, updating `rewardPerTokenStored += amountReward * scale / totalStaked()` using the now-inflated `totalStaked()` that includes the attacker's just-deposited balance [8](#0-7) .
4. Attacker immediately calls `MasterMagpie.withdraw(_stakingToken, largeAmount)` and then claims via `getReward`, receiving a full proportional share of the reward despite having staked for a negligible amount of time, diluting the share available to genuine long-term stakers.

**File:** rewards/BaseRewardPool.sol (L297-320)
```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
```
