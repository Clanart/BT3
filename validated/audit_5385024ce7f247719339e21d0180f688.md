### Title
Inverted subtraction in `created_output` silently drops all payments under a fee-reduced branch output - (File: processor/src/multisigs/scheduler/utxo.rs)

### Summary
The external report's bug class is an incorrect quantity used inside an edge-case branch (refund computed against `block.timestamp` instead of the relevant event). The same class exists in Serai's UTXO scheduler: `created_output` amortizes the fee charged to a branch output by computing `to_amortize = actual - expected`, where `actual` is the post-fee on-chain amount and `expected` is the pre-fee planned amount. Since the fee reduces the output, `actual < expected`, so the subtraction is inverted.

### Finding Description
In `Scheduler::created_output` (processor/src/multisigs/scheduler/utxo.rs), the branch outputs created by a prior transaction report `expected` (the planned amount, used as the `queued_plans` key) and `actual` (what was actually created after fees). The fee to amortize across child payments is `expected - actual`, but the code computes:

```rust
let mut to_amortize = actual - expected;
```

`PostFeeBranch` records `expected: initial_amount` and `actual: Some(post_fee_amount)` in `prepare_send` (processor/src/networks/mod.rs), and `initial_amount >= post_fee_amount` always holds because the amortization loop only ever decreases payment amounts. Therefore `actual - expected` underflows for every branch output that paid any fee. In release builds the u64 wraps to a near-`u64::MAX` value; the `while to_amortize != 0` loop then subtracts `min(payment.balance.amount.0, to_subtract)` from every payment until all are zeroed. The subsequent dust filter drops them all, and the function returns without ever inserting a plan — every payment underneath the branch is silently discarded while the coins remain in the multisig-controlled output.

An unprivileged user reaches this path by triggering an out instruction whose plan requires an intermediate branch output (scheduled via `Scheduler::schedule` / `add_outputs`), which is standard protocol operation.

### Impact Explanation
All child payments of any fee-reduced branch output are reduced to zero and dropped: the wrapped `to_amortize` ensures the amortization loop never terminates until `payments` are fully drained. Affected users' withdrawals are silently lost — the multisig retains the funds but no plan will ever disburse them, i.e., funds effectively burned/locked. This mirrors the report's "funds being drained by the miscalculation" in the edge-case branch.

### Likelihood Explanation
Any branch output created for less than its planned amount — i.e., whenever a nonzero fee is charged, the normal case — hits this path. Reachability requires only that the scheduler produce a `PostFeeBranch` with `actual < expected`, which occurs on ordinary fee-bearing transactions initiated from public user instructions.

### Recommendation
Change `let mut to_amortize = actual - expected;` to `let mut to_amortize = expected - actual;`, matching the documented intent ("amortize the fee amongst all payments underneath this branch"). Add a regression test where a branch output is created with `actual < expected` and verify child payments are reduced by exactly `expected - actual` rather than dropped.

### Proof of Concept
- `PostFeeBranch` sets `expected` to the pre-fee amount and `actual` to the post-fee amount (`actual <= expected`): `processor/src/networks/mod.rs` lines 506–515.
- `created_output` receives these and computes `let mut to_amortize = actual - expected;` then loops subtracting `min(payment.amount, to_subtract)` until `to_amortize == 0`: `processor/src/multisigs/scheduler/utxo.rs` lines 484–504.
- With `expected = 10_000`, `actual = 9_000` (1,000 sat fee): `to_amortize` wraps to `u64::MAX - 999`; the loop zeroes every payment; the dust filter at lines 508–511 empties `payments`; line 520 is never reached, so no plan is registered for the 9,000 sats — funds locked.

Note: I could not fully confirm the caller's argument ordering at the `created_output` callsite in `processor/src/multisigs/mod.rs` (the grep returned only a match count, not lines). The finding assumes `expected`/`actual` are forwarded directly from `PostFeeBranch`, which is the only producer of these values.
