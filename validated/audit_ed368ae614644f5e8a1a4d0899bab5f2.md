## Title
Missing chain-continuity check in `verify_pharos_block` allows acceptance of a validly-signed fork block unrelated to the trusted chain - (File: modules/consensus/pharos/verifier/src/lib.rs)

### Summary
`verify_pharos_block` never checks that `update.header.parent_hash` links back to `trusted_state.finalized_hash` (directly or transitively). It only checks that the new block number is greater than the currently finalized number, that the header hashes to the value referenced in the block proof, that the proven epoch is consistent, and that a BLS super-majority of the *currently trusted* validator set signed that header. Any header satisfying those four checks is accepted and its hash/state root become the new `finalized_hash`/`finalized_block_number`, with no verification that the header actually descends from the previously trusted block.

### Finding Description
The verification flow in `verify_pharos_block` is:
1. `update_block_number > current_block_number` [1](#0-0) 
2. `computed_hash == update.block_proof.block_proof_hash` — this only proves the header is self-consistent with the accompanying proof, not that it extends the trusted chain [2](#0-1) 
3. Epoch proof against `update.header.state_root`, and rotation/no-rotation branching based on `observed_epoch` vs `trusted_epoch` [3](#0-2) 
4. BLS signature verification of `update.block_proof` against the currently trusted validator set [4](#0-3) 

At no point is `update.header.parent_hash` compared to `trusted_state.finalized_hash`. On success, the function unconditionally overwrites the trusted state with the new header's hash/number: `Ok(VerifierState { finalized_block_number: update_block_number, finalized_hash: computed_hash, ..trusted_state })` in the same-epoch branch, and similarly in the epoch-rotation branch [5](#0-4) [6](#0-5) .

Because the only chain-position check is a strict numeric inequality on block number (`update_block_number <= current_block_number`), two competing headers with the same or a higher block number but different `parent_hash` values — as long as each carries a validly-signed `block_proof` from a supermajority of the trusted validator set at the correct epoch — will both pass `verify_pharos_block` independently. There is no assertion that `computed_hash`'s header actually chains from `trusted_state.finalized_hash`.

This is consumed directly by `PharosClient::verify_consensus`, which decodes the untrusted `proof: Vec<u8>` into a `VerifierStateUpdate`, calls `verify_pharos_block`, and persists the returned state (including `finalized_hash` and the `state_root`-derived `StateCommitment`) as the new trusted `ConsensusState` for the `Evm(chain_id)` state machine [7](#0-6) . Any state root accepted this way becomes the trusted root used for subsequent request/response/state proofs on that state machine.

### Impact Explanation
If a header at a higher (or non-monotonically-descending) block number carrying a validly aggregated BLS signature over the trusted validator set can be produced for a block that does not descend from the last finalized header, the light client's `finalized_hash`/`finalized_block_number`/`state_root` get corrupted with an unrelated fork's state. Since the ISMP consensus client stores this as ground truth for the `Evm(chain_id)` state machine, any state/storage proofs verified against that root would be treated as authentic, enabling downstream message, order, or governance settlement derived from a chain state that was never actually finalized by the canonical Pharos chain.

### Likelihood Explanation
This finding is a structural gap in the verifier's invariants rather than a demonstration that an attacker can unilaterally forge a supermajority BLS signature without any validator collusion or equivocation. Under correct BFT operation, a supermajority of honest validators is not expected to sign two conflicting non-descendant headers at the same or overlapping heights, and the review scope explicitly excludes attacks that require malicious/compromised validators or infrastructure. Absent an actual competing supermajority-signed fork, an unprivileged attacker with no signing power cannot forge the `aggregate_signature`/`participant_keys` needed to pass `verify_bls_signature`, so this cannot be exploited purely from unauthenticated proof/message inputs alone — it requires a validator-level equivocation event that the verifier's design should be defending against but currently does not check for via `parent_hash`/continuity comparison.

### Recommendation
Add an explicit chain-continuity assertion in `verify_pharos_block`: require `update.header.parent_hash == trusted_state.finalized_hash` for direct single-block advancement, or otherwise validate a chain of headers back to the trusted hash before accepting `update_block_number`/`computed_hash` as the new finalized state. This closes the gap regardless of how a conflicting signed proof might be produced (equivocation, reorg replay, or relayer misbehavior).

### Proof of Concept
Construct two `VerifierStateUpdate` values, `update_a` and `update_b`, at the same `block_number` and `epoch`, each with a different `parent_hash` (so `computed_hash` differs), each carrying a `block_proof` with a valid BLS aggregate signature from ≥2/3 stake of `trusted_state.current_validator_set` over its own `block_proof_hash`. Only `update_a.header.parent_hash == trusted_state.finalized_hash`. Calling `verify_pharos_block(trusted_state.clone(), update_b)` succeeds and returns a `VerifierState` with `finalized_hash = hash(update_b.header)`, identical to calling it with `update_a`, because no code path compares either header's `parent_hash` to `trusted_state.finalized_hash` — confirmed by inspection of lines 45-129 of [8](#0-7) , which contains no reference to `update.header.parent_hash` anywhere in the function body.

pub fn verify_pharos_block<C: Config, H: Keccak256 + Send + Sync>(
	trusted_state: VerifierState,
	update: VerifierStateUpdate,
) -> Result<VerifierState, Error> {
	let update_block_number = update.block_number();
	let current_block_number = trusted_state.finalized_block_number;

	if update_block_number <= current_block_number {
		return Err(Error::StaleUpdate {
			current: current_block_number,
			update: update_block_number,
		});
	}

	let computed_hash = Header::from(&update.header).hash::<H>();

	if computed_hash != update.block_proof.block_proof_hash {
		return Err(Error::BlockProofHashMismatch {
			computed: computed_hash,
			provided: update.block_proof.block_proof_hash,
		});
	}

	let observed_epoch = state_proof::verify_current_epoch_proof(
		update.header.state_root,
		&update.current_epoch_proof,
	)?;

	let trusted_epoch = trusted_state.current_epoch;

	match observed_epoch.cmp(&trusted_epoch) {
		Ordering::Less =>
			Err(Error::EpochRegressed { trusted: trusted_epoch, observed: observed_epoch }),
		Ordering::Equal => {
			if update.validator_set_proof.is_some() {
				return Err(Error::UnexpectedValidatorSetProof {
					block_number: update_block_number,
				});
			}

			verify_block_signature(
				&trusted_state.current_validator_set,
				&update.block_proof,
				computed_hash,
			)?;

			Ok(VerifierState {
				finalized_block_number: update_block_number,
				finalized_hash: computed_hash,
				..trusted_state
			})
		},
		Ordering::Greater => {
			if observed_epoch != trusted_epoch + 1 {
				return Err(Error::EpochSkipped {
					trusted: trusted_epoch,
					observed: observed_epoch,
				});
			}

			let validator_set_proof = update
				.validator_set_proof
				.ok_or(Error::MissingValidatorSetProof { block_number: update_block_number })?;

			let new_validator_set = state_proof::verify_validator_set_proof::<H>(
				update.header.state_root,
				&validator_set_proof,
				observed_epoch,
			)?;

			verify_block_signature(
				&trusted_state.current_validator_set,
				&update.block_proof,
				computed_hash,
			)?;

			Ok(VerifierState {
				current_validator_set: new_validator_set,
				finalized_block_number: update_block_number,
				finalized_hash: computed_hash,
				current_epoch: observed_epoch,
			})
		},
	}
}

	fn verify_consensus(
		&self,
		_host: &dyn IsmpHost,

		proof: Vec<u8>,

		let update = VerifierStateUpdate::decode(&mut &proof[..])

		let consensus_state =
			ConsensusState::decode(&mut &trusted_consensus_state[..]).map_err(|e| {

				)

		let new_state = verify_pharos_block::<C, H>(trusted_state, update.clone())
			.map_err(|e| Error::AnyHow(anyhow::Error::from(e).into()))?;

		let state_commitment = StateCommitmentHeight {
			commitment: StateCommitment {
				timestamp: update.header.timestamp,
				overlay_root: None,
				state_root: update.header.state_root,
			},
			height: new_state.finalized_block_number,
		};

		let new_consensus_state = ConsensusState {
			current_validators: new_state.current_validator_set,
			finalized_height: new_state.finalized_block_number,

		);
