### Title
secp256k1 precompile accepts malleable signatures (missing low-S / canonical-signature check) - (File: precompiles/src/secp256k1.rs)

### Summary
The `secp256k1_program` precompile's `verify()` function recovers a public key from an arbitrary `(r, s, recovery_id)` triple and only checks that the recovered address matches the expected `eth_address`. Unlike the `secp256r1` precompile, which explicitly enforces canonical (low-S) signatures, and the `ed25519` precompile, which uses `verify_strict` to reject malleable signatures, the secp256k1 path performs no `s`-range or canonical-form check. As a result, for any valid `(message, r, s, v)` triple, the trivially-derived malleable variant `(message, r, -s mod n, v ^ 1)` is also accepted as a *different* valid signature for the exact same message and signer.

### Finding Description
`precompiles/src/secp256k1.rs::verify` parses the signature via `libsecp256k1::Signature::parse_standard_slice`, parses the recovery id via `libsecp256k1::RecoveryId::parse`, and calls `libsecp256k1::recover`, checking only that the recovered Ethereum address matches: [1](#0-0) 

No check is performed to ensure `s` is in the lower half of the curve order (canonical form), unlike the `secp256r1` precompile which explicitly bounds `s` to `[1, half_order]`: [2](#0-1) 

and unlike the `ed25519` precompile, which calls `verify_strict` specifically to reject malleable signature encodings: [3](#0-2) 

The malleability of secp256k1 signatures accepted by this precompile is explicitly exercised (and asserted to succeed) by the codebase's own test: [4](#0-3) 

The same underlying `sol_secp256k1_recover` syscall used by on-chain programs exhibits identical behavior and is likewise documented as malleable in its test suite: [5](#0-4) [6](#0-5) 

This is directly analogous to the reported mai-protocol-v2 issue: signature verification accepts more than one valid encoding for the same logical signed message/signer pair because `s` (and the paired recovery id) is not constrained to a canonical value.

### Impact Explanation
Any unprivileged user can submit a `secp256k1_program` instruction (or invoke `sol_secp256k1_recover` from a BPF program) containing a flipped-`s`/flipped-recovery-id variant of a previously observed valid signature and have it accepted as valid by the runtime precompile / syscall. Downstream on-chain programs (e.g., bridges, oracles, or any protocol using secp256k1-signed messages as a nonce/replay-protection mechanism, mirroring the exact pattern flagged in the external report) that assume a 1:1 mapping between "message" and "signature bytes" for replay protection can have that assumption defeated: an attacker can derive a second, distinct-but-valid signature for an already-used message and resubmit it, bypassing signature-based duplicate/replay checks implemented by the calling program. This falls under "forged signature acceptance" since the precompile treats a derived, non-canonical signature as an independently valid proof of the same signing event.

### Likelihood Explanation
High reachability: this code path is exercised by any transaction that includes a `secp256k1_program` instruction or by any BPF program that calls the `sol_secp256k1_recover` syscall — both fully accessible to unprivileged users with no special permissions. The malleable-signature derivation (`s -> -s mod n`, `v -> v ^ 1`) is a well-known, trivial, constant-time computation requiring no private key knowledge, only knowledge of an existing valid signature.

### Recommendation
Add a canonical-signature check to `precompiles/src/secp256k1.rs::verify` (and to the `sol_secp256k1_recover` syscall implementation) mirroring the low-S enforcement already present in `precompiles/src/secp256r1.rs`: reject signatures where `s > SECP256K1_ORDER / 2` (or normalize `s` to low-form before comparison) so that only one canonical signature is considered valid per `(message, signer)` pair.

### Proof of Concept
The existing repository test demonstrates the acceptance of a malleable signature as if it were valid, which is the crux of the issue (the test currently asserts `.unwrap()` succeeds for both the original and the flipped-`s` signature): [7](#0-6)
