## Analog Found

### Title
Trusting an unsafe repository directory writes a permanent, content-blind exception to Git's ownership check - (File: `app/src/lib/git/config.ts`)

### Summary
The bug report's core flaw is that a one-time "signal" action permanently satisfies a security precondition (a waiting-period gate), after which the delegator can act at any future moment without the gate being re-validated against present conditions. GitHub Desktop has a structurally identical pattern in its handling of Git's "dubious ownership" protection: clicking "Trust Repository" once permanently whitelists a directory path in the global `safe.directory` Git config, and that exception is never revisited or scoped to the content that existed at approval time.

### Finding Description
When Desktop detects a repository owned by a different user, `getRepositoryType` in [1](#0-0)  parses Git's `fatal: detected dubious ownership` message and returns `{ kind: 'unsafe', path: unsafeMatch[1] }`. The UI (`add-existing-repository.tsx`, `missing-repository.tsx`) then offers a "Trust Repository" action, whose handler calls `addSafeDirectory(repositoryUnsafePath)`: [2](#0-1) [3](#0-2) 

`addSafeDirectory` writes the path string directly into the **global** `~/.gitconfig` `safe.directory` list: [4](#0-3) 

This is a pure string-match exception — Git's `safe.directory` mechanism (and Desktop's wrapper around it) has no concept of "trust this content" vs. "trust this path forever, regardless of what occupies it later." Once the user clicks "Trust," the ownership check for that exact path is disabled permanently and globally, for every future Git invocation on the machine (not just GitHub Desktop), exactly as the report's delegator satisfies the undelegate waiting-period once and then retains the ability to act at any point in the future without the check being re-evaluated against current risk.

### Impact Explanation
The `safe.directory` ownership check exists specifically because a directory whose ownership can change (shared drives, multi-user machines, synced/mounted folders, extracted archives, restored VM snapshots) may later be repopulated by a different, potentially malicious, actor with attacker-controlled `.git` hooks, `core.fsmonitor`, or other auto-executed configuration. Because the trust decision is keyed only by path and persists indefinitely, once a user has trusted a path (e.g., a shared sync folder, USB mount point, or CI workspace path reused across sessions), any future content placed at that identical path — including a malicious repository swapped in later — inherits the trust exception with no re-prompt and no re-validation, enabling Git (and Desktop's automatic operations on the repo, like loading remotes) to run against attacker-supplied hooks/config without the ownership guard ever firing again.

### Likelihood Explanation
This requires a plausible but non-trivial precondition: the user must have previously trusted a path that is later reoccupied by attacker-controlled content at the exact same path (common with shared/synced storage, removable media, or reused temp/build directories — which is precisely the multi-user threat model `safe.directory` was built to address). No local admin rights, malware, or leaked credentials are needed; the attacker only needs to control content placed at a path the victim already exempted. Medium likelihood, consistent with the "Medium" severity of the original report's analogous timing bypass.

### Recommendation
- **Short term**: When re-encountering a previously-trusted path, re-validate that the repository's identity (e.g., remote URL, initial commit hash, or a recorded fingerprint) matches what was present at trust time before silently proceeding; if it doesn't, prompt again rather than relying solely on the persisted `safe.directory` path match.
- **Long term**: Avoid caching security-relevant approvals as unconditionally permanent, global state. Scope trust decisions as narrowly as possible (e.g., session-scoped or content-fingerprint-scoped) and review all "trust once, exempt forever" flows in Desktop for similar TOCTOU-style caching issues, mirroring the original report's guidance to review timestamp/state-based gates for what happens when the underlying condition changes after the gate was passed.

### Proof of Concept
1. User A adds an existing repository located on a shared/synced path (e.g., `\\shared\project` or a mounted drive) that is currently owned by a different OS user; Desktop shows "is potentially unsafe" and the "Trust Repository" button.
2. User A clicks "Trust Repository" → `addSafeDirectory(path)` adds `path` to the global `safe.directory` list permanently.
3. Later, the directory at that same path is deleted and replaced (by another user of the shared machine, a sync conflict, or a re-mount) with an attacker-controlled Git repository containing malicious hooks/config.
4. GitHub Desktop (and plain `git`) no longer warns about dubious ownership for that path — the exception from step 2 still matches — so Desktop proceeds to run Git operations (e.g., `loadRemotes`, LFS checks) against the attacker-controlled repository without any re-prompt, exactly as the original delegator's early "signal" permanently defeats a check meant to be re-validated at the time of the sensitive action.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```
