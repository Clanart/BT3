### Title
KIP-71 `GasTarget` governance parameter accepts `0`, causing a division-by-zero panic in `KIP71Config.NextMagmaBlockBaseFee()` - (File: `params/kip71_config.go`)

### Summary
The original report describes `OptionMath._getPositivePlaceValues()` reverting due to an unguarded division by a derived divisor that can become zero for certain inputs. The Kaia codebase has the exact same bug class in the KIP-71 base-fee calculation: the `GasTarget` governance parameter is used as a raw divisor in `KIP71Config.NextMagmaBlockBaseFee()` but, unlike the sibling parameter `BaseFeeDenominator`, it has no non-zero validation, so it can be voted to `0` and subsequently crash every node's base-fee computation.

### Finding Description
`NextMagmaBlockBaseFee()` uses `gasTarget` (taken directly from governance config) as a divisor in both the "gas used above target" and "gas used below target" branches: [1](#0-0) [2](#0-1) 

The function explicitly guards against `BaseFeeDenominator == 0` by falling back to a default value: [3](#0-2) 

but performs no equivalent guard for `gasTarget`. If `gasTarget == 0` and `parentGasUsed != 0` (the overwhelmingly common case for any live network), the code takes the `parentGasUsed > gasTarget` branch and calls `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor, which is a `big.Int` division-by-zero panic in Go — analogous to the Solidity revert on `ruler == 0` in the original report, except in Go this crashes the entire process rather than reverting a single call.

The root cause is the governance parameter registration for `Kip71GasTarget`, which uses a no-op format checker with no minimum-value check, unlike its sibling `Kip71BaseFeeDenominator`, which explicitly rejects `0`: [4](#0-3) 

This asymmetry (denominator protected both at validation time and defensively in the math function, target protected at neither) mirrors the "some divisor paths handled, one not" root cause of the referenced bug.

### Impact Explanation
`NextMagmaBlockBaseFee()` is invoked on the hot path of block header verification (`VerifyMagmaHeader`) for every block after the Magma fork, as well as by RPC-facing gas price oracles reachable by any public-RPC caller: [5](#0-4) [6](#0-5) 

Once `GasTarget` is set to `0` via governance, every subsequent block whose gas usage differs from `0` triggers the panic on all nodes simultaneously during header verification, and any RPC caller invoking `eth_feeHistory`/`eth_gasPrice`-style calls (`Oracle.SuggestPrice`/`processBlock`) triggers the same panic. Because block header verification is part of consensus, this is a chain-halting bug reachable by any block containing a normal transaction (i.e., any unprivileged transaction sender) once the misconfiguration is live — a network-wide denial of service, not a resource-only or single-node issue.

### Likelihood Explanation
Triggering requires `GasTarget` to be voted to `0` through the standard governance-vote mechanism, which is gated to network governance participants; however, the vote/verification layer performs no bounds check to prevent this value, unlike the closely related `BaseFeeDenominator` parameter which is explicitly guarded. This is a legitimate, reachable governance misconfiguration (accidental or malicious single vote) rather than a hypothetical edge case, and the resulting DoS activates automatically the very next block that has non-zero gas usage — effectively guaranteed once the parameter is enacted.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check) at `kaiax/gov/param.go:324-333`, and additionally add a defensive zero-check/fallback for `gasTarget` inside `NextMagmaBlockBaseFee()` at `params/kip71_config.go`, consistent with the existing `BaseFeeDenominator == 0` fallback, so that a division by zero can never occur regardless of how the parameter was set.

### Proof of Concept
1. Governance votes `kip71.gastarget = 0` (accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, see `kaiax/gov/param.go:324-333`).
2. Once enacted, on the next Magma-enabled block where `parentHeaderGasUsed != 0`, `NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)` is called by `VerifyMagmaHeader` during header verification.
3. Inside, `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)` is nonzero and not equal to `gasTarget (0)`, so execution enters the `parentGasUsed > gasTarget` branch at `params/kip71_config.go:92-109`.
4. `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` divides by a zero-valued `big.Int`, causing a runtime panic ("division by zero") in every node computing/verifying this header, crashing block processing network-wide. The same panic is separately reachable by any public RPC caller through `Oracle.processBlock`/`SuggestPrice` calling into the same `NextMagmaBlockBaseFee` function (`node/cn/gasprice/feehistory.go:111-115`, `node/cn/gasprice/gasprice.go`).

	}
	return nil
}
