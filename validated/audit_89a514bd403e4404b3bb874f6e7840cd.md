### Title
Auction bid signature fields (`SearcherSig`/`AuctioneerSig`) are indexed at fixed offsets without length validation, allowing an out-of-bounds panic / DoS from an unprivileged auction bidder - (File: kaiax/auction/bid.go)

### Summary
`BidData.SearcherSig` and `BidData.AuctioneerSig` are decoded as arbitrary-length `[]byte` via RLP with no minimum-length check [1](#0-0) . Both fields flow into `getSigner`, which immediately indexes `copiedSig[crypto.RecoveryIDOffset]` and slices `copiedSig[0:32]` / `copiedSig[32:64]` before any length check [2](#0-1) . This mirrors the rAthena `CA_SSO_LOGIN_REQ` bug class: an attacker-supplied, insufficiently validated length field is used to drive fixed-offset memory access.

### Finding Description
`Bid.ValidateSearcherSig` and `Bid.ValidateAuctioneerSig` call `getSigner(b.SearcherSig, digest)` / `getSigner(b.AuctioneerSig, digest)` directly on bytes that originate from an externally submitted `Bid` (decoded via `DecodeRLP`, which simply RLP-decodes `BidData` with no field-length constraints) [3](#0-2) . Inside `getSigner`, the code accesses `copiedSig[crypto.RecoveryIDOffset]` and `copiedSig[0:32]`/`copiedSig[32:64]` with no prior `len(sig) >= 65` (or `> crypto.RecoveryIDOffset`) guard [2](#0-1) . Any `Bid` with a `SearcherSig` or `AuctioneerSig` shorter than 65 bytes (including a zero-length or empty slice) causes a Go runtime index-out-of-range panic when this code path executes.

### Impact Explanation
A crash in bid signature validation triggered by a single malformed, unprivileged auction bid submission is a denial-of-service against the node processing/validating auction bids (bid pool admission / auctioneer/searcher signature verification), analogous in bug-class terms to the crash primitive described in the rAthena CVE (oversized/undersized length field driving unchecked fixed-offset access on attacker data). Depending on whether panics in this call path are recovered by the surrounding goroutine/handler, this can produce repeated node crashes reachable by any bidder submitting bids through the public bid-submission surface, without requiring any privileged role.

### Likelihood Explanation
Likelihood is high for triggering the panic: any external bid submitter (searcher) fully controls `SearcherSig`/`AuctioneerSig` contents and lengths, and no length validation exists prior to the fixed-offset access in `getSigner`. The only uncertainty is whether an outer panic-recovery wrapper exists around bid-pool/API processing that would downgrade this from a crash to a mere rejected request — this could not be confirmed from the indexed code, since the goroutine/HTTP handler wrapping `ValidateSearcherSig`/`ValidateAuctioneerSig` call sites (e.g., in `kaiax/auction/impl/bid_pool.go` or `kaiax/auction/impl/api.go`) was not fully traced for panic recovery.

### Recommendation
In `getSigner` (or upstream in `ValidateSearcherSig`/`ValidateAuctioneerSig`/`DecodeRLP`), validate `len(sig) == crypto.SignatureLength` (65 bytes) before any indexing or slicing, returning `ErrInvalidSignature` otherwise, mirroring the length checks already used elsewhere (e.g., `crypto.SignatureLength`-based checks in `blockchain/types/transaction_signing.go`) [4](#0-3) .

### Proof of Concept
Construct a `Bid` (or `BidData`) with `SearcherSig` set to an empty byte slice (or any slice shorter than 65 bytes) and a well-formed `Sender`/other fields, submit it through the auction bid ingestion path so that `ValidateSearcherSig` is invoked, which calls `getSigner(b.SearcherSig, digest)` and panics on `copiedSig[crypto.RecoveryIDOffset]` since `len(copiedSig) < crypto.RecoveryIDOffset+1`.

Note: I was unable to fully verify (within available context) whether the bid-processing goroutine(s) in `kaiax/auction/impl/bid_pool.go` / `kaiax/auction/impl/api.go` wrap this validation call in a `recover()`, which would affect whether the impact is a per-request error or a full node crash — this should be verified directly in those files before finalizing severity.
