Based on my investigation, I found a concrete Cosmos EVM analog to the ERC777-hook fee-bypass bug class: the `BalanceHandler` event-replay mechanism used by all Cosmos SDK-module precompiles (staking, distribution, bank, etc.) trusts *every* `bank` module event emitted during a precompile call to update the EVM `StateDB` balance — a pattern structurally identical to the Illuminate bug, where a downstream call's side-effects (there: ERC777 hooks; here: recursive/nested precompile calls triggered from an ERC20 token's `_beforeTokenTransfer`/`_afterTokenTransfer` hook) are trusted without re-validating that they correspond 1:1 to the intended state change.

### Title
Recursive precompile calls from ERC20 transfer hooks cause `BalanceHandler` to double-apply bank events, corrupting StateDB balances - ([File: precompiles/common/balance_handler.go])

### Summary
`BalanceHandler.AfterBalanceChange` (analogous to Lender's `swivelLendPremium` trusting any residual balance delta) blindly replays *all* `bank.EventTypeCoinSpent` / `EventTypeCoinReceived` events emitted since `BeforeBalanceChange` was called into the EVM `StateDB` via `AddBalance`/`SubBalance` [1](#0-0) . This mirrors the report's root cause: fees/deltas being computed from a value produced by attacker-influenced side effects (hooks) rather than from validated accounting.

### Finding Description
Cosmos EVM precompiles (staking, distribution, bank, etc.) wrap Cosmos SDK message execution and rely on `BalanceHandler` to synchronize resulting bank balance changes into the EVM `StateDB`, since precompile calls happen "outside" normal EVM value-transfer opcodes. `BeforeBalanceChange` records `len(ctx.EventManager().Events())`, then after the precompile's Cosmos SDK call executes, `AfterBalanceChange` iterates every event appended after that point and applies its amount to `StateDB` [2](#0-1) .

The repository's own test suite documents that this exact mechanism has a known "native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated" [3](#0-2) . The test harness reproduces it using an ERC20 token (`ERC20RecursiveNonRevertingPrecompileCall.sol` / `ERC20RecursiveRevertingPrecompileCall.sol`) whose `_beforeTokenTransfer` hook — the same hook mechanism used by ERC777 in the referenced report — recursively calls the distribution precompile's `claimRewards()` in a loop with `try/catch`, before the outer ICS20/ERC20 transfer completes [4](#0-3) .

The test's own expectations show the corruption: in the "with reverts" scenario the contract's native balance ends at `0` (rewards effectively lost/unclaimed) [5](#0-4) , whereas in the "without reverts" scenario — where the same recursive claim loop runs during the token transfer hook but does not revert — the contract ends up with a native balance of `50` despite `afterRewards.Rewards` being `nil` (i.e., no rewards left to claim on-chain) [6](#0-5) . This is a direct duplication of spendable value: the EVM-visible balance (`50`) diverges from and exceeds what the Cosmos SDK distribution/staking accounting actually paid out, exactly the "amount not tied to authorized spend/fee logic" flaw described in the ERC777 report, just realized through nested precompile calls instead of an ERC777 hook triggering an unrelated underlying-token transfer.

Root cause: `BalanceHandler` has no mechanism to detect or discard events generated by reverted/rolled-back nested calls, or by recursive invocations of the same precompile within a single outer call — it naively slices `events[prevEventsLen:]` and applies every entry, so repeated/duplicate `EventTypeCoinReceived` events from recursive `claimRewards()` invocations (or partially-reverted sub-calls whose Cosmos-level state changes were rolled back via the SDK's `CacheContext`/branch mechanism but whose events were not correctly discarded) get replayed into the StateDB as additional balance increases that never actually landed in the bank keeper's committed state.

### Impact Explanation
This breaks the "Asset-representation path" invariant that x/vm StateDB-visible native balances must equal the bank keeper's actual committed balances. Any user-deployed ERC20 token with a transfer hook (a pattern common to fee-on-transfer/rebasing/reward tokens, and exactly how ERC777-style tokens are structured) that recursively invokes a value-distributing precompile (`distribution.claimRewards`, `staking` rewards, or similar) during token transfer can cause the caller's EVM-visible native balance to be inflated beyond what is actually escrowed/owned in the bank module — a Critical "unauthorized minting/duplication of spendable user value" per the allowed impact gate, since the discrepancy is a StateDB balance that can subsequently be spent or bridged (e.g. via ICS20/x/erc20 conversion) without a matching backing asset.

### Likelihood Explanation
The trigger is fully permissionless: any unprivileged user can deploy an ERC20 contract with a `_beforeTokenTransfer`/`_afterTokenTransfer` hook that calls a value-distribution precompile recursively, then route ordinary ERC20 transfers or ICS20 transfers through it, exactly as the repository's own regression test does [7](#0-6) . No validator, relayer, or governance action is required.

### Recommendation
`BalanceHandler.AfterBalanceChange` should not naively replay every bank event in the recorded window; it should instead diff actual committed balances (before/after, per address touched) at the top level of the precompile call, discard events originating from nested/recursive precompile invocations that were rolled back, and/or track a call-depth/reentrancy guard so recursive precompile calls cannot each contribute independent, additive balance-sync events for the same underlying state change. This mirrors the report's fix recommendation of "charge/settle based on the actual total after all downstream effects are executed, not fragmented per intermediate step."

### Proof of Concept
The repository already contains a working PoC in its test suite: `ICS20RecursivePrecompileCallsTestSuite.TestHandleMsgTransfer`, "test recursive precompile call without reverts" case, deploys `ERC20RecursiveNonRevertingPrecompileCall`, sets up a delegation/reward position for the contract, and performs an ICS20 transfer of the ERC20-backed token. The transfer's underlying token movement invokes `_beforeTokenTransfer`, which loops 5 times calling `claimRewards()` via `try/catch` [8](#0-7) . Post-transfer, the test asserts the contract's native bond-denom balance is `50` even though `DelegationRewards` query shows no remaining rewards (`afterRewards.Rewards` is `nil`) [6](#0-5) , confirming the StateDB/bank-keeper divergence.

Note: I was unable to fully trace the exact internal Cosmos SDK branch/cache-context rollback behavior that leaves "persistent" events after a reverted nested call (the comment in the test file references this but the underlying rollback mechanism is in vm/statedb or SDK-level `CacheContext` code I could not fully inspect in the available index). A Devin session with full repository access would be needed to pinpoint the exact code path where reverted nested-call events survive into `ctx.EventManager().Events()` and confirm whether this is already partially mitigated elsewhere (e.g., in `x/vm/keeper` nested-call/journal handling) before finalizing a fix.

```go
// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
```
