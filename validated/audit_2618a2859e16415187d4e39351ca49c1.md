### Title
Bitcoin `Schnorr::sign_share` never negates the secret share for odd-Y Taproot group keys, producing BIP340-invalid signatures - (File: `networks/bitcoin/src/crypto.rs`)

### Summary
The bug class of the external report is "an alternate/secondary code path omits a required internal step that every other path performs" (a deposit variant skipping `updateState()`). The analog in Serai: BIP-340 Schnorr signing requires two normalizations — negating the nonce when `R` has odd Y (handled in `Hram::hram` and `Schnorr::verify` via `needs_negation`), **and** negating the secret key/share when the group public key has odd Y. The second step is skipped entirely: `Schnorr::sign_share` delegates straight to `FrostSchnorr::sign_share`, which calls `SchnorrSignature::sign(params.secret_share(), nonce, c)` with the un-negated share. The negation compensation in `verify` only fixes the `R` parity of `s`, never the key parity.

### Finding Description
In `networks/bitcoin/src/crypto.rs`:

- `needs_negation(key)` returns whether a point has odd Y (`crypto.rs:26-28`).
- `Hram::hram` negates the challenge when `R` is odd so signers can sign `r - cx` and flip `s` at the end (`crypto.rs:70-72`).
- `Schnorr::verify` conditionally negates the summed `s` based on `needs_negation(&sig.R)` (`crypto.rs:145-149`).
- `Schnorr::sign_share` (`crypto.rs:128-136`) forwards `params.secret_share()` unchanged; `FrostSchnorr::sign_share` computes `s = nonce + c * secret_share` (`crypto/frost/src/algorithm.rs:201-211`).

BIP-340 verification is over x-only keys: the verifier computes `sG = R' + e·P'` where `P'` is the even-Y representative of the x-only pubkey and `R'` is the even-Y representative of `R`. When `P` (the aggregate/tweaked Taproot key) has odd Y, `P' = -P`, so the valid signature requires `s = r' + e·(-x)`, i.e. every participant's contribution of `x` must be negated. Serai never negates `params.secret_share()` (nor the `ThresholdView` scalar/offset) based on `needs_negation(group_key)`, so whenever the effective group key is odd-Y the aggregate `sG = R + e·P ≠ R' + e·P'`.

### Impact Explanation
`ThresholdKeys` used for Bitcoin spends are passed through `keys.clone().offset(self.offsets[i])` in `SignableTransaction::multisig` (`networks/bitcoin/src/wallet/send.rs:273-285`), and `p2tr_script_buf(offset.group_key())` must match the prevout `script_pubkey` — i.e. the output key is the x-only Taproot-tweaked key, which has a ~50% chance of odd Y. For those keys/inputs, `TransactionSignMachine::sign` → `sign_share` produces shares that verify individually (blame check passes, since `verify_share` uses the same un-negated secret-share relationship), and `complete` then returns a `Transaction` whose witnesses contain signatures that are invalid under Bitcoin consensus/BIP-340. The signed transaction cannot be broadcast — funds received at an odd-Y tweaked key become unspendable through this signing path (liveness/availability loss on wallet funds, not just a cosmetic verification difference). An unprivileged party reaches this purely by sending Bitcoin to a Serai deposit output whose tweaked key happens to be odd-Y — no cooperation from any validator is required for the failure to occur.

### Likelihood Explanation
~50% of tweaked aggregate keys have odd Y, so roughly half of deposit/spend keys are affected whenever this path is exercised. The failure is deterministic given the key; no race or adversarial computation is needed. Severity is bounded to availability of funds (protocol can re-key in theory, but the produced signatures are simply invalid), so Medium-High rather than Critical.

### Recommendation
In the Bitcoin `Schnorr` algorithm, normalize the key parity before signing: when `needs_negation(view.group_key())` is set, use `-secret_share` (and `-offset`) in `sign_share`, or equivalently negate `s` once more at `verify`/aggregation time. Concretely, apply a `conditional_select(&share, &-share, needs_negation(&group_key))` inside `sign_share` (and the matching scalar used in `verify_share`/`complete`), mirroring the existing `R`-parity handling in `Hram::hram` and `Schnorr::verify`.

### Proof of Concept
1. Build a `ThresholdKeys<Secp256k1>` set, choose offsets such that `offset.group_key()` has odd Y (~half of random keys).
2. Construct a `SignableTransaction` spending a prevout whose `script_pubkey` equals `p2tr_script_buf(group_key)`; call `multisig` → `preprocess` → `sign` → `complete` with honest shares.
3. The returned transaction's witness signature fails `bitcoin::secp256k1`/`schnorr` verification against the x-only key (verify uses `x(A)` of the even-Y key, while `s` embeds `+c·x` instead of `-c·x`).
4. Internally, `Schnorr::verify` accepts it — showing the shares verify under the un-negated relation and no participant is blamed, yet the output is consensus-invalid.
