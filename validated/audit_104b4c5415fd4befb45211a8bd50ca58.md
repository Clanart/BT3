### Title
Zero-fee-remainder token entry permanently deadlocks `withdraw()` and locks all escrowed order funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The `withdraw()` function in `evm/tron/contracts/apps/IntentGatewayV2.sol` releases every escrowed token for an order in a single loop and reverts the whole transaction if any single token entry in that loop reads a zero escrow balance (`if (_orders[body.commitment][token] == 0) revert UnknownOrder();`). A per-token escrow amount can legitimately become `0` when the destination's protocol fee (`_destinationProtocolFees[destinationHash]`, falling back to `_params.protocolFeeBps`) is `10000` (100%) for that input token, since `reducedAmount = originalAmount - protocolFee` collapses to `0` in `placeOrder()`. Because that same zero-amount token entry is still carried through `body.tokens` at settlement time, `withdraw()` reverts on it — permanently blocking the release of *every other, non-zero* escrowed token for that same order commitment. This is the same broken invariant as the external report: a subtraction of two equal values yields `0`, and a mandatory downstream operation is not tolerant of that `0`, deadlocking the claim/settlement path.

### Finding Description
In `placeOrder()` (`evm/tron/contracts/apps/IntentGatewayV2.sol:300-330`, mirrored in `evm/src/apps/IntentGatewayV2.sol`), each input's escrowed amount is fee-reduced:

```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
...
reducedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: reducedAmount});
``` [1](#0-0) 

When `protocolFeeBps == 10_000` (100%, the max representable basis-points value, and not bounded away from 10000 anywhere in the reviewed code), `reducedAmount` is exactly `0`, and this value is written to escrow:

```solidity
_orders[commitment][token] += reducedInputs[i].amount; // adds 0
``` [2](#0-1) 

At settlement time, `onAccept` decodes the `WithdrawalRequest` and calls `withdraw()`, which iterates every token in `body.tokens` (mirroring `order.inputs`, including the zero-amount one) and treats a zero stored balance as fatal:

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        ...
        _orders[body.commitment][token] -= amount;
        ...
    }
``` [3](#0-2) 

Unlike this `withdraw()`, the shared `IntentsBase._withdraw()` used elsewhere explicitly guards against this exact case with `if (amount == 0) continue;` before checking escrow:

```solidity
uint256 amount = body.tokens[i].amount;
if (amount == 0) continue;

uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
``` [4](#0-3) 

The Tron variant's `withdraw()` has no such skip, so any legitimately zero-value token entry (produced by the 100%-fee edge case, or any future path that can drive a per-token escrow to `0`) causes `revert UnknownOrder()` on the entire settlement call. Since Solidity reverts unwind the whole transaction, `_filled[body.commitment]` is never persisted and none of the order's other tokens (including non-zero ones) are ever released — the escrow is deadlocked, exactly mirroring how `PayoutPool.claimPayout` used to revert on `newGenerationCRAmount == 0` and block the entire claim.

### Impact Explanation
Once an order commitment contains a zero-amount token entry, the *entire* cross-chain settlement message for that order becomes permanently unprocessable via `withdraw()`, since `onAccept` will keep reverting on the same escrow check every time the message is relayed. All escrowed inputs for that order (potentially significant value across multiple token types) become permanently locked in the `IntentGatewayV2` (Tron) contract, with no recovery path other than a contract upgrade/migration, since the withdrawal path used both for successful fills (`RedeemEscrow`) and for refunds/cancellations (`RefundEscrow`, `onGetResponse`) shares this same `withdraw()` function.

### Likelihood Explanation
Triggering requires only that the destination protocol fee configured for an order (via `UpdateParams`, `_destinationProtocolFees` or the default `_params.protocolFeeBps`) equals `10000` (100%) for at least one input token in the order at the time `placeOrder()` is called — no malicious relayer, prover, or admin collusion is needed beyond a normal (if extreme) protocol-fee configuration, and no code path was found bounding `protocolFeeBps` below `10000`. Any user placing an order under such a fee configuration, or any governance misconfiguration setting the fee to 100% (even temporarily, e.g., to fully redirect a token to protocol treasury), silently locks user funds the next time settlement runs.

### Recommendation
Add the same zero-amount skip that `IntentsBase._withdraw()` already uses to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`:
```solidity
uint256 amount = body.tokens[i].amount;
if (amount == 0) { unchecked { ++i; } continue; }
```
before the `_orders[body.commitment][token] == 0` check, so a legitimately zero-value token entry does not abort release of the rest of the order's escrow. Additionally, consider capping `protocolFeeBps` (and `_destinationProtocolFees`) strictly below `10000` at the point they are set (`UpdateParams` handling) to prevent a 100%-fee configuration from producing zero-value escrow entries in the first place.

### Proof of Concept
1. Governance (or default `_params.protocolFeeBps`) sets the protocol fee for a destination to `10000` (100%) for one of the order's input tokens.
2. A user calls `placeOrder()` on the Tron `IntentGatewayV2` with two inputs: Token A (fee = 100%) and Token B (fee = 0%). For Token A, `protocolFee == originalAmount`, so `reducedAmount = 0`; `_orders[commitment][TokenA] += 0` (stays 0), while `_orders[commitment][TokenB] += reducedAmountB` (non-zero).
3. The order is filled/cancelled cross-chain; the source-chain `IntentGatewayV2.onAccept` decodes a `WithdrawalRequest` whose `body.tokens` includes both Token A (amount 0) and Token B (amount > 0), and calls `withdraw(body, ...)`.
4. In the loop, when `token == TokenA`, `_orders[body.commitment][TokenA] == 0` triggers `revert UnknownOrder()`, aborting the transaction before Token B's non-zero escrow can be released.
5. Every subsequent attempt to settle the same commitment (from `onAccept` or `onGetResponse`) reverts identically — Token B's legitimately escrowed funds are permanently stuck.
