Confirmed: `NativeSeiTokensERC20.sol` is compiled into `NativeSeiTokensERC20.bin`/`.abi` [1](#0-0)  and deployed on-chain as the production ERC20 pointer contract for every native `usei`/tokenfactory denom whenever a pointer is created via the `pointer` precompile's `AddNative`/`addNativePointer` method, which any EVM caller can invoke [2](#0-1) . This contract extends OpenZeppelin's `ERC20` and only overrides `name`, `symbol`, `balanceOf`, `decimals`, `totalSupply`, and `_update` — it does **not** override `approve`, `allowance`, or `transferFrom` [3](#0-2) . This means it inherits the stock OpenZeppelin `approve` semantics, which overwrite the allowance unconditionally — exactly the pattern flagged in the M-7 report as vulnerable to front-running.

By contrast, the `CW20ERC20Pointer.sol` contract (used for CW20 token pointers) already implements the mitigated pattern: its `approve` function computes the delta between old and new allowance and issues `increase_allowance`/`decrease_allowance` calls instead of a blind overwrite [4](#0-3) .

### Title
Native-token ERC20 pointer contract inherits unmitigated OpenZeppelin `approve`, enabling front-run/allowance-overwrite exploitation - (File: contracts/src/NativeSeiTokensERC20.sol)

### Summary
`NativeSeiTokensERC20.sol`, the Solidity source compiled and deployed on-chain as the ERC20 pointer for every native/tokenfactory denom, extends OpenZeppelin `ERC20` without overriding `approve`, `allowance`, or `transferFrom`. It therefore uses the standard OpenZeppelin allowance-overwrite `approve` implementation, which is the exact bug class described in the M-7 report: a spender who has an outstanding allowance can front-run an owner's new `approve` transaction with a `transferFrom` call, then benefit from the newly set allowance as well, netting more tokens than the owner ever intended to authorize.

### Finding Description
Any EVM user can trigger deployment of a `NativeSeiTokensERC20` pointer contract for a given bank denom by calling `addNativePointer` on the `pointer` precompile [2](#0-1) . The deployed bytecode comes straight from `contracts/src/NativeSeiTokensERC20.sol`, which inherits `ERC20` from OpenZeppelin and only overrides token metadata and transfer accounting (`_update`, backed by the bank precompile) [5](#0-4) . Because `approve`/`transferFrom`/`allowance` are not overridden, the contract uses OpenZeppelin's default behavior of unconditionally overwriting `_allowances[owner][spender]` on every `approve` call, with no atomic increase/decrease primitive. This is the textbook allowance front-running pattern: Alice sets allowance N for Bob, later calls `approve` again to change it to M; if Bob's `transferFrom(N)` lands between Alice's two transactions, Bob can spend N and then M — a total of N+M — exceeding what Alice ever intended to allow at any single point in time.

Unlike this contract, the CW20 pointer explicitly patches this by converting `approve(spender, newAmount)` into a diff-based `increase_allowance`/`decrease_allowance` CosmWasm execute call [4](#0-3) , showing the team is aware of and has fixed this bug class elsewhere, but the native-token pointer was left using the vulnerable default.

### Impact Explanation
Native-token ERC20 pointers are the standard way EVM contracts and DeFi integrations interact with native Sei/tokenfactory denoms (e.g. `usei`) via ERC20 semantics. Any protocol or user that relies on `approve`+`transferFrom` against these pointer contracts (e.g., DEX routers, lending protocols) is exposed to the classic allowance front-running attack, resulting in unauthorized transfer of tokens beyond the owner's final intended allowance — i.e., concrete fund loss for the token owner.

### Likelihood Explanation
The precondition (owner changes an existing non-zero allowance to a different non-zero value, and the spender is a malicious or compromised actor monitoring the mempool) is a common integration pattern for approvals to routers/vaults, and the exploit requires only a public RPC user submitting a transaction ahead of the owner's pending `approve` — no privileged access needed. This is reachable purely through the pointer precompile and standard EVM transaction submission, matching the required "unprivileged transaction sender" threat model.

### Recommendation
Override `approve` in `NativeSeiTokensERC20.sol` to use the diff-based `increase_allowance`/`decrease_allowance` pattern already implemented in `CW20ERC20Pointer.sol` [4](#0-3) , or add explicit `increaseAllowance`/`decreaseAllowance` functions and document that `approve` should not be used for allowance updates on an existing non-zero allowance.

### Proof of Concept
1. Alice deploys/uses the native pointer for `usei` (or any tokenfactory denom) via `addNativePointer`.
2. Alice calls `approve(Bob, N)` on the pointer contract; `allowance(Alice, Bob) == N`.
3. Alice decides to change Bob's allowance and submits `approve(Bob, M)`.
4. Bob observes the pending transaction in the mempool and front-runs it with `transferFrom(Alice, Bob, N)`, which succeeds against the still-live allowance of N (inherited standard OpenZeppelin `transferFrom`/`_spendAllowance` logic, unmodified in this contract).
5. Alice's `approve(Bob, M)` is then mined, resetting `allowance(Alice, Bob)` to M.
6. Bob calls `transferFrom(Alice, Bob, M)` again, netting N+M total, more than Alice ever intended to allow outstanding at once.

pragma solidity ^0.8.0;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {IBank} from "./precompiles/IBank.sol";

contract NativeSeiTokensERC20 is ERC20 {

    address constant BANK_PRECOMPILE_ADDRESS = 0x0000000000000000000000000000000000001001;

    string public denom;
    string public nname;
    string public ssymbol;
    uint8 public ddecimals;
    IBank public BankPrecompile;

    constructor(string memory denom_, string memory name_, string memory symbol_, uint8 decimals_) ERC20("", "") {
        BankPrecompile = IBank(BANK_PRECOMPILE_ADDRESS);
        denom = denom_;
        nname = name_;
        ssymbol = symbol_;
        ddecimals = decimals_;
    }

    function name() public view override returns (string memory) {
        return nname;
    }

    function symbol() public view override returns (string memory) {
        return ssymbol;
    }

    function balanceOf(address account) public view override returns (uint256) {
        return BankPrecompile.balance(account, denom);
    }

    function decimals() public view override returns (uint8) {
        return ddecimals;
    }

    function totalSupply() public view override returns (uint256) {
        return BankPrecompile.supply(denom);
    }

    function _update(address from, address to, uint256 value) internal override {
        bool success = BankPrecompile.send(from, to, denom, value);
        require(success, "NativeSeiTokensERC20: transfer failed");
        emit Transfer(from, to, value);
    }
}

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }
