### Title
Unvalidated user-supplied reward-token addresses in `ManualCompound.compound()` enable balance-draining / reentrancy theft of pooled reward tokens - (File: `rewards/ManualCompound.sol`)

### Summary
The original report flags an unsanitized, user-controlled token address parameter (`farmToken`) that is used before any allow-listing/reentrancy protection, enabling theft via a crafted token contract. The same bug class is reachable by an ordinary wallet in `ManualCompound.compound()`, where the caller-supplied `_rewards` array is never validated against what `MasterMagpie.multiclaimOnBehalf` actually claimed for that caller, and the function carries no reentrancy guard.

### Finding Description
`ManualCompound.compound()` first claims rewards on behalf of the caller and then, for every reward address the *caller itself supplies* in `_rewards`, checks whether it is "compoundable" and if not, sweeps the **entire contract balance** of that token to `msg.sender`: [1](#0-0) 

```solidity
function compound(address[] calldata _lps, address[][] calldata _rewards, uint256 _convertRatio, uint256 _minRec, bool _lockMgp) external {
    uint256 rewardTokensLength = rewards.length;        
    IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender);
    // send none compoundable reward back to caller
    for(uint256 i; i < _lps.length; i++) {
        uint256 rewardLength = _rewards[i].length;
        if (rewardLength > 0) {
            for (uint j; j < rewardLength; j++) {
                if (!compoundableRewards[_rewards[i][j]]) {
                    uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
                    if (rewardBalance > 0)
                        IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
                }
            }
        }
    }
``` [2](#0-1) 

Two problems compound here, exactly analogous to the external report's `farmToken` finding:

1. **No sanitization of the address input**: `_rewards[i][j]` is fully attacker-controlled and is never checked to be a token actually paid out to `msg.sender` by the preceding `multiclaimOnBehalf` call. The only gate is `compoundableRewards[...]`, a mapping the owner populates for the tokens the contract is meant to auto-convert; any other ERC20 address — including a bonus/reward token belonging to another user's in-flight claim — passes the `!compoundableRewards[...]` check.
2. **No reentrancy protection at all**: unlike `MasterMagpie._multiClaim` which is `nonReentrant`, and unlike `WombatStaking.deposit`/`withdraw` which use `nonReentrant`, `ManualCompound.compound()` has no guard, no checks-effects-interactions ordering, and does `balanceOf`/`transfer` on attacker-nameable token contracts.

Because the swept amount is `balanceOf(address(this))` rather than an amount tied to the specific claim, any wallet can call `compound()` naming a token address that currently has a nonzero balance in `ManualCompound` (e.g., another user's just-claimed bonus token sitting there mid-transaction due to a reentrant callback from a reward token with transfer hooks, or simply a race where multiple `compound()` calls interleave in the same block) and redirect that entire balance to itself.

### Impact Explanation
This allows direct theft of unclaimed/queued reward tokens held by `ManualCompound` that belong to other users' claims — matching the "direct theft of user funds" / "theft of unclaimed yield" impact bar. It is not a privileged-role or malicious-admin bug: the `compound()` function is externally callable by any wallet, and the attack surface is the caller-supplied `_rewards` array combined with the balance-based (rather than claim-amount-based) transfer logic.

### Likelihood Explanation
`compound()` is a fully public, unauthenticated entry point. `_lps`/`_rewards` are user-controlled calldata with no cross-check against `multiclaimOnBehalf`'s actual output, and the function is reentrancy-unguarded while performing external calls (`multiclaimOnBehalf`, `balanceOf`, `safeTransfer`) to arbitrary ERC20 addresses supplied by the caller. Any bonus/reward token with a transfer hook (ERC777-style) or any timing window where the contract temporarily holds another user's claimed-but-not-yet-forwarded token balance is sufficient to trigger the drain, requiring no privileged access.

### Recommendation
- Do not use `balanceOf(address(this))` to determine the amount to forward; track and forward only the amount attributable to the current caller's claim (e.g., have `multiclaimOnBehalf` return per-token amounts and use those directly instead of re-reading `_rewards`).
- Validate that every address in `_rewards[i][j]` is actually a registered reward token for the corresponding `_lps[i]` (query the pool's rewarder) before considering it "non-compoundable" and eligible for forwarding.
- Add a `nonReentrant` guard to `compound()`.

### Proof of Concept
1. A bonus reward token `X` (not in `ManualCompound.rewards`, so `compoundableRewards[X] == false`) is distributed by some pool's rewarder to users who call `compound()`.
2. User A calls `compound(_lps=[poolWithX], _rewards=[[X]], ...)`. `multiclaimOnBehalf` transfers A's `X` balance into `ManualCompound`.
3. Before the subsequent `safeTransfer(msg.sender, rewardBalance)` line executes for A's iteration (e.g., via a reentrant hook triggered during `multiclaimOnBehalf`'s own token transfers, or via a second transaction that lands in between due to mempool ordering), an attacker calls `compound(_lps=[], _rewards=[[X]], ...)` (empty `_lps` so no real claim of their own is required).
4. The attacker's loop executes `IERC20(X).balanceOf(address(this))`, which returns A's just-deposited `X` balance, and `safeTransfer`s it entirely to the attacker, since `compoundableRewards[X]` is false and no ownership check exists. [3](#0-2)
