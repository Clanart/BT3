### Title
Malformed threshold keys with an identity group key abort Bitcoin FROST signing - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts attacker-controlled verification shares and derives the group key without rejecting the identity point. [1](#0-0) [2](#0-1) 

Bitcoin’s BIP-340 `Hram` implementation unconditionally extracts x-coordinates and explicitly panics when the aggregate nonce or group key is infinity. [3](#0-2) [4](#0-3) 

### Finding Description
`C::read_G` validates only canonical encoding; it does not reject the identity point. [5](#0-4) 

For a serialized `t = 1, n = 1` `ThresholdKeys<Secp256k1>`, a single identity verification share therefore produces an identity `group_key` while remaining acceptable to `ThresholdKeys::new` and `ThresholdKeys::read`. [6](#0-5) [1](#0-0) 

When the deserialized keys are used by the Bitcoin Schnorr algorithm, `sign` reaches `sign_share`, which computes the BIP-340 challenge using `x(A)`; `A` is the identity group key, so `x` unwraps a missing x-coordinate and aborts the process. [7](#0-6) [8](#0-7) 

### Impact Explanation
An unprivileged party who can supply serialized `ThresholdKeys` bytes can reliably crash a Bitcoin FROST signing process instead of receiving an `io::Error` or `FrostError`. [9](#0-8) [3](#0-2) 

Repeated submission of the malformed key package can repeatedly abort signing attempts, matching the externally reported class of attacker-controlled input causing process termination. [4](#0-3) 

### Likelihood Explanation
The serialized form is directly attacker-controlled: the participant count, interpolation variant, secret-share encoding, and every verification share are all read from the supplied byte stream. [10](#0-9) 

No signature, proof, secret knowledge, or malformed point encoding is required because the identity point is canonical and passes `read_G`. [5](#0-4) 

The exploit requires the target to consume an attacker-supplied serialized `ThresholdKeys`, but that input path is within the exposed deserialization API. [11](#0-10) 

### Recommendation
Reject an identity `group_key` in `ThresholdKeys::new`, preferably returning a new semantic-validation `DkgError`, and consider rejecting identity verification shares as well. [6](#0-5) 

Bitcoin signing should also validate that the group key and aggregate nonce are non-identity before calling `x`, returning `FrostError` rather than panicking on malformed key material. [4](#0-3) [7](#0-6) 

### Proof of Concept
```rust
use std::collections::HashMap;

use zeroize::Zeroizing;
use rand_core::OsRng;
use k256::{ProjectivePoint, Scalar};

use frost::{
  Participant, ThresholdParams, ThresholdKeys, Interpolation,
  curve::Secp256k1,
  sign::{AlgorithmMachine, PreprocessMachine, SignMachine},
};
use bitcoin_serai::Schnorr;

let participant = Participant::new(1).unwrap();
let params = ThresholdParams::new(1, 1, participant).unwrap();

let mut verification_shares = HashMap::new();
verification_shares.insert(participant, ProjectivePoint::IDENTITY);

// ThresholdKeys::new accepts this and derives an identity group key.
let keys = ThresholdKeys::<Secp256k1>::new(
  params,
  Interpolation::Lagrange,
  Zeroizing::new(Scalar::ZERO),
  verification_shares,
)
.unwrap();

assert!(bool::from(keys.group_key().is_identity()));

// The same state can cross the public byte boundary.
let encoded = keys.serialize();
let decoded =
  ThresholdKeys::<Secp256k1>::read(&mut encoded.as_slice()).unwrap();

let (machine, _) =
  AlgorithmMachine::new(Schnorr::new(), decoded).preprocess(&mut OsRng);

// Panics inside bitcoin_serai::crypto::x when hashing the identity group key.
let _ = machine.sign(HashMap::new(), b"message");
```

The panic occurs because `keys.group_key()` remains identity after serialization/deserialization, and the Bitcoin challenge routine passes that point to `x`, whose `expect("point at infinity")` aborts execution. [12](#0-11) [3](#0-2)
