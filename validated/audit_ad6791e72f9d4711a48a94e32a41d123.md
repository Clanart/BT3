### Title
App Proxy signature verification accepts stale/replayed requests due to missing timestamp freshness check - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` verifies only that the HMAC `signature` query parameter matches the other query parameters, but it never validates the `timestamp` parameter that Shopify includes in every app-proxy request. [1](#0-0)  This mirrors the reported oracle bug class: a signed/authenticated value is accepted without checking that it is fresh (staleness/round validation), allowing indefinite reuse of a previously valid signed payload.

### Finding Description
`verify_proxy_request` is registered as a `before_action` for any controller including this concern, and it only calls `query_string_valid?`, which recomputes the HMAC over the query string (excluding `signature`) and compares it to the supplied `signature` using `secure_compare`. [2](#0-1)  Although Shopify's app-proxy requests always include a `timestamp` parameter (visible in the gem's own tests, e.g. `timestamp=1466106083`), the code treats it purely as HMAC input data and never checks it against the current time. [3](#0-2)  Consequently, a request whose `timestamp` value is from far in the past will pass verification just as validly as a fresh one, since the signature is only checked for integrity of the query string content, not the age of the request. This is functionally analogous to the wstETHChainlinkOracle bug: a downstream consumer trusts signed/oracle data without validating that it is not stale, opening the door to replay of old, potentially outdated or leaked signed data as if it were current.

### Impact Explanation
An app-proxy URL (including its `shop`, `path_prefix`, `timestamp`, and `signature` params) is exposed in the browser address bar/referrer of any storefront visitor and can end up in browser history, server access logs, analytics tools, or shared/cached links. Because the signature never expires, anyone who obtains a previously issued, valid app-proxy URL can replay it indefinitely to invoke the app's proxied endpoint in the context of that shop, even long after the original request. Depending on what the proxied controller action does (e.g., returning shop-specific data, or triggering shop-scoped side effects), this enables an unrelated party to obtain a valid, accepted forged/replayed signed request outside of any legitimate storefront session — a "stale" credential being treated as fresh.

### Likelihood Explanation
Exploitation requires the attacker to have captured a genuine app-proxy URL at some point (e.g., via logs, browser history, shared links, or a leaky referer). This is a real, commonly-cited risk for HMAC-based, non-expiring URLs (similar to the well-known "signed URL replay" class of issues), and it does not require any secret compromise or elevated privilege — only observation of a previously issued signed request.

### Recommendation
Add a freshness check on the `timestamp` query parameter in `query_string_valid?` (or `verify_proxy_request`), rejecting requests whose `timestamp` is outside an acceptable window (e.g., a few minutes) from the current time — analogous to the oracle fix's `updatedAt`/`roundId` checks:

```ruby
def verify_proxy_request
  head(:forbidden) unless query_string_valid?(request.query_string) && timestamp_fresh?(request.query_string)
end

def timestamp_fresh?(query_string, max_age = 5.minutes)
  timestamp = Rack::Utils.parse_query(query_string)["timestamp"].to_i
  (Time.now.to_i - timestamp).abs <= max_age
end
```

### Proof of Concept
1. A merchant's storefront visitor loads a page containing an app-proxy link, e.g. `https://shop.example.com/apps/my-app?shop=some-shop.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=f5cd7233...`.
2. An attacker later obtains this exact URL (via browser history, a shared link, log exposure, etc.) long after `timestamp=1466106083` has passed.
3. The attacker replays the identical URL against the app's app-proxy endpoint.
4. `query_string_valid?` recomputes the HMAC over the same query parameters and it still matches, so `verify_proxy_request` allows the request through with no check on how old `timestamp` is. [2](#0-1) 
5. The proxied controller action executes as if this were a fresh, legitimate storefront-initiated request.

Note: I was unable to verify from this index whether any app built on this gem places sensitive, state-changing logic directly in an app-proxy controller (this depends on the consuming app), so real-world impact severity depends on what actions the app exposes via app-proxy routes.

      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
