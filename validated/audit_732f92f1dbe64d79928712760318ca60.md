### Title
`ThresholdKeys::read` trusts attacker-supplied `t`, `n`, and interpolation mode — threshold policy can be downgraded from the wire - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes the threshold `t`, participant count `n`, the interpolation-mode byte, the secret share, and all `n` verification shares from a single untrusted byte stream, then calls `ThresholdKeys::new` which computes the group key and enforces consistency rules only against those same attacker-chosen parameters. There is no MAC, commitment, transcript binding, or external check tying `t`/`n`/`interpolation` to the key set that was actually produced by the DKG. An unprivileged party who can feed bytes to `ThresholdKeys::read` can therefore force a weaker security configuration — the exact analog of a client forcing selection of a weaker TLS protocol than the one configured.

### Finding Description
The deserializer reads every security-critical parameter directly from the stream:

- `t`, `n`, `i` are read as raw little-endian `u16`s and passed to `ThresholdParams::new`, which only checks `t != 0`, `n != 0`, `t <= n`, `i <= n` — no relation to any real key set (crypto/dkg/src/lib.rs, `ThresholdKeys::read`, lines 591–631; `ThresholdParams::new`, lines 166–179).
- A single byte selects the interpolation method: `0` → `Constant` (with `n` scalar coefficients), `1` → `Lagrange` (lines 604–616).
- `ThresholdKeys::new` then derives `group_key` as the interpolation of `verification_shares[1..=t]` — i.e., over the *attacker-supplied* `t` (lines 376–378).

Downstream, the only guard on the signing set is `included.len() < multisig_params.t()` in `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs:298) and the same `included.len() < t` check in `ThresholdKeys::view` (crypto/dkg/src/lib.rs:464). Both consume the deserialized `t`. Nothing anywhere re-derives or pins the intended threshold.

Two distinct downgrade paths exist:

1. **Threshold downgrade.** Keep the victim's secret share and verification shares but serialize a smaller `t` (and consistent `n`). `sign`/`view` will now accept a signing set smaller than the true DKG threshold — e.g. `t=1` lets a single participant (whoever loads the blob) produce FROST shares that verify, since the Lagrange factors and verification shares are still internally consistent.
2. **Interpolation downgrade.** Flip the interpolation byte from `Constant` to `Lagrange`. The `Constant` branch is the only one that enforces `t == n` (`InapplicableInterpolation`, lines 368–374); selecting `Lagrange` silently skips that requirement and changes how `group_key` and per-set factors are computed, producing a different effective key and policy from the same encoded shares — a semantics downgrade invisible to the loader.

Additionally, because all `n` verification shares come from the same blob, an attacker can simply write `t=1, n=1`, an arbitrary `secret_share`, and `G*secret_share` as the only verification share. `ThresholdKeys::read` accepts this and yields a fully valid "threshold" key under an attacker-chosen group key; any `AlgorithmMachine` built on it signs whatever message it is fed under the attacker's key.

### Impact Explanation
The configured threshold policy (`t`-of-`n`) is the core security invariant of the FROST multisig. By treating it as an attacker-controlled wire field, the code allows an unprivileged party to:

- cause `sign`/`complete` to emit valid signatures with fewer than the intended `t` participants (unintended signing under a weakened quorum);
- substitute an entirely attacker-controlled 1-of-1 key hierarchy, causing the host to produce signatures binding to an attacker-chosen group key — usable for tricking services that treat the resulting signature/group key as authoritative;
- silently alter key semantics via the interpolation byte, producing signatures under a group key different from what peers expect without any deserialization error.

This is a "client chooses the weaker supported option and the configured option is not enforced" bug, matching CVE-2023-2974's class.

### Likelihood Explanation
`ThresholdKeys::read` is the canonical rehydration path for persisted or transmitted key material; any flow where key blobs are stored, backed up, synced, or supplied by a coordinator/peer (rather than generated in-process via PedPoP) is exposed. The attacker needs only to influence the bytes read — no key material, no collusion, no validator privileges. Exploitation is deterministic (no probabilistic work) and produces signatures that pass all in-library verification checks, since every check is self-consistent with the downgraded parameters. Severity: Medium — it requires a delivery path for the crafted blob, but once delivered the security guarantees are fully voided.

### Recommendation
Do not trust serialized security parameters:

- Bind `t`, `n`, `i`, the interpolation tag, and `secret_share` into a keyed commitment/MAC or a transcript hash computed at DKG completion (`PedPoP`/`generate`), stored alongside the blob, and verified inside `ThresholdKeys::read` before constructing `ThresholdCore`.
- Alternatively, store only the `secret_share` and a commitment to the parameter set + verification shares; recompute `group_key` and verify it equals a pinned expected group key supplied by the caller.
- At minimum, have callers pass the expected `ThresholdParams` into `read` and reject mismatches, and require the interpolation method be fixed per deployment rather than byte-selected.

### Proof of Concept
```rust
use std::io::Cursor;
use rand_core::OsRng;
use zeroize::Zeroizing;

use ciphersuite::Ciphersuite;
use dkg::{Participant, ThresholdParams, ThresholdKeys, Interpolation};
use frost::{curve::Ristretto, sign::*};

// Honest 2-of-3 keys
let params = ThresholdParams::new(2, 3, Participant::new(1).unwrap()).unwrap();
let share = Zeroizing::new(<Ristretto as Ciphersuite>::random_nonzero_F(&mut OsRng));
let shares: Vec<_> = (1..=3)
  .map(|_| <Ristretto as Ciphersuite>::random_nonzero_F(&mut OsRng))
  .collect();
let vshares = shares
  .iter()
  .enumerate()
  .map(|(i, s)| (Participant::new(i as u16 + 1).unwrap(),
                 <Ristretto as Ciphersuite>::generator() * s))
  .collect();
let keys = ThresholdKeys::<Ristretto>::new(
  params, Interpolation::Lagrange, share, vshares).unwrap();

// Serialize, then downgrade t: 2 -> 1 in the wire bytes
let mut blob = keys.serialize().to_vec();
// Layout: [id_len:u32][ID][t:u16][n:u16][i:u16][interp:u8][share][vshares...]
let id_len = u32::from_le_bytes(blob[0..4].try_into().unwrap()) as usize;
blob[4 + id_len] = 1; // t low byte: 2 -> 1
blob[4 + id_len + 1] = 0;

// Deserialization succeeds — no binding of t to the key set
let downgraded = ThresholdKeys::<Ristretto>::read(&mut Cursor::new(&blob)).unwrap();
assert_eq!(downgraded.params().t(), 1); // threshold silently lowered

// A single-participant signing set now passes the quorum check
// sign(): included.len() (=1) < t (=1) is false -> proceeds to sign
let machine = AlgorithmMachine::<Ristretto, _>::new(schnorr_algo(), downgraded);
let (sign_machine, _preprocess) = machine.preprocess(&mut OsRng);
// sign(empty_preprocesses, msg) succeeds instead of failing with
// FrostError::InvalidSigningSet, producing a valid share for a
// "threshold" signature produced by fewer than the intended t parties.
```

Similarly, setting `t=1, n=1`, `i=1`, interpolation byte `1`, an arbitrary `secret_share`, and `generator()*secret_share` as the single verification share yields a `ThresholdKeys` that signs under a fully attacker-chosen group key with no error.
