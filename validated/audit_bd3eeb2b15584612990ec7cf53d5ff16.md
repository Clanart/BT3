### Title
Aggregator gRPC surface reachable with zero client authentication when `client_verification=false` - (File: core/src/servers.rs)

### Summary
`create_grpc_server` builds `ServerTlsConfig` without `.client_ca_root(...)` and wraps the service with the `Noop` interceptor whenever `config.client_verification == false`, so the TLS layer never requests a client certificate and no application-level check substitutes for it. This exposes the entire `ClementineAggregator` service (`Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`, `InternalSendTx`, `SendMoveToVaultTx`, `InternalGetEmergencyStopTx`) to any host that can complete a plain server-auth-only TLS handshake, with no certificate, no key share, and no prior relationship to the bridge.

### Finding Description
The claimed binding — CALLER_AUTHORITY: "party reaching any `ClementineAggregator` method" == "party holding a certificate trusted by `ca_cert_path`" — is enforced only through two mechanisms that are both disabled together when `client_verification` is `false`:

1. TLS-layer mTLS: `ServerTlsConfig::new().identity(server_identity).client_ca_root(client_ca)` is only applied when `config.client_verification` is `true`; otherwise `ServerTlsConfig::new().identity(server_identity)` is used with no `client_ca_root`, so `rustls`/`tonic` never asks the peer for a certificate at all. [1](#0-0) 

2. Application-layer interceptor: `InterceptedService::new(service, ...)` picks `Noop` (a passthrough that returns `Ok(req)` unconditionally) instead of `OnlyAggregatorAndSelf` when `client_verification` is `false`. [2](#0-1) [3](#0-2) 

`OnlyAggregatorAndSelf`, when active, pins the leaf certificate to either the aggregator's own certificate or the callee's own certificate, and rejects the request if `peer_certs()` returns `None` outside test builds. [4](#0-3) 
None of this runs when `Noop` is selected, so there is no second line of defense once TLS itself fails to demand a cert.

Critically, `BridgeConfig::check_mainnet_requirements` only rejects `client_verification=false` for `cli::Actor::Verifier` and `cli::Actor::Operator`; the aggregator actor is not checked, so an aggregator running with `client_verification=false` passes mainnet configuration validation. [5](#0-4) 
This confirms `client_verification=false` is an accepted deployment state specifically for the aggregator, not merely a misconfiguration caught elsewhere.

Exploit flow: an attacker opens a TCP connection to the aggregator's public port and performs a TLS handshake presenting only server-side validation (verifying the aggregator's server cert, or skipping verification entirely since the attacker is the initiator) and no client certificate/identity. Because `client_ca_root` was never set, `rustls` completes the handshake without requesting a `CertificateRequest` from the client. The resulting HTTP/2 stream reaches `InterceptedService` wrapping `Noop`, which passes every request through untouched to the underlying `ClementineAggregatorServer`, including state-changing/broadcasting RPCs like `SendMoveToVaultTx` and `InternalSendTx`.

### Impact Explanation
Any unauthenticated party can invoke aggregator RPCs that trigger deposit setup, withdrawal orchestration, and transaction broadcasting logic that is otherwise gated to trusted operators/verifiers holding a CA-issued certificate. This matches the "High - an unauthenticated state-changing or broadcasting call" category: the caller needs zero credentials, no key share, and no certificate to reach RPCs that cause the aggregator to send/broadcast transactions (`InternalSendTx`, `SendMoveToVaultTx`) or drive the deposit/withdrawal state machine (`NewDeposit`, `Withdraw`, `OptimisticPayout`). The blast radius is the entire aggregator instance and every deposit/operator it coordinates, and the attack is fully repeatable per connection since no rate limiting or credential state is consumed.

### Likelihood Explanation
The only precondition is `config.client_verification == false` on the aggregator, which is a supported and mainnet-permitted configuration per `check_mainnet_requirements` (which exempts the aggregator actor from this check). No BTC cost, no fees, no prior deposit or withdrawal is required — the attacker only needs network reachability to the aggregator's TCP port and a standard TLS client library. This makes the finding fully feasible and trivially repeatable in any deployment using this configuration.

### Recommendation
Do not allow `client_verification=false` to remove `client_ca_root` from `ServerTlsConfig` for the aggregator. At minimum:
- Always call `.client_ca_root(client_ca)` on `ServerTlsConfig` so mTLS is enforced at the transport layer regardless of `client_verification`, and use `client_verification` only to toggle the additional `OnlyAggregatorAndSelf` identity-pinning check on top of a mandatory client-cert requirement.
- Extend `check_mainnet_requirements` to also flag `client_verification=false` (or the absence of `client_ca_root`) for `cli::Actor::Aggregator`.

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
