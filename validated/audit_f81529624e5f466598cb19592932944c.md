### Title
`SignableTransaction::new` omits the OP_RETURN output from the weight/vbyte calculation, undercounting the required fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the oracle's inverted/mis-scaled price formula, `SignableTransaction::new` computes the transaction's weight and vbytes from `payments` only, even though an OP_RETURN output (up to 80 bytes of data) has already been appended to `tx_outs`. The resulting `needed_fee` is an incorrect fee formula output: it does not cover the actual serialized size of the transaction being built.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed into `tx_outs` at lines 194–202, but the weight used for fee estimation is computed from `payments` (which excludes the OP_RETURN) at line 204:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds a mock `Transaction` whose `output` list is derived only from the `payments` slice (plus an optional change output), so the OP_RETURN output's size is never included in `weight`/`vbytes` (`send.rs:85-99`). The same omission occurs in the change-aware recomputation at lines 225–227.

Consequences of the wrong formula:
- `needed_fee` is undercharged by roughly `fee_per_vbyte * (9 + data_len)` vbytes worth of fee.
- The minimum-relay-fee check at line 211 uses the undercounted `vbytes`, so a transaction that should be rejected as below the relay minimum can pass.
- When a change output exists, the change amount is `input_sat - payment_sat - fee_with_change` (line 228), so the sats that should have paid for the OP_RETURN's weight are instead diverted into change; the effective fee rate of the broadcast transaction is lower than the caller-requested `fee_per_vbyte`, potentially below mempool acceptance, leaving the spend unconfirmed.

### Impact Explanation
A caller supplying `data` receives a `SignableTransaction` whose `needed_fee()` under-reports the true cost of the requested fee rate. Downstream logic that amortizes `needed_fee` across payments and relies on the invariant "fee paid ≈ fee_per_vbyte × vsize" is violated; the produced transaction pays a lower effective feerate than intended and may fail relay or stall unconfirmed, making the input funds temporarily unspendable. This is an incorrect-formula bug of the same class as the DAI oracle report (wrong quantity produced by a calculation), reachable purely via the public `data` argument.

### Likelihood Explanation
Any invocation of `SignableTransaction::new` with `data: Some(_)` and a `change` script triggers the undercount. The impact is bounded (~90 bytes of weight, i.e., ~23 vbytes of uncounted fee), so it is a Medium-severity correctness bug rather than fund loss.

### Recommendation
Include the OP_RETURN output in the weight calculation — e.g., pass the already-built `tx_outs` (or a `data_len` parameter) into `calculate_weight_vbytes` instead of `payments`, in both call sites (lines 204 and 225–227), so `vbytes` reflects the real transaction size.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)`. The returned `tx.output` contains the OP_RETURN output, but `tx.needed_fee()` equals `fee_per_vbyte * vsize(without OP_RETURN)`. Compare with `u64::try_from(tx.tx.vsize()).unwrap() * fee_per_vbyte` — `needed_fee` is smaller by `fee_per_vbyte *` the OP_RETURN output's vsize, and when change is present, `tx.fee() - needed_fee` sats are wrongly allocated to the change output.
