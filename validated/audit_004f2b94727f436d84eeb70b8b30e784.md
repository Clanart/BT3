### Title
Vesting logic in `_getClaimable` is non-functional — allows immediate full-amount claim, causing possible protocol insolvency for other claimants - ([File: rewards/ArbitrumMWomAirdrop.sol])

### Summary
`_getClaimable` unconditionally sets `vested = totalAmount`, meaning every eligible account can claim their *entire* `totalAmount` the moment `startVestingTime` is reached, instead of a linearly vested portion. The state variables `vestingPeriodCount` and `intervals` are declared and set via constructor/config but never referenced in the vesting computation, confirming the vesting schedule is dead code.

### Finding Description
In `rewards/ArbitrumMWomAirdrop.sol`: [1](#0-0) 

```solidity
function _getClaimable(address account, uint256 totalAmount) internal view returns (uint256) {
    uint256 claimed = getClaimed(account);
    if (claimed >= totalAmount) {
        return 0;
    }

    uint256 vested = totalAmount;
    if (vested > totalAmount) {
        return totalAmount - claimed;
    }

    return vested - claimed;
}
```

`vested` is hardcoded to `totalAmount` — there is no reference to `block.timestamp`, `startVestingTime`, `vestingPeriodCount`, or `intervals` anywhere in this calculation. The `vested > totalAmount` guard can never be true since `vested` is exactly `totalAmount`, so it is dead code. As a result, `getClaimable()` and `claim()` both return the full `totalAmount - claimed` as soon as `block.timestamp >= startVestingTime` is satisfied (checked separately at line 86 and 57), with no gradual release over time.

Any account with a valid merkle leaf (the intended, permissionless call path — no privileged role required) can call `claim(totalAmount, proof, false, false)` right at `startVestingTime` and receive their full allocation in one transaction: [2](#0-1) 

No modifier, reentrancy guard, or balance check other than the ERC20 transfer's implicit balance check prevents this — `nonReentrant` and `whenNotPaused` do not address the vesting-schedule flaw, they only guard against reentrancy/pausing. If the contract is funded assuming a linear/period-based drip (sized only to cover vested amounts up to some point in time, not the full sum of all `totalAmount`s), whichever addresses claim first can drain the full reward balance, leaving `reward.safeTransfer` to revert for later legitimate claimants due to insufficient balance.

### Impact Explanation
This is a protocol-insolvency / broken-vesting-invariant issue: the contract's funding model (matching an intended gradual vesting schedule) can be exhausted by early claimants taking their full lump sum immediately, causing later legitimate claimants' `claim()` calls to revert (their unclaimed yield becomes effectively frozen/unpayable until the owner tops up the balance). This matches the "theft or permanent freezing of unclaimed yield / protocol insolvency for other claimants" impact class.

### Likelihood Explanation
Highly likely/trivial to trigger: it requires no special privilege, capital, or timing skill beyond having a valid merkle leaf (which any of the intended airdrop recipients naturally have) and calling `claim()` right at or after `startVestingTime`. It is fully repeatable by any/every recipient, and does not depend on admin misconfiguration — it is a direct consequence of the `_getClaimable` implementation itself.

### Recommendation
Implement the actual linear/periodic vesting formula using `startVestingTime`, `vestingPeriodCount`, and `intervals`, e.g.:
```solidity
uint256 elapsed = block.timestamp - startVestingTime;
uint256 periodsElapsed = Math.min(elapsed / intervals, vestingPeriodCount);
uint256 vested = totalAmount * periodsElapsed / vestingPeriodCount;
```
and only allow `claimable = vested - claimed`, ensuring the contract only ever needs to hold the currently-vested amount at each point, not the entire sum up front, and no claimant can obtain their unvested remainder early.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbitrumMWomAirdrop` with `startVestingTime = t0`, `vestingPeriodCount = 10`, `intervals = 30 days`, and a merkle root covering two accounts `A` (totalAmount = 1000e18) and `B` (totalAmount = 1000e18).
2. Fund the contract with only `100e18` reward tokens (i.e., an amount sized to cover only the first vesting period's worth for both accounts combined, per the intended linear schedule).
3. Warp to `t0` (start of vesting, period 1 of 10 elapsed).
4. Have account `A` call `claim(1000e18, proofA, false, false)`.
5. Assert: `A` receives the **full** `1000e18` (not `100e18` = 1/10th), draining the entire contract balance in one call — proving `_getClaimable` ignores the vesting schedule.
6. Have account `B` call `claim(1000e18, proofB, false, false)`.
7. Assert: transaction reverts due to insufficient `reward` balance (`ERC20: transfer amount exceeds balance`), demonstrating `B`'s legitimately vested (or even period-1-only) claim is now permanently blocked/frozen until the owner manually refunds the contract.
