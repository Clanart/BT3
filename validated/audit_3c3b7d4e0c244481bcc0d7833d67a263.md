### Title
Permanent fund lock in `IntentGatewayV2.withdraw` when beneficiary cannot receive native ETH - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` — invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` messages, and reachable from a solver's `fillOrder` cross-chain settlement or a user's `_cancelFromSource` refund path — pays out native-token escrow legs with a raw `.call{value: amount}("")` and **hard-reverts the entire function** if the send fails [1](#0-0) . Unlike `WrappedHyperFungibleTokenUpgradeable.onAccept`/`onPostRequestTimeout`, which explicitly guard against non-payable beneficiaries by falling back to wrapping and delivering an ERC-20 transfer instead [2](#0-1) , `IntentGatewayV2.withdraw` has no such fallback.

### Finding Description
`withdraw()` is called for two settlement kinds from `onAccept`: `RedeemEscrow` (order successfully filled cross-chain, escrow released to the filler/solver) and `RefundEscrow` (order canceled/expired, escrow returned to the original user) [3](#0-2) . The `body.beneficiary` address is attacker/user-controlled data that originated from the `Order.user` or `Order.output.beneficiary` field set at `placeOrder`/`fillOrder` time on the counterpart chain, then round-tripped through a cross-chain POST message. If that address is a contract with no `receive()`/payable `fallback()` (or one that deliberately reverts on ETH receipt), the low-level call in the native-token branch fails and the function reverts:

```
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
}
``` [4](#0-3) 

Because this revert happens inside `onAccept`, which is invoked by the ISMP host's `dispatchIncoming` message-handling loop (`(bool success,) = ... .call(abi.encodeWithSelector(IApp.onAccept.selector, ...))`), the host marks the request as retryable by deleting the receipt [5](#0-4) . In principle a relayer can keep retrying, but the payout will keep reverting deterministically for that beneficiary forever — there is no way to change the destination address once the order's escrow record is committed (`_orders[commitment][token]`), and no separate rescue/pull-payment path exists. This applies identically to the multi-asset loop: a single unpayable native leg among several output/refund assets blocks release of *all* other escrowed assets in the same withdrawal, and also blocks the transaction-fee redemption further down in the same function [6](#0-5) .

This differs from the reported StabilityPool issue only in mechanism (here it's `.call()` not `.transfer()`, so the 2300-gas starvation vector doesn't apply), but the root broken invariant is the same: unconditional native-token push with an all-or-nothing revert to a recipient address that is not guaranteed to accept ETH, with no escape hatch. The codebase's own `WrappedHyperFungibleToken(Upgradeable)` contracts demonstrate the project is aware of this exact class of bug and mitigates it with a wrap-and-ERC20-fallback pattern — `IntentGatewayV2`'s escrow settlement path was not given the same protection.

### Impact Explanation
An order whose beneficiary/refund-recipient is a non-payable contract permanently locks the escrowed input/output tokens (and any accompanying transaction fee) inside `IntentGatewayV2`, since `withdraw()` can never succeed for that commitment and there is no admin/keeper override to redirect the beneficiary or force-push funds via an alternate mechanism. This is a direct, protocol-level loss/lock of user or solver funds triggered without any relayer/prover/admin misbehavior — an ordinary user (or a solver filling on their behalf) simply needs to specify a beneficiary contract lacking `receive()`.

### Likelihood Explanation
High. Any user or solver can set `order.output.beneficiary` / `order.user` to an arbitrary address; no validation exists that the beneficiary can accept native ETH. This can happen accidentally (a smart-contract wallet without a receive function) or, in an adversarial griefing scenario against a solver, by a malicious order-filler encoding a solver-controlled beneficiary that reverts once and traps the solver's fill fee/dust as well.

### Recommendation
- Do not let a failed native-token push abort the whole settlement: isolate the transfer per-asset (e.g., wrap failures in a try/catch or move to a pull-based withdrawal credit) so other legs and the fee redemption still settle.
- Mirror the `WrappedHyperFungibleToken` pattern: on failed native push, fall back to crediting an internal balance mapping the beneficiary can later `claim()`/`pull()` via a separate function, rather than reverting the entire `onAccept` handling.
- Consider capping the gas forwarded and explicitly documenting/enforcing that native-ETH beneficiaries must be EOAs or contracts implementing `receive()`, or require WETH-style ERC-20 delivery for contract beneficiaries.

### Proof of Concept
1. Attacker/solver deploys `MaliciousBeneficiary`, a contract with no `receive()`/payable fallback.
2. User places a cross-chain order via `placeOrder` (or a solver fills via `fillOrder`) with `order.output.beneficiary = address(MaliciousBeneficiary)` and a native-ETH (`token == address(0)`) output/input leg.
3. Once the order is filled/expired, the counterpart chain dispatches a `RedeemEscrow`/`RefundEscrow` POST request; the host calls `IntentGatewayV2.onAccept` → `withdraw(body, ...)`.
4. Inside `withdraw`, `beneficiary.call{value: amount}("")` fails because `MaliciousBeneficiary` has no payable receive path; `withdraw` reverts with `InsufficientNativeToken`.
5. The host deletes the request receipt for retry per `dispatchIncoming`/timeout handler logic [5](#0-4) , but every retry hits the same deterministic revert — the escrowed funds (native ETH, any co-escrowed ERC-20 legs, and the transaction fee) remain locked in `IntentGatewayV2` indefinitely with no recovery path.
