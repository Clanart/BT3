## Finding: OAuth callback resolution race condition allows cross-session account/token confusion

### Title
Stale-state OAuth callback resolution allows cross-session account injection due to TOCTOU race - (`app/src/lib/stores/sign-in-store.ts`)

### Summary
The WalletConnect fix addressed a race condition where a session-approval response could be delivered/processed against session state that had already moved on, because the code didn't wait for/re-validate the session before acting on it. GitHub Desktop's `SignInStore.resolveOAuthRequest` has the same class of bug: it validates the in-flight OAuth session once, performs two `await`s against an attacker-influenced remote endpoint, and then re-reads the *live* `this.state` object to deliver the result — instead of using the state object it validated before the awaits.

### Finding Description
`resolveOAuthRequest` is invoked by `Dispatcher.dispatchURLAction` (`app/src/ui/dispatcher/dispatcher.ts:2102-2103`) whenever an `x-github-client://oauth?code=...&state=...` deep link is received, which is parsed by `parseAppURL` in `app/src/lib/parse-app-url.ts:77-85`. [1](#0-0) 

```
public async resolveOAuthRequest(action: IOAuthAction) {
  if (!this.state || this.state.kind !== SignInStep.Authentication) return
  if (!this.state.oauthState) return
  if (this.state.oauthState.state !== action.state) { ... return }

  const { endpoint } = this.state
  const token = await requestOAuthToken(endpoint, action.code)   // network round trip #1

  if (token) {
    const account = await fetchUser(endpoint, token)             // network round trip #2
    this.state.oauthState.onAuthCompleted(account)                // <-- re-reads live `this.state`
  } else {
    this.state.oauthState.onAuthError(new Error(...))
  }
}
```

The `state` (CSRF token) check is only performed **once, before** the two `await`s. After the awaits resolve, the code reads `this.state.oauthState` again rather than the `oauthState` object it already validated. If a *new* sign-in flow is started in the meantime (`beginDotComSignIn`/`beginEnterpriseSignIn` → `authenticateWithBrowser`, see `app/src/lib/stores/sign-in-store.ts:260-330`), `this.state` is replaced with a brand-new `Authentication` state carrying a new `oauthState` (new csrf `state`, new `onAuthCompleted`/`onAuthError` tied to a new pending `Promise`). The delayed response from the *first* flow will then invoke the **second** flow's `onAuthCompleted` with an `account` fetched from the **first** flow's `endpoint`/token.

Compare this with `authenticateWithBrowser`'s own promise resolution handler, which explicitly re-validates the session and csrf token after its await completes: [2](#0-1) 

`resolveOAuthRequest` has no equivalent re-validation, so it is the one path in this flow that is not race-safe.

Since `requestOAuthToken` and `fetchUser` both hit the endpoint captured from the *first* flow's state (`app/src/lib/api.ts:2370-2395`), and that endpoint/host is attacker-controlled whenever the user is signing in to a GitHub Enterprise instance the attacker operates, the attacker's server fully controls both the timing (how long it delays the `access_token`/`user` responses) and the content (fabricated `access_token`, fabricated user identity) of the two awaited calls.

### Impact Explanation
On resolution, `onAuthCompleted(account)` resolves the pending promise for whichever sign-in flow is *currently* active, which flows into `SignInStore.emitAuthenticate` → `AppStore._addAccount` → `AccountsStore.addAccount`, silently persisting the attacker-supplied token/identity into the OS keychain and the app's accounts list: [3](#0-2) [4](#0-3) [5](#0-4) 

This lets a malicious/attacker-controlled endpoint inject an account into a sign-in session the user believes belongs to a different (possibly legitimate) flow, causing the UI to report success for the wrong sign-in attempt and adding an untrusted, attacker-chosen token/identity to the app's stored credentials without the user knowingly completing that flow. This corrupts the invariant that "the account resolved for a given sign-in attempt originates from the endpoint/CSRF state the user actually initiated that attempt with."

### Likelihood Explanation
The attacker needs to control (or operate) the GitHub Enterprise endpoint the user is/was signing in to and to be able to delay/craft its OAuth token and user-info responses — both of which a malicious "GHE" server the attacker fully controls can trivially do (it decides when to answer `POST /login/oauth/access_token` and `GET /user`, and with what content). The remaining requirement — that the user starts a second, unrelated sign-in flow while the first is still pending — is a plausible real-world action (e.g., the user gives up waiting on a slow/malicious enterprise sign-in and instead signs in to GitHub.com, or retries sign-in against a different account) that requires no unusual or unnatural steps beyond normal UI interaction (Preferences/Accounts → sign in). This is an unprivileged, remote (network-timing) primitive with a clear code path to account/credential store corruption.

### Recommendation
Capture the validated `oauthState` (and its `onAuthCompleted`/`onAuthError` closures) into a local variable *before* the `await` calls in `resolveOAuthRequest`, and invoke those captured callbacks directly rather than re-reading `this.state` after the network calls complete. Additionally, re-validate that `this.state` is still the same `Authentication` step with the same csrf `state` value before acting on the result, mirroring the guard already present in `authenticateWithBrowser`'s `.then`/`.catch` handlers.

### Proof of Concept
1. User selects "Sign in to GitHub Enterprise" and enters a hostname operated by the attacker (`https://evil.example.com`). Desktop opens the browser to the attacker's OAuth authorize page and sets `this.state.oauthState = { state: S1, endpoint: E1, onAuthCompleted: resolve1, onAuthError: reject1 }`.
2. The attacker's authorize page redirects back to `x-github-client://oauth?code=C1&state=S1`. Desktop's `resolveOAuthRequest` validates `S1` and calls `requestOAuthToken(E1, C1)` against the attacker's server, which intentionally delays its response.
3. Before the attacker's server responds, the user gives up and instead clicks "Sign in to GitHub.com" (`beginDotComSignIn` → `authenticateWithBrowser`), setting a fresh `this.state.oauthState = { state: S2, endpoint: E2=github.com, onAuthCompleted: resolve2, onAuthError: reject2 }` and opening a new browser tab to github.com's real OAuth page (still pending, user hasn't completed it).
4. The attacker's server now responds to the earlier pending request with a forged `access_token` and an attacker-controlled user object (from `fetchUser(E1, token)`).
5. `resolveOAuthRequest` calls `this.state.oauthState.onAuthCompleted(account)` — but `this.state.oauthState` is now `S2`'s, so `resolve2` fires with the attacker's account, completing the *GitHub.com* sign-in flow with an attacker-provided identity/token from `E1`, which gets added to `AccountsStore` and displayed to the user as a completed, successful sign-in.
