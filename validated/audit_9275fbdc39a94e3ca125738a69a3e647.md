### Title
Git credential helper trusts an attacker-controlled `WWW-Authenticate` realm to classify a remote as "GitHub", enabling credential phishing via a malicious remote/proxy - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's git credential helper (`createCredentialHelperTrampolineHandler`) decides whether a remote host should be treated as "GitHub"/"GitHub Enterprise" (and therefore should trigger Desktop's GitHub sign-in UI and credential attachment logic) using a "happy path" shortcut that trusts the `WWW-Authenticate` header returned by the remote server, instead of the authoritative network verification (`isGitHubHost`). A malicious git remote or a MITM proxy sitting on a non-GitHub host can forge this header to be classified as GitHub Enterprise, causing Desktop to present its "sign in to GitHub" prompt for that attacker-controlled endpoint.

### Finding Description
The bug-class from the external report is: a verification/classification step omits an authoritative check on an attacker-influenceable field, while a *different*, more trustworthy check exists and is skipped, and that classification is later used to drive a security-relevant branch (issuing/attaching credentials).

In `getEndpointKind`, Desktop classifies a git credential request's host before deciding to prompt for GitHub sign-in or hand out a token: [1](#0-0) 

Specifically:
- Real, authoritative checks (`isDotCom`, `isGHE`, or an actual `isGitHubHost(endpoint)` HTTP probe) exist, but the function first inspects the credential input's captured `wwwauth[...]` entries — which are populated directly from the remote server's HTTP response headers that git forwards to the credential helper — and short-circuits to `'enterprise'` if any of them contains `realm="GitHub"`, with no cross-check against the endpoint's actual identity: [2](#0-1) 

This classification then determines the credential flow in `getCredential`: [3](#0-2) 

If the (attacker-forged) classification is not `'generic'` and no existing account matches the (attacker-controlled) endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, presenting the user with what looks like Desktop's native "Sign in to GitHub"/GitHub Enterprise authentication UI — but scoped to the attacker's domain: [4](#0-3) 

The actual network-based verification (`isGitHubHost(endpoint)`) is only reached as a last resort, *after* the forged `WWW-Authenticate` short-circuit has already returned: [5](#0-4) 

This is structurally the same flaw as [H-14]: a security decision (classify host as trusted "GitHub"/GHE vs. "generic") is made from a field the attacker controls (`WWW-Authenticate` realm from a remote/proxy response) while the field that should gate that decision (the actual verified server identity via `isGitHubHost`) is bypassed.

### Impact Explanation
An attacker who controls a git remote server (e.g., a repository clone/fetch URL the victim is lured into adding, or a MITM/malicious proxy in front of an arbitrary hostname) can return `WWW-Authenticate: Basic realm="GitHub"` on an HTTP 401 during a git operation. This causes GitHub Desktop's credential helper to present its GitHub Enterprise sign-in UI for the attacker's domain. If the victim, believing this is a legitimate GitHub prompt, enters a Personal Access Token or completes a browser-based sign-in against that endpoint, the credential/token is sent to the attacker-controlled server as part of the resulting git HTTP Basic Auth flow, or an OAuth handshake is initiated against the attacker's endpoint. This matches the "credential/token exfiltration" and "unauthorized OAuth or account binding" impact categories.

### Likelihood Explanation
No local access, malware, or elevated privileges are required — only that the victim clones/fetches from or has a remote pointed at (directly or via a compromised/MITM proxy) a server the attacker controls, which is a standard GitHub Desktop usage pattern (cloning third-party repositories). The `WWW-Authenticate` header is fully attacker-controlled server response content, requiring no special positioning beyond serving the git HTTP(S) endpoint itself.

### Recommendation
Do not use the `WWW-Authenticate` realm as a trust signal for classifying a host as GitHub/GitHub Enterprise. Always perform the authoritative `isGitHubHost(endpoint)` check (or another cryptographically/certificate-bound verification) before elevating a remote's credential-request classification above `'generic'`, and never present the GitHub sign-in UI for a host that has not passed that verification.

### Proof of Concept
1. Attacker sets up an HTTPS git server (or MITM proxy) at `https://evil.example.com/some-repo.git`.
2. Victim adds/clones this remote in GitHub Desktop.
3. When git requests credentials during fetch/push, the attacker's server responds with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
4. Desktop's `getEndpointKind` (app/src/lib/trampoline/trampoline-credential-helper.ts:152-165) matches the `wwwauth[...]` entry and returns `'enterprise'` without calling `isGitHubHost`.
5. `getCredential` sees `endpointKind !== 'generic'` and no matching account for `evil.example.com`, so it calls `ui.promptForGitHubSignIn('https://evil.example.com')` (trampoline-credential-helper.ts:107-125), presenting a GitHub-branded sign-in prompt for the attacker's domain.
6. Victim enters a PAT or completes sign-in, and the resulting credential/token is used for HTTP Basic Auth against `evil.example.com`, which the attacker controls and logs.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
