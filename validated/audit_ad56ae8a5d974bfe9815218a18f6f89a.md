### Title
Divergent conflict-marker parsers between context extraction and reassembly cause silent conflict-marker leakage into committed files - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
Copilot conflict resolution in Desktop uses two independently implemented parsers over the same raw file content: `extractConflictHunks()` in `app/src/lib/copilot-conflict-context.ts` (used to build the hunks sent to the model) and `reassembleResolvedFile()` in `app/src/lib/copilot-conflict-resolution.ts` (used to splice the model's per-hunk resolutions back into the file that gets written to disk and committed). Like the `IdleCDO.virtualPrice()` / `_updatePrices()` bug, these two functions can disagree on how many "hunks" a given conflicted file contains when the file has malformed/irregular marker sequences, causing the ordered splice in `reassembleResolvedFile` to misalign with the hunks the model actually resolved. In at least one concrete case this results in literal `<<<<<<<`/`>>>>>>>` conflict-marker text being written into the "resolved" file that is then staged and committed, with no error surfaced to the user.

### Finding Description
`extractConflictHunks()` [1](#0-0)  scans for conflict blocks by looking for a `baseMarker`/`separatorMarker` while collecting "ours" content, but that inner loop never checks for a `theirsMarker`. If a block is missing its `=======` separator, the "ours" collection loop keeps consuming lines — including any subsequent, well-formed conflict markers — until end of file, then fails to find a closing marker and silently drops the block (`hunkEnd === -1` → not pushed, no hunk emitted) [2](#0-1) .

`reassembleResolvedFile()` implements a *different* lookahead algorithm: for each `<<<<<<<` marker it scans forward for a `=======` and the *next* `>>>>>>>`, and only requires `hasSeparator` to have been seen at least once before the closing marker — it does not require the block to be closed before hitting the next `<<<<<<<` or otherwise validate that "ours"/"theirs" content doesn't itself contain marker lines [3](#0-2) .

Because these two parsers use different heuristics for what counts as a valid/malformed conflict block, a file with a well-formed conflict hunk followed later by a malformed one (e.g. missing `=======`) can be seen by `extractConflictHunks` as containing exactly **one** hunk (the malformed one is silently absorbed/dropped), while `reassembleResolvedFile`, run independently on the very same raw content, treats the *second* block as malformed only after already having spliced the model's one resolution into the *first* block. Since `reassembleResolvedFile` matches resolutions to conflict blocks "by order, not by line number" using a simple `hunkIndex` counter [4](#0-3) , once the assumption "number/order of hunks extractConflictHunks found == number/order of conflict blocks reassembleResolvedFile finds" breaks, the malformed second block's raw marker lines (`<<<<<<< HEAD`, `>>>>>>> feature`) are pushed through verbatim as regular file content instead of being resolved or flagged.

The corrupted value is the on-disk/staged file content produced by `reassembleResolutions()` → `IFileResolution.resolvedContent`, which is written directly via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and staged with `git add` in `_applyCopilotConflictResolutions()` [5](#0-4) . No existing guard checks that `resolvedContent` is free of conflict markers before it is written and staged; `resolveWithin()` only guards path traversal, not content correctness, and the "user edited externally" skip check only compares git status, not marker content [6](#0-5) .

### Impact Explanation
This falls squarely in the "silent corruption of what the user commits or pushes" impact category. The attacker primitive is a crafted repository/branch whose merge produces a conflicted file containing an irregular/malformed conflict-marker sequence (attacker fully controls the content of both `ours` and `theirs` sides in a repository the victim clones/merges). If the victim uses "Resolve with Copilot," Desktop can silently write literal `<<<<<<<`/`>>>>>>>` marker text into the merged file and stage it as the final resolution — the user sees a seemingly normal diff/summary but the committed file now contains malformed syntax/build-breaking content or misplaced code, without Desktop reporting that the file still has unresolved markers. Depending on file type, embedded literal `<<<<<<<`/`=======`/`>>>>>>>` strings inside source, config, or scripts can silently break behavior downstream, or in more contrived cases could relocate/alter logic in a security-relevant file the victim then pushes.

### Likelihood Explanation
Requires the model to actually accept and resolve a file with this specific structural irregularity, and requires the user to be using the (opt-in) Copilot conflict resolution feature and click "Continue Merge" without carefully reviewing the diff for lingering marker text. This is a genuine reachable code path (no special local access, admin rights, or social engineering beyond a normal merge with an attacker-influenced branch/PR), but it depends on a specific malformed-marker edge case and on the model actually preserving/ignoring the malformed block as the two parsers diverge — making it a real but narrow corner-case, similar in spirit to the original IdleCDO report ("primarily corner cases that are not obviously exploitable in practice ... potential violations of key accounting invariants should always be considered serious").

### Recommendation
Implement a single canonical conflict-marker parser/tokenizer used by both `extractConflictHunks()` (context building) and `reassembleResolvedFile()` (reassembly), so hunk counts and malformed-block handling are guaranteed identical between the two call sites — mirroring the upstream fix pattern of consolidating divergent implementations into one shared method. Additionally, add a post-reassembly validation step in `reassembleResolutions()`/`_applyCopilotConflictResolutions()` that rejects (or flags for manual review) any `resolvedContent` still containing `<<<<<<<`, `=======`, or `>>>>>>>` marker patterns before it is written to disk and staged.

### Proof of Concept
Given a conflicted file with the following raw content (one well-formed hunk followed by one malformed hunk missing its `=======` separator):
```
line1
<<<<<<< HEAD
oursA
=======
theirsA
>>>>>>> feature
line2
<<<<<<< HEAD
oursB
line3
>>>>>>> feature
line4
```
1. `extractConflictHunks(content)` returns exactly **one** hunk (`oursA`/`theirsA`); the malformed second block is silently absorbed while scanning for the separator and never emitted (see logic at [7](#0-6) ). `buildConflictContext` therefore sends the model only one hunk and stores `rawContent` unchanged.
2. The model returns a single resolved hunk for hunk index 0.
3. `reassembleResolvedFile(rawContent, [resolvedHunk0])` splices the model's content into the first block correctly, but at the second block it independently determines `hasSeparator === false` (since it never checks for the missing separator the same way) and falls into the "malformed marker — copy through as regular content" branch, pushing the literal `<<<<<<< HEAD` line, then `oursB`, `line3`, and the literal `>>>>>>> feature` line straight into the output (see [3](#0-2) ).
4. The final `resolvedContent` written by `writeFile()` and staged by `git add` in `_applyCopilotConflictResolutions` [8](#0-7)  contains raw `<<<<<<<`/`>>>>>>>` marker text as ordinary committed content, with no error or warning surfaced to the user.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }
