### Title
`updateEndRemainingAllocation()` is unguarded and callable repeatedly, letting any unprivileged caller re-lock the bonus denominator to manipulate `getBonusAmount` payouts - ([File: rewards/Airdrop.sol])

### Summary
`Airdrop.updateEndRemainingAllocation()` has no guard preventing it from being called more than once, and no access control restricting who can call it. Any address — including one with `allocations[caller] == 0` — can call it at any time after `periodsEndTime[4]` to overwrite `totalEndRemainingAllocation` with whatever `totalRemainingAllocation` currently is, which shrinks monotonically as people `claim()`. Because `getBonusAmount()` recomputes each user's bonus share on-the-fly using whatever `totalEndRemainingAllocation` happens to be set to at claim time, an attacker/allocatee can strategically re-trigger this function to change the denominator seen by different claimants, breaking the intended conservation of `totalBonus` across all claimants.

### Finding Description
The relevant code: [1](#0-0) 

`updateEndRemainingAllocation()` (lines 146-150) only checks `block.timestamp >= periodsEndTime[4]` — it does **not** check `totalEndRemainingAllocation == 0` before writing, and it is `public` with no `onlyOwner`/access restriction. `claim()` (lines 153-170) only invokes it conditionally (`if (totalEndRemainingAllocation == 0)`), but that guard is meaningless as a "lock" because anyone can call `updateEndRemainingAllocation()` directly at any later time to overwrite the already-set value with the then-current `totalRemainingAllocation`.

`totalRemainingAllocation` strictly decreases every time someone claims (`totalRemainingAllocation -= userAllocation` at line 164). `getBonusAmount()` (lines 127-143) computes:

`bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation`

using whatever `totalEndRemainingAllocation` currently holds, not a value fixed once at protocol design intent. Since the denominator is mutable and unprivileged, an attacker or self-interested allocatee can:
1. Wait until several legitimate allocatees claim (shrinking `totalRemainingAllocation`).
2. Call `updateEndRemainingAllocation()` directly, re-locking `totalEndRemainingAllocation` to this smaller value.
3. Immediately `claim()`, receiving a bonus computed against the smaller denominator — a larger bonus per token than what the pool design intended (which assumed the denominator equals the remaining allocation at the moment of the *first* claim after period 4, mirroring `totalBonus`'s forfeiture accounting).

Because different claimants can end up using different denominators for the same shared `totalBonus` pool, the sum of `bonusAmount` paid out is no longer conserved against `totalBonus`. This can cause overpayment to early manipulators and underpayment/`InsufficientBalance` reverts (line 160) for legitimate late claimants — i.e., their yield becomes effectively frozen/unclaimable, while the manipulator has already extracted a disproportionate share.

No `nonReentrant`, `onlyOwner`, or "set-once" check exists to stop this reachable, purely externally-triggerable path.

### Impact Explanation
This breaks the Conservation invariant of the bonus pool: the denominator used to split `totalBonus` is not deterministic and can be manipulated by any unprivileged caller timing their call around other users' claims. This matches "theft of unclaimed yield" — later/manipulating claimants can extract a disproportionate share of `totalBonus`, permanently altering (reducing) the payout other allocatees ultimately receive, and can push some legitimate claimants into reverting on `InsufficientBalance`, freezing their yield.

### Likelihood Explanation
No capital or privilege is required — `updateEndRemainingAllocation()` and `claim()` are both `external`/`public` with no access control. Any EOA can observe when other users claim (public mempool/chain state), wait for `totalRemainingAllocation` to shrink to a favorable value, then call `updateEndRemainingAllocation()` followed by `claim()` in the same or a following transaction. This is fully repeatable throughout the entire post-`periodsEndTime[4]` claiming window, not just a one-time front-run at the very first block.

### Recommendation
Add a guard so `totalEndRemainingAllocation` can only be set once (e.g., `if (totalEndRemainingAllocation != 0) return;` or track a separate boolean flag), consistent with the existing intent shown in `claim()`'s `if (totalEndRemainingAllocation == 0)` check. Alternatively, restrict `updateEndRemainingAllocation()` to `onlyOwner` or compute it automatically and immutably at the exact `periodsEndTime[4]` boundary (e.g., via a keeper-triggered one-time initialization) so the denominator cannot be re-written after being fixed.

### Proof of Concept
Foundry test plan (`AirdropBonusManipulation.t.sol`):
1. Deploy `Airdrop` with a `startTime`; `register()` several allocatees (A, B, C, attacker excluded/zero-allocation) before `startTime`; fund the contract with `aidropToken`.
2. Warp to `periodsEndTime[4]`.
3. **Scenario 1 (baseline)**: Have allocatee A immediately call `claim()` as the very first post-period-4 tx (triggers `updateEndRemainingAllocation()` internally with full `totalRemainingAllocation`). Record `totalEndRemainingAllocation_1` and A's `bonusAmount` via `getBonusAmount`.
4. Reset state (redeploy). **Scenario 2 (manipulated)**: Have allocatees B and C `claim()` first (shrinking `totalRemainingAllocation`), then have A directly call `updateEndRemainingAllocation()` before calling `claim()`. Record `totalEndRemainingAllocation_2` (should be smaller than `totalEndRemainingAllocation_1`) and A's resulting `bonusAmount`.
5. Assert `totalEndRemainingAllocation_2 < totalEndRemainingAllocation_1` and A's bonus in Scenario 2 > A's bonus in Scenario 1 for the identical `userAllocation`, proving the payout is order/timing-dependent and manipulable by an unprivileged caller.
6. Additionally simulate a remaining claimant D after Scenario 2 and assert their `claim()` reverts with `InsufficientBalance` due to pool depletion caused by A's inflated bonus, demonstrating frozen/lost yield for D.

```text
    /// @notice This will store the ending remaining amount for the bonus.
    function updateEndRemainingAllocation() public {
        if (block.timestamp >= periodsEndTime[4]) {
            totalEndRemainingAllocation = totalRemainingAllocation;
        }
    }

    /// @notice Claim MGP and forfeit remaining allocation
    function claim() external {
        if (totalEndRemainingAllocation == 0) {
            updateEndRemainingAllocation();
        }
        uint256 claimableAmount = getClaimableAmount(msg.sender);
        
        if(claimableAmount == 0) revert NothingToClaim();
        if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();

        uint256 userAllocation = allocations[msg.sender];
        allocations[msg.sender] = 0;
        totalRemainingAllocation -= userAllocation;
        if (claimableAmount <= userAllocation) {
            uint256 forfeited = userAllocation - claimableAmount;
            totalBonus += forfeited;
        }
        aidropToken.safeTransfer(msg.sender, claimableAmount);
    }
```
