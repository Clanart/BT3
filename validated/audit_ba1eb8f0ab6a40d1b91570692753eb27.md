Legacy pool wallet code exhibits the same bug pattern as the reported RedeemManager issue: a user can send XCH directly to the pool contract's `p2_singleton_puzzle_hash`, bypassing the reward-tracking mechanism, and the funds become permanently unrecoverable through the normal claim path.

### Title
Coins sent directly to a Pool Wallet's `p2_singleton_puzzle_hash` are permanently unclaimable because `claim_pool_rewards` only recognizes formula-verified coinbase rewards - ([File: chia/pools/pool_wallet.py])

### Summary
`PoolWallet.claim_pool_rewards()` sweeps coins sitting at the pool singleton's `p2_singleton_puzzle_hash` ("pool contract address"), but it only ever attempts to claim coins that are recognized block-reward outputs. Any XCH sent by a wallet user directly to that address (a mistake, a misunderstanding of the address label, or intentional-but-non-reward payment) is silently skipped and can never be swept by the wallet, mirroring the reported RedeemManager issue where a direct `transferFrom` to the manager address bypasses the intended request/redeem accounting and leaves funds stuck until a protocol-level fix.

### Finding Description
`claim_pool_rewards()` builds a `coin_to_height_farmed` map strictly from recognized farming-reward transactions returned by `tx_store.get_farming_rewards()`, then only includes an unspent coin at the p2-singleton address in the claim spend if it appears in that map: [1](#0-0) [2](#0-1) 

If no coin at that address matches a recognized coinbase reward, the claim raises `"Nothing to claim, no unspent coinbase rewards"` and skips the coin entirely: [3](#0-2) 

The underlying CLVM absorb path reinforces this: `create_absorb_spend()` reconstructs the "reward coin" purely from a formula (`pool_parent_id(height, genesis_challenge)` and `calculate_pool_reward(height)`), not from the actual coin the user sent: [4](#0-3) 

Because the synthetic `reward_coin.parent_coin_info`/`amount` must match the consensus reward schedule exactly, a coin whose parent id/amount don't match this formula (i.e., any coin sent by a normal wallet spend rather than a block reward) can never be constructed as an absorbable spend target - there is no code path that lets the pool wallet sweep an arbitrary, non-formula-conforming coin sitting at its own `p2_singleton_puzzle_hash`.

This is functionally identical to the reported bug class: the pooling/CAT-share-equivalent address ("RedeemManager"/"pool contract address") accepts a direct, unrequested transfer from an allowed user, the manager-side accounting (`RedeemDemand`-equivalent = `coin_to_height_farmed`) has no entry for it, and the funds sit unclaimed with no recovery path except a wallet/consensus code update.

### Impact Explanation
Funds sent to a Plot NFT/pool wallet's advertised "pool contract address" via any standard wallet transfer (not a farmed block reward) become permanently locked from the user's own pool wallet's perspective - `pw_absorb_rewards`/`claim_pool_rewards` can never retrieve them. This is a direct, user-triggered fund lock reachable by any wallet holder who mistakenly (or is tricked into) sending XCH to that address, which the CLI/RPC explicitly labels as a valid-looking address (`Pool contract address`): [5](#0-4) 
No privileged access, malicious peer, or consensus change is required - only a normal spend bundle from the affected wallet's own action.

### Likelihood Explanation
This is highly likely to be triggered accidentally in practice: the address is displayed to users by CLI/RPC as a legitimate address string (encoded/printed exactly like any other Chia address), and nothing in the wallet or CLVM layer prevents an ordinary `send_transaction` to it. The existing test suite explicitly exercises and confirms this exact scenario, showing the balance ignores such a transfer and `pw_absorb_rewards` raises `ValueError`: [6](#0-5) 

### Recommendation
Either (a) have the pool wallet detect and refund/sweep any non-reward-shaped coin found at its `p2_singleton_puzzle_hash` back to the user's main wallet via a generic (non-reward-formula) spend path, or (b) have the CLI/RPC explicitly warn/disallow sending regular transactions to a pool-contract address, and document clearly that only farming rewards are recoverable from that address.

### Proof of Concept
1. Create a `PoolWallet` (self-pooling or farming-to-pool) and note its `p2_singleton_puzzle_hash`.
2. From the main wallet, send an arbitrary amount of XCH directly to that address via `send_transaction`, as done in the existing test: [7](#0-6) 
3. Confirm the transaction; the pool wallet's balance ignores it: [8](#0-7) 
4. Call `pw_absorb_rewards` - it raises `ValueError`, and there is no other wallet or CLVM code path that lets the pool wallet ever spend that coin, permanently locking the funds: [9](#0-8)
