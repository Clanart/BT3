### Title
Remote denial of service via panic on duplicate DKG encryption-key registration - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2015-2689 (remote assertion failure → daemon exit), `Decryption::register` in PedPoP contains a reachable `assert!` that panics when a participant registers an encryption key twice. A DKG counterparty who submits two `EncryptionKeyMessage`s under the same `Participant` index crashes the honest party's process during key generation. Because every in-scope deployment runs the DKG inside long-lived coordinator/processor daemons, a single crafted duplicate message aborts the ceremony and kills the node, matching the "assertion failure and daemon exit" bug class.

### Finding Description
`Decryption::register` guards key registration with a hard assertion rather than an error:

```rust
// crypto/dkg/pedpop/src/encryption.rs:351-362
pub(crate) fn register<M: Message>(
  &mut self,
  participant: Participant,
  msg: EncryptionKeyMessage<C, M>,
) -> M {
  assert!(
    !self.enc_keys.contains_key(&participant),
    "Re-registering encryption key for a participant"
  );
  self.enc_keys.insert(participant, msg.enc_key);
  msg.msg
}
```

`Encryption::register` forwards to it unconditionally (`encryption.rs:452-458`), and it is invoked once per received `EncryptionKeyMessage` during PedPoP's first-round handling in `crypto/dkg/pedpop/src/lib.rs`. The wire format (`EncryptionKeyMessage::read`, `encryption.rs:57-59`) imposes no uniqueness constraint — uniqueness of senders is left entirely to the caller, which the library's own docs admit it cannot enforce (see the `Commitments` doc comment at `crypto/dkg/pedpop/src/lib.rs:96-101` noting the library "does not handle networking" and cannot detect a participant sending multiple messages). Any plumbing that processes two messages from the same claimed `Participant` — or processes a message batch where a malicious party's message appears twice — hits `assert!` and panics. This is a reachable panic on attacker-controlled input, not a `debug_assert!`.

A second, related panic exists at `encryption.rs:466` (`self.decryption.enc_keys[&participant]`) and `encryption.rs:388` (`self.enc_keys[&decryptor]`), which panic via HashMap indexing if a `Participant` index outside the registered set reaches `encrypt`/`decrypt_with_proof`.

### Impact Explanation
A single malformed DKG round-1 message set causes an unconditional panic in an honest participant's process. In production this kills the coordinator/processor daemon mid-ceremony (assertion failure → exit, exactly the CVE-2015-2689 shape), aborting key generation for the whole set and, depending on the panic hook used by Serai binaries (e.g., the `std::process::exit(1)` hook pattern used elsewhere in the repo), taking down the entire node rather than just the task. Repeated at each retry, this permanently wedges DKG/key-rotation.

### Likelihood Explanation
Reachable by any party able to send PedPoP messages to a victim during a DKG session — the attacker only needs to deliver two `EncryptionKeyMessage`s bearing the same `Participant` index, both of which deserialize successfully via `EncryptionKeyMessage::read`. No valid proof, signature, or secret is required; the panic fires before any cryptographic check. Exploitability is bounded by how callers multiplex messages per sender, but the library places that burden on the caller explicitly, so any caller that deduplicates by message content rather than sender index, or processes messages from an unordered/unauthenticated queue, is vulnerable.

### Recommendation
Replace the `assert!` in `Decryption::register` with a fallible check returning an error (e.g., extend `DecryptionError` or add a `RegistrationError::DuplicateParticipant`), and propagate it through `Encryption::register`. Similarly, replace the HashMap index panics at `encryption.rs:388` and `encryption.rs:466` with `.get()`/`ok_or` lookups so untrusted `Participant` indices can never panic the process.

### Proof of Concept
```rust
// Conceptual: inside PedPoP round-1 handling, for each received
// EncryptionKeyMessage the victim executes:
//   let msg = EncryptionKeyMessage::<C, Commitments<C>>::read(&mut bytes, params)?;
//   let commitments = encryption.register(sender_participant, msg);
//
// Attacker sends two well-formed messages claiming the same `Participant`:
let m1 = EncryptionKeyMessage::read(&mut evil_bytes_1, params)?; // sender = P
let m2 = EncryptionKeyMessage::read(&mut evil_bytes_2, params)?; // sender = P again
encryption.register(p, m1); // ok
encryption.register(p, m2); // assert! fires -> panic -> daemon exit
```
Root cause: `crypto/dkg/pedpop/src/encryption.rs:356-359` — `assert!(!self.enc_keys.contains_key(&participant))` on attacker-controlled `participant`, reachable through `Encryption::register` (`encryption.rs:452-458`) from deserialized `EncryptionKeyMessage` bytes (`encryption.rs:57-59`).
