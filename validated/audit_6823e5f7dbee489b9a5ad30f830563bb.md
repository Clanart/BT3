### Title
Missing zero-check on `kip71.gastarget` causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: `params/kip71_config.go`)

### Summary
`KIP71Config.GasTarget` is used unconditionally as a divisor in `NextMagmaBlockBaseFee`, but unlike its sibling parameter `BaseFeeDenominator`, the governance `FormatChecker` for `kip71.gastarget` does not reject `0`. If governance ever sets `GasTarget` to `0`, every subsequent call to `NextMagmaBlockBaseFee` — which runs on every block after the Magma hardfork — panics with a `big.Int` division-by-zero error, mirroring the DAIInterestRateModel bug class where an unchecked boundary value (here, `dsr < 1e27`; there, `GasTarget == 0`) makes a core accounting function unconditionally fail.

### Finding Description
`NextMagmaBlockBaseFee` computes `baseFeeDelta` by dividing by `gasTarget` in both the "used more than target" and "used less than target" branches: [1](#0-0) [2](#0-1) 

`gasTarget` comes directly from the governance-controlled `KIP71Config.GasTarget` field with no zero-guard: [3](#0-2) 

Compare this to `BaseFeeDenominator`, which explicitly special-cases `0` to avoid a similar divide-by-zero (defaulting to 64): [4](#0-3) 

The governance parameter definition for `kip71.basefeedenominator` explicitly rejects `0` via its `FormatChecker`: [5](#0-4) 

But the analogous definition for `kip71.gastarget` uses `noopFormatChecker`, which accepts any `uint64` including `0`: [6](#0-5) 

Additionally, `checkConsistency` in the header-vote verification path only cross-checks `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` against each other; `Kip71GasTarget` and `Kip71MaxBlockGasUsedForBaseFee` fall through to the "no more checks" branch and are accepted as long as they pass the (no-op) format check: [7](#0-6) 

Once `GasTarget == 0` is committed as the active governance parameter set (e.g., via a validator vote or, for post-Kore chains, via the on-chain GovParam contract, whose values are likewise applied without a gastarget-specific sanity check other than the same no-op `FormatChecker`), `NextMagmaBlockBaseFee` will be invoked with `kc.GasTarget == 0` on the very next block computation.

`NextMagmaBlockBaseFee` is on the hot path for ordinary node/RPC operation, not merely block sealing:
- Transaction-pool base-fee refresh after every new head: [8](#0-7) 
- Fee-history / gas-price oracle RPC calls served for any public caller: [9](#0-8) 
- Header base-fee verification during block processing: [10](#0-9) 

Because `math/big`'s `Int.Div` panics on division by zero (there is no returned error), any of these call sites will crash the node process the moment they execute after `GasTarget` becomes `0`. Since this function is deterministic and identical across all conforming nodes, every node in the network reaches the same panic at the same point — a full chain halt, not merely one caller's request failing.

### Impact Explanation
Unlike the original Compound bug (which merely reverts specific calls, temporarily freezing rate updates), this Kaia analog is more severe: an unguarded `0` for a governance-controlled divisor causes a **process panic across all consensus/RPC-serving nodes simultaneously** as soon as they attempt to compute the next block's base fee (transaction pool refresh, block validation, or fee-history/gas-price RPC calls). This halts the entire network's block production and RPC availability until every node's governance parameter is manually rolled back and nodes restarted — a critical liveness failure of the KIP-71 pricing mechanism.

### Likelihood Explanation
This requires the governance parameter `kip71.gastarget` to actually be set to `0`. Reachability is gated by the governance voting/parameter mechanism (single governing node for pre-permissionless chains, or council vote/GovParam contract afterward), so it is not achievable by an arbitrary unprivileged transaction sender. However, within the explicitly in-scope "governance parameters" category, there is no validation anywhere in the vote-consistency checks, format checkers, or `ParamSet` application path that rejects `GasTarget == 0`, in clear contrast to the sibling `BaseFeeDenominator` parameter, which was deliberately hardened against exactly this class of bug. This asymmetry indicates the omission for `GasTarget` is an oversight rather than an intentional design decision.

### Recommendation
Add an explicit zero-check to the `Kip71GasTarget` parameter's `FormatChecker` (mirroring `Kip71BaseFeeDenominator`) to reject `0` at vote/gov-application time:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
As defense in depth, also guard `NextMagmaBlockBaseFee` itself (similar to the existing `BaseFeeDenominator == 0` fallback) so that a `GasTarget == 0` value already embedded in historical chain configuration or contract-governance data cannot crash the node.

### Proof of Concept
1. Governance votes (or the GovParam contract, post-Kore) to set `kip71.gastarget = 0`. This passes `NewVoteData`/`PartialParamSet.Add` because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` [6](#0-5) , and `checkConsistency` performs no cross-parameter validation for `Kip71GasTarget` [11](#0-10) .
2. Once the parameter set takes effect at the next epoch, `pool.govModule.GetParamSet(...).ToKip71Config()` returns a `KIP71Config` with `GasTarget: 0` [12](#0-11) .
3. On the very next block, `TxPool.reset` calls `NextMagmaBlockBaseFee` [8](#0-7) , which executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0` in whichever of the two non-equal branches is taken [13](#0-12) , causing an unrecoverable `big: division by zero` panic and crashing the node process. The same panic is reachable via any `eth_feeHistory`/gas-price RPC call served after this point [9](#0-8) .
