### Title
JIT liquidity sandwich attack on `BaseRewardPool`/`BaseRewardPoolV2` reward accounting via permissionless `harvest()` and unrestricted deposit/withdraw - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`, `wombat/WombatPoolHelper.sol`, `rewards/MasterMagpie.sol`)

### Summary
`BaseRewardPool`/`BaseRewardPoolV2` distribute newly arriving reward tokens instantly and proportionally to `totalStaked()` at the moment `queueNewRewards`/`donateRewards` is called, exactly like the `FM_Rebasing_v1` bit-ratio mechanism described in the report. Because deposits and withdrawals of the underlying LP/staking tokens (via `WombatPoolHelper`/`WombatPoolHelperV2` → `MasterMagpie.deposit`/`withdraw`) are completely unrestricted (no cooldown, no minimum staking duration, no linear/streamed vesting of newly queued rewards), an unprivileged wallet can front-run a reward-funding transaction (e.g., a `harvest()` call that ultimately calls `queueNewRewards`) with a large deposit, and back-run it with an immediate withdrawal, capturing a disproportionate share of the reward that should have accrued to long-term stakers.

### Finding Description
`BaseRewardPool._provisionReward` (and the identical logic in `BaseRewardPoolV2._provisionReward` and `mWOMSVBaseRewarder._provisionReward`) updates `rewardInfo.rewardPerTokenStored` immediately, in one step, based on `totalStaked()` at the time of the call: [1](#0-0) 

There is no time-based streaming/vesting of the reward (no `periodFinish`/`rewardRate` over a duration as in typical Synthetix-style `StakingRewards`) — the entire `_amountReward` is baked into `rewardPerTokenStored` in the same transaction that funds it. This is functionally identical to the `FM_Rebasing_v1` bit-ratio increase described in the report: a single transaction that instantaneously changes the value-per-share for the entire pool.

Deposits/withdrawals into the underlying staking token are unrestricted and update the user's share (`balanceOf`, driven by `MasterMagpie.userInfo[...].amount`) with no lock or cooldown: [2](#0-1) 

A user calls `WombatPoolHelper.deposit`/`depositLP`, which calls `MasterMagpie.depositFor`, immediately crediting `user.available`/`user.amount` and thus `BaseRewardPool.balanceOf`: [3](#0-2) 

and can withdraw again in the same block/next block with no penalty via `WombatPoolHelper.withdraw` → `MasterMagpie.withdrawFor` → `_harvestAndUnstake`: [4](#0-3) [5](#0-4) 

The reward funding event itself (`queueNewRewards`/`donateRewards`) is a routine, expected, non-malicious operation — reward tokens (e.g., harvested WOM rewards or bribes) are periodically pushed into the pool via `WombatStaking`'s `harvest()`/`queueNewRewards` flow. Because this event is externally observable in the mempool before inclusion, and reward accrual is instantaneous rather than time-weighted, any wallet can:
1. Detect the pending reward-funding transaction.
2. Front-run it with a large `deposit()`.
3. Let the reward-funding transaction execute, which raises `rewardPerTokenStored` proportional to the attacker's now-inflated share of `totalStaked()`.
4. Back-run with `withdraw()` and `getReward()` to claim the disproportionate reward share, then exit.

This directly dilutes the rewards owed to genuine long-term stakers, mirroring the exact mechanism described for `FM_Rebasing_v1`.

### Impact Explanation
Long-term stakers in any pool routed through `BaseRewardPool`/`BaseRewardPoolV2` (all Wombat LP pools via `WombatPoolHelper`/`WombatPoolHelperV2`, `AnkrBNBPoolHelper`, etc.) have their unclaimed yield partially stolen/redirected to JIT attackers with no capital risk beyond gas and a single-block MEV bundle. This is a direct theft of unclaimed yield belonging to other users, satisfying the "theft or permanent freezing of unclaimed yield" impact bar.

### Likelihood Explanation
Reward-funding transactions (`queueNewRewards`/`donateRewards` calls triggered by harvests or bribe distributions) are visible in the public mempool before confirmation, and deposit/withdraw operations have zero cost beyond gas and no time-lock, making this trivially executable by any MEV searcher/bot each time a reward funding transaction is queued. This is a recurring, low-effort, high-frequency attack vector rather than a one-off edge case.

### Recommendation
Implement time-weighted reward streaming (e.g., a `rewardRate` distributed linearly over a fixed duration, as in standard `StakingRewards`/Synthetix patterns) instead of instantly baking the entire `_amountReward` into `rewardPerTokenStored`. Alternatively, introduce a minimum staking duration or withdrawal cooldown/window (as suggested in the referenced report) so that deposits made immediately before a reward-funding event do not qualify for the newly queued rewards.

### Proof of Concept
1. Attacker monitors mempool for a pending transaction that will call `BaseRewardPool.queueNewRewards`/`donateRewards` (e.g., a keeper harvesting WOM rewards through `WombatStaking.harvest()` and forwarding to the rewarder), or a bribe distribution into `BaseRewardPool`.
2. Attacker submits a `WombatPoolHelper.depositLP()`/`deposit()` (or `AnkrBNBPoolHelper.depositLP`) transaction with high gas priority to land immediately before the reward-funding transaction, crediting a large `balanceOf` share via `MasterMagpie._deposit` [6](#0-5) .
3. The reward-funding transaction executes, calling `_provisionReward`, which raises `rewardInfo.rewardPerTokenStored` for the entire pool based on `totalStaked()` including the attacker's inflated deposit [1](#0-0) .
4. Attacker calls `WombatPoolHelper.withdraw()` to remove the deposited LP and calls `getReward()` (via `MasterMagpie.multiclaim`) to claim the proportional share of the newly queued reward, exiting the position in the same or next block with the reward captured and no exposure to prior pool performance.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }

        UserInfo storage user = userInfo[_stakingToken][_account];

        _harvestBaseRewarder(_stakingToken, _account);

            user.available = user.available - _amount;
