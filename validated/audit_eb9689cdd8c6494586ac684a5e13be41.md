## Analog Found

The report's core broken invariant — "ERC-20 `transfer`/`transferFrom` success is assumed, and a `false` return value (rather than a revert) is never checked" — has a direct local analog in `evm/tron/contracts/apps/IntentGatewayV2.sol`, the Tron variant of the Intent Gateway escrow contract.

### Title
Unchecked ERC20/TRC20 return value in escrow `withdraw()` and `SweepDust` allows escrow to be marked released/filled without tokens actually reaching the beneficiary - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` (Tron) imports and enables `SafeERC20` (`using SafeERC20 for IERC20;`) but the actual token-release paths — `withdraw()` and the `SweepDust` branch of `onAccept()` — bypass it. They instead perform a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the *call itself* did not revert (`success`), never decoding/validating the ABI-encoded boolean return value. This is exactly the pattern flagged in the external report: per ERC-20, callers "MUST handle false from returns" and must not assume a token throws on failure.

### Finding Description
In `withdraw()`: [1](#0-0) 
escrowed input tokens are released with:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
and fee redemption: [2](#0-1) 
does the same for the fee token. The `SweepDust` request handler in `onAccept()` repeats this exact unchecked pattern: [3](#0-2) 

Contrast this with the EVM (non-Tron) sibling contracts, which correctly use `safeTransfer`/`safeTransferFrom` throughout (`IntentGatewayV2.sol:219`, `IntentsBase.sol:408,416`), and with the contract's own declaration `using SafeERC20 for IERC20;` at the top of the file — the Tron variant declares the safe wrapper but doesn't apply it on the release path. [4](#0-3) 

The input token for an order is fully attacker/user-controlled at order placement (`address(uint160(uint256(order.inputs[i].token)))`), so a user can escrow any TRC20-compatible token address of their choosing, including one that returns `false` on a failed transfer instead of reverting — a common pattern for non-standard TRC20 tokens on Tron. [5](#0-4) 

`(bool success,)` only reflects whether the low-level call reverted; if the token contract executes normally and simply returns `abi.encode(false)`, `success` is `true` and the check `if (!success) revert TransferFailed();` never fires. Execution then proceeds to decrement `_orders[...]` and, in `withdraw()`, permanently sets `_filled[body.commitment] = beneficiary` and emits `EscrowReleased`/`EscrowRefunded`, finalizing the order.

### Impact Explanation
Because the order is finalized (`_filled` set, escrow balance zeroed) even though the token transfer silently failed, the escrowed funds become permanently stuck in the contract with no beneficiary ever receiving them, and no retry path exists (the order is already marked filled/refunded, so a second `withdraw()` call for the same commitment is not reachable through normal flows). This is a direct loss of funds for the legitimate beneficiary/solver, matching the bounty's "stealing or loss of funds" and "false state acceptance" impact categories — the on-chain escrow state falsely reflects a successful settlement that never occurred.

### Likelihood Explanation
No malicious peer, relayer, prover, or admin is required — this is triggerable by an ordinary unprivileged user who selects an arbitrary/attacker-chosen input token when placing an order (`placeOrder`/`newOrder`), then lets the fill/settlement flow (`onAccept` → `withdraw`) run normally. Any TRC20 token that returns `false` instead of reverting on a failed transfer (out of gas token balance moved elsewhere, blacklist, paused-token semantics, or a deliberately crafted token) triggers the bug deterministically at redemption time. This is a realistic likelihood given Tron's TRC20 ecosystem has multiple tokens with non-standard, non-reverting failure semantics, and given the gateway does not restrict escrowable tokens to an allowlist in the code shown.

### Recommendation
Apply the already-imported `SafeERC20` wrapper consistently: replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `withdraw()` and the `SweepDust` branch of `onAccept()` with `IERC20(token).safeTransfer(beneficiary, amount)` (and `safeTransferFrom` where applicable), mirroring the pattern already used in the non-Tron `IntentGatewayV2.sol` and `IntentsBase.sol`. This ensures a `false` return decodes and reverts the entire settlement rather than silently finalizing escrow state.

### Proof of Concept
1. User deploys/uses a TRC20 token `EvilToken` whose `transfer()` returns `false` (no revert) when, e.g., the sender lacks a required role/allowance state that the user can toggle.
2. User calls the order-placement flow escrowing `EvilToken` as an input asset; `_orders[commitment][EvilToken] = amount` is recorded. [6](#0-5) 
3. A solver fills the order; the cross-chain settlement message triggers `onAccept()` → `withdraw(body, false)` on the escrow side.
4. Prior to the transfer being processed, the user manipulates `EvilToken` state so `transfer()` returns `false` without reverting (e.g., toggling an internal restricted-transfer flag they control).
5. `withdraw()` calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`; the call succeeds (`success == true`) even though the encoded return value is `false`, so no tokens move. [7](#0-6) 
6. `_orders[commitment][EvilToken] -= amount` and `_filled[commitment] = beneficiary` are set, `EscrowReleased` is emitted — the order is permanently finalized as settled while the solver/beneficiary received zero tokens, and the tokens remain locked in the contract with no further redemption path.
