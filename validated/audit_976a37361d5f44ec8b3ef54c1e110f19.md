## Finding [1](#0-0) 

The `pallet-hyper-fungible-token` design is a close local analog of the reported `BitcornOFT`/`SwapFacility` issue: a single fungible asset is escrowed/redeemed across **multiple independent remote counterparties that share one commingled custody pool**, with no per-counterparty partitioning of collateral.

### Title
Single local asset escrowed against multiple independent EVM chain contracts shares one commingled pool, so any one compromised remote counterpart can drain funds legitimately locked by users of other chains - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`register_token` lets one local `AssetId` be paired with **multiple remote `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts across different EVM chains** via `TokenRegistration.chains: BTreeMap<StateMachine, ChainConfig>` [2](#0-1) . All escrow for that asset — regardless of which remote chain the funds came from or will return to — is held in a single shared account, `Pallet::<T>::pallet_account()` [1](#0-0) , with no per-`StateMachine` sub-accounting of how much was escrowed on behalf of each remote chain's users.

### Finding Description
- On `send`, native assets are moved into `Self::pallet_account()` regardless of destination chain [3](#0-2) .
- On `on_accept`, the release/mint back to a beneficiary again draws from — or mints against — the same shared `Pallet::<T>::pallet_account()` balance, keyed only by `local_asset_id`, not by which chain originated the message [4](#0-3) .
- The only per-chain authentication is that the incoming request's `(source, from)` must match a registered `ContractToAsset` entry [5](#0-4) , and the amount is decoded using that chain's `Precisions` entry. There is **no invariant tying total value released for a given source chain back to what was escrowed specifically because of that chain's outbound `send`s.**
- This is architecturally identical to the reported bug: multiple "vaults" (here, multiple EVM chains' paired contracts) back one fungible pool (here, the local escrowed balance of a single `AssetId`), and redemption from any one paired chain draws indiscriminately from the shared pool built up by all other paired chains.

### Impact Explanation
If any one of the paired EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts on a given chain is compromised, buggy, or its collateral otherwise loses integrity (e.g., an exploit lets an attacker mint that chain's wrapped representation without a genuine backing lock), the attacker can bridge that illegitimately-minted amount back to the substrate side. `on_accept` will release real escrowed collateral from the single shared `pallet_account()` [4](#0-3) , up to draining the entire pool — including the portion that was honestly escrowed by users who transacted only through a different, uncompromised chain. This is a direct "loss of funds to the wrong beneficiary" scenario: honest users on Chain B lose their redemption claim because Chain A's counterpart was exploited, exactly mirroring `bBTC` depositors losing collateral because `aBTC`'s `SwapFacility` was drained.

### Likelihood Explanation
Any operator that registers one local asset against more than one EVM chain (a normal, encouraged multi-chain configuration per the `chains` map in `TokenRegistration`) is exposed. No governance or malicious-relayer assumption is required — the only precondition is that one of the N paired remote contracts has an exploitable bug or degrades in integrity, which is exactly the risk class the original report calls out for the multi-`SwapFacility` design.

### Recommendation
Track escrowed balances per `(AssetId, StateMachine)` pair rather than one blended `pallet_account()` total per asset, and cap `on_accept` releases for a given source chain to the cumulative amount actually escrowed via `send` to that specific chain. Alternatively, use per-chain sub-accounts (e.g., derive `pallet_account()` from `(PALLET_ID, StateMachine)`), so a compromise or over-mint on one paired chain cannot draw down collateral that other chains' users are relying on.

### Proof of Concept
1. Operator calls `register_token` for local asset `X` with `chains = {Evm(A): ChainConfigA, Evm(B): ChainConfigB}` [6](#0-5) .
2. Honest user on Chain B calls `send(asset_id=X, destination=Evm(B), amount=1000)`; `1000 X` moves into `Self::pallet_account()` [7](#0-6) .
3. Chain A's `HyperFungibleToken` contract has (or later develops) a bug/exploit letting an attacker mint `1000` units of the Chain-A wrapped representation of `X` without ever locking/burning anything real.
4. Attacker bridges those `1000` units from Chain A back to substrate. `on_accept` verifies only `(source=Evm(A), from=chainA_contract)` maps to asset `X` via `ContractToAsset` [5](#0-4)  and then transfers `1000 X` out of the single shared `pallet_account()` to the attacker [8](#0-7) .
5. The pool is now empty; the honest Chain-B user's escrowed `1000 X` deposit from step 2 is unrecoverable — drained via a different chain's compromised counterpart, with no code path detecting or preventing the cross-chain draw-down.

		/// Registers a new token with per-chain contract configuration
		#[pallet::call_index(1)]
		#[pallet::weight(T::WeightInfo::register_token(registration.chains.len() as u32))]
		pub fn register_token(
			origin: OriginFor<T>,
			registration: TokenRegistration<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if registration.local_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					registration.local_id.clone(),
				)
			};

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}
