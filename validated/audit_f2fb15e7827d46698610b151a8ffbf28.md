## Title
Mainnet `reject_unstable_bytecode`/`reject_unstable_bytecode_for_script` gate is bypassed when the `compilation_metadata` entry is stripped or never embedded, allowing unstable-compiled bytecode to be published/executed on mainnet - (File: aptos-move/aptos-vm/src/aptos_vm.rs)

## Summary
`AptosVM::reject_unstable_bytecode` and `reject_unstable_bytecode_for_script` are the only checks that prevent bytecode compiled with unstable compiler/language versions from being published or executed on mainnet. Both functions only inspect `metadata.unstable` when `get_compilation_metadata()` returns `Some(...)`. If the `Metadata` entry keyed `COMPILATION_METADATA_KEY` is absent from the submitted module/script bytes, the check silently passes (`Ok(())`), regardless of how the bytecode was actually compiled.

## Finding Description
`reject_unstable_bytecode` in [1](#0-0)  only enters the rejecting branch `if let Some(metadata) = get_compilation_metadata(module)`. The same pattern is used for scripts in [2](#0-1) . `get_compilation_metadata` simply looks for a `Metadata` entry with key `COMPILATION_METADATA_KEY` in the module's/script's self-declared `metadata` vector and deserializes it if found, returning `None` otherwise: [3](#0-2) .

Crucially, this `metadata` vector is part of the raw `CompiledModule`/`CompiledScript` bytes that the publisher submits in the transaction payload — it is not independently derived or verified by the VM from the actual bytecode content. The official compiler pipeline (`move-compiler-v2`) inserts the `CompilationMetadata` entry automatically at code-generation time based on the compiler/language version used [4](#0-3) , but nothing prevents a publisher from taking the compiled bytes and removing that specific `Metadata` entry (or constructing the bytecode via any other path that never adds it) before submitting the publish transaction.

The only structural check on the `metadata` vector, `check_metadata_format`, enforces that keys are one of the known keys and that there are no duplicates, and that if a `COMPILATION_METADATA_KEY` entry exists it deserializes correctly — but it does not require such an entry to be present: [5](#0-4) . This is consistent with the CLI's own fallback logic, which explicitly assumes missing compilation metadata is a legitimate ("legacy") case rather than an error: [6](#0-5) .

The existing e2e tests only exercise the case where the metadata is present and either `unstable: true` or `unstable: false`; there is no test asserting behavior when the entry is entirely absent while the underlying bytecode was actually produced with `CompilerVersion::latest()`/unstable language version: [7](#0-6) .

## Impact Explanation
`reject_unstable_bytecode` is called from `validate_publish_request`, the gate for all module publish and upgrade paths [8](#0-7) , and `reject_unstable_bytecode_for_script` gates script execution [9](#0-8) . Since the flag is entirely attacker-controlled metadata bundled inside the submitted bytecode blob rather than something independently derived from the bytecode's actual provenance, any unprivileged publisher can compile code with `CompilerVersion::latest()` / unstable `LanguageVersion`, strip the `compilation_metadata` entry, and publish to mainnet as if it were stable. This defeats the intended invariant "only stable-compiled bytecode reaches mainnet," which exists specifically because unstable compiler/language versions may not have received the same level of security/soundness scrutiny as stable releases.

## Likelihood Explanation
High feasibility for anyone able to construct raw module bytes (any developer using the Move bytecode APIs directly, bypassing the standard `aptos move publish` CLI flow) — no privileged access, ownership, or special conditions are required. The check purely trusts self-declared metadata bytes that travel with the publisher-supplied payload.

## Recommendation
Do not treat absence of `compilation_metadata` as "assumed stable." On mainnet, either:
- Require modules/scripts to carry a valid `compilation_metadata` entry and reject publish/execution if it is missing, or
- Independently determine "unstable" status from properties of the bytecode itself (e.g., minimum/maximum file-format version, and per-feature bytecode-level checks already present for specific new instructions/features), rather than from self-declared, publisher-controlled metadata.

## Proof of Concept
1. Build a Move package with `BuildOptions { compiler_version: Some(CompilerVersion::latest()), ... }` so the compiler embeds `CompilationMetadata { unstable: true, .. }` (mirrors `test_compilation_metadata_internal` with `unstable_flag = true`) — see the test harness at [10](#0-9) .
2. Deserialize the resulting module bytes with `CompiledModule::deserialize`, remove the `Metadata` entry whose `key == COMPILATION_METADATA_KEY`, and re-serialize (mirrors the mutation pattern already used in `test_compilation_metadata_with_changes`, but deleting instead of duplicating) [11](#0-10) .
3. Set the chain resource to mainnet (`ChainId::mainnet()`), and submit `aptos_stdlib::code_publish_package_txn` with the mutated bytes, as done via `h.run_transaction_payload_mainnet` in the existing tests [12](#0-11) .
4. Assert the transaction status is success (not `StatusCode::UNSTABLE_BYTECODE_REJECTED`), confirming the mainnet gate in `reject_unstable_bytecode` was bypassed [13](#0-12) .

    /// Check whether the bytecode can be published to mainnet based on the unstable tag in the metadata
    fn reject_unstable_bytecode(&self, modules: &[CompiledModule]) -> VMResult<()> {
        if self.chain_id().is_mainnet() {
            for module in modules {
                if let Some(metadata) = get_compilation_metadata(module) {
                    if metadata.unstable {
                        return Err(PartialVMError::new(StatusCode::UNSTABLE_BYTECODE_REJECTED)
                            .with_message(
                                "code marked unstable is not published on mainnet".to_string(),
                            )
                            .finish(Location::Undefined));
                    }
                }
            }
        }
        Ok(())
    }

/// Check if the metadata has unknown key/data types
fn check_metadata_format(module: &CompiledModule) -> Result<(), MalformedError> {
    let mut exist = false;
    let mut compilation_key_exist = false;
    for data in module.metadata.iter() {
        if data.key == *APTOS_METADATA_KEY || data.key == *APTOS_METADATA_KEY_V1 {
            if exist {
                return Err(MalformedError::DuplicateKey);
            }
            exist = true;

            if data.key == *APTOS_METADATA_KEY {
                bcs::from_bytes::<RuntimeModuleMetadata>(&data.value)
                    .map_err(|e| MalformedError::DeserializedError(data.key.clone(), e))?;
            } else if data.key == *APTOS_METADATA_KEY_V1 {
                bcs::from_bytes::<RuntimeModuleMetadataV1>(&data.value)
                    .map_err(|e| MalformedError::DeserializedError(data.key.clone(), e))?;
            }
        } else if data.key == *COMPILATION_METADATA_KEY {
            if compilation_key_exist {
                return Err(MalformedError::DuplicateKey);
            }
            compilation_key_exist = true;
            bcs::from_bytes::<CompilationMetadata>(&data.value)
                .map_err(|e| MalformedError::DeserializedError(data.key.clone(), e))?;
        } else {
            return Err(MalformedError::UnknownKey(data.key.clone()));
        }
    }

    Ok(())
}
