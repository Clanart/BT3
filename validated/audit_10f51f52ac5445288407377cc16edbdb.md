### Title
Silent, unauthenticated auto-rewrite of a repository's git remote URL from GitHub API data enables repo-swap "remote hijack" - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` automatically rewrites the local `origin` remote's URL whenever the cached `GitHubRepository.cloneURL` matches the *current* local remote, the URL scheme (protocol) matches, and the newly-fetched API `clone_url` differs. This mirrors the oracle report's broken invariant: a trusted external value (there, a Chainlink price feed address; here, a GitHub API `clone_url`) is consumed and used to overwrite a security‑relevant local value with **no mechanism to independently verify the referenced object's identity** (no immutable repository ID check) and no way for the user to review/reject the change before it silently takes effect.

### Finding Description
`updateRemoteUrl` is invoked from `app-store.ts` whenever Desktop refreshes GitHub repository metadata from the API. It only checks:
- that the local remote's protocol matches the new `clone_url`'s protocol,
- that the local remote still equals the previously cached `gitHubRepository.cloneURL`,
- that the new `clone_url` differs from the current remote URL,

then calls `gitStore.setRemoteURL(...)` to rewrite `origin` to the API-provided `clone_url`, with no user prompt: [1](#0-0) 

Matching is purely by owner/name string comparison via `urlMatchesRemote`/`parseRemote`, not by the GitHub repository's immutable numeric ID: [2](#0-1) 

If an owner deletes a GitHub repository (or renames it and abandons the old name) and an attacker subsequently creates a new repository at the same `owner/name`, the next time Desktop refreshes the GitHub repository info for a user who still has the old repo open locally, the API's `clone_url` for that owner/name will resolve to the attacker's repository. Because the check only compares owner/name strings (not repository ID) and only guards protocol equality, Desktop will silently call `setRemoteURL` and repoint the local `origin` remote at the attacker-controlled repository — with no user confirmation dialog.

### Impact Explanation
Once `origin` is silently repointed to an attacker's repository:
- Future `git push` operations from the user (who believes they're pushing to their known repository) send code/history to the attacker's remote, potentially leaking private code/commits.
- Future `git fetch`/`pull` operations pull attacker-controlled refs/objects into the user's working repository, which can plant malicious commits, hooks, or files that get merged into the user's tree — corrupting what the user believes they are committing/reviewing.
- Desktop's own PR/branch UI, which trusts `gitStore.defaultRemote`, would then interact with the attacker's repository (e.g., fetching "PR" branches) without any indicator to the user that the remote identity changed.

This matches the required impact class: an attacker who controls a GitHub API object (a re-created repository at a previously-used owner/name) can cause silent corruption of what the user pushes/fetches, without any local access, admin rights, or social engineering step beyond the pre-existing act of opening/using a repository that later becomes rename/delete-and-recreate eligible on GitHub.

### Likelihood Explanation
The scenario ("dangling repository slot re-registered by an attacker," i.e., classic GitHub repo-jacking) is a well known, externally-observed attack pattern (used against orgs whose repos moved/were deleted). The vulnerable code path executes automatically as part of routine background refresh of GitHub repository metadata — it requires no unusual user action, just that the user has a repository open in Desktop whose upstream identity later gets reused by an attacker. The existing guard (`protocolsMatch` + owner/name string match) does not stop this because the attacker's newly created repo will naturally have the same owner/name and the same (https) protocol as the original — the very information being validated is exactly what an attacker controls when re-registering the name.

### Recommendation
Before calling `setRemoteURL`, verify the API-returned repository against an immutable identity captured at the time Desktop first associated with it (e.g., the GitHub repository's numeric `id`/`node_id`), not just owner/name path matching. If the ID does not match the previously stored `GitHubRepository.dbID`/API id, treat the repository as a different object and do **not** auto-update the remote; instead, surface a warning to the user (similar to how GitHub.com detects and warns about renamed/moved repositories) so they can decide whether to update the remote manually.

### Proof of Concept
1. User clones `https://github.com/some-org/some-repo` in Desktop; Desktop caches the associated `GitHubRepository` with `cloneURL` = that URL.
2. `some-org` deletes `some-repo` (or renames it away).
3. An attacker creates a new repository `some-org/some-repo` (assuming `some-org` allows it, e.g., an org that permits arbitrary repo creation, or via a similarly-named personal account scenario) with malicious content.
4. On the victim's next background repository-info refresh, the API call underlying `fetchRepository`/`fetchRepositoryCloneInfo` returns the attacker's repo's `clone_url` for `some-org/some-repo`: [3](#0-2) 
5. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (cached clone URL still equals current remote), `urlsMatch === false` (new clone_url differs from old, but owner/name path is identical) and calls `gitStore.setRemoteURL(...)`, repointing `origin` to the attacker's clone URL: [4](#0-3) 
6. The user's next `git push`/`git fetch` silently interacts with the attacker's repository instead of the one they originally cloned.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
