### Title
Unchecked caller-supplied `change` address in `SignableTransaction::new` lets a transaction proposer steal the change output - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts an arbitrary `change: Option<ScriptBuf>` parameter and appends an output paying all leftover input value to that script [1](#0-0) . When the transaction is later signed through `TransactionMachine`, the signing machines only verify that each *input's* script matches the offset group key — no check exists that the change script is controlled by the threshold group [2](#0-1) . This mirrors the `PerpDepository.rebalance()` bug class: a caller-controlled address receives the residual funds, with no protocol-side enforcement.

### Finding Description
In `multisig()`, each signer checks `p2tr_script_buf(offset.group_key()) == self.prevouts[i].script_pubkey` for inputs only [3](#0-2) . `sign()` then produces signature shares over the taproot sighash of the stored transaction, including whatever outputs the proposer embedded [4](#0-3) . An unprivileged proposer who submits a `SignableTransaction` for signing can set `change` to a script they control; any excess `input_sat - payment_sat - fee_with_change` ≥ `DUST` is routed to them [5](#0-4) . The honest protocol flow always derives change from a group-key offset (`OutputType::Change` via `scanner()`), confirming the intended invariant that change belongs to the group [6](#0-5)  — but nothing in the wallet signing path enforces it.

### Impact Explanation
A malicious proposer crafts a `SignableTransaction` where `payments` deliberately under-spend the inputs (or where the proposer simply controls the change field), and the leftover — potentially the bulk of the input value — is paid to an attacker script. Once `t` signers complete `TransactionSignatureMachine::complete`, the signed transaction is valid and irreversible [7](#0-6) . Additionally, since `needed_fee` is recomputed with the change output, a proposer can inflate/redirect the difference between `needed_fee` and actual fee. This is signing of an unintended message: signers authorize a transfer they never vetted.

### Likelihood Explanation
Any party able to submit a `SignableTransaction` (or serialized `ReceivedOutput`s plus outputs) into the signing flow controls `change`. Honest signers' machines give no warning — `sign()` panics only on a non-empty `msg`, not on untrusted output scripts [8](#0-7) . Exploitation requires only that signers rely on the machine rather than manually auditing `tx.transaction()` outputs, which the API design encourages since `multisig` performs validation that implicitly appears complete. Rated Medium: theft is bounded to residual change per transaction and requires a proposer position in the signing flow.

### Recommendation
Have `multisig()` (or `TransactionMachine::sign`) verify that every output is either an expected payment or a change script derived from the group key — e.g., require `change` to equal `p2tr_script_buf(group_key + G * change_offset)` for a registered/committed offset, matching the `OutputType::Change` derivation in the processor. Alternatively, have signers reject transactions whose change script does not scan under the group's `Scanner`.

### Proof of Concept
```rust
// Attacker (proposer) with their own key pair:
let attacker_key = ProjectivePoint::random(&mut OsRng);
let attacker_addr = p2tr_script_buf(attacker_key).unwrap();

// Honest inputs paying to the group key, but change set to attacker:
let tx = SignableTransaction::new(
  vec![group_output],           // ReceivedOutput owned by group key
  &[(payment_addr, 1000)],      // small payment; most value left over
  Some(attacker_addr),          // <-- unchecked beneficiary
  None,
  FEE,
).unwrap();

// Each honest signer runs:
let machine = tx.clone().multisig(&keys[&i]).unwrap(); // succeeds: inputs check out
// ... FROST preprocess/sign/complete ...
// Result: tx.output[last] pays ~all excess to attacker_addr; signature is valid.
```
The signers' verification in `multisig` (lines 275–279) covers only `prevouts`, so the malicious change output is signed without objection.
