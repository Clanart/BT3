## Title
Unrestricted `purchase()` lets any caller evict another app's paid bandwidth subscriptions via the FIFO 1024-cap - ([File: modules/pallets/bandwidth/src/lib.rs])

## Summary
`pallet_bandwidth::push_subscription` unconditionally evicts the oldest entry in an `(app_chain, app)` `SubscriptionList` once it hits the 1024-entry cap, and `BandwidthManager.purchase()` on the EVM side lets **any address** target **any `app`/`chain` pair** with no ownership check. This mirrors the M‑6 pattern: an actor with no legitimate stake in a specific accounted resource can nonetheless mutate the shared counter/queue that gates it, destroying value that belongs to someone else.

## Finding Description
`purchase()` in `evm/src/apps/BandwidthManager.sol` only validates that `app`/`chain` are non-empty and that the tier is priced — it never checks that `msg.sender` owns or is authorized for `app`: [1](#0-0) 

The dispatched `BandwidthPurchaseMsg` is handled by `on_accept` in `modules/pallets/bandwidth/src/lib.rs`, which only checks that the *sender chain's registered manager* sent it — again nothing ties the purchase to who owns `app`: [2](#0-1) 

Every accepted purchase calls `push_subscription`, which appends to a `BoundedVec` capped at `MAX_SUBSCRIPTIONS = 1024`. When the cap is hit, it unconditionally removes index `0` (the oldest entry) regardless of whether that entry still has `remaining_bytes` un-consumed: [3](#0-2) 

Critically, `push_subscription` never sweeps expired entries before checking capacity — only the consumption path (`try_consume`, invoked by the gate on message delivery) does that: [4](#0-3) 

So a low-traffic app's queue can accumulate many already-expired-but-unswept rows, meaning an attacker doesn't even need 1024 real purchases to force an eviction of a live entry — just enough to top off whatever slack remains before the cap. Since `app` is attacker-chosen bytes with no ownership binding, anyone can target a specific victim `(app_chain, app)` key and drive `list.len()` to 1024, then push one more cheap purchase to evict the oldest (often the victim's still-unconsumed, previously paid) subscription. The eviction is logged (`SubscriptionEvicted`) but is irreversible — there is no refund path anywhere in the pallet or the EVM contract.

This is structurally the same broken invariant as the reported bug: a party not entitled to influence a specific victim's accounting (the inactive vault reporting into `underlyingReceived`; here, an unrelated purchaser writing into a victim app's `Allowance` list) is permitted by a public, unauthenticated entrypoint to corrupt/erase state that gates another party's legitimate resource, with no owner check and no way to reverse the damage.

## Impact Explanation
The victim app irrecoverably loses bandwidth it already paid for (`lost_bytes` in `SubscriptionEvicted`), and its subsequent legitimate ISMP messages are rejected by `BandwidthGate::try_consume` (`GateError::NoAllowance`/`Insufficient`) even though it paid for a live, unexpired allowance. This is a direct loss-of-funds event (the paid-for bytes are destroyed with no refund) reachable by any unprivileged caller through the public `purchase()` entrypoint — it requires no malicious relayer, prover, admin, or governance actor, satisfying the bounty's "stealing or loss of funds" / "logic attack" categories.

## Likelihood Explanation
The attack requires only calling a public, permissionless function (`purchase()`) repeatedly for a chosen `(app, chain)` key, paying the lowest configured tier price per call. Cost scales with however many pushes are needed to reach the 1024 cap while the victim's target entry is still at the head — cheaper still if the victim's queue already contains stale/expired-but-unswept rows (which is expected for any app that doesn't dispatch messages frequently enough to trigger sweeps). No race with relayers, provers, or governance timing is needed.

## Recommendation
- Bind purchases to an authenticated owner of `app` (e.g. require the purchase to originate from the app contract itself, or maintain a per-app allow/owner mapping validated in `on_accept`), or
- Sweep expired subscriptions before applying the capacity check in `push_subscription` (mirroring the `try_consume` sweep), and/or refuse to evict an entry that still has non-zero `remaining_bytes` and has not expired — instead reject the purchase or raise the cap dynamically, and
- Consider rate-limiting/costing evictions proportionally to the bytes being destroyed so griefing a large paid subscription is economically irrational.

## Proof of Concept
1. Victim (owner of `app` on `app_chain`) legitimately calls `BandwidthManager.purchase(app, TierFour, 1, app_chain)`, crediting a large, long-lived `Subscription` at the head of `Allowance[app_chain][app]`.
2. Attacker, with no relationship to `app`, repeatedly calls `purchase(app, TierOne, 1, app_chain)` (cheapest tier) targeting the same `app`/`app_chain` pair. Each call succeeds because `purchase()`/`on_accept` never check who owns `app` — see `evm/src/apps/BandwidthManager.sol:148-163` and `modules/pallets/bandwidth/src/lib.rs:455-477`.
3. Once `Allowance[app_chain][app].len() == MAX_SUBSCRIPTIONS (1024)` — cheaply achievable if some slots are already stale/expired-but-unswept — the attacker's next purchase triggers `push_subscription`'s eviction branch, removing index `0` (the victim's still-live TierFour subscription) and emitting `SubscriptionEvicted { lost_bytes: <victim's remaining_bytes> }` (`modules/pallets/bandwidth/src/lib.rs:416-425`).
4. The victim's app now has its paid allowance destroyed with no refund mechanism; its next dispatch is rejected by `BandwidthGate::try_consume` with `NoAllowance`/`Insufficient` (`modules/pallets/bandwidth/src/lib.rs:509-555`), despite having paid for bandwidth that had not expired.

			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
