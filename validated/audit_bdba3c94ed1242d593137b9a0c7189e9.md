### Title
Unauthenticated Payout Attribution via Unsigned OP_RETURN Lets Anyone Credit an Arbitrary Operator for a Payout It Never Fronted - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `payout_tx` that attributes which operator "fronted" a Citrea withdrawal is only ever authorized by the withdrawing user's `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` signature over input 0 and output 0 (the user's payout). The transaction's OP_RETURN output, which the whole reimbursement/attribution pipeline treats as ground truth for "who paid," is never covered by that signature (nor by any other signature), so anyone who observes the pending payout transaction in the mempool can rebroadcast a fee-bumped variant that pays the user identically but embeds a different operator's x-only public key in the OP_RETURN. This breaks the binding "operator credited == party that actually paid."

### Finding Description
`create_payout_txhandler` builds the payout transaction with a single signed input (the user's withdrawal UTXO, signed off-chain by the user) and three outputs: the user's payout (`output_txout`), an anchor for CPFP, and an OP_RETURN carrying `operator_xonly_pk`: [1](#0-0) 

The witness is only set for input 0 with the user's signature: [2](#0-1) 

The registered withdrawal signature is generated with `SinglePlusAnyoneCanPay`, which per BIP-143 only commits the signer to *input 0* and *its corresponding output 0*; every other output (the anchor and, critically, the OP_RETURN containing the operator's identity) is unconstrained and can be freely substituted by anyone who can observe the input+witness pair, e.g., from the operator's own broadcast in the mempool: [3](#0-2) 

Downstream, the verifier's block-sync logic derives the "payer" of a withdrawal purely by parsing whatever bytes are present in the confirmed transaction's OP_RETURN — with no signature check that the embedded key belongs to whoever actually constructed/funded the transaction: [4](#0-3) 

This value is persisted directly into `withdrawals.payout_payer_operator_xonly_pk`: [5](#0-4) 

That column then drives two critical, automated consequences:

1. `PayoutCheckerTask` polls for unhandled payouts *by this operator's own xonly_pk* and, once found, automatically triggers `handle_finalized_payout`, which schedules the credited operator's own round/kickoff flow to reimburse itself: [6](#0-5) 

2. `validate_payer_is_operator` (used by manual/no-automation reimbursement via `get_reimbursement_txs`) only checks that the stored payer key equals `self.signer.xonly_public_key` — it has no way to verify that the credited operator actually authorized or funded the specific payout transaction that produced this attribution: [7](#0-6) 

3. `is_kickoff_malicious` cross-checks the stored `payout_payer_operator_xonly_pk` against the `kickoff_data.operator_xonly_pk` of whoever starts the kickoff — but since the OP_RETURN value is attacker-controlled at the payout-transaction level, this check can be satisfied by matching whatever value the attacker chose to plant: [8](#0-7) 

Because none of these checks verify a signature binding the OP_RETURN operator identity to the actual constructor/broadcaster of the payout transaction, the equality the protocol relies on — `payout_payer_operator_xonly_pk == operator that actually fronted the withdrawal` — does not hold. An unprivileged party who sees a pending payout transaction (any legitimate operator's fronted payout, visible in the mempool before confirmation) can construct a conflicting transaction that:
- spends the same input (the user's withdrawal UTXO),
- reproduces the exact same output 0 (still valid under the user's `SIGHASH_SINGLE|ANYONECANPAY` signature, since that output is unchanged),
- but replaces the anchor amount (to win the fee race / RBF) and the OP_RETURN payload with an arbitrary x-only public key of the attacker's choosing (e.g., a real, unrelated registered operator's public key, which is public information),

and broadcasts it with a higher fee so it confirms instead of the legitimate broadcaster's version.

### Impact Explanation
This crosses the "operator credited versus the party that paid" custody-attribution boundary explicitly called out as in-scope. Concretely:
- An attacker can force an arbitrary, uninvolved operator to be recorded as the "payer" of a withdrawal it never chose to front, never signed for, and never funded. `PayoutCheckerTask`'s automation will then automatically drive that operator's kickoff/reimbursement machinery for a payout it did not evaluate for profitability (the `is_profitable` check in `Operator::withdraw` is bypassed entirely, since the credited operator never called `withdraw`).
- Because the reimbursement pipeline (`send_asserts`, `get_next_txs_to_send`, `validate_payer_is_operator`) is keyed off this unauthenticated attribution, an operator can be made to consume its own round/kickoff connector for a payout transaction it never authorized, misusing its collateral/round slot cycle, or made to unknowingly enter the on-chain kickoff process for a withdrawal it never intended to service.
- The actual legitimate operator that funded and broadcast the transaction (paid the broadcasting/relay/CPFP fees) can be denied credit for the payout it fronted if its transaction loses the fee race, since the DB attribution is derived only from whichever version of the transaction is ultimately confirmed.

This matches the Critical impact "an operator reimbursed for a payout it never funded" / "an honest operator permanently unable to be reimbursed" categories, since attribution — not actual signed authorization — decides who is obligated/entitled in the reimbursement flow.

### Likelihood Explanation
The only capability required is observing a pending payout transaction in the Bitcoin mempool (an inherently public event once any operator broadcasts it via `TxSender`) and being able to fee-bump a conflicting transaction that reuses the same input and identical output 0 — something any Bitcoin participant with funds for fees can do, without any protocol role, key, or verifier/operator/watchtower privilege. The relevant signature (`SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`) is by design permissive of exactly this kind of output substitution outside the committed output index.

### Recommendation
Bind the operator identity cryptographically to the payout transaction rather than trusting an unsigned OP_RETURN:
- Require the operator to sign (e.g., with their own xonly key, covering all outputs) the specific `operator_xonly_pk` value embedded in the payout transaction, and have `update_finalized_payouts` verify this signature before recording `payout_payer_operator_xonly_pk`.
- Alternatively, commit the OP_RETURN operator pubkey inside the sighash covered by the user's signature (e.g., using `SIGHASH_ALL` or otherwise covering all outputs), so a third party cannot alter attribution without invalidating the withdrawal signature.
- As a defense-in-depth measure, cross-check that the confirming transaction was originally queued/signed by the credited operator's own `TxSender` instance (e.g., via a locally-tracked txid-to-operator mapping) rather than trusting on-chain OP_RETURN content alone.

### Proof of Concept
1. Operator `H` (honest) receives a valid user withdrawal signature via `withdraw()`, builds a `payout_tx` via `create_payout_txhandler` embedding `H`'s xonly pk in the OP_RETURN, and broadcasts it through `TxSender` (unconfirmed in mempool).
2. Attacker `A` (no protocol role) observes this unconfirmed transaction, extracts `input_utxo` and the user's `taproot::Signature` witness from it.
3. `A` constructs a new transaction:
   - Same input (`input_utxo.outpoint`) and witness (still valid for output 0 since it is `SIGHASH_SINGLE|ANYONECANPAY`).
   - Identical output 0 (`output_txout` — user's payout, unchanged so the signature remains valid).
   - Modified anchor output value (higher fee) and OP_RETURN payload containing an arbitrary registered operator `V`'s public xonly key (public knowledge from `fetch_operator_keys`), per `op_return_txout` construction in `create_payout_txhandler`.
4. `A` broadcasts this transaction with a fee high enough to be mined ahead of `H`'s original broadcast.
5. Once confirmed, `update_finalized_payouts` parses the OP_RETURN of the *attacker's* version and stores `payout_payer_operator_xonly_pk = V` in the `withdrawals` table (`core/src/verifier.rs:2319-2350`, `core/src/database/verifier.rs:198-251`), even though `V` never constructed, signed, or broadcast any transaction for this withdrawal.
6. `PayoutCheckerTask` running for operator `V` subsequently picks up this "unhandled payout" (`get_first_unhandled_payout_by_operator_xonly_pk` keyed on `V`'s xonly pk) and automatically drives `V`'s kickoff/reimbursement flow for a payout `V` never funded or approved.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
