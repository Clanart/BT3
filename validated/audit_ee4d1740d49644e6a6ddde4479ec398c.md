Audit Report

## Title
Vote account VAT burn can panic the validator because vote-account balance is not re-validated between admission filtering and the burn - (File: `runtime/src/bank.rs`)

## Summary
`Bank::maybe_burn_vat_from_staked_accounts` performs an unchecked `.expect()`-guarded `checked_sub(vat_to_burn_per_epoch)` on each admitted vote account's lamport balance, relying solely on the earlier `clone_and_filter_for_vat` admission check rather than re-validating the balance at burn time. <cite repo="Kirstentat/agave--040" path="runtime/src/bank.rs" start="2644-2677" /> However, whether an unprivileged withdrawer can actually shrink the balance below `vat_to_burn_per_epoch` in the window between admission and burn is not established by the evidence gathered.

## Finding Description
`maybe_burn_vat_from_staked_accounts` iterates `epoch_stakes.stakes().vote_accounts()` and does:
```rust
account.lamports().checked_sub(vat_to_burn_per_epoch).expect("Vote accounts should have already been filtered...")
``` [1](#0-0) 

The admission filter `clone_and_filter_for_vat` requires `vote_account.lamports() >= minimum_vote_account_balance`, and `Bank::minimum_vote_account_balance_for_vat` explicitly sets that minimum to `vote_account_rent_exempt_minimum + vat_to_burn_per_epoch()` whenever `alpenglow` is active. [2](#0-1) [3](#0-2) 

This means the admission threshold is always at least `rent_exempt_minimum + vat_to_burn_per_epoch`, i.e., there is built-in headroom of `vat_to_burn_per_epoch` above rent-exemption baked into the admission check itself. The vote program's `withdraw` instruction, in the non-closing branch, enforces `remaining_balance >= min_rent_exempt_balance + pending_delegator_rewards` — it does **not** enforce the higher `vat_to_burn_per_epoch`-inclusive threshold. [4](#0-3)  So an authorized withdrawer could, after admission, withdraw down to just `rent_exempt_minimum`, which is below the admission threshold but still `>= 0` and thus would not, by itself, trigger the `.expect()` panic since `rent_exempt_minimum` for a `VoteStateV4` account is typically far larger than any single `vat_to_burn_per_epoch` value — the panic only occurs if the balance drops **below** `vat_to_burn_per_epoch`, which for a partial withdrawal down to the rent-exempt floor would not happen.

The more concrete path to a balance below `vat_to_burn_per_epoch` is the account-closing branch of `withdraw`, which allows draining the account entirely to a `remaining_balance == 0` (subject to `pending_delegator_rewards == 0` and the vote account not having received credits within the last 2 epochs). [5](#0-4)  If such a full closure happens between the time the epoch's admitted vote-account set is computed (`clone_and_filter_for_vat`, called from `compute_new_epoch_caches_and_rewards`) [6](#0-5)  and the time `maybe_burn_vat_from_staked_accounts` actually executes against `epoch_stakes`, the account's lamports could be `0 < vat_to_burn_per_epoch`, causing the `.expect()` to panic.

**What could not be verified:** I was unable to confirm, within the available tooling, (a) the exact call site and timing of `maybe_burn_vat_from_staked_accounts` relative to `compute_new_epoch_caches_and_rewards`/epoch-stakes construction, (b) whether `epoch_stakes` used by the burn function is captured/frozen strictly at epoch-boundary processing such that no interleaving user transaction (including a withdraw) can execute against the *same* vote accounts before the burn consumes the snapshot, and (c) whether the "reject_active_vote_account_close" gate (any account credited within the last 2 epochs cannot be closed) effectively excludes exactly those Alpenglow-participating admitted accounts (which by definition are actively voting, since `has_bls` + `has_stake` filtering in `clone_and_filter_for_vat` correlates with active participation) from ever reaching zero balance in practice. If actively-voting admitted accounts are always blocked from full closure by `reject_active_vote_account_close`, then the panic path described may not be reachable under realistic conditions, which would materially undercut the claim's likelihood.

## Impact Explanation
If reachable, an `.expect()` panic inside deterministic epoch-boundary bank processing (`maybe_burn_vat_from_staked_accounts`) executed identically by every validator would indeed constitute a network-wide consensus/liveness halt rather than a single-node crash, matching the "cause consensus halt" impact bucket, since it is core bank-processing code, not privileged or plugin code. [7](#0-6) 

## Likelihood Explanation
The likelihood is uncertain and cannot be confirmed as "narrow but realistic" without further investigation. The straightforward partial-withdraw path (withdrawing down toward `rent_exempt_minimum`) does not by itself drop the balance below `vat_to_burn_per_epoch`, since the admission threshold already reserves that headroom above rent-exemption. The only path that plausibly reaches balance `< vat_to_burn_per_epoch` is full account closure via `withdraw`'s zero-balance branch, which is gated by `reject_active_vote_account_close` — a check tied to recent voting activity that likely conflicts with the account having been recently admitted into the Alpenglow vote-account set via `clone_and_filter_for_vat` (which itself requires active BLS participation and stake). This tension was not resolved in this investigation. [8](#0-7) [9](#0-8) 

## Recommendation
Regardless of the exact reachability determination, defensive coding is warranted: `maybe_burn_vat_from_staked_accounts` should not `.expect()` on a value computed from stale filtering, but should instead re-check the current balance at burn time (e.g., `saturating_sub` combined with skipping/logging accounts that no longer qualify, rather than panicking the whole bank).

## Proof of Concept
Not confirmed. Reaching a definitive reproduction requires access to the exact call sequencing of `compute_new_epoch_caches_and_rewards` and `maybe_burn_vat_from_staked_accounts` (call site not found via search tools), and building/running `runtime/src/bank/tests.rs` VAT-related tests to determine whether a `Withdraw` instruction can be interleaved against an admitted vote account before the burn executes, and whether `reject_active_vote_account_close` prevents the zero-balance path for actively-participating admitted accounts. This would require a Devin session with full build/test access to the repository, since the index used here does not expose the complete call graph needed to confirm exploitability.

    pub fn clone_and_filter_for_vat(
        &self,
        max_vote_accounts: usize,
        minimum_vote_account_balance: u64,
    ) -> VoteAccounts {
        assert!(max_vote_accounts > 0, "max_vote_accounts must be > 0");
        let capacity = max_vote_accounts.min(self.vote_accounts.len());
        let mut entries_to_sort: Vec<(&Pubkey, &VoteAccount, u64)> = Vec::with_capacity(capacity);
        for (pubkey, (stake, vote_account)) in self.vote_accounts.iter() {
            let has_bls = vote_account
                .vote_state_view()
                .bls_pubkey_compressed()
                .is_some();
            let has_stake = *stake != 0u64;
            let has_balance = vote_account.lamports() >= minimum_vote_account_balance;

            if !has_bls || !has_stake || !has_balance {
                continue;
            }
            entries_to_sort.push((pubkey, vote_account, *stake));
