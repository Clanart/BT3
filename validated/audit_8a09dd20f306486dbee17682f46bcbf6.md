### Title
PedPoP accepts the identity point as a participant encryption key, making all secret shares sent to that participant publicly decryptable - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
The elFinder advisory is a "dangerous input type slips through an incomplete filter" bug: `.phar` files were not in the denylist and were subsequently processed in a security-sensitive way (executed as PHP). The analogous shape in Serai is point-deserialization filtering in the PedPoP DKG: `Ciphersuite::read_G` enforces canonicality but does not reject the identity point, and `EncryptionKeyMessage::read` / `Decryption::register` apply no further filter on `enc_key`. An identity encryption key is the equivalent of the un-filtered `.phar`: it is accepted by the reader, stored, and later used in ECDH, where it degenerates every handshake to a publicly computable value.

### Finding Description
- `EncryptionKeyMessage::read` reads `enc_key` with `C::read_G(reader)` at crypto/dkg/pedpop/src/encryption.rs:58. For `C: Ciphersuite`, this resolves to the default `Ciphersuite::read_G` at crypto/ciphersuite/src/lib.rs:91-101, which rejects only invalid/non-canonical encodings — never the identity. (The identity check exists only in `Curve::read_G`, crypto/frost/src/curve/mod.rs:125-131, which PedPoP does not use since it is generic over `Ciphersuite`, not `Curve`.)
- `Decryption::register` stores `msg.enc_key` unconditionally at encryption.rs:351-362; there is no `is_identity` check anywhere on the registration path.
- When any participant encrypts to that participant, `Encryption::encrypt` → `encrypt()` → `ecdh(&key, to)` (encryption.rs:466, 154, 95-97) computes `key * identity = identity`. `cipher()` (encryption.rs:101-133) then derives the ChaCha20 key solely from the public `context` and the encoding of the identity point — a key computable by anyone, since everything fed into `RecommendedTranscript` is public.
- Result: every `EncryptedMessage<_, SecretShare>` sent to a participant who registered an identity `enc_key` is encrypted under a public key. Any observer of the wire bytes obtains the `SecretShare` plaintext — i.e., the full secret share of that participant index (`self.secret` accumulated at crypto/dkg/pedpop/src/lib.rs:484).

This mirrors elFinder exactly: the reader's filter covers canonicality but omits one dangerous class (identity), and the unfiltered value is then used in a security-critical operation (ECDH shared-key derivation) where it silently collapses confidentiality.

### Impact Explanation
An unprivileged DKG participant registers `enc_key` equal to the identity encoding in their `EncryptionKeyMessage`. Honest participants then encrypt their Pedersen-share evaluations `p_l(r)` to that key, producing ciphertexts decryptable by anyone who can observe the authenticated channel (the protocol relies on this encryption for share confidentiality; blame shares are even relayed publicly, e.g. `VerifyBlame` handling). Whoever obtains the plaintext recovers participant `r`'s full DKG secret share `Σ_l p_l(r)` — the same value `r` holds — letting a third party reconstruct `r`'s threshold share and produce signature shares indistinguishable from `r`'s against `r`'s verification share in subsequent FROST signing. This is secret-share recovery / share impersonation caused by unfiltered attacker-supplied bytes, satisfying the accepted impact class, without requiring the attacker to collude at threshold.

### Likelihood Explanation
The trigger is a single unprivileged participant broadcasting a malformed `EncryptionKeyMessage`; no PoK or PoP covers `enc_key` (the only Schnorr proofs bind `msg.key`/`commitments[0]`, not the registered encryption key), and no caller checks `is_identity`. The attack is deterministic, needs no race or probabilistic condition, and requires no other party to misbehave. Its ceiling is bounded by needing the share's confidentiality to matter (observer model) and by one share per malicious registrant, so Medium is appropriate.

### Recommendation
Reject the identity point when registering encryption keys and when reading `EncryptedMessage.key`/`EncryptionKeyProof.key` — e.g., in `Decryption::register`/`EncryptionKeyMessage::read` and `EncryptedMessage::read` (encryption.rs:58, 173, 268), add an `is_identity` check, or use a `read_G` variant equivalent to `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) for all DKG-exchanged points. This closes the "dangerous input class" gap the same way the elFinder fix added `.phar` to the MIME map.

### Proof of Concept
```rust
// Malicious participant r broadcasts an EncryptionKeyMessage whose
// enc_key is the identity encoding.
let mut msg = EncryptionKeyMessage::<C, Commitments<C>>::read(&mut bytes, params)?;
// or construct directly:
let enc_key = C::G::identity(); // Ciphersuite::read_G accepts this encoding

// Registration succeeds — no identity check:
decryption.register(r, msg); // enc_keys[r] = identity

// Any honest sender l encrypts a share to r:
//   ecdh(&ephemeral_key, identity) == identity
//   cipher(context, identity) -> ChaCha20 keyed by public data
let shared = ecdh::<C>(&Zeroizing::new(k), C::G::identity()); // == identity

// An observer recomputes the same cipher and decrypts the share bytes:
let mut observer_msg = msg.clone(); // wire bytes observed
cipher::<C>(context, &Zeroizing::new(C::G::identity()))
    .apply_keystream(observer_msg.msg_as_mut());
// observer_msg now contains SecretShare<C::F> for participant r in plaintext.
```

Caveat: I could not fully trace every downstream consumer of `Decryption`/`enc_keys` within the iteration budget; the analysis above rests on the ECDH/`cipher` code paths shown, which are sufficient to establish the confidentiality collapse, but the exact blast radius in `processor`/`coordinator` call sites was not exhaustively verified.
