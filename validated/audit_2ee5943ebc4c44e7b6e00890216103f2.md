## Finding: Untracked working-directory image reads follow symlinks outside the repository (no `resolveWithin` guard) - (`app/src/lib/git/diff.ts`)

### Summary
`getWorkingDirectoryImage` builds the path to read a "changed" file's binary content by naively joining the repository root with the git-reported file path, then calling `readFile` directly — with no symlink/traversal containment check. Other parts of the codebase (PR-checkout deep links, Copilot conflict resolution) explicitly guard the same class of operation with `resolveWithin`, which resolves symlinks via `realpath` and rejects anything that escapes the repository root. `getWorkingDirectoryImage` does not use that guard.

### Finding Description
`getWorkingDirectoryImage` is used to render an image preview for a file shown in the Changes/diff view: [1](#0-0) 

It computes the on-disk path with `Path.join(repository.path, file.path)` and immediately reads it, unlike the deep-link file-open path in the dispatcher, which resolves the same kind of repository-relative, attacker-influenced path through `resolveWithin` and explicitly rejects results that escape the repository root (including via symlinks, since `resolveWithin` compares `realpath` output): [2](#0-1) [3](#0-2) 

The same containment pattern is also applied when Copilot reads conflicted files off disk, precisely to guard "against path traversal and symlink escapes (cross-platform)": [4](#0-3) 

`file.path` for an untracked/new working-directory file comes straight from `git status` parsing of whatever is physically present in the working tree (`getStatus` → `buildStatusMap`), which is fully attacker-controlled content once a malicious repository is cloned or fetched and checked out: [5](#0-4) 

Because `Path.join` only does lexical/string joining, a working-directory entry that is itself a symlink (e.g., `evil.png -> ../../../../.ssh/id_rsa` or an absolute target) will have a perfectly ordinary repository-relative `file.path` (e.g. `evil.png`) that satisfies any naive prefix check, but at read time the OS follows the symlink to a location entirely outside the repository. `getWorkingDirectoryImage` never calls `realpath`/`resolveWithin`, so nothing detects or blocks that escape — the exact invariant `resolveWithin` exists to protect elsewhere in this codebase is silently broken here. The same unguarded `Path.join(repository.path, file.path)` pattern is also used for large-file size checks and syntax-highlighting content loads, but those don't expose file content back to the user, whereas the image path does: [6](#0-5) [7](#0-6) 

### Impact Explanation
A malicious repository the user clones, fetches+checks-out, or opens can contain a symlink checked in as a working-directory entry (created via a normal `git add`/commit of a symlink, which git tracks as a blob containing the target path). When Desktop renders that entry as an "image" diff, it reads through the symlink and base64-encodes whatever bytes are at the target location, embedding them in a data URI rendered by the renderer. This is an out-of-repo file read triggered purely by viewing changes in an attacker-supplied repository — no local access, admin rights, or unnatural user steps beyond normal repo browsing are required, matching the "attacker controls a cloned/fetched repository … result is … file read outside the repo" criterion.

### Likelihood Explanation
Git fully supports committing symlinks cross-platform (mode `120000`), and Desktop's `imageFileExtensions` set determines image rendering purely by file extension, not by verifying the path resolves inside the repo. Simply naming the symlink with an image-like extension (`.png`, `.svg`, `.dds`, etc.) and opening/viewing the Changes list is sufficient to trigger the read — no special interaction beyond what a user does routinely when reviewing a newly cloned/fetched repository's changes.

### Recommendation
Route `getWorkingDirectoryImage` (and the other direct `Path.join(repository.path, file.path)` call sites in `diff.ts`, `large-files.ts`, and `syntax-highlighting/index.ts`) through `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` from `app/src/lib/path.ts`, mirroring the containment check already used in `dispatcher.ts` and `copilot-conflict-context.ts`, and treat a `null` result (path escapes the repo, including via symlink) as an unreadable/skippable file rather than reading it.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink: `ln -s ../../../../.ssh/id_rsa evil.png; git add evil.png; git commit -m x` (or any target reachable from the eventual clone location, e.g. `/etc/passwd`), and publishes it.
2. Victim clones the repository in GitHub Desktop (or fetches/checks out a branch containing this commit) and then makes/reverts a trivial local change to `evil.png`, or otherwise causes it to appear in the Changes view.
3. Desktop calls `buildDiff` → `getWorkingDirectoryImage(repository, file)` for the `.png` extension file, which does `readFile(Path.join(repository.path, 'evil.png'))`. Because the working-tree entry is a symlink, the OS resolves and reads the target file's bytes.
4. Those bytes are base64-encoded and rendered as an image preview in the diff pane, disclosing content of an arbitrary file outside the repository to the renderer.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
