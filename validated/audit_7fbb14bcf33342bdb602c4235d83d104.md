## Finding: Unchecked ERC-20 return value in Tron IntentGateway `withdraw()` / `SweepDust` handler causes silent fund loss

### Title
Missing ERC-20 return-value check on escrow release lets a malicious input token silently fail transfers while escrow accounting is finalized - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` reimplements token transfers with a raw low-level `.call()` instead of `SafeERC20.safeTransfer()` (which every other Hyperbridge intents contract uses, e.g. `IntentsBase.sol` and `evm/src/apps/IntentGatewayV2.sol`). It only checks that the external call did not revert (`success`), never decoding/validating the ERC-20 `transfer()` boolean return value, per [1](#0-0) . This is the exact same missing-safety-check class as the seed report (`transferFrom` used where a safety check like `onERC721Received`/return-value validation is required and skipped for gas), just relocated to ERC-20 escrow release instead of ERC-721 custody.

### Finding Description
`withdraw()` is invoked from `onAccept()` for both `RedeemEscrow` and `RefundEscrow` message kinds [2](#0-1) . Inside it:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`_orders[body.commitment][token] -= amount;` and `_filled[body.commitment] = beneficiary;` are then unconditionally applied regardless of whether `transfer()` actually moved funds [3](#0-2) .

Per the ERC-20 spec, `transfer()` is only required to return a boolean; some token implementations return `false` on failure rather than reverting (the exact scenario `SafeERC20` exists to guard against). Because the code checks only `success` (i.e., that the low-level call itself didn't revert) and never decodes/validates the returned `bool`, a `transfer()` call that returns `false` is treated identically to a successful transfer. The escrow ledger (`_orders`) is decremented and the order is marked `_filled` even though the beneficiary received zero tokens. The identical unchecked pattern also exists in the `SweepDust` handler [4](#0-3)  and for the transaction-fee payout inside `withdraw()` [5](#0-4) .

The input token for any order is chosen entirely by the unprivileged order placer at `placeOrder()` time — no allowlist restricts which ERC-20 the escrow accepts [6](#0-5) . An order placer can therefore escrow a custom token whose `transfer()` returns `false` under attacker-chosen conditions (e.g., always returns `false` for calls not originating from a specific allowed caller, or when the recipient is on an attacker-defined blacklist) while still allowing the escrow deposit's `safeTransferFrom()` from the user to the gateway to succeed normally. Once a solver fills the order (delivering genuine output tokens to the order's beneficiary) and the settlement message reaches the source chain, `withdraw()` "succeeds" per its own check, permanently finalizing the order and zeroing escrow accounting — but the solver never receives the input tokens they were owed.

Compare this to the correctly-guarded EVM (non-Tron) equivalent, which always uses `IERC20(token).safeTransfer(beneficiary, amount)` [7](#0-6) , confirming the Tron file is the outlier missing the standard guard.

### Impact Explanation
This is direct, unauthorized loss of funds for the solver/beneficiary of a fill or refund: escrowed tokens are accounted as released (`_orders` decremented, order marked `_filled`) without the tokens actually leaving the contract to the intended party. It is a false-settlement-acceptance bug — the contract accepts a failed transfer as a successful one, permanently locking the true value inside the gateway (or letting a malicious order-placer's crafted token grief solvers who fronted real output assets in good faith).

### Likelihood Explanation
High for any order that escrows a non-standard ERC-20 (a very common category on Tron-style deployments, where many TRC-20/BEP-20-style tokens historically return `false` instead of reverting). No privileged actor, relayer, prover, or governance action is required — the order placer alone selects the input token and can trigger the condition unilaterally.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer()` (already imported and used via `using SafeERC20 for IERC20;` in this same file), mirroring `IntentsBase._withdraw()` in the standard EVM contracts.

### Proof of Concept
1. Attacker deploys a token `EvilToken` whose `transferFrom` behaves like a standard ERC-20 (so `safeTransferFrom` at `placeOrder` succeeds) but whose `transfer()` returns `false` (without reverting) whenever called by the `IntentGatewayV2` contract address (or under any attacker-chosen condition).
2. Attacker calls `placeOrder()` with `EvilToken` as an input asset, escrowing tokens into the gateway.
3. A solver fills the order on the destination chain, delivering genuine output tokens to the attacker's beneficiary, per `_fillCrossChain`/`ExtrinsicIntents.sol` logic.
4. The `RedeemEscrow` message reaches the source chain; `onAccept()` calls `withdraw()`.
5. `token.call(...transfer...)` returns `success = true` (call did not revert) with decoded return data `false`; the unchecked code path treats it as a success, decrements `_orders[...]`, and marks `_filled[commitment] = beneficiary`.
6. The solver receives none of the escrowed `EvilToken`, yet the order is irreversibly finalized — the solver has lost the value they paid out on the destination chain.
