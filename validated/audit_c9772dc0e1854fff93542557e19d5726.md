## Analysis Result

I found a plausible analog: **unbounded recursive RLP decoding of `AccountKeyRoleBased` before any nesting-depth validation is applied**, reachable by any unprivileged account submitting a `TxTypeAccountUpdate` (or fee-delegated variants) transaction, e.g. via `eth_sendRawTransaction`.

### Root cause path
- `TxInternalDataAccountUpdate.DecodeRLP` decodes the raw tx bytes and immediately calls `t.fromSerializable`, which does `rlp.DecodeBytes(serialized.Key, serializer)` on the account-key blob [1](#0-0) , before any semantic validation runs.
- `AccountKeySerializer.DecodeRLP` decodes the key type, then calls `s.Decode(serializer.key)`, dispatching to the concrete key's own `DecodeRLP` [2](#0-1) .
- `AccountKeyRoleBased.DecodeRLP` decodes a list of byte-strings and, for **each element**, calls `NewAccountKeySerializer()` + `rlp.DecodeBytes(b, &serializer)` again [3](#0-2) . If that inner blob itself encodes an `AccountKeyTypeRoleBased`, this recurses back into `AccountKeyRoleBased.DecodeRLP` with no depth limit.
- The only defense against "a `RoleBased` key containing a `RoleBased` sub-key" is `IsCompositeType()`/`CheckInstallable`/`CheckUpdatable`, which are only invoked **after** decoding completes, inside `Validate()` via `accountkey.CheckReplacable` [4](#0-3) [5](#0-4) , and the composite check itself is only applied one level deep [6](#0-5) .

This mirrors the CVE-2018-12183 bug class exactly: a recursive parser (`AccountKeyRoleBased.DecodeRLP`) with no recursion-depth guard, whose only depth restriction is enforced *after* full parsing rather than during it.

### Caveat / what I could not fully verify
I was not able to trace the exact call site where `tx.DecodeRLP` is first invoked on an attacker-supplied raw transaction in the txpool/RPC ingestion path (e.g. `eth_sendRawTransaction` → `TxPool.AddRemote` → `types.Transaction.DecodeRLP`) within the available index, nor measure precisely how much RLP overhead each nesting level costs (to determine whether an attacker can reach thousands of stack frames within typical tx-size/gas limits before hitting `ErrValueTooLarge`/`ErrElemTooLarge` RLP size checks in `rlp/decode.go`). Given index size limits, I could not confirm whether some outer size limit (e.g., max tx size or `rlp.NewStream` limit) caps nesting depth to a small, safe number. I recommend starting a full Devin session to fetch complete file contents for `blockchain/transaction.go` (or equivalent), `blockchain/tx_pool.go`, and `rlp/decode.go`'s stream size-limit constants, and to write a proof-of-concept crafted RLP payload to empirically confirm whether recursion depth is bounded before submitting this as a confirmed finding.

### Title
Unbounded recursive `AccountKeyRoleBased.DecodeRLP` allows stack-overflow DoS via crafted AccountUpdate transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes nested account-key blobs without any depth limit. The single defense against nested `RoleBased` keys (`IsCompositeType`/`CheckInstallable`) executes only after the entire structure has been decoded, in `TxInternalDataAccountUpdate.Validate`. An attacker who crafts a `TxTypeAccountUpdate` (or fee-delegated variant) transaction with deeply self-nested `AccountKeyRoleBased` blobs could drive unbounded Go call-stack recursion during RLP decoding, potentially causing a stack overflow / node crash before the nested-composite-key rejection ever runs.

### Finding Description
`TxInternalDataAccountUpdate.DecodeRLP` decodes the account-key bytes unconditionally via `fromSerializable` → `rlp.DecodeBytes(serialized.Key, serializer)`, and `AccountKeySerializer.DecodeRLP` dispatches to `AccountKeyRoleBased.DecodeRLP` when the type byte says `AccountKeyTypeRoleBased`. That method loops over the decoded byte-string list and, for each element, again constructs a fresh `AccountKeySerializer` and calls `rlp.DecodeBytes` — which can itself decode another `AccountKeyTypeRoleBased`, recursing indefinitely. Depth is only rejected afterward by `CheckInstallable`/`CheckUpdatable` (`IsCompositeType()` check), which is invoked from `Validate()`, i.e., strictly after the (potentially crashing) decode has already completed.

### Impact Explanation
A stack overflow in Go causes an unrecoverable fatal runtime error (process termination), not a panic recoverable via `recover()`. If reachable through public transaction ingestion (mempool `AddRemote`/RPC `eth_sendRawTransaction`, or block/tx propagation decode paths that call `rlp.DecodeBytes`/`tx.DecodeRLP`), this could let any unprivileged sender crash validating full nodes, causing denial of service across the network (liveness impact), matching the CVSS pattern of the original CVE (availability impact via unauthenticated/low-privilege access).

### Likelihood Explanation
Likelihood depends on (a) whether the RLP stream's built-in size limits (`ErrValueTooLarge`/`ErrElemTooLarge` in `rlp/decode.go`) bound the achievable nesting depth to something below Go's default goroutine stack growth limit, and (b) whether transaction-size/gas limits prevent constructing enough nesting levels. Because each nesting level appears to add only a small constant number of bytes (type tag + list/string overhead), an attacker plausibly could reach very deep nesting within a modestly-sized transaction, but this was not empirically confirmed.

### Recommendation
Add an explicit recursion-depth counter/parameter threaded through `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` (e.g., reject decoding if depth > 1, since only one level of nesting is ever legitimate), so the depth check occurs during decoding rather than only after full recursion completes. Alternatively, decode with a `maxDepth` guard analogous to existing RLP list/size limits before ever reaching the composite-key business-logic check.

### Proof of Concept
Conceptual construction (not executed/verified):
1. Build a minimal `AccountKeyLegacy`-typed leaf serializer blob `B0`.
2. Build `AccountKeyRoleBased` blob `B1 = RLP([keyType=RoleBased, RLP([B0])])`.
3. Repeat: `B_{i+1} = RLP([keyType=RoleBased, RLP([B_i])])` for N iterations (e.g., N = 100,000), each iteration adding only a few bytes.
4. Embed final blob `B_N` as the `Key` field of a `TxTypeAccountUpdate` transaction, sign it, and submit via `eth_sendRawTransaction`.
5. Expect: `AccountKeyRoleBased.DecodeRLP` recurses N times during decode, before `CheckInstallable`'s `IsCompositeType` rejection can ever run, potentially causing a Go stack overflow/fatal crash on the receiving node.

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
