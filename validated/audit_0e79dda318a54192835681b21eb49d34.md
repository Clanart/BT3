### Title
Computation-cost limit is bypassed for the `VALIDATE_SENDER` precompile, allowing a single tx to exceed the per-tx computation budget - (File: blockchain/vm/evm.go, blockchain/vm/contracts.go)

### Summary
The `VALIDATE_SENDER` precompiled contract accepts a caller-controlled, effectively unbounded number of 65-byte ECDSA signature chunks and performs a full `secp256k1` recovery (`crypto.Ecrecover`) for every chunk in a single call. Gas for this loop is charged proportionally (`numSigs * ValidateSenderGas`), but the node's dedicated safety mechanism against exactly this class of DoS — the opcode/precompile **computation cost limit** (`OpcodeComputationCostLimit`) — is only accounted for *after* the precompile has already run to completion, not enforced during or before its execution. This mirrors the reported bug class: an unbounded loop over caller-supplied arrays (signers) whose real (CPU) cost is not properly capped, even though a bound-checking mechanism nominally exists for this purpose.

### Finding Description
`validateSender.GetRequiredGasAndComputationCost` derives the number of signatures purely from input length with no upper bound: [1](#0-0) 

`validateSender.Run`/`validateSender.validateSender` then loops over `numSigs` and calls `crypto.Ecrecover` for every chunk, unconditionally, regardless of validity: [2](#0-1) 

`RunPrecompiledContract` only checks the **gas** budget (`contract.UseGas(gas)`) before invoking `Run`; it does not check or gate execution against the computation-cost limit: [3](#0-2) 

The caller, `run()` in `evm.go`, adds the precompile's `computationCost` to `evm.opcodeComputationCostSum` only *after* `RunPrecompiledContract` (and therefore the entire signature-recovery loop) has already finished executing: [4](#0-3) 

By contrast, for ordinary EVM opcodes the interpreter checks `opcodeComputationCostSum` against `ComputationCostLimit` *before* executing each additional opcode, aborting with `ErrOpcodeComputationCostLimitReached` if exceeded: [5](#0-4) 

This means the computation-cost limit (designed to bound wall-clock EVM execution time to ~100ms/150ms per tx, per `OpcodeComputationCostLimit`/`OpcodeComputationCostLimitCancun`) is enforced granularly per-opcode, but is completely bypassed *within* a single precompile call. `VALIDATE_SENDER`'s per-signature computation cost is deliberately set very high (`ValidateSenderPerSigComputationCost = 180000`), reflecting the real CPU cost of an ECDSA recovery: [6](#0-5) 

Since gas for the recovery loop is charged only proportionally to `numSigs` (not gated by the computation budget), an attacker who pays for enough gas (bounded only by the transaction/block gas limit, not by `ComputationCostLimit`) can force the node to perform far more expensive ECDSA-recovery work inside one `Run()` call than the computation-cost mechanism is meant to allow for an entire transaction — the check only fires (too late) on the *next* opcode after the call returns.

### Impact Explanation
This defeats the purpose of the `ComputationCostLimit` safety valve that Kaia specifically introduced to bound per-transaction EVM execution time (to protect block generation/propagation timing, per `BlockGenerationTimeLimit`). A single crafted call (real signatures aren't even required — the attacker can supply garbage 65-byte chunks; `Ecrecover` still performs the expensive elliptic-curve recovery work before failing) can force disproportionate CPU consumption per transaction, well beyond the ~100-150ms budget the mechanism is meant to enforce, while nominally "paying" only linear gas. This can degrade block generation/validation performance across honest nodes processing the same transaction, which is the same "unbounded array iteration exceeds computation budget" bug class as the reported GMX finding, mapped onto Kaia's EVM computation-cost metering system.

### Likelihood Explanation
Reachable by any unprivileged transaction sender/public RPC caller with a single `CALL` to the `VALIDATE_SENDER` precompile address, using deterministic, fully-controlled calldata (`from` address + message hash + N * 65-byte chunks). No special privileges, races, or malicious peer/validator behavior are required — only the willingness to pay gas proportional to `numSigs`. The only constraint is calldata/gas-limit size caps (`MaxTxDataSize`, block gas limit), which in practice still permit a large multiple of the number of recoveries the computation-cost budget is intended to allow within one call.

### Recommendation
Enforce the computation-cost limit check *before or during* precompiled contract execution rather than only after it returns — e.g., have precompiles like `VALIDATE_SENDER` check `evm.opcodeComputationCostSum + incrementalCost` against `evm.Config.ComputationCostLimit` inside their per-signature loop (similar to the interpreter's per-opcode check), aborting early with `ErrOpcodeComputationCostLimitReached` instead of running the full loop unconditionally. Alternatively, impose an explicit maximum `numSigs` bound in `GetRequiredGasAndComputationCost`/`Run` for `VALIDATE_SENDER`, consistent with `accountkey.MaxNumKeysForMultiSig` used elsewhere in the codebase.

### Proof of Concept
1. Construct calldata for a `CALL` to the `VALIDATE_SENDER` precompile: `from (20 bytes) || msg (32 bytes) || N * 65-byte chunks`, where each 65-byte chunk can be arbitrary/garbage bytes (still parses as a signature).
2. Set `N` as large as calldata-size (`MaxTxDataSize`) and gas-limit constraints allow (gas cost is only `N * ValidateSenderGas`, a modest linear multiplier), e.g. on the order of ~1,500–2,000 signature chunks within a single ~128KB-calldata transaction.
3. Submit the transaction. `validateSender.validateSender` (`blockchain/vm/contracts.go:879-924`) will call `crypto.Ecrecover` `N` times unconditionally before returning, incurring `N * 180000` computation-cost units of real CPU work — multiple times the entire per-tx `OpcodeComputationCostLimit`/`OpcodeComputationCostLimitCancun` (100,000,000 / 150,000,000) — none of which is checked until the call already completed and the interpreter proceeds to the *next* opcode.
4. Observe that the check in `interpreter.go:262-265` never had a chance to interrupt the in-flight precompile loop, confirming the computation budget was bypassed for the duration of this single call.

// RunPrecompiledContract runs and evaluates the output of a precompiled contract.
func RunPrecompiledContract(p PrecompiledContract, input []byte, contract *Contract, evm *EVM) (ret []byte, computationCost uint64, err error) {
	gas, computationCost := p.GetRequiredGasAndComputationCost(input)
	if contract.UseGas(gas) {
		ret, err = p.Run(input, contract, evm)
		return ret, computationCost, err
	}
	return nil, computationCost, kerrors.ErrOutOfGas
}

func (c *validateSender) GetRequiredGasAndComputationCost(input []byte) (uint64, uint64) {
	numSigs := uint64(len(input) / common.SignatureLength)
	return numSigs * params.ValidateSenderGas,
		numSigs*params.ValidateSenderPerSigComputationCost + params.ValidateSenderBaseComputationCost
}
