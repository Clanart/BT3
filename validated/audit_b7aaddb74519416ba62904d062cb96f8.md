### Title
Unbounded `order.inputs`/`order.output.assets` array lets an order creator permanently OOG-lock a solver's escrowed redemption - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.placeOrder()` accepts an `Order` struct with attacker-controlled, unbounded `inputs` and `output.assets` arrays — the only check is `order.inputs.length == 0` revert (`evm/src/apps/IntentGatewayV2.sol:163`). Every downstream settlement path (`_withdraw` in `IntentsBase.sol:390-425`, `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol:682-721`, and the cancel paths in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`) loops over `body.tokens.length` (which is populated directly from `order.inputs`) performing an external transfer per entry, with zero cap. This is the same bug class as the reported "any staker can register unlimited vaults and OOG the slashing loop": an unprivileged actor pads an attacker-controlled array to a size that makes a *required* on-chain loop exceed the block gas limit, permanently blocking execution of that function.

### Finding Description
`placeOrder` lets the order creator supply an arbitrary number of `inputs` (and `output.assets`) entries, each of which must be a distinct token address to pass the duplicate check in `IntentGatewayV2.sol:334-343` (`if (_orders[commitment][token] != 0) revert InvalidInput()`), so an attacker can legitimately register hundreds of distinct dummy ERC20 addresses as inputs with trivial escrowed amounts. There is no `MAX_INPUTS`-style bound anywhere in `IntentGatewayV2.sol`, `IntentsBase.sol`, `IntrinsicIntents.sol`, or `ExtrinsicIntents.sol`.

Once a solver fills such an order, redemption is settled via `withdraw()` (or `_withdraw()` in the mainline contract), which iterates the full `tokens` array unconditionally: [1](#0-0) 

The same unbounded pattern appears in the cancel/refund flow and in the standalone Tron deployment: [2](#0-1) 

Cross-chain cancellation from the source chain also loops over `order.inputs` before dispatching the GET query: [3](#0-2) 

The critical broken invariant: **the order creator, not the protocol, controls the size of the array that gates whether the redemption/refund transaction can execute at all.** A malicious user places an order with enough distinct input tokens that `_withdraw`'s loop (SLOAD + external `transfer`/`safeTransfer` per entry) exceeds the chain's block gas limit. This function has no batching, no pagination, and no way to redeem a subset of tokens independently — `finalize` and `isFilled`/fee release only happen once the full loop completes. If the loop cannot complete in one block, `RedeemEscrow`/`RefundEscrow` can never succeed for that commitment.

### Impact Explanation
Once a solver has filled such an order (already having paid outputs to the beneficiary on the destination side, or having escrowed input tokens as the counterparty), the incoming `RedeemEscrow` (or `RefundEscrow`) message triggers `onAccept` → `withdraw`/`_withdraw`. If that loop OOGs deterministically for every relayer/attempt, the escrowed input tokens become permanently unretrievable — a direct, permanent loss/lock of funds belonging to the solver (or the user, on refund). This matches the bounty's "stealing or loss of funds" / "logic attacks" impact class: an unprivileged order creator can grief and permanently freeze counterparty funds inside the contract with no admin recovery path (there's no owner-only sweep for `_orders[commitment][token]` balances once locked in a too-large order).

### Likelihood Explanation
High: `placeOrder` is a fully public, unprivileged entry point; the only cost to the attacker is escrowing a small nonzero amount (or bypassing that via fee-on-transfer edge cases) across N distinct dummy token contracts they deploy themselves. No relayer, prover, or admin involvement is required — this is a pure single-transaction griefing setup, and it is guaranteed to trigger on the very next settlement attempt, deterministically, not merely probabilistically.

### Recommendation
Enforce a hard cap on `order.inputs.length` and `order.output.assets.length` (e.g., a small constant such as 10–20) in `placeOrder`, mirroring the fix applied to the vault-registration bug (bounding the attacker-controlled collection size before it is ever iterated in a settlement-critical loop). Alternatively, redesign `_withdraw`/`withdraw` to support incremental/paginated per-token redemption so a partial loop failure cannot block all other tokens' entries in the same order.

### Proof of Concept
1. Attacker deploys N (e.g., 300) trivial ERC20 tokens, each supporting `transfer`.
2. Attacker calls `placeOrder` with `order.inputs` containing 300 distinct token entries, each with a minimal escrow amount, and normal `output.assets`.
3. A solver, unaware of the gas bomb, fills the order (`fillOrder`), paying the requested outputs to the beneficiary.
4. The fill triggers dispatch of a `RedeemEscrow` request back to the source chain; `onAccept` calls `withdraw(body, false)`.
5. `withdraw`'s loop over `body.tokens` (300 entries, each doing an SLOAD-then-external-call) exceeds the destination chain's block gas limit; the transaction reverts on every retry regardless of gas provided up to the block limit.
6. The solver's already-delivered output payment is unrecoverable, and the escrowed input tokens remain permanently stuck in the `IntentGatewayV2`/`IntentsBase` contract with no way to redeem them.
