### Title
`SignableTransaction::new` omits the OP_RETURN `data` output from the fee/size calculation, producing transactions that pay less than the requested fee rate and over-credit change - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The external report describes a distribution routine that computes payout amounts from a balance without first deducting a required fee, so more value is handed out than should be available. The analog exists in `bitcoin-serai`'s transaction builder: `SignableTransaction::new` adds an `OP_RETURN` output to `tx_outs` when `data` is `Some`, but computes `needed_fee` and the change amount via `calculate_weight_vbytes`, which only ever receives `payments` — the `data` output's weight/vbytes are never included. The result is a signed transaction whose actual fee rate is below `fee_per_vbyte` (potentially below the minimum relay fee even though the `TooLowFee` check passed), and a change output that is larger than it should be under the requested fee policy.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before any fee computation:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...)
  })
}
``` [1](#0-0) 

But both weight calculations pass `payments`, not `tx_outs`, so the OP_RETURN output (up to ~90 bytes: 8-byte value + script with up to 80 bytes of pushdata, permitted by the `> 80` check at line 171) is excluded from the size used for `needed_fee`:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
``` [2](#0-1) 

The same omission occurs in the change branch — `fee_with_change` is computed from a weight that also lacks the data output:

```rust
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
let fee_with_change = fee_per_vbyte * vbytes_with_change;
``` [3](#0-2) 

The change value is then `input_sat - payment_sat - fee_with_change`, crediting the change address with sats that should have covered the data output's share of the fee — the direct analog of "distributing lamports without deducting the launch fee." Additionally, the `TooLowFee` check at line 211 validates `needed_fee` against the underestimated `vbytes`, so a transaction can pass validation while its true fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`.

### Impact Explanation
- The produced transaction pays an effective fee rate lower than `fee_per_vbyte`. With a large `data` payload and a fee rate near minimum, the real rate can drop below the relay minimum, so the signed transaction will not propagate or confirm — funds in its inputs are locked until a replacement is built and re-signed.
- When `change` is supplied, the change output is over-valued by roughly `data_output_vbytes * fee_per_vbyte` relative to the caller's fee policy: value is "distributed" to the change address that was meant to fund the fee, exactly the mis-accounting class from the report.
- `needed_fee()` and `fee()` will diverge from caller expectations of fee-rate correctness; `fee()` (inputs − outputs) is correct, but equals `fee_per_vbyte * (true_vbytes)` only coincidentally — it equals the underestimated `needed_fee`, meaning the transaction simply underpays.

### Likelihood Explanation
`data` is a public, caller-supplied parameter of `SignableTransaction::new` (`Option<Vec<u8>>`, ≤80 bytes). Any caller that attaches an OP_RETURN — the standard mechanism for embedding Serai `InInstruction`-style metadata in Bitcoin transactions — triggers the miscalculation deterministically. The magnitude scales with `fee_per_vbyte`, so it is worst precisely when fees are high or when the requested rate is near the relay minimum.

### Recommendation
Build the fee calculation from the complete output set. Either pass `tx_outs`-equivalent data into `calculate_weight_vbytes` (including the OP_RETURN output and any change output) or compute the weight after `tx_outs` is fully assembled, e.g. by constructing the candidate `Transaction` with the actual output list rather than reconstructing it from `payments` inside `calculate_weight_vbytes`. Apply the same fix to the change branch so `fee_with_change` reflects all outputs.

### Proof of Concept
```rust
// regtest/unit sketch against networks/bitcoin/src/wallet/send.rs
let inputs = vec![received_output];          // e.g. 100_000 sat input
let payments = [(p2tr_script_buf(dest).unwrap(), 50_000)];
let data = vec![0xaa; 80];                   // max-size OP_RETURN, ~90 byte output
let tx = SignableTransaction::new(
    inputs, &payments, Some(change_script), Some(data), /* fee_per_vbyte */ 10,
).unwrap();

// The signed TX's real vsize includes the OP_RETURN output:
let actual_vsize = tx.tx.vsize() as u64;     // larger than estimated
// needed_fee was computed WITHOUT the OP_RETURN:
assert!(tx.needed_fee() < actual_vsize * 10);
// Change received more than it should at a 10 sat/vb policy:
// change == 100_000 - 50_000 - 10*(vsize_without_opreturn)
// effective fee rate == needed_fee / actual_vsize < 10 sat/vb
```
Concretely, `calculate_weight_vbytes` at lines 62–127 only iterates `payments` plus an optional change output, so the OP_RETURN `TxOut` pushed at lines 194–202 contributes ~90 bytes of real transaction weight that is never priced.
