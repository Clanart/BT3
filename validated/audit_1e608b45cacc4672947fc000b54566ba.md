Based on the exploration, the strongest analog I found in `bsaldua/desktop--003` centers on the "Open in Desktop" deep-link handler, which accepts an attacker-controlled `branch` parameter and validates it only against a character blacklist that does not block a leading `-`, before it is passed straight into a `git checkout` invocation.

### Title
Deep-link `branch` parameter is validated with a character blacklist that permits a leading `-`, enabling git argument injection during branch checkout - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` accepts the custom-protocol deep link (`x-github-client://openRepo/...`) that any website or email can trigger via a link click, and extracts a `branch` query parameter that is checked only with `testForInvalidChars`. [1](#0-0)  That function is a denylist regex covering control characters and a handful of Git ref-format-illegal symbols, but it does not reject a leading hyphen `-`. [2](#0-1)  The resulting `branch` string is handed to `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl`, which fetches the repository and then calls `checkoutLocalBranch(repository, branchName)` with the raw, attacker-supplied string. [3](#0-2) 

### Finding Description
This mirrors the broken invariant in the `DaosVesting::claim()` report: a caller-supplied identifier (there, a contract address; here, a git ref name) is accepted from an untrusted source and used directly in a sensitive operation without validating that it is a *safe*, well-formed value rather than merely "not on a blacklist." In the Solidity report, the vesting contract trusted whatever `IDaosLive(dao)` returned instead of confirming the DAO's legitimacy. In Desktop, `testForInvalidChars` trusts the deep-link `branch` value as long as it avoids a specific character set, but a value that starts with `-` (e.g. `--upload-pack=/bin/sh` or other Git checkout flags) is still considered "valid" and forwarded to the git command layer. Unlike the PR-branch case, which is additionally constrained by the regex `/^pr\/\d+$/`, the free-form `branch` parameter used by `openBranchNameFromUrl` has no such positive-format constraint. [4](#0-3) 

I was not able to fully confirm, within the remaining tool budget, whether the underlying `git checkout`/`git branch` invocation in `app/src/lib/git/branch.ts` (or wherever `checkoutLocalBranch` bottoms out) inserts a `--` separator before the ref argument, which is the standard mitigation against this exact class of argument injection. That file was not opened before the iteration budget ran out, so whether this is fully exploitable end-to-end (vs. only reaching a benign git error) is unverified.

### Impact Explanation
If the branch string reaches a `git` argv without a preceding `--` separator, an attacker who gets a victim to click a single `x-github-client://openRepo/<url>?branch=<payload>` link could inject Git command-line options into a `checkout`/`branch` invocation running inside the user's already-open or newly cloned repository. Depending on which flags are reachable, this ranges from repository corruption/unexpected file writes to invoking Git functionality that spawns external processes (a known git argument-injection primitive), which would satisfy the "code execution, file write... outside the repo... or silent corruption of what the user commits" bar in the Valid Impact criteria for this task.

### Likelihood Explanation
The trigger is a single, ordinary link click, no local access, no prior malware, and no elevated privileges — matching the "link or deep link the user clicks" acceptance criterion in the task. The protocol handler is registered by default on all platforms Desktop supports. [5](#0-4)  The only barrier is whatever guard exists (or doesn't) inside the eventual `git` argv construction, which I could not verify in this session.

### Recommendation
- In `parse-app-url.ts`, reject (or strip/prefix) any `branch` value that begins with `-` before returning `IOpenRepositoryFromURLAction`, in addition to the existing `testForInvalidChars` check. [6](#0-5) 
- Audit every git invocation that receives a branch/ref name derived from `parse-app-url.ts` or other externally-sourced strings (`checkoutLocalBranch`, `fetchRefspec`, etc.) to ensure a literal `--` separator always precedes the ref argument, independent of the higher-layer sanitization.
- Apply the same positive-format validation used for the PR branch case (`^pr\/\d+$`) or an equivalent Git-ref allowlist to the general `branch` parameter rather than relying solely on a denylist.

### Proof of Concept
1. Attacker hosts a link: `x-github-client://openRepo/https://github.com/some/repo?branch=--upload-pack%3D%2Fbin%2Fsh`
2. Victim (with GitHub Desktop installed and registered as the protocol handler) clicks the link.
3. `handleAppURL` → `parseAppURL` parses this as `{ name: 'open-repository-from-url', url: 'https://github.com/some/repo', branch: '--upload-pack=/bin/sh' }`, since `testForInvalidChars` does not flag a leading `-`. [4](#0-3) 
4. `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` clones/opens the repository and calls `checkoutLocalBranch(repository, branchName)` with the unmodified string. [3](#0-2) 
5. Whether this results in argument injection depends on the exact `git` argv built downstream, which was not confirmed in this session — a background Devin session with full file access should trace `checkoutLocalBranch` into `app/src/lib/git/branch.ts` to confirm whether a `--` separator is present before the ref argument.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

async function handleCommandLineArguments(argv: string[]) {
  const args = parseCommandLineArgs(argv, {
    boolean: ['protocol-launcher'],
  })

  // Desktop registers it's protocol handler callback on Windows as
  // `[executable path] --protocol-launcher "%1"`. Note that extra command
  // line arguments might be added by Chromium
  // (https://electronjs.org/docs/api/app#event-second-instance).

  if (__WIN32__ && args['protocol-launcher'] === true) {
    // On Windows we'll end up getting called with something like
    // `--protocol-launcher --allow-file-access-from-files x-github-client://..`
    // which minimist naturally interprets as
    // `--allow-file-access-from-files=x:/github-client`. This is due to
    // Chromium's hot take on parsing command line arguments, see:
    // https://github.com/electron/electron/issues/20322#issuecomment-534137321
    // So while we could add '--allow-file...' as a boolean we can't know for
    // sure that Chromium won't add more switches later on which is why we have
    // to resort to looking through all arguments looking for something that
    // appears to be an app url.
    const prefixes = Array.from(possibleProtocols, p => `${p}://`)
    const matchingUrl = argv.find(arg => {
      if (prefixes.some(p => arg.startsWith(p))) {
        try {
          new URL(arg)
          return true
        } catch (e) {
          log.error(`Unable to parse argument as URL: ${arg}`)
        }
      }
      return false
    })

    if (matchingUrl) {
      handleAppURL(matchingUrl)
    } else {
      log.error(`Encountered --protocol-launcher without app url`)
    }
    // If --protocol-launcher is present we always want to bail and not
    // risk a smuggled cli switch
    return
  }
