### Title
Stale cached working-directory diff reused across status refreshes lets partial line-selection map onto a different (fresh) diff at commit time - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
GitHub Desktop's changes-state reducer reuses a previously loaded working-directory diff purely by matching the *selected file ID*, without verifying that the file's on-disk content (and therefore its diff/hunk structure) is still the same as when the diff was cached. The actual patch that gets committed, however, is generated from a **freshly** computed diff at commit time. If the file content changes between the moment the cached diff was captured and the moment the user commits, the user's partial line-selection (computed against the old, cached diff's line indices) gets silently re-applied against the new diff's line indices in `formatPatch`, which can stage/commit different lines than what the user actually reviewed and approved. This is the same bug class as the reported stUSDC issue: a decision (deposit amount / committed lines) is computed by comparing a fresh value against a value that was allowed to go stale, with no reconciliation step to detect the mismatch.

### Finding Description
`updateChangedFiles` in `app/src/lib/stores/updates/changes-state.ts` decides whether to keep the previously-loaded diff for the working directory: [1](#0-0) 

```
    const diff =
      selectedFileIDs.length === 1 &&
      state.selection.selectedFileIDs.length === 1 &&
      state.selection.selectedFileIDs[0] === selectedFileIDs[0]
        ? state.selection.diff
        : null
```

The only condition checked is that the same file ID is still selected before and after a status refresh — there is no comparison of file content/hash/mtime. This function is invoked from `_loadStatus`, which runs on every repository refresh (background fetch completion, periodic indicator refresh, focus-in refresh, etc.), so the diff shown to the user in the Changes view can persist unchanged across many refresh cycles even though the underlying file content silently changed on disk.

Separately, `updateChangesWorkingDirectoryDiff` in `app-store.ts` does refresh the diff and explicitly acknowledges that a diff can become stale relative to line selection: [2](#0-1) 
```
    const selectableLines = new Set<number>()
    if (diff.kind === DiffType.Text || diff.kind === DiffType.LargeText) {
      // The diff might have changed dramatically since last we loaded it.
      ...
      diff.hunks.forEach(h => {
        h.lines.forEach((line, index) => {
          if (line.isIncludeableLine()) {
            selectableLines.add(h.unifiedDiffStart + index)
          }
        })
      })
    }
```
This reconciliation path is only reached when the diff-loading code path runs; it is bypassed by the `updateChangedFiles` short-circuit above, which is what actually executes on ordinary status refreshes while the Changes tab is open.

At commit time, the actual patch fed to git is built from a **brand-new** diff pulled fresh from disk, not the cached one shown in the UI: [3](#0-2) 
```
  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)
```

`formatPatch` then walks this fresh diff's hunks and consults `file.selection.isSelected(absoluteIndex)` — an index space that was defined against the *old* (possibly stale/cached) diff shown to the user: [4](#0-3) 
```
    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex
      ...
      } else if (file.selection.isSelected(absoluteIndex)) {
```

Because hunk boundaries (`unifiedDiffStart`/`unifiedDiffEnd`) shift whenever the file content changes (added/removed lines change offsets), an `absoluteIndex` that pointed at "line X the user intentionally excluded" in the cached diff can point at an entirely different line in the fresh diff used to build the actual patch. The broken invariant is: **the line-selection indices the user set are only valid for the exact diff they were computed against, but Desktop does not guarantee the diff used for staging is the same diff the indices were derived from.**

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user reviewing a stale/cached partial diff (e.g., deliberately excluding a hunk containing a secret, a debug statement, or unwanted changes) could end up committing and pushing content they never approved, because the underlying diff shifted between review and commit and the selection indices were blindly re-applied to different line offsets. Nothing in the commit flow re-validates that the reviewed diff still matches the file before staging — `_commitIncludedChanges` reads `state.changesState.workingDirectory.files` and hands the stale `file.selection` straight to `createCommit`/`applyPatchToIndex`.

### Likelihood Explanation
The condition requires the working-directory file to change on disk between diff caching and commit without the Desktop UI reloading a fresh diff — e.g., an external process, an editor autosave/format-on-save, a build tool, a git hook triggered by another concurrent Desktop/CLI operation, or (in an attacker-controlled-repository scenario) a smudge/clean filter or hook defined in the cloned repository that rewrites tracked files as a side effect of routine operations (checkout, fetch, LFS/filter operations) Desktop performs automatically. Combined with `updateChangedFiles`'s ID-only cache-validity check, which runs on every background/periodic refresh while Changes is open, this is plausible without unusual user steps, but it does depend on some external mutation of the working tree happening in the specific timing window between diff display and the user's click on Commit — which the report author would need to more precisely reproduce to confirm severity.

### Recommendation
When reusing a cached diff for the currently selected file, `updateChangedFiles` should invalidate the diff (not just the file selection) whenever the file's status entry indicates the underlying content changed (e.g., compare `status`/blob OID, mtime, or size, not just file ID). Additionally, `_commitIncludedChanges` should re-validate (or re-derive) each file's diff/selection immediately before generating the patch, reusing the same "selectable lines" reconciliation logic already present in `updateChangesWorkingDirectoryDiff`, so that a partial selection can never be silently reinterpreted against a structurally different diff.

### Proof of Concept
Verified from local code only (not dynamically reproduced):
1. Open a repository in Desktop with a modified tracked file; in the Changes view, deselect specific lines/hunks you do not want to commit (`DiffSelection` line-level selection).
2. While Desktop is idle, have the file's content change on disk in a way that shifts hunk offsets (e.g., an external editor inserts lines above the hunk you deselected, or a git filter/hook rewrites the file during a Desktop-initiated fetch/checkout).
3. Desktop's periodic/background refresh calls `_loadStatus` → `updateChangedFiles`; since the same file ID remains selected, the cached diff (and hence the UI you see) is preserved unchanged per `app/src/lib/stores/updates/changes-state.ts` lines 90-104, even though file content has changed.
4. Click Commit. `_commitIncludedChanges` → `createCommit` → `applyPatchToIndex` calls `getWorkingDirectoryDiff` fresh (`app/src/lib/git/apply.ts` line 60) and `formatPatch` applies the old selection indices to the new hunk structure (`app/src/lib/patch-formatter.ts` lines 143-171), potentially staging/committing different lines than what was shown and approved in step 1.

I was not able to dynamically execute this scenario or inspect `DiffSelection.isSelected`'s exact out-of-range/shifted-index behavior from the index (its implementation lives in `app/src/models/diff/diff-selection.ts`, which I located but did not have time to read in full), so the precise mis-selection outcome (extra lines included vs. lines silently dropped) is inferred from the surrounding code and comments (e.g., the explicit "diff might have changed dramatically since last we loaded it" comment in `app-store.ts`) rather than confirmed end-to-end.
