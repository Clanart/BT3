### Title
`ReceivedOutput::read` accepts an unverified scalar offset not bound to the output's script_pubkey, causing received funds to be unspendable - ([File: networks/bitcoin/src/wallet/mod.rs](crypto/dkg/src/lib.rs))

### Summary
Analogous to the Formie missing-authorization bug (a privileged configuration value accepted without the required check), `ReceivedOutput` couples a `TxOut`/`OutPoint` with a secret scalar `offset` that authorizes which tweaked key may spend it. The deserialization path `ReceivedOutput::read` performs no authorization-equivalent check: it never verifies that `key + offset*G` (the tweaked key) actually maps to `output.script_pubkey`. The only code that establishes this binding is `Scanner::register_offset`/`scan_transaction`, which computes the script from `self.key + GENERATOR * offset` and stores the offset keyed by script.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` populated by `register_offset`, which loops until `p2tr_script_buf(self.key + GENERATOR * offset)` is even and inserts `script -> offset`. `scan_transaction` then only emits a `ReceivedOutput` when `output.script_pubkey` is present in that map, so honestly-produced `ReceivedOutput`s carry an offset that provably derives the output's script under the scanner's key.

However, `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs, lines ~122-133) reads `offset` via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, and returns the tuple with zero consistency check. There is no `p2tr_script_buf(key + offset*G) == output.script_pubkey` verification — exactly the shape of the reference bug: a sensitive field is accepted and later used to authorize a privileged action (selecting the spending key) without enforcement.

Downstream, the spend path treats `received.offset()` as authoritative: the wallet offsets the `ThresholdKeys` (`tweak_keys`/`keys.offset(...)`) so the group signs under `key + offset*G`. If the offset does not correspond to the output's script_pubkey, the resulting BIP-340 signature is produced under the wrong tweaked key and cannot satisfy the output.

### Impact Explanation
An attacker who can feed crafted bytes to `ReceivedOutput::read` (e.g., malicious/ compromised serialization source feeding the coordinator or processor) can make the wallet treat a `TxOut` as spendable under an offset that does not derive its script_pubkey. The node will report funds as received, attempt to spend them, and produce a threshold signature under the wrong tweaked key — the transaction is consensus-invalid and the funds are effectively unspendable (or, if the attacker chose the output's key, the wallet signs for an unintended tweaked key it never meant to authorize). This matches the accepted impact class "funds reported received that are not spendable."

### Likelihood Explanation
Exploitation requires only that an untrusted party supply bytes to `ReceivedOutput::read` — the entry point explicitly listed as attacker-reachable. No key material, validator status, or collusion is needed; the bug is that the bytes themselves authorize the spending-key selection without any proof the offset is correct for the claimed output. Severity is Medium: it causes denial of spendability / incorrect signing rather than direct key compromise.

### Recommendation
Bind the offset to the output at deserialization or first use: recompute `p2tr_script_buf(scanner_key + GENERATOR * offset)` and reject the `ReceivedOutput` unless it equals `output.script_pubkey`. Alternatively, store `ReceivedOutput` as `(outpoint, offset)` only and re-derive/verify the script at spend time before applying `keys.offset(offset)`.

### Proof of Concept
```rust
// Scanner legitimately registers offset o2 producing script S2 = p2tr(key + o2*G)
// Attacker serializes a malicious ReceivedOutput: offset = o1 (o1 != o2),
// output = TxOut { script_pubkey: S2, .. }
let mut bytes = vec![];
bytes.extend(o1.to_bytes());            // wrong offset for this script
bytes.extend(serialize(&txout_S2));
bytes.extend(serialize(&outpoint));

let received = ReceivedOutput::read(&mut bytes.as_ref()).unwrap(); // accepted, no check
assert_eq!(received.offset(), o1);

// Spend path does: keys.offset(o1) -> signs under key + o1*G
// but output requires key + o2*G -> BIP-340 signature invalid, output unspendable
```
