## Finding: Duplicate Authority Signatures Are Not Deduplicated Before the Supermajority Check in `verify_mmr_update_proof`

### Summary
`beefy_verifier::verify_mmr_update_proof` (the function driving `verify_consensus`, reachable from `pallet_ismp::handle_unsigned` via the consensus-message path) computes the BEEFY supermajority threshold using the **raw length** of the attacker-supplied `signed_commitment.signatures` array, and builds the merkle multi-proof leaf/index arrays directly from that same array **without checking for duplicate `sig.index` values**. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`verify_mmr_update_proof` takes `signatures_length = mmr.signed_commitment.signatures.len()` directly from the untrusted proof and feeds it into `check_participation_threshold(signatures_length as u32, authority_set.len)` before any uniqueness check is performed [4](#0-3) . The loop that follows recovers a public key for **every** entry in `signatures` (regardless of whether the same `sig.index`/signature pair appears more than once) and pushes the resulting leaf hash and index into `authority_leaves` / `authority_indices` with no dedup step [5](#0-4) , which are then passed straight to `merkle_proof.verify(...)` [6](#0-5) .

Because the threshold check happens on the raw (possibly duplicated) `signatures_length` rather than on the count of unique authority indices, an attacker who can obtain even a small number of validly-signed relay-chain commitments (e.g. from a legitimately-published commitment that did not reach 2/3+1 participation, or by re-broadcasting the same authority's signature under different envelope framing) could pad `mmr.signed_commitment.signatures` with repeated copies of the same `(index, signature)` pair to push `signatures_length` above the 2f+1 supermajority threshold, while the number of *distinct* authorities actually authenticating the commitment stays below quorum.

The Solidity counterpart (`EcdsaBeefy.sol::verifyMmrUpdateProof`) has the identical structural weakness: `sigLen = relayProof.signedCommitment.votes.length` is used for `checkParticipationThreshold` before the votes are turned into merkle leaves, with no check that `vote.authorityIndex` values are unique [7](#0-6) .

Whether this padding ultimately produces a *valid* merkle-multiproof verification result depends on the internal behavior of the external `rs_merkle::MerkleProof::verify` (Rust) / `MerkleMultiProof.VerifyProof` (Solidity) implementations when given duplicate leaf positions — that library-internal behavior is not part of this codebase's index and could not be verified directly. If the multi-proof reconstruction algorithm tolerates or silently collapses duplicate positions (a common property of position-indexed multiproof algorithms that key intermediate layers by position), the duplicated entries would verify successfully as "proof" of a signature that was only counted once toward actual quorum, while being counted N times toward the threshold check — exactly the amplification pattern described in the question. If, instead, the library strictly rejects duplicate positions (e.g., by requiring strictly sorted/unique indices for the proof to reconstruct the correct root), this specific vector is blocked at that boundary, but the boundary is an unaudited external dependency rather than an explicit invariant enforced in `verify_mmr_update_proof` itself.

### Impact Explanation
If duplicate-index amplification succeeds through the underlying merkle-multiproof libraries, an attacker could get a BEEFY consensus update accepted with fewer than the required 2/3+1 unique relay-chain authority signatures. This directly breaks the "duplicate proof items must never increase voting weight" invariant, letting a minority (or in the worst case a single) set of colluding/compromised signatures forge acceptance of an arbitrary MMR root/authority-set rotation, from which forged parachain header inclusion and forged intermediate state commitments follow — enabling unauthorized cross-chain execution, withdrawals, or settlement, consistent with the "Critical: false state acceptance" impact class in scope.

### Likelihood Explanation
The entry point (`consensus_proof` unsigned message via `pallet_ismp::handle_unsigned`) is unprivileged and fully attacker-controlled in terms of proof bytes, signature list contents, and indices [8](#0-7) . The missing explicit dedup step is a clear code-level gap regardless of the exact external library behavior, and the fix (deduplicate on `sig.index` / `vote.authorityIndex` before computing `signatures_length` and before building the merkle leaf set, rejecting proofs with any duplicate index) is cheap and directly closes the gap without relying on undocumented library internals.

### Recommendation
- In `verify_mmr_update_proof`, deduplicate signatures by `sig.index` (e.g., collect into a `BTreeSet`/`BTreeMap` keyed by index) and use the count of unique indices for `check_participation_threshold`, rejecting the proof outright if any duplicate index is present.
- Apply the equivalent fix in `EcdsaBeefy.sol::verifyMmrUpdateProof` (dedupe `vote.authorityIndex` before computing `sigLen`/threshold and before building the `authorities` leaf array).
- Do not rely on the merkle multi-proof library to implicitly reject duplicate positions; enforce uniqueness explicitly as a protocol invariant.

### Proof of Concept
1. Take a legitimately signed BEEFY commitment where only `k < 2f+1` authorities actually signed (or reuse one authority's valid `(index, signature)` pair from a genuine commitment).
2. Construct `MmrProof.signed_commitment.signatures` by repeating that same `(index, signature)` pair `m` times such that `k*duplication_count ≥ 2f+1` (i.e., `signatures.len() ≥ threshold`) while the number of distinct indices remains `< 2f+1`.
3. Submit via `pallet_ismp::handle_unsigned` → `verify_and_apply` → `verify_consensus` → `verify_mmr_update_proof`.
4. Assert: `check_participation_threshold` passes on the padded length at line 131, and observe whether `merkle_proof.verify` (line 166) also succeeds despite the duplicated index entries in `authority_indices`/`authority_leaves` — if so, a sub-quorum signature set is accepted as a valid consensus update, updating `latest_beefy_height` and authority sets from far fewer real signers than required.

**Caveat:** confirming step 4 conclusively requires inspecting the external `rs_merkle` (Rust) and `solidity-merkle-trees` `MerkleMultiProof` (Solidity) library source for duplicate-index handling, which is outside this codebase's indexed contents. I recommend validating this with an actual unit test in `modules/consensus/beefy/verifier/src/test.rs` that submits duplicated `SignatureWithAuthorityIndex` entries and asserts on the outcome, since the in-repo code shown here provides no explicit protection against it either way.
