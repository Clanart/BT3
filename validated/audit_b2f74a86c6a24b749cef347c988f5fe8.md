### Title
Client-side gasless swap balance-check (`checkBalanceForSwap`) is a mempool-only heuristic that does not guarantee on-chain slippage enforcement, allowing tx-pool admission decisions to diverge from actual on-chain execution results - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The reported bug class ("slippage-protection options exist on a low-level function but are silently dropped by an intermediate/aggregating caller") maps onto Kaia's `kaiax/gasless` module. `checkBalanceForSwap` in `kaiax/gasless/impl/tx_pool.go` computes `minAmountOut`/`amountIn` sufficiency using a *live* on-chain read (`routerContract.GetAmountIn`) taken at admission time, then the module only gates whether a `SwapTx` is accepted into the pool — it never re-validates the same condition at inclusion/execution time, and the check is entirely skippable depending on `GaslessConfig.BalanceCheckLevel`.

### Finding Description
`GaslessModule.checkBalanceForSwap` (`kaiax/gasless/impl/tx_pool.go:107-182`) implements the "protection" logic analogous to the report's `options`/minimum-amount parameters: [1](#0-0) 

This is only a *tx-pool admission* check invoked from `GetCheckBalance` (`kaiax/gasless/impl/tx_pool.go:62-72`), which is registered as a `TxPoolModule` hook. Crucially:
- Two of the sub-checks (`ShouldCheckSwapAmount`, `ShouldCheckToken`) are gated by `GaslessConfig.BalanceCheckLevel`, a node-local, non-consensus configuration value [2](#0-1) . A node operator (or a public RPC endpoint with a lower `BalanceCheckLevel`) can accept/relay a `SwapTx` whose `amountIn` is insufficient for the declared `minAmountOut` at current pool price, or skip the balance/allowance check entirely.
- Even when fully enabled, `GetAmountIn(token, minAmountOut)` is read from current chain state at the moment of tx-pool admission (`kaiax/gasless/impl/tx_pool.go:130-141`), not at the moment the transaction is actually executed in a block. Between admission and inclusion, other transactions can move the pool price, so the "protection" check can pass at admission and yet the real on-chain swap executes with a materially different result — the actual enforcement of `minAmountOut` inside the deployed `GaslessSwapRouter` contract bytecode is the only real backstop, and this Go-level pre-check gives a false sense of protection while not being a substitute for it, mirroring the report's pattern where a low-level function's slippage option exists but an upper-level caller's use of it is incomplete/soft rather than authoritative.
- The same soft-check pattern is repeated for `checkBalanceForApprove` (`kaiax/gasless/impl/tx_pool.go:74-100`), which only checks `balance > 0`, not sufficiency for the paired swap.

### Impact Explanation
This is a Medium-severity node/mempool-policy inconsistency, not a fund-loss bug in the deployed router contract (the actual `minAmountOut` enforcement, if present in `GaslessSwapRouter.swapForGas`, still executes on-chain and can revert the tx). The practical impact is:
- Divergent transaction admission decisions across nodes with different `BalanceCheckLevel` configurations (a public-RPC/endpoint node vs. a CN with strict checks), which can cause a `SwapTx` accepted by one node's mempool to be rejected by another's, or accepted broadly but reverted on execution, wasting gas for users and creating inconsistent mempool/propagation behavior across the network.
- Because the check is a point-in-time price read rather than a guarantee re-verified at inclusion, a gasless sender's `minAmountOut` guarantee is weaker than it appears from the tx-pool acceptance signal, which is the same "slippage option not actually enforced by the calling layer" pattern flagged in the source report.

### Likelihood Explanation
Reachable by any unprivileged transaction sender submitting a `SwapTx`/`ApproveTx` pair to a public RPC endpoint; no special privilege required. The condition depends on configuration (`BalanceCheckLevel`) and normal price movement in the interval between mempool admission and block inclusion, both of which are common and easily triggerable, but the ultimate financial-loss outcome is still guarded by the on-chain router's own slippage check (not shown in this index), which lowers the confirmed severity of value-movement impact.

### Recommendation
- Re-validate `minAmountOut`/`amountRepay`/`amountIn` sufficiency at the point of transaction execution (or immediately prior to block inclusion) rather than relying solely on the mempool-admission snapshot in `checkBalanceForSwap`.
- Make `ShouldCheckSwapAmount`/`ShouldCheckToken` checks mandatory (non-configurable) for gasless swap admission, or clearly document that `BalanceCheckLevel` only affects local mempool policy and provide no guarantee about on-chain outcome, so integrators do not treat pool acceptance as a slippage guarantee.
- Ensure the deployed `GaslessSwapRouter.swapForGas` (on-chain Solidity, not present in this index) itself enforces `minAmountOut` unconditionally regardless of any Go-side pre-check level, and consider surfacing this explicitly in the module documentation.

### Proof of Concept
1. Configure a node’s gasless module with `BalanceCheckLevel = BalanceCheckLevelStatic` (skips `ShouldCheckSwapAmount`/`ShouldCheckToken`), as used in `kaiax/gasless/impl/tx_pool_test.go:450-451` (`gaslessConfig.BalanceCheckLevel = gasless.BalanceCheckLevelStatic`). [3](#0-2) 
2. Submit a `SwapTx` with `amountIn` insufficient for the declared `minAmountOut` at the current pool exchange rate; this node's mempool will admit it because the `ShouldCheckSwapAmount` branch is skipped, while a node with `BalanceCheckLevelSwapAmount` or higher would reject it with `"insufficient amountIn"` (as demonstrated in `tests/gasless_test.go:251-253`). [4](#0-3) 
3. This produces inconsistent transaction admission/propagation across the network purely due to local configuration, and even on nodes with the check enabled, the price read is a point-in-time snapshot that can be stale relative to actual block-inclusion-time execution.
