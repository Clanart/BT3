### Title
Unbounded caller-supplied Bitcoin fee rate can commit threshold wallet to a wallet-draining transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` accepts an arbitrary `fee_per_vbyte` and validates only that the computed fee meets Bitcoin’s minimum relay fee and is covered by the selected inputs. There is no upper bound, sanity limit, or explicit confirmation of the resulting absolute fee before the transaction is placed into `SignableTransaction` and subsequently signed by the FROST transaction machine.

### Finding Description
The fee rate is a public constructor input: [1](#0-0) 

It is multiplied directly by the estimated transaction size and only checked against the minimum relay fee: [2](#0-1) 

The only upper-side validation is whether the inputs can cover the payment and requested fee: [3](#0-2) 

This is especially dangerous around change handling. The transaction is first priced without a change output. If adding change would leave less than `DUST`, no change output is appended. The transaction nevertheless remains valid and all input value not assigned to explicit outputs becomes the actual miner fee. The API documents that behavior: [4](#0-3) 

The change suppression logic is: [5](#0-4) 

Once constructed, `multisig` creates the signing machines and `sign` commits each input signature to the complete transaction sighash using `Prevouts::All`: [6](#0-5) [7](#0-6) 

Thus, an unbounded fee parameter is not merely an accounting error: it becomes part of the exact transaction message that the threshold key signs.

### Impact Explanation
An unprivileged requester who can influence the transaction-construction parameters can provide an excessively high fee rate and cause the wallet to authorize a transaction paying nearly all selected input value to miners. If the residual change would be dust, it is omitted, potentially making the effective fee even larger than `needed_fee` and consuming the entire difference between inputs and payment outputs.

This is the same core weakness as the reported fee-payer issue: attacker-controlled fee semantics are incorporated into a signature without an upper bound, allowing a single signed transaction to drain wallet funds. The funds are not stolen to an attacker address, but they are irrecoverably paid as transaction fees and the wallet loses spendable balance.

### Likelihood Explanation
The vulnerable path is reachable entirely through public transaction-construction inputs: `payments`, `change`, and `fee_per_vbyte`. No malicious validator, compromised signer, leaked key, malformed curve point, or invalid protocol message is required. Any service exposing transaction creation while deriving the fee rate from requester-controlled data reaches the issue.

The likelihood is dependent on deployment behavior. The in-repository processor currently obtains Bitcoin fees through `median_fee` rather than directly accepting a requester fee, which limits that call path: [8](#0-7) 

However, `bitcoin-serai` exposes the unsafe primitive as a public wallet API, and integrations using client-specified fee parameters would be directly affected.

### Recommendation
- Reject fee rates above a configured policy maximum before transaction creation.
- Validate the absolute `needed_fee` against a maximum fee budget and the transaction’s economic purpose, not merely against input balance.
- Use `checked_mul` and `checked_add` for `fee_per_vbyte * vbytes` and `payment_sat + needed_fee`.
- Reject transactions where suppressing change would make `SignableTransaction::fee()` exceed the intended `needed_fee` by more than an explicitly configured bound.
- Require callers to explicitly acknowledge unusually large absolute fees through a separate unsafe/override parameter.
- Consider returning an error when a requested change output is omitted and the resulting implicit fee differs materially from the quoted fee.

### Proof of Concept
A conceptual proof can be constructed against `SignableTransaction::new` using one wallet-controlled `ReceivedOutput` with a high value, one minimum-sized payment, a change script, and a very large fee rate.

```rust
use bitcoin_serai::wallet::SignableTransaction;
use bitcoin::ScriptBuf;

let input_value = 1_000_000u64;
let payment = 546u64;

// Chosen so the estimated fee passes the minimum and is covered by inputs,
// but leaves less than DUST if change is added.
let excessive_fee_per_vbyte = 8_000;

let tx = SignableTransaction::new(
  vec![wallet_input],                         // input_value = 1_000_000 sats
  &[(attacker_requested_payment, payment)],   // 546-sat payment
  Some(wallet_change_script),                 // may be omitted if change < DUST
  None,
  excessive_fee_per_vbyte,
)
.expect("unbounded fee rate was accepted");

// The signed transaction commits all inputs and all outputs.
// If the change output was suppressed, nearly the entire
// 1_000_000 - 546 sats become miner fees.
assert!(tx.fee() >= tx.needed_fee());
assert!(tx.fee() > 900_000);
```

The precise boundary can be determined from `needed_fee()` or `transaction().vsize()`. Increasing `fee_per_vbyte` is sufficient to push the transaction from retaining change to suppressing it as dust, at which point the final signed transaction sends all unassigned input value to miners. The signature path then commits to that output set through `taproot_key_spend_signature_hash` and `Prevouts::All`.
