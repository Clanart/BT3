### Title
Malformed unified-diff hunk header from a crafted repository crashes the DiffParser and can bring down GitHub Desktop's renderer - (File: `app/src/lib/diff-parser.ts`)

### Summary
The Nimbus report describes a remote peer sending a malformed attestation that the consensus-layer node fails to validate defensively, causing a crash (DoS). The Desktop analog is `DiffParser.parse()`, which is fed `git diff`/`git log --patch` output derived from the contents of a cloned/fetched/checked-out repository. If a hunk header or "no newline" marker line doesn't match the expected format, the parser throws synchronously, and none of the call sites (`getWorkingDirectoryDiff`, `getCommitDiff`, `getResolutionDiff`, etc.) wrap the parse step in a `try/catch`. An uncaught exception in the renderer is explicitly treated by Desktop as fatal.

### Finding Description
`DiffParser.parseHunkHeader()` matches lines against `diffHeaderRe` and throws `Invalid hunk header format` if the regex fails [1](#0-0) . `parseHunk()` throws further errors such as `Expected hunk header but reached end of diff`, `Expected unified diff line but reached end of diff`, an explicit length check throwing `Expected "no newline at end of file" marker to be at least 12 bytes long`, and `Malformed diff, empty hunk` [2](#0-1) [3](#0-2) .

`diffFromRawDiffOutput()` — the shared entry point used by `getCommitDiff`, `getWorkingDirectoryDiff`, and `getResolutionDiff` — calls `parser.parse()` directly with no try/catch around it [4](#0-3) . `buildDiff()`, which is invoked after every working-directory or commit diff fetch, calls `diffFromRawDiffOutput(buffer)` unguarded as well [5](#0-4) . The stack that leads here (`AppStore._selectWorkingDirectoryFiles` → `updateChangesWorkingDirectoryDiff` → `getWorkingDirectoryDiff`) similarly awaits the diff without a try/catch around the call [6](#0-5) .

The raw diff text ultimately comes from `git diff`/`git log --patch` output run against the checked-out working tree or commit content — i.e., attacker-controlled file content in a cloned/fetched repository can shape what git prints in a hunk. While `git` itself normally emits well-formed unified diffs, Desktop's parser is a hand-written state machine that assumes strict conformance to `diffHeaderRe` and the "no newline" marker's exact byte length; any line that diverges from those exact assumptions (e.g., due to a "diff.external"/textconv-influenced or unusual encoding/mixed-newline content that changes marker formatting, or hunk headers whose numeric groups are ambiguous) causes a thrown `Error` rather than a graceful fallback.

Crucially, Desktop's renderer process is explicitly configured to treat uncaught exceptions as fatal: `process.on('uncaughtException', onUncaughtException)` is installed with the stated design intent that "unhandled errors should crash the app" [7](#0-6) . Unlike `unhandledrejection`, which is only logged/reported non-fatally [8](#0-7) , a promise chain that surfaces as an actual thrown/uncaught error (or a subsequent synchronous re-throw in a React render path fed by the malformed diff data) is designed to crash.

### Impact Explanation
This is a Denial-of-Service against the Desktop application itself: opening/refreshing the Changes view or History view for a repository containing a crafted file whose diff triggers one of these thrown parser errors can crash or repeatedly fail to render the diff for the affected file, disrupting the user's workflow. This matches the "DoS" class from the seed report, mapped onto the equivalent trust boundary in Desktop (attacker-controlled repository content parsed by application logic). It does not achieve code execution, file write/read outside the repo, or credential exfiltration, so severity is best characterized as Low/Medium DoS-class, consistent with the original report's "Medium" severity for a crash bug.

### Likelihood Explanation
Medium-low. It requires an attacker to control the content of a repository a victim clones/fetches/checks out (e.g., via a malicious commit crafted to make git emit a hunk header or "no newline" marker line that fails the parser's strict regex or length assumptions) and for the victim to view the diff for the affected file in Desktop. Because `git` itself is a well-behaved tool, forcing it to emit a header/marker line that violates the parser's assumptions is non-trivial and would need further verification against the exact `git diff --patch-with-raw` output format edge cases (e.g., unusual filenames, binary/text boundary detection, or huge line-count values causing `numberFromGroup` to overflow) — I was not able to construct or confirm a concrete git-produced input that trips this parser within the scope of this investigation.

### Recommendation
- Wrap `DiffParser.parse()` invocations in `diffFromRawDiffOutput` / `buildDiff` in a try/catch and fail gracefully (return `DiffType.Unrenderable`) instead of letting the exception propagate to the renderer's fatal exception handler.
- Add defensive validation for numeric group parsing in `numberFromGroup`/hunk headers to reject or clamp unexpected values rather than throwing uncontrolled errors.
- Consider making the `updateChangesWorkingDirectoryDiff` / `getCommitDiff` / `getResolutionDiff` call sites resilient to diff-parsing failures so a single malformed file cannot crash the whole application.

### Proof of Concept
Not independently reproduced against real `git` output. Conceptually: craft a repository/commit whose diff for a specific file, when Desktop invokes `git diff --patch-with-raw -z --no-color` (`getWorkingDirectoryDiff`, `app/src/lib/git/diff.ts:342-401`), yields a hunk header line that does not match `^@@ -(\d+)(?:,(\d+))? \+(\d+)(?:,(\d+))? @@` or a "no newline" marker shorter than 12 bytes. Selecting that file in the Changes view invokes `AppStore._selectWorkingDirectoryFiles` → `updateChangesWorkingDirectoryDiff` → `getWorkingDirectoryDiff` → `buildDiff` → `diffFromRawDiffOutput` → `DiffParser.parse()`, which throws synchronously and is uncaught along that path, hitting the renderer's "crash the app" design in `app/src/ui/index.tsx`.
