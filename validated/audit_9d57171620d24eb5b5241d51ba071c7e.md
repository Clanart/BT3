### Title
Unauthenticated `Setup` call on aggregator gRPC server when `client_verification=false` uses `Interceptors::Noop` - ([File: core/src/servers.rs])

### Summary
When `config.client_verification` is `false`, `create_grpc_server` wraps the aggregator's `ClementineAggregatorServer` in `InterceptedService::new(service, Noop)` instead of `OnlyAggregatorAndSelf`, and `Interceptors::call` for `Noop` unconditionally returns `Ok(req)` with no identity check. Any unprivileged network caller can therefore invoke `setup` (and any other aggregator RPC) directly, triggering verifier key distribution / operator config collection state changes with no caller authentication.

### Finding Description
The broken binding: CALLER_IDENTITY(request reaching `AggregatorServer::setup`) == AGGREGATOR_OR_SELF_CERT_HOLDER should hold, enforced by `only_aggregator_and_self` in `core/src/rpc/interceptors.rs` (checking `leaf_cert == aggregator_cert || leaf_cert == our_cert`) [1](#0-0) . But when `config.client_verification == false`, `create_grpc_server` builds the TLS config without a `client_ca_root` and selects `Interceptors::Noop` for the `InterceptedService` instead of `OnlyAggregatorAndSelf` [2](#0-1) , and `Interceptors::call` for the `Noop` variant returns `Ok(req)` unconditionally with no certificate check at all [3](#0-2) . The only signal about this insecure state is a `tracing::warn!` that fires when `client_verification` is `true` (an oddly inverted log, not a warning about the insecure default) [4](#0-3) . Under this configuration, any TCP client that can complete a plaintext-cert or self-signed TLS handshake (no need to hold the aggregator's real certificate) reaches `AggregatorServer::setup`'s gRPC handler unauthenticated.

### Impact Explanation
This matches the "unauthenticated state-changing call" High-severity category defined in the rules, since it lets an unprivileged caller invoke aggregator RPCs (including `setup`, which redistributes verifier keys/collects operator configs) without holding any certificate or key material. I was not able to fully verify within tool budget whether `setup`'s internal logic (`core/src/rpc/aggregator.rs`) enforces any additional state-guard that would make repeated/attacker-triggered calls idempotent-safe or would reject calls after initial setup has completed; I did not get to read the full body of `ClementineAggregator::setup`. This is a caveat on exact blast radius (whether it can be called only once at genesis vs. repeatably later during live deposits) that a full review would need to close before final severity confirmation.

### Likelihood Explanation
The precondition (`client_verification == false`) is described in the audit prompt as the aggregator's "documented deployment state," and the code confirms this is a valid, reachable configuration path in `create_grpc_server`/`create_aggregator_grpc_server` with no additional required privilege beyond network reachability to the TCP port [5](#0-4) . No Bitcoin funds, fees, or key shares are required to reach the vulnerable code path — only network access to the aggregator's gRPC port.

### Recommendation
Regardless of `client_verification` configuration, the aggregator (and operator/verifier) servers should not fall back to `Interceptors::Noop` for internet-facing TCP listeners. Either always require mTLS with `OnlyAggregatorAndSelf`, or explicitly document/enforce that `client_verification=false` is only safe for loopback/Unix-socket transports, and reject binding `Noop` service to a non-local TCP `ServerAddr` at server construction time.

### Proof of Concept
I could not fully complete verification of `ClementineAggregator::setup`'s internal behavior (e.g., whether it can be invoked idempotently/repeatably after genesis) due to the final-iteration constraint, so I cannot provide a fully validated `cargo test` assertion pair confirming the state-mutation impact beyond the authentication bypass itself. The authentication-bypass code path itself (`Noop` reached whenever `client_verification=false`) is directly confirmed in the cited source; a reproducible test would start `create_aggregator_grpc_server` with `client_verification=false`, connect with a bare channel lacking any client certificate, call `setup`, and assert the call returns `Ok` rather than `Status::unauthenticated`, per the interceptor code shown above.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
