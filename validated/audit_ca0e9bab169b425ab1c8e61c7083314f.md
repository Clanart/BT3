Based on my investigation, I found a concrete local analog: the TRON deployment of `IntentGatewayV2` still contains a self-referential default-identity fallback in its peer-authentication logic that the mainline EVM contract has since removed/hardened. This is the same bug class as the report — an address value that is supposed to represent a *distinct, deliberately configured* identity instead silently resolves to "itself", collapsing an intended two-party trust check into a tautology.

### Title
TRON `IntentGatewayV2.instance()` defaults unregistered source chains to `address(this)`, allowing forged escrow release/refund authentication - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`authenticate()` in the TRON `IntentGatewayV2` gates `RedeemEscrow`/`RefundEscrow` processing on `instance(request.source) == module`, where `module` is read directly from attacker-influenced `request.from` bytes. `instance()` returns `address(this)` whenever no peer gateway has been explicitly registered for `request.source`, instead of reverting. [1](#0-0) 

### Finding Description
`instance()` is defined as:
```
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}
``` [2](#0-1) 

`authenticate()` then checks:
```
function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (instance(request.source) != module) revert Unauthorized();
}
``` [3](#0-2) 

For any `request.source` state machine that has never had a peer gateway registered via `NewDeployment`/`_addDeployment`, `instance()` returns `address(this)` — the gateway's own address — instead of reverting. Consequently, any incoming `PostRequest` whose `from` field is set to `address(this)` (the destination gateway's own address) will pass authentication as if it came from a legitimately registered peer, even though no such peer was ever configured for that source chain.

This is the exact bug class from the report: a value meant to enforce a distinct, deliberately-provisioned identity (a registered remote gateway) instead resolves to the checking contract's own identity by default, collapsing the intended two-party binding.

By contrast, the current mainline EVM contract fixed this exact pattern — its `_instance()` now reverts with `UnknownInstance` when no gateway is registered, rather than falling back to `address(this)`: [4](#0-3) 

This shows the TRON contract is a stale/divergent copy that reintroduces a since-patched authentication weakness.

### Impact Explanation
If a `PostRequest` can reach `onAccept` with `source` set to any state machine ID that the TRON gateway has not explicitly registered a peer for, and with `from` forged to `address(this)`, `authenticate()` passes, letting the caller drive `RedeemEscrow`/`RefundEscrow` against escrowed order state with an attacker-chosen `beneficiary`, causing funds held in `_orders` escrow to be redirected/drained. This is a false-state/false-authentication acceptance leading directly to fund loss, matching the bounty's "false proof/state acceptance" and "stealing or loss of funds" categories.

### Likelihood Explanation
Exploitability depends on whether the local ISMP host enforces `from == msg.sender` (the true dispatching contract) when relaying an inbound `PostRequest`, or trusts the `from` field as supplied within the message body from the source-chain dispatch, which was not fully verifiable from indexed contents. If `from` is attacker-controllable at dispatch time (i.e., set by the dispatching contract itself rather than forced to equal the dispatcher's `msg.sender`), then any account that can dispatch a genuine cross-chain message from an as-yet-unregistered source chain (no relayer collusion needed — the message is real and provably delivered) can trigger this bypass without any privileged, admin, or malicious-relayer assumption. Given the pattern was already fixed in the primary EVM codebase, the TRON deployment's unpatched fallback represents a real, reachable regression rather than a purely theoretical one.

### Recommendation
Align TRON's `instance()`/`authenticate()` with the mainline EVM implementation: revert with an `UnknownInstance`-style error when no peer gateway is registered for `request.source`, instead of defaulting to `address(this)`. Never treat "identity unset" as equivalent to "identity is self."

### Proof of Concept
1. Deploy TRON `IntentGatewayV2`; do not call `NewDeployment`/`_addDeployment` for state machine ID `X` (a real, ISMP-supported chain with no explicit peer configured on this gateway instance).
2. From chain `X`, dispatch a genuine ISMP `PostRequest` (`source = X`, `to = <TRON gateway address>`, `body` = `RedeemEscrow`/`RefundEscrow` kind with attacker-chosen `beneficiary` and a real escrowed `commitment`/`token` amount) with `from` bytes equal to `address(this)` (the TRON gateway's own address) if the dispatching side allows setting `from` freely.
3. The TRON host verifies the proof genuinely (message really was dispatched on `X`), delivers to `onAccept`.
4. `authenticate()` calls `instance(X)`, which returns `address(this)` because `X` has no registered `_instances` entry; `module` (`address(this)`) matches, authentication passes.
5. `_withdraw` executes, releasing/reassigning escrowed tokens to the attacker-specified `beneficiary`.

Note: full confirmation that `request.from` is attacker-settable at dispatch (rather than forced to `msg.sender` by the source-chain host) could not be completed within the available index before this response was finalized; this should be verified against `evm/src/core/DispatcherV2.sol` (or TRON's equivalent host/dispatcher) before treating this as fully proven.
