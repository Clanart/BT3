### Title
Unauthenticated senders can inject outputs under privileged internal classifications by depositing to Serai's offset-derived addresses (Branch/Change/Forwarded), bypassing `InInstruction` data extraction - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The CVE-2018-17553 class is "an attacker-controlled identifier selects a resource/type outside the intended domain" (`id=../../../navigate_info.php` picks an arbitrary file/type). In Serai's Bitcoin scanner, the analogous "identifier" is the output's `script_pubkey`: `Scanner::scan_transaction` classifies a received output purely by looking the script up in a script→offset map, and `get_outputs` then maps the offset to an `OutputType` (`External`, `Branch`, `Change`, `Forwarded`). Since all offset addresses are publicly computable (`key + G*offset` with `offset = hash_to_F(b"Serai Bitcoin Output Offset", kind)`), any unprivileged party can craft a transaction whose output lands in an internal-only classification, exactly like an attacker choosing `id` to select a resource they shouldn't reach.

### Finding Description
`Scanner::new`/`register_offset` build `scripts: HashMap<ScriptBuf, Scalar>` keyed only by the Taproot script. [1](#0-0)  `scan_transaction` returns a `ReceivedOutput` for any output whose `script_pubkey` is in that map, with no distinction of who created it. [2](#0-1)  The processor-side `scanner()` registers the well-known offsets deterministically from `Secp256k1::hash_to_F(KEY_DST, b"branch"|b"change"|b"forward")` — public values anyone can recompute for the public group key. [3](#0-2)  `get_outputs` then assigns `kind` by `kinds[offset_repr]` and only attaches `extract_serai_data(tx)` (the `InInstruction`/refund payload) when `kind == OutputType::External`; for Branch/Change/Forwarded the data is silently dropped and the attacker-controlled `presumed_origin` is still attached. [4](#0-3)  `Output::key()` simply subtracts `G*offset` from the script's x-only key, so these spoofed outputs pass key validation and are reported as genuine internal outputs. [5](#0-4) 

### Impact Explanation
An unprivileged Bitcoin user (not a validator, not a signer) sends an ordinary transaction to the group's Branch/Change/Forwarded address — addresses fully derivable from public data. The scanner reports this as an *internal* output, not an `External` deposit:

- The attacker's deposit is emitted with `kind != External`, so its `data` field stays empty even if the transaction embeds a valid `InInstruction` OP_RETURN. The deposit's instruction (e.g. destination/refund metadata) is silently discarded — funds are reported received yet never processed as the deposit the sender intended.
- Conversely, spoofed internal outputs enter the pool of Serai-owned UTXOs with internal semantics (branch/change/forwarded), letting an external party inject outputs into internal accounting/rotation flows that were designed to only be produced by Serai's own transactions. This is the analog of selecting an unintended resource type: the same unsanitized "which slot does this land in" confusion that let `engine=picnik` + traversal write to `navigate_info.php`.

### Likelihood Explanation
Reachability requires only broadcasting a standard P2TR Bitcoin transaction — public input per the rules. The offsets are fixed, domain-separated hashes of constant strings, so the destination scripts are computable by anyone who knows the group key (which is public). No collusion, no malicious validator, no leaked key. Exploitation for profit is limited (the attacker largely donates or mis-routes their own funds), but the misclassification is deterministic and reliable, so this sits at Medium rather than High.

### Recommendation
Stop relying on `script_pubkey` equality alone to determine output kind. Either (a) require `External`-versus-internal discrimination via authenticated data (e.g., only treat an output as Branch/Change/Forwarded if the transaction itself is a Serai-constructed transaction matching a pending eventuality/ID registered via `register_eventuality`), or (b) always run `extract_serai_data` and attach `InInstruction` parsing regardless of kind, so a spoofed internal output cannot shed its embedded metadata. Additionally, `get_outputs` indexing `kinds[offset_repr]` assumes every scanned offset maps to a known kind; use `get()` to avoid a panic if the map is ever extended.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

      for output in scanner.scan_transaction(tx) {
        let offset_repr = output.offset().to_repr();

        let kind = kinds[offset_repr_ref];

        assert_eq!(output.tx_id(), tx.id());

        continue;

        // We *could* parse out the script *without the InInstruction prefix* and declare that the
