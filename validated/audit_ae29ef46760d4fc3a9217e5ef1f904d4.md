## Summary

The `_fillSameChain` function in `IntrinsicIntents.sol` computes the escrow amount to release to a solver, on the leg that completes an output, by reading the **entire current balance** of the shared `_orders[commitment][token]` bucket instead of the amount actually owed for that specific output leg. Because `_orders` is keyed only by `(commitment, token)` and not by leg index, an order whose output legs reference the same input token pools their escrow into a single bucket. The first leg to reach full completion drains that whole bucket — including escrow reserved for the other, not-yet-filled leg — and pays it to the wrong solver, exactly mirroring the `_checkBalance` class of bug where a balance read fails to subtract/attribute a competing claim on the same pool.

## Finding Description

In `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `_fillSameChain` iterates over `order.output.assets` by index `i`, treating `order.inputs[i]` as the input backing output leg `i`: [1](#0-0) 

When a leg completes (`amountFilled == totalRequired`), instead of computing the *proportional remaining* input amount for that leg, the code reads the raw current value of `_orders[commitment][token]` — the aggregate escrow bucket for that input token across the whole order:

```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

This aggregate is populated at order placement by summing all input entries sharing that token address: [2](#0-1) 

and it is decremented generically by `_withdraw`, which has no notion of "leg": [3](#0-2) 

If a user places an order with two (or more) output legs whose corresponding `order.inputs[i].token` and `order.inputs[j].token` are the same address (i ≠ j), both legs' escrow lands in the *same* `_orders[commitment][token]` slot. There is no validation anywhere in `IntentsBase.sol` or `IntrinsicIntents.sol` preventing duplicate input tokens across different leg indices. When the first of these legs is fully filled, `escrowedAmount` for that leg is set to the *entire pooled balance* — which still includes the portion meant to back the other, unfilled leg — and that whole amount is transferred to the solver who completed the first leg via `_withdraw`.

## Impact Explanation

- **Wrong beneficiary / amount**: the solver completing the first shared-token leg receives escrow that rightfully belongs to a different, still-unfilled leg of the same order — a direct fund-diversion from the intended recipient/purpose.
- **Fund loss / lock for subsequent legs**: when the second leg is later filled, `_withdraw` reads `_orders[commitment][token]`, finds it already zeroed (or reduced below the proportional share), and reverts with `UnknownOrder` (`escrowed == 0`) or underflows the `escrowed - amount` subtraction and reverts. Either way, the solver who fulfilled the second leg has already sent the beneficiary their output tokens (`beneficiaryTotal` transfer happens before the escrow computation) but cannot collect the input escrow they are owed — a real loss of funds with no recovery path other than the user cancelling (which itself now refunds a smaller-than-expected residual, since the pooled escrow was already drained).
- This requires no relayer, prover, governance, or admin action — it is triggered purely by an unprivileged order creator and unprivileged solver(s) interacting through the public `placeOrder`/`fillOrder` entry points, satisfying the "stealing or loss of funds" / "wrong beneficiary or amount" bounty categories.

## Likelihood Explanation

Likelihood is moderate: nothing in the order-validation path rejects duplicate input tokens mapped to different output legs, so any user (potentially in collusion with, or acting as, a solver) can construct such an order deliberately. Solvers competing to fill legs of a public order have direct incentive to be the one who completes the shared-token leg first, since doing so pays them the full pooled escrow.

## Recommendation

Compute the amount released for a completed leg as the leg's own **proportional share of the pool `_orders[commitment][token]`**, or restructure escrow accounting to be tracked per-leg (e.g., keyed by `(commitment, outputIndex)` rather than by token alone), rather than defaulting to "hand over whatever remains in the shared bucket." At minimum, on full-leg completion, cap `escrowedAmount` at `order.inputs[i].amount` (the leg's original allotment) instead of the live aggregate `_orders[commitment][token]` balance, and only release the true remainder pooled across *all* legs once every leg backed by that token has been resolved.

## Proof of Concept

1. User places a same-chain order with two output legs, both backed by the same input token `USDC`:
   - `inputs[0] = {token: USDC, amount: 500e6}`, `output.assets[0] = {token: DAI, amount: 500e18}`
   - `inputs[1] = {token: USDC, amount: 500e6}`, `output.assets[1] = {token: WETH, amount: 1e18}`
   - Total escrow: `_orders[commitment][USDC] = 1000e6`.
2. Solver A calls `fillOrder` supplying `outputs[0].amount = 500e18` (fully fills leg 0) and `outputs[1].amount = 0` (skips leg 1).
3. In the loop, leg 0 hits `amountFilled == totalRequired`, so `escrowedAmount = _orders[commitment][USDC] = 1000e6` — the entire pool, not leg 0's `500e6` share. `_withdraw` transfers all `1000e6` USDC to Solver A.
4. Solver B later attempts to fill leg 1 (WETH) with `outputs[1].amount = 1e18`. On completion, `_withdraw` is called for `USDC` with `escrowed = _orders[commitment][USDC] = 0`, triggering `revert UnknownOrder()` — Solver B has already sent 1 WETH to the beneficiary but receives no USDC in return, and the order is left in a stuck/partial state.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
