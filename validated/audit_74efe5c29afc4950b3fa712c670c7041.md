### Title
NFT1 royalty payment amount is derived from an unsigned, submitter‑controlled `trade_prices_list` value that is never checked against the real settlement price - (File: `chia/wallet/nft_wallet/nft_puzzle_utils.py`, `chia/wallet/nft_wallet/transfer_program_puzzle.py`, `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
Just as the Biconomy `SmartAccount` bug let a submitter alter an unsigned `tokenGasPriceFactor` to inflate the gas refund it paid itself, Chia's NFT1 royalty mechanism lets the party who completes (solves) an NFT transfer supply an arbitrary, unsigned `trade_prices_list` to the `NFT_TRANSFER_PROGRAM_DEFAULT` puzzle. This value — not the actual amount paid to the seller — is what the on‑chain royalty calculation uses to size the payment to the royalty/DID address. Because it is a solution-time parameter chosen by whoever completes the spend rather than a value bound to the seller's signature or to the real settlement amount, the completer of an NFT trade can declare a trade price far lower than what is truly exchanged, driving the enforced royalty toward zero while still consummating the trade at the true (higher) price via the separate `requested_payments`/offer-settlement announcement.

### Finding Description
When an NFT1 (ownership-layer) coin changes owner, the inner solution passes `trade_prices_list` into the transfer program: [1](#0-0) 

This solution is combined with the curried, signature-independent royalty percentage in `NFT_TRANSFER_PROGRAM_DEFAULT`: [2](#0-1) 

The royalty amount actually enforced on-chain is `trade_price * royalty_percentage`, and it is this derived (not the real trade) amount that other coins in the bundle must satisfy via puzzle announcements, as shown by the test harness that builds the expected announcement directly from an attacker-suppliable `trade_prices_list`: [3](#0-2) 

On the wallet side, `trade_prices_list` is computed heuristically from the *requested* fungible amount divided by the number of NFTs on the offering side, and handed to the counterparty's `generate_signed_transaction` as a plain (unsigned, non-committed) argument used only to solve the transfer program: [4](#0-3) [5](#0-4) 

Nowhere in this flow is `trade_prices_list` tied — via signature, announcement, or coin-amount check — to the amount the NFT seller actually receives through `Offer.notarize_payments`/`Offer.calculate_announcements`, which are keyed only on the requested payments and coin set, not on the declared trade price: [6](#0-5) [7](#0-6) 

Consequently, whoever assembles the final spend that completes the NFT ownership transfer (the offer taker, or any party constructing/re-solving the transfer-layer coin) fully controls `trade_prices_list` independent of the true consideration paid for the NFT — exactly analogous to the submitter freely choosing `tokenGasPriceFactor` independent of the values the user actually signed off on.

### Impact Explanation
A malicious offer taker (or anyone able to construct/solve the ownership-layer spend, e.g. by directly building a spend bundle rather than going through the standard `TradeManager`/`make_nft1_offer` path) can set `trade_prices_list` to zero or a token far below the real exchanged value. The `-10` (change owner) condition's royalty enforcement then only requires a correspondingly tiny (or zero) payment to the royalty/DID address, while the seller can still receive the full agreed price through the independent `requested_payments` settlement path. This siphons value away from the NFT creator's committed royalty stream — a real loss of funds to a party (the royalty beneficiary) who has no say in, and whose entitlement is supposed to be protected by, the on-chain transfer program.

### Likelihood Explanation
Reachable by any unprivileged wallet user/offer counterparty who constructs the coin spend that completes an NFT1 transfer; it requires only assembling a spend bundle with a chosen `trade_prices_list`, not any privileged access, malicious peer, or protocol-level exploit. The standard wallet code path (`make_nft1_offer`) computes this value heuristically rather than committing it cryptographically to the real trade, so the guard rail depends entirely on honest wallet software, not on-chain enforcement.

### Recommendation
Bind the royalty-determining trade price to the actual value exchanged rather than to an arbitrary solution parameter — e.g., derive/verify `trade_prices_list` against the `NotarizedPayment` amounts and nonce created by `Offer.notarize_payments`/`Offer.calculate_announcements` (which are already committed via puzzle announcements), so that the transfer program can only be solved with a trade price cryptographically tied to the payment the seller actually receives, closing the gap between the declared and real settlement amount.

### Proof of Concept
1. Seller creates and signs an NFT1 offer requesting `X` XCH for the NFT, using `TradeManager.make_nft1_offer`, which computes `trade_prices_list` off of `X` on the maker's side only for its own driver metadata (`chia/wallet/nft_wallet/nft_wallet.py:896-902`).
2. A taker/attacker, instead of using the standard `respond_to_offer` completion flow, constructs their own completion spend for the ownership-layer coin, supplying `create_ownership_layer_transfer_solution(new_did, new_did_inner_hash, trade_prices_list=[[0, OFFER_MOD_HASH]], new_puzhash)` (`chia/wallet/nft_wallet/nft_puzzle_utils.py:214-231`).
3. Because `NFT_TRANSFER_PROGRAM_DEFAULT` computes the required royalty announcement purely from the curried `royalty_percentage` and the attacker-supplied `trade_prices_list` (as validated by `chia/_tests/wallet/nft_wallet/test_nft_lifecycle.py:248-349`), the attacker only needs to satisfy a near-zero royalty announcement while still consummating the full-price settlement via the unrelated `requested_payments`/`OFFER_MOD` announcement path, resulting in the royalty beneficiary receiving little to no payment despite the NFT trading at its full agreed price.

    @staticmethod
    def notarize_payments(
        requested_payments: dict[bytes32 | None, list[CreateCoin]],  # `None` means you are requesting XCH
        coins: list[Coin],
    ) -> dict[bytes32 | None, list[NotarizedPayment]]:
        # This sort should be reproducible in CLVM with `>s`
        sorted_coins: list[Coin] = sorted(coins, key=Coin.name)
        sorted_coin_list: list[list[bytes32 | uint64]] = [coin_as_list(c) for c in sorted_coins]
        nonce: bytes32 = Program.to(sorted_coin_list).get_tree_hash()

        notarized_payments: dict[bytes32 | None, list[NotarizedPayment]] = {}
        for asset_id, payments in requested_payments.items():
            notarized_payments[asset_id] = []
            for p in payments:
                notarized_payments[asset_id].append(NotarizedPayment(p.puzzle_hash, p.amount, p.memos, nonce=nonce))

        return notarized_payments

    @staticmethod
    def calculate_announcements(
        notarized_payments: dict[bytes32 | None, list[NotarizedPayment]],
        driver_dict: dict[bytes32, PuzzleInfo],
    ) -> list[AssertPuzzleAnnouncement]:
        announcements: list[AssertPuzzleAnnouncement] = []
        for asset_id, payments in notarized_payments.items():
            if asset_id is not None:
                if asset_id not in driver_dict:
                    raise ValueError("Cannot calculate announcements without driver of requested item")
                settlement_ph: bytes32 = construct_puzzle(driver_dict[asset_id], OFFER_MOD).get_tree_hash()
            else:
                settlement_ph = OFFER_MOD_HASH

            msg: bytes32 = Program.to((payments[0].nonce, [p.as_condition_args() for p in payments])).get_tree_hash()
            announcements.append(AssertPuzzleAnnouncement(asserted_ph=settlement_ph, asserted_msg=msg))

        return announcements
