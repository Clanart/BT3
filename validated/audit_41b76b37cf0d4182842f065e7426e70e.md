### Title
Destination-side `_filled` gate is never checked before fill/cancel, allowing racing `RedeemEscrow`/`RefundEscrow` dispatches that strand solver payment or double-benefit the user - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_filled[commitment]` is the invariant Hyperbridge's cross-chain Intent Gateway relies on to guarantee an order is settled exactly once. Both destination-side entry points that write to this mapping — `_fillCrossChain` and `_cancelFromDest` — unconditionally overwrite `_filled[commitment]` and unconditionally dispatch a settlement message (`RedeemEscrow` or `RefundEscrow`) to the source chain, without first checking whether the commitment was already finalized. This mirrors the reported bug class exactly: a primary/gating mapping is mutated by one code path while a sibling code path that should consult (and be blocked by) that same mapping never does, so two independent, self-consistent-looking updates race each other and corrupt shared state.

### Finding Description
`_fillCrossChain` (evm/src/apps/intentsv2/ExtrinsicIntents.sol:89-171) does: [1](#0-0) 
It sets `_filled[commitment] = msg.sender` with no prior check of `_filled[commitment]`, pays the beneficiary output tokens, and dispatches a `RedeemEscrow` POST to the source chain instructing it to release the input escrow to the solver.

`_cancelFromDest` (evm/src/apps/intentsv2/ExtrinsicIntents.sol:240-267) does: [2](#0-1) 
After the deadline, it is callable by *anyone* (`if (order.deadline >= _blockNumber())` gates the caller check only *before* the deadline), sets `_filled[commitment] = order.user` with no check of the existing value, and dispatches a `RefundEscrow` POST to the source chain instructing it to refund the input escrow to the user.

Neither function reads `_filled[commitment]` before writing it or before dispatching its message. The doc comment on `_cancelFromDest` even claims it "Marks the order as filled (to prevent future fill attempts)" — but nothing ever checks that mark on the destination chain, so the mark is purely decorative there, exactly like `_autoDeployedVault` in the reported bug: written by one path, silently ignored by the other.

The only real replay guard lives on the *source* chain, in `_withdraw` (evm/src/apps/intentsv2/IntentsBase.sol:390-425): [3](#0-2) 
It gates on `_orders[commitment][token] == 0` (escrow already consumed), not on `_filled`. This does prevent a literal double-payout of the *same* input tokens, but it does not prevent the race: whichever message (`RedeemEscrow` or `RefundEscrow`) lands at the source first consumes the escrow and wins; the other reverts. Because message delivery order across two independently-dispatched ISMP requests is not guaranteed to match causal/destination order, this is a genuine non-privileged race, not a "malicious relayer" scenario — it is triggered purely by normal user/solver action timing near the order deadline.

### Impact Explanation
Concrete attack path (no malicious relayer/prover/admin required):
1. Order is close to its `deadline`. A solver calls `fillOrder` → `_fillCrossChain` fires: solver pays the beneficiary in full and a `RedeemEscrow` message is dispatched toward the source chain.
2. Before that `RedeemEscrow` message lands on the source chain, the user (or literally anyone, since post-deadline `_cancelFromDest` has no caller restriction) calls `cancelOrder` from the destination → `_cancelFromDest` fires: it does not see that `_filled[commitment]` is already set to the solver, and dispatches a `RefundEscrow` message toward the same source chain for the same commitment.
3. If `RefundEscrow` arrives at the source chain first, `_withdraw` consumes the escrow and pays it back to the user. When `RedeemEscrow` later arrives, `_orders[commitment][token] == 0` so it reverts — the solver, having already paid the beneficiary in full on the destination chain, receives nothing back. Funds are effectively stolen from the solver: the user gets both the solver's output tokens on the destination AND their original input tokens refunded on the source.
4. This is a fund-loss / wrong-beneficiary outcome achievable by any unprivileged user racing normal message delivery timing — squarely inside the bounty's "stealing or loss of funds" / "logic attacks" / "transaction manipulation" categories, and does not require a compromised relayer, prover, or admin (only ordinary asynchronous delivery of two independently dispatched cross-chain messages).

### Likelihood Explanation
The precondition is simply that a fill happens near an order's deadline and a cancel is triggered (by the user, or — post-deadline — by any third party) before the `RedeemEscrow` message is confirmed on the source chain. Since `_cancelFromDest` is explicitly permissionless after `deadline`, an attacker does not even need to be the order's user to trigger the race once the deadline has passed; they only need visibility into the mempool/relayer queue to time the cancel dispatch ahead of the redeem dispatch. This is a realistically triggerable, non-privileged condition, not merely theoretical.

### Recommendation
Gate both destination-side mutators on the existing `_filled` value before acting:
- In `_fillCrossChain`, revert with `Filled()`/`Cancelled()` if `_filled[commitment] != address(0)` before setting it.
- In `_cancelFromDest`, revert with `Filled()` if `_filled[commitment] != address(0)` before setting it and dispatching `RefundEscrow`.

This restores the invariant the code comments already assume exists, closing the race window entirely at the destination chain rather than relying solely on the source-chain escrow-zero check to sort out the aftermath.

### Proof of Concept
Conceptual sequence (no code changes needed to demonstrate, purely a call-ordering PoC against the existing contracts):
1. Deploy order with `deadline = D`.
2. At block `D`, Solver calls `fillOrder(order, fillOptions)` on the destination gateway → `_fillCrossChain` executes, solver transfers output tokens to beneficiary, `RedeemEscrow` dispatched to source.
3. Immediately after (same block or next), any address calls `cancelOrder(order, cancelOptions)` on the destination gateway → since `order.deadline >= _blockNumber()` is now false, no user-auth check applies; `_cancelFromDest` executes, overwrites `_filled[commitment]`, dispatches `RefundEscrow` to source.
4. Depending on which POST is processed first by the source-chain host (`EvmHost.dispatchIncoming`/`onAccept` → `_withdraw`), either the solver or the user is left without a corresponding payment — reproducible by controlling relative relayer submission order of the two independently dispatched messages, which is not enforced by the protocol.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );
