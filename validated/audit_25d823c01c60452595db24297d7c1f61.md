## Title
Gossip staked-CRDS purge timeout uses hardcoded legacy slot duration instead of the runtime's actual (variable) slot duration - ([File: core/src/epoch_specs.rs])

### Summary
The External Report's bug class is "one fixed staleness period applied uniformly to data whose real refresh rate varies," causing either premature rejection or excessive retention of stale data. Agave has a direct structural analog in `get_epoch_duration()` in `core/src/epoch_specs.rs`, which derives the CRDS-purge "epoch duration" for staked gossip records using a hardcoded constant `DEFAULT_MS_PER_SLOT` rather than the bank's actual, possibly-changed slot duration.

### Finding Description
`EpochSpecs::epoch_duration()` feeds directly into gossip's staked-node CRDS timeout calculation. It is computed as: [1](#0-0) 

```rust
fn get_epoch_duration(bank: &Bank) -> Duration {
    let num_slots = bank.get_slots_in_epoch(bank.epoch());
    // Gossip staked-CRDS timeout/purge intentionally follows the legacy
    // default slot duration, not the runtime slot duration.
    Duration::from_millis(num_slots.saturating_mul(DEFAULT_MS_PER_SLOT))
}
```
The comment makes the design choice explicit: it multiplies the number of slots in the epoch by the fixed constant `DEFAULT_MS_PER_SLOT`, not by the bank's live, per-slot `ns_per_slot`/`SlotParams` value.

This value is used by `CrdsTimeouts::new()` to compute `extended_timeout` (the timeout applied to staked validators' CRDS records): [2](#0-1) 

```rust
impl<'a> CrdsTimeouts<'a> {
    pub fn new(
        pubkey: Pubkey,
        default_timeout: u64,
        epoch_duration: Duration,
        stakes: &'a HashMap<Pubkey, u64>,
    ) -> Self {
        let extended_timeout = default_timeout.max(epoch_duration.as_millis() as u64);
        ...
```
and that timeout gates `Crds::find_old_labels()`, which purges CRDS entries (ContactInfo, Votes, EpochSlots, etc.) whose `wallclock`/`local_timestamp` age exceeds the timeout: [3](#0-2) 

Critically, this repository's own `runtime/src/slot_params.rs` shows that slot duration (`ns_per_slot`) is no longer a single global constant — it is a per-epoch/per-slot configurable parameter with distinct presets (`LEGACY_SLOT_PARAMS` at 400ms, `SLOT_PARAMS_350MS`, `SLOT_PARAMS_300MS`): [4](#0-3) 

`Bank` tracks and can transition between these live slot-time parameters (`slot_params_at_slot`, `ns_per_slot_at_slot`, `apply_slot_time_persistent_changes`), and even asserts snapshot consistency for `ns_per_slot`: [5](#0-4) [6](#0-5) 

So the network's real block-production cadence can now differ from the legacy 400ms assumption baked into `get_epoch_duration()`. This is exactly the report's bug class: a single fixed "heartbeat" assumption (400ms/slot) used to compute a staleness window for data (gossip CRDS records) whose real update cadence is governed by a different, variable parameter (actual `ns_per_slot`).

### Impact Explanation
If the cluster runs with a shortened slot time (e.g. `SLOT_PARAMS_300MS`), an epoch's real wall-clock duration is shorter than `DEFAULT_MS_PER_SLOT * num_slots` computed by `get_epoch_duration()`. The `extended_timeout` used for staked nodes' CRDS purging is then an overestimate of actual epoch length, meaning stale gossip data for staked nodes (e.g., ContactInfo whose validator is no longer live/responsive, or a still-listed CRDS entry that should be reaped) is retained far longer than one true epoch. This bloats/pollutes the CRDS table with data that should have been purged, feeding pull-request/pull-response filtering (`filter_pull_responses`, `filter_crds_values`) and push logic with stale data for longer than intended — a non-RPC resource/consistency degradation on unprivileged, ordinary nodes with no attacker required.

Conversely, if the cluster runs a slot time *longer* than legacy (hypothetically), `get_epoch_duration()` would underestimate the real epoch duration, causing the staked-node extended timeout to expire before the epoch it's meant to cover has actually elapsed — causing valid, still-active staked validators' CRDS records to be evicted from `find_old_labels`/`purge_active` prematurely mid-epoch, before their contact info is naturally refreshed on the next epoch boundary. This directly degrades gossip liveness/connectivity for a subset of validators cluster-wide, which is the closest local-code analog to the report's "PriceOracle rejects valid, not-actually-stale data because the staleness window doesn't match the real update cadence."

### Likelihood Explanation
This is not an attacker-triggered exploit — the code comment itself documents that the choice to use `DEFAULT_MS_PER_SLOT` instead of the runtime slot duration was intentional, which lowers confidence that this is unintentionally broken versus a deliberate (if fragile) simplification. The bug only manifests once the cluster actually activates a non-legacy slot-time preset (300ms/350ms) network-wide; I could not verify from local code search alone whether such a preset is currently activated/activatable on mainnet-class clusters or is still gated behind an unreleased feature. This uncertainty limits confidence in real-world exploitability today, but the structural mismatch (fixed constant vs. variable `SlotParams`) exists in the current code and exactly reproduces the report's misconfiguration pattern.

### Recommendation
- **Short term**: Compute `get_epoch_duration()` from the bank's actual, possibly-varying slot-time parameters (e.g. via `Bank::slot_range_duration_nanos`/`ns_per_slot_at_slot`, which already account for `SlotParams` transitions) instead of the hardcoded `DEFAULT_MS_PER_SLOT`, so the CRDS timeout tracks real network cadence.
- **Long term**: Add an automated/integration test that activates a non-legacy `SlotParams` preset and asserts that gossip's computed `epoch_duration` (and resulting `CrdsTimeouts::extended_timeout`) matches the actual epoch wall-clock time, catching any future drift between slot-time configuration and gossip timeout assumptions.

### Proof of Concept
Not independently verifiable from static code alone (no live cluster/harness available in this session). The existing unit test `test_get_epoch_duration` in `core/src/epoch_specs.rs` (lines 110–169) actually asserts the *buggy* behavior as correct — it checks that `get_epoch_duration()` always equals `num_slots * DEFAULT_MS_PER_SLOT`, regardless of what the bank's real `ns_per_slot`/`SlotParams` are configured to. A reproduction would be: construct a bank with `SLOT_PARAMS_300MS` active for an epoch, compute the real wall-clock epoch duration via `bank.slot_range_duration_nanos(epoch_start, epoch_end)`, and show it diverges from `get_epoch_duration(&bank)`'s `DEFAULT_MS_PER_SLOT`-based result — then trace that divergence through `CrdsTimeouts::new` into `Crds::find_old_labels` to demonstrate stale/at-risk CRDS entries are retained or purged inconsistently with real-elapsed epoch time.

    /// Find all the keys that are older or equal to the timeout.
    /// * timeouts - Pubkey specific timeouts with Pubkey::default() as the default timeout.
    pub fn find_old_labels(
        &self,
        thread_pool: &ThreadPool,
        now: u64,
        timeouts: &CrdsTimeouts,
    ) -> Vec<CrdsValueLabel> {
        // Given an index of all crd values associated with a pubkey,
        // returns crds labels of old values to be evicted.
        let evict = |pubkey, index: &IndexSet<usize>| {
            let timeout = timeouts[pubkey];
            // If the origin's contact-info hasn't expired yet then preserve
            // all associated values.
            let origin = CrdsValueLabel::ContactInfo(*pubkey);
            if let Some(origin) = self.table.get(&origin)
                && origin
                    .value
                    .wallclock()
                    .min(origin.local_timestamp)
                    .saturating_add(timeout)
                    > now
            {
                return vec![];
            }
            // Otherwise check each value's timestamp individually.
            index
                .into_iter()
                .map(|&ix| self.table.get_index(ix).unwrap())
                .filter(|(_, entry)| {
                    entry
                        .value
                        .wallclock()
                        .min(entry.local_timestamp)
                        .saturating_add(timeout)
                        <= now
                })
                .map(|(label, _)| label)
                .cloned()
                .collect::<Vec<_>>()
        };
        thread_pool.install(|| {
            self.records
                .par_iter()
                .flat_map(|(pubkey, index)| evict(pubkey, index))
                .collect()
        })
    }
