**Analysis:**

The proposed attack requires a race between a background `fetch`+checkout operation and a pending discard action, but this does not introduce a Desktop-specific vulnerability distinct from ordinary Git behavior:

1. `checkoutIndex` operates by design against whatever is *currently* in the git index at execution time — it is not supposed to be pinned to the index snapshot from when the discard dialog was opened. `git-store.ts`'s `discardChanges` explicitly re-reads `getIndexChanges(this.repository)` right before performing the reset/checkout, so it intentionally reflects the current index rather than a stale one, per the documented design in `docs/technical/discard-changes.md`. [1](#0-0) [2](#0-1) 

2. `checkoutIndex` only writes paths that are relative and originate from `getIndexChanges`/working-directory status, using `git checkout-index -f -u -q --stdin -z`; this is standard `checkout-index` usage and any protection against symlink-swap/path-escape attacks (e.g. a directory component becoming a symlink to escape the repo) is enforced by Git itself (`core.protectNTFS`, `core.protectHFS`, symlink checks in `checkout_entry`), not by Desktop-specific logic that could be bypassed here. [3](#0-2) 

3. Concurrent network operations (fetch/pull/push) on a repository are serialized via `withPushPullFetch`, which refuses to start a new fetch/pull if one is already in progress, reducing (though not eliminating in every code path) the window for the described race. [4](#0-3) 

4. No code was found that allows an attacker to control the *target path* of `checkout-index` differently from what the user selected in the discard-changes dialog — the paths passed to `checkoutIndex` come directly from the `WorkingDirectoryFileChange` list the user selected, not from remote-controlled data at execution time. [5](#0-4) 

The scenario describes a theoretical TOCTOU race on the underlying Git checkout mechanics (a known class of git-level symlink races, generally mitigated in modern Git versions) rather than an exploitable flaw introduced by GitHub Desktop's `checkoutIndex`/`discardChanges` code. No missing allow-list or path-validation bug specific to Desktop was identified, and the question does not name a concrete wrong value being used at the sink — it only speculates about a race without demonstrating that Desktop fails to serialize operations or that `checkout-index` writes to a path outside what the user selected.

    moveToTrash: boolean = true,

    const submodules = await listSubmodules(this.repository)

    for (const file of files) {
      const foundSubmodule = submodules.some(s => s.path === file.path)

      if (file.status.kind !== AppFileStatusKind.Deleted && !foundSubmodule) {
        if (moveToTrash) {
          try {

            )
          } catch (e) {
            if (askForConfirmationOnDiscardChangesPermanently) {
              throw new DiscardChangesError(e, this.repository, files)

            // chosen to always discard the changes permanently if trash failes.

          }
        }

export async function checkoutIndex(
  repository: Repository,
  paths: ReadonlyArray<string>
) {
  if (!paths.length) {
    return
  }

  const options = {
    successExitCodes: new Set([0, 1]),
    stdin: paths.join('\0'),
  }

  await git(
    ['checkout-index', '-f', '-u', '-q', '--stdin', '-z'],
    repository.path,
    'checkoutIndex',
    options
  )
}

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }
