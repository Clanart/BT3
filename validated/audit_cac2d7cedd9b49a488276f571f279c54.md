## Analog Identified: Front-Running a Predictable `CnStakingV4` Proxy Address to Inflate Effective Stake

### Title
Front-runnable CREATE2 CnStaking proxy address allows balance pre-funding that inflates validator stake weight — (`blockchain/system/permissionless.go`, `contracts/bindings/cnstakingv4factory/CnStakingV4Factory.go`, `kaiax/staking/impl/getter.go`)

### Summary
The C4 report describes a class of bug where a value derived from a *mutable, currently-observed* piece of on-chain state (`ownerOf(id)` for a transferable NFT) is used by privileged accounting logic instead of a fixed, creation-time value, and where the *future* address of that privileged state is deterministically predictable, allowing an unprivileged actor to front-run and pre-position value/ownership before the privileged role is assigned. Kaia's staking pipeline exhibits the same structural pattern: a validator's staking weight is computed directly from `address(stakingContract).balance` after the address is registered, and the `CnStakingV4` proxy address is deployed by `CnStakingV4Factory` using a deterministic (`CREATE2`) scheme, so its address is knowable before deployment/registration.

### Finding Description
`CnStakingV4Factory.deployCnStaking` / `deployCnStakingWithPD` deploy each validator's staking proxy as a `BeaconProxy`. The genesis/permissionless test harness explicitly documents that these proxies are created deterministically: [1](#0-0) 
which lists `"11+. CnStaking proxy * N - BeaconProxy, CREATE2 by Factory"`, confirming the proxy address is computed via `CREATE2` (a function of factory address, salt, and init code) rather than a fresh externally-owned nonce, meaning the address is fully predictable off-chain before the transaction that actually deploys it is even sent.

Once a `CnStakingV4` proxy is deployed and registered (via `AddressBook`/`AddressBookV2.createNode`), Kaia's staking module computes each validator's effective staking amount directly from the **native KAIA balance of that address**, with no adjustment for balance received prior to registration or deployment: [2](#0-1) [3](#0-2) 
This is the same structural weakness as `LienToken.transferFrom`: a downstream module (`PublicVault`/`StakingModule`) trusts whatever value/ownership currently sits at an address, without verifying that the value arrived only through the legitimate, expected deployment/registration flow.

**Attack path (unprivileged, single-transaction reachable):**
1. An attacker observes a `deployCnStaking(_owner)` / `deployCnStakingWithPD` call is about to be sent for a specific validator (e.g., via mempool monitoring of `CnStakingV4Factory` calls, analogous to monitoring `AstariaRouter.newPublicVault()` in the original report).
2. Because the proxy address is `CREATE2`-derived from the factory address and a deterministic salt/args (per the deployment scheme documented in the test comment above), the attacker can compute the future proxy address before it is deployed.
3. The attacker front-runs with a plain value-transfer transaction sending KAIA to that not-yet-deployed address. Since it is just an EOA-like empty account, any unprivileged sender can transfer value to it with `TxTypeValueTransfer`.
4. The proxy is deployed at that address and registered as the validator's official staking contract.
5. `kaiax/staking` reads `GetBalance` of the staking contract to compute `StakingAmounts`, which folds in the attacker's pre-sent balance as if it were the validator's legitimate stake, inflating the validator's weight in `WeightedRandom` proposer selection and reward distribution.

### Impact Explanation
Because `StakingInfo.StakingAmounts` directly feeds the `WeightedRandom` proposer-selection algorithm and consensus/reward computations (see `kaiax/staking/README.md` — "StakingInfo... primarily used to determine validator set and rewards distribution"), an attacker who can pre-fund a predictable, not-yet-deployed `CnStakingV4` proxy can:
- Artificially inflate a target validator's voting/proposer weight without that validator's consent, distorting consensus fairness (state divergence risk if different nodes observe pre-funding timed differently is not present here since it's on-chain state, but the *unauthorized* effect on stake-derived weight is the direct impact), or
- Grief a validator by forcing extra, unaccounted-for balance into their staking contract that inflates their apparent stake and thus reward share, effectively donating value the attacker cannot recover (since `CnStakingV4` custody logic likely doesn't allow withdrawal of unaccounted deposits) — a value-movement/manipulation vector reachable purely from a public unprivileged transaction sender.

This maps to the "unauthorized value movement" / "reward redirection" category permitted by the validation rules.

### Likelihood Explanation
This requires only:
- Monitoring the public mempool for `deployCnStaking`/`deployCnStakingWithPD` calls (or, in the permissionless bootstrap flow, knowledge of manager addresses used as `CREATE2` salts), and
- Sending an ordinary value-transfer transaction to a computed address before the factory's deployment transaction confirms.

No special privilege, validator role, or node access is required — it is achievable by any unprivileged public-RPC transaction sender performing standard front-running, which is a routinely observed technique on EVM-compatible chains. The main uncertainty (see below) is whether `CnStakingV4Factory`'s registration/initialization path rejects a proxy address that already holds a non-zero balance or has already been "touched"; I could not fully verify this because the Solidity source of `CnStakingV4Factory.sol` was not present in the indexed codebase (only Go bindings were available).

### Recommendation
- When computing a validator's staking amount, do not rely purely on `address(stakingContract).balance`; instead, track stake via the `CnStakingV4` contract's own accounted `staking`/`unstaking` state variables (which are incremented only through legitimate `delegate()`/`stake()` calls) rather than raw native balance, so that unsolicited transfers cannot be counted as stake.
- In `CnStakingV4Factory.deployCnStaking`/`deployCnStakingWithPD`, add a check that reverts (or sweeps/rejects) if the computed `CREATE2` address already holds a non-zero balance or non-empty code prior to deployment, preventing pre-funding griefing.
- Consider deriving proxy salts from values unpredictable to third parties (e.g., including the deploying transaction's future nonce commitment or a random beacon) to reduce the window for address prediction.

### Proof of Concept
Concrete step-by-step (conceptual, given available code):
1. Off-chain: compute the deterministic `CnStakingV4` `BeaconProxy` address that `CnStakingV4Factory.deployCnStaking(_owner)` will produce for a known upcoming validator `_owner`, using the `CREATE2` scheme confirmed by the genesis test harness comment `"CnStaking proxy * N - BeaconProxy, CREATE2 by Factory"` at [1](#0-0) .
2. Send a normal `TxTypeValueTransfer` (or legacy tx) from any account to that computed address before the real `deployCnStaking` transaction lands.
3. After deployment/registration, call the staking module's `GetStakingInfo` (as exercised by [2](#0-1)  and tested in [4](#0-3) ) and observe that `StakingAmounts` for that validator includes the attacker's pre-sent balance.

**Uncertainty:** I was unable to retrieve `contracts/*/CnStakingV4Factory.sol` source (only auto-generated Go bindings were indexed), so I could not directly confirm whether the factory's `initialize`/`deployCnStaking` logic includes any check that would reject or account for a pre-existing balance at the computed proxy address before initialization. This should be verified directly in the source before treating this as fully confirmed; if such a check exists, the practical impact would be null. Given index size limits, a full-repository Devin session would be needed to inspect the actual `CnStakingV4Factory.sol` and `CnStakingV4.sol` implementation to close this gap.

func parsePermissionlessCallResult(num uint64, profiles []multicall.Profile, amounts []*big.Int, kefAddr, kifAddr, kpfAddr common.Address, clRes clRegistryResult) (*staking.StakingInfo, error) {
	if len(profiles) == 0 {
		return emptyStakingInfo(num), nil
	}
	if len(profiles) != len(amounts) {
		logger.Error("length of profiles and amounts differ", "sourceNum", num, "profileLen", len(profiles), "amountLen", len(amounts))
		return nil, staking.ErrAddressBookResult
	}
	if len(clRes.NodeIds) != len(clRes.ClPools) || len(clRes.NodeIds) != len(clRes.StakingAmounts) {
		logger.Error("length of CL registry result fields differ", "sourceNum", num, "nodeLen", len(clRes.NodeIds), "poolLen", len(clRes.ClPools), "amountLen", len(clRes.StakingAmounts))
		return nil, staking.ErrCLRegistryResult
	}

	nodeIds := make([]common.Address, 0, len(profiles))
	stakingContracts := make([]common.Address, 0, len(profiles))
	rewardAddrs := make([]common.Address, 0, len(profiles))
	stakingAmounts := make([]uint64, 0, len(profiles))
	for i, p := range profiles {
		if !valset.NodeState(p.State).IsRewardEligible() {
			continue
		}
		nodeIds = append(nodeIds, p.NodeId)
		stakingContracts = append(stakingContracts, p.StakingContract)
		rewardAddrs = append(rewardAddrs, p.RewardAddress)
		stakingAmounts = append(stakingAmounts, new(big.Int).Div(amounts[i], big.NewInt(params.KAIA)).Uint64())
	}
