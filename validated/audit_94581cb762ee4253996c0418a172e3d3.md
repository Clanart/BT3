### Title
Deep-link protocol dispatch relies on legacy `url.parse` while other URL-consuming paths use WHATWG `URL`, creating a parser-interpretation conflict for attacker-controlled links - (File: app/src/lib/parse-app-url.ts)

### Summary
The seed report's broken invariant is: two different components decode the same untrusted input (calldata / a URL) with different parsing rules, so a value classified one way by the "gatekeeper" component is classified a different way by the component that actually acts on it. GitHub Desktop has a structurally identical setup for `x-github-client://` deep links: routing of privileged actions (`oauth` vs `open-repository-from-url`) is decided by the deprecated, legacy Node `url` module, while the surrounding process (OS protocol launch, Windows CLI validation, and other URL-comparison code elsewhere in the same codebase) uses the modern WHATWG `URL`.

### Finding Description
`parseAppURL` is the single dispatcher that decides whether an incoming protocol URL is treated as an OAuth callback (privileged: exchanges `code`/`state` for a token via `appStore._resolveOAuthRequest`) or as an "open repository from URL" request. It parses the attacker-controlled string with the legacy, deprecated `url` module: [1](#0-0) [2](#0-1) 

This URL originates from fully untrusted, attacker-controllable sources: any link a user clicks (macOS forwards it straight from the OS via `open-url` with **no validation at all**): [3](#0-2) 

On Windows, the raw command-line argument is instead pre-validated with the WHATWG `new URL(arg)` constructor before the same raw string is forwarded to `handleAppURL` → `parseAppURL`: [4](#0-3) 

So the same string can be judged "well-formed" by one URL-parsing implementation (WHATWG `URL`, used for gatekeeping on Windows, and implicitly assumed correct by the OS-level scheme launch on macOS) and then be decoded into a *different* hostname/pathname/query by the legacy `url.parse(url, true)` implementation that actually performs the security-relevant dispatch decision (`oauth` vs `openrepo` vs `unknown`). This is precisely the "interpretation conflict" class from the seed report: a router/gatekeeper and the actual consumer disagree on how to decode the same bytes, and the gap between them is exploitable. Elsewhere in the same codebase, URL comparison logic already uses the same legacy `url` import for a different purpose (`import * as URL from 'url'` in `update-remote-url.ts`), confirming the codebase mixes both parser families for equivalent-looking URL strings without a single canonical parser being enforced: [5](#0-4) 

### Impact Explanation
If an attacker crafts a deep link whose hostname/path is interpreted as `oauth` (or `openrepo`) by the legacy parser but would be classified differently (or rejected) under WHATWG `URL` semantics, they can:
- Force the app into the privileged `oauth` code path with attacker-chosen `code`/`state` query values (`getQueryStringValue` pulls `code`/`state` straight from the legacy-parsed query string) and reach `appStore._resolveOAuthRequest`, or
- Smuggle values through the `open-repository-from-url` path (`url`, `branch`, `pr`, `filepath`) that a stricter/standard parser would have rejected as malformed.

This matches the "Valid Impact" bar: the attacker only needs to get the user to click a link (a normal, expected Desktop workflow, not social engineering or local access), and the result is misrouted, security-relevant dispatch of an OAuth/token exchange or repository-open action.

### Likelihood Explanation
Medium. Exploitation requires finding a concrete URL string where legacy `url.parse` and WHATWG `URL` disagree on hostname/pathname boundaries for a non-special (custom) scheme like `x-github-client:`/`x-github-desktop-auth:` — a documented category of parser-differential bugs (e.g., differing treatment of backslashes, repeated slashes, or userinfo `@` delimiters for non-`http(s)` schemes). I was not able to execute code in this environment to enumerate a concrete byte-for-byte divergent payload, so the exact trigger string is unverified; this should be validated with a small differential-fuzzing pass against Node's legacy `url.parse` vs `URL` for the app's registered custom schemes.

### Recommendation
- Replace `import * as URL from 'url'; URL.parse(url, true)` in `app/src/lib/parse-app-url.ts` with the WHATWG `URL` API (`new URL(url)` + `url.searchParams`), matching the parser already used for validation on the Windows launch path.
- Ensure macOS's `open-url` handler performs the same validation/normalization before calling `parseAppURL`, rather than trusting the OS-forwarded string unmodified.
- Add an explicit allow-list check on `parsedURL.protocol` against `possibleProtocols` inside `parseAppURL` itself so the dispatcher and the launcher agree on scheme validity, not just hostname.

export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  public async dispatchURLAction(action: URLActionType): Promise<void> {
    switch (action.name) {
      case 'oauth':
        await this.appStore._resolveOAuthRequest(action)

        if (__DARWIN__) {
          // workaround for user reports that the application doesn't receive focus
          // after completing the OAuth signin in the browser
          const isFocused = await isWindowFocused()
          if (!isFocused) {
            log.info(
              `refocusing the main window after the OAuth flow is completed`
            )
            window.focus()
          }
        }
        break

      case 'open-repository-from-url':
        this.openRepositoryFromUrl(action)
        break

      default:
        const unknownAction: IUnknownAction = action
        log.warn(
          `Unknown URL action: ${
            unknownAction.name
          } - payload: ${JSON.stringify(unknownAction)}`
        )
    }
  }
