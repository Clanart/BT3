### Title
Attacker-Controlled Refund Address Produces Unbroadcastable / Unbuildable Transaction, Permanently Locking the Deposited Input - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts payment destinations as raw `ScriptBuf`s and validates only the payment amount (`>= DUST`) and the aggregate transaction weight. It performs no validation that the destination script is standard or relayable. When an untrusted party supplies the destination script — e.g., the refund address parsed from deposit metadata and turned into a `Payment` — they can pick a script that either (a) forces `TransactionError::TooLargeTransaction`, making plan construction fail outright, or (b) yields a syntactically valid but non-standard transaction (oversized script, provably-unspendable/`OP_RETURN`-style script carrying value, disallowed opcodes) that no Bitcoin node will relay or mine. In both cases the input committed to the plan can never be paid out — the exact same "malicious recipient blocks the final transfer" DoS class as the Ethereum report, expressed in UTXO terms.

### Finding Description
The destination of a payment is taken verbatim: [1](#0-0) 

The only checks applied to the payment are: [2](#0-1) [3](#0-2) 

There is no standardness check on `script_pubkey` — no maximum script size, no rejection of non-relayable templates, no requirement that the script correspond to a known address type (P2TR, P2WPKH, etc.). Bitcoin's standardness policy rejects transactions whose outputs carry scripts exceeding ~10 KB, scripts containing disabled/unassigned opcodes, or provably unspendable outputs carrying value. Because the weight check (`MAX_STANDARD_TX_WEIGHT` ≈ 400,000 WU) permits payment scripts up to ~100 KB, a large window of scripts exists that `SignableTransaction::new` accepts yet the network will never accept.

Two failure modes:

1. **Construction failure**: a refund address whose script pushes total weight over `MAX_STANDARD_TX_WEIGHT` (≈ 100 KB script) makes `new` return `TooLargeTransaction`, so no transaction can ever be built for the plan spending that input.
2. **Signed-but-unbroadcastable**: a script under the weight limit but non-standard (e.g., a large push, `OP_RETURN` carrying value, or invalid opcodes) produces a valid `SignableTransaction`; `TransactionSignMachine::sign`/`TransactionSignatureMachine::complete` will happily produce a fully signed transaction committing `Prevouts::All`, and it will be rejected by every node's mempool. The consumed input is still marked spent by the plan. [4](#0-3) 

Note the API boundary: `payments: &[(ScriptBuf, u64)]` is the raw destination encoding — any caller feeding an attacker-influenced address (refund addresses, withdrawal destinations) flows untrusted bytes straight into `script_pubkey`.

### Impact Explanation
A single malicious deposit with a hostile refund `script_pubkey` permanently blocks spending of that deposited input (and, in batched plans, any co-spent inputs): either transaction construction errors forever, or the multisig produces a signed transaction no relay will accept. Unlike the Ethereum original where a revert could be caught, failure here is discovered only at broadcast time, after the FROST signing round has completed. The deposited funds are frozen — reported received by the scanner (`Scanner::scan_transaction` matches only `script_pubkey`, so the deposit itself succeeds) but never spendable or refundable.

### Likelihood Explanation
Any party able to set their own refund/destination script (standard refund flow) can trigger this with a crafted `ScriptBuf` — no collusion or privileged position needed. The requirement is only that the caller path pass attacker-controlled address bytes into `payments`, which is the documented shape of the refund/withdrawal flow.

### Recommendation
Validate payment destinations at construction time in `SignableTransaction::new`: require each `script_pubkey` to match a known standard template (e.g., via `script.is_p2tr() || is_p2wpkh() || ...`, or `bitcoin::policy`/`Address` round-trip), enforce a maximum script size consistent with standardness (~10 KB), and reject `OP_RETURN` outputs carrying nonzero value. Treating destinations as opaque scripts should be an explicitly internal-only API.

### Proof of Concept
1. Attacker deposits to the multisig's external address and encodes a refund address whose `script_pubkey` is, e.g., `ScriptBuf` = 50 KB of `OP_NOP` pushes (non-standard but under `MAX_STANDARD_TX_WEIGHT`), or alternatively > 100 KB to force `TooLargeTransaction`.
2. `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-213`) matches the deposit and emits a `ReceivedOutput`.
3. A refund plan is built with `payments = vec![(attacker_script, amount)]`.
4. Either `SignableTransaction::new` returns `Err(TooLargeTransaction)` — plan unbuildable — or a `SignableTransaction` is produced, the threshold signs it via `TransactionSignMachine::sign`/`complete`, and the resulting `Transaction` is rejected by all Bitcoin nodes as non-standard. The deposited input can never be recovered through this flow.
