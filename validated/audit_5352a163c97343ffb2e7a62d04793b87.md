## Analysis Summary

The TinyWeb report's failed invariant is: **attacker-controlled string data (HTTP header values) is written verbatim into a structured downstream format (CGI environment variables) without rejecting/escaping control characters (`CR`, `LF`, `NUL`) or their encoded forms, allowing the value to break out of its intended field boundary and inject additional structured content.**

Searching the Protobuf codebase for this bug class across every text-emitting serializer (C++ `TextFormat`/JSON, Java `TextFormatEscaper`/`JsonFormat`, C# `JsonFormatter`, upb `jsonenc`/`txtenc`, Python `text_encoding`), every single implementation explicitly scans for and escapes ASCII control characters (`< 0x20`), quotes, and backslashes before emitting a string into JSON or TextFormat output: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

One exception exists, however, in the **pure-PHP** implementation of `Any` JSON serialization: `Message::serializeToJsonStream()` writes the `type_url` field into the `"@type"` JSON key **raw, with no escaping at all**, unlike every other string field (which goes through `GPBJsonWire::serializeFieldToStream`) and unlike every other WKT branch in the same function (`FieldMask`, `Duration`, `Timestamp` all go through PHP's `json_encode`): [5](#0-4) 

`type_url` is an ordinary `string` field on `Any` — it is only required to be valid UTF‑8 on the wire; nothing in the binary parser or in `AnyBase::unpack()`/`pack()` restricts its byte content to the URL charset described in `any.proto`'s comments (that restriction is documentation-only and enforced nowhere in code I could find for the PHP path): [6](#0-5) [7](#0-6) 

### Title
JSON Injection via Unescaped `Any.type_url` in PHP `serializeToJsonStream` - (File: php/src/Google/Protobuf/Internal/Message.php)

### Summary
The pure-PHP Protobuf runtime's JSON serializer for `google.protobuf.Any` writes the attacker-controlled `type_url` string field directly into the output JSON buffer via `writeRaw()`, without JSON-escaping quotes, backslashes, or control characters. Every other string-valued field in the same codebase (including every other WKT special case in the same function) is escaped before being embedded in JSON. An `Any` message containing a `type_url` value with an embedded `"` (and forged content after it) can break out of the `"@type"` JSON string literal and inject arbitrary sibling keys/values into the surrounding JSON object.

### Finding Description
`Message::serializeToJsonStream()` special-cases `Any` and manually assembles the JSON object instead of delegating to the generic field serializer used for regular string fields: [8](#0-7) 
It calls `$output->writeRaw($this->getTypeUrl(), strlen($this->getTypeUrl()))` between two literal `"` bytes with no call into `GPBJsonWire`'s string-escaping logic. `type_url` is populated by an ordinary binary/ProtoJSON parse of a `string` field on `Any` — the only invariant enforced anywhere for `Any.type_url` at parse time is UTF‑8 validity (consistent with every other `string` field), not the "alphanumeric + limited punctuation" URL charset that is only described as a comment in `any.proto`: [7](#0-6) 
`AnyBase::unpack()`/`pack()` in the PHP runtime only checks a string prefix match (`substr(...) != TYPE_URL_PREFIX`) and does not sanitize or reject unusual bytes such as `"`, `\`, or control characters: [9](#0-8) 
Because the value is written with `writeRaw` (a direct byte-append, same primitive used for pre-formatted binary/JSON fragments elsewhere) rather than through the escaping helper used for all other JSON string emission in this codebase (`GPBJsonWire::serializeFieldToStream`, or PHP's own `json_encode` used for `Duration`/`Timestamp`/`FieldMask` in the very same function), the control-character/quote-escaping invariant that holds everywhere else in Protobuf's JSON encoders is broken specifically for this one field on this one code path.

### Impact Explanation
This is analogous to the TinyWeb bug: an attacker-controlled value crosses from one parser's trust boundary (the binary Protobuf wire format, which allows arbitrary UTF‑8 bytes including `"` and control characters in a `string` field) into a second structured format (JSON) without the receiving code enforcing/escaping the second format's delimiters. A consuming PHP application that calls `Any::serializeToJsonStream()` (directly, or via `JsonEncode`/`Message::serializeToJsonString` on a message that embeds an `Any`) and then parses or logs the resulting JSON can have extra JSON keys injected, alter or spoof sibling values, or in specific consuming contexts change how the JSON document is interpreted downstream. It does not on its own achieve memory corruption, but it does violate protobuf's documented invariant that JSON output produced by its own serializer is always valid, faithfully-encoded JSON, and it is the closest true analog to the "value crosses a delimiter boundary due to unescaped control character" bug class described in the report.

### Likelihood Explanation
Reachable purely through the public, supported `Any::pack()`/binary-`mergeFromString()` + `serializeToJsonString()` API surface using only a bounded, well-formed binary Protobuf payload (an `Any` submessage with a crafted `type_url` string field) — no privileged access, hostile schema, or plugin is required. The only precondition is that the pure-PHP runtime (rather than the C extension, which uses upb's `jsonenc_string`, a properly escaping path) is in use; the PHP C-extension/upb path is not affected because it always calls the escaping `jsonenc_string`/`jsonenc_stringbody` helpers, as seen for comparison: [10](#0-9) 

### Recommendation
In `php/src/Google/Protobuf/Internal/Message.php`, route the `type_url` write in the `Any` branch of `serializeToJsonStream()` through the same JSON-string-escaping routine used for ordinary string fields (`GPBJsonWire`'s escaping logic, or `json_encode($this->getTypeUrl())` as is already done for `Duration`/`Timestamp` in the same function) instead of calling `writeRaw()` on the unescaped value.

### Proof of Concept
Conceptual reproduction using only the public PHP API (pure-PHP runtime, no C extension):
1. Construct any message type, serialize it to bytes (`$msg->serializeToString()`).
2. Build an `Any` message and manually set `type_url` to a value containing a double quote, e.g. `type.googleapis.com/Foo","injected":"1` and set `value` to the serialized bytes (this is possible because `type_url` is only UTF‑8 validated on the wire/at the setter, not charset-restricted).
3. Call `$any->serializeToJsonStream($output)` (or embed `$any` in a parent message and call `serializeToJsonString()`).
4. Observe the emitted JSON contains an injected `"injected":"1"` key-value pair outside the intended `"@type"` string literal, because `getTypeUrl()`'s bytes were written via `writeRaw()` unescaped at [11](#0-10) , in contrast to the escaped handling every other string field receives.

I was not able to execute this PoC in a live PHP environment (no filesystem/interpreter access in this mode), so this should be verified with an actual run before treating it as confirmed; the code-level evidence (unescaped `writeRaw` call versus escaped handling everywhere else) is, however, directly citable and consistent across the files I examined.
