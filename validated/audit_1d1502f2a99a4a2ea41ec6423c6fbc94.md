### Title
Improper path-prefix check in `resolveWithin()` allows sibling-directory escape outside the repository root - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is Desktop's central guard used to make sure a repository-relative (or attacker-influenced) path cannot be used to read or reveal a file outside a repository's working directory. The final containment check uses a bare string `startsWith()` comparison between the resolved real path and the real root path, without requiring a path-separator boundary. This is the classic CWE-22 "prefix without separator" bug: a path that resolves to a *sibling* directory whose name has the repository directory name as a prefix (e.g. `myrepo-evil` vs `myrepo`) passes the check even though it is not actually inside the repository.

### Finding Description
`resolveWithin()` / `_resolveWithin()` computes the final containment check as: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`realResolved.startsWith(realRoot)` is true for any path that merely shares the root path as a string prefix — it does not require the next character to be a path separator. Given `realRoot = /Users/victim/Documents/GitHub/myrepo`, a resolved path of `/Users/victim/Documents/GitHub/myrepo-evil/secret.txt` also satisfies `startsWith`, even though `myrepo-evil` is a completely different, sibling directory.

This can be triggered with a purely **relative** path segment, so it is not blocked by upstream `isAbsolute()` guards. For example, `resolveWithin('/Users/victim/Documents/GitHub/myrepo', '../myrepo-evil/secret.txt')`:
- `normalizedRelative = '../myrepo-evil/secret.txt'`
- `resolved = resolve(root, normalizedRelative) = '/Users/victim/Documents/GitHub/myrepo-evil/secret.txt'`
- `realResolved.startsWith(realRoot)` → `true` (bug) → function returns the resolved path instead of `null`.

The one caller that does pre-filter *absolute* filepaths is `openRepositoryFromUrl()`: [2](#0-1) 

That `isAbsolute(filepath)` check only stops absolute-path payloads; it does nothing to stop the `../sibling-prefix/...` relative traversal shown above, so a crafted deep link (`x-github-client://openRepo/<repo-url>?filepath=../<localFolderName>-something/secret.txt`) can still cause `shell.showItemInFolder()` to reveal a file outside the cloned repository, provided a sibling folder exists whose name begins with the repository's local folder name.

The same primitive is reused by `buildConflictContext()` to gate reads of merge-conflict file contents before sending them to Copilot: [3](#0-2) 

Existing unit tests only cover `..`-only traversal and symlink escapes, not the sibling-prefix case, so the bug is unguarded and untested: [4](#0-3) 

### Impact Explanation
`resolveWithin()` is the app's primary "is this path safely inside the repo" invariant, analogous to `safeTransferFrom()`'s "is the recipient capable of receiving this" invariant — a cheap safety check that downstream code trusts implicitly. When the check is bypassed, a path outside the intended repository is treated as validated and passed on to file-system operations (`shell.showItemInFolder`, `readFile` for conflict content). Depending on the caller, this can result in disclosure of arbitrary sibling-directory contents (e.g. another cloned repository containing credentials, `.env` files, or private code) via a crafted deep link or crafted repository/merge state, without any local access, admin rights, or pre-existing malware.

### Likelihood Explanation
Exploitation requires: (1) a caller that passes attacker-influenced relative path segments into `resolveWithin` (the `filepath` deep-link parameter qualifies, and merge-conflict `file.path` values are influenced by whatever branch/remote content is being merged), and (2) a sibling directory on disk whose name has the repo's directory name as a string prefix. Directory-naming collisions of this kind are plausible in typical "GitHub" folders (Desktop's default clone location groups all repos under one parent, and users/organizations commonly have differently-suffixed repo names, e.g. `foo` and `foo-docs`, `foo` and `foo.wiki`). The deep-link vector is user-clickable and requires no other unnatural steps, satisfying the "link the user clicks" impact category. Likelihood is moderate: it needs pre-existing sibling directories with the right prefix relationship, but that is realistic in real-world Desktop usage rather than a contrived setup.

### Recommendation
Fix the containment check in `_resolveWithin()` (`app/src/lib/path.ts`) to require a path-separator boundary (or equality) rather than a raw string prefix, e.g.:
```diff
- return realResolved.startsWith(realRoot) ? resolved : null
+ return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
+   ? resolved
+   : null
```
(using the platform-appropriate separator from the `options` argument for the win32/posix variants). Add regression tests covering sibling-directory-prefix payloads (e.g. `resolveWithin('/root/myrepo', '../myrepo-evil/secret.txt')` must return `null`) alongside the existing `..`/symlink tests.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import { mkdir, mkdtemp, writeFile } from 'fs/promises'
import { join } from 'path'
import { tmpdir } from 'os'

// Simulates: /Users/victim/Documents/GitHub/myrepo  and a sibling
// /Users/victim/Documents/GitHub/myrepo-evil/secret.txt
const parent = await mkdtemp(join(tmpdir(), 'gh-'))
const repoRoot = join(parent, 'myrepo')
const evilDir = join(parent, 'myrepo-evil')
await mkdir(repoRoot)
await mkdir(evilDir)
await writeFile(join(evilDir, 'secret.txt'), 'TOP SECRET')

// Attacker-controlled relative filepath (e.g. from a deep link
// x-github-client://openRepo/...&filepath=../myrepo-evil/secret.txt)
const result = await resolveWithin(repoRoot, '../myrepo-evil/secret.txt')

console.log(result)
// BUG: prints the absolute path to secret.txt instead of null,
// because '/parent/myrepo-evil/secret.txt'.startsWith('/parent/myrepo') === true
```
In `dispatcher.ts`'s `openRepositoryFromUrl`, since the payload above is relative (not absolute), it bypasses the `isAbsolute(filepath)` guard and reaches `resolveWithin`, which incorrectly returns a non-null path, causing `shell.showItemInFolder(resolved)` to reveal the sibling file to the user/attacker flow instead of being rejected as "outside the repository root."
