### Title
Unchecked low-level `IERC20.transfer` return value in `IntentGatewayV2::withdraw` and `SweepDust` permanently traps escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` imports and enables `SafeERC20` (`using SafeERC20 for IERC20;`) but does not use it inside `withdraw()` or the `SweepDust` branch of `onAccept()`. Instead of `safeTransfer`, both paths issue a raw low-level `.call` with the `transfer` selector and only check that the *call itself* did not revert, never decoding the boolean return value the ERC-20 standard requires. ### Finding Description
`withdraw()` is invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests, and from `onGetResponse()` for cancellation checks. For each escrowed ERC-20 token it does:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```

`success` here reflects only whether the external call reverted — it does not reflect the token contract's own returned boolean. Many standard-compliant ERC-20 tokens (e.g. tokens following the "return false instead of reverting" pattern permitted by EIP-20) return `false` on a failed transfer rather than reverting. In that case the low-level `.call` succeeds (`success == true`), the code proceeds as if the transfer happened, decrements `_orders[commitment][token]`, and (for the finalize path) marks `_filled[commitment] = beneficiary` and emits `EscrowReleased`/`EscrowRefunded` — even though no tokens were actually delivered.

By contrast, the canonical (non-Tron) implementation of the exact same escrow-release logic in `IntentsBase._withdraw` correctly uses `SafeERC20.safeTransfer`, which decodes and enforces the boolean return value: [4](#0-3) 

The Tron file has the exact same `SafeERC20` import and `using` declaration available but bypasses it for `withdraw()` and `SweepDust`, reintroducing the classic "unchecked ERC-20 return value" flaw in a bridge settlement path.

### Impact Explanation
Once `onAccept`/`onGetResponse` processes the withdrawal, the escrow accounting (`_orders[commitment][token]`) is decremented and the order is marked filled/refunded — this is the on-chain "receipt" that the corresponding side of the bridge relies on to consider the transfer complete. If the underlying token silently returns `false`:
- The rightful beneficiary (user or solver) never receives their tokens.
- The tokens remain stuck inside the `IntentGatewayV2` contract balance.
- Because the commitment is already marked filled/refunded and escrow debited, there is no retry path — the same `WithdrawalRequest` cannot be replayed, and no other function grants access to that specific stranded balance.

This is a direct, irrecoverable loss of user/solver funds, matching the external report's core invariant break ("assets moved into a state where they cannot be moved out again, because the code that would normally provide a recovery/transfer capability doesn't validate success").

### Likelihood Explanation
No malicious relayer, prover, or admin action is required. The trigger is simply: a legitimate cross-chain intent order whose escrowed input token is a non-reverting ERC-20 (a real, common token behavior class, not a compromised token). Reaching this path only requires a normal solver/user completing an intent flow, which is entirely within the unprivileged, public entry points (`placeOrder` → cross-chain settlement → `onAccept`/`onGetResponse` → `withdraw`). The `SweepDust` variant is reachable via ordinary governance-initiated but externally-triggered dust sweeps for any registered token, and shares the identical unchecked-call pattern.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` invocations in `withdraw()` and the `SweepDust` branch of `onAccept()` with `IERC20(token).safeTransfer(beneficiary, amount)` (and `safeTransfer` for the transaction-fee payout), consistent with `IntentsBase._withdraw` and `_sweepDust` in the non-Tron implementation. This ensures a `false` return value reverts the transfer instead of being silently accepted as success.

### Proof of Concept
1. Deploy an ERC-20 mock whose `transfer(address,uint256)` returns `false` on failure (e.g., insufficient balance/blacklist) instead of reverting — this mirrors real-world non-reverting ERC-20 semantics.
2. Place a cross-chain (or same-chain) intent order in `IntentGatewayV2` (Tron variant) using this token as an input, escrowing `amount` tokens in the gateway.
3. Trigger the settlement path so `onAccept`/`onGetResponse` calls `withdraw(body, false)` with `token.transfer` engineered to return `false` (e.g., temporarily blacklist the beneficiary if the mock supports it, or drain the contract's own balance beforehand via a second interaction) while the low-level `.call` itself still succeeds.
4. Observe: `_orders[commitment][token]` is decremented to zero, `_filled[commitment]` is set, `EscrowReleased`/`EscrowRefunded` is emitted — yet `token.balanceOf(beneficiary)` remains unchanged and the tokens remain in `IntentGatewayV2`'s balance with no function able to move them back out to the beneficiary.

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");

                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {

        if (isRefund) {

        } else {
