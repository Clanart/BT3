## Title
Tron `IntentGatewayV2.placeOrder()` credits escrow with a pre-transfer nominal amount, allowing under-collateralized escrow and loss of pooled funds for fee-deducting ERC-20 inputs — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
This is the direct local analog of the M-21 report: the Tigris bug credited `OpenInterest` using the pre-fee margin instead of the actual (post-fee) position size. In the Tron fork of `IntentGatewayV2`, the escrow ledger `_orders[commitment][token]` is credited using a value derived from the *pre-transfer, nominal* `order.inputs[i].amount`, while the actual token balance the contract custodies after `safeTransferFrom` is never verified to match. For any ERC-20 input whose transferred amount can differ from the nominal amount requested (fee-on-transfer tokens, tokens with transfer-time deductions/burns, blacklist-partial transfers, etc.), the contract can register more escrowed value than it actually holds — an accounting overstatement identical in kind to the OI-overstatement bug, but here it directly threatens custodial solvency of pooled escrow funds.

## Finding Description
In `placeOrder()`, the reduced (post-protocol-fee) input amounts used for escrow accounting are computed **before** any token transfer occurs, straight from the nominal `order.inputs[i].amount` supplied by the caller: [1](#0-0) 

Then, in the non-predispatch branch, the ERC-20 transfer is executed with no verification that the amount actually received equals what was requested: [2](#0-1) 

The escrow ledger is incremented by `reducedInputs[i].amount` (line 457) — a value derived solely from the nominal amount computed at lines 356–358, not from any post-transfer balance measurement. Contrast this with the corrected mainline EVM contract, which explicitly re-derives the input amount from the actual balance delta after transfer, specifically to defend against fee-on-transfer tokens: [3](#0-2) 

and only computes protocol fees / escrow amounts afterward, from the *actual received* amount: [4](#0-3) 

The mainline contract's test suite explicitly documents and verifies this exact hazard class: [5](#0-4) 

The Tron contract has no equivalent balance-delta check anywhere in its `placeOrder()` — the fee/escrow amount is fixed from the nominal amount at the top of the function, before the transfer even happens, and is never reconciled with what the contract actually received.

## Impact Explanation
`_orders[commitment][token]` is the sole source of truth used later for filling (`fillOrder`), redemption (`RedeemEscrow` via `onAccept`/`withdraw`), and cancellation/refund payouts. If the escrow ledger for one order records more tokens than the contract actually holds (because the transferred token deducted a fee/burn during `transferFrom`), the contract becomes under-collateralized: it owes more in aggregate liabilities (sum of all `_orders[...]` entries) than its actual token balance. Because escrow tokens for all orders sit in the same shared contract balance, this shortfall is paid out of other users' escrowed funds — whichever order settles/redeems/cancels last will find the pool short, resulting in real loss of user funds. This satisfies the bounty gate's "stealing or loss of funds" / "false state acceptance" criteria and requires no malicious relayer, prover, or admin — only an unprivileged user placing an order with a token whose transfer semantics deduct a fee.

## Likelihood Explanation
`placeOrder()` accepts an arbitrary `TokenInfo.token` address supplied by the caller with no on-chain allow-list check visible in this function, so any attacker (or even an unwitting integrator) using a fee-on-transfer/deflationary/rebasing ERC-20 as an input token triggers the discrepancy on every single order placement involving that token — not a rare edge case. The mainline EVM contract's author clearly recognized this exact class of risk (hence the balance-delta fix and dedicated test suite), which strongly indicates the Tron variant is simply missing that fix, a realistic maintenance/porting gap rather than a theoretical concern.

## Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure the actual token balance delta after each `safeTransferFrom` (and after any predispatch/dispatcher flow) and use that measured amount — not the caller-supplied nominal amount — as the basis for protocol-fee calculation, commitment hashing, and escrow crediting in the Tron contract's `placeOrder()`.

## Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a nonzero `protocolFeeBps`.
2. Register/use an ERC-20 input token that deducts a transfer fee (e.g., 1% fee-on-transfer), analogous to the `FeeOnTransferToken` mock already used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`.
3. Call `placeOrder()` with `order.inputs[0].amount = 1000e18` of that token.
   - `reducedInputs[0].amount` is computed from `1000e18` (nominal) minus protocol fee, e.g. `990e18` after a 1% protocol fee.
   - `safeTransferFrom(msg.sender, address(this), 1000e18)` actually delivers only `990e18` to the contract (1% FOT deduction), with no balance check performed.
   - `_orders[commitment][token] += 990e18` is credited regardless.
4. Contract's actual token balance for that token increases by only `990e18`, but the escrow ledger for this order alone claims `990e18` while other pre-existing orders' balances are untouched — repeat with several FOT-token orders, and cumulative `_orders[...]` liabilities exceed the actual `balanceOf(gateway)`.
5. When earlier orders are redeemed/cancelled first, the last order's beneficiary finds the transfer reverts or is shorted, i.e., permanent loss of that user's expected input funds.
