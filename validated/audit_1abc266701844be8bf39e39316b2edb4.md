### Title
`ReceivedOutput::read` does not bind the scalar offset to the output's script_pubkey, allowing cross-context routing of received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` guarantees offset/script consistency because it only emits `ReceivedOutput`s whose `script_pubkey` was derived from `key + offset·G` via its internal `scripts` map. However, `ReceivedOutput::read` deserializes an arbitrary `(offset, TxOut, OutPoint)` triple from untrusted bytes with no check that `offset` actually produces `output.script_pubkey`. Analogous to the undici SOCKS5 pool-reuse bug (a resource/connection established for one origin is silently used for requests destined to a different origin), a `ReceivedOutput` parsed from bytes routes funds locked under one tweaked key into a context that will try to spend them with a different derived key.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs:122-134`, `ReceivedOutput::read` reads `offset` via `Secp256k1::read_F`, then consensus-decodes `output` and `outpoint`, and returns the struct without verifying `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey`. The `offset` is the scalar needed to spend the output (`networks/bitcoin/src/wallet/mod.rs:91-97`). When scanners construct outputs themselves this invariant holds (`scan_transaction`, lines 199-214, only matches `scripts.get(&output.script_pubkey)`), but the deserialization path — the route by which a `ReceivedOutput` travels between components (as in `Output::read` in the processor, which wraps `ReceivedOutput::read`) — accepts attacker-influenced bytes. A mismatched pair means the reported spendable key (`script_key − offset·G`) is not the group key, i.e. the funds are attributed to a destination ("origin") different from the one the script actually locks to.

### Impact Explanation
An unprivileged party who can cause a crafted `ReceivedOutput` blob to be ingested (e.g., outputs relayed/queued between processors or restored from externally-supplied data) can cause funds to be reported as received under a key that cannot spend them: the script locks to `key + offset_A·G` while the stored `offset_B` yields a different derived key. This produces either unspendable outputs (funds reported received that are not spendable) or attribution of an output to the wrong offset context — the direct analog of request data intended for origin B being routed to origin A. Additionally, since `register_offset` is surjective (`networks/bitcoin/src/wallet/mod.rs:180-196`), a forged offset can point at a registered offset for a different output kind (e.g., change vs. external), misclassifying funds.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ReceivedOutput::read`, which is a listed untrusted-input surface. No secret leakage or key recovery results; the impact is integrity/availability of funds accounting, matching a Medium severity.

### Recommendation
Either (a) make `ReceivedOutput` construction private and provide `ReceivedOutput::read(key, r)` that recomputes `p2tr_script_buf(key + GENERATOR * offset)` and rejects on mismatch, or (b) store the intended key in `ReceivedOutput` and verify on deserialization, so the destination context is cryptographically bound to the output rather than trusted from the byte stream.

### Proof of Concept
```rust
// networks/bitcoin context; key = group key the Scanner was built for
let key: ProjectivePoint = ...; // even-Y so Scanner::new succeeds
let real_offset = Scalar::ZERO;
let script = p2tr_script_buf(key).unwrap(); // locks to `key`
let output = TxOut { value: Amount::from_sat(100_000), script_pubkey: script };
let outpoint = OutPoint::new(Txid::all_zeros(), 0);

// Attacker crafts a ReceivedOutput pairing the real script with a wrong offset
let forged = ReceivedOutput { offset: Scalar::ONE, output, outpoint };
let bytes = forged.serialize();
let parsed = ReceivedOutput::read(&mut bytes.as_slice()).unwrap(); // succeeds

// Downstream (e.g. Output::key in the processor) derives:
//   script_key - offset*G == key - G != key
// The output is reported received under a key that cannot spend it.
assert_ne!(
  /* derived spend key */ parsed.offset(),
  real_offset
);
```
