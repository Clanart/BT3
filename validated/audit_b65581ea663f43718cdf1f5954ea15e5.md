### Title
Unbounded recursive decoding of nested `AccountKeyRoleBased` allows stack-exhaustion DoS from a single submitted transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each of its role sub-keys by re-invoking `rlp.DecodeBytes` on nested byte blobs. If a sub-key is itself of type `AccountKeyTypeRoleBased`, this triggers another full recursive decode cycle with no depth limit, exactly analogous to the Akka HTTP CVE-2021-42697 pattern where deeply nested comment structures caused unbounded recursive parsing and stack exhaustion.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes each role entry as an independent byte blob and immediately re-decodes it via a fresh `rlp.DecodeBytes` call: [1](#0-0) 

Each element decode goes through `AccountKeySerializer.DecodeRLP`, which reads the key type and then calls `s.Decode(serializer.key)` on the target `AccountKey` implementation: [2](#0-1) 

If the decoded `keyType` is `AccountKeyTypeRoleBased` again, `NewAccountKey` allocates another `*AccountKeyRoleBased`, and `s.Decode` dispatches back into `AccountKeyRoleBased.DecodeRLP`, restarting the same recursive cycle (`DecodeRLP` → `rlp.DecodeBytes` → `NewStream`/`Decode` → `decodeDecoder` → `AccountKeySerializer.DecodeRLP` → `s.Decode` → `AccountKeyRoleBased.DecodeRLP` → …). Nothing in `rlp/decode.go`'s decoder dispatch (`makeDecoder`, `decodeDecoder`) enforces a recursion/nesting depth limit for `Decoder`-implementing types.

The only place that rejects a role-based key nested inside a role-based key is the semantic validation performed in `CheckInstallable`/`CheckUpdatable`, which runs *after* decoding has already completed: [3](#0-2) 
This is confirmed by the existing regression test, which only checks that nesting is rejected at the tx-pool/apply stage — i.e., after a successful decode — not that decoding itself is bounded: [4](#0-3) 

An `AccountUpdate`-family transaction (`TxInternalDataAccountUpdate`, `TxInternalDataFeeDelegatedAccountUpdate`, `TxInternalDataFeeDelegatedAccountUpdateWithRatio`) carries the account key as an opaque encoded byte blob that is separately RLP-decoded once the outer transaction fields are parsed: [5](#0-4) 
This decode path is reached the moment any node parses a raw transaction — e.g. via transaction pool ingestion or RPC submission of a raw signed transaction (`Transaction.DecodeRLP` → `txInternalDataSerializer` → `fromSerializable` → `accountkey.AccountKeySerializer` decode chain): [6](#0-5) 

### Impact Explanation
An attacker (any unprivileged account, no special key or balance needed beyond gas for a properly-signed AccountUpdate tx, or even before full validation during RLP decode) can construct an `AccountUpdate`/`FeeDelegatedAccountUpdate(WithRatio)` transaction whose account-key payload nests `AccountKeyRoleBased` deeply (e.g., thousands of levels), each level adding only a small number of bytes. Submitting this transaction (via `sendRawTransaction` RPC or block propagation) forces every node that decodes it — during tx-pool admission and during block validation — to recurse to the crafted depth. Because Go's goroutine stacks grow dynamically but ultimately hit a hard limit, sufficiently deep recursion triggers a fatal, unrecoverable `runtime: goroutine stack exceeds ... - fatal error: stack overflow`, crashing the node process. This is a network-wide, remotely triggerable Denial of Service impacting availability of the transaction pool and block-processing pipeline on every node that receives the transaction — matching CWE-674 (Uncontrolled Recursion) and CVSS Availability:High as in the source advisory.

### Likelihood Explanation
High. No signature validation, balance check, or gas payment is required to reach the vulnerable decode path — decoding occurs immediately upon receiving/parsing the raw transaction bytes (or an encoded key blob) before intrinsic gas / signature checks conclude. The only mitigations present (`CheckInstallable`/`CheckUpdatable` rejecting nested `RoleBased`) execute strictly after the vulnerable decode has already run to completion or crashed the process, so they provide no protection against this specific bug class.

### Recommendation
Add an explicit recursion-depth (or nesting-depth) limit to `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` (e.g., reject decoding if `AccountKeyTypeRoleBased` is encountered while already decoding within a `RoleBased` context, mirroring the existing but too-late `isNested` check used in `api_kaia.go`'s `checkAccountKeyZeroValues`), and/or impose a global maximum decode-nesting depth in the `rlp` package for any type implementing `Decoder` that can recursively invoke `rlp.DecodeBytes`/`Decode` on itself.

### Proof of Concept
Conceptually (cannot execute in this environment):
1. Build an `AccountKeySerializer`-encoded `AccountKeyRoleBased` value `K0` containing exactly one role entry.
2. Set that role entry's encoded bytes to be another `AccountKeySerializer`-encoded `AccountKeyRoleBased` `K1` (also with one role entry).
3. Repeat, nesting `K0 ⊃ K1 ⊃ K2 ⊃ … ⊃ Kn` for a large `n` (e.g., 50,000), using `rlp.EncodeToBytes(accountkey.NewAccountKeySerializerWithAccountKey(...))` as shown in `toSerializable`: [7](#0-6) 
4. Place `Kn` (the outermost) into a `TxTypeAccountUpdate` transaction's `Key` field and sign it normally.
5. Submit via `sendRawTransaction`; upon decode of the `Key` blob (`fromSerializable` → `rlp.DecodeBytes(serialized.Key, serializer)`), the node recurses `n` times through `AccountKeyRoleBased.DecodeRLP`/`AccountKeySerializer.DecodeRLP`, exhausting the goroutine stack and crashing the node.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (a *AccountKeyRoleBased) CheckUpdatable(newKey AccountKey, currentBlockNumber uint64) error {
	if newKey, ok := newKey.(*AccountKeyRoleBased); ok {
		lenOldKey := len(*a)
		lenNewKey := len(*newKey)
		// If no key is to be replaced, it is regarded as a fail.
		if lenNewKey == 0 {
			return kerrors.ErrZeroLength
		}
		// Do not allow undefined roles.
		if lenNewKey > (int)(RoleLast) {
			return kerrors.ErrLengthTooLong
		}
		for i := range lenNewKey {
			switch {
			// A composite key is not allowed.
			case (*newKey)[i].IsCompositeType():
				return kerrors.ErrNestedCompositeType
			// If newKey is longer than oldKey, init the new attributes.
			case i >= lenOldKey:
				if err := (*newKey)[i].CheckInstallable(currentBlockNumber); err != nil {
					return err
				}
			// Do nothing for AccountKeyTypeNil
			case (*newKey)[i].Type() == AccountKeyTypeNil:

			// Check whether the newKey is replacable or not
			default:
				if err := CheckReplacable((*a)[i], (*newKey)[i], currentBlockNumber); err != nil {
					return err
				}
			}
		}
		return nil
	}
	// Update is not possible if the type is different.
	return kerrors.ErrDifferentAccountKeyType
}

	if err := s.Decode(&serializer.keyType); err != nil {

	}

	t.Price = serialized.Price
	t.GasLimit = serialized.GasLimit
