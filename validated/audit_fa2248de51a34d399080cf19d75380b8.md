### Title
`Scanner::scan_block` reports immature coinbase outputs as received funds that cannot actually be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in a block — including `txdata[0]`, the coinbase — and returns any output paying a registered script as a `ReceivedOutput` indistinguishable from a mature, spendable one. Coinbase outputs are unspendable for 100 blocks under Bitcoin consensus rules, so the scanner reports funds as received which cannot actually be used. This is the analog of `autoRedeem()` being callable before the external principal tokens were redeemed: an action (recognition/crediting of funds) is performed before the prerequisite condition (coinbase maturity) is satisfied, producing a state that overstates what is actually available.

### Finding Description
In `scan_transaction`, each `TxOut` is matched purely on `script_pubkey` against `self.scripts`, and `scan_block` applies it to all of `block.txdata` with no coinbase exclusion and no maturity marker on the returned `ReceivedOutput` [1](#0-0) . A `ReceivedOutput` carries only `offset`, `output`, and `outpoint` — nothing encoding that the output came from a coinbase or when it becomes spendable. The only safeguard is a doc comment telling callers that "a post-processing pass is needed to remove those outputs" [2](#0-1) . Notably, Serai's own Bitcoin processor had to work around this by explicitly skipping `block.txdata[0]` when feeding `scan_transaction` [3](#0-2) , confirming the library-level behavior is a real footgun rather than a theoretical one.

### Impact Explanation
Any consumer of `bitcoin-serai`'s `Scanner` that treats `scan_block` results as spendable inputs will build transactions spending a coinbase output before its 100-block maturity. Consensus will reject such a transaction (`bad-txns-premature-spend-of-coinbase`), so at minimum the wallet constructs permanently invalid spends. More seriously for a bridge/aggregator design like Serai's, crediting deposited value before it is actually spendable mirrors the Illuminate bug exactly: the protocol acts on a balance whose backing funds are not yet redeemable, enabling the same premature-action / wrong-availability class — funds reported received that are not spendable, one of the explicitly accepted impact categories.

### Likelihood Explanation
Any miner can trigger this with public inputs: mine a block whose coinbase pays a registered Serai P2TR script (derived from the publicly known group key plus a registered offset). No access to any secret is required — an unprivileged party simply needs to produce a valid block, which any mining pool or regtest/signet participant can do. The outputs are returned identically to normal outputs, so detection depends entirely on the caller remembering the documented post-processing pass.

### Recommendation
Do not scan `block.txdata[0]` inside `scan_block` — skip the coinbase transaction the same way `get_outputs` does in `processor/src/networks/bitcoin.rs` (iterating `block.txdata[1 ..]`). If scanning coinbases is desired for observability, either carry a maturity height / `is_coinbase` flag on `ReceivedOutput` so downstream code can enforce spendability, or return coinbase outputs through a separate API. Relying on a doc comment for a consensus-critical exclusion is insufficient.

### Proof of Concept
```rust
// Using the existing regtest harness in networks/bitcoin/tests/wallet.rs
let mut scanner = Scanner::new(group_key).unwrap();

// A miner mines a block whose COINBASE pays the Serai multisig script
rpc.rpc_call::<Vec<String>>(
  "generatetoaddress",
  serde_json::json!([1, serai_p2tr_address]),
).await.unwrap();

let block = rpc.get_block(&rpc.get_block_hash(block_number).await.unwrap()).await.unwrap();
let outputs = scanner.scan_block(&block);

// The coinbase output is reported identically to a normal received output...
assert_eq!(outputs.len(), 1);
// ...yet it is not spendable for 100 blocks. Any downstream code that builds a
// transaction spending outputs[0].outpoint() produces a consensus-invalid TX
// (bad-txns-premature-spend-of-coinbase), and any code that credits its value
// as immediately available liquidity has accounted funds it cannot move.
```

Note: the codebase's own test at `networks/bitcoin/tests/wallet.rs` mines 100 additional blocks before calling `scan_block` precisely because the coinbase is immature — demonstrating the behavior and confirming `scan_block` itself performs no maturity check.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
