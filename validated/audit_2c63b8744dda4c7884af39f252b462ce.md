Audit Report

## Title
Unbounded stake-program index scan in `calculate_non_circulating_supply` degrades `getSupply`/`getLargestAccounts` - (File: `runtime/src/non_circulating_supply.rs`)

## Summary
`calculate_non_circulating_supply`, invoked on every `getSupply` and `getLargestAccounts` RPC call, calls `bank.get_filtered_indexed_accounts(&IndexKey::ProgramId(stake::program::id()), ..., None)` with the byte-limit parameter hard-coded to `None`. This differs from the RPC layer's own generic wrapper `JsonRpcRequestProcessor::get_filtered_indexed_accounts`, used for `getProgramAccounts`, which always forwards the operator-configured `scan_results_limit_bytes` so the scan can abort once results exceed a bound.

## Finding Description
`calculate_non_circulating_supply` at [1](#0-0)  reaches the indexed-scan branch only when `AccountIndex::ProgramId` is enabled, and calls `bank.get_filtered_indexed_accounts` with `byte_limit_for_scan` fixed to `None`. The owner-equality closure at line 42 is applied only after each pubkey under the index has already been loaded via `do_load`; it does not reduce the number of index entries iterated by `index_scan_accounts`, shown at [2](#0-1) , which walks `self.accounts_index.get_index_key_pubkeys(&index_key)` unconditionally except for `config.is_aborted()`. `Accounts::load_by_index_key_with_filter` at [3](#0-2)  only triggers `config.abort()` via `accumulate_and_check_scan_result_size` when a `Some(byte_limit_for_scan)` is supplied; with `None`, no abort condition is ever reached, matching the behavior demonstrated by `test_get_filtered_indexed_accounts_limit_exceeded` in [4](#0-3) . By contrast, `JsonRpcRequestProcessor::get_filtered_indexed_accounts` used for `getProgramAccounts` always threads through `self.config.scan_results_limit_bytes` at [5](#0-4) .

## Impact Explanation
An RPC node with `--account-index program-id` enabled and `--full-rpc-api` performs an unbounded `do_load` over every pubkey registered under the `ProgramId(stake::program::id())` secondary index on each `getSupply`/`getLargestAccounts` call, with no scan-size circuit breaker unlike the equivalent `getProgramAccounts` code path. This can degrade CPU/IO/latency of that single RPC node proportional to attacker-inflated index size, falling into the "single-client low-rate RPC crash/degradation" impact category. It has no effect on consensus, other validators, or funds.

## Likelihood Explanation
Exploitation requires the operator to have opted into the non-default `ProgramId` secondary index and exposed the full RPC API; it also requires the attacker to fund rent-exempt accounts owned by the stake program, which imposes an economic throttle. Given these preconditions, the degradation is straightforward and repeatable.

## Recommendation
Thread the same configured byte-limit (`scan_results_limit_bytes` or an equivalent bound) into `calculate_non_circulating_supply`'s call to `bank.get_filtered_indexed_accounts`, mirroring the `rpc.rs::get_filtered_indexed_accounts` wrapper, and propagate a scan-abort error to the RPC caller instead of allowing an unbounded scan.

## Proof of Concept
1. Run a validator with `--account-index program-id` and `--full-rpc-api`.
2. As an unprivileged client, create many rent-exempt-funded accounts owned by `stake::program::id()`.
3. Confirm via `bank.get_filtered_indexed_accounts(&IndexKey::ProgramId(stake::program::id()), |_| true, None)` that scanned/loaded entries grow linearly with attacker-created accounts, contrasting with `test_get_filtered_indexed_accounts_limit_exceeded`, which only aborts when an explicit `Some(limit)` is passed.
4. Measure `getSupply`/`getLargestAccounts` latency before/after account creation to observe degradation proportional to injected account count.

        &self,

        index_key: &IndexKey,
        filter: F,
        byte_limit_for_scan: Option<usize>,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let sum = AtomicUsize::default();
        let config = ScanConfig::default().recreate_with_abort();
        let mut collector = Vec::new();
        let result = self
            .accounts_db
            .index_scan_accounts(
                ancestors,
                bank_id,
                *index_key,
                |some_account_tuple| {
                    Self::load_while_filtering(&mut collector, some_account_tuple, |account| {
                        let use_account = filter(account);
                        if use_account
                            && Self::accumulate_and_check_scan_result_size(
                                &sum,
                                account,
                                &byte_limit_for_scan,
                            )
                        {
                            // total size of results exceeds size limit, so abort scan

                        }
                        use_account
                    });
                },
                &config,
            )
            .map(|_| collector);

    }

        &self,
        bank: &Arc<Bank>,
        index_key: &IndexKey,
        program_id: &Pubkey,
        filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(

                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)

                )
            })
