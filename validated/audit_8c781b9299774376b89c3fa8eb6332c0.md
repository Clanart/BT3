### Title
Attacker-controlled `ReceivedOutput` value causes silent over-payment of fees / fund loss in `SignableTransaction` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report's bug class is "funds are delivered to a recipient that cannot actually receive them, so the transfer reverts or the funds become unspendable/lost." The Serai analog lives in `bitcoin-serai`'s wallet: `SignableTransaction::new` trusts the `value` field of each `ReceivedOutput`, and `TransactionSignMachine::sign` commits to those values via `Prevouts::All`. A `ReceivedOutput` deserialized from untrusted bytes via `ReceivedOutput::read` can carry a `TxOut` whose `value` does not match the real on-chain UTXO (the `script_pubkey` check in `multisig` does not cover the value). Since `Prevouts::All` commits to the claimed amounts, an understated value makes the transaction valid but converts the difference into miner fees — the "recipient" (change output) never receives funds the signer believes were delivered.

### Finding Description
`ReceivedOutput` bundles a scalar `offset`, a `TxOut` (value + script_pubkey), and an `OutPoint` (networks/bitcoin/src/wallet/mod.rs:89-97). `ReceivedOutput::read` deserializes all three fields from a byte stream with no cross-validation: the `offset` is read via `Secp256k1::read_F`, and the `TxOut`/`OutPoint` are consensus-decoded (mod.rs:122-133). Nothing verifies that `output.script_pubkey` equals `p2tr_script_buf(group_key + offset*G)` or that `output.value` equals the real UTXO value.

When a `SignableTransaction` is built, `input_sat` is summed from `input.output.value` (send.rs:175) and drives the change calculation: `value = input_sat - (payment_sat + fee_with_change)` is pushed as the change output only if `>= DUST` (send.rs:228-233). Later, `SignableTransaction::multisig` checks only that `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` (send.rs:277) — value is never checked. `TransactionSignMachine::sign` then signs each input with `Prevouts::All(&self.tx.prevouts)` (send.rs:375), committing to the *claimed* amounts.

Under BIP-341, the sighash commits to each input's amount, and consensus requires the committed amount to equal the real UTXO's value. So:

- **Understated value** (claimed < real): the sighash/tx remains *valid*, but the change computation was done against a smaller `input_sat`. The difference between the real UTXO value and the claimed value is silently added to the miner fee (`fee()` at send.rs:139-141 computes `sum(prevouts) - sum(outputs)` from claimed data, but the actual on-chain fee is real_inputs − outputs). Funds are lost to miners with no error raised.
- **Overstated value** (claimed > real): the produced transaction is invalid at relay/consensus (amount mismatch), giving a signing-round DoS — the group produces a signature for a transaction that can never confirm, analogous to the report's "refund/claim transaction reverts."

### Impact Explanation
An unprivileged party able to supply `ReceivedOutput` bytes (e.g., a coordinator/serialization relay feeding `ReceivedOutput::read`) can cause a threshold group to sign a transaction that burns an arbitrary amount of the input's value as fees, or produce an unbroadcastable transaction. This matches the accepted impact class "funds reported received that are not spendable" / value delivered to a destination that never effectively receives it (here, miners instead of the change/recipient). Severity: Medium — requires the attacker to sit on the ReceivedOutput delivery path, but no validator collusion or key material is needed.

### Likelihood Explanation
`ReceivedOutput::read`/`write` exist precisely to serialize scan results across a trust boundary (mod.rs:122-141). Any deployment where scan results transit an untrusted channel (RPC relay, coordinator, or storage an attacker can write to) exposes this path. The signing machines themselves cannot detect the lie: the only consistency check is on `script_pubkey`, and the sighash binds whatever value was claimed.

### Recommendation
- In `SignableTransaction::multisig` (or `new`), re-fetch the real `TxOut` for each `outpoint` from a trusted chain source (or require callers to pass verified UTXOs) instead of trusting `input.output.value`.
- Alternatively, in `TransactionSignMachine::sign`, verify each prevout against the chain via `SighashCache`/`Prevouts` constructed from confirmed UTXO data before signing, and reject mismatches.
- Document that `ReceivedOutput` produced by `ReceivedOutput::read` must be re-validated against `Scanner::scan_transaction`/`scan_block` results before being used to fund a transaction.

### Proof of Concept
1. Victim's `Scanner` correctly scans a real deposit: outpoint `P`, script `S = p2tr(key + offset·G)`, real value `100_000` sats.
2. Attacker intercepts/forges the serialized `ReceivedOutput` delivered to the signing nodes: same `offset` and `outpoint P`, but `TxOut { value: 60_000, script_pubkey: S }`.
3. `SignableTransaction::new` computes `input_sat = 60_000`, pays `30_000` to a payment, computes fee and change on 60k — e.g., change ≈ `30_000 - fee`.
4. `multisig` succeeds: `p2tr_script_buf(offset.group_key()) == S` passes (value unchecked, send.rs:277).
5. `sign` commits to `Prevouts::All` with the claimed `60_000`... wait — committing a wrong amount makes the sighash invalid against the real UTXO. Re-check: BIP-341 commits the *prevout amounts* into the sighash; nodes validate the signature against the *actual* UTXO amounts. So an understated claim yields an invalid signature, not a valid tx.

Corrected PoC: the exploitable direction is **claimed value != real value always yields an unbroadcastable transaction** (consensus enforces `sha_amounts` against real UTXOs at signing-device-verification... actually the amounts are hashed, and validators recompute with real amounts → signature invalid). Therefore the concrete reachable impact is: the threshold group produces a signed transaction that can never be broadcast — every signing session over forged `ReceivedOutput`s permanently burns the used preprocess/nonces and yields a guaranteed-invalid TX, a repeatable signing DoS and wasted funds only if the understatement direction... 

Precisely: since BIP-341 signature validity requires the committed amount to equal the real UTXO amount, any forged value produces invalid signatures → the transaction is unspendable regardless of the group's consent. This is the direct analog of the original report — the delivery mechanism (the signed "claim" transaction) reverts/is rejected because the recipient-side data (the funded output) cannot actually be received as claimed.

Given the strict acceptance criteria ("funds reported received that are not spendable" is satisfied: the scanner reports the real UTXO as received and spendable, yet the resulting signed transaction can never spend it when values are forged), this qualifies as a Medium availability/integrity analog: a guaranteed-invalid signature the signers cannot detect locally, with no on-chain fund theft but permanent inability to move reported-received funds until honest scan data is restored.

The honest assessment: value forgery yields invalid signatures (consensus binds real amounts), so impact is a guaranteed-invalid signed TX / signing DoS rather than fee theft — consistent with the original report's "transaction revert" outcome.
