## Finding

### Title
Tokenfactory denom admin can retroactively add/modify the `AllowList` via `MsgUpdateDenom` to freeze already-distributed tokens - (File: `x/tokenfactory/keeper/msg_server.go`)

### Summary
The OpenQ report describes an issuer that retains unilateral, unrestricted control to change bounty terms (KYC/invoice/tier requirements) *after* a bounty has started, allowing it to block legitimate claimants after the fact. The Sei tokenfactory module has an analogous pattern: any account that creates a `factory/{creator}/{subdenom}` denom becomes its permanent "admin" and can call `MsgUpdateDenom` at *any* time — including after minting and freely distributing/trading the token to third parties — to impose or change a `bank.AllowList` that instantly blocks previously-unrestricted holders from sending or receiving that denom, with no time-lock, grandfathering, or "bounty-closed"-style immutability guard.

### Finding Description
`CreateDenom` optionally sets an `AllowList` for the newly created denom via `server.bankKeeper.SetDenomAllowList`, but a denom can also be created with **no** allow list at all, in which case anyone can freely trade the token. [1](#0-0) 

The denom's `admin` (defaulted to the creator) can subsequently call `UpdateDenom` and unconditionally overwrite the allow list for the denom, with the only check being that `msg.Sender` equals the current admin — there is no check on prior holder consent, no restriction based on how long the denom has existed, and no protection for addresses that already legitimately hold the token: [2](#0-1) 

The bank keeper's send-path enforcement, `IsInDenomAllowList`, checks **both** the sender and the recipient against the allow list for every token-factory-prefixed coin on every `Send`/`MultiSend`, without any exemption for balances acquired before the allow list was set: [3](#0-2) [4](#0-3) 

This is exercised in the module's own regression tests, confirming the mechanic: a denom is created and freely funded/tradable, and only after that does the admin retroactively install an allow list, immediately preventing sends to/from any address not on it: [5](#0-4) 

So the exact bug class from the report — "issuer/admin can change the rules governing fund release/movement at any time, even after users have already committed to (or received) the asset, with no immutability guarantee" — is directly reachable by any unprivileged account acting in the tokenfactory-denom-creator role that the analog rules explicitly permit.

### Impact Explanation
Because `IsInDenomAllowList` gates both the sender and the recipient leg of every transfer, an admin can add an allow list that excludes specific addresses (or set an allow list containing only itself) *after* those addresses have already received tokens through legitimate mint/transfer activity. Those holders' balances become permanently un-transferable (frozen) for as long as the admin — who has no obligation to ever relax the list — chooses to keep them excluded. Any application (DEX pools, integrators, other users who received the token in good faith believing it was freely transferable) can have its holdings of that token silently and unilaterally frozen. This is a concrete, permanent fund-freezing vector reachable from a standard `MsgUpdateDenom` transaction.

### Likelihood Explanation
Likelihood is high: any account can create a tokenfactory denom, mint and distribute it (or let it be freely traded) with no allow list, and then submit a single `MsgUpdateDenom` transaction to impose a restrictive allow list. No governance, no multisig, no time delay, and no consent from existing holders is required — only the admin's own signature.

### Recommendation
Consider one or more of the following mitigations, mirroring the OpenQ recommendation to prevent post-hoc rug-pulls:
- Require that `AllowList` be fixed at `CreateDenom` time and disallow later additions/removals via `UpdateDenom` (or only allow the list to be relaxed/expanded, never newly restricted for a denom that has already had transfers).
- If retroactive restriction must be supported, grandfather addresses that already hold a positive balance of the denom at the time the allow list changes, so previously acquired tokens remain transferable.
- Emit prominent on-chain signaling / require a delay window before a newly added restriction takes effect, so holders can react before being frozen.

### Proof of Concept
1. Account `A` calls `MsgCreateDenom` for `factory/A/foo` with no `AllowList` (or an empty one). [1](#0-0) 
2. Account `A` mints `factory/A/foo` and sends/sells it freely to accounts `B`, `C`, `D`, etc. Because there is no allow list, `IsInDenomAllowList` allows every transfer. [6](#0-5) 
3. Once `B`, `C`, `D` hold meaningful balances, `A` (still the admin) submits `MsgUpdateDenom` with `AllowList.Addresses = ["A"]` (or any list excluding `B/C/D`). [2](#0-1) 
4. Any subsequent `MsgSend`/`MsgMultiSend` involving `B`, `C`, or `D` as sender or recipient for `factory/A/foo` now fails with `"is not allowed to send/receive funds"`, exactly as demonstrated in `TestSendReceiverNotInAllowList`/`TestSendSenderNotInAllowList`, permanently freezing their already-acquired balances at the admin's sole discretion. [5](#0-4)

func (server msgServer) CreateDenom(goCtx context.Context, msg *types.MsgCreateDenom) (*types.MsgCreateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.Keeper.CreateDenom(ctx, msg.Sender, msg.Subdenom)
	if err != nil {
		return nil, err
	}

	createDenomEvent := sdk.NewEvent(
		types.TypeMsgCreateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeNewTokenDenom, denom),
	)

	if msg.AllowList != nil {
		err = server.validateAllowList(ctx, msg.AllowList)
		if err != nil {
			return nil, err
		}
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		createDenomEvent = createDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		createDenomEvent,
	})

	return &types.MsgCreateDenomResponse{
		NewTokenDenom: denom,
	}, nil
}

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}
