### Title
Empty aggregate signature verifies as valid for zero signers - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::verify` accepts a serialized aggregate containing zero nonces (`Rs`) and `s = 0` when the caller supplies an empty `keys_and_challenges` list. The verification equation degenerates to `-0 * G == identity`, so the verifier returns `true` without any signer, key, nonce, challenge, or message being bound.

### Finding Description
`SchnorrAggregate::read` parses a `u32` length, then that many `R` points, then scalar `s`. An attacker can supply length `0` followed by a canonical zero scalar. In `SchnorrAggregate::verify` (`crypto/schnorr/src/aggregate.rs:127-145`), the only checks are `Rs.len() == keys_and_challenges.len()` and a multiexp over `pairs`. With both lists empty, no per-signer weights are sampled and `pairs` contains only `(-self.s, C::generator())`. Submitting `s = 0` makes that term the identity, so `multiexp_vartime(&pairs).is_identity()` is true and verification succeeds. `SchnorrAggregator::complete` refuses to produce an aggregate for zero signatures (`crypto/schnorr/src/aggregate.rs:174-178`), but the decoder/verifier path accepts the attacker-encoded empty aggregate anyway.

### Impact Explanation
This is a forged signature primitive: bytes controlled by an unprivileged party pass `verify` while proving knowledge of no private key and authorizing no message. Any protocol path that interprets a successful aggregate verification as authorization — especially where an empty signer/challenge list can arise from attacker-supplied or attacker-influenced input — processes the request without authentication, matching the missing-authorization bug class.

### Likelihood Explanation
Exploitation only requires reaching `SchnorrAggregate::read`/`verify` with an empty signer set and a zero `s`, both fully attacker-encodable. Whether it is reachable depends on callers permitting empty `keys_and_challenges`; the primitive itself provides no defense and behaves opposite to `complete`, which treats empty aggregation as invalid.

### Recommendation
Reject empty aggregates in `SchnorrAggregate::verify` (return `false` when `keys_and_challenges.is_empty()` or `Rs.is_empty()`), consistent with `SchnorrAggregator::complete` returning `None` for empty input. Callers should also assert non-empty expected signer sets before verification.

### Proof of Concept
```rust
// crypto/schnorr/src/aggregate.rs
// Serialized SchnorrAggregate for an empty Rs list and s = 0:
let mut bytes = 0u32.to_le_bytes().to_vec();
bytes.extend([0u8; 32]); // canonical zero scalar for Ristretto/25519-class fields

let agg = SchnorrAggregate::<Ristretto>::read(&mut bytes.as_slice()).unwrap();
assert!(agg.verify(b"any dst", &[])); // returns true with zero signers
```
