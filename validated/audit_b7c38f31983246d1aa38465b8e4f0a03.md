### Title
Unauthenticated `setup()` RPC on aggregator when `client_verification=false` uses `Interceptors::Noop`, allowing any network caller to re-distribute verifier/operator keys - ([File: core/src/servers.rs])

### Summary
`create_grpc_server` selects `Interceptors::Noop` for the aggregator's gRPC service whenever `config.client_verification` is `false`, and `Noop::call` unconditionally returns `Ok(req)` for every request with no other authentication layer applied. Because the aggregator's `setup()` RPC is state-changing (it re-distributes verifier/operator keys), any unprivileged network caller who can reach the aggregator's TCP port can invoke it while this flag is disabled.

### Finding Description
The binding the code is supposed to enforce is: `caller allowed to invoke ClementineAggregatorServer methods == holder of a TLS client certificate trusted by the aggregator's CA`. In `create_grpc_server`, when `config.client_verification` is `true`, the server sets `ServerTlsConfig::client_ca_root` and wraps the service in `InterceptedService::new(service, OnlyAggregatorAndSelf{...})`, which checks the leaf peer certificate against pinned certs before forwarding any request [1](#0-0) . When `config.client_verification` is `false`, no `client_ca_root` is configured on the TLS transport and the interceptor becomes `Interceptors::Noop` [1](#0-0) , and `Noop::call` returns `Ok(req)` for every request with zero checks [2](#0-1) . There is no secondary authorization check inside the interceptor module or in `create_grpc_server` that re-verifies caller identity for state-changing RPCs such as `setup()`; the only gate is this single interceptor selection driven by `config.client_verification`. `create_aggregator_grpc_server` does not force `client_verification` to `true` — it merely logs a warning if it happens to be `true`, and calls the same generic `create_grpc_server` path for both `true` and `false` cases [3](#0-2) . Consequently, if the aggregator is deployed with `client_verification=false`, any caller reaching the TCP port can call `setup()` (or any other aggregator RPC) with no client certificate at all, since the equality "caller reaching the service == a party holding the aggregator's trusted client certificate" collapses to "caller reaching the service == anyone."

I was not able to confirm within the available context (i) the exact default value of `client_verification` shipped in `core/src/config/mod.rs`/`env.rs`, and (ii) the internal implementation of `AggregatorServer::setup` (its file/module was not located, so I cannot confirm whether `setup()` performs any additional internal authorization, idempotency guard, or state check beyond the transport-level interceptor). These are material gaps: if `client_verification` defaults to `true` in production configs, or if `setup()` itself refuses to re-run key distribution once verifiers/operators are already configured, the practical exploitability described in the question would not hold as stated.

### Impact Explanation
If `client_verification=false` is genuinely how the aggregator is deployed (or defaults), an unauthenticated caller can invoke any aggregator RPC including `setup()`, which the question states re-distributes verifier/operator keys — a state-changing protocol operation. This matches the "High - an unauthenticated state-changing or broadcasting call" category. It does not on its own demonstrate BTC leaving a move-to-vault UTXO or a false claim being proved, so it should not be scored as Critical without further evidence that key re-distribution can be weaponized into fund movement (e.g., substituting attacker-controlled verifier/operator keys). That escalation path (from "can call setup()" to "can steal funds") is not demonstrated in the available code.

### Likelihood Explanation
Exploitability depends entirely on the deployment/default of `config.client_verification`. The transport-layer bypass mechanism (`ServerTlsConfig` without `client_ca_root` plus `Interceptors::Noop`) is confirmed in code, but whether this is the actual default, or an intentionally documented opt-out for local/dev use, could not be confirmed from the files I was able to inspect. Given typical secure-by-default design intent implied by `OnlyAggregatorAndSelf` existing as the "on" path with client cert pinning, and the warning log only firing when verification is *enabled* (rather than warning when it's disabled), the default posture is ambiguous from the code alone.

### Recommendation
Regardless of default, treat `client_verification=false` as a testing-only mode: refuse to start the aggregator's public TCP listener with `Noop` unless an explicit, separate "insecure" flag is set (distinct from `client_verification`), and require additional method-level authorization inside `AggregatorServer::setup` (e.g., checking a caller-provided credential or restricting setup to loopback/Unix socket) independent of the transport interceptor, so that a misconfigured or defaulted `client_verification=false` cannot alone expose state-mutating RPCs.

    let result = client.setup(tonic::Request::new(Empty {})).await;
    // If Noop bypass is exploitable, this succeeds despite no auth
    assert!(result.is_ok(), "unauthenticated setup() should have been rejected");

This test needs to be paired with inspection of `AggregatorServer::setup`'s actual body (not located in this pass) to confirm it performs the key re-distribution described, and with confirmation of the real default of `client_verification` in `core/src/config/mod.rs`, before treating this as a confirmed, exploitable finding rather than an intended (if risky) configuration toggle.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
