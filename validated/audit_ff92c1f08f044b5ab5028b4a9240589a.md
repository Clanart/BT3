### Title
`ReceivedOutput::read` accepts an inconsistent (offset, output) pair, letting attacker-supplied bytes report funds the multisig key cannot spend - (networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in the external report is *unvalidated parameter/type confusion*: a caller-controlled flag (`order.isETHSell`) causes a value produced under one denomination (ERC20 tokens) to be carried and returned under another (`ethAmount`), because the code never checks that the supplied parameters are consistent with the asset actually being handled.

The analog in Serai's Bitcoin wallet is `ReceivedOutput::read`. A `ReceivedOutput` pairs a scalar `offset` with a `TxOut`. The only code that establishes the critical invariant — that `output.script_pubkey == p2tr(key + offset·G)` — is `Scanner::scan_transaction`, which derives `offset` *from* the matched script via the `scripts: HashMap<ScriptBuf, Scalar>` table. `ReceivedOutput::read`, however, deserializes `offset`, `output`, and `outpoint` from untrusted bytes as three independent fields and never checks that the offset actually opens the output's script. An unprivileged party that feeds bytes to `ReceivedOutput::read` can therefore supply an output paying to script S together with an offset belonging to a different script S′ — the exact analog of "the supplied parameters are not verified to be compatible with the thing being returned."

### Finding Description
`Scanner::new`/`register_offset` build a `scripts` map from `ScriptBuf` to `Scalar` (`networks/bitcoin/src/wallet/mod.rs:163-196`), and `scan_transaction` only emits a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` yields the offset (`mod.rs:205-211`). That lookup is the consistency proof: the offset is correct *by construction*.

`ReceivedOutput::read` (`mod.rs:122-134`) bypasses that construction entirely:

```rust
let offset = Secp256k1::read_F(r)?;
output  = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

There is no scanner context and no check that `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey` — or even that the script is P2TR at all. The fields are private (`mod.rs:90-97`), so a deserialized object is indistinguishable from a scanner-produced one to every downstream consumer (`offset()`, `output()`, `outpoint()`, `value()` at `mod.rs:99-118`).

### Impact Explanation
Downstream wallet/signing code (e.g., the `send` module that consumes `ReceivedOutput`s) trusts `offset` as "the scalar which, added to the multisig's private key, produces the key able to sign for this output." With a mismatched pair:

- The multisig will run a FROST signing session over a Bitcoin transaction spending an output whose Taproot internal key is `key + offset′·G` (offset′ ≠ supplied offset). The produced BIP-340 signature is valid for the *wrong* key — the transaction is unspendable/invalid on-chain even though the coordinator believes it completed a spend. This is a concrete signing-of-an-unintended-spend outcome.
- Equivalently, bytes can inflate `output.value` (the `TxOut` is attacker-chosen) so funds are *reported received* under a value/offset combination that does not correspond to any real, spendable UTXO — mirroring the original report's "wrong number of tokens added to the returned amount."

Because `read` is a pure deserialization sink with no consistency invariant, the confusion is silent: no error is raised at parse time.

### Likelihood Explanation
Reachable by any unprivileged party able to supply bytes to `ReceivedOutput::read` (e.g., outputs relayed through the scanner/coordinator data path). Exploitation requires no collusion, no leaked keys, and no honest-signer misbehavior — the signer set faithfully signs a message built on attacker-shaped data. Impact is bounded by what the system does with a bogus `ReceivedOutput` (a wasted/bricked signing attempt or misreported balance), consistent with a Medium severity.

### Recommendation
Either:

1. Make `ReceivedOutput` construction go through a checked constructor that verifies `p2tr_script_buf(self.key + GENERATOR * offset) == output.script_pubkey` against the scanner's key — i.e., give `read` access to the `Scanner`/`key` context and reject inconsistent pairs, or
2. Store only the matched script identity (or the key) in the serialized form and re-derive the offset on read, restoring the "offset derived from script" invariant that `scan_transaction` enforces.

### Proof of Concept
1. Build a `Scanner` for key `K` and register offsets `o1`, `o2` producing scripts `S1`, `S2` (`register_offset`, `mod.rs:180-196`).
2. Have an output `O` on-chain paying to `S1`.
3. Serialize a `ReceivedOutput` by hand: `offset = o2`, `output = O` (script_pubkey `S1`), `outpoint = O`'s outpoint. This is not a pair `scan_transaction` could ever produce.
4. Feed the bytes to `ReceivedOutput::read` — it returns `Ok` with no error (`mod.rs:122-134`).
5. Wallet code builds a spend of `O` and requests a signature under offset `o2`; the resulting signature verifies against `K + o2·G` but `O` requires `K + o1·G` — the transaction is invalid and the funds remain unspendable despite being "received" and "spent" by the protocol's accounting.
