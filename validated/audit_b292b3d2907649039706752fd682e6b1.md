### Title
Panic on PedPoP blame decryption via unregistered attacker-controlled `decryptor` index - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP encryption layer indexes `self.enc_keys` with a message-derived `Participant` index instead of using `get()`/`ok_or()`. When processing a blame/accusation decryption with a proof (`decrypt_with_proof`), a `decryptor` index that was never registered in `enc_keys` causes a `HashMap` index panic, crashing the thread — a denial of service from peer-supplied bytes, the same bug class as the malformed-input crash in CVE-2014-9811.

### Finding Description
`Decryption::register` only inserts keys that arrive in `EncryptionKeyMessage`s; nothing guarantees a `decryptor` referenced later was ever registered. `decrypt_with_proof` then performs an unchecked index into the map when verifying the accuser's `EncryptionKeyProof`:

- `crypto/dkg/pedpop/src/encryption.rs:356-360` — `assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant")` panics if the same `participant` submits a second `EncryptionKeyMessage`. A crafted/duplicated registration message is sufficient.
- `crypto/dkg/pedpop/src/encryption.rs:388` — `&[self.enc_keys[&decryptor], *proof.key]` panics if `decryptor` was never registered (e.g., a participant who skipped the key-registration round, or an index the local node never saw register).
- `crypto/dkg/pedpop/src/encryption.rs:466` — `self.decryption.enc_keys[&participant]` in `encrypt` panics if a share is requested for a participant whose key was never registered.

All three sites treat attacker-influenced map membership as a panic-level invariant instead of returning `DecryptionError`. `EncryptedMessage::read` / `EncryptionKeyProof::read` / `EncryptionKeyMessage::read` (`encryption.rs:171-177`, `:267-269`, `:57-59`) accept arbitrary bytes and only error on malformed encodings — the crash occurs after successful parsing, purely because the referenced index is absent from local state.

### Impact Explanation
An unprivileged DKG participant (or anyone able to submit blame/registration messages in an in-progress PedPoP session) can crash the process handling their message. Since PedPoP runs inside validator DKG processing, a panic aborts the key-generation session and takes down the affected node's processing task — availability loss equivalent to the CVE's segmentation-fault DoS. No secret material is required; only control over which `Participant` index a blame/registration message claims and whether that index exists in `enc_keys`.

### Likelihood Explanation
Reachable whenever a blame or duplicate registration is processed before the referenced key is in `enc_keys`: e.g., accusing a participant whose `EncryptionKeyMessage` wasn't accepted/parsed locally, or replaying a registration. The inputs (`Participant` index, `EncryptedMessage`, `EncryptionKeyProof`) are all peer-supplied byte fields read via the `read` functions above, so no privileged position is needed beyond being a DKG round participant. The main uncertainty is how strictly higher layers order/validate messages before calling `register`/`decrypt_with_proof`; if upstream deduplication exists, reachability narrows but is not eliminated for the `decryptor`-index path.

### Recommendation
Replace panicking constructs with error returns:

```rust
// encryption.rs:356-360
if self.enc_keys.contains_key(&participant) {
  return Err(io::Error::other("re-registered encryption key"));
}
// encryption.rs:388
let decryptor_key = self.enc_keys.get(&decryptor)
  .ok_or(DecryptionError::InvalidProof)?;
// encryption.rs:466 — surface as io::Result or checked path
```

All `Participant` indexes crossing message boundaries should be validated against registered membership before indexing.

### Proof of Concept
```rust
// Conceptual: build a Decryption box with only one registered key
let mut dec = Decryption::<Ristretto>::new(context);
dec.register(Participant(1), key_msg_for_1);
// Accuser supplies blame referencing decryptor Participant(2),
// who never sent an EncryptionKeyMessage
let bad: Participant = Participant(2);
let proof = EncryptionKeyProof::read(&mut attacker_bytes).unwrap();
let msg = EncryptedMessage::<Ristretto, Share>::read(&mut attacker_bytes, params).unwrap();
// pop must verify — attacker can sign a valid PoP for their own key
dec.decrypt_with_proof(from, bad, msg, Some(proof));
// -> panics at enc_keys[&decryptor]: index not found
```

Result: panic (`HashMap` index out of bounds / assert failure) → thread/process abort, no error return — a remote DoS on the PedPoP blame path.
