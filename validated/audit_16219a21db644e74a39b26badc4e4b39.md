### Title
Unauthenticated `new_deposit` on Aggregator Exhausts Verifier Nonce-Session Map, Permanently Blocking Deposit Finalization — (`core/src/rpc/aggregator.rs`, `core/src/verifier.rs`)

---

### Summary

The Clementine aggregator's `new_deposit` gRPC endpoint carries no caller authentication (`Interceptors::Noop`). Every call to `new_deposit` triggers `NonceGen` on every verifier, inserting a bounded nonce session into each verifier's `AllSessions` map. When the call subsequently fails (invalid deposit), the session is **removed** from the map inside `deposit_sign` but is **never re-inserted**, permanently consuming that slot. An attacker who floods `new_deposit` with crafted-but-plausible deposit outpoints can fill the session maps on all verifiers, causing the oldest sessions to be evicted. A legitimate deposit whose session is evicted between `NonceGen` and `deposit_sign` receives "Session not found", the move-to-vault transaction is never created, and the depositor's BTC is locked in the deposit address.

---

### Finding Description

**Step 1 – No authentication on the aggregator.**

`Interceptors::Noop` passes every request unconditionally: [1](#0-0) 

The aggregator server is built with `Noop` whenever `client_verification` is false (the documented default for the aggregator): [2](#0-1) 

The documentation confirms: *"The aggregator does not enforce client certificates but does use TLS for encryption."* [3](#0-2) 

**Step 2 – `new_deposit` calls `NonceGen` before any on-chain validation.**

Inside `new_deposit`, `create_nonce_streams` (which calls `NonceGen` on every verifier and inserts sessions) is invoked **before** `deposit_sign`, which is where `is_deposit_valid` actually runs: [4](#0-3) 

**Step 3 – Each verifier's session map is bounded; oldest sessions are evicted.**

`AllSessions` enforces `MAX_ALL_SESSIONS_BYTES` and `MAX_NUM_SESSIONS`. When either limit is exceeded, `remove_oldest_session` is called in a loop before the new session is inserted: [5](#0-4) 

**Step 4 – A failed `deposit_sign` permanently consumes the session slot.**

`deposit_sign` removes the session at the start: [6](#0-5) 

It only re-inserts the session on the success path: [7](#0-6) 

If `is_deposit_valid` (called at line 876) rejects the deposit, the session is gone and the slot is permanently consumed for the lifetime of the map. [8](#0-7) 

---

### Impact Explanation

A legitimate deposit's `NonceGen` creates a session. If the attacker floods `new_deposit` calls between that `NonceGen` and the legitimate `deposit_sign`, the session map fills and the legitimate session is evicted. The legitimate `deposit_sign` then fails:

```
session_map.remove_session_with_id(session_id)?
// → Err("Session not found")
```

The move-to-vault transaction is never produced. The depositor's BTC remains locked in the deposit address indefinitely. Because the aggregator is the sole orchestrator of the MuSig2 signing pipeline, no alternative path exists to complete the deposit without restarting the entire `new_deposit` flow — which the attacker can again disrupt.

---

### Likelihood Explanation

- The aggregator is intentionally accessible without client certificates (by design, to accept deposits from users/backends).
- The attacker needs only a TLS connection to the aggregator's gRPC port and any plausible-looking deposit outpoint (a real UTXO of the correct amount sent to a valid deposit address, which is deterministically derivable from public parameters).
- The server-side rate limit and concurrency limit slow the attack but do not prevent it: the attacker can use multiple source IPs or connections, and each successful `NonceGen` call consumes a session slot even if the overall `new_deposit` eventually fails.
- The session map is bounded, so the number of calls required is finite and predictable.

---

### Recommendation

1. **Short term:** Add caller authentication to the aggregator's `new_deposit` endpoint. Even a simple pre-shared API key or a separate mTLS tier for deposit initiators would prevent unauthenticated flooding. Alternatively, move on-chain deposit validation (confirming the UTXO exists, has the correct amount, and matches the expected script) to **before** `create_nonce_streams` is called, so sessions are never generated for invalid deposits.

2. **Short term:** On any failure path inside `deposit_sign`, re-insert the session back into `AllSessions` (or explicitly mark it as available) so that a failed call does not permanently consume a slot.

3. **Long term:** Decouple nonce generation from the `new_deposit` RPC. Pre-generate nonce pools per verifier independently of incoming deposit requests, and only bind a pool to a specific deposit after the deposit outpoint has been validated on-chain.

---

### Proof of Concept

```
# Attacker (no client cert required):
for i in $(seq 1 500); do
  grpcurl -insecure \
    -d '{"deposit_outpoint": {"txid": {"txid": "<any_real_utxo_txid>"}, "vout": 0},
         "deposit_data": {"base_deposit": {"evm_address": "0x...", "recovery_taproot_address": "..."}}}' \
    aggregator:17785 clementine.ClementineAggregator/NewDeposit &
done
wait

# Each call:
# 1. Passes Noop interceptor (no auth check)
# 2. Calls NonceGen on all verifiers → inserts sessions into AllSessions
# 3. Fails at is_deposit_valid (deposit not a valid bridge deposit)
# 4. Session removed in deposit_sign, never re-added → slot consumed

# Legitimate deposit now calls new_deposit:
# → NonceGen creates session (evicts oldest → may evict legitimate session)
# → deposit_sign: remove_session_with_id(session_id) → Err("Session not found")
# → move-to-vault tx never created
# → depositor BTC locked in deposit address
```

The attack requires no privileged key material, no on-chain funds, and no modification of any deployed contract — only network access to the aggregator's gRPC port.
