### Title
Attacker-crafted OP_RETURN in a SinglePlusAnyoneCanPay payout tx lets an unrelated operator be auto-credited for a payout it never funded - ([File: circuits-lib/src/bridge_circuit/spv.rs / mod.rs])

### Summary
The user's `WithdrawParams` signature (`TapSighashType::SinglePlusAnyoneCanPay`) only covers the single withdrawal input and the matching output; per BIP341 `ANYONECANPAY|SINGLE` semantics, every other input/output of the transaction, including the OP_RETURN carrying the operator's x-only pubkey, is unsigned and freely rewritable by anyone. An unprivileged attacker who obtains this signature (e.g. via the public `withdraw`/`internal_withdraw` gRPC, or simply the mempool/relay once an operator broadcasts) can build a competing payout transaction that reuses the exact signed input/output pair, self-funds the withdrawal amount, and stamps an arbitrary, uninvolved operator's x-only pubkey into the OP_RETURN, then broadcast it first.

### Finding Description
The claimed binding is:
`deposit_constant.operator_xonlypk == xonly-pubkey of the party whose BTC actually funded the withdrawer's payout`

Trace:
- `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:161-203`) and `Operator::withdraw` (`core/src/operator.rs:560-637`) only verify that `in_signature.sighash_type == SinglePlusAnyoneCanPay` and that the Schnorr signature is valid for the *committed input+output pair*. They never constrain who supplies the remaining funding inputs or what OP_RETURN payload is attached, because `SIGHASH_SINGLE|ANYONECANPAY` structurally excludes those bytes from the signed digest.
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) is only how the *legitimate* operator would build the tx; nothing prevents an attacker from independently constructing an equivalent transaction with the same signed input/output, their own funding inputs, and an OP_RETURN naming operator `X`.
- `get_first_op_return_output` + `parse_op_return_data` (`circuits-lib/src/bridge_circuit/mod.rs:206-219, 608-617`) blindly extract `operator_xonlypk` from the first OP_RETURN of whichever payout tx got confirmed on-chain — there is no cryptographic link from this value to who funded the transaction's non-signed inputs.
- `deposit_constant` (`circuits-lib/src/bridge_circuit/mod.rs:634-663`) binds this attacker-controlled `operator_xonlypk` directly into the journal hash used by the succinct bridge-circuit proof (also duplicated host-side in `bridge-circuit-host/src/structs.rs:482-516`).
- On the verifier/operator side, the only sanity checks are self-consistency checks, not funding-provenance checks:
  - `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only checks that the OP_RETURN-derived operator equals `kickoff_data.operator_xonly_pk` (i.e. that the same party who names itself in OP_RETURN is the one sending the kickoff) — it never verifies that operator actually paid.
  - `Operator::send_asserts` (`core/src/operator.rs:1284-1295`) performs the identical self-consistency check.
  - `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) simply records whatever pubkey is parsed from OP_RETURN into the DB as the "payer operator," with no funding verification.
  - `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) is fully automated: it calls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and, if any confirmed payout tx's OP_RETURN matches the operator's own pubkey, automatically calls `handle_finalized_payout` and proceeds to kickoff — with zero check that this specific operator broadcast, signed, or funded that transaction.

Exploit flow: the attacker takes the signed input/output pair from a `WithdrawParams` call, builds their own transaction funding the withdrawal amount from their own wallet, sets the OP_RETURN to a completely uninvolved, but real, registered operator `X`'s x-only pubkey (public information obtainable via `fetch_operator_keys`/config), and broadcasts it via any Bitcoin node before any legitimate operator's payout tx confirms. Once confirmed:
1. The withdrawal UTXO is now spent, so no legitimate operator (who might have intended to front this withdrawal for real reimbursement) can ever construct a valid competing payout tx — "an honest operator permanently unable to be reimbursed."
2. Operator `X`'s own automation (`PayoutCheckerTask`) sees "its" OP_RETURN match and automatically drives the kickoff → bridge-circuit → assert/disprove flow, which succeeds because every downstream check (`is_kickoff_malicious`, `send_asserts`, the circuit's `deposit_constant`) only compares OP_RETURN-derived identity to kickoff-sender identity, never to "who actually funded the payout tx." `X` ends up reimbursed from the move-to-vault deposit collateral for BTC it never sent — "an operator reimbursed for a payout it never funded," breaking the claimed equality exactly as stated.

### Impact Explanation
This directly matches two Critical categories: (a) an operator reimbursed for a payout it never funded (operator `X` gets bridge collateral released to it without spending any of its own BTC), and (b) an honest operator's inability to ever be reimbursed for that withdrawal (the withdrawal UTXO is a single-spend resource; once front-run, no other operator can claim it). The blast radius is per-withdrawal and repeatable: any time an attacker observes a signed `WithdrawParams` before it is broadcast by an operator, they can front-run it naming any registered operator of their choosing, across any number of deposits/withdrawals, at the cost of funding one withdrawal payout per attempt.

### Likelihood Explanation
Preconditions: the attacker needs a legitimately signed `SinglePlusAnyoneCanPay` withdrawal (obtainable via the public `withdraw`/`internal_withdraw` gRPC calls, which are explicitly reachable by an unprivileged caller per the threat model, or by observing an operator's own payout tx in the mempool before confirmation), knowledge of a target operator's public x-only pubkey (public), and enough BTC to fund the withdrawal output plus fees (a real but bounded cost, no more than the withdrawal amount itself). No key compromise, no majority hashrate, and no privileged role is required — this is feasible purely as a mempool/broadcast race using public gRPC/Bitcoin RPC access, which is explicitly in-scope for the stated unprivileged attacker.

### Recommendation
Bind the operator identity cryptographically to the transaction's actual funding, not to an unsigned OP_RETURN. Options: require the operator's signature over the full payout transaction (e.g., have the operator co-sign with SIGHASH_ALL or a covenant-style commitment covering the funding inputs and OP_RETURN), or require the funding inputs themselves to be provably controlled by the operator named in OP_RETURN (e.g., a distinguished operator-collateral-tagged input verified in-circuit). At minimum, `PayoutCheckerTask`/`is_kickoff_malicious`/`send_asserts` should refuse to treat a payout as "this operator's" unless the operator itself recorded having broadcast that specific txid (e.g., compare against the operator's own tx-sender history) rather than trusting the OP_RETURN payload alone.

   - input[0] = the withdrawer's dust UTXO with a valid `SinglePlusAnyoneCanPay` signature over output[0] only,
   - additional funding input(s) controlled by a synthetic "attacker" key (not any registered operator's key),
   - output[0] = the withdrawer's committed payout (script/amount identical to what the signature covers),
   - OP_RETURN output naming operator `X`'s x-only pubkey, where `X` is a distinct, uninvolved test operator key.
2. Run `bridge_circuit::deposit_constant` / `get_first_op_return_output` (or the full `bridge_circuit` entrypoint via `mock_zkvm`) and assert:
   - `deposit_constant.operator_xonlypk == X.serialize()` (left side of the claimed equality),
   - while the transaction's actual funding key controlling the extra input is the attacker's key ≠ X (right side),
   - i.e., assert `deposit_constant.operator_xonlypk != actual_funder_pubkey`, demonstrating the equality is broken and the circuit still accepts/commits the journal hash successfully.
3. Separately (core integration test), simulate `PayoutCheckerTask::run_once` for operator `X` against a DB row where `update_finalized_payouts` recorded the spoofed OP_RETURN pubkey, and assert it proceeds to call `handle_finalized_payout` despite `X` never having called `Operator::withdraw`/`fund_raw_transaction` for that txid.
