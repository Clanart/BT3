### Title
Out-of-bounds slice panic in `console.log` precompile via crafted `string`/`bytes` offset - (File: blockchain/vm/contracts.go)

### Summary
The `consoleLog` precompile (Hardhat-style `console.log`, gas cost `0`) decodes ABI-encoded `string`/`bytes` arguments by reading a 32-byte "offset" word directly from attacker-controlled calldata and converting it with `big.Int.Int64()` without validating that the result is non-negative or in-range before using it as a slice index. This mirrors the OOB-read bug class in CVE-2025-11211 (crafted input causing out-of-bounds memory access during data parsing), except here it is reachable purely via a Kaia transaction/contract call rather than a browser page.

### Finding Description
`consoleLog.decode` at [1](#0-0)  for the `StringTy`/`BytesTy` cases computes:

```go
start := int(big.NewInt(0).SetBytes(params[pos : pos+registerSize]).Int64())
if len(params) < start+registerSize { ... }
size := int(big.NewInt(0).SetBytes(params[start : start+registerSize]).Int64())
```

`big.Int.Int64()` on a value that doesn't fit in an `int64` returns the low 64 bits reinterpreted as a signed `int64` (per Go's documented "undefined but deterministic" behavior for out-of-range values). An attacker can choose the 32-byte "offset" word in the call data such that `Int64()` yields a **negative** `int` value for `start`. The subsequent bounds check `len(params) < start+registerSize` is computed with signed integer arithmetic, so a sufficiently negative `start` makes `start+registerSize` negative as well, and the check `len(params) < (negative number)` is false — the guard is bypassed. The code then executes `params[start : start+registerSize]` with a negative `start`, which triggers an unrecovered Go runtime panic (`slice bounds out of range`), not a normal EVM `error` return.

The precompile is registered and dispatched like any other precompile via `RunPrecompiledContract` in `blockchain/vm/contracts.go`, and its address/cost function returns `(0, 0)` [2](#0-1) , meaning any account (an ordinary EOA transaction sender, or any contract making a `CALL`/`STATICCALL`) can invoke it directly and for free by targeting the console.log precompile address with a crafted selector + payload matching an entry in `common.ConsoleLogSignatures`.

Unlike the browser CVE, Go's runtime does not silently read adjacent memory on an out-of-bounds slice access — it panics. Searching the `blockchain/vm` package shows no `recover()` guarding contract/precompile execution, so a panic raised inside `Run()` propagates up through `EVM.Call` → the state transition / block-processing call stack. If none of the callers up the chain (worker, state processor, `ApplyTransaction`, etc.) install a `recover()`, this becomes an unhandled panic that crashes the node process that is executing/validating the transaction — turning a single crafted transaction into a chain-wide denial-of-service/consensus-halt vector, since every node (validator and endpoint node) that processes the block containing this transaction will independently hit the same panic.

### Impact Explanation
If the panic is indeed unrecovered up the call stack (which I could not fully confirm beyond the `blockchain/vm` package boundary within this investigation), then any single unprivileged transaction sender or contract deployer can crash all nodes that execute the transaction/block, i.e., a chain-halting DoS — a High severity, consensus-availability-impacting bug reachable from a single submitted transaction, consistent with the required "state divergence between honest nodes" / block-processing invalidity category. If a `recover()` exists further up the stack (e.g., in the tx-processing/mining code, which I was not able to verify with the remaining tool budget), the practical impact would be downgraded to a caught error causing the transaction to simply fail/revert, which would not meet the severity bar for this report.

### Likelihood Explanation
Likelihood is high assuming no upstream `recover()`: the trigger requires only a single, cheaply-gas-priced (the precompile itself costs 0 gas) transaction or internal `CALL` to the console.log precompile address with an attacker-chosen 32-byte word that yields a negative `int64` via `big.Int.Int64()` truncation — no special privileges, staking, or governance access needed.

### Recommendation
In `consoleLog.decode` (`blockchain/vm/contracts.go`), validate that `start` (and `size`) are non-negative and fit within `len(params)` using unsigned arithmetic / `uint64` comparisons before using them as slice bounds (e.g., check `start < 0 || start > len(params)-registerSize` first, and similarly bound `size`), rather than relying on `big.Int.Int64()` output directly as an `int` index. Additionally, wrap precompiled-contract execution (`RunPrecompiledContract`) with a `recover()` that converts any panic into an EVM execution error, so that a single malformed input can never crash the node process regardless of future decoding bugs.

### Proof of Concept
1. Craft calldata for the console.log precompile matching a known selector in `common.ConsoleLogSignatures` whose corresponding type list includes a `StringTy` or `BytesTy` parameter.
2. In the 32-byte word at the parameter's `pos` (the "offset" slot), place a value whose low 64 bits, interpreted as signed `int64`, are negative (e.g., a 32-byte word with only the most-significant-bit region and low bits set such that `big.Int.SetBytes(...).Int64()` returns a negative number, e.g. bytes `0xFFFFFFFFFFFFFFFF...` in the low 8 bytes with the value `0x8000000000000000`).
3. Send/execute a transaction whose EVM code performs a `CALL`/`STATICCALL` to the console.log precompile address with this calldata (or, if reachable directly, send the transaction with `to` = the precompile address and this `data`).
4. During EVM execution, `consoleLog.Run` → `toLogString` → `decode` computes a negative `start`, the bypassed length check lets execution reach `params[start:start+registerSize]`, and Go panics with `slice bounds out of range` inside precompile execution, propagating as an unhandled panic if no `recover()` exists further up the call chain.
