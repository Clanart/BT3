### Title
Zero-value outputs are reported as received funds by the Bitcoin `Scanner` - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the reported `mintFresh(0)` bug — a zero-amount operation that changes no meaningful state yet completes "successfully" and emits a success-indicating record — `Scanner::scan_transaction` in bitcoin-serai registers any output paying to a tracked `script_pubkey` as a `ReceivedOutput`, with no check that `output.value` is non-zero or economically spendable.

### Finding Description
`Scanner::scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for every output whose `script_pubkey` is in `self.scripts`, unconditionally:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
``` [1](#0-0) 

The same occurs in `scan_block` [2](#0-1) , and `ReceivedOutput::read` deserializes a `TxOut` without any value/dust validation [3](#0-2) . A `TxOut` with `value = 0` is consensus-valid (zero-value outputs are only non-standard under relay policy, and even sub-`DUST` (546 sat) values are not rejected here — `DUST` is only enforced on outgoing payments in `SignableTransaction::new`, not on received inputs [4](#0-3) ).

Just as `mintFresh(0)` emits a success event while minting nothing, a `ReceivedOutput` is emitted to the caller asserting funds were received, while a zero/sub-dust output carries zero or negative-net value (spending it costs more in fees than it is worth — each Taproot input adds ~58 vbytes of weight [5](#0-4) ).

### Impact Explanation
Any third party can send a 0-value (or sub-dust) output to a published multisig `script_pubkey`. The scanner reports it as a received `ReceivedOutput`, inflating apparent received funds. Downstream, `SignableTransaction::new` will accept it as an input (`input_sat` includes 0-value outputs [6](#0-5) ), so it either wastes fee weight or, if relied upon as spendable balance, produces transactions that fail `NotEnoughFunds` — i.e., funds reported received that are not spendable.

### Likelihood Explanation
An unprivileged attacker only needs to broadcast a valid Bitcoin transaction paying a dust/zero output to a known multisig script — a public, low-cost action requiring no collusion or privilege.

### Recommendation
Reject outputs below the `DUST` constant (already defined in `send.rs`) in `Scanner::scan_transaction` / `scan_block`, or at minimum expose the value check so callers cannot mistake zero-value outputs for spendable funds. Also validate `output.value != 0` in `ReceivedOutput::read` for defense in depth.

Note: `processor/src/multisigs/scanner.rs` filters `output.balance().amount.0 >= N::DUST` downstream [7](#0-6) , which mitigates this for the in-tree processor, but the in-scope library primitive itself accepts and reports valueless outputs.

### Proof of Concept
1. `Scanner::new(even_key)` for the multisig key.
2. Attacker crafts a transaction with `TxOut { value: Amount::ZERO, script_pubkey: p2tr_script_buf(key) }`.
3. `scanner.scan_transaction(&tx)` returns a `ReceivedOutput` with `value() == 0` — reported as received despite carrying no spendable value.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
