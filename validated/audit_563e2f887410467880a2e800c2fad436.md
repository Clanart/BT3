## Title
One withdrawal UTXO can duplicate to two different Citrea withdrawal indices, causing a single payout spend to falsely mark two indices as paid ("ONE PAYOUT, TWO REIMBURSEMENTS") - (File: `core/src/database/verifier.rs`)

## Summary
`update_withdrawal_utxo_from_citrea_withdrawal` writes `withdrawal_utxo_txid`/`withdrawal_utxo_vout` per Citrea withdrawal index with no uniqueness constraint across indices, and `get_payout_txs_for_withdrawal_utxos` joins purely on `(txid, vout)` equality against `bitcoin_syncer_spent_utxos`. If an attacker registers the same Bitcoin outpoint for two different Citrea withdrawal indices `i` and `j` via two `withdraw()` calls to the Citrea Bridge contract, a single real spend of that outpoint causes both `i` and `j` to be marked as paid by the same payout transaction. [1](#0-0) [2](#0-1) 

## Finding Description
The claimed binding is: `withdrawals.idx == the Citrea withdrawalUTXOs[idx] outpoint` should be a bijection — each `(withdrawal_utxo_txid, withdrawal_utxo_vout)` pair should attribute to exactly one `idx`. This binding is not enforced anywhere in the Rust/DB layer.

`update_withdrawal_utxo_from_citrea_withdrawal` performs a bare `UPDATE ... WHERE idx = $1` with the outpoint bytes taken directly from Citrea's `withdrawalUTXOs[idx]`, with no check that this `(txid, vout)` is not already used by another `idx`. [1](#0-0) 

`collect_withdrawal_utxos` simply reads each sequential Citrea withdrawal slot and returns whatever outpoint bytes the contract's `withdraw()` caller supplied — these are attacker-controlled, unauthenticated at registration time (no ownership signature is required by `withdraw()` itself; the Bitcoin signature is only checked later by the operator during payout construction). [3](#0-2) [4](#0-3) 

`get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`. If two rows `i` and `j` share the same `(txid, vout)`, a single spend event of that outpoint matches BOTH rows. [2](#0-1) 

`update_finalized_payouts` then blindly writes the same `payout_txid`, `payer_operator_xonly_pk`, and `payout_tx_blockhash` into every matched row — including `j`, which was never actually paid. [5](#0-4) 

This propagates into value-moving logic: `is_kickoff_malicious` looks up payout info keyed by `move_to_vault_txid` (unique per deposit/index) and treats a matching `operator_xonly_pk`/committed blockhash as proof of an honest payout, skipping the challenge. [6](#0-5)  Worse, `get_first_unhandled_payout_by_operator_xonly_pk` is polled automatically by `PayoutCheckerTask::run_once`, which will pick up the *fraudulently attributed* row `j` (because `payout_payer_operator_xonly_pk = $1` matches) and automatically drive `handle_finalized_payout` → kickoff → reimbursement for a withdrawal the operator never funded. [7](#0-6) [8](#0-7) 

Exploit flow:
1. Attacker makes (or already owns) two deposits into the bridge, receiving Citrea withdrawal slots `i` and `j` (each with its own `move_to_vault_txid`).
2. Attacker owns a Bitcoin UTXO `X:0` (e.g. a small dust output they control).
3. Attacker calls the Citrea Bridge contract's `withdraw(txid=X, vout=0)` twice, registering `withdrawalUTXOs[i] = X:0` and `withdrawalUTXOs[j] = X:0` (no on-chain dedup check exists in this repo's client/DB path, and `withdraw()` requires no Bitcoin ownership proof at registration time).
4. Clementine's Citrea sync writes both rows via `update_withdrawal_utxo_from_citrea_withdrawal`, giving `idx=i` and `idx=j` identical `withdrawal_utxo_txid/vout`.
5. Attacker submits a valid gRPC `withdraw` for index `i` only, with a valid signature over `X:0`; some operator constructs and broadcasts the real payout transaction `Y` spending `X:0`.
6. `get_payout_txs_for_withdrawal_utxos` matches both `i` and `j` to `Y` because of the duplicate outpoint columns; `update_finalized_payouts` marks both rows paid by `Y` with the paying operator's xonly key.
7. That operator's own `PayoutCheckerTask` (or any verifier checking kickoffs) now treats withdrawal `j` as legitimately paid by them, and the operator can be reimbursed for `j` from the round/collateral machinery despite having spent BTC only once (for `X:0`).

Existing guards fail because: `is_deposit_valid`, `Operator::withdraw`'s outpoint-match check, and `sign_optimistic_payout`'s outpoint-match check all compare a *single* index's DB-recorded outpoint against the caller-provided outpoint — none of them detect or prevent a second index from having been silently populated with the same outpoint before the spend. The final circuit-level `verify_storage_proofs` binds `storage_proof.index` to the Citrea storage slot value, but the storage slot for `j` genuinely equals `X:0` on Citrea (since the attacker legitimately paid to register it there), so the circuit sees a consistent (if collided) value — the collision itself is never checked.

## Impact Explanation
The operator that processes the real payout for index `i` can end up credited/reimbursed for index `j` as well, without ever transferring any Bitcoin value for `j`. This is exactly the Critical category "operator reimbursed for a payout it never funded," extracting bridge collateral/round funds disproportionate to actual value fronted. It also blocks the honest resolution of index `j`: if a *different, honest* operator later tries to legitimately service withdrawal `j`, `is_kickoff_malicious`/payout bookkeeping for `j` already shows a payout by a different operator and blockhash, so the honest operator's kickoff may be judged malicious or their fronted payment permanently unrecognized — i.e., "an honest operator permanently unable to be reimbursed." The blast radius scales with however many withdrawal indices the attacker is willing to register with a colliding outpoint (bounded only by the number of deposits/withdrawal registrations the attacker funds on Citrea), and is repeatable across any pair of indices and any operator that happens to service the first of the pair.

## Likelihood Explanation
Feasibility depends heavily on preconditions that are outside pure Clementine control:
- The attacker must be able to register the same outpoint twice at the Citrea Bridge contract without the contract detecting/rejecting the duplicate — this is a Citrea Bridge contract behavior not verifiable from this repo (contract source isn't in scope/available here; only the Rust client wrapper and ABI usage are visible), so it cannot be conclusively proven from this codebase alone that `withdraw()` permits registering a duplicate outpoint across indices.
- The attacker needs at least two funded deposit slots (paying bridge_amount each) to obtain two withdrawal indices, and needs a Bitcoin UTXO they control to reuse as the "shared" outpoint.
- No DB uniqueness constraint or application-level check currently guards against the (txid, vout) collision in `core/src/database/schema.sql`/`update_withdrawal_utxo_from_citrea_withdrawal`, so once the collision exists on Citrea, propagation into Clementine's DB and the automatic reimbursement path (`PayoutCheckerTask`) is deterministic and requires no further attacker action.

## Recommendation
Add a uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table (or enforce it at write time in `update_withdrawal_utxo_from_citrea_withdrawal`), and make `get_payout_txs_for_withdrawal_utxos` / `update_finalized_payouts` fail loudly (rather than silently multi-attributing) if more than one `idx` maps to the same spent outpoint in a block, so the ambiguity is surfaced as an error instead of being resolved by crediting all matching indices.

#[tokio::test]
async fn duplicate_withdrawal_utxo_across_two_indices_conflates_payout() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();
    let mut dbtx = db.begin_transaction().await.unwrap();

    let shared_utxo = bitcoin::OutPoint {
        txid: bitcoin::Txid::from_byte_array([0x11; 32]),
        vout: 0,
    };
    let spending_txid = Txid::from_byte_array([0x99; 32]);
    let move_txid_i = Txid::from_byte_array([0xAA; 32]);
    let move_txid_j = Txid::from_byte_array([0xBB; 32]);
    let idx_i = 1u32;
    let idx_j = 2u32;

    let block_id = db.insert_block_info(Some(&mut dbtx), &BlockHash::all_zeros(), &BlockHash::all_zeros(), 0).await.unwrap();
    db.insert_txid_to_block(&mut dbtx, block_id, &spending_txid).await.unwrap();
    db.insert_spent_utxo(&mut dbtx, block_id, &spending_txid, &shared_utxo.txid, shared_utxo.vout.into()).await.unwrap();

    // Two separate deposits/indices
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_i, &move_txid_i).await.unwrap();
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_j, &move_txid_j).await.unwrap();

    // Attacker registers the SAME outpoint for both withdrawal indices
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_i, shared_utxo, block_id).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_j, shared_utxo, block_id).await.unwrap();

    // ONE real spend of the shared outpoint is observed
    let txs = db.get_payout_txs_for_withdrawal_utxos(Some(&mut dbtx), block_id).await.unwrap();

    // VIOLATION: both idx_i and idx_j are attributed the same single spend
    assert_eq!(txs.len(), 2);
    assert!(txs.iter().any(|(idx, txid)| *idx == idx_i && *txid == spending_txid));
    assert!(txs.iter().any(|(idx, txid)| *idx == idx_j && *txid == spending_txid));
    // Binding "withdrawal_utxo uniquely and exclusively records idx" is broken:
    // idx_i's fronted UTXO == idx_j's fronted UTXO, yet only one Bitcoin spend occurred.
}

    async fn collect_withdrawal_utxos(
        &self,
        last_withdrawal_idx: Option<u32>,
        to_height: u64,
    ) -> Result<Vec<(u64, OutPoint)>, BridgeError> {
        let mut utxos = vec![];

        let mut start_idx = match last_withdrawal_idx {
            Some(idx) => idx + 1,
            None => 0,
        };

        loop {
            let withdrawal_utxo = self
                .contract
                .withdrawalUTXOs(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;
            match withdrawal_utxo {
                Err(e) if e.to_string().contains("execution reverted") => {
                    tracing::trace!("Withdrawal utxo not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}
            }
            let withdrawal_utxo = withdrawal_utxo.expect("Failed to get withdrawal UTXO");
            let txid = withdrawal_utxo.txId.0;
            let txid =
                Txid::from_slice(txid.as_ref()).wrap_err("Failed to convert txid to Txid")?;
            let vout = withdrawal_utxo.outputId.0;
            let vout = u32::from_le_bytes(vout);
            let utxo = OutPoint { txid, vout };
            utxos.push((start_idx as u64, utxo));
            start_idx += 1;
        }
        Ok(utxos)
    }

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN

                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk

                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self

                Some(&mut dbtx),

            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;

            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;
