### Title
Distribution precompile `rewards()` view accepts and permanently strands ETH/usei value sent with the call - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards` query method of the distribution precompile (address `0x...1007`) is dispatched without a non-payable check, unlike every other method on the same precompile. Any account can call `rewards(address)` with a non-zero `msg.value` and the call succeeds; the sent usei/wei is transferred to the precompile's module address as part of normal EVM value transfer semantics, but no code path ever refunds or moves it back out, permanently locking the funds.

### Finding Description
The precompile's `Execute` switch statement calls `pcommon.ValidateNonPayable(value)` for state-mutating methods such as `WithdrawValidatorCommissionMethod` [3](#0-2) , and query methods pass `value` through to their handler functions (`p.params(ctx, method, args, value)`, `p.validatorOutstandingRewards(ctx, method, args, value)`, etc.) [4](#0-3) . In contrast, `case RewardsMethod: return p.rewards(ctx, method, args)` at line 205 neither validates `value` is zero nor even forwards it to `rewards` for any downstream check [1](#0-0) .

Because in Sei's EVM, `value` sent in a top-level or internal call is transferred via the EVM's normal balance-transfer machinery (StateDB `SubBalance`/`AddBalance`, which map to usei/wei bank keeper credits/debits at the associated Sei address for the precompile) before/around precompile execution, a `rewards()` call carrying `msg.value > 0` succeeds and the value is credited to the precompile module account rather than reverted. Since `rewards()` is a pure informational query with no mechanism to route or refund an accidental payment, and there is no other function on the distribution precompile (or anywhere else) to sweep/withdraw balance mistakenly sent to the module address via this path, the funds are permanently stuck.

This is a maintainer-acknowledged behavior, explicitly called out in the audit/regression test file's comment block, which states the spec "deliberately has no 'view rejects value' test" because a value-bearing call to `rewards()` "would succeed and strand the funds" [5](#0-4) .

### Impact Explanation
Any unprivileged EVM transaction sender or contract that calls `rewards(address)` on the distribution precompile with a nonzero `value` (either by mistake, by a poorly written wallet/dApp integration, or an attacker tricking a user/contract into doing so) will have that Sei/usei permanently locked with no recovery path — a direct, irreversible loss of user funds. This matches the "permanent freezing of funds" impact class.

### Likelihood Explanation
Likelihood is moderate: this requires an EOA or contract to explicitly attach `value` to a call that is semantically a view/query, which is an easy user/integration mistake (e.g., mis-generated calldata, a wallet defaulting to reuse `value` from a prior payable call, or bundlers/aggregators that attach value to batched multicalls without per-call `ValidateNonPayable` guarantees). Because all sibling methods on the same precompile enforce non-payable behavior and revert cleanly, users/integrators reasonably assume the whole precompile is protected, increasing the chance of an accidental payable call to this one exception going unnoticed until funds are already lost.

### Recommendation
Add the same non-payable enforcement used elsewhere in the precompile to the `rewards` view: call `pcommon.ValidateNonPayable(value)` (or pass `value` into `p.rewards` and validate there) before executing the query, exactly matching the pattern already used by `ParamsMethod`, `ValidatorOutstandingRewardsMethod`, and other read-only methods. Additionally, run the same audit across all precompiles' `Execute` switch statements to confirm no other query/view method omits the non-payable guard.

### Proof of Concept
1. Deploy/use any EVM account associated with a Sei address.
2. Call the distribution precompile at `0x0000000000000000000000000000000000001007` via `rewards(address delegatorAddress)` while attaching `value: 1000000000000` wei (1 usei) or more, e.g.:
   ```js
   const distribution = new ethers.Contract(DISTR_PRECOMPILE_ADDRESS, abi, signer);
   await distribution.rewards(signer.address, { value: ethers.parseEther("1") });
   ```
3. The transaction succeeds (returns `1`/success status) because `Execute`'s `RewardsMethod` branch never calls `ValidateNonPayable`, unlike `params`/`validatorOutstandingRewards`/state-mutating methods [6](#0-5) .
4. The sent value is debited from the caller's balance and credited into the precompile's underlying module account balance through the normal EVM value-transfer/StateDB bridge, with no function existing anywhere to withdraw or refund it — the value is permanently locked, as explicitly acknowledged in the test suite comment [5](#0-4) .
