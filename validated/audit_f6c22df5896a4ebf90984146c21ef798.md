### Title
Unbounded backward-chain walk in `Offer.get_root_removal` allows a crafted offer to hang the wallet (analog of CVE-2016-8576) - ([File: chia/wallet/trading/offer.py])

### Summary
CVE-2016-8576 is an infinite-loop DoS caused by QEMU's `xhci_ring_fetch` following a chain of link Transfer Request Blocks (TRBs) with no bound on how many links may be followed, letting an attacker construct a self-referential/looping chain that never terminates. The same bug class — walking a parent/child linkage supplied by an untrusted party with no cycle detection or iteration bound — exists in `Offer.get_root_removal` in `chia/wallet/trading/offer.py`, which is exercised whenever a wallet user inspects/accepts/cancels an untrusted offer file.

### Finding Description
`Offer.get_root_removal` walks backward from a given coin through the offer's `removals()` set, following `coin.parent_coin_info` links until it reaches a coin that is a "non-ephemeral" removal: [1](#0-0) 

```python
def get_root_removal(self, coin: Coin) -> Coin:
    all_removals: set[Coin] = set(self.removals())
    all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
    non_ephemeral_removals: set[Coin] = {
        c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
    }
    if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
        raise ValueError("The specified coin is not a coin in this bundle")

    while coin not in non_ephemeral_removals:
        coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

    return coin
```

The `removals()` set is derived purely from the `coin_spends` embedded in the attacker/counterparty-supplied `Offer`/`SpendBundle` object (a serialized offer file that a wallet user loads or receives), not from any chain-validated state. `Coin.name()` and `parent_coin_info` are attacker-controlled fields inside that bundle before the bundle is ever validated against the blockchain. Because the `while` loop has no visited-set / iteration bound, and only terminates when it lands on a coin in `non_ephemeral_removals`, a bundle whose removal coins form a cycle in the "coin id -> parent_coin_info" graph (e.g., coin A's parent_coin_info equals coin B's name and vice versa, both present in `coin_spends`) will never satisfy the loop's termination condition, causing `next()` to keep resolving indefinitely inside an unbounded `while True`-equivalent loop — a direct infinite-loop / DoS analog to the unbounded TRB-link chain walk in the CVE.

`get_root_removal` is called by `get_pending_amounts()` (used to build the JSON summary of pending amounts for offers) and `get_primary_coins()` (used by `get_cancellation_coins()`), both of which are invoked from `chia/wallet/trade_manager.py` when handling an offer the wallet user is viewing, taking, or cancelling.

### Impact Explanation
This is a spend-triggered transaction-processing halt: a wallet user (or offer counterparty) loading/parsing a malicious offer file causes the wallet process to hang in an infinite Python loop while holding the wallet lock, since these summary/cancellation code paths are invoked during normal offer-viewing/-taking/-cancelling RPC calls. This denies service to the wallet, matching the "spend-triggered transaction-processing halt" impact bucket, at Medium severity — consistent with the CVE's local DoS via unbounded linked-structure iteration.

### Likelihood Explanation
Likelihood is moderate: an attacker only needs to craft an `Offer`/`SpendBundle` whose (unvalidated, pre-blockchain) coin_spends form a cyclic `parent_coin_info -> name()` relationship among the removal coins and get a wallet user to load/view/accept/cancel that offer file — a normal, low-privilege user action. No signature validity or on-chain acceptance is required to trigger the hang, since the vulnerable code executes before/during offer inspection, not after confirmation.

### Recommendation
Add a visited-coin set (or a hard iteration cap) to `get_root_removal`'s `while` loop, raising a `ValueError`/rejecting the offer immediately if a cycle is detected (i.e., if the same coin id is revisited) instead of looping indefinitely. Additionally, validate that an offer bundle's coin_spends form a valid DAG (no cycles) as part of offer sanity-checking before this code path is reached.

### Proof of Concept
Conceptually: construct a `SpendBundle` with two `CoinSpend`s for coins A and B such that `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()` (both coins otherwise minimal/valid enough to be included in `coin_spends`, with no coin being an addition so both remain in `removals()`). Wrap it in an `Offer` and call `offer.get_pending_amounts()` or `offer.get_cancellation_coins()` (as triggered via `trade_manager.py` when a user inspects/cancels the offer): `get_root_removal` will loop forever because `non_ephemeral_removals` (computed from the same cyclic parent-id relationships) never contains either coin, and the `while` loop keeps resolving `next()` between A and B without termination.
