### Title
Authz "join-class" bypass of the EVM-tx nested-message guard - ([File: app/antedecorators/authz_nested_message.go])

### Summary
The iTop CVE is a class of bug where an authorization check only inspects the object named in the outer query (SELECT clause) while identical objects reachable through a join are left unchecked. Sei-chain's `AuthzNestedMessageDecorator` has the same structural weakness: it walks `authz.MsgExec` "joins" recursively looking for a nested `*evmtypes.MsgEVMTransaction`, but its `switch` statement only recurses into further `*authz.MsgExec` wrappers and silently `continue`s (i.e. treats as safe) any other Cosmos SDK message type, even ones that themselves carry an arbitrary list of `sdk.Msg` to be executed in the same transaction.

### Finding Description
`NewAnteHandler` in [1](#0-0)  installs `antedecorators.NewAuthzNestedMessageDecorator()` as the guard that is supposed to prevent `MsgEVMTransaction` from ever being routed through the Cosmos `authz` grant/exec path (which has none of the EVM-specific fee, nonce, and signature checks that `evmAnteDecorators` enforce).

The decorator's logic is: [2](#0-1) 

It only recognizes two cases in its type switch: `*evmtypes.MsgEVMTransaction` (reject) and `*authz.MsgExec` (recurse). Every other message type falls into `default: continue`, i.e. is treated as harmless and is never inspected for nested content. The identical pattern also exists in the (now presumably legacy/duplicate) helper `CheckAuthzContainsEvm` in [3](#0-2) .

This mirrors the iTop bug exactly: the access check ("does this tx contain an EVM message that must go through evmAnteDecorators") is only enforced on the object type explicitly enumerated (`authz.MsgExec`), not on every code path capable of carrying a nested message list to execution within the same or a subsequently triggered handler — the "join" in this analogy is any other wrapper message type that embeds/dispatches arbitrary `sdk.Msg`s and is processed by the same top-level `anteHandler`/msg-service router without being unwrapped by this decorator.

### Impact Explanation
If any Cosmos message type reachable in the standard `anteDecorators` pipeline (before `evmAnteDecorators` is invoked) can carry or trigger execution of an embedded `MsgEVMTransaction` and is not `*authz.MsgExec`, this decorator will not catch it, and the EVM transaction could be processed while bypassing `evmante.NewEVMNoCosmosFieldsDecorator`, `evmante.NewEVMFeeCheckDecorator`, `evmante.NewEVMSigVerifyDecorator`, and `evmante.NewGasDecorator` (see the `evmAnteDecorators` slice at [4](#0-3) ). Bypassing fee/signature/gas checks for an EVM transaction could enable fee/gas abuse or unauthorized EVM execution attributable to another account's authz grant, which the decorator was specifically designed to prevent (see the explicit ante-ordering comment about `EVMPreprocessDecorator` short-circuiting later handlers at [5](#0-4) ).

### Likelihood Explanation
This is **unconfirmed** rather than proven: my search only found `authz.MsgExec` as the sole outer wrapper type registered in the standard message routing that is capable of carrying arbitrary nested `sdk.Msg`s reachable from a single signed transaction within `app/ante.go`'s `anteDecorators` chain. I was not able to fully verify, within the available indexed code, whether any other message type in this codebase (e.g., `x/group` exec, ICA `MsgSubmitTx`, or a custom Sei message) is registered in the tx router and also carries a nested/embedded message list that reaches `MsgHandler` execution without being decoded and checked by `AuthzNestedMessageDecorator` or an equivalent guard. Without confirming such a second wrapper type exists and is enabled in this chain's module set, this remains a structurally identical but not concretely exploited instance of the iTop bug class — the code pattern (allow-list of one wrapper type, default-continue on everything else) is the same root cause, but the reachable severity depends on whether a second "join" message type currently exists in this build's registered modules.

### Recommendation
Change the nested-message scan from an allow-list (`switch` on known safe types) to a deny-by-default check: recursively inspect every message that implements a "get nested messages" style interface (or explicitly walk the full set of message types the msg service router can dispatch to), rather than special-casing only `*authz.MsgExec`. Alternatively, move the EVM-message exclusion check to run generically against `tx.GetMsgs()` at every level of nesting regardless of the wrapping type, and add a test asserting that no currently-registered message type can smuggle a `MsgEVMTransaction` through the standard `anteHandler` without traversing `evmAnteDecorators`.

### Proof of Concept
Not concretely constructible from the indexed code alone: doing so requires confirming a second registered Cosmos message type (besides `authz.MsgExec`) in this chain's module set that (a) is routed through the standard `anteHandler`/msg-service pipeline shown in [6](#0-5)  and (b) itself carries/dispatches an embedded `sdk.Msg` list including a `MsgEVMTransaction`. I could not verify this second condition within the available index; a Devin session with full repo/module registration visibility (`app.go` module manager, all `x/*` proto message definitions) would be needed to confirm or rule out a concrete second wrapper type before this can be escalated from "structural analog" to "proven exploit."

func (ad AuthzNestedMessageDecorator) CheckAuthzContainsEvm(ctx sdk.Context, authzMsg *authz.MsgExec, nestedLvl int) (bool, error) {
	if nestedLvl >= maxNestedMsgs {
		return false, errors.New("permission denied, more nested msgs than permitted")
	}
	msgs, err := authzMsg.GetMessages()
	if err != nil {
		return false, err
	}
	for _, msg := range msgs {
		// check if message type is authz exec or evm
		switch m := msg.(type) {
		case *evmtypes.MsgEVMTransaction:
			return true, nil
		case *authz.MsgExec:
			// find nested to check for evm
			valid, err := ad.CheckAuthzContainsEvm(ctx, m, nestedLvl+1)
			if err != nil {
				return false, err
			}
			if valid {
				return true, nil
			}
		default:
			continue
		}
	}
	return false, nil
