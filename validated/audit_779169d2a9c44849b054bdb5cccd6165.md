### Title
Encrypted DKG share PoP omits the recipient, allowing replay of a valid `EncryptedMessage` to a different recipient and wrongful blame of an honest sender - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
Analogous to the JOJO finding — a Schnorr signature whose challenge fails to bind all semantically relevant data can be replayed in a context it wasn't produced for — PedPoP's per-message proof-of-possession (`pop_challenge`) binds the context, sender, nonce, key, and ciphertext, but **not the intended recipient**. An `EncryptedMessage` that Alice created for Bob is therefore also a fully valid `EncryptedMessage` "for" any other participant, and will pass PoP verification when replayed under a different `(sender, recipient)` pair.

### Finding Description
In `encrypt`, the per-message encryption key is `k` with `key = k·G`, and the ciphertext is encrypted under `cipher(context, ecdh(k, to))` where `to` is the *recipient's* registered encryption public key. The accompanying PoP signature is computed as:

```rust
// crypto/dkg/pedpop/src/encryption.rs
pop_challenge::<C>(context, pub_nonce, pub_key, from, msg)
```

`pop_challenge` (encryption.rs:302-324) transcripts `context`, `nonce`, `key`, `sender` (`from`), and `message` — there is no `recipient`/`to` field anywhere in the challenge.

On verification, `Decryption::decrypt_with_proof` recomputes the challenge with the externally supplied `from` only; nothing ties the message to `decryptor`:

```rust
msg.pop.verify(msg.key, pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg...))
```

And in `Encryption::decrypt` (encryption.rs:487-488), the actual decryption key is derived as `ecdh(self.enc_key, msg.key)` — i.e., bound to *whichever* participant's encryption key the local machine registered. The PoP check therefore succeeds for any replayed message, while the ECDH-derived cipher key silently mismatches for everyone except the original recipient.

Since DKG round-1 commitments and round-2 share messages are broadcast over an authenticated-but-public channel (all participants observe every `EncryptedMessage`), an unprivileged participant Eve can take Alice's valid message to Bob and present it as Alice's message to Eve inside `generate_secret_shares`/`calculate_share`.

### Impact Explanation
Replaying Alice's `EncryptedMessage` under Eve's recipient slot causes Eve's decryption to produce garbage (the ECDH key differs). Eve then issues a blame proof: `EncryptionKeyProof` containing Eve's honest DLEq of `ecdh(enc_key_eve, msg.key)`, which verifies correctly because the DLEq is properly bound to `msg.key` and `proof.key` (encryption.rs:383-390). `blame_internal` then decrypts, obtains a non-canonical or verification-failing share, and returns **the sender** as faulty (encryption.rs:590-605). The result: an honest participant is identified as malicious — which in Serai's processor (`VerifyBlame` → `ProcessorMessage::Blame`) leads to slashing/fatal blame of an innocent party and abort of the DKG. This is precisely the "replay within validity window → griefing" impact of the reference report, mapped onto the replayable PoP signature.

### Likelihood Explanation
Any participant in the DKG session observes all encrypted share messages (they must, for blame adjudication), so the input is publicly reachable. The attack requires only copying bytes already on the wire into the attacker's own inbound slot — no forgery, no broken crypto. The only mitigating factor is that if the network layer strictly enforces which ciphertext belongs to which recipient slot at the message level, the replay surface shrinks, but nothing in the cryptographic verification itself enforces it, and the library explicitly delegates message routing/authentication to the caller.

### Recommendation
Bind the intended recipient into the PoP challenge: extend `pop_challenge` to take `to: Participant` (or the recipient's registered `enc_key`/`EncryptionKeyMessage` commitment) and append it to the transcript, e.g. `transcript.append_message(b"recipient", to.to_bytes())`, updating both `encrypt` and all `pop_challenge` call sites (`decrypt`, `decrypt_with_proof`, and the test helpers) accordingly. This makes each `EncryptedMessage`'s PoP valid for exactly one `(sender, recipient)` pair.

### Proof of Concept
1. Alice runs `generate_secret_shares`, producing `EncryptedMessage<C, SecretShare>` values keyed by recipient, including `msg_AB` for Bob.
2. Eve (a participant) copies the serialized `msg_AB` from the broadcast channel and supplies it to her own `KeyMachine::calculate_share` as the share `from` Alice.
3. Inside `Encryption::decrypt`, `msg_AB.pop.batch_verify(...)` succeeds — `pop_challenge(context, R, key, Alice, ciphertext)` is identical to what Alice signed.
4. `ecdh(enc_key_eve, msg_AB.key)` yields the wrong shared key; decryption produces garbage bytes.
5. Eve calls `blame(Alice, Eve, msg_AB, Some(eve_proof))`. `decrypt_with_proof` verifies the PoP (passes), verifies Eve's DLEq (passes), decrypts to an invalid share, and `blame_internal` returns `Alice` as faulty — wrongfully blaming an honest sender via signature replay.
