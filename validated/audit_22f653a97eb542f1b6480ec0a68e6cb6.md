### Title
Deterministic reuse of cached FROST nonces across signatures enables linear recovery of the secret share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Elasticsearch advisory describes an incorrect-authorization flaw: a caller holding a valid credential can bypass the intended access layer by supplying raw internal identifiers directly. The analog in Serai is the deterministic `CachedPreprocess` mechanism in `SigningProtocol::preprocess_internal`: the preprocess (and therefore the secret nonces) is regenerated identically from a fixed seed keyed only by `context`, so the caller's controlled inputs (the signed message and the set of remote preprocesses) are the *only* entropy distinguishing two signing sessions. Because Serai's nonce is `base + rho * actual` where `rho` is publicly computable, repeated signatures under the same context expose a linear system that leaks the secret key share — an object the protocol's authorization model is supposed to keep sealed.

### Finding Description
In `preprocess_internal`, the coordinator caches a 32-byte seed in `CachedPreprocesses`, encrypted with a key derived from `"Cached Preprocess Encryption Key" || context || key`. The cache is only *written* when absent (`CachedPreprocesses::get(...).is_none()` at line 123); it is never rotated or consumed after use. Every subsequent `preprocess_internal`/`share_internal` call for the same `context` XORs the stored seed with the same encryption key and calls `AlgorithmSignMachine::from_cache` → `seeded_preprocess`, which deterministically regenerates the identical nonces and preprocess commitments. [1](#0-0) 

The nonce actually used in signing is `actual = base + rho * actual_seed`, where `base`/`actual_seed` are fixed by the cached seed and `rho` is the public binding factor computed from `group_key`, `hash_msg(msg)`, and the hash of everyone's preprocesses (`rho_transcript` in `AlgorithmSignMachine::sign`). [2](#0-1) 

Each produced share therefore satisfies the public linear relation `s = base + rho * actual + c * x` where `c` is the public Schnorr challenge and `x` is the interpolated secret share. `base`, `actual`, `x` are fixed unknowns per (context, included-set); `rho`, `c`, `s` are all public. Every additional signature under the same `context` (same preprocess → same `base`/`actual`) yields one equation. Three signatures over distinct `rho`/`c` values give three independent linear equations in three unknowns, solvable for the signer's secret share `x`.

### Impact Explanation
Any party able to observe ≥3 signature shares produced by the same coordinator signing context — including an unprivileged external user whose Bitcoin transactions cause the validators to sign arbitrary `msg` values, and any validator receiving broadcast shares — can recover that signer's interpolated secret share. Combined with the threshold structure this degrades to key-share recovery and, with enough compromised/derived shares, full private-key recovery of the threshold key protecting all bridged funds. This satisfies the "key share recovery" impact criterion.

### Likelihood Explanation
The vulnerability triggers whenever `context` is reused across distinct signed messages. `context` is the sole DB key for the seed and is chosen by the caller of `SigningProtocol` — any per-validator or per-set context (rather than per-message) satisfies the condition. `share_internal` re-invokes `preprocess_internal`, and retries/reattempts or repeated substrate block cosigning naturally produce multiple signatures per context. Since `rho` also depends on attacker-influenced remote preprocesses and the attacker-chosen message, the unknowns are not eliminated by the binding factors — they merely become per-signature coefficients. No collusion with the threshold, no malicious node, and no leaked material is required; only signatures the victim produces over attacker-influenced messages.

### Recommendation
- Rotate or delete `CachedPreprocesses` after each completed `sign` call, so a cached seed is single-use.
- Alternatively, mix the message digest (or a monotonically increasing per-context counter) into the nonce derivation seed so that `base`/`actual` differ per message, breaking the fixed-unknown linear system.
- Bind the encryption key and cache key to a unique per-signing-session identifier (e.g., `SignId` including attempt), not a reusable context.

### Proof of Concept

```rust
assert_eq!(p1, p2); // same seed -> same CachedPreprocess -> identical nonces
```
For each share `s_i` observed on the wire for three distinct messages under that context:
`s_i = base + rho_i * actual + c_i * x`
with `rho_i` from the public `rho_transcript` (`group_key`, `hash_msg(msg)`, hashed preprocesses) and `c_i` the Schnorr challenge. Solve the 3×3 linear system for `(base, actual, x)`; `x` is the victim's secret key share.
