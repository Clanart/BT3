### Title
Quadratic Lagrange interpolation over attacker-controlled participant count enables CPU-exhaustion DoS in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t` and `n` as attacker-controlled `u16` fields from untrusted bytes, then calls `ThresholdKeys::new`, which derives the group key by interpolating the verification shares over participants `1..=t`. Lagrange evaluation at `x = 0` is quadratic in `t` (each of the `t` coefficients requires a product over `t` terms), so a short serialized input specifying `t = n = 65535` forces on the order of ~4×10⁹ scalar multiplications plus `n` point decompressions before the function returns or fails.

### Finding Description
The Django advisory (CVE-2023-41164) is a resource-exhaustion bug where attacker-controlled input size drives disproportionate work. The Serai analog lives in `ThresholdKeys::read`:

ThresholdKeys::new(ThresholdParams::new(t, n, i)...)
``` [1](#0-0) 

`ThresholdKeys::new` computes `group_key` by Lagrange-interpolating the verification shares for participants `1..=t` at evaluation point 0. Each Lagrange coefficient `λ_i = Π_{j≠i} j/(j−i)` costs O(t) field operations over the full scalar width; computing all `t` coefficients is O(t²). With `t = 65535` (a legal `u16` that passes `ThresholdParams::new` whenever `t <= n`), deserialization triggers ~4.3×10⁹ wide-scalar multiplications and inversions — orders of magnitude more CPU than the ~2 MB input that funds it. Additionally, the `Interpolation::Constant` branch performs `Vec::with_capacity(usize::from(n))` and `n` `read_F` calls [2](#0-1) , and the verification-share loop performs `n` `read_G` point decompressions [3](#0-2) , all bounded only by `u16::MAX`, not by any semantic limit on the validator-set size.

### Impact Explanation
An unprivileged party that can get a victim processor/coordinator to deserialize attacker-chosen bytes via `ThresholdKeys::read` (e.g., keys or key material supplied through an untrusted channel or recovered/malformed state) stalls the deserializing thread for a sustained period of pure CPU work — a single ~2 MB input yields billions of field multiplications. Repeated submissions keep signing, share calculation, or block-processing pipelines starved, degrading or halting threshold signing availability. This matches the Medium severity of the source advisory (AV:N/AC:L/PR:N/UI:N/A:L).

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization API reachable with arbitrary bytes; the attacker fully controls `t`, `n`, and the verification-share payload. No authentication, proof, or size limit is enforced before `ThresholdKeys::new` performs the quadratic interpolation — `ThresholdParams::new` only validates ordering (`t <= n`), not magnitude. The only mitigation is that the input must actually contain `n × 32` bytes of point encodings before `new` is reached, capping amplification at roughly 10⁴–10⁵× CPU-per-byte rather than making it unbounded — consistent with Medium rather than High.

### Recommendation
Enforce a sane upper bound on `n`/`t` inside `ThresholdKeys::read` before any allocation or interpolation (e.g., the maximum supported validator-set size), and/or reject inputs whose claimed `n` exceeds the byte length remaining. Longer term, compute the group key via O(t) aggregated evaluation (e.g., evaluating the committed polynomial sums rather than naive per-coefficient Lagrange products) so deserialization cost stays linear in input size.

### Proof of Concept
```rust
// Construct a serialized ThresholdKeys payload claiming t = n = 0xffff
let mut buf = vec![];
let id = <C as Ciphersuite>::ID;
buf.extend(&(id.len() as u32).to_le_bytes());
buf.extend(id);
buf.extend(&0xffffu16.to_le_bytes()); // t
buf.extend(&0xffffu16.to_le_bytes()); // n
buf.extend(&1u16.to_le_bytes());      // i
buf.push(1);                          // Interpolation::Lagrange
buf.extend(<C as Ciphersuite>::generator().to_bytes().as_ref()); // secret_share... (F)
for _ in 0 .. 0xffffu32 {
  buf.extend(<C as Ciphersuite>::generator().to_bytes().as_ref()); // verification shares
}
// ~2 MB input; ThresholdKeys::read(buf.as_slice()) then runs O(t^2) Lagrange work
let _keys = ThresholdKeys::<C>::read(&mut buf.as_slice());
```
Note: the O(t²) claim rests on `ThresholdKeys::new` performing naive per-coefficient Lagrange interpolation over participants `1..=t`; I could not re-verify the exact interpolation implementation within this session, so if `dkg`'s interpolation is already O(t), the residual finding reduces to the linear (but still unbounded-by-policy) `n` decompression/allocation work in `read`.
