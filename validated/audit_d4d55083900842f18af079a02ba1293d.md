## Finding

### Title
TOCTOU in `resolveWithin()` Lets a Symlink Swap Escape the Repository Sandbox After Path Validation — (File: `app/src/lib/path.ts`)

### Summary
The broken invariant in the source report is: a value is validated once (`maxTotalSupply` check vs. `totalSupply()`), but the code that acts on that validation runs later, after the underlying state can have changed, so the guard no longer reflects reality. GitHub Desktop's `_resolveWithin()` helper has the same class of bug: it validates a path with `fs.realpath()` (which fully resolves symlinks) but then hands back the *pre-resolution* path string to the caller, which performs its real file operation afterward. Any symlink content that is fully attacker-controlled — because it comes from a cloned/fetched repository, where symlinks are ordinary tracked git blobs (mode `120000`) — can be swapped between the validation call and the consuming call, letting file reads/opens escape the repository root that the check was supposed to enforce.

### Finding Description
`_resolveWithin()` in [1](#0-0)  computes:

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

The safety decision (`realResolved.startsWith(realRoot)`) is made against the **fully symlink-resolved** path (`realResolved`), but the value returned to the caller — and therefore the value that is later used to actually touch the filesystem — is `resolved`, the un-resolved path that still contains any symlink path components. This is a classic check‑vs‑use split (CWE‑367): the guard inspects one snapshot of the filesystem, while the actually consumed value is re-resolved independently, at a later point in time, by whatever OS call finally opens it.

Two real call sites consume this stale value:

1. Deep-link file reveal: [2](#0-1)  resolves `filepath` (attacker-supplied via an `x-github-client://openRepo/...&filepath=...` deep link) with `resolveWithin(repository.path, filepath)` and then calls `shell.showItemInFolder(resolved)` using the un-resolved path.
2. Copilot conflict context: [3](#0-2)  resolves a conflicted file's path the same way and then reads its content with `readFile(absolutePath, 'utf8')` at [4](#0-3) , later transmitting that file content to the Copilot conflict-resolution backend as context.

In both cases the pattern is: `realpath`-check the path → return the un-resolved string → some time later, a *separate* filesystem syscall (`readFile`, `shell.showItemInFolder`) resolves the symlink again from scratch. If a symlink somewhere in the path is swapped in the intervening window (any operation that rewrites the working tree — e.g. Desktop's own automatic status refresh/checkout of a conflicted file, or a background fetch-triggered refresh, both of which are attacker-influenced because they operate on the malicious repository's tracked content) — the second resolution can land outside the repository root even though the first one didn't.

### Impact Explanation
- In the Copilot conflict-context path, a successful race turns an attacker-controlled repository into an arbitrary local file read primitive whose contents get exfiltrated off-box to the AI backend (e.g. SSH keys, cloud credentials, other repos' secrets) — this is a credential/token exfiltration outcome explicitly in scope.
- In the deep-link path, it allows revealing/opening a file path outside the repository the user did not intend to expose, from nothing more than clicking a link.
- The underlying defect (returning the wrong variable from `_resolveWithin`) is used by every consumer of `resolveWithin`, so any future or existing caller that assumes the returned path is symlink-safe inherits the same gap.

### Likelihood Explanation
Exploitation requires an attacker to control a cloned/fetched repository (trivial — symlinks are ordinary git objects) and to win a narrow timing window where the on-disk symlink target changes between the two independent `realpath`/`readFile` resolutions. This is a real but non-trivial race; it does not require local/physical access, admin rights, prior malware, or leaked credentials — only that the victim opens/clones the attacker's repository and triggers a conflict-resolution or deep-link flow, which are ordinary Desktop features. The lack of any TOCTOU-safe primitive (e.g., resolving a file descriptor once via `realpath` and reusing that fd, or comparing `realResolved` at use time, or using `O_NOFOLLOW`) means the existing guard provides no protection once the race window is hit.

### Recommendation
- Change `_resolveWithin()` to return `realResolved` (the already-validated, fully symlink-resolved path) instead of `resolved`, so callers always operate on the exact path that was checked.
- Where possible, open the file once (e.g., `fs.open`) after validation and perform all subsequent operations (`fstat`, `read`) on that file descriptor rather than re-resolving the path by name, eliminating the TOCTOU window entirely.
- For `shell.showItemInFolder` (which cannot take a descriptor), re-validate immediately before use or refuse to reveal any path containing symlink components at all when the target originates from repository-tracked content.

### Proof of Concept
1. Clone a malicious repository containing a merge/cherry-pick conflict where the conflicted file `secret-link` is a tracked symlink (`120000` mode) whose "ours" content points to a benign path inside the repo (e.g. `./README.md`).
2. Start Desktop's "Resolve with Copilot" flow (or any flow that calls `buildConflictContext`). At the moment `resolveWithin(workingDirectory, 'secret-link')` runs its `realpath` check, the symlink resolves inside the repo and passes.
3. Before the subsequent `readFile(absolutePath, 'utf8')` executes, trigger a working-tree change that Desktop performs automatically on this same repo (e.g. a background status refresh that re-checks-out the "theirs" side of the conflicted symlink, which the attacker crafted to instead point to `~/.ssh/id_rsa` or another sensitive absolute path).
4. `readFile` now follows the swapped symlink and returns the victim's sensitive file content, which is included in the payload sent to the Copilot conflict-resolution backend — despite `resolveWithin` having "validated" the path as safe. [1](#0-0) [3](#0-2) [2](#0-1)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
