### Title
Webhook Verification Does Not Bind the Shop Domain Header to the HMAC-Signed Payload, Enabling Cross-Shop Webhook Replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
This mirrors the reported bug class: a verified message (the HMAC-signed webhook body) is accepted without validating an accompanying, unsigned parameter (the `X-Shopify-Shop-Domain` header) against the value that was actually intended to travel with that signed payload. `ShopifyApp::WebhookVerification#verify_request` only computes the HMAC over `request.raw_post`; the shop domain is read separately from an unauthenticated header and handed to application code as trusted context.

### Finding Description
`WebhookVerification#verify_request` computes and checks the HMAC exclusively over the raw POST body: [1](#0-0) 

and separately exposes an unsigned header value as `shop_domain`: [2](#0-1) 

`hmac_valid?` in `PayloadVerification` only compares the HMAC of `data` (the raw body) against the `HTTP_X_SHOPIFY_HMAC_SHA256` header value — it never incorporates `HTTP_X_SHOPIFY_SHOP_DOMAIN` or any other header into the signed material: [3](#0-2) 

The gem's own documentation instructs developers to build custom webhook controllers exactly this way — passing the unauthenticated `shop_domain` header alongside the (validly-signed) body to background jobs: [4](#0-3) 

Because the signature covers only the body, any HTTP request bearing a *body+HMAC pair that is valid for the app's shared secret* will pass `verify_request` regardless of what shop-domain header accompanies it. A merchant who has legitimately installed the app receives real, validly-signed webhook deliveries from Shopify for their own shop (e.g., `app/uninstalled`, `shop/redact`). Nothing prevents that merchant from replaying the exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a different, victim shop. `verify_request` still validates because it never checks the header against the signed content.

### Impact Explanation
Generated job templates that follow the documented pattern use the header-derived `shop_domain` (not anything from the signed body) to look up and act on shop records, e.g., destroying the shop record for `AppUninstalledJob` or performing GDPR redaction for `ShopRedactJob`: [5](#0-4) [6](#0-5) 

If a custom controller is built per the documented recipe (using `ShopifyApp::WebhookVerification` and the `shop_domain` helper directly, as shown in `docs/shopify_app/webhooks.md`), an attacker-controlled shop domain can be paired with a replayed, validly-signed body, causing the app to act (delete data, trigger redaction, mutate records) on behalf of a shop the request did not actually originate from — a cross-shop action performed with a request that passes signature verification.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on their own store (unprivileged, anonymous relative to the victim) to obtain one genuinely-signed webhook body+HMAC, then replay it with a modified `X-Shopify-Shop-Domain` header to the app's public webhook endpoint. No secret leakage or host-operator access is required. It is limited to apps that implement custom controllers via `ShopifyApp::WebhookVerification`/`shop_domain` as documented, rather than the built-in `WebhooksController`, which delegates parsing and shop derivation to `ShopifyAPI::Webhooks::Request`/`Registry` (an external dependency not in this repo, and out of scope here).

### Recommendation
Do not treat `X-Shopify-Shop-Domain` (or any other webhook header) as trusted context independent of the signed body. Either bind the header into the HMAC computation, or require that any shop-identifying value used for authorization/context be sourced only from data covered by the signature (or from Shopify API calls made in the resulting job using the shop record verified through a separate, signed channel).

### Proof of Concept
1. Attacker installs the target app on their own controlled shop `attacker.myshopify.com`; app registers `app/uninstalled` webhook.
2. Attacker uninstalls the app, causing Shopify to deliver a real webhook: body `B` with header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this request and replays it to the app's custom webhook endpoint (built with `ShopifyApp::WebhookVerification` per `docs/shopify_app/webhooks.md`), keeping body `B` and its HMAC unchanged but setting `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `verify_request` calls `hmac_valid?(request.raw_post)`, which only checks `B` against the HMAC — passes.
5. Application code, per the documented pattern, uses `shop_domain` (now `victim.myshopify.com`) to enqueue `AppUninstalledJob`/`ShopRedactJob`, causing the victim shop's record to be destroyed/redacted even though the actual webhook event pertained to the attacker's own shop.

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

class CustomWebhooksController < ApplicationController

    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)

  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end

```text
class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
```
