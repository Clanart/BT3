### Title
Panic on unindexed `Participant` in PedPoP blame evaluation enables remote denial of service - (File: crypto/dkg/pedpop/src/lib.rs, crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG blame-handling code indexes `HashMap`s keyed by `Participant` using attacker-influenced `sender`/`recipient` values without validating that the participant is in-range or registered. Analogous to CVE-2019-20396 (a crash on malformed parser input), a malformed blame accusation — attacker-controlled `Participant` indexes plus a self-constructed `EncryptedMessage`/`EncryptionKeyProof` — reaches `self.enc_keys[&decryptor]` / `self.commitments[&sender]` indexing and panics the process instead of returning an error.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` take `sender`, `recipient`, a `msg`, and an optional `proof` and funnel them into `blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609). Two unchecked indexing operations exist:

1. `decrypt_with_proof` in crypto/dkg/pedpop/src/encryption.rs:381-389: after verifying the message's Schnorr PoP, it evaluates `self.enc_keys[&decryptor]` to build the DLEq verify statement list. `enc_keys` only contains entries for participants who registered an `EncryptionKeyMessage` (inserted in `Decryption::register`, encryption.rs:351-362). `std::collections::HashMap`'s `Index` impl panics on a missing key.
2. `blame_internal` at crypto/dkg/pedpop/src/lib.rs:599 passes `&self.commitments[&sender]`, likewise panicking if `sender` is absent.

`Participant` is just a non-zero `u16` (`Participant::new` rejects only 0 — see dkg/lib.rs:600 usage), and neither `blame` nor `blame_internal` validates that `sender`/`recipient` are within `1..=n` or present in the maps. `AdditionalBlameMachine::new` explicitly constructs this machine for callers who were "not a member in the DKG protocol" and feeds only `1..=n` into `register` (lib.rs:649-661), so any index `> n` or an index whose commitment message was never registered is guaranteed to be missing.

To reach the panic in path 1, the attacker must supply a `msg` whose PoP verifies and a `Some(proof)`. The PoP (`pop_challenge`, encryption.rs:302-324) is an unkeyed Schnorr proof of knowledge over `msg.key` binding only `context`, `from`, and the ciphertext — anyone can generate a fresh `key` scalar and produce a valid `EncryptedMessage`/`pop` pair (the same construction `encrypt` uses, encryption.rs:135-168). A dummy `EncryptionKeyProof` (any `key` point + any `DLEqProof` bytes) suffices because the `HashMap` index is evaluated while constructing `dleq.verify`'s arguments, before the proof is actually checked.

### Impact Explanation
An unprivileged party who can submit (or cause an honest node to evaluate) a blame accusation crashes the evaluating node — a segfault-class availability failure identical in shape to the reference CVE. For `AdditionalBlameMachine`, which is documented as usable by non-participants evaluating third-party blame, the hostile `sender`/`recipient`/`msg`/`proof` tuple is entirely attacker-supplied. A single panic in a node's blame/processing thread aborts DKG completion and can repeatedly crash nodes on restart if the malicious accusation is reprocessed.

### Likelihood Explanation
Reachability requires the host protocol to route blame accusations into `BlameMachine::blame`/`AdditionalBlameMachine::blame` without first checking that `recipient` and `sender` are registered DKG participants — the library itself performs no such check, and `AdditionalBlameMachine` is explicitly designed for external blame evaluation. The malicious input is trivially constructible: any `Participant` index outside the registered set, a self-signed `EncryptedMessage` (the PoP is satisfiable by anyone), and an arbitrary `EncryptionKeyProof`. This matches the CVE pattern of a medium-severity, low-complexity input-driven crash; it does not leak key material, so Medium is appropriate.

### Recommendation
Replace `HashMap` indexing with fallible lookups in both places:

- In `Decryption::decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:388), use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` — an unregistered decryptor means the accuser's claim is malformed, which should be an error, not a panic.
- In `blame_internal` (crypto/dkg/pedpop/src/lib.rs:599), look up `self.commitments.get(&sender)` and treat a missing sender as `sender`-faulty or reject the accusation.
- Additionally, validate `sender` and `recipient` against `self.commitments`/`enc_keys` membership at the top of `blame`/`AdditionalBlameMachine::blame` so out-of-protocol indexes are rejected before any map access.

### Proof of Concept
```rust
// Requires: a BlameMachine or AdditionalBlameMachine built for a DKG with n
// participants (so enc_keys holds participants 1..=n only).

// 1) Choose a recipient index that was never registered.
let attacker_recipient = Participant::new(n + 1).unwrap(); // or any absent index

// 2) Build a self-consistent EncryptedMessage whose PoP verifies.
//    Replicates encrypt() from encryption.rs:135-168 with attacker-chosen key.
let key = Zeroizing::new(C::random_nonzero_F(&mut rng));
let mut msg_bytes = Zeroizing::new(SecretShare::<C::F>(<C::F as PrimeField>::Repr::default()));
cipher::<C>(context, &ecdh::<C>(&key, C::generator())) // any "to" point works
    .apply_keystream(msg_bytes.as_mut().as_mut());
let pub_key = C::generator() * key.deref();
let nonce = Zeroizing::new(C::random_nonzero_F(&mut rng));
let pub_nonce = C::generator() * nonce.deref();
let pop = SchnorrSignature::sign(
    &key, nonce,
    pop_challenge::<C>(context, pub_nonce, pub_key, sender, msg_bytes.deref().as_ref()),
);
let msg = EncryptedMessage { key: pub_key, pop, msg: msg_bytes };

// 3) Any parseable EncryptionKeyProof; it is never verified because the
//    `enc_keys[&decryptor]` index is evaluated while building dleq.verify's args.
let proof = Some(EncryptionKeyProof::<C>::read(&mut arbitrary_bytes.as_ref()).unwrap());

// 4) Trigger: panics inside decrypt_with_proof at
//    `self.enc_keys[&decryptor]` (encryption.rs:388).
machine.blame(sender, attacker_recipient, msg, proof);
```

Caveat: I could not inspect the host code that feeds `blame` to confirm whether callers pre-validate `sender`/`recipient` against the DKG roster; if an in-scope caller already rejects non-participants, reachability narrows to `AdditionalBlameMachine::blame`, which accepts fully external input.
