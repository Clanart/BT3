### Title
Same-chain partial-fill escrow release mis-indexes `order.inputs` by output position, permanently locking or misreleasing input assets on multi-input orders - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain()` computes and releases escrowed input tokens by reading `order.inputs[i]`, where `i` is the loop index over `order.output.assets` (`outputsLen`), not an index that is proven to correspond to the same economic input. This is structurally the same class of bug as the reported `calculate_maximum_withdraw_amount()` issue: a per-asset amount (there: withdraw amount derived from an *aggregated* collateral factor; here: escrow release amount derived from a *positionally paired but economically unrelated* output's fill ratio) is computed using a value that doesn't correctly correspond to the specific asset being moved, when the basket contains multiple assets of different sizes/kinds.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:54-149`), the loop bound is `outputsLen = order.output.assets.length` [1](#0-0) . Inside that loop, the escrow amount to release for iteration `i` is taken directly from `order.inputs[i]`:

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
``` [2](#0-1) 

This assumes `order.inputs` and `order.output.assets` are the same length and are positionally 1:1-related (input asset `i` funds output asset `i`). Nothing in `IntentsBase.sol` or the visible `IntentGatewayV2.sol` escrow-crediting code (`Phase 3: Credit escrow`, `evm/src/apps/IntentGatewayV2.sol:333-343`) enforces `order.inputs.length == order.output.assets.length`, nor any semantic pairing between input `i` and output `i` — `_orders` is keyed independently per `(commitment, token)` [3](#0-2) , and `placeOrder` escrows each input token independently, rejecting only exact duplicate tokens [4](#0-3) .

Consequences when `order.inputs.length != order.output.assets.length` (a user-controlled order shape, since `placeOrder` builds `_orders[commitment][token]` per input independently of output count):
- If `inputs.length > outputsLen` (e.g., 2 inputs funding 1 output), the loop only ever touches `order.inputs[0..outputsLen-1]`. Any input at index `>= outputsLen` is never added to `escrowedInputs` and is never passed to `_withdraw` in this call, so its escrow entry in `_orders[commitment][token]` is left non-zero. Because `_filled[commitment]` is set unconditionally at the top of `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:57`) before the loop runs, the order becomes finalized as filled with residual escrow permanently stuck — no subsequent cancel path is reachable since `_cancelSameChain` requires the caller to be `order.user` and the order to not already be filled, and the cross-chain refund/redeem paths key off `_filled`/commitment state that this same-chain flow already sets.
- If `inputs.length < outputsLen`, `order.inputs[i]` for `i >= inputs.length` reverts (array out-of-bounds), which is at minimum a griefing/DoS vector but not exploitable for profit.
- Even when lengths happen to match, the escrow release ratio for input `i` is driven by the *fill ratio of output `i`* (`fillAmount/totalRequired`), not by any invariant tying input `i`'s value to output `i`'s value. A solver can selectively fill only the output index that maximizes the resulting release ratio applied to a high-value input paired at the same index, extracting more escrow value per unit filled than the order's true price basket intended — the same "aggregate factor applied to the wrong per-asset amount" defect described in the external report, just realized here as an index-mismatch rather than a collateral-factor mismatch.

### Impact Explanation
This falls squarely within the bounty's "stealing or loss of funds" and "transaction manipulation" categories for the intent-settlement/bridge-custody surface: an unprivileged order creator can construct a multi-input, fewer-output same-chain order such that part of their own escrowed funds becomes permanently unreleasable through the intended fill/cancel flow once `_filled[commitment]` is set, and/or a solver can exploit the mismatched per-index pairing to receive escrow disproportionate to the value they actually delivered. Both are within-scope fund-loss/fund-manipulation impacts on `IntentGatewayV2`'s escrow custody, not a relayer/prover/admin-privileged scenario.

### Likelihood Explanation
The order shape (differing `inputs`/`output.assets` array lengths, or same-length but economically mismatched inputs/outputs) is fully attacker-controlled via `placeOrder`, requiring no relayer, prover, governance, or malicious peer — only a self-crafted order and a solver willing to fill it (which could be the same actor colluding with themselves to trigger the locked-escrow condition, or exploiting the ratio mismatch as a solver). No proof forgery or consensus manipulation is needed since this is purely local Solidity state accounting on `_orders`/`_partialFills`.

### Recommendation
Enforce `order.inputs.length == order.output.assets.length` at `placeOrder` time (reject otherwise), and/or redesign `_fillSameChain` to release input escrow based on the *aggregate* remaining escrow proportional to *overall* order fill progress rather than indexing `order.inputs` by the output loop variable. If inputs and outputs are intentionally allowed to have independent cardinality (e.g., an N-input basket funding a single output), the escrow-release computation must be restructured to prorate every input asset by the same global fill fraction, computed once per fill call, rather than pairing `order.inputs[i]` with `order.output.assets[i]`.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [ {token: TOKEN_A, amount: 1000}, {token: TOKEN_B, amount: 500} ]` and `order.output.assets = [ {token: TOKEN_C, amount: 100} ]` (one output, two inputs) — this is accepted since `placeOrder`'s Phase-3 escrow crediting loop iterates over `inputsLen` independently of `output.assets.length` (`evm/src/apps/IntentGatewayV2.sol:333-343`).
2. A solver calls `fillOrder` with `options.outputs = [ {token: TOKEN_C, amount: 100} ]`, fully satisfying the single output.
3. In `_fillSameChain`, `outputsLen = 1`, so the loop runs only for `i = 0`: `escrowedAmount = _orders[commitment][TOKEN_A]` (the full 1000 TOKEN_A) is added to `escrowedInputs` and released to the solver via `_withdraw`; `_filled[commitment] = msg.sender` was already set at function entry.
4. TOKEN_B's escrow entry `_orders[commitment][TOKEN_B] = 500` is never touched, never appears in `escrowedInputs`, and is never withdrawn. `isFullyFilled` is `true` (based only on output completeness), so the order is finalized (`OrderFilled` emitted) and `_cancelSameChain` (which requires `order.user == msg.sender` and effectively an un-filled/cancelable state) is the user's only path back — but the finalized/filled marking and the escrow-checking logic in `_withdraw`/`_cancelSameChain` were not fully traceable in the available excerpts to confirm a rescue path exists; the 500 TOKEN_B either remains permanently locked in the contract or is claimable only through an unintended state combination, constituting fund loss/lock. (Full confirmation of whether any downstream governance sweep can recover it requires reading `_sweepDust`'s callers/authorization, which was not fully explored in this session — flagged as an open item for the engineer executing this analog.)
