### Title
Permissionless cross-chain bandwidth sponsorship lets an attacker evict a victim app's paid-for `Subscription` entries via the FIFO cap - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth` stores each `(app_chain, app)` bandwidth allowance as a `BoundedVec<Subscription, MAX_SUBSCRIPTIONS>` FIFO list capped at 1024 entries [1](#0-0) . When the list is full, a new purchase silently evicts the oldest (still-live, unconsumed) subscription and emits `SubscriptionEvicted` with the lost bytes [2](#0-1) . Crucially, the credit target `(app_chain, app)` is taken from the purchase message body, not from `request.source`, which is an intentional "sponsorship" feature that lets any payer on any chain top up any app on any other chain [3](#0-2) . Combining unrestricted third-party crediting with a hard, evict-oldest cap allows any unprivileged actor to grief a specific victim app by cheaply filling its subscription queue, evicting the victim's own (larger, real) prepaid subscriptions before they can be consumed — a direct loss of prepaid funds for the victim.

### Finding Description
`push_subscription` is the single insertion point used by both real purchases (`on_accept`) and governance `force_credit`:

```rust
let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
    let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
        Some(list.remove(0))
    } else { None };
    let _ = list.try_push(new_sub);
    evicted
});
``` [4](#0-3) 

This is the same broken invariant as the C4 report: a hard-capped queue that evicts/blocks based on FIFO order rather than value or ownership, and the entity that fills the queue is not the entity that bears the loss. In Salty's case attackers blocked new legitimate proposals; here the analog is stronger because the queue holds *already-paid-for value* (`remaining_bytes`), so eviction isn't just a DoS on future writes — it destroys funds a legitimate payer already spent.

The attack surface is that `purchase()` on `BandwidthManager.sol` is a permissionless external call, and its `chain`/`app` arguments are validated only as "does a `TierConfig` and registered manager exist" — not against the caller's identity or the destination app's consent:

> "The `chain` argument is **not validated against the source chain**... A buyer on Ethereum credits an app on Base by passing the credit chain id in `chain`" [5](#0-4) 

> "The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`... This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains" [3](#0-2) 

So any address, with no relationship to the victim app, can call `purchase(app = victim_app, tier = cheapest, months = 1, chain = victim_chain)` repeatedly. Each call appends one `Subscription` row keyed to the victim's `(app_chain, app)` bucket. Because same-tier repurchases "don't stack, they queue" [6](#0-5) , and drains/evictions happen strictly from the front of the list [7](#0-6) , cheap repeated purchases will push the queue length to `MAX_SUBSCRIPTIONS` (1024) and every purchase after that evicts the current head — which could be the victim's own large, legitimately-purchased, unconsumed subscription (e.g. the $1000 / 8 MB tier) rather than the attacker's cheap filler entries, since eviction order is purely insertion time, not remaining value or entry size. The test suite explicitly documents and exercises this eviction path but never checks *who* purchased the evicted entry or its relative value: [8](#0-7) .

### Impact Explanation
This causes direct loss of prepaid funds to the victim app: bytes it already paid for (via `purchase()`, real ERC-20 payment pulled by `BandwidthManager.sol`) are silently destroyed by an unrelated third party's cheap purchases, with no signature, allowlist, or ownership check tying eviction rights to the app being credited. Under the Impact Gate this is "loss of funds" via "logic attack" on the bandwidth accounting module — a production pallet path (`pallet-bandwidth`, live under `evm/src/apps/BandwidthManager.sol` ↔ Hyperbridge), reachable by any unprivileged EVM account with no relayer/prover/admin compromise required. Practically: an attacker who wants to grief a competing dapp, or extort an app operator, can spend `1024 × cheapest_tier_price` (at the $50/100KB tier, a bounded and comparatively small cost) to guarantee eviction of the victim's prior subscriptions, including ones many times more valuable that the victim just paid for and has not yet consumed.

### Likelihood Explanation
Medium-High. The `purchase()` entrypoint is intentionally permissionless and multi-tenant by design (that's the documented "sponsorship" feature), so no privileged access or race condition is needed — this is a pure logic gap in the eviction policy, not a griefing-via-frontrunning scenario. The cost to fully evict a victim's queue is bounded (1024 cheap purchases) and does not require the attacker to guess timing; it just needs the victim's `(app_chain, app)` identifier, which is public (it's the destination app address). The main constraint reducing likelihood is that it requires deliberate targeting of a specific, valuable victim subscription and 1024 dispatches routed through a relayer to land the credit on Hyperbridge, but nothing in the protocol prevents or rate-limits this per external payer.

### Recommendation
- Key eviction eligibility (or at least a large fraction of the queue) to the same purchaser/sponsor identity, or require `force_push`/normal purchase eviction to only remove entries whose remaining value is below a floor, so a third party cannot cheaply displace another payer's larger, unconsumed allowance.
- Alternatively, merge same-tier or same-(payer) subscriptions instead of always appending a new FIFO row, reducing the number of cheap rows an attacker can inject per unit cost.
- Consider evicting based on "smallest remaining value" or "soonest to expire" rather than strict insertion order, so a cheap attacker purchase can only ever evict another cheap/soon-expiring entry, not a large prepaid one.
- Emit `SubscriptionEvicted` pre-eviction reject (or require confirmation) when the evicted entry's `remaining_bytes` value exceeds the new entry's `remaining_bytes`, converting a silent loss into an explicit, auditable governance decision.

### Proof of Concept
1. Victim app `V` on chain `EVM-8453` calls `purchase(app=V, tier=TierFour /* $1000, 8MB */, months=1, chain="EVM-8453")` — this appends one `Subscription` with `remaining_bytes = 8_000_000` to `Allowance[EVM-8453][V]`.
2. Attacker (unrelated EOA, any chain with a registered `BandwidthManager`) calls `purchase(app=V, tier=TierOne /* $50, 100KB */, months=1, chain="EVM-8453")` 1024 times in a row (or spread across several blocks — no rate limit exists).
   - `push_subscription` is invoked on `on_accept` for each attacker purchase, each appending to the *same* `Allowance[EVM-8453][V]` list [9](#0-8) .
   - Once the list reaches `MAX_SUBSCRIPTIONS = 1024`, each further attacker purchase evicts `list.remove(0)` — the oldest entry, which is victim `V`'s legitimate `TierFour` subscription (since it was inserted before the attacker's spam and drains from the front only as bytes are consumed, not merely inserted).
3. `SubscriptionEvicted { app_chain: EVM-8453, app: V, tier: TierFour, lost_bytes: 8_000_000 }` fires, and `V`'s paid-for 8 MB allowance is gone even though `V` never consumed a single byte of it.
4. `V`'s subsequent dispatches through the bandwidth gate now hit `GateError::Insufficient` / `NoAllowance` against the cheap attacker-filler entries, despite having paid $1000 for bandwidth that was destroyed by an unrelated party at a fraction of the cost (1024 × $50 filler purchases, of which the attacker can reclaim near-zero remaining value since the entries are cheap tiers created purely to trigger eviction, or can even reuse the same low-value entries repeatedly across multiple victims by adjusting the `app`/`chain` fields per call).

This PoC only requires calling the public `purchase()` function on `BandwidthManager.sol` with attacker-chosen `app`/`chain` parameters — no relayer collusion, no governance action, and no compromise of any privileged role, matching the required "unprivileged attacker" and "loss of funds" criteria.

	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.

## Sponsoring Another Chain

The `chain` argument is **not validated against the source chain** — see [Overview → Sponsorship](/developers/evm/bandwidth/overview#sponsorship) for the model. A buyer on Ethereum credits an app on Base by passing the credit chain id in `chain`:

```solidity
manager.purchase({
    app:    abi.encodePacked(appAddressOnBase),
    tier:   2,
    months: 6,
    chain:  bytes("EVM-8453")
});
```

The pallet keys allowance storage on `(msg.chain, msg.app)`, so the credit lands on Base regardless of which chain sent the payment. The recommended pattern for teams running a central treasury is to deploy `BandwidthManager` on one low-fee chain and sponsor bandwidth for app instances elsewhere.

/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
}
