### Title
Withdrawal indices sharing a Bitcoin outpoint let one operator claim Reimburse credit for a withdrawal it never fronted - (File: core/src/verifier.rs)

### Summary
`update_citrea_deposit_and_withdrawals` writes `withdrawal_utxo_outpoint` into the `withdrawals` table keyed solely on the Citrea-assigned `idx`, with no check that the outpoint is not already the recorded `withdrawal_utxo` of another `idx`. Because `get_payout_txs_for_withdrawal_utxos` later joins purely on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, two withdrawal indices sharing one outpoint both get matched to the same on-chain spend and both get marked "paid" by `update_payout_txs_and_payer_operator_xonly_pk`, even though only one payout transaction actually moved funds.

### Finding Description
The binding that must hold is: `withdrawals.idx == 1:1 mapping to a distinct (withdrawal_utxo_txid, withdrawal_utxo_vout)`, and each `(txid, vout)` pair should resolve to exactly one funded payout credited to exactly one withdrawal `idx`.

Trace:
1. `Verifier::update_citrea_deposit_and_withdrawals` (`core/src/verifier.rs:2205-2281`) fetches `new_withdrawals` from `citrea_client.collect_withdrawal_utxos` and, for each `(idx, withdrawal_utxo_outpoint)`, calls:
```
core/src/verifier.rs:2254-2261
self.db.update_withdrawal_utxo_from_citrea_withdrawal(Some(dbtx), idx as u32, withdrawal_utxo_outpoint, block_height).await?;
```
This is a per-`idx` UPDATE with no read-before-write check against other rows already holding that outpoint.

2. When a block finalizes, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) calls `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`):
```
SELECT w.idx, bsu.spending_txid
FROM withdrawals w
JOIN bitcoin_syncer_spent_utxos bsu
   ON bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout
WHERE bsu.block_id = $1
```
This join is keyed only on `(txid, vout)`. If two `withdrawals` rows (idx1, idx2) share the same `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, and that single outpoint is spent once on-chain, **both** rows join to the same `spending_txid`.

3. `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`) then sets `payout_txid`, `payout_payer_operator_xonly_pk`, and `payout_tx_blockhash` for **both** idx1 and idx2 using the same single spending transaction/operator.

Root cause: neither the write path (`update_withdrawal_utxo_from_citrea_withdrawal`) nor the read path (`get_payout_txs_for_withdrawal_utxos`) enforces that a Bitcoin outpoint is the withdrawal UTXO of exactly one `idx`, and no "consumed" flag distinguishes which withdrawal actually caused the spend. Since a single Bitcoin outpoint can only be spent once, only one of the two withdrawers is actually fronted funds, yet the DB state after `update_finalized_payouts` shows both idx1 and idx2 as paid by the same operator/txid, which downstream reimbursement logic (`get_payout_info_from_move_txid`, `get_first_unhandled_payout_by_operator_xonly_pk`, `Operator::get_reimbursement_txs`) uses to grant Reimburse credit per `idx`/deposit.

None of the referenced guards (`Verifier::is_deposit_valid`, `SPV::verify`, `lc_proof_verifier`, presigned tx graph) validate that a withdrawal's recorded outpoint is unique across indices; this is purely a database-join/bookkeeping gap in this repo.

### Impact Explanation
An operator can be credited with Reimburse for a withdrawal (idx2) it never actually fronted, because idx2's `payout_txid`/`payout_payer_operator_xonly_pk` are populated from idx1's real spend. The genuine withdrawer behind idx2 is never paid, yet Clementine's bookkeeping marks their withdrawal as handled, permanently blocking any legitimate future reimbursement bookkeeping for that deposit (`is_payout_handled`/`get_first_unhandled_payout_by_operator_xonly_pk` will skip it). This matches "an operator reimbursed for a payout it never funded" / "an honest operator's [counterpart withdrawer's] payout permanently unfronted" — Critical. It is repeatable for any pair of withdrawal indices that end up sharing an outpoint, across arbitrary deposits/operators.

### Likelihood Explanation
This requires the Citrea Bridge contract to actually allow two `withdraw()` calls to register the identical Bitcoin outpoint as the withdrawal UTXO for two different indices. That is an assumed attacker capability per the problem statement, but whether the real Citrea Bridge contract permits registering an already-used withdrawal UTXO for a second index is a Citrea-contract-side question outside this repo's control/visibility, and I could not verify it because `collect_withdrawal_utxos`'s underlying contract semantics live in `core/src/citrea.rs`/the Citrea contract, not in indexed Rust logic I could fully inspect. If the Citrea contract independently prevents outpoint reuse across indices (e.g., it requires spending a fresh, never-before-seen UTXO and validates ownership/signature per call), this path is not reachable from Clementine's side at all.

### Recommendation
Add a uniqueness/consumption check in `update_withdrawal_utxo_from_citrea_withdrawal` (reject or flag if the outpoint is already assigned to a different `idx`), and change `get_payout_txs_for_withdrawal_utxos` to join withdrawal-to-payout mapping in a way that a given spent outpoint can satisfy at most one `idx`, or add a DB-level `UNIQUE` constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table.

// core/src/database/verifier.rs tests module (conceptual, not to be placed in excluded test dirs)
#[tokio::test]
async fn duplicate_withdrawal_utxo_across_two_indices() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();
    let mut dbtx = db.begin_transaction().await.unwrap();

    let shared_utxo = bitcoin::OutPoint { txid: Txid::from_byte_array([0xAA; 32]), vout: 0 };
    let idx1 = 1u32;
    let idx2 = 2u32;

    // idx1 registers shared_utxo
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx1, shared_utxo, 100)
        .await.unwrap();
    // idx2 also registers the SAME outpoint (no rejection expected today)
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx2, shared_utxo, 100)
        .await.unwrap();

    let utxo1 = db.get_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx1).await.unwrap();
    let utxo2 = db.get_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx2).await.unwrap();

    // BINDING VIOLATION: two distinct withdrawal indices resolve to the same on-chain outpoint,
    // with no consumed marker distinguishing which one was actually fronted.
    assert_eq!(utxo1, utxo2, "expected duplicate outpoint to be accepted for both idx");

    // Simulate spend of shared_utxo, then confirm get_payout_txs_for_withdrawal_utxos
    // returns BOTH idx1 and idx2 mapped to the same spending_txid, and
    // update_payout_txs_and_payer_operator_xonly_pk marks both as paid by one operator.
}
