## Analysis

The vulnerability path is real at the validation layer, though full exploitability depends on code I could not fully retrieve (see caveat at the end).

### Finding Description

In `parseAppURL` (`app/src/lib/parse-app-url.ts`), the strict `^pr\/\d+$` format check on `branch` (lines 108-111) is only applied **inside the `if (pr != null)` block**: [1](#0-0) 

When the `pr` query parameter is omitted, the only remaining validation on `branch` is `testForInvalidChars(branch)`: [2](#0-1) 

`testForInvalidChars` uses `invalidCharacterRegex`, which blocks ASCII control chars/space, `~ ^ : ? * [ \ | " < >`, `@{`, consecutive/leading/trailing dots, `.lock` suffix, and trailing `/`: [3](#0-2) 

Notably, this regex **does not reject a leading `-`**. By contrast, the sibling function `sanitizedRefName` in the same file explicitly strips leading `-`/`+` characters (`.replace(/^[-\+]*/g, '')`), showing the developers are aware leading dashes are a hazard — but that stripping function is never called on the `branch` value in `parseAppURL`.

A crafted `x-github-client://openrepo/...?branch=-XYZ` (with `pr` omitted) therefore passes `parseAppURL` unmodified and is returned as `action.branch`.

Following the value downstream, `Dispatcher.dispatchURLAction` routes `open-repository-from-url` actions to `openRepositoryFromUrl`, which — when `pr` is `null` and `branch` is non-null — calls `openBranchNameFromUrl(url, branch)`: [4](#0-3) 

That method fetches the remote and then calls `this.checkoutLocalBranch(repository, branchName)` with the raw, attacker-supplied string.

### Caveat / what I could not verify

I was not able to retrieve the actual body of `Dispatcher.checkoutLocalBranch` (only its two call-site references were located via search, not its implementation) to confirm:
- whether it passes `branchName` to `git` as a positional argument preceded by a `--` separator (which would neutralize `-`-prefixed argv/flag injection), and
- which specific `git checkout`/`git branch` flags would be reachable if no separator is used (e.g., `-B`, `--orphan`, `--force`, `--track`, `--pathspec-from-file=<file>`), which determines actual impact (forced/destructive checkout vs. more severe primitives).

Because of this gap, I can confirm the **input-validation weakness** (leading `-` is not rejected when `pr` is absent) but cannot fully confirm the **downstream sink is unguarded**, which is required to assert concrete impact (e.g., destructive checkout, arbitrary flag injection) per the review path's "reject if existing checks already stop it" rule.

## Title
Insufficient branch-name validation in `parseAppURL` allows dash-prefixed argv-injection strings to reach `checkoutLocalBranch` when `pr` is omitted - (File: `app/src/lib/parse-app-url.ts`)

### Summary
When a deep link omits `pr`, `parseAppURL` only runs `branch` through `testForInvalidChars`, whose regex does not exclude a leading `-`, unlike the sibling `sanitizedRefName` function which explicitly strips leading `-`/`+`. This lets an attacker-controlled `branch` value such as `-XYZ` reach `Dispatcher.openBranchNameFromUrl` → `checkoutLocalBranch` unmodified.

### Impact Explanation
If the (unverified) `checkoutLocalBranch` implementation passes `branchName` to `git` without a `--` separator, a dash-prefixed value could be interpreted as a `git checkout`/`git branch` flag rather than a ref name, potentially causing a forced/destructive checkout or other unintended git behavior triggered purely by a clicked link. Actual severity (whether it rises to file corruption or worse) depends on code not confirmed here.

### Likelihood Explanation
Reaching the sink only requires a user to click an `x-github-client://openrepo/...?branch=-something` link (no `pr` param); no other preconditions are needed.

### Recommendation
Apply the same leading-`-`/`+` stripping used by `sanitizedRefName` (or reject strings starting with `-`) to `branch` in `parseAppURL` unconditionally, not only when `pr` is set. Independently, verify/ensure all git invocations that consume this `branch` value insert a `--` separator before the ref argument as defense in depth.

### Proof of Concept
```ts
// app/src/lib/parse-app-url.ts
parseAppURL('x-github-client://openrepo/owner/repo?branch=-XYZ')
// -> { name: 'open-repository-from-url', url: 'owner/repo', branch: '-XYZ', pr: null, filepath: null }
```
This action is then dispatched to `Dispatcher.openRepositoryFromUrl` → `openBranchNameFromUrl(url, '-XYZ')` → `this.checkoutLocalBranch(repository, '-XYZ')` [5](#0-4) , without further sanitization visible at this layer. Confirming exploit impact requires inspecting the `checkoutLocalBranch` implementation itself, which I was unable to locate in this pass — recommend a follow-up session with full repo access to trace it precisely.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
