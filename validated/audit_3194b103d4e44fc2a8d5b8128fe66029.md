### Title
Participant index `0` accepted in DKG parameter/share validation due to missing zero check, placing a signer at the group-secret evaluation point — (File: `crypto/dkg/src/lib.rs`)

### Summary
The reference bug is an off-by-one boundary check (`>` instead of `>=`) that lets an update set a parameter to its harmful extreme value. The analog in Serai is the participant-index validation in `crypto/dkg`: `Participant` is documented as "a non-zero u16" and `Participant::new` rejects `0` (`crypto/dkg/src/lib.rs:23-35`), but `ThresholdParams::new` only checks `i.0 > n` and never `i.0 == 0` (`crypto/dkg/src/lib.rs:166-179`). The same `>`-only pattern appears in `ThresholdKeys::new`, which validates `verification_shares` keys with `u16::from(participant) > params.n()` (`crypto/dkg/src/lib.rs:361-365`), and in `ThresholdKeys::view`, which only checks the sorted `included` set's last element against `n` and never checks `included[0] != 0` (`crypto/dkg/src/lib.rs:486-491`). Because `ThresholdParams` (and `Participant`) are deserialized from untrusted bytes via `borsh::BorshDeserialize` — which constructs `Participant` directly, bypassing `Participant::new`'s zero check (`crypto/dkg/src/lib.rs:200-208`) — an unprivileged party can feed `Participant(0)` into these paths.

### Finding Description
The Shamir/DKG scheme places the group secret at evaluation point `x = 0`; honest participants use indexes `1..=n`. Serai's own code encodes this invariant: `Participant::new` returns `None` for `0`, and `all_participant_indexes` iterates `1..=n` (`crypto/dkg/src/lib.rs:194-197`). However, three validation sites use a `>`-only bound that treats index `0` as merely "not too large":

- `ThresholdParams::new`: `if i.0 > n { Err(InvalidParticipant) }` — `i.0 == 0` passes.
- `ThresholdKeys::new` share-key check: `u16::from(participant) > params.n()` — a `verification_shares` map containing key `0` passes.
- `ThresholdKeys::view`: after sorting, only `u16::from(*included.last()) > n` is checked — `included[0] == 0` passes, and the loop computes an `interpolation_factor` for it.

For Lagrange interpolation, `interpolation_factor` for `i = 0` computes `i_f = F::from(0)`, then `num = Π x_l` and `denom = Π (x_l - 0) = Π x_l`, so the factor is exactly `1` (`crypto/dkg/src/lib.rs:229-247`). A share at index `0` is therefore weighted by `1` and is cryptographically the group secret `f(0)` itself: `verification_share(0) = s·G = group_key`. Any actor holding the index-0 secret share holds the full group private key, not a threshold share of it.

### Impact Explanation
If `Participant(0)` reaches `ThresholdKeys::new` (via deserialization or a malicious DKG message carrying a share keyed at index `0`), the resulting `ThresholdCore` treats the group secret `f(0)` as an ordinary participant share: `original_secret_share()`/`secret_share` for index `0` equals the group's private key, and `verification_shares[0]` equals the group key. Whoever controls index `0` can then unilaterally sign (their share needs no interpolation; factor is `1`) and, more fundamentally, has recovered the complete threshold secret without any threshold quorum — defeating the entire `t`-of-`n` construction and enabling theft of all funds under the threshold key. In `view()`, an attacker-controlled `included` list containing `0` additionally triggers `verification_shares.insert(0, ...)` and places the offset on `included[0]` (`crypto/dkg/src/lib.rs:500-521`), corrupting the view for all other signers.

### Likelihood Explanation
Reachability requires untrusted bytes to flow into `ThresholdParams`/`Participant`/`ThresholdKeys` construction. `ThresholdParams` implements `borsh::BorshDeserialize` reading raw `u16`/`Participant` fields and calling `ThresholdParams::new` (`crypto/dkg/src/lib.rs:200-208`), and the task's read surface includes `ThresholdKeys::read`, meaning peer-supplied serialized parameters are a documented input vector. A malicious DKG peer or a peer supplying a serialized key-set can encode participant index `0`; the only validation (`i.0 > n`, `participant > n`) does not reject it. Whether index `0` can be consistently carried end-to-end through PedPoP/FROST depends on those callers' own checks, which were not fully verified — this is the residual uncertainty — but the missing bound in the core `crypto/dkg` validation is exact and matches the `>`-vs-`>=` bug class precisely.

### Recommendation
Enforce the documented `1 <= i <= n` invariant at every boundary:

```rust
// ThresholdParams::new, crypto/dkg/src/lib.rs
if (i.0 == 0) || (i.0 > n) {
  return Err(DkgError::InvalidParticipant { n, participant: i });
}

// ThresholdKeys::new share-key check
for participant in verification_shares.keys().copied() {
  if (u16::from(participant) == 0) || (u16::from(participant) > params.n()) {
    Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
  }
}

// ThresholdKeys::view — reject a zero first element after sorting
if (u16::from(included[0]) == 0) || (u16::from(*included.last().unwrap()) > n) {
  Err(DkgError::InvalidParticipant { n: self.params().n(), participant: included[0] })?;
}
```

Alternatively (defense in depth), make `Participant`'s deserialization reject `0` so the invariant cannot be bypassed by `borsh`/byte readers.

### Proof of Concept
1. Craft serialized bytes for a `ThresholdParams` with `t = 2, n = 3, i = 0x0000`. `borsh` deserialization succeeds: `Participant::deserialize_reader` yields `Participant(0)` and `ThresholdParams::new` accepts it because `0 > 3` is false.
2. Submit a `verification_shares` map containing key `Participant(0)` (replacing any honest index) to `ThresholdKeys::new`; the `> n` loop accepts it.
3. In `view(included)` or any sign flow, `interpolation_factor(Participant(0), included)` returns `F::ONE` since `denom = Π(x_l - 0) = Π x_l = num`. The index-0 holder's "share" `s = f(0)` is the group secret key itself: `s·G == group_key == verification_shares[0]`. The holder can produce valid Schnorr/FROST signatures for the threshold key alone — full private-key recovery with zero threshold participation.
