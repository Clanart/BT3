### Title
Stale AccountKey signature acceptance due to inconsistent SET-style validation between TxPool admission and block-execution paths - (File: blockchain/types/transaction.go)

### Summary
CVE-2022-24806 describes net-snmp accepting a malformed SET OID because the master agent and subagent each validated the input independently and inconsistently, letting an invalid value slip through into committed state. Kaia's transaction-signature/AccountKey validation exhibits the same "two independent validators, one skips the check" pattern: `Transaction.Validate` only performs the AccountKey re-validation when `checkMutableValue`/`onlyMutableChecks` is `true`, but the two authoritative call sites that actually admit/execute a transaction — `TxPool.validateTx` and `BlockChain.ApplyTransaction` — both invoke it with `false`.

### Finding Description
`Transaction.Validate` gates the AccountKey signature re-check behind the `checkMutableValue` flag: [1](#0-0) 

The comment on the interface itself flags this as an unresolved inconsistency: [2](#0-1) 

- `TxPool.validateTx` calls `tx.Validate(pool.currentState, pool.signer, pool.currentBlockNumber, false)` at admission time, and separately calls `tx.ValidateSender`, which caches `tx.validatedSender`/`tx.validatedFeePayer` **only once** (`if tx.validatedSender == (common.Address{})`): [3](#0-2) [4](#0-3) 

- The *only* place that re-validates the AccountKey against a possibly-mutated state (`checkMutableValue=true`) is `txList.Filter`, used for periodic pool maintenance/eviction: [5](#0-4) 

- The final, consensus-critical path — `BlockChain.ApplyTransaction`, which actually mutates state and burns/moves value — calls `tx.Validate(statedb, signer, blockNumber, false)`, i.e. with the AccountKey mutable-check explicitly disabled, and then relies purely on the cached `validatedSender`/`validatedFeePayer` via `AsMessageWithAccountKeyPicker`: [6](#0-5) 

Because the account-key cache set in `ValidateSender` is a "set-once" guard rather than a live check, and `ApplyTransaction`'s `Validate` call intentionally skips the mutable AccountKey re-check, the two enforcement points ("admission" and "execution") disagree about whether a transaction's signature is still consistent with the sender's *current* on-chain `AccountKey`. This is structurally identical to net-snmp's flaw: one validator (subagent/mempool) checks the input once, another validator (master agent/block executor) trusts a stale result instead of independently re-validating, and the malformed/now-invalid input is applied.

### Impact Explanation
If a transaction's signature was valid under the sender's `AccountKey` *at pool-admission time*, but the account's key is subsequently updated (e.g., via a concurrent `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction, or via `TxPoolModule` interactions) before the original transaction is picked up for block inclusion, and the periodic `txList.Filter` mutable re-check has not yet run or misses the window, `ApplyTransaction` will execute the transaction without re-validating the signature against the new key — because `checkMutableValue=false` skips exactly that check. This can let a transaction signed under a *revoked/old* key mutate state (value transfer, fee payment, contract call) after the legitimate account owner believed the key was rotated away, causing state divergence between nodes whose mempool eviction timing differs, or fee/value movement the current key holder did not authorize.

### Likelihood Explanation
Exploitability depends on precise timing between an `AccountUpdate` transaction and pending transactions signed under the old key sitting in the pool/queue across block boundaries, and on the cadence of `txList.Filter`'s mutable-check pass relative to block production. This is a race-condition-dependent condition rather than a trivially always-reachable bug, which reduces (but does not eliminate) likelihood — it is reachable by any regular tx sender (self-triggered key rotation) or an account interacting with a pending fee-delegation counterparty.

### Recommendation
Make `BlockChain.ApplyTransaction` (and any other consensus-execution path) always perform the mutable AccountKey re-check (`checkMutableValue=true`) immediately before applying a transaction to state, rather than relying on a set-once cached `validatedSender`. Alternatively, remove the set-once guard in `ValidateSender` and always re-derive/re-validate the sender's key against the state passed at call time, so that admission-time and execution-time validation are provably consistent — closing the TODO noted in `tx_internal_data.go:335`.

### Proof of Concept
Conceptual PoC (cannot be executed without live node/mempool access):
1. Account A signs Tx1 (e.g., a `ValueTransfer`) with `AccountKey_old`. Tx1 is submitted and admitted into `TxPool` via `validateTx`, which validates against current state and caches `validatedSender` (once).
2. Immediately after, Account A submits an `AccountUpdate` transaction (Tx2) that rotates its `AccountKey` to `AccountKey_new`, and Tx2 is included in block N before Tx1.
3. If `txList.Filter`'s mutable recheck of Tx1 (using `checkMutableValue=true`) does not evict Tx1 before it is selected for block N+1 (e.g., due to scheduling/timing, or Tx1 residing in a list snapshot not yet filtered), `ApplyTransaction` executes Tx1 in block N+1 using `tx.Validate(..., false)`, skipping the `AccountKey` mutable check, and relies on the stale cached `validatedSender`.
4. Tx1 succeeds under the old, now-revoked key, moving value/state that the account owner intended to prevent by rotating keys.

func (tx *Transaction) Validate(db StateDB, signer Signer, currentBlockNumber uint64, checkMutableValue bool) error {
	// validate the sender's account key
	if checkMutableValue {
		accKey := db.GetKey(tx.ValidatedSender())
		if tx.IsEthereumTransaction() {
			if !accKey.Type().IsLegacyAccountKey() {
				return ErrNotLegacyAccount
			}
		} else {
			if pubkey, err := SenderPubkey(signer, tx); err != nil {
				return ErrInvalidSigSender
			} else if accountkey.ValidateAccountKey(currentBlockNumber, tx.ValidatedSender(), accKey, pubkey, GetRoleTypeForValidation(tx.Type())) != nil {
				return ErrInvalidAccountKey
			}
		}

				return ErrInvalidAccountKey
			}
		}
	}

// ValidateSender finds a sender from both legacy and new types of transactions.
// It returns the senders address and gas used for the tx validation.
func (tx *Transaction) ValidateSender(signer Signer, p AccountKeyPicker, currentBlockNumber uint64) (uint64, error) {
	if tx.IsEthereumTransaction() {
		addr, err := Sender(signer, tx)
		// Legacy transaction cannot be executed unless the account has a legacy key.
		if p.GetKey(addr).Type().IsLegacyAccountKey() == false {
			return 0, kerrors.ErrLegacyTransactionMustBeWithLegacyKey
		}
		tx.mu.Lock()
		if tx.validatedSender == (common.Address{}) {
			tx.validatedSender = addr
			tx.validatedFeePayer = addr
		}
		tx.mu.Unlock()
		return 0, err
	}

	pubkey, err := SenderPubkey(signer, tx)
	if err != nil {
		return 0, err
	}
	txfrom, ok := tx.data.(TxInternalDataFrom)
	if !ok {
		return 0, errNotTxInternalDataFrom
	}
	from := txfrom.GetFrom()
	accKey := p.GetKey(from)

	gasKey, err := accKey.SigValidationGas(currentBlockNumber, GetRoleTypeForValidation(tx.Type()), len(pubkey))
	if err != nil {
		return 0, err
	}

	if err := accountkey.ValidateAccountKey(currentBlockNumber, from, accKey, pubkey, GetRoleTypeForValidation(tx.Type())); err != nil {
		return 0, ErrInvalidAccountKey
	}

	tx.mu.Lock()
	if tx.validatedSender == (common.Address{}) {
		tx.validatedSender = from
		tx.validatedFeePayer = from
	}
	tx.mu.Unlock()

	return gasKey, nil
}
