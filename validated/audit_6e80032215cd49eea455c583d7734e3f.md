### Title
Attacker-controlled item count drives unbounded deserialization work in `SchnorrAggregate::read` — partial denial of service - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` in `crypto/schnorr` reads a 32-bit count from the attacker-controlled byte stream and then loops that many times performing elliptic-curve point deserialization (`C::read_G`), with no cap on the count, no check against the remaining input length, and no bound on the work performed. This is the direct analog of the referenced Discourse issue: an endpoint accepts an unbounded number of items supplied by a remote party and performs per-item processing proportional to that count.

### Finding Description
```rust
// crypto/schnorr/src/aggregate.rs
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
  let mut len = [0; 4];
  reader.read_exact(&mut len)?;

  let mut Rs = vec![];
  for _ in 0 .. u32::from_le_bytes(len) {
    Rs.push(C::read_G(reader)?);
  }
  Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
``` [1](#0-0) 

The count field is `u32`, permitting up to ~4.29 billion iterations. Each iteration pushes a group element into `Rs` and invokes `C::read_G`, which performs a full point decompression/validation (canonical encoding check, curve equation / subgroup checks depending on the `Ciphersuite` — e.g., `dalek-ff-group` or `kp256`/`ed448` `read_G` implementations). There is:

- No upper bound on `len` (compare with `Transaction::read` in `coordinator/src/tributary/transaction.rs:286`, which explicitly rejects payloads exceeding `TRANSACTION_SIZE_LIMIT`, and the `SlashReport` arm at line 431 which caps the item count at `MAX_KEY_SHARES_PER_SET - 1` — demonstrating the codebase knows to bound attacker-controlled counts but this site was missed).
- No pre-check that the stream even plausibly contains `len` group elements; `read_exact` will only fail at EOF, so an attacker who supplies a large padded stream forces proportional point-decompression CPU work and `Vec` growth before deserialization completes.

The deserialized `Rs` vector is then consumed by `SchnorrAggregate::verify` (aggregate.rs:127-146), which builds a `multiexp_vartime` pair list of size `2*len + 1` — a second, even more expensive linear pass over attacker-controlled point count.

### Impact Explanation
An unprivileged party who can feed bytes into `SchnorrAggregate::read` (any aggregator/batch-verification path that accepts serialized aggregate signatures from peers or users) can force the victim to allocate and decompress up to millions/billions of curve points — CPU-heavy group operations — plus a multiexponentiation over the resulting vector in `verify`. This yields a sustained partial denial of service on the verifying component, analogous to the Discourse onebox endpoint consuming unbounded work per request. Because the count is `u32`-driven and unchecked, a modestly sized input still causes worst-case `read_exact` stream consumption and per-point group operations before any error is raised; the only limit is how much input the transport allows, which is an integration property, not a guarantee of this code.

### Likelihood Explanation
`SchnorrAggregate` and `SchnorrAggregator` are public API types intended exactly for aggregating signatures from multiple parties — i.e., inputs originating from untrusted signers. `read` is the deserialization entry point listed among the reachable surfaces (`...::read` / verify APIs). Any deployment that accepts serialized aggregate signatures over a network channel reaches this code with zero privileges beyond the ability to send bytes. No key material or collusion is needed. The trigger is a single crafted length prefix plus a large padded byte stream.

### Recommendation
Bound `len` before looping: either reject counts above a sane maximum number of aggregated signatures (e.g., the maximum plausible participant count, as `SlashReport` does with `MAX_KEY_SHARES_PER_SET`), or check `len` against a known remaining-input-length budget before iterating. A cheap guard such as `if u32::from_le_bytes(len) > MAX_AGGREGATE_SIGS { return Err(...) }` restores parity with the limit enforcement already present elsewhere in the codebase.

### Proof of Concept
1. Serialize a `SchnorrAggregate` wire payload: `len = 0xFFFFFFFF` (u32 LE) followed by a large body of validly encoded points (or simply a large stream so `read_G` keeps succeeding as long as bytes remain).
2. Hand it to any code path calling `SchnorrAggregate::<C>::read(&mut bytes)`.
3. Observe the loop performs `read_G` per remaining input chunk with no rejection of the declared count; memory grows linearly in `Rs`, and a subsequent `verify` call runs `multiexp_vartime` over `2*len + 1` pairs, amplifying the CPU cost.

Note: because each iteration must consume bytes via `read_exact`, practical work is bounded by input size the caller allows through; the defect is that this limit is entirely external — the decoder itself accepts and acts on a count of up to 4 billion with no semantic cap, unlike sibling deserializers in the codebase that enforce explicit limits.
