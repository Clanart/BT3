### Title
Unbounded length-prefixed deserialization of `SchnorrAggregate::Rs` allows remote memory exhaustion - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The external report describes CWE-770: a missing bound on attacker-influenced resource consumption that lets an unauthenticated remote party crash the service (in ntpd-rs, an unlimited accept loop exhausts file descriptors until `accept()` aborts the process). The same class exists in Serai's in-scope `crypto/schnorr` crate: `SchnorrAggregate::read` reads an attacker-controlled `u32` element count and then pushes that many group elements into a `Vec` with no upper bound, no size limit, and no relationship to the amount of data actually available [1](#0-0) . An untrusted byte stream fed to this deserialization API can therefore force heap allocation proportional to whatever the attacker supplies — up to ~4 billion `C::G` elements — and abort the process via OOM, mirroring the advisory's crash impact.

### Finding Description
`SchnorrAggregate` is the half-aggregation signature type from `crypto/schnorr` (eprint 2021/350), holding `Rs: Vec<C::G>` and a scalar `s` [2](#0-1) . Its `read` implementation is:

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;
    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }
    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
``` [3](#0-2) 

Two properties make this the analog:

1. **No bound on the count.** The `u32` length field permits up to 4,294,967,295 iterations. Nothing in `read` caps the declared count against a sane maximum, the enclosing message size, or the remaining bytes. Compare with `EncryptedMessage`/`Commitments` deserialization in PedPoP, which bounds the number of group elements by `params.t()` [4](#0-3) , and with the coordinator's `DkgCommitments` parsing, which explicitly checks `commitments_len * each_commitments_len` against `TRANSACTION_SIZE_LIMIT` before allocating [5](#0-4) . `SchnorrAggregate::read` has no equivalent guard.

2. **Reachable from untrusted bytes.** `SchnorrAggregate::read` is a public deserialization entry point of the same shape as the in-scope `read` APIs (`SchnorrSignature::read`, `DLEqProof::read`, `Commitments::read`), intended for aggregate Schnorr signatures received over the wire. An unprivileged peer controls the 4-byte count and the point bytes that follow; `C::read_G` performs a full point decode per element, so the attacker both forces memory growth via `Vec::push` reallocation (amortized doubling keeps up to ~2× the input resident) and imposes a point-decompression cost per ~32-byte input.

The follow-on `verify` does check `self.Rs.len() != keys_and_challenges.len()` before doing the multiexp [6](#0-5) , so the CPU amplification in `verify` is bounded by the honest statement count — the vulnerability is in `read` itself, which builds the unbounded `Vec` before any verification context exists.

### Impact Explanation
Identical to the advisory: a missing resource limit reachable by an unauthenticated remote party leads to process termination. Where ntpd-rs aborts on `EMFILE`, a Serai node deserializing an attacker-supplied `SchnorrAggregate` aborts on allocation failure / OOM kill as `Rs` grows without bound. For a long-running validator/processor this is a full availability loss of the signing process; if it auto-restarts, the attack repeats indefinitely (the advisory's exact impact model). This maps to CWE-770 (Allocation of Resources Without Limits or Throttling). Severity: High for availability, matching the advisory; no secret-key or forgery impact.

### Likelihood Explanation
Exploitation requires only that the attacker can get their bytes passed to `SchnorrAggregate::read` — i.e., wherever aggregate signatures are exchanged between participants or validators. The input is trivially constructed: a 4-byte little-endian count followed by valid point encodings (invalid encodings also work; `read_G` fails per-element, but each failed element still consumed a `push` slot's worth of work and any large count combined with a large stream already grew the Vec). No authentication, no valid key material, and no protocol state is needed — the crash occurs during deserialization, before signature verification. This matches the advisory's "unauthenticated remote attacker opens resources faster than a timeout" bar; here there is no timeout at all because no limit exists to trip.

### Recommendation
Bound the count before iterating, the same way the rest of the codebase handles attacker-controlled lengths:

```rust
// crypto/schnorr/src/aggregate.rs
const MAX_AGGREGATE_SIGNATURES: u32 = /* sane protocol bound, e.g. MAX_KEY_SHARES_PER_SET */;
let len = u32::from_le_bytes(len);
if len > MAX_AGGREGATE_SIGNATURES {
    Err(io::Error::other("aggregate signature exceeds maximum signer count"))?;
}
```

Additionally, validate `len` against remaining input where the reader supports it (e.g., wrap in `io::Take`), mirroring the `TRANSACTION_SIZE_LIMIT` check in `coordinator/src/tributary/transaction.rs` [7](#0-6)  and the chunked-read defense already used in `networks/ethereum/src/machine.rs` for claimed lengths [8](#0-7) .

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use schnorr::SchnorrAggregate;
use frost::curve::Secp256k1; // any Ciphersuite

// Craft a stream: u32 count = u32::MAX, followed by as many valid
// compressed points as bandwidth allows. Each Secp256k1 read_G is 33 bytes.
let mut buf = u32::MAX.to_le_bytes().to_vec();
let g = <Secp256k1 as Ciphersuite>::generator().to_bytes();
// attacker streams point bytes; memory grows ~linearly with bytes sent,
// Vec doubling keeps up to ~2x resident; count never forces an early stop
for _ in 0 .. 50_000_000 { buf.extend(g.as_ref()); } // ~1.6 GB stream
// Process aborts / OOM-kills inside read before verify is ever reached:
let _ = SchnorrAggregate::<Secp256k1>::read(&mut Cursor::new(&buf));
```

The read loop has no ceiling; the only thing that stops it is EOF after `len` point decodes — so an attacker streaming data (or simply supplying a multi-hundred-MB payload, small relative to peer message allowances) drives resident memory to exhaustion. `Vec` growth to `u32::MAX` elements would require ~128 GB of points if fully satisfied, but the crash only needs the attacker to supply input exceeding available RAM — no valid signatures, keys, or protocol participation required.
