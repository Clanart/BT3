### Title
Payout `OP_RETURN` operator attribution is unsigned and RBF-malleable, letting an attacker frame an arbitrary honest operator as payer - (File: `core/src/builder/transaction/operator_reimburse.rs`, `core/src/verifier.rs`)

### Summary
`create_payout_txhandler` builds the payout transaction with three outputs (payout, anchor, `OP_RETURN(operator_xonly_pk)`) but only signs input 0 with the withdrawing user's `KeySpend` signature, whose sighash flag (`SinglePlusAnyoneCanPay` per the withdrawal design) commits only to input 0 and output 0. `update_finalized_payouts` then blindly trusts whichever `OP_RETURN` value is present in the confirmed block to attribute the payout to an operator, with no cryptographic proof that the named operator actually broadcast or funded the transaction.

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk[withdrawal_id] == pubkey_of_party_that_funded_output_0`.

`create_payout_txhandler` constructs the payout tx with output 0 = user payout, output 1 = anchor, output 2 = `op_return_txout(operator_xonly_pk)`, and signs only input 0 via `set_p2tr_key_spend_witness(&user_sig, 0)`: [1](#0-0) 

Because the withdrawal signature is `SIGHASH_SINGLE | ANYONECANPAY` (as stated in the docstring "signature given to operators off-chain" and consistent with allowing any operator to plug their own key into the same user signature), the signature commits only to input 0 and output 0. Outputs 1 (anchor) and 2 (`OP_RETURN`) are outside the signed digest and can be replaced by anyone without invalidating the witness.

`update_finalized_payouts` scans the confirmed block, extracts whichever payout tx now spends withdrawal outpoint `W`, and naively parses whatever `OP_RETURN` bytes are present as the "payer" operator, with no check that this key corresponds to the actual broadcaster or fee-payer of the transaction: [2](#0-1) 

Exploit flow: honest operator O broadcasts `payout_tx` (input 0 = W, output 0 = payout, output 2 = `OP_RETURN(O)`), reusing the withdrawing user's off-chain signature. Because output 2 is unsigned, the attacker (who is the withdrawing user or anyone who observed the mempool tx) constructs `payout_tx'` with identical input 0/witness and output 0, but with `OP_RETURN(P)` for an arbitrary real, registered operator P, and RBF-replaces O's transaction with a higher fee. `payout_tx'` confirms, `update_finalized_payouts` writes `payout_payer_operator_xonly_pk = P`, and `PayoutCheckerTask` later finds withdrawal `i` for operator P via `get_first_unhandled_payout_by_operator_xonly_pk`, leading P into the reimbursement flow for a payout it never funded, while O — who actually paid the withdrawal out of pocket — is permanently unable to be credited for it.

None of the existing guards catch this: `is_deposit_valid` and `SECP.verify_schnorr` validate only the withdrawal input signature (input 0/output 0), not the `OP_RETURN` output; there is no musig2/N-of-N signature over the `OP_RETURN`; and the database update in `update_payout_txs_and_payer_operator_xonly_pk` has no uniqueness/ownership constraint tying the recorded pubkey to the actual fee-payer of the confirmed transaction.

### Impact Explanation
An honest operator (O) that fronted a withdrawal from its own funds is left permanently unattributed and unable to claim reimbursement for that payout, since the DB row for that withdrawal is now credited to a different operator (P) it never funded. Operator P is drawn into believing it fronted a payout it never paid, entering the reimbursement/kickoff process for that withdrawal, potentially leading to disputes over Reimburse collateral or malformed kickoffs it cannot back with a real payout on-chain. This matches the Critical category: "an operator reimbursed for a payout it never funded" and "an honest operator permanently unable to be reimbursed." The attack is repeatable across any withdrawal/operator pair, since it only requires observing/RBF-replacing a mempool payout tx before confirmation, which is possible for every withdrawal cycle.

### Likelihood Explanation
Preconditions are minimal and match normal operation: a registered withdrawal `W` with no payout yet confirmed, RBF enabled (default in Bitcoin Core/regtest), and knowledge of the honest operator's in-flight `payout_tx` (visible in mempool) plus any real operator P's public xonly pubkey (operator set is public). The attacker needs only to pay a marginally higher fee to win the RBF replacement — a small, bounded BTC cost, well within reach of an unprivileged actor (indeed the withdrawing user themselves already holds the signature needed to construct alternate payout tx templates, since it was designed to be reusable across different operators' `OP_RETURN` values).

### Recommendation
Bind the `OP_RETURN` operator attribution cryptographically to whichever party actually pays: e.g., require the withdrawal signature to use `SIGHASH_ALL` (or `SIGHASH_SINGLE` without `ANYONECANPAY` plus committing to all outputs) so the `OP_RETURN` output cannot be malleated after broadcast, or require a separate operator-specific signature/covenant proving the named operator authorized/funded that specific `OP_RETURN` value before `update_finalized_payouts` accepts it as attribution.

### Proof of Concept
In a `cargo test` (regtest, no live Citrea):
1. Perform a deposit + withdrawal registration for withdrawal `i`, obtaining the off-chain user signature for the withdrawal UTXO `W`.
2. Have operator O build and broadcast `payout_tx` via `create_payout_txhandler` with `operator_xonly_pk = O`.
3. Before confirmation, construct `payout_tx'` reusing input 0/witness and output 0 from `payout_tx`, but with `OP_RETURN(P)` for a different registered operator P, and a higher fee; broadcast it (RBF) and mine it.
4. Call `Verifier::update_finalized_payouts` (via normal block-sync flow) on the block containing `payout_tx'`.
5. Assert `db.get_payout_payer_operator_xonly_pk(i) == P.xonly_pk` (not `O.xonly_pk`), demonstrating `payout_payer_operator_xonly_pk[i] != funder_of_output_0 (O)`.
