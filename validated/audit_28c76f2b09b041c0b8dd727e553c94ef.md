### Title
`HostManager.onAccept` authenticates cross-chain governance by source chain only, not by source module — any Hyperbridge-chain sender can trigger `Withdraw` or `updateHostParams` - (File: `evm/src/core/HostManager.sol`)

### Summary
The Code4rena report's core invariant is "a single trusted authority gates every privileged action, and if that authority's identity check is broken/absent, the whole protocol's execution can be redirected." Hyperbridge's local analog is not "an EOA admin is powerful" (that pattern is explicitly gated by legitimate `restrict(admin)`/`restrict(handler)` checks throughout `EvmHost.sol` and is out of scope per the impact gate). Instead, the analogous *broken identity-binding* pattern shows up in `HostManager.onAccept`, which is the contract EVM hosts trust to execute cross-chain governance (fund withdrawals and full `HostParams` replacement) arriving over ISMP from the Hyperbridge parachain.

### Finding Description
`HostManager.onAccept` is the sole authenticator for privileged, unattended, EVM-side execution of governance actions dispatched from Hyperbridge: [1](#0-0) 

The only authentication performed is:
```solidity
if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
```
This checks that the request's **source chain id** equals the Hyperbridge state machine id, i.e. that the message came from *some* account/pallet on the Hyperbridge parachain. It never checks `request.from` — the specific module/pallet identity on that chain that dispatched the message. Once that single chain-level check passes, the raw `request.body` is decoded and dispatched directly into privileged host mutators:

```solidity
} else if (action == OnAcceptActions.SetHostParam) {
    HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
    IHostManager(_params.host).updateHostParams(hostParams);
}
```

`updateHostParams` replaces `admin`, `hostManager`, `handler`, `consensusClient`, `feeToken`, and the `stateMachines` whitelist wholesale (guarded only by non-zero/interface checks, not by authorization beyond the `restrict(_hostParams.hostManager)` on `EvmHost`, which the attacker already satisfies by going through `HostManager`): [2](#0-1) 

By contrast, the project's own `BandwidthManager` pattern explicitly binds inbound governance to a **specific registered module address** on the source chain, not merely the source chain itself — the pallet "accepts purchases dispatched from `source` if and only if `request.from` matches the registered address; any other sender on that chain is rejected": [3](#0-2) 

`HostManager` has no equivalent `request.from` allowlist. Any pallet, precompile, or signed extrinsic capable of dispatching an ISMP `PostRequest` from the Hyperbridge parachain to this specific `HostManager` address (i.e., anything satisfying `request.source == hyperbridge`) can supply an arbitrary `request.body` and have it decoded as either:
- `Withdraw` → `IHostManager(_params.host).withdraw(withdrawParams)` (drains accumulated bridge/relayer revenue to an attacker-chosen address), or
- `SetHostParam` → `updateHostParams(hostParams)` (replace `admin`, `hostManager`, `consensusClient`, `handler`, `feeToken` with attacker-controlled addresses).

Once `hostManager`/`admin`/`consensusClient` are attacker-controlled, the attacker can subsequently forge consensus/state proofs or freeze/thaw the host at will, i.e. full compromise of that EVM deployment of the host — a direct instance of the "false remote state acceptance" and "cross-chain admin effects reachable through wrong module bindings" pivots called out in the task.

### Impact Explanation
This is a false-state-acceptance / unauthorized-execution primitive on the module-binding boundary explicitly flagged as in-scope ("Request... paths must bind chain id, module/app identity... on both Substrate and EVM" and "Cross-chain admin or host-management effects must not be reachable through malformed proofs, wrong module bindings, or unauthenticated message flow"). If any non-privileged, non-governance-restricted pallet/account on the Hyperbridge chain can dispatch a `PostRequest` with `source == hyperbridge` to the registered `HostManager` module id, it can drain the bridge revenue via `Withdraw` and/or hijack `admin`/`hostManager`/`consensusClient` via `SetHostParam`, leading to outright loss of funds and complete takeover of the EVM host's trust root.

### Likelihood Explanation
I was not able to fully verify, within this session, whether the Hyperbridge parachain-side dispatcher that targets `HostManager`'s registered module id is itself restricted so that only a governance-restricted origin (e.g., `EnsureRoot`/`host-executive` pallet) can ever produce a `PostRequest` whose `to`/module binding resolves to this specific `HostManager` contract address. My `grep_search` against `modules/pallets/host-executive/src/lib.rs` returned matches but the tool budget was exhausted before I could read the actual dispatch-authorization code (e.g. `set_host_params` extrinsic's `ensure_origin` and whether the pallet is the only entity permitted to dispatch to a per-chain-registered `HostManager` address on the Hyperbridge side, analogous to `BandwidthPallet::set_manager`). If Hyperbridge enforces a similarly strict, root-only "manager address is fixed per source chain and only one pallet may dispatch to it" model at the ISMP router/dispatch level, then the *EVM-side* missing `request.from` check may be an unexercised gap (defense-in-depth) rather than a directly exploitable path, since nothing else on the Hyperbridge chain would ever produce a request bound for this contract. Confirming or refuting this requires reading `modules/pallets/host-executive/src/lib.rs` and the ISMP router/module-id binding config in `parachain/runtimes/*/src/ismp.rs` in full, which needs a fresh session.

### Recommendation
Add an explicit `request.from` check in `HostManager.onAccept`, mirroring the `BandwidthManager`/pallet-bandwidth model: store the expected Hyperbridge-side module id (the `host-executive` pallet's `ModuleId`) at construction/configuration time, and require `request.from == expectedModuleId` in addition to `request.source == hyperbridge` before decoding and dispatching `Withdraw`/`SetHostParam`. This closes the gap regardless of whether the parachain-side dispatch path is currently exclusive, and brings `HostManager` in line with the project's own stated module-binding invariant used elsewhere (`BandwidthManager`).

### Proof of Concept
Conceptual PoC (cannot be fully executed without confirming the parachain-side dispatch restriction, see Likelihood):
1. On Hyperbridge, from any pallet/account capable of calling the generic ISMP dispatcher (`IsmpDispatcher::dispatch_request`) with `source = host_state_machine()` and `to` set to the target EVM `HostManager` contract's address bytes.
2. Set `body[0] = 1` (`OnAcceptActions.SetHostParam`) and `body[1:]` to an ABI-encoded `HostParams` struct with `admin`/`hostManager` set to attacker-controlled addresses.
3. Once relayed and proven on the EVM host, `HandlerV2` calls `HostManager.onAccept`, which only checks `request.source.equals(hyperbridge)` — true — and proceeds to call `IHostManager(_params.host).updateHostParams(hostParams)`: [1](#0-0) 
4. `admin`/`hostManager`/`consensusClient` on the EVM host are now attacker-controlled, enabling subsequent draining via `withdraw` or forged consensus/state proofs.

```text
    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
```

```text
    /**
     * @dev Updates the HostParams. Only callable by cross-chain governance
     * via the configured `hostManager`. The admin has no privileges here —
     * environments that need a privileged admin override (testnets, forks)
     * should use `TestnetHost`, which extends this contract.
     *
     * Marked `virtual` so subclasses can broaden the authorization
     * @param params, the new host params.
     */
    function updateHostParams(HostParams memory params) external virtual restrict(_hostParams.hostManager) {
        updateHostParamsInternal(params);
    }

    /**
     * @dev Updates the HostParams. Will reset all fishermen accounts and initialize any new state machines.
     * @param params, the new host params.
     */
    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }
```

Governance binds the deployed contract address to the source chain on the pallet side:
