### Title
SSRF via unvalidated Data Layer mirror/subscription URLs used for outbound HTTP downloads - (File: chia/data_layer/download_data.py)

### Summary
The Data Layer service performs outbound HTTP(S) requests to server URLs that are fully attacker-controlled — either supplied directly via the `subscribe` RPC or learned from another peer's on-chain-announced mirror record — with no validation of scheme, host, or destination address. This mirrors the classic SSRF pattern in CVE-2025-22952 (memos), where a user-supplied URL is used server-side without validating that it doesn't point at internal/private network resources.

### Finding Description
`DataLayerRpcApi.subscribe()` forwards a caller-supplied list of `urls` straight into `DataLayer.subscribe()`, which only strips trailing slashes before persisting them as `ServerInfo` entries: [1](#0-0) [2](#0-1) 

During the periodic sync loop, `fetch_and_validate()` iterates over `servers_info` (URLs for a given `store_id`) and calls `insert_from_delta_file` → `download_file` → `http_download`, which issues an `aiohttp` GET directly against `server_info.url + "/" + filename` with no restriction on scheme or target host/IP: [3](#0-2) [4](#0-3) 

Per the module's own architecture notes, these server URLs are not limited to what the local operator entered — they are also synced from other stores' on-chain mirror announcements: "`update_subscription()` performs four ordered steps: sync subscription URLs from wallet mirrors, fetch/validate remote data..." and "Plugin and mirror URLs are external trust inputs." [5](#0-4) [6](#0-5) 

This means any counterparty who publishes a DataLayer mirror record for a store id (or any RPC caller who calls `subscribe`) can cause the local DataLayer service to issue outbound HTTP requests to an arbitrary attacker-chosen URL — including `http://127.0.0.1/...`, internal RPC ports, or cloud metadata endpoints (`http://169.254.169.254/...`) — with no allowlist/denylist or DNS-rebinding protection.

### Impact Explanation
An attacker who gets a victim node to subscribe to (or track a mirror for) a malicious store can force the node to make server-side HTTP requests to internal-only network resources reachable from the machine running the DataLayer service — e.g., probing internal services/ports, hitting cloud metadata services to steal credentials, or reaching loopback-bound RPC endpoints that trust local origin. Because the URL is used verbatim (`server_info.url + "/" + filename`) with attacker-controlled path/host, this is a full SSRF primitive, not merely a resource-exhaustion issue.

### Likelihood Explanation
Reaching this path only requires (a) calling the local `subscribe` RPC with an attacker-influenced URL, or (b) publishing an on-chain DL mirror record that another node syncs and treats as a valid server for a subscribed store — both are normal, expected Data Layer client/subscriber workflows, not privileged or malicious-peer-only actions. No additional confirmation of intent or destination is performed before the outbound request fires.

### Recommendation
Before issuing any outbound request in `http_download`/`get_downloader`, validate and restrict destination URLs: enforce an allowed scheme set, resolve and reject requests to loopback/link-local/private/reserved IP ranges (and re-validate after redirects/DNS resolution to prevent rebinding), and consider requiring explicit operator opt-in/allowlisting for externally-supplied mirror URLs before they are used for automatic downloads.

### Proof of Concept
1. Attacker creates a DataLayer store and publishes a mirror record whose URL is `http://169.254.169.254/latest/meta-data/` (or `http://127.0.0.1:<internal-port>/...`).
2. Victim subscribes to the attacker's `store_id` via the `subscribe` RPC (`chia data subscribe -i <store_id>`), matching the documented flow in [1](#0-0) .
3. During the periodic sync loop, `fetch_and_validate()` selects the attacker's server URL and calls `http_download`, causing the victim's DataLayer process to issue an HTTP GET to the attacker-chosen internal/metadata address, as shown in [3](#0-2) .

    async def subscribe(self, store_id: bytes32, urls: list[str]) -> Subscription:
        parsed_urls = [url.rstrip("/") for url in urls]
        subscription = Subscription(store_id, [ServerInfo(url, 0, 0) for url in parsed_urls])
        await self.wallet_rpc.dl_track_new(DLTrackNew(launcher_id=subscription.store_id))
        async with self.subscription_lock:
            await self.data_store.subscribe(subscription)
        self.log.info(f"Done adding subscription: {subscription.store_id}")
        return subscription

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()

```markdown
- `update_subscription()` performs four ordered steps: sync subscription URLs from wallet mirrors, fetch/validate remote data, upload local files for owned/current data, then prune old full files. Reordering these affects mirror discovery and file availability.
- Wallet reachability failures are intentionally non-fatal. Subscription tracking stops early if the wallet RPC connection is unavailable and retries next cycle; per-subscription failures are logged without killing the loop.
- `fetch_and_validate()` uses wallet singleton history as the target generation/root sequence, randomizes eligible server URLs, tries plugin-specific or plain HTTP delta downloads, and marks mirror/server failures with backoff in the subscriptions table.
- Unsubscribe is queued and processed only after fetch jobs complete while holding `subscription_lock`, avoiding races between deletion of local subscription/data and active download/update work.
- Owned stores are treated as local publication sources even when they have no external mirror URLs. Subscribed stores are treated as replication targets whose chain roots are verified through wallet state.
```

## Fragility Hotspots

- High-risk edits move work across DB writer transactions, `_update_confirmation_status()`, pending-root status changes, or wallet RPC calls. These boundaries encode publication and rollback assumptions.
- File-system writes for Merkle blobs, key/value blobs, and `.dat` files have TODOs around locking. Concurrent service/plugin/server access should be treated as a real consistency concern.
- Empty-root normalization is subtle and historically uneven. Audit any change touching `bytes32.zeros`, `None`, `Root.node_hash`, or proof roots with both empty and non-empty stores.
- Plugin and mirror URLs are external trust inputs. Downloaded data must continue to be verified against wallet-advertised roots, and file path/name validation must stay strict.
- DataLayer wallet code depends on singleton CLVM structure, odd singleton amounts, lineage proofs, and offer solver field names. Changes in wallet puzzle drivers or offer summaries can break this module without direct edits here.
