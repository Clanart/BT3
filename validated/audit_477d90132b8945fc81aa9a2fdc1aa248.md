The strongest analog is a **fixed, undersized gas budget wrapped around an attacker-sized loop of external lookups/calls** in the CW→EVM synthetic-receipt hook, structurally identical to the reported `_healRequestFulfilled` pattern (bounded callback gas budget + loop + external work).

### Title
Fixed `DeliverTxHookWasmGasLimit` gas meter can be exhausted by an attacker-controlled number of wasm events, silently dropping synthetic EVM logs for a successful transaction - ([File: app/receipt.go])

### Summary
`AddCosmosEventsToEVMReceiptIfApplicable` runs after every successful CosmWasm `DeliverTx` and, for each `wasm` module event emitted by the tx, looks up CW20/CW721/CW1155 pointer contracts and translates the event into synthetic EVM logs [1](#0-0) . This entire loop is wrapped in a gas meter capped at the fixed param `DeliverTxHookWasmGasLimit` (default 300,000) regardless of how many wasm events the underlying transaction produced [2](#0-1) , [3](#0-2) .

### Finding Description
The loop at [4](#0-3)  iterates over every wasm event in the tx result and, per event, performs three pointer-registry keeper lookups (`GetERC20CW20Pointer`, `GetERC721CW721Pointer`, `GetERC1155CW1155Pointer`) plus event translation (`translateCW20Event`, `translateCW721Event`, `translateCW1155Event`). `translateCW20Event` can additionally issue a `WasmKeeper.QuerySmart` external call per `increase_allowance`/`decrease_allowance` action [5](#0-4) . All of this state-charged work is metered against `wasmToEvmEventCtx`, whose gas meter has a hard-coded limit sourced only from the on-chain param (300,000 gas by default) — not scaled to the number of wasm events, the tx's actual gas limit, or the number of distinct CW20/721/1155 contracts touched [6](#0-5) .

A CosmWasm transaction can legitimately emit an unbounded number of wasm events within a single Cosmos gas-metered tx (e.g., a CW20/CW721/CW1155 contract that emits many `transfer`/`mint`/`approve` events in one execution, or a multi-message tx batching many wasm calls). Because Cosmos tx gas limits can be set far higher than 300,000, a user can craft a transaction whose "outer" gas budget comfortably covers many wasm sub-calls/events, but whose post-processing synthetic-log translation exceeds the fixed 300,000-gas hook budget. The comment in the code itself anticipates this risk: "txs with a very large number of WASM events may run out of gas" [7](#0-6) .

### Impact Explanation
`NewGasMeterWithMultiplier` panicking with out-of-gas inside this hook would propagate up through `evmHook(...)` called from `DeliverTx` after the message result is already committed to the cache multi-store [8](#0-7) . Depending on how the panic is recovered relative to `msCache.Write()` at line 117, this can result in: (a) inconsistent EVM synthetic receipts/logs for pointer contracts (missing ERC20/721/1155 Transfer/Approval events even though the underlying CW state change succeeded and was committed), breaking EVM light-client/indexer assumptions of receipt-log completeness for a status-success tx, or (b) if it aborts/reverts the whole tx path, it produces a state-dependent, event-count-triggered DoS on that specific transaction category, since the wasm side effects already landed in state before the hook runs. Either outcome is a correctness/availability defect in the CW↔EVM pointer bridge reachable by simply calling a CW20/721/1155 pointer-mapped contract with a transaction crafted to emit enough events.

### Likelihood Explanation
Any pointer-user or public RPC client submitting a wasm transaction can trigger this: no privileged access, no validator collusion, and no p2p/message manipulation is required — only crafting a transaction (e.g., calling a CW20/721/1155 contract many times in a batched multi-message tx, or interacting with a contract designed to emit many mint/transfer/approval sub-events) that has more than ~300k gas worth of translation work but is well within normal Cosmos tx gas limits. This is reachable purely through the existing CW→EVM pointer/wasm bridge described in `x/evm/AGENTS.md`'s "Synthetic Receipts and Logs" section [9](#0-8) .

### Recommendation
Do not use a single fixed, on-chain-configurable-but-not-caller-scaled gas cap for the whole translation loop. Options: (1) scale the hook gas budget to the number of wasm events actually being translated (with a sane per-event minimum) rather than a single flat constant; (2) meter/skip individual events independently so a shortfall degrades gracefully (drop only the logs that don't fit) instead of risking a panic that can propagate past the point where wasm state changes were already committed; (3) ensure any out-of-gas panic in this hook is caught and treated as "no synthetic logs emitted" without affecting the already-committed CW execution result, and emit a clear diagnostic/metric so operators can raise `DeliverTxHookWasmGasLimit` via governance if legitimate contracts are being truncated.

### Proof of Concept
1. Deploy or use a CW20/CW721/CW1155 contract that is registered as a pointer-backed contract (`GetERC20CW20Pointer`/`GetERC721CW721Pointer`/`GetERC1155CW1155Pointer` returns `exists=true`).
2. Submit a single Cosmos tx (regular gas limit, e.g. 5,000,000) containing many `MsgExecuteContract` wasm messages against that contract (or a contract that internally loops and emits many `transfer`/`mint`/`approve` wasm events), such that the total wasm events exceed the number translatable within 300,000 gas of pointer lookups + log construction (+ optional `QuerySmart` calls for allowance events).
3. Observe: the underlying wasm state changes commit successfully (Cosmos tx succeeds), but `AddCosmosEventsToEVMReceiptIfApplicable`'s gas-limited loop either truncates/drops the tail of synthetic EVM logs or panics inside the hook — in both cases producing synthetic EVM receipt/log data inconsistent with the actual state change, exactly analogous to the reported VRF `_healRequestFulfilled` gas-exhaustion pattern where a fixed callback budget is exceeded by an attacker-sized loop with external calls.

### Synthetic Receipts and Logs
There are several types of synthetic receipts/logs on Sei.
