### Title
Missing-proof panic in `GeneratorPromotion::complete` enables a faulty DKG participant to crash honest nodes - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` iterates `1 ..= params.n()` and unconditionally `unwrap()`s `proofs.get(&i)` for every participant other than itself. The only prior validation is `proofs.len() == n - 1` and `u16::from(i) <= n` for each key. A faulty participant can therefore submit a `GeneratorProof` labeled under an already-covered `Participant` index (e.g. the receiver's own `params.i()`), keeping the map size at `n - 1` while leaving some participant `j` absent, causing `proofs.get(&j).unwrap()` to panic instead of returning `PromotionError`.

### Finding Description
The validation in `complete` checks quantity and upper bounds only:

```rust
// crypto/dkg/promote/src/lib.rs:125-136
if proofs.len() != (usize::from(params.n()) - 1) {
  Err(PromotionError::IncorrectAmountOfParticipants { ... })?;
}
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() {
    Err(PromotionError::InvalidParticipant { ... })?;
  }
}
```

The consuming loop then assumes complete coverage of `1..=n` minus `params.i()`:

```rust
// crypto/dkg/promote/src/lib.rs:140-146
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();   // panic if `i` was displaced
```

Because the checks never verify that the map keys form the exact set `{1..=n} \ {params.i()}`, a `proofs` map like `{params.i(), 2, .., n-1}` (participant `n` missing) passes both checks — it has `n - 1` entries and every key `<= n` — then panics at `proofs.get(&n).unwrap()`. The rest of the crate family (PedPoP, FROST `sign`/`complete`) deliberately returns structured errors (`PedPoPError::InvalidShare`, `FrostError::DuplicatedParticipant`, `MissingParticipant`, `InvalidProof`) for exactly this class of faulty-participant input, so the panic is an unhandled fault path rather than a documented abort.

### Impact Explanation
This is the direct analog of CVE-2025-55521: a crafted message from an authenticated protocol participant causes a denial of service. During generator promotion (used to rotate `ThresholdKeys` to a new generator without re-running the full DKG), one faulty participant's mislabeled `GeneratorProof` crashes every honest node's `complete` call. Promotion is a `params.n() - 1`-of-`n` completion step, so a single fault halts the rotation for the entire set — and if the panic is not caught at the caller, it takes down the whole processor, blocking all pending signing and scanning work, not just the promotion.

### Likelihood Explanation
Reachability requires only that the attacker be one of the `n` threshold participants and send a `GeneratorProof` whose map key is a duplicate `Participant` instead of their own index — this is precisely the adversary model the DKG crates are built to handle via blame/error paths elsewhere (`ThresholdKeys::new` returns `DkgError::InvalidParticipant`/`IncorrectAmountOfVerificationShares` rather than panicking). No collusion, no broken BFT, and no leaked keys are required; one faulty participant with valid signature material for their (mislabeled) proof suffices.

### Recommendation
Replace the unconditional `proofs.get(&i).unwrap()` with checked coverage: before consuming, verify that `proofs.keys()` equals the exact expected set `{Participant(1) ..= Participant(n)} \ {params.i()}` (e.g. iterate `1..=n`, skip `params.i()`, and return `PromotionError::InvalidParticipant { n, participant: i }` or a new `MissingParticipant` variant when `proofs.get(&i)` is `None`). Also reject `proofs` maps that contain `params.i()` as a key. This mirrors the dedup/coverage checks in `ThresholdKeys::view` (`DuplicatedParticipant`, `NotParticipating`) and `validate_map` in `crypto/frost/src/lib.rs`.

### Proof of Concept
```rust
use std::collections::HashMap;
use rand_core::OsRng;
use dalek_ff_group::Ristretto;
use ciphersuite::Ciphersuite;
use dkg::{Participant, ThresholdParams, ThresholdKeys, Interpolation};
use dkg_promote::GeneratorPromotion;

// Setup: n-of-n keys (n = 3), we are participant 1.
// Build a proofs map with n-1 = 2 entries keyed {1, 2} — participant 3 is
// displaced by a proof filed under our own index (params.i()).
let mut proofs: HashMap<Participant, GeneratorProof<Ristretto>> = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), proof_from_malicious); // should be rejected: it's our own index
proofs.insert(Participant::new(2).unwrap(), proof_from_p2);
// participant 3 absent — but proofs.len() == n - 1 and all keys <= n, so both
// checks at lib.rs:125-136 pass.

// Panics at crypto/dkg/promote/src/lib.rs:146:
//   `proofs.get(&Participant(3)).unwrap()` -> None.unwrap()
let _ = promotion.complete(&proofs);
```

The panic occurs inside `complete` before any proof verification, so no valid `GeneratorProof` forgery is needed — the attacker only needs the coordinator to file their proof under the wrong `Participant` key, or to include a self-addressed proof, which the current validation does not exclude.
