### Title
Missing `chainId` in EIP-712 Domain Enables Cross-Network Replay of Aggregator Withdrawal Authorization Signatures - (File: `core/src/rpc/ecdsa_verification_sig.rs`)

### Summary

The `CLEMENTINE_EIP712_DOMAIN` used to sign and verify aggregator authorization signatures for optimistic payout and operator withdrawal flows omits the `chain_id` field. A signature produced for one Citrea network deployment (e.g., testnet4, chain ID 5655) is cryptographically valid on any other deployment sharing the same `aggregator_verification_address` key, because the domain hash does not bind the signature to a specific chain.

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

The EIP-712 standard explicitly includes `chainId` as a domain separator field to prevent cross-chain replay. Here, neither `chain_id` nor `verifying_contract` is present. The domain hash is therefore identical across all Citrea network deployments.

This domain is used in `recover_address_from_ecdsa_signature` to verify both `OptimisticPayoutMessage` and `OperatorWithdrawalMessage`:

```rust
let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);
let address = signature.recover_address_from_prehash(&eip712_hash)...;
``` [2](#0-1) 

This function is called in two production paths:

1. **Verifier optimistic payout** (`Verifier::sign_optimistic_payout`): recovers the signer address and compares it to `aggregator_verification_address` in config. [3](#0-2) 

2. **Operator withdrawal** (`ClementineOperator::withdraw` RPC): same recovery and comparison. [4](#0-3) 

The `aggregator_verification_address` is an `Option<Address>` in `BridgeConfig`. When `Some`, the signature check is enforced; when `None`, the check is skipped entirely. [5](#0-4) 

Clementine is deployed on multiple networks. The `.env.example` and docker configs show `CITREA_CHAIN_ID=5655` (testnet) and `62298` (regtest), and the `BatchProofMethodIdBody` in the tx-sender crate explicitly includes `chain_id` to prevent cross-network replay — demonstrating the project is aware of this class of issue in other contexts:

```rust
pub chain_id: u64,  // Network identifier to prevent cross network replay attacks
``` [6](#0-5) 

### Impact Explanation

When `aggregator_verification_address` is configured, the verification signature is the sole authorization gate controlling which withdrawals operators and verifiers will process. Without `chainId` in the domain:

- A signature produced by the aggregator key for a withdrawal on testnet (chain ID 5655) is cryptographically identical to a signature for the same withdrawal parameters on mainnet.
- An attacker who obtains a valid testnet aggregator signature can submit it to mainnet operators/verifiers. The `recover_address_from_prehash` call will return the same address, passing the authorization check.

**Partial mitigation present**: The verifier's `sign_optimistic_payout` also checks that `withdrawal_utxo == input_outpoint` against its database, and that the UTXO is unspent. Since Bitcoin UTXOs are network-specific, a testnet outpoint is unlikely to match a mainnet DB entry. This makes cross-network exploitation difficult in practice but not impossible (e.g., if the same txid appears on both networks, or if the attacker controls deposit flow).

The operator's `withdraw` path has no equivalent UTXO binding check before calling `operator.withdraw`, making it the more exposed surface. [7](#0-6) 

### Likelihood Explanation

- Requires `aggregator_verification_address` to be configured (opt-in feature).
- Requires the same aggregator key to be used across multiple network deployments.
- Cross-network replay is partially blocked by Bitcoin UTXO binding in the verifier path, but not in the operator path.
- The `withdrawal_id` is a sequential integer that will collide across deployments.

### Recommendation

Add `chain_id` to `CLEMENTINE_EIP712_DOMAIN`, sourced from `BridgeConfig::citrea_chain_id`:

```rust
pub fn clementine_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Pass the domain dynamically to `recover_address_from_ecdsa_signature` and `eip712_signing_hash` calls, using the configured `citrea_chain_id`. This matches the pattern already used in `BatchProofMethodIdBody`.

### Proof of Concept

1. Aggregator signs an `OptimisticPayoutMessage` for testnet (chain ID 5655) with `withdrawal_id=1`, `input_outpoint=<testnet_utxo>`, `output_amount=X`.
2. Attacker captures this signature.
3. Attacker submits the same parameters + signature to a mainnet operator's `withdraw` RPC.
4. Mainnet operator calls `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>(...)` with `CLEMENTINE_EIP712_DOMAIN` (no chain ID).
5. The recovered address matches `aggregator_verification_address` (same key, same domain hash).
6. Authorization check passes; operator proceeds to execute the withdrawal payout on mainnet. [1](#0-0) [8](#0-7) [9](#0-8)

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
