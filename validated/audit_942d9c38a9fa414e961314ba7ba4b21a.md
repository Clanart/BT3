### Title
Untrusted `ThresholdKeys` deserialization accepts attacker-controlled verification shares, yielding a group key with a known discrete logarithm - (crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation table, the secret share, and all `n` verification shares from a byte stream, then calls `ThresholdKeys::new`, which derives the group key purely as the interpolated sum of the *deserialized* verification shares for participants `1..=t`. No check verifies that the group key is non-identity, that any verification share is non-identity, or that `G * secret_share == verification_shares[i]`. An attacker who supplies the serialized bytes therefore fully controls the resulting `group_key` and can set it to a point whose discrete log they know.

### Finding Description
The analog to "RCE via vulnerable API" — attacker-supplied input reaching a security-critical sink without validation — is attacker-supplied bytes reaching `ThresholdKeys::read`.

Two compounding issues:

1. `ThresholdKeys::read` reads verification shares via `<C as Ciphersuite>::read_G` [1](#0-0) , which only enforces canonical encoding — it does **not** reject the identity point [2](#0-1) . Contrast with `Curve::read_G` in FROST, which explicitly rejects identity [3](#0-2) . For Ristretto/dalek-ff-group, the identity element has a valid canonical encoding (all zeros), so it deserializes cleanly.

2. `ThresholdKeys::new` computes `group_key` as `Σ verification_shares[i] * interpolation_factor(i, 1..=t)` [4](#0-3)  and stores it without any consistency check — it never verifies `group_key != identity`, never checks `C::generator() * secret_share == verification_shares[i]`, and never validates that the shares form a coherent polynomial. The codebase itself acknowledges this gap: `AlgorithmSignatureMachine::complete` comments that "the only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" [5](#0-4) .

Because the shares are fully attacker-chosen points, the attacker can set e.g. `verification_shares[1] = G * k` (for Lagrange with `t = 1` interpolation factors of 1, or by solving the linear system) so that `group_key = G * k` with `k` known, or set all shares to identity so `group_key = identity` (since `scalar = ONE`, `offset = ZERO` on a fresh read [6](#0-5) ).

### Impact Explanation
- **Forged signatures**: if `group_key = G * k` with attacker-known `k`, the attacker produces valid Schnorr signatures for the "multisig" key alone. If `group_key = identity`, signatures verify trivially for anyone (`R + c·A − sG = rG − rG = 0` with `A = identity`), per `SchnorrSignature::verify` / `batch_statements` [7](#0-6) .
- **Funds reported received that are not spendable / stealable**: downstream networks (e.g., bitcoin-serai, Monero-style outputs over Ristretto/dalek-ff-group) derive output keys from `group_key()`. Outputs addressed to an attacker-controlled or identity group key are spendable by the attacker/anyone, not by the honest threshold.

### Likelihood Explanation
Reachability is limited to contexts where serialized `ThresholdKeys` come from an untrusted source (key restore/import, backups, network-provided blobs) — the prompt's stated threat model explicitly includes untrusted bytes fed to `ThresholdKeys::read`. Exploitation requires no computation beyond choosing the verification-share points; canonical encoding is trivially satisfied. Severity is bounded by the delivery requirement — this cannot be triggered purely by DKG protocol messages, since `calculate_share`/`BlameMachine` construct `ThresholdKeys` from verified commitments rather than a raw blob.

### Recommendation
In `ThresholdKeys::new` (and thereby `ThresholdKeys::read`):
- Reject identity verification shares (read via an identity-rejecting point reader, mirroring `Curve::read_G`).
- Check `group_key != identity`.
- Check `C::generator() * secret_share == verification_shares[&params.i()]` for `Interpolation::Lagrange`-consistent shares, or at minimum document that `read` output must be treated as untrusted until cross-checked against an externally committed group key.

### Proof of Concept
Conceptual (Ristretto, `t = n = 2`, `i = 1`, `Interpolation::Lagrange`):
1. Build a serialization: `C::ID` len+ID, `t=2, n=2, i=1`, interpolation byte `1`, an arbitrary canonical `secret_share` scalar.
2. For the two verification shares, encode `V1 = identity` (32 zero bytes for Ristretto) and `V2 = G * k_attacker` where `k_attacker` is a known scalar.
3. `ThresholdKeys::read` succeeds; `group_key = V1·λ1 + V2·λ2`. With Lagrange over `{1,2}`, `λ1 = 2`, `λ2 = -1`, so `group_key = -k_attacker·G` — a key whose discrete log (`-k_attacker`) the attacker knows.
4. The attacker signs arbitrary messages for `group_key` unilaterally; any funds or authorizations bound to the deserialized multisig key are compromised. Alternatively, setting both shares to identity yields `group_key = identity`, for which anyone can produce a verifying `SchnorrSignature { R: r·G, s: r }`.

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
  }
