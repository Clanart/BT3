## Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-shop webhook forgery - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` authenticates a webhook request solely by validating an HMAC over the raw request body, then exposes a separate `shop_domain` helper that reads the tenant identifier straight from the `X-Shopify-Shop-Domain` header — a value that is never included in the HMAC computation. Any app built on this gem's documented custom-webhook pattern binds business logic (e.g. background jobs) to that unverified header value, so a party who can obtain one validly-signed webhook body/HMAC pair (e.g. by installing the app on their own shop and receiving a real webhook) can replay it against the shared webhook endpoint with a forged `X-Shopify-Shop-Domain` header and have it accepted as belonging to a different shop.

### Finding Description
`PayloadVerification#hmac_valid?` computes/validates the signature only over `request.raw_post`: [1](#0-0) 

`WebhookVerification#verify_request` gates the action solely on that body HMAC, and separately exposes `shop_domain`, read verbatim from the `X-Shopify-Shop-Domain` header, with no cryptographic binding to the verified body: [2](#0-1) 

The gem's own documentation instructs developers building custom webhook controllers to use exactly this unverified `shop_domain` for tenant-scoped side effects, such as enqueuing a shop-scoped job: [3](#0-2) 

Because the app's webhook secret (`ShopifyApp.configuration.secret`) is a single per-app secret shared across every shop that installs the app (not a per-shop secret), any merchant/attacker who installs the app on their own store will receive genuinely-signed webhooks (valid body + valid `X-Shopify-Hmac-Sha256`) from Shopify for their own shop's events. Since the `X-Shopify-Shop-Domain` header is not part of the signed payload, the attacker can resend that same body/HMAC pair to the shared webhook endpoint while substituting an arbitrary victim shop domain in the header. `verify_request` still passes because the body and HMAC match, and the downstream code (as documented) trusts `shop_domain` to route the payload to the victim shop's processing pipeline.

This is structurally the same defect class as the reported `RootValidator::onInstall` bug: a caller-influenced, unauthenticated value (`_data`'s address bytes / the `X-Shopify-Shop-Domain` header) is trusted to establish a critical binding (validator-to-account / webhook-to-shop) without verifying it is actually tied to the authenticated principal (`msg.sender` / the HMAC-verified payload).

### Impact Explanation
An attacker-controlled shop can inject forged webhook data attributed to a victim shop into any custom webhook controller built per the gem's documented pattern — e.g. queuing jobs, updating shop-scoped records, or triggering business logic (billing state changes, order/cart processing) under the victim's `shop_domain`. This is a cross-shop data-integrity/confusion vulnerability enabled by an accepted forged signed request, matching the required "cross-shop access" / "accepted forged signed request" impact class.

### Likelihood Explanation
Reachable by any unrelated party who can install the target app on their own development/trial store (a normal, unprivileged action), capture one legitimate webhook, and replay it with a modified header to the app's single shared webhook endpoint. No secret leakage or host-operator access is required — only the documented, expected capabilities of an app-installing merchant.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` (or any other header/param not covered by the HMAC) as a trusted tenant identifier. Instead:
- Derive the shop from the HMAC-verified payload itself (most Shopify webhook bodies embed shop-identifying fields), or
- Bind the header value into the HMAC computation before trusting it, or
- Follow the same pattern used by `ShopifyAPI::Webhooks::Registry.process`/`ShopifyAPI::Webhooks::Request`, which is the gem's built-in, already-safer default path, and update `docs/shopify_app/webhooks.md` to stop recommending the unverified `shop_domain` helper for tenant-scoped side effects.

### Proof of Concept
1. Attacker registers/installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook (e.g. `carts/update`) to the app's shared endpoint, with body `B`, header `X-Shopify-Hmac-Sha256: H` (valid, computed with the app's shared secret) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the exact same request to the same endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which passes because `B` and `H` still match: [4](#0-3) 
5. The custom controller (per documented pattern) calls `shop_domain`, which returns `"victim.myshopify.com"` from the forged header, and enqueues `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)` — processing attacker-supplied data as if it belonged to the victim shop.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
