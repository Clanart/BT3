## Analysis

The Monero report's broken invariant is: **a tool that is trusted to "show what will actually happen" can be made to display something benign while the real state differs**, and the victim acts (credits a balance / commits code) based on the misleading display. The closest Desktop analog is the **Trojan Source / hidden bidirectional-Unicode** class: Desktop already has a mitigation (`HiddenBidiCharsRegex` + `DiffContentsWarning`) but that mitigation is *not evaluated on the path a user actually takes when committing/pushing a large diff*, because large diffs are hidden behind an optional "Show Diff" click while the Commit/Push actions remain fully enabled regardless.

### Title
Hidden bidirectional-Unicode ("Trojan Source") warning is silently bypassed for large diffs, allowing a malicious file to be committed/pushed without detection - (File: `app/src/lib/git/diff.ts`, `app/src/ui/diff/index.tsx`)

### Summary
Desktop parses every diff and computes `hasHiddenBidiChars` via `HiddenBidiCharsRegex` to warn users when a diff contains invisible bidi-override characters that can make code appear different from what it actually is [1](#0-0) . This flag is surfaced to the user only through the `DiffContentsWarning` component, which is rendered as part of the full text-diff view [2](#0-1) . However, when a diff/buffer exceeds `MaxReasonableDiffSize` (~4.375MB) or contains a line longer than `MaxCharactersPerLine` (5000 chars), it is classified as `DiffType.LargeText` and Desktop shows a collapsed placeholder instead of the diff, requiring the user to click "Show Diff" before the warning (or any diff content) is rendered [3](#0-2) . If the buffer exceeds the hard `MaxDiffBufferSize` (70MB) it becomes `DiffType.Unrenderable` and no diff or warning is ever produced at all [4](#0-3) .

### Finding Description
The staging/commit machinery in `stageFiles`/`applyPatchToIndex` does not depend on the diff having been viewed - files can be fully staged and committed regardless of whether the user expanded the large-diff view [5](#0-4) . The bidi-character warning is purely a UI affordance gated behind `ITextDiff`/`ILargeTextDiff` rendering (`renderTextDiff` / `renderLargeText`), not a blocking check anywhere in the commit or push pipeline [6](#0-5) .

An attacker who controls a cloned/fetched repository (e.g., a dependency, template, or PR branch a developer pulls down) can craft a file that:
1. Contains Trojan-Source-style hidden bidi override characters (`\u202A-\u202E`, `\u2066-\u2069`) that make the rendered code look benign/harmless while the actual bytes execute differently, and
2. Is padded (long lines beyond 5000 chars, or overall diff size beyond ~4.375MB) so the diff is classified as `LargeText` by default.

Because `MaxCharactersPerLine`/`MaxReasonableDiffSize` checks look only at *raw diff/line size*, not at whether bidi characters are present, an attacker can make an otherwise small malicious change appear large purely by injecting a long unrelated line/comment, forcing Desktop into the collapsed `renderLargeTextDiff` path where the hidden-bidi warning is never shown to the user unless they proactively click "Show Diff" [7](#0-6) [8](#0-7) . The user can then stage and commit/push the file exactly as-is, silently corrupting what they believe they committed.

### Impact Explanation
This allows an attacker-controlled repository/branch to smuggle Trojan-Source-style code into a victim's commit history via GitHub Desktop's normal commit/push flow, with the victim never having been shown the warning that would normally flag the danger. The result is silent corruption of what the user commits/pushes - matching the "silent corruption" impact category - and can lead to supply-chain compromise if the victim is a maintainer merging PRs reviewed only through Desktop's diff viewer.

### Likelihood Explanation
Moderate. It requires the attacker to control the content of a file the victim diffs/commits (e.g., a PR branch, a vendored dependency, or a file the victim edits after copy-pasting attacker content) and to pad the diff enough to cross the ~4.375MB/5000-char thresholds - both attacker-controlled and easy to achieve deliberately. It does not require local access, admin rights, or social engineering beyond the victim performing an ordinary "review PR / commit / push" workflow in Desktop.

### Recommendation
- Compute `hasHiddenBidiChars` independently of the `LargeText`/`Unrenderable` classification and surface a warning banner even when the diff body itself is collapsed or unrenderable (i.e., don't gate the warning behind the "Show Diff" click).
- Consider blocking or requiring explicit confirmation before committing/pushing files whose diff contains hidden bidi characters, rather than relying solely on a passive banner inside an optional expanded view.

### Proof of Concept
1. Attacker creates/modifies a file in a repository with a line containing Unicode bidi-override characters (e.g., `\u202E`) that reorders displayed characters to hide malicious logic, per the Trojan Source technique referenced in `HiddenBidiCharsRegex`'s own comment [1](#0-0) .
2. Attacker pads the same file/diff so a line exceeds 5000 characters or the whole diff exceeds ~4.375MB (e.g., appending a very long comment or blank-padded string), forcing `isDiffTooLarge`/`isBufferTooLarge` to classify it as `DiffType.LargeText` [9](#0-8) .
3. Victim pulls/reviews the branch in GitHub Desktop; the Changes/History view shows the collapsed "The diff is too large to be displayed by default" panel with a "Show Diff" button, and no bidi warning is shown [3](#0-2) .
4. Victim commits and pushes without clicking "Show Diff" (a very common action for large/generated-looking files), and `DiffContentsWarning` is never rendered because it only exists inside `renderTextDiff` [2](#0-1) .
5. The Trojan-Source file is committed/pushed with no in-app indication of the hidden bidi manipulation.

**Confidence note:** I confirmed the size thresholds (`MaxReasonableDiffSize`, `MaxCharactersPerLine`, `MaxDiffBufferSize`) and the gating of `DiffContentsWarning` inside `renderTextDiff`/`renderLargeText` from the indexed source, but did not have access to the full `side-by-side-diff.tsx` render tree to verify there is no secondary/independent bidi-warning surfaced elsewhere in the collapsed state (e.g., in a toast or file-list badge). If such a secondary indicator exists, it would reduce the severity of this finding; a full-repo Devin session could verify this exhaustively.

/** Is the diff too large for us to reasonably represent? */
function isDiffTooLarge(diff: IRawDiff) {
  for (const hunk of diff.hunks) {
    for (const line of hunk.lines) {
      if (line.text.length > MaxCharactersPerLine) {
        return true
      }
    }
  }

  return false
}

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }
