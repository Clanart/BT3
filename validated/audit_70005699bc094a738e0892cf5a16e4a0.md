### Title
Uncontrolled Resource Consumption when parsing an untrusted offer via `Offer._get_offered_coins()` - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer._get_offered_coins()` executes the inner puzzle of every coin spend in an offer with `cost_left = INFINITE_COST` [1](#0-0) , i.e. with no CLVM cost limit at all, in contrast to every other CLVM-execution path in the codebase (mempool admission, block validation, `Offer.__post_init__`/`conditions()`, `compute_additions_with_cost`, `compute_spend_hints_and_additions`) which all bound execution to `MAX_BLOCK_COST_CLVM` or `max_tx_clvm_cost` [2](#0-1) [3](#0-2) [4](#0-3) . This mirrors the class of bug in CVE-2022-24839 (nekohtml): attacker-controlled input reaching a parsing/execution routine that has no resource ceiling, allowing unbounded CPU/memory consumption from a single malicious input.

### Finding Description
An `Offer` object is built directly from untrusted, counterparty- or file-supplied bytes (`Offer.from_bech32`/`from_bytes`, taken from an `.offer` file or a bech32m string a wallet user pastes in). Its `puzzle_reveal`/`solution` for each coin spend are fully attacker-controlled CLVM programs. When a wallet inspects such an offer — e.g. to compute offered amounts/pending amounts for display, via `get_offered_amounts()`/`get_pending_amounts()` which internally rely on `_get_offered_coins()` [5](#0-4)  — the code runs:

```
cost_left = INFINITE_COST
...
puzzle_cost, conditions = inner_puzzle.run_with_cost(cost_left, inner_solution)
``` [1](#0-0) 

`INFINITE_COST` disables the cost meter entirely for this execution, unlike the bounded `run_with_cost(cs.puzzle_reveal, max_cost, cs.solution)` calls used elsewhere in the same file (`__post_init__`, `conditions()`) that decrement a `max_cost` initialized from `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM` and raise `ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, ...)` when exceeded [2](#0-1) [6](#0-5) . Because CLVM allows exponential blow-up via nested `concat`/recursive constructs (the same technique used in the repository's own "malicious generator program" regression tests, `SINGLE_ARG_INT_COND`/`SINGLE_ARG_INT_SUBSTR_COND`, which were specifically crafted to exhaust CPU/memory and are only rejected today because of the cost limit enforced during mempool/block validation) [7](#0-6) , an attacker can construct a single offer whose "inner puzzle" recurses/duplicates data similarly, but because `_get_offered_coins()` runs it with `INFINITE_COST`, none of the cost-based defenses that protect the mempool and block-validation paths apply here.

### Impact Explanation
A malicious offer counterparty (or anyone who gets a wallet user to load a crafted `.offer` file/bech32m string, e.g. via a trade marketplace, DM, or `get_offer_summary`/`take_offer` preview UI) can cause the recipient's wallet process to consume unbounded CPU and memory while evaluating `_get_offered_coins()`, hanging or crashing the wallet (and potentially the machine, given CLVM's ability to blow up memory via repeated `concat`), before the user ever decides whether to accept the trade. This is a spend/offer-triggered resource-consumption halt of the wallet's transaction-processing path, reachable by an unprivileged offer counterparty with no signature or on-chain broadcast required — the offer only needs to be shown/summarized locally.

### Likelihood Explanation
Likelihood is high for wallet operators who preview offers before accepting them (a normal, expected workflow — `get_offer_summary`, `check_offer_validity`, CLI/GUI offer previews all eventually touch offer amount computations). Building the malicious puzzle reveal requires only chialisp knowledge, no special access, no valid coin ownership, and no network broadcast — an offer file is a self-contained, unsigned-until-accepted artifact that can be freely crafted and shared. However, I could not fully trace at this iteration limit which specific RPC entry points (`get_offer_summary`, `check_offer_validity`, CLI commands) invoke `get_offered_amounts()`/`get_pending_amounts()`/`_get_offered_coins()` versus only `summary()`; that mapping should be confirmed with a live Devin session before treating this as fully proven end-to-end from RPC input to the vulnerable call.

### Recommendation
Replace `cost_left = INFINITE_COST` in `Offer._get_offered_coins()` with a bounded cost budget (e.g. `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`, consistent with `__post_init__` and `conditions()`), decrement it per spend, and raise/propagate a `ValidationError`/catch when exceeded instead of letting execution run unbounded. Audit all other `run`/`run_with_cost`/`uncurry` calls in wallet-side code that process untrusted offer/puzzle-reveal data (e.g. `outer_puzzles.py`, `uncurry_nft.py`, `puzzle_drivers.py`) for similarly unbounded execution.

### Proof of Concept
1. Craft a `WalletSpendBundle` whose single `CoinSpend`'s `puzzle_reveal` matches one of the outer-puzzle drivers recognized by `match_puzzle()` (e.g. a CAT/singleton outer puzzle) so that `get_inner_puzzle`/`get_inner_solution` in `_get_offered_coins()` successfully extract an `inner_puzzle`/`inner_solution`.
2. Make the extracted `inner_puzzle` a chialisp program analogous to the repo's own `SINGLE_ARG_INT_SUBSTR_COND`/`SINGLE_ARG_INT_COND` test payloads [7](#0-6)  — i.e. one that repeatedly `concat`s a buffer against itself to blow up exponentially — with a large iteration count `B`.
3. Wrap this into a syntactically valid `Offer` (`Offer(requested_payments, spend_bundle, driver_dict)`) and serialize it with `Offer.to_bech32()`.
4. Have a victim wallet call any code path that reaches `_get_offered_coins()` (e.g. `offer.get_offered_amounts()` / `offer.get_pending_amounts()`), such as previewing/summarizing the received offer.
5. Observe `inner_puzzle.run_with_cost(INFINITE_COST, inner_solution)` execute without any cost ceiling, consuming excessive CPU/memory and hanging or crashing the wallet process — unlike the mempool/block-validation paths, which reject the same payload shape once cost exceeds `MAX_BLOCK_COST_CLVM`.
