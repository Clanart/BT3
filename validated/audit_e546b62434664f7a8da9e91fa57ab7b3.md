### Title
Reward accounting overwrite instead of accumulation for shared CL pool addresses in `assignStakingRewards`/`assignStakingRewardsFlex` - (File: kaiax/reward/impl/getter.go)

### Summary
The Gondi `Pool.sol` bug (`_pendingWithdrawal[secondIdx] = pendingForQueue` instead of `+=`) is a case of a loop writing computed per-iteration values into a map/array keyed by an address/index that is not guaranteed unique, silently discarding a prior iteration's accumulated value. The same code pattern — `alloc[addr] = amount` inside a `for _, cn := range cns` loop, rather than accumulating — exists in Kaia's reward module's consensus-liquidity (CL) reward-splitting logic.

### Finding Description
In `assignStakingRewards` and `assignStakingRewardsFlex` (`kaiax/reward/impl/getter.go`), staking rewards are distributed to consolidated nodes (`cn`) by iterating over `cns := si.ConsolidatedNodes()` and writing directly into a `map[common.Address]*big.Int` keyed by address: [1](#0-0) 

and [2](#0-1) 

`ConsolidatedNodes()` guarantees `cn.RewardAddr` is unique per entry in `cns` (nodes sharing a `RewardAddr` are merged into a single `consolidatedNode`), so `alloc[cn.RewardAddr] = ...` is safe by construction: [3](#0-2) 

However, the `CLStakingInfo.CLPoolAddr` field attached to each consolidated node comes from an entirely separate data source — the external `CLRegistry` contract, queried via `MultiCallDPStakingInfo`/`clRegistryResult` — and is only asserted unique per `CLNodeId` ("One CLStakingInfo per validator is guaranteed by CLRegistry"), **not** unique per `CLPoolAddr`: [4](#0-3) [5](#0-4) 

If the CL registry ever returns two different validators (i.e., two `consolidatedNode`s with distinct `RewardAddr`) whose `CLStakingInfo.CLPoolAddr` is the same address (e.g. a shared/misconfigured liquid-staking pool contract, or multiple node operators pointed at one pool), the second loop iteration's `alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount` overwrites the first iteration's allocation instead of accumulating it — exactly the `=` vs `+=` bug from the referenced report. The overwritten `remaining` bookkeeping already subtracted both amounts from the budget, so the lost portion is never credited to any address in `FinalizeState`'s balance-crediting loop: [6](#0-5) 

### Impact Explanation
This is squarely in the "staking and reward distribution" bug class explicitly in scope. If triggered, minted staking-reward tokens computed as owed to a CL pool are silently dropped rather than credited to any address on `FinalizeState`, causing incorrect reward accounting/loss of funds every block this condition holds (deterministically, on every honest node, since it's part of consensus state transition — so it wouldn't cause a chain split, but it does cause systematic, silent fund loss/incorrect token distribution across the network, understating validator/CL staker rewards).

### Likelihood Explanation
Likelihood is **not established with certainty** from the available code: the collision requires the external `CLRegistry` system contract to return two entries with distinct `CLNodeId`/`RewardAddr` but identical `CLPoolAddr`. I could not find in-repo enforcement (in `kaiax/staking` or `kaiax/reward`) of `CLPoolAddr` uniqueness across different validators, and the real `CLRegistry` contract's registration logic is not included in this repo (only mocks such as `CLRegistryMockThreeCL.sol` are present), so I cannot confirm whether CL pool registration is permissionless/staker-controlled or admin/operator-gated. This is a genuine gap in the reviewed code's defensive checks (no uniqueness assertion on `CLPoolAddr` before the `alloc[...] = ...` overwrite), but whether it is reachable by an ordinary staker submitting a registration versus only by a privileged CLRegistry operator could not be verified with the indexed content.

### Recommendation
- Add an explicit sanity check that no two `consolidatedNode` entries share the same `CLStakingInfo.CLPoolAddr` (or `RewardAddr` colliding with a `CLPoolAddr`), and return an error (as is already done for other malformed `clRegistryResult` shapes) if violated, rather than silently overwriting.
- Alternatively, change `alloc[cn.RewardAddr] = cnAmount` / `alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount` to accumulate (`+=` via `new(big.Int).Add`) so that even if a collision occurs, no funds are lost.

### Proof of Concept
1. Two AddressBook entries produce two distinct `consolidatedNode`s `CN1{RewardAddr: R1, CLStakingInfo:{CLPoolAddr: P}}` and `CN2{RewardAddr: R2, CLStakingInfo:{CLPoolAddr: P}}` (same `P`), which is possible if the `CLRegistry` multicall result associates the same pool address with two different `CLNodeId`s (see `parseCallResult`/`parsePermissionlessCallResult`, `kaiax/staking/impl/getter.go:290-302`).
2. During `FinalizeState`, `getDeferredRewardFullKore`/`getDeferredRewardFullFlex` calls `assignStakingRewards`/`assignStakingRewardsFlex`, iterating `cns` and computing `clAmount` for each.
3. For `CN1`, `alloc[P] = clAmount1` is set; `remaining` is decremented by `clAmount1`.
4. For `CN2`, `alloc[P] = clAmount2` **overwrites** the entry; `remaining` is decremented by `clAmount2` as well.
5. Final `alloc[P]` only reflects `clAmount2`; `clAmount1` (owed to pool `P` on behalf of `CN1`'s validator) is never added to `spec.Rewards`/never credited via `state.AddBalance` in `blockstate.go:53-55`, so it is permanently lost from circulation despite having been subtracted from the reward budget.

func (si *StakingInfo) consolidateNodes() *[]consolidatedNode {
	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))
	nToR := make(map[common.Address]common.Address)

	for i, n := range si.NodeIds {
		r := si.RewardAddrs[i]
		// Unique nodeId is guaranteed by AddressBook.
		nToR[n] = r
		if cn, ok := cmap[r]; ok {
			cn.NodeIds = append(cn.NodeIds, n)
			cn.StakingContracts = append(cn.StakingContracts, si.StakingContracts[i])
			cn.StakingAmount += si.StakingAmounts[i]
		} else {
			cmap[r] = &consolidatedNode{
				NodeIds:          []common.Address{n},
				StakingContracts: []common.Address{si.StakingContracts[i]},
				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}
