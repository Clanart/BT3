## Title
IntentGatewayV2 (Tron fork) escrows the requested input amount instead of the actual tokens received, allowing fee-on-transfer/deflationary tokens to create an escrow-accounting overstatement that drains other orders' pooled funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`AaveV3HoldingsOracle.getOracleData()` computed `maxExternalDeposit` from `supplyCap - aTokenSupply` without subtracting `reserve.accruedToTreasury`, so the tracked "available" value diverged from what AAVE's own `ValidationLogic` actually enforced. The same class of bug — an internal accounting value computed from a *requested/nominal* amount instead of the *actually received/held* amount — exists in the Tron fork of `IntentGatewayV2.placeOrder()`. The canonical EVM contract was hardened to measure actual token balance deltas for exactly this reason (fee-on-transfer tokens), but the Tron fork was not updated to match, leaving `_orders[commitment][token]` (the escrow ledger that later pays out solvers/fillers and refunds) inflated relative to the gateway's real token balance.

### Finding Description
In the canonical EVM `IntentGatewayV2.sol`, `placeOrder()` explicitly snapshots the gateway's balance before and after `safeTransferFrom`, and overwrites `order.inputs[i].amount` with the measured delta so that escrow accounting always matches what the contract actually holds: [1](#0-0) 

That measured, real amount is what `reducedInputs`/the commitment/escrow are subsequently built from: [2](#0-1) 

The project's own test suite documents why this matters — fee-on-transfer and double-taxed (predispatch) tokens must have the escrow reflect the *actual received* amount, not the nominal one: [3](#0-2) 

The Tron fork at `evm/tron/contracts/apps/IntentGatewayV2.sol` reimplements the same flow but drops the balance-delta measurement. It computes `reducedInputs` (protocol-fee-reduced) directly from the caller-supplied `order.inputs[i].amount`, calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` for that same nominal amount, and then credits the escrow ledger with the fee-reduced *nominal* amount — never checking what the gateway's balance actually increased by: [4](#0-3) 

The predispatch branch has the same gap: it computes `dust = balance - requiredAmount` (checking for *surplus*) but still unconditionally books `reducedInputs[i].amount` into escrow regardless of whether `balance` (what the dispatcher actually forwarded) was less than `requiredAmount` would imply after fees: [5](#0-4) 

`_orders[commitment][token]` is a shared claim against the gateway's single pooled token balance across *every* outstanding order for that token — exactly like AAVE's shared reserve accounting. Any token with a transfer fee, rebase, or non-standard `transferFrom` behavior (common on Tron's TRC20 ecosystem and increasingly common generally) will cause the gateway to receive strictly less than `order.inputs[i].amount`, while `_orders[commitment][token]` still records the fee-reduced *nominal* value. This is the same "invariant broken by an unaccounted deduction" pattern as M-11: the contract's internal ledger overstates what it actually custodies.

### Impact Explanation
Because escrow is a shared per-token pool (not a per-order isolated balance), when a solver later redeems escrow (`RedeemEscrow`) or a user cancels and reclaims, the payout is sized from the inflated `_orders[commitment][token]` value rather than the token the gateway actually received for that specific order. Since the ledger total across all orders can now exceed the gateway's real balance for that token, later redemptions/cancellations/fills — belonging to *other, unrelated* users' orders — can fail to be honored or can be paid out of tokens that were actually escrowed by a different order, i.e., cross-order fund loss/insolvency of the pool. This matches "stealing or loss of funds" / "transaction manipulation" in the required impact set: an unprivileged user can place an order with a fee-on-transfer token to under-fund the shared pool while still minting a full-value escrow claim, degrading or misappropriating the pool that legitimately belongs to other users' orders.

### Likelihood Explanation
No malicious relayer, prover, or admin is required — a single unprivileged user placing an order with any deflationary/fee-on-transfer ERC-20/TRC-20 (or a token with non-1:1 `transferFrom` semantics) triggers the mismatch deterministically. The bug is a straightforward code-parity regression from the (patched) canonical EVM contract, and the codebase's own tests prove this exact class of token is treated as a first-class concern that the Tron fork fails to reproduce.

### Recommendation
Mirror the canonical EVM implementation in the Tron fork: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom`/dispatcher sweep, use the delta as the "actual received" amount for the corresponding `order.inputs[i].amount`, and compute `reducedInputs`/commitment/escrow credit from that measured value rather than the caller-supplied nominal amount, exactly as done in `evm/src/apps/IntentGatewayV2.sol` lines 281-331.

### Proof of Concept
1. Deploy a fee-on-transfer token (e.g. 1% fee, as in `FeeOnTransferToken` from the test suite) on the Tron-fork deployment of `IntentGatewayV2`.
2. User A calls `placeOrder` with `inputs[0] = {token: FOT, amount: 1000e18}`. `safeTransferFrom` moves 1000e18 nominally but the gateway's real balance only increases by 990e18 (1% fee retained by the token).
3. `reducedInputs[0].amount` is computed from `originalAmount = 1000e18` (minus protocol fee, if any) and `_orders[commitment][FOT] += reducedInputs[0].amount` credits ~1000e18 worth of claim, while the gateway only holds 990e18 of FOT contributed by this order.
4. Repeat with additional legitimate orders in the same token to build up pooled balance.
5. When User A's order is later filled (`RedeemEscrow`) or cancelled, the contract pays out based on the inflated `_orders[commitment][FOT]` entry, which — combined with other orders' entries — can exceed the gateway's actual FOT balance, causing later legitimate redemptions/cancellations for *other* users' orders to revert (funds locked) or, depending on settlement ordering, allow User A's overstated claim to be paid from tokens actually escrowed by another user's order (fund misappropriation).

Note: I could not fully trace `fillOrder`/`RedeemEscrow` payout code in the Tron fork within the available search budget to confirm the exact downstream payout mechanics (e.g., whether it does its own balance checks that might mitigate the drain scenario); this should be verified directly in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s fill/redeem/cancel functions before remediation.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
