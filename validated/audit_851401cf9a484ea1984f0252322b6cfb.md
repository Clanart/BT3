### Title
Cached FROST preprocess seed is never invalidated, enabling nonce reuse and validator key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

`SigningProtocol::preprocess_internal` persists a 32-byte FROST preprocess seed in `CachedPreprocesses` keyed only by `context` (e.g., `(b"DkgConfirmer", attempt)`), and `share_internal`/`complete` reload it on every invocation. The seed is `set` once and never deleted, so every re-execution — a retry after `read_preprocess`/`sign` returns `Err`, a `share` followed by `complete`, or a rebuild — re-derives the identical nonces `(d, e)` via `ChaCha20Rng::from_seed(*seed.0)`. This is the direct analog of the reported "allocate, then return without freeing" bug class: the one-shot resource is acquired and never invalidated on the error/re-execution path. The file's own safety argument ("Upon any complete rebuild, we'd re-decide nonces, achieving safety") is false — the seed lives in the DB, so a rebuild following a distinct chain/fork reuses the same nonces over a different `set_keys_message`, which is the exact condition for secret-share recovery.

### Finding Description

- `preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:123-145) checks `CachedPreprocesses::get`; if absent it creates a preprocess, XOR-encrypts the `CachedPreprocess` seed, and `CachedPreprocesses::set`s it. It then loads the seed and calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`.
- `from_cache`/`seeded_preprocess` (crypto/frost/src/sign.rs:121-144) deterministically derives `nonces` and `commitments` from `ChaCha20Rng::from_seed(*seed.0)`. Identical seed ⇒ identical `d`, `e`.
- `share_internal` (lines 150-181) loads this machine, reads peer preprocesses, and calls `machine.sign(preprocesses, msg)`. On `Err` (line 166 `map_err(|_| participant)?`, line 178) it returns early — the analog of the leaked `victim_name`: the consumed-once seed is not cleared, so a retry signs again with the same nonces.
- `DkgConfirmer::complete` (lines 312-327) calls `share_internal` a second time, re-signing with the same nonces. If the caller-supplied `preprocesses`/`key_pair` differ from the earlier `share` call (distinct finalized messages, or a rebuilt process following a different fork per the header's own threat discussion at lines 30-48), the emitted Schnorrkel share equation `z = d + ρ·e + λ·s·c` is produced twice under the same `(d, e)`.
- With identical peer preprocesses but a different `msg`/`key_pair`, `ρ` and `λ` are unchanged while the challenge `c` differs; `s = (z1 − z2) / (λ·(c1 − c2))` recovers the validator's MuSig secret key outright. With differing peer preprocess sets, repeated re-execution across attempts still collapses the unknowns.

### Impact Explanation

Recovery of a validator's Ristretto secret key — the root-of-trust key used for on-chain DKG confirmation — enables forging the supermajority `set_keys` MuSig signature and installing an attacker-controlled validator-set key on Substrate. That is full compromise of the threshold network's root key, not a DoS. Because `context` includes `attempt`, cross-attempt reuse is avoided, but every re-execution within an attempt (retry, `share`+`complete`, post-rebuild re-processing) reuses the nonce deterministically.

### Likelihood Explanation

Medium. The leak does not require memory corruption or integrator misuse; it requires the signer to emit two shares under one `attempt` context where the signed transcript differs — which the code structure actively invites: `share` and `complete` are separate public entry points both calling `share_internal`, error returns leave the cache intact, and the documented "rebuild re-decides nonces" mitigation is contradicted by the DB-persistent seed. A peer who can cause a validator to process a second `share`/`complete` round under the same attempt with a different `key_pair` or different preprocess set (distinct finalized tributary messages, or a rebuild over a different history) obtains key-recovery equations from publicly broadcast shares.

### Recommendation

Delete (or version/rotate) the `CachedPreprocesses` entry the first time `share_internal` succeeds, and refuse to sign again under the same `context` — mirroring `SignMachine::from_cache`'s contract that "after this, the preprocess must be deleted so it's never reused" (crypto/frost/src/sign.rs:216-224). Additionally, persist the exact `preprocesses` and `msg` signed alongside the seed and `assert_eq!` them on re-execution, so `complete` and retries can only reproduce byte-identical shares rather than signing a different message with reused nonces.

### Proof of Concept

```rust
// Both calls hit the same context key (b"DkgConfirmer", attempt)
// and reload the same CachedPreprocesses seed -> same (d, e).

// Round 1: publish a share for key_pair A
let share1 = confirmer.share(preprocesses.clone(), &key_pair_a).unwrap();

// Round 2 (retry after error, complete(), or rebuild on a fork):
// same nonces, different msg => c' != c
let share2 = confirmer.share(preprocesses.clone(), &key_pair_b).unwrap();

// z1 - z2 = lambda * s * (c1 - c2)  =>  s = (z1 - z2) / (lambda * (c1 - c2))
// The validator's MuSig secret share s is recovered from the two
// public signature shares.
```

The same sequence triggers through `complete(...)` at coordinator/src/tributary/signing_protocol.rs:312-327, which unconditionally re-invokes `share_internal` and re-signs with the DB-cached seed instead of reusing the already-produced `AlgorithmSignatureMachine` state.
