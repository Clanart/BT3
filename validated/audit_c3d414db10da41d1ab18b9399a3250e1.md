### Title
Underpriced CPI account-data compute cost via per-account floor-division truncation - (File: program-runtime/src/cpi.rs)

### Summary
The TrailOfBits report describes a bug class where a fixed-point division that rounds down (`x / y`, floor) is applied repeatedly across many smaller operations instead of once across the aggregate amount, letting a user accumulate more "truncation savings" the more they split the operation. The Agave CPI account-translation code contains the same arithmetic pattern: the compute-unit cost for transferring account data during a cross-program invocation is computed with `checked_div(cpi_bytes_per_unit)` (floor division, no rounding up) and is applied **per account** rather than on the aggregated byte total, in some code paths.

### Finding Description
`cpi_bytes_per_unit` (default `250`, i.e. "account data bytes per compute unit charged during a CPI") is used to price the bytes moved through a CPI: [1](#0-0) 

In `translate_accounts_common`, when an instruction account maps to a caller-supplied `account_info`, the cost of the associated data is computed and charged individually, once per account, using floor division: [2](#0-1) [3](#0-2) 

The same floor-division-per-item pattern (rather than dividing once over the aggregate) also appears for lamports/data translation in `cpi.rs`: [4](#0-3) 

Because `checked_div` truncates toward zero, any account whose data length is less than `cpi_bytes_per_unit` (250 bytes) is charged **zero** compute units for its data-translation cost, and any account whose length is not an exact multiple of 250 loses the remainder. If a caller-controlled BPF program passes the same total amount of account data as many small `AccountInfo` entries (up to the per-instruction account limit, ~64 account infos / 255 account metas as exercised by `TEST_CU_USAGE_BASELINE`) instead of one large account, each small chunk is truncated to a lower (or zero) cost independently, and the sum of the per-account truncated costs is materially lower than the cost that would be charged for the same number of bytes charged once in aggregate — exactly the "split into smaller amounts to reduce compounded truncation loss" bug class described in the report. [5](#0-4) 

### Impact Explanation
This results in materially underpriced compute for CPI account-data translation: the actual work performed (translating/validating N accounts' worth of data) is undercharged relative to the true per-byte cost model, letting an attacker perform more account-data-heavy CPI operations per compute-unit budget than intended by splitting data across many small accounts. This is a compute-cost-model integrity issue reachable by any unprivileged BPF program via ordinary CPI, matching the "materially underpriced compute" acceptance criterion.

### Likelihood Explanation
Likelihood is limited by the fact that each CPI already pays a large fixed `invoke_units` cost (`DEFAULT_INVOCATION_COST = 946`) per invocation: [6](#0-5) 
so splitting into *separate CPI calls* to exploit the truncation is not economical (the 946 CU overhead per extra CPI dwarfs the ≤249 CU savings from truncation). However, the truncation can still be triggered **within a single CPI call** by supplying multiple small accounts in the same instruction's account list (bounded by the ~64 account-info / 255 account-meta limit per CPI), which does not incur the extra fixed invocation cost. This bounds the magnitude of the underpricing (at most a few hundred to a few thousand CU per CPI depending on account count), making it a real but limited-impact instance of the reported bug class rather than an unbounded one.

### Recommendation
Compute the CPI account-data cost once over the aggregate byte count (as is already done in `translate_account_infos` for `account_infos_bytes`) rather than per individual account inside `translate_accounts_common`, and/or use ceiling ("round up") division consistently for all `cpi_bytes_per_unit` cost calculations in `program-runtime/src/cpi.rs`, mirroring the ceiling-division pattern already used elsewhere in the cost model (e.g., `CostModel::calculate_pages_for_bytes`). Add property/fuzz tests asserting that the total CPI compute cost charged for moving X bytes of account data is independent of how many accounts/CPIs that X bytes is split across.

### Proof of Concept
A BPF program can construct a CPI instruction where, instead of passing one `AccountInfo` with `N * 249` bytes of data (charged `N * 249 / 250 ≈ N - 1` CU under floor division), it passes `N` separate `AccountInfo` entries each with `249` bytes of data. Because the cost in `cpi.rs:1016-1019` / `1052-1058` is computed per account via `checked_div(cpi_bytes_per_unit)`, each 249-byte account is individually floored to `0` CU (`249 / 250 == 0`), so the total charged cost for the same `N * 249` bytes of account data moved in one CPI call drops from `≈N` CU to `0` CU, up to the per-CPI account-count limit (bounded near 64 account infos, as exercised in `programs/sbf/rust/invoke/src/lib.rs` `TEST_CU_USAGE_BASELINE`/`TEST_CU_USAGE_MAX` tests).
