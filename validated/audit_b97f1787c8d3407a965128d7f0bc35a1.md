### Title
ThresholdKeys Accepts Duplicate Verification Shares for Distinct Participant Indexes, Collapsing t-of-n to Fewer Real Signers - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::new` validates the count of `verification_shares` and that every `Participant` index is `<= n`, but never checks that the shares for distinct participant indexes are actually distinct points. `ThresholdKeys::read`, which parses attacker-influenceable bytes, feeds directly into `ThresholdKeys::new` without any per-share distinctness check either. This mirrors the "same identity in two distinct roles" bug class: two different participant indexes (distinct voting/signature slots) can be backed by the same underlying public key, so one secret holder can satisfy multiple threshold slots.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::new` (lines 349-391) performs only two checks on `verification_shares`:

```rust
if verification_shares.len() != usize::from(params.n()) { ... IncorrectAmountOfVerificationShares ... }
for participant in verification_shares.keys().copied() {
  if u16::from(participant) > params.n() { ... InvalidParticipant ... }
}
```

There is no check that `verification_shares[i] != verification_shares[j]` for `i != j`. The `group_key` is then computed by interpolating the shares for participants `1 ..= t` (lines 376-378).

`ThresholdKeys::read` (lines 574-632) builds `verification_shares` purely from serialized bytes — one `read_G` per `Participant` in `1 ..= n` — and hands the map to `ThresholdKeys::new`. Nothing in the read path rejects a stream where the encoded point for index `l1` byte-for-byte equals the point for `l2` (canonical encodings make duplicates easy to produce).

The downstream consequence materializes in `crypto/frost/src/sign.rs`: `AlgorithmSignatureMachine::complete` (lines 447-495) verifies each participant's signature share against `self.view.verification_share(*l)` — a per-index share. If two indexes `l1, l2` share the same verification share `V = x·G` and the group key interpolates to a point whose discrete log an attacker knows (e.g., for `t = 2`, `included = {1,2}`: Lagrange factors `f1 = 2, f2 = -1`, so `group_key = 2V − V = V = x·G`), then the holder of `x` alone can produce a valid `SignatureShare` for *both* indexes, and the sum `x·f1 + x·f2 = x` verifies against `group_key` via `algorithm.verify` (line 465). A t-of-n signature is produced by one party controlling multiple participant "roles".

Note the inconsistency: `ThresholdKeys::view` (lines 473-484), `musig`'s `check_keys` (crypto/dkg/musig/src/lib.rs:54-60), and `validate_map` (crypto/frost/src/lib.rs:50-73) all explicitly reject duplicated participants/keys — but the foundational key-loading path `ThresholdKeys::new`/`read` does not reject duplicated verification shares, which is the equivalent duplication at the key layer.

### Impact Explanation
An attacker who supplies a serialized `ThresholdKeys` blob (the format is trivially constructible: `t`, `n`, `i`, interpolation tag, secret share, then `n` group encodings) can bind the same point to multiple participant indexes. For a `t` whose first-`t` indexes include the duplicated share, the interpolated `group_key` reduces to a scalar multiple of a key the attacker knows the discrete log of. During signing, every `included` slot whose verification share equals the duplicate accepts the same valid share — the attacker fills `t` slots solo and `complete` returns a valid signature for a message the other supposed participants never saw. This is a threshold-policy bypass / forged signature via public input bytes.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ThresholdKeys::read` (or an integrator constructing `ThresholdKeys` with an attacker-supplied share map). The serialized format has no authentication, and the code comments itself (`sign.rs:492-493`: "deserialized a semantically invalid FrostKeys") acknowledge semantically invalid keys are only detectable as an internal error — this semantic invalidity is simply never checked. Likelihood is bounded by whether an integrator loads keys from untrusted sources, hence Medium rather than High.

### Recommendation
In `ThresholdKeys::new`, additionally enforce that all `verification_shares` values are distinct (e.g., insert `share.to_bytes()` into a `HashSet` and error with a new `DuplicatedVerificationShare` variant on collision), and also reject identity/zero shares if the ciphersuite permits. This restores the same distinctness invariant already enforced for participant indexes in `view`, `musig`, and `validate_map`.

### Proof of Concept
Construct serialized keys for `t = 2, n = 3, i = 1` (Lagrange interpolation tag `1`), with an arbitrary `secret_share = x` and `verification_shares = {1: x·G, 2: x·G, 3: arbitrary}`. `ThresholdKeys::read` accepts it. `group_key` interpolates over `{1,2}` as `2·(xG) − (xG) = x·G`. A FROST session with `included = {1,2}`: the attacker supplies shares derived from `x` for both indexes; `verify_share` passes for both (same verification share), and `algorithm.verify(group_key, Rs, sum)` succeeds — yielding a valid group signature from a single signer.
