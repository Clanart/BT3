### Title
A single malformed `ReceivedOutput` poisons the entire `SignableTransaction`, silently preventing signing of all inputs - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::multisig` iterates over every input and returns `None` (with no error attribution) if any one input's `offset` fails to reproduce the prevout's `script_pubkey` — including when `p2tr_script_buf(offset.group_key())` returns `None` because `key + offset·G` has odd Y. `ReceivedOutput::read` deserializes the `offset` and `output` fields from untrusted bytes without checking that the offset actually derives the output's script. One maliciously crafted `ReceivedOutput` mixed into an otherwise honest input set therefore aborts transaction construction entirely, DoSing the spend of all batched inputs — the same "one bad element bricks the whole loop" class as a blacklisted recipient bricking `netAtPrice()`.

### Finding Description
`ReceivedOutput::read` accepts an arbitrary scalar `offset` and an arbitrary `TxOut`/`OutPoint` from the byte stream, with no consistency check between them: [1](#0-0) 

Later, `SignableTransaction::multisig` assumes every input's offset was honestly derived (i.e., produced by `Scanner::scan_transaction`, which only yields offsets whose keys produce even-Y P2TR scripts): [2](#0-1) 

Two poison paths exist at line 277:
1. `p2tr_script_buf(offset.group_key())` returns `None` when the offset key is odd-Y (line 80-83 of `wallet/mod.rs`), and the `?` propagates `None` for the whole `multisig` call.
2. The derived script doesn't equal `prevouts[i].script_pubkey`, so `None?` fires.

In both cases the function returns `None` for the *entire* transaction, with no indication of which input index was faulty. `SignableTransaction::new` happily accepts the poisoned input since it only validates amounts/dust/fees, never offset-to-script consistency: [3](#0-2) 

### Impact Explanation
Any caller that deserializes `ReceivedOutput`s from untrusted storage, a network message, or a coordinator-supplied set and then batches them into `SignableTransaction::new(...).multisig(&keys)` gets a flat `None` and cannot produce the signing machine. Every other legitimate input in that transaction is unspendable for that attempt. Because the failure carries no index or reason, the caller cannot programmatically identify and quarantine the bad input — recovery requires trial-and-error bisection over the input set outside the API. This is precisely the blacklisted-withdrawal shape: one attacker-injected element in an iterated set aborts a batch operation assumed to always succeed.

### Likelihood Explanation
Reachable whenever `ReceivedOutput::read` consumes bytes not produced by the local `Scanner` — e.g., outputs relayed between processor components or restored from data an attacker influenced. The attacker needs only pick an `offset` scalar such that `key + offset·G` is odd-Y (~50% of random scalars) or mismatched to a real prevout's `script_pubkey`, and have that `ReceivedOutput` included in a spending batch alongside honest inputs. It requires no keys, no validator position, and no control of other participants.

### Recommendation
- Validate at deserialization or at `SignableTransaction::new` time: for each `ReceivedOutput`, check `p2tr_script_buf(key + G·offset)` is `Some` and equals `output.script_pubkey` (this requires passing the base group key, or deferring the check into `multisig` as an error rather than `None`).
- Change `multisig`'s failure mode to `Result<_, usize>`/`Result<_, TransactionError>` reporting the offending input index so callers can drop the poisoned element and retry, rather than a blanket `None`.

The variant with a mismatched `script_pubkey` (offset deriving a valid even-Y script different from the prevout's) hits the explicit `None?` on line 278 of `send.rs` with the same whole-batch abort.

Note: I could not fully trace how `processor`'s output-DB pipeline feeds `ReceivedOutput`s (whether bytes ever cross a trust boundary before `multisig`), as that code is outside the in-scope crates. The in-scope API contract — an unchecked `read` feeding an all-or-nothing `multisig` — is itself the defect; if deployment guarantees only `Scanner`-produced outputs are ever used, severity drops to low/defense-in-depth.
