### Title
OP_RETURN outputs are omitted from fee and weight accounting - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` adds a caller-controlled `OP_RETURN` output before calculating transaction weight, but `calculate_weight_vbytes` only receives the payment outputs and optional change output. Consequently, `needed_fee`, the minimum-relay-fee check, the insufficient-funds check, the change calculation, and the maximum-weight check all exclude the `OP_RETURN` output. A transaction containing up to 80 bytes of attacker/caller-controlled data can therefore be signed with a lower effective fee rate than requested, potentially below the minimum relay rate.

### Finding Description
`SignableTransaction::new` accepts a public `data: Option<Vec<u8>>` argument, permits up to 80 bytes, and appends the corresponding zero-value `OP_RETURN` output to `tx_outs`. [1](#0-0) [2](#0-1) 

After that output is added, the code calculates the initial vbytes using only `payments`, not `tx_outs`. [3](#0-2)  `calculate_weight_vbytes` reconstructs a transaction containing only the supplied payment outputs, optionally followed by a change output. [4](#0-3)  The same omission occurs when calculating the fee and change amount with a change output. [5](#0-4) 

The resulting `needed_fee` is stored and later reported as the fee required to achieve the requested fee rate, while `fee()` derives the actual fee from the signed transaction's real outputs. [6](#0-5)  Signing commits to the complete transaction, including the omitted `OP_RETURN` output, through the Taproot signature hash. [7](#0-6) 

### Impact Explanation
When a change output is present, the transaction's actual fee equals `needed_fee`, but its actual vsize is larger than the vsize used to calculate that fee. The signed transaction therefore pays less than the requested sat/vbyte rate. At a requested rate of approximately the minimum relay rate, the missing 9–92 vbytes attributable to an `OP_RETURN` output can make the transaction nonstandard or economically unattractive to relay/mining. The same omission can also let the final transaction exceed the checked standard-weight bound or produce a materially different effective fee policy than the caller requested. [8](#0-7) 

### Likelihood Explanation
The vulnerable path is directly reachable through the public `SignableTransaction::new` API by supplying `Some(data)`, `Some(change)`, and enough input value to create change. No key compromise, malicious validator, network control, or collusion is required. The processor's Bitcoin adapter currently passes `None` for data, so the internal processor send path does not exercise this bug; exploitation requires a public wallet/API caller or an upstream flow that permits externally supplied transaction data. [9](#0-8) [10](#0-9) 

### Recommendation
Calculate weight and vbytes from the final `tx_outs` vector, or pass the `OP_RETURN` output into `calculate_weight_vbytes` alongside payments and change. The fee, minimum-relay check, funds check, change calculation, and maximum-standard-weight check must all use the same complete output set that will be inserted into the signed transaction. A regression test should construct a transaction with a change output and an 80-byte payload, then assert `needed_fee == transaction.vsize() * fee_per_vbyte`. [11](#0-10) [8](#0-7) 

### Proof of Concept
```rust
// Conceptual PoC for networks/bitcoin/src/wallet/send.rs.

let fee_per_vbyte = 1;

let signable = SignableTransaction::new(
  vec![sufficiently_funded_received_output],
  &[],                                      // no payment outputs
  Some(change_script),                      // exact fee is retained
  Some(vec![0x42; 80]),                     // public OP_RETURN data
  fee_per_vbyte,
).unwrap();

let actual_vbytes = signable.transaction().vsize() as u64;

// The first output is the attacker/caller-controlled OP_RETURN output.
assert!(signable.transaction().output[0].script_pubkey.is_op_return());

// Fee accounting ignored that output.
assert_eq!(
  signable.needed_fee(),
  fee_per_vbyte * actual_vbytes - fee_per_vbyte * omitted_op_return_vbytes
);

// After signing, the actual fee remains needed_fee, while the serialized
// transaction is larger by the OP_RETURN output's serialized size.
assert!(signable.needed_fee() < fee_per_vbyte * actual_vbytes);
```

The existing test path already constructs the vulnerable shape—a spend with no payments, a change output, and 60–80 bytes of `OP_RETURN` data—but only checks the script contents and does not compare `needed_fee` with the signed transaction's actual virtual size. [12](#0-11)
