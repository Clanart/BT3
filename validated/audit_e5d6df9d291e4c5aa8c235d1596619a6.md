### Title
`ReceivedOutput::read`/`Output::read` trusts a serialized scalar `offset` that is never validated against the output's `script_pubkey` - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to `validateOrder` reading `consideration[0].amount` without checking it against the actual balance, `ReceivedOutput` carries a self-declared scalar `offset` alongside the `TxOut`, and `ReceivedOutput::read` deserializes both from untrusted bytes with no check that the offset actually derives the output's key. Downstream, `Output::key()` in `processor/src/networks/bitcoin.rs` *derives* the owning key as `script_pubkey_key - offset·G`, so a forged/mismatched offset silently re-attributes the output to a different key, producing funds reported received that are not spendable (or spendable by the wrong multisig).

### Finding Description
`ReceivedOutput` is `{ offset: Scalar, output: TxOut, outpoint: OutPoint }` [1](#0-0) . `ReceivedOutput::read` reads `offset` via `Secp256k1::read_F` and then decodes the `TxOut`/`OutPoint`, performing no consistency check [2](#0-1) . Legitimate construction only happens in `Scanner::scan_transaction`, where `offset` is looked up from `self.scripts` keyed by `output.script_pubkey` [3](#0-2)  — that binding is established by the scanner but never re-verified on deserialization.

The offset is load-bearing twice:

1. `Output::key()` reconstructs the "base" key by *subtracting* `offset·G` from the key embedded in the script: `Secp256k1::read_G(...) - GENERATOR * self.output.offset()` [4](#0-3) . Any attacker-chosen offset therefore yields an arbitrary attacker-chosen `key()`.
2. `SignableTransaction::new`/`multisig` uses `offset` (added to the signer's secret share via `ThresholdKeys::offset`/`ThresholdView`) to produce the spending signature, and `Plan.key` selects which multisig key signs — both come from the untrusted `offset`/`key()` pair [5](#0-4) .

`Output::read` calls `ReceivedOutput::read` directly on the byte stream [6](#0-5) , and `Scheduler::read`/`from_db` consume those bytes into `utxos` which are then scheduled into `Plan`s [7](#0-6) .

### Impact Explanation
A `ReceivedOutput`/`Output` decoded from untrusted bytes can claim any `offset`. The value (`output.value`) is credited under `output.key()` — computed as script key minus `offset·G` — while the actual spend requires `secret_share + offset`. If the offset does not match the script, the output is counted in `balance`/`utxos` and scheduled into plans, yet any signature produced is invalid for that UTXO: funds are reported received that are not spendable. Alternatively the output can be attributed to a different multisig key (`assert_eq!(self.key, output.key())` in `forward_plan` notwithstanding, `schedule` only checks coin, not key [8](#0-7) ), causing mis-signed or stuck transactions.

### Likelihood Explanation
Medium-low: requires attacker-controlled bytes reaching `ReceivedOutput::read`/`Output::read` (e.g., outputs relayed between processors, DB/state channels, or any integrator deserializing scanner results) rather than bytes produced by a local `Scanner`. Where such deserialization crosses a trust boundary, a single crafted `(offset, TxOut)` pair is trivial to construct — no cryptographic break is needed, just a mismatched scalar.

### Recommendation
Bind `offset` to `output.script_pubkey` at the trust boundary: after `ReceivedOutput::read`/`Output::read`, verify `p2tr_script_buf(group_key + GENERATOR * offset) == output.script_pubkey` for the expected `group_key` (mirroring `Output::key()`), and reject otherwise — the analogue of checking `balanceOf` / deriving the correct amount via `_locateCurrentAmount` rather than trusting the declared value. Alternatively store only the outpoint+TxOut and re-derive `offset` via `Scanner`'s script map on load, and assert `utxo.key() == self.key` in `Scheduler::schedule`.

### Proof of Concept
```rust
// Given a real output paying to key+registered_offset*G:
let legit = scanner.scan_transaction(&tx).remove(0);

// Attacker crafts bytes with a different offset:
let mut forged = ReceivedOutput {
    offset: Scalar::random(&mut rng),          // does NOT match script_pubkey
    output: legit.output().clone(),
    outpoint: *legit.outpoint(),
};
let bytes = forged.serialize();
let decoded = ReceivedOutput::read(&mut bytes.as_slice()).unwrap(); // accepted, no error

// decoded.value() is credited; Output::key() = script_key - forged_offset*G
// attributes it to the wrong key; signing with secret_share + forged_offset
// produces a signature invalid for the actual UTXO -> unspendable "received" funds.
```
Conceptual reproduction: `tests/wallet.rs` shows `read` round-trips any `ReceivedOutput` equality-wise without key binding [9](#0-8) .
