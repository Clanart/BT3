### Title

Unvalidated peer message lengths panic during Bitcoin transaction signing - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary

`TransactionSignMachine::read_preprocess` and `TransactionSignatureMachine::read_share` deserialize a variable number of per-input messages without recording or validating the peer's claimed input count. A peer can provide an empty or truncated message vector, which deserializes successfully but later causes an indexing panic in `TransactionSignMachine::sign` or `TransactionSignatureMachine::complete`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

`read_preprocess` derives the returned `Vec` solely from the bytes supplied by the peer, so a zero-byte preprocess produces an empty `Vec`. [1](#0-0) 

`sign` then iterates over every locally expected input and indexes each peer preprocess as `commitments[c]` without first checking that its length equals `self.sigs.len()`. [2](#0-1) 

Likewise, `read_share` accepts an empty byte stream and returns an empty vector, while `complete` assumes every participant supplied one share per transaction input and calls `shares.remove(0)`. [3](#0-2) 

### Impact Explanation

An unauthenticated participant whose serialized preprocess or signature share reaches either API can crash the signing task or process with a Rust index-out-of-bounds panic. [4](#0-3) [5](#0-4) 

This matches the missing-input-validation/denial-of-service class of the reference issue: malformed count-like data is accepted during deserialization and subsequently used as if it had the expected cardinality. [1](#0-0) [6](#0-5) 

### Likelihood Explanation

The trigger requires only malformed public preprocess/share bytes from a signing participant, not secret material, malformed curve encodings, or a broken cryptographic primitive. [1](#0-0) [6](#0-5) 

The empty-vector path deterministically panics whenever the transaction has at least one input, and `SignableTransaction::new` requires at least one input. [7](#0-6) 

### Recommendation

Validate that each peer's preprocess and share vectors contain exactly `self.sigs.len()` elements immediately after deserialization, returning an `io::Error` or `FrostError` on mismatch. [1](#0-0) [6](#0-5) 

As defense in depth, replace direct indexing/removal with fallible accesses such as `get(c).ok_or(...)` and return `InvalidPreprocess` or `InvalidShare` rather than panicking. [2](#0-1) [5](#0-4) 

### Proof of Concept

For a transaction with one input, these calls demonstrate both deterministic panic paths:

```rust
// Path 1: preprocess parsing succeeds, then sign panics.
let empty: &[u8] = &[];
let peer_preprocess = sign_machine.read_preprocess(&mut &empty[..])?;
assert!(peer_preprocess.is_empty());

let mut peers = HashMap::new();
peers.insert(peer_participant, peer_preprocess);
let _ = sign_machine.sign(peers, &[]); // panics at commitments[c]

// Path 2: share parsing succeeds, then complete panics.
let peer_share = signature_machine.read_share(&mut &empty[..])?;
assert!(peer_share.is_empty());

let mut shares = HashMap::new();
shares.insert(peer_participant, peer_share);
let _ = signature_machine.complete(shares); // panics at shares.remove(0)
```

The panic is caused by missing semantic length validation rather than rejected malformed bytes. [8](#0-7) [3](#0-2)
