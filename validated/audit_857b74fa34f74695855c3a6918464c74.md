### Title
Unhandled ERC20 transfer failure in ArbWomUp/ArbWomUp2 permanently loses user airdrop-incentive rewards - (File: wombat/ArbWomUp.sol, wombat/ArbWomUp2.sol)

### Summary
`ArbWomUp.sol` and `ArbWomUp2.sol` are user-facing airdrop-incentive contracts ("for the arbitrum Airdrop") that reward ordinary wallets with `usdt`/`busd` when they deposit WOM. Both contracts' `incentiveDeposit()` functions update `claimedReward[msg.sender]` and then perform a raw, unchecked `IERC20(...).transfer(...)` to pay the reward, instead of using `SafeERC20.safeTransfer`. If the reward token returns `false` on failure instead of reverting, the user's `claimedReward` accounting is updated even though they never received the tokens.

### Finding Description
In `ArbWomUp.sol`, `incentiveDeposit()` does: [1](#0-0) 
`claimedReward[msg.sender] += rewardToSend` is incremented unconditionally, and the payout uses the raw `IERC20(usdt).transfer(msg.sender, rewardToSend)` call whose boolean return value is discarded — unlike `_deposit()` in the same contract, which correctly uses `safeTransferFrom`: [2](#0-1) 

The same pattern exists in `ArbWomUp2.sol`, where `busd` is paid out with a raw `.transfer()` call while `claimedReward` is already incremented beforehand: [3](#0-2) 

`getRewardAmount()` computes future rewards as `rewardAmount/DENOMINATOR - claimedReward[_account]`, so any amount already recorded in `claimedReward` is permanently subtracted from what the user can ever claim in the future: [4](#0-3) 

If the reward token (`usdt`/`busd`) is a non-standard ERC20 that returns `false` instead of reverting on failure (e.g. a blacklist/pausable stablecoin implementation where the recipient is momentarily restricted, or any other non-reverting failure condition), the `transfer` silently fails while `claimedReward[msg.sender]` has already been bumped by the full `rewardToSend`. The user's on-chain accounting shows the reward as claimed, but the tokens never arrived, and there is no way to re-claim the difference since `getRewardAmount` always nets out the recorded `claimedReward`.

### Impact Explanation
This causes a permanent, unrecoverable loss of the user's incentive-reward entitlement (unclaimed yield) — the tokens are never delivered but are marked as claimed forever, with no user-facing or admin recovery path in either contract. This matches the "theft or permanent freezing of unclaimed yield" impact category.

### Likelihood Explanation
The path is directly reachable by any ordinary wallet calling the permissionless `incentiveDeposit()` function; no privileged role is required. The impact is conditioned on the reward token (`usdt`/`busd`, addresses set by an admin `setup()`/init call, not by the caller) exhibiting non-reverting-failure semantics on `transfer` (e.g. blacklisting), which is a realistic behavior for USDT-family tokens deployed on BSC/other EVM chains.

### Recommendation
Replace the raw `IERC20(usdt).transfer(...)` / `IERC20(busd).transfer(...)` calls in `incentiveDeposit()` (and the admin `transferToAdmin()` for consistency) with `SafeERC20.safeTransfer`, consistent with the pattern already used elsewhere in these same files (`safeTransferFrom` in `_deposit()`), so that a failed transfer reverts the whole transaction (including the `claimedReward` update) rather than silently succeeding.

### Proof of Concept
1. Admin sets `usdt` in `ArbWomUp` to a non-standard ERC20 that returns `false` (rather than reverting) when `transfer` fails for a given recipient (e.g., a blacklisted/paused address, or contract-specific failure condition).
2. A user calls `incentiveDeposit(_amount)`. `_deposit()` correctly locks WOM via `safeTransferFrom`. `rewardToSend` is computed and `claimedReward[msg.sender] += rewardToSend` executes.
3. `IERC20(usdt).transfer(msg.sender, rewardToSend)` returns `false` (fails) but the call does not revert, so the transaction succeeds.
4. The user received 0 USDT, but `claimedReward[msg.sender]` reflects the full `rewardToSend`.
5. On any subsequent call to `incentiveDeposit()`, `getRewardAmount()` subtracts the already-recorded `claimedReward[_account]`, so the user can never claim the lost reward — it is permanently forfeited.

    function getRewardAmount(uint256 _amount, address _account) external view returns (uint256) {
        if (_amount == 0 || rewardMultiplier.length == 0) return 0;
        uint256 accumulated = _amount + userWOMDeposited[_account];

        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accumulated > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }
        rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];

        uint256 usdtReward = (rewardAmount / DENOMINATOR) - claimedReward[_account];
        uint256 usdtleft = IERC20(usdt).balanceOf(address(this));

        return usdtReward > usdtleft ? usdtleft : usdtReward;
    }
