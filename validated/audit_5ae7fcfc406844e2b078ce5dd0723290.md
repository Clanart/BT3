## Title
DID transfer preserves the seller's recovery list, allowing the previous owner to reclaim a "sold" DID (and any NFTs bound to it) via the recovery backdoor - ([File: chia/wallet/did_wallet/did_wallet.py])

## Summary
`DIDWallet.transfer_did()` constructs the new owner's DID inner puzzle by re-currying with the **same** `backup_ids` / `num_of_backup_ids_needed` that the current (selling) owner already had configured, instead of forcing the recovery list to be cleared. This mirrors the CVE-2005-0406 bug class: an "edit" operation (transferring/sanitizing ownership) is performed on the visible/primary state, but stale sensitive metadata from before the edit (the old recovery-list) is carried forward unmodified into the new state, silently preserving a channel for the previous owner (or their designated backup DIDs) to regain control.

## Finding Description
`transfer_did()` in `chia/wallet/did_wallet/did_wallet.py` builds the new DID puzzle hash like this: [1](#0-0) 
```
backup_ids = self.did_info.backup_ids
backup_required = self.did_info.num_of_backup_ids_needed
new_did_puzhash = did_wallet_puzzles.get_inner_puzhash_by_p2(
    p2_puzhash=new_puzhash,
    recovery_list=backup_ids,
    num_of_backup_ids_needed=backup_required,
    launcher_id=self.did_info.origin_coin.name(),
    metadata=...,
    recovery_list_hash=self.reset_recovery_list(),
)
```
`backup_ids`/`backup_required` are pulled straight from the current `did_info` — the exact same recovery configuration the *seller* set up — and are curried unchanged into the buyer's new inner puzzle. The helper `reset_recovery_list()` only clears the recovery hash if it is already nil and `backup_ids` is empty; otherwise it just returns the pre-existing recovery hash, again keeping the old configuration: [2](#0-1) 

The equivalent path in `get_innerpuz_for_new_innerhash()` documents this explicitly as intentional-but-dangerous behavior: [3](#0-2) 
```
# Note: the recovery list will be kept.
# In a selling case, the seller should clean the recovery list then transfer to the new owner.
```

The DID inner puzzle (`DID_INNERPUZ_MOD`) is curried with `(p2_puzzle, backup_ids_hash, num_of_backup_ids_needed, singleton_struct, metadata)`: [4](#0-3) 

Because `backup_ids_hash` and `num_of_backup_ids_needed` are unchanged after transfer, any coin whose puzzle hash matches one of the entries in the original `backup_ids` list retains the cryptographic ability to invoke the DID recovery/message-spend path against the new owner's coin — exactly the mechanism the DID puzzle exposes for legitimate lost-key recovery (`find_lost_did`, `create_message_spend`). The new owner has no visibility into this: nothing in the transfer flow, RPC, or CLI forces or even warns that the recovery list must be purged before a sale/offer completes (this is left as a manual "should" in a comment, not an enforced invariant).

This is the direct analog of CVE-2005-0406: the "visible" ownership data (the p2 puzzle / target address) is correctly updated, but a secondary, less-visible piece of state (the recovery list, analogous to an EXIF thumbnail) that should have been sanitized as part of the transfer is left intact, leaking the previous owner's control capability into the transferred asset.

## Impact Explanation
An NFT/DID sold via an offer (or any `did_transfer_did` RPC/CLI call) can be silently recoverable by the seller after the sale, because the seller's previously-configured `backup_ids` remain valid recovery authorities on the buyer's new coin. This is an "unauthorized coin movement" primitive: a party who no longer owns the DID (and by extension any NFTs whose DID association or transfer approvals depend on that DID) retains a cryptographically valid path to move/reclaim the coin, defeating the security assumption of a completed transfer/offer settlement. Because DIDs are frequently used as approval/authorization anchors for NFT ownership and CR-CAT/VC provider checks, unauthorized recovery of a DID can cascade into unauthorized control over dependent assets.

## Likelihood Explanation
This requires only that a seller configure (or fail to clear) a `num_of_backup_ids_needed > 0` recovery list before transferring/selling the DID — a completely normal, unprivileged wallet operation reachable by any wallet user performing `did_transfer_did` or completing an offer that includes a DID transfer. No malicious peer, node, or protocol-level capability is required; the flaw is in the wallet's spend-construction logic itself, and the buyer has no way to detect the retained backup authority without manually decompiling the puzzle.

## Recommendation
`transfer_did()` (and the underlying `get_innerpuz_for_new_innerhash`/`get_did_innerpuz` helpers used during transfer) should default to zeroing `backup_ids`/`num_of_backup_ids_needed` (or require an explicit, RPC-surfaced flag to preserve them) whenever ownership changes to a new p2 puzzle hash outside the current wallet, rather than silently carrying forward the seller's recovery configuration. At minimum, `did_transfer_did`/offer-settlement flows should surface a clear warning/require explicit confirmation when a non-empty recovery list will be transferred along with the DID.

## Proof of Concept
1. Wallet A creates a DID with `num_of_backup_ids_needed=1` and `backup_ids=[bytes32_of_wallet_A_controlled_backup_DID]`.
2. Wallet A sells/transfers the DID to Wallet B via `did_transfer_did` (or via an offer that includes the DID) — `transfer_did()` curries the new inner puzzle with the *same* `backup_ids`/`num_of_backup_ids_needed` as shown in `chia/wallet/did_wallet/did_wallet.py:825-832`.
3. Wallet B now owns the DID coin, unaware that Wallet A's backup DID is still a valid recovery authority curried into the puzzle.
4. Wallet A initiates the DID recovery flow (the message-spend/attestation path validated by `DID_INNERPUZ_MOD` against `backup_ids_hash`) using its still-valid backup DID, producing a valid CoinSpend that moves the DID coin to a puzzle hash of Wallet A's choosing — without Wallet B's cooperation or signature.
5. This spend is fully valid per consensus (it follows the DID puzzle's recovery branch, which was intentionally left unmodified across the transfer), demonstrating unauthorized coin movement following a "completed" sale.

    def reset_recovery_list(self) -> Program | None:
        if self.did_info.current_inner is None:
            return None

        uncurried_args = uncurry_innerpuz(self.did_info.current_inner)
        if uncurried_args is None:
            return None

        _, og_recovery_list_hash, _, _, _ = uncurried_args
        if self.did_info.num_of_backup_ids_needed == 0 and not did_recovery_is_nil(og_recovery_list_hash):
            return None

        if len(self.did_info.backup_ids) > 0:
            return None

        return og_recovery_list_hash
