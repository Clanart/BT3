### Title
Attacker-controlled dust outputs accumulate as mandatory transaction inputs, permanently DoSing `SignableTransaction::new` via `TooLargeTransaction` - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The external report describes an array (`deposits`) that grows via unprivileged user actions and is traversed wholesale by a later function (`refundDeposit` → `getLockedFunds`), eventually causing an out-of-gas DoS that locks funds. The Serai analog lives in the Bitcoin wallet: `Scanner` records every output paying to any registered `script_pubkey` — which any Bitcoin user can create permissionlessly — and `SignableTransaction::new` unconditionally turns *all* supplied `ReceivedOutput`s into transaction inputs, one FROST signing machine per input, then aborts with `TransactionError::TooLargeTransaction` once the count is too large. There is no coin selection, input cap, or filtering of dust inputs, so an attacker who floods the vault address with cheap dust outputs makes every subsequent spend fail.

### Finding Description
`Scanner::scan_transaction` pushes a `ReceivedOutput` for every transaction output whose `script_pubkey` matches a registered script (`networks/bitcoin/src/wallet/mod.rs:199-214`). Creating such an output requires no privilege — anyone can send a P2TR payment to the vault's `p2tr_script_buf` address.

On the spend side, `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150`) consumes the entire `inputs: Vec<ReceivedOutput>`:
- `tx_ins` is built from *every* input (send.rs:177-185) — no selection or cap.
- The only size control is a post-hoc weight check: `if weight > MAX_STANDARD_TX_WEIGHT { Err(TooLargeTransaction) }` (send.rs:241-243).
- Each input costs a fixed ~58 vbytes of keyspend weight (`calculate_weight_vbytes`, send.rs:71-84), so ~1700 inputs exceed the 400,000 WU standard-weight limit.
- `multisig` additionally creates one `AlgorithmMachine` per input and re-derives `keys.offset(self.offsets[i])` per input (send.rs:273-284), and `TransactionSignMachine::sign` runs a full FROST sign + `taproot_key_spend_signature_hash` per input (send.rs:377-395) — CPU/memory cost grows linearly before the weight check is even reached for large input sets.

Notably, inputs are not subject to the dust check — only `payments` are (send.rs:165-169), so attacker dust outputs of ≥546 sats (or even below, since input values are never validated) count fully as inputs.

### Impact Explanation
Once enough dust outputs to the vault's registered scripts are confirmed, any call path that feeds the scanned `ReceivedOutput`s into `SignableTransaction::new` fails with `TooLargeTransaction`, and `multisig`/`sign` never run. Funds remain received and scannable but cannot be moved through this API — the same "funds locked by unbounded accumulated state" impact as the OpenQ finding. Recovery requires the integrator to manually partition inputs into multiple transactions, which the API supports only by the caller subsetting `inputs` itself; nothing in the in-scope code performs that subsetting.

### Likelihood Explanation
An unprivileged attacker only needs to broadcast ordinary Bitcoin transactions paying dust to the vault's public `script_pubkey`. Each output costs the attacker ~546 sats plus fees; a few thousand outputs (well under 1 BTC at minimum relay fees) suffices to push a single-input-set transaction over the standard weight limit. This requires no validator key, no protocol participation, and no malicious peer — just public blockchain transactions, matching the "deposit spam" vector of the original report.

### Recommendation
- Enforce a maximum input count in `SignableTransaction::new` (or select a subset of inputs covering `payment_sat + fee`) instead of consuming `inputs` wholesale.
- Skip inputs whose value is below an economic threshold (e.g., below `DUST` or below the marginal fee cost of spending them) so dust cannot force inclusion.
- Alternatively, sort inputs by value and add them greedily until the payment + fee is covered, leaving excess dust unspent rather than failing.

### Proof of Concept
```rust
// Conceptual PoC against networks/bitcoin/src/wallet
let scanner = Scanner::new(vault_group_key).unwrap();

// Attacker: broadcast a tx with thousands of dust P2TR outputs to the vault address
let mut attacker_tx = Transaction { /* version, locktime */ ..Default::default() };
let dust = TxOut {
  value: Amount::from_sat(546),
  script_pubkey: p2tr_script_buf(vault_group_key).unwrap(),
};
for _ in 0 .. 3000 { attacker_tx.output.push(dust.clone()); }

// Scanner records all of them
let received = scanner.scan_transaction(&attacker_tx);
assert_eq!(received.len(), 3000);

// Victim: attempts to spend; every input is included unconditionally
let res = SignableTransaction::new(
  received,                                   // all scanned outputs become inputs
  &[(recipient_script, 1_000_000u64)],        // any payment
  Some(change_script),
  None,
  fee_per_vbyte,
);
// tx weight ≈ 3000 * ~58 vB inputs >> 400_000 WU limit
assert_eq!(res, Err(TransactionError::TooLargeTransaction));
// Every retry with the full scanned set fails; vault funds are unspendable via this API.
```

The root cause is structural and identical to the source finding: unprivileged writes grow an unbounded collection (`Scanner`'s matched outputs / the `inputs` vector), and a downstream function (`SignableTransaction::new`/`multisig`/`sign`) is forced to process all of it at once, turning growth into a hard failure that locks funds.
