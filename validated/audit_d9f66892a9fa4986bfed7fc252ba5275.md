**Checks performed** in `send_move_to_vault_tx`:
1. Exactly 1 input, 2 outputs
2. `output[0].value == bridge_amount`, `output[1].value == 0`
3. `output[0].script_pubkey == bridge vault taproot address`

**Tx-sender deduplication**: `insert_try_to_send` deduplicates by Bitcoin txid. If the txid already exists, it returns the existing row ID immediately without updating the stored `raw_tx` bytes: [4](#0-3)

## Attack Path

In Bitcoin (segwit), the **txid is computed from non-witness data only** (version, inputs, outputs, locktime). Two transactions with identical inputs and outputs but different witnesses share the same txid.

The attacker can:
1. Observe the deposit outpoint on the Bitcoin blockchain (public)
2. Query `get_nofn_aggregated_xonly_pk` (public endpoint) to compute the bridge vault script pubkey
3. Construct a transaction: `input = deposit_outpoint`, `output[0] = bridge_amount → vault script`, `output[1] = 0 → anchor script`, **witness = garbage bytes**
4. This transaction passes all 4 structural checks in `send_move_to_vault_tx`
5. Submit it **before** the legitimate `send_move_to_vault_tx` call (the window is the duration of `new_deposit` verifier coordination — several minutes)
6. The garbage transaction is stored in the tx_sender queue
7. When the legitimate move transaction (same txid, valid witness) is submitted, `check_if_tx_exists_on_txsender` finds the existing row and returns early — the correct witness is **never stored**
8. The tx_sender retries the garbage transaction indefinitely; Bitcoin rejects it every time (invalid witness)
9. The deposit UTXO is never spent

## Impact Assessment

The deposit process is permanently disrupted for the targeted deposit. However, the funds are **not permanently frozen**: the deposit address includes a `user_takes_after` timelock script (200 blocks in production config) that allows the user to reclaim their BTC after the timelock expires. [7](#0-6) [8](#0-7) 

The impact is therefore a **liveness attack on the deposit flow** — any deposit can be griefed by an unprivileged attacker who monitors the Bitcoin mempool/chain. The user loses the deposit attempt and must wait for the timelock to recover funds, but does not permanently lose them. This does not meet the "permanent freezing of bridged funds" threshold claimed.

### Title
Missing input-outpoint binding and witness validation in `send_move_to_vault_tx` enables deposit-flow griefing — (`core/src/rpc/aggregator.rs`)

### Summary
`send_move_to_vault_tx` validates output structure but never checks that `movetx.input[0].previous_output == deposit_outpoint` and never validates the witness. An attacker can inject a structurally valid but witness-invalid transaction with the same txid as the legitimate move transaction into the tx_sender queue before the honest submission, permanently blocking that deposit from being broadcast.

### Finding Description
The function at lines 2019–2073 checks output count, values, and script pubkeys, but performs no binding check between the transaction's actual input and the `deposit_outpoint` parameter, and no witness/signature validation. The tx_sender deduplicates by txid (non-witness data). An attacker who submits a transaction with the correct non-witness structure but a garbage witness first will occupy the txid slot; the legitimate transaction is silently deduplicated and its valid witness is never stored. The tx_sender retries the garbage transaction indefinitely, always failing Bitcoin script validation. [2](#0-1) [4](#0-3) 

### Impact Explanation
Any deposit can be griefed. The deposit UTXO is never spent by the bridge. The user must wait for the `user_takes_after` timelock to reclaim their BTC. The bridge loses liveness for that deposit. This is **not** permanent fund loss (user can recover via timelock), but it is a reliable, low-cost denial-of-service against any individual deposit.

### Likelihood Explanation
The aggregator endpoint is publicly accessible (no client certificate enforcement by design). The deposit outpoint is visible on-chain. The bridge vault script pubkey is derivable from the public `get_nofn_aggregated_xonly_pk` endpoint. The attack window (duration of `new_deposit` verifier coordination) is several minutes. No special privileges are required.

### Recommendation
Add an explicit check that `movetx.input[0].previous_output == deposit_outpoint` before inserting into the tx_sender queue. Additionally, verify the transaction's witness against the expected deposit script and nofn signature before accepting it. This binds the submitted transaction to the exact deposit it is meant to finalize.
