### Title
Payout OP_RETURN attribution is not covered by the required `SinglePlusAnyoneCanPay` signature, letting anyone re-attribute a fronted payout to an arbitrary operator's xonly pubkey - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` builds the payout tx's OP_RETURN with only `operator_xonly_pk.serialize()` [1](#0-0) , and the user signature that authorizes spending `withdrawal_utxo` is enforced to use `SinglePlusAnyoneCanPay` [2](#0-1) . That sighash flag only commits to input 0 and output 0 - it does not cover the OP_RETURN output or any additional funding inputs. Anyone who has the withdrawer's signature (the withdrawer themself, or anyone observing a broadcast/mempool payout tx) can therefore build an alternate, still-validly-signed payout transaction that pays the exact same user output but attributes the payout to a different, arbitrary operator xonly pubkey in the OP_RETURN, and get that variant confirmed instead (first-broadcast race or RBF replacement, since the operator's tx is built with `DEFAULT_SEQUENCE` and typically funded via `fund_raw_transaction`/RBF flow).

### Finding Description
The binding this exploits is: **the operator credited by `update_finalized_payouts` as `payout_payer_operator_xonly_pk`** must equal **the operator who actually funded the output paid at `withdrawal_utxo`**.

Trace:
1. `Operator::withdraw` validates `withdrawal_utxo == input_utxo.outpoint` [3](#0-2) , verifies the schnorr signature over `payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` [4](#0-3) , then funds/signs/broadcasts via `fund_raw_transaction` + RBF [5](#0-4) .
2. The RPC layer enforces the signature's sighash type must be `SinglePlusAnyoneCanPay` [6](#0-5) . `taproot_key_spend_signature_hash` for `*PlusAnyoneCanPay` only commits to the single spent prevout (`Prevouts::One`) and, for `Single`, only the output at the same index (index 0) [7](#0-6) . It does **not** commit to output index 1 (anchor) or index 2 (the OP_RETURN carrying `operator_xonly_pk`), nor to any other inputs added by `fund_raw_transaction`.
3. `create_payout_txhandler` places `PushBytesBuf::from(operator_xonly_pk.serialize())` in an uncommitted output [8](#0-7) .
4. Because output 0 (recipient + amount) is what's cryptographically bound, an attacker can reuse the exact same witness/signature and construct a different transaction: identical input (withdrawal_utxo) and identical output 0, but with a different OP_RETURN xonly pubkey and their own fee-paying input(s). This new transaction remains fully valid against the user's original signature.
5. On confirmation, `Verifier::update_finalized_payouts` parses the OP_RETURN of whichever transaction actually confirmed and stores that pubkey as `payout_payer_operator_xonly_pk` [9](#0-8) , with no cross-check against who actually built/funded/broadcast the original tx.
6. The victim operator's own automation, `PayoutCheckerTask`, blindly trusts this DB attribution: it selects "its" unhandled payout purely by matching `payout_payer_operator_xonly_pk == self.operator.signer.xonly_public_key` [10](#0-9)  and then calls `handle_finalized_payout`, which proceeds to build/queue Kickoff/Reimburse transactions with **no check that this operator ever built, signed, or broadcast that specific payout tx** [11](#0-10) . The only guard resembling a check, `validate_payer_is_operator`, is used solely by the *manual* `get_reimbursement_txs` RPC path and simply re-confirms the DB's (already attacker-controlled) attribution equals the caller's own key [12](#0-11)  - it does not validate authorship of the payout tx either.
7. `is_kickoff_malicious` in the verifier likewise only checks `operator_xonly_pk == kickoff_data.operator_xonly_pk` sourced from the same DB row [13](#0-12) ; since the kickoff is issued by the operator whose key was (falsely) attributed, this check passes and the kickoff is judged non-malicious.

Why existing guards fail: none of `is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, `is_kickoff_malicious`, or DB uniqueness constraints validate that the operator issuing the Kickoff/Reimburse actually funded/broadcast the confirmed payout transaction - they only check that the (attacker-controllable) OP_RETURN pubkey matches the kickoff's operator pubkey, and that the enforced-`SinglePlusAnyoneCanPay` signature is valid, which by design does not commit to the OP_RETURN.

### Impact Explanation
An operator can be made to run its full Kickoff → Reimburse flow and be reimbursed `bridge_amount` for a payout it never authored/funded - the payout tx (input 0, output 0) is entirely reused/refunded by the attacker, who freely rewrites the attribution output. This exactly matches the Critical category "an operator reimbursed for a payout it never funded." It also forces the targeted operator's automation to unwillingly spend collateral/round capacity and broadcast on-chain transactions (Kickoff, later Reimburse) it never chose to issue, coupling any registered operator's identity to a transaction it has no record of. This is repeatable across every withdrawal and can target any operator's xonly pubkey (since the OP_RETURN accepts any syntactically valid xonly pubkey, no proof of operator participation is required in the OP_RETURN itself).

### Likelihood Explanation
Preconditions are minimal and fully within the stated attacker capability: the attacker only needs to be the withdrawer (or observe a withdrawer's already-broadcast payout tx in the public mempool) and be able to broadcast a Bitcoin transaction with their own fee-paying input. The `SinglePlusAnyoneCanPay` enforcement is a protocol-wide, non-test code path (`core/src/rpc/parser/operator.rs`, used by both `Operator::withdraw` and the aggregator's optimistic-payout path), so this is not a corner case - it is the required signature scheme for every standard operator-fronted payout. Attacker cost is only the cost of funding the identical user-facing output (same as any legitimate front-runner) plus a small transaction fee to win the race/RBF. This is deployable on regtest with no mainnet/Citrea live dependency, since it only touches L1 Bitcoin transaction construction and the verifier's `update_finalized_payouts`/`is_kickoff_malicious` code paths, which are exercised by existing e2e test helpers.

### Recommendation
Bind the operator attribution to the signature that authorizes spending the withdrawal UTXO. Options: (1) require the user's signature to use `SIGHASH_ALL` (or `AllPlusAnyoneCanPay`) so it commits to all outputs including the OP_RETURN, forcing the withdrawer to pre-commit to a specific operator (or to none, if using a separate mechanism for operator selection); or (2) if the "any operator can front the same signed payout" design is intentional, require the operator's own kickoff/reimbursement flow to independently prove authorship (e.g., by storing/verifying a proof that the specific broadcasting wallet/operator produced the `fund_raw_transaction`/`sign_raw_transaction_with_wallet` result, or requiring an additional operator-signed commitment over the whole payout tx including the OP_RETURN) before `update_finalized_payouts`/`PayoutCheckerTask` treats a confirmed payout as attributable to that operator.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

            .await?

        let current_round_index = self.db.get_current_round_index(Some(dbtx)).await?;
        tracing::info!(

        #[cfg(feature = "automation")]
        if current_round_index != round_idx {
            // we currently have no free kickoff connectors in the current round, so we need to end round first

                "Operator: Starting next round to be able to get reimbursement for the payout"
            );
            // start the next round to be able to get reimbursement for the payout
            self.end_round(dbtx).await?;

        // by the PayoutCheckerTask, meaning kickoff_txid is set

            payout_blockhash,
            kickoff_txid,

                    .into());

                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };
