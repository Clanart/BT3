### Title
Forged `ReceivedOutput` metadata creates phantom Bitcoin inputs that are treated as spendable - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` trusts attacker-supplied output metadata without proving that the claimed `OutPoint`, `TxOut`, and scalar spending offset describe a real output controlled by the threshold key. A forged serialized input can therefore inflate the wallet’s apparent balance and cause the signing flow to commit signatures to an invalid or unspendable UTXO.

### Finding Description
`ReceivedOutput` is documented as “a spendable output,” but its deserializer independently accepts a scalar offset, arbitrary `TxOut`, and arbitrary `OutPoint` without checking that the outpoint exists or that the referenced on-chain output equals the supplied `TxOut`. [1](#0-0) 

`SignableTransaction::new` then trusts both the claimed value and outpoint: it sums `input.output.value` as available funds and inserts `input.outpoint` into the transaction inputs. [2](#0-1) 

The only consistency check in `SignableTransaction::multisig` verifies that the supplied `prevouts[i].script_pubkey` matches `p2tr_script_buf(keys.offset(offset).group_key())`; it does not verify that `tx.input[i].previous_output` references that prevout or that its on-chain amount and script match the supplied data. [3](#0-2) 

During signing, `TransactionSignMachine::sign` commits to all supplied claimed prevouts using `Prevouts::All`. An attacker can choose the public wallet script—or compute the script for an arbitrary public offset—while pointing the outpoint to a nonexistent or unrelated output. The resulting transaction passes the local multisig setup but is not a valid spend of the claimed input. [4](#0-3) 

### Impact Explanation
This is an unauthorized-input consistency failure analogous to treating one asset balance as if it were another at a fixed rate: the implementation treats a serialized claim as equivalent to a verified spendable output.

An attacker-controlled `ReceivedOutput` can report Bitcoin funds as received when no corresponding spendable UTXO exists. The claimed amount is used for balance and fee calculations, and the forged input enters the FROST signing flow. The eventual transaction cannot spend that input because the outpoint is absent or because the signed Taproot prevout commitment does not match the actual UTXO.

### Likelihood Explanation
The attack requires only public information: a wallet P2TR script or group key and any scalar offset. No validator compromise, leaked key, malformed curve point, or malicious RPC result is required. The reachable public input is an untrusted byte stream passed to `ReceivedOutput::read`, followed by use of the returned object in `SignableTransaction::new` and `multisig`.

The result is a signing failure or persistently inflated/unspendable balance rather than direct theft, so the practical severity is Medium in an implementation that persists or relays untrusted `ReceivedOutput` records.

### Recommendation
Do not construct spendable-wallet inputs from an unauthenticated `ReceivedOutput` serialization. Either:

- require outputs entering `SignableTransaction::new` to come from `Scanner::scan_transaction`/`scan_block`, or
- authenticate the serialized record against the expected scanner and verify on-chain that `outpoint` resolves to the supplied `TxOut`.

At minimum, add a validation API that binds `{offset, output, outpoint}` to the scanner’s threshold key and rejects records whose `output.script_pubkey` does not equal `p2tr_script_buf(key + G * offset)`. Separately verify the referenced UTXO’s amount and script before treating the record as spendable.

### Proof of Concept
```rust
use bitcoin::{
  Amount, OutPoint, ScriptBuf, TxOut, Txid,
  hashes::Hash,
};
use k256::Scalar;
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction, p2tr_script_buf};

// `wallet_key` is the even-Y threshold group key corresponding to a public deposit
// address. This can be obtained publicly.
let script: ScriptBuf = p2tr_script_buf(wallet_key).unwrap();

// Claim that a nonexistent or unrelated outpoint pays a large amount to the wallet.
let forged = ReceivedOutput::read(&mut [
  Scalar::ZERO.to_bytes().as_slice(),                    // offset = 0
  &bitcoin::consensus::encode::serialize(&TxOut {
    value: Amount::from_sat(100_000_000),
    script_pubkey: script.clone(),
  }),
  &bitcoin::consensus::encode::serialize(&OutPoint {
    txid: Txid::all_zeros(),                             // no real spendable UTXO
    vout: 0,
  }),
].concat().as_slice()).unwrap();

// The forged value is counted as spendable input.
let signable = SignableTransaction::new(
  vec![forged],
  &[(destination_script, 50_000_000)],
  Some(change_script),
  None,
  10,
).unwrap();

// This succeeds locally because the forged TxOut script matches key + 0*G.
let machine = signable.multisig(&threshold_keys).unwrap();

// Signing commits to the forged prevout. Broadcasting or validating the completed
// transaction fails because Txid::all_zeros():0 is not the claimed spendable output.
```

The decisive condition is that `ReceivedOutput::read` accepts the forged association and `multisig` validates only the local script/offset relationship, not the outpoint’s existence or the claimed prevout’s on-chain identity.
