### Title
Latent reward-token balances in `ManualCompound.compound` can be swept for free by any caller - (File: `rewards/ManualCompound.sol`)

### Summary
`ManualCompound.compound()` distributes reward tokens based on `IERC20(token).balanceOf(address(this))` — the contract's total current balance — rather than the amount actually attributable to `msg.sender`'s own claim in that call. This is the same underaccounting root cause as the LiFi finding: using "whatever balance the contract happens to hold" as the transferable amount instead of tracking a delta tied to the caller's own deposited/claimed funds, letting an unrelated caller sweep latent tokens that belong to previous callers.

### Finding Description
`compound()` first calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` to pull the caller's pending rewards into the `ManualCompound` contract [1](#0-0) . It then sweeps "non-compoundable" reward tokens back to the caller using the *entire* current token balance of the contract, not a before/after delta scoped to this call: [2](#0-1) 

and separately, for the protocol-configured compoundable reward tokens, it again uses `IERC20(_tokenAddress).balanceOf(address(this))` as `receivedBalance` to decide how much to convert/lock/deposit/transfer on behalf of `msg.sender`: [3](#0-2) 

Whether a reward token is fully swept back to the caller (lines 126-138 path) depends entirely on `msg.sender`-supplied `_rewards[i][j]` arrays. `_claimBaseRewarder` in `MasterMagpie` claims *all* registered reward tokens for a staking pool when the caller passes an empty reward-token array for that pool (`rewarder.getReward(_account, _receiver)`), versus only the explicitly-specified subset when a non-empty array is passed (`rewarder.getRewards(...)`) [4](#0-3) . Consequently, if a legitimate user calls `compound()` and omits a token from `_rewards[i]` for a pool whose rewarder actually pays out that token (or if that token isn't in `_rewards` at all for that pool while other pools trigger claim of all tokens), that token gets pulled into `ManualCompound` via `multiclaimOnBehalf` but is neither swept back in the "non-compoundable" loop (because it wasn't named in `_rewards`) nor processed in the "compoundable" loop (because it isn't in the owner-configured `rewards[]` list). The token then sits as a latent balance in the `ManualCompound` contract.

Because the sweep condition in the non-compoundable loop only checks `!compoundableRewards[_rewards[i][j]]` and unconditionally transfers `IERC20(_rewards[i][j]).balanceOf(address(this))` (the whole contract balance, not a per-call delta) to whichever `msg.sender` supplies that token address, any subsequent unrelated wallet can call `compound()` naming an arbitrary `_lps`/`_rewards` combination that references that leftover token (even with zero personal stake, yielding zero legitimate claim for themselves) and receive the entire latent balance belonging to the earlier user.

### Impact Explanation
This allows direct theft of another user's unclaimed reward/yield tokens that are transiently or unintentionally left in the `ManualCompound` contract, without requiring any privileged role — any ordinary wallet calling the public `compound()` function can trigger the sweep. This matches the LiFi bug class of "anyone can get free funds because the contract accounts by raw balance instead of a delta tied to the actual transaction."

### Likelihood Explanation
Exploitation requires that some reward token balance be left un-swept in the contract from a prior `compound()` call (e.g., a user omitting a token from `_rewards` for a pool that pays out multiple reward tokens, or an owner later adding/removing a token from the `compoundableRewards`/`rewards` list while token balance is in flight). This is a plausible, unprivileged, reachable condition given `compound()`'s reward-token parameters are fully caller-controlled, and no code path forces reconciliation of `balanceOf(address(this))` against per-call claimed amounts.

### Recommendation
Track and use exact per-call deltas (balance before vs. after `multiclaimOnBehalf`) per reward token instead of raw `balanceOf(address(this))`, and ensure every reward token actually claimed by `multiclaimOnBehalf` for `msg.sender` is either swept back or routed to compounding within the same call, so no token balance attributable to one user can be later claimed by an unrelated caller.

### Proof of Concept
1. User A calls `compound(_lps, _rewards, ...)` where `_lps` includes a pool whose rewarder pays out reward tokens `[X, Y]`, but User A's `_rewards[i]` array for that pool is `[X]` only (omitting `Y`), while another pool in the same call has an empty reward array causing `getReward()` to claim all tokens including `Y` from elsewhere. Token `Y` ends up transferred into `ManualCompound` via `multiclaimOnBehalf` but is not referenced in any sweep path in that call (not in `_rewards`, not in the protocol's `rewards[]` list), leaving `Y`'s balance sitting in `ManualCompound`.
2. Attacker B, with zero stake in any pool, calls `compound([_somePoolWithYAsARewardToken], [[Y]], 0, 0, false)`. Since `Y` is not in `compoundableRewards`, the code hits the branch at `rewards/ManualCompound.sol:131-134`, computes `rewardBalance = IERC20(Y).balanceOf(address(this))` (User A's leftover balance), and transfers the entire amount to attacker B, even though B claimed nothing of value themselves.
