### Title
Broken `_calExpireForfeit` in `mWOMSVBaseRewarder` always returns zero forfeit, letting users in cooldown claim full rewards at the expense of remaining full lockers - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` is dead code: it initializes `rewardableAmount = _amount` and never adjusts it based on the account's lock/cooldown state, so `forfeitAmount = _amount - rewardableAmount` is always `0`. Consequently `_sendReward` never routes any portion of a claiming user's earned rewards back into the pool via `_queueNewRewardsWithoutTransfer`, even when that user has started/partially started unlocking (cooldown). Any unprivileged holder of mWomSV can lock, immediately call `startUnlock`, and receive their full accrued reward with zero forfeit, defeating the intended penalty/redistribution mechanism that should benefit stakers who remain fully locked.

### Finding Description
`mWOMSVBaseRewarder.getReward`/`getRewards` are gated by `onlyMasterMagpie` and reached through `MasterMagpie.multiclaimFor`, which `mWomSV.startUnlock` and `mWomSV.unlock` call automatically before recording a cooldown slot: [1](#0-0) 

Reward accounting flows through `_sendReward`, which is supposed to forfeit a portion of `userRewards` when a user's stake is in cooldown, by calling `_calExpireForfeit`: [2](#0-1) 

However, `_calExpireForfeit` is broken — it sets `rewardableAmount = _amount` and never derives it from the account's actual lock/cooldown state, so the subtraction always yields zero: [3](#0-2) 

The rewarder's `balanceOf` also pulls the user's full staked amount from `MasterMagpie.stakingInfo`, which is unaffected by `mWomSV`'s internal cooldown bookkeeping (`getUserTotalLocked` + `getUserAmountInCoolDown` always sum back to the same staked total): [4](#0-3) [5](#0-4) 

So a user in cooldown continues to accrue rewards at the exact same rate as a fully-locked user of equal balance, and — because the forfeit branch never fires — none of their yield is ever redirected to `_queueNewRewardsWithoutTransfer` for the benefit of remaining full lockers. This confirms the described asymmetry: `queueMGP` (present in the sibling `vlMGPBaseRewarder.sol`, which actually computes and forfeits) is absent in `mWOMSVBaseRewarder.sol`, and the forfeit logic that does exist here is a no-op.

Note on the specific proof claim in the prompt ("sum(claims) > queued amount"): this is not accurate. Because rewards are distributed via the standard `rewardPerTokenStored` proportional-share accounting, the sum of all claims still equals the total amount queued — there is no protocol insolvency or unbacked payout. The real, provable impact is distributional: cooling/unlocking stakers wrongly retain 100% of their proportional share instead of forfeiting part of it, so the redistribution benefit that fully-locked stakers should have received (extra `queuedRewards` from others' forfeits) never materializes.

### Impact Explanation
This is theft/permanent loss of unclaimed yield relative to intended tokenomics: full lockers are permanently denied the forfeit-redistribution boost to their reward rate that the protocol design promises, while users who partially/fully unlock are permanently over-rewarded relative to the documented incentive structure. This falls under "theft or permanent freezing of unclaimed yield" — the forfeited yield that should accrue to remaining lockers is instead retained by the exiting user and is never recovered.

### Likelihood Explanation
Trivially reachable by any unprivileged holder of mWOM/mWomSV: no special role required, capital needed is only whatever amount the attacker wants staked, and the sequence (lock → `startUnlock` → auto-claim via `multiclaimFor`) is a single, repeatable, always-available call path with no cooldown gating on the claim itself. It requires no flash loan, front-running, or reentrancy — the bug is a pure logic error in `_calExpireForfeit` triggered on every normal claim.

### Recommendation
Rewrite `_calExpireForfeit` to actually compute the rewardable/forfeit split based on the account's real lock state (e.g., proportion of `getUserAmountInCoolDown(_account)` vs. `getUserTotalLocked(_account)` from `mWomSV`), analogous to how `vlMGPBaseRewarder.queueMGP` performs its forfeit calculation, and ensure `_sendReward` correctly forfeits the cooling portion back into `queuedRewards` for redistribution to full lockers.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie` with a reward token; fund two users (A, B) with equal mWOM, both lock equal amounts into `mWomSV`.
2. Queue a reward amount via `queueNewRewards`.
3. Warp time so both A and B accrue equal `earned()`.
4. User A calls `mWomSV.startUnlock(partialAmount)`, which triggers `multiclaimFor` → `getReward` → `_sendReward`.
5. Assert `calExpireForfeit(A, rewardToken)` returns `0` despite A now having a nonzero `getUserAmountInCoolDown(A)`.
6. Assert A received the exact same `toSend` amount as B would have received for the identical earned amount (i.e., no forfeit applied), proving cooldown status has zero effect on payout.
7. Confirm `queuedRewards` for the reward token is unchanged (no forfeit was queued back), showing the intended redistribution to remaining full lockers (like B) never occurs.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
