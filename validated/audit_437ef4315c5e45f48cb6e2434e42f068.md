### Title
Cached FROST preprocess seed is reused across distinct signing operations, enabling nonce reuse and private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The "use after free" bug class maps onto Serai as a *use-after-consumption* flaw: a nonce-generation seed that FROST requires to be consumed exactly once is instead stored in the database keyed only by `context` and deterministically reused for every subsequent `share`/`complete` call in that context. `preprocess_internal` writes `CachedPreprocesses` once and then regenerates the identical nonces/commitments from the same seed each time it is invoked. If the coordinator signs two different messages under the same context (e.g., `DkgConfirmer::share`/`complete` called with two different `key_pair` values within the same `attempt`), the resulting signature shares reuse the same nonces, allowing arithmetic recovery of the signer's secret share. [1](#0-0) 

### Finding Description
`SigningProtocol::preprocess_internal` encrypts and stores a `CachedPreprocess` seed in the DB under key `self.context`, then on *every* call loads the same seed and passes it to `AlgorithmSignMachine::from_cache`, which regenerates the deterministic RNG stream. [2](#0-1) 

In `AlgorithmMachine::seeded_preprocess`, the seed seeds `ChaCha20Rng` and deterministically derives `Commitments::new` — i.e., the same seed always produces the same nonces `(d, e)` and the same preprocess message. [3](#0-2) 

The seed is never deleted or rotated after use. `share_internal` calls `preprocess_internal().0` again for each signing attempt, so the identical nonces are consumed a second (third, …) time — precisely the "use after free" pattern applied to a single-use secret. [4](#0-3) 

For `DkgConfirmer`, `context = (b"DkgConfirmer", self.attempt)`, while the signed message is `set_keys_message(set, removed, key_pair)`, which varies with `key_pair`. `share()` and `complete()` both route through `share_internal`, and `complete` can be invoked after `share` already emitted a share for a different `key_pair` in the same attempt. [5](#0-4) 

FROST's own documentation states a cached preprocess "MUST only be used once. Reuse will enable third-party recovery of your private key share." [6](#0-5) 

### Impact Explanation
A FROST signature share is `s_i = d_i + (e_i · ρ_i) + λ_i · x_i · c`, where `d_i, e_i` are the secret nonces derived from the reused seed and `c` binds the message and commitment set. If two shares are emitted with the same `(d_i, e_i)` but different `c` (different `key_pair` → different message → different challenge), anyone holding both shares solves for `λ_i · x_i` and recovers the validator's MuSig/FROST secret share `x_i`. Combined with threshold-many compromised/reused shares (or for the signer's own share, a single pair suffices to expose that share), this can lead to full key recovery of the validator set key — the analog of Chrome's heap corruption escalating to code execution, here escalating to threshold key compromise.

### Likelihood Explanation
Reachability requires two shares under one context with distinct messages. In the DKG confirmation flow this occurs when `share`/`complete` are invoked with differing `key_pair` inputs for the same `attempt` (e.g., competing DKG results or a retried confirmation after the key pair changed), since the DB-cached seed is keyed only on `("DkgConfirmer", attempt)`. The seed persists across restarts because it is committed to `SigningProtocolDb`. The exposure requires no malicious validator or collusion beyond inputs an unprivileged participant can cause to be signed — the leak is in the published shares themselves. (I could not fully trace every upstream caller of `DkgConfirmer::share`/`complete` to confirm how often divergent `key_pair` values occur per attempt; the reuse primitive itself is unconditional.)

### Recommendation
- Consume-and-delete: remove `CachedPreprocesses` for `context` once `share_internal` has used it, or key the cache by a value that is unique per signed message (e.g., hash of `context || msg`) so nonces can never repeat across distinct messages.
- Alternatively, derive nonces via `Curve::random_nonce` over `seed || H(msg)` so that different messages never share a nonce even under a cached seed.
- Document and enforce in `SigningProtocol` that each cached seed corresponds to exactly one message.

### Proof of Concept
1. Within one DKG `attempt`, cause `DkgConfirmer::share(preprocesses, key_pair_A)` to emit share `s_A` for `msg_A = set_keys_message(set, removed, key_pair_A)`.
2. Cause `DkgConfirmer::share(preprocesses', key_pair_B)` (or `complete` with `key_pair_B`) to emit share `s_B` for `msg_B`, with `key_pair_B != key_pair_A`.
3. Both shares use nonces regenerated from the identical cached seed (`CachedPreprocesses[("DkgConfirmer", attempt)]`), so `d, e` are identical.
4. Compute the binding factor `ρ` and challenge `c_A`, `c_B` for each session; solve `s_A − s_B = λ·x·(c_A − c_B) + e·(ρ_A − ρ_B)` — with identical `e` and known `ρ` values, recover `λ·x`, hence the secret share `x` of that participant's MuSig key.
5. The published preprocesses are identical (same commitments), publicly confirming nonce reuse before any algebraic work is needed.

      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
