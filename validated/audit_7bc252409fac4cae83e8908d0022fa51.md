Confirmed: `calculate_priority` / `calculate_priority_and_cost` in `core/src/transaction_priority.rs` computes priority purely from fee/cost (`reward.saturating_mul(MULTIPLIER).saturating_div(cost + 1)`) — it never checks `recent_blockhash` age, nonce validity, or any remaining-validity/TTL of the transaction. That priority is what `forwarding_stage.rs` uses to admit/evict packets from its bounded `PacketContainer`, with no blockhash-age gate before insertion.

### Title
Forwarding-stage `PacketContainer` accepts and evicts on fee-only priority with no blockhash-validity floor, letting near-expired high-fee transactions permanently displace valid forwardable transactions - (File: core/src/forwarding_stage.rs)

### Summary
`ForwardingStage::buffer_packet_batches` (`core/src/forwarding_stage.rs:270-336`) inserts every sanitized packet into a fixed-capacity `PacketContainer` keyed solely by `calculate_priority` (`core/src/transaction_priority.rs:32-66`), a pure fee/cost ratio. When the container is full, it evicts the current minimum-priority packet (`self.packet_container.pop_min()`, line 326) to make room for a higher-priority one. Nowhere in this path is the transaction's `recent_blockhash` age, nonce validity, or remaining processing lifetime checked — unlike `receive_and_buffer.rs`, which explicitly calls `working_bank.check_transaction_without_status_cache(..., working_bank.max_processing_age(), ...)` before buffering (`core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs:314-330`). This mirrors the audited Auction.sol flaw exactly: a "bid" (transaction) with an artificially high value (compute-unit-price) but a validity window that is already effectively exhausted (blockhash at or near `MAX_PROCESSING_AGE`, i.e. `solana_clock::MAX_RECENT_BLOCKHASHES`/`MAX_PROCESSING_AGE`) can outrank and evict a genuinely valid, lower-fee "bid" that still has ample time to land.

### Finding Description
- `buffer_packet_batches` only sanitizes the packet and computes `priority` from `calculate_priority` — a fee/cost ratio with no dependency on blockhash freshness — before deciding eviction (`core/src/forwarding_stage.rs:294-313`).
- Eviction logic: if the container `is_full()`, the packet with `min_priority` is checked against the incoming `priority`; if the incoming priority is strictly greater, the minimum-priority packet is permanently popped (`self.packet_container.pop_min()`) and discarded, and the new packet is inserted (`core/src/forwarding_stage.rs:315-334`, `core/src/forwarding_stage/packet_container.rs:19-33`).
- Nothing here validates that the incoming transaction's blockhash still has meaningful remaining life. An attacker can craft (and self-sign, at essentially zero cost since fees are only charged on execution, not on forwarding) a transaction using a blockhash that is already at the boundary of `max_processing_age` (i.e., about to fail `check_age`/`check_transaction_without_status_cache` at the leader) combined with an inflated `compute_unit_price`, producing a very high `calculate_priority_and_cost` value.
- Because the eviction decision compares only these fee-derived priorities, this "already-expiring" transaction beats and evicts a legitimate lower-fee transaction that is still comfortably within its validity window and would have landed if forwarded.
- The evicted legitimate packet is unrecoverable — `pop_min` removes it from the heap entirely (`core/src/forwarding_stage/packet_container.rs:27-29`), it is never resent by the forwarding stage.
- The attacker's transaction, once actually forwarded to and processed by the leader, is rejected on the age check (`runtime/src/bank/check_transactions.rs`), so it "expires immediately" just like the auction bid with a 1-second valid time — it never executes and the attacker pays nothing, while the honest user's transaction is gone.

### Impact Explanation
This is a non-RPC remote degradation/exhaustion vector against unprivileged transaction ingestion: any network sender can flood the forwarding stage with cheap-to-produce, "sacrificial" high-fee/near-expired transactions to selectively evict genuinely valid, fee-paying transactions from the bounded forwarding buffer (`PacketContainer::with_capacity(4 * 4096)`, `core/src/forwarding_stage.rs:218`). This causes legitimate transactions to be dropped/never forwarded, degrading transaction inclusion fairness and availability without costing the attacker any lamports (since the sacrificial transactions never execute). It does not directly steal funds or halt consensus, but it is a real, unauthenticated griefing/DoS primitive analogous to the reported auction bug.

### Likelihood Explanation
Likelihood is credible but bounded: an attacker must be able to produce many sanitizable, well-formed transactions (fee payer must pass `initial_packet_meta_filter`/sanitization, but does not need funds beyond having a valid signer since fees are never deducted for non-executed transactions) with maximized `compute_unit_price` and a blockhash chosen at the edge of validity. This requires no special privileges, no malicious peer/validator assumption, and no trust relationship — only ordinary TPU packet submission that reaches the forwarding stage.

### Recommendation
Before accepting a packet into `PacketContainer` or using it in the min-priority eviction comparison, `ForwardingStage::buffer_packet_batches` should verify the transaction's blockhash/nonce still has a minimum remaining validity margin (e.g., reject or de-prioritize transactions whose blockhash age already exceeds `max_processing_age().saturating_sub(MAX_TRANSACTION_FORWARDING_DELAY)`, the same margin already used in `Bank::check_transactions_with_forwarding_delay`, `runtime/src/bank/check_transactions.rs:28-51`). This prevents fee-inflated but effectively-already-expired transactions from displacing genuinely forwardable ones.

### Proof of Concept
1. Attacker crafts transaction `T_bad`: `recent_blockhash` = a hash whose age is already at/near `max_processing_age` (so it will fail the leader's age check within one forwarding round-trip), `compute_unit_price` set very high to maximize `calculate_priority_and_cost` (`core/src/transaction_priority.rs:32-66`).
2. Attacker sends a burst of such `T_bad` transactions to the forwarding stage's TPU-forward endpoint faster than the container drains.
3. In `buffer_packet_batches` (`core/src/forwarding_stage.rs:315-334`), each `T_bad` has priority higher than the current `min_priority` entries (genuine, lower-fee, but still-valid user transactions `T_good`), so each `T_bad` insertion triggers `pop_min()`, evicting a `T_good`.
4. `T_good` transactions are permanently discarded and never forwarded/land.
5. When `T_bad` transactions are eventually forwarded and reach the leader's `check_transactions`/`check_transaction_without_status_cache` (`runtime/src/bank/check_transactions.rs`), they fail the age check and are rejected — the attacker paid nothing, while honest users' transactions were silently lost from the forwarding buffer.

Note: I could not execute this scenario against a running validator/testnet from this static analysis; verification of exact timing windows (how close to `max_processing_age` a blockhash must be to reliably "expire" before landing, given forwarding delay `MAX_TRANSACTION_FORWARDING_DELAY`) would require dynamic testing, which is out of scope for this read-only review.
