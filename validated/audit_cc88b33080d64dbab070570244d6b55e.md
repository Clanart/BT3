## Finding

**Analog to the report's bug class:** two sibling code paths handle the *same* untrusted input (a conflicted file's repo-relative path during merge/rebase/cherry-pick), but only one of them enforces the safety check — exactly like `withdraw` enforcing the locking check while `emergencyWithdraw` (same "withdraw" operation) omits it.

### Title
Path-traversal/symlink-escape guard missing in `getResolutionDiff` while present in the sibling `buildConflictContext` for the same conflicted-file input - (File: app/src/lib/git/diff.ts)

### Summary
`app/src/lib/git/diff.ts#getResolutionDiff` reads a conflicted file straight off disk with `Path.join(repository.path, filePath)` and no traversal/symlink check, whereas the sibling function that consumes the exact same kind of input — conflicted-file paths surfaced during a merge/rebase/cherry-pick for GitHub Desktop's Copilot conflict-resolution feature — `app/src/lib/copilot-conflict-context.ts#buildConflictContext`, explicitly resolves the path with `resolveWithin()` and rejects it if it escapes the working directory or is a symlink pointing outside the repo.

### Finding Description
`buildConflictContext` treats conflicted-file paths as untrusted and defends against traversal/symlink escape: [1](#0-0) 

`getResolutionDiff`, used by the same Copilot merge-conflict-resolution UI flow (`copilot-conflicts-changes.tsx`) to build the "ours/theirs/Copilot" diff preview for a conflicted file, instead joins the path directly and reads it with no equivalent guard: [2](#0-1) 

Both functions are fed the same class of value: a file path taken from the set of files reported as conflicted during a merge/rebase/cherry-pick. That value is effectively attacker-influenced — a crafted upstream branch/PR can produce a conflict whose path component is chosen by the attacker (e.g. via `git mv`/renames in the incoming history) and, if a pre-existing tracked entry at that path in the victim's working tree is (or can be made) a symlink pointing outside the repository, `Path.join(repository.path, filePath)` will happily follow the symlink out of the repo when `getResolutionDiff` calls `readFile()` on it. `buildConflictContext`'s own doc comment ("Guard against path traversal and symlink escapes (cross-platform)") shows the maintainers recognize this exact risk class for conflicted-file paths — but the guard was not applied consistently to the sibling diff-building code path.

### Impact Explanation
If reachable with a symlinked conflict path, `getResolutionDiff` would read (`baseContent`) and potentially display the contents of a file outside the repository (e.g. `~/.ssh/id_rsa`, credential files, or other sensitive host files) inside the Copilot conflict-resolution diff view, and could also write that content into a temp file (`tempBase`) as part of the `git diff --no-index` invocation. This is a file-read outside the repo, which for a git client can lead to credential/secret disclosure to the on-screen diff UI (and to whatever process consumes it) — matching the impact bar (file read outside the repo).

### Likelihood Explanation
This requires: (1) a conflict to be produced by merging/rebasing/cherry-picking attacker-controlled history against a path that is a symlink in the victim's working tree, and (2) the user to open the Copilot conflict-resolution diff view for that file. Confirming exploitability fully would require tracing how `filePath` is populated before being passed to `getResolutionDiff` from `copilot-conflicts-changes.tsx`, which I was not able to fully verify with the available index (the component file's content was not returned in full). This is stated as an open uncertainty.

### Recommendation
Apply the same `resolveWithin()` guard used in `buildConflictContext` to `getResolutionDiff` (and audit other direct `Path.join(repository.path, file.path)` + `readFile` call sites such as `getWorkingDirectoryImage`, `app/src/lib/git/diff.ts:930`) before reading conflicted/working-directory file paths from disk.

### Proof of Concept
Conceptual PoC (unverified end-to-end due to index limits on `copilot-conflicts-changes.tsx`):
1. In a victim repo, have a tracked file `foo` become a symlink to `/Users/victim/.ssh` (via a normal commit, or preexisting state).
2. An attacker-supplied branch/PR modifies `foo` differently, causing a merge conflict at path `foo` when merged/rebased by the victim.
3. Victim opens Copilot's conflict-resolution dialog and views the diff for `foo`; `getResolutionDiff(repository, 'foo', ...)` executes `readFile(Path.join(repository.path, 'foo'), 'utf8')`, which follows the symlink and reads outside the repository, unlike `buildConflictContext`, which would reject the same path via `resolveWithin`.
