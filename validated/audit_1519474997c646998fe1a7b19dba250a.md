## Finding

I traced the report's core invariant — *a function that's supposed to validate/bound a value fails to do so, and that unguarded function feeds directly into a security-relevant decision* — to a concrete local analog in the object-ownership code that gates code-object publishing and lazy module self-initialization.

### Title
Unbounded object-ownership traversal in `root_owner` allows permanent DoS of code-object publish/upgrade and lazy module self-init - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`Object::root_owner` walks the object ownership chain with no depth bound, unlike its sibling functions `owns` and `verify_ungated_and_descendant`, which both cap traversal at `MAXIMUM_OBJECT_NESTING`. `root_owner` is now a load-bearing part of the publish-path: `code::publish_package` calls it to record the "deploy owner" used to gate lazy module self-initialization (`init::assert_may_self_initialize`). If an object address ends up in an ownership cycle, every future call into this path infinite-loops until gas exhaustion, permanently bricking publish/upgrade and self-init for that code object.

### Finding Description
`root_owner` [1](#0-0)  has no loop bound:
```
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```
Compare this with `owns` [2](#0-1)  and `verify_ungated_and_descendant` [3](#0-2) , both of which explicitly bound the same kind of walk with `count < MAXIMUM_OBJECT_NESTING`.

`root_owner` is used by `code::publish_package` to compute and record the "deploy owner" for every module in a package deployed to an object, whenever lazy module initialization is enabled: [4](#0-3) . That recorded value is later re-derived via `root_owner` again in `init::assert_may_self_initialize` to gate whether a module hosted on that object may mint its own signer: [5](#0-4) .

Ownership cycles among objects are constructible: `transfer_raw` only verifies that the caller is a (bounded) ancestor of the object being moved — via `verify_ungated_and_descendant` — it never checks that the destination is not itself a descendant of the object [6](#0-5) . Anyone controlling two objects A and B can: (1) transfer A to B, then (2) transfer B to A (still authorized, since B's current owner hasn't changed yet), producing `A.owner == B` and `B.owner == A`. Once either A or B hosts a package under lazy module initialization, any subsequent `code::publish_package` (upgrade) or `init::internal_maybe_initialize` call on that address invokes the unbounded `root_owner` loop and never terminates cleanly — it runs until the transaction exhausts its gas budget and aborts.

### Impact Explanation
This breaks a code-safety invariant of the publish/init path: legitimate operations (`object_code_deployment::upgrade`, `code::freeze_code_object`, and any lazy self-init call) on an object caught in such a cycle can no longer complete, because every attempt burns gas without reaching a stable owner and aborts. This is an availability failure inside the exact machinery this codebase added to gate object-hosted module publish/init ownership (`init::assert_may_self_initialize`, `code::publish_package`'s deploy-owner recording) — i.e., a "module-init/native-validation/write-set-publish failure that reaches protected state mutation," matching the Publish Impact Gate. The affected code object is effectively bricked for upgrade and self-init without ever going through the sanctioned `freeze_code_object` authorization flow, and there is no unfreeze/recovery function for accidental or malicious freezing of this kind (mirroring the module's own note that "there is no unfreeze function").

### Likelihood Explanation
Exploitability depends on getting the code object's address into a cyclic ownership relationship, which requires control (directly or via a composable contract with delegated transfer authority) over both objects in the cycle. This is plausible in escrow/marketplace/composable-object patterns where a contract is granted transfer rights over multiple objects it manages, but it is not a trivial single-transaction attack against an arbitrary victim's account. I could not fully verify whether any existing framework module (e.g., marketplace/escrow helpers) grants this kind of unchecked bidirectional transfer authority in a way reachable by an unprivileged attacker against a victim's object; that would need further investigation to establish a fully unprivileged, remote-attacker path rather than a self-inflicted or cooperating-contract scenario.

### Recommendation
Bound `root_owner`'s traversal the same way `owns` and `verify_ungated_and_descendant` are bounded, e.g.:
```
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    let count = 0;
    while (is_object(obj_owner)) {
        count += 1;
        assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```
Additionally, consider whether `transfer_raw`/`verify_ungated_and_descendant` should reject transfers that would introduce a cycle at all, rather than only relying on downstream consumers of `root_owner` to survive one.

### Proof of Concept
1. Create two objects `A` and `B` under the same signer, each with `allow_ungated_transfer = true`.
2. Deploy a package with lazy module initialization enabled to object `A` (so `code::publish_package` records a deploy owner via `root_owner`).
3. Call `object::transfer_call(signer, A, B)` — allowed, since signer is A's current owner.
4. Call `object::transfer_call(signer, B, A)` — allowed, since signer is still B's current owner (unaffected by step 3); this makes `A.owner == B` and `B.owner == A`, a cycle.
5. Attempt `object_code_deployment::upgrade` (or any lazy self-init entry function) on a module hosted at `A`. The internal `root_owner(A)` call loops `A -> B -> A -> B -> ...` indefinitely, exhausting the gas budget and aborting the transaction — the object is now permanently unable to complete publish/upgrade or self-init.     /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(

                return false
            };

            current_address = object.owner;
        };
        true
    }
