### Title
`ThresholdKeys::read` deserializes attacker-set fields without consistency checks, letting crafted bytes set an arbitrary `group_key` and mismatched `secret_share` — (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to CVE-2022-2200 (corrupted object prototype lets an attacker set undesired attributes on an object, producing privileged effects), `ThresholdKeys::read` reconstructs a key object entirely from untrusted bytes — `t`, `n`, `i`, the interpolation vector, `secret_share`, and all `n` `verification_shares` — and `ThresholdKeys::new` validates only shape (counts, index bounds, `t == n` for `Constant`), never that `verification_shares[i] == G * secret_share` nor that the shares lie on a common polynomial. The object is therefore "corrupt": its public-facing attribute (`group_key`) is derived from attacker-chosen verification shares while its privileged attribute (`secret_share`) is unrelated.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, an interpolation encoding, a scalar `secret_share`, then `n` group elements as `verification_shares` keyed `1..=n` [1](#0-0) . `ThresholdKeys::new` checks only that the map has `n` entries with indexes `<= n`, and computes `group_key` by Lagrange-interpolating `verification_shares[1..=t]` [2](#0-1) . Nothing ties `secret_share` to `verification_shares[i]` or to the other shares. The signing path then trusts both halves independently: `view()` interpolates `secret_share` into the signing share and interpolates `verification_shares` into per-signer verification shares [3](#0-2) , and `complete()` verifies the aggregate signature against `view.group_key()` [4](#0-3) , falling back to per-share blame which will finger the victim's own share as `InvalidShare` [5](#0-4)  — the code itself acknowledges this reachability ("deserialize a semantically invalid FrostKeys") at [6](#0-5) .

### Impact Explanation
An unprivileged party who can supply serialized `ThresholdKeys` bytes (a corrupted/attacker-written key file, DB row, or message consumed via `ThresholdKeys::read`) sets two "attributes" that were never meant to be independent:
- `group_key` becomes a fully attacker-chosen point. If the integrator uses `group_key()`/`view.group_key()` as a deposit address or identity, funds are directed to a key the attacker selected — including one constructed from shares the attacker fully knows (consistent shares under attacker-chosen scalars yield a key whose secret the attacker holds), i.e. funds "received" are spendable only by the attacker.
- Alternatively, a `secret_share` inconsistent with the verification shares causes every signing session to fail aggregate verification and emit `InvalidShare(i)` blame against the honest holder of the poisoned keys — a forgeable-fault signal that downstream slash/blame handling treats as the victim's misbehavior.

### Likelihood Explanation
Reachability requires an attacker to control bytes fed to `ThresholdKeys::read`; within the threat model this covers untrusted stored/transmitted key material. The exploit needs no collusion, no malformed curve points (`read_F`/`read_G` canonical checks are unchanged), and no protocol round — only syntactically valid, semantically corrupt fields, exactly the "undesired attributes on an object" primitive of the reference CVE. It is at least Medium; High if an integrator loads key material from a less-trusted store, since it converts to theft of deposits addressed to `group_key`.

### Recommendation
In `ThresholdKeys::new` (or at least in `ThresholdKeys::read`), enforce consistency: require `verification_shares[params.i()] == C::generator() * secret_share`, and reject keys where this fails. Optionally also spot-check that `verification_shares` are mutually consistent with a degree-`t-1` polynomial (e.g., verify a random linear combination or require dealer/PedPoP-derived provenance rather than raw deserialization for key loading), and document that `read` is only for trusted, self-produced serializations.

### Proof of Concept
1. Attacker chooses arbitrary scalar `k` and sets `verification_shares[j] = C::generator() * (k * L_j)` for `j = 1..=n` where `L_j` are Lagrange evaluations making the `1..=t` interpolation equal `k` — or simply picks any `n` points whose `1..=t` Lagrange sum is a chosen `K = G*k`.
2. Attacker sets `secret_share` to a known scalar `s_1` with `G * s_1 = verification_shares[i]` (consistent variant → attacker knows the full secret of `group_key`) or to an unrelated scalar (inconsistent variant → victim's shares always fail blame).
3. Victim passes the bytes to `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574). `ThresholdParams::new(t, n, i)` and the share-count/index checks pass.
4. `group_key()` returns attacker-chosen `K`; funds sent to `K` are either attacker-controlled, or every `sign`/`complete` fails with `InvalidShare(victim_i)` blame against the honest party.
