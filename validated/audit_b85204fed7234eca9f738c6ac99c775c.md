### Title
Clawback coin is permanently marked "already pending" before its spend bundle is committed, blocking future claim/clawback attempts on the coin - (File: `chia/wallet/clawback_manager.py`)

### Summary
`ClawbackManager.spend_clawback_coins()` calls `self.transaction_store.increment_sent(incoming_tx.name, "", MempoolInclusionStatus.PENDING, None)` to mark the original incoming clawback transaction as "sent" *before* the outgoing claim/clawback spend bundle has actually been successfully assembled, signed, or pushed to the mempool. This mirrors the reported analog bug class: a status flag (`executed`/`sent`) is set prematurely, before the actual state-changing action has completed, so the system's own guard against re-execution now incorrectly reports the action as already done. [1](#0-0) 

### Finding Description
In `spend_clawback_coins()`, for each coin being claimed or clawed back, the code first checks a guard:

```
if incoming_tx.sent > 0 and not force:
    self.log.error(...)
    continue
```
and then, after building the inner puzzle/solution and constructing the `coin_spend`, calls:
```
await self.transaction_store.increment_sent(incoming_tx.name, "", MempoolInclusionStatus.PENDING, None)
``` [2](#0-1) 

This `increment_sent` call happens inside a per-coin `try` block, and the loop continues to aggregate `coin_spends` for *all* coins in the batch, but the aggregate `WalletSpendBundle` and the `TransactionRecord` describing the actual outgoing transaction are only built and appended to `action_scope.side_effects.transactions` *after* the loop finishes. If:
- an exception occurs later in the same call (e.g., in the fee/tandem-tx branch using `action_scope_sandbox`), or
- the surrounding `WalletActionScope` exits without `push=True`, or
- the process crashes/disconnects before the spend bundle is actually broadcast,

then `incoming_tx.sent` has already been durably persisted as `PENDING` (`increment_sent` calls `add_transaction_record`), while no real spend was ever pushed to the network. On any subsequent call to `spend_clawback_coins` (via `auto_claim_coins` or the RPC endpoint `spend_clawback_coins`), the guard `if incoming_tx.sent > 0 and not force` now silently skips that coin, exactly like the referenced bug where `executed` was set `true` before the real execution occurred, causing `state()` to report `Executed` prematurely and blocking legitimate future execution. [3](#0-2)  shows the RPC surface (`spend_clawback_coins`) that any wallet client/RPC caller can invoke, and `auto_claim_coins` shows the same manager method is invoked automatically for auto-claim [4](#0-3) .

### Impact Explanation
A clawback (timelocked, sender/recipient re-assignable) coin's legitimate claim or claw-back can become silently stuck: the wallet believes the coin is already "in flight" (`sent > 0`) although no spend was actually broadcast/confirmed on chain. Funds locked in the clawback puzzle remain unspendable by the wallet's normal auto-claim and RPC paths until a user manually notices and re-issues the same RPC call with `force=True`. Because clawback coins secure real value transferred as a locked, recoverable state (sender/recipient can later claim/claw back), a false-positive "pending" mark can cause funds to appear frozen and the automatic reclaim mechanism (`auto_claim_coins`) to never retry, since `force` is not set in the auto-claim path. [5](#0-4) 

Unlike the original GovernorBravo bug (which makes execution *permanently* impossible), the wallet exposes a `force: bool` field on the RPC request that bypasses the guard and lets the caller retry. [6](#0-5)  This materially reduces severity relative to the reported bug: the block is not unconditional, and a user/wallet operator can escape it by explicitly forcing the spend.

### Likelihood Explanation
Likelihood is moderate: the condition requires a failure or non-push scenario to occur strictly between the `increment_sent` call and successful confirmation/broadcast (e.g., process crash, an unhandled exception in the fee/tandem-tx path, or a caller building an unsigned/`push=False` transaction and never following up). Because `spend_clawback_coins` is reachable via a standard wallet RPC call and via automatic background auto-claim, an unprivileged wallet user could trigger this state without any malicious peer, purely from ordinary interruptions (e.g., an RPC-issued `push=False` request that never gets separately pushed, or an exception thrown mid-batch for the fee code path while a `force=False` retry is later attempted by auto-claim).

### Recommendation
Only mark the incoming transaction as `sent`/`PENDING` after the outgoing spend bundle transaction record has been finalized and successfully staged for push (i.e., alongside/after `interface.side_effects.transactions.append(tx_record)` at the end of `spend_clawback_coins`), or make `increment_sent` conditional on a successful `action_scope` exit/push. At minimum, ensure any exception path that aborts the transaction also resets `incoming_tx.sent` back to its previous value (e.g., via `tx_reorged`-style rollback) so the "already pending" guard cannot outlive an actual failed/unpushed spend attempt.

### Proof of Concept
1. Send a clawback-style transaction from wallet A to wallet B (`clawback_time` set), then wait for confirmation, so wallet B has an incoming clawback coin with a corresponding `incoming_tx` record.
2. From wallet B, call the `spend_clawback_coins` RPC with `fee > 0` and force an exception in the fee/tandem-tx path (e.g., by supplying a fee amount with insufficient available coins to fund the tandem transaction after `increment_sent` already executed) — per the code, `increment_sent` runs per-coin in the earlier loop before the `if fee > 0` block that constructs the tandem fee transaction. [7](#0-6) 
3. Observe that `incoming_tx.sent` is now `PENDING` in the transaction store even though the overall call raised/aborted before the final `tx_record` was appended and no spend bundle was ever pushed.
4. Call `spend_clawback_coins` again with `force=False` (the default, as used in `auto_claim_coins`) for the same coin: the loop's guard `if incoming_tx.sent > 0 and not force: continue` causes the coin to be silently skipped, reproducing the "operation permanently blocked by a prematurely set status flag" bug class from the report. [8](#0-7)

    async def spend_clawback_coins(
        self,
        request: SpendClawbackCoins,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> SpendClawbackCoinsResponse:
        """Spend clawback coins that were sent (to claw them back) or received (to claim them).

        :param coin_ids: list of coin ids to be spent
        :param batch_size: number of coins to spend per bundle
        :param fee: transaction fee in mojos
        :return:
        """
        coin_records = await self.service.wallet_state_manager.coin_store.get_coin_records(
            coin_id_filter=HashFilter.include(request.coin_ids),
            coin_type=CoinType.CLAWBACK,
            wallet_type=WalletType.STANDARD_WALLET,
            spent_range=UInt32Range(stop=uint32(0)),
        )

        batch_size = (
            request.batch_size
            if request.batch_size is not None
            else self.service.wallet_state_manager.clawback_manager.auto_claim_batch_size
        )
        records_list = list(coin_records.coin_id_to_record.values())
        for i in range(0, len(records_list), batch_size):
            try:
                coin_batch = {
                    coin_record.coin: coin_record.parsed_metadata() for coin_record in records_list[i : i + batch_size]
                }
            except WalletCoinRecordMetadataParsingError as e:
                log.error("Failed to spend clawback coin: %s", e)
                continue
            await self.service.wallet_state_manager.clawback_manager.spend_clawback_coins(
                # Semantically, we're guaranteed the right type here, but the typing isn't there
                coin_batch,  # type: ignore[arg-type]
                request.fee,
                action_scope,
                request.force,
                extra_conditions=extra_conditions,
            )
