## Analysis

The `StHEU` bug is about `totalHEU * 1e18 / totalSupply` truncating to zero when the numerator is small relative to the denominator, silently zeroing out a legitimate payout while internal accounting still advances. The Hyperbridge repo has a structurally identical truncating-division payout inside `IntrinsicIntents._fillSameChain`, in the escrow-release calculation for **intermediate** partial fills.

### Title
Truncating division on intermediate partial fills can zero out a solver's escrow payout while state still advances - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` computes the input-side escrow released to a solver on a partial fill as `order.inputs[i].amount * fillAmount / totalRequired` [1](#0-0) . This integer division truncates toward zero. The codebase's own test suite documents and fixes truncation *only for the final fill that completes an order*, by releasing the full remaining `_orders[...]` balance instead of the proportional (truncated) share [2](#0-1) . That fix does not cover non-final partial fills: any partial fill for which `order.inputs[i].amount * fillAmount < totalRequired` yields `escrowedAmount == 0`, while the solver has already sent real, non-rounded output tokens (`fillAmount`, `beneficiaryTotal`) to the beneficiary and `_partialFills[commitment][outputToken]` has been permanently advanced by that same `fillAmount` [3](#0-2) .

### Finding Description
In `_fillSameChain`, for each output asset index `i`:
- `fillAmount` is derived from the solver-supplied `solverAmount` and is not rounded — it is transferred to the beneficiary as `beneficiaryTotal = fillAmount + beneficiaryShare` via `safeTransferFrom`/native transfer [4](#0-3) .
- The corresponding escrow released back to the solver, `escrowedAmount`, is only computed via the proportional formula when the fill does **not** complete the order (`amountFilled != totalRequired`): `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` [1](#0-0) .
- If `order.inputs[i].amount` is small relative to `totalRequired` (e.g. the order's input token has few decimals or a small total amount, while the output requirement is large), any `fillAmount` satisfying `order.inputs[i].amount * fillAmount < totalRequired` truncates `escrowedAmount` to `0`.
- `_withdraw` is then called with `escrowedInputs[i].amount == 0`; the loop in `_withdraw` explicitly `continue`s on `amount == 0` without decrementing `_orders` and without transferring anything to the solver [5](#0-4) .
- Critically, `_partialFills[commitment][outputToken]` was already incremented by the *full, non-truncated* `fillAmount` before this check [6](#0-5) , and the solver already paid the beneficiary the full `fillAmount` of real output tokens.

The net effect: the solver's proportional share of escrow for that fill is truncated to zero and effectively absorbed into the contract's `_orders` balance rather than being paid to the filling solver — the same "rounds to zero, payout denied" pattern as the reported `StHEU` bug, except here the truncated share is not merely undistributed but is actually consumed/paid by a real token transfer that receives no offsetting release.

A malicious order creator can deliberately engineer this: place an order where `order.inputs[i].amount` is tiny relative to `order.output.assets[i].amount` (a valid, unrestricted order shape — nothing in `placeOrder`/`_validateParams` bounds the input/output ratio). Any solver attempting a partial fill below the rounding threshold sends real tokens to the beneficiary and is paid zero escrow for that fill, while the accounting (`_partialFills`) still records the fill as consumed. This is a pure logic/arithmetic flaw reachable by any unprivileged solver interacting with an adversarially-shaped, otherwise valid order — no relayer, prover, or admin involvement required.

### Impact Explanation
This falls under "logic attacks" / "loss of funds" in the bounty scope: an unprivileged solver can lose real, transferred output-token value with zero compensating input-token release, and that lost value is not refunded to the solver — it stays escrowed under the order and can only ever be reclaimed by the user (via cancel) or a different, later solver who happens to complete the order, never by the solver who actually paid for that increment of `_partialFills`. This is a genuine fund-loss / misdirected-payout vulnerability in a production contract path (`fillOrder` → `_fillSameChain`), matching the bug class of the seed report (rounding-to-zero payout) mapped onto Hyperbridge's intent-settlement escrow accounting.

### Likelihood Explanation
Likelihood is **medium**: it requires a specific order shape (small input amount relative to output amount, or a partial fill sized just below the rounding threshold) and a solver willing to submit a sub-threshold partial fill. Solvers acting rationally would normally size fills to avoid this, but nothing in the contract prevents or warns against it, and a malicious order creator/beneficiary can shape their own order to bait naive or automated solver bots into sub-threshold fills, which is a realistic MEV-adjacent scenario given the permissionless, unrestricted `placeOrder` interface.

### Recommendation
Extend the same fix already applied to the final-fill case to all intermediate partial fills: track cumulative escrow already released per `(commitment, inputToken)` and, on each fill, release `min(proportional_share, remaining_escrow)` computed so that the *sum* of releases never truncates away real value — e.g., compute `escrowedAmount` from the delta of `(order.inputs[i].amount * amountFilled) / totalRequired` minus what has already been released, rather than `(order.inputs[i].amount * fillAmount) / totalRequired` in isolation. This guarantees rounding dust accumulates and is eventually paid out as fills progress, rather than being silently zeroed per-fill.

### Proof of Concept
1. User places an order with `inputs = [{token: USDC, amount: 1}]` (1 unit, i.e. smallest denomination) and `output.assets = [{token: DAI, amount: 1000e18}]`.
2. Solver A calls `fillOrder` with `outputs[0].amount = 500e18` (a legitimate 50% partial fill): `fillAmount = 500e18`, `totalRequired = 1000e18`.
3. `escrowedAmount = (1 * 500e18) / 1000e18 = 0` (truncated).
4. Solver A's `beneficiaryTotal = 500e18` DAI is transferred out of Solver A's wallet to the beneficiary.
5. `_withdraw` is called with `amount == 0` for the USDC leg; it `continue`s — Solver A receives 0 USDC.
6. `_partialFills[commitment][DAI]` is now `500e18`, i.e., 50% "consumed," yet the 1-unit USDC escrow is untouched in `_orders`.
7. Solver A has paid 500 DAI and received nothing in return; the escrowed USDC unit remains locked, available only to whoever fills the remaining 50% (via the final-fill full-balance-release branch) or to the user on cancellation — never refunded to Solver A. [7](#0-6) [8](#0-7)
