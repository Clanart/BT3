### Title
`SchnorrAggregate::verify` accepts a forged signature over an empty signer set because it checks `Rs.len() == keys.len()` without requiring the set to be non-empty - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The audited bug: `unlock` reverts when `STAKER_DISTRIBUTION_POOL.getTotalUnits() == 0`, checking only the dependent value (`totalUnits`) and not the governing parameter (`stakerAllocationBP`, which may legitimately be `0`). The Serai analog lives in the half-aggregation verifier: `SchnorrAggregate::verify` gates validity on a dependent equality — the signature's `Rs` count matching the provided `keys_and_challenges` count — and never checks the governing condition, i.e. that the statement set being verified is actually non-empty. When both are zero the multiexp reduces to `-s·G == 0`, so an attacker who controls the aggregate bytes and causes verification against an empty key list produces a forged, "valid" aggregate signature. Meanwhile `SchnorrAggregator::complete` refuses to *produce* an empty aggregate, so the verifier accepts a class of signatures the honest aggregation path explicitly rejects — the same asymmetric-guard shape as the locker bug.

### Finding Description
`SchnorrAggregate::read` accepts a length-prefixed `Rs` vector of any size, including zero, followed by `s` (`crypto/schnorr/src/aggregate.rs:77-88`). `verify` then only enforces `self.Rs.len() == keys_and_challenges.len()` (`aggregate.rs:128-130`) and constructs `2*n + 1` multiexp pairs (`aggregate.rs:138-144`). With `n == 0`, the loop appends nothing and the only remaining pair is `(-self.s, G)`; verification succeeds iff `s == 0`. The weight derivation (`weight`, `aggregate.rs:22-65`) and the `"signatures"` domain separation offer no constraint when no challenge is ever appended to the digest — `digest` is built but never consumed. An attacker serializes `u32 len = 0 || F::ZERO`, calls `SchnorrAggregate::read`, and obtains a signature that returns `true` from `verify(dst, &[])`.

`SchnorrAggregator::complete` demonstrates the protocol intends empty aggregates to be meaningless: it returns `None` when `self.sigs.is_empty()` (`aggregate.rs:175-178`). The verify path lacks the corresponding check, exactly like the locker checking `totalUnits == 0` without consulting the allocation that determines whether zero units is legitimate. Here the verifier checks the count-equality proxy (`totalUnits`) rather than the controlling fact that there is at least one signer (`allocation > 0` / non-empty statement set). The same vacuous-verification pattern exists in `BatchVerifier::verify`/`verify_vartime`, which return `true` on an empty queue since `multiexp([]).is_identity()` (`crypto/multiexp/src/batch.rs:93-101`), though callers there are responsible for queueing.

### Impact Explanation
Any caller that routes attacker-controlled bytes through `SchnorrAggregate::read` into `verify` — an in-scope untrusted-bytes-to-verify path — can present a signature that verifies against an empty signer set. If an integrating system derives the key/challenge list from the same attacker-controlled context that yielded zero signers (e.g., an empty claim set in an aggregation-based consensus or multisig wrapper), the forged `(len=0, s=0)` aggregate is accepted as proof that "the signers" authorized a message, when no key signed anything. This is a forged signature accepted by the verifier — a Medium severity: it requires the caller to verify against an empty list, but the verifier gives no signal that it has vacuously succeeded, and the honest aggregation API (`complete → None`) signals the developers considered empty aggregates invalid.

### Likelihood Explanation
Reachability requires a caller to invoke `verify` with an empty `keys_and_challenges` slice alongside attacker-controlled aggregate bytes — plausible wherever the signer set is computed dynamically (filtered validator lists, claim-derived signer sets, retry paths with zero participants). Within the audited in-scope surface (`SchnorrAggregate::read` + `verify`), the primitive itself is fully attacker-reachable; the residual condition is on the integrator's key list being empty, which is precisely the edge case the report's bug class targets — a state that is legitimate yet mishandled by the guard. This keeps it at Medium rather than High.

### Recommendation
Mirror the audited fix — check the governing condition, not just the derived metric. In `SchnorrAggregate::verify` (`crypto/schnorr/src/aggregate.rs:127`), reject empty statement sets:

```rust
if keys_and_challenges.is_empty() || self.Rs.len() != keys_and_challenges.len() {
  return false;
}
```

Optionally also require `self.s != C::F::ZERO` is not needed once non-emptiness is enforced, since at least one `z·R + z·c·key` term then binds the equation. Consider a defensive `debug_assert!`/`false` for empty `BatchVerifier`s in `crypto/multiexp/src/batch.rs:93` for the same reason, and document on `verify` that a non-empty signer set is a precondition.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::{Ciphersuite, group::ff::Field};
use schnorr::aggregate::SchnorrAggregate;
use frost::curve::Ristretto;

// Attacker-controlled bytes: zero Rs, s = 0
let mut bytes = vec![];
bytes.extend(0u32.to_le_bytes());            // len = 0
bytes.extend(<Ristretto as Ciphersuite>::F::ZERO.to_repr());

let agg = SchnorrAggregate::<Ristretto>::read(&mut Cursor::new(bytes)).unwrap();
// Verifies against an empty signer/challenge set — no key signed anything
assert!(agg.verify(b"any-dst", &[]));

// Honest aggregation refuses to produce this:
// SchnorrAggregator::<Ristretto>::new(b"any-dst").complete() == None
```
