Found the analog in `pallet-collator-manager`'s `new_session` selection logic, which burns each newly-selected collator's Reputation Asset balance to zero as part of the SessionManager hook — structurally the same "checkpoint reset without settling pending accrual" pattern as the SuperDCA bug, except here the "reward index" is the Reputation Asset balance itself and the "settlement" that must have already happened first is minting from `pallet-messaging-incentives` / `pallet-consensus-incentives` / `pallet-beefy-consensus-proofs` for the current session's activity.

### Title
Collator reputation burn in `new_session` can race and wipe reputation minted for the same session, distorting collator selection - (File: `modules/pallets/collator-manager/src/lib.rs`)

### Summary
`SessionManager::new_session` ranks candidates by `T::ReputationAsset::balance(&controller)` and then, for every account selected into `new_set`, unconditionally burns that account's *entire current* Reputation Asset balance via `T::ReputationAsset::burn_from(account_id, balance, ...)`. `balance` is re-read at burn time [1](#0-0) , not the balance that was used to rank the candidate a few lines earlier [2](#0-1) . This is the same "checkpoint/index gets reset to the live value instead of the value that was actually settled" shape as the SuperDCA bug: any reputation minted between the ranking read and the burn (or, more importantly, any reputation minted by the *same block's* relayer/prover reward pallets that also execute around session boundaries) is destroyed with no attribution, and the controller's future reputation trajectory silently loses that increment.

### Finding Description
`new_session` does three passes over `ReputationAsset::balance`:
1. Build `candidates` sorted by `T::ReputationAsset::balance(&controller_account)` [3](#0-2) .
2. Pick the top `desired_collators` into `new_set`.
3. For each account in `new_set`, re-read `T::ReputationAsset::balance(account_id)` and burn all of it: `T::ReputationAsset::burn_from(account_id, balance, Preservation::Expendable, Precision::Exact, Fortitude::Polite)` [1](#0-0) .

Reputation is minted by three independent, unprivileged-triggered pallets whenever a relayer/prover submits a valid message, consensus proof, or BEEFY proof: `pallet-messaging-incentives`, `pallet-consensus-incentives` (`T::ReputationAsset::mint_into` in `process_message`) [4](#0-3) , and `pallet-beefy-consensus-proofs` (`T::ReputationAsset::mint_into` in `pay_position_reward`) [5](#0-4) . Because minting happens via ordinary unsigned/signed extrinsics processed in normal block order, and `new_session` runs at a session-boundary block as part of `pallet_session`'s block-initialization hooks, any of these reward extrinsics that land in the same block as (and before) the session rotation will mint reputation that is immediately wiped by the burn in step 3 without ever being counted toward that controller's selection weight for the *next* session, and with no event correlating the burn amount to "how much was earned this session" versus "how much just got minted this block before rotation." The burn always takes `balance` at burn time, not the value used for ranking, so the two reads are inherently inconsistent whenever any mint lands between them — the pallet has no lock or snapshot mechanism to bind ranking and burning to the same reputation figure.

### Impact Explanation
This does not (from local code alone) let an attacker steal `$BRIDGE` or reroute funds directly, but it does cause silent, unauthorized loss of the reputation asset that gates access to a privileged, revenue-generating role (Collator block-authoring rewards, `0.7 $BRIDGE` per block) [6](#0-5) . A relayer/prover whose reward-earning extrinsic lands in the same session-rotation block loses that reputation increment permanently and without an on-chain accounting trail distinguishing "burned because selected" from "burned before it could even count," which can distort collator selection fairness (the resettlement-eligibility invariant analogous to the SuperDCA bucket's `delta`). Because reputation is non-transferable and the sole selection metric, this is a logic/accounting defect in a production pallet governing block-producer selection, not merely cosmetic.

### Likelihood Explanation
The trigger condition — a reward-minting extrinsic (from any of three independently-running, permissionless-to-trigger incentive pallets) landing in the same block that also executes `new_session` — occurs naturally on every session rotation whenever relayer/prover activity coincides with the boundary; no malicious relayer/prover/admin coordination is required, only ordinary operation timing, so this is a normal, unprivileged-triggerable event rather than a contrived one.

### Recommendation
Snapshot the balance used for ranking (`candidates`) and reuse that exact snapshotted value for the burn in the same pass, rather than re-reading `T::ReputationAsset::balance` a second time; alternatively, cap the burn at the ranking-time value and leave any excess (minted after ranking) untouched so activity is never destroyed without being counted toward some session's selection.

### Proof of Concept
Not independently reproduced in a test; conceptually: (1) queue a `pallet-consensus-incentives::process_message` or `pallet-beefy-consensus-proofs::submit_proof` extrinsic that mints reputation to controller `C`; (2) have it execute in the same block where `new_session` fires (session boundary); (3) observe `new_session` ranks candidates using pre-mint balance, but its subsequent `ReputationReset` burn (via `burn_from`) removes the post-mint balance, i.e., the reputation earned for that block is discarded with `ReputationReset { who: C, amount: balance }` reflecting a value never used for selection weighting [7](#0-6) .

**Confidence caveat**: I was not able to fully verify the exact ordering of `pallet_session`'s session-boundary hook execution relative to other pallets' extrinsics within the same block from local code alone (that depends on runtime `construct_runtime!` pallet ordering and `on_initialize`/extrinsic-application sequencing, which I could not locate/confirm in this pass). This finding should be treated as a plausible, code-supported accounting inconsistency rather than a confirmed, exploitable double-loss with a concrete transaction ordering PoC.
