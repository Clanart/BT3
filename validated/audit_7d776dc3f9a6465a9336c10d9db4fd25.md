### Title
Ungated, unmetered `DeleteAll`/`PurgePrefix` bulk-delete on EVM account storage clearing can stall block execution — (File: `sei-cosmos/store/gaskv/store.go`)

### Summary
`gaskv.Store.DeleteAll` bypasses the gas meter that every other KVStore operation (`Get`, `Set`, `Delete`, `Iterator`) goes through, and is the primitive used by `Keeper.PurgePrefix`, which is invoked from `clearAccountState` when an EVM contract self-destructs in the same transaction it was created (EIP‑6780). This mirrors CVE‑2022‑33746's root cause: a large free/delete operation performed without any incremental cost or preemption check, letting an unprivileged caller force disproportionate node-side work per unit of metered/charged resource.

### Finding Description
`gaskv.Store` wraps a `KVStore` to charge gas for every read/write/delete/iterate operation so that transaction execution cost scales with EVM gas actually purchased by the sender: [1](#0-0) 
However, `DeleteAll` is implemented as a pure passthrough with zero gas consumption: [2](#0-1) 

This bulk-delete path is reached by `Keeper.PurgePrefix`, which is used to wipe an EVM contract's entire per-account storage prefix on self-destruct cleanup: [3](#0-2) 
called from `clearAccountState`, itself invoked when a contract created and destructed in the same tx (per EIP‑6780) has its account marked deleted: [4](#0-3) 

The underlying `DeleteAll` implementations across store layers (`cachekv`, `dbadapter`, `prefix`, `rootmulti`, `storev2`) all perform a full iterate-then-delete over every key in the prefix with no batching, no time-based preemption check, and — critically for `gaskv` — no per-key gas charge: [5](#0-4) [6](#0-5) 

While `SSTORE` gas costs (20000 for a new nonzero slot) bound how much storage a single tx can *write*, an attacker can accumulate a large number of storage slots on a contract across many prior, individually cheap transactions (each paying only its own tx's incremental gas), then trigger the deletion of the *entire* accumulated slot set in one later transaction (create+selfdestruct combos, or via `SelfDestructTester`-style contracts) — and that deletion sweep itself is not billed to the triggering transaction's gas at all, only the fixed SELFDESTRUCT opcode cost (~5000 gas) is charged, regardless of how many stored slots must actually be iterated and deleted from the persistent KVStore.

### Impact Explanation
Because the free/delete work is disconnected from the gas paid by the transaction that triggers it, a comparatively cheap transaction can force the validator to perform an arbitrarily large number of store deletions synchronously during block execution. This directly threatens the "block delay beyond 2.5 seconds" impact category: enough accumulated storage slots on a single account, cleared in one self-destruct transaction, can make that block's execution time balloon without a corresponding gas cost that would otherwise throttle it, since the SELFDESTRUCT gas charge is fixed and does not scale with the number of preexisting storage entries being purged. This is directly analogous to the Xen P2M pool freeing issue: a large, unpreemptible free operation triggered by a guest/tenant action.

### Likelihood Explanation
Reachable via a normal EVM transaction sequence available to any unprivileged sender: (1) write many storage slots to a contract over multiple cheap transactions, (2) trigger a same-tx create+destruct (or any EIP-6780 same-tx destruct) to invoke `clearAccountState` → `PurgePrefix` → `DeleteAll` on that prefix. No special privilege, precompile access, or governance action is required. The `SelfDestructTester`/`SelfDestructFactory` contracts already present in the test suite demonstrate exactly this call pattern is exercised and expected to work in production.

### Recommendation
Charge gas proportional to the number of keys iterated/deleted inside `gaskv.Store.DeleteAll` (mirroring `Delete`'s per-key `DeleteCost` charge), or replace the unmetered bulk purge in EVM storage cleanup with a bounded, checkpointed sweep (similar to the existing `PruneZeroStorageSlots` batch-checkpoint mechanism already present in `x/evm/keeper`) so that any single transaction can only clear a gas-bounded number of slots, deferring the remainder to subsequent blocks/transactions.

### Proof of Concept
1. Deploy a contract and, across several transactions, write N storage slots to it (each write individually gas-bounded, so the attacker's total up-front gas cost scales only with N × SSTORE cost, paid over time and possibly across many blocks).
2. In a later transaction, deploy-and-self-destruct (or otherwise trigger a same-tx EIP-6780 destruct) a contract at that same/derived storage prefix, e.g. via a pattern analogous to `contracts/src/SelfDestructTester.sol`'s `SelfDestructFactory.createAndDestroy`. [7](#0-6) 
3. Observe that the triggering transaction pays only the fixed SELFDESTRUCT opcode gas cost while the node performs `PurgePrefix` → `DeleteAll`, iterating and deleting all N accumulated slots with no corresponding metered cost, and no preemption checkpoint — demonstrating the cost/impact ratio can be made arbitrarily large by growing N beforehand at low marginal cost per slot.

func (dsa Store) DeleteAll(start, end []byte) error {
	iter := dsa.Iterator(start, end)
	keys := [][]byte{}
	for ; iter.Valid(); iter.Next() {
		keys = append(keys, iter.Key())
	}
	if err := iter.Close(); err != nil {
		return err
	}
	for _, key := range keys {
		dsa.Delete(key)
	}
	return nil
}
