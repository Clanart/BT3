## Title
Unprivileged RPC-triggered account scans can indefinitely pin `ScanTracker::ongoing_scan_roots`, permanently blocking `clean_accounts()` and causing unbounded AccountsDb growth - (File: `accounts-db/src/accounts_scan.rs`)

## Summary
The external report describes a function (`takeClaimingSnapshot()`) that, once invoked, can leave a shared process (the distribution event) blocked/inconsistent until an external, out-of-band action resolves it, and notes that the existing recovery mechanism (`topUpDistributionEvent()`) is not automatically invoked. The Agave analog is `ScanGuard`/`ScanTracker` in `accounts-db/src/accounts_scan.rs`, which pins a `max_root` in `ongoing_scan_roots` for the full duration of any account scan (including scans driven purely by unprivileged RPC calls such as `getProgramAccounts`). `AccountsDb::clean_accounts()` is documented and implemented to never clean past `min_ongoing_scan_root()`, so as long as an unprivileged client keeps at least one scan pinned near an old root, cleaning is deferred indefinitely — the codebase only *measures* this risk (`max_distance_to_min_scan_slot`) but enforces no cap or timeout on it.

## Finding Description
`ScanGuard::try_new()` inserts the scan's `max_root_inclusive` into `ongoing_scan_roots` and increments its refcount; the guard is only removed on `Drop` when the scan completes: [1](#0-0) 

`ScanTracker::min_ongoing_scan_root()` exposes the oldest pinned root, and the code comments explicitly document that `clean_accounts()` shares the same lock and is bounded by this value: "This lock is also grabbed by `clean_accounts()`, so clean has at most cleaned up to the current `max_root`": [2](#0-1) [3](#0-2) 

The only signal the system keeps about a stale pin growing dangerously large is a *metric*, `max_distance_to_min_scan_slot`, which is simply tracked with `fetch_max` and never used to abort, expire, or reject scans: [4](#0-3) [5](#0-4) 

The only cancellation path available is `removed_bank_ids`, which is populated when a fork/bank is pruned (`remove_unrooted_slots`), not when a scan simply runs long or when many overlapping scans are issued back-to-back: [6](#0-5) [7](#0-6) 

Account scans of this kind are reachable from ordinary, unprivileged RPC methods that enumerate accounts (e.g. `getProgramAccounts`), which are implemented in `rpc/src/rpc.rs` and route down to `Bank`'s account-scanning APIs backed by `AccountsDb`'s scan machinery: [8](#0-7) 

This mirrors the external report's broken invariant exactly: a normal, non-privileged call (there, `takeClaimingSnapshot()`; here, a scanning RPC call) enters a shared critical section (there, the distribution event; here, `ongoing_scan_roots`/clean-eligible root range) and the codebase provides no automatic mechanism to force that section back to a safe state — only an out-of-band remedy (`topUpDistributionEvent()` there; a bank/fork removal event here) can release it.

## Impact Explanation
As long as pinned scans continuously overlap at (or near) an old root, `AccountsDb::clean_accounts()` cannot advance its cleaning root past `min_ongoing_scan_root()`. This means dead/duplicate/zero-lamport account versions accumulate in storage instead of being purged, causing unbounded growth of on-disk append-vec storages and increased index/memory pressure on the validator over time. This is a resource-exhaustion / degradation condition triggerable purely by an unprivileged RPC client issuing legitimate read requests, without any malicious peer, validator, or leader assumption, and without needing elevated trust.

## Likelihood Explanation
Medium. Any RPC node exposing `getProgramAccounts` (or similar scanning RPC methods) against programs/owners with large account sets can be driven by a single low-rate client that keeps issuing overlapping scan requests such that at least one scan is always active and pinned at an old root, since `ScanGuard` refcounts are only released on scan completion via `Drop`. No special permissions, stake, or protocol-level trust are required — this is a "single-client low-rate RPC degradation" primitive matching the accepted impact categories, and the existing guard (`max_distance_to_min_scan_slot`) is measured but never enforced.

## Recommendation
- Enforce a maximum allowed distance between `min_ongoing_scan_root` and the current root (the codebase already computes this distance but never acts on it) and either expire/abort scans exceeding it, or reject new overlapping scans against stale roots.
- Decouple `clean_accounts()`'s pruning boundary from the single global `min_ongoing_scan_root`, e.g., by allowing clean to skip only the specific slot ranges actively referenced by a scan rather than halting all progress at the oldest pinned root.
- Apply request-level throttling/timeouts to scanning RPC methods (`getProgramAccounts` and similar) so a single client cannot sustain an indefinite chain of overlapping large scans.

## Proof of Concept
1. Start a validator with `getProgramAccounts` enabled and a program/owner having a very large number of accounts.
2. From a single unprivileged RPC client, continuously issue overlapping `getProgramAccounts` requests (e.g., with concurrency > 1, ensuring the next request starts before the previous returns) so that `ScanGuard::try_new()` always keeps at least one entry near the oldest live root in `ongoing_scan_roots`.
3. Observe (via internal metrics or by instrumenting `ScanTracker::min_ongoing_scan_root()`/`max_distance_to_min_scan_slot`) that `clean_accounts()` cannot advance its cleaning boundary while the client sustains this scan pattern, per the documented locking behavior in `accounts_scan.rs` lines 119-127, and that append-vec/storage counts continue growing unchecked.

Note: I was unable to fully trace the exact call chain from `rpc/src/rpc.rs`'s `getProgramAccounts` handler down to `ScanGuard::try_new()` in `accounts_db.rs` within the available tool budget; this connection is inferred from `bank.rs`/`rpc.rs`'s use of `get_program_accounts`/`scan_accounts`-style calls and `accounts_db.rs`'s two call sites of `ScanGuard::try_new` [9](#0-8) , and should be verified directly in a full checkout if precision on the exact RPC entrypoint is required.
