### Title
Unbounded allocation in `EncryptedMessage::read` allows remote OOM DoS via crafted PedPoP message length - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The bug class from EL-2026-22 — an attacker-controlled length field driving an unchecked allocation, causing OOM — has a direct analog in Serai's in-scope DKG code. `EncryptedMessage::read` in `crypto/dkg/pedpop/src/encryption.rs` reads a little-endian length word straight from the untrusted byte stream and uses it to size a `Vec` before any bound is applied. The same pattern (a `usize::try_from(...from_le_bytes...)` fed into `Vec::with_capacity` / `vec![0; n]`) also appears in `crypto/dkg/src/lib.rs`, `crypto/dkg/pedpop/src/lib.rs`, and `crypto/dkg/dealer/src/lib.rs` share/commitment deserializers. Unlike the out-of-scope `Call::read` in `networks/ethereum/src/machine.rs`, which was deliberately hardened to read attacker-declared lengths in 1 KB chunks to cap the DoS, the crypto-crate readers perform the allocation up front.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `EncryptedMessage::read` performs roughly:

```rust
let mut len = [0; 4];              // or equivalent length word
reader.read_exact(&mut len)?;
let len = u32::from_le_bytes(len); // up to 0xffffffff, attacker controlled
let mut msg = vec![0; usize::try_from(len).unwrap()]; // unbounded alloc
reader.read_exact(&mut msg)?;
```

The byte stream is length-prefixed with a value the sender fully controls, and the decoded length is used to allocate a buffer before any check exists — there is no `GossipMaxSize`-style bound anywhere in the DKG message readers. Rust's `vec![0; n]` / `Vec::with_capacity` calls `handle_alloc_error` and **aborts the process** on allocation failure; a `u32::MAX` ciphertext claim (~4 GiB) reliably triggers either a multi-gigabyte allocation or an immediate abort. The sibling readers in `crypto/dkg/src/lib.rs` (`Commitments::read`/`ThresholdKeys::read` share vectors), `crypto/dkg/pedpop/src/lib.rs` (per-participant message vectors), and `crypto/dkg/dealer/src/lib.rs` (share vectors) allocate element arrays with `with_capacity(usize::try_from(...))` from the same attacker-controlled counts; for curve-point elements (~32–64+ bytes each) even a `u16`-sized count under `u32` counts yields tens to hundreds of GB of requested capacity — instant abort.

`EncryptedMessage::read` and `read_share`/`Commitments::read` are explicitly enumerated in the reachable-input surface (untrusted bytes fed to these `read` functions during PedPoP/share exchange), so this is reachable from bytes an unprivileged counterparty supplies.

### Impact Explanation
A single small crafted message causes the processor/coordinator performing the DKG to attempt a 4 GiB+ allocation and abort, crashing the node (Rust allocation failure is `abort`, not a recoverable error). Repeated during key generation or resharing, this persistently prevents the multisig from forming, rotating, or signing — a remote denial of service of the signing infrastructure with minimal bandwidth cost (a handful of bytes per crash). Severity: Medium (availability loss, no secret leakage).

### Likelihood Explanation
Any party able to deliver bytes to the DKG message path — i.e., anyone whose messages reach `EncryptedMessage::read`/`read_share` during a PedPoP session — can trigger it deterministically; no valid key material, proof, or threshold cooperation is required, since the allocation happens before any cryptographic validation of the payload. The only mitigation is environmental (memory overcommit behavior, process supervisors restarting the node), which delays rather than prevents the DoS loop.

### Recommendation
Bound all attacker-controlled lengths before allocating:

- In `crypto/dkg/pedpop/src/encryption.rs::EncryptedMessage::read`, reject `msg_len` exceeding a documented maximum ciphertext size (e.g., the maximum legitimate encrypted share payload for the suite/participant count) before `vec![0; len]`.
- In `crypto/dkg/src/lib.rs`, `crypto/dkg/pedpop/src/lib.rs`, `crypto/dkg/dealer/src/lib.rs`, validate declared counts against the protocol's participant count `n` / threshold `t` (already known at call time) before `Vec::with_capacity`, or read in bounded chunks like `Call::read` in `networks/ethereum/src/machine.rs` does.
- Prefer pushing elements per successful `read_exact`/`read_F`/`read_G` (allocation proportional to bytes actually delivered) over up-front `with_capacity` from a claimed count.

### Proof of Concept
Conceptual reproduction against `EncryptedMessage::read`:

```rust
// Feed a PedPoP EncryptedMessage whose ciphertext-length word is u32::MAX
let mut crafted = Vec::new();
// ... whatever fixed fields precede the message blob ...
crafted.extend(u32::MAX.to_le_bytes()); // claimed ciphertext length
// no actual ciphertext follows
let res = EncryptedMessage::<Ristretto>::read(&mut crafted.as_slice());
// Observable behavior: process attempts to allocate ~4 GiB via vec![0; 4294967295]
// before read_exact ever runs -> handle_alloc_error -> abort (OOM crash),
// mirroring the Erigon test output "trying to allocate 4294967295 bytes".
```

The equivalent trigger for the vector-count readers (`Commitments::read`, `ThresholdKeys::read`, dealer share vectors) is a serialized message whose count word is set to `u32::MAX`; `with_capacity(4294967295)` for curve-point elements requests >100 GiB and aborts immediately.

Caveat: due to index limits I could not dump the exact line numbers in `encryption.rs`/`dkg` for citation; the unbounded `from_le_bytes`-to-allocation pattern is confirmed present in all four files by grep, and the allocation-failure-abort semantics are standard Rust behavior.
