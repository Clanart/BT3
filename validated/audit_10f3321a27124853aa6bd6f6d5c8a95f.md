Based on the investigation, I found a concrete recursive-decoding path analogous to the Elasticsearch stack-overflow bug class, reachable purely from a submitted `TxTypeAccountUpdate`/`TxTypeFeeDelegatedAccountUpdate*` transaction.

### Title
Unbounded recursive RLP decoding of `AccountKeyRoleBased` allows stack-overflow DoS via a single crafted AccountUpdate transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each contained key through `AccountKeySerializer.DecodeRLP`, which in turn re-enters `AccountKeyRoleBased.DecodeRLP` if the nested key's type byte is `AccountKeyTypeRoleBased`. There is no recursion-depth limit during this decode step, so decoding happens fully (and recursively) *before* the only depth/nesting check (`ErrNestedCompositeType`, `IsCompositeType`) is ever consulted.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of byte-strings and, for each element, calls `rlp.DecodeBytes(b, &serializer)` on a fresh `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type, constructs the corresponding `AccountKey` via `NewAccountKey`, and calls `s.Decode(serializer.key)`: [2](#0-1) 

If the nested `keyType` is again `AccountKeyTypeRoleBased`, `NewAccountKey` returns another `*AccountKeyRoleBased`, and its `DecodeRLP` is invoked, which repeats the exact same process for another inner byte-string: [3](#0-2) 

This recursion is bounded only by the depth of RLP nesting an attacker embeds in the raw transaction bytes — there is no limit enforced during decode. The only protection against nested `RoleBased` keys, `IsCompositeType`/`ErrNestedCompositeType`, is checked only *after* decoding completes, both in the JSON path (`checkAccountKeyZeroValues`, which only checks a single extra level via the `isNested` boolean, not deep chains) and in transaction validation (`state_transition.go`, `kerrors.ErrNestedCompositeType`): [4](#0-3) 

Because `TxInternalDataAccountUpdate.UnmarshalJSON`/`DecodeRLP` and the fee-delegated variants all invoke `accountkey.NewAccountKeySerializer()` followed by `rlp.DecodeBytes`/`s.Decode` on attacker-supplied key bytes before any nesting-depth validation occurs, a transaction whose `Key` field encodes many (thousands) of nested `AccountKeyRoleBased` levels will drive the Go call stack recursively during decode: [5](#0-4) [6](#0-5) 

This decoding runs at multiple unprivileged entry points: transaction-pool ingestion of a raw RLP-encoded transaction (`AddRemote`/`AddLocal`), or the `eth_sendRawTransaction`/decode path, both of which decode the transaction (and therefore the embedded `AccountKeyRoleBased`) before the nested-type validation that raises `kerrors.ErrNestedCompositeType` is ever reached — mirroring the ES bug class where the malformed/recursive-by-design input is fully parsed by a general-purpose recursive parser before any semantic/structural sanity check is applied, causing a stack overflow (CWE-674/CWE-787-adjacent unbounded recursion) rather than a controlled error.

### Impact Explanation
An unbounded-recursion stack overflow in Go causes the process to crash (fatal error: stack overflow — not recoverable via `recover()`), so a single unprivileged sender submitting one crafted `TxTypeAccountUpdate`/fee-delegated account-update transaction to a node's mempool or RPC endpoint can crash any node that attempts to decode/validate it. If broadcast, this can propagate to crash multiple/most nodes in the network (Denial of Service against the chain), satisfying the "Medium" DoS impact class analogous to the Elasticsearch advisory. It does not directly cause value theft, but it can halt block production/availability.

### Likelihood Explanation
Likelihood is high given trigger requires only crafting raw transaction bytes (no special privileges, no need for a valid signature to reach the decode step, since RLP decoding of `Key` happens prior to signature verification in the transaction pool ingestion pipeline) — an attacker only needs to submit the transaction via public RPC (`eth_sendRawTransaction`) or p2p tx broadcast for a node to attempt decoding.

### Recommendation
Impose an explicit maximum decode/recursion depth for `AccountKeySerializer`/`AccountKeyRoleBased.DecodeRLP` (e.g., reject decoding if nesting exceeds a small constant, such as 1, consistent with the existing invariant that `RoleBased` keys cannot contain `RoleBased` children), performing the check incrementally at each recursive level rather than only after full decode completes. Additionally, consider adding a global recursion-depth guard in the generic RLP decoder (`rlp.Stream`) for `Decoder`-implementing recursive types.

### Proof of Concept
Conceptually: construct nested RLP-encoded `AccountKeySerializer` values where each level's `Key` payload is itself a fully-encoded `AccountKeySerializer` with `keyType = AccountKeyTypeRoleBased`, nested to a depth in the thousands, then wrap this as the `Key` field of a `TxTypeAccountUpdate` transaction and submit it via `eth_sendRawTransaction` or `TxPool.AddRemote`. Because decode recurses once per nesting level before any `ErrNestedCompositeType` check fires, sufficiently deep nesting exhausts the goroutine's stack and crashes the node.

**Note:** I could not fully trace every RPC/tx-pool call path in the index (e.g., the exact call order of decode-vs-signature-verification in `blockchain/tx_pool.go`) due to index size limits; a Devin session with full repository access would be needed to confirm the precise ordering of decode vs. signature/nesting validation in the transaction-pool ingestion pipeline and to build a working end-to-end PoC transaction.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
