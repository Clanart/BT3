## Analysis

Reducing the external report to its core broken invariant: **a quorum/threshold check is computed by counting a raw quantity (submitted votes) without verifying that the counted units correspond to distinct, unique underlying accounts, so the count can diverge from the value the threshold formula assumes it represents.** In the Lucid case that divergence made quorum unreachable; the exploitable direction of the same bug class is when the counted quantity can be *inflated* relative to what the threshold assumes, causing a check to pass when it should not.

The local analog is in the BEEFY consensus verifier's supermajority check.

### Title
Supermajority threshold in BEEFY verifier counts raw signature entries instead of distinct authorities - (`modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
`verify_mmr_update_proof` computes `signatures_length` as `mmr.signed_commitment.signatures.len()` and passes it directly into `check_participation_threshold(signatures_length as u32, authority_set.len)` [1](#0-0) . Unlike the sibling Pharos verifier, which explicitly rejects duplicate participant keys before evaluating its stake threshold [2](#0-1) , the BEEFY verifier never checks that the `sig.index` values in `mmr.signed_commitment.signatures` are unique before counting them toward the 2/3+1 quorum [3](#0-2) .

### Finding Description
`check_participation_threshold(len, total)` returns `len >= (2*total)/3 + 1` [4](#0-3) . `len` here is simply `signatures.len()`, the number of `(index, signature)` entries submitted in the proof — not the number of distinct authority indices that actually signed. The loop that builds `authority_leaves`/`authority_indices` for the subsequent merkle membership check does not deduplicate `sig.index` either [5](#0-4) .

This mirrors the reported bug's broken invariant exactly: the quorum arithmetic assumes `len` counts *distinct* participants (analogous to assuming total-supply-scale voting power), but nothing enforces that assumption on the actual input. In the Lucid case the mismatch made the threshold unreachable (DoS on governance); here the same class of mismatch runs in the attacker-favorable direction — an attacker constructing/relaying a consensus proof can list the *same* signature/index multiple times to inflate `signatures_length` past the 2/3+1 bar while the number of distinct real signers stays below quorum.

Whether this is fully exploitable end-to-end depends on whether the subsequent merkle multi-proof check (`merkle_proof.verify(..., &authority_indices, &authority_leaves, ...)`) would also accept a proof containing duplicate indices/leaves; I could not fully verify the `rs_merkle` crate's multi-proof algorithm behavior for duplicated indices within the available context. This is the one piece of the chain that is not locally confirmed — the missing invariant (no duplicate-index rejection) is confirmed in this repo's code, but whether the external `rs_merkle::MerkleProof::verify` independently blocks duplicate-index multiproofs is not something I could establish from the indexed code.

### Impact Explanation
If duplicate-index signatures pass the merkle membership check, an attacker can construct a `ConsensusMessage` where fewer than the true supermajority of authorities have signed, and the verifier will accept it as satisfying `SuperMajorityRequired`, updating `trusted_state.latest_beefy_height` and (on epoch boundaries) rotating `current_authorities`/`next_authorities` off of insufficient real consensus. Since `verify_mmr_update_proof` output feeds `verify_consensus`, which is used to accept parachain header state roots into Hyperbridge's trusted state, a false quorum here means **false remote state acceptance** — exactly the class of impact called out as in-scope (false proof/state acceptance leading to unauthorized cross-chain execution).

### Likelihood Explanation
Unlike the excluded categories (malicious relayer/prover assumptions), constructing this proof requires only reusing already-public BEEFY signature data in a duplicated-index array — a permissionless proof submitter does not need any private key beyond what a legitimate authority already broadcasts, and no privileged role is required to submit `ConsensusMessage`s. The missing dedup check is a genuine gap relative to the equivalent Pharos verifier in the same repo, which explicitly guards against it. However, exploitability is contingent on the external merkle multi-proof library's behavior with duplicate indices, which I was not able to confirm from the available code/context.

### Recommendation
Deduplicate `sig.index` values (e.g., via a `BTreeSet`, matching the Pharos verifier's `verify_validator_membership` pattern) before computing `signatures_length` and before building `authority_indices`/`authority_leaves`, rejecting the proof with a new `DuplicateParticipant`-style error if duplicates are found — mirroring `modules/consensus/pharos/verifier/src/lib.rs` lines 144-157.

### Proof of Concept
Conceptual PoC (not independently executed against `rs_merkle`):
1. Take a real BEEFY signed commitment with, say, 40% of authorities signing (below 2/3+1).
2. Build `mmr.signed_commitment.signatures` by repeating one or more of the genuine `(index, signature)` pairs multiple times so `signatures.len()` clears `(2*total)/3+1`.
3. Duplicate the corresponding entries in `authority_indices`/`authority_leaves` fed into the merkle multiproof.
4. Submit as a `ConsensusMessage`; `check_participation_threshold` passes on the inflated count, and if the merkle multiproof verification does not itself reject duplicate indices, `verify_mmr_update_proof` returns `Ok`, advancing `latest_beefy_height` on sub-quorum real participation. [6](#0-5)  shows the test harness (`dummy_mmr_proof`) already builds signature vectors purely by count with sequential indices `0..signature_count`, with no test exercising duplicate/repeated index submission — corroborating that this path is untested for the dedup case.

fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
