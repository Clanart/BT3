### Title
Ed448 scalar inversion drops the exponent’s two highest bits, corrupting interpolation and share recovery - ([File: crypto/ed448/src/backend.rs])

### Summary
`Scalar::invert` is implemented as `self.pow(NEG_2)`, but the Ed448 scalar field has `NUM_BITS = 446`, which is not divisible by the exponentiation routine’s four-bit window. `pow` only emits a window when `(i + 1) % 4 == 0`, so after processing bit index 443 it accumulates indexes 444 and 445 and returns without applying them. Consequently, inversion computes a different exponent than `MODULUS - 2`. [1](#0-0) [2](#0-1) 

### Finding Description
The reference issue was a scaling formula that omitted exponentiation. The analogous Serai defect is a literal omitted portion of an exponent:

- `Scalar::pow` builds a 4-bit lookup table.
- It iterates the exponent’s bits from most significant to least significant.
- It only squares/selects/multiplies after every fourth bit.
- Ed448’s scalar field declares `NUM_BITS` as 446.
- The final two bits are accumulated into `bits` but are never applied because the loop ends before the next `% 4` boundary.
- `Scalar::invert` relies on this broken `pow` implementation.

For an exponent represented as `e = high * 2^444 + low`, where `high` contains the final two bits, the implementation effectively evaluates `a^low` rather than `a^e`. Since `NEG_2` is the 446-bit modulus-minus-two exponent, its discarded top bits are nonzero, so `invert(x)` does not generally return `x^-1`. [3](#0-2) [4](#0-3) 

### Impact Explanation
This produces an incorrect finite-field verifier/interpolation formula for the Ed448 ciphersuite. Scalar inversion is a foundational operation for threshold interpolation and share-reconstruction workflows; an attacker-controlled share, preprocess, commitment, or serialized threshold object processed through the in-scope Ed448/FROST APIs can therefore evaluate Lagrange coefficients or recover shares under the wrong field operation.

The expected result of `x.invert() * x == 1` fails for nonzero `x`. Depending on the consuming API, this can cause valid inputs to be rejected or untrusted shares to be combined into an incorrect recovered value. This is more than a rounding issue: every Ed448 scalar inversion uses an exponent missing its two most-significant bits. [5](#0-4) [3](#0-2) 

### Likelihood Explanation
The defect is deterministic rather than attacker-dependent. `NUM_BITS` is always 446, so every call to `Scalar::invert` leaves two exponent bits unprocessed. It is reachable whenever the Ed448 ciphersuite is selected for a threshold operation whose algebra requires inversion, including participant interpolation or share recovery from externally supplied encoded shares. [4](#0-3) [1](#0-0) 

### Recommendation
Rework `pow` so all bits of `to_le_bits()` are consumed. A simple implementation should iterate bits directly and perform square-and-multiply, or process the remaining `bits` after the loop if the bit length is not divisible by four.

Add tests asserting:

```rust
for x in nonzero_scalars {
  assert_eq!(x.invert().unwrap() * x, Scalar::ONE);
}
```

The tests should include exponents/scalars with either of the two highest bit positions set and should exercise FROST interpolation/recovery on Ed448. [1](#0-0) 

### Proof of Concept
The issue can be demonstrated without network access by checking the field inversion invariant:

```rust
use ff::Field;
use rand_core::OsRng;
use serai_ed448::Scalar;

let x = Scalar::random(&mut OsRng);
let inverse = x.invert().unwrap();

// Required property: x^-1 * x == 1.
assert_eq!(inverse * x, Scalar::ONE);
```

Because `invert()` calls `pow(NEG_2)` and `pow` drops bit indexes 444 and 445, the returned value is not the modular inverse. [6](#0-5) [3](#0-2) [4](#0-3)
