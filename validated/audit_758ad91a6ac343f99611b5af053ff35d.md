## Finding: Excess native `msg.value` sent to `EvmHost.dispatch()` / `fundRequest()` is silently trapped in the host contract instead of being refunded to the caller

### Title
Unrefunded excess native token payment permanently locks caller funds in `EvmHost` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and forward it entirely to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)` to buy an exact amount of fee token. Any unused native token that the router refunds is sent back to `msg.sender` of the swap call — which is `EvmHost` itself, not the original caller — and the dispatch functions never forward that leftover balance back to the user. This is the same broken-invariant class as the referenced Derby report (M-2): native funds attached to a call to cover fees are frozen on the receiving contract whenever the full amount isn't consumed, with no return path to the payer.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest()`: [3](#0-2) 

In each case, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` is called with the full `msg.value`, but `post.fee`/`amount` is only the exact fee-token amount needed. Standard `UniswapV2Router02.swapETHForExactTokens` (and the repo's own wrapper, which implements the identical "refund dust ETH to `msg.sender`" behavior) refunds any unspent native token to whoever called the swap — that caller is `EvmHost`, not the end user who supplied `msg.value` to `dispatch()`/`fundRequest()`: [4](#0-3) 

None of the three `EvmHost` functions track a `msgValue` remainder or forward any leftover ETH back to `_msgSender()` after the swap, unlike the pattern correctly implemented elsewhere in the same codebase (`IntentGatewayV2.sol` and `ExtrinsicIntents.sol`), where the leftover is explicitly computed and refunded: [5](#0-4) [6](#0-5) 

Once the excess ETH lands in `EvmHost`'s balance, the only way to move it out is the cross-chain governance path `withdraw(WithdrawParams)`, gated to `_hostParams.hostManager`, which sends the withdrawn amount to whatever `beneficiary` governance specifies — not necessarily (or ever) the original overpaying caller: [7](#0-6) 

### Impact Explanation
Any caller (an application contract or, through it, an end user) who dispatches a POST/GET request or funds a pending request with more native token than the exact swap requires has that excess permanently trapped in `EvmHost`. It is not automatically recoverable by the payer — recovery, if it ever happens, is entirely at governance's discretion and directed to an address governance chooses, which need not be the original depositor. This is a direct loss-of-funds condition triggered purely by normal usage (e.g. a caller estimating `msg.value` slightly high to guarantee the swap succeeds, which is the exact usage pattern shown/encouraged in the docs), matching the bounty's "loss of funds" impact category.

### Likelihood Explanation
Likelihood is high and requires no privileged or malicious actor: every `dispatch()`/`fundRequest()` caller supplying native token is at risk any time `msg.value` exceeds the exact `swapETHForExactTokens` input requirement (price movement between fee estimation and execution, or simple over-provisioning to avoid reverts from `EXCESSIVE_INPUT_AMOUNT`/insufficient-amount failures, makes this the common case rather than an edge case).

### Recommendation
After each `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the actual amount spent (e.g., from the returned `amounts[0]`) and refund `msg.value - amounts[0]` back to `_msgSender()`, following the same pattern already used in `IntentGatewayV2.sol` / `ExtrinsicIntents.sol`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch(DispatchPost{..., fee: F})` with `msg.value = V > requiredInput(F)` (e.g., adding a safety margin, or price moves favorably between quote and execution).
2. Inside `dispatch`, `swapETHForExactTokens{value: V}(F, path, address(this), ...)` executes; the router spends only `amounts[0] < V` and refunds `V - amounts[0]` to `msg.sender` of the swap call, i.e. `EvmHost`'s own address.
3. `dispatch()` returns without ever inspecting or forwarding the refunded dust — `EvmHost.balance` permanently increases by `V - amounts[0]`.
4. The caller has no function to reclaim this amount; it is only movable via `withdraw()`, callable solely by the `hostManager` via cross-chain governance, to a beneficiary governance selects.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
