### Title
`revealInFileManager` / "Open with default program" resolve untrusted repository-relative paths without containment checks - (File: `app/src/lib/app-shell.ts`)

### Summary
The C4 finding is fundamentally about a function that accepts a caller-supplied destination but silently substitutes an unverified value, so the actual target differs from what the caller (and the guard rails elsewhere in the same codebase) assume. The closest concrete analog in this GitHub Desktop fork is `revealInFileManager`, which naively joins the repository root with a file path taken from git's own file-change data, while every other place in this same codebase that resolves a repository-relative, externally-influenced path (the `openrepo://` deep-link `filepath` handler and the Copilot conflict-context file reader) explicitly funnels the same kind of value through `resolveWithin` to guarantee containment.

### Finding Description
`revealInFileManager` builds the final filesystem path with a plain `Path.join` and no post-resolution containment check: [1](#0-0) 

This function is invoked from several context menus with `file.path` values that originate from `git status`/diff output of the *currently open repository* — i.e., values that ultimately come from tree/index entries of a cloned or fetched repository (a "GitHub API object"/"cloned repository" content source in terms of the task's valid-impact list): [2](#0-1) [3](#0-2) [4](#0-3) 

The same "Open with default program" menu item passes the raw relative `file.path` straight to `onOpenItem`, gated only by an *extension* allow-list (`isSafeFileExtension`), not by a path-containment check: [5](#0-4) [6](#0-5) 

Contrast this with the codebase's own established remediation pattern for the exact same class of input (a repo-relative path that can come from an untrusted source): the `openrepo://…&filepath=` deep-link handler explicitly rejects absolute paths and calls `resolveWithin(repository.path, filepath)` before ever touching the filesystem or shell: [7](#0-6) 

And the Copilot conflict-context reader does the same for conflicted file paths: [8](#0-7) 

`resolveWithin` itself is specifically built to defeat `..` traversal *and* symlink-based escapes (it `realpath`s both the root and the candidate before checking the prefix): [9](#0-8) 

`revealInFileManager` (and the "open with default program" path) never calls `resolveWithin` or any equivalent check — it simply trusts that `Path.join(repository.path, path)` stays inside the repository. This is precisely the "broken invariant" pattern from the C4 report: a function that is supposed to operate on a validated/contained target instead operates on an unchecked value that a hostile input source (crafted repository content, or a symlinked working-tree entry) can influence.

### Impact Explanation
If an attacker can get git to report (or the user to have on disk, e.g., via a symlinked tracked path or a case/normalization trick) a `file.path` value that escapes the repository root once resolved, `revealInFileManager` will call `shell.showItemInFolder` on a path outside the repo, and "Open with default program" will hand an out-of-repo path to the OS's default-application launcher — this can disclose the existence/location of arbitrary files to the user's file manager, or, worse, cause the OS default handler to execute a file outside the repo tree (subject to `isSafeFileExtension`, which only screens extensions, not location). This matches the task's valid-impact categories of "file write or read outside the repo" and potentially "code execution" via a maliciously-authored/cloned repository.

### Likelihood Explanation
Likelihood is lower than the original C4 finding because git itself normally rejects literal `..` path components inside tracked paths, which is the primary traversal vector `resolveWithin` was built to stop. The realistic trigger here is narrower: a tracked path that is (or contains) a symlink pointing outside the repository, or a working-directory entry manipulated after clone/checkout, combined with the user right-clicking that file and choosing "Reveal in Finder/Explorer" or "Open with default program." I could not fully verify from the index whether git-on-disk symlink entries reaching `file.path` in these UI paths are otherwise filtered upstream (e.g., during status parsing) before reaching `revealInFileManager` — this needs verification in a live checkout, which the current index/tooling cannot provide with certainty.

### Recommendation
Route `revealInFileManager` (and any "open with default program" / "open in external editor" callers that build a path via `Path.join(repository.path, path)`) through `resolveWithin(repository.path, path)`, refuse to proceed if it resolves to `null`, exactly as already done for the `openrepo://…&filepath=` handler and the Copilot conflict-context reader, so all repository-relative-path consumers share one containment guarantee instead of some being guarded and others not.

### Proof of Concept
1. Obtain (via clone, or a crafted tracked entry that becomes a symlink in the working directory) a repository where a tracked/working-directory file path, when joined to the repo root, resolves (following any symlink) to a location outside the repository — e.g., a working-tree entry `evil -> /Users/victim/.ssh` created by a build/post-checkout step referenced by the repo.
2. Open the repository in Desktop, go to the Changes/History view, right-click the entry, and choose "Show in Finder/Explorer" (`RevealInFileManagerLabel`), which calls:
```ts

3. Because no `resolveWithin`-style containment check is applied (unlike `dispatcher.ts`'s `openRepositoryFromUrl` filepath handling), `fullyQualifiedFilePath` can resolve outside `repository.path`, and the OS file manager/opener acts on that external path — the exact "guard exists elsewhere in the codebase but not here" gap that mirrors the original report's broken `to`-address invariant.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
