### Title
Value-bearing calls to distribution precompile's `rewards()` view strand attached usei/wei with no refund path - (File: precompiles/distribution/distribution.go)

### Summary
The distribution precompile's `rewards()` method is dispatched by `Execute` without any non-payable validation and without any logic that consumes, refunds, or accounts for `value` sent along with the EVM call. Any caller who sends a nonzero `value` to `rewards()` has that usei/wei debited from their EVM balance by the EVM value-transfer mechanics (the value is transferred to the precompile address before `Execute` even runs), but the precompile function itself performs only a read-only delegation-rewards query and never moves or refunds the transferred value.

### Finding Description
`Execute` in `precompiles/distribution/distribution.go` dispatches on `method.Name`. For state-mutating (`IsTransaction`) methods, `value` is either explicitly rejected via `pcommon.ValidateNonPayable(value)` (e.g. `setWithdrawAddress`, `withdrawValidatorCommission`) or consumed as payment (patterns elsewhere in the precompile suite such as `gov`'s `deposit`, which calls `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` to explicitly redirect the attached value). [3](#0-2) [4](#0-3) 

For `RewardsMethod`, however, `Execute` calls `p.rewards(ctx, method, args)` directly with no `pcommon.ValidateNonPayable(value)` check and no `value` argument passed at all: [1](#0-0) 

```go
case RewardsMethod:
    return p.rewards(ctx, method, args)
```

The `rewards` function itself only queries `DelegationTotalRewards` and packs the response — it never touches `value`, never refunds it, and never records/uses it: [2](#0-1) 

By EVM semantics, when a caller sends a transaction/call to the precompile address with `msg.value > 0`, that native value is debited from the caller and credited to the precompile's (module) account balance as part of standard `CALL`/value-transfer processing, independent of what the precompile's Go logic does. Because `rewards()` runs this transfer without ever crediting it back to the caller or to any beneficiary account, the usei/wei sent along with the call is permanently stranded at the precompile's associated account — this is structurally the same "state update happens outside of an accounting path that the rest of the contract logic tracks" bug pattern as the reported `add_margin` issue, where the added margin was credited to `position.margin_amount` but never reflected in the values used at close time, permanently freezing it.

This exact pathological gap was flagged as a known quirk in the integration-test comments for this precompile: "rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)". [5](#0-4) 

### Impact Explanation
Any unprivileged EVM caller (contract or externally-owned account) that calls `rewards(address)` on the distribution precompile at `0x0000000000000000000000000000000000001007` with a nonzero `value` permanently loses that usei/wei — there is no recovery path since the funds land in a module-controlled account with no corresponding accounting entry that any user-facing withdraw flow reads from. This is a concrete permanent freezing/loss-of-funds bug, matching the "Stuck funds" impact class in the reported analog.

### Likelihood Explanation
Trivially reachable: any account can call the public JSON-RPC / EVM `eth_call`/transaction path to invoke `rewards(address)` on the known precompile address while attaching value; no association beyond the caller's own address is even strictly required to trigger the value transfer (the transfer happens before any precompile-specific reverts on unrelated validation checks). The only barrier is user/tooling awareness — an integrator building a UI/wallet without care, or a naive script, could easily attach value by mistake, or a malicious dApp/frontend could induce mistaken payable calls to this address.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` at the top of the `rewards` dispatch (mirroring every other query/method in this precompile family that already guards non-payability, and mirroring how state-mutating methods either reject or explicitly route `value`), so that any attached `value` causes the call to revert instead of being silently absorbed with no accounting.

### Proof of Concept
1. Associate a Sei/EVM address pair and fund the EVM address with usei/wei, per `contracts/test/AssociateTest.js`-style association flow. [6](#0-5) 
2. Build a call to the distribution precompile (`0x0000000000000000000000000000000000001007`) invoking `rewards(address)` with the caller's own address as argument, but attach `value > 0` (e.g. `value: 1000000000000` swei = 1 usei) in the transaction.
3. Observe the call succeeds and returns reward data as normal (per `RewardsMethod` dispatch at `precompiles/distribution/distribution.go:204-205`), while the caller's EVM balance is reduced by the attached value and no corresponding refund or credit occurs anywhere in `p.rewards` (`precompiles/distribution/distribution.go:543-579`), and no error is raised as would happen for other methods guarded by `pcommon.ValidateNonPayable`.
4. Confirm the value is unrecoverable: no withdraw/redeem endpoint on the distribution module keeper reads or refunds a "value sent to `rewards()`" balance, since it was never tracked.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
