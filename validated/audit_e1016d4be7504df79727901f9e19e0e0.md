### Title
Symlink-following file read outside repository in `getResolutionDiff` merge-conflict diff preview - (File: `app/src/lib/git/diff.ts`)

### Summary
`getResolutionDiff` reads the working-tree "conflicted" entry with a plain `readFile(Path.join(repository.path, filePath), 'utf8')` call, with no check that the resolved path stays inside the repository and no check that `filePath` isn't a symlink. Node's `fs.readFile` transparently follows symlinks, so if the conflicted path in the working tree is a symlink pointing outside the repository, the function will read the *target's* content instead of repo content, write it to a temp file, diff it, and hand it to the renderer's Copilot conflict-resolution UI.

### Finding Description
`getResolutionDiff` computes the "base" side of the resolution diff directly from disk: [1](#0-0) 

There is no `lstat`/symlink check and no containment check (e.g. `resolveWithin`) before this read. Contrast this with the sibling function `buildConflictContext`, used to build the actual Copilot prompt, which explicitly guards against exactly this class of attack: [2](#0-1) 

`buildConflictContext` calls `resolveWithin(workingDirectory, file.path)` and rejects the file ("File path is outside the repository") if the symlink escapes the repo — this is a deliberate, already-implemented mitigation for symlink/path-traversal escapes that was **not** applied to `getResolutionDiff`.

The `filePath` passed into `getResolutionDiff` is the repository-relative path of a conflicted `WorkingDirectoryFileChange`, taken straight from git status and passed through unmodified from the Copilot conflicts UI: [3](#0-2) [4](#0-3) 

Git can leave a conflicting path checked out as an actual filesystem symlink in the working tree when a merge/rebase produces an add/add or content conflict on a symlink entry (e.g., one side changes a regular file to a symlink, or both sides change a symlink's target differently). An attacker who controls a branch/repository the victim merges/rebases against can therefore craft a conflict where the on-disk entry at the conflicted path is a symlink pointing to an arbitrary out-of-repo file (e.g., `../../.ssh/id_rsa`, an absolute path, or another sensitive file readable by the Desktop app's OS user).

When the victim opens the Copilot conflicts dialog, the first conflicted file is auto-selected and its diff is loaded on mount: [5](#0-4) 

If that file is the crafted symlink, `getResolutionDiff` reads through it, and the resulting content is fed to the diff viewer/syntax highlighter as `oldContents`: [6](#0-5) [7](#0-6) 

### Impact Explanation
This is a file-read-outside-the-repository primitive: content of an arbitrary file readable by the Desktop process's OS user (SSH keys, other repositories, config/credential files, etc.) is disclosed into the app's rendered conflict-resolution diff view. It is triggered by opening the built-in merge-conflict resolution UI, a normal user action, and does not require the user to interact with the symlinked file in any unusual way (auto-selection of the first conflicted file is enough). The disclosure is confined to the local renderer UI in this specific code path (unlike `buildConflictContext`, this data is not sent to the Copilot network endpoint), but it still meets the "file read outside repo" bar in scope, and a leaked secret displayed in-app can subsequently be copied, screenshotted, or accidentally committed/pushed by the user.

### Likelihood Explanation
Requires the attacker to control repository content that the victim merges/rebases against (in scope) and craft a symlink-based conflict at a specific path — technically achievable using standard git symlink semantics, no special git server behavior needed. The victim only needs to perform a normal merge/rebase resulting in a conflict and open the standard Copilot conflict-resolution dialog.

### Recommendation
Apply the same protection already used in `app/src/lib/copilot-conflict-context.ts` — resolve/validate the path with `resolveWithin(repository.path, filePath)` (or equivalent `lstat` + symlink rejection) in `getResolutionDiff` before calling `readFile`, and reject/skip files whose resolved path is a symlink or escapes the repository root.

### Proof of Concept
1. Attacker prepares a branch such that merging it with the victim's branch produces a conflict at path `evil-link`, where the working-tree entry after the failed merge is a symlink `evil-link -> /Users/victim/.ssh/id_rsa` (or a relative path escaping the repo, e.g. `../../.ssh/id_rsa`).
2. Victim clones/fetches and merges/rebases onto this branch in GitHub Desktop, hits the conflict, and opens the Copilot conflicts dialog (`CopilotConflictsChanges`).
3. On mount, `loadDiffForFile` is called for `evil-link` (auto-selected as `files[0]`), invoking `getResolutionDiff(repository, 'evil-link', {content: ...} | {stage: ...})`.
4. `readFile(Path.join(repository.path, 'evil-link'), 'utf8')` follows the symlink and reads `/Users/victim/.ssh/id_rsa` into `baseContent`.
5. The content is written to a temp file, diffed, and rendered in the Changes tab of the Copilot conflicts dialog, disclosing the private key contents in the app UI. [8](#0-7)

  private buildFileContents(
    file: CommittedFileChange,
    result: IResolutionDiff
  ): IFileContents {
    // Mirror the standard getFileContents path, which caps the amount of
    // content it hands to the syntax-highlighting worker. We only allow
    // expansion when the whole (untruncated) resolution fits under the limit.
    const canBeExpanded =
      result.newContents.length <= MaxDiffExpansionNewContentLength
    const oldContents = result.oldContents
      .slice(0, MaxDiffExpansionNewContentLength)
      .split(/\r?\n/)
    const newContents = result.newContents
      .slice(0, MaxDiffExpansionNewContentLength)
      .split(/\r?\n/)

    return { file, oldContents, newContents, canBeExpanded }
  }
