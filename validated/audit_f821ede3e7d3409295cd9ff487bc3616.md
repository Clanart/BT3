### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub/Enterprise trust decision in credential helper, tricking users into sending real GitHub credentials to a malicious remote - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
Like Futureswap's meta-transaction flow, which used to trust the oracle's appended data with no independent verifier, GitHub Desktop's git-credential-helper trampoline trusts an **unauthenticated, attacker-controlled** HTTP response header (`WWW-Authenticate`) forwarded verbatim by git, and uses it — with no cross-check — to decide whether a remote counts as a "GitHub"/"enterprise" endpoint. That decision then drives Desktop to launch a GitHub sign-in/token-entry flow whose resulting credential is handed straight back to the very (attacker) remote that supplied the header.

### Finding Description
`getEndpointKind()` classifies the remote a git operation is talking to: [1](#0-0) 

The comment is explicit that this is a "happy-path" heuristic used *instead of* an independent verification request:
`// We use them as a happy-path to determine if the host is a GitHub host without having to resort to making a request ourselves.`

The `wwwauth[]` values come from the credential-fill data git passes to the helper, which in turn is populated from the target server's own `WWW-Authenticate` HTTP response header — a value fully controlled by whatever server (or proxy/MITM) the current git operation is connecting to. There is no signature, no independent "verifier" check (unlike the Futureswap fix that added a verifier/stamper signature), and no confirmation against GitHub's own API before this value is trusted.

If a malicious/rogue remote (or a proxy sitting in front of one, per the "git remote/proxy response" attacker model) answers with `WWW-Authenticate: Basic realm="GitHub"` for a plain HTTPS clone/fetch/push URL that is neither `github.com` nor a recognized GHE domain and for which the user has no existing matching account, `getEndpointKind` returns `'enterprise'`.

That result feeds directly into `getCredential`: [2](#0-1) 

Because `endpointKind !== 'generic'` and no stored account's `endpoint` matches the attacker's host, Desktop calls `ui.promptForGitHubSignIn(endpoint)` where `endpoint` is the attacker-controlled URL: [3](#0-2) 

This begins an "Enterprise sign-in" flow bound to the attacker's `origin` (`this.dispatcher.setSignInEndpoint(origin)`), presenting the user a UI that looks like a legitimate GitHub/Enterprise authentication request. Any resulting `Account`/token (whether a freshly entered PAT or an OAuth-derived token) is merged back into the credential via `credWithAccount` and returned to git (`formatCredential`), which git then transmits as HTTP Basic auth **to the attacker's own remote** to complete the original fetch/clone/push.

### Impact Explanation
This corrupts the trust decision that governs which credential-acquisition path (trusted GitHub OAuth token vs. arbitrary generic username/password) is used for a remote — the exact analog of the Futureswap oracle-trust invariant. The concrete corrupted value is `endpointKind`, derived solely from an untrusted, attacker-supplied `wwwauth[]` header. Concretely exploitable outcomes:
- **Credential/token exfiltration**: a user tricked into entering a PAT (or completing an Enterprise sign-in) against what they believe is a legitimate GitHub-style prompt has that secret sent directly to the attacker-controlled remote.
- **Unauthorized account binding**: `setSignInEndpoint(origin)` binds an Enterprise "account" record to an arbitrary attacker origin inside Desktop's own state.

This matches the valid-impact categories: attacker controls a git remote/proxy response, resulting in credential/token exfiltration and unauthorized account binding.

### Likelihood Explanation
No local access, malware, or leaked credentials are required — only that the user perform a normal git operation (clone/fetch/push) against a remote that returns a crafted `WWW-Authenticate` header, e.g. an attacker-hosted git server, a compromised/malicious proxy, or a spoofed `http://` remote. The check exists purely to avoid an extra network round-trip and is explicitly documented as a heuristic with no secondary verification, so there is no existing guard preventing the spoof — the only mitigations are the unrelated `isDotCom`/`isGHE`/`isGist` domain checks, none of which apply once the attacker uses an arbitrary hostname.

### Recommendation
Do not trust the `WWW-Authenticate` realm value alone for the security-relevant "is this host GitHub" decision. Require either: (1) a match against the resolved API endpoint of an existing, previously authenticated GitHub/Enterprise account, or (2) an authenticated verification call to `isGitHubHost()` before granting the "enterprise" classification, similar to how Futureswap added an independent verifier signature rather than trusting the oracle's self-reported metadata.

### Proof of Concept
1. Host a plain git-over-HTTP(S) server at `https://evil.example.com/repo.git` that responds to unauthenticated requests with `HTTP 401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Have the victim `git clone https://evil.example.com/repo.git` (or add it as a remote and fetch/push) via GitHub Desktop, with no account already registered for `evil.example.com`.
3. `getEndpointKind` (app/src/lib/trampoline/trampoline-credential-helper.ts:137-179) matches the spoofed header and returns `'enterprise'`.
4. `getCredential` (same file, 101-125) finds no matching account and calls `ui.promptForGitHubSignIn('https://evil.example.com/...')`.
5. Desktop shows a "GitHub sign in" popup and binds the sign-in flow to `evil.example.com` (app/src/lib/trampoline/trampoline-ui-helper.ts:80-104).
6. Whatever token/credential the user supplies is returned to git and sent as Basic auth to `evil.example.com`, exfiltrating it to the attacker.

```typescript
  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
```

```typescript
  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
```
