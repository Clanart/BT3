### Title
Invalid PedPoP secret-share messages reveal ECDH keys before PoP verification - ([File: `crypto/dkg/pedpop/src/lib.rs`])

### Summary
`KeyMachine::calculate_share` returns an encryption-key blame proof for a malformed secret share before verifying the queued per-message proof of possession. An attacker can reuse another sender’s ephemeral encryption key, submit a malformed message with an invalid PoP, and cause the recipient to emit the corresponding ECDH shared key. That shared key can then decrypt the victim’s previously observed secret-share ciphertext.

### Finding Description
`Encryption::decrypt` queues verification of `msg.pop` in the caller-provided batch verifier, but immediately performs ECDH, decrypts the message, and returns an `EncryptionKeyProof` containing the shared key and a DLEq proof for it. [1](#0-0) 

In `KeyMachine::calculate_share`, scalar deserialization happens before `batch.verify_with_vartime_blame` is called. If the decrypted bytes are not a canonical scalar, the function immediately returns `InvalidShare` with `Some(blame)`, bypassing the batch check that would otherwise reject the message’s invalid PoP without disclosing the proof. [2](#0-1) 

The comments explicitly identify the intended attack: an observer who cannot prove possession of Alice’s ephemeral key should not be able to make Bob reveal Bob’s ECDH output under that key. The ordering bug reintroduces that attack because the invalid PoP is only checked after the secret-share parser has already caused an early return. [3](#0-2) 

The disclosed `EncryptionKeyProof` serializes the ECDH point as `key`, and `cipher` derives the ChaCha20 stream directly from that point, DKG context, and fixed IV. Consequently, disclosure of `proof.key` is sufficient to decrypt the original message protected by that ECDH point. [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker can recover a secret share sent to a DKG participant without knowing either the sender’s ephemeral secret or the recipient’s encryption secret. Repeating this against shares sent to the same participant recovers that participant’s aggregate threshold secret share; repeating it against enough participants can recover threshold key shares and compromise signing authority.

This is a confidentiality and threshold-key compromise, not merely an invalid-message or blame-accuracy failure.

### Likelihood Explanation
The attacker needs to observe an encrypted share addressed to the target, reuse that message’s public ephemeral key in an attacker-controlled `EncryptedMessage`, and obtain the emitted blame proof. The protocol comments explicitly contemplate an observer capable of seeing encrypted messages, and the vulnerable path requires only malformed public ciphertext bytes plus a syntactically valid `Participant` map entry.

The malformed ciphertext must deserialize to a non-canonical scalar so the early `from_repr` error occurs before batch verification. This is straightforward to arrange, for example by filling the scalar field with bytes outside the field modulus.

### Recommendation
Do not return an `EncryptionKeyProof` until every queued PoP associated with the decrypted message has been verified.

Concretely:

- Verify `msg.pop` synchronously inside `Encryption::decrypt` before calculating or returning the ECDH key, or
- Continue through `calculate_share` far enough to run `batch.verify_with_vartime_blame`, discard any generated proof if a `BatchId::Decryption` failure exists, and only attach blame proofs after all PoPs pass.
- Ensure non-canonical scalar errors cannot bypass pending PoP verification or select a blame proof before the proof’s validity has been established.

### Proof of Concept
```text
1. Alice sends Bob EncryptedMessage {
     key: X = aG,
     pop: valid PoP for a,
     msg: ChaCha20(ECDH = bX)[alice_share_for_bob]
   }

2. Eve observes X and the ciphertext but does not know a.

3. Eve registers as a PedPoP participant and sends Bob:
   EncryptedMessage {
     key: X,
     pop: invalid SchnorrSignature,
     msg: bytes guaranteed to deserialize as non-canonical F
   }

4. Bob calls calculate_share:
   - decrypt queues Eve's invalid PoP for later batch verification
   - computes K = bX
   - decrypts the malformed ciphertext
   - creates EncryptionKeyProof { key: K, dleq: ... }
   - C::F::from_repr fails before batch.verify_with_vartime_blame
   - returns InvalidShare { blame: Some(EncryptionKeyProof { key: K, ... }) }

5. Eve obtains the emitted blame proof and extracts K.

6. Eve derives ChaCha20(context || K || fixed IV) and decrypts Alice's
   original ciphertext, recovering Alice's secret share for Bob.
```

pub struct EncryptedMessage<C: Ciphersuite, E: Encryptable> {
  key: C::G,
  // Also include a proof-of-possession for the key.
  // If this proof-of-possession wasn't here, Eve could observe Alice encrypt to Bob with key X,
  // then send Bob a message also claiming to use X.
  // While Eve's message would fail to meaningfully decrypt, Bob would then use this to create a

  // While Eve can still reuse their own keys, causing Bob to leak all messages by revealing for

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res

#[derive(Clone, PartialEq, Eq, Debug, Zeroize)]
pub struct EncryptionKeyProof<C: Ciphersuite> {
  key: Zeroizing<C::G>,
  dleq: DLEqProof<C::G>,
}

impl<C: Ciphersuite> EncryptionKeyProof<C> {
  pub fn read<R: io::Read>(reader: &mut R) -> io::Result<Self> {
    Ok(Self { key: Zeroizing::new(C::read_G(reader)?), dleq: DLEqProof::read(reader)? })
  }

  pub fn write<W: io::Write>(&self, writer: &mut W) -> io::Result<()> {
    writer.write_all(self.key.to_bytes().as_ref())?;
    self.dleq.write(writer)
  }

    rng: &mut R,
    batch: &mut BatchVerifier<I, C::G>,
    // Uses a distinct batch ID so if this batch verifier is reused, we know its the PoP aspect
    // which failed, and therefore to use None for the blame
    batch_id: I,
    from: Participant,
    mut msg: EncryptedMessage<C, E>,
  ) -> (Zeroizing<E>, EncryptionKeyProof<C>) {
    msg.pop.batch_verify(
      rng,
      batch,
      batch_id,
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    );

    let key = ecdh::<C>(&self.enc_key, msg.key);
    cipher::<C>(self.context, &key).apply_keystream(msg.msg.as_mut().as_mut());

      msg.msg,
      EncryptionKeyProof {
        key,
        dleq: DLEqProof::prove(
          rng,
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &self.enc_key,
        ),
      },
    )
