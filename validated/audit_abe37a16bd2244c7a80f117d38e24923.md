### Title
Unbounded attacker-controlled participant count causes excessive allocation and O(n) group operations in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to GHSA-vc29-vg52-6643 (CWE-770, allocation/processing of attacker-controlled input without a limit), `ThresholdKeys::read` deserializes a fully attacker-controlled `n` (u16) and immediately trusts it to drive allocation and expensive elliptic-curve work: it allocates `Vec::with_capacity(n)` for the `Interpolation::Constant` coefficients, reads `n` scalars, builds a `HashMap` of `n` verification shares via `C::read_G`, and then runs `ThresholdKeys::new`, which performs Lagrange interpolation over participants `1..=t` to reconstruct the group key. An unprivileged party that can feed bytes to `ThresholdKeys::read` (an explicitly exposed deserialization entry point) can force ~4 MB of parsing plus tens of thousands of scalar multiplications per call, amplified arbitrarily by repeatedly invoking it.

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs`), `t`, `n`, and `i` are read from the input stream with no validation against any caller-specified bound:

- `n` is a raw `u16` read at crypto/dkg/src/lib.rs:591-602.
- `Interpolation::Constant` allocates `Vec::with_capacity(usize::from(n))` and reads `n` scalars at crypto/dkg/src/lib.rs:604-613.
- A `HashMap` of `n` verification shares is built, each requiring a full `read_G` decode and canonicality re-encoding check (crypto/dkg/src/lib.rs:620-623; `read_G` at crypto/ciphersuite/src/lib.rs:91-101 performs `from_bytes` plus a re-serialization comparison).
- `ThresholdKeys::new` at crypto/dkg/src/lib.rs:625-631 then interpolates the first `t` verification shares (each Lagrange evaluation is a multiexp of length `t`), so `n = t = 65535` forces ~65k point multiplications plus ~65k hash-map inserts and group decodes per call.

Unlike the comparable reads elsewhere in Serai (e.g., `Transaction::read` in the coordinator checks `commitments_len * each_commitments_len` against `TRANSACTION_SIZE_LIMIT`, and `RrCodec::read_request` enforces `MAX_LIBP2P_REQRES_MESSAGE_SIZE`), there is no size limit or consistency check against expected parameters here — the reader cannot pre-commit to an expected `(t, n)` because those come from the stream itself. Similarly, `Commitments::read` in `crypto/dkg/pedpop/src/lib.rs:110-128` bounds its loop by the caller-supplied `params.t()`, which is safe, but `ThresholdKeys::read` is fully self-describing.

### Impact Explanation
Any component that accepts serialized `ThresholdKeys` from an untrusted or unauthenticated source — or reads attacker-influenced bytes into `ThresholdKeys::read` — can be forced to allocate megabytes and burn hundreds of milliseconds of CPU on curve operations per invocation. Repeated calls (e.g., a peer replaying crafted blobs, or an attacker-controlled blob supplied through any layer that round-trips through this API) yield a CPU/memory amplification DoS, degrading or stalling the node's signing pipeline, mirroring the advisory's "excessive resource consumption, increased latency, degraded performance, or downtime".

### Likelihood Explanation
`ThresholdKeys::read` is a public API on `ThresholdKeys` and is one of the enumerated untrusted-byte entry points. Triggering it requires only that an attacker cause a node to deserialize a crafted `ThresholdKeys` blob (malformed backups, peer-supplied key material, or any protocol path that round-trips serialized keys). No signature, proof, or consensus participation is needed to reach the expensive path — the cost is incurred during deserialization and `ThresholdKeys::new` before any semantic rejection could occur. The 16-bit width of `n` caps a single call at ~4 MB and ~65k group operations, which bounds the per-call cost and keeps this at Medium rather than High.

### Recommendation
Have `ThresholdKeys::read` accept the expected `ThresholdParams` (or at least an upper bound) from the caller, consistent with how `Commitments::read`/`EncryptedMessage::read` in `crypto/dkg/pedpop` already take `params: ThresholdParams`, and reject `n` exceeding it before allocating. Additionally, defer `Vec::with_capacity(n)` until after the first element reads succeed, and bound the total byte consumption (e.g., wrap the reader in a `Take`-style limit proportional to the caller's expected size).

### Proof of Concept
```rust
use std::io;
use frost::{ThresholdKeys, curve::{Ciphersuite, Secp256k1}};
use ciphersuite::group::{ff::Field, GroupEncoding};

// Attacker-controlled blob: valid C::ID, t = n = 65535, i = 1, Lagrange interpolation
let mut buf = vec![];
buf.extend((Secp256k1::ID.len() as u32).to_le_bytes());
buf.extend(Secp256k1::ID);
buf.extend(65535u16.to_le_bytes()); // t
buf.extend(65535u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes());     // i
buf.push(1);                        // Interpolation::Lagrange
buf.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr().as_ref()); // secret_share
// n attacker-generated (but canonical) points, e.g. the generator repeated
for _ in 0 .. 65535u16 {
  buf.extend(Secp256k1::generator().to_bytes().as_ref());
}

// Each call: ~65k point decodes + ~65k HashMap inserts + Lagrange interpolation over t=65535
// shares (~65k scalar multiplications). Repeated calls on a byte stream DoS the host.
let res = ThresholdKeys::<Secp256k1>::read::<&[u8]>(&mut buf.as_slice());
```

The payload is ~4 MB and is fully satisfiable by an unprivileged party; no cryptographic validity beyond canonical encodings is required to trigger the allocation and the interpolation cost inside `ThresholdKeys::new`.
