### Title
Symlinked repository files escape the repo root when revealed/opened, bypassing the app's own `resolveWithin` containment guard - ([File: app/src/lib/app-shell.ts])

### Summary
GitHub Desktop already has a dedicated path-containment primitive, `resolveWithin`, used to stop exactly this class of bug in a few call sites (`openRepositoryFromUrl`, `buildConflictContext`). However, the file-reveal / file-open code paths that are driven by attacker-controlled repository content (a symlink checked into a cloned/fetched/PR-reviewed repo) still build the on-disk path with a naive `Path.join(repository.path, path)` and never validate that the resolved target stays under `repository.path`. This mirrors the GitLab cache report's root cause: an attacker-influenced relative value (`cache: key`) is concatenated into a filesystem path without verifying containment, letting the resolved path land outside the intended root.

### Finding Description
`revealInFileManager` builds the fully-qualified path purely by joining the repo path and the (repo-supplied) relative file path, with no containment check: [1](#0-0) 

The same unguarded pattern is used to launch the user's external editor for a file: [2](#0-1) 

Both are reachable from the Pull Request "Files changed" view, where `file.path` comes from the diff of a PR that can originate from a fork/attacker (context menu "Reveal in File Manager" / "Open in External Editor" / double-click): [3](#0-2) [4](#0-3) 

`openFile` (used from the Changes list) similarly just receives whatever `fullPath` was computed and hands it to the shell with no re-validation: [5](#0-4) 

Git blocks `..` path *components* inside a tree, but it does not forbid a tracked **symlink** (mode `120000`) whose *target* string is `../../../../.ssh/id_rsa` or an absolute path such as `/Users/victim/.ssh/id_rsa`. When such a commit is cloned, fetched, or checked out (including checking out a malicious pull request for review), git happily creates that symlink on disk at a perfectly normal-looking relative path like `notes.txt`. `Path.join(repository.path, 'notes.txt')` still resolves to a path *inside* the repo, but that path *is a symlink* pointing arbitrarily far outside the repo. The application already has the correct fix pattern available (`resolveWithin`, which explicitly performs `realpath` resolution and rejects symlink escapes — see the existing unit test for exactly this scenario): [6](#0-5) [7](#0-6) 

and it is applied at some call sites: [8](#0-7) [9](#0-8) 

...but not at `revealInFileManager`, `openFile`, or `_openInExternalEditor`/`onOpenInExternalEditor`, which is exactly the "same root cause, multiple call sites, some fixed some not" pattern described in the source report.

### Impact Explanation
An attacker who controls the content of a cloned/fetched repository (a malicious repo, a fork used to open a pull request, or any repo added to Desktop) can commit a symlink pointing to a sensitive file outside the repository (e.g. `~/.ssh/id_rsa`, a cloud-credentials file, `~/.aws/credentials`, or an app config containing tokens). When the victim uses ordinary Desktop UI affordances — "Reveal in File Manager", "Open in External Editor", "Open with Default Program", or double-clicking a changed/PR file — Desktop resolves and opens/reveals the symlink target, which lies outside the repository root. Depending on the target and the associated program, this can expose file existence/contents (credential/secret exfiltration) or invoke arbitrary local executables/scripts if the symlink points at an executable path, satisfying the "read outside the repo" / "credential exfiltration" impact bar.

### Likelihood Explanation
No unusual or unnatural steps are required beyond normal review workflow: cloning a repo, checking out/reviewing a PR, and using the standard right-click / double-click actions that Desktop already surfaces for every changed or PR file. Git symlink blobs are ordinary, valid git objects — no corrupted objects or special git config are needed to create one, and Desktop performs no target-path validation on checkout. The only gating factor is that the user must click on the malicious file entry, which is the exact interaction the UI encourages when reviewing changes/PRs.

### Recommendation
Route every path derived from repository-tracked/PR-supplied relative paths through `resolveWithin` (or equivalent `realpath`-based containment check) before it is passed to `shell.showItemInFolder`, `shell.openExternal`, or `launchExternalEditor`/`launchCustomExternalEditor`. Concretely:
- In `app/src/lib/app-shell.ts`'s `revealInFileManager`, resolve `path` via `resolveWithin(repository.path, path)` and refuse to reveal (or show an error) if it returns `null`.
- In `app/src/ui/app.tsx`'s `onOpenInExternalEditor` and `app/src/lib/stores/app-store.ts`'s `_openInExternalEditor`/`_openInSelectedExternalEditor`, perform the same containment check before invoking the editor.
- In `app/src/ui/lib/open-file.ts`'s `openFile`, validate the resolved path the same way before calling `shell.openExternal`.
- Add regression tests mirroring `app/test/unit/path-test.ts`'s existing symlink-escape test, exercised through these UI-facing functions.

### Proof of Concept
1. Attacker creates a repository/fork containing a commit that adds a symlink blob, e.g. `git symlink notes.txt -> ../../../../../../Users/victim/.ssh/id_rsa` (via `ln -s ../../../../../../Users/victim/.ssh/id_rsa notes.txt; git add notes.txt; git commit`).
2. Victim clones the repo (or opens a PR from the fork) in GitHub Desktop and reviews/checks it out; git checkout creates the real symlink `notes.txt` inside the repo working directory pointing at `~/.ssh/id_rsa`.
3. In the Changes list or the "Files changed" PR view, victim right-clicks `notes.txt` and selects "Reveal in File Manager" or "Open in External Editor" (or double-clicks the row).
4. `revealInFileManager`/`onOpenInExternalEditor` compute `Path.join(repository.path, 'notes.txt')`, which the OS resolves through the symlink to `~/.ssh/id_rsa`; the file manager/editor opens the private key file, disclosing its location and contents — all without any `resolveWithin` containment check being applied.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
