### Title
Missing participant-range check on blame arguments causes panic/DoS via HashMap index on absent key - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2023-3359 is a missing NULL check on `kzalloc()`'s return, yielding a NULL dereference (availability-only, CVSS 5.5). The Rust analog in Serai is an unchecked `HashMap` index: `Decryption::decrypt_with_proof` dereferences `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` dereferences `self.commitments[&sender]` without verifying the `Participant` indexes actually exist in the maps. Attacker-controlled `Participant` values (any non-zero `u16`) reach these lookups through the blame/accusation path, producing a panic that crashes the processor — a direct mirror of "unchecked lookup → dereference of absent value → crash".

### Finding Description
`AdditionalBlameMachine::new` populates `encryption.enc_keys` and `commitments` strictly for `Participant::new(1..=n)` [1](#0-0) . `blame` then forwards its caller-supplied `sender`/`recipient` indexes to `blame_internal` with no membership or range check [2](#0-1) . Inside `decrypt_with_proof`, `self.enc_keys[&decryptor]` panics if the recipient was never registered [3](#0-2) , and in `blame_internal` `self.commitments[&sender]` panics if the sender is not a protocol participant [4](#0-3) . `Participant::new` only enforces non-zero, not `<= n`, so any `u16` in `1..=u16::MAX` is accepted at the parsing layer (e.g. `accuser`/`faulty` fields of an `InvalidDkgShare` transaction are parsed with only a non-zero check) [5](#0-4) . The processor's `VerifyBlame` handler passes these indexes straight into `AdditionalBlameMachine::blame` [6](#0-5) .

### Impact Explanation
An unprivileged DKG participant can submit an accusation naming a `Participant` index greater than `n` (or simply not enrolled). Every processor evaluating that blame hits the unchecked `HashMap` index and panics, aborting key generation and crashing the handling thread. This is an availability-only impact matching the CVE's A:H profile (Medium). Note the crate documents that *invalid commitments* may cause panics [7](#0-6) , but here the commitments are valid — the panic is caused by unvalidated `sender`/`recipient` arguments, which is an undocumented crash surface.

### Likelihood Explanation
Triggering requires only control of the `accuser`/`accused`/`faulty` indexes in a blame flow — fields a participant picks when filing an `InvalidDkgShare` or `VerifyBlame` message. The share ciphertext itself can be valid; only the claimed participant index must be out of range or absent, so no cryptographic work is needed. Since PedPoP explicitly models participants as potentially malicious (the entire blame subsystem exists for that), this attacker is in-scope.

### Recommendation
In `blame_internal`/`decrypt_with_proof`, replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get()` + explicit error/return (e.g. blame the accuser or return `InvalidShare`), or validate `sender`/`recipient` against `params.all_participant_indexes()` before any map access. Bounds-check participant fields at the transaction-parsing boundary (`Participant::new(x).filter(|p| u16::from(*p) <= n)`).

### Proof of Concept
1. Complete a PedPoP DKG attempt with `n` participants; `AdditionalBlameMachine` is built with `enc_keys`/`commitments` keyed only by `1..=n`.
2. A participant submits a blame/accusation naming `faulty = Participant::new(n + 1)` (or any absent index), with an otherwise valid `EncryptedMessage<SecretShare>` and a valid `EncryptionKeyProof`.
3. `VerifyBlame` handling calls `AdditionalBlameMachine::blame(accuser, Participant(n+1), share, Some(proof))`.
4. `decrypt_with_proof` reaches `self.enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388`; the key does not exist → panic (`HashMap` index on absent key). Symmetrically, naming a non-participant `sender` panics at `crypto/dkg/pedpop/src/lib.rs:599` on `self.commitments[&sender]`.
