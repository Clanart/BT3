### Title
FROST `Schnorr` algorithm challenge excludes the algorithm transcript, allowing signature replay across protocols sharing a group key - (File: crypto/frost/src/algorithm.rs)

### Summary
The FROST `Schnorr<C, T, H>` algorithm is instantiated with a caller-supplied transcript (`Schnorr::new(transcript)`), which any integrator would reasonably expect to provide domain separation for the signatures it produces — exactly the role the transcript plays everywhere else in Serai (PedPoP PoKs, encryption PoPs, Tributary tendermint `challenge`, etc.). However, the transcript is only consumed for binding-factor (`rho`) generation during `sign()`; the actual signature challenge is computed as `H::hram(&nonce_sums[0][0], &params.group_key(), msg)` — a function of `(R, A, m)` only, with no access to the transcript at all. This is the direct analog of the Clave `isValidSignature()` bug: the signed challenge is not bound to the verifying domain (there `address(this)`, here the algorithm's transcript/context), so a signature produced under one domain is valid in every other domain that uses the same group key.

### Finding Description
In `crypto/frost/src/sign.rs`, `AlgorithmSignMachine::sign` feeds the entire session context — `domain_separate(b"FROST")`, each participant index, each participant's commitments and addendum — into `algorithm.transcript()`, then builds a `rho_transcript` committing `group_key`, `hash_msg(msg)`, and the `preprocesses` challenge. All of that work only determines the binding factors `rho` used to combine nonces. The value that actually defines the signature, the challenge `c`, is computed in `Schnorr::sign_share` as:

```rust
// crypto/frost/src/algorithm.rs
let c = H::hram(&nonce_sums[0][0], &params.group_key(), msg);
self.c = Some(c);
SchnorrSignature::<C>::sign(params.secret_share(), nonces.swap_remove(0), c).s
```

The `Hram` trait signature `fn hram(R: &C::G, A: &C::G, m: &[u8]) -> C::F` has no transcript parameter, so the domain can never reach the challenge. `verify` then checks `sig.verify(group_key, self.c.unwrap())`, and `verify_share` uses the same `c` — so `c` is fully determined by `(R, group_key, msg)`.

The result: if a `ThresholdKeys` group key is used in two distinct signing protocols — e.g., the same validator set key used for two different networks/applications, each instantiating `Schnorr::new()` with its own `RecommendedTranscript` domain separator — a signature `(R, s)` produced for `msg` in protocol A verifies identically in protocol B, because B's verifier recomputes the same `hram(R, A, msg)`. The transcript each side fed to `Schnorr::new` contributes nothing to verification. Serai's own `Schnorrkel` algorithm demonstrates the intended fix pattern: it manually folds its `context` into `msg` (`[len(context), context, msg].concat()`) before delegating to `schnorr.sign_share`, precisely because `Schnorr` does not bind context itself. The plain `Schnorr` algorithm offers no such binding, and nothing in its API documents that `Schnorr::new(transcript)` leaves the produced signatures unbound to that transcript — making this an undocumented transcript/domain-separator collision, analogous to the ERC-1271 hash missing `address(this)`.

### Impact Explanation
An unprivileged party who can cause a FROST group to sign a chosen message in one context obtains a signature that is a forgery-equivalent in any second context verifying with the same group key and algorithm. Concretely, any verifier that computes `c = hram(R, group_key, msg)` — including `SchnorrSignature::verify(group_key, hram(...))` called directly — accepts the replayed signature. This is concrete "signing of an unintended message" acceptance: protocol B accepts a signature it never solicited, for a `msg` that in its domain may carry a different semantic meaning (e.g., an authorization, a batch, a payment). The precondition (the same threshold key backing two domains) is exactly the "shared owner across accounts" precondition of the Clave finding, which was deemed a real, fixable vulnerability.

### Likelihood Explanation
Exploitability requires the same FROST group key to be used in two verification domains that accept the same message bytes — plausible whenever an integrator reuses a `ThresholdKeys` group key across subprotocols or networks while believing the per-protocol transcript passed to `Schnorr::new` provides replay protection. The attacker needs only to obtain or observe one legitimately produced signature (public inputs: a message they caused to be signed and the resulting signature), then submit it to the second domain. No malicious signer, collusion, or key leakage is required — all signers can be fully honest. Severity is bounded by the requirement of key reuse across domains, making this Medium (High if such reuse is common).

### Recommendation
Bind the algorithm's domain into the signature challenge rather than only into `rho`. Options:
- Have `Schnorr::sign_share` (and `verify`/`verify_share`) compute the challenge over `msg` prefixed/framed with a digest of `self.transcript` (e.g., `transcript.challenge(b"schnorr_domain")`), so the produced signature is unforgeable outside the instantiated domain — the analogue of hashing `signedHash` with `address(this)` per EIP-712.
- Alternatively, extend `Hram::hram` to accept the transcript (or a domain challenge derived from it), and update `IetfTranscript`-based `IetfSchnorr` to preserve IETF vector compatibility by only applying the binding for the non-IETF transcript type.
- At minimum, document explicitly that `Schnorr::new(transcript)` does not domain-separate the resulting signature and that callers must fold any context into `msg` themselves, as `Schnorrkel` does.

### Proof of Concept
Conceptual, over `Ristretto` with an arbitrary `Hram` implementation `H` (e.g., `IetfRistrettoHram`):

1. A threshold group completes a DKG (or `musig`) producing `ThresholdKeys<Ristretto>` with group key `A`. Two independent protocols, `P1` and `P2`, both verify Schnorr signatures under `A`. `P1` builds its machines with `Schnorr::<Ristretto, RecommendedTranscript, H>::new(RecommendedTranscript::new(b"Protocol One"))`; `P2` uses `RecommendedTranscript::new(b"Protocol Two")`.
2. The attacker submits `msg` to `P1`'s signing round. Honest signers run `sign()`: all of `P1`'s transcript data (`b"FROST"` domain separator, participants, commitments, `rho_transcript` merge) flows only into `B.calculate_binding_factors`, yielding `R`. `sign_share` computes `c = H::hram(R, A, msg)` — identical to what `P2` would compute — and returns share `s_i = r_i + c·x_i`. `complete` emits `(R, s)` with `sG = R + cA`.
3. The attacker relays `(R, s)` with `msg` to `P2`. `P2`'s verifier recomputes `c' = H::hram(R, A, msg) = c` (its `b"Protocol Two"` transcript never enters this computation) and `SchnorrSignature { R, s }.verify(A, c')` returns true — `P2` accepts a signature produced exclusively under `P1`'s domain, with zero involvement of `P2`'s signers.

The fix (challenge over `domain_challenge || msg`, or folding the transcript into `hram`) makes `c` domain-dependent, so the replayed signature fails verification in `P2`, exactly as the Clave fix bound `signedHash` to `address(this)`.
