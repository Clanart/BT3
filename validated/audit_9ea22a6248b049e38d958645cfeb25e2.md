## Finding

### Title
Hardcoded Arbitrum chain-ID allowlist for block-number source can desynchronize order deadlines and lock escrowed funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase` defines an `ARB_SYS` precompile wrapper and a fixed allowlist of Arbitrum chain IDs used to decide whether order deadlines should be measured against the true L2 block number (via the `ArbSys` precompile) or the raw `block.number` opcode: [1](#0-0) [2](#0-1) 

This is the same bug class as the external report's hardcoded Uniswap router: a network-specific constant (here, a closed set of Arbitrum chain IDs plus the fixed `ArbSys` precompile address `address(100)`) is baked into the contract instead of being derived or configured dynamically, and the deployment is intended to be reused across many EVM networks (the IntentGateway/IntentsBase contracts are explicitly multi-chain, deployed to each supported destination).

### Finding Description
The comment on `IArbSys` states the reason for this special-casing explicitly: on Arbitrum, `block.number` returns an approximate L1 block number rather than the true L2 block count, so the contract must query `ArbSys.arbBlockNumber()` to get an accurate, fast-incrementing block counter for time-based logic (order deadlines, per `OrderPlaced.deadline` which is documented as "The block number after which the order expires").

The chain selection is a closed, hardcoded list — only `ARBITRUM_ONE` (42161), `ARBITRUM_NOVA` (42170), and `ARBITRUM_SEPOLIA` (421614) trigger use of the precompile. Any other Arbitrum-stack chain (Arbitrum Orbit L2/L3 chains, which are commonly deployed with custom chain IDs and also expose `ArbSys` at `address(100)`, and which Hyperbridge's IntentGateway is designed to be redeployed to for new networks) will silently fall through to using raw `block.number` instead. On such a chain, `block.number` still exhibits the same L1-approximation behavior described in the code's own comment, but the contract will not detect it because the chain ID isn't in the allowlist.

### Impact Explanation
Order deadlines are the mechanism that gates the escrow-refund/cancel path (`Expired`/`NotExpired` errors referenced in `IntentsBase.sol`). If the deployed chain uses a `block.number` that increments far more slowly than real elapsed L2 time (because it's actually tracking approximate L1 blocks, as on Arbitrum), a deadline expressed in "block units" will take much longer than the order creator or solver expects to be reached. Concretely:
- Orders that go unfilled can become effectively unrefundable within any reasonable timeframe, since the code path that permits cancellation/refund requires `block.number` (not the true L2 height) to reach the deadline — this can lock escrowed input tokens for a much longer, and potentially indefinite, period from the user's perspective.
- Conversely, if a future Orbit chain's `block.number` semantics diverge in the other direction, deadlines could resolve prematurely, permitting cancellation while a solver-fill is still legitimately in flight, creating a race between the fill and refund paths over the same escrowed funds.

Either direction results in bridged/escrowed user funds moving on a timeline inconsistent with the deployer's and users' expectations, directly matching the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" and fund-lock impact classes named in the bounty scope.

### Likelihood Explanation
This does not require a malicious peer, relayer, or admin — it is a deterministic consequence of deploying the existing, unmodified `IntentsBase`/`IntentGatewayV2` contracts (which are designed for multi-chain redeployment) to any Arbitrum-stack network whose chain ID is not literally `42161`, `42170`, or `421614`. Given the growing number of Arbitrum Orbit chains, this is a realistic deployment scenario for a protocol that markets itself as chain-agnostic, and the failure is silent — there is no revert or warning when the unlisted chain ID falls through to `block.number`.

### Recommendation
Replace the hardcoded chain-ID allowlist with a dynamic check, e.g. attempt to call `ArbSys.arbBlockNumber()` (or detect the presence of the precompile) rather than gating on an enumerated set of chain IDs, or make the block-number source configurable per-deployment (constructor argument or governance-settable parameter) so new Arbitrum-stack networks can be onboarded without silently reverting to L1-approximate `block.number` semantics.

### Proof of Concept
1. Deploy `IntentGatewayV2`/`IntentsBase` to an Arbitrum Orbit L3 chain with `block.chainid` not equal to 42161/42170/421614 (a realistic, supported deployment target for the gateway).
2. A user calls `placeOrder` with a `deadline` computed assuming block-number increments at the true L2 rate (as documented for genuine Arbitrum deployments).
3. Because the chain ID isn't in the allowlist, the contract's internal deadline comparisons use `block.number`, which on this Orbit chain still reflects the slower, L1-approximate counting behavior described in the `IArbSys` comment.
4. The order is never filled by a solver. The user attempts to cancel and reclaim escrowed input tokens once the intended deadline (in real time) has passed, but the `Expired`/deadline check reverts with `NotExpired` because `block.number` has not yet reached the configured value — escrowed tokens remain locked in the contract far beyond the intended timeout, with no admin-level remedy available to the user.
