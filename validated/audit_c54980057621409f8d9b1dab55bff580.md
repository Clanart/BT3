No vulnerability found for this question.

**Reasoning:**

`getExternalCredential` does forward the credential map produced from `parseCredential` straight into `fillCredential` → `exec`'s stdin via `formatCredential`, without filtering unexpected keys [1](#0-0) [2](#0-1) . However this matches the standard `gitcredentials(7)` protocol, not a GitHub-Desktop-introduced flaw:

1. **The `wwwauth[]` fields are a documented, intended part of the git credential-helper protocol.** Git itself (not GitHub Desktop) captures `WWW-Authenticate` response headers and passes them as `wwwauth[N]=` fields to whichever credential helper is configured — this is exactly how real `git-credential-manager` (GCM) is invoked when used directly with git, and GCM is built to receive and safely ignore/interpret this exact key set [3](#0-2) . GitHub Desktop is simply relaying the same protocol payload that git would send to any configured `credential.helper`, GCM included.

2. **Field values are strictly validated before being serialized**, so an attacker cannot use a malformed `wwwauth` value to smuggle extra `key=value` lines (e.g. inject a fabricated `xdg-config=/tmp/evil` line) via newline/NUL injection — `formatCredential` throws if any value contains `\n` or `\0` [4](#0-3) . Each map entry becomes exactly one well-formed `key=value` line, and the key itself is only ever `[a-zA-Z_-]`-style protocol keys produced by `parseCredential` from git's own credential dialog input, not arbitrary attacker-chosen keys smuggled through header text [5](#0-4) .

3. GCM (the external helper binary invoked via `exec`) is a separate, actively maintained project whose credential-fill implementation is required by the same protocol spec to ignore unrecognized keys; unknown keys reaching its stdin is expected protocol behavior, not "reading/writing unintended host-keyed secrets on disk." There is no code path shown where GitHub Desktop itself uses these extra fields to control a filesystem path or storage key on GCM's behalf — GitHub Desktop only passes the credential URL/host used for key derivation (`getCredentialUrl`), and GCM derives its own storage keys internally from the `protocol`/`host`/`path` fields per its own logic, not from arbitrary extra keys.

Since (a) this behavior mirrors intended git/GCM protocol design, (b) value injection into extra lines is blocked by `formatCredential`'s newline/NUL check, and (c) there's no demonstrated sink in GitHub Desktop's own code where an extra key changes a file path or secret storage location, this does not meet the bar for a valid, exploitable vulnerability under the given scope.

export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred
}
```

export const formatCredential = (credential: Map<string, string>) => {
  const lines = []
  for (const [k, v] of credential) {
    if (v.includes('\n') || v.includes('\0')) {
      throw new Error(`forbidden characters in credential value: ${k}`)
    }
    lines.push(`${k.replace(/\[\d+\]$/, '[]')}=${v}\n`)
  }

  return lines.join('')
}
```
