## Title
Payout OP_RETURN operator-identity binding is unauthenticated and forgeable via SIGHASH_SINGLE|ANYONECANPAY malleability, permanently blocking the fronting operator's reimbursement - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` signs only input 0 and output 0 of the payout transaction with the user's `SinglePlusAnyoneCanPay` Schnorr signature, leaving output 2 (the OP_RETURN operator-identity commitment) and output 1 (anchor) completely unauthenticated. Any observer of the broadcast/mempool payout transaction can rebuild a byte-identical-input/output-0 transaction with a different OP_RETURN payload, get it mined first (the original transaction opts into RBF), and permanently corrupt the operator-identity binding that `Verifier::is_kickoff_malicious` relies on.

### Finding Description
The claimed binding is: `withdrawals.payout_payer_operator_xonly_pk[idx]` (as read by `is_kickoff_malicious`) `== operator that funded output 0 of the mined payout tx for that withdrawal`.

`create_payout_txhandler` builds the payout tx with a single signed input (KeySpend, index 0) and three outputs: user payout (0), anchor (1), and `OP_RETURN(operator_xonly_pk)` (2): [1](#0-0) 

The witness set on this handler is the *user's* signature with sighash type `SinglePlusAnyoneCanPay`, enforced both when the operator verifies it and when the gRPC parser accepts it: [2](#0-1) [3](#0-2) 

Per BIP-341, `SIGHASH_SINGLE` only commits to the output *at the same index* as the signed input (index 0), and `ANYONECANPAY` only commits to the signed input itself. Outputs 1 (anchor) and 2 (OP_RETURN operator pubkey) are **not covered** by this signature. Consequently, anyone who obtains the signed payout tx (e.g., from the mempool) can construct a new transaction that reuses input 0's witness verbatim, keeps output 0 identical, but swaps output 2's OP_RETURN payload for an arbitrary 32 bytes (operator B's key, or even a non-operator key) — this is a valid signature for the new transaction too, since the sighash is unchanged.

The operator's own broadcast path funds this tx via `fund_raw_transaction` and queues it under `FeePayingType::RBF`, i.e., it is BIP125-replaceable by design: [4](#0-3) [5](#0-4) 

An attacker (no privileges required — just the ability to see/relay transactions and pay fees) broadcasts a higher-fee replacement with the forged OP_RETURN before/instead of operator A's original. Once mined, `Verifier::update_finalized_payouts` blindly parses whatever OP_RETURN ends up in the confirmed transaction and writes it as `payout_payer_operator_xonly_pk`, with no check that it matches any real operator or the transaction's actual output-0 funding source: [6](#0-5) 

`Verifier::is_kickoff_malicious` then compares this attacker-controlled DB value against `kickoff_data.operator_xonly_pk` (operator A's real kickoff identity) and flags the kickoff malicious on any mismatch: [7](#0-6) 

Because `get_payout_txs_for_withdrawal_utxos` simply looks up whichever transaction spent the registered `withdrawal_utxo` on-chain (a UTXO can only be spent once), there is no secondary check reconciling "who actually paid the user" with "whose pubkey is in the OP_RETURN": [8](#0-7) 

No existing guard closes this gap: `SECP.verify_schnorr` in `Operator::withdraw` only validates the user's signature against the *original* tx shape before broadcast, not against whatever eventually confirms on-chain; `is_deposit_valid`/`is_profitable`/`verify_storage_proofs` do not touch the OP_RETURN payload; and the bridge circuit (`circuits-lib/src/bridge_circuit/mod.rs`) trusts the OP_RETURN of whatever payout tx is included via SPV, with the same lack of binding to output 0's actual payer.

### Impact Explanation
- Operator A funds the user's withdrawal (output 0 pays the user from A's own capital) but the OP_RETURN recorded in the DB no longer names A.
- `is_kickoff_malicious` will return `true` for every subsequent kickoff A sends for this withdrawal (`operator_xonly_pk != kickoff_data.operator_xonly_pk` at core/src/verifier.rs:1887), triggering `handle_kickoff`'s challenge path and ultimately blocking A's `Reimburse` transaction while risking Disprove/collateral burn — this matches "an honest operator permanently unable to be reimbursed" / "an honest operator's collateral burned."
- If the attacker instead writes a real operator B's key, `PayoutCheckerTask::run_once` for B will find and process the unhandled payout via `get_first_unhandled_payout_by_operator_xonly_pk(B)` and credit B for a payout B never funded — matching "an operator reimbursed for a payout it never funded."
- This is repeatable for every withdrawal an operator fronts, across all operators, since the flaw is structural (a protocol-level malleability of the payout tx, not a one-off bug), giving it a broad blast radius.

### Likelihood Explanation
- Preconditions: a finalized deposit + withdrawal registered on Citrea, and an operator having broadcast (but not yet confirmed) the payout tx — a routine, expected state in normal operation.
- The attacker needs no keys, no operator role, no verifier role — only the ability to observe the mempool (any full node/mempool watcher can do this) and pay a modestly higher fee to win the RBF race, since the operator's tx is explicitly RBF-enabled (`fund_raw_transaction` with default `replaceable`, queued as `FeePayingType::RBF`).
- Cost is bounded by the fee differential needed to outbid the operator's payout tx in mempool/miner selection — cheap relative to the withdrawal amount (`bridge_amount`) at stake.
- Fully reproducible on regtest with no mainnet and no live Citrea dependency.

### Recommendation
Bind the operator-identity commitment to the same signature that authorizes spending the user's UTXO. Options:
- Change the sighash type required from the user to `All` (or otherwise cover all outputs) so any OP_RETURN tampering invalidates the signature, or
- Have the *operator* (not just the user) additionally sign/commit to the OP_RETURN output via a second covenant/output structure that can't be altered without invalidating the whole transaction, or
- In `update_finalized_payouts`/`is_kickoff_malicious`, cross-check that the OP_RETURN operator key corresponds to an operator that can be proven (e.g., via a covenant output or presigned commitment) to be the one who funded output 0, rather than trusting an unauthenticated OP_RETURN push.

### Proof of Concept
`cargo test` plan (regtest, no mainnet/live Citrea):
1. Run the existing `deposit_and_withdraw_e2e`/`manual_reimbursement` flow to get operator A's signed `payout_tx` (input 0 = withdrawal UTXO KeySpend with user's `SinglePlusAnyoneCanPay` sig, output 0 = user payout, output 2 = `OP_RETURN(A.xonly_pk)`), broadcast but not yet mined.
2. Build a second transaction reusing input 0's witness and output 0 verbatim, add attacker's own fee input(s)/change, and set output 2's OP_RETURN to operator B's (or a random) xonly pubkey; verify with `SECP.verify_schnorr` that the copied signature still validates against the new sighash for input 0 (asserting no witness recomputation was needed).
3. Broadcast the forged tx with a higher fee (RBF) so it confirms instead of/before A's original; mine it.
4. Assert `db.get_payout_info_from_move_txid(move_txid)` returns `Some(B)` (or `Some(<random>)`), not `Some(A)`.
5. Call `Verifier::is_kickoff_malicious(kickoff_witness_from_A, deposit_data, kickoff_data_with_A, dbtx)` and assert it returns `true`, proving A can never pass this check for this withdrawal despite having funded output 0.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Returns the withdrawal indexes and their spending txid for the given
    /// block id.
    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }
