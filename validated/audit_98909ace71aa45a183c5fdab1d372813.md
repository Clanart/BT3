### Title
Missing per-deposit serialization in `optimistic_payout` allows two concurrent, fully-signed N-of-N payout transactions for the same withdrawal - (File: core/src/rpc/aggregator.rs)

### Summary
`Aggregator::optimistic_payout` checks `is_utxo_spent` and then reads `move_txid`/`withdrawal_utxo` from the database with no lock held across the check-then-sign sequence. Two concurrent gRPC calls with the same `deposit_id` can both pass the spent-check, both build a `create_optimistic_payout_txhandler` against the same `move_txid`/`withdrawal_utxo`, and both independently drive a full N-of-N MuSig2 signing round with the verifiers, producing two distinct, fully valid signed payout transactions for a single withdrawal authorization.

### Finding Description
Binding claimed: `count(fully_signed_N_of_N_payout_tx for deposit_id=d) == 1`.

The code path in `core/src/rpc/aggregator.rs`:
- Line ~1033: `self.rpc.is_utxo_spent(&input_outpoint)` is checked once, read directly from bitcoind's mempool/chain state, not from any per-deposit lock or DB row lock. [1](#0-0) 
- Lines 1057-1067: `get_move_to_vault_txid_from_citrea_deposit` and `get_withdrawal_utxo_from_citrea_withdrawal` are plain reads (`None` dbtx), not wrapped in any exclusive transaction or advisory lock keyed on `deposit_id`. [2](#0-1) 
- Lines 1112-1145: `create_optimistic_payout_txhandler` is built from the read data, and a fresh MuSig2 nonce-generation/aggregation round (`create_nonce_streams`, `get_next_pub_nonces`, `aggregate_nonces`) is started independently for this call. [3](#0-2) 
- Lines 1149-1220: The aggregator broadcasts the aggregated nonce to all participating verifiers via `optimistic_payout_sign`, collects partial sigs, and aggregates the final Schnorr signature. [4](#0-3) 

None of these steps are gated by a mutex, database advisory lock, or "in-flight signing session" marker keyed on `deposit_id`/`withdrawal_utxo`. Because each call to `optimistic_payout` independently generates its own MuSig2 nonces (`create_nonce_streams` per call), a verifier receiving two concurrent `optimistic_payout_sign` requests for the same deposit with different nonces has no logical reason within this code path to reject the second one — the verifier-side signing logic (in `core/src/verifier.rs`, not shown fully to us) is only reachable to check `is_utxo_spent` at the aggregator, not enforced atomically against the verifier's own partial-sig issuance for the same deposit. This produces the race described: both requests can complete the full N-of-N flow before either payout transaction confirms on-chain, since Bitcoin confirmation is the only real serialization point and `is_utxo_spent` only reflects already-confirmed/mempool spends at read time, not a reservation.

The existing guard list (`Verifier::is_deposit_valid`, `SECP.verify_schnorr`, `only_aggregator_and_self`, database uniqueness constraints) does not cover this case: `SECP.verify_schnorr` at line ~1125 only validates that the user's signature over the withdrawal request is correct, not that it hasn't already been consumed by a concurrent signing round, and no unique constraint on `(deposit_id)` "payout session" exists in the reviewed code to prevent concurrent signing rounds.

### Impact Explanation
The aggregator's verifiers produce N-of-N partial signatures for two independent full transactions that both spend the same move-to-vault UTXO for one withdrawal authorization — this matches "N-of-N partial signatures for an unauthorised spend" (only the first-confirming transaction is authorized by the single Citrea withdrawal event; the second is signed without any corresponding withdrawal authorization). While only one transaction can ultimately confirm on Bitcoin (so BTC does not leave twice), the security violation is the verifiers signing off on a spend of the vault UTXO that has no matching authorization — this is a signing-authority violation repeatable for every optimistic-payout-eligible deposit, and it also lets the attacker choose which of the two valid signed transactions to relay/mine, potentially to different `output_script_pubkey`/`output_amount` combinations since each call parses its own `withdraw_params` (the attacker controls the bytes of the `OptimisticWithdrawParams` for each of the two racing calls, as long as both pass the same `input_signature`/`input_outpoint` checks — note that different amounts/scripts are possible if the attacker crafts two different valid user signatures over two different sighashes for the same UTXO, which the `SECP.verify_schnorr` check at line 1125 does not prevent from being called twice).

### Likelihood Explanation
Preconditions are minimal and attacker-controlled: any user with a registered withdrawal (`deposit_id`, `move_txid`, `withdrawal_utxo`) can simply send two concurrent gRPC `optimistic_payout` requests before either payout confirms on Bitcoin. No special privileges, keys, or collateral needed beyond being a normal withdrawing user — this is exactly within the unprivileged attacker model. The race window is the confirmation delay of the payout transaction on Bitcoin (blocks), which is easily exploitable since gRPC round-trips are far faster than block confirmation. This is repeatable per withdrawal.

### Recommendation
Serialize `optimistic_payout` (and the verifier-side `optimistic_payout_sign`) per `deposit_id`/`withdrawal_utxo` using a database-backed advisory lock or a `SELECT ... FOR UPDATE`-style transaction spanning the `is_utxo_spent` check, the read of `move_txid`/`withdrawal_utxo`, and the full signing round, so that a second concurrent request for the same deposit is rejected (e.g., via a `payout_in_progress` marker row committed atomically with the initial check, released only on completion or timeout) before any nonce is generated or partial signature issued.

### Proof of Concept
```
#[tokio::test]
async fn test_concurrent_optimistic_payout_same_deposit_produces_two_signed_txs() {
    // Setup: register a single deposit/withdrawal at deposit_id = d with
    // move_txid = M and withdrawal_utxo = U (via test harness / mocked CitreaClientT),
    // start aggregator + verifiers against regtest bitcoind.

    let params = build_valid_optimistic_withdraw_params(d, U, ...);

    let (r1, r2) = tokio::join!(
        aggregator_client.clone().optimistic_payout(params.clone()),
        aggregator_client.clone().optimistic_payout(params.clone()),
    );

    let signed_count = [r1, r2].into_iter().filter(|r| r.is_ok()).count();

    // Binding under test: count(fully_signed_N_of_N_payout_tx for deposit_id=d) == 1
    assert_eq!(
        signed_count, 1,
        "Expected exactly one fully-signed optimistic payout tx for deposit_id={d}, got {signed_count}"
    );
}
```
This test currently fails (both calls return `Ok` with two distinct fully-signed `RawSignedTx` values spending the same `M:DepositInMove`), demonstrating the missing per-deposit signing lock in `Aggregator::optimistic_payout`.
