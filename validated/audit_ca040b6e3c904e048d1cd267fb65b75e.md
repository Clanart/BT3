## Title
Payout tx uses `SIGHASH_SINGLE|ANYONECANPAY`, letting anyone forge the OP_RETURN "payer" attribution and cause a false reimbursement credit - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The payout transaction that discharges a user withdrawal is built with a user signature covering only the withdrawal input and its matching output via `SIGHASH_SINGLE | ANYONECANPAY` [1](#0-0) . The operator-attribution `OP_RETURN` output (which the whole protocol later trusts to decide *who gets reimbursed*) is **not covered** by that signature [2](#0-1) . Consequently, once the operator broadcasts this transaction, anyone on the Bitcoin network can reuse the same signed input/output pair, add their own funding inputs, and rebroadcast (via RBF) a variant of the transaction with a different `operator_xonly_pk` embedded in the `OP_RETURN`. Verifiers accept whichever version confirms and record its OP_RETURN blindly as the "payer" of the withdrawal.

### Finding Description
`create_payout_txhandler` builds the payout transaction with three outputs: the user payout, an anchor output, and an `OP_RETURN` containing the fronting operator's x-only pubkey [3](#0-2) . Only the withdrawal input (index 0) is signed by the user with `SinglePlusAnyoneCanPay`, and that sighash type commits only to the single output at the same index (the payout output) and the single input being spent — not to any other outputs/inputs added afterward [4](#0-3) .

The operator then funds the transaction via `fund_raw_transaction` (adding wallet inputs to pay the withdrawal amount and fees) and broadcasts it through the TxSender with RBF enabled [5](#0-4) . Because the `OP_RETURN`/attribution output and the added funding inputs are unsigned by the withdrawing user, any third party who observes the unconfirmed transaction in the mempool can:
1. Reuse the same signed withdrawal input and payout output (preserving signature validity, since `SIGHASH_SINGLE|ANYONECANPAY` only binds those).
2. Supply their own funding inputs to cover the payout amount + a higher fee.
3. Replace the `OP_RETURN` output with an arbitrary x-only pubkey (e.g., that of any known operator).
4. RBF-replace the original transaction with this variant.

Verifiers do not authenticate the `OP_RETURN` content in any way — they simply parse whatever confirms on-chain: `update_finalized_payouts` extracts `operator_xonly_pk` straight from the confirmed payout tx's `OP_RETURN` and stores it as `payout_payer_operator_xonly_pk` [6](#0-5) . Downstream, this value is the sole basis for deciding who is entitled to reimbursement: `validate_payer_is_operator` compares it directly against `self.signer.xonly_public_key` with no additional proof of actual funding [7](#0-6) , and `is_kickoff_malicious` uses the same field to decide which operator's kickoff is legitimate [8](#0-7) .

This breaks the intended binding **operator credited == party that funded the payout**: the party who actually pays out of pocket (the malleator) and the party subsequently marked/entitled to claim reimbursement (whichever pubkey the malleator chose to embed) can differ.

### Impact Explanation
This directly matches the Critical impact class "an operator reimbursed for a payout it never funded" / "an honest operator permanently unable to be reimbursed." An attacker can embed a target operator's pubkey in a malleated payout they fund themselves, causing that operator's local bookkeeping (`get_first_unhandled_payout_by_operator_xonly_pk`, `validate_payer_is_operator`) to believe it is the legitimate payer and proceed through the kickoff/reimbursement flow for a payout it never made, or conversely, attacker can embed a garbage/unknown pubkey so that no operator ever matches `payer_xonly_pk`, permanently blocking `get_reimbursement_txs`/`validate_payer_is_operator` for that withdrawal and freezing the deposit's reimbursement path.

### Likelihood Explanation
The only requirement is observing an unconfirmed, broadcast payout transaction in the mempool and being able to fund and RBF-replace it with a higher fee — no privileged role, key compromise, or certificate is needed. This is a standard, unprivileged Bitcoin-network-level capability, consistent with the analog bug class (binding broken by relying on an unauthenticated field instead of a cryptographically enforced one).

### Recommendation
Cover the `OP_RETURN` operator-attribution output (and ideally all outputs/inputs) with the transaction's committed signature data, or otherwise cryptographically bind the payer's identity to the transaction (e.g., have the operator co-sign the whole transaction with `SIGHASH_ALL`, or use a Taproot script path requiring the claiming operator's own signature to spend the payout output before it can be treated as "fronted" by that operator) instead of trusting an unsigned `OP_RETURN` field.

### Proof of Concept
1. Operator Y calls `withdraw()`, producing and broadcasting a payout tx: input0 = withdrawal UTXO (user-signed `SinglePlusAnyoneCanPay`), output0 = user payout, output1 = anchor, output2 = `OP_RETURN(Y_xonly_pk)`, plus Y's funding inputs [2](#0-1) [5](#0-4) .
2. Before confirmation, attacker A observes this in the mempool, extracts input0+output0 (signature still valid under `SIGHASH_SINGLE|ANYONECANPAY`), and constructs tx': input0 (reused) + A's own funding input(s) + output0 (identical) + output2' = `OP_RETURN(X_xonly_pk)` where X is any target operator's pubkey.
3. A broadcasts tx' with a higher fee, replacing Y's tx via RBF.
4. Verifiers' `update_finalized_payouts` records `payout_payer_operator_xonly_pk = X` from the confirmed tx' [9](#0-8) .
5. Operator X's `validate_payer_is_operator`/`PayoutCheckerTask` now believes it is the payer and proceeds to claim reimbursement it never funded, while Y's actual funds went unused for this withdrawal (or, if X's pubkey is arbitrary/unassigned, no operator can ever satisfy the payer check, permanently blocking reimbursement) [10](#0-9) [11](#0-10) .

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
