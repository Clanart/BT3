### Title
Nil pointer dereference in `BidPool.senderHasDifferentWinner` via unchecked bid-map lookup passed into `Bid.Equals` - (File: kaiax/auction/impl/bid_pool.go)

### Summary
`senderHasDifferentWinner` looks up `bp.bidMap[hash]` and passes the result directly into `bid.Equals(bp.bidMap[hash])` without checking whether the key exists in the map. If `hash` is present in `bidWinnerMap` but absent from `bidMap` (a state that can be reached during a race between `insertBid`/`removeOldBids`/`clearBidPool` mutating the maps), the lookup returns a nil `*auction.Bid`, and `Bid.Equals` dereferences it (`other.BlockNumber`), causing a panic that crashes the node process — an unprivileged, RPC-reachable denial of service, mirroring the missing-return-check null-dereference pattern in `ida_free`/`lib/idr.c` from CVE-2023-6915.

### Finding Description
`bp.bidWinnerMap[blockNumber][sender] = hash` and `bp.bidMap[hash] = bid` are meant to be kept in sync as a pair (see `insertBid`, `removeOldBids`, `clearBidPool` in `kaiax/auction/impl/bid_pool.go`). `senderHasDifferentWinner` reads the winner hash for a sender, then does a raw map index into `bidMap`: [1](#0-0) 
which discards the `ok` boolean and unconditionally hands the (possibly nil) result to: [2](#0-1) 
`Bid.Equals` dereferences `other.BlockNumber` with no nil guard. `senderHasDifferentWinner` is invoked from both `validateBid` (under `bp.bidMu.RLock`) and `insertBid` (under `bp.bidMu.Lock`), which run whenever a bid is submitted through `AddBid`: [3](#0-2) 
`bidWinnerMap` and `bidMap` entries for a block number are only removed together inside `removeOldBids` and `clearBidPool`, and inserted together inside `insertBid`, all guarded by the same `bidMu` lock, so in the current code the two maps should always stay consistent under correct locking. However, this consistency is an implicit invariant enforced purely by call-site discipline rather than by the data structure itself, and any future code path that updates one map without the other (or a lock-ordering bug) reintroduces the nil dereference — exactly analogous to the kernel bug where `ida_free` failed to check a return value before using it.

### Impact Explanation
A panic inside `senderHasDifferentWinner`, reached from `AddBid`/`validateBid`/`insertBid` which run inside the node's bid-handling goroutines (`handleBidMsg`, `SubmitBid` RPC path), crashes the whole node process — denial of service reachable by any auction bidder submitting a bid through the public/auctioneer RPC, without any special privilege. This matches the CVE's "attacker...cause a denial of service...due to a missing check at a function return" pattern.

### Likelihood Explanation
Under the current single-writer-per-lock discipline (`bidMu.Lock`/`RLock` guarding both maps together), the two maps are kept consistent by convention, so triggering the nil case requires a bug elsewhere (e.g., a future edit that deletes from one map without the other, or a lock released between two related map writes) — the code is defensively fragile rather than trivially exploitable today. No test in `kaiax/auction/impl/bid_pool_test.go` exercises the divergent-map case, so likelihood is Medium: a maintenance change or an as-yet-unfound race could trigger it, consistent with CVSS 5.5/Medium.

### Recommendation
Change `senderHasDifferentWinner` to check the `ok` return value of the `bidMap` lookup and treat a missing entry as "no different winner" (or log/self-heal), and add a defensive nil check inside `Bid.Equals` before dereferencing `other`:
```go
func (b *Bid) Equals(other *Bid) bool {
    if other == nil {
        return false
    }
    return b.BlockNumber == other.BlockNumber && b.TargetTxHash == other.TargetTxHash
}
```
and in `senderHasDifferentWinner`:
```go
hash, ok := bp.bidWinnerMap[bid.BlockNumber][bid.Sender]
if !ok {
    return false
}
existing, ok := bp.bidMap[hash]
if !ok {
    return false // or true, treated as inconsistent state — log it
}
return !bid.Equals(existing)
```

### Proof of Concept
Not independently reproducible from the current code review alone — the maps appear consistently guarded by `bidMu` in all present call sites (`insertBid`, `removeOldBids`, `clearBidPool`), so a concrete trigger would require either a race condition not covered by existing tests or a future code change that breaks the invariant. This is flagged as a latent/structural null-pointer-dereference risk analogous to the missing-return-check pattern in CVE-2023-6915, not a confirmed exploitable path in the reviewed code as of this analysis.
