### Title
Quadratic-to-cubic resource exhaustion in `ThresholdKeys::read` via attacker-controlled `t`/`n` parameters - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts untrusted bytes and lets the attacker specify `t` and `n` up to `u16::MAX` (65535). `ThresholdKeys::new` then computes the group key by evaluating `interpolation_factor` once per threshold participant, where each Lagrange `interpolation_factor` call iterates over the whole included set — O(t²) field multiplications plus O(t) point multiplications, on top of O(n) expensive `read_G` decompressions. A single small message therefore forces minutes-to-hours of CPU work, analogously to CVE-2025-32034 where a small query forced prohibitive planner work due to an unchecked expansion count (CWE-770).

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` from the stream and then calls `ThresholdKeys::new`, which only checks `t <= n` and `i <= n` — both u16, so up to 65535 — with no resource bound [1](#0-0) . `ThresholdKeys::new` builds `t = 1..=params.t()` and computes `verification_shares[i] * interpolation.interpolation_factor(*i, &t)` for every one of the t participants [2](#0-1) . `interpolation_factor` for `Interpolation::Lagrange` loops over the entire `included` slice performing a field multiply and subtraction per element — O(t) work per call [3](#0-2) . The result is O(t²) scalar operations plus t point-multiplications, and additionally `read` performs n `read_G` point decodings before that (each a full decompress + subgroup-consistent parse) [4](#0-3) . With `Interpolation::Constant` selected (tag `0`), the reader also consumes n scalars via `read_F` [5](#0-4) .

With t = n = 65535, a roughly 2 MB input (65535 encoded points) triggers ~4.3×10⁹ field multiplications for interpolation alone — a ~10⁶× amplification between bytes supplied and work performed — plus 65535 point multiplications for the group-key sum and 65535 point decompressions. This is reachable by an unprivileged party feeding bytes to `ThresholdKeys::read`, which the task scope explicitly lists as attacker-reachable.

### Impact Explanation
Any service or protocol handler that deserializes `ThresholdKeys` from untrusted input (key-distribution messages, recovery flows, share-import APIs) can be driven into effectively unbounded CPU consumption by a single short message, denying service to the victim. This mirrors the advisory: a cheap input produces an internally expanded workload (here `t²` interpolation work + `n` point decodings) with no expansion limit metric or cap, exactly the CWE-770 pattern.

### Likelihood Explanation
The public `ThresholdKeys::read`/`read_F`/`read_G` surface accepts a raw `io::Read` stream and performs all expensive work before any semantic rejection that would bound cost (the `t <= n` check happens inside `ThresholdParams::new` only *after* n point reads, and permits t=n=65535). No size limit, participant cap, or "expansion limit" equivalent exists. A peer able to submit key material bytes triggers it trivially; the only constraint is the ~2 MB input for the worst case, and even small inputs (t = n = a few hundred) give quadratic blowup.

### Recommendation
Enforce a sane upper bound on `t`/`n` early in `ThresholdKeys::read` (before allocating or decoding n group elements), e.g., reject `n` above the protocol's maximum validator set size. Equivalently, add a check analogous to the fix's "fragment expansion limit": compute the projected work (`n` reads + `t²` interpolation) from the header fields and reject before performing it. `ThresholdParams::new` could additionally gain a documented `MAX_PARTICIPANTS` bound so all callers are protected regardless of input source.

### Proof of Concept
Conceptual byte stream fed to `ThresholdKeys::<C>::read`:

```
id_len (u32 LE) = C::ID.len() ; id = C::ID
t = 0xFFFF (u16 LE), n = 0xFFFF, i = 0x0001
interpolation = 0x01 (Lagrange)
secret_share  = 32 bytes encoding a valid scalar
verification_shares = 65535 × G::Repr valid point encodings
```

Processing: `read` loops 65535 times over `read_G` (each a full point decompression) [4](#0-3) , then `ThresholdKeys::new` runs 65535 `interpolation_factor` calls, each iterating 65535 elements — ≈4.3×10⁹ `F` multiplications/inversions-path work plus 65535 point multiplications [2](#0-1) [6](#0-5) . A ~2 MB input thus consumes effectively unbounded CPU, with no limit check anywhere in the path.
