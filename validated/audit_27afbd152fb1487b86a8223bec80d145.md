### Title
Divergent conflict-marker parsing between prompt extraction and file reassembly allows a malicious merge/rebase branch to corrupt Copilot-resolved commits - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The external report's broken invariant is "the code assumes uniform segments (epoch length) when segments actually vary, and processes them positionally instead of individually verifying each segment." The Desktop analog is in the Copilot merge-conflict auto-resolution feature: the file is scanned for `<<<<<<<`/`=======`/`>>>>>>>` conflict markers **twice**, by two independently-written state machines, and the results are stitched back together purely by **positional index**, with no check that the two scans agree on hunk boundaries or count. [1](#0-0) [2](#0-1) 

### Finding Description
`extractConflictHunks()` walks the raw conflicted file once to build the hunks that are shown to the Copilot model in the prompt: it collects "ours" lines until it sees a `=======`/`|||||||` marker, then "theirs" lines until it sees the first line matching the `>>>>>>>` regex, treating that as the closing marker of the current hunk. [3](#0-2) 
If no closing marker is ever found, the hunk is discarded via `continue` — but because the inner loops already advanced `i` to end-of-file while searching, the *entire remainder of the file is silently abandoned*, potentially dropping legitimate hunks that occur later in the file. [4](#0-3) 

Later, `reassembleResolvedFile()` re-scans the *same raw file from scratch*, independently, to splice the model's per-hunk `resolvedContent` back into place. Its malformed-block detection is written differently: it treats a leading `<<<<<<<` as malformed only if it can't find *both* a later separator and a later `>>>>>>>` anywhere in the rest of the file — and if malformed, it pushes only the single marker line as "regular content" and resumes scanning from the very next line, rather than abandoning the rest of the file. [5](#0-4) 

The two functions:
1. Are maintained/implemented separately with different tolerance for malformed or repeated marker-like lines,
2. Do not communicate hunk boundaries to each other,
3. Are stitched together purely by an incrementing `hunkIndex`/array-position (`hunkResolutions[hunkIndex]`), with **no verification that the count of markers found in the second scan matches the count of hunks sent to the model in the first scan**.

This is structurally the same accounting bug as the report: the code assumes each "unit" (conflict hunk / epoch) is discovered identically and uniformly across two separate calculations, when a crafted input can make the two calculations disagree. Just as the reward math averaged across time instead of respecting each epoch's real boundary, `reassembleResolvedFile` blindly maps resolution `i` onto marker-block `i` instead of verifying that marker-block `i` is the *same* semantic hunk that resolution `i` was generated for.

### Impact Explanation
If an attacker crafts a branch/PR containing a conflicted file with a marker-like line embedded inside otherwise-legitimate content (e.g. a code comment, string literal, or generated file containing a stray `<<<<<<<`/`=======`/`>>>>>>>`-looking line), the extraction pass and the reassembly pass can disagree about how many hunks exist and where their boundaries fall. When that happens, `reassembleResolvedFile` will splice a resolution generated for one logical conflict onto the location of a different physical marker block in the file — i.e., a `writeFile` of attacker-influenced or simply mismatched content directly into the user's working tree, which is then `git add`-ed and committed/pushed on the user's behalf. [6](#0-5) 

This is "silent corruption of what the user commits or pushes": the resulting file has no conflict markers, looks resolved, and is written and staged automatically; nothing in the pipeline verifies that the number/order of markers found by the two scanners agree.

### Likelihood Explanation
The path requires only ordinary, expected user behavior: cloning/pulling a branch that has a genuine merge conflict and using GitHub Desktop's built-in "resolve conflicts with Copilot" feature — no elevated privileges, no local/physical access, no social engineering beyond the attacker's branch/PR being merged or rebased against, which is the normal collaborative workflow the feature is designed for. The size and content-safety guards in `getHunkSkipReason` limit line length and total conflict size but do nothing to prevent marker-like lines from appearing inside legitimate-looking content within those limits. [7](#0-6) 

There is a manual-override review step (`ShowCopilotConflicts` / `manualResolutions`) before writing, but that dialog displays the *already reassembled* content — i.e., the corrupted output itself — so it does not reliably catch a positional mismatch unless the user manually diffs every hunk against the original markers. [8](#0-7) 

### Recommendation
Do not re-scan the raw file twice with two independently-implemented parsers. Have `extractConflictHunks` return the exact line ranges (marker positions) of each hunk it identified, and have `reassembleResolvedFile` consume those same recorded ranges instead of re-detecting markers from scratch. Additionally, assert that the number of marker blocks found during reassembly equals the number of hunks sent to the model, and fail closed (skip the file, surface it to the user for manual resolution) rather than silently proceeding on any mismatch — mirroring the report's recommendation to account for each unit individually rather than assuming uniformity across two separate passes.

### Proof of Concept
Conceptual PoC (exact line-by-line divergence would need to be confirmed by running the parser, which I could not execute in this session):
1. Attacker opens a PR whose branch, when merged, produces a conflicted file containing:
   - A genuine conflict block `A` (`<<<<<<<`/`=======`/`>>>>>>>`) with benign content.
   - Immediately after, in the "theirs" section of block `A`, a line that itself matches the `>>>>>>>` marker regex (7+ `>` followed by whitespace/EOL) as part of ordinary content (e.g. a shell heredoc, ASCII banner, or diff-format sample embedded in a doc/config file).
   - A second, genuine conflict block `B` further down in the file.
2. `extractConflictHunks` terminates block `A`'s "theirs" collection at the embedded fake marker (first match wins), truncating block `A` and treating the real closing marker of `A` (and anything up to the next real `<<<<<<<`) as ordinary untouched file content — potentially merging into `B`'s `contextBefore` or being dropped, and the hunk count sent to the model does not correspond to the true marker layout.
3. `reassembleResolvedFile`, scanning from scratch with looser malformed-detection logic, resolves the same content boundaries differently.
4. The victim accepts Copilot's suggested resolution; `applyCopilotResolutions` writes the reassembled content to disk and stages it via `git add`, without the review dialog reliably surfacing the positional mismatch, resulting in incorrect/attacker-influenced content being committed and possibly pushed. [9](#0-8) 

Given the complexity of the two independent state machines, I recommend a background engineer construct concrete marker sequences and run both `extractConflictHunks` and `reassembleResolvedFile` against them directly (unit-test style, as already scaffolded in `app/test/unit/copilot-conflict-resolution-test.ts`) to confirm the exact divergent boundary and produce a minimal failing fixture.

export function getHunkSkipReason(
  hunks: ReadonlyArray<IConflictHunk>
): string | null {
  let totalContent = 0

  for (const hunk of hunks) {
    const sides = [hunk.oursContent, hunk.theirsContent, hunk.baseContent ?? '']
    for (const side of sides) {
      totalContent += side.length
      for (const line of side.split('\n')) {
        if (line.length > MAX_CONFLICT_LINE_LENGTH) {
          return 'Conflict contains lines too long to resolve automatically'
        }
      }
    }
    if (totalContent > MAX_CONFLICT_CONTENT_SIZE) {
      return 'Conflict region too large to resolve automatically'
    }
  }

  return null
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
