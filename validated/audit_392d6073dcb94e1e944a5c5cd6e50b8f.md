# Authority Set Misbinding in Tendermint Light Client State Promotion — (File: `modules/consensus/tendermint/verifier/src/verifier.rs`)

## Summary

`create_updated_trusted_state` unconditionally promotes the *stored* `next_validators` set into the new trusted `validators` field on every successful header update — even when the header was actually verified against the *current* validator set (no rotation happened). This decouples "the validator set recorded as having finalized the block" from "the validator set that actually produced the signatures verified by `extract_validators`," violating the stated invariant that a consensus update must advance only under the exact set that authenticated it. This client backs both the Polygon (`modules/ismp/clients/polygon/src/lib.rs::verify_consensus`) and generic Tendermint (`modules/ismp/clients/tendermint/src/lib.rs::verify_consensus`) ISMP consensus clients reachable unsigned via `pallet_ismp::handle_unsigned`.

## Finding Description

`verify_header_update` first calls `extract_validators`, which correctly determines *which* stored set (`trusted_state.validators` or `trusted_state.next_validators`) actually matches `header.validators_hash`, and uses that matched set for BFT signature verification: [1](#0-0) 

After verification succeeds, `create_updated_trusted_state` builds the next `TrustedState` but does **not** use the information about which branch actually matched. It always does: [2](#0-1) 

i.e. `validators = old_trusted_state.next_validators.clone()` unconditionally, regardless of whether the just-verified header was signed by the old `current` set (no rotation, `extract_validators` took the "current" branch) or the old `next` set (real rotation). The `rotates` flag only guards whether `next_validators`/`next_validators_hash` are replaced — it does nothing to guard the `validators` (current) field.

Consequence: for a legitimate, honestly-signed header at height H that is still within the *current* epoch (i.e., `header.validators_hash == hash(old current set)`, no rotation signaled), the update is correctly verified using the current set, but the resulting stored state falsely records the *next* (future, not-yet-active) validator set as the set that finalized block H. The recorded "current authority set" for the new trusted height no longer matches the authority set that actually finalized that block.

This is reachable by any unprivileged party relaying a genuine, already-publicly-available header/commit through `pallet_ismp::handle_unsigned(origin=None, messages)` into `PolygonClient::verify_consensus` / `TendermintClient::verify_consensus`, both of which call `tendermint_verifier::verify_header_update` directly with no additional binding check: [3](#0-2) [4](#0-3) 

## Impact Explanation

The stored trusted state (`current validators` / `next validators`) is the sole basis for authenticating all future consensus updates via `extract_validators`. Once corrupted, the trust anchor for the light client silently collapses (in the non-rotating case, `next_validators` was unchanged, so after promotion `validators == next_validators`, effectively freezing/desynchronizing the two slots from what the chain's real epoch schedule dictates). This breaks the fundamental light-client invariant that "the accepted authority set == the authority set that finalized the block," corrupting the anchor used by both the Polygon and generic Tendermint consensus clients that gate all downstream state-commitment acceptance for cross-chain messages, and can either brick the client (denial of new legitimate updates once the real chain continues signing with the true current set) or allow premature/out-of-schedule acceptance of a future epoch's authority as already active, undermining the sequencing guarantees the invariant is meant to preserve.

## Likelihood Explanation

Any unprivileged relayer can trigger this merely by submitting one legitimate, honestly-signed, non-rotating header (i.e., a normal same-epoch update, which is a routine, expected occurrence for any chain with multi-block epochs) through the unsigned ISMP message path. No malicious validator, relayer, or forged signature is required — only public chain data and the standard message-submission entrypoint.

## Recommendation

`create_updated_trusted_state` must track and use which branch `extract_validators` actually matched (current vs. next) to decide the new `validators` field: if the header was verified against the *current* stored set (no rotation), the new `validators` must remain the current set (or, if height doesn't increase the active set, be explicitly derived from the actually-matched signer set), and only promote `next_validators` into `validators` when the header truly signals/uses the next set. Thread the matched `ValidatorSet` (or a boolean flag) from `extract_validators` through to `create_updated_trusted_state` instead of re-deriving it independently and unconditionally.

## Proof of Concept

1. Build `trusted_state` with `validators = V1` (epoch N), `next_validators = V2` (epoch N+1, publicly known ahead of activation), `next_validators_hash = hash(V2)`.
2. Obtain (from a real, honest node — no malicious party needed) a genuine signed header for a later height H that is still within epoch N: `header.validators_hash == hash(V1)`, `header.next_validators_hash == hash(V2)` (unchanged, `rotates = false`).
3. Submit via `pallet_ismp::handle_unsigned(origin=None, [Message::Consensus(proof)])` → `PolygonClient::verify_consensus`/`TendermintClient::verify_consensus` → `verify_header_update`.
4. Verification succeeds using `V1` (per `extract_validators`), matching the intent. But the assertion to check: the resulting `updated_state.trusted_state.validators` equals `V2`, not `V1`, even though `V1` — not `V2` — finalized block H, per [2](#0-1) . This violates the "assert consensus state does not advance to an authority set that didn't authenticate the block" fast-validation check from the question.

fn extract_validators<'a>(
	trusted_state: &'a TrustedState,
	consensus_proof: &'a ConsensusProof,
) -> Result<ValidatorSet, VerificationError> {
	let header = &consensus_proof.signed_header.header;
	let current_set = ValidatorSet::new(trusted_state.validators.clone(), None);
	let next_set = ValidatorSet::new(trusted_state.next_validators.clone(), None);

	// Validate current and next validator set hashes using the shared helper
	let current_hash_result =
		validate_validator_set_hash(&current_set, header.validators_hash, false);
	let next_hash_result = validate_validator_set_hash(&next_set, header.validators_hash, true);

	let validators = if current_hash_result.is_ok() {
		current_set
	} else if next_hash_result.is_ok() {
		next_set
	} else {
		return Err(VerificationError::Invalid(format!(
			"Unknown validator set hash: {:?}",
			header.validators_hash
		)));
	};

fn create_updated_trusted_state(
	old_trusted_state: &TrustedState,
	consensus_proof: &ConsensusProof,
) -> Result<UpdatedTrustedState, VerificationError> {
	let header = &consensus_proof.signed_header.header;

	// Promote next_validators to validators
	let validators = old_trusted_state.next_validators.clone();

	// Only a signalled rotation may replace the stored next set, and only with a list
	// that hashes to the new signed next_validators_hash. When the interval is unchanged
	// we keep the trusted set and ignore any list the proof happened to carry.
	let old_next_hash = Hash::Sha256(old_trusted_state.next_validators_hash);
	let rotates =
		!header.next_validators_hash.is_empty() && header.next_validators_hash != old_next_hash;
