## Analysis

The ALCX report's core pattern is: **a reward that has already been "earned"/computed for an account becomes permanently unclaimable because the account is destroyed before the reward is actually delivered, and no guard prevents (or compensates for) that destruction.**

Agave has a direct structural analog to this in the **partitioned epoch-rewards mechanism** for stake accounts.

### Title
Partitioned stake rewards are permanently burned if a staker closes/withdraws their stake account between reward calculation and reward distribution - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
Stake rewards are computed once at the epoch boundary ("calculation" block) into an immutable `PartitionedStakeRewards` list, but the actual crediting to accounts happens later, spread across several subsequent blocks ("distribution" phase). If, in that gap, the staker executes an ordinary, unprivileged `Withdraw` on the stake program that empties/closes the stake account, the stake pubkey disappears from `StakesCache`. When that account's turn in the partition comes up, distribution fails with `DistributionError::AccountNotFound` and the already-computed reward is unconditionally burned rather than paid — mirroring exactly the ALCX pattern of "reward accrued but stuck/lost because the underlying position was destroyed first."

### Finding Description
Reward calculation happens once, producing `PartitionedStakeReward` entries containing a `stake_reward`/`block_reward` value for each stake pubkey that was active in the rewarded epoch: [1](#0-0) 

These entries are spread out over multiple blocks via `distribute_partitioned_epoch_rewards` / `distribute_epoch_rewards_in_partition`, which is a multi-block process, not atomic with calculation: [2](#0-1) 

At the actual distribution step, each pubkey is looked up in the *current* `StakesCache`, not the cache snapshot at calculation time: [3](#0-2) 

If the account no longer exists in the cache (e.g. because the owner fully withdrew/closed it via the stake program's ordinary `Withdraw` instruction in the intervening blocks), the code explicitly takes the `AccountNotFound` branch and burns the reward instead of delivering it: [4](#0-3) 

The code's own comment acknowledges the assumption this relies on — that "stake-program restrictions" prevent such a state mutation from happening in that window — but the stake program's `Withdraw` instruction has no notion of `EpochRewardStatus`/pending distribution at all (no such check exists anywhere under `programs/stake*`), so nothing actually enforces that assumption: [5](#0-4) 

This is corroborated by a unit test in the calculation module that explicitly demonstrates a stake reward computed for calculation can be `> 0` even for a stake that is deactivating/being withdrawn, and that the recalculation path treats already-consumed vs. not-yet-consumed partitions differently — i.e., the system already recognizes stake accounts can have positive computed rewards while transitioning out of the delegated set: [6](#0-5) 

### Impact Explanation
This matches the report's "Permanent freezing of unclaimed yield" / "fails to deliver promised returns" impact class. A reward that the protocol has already computed and committed to (it is part of `all_stake_rewards`, backed by lamports reserved in the `EpochRewards` sysvar / bank capitalization) is silently and permanently burned — `stake_reward_lamports_burned` — instead of being paid to the staker, with only a `debug!`/`error!` log and no recovery path. Nothing (like `remaining_balance` checks in the vote program's `withdraw`, which is exactly analogous and does protect `pending_delegator_rewards`, see `programs/vote/src/vote_state/mod.rs` `withdraw`) exists in the stake program to prevent a staker from closing their own account while a computed-but-undelivered reward is still pending for it.

### Likelihood Explanation
Likelihood is bounded by how easy it is to align stake deactivation/cooldown so that a stake account becomes fully withdrawable to zero exactly in the first few blocks following the reward-calculation block (the distribution phase spans only a handful of blocks, chosen by `REWARD_CALCULATION_NUM_BLOCKS`/partitioning), while it was still counted as earning a positive reward for the just-finished rewarded epoch. This requires precise but achievable timing by an ordinary unprivileged staker using only standard, permissionless stake instructions (`Deactivate`, `Withdraw`) — no malicious validator, RPC, or privileged access is required.

### Recommendation
Either (a) have the stake program refuse full account closure/withdrawal while an `EpochRewardStatus::Active` distribution is outstanding for that stake pubkey, or (b) have `build_updated_stake_reward` fall back to crediting the reward lamports elsewhere (e.g., to the withdrawal destination, or by recreating a minimal account) instead of unconditionally burning them when `AccountNotFound` is hit, analogous to how `programs/vote/src/vote_state/mod.rs::withdraw` blocks closing a vote account while `pending_delegator_rewards > 0`.

### Proof of Concept
1. Delegate a stake account and let it earn credits through epoch `N` (active the whole epoch).
2. At/just after the epoch `N+1` boundary, the bank's calculation block computes a `PartitionedStakeReward` with `stake_reward > 0` for this stake pubkey, per `redeem_delegation_rewards`/`calculate_stake_rewards_and_commissions` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs`).
3. Before the block whose partition index contains this pubkey is reached (distribution is spread over several blocks per `distribute_partitioned_epoch_rewards`), submit an ordinary `Deactivate` (if not already deactivating from a prior epoch) followed by `Withdraw` for the full balance of the stake account, removing it from `StakesCache`.
4. When `store_stake_accounts_in_partition` reaches this pubkey's partition, `build_updated_stake_reward` returns `Err(DistributionError::AccountNotFound)` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs` lines 249-251), and the reward amount is added to `stake_reward_lamports_burned` instead of being paid — the staker's already-computed reward is permanently lost.

    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

        assert!(
            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);
        }
