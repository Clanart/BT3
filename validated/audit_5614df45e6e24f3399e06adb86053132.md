### Title
Stale-height `handleGetRequestTimeouts` can trigger `onGetTimeout` after a GET request was already answered via `onGetResponse` — ([File: evm/src/core/HandlerV2.sol])

### Summary
On `EvmHost`, a GET request's `FeeMetadata` in `_requestCommitments` is never deleted once its response is delivered through `dispatchIncoming(GetResponse)`, and `handleGetRequestTimeouts` only checks non-membership of a response receipt against an arbitrary, caller-chosen historical `message.height`. Together, this allows a GET request that was already legitimately fulfilled (module received `onGetResponse`) to still be timed out later via `onGetTimeout`, because the timeout path has no check against the current/local response-delivery state — only a proof anchored on a stale height that predates the response.

### Finding Description
`dispatchIncoming(GetResponse, ...)` in `evm/src/core/EvmHost.sol` (lines 824-847) records `_responseReceipts[commitment]` and, on success, pays the relayer fee from `_requestCommitments[commitment].fee` — but it never deletes `_requestCommitments[commitment]`: [1](#0-0) 

By contrast, `dispatchTimeOut` for a GET timeout (lines 856-870) deletes `_requestCommitments[commitment]` up front (with reinsertion only on a failed callback), following the correct "delete-then-retry" pattern: [2](#0-1) 

`HandlerV2.handleGetRequestTimeouts` (evm/src/core/HandlerV2.sol, lines 293-321) gates the timeout purely on:
1. `challengePeriod` elapsed for `message.height`,
2. `state.stateRoot != 0` at `message.height`,
3. `request.timeout() > state.timestamp` (i.e., timed out per that height's timestamp),
4. `meta.sender != address(0)` in `_requestCommitments` (never cleared for GET-response success, per above),
5. A non-membership proof of `RESPONSE_RECEIPTS_STORAGE_PREFIX + commitment` in the Substrate/pallet-ismp trie at `state.stateRoot` for the chosen `message.height`. [3](#0-2) 

Because `_stateCommitments` for a state machine ID retains historical heights indefinitely (heights are only added via consensus/intermediate-state updates, never pruned in `EvmHost.sol`), any previously-committed height where the response had genuinely not yet been recorded on Hyperbridge remains a valid `message.height` to submit against, even long after the response was legitimately delivered and answered on this host via `onGetResponse`. Nothing in `handleGetRequestTimeouts` requires `message.height` to be the *latest* height, nor does it check the *local* `_responseReceipts` mapping (which would correctly show the response was already delivered).

The result: an unprivileged caller can submit a `GetTimeoutMessage` anchored at a stale (but still legitimate/queryable) height, produce a genuine non-membership proof for that old height, and pass every check in `handleGetRequestTimeouts`, causing `IApp.onGetTimeout()` to fire on the destination module for a request that has already been fulfilled via `onGetResponse()`.

### Impact Explanation
This is a double-settlement/duplicate-callback bug: application modules built on `IApp` are documented to use `onGetTimeout` for "cleanup and rollback" (see `docs/content/developers/evm/messaging/get-requests.mdx`), which typically un-does state changes made in anticipation of a response (e.g., deleting `pendingRequests[commitment]`, or in more elaborate integrations, refunding escrowed value or reverting optimistic state). If a module also performed value-moving logic on `onGetResponse` (e.g., releasing funds, marking an intent settled, crediting a beneficiary) and then *also* executes rollback/refund logic on the later spurious `onGetTimeout`, the module can suffer double-refunds, incorrect accounting, or unauthorized state transitions — violating the "move exactly once" invariant central to the bounty scope (double-claim/double-settlement, false state acceptance via a stale-but-technically-valid proof).

### Likelihood Explanation
The attack requires no privileged role, malicious relayer, prover, or governance actor — any address can call `handleGetRequestTimeouts` (documented as "Access: Permissionless" in `docs/content/developers/evm/api/ihandler.mdx`) with a genuine non-membership proof sourced from a historical (but still-tracked) Hyperbridge height. The only requirements are: (a) the GET request's `timeout_timestamp` has passed relative to that historical height's timestamp (trivially true for old heights), and (b) the response wasn't yet recorded at that older height (true by construction, since the response was only recorded at a later height). This is directly analogous to the Cosmos `x/crisis` report's core issue — a failure/negative-invariant condition (here: "was this GET request actually still outstanding?") is checked against stale/incomplete data instead of halting or requiring freshness, letting an attacker repeatedly trigger the unintended path.

### Recommendation
- In `dispatchIncoming(GetResponse, ...)`, delete `_requestCommitments[commitment]` once the response has been successfully dispatched (mirroring the GET-timeout delete-then-retry pattern), so `meta.sender == address(0)` in `handleGetRequestTimeouts` correctly rejects a timeout for an already-answered request.
- Additionally/alternatively, have `handleGetRequestTimeouts` reject non-latest heights for timeout proofs, or explicitly check the local `_responseReceipts[commitment]` before dispatching a timeout, ensuring a timeout cannot be processed once a response has already been recorded locally, regardless of which historical remote height is used for the non-membership proof.

### Proof of Concept
1. Source-chain module `M` dispatches a `GetRequest` via `EvmHost`; `_requestCommitments[commitment]` is set with `fee` and `sender`.
2. Response is produced, relayed, and delivered: `HandlerV2.handleGetResponses` verifies inclusion and calls `host.dispatchIncoming(GetResponse, relayer)`. This sets `_responseReceipts[commitment]`, calls `M.onGetResponse(...)` successfully, and pays the relayer fee — but `_requestCommitments[commitment]` is left untouched (evm/src/core/EvmHost.sol:824-847).
3. Attacker (any address) finds a Hyperbridge state-commitment height `H_old` that was committed to this `EvmHost` *before* the response was written into Hyperbridge's pallet-ismp storage (such a height necessarily exists, since the response was written at some later height).
4. Attacker constructs a non-membership proof of `RESPONSE_RECEIPTS_STORAGE_PREFIX + commitment` against `H_old`'s state root (true, since the response hadn't been recorded yet at `H_old`) and calls `handleGetRequestTimeouts(host, GetTimeoutMessage{ timeouts: [request], height: H_old, proof })`.
5. All checks pass: challenge period for `H_old` has elapsed, `state.stateRoot != 0`, `request.timeout() > state.timestamp` (true for an old height), `meta.sender != address(0)` (still true — never cleared), and the non-membership proof verifies.
6. `host.dispatchTimeOut(...)` fires, calling `M.onGetTimeout(...)` — even though `M.onGetResponse(...)` already executed successfully for the same commitment, producing whatever double-execution effects `M`'s timeout-cleanup logic implies. [3](#0-2) [4](#0-3)

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
    }
