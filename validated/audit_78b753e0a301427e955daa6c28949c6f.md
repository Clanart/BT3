### Title

Invalid FROST signature shares can evade blame by cancelling each other - ([File: crypto/frost/src/sign.rs](crypto/frost/src/sign.rs))

### Summary

`AlgorithmSignatureMachine::complete` verifies only the sum of all submitted signature shares before checking any individual share. If the aggregate Schnorr signature verifies, the function returns it immediately and never invokes the per-share `BatchVerifier`, allowing two or more malformed shares whose errors cancel to be accepted without attributing fault. [1](#0-0) 

### Finding Description

The completion path first sums the caller’s share with every externally supplied `SignatureShare` and calls `Algorithm::verify` on that sum. [2](#0-1)  Individual accountability is only evaluated after aggregate verification fails, by queuing `verify_share` statements for every included participant. [3](#0-2) 

For the Schnorr algorithm, the aggregate check is the standard equation `R + cA - sG == 0`. [4](#0-3)  Each individual share is separately checked as `R_i + cY_i - s_iG == 0`, where `R_i` is that participant’s bound nonce commitment and `Y_i` is its interpolated verification share. [5](#0-4)  These scalar errors are additive, so changing two valid responses to `s_i - δ` and `s_j + δ` makes each individual statement invalid by `δG` and `-δG`, while preserving the aggregate sum and signature validity. [6](#0-5) 

This is analogous to accepting current collateral for health while limiting enforcement to an older subset: malformed responses contribute to the successful aggregate result, but the later blame stage that would identify them is skipped. [7](#0-6) 

### Impact Explanation

A participant controlling two included key shares can submit individually invalid signature shares that still produce a valid threshold signature, causing both malformed responses to evade `InvalidShare` attribution. [1](#0-0)  More generally, any set of supplied share errors summing to zero is accepted without blame because per-share verification is unreachable when the aggregate signature verifies. [3](#0-2) 

The externally observable result is a valid signature, but the protocol loses the ability to identify which supplied shares violated the FROST share equation. [5](#0-4)  In deployments where `InvalidShare` drives slashing or exclusion, this weakens accountability for signing inputs supplied through `read_share` and `complete`. [8](#0-7) 

### Likelihood Explanation

The attack requires control over at least two included participant IDs, or cooperation between their holders, rather than knowledge of another participant’s secret share. [9](#0-8)  Once a valid pair of shares is known, constructing the malicious pair is only scalar arithmetic: subtract `δ` from one response and add `δ` to the other. [10](#0-9) 

A single participant cannot use this to forge a signature by modifying only its own share, because a nonzero lone error changes the aggregate response and fails verification. [4](#0-3)  The issue therefore primarily affects accountability, not the unforgeability of the emitted aggregate signature. [11](#0-10) 

### Recommendation

Do not treat aggregate signature validity as proof that every supplied share is individually valid when attribution is required. [12](#0-11)  Add an explicit accountability mode, or a caller-controlled flag, that always queues and verifies the per-share statements before returning the signature. [3](#0-2) 

If the aggregate-first path is retained for performance, document that `Ok(signature)` proves only that the sum is valid and does not prove that every submitted share satisfied `verify_share`. [13](#0-12)  Systems using `FrostError::InvalidShare` for slashing should not rely on `complete` alone for attributable share validation. [14](#0-13) 

### Proof of Concept

Let two included participants `i` and `j` have valid Schnorr responses `s_i` and `s_j`. Each valid share satisfies:

```text
s_iG = R_i + cY_i
s_jG = R_j + cY_j
```

An attacker who controls both IDs chooses a nonzero scalar `δ` and submits:

```text
s_i' = s_i - δ
s_j' = s_j + δ
```

Each individual share is now invalid:

```text
R_i + cY_i - s_i'G =  δG ≠ 0
R_j + cY_j - s_j'G = -δG ≠ 0
```

However, the submitted sum remains unchanged:

```text
s_i' + s_j' = s_i + s_j
```

`complete` inserts the local response, adds all supplied responses, verifies the summed Schnorr signature, and returns before constructing the per-share `BatchVerifier`. [1](#0-0)  Consequently, neither malformed share reaches `verify_share`, and `InvalidShare(i)` or `InvalidShare(j)` is never emitted. [3](#0-2)

  fn complete(
    self,
    mut shares: HashMap<Participant, SignatureShare<C>>,
  ) -> Result<A::Signature, FrostError> {
    let params = self.params.multisig_params();
    validate_map(&shares, self.view.included(), params.i())?;

    let mut responses = HashMap::new();
    responses.insert(params.i(), self.share);
    let mut sum = self.share;
    for (l, share) in shares.drain() {
      responses.insert(l, share.0);
      sum += share.0;
    }

    // Perform signature validation instead of individual share validation
    // For the success route, which should be much more frequent, this should be faster
    // It also acts as an integrity check of this library's signing function
    if let Some(sig) = self.params.algorithm.verify(self.view.group_key(), &self.Rs, sum) {
      return Ok(sig);
    }

    // We could remove blame_entropy by taking in an RNG here
    // Considering we don't need any RNG for a valid signature, and we only use the RNG here for
    // performance reasons, it doesn't feel worthwhile to include as an argument to every
    // implementor of the trait
    let mut rng = ChaCha20Rng::from_seed(self.blame_entropy);
    let mut batch = BatchVerifier::new(self.view.included().len());
    for l in self.view.included() {
      if let Ok(statements) = self.params.algorithm.verify_share(
        self.view.verification_share(*l),
        &self.B.bound(*l),
        responses[l],
      ) {
        batch.queue(&mut rng, *l, statements);
      } else {
        Err(FrostError::InvalidShare(*l))?;
      }
    }

    if let Err(l) = batch.verify_vartime_with_vartime_blame() {
      Err(FrostError::InvalidShare(l))?;
    }

    // If everyone has a valid share, and there were enough participants, this should've worked
    // The only known way to cause this, for valid parameters/algorithms, is to deserialize a
    // semantically invalid FrostKeys
    Err(FrostError::InternalError("everyone had a valid share yet the signature was still invalid"))
