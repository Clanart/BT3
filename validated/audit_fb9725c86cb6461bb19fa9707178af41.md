### Title
Sensitive IPC handlers registered in `main.ts` bypass the `isTrustedIPCSender` access-control check enforced by the `on`/`handle` wrapper - (File: `app/src/main-process/main.ts`)

### Summary
Desktop has a dedicated access-control mechanism for IPC: `app/src/main-process/ipc-main.ts` exports `on`/`handle` wrappers that call `safeListener`, which rejects any IPC message whose sender `WebContents` is not registered as trusted via `isTrustedIPCSender`. [1](#0-0) 
Trust is granted explicitly per-window with `addTrustedIPCSender(wc)` in `app-window.ts`/`crash-window.ts`. [2](#0-1) 

However, the bulk of the IPC surface registered directly in `app/src/main-process/main.ts` (privileged, file-system/process-affecting channels like `open-external`, `move-to-trash`, `show-item-in-folder`, `unsafe-open-directory`, `resolve-proxy`, `show-open-dialog`, `show-save-dialog`, `get-path`, `execute-menu-item-by-id`, etc.) is registered with the **raw** `ipcMain.on`/`ipcMain.handle` from Electron, not the `on`/`handle` wrapper from `./ipc-main`. These handlers therefore never call `isTrustedIPCSender` and accept messages from *any* sender `WebContents`. [3](#0-2) [4](#0-3) 

This is structurally identical to the Vader `Pools.sync()` finding: a function meant to be reachable only after an enforcing/checking layer (the Router's balance accounting, here `isTrustedIPCSender`'s sender check) is instead exposed through a path that skips the guard entirely.

### Finding Description
The intended invariant, stated explicitly in `trusted-ipc-sender.ts`'s comment referencing Electron's security guidance ("validate the sender of all IPC messages"), is that privileged main-process actions must only be executed on behalf of `WebContents` that Desktop itself created and explicitly marked as trusted. [5](#0-4) 

That guard is implemented once, centrally, inside `safeListener` — but it only applies to channels registered through the `on`/`handle` helpers exported by `ipc-main.ts`. [6](#0-5) 

`main.ts` however wires most of the app's IPC surface with the unwrapped `ipcMain.on`/`ipcMain.handle` calls, so no sender check occurs before executing the handler body — e.g. `shell.openExternal(path)`, `shell.trashItem(path)`, `shell.showItemInFolder(path)`, `UNSAFE_openDirectory(path)`, `session.defaultSession.resolveProxy(url)`, and popping native open/save dialogs are all invoked directly on whatever data the sender supplied. [3](#0-2) [7](#0-6) 

Any renderer-side code execution that isn't the trusted main window's own bundled script (for example, JS running inside a secondary `WebContents`/window or a compromised renderer context, akin to the "attacker controls a link/deep link/rendered remote content" class in the Valid Impact list) can call these channels directly via `ipcRenderer.send`/`invoke`, bypassing the one centralized defense (`isTrustedIPCSender`) that exists precisely to prevent this. This mirrors the Vader bug: the enforcing check exists, but is only wired into one code path (Router/`on`-`handle` wrapper) while a parallel, equally-privileged path (`sync()`/raw `ipcMain`) omits it.

### Impact Explanation
Successful invocation of these unguarded channels lets untrusted script:
- exfiltrate or trigger arbitrary `shell.openExternal` calls with attacker-chosen paths/URLs, `shell.trashItem`/`UNSAFE_openDirectory` on attacker-chosen filesystem paths — silent file deletion or unwanted external process launches outside repo boundaries, and
- read/query internal state (`get-path`, `get-app-path`, `resolve-proxy`) that should not be attacker-reachable.

This matches "file write or read outside the repo" / "renderer-sandbox... escape" categories in the accepted impact list.

### Likelihood Explanation
Exploitation requires the attacker to first get script execution in *some* Electron `WebContents` belonging to Desktop (e.g., through a secondary window/webview rendering less-trusted content, or a renderer compromised via a malicious link/deep link opened in-app). Whether such a code-execution primitive currently exists elsewhere in the app is not something I could fully confirm from the indexed code — the `web-contents-created` hardening (`setWindowOpenHandler` deny, `will-navigate` prevention) suggests Desktop actively defends against untrusted content gaining a foothold, which somewhat reduces but does not eliminate likelihood, since the very existence of `isTrustedIPCSender` implies the Desktop team considers a rogue/compromised sender realistic enough to defend against for *some* channels but not others.

### Recommendation
Route all privileged IPC registrations in `main.ts` through the `on`/`handle` wrapper functions exported by `app/src/main-process/ipc-main.ts` instead of calling `ipcMain.on`/`ipcMain.handle` directly, so every channel is uniformly subject to the `isTrustedIPCSender` check.

### Proof of Concept
1. Obtain a `WebContents` whose id was never passed to `addTrustedIPCSender` (any window/frame not created via `AppWindow`/`CrashWindow`, or any renderer able to execute script from injected/compromised content).
2. From that context, call e.g. `ipcRenderer.send('unsafe-open-directory', '<attacker path>')` or `ipcRenderer.invoke('open-external', 'attacker-uri')`.
3. Because `main.ts` registered these with raw `ipcMain.on('unsafe-open-directory', ...)` / `ipcMain.handle('open-external', ...)` (not the `isTrustedIPCSender`-checked wrapper), the handler executes without any sender validation. [3](#0-2) [8](#0-7)

/**
 * Subscribes to the specified invokeable IPC channel and provides strong typing
 * of the channel name, and request parameters. This is the equivalent of using
 * ipcMain.handle.
 */

  channel: T,
  listener: RequestResponseChannelListener<T>
) {
  ipcMain.handle(channel, safeListener(listener))
}

function safeListener<E extends IpcMainEvent | IpcMainInvokeEvent, R>(
  listener: (event: E, ...a: any) => R
) {
  return (event: E, ...args: any) => {
    if (!isTrustedIPCSender(event.sender)) {
      log.error(
        `IPC message received from invalid sender: ${event.senderFrame?.url}`
      )
      return
    }

    return listener(event, ...args)
  }
}

```typescript
import { WebContents } from 'electron'

// WebContents id of trusted senders of IPC messages. This is used to verify
// that only IPC messages sent from trusted senders are handled, as recommended
// by the Electron security documentation:
// https://github.com/electron/electron/blob/main/docs/tutorial/security.md#17-validate-the-sender-of-all-ipc-messages
const trustedSenders = new Set<number>()

/** Adds a WebContents instance to the set of trusted IPC senders. */
export const addTrustedIPCSender = (wc: WebContents) => {
  trustedSenders.add(wc.id)
  wc.on('destroyed', () => trustedSenders.delete(wc.id))
}

/** Returns true if the given WebContents is a trusted sender of IPC messages. */
export const isTrustedIPCSender = (wc: WebContents) => trustedSenders.has(wc.id)


```
