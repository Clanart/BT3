### Title
Unvalidated `file://` path from diff-derived binary file open reaches `shell.openExternal` with no root-containment check - (File: `app/src/ui/diff/binary-file.tsx`, `app/src/ui/lib/open-file.ts`, `app/src/main-process/main.ts`)

### Summary
The "Open file in external program" action for binary diffs builds a filesystem path by naively joining the repository root with an attacker-controlled diff path, and neither the renderer helper nor the main-process IPC handler ever verifies that the resulting path stays inside the repository before calling Electron's `shell.openExternal`.

### Finding Description
`BinaryFile.open()` builds the path to open as: [1](#0-0) 
This is a plain `Path.join(repository.path, this.props.path)` with no containment check, unlike the equivalent flow in `dispatcher.ts`'s `openRepositoryFromUrl`, which explicitly rejects absolute paths and calls `resolveWithin` (which also protects against symlink-based escapes, per its dedicated tests) before touching the filesystem: [2](#0-1) [3](#0-2) 

The resulting `fullPath` is passed to `openFile`, which wraps it in a `file://` URL and calls `shell.openExternal` unconditionally: [4](#0-3) 

That call is proxied over IPC into the main process, where `ipcMain.handle('open-external', ...)` inspects the string only to decide whether to *log* it as a browser navigation — it does not gate on scheme, and it performs no filesystem validation whatsoever before invoking Electron's `shell.openExternal`: [5](#0-4) 

Other call sites in the codebase that expose "open with default program" (e.g. `selected-commits.tsx`, `pull-request-files-changed.tsx`) at least gate the menu item on `isSafeFileExtension` and `pathExists`, but `binary-file.tsx`'s single-click "Open file in external program" link has none of these guards: [6](#0-5) 

Git supports committing symlinks (blob mode `120000`) whose target string can be an arbitrary path, including one that points outside the repository (e.g. `../../../../some/absolute/path` or an absolute path). A repository can therefore contain a tracked symlink entry whose diff is classified as a binary file change. When the victim opens that diff and clicks "Open file in external program," `fullPath` is a path *inside* the repo (the symlink itself), but the OS/`shell.openExternal` will follow the symlink to the attacker-chosen target and hand it to the OS default-application handler — with no `resolveWithin`/`realpath`-based containment check anywhere in this path, in contrast to the deep-link flow which does perform that check.

### Impact Explanation
Depending on the target file's type and OS file associations, this can result in launching an attacker-chosen executable/script/application (e.g. `.exe`, `.scr`, `.desktop`, `.app`) or disclosing local file contents by opening them in a viewer, i.e., execution or unintended file access outside the cloned repository — reachable purely from cloning/opening a malicious, attacker-controlled repository and a single expected UI click, no local access or credentials required.

### Likelihood Explanation
Requires the victim to clone/open a malicious repository and click "Open file in external program" on a binary-classified diff entry — a normal, expected interaction with the diff viewer, not an unnatural step. The attacker fully controls the repository content (a tracked symlink), which is exactly the "malicious repository content" input class in scope.

### Recommendation
Before calling `shell.openExternal`/`openFile` for any repository-derived path, resolve and validate it the same way `openRepositoryFromUrl` does: reject absolute/traversal paths and use `resolveWithin(repository.path, path)` (which also resolves symlinks via `realpath`) so the final target is provably inside the repository root; additionally, the `open-external` IPC handler in `main.ts` should not treat scheme-checking as merely a logging concern — it should explicitly restrict accepted values to `http(s)://` URLs for browser-navigation calls and require pre-validated absolute paths (already checked in the renderer) for `file://`/local-open calls, rather than passing an unchecked string straight to `shell.openExternal`.

### Proof of Concept
1. Create a repository containing a tracked symlink `evil-file` (git blob mode `120000`) with target set to an absolute path outside the repo (e.g. pointing at an executable/script or sensitive file).
2. Have the victim clone this repository in GitHub Desktop and view the commit/diff introducing `evil-file`; it will be rendered as a changed binary file via `BinaryFile` (`app/src/ui/diff/binary-file.tsx`).
3. Victim clicks "Open file in external program," triggering `onOpenBinaryFile(fullPath)` → `openFile(fullPath, dispatcher)` (`app/src/ui/lib/open-file.ts:8`) → IPC `open-external` → `main.ts:581-597`.
4. Confirm `shell.openExternal` is invoked and succeeds (`return true`) with no rejection, and the OS follows the symlink to open/execute the attacker-chosen external target, since no `resolveWithin`/`realpath` containment check exists anywhere on this call path.
