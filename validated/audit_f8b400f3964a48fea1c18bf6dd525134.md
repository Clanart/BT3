### Title
Missing `chain_id` in EIP-712 Domain Separator Enables Cross-Network Signature Replay for Optimistic Payout and Operator Withdrawal Authorization — (File: `core/src/rpc/ecdsa_verification_sig.rs`)

### Summary

`CLEMENTINE_EIP712_DOMAIN` is defined without a `chain_id` or `verifying_contract` field. Any aggregator verification signature produced for one Citrea network (e.g., testnet, devnet, or a fork) is cryptographically identical to a signature for any other network, because the domain separator does not bind the signature to a specific chain. This allows a captured or leaked signature from one deployment to be replayed on another, bypassing the aggregator authorization gate that guards optimistic payout signing and operator withdrawal execution.

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is declared as a static constant:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

The EIP-712 specification defines `chainId` and `verifyingContract` as standard domain fields specifically to prevent cross-chain and cross-contract replay. Neither is present here. The `citrea_chain_id` field exists in `BridgeConfig` and is used elsewhere in the system, but it is never incorporated into this domain separator. [2](#0-1) 

The domain is used in `recover_address_from_ecdsa_signature`, which computes the EIP-712 signing hash and recovers the signer address:

```rust
let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);
let address = signature.recover_address_from_prehash(&eip712_hash)...;
``` [3](#0-2) 

This recovered address is then compared against `aggregator_verification_address` in two places:

1. **Verifier** — `sign_optimistic_payout` in `core/src/verifier.rs` (line 1602–1618): verifiers refuse to produce a partial MuSig2 signature for an optimistic payout unless the verification signature passes. [4](#0-3) 

2. **Operator** — `withdraw` RPC handler in `core/src/rpc/operator.rs` (line 209–238): the operator refuses to execute a withdrawal unless the verification signature passes. [5](#0-4) 

Because the domain separator contains only `name` and `version`, the EIP-712 hash for a given `(withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount)` tuple is **identical across all EVM chains**. A signature produced on Citrea testnet (chain_id=5655 in `.env.example`) is byte-for-byte valid on Citrea mainnet or any fork. [6](#0-5) 

### Impact Explanation

If the aggregator uses the same ECDSA key on multiple Citrea deployments (testnet and mainnet, or a fork scenario), an attacker who observes a valid verification signature on one network can replay it on another. The replayed signature passes the `address_from_sig != address_in_config` check because the recovered address is the same on all chains. This allows the attacker to:

- Cause verifiers to co-sign an optimistic payout MuSig2 transaction on the wrong network, potentially releasing bridge-controlled BTC without a legitimate L2 withdrawal backing it.
- Cause an operator to execute a withdrawal transaction on the wrong network.

The remaining checks (withdrawal UTXO existence, deposit existence, amount bounds) are DB-state checks that are network-local, so they do not prevent the replay if the same deposit/withdrawal IDs exist on both networks — which is likely given sequential indexing.

### Likelihood Explanation

The `aggregator_verification_address` is set by default in both `BridgeConfig::default()` and `.env.example`, meaning the check is active in standard deployments. Operators commonly reuse keys across testnet and mainnet. Deposit IDs are sequential integers starting from 0 on every deployment, so ID collisions across networks are expected. The signature is transmitted over gRPC and is observable to any party with network access to the aggregator's RPC calls. [7](#0-6) 

### Recommendation

Include `citrea_chain_id` from `BridgeConfig` in the EIP-712 domain separator. Replace the static constant with a function that constructs the domain dynamically using the configured chain ID:

```rust
pub fn clementine_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Pass `config.citrea_chain_id as u64` wherever `CLEMENTINE_EIP712_DOMAIN` is currently used. This binds every verification signature to a specific Citrea chain, making cross-network replay impossible.

### Proof of Concept

1. Deploy Clementine on Citrea testnet (chain_id=5655) and Citrea mainnet (chain_id=5115) with the same aggregator ECDSA key.
2. On testnet, the aggregator signs an `OptimisticPayoutMessage` for `withdrawal_id=0`, producing signature `S`.
3. On mainnet, deposit ID 0 also exists (sequential IDs). Submit `S` as the `verification_signature` in an `optimistic_payout` gRPC call to the mainnet aggregator.
4. `recover_address_from_ecdsa_signature` computes `eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)` — identical on both chains because `CLEMENTINE_EIP712_DOMAIN` has no `chain_id`.
5. The recovered address matches `aggregator_verification_address` in the mainnet config.
6. Mainnet verifiers co-sign the optimistic payout MuSig2 transaction, releasing BTC from the mainnet bridge for a withdrawal that was only authorized on testnet. [1](#0-0) [8](#0-7)

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
