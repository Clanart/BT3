### Title
Working-directory diff for renamed files is computed against the index instead of `HEAD`, letting an attacker-controlled merge silently hide staged content from the pre-commit review - (File: `app/src/lib/git/diff.ts`)

### Summary
This is the closest Desktop analog to the SushiToken bug class: an accounting/lookup routine operates on the wrong reference point (`from` instead of `_delegates[from]`), so the value the code believes it's reasoning about diverges from the value that actually governs the on-chain state transition. In `getWorkingDirectoryDiff` the equivalent divergence occurs between "index" and "HEAD" as the diff baseline for renamed files, which are two different reference points whose mismatch is silently absorbed instead of surfaced.

### Finding Description
`getWorkingDirectoryDiff` builds the diff that Desktop shows the user for a file in the Changes list before it gets committed. For most file kinds it diffs against `HEAD`: [1](#0-0) 

But for `AppFileStatusKind.Renamed` files, the code intentionally diffs against the index instead of `HEAD`, and the author's own comment flags this as a known compromise: [2](#0-1) 

`git diff -- <path>` (with no commit-ish argument) compares the **working tree to the index**, not the working tree (or index) to `HEAD`. This means: any content that is already staged for a renamed path (i.e., already differs from `HEAD`) is invisible to this diff. Only additional edits made in the working tree on top of what's already staged are shown.

The staged content for a rename is not something the user necessarily typed by hand - it is exactly what `git merge`/`git rebase` write into the index automatically when Git auto-resolves a rename+content change during a merge/rebase that also produces unrelated conflicts elsewhere in the tree. Desktop pauses such an operation for the user to resolve conflicts and review the result via the standard Changes/commit-review UI, which calls this same function: [3](#0-2) 

Because the working tree is checked out to match the index right after the merge/rebase step, `git diff -- path` for the renamed file returns **empty or minimal** output even though the file's content relative to the previous commit changed substantially (the rename + content rewrite performed by the merge). The user reviews what looks like "no changes" for that file and proceeds to finish the commit, but the commit will still include the fully rewritten (attacker-authored) content.

### Impact Explanation
This breaks the core guarantee that the Changes view accurately previews "what you are about to commit." An attacker who controls a branch/PR that gets merged (a standard, unprivileged git object the victim fetches and merges) can craft a rename+content change that auto-merges cleanly for that file while leaving genuine conflicts elsewhere, forcing the user into the manual-resolution flow. When the user reviews the renamed file's diff to sanity-check the merge, Desktop shows them an empty/near-empty diff, hiding the attacker's payload from review. The user then commits and (in the common workflow) pushes that content, unknowingly propagating attacker-controlled file content that they explicitly believed they had reviewed and found unchanged. This is exactly the "silent corruption of what the user commits or pushes" impact category, achieved purely by a crafted git history the victim merges — no local access, no malware, no social engineering beyond a routine merge action.

### Likelihood Explanation
Renames combined with content changes are common in real branches (refactors, restructurings), and merges/rebases that produce partial conflicts elsewhere in the tree while auto-resolving a rename cleanly are a normal, everyday git occurrence — not a contrived edge case. The code path is unconditional (it always takes this branch for `AppFileStatusKind.Renamed`) and is on the default, most-used review flow (Changes tab diff), so any user who reviews a merge/rebase conflict set containing an untouched-but-renamed file is exposed. The bug is also explicitly acknowledged in a code comment as "the best kind of incorrect," indicating the maintainers were aware of the semantic gap without addressing the security implication for untrusted/adversarial merge content.

### Recommendation
For `AppFileStatusKind.Renamed` files, compute the diff against `HEAD` (post-rename path vs. the pre-rename blob at `HEAD`), consistent with every other status kind, e.g. by resolving the old blob via `--find-renames`/explicit blob comparison instead of relying on an implicit working-tree-vs-index diff. At minimum, when index content differs from `HEAD` for a renamed path, that portion must not be dropped from what's rendered to the user prior to commit.

### Proof of Concept
1. Attacker prepares `feature` branch: renames `report.txt` → `summary.txt` and rewrites its contents completely; also modifies an unrelated file `x.txt` in a way that conflicts with the victim's `main` branch.
2. Victim, using Desktop, merges `feature` into `main`. Git auto-resolves the rename+rewrite of `report.txt`/`summary.txt` cleanly (staged into the index, working tree checked out to match), while `x.txt` is left with conflict markers requiring manual resolution.
3. Desktop shows the merge-conflict resolution UI; the victim resolves `x.txt` and, before finishing the merge commit, inspects the Changes list, clicking on `summary.txt` (status: Renamed).
4. `updateChangesWorkingDirectoryDiff` → `getWorkingDirectoryDiff` runs `git diff --no-ext-diff --patch-with-raw -z --no-color -- summary.txt` (no `HEAD` argument) per [2](#0-1) . Since the working tree already matches the index (post-checkout), this returns an empty diff.
5. Believing `summary.txt` is unchanged in substance (just renamed), the victim completes the merge commit and pushes. The commit actually contains the attacker's full content rewrite, which was never shown for review.
