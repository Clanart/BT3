### Title
`ReceivedOutput::read` accepts untrusted offset/script_pubkey pairs without verifying consistency, allowing misrepresented "spendable" outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes three independent fields — `offset` (a scalar), `output` (a `TxOut`), and `outpoint` — and returns a `ReceivedOutput` that downstream code treats as a spendable output belonging to a specific key/offset. No check verifies that `output.script_pubkey` is actually the P2TR script derived from `key + G * offset`. This is the Serai analog of CVE-2023-4360 (crafted input causing security-relevant state to be displayed/reported misleadingly): attacker-controlled bytes produce a "received output" whose reported ownership (offset) does not match the on-chain output.

### Finding Description
When `Scanner::scan_transaction` produces a `ReceivedOutput`, consistency between `offset` and `output.script_pubkey` is guaranteed because the script is looked up in `self.scripts` (`networks/bitcoin/src/wallet/mod.rs:205-211`). However, `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) reconstructs the struct purely from the byte stream:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
```

There is no verification that `p2tr_script_buf(scanner_key + GENERATOR * offset) == output.script_pubkey`, nor that the `outpoint` actually refers to a transaction containing that output. The round-trip test (`networks/bitcoin/tests/wallet.rs:73-75`) only proves self-consistency of honest serialization, not validation of adversarial input.

Downstream, the processor trusts these fields independently:

- `Output::key()` (`processor/src/networks/bitcoin.rs:112-122`) extracts the key from `script_pubkey` and subtracts `offset * G`, attributing the output to a group key that never received it (or vice versa).
- `Output::id()` uses only the attacker-claimed `outpoint` (`processor/src/networks/bitcoin.rs:92-104`), and `balance()` uses the claimed `TxOut` value (`processor/src/networks/bitcoin.rs:128-130`).
- The signing path (`TransactionMachine` / `SignableTransaction::multisig` in `networks/bitcoin/src/wallet/send.rs`) applies `offset` to the signing keys when spending the input.

### Impact Explanation
An attacker who can feed bytes to `ReceivedOutput::read` (or to `Output::read`, which embeds it at `processor/src/networks/bitcoin.rs:156`) can cause the processor to report an output as received and spendable under an offset/key it does not belong to, or with a fabricated outpoint/value. Concretely:

- **Funds reported received that are not spendable**: an output whose script_pubkey corresponds to key K can be annotated with an arbitrary offset, causing `key()` to misattribute it and the wallet to attempt spending it with the wrong tweaked key — the resulting signature will not satisfy the Taproot output, permanently burning it if consumed by a scheduler plan.
- **Obfuscated provenance/ownership**: because `id()` and `balance()` are taken verbatim from untrusted bytes, a forged `ReceivedOutput` can impersonate another output's identity, mirroring the "obfuscated security UI" bug class — the system presents security-relevant state (who owns/received funds) that does not reflect chain reality.

### Likelihood Explanation
Reachability requires attacker-influenced bytes reaching `ReceivedOutput::read`/`Output::read`. Within Serai, `ReceivedOutput` values are serialized and deserialized through DB storage and processor message/event plumbing (`scanner.rs` output handling, `Output::read`), so any channel where a peer or corrupted store supplies these bytes qualifies. Exploitation requires no collusion or validator compromise — only control over the serialized blob — and the resulting misattribution/loss is deterministic. Rated Medium, matching the source CVE's severity.

### Recommendation
Either make `ReceivedOutput` self-validating or scope `read` to trusted contexts:

1. Add a `ReceivedOutput::verify(key)` (or take the `Scanner`) that recomputes `p2tr_script_buf(key + G * offset)` and compares it to `output.script_pubkey`, returning an error on mismatch.
2. Have `Output::read` in `processor/src/networks/bitcoin.rs` reject outputs whose recomputed key is inconsistent with the expected group key, rather than deriving `key()` from the mismatched pair.
3. Document that deserialization is unchecked and must be followed by `verify` before the output is used for balance accounting or signing.

### Proof of Concept
1. Honest path: `Scanner::register_offset(o)` yields script S for `key + G*o`; a TX paying S produces `ReceivedOutput { offset: o, output: S, .. }`.
2. Attack: craft bytes for `ReceivedOutput::read` with `offset = o' ≠ o`, `output.script_pubkey = S`, and any outpoint. `read` succeeds.
3. `Output::key()` returns `xonly(S) - o'*G = key + (o - o')*G` — a key that never received these funds, misattributing the output. Conversely, `offset = o` with a `script_pubkey` belonging to an unrelated P2TR key yields an output the scheduler believes is spendable by `key + o*G`; the Taproot key-path signature will fail and any plan consuming it locks/burns the claimed input.
