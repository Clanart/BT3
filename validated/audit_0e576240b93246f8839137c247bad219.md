### Title
Unbounded participant count in `ThresholdKeys::read` enables a "malloc bomb" memory/CPU exhaustion attack - (File: crypto/dkg/src/lib.rs)

### Summary
The curl advisory JLSEC-2026-404 describes an allocation-of-resources-without-limits flaw: a length/count under attacker control is used to drive heap allocation, allowing a tiny input to trigger a "malloc bomb". The same class exists in `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`: the serialized participant count `n` is read as an attacker-controlled `u16` and immediately used to size allocations and drive scalar/point deserialization loops *before* `ThresholdParams::new` validates it, with no cap tied to the expected committee size.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, and `i` as raw `u16`s from the reader, then:

1. For `Interpolation::Constant`, allocates `Vec::with_capacity(usize::from(n))` and reads `n` scalars via `C::read_F` (crypto/dkg/src/lib.rs:607-613).
2. Reads `n` group elements into a `HashMap` via `C::read_G` — each requiring a full point decompression/validation (crypto/dkg/src/lib.rs:620-623).
3. Only afterwards calls `ThresholdParams::new(t, n, i)` and `ThresholdKeys::new` (crypto/dkg/src/lib.rs:625-631), so `n` is entirely attacker-controlled up to `u16::MAX` = 65535, decoupled from any real threshold parameters. [1](#0-0) 

A few header bytes therefore force up to 65,535 elliptic-curve point decompressions plus ~65,535 scalar reads and a `HashMap` with 65,535 entries — several MB of heap and substantial CPU — from a handful of input bytes. The allocation/iteration count is derived purely from the untrusted length field, exactly the "per-header / attacker-declared count" shape of the curl chained-decompression cap bypass.

By contrast, the in-scope code shows the correct pattern elsewhere: `Commitments::read` in PedPoP bounds its loop by `params.t()` from already-validated `ThresholdParams` (crypto/dkg/pedpop/src/lib.rs:110-128), and `Transaction::read` for `DkgCommitments` rejects when `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` before allocating (coordinator/src/tributary/transaction.rs:286-295).

### Impact Explanation
`ThresholdKeys::read` is a listed untrusted-bytes sink. An unprivileged party who can feed serialized key material to a node running this deserialization (e.g., malformed DKG/key payloads routed to a processor) can cause repeated multi-MB allocations and tens of thousands of point decompressions per message. Repeated or concurrent submissions exhaust heap or starve CPU — a remote availability loss matching the advisory's CVSS A:H profile, with extreme input-to-work amplification (~8 bytes of header → ~65k expensive operations).

### Likelihood Explanation
Reachability requires a path where untrusted bytes reach `ThresholdKeys::read` on a victim (processor/node deserialization of peer- or coordinator-supplied key blobs, or blame/recovery payloads). No authentication, threshold, or honest-majority assumption is needed — a single malformed buffer suffices, and the cost is incurred before any validation can reject it. The bound is `u16::MAX` rather than truly unlimited, which caps per-message damage and supports Medium rather than High severity.

### Recommendation
Validate `n` against a sane bound *before* using it to size allocations or loops — e.g., construct `ThresholdParams::new(t, n, i)` first (rejecting `t > n`, `n == 0`, `i > n`), and additionally enforce a protocol-level maximum participant count before the `Vec::with_capacity`/`read_G` loops. Alternatively, stream the reads without pre-allocating based on `n`, so at most the bytes actually present are consumed.

### Proof of Concept
Construct a `ThresholdKeys` byte string with:
- `id_len`/`id` matching the target `C::ID`,
- `t = 1`, `n = 0xFFFF`, `i = 1`,
- interpolation byte `0` (Constant).

`ThresholdKeys::read` will then perform `Vec::with_capacity(65535)`, attempt 65,535 `read_F` reads, then a 65,535-iteration `read_G` loop — allocating megabytes and decompressing tens of thousands of points — before `ThresholdParams::new`/committee checks run. Feeding this ~8-byte prefix (with truncated body) to any endpoint that calls `ThresholdKeys::read` on untrusted input reproduces the resource-exhaustion primitive.
