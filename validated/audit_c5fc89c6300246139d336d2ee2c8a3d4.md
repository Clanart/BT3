### Title
Integer overflow in Bitcoin input/output totals panics transaction construction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`SignableTransaction::new` sums attacker-influenced `ReceivedOutput` values with `u64` and adds the payment total to the calculated fee without checked arithmetic. [1](#0-0) 

Release builds enable integer overflow checks, so overflowing these totals causes a panic rather than wrapping. [2](#0-1) 

### Finding Description

`ReceivedOutput::read` accepts untrusted serialized output data and consensus-decodes the embedded `TxOut` without an additional monetary-range check in Serai's own code. [3](#0-2) 

`SignableTransaction::new` then calculates `input_sat` using `sum::<u64>()` over all supplied output values. [4](#0-3) 

It similarly calculates `payment_sat` using an unchecked `u64` sum and later evaluates `payment_sat + needed_fee`. [5](#0-4) 

A serialized `TxOut` containing `u64::MAX` is therefore sufficient to reach the vulnerable arithmetic; two such inputs overflow `input_sat`, while a sufficiently large payment list can overflow `payment_sat` or `payment_sat + needed_fee`. [1](#0-0) 

### Impact Explanation

An unprivileged party who can supply serialized `ReceivedOutput` values or influence the outputs requested in a transaction can cause an integer-overflow panic during transaction construction. [3](#0-2) [1](#0-0) 

If the panic is not caught by the embedding service, this aborts the process handling the spend request and produces a remote denial of service. [2](#0-1) 

### Likelihood Explanation

The trigger requires only crafted public input bytes or extreme payment/output values; it does not require validator privileges, a private key, malformed curve points, or protocol collusion. [3](#0-2) 

The panic occurs before the function returns `TransactionError::NotEnoughFunds`, so ordinary validation does not protect the affected path. [6](#0-5) 

### Recommendation

Use `checked_add`, `checked_mul`, or saturating accumulation for `input_sat`, `payment_sat`, `payment_sat + needed_fee`, `fee_per_vbyte * vbytes`, and the change-output calculation. [7](#0-6) 

Return `TransactionError::NotEnoughFunds` or a dedicated amount-overflow error when any total cannot be represented as `u64`. [8](#0-7) 

Also validate decoded Bitcoin amounts against the consensus monetary range in `ReceivedOutput::read` before constructing a spendable-output record. [3](#0-2) 

### Proof of Concept

```rust
use bitcoin::{
  Amount, OutPoint, ScriptBuf, TxOut,
  consensus::Encodable,
};
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction};

fn received_output(value: u64) -> ReceivedOutput {
  // Scalar 1 in canonical little-endian representation.
  let mut encoded = vec![1];
  encoded.extend([0; 31]);

  TxOut {
    value: Amount::from_sat(value),
    script_pubkey: ScriptBuf::new(),
  }
  .consensus_encode(&mut encoded)
  .unwrap();

  OutPoint::default().consensus_encode(&mut encoded).unwrap();

  ReceivedOutput::read(&mut encoded.as_slice()).unwrap()
}

let inputs = vec![
  received_output(u64::MAX),
  received_output(u64::MAX),
];

// A change output is supplied so the request is not rejected by NoOutputs.
// input_sat overflows before the NotEnoughFunds check is reached.
let _ = SignableTransaction::new(
  inputs,
  &[],
  Some(ScriptBuf::new()),
  None,
  1,
);
```

With workspace release settings, `input_sat` panics on `u64::MAX + u64::MAX` because `overflow-checks` is enabled. [4](#0-3) [2](#0-1)
