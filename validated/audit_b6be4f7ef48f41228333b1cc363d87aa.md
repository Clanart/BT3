### Title
Missing length check on per-input preprocess vector enables index-out-of-bounds panic in `TransactionSignMachine::sign` — (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
The CVE-2023-38703 bug class is a higher-layer object operating on a lower-layer object whose state it does not synchronize with (SRTP transport vs. underlying media transport → use-after-free). In Serai's safe-Rust in-scope code, the structural analog is `TransactionSignMachine`, which layers a per-input signing machine (`self.sigs`) over an externally supplied `Vec<Preprocess>` per participant without checking the two layers' lengths agree. A malicious signing-set participant can supply a short preprocess vector, causing an out-of-bounds index panic when shares are produced.

### Finding Description
`TransactionSignMachine::read_preprocess` parses one `Preprocess` per inner `AlgorithmSignMachine` by iterating `self.sigs` [1](#0-0) . There is no requirement that the returned `Vec<Preprocess>` actually have `self.sigs.len()` elements — a peer can send bytes that parse into fewer preprocesses (the readers simply consume what's present; a shorter encoding yields a shorter `Vec` if the caller feeds it per-participant, and even when read from one stream, any `Err` short-circuits, but a legitimately-encoded short Vec can be constructed by the sending participant before serialization).

In `sign`, each participant's preprocess vector is then indexed by input index `c` over `0 .. self.sigs.len()` [2](#0-1) . `commitments[c]` is a direct `Vec` index with no bounds check. If the desynchronization occurs — the higher layer (`self.sigs`) has more elements than the lower layer (the peer-supplied preprocess `Vec`) — the index panics.

This mirrors the report precisely: the upper object (transaction-level machine) iterates over its own state while assuming the lower object (per-participant preprocess list) kept pace, and dereferences a stale/out-of-range slot when it hasn't.

### Impact Explanation
An unprivileged cosigner participating in a Bitcoin transaction signing session can trigger a panic in the victim's processor during the `Preprocesses → sign` phase. In `processor/src/signer.rs`, `machine.sign(preprocesses, &[])` is invoked directly on the `TransactionSignMachine` with attacker-controlled `Vec<Preprocess>` values [3](#0-2) . A panic there kills the signing attempt/task; repeated across attempts it prevents the validator from ever producing its share for batch/TX signing — a reachable denial of service of the threshold-signing path driven purely by public protocol bytes.

### Likelihood Explanation
The malicious participant only needs to serialize a `Vec<Preprocess>` shorter than the number of transaction inputs and send it as their `Preprocess` message — bytes fully under their control, parsed via the public `read_preprocess` path. No collusion, leaked keys, or consensus faults are required. Impact is limited to DoS (panic, not memory corruption, since Rust bounds-checks the index), so severity is Medium rather than Critical.

### Recommendation
In `TransactionSignMachine::sign` (`networks/bitcoin/src/wallet/send.rs`), validate `commitments.len() == self.sigs.len()` for every participant's preprocess vector before indexing, and return `FrostError::InvalidPreprocess(l)` for the offending participant instead of panicking. Equivalently, enforce the length in `read_preprocess` so a short vector fails deserialization.
