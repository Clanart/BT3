### Title
Webhook shop-domain attribution is not covered by the HMAC signature, enabling cross-shop webhook forgery - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates a webhook solely by HMAC-signing the raw request body against the app's single shared client secret. The `shop_domain` helper that the module exposes for consumers to attribute the webhook to a merchant is read directly from the `X-Shopify-Shop-Domain` header, which is **not** part of the signed data. Any party that can obtain a validly-signed webhook payload (e.g., an unrelated merchant who has installed the app themselves) can replay that body/HMAC pair while substituting an arbitrary victim shop domain in the header, and the request will still pass verification.

### Finding Description
`hmac_valid?` computes the digest only over `request.raw_post` and compares it to the `HTTP_X_SHOPIFY_HMAC_SHA256` header using the app-wide `ShopifyApp.configuration.secret`/`old_secret`: [1](#0-0) 

`ShopifyApp::WebhookVerification#verify_request` gates the action purely on this body HMAC check, and separately exposes `shop_domain` for use by the including controller, sourced from an unsigned header: [2](#0-1) 

This is precisely the same bug class as the external report: the "signer" (Shopify, holding the app's client secret) authorizes the payload body, but a value the application treats as authoritative — here, which shop the webhook belongs to — is never included in what was signed, so it can be swapped after the fact without invalidating the signature (an analog of paymaster gas limits not being covered by `getHash()`).

Because Shopify webhook HMACs are signed with the app's single client secret shared by every shop that installs the app (not a per-shop secret), any merchant who installs the app can capture their own legitimately-signed webhook (valid body + valid HMAC), then resend that exact body/HMAC pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop. `verify_request` will accept it because it only checks the body signature, and `shop_domain` will return the attacker-controlled header value.

This pattern is not merely theoretical — it is the officially documented way to write custom webhook controllers with this gem: [3](#0-2) 

Downstream job classes trust that value as the authoritative shop identity for processing, e.g. `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)`.

### Impact Explanation
An attacker with app access to only their own shop (an "unrelated merchant") can forge webhook events attributed to any other shop domain that uses the app, because the shop-domain binding used by the app is not authenticated by the signature. Depending on how the consuming job uses `shop_domain` (e.g., to look up a stored access token/session for that shop and perform actions, or to write/merge data keyed by shop), this can lead to cross-shop data injection, cross-shop actions being performed using the victim's session/access token, or poisoning of shop-specific application state — a cross-shop access/data-confusion vulnerability.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs at least one legitimately-signed webhook body of their own (trivial to obtain by installing the app on their own store and triggering any subscribed webhook topic, e.g., `carts/update`), and needs a target app that both uses `ShopifyApp::WebhookVerification` in a custom controller (the officially documented pattern) and trusts the `shop_domain` helper for shop attribution in subsequent processing. This is a realistic scenario for any app that follows the documented custom-webhook-controller pattern.

### Recommendation
Bind the shop attribution to the signed payload rather than to an unsigned header:
- Include the shop domain (and/or webhook id/topic) in the HMAC-verified material, or
- Require that `shop_domain` be independently derived/verified against Shopify (e.g., cross-checked against an existing, previously verified session/shop record) before being trusted, or
- Adopt the same binding scheme shopify_api's `ShopifyAPI::Webhooks::Registry`/`Request` uses internally, and deprecate the bare `shop_domain` header accessor in `ShopifyApp::WebhookVerification` in favor of a verified equivalent.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a subscribed webhook topic to receive a request with a valid `X-Shopify-Hmac-Sha256` header for some body `B`.
2. Resend a POST to the app's custom webhook endpoint (implemented with `include ShopifyApp::WebhookVerification`, per the documented pattern) with the exact same body `B` and HMAC header, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `hmac_valid?` succeeds because it only checks `B` against the shared secret; `verify_request` allows the request through.
4. The controller's `shop_domain` call returns `victim.myshopify.com`, and any downstream job processes attacker-supplied webhook data as if it originated from the victim shop.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
