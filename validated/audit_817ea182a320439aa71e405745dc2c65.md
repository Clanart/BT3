Based on my research, I found a strong analog: GitHub Desktop's AI-assisted merge-conflict resolution feature ("Copilot Conflict Resolution") sends the raw content of unresolved merge conflicts — which is directly attacker-controlled if the conflicting branch/commit was fetched from a remote — to an LLM, and then automatically writes and stages whatever the model returns, with only a narrow set of guards (path-traversal check, and an on-disk conflict-marker re-check). Unlike the analogous C4 report (an over-strict `require()` that *blocks* a legitimate action), this Desktop path has the opposite and more severe failure mode: the check is too *permissive*, so attacker-influenced content can flow straight into a commit and push without the user reviewing exactly what was written.

### Title
Silent corruption of committed content via attacker-controlled merge-conflict text fed into unreviewed Copilot auto-resolution write path - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_applyCopilotConflictResolutions` writes AI-generated conflict resolutions straight to disk and `git add`s them in a batch, gated only by a path-traversal check and a same-path "did the user already resolve this externally" check. The resolution content itself — and the underlying conflict text that drove the model's output — originates from merge/rebase conflicts that can be entirely attacker-controlled (a hostile branch fetched and merged/rebased against by the victim). Nothing in this path re-verifies that the written content is faithful to both sides of the conflict, or protects against the conflicting branch's content manipulating the model output (indirect prompt injection), before the result is staged for commit.

### Finding Description
The flow is:
1. `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:376-470`) reads the raw on-disk conflict-marked content of every conflicted file and forwards it, largely unfiltered (beyond a size cap and a path-traversal/symlink check via `resolveWithin`), as `rawContent`/`hunks` to the model. [1](#0-0) 
2. This conflict content is attacker-controlled whenever the "theirs" side comes from a fetched remote branch/PR that the user merges or rebases onto — i.e. the classic "attacker controls a fetched repository" primitive.
3. The model's resulting `copilotResolutions` (each with a `path` and `resolvedContent`) are consumed by `_applyCopilotConflictResolutions`, which:
   - Skips paths the user manually overrode.
   - For "delete vs modify" conflicts, funnels into the existing manual-resolution flow.
   - For all other conflicts, resolves a path with `resolveWithin` (traversal/symlink guard) and then unconditionally writes `resolution.resolvedContent` to disk and queues it for `git add`, unless the on-disk file's *own* status shows the user externally cleared conflict markers. [2](#0-1) 
4. The only integrity check present (`isConflictedFileStatus`/`hasUnresolvedConflicts`) validates whether the *file* still looks conflicted — it says nothing about whether the *content* the model produced correctly incorporates both sides of the conflict. There is no diffing/verification step confirming the AI resolution didn't drop the user's own changes or silently favor attacker-supplied hunks.
5. Once written, the file is added to the index (`git add`) in the same call, and normal commit flow (`createCommit`, `app/src/lib/git/commit.ts:15-72`) will include it, meaning the corrupted content becomes part of the user's next commit/push without an explicit diff review comparable to the normal commit flow (contrast with `formatCommitMessage`/repo-rules checks, which exist for the message but not for conflict-resolution body content). [3](#0-2) 

By contrast, the project's own commit-message-generation pipeline explicitly hardens against adversarial input embedded in repo-rule descriptions ("strips control characters from rule descriptions so they cannot escape the block" — `app/test/unit/copilot-commit-message-prompt-test.ts:135-154`), showing the team is aware of prompt-injection risk in AI features, but the equivalent hardening for merge-conflict content driving `resolvedContent` was not found in the reviewed code.

### Impact Explanation
If an attacker crafts a branch/PR whose diff creates conflicts against a target repo, and the victim uses Copilot-assisted conflict resolution to reconcile it, carefully engineered conflict-marker content can manipulate the model into emitting `resolvedContent` that silently drops the victim's intended changes, reintroduces attacker payload, or otherwise diverges from a correct three-way merge. Because the batch-apply path writes and stages this content automatically (subject only to path-safety and "already externally resolved" checks — not content-correctness checks), the corrupted result is silently baked into the user's next commit and can be pushed upstream. This matches the "silent corruption of what the user commits or pushes" impact category, driven by an attacker-controlled fetched/merged repository, without any local access, admin rights, or social engineering beyond a normal merge/rebase workflow.

### Likelihood Explanation
Likelihood depends on (a) how effectively the underlying model resists adversarial conflict content (unverified from the code alone — no equivalent sanitization/stripping was found for merge-conflict hunks as exists for repo-rule descriptions in commit-message generation), and (b) users adopting the Copilot conflict-resolution flow and clicking "Continue Merge" without diffing every resolved file. Given Desktop explicitly supports batch acceptance of multiple resolutions with only per-file manual override as a mitigation, the practical safeguard is largely "the user trusts the AI," which is the same trust-boundary weakness LLM-in-the-loop features are known to have. I could not verify from the available code whether a mandatory diff-review step exists before commit for these resolutions (this needs further inspection of the result dialog, e.g. `copilot-conflicts-dialog.tsx`, which I did not fully load).

### Recommendation
- Treat conflict-hunk content the same as other untrusted, attacker-influenced input: sanitize/delimit it in the prompt the way `buildCommitMessageUserPrompt` already does for repo-rule descriptions, and instruct/validate that the model may not fabricate content absent from either side of the conflict.
- Require an explicit, mandatory diff view (old vs. "ours" vs. "theirs" vs. proposed resolution) for every file before it is written/staged, rather than silently writing on "Continue Merge."
- Add a structural verification step after resolution: confirm the resolved content is derivable from the two conflict sides (e.g., line-level provenance checking) and flag/reject resolutions that introduce content not traceable to either side.
- Avoid auto-staging (`git add`) resolved files as part of the same operation that writes them; separate "apply resolution" from "stage for commit" so the user has a natural breakpoint to inspect the working tree diff.

### Proof of Concept
Conceptual PoC (not fully verifiable without running the model, since sanitization behavior of the prompt for conflict content was not located in the reviewed code):
1. Attacker publishes a branch that conflicts with a file the victim is likely to merge/rebase against (e.g. via a PR).
2. The attacker crafts the conflicting hunk's text to include instructions/content designed to manipulate the model (indirect prompt injection) into emitting a "resolution" that omits the victim's own change or inserts attacker-chosen code, while still looking like a plausible merge.
3. Victim merges/rebases, triggers Copilot Conflict Resolution, and accepts the batch result via "Continue Merge" (`_applyCopilotConflictResolutions`, `app/src/lib/stores/app-store.ts:7169-7269`).
4. The manipulated `resolvedContent` is written to disk and `git add`-ed without a content-correctness check, then committed/pushed by the victim.

Note: I was unable to fully confirm (within tool budget) whether `copilot-conflicts-dialog.tsx` enforces a mandatory per-file diff review before "Continue Merge" is enabled, or whether the model prompt for conflict resolution applies input-sanitization comparable to the commit-message-generation prompt. These are the key open questions that would determine whether this is fully exploitable as described or only partially mitigated by UI review; a deeper look at `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx` and the prompt-construction code for conflict resolution (analogous to `buildCommitMessageUserPrompt`) would be needed to close this gap.
