### Title
Rebase executes against live branch refs while user approval is based on a stale commit preview, allowing a remote-controlled ref update to rewrite history the user never reviewed - (File: `app/src/lib/git/rebase.ts`, `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The reported DeFi bug is a TOCTOU: a rebalance amount is computed from a price snapshot, submitted as a transaction, and then executed later against the *current* (possibly attacker-manipulated) pool state, so the on-chain effect no longer matches what was approved. The same pattern exists in Desktop's rebase flow: the commit list and force-push warning shown to the user are computed from `baseBranch.tip.sha` / `targetBranch.tip.sha` captured at dialog-open time [1](#0-0) , but the actual git operation is executed by branch *name*, not by the pinned SHA [2](#0-1) . If the local ref for either branch moves between preview/confirmation and execution - e.g. because GitHub Desktop's background fetcher runs `fastForwardBranches` concurrently [3](#0-2)  after the remote (attacker-controlled) pushes new commits - the rebase silently rewrites history using a different commit range than the one the user reviewed and clicked "Start rebase" on.

### Finding Description
`updateRebasePreview` computes `commitsAhead`/`commitsBehind` from `baseBranch.tip.sha` and `targetBranch.tip.sha` at the moment the dialog renders [1](#0-0) . This preview (and, when force-push confirmation is enabled, the "warn about remote commits" check) is what the user relies on to decide whether to proceed [4](#0-3) .

When the user confirms, `startRebase`/`rebase` in the dispatcher pass `baseBranch`/`targetBranch` objects through to the low-level `rebase()` git wrapper, which invokes `git rebase <baseBranch.name> <targetBranch.name>` using the branch **names**, not the SHAs that were used to build the preview [5](#0-4) . Between the preview being computed and this command actually running, the app can perform a background fetch (`BackgroundFetcher` / `performFetch`) that calls `fastForwardBranches`, which updates local branch refs to match the remote [6](#0-5) . Because the remote is attacker-influenced (any git remote/proxy the user has added, or a compromised/malicious collaborator's push to a shared branch), the attacker can move `baseBranch` or `targetBranch` between the time the preview/warning was computed and the time the rebase command actually runs.

The existing "stale preview" guard in the UI (`updateStatus`/`updateRebasePreview` checking `computingRebaseForBranch !== baseBranch.name`) only protects against the *user* switching branches in the dropdown while a preview is loading [7](#0-6) ; it does not re-validate that the ref hasn't moved once the operation has been confirmed and is executing. Likewise `warnAboutRemoteCommits` is invoked once, before the operation starts [8](#0-7) , with no re-check immediately before the actual `git rebase` call.

### Impact Explanation
This silently corrupts what the user commits/rebases: the local branch can be rebased onto a base commit, or include target commits, that differ from what was shown in the "commits ahead/behind" preview and from what the force-push warning evaluated. If the target branch is subsequently force-pushed (a rebase is often followed by a force push), the user may push a history that incorporates commits they never saw or approved, based on a remote ref that moved out from under them - this matches the "silent corruption of what the user commits or pushes" impact class, driven by an attacker-controlled git remote.

### Likelihood Explanation
The race window is real but narrow: the local ref must move between preview computation/confirmation and the `git rebase` invocation. GitHub Desktop performs periodic background fetches and fast-forwards tracked branches automatically [9](#0-8) , so this is not a contrived scenario - it's the app's normal behavior colliding with user-driven multi-step dialogs (choose branch → confirm force-push warning → execute), each of which introduces a delay where a background fetch can land. No local/physical access or malware is required; the only requirement is that the attacker can push to (or control) a remote the victim has configured, which is within the stated valid-impact scope. However, exploitation requires precise timing relative to the user's UI interaction and the background-fetch interval, which likely keeps likelihood at low-to-moderate rather than trivial.

### Recommendation
Re-resolve and re-validate both `baseBranch.tip.sha` and `targetBranch.tip.sha` immediately before invoking `rebase()`, and abort/re-prompt if either has changed since the preview/confirmation was computed - mirroring the mitigation given for the on-chain report ("ensure re-balancing is necessary... compute on-chain at execution time"). Concretely, pass the pinned SHAs (not just branch names) into the low-level `rebase()` call, or perform a final `getMergeBase`/`getCommitsBetweenCommits` check against the live tips right before executing `git rebase`, surfacing a fresh confirmation dialog if the range differs from what was approved.

### Proof of Concept
1. Victim adds attacker-controlled remote (or attacker has push access to the tracked remote branch, e.g. a compromised collaborator).
2. Victim opens Rebase dialog; `updateRebasePreview` computes `commitsAhead`/`commitsBehind` from current `baseBranch.tip.sha`/`targetBranch.tip.sha` [1](#0-0) .
3. While the victim reads the dialog (or is shown the `WarnForcePush` interstitial), Desktop's background fetcher runs and fast-forwards the local base branch to new attacker-pushed commits [6](#0-5) .
4. Victim clicks "Start rebase". `dispatcher.rebase` → `appStore._rebase` → `rebase()` executes `git rebase <baseBranch.name> <targetBranch.name>`, resolving names to the now-updated refs, not the SHAs shown in the preview [5](#0-4) .
5. The rebase completes using the attacker's newly introduced base commits, which never appeared in the reviewed `commitsAhead`/`commitsBehind` preview - the user unknowingly rebases/pushes on top of unreviewed history.

export async function rebase(
  repository: Repository,
  baseBranch: Branch,
  targetBranch: Branch,
  progressCallback?: (progress: IMultiCommitOperationProgress) => void
): Promise<RebaseResult> {
  const baseOptions: IGitStringExecutionOptions = {
    expectedErrors: new Set([GitError.RebaseConflicts]),
  }

  let options = baseOptions

  if (progressCallback !== undefined) {
    const commits = await getCommitsBetweenCommits(
      repository,
      baseBranch.tip.sha,
      targetBranch.tip.sha
    )

    if (commits === null) {
      // BadRevision can be raised here if git rev-list is unable to resolve a
      // ref to a commit ID, so we need to signal to the caller that this rebase
      // is not possible to perform
      log.warn(
        'Unable to rebase these branches because one or both of the refs do not exist in the repository'
      )
      return RebaseResult.Error
    }

    options = configureOptionsForRebase(baseOptions, {
      commits,
      progressCallback,
    })
  }

  const result = await git(
    [...gitRebaseArguments(), 'rebase', baseBranch.name, targetBranch.name],
    repository.path,
    'rebase',
    options
  )

  return parseRebaseResult(result)
}

  private async performFetch(
    repository: Repository,
    fetchType: FetchType,
    remotes?: IRemote[]
  ): Promise<void> {
    await this.withPushPullFetch(repository, async () => {
      const gitStore = this.gitStoreCache.get(repository)

      try {
        const fetchWeight = 0.9
        const refreshWeight = 0.1
        const isBackgroundTask = fetchType === FetchType.BackgroundTask

        const progressCallback = (progress: IFetchProgress) => {
          this.updatePushPullFetchProgress(repository, {
            ...progress,
            value: progress.value * fetchWeight,
          })
        }

        if (remotes === undefined) {
          await gitStore.fetch(isBackgroundTask, progressCallback)
        } else {
          await gitStore.fetchRemotes(
            remotes,
            isBackgroundTask,
            progressCallback
          )

          : 'Refreshing repository'

          title: refreshTitle,

          kind: 'generic',
          title: refreshTitle,

  /** Initialize and start the rebase operation */
  public async startRebase(
    repository: Repository,
    baseBranch: Branch,
    targetBranch: Branch,
    commits: ReadonlyArray<CommitOneLine>,
    options?: { continueWithForcePush: boolean }
  ): Promise<void> {
    const { askForConfirmationOnForcePush } = this.appStore.getState()

    const hasOverriddenForcePushCheck =
      options !== undefined && options.continueWithForcePush

    const { branchesState } = this.repositoryStateManager.get(repository)
    const originalBranchTip = getTipSha(branchesState.tip)

    this.appStore._initializeMultiCommitOperation(
      repository,
      {
        kind: MultiCommitOperationKind.Rebase,
        commits,
        currentTip: baseBranch.tip.sha,
        sourceBranch: baseBranch,
      },
      targetBranch,
      commits,
      originalBranchTip
    )

    if (askForConfirmationOnForcePush && !hasOverriddenForcePushCheck) {
      const showWarning = await this.warnAboutRemoteCommits(
        repository,
        baseBranch,
        targetBranch.tip.sha
      )

      if (showWarning) {
        this.setMultiCommitOperationStep(repository, {
          kind: MultiCommitOperationStepKind.WarnForcePush,
          targetBranch,
          baseBranch,
          commits,
        })
        return
      }
    }

    await this.rebase(repository, baseBranch, targetBranch)
  }
