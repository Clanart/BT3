### Title
Cached FROST preprocess seed is committed and reused before the signing set is finalized, enabling nonce reuse and secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug class in the external report is "state is committed and externally acted upon before the authorizing vote/decision completes." In Serai's coordinator signing protocol, the FROST preprocess seed is persisted to the database (`CachedPreprocesses::set`) in `preprocess_internal` *before* any signing set, message, or preprocess validity is decided — and it is never invalidated. Every subsequent `share_internal`/`complete` call under the same context deterministically regenerates the identical nonces and emits a new signature share, so a participant who causes the node to evaluate two distinct preprocess sets for the same context receives two shares bound to the same nonce, allowing recovery of the victim's secret share.

### Finding Description
`SigningProtocol::preprocess_internal` writes an XOR-encrypted `CachedPreprocess` keyed only by `self.context` (`coordinator/src/tributary/signing_protocol.rs:123-145`). If an entry exists, it is loaded and fed to `AlgorithmSignMachine::from_cache`, which re-derives the nonces via `ChaCha20Rng::from_seed(*seed.0)` (`crypto/frost/src/sign.rs:127-133`). The cached seed is:

- written before the preprocesses/message are known (analogous to `backend_url` being set before the vote resolves), and
- never deleted or rotated after `sign` runs, so every call under the same context reuses the same nonce pair `(d, e)`.

`DkgConfirmer::share` (`coordinator/src/tributary/signing_protocol.rs:304-310`) maps an *attacker-supplied* `HashMap<Participant, Vec<u8>>` of preprocesses through `threshold_i_map_to_keys_and_musig_i_map` and then calls `share_internal`, which calls `machine.sign(preprocesses, msg)` (`crypto/frost/src/sign.rs:283-...`). `sign` validates the set but emits `SignatureShare` = `d + e·ρ_i + λ_i·x_i·c`, where `ρ_i` (binding factor) and `λ_i` (Lagrange coefficient) both depend on the *submitted* preprocess set, and `c` commits to all preprocesses. Since `share` is a non-consuming query that can be evaluated for any submitted preprocess map under the fixed context `(b"DkgConfirmer", attempt)`, a malicious validator who submits two different preprocess sets obtains:

```
s1 = n + ρ1·λ1·x·c1
s2 = n + ρ2·λ2·x·c2
```

with the same `n = d + e`. The attacker knows `ρ1, ρ2, λ1, λ2, c1, c2` (all public/derivable from the transcripts), giving two linear equations in two unknowns `(n, x)` — direct recovery of the node's MuSig secret share `x`.

### Impact Explanation
Recovery of `x` breaks the confidentiality of the validator's key share for the affected set. Combined with fewer-than-threshold additional shares, or used to produce valid-looking blame/framing evidence, it compromises the threshold key. This is the FROST nonce-reuse (parallel-session / ROS-style) primitive: the nonce is fixed by a DB write that precedes and survives the signing-set decision, so re-evaluation over distinct attacker-controlled preprocess sets leaks the secret.

### Likelihood Explanation
Reachability requires that the coordinator emits signature shares for more than one preprocess set under a single `(context, attempt)` — i.e., that `share`/`complete` be evaluated against attacker-influenced preprocess maps more than once, which the API shape permits (`share` takes the full preprocess map as an argument rather than binding to a single decided set, and `complete` internally re-runs `share_internal`). The vulnerable primitives are all in-scope: `SigningProtocol::preprocess_internal`, `DkgConfirmer::share`, `AlgorithmSignMachine::sign`, `CachedPreprocess`. One caveat I could not fully resolve without reading `coordinator/src/tributary/handle.rs` in full: whether the call site deduplicates/prevents a second `share` evaluation per attempt. The nonce reuse itself is unconditional once two evaluations occur, and `complete`'s internal re-derivation shows the cached seed is reused as a matter of design.

### Recommendation
- Do not derive/reuse nonces before the signing set and message are fixed. Either delete `CachedPreprocesses[context]` on the first `sign` evaluation, or bind the derived nonce to the decided `included` set and `msg` (e.g., mix their hashes into the ChaCha20 seed) so that distinct preprocess sets never reuse `(d, e)`.
- Make `share`/`complete` single-shot per context: record that a share was already emitted for `(context, attempt, included, msg)` and refuse divergent re-evaluations.
- Enforce the documented `CachedPreprocess` "MUST only be used once" contract inside the crate rather than leaving it to callers.

### Proof of Concept
1. Eve participates in DKG confirmation attempt `a` with honest victim V. Context is fixed: `("DkgConfirmer", a)`.
2. Eve causes V's `DkgConfirmer::share` to be evaluated with preprocess set `S1` (participants `{Eve, V, …}` in one ordering/subset). V emits `s1 = n + ρ1·λ1·x·c1`.
3. Eve causes a second evaluation with a different valid set `S2` (different included participants or a different preprocess commitment for Eve). `preprocess_internal` reloads the same `CachedPreprocess` (`signing_protocol.rs:137-145`), so `sign` reuses `n`; V emits `s2 = n + ρ2·λ2·x·c2`.
4. Eve solves the 2×2 linear system over the Ristretto scalar field for `x`, V's secret share.

Concrete code anchors: the persistent cache write at `coordinator/src/tributary/signing_protocol.rs:134`, the deterministic reload at `coordinator/src/tributary/signing_protocol.rs:137-145`, nonce regeneration from the seed at `crypto/frost/src/sign.rs:127-141`, and attacker-controlled set admission at `crypto/frost/src/sign.rs:290-313`.
