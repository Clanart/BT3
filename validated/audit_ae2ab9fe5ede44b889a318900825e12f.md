### Title
Missing duplicate-output-token validation in Tron IntentGatewayV2 `placeOrder` enables incorrect escrow/fill accounting on same-chain partial fills - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol:165-189`) rejects orders whose `output.assets` array contains a duplicate token, using transient storage (`tload`/`tstore`) as a same-transaction dedup guard before `placeOrder` proceeds. A dedicated regression test suite (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol:1927-1964`, "DUPLICATE INPUT TOKEN REJECTION TESTS") documents that this class of bug was previously exploitable and was fixed ("previously merged into one escrow bucket"). The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does not carry this fix forward: its `placeOrder` function performs no duplicate check on `order.output.assets` at all.

### Finding Description
This is the direct local analog of the StakeDAO bug: an array that can legitimately contain the same key (token) twice is consumed by downstream logic that assumes uniqueness, and per-key state gets aggregated/read incorrectly as a result.

In the same-chain fill path (`IntrinsicIntents.sol` / the equivalent logic ported for Tron use), partial fill progress is tracked in a mapping keyed by **output token address**, not by leg index: [1](#0-0) 
```
for (uint256 i; i < outputsLen; i++) {
    bytes32 outputToken = order.output.assets[i].token;
    ...
    uint256 alreadyFilled = _partialFills[commitment][outputToken];
    uint256 remaining = totalRequired - alreadyFilled;
    ...
    uint256 amountFilled = alreadyFilled + fillAmount;
    _partialFills[commitment][outputToken] = amountFilled;
```
If `order.output.assets` contains the same token twice (two separate legs, each with its own `totalRequired`), a fill against one leg writes `_partialFills[commitment][outputToken]` and the *other* leg's iteration reads that same slot as its own `alreadyFilled`. This corrupts the per-leg "remaining" computation: one leg can appear fully filled (or over-filled) based on payment made toward the other leg, letting `remaining == 0` short-circuit escrow release logic, or letting `escrowedAmount = _orders[commitment][...]` (full remaining escrow) be released prematurely while the corresponding output was never actually paid in full.

The canonical EVM gateway (`evm/src/apps/IntentGatewayV2.sol:165-189`) forecloses this entirely by rejecting duplicate output tokens **before** any escrow is created, using a transient-storage check: [2](#0-1) 

The Tron contract's `placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol:332-497`) has no equivalent block — it goes straight from input validation into fee computation and escrow crediting, never inspecting `order.output.assets` for duplicates.

### Impact Explanation
This maps directly to the required Hyperbridge impact categories: transaction manipulation and loss/misallocation of escrowed bridged funds. A user (order placer) can craft an order with a duplicated output token across two legs with different `totalRequired` amounts. A solver filling one leg can cause the escrow-release accounting for the other leg to under- or over-release input tokens relative to what was actually paid to the beneficiary, since `_partialFills` conflates the two legs' progress into one shared counter. This is a state-corruption bug reachable by an ordinary, permissionless user placing an order — no relayer, prover, or admin involvement required — directly analogous to the H-3 report's "duplicate key overwrites/aggregates incorrectly and funds are misaccounted" pattern.

### Likelihood Explanation
Likelihood is high for any deployment of this Tron contract: the attacker only needs to call the public, unprivileged `placeOrder` entrypoint with a normal `Order` struct containing two output legs referencing the same token address. No special timing, relayer collusion, or proof forgery is needed. The vulnerability class was serious enough that the canonical EVM contract shipped an explicit fix and regression test for it, but the Tron variant appears to be missing that fix, indicating a real drift between the two deployments of "the same" contract.

### Recommendation
Port the duplicate-output-token guard from `evm/src/apps/IntentGatewayV2.sol:165-189` into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, rejecting orders whose `order.output.assets` contains a repeated token before any escrow bookkeeping occurs. Alternatively/additionally, change `_partialFills` (and any equivalent Tron-side partial-fill state) to be keyed by `(commitment, outputIndex)` rather than `(commitment, outputToken)`, so distinct legs never alias the same storage slot even if they share a token.

### Proof of Concept
1. Construct a same-chain `Order` where `order.output.assets[0].token == order.output.assets[1].token == T`, with `assets[0].amount = 100` and `assets[1].amount = 500`.
2. Call `placeOrder` on the Tron `IntentGatewayV2` — succeeds because no duplicate-output check exists (contrast with `evm/src/apps/IntentGatewayV2.sol`, where this would revert with `InvalidInput`).
3. A solver fills leg 0 by providing `100` of token `T`, calling the same-chain fill path. `_partialFills[commitment][T]` is set to `100`.
4. When leg 1 (`totalRequired = 500`) is processed in the same or a later fill call, `alreadyFilled = _partialFills[commitment][T] = 100` is read for leg 1 even though leg 1 received nothing, causing `remaining = 500 - 100 = 400` instead of `500` — under-charging the solver for leg 1's output and/or triggering incorrect `isFullyFilled`/escrow-release computations relative to the two legs' actual escrowed input amounts.

Note: I was not able to fully trace whether the Tron `IntrinsicIntents`-equivalent fill logic is byte-for-byte identical to `evm/src/apps/intentsv2/IntrinsicIntents.sol` (the Tron repo directory structure for the same-chain fill path was not fully retrievable within the tool budget); the finding is anchored on the confirmed absence of the duplicate-output guard in `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, which is the root precondition the EVM version explicitly prevents.
