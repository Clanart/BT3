### Title
Aggregator gRPC server skips all client TLS authentication when `client_verification=false`, allowing unauthenticated callers to invoke state-changing/broadcasting RPCs like `SendMoveToVaultTx` - (File: `core/src/servers.rs`)

### Summary
`create_grpc_server` only attaches `.client_ca_root(..)` to `ServerTlsConfig` and only installs the `OnlyAggregatorAndSelf` interceptor when `config.client_verification` is `true`; when it is `false`, the TLS layer never requests a client certificate and the interceptor degrades to `Noop`, which passes every request through unchecked. This is a genuine, demonstrable authentication bypass on the exact reachable path documented in the question.

### Finding Description
The binding this claims is broken: `CALLER_AUTHORITY(reaching send_move_to_vault_tx) == certificate_holder(aggregator's CA)`.

- In `create_grpc_server`, TLS config is built as:
```
let tls_config = if config.client_verification {
    ServerTlsConfig::new().identity(server_identity).client_ca_root(client_ca)
} else {
    ServerTlsConfig::new().identity(server_identity)
};
``` [1](#0-0) 
When `client_verification` is `false`, no `client_ca_root` is set, so `rustls`/tonic never requests or verifies a client certificate during the handshake — any TLS client, including one with a throwaway self-signed keypair or no certificate at all, completes the handshake.

- The authorization layer is likewise disabled: the `InterceptedService` is built with `Noop` instead of `OnlyAggregatorAndSelf` in this branch:
```
let service = InterceptedService::new(service, if config.client_verification { ... OnlyAggregatorAndSelf {...} } else { Noop });
``` [2](#0-1) 
`Noop` unconditionally returns `Ok(req)` with no certificate check at all: [3](#0-2) 
Even the `OnlyAggregatorAndSelf` interceptor — which is what would enforce "caller == aggregator cert holder" — only compares the leaf peer certificate against pinned `aggregator_cert`/`our_cert` values, and this comparison never executes in the `false` branch because `Noop` is installed instead.

After the handshake and interceptor pass-through, the request reaches `AggregatorServer::send_move_to_vault_tx` (the `SendMoveToVaultTx` RPC), which is a state-changing/broadcasting endpoint that participates in the operator-signature-collection and movetx-broadcast path (`Aggregator::collect_operator_sigs`, `create_movetx`) exposed in `core/src/rpc/aggregator.rs`. [4](#0-3) [5](#0-4) 

Before the fix (intended state): CALLER_AUTHORITY should equal `aggregator's certificate holder` for every non-Noop-eligible RPC. After, with `client_verification=false`: CALLER_AUTHORITY equals "any TCP peer able to complete a TLS handshake with no cert requirement," which does not equal `certificate holder`. The equality is broken — no existing guard (`only_aggregator_and_self`, `is_deposit_valid`, etc.) intercepts this because the interceptor that would perform the check is never installed in this configuration branch.

### Impact Explanation
This matches the rule's High-severity category: "an unauthenticated state-changing or broadcasting call." Any unprivileged network client reaching the aggregator's TCP port can invoke `SendMoveToVaultTx` and any other aggregator RPC without holding a TLS certificate, i.e., without being a party the protocol was designed to trust. I was not able to fully inspect the body of `send_move_to_vault_tx` (the file was truncated in the tool output before that specific handler), so I cannot independently confirm whether it directly broadcasts attacker-supplied raw bytes or only triggers broadcast of an already-N-of-N-signed transaction looked up server-side by `deposit_outpoint`. In either case, the authentication bypass itself is confirmed and repeatable across every RPC method and every deposit/operator, since the flaw is in the shared `create_grpc_server` path used by all three server types (verifier, operator, aggregator) whenever `client_verification=false`.

### Likelihood Explanation
Preconditions: exactly as stated in the question, `client_verification=false` in `BridgeConfig`. Under that single configuration flag, the exploit requires no BTC cost, no key compromise, and no privileged role — only network reachability to the aggregator's gRPC port and a throwaway TLS keypair. This is fully consistent with the excluded threat model (no reliance on TLS interception, node compromise, or key theft).

### Recommendation
Always set `.client_ca_root(client_ca)` on `ServerTlsConfig` regardless of `config.client_verification`, so the TLS layer itself enforces "client must present a certificate signed by our CA." If `client_verification` is meant to be a legitimate operational toggle, it should only ever gate additional authorization logic (e.g., which specific certs are accepted), never remove the requirement to present *any* verified certificate. Remove or clearly document/guard the `Noop`-on-TCP code path so it can never be reached in production TCP deployments; at minimum, refuse to start a TCP aggregator/operator/verifier server with `client_verification=false`.

            0,

        )?;

        let musig_sigs_and_nonces = musig_partial_sigs
            .into_iter()
