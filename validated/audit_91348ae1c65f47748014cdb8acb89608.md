## Reduction of the external report

The Exchange bug is: state that should be "consumed exactly once" (a transaction's completion) is not cleared before/atomically with the side effect, leaving room for the same logical operation to be executed/paid twice. The devs' own fix pattern for Hyperbridge's ISMP core confirms the team already understands and applies this invariant everywhere else: delete the commitment/receipt *before* invoking the untrusted callback, and re-check it immediately before use, e.g. [1](#0-0) [2](#0-1) 
and in the EVM host, `dispatchIncoming(PostRequest,...)` and `dispatchTimeOut(...)` both write/clear the receipt/commitment *before* the external `.call`: [3](#0-2) [4](#0-3) 

## The one path that breaks the pattern: `dispatchIncoming(GetResponse,...)`

`dispatchIncoming` for a `GetResponse` sets `_responseReceipts[commitment]` before the external call (correct CEI for the *response* replay-guard), but it never deletes/clears `_requestCommitments[commitment]` — the record that backs the request's escrowed relayer fee — either before or after paying that fee: [5](#0-4) 

Compare this to the sibling function `dispatchTimeOut(GetRequestTimeout,...)`, which handles the *timeout* of the exact same `GetRequest` commitment. That function requires `_requestCommitments[commitment]` to still exist (`meta.sender != address(0)`, checked in `HandlerV2.handleGetRequestTimeouts`) and, on success, refunds the fee to `meta.sender` — a second, independent fee payout keyed off the very same commitment: [6](#0-5) [7](#0-6) 

### Title
Fee-accounting double-settlement: `GetRequest` relayer fee can be paid twice via `dispatchIncoming(GetResponse)` + `dispatchTimeOut(GetRequestTimeout)` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`_requestCommitments[commitment]` is the single source of truth for a `GetRequest`'s escrowed fee and its "still pending" status, consumed by two mutually-exclusive terminal paths: a successful `GetResponse` (pays the relayer) and a proven timeout (refunds the sender). The successful-response path pays the relayer fee but never deletes `_requestCommitments[commitment]`, so the record remains "live" and can still satisfy the `meta.sender != address(0)` gate used by the timeout path.

### Finding Description
`dispatchIncoming(GetResponse memory response, address relayer)` reads `_requestCommitments[commitment].fee` and pays it to `relayer` on a successful callback, but the mapping entry itself is left untouched: [8](#0-7) 

`handleGetRequestTimeouts` in `HandlerV2.sol` only checks that `meta.sender != address(0)` before calling `dispatchTimeOut`, and the non-membership proof it verifies is a proof against the *destination chain's* state trie (whether a response/request-receipt was ever recorded there) — it is completely decoupled from Hyperbridge's own `_responseReceipts` bookkeeping on the source (this) chain: [7](#0-6) 

`dispatchTimeOut(GetRequestTimeout,...)` then unconditionally refunds `meta.fee` to `meta.sender` and only *now* deletes `_requestCommitments[commitment]`: [6](#0-5) 

Because the response path never clears its half of the shared state (`_requestCommitments`), the same fee-escrow record can be consumed twice: once by the relayer who delivered a valid `GetResponse`, and a second time by whoever later produces a valid non-membership proof for `handleGetRequestTimeouts` and drives it to `dispatchTimeOut`. All the pieces needed to reach this state are exposed through unprivileged, permissionless entrypoints (`HandlerV2.handleGetResponses` / `handleGetRequestTimeouts`), gated only by proof verification against Hyperbridge/consensus state, not by any check of the local `_responseReceipts`/`onGetResponse` outcome.

### Impact Explanation
This is a direct loss-of-funds / double-settlement bug in the fee escrow: the same `GetRequest.fee` deposit can be paid out twice from `EvmHost`'s fee-token balance — once as relayer compensation, once as a sender refund — for a single logical request. That matches the bounty's "stealing or loss of funds" / "replay / double-claim / double-settlement" categories, and requires no malicious relayer, prover, or admin — only two otherwise-legitimate message deliveries hitting the same commitment.

### Likelihood Explanation
The response path is reachable by any relayer submitting a valid Merkle-proof-backed `GetResponseMessage` (no privilege required), and the timeout path is reachable by anyone who can later produce a valid non-membership proof for the same request against the state machine's trie at some height. Because the two verifications are against different trees (Hyperbridge's own MMR/overlay root for `GetResponse` vs. the destination chain's Polkadot trie for the timeout), nothing prevents both proofs from independently validating for the same commitment if the request's window and destination-chain history allow it — the bug is purely in `EvmHost.sol` failing to null out `_requestCommitments[commitment]` after paying the relayer, not in proof forgery.

### Recommendation
Delete `_requestCommitments[commitment]` in `dispatchIncoming(GetResponse,...)` immediately after (or as part of) paying the relayer fee, mirroring the pattern already used in `dispatchTimeOut` and `dispatchIncoming(PostRequest,...)`. Optionally also add an explicit check in `handleGetRequestTimeouts`/`dispatchTimeOut` that `_responseReceipts[commitment]` is empty before allowing the timeout refund, as defense in depth.

### Proof of Concept
1. Attacker/user dispatches a `GetRequest` via `EvmHost.dispatch(...)`, escrowing `fee` in `_requestCommitments[commitment]`.
2. A relayer submits a valid `GetResponseMessage` through `HandlerV2.handleGetResponses` → `EvmHost.dispatchIncoming(GetResponse,...)`. `onGetResponse` succeeds, `_responseReceipts[commitment]` is set, and `fee` is paid to the relayer (`EvmHost.sol:841-847`). `_requestCommitments[commitment]` remains populated with the same `fee` value.
3. Separately (e.g., because the destination chain's queried key was later pruned/never populated, or because a state height prior to the response is used), a party assembles a valid `GetTimeoutMessage` with a non-membership proof for `RESPONSE_RECEIPTS_STORAGE_PREFIX || commitment` against the destination chain's trie at `message.height`, and calls `HandlerV2.handleGetRequestTimeouts`.
4. `meta.sender != address(0)` still holds (never cleared in step 2), so the proof verifies and `EvmHost.dispatchTimeOut(GetRequestTimeout,...)` executes, refunding `meta.fee` to `meta.sender` — a second payout of the same escrowed fee for one `GetRequest`.

    /**
     * @dev Dispatch an incoming GET response to source module
     * @param response - get response
     */
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
