### Title
Owner can retroactively change `commissionRate` and reduce a user's already-submitted gasless swap payout - ([File: contracts/bindings/kip247/GaslessSwapRouter.go])

### Summary
`GaslessSwapRouter`, the KIP-247 gasless-swap settlement contract used by the Kaia gasless module, exposes an owner-only `updateCommissionRate(uint256 _commissionRate)` function that mutates the single global `commissionRate` state variable consumed by `swapForGas()`. [1](#0-0)  This mirrors the reported `BvbProtocol.setFee` bug class: a fee value applied to already-created, in-flight value (an "Order"/pending swap) can be changed by the privileged owner at any time, with no mechanism to lock the fee at the moment the user's value entered the pending state.

### Finding Description
`swapForGas(address token, uint256 amountIn, uint256 minAmountOut, uint256 amountRepay, uint256 deadline)` swaps a user's ERC-20 token for KAIA to repay the gas-paying proposer, and the contract computes a `Commission` deducted from the swap output before returning `FinalUserAmount` to the user, as evidenced by the `SwappedForGas(proposer, amountRepaid, user, finalUserAmount, commission)` event. [2](#0-1)  The commission taken is a live read of `commissionRate` at execution time, not a value fixed when the user signed/submitted the transaction: `commissionRate()` is a plain state getter, and it can be changed at any time via `updateCommissionRate`, which is gated only by `Ownable` (owner-only), with a `CommissionRateUpdated(oldRate, newRate)` event and no evidence in the generated bindings of an upper-bound `require` (unlike `BvbProtocol.setFee`'s `require(_fee <= 50)`). [3](#0-2) [4](#0-3) 

The gasless module's tx-pool validation (`IsSwapTx`/`VerifyExecutable` in `kaiax/gasless/impl`) only checks structural properties of the `swapForGas` call — token whitelisting and function selector/argument decoding — via `decodeSwapTx`/`isSwapTx`, and the user-supplied `minAmountOut` only bounds the DEX-side swap output, not the post-swap commission deduction. [5](#0-4)  This means a user's gasless swap transaction, once signed and sitting in the pool (or in the block-building path used by proposers), can have its effective take-rate changed by the owner calling `updateCommissionRate` before the swap executes, with no per-transaction commitment of the fee that was in effect when the user built/signed the transaction.

### Impact Explanation
Because `commissionRate` is a single mutable global applied at execution time rather than pinned per-transaction, the owner can unilaterally increase the commission and apply it to swaps that users already signed and submitted expecting the previously-effective (lower) rate. This directly reduces `FinalUserAmount` paid to the swap sender and increases the amount claimable by the owner via `ClaimCommission`, effectively redirecting value away from the unprivileged gasless-swap sender without their consent — the same "owner modifies fee on existing/pending amount and steals value" pattern as the source report, just relocated to Kaia's KIP-247 gasless settlement flow. [6](#0-5) 

### Likelihood Explanation
The precondition (owner privilege) is the same as in the original finding; likelihood of exploitation depends on the owner/governance actually behaving maliciously or the key being compromised, which is consistent with how the original Sherlock report was scored Medium (privileged-role fee-change abuse rather than a fully permissionless exploit). Given the absence of a per-transaction fee commitment or maximum-rate cap visible in the available bindings, any owner-side fee change takes effect immediately on all pending/pooled gasless swaps.

### Recommendation
- Commit the `commissionRate` (or a maximum-allowed commission) into the swap transaction/order itself (e.g., an additional user-supplied `maxCommission` parameter checked in `swapForGas`, analogous to `minAmountOut`), so a later owner-side rate change cannot retroactively affect already-signed transactions.
- Add a hard upper bound (`require(_commissionRate <= MAX_RATE)`) in `updateCommissionRate`, and consider a timelock/delay before a new rate takes effect so it cannot be applied to transactions already broadcast.

### Proof of Concept
1. User signs and broadcasts a `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` transaction while `commissionRate` = R0, expecting `FinalUserAmount ≈ swapOutput - amountRepay - R0*swapOutput`.
2. Before the transaction is executed/included, the owner calls `updateCommissionRate(R1)` with `R1 >> R0` (bindings show no visible cap). [7](#0-6) 
3. The user's previously-signed transaction executes against the new, higher `commissionRate` R1 (read live in `swapForGas`), producing a much smaller `FinalUserAmount` than the user expected when signing, with the difference captured as `Commission` claimable by the owner via `claimCommission()`. [8](#0-7)
