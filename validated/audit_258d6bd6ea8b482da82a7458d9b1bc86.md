## Title
Stale line-selection applied to a freshly re-fetched diff can silently corrupt partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
`applyPatchToIndex()` re-fetches the working-directory diff for a file at commit time and reuses the `DiffSelection` object the user built against a *previously rendered* diff. The selection only stores raw line indices, with no check that the diff it is being applied to is the same diff the user actually reviewed. If the file's content on disk changes between the moment Desktop renders the diff (and the user selects/deselects lines) and the moment the user clicks "Commit," the stale index-based selection is applied to a structurally different diff, causing Desktop to silently commit different lines than the ones the user saw and approved.

### Finding Description
When a user partially stages a file, Desktop stores the selection as a `DiffSelection`, an opaque set of line indices with no notion of file content identity: [1](#0-0) 

That selection is created against a diff fetched once for display in the Changes view: [2](#0-1) 

At commit time, however, `createCommit` → `stageFiles` → `applyPatchToIndex` does **not** reuse that already-loaded diff. It calls `getWorkingDirectoryDiff` again, independently, right before building the patch: [3](#0-2) 

The freshly-fetched diff's hunks are then walked and `file.selection.isSelected(absoluteIndex)` is used purely by numeric line-index, with zero validation that the hunk layout still matches the diff the selection was computed against: [4](#0-3) 

Desktop is aware that diffs can go stale relative to a selection — there is explicit reconciliation logic for this, but it is *only* wired into the UI refresh path (`updateChangesWorkingDirectoryDiff`), not into the commit path: [5](#0-4) 

`_commitIncludedChanges` goes straight from the cached `WorkingDirectoryFileChange.selection` to `createCommit`, with no intervening call to refresh/reconcile the selection against the current on-disk diff: [6](#0-5) [7](#0-6) 

So the guard rail that exists for the *rendering* path ("previously selected line which now no longer exists...isn't still selected") is never applied on the *commit* path, which independently re-diffs the file and blindly re-applies the old index-based selection.

### Impact Explanation
If a tracked file's content changes on disk between diff render and commit (e.g. because of an in-repo build/format/lint step, a checked-in editor auto-formatter, a background `git status`/refresh cycle that Desktop itself performs, or content restored by a concurrent git operation), the hunks and line numbering the user saw when selecting individual lines/hunks no longer correspond to the hunks Desktop re-diffs at commit time. Because selection is keyed purely on positional index with no diff-identity check, the resulting patch built by `formatPatch`/`applyPatchToIndex` can:
- silently include attacker/tool-injected lines the user never reviewed or intended to commit, or
- silently drop lines the user explicitly selected.

This is a silent corruption of what the user commits (and subsequently pushes), which is explicitly in scope of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
The window is real but narrow: it requires the working copy of the selected file to change between the diff being loaded for display and the user clicking Commit. Desktop performs many git operations (periodic background refresh, status polling, checkout follow-ups) that can race with a user reviewing/staging changes over a period of seconds; a repository containing tooling (pre-commit hooks, watch-mode formatters, build scripts) that legitimately rewrites tracked files during this window is enough to trigger the mismatch without any explicit malicious action from the user. It is a moderate-likelihood logic bug rather than a directly attacker-triggered exploit, since it depends on a content-changing side effect happening within the review window.

### Recommendation
Before staging a partial selection at commit time, `applyPatchToIndex` (or its caller) should validate that the diff it just re-fetched matches the diff the selection was computed against (e.g., by comparing hunk headers/line counts or by carrying a content hash/identity token alongside `DiffSelection`), and either abort with an explicit "diff changed, please re-review" error or recompute `selectableLines` the same way `updateChangesWorkingDirectoryDiff` already does, prior to generating the patch — never silently apply a stale index-based selection to a structurally different diff.

### Proof of Concept
1. Modify a tracked file with several hunks; open it in Desktop's Changes view so the diff and selectable lines are computed and cached.
2. Deselect a subset of lines in one hunk (partial selection), leaving the commit dialog open.
3. Before clicking Commit, have the working copy of that same file change on disk (e.g. via an external formatter/watcher rewriting whitespace/line order, or a script triggered by Desktop's own background refresh) such that hunk boundaries shift.
4. Click Commit. Observe that `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff and `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) applies the old positional selection to the new hunks, producing a commit whose content differs from what was visually selected in step 2 — with no warning shown to the user.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
