Confirmed: `noopFormatChecker` always returns `true` for `Kip71GasTarget`, so no zero-check exists anywhere on this governance parameter's value.

### Title
Division by zero in KIP-71 `NextMagmaBlockBaseFee` when `GasTarget` governance parameter is set to 0 - (File: params/kip71_config.go)

### Summary
The KIP-71 base fee formula in `KIP71Config.NextMagmaBlockBaseFee` divides by the `GasTarget` governance parameter without ever validating that it is non-zero. `GasTarget` is settable via a standard governance vote (`Kip71GasTarget`), and its `FormatChecker` is `noopFormatChecker`, which unconditionally returns `true`, accepting any `uint64` value including `0`.

### Finding Description
`NextMagmaBlockBaseFee` computes the base fee delta using `gasTarget` as a divisor in two branches: [1](#0-0) [2](#0-1) 

If `gasTarget == 0` and `parentGasUsed != 0` (essentially any block with nonzero gas usage), the code enters either the `parentGasUsed > gasTarget` or `parentGasUsed < gasTarget` branch (the `==` shortcut only triggers when `parentGasUsed` is also 0), and calls `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`. Go's `big.Int.Div` panics on division by zero.

The `GasTarget` parameter is fully attacker/voter-controllable through the governance module. Its parameter definition uses no lower-bound check: [3](#0-2) 

`noopFormatChecker` is a true no-op: [4](#0-3) 

And header-level vote consistency checking (`checkConsistency`) explicitly allows `Kip71GasTarget` votes through with no additional validation beyond `NewVoteData()`'s format check (which is the same no-op): [5](#0-4) 

This is directly analogous to the TFLite `BatchToSpaceNd` bug class: an attacker-influenced parameter (`block_shape` there, `GasTarget` here) reaches a division operation with no zero-guard, causing a crash.

### Impact Explanation
Once a governance vote sets `GasTarget = 0` and the vote is applied (epoch boundary), every node computing the next Magma-era block's base fee — during block validation (`VerifyMagmaHeader`), block assembly, `SuggestGasPrice`/`feehistory` RPC calls, and `EstimateGas`/`DoCall` paths that use `NextMagmaBlockBaseFee` — will panic with a division-by-zero as soon as a block with nonzero `GasUsed` is processed. This affects consensus-critical block processing on all full/consensus nodes simultaneously, functioning as a network-wide safety/liveness bug reachable purely through the in-scope "governance parameters" path (no malicious peer/p2p/consensus-message needed — it's a standard on-chain governance vote). This can halt chain progression across all honest nodes at once (a form of state-processing failure at consensus-critical code), which is High severity.

### Likelihood Explanation
The precondition is a single governance vote (`Kip71GasTarget = 0`) being cast by any council member/governing node and passing the standard vote-collection process at an epoch boundary — no format or bound check rejects this value anywhere in the pipeline described above. Governance votes are part of Kaia's normal, in-scope operation, making this readily reachable, though it requires the voting entity's usual authorization to cast governance votes (a validator/council member or the single-mode governing node), not an arbitrary unprivileged transaction sender.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally for `Kip71BaseFeeDenominator`, which is defensively handled at line 71-76 of `kip71_config.go` but for gas target no analogous default fallback exists) that rejects `0`, e.g. `v > 0`, mirroring the existing zero-check pattern already used for `BaseFeeDenominator`: [6](#0-5) 
Additionally, add a defensive zero-check for `gasTarget` inside `NextMagmaBlockBaseFee` itself (fallback to a safe default, consistent with the `BaseFeeDenominator` handling) so that even historically-accepted or malformed configs cannot trigger a panic.

### Proof of Concept
1. Via governance voting, a council member/governing node casts a vote `Kip71GasTarget = 0`.
2. The vote is collected and, since `checkConsistency` performs no extra validation for this key [5](#0-4) , and `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` [3](#0-2) , the value `0` is accepted and becomes effective at the next epoch.
3. Once effective, any block whose parent has `GasUsed > 0` (virtually guaranteed) causes `NextMagmaBlockBaseFee` to execute `x.Div(x, new(big.Int).SetUint64(0))` [7](#0-6)  or the symmetric branch at lines 118-121, panicking with a runtime division-by-zero on every node that processes/validates/prepares that header or serves `eth_feeHistory`/`kaia_gasPrice`/`eth_estimateGas` RPC calls referencing the new parameter set.
