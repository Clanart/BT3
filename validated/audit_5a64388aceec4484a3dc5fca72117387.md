## Analog Identified

### Title
Disabled overfill clamp lets a manipulated venue price drain filler funds through unbounded output payout - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The bug report's core invariant is: *a value used to size a payout must track the instrument's real, current tradable price — not a stale or attacker-influenced reference — or a counterparty can extract more value than they are owed.* The local Hyperbridge analog is the `FXFiller` intents strategy: it sizes solver payouts against a live Uniswap V4 venue quote, but the loss-bound that was supposed to cap payout to the user's requested amount plus a small overfill tolerance has been explicitly disabled, leaving the payout amount fully driven by whatever price the venue reports at fill time.

### Finding Description
`calculateProfitability` resolves each order leg's payout rate via `resolveLegRates`, which for venue-priced pairs takes `venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)` directly from a live AMM quote [1](#0-0) . `computeLegPolicyOutput` then converts the leg's input amount into an output (`policyMaxOutput`) using that rate [2](#0-1) .

The only safety net against a bad or manipulated rate is `checkPriceGuard`, which compares the venue quote to a *static configured reference* and rejects only if it deviates — but if no `priceGuard` is configured for the chain (or `guard.reference` is `0`), the function returns `true` unconditionally, i.e. no protection at all [3](#0-2) .

The second, independent safety net — an absolute overfill ceiling on the computed payout — has been deliberately disabled. The code computes `overfillCeiling = output.amount * (1 + maxOverfillBps) / 10000` but then assigns `policyMaxOutput = rawPolicyMaxOutput` unconditionally and only logs a warning if the ceiling is exceeded, instead of clamping: [4](#0-3) 

The comment in the code is explicit about what this removes: *"this removes the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price. Output is no longer capped; we only emit a warning."* [5](#0-4) 

The uncapped `policyMaxOutput` then flows straight into `finalOutputAmount` (bounded only by the filler's wallet/venue liquidity, not by any price-correctness bound) and is used to actually pay the beneficiary through `fillOrder` on-chain [6](#0-5) .

This is structurally identical to the report's broken invariant: the amount paid out is sized from a price reference (the live venue quote) that is not guaranteed to reflect the true settlement value, and the guard that would catch such divergence is either unconfigured or explicitly bypassed by the disabled clamp.

### Impact Explanation
An attacker who can transiently move the Uniswap V4 pool price used by `venueUsdPrice` (e.g., a large swap or flash-loan-funded trade immediately before placing/triggering an order fill) can inflate `rawPolicyMaxOutput` far beyond the order's actual requested amount. Because the clamp is disabled, the filler will pay out the full manipulated amount to the beneficiary rather than the ceiling-limited amount, causing direct loss of solver/filler funds on every fill priced off that venue for any chain lacking (or with a stale/zero) `priceGuard.reference`. This is a genuine "loss of funds" / "transaction manipulation" primitive matching the bounty's accepted impact classes, reachable by an ordinary unprivileged actor manipulating a public AMM pool — not a relayer, prover, or admin.

### Likelihood Explanation
Likelihood depends on operational configuration: if every deployed `FXFiller` has a non-zero `priceGuard.reference` configured for every chain/pair it prices via venue, the guard mitigates gross manipulation. However, the code's own comments confirm the overfill ceiling was a previously-relied-upon defense that has since been turned into a no-op, and `checkPriceGuard` has a documented no-guard pass-through, so any pair/chain combination that is venue-priced without an explicit, well-maintained reference price is exposed. This is a realistic, plausible misconfiguration/operational gap rather than a purely theoretical one, since the guard is optional per-chain (`this.priceGuard?.get(chain)`).

### Recommendation
Re-enable the overfill ceiling as a hard clamp (`policyMaxOutput = min(rawPolicyMaxOutput, overfillCeiling)`) rather than a warning, and require a configured, actively-refreshed `priceGuard.reference` for every chain that can be venue-priced, rejecting the leg (not just logging) when no reference exists. Treat the venue quote used for accounting as untrusted input and always bound the resulting payout to the order's requested amount plus a small, fixed tolerance, independent of the live price feed.

### Proof of Concept
Conceptual PoC (parallels the perp-price report exactly):
1. Configure/observe an `FXFiller` pair that resolves via `resolveLegRates`'s venue branch (curveless pair, USD-stable `token0`), on a chain with no `priceGuard` entry (or a stale zero reference).
2. Attacker manipulates the Uniswap V4 pool for `leg.token1Address` (e.g., via a same-block large swap) so `venueUsdPrice` returns a distorted quote.
3. Attacker (or a colluding party) places/matches an intent order sized against that pair; `computeLegPolicyOutput` computes `rawPolicyMaxOutput` from the distorted rate, well above `overfillCeiling`.
4. Because the clamp at `sdk/packages/simplex/src/strategies/fx.ts:601` no longer restricts `policyMaxOutput`, the filler calls `fillOrder` and pays the inflated amount to the beneficiary, realizing an immediate loss for the filler equal to the manipulated excess.

Note: this analysis is limited to what is present in the repository's SDK/filler code; I could not verify runtime `priceGuard` configuration values actually deployed in production (those live in operator TOML configs not fully indexed here), so the exact blast radius depends on operational settings, but the code-level removal of the hard clamp is the concrete, provable local defect.

		const guard = this.priceGuard?.get(chain)

	private computeLegPolicyOutput(
		inputAmount: bigint,
		inputIsToken0: boolean,
		token0Decimals: number,
		token1Decimals: number,
		remainingToken0: Decimal,
		rate: Decimal,
	): { token0Used: Decimal; policyMaxOutput: bigint } | null {
		let legMaxToken0: Decimal
		if (inputIsToken0) {
			legMaxToken0 = new Decimal(formatUnits(inputAmount, token0Decimals))
		} else {
			legMaxToken0 = new Decimal(formatUnits(inputAmount, token1Decimals)).div(rate)
		}

		const token0ForLeg = Decimal.min(legMaxToken0, remainingToken0)
		if (token0ForLeg.lte(0)) {
			return null
		}

		let policyMaxOutput: bigint
		if (inputIsToken0) {
			// Output is token1: convert the token0 allocation at the pair rate.
			policyMaxOutput = BigInt(
				token0ForLeg.mul(rate).mul(new Decimal(10).pow(token1Decimals)).floor().toFixed(0),
			)
		} else {
			// Output is token0: pay out the token0 equivalent of the token1 input.
			policyMaxOutput = BigInt(token0ForLeg.mul(new Decimal(10).pow(token0Decimals)).floor().toFixed(0))
		}

		return { token0Used: token0ForLeg, policyMaxOutput }
	}
