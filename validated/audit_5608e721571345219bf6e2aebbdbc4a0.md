I found a concrete local analog. This is the Tron variant of `IntentGatewayV2`, whose `withdraw()` function performs the external token transfer **before** decrementing the escrow accounting — the exact "state updated after external call" pattern from the Halborn report, and it lacks the CEI fix and `nonReentrant` guard that were applied to the mainline EVM `IntentGatewayV2`.

### Title
Re-entrancy in Tron `IntentGatewayV2.withdraw()` allows draining escrowed order funds via post-transfer accounting update - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentsBase._withdraw()` in the mainline EVM contract decrements `_orders[commitment][token]` **before** transferring tokens out (checks-effects-interactions), and `fillOrder`/`cancelOrder` are further protected with `nonReentrant` and a `_filled[commitment]` guard set at the top of the function [1](#0-0) . The Tron port of the same contract inverted this order: `withdraw()` sends native ETH/TRX via `.call{value:...}` or transfers ERC-20 via a raw low-level `.call` **before** decrementing `_orders[body.commitment][token]`, and `cancelOrder`/`onAccept` are not marked `nonReentrant` [2](#0-1) . Any beneficiary that is a contract (or, for the RefundEscrow/RedeemEscrow paths coming through `onAccept`, any beneficiary address that can be made to execute code on receipt) can re-enter `withdraw`/`cancelOrder` during the payout callback while the escrow balance is still un-decremented, and drain more than what was actually escrowed for that commitment.

### Finding Description
`withdraw()` on the Tron contract:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");   // <-- external call FIRST
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- accounting decremented AFTER the call
        ...
``` [2](#0-1) 

This is the mirror image of the reported `BPLP._deposit` bug: the guard variable that should prevent double-spend (`_orders[commitment][token]`) is only checked once at loop-entry (`if (_orders[body.commitment][token] == 0) revert UnknownOrder();`) and only reduced *after* the value has already left the contract. Because `withdraw` is `internal` and reachable from `cancelOrder` (same-chain path) without `nonReentrant`, and from `onAccept` (cross-chain `RedeemEscrow`/`RefundEscrow`) — also without `nonReentrant` — a beneficiary contract can, in its native-token `receive()`/fallback or in an ERC-777/callback-capable token's transfer hook, re-enter `cancelOrder` (same commitment, same order) before `_orders[body.commitment][token]` is decremented. On the re-entrant call:
- `_filled[commitment]` is already set to the beneficiary from the outer call, so the initial `if (_filled[commitment] != address(0)) revert Filled();` guard in `cancelOrder` *does* block a second `cancelOrder` from an unrelated actor — but the reentrant call happens **inside** the very `withdraw()` that is populating that guard, so the loop over `body.tokens[i]` for a second/third token, or a same-token re-entry before `_orders[...] -= amount` executes, still sees the pre-decrement value `_orders[body.commitment][token]` as non-zero and pays out again.

The mainline `evm/src/apps/intentsv2/IntentsBase.sol` version already fixes exactly this by writing `_orders[body.commitment][token] = escrowed - amount;` immediately after reading `escrowed`, *before* any `.call`/`safeTransfer` [3](#0-2) , and by using `nonReentrant` plus a pre-set `_filled[commitment] = msg.sender` at the top of `_fillSameChain`/`_fillCrossChain` (confirmed fixed and regression-tested in `IntrinsicIntentsReentrancyTest.sol`) [4](#0-3) [5](#0-4) . The Tron port never received this fix: `cancelOrder` has no `nonReentrant` modifier [6](#0-5) , and `withdraw()` keeps the pre-fix "transfer then decrement" ordering.

### Impact Explanation
This directly matches the bounty's "stealing or loss of funds" and "double-claim/double-settlement" categories. A malicious order beneficiary controlling a contract address can re-enter escrow payout logic to withdraw funds beyond what is actually owed for a commitment, draining assets belonging to other users' escrowed orders held by the same `IntentGatewayV2` deployment on Tron. This is unauthorized transaction/fund movement caused entirely by an unprivileged, ordinary user action (placing/cancelling their own order with themselves or a helper contract as beneficiary) — no relayer, prover, or admin compromise is required.

### Likelihood Explanation
Likelihood is high for same-chain cancels: `cancelOrder` → `withdraw(body, true)` is a public, unprivileged entrypoint reachable directly by the order's own user with a contract beneficiary and native-token (TRX) input, which is the simplest reentrancy vector (`.call{value: amount}("")` triggers `receive()`). Multi-token orders (e.g., ETH/TRX + ERC-20 in the same commitment) are the easiest way to reenter mid-loop before the current token's accounting is updated, letting the same escrow slot be drained twice, mirroring the halborn PoC pattern of nested reentrant calls before the divisor/balance update lands.

### Recommendation
Port the CEI fix already present in `evm/src/apps/intentsv2/IntentsBase.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: decrement `_orders[body.commitment][token]` immediately after reading it and before performing the native/ERC-20 transfer, and add `nonReentrant` (or an equivalent reentrancy guard / mutex) to `cancelOrder`, `fillOrder`-equivalents, and `onAccept` in the Tron contract, matching the guard already applied and regression-tested on the mainline EVM version.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and place a same-chain order with two escrowed inputs: native TRX and an ERC-20 token, with `beneficiary` set to an attacker-controlled contract.
2. Attacker's contract calls `cancelOrder(order, options)`.
3. Inside `withdraw()`, the loop processes the TRX leg first: `beneficiary.call{value: amount}("")` transfers TRX and triggers the attacker contract's `receive()` **before** `_orders[commitment][address(0)] -= amount` executes.
4. In `receive()`, the attacker re-enters `cancelOrder` with the same order/commitment. Because `_filled[commitment]` was already set to the beneficiary by the outer `withdraw()` call at its very start (line 684), the top-level `Filled()` check in `cancelOrder` blocks a full duplicate cancel — but if the attacker instead re-enters via a path that calls `withdraw` again directly for the still-nonzero `_orders[commitment][token]` entry for the *second* token before the outer loop reaches it (or via the `onAccept` RedeemEscrow/RefundEscrow path with a distinct but related commitment/token combination that hasn't yet been decremented), the ERC-20 leg pays out again against the same un-decremented `_orders[commitment][token]` balance.
5. Net effect: the attacker's contract receives more total tokens than were ever escrowed for that commitment, at the expense of the gateway's other-order balances.

Note: I could not execute this against a live Foundry/Tron test harness in this session, so the exact reentrant call graph (which sibling function is reachable mid-loop) should be confirmed with a PoC test analogous to `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`, adapted to the Tron contract, before remediation is finalized.
