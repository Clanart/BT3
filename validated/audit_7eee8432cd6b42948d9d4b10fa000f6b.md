Confirmed. `MasterMagpie.withdraw(address _stakingToken, uint256 _amount)` at [1](#0-0)  is a public, unrestricted entry point that lets `msg.sender` withdraw their `available` staked balance for any registered `_stakingToken` directly — with no awareness of `AnkrBNBPoolHelper`'s `unlockTime`/`lockedAmount` restriction at all.

### Title
Ankr 1-year lock can be fully bypassed by withdrawing staked LP directly through `MasterMagpie` instead of `AnkrBNBPoolHelper` - (File: `wombat/AnkrBNBPoolHelper.sol`, `rewards/MasterMagpie.sol`)

### Summary
`AnkrBNBPoolHelper` enforces a time lock (`unlockTime`) on affected users' compensated LP positions solely inside its own `withdraw()` wrapper. The actual staked balance, however, lives in `MasterMagpie`, which exposes a fully public, permissionless `withdraw(address _stakingToken, uint256 _amount)` function that performs the unstake and token transfer with no knowledge of `lockedAmount`/`unlockTime`. Any locked user can simply call `MasterMagpie.withdraw` directly for the `stakingToken` and receive their tokens, completely skipping the helper's lock check.

### Finding Description
`AnkrBNBPoolHelper.batchDepositLPFor` records a locked amount for affected users, `lockedAmount[_for[i]] += amount`, and stakes the LP receipt token into `MasterMagpie` on their behalf via `depositFor`: [2](#0-1) .

The lock is enforced only in the helper's own `withdraw` function:
```solidity
function withdraw(uint256 _liquidity, uint256 _minAmount) external override {        
    IWombatStaking(wombatStaking).withdraw(lpToken, _liquidity, _minAmount, msg.sender);
    _unstake(_liquidity, msg.sender);
    uint256 rest = this.balance(msg.sender);
    if (unlockTime > block.timestamp && lockedAmount[msg.sender] > rest) revert NotAllowed();
    IWombatStaking(wombatStaking).burnReceiptToken(lpToken, _liquidity);
    emit NewWithdraw(msg.sender, _liquidity);
}
``` [3](#0-2) 

However, the underlying staking position is a normal pool entry in `MasterMagpie`, tracked per `(stakingToken, account)` in `userInfo`, and `MasterMagpie` exposes a completely permissionless top-level `withdraw` that any `msg.sender` can call for their own `available` balance:
```solidity
function withdraw(address _stakingToken, uint256 _amount) external whenNotPaused nonReentrant {
    _withdraw(_stakingToken, msg.sender, _amount, false);
}
``` [1](#0-0) 

`_withdraw`/`_harvestAndUnstake` only check `user.available < _amount` — there is no reference anywhere to `AnkrBNBPoolHelper.unlockTime` or `lockedAmount` [4](#0-3) . Because the locked user's position was staked with `_for = user` (not the helper contract), the user is the legitimate `msg.sender` of `userInfo[stakingToken][user]`, and can call `MasterMagpie.withdraw(stakingToken, lockedAmount)` directly to receive the raw LP receipt tokens, then redeem/withdraw them from the Wombat pool through the normal path, entirely skipping the helper's `unlockTime` check.

This mirrors the reported bug class: a lock/vesting restriction is enforced only in a wrapper function around a shared, generic staking primitive, while the primitive itself remains reachable and unaware of the restriction, allowing the restriction to be trivially bypassed by calling the underlying contract directly.

### Impact Explanation
This defeats the entire purpose of the Ankr-exploit compensation lock: users who were supposed to have their compensated LP position locked for `unlockTime` (documented as a 1-year lock) can withdraw and liquidate their full locked position immediately, at any time, by simply calling `MasterMagpie.withdraw` instead of the pool helper. This is a direct, unrestricted bypass of a fund-locking mechanism for the affected user's own locked funds, which the protocol relies on to enforce a time-based restriction — an analogous outcome to the reported vault-lock bypass.

### Likelihood Explanation
High likelihood: no special conditions, front-running, race window, or additional capital are required (unlike the Sablier PoC's need for a fresh address and 1 extra wei). Any user with a `lockedAmount` entry can simply call the already-public `MasterMagpie.withdraw(stakingToken, amount)` function directly instead of the helper, using their normal wallet.

### Recommendation
Enforce the lock at the `MasterMagpie`/staking-token level, not only in the wrapper helper — e.g., add a check in `MasterMagpie._withdraw`/`_harvestAndUnstake` (or in the staking token / pool itself) that consults `AnkrBNBPoolHelper.unlockTime` and `lockedAmount` for the relevant pool before allowing a raw withdrawal, or otherwise architect the compensation pool so the lock cannot be bypassed by interacting with `MasterMagpie` directly (e.g., use a dedicated non-transferable/non-withdrawable staking token for locked positions, similar to how `VLMGP`/`mWomSV` restrict transfers via `_beforeTokenTransfer`) [5](#0-4) .

### Proof of Concept
1. `ankrOperator` calls `AnkrBNBPoolHelper.batchDepositLPFor(lpAmount, [alice], [DENOMINATOR])`, setting `lockedAmount[alice] = lpAmount` and staking `lpAmount` of `stakingToken` into `MasterMagpie` for `alice` via `depositFor` [2](#0-1) .
2. Before `unlockTime`, Alice does NOT call `AnkrBNBPoolHelper.withdraw` (which would revert due to the `lockedAmount` check).
3. Instead, Alice calls `MasterMagpie.withdraw(stakingToken, lpAmount)` directly [1](#0-0) . This succeeds because `_harvestAndUnstake` only checks `user.available >= _amount` [6](#0-5) , with no `unlockTime`/`lockedAmount` awareness, and transfers the raw `stakingToken` (LP receipt) back to Alice.
4. Alice now holds the raw LP receipt tokens outside of any lock and can redeem them through `WombatStaking`/the Wombat pool for the underlying assets, fully bypassing the intended 1-year lock.
