## Analysis Result

### Title
Silent corruption of partial commits due to unsynchronized diff-selection vs. commit-time re-diff (TOCTOU on working-directory content) - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The Bitcoin/Dash fix addressed a class of bug where a value (chain tip / blockheight+blockhash) is captured at one point in time and used later without holding a lock, allowing concurrent mutation to produce an inconsistent or corrupted result. In GitHub Desktop, the closest analog with an unprivileged, attacker-controllable input is the partial-commit staging pipeline, where a line-based `DiffSelection` is computed against one snapshot of a file's diff (rendered in the UI) but is later applied (`isSelected(absoluteIndex)`) against a **freshly re-fetched** diff of the working directory at commit time, with no verification that the two diffs still agree on line indices/content.

### Finding Description
When a user commits partially-selected changes, the flow is:

1. UI computes a `DiffSelection` (a set of line indices) against a diff snapshot rendered earlier.
2. `_commitIncludedChanges` in `app-store.ts` captures `selectedFiles` from `state.changesState.workingDirectory.files` — a state snapshot — then performs an async `formatCommitMessage` await before calling `createCommit`: [1](#0-0) 
3. `createCommit` calls `stageFiles`, which for any partially-selected file calls `applyPatchToIndex`: [2](#0-1) 
4. `applyPatchToIndex` re-fetches the diff **at commit time** via `getWorkingDirectoryDiff(repository, file)` rather than reusing the diff the selection was computed against, then builds the patch from that fresh diff plus the stale `file.selection`: [3](#0-2) 
5. `formatPatch` blindly maps the old line-index-based `DiffSelection.isSelected(absoluteIndex)` onto the hunks/lines of this newly fetched diff, with no check that the new diff's hunk structure/line offsets match what the selection was originally created against: [4](#0-3) 

The broken invariant: the `DiffSelection`'s line indices are only valid against the exact diff hunk layout they were computed from. If the working-directory file content changes between when the user made their line selection (UI diff render) and when `applyPatchToIndex` re-diffs the file at commit time, the "same" index numbers now refer to different lines/hunks. Nothing in `formatPatch` or `stageFiles` detects or rejects this mismatch — it silently generates a patch and applies it via `git apply --cached`.

This mirrors the Bitcoin bug precisely: a value (`DiffSelection`) captured under one "chain state" (diff snapshot) is combined with a second value (fresh diff) fetched later without a consistency check, producing a corrupted composite result — here, a corrupted commit rather than a corrupted RPC response.

### Impact Explanation
An attacker who can cause changes to files in the user's working directory during the window between diff-render and commit (e.g. via a build tool, file watcher, editor auto-format-on-save, a malicious pre-commit-adjacent tool, or another process triggered by opening the repository — all things a hostile repository can configure, e.g. via `.vscode/tasks.json`, husky/lint-staged hooks, or file watchers configured in-repo) can cause Desktop to silently commit or omit different content than what the user visually selected and approved. This is a direct "silent corruption of what the user commits" scenario: the user reviews and stages hunk A intending to exclude sensitive lines, but if the file is rewritten in that window, the same line indices may now include different (possibly attacker-planted or sensitive) content in the final commit — the user never sees or approves the actual staged diff.

### Likelihood Explanation
This requires a window between the user making a partial selection and clicking "Commit," during which the working file on disk changes (not merely re-selected in UI). GitHub Desktop does not lock the working directory or re-validate selections against a fresh diff before staging, and the time-of-check-to-time-of-use gap is real (`formatCommitMessage` await plus the additional `unstageAll`/`stageFiles` git calls in `createCommit`, each an async round trip to `git`). The likelihood is moderate: it requires an external actor/process modifying the file during this narrow window, which is plausible in repositories with active build/format tooling or CI-triggered local scripts, but not trivially attacker-controlled remotely without such tooling present.

### Recommendation
Before staging partially-selected files in `applyPatchToIndex`/`stageFiles`, re-validate that the diff used to construct `file.selection` still matches the current working-directory diff (e.g., compare the diff's hash/hunk layout or the file's mtime/content hash from when selection was made) and abort/refresh the selection if it has changed, rather than silently applying line-index-based selections against a divergent diff.

### Proof of Concept
1. Open a repository in Desktop, modify a tracked file with two hunks, and partially select only certain lines in hunk 1 (unselect hunk 2) for the commit.
2. Before pressing "Commit", have an external process (e.g., a git hook trigger, IDE auto-format-on-save, or file watcher script placed in the repo, e.g. via a `package.json` `postinstall`/watch script) rewrite the file so hunk boundaries shift (e.g., insert lines above the original hunks).
3. Click "Commit" without re-opening the diff view (so the stale `DiffSelection` from step 1 is reused).
4. Observe that `applyPatchToIndex` re-diffs the file (fresh hunks) and `formatPatch` applies the old line indices to the new hunk layout, producing a commit whose actual staged content differs from what the user visually selected in the UI — confirmable by comparing `git show <new-sha>` to the file state the user intended to commit.   public async _commitIncludedChanges(
    repository: Repository,
    context: ICommitContext
  ): Promise<boolean> {
    const state = this.repositoryStateCache.get(repository)
    const files = state.changesState.workingDirectory.files
    const selectedFiles = files.filter(file => {
      return file.selection.getSelectionType() !== DiffSelectionType.None
    })

    const gitStore = this.gitStoreCache.get(repository)

    return this.withIsCommitting(repository, async () => {
      const result = await gitStore.performFailableOperation(
        async () => {
          const message = await formatCommitMessage(repository, context)
          let aborted = false
          return createCommit(repository, message, selectedFiles, {
            amend: context.amend,
            onHookProgress: this.onHookProgress(repository),
            onHookFailure: this.onHookFailure(() => (aborted = true)),
            onTerminalOutputAvailable: subscribeToCommitOutput => {
              this.repositoryStateCache.update(repository, state => ({
                ...state,
                subscribeToCommitOutput,
              }))
            },
            noVerify: state.skipCommitHooks,
            signOff: state.signOffCommits,
            allowEmpty: state.allowEmptyCommit,
          }).catch(err => (aborted ? undefined : Promise.reject(err)))
        },
        { gitContext: { kind: 'commit' }, repository }
      )

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

  // If we get into this state we should never have been called in the first
  // place. Someone gave us a faulty diff and/or faulty selection state.
  if (!patch.length) {
    log.debug(`formatPatch: empty path for ${file.path}`)
    throw new Error(`Could not generate a patch, no changes`)
  }

  patch = formatPatchHeaderForFile(file) + patch

  return patch
}
