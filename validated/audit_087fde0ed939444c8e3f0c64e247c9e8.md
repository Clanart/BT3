### Title
Online (user) session storage and lookup key exclusively on `shopify_user_id`, causing cross-shop session/token collision - (File: `lib/shopify_app/session/user_session_storage.rb`, `lib/shopify_app/session/session_repository.rb`)

### Summary
Just as the Predy report shows a shared-resource pool (Uniswap tick range) being accounted for without verifying which "pair" actually owns the liquidity, `shopify_app`'s online session storage treats `shopify_user_id` as a globally-unique key without ever scoping it to the shop the session belongs to. Any store/lookup/delete operation on a user (online) session ignores the shop portion of the session id and operates purely on the trailing user id, so a session belonging to one shop can be overwritten or returned when the same numeric user id is used for a different shop.

### Finding Description
`ShopifyApp::UserSessionStorage.store` persists (and later locates) an online session record keyed only by `shopify_user_id`: [1](#0-0) 

`retrieve_by_shopify_user_id` similarly performs `find_by(shopify_user_id: user_id)` with no shop qualifier: [2](#0-1) 

The central `SessionRepository.load_session` / `delete_session` methods, which are invoked from `LoginProtection#load_current_session` on every authenticated request, parse the incoming session id and, for non-"offline_" (i.e., online/user) ids, take only the substring after the last underscore — discarding the shop domain that prefixes the id — before doing the lookup: [3](#0-2) [4](#0-3) 

The tests confirm the id format is `"{shop}_{user_id}"` (e.g. `"test_shop.myshopify.com_1234"`, `"#{shop}_#{user_id}"`), and that only the `user_id` fragment is ever used for storage/retrieval/deletion: [5](#0-4) [6](#0-5) 

Because the DB row is found/initialized by `shopify_user_id` alone (`find_or_initialize_by(shopify_user_id: user.id)`), if the same numeric associated-user id is ever presented in the context of two different shops (e.g., an agency/Plus staff account that has access to multiple stores where Shopify happens to assign the same collaborator id, or any app-level or storage misconfiguration that causes id reuse across shops), storing a session for shop B **overwrites** the `shopify_domain` and `shopify_token` columns of the record that was previously storing shop A's session — exactly the "shared pool without per-owner accounting" pattern described in the Predy report, just applied to a session-token table instead of a Uniswap position.

### Impact Explanation
When the row is overwritten, a subsequent valid, cryptographically-verified request for shop A (whose session id resolves to `"shopA.myshopify.com_<user_id>"`) is reduced by `load_session` to just `<user_id>`, and `retrieve_by_shopify_user_id` returns the row now holding shop B's `shopify_domain`/`shopify_token`. `ShopifyAPI::Context.activate_session(current_shopify_session)` in `activate_shopify_session` then makes authenticated Admin API calls using shop B's access token while the app/controller logic still believes it is acting for shop A's request context: [7](#0-6) 

The only guard rails, `session_id_conflicts_with_params` / `session_shop_conflicts_with_params`, compare the retrieved session against the `params[:shop]` query string, not against the shop encoded in the verified JWT/id-token, so this mismatch is not detected for typical embedded, JWT-driven requests: [8](#0-7) 

This is a cross-shop session/token theft: shop A's stored access token is silently replaced and API operations for shop A can be executed with shop B's credentials (or vice versa), corrupting the token accounting the same way the Predy pair's liquidity accounting was corrupted by an unscoped shared key.

### Likelihood Explanation
This does not require a privileged "trusted operator" action, unlike the Predy PoC — it is triggered by ordinary, unprivileged app usage: any legitimate install/login flow for two different shops that happens to produce identical `associated_user.id` values (the same staff account added to multiple stores, e.g. in a Shopify Plus organization or via an app-provisioning workflow that reuses ids) is sufficient. Because the storage contract documented in `docs/shopify_app/sessions.md` explicitly requires only `store(auth_session, user)` / `retrieve_by_shopify_user_id(user_id)` / `destroy_by_shopify_user_id(user_id)` — with no shop parameter — this is the sanctioned, gem-provided default behavior, not a misuse by app developers: [9](#0-8) 

### Recommendation
Scope online-session storage, retrieval, and deletion by the `(shopify_domain, shopify_user_id)` pair instead of `shopify_user_id` alone: change `find_or_initialize_by`/`find_by` in `UserSessionStorage` (and `UserSessionStorageWithScopes`) to include the shop domain, and change `SessionRepository#load_session`/`#delete_session` to pass and use the shop portion of the session id (not just the trailing user-id fragment) when resolving online sessions, mirroring how offline sessions are already correctly scoped by `shopify_domain`.

### Proof of Concept
1. Configure `ShopifyApp::SessionRepository.user_storage = User` (default `UserSessionStorage` concern).
2. User with `associated_user.id = 42` installs the app on `shop-a.myshopify.com`; `store(auth_session_a, user)` creates a `User` row: `shopify_user_id=42, shopify_domain=shop-a.myshopify.com, shopify_token=token_a` (`lib/shopify_app/session/user_session_storage.rb:13-17`).
3. The same `associated_user.id = 42` later authenticates on `shop-b.myshopify.com` (e.g., an agency staff account added to a second store); `store(auth_session_b, user)` finds the *same* row via `find_or_initialize_by(shopify_user_id: 42)` and overwrites it to `shopify_domain=shop-b.myshopify.com, shopify_token=token_b`.
4. A subsequent legitimate, signed request for `shop-a.myshopify.com` produces session id `"shop-a.myshopify.com_42"`; `SessionRepository.load_session` strips it to `"42"` and calls `retrieve_user_session_by_shopify_user_id("42")`, returning the row now containing shop B's domain and token (`lib/shopify_app/session/session_repository.rb:67-78`).
5. `activate_shopify_session` activates this session and issues Admin API calls using `token_b` against `shop-b.myshopify.com`'s data even though the request was authenticated for shop A, and shop A's stored token is now unrecoverable/lost — directly analogous to the Predy pair losing its Uniswap liquidity to another pair sharing the same unscoped range key.

      def load_session(id)
        match = id.match(/^offline_(.*)/)
        if match
          domain = match[1]
          ShopifyApp::Logger.debug("Loading session by domain - domain: #{domain}")
          retrieve_shop_session_by_shopify_domain(domain)
        else
          user = id.split("_").last
          ShopifyApp::Logger.debug("Loading session by user_id - user: #{user}")
          retrieve_user_session_by_shopify_user_id(user)
        end
      end

      # ShopifyAPI::Auth::SessionStorage override
      def delete_session(id)
        match = id.match(/^offline_(.*)/)

        if match
          domain = match[1]
          ShopifyApp::Logger.debug("Destroying session by domain - domain: #{domain}")
          destroy_shop_session_by_domain(domain)

        else
          shopify_user_id = id.split("_").last
          ShopifyApp::Logger.debug("Destroying session by user - user_id: #{shopify_user_id}")
          destroy_user_session_by_shopify_user_id(shopify_user_id)
        end

        true
      end

    def activate_shopify_session
      if current_shopify_session.blank?
        signal_access_token_required
        ShopifyApp::Logger.debug("No session found, redirecting to login")
        return redirect_to_login
      end

      if ShopifyApp.configuration.check_session_expiry_date && current_shopify_session.expired?
        ShopifyApp::Logger.debug("Session expired, redirecting to login")
        clear_shopify_session
        return redirect_to_login
      end

      if ShopifyApp.configuration.reauth_on_access_scope_changes &&
          !ShopifyApp.configuration.user_access_scopes_strategy.covers_scopes?(current_shopify_session)
        clear_shopify_session
        return redirect_to_login
      end

      begin
        ShopifyApp::Logger.debug("Activating Shopify session")
        ShopifyAPI::Context.activate_session(current_shopify_session)
        yield
      ensure
        ShopifyApp::Logger.debug("Deactivating session")
        ShopifyAPI::Context.deactivate_session
      end
    end
