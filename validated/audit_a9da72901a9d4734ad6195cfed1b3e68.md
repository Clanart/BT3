Based on my research, I found a concrete division-by-zero condition in the consensus-liquidity reward-splitting logic that is structurally analogous to the dYdX bug: a ratio/split calculation that silently assumes a non-zero denominator, and can be driven to zero through ordinary, permissionless actions (staking/unstaking), causing reward-distribution logic to break for legitimate participants — in this case crashing block finalization rather than merely zeroing a payout.

### Title
Division-by-zero panic in consensus-liquidity reward split when proposer's CN and CL stake are both zero - (File: kaiax/staking/staking_info.go)

### Summary
`consolidatedNode.Split()` divides an amount between the CN (staking-only) contract and the CL (consensus liquidity) pool using `totalAmount = cnAmountBig + clAmountBig` as the denominator. This function is invoked unconditionally for the block proposer in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` without first verifying that the proposer's combined stake exceeds any minimum threshold, unlike the staker-reward allocation paths which only call `Split` after confirming `cnTotalStakingAmount > minStake`.

### Finding Description
`consolidatedNode.Split` is defined as: [1](#0-0) 

When `c.CLStakingInfo != nil` but both `c.StakingAmount` (CN stake) and `c.CLStakingInfo.CLStakingAmount` (CL stake) are `0`, `totalAmount` becomes `0`, and `big.Int.Div` panics on division by zero.

This function is called for the proposer's reward allocation with no minimum-stake guard: [2](#0-1) [3](#0-2) 

Contrast this with the staker-reward allocation path, which only calls `Split` after confirming the combined stake exceeds `minStake`, guaranteeing `totalAmount > 0`: [4](#0-3) 

The `StakingAmount` for a CN is sourced directly from the AddressBook/CNStaking contract balance (rounded to whole KAIA) and can legitimately reach `0` if a validator fully withdraws its CN stake while its NodeId/RewardAddr entries remain registered in AddressBook: [5](#0-4) 

Similarly, `CLStakingAmount` is read from the CLRegistry/CL pool balance and can independently drop to `0` when depositors fully withdraw from the CL pool while the pool/node mapping remains registered: [6](#0-5) 

Since `ConsolidatedNodes()` merges CN and CL entries purely by matching `RewardAddr`/`CLNodeId` (with no stake-amount validation), a proposer whose combined CN+CL stake has fallen to zero — while still being selected to propose per whatever committee-selection rule is active — will trigger the unguarded `Split()` call during `FinalizeState`.

### Impact Explanation
This mirrors the dYdX root cause pattern: an unvalidated ratio/split denominator that can silently become zero through normal operational state (there, an uninitialized/misconfigured ratio; here, fully-withdrawn stake), breaking reward accounting. Here the consequence is worse than a silent zero-payout: it is a deterministic panic in `FinalizeState`, which every honest node executes identically while processing the same block, resulting in a full chain halt (all nodes crash processing the block) rather than mere fund loss. This is reachable purely through the staking/withdrawal path available to any validator or staker, without any privileged or malicious-node action.

### Likelihood Explanation
Reaching this requires a validator/CN whose reward address is due to propose a block to have both zero CN stake and zero CL stake simultaneously while still retaining CLRegistry/AddressBook entries. Whether the validator-set/proposer-selection logic filters out zero-stake nodes before they can become proposer is a key mitigating factor not fully confirmed here; if such filtering exists elsewhere in valset code, likelihood is lower. If proposer eligibility only depends on committee membership (not immediate re-verified live stake at reward time), a validator could withdraw all CN and CL stake in the same staking-interval window that it is still elected proposer, triggering the panic deterministically.

### Recommendation
Add an explicit zero-check in `consolidatedNode.Split()` (return `(amount, big.NewInt(0))` when `totalAmount.Sign() == 0`), or guard the proposer-reward paths (`specWithProposerAndFunds`/`specWithProposerAndFundsFlex`) with the same minimum-stake validation already applied to `assignStakingRewards`/`assignStakingRewardsFlex` before invoking `cn.Split`.

### Proof of Concept
1. A validator registers a CN in AddressBook and a corresponding CL pool in CLRegistry, both initially non-zero.
2. The validator (or CL depositors) fully withdraws both the CN staking-only contract balance and the CL pool balance, so `StakingAmount == 0` and `CLStakingInfo.CLStakingAmount == 0`, while both entries remain registered (not removed from AddressBook/CLRegistry).
3. This validator's `RewardAddr` is selected as `config.Rewardbase` (proposer) for a block.
4. During `FinalizeState`, `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` locates the matching consolidated node and calls `cn.Split(proposer)` unconditionally (`kaiax/reward/impl/getter.go:583`/`633`), where `totalAmount = 0 + 0 = 0`, causing `big.Int.Div` to panic and crash block finalization on every node processing the block.

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
