### Title
Automatic remote-URL rewrite from GitHub API `clone_url` can silently repoint a user's git remote when the cached comparison state is stale - (`File: app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` in `app/src/lib/stores/updates/update-remote-url.ts` automatically rewrites a repository's git remote URL, without any user confirmation, whenever GitHub's API-reported `clone_url` for the associated `GitHubRepository` no longer matches the local remote, provided a set of heuristic guard conditions pass. This mirrors the Euler bug-class shape: an accumulated, trusted piece of local state (the git remote configuration the user intentionally set) can be silently overwritten as a side effect of an external, attacker-influenced input (a GitHub API repository object) being refreshed, with no persisted record of "why" or opportunity for the user to notice before the next push/fetch operation uses the new value.

### Finding Description
`updateRemoteUrl()`: [1](#0-0) 

The function performs the following checks before silently calling `gitStore.setRemoteURL(...)`:
1. `protocolsMatch` – old and new URL protocols must match. [2](#0-1) 
2. `remoteUrlUnchanged` – the *current* local remote must still match the *previously cached* `gitHubRepository.cloneURL` via `urlMatchesRemote`, i.e. it assumes the user never manually changed the remote since Desktop last saw it. [3](#0-2) 
3. `!urlsMatch` – the new API-reported clone URL differs from the current remote (e.g., owner/name changed).

If all three hold, Desktop calls `gitStore.setRemoteURL()`, which invokes the underlying git `remote set-url` command and re-loads remotes: [4](#0-3) 

The `urlMatchesRemote` comparison used both for `remoteUrlUnchanged` and `urlsMatch` only checks hostname/owner/name case-insensitively — it does not verify anything about how the previous "cached" `GitHubRepository` object was originally established, nor does it re-validate that the *account/endpoint* tied to that cached `GitHubRepository` is still the account performing the fetch: [5](#0-4) 

The corrupted value is the git remote URL entry in `.git/config` — a value the user explicitly configured (e.g. `origin`) that Desktop overwrites automatically as a "convenience" sync whenever the GitHub API object it is tracking reports a different `clone_url` (e.g., because the upstream repository was renamed, transferred, or because the cached `GitHubRepository` row in Desktop's database was associated with the wrong API object). Because `IAPIFullRepository.clone_url` is attacker-influenceable data returned by the GitHub API for a repository the user has added to Desktop (forks, renamed repos, repos an attacker controls and can rename/transfer), this write happens without a diff prompt, confirmation dialog, or any indication to the user that their remote changed. The `GitStore.setRemoteURL` guard performs no revalidation of the target host being “still github.com” trust boundary beyond the loose `urlMatchesRemote` hostname compare, which is satisfied trivially by any GitHub-hosted rename.

### Impact Explanation
Like the Euler case — where an accumulated/trusted value (`interestAccumulator`) is silently reset by a routine administrative action (`setInterestRateModel`) without any signal that data was lost — here a trusted, user-set value (the git remote URL) is silently mutated by a routine background action (API repository refresh) triggered by data the attacker can influence (repository rename/transfer via the GitHub API, or fork chains). The user has no confirmation step; the next `git push`/`git fetch`/`git pull` silently operates against the new remote endpoint. This does not require the local machine to be compromised, no admin rights, and no unnatural user interaction — it happens automatically as part of Desktop's normal repository refresh cycle for any tracked repo whose upstream API metadata changes.

### Likelihood Explanation
Medium. `updateRemoteUrl` is gated by a same-hostname check, so this is not an arbitrary drive-by exfiltration to an attacker's own server (both old and new `clone_url` values must be same hostname, e.g. `github.com`), which caps severity below full RCE/exfil-to-arbitrary-host. It is exploitable specifically in narrower scenarios such as repository owner-name races, transfer/rename sequences, or a forked-network trust confusion where the cached `GitHubRepository` object ends up representing a different repository than the one the user believes they are tracking, causing subsequent commits to be silently pushed to the wrong (still github.com-hosted, but attacker-controlled) repository/owner. This is a narrower, same-host variant of the general "silently corrupt what the user pushes" impact category.

### Recommendation
- Require explicit user confirmation before silently rewriting a configured git remote URL as a side effect of a GitHub API metadata refresh, mirroring the manual flow already present in `RepositorySettings` (`onSubmit`) where remote URL changes are explicit user actions: [6](#0-5) 
- Persist and display an audit trail / notification whenever `updateRemoteUrl` performs an automatic rewrite, so users can detect unexpected remote changes.
- Tighten `urlMatchesRemote`/`remoteUrlUnchanged` heuristics to also validate the `GitHubRepository`'s owning `Account`/`dbID` lineage, not just hostname/owner/name string equality, to reduce trust-confusion between distinct API objects that happen to normalize to the same string shape.

### Proof of Concept
Not independently verified end-to-end (would require reproducing an actual GitHub-side rename/transfer sequence plus Desktop's background refresh timing), but the code path is directly traceable:
1. User adds Desktop tracking for a repository `owner/repo` on `github.com`; Desktop stores `GitHubRepository.cloneURL = https://github.com/owner/repo`.
2. Attacker (owner of `owner/repo`, or via a repo-transfer/rename they control) changes the repository name/owner on GitHub; the GitHub API now reports a different `clone_url` for the same underlying repository object Desktop is tracking.
3. On Desktop's routine repository refresh, `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)` is invoked with the updated `apiRepo.clone_url`. [7](#0-6) 
4. Because the local remote still matches the previously cached `cloneURL` (`remoteUrlUnchanged === true`), protocols match, and `urlsMatch === false`, Desktop silently calls `gitStore.setRemoteURL(...)`, executing `git remote set-url origin <new-url>` with no user prompt. [8](#0-7) 
5. The existing unit tests confirm this automatic-rewrite behavior is intentional and exercised: [9](#0-8)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
