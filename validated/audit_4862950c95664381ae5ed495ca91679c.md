### Title
Unauthenticated attacker-controlled prevout data proxied into the Taproot sighash — forged `ReceivedOutput` values cause the threshold group to sign invalid/unintended transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The marimo flaw was an endpoint that proxied unauthenticated, attacker-chosen inputs into an internal trust boundary. The analog in Serai is `SignableTransaction`, which takes `ReceivedOutput`s — constructible by an unprivileged party from raw bytes via `ReceivedOutput::read` — and forwards their attacker-controlled fields (`output.value`, `outpoint`) unauthenticated into the BIP-341 sighash that the FROST multisig signs. The only consistency check in `SignableTransaction::multisig` is on `script_pubkey`; the prevout amount and outpoint are never validated against chain state before being committed into `Prevouts::All`.

### Finding Description
`ReceivedOutput::read` deserializes `offset`, `TxOut` (including `value`), and `OutPoint` directly from untrusted bytes with no authentication or binding to a real UTXO (`networks/bitcoin/src/wallet/mod.rs:122-134`). A forged `ReceivedOutput` can therefore carry an arbitrary claimed amount and outpoint while keeping the correct `script_pubkey`.

`SignableTransaction::multisig` verifies only that `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` (`send.rs:277`). The prevout `value` is never checked. That value is used twice:

1. In `SignableTransaction::new`, `input_sat` (sum of claimed values) gates the `NotEnoughFunds` check and determines change/fee (`send.rs:175`, `215-235`).
2. In `TransactionSignMachine::sign`, all claimed `prevouts` are committed via `Prevouts::All` into `taproot_key_spend_signature_hash` for every input (`send.rs:373-390`).

Because BIP-341 commits to every prevout's amount, a single forged amount poisons the sighash for all inputs — the attacker acts as an unauthenticated "proxy" injecting arbitrary data into the message the threshold group signs, exactly the "unauthenticated reach into an internal function" shape of the marimo bug.

### Impact Explanation
- The group produces a transaction whose signatures commit to fabricated prevout amounts/outpoints; no honest validator will accept it. Every spending plan that includes the forged input is dead — multisig funds are rendered unspendable through that signed transaction even though a valid `Transaction` object (signatures attached) is returned by `complete` (`send.rs:413-428`). This is "concrete signing of an unintended message": the group signs a sighash committing to amounts that do not exist on chain.
- Inflating `value` inflates `input_sat`, so `NotEnoughFunds` is bypassed and a transaction is constructed and signed that pays out more than the real inputs contain — it is signed, yet permanently invalid.
- Since `TransactionMachine` cannot cache preprocesses and each attempt consumes fresh FROST nonces/preprocesses (`send.rs:290-318`), repeated injection forces repeated full signing rounds that yield only invalid transactions: a sustained denial of spendability for the multisig.

### Likelihood Explanation
Any party able to supply serialized `ReceivedOutput` bytes into the transaction-construction path (the explicitly reachable `ReceivedOutput::read` boundary) can set the amount and outpoint arbitrarily — no key material, collusion, or validator access is required. The code performs zero verification of these fields: only the `script_pubkey` is bound to the offset key (`send.rs:277`).

### Recommendation
Bind each `ReceivedOutput` to authenticated chain data before use: verify `output.value` and `outpoint` against the confirmed UTXO set (or the scanner output which observed it) inside `SignableTransaction::new`/`multisig`, not just `script_pubkey`. Alternatively, carry the amount/outpoint only from authenticated scanner state and reject deserialized `ReceivedOutput`s whose fields were not produced by `Scanner::scan_transaction`/`scan_block` on a block the caller trusts.

### Proof of Concept
```rust
// Attacker crafts a ReceivedOutput for a real multisig UTXO
// but with a forged value (e.g., 1 BTC instead of 0.001 BTC).
let mut forged_bytes = Vec::new();
forged_bytes.extend(Scalar::ZERO.to_bytes());          // offset (main key)
// TxOut: script_pubkey = the multisig's real P2TR script (passes the
// multisig() check), value = 100_000_000 (forged, 1 BTC)
forged_bytes.extend(serialize(&TxOut {
    value: Amount::from_sat(100_000_000),
    script_pubkey: real_multisig_script.clone(),       // correct script
}));
forged_bytes.extend(serialize(&OutPoint::new(real_txid, 0)));
let forged = ReceivedOutput::read(&mut forged_bytes.as_slice()).unwrap();

// SignableTransaction::new accepts it: input_sat is inflated,
// NotEnoughFunds passes even though real funds are insufficient.
let stx = SignableTransaction::new(
    vec![forged], &payments, change, None, fee_rate
).unwrap();

// multisig() only checks script_pubkey -> Some(...)
let machine = stx.multisig(&keys).unwrap();
// ... FROST signing produces a fully-signed Transaction committing to
// prevout amount 1 BTC. The tx is permanently invalid on-chain and any
// co-signed honest inputs in the same Prevouts::All sighash are burned
// into the same invalid transaction.
```
