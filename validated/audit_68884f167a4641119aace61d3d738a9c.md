### Title
Half-aggregation weights do not observe nonces/keys, enabling aggregate signature forgery - (File: crypto/schnorr/src/aggregate.rs)

### Summary
In `SchnorrAggregate::verify` (and matching `SchnorrAggregator::aggregate`/`complete`), the per-signature weight `z_i` is derived from a transcript that observes only the caller-supplied challenges — never the nonces `Rs[i]` nor the public keys being verified. This mirrors the SP1/Plonky3 flaw where evaluation claims were not observed before sampling the random linear combination coefficient: here, the Fiat-Shamir weight does not bind the values it is meant to randomize. An attacker who submits a `SchnorrAggregate` (parsed via `SchnorrAggregate::read`, canonical-checked but otherwise attacker-controlled) can forge an aggregate signature over public keys they do not control.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `verify` builds the digest as: [1](#0-0) 

Only `challenge` values are appended via `digest.append_message(b"challenge", ...)` at line 135; neither `self.Rs[i]` nor `key` is ever appended. The aggregator side is symmetric: `aggregate` appends only the challenge (line 170), so honest aggregations still verify, but the transcript never binds `R` or the key.

Verification checks `Σ z_i·R_i + Σ z_i·c_i·A_i − s·G == 0`. Because `z_i` is computable by the attacker before choosing `R_i` (it depends only on the challenges, which are fixed verifier inputs), the attacker performs a rogue-key-style attack per index:

- Choose arbitrary scalars `x_i`.
- Set `R_i = x_i·G − c_i·A_i` (each `R_i` is a valid, canonical, non-identity group element; `C::read_G` accepts it).
- Set `s = Σ z_i·x_i`.

Then `z_i·R_i + z_i·c_i·A_i = z_i·x_i·G`, and the multiexp sums to `Σ z_i x_i G − s G = 0`. Verification passes for keys `A_i` whose discrete logs the attacker does not know.

Had `z_i` bound `R_i` (as required by the half-aggregation construction in eprint 2021/350 cited in the code), `R_i` could not be chosen adaptively after the weight is known, and this forgery is blocked.

### Impact Explanation
Any verifier relying on `SchnorrAggregate::verify` accepts a forged aggregate signature attesting that a set of public keys each signed their respective challenge/message. This is a direct signature forgery primitive: funds or protocol actions gated on aggregated threshold/delegated signatures can be authorized without any signer participating. Severity: High (forgeability with only public data and attacker-chosen bytes; no secret leakage or protocol misuse required — the documented-MUST caveats in the API concern challenge construction, which this attack does not rely on).

### Likelihood Explanation
Fully deterministic forgery, requiring only knowledge of the public keys and the challenges the verifier will use (both are public/verifier-supplied inputs). The attacker controls `Rs` and `s` via `SchnorrAggregate::read`/`serialize`. The only prerequisite is a deployment that verifies aggregated Schnorr signatures — exactly the feature this module exists for — so likelihood is high wherever the `aggregate` feature is enabled.

### Recommendation
Bind each `R_i` and each public key (and ideally the index) into the weight transcript before drawing `z_i`. In both `SchnorrAggregate::verify` and `SchnorrAggregator::aggregate`/`complete`, append `R` and the public key to the digest alongside the challenge, e.g. `digest.append_message(b"nonce", R.to_bytes()); digest.append_message(b"key", key.to_bytes());` before sampling the weight, so `z_i` cannot be predicted before `R_i` is fixed. Prover and verifier must apply the identical ordering.

### Proof of Concept
```
// Verifier will call:
//   aggregate.verify(dst, &[(A_0, c_0), (A_1, c_1), ...])
// Attacker (knowing only A_i, c_i, dst):
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for (_, c) in keys_and_challenges { digest.append_message(b"challenge", c.to_repr()); }

let mut Rs = vec![]; let mut s = C::F::ZERO;
for (i, (A_i, c_i)) in keys_and_challenges.iter().enumerate() {
    let z_i = weight::<_, C::F>(&mut digest);      // predictable: ignores R_i, A_i
    let x_i = C::random_nonzero_F(&mut OsRng);
    Rs.push(C::generator() * x_i - *c_i * *A_i);   // R_i + c_i A_i = x_i G
    s += z_i * x_i;
}
let forgery = SchnorrAggregate::<C> { Rs, s };
assert!(forgery.verify(dst, keys_and_challenges)); // passes
```
