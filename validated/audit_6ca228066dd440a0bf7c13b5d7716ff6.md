## Analysis

The Solidity finding is a **boundary-condition bug in a security check**: a strict inequality (`>` used where `>=` was required) makes the guard silently accept a value it was meant to reject (`block.timestamp == order.expiry`). The Desktop analog with the same class of bug — a boundary comparison in a security-relevant equality/containment check that admits values it should reject — is the "is this path inside the sandbox root" test in `resolveWithin`.

### The broken invariant

`_resolveWithin()` is supposed to guarantee "the resolved path is at, or **strictly beneath**, `rootPath`." It computes the real (symlink-resolved) paths and then does: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` is a pure prefix test with **no path-separator boundary check**, exactly analogous to the Solidity bug's `>` vs `>=` mistake: the intended boundary ("must be a child of `realRoot`") is checked with an operator that also matches an unintended adjacent case ("shares `realRoot`'s characters as a string prefix, but isn't actually inside it"). If `realRoot` is `/Users/victim/Documents/GitHub/repo` and a symlink resolves to `/Users/victim/Documents/GitHub/repo-secrets/id_rsa`, `startsWith` returns `true` even though `repo-secrets` is a sibling directory, not a subdirectory of `repo`. The missing check is `realResolved === realRoot || realResolved.startsWith(realRoot + sep)`.

### Where this is exploited by attacker-controlled repo content

`resolveWithin` is the sole traversal/symlink guard used in `buildConflictContext`, which reads the contents of conflicted files straight off disk to feed into the Copilot merge-conflict resolver: [2](#0-1) 

The comment states the explicit intent: *"Guard against path traversal and symlink escapes (cross-platform)."* An attacker who gets a victim to clone/fetch a malicious repository can commit a symlink at a repo-relative path (e.g. `notes.txt` → `../repo-secrets/ssh_key`) that, when a merge/rebase conflict is later triggered on that path, causes `buildConflictContext` to `readFile` and ship the sibling directory's contents (which can include `.ssh` keys, other repos, credential files, etc., if such a directory happens to be adjacent with a name sharing `repo`'s prefix) into the Copilot prompt sent off-machine — an exfiltration primitive that the existing guard was specifically designed, but fails, to stop.

### Why existing guards don't stop it

- Null-byte and syntactic `..`-traversal are already normalized/blocked earlier in `_resolveWithin` [3](#0-2) , so the only remaining defense against symlink escapes is the final `startsWith` check, which is where the boundary bug lives.
- The existing unit tests only cover symlinks that traverse *out and back into* the same root, or fully outside with an unrelated path, never the adjacent-directory-with-shared-prefix case, so the gap is untested. [4](#0-3) 

### Title
Prefix-only containment check in `resolveWithin()` lets a symlink escape into a sibling directory - (File: app/src/lib/path.ts)

### Summary
`resolveWithin()`'s final containment check uses `realResolved.startsWith(realRoot)` with no path-separator boundary, so a real path in a sibling directory whose name shares `realRoot` as a string prefix is incorrectly treated as being inside the root.

### Finding Description
`_resolveWithin` correctly rejects `..`-only escapes and null bytes, but its final safety check is a bare string-prefix test [1](#0-0) . This mirrors the sherlock report's bug class: a comparison operator (`startsWith`, analogous to `>`/`<`) is used at a boundary where an exact/adjacency check is required (analogous to `>=`/`<=`), letting an unintended value pass the guard.

### Impact Explanation
`buildConflictContext` relies exclusively on `resolveWithin` to keep conflicted-file reads inside the repository working directory before sending content to the Copilot conflict-resolution model [2](#0-1) . A malicious repository containing a symlink whose resolved target lands in a same-prefixed sibling directory can cause disclosure of file contents outside the repository (credentials, keys, other projects) to an external LLM service, satisfying the "read outside the repo" / "credential exfiltration" impact bar.

### Likelihood Explanation
Exploitation requires the attacker-controlled repo to contain a symlink and requires a sibling directory on the victim's machine whose name shares a prefix with the repository's directory name (e.g., cloning into `GitHub/repo` while `GitHub/repo-secrets` or `GitHub/repository` exists) — a naming coincidence that is plausible for common clone folder layouts (Desktop's own default clone path convention often creates such name families) but not guaranteed, so likelihood is moderate rather than universal.

### Recommendation
Change the final check to also require a path-separator boundary or exact equality:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```

### Proof of Concept
1. Victim clones attacker's repo into `/Users/victim/Documents/GitHub/repo`, and `/Users/victim/Documents/GitHub/repo-secrets/id_rsa` happens to exist (or attacker structures their repo suggestion/README to encourage cloning into a folder like `repo` next to an existing `repo-secrets`/`repository` directory).
2. Attacker's repo includes a tracked symlink `conflict-file.txt -> ../repo-secrets/id_rsa`.
3. Victim performs a merge/rebase that conflicts on `conflict-file.txt`.
4. `buildConflictContext` calls `resolveWithin('/Users/victim/Documents/GitHub/repo', 'conflict-file.txt')`; `realpath` resolves the symlink to `/Users/victim/Documents/GitHub/repo-secrets/id_rsa`, and `startsWith('/Users/victim/Documents/GitHub/repo')` returns `true`, so the function returns this path as "safe".
5. The file is read and its content is embedded into the Copilot prompt, exfiltrating it. [5](#0-4)
