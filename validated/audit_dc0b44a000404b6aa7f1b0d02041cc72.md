### Title
Missing-participant panic in `GeneratorPromotion::complete` allows a DKG peer to crash the node via a malformed proof map - (File: crypto/dkg/promote/src/lib.rs)

### Summary
The kernel bug class behind CVE-2016-2543 is "operation proceeds on an object that was never assigned/validated, causing a NULL dereference." The same shape exists in `GeneratorPromotion::complete`: it validates only the *quantity* and *upper bound* of the supplied `proofs` map, then unconditionally indexes it for every expected participant. A proof map that is missing a required participant — while compensating with an out-of-place entry such as the caller's own index — passes both checks and hits `proofs.get(&i).unwrap()` on `None`, panicking the process.

### Finding Description
`complete` performs exactly two validations on the peer-supplied `proofs` map:

```rust
// crypto/dkg/promote/src/lib.rs:125-136
if proofs.len() != (usize::from(params.n()) - 1) {
  Err(PromotionError::IncorrectAmountOfParticipants { ... })?;
}
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() {
    Err(PromotionError::InvalidParticipant { ... })?;
  }
}
```

Neither check enforces that the map's keys form exactly the set `{1..=n} \ {params.i()}`. A map containing a duplicate semantic entry — most simply, the caller's own participant index `params.i()` — in place of a missing legitimate participant still satisfies `len() == n - 1` and `key <= n`. The subsequent loop then dereferences a missing entry:

```rust
// crypto/dkg/promote/src/lib.rs:140-146
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() {
    continue;
  }
  let proof = proofs.get(&i).unwrap();   // panic on None
```

Compare with `validate_map` in `crypto/frost/src/lib.rs:50-72`, which correctly rejects both missing and duplicated participants, and with `ThresholdKeys::view` (`crypto/dkg/src/lib.rs:474-485`), which rejects duplicates and non-participation. `complete` reimplements this membership check incompletely.

### Impact Explanation
A single peer in a generator-promotion round can abort the entire operation and crash the calling process (or, if the panic is caught per-message, force repeated failures of the promotion protocol). This is a remote, input-triggered denial of service — the direct analog of the CVE's "crafted ioctl → OOPS." The panic occurs before any proof is verified, so no valid participation is required beyond delivering a `GeneratorProof`-shaped message keyed under the wrong `Participant`.

### Likelihood Explanation
The `proofs` map is assembled by the integrator from per-participant `GeneratorProof` messages read with `GeneratorProof::read` — a deserialization API that parses only `share` and `dleq` bytes and performs no participant-set validation. Any participant that sends a proof addressed as (or misfiled under) an index already covered — trivially, the victim's own index — while withholding a proof for another participant produces a map of size `n - 1` with a hole at the expected index. The panic is deterministic once the loop reaches the missing index.

### Recommendation
Replace the length/upper-bound checks with a strict membership check, mirroring `validate_map`: verify `proofs` does not contain `params.i()`, and that every `i` in `1..=params.n()` (excluding `self`) is present, e.g.:

```rust
let proof = proofs.get(&i).ok_or(PromotionError::MissingProof(i))?;
```

and reject `proofs.contains_key(&params.i())`. Alternatively, reuse `frost::validate_map`-style logic keyed on the expected participant set.

### Proof of Concept
Conceptual, for `n = 3`, local participant `i = 1`:

1. Victim calls `GeneratorPromotion::<C1, C2>::promote(rng, base_keys)` producing its own proof.
2. Attacker (participant 2) delivers a `proofs` map serialized/inserted as `{1: proof_a, 2: proof_b}` — i.e., it includes an entry under the victim's own index `1` (a duplicate) and omits participant `3` entirely. The `GeneratorProof` bytes for entries `1` and `2` can be well-formed (`GeneratorProof::read` succeeds).
3. `complete` checks: `proofs.len() == 2 == n - 1` passes; all keys (`1`, `2`) satisfy `<= n` — passes.
4. Loop: `i = 1` skipped (self); `i = 2` resolves and verifies; `i = 3` → `proofs.get(&Participant(3))` returns `None` → `.unwrap()` panics.

Result: unhandled panic originating purely from attacker-controlled key selection in the proof map, with no signature/proof forgery required.
