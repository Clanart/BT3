## Title
Arbitrary-Sender Fund Transfer in Bank Precompile `send()` Gated Only by Caller Identity, Not Owner Consent - (File: `precompiles/bank/bank.go`)

### Summary
The Bank precompile's `send` function (and all its legacy versions) mirrors the `addGasFee` bug class from the report: it moves native-denom funds out of an arbitrary account (`args[0]`) supplied entirely by the calling contract, with **no allowance/approval check** performed inside the precompile itself. The only safeguard is that the immediate EVM `caller` must equal whichever contract address is currently registered as the "ERC20 native pointer" for that denom.

### Finding Description
`PrecompileExecutor.send` in `precompiles/bank/bank.go` decodes a sender address, receiver address, denom, and amount purely from calldata (`args[0]`/`args[1]`), then unconditionally executes a `bankMsgServer.Send`/`bankKeeper.SendCoins` moving funds from `senderSeiAddr` to `receiverSeiAddr`: [1](#0-0) 

The *only* access-control check is: [2](#0-1) 

i.e. it verifies that the immediate `caller` (the contract that directly invoked the precompile) equals `pointer`, the contract address currently registered via `GetERC20NativePointer` for `denom`. It never verifies that `senderSeiAddr` (the account whose funds are being moved) actually authorized this specific transfer — that responsibility is delegated entirely to whatever contract is registered as the "pointer".

This is structurally identical to `addGasFee`: a caller supplies an arbitrary "owner"/"sender" address for a value-moving operation, and the function trusts it based on a caller-identity check rather than verifying the owner's actual consent (allowance) for that specific transfer.

The intended safe design relies on the registered pointer being the honest `NativeSeiTokensERC20` wrapper, whose `_update` override performs the real ERC20 allowance/authorization logic (via OpenZeppelin's `_spendAllowance` inside `transferFrom`) before ever calling into the precompile: [3](#0-2) 

Consequently, the entire security guarantee for every holder of that native denomination collapses to a single implicit trust assumption: "the currently registered ERC20NativePointer contract address for this denom is honest and enforces allowances correctly." If that assumption is ever violated — e.g., if the pointer registration for a denom can be created or reassigned to attacker-controlled bytecode (via `MsgRegisterPointer`, referenced in `x/evm/types/message_register_pointer.go` and `x/evm/keeper/pointer.go`) — an attacker's malicious "pointer" contract can call `send(victim, attacker, denom, amount)` directly, and the precompile will move funds from any victim's real bank balance to the attacker, with zero allowance/approval verification, exactly like the `addGasFee` PoC.

### Impact Explanation
If pointer assignment/reassignment for a native denom is not strictly permissioned so that a non-canonical or attacker-supplied contract can ever become (or be swapped in as) the registered pointer, this results in unauthorized transfer of native token balances for every holder of that denom without any prior approval — direct fund loss, matching the report's "steal users' tokens" impact class (Impact 5).

### Likelihood Explanation
The precompile logic itself contains no allowance check whatsoever; the vulnerability's actual exploitability hinges entirely on the access control surrounding pointer registration/reassignment (`x/evm/keeper/pointer.go`, `MsgRegisterPointer` handling, and any later migration such as `x/evm/migrations/disable_register_pointer.go`), which I was not able to fully inspect before running out of iterations. I could not confirm within the available searches whether pointer registration for an *existing* denom (one already held by users) is permissionless, restricted to governance, or blocked entirely by the `disable_register_pointer` migration. This is a material gap: the severity/likelihood of this analog depends on that access-control boundary, which should be verified directly (via a Devin session with full repo access) before treating this as a confirmed, immediately exploitable bug versus a design fragility that is currently contained by pointer-registration permissions.

### Recommendation
- Verify and, if necessary, harden pointer registration (`x/evm/keeper/pointer.go`, `MsgRegisterPointer`) so a native denom's `ERC20NativePointer` can never be created or reassigned to an arbitrary/attacker-controlled contract once the denom has existing holders.
- Independent of that, avoid relying solely on "caller is the registered pointer" as the security boundary for actual fund movement in `send`. Consider requiring the precompile to itself validate real authorization (e.g., require `senderSeiAddr == origin` derived from the actual EOA `tx.origin`/associated Sei address, or explicit allowance bookkeeping at the precompile/bank-module level) rather than fully delegating consent-checking to whichever contract happens to be registered as "the pointer."

### Proof of Concept
Conceptual (contingent on pointer-registration access control, unverified in this pass):
1. Attacker registers (or otherwise causes to be registered) a malicious contract as the `ERC20NativePointer` for a native denom `X` that victims already hold, via the pointer-registration path in `x/evm/keeper/pointer.go`.
2. Attacker's malicious contract calls `BANK_PRECOMPILE_ADDRESS.send(victim, attacker, "X", victimBalance)`.
3. `PrecompileExecutor.send` (`precompiles/bank/bank.go:198-249`) checks only that `caller == pointer` (the attacker's own malicious contract, which now legitimately satisfies this check) — it performs no allowance check on `victim` — and executes `bankMsgServer.Send` moving `victimBalance` of denom `X` from `victim` to `attacker`. func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, uint64, error) {
	if readOnly {
		return nil, 0, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, 0, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, 0, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		bz, err := method.Outputs.Pack(true)
		return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, 0, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, 0, err
	}

	msg := &banktypes.MsgSend{
		FromAddress: senderSeiAddr.String(),
		ToAddress:   receiverSeiAddr.String(),
		Amount:      sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount))),
	}

	err = msg.ValidateBasic()
	if err != nil {
		return nil, 0, err
	}

	if _, err = p.bankMsgServer.Send(sdk.WrapSDKContext(ctx), msg); err != nil {
		return nil, 0, err
	}

	bz, err := method.Outputs.Pack(true)
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
