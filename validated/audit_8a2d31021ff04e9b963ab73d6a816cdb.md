### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw` permanently locks escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` on Tron escrows arbitrary ERC20 tokens supplied by order creators (any token address can be used as `order.inputs[i].token`) and later releases them via the internal `withdraw()` function, reached from `onAccept()` (`RedeemEscrow`/`RefundEscrow`) and `onGetResponse()`, both of which are cross-chain-triggered, `onlyHost`-gated paths. `withdraw()` moves tokens using a raw low-level call, `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));`, and only checks that the call itself did not revert, never decoding/inspecting the returned `bool` payload. [1](#0-0) 

### Finding Description
This is the same broken invariant as the external Zerem report: some ERC20 tokens (e.g. ZRX-style tokens) signal transfer failure by returning `false` rather than reverting. A `.call(...)` to such a token still returns `success == true` (the call didn't revert), so the `if (!success) revert TransferFailed();` guard passes even though zero tokens were actually moved.

Despite this, `withdraw()` unconditionally proceeds to decrement the escrow bookkeeping (`_orders[body.commitment][token] -= amount;`) and marks the order as filled/refunded (`_filled[body.commitment] = beneficiary;`, `EscrowReleased`/`EscrowRefunded` events), permanently closing out the order. [2](#0-1) 

The same unchecked pattern is repeated for `TRANSACTION_FEES` redemption and in the `SweepDust` handler inside `onAccept()`. [3](#0-2) [4](#0-3) 

Because the order-creation path (`newOrder`) accepts an attacker-chosen `order.inputs[i].token` address and escrows it without an allowlist, an order can be created against a token that returns `false` on transfer instead of reverting. When the cross-chain fill/refund flow later calls `withdraw()`, the escrow state is wiped and the order is marked filled/refunded even though the beneficiary received nothing — the tokens remain stuck in the `IntentGatewayV2` contract with no code path left to reclaim them, since `_filled[commitment]` is now set and further calls hit `Filled()`/`UnknownOrder()` reverts.

By contrast, the primary EVM `IntentGatewayV2.sol` (non-Tron) consistently uses OpenZeppelin's `SafeERC20.safeTransferFrom`/`safeTransfer`, which correctly reverts on a `false` return. [5](#0-4) 
This shows the Tron variant diverged from the safe pattern used elsewhere in the same protocol.

### Impact Explanation
Escrowed order funds (and accrued transaction fees) can become permanently stuck in the `IntentGatewayV2` contract on Tron when the input token is one of the (documented, non-standard but real-world) ERC20 implementations that return `false` instead of reverting on failure. This matches the "stealing or loss of funds" / fund-lock category of the bounty scope, since order state is irreversibly finalized (`_filled` set, escrow decremented, events emitted) without the corresponding value transfer actually occurring.

### Likelihood Explanation
Reaching `withdraw()` requires the normal cross-chain intent lifecycle (order creation → fill/cancel → ISMP request/response processed by the host) — no malicious relayer, prover, or admin is required. The only precondition is that the order's input/fee token be a non-standard ERC20 that returns `false` rather than reverting, which is a property of the token contract, not of any privileged actor, and is explicitly the scenario the cited external Zerem report calls out as realistic.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the pattern already used in `evm/src/apps/IntentGatewayV2.sol` and `IntentsBase.sol` (`safeTransferFrom`/`safeTransfer`), so that non-reverting `false`-returning tokens cause the transaction (and therefore the escrow-state update) to revert instead of silently succeeding.

### Proof of Concept
1. On the source chain, attacker calls `newOrder` (or equivalent) specifying `order.inputs[0].token = maliciousToken`, where `maliciousToken.transfer()` always returns `false` without reverting; the amount is escrowed via `safeTransferFrom` succeeding normally (deposit uses `transferFrom`, which behaves fine).
2. Order is filled/cancelled on the destination chain and a `RedeemEscrow`/`RefundEscrow` ISMP request is relayed back and accepted by `onAccept()` → `withdraw()`.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (no revert) even though the token internally returned `false` and moved no balance.
4. `_orders[body.commitment][token] -= amount;` executes, `_filled[body.commitment] = beneficiary;` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — the order is now permanently closed with the beneficiary holding zero tokens and the contract retaining the escrowed balance with no remaining withdrawal path.
