### Title
PedPoP plaintext-validity check bypasses PoP verification and leaks a reused message's ECDH key - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts each `EncryptedMessage` and immediately generates an `EncryptionKeyProof` before the batched Schnorr proof-of-possession is verified. If the decrypted share bytes are non-canonical, the function returns that proof before `BatchVerifier` can reject the message's `pop`, allowing a caller to reuse the per-message public key from someone else's ciphertext while substituting malformed ciphertext bytes. [1](#0-0) [2](#0-1) 

### Finding Description
`Encryption::decrypt` queues the `pop` proof under `BatchId::Decryption`, then computes the ECDH point and returns an `EncryptionKeyProof` containing that point and a DLEq proof. [3](#0-2)  In `calculate_share`, `C::F::from_repr` is applied to the decrypted plaintext before the queued batch verification runs; a non-canonical plaintext causes an early `InvalidShare` error carrying `Some(blame)`. [4](#0-3)  The code intended the PoP to prevent exactly this disclosure: its challenge binds the sender, message ciphertext, and ephemeral key. [5](#0-4)  Because the early return bypasses the batch verifier, the malformed message does not need a valid PoP before its ECDH proof is emitted. [6](#0-5) 

### Impact Explanation
The disclosed `EncryptionKeyProof.key` is the ECDH result for the attacker-selected `msg.key`. Reusing the `key` field from a victim's encrypted share therefore reveals the shared point needed to derive that victim message's ChaCha20 keystream. [7](#0-6)  `decrypt_with_proof` confirms that a verified proof key is sufficient to decrypt the associated message. [8](#0-7)  This converts an invalid, attacker-created DKG share into a public decryption capability for an unrelated encrypted share, leaking that secret share's plaintext. [9](#0-8) 

### Likelihood Explanation
The attacker supplies an `EncryptedMessage` to `calculate_share`, copies the serialized point and signature fields from a victim-directed ciphertext, and replaces the encrypted scalar bytes with attacker-controlled bytes. The copied Schnorr PoP fails because `pop_challenge` binds both `sender` and `message`, but the failure is only detected later by the batch verifier. [10](#0-9)  For Ristretto-sized scalar encodings, random replacement plaintext is usually non-canonical, so the early `from_repr` failure will normally occur before that PoP failure is evaluated. [4](#0-3) 

### Recommendation
Do not create or return an `EncryptionKeyProof` until the message's PoP has been verified synchronously. `Encryption::decrypt` should verify `msg.pop` before deriving and exposing `key`, or return a typed result that lets `calculate_share` suppress the proof whenever `BatchId::Decryption` is invalid. The scalar-canonicality check should also occur only after authentication succeeds, ensuring malformed ciphertext cannot bypass proof verification through an earlier error path. [3](#0-2) [6](#0-5) 

### Proof of Concept
1. Let `M` be an encrypted secret share produced by an honest sender for recipient `B`; its serialization contains `key`, `pop`, and encrypted `SecretShare` bytes. [11](#0-10) 
2. An attacker submitting shares to `B` constructs `M'` by copying `M.key` and `M.pop`, while replacing the encrypted `SecretShare` payload with random bytes, and inserts `M'` under the attacker's own `Participant` ID. [12](#0-11) 
3. `B` calls `EncryptedMessage::read` and `KeyMachine::calculate_share` on the attacker-controlled map. `decrypt` queues a PoP check bound to the attacker as sender and to `M'`'s ciphertext, then derives `key = B_enc_key * M.key`. [2](#0-1) 
4. When the random plaintext is non-canonical, `calculate_share` returns `InvalidShare { participant: attacker, blame: Some(proof) }` without executing the batched PoP verification. [4](#0-3) 
5. `proof.key` is the ECDH point for `M.key` and `B`'s encryption key. The same point derives the keystream for the original `M`, so publication of the blame proof lets observers decrypt `M` even though `M'`'s PoP was invalid. [13](#0-12)

fn ecdh<C: Ciphersuite>(private: &Zeroizing<C::F>, public: C::G) -> Zeroizing<C::G> {

// Each ecdh must be distinct. Reuse of an ecdh for multiple ciphers will cause the messages to be
// leaked.
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this

  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))

  context: [u8; 32],
  enc_keys: HashMap<Participant, C::G>,

impl<C: Ciphersuite> Decryption<C> {
  pub(crate) fn new(context: [u8; 32]) -> Self {
    Self { context, enc_keys: HashMap::new() }
  }
  pub(crate) fn register<M: Message>(
    &mut self,
    participant: Participant,
    msg: EncryptionKeyMessage<C, M>,
  ) -> M {
    assert!(
      !self.enc_keys.contains_key(&participant),
      "Re-registering encryption key for a participant"
    );
    self.enc_keys.insert(participant, msg.enc_key);
    msg.msg
  }

  // Given a message, and the intended decryptor, and a proof for its key, decrypt the message.
  // Returns None if the key was wrong.

    from: Participant,
    decryptor: Participant,

    if !msg.pop.verify(
