### Title
Cross-vote KIP-71 base-fee bound consistency check uses stale ratified state, allowing an inconsistent (Lower > Upper) bound pair to be ratified - (File: kaiax/gov/headergov/impl/header.go)

### Summary
The Linux tracefs CVE-2024-36963 root cause is that a per-item override is validated/applied against a stale reference point instead of the fully up-to-date, currently-pending state, so two individually "valid" updates combine into an inconsistent result. The Kaia governance vote consistency check for KIP-71's `governance.kip71.lowerboundbasefee` / `governance.kip71.upperboundbasefee` parameters has the same structural flaw: each vote is validated against `GetParamSet(blockNum)`, which reflects only the last *ratified* parameter set, not any other vote already accepted earlier in the same epoch. Two votes cast in the same epoch can each individually pass the check yet jointly ratify a state where `LowerBoundBaseFee > UpperBoundBaseFee`.

### Finding Description
`checkConsistency` in `kaiax/gov/headergov/impl/header.go` validates `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` votes as follows: [1](#0-0) 

```
case gov.Kip71LowerBoundBaseFee:
    params := h.GetParamSet(blockNum)
    if vote.Value().(uint64) > params.UpperBoundBaseFee {
        return ErrLowerBoundBaseFee
    }
case gov.Kip71UpperBoundBaseFee:
    params := h.GetParamSet(blockNum)
    if vote.Value().(uint64) < params.LowerBoundBaseFee {
        return ErrUpperBoundBaseFee
    }
```

`GetParamSet(blockNum)` is computed from the `history` map, which is only updated at ratification time (`GovsToHistory` in `kaiax/gov/headergov/history.go`), i.e., it reflects the previous epoch's ratified values, not any vote cast earlier in the *same* epoch. As documented in `kaiax/gov/headergov/README.md`, all votes cast within an epoch are collected and, in `single` mode, the last vote per parameter name in the epoch is the one ratified — but the cross-parameter consistency check (`Lower <= Upper`) is only evaluated against the old ratified baseline, never against the other new vote(s) about to be ratified together.

Scenario:
1. Old ratified state: `LowerBoundBaseFee = 100`, `UpperBoundBaseFee = 1000`.
2. Within the same epoch, the governing node casts vote A: `LowerBoundBaseFee = 900` (passes check: `900 <= 1000`, the old Upper).
3. Later in the same epoch, the governing node casts vote B: `UpperBoundBaseFee = 200` (passes check: `200 >= 100`, the old Lower).
4. At the epoch boundary, both votes are ratified together (last vote per name wins), producing `LowerBoundBaseFee = 900`, `UpperBoundBaseFee = 200` — an inconsistent pair where `Lower > Upper`, which the individual per-vote checks never caught because each was checked against a stale snapshot instead of the jointly-final values.

This exactly mirrors the tracefs bug class: partial/point-in-time validation against a stale baseline instead of the final combined outcome, so the system ends up in a state believed to be validated (each vote individually legal) but that is globally inconsistent once fully applied — same as tracefs's per-file permission flags surviving inconsistently across a bulk update.

### Impact Explanation
`LowerBoundBaseFee`/`UpperBoundBaseFee` govern the KIP-71 dynamic base-fee bounds used by proposers and validators when computing/clamping the block base fee (`params/kip71_config.go` and the block-assembly/base-fee logic that consumes `gov.ParamSet`). Once `Lower > Upper` is ratified, all honest nodes deterministically read the same broken parameter set (this is not a fork/divergence issue by itself since all nodes derive the same history), but it corrupts the fee-bound invariant that KIP-71 base-fee clamping logic assumes, which can produce undefined/incorrect base-fee clamping behavior network-wide (e.g., the clamp `max(Lower, min(Upper, computed))` becomes non-monotonic/contradictory), degrading fee-market correctness and potentially enabling under/over-charging of transaction fees relative to intended KIP-71 semantics. This falls under the explicitly in-scope "KIP-71 pricing" and "governance parameters" categories.

### Likelihood Explanation
Exploiting/triggering this requires two `governance_vote` RPC calls by the governing node (or, in `none` mode, any GC member with the last vote per epoch winning) within the same epoch — a legitimate governance action, not a byzantine/malicious-validator consensus fault, and not restricted to CLI/operator-only paths (it's exposed via the standard `governance_vote` JSON-RPC API). It could be triggered accidentally by a well-meaning governance operator making sequential updates, or deliberately by a governing node wanting to exploit fee-bound clamping in a way not intended by KIP-71's designers.

### Recommendation
When validating `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` votes in `checkConsistency`, compare against the combination of the ratified baseline **and** any other pending vote for the counterpart parameter already accepted within the current (not-yet-ratified) epoch, rather than only `GetParamSet(blockNum)`. Alternatively, perform a final joint-consistency check at ratification time (when building `header.Governance` for the epoch) that rejects/reorders ratification if the resulting `LowerBoundBaseFee > UpperBoundBaseFee`, analogous to tracefs's fix of tracking and atomically resetting all related state together instead of relying on incremental, independently-validated updates.

### Proof of Concept
Not independently executed in this ask-only session; the flow is derivable directly from the cited code: `checkConsistency` reads only `h.GetParamSet(blockNum)` (last ratified state) for both `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` cases, with no reference to intra-epoch pending votes, and `kaiax/gov/headergov/README.md` confirms only the last vote per name per epoch is ratified — so casting the two sequential votes described above (Lower raised in reference to old Upper, then Upper lowered in reference to old Lower) would ratify a globally inconsistent bound pair. Reproducing this end-to-end (via `governance_vote` RPC calls across an epoch boundary and inspecting the resulting `ParamSet`) would require running a Devin session against a live/test node.
