## Title
NFT offer royalty payments can be reduced to zero via repeated floor-division truncation across split assets/split royalty NFTs - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

## Summary
The Chia NFT offer/royalty flow contains the same rounding-truncation bug class as the referenced report: a percentage fee (here, the creator royalty) is computed with integer floor division, and an unprivileged offer participant can structure the trade (by splitting the payment across multiple royalty-enabled NFTs, or using small enough per-asset amounts) so that the computed royalty for each unit truncates to zero, letting them pay less royalty in aggregate than the configured percentage — without any minimum-amount guard.

## Finding Description
`compute_royalty_amount()` computes the royalty owed to an NFT creator using pure integer arithmetic with two sequential floor divisions: [1](#0-0) 

```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```

This is invoked once per royalty-enabled NFT included in an offer, from `make_nft1_offer()`: [2](#0-1) 

`royalty_split` is simply the count of royalty-enabled NFTs on the requesting side of the offer, controlled entirely by the offer maker/taker (an unprivileged wallet user constructing the trade). Because the amount is first divided by `royalty_split` (floor) and only afterward multiplied by `percentage` and floor-divided by `MAX_ROYALTY_BASIS_POINTS` (10000 bps), increasing `royalty_split` (i.e., bundling the trade across more royalty-enabled NFTs from the same creator/collection, or lowering the per-asset offered amount) drives each individual royalty share toward zero. The code even acknowledges this truncation exists and only guards against it in one place — filtering zero trade prices before passing them to `generate_signed_transaction` — rather than enforcing a floor/minimum on the royalty itself: [3](#0-2) 

The existing unit tests explicitly document this as expected behavior with no protection: [4](#0-3) 

This mirrors the "buy dust amounts to skip paying fee" bug class from the external report: the fee/royalty formula rounds to zero for small enough inputs, and there is no `minBuyAmount`/minimum-royalty analog to prevent a caller from repeatedly (or structurally, in one offer) exploiting the truncation.

## Impact Explanation
An offer maker/taker fully controls `royalty_split` (how many royalty NFTs are bundled) and the per-asset fungible amount in the offer. By bundling many low-value royalty-enabled NFTs together (or driving the per-NFT requested/offered amount low enough relative to `royalty_split`), the resulting `compute_royalty_amount()` output for each NFT — and potentially the summed royalty across the whole trade — truncates to zero or to a value far below the creator's configured percentage. This denies the NFT creator/royalty address their entitled portion of an otherwise valid, high-value settlement, which is an economic theft from the intended offer settlement, exactly analogous to the referenced bonding-curve fee-bypass finding.

## Likelihood Explanation
This requires no special privileges — any wallet user constructing or accepting an NFT offer via `TradeManager`/`NFTWallet.make_nft1_offer` chooses how many royalty NFTs to bundle and the exact fungible amounts, so the truncation can be reliably and deterministically triggered by adversarial offer construction. Likelihood is high for any motivated market participant trading royalty-bearing NFTs in bulk/split trades.

## Recommendation
Enforce a minimum royalty amount (or compute royalty using a single combined floor division over the total amount before splitting, then distribute remainders) so that `compute_royalty_amount()` cannot be driven to zero (or under-collected) purely by increasing `royalty_split` or shrinking per-asset amounts. Alternatively, require `royalty_split`-adjusted royalty to be computed on the aggregate offered/requested amount first, and only then divided per-NFT, ensuring total royalty collected across an offer never falls below `percentage * total_amount // MAX_ROYALTY_BASIS_POINTS`.

## Proof of Concept
Using the existing test harness pattern in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py`, calling `compute_royalty_amount(offered_amount=-50, royalty_split=1, percentage=100)` already yields `0` royalty for a 1% fee on 50 mojos. [4](#0-3)  An attacker extends this by bundling a real trade (e.g., total value V, percentage P) across N royalty-enabled NFTs of the same collection such that for every NFT, `(V/N) // 1 * P // 10000 == 0`, while a single non-split royalty computation on the full amount `V * P // 10000` would be nonzero — showing the creator receives strictly less royalty than the configured percentage entitles them to, purely by choosing how the offer is structured.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
