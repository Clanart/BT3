### Title
`Operator::handle_duty` Returns Wrong `DutyResult` Variant for `CheckIfKickoffMalicious`, Crashing `StateManager<Operator>` on Every Kickoff - (`core/src/operator.rs`)

### Summary

`StateManager<T>::check_if_kickoff_malicious` dispatches `Duty::CheckIfKickoffMalicious` and **requires** the owner to return `DutyResult::CheckIfKickoffMalicious { challenged }`. The `Operator` implementation returns `DutyResult::Handled` instead. When automation is enabled and `StateManager<Operator>` receives a `NewKickoff` event, the mismatch causes `handle_event` to return a hard error, breaking the operator's entire state machine loop.

### Finding Description

`StateManager<T>::check_if_kickoff_malicious` (called from `handle_event` for every `SystemEvent::NewKickoff` whose LCP height has been processed) dispatches the duty and then pattern-matches the result:

```rust
// core/src/states/event.rs  ~line 370
match res {
    DutyResult::CheckIfKickoffMalicious { challenged } => { … }
    other => {
        return Err(eyre::eyre!(
            "Expected CheckIfKickoffMalicious duty result, got {other:?}"
        ).into());
    }
}
``` [1](#0-0) 

The `Verifier` implementation correctly returns `DutyResult::CheckIfKickoffMalicious { challenged: is_malicious }`: [2](#0-1) 

The `Operator` implementation, however, returns `DutyResult::Handled`:

```rust
// core/src/operator.rs  ~line 2640
// Operators do not check if kickoffs are malicious
Duty::CheckIfKickoffMalicious { .. } => Ok(DutyResult::Handled),
``` [3](#0-2) 

`check_if_kickoff_malicious` is called unconditionally (no owner-type guard) from `handle_event` whenever a `NewKickoff` event arrives and the LCP for that height has already been processed: [4](#0-3) 

It is also called for every pending kickoff when a `LCPProcessed` event fires: [5](#0-4) 

`StateManager<Operator>` is a real, instantiated generic — the verifier explicitly dispatches `NewKickoff` events to the operator's queue when automation is enabled: [6](#0-5) 

The `Duty` and `DutyResult` types are shared across both owners: [7](#0-6) 

### Impact Explanation

Every time a kickoff UTXO is spent on-chain and the LCP for that block has been processed, `StateManager<Operator>::handle_event` returns a `BridgeError` ("Expected CheckIfKickoffMalicious duty result, got Handled"). This error propagates out of `handle_event`, causing the operator's state machine task to fail. As a result:

1. The kickoff state machine for that deposit is never fully initialized inside the operator's `StateManager`.
2. Duties such as `AddNecessaryTxsForKickoff` (which queues `ChallengeTimeout` transactions) may not be dispatched or may be lost if the task crashes before they are processed.
3. If `ChallengeTimeout` is not queued, the operator cannot reclaim the kickoff connector after the challenge window expires, and the operator's collateral UTXO remains at risk of being slashed by a verifier who sends a challenge.

This is a direct, reachable path to loss of operator collateral — a bridge-controlled fund.

### Likelihood Explanation

The trigger is automatic and unprivileged: any legitimate kickoff transaction mined on Bitcoin (including the operator's own kickoffs) causes the bug to fire. No adversarial action is required. The condition is met in every normal bridge withdrawal cycle when the operator runs with `--features automation`.

### Recommendation

Change the `Operator` implementation to return the correct variant:

```rust
// core/src/operator.rs
Duty::CheckIfKickoffMalicious { .. } => {
    // Operators do not challenge, but must return the correct variant
    Ok(DutyResult::CheckIfKickoffMalicious { challenged: false })
}
```

Alternatively, add a guard in `StateManager::check_if_kickoff_malicious` to skip the call when the owner is not a verifier (e.g., via a new `Owner` method `should_check_kickoff_malicious() -> bool` defaulting to `true`, overridden to `false` for `Operator`).

### Proof of Concept

1. Deploy Clementine with `--features automation` so that both `StateManager<Verifier>` and `StateManager<Operator>` are running.
2. Complete a deposit and have the operator send a kickoff transaction.
3. Wait for the LCP for the kickoff block to be processed (`StateManager::dispatch_lcp_processed` fires).
4. Observe that `StateManager<Operator>::handle_event` returns `Err("Expected CheckIfKickoffMalicious duty result, got Handled")`.
5. The operator's state machine task exits; `ChallengeTimeout` is never queued; the operator's collateral connector is left unprotected.
