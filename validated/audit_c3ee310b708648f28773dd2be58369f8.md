### Title
Fee amortized a second time on an already post-fee branch output — inverted subtraction underflows, draining or hanging the scheduler - (File: processor/src/multisigs/scheduler/utxo.rs)

### Summary
The external report describes a `loop()` that charges a fee twice — once before the cycle and once inside it. The Serai analog lives in the UTXO scheduler's `created_output`, which applies fee amortization a second time to an output amount that already had the transaction fee deducted, and does so with the subtraction operands inverted (`actual - expected` where `actual < expected`).

### Finding Description
When a plan's payments are batched into a branch output, `prepare_send` amortizes the transaction fee across the payments, producing a `PostFeeBranch { expected: initial_amount, actual: post_fee_amount }`. The resulting on-chain output therefore has value `actual`, which is strictly less than `expected`. Later, `Scheduler::created_output` is called with `expected` (the pre-fee amount) and `actual` (the post-fee amount actually created):

```rust
// processor/src/multisigs/scheduler/utxo.rs
let mut to_amortize = actual - expected;
```

Because `actual < expected` always holds (fees are non-negative and the fee was already subtracted), this `u64` subtraction underflows:

- Debug builds: immediate panic, crashing the processor.
- Release builds: `to_amortize` wraps to ~`u64::MAX`. The `while to_amortize != 0` loop then subtracts `payment.balance.amount.0.min(to_subtract)` from every child payment, driving them all to zero. Once all payments are zero, `subtractable` is 0 each iteration, so `to_amortize` never decreases and the loop never terminates — a permanent hang of the scheduler thread.

The intended formula was clearly `expected - actual` (the fee actually paid, to be re-amortized over child payments), mirroring the correct amortization loop in `prepare_send` (`remaining_fee = total_fee`, subtracting down to 0).

### Impact Explanation
An unprivileged user triggers this path by performing ordinary withdrawals that get batched through a branch output — no validator privileges, no malformed cryptography required; the inputs are ordinary payment amounts and balances. Consequences:

- Debug/ panic-enabled builds: processor crash on `created_output` — liveness failure freezing all pending payments for that multisig.
- Release builds: infinite loop inside `created_output`, permanently stalling scheduling, or (if it ever exited) all child payments drained to dust and silently dropped — funds reported as processed that were never sent, i.e., user funds burned.

Either way, the fee subtraction is applied a second time to funds that already paid it — precisely the "charged twice" bug class.

### Likelihood Explanation
High for reachability: any routed/batched payment flow that produces a `PostFeeBranch` with `actual < expected` reaches this code via the normal scheduler event path (`created_output` is invoked whenever a branch output is observed created with `Some(actual)`). The underflow occurs on the very first invocation where a fee was deducted — which is every invocation where a non-zero fee exists.

### Recommendation
In `processor/src/multisigs/scheduler/utxo.rs` (`Scheduler::created_output`), change:

```rust
let mut to_amortize = actual - expected;
```

to use checked subtraction in the correct direction:

```rust
let mut to_amortize = expected.checked_sub(actual)
  .expect("actual branch output exceeded expected pre-fee amount");
```

and add a regression test where a branch output is created with `actual < expected` and child payments retain the correct post-amortization balances.

### Proof of Concept
1. Configure the scheduler so a plan produces a branch output (multiple payments aggregated under one `branch_address` output) — reachable via ordinary user withdrawals.
2. `prepare_send` amortizes `tx_fee` over payments, emitting `PostFeeBranch { expected: A, actual: Some(A - f) }` with `f > 0`.
3. When the branch output is confirmed, `created_output(txn, expected = A, actual = Some(A - f))` executes `A - f - A` → underflow → panic (debug) or wraparound (release).
4. Release-mode wraparound: the `while to_amortize != 0` loop zeroes every queued child payment (`payment.balance.amount.0.min(to_subtract)`), then spins forever since `subtractable` becomes 0 — scheduler hangs; all child payments are destroyed.

    {
      let mut to_amortize = actual - expected;
      // If the payments are worth less than this fee we need to amortize, return, dropping them
      if payments.iter().map(|payment| payment.balance.amount.0).sum::<u64>() < to_amortize {
        return;
      }
      while to_amortize != 0 {
        let payments_len = u64::try_from(payments.len()).unwrap();
        let per_payment = to_amortize / payments_len;
        let mut overage = to_amortize % payments_len;

        for payment in &mut payments {
          let to_subtract = per_payment + overage;
          // Only subtract the overage once
          overage = 0;

          let subtractable = payment.balance.amount.0.min(to_subtract);
          to_amortize -= subtractable;
          payment.balance.amount.0 -= subtractable;
        }
      }
    }
