## Finding

### Title
Native fee-payment dispatch traps unrefunded ETH in EvmHost due to missing slippage/refund handling in `swapETHForExactTokens` — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all pay Hyperbridge's protocol fee in native token by calling UniswapV2's `swapETHForExactTokens` with the *entire* `msg.value` forwarded as the swap's native input, requesting an exact output of `post.fee`/`get.fee`/`amount` fee-tokens [1](#0-0) . This mirrors the Yearn bug-class: a value-moving call is made with a hardcoded, unchecked economic parameter (in this case the *entire* `msg.value` as `amountInMaximum` with no bound and no capture of the resulting refund), causing funds that should return to the payer to be silently lost.

### Finding Description
UniswapV2Router02's `swapETHForExactTokens(amountOut, path, to, deadline)` semantics: it computes the exact ETH input required to obtain `amountOut` of the output token, executes the swap, and if `msg.value` exceeds the computed input, it refunds the difference to `msg.sender` of that call — not to `to`. In `EvmHost.dispatch(...)`, the call is:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```

`msg.sender` of this inner call is `EvmHost` itself (since `EvmHost` calls the router directly), so any refund the router sends for unspent ETH lands in the `EvmHost` contract balance, not back to the original caller (`_msgSender()`/`post.payer`) who supplied `msg.value` to the outer `dispatch()` call [1](#0-0) . There is no subsequent code in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` that captures this refund and forwards it back to the payer [2](#0-1) .

Callers determine how much native token to send via `HyperApp.quote()`, which calls `getAmountsIn(request.fee, path)` at call time to estimate the ETH cost [3](#0-2) . Between the quote and the actual `dispatch()` transaction, AMM price can move (natural price movement, MEV, or a scripted counter-trade), so the value transferred at execution time is frequently less than `msg.value`. The identical pattern repeats for `DispatchGet` and `fundRequest`, which additionally allows an attacker/donor to over-fund and lose the surplus with each call [4](#0-3) .

This is the exact analog of the Yearn `maxLoss = 10_000` bug: a fixed, uncontrolled parameter (`msg.value` forwarded wholesale, with no cap or refund handling) is used in a value-transfer call to an external AMM, and any resulting "loss" (unspent value/slippage) is not returned to the rightful owner — it is trapped by the calling contract instead.

### Impact Explanation
Any unprivileged user dispatching a POST/GET request or funding a request with native token payment permanently loses the ETH difference between `msg.value` and the actual swap cost — that value becomes stranded in the `EvmHost` contract with no accounting, no event, and no governance-facing sweep mechanism visible in this dispatch path. This is a direct, repeatable loss of user funds triggered purely by normal usage (price moves between quote and execution) and is exploitable more aggressively by sandwiching the AMM pool to widen the ETH/feeToken price gap right before a victim's `dispatch()` transaction, maximizing the amount stranded in `EvmHost`. This satisfies the "stealing or loss of funds" impact category, since value that should be refunded to the payer never returns to the rightful beneficiary.

### Likelihood Explanation
High. The vulnerable code path executes on every native-token-funded `dispatch()`, `fundRequest()` call — a first-class, public, unprivileged entry point used by ordinary applications and end users on every EVM deployment of Hyperbridge. No relayer, prover, admin, or malicious peer is required; only normal AMM price movement between quote-time and execution-time (or a simple sandwich) is needed to trigger fund loss.

### Recommendation
Capture the actual ETH spent and refund the remainder to the true payer:
```solidity
uint256 balanceBefore = address(this).balance - msg.value;
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
uint256 spent = amounts[0];
if (msg.value > spent) {
    (bool sent, ) = _msgSender().call{value: msg.value - spent}("");
    if (!sent) revert RefundFailed();
}
```
Apply the same fix to `dispatch(DispatchGet)` and `fundRequest()`.

### Proof of Concept
1. Application `A` calls `HyperApp.quote(post)` to estimate native cost for `post.fee` feeTokens; assume it returns `X` wei.
2. `A` calls `IDispatcher(host).dispatch{value: X}(post)`.
3. Before this transaction lands, an unrelated trade shifts the ETH/feeToken pool price favorably (or an attacker sandwiches it), so the actual ETH required to buy `post.fee` feeTokens is now `Y < X`.
4. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` spends only `Y`; the router refunds `X - Y` to `msg.sender`, which is `EvmHost`, not `A`.
5. `EvmHost` never forwards `X - Y` back to `A`; the amount permanently accumulates in the Host contract balance, unaccounted for and unrecoverable by `A`. [1](#0-0)
