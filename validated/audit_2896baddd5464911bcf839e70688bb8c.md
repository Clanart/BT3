## Title
Missing symlink/path-containment check when opening tracked-file paths from a cloned repository (Reveal in File Manager / Open in External Editor / Open with Default Program) - (File: `app/src/ui/history/selected-commits.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`)

## Summary
The external report's underlying pattern is "an attacker-influenced identifier is used to trigger a state-changing action without validating that it refers to what the code assumes it refers to" (a zero address treated as a valid burn/mint target). The closest Desktop analog is a repo-relative file path — sourced from a cloned/fetched repository's tracked files or diff — being joined with the repository root and handed to file-system-affecting actions (`shell.showItemInFolder`, `shell.openExternal('file://...')`, external editor launch) using plain `Path.join`, with no check that the resolved path still lives inside the repository. Desktop already has a purpose-built guard for exactly this class of bug, `resolveWithin` in `app/src/lib/path.ts`, which is applied in two places (the deep-link `filepath` handler and the Copilot conflict file reader) but not consistently applied to the Changes/History/PR "open" actions.

## Finding Description
Several UI surfaces compute a "full path" for a tracked file by concatenating the repository path with the file's repo-relative path and then act on it without verifying containment:

- `app/src/ui/history/selected-commits.tsx:384-419` builds `fullPath = Path.join(repository.path, file.path)` and wires it to `revealInFileManager`, `onOpenInExternalEditor`, and `onOpenItem` (Open with Default Program). [1](#0-0) 
- `app/src/ui/open-pull-request/pull-request-files-changed.tsx:162-199` does the same for PR-changed files, feeding `dispatcher.openInExternalEditor(fullPath)` and `revealInFileManager`. [2](#0-1) 
- `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx:212-234` builds `absolutePath = join(repository.path, path)` for the "Open in editor / Open with default program / Reveal in file manager" overflow menu. [3](#0-2) 
- The resulting path is then passed to `openFile()`, which calls `shell.openExternal('file://' + fullPath)` directly. [4](#0-3) 
- These paths ultimately also flow to `_openInExternalEditor` / `launchExternalEditor`, which spawns the configured editor with the path as an argument, again with no containment check. [5](#0-4) [6](#0-5) 

By contrast, Desktop has already recognized this exact "broken invariant" (a repo-relative path can resolve outside the repository root via symlinks or traversal) and built `resolveWithin` to close it — used only for the `x-github-client://openRepo` deep-link `filepath` parameter and the Copilot conflict-resolution file reader: [7](#0-6) [8](#0-7) 

Because a Git tree entry can be a symlink, an attacker who controls a cloned/fetched repository (or a fork whose PR is viewed via "Open Pull Request Files Changed") can commit a symlink (e.g. `evil -> /etc` or `evil -> ..\..\..\AppData\Roaming`) plus a file reported as changed "inside" that symlinked directory. When the local Git status/diff machinery reports `file.path` like `evil/passwd`, `Path.join(repository.path, 'evil/passwd')` textually stays inside the repo, but the OS resolves it through the symlink to an arbitrary location outside the repository — exactly the kind of unchecked-address-then-use-it pattern flagged in the original report, just applied to filesystem paths instead of Ethereum addresses.

## Impact Explanation
If validated, this allows content outside the repository working directory to be revealed in the file manager, opened with the OS default handler, or opened in the user's configured external editor, based purely on data an attacker fully controls in a cloned/fetched repository or PR fork. Depending on the target (a script with a "safe" extension check bypass via symlink target, an OS shortcut/`.desktop`/`.lnk` file reached through the symlink, or sensitive files under the user's home directory), this can result in unintended file exposure/read or, for double-click/"Open with Default Program" flows, execution of attacker-chosen content — matching the report's required impact class of "file write or read outside the repo" from an attacker-controlled cloned/fetched repository.

## Likelihood Explanation
Medium. It requires the user to right-click and choose "Reveal in File Manager"/"Open in External Editor"/"Open with Default Program" on a file from a malicious commit (own clone, a collaborator's push, or a PR fork opened via "Open Pull Request Files Changed"), which is a normal, expected user action rather than an unnatural step. The `isSafeFileExtension` gate used for "Open with Default Program" only inspects the tracked path's extension, not the resolved symlink target, so it does not stop this path.

## Recommendation
Apply the same `resolveWithin` containment/symlink-escape check (already implemented in `app/src/lib/path.ts` and used in `dispatcher.ts`/`copilot-conflict-context.ts`) to every place that turns a repo-relative, potentially attacker-controlled `file.path` into a full path before calling `revealInFileManager`, `openFile`, or `openInExternalEditor` — specifically `selected-commits.tsx`, `pull-request-files-changed.tsx`, `copilot-conflicts-dialog.tsx`, `sidebar.tsx`/`filter-changes-list.tsx`, and any other call site that does a bare `Path.join(repository.path, file.path)` for these actions. Refuse or warn instead of opening when the resolved path escapes the repository root.

## Proof of Concept
1. Attacker creates a repo containing a symlink `link` pointing to a sensitive directory (e.g. `ln -s /Users/victim/Library ../../Library`, or on Windows a directory symlink to `%APPDATA%`), commits it, and pushes/opens a PR.
2. Victim clones the repo (or opens the PR via "Open Pull Request Files Changed"), which lists a file such as `link/some-file` as part of the diff/tree.
3. Victim right-clicks the entry and selects "Reveal in File Manager" or "Open in External Editor".
4. `Path.join(repository.path, 'link/some-file')` is passed straight to `shell.showItemInFolder` / the external editor launcher without any `resolveWithin`-style containment check, causing the file manager/editor to open a path outside the cloned repository, at a location fully chosen by the attacker via the symlink target.

Note: I was not able to inspect the exact internal implementation of `revealInFileManager` in `app/src/lib/app-shell.ts` within the available tool budget; the analysis above is based on the call-site code (which computes/forwards the un-validated joined path) and the confirmed existence of a purpose-built `resolveWithin` guard used elsewhere for the identical class of bug. A Devin session with full file access should verify `app-shell.ts`'s `revealInFileManager` implementation before treating this as fully confirmed.

import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
