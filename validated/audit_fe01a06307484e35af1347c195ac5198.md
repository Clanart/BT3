### Title
Sybil bypass of self-referral protection in `useCode`/`registerCode` allows an attacker to collect both referrer and referee bonus rewards on their own activity - ([File: rewards/ReferralStorage.sol])

### Summary
`ReferralStorage.useCode` only blocks a user from using a code they registered themselves (`codeOwners[_code] == msg.sender`), but does not prevent an attacker from registering a code with a second, sybil-controlled EOA and then using it from a first EOA. This lets a single actor become both "referrer" and "referee" of the same referral relationship, entitling them to collect both `refererAmount` and `refereeAmount` from `trigger()` on volume that is entirely their own, with no genuine third party involved.

### Finding Description
`registerCode` lets any address register an arbitrary unused code with itself as owner: [1](#0-0) 

`useCode` only rejects the case where the caller directly registered the code being used (`codeOwners[_code] == msg.sender` → `Circled()`), and rejects re-referral (`HasReferral()`), but has no check that the code owner and the caller are not the same economic entity via a second address: [2](#0-1) 

An attacker deploys/controls two EOAs, A and B:
1. B calls `registerCode(codeB)` → `codeOwners[codeB] = B`.
2. A calls `useCode(codeB)` → `myReferer[A] = B`, `myReferees[B].push(A)`. The `Circled()` check does not trigger because `codeOwners[codeB] == B != A`.
3. `masterMagpie` later calls `trigger(A, amount)` as part of normal referee reward-claim flow, which computes and credits both: [3](#0-2) 
Both `refererInfo(B).rewardAmount` and `refereeInfo(A).rewardAmount` are increased from a single flow of value that the attacker fully controls end-to-end.
4. Both A and B independently call `claimReward()` and receive MGP: [4](#0-3) 

The `Circled()` check demonstrates the protocol's explicit intent to prevent self-dealing referral rewards, but it is implemented as a same-address equality check rather than a same-entity check, so it is trivially bypassed with a second wallet (a zero-cost sybil, well within an unprivileged attacker's capability). No other check (`HasReferral`, `HasReferee`, uniqueness of referrer/referee sets) enforces that the referrer and referee be distinct, unaffiliated parties.

### Impact Explanation
This allows theft/over-extraction of the referral reward pool (unclaimed MGP sitting in the `ReferralStorage` contract, transferred out via `claimReward`) by fabricating referral relationships with zero genuine third-party value. Any attacker who is already a masterMagpie participant can multiply their effective reward share (referrer share + referee share) purely by owning two addresses, extracting MGP that the reward-sharing design intends only for real referrer/referee pairs. This falls under "theft of unclaimed yield" — the referral bonus budget is finite protocol-funded yield, and self-dealing sybils divert it away from genuine referral participants.

### Likelihood Explanation
Preconditions are trivial and fully within an unprivileged attacker's control: create a second EOA (near-zero cost), call two public functions (`registerCode`, `useCode`), and proceed with normal staking/claim activity that triggers `trigger()` through `masterMagpie`. No special capital, timing, or privileged role is required, and the exploit is fully repeatable for every claim cycle.

### Recommendation
Add a same-entity/self-dealing guard beyond simple address equality, e.g.: track and reject referral relationships where the referee address was ever used to register the same or a linked code, and/or restrict `useCode` when the caller has any prior first-party relationship with `codeOwners[_code]` (e.g., disallow if the referee itself owns a code that the referrer's account has used, or otherwise require KYC/off-chain sybil resistance). At minimum, consider capping/removing purely additive bonus payouts that can be triggered without independent verification of referrer/referee distinctness, or funneling referral bonuses only from a portion of the referee's own share (not as pure additive minted-style rewards) so self-referral yields no net gain.

### Proof of Concept
Foundry test outline:
1. Deploy `ReferralStorage`, `masterMagpie` mock, `MGP` token; fund `ReferralStorage` with MGP for reward payouts; set a tier with nonzero `rewardPercentage` and `sharePercent`.
2. `vm.prank(B); referralStorage.registerCode(codeB);`
3. `vm.prank(A); referralStorage.useCode(codeB);`
4. `vm.prank(masterMagpie); referralStorage.trigger(A, amount);`
5. Assert `refererInfo(B).rewardAmount > 0` and `refereeInfo(A).rewardAmount > 0`.
6. `vm.prank(A); referralStorage.claimReward();` and `vm.prank(B); referralStorage.claimReward();`
7. Assert `MGP.balanceOf(A) + MGP.balanceOf(B) == refererAmount + refereeAmount`, both fully captured by the same attacker-controlled entity, versus the baseline (no referral) case where the attacker (as a lone, non-referred user) would receive `amount` with zero bonus — demonstrating the additive extraction achieved purely through sybil self-referral.

        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
