### Title
Coinbase outputs are reported as spendable despite maturity restrictions - (networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` scans every transaction in a block, including the coinbase transaction, and returns matching outputs as ordinary `ReceivedOutput`s. A coinbase output cannot be spent until it has matured for 100 blocks. The wallet signing path treats the returned output as immediately spendable, allowing a plan/signature attempt to be constructed around an input that Bitcoin consensus will reject. This is analogous to a permanently failing proposal occupying capacity: the invalid work item enters the spendable-input queue and can prevent useful execution until it is abandoned or becomes valid.

### Finding Description
`Scanner::scan_block` iterates over `block.txdata` without excluding `block.txdata[0]`, the coinbase transaction. [1](#0-0) 

`Scanner::scan_transaction` then reports every output whose `script_pubkey` matches a registered scanner script, with no check that the containing transaction is coinbase or that the block height is sufficiently mature. [2](#0-1) 

`SignableTransaction::new` accepts these `ReceivedOutput`s as inputs, copies their outpoints and values into a transaction, and records their offsets for signing. [3](#0-2) 

`TransactionSignMachine::sign` commits to all supplied previous outputs with `Prevouts::All`, so the signing process incorporates the immature coinbase input rather than rejecting it. [4](#0-3) 

The implementation itself acknowledges the problem in a comment: coinbase transactions are scanned, are bound by maturity, and require post-processing to remove outputs that must be immediately spendable. [5](#0-4) 

### Impact Explanation
An immature coinbase output is consensus-invalid as a transaction input even though its script corresponds to a registered Serai key. If it reaches transaction construction and signing, the resulting transaction cannot be relayed or confirmed for 100 blocks. Any signing attempt, batch, queue slot, or wallet state that assumes the output is executable can therefore become stuck on a permanently failing action for the maturity period.

The concrete result is funds reported as received and usable that are not currently spendable. This matches the failed-proposal pattern: malformed or premature work enters the active execution path, fails when executed, and may require retry/expiration logic before the system can proceed.

### Likelihood Explanation
A miner can place an output paying a scanned Serai script into a coinbase transaction. Once Serai scans that block through `scan_block`, the output appears as a normal `ReceivedOutput`. If the scheduler or wallet selects it before maturity, the generated transaction is guaranteed to fail consensus validation.

The issue does not corrupt keys, forge signatures, or permanently lose funds. After 100 confirmations, the same output becomes spendable. Severity is Medium because exploitation requires the output to be selected before maturity, but the resulting execution failure is deterministic once selected.

### Recommendation
Do not return coinbase outputs from APIs that promise immediately spendable outputs. Specifically:

- Have `Scanner::scan_block` ignore `block.txdata[0]`, or return coinbase outputs through a separate pending-output type.
- Carry block height/transaction-position metadata in `ReceivedOutput` if coinbase outputs must be tracked.
- Enforce the 100-block maturity rule before feeding outputs to `SignableTransaction::new`.
- Add a regression test proving a matching coinbase output is not reported as spendable before maturity.

### Proof of Concept
```rust
use bitcoin::{absolute::LockTime, transaction::Version, Amount, Block, Transaction, TxIn, TxOut};
use bitcoin::blockdata::script::ScriptBuf;
use bitcoin::hashes::Hash;
use k256::ProjectivePoint;
use serai_bitcoin::wallet::Scanner;

let scanner = Scanner::new(vault_key).unwrap();
let vault_script = bitcoin::ScriptBuf::new_p2tr_tweaked(
    bitcoin::key::TweakedPublicKey::dangerous_assume_tweaked(vault_x_only)
);

let coinbase = Transaction {
    version: Version(2),
    lock_time: LockTime::ZERO,
    input: vec![TxIn {
        previous_output: bitcoin::OutPoint::null(),
        script_sig: ScriptBuf::new(),
        sequence: bitcoin::Sequence::MAX,
        witness: bitcoin::Witness::new(),
    }],
    output: vec![TxOut {
        value: Amount::from_sat(100_000),
        script_pubkey: vault_script,
    }],
};

let block = Block {
    header: valid_header,
    txdata: vec![coinbase],
};

let received = scanner.scan_block(&block);
assert_eq!(received.len(), 1);

// received[0] is represented as spendable, but Bitcoin rejects spends of this
// coinbase output until the block is 100 confirmations deep.
```

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
