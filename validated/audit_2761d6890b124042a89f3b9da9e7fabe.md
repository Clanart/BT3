Based on my investigation, I found a plausible domain-separation gap in GitHub Desktop's git trampoline credential mechanism, but I want to flag upfront that I could **not** fully verify whether Desktop sanitizes the environment passed to git hooks/filters (there is a `app/src/lib/hooks/with-hooks-env.ts` file I did not get to inspect before running out of iterations), so the exact reachability of the final trigger step is not 100% confirmed from the index alone.

### Title
Trampoline credential token has no binding to the requesting repository/remote, allowing any process that obtains the token+port to query the real GitHub credential for any known host - (File: `app/src/lib/trampoline/trampoline-tokens.ts`, `app/src/lib/trampoline/trampoline-server.ts`, `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Code4rena finding is about a hash/authorization value that omits a domain-separator (`chainId`), so a value valid in one context can be replayed in another. GitHub Desktop's local "trampoline" credential mechanism has the same structural gap: the `DESKTOP_TRAMPOLINE_TOKEN` that authorizes a request to the trampoline server is checked only for Set membership [1](#0-0)  and [2](#0-1) , with no binding to the specific git operation, repository, or requested host it was minted for. Anything presenting a currently-valid token to the local TCP server can invoke `CREDENTIALHELPER get` for an arbitrary host and receive the user's real GitHub/GHE token if one exists for that host.

### Finding Description
When Desktop spawns a git operation, it mints a random UUID trampoline token via `requestTrampolineToken`/`withTrampolineToken` [3](#0-2)  and injects it, along with the server's TCP port, into the child process environment as `DESKTOP_TRAMPOLINE_TOKEN` / `DESKTOP_PORT` [4](#0-3) .

The trampoline server's only authorization check for any inbound command (ASKPASS or CREDENTIALHELPER) is that the token exists in the flat, process-wide `trampolineTokens` set: [2](#0-1) 

There is no check that the command originated from the actual git subprocess it was issued to, nor that the requested credential host (`cred.get('host')`/`url`) corresponds to the repository/remote the user is actually operating on. The credential decision in `getCredential` is based solely on whether the requested URL's host looks like a known GitHub/GHE host and whether an account exists for it: [5](#0-4) 
and the GitHub account lookup itself matches purely by origin: [6](#0-5) 

So the "context" that should be bound into the authorization decision — which repository/session initiated the trampoline invocation, and what host that specific git process is legitimately talking to — is missing, analogous to the missing `chainId` in the original report's `getHash`. The token only tracks a `path` (cwd) and a `isBackgroundTask` flag via separate maps [7](#0-6) , neither of which is used to constrain which hosts/credentials can be returned for that token.

### Impact Explanation
If any code running as a child of (or otherwise able to read the environment of) a Desktop-spawned git process for one repository can read `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` (e.g., a git clean/smudge filter or hook declared in an attacker-controlled cloned/fetched repository, which git would execute as a subprocess and which by default inherits the parent git process's environment), that code can open its own connection to the trampoline server and issue a `CREDENTIALHELPER get` request for `https://github.com` (or the user's GHE endpoint) regardless of what repository or remote the token was actually minted for. Because the server's only check is `isValidTrampolineToken` (Set membership) [2](#0-1) , and `getGitHubCredential` returns the account's real token for any URL whose origin matches a signed-in account [8](#0-7) , this would exfiltrate the user's real GitHub OAuth token — from an untrusted/malicious repository the user merely cloned or fetched, satisfying the "credential/token exfiltration" impact category.

### Likelihood Explanation
I could not fully confirm the trigger step from the indexed code: whether Desktop deliberately strips `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` (or otherwise sandboxes environment) before running repository-controlled hooks/filters. I located `app/src/lib/hooks/with-hooks-env.ts` and `app/src/lib/hooks/get-repo-hooks.ts` but did not have a remaining iteration to read their contents, so I cannot confirm or rule out that this mitigation already exists. If such sanitization exists, the practical likelihood of this analog is significantly lower, since the underlying `isValidTrampolineToken`/host-matching gap would still exist but would no longer be reachable by an unprivileged repository-controlled process. This should be treated as **unconfirmed/medium-confidence** rather than a fully proven end-to-end exploit.

### Recommendation
Bind trampoline commands to the operation context they were issued for: track, per token, the specific remote/host (and/or repository) the token is valid for (similar to how `trampolineEnvironmentPath` already tracks a path), and reject `CREDENTIALHELPER`/`ASKPASS` requests whose target host doesn't match the expected remote for that token/operation. Additionally, verify (and if necessary fix) that any repository-controlled subprocess (git hooks, clean/smudge filters, LFS custom transfer agents) invoked during a Desktop git operation does not inherit `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT`.

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitattributes` entry that declares a smudge/clean filter executable (or a repository designed to be cloned with `--recurse-submodules`/hooks enabled).
2. Victim clones/fetches this repository in GitHub Desktop; Desktop spawns `git` with `DESKTOP_TRAMPOLINE_TOKEN` and `DESKTOP_PORT` in its environment [4](#0-3) .
3. If the filter/hook subprocess inherits this environment (unconfirmed — see Likelihood section), it reads the two variables and opens a raw TCP connection to `127.0.0.1:<DESKTOP_PORT>`, sending a `CREDENTIALHELPER get` command with `host=github.com`/`protocol=https` and the captured token, formatted per the trampoline wire protocol [9](#0-8) .
4. `trampolineServer.processCommand` accepts the request because the token is present in the flat `trampolineTokens` set [2](#0-1) , and `createCredentialHelperTrampolineHandler` → `getCredential` → `getGitHubCredential` returns the victim's real GitHub token for `github.com` [8](#0-7) .

function requestTrampolineToken() {

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}

  /**
   * Returns a command.
   *
   * It will return null if the parser hasn't finished yet, or if the identifier
   * is missing or invalid.
   **/
  public toCommand(): ITrampolineCommand | null {
    if (this.hasFinished() === false) {
      const error = new Error(
        'The command cannot be generated if parsing is not finished'
      )
      this.logCommandCreationError(error)
      return null
    }

    const identifierString = this.environmentVariables.get(
      'DESKTOP_TRAMPOLINE_IDENTIFIER'
    )

    if (identifierString === undefined) {
      const error = new Error(
        `The command identifier is missing. Env variables received: ${Array.from(
          this.environmentVariables.keys()
        )}`
      )
      this.logCommandCreationError(error)
      return null
    }

    const identifier = parseEnumValue(
      TrampolineCommandIdentifier,
      identifierString
    )

    if (identifier === undefined) {
      const error = new Error(
        `The command identifier ${identifierString} is not supported`
      )
      this.logCommandCreationError(error)
      return null
    }

    const trampolineToken = this.environmentVariables.get(
      'DESKTOP_TRAMPOLINE_TOKEN'
    )

    if (trampolineToken === undefined) {
      const error = new Error(`The trampoline token is missing`)
      this.logCommandCreationError(error)
      return null
    }

    return {
      identifier,
      trampolineToken,
      parameters: this.parameters,
      environmentVariables: this.environmentVariables,
      stdin: this.stdin,
    }
  }
