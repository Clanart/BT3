## Title
CW20 pointer for ERC20 tokens (`example/cosmwasm/cw20`) ignores ERC20 `transfer`/`transferFrom` boolean return value, allowing spoofed "successful" transfers - (File: `example/cosmwasm/cw20/src/contract.rs`)

### Summary
The CosmWasm CW20 pointer contract that wraps an arbitrary EVM ERC20 token (deployed via the `deployErc20PointerForCw20` / "ERC20 to CW20 Pointer" flow, backed by `example/cosmwasm/cw20`) builds its `transfer` and `transfer_from` messages as an `EvmMsg::DelegateCallEvm` and never inspects the boolean success value that the wrapped ERC20's `transfer`/`transferFrom` returns. Some ERC20 implementations legally return `false` on failure instead of reverting (the exact bug class from the referenced Footium report). Because neither the CosmWasm contract nor the underlying Go message handler decodes/validates that boolean, such a transfer is reported as fully successful (attributes + events emitted, tx succeeds) even though no value moved.

### Finding Description
`transfer()`/`transfer_from()` in `example/cosmwasm/cw20/src/contract.rs` construct the ERC20 call payload and dispatch it without any result validation: [1](#0-0) 

The message is queued with `add_message` (no `SubMsg`/`reply_on_success`), so the contract has no visibility into the ABI-encoded `bool` that `transfer`/`transferFrom` return.

On the chain side, `EvmMsg::DelegateCallEvm` is handled by `HandleInternalEVMDelegateCall` → `CallEVM`, which only surfaces an error when the EVM execution itself reverts (`res.Err`); the raw `ReturnData` (which encodes the ERC20's `bool`) is returned to the CosmWasm runtime but is not decoded or checked by the caller anywhere in this code path: [2](#0-1) [3](#0-2) 

Consequently, if the pointed-to ERC20 contract returns `false` instead of reverting on a failed transfer (a valid ERC20 pattern explicitly called out as in-scope — "the contracts should be compatible with all types of ERC20 tokens"), the CW20 pointer's `execute_transfer`/`execute_transfer_from` will still return `Ok(Response)` with `from`/`to`/`amount` attributes and a successful transaction, while the actual ERC20 balances are unchanged.

This directly contrasts with the reverse-direction pointer (`CW20ERC20Pointer.sol`, ERC20 wrapping CW20), which at least checks the `delegatecall` `success` flag (though it also doesn't validate CW20-specific error semantics beyond that): [4](#0-3) 

### Impact Explanation
Any user can register a CW20 pointer for an arbitrary ERC20 contract (including a purpose-built one that returns `false` on `transfer`/`transferFrom` instead of reverting). Once such a pointer exists, calling `transfer`/`transfer_from`/`send`/`send_from` on it will always emit success attributes/events and a successful transaction receipt regardless of whether the underlying ERC20 balance actually moved. Any downstream system (bridge, exchange, custodial deposit tracker, or another contract) that trusts CW20 execute success + emitted `from`/`to`/`amount` attributes as proof-of-transfer can be tricked into crediting value that was never actually transferred — a fund-loss/spoofed-transfer scenario via a Sei pointer contract, matching the "unauthorized transfer via pointer" impact category.

### Likelihood Explanation
Likelihood is high for any protocol/integration that relies on CW20 pointer contracts to move value backed by third-party or user-supplied ERC20 tokens, since:
- Pointer creation for arbitrary ERC20 addresses is permissionless (any pointer-user/RPC client action).
- Creating an ERC20 contract that returns `false` instead of reverting is trivial and standards-compliant.
- No special privileges are required to trigger the mismatch — a single `transfer`/`transferFrom` message against the pointer suffices.

### Recommendation
- In `example/cosmwasm/cw20/src/contract.rs`, wrap the `EvmMsg::DelegateCallEvm` for `transfer`/`transferFrom`/`approve` in a `SubMsg` with a reply handler, decode the returned ABI-encoded `bool`, and return `ContractError` if it is `false`.
- Alternatively/additionally, have `HandleInternalEVMDelegateCall`/`CallEVM` (or a wrapper used specifically for ERC20 pointer operations) decode the standard ERC20 return value and surface failure as an error rather than silently returning success data.
- Apply the same fix to `transfer_from`, `send`, `send_from`, and allowance operations that rely on ERC20 boolean returns.

### Proof of Concept
1. Deploy a malicious ERC20 contract on the Sei EVM whose `transfer`/`transferFrom` functions do not `require()` on balance/allowance checks, but instead compute the check and `return false` on failure (fully ERC20-spec-compliant behavior).
2. Register a CW20 pointer for this ERC20 contract (the `example/cosmwasm/cw20` pointer, deployed via the standard "ERC20 to CW20 Pointer" registration flow).
3. Call `transfer { recipient, amount }` on the CW20 pointer with an amount exceeding the sender's actual ERC20 balance (or from an account with no balance at all).
4. Observe: the CosmWasm transaction succeeds, `execute_transfer` returns `Ok` with `from`/`to`/`amount`/`action=transfer` attributes, and no error is raised — even though the underlying ERC20 `transfer` call returned `false` and no balance change occurred on the EVM side (verifiable via `balanceOf` on the ERC20 contract before/after).

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}
