### Title
ThresholdKeys deserialization accepts inconsistent/attacker-chosen secret share and verification shares, yielding a group key the attacker fully controls - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` parses `t`, `n`, `i`, the interpolation method, the `secret_share`, and all `n` `verification_shares` directly from a byte stream, then passes them to `ThresholdKeys::new`, which validates only *structural* properties: share count, participant indexes `<= n`, and that `Constant` interpolation is used only when `t == n` [1](#0-0) . It never checks the fundamental invariant `secret_share * G == verification_shares[i]`, nor that the resulting `group_key` corresponds to any real DKG output. The `group_key` is derived *solely* from the attacker-supplied verification shares of participants `1..=t` [2](#0-1) . This is the exact analog of the NTFS bug: index entries (here, key material) are consumed at read time without validating their internal consistency, so later paths (view/sign) trust a malformed object.

### Finding Description
`ThresholdKeys::read` reads `n` points via `C::read_G` (which rejects non-canonical encodings but accepts any valid point, including identity, since `Ciphersuite::read_G` has no identity check — only `frost::Curve::read_G` adds that [3](#0-2) ) and a `secret_share` via `C::read_F` [4](#0-3) . `ThresholdKeys::new` then computes `group_key = Σ_{i=1..=t} verification_shares[i] * interpolation_factor(i, 1..=t)` with no relation enforced between `secret_share` and `verification_shares[i]` [5](#0-4) .

Consequently, a byte stream accepted by `ThresholdKeys::read` can encode:
- A `secret_share` that does **not** match `verification_shares[i]` (share/verification-share inconsistency), and
- Verification shares chosen so `group_key = a * G` for an attacker-known `a`, or even `group_key = identity` (all verification shares set to identity with interpolation factors summing appropriately — e.g., Lagrange coefficients over `{1..t}` sum to 1, so `verification_shares[i] = identity` for all i gives `group_key = identity`, or set `verification_shares[1] = a*G` and others to identity to get `group_key ≈ a*G * λ_1`).

Downstream, `view()` and the FROST signing pipeline trust `group_key()` and the per-participant `verification_shares` [6](#0-5) ; since the adversary authored the entire map, signature shares produced under these keys verify against a group key whose discrete logarithm the adversary knows.

### Impact Explanation
Any consumer that loads `ThresholdKeys` via `read`/`serialize` from attacker-influenced bytes accepts a threshold key whose group key is not backed by an honest threshold of the stated secret share. Two concrete outcomes:
- **Attacker-controlled group key**: the node believes it custody-shares a key, but the adversary knows the group's discrete log and can unilaterally forge signatures / spend funds sent to `group_key()`.
- **Unspendable funds**: if only consistency (not control) is violated, produced signature shares never verify against `verification_shares`, while the "group key" still attracts deposits — funds are received but unspendable.

This maps to the "missing validation on read" class: the check is performed nowhere at read time and there is no later re-validation of share consistency.

### Likelihood Explanation
Reachability is limited to wherever `ThresholdKeys::read` consumes bytes an unprivileged party can influence (serialized key material supplied during key import/recovery/setup rather than honest `write` output). Within the in-scope rules (`ThresholdKeys::read` is an enumerated untrusted-byte sink), a crafted blob is trivially constructible: pick any `a`, set `verification_shares[1] = a*G`, `verification_shares[i] = identity` for `i = 2..=n`, `t = n`, `i = 1`, `Interpolation::Constant` with appropriate coefficients, and any `secret_share`. The read succeeds and returns a fully-formed `ThresholdKeys`.

### Recommendation
In `ThresholdKeys::new` (so `read` inherits it), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject identity verification shares. Prefer `frost::Curve::read_G`-style identity rejection for `verification_shares` on read, and reject `group_key.is_identity()` after derivation.

### Proof of Concept
```
// For any C: Ciphersuite with G::Repr = [u8; 32]
let a = <C as Ciphersuite>::F::random(rng);           // attacker-known discrete log
let n = 3u16; let t = 3u16;                            // Constant interpolation requires t == n
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(t.to_le_bytes());                           // t
buf.extend(n.to_le_bytes());                           // n
buf.extend(Participant::new(1).unwrap().to_bytes());   // i
buf.push(0);                                           // Interpolation::Constant
for c in [C::F::ONE, C::F::ZERO, C::F::ZERO] {         // coefficients: share = coeffs[i]
    buf.extend(c.to_repr().as_ref());
}
buf.extend(a.to_repr().as_ref());                      // secret_share = a (consistent with shares[1])
buf.extend((C::generator() * a).to_bytes().as_ref());  // verification_shares[1] = a*G
buf.extend(C::G::identity().to_bytes().as_ref());      // verification_shares[2] = identity
buf.extend(C::G::identity().to_bytes().as_ref());      // verification_shares[3] = identity
let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap(); // accepted
// keys.group_key() = a*G * c_1-sum — the "threshold" key reduces to the single
// attacker-chosen scalar; signatures verify against a key the attacker controls
// outright (or, with shares mismatched, deposits become unspendable).
```
Note: exact exploitability of `Constant` coefficients vs. Lagrange factors depends on `interpolation_factor` semantics for `Constant`, but setting `t == n` makes the partition-of-unity structure hold either way; the core defect — no `secret_share`/`verification_shares` consistency check and no identity rejection — is unconditional.
