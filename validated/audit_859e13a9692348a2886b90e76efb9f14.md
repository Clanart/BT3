### Title
Permanent, ownership-blind `safe.directory` trust grant lets an attacker who later gains write access to a previously-trusted repository path achieve code execution - (File: `app/src/lib/git/config.ts`)

### Summary
When Desktop detects a repository owned by a different OS user than the current process ("dubious ownership"), it shows a "Trust Repository" prompt. Accepting it calls `addSafeDirectory(path)`, which permanently whitelists the **path string** in the user's global Git configuration via `git config --global --add safe.directory <path>`. This whitelist entry is never removed or re-validated against the identity/ownership/content of the repository that currently lives at that path, similar to how `VotesGCByVault` in the report was never reset after a governance change, letting a stale approval silently re-authorize a different (and now untrusted) target.

### Finding Description
`addSafeDirectory` unconditionally appends the path to global config and never removes it: [1](#0-0) 

The safety check itself, `getRepositoryType`, only asks Git whether the *current* owner of the directory matches the process owner; it has no notion of "this is the same repository I trusted before" — it purely maps a path string to a "safe"/"unsafe" verdict via Git's own `safe.directory` lookup: [5](#0-4) 

The two UI entry points that call `addSafeDirectory` explicitly warn that untrusted repositories "may automatically execute files in the repository," acknowledging the code-execution risk that the ownership check exists to prevent, yet they only ask for consent once, keyed by path, with no expiry or re-validation: [6](#0-5) [7](#0-6) 

Because the trust decision is stored globally by path (not by repository identity, commit hash, or remote URL) and is never invalidated, any future change of ownership/content at that exact path — e.g., the folder is later deleted and repopulated by another local account, a shared/synced folder (Dropbox, network share, CI workspace, multi-user machine) is reused, or a symlink at that path is redirected — silently inherits the old trust decision. Git will no longer perform the dubious-ownership check for that path, so repository-local execution vectors (`core.fsmonitor`, `core.pager`, `.git/hooks` invoked by subsequent Desktop or `git` operations) execute without the safeguard or any renewed prompt to the user.

This is the direct structural analog of the audit finding: a security-relevant approval state (`VotesGCByVault[vault][guard]` / `safe.directory` entry) is written once to satisfy a check tied to a mutable target (`vault`'s governance / the directory's current owner and contents), and is never cleared when that target's trusted state changes, allowing the previous approval to silently re-apply to a new, untrusted target.

### Impact Explanation
Impact is Medium: exploitation requires the specific precondition that a path the user previously trusted becomes controlled by another (untrusted) local account or is repopulated with attacker content — this is realistic on shared machines, CI runners, synced/network folders, and containers/VMs where paths are reused across users/sessions, which is the exact scenario the dubious-ownership check is designed to defend against. When triggered, the result is silent execution of repository-controlled configuration/hooks without any renewed user consent, i.e., a bypass of a security control the user believes protects them "per repository."

### Likelihood Explanation
Likelihood is Medium: it does not require local malware or admin rights on the victim's own account — only that the reused path later comes under the control of a different, less-trusted party (a common real-world condition for shared directories, multi-tenant build agents, or restored/mounted volumes), consistent with the valid-impact scope where "attacker controls a cloned/fetched repository."

### Recommendation
Do not treat `safe.directory` trust as permanent/global-only. At minimum, re-validate trust at use-time rather than relying solely on Git's persisted global config, or scope/store the trust decision together with an identity of the specific repository (e.g., its initial `HEAD`/remote or an owner UID snapshot) and prompt again if that identity changes. Consider exposing a way for Desktop to remove entries via `git config --global --unset safe.directory <path>` when Desktop stops managing that repository (e.g., on remove-from-Desktop), and warn users if a previously trusted path's ownership changes again after having been trusted.

### Proof of Concept
1. On a shared machine (or in a container/CI workspace with reused workspace paths), User A clones/creates a benign repository at `/workspace/project`.
2. Due to a container restart, permission change, or synced-folder reassignment, `/workspace/project` becomes owned by a different account (attacker-controlled), and Desktop reports it as "potentially unsafe" the first time (`getRepositoryType` returns `{kind: 'unsafe'}`).
3. User clicks "Trust Repository" (`onTrustDirectory` in `app/src/ui/missing-repository.tsx`), which calls `addSafeDirectory('/workspace/project')`, permanently adding the path to the global `safe.directory` list.
4. Later, the attacker (who now owns/controls that same path, e.g., via the shared workspace) replaces the repository contents at `/workspace/project` with a malicious repo containing crafted `.git/hooks`, `core.fsmonitor`, or `core.pager` config.
5. Desktop/Git no longer flags the path as unsafe (the global `safe.directory` entry still matches the path), so no prompt is shown, and the attacker-controlled repository-local execution vectors run the next time Desktop or Git performs an operation in that directory — achieving code execution without the user ever consenting to trust *this* new content.

export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }
