### Title
Program ELF verification and JIT compilation cost is charged as a flat, size/complexity-independent compute-unit fee, allowing materially underpriced compute during program deployment and cache population - ([File: program-runtime/src/deploy.rs], [programs/bpf_loader/src/lib.rs], [svm/src/program_loader.rs])

### Summary
Deploying or upgrading a BPF Loader Upgradeable program charges a fixed `UPGRADEABLE_LOADER_COMPUTE_UNITS` (2,370 CU) regardless of the size or structural complexity of the ELF being loaded, verified (`RequisiteVerifier`), and JIT-compiled. The real CPU cost of these operations — timed and recorded only for observability in `LoadProgramMetrics`/`ExecuteDetailsTimings` (`create_executor_load_elf_us`, `create_executor_verify_code_us`, `create_executor_jit_compile_us`) — scales with ELF size/complexity up to `MAX_PERMITTED_DATA_LENGTH` (~10 MiB) but is never deducted from `invoke_context.compute_meter`. The same load/verify/JIT work also happens for free (zero CU) whenever `replenish_program_cache`/`load_program_with_pubkey` must populate a cold program-cache entry, since that occurs before any per-instruction compute metering.

### Finding Description
`process_instruction_inner` in `programs/bpf_loader/src/lib.rs:93-103` charges a single flat cost before invoking loader management logic: [1](#0-0) 

For `DeployWithMaxDataLen`/`Upgrade`, this flat `UPGRADEABLE_LOADER_COMPUTE_UNITS` (2,370 CU) is consumed once at the top of `process_loader_upgradeable_instruction` before the `deploy_program!` macro (which invokes `deploy_program` in `program-runtime/src/deploy.rs`) actually loads, verifies, and JIT-compiles the attacker-supplied ELF: [2](#0-1) [3](#0-2) 

None of these three timed phases (`load_elf_time`, `verify_code_time`, `jit_compile_time`) ever call `invoke_context.compute_meter.consume_checked(...)`; they only populate `LoadProgramMetrics`, which is later merged into `ExecuteDetailsTimings` purely for metrics/telemetry: [4](#0-3) 

The attacker-controlled input is the ELF bytes written into the buffer account via repeated `Write` instructions (each itself only charged a flat `DEFAULT_LOADER_COMPUTE_UNITS`/`UPGRADEABLE_LOADER_COMPUTE_UNITS`), up to `MAX_PERMITTED_DATA_LENGTH` bytes, as enforced in the `DeployWithMaxDataLen` handler: [5](#0-4) 

Because the sBPF verifier (`RequisiteVerifier`) and the x86_64 JIT compiler process instruction count/complexity (branches, jump targets, basic blocks) rather than a fixed cost, an attacker can construct a large, deeply-branching-but-still-valid ELF near the max permitted size that maximizes `verify_code_us`/`jit_compile_us`/`load_elf_us` while the transaction is charged the same fixed 2,370 CU as a trivial one-instruction program.

Separately, and more severely, whenever a program's cache entry has been evicted/unloaded and a subsequent *invoking* transaction misses the cache, `TransactionBatchProcessor::replenish_program_cache` calls `load_program_with_pubkey` (`svm/src/program_loader.rs:99-193`), which performs the identical `ProgramCacheEntry::new`/load+verify+JIT sequence: [6](#0-5) 

This happens in `load_and_execute_sanitized_transactions` *before* `execute_loaded_transaction` runs and *before* any instruction-level `compute_meter` accounting for that transaction begins — it is charged nothing at all, not even a flat fee, only contributing to `ExecuteTimingType::ProgramCacheUs` for telemetry.

### Impact Explanation
This is a case of materially underpriced/uncharged compute: real, size/complexity-scaling CPU work (ELF parsing, relocation, verification, and JIT compilation) performed by the leader/replaying validator is billed at a constant rate independent of the actual work performed, and in the program-cache-miss path is not billed at all. An attacker can deploy (and cause repeated cache-miss reloads of) maximally-sized, verifier/JIT-heavy-but-valid programs at minimal, size-independent CU/fee cost, causing the validator to spend disproportionate wall-clock CPU time relative to the CUs charged. This falls into the "materially underpriced compute" category that can degrade block production throughput/latency (a compute-DoS-adjacent issue) without violating any transaction-level compute limit, since the actual expensive work occurs outside the metered VM-execution accounting.

### Likelihood Explanation
Preconditions are trivial for any unprivileged user: fund a buffer account with a valid, adversarially-large/complex sBPF ELF (up to `MAX_PERMITTED_DATA_LENGTH`), write it in chunks, and issue `DeployWithMaxDataLen`/`Upgrade`. The only economic friction is the rent-exempt lamport cost of the buffer/programdata accounts and per-`Write` fees, not CU cost. Since deployment cost is a documented flat design choice in `programs/bpf_loader/src/lib.rs`, the bar to reproduce is low and fully repeatable; the main open question for exploit severity is how large the verify/JIT-time-to-CU ratio can practically be made for a valid ELF at the size cap, which is directly measurable via the existing metrics fields.

### Recommendation
Introduce compute charges (or at least a per-byte/per-instruction-count surcharge) for the `load_elf`, `verify`, and `jit_compile` phases performed in `deploy_program`/`ProgramCacheEntry::new_internal`, scaled to ELF size and/or instruction/basic-block count, and deduct them via `invoke_context.compute_meter` at deployment time. For the program-cache-miss path (`load_program_with_pubkey`/`replenish_program_cache`), consider either pre-charging a size-scaled fee against the invoking transaction, or bounding/caching aggressively enough that cold-cache reload frequency cannot be weaponized, and add telemetry-driven alerting/limits so `create_executor_verify_code_us`/`create_executor_jit_compile_us` cannot grow unboundedly relative to charged CU.

### Proof of Concept
Rust benchmark/integration-test plan (extends existing `svm_metrics_accumulation` style tests in `svm/tests/integration_test.rs`):
1. Generate a corpus of valid sBPF ELFs of increasing size/complexity (e.g., increasing count of unique basic blocks/branches) up to near `MAX_PERMITTED_DATA_LENGTH`, using the existing test-ELF assembly tooling (`ledger-tool/src/program.rs`'s `assemble` helper or `test_elfs`).
2. For each ELF, drive a `DeployWithMaxDataLen` transaction through `TransactionBatchProcessor::load_and_execute_sanitized_transactions` (as in `svm/tests/integration_test.rs::svm_metrics_accumulation`), and record:
   - Charged CU (fixed `UPGRADEABLE_LOADER_COMPUTE_UNITS` = 2,370, verifiable via `execute_timings`/transaction return).
   - `execute_timings.details.create_executor_load_elf_us`, `create_executor_verify_code_us`, `create_executor_jit_compile_us` (populated per `program_metrics.rs::submit_datapoint`).
3. Assert the ratio `(load_elf_us + verify_code_us + jit_compile_us) / charged_CU` grows with ELF size/complexity and is unbounded relative to a fixed `COST_UPPER_BOUND`, while `charged_CU` remains constant at 2,370 across all sizes — demonstrating the underpricing.
4. Separately, evict a deployed program's cache entry (or simulate a new batch after unload) and re-invoke it; assert `execute_timings.details.create_executor_*` fields are non-zero for that invoking transaction while the transaction's own charged CU reflects only its own instruction cost with zero contribution from cache-repopulation work.
