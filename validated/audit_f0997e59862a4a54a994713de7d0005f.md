### Title
`ReceivedOutput::read` accepts a scalar offset without binding it to the output's `script_pubkey`, allowing attacker-supplied bytes to claim arbitrary outputs as spendable by Serai's key - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to the DRF `AdminRenderer` flaw — where a secondary rendering path invoked the privileged `view.get` handler while bypassing `check_permissions` — Serai's Bitcoin wallet has two paths that produce a `ReceivedOutput`. The trusted path (`Scanner::scan_transaction`) *derives* the spend offset by matching `output.script_pubkey` against the registered script table, so the returned `offset` is cryptographically bound to the key that actually controls the output. The deserialization path (`ReceivedOutput::read`) skips that binding entirely: it accepts any scalar `offset` and any `TxOut`/`OutPoint` from untrusted bytes, returning an object the rest of the wallet treats as "a spendable output we control."

### Finding Description
`scan_transaction` only emits a `ReceivedOutput` when the output's script is present in `self.scripts`, and stores the offset that generated that script (`networks/bitcoin/src/wallet/mod.rs:199-214`). This is the equivalent of DRF's normal request path through `APIView.check_permissions`: the offset↔script binding is the authorization check proving the wallet can spend the output.

`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) performs only structural decoding:

- `Secp256k1::read_F(r)` — any scalar, unchecked against the wallet key
- `TxOut::consensus_decode` / `OutPoint::consensus_decode` — any output, including script_pubkeys that don't correspond to `key + G·offset` or that Serai doesn't control at all

There is no equivalent of `p2tr_script_buf(self.key + G·offset) == output.script_pubkey`. The scanner path's permission check (membership in `self.scripts`) is structurally unreachable from `read`, exactly as `check_permissions` was unreachable from `AdminRenderer`'s direct `view.get(...)` call.

### Impact Explanation
`ReceivedOutput` values feed `SignableTransaction::new`, which tweaks each input's key by `output.offset()` and produces a per-input FROST signing context (`networks/bitcoin/src/wallet/send.rs`, exercised via `tx.multisig(&keys[i])` in `networks/bitcoin/tests/wallet.rs:89-98`). With a forged `ReceivedOutput`:

1. An output paying a third party (or a script derived from a different offset) is reported as received and spendable — the accepted "funds reported received that are not spendable" impact. The wallet signs with `secret + offset` against a script the tweaked key doesn't control, yielding an invalid witness.
2. Because inputs are batched, one poisoned `ReceivedOutput` causes the entire signed transaction to be rejected by the Bitcoin network, stalling the batch/co-signing flow for every legitimate input in it — a reachable denial of service on withdrawals triggered purely by untrusted bytes, with no valid-serialization precondition (the bytes decode fine; only the skipped semantic check would have rejected them).

### Likelihood Explanation
`ReceivedOutput::read` is a public `std`-feature API explicitly designed to ingest serialized bytes, and any consumer deserializing outputs obtained over a channel an unprivileged party can influence (network gossip, recovery data, RPC-fetched payloads) is exposed. The attacker needs only to emit well-formed consensus-encoded bytes — no validator status, no key material, no collusion. The mismatch is silent: nothing downstream re-derives the script from the offset before signing, so detection only occurs when the broadcast transaction fails.

### Recommendation
Bind the offset to the output at the trust boundary. Either:

- Make `read` fallible in the cryptographic sense: require the caller's wallet key and verify `p2tr_script_buf(key + G·offset) == output.script_pubkey`, rejecting on mismatch (mirroring the fix of performing permission checks before the simulated GET), or
- Store/derive only the script→offset association produced by `Scanner` and rebuild `ReceivedOutput` from scanned data rather than trusting a serialized offset — the analog of "render only validation errors instead of retrieving the GET representation."

### Proof of Concept
```rust
// Attacker constructs bytes for an output Serai does NOT control,
// paired with an arbitrary offset.
let mut buf = Vec::new();
// offset = 1
buf.extend(Scalar::ONE.to_bytes());
// TxOut paying someone else's script_pubkey, arbitrary value
let foreign = TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: ScriptBuf::new_p2tr_tweaked(
        TweakedPublicKey::dangerous_assume_tweaked(attacker_xonly),
    ),
};
buf.extend(serialize(&foreign));
buf.extend(serialize(&OutPoint::new(victim_txid, 0)));

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// Succeeds: no check that p2tr_script_buf(key + G*forged.offset())
//           == forged.output().script_pubkey
// SignableTransaction::new(vec![forged], ...) would include an input
// the multisig cannot actually spend, invalidating the whole TX.
```
