## Finding

The bug-report's core issue is "the app grants broad, persistent trust (an unlimited allowance) based on a claim it never independently verifies, and that trust is later spent by another privileged operation." In GitHub Desktop this same broken-invariant pattern shows up in the trampoline credential helper's host-classification logic, which decides whether a host is treated as a real GitHub identity provider based purely on an attacker-controlled HTTP response header, and that classification later drives the branded "Sign in to GitHub" OAuth flow (with Desktop's own OAuth `client_id`/`client_secret`).

### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub identity and triggers OAuth flow / credential-secret exfiltration to an untrusted host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
When Git performs an HTTPS operation and gets an authentication challenge, it forwards the server's `WWW-Authenticate` header(s) to Desktop's credential helper as `wwwauth[]` entries. `getEndpointKind()` trusts the `realm=` value in that header to decide the remote is a GitHub Enterprise host, without verifying the host is actually GitHub-affiliated, and `getCredential()` then invokes the full "Sign in to GitHub" OAuth flow against that host.

### Finding Description
`getEndpointKind()` classifies an unknown HTTPS remote as `'enterprise'` purely because it echoes a server-supplied realm string: [1](#0-0) 

This check runs before any real verification such as `isGitHubHost(endpoint)`, which is only reached if the header-based heuristic didn't already match: [2](#0-1) 

`getCredential()` then treats any non-`'generic'` endpoint that isn't already a known account as GitHub-worthy of a sign-in prompt: [3](#0-2) 

If the user completes the resulting sign-in ("this looks like a legitimate GitHub Enterprise prompt"), the OAuth authorize URL is built directly from the attacker's `endpoint` and opened in the system browser using Desktop's real `client_id`: [4](#0-3) 

When the browser redirects back with a code, Desktop exchanges it by POSTing Desktop's embedded `client_id` **and `client_secret`** to that same attacker-controlled `endpoint`: [5](#0-4) [6](#0-5) 

The broken invariant: the decision to treat a host as a "GitHub identity provider" eligible for the OAuth `client_id`/`client_secret` flow is derived from unauthenticated, attacker-supplied response content (`WWW-Authenticate: realm="GitHub"`) rather than from a verified GitHub domain allowlist or TLS-pinned identity — the exact "unlimited/unchecked trust extension" pattern described in the source report, just expressed as identity trust instead of token allowance.

### Impact Explanation
A malicious HTTPS git remote/proxy (attacker controls the server the user is fetching/cloning/pushing to) can:
1. Trigger a fake "Sign in to GitHub" prompt for its own domain, phishing the user's real GitHub credentials via a browser page it fully controls (`endpoint`'s `/login/oauth/authorize`).
2. Cause Desktop to POST its embedded OAuth `client_secret` to the attacker's server during token exchange — leaking a credential/secret shared across all Desktop installs, and enabling unauthorized OAuth usage of Desktop's app identity.

This matches the "Valid Impact" categories: attacker-controlled git remote/proxy response leading to unauthorized OAuth flow and credential/token exfiltration, with no local access, admin rights, or social engineering beyond the user performing a normal git operation (fetch/clone/push) against a repository they added.

### Likelihood Explanation
Reaching this path only requires the victim to add or interact with a remote pointing at an attacker-controlled HTTPS server (a very ordinary Desktop action — cloning any repo whose remote is attacker-controlled, or a repo where the origin was later changed). No certificate pinning, domain allowlist, or TLS verification of "is this really GitHub" is performed before entering the `'enterprise'` branch — only a string match on a header the attacker's server produces at will. The `isGitHubHost` real check is bypassed entirely once the `wwwauth[]` heuristic matches.

### Recommendation
Do not classify a host as GitHub/Enterprise based on `WWW-Authenticate` realm content alone. Require this heuristic to be corroborated by an independent, authenticated check (e.g., `isGitHubHost()`/API probe against a known-good GitHub API path with certificate validation) before offering the "Sign in to GitHub" OAuth flow, and never construct OAuth authorize/token-exchange URLs from a remote-supplied endpoint without that verification.

### Proof of Concept
1. Attacker stands up an HTTPS git server at `https://evil.example.com/repo.git` that, on an unauthenticated request, responds with `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this as a remote/clones/fetches it in GitHub Desktop.
3. Git forwards the header to the credential helper; `getEndpointKind()` returns `'enterprise'` for `evil.example.com` per `app/src/lib/trampoline/trampoline-credential-helper.ts:159-160`.
4. Since no account exists for that endpoint, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com')`.
5. User clicks "Sign in", `authenticateWithBrowser()` opens `getOAuthAuthorizationURL('https://evil.example.com', state)`, i.e. `https://evil.example.com/login/oauth/authorize?client_id=<real_id>&scope=repo+user+workflow&state=...`, which the attacker's server fully controls and can use to phish for real GitHub credentials or capture the `code`.
6. If the attacker returns a `code` via the `x-github-client://oauth` deep link, `resolveOAuthRequest()` calls `requestOAuthToken('https://evil.example.com', code)`, which POSTs `client_id` and `client_secret` to `https://evil.example.com/login/oauth/access_token` per `app/src/lib/api.ts:2370-2386`.

Note: I could not execute this end-to-end in a live Desktop instance (no runtime/browser access here); the analysis is based on static code tracing of the cited functions and their call chain. If further confirmation is needed (e.g., exact behavior of `parseCredential`/`wwwauth[]` population from Git's credential-fill protocol, or whether any additional caller-side allowlist exists), a Devin session with repo checkout and the ability to run Desktop against a controlled git server would be needed to fully validate exploitability end-to-end.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
