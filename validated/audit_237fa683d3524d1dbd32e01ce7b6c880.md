### Title
Stale OS-keychain token retained for previous account after switching GitHub.com/Enterprise accounts on the same endpoint - (`app/src/lib/stores/accounts-store.ts`)

### Summary
This is the closest structural analog to the AmoManager bug: a "replace the active credential holder without revoking the previous holder's access" pattern. In `AccountsStore.addAccount`, a new account's token is written to the OS keychain, but the previous account's token for the same endpoint is only removed if a separate, explicit `removeAccount` call happens first. Several code paths can add/replace an account for an endpoint without ever calling `removeAccount` on the account that is being displaced.

### Finding Description
`AccountsStore` persists tokens in the OS keychain (`TokenStore`, backed by `keytar`) keyed by `getKeyForAccount(account)`, which resolves to `getKeyForEndpoint(account.endpoint)` — i.e., the keychain *service* name is derived purely from the endpoint (`"GitHub - <endpoint>"`), not from the login: [1](#0-0) 

Within that service, `keytar` entries are further keyed by `account.login`: [2](#0-1) 

`addAccount` writes the new account's token under `(service=key(endpoint), account=newLogin)` but never deletes any previously stored token under `(service=key(endpoint), account=oldLogin)`: [3](#0-2) 

The in-memory/`localStorage` account list is deduplicated **by endpoint** (one account object per endpoint), so once a new account replaces the old one in `this.accounts`, the app has no reference to the old login and can never call `removeAccount` for it again: [4](#0-3) 

The only code path that proactively removes the *old* account's keychain entry before adding a new one is `SignInStore.authenticateWithBrowser`, and only when the store is already in the `ExistingAccountWarning` step (i.e., the UI explicitly warned the user and they chose "sign in anyway"): [5](#0-4) 

However, `removeAccount` itself only deletes the keychain entry for the **exact `account.login` passed in** — it does not enumerate or purge all logins under that endpoint's keychain service: [6](#0-5) 

So even the "correct" flow only cleans up the one account object currently held in memory. If a user has ever authenticated with login A on an endpoint, then later re-authenticates that same endpoint with login B via any path that does not pass the exact stale `Account(A)` object into `removeAccount` first (for example, `resolveOAuthRequest` completing an OAuth deep-link callback that was not preceded by the `ExistingAccountWarning` flow, a stale/duplicated in-memory account no longer matching what's on disk, or account IDs changing across a GHE migration handled by `getMigratedGHEAccounts`), login A's token is left behind in the OS keychain under `GitHub - <endpoint>` / `A`, orphaned and unreachable by any subsequent `removeAccount` call, since the app's account list now only holds account B.

### Impact Explanation
An orphaned but still-valid OAuth token sits permanently in the user's OS keychain, invisible to GitHub Desktop's UI (Preferences > Accounts only shows the current account per endpoint) and therefore never revoked via `deleteToken`, which calls the GitHub `DELETE /applications/:client_id/token` revocation endpoint: [7](#0-6) 

Since the user is never shown that account A's credentials remain live, they have no way to know they need to manually revoke the token from github.com's settings. If the machine, keychain, or a backup of it is later compromised, or if another process/extension queries the OS keychain, the leftover token grants full account access (repo read/write, depending on OAuth scope) even though the user believes they've fully "switched off" that account in Desktop.

### Likelihood Explanation
This requires no attacker action beyond normal user behavior (switching accounts on the same GitHub.com/GHE endpoint), which is an unprivileged, commonly performed action. It relies purely on local application logic gaps rather than any external attacker input, so likelihood of the corrupted state occurring is driven by everyday user account-switching, and its severity is capped by the fact that it needs a *separate* compromise of the token store to be exploited (comparable in structure to the original finding, where "keeping stale approvals" is a latent risk multiplier rather than a directly triggerable drain).

### Recommendation
When adding an account for an endpoint that already has a different account associated with it, explicitly delete the keychain entry for the outgoing login before or as part of `addAccount`, rather than relying on a separate UI-driven `removeAccount` call:

```ts
public async addAccount(account: Account): Promise<Account | null> {
  await this.loadingPromise

  // Revoke/erase any previously stored credential for this endpoint under a
  // different login before persisting the new one.
  const existing = this.accounts.find(a => a.endpoint === account.endpoint)
  if (existing && existing.login !== account.login) {
    try {
      await this.secureStore.deleteItem(getKeyForAccount(existing), existing.login)
    } catch (e) {
      log.error(`Error clearing stale credential for '${existing.login}'`, e)
    }
  }

  try {
    const key = getKeyForAccount(account)
    await this.secureStore.setItem(key, account.login, account.token)
  } catch (e) { /* ... */ }
  // ...
}
```

Additionally, ensure every account-replacement code path (OAuth deep-link completion, enterprise re-auth, GHE endpoint migration) funnels through this single point so no route can add an account without cleaning up a prior login for the same endpoint.

### Proof of Concept
1. Sign in to GitHub.com in Desktop as `userA`. `AccountsStore.addAccount` stores the token under keychain service `GitHub - https://api.github.com`, account `userA`.
2. Sign out is *not* performed via the UI's explicit "remove account" action; instead, the user re-authenticates directly (e.g., via a deep-link OAuth callback resolved through `resolveOAuthRequest`, bypassing the `ExistingAccountWarning`/`removeAccount` step that only exists in `authenticateWithBrowser`).
3. `_addAccount(userB)` → `AccountsStore.addAccount` runs, storing `userB`'s token under the same keychain service, and overwrites `this.accounts` map entry keyed by endpoint with `userB` only: [8](#0-7) 
4. `userA`'s keychain entry (`GitHub - https://api.github.com` / `userA`) is never touched — it is not visible in `this.accounts` anymore, so no future `removeAccount` call can target it.
5. Inspecting the OS keychain (e.g., macOS Keychain Access, searching for "GitHub - https://api.github.com") shows two live password entries — one for `userA` and one for `userB` — with `userA`'s OAuth token still fully valid and never revoked via `deleteToken`.

  public async addAccount(account: Account): Promise<Account | null> {
    await this.loadingPromise

    try {
      const key = getKeyForAccount(account)
      await this.secureStore.setItem(key, account.login, account.token)
    } catch (e) {
      log.error(`Error adding account '${account.login}'`, e)

      if (__DARWIN__ && isKeyChainError(e)) {
        this.emitError(
          new Error(
            `GitHub Desktop was unable to store the account token in the keychain. Please check you have unlocked access to the 'login' keychain.`
          )
        )
      } else {
        this.emitError(e)
      }
      return null
    }

    const accountsByEndpoint = this.accounts.reduce(
      (map, x) => map.set(x.endpoint, x),
      new Map<string, Account>()
    )
    accountsByEndpoint.set(account.endpoint, account)

    this.accounts = sortAccounts([...accountsByEndpoint.values()])

    this.save()
    return account
  }

export async function deleteToken(account: Account) {
  try {
    const creds = Buffer.from(`${ClientID}:${ClientSecret}`).toString('base64')
    const response = await request(
      account.endpoint,
      null,
      'DELETE',
      `applications/${ClientID}/token`,
      { access_token: account.token },
      { Authorization: `Basic ${creds}` }
    )

    return response.status === 204
  } catch (e) {
    log.error(`deleteToken: failed with endpoint ${account.endpoint}`, e)
    return false
  }
}
