Based on my research, I found a directly analogous bug class in the Kaia governance parameter validation logic.

### Title
Missing bounds/sign validation on `reward.mintingamount` governance parameter enables unbounded token supply inflation - (File: kaiax/gov/param.go)

### Summary
The `EmergencyProposer` report describes a bug class where a critical protocol parameter setter (`setQuorum`/`setMinimumWaitTime`) lacks bounds validation, allowing the mechanism to be rendered unsafe or useless when an out-of-range value is accepted. The Kaia `kaiax/gov` package exhibits the same bug class for the `reward.mintingamount` governance parameter: unlike sibling reward parameters, it accepts any value with no bound or sign check, so a governance vote that sets an absurdly large (or negative) minting amount is accepted without validation and is applied to per-block token minting.

### Finding Description
Every governance parameter in `kaiax/gov/param.go` is validated by a `Canonicalizer` (type conversion) and a `FormatChecker` (semantic bounds check) before being accepted into the `ParamSet`, e.g. `RewardMinimumStake` and `RewardStakingRewardThreshold` both enforce `v.Sign() >= 0`: [1](#0-0) [2](#0-1) 

However, `RewardMintingAmount` — the amount of native token minted as block reward every block — uses `noopFormatChecker`, which unconditionally returns `true` and performs no validation at all: [3](#0-2) [4](#0-3) 

The value is only converted via `bigIntCanonicalizer`, which merely parses the string/bytes into a `*big.Int` without any range or sign restriction: [5](#0-4) 

This is accepted through the standard governance-vote pipeline (`PartialParamSet.Add`), which only rejects a value if `FormatChecker` returns false — which it never does here: [6](#0-5) 

Once accepted into `header.Governance` at an epoch block (per `VerifyGov`/`checkConsistency` in `headergov/impl/header.go`, which treats `RewardMintingAmount` as one of the votes requiring "no more checks here" beyond `NewVoteData()`'s format check), the value becomes the canonical `ParamSet.MintingAmount` used by all nodes for reward distribution: [7](#0-6) [8](#0-7) 

### Impact Explanation
`MintingAmount` directly drives the amount of new native token minted at every block as part of the block reward distribution (via `kaiax/reward`). Since no upper bound is enforced anywhere in the acceptance pipeline (`Canonicalizer` → `FormatChecker` → `ParamSet.Set`), an incorrectly or maliciously set `reward.mintingamount` value would cause the chain to mint an arbitrarily large amount of native token on every subsequent block — a direct, ongoing supply-inflation event that inflates the token beyond any economically intended amount, silently diluting all holders. This is a direct analog to the reported bug class: an unvalidated economic-critical parameter setter that can silently break the invariants the mechanism (block reward economics) depends on.

### Likelihood Explanation
The parameter is set through the standard, always-available on-chain governance vote mechanism (header-based governance voting), which is an explicitly in-scope "governance parameters" pathway. No special validator or contract-owner privilege beyond normal governance participation is required to propose the vote value; the vulnerability is that once such a vote succeeds (accidentally or through compromised/malicious governance), there is no software-level safety net (unlike similarly-typed sibling parameters `RewardMinimumStake`/`RewardStakingRewardThreshold`, which do enforce non-negativity). This mirrors the reported issue precisely: the underlying report is about lack of defense-in-depth validation on economically critical setters, not about the initial privilege needed to call the setter.

### Recommendation
Add a `FormatChecker` for `RewardMintingAmount` (and audit other `noopFormatChecker`-using economic parameters such as `Kip71GasTarget`) that enforces:
- `v.Sign() >= 0` (reject negative amounts), and
- an upper bound relative to a sane maximum per-block issuance (e.g., a hard cap consistent with tokenomics), consistent with the pattern already used for `RewardMinimumStake` and `RewardStakingRewardThreshold`.

### Proof of Concept
1. A governance participant casts a vote (`headergov.NewVoteData(voter, "reward.mintingamount", "<huge or negative number as string>")`).
2. `NewVoteData` / `PartialParamSet.Add` accepts the value because `bigIntCanonicalizer` only checks it parses as a valid base-10 integer, and `noopFormatChecker` always returns `true`. [5](#0-4) [6](#0-5) 
3. `checkConsistency` in `headergov/impl/header.go` performs no additional state-based validation for `gov.RewardMintingAmount`, letting the vote pass into the epoch's governance data. [7](#0-6) 
4. From the next epoch onward, `ParamSet.MintingAmount` reflects the unvalidated value and is used by the reward distribution logic for every block, minting the attacker/error-controlled amount of new native token perpetually.

func (p PartialParamSet) Add(name string, value any) error {
	param, ok := Params[ParamName(name)]
	if !ok {
		return ErrInvalidParamName
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		return err
	}

	if !param.FormatChecker(cv) {
		return ErrInvalidParamValue
	}

	p[ParamName(name)] = cv
	return nil
}
