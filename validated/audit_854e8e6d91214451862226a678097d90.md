### Title
Identity encryption keys in PedPoP DKG produce a publicly-known ECDH secret, exposing secret shares to any observer - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Like CVE-2021-36158 (pre-generated keys allowing anyone to decrypt sessions), the PedPoP DKG accepts the identity point as an encryption key in both directions of its ECDH-based share encryption. Because `EncryptionKeyMessage::read` and `EncryptedMessage::read` use `Ciphersuite::read_G`, which does not reject identity (only FROST's `Curve::read_G` adds an identity check on top), an attacker can force the ECDH shared point to the identity element. The ChaCha20 key is then derived from a publicly-known input (`transcript(context, identity.to_bytes())`), so the "encrypted" secret share is readable by anyone observing the wire — a pre-known shared key, exactly the "known private key ⇒ MITM decryption" class.

### Finding Description
- `EncryptionKeyMessage::read` reads `enc_key` via `C::read_G` (the `Ciphersuite` trait method), with no identity rejection — `crypto/dkg/pedpop/src/encryption.rs:57-59`. FROST's `Curve::read_G` explicitly rejects identity *because* the base `Ciphersuite::read_G` does not — `crypto/frost/src/curve/mod.rs:123-131`.
- `Decryption::register` stores whatever `enc_key` a participant registered, unchecked — `crypto/dkg/pedpop/src/encryption.rs:351-362`.
- `encrypt` computes `ecdh(&key, to)` where `to` is that registered `enc_key`; if it is identity, the shared point is identity — `encryption.rs:95-97,154`.
- Symmetrically, `EncryptedMessage::read` reads the per-message `key` via `C::read_G` with no identity check — `encryption.rs:171-177`. The attached Schnorr PoP does not save it: with `key = identity`, `SchnorrSignature::verify` reduces to `s·G == R` (since `c·identity = 0`), and `sign` with private scalar 0 yields `s = nonce`, `R = nonce·G`, which passes — `encryption.rs:479-485` verifies only the PoP before `ecdh(&self.enc_key, msg.key)` at `encryption.rs:487-488`.
- `cipher` derives the ChaCha20 key solely from `transcript(context || shared_key_bytes)` with a static IV — `encryption.rs:101-133`. With `shared_key = identity.to_bytes()` (a public constant), the keystream is computable by any eavesdropper.

Two reachable attack variants for an unprivileged DKG participant:
1. Register `enc_key = identity` in the round-1 `EncryptionKeyMessage`; every honest sender then encrypts that participant's share under a publicly derivable key.
2. Send an `EncryptedMessage` with `key = identity` plus a trivially valid PoP (private scalar 0); the victim decrypts with a public keystream and the ciphertext is plaintext to all observers, while still passing the blame/PoP checks.

### Impact Explanation
Secret shares transmitted during key generation are decryptable by any passive observer, yielding recovery of a participant's key share without breaking any cryptographic primitive — the confidentiality of the DKG relies entirely on the ECDH secret being unknown, and identity makes it a constant. This matches the CVE class: a "key" known to the adversary makes the channel protection void.

### Likelihood Explanation
Any DKG participant (or anyone able to inject a DKG message into the authenticated channel carrying `EncryptedMessage`s) can trigger it with public inputs only; no collusion or validator privilege is needed. One caveat: group-key cancellation is not achieved — the leaked share still fails share verification unless the sender is honest, so the concrete outcome is confidentiality loss of a share rather than a forged key. If the attacked share belongs to an honest dealer's polynomial, the attacker recovers a share contributing to the final `ThresholdKeys` — i.e., key-share recovery, an accepted impact.

### Recommendation
Reject the identity point in `EncryptedMessage::read` and `EncryptionKeyMessage::read` (e.g., use an identity-checking `read_G` or add `if res.is_identity() { Err(...) }`), and assert non-identity on registered `enc_key`s in `Decryption::register`. Also consider rejecting `enc_key`/message `key` equal to the identity inside `encrypt`/`decrypt` as defense in depth.
