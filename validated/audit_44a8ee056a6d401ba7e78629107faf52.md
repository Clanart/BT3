### Title
Missing linear vesting enforcement lets full airdrop amount be claimed instantly at `startVestingTime` - ([File: rewards/ArbitrumMWomAirdrop.sol])

### Summary
`ArbitrumMWomAirdrop` declares `vestingPeriodCount` and `intervals` state variables implying a gradual/linear vesting release schedule, but `_getClaimable` never uses them to compute a time-proportional vested amount. Instead it unconditionally sets `vested = totalAmount`, making the `if (vested > totalAmount)` check permanently dead code, so any eligible claimant can withdraw 100% of their allotted `totalAmount` in a single `claim()` call the moment `block.timestamp >= startVestingTime`.

### Finding Description
`getClaimable`/`claim` both route through `_getClaimable`: [1](#0-0) 

```solidity
function _getClaimable(address account, uint256 totalAmount) internal view returns (uint256) {
    uint256 claimed = getClaimed(account);
    if (claimed >= totalAmount) {
        return 0;
    }

    uint256 vested = totalAmount;
    if (vested > totalAmount) {
        return totalAmount - claimed;
    }

    return vested - claimed;
}
```

`vested` is assigned `totalAmount` directly, with no reference to `startVestingTime`, `vestingPeriodCount`, or `intervals`. Since `vested` always equals `totalAmount`, the `vested > totalAmount` branch can never be true — it is unreachable dead code — and the function always returns `totalAmount - claimed`. Any address with a valid Merkle leaf (`account`, `totalAmount`) can call `claim(totalAmount, merkleProof, false, false)` as soon as `block.timestamp >= startVestingTime` (enforced by the `require` in `claim`) and immediately receive the entire `totalAmount` in one transaction: [2](#0-1) 

No modifier, reward-index update, or time-proportioning logic in `claim()` or `_getClaimable` restricts the payout to a per-interval fraction; `whenNotPaused`/`nonReentrant` guard against pausing/reentrancy only, not against premature full claim. The `vestingPeriodCount`/`intervals` variables are set in the constructor comments/state but are otherwise unused in this contract, confirming they were intended to gate a gradual release that was never implemented.

### Impact Explanation
This breaks the documented/intended vesting invariant: the protocol distributes its airdropped reward token on a schedule presumably chosen to manage market impact, retention incentives, or matched liquidity/lock-up commitments. Because the whole allocation is claimable in one transaction, any recipient can bypass the intended linear vesting and receive/dump their full allocation immediately, defeating the purpose of `vestingPeriodCount`/`intervals` and constituting a loss of the intended time-locked ("unclaimed yield") vesting mechanism at the contract level (Immunefi class: theft/premature release of unclaimed yield due to broken vesting logic).

Note: this does not let an attacker steal funds belonging to other Merkle-tree entries — a claimant can only ever draw their own allotted `totalAmount`, which the protocol has already earmarked for them via the Merkle root. The economic harm is that the vesting schedule the protocol relies on (to stagger token release) is entirely non-functional, not that principal is stolen from other users.

### Likelihood Explanation
Trivial to trigger: any address with a valid Merkle proof (i.e., an already-designated recipient of the airdrop) can call `claim()` a single time at or after `startVestingTime` with no special capital, front-running, or privileged role required. This is 100% reproducible for every eligible claimant, every time.

### Recommendation
Implement actual time-based vesting in `_getClaimable`, e.g. compute elapsed intervals since `startVestingTime` using `intervals`/`vestingPeriodCount` and cap `vested` at `totalAmount * min(elapsedIntervals, vestingPeriodCount) / vestingPeriodCount`, then return `vested - claimed`. Remove the dead `if (vested > totalAmount)` branch since it can never trigger under correct logic (it would only be reachable if vesting computation could exceed `totalAmount`, which should be clamped explicitly instead).

### Proof of Concept
Foundry test plan:
1. Deploy `ArbitrumMWomAirdrop` with `vestingPeriodCount = 10`, `intervals = 30 days`, `startVestingTime = block.timestamp + 1 days`, and a Merkle root containing a leaf for `(alice, 1000e18)`.
2. Fund the contract with `reward` tokens ≥ 1000e18.
3. Warp to exactly `startVestingTime`.
4. As `alice` (no special privileges), call `claim(1000e18, proof, false, false)`.
5. Assert `reward.balanceOf(alice) == 1000e18` (100% of `totalAmount`) immediately at `t = startVestingTime`, i.e., with zero elapsed vesting intervals.
6. Assert this contradicts an expected linear schedule where, at `t = startVestingTime` with 0 of `vestingPeriodCount` intervals elapsed, claimable should be `0` (or `totalAmount / vestingPeriodCount` after one interval), demonstrating the vesting schedule implied by `vestingPeriodCount`/`intervals` is never enforced.

    function claim(
        uint256 totalAmount,
        bytes32[] calldata merkleProof,
        bool isStake,
        bool isLock
    ) external whenNotPaused nonReentrant {
        require(block.timestamp >= startVestingTime, "ArbitrumMWomAirdrop: Drop dose not start.");
        // isStake & isLock cannot be true at the same time
        require(!(isStake && isLock), "ArbitrumMWomAirdrop: Operation error.");
        //Verify the merkle proof.
        require(verifyProof(msg.sender, totalAmount, merkleProof), "ArbitrumMWomAirdrop: Invalid proof.");

        uint256 claimable = _getClaimable(msg.sender, totalAmount);
        require(claimable > 0, "ArbitrumMWomAirdrop: Insufficient claimable.");

        // Mark it claimed and send the token.
        if (isStake) {
            reward.safeApprove(address(helper), claimable);
            helper.depositFor(claimable, address(msg.sender));
        } else if (isLock) {
            reward.safeApprove(address(locker), claimable);
            locker.lockFor(claimable, address(msg.sender));
        } else {
            reward.safeTransfer(msg.sender, claimable);
        }

        uint256 userClaimedAmount = claimedAmount[msg.sender];
        claimedAmount[msg.sender] = userClaimedAmount + claimable;
        emit ClaimEvent(msg.sender, claimable, isStake, isLock);
