## Title
Stale/unsynchronized diff-selection indices allow silent corruption of partial commits - (File: `app/src/lib/patch-formatter.ts`, `app/src/lib/git/apply.ts`)

### Summary
Desktop lets a user select individual add/delete lines in a diff to build a partial commit. The selection is stored as a set of numeric, hunk-relative line indices (`DiffSelection`), completely decoupled from the diff content those numbers were computed against. When the patch used for `git apply --cached` is generated, the code re-fetches the working directory diff and blindly reapplies the *old* selection indices to the *new* hunk structure with no check that the indices still refer to the same logical lines the user actually reviewed and clicked. This mirrors the reported Solidity pattern: an index/id is accepted and used to reach into a collection without validating it still identifies the entity the caller intended, silently taking the wrong branch instead of failing loudly.

### Finding Description
`DiffSelection.isSelected(lineIndex)` and `withLineSelection`/`withRangeSelection` operate purely on integer line numbers stored in a `Set<number>` (`divergingLines`), with no reference back to the diff/hunks that produced them: [1](#0-0) 

`formatPatch` walks the hunks of a diff object and, for every non-context line, asks `file.selection.isSelected(absoluteIndex)` to decide whether to keep, drop, or convert that line — this is the only gate deciding what content ends up in the generated patch: [2](#0-1) 

Critically, `applyPatchToIndex` (used by `stageFiles` right before every partial commit) fetches a **fresh** diff from disk with `getWorkingDirectoryDiff` and immediately feeds it to `formatPatch` together with the file's previously computed `selection`: [3](#0-2) [4](#0-3) 

There is no check anywhere in this path that the newly fetched diff's hunk layout (`unifiedDiffStart`/`unifiedDiffEnd`, line count, line content) matches the diff the selection indices were originally computed from. The only place in the codebase that attempts to keep selection state consistent with a changed diff is `updateChangesWorkingDirectoryDiff`, which recomputes `selectableLines` when the Changes view refreshes its rendered diff — but this reconciliation is a UI-refresh side effect, not something enforced at the point where the patch is actually built and applied: [5](#0-4) 

If the working tree content changes between the moment the user visually reviews and selects lines and the moment `createCommit` → `stageFiles` → `applyPatchToIndex` runs — for example because a hostile repository ships hooks or tooling (post-checkout/post-merge scripts, file watchers, build steps) that rewrite tracked files, or because an async refresh/pull lands mid-review — `getWorkingDirectoryDiff` will return hunks whose `unifiedDiffStart` offsets and line contents no longer correspond 1:1 to what the user saw. `DiffSelection.isSelected(absoluteIndex)` has no way to detect this: it will happily report "selected" or "not selected" for whatever line now occupies that numeric slot, exactly like the reported contract accepting an `_index` that no longer points at the claim the caller thinks it does, because nothing analogous to `require(_index < coverPoolClaims[...].length, "bad indexes")` exists to revalidate the index against the current, live collection before acting on it.

### Impact Explanation
This can silently corrupt what a user commits and pushes: lines never shown to or approved by the user can be included in the staged patch, or lines the user explicitly checked can be silently omitted, all without error (since every index still resolves to *some* line in the new `hunk.lines` array — there is no out-of-bounds condition to trip an exception, just semantic index confusion). This falls squarely under the listed valid impact "silent corruption of what the user commits or pushes," triggered by content controlled through a fetched/cloned repository (e.g., a hook or tooling that mutates tracked files as part of normal repository operations).

### Likelihood Explanation
Exploitation requires an attacker-controlled repository to cause the working tree content to shift between the user's diff review/selection and the final `stageFiles` call — e.g. via a hook or background process tied to repository activity. This requires a specific timing window and is not trivially triggerable by a passive malicious repo alone, so likelihood is moderate; the more common trigger would be Desktop's own async refresh/hunk-expansion logic racing with staging rather than deliberate attacker timing, but the attacker-controlled repository vector (hooks rewriting files) is the concrete path that fits the "Valid Impact" criteria.

### Recommendation
Before applying `file.selection` to a diff in `formatPatch`/`applyPatchToIndex`, revalidate that the diff currently being formatted structurally matches (same hunk boundaries/line count/line hashes) the diff the selection was computed against; if it doesn't, refuse to stage/commit and force a diff refresh + re-selection, analogous to adding an explicit bounds/identity check (`require(_index < coverPoolClaims[...].length)`) before trusting a caller-supplied index.

### Proof of Concept
1. User modifies `file.md`, opens the Changes view; Desktop computes a diff and the user selects only line 5 for the commit (`DiffSelection` divergingLines = `{5}`, tied to the current hunk layout).
2. Before the user clicks "Commit," a hook or background process (attacker-controlled via the cloned repository, e.g. a `post-checkout`/tooling script) rewrites `file.md`, shifting/adding lines above line 5 so a different line now falls at absolute index 5 in the newly-computed diff.
3. User clicks "Commit." `stageFiles` → `applyPatchToIndex` calls `getWorkingDirectoryDiff` (fresh diff, new hunk layout) and passes the stale `file.selection` into `formatPatch`, which calls `isSelected(5)` — this now matches a different, unreviewed line.
4. The resulting patch stages/commits content the user never saw or approved, with no error raised, because `DiffSelection` never validates that its indices still refer to the entity the user selected.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
