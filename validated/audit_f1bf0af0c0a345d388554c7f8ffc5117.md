### Title
Aliased mutable CPI account references via unchecked AccountInfo/SolAccountInfo pointers when `syscall_parameter_address_restrictions` is inactive - ([File: program-runtime/src/cpi.rs])

### Summary
`CallerAccount::from_account_info` / `CallerAccount::from_sol_account_info` call `translate_type_mut_for_cpi`/`translate_slice_mut_for_cpi` using pointer values taken directly from attacker-controlled `AccountInfo`/`SolAccountInfo` structs. When the feature `syscall_parameter_address_restrictions` (SIMD-0459) is not active, the pointer-pinning checks (`check_account_info_pointer`) that normally force each account's lamports/owner/data addresses to the unique serialized VM address are skipped, so a malicious program can make two distinct real accounts' `AccountInfo` fields alias the same VM address, producing two simultaneous live `&mut` references to the same host memory.

### Finding Description
In `program-runtime/src/cpi.rs`, `translate_accounts_common` iterates over the *real, unique* instruction accounts of the pending CPI (`next_instruction_context.instruction_accounts()`, deduplicated via `is_instruction_account_duplicate`) and, for each one, looks up the matching `AccountInfo`/`SolAccountInfo` entry supplied by the caller program in `account_infos` by key (`account_info_keys.iter().position(...)`), then calls `do_translate` (`CallerAccount::from_account_info` / `from_sol_account_info`) once per distinct account key [1](#0-0) .

Inside `from_account_info`, when `syscall_parameter_address_restrictions` is `false`, the `check_account_info_pointer` calls that pin `lamports`, `owner`, `data` addresses to the pre-recorded, unique `account_metadata.vm_*_addr` values are skipped, and the code instead directly translates whatever address value is embedded in the attacker-controlled `AccountInfo` struct (`account_info.lamports.as_ptr()` double-dereferenced, `account_info.owner`, `account_info.data`) via `translate_type_mut_for_cpi`/`translate_slice_mut_for_cpi` [2](#0-1) . The same pattern exists in `from_sol_account_info` for the C ABI, where `lamports_addr`, `owner_addr`, `data_addr` are raw `u64` fields directly inside the (attacker-writable) `SolAccountInfo` struct, guarded only conditionally on the same feature flag [3](#0-2) .

`translate_type_mut_for_cpi`/`translate_slice_mut_for_cpi` themselves perform no aliasing check against other already-translated accounts; they only validate that the address resolves to a valid, writable memory region [4](#0-3) . Unlike `syscalls/src/lib.rs`'s `translate_mut!` macro, which explicitly collects all host address ranges for a single syscall call and checks `is_nonoverlapping` across all of them before returning any reference [5](#0-4) , `translate_accounts_common` has no equivalent cross-account overlap check across the `Vec<TranslatedAccount>` it builds.

Because a malicious program can freely construct raw `AccountInfo`/`SolAccountInfo` structures (it is not required to use the SDK-provided ones from `deserialize`), it can set the lamports/owner/data pointer fields of two distinct real accounts (distinct pubkeys, both passed in the instruction's account list) to the identical VM address. With the restriction feature off, `from_account_info`/`from_sol_account_info` will happily translate both to `&'a mut` references pointing at the same host memory, held live simultaneously in the returned `Vec<TranslatedAccount>` — violating Rust's mutable-reference-uniqueness invariant (explicitly called out as a caller obligation in the `# Safety` doc comments of `get_serialized_data` and `translate_slice_mut_for_cpi`) [6](#0-5) [7](#0-6) .

Concretely, `update_callee_account` later reads `*caller_account.lamports` and `*caller_account.ref_to_len_in_vm`/`serialized_data` to write into each callee `BorrowedInstructionAccount` [8](#0-7) . If the lamports/data cells of accounts A and B alias, a write intended for A's account becomes visible/attributable in B's account and vice versa, giving cross-account state corruption in addition to the raw Rust-level UB from two live overlapping `&mut` references.

When `syscall_parameter_address_restrictions` is active, this is prevented: `check_account_info_pointer` forces each account_info's lamports/owner/data/key address to exactly match the account's own unique, non-overlapping serialized VM address recorded in `SerializedAccountMetadata` at serialization time, so two distinct accounts can never be forced to the same address through this path [9](#0-8) .

### Impact Explanation
When the feature is inactive, an unprivileged attacker's own deployed program can trigger simultaneous aliased mutable references to host memory backing two different accounts during a CPI, corrupting or leaking lamports/data belonging to accounts other than the ones the attacker intends to touch, and creating undefined behavior in the validator process (non-deterministic execution across builds due to violated Rust aliasing guarantees). This matches the "aliased memory access" / "cross-account corruption" bounty category.

### Likelihood Explanation
Exploitability is entirely gated on the cluster not having activated `syscall_parameter_address_restrictions`/`virtual_address_space_adjustments`/`account_data_direct_mapping` (SIMD-0459/0460). The repo's own test suite exercises both `true` and `false` states for this flag, confirming it is a real, still-toggleable code path rather than dead code [10](#0-9) . On any cluster (e.g., devnet/testnet or a mainnet snapshot prior to full activation) where the flag is off, the attack requires only deploying an ordinary sBPF program that manually crafts `AccountInfo`/`SolAccountInfo` structs with colliding pointer fields and issues a CPI — fully within the unprivileged attacker model.

### Recommendation
Make the pointer-pinning checks in `check_account_info_pointer` (or an equivalent aliasing check across all `TranslatedAccount`s in `translate_accounts_common`) unconditional, i.e., not gated behind `syscall_parameter_address_restrictions`, or add an explicit cross-account `is_nonoverlapping` pass (similar to `translate_mut!` in `syscalls/src/lib.rs`) over the lamports/owner/data/len host ranges of all accounts collected in `translate_accounts_common` before returning `Vec<TranslatedAccount>`.

### Proof of Concept
Integration test plan (add to `programs/sbf/tests/programs.rs` alongside `test_cpi_invalid_account_info_pointers`):
1. Deploy a custom sBPF program (Rust, no-`entrypoint!`-macro, manual byte manipulation) that:
   - Takes two distinct writable accounts A and B (different pubkeys) as instruction accounts.
   - Manually builds two `AccountInfo` structs where `account_info_a.lamports.as_ptr()`-referenced pointer value and `account_info_b.lamports.as_ptr()`-referenced pointer value are forced to be identical (or the `SolAccountInfo.lamports_addr` fields identical, for the C path).
   - Invokes CPI (`sol_invoke_signed_rust`/`_c`) to a no-op program passing both AccountInfos.
2. Run the transaction with a `Bank` where `syscall_parameter_address_restrictions` (and dependent features) are deactivated via `feature_set.deactivate(...)`, mirroring the pattern in `test_account_info_in_account` [11](#0-10) .
   - Expected (bug): the CPI succeeds without an aliasing error, and after execution, a lamport transfer/write applied to account A's `CallerAccount.lamports` is observably reflected in account B's post-transaction lamports (or vice-versa) — demonstrating cross-account corruption / non-deterministic state.
3. Run the same transaction with the features activated.
   - Expected (correct behavior, and current mitigation): the transaction fails with `CpiError::InvalidPointer` ("Invalid pointer") from `check_account_info_pointer`, as in `test_cpi_invalid_account_info_pointers` [12](#0-11) .
4. Assert: with restrictions off, result is `Ok` and lamports/data diverge from the "restrictions on" run — proving the aliasing is only prevented by the (still-toggleable) feature, not by an unconditional invariant in `translate_accounts_common`/`translate_type_mut_for_cpi`.

            field,
            vm_addr,

        return Err(Box::new(CpiError::InvalidPointer));
    }
    Ok(())
}

fn update_callee_account(
    memory_mapping: &MemoryMapping,
    check_aligned: bool,
    caller_account: &CallerAccount,
    mut callee_account: BorrowedInstructionAccount<'_, '_>,
    syscall_parameter_address_restrictions: bool,
    virtual_address_space_adjustments: bool,
    account_data_direct_mapping: bool,
) -> Result<bool, Error> {
    let mut must_update_caller = false;

    if callee_account.get_lamports() != *caller_account.lamports {
        callee_account.set_lamports(*caller_account.lamports)?;
    }

    if virtual_address_space_adjustments {
        let prev_len = callee_account.get_data().len();
        let post_len = *caller_account.ref_to_len_in_vm as usize;
        if prev_len != post_len {
            if !account_data_direct_mapping && post_len < prev_len {
                // If the account has been shrunk, we're going to zero the unused memory
                // *that was previously used*.
                let serialized_data = unsafe {
                    CallerAccount::get_serialized_data(
                        memory_mapping,
                        check_aligned,
                        caller_account.vm_data_addr,
                        caller_account.original_data_len,
                        prev_len,
                        syscall_parameter_address_restrictions,
                        virtual_address_space_adjustments,
                        account_data_direct_mapping,
                    )?
                };
                serialized_data
                    .get_mut(post_len..)
                    .ok_or_else(|| Box::new(InstructionError::AccountDataTooSmall) as Error)?
                    .fill(0);
            }
            callee_account.set_data_length(post_len)?;
            // pointer to data may have changed, so caller must be updated
            must_update_caller = true;
        }
        if !account_data_direct_mapping && callee_account.can_data_be_changed().is_ok() {
            callee_account.set_data_from_slice(caller_account.serialized_data)?;
        }
    } else {
        // The redundant check helps to avoid the expensive data comparison if we can
        match callee_account.can_data_be_resized(caller_account.serialized_data.len()) {
            Ok(()) => callee_account.set_data_from_slice(caller_account.serialized_data)?,
            Err(err) if callee_account.get_data() != caller_account.serialized_data => {
                return Err(Box::new(err));
            }
            _ => {}
        }
    }

    memory_mapping: &MemoryMapping,
    vm_addr: u64,
    len: u64,

        memory_mapping,
        AccessType::Store,
        vm_addr,
