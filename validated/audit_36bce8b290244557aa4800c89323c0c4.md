Based on my research, I found that the pointer precompile's upsert mechanism (`UpsertERCPointer` in `x/evm/keeper/pointer_upgrade.go`) permits **any unauthenticated caller** to re-run `addNativePointer`/`addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` for an **already-registered, known pointee identifier** (denom or CW address) and have the keeper overwrite the *existing* pointer contract's bytecode in place, with no check that the caller is the original registrant or has any privilege over that pointee.

### Title
Unauthenticated re-registration of existing CW/native pointer overwrites live pointer contract bytecode via `addNativePointer`/`addCW20/721/1155Pointer` upsert path - ([File: x/evm/keeper/pointer_upgrade.go])

### Summary
The `pointer` precompile at `0x100b` exposes `addNativePointer`, `addCW20Pointer`, `addCW721Pointer`, and `addCW1155Pointer` to any EVM caller with no authorization check tied to the pointee (denom or CW contract address). [1](#0-0)  When the pointee already has a registered pointer, `UpsertERCPointer` does not create a new contract — it calls `evm.GetDeploymentCode` against the **existing** pointer address and overwrites its bytecode with `k.SetCode`, keeping the same on-chain address. [2](#0-1)  This is explicitly documented as "upsert semantics" for the native case (re-registering the same denom succeeds and keeps the pointer address stable). [3](#0-2) 

### Finding Description
`AddNative`, `AddCW20`, and (in current `pointer.go`) `AddCW721`/`AddCW1155` all take a caller-supplied string identifier (`token` denom or `cwAddr`) and immediately call into `UpsertERCPointer` without first checking whether the pointer already exists and is owned/administered by someone else. [4](#0-3)  `UpsertERCPointer` looks up the existing pointer via `getter(liveCtx(), pointee)`; if found, it reuses `existingAddr` as `contractAddr`, regenerates the constructor bytecode from **freshly supplied** metadata (name/symbol/decimals pulled from current bank denom metadata or the current on-chain CW `token_info`/`contract_info` query), and overwrites the code at that address with `k.SetCode(writeCtx, contractAddr, ret)`. [2](#0-1)  Critically, there is no verification that the caller invoking `addNativePointer`/`addCWxPointer` is the denom admin, the CW20/721/1155 contract owner, or any privileged account — any address can trigger this re-registration for an existing pointee identifier they don't control, analogous to the OpenRemote flaw where a known asset ID is enough to overwrite an existing resource without ownership checks.

Some legacy versions add an explicit version-gate (`existingVersion >= currentVersion` returns an error) as the only defense, e.g. in `x/evm/keeper/msg_server.go`'s `RegisterPointer` gov-msg path, and in early legacy pointer precompiles. [5](#0-4)  However, the current (non-legacy) `pointer.go` `AddCW20`/`AddCW721`/`AddCW1155` handlers in this snapshot no longer perform that version check before calling `Upsert...Pointer`, unlike the historical `v552`/`v555`/`v562` legacy copies which guarded with `existingVersion >= X`. [6](#0-5) 

### Impact Explanation
The practical impact is bytecode replacement of an already-deployed, potentially widely-integrated ERC pointer contract at a **stable, known address**, triggered by an unrelated third party. Because `GetDeploymentCode`/`SetCode` fully replace the contract's runtime bytecode using data pulled live from the current CW20/CW721/tokenfactory metadata, this could redeploy a functionally different pointer implementation (e.g., after a metadata change) at the same address that downstream integrators (DEXs, wallets, other contracts) already trust and hold balances/allowances against, without any of those integrators or the original registrant approving the change. This risks unauthorized state mutation and potential value-relevant behavior changes (e.g., mismatched decimals/name/symbol, or future codegen differences) being pushed onto a live pointer that other unprivileged contracts rely on for token accounting — matching the report's "update existing asset by supplying a known identifier without ownership validation" bug class.

### Likelihood Explanation
Likelihood is high for triggering the re-registration path itself: `addNativePointer`/`addCW20Pointer`/etc. are permissionless precompile calls reachable from any EVM transaction sender, requiring only a known, already-registered denom or CW contract address (both are public on-chain identifiers). No signature, ownership, or admin check is required beyond the pointee already having metadata queryable via `bankKeeper.GetDenomMetaData` or `wasmdKeeper.QuerySmartSafe`.

### Recommendation
Require that the re-registration/upsert operation be restricted to the pointee's legitimate administrator (tokenfactory denom admin, CW20/721/1155 contract admin, or governance) before allowing `UpsertERCPointer` to overwrite bytecode at an existing pointer address, or otherwise gate re-registration strictly behind a version bump check consistently across all pointer types (as some legacy versions did) so that arbitrary unprivileged callers cannot force redeployment of pointer bytecode for pointees they do not control.

### Proof of Concept
1. Attacker observes an existing tokenfactory denom `factory/creator/mydenom` (or an existing CW20/CW721 contract address) that already has a registered ERC pointer at `0x100b`.
2. Attacker (any unrelated EOA) submits an EVM transaction calling `addNativePointer("factory/creator/mydenom")` (or `addCW20Pointer(cwAddr)` / `addCW721Pointer(cwAddr)`) via the pointer precompile.
3. `UpsertERCPointer` finds the pointer already `exists`, and instead of rejecting, calls `evm.GetDeploymentCode(...)` and `k.SetCode(writeCtx, existingAddr, ret)`, overwriting the bytecode at the pre-existing, already-integrated pointer address — with the attacker as the triggering caller and no check that they control the denom/contract. func (p PrecompileExecutor) AddNative(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	token := args[0].(string)
	metadata, metadataExists := p.bankKeeper.GetDenomMetaData(ctx, token)
	if !metadataExists {
		return nil, 0, fmt.Errorf("denom %s does not have metadata stored and thus can only have its pointer set through gov proposal", token)
	}
	name := metadata.Name
	symbol := metadata.Symbol
	var decimals uint8
	for _, denomUnit := range metadata.DenomUnits {
		if denomUnit.Exponent > uint32(decimals) && denomUnit.Exponent <= math.MaxUint8 {
			decimals = uint8(denomUnit.Exponent)
			name = denomUnit.Denom
			symbol = denomUnit.Denom
			if len(denomUnit.Aliases) > 0 {
				name = denomUnit.Aliases[0]
			}
		}
	}
	contractAddr, err := p.evmKeeper.UpsertERCNativePointer(ctx, evm, token, utils.ERCMetadata{Name: name, Symbol: symbol, Decimals: decimals})
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(contractAddr)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}

	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(contractAddr)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
