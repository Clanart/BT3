### Title
Automatic remote URL rewrite trusts unvalidated `clone_url` from GitHub API response, allowing silent redirection of pushes/fetches - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` silently calls `git remote set-url` to change a repository's `origin` remote whenever the API-reported `clone_url` differs from the locally configured remote, gated only by a same-protocol check and a "did the user change this remote since we last saw it" check — neither of which validates that the new URL still points at the same host/owner that the user originally trusted.

### Finding Description
`updateRemoteUrl` compares the current git remote URL (`gitStore.defaultRemote.url`) to the URL freshly returned by the GitHub API (`apiRepo.clone_url`): [1](#0-0) 

The only preconditions before silently rewriting the remote are:
- `protocolsMatch`: both URLs use the same scheme (e.g. both `https:`) — this **does not check hostname, owner, or repo name**.
- `remoteUrlUnchanged`: the *previously cached* `gitHubRepository.cloneURL` still matches the local remote (i.e. the user hasn't hand-edited the remote since Desktop last looked at it).
- `!urlsMatch`: the new API URL differs from the current remote.

If all three hold, Desktop calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` with no user confirmation, immediately reconfiguring the git remote that all subsequent `push`/`fetch`/`pull` operations use.

`apiRepo` is an `IAPIRepository` object obtained from a GitHub API/GHE response (an attacker-controlled surface explicitly called out in the task's valid-impact list). A malicious or compromised GitHub Enterprise server, a spoofed/MITM'd API response, or a repository transfer/rename response crafted by an attacker who controls the account/repo being tracked can supply an arbitrary `clone_url` (e.g. `https://attacker.example/foo/bar.git`) that still satisfies `protocolsMatch` (same scheme) while pointing at a completely different host. Because hostname/owner/name are never cross-checked against the *account's* expected endpoint (only against the previous cached clone URL, which is itself sourced from the same untrusted API), the remote is silently repointed.

This mirrors the reported smart-contract bug's broken invariant: a value that should be locked to what the user originally consented to (their configured remote / the collateral rate they set) is instead recomputed from a different, attacker-influenced source at write time, with the guard checking the wrong thing (protocol only, not full origin identity).

### Impact Explanation
Once the remote URL is silently rewritten to an attacker-controlled host:
- Every subsequent `git push` from the user silently goes to the attacker's server instead of GitHub, allowing the attacker to capture private code/commits or serve back manipulated history.
- Every subsequent `git fetch`/`pull` retrieves refs/objects from the attacker's server, letting the attacker inject malicious commits into the user's local branches without any warning that the remote changed.
- Depending on credential-helper host-matching logic (`getCredentialUrl`, `isGitHubHost` in `app/src/lib/trampoline/trampoline-credential-helper.ts`), credentials could be requested/sent to the new host if the app misclassifies it, risking token exfiltration.
This is a silent corruption of what the user pushes/fetches with no user-facing prompt, matching the "silent corruption of what the user commits or pushes" and "credential exfiltration" impact categories.

### Likelihood Explanation
Exploitation requires the attacker to control (or spoof) the GitHub API/GHE response for a repository the victim is already tracking in Desktop — a plausible scenario for a compromised or rogue GitHub Enterprise instance, a network-level API response tamperer, or an attacker who can trigger a repository rename/transfer event that the app's API polling picks up. No local access, admin rights, or leaked credentials are required; the victim only needs to have the repository open in Desktop while it periodically refreshes API metadata.

### Recommendation
Require the new `clone_url` to match the *account's expected endpoint* (hostname) in addition to protocol before auto-updating the remote, and/or always prompt the user to confirm a remote URL change instead of applying it silently — analogous to fixing the collateral bug by validating the changed value against the originally-authorized parameter rather than trusting the newly supplied one.

### Proof of Concept
1. Victim has a repository cloned via `https://ghe.example.com/org/repo.git`, tracked by GitHub Desktop against a GitHub Enterprise account.
2. Attacker controls or MITMs the GHE API endpoint used for repository metadata refresh and returns an `IAPIRepository` with `clone_url: "https://attacker.example/org/repo.git"` (or, more realistically, causes the tracked repo's `clone_url` field to reflect a repo the attacker now controls, e.g. via a crafted rename/transfer response).
3. On the next metadata refresh, `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:7-45`) sees `protocolsMatch === true` (both `https:`) and `remoteUrlUnchanged === true` (user hasn't touched the remote), and `urlsMatch === false` (host differs) — so it calls `gitStore.setRemoteURL('origin', 'https://attacker.example/org/repo.git')` without any dialog.
4. The victim's next `git push`/`fetch` in Desktop silently targets `attacker.example`. [2](#0-1) [3](#0-2)

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
