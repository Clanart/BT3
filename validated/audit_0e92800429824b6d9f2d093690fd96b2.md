## Title
Future-dated oracle timestamp permanently locks price resolution for an asset via the monotonic freshness check - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`price-resolve` in `mainnet/contracts/market/v0-4-market.clar` gates every oracle read behind `oracle-timestamp-fresh`, which is meant to reject stale prices and enforce monotonic per-feed timestamps. The staleness half of the check is bypassed whenever the reported timestamp is ahead of `stacks-block-time`, and the monotonicity half then permanently latches onto that future value, blocking all subsequent (correct) lower timestamps forever — the same "reported-then-can't-recompute" failure mode described in the CometBFT analog, but expressed as a stuck oracle instead of a stuck blocksync target.

### Finding Description
`oracle-timestamp-fresh` computes staleness as: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

If the reported feed timestamp `ts` is greater than the chain's own `stacks-block-time` (e.g. minor clock/latency skew between the Pyth/DIA publish time and the Stacks block, or a corrupted/incorrect single value from either feed), `delta` is forced to `u0`, which trivially satisfies `(<= delta max-staleness)` — the staleness bound is fully bypassed for any future timestamp, no matter how far ahead it is.

`price-resolve` then unconditionally advances the stored watermark whenever the incoming timestamp is larger than the last stored one: [2](#0-1) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data)) ...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution)) ...)
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

Once a single abnormally future `ts` is accepted (because staleness was bypassed via the `delta = u0` escape) it is written to `last-update` as the new watermark for that `{type, ident}` feed. Every subsequent legitimate report, whose timestamp is a real, ordinary current time, will now be strictly less than this poisoned watermark, so `(>= ts prev)` fails on every future call, permanently. There is no admin/DAO reset path for the `last-update` map visible in the market contract, and the market's local caller of Pyth uses the raw `get-price` accessor (not the staleness-checked `read-price-with-staleness-check`), so the market's own `oracle-timestamp-fresh` check is the sole line of defense — and it is the thing that gets bricked. This is exactly analogous to the CometBFT bug class: a single anomalous report of an out-of-range value (there: `latest` height; here: feed `timestamp`) gets latched into monotonic state that later legitimate reports can never overtake, leaving the consumer permanently stuck.

### Impact Explanation
`price-resolve`/`price-multi-resolve` back every price read used throughout `v0-4-market.clar` for collateral valuation, debt valuation, borrow limit checks, withdrawal checks, and liquidation health calculations. Once the `last-update` watermark for a given feed is poisoned, every call that needs that asset's price reverts with `ERR-ORACLE-INVARIANT` indefinitely (until, if ever, a real timestamp manages to exceed the poisoned value — which for a large jump could be a very long wait). This freezes borrowing, withdrawal, and liquidation for any position that depends on that asset's price, i.e. temporary freezing of user funds tied to that feed. No party gains value directly; the effect is a denial-of-service on collateral/debt priced by the affected feed rather than a profit for an attacker, but it satisfies the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
Triggering requires one feed update to report a timestamp ahead of `stacks-block-time` by more than the natural catch-up window (a single bad/skewed value is enough, since the staleness bound offers no defense once `ts > stacks-block-time`). This can happen from ordinary clock/latency skew between an external oracle's publish time and the Stacks chain's block time, or from a single erroneous read from either the DIA push oracle or Pyth's stored value, and does not require compromising governance, DAO registries, or forging Wormhole VAAs. The condition is a pure logic gap in this contract's own freshness/monotonicity function, independent of whether the underlying price value itself is manipulated.

### Recommendation
Do not zero out `delta` when `ts > stacks-block-time`; instead bound how far into the future a timestamp may legitimately be (e.g. reject if `ts - stacks-block-time` exceeds a small clock-skew tolerance) so an anomalous future timestamp cannot pass the freshness check nor become the new monotonic watermark. Additionally, consider allowing the monotonic watermark to be correctable (e.g., DAO-gated repair function, or bounding how far `last-update` can be advanced beyond the current block time) so a single bad report cannot permanently lock a feed.

### Proof of Concept
1. A single price update for feed `{type, ident}` is resolved with `timestamp = stacks-block-time + N` (`N` arbitrarily large), due to skew or a bad read from Pyth/DIA.
2. In `oracle-timestamp-fresh`, `ts > stacks-block-time` so `delta = u0`, satisfying `(<= delta max-staleness)`; `(>= ts prev)` also passes since it's the largest timestamp seen so far. `price-resolve` succeeds and executes `(map-set last-update key timestamp)`, storing the future timestamp.
3. On the next legitimate oracle update, the true current publish time `ts'` (a normal, real-time value) is far less than the poisoned `prev = stacks-block-time + N`. `(>= ts' prev)` now fails for every subsequent call, so `price-resolve` returns `ERR-ORACLE-INVARIANT` on every call referencing that feed until real time actually surpasses the poisoned watermark.
4. Any borrow, withdraw, or liquidation call that needs this feed's price via `price-multi-resolve`/`price-resolve` reverts, freezing operations dependent on that asset. [3](#0-2)
