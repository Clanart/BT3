### Title
Out-of-range participant indexes in DKG blame statements panic via HashMap indexing, crashing the node - (File: crypto/dkg/pedpop/src/encryption.rs, crypto/dkg/pedpop/src/lib.rs)

### Summary
CVE-2021-36222 is an unchecked-return-value NULL-deref crashing the KDC daemon. The Serai analog is an unchecked HashMap lookup on untrusted `Participant` indexes in the PedPoP blame path. `Participant` is any nonzero `u16`, but `AdditionalBlameMachine::blame` / `BlameMachine::blame` accept `sender` and `recipient` from the wire and index `self.enc_keys[&decryptor]` and `self.commitments[&sender]` without checking they are within `1 ..= n`. `std::collections::HashMap`'s `Index` impl panics on a missing key, so a blame statement naming a participant index `> n` aborts the process — a remote DoS reachable purely from public inputs (`EncryptedMessage::read`, `EncryptionKeyProof::read`, `Participant`).

### Finding Description
`AdditionalBlameMachine::new` populates `encryption.enc_keys` and `commitments` only for `Participant`s `1 ..= n` (crypto/dkg/pedpop/src/lib.rs:656-660). `blame()` then forwards attacker-controlled `sender`/`recipient` to `blame_internal` (lib.rs:623-632, 674-682). Inside `Decryption::decrypt_with_proof`, when a `proof` is supplied, the DLEq verification indexes `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388). Separately, `blame_internal` indexes `self.commitments[&sender]` to build share-verification statements (lib.rs:599). Neither `blame` entry point validates that `sender`/`recipient` are members of the `1 ..= n` set. A `Participant` like `Participant(0xFFFF)` in a 150-participant DKG passes `Participant::new` and any outer parsing (only nonzero-ness is enforced), then hits a missing-key panic in `HashMap::index`.

This is directly reachable: the processor's `VerifyBlame` handler constructs `AdditionalBlameMachine` and calls `.blame(accuser, accused, share, blame)` where `accuser` and `accused` are taken from the coordinator message and the share is parsed with `EncryptedMessage::read` (processor/src/key_gen.rs:504-549). The panic occurs regardless of message validity — for the `enc_keys[&decryptor]` path, the sender merely needs a well-formed `EncryptedMessage` with a valid per-message PoP (they can generate one themselves) plus any `EncryptionKeyProof`, and the panic fires inside `dleq.verify` argument evaluation before the proof is even checked.

### Impact Explanation
Unauthenticated denial of service. Any party able to submit a blame/accusation statement to a node running PedPoP blame resolution can crash the process during a DKG/key-rotation attempt, aborting threshold-key generation and potentially the node's entire operation (the panic is not caught; it propagates out of `blame`). Repeated crashes across the validator set could indefinitely stall key generation for a Serai validator set or a bridge deployment.

### Likelihood Explanation
High. Triggering requires only choosing `sender` or `recipient` as a nonzero `u16` greater than `n` — no valid DKG membership, key material, or proof correctness is required for the `enc_keys` path (the lookup is evaluated to construct the `points` argument before the DLEq proof is verified). The only prerequisite is that the node processes blame messages, which occurs whenever any DKG share is disputed.

### Recommendation
Validate `sender` and `recipient` against `1 ..= n` at the top of `blame_internal` (or in `blame`) and return a defined faulty/`PedPoPError` result instead of indexing. Replace `enc_keys[...]` / `commitments[...]` `Index` usage with `get()` returning a blameable error (e.g., blame the accuser for referencing a non-participant). Callers in `processor/src/key_gen.rs` should additionally bound-check `accuser`/`accused` against `params.n()` before constructing blame machines.

### Proof of Concept
```rust
// DKG with n = 3, t = 2. commitments/commitment_msgs for participants 1..=3
// are legitimately formed; an attacker submits blame naming participant 0xFFFF.
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// EncryptedMessage<_, SecretShare<_>> read from attacker bytes: valid `key`, a
// SchnorrSignature `pop` the attacker generated over their own key, and any 32-byte msg.
// `proof` = Some(attacker-crafted EncryptionKeyProof::read(...)).
// Inside decrypt_with_proof, evaluation of `self.enc_keys[&decryptor]` where
// decryptor == Participant(0xFFFF) panics:
//   "no entry found for key" (HashMap Index impl)
machine.blame(
  Participant::new(1).unwrap(),        // sender
  Participant::new(0xFFFF).unwrap(),   // recipient — valid nonzero u16, not in 1..=3
  msg, Some(proof),
);
```
Likewise, `blame(Participant::new(0xFFFF), recipient, msg, proof)` reaching lib.rs:599 panics on `self.commitments[&sender]` once `decrypt_with_proof` succeeds (attacker can supply the honest encrypted share they legitimately received, plus their own ECDH key proof, which verifies since the DLEq binds to `msg.key` and their registered `enc_key` — wait, only if sender is registered; for the `commitments[&sender]` path, supplying `sender = 0xFFFF` with a decryptable message hits the missing key at line 599 even when decryption fails to a valid-scalar share path only after decrypt succeeds; the `enc_keys[&decryptor]` path on `recipient` is the cleaner trigger).
