### Title
Unvalidated `ReceivedOutput::read` permits forging the outpoint↔TxOut binding, reporting unspendable phantom funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` is the wallet's unit of "a UTXO we can spend": it couples a claimed `TxOut` (script_pubkey + value) with a claimed `OutPoint`. The scanner establishes this binding legitimately by matching `output.script_pubkey` against registered scripts and recording the real txid/vout (`scan_transaction`, `networks/bitcoin/src/wallet/mod.rs:199-214`). However, `ReceivedOutput::read` (`mod.rs:122-134`) deserializes `offset`, `TxOut`, and `OutPoint` as three independent, attacker-controlled fields with no consistency check. This mirrors the TOCTOU class: the object whose identity was "checked" (the on-chain output that satisfied the script match) can be swapped for attacker-supplied bytes at "use" time (deserialization and later signing), redirecting the wallet's accounting and signing logic to data that never existed on chain.

### Finding Description
In `Scanner::scan_transaction`, the `script_pubkey` lookup produces a `ReceivedOutput` whose `outpoint` is `OutPoint::new(tx.compute_txid(), vout)` — the binding between the spendable coin and its reference is guaranteed by construction. `ReceivedOutput::read` performs no equivalent validation: it accepts any `Scalar` offset, any `TxOut`, and any `OutPoint`. Downstream consumers trust the tuple:

- `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:175-185`) sums `input.output.value` for the funding check and uses `input.outpoint` as the `TxIn`, then stores the attacker-claimed `TxOut`s in `prevouts` (`send.rs:253`), which `TransactionSignMachine::sign` commits into every BIP-341 sighash via `Prevouts::All(&self.tx.prevouts)` (`send.rs:373-386`).
- The processor path (`processor/src/networks/bitcoin.rs:686-739`) wraps `ReceivedOutput` in `Output`, and `Output::read` (`bitcoin.rs:145-166`) equally accepts the forged triple without recomputing any chain-derived fact. The `output.key()` check at `processor/src/multisigs/scanner.rs:563` only verifies `script_key − offset·G == group_key`, which an attacker satisfies trivially by setting `offset = 0` and the wallet's public base P2TR `script_pubkey`.

An unprivileged party able to feed serialized bytes to `ReceivedOutput::read` / `Output::read` can therefore inject a `ReceivedOutput` referencing an outpoint that does not exist, belongs to a third party, or carries a fabricated value, while presenting a perfectly consistent `offset`/`script_pubkey` pair.

### Impact Explanation
Funds reported received that are not spendable: a forged `ReceivedOutput` credits the wallet/scheduler with a deposit that has no on-chain UTXO behind it. Because `SignableTransaction` computes the funding check, change amount, and fee from the claimed `TxOut.value` while the sighash commits to those claimed prevouts, every spend plan built on the forged input either (a) produces signatures over non-existent prevout data that consensus rejects, permanently stalling the associated plan/eventuality, or (b) corrupts the fee/change arithmetic for a batch mixed with real inputs (claimed input value inflates `input_sat`, causing real value to be burned as fee before the tx is found unbroadcastable). The mismatch between "what was scanned" and "what is spent" is exactly the redirect-to-attacker-controlled-target shape of the TOCTOU class, and it is reachable purely through untrusted bytes on a public read API.

### Likelihood Explanation
Any component that ingests scan results, coordinator-supplied inputs, or peer-provided `ReceivedOutput`/`Output` blobs via `read` trusts the forged binding. No curve math, collusion, or key material is needed — only the ability to write well-formed serialized fields. The only mitigating factor is that Serai's first-party scanner constructs `ReceivedOutput`s in memory, so exploitation requires an integrator or peer path that feeds adversarial bytes into `read` — which the public `read`/`serialize` API explicitly supports.

### Recommendation
Treat `ReceivedOutput` as untrusted after deserialization: before crediting or spending, re-resolve `outpoint` against the chain (or against the scanner's own stored block/tx evidence) and verify the resolved `TxOut` equals the claimed one. At minimum, document `ReceivedOutput::read`/`Output::read` as requiring an authenticated source, and have consumers assert `output.key()` consistency plus on-chain outpoint existence before `SignableTransaction::new`/`attempt_sign` are reached.

### Proof of Concept
```rust
// networks/bitcoin context
let key = /* wallet group key, public */;
let script = p2tr_script_buf(key).unwrap(); // registered script, offset 0

// Attacker crafts bytes: offset = 0, fabricated TxOut, arbitrary outpoint
let forged = {
    let mut buf = vec![];
    buf.extend(Scalar::ZERO.to_bytes());                       // offset
    buf.extend(serialize(&TxOut {                              // claimed TxOut
        value: Amount::from_sat(100_000_000),
        script_pubkey: script.clone(),
    }));
    buf.extend(serialize(&OutPoint {                           // victim/nonexistent outpoint
        txid: some_other_txid, vout: 0,
    }));
    buf
};

let ro = ReceivedOutput::read(&mut forged.as_slice()).unwrap();
// ro now reports a 1 BTC deposit under a script matching the wallet,
// passes output.key() == key checks, yet references an outpoint the
// wallet does not control. SignableTransaction::new(vec![ro], ...) will
// compute funding/fee/change on the phantom value and produce signatures
// committed to prevouts that do not match the chain.
```
