## No vulnerability found for this question.

**Analysis supporting this conclusion:**

The binding under scrutiny is: `num_required_sigs = config.get_num_required_nofn_sigs(&deposit_data)` (computed before nonce_gen) must equal the number of sighashes `create_nofn_sighash_stream` actually yields for that same call.

Both sides of this equality are pure, deterministic functions of the *same* `deposit_data.actors` (verifiers/operators/watchtowers) evaluated within the same `deposit_sign`/`deposit_finalize` invocation: [1](#0-0) [2](#0-1) 

`get_num_required_nofn_sigs_per_kickoff` and `get_operators()`/`get_num_verifiers()` are called on the identical `deposit_data` struct that flows into `create_nofn_sighash_stream`, so the counts cannot diverge within one signing session — this is enforced by construction, not by a cross-check against a separate "old" actor set. The stream additionally self-validates per kickoff: `sum != config.get_num_required_nofn_sigs_per_kickoff(&deposit_data)` triggers a hard error. [3](#0-2) 

Critically, the premise that an attacker can set `get_num_operators()`/`get_num_watchtowers()` on a `ReplacementDeposit` is false. The `actors` field of `DepositData` is never attacker-supplied — it is always fetched fresh by the aggregator from its own verifier/operator registries, regardless of deposit type: [4](#0-3) 

The only attacker-controllable field for a `ReplacementDeposit` is `old_move_txid`, which is used solely to build the `ReplacementDepositScript` (checked against the on-chain deposit output's scriptPubkey in `is_deposit_valid`) and has no bearing on `get_num_required_nofn_sigs` or the sighash stream count: [5](#0-4) [6](#0-5) 

The intentional design purpose of a `ReplacementDeposit` is precisely to allow the actor set (operators/watchtowers/verifiers) to differ from whatever set produced the old move transaction's kickoffs — this is a legitimate protocol feature gated by the security council multisig unlocking `old_move_txid`'s output, not an unprivileged-attacker-reachable divergence. Since `num_required_sigs` and the sighash stream are computed from one server-controlled, internally-consistent `deposit_data` snapshot, the guard at `core/src/verifier.rs:919` (`num_required_sigs + 2 != session.nonces.len()`) can never be triggered by this attack vector. [7](#0-6) 

No path exists for an unprivileged depositor to make `num_required_sigs` diverge from the actual sighash count for a given `deposit_data`, since both derive deterministically from server-controlled `actors` data within the same call.
