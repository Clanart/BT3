This confirms the vulnerability: `resolveWithin` (with symlink-aware `realpath` checks) exists in the codebase specifically to prevent symlink-based path traversal [1](#0-0) , and its test suite explicitly documents that "paths that use a symlink to traverse outside of the root" must be rejected [2](#0-1) . However, `GitStore.discardChanges` — the code path that deletes/moves working-directory files chosen by a user to "discard" — never calls `resolveWithin`. It builds the target path with plain `Path.resolve`/`Path.join` using `file.path` taken directly from `git status` output, then hands it to `shell.moveItemToTrash` or `fs.rm` [3](#0-2) .

### Title
Discard Changes follows attacker-controlled symlinks to delete/trash files outside the repository - (File: app/src/lib/stores/git-store.ts)

### Summary
`GitStore.discardChanges` resolves each file to discard with `Path.resolve(repository.path, file.path)` / `Path.join(repository.path, file.path)` and passes the result straight to `shell.moveItemToTrash` (Electron trash) or `fs.rm`, without ever validating that the resolved path is truly contained within the repository's real (symlink-resolved) directory tree [4](#0-3) . The repository already has a dedicated utility, `resolveWithin`, that performs exactly this containment check by comparing `realpath()` of the root and the resolved path, explicitly to defeat symlink traversal [1](#0-0) , and it is used elsewhere (`app-store.ts`, `dispatcher.ts`, `copilot-conflict-context.ts`) — but not in the discard-changes flow.

### Finding Description
A cloned/checked-out repository is attacker-controlled content: a malicious repo can contain a tracked or untracked directory entry that is a symlink pointing outside the repository (e.g., to the user's home directory or another sensitive folder). Because Desktop's discard flow only prevents this for "unsafe"/untrusted-owner repositories at open time (`getRepositoryType` "unsafe" checks in `app-store.ts` / `add-existing-repository.tsx`), a normal clone from a hostile remote is trusted and its symlinks are followed unchecked at `discardChanges` time. When `git status` reports a modified/new file underneath that symlinked path, `WorkingDirectoryFileChange.path` is simply the relative status path from `status-parser.ts`, with no `..` segments but a first path component that is itself a symlink to outside the working tree [5](#0-4) . `discardChanges` then does `Path.resolve(this.repository.path, file.path)`, which syntactically stays "inside" the repo path string, but the OS resolves the symlink component and the actual file operation (`shell.moveItemToTrash` or `rm`) lands on the real target outside the repo [3](#0-2) . This is conceptually the same broken invariant as the reported bug class: an operation intended to affect only the caller's own scope (their own tokens / their own repo's working tree) is instead performed against a target the caller does not actually control, because the identifier used for the operation is not verified to point where it claims to.

### Impact Explanation
If the "move to trash" attempt fails (e.g., cross-device trash limitations, path length, or platform trash errors) and the user has previously opted into "always discard permanently," Desktop falls back to `rm(Path.join(this.repository.path, file.path))` for untracked files — an unrecoverable delete outside the repository, entirely driven by attacker-supplied symlink placement [6](#0-5) . Even the "successful" trash path silently moves a file that is not actually part of the repo, which the user did not intend to touch and may not notice, since the UI just shows the repo-relative path. This matches the requested impact class: "file write or read outside the repo" / "silent corruption" resulting from an attacker-controlled cloned/fetched repository.

### Likelihood Explanation
Exploitation only requires the victim to: clone or open an attacker's repository (a completely ordinary Desktop workflow, not "unnatural user steps"), have the repository create a symlinked directory/file as part of its tracked or untracked content, modify or create a file reachable through that symlink (or simply have the attacker's initial commit contain an untracked-looking entry), and click "Discard Changes" on it — a very common, low-friction action in Desktop. No admin rights, local access, or pre-existing malware is needed; the "unsafe repository" ownership check does not apply to a repo the victim consciously clones and owns.

### Recommendation
Route every path used by `GitStore.discardChanges` (and similarly `checkoutPaths`/`applyPatchToIndex`, if not already covered) through `resolveWithin(this.repository.path, file.path)` / `resolveWithinPosix` before calling `shell.moveItemToTrash` or `rm`, and abort/skip the operation (surfacing an error) when the resolved real path escapes the repository root, exactly as `resolveWithin` already does for other consumers [7](#0-6) .

### Proof of Concept
1. Attacker creates a repository containing a symlink `evil -> /Users/victim` (or any sensitive absolute path) committed or left untracked, plus a file placed so that git reports a change under `evil/some-file` (e.g., attacker crafts the repo so that after clone, `git status` shows `evil/.bash_profile` as untracked/modified — achievable because symlinked directories are followed by the filesystem and by `git status`'s untracked-file walk).
2. Victim clones the repository via GitHub Desktop.
3. Desktop's Changes list shows `evil/.bash_profile` as a changed/untracked file.
4. Victim selects "Discard Changes" on that entry.
5. `GitStore.discardChanges` computes `Path.resolve(repo.path, 'evil/.bash_profile')`, which resolves (via the OS-level symlink) to `/Users/victim/.bash_profile`, and calls `shell.moveItemToTrash`/`rm` on it — moving/deleting a file entirely outside the cloned repository, matching the symlink-escape scenario `resolveWithin`'s own tests are designed to catch [2](#0-1) .
