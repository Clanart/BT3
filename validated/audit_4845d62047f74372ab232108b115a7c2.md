### Title
Session-key private keys are persisted in plaintext by `createSessionKeyStorage`, allowing device/browser-storage compromise to forge on-chain solver authorizations - (File: `sdk/packages/sdk/src/storage/index.ts`)

### Summary
The IntentGatewayV2 solver-selection flow relies on a disposable "session key" whose private key is generated client-side and used to sign an EIP-712 `SolverSelection` message that authorizes a specific solver to fill a user's intent order [1](#0-0) . The SDK persists this private key **unencrypted** via `createSessionKeyStorage`, writing raw JSON (including the `privateKey` field) into `localStorage`/`indexedDB` (browser) or an equivalent driver, keyed by order commitment and by address [2](#0-1) . This mirrors exactly the bug class in the external report: a credential/state artifact that grants transaction-authorizing power is written to durable local storage in plaintext, readable by anyone with access to the victim's machine/browser profile (malicious browser extension, XSS, shared/compromised device, synced browser storage, or forensic recovery after "deletion").

### Finding Description
`createSessionKeyStorage` defines `SessionKeyData` with a plaintext `privateKey: HexString` field and stores it via `JSON.stringify(data)` under keys such as `session-key:${commitment}` and `session-key-address:${address}` [3](#0-2) . The underlying driver for browser environments is either `localStorageDriver` or `indexedDBDriver`, both of which store data unencrypted on disk/in the browser profile [4](#0-3) .

This key is not a throwaway convenience value — it is the sole authorization credential for `IntentGatewayV2.select()`/`SolverAccount.validateUserOp()` on the destination chain. `Bid.signSelection()` loads the stored `sessionKeyData.privateKey` and signs the `SelectSolver(bytes32 commitment, address solver)` EIP-712 message with it via `CryptoUtils.signSolverSelection` [5](#0-4) [6](#0-5) . On-chain, `IntentsBase._select()` recovers the session key from this signature and stashes `keccak256(solver, sessionKey)` in transient storage, which `fillOrder` later trusts as authorization to execute the fill [7](#0-6) .

Because the session-key private key sits unencrypted in the browser's persistent storage for the lifetime of the order (and potentially after, since no proactive wipe-on-completion is evident in the storage API), an attacker who gains local/browser-storage access to the victim's device can extract it and independently sign a `SolverSelection` message picking **any solver address they control** for that commitment — without needing the user's cooperation, a malicious relayer, or a malicious prover. This is a pure local-secrets-exposure primitive, structurally identical to the ZecWallet `senttxstore.dat` plaintext-storage report, except the artifact here is a signing key that authorizes on-chain execution rather than passive transaction history.

### Impact Explanation
Compromise of the session key does not merely leak private data (per the original report) — it grants the ability to submit a valid, on-chain-verifiable `SolverSelection` authorization for the order, redirecting `IntentGatewayV2.fillOrder`'s trusted-solver slot to an attacker-controlled `SolverAccount`. Depending on how loosely the order's output-amount floor is enforced relative to the winning bid (a detail in `IntentGatewayV2.fillOrder`/`Order.outputs` that I could not fully verify in this pass), this enables unauthorized selection of a solver the user never intended, i.e., transaction manipulation of the settlement path for that order via a forged authorization signature — satisfying the "unauthorized transaction or execution" / "transaction manipulation" categories of the impact gate.

### Likelihood Explanation
The attack requires only local access to the victim's storage (browser profile, synced storage, XSS in the dApp origin, or filesystem access on Node-based fillers using this SDK) — no malicious relayer, prover, governance actor, or leaked on-chain key is needed, matching the gate's requirement to exclude those actors. Session keys are also long-lived relative to the order lifecycle (`createdAt` timestamp with no visible mandatory expiry/clearing on read), widening the exposure window [8](#0-7) .

### Recommendation
- Never persist raw session-key private keys in plaintext `localStorage`/`indexedDB`. Encrypt at rest using a user/device-bound key (e.g., WebCrypto non-extractable key wrapping, platform keychain analogs) before calling `setSessionKey`/`setSessionKeyByAddress`.
- Reduce the exposure window: clear the session key from storage immediately after a successful `select`/`fillOrder`, and enforce a short TTL independent of order deadline.
- Consider deriving the session key deterministically from an ephemeral in-memory secret plus a server-verifiable nonce rather than persisting the raw key at all, or scope its authority server-side so a leaked key alone cannot authorize an arbitrary solver without an additional binding factor.

### Proof of Concept
1. User places an intent order; SDK calls `createSessionKeyStorage().setSessionKey(commitment, { privateKey, address, commitment, createdAt })`, writing plaintext JSON to the browser's `localStorage`/`indexedDB` under key `session-key:${commitment}` [9](#0-8) .
2. Attacker with local access to the victim's browser profile (shared device, malicious extension, or storage-exfiltrating XSS on the dApp origin) reads this storage entry directly — no cryptographic barrier exists.
3. Attacker extracts `privateKey`, computes `SELECT_SOLVER_TYPEHASH` digest for `(commitment, attackerSolverAddress)`, and signs it exactly as `CryptoUtils.signSolverSelection` does [6](#0-5) .
4. Attacker submits a `PackedUserOperation` for their own `SolverAccount` with `signature = abi.encodePacked(commitment, solverSignature, sessionSignature)` matching the nonce-key binding `keccak256(commitment ‖ sessionKeyAddress)` [10](#0-9) .
5. `IntentGatewayV2.select()`/`fillOrder()` accepts the forged authorization since the recovered session key matches `order.session`, letting the attacker's solver be recorded as authorized and execute the fill in place of the legitimate winning bidder [11](#0-10) .

Note: full confirmation of the maximum extractable value (i.e., whether `Order.outputs` enforces a hard minimum independent of the selected bid) requires reading `IntentGatewayV2.fillOrder` and `Order` struct definitions directly, which I was unable to complete before running out of tool-call budget — a Devin session with full repo access should verify this bound before treating the impact as unbounded fund loss versus bounded "worse execution price" manipulation.

/**
 * Creates a session key storage instance for IntentGatewayV2 orders.
 * The storage is used to persist session key private keys so they can be
 * used later to sign solver selection messages.
 *
 * @param options - Optional configuration for the storage driver
 * @returns A storage instance with methods to get, set, and remove session keys
 */
export function createSessionKeyStorage(options: SessionKeyStorageOptions = {}) {
	const key = options.env ?? detectEnvironment()
	const driver = loadDriver({ key, options }) ?? inMemoryDriver()
	const baseStorage = createStorage({ driver })

	const SESSION_KEY_PREFIX = "session-key:"
	const SESSION_KEY_ADDRESS_PREFIX = "session-key-address:"

	/**
	 * Gets a session key by order commitment
	 */
	const getSessionKey = async (commitment: HexString): Promise<SessionKeyData | null> => {
		const storageKey = `${SESSION_KEY_PREFIX}${commitment}`
		const value = await baseStorage.getItem<string>(storageKey)
		if (!value) return null

		try {
			return JSON.parse(value) as SessionKeyData
		} catch {
			return null
		}
	}

	/**
	 * Gets a session key by session key address
	 */
	const getSessionKeyByAddress = async (address: HexString): Promise<SessionKeyData | null> => {
		const storageKey = `${SESSION_KEY_ADDRESS_PREFIX}${address.toLowerCase()}`
		const value = await baseStorage.getItem<string>(storageKey)
		if (!value) return null

		try {
			return JSON.parse(value) as SessionKeyData
		} catch {
			return null
		}
	}

	/**
	 * Stores a session key for an order commitment

	private async signSelection(): Promise<HexString> {
		if (this.cachedSignature) return this.cachedSignature

		const commitment = this.order.id as HexString
		const sessionKeyAddress = this.order.session as HexString

		const sessionKeyData = this.sessionPrivateKey
			? { privateKey: this.sessionPrivateKey }
			: await this.ctx.sessionKeyStorage.getSessionKeyByAddress(sessionKeyAddress)
		if (!sessionKeyData) {
			throw new Error(`SessionKey not found for commitment: ${commitment}`)
		}

		const signature = await CryptoUtils.signSolverSelection(
			commitment,
			this.solverAddress,
			this.domainSeparator,
			sessionKeyData.privateKey,
		)
		if (!signature) {
			throw new Error("Failed to sign solver selection")
		}

		this.cachedSignature = signature
		return signature
	}

	static async signSolverSelection(
		commitment: HexString,
		solverAddress: HexString,
		domainSeparator: HexString,
		privateKey: HexString,
	): Promise<HexString | null> {
		const account = privateKeyToAccount(privateKey as Hex)

		const structHash = keccak256(
			encodeAbiParameters(
				[{ type: "bytes32" }, { type: "bytes32" }, { type: "address" }],
				[SELECT_SOLVER_TYPEHASH, commitment, solverAddress],
			),
		)

		const digest = keccak256(concat(["0x1901" as Hex, domainSeparator as Hex, structHash]))
		const signature = await account.sign({ hash: digest })

		return signature as HexString
	}

    /**
     * @dev Verifies an EIP-712 solver selection signature and stores a commitment to
     * `keccak256(abi.encode(solver, sessionKey))` in transient storage. The hash is
     * stored using `tstore` so it is only available within the same transaction —
     * this ensures atomicity between `select` and `fillOrder` calls.
     *
     * The session key is recovered from the EIP-712 signature over the (commitment, solver)
     * tuple. At fill time, `fillOrder` re-derives the same hash from `msg.sender` and
     * `order.session` and compares it against the value stored at the commitment slot.
     *
     * @param options The selection options containing the commitment, solver address, and signature.
     * @return The recovered session key address.
     */
    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }
