### Title
Unbounded recursion in wallet outer-puzzle driver chain allows a malicious offer/spend to crash a wallet via Python stack exhaustion - ([File: chia/wallet/outer_puzzles.py])

### Summary
The ALPINE-CVE-2026-32327 bug class is "unbounded native-stack recursion driven by attacker-supplied nested/recursive structure, reachable through a library function that parses untrusted input" (`apr_xml_quote_elem()` recursing once per XML nesting level). The closest reachable analog in this codebase is the wallet's outer-puzzle driver dispatch, which recurses once per curried puzzle "layer" with no depth limit, and is invoked while parsing puzzle reveals coming from an untrusted counterparty (e.g. an offer file or a synced coin's puzzle reveal).

### Finding Description
`match_puzzle()`, `get_inner_puzzle()`, `get_inner_solution()`, `construct_puzzle()`, and `solve_puzzle()` in [1](#0-0)  dispatch to per-asset-type "outer puzzle" driver objects (`CATOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `SingletonOuterPuzzle`, `CROuterPuzzle`, etc.).

Each of these drivers implements `match`/`get_inner_puzzle`/`get_inner_solution`/`construct` by unwrapping exactly one curried layer and then calling back into the *same* dispatcher (`self._match`, `self._get_inner_puzzle`, …) on the puzzle's inner puzzle, e.g.:

- `CATOuterPuzzle.match()` / `.get_inner_puzzle()` recurse via `self._match(...)` / `self._get_inner_puzzle(...)` on the next inner layer [2](#0-1) 
- `OwnershipOuterPuzzle` recurses the same way [3](#0-2) 
- `MetadataOuterPuzzle` recurses the same way [4](#0-3) 
- `SingletonOuterPuzzle` recurses the same way [5](#0-4) 
- `CROuterPuzzle` recurses the same way [6](#0-5) 

There is no depth counter or Python-side recursion-depth guard anywhere in this dispatch chain — each "also" layer in a `PuzzleInfo`, or each curried inner puzzle in a puzzle reveal, adds one native Python stack frame per driver call. The existing unit test explicitly demonstrates that nested CAT-in-CAT puzzles are a legitimate, constructible pattern (`double_cat_puzzle` wraps a CAT puzzle inside another CAT puzzle) [7](#0-6) , confirming that a puzzle reveal with N nested outer-puzzle layers is a valid, low-cost-to-construct CLVM byte blob (it doesn't need to be run/validated by CLVM to be recognized — `match_puzzle` only uncurries, it doesn't execute the program).

This driver chain is invoked from wallet-side, untrusted-input-adjacent code paths:
- `Offer._get_offered_coins()` calls `match_puzzle`, `get_inner_puzzle`, `get_inner_solution`, and `construct_puzzle` directly on `parent_spend.puzzle_reveal` taken from the (possibly attacker-supplied) `SpendBundle` inside an offer [8](#0-7) 
- `Offer.from_spend_bundle()` calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` for every coin spend in a bundle when reconstructing an `Offer` object from spend-bundle bytes [9](#0-8) 
- `UnknownPuzzle.mod` / `.curried_args` (used pervasively by these drivers) lazily uncurry on first access with `cached_property`, but caching only helps the *outer* call — every recursive inner call still constructs a brand-new `UnknownPuzzle` and a brand-new Python stack frame [10](#0-9) 

A counterparty who crafts an offer (or a coin whose puzzle reveal is later synced by a victim wallet) with a puzzle-reveal containing an arbitrarily deep chain of nested "outer puzzle" curry layers (e.g., CAT-wrapping-CAT-wrapping-CAT…, or ownership/metadata/singleton layers stacked) can drive Python's call stack to its recursion limit purely by constructing bytes with `Program.to(...).curry(...)` — no CLVM execution or cost accounting gates this, since matching happens before/independent of running the puzzle.

### Impact Explanation
When a victim wallet parses such a malicious offer (e.g., via `chia wallet take_offer`, viewing offer details in the GUI, or `WalletRpcApi` offer-inspection endpoints that route through `Offer.from_spend_bundle` / `_get_offered_coins`), the unbounded Python recursion raises `RecursionError`, which is generally unhandled in this code path (no `try`/`except RecursionError`), crashing the wallet's request-processing task or, depending on where the recursion happens (main thread of a long-lived wallet process), potentially the entire wallet process. This is a spend-triggered/offer-triggered transaction-processing halt — a denial of service against a specific wallet user or offer counterparty, matching the accepted impact category "a spend-triggered transaction-processing halt."

### Likelihood Explanation
Likelihood is only moderate-to-uncertain:
- Constructing the malicious puzzle reveal is cheap and requires no special privileges — any unprivileged offer counterparty can create it entirely off-chain with `Program.curry()` in a loop.
- However, the exact number of nesting levels needed to exhaust Python's default recursion limit (~1000) has not been empirically verified in this codebase, and I could not confirm from the index whether any outer caller (`WalletRpcApi`, offer file loader) imposes a size/complexity limit on offer or puzzle-reveal bytes before this code runs. If such a limit exists and is smaller than the required nesting depth, the issue would not be reachable.
- I was also unable to fully verify the exact `Offer.from_bytes`/deserialization entry point within the tool-call budget (grep matched but I could not retrieve the surrounding code before running out of iterations), so the precise trigger surface (bech32-decoded offer file → `from_spend_bundle`) is inferred from `from_spend_bundle`'s signature and known offer-file conventions rather than fully confirmed by direct reading of the wrapping deserialization function.

### Recommendation
- Add an explicit recursion/nesting-depth limit (e.g., a `depth` parameter threaded through `match_puzzle`, `get_inner_puzzle`, `get_inner_solution`, `construct_puzzle`, `solve_puzzle` and each driver's recursive calls) that raises a clean `ValueError` once a bounded number of "outer puzzle" layers (e.g., 50–100) is exceeded, mirroring the non-recursive design already used deliberately in `sha256_treehash()` [11](#0-10)  and the iterative rewrite of `create_graph_util`'s tree walk to avoid Python recursion limits [12](#0-11) .
- Alternatively/additionally, convert the outer-puzzle dispatch chain to an iterative loop (unwrap layers in a `while` loop, appending to a list) instead of mutual Python recursion across driver objects.
- Ensure any `RecursionError` raised while parsing untrusted offer/spend-bundle data is caught and converted into a normal validation failure rather than propagating and potentially destabilizing the wallet process.

### Proof of Concept
Conceptual PoC (depth number is illustrative and unverified against the actual Python recursion limit in the deployed environment):
```python
from chia.types.blockchain_format.program import Program
from chia.wallet.cat_wallet.cat_utils import CAT_MOD, construct_cat_puzzle
from chia.wallet.outer_puzzles import match_puzzle
from chia.wallet.puzzles.puzzle_drivers import UnknownPuzzle

ACS = Program.to(1)
tail = bytes(32)

# Build N deeply-nested CAT-wrapped-in-CAT puzzles, as already shown to be
# a valid pattern in test_cat_outer_puzzle.py.
puzzle = ACS
for _ in range(5000):  # depth chosen to exceed Python's default recursion limit
    puzzle = construct_cat_puzzle(CAT_MOD, tail, puzzle)

# Embed `puzzle` as a coin's puzzle_reveal inside a crafted offer/SpendBundle
# and send it to a victim. When the victim's wallet calls match_puzzle(...)
# (e.g. via Offer.from_spend_bundle / Offer._get_offered_coins while
# inspecting the received offer), the mutual recursion in
# CATOuterPuzzle.match -> match_puzzle -> CATOuterPuzzle.match ... exhausts
# the Python call stack and raises RecursionError.
match_puzzle(UnknownPuzzle(known_program=puzzle))
```
