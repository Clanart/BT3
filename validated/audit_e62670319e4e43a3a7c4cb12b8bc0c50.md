### Title
Unauthenticated `ReceivedOutput` deserialization accepts arbitrary offsets, outputs, and outpoints - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` interprets untrusted bytes as a spendable wallet output without validating the semantic binding that the scanner establishes between the scanner key, offset, `script_pubkey`, and on-chain outpoint. The function canonical-decodes the scalar, `TxOut`, and `OutPoint`, then returns them directly as a `ReceivedOutput`. [1](#0-0) 

### Finding Description
`Scanner` only creates a `ReceivedOutput` after matching `output.script_pubkey` against a registered Taproot script derived from `key + G * offset`. [2](#0-1)  `ReceivedOutput::read` does not preserve this invariant: a serialized object can pair any offset with any `TxOut` and any claimed `OutPoint`. [3](#0-2) 

The resulting object can be supplied to `SignableTransaction::new`, which trusts the embedded `TxOut` as the input’s previous output and derives signing offsets from the serialized `ReceivedOutput` values. [4](#0-3)  Those attacker-controlled previous outputs are subsequently committed by `taproot_key_spend_signature_hash` using `Prevouts::All`. [5](#0-4) 

### Impact Explanation
An unauthenticated byte stream can cause a caller to treat an output as received even though it was never produced by `Scanner`, does not correspond to the scanner’s key/offset relation, or does not correspond to the claimed on-chain outpoint. This satisfies the “funds reported received that are not spendable” impact class: accounting or scheduling code can accept the forged object as an owned UTXO, while transaction construction either produces signatures over a false prevout or fails once the embedded script/key mismatch is detected. [6](#0-5) 

If the embedded script is changed to an attacker-controlled Taproot key while retaining an existing victim outpoint, the object still deserializes successfully but does not represent a spendable Serai-controlled output under the victim key. [3](#0-2) 

### Likelihood Explanation
The vulnerability requires untrusted serialized `ReceivedOutput` bytes to reach `ReceivedOutput::read`; the exposed API performs canonical decoding but no authentication or contextual key validation. [1](#0-0)  No cryptographic break or privileged participant is required to construct such bytes because all three fields are attacker-controlled. [7](#0-6) 

### Recommendation
Do not deserialize `ReceivedOutput` as trusted wallet state. Include the expected scanner key in validation and reject values unless `output.script_pubkey == p2tr_script_buf(scanner_key + G * offset)`, then independently retrieve and compare the referenced on-chain transaction output before reporting or spending it. [2](#0-1)  Alternatively, remove `ReceivedOutput::read` from trust boundaries and treat deserialization as transport encoding only, requiring a subsequent scanner/chain verification phase. [1](#0-0) 

### Proof of Concept
```rust
use bitcoin::{absolute::LockTime, transaction::Version, Transaction, TxIn, TxOut, Amount, ScriptBuf};
use bitcoin::consensus::Encodable;
use bitcoin::{OutPoint, Txid, hashes::Hash};
use k256::Scalar;
use bitcoin_serai::wallet::ReceivedOutput;

// Public input: a serialized ReceivedOutput claimed to belong to the wallet.
let mut bytes = Vec::new();

// Claim offset zero, which normally means the base scanner key.
bytes.extend_from_slice(&Scalar::ZERO.to_bytes());

// Encode an arbitrary TxOut not produced by the victim's Scanner.
TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new(), // or an attacker-controlled P2TR script
}.consensus_encode(&mut bytes).unwrap();

// Claim an arbitrary outpoint.
OutPoint {
  txid: Txid::all_zeros(),
  vout: 0,
}.consensus_encode(&mut bytes).unwrap();

// Accepted despite the output not being bound to the scanner key, offset,
// claimed outpoint, or any observed transaction.
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.value(), 100_000);
assert_eq!(forged.offset(), Scalar::ZERO);
```

The crafted object is accepted because `read` only decodes the three fields and returns them without checking the scanner-derived script relationship. [3](#0-2)
