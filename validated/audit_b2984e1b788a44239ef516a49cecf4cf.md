## Title
Harvester RPC `delete_plot` performs unrestricted file deletion on any path supplied by the caller — ([File: chia/harvester/harvester_rpc_api.py])

### Summary
The harvester's `/delete_plot` RPC endpoint takes a caller-supplied `filename` string and passes it straight through to `Path.unlink()` with no check that the path is actually a plot file located in one of the harvester's configured `plot_directories`. Any local RPC caller authenticated to the harvester service can delete an arbitrary file on disk that the harvester process has permission to remove, exactly analogous to the ZimaOS bug class where a delete API accepts an attacker-controlled path without validating it against the set of allowed/managed locations.

### Finding Description
The RPC handler extracts the path directly from the request body: [1](#0-0) 

which calls into the service method: [2](#0-1) 

which in turn calls `remove_plot()`: [3](#0-2) 

`remove_plot()` performs no validation whatsoever: it does not check that the resolved path is inside any directory returned by `get_plot_directories()`, does not check the file extension (`.plot`/`.plot2`), and does not confirm the path is even tracked in `PlotManager.plots`. It simply checks `path.exists()` and calls `unlink()`. There is no path-containment/canonicalization check comparable to what would be needed to keep the delete operation scoped to configured plot directories.

The project's own internal documentation for this module confirms this is the intended (unguarded) behavior: [4](#0-3)  — "There is no extra ownership model in this module; RPC authorization and local file permissions are the relevant gates."

This mirrors the reported bug class precisely: any restriction on deletable targets (e.g., "only files inside plot directories") is assumed/enforced by the UI/client layer (`HarvesterRpcClient.delete_plot(filename)` in [5](#0-4) ), but the backend RPC handler and service method accept and act on an arbitrary path string with no server-side containment check.

### Impact Explanation
Any caller holding valid harvester RPC credentials (a private-CA-signed client cert, as used for local RPC/daemon access) can invoke `delete_plot` with an arbitrary absolute path — for example the harvester's own SSL private key, `config.yaml`, the plot manager cache, or any other file the OS user running the harvester process can write to — and have it unlinked. This can disable the harvester (deleting `ssl/harvester/private_harvester.key` or `config.yaml`), destroy plot-manager state/cache files, or delete files outside the farming directories entirely, causing local denial of service / configuration destruction on the host. Because the harvester process typically runs as the same OS user as the rest of the node's file layout (config, keys, plots), this can escalate a “local RPC caller” capability into destructive file-system impact well beyond plot management, satisfying a High-severity spend-triggered/administrative-action-triggered halt or data-loss condition.

### Likelihood Explanation
Exploitation requires only a single authenticated RPC call (`POST /delete_plot` with an attacker/misuse-controlled `filename`) from any party that already has harvester RPC access (a local admin tool, a compromised UI/automation script, or any client possessing the private RPC certificate). No additional race conditions, timing, or network positioning are needed — this is a direct, single-request confused-deputy/path-manipulation issue, making likelihood high once RPC access is available.

### Recommendation
In `HarvesterRpcApi.delete_plot` / `Harvester.delete_plot` / `remove_plot()`, validate that the resolved (canonicalized) target path is strictly contained within one of the harvester's currently configured `plot_directories` (via `get_plot_directories()`) and matches the expected plot filename pattern (`*.plot`/`*.plot2`) before calling `unlink()`. Reject the request otherwise, mirroring the containment checks already used elsewhere for directory validation (e.g., `add_plot_directory`'s existence/is-directory checks).

### Proof of Concept
1. Obtain harvester RPC access (valid private-CA client cert, as any local RPC tool would have).
2. Call the RPC:
```
POST https://<harvester-host>:8560/delete_plot
{"filename": "/home/user/.chia/mainnet/config/ssl/harvester/private_harvester.key"}
```
3. `HarvesterRpcApi.delete_plot` → `Harvester.delete_plot` → `remove_plot(Path(str_path))` unlinks the file with no check that it resides under any configured plot directory, deleting the harvester's private key file (or any other reachable file) instead of a plot.
