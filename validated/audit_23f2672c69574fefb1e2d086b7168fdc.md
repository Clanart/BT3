### Title
Permanent loss of excess `feeToken` funds due to unrecoverable 2x fee buffer in `HyperbridgeLzEndpoint` - (File: `sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol`)

### Summary
The external report's core broken invariant is: a fee-quoting function returns an amount for a payment channel that doesn't match what is actually consumed downstream, and the un-consumed remainder is neither zeroed out nor safely returned, so real value is exposed to being wasted/lost. The local Hyperbridge analog is in `HyperbridgeLzEndpoint`, the LayerZero-V2-compatible adapter that lets existing OFTs route through ISMP. Its `quote()` deliberately over-quotes the `lzTokenFee` by 2x versus what `send()` actually spends, and the excess `feeToken` that OFTs transfer in based on that quote becomes permanently trapped in the contract with no sweep/refund path.

### Finding Description
`quote()` computes the fee an OApp/OFT must pay and, for the `lzToken` (feeToken) path, deliberately doubles it as a buffer: [1](#0-0) 

The comment explains the buffer is meant to "absorb the legacy deployed host's per-byte protocol fee," and states that "excess feeToken approval is simply unused" — but this reasoning only covers the *approval*, not the tokens that were actually **transferred** into the contract.

In the real LayerZero OFT flow, when `payInLzToken` is true, the OApp calls `_payLzToken`, which transfers the *entire* quoted `lzTokenFee` (i.e., `relayerFee * 2`) into the endpoint contract before calling `send()`: [2](#0-1) 

`send()` then only approves and dispatches with `request.fee` (the un-doubled `relayerFee(_params.dstEid)`), and `EvmHost.dispatch()` pulls **exactly** `post.fee` from the endpoint via `safeTransferFrom`, not the doubled amount: [3](#0-2) 

The difference — one full `relayerFee` worth of `feeToken` per lzToken-paid message — remains sitting in the `HyperbridgeLzEndpoint` contract's own token balance. The contract has no owner or user-facing withdrawal/sweep function for its `feeToken` balance (verified by reviewing the entire contract: only `pause`/`unpause`/config setters and LZ-stub functions exist, no `withdraw`, `sweep`, or `rescue` entrypoint). Unlike `SimplexPaymaster`, which has an explicit governance-gated `_withdrawAssets`/`swapAndDeposit` recycling path, `HyperbridgeLzEndpoint` has none.

### Impact Explanation
Every message sent through this endpoint using the `lzToken`/feeToken payment path (the recommended, gas-cheaper path per the docs) permanently locks 50% of the transferred fee amount inside the endpoint contract, unrecoverable by the payer, the OApp, or the protocol owner. This is a direct, systemic loss of funds for every user of the feeToken payment path — not a one-off edge case but the default accounted behavior of `quote()`/`send()`. Over the lifetime of the deployed adapter this compounds into significant stuck value with no code path to reclaim it, matching the "stealing or loss of funds" impact category.

### Likelihood Explanation
This is triggered by ordinary, expected usage — any OFT/OApp built on `HyperbridgeLzEndpoint` that quotes and pays in `lzToken` (as recommended for gas efficiency) hits this on every single send. No malicious peer, relayer, prover, or governance actor is required; it is a self-contained accounting bug in the adapter's own `quote()`/`send()` pair, reachable by any unprivileged caller of the standard OFT send flow.

### Recommendation
Either (a) have `send()` sweep/refund the actual excess `feeToken` balance back to the payer/refund address after dispatch, or (b) remove the 2x buffer from `quote()`'s `lzTokenFee` and instead compute the exact per-byte legacy-host fee on-chain so the quoted and consumed amounts match, or (c) add an owner-gated (or automatic, permissionless) sweep function analogous to `SimplexPaymaster.swapAndDeposit`/`_withdrawAssets` that can recover the residual `feeToken` balance and return/recycle it rather than leaving it permanently stranded.

### Proof of Concept
1. Owner calls `setHost` and `setEidMapping` to configure a destination chain, with `relayerFee(dstEid) = F` (feeToken units).
2. An OFT wired to this endpoint calls `quote(params, sender)` with `payInLzToken = true`. Per lines 341-345, this returns `lzTokenFee = F * 2`.
3. The OFT's `_payLzToken` logic transfers `F * 2` feeToken into `HyperbridgeLzEndpoint`.
4. The OFT calls `send(params, refundAddress)`. Since `msg.value == 0`, the branch at lines 298-305 executes: the endpoint approves its **full balance** (`F * 2`) to the host, but `dispatch()` in `EvmHost` (lines 921-932) only pulls `post.fee = F` via `safeTransferFrom`.
5. Result: `F` feeToken tokens remain in `HyperbridgeLzEndpoint`'s balance. No function in the contract can move this balance out — repeating step 1-4 for N messages accumulates `N * F` permanently stuck tokens.
