### Title
Bridge trusts declared `_value` instead of measured token receipt in `requestERC20Transfer`, enabling fee-on-transfer/rebasing ERC20 to desync escrow vs. minted/released value - ([File: contracts/service_chain/bridge/BridgeTransferERC20.sol])

### Summary
`requestERC20Transfer()` calls `safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))` and then emits `RequestValueTransfer` carrying the caller-supplied `_value`, without ever verifying that the bridge contract's balance actually increased by that amount. This mirrors exactly the Sudoswap `_validateTokenInput()` bug class: a token transfer path exists that never checks the real number of tokens received, trusting the nominal transfer amount instead.

### Finding Description
`requestERC20Transfer` in [1](#0-0)  performs `IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))` and immediately proceeds to `_requestERC20Transfer`, which emits `RequestValueTransfer(..., _value, ...)` using the parameter `_value` — not a measured before/after balance delta of the bridge contract. `safeTransferFrom` (via `SafeERC20.callOptionalReturn`, [2](#0-1) ) only checks that the call succeeded and optionally returned `true`; it does not check the actual amount credited to the recipient. For a fee-on-transfer or rebasing ERC20 token, the bridge may receive fewer tokens than `_value + _feeLimit`, yet the emitted event (and the nonce-based value-transfer vote mechanism operators rely on) still records the full nominal `_value`.

On the counterpart chain, `handleERC20Transfer` ( [3](#0-2) ) mints or releases exactly `_value` tokens based on that same operator-relayed event data, with no cross-check against what was actually escrowed/burned on the source chain. Additionally, in `modeMintBurn`, `_requestERC20Transfer` calls `ERC20Burnable(_tokenAddress).burn(_value)` ( [4](#0-3) ) — if the bridge actually received less than `_value` due to token fees, this burn call would revert or burn from insufficient balance, but in the escrow (non mint-burn) mode there is no such safety net at all: the bridge simply forwards whatever balance it holds later based on `_value`, with no relation to actually-escrowed funds. Token registration (`registerToken` in `BridgeTokens.sol`, [5](#0-4) ) imposes no restriction on token behavior — any ERC20-compatible address can be registered by the owner, including deflationary/fee-on-transfer/rebasing tokens.

### Impact Explanation
If a registered ERC20 token exhibits transfer fees or rebasing, an unprivileged caller invoking `requestERC20Transfer` can cause the bridge to record and later relay (once approved by operators) a `_value` amount larger than what was actually escrowed in the bridge contract's balance. In escrow (non-mint-burn) mode this directly creates a shortfall between the bridge's real token reserves and the cumulative amount it is expected to release across both chains — a supply/accounting divergence that can be exploited to drain the bridge's genuine token reserves over repeated round-trips (deposit token with fee -> only partial amount escrowed -> full nominal `_value` released on the other chain -> repeat), effectively inflating claimable value beyond real backing.

### Likelihood Explanation
Exploitation requires the token registered via `registerToken` to have non-standard transfer semantics (fee-on-transfer or rebasing) — this needs either an owner registering such a token (intentionally or by mistake) or a token later becoming fee-on-transfer/rebasing after registration (e.g., through an upgradeable token). Sudoswap's own team classified the analogous issue as Medium risk with the same caveat ("pair creators would have to willingly deploy ... a token using non-standard ERC20 token behavior"), so likelihood here is similarly conditioned on token selection rather than being universally exploitable against arbitrary tokens.

### Recommendation
In `requestERC20Transfer` (and `onERC20Received`), measure the actual balance delta of the bridge contract before and after `safeTransferFrom`, and use that measured amount — not the caller-supplied `_value` — as the value emitted in `RequestValueTransfer` and used for burn accounting. Alternatively/additionally, restrict `registerToken` to disallow tokens with non-standard transfer behavior, or document and enforce that only standard ERC20 tokens (no fee-on-transfer/rebasing) can be registered.

### Proof of Concept
1. Bridge owner registers a fee-on-transfer ERC20 token `T` via `registerToken(T, cT)` (`BridgeTokens.sol` lines 57-71).
2. A user calls `requestERC20Transfer(T, to, value, feeLimit, extraData)`.
3. `safeTransferFrom(msg.sender, address(this), value + feeLimit)` executes, but because `T` charges a transfer fee, the bridge actually receives `< value + feeLimit`.
4. `_requestERC20Transfer` still emits `RequestValueTransfer(..., value, ...)` using the full nominal `value`, unaffected by the real amount received (`BridgeTransferERC20.sol` lines 76-108).
5. Once operators vote/approve, `handleERC20Transfer` on the counterpart chain mints or transfers the full `value` to `to` (`BridgeTransferERC20.sol` lines 32-73), exceeding what was actually escrowed/burned on the source chain — repeating this process progressively desyncs the bridge's real reserves from its liability.

Note: I could not access the source of `GaslessSwapRouter.sol` (only its Go bindings are indexed) to confirm whether a similar unmeasured-transfer issue exists in the `kaiax/gasless` swap execution path; that avenue remains unverified due to index limitations, and a Devin session with full repo access could confirm or rule it out.
