### Title
Zero-slippage buyback swap in `ArbWomUp3._deposit`/`SmartWomConvert._convertFor` enables sandwich-attack theft of user WOM value - ([File: wombat/ArbWomUp3.sol, wombat/SmartWomConvert.sol])

### Summary
`ArbWomUp3.incentiveDeposit` (mode 2) calls `SmartWomConvert.convert` with a hard-coded `_minRec` of `0`, and `SmartWomConvert._convertFor` in turn executes the WOM→mWOM buyback swap on the Wombat pool with a hard-coded minimum-out of `0`. Both layers of slippage protection are disabled, so the swap price is whatever the Wombat pool's current cash/liability curve happens to be at execution time, letting an attacker sandwich the user's transaction and extract value directly from the user's deposited WOM.

### Finding Description
In `ArbWomUp3._deposit`, when `_mode == 2`, half of the user's deposited WOM is routed through the external `SmartWomConvert` contract: [1](#0-0) 

The call `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` passes `_minRec = 0`. Inside `SmartWomConvert._convertFor`, this `_minRec` is the *only* protection check applied, and it is checked against the *combined* result of a direct 1:1 mint (`convertAmount`) and a pool swap (`amountRec`) — but since it is `0`, it never reverts: [2](#0-1) 

Crucially, the actual on-chain swap itself is also executed with no slippage bound:
```solidity
amountRec = IWombatRouter(router).swapExactTokensForTokens(
    tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp
);
``` [3](#0-2) 

The swap rate is determined entirely by the live state of `womMWomPool` (Wombat's cash/liability curve), which functions analogously to the Uniswap spot price in the external report: it can be freely moved within a single block by any actor executing a large swap against the same pool immediately before the victim's transaction, and reversed immediately after. Because both the router-level `amountOutMin` and the aggregate `_minRec` check are `0`, there is no mechanism to bound how unfavorable the executed price can be — the victim's WOM is swapped at whatever price the attacker has pushed the pool to.

### Impact Explanation
This directly causes theft of user funds: a user calling `incentiveDeposit` with `_mode == 2` has half of their WOM converted at an attacker-manipulated rate, and the resulting mWOM shortfall relative to fair value is captured by the sandwiching attacker when they reverse their manipulation trade. Since the check is against `0`, the transaction never reverts to protect the user — the loss is silent and final, satisfying the "concrete direct theft of user funds" bar.

### Likelihood Explanation
Likelihood is high for any user who calls `incentiveDeposit(..., _mode == 2)` (the "lock" path of the ArbWomUp3 airdrop program) — this is a normal, unprivileged, user-initiated action with no special preconditions. Sandwiching a public mempool transaction against a known, low-liquidity conversion pool (`womMWomPool`) is a standard, low-cost MEV technique requiring no privileged access.

### Recommendation
Do not hard-code `_minRec = 0` when calling `SmartWomConvert.convert` from `ArbWomUp3._deposit`; instead accept and forward a caller-supplied, meaningful minimum-output parameter (e.g., computed off-chain via `estimateTotalConversion` with an acceptable slippage tolerance) so the aggregate check in `_convertFor` can actually revert on unfavorable execution. Additionally, `SmartWomConvert._convertFor` should pass a non-zero, proportionally-derived `amountOutMin` into `swapExactTokensForTokens` itself (rather than `0`), and/or use a TWAP-based reference price to bound acceptable execution price, rather than relying solely on a post-trade aggregate check that can be trivially bypassed by passing `_minRec = 0`.

### Proof of Concept
1. Attacker monitors the mempool for calls to `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, false, 2)`.
2. Before the victim's transaction, attacker swaps a large amount of mWOM into `womMWomPool` via the Wombat router, skewing `cash`/`liability` so that WOM→mWOM conversion becomes unfavorable.
3. Victim's transaction executes: `ArbWomUp3._deposit` calls `SmartWomConvert.convert(toSwap, _convertRatio, 0, 0)`, which calls `swapExactTokensForTokens(..., amountOutMin = 0, ...)` — executing at the manipulated price with no revert possible since both minimums are `0`.
4. Attacker immediately reverses their initial swap, restoring the pool and pocketing the spread extracted from the victim's WOM, while the victim receives less mWOM than fair value with no way to detect or prevent it on-chain.
