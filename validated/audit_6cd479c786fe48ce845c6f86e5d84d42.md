### Title
DataLayer mirror-URL fetching is attacker-controlled server-side request forgery - (File: chia/data_layer/data_layer.py)

### Summary
Any wallet participant can publish a `Mirror` coin on-chain that attaches an arbitrary list of URL strings (as memos) to a DataLayer `launcher_id`. Every node that tracks that launcher — because it owns, subscribes to, or otherwise follows that DataLayer store — automatically ingests those attacker-chosen URLs into its local subscription table and later fetches from them over plain HTTP with no destination restriction, mirroring the phpseclib SSRF pattern (untrusted-input URL → default-on outbound fetch → no destination allow/deny list).

### Finding Description
`DataLayerWallet.coin_added()` watches for coins sent to the fixed, publicly known `create_mirror_puzzle()` puzzle hash. When such a coin appears, it decodes the URL list straight out of the spend's memos via `get_mirror_info()` and, if the wallet is already tracking that `launcher_id`, stores the URLs verbatim as a `Mirror` with no validation of host, scheme, or port: [1](#0-0) 

The only puzzle used for these coins is a global, attacker-spendable puzzle — anyone can create one by spending their own coin with `create_new_mirror()`/`DLNewMirror`, paying just a fee and an amount, and embedding arbitrary bytes as "urls": [2](#0-1) [3](#0-2) 

The DataLayer service periodically pulls these wallet-known mirror URLs and merges them into its subscription table without validation: [4](#0-3) [5](#0-4) 

Those URLs are then used as fetch targets during the sync loop, which runs unattended for every tracked/subscribed store: [6](#0-5) [7](#0-6) 

The project's own module notes acknowledge mirror URLs are untrusted external input but only in the sense of "don't trust the *data* returned" — not that the *destination itself* is validated before connecting: [8](#0-7) [9](#0-8) 

This is structurally identical to the phpseclib bug class: (1) URL comes from untrusted on-chain input controlled by an unprivileged spender, (2) fetching happens automatically as part of normal periodic sync with no opt-in beyond already tracking/subscribing to the store, and (3) there is no restriction on destination host/port (loopback, `169.254.169.254`, internal service ports, etc. are all reachable), consistent with the test suite's own use of bare loop-back mirror URLs like `http://127.0.0.1/8000`. [10](#0-9) 

### Impact Explanation
Any user who can afford a small on-chain fee can force any node that tracks a given DataLayer store (its owner, or any wallet/offer counterparty subscribed to it for offer verification) to open outbound HTTP connections to an attacker-chosen host and port — including loopback services, cloud metadata endpoints, or other internal-only services reachable from the victim's machine. This is unauthenticated network reconnaissance/SSRF against operators running DataLayer nodes (a supported, non-privileged production feature used for offers and store replication), satisfying the CWE-918 pattern from the reference advisory. Although the fetched content must still parse as a valid delta/full-tree file to be accepted into the Merkle store (limiting confidentiality impact, similar to phpseclib's "blind" AIA fetch), the request-forgery/reconnaissance primitive itself is fully attacker-controlled and free of destination checks.

### Likelihood Explanation
Likelihood is high for any environment where DataLayer subscriptions/offers are used: mirror-coin creation requires no special permission beyond a standard spend (a fee and mirror amount), the mirror puzzle hash is public/fixed, and any node tracking the targeted `launcher_id` (owner or subscriber) will pick up the URL automatically on its next `periodically_manage_data()` cycle without any explicit approval of the specific URL.

### Recommendation
- Validate mirror/subscription URLs before they are ever attempted as fetch targets: reject loopback, link-local (`169.254.0.0/16`), private ranges, and disallow arbitrary ports unless explicitly allow-listed by the operator.
- Require explicit operator opt-in (e.g., a config flag) before URLs discovered via on-chain mirror coins are auto-subscribed, distinct from URLs a user manually supplies via `subscribe`/`add_mirror` on their own store.
- Add an egress policy hook (analogous to phpseclib's suggested callback) that operators can use to restrict/inspect DataLayer HTTP fetch destinations.
- Document clearly that tracking/subscribing to any DataLayer store can result in outbound HTTP requests to URLs supplied by unrelated third parties via on-chain mirror coins.

### Proof of Concept
1. Attacker identifies a `launcher_id` that the victim's DataLayer node tracks (its own owned store, or a store it has subscribed to for an offer).
2. Attacker calls `dl_new_mirror` (or the CLI `chia data add_mirror`) on their own wallet, specifying `launcher_id=<victim's store>`, a small `amount`, `fee`, and `urls=["http://127.0.0.1:6379/", "http://169.254.169.254/latest/meta-data/"]`: [11](#0-10) 
3. Once the spend confirms, the victim's `DataLayerWallet.coin_added()` observes the mirror coin (puzzle hash matches the public mirror puzzle), decodes the attacker URLs, and stores them because the victim's node already tracks `launcher_id`: [1](#0-0) 
4. On the victim's next `periodically_manage_data()` cycle, `update_subscriptions_from_wallet()` merges the attacker URLs into the local subscription table, and `update_subscription()`/`fetch_and_validate()` attempts an HTTP connection to each URL as part of normal delta-file discovery: [4](#0-3) [6](#0-5) 
5. The victim's node makes an outbound request to the attacker-chosen host/port, confirmable by an attacker-controlled listener or by observing connection attempts to internal-only services, without any interaction from the victim beyond already tracking the store.

**Note on verification depth:** I could not fully trace the low-level HTTP client call inside `insert_from_delta_file()`/`fetch_and_validate()` (in `chia/data_layer/download_data.py`) within the indexed context to confirm exactly which library performs the GET and whether any implicit proxy/timeout settings partially mitigate reachability of certain address ranges; the index did not return that file's contents. A Devin session with full repository access would be needed to inspect `chia/data_layer/download_data.py` directly to confirm the exact request mechanics and any existing (if any) URL-scheme/host filtering.

def create_mirror_puzzle() -> Program:
    return P2_PARENT.curry(Program.to(1))


MIRROR_PUZZLE_HASH = create_mirror_puzzle().get_tree_hash()


def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")

    async def update_subscriptions_from_wallet(self, store_id: bytes32, new_urls: list[str]) -> None:
        async with self.db_wrapper.writer() as writer:
            cursor = await writer.execute(
                "SELECT * FROM subscriptions WHERE from_wallet == 1 AND tree_id == :tree_id",
                {
                    "tree_id": store_id,
                },
            )
            old_urls = [row["url"] async for row in cursor]
            cursor = await writer.execute(
                "SELECT * FROM subscriptions WHERE from_wallet == 0 AND tree_id == :tree_id",
                {
                    "tree_id": store_id,
                },
            )
            from_subscriptions_urls = {row["url"] async for row in cursor}
            additions = {url for url in new_urls if url not in old_urls}
            removals = [url for url in old_urls if url not in new_urls]
            for url in removals:
                await writer.execute(
                    "DELETE FROM subscriptions WHERE url == :url AND tree_id == :tree_id",
                    {
                        "url": url,
                        "tree_id": store_id,
                    },
                )
            for url in additions:
                if url not in from_subscriptions_urls:
                    await writer.execute(
                        "INSERT INTO subscriptions(tree_id, url, ignore_till, num_consecutive_failures, from_wallet) "
                        "VALUES (:tree_id, :url, 0, 0, 1)",
                        {
                            "tree_id": store_id,
                            "url": url,
                        },
                    )
