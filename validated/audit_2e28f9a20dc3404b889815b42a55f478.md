### Title
Unauthenticated CPU exhaustion via quadratic Lagrange interpolation in `ThresholdKeys::read` - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
A serialized `ThresholdKeys` object can specify up to 65,535 participants and select Lagrange interpolation. During deserialization, `ThresholdKeys::read` accepts attacker-controlled `t` and `n`, reads `n` verification shares, then calls `ThresholdKeys::new`. `ThresholdKeys::new` computes a Lagrange interpolation factor for each of the first `t` participants, and each factor calculation iterates over all `t` participants, producing `O(t²)` field operations. A few megabytes of attacker-controlled input can therefore trigger billions of scalar operations. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`ThresholdKeys::read` trusts the serialized threshold parameters before performing any bound on computational cost. The attacker can set `t = n = 65535`, use interpolation byte `1` for `Interpolation::Lagrange`, provide one scalar and 65,535 canonical group encodings, and pass validation because `t <= n` and `i <= n`. [4](#0-3) [5](#0-4) 

`ThresholdKeys::new` then builds `included = 1..=t` and evaluates `interpolation.interpolation_factor(*i, &t)` once for every participant. For Lagrange interpolation, each call iterates over every other participant and performs field multiplication, subtraction, and a final inversion. With `t = 65535`, this executes approximately `65535²` inner-loop operations, or over 4.29 billion iterations. [2](#0-1) [3](#0-2) 

### Impact Explanation
Any service that calls `ThresholdKeys::read` on attacker-supplied bytes can be forced to spend excessive CPU time reconstructing keys. The input itself is only on the order of a few megabytes for typical 32-byte scalar and compressed-point encodings, while the resulting Lagrange computation is quadratic in the encoded participant count. Repeated submissions can saturate worker threads or block a single-threaded caller, producing denial of service. [6](#0-5) [3](#0-2) 

### Likelihood Explanation
The attack requires no private state, valid threshold key, signature, or protocol cooperation. All scalar and point encodings can be canonical and individually valid; the expensive path is reached solely through attacker-selected `t`, `n`, and the Lagrange variant. Exploitation depends on an integration exposing `ThresholdKeys::read` to untrusted serialized data, which is the explicitly reachable input surface. [1](#0-0) 

### Recommendation
Bound the deserialization work before calling `ThresholdKeys::new`. Practical mitigations include:

- Impose a protocol-appropriate maximum `n` and `t` in `ThresholdKeys::read` rather than allowing the full `u16` range.
- Precompute and cache Lagrange factors so group-key derivation is not quadratic.
- Reject large `n` for `Interpolation::Lagrange` during deserialization unless an application explicitly opts in.
- Decode untrusted `ThresholdKeys` in a bounded worker with input-size and CPU limits.

The parameter validation and expensive group-key construction are located in `ThresholdParams::new`, `ThresholdKeys::read`, `Interpolation::interpolation_factor`, and `ThresholdKeys::new`. [5](#0-4) [2](#0-1) [1](#0-0) 

### Proof of Concept
The serialized format is:

```text
u32 curve_id_len || curve_id
u16 t || u16 n || u16 participant_i
u8 interpolation
scalar encoding
n group encodings
```

Set `t = 65535`, `n = 65535`, `participant_i = 1`, `interpolation = 1` for Lagrange, then provide a canonical scalar followed by 65,535 canonical copies of the generator encoding. Deserialization reaches `ThresholdKeys::new`, which evaluates 65,535 Lagrange factors over a 65,535-element signing set. [1](#0-0) [3](#0-2) 

```rust

//   [1]                     // Lagrange interpolation
//   canonical scalar encoding
//   canonical generator encoding repeated 65535 times
//
// ThresholdKeys::<C>::read(&mut bytes) then performs O(65535^2)
```

```rust
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;

          if i == *l {
            continue;

          num *= share;
          denom *= share - i_f;

        // (which we have an if case to avoid)
```
