## Analysis

The external report's core broken invariant: **an authoritative contract-reference is swapped in place, and messages/state produced under the old reference are silently judged against the new one**, letting one side settle twice while the other permanently fails.

The Hyperbridge analog is the `_instances` mapping in `evm/src/apps/intentsv2/IntentsBase.sol`, which records the trusted IntentGatewayV2 deployment address per remote state machine, and is consumed asymmetrically by the cross-chain redeem/refund and cancel paths in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`.

### Title
Immediate `_instances` remap in IntentGatewayV2 lets solvers pay out while users are also refunded (double-settlement) - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`_addDeployment` overwrites the trusted remote-gateway address for a state machine in place, with no draining period and no versioning of in-flight orders. [1](#0-0)  Because the storage-proof key used for cancellation, and the sender-authentication check used for redeem/refund, both re-read the *current* `_instances` value rather than the value that was active when the order was filled, an order that was legitimately filled against the old gateway address can be refunded on the source chain as if it were never filled, while the solver's original `RedeemEscrow` message becomes permanently unauthenticatable.

### Finding Description
- `_addDeployment` (invoked from `onAccept` on `RequestKind.NewDeployment`) sets `_instances[keccak256(body.chain)] = body.gateway` unconditionally and immediately. [1](#0-0) 
- When a solver fills a cross-chain order on the destination chain, `_fillCrossChain` marks `_filled[commitment] = msg.sender` on the destination gateway and dispatches a `RedeemEscrow` message back to `_instance(order.source)` — the *source*-chain gateway address as known to the *destination* deployment. [2](#0-1) 
- On the source chain, that `RedeemEscrow` message is authenticated in `_authenticate`, which compares the message's `from` address to `_instance(request.source)` — the *current* value of `_instances` for that chain. [3](#0-2) [4](#0-3) 
- Independently, if the user calls `_cancelFromSource` after the deadline (because the redeem message is still in flight, e.g. delayed relaying), the GET storage-proof key is built from `_instance(order.destination)` — again the *current* registered address — concatenated with the `_filled` slot hash, and dispatched to read that address's storage on the destination chain. [5](#0-4) 
- `onGetResponse` refunds escrow whenever the returned slot value is empty: `if (incoming.response.values[0].value.length != 0) revert Filled();` otherwise it unconditionally calls `_withdraw(..., isRefund: true, finalize: true)`. [6](#0-5) 

If governance migrates the registered gateway for a chain (a normal `NewDeployment` operation — e.g. moving to a new proxy address) while an order that was already filled against the *old* gateway is still awaiting its `RedeemEscrow` message:
1. The cancel's storage proof is read from the *new* gateway address, whose `_filled[commitment]` slot was never touched by the actual fill — it reads as empty, so `onGetResponse` refunds the user's escrow on the source chain, believing the order was never filled.
2. When the solver's original `RedeemEscrow` message (whose `from` field is immutably the *old* gateway address) later arrives, `_authenticate` compares it against the *new* `_instances` value and reverts with `Unauthorized`, so the solver is never paid from escrow.

The solver has already delivered the output tokens to the beneficiary at fill time (unconditionally, before any cross-chain message is even sent, per `_fillCrossChain`). [7](#0-6)  So the net result is the protocol pays out twice for one order: once to the solver (output tokens) and once to the user via refund — a double-settlement causing direct loss of escrowed input tokens, with no code path checking that the redeem/refund pairing is bound to the specific gateway instance that actually performed the fill.

### Impact Explanation
This directly matches the bounty's fund-loss / double-settlement class: escrowed input tokens are released to the wrong party (refunded to the user) even though a solver already fulfilled the obligation and is entitled to those funds, and the solver's legitimate claim path is permanently blocked (`Unauthorized`), with no recovery mechanism since `_instances` holds only the latest value.

### Likelihood Explanation
This requires only a normal, expected governance operation — registering/updating a gateway deployment for a chain via `NewDeployment` — combined with an order whose redeem message is still in flight when that update lands. No malicious relayer, prover, or governance intent is required; it is a race inherent to overwriting `_instances` in place with no transition/draining window and no per-order binding to the instance address active at fill time.

### Recommendation
Bind each order's redeem/cancel authentication and storage-proof key to the specific gateway instance address that was registered at the time the order was placed/filled (e.g., snapshot `_instance(...)` into the order or commitment context), or retain historical `_instances` entries and validate incoming messages/proofs against any previously valid address for that chain, similar to avoiding "two active versions" ambiguity flagged in the original zAuction report. At minimum, gate `_addDeployment` so that migrating a chain's instance requires no in-flight orders for that chain, or maintain a mapping capable of recognizing both the old and new instance for a safe transition period.

### Proof of Concept
1. Gateway A (chain A) has `_instances[hash(chainB)] = G_old`.
2. User places order on A with `destination = chainB`, escrowing input tokens (`_orders[commitment][token] > 0`).
3. Solver fills the order on `G_old` (chain B): `_filled[commitment] = solver` is set in `G_old`'s storage, output tokens are sent to beneficiary immediately, and a `RedeemEscrow` post request is dispatched to A with `from = G_old`.
4. Before that message is relayed/executed, Hyperbridge governance issues `NewDeployment` for chainB pointing at `G_new` on gateway A; `_addDeployment` overwrites `_instances[hash(chainB)] = G_new` immediately. [1](#0-0) 
5. The order's deadline passes before the `RedeemEscrow` message lands (or the user simply calls cancel first); user calls `_cancelFromSource`, which builds the storage-proof key from `_instance(chainB) = G_new` and dispatches a GET. [8](#0-7) 
6. `G_new`'s `_filled[commitment]` slot is empty (it never processed this order), so the GET response returns empty and `onGetResponse` refunds the user's escrow in full. [6](#0-5) 
7. The delayed `RedeemEscrow` from `G_old` finally arrives at A's `onAccept`; `_authenticate` computes `_instance(chainB) = G_new != G_old`, so it reverts `Unauthorized` — the solver's claim is permanently blocked. [3](#0-2) 
8. Net effect: the solver paid the beneficiary in step 3 and receives nothing back; the user received a refund in step 6 that they were not entitled to — the protocol/solver has lost the escrowed funds.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        if (options.nativeDispatchFee > 0 && msgValue >= options.nativeDispatchFee) {
            IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request);
            msgValue -= options.nativeDispatchFee;
        } else {
            dispatchWithFeeToken(request);
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
