### Title
SignableTransaction trusts deserialized `ReceivedOutput` values and never deduplicates outpoints, allowing cumulative claimed inputs to exceed the wallet's real balance - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The Ethereum report's bug class is per-item validation without cumulative accounting: `get_expected_withdrawals` checked each pending withdrawal against the validator's balance individually, so two individually-valid withdrawals summed to more than the balance, causing a downstream subtraction underflow and a client disagreement. The analog in Serai's `networks/bitcoin` wallet is `SignableTransaction::new`: it sums the *claimed* `value` of every supplied `ReceivedOutput` (`input_sat`) and checks `input_sat < payment_sat + needed_fee` once, but it never (a) verifies the serialized `TxOut`/`OutPoint` bytes correspond to a real on-chain UTXO, nor (b) deduplicates inputs by `outpoint`. An attacker who can feed crafted bytes to `ReceivedOutput::read` can supply inputs whose cumulative claimed value exceeds the multisig's real balance — exactly the "multiple withdrawals exceeding balance" pattern — and the multisig will sign a transaction committing (via `Prevouts::All`) to fabricated prevout amounts.

### Finding Description
`ReceivedOutput::read` deserializes `offset`, `output` (a `TxOut`, including its `value` and `script_pubkey`), and `outpoint` verbatim with no semantic validation — the `value` field is fully attacker-controlled. [1](#0-0) 

`SignableTransaction::new` then computes `input_sat` as the plain sum of claimed values and builds one `TxIn` per input with no check for duplicate outpoints. [2](#0-1) 

The only solvency check is `input_sat < payment_sat + needed_fee` and the change computation `input_sat.checked_sub(payment_sat + fee_with_change)`, both operating purely on claimed values. [3](#0-2) 

The claimed `TxOut`s are stored as `prevouts` and later committed into every input's sighash via `Prevouts::All(&self.tx.prevouts)`, so the threshold signature binds to the fabricated amounts. [4](#0-3) [5](#0-4) 

Like the Ethereum bug, each component is individually "valid" (each `TxIn` is well-formed, the aggregate check passes) while the *cumulative* claimed input value exceeds the real spendable balance, and downstream arithmetic (`fee()` at send.rs:139, `prevouts - outputs`, a bare `u64` subtraction) can panic on underflow.

### Impact Explanation
Two attacker-reachable effects:

1. **Unfunded payment signed by the multisig.** Supplying a `ReceivedOutput` whose `script_pubkey` matches a registered offset (or offset zero — the base P2TR script, which is publicly known) but with an inflated `value` lets `input_sat` pass the solvency check for a payment the wallet cannot actually fund. The multisig produces a fully valid-looking signed transaction paying the attacker, committing to a prevout amount that doesn't exist. Downstream accounting (e.g., a processor recording the payment as executed, or the expected change output) is corrupted: funds are reported as spendable/sent that never will be, and the change output the wallet expects never materializes. This is the direct analog of "withdraw more than current validator balance."

2. **Duplicate-outpoint double-count.** Two `ReceivedOutput`s referencing the same real outpoint each contribute their value to `input_sat` and each becomes a `TxIn`. The transaction is invalid on-chain, but the wallet logic treats the balance as doubled, and `fee()`'s unchecked subtraction can panic — a DoS crashing the signing path.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ReceivedOutput::read` (explicitly listed as an untrusted sink) or a scanner/serialization path that does not cross-check the claimed `TxOut` against chain state. `SignableTransaction::new` performs no on-chain verification itself and no outpoint dedup, so the defect is unconditional in this code; the only mitigation is that `multisig()` verifies `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey`, which constrains the *script* but not the *value* or the *outpoint* — an attacker can reuse a genuinely-observed script_pubkey (e.g., the multisig's base address or a known offset address) with a fabricated value and a fabricated or duplicated outpoint.

### Recommendation
- In `SignableTransaction::new`, reject duplicate `outpoint`s among `inputs` (insert into a `HashSet` and error on collision).
- Treat `ReceivedOutput` as untrusted provenance: require the caller (or scanner) to only pass outputs verified against confirmed chain state, and document this as a hard invariant; ideally carry a proof or have `new` take only scanner-produced outputs.
- Make `fee()` use `checked_sub` and return an error rather than panicking on inconsistency.

### Proof of Concept

// networks/bitcoin context: attacker-controlled bytes -> ReceivedOutput::read
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction};
use bitcoin::{OutPoint, TxOut, Amount, Txid};

// A real output the multisig received: script_pubkey = p2tr(group_key), value = 1_000 sats.
let real_script = p2tr_script_buf(group_key).unwrap();
let real_outpoint = OutPoint::new(real_txid, 0);

// Craft bytes: same script_pubkey and outpoint, but claim 10 BTC.
let forged = TxOut { value: Amount::from_sat(1_000_000_000), script_pubkey: real_script.clone() };
let mut bytes = Vec::new();
bytes.extend(Scalar::ZERO.to_repr().as_ref());       // offset = 0 (base key)
bytes.extend(bitcoin::consensus::serialize(&forged));
bytes.extend(bitcoin::consensus::serialize(&real_outpoint));
let ro = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// Also duplicate it: same outpoint counted twice.
let ro2 = ro.clone();

// SignableTransaction accepts: input_sat = 20 BTC claimed against 0.00001 BTC real.
let payment_to_attacker = (attacker_script, 500_000_000u64); // 5 BTC
let tx = SignableTransaction::new(
    vec![ro, ro2],
    &[payment_to_attacker],
    Some(real_script), // change back to multisig
    None,
    fee_per_vbyte,
).unwrap(); // succeeds: checks pass on phantom input value

// multisig() passes the prevout script check and produces signing machines that

// transaction can never confirm, but all internal accounting treats the 5 BTC
// payment and ~15 BTC change as funded — cumulative claimed inputs exceed the
