### Title
Assertion failure (panic) in PedPoP `Decryption::register` on re-registration aborts honest participants - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The Exiv2 bug class is an assertion failure reachable via crafted input, causing denial of service. Serai's PedPoP DKG contains the same shape: `Decryption::register` enforces "one encryption-key registration per participant" with `assert!` rather than a recoverable error, and `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` unconditionally. An unprivileged participant in the DKG can reach both code paths with public inputs (an extra `EncryptionKeyMessage`, or an accusation naming a decryptor who never registered), turning malformed input into a process panic on every honest party that processes it.

### Finding Description
`Decryption::register` panics if a participant submits a second `EncryptionKeyMessage`:

```rust
// crypto/dkg/pedpop/src/encryption.rs:351-362
pub(crate) fn register<M: Message>(
    &mut self,
    participant: Participant,
    msg: EncryptionKeyMessage<C, M>,
) -> M {
    assert!(
        !self.enc_keys.contains_key(&participant),
        "Re-registering encryption key for a participant"
    );
    self.enc_keys.insert(participant, msg.enc_key);
    msg.msg
}
```

The peer-controlled type `EncryptionKeyMessage` is parsed from untrusted bytes via `EncryptionKeyMessage::read` (lines 57–59), which happily deserializes `M::read` plus `C::read_G`. Nothing in the read path prevents the same `participant` from appearing twice; the duplicate-detection invariant is enforced only by the `assert!` inside `register`.

A second reachable panic is in `decrypt_with_proof` (lines 381–390): the expression `self.enc_keys[&decryptor]` uses `HashMap` indexing, which panics on a missing key. The `decryptor` participant is attacker-chosen, so a blame/accusation flow naming a decryptor who never submitted an `EncryptionKeyMessage` panics instead of returning `DecryptionError`. Relatedly, `Encryption::encrypt` (line 466) indexes `self.decryption.enc_keys[&participant]` the same way.

### Impact Explanation
Availability: medium. A single malformed (or duplicated) DKG message from one participant causes a panic in every honest party that runs `register`, aborting their key-generation session and, depending on the caller, the process. In `decrypt_with_proof`, an accusation naming an unregistered decryptor panics during blame resolution rather than cleanly reporting `DecryptionError::InvalidProof`, preventing the protocol from completing or correctly identifying the faulty party. This mirrors the Exiv2 advisory exactly: an assertion reachable only on the less-common input path (duplicate registration / blame flow) that kills the process.

### Likelihood Explanation
Medium. Triggering it requires only that a DKG participant broadcast a second `EncryptionKeyMessage` under its own participant index, or that an accusation message reference a decryptor index with no registered key — both are attacker-controlled, public protocol inputs with no signature/precondition gating. The panic occurs before any validity check could reject the input, so honest nodes crash deterministically. Impact is limited to availability (no secret leakage or forgery), consistent with a Medium (CVSS ~5.5) rating.

### Recommendation
Replace the `assert!` in `Decryption::register` with a checked error (e.g., return `Err`/`Result<M>` and propagate a `DuplicateRegistration` error to the caller so the faulty participant can be blamed without crashing). Similarly, replace `self.enc_keys[&decryptor]` and `self.decryption.enc_keys[&participant]` with `.get(...)` returning a `DecryptionError`/`Err` on absence. Any invariant on attacker-supplied data should produce an error, not `assert!`/`panic!`.

### Proof of Concept
1. In a PedPoP session, participant `i` serializes two distinct `EncryptionKeyMessage` values (both parse cleanly via `EncryptionKeyMessage::read`) and broadcasts both under participant index `i`.
2. Each honest peer calls `Decryption::register(i, msg1)` then `Decryption::register(i, msg2)`. The second call hits `assert!(!self.enc_keys.contains_key(&participant))` at `crypto/dkg/pedpop/src/encryption.rs:356-359` and panics.
3. Alternatively, an accuser triggers `decrypt_with_proof` with a `decryptor` participant that never registered a key; `self.enc_keys[&decryptor]` at line 388 panics on the missing entry.

Note: I verified the panic sites and the untrusted read path (`EncryptionKeyMessage::read`, `EncryptedMessage::read`), but did not trace every upstream caller to confirm no outer deduplication guards exist; if the sole caller already deduplicates by `Participant`, the `register` assert is defense-in-depth, though the `decrypt_with_proof` indexing panic stands on its own since `decryptor` is chosen per-accusation.
