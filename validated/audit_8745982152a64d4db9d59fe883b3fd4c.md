## Analysis Result

### Title
DataLayer Mirror URLs Enable Server-Side Request Forgery via Unvalidated Attacker-Controlled URLs - (File: chia/data_layer/data_layer.py)

### Summary
Any wallet user can create an on-chain DataLayer "mirror" coin advertising arbitrary URLs for **any** store/launcher id — including stores they do not own — because `DataLayerWallet.create_new_mirror()` performs no ownership check on the target `launcher_id`. Any other node that later subscribes to that store automatically ingests these attacker-supplied URLs and issues unauthenticated outbound HTTP requests to them, exactly matching the reported bug class of unvalidated external-controlled URL/config leading to Server-Side Request Forgery (CWE-918).

### Finding Description
`DataLayerWallet.create_new_mirror()` builds a standard coin spend whose memo simply embeds the caller-supplied `launcher_id` and `urls`, with no verification that the caller's wallet owns or tracks that `launcher_id`: [1](#0-0) 

This is exposed directly via the `dl_new_mirror` wallet RPC, which likewise performs no ownership check before pushing the mirror coin on-chain: [2](#0-1) 

Once this coin confirms, **any** DataLayer node/service that subscribes to that `launcher_id` (a normal, unprivileged action any DL client can take) will pull the mirror's URLs via `dl_get_mirrors` and merge them into its own local subscription table without validating scheme or destination host: [3](#0-2) [4](#0-3) 

The background sync loop (`periodically_manage_data` → `update_subscription` → `fetch_and_validate`) then selects one of these attacker-controlled URLs and issues an outbound HTTP request from the victim's DataLayer process: [5](#0-4) 

The actual request is a raw `aiohttp` GET built by directly concatenating the attacker-supplied URL: [6](#0-5) 

No allow-list, scheme restriction, or private/loopback-address blocking is applied to `server_info.url` anywhere in this path; the only validation performed (`is_filename_valid`) constrains the *filename* suffix, not the destination host. The `.cursor/context/data-layer.md` documentation explicitly acknowledges "mirror URLs... are external trust inputs" for *data* integrity, but no such protection exists for the *network destination* of the fetch itself.

### Impact Explanation
Any wallet user can force every DataLayer node that subscribes to a given store to make attacker-chosen outbound HTTP requests (e.g., to internal services, localhost RPC ports, or cloud metadata endpoints such as `169.254.169.254`), without needing to own the singleton being mirrored. This is a classic SSRF: it can be used to probe/attack internal network topology of any node running DataLayer with subscriptions enabled, and because the URL is fully attacker-controlled and persisted on-chain, the attack is durable and replays automatically on every sync cycle for as long as the mirror coin/subscription exists.

### Likelihood Explanation
This is trivially reachable: creating a mirror coin only requires a funded wallet and a `dl_new_mirror` RPC call naming any `launcher_id` (not necessarily one's own) — no consensus rule or puzzle constraint ties the mirror to actual ownership of that singleton. Any node subscribing to the targeted store (a routine DL client operation) will automatically fetch from the malicious URL with no user interaction.

### Recommendation
- Restrict `create_new_mirror`/`dl_new_mirror` so mirrors can only be created by singleton owners the wallet actually tracks and owns, or at minimum document/flag mirrors from untrusted advertisers so DataLayer treats them as lower priority/opt-in.
- Validate mirror/subscription URLs before use in `update_subscriptions_from_wallet`/`http_download`: enforce an allow-listed scheme (`http`/`https`), reject loopback/link-local/private IP ranges and non-standard ports pointing at local services, and consider a configurable SSRF-safe HTTP client (e.g., resolving and validating the target IP prior to connecting).
- Add explicit tests asserting that mirror URLs pointing at loopback/private ranges are rejected by the subscription/fetch pipeline.

### Proof of Concept
1. Attacker wallet (no relationship to store `S`) calls `dl_new_mirror` with `launcher_id=S`, `urls=["http://169.254.169.254/latest/meta-data/", "http://127.0.0.1:9256/actions"]`, and pushes the transaction.
2. Victim node's DataLayer service is (or later becomes) subscribed to store `S` — a normal, unprivileged DL client action (`subscribe`).
3. On the next `periodically_manage_data` cycle, `update_subscriptions_from_wallet` pulls the attacker's URLs into the victim's subscription table, and `fetch_and_validate`/`http_download` issues an HTTP GET to the attacker-chosen host from the victim's process, demonstrating SSRF against arbitrary internal/loopback/metadata endpoints reachable from that node.

    async def dl_new_mirror(
        self,
        request: DLNewMirror,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> DLNewMirrorResponse:
        """Add a new on chain message for a specific singleton"""
        if self.service.wallet_state_manager is None:
            raise ValueError("The wallet service is not currently initialized")

        dl_wallet = await self.service.wallet_state_manager.get_dl_wallet()
        async with self.service.wallet_state_manager.lock:
            await dl_wallet.create_new_mirror(
                request.launcher_id,
                request.amount,
                Mirror.encode_urls(request.urls),
                action_scope,
                fee=request.fee,
                extra_conditions=extra_conditions,
            )

        # tx_endpoint will take care of default values here
        return DLNewMirrorResponse(unsigned_transactions=[], transactions=[])

    async def update_subscriptions_from_wallet(self, store_id: bytes32, new_urls: list[str]) -> None:
        async with self.db_wrapper.writer() as writer:
            cursor = await writer.execute(
                "SELECT * FROM subscriptions WHERE from_wallet == 1 AND tree_id == :tree_id",
                {
                    "tree_id": store_id,
                },
            )
            old_urls = [row["url"] async for row in cursor]
            cursor = await writer.execute(
                "SELECT * FROM subscriptions WHERE from_wallet == 0 AND tree_id == :tree_id",
                {
                    "tree_id": store_id,
                },
            )
            from_subscriptions_urls = {row["url"] async for row in cursor}
            additions = {url for url in new_urls if url not in old_urls}
            removals = [url for url in old_urls if url not in new_urls]
            for url in removals:
                await writer.execute(
                    "DELETE FROM subscriptions WHERE url == :url AND tree_id == :tree_id",
                    {
                        "url": url,
                        "tree_id": store_id,
                    },
                )
            for url in additions:
                if url not in from_subscriptions_urls:
                    await writer.execute(
                        "INSERT INTO subscriptions(tree_id, url, ignore_till, num_consecutive_failures, from_wallet) "
                        "VALUES (:tree_id, :url, 0, 0, 1)",
                        {
                            "tree_id": store_id,
                            "url": url,
                        },

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
