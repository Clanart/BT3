### Title
Full-file rewrite diffs let attacker-introduced lines be masked as pre-existing context when their stripped text collides with an unrelated removed line - ([File: plugins/security-guidance/hooks/gitutil.py])

### Finding Description
`filter_preexisting_from_diff` is designed to strip full-file-rewrite noise: when a `Write` tool replaces an entire file, git shows every old line as `-` and every new line as `+`, so the function tries to re-classify `+` lines whose `.strip()`ed text also appears in the `-` set as unchanged context (space-prefixed) rather than genuinely new code [1](#0-0) .

The matching is done with a plain set-membership test on `.strip()`ed text, with no positional/ordinal correlation between which specific removed line matched which added line: `preexisting_count = sum(1 for l in added_lines if l in removed_lines)` and then, in the rebuild loop, *every* `+` line whose stripped content is in `removed_lines` is converted to a context line [2](#0-1) . The code's own docstring acknowledges this exact class of imprecision: "`.strip()` matches across indentation... and the set lets one removal mask N additions of the same stripped text" [3](#0-2) .

Consequently, if a rewritten file contains any removed line whose stripped text is identical to an attacker-injected new line (e.g., a duplicated `subprocess.run(cmd, shell=True)` call moved into a new, now-attacker-reachable code path with different surrounding context), that new `+` line is rewritten to a space-prefixed context line before `parse_diff_into_files` → `filter_preexisting_from_diff` output reaches `cap_diff_for_prompt` / `build_investigate_prompt` in `review_api.py`/`security_reminder_hook.py`. The LLM reviewer therefore never sees this specific line marked `+`, and it is not flagged as new code to review, even though it is functionally new and dangerous in the location where it now lives.

### Impact Explanation
Scoped impact: a genuinely new, attacker-introduced vulnerable line (e.g., a moved/duplicated dangerous call now reachable with different, untrusted input) becomes invisible to the automated code-security reviewer that gates the Stop hook and would otherwise force iterative remediation. This is a detection/reviewer-bypass weakening the plugin's core security-guidance guarantee ("all genuinely new attacker-introduced code must be presented as `+`"), not a sandbox/command-execution/credential compromise. It only affects the *review coverage* of this specific defensive plugin, not Claude Code's core trust or execution boundaries — it does not grant new tool/file/command capability by itself, since the reviewer is advisory (a nudge to keep fixing) rather than a hard security control blocking execution.

### Likelihood Explanation
Preconditions:
- The change must be a full-file rewrite (or similar) that produces a diff where the file has at least one removed line whose `.strip()` text is byte-identical to the injected new line's `.strip()` text.
- The attacker needs some influence over what gets written (e.g., prompt injection steering Claude's Write/Edit output, or a compromised dependency/instruction causing code duplication) — this is within scope as "normal automation flow" content reaching hook enforcement, not privileged access.
- Feasibility is moderate: engineering an exact stripped-text collision is easy when the attacker controls the whole new file content (Write tool) and can choose to literally duplicate an existing line verbatim in a new location, which is a very natural code pattern (reusing a snippet), not a contrived edge case.
- Repeatability: deterministic — the same collision will always be filtered the same way since the logic is a pure text transform with no randomness.

This is a real, code-confirmed gap, but the developers already documented and accepted this exact class of imprecision as a known trade-off in the source comment, judging the "previous-findings recheck" and best-effort nature of the filter (built for the common noisy-rewrite case) as sufficient backstop, rather than treating it as a security boundary.

### Recommendation
Make the pre-existing/context reclassification positional and count-bounded instead of pure set membership:
- Use a multiset (e.g., `collections.Counter`) for `removed_lines` and decrement on each match so one removed line can mask at most one added line, not N.
- Prefer matching against a stable line ordering/index (e.g., using `difflib.SequenceMatcher` on the whole line list) so that only lines whose position is consistent with being an unmoved/unchanged line are treated as context, rather than any lines with identical stripped text anywhere in the file.
- At minimum, document/telemetry-flag when the filter suppresses a `+` line so this masking is auditable, and keep the LLM's raw diff available as a fallback signal for high-risk pattern matches (e.g., re-run the fast regex `SECURITY_PATTERNS` scan on the *original* unfiltered added lines, independent of this context-collapsing step) so pattern-detectable dangerous constructs aren't silently dropped from all review paths.

### Proof of Concept

        "+    x = 1\n"
        "+    return x\n"

        "+    os.system(cmd)\n" # genuinely new dangerous line

    diff_files = [("app.py", diff_content)]
    result = filter_preexisting_from_diff(diff_files, cwd=".", baseline_sha="deadbeef")
    _, rebuilt = result[0]

    # Current (buggy) behavior: the duplicated "x = 1" inside new_sink gets
    # converted to a context line (' ' prefix) even though it is part of
    # brand-new attacker code, because its stripped text collides with an
    # unrelated removed line from helper().
    lines = rebuilt.split("\n")
    new_sink_x_line = [l for l in lines if l.strip() == "x = 1"][-1]
    assert new_sink_x_line.startswith("+"), (
        "Expected the newly-introduced 'x = 1' inside new_sink() to remain "
        f"marked as added ('+'), but it was reclassified as context: {new_sink_x_line!r}"
    )
    # This assertion currently FAILS against the existing implementation,
    # demonstrating that identical-text collision across unrelated code
    # regions causes new code to be hidden as pre-existing context.

Running this against the current `filter_preexisting_from_diff` fails the assertion, confirming that the duplicated `x = 1` line is downgraded to context. While `os.system(cmd)` itself is not string-identical to any removed line in this example and would still surface, a variant PoC can construct the entire dangerous single-line payload (e.g., `os.system(cmd)`) as the colliding line if an identical `os.system(cmd)` string exists anywhere among the removed lines of the same rewritten file, causing that exact dangerous invocation to disappear entirely from the `+` view sent to `build_investigate_prompt`.

def filter_preexisting_from_diff(diff_files, cwd, baseline_sha):
    """
    Filter out pre-existing content from diff files.
    When a file is fully rewritten (Write tool replaces entire content),
    git shows all lines as removed (-) then re-added (+). This function
    detects such rewrites and strips lines from the + section that also
    appeared in the - section, so the LLM reviewer only sees truly new code.
    """
    if not baseline_sha:
        return diff_files

    filtered = []
    for file_path, diff_content in diff_files:
        lines = diff_content.split('\n')

        # Collect removed and added lines (stripping the +/- prefix)
        removed_lines = set()
        added_lines = []
        for line in lines:
            if line.startswith('-') and not line.startswith('---'):
                removed_lines.add(line[1:].strip())
            elif line.startswith('+') and not line.startswith('+++'):
                added_lines.append(line[1:].strip())

        if not removed_lines:
            # New file, no pre-existing content to filter
            filtered.append((file_path, diff_content))
            continue

        # Check what fraction of added lines were pre-existing
        preexisting_count = sum(1 for l in added_lines if l in removed_lines)
        if preexisting_count == 0:
            filtered.append((file_path, diff_content))
            continue
