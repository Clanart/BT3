## Finding [1](#0-0) 

### Title
Unauthenticated Forgery of `ICallbacks.onPacketAcknowledgement`/`onPacketTimeout` via `msg.sender` Spoofing - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
This is the Cosmos EVM analog of the SignalService bug: a downstream contract's trust decision is based on `msg.sender`, but the value used for `msg.sender` in the "trusted" call path is fully attacker-controlled, so an attacker can bypass the intended caller (the IBC module) entirely and call the target function directly with an identical `msg.sender`, forging the "trusted" event.

### Finding Description
The EVM IBC-callbacks module lets a contract register itself (via the ICS-20 `memo.src_callback.address` field) to receive `onPacketAcknowledgement`/`onPacketTimeout` notifications once a packet it sent completes its lifecycle [2](#0-1) . The module documents an implicit trust assumption for these callbacks: "Implementing contracts must ensure that only the IBC module can invoke these callback methods. This prevents unauthorized contracts from triggering callback logic." [3](#0-2) 

However, when the keeper actually performs this "trusted" invocation, it calls the EVM using the **original packet sender's own hex address** as the `from`/`msg.sender` of the call: [1](#0-0) 

```go
sender, err := utils.HexAddressFromBech32String(packetSenderAddress)
...
contractAddr := common.HexToAddress(contractAddress)
...
res, err := k.evmKeeper.CallEVM(cachedCtx, *abi, sender, contractAddr, true, ...,
    "onPacketAcknowledgement",
    packet.GetSourceChannel(), packet.GetSourcePort(), packet.GetSequence(), packet.GetData(), acknowledgement)
```

Because `sender` here is simply the hex-address representation of the packet's original sender — an address controlled by an ordinary externally-owned account or contract that the attacker themselves already owns — there is **no cryptographic or protocol-level difference** between:
1. The legitimate flow: IBC module calls `contractAddr.onPacketAcknowledgement(...)` with `msg.sender = sender`.
2. An attacker directly sending an EVM transaction from `sender`'s own key to `contractAddr.onPacketAcknowledgement(channelId, portId, sequence, data, acknowledgement)` with arbitrary attacker-chosen `channelId`, `sequence`, `data`, and `acknowledgement` bytes.

Both produce the exact same `msg.sender` value inside the target contract, so any `ICallbacks` implementation cannot distinguish a genuine post-packet-lifecycle notification from a directly attacker-forged call — exactly analogous to the SignalService bug, where the `SignalService` contract could not distinguish a message legitimately routed by the `Bridge` from one crafted by an attacker, because both resulted in the same storage-slot identity (`msg.sender = Bridge`). Here the "identity" (`msg.sender = sender`) is even weaker, since the attacker directly holds the private key for it.

Note that this differs from the `onRecvPacket` destination-callback path, which correctly derives an *isolated address* with no corresponding private key [4](#0-3) , making that path safe; the acknowledgement/timeout callback path does not use an equivalent unforgeable identity.

The same-origin contract example shipped with the module (`CounterWithCallbacks.sol`) demonstrates the pattern most `ICallbacks` implementers would naturally write, using state mutation directly in the callback body with no additional caller checks [5](#0-4)  — and per the module's own documentation, correctly restricting the caller is not actually achievable given this design, since there is no fixed, well-known module address to check against.

### Impact Explanation
Any contract built to react to IBC packet lifecycle completion (e.g., releasing escrowed funds on failure/ack, retrying a transfer, unlocking collateral, crediting internal balances) via the documented `ICallbacks` interface can have its `onPacketAcknowledgement`/`onPacketTimeout` logic triggered directly by an unprivileged attacker with completely fabricated `data`/`acknowledgement` payloads, without any real IBC packet ever having been sent or acknowledged. Depending on the downstream contract's logic (which the module's own documentation encourages, e.g. "sender should be able to retrieve their funds which would otherwise be stuck," or retry logic), this can lead to unauthorized fund release/duplication, double-refunds, or other irreversible accounting corruption of contract-held or escrowed assets — matching the "Critical unauthorized... duplication... theft... of escrowed assets" impact class.

### Likelihood Explanation
Trivial and fully attacker-reachable: the attacker only needs to be a normal, unprivileged sender of any IBC transfer packet (establishing their `sender` identity), then directly call the target contract's public `onPacketAcknowledgement`/`onPacketTimeout` function from that same EVM account with attacker-chosen data — no relayer, proof, or privileged role required.

### Recommendation
Do not use the original packet sender's address as `msg.sender` when invoking `onPacketAcknowledgement`/`onPacketTimeout`. Instead call from a fixed, unforgeable identity that has no corresponding private key (e.g., a dedicated module account address, similar to the isolated-address approach already used for `onRecvPacket`), so that implementing contracts can reliably gate these entrypoints to "only the IBC module."

### Proof of Concept
1. Deploy a contract implementing `ICallbacks` (e.g., `CounterWithCallbacks.sol`) that performs a sensitive action inside `onPacketAcknowledgement` based on `acknowledgement`/`data` (e.g., releases escrowed funds on success).
2. Attacker sends a normal ICS-20 transfer (any amount, even dust) with `memo.src_callback.address` pointing at the target contract, establishing themselves as `sender`.
3. Without waiting for any real acknowledgement, the attacker directly calls `TargetContract.onPacketAcknowledgement(channelId, portId, sequence, arbitraryData, fakeSuccessAck)` from their own EOA.
4. Since `msg.sender` inside the contract equals the attacker's own address — identical to what the legitimate IBC-triggered call would have set — the contract cannot reject the call, and executes the sensitive logic as if the real packet had succeeded.

## Ack and Timeout callbacks

A contract that sends an IBC transfer may need to listen for the outcome of the packet lifecyle.
`Ack`and `Timeout` callbacks allow
contracts to execute custom logic on the basis of how the packet lifecyle completes.

### Design

The sender of an IBC transfer packet may specify a contract to be called when the packet lifecycle completes.
This contract **must** implement the expected entrypoints for `onAcknowledgePacket` and `onTimeoutPacket`.

Crucially, **only the IBC packet sender can set the callback**.

### Use case

The cross-chain swaps implementation sends an IBC transfer. If the transfer were to fail, the sender should
be able to retrieve their funds which would otherwise be stuck in the contract. A contract may also wish to
retry sending the packet. In order to do either, the contract must receive the acknowledgement and timeout
callback to understand what occured in the packet lifecyle.

### Implementation

#### Callback information in memo

For the callback to be processed, the transfer packet's `memo` should contain the following in its JSON:

```json
"memo": {
    "src_callback": {
        "address": "evm_contract_addr",
        "gas_limit": "1000000",
    }
}
```

NOTE: For the source callbacks, the calldata **must** be empty since we do not support custom calldata and
instead expect to call a specific entrypoint with the packet information and acknowledgement.
```

    /**
     * @dev Implementation of ICallbacks interface
     * Called when a packet acknowledgement is received
     */
    function onPacketAcknowledgement(
        string memory channelId,
        string memory portId,
        uint64 sequence,
        bytes memory data,
        bytes memory acknowledgement
    ) external override {
        // Emit event when packet is acknowledged
        emit PacketAcknowledged(channelId, portId, sequence, data, acknowledgement);

        counter += 1; // Increment counter on acknowledgement
    }

    /**
     * @dev Implementation of ICallbacks interface
     * Called when a packet times out
     */
    function onPacketTimeout(
        string memory channelId,
        string memory portId,
        uint64 sequence,
        bytes memory data
    ) external override {
        // Emit event when packet times out
        emit PacketTimedOut(channelId, portId, sequence, data);
        counter -= 1; // Decrement counter on timeout
    }
