### Title
Unfixed bonus snapshot in `Airdrop.claim()` allows an attacker to manipulate `totalEndRemainingAllocation` via front-running/repeated calls to `updateEndRemainingAllocation()`, stealing bonus tokens from later claimants - (File: rewards/Airdrop.sol)

### Summary
`Airdrop.claim()` only triggers the bonus-denominator snapshot (`totalEndRemainingAllocation`) lazily, the first time it is zero, but `updateEndRemainingAllocation()` itself is a public, unguarded function that can be called by anyone at any time after `periodsEndTime[4]` and will always overwrite `totalEndRemainingAllocation` with the current (mutable) `totalRemainingAllocation`. This lets an attacker choose the exact moment the "snapshot" is taken — including re-triggering it right before their own claim, after other users have already withdrawn and shrunk the denominator — to inflate their own bonus share at the expense of remaining/later claimants.

### Finding Description
The bonus share formula is: [1](#0-0) 

`totalEndRemainingAllocation` is supposed to be a fixed snapshot of `totalRemainingAllocation` taken once, at the point `periodsEndTime[4]` is reached, so that every claimant's bonus is computed against the same, immutable denominator: [2](#0-1) 

However, `updateEndRemainingAllocation()` has no guard preventing repeated updates — it unconditionally reassigns `totalEndRemainingAllocation = totalRemainingAllocation` on every call once `block.timestamp >= periodsEndTime[4]`, and it is `public`, callable directly by anyone (not just internally from `claim()`): [3](#0-2) 

`claim()` only relies on the `totalEndRemainingAllocation == 0` check to decide whether to (re)compute the snapshot for its own call, which is insufficient because the value can already be non-zero yet still be re-overwritten by anyone calling `updateEndRemainingAllocation()` directly beforehand: [4](#0-3) 

Exploit flow:
1. `periodsEndTime[4]` is reached. Multiple users, including the attacker (holding the largest remaining allocation), have not claimed yet.
2. The attacker waits/observes other users' `claim()` transactions land first — each of those `claim()` calls subtracts the claimant's full original `allocations[user]` from `totalRemainingAllocation` (line 164), shrinking it, without adding anything to `totalBonus` (no forfeiture occurs once all periods have vested).
3. Immediately before submitting their own `claim()`, the attacker calls `updateEndRemainingAllocation()` directly. Since it is unguarded, it overwrites `totalEndRemainingAllocation` with the now-shrunk `totalRemainingAllocation` (excluding all the allocations of users who already claimed).
4. The attacker's `claim()` then computes `bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation` using this artificially shrunk denominator while `userAllocation` (attacker's, the largest) is unchanged — inflating the attacker's bonus share far beyond what was proportionally accrued when `periodsEndTime[4]` actually passed.
5. This either drains disproportionate bonus tokens to the attacker, or causes the contract to run out of `aidropToken` balance for legitimate remaining claimants, reverting their `claim()` via the `InsufficientBalance` check (line 160), freezing/stealing their expected bonus.

The `if (totalEndRemainingAllocation == 0)` guard in `claim()` only prevents redundant internal calls from itself; it does nothing to stop an external actor from repeatedly calling the public `updateEndRemainingAllocation()` and resetting the "snapshot" at will at any later time.

### Impact Explanation
This directly enables a form of theft/misappropriation of pooled bonus tokens (`totalBonus`), which were forfeited by early claimants and are meant to be distributed proportionally among all users who wait until `periodsEndTime[4]`. By manipulating the timing of the snapshot, an attacker with the largest remaining allocation can claim a disproportionately large share of `totalBonus`, at the direct expense of other legitimate claimants (either reducing their bonus or causing their `claim()` to revert due to insufficient contract balance). This matches "Direct theft of user funds."

### Likelihood Explanation
No privileged role is required — `updateEndRemainingAllocation()` is `public` with zero access control, and `claim()` is externally callable by anyone with a nonzero `allocations[msg.sender]`. The attacker only needs: (1) to be a registered allocation holder (ideally the largest remaining one, as stated in the precondition), and (2) the ability to observe/order transactions relative to other claimants around `periodsEndTime[4]` (a common and cheap capability — front-running via higher gas or simply waiting for others to claim first). This is repeatable/observable on every Airdrop deployment using this pattern.

### Recommendation
Make the snapshot immutable once set: guard `updateEndRemainingAllocation()` itself with `if (totalEndRemainingAllocation != 0) return;` (or restrict its callable window strictly to the first call at/after `periodsEndTime[4]`), and/or make it `internal`/access-controlled so it cannot be invoked independently of `claim()`'s already-existing zero-check. Ideally, snapshot `totalRemainingAllocation` deterministically based on `periodsEndTime[4]` timestamp logic rather than "whichever transaction happens to call it first."

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `Airdrop` with `startTime` such that `periodsEndTime[4]` is reachable; `register()` allocations for users A (small), B (small), and Attacker (largest).
2. Advance time past an early period so that A and B each call `claim()` early (before `periodsEndTime[4]`), forfeiting unvested portions into `totalBonus`.
3. Advance time to/past `periodsEndTime[4]`.
4. Have remaining smaller-allocation user C `claim()` first (full claim, no forfeiture) — `totalRemainingAllocation` shrinks by C's allocation.
5. Attacker calls `updateEndRemainingAllocation()` directly, then calls `claim()`.
6. Assert: `getClaimableAmount(attacker)` bonus component computed against the post-C-claim `totalEndRemainingAllocation` is strictly greater than what it would have been had the snapshot been taken atomically at `periodsEndTime[4]` before C's claim (i.e., before C's allocation was excluded from the denominator).
7. Assert a remaining legitimate claimant's subsequent `claim()` reverts with `InsufficientBalance` or receives less than their fair proportional share, demonstrating value extracted by the attacker exceeds their proportional entitlement.

        }

        if(claimableAmount == 0) revert NothingToClaim();

        uint256 userAllocation = allocations[msg.sender];
        allocations[msg.sender] = 0;
        totalRemainingAllocation -= userAllocation;
        if (claimableAmount <= userAllocation) {
            uint256 forfeited = userAllocation - claimableAmount;
            totalBonus += forfeited;
        }
        aidropToken.safeTransfer(msg.sender, claimableAmount);
    }
