### Title
OP_RETURN `data` output omitted from fee/weight calculation in `SignableTransaction::new`, producing under-funded, unbroadcastable transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts an optional `data` payload that is appended as a zero-value `OP_RETURN` output to `tx_outs` (lines 194-202). However, both calls to `calculate_weight_vbytes` (lines 204 and 226) are invoked with `payments` only and never include the data output. The resulting `needed_fee`, the `TooLowFee` minimum-relay check, and the change-amount computation are all derived from a transaction that is smaller than the one actually built and signed.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

1. Lines 194-202: `tx_outs` gets an extra `TxOut` carrying the `OP_RETURN` data (up to 80 bytes of payload per the check at line 171).
2. Line 204: `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — the weight/vbytes are computed on a transaction containing only `payments`, not `tx_outs`, so the `OP_RETURN` output (~9 + payload bytes, up to ~95+ bytes ≈ 24+ vbytes, more in weight terms) is never counted.
3. Line 206: `needed_fee = fee_per_vbyte * vbytes` uses this under-measured vsize.
4. Lines 211-213: the `TooLowFee` check compares the underestimated `needed_fee` against the minimum relay fee, so it can pass even though the actual fee rate of the final transaction is below the network minimum.
5. Lines 224-235: the change amount is computed as `input_sat - payment_sat - fee_with_change`, where `fee_with_change` is again derived without the data output. The change output therefore absorbs satoshis that should have funded the data output's share of the fee, and the *actual* fee paid (`sum(inputs) - sum(outputs)`) equals the underestimated `needed_fee`.

The net effect mirrors the LSSVMRouter bug class: a component that must be paid for is silently excluded from the internal balance accounting (`minOutput` excluded from `remainingValue` there; the `data` output's vbytes excluded from `needed_fee`/`change` here). The missing value is not refunded to anyone — it is simply never allocated, leaving the transaction under-funded by up to `fee_per_vbyte * ~95` satoshis.

### Impact Explanation
- The produced transaction's effective fee rate is strictly lower than the caller-requested `fee_per_vbyte`, by up to ~95 vbytes worth of fee.
- When the underestimated `needed_fee` passes the `DEFAULT_MIN_RELAY_TX_FEE` check but the true fee rate does not, the signed transaction is non-standard/below-min-relay: it will not propagate and cannot confirm. For a threshold wallet this means the inputs are effectively locked until the plan is abandoned and rebuilt — the exact "funds remain locked" consequence of the reference bug.
- Callers that rely on `needed_fee()`/`fee()` for accounting (e.g., fee amortization and change estimation, as in `processor/src/networks/mod.rs::prepare_send` which uses `needed_fee` to compute `on_chain_expected_change`) will compute incorrect change/fee expectations whenever `data` is used.

### Likelihood Explanation
`data` is an optional public parameter of `SignableTransaction::new` in the in-scope `bitcoin-serai` wallet crate; any integrator passing `Some(data)` triggers it deterministically. The under-count is proportional to payload size and always occurs when `data.is_some()`. Whether the resulting transaction is actually unrelayable depends on how close the chosen `fee_per_vbyte` is to the relay minimum, but the fee and change misaccounting occurs unconditionally. The in-repo processor currently passes `None` for `data`, which lowers the realized likelihood in that integration.

### Recommendation
Pass the complete output set into `calculate_weight_vbytes` — e.g., include the `OP_RETURN` output (fixed-size script derived from the validated `data`) in both the no-change and with-change weight computations — so `needed_fee`, the `TooLowFee` check, and the change deduction all reflect the true transaction size. Alternatively, build `tx_outs` (payments + optional data + optional change) first and measure weight directly on the real output vector.

### Proof of Concept
```rust
// In-network unit test sketch (networks/bitcoin):
let data = vec![0xAA; 80];
let tx = SignableTransaction::new(
    vec![output.clone()],
    &payments,
    Some(change_addr.clone()),
    Some(data.clone()),
    FEE,
).unwrap();

// The real transaction contains an extra OP_RETURN output:
assert_eq!(tx.transaction().output.len(), payments.len() + 2);

// Actual vsize exceeds the vsize the fee was computed for:
let actual_vsize = tx.transaction().vsize() as u64;
let paid_fee = tx.fee();
// paid_fee == FEE * vsize_without_data < FEE * actual_vsize
assert!(paid_fee < FEE * actual_vsize);

// If FEE * actual_vsize < min_relay_fee <= paid_fee, the TooLowFee
// check passed yet the transaction cannot be relayed.
```
