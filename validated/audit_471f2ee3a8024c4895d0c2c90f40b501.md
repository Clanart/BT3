### Title
`BlameMachine::blame` / `AdditionalBlameMachine::blame` attribute a failed accusation to an attacker-chosen `recipient`, allowing any party to get an honest participant blamed — (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The CVE's bug class is broken access control: a low-privileged party performs an action (deleting another user's OAuth token) that affects another principal's credential/session without authorization. The PedPoP analog is the blame evaluation path. `blame_internal` takes `sender` and `recipient` as caller-supplied `Participant` indexes, and when the supplied `EncryptionKeyProof` is absent or fails its DLEq verification, it returns `recipient` — i.e., the accused receiver — as the faulty party. Nothing in the library binds the accusation to the party who actually holds the decryption key; anyone can nominate any participant as `recipient` and have them marked faulty by simply not providing a valid proof.

### Finding Description
`Decryption::decrypt_with_proof` in `crypto/dkg/pedpop/src/encryption.rs` returns `DecryptionError::InvalidProof` whenever `proof` is `None` or the DLEq fails: [1](#0-0) 

`BlameMachine::blame_internal` then maps that error to blaming the `recipient`: [2](#0-1) 

The intended semantics — "if your revealed ECDH key doesn't decrypt the message, you lied about the share being bad" — only hold if the accuser *is* the `recipient`. But `blame` accepts both `sender` and `recipient` as free parameters and the `proof` as attacker-controlled bytes (`EncryptionKeyProof::read`, `encryption.rs:267-269`). The DLEq verification does correctly bind the proof to `enc_keys[decryptor]` (`encryption.rs:383-390`), so a proof can't be replayed across recipients — but that is exactly what makes the *absence* of a valid proof attributable to `recipient`, and the attacker chooses `recipient`.

An attacker only needs a well-formed `EncryptedMessage` from some `sender` to the victim (these are relayed/stored per-participant, e.g. via `DkgShare::set`), which passes the PoP check in `decrypt_with_proof` (`encryption.rs:374-379`), then submits `blame(sender, victim, msg, None)`. The result is `victim` returned as faulty.

### Impact Explanation
The victim is publicly identified as the faulty party of a DKG fault they did not cause. Downstream, blame is used to remove/slash participants from the validator set (`InvalidDkgShare` / `RemoveParticipantDueToDkg` handling), so this forces the honest party's credentials out of the protocol — the direct analog of deleting another user's OAuth token to force re-authentication, here forcing exclusion/abort instead. It also aborts the DKG (`blame` "prevent[s] completion of the machine, forcing an abort", lib.rs:612-613), letting a single unprivileged message kill a key-generation round while pinning the fault on an honest validator.

### Likelihood Explanation
Any party able to submit a blame accusation (no threshold, no secret knowledge required) can trigger it. The attacker needs only the victim's share message bytes, which are by design visible to blame evaluators (`AdditionalBlameMachine::new` is explicitly "capable of evaluating Blame regardless of if the caller was a member in the DKG protocol", lib.rs:639-648). Cost is one malformed accusation; success is deterministic since the `InvalidProof → recipient` branch requires no valid cryptographic material.

### Recommendation
Authenticate the accuser as the claimed `recipient` before attributing `InvalidProof` to them: e.g., require the blame submission to carry a signature/PoP over `(context, sender, recipient, msg)` under a key belonging to `recipient` (analogous to the per-message `pop` already verified for `sender` in `pop_challenge`, encryption.rs:302-323), or change the API so `blame` takes only `sender` and derives `recipient` from an authenticated accusation, never from attacker-chosen input. Absent such binding, `InvalidProof` should blame the accuser, not the named `recipient`.

### Proof of Concept
Conceptual, using the in-scope API:

```rust
// context, commitment_msgs: the DKG's public commitment messages (n participants).
// Attacker is not necessarily a participant (AdditionalBlameMachine::new supports this).
let abm = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs).unwrap();

// victim's encrypted share from honest sender, as relayed/stored for blame purposes
let msg_to_victim: EncryptedMessage<C, SecretShare<C::F>> = /* publicly available bytes */;

// Victim = `recipient`. PoP verifies because the msg genuinely came from `sender`
// to `victim` (pop_challenge binds only `from`).
// proof = None  ->  decrypt_with_proof returns Err(InvalidProof)
//               ->  blame_internal returns `recipient` = victim
let faulty: Participant = abm.blame(sender, victim, msg_to_victim, None);

assert_eq!(faulty, victim); // honest participant blamed; protocol aborts
```

The same result holds with a garbage `EncryptionKeyProof` whose DLEq fails verification. Root cause is the `Err(DecryptionError::InvalidProof) => return recipient` branch in `blame_internal` (lib.rs:587) combined with `recipient` being an unauthenticated input. [3](#0-2)

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }

  /// Given an accusation of fault, determine the faulty party (either the sender, who sent an
  /// invalid secret share, or the receiver, who claimed a valid secret share was invalid). No
  /// matter which, prevent completion of the machine, forcing an abort of the protocol.
  ///
  /// The message should be a copy of the encrypted secret share from the accused sender to the
  /// accusing recipient. This message must have been authenticated as actually having come from
  /// the sender in question.
  ///
  /// In order to enable detecting multiple faults, an `AdditionalBlameMachine` is returned, which
  /// can be used to determine further blame. These machines will process the same blame statements
  /// multiple times, always identifying blame. It is the caller's job to ensure they're unique in
  /// order to prevent multiple instances of blame over a single incident.
  pub fn blame(
    self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> (AdditionalBlameMachine<C>, Participant) {
    let faulty = self.blame_internal(sender, recipient, msg, proof);
    (AdditionalBlameMachine(self), faulty)
  }
