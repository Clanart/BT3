## Title
Unauthenticated OP_RETURN operator attribution lets an attacker forge phantom payouts that consume an honest operator's kickoff/round slots - (`File: core/src/verifier.rs`, `core/src/task/payout_checker.rs`, `core/src/operator.rs`)

### Summary
`update_finalized_payouts` attributes a payout to an operator purely by parsing the `OP_RETURN` bytes of whichever transaction happens to spend a registered `withdrawal_utxo`, with no cryptographic check that the named operator actually broadcast, signed, or funded that transaction. Because a withdrawal's user-provided `in_signature` uses `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`, it only binds the input and the user's own payout output — leaving the `OP_RETURN` output completely unconstrained and forgeable by whoever controls the withdrawal (i.e., the attacker themselves, since they registered it).

### Finding Description
Binding claimed to hold: `slots_consumed_by(O) == withdrawals_actually_funded_by(O)` for every operator `O`, where "funded" means `Operator::withdraw` (`core/src/operator.rs:560-627`) was invoked by `O` and its `fund_raw_transaction` call added real value.

Trace:
1. An attacker (unprivileged, per the rules can deposit and call `withdraw` on the Citrea Bridge contract, choosing withdrawal UTXO bytes) registers a withdrawal on Citrea for a deposit they control, specifying a `withdrawal_utxo` outpoint they themselves can spend, and signs `in_signature` with `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` as the "user". This signature only commits to input 0 and output 0 (the payout to the user's own script) - see `create_payout_txhandler` at [1](#0-0) , which appends an unconstrained `OP_RETURN` output holding an arbitrary operator xonly pubkey.
2. Since the attacker is the "user" for their own withdrawal, they already possess a valid `in_signature` and can directly construct and broadcast a self-spend payout transaction on Bitcoin (no operator cooperation needed), embedding the victim operator's xonly pubkey in the `OP_RETURN`.
3. The verifier's chain scanner picks up any transaction spending a tracked `withdrawal_utxo` and blindly parses the `OP_RETURN` to determine `operator_xonly_pk`, with no signature or authorization check tying that key to the actual broadcaster: [2](#0-1) . This is stored via `update_payout_txs_and_payer_operator_xonly_pk`.
4. The victim operator's own `PayoutCheckerTask` polls for unhandled payouts filtered strictly by `self.operator.signer.xonly_public_key` ( [3](#0-2) , [4](#0-3) ), finds the forged row, and unconditionally calls `handle_finalized_payout`.
5. `handle_finalized_payout` ( [5](#0-4) ) never checks that this specific operator actually funded/broadcast the payout tx (no lookup against its own tx_sender history or `Operator::withdraw` invocation record) - it simply grabs `get_unused_and_signed_kickoff_connector` for its own `xonly_public_key` and consumes that round/kickoff slot, then `mark_payout_handled` finalizes it.

Existing guards do not stop this: `validate_payer_is_operator` ( [6](#0-5) ) only compares the (forged) DB-stored `payer_xonly_pk` against `self.signer.xonly_public_key` - it trivially "passes" because the attacker forged exactly that value. `Operator::is_profitable` and `SECP.verify_schnorr` are only invoked inside the operator's own `withdraw` RPC path ( [7](#0-6) ), which the attacker never calls and which `handle_finalized_payout` never cross-checks against.

### Impact Explanation
Each forged phantom payout permanently consumes one round/kickoff slot (and its associated collateral-bearing kickoff connector) from the targeted honest operator via `handle_finalized_payout`'s `get_unused_and_signed_kickoff_connector` call, for a withdrawal the operator never funded. Since the attack only requires attacker-controlled self-spends of self-registered withdrawal UTXOs, it is repeatable per round, per operator, and across all operators simultaneously (attacker just changes the `OP_RETURN` xonly pubkey each time). Repeating it `num_kickoffs_per_round` times per round can exhaust an operator's entire round capacity every round, indefinitely denying that operator reimbursement for withdrawals it genuinely fronts - matching the Critical category "an honest operator permanently unable to be reimbursed."

### Likelihood Explanation
Feasible for any unprivileged party. Cost is limited to Bitcoin transaction fees for a self-spend transaction (plus, at most, once establishing a deposit/withdrawal registration that the attacker gets back to themselves) - no verifier/operator/aggregator key material, TLS access, or majority hashrate needed. Fully repeatable and automatable, and can target every operator concurrently by iterating the `OP_RETURN` payload.

### Recommendation
Do not trust the `OP_RETURN` bytes alone to attribute a payout to an operator. Require a cryptographic binding between the claiming operator and the payout transaction - e.g., have the operator sign the payout transaction (or a commitment including the withdrawal index/outpoint) with its own key, and verify that signature (via `SECP.verify_schnorr`) against the claimed `operator_xonly_pk` before `update_finalized_payouts` stores the attribution, or before `handle_finalized_payout` consumes a kickoff slot. Additionally, `handle_finalized_payout` should cross-check that the payout transaction actually matches one this operator instance itself broadcast/funded (e.g., recorded via its own `tx_sender`/`withdraw` call), rather than trusting the shared DB column populated purely from chain-observed `OP_RETURN` data.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

                        .0,

    pub async fn handle_finalized_payout<'a>(
        &'a self,
        dbtx: DatabaseTransaction<'a>,
        deposit_outpoint: OutPoint,
        payout_tx_blockhash: BlockHash,
    ) -> Result<bitcoin::Txid, BridgeError> {
        let (deposit_id, deposit_data) = self
            .db
            .get_deposit_data(Some(dbtx), deposit_outpoint)
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        // get unused kickoff connector
        let (round_idx, kickoff_idx) = self
            .db
            .get_unused_and_signed_kickoff_connector(
                Some(dbtx),
                deposit_id,
                self.signer.xonly_public_key,
            )
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        let current_round_index = self.db.get_current_round_index(Some(dbtx)).await?;
        tracing::info!(
            "Operator: Current round index: {}, round idx for kickoff: {}",
            current_round_index,
            round_idx
        );
        #[cfg(feature = "automation")]
        if current_round_index != round_idx {
            // we currently have no free kickoff connectors in the current round, so we need to end round first
            // if current_round_index should only be smaller than round_idx, and should not be smaller by more than 1
            // so sanity check:
            if current_round_index.next_round() != round_idx {
                return Err(eyre::eyre!(
                    "Internal error: Expected the current round ({:?}) to be equal to or 1 less than the round of the first available kickoff for deposit reimbursement ({:?}) for deposit {:?}. If the round is less than the current round, there is an issue with the logic of the fn that gets the first available kickoff. If the round is greater, that means the next round do not have any kickoff connectors available for reimbursement, which should not be possible.",
                    current_round_index, round_idx, deposit_outpoint
                ).into());
            }
            tracing::info!(
                "Operator: Starting next round to be able to get reimbursement for the payout"
            );
            // start the next round to be able to get reimbursement for the payout
            self.end_round(dbtx).await?;
        }
