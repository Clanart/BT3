### Title
`ThresholdKeys::read` accepts untrusted serialized keys without binding the secret share to the verification shares, yielding attacker-controlled or unspendable group keys - (File: crypto/dkg/src/lib.rs)

### Summary
The Snakeyaml CVE is an unsafe-deserialization class bug: untrusted input is turned into an object whose internal consistency is assumed but never verified, giving the attacker control over downstream behavior. The Serai analog is `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632), which deserializes `t`, `n`, `i`, an interpolation method, a `secret_share`, and `n` `verification_shares` purely from the input bytes, then hands them to `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391). `ThresholdKeys::new` checks only counts and index bounds; it never verifies that `C::generator() * secret_share == verification_shares[i]`, that any of the verification shares are non-identity, or that the first `t` shares interpolate to the intended group key. `group_key` is computed as `sum(verification_shares[j] * interpolation_factor(j, 1..=t))` over fully attacker-supplied points (crypto/dkg/src/lib.rs:376-378). Additionally, `read` uses `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101), which accepts the identity point — unlike `frost::Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) which rejects it.

### Finding Description
Three concrete gaps exist on this reachable path:

1. No consistency check between `secret_share` and `verification_shares[params.i()]`. An attacker can serialize a blob where the `secret_share` is `s` but `verification_shares[i]` is `g * s'` for `s' != s`. `ThresholdKeys::new` accepts it, and the holder proceeds believing it owns a share of `group_key` when its share is invalid (crypto/dkg/src/lib.rs:349-391).
2. Identity verification shares are accepted. `Ciphersuite::read_G` only rejects non-canonical/invalid encodings; `is_identity` points pass (crypto/ciphersuite/src/lib.rs:95-100). Setting all `verification_shares[1..=t]` to identity produces `group_key = identity`.
3. The resulting `ThresholdKeys` is then used by `tweak_keys`/`view`/`group_key` (crypto/dkg/src/lib.rs:445-447, 463-533; networks/bitcoin/src/wallet/mod.rs:46-75), so any downstream component that derives a Bitcoin address or performs FROST signing from deserialized keys operates on attacker-controlled values.

### Impact Explanation
- Funds reported received that are not spendable / theft: if deserialized `ThresholdKeys` come from a party who crafted the blob, the derived `group_key` (and hence the Taproot address via `tweak_keys`) is fully attacker-chosen — the attacker sets `verification_shares` and `secret_share` to a key they alone control.
- Signature-failure / malformed-signing: with an inconsistent `secret_share`, `ThresholdView::verification_share(i)` will not equal `g * interpolated_secret_share` (crypto/dkg/src/lib.rs:494-521), so FROST signature shares produced by this participant will fail share verification — the participant unknowingly emits invalid shares and can be wrongly blamed, or the multisig produces an invalid aggregate signature.
- Identity group key: `group_key()` returns the identity point scaled/offset; a BIP-340 signature against an identity key is forgeable in several verifier formulations.

Severity: Medium/High — requires a path where serialized `ThresholdKeys` cross a trust boundary (e.g., recovery import, coordinator-supplied key material).

### Likelihood Explanation
`ThresholdKeys::read` is listed as an untrusted-bytes entry point, and the constructor performs zero cryptographic validation — acceptance is deterministic for any canonical encodings. Exploitability depends on a caller accepting serialized keys from an untrusted source rather than generating them via `dkg`/`musig`; where it occurs, no computationally-hard step is needed to forge a malicious blob.

### Recommendation
In `ThresholdKeys::new` (or in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[params.i()]` and reject identity verification shares and an identity `group_key`. This mirrors the existing `Curve::read_G` identity rejection and the documented intent that deserialization should produce valid keys.

### Proof of Concept
```rust
// Crafted serialization for ThresholdKeys<Secp256k1> where the holder's
// "share" does not match verification_shares[i], and the group key is
// attacker-controlled.
let t: u16 = 2; let n: u16 = 3; let i: u16 = 1;
let attacker_scalar = Scalar::random(&mut OsRng);
// Attacker-chosen group key = G * attacker_scalar: pick shares s.t.
// sum(vs_j * lambda_j(1..=t)) = G * attacker_scalar
let mut blob = vec![];
blob.extend((Secp256k1::ID.len() as u32).to_le_bytes());
blob.extend(Secp256k1::ID);
blob.extend(t.to_le_bytes()); blob.extend(n.to_le_bytes()); blob.extend(i.to_le_bytes());
blob.push(1); // Lagrange
blob.extend(Scalar::random(&mut OsRng).to_repr().as_ref()); // arbitrary secret_share
// verification_shares chosen so vs[1]*λ1 + vs[2]*λ2 == G*attacker_scalar
// ThresholdKeys::<Secp256k1>::read(&mut blob.as_ref()) succeeds and
// group_key() == attacker key — funds to its tweaked address are the attacker's.
```
