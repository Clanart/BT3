This is a genuine, reachable analog. The gov and staking precompiles' `RequiredGas` returns a **fixed constant** (e.g. `30000` for `VoteMethod`/`DepositMethod`, `50000`–`100000` for staking methods) regardless of calldata size, while go-ethereum's `vm.RunPrecompiledContract` only compares `suppliedGas >= RequiredGas(input)` *before* calling `Precompile.Run`, which then calls `Prepare` → `method.Inputs.Unpack(input[4:])` unconditionally. Unlike the `DynamicGasPrecompile` path (`precompiles/common/precompiles.go`), which was explicitly hardened with `chargeDecodeGas`/`DecodeGasCost` to price ABI decoding *before* decoding (per the regression test `TestDynamicGasPrecompileGasGate` and the vote-weighted overflow fix `TestVoteWeightedAliasedOptionsRejectedBeforeUnpack`), the plain `Precompile.Run` path used by `gov`'s `Vote`/`Deposit` and `staking`'s `Delegate`/`Redelegate`/`Undelegate`/`CreateValidator`/`EditValidator` methods has no equivalent gate.

### Title
Static (non-dynamic-gas) EVM precompiles decode attacker-supplied ABI calldata before charging length-proportional gas, enabling memory-exhaustion DoS - ([File: precompiles/common/precompiles.go])

### Summary
`gov` and `staking` precompiles that implement the plain `PrecompileExecutor` interface (used via `pcommon.NewPrecompile`, not `NewDynamicGasPrecompile`) return a **flat, input-size-independent** gas figure from `RequiredGas` (e.g. `30000` for `gov.VoteMethod`/`DepositMethod` [1](#0-0) , `50000`–`100000` for staking methods [2](#0-1) ). go-ethereum's EVM only checks `suppliedGas >= RequiredGas(input)` before invoking `Run`; it does not scale that check with `len(input)`. `Precompile.Run` → `Prepare` then unconditionally calls `method.Inputs.Unpack(input[4:])` on the full calldata [3](#0-2) , exactly the string/bytes-copy amplification pattern documented in `precompiles/common/decode_cost.go` — a single crafted `string`/`[]string` argument can make the decoder copy volume roughly `O(len(input)^2)` [4](#0-3)  — while the caller only pays the fixed 30k/50k/70k/100k gas floor, not a cost proportional to the actual decode work.

### Finding Description
The fix already applied to `DynamicGasPrecompile.RunAndCalculateGas` (added specifically to close this exact bug class — see the regression test comment: "a call that forwarded ~zero gas could still force every validator to parse and allocate the calldata for free" [5](#0-4) ) installs a gas meter from the *supplied EVM gas* and calls `chargeDecodeGas` — which charges `DefaultGasCost(input)` plus `DecodeGasCost` (a walk that prices string-copy volume) — **before** calling `method.Inputs.Unpack` [6](#0-5) .

The plain `Precompile` type used by `gov` and `staking` has no such gate: `Run` calls `Prepare`, which calls `method.Inputs.Unpack(input[4:], ...)`-equivalent decoding unconditionally, with no gas meter tied to decode cost. The only gas check that happened was the flat `RequiredGas` constant checked by go-ethereum's EVM dispatcher before `Run` is ever called — a check that is independent of `len(input)` and therefore of the ABI decode cost. An attacker (unprivileged EVM contract caller / EOA) can:
1. Craft `Vote`/`Deposit` (gov) or `Delegate`/`Redelegate`/`CreateValidator` (staking) calldata containing a dynamic `string`/`bytes[]` argument whose ABI length-prefix is set to a very large value but whose ABI payload is padded minimally (or, per the `walkTuple`/array-of-offsets aliasing trick shown in the `craftAliasedVoteWeightedArgs` PoC pattern already in the test suite [7](#0-6) ), the same offset can be referenced by many array/tuple slots to multiply the copy volume super-linearly relative to calldata size.
2. Supply only `RequiredGas` worth of EVM gas (30000–100000), which passes go-ethereum's pre-`Run` check.
3. `Run`/`Prepare` then performs the full `Unpack`, forcing every validator processing the block to allocate and copy the attacker-declared length — the same "declared-length-drives-allocation-regardless-of-actual-payload" pattern as the pypdf `/Length` bug — for gas that is far below the actual cost, since the flat constant does not scale with `len(input)` or with the decode's super-linear string-copy cost.

### Impact Explanation
This can force excessive memory allocation on every validator processing the transaction for gas cost far below actual work, causing node slowdown or crash under repeated/concentrated exploitation, which can delay block production beyond acceptable thresholds — a resource-exhaustion DoS against consensus-critical execution, directly analogous to the pypdf vulnerability class (attacker-controlled length field drives allocation cost that isn't gated by the actual work required).

### Likelihood Explanation
High reachability: any EOA or contract can call the `gov` or `staking` precompile at their well-known addresses with minimal EVM gas and standard ABI-encoded calldata; no special privilege is required, and the vulnerable code paths (`RequiredGas` returning flat constants, `Prepare`/`Run` decoding unconditionally) are on the default hot path for these precompiles, unlike the already-hardened `DynamicGasPrecompile` path. However, exploitability at scale should be validated empirically (e.g., what calldata size is needed for a meaningful allocation given EVM calldata gas floor costs, and whether existing `intrinsic gas` / calldata-gas charges already bound how large `input` can practically be for a given `suppliedGas`) before assuming full crash-level impact; this is uncertain and worth verifying with a concrete PoC transaction.

### Recommendation
Apply the same pattern used for `DynamicGasPrecompile` to the plain `Precompile.Run` path: before calling `Unpack`, charge a gas meter installed from the actual EVM gas supplied to the call (not merely the static `RequiredGas` floor) using `DefaultGasCost`/`DecodeGasCost`-equivalent pricing, or make `RequiredGas` for `gov`/`staking`/other affected precompiles scale with `len(input)` and the `DecodeGasCost` estimate so go-ethereum's pre-`Run` gas check itself bounds decode cost.

### Proof of Concept
Not independently verified in this session — a concrete transaction/PoC (crafted `gov.Vote`/`staking.Delegate` calldata with an oversized/aliased dynamic-array offset structure, submitted with gas equal to the fixed `RequiredGas` constant) would be needed to measure actual memory/CPU blowup versus gas charged, similar to `craftAliasedVoteWeightedArgs` in `precompiles/gov/gov_test.go` but targeting the non-dynamic-gas `Precompile.Run` path instead of `RunAndCalculateGas`. This should be validated with a background Devin session that can run the test suite and measure actual gas-vs-allocation ratios.
