This is a strong analog: the `Bridge` report's broken invariant is "the privileged/trusted component has no way to enforce/rotate a security guard on a resource it controls, so an attacker-influenced object escapes the intended safety policy." In Desktop, the analog is `clone()` explicitly disabling Git's own clone-time safety guard.

### Title
`Bridge`'s missing safety guard analog: Desktop disables Git's clone-time protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) during `--recursive` clones - (`File: app/src/lib/git/clone.ts`)

### Summary
Desktop's `clone()` function invokes `git clone --recursive` with the environment variable `GIT_CLONE_PROTECTION_ACTIVE` explicitly set to `'false'` [1](#0-0) . This variable is the toggle Git itself introduced to guard against unsafe/attacker-controlled repository content encountered during recursive clone/submodule checkout (e.g., malicious `.gitmodules`/nested repository layouts that can place files outside the intended working tree or trigger hook/config injection). By forcing this protection off for every clone, Desktop removes Git's own defense-in-depth check whenever a user clones an attacker-supplied URL (from a deep link, "Open in Desktop" action, or a typed clone URL), while Desktop's own downstream mitigations only cover a narrower slice of the problem.

### Finding Description
The clone path takes an arbitrary, attacker-influencable `url` — reachable via `openrepo` deep links parsed in `parseAppURL`/`IOpenRepositoryFromURLAction` [2](#0-1) , via CLI `--cli-clone` [3](#0-2) , and via the normal "Clone repository" UI flow that eventually calls `Dispatcher.clone` → `AppStore._clone` → `CloningRepositoriesStore.clone` → `clone()` in `app/src/lib/git/clone.ts` [4](#0-3) .

Inside `clone()`, the command is built as `git -c init.defaultBranch=<x> clone --recursive -- <url> <path>` and executed with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` merged into the environment [1](#0-0) . `--recursive` causes Git to also clone/initialize any submodules referenced by the fetched repository's `.gitmodules`, and the disabled protection variable removes Git's own guard rail that is specifically meant to stop this exact sequence from being abused with attacker-crafted submodule paths/URLs.

Desktop does have *some* related mitigations nearby (a `isClonePathSensitive` destination check for the top-level clone path [5](#0-4) , and `sanitizeCloneName` for deriving a safe directory name from a URL [6](#0-5) ), but these only protect the *outer* clone destination decided by Desktop's own UI — they say nothing about what Git does internally while recursively resolving and checking out submodules once the protection flag has been switched off. The recursive submodule step is driven entirely by content inside the attacker-controlled remote repository (`.gitmodules` entries), which is exactly the surface `GIT_CLONE_PROTECTION_ACTIVE` exists to police, and Desktop unconditionally disables it before Git even starts.

### Impact Explanation
Because the guard is disabled for *every* clone (not opt-in, not scoped to trusted hosts), any attacker who can get a victim to clone a repository — via a `x-github-client://openrepo/...` deep link, a "Clone in Desktop" button on a malicious page, a CLI clone argument, or simply sharing a clone URL — gets Git's recursive-submodule handling to run without the safety net Git's own maintainers added for this scenario. Depending on the underlying Git version's protected condition, this can degrade into writes/behavior outside the intended working tree during the automatic `--recursive` submodule checkout, i.e. exactly the "silent corruption of what the user commits/checks out" and potential file-write-outside-repo class called out as in-scope.

### Likelihood Explanation
High reachability: cloning an arbitrary attacker-supplied URL is one of Desktop's core, unauthenticated-by-design flows (deep link, CLI, and normal UI clone), and `--recursive` is unconditionally passed, so any repository with submodules exercises the disabled-protection code path with no additional user action beyond initiating a normal clone.

### Recommendation
Do not unconditionally set `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Only disable the protection (if at all) for narrowly justified, already-trusted scenarios (e.g. test fixtures), and otherwise let Git's built-in guard run during `clone --recursive`. If the flag was disabled to work around a specific compatibility issue, that workaround should be scoped/conditioned rather than applied globally to every user-initiated and deep-link-initiated clone.

### Proof of Concept
1. Host a Git repository containing a `.gitmodules` file whose submodule path/URL is crafted to trigger the condition Git's clone protection is designed to reject (this repository is fully attacker-controlled).
2. Get the victim to clone it through any Desktop-reachable path, e.g. a deep link: `x-github-client://openrepo/https://evil.example.com/attacker/repo` (parsed by `parseAppURL` into an `open-repository-from-url` action) or simply "Clone repository" with the attacker's URL.
3. Desktop calls `clone(url, path, options)` in `app/src/lib/git/clone.ts`, which runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` [1](#0-0) .
4. Because the protection Git added for this exact recursive-clone/submodule scenario is disabled, the crafted `.gitmodules` content is processed without that safety check, unlike a plain `git clone --recursive` run by the user directly (which would retain the protection).

Note: I was not able to execute an end-to-end exploit against a live Desktop build (no filesystem/terminal access in this mode), so I cannot confirm which specific Git version/behavior is unlocked by disabling `GIT_CLONE_PROTECTION_ACTIVE` in this checkout, nor whether any other layer elsewhere in the codebase further restricts submodule checkout after this point. A Devin session with repo/terminal access could pin the exact Git version in use and reproduce the unguarded recursive-clone behavior concretely.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
