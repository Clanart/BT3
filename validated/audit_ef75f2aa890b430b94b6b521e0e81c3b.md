### Title
Unsolicited deposits to internally-registered offset addresses (Branch/Change/Forwarded) are absorbed as protocol-owned UTXOs with no credit or refund - (File: processor/src/networks/bitcoin.rs)

### Summary
Analogous to the Derby issue — where a user who mistakenly calls `withdrawalRequest()` has funds irreversibly committed to a delayed path because the function never checks whether immediate fulfillment was possible — Serai's Bitcoin processor commits any output paying to one of its internally-registered script addresses into the protocol's own UTXO set, without checking whether the output was protocol-created or an unsolicited third-party deposit. The depositor is never credited and cannot be refunded, permanently locking their funds into the protocol's internal pipeline.

### Finding Description
`Scanner::register_offset` deterministically derives P2TR scripts for internal paths (`Branch`, `Change`, `Forwarded`) from the group key via `Secp256k1::hash_to_F(KEY_DST, ...)` (`processor/src/networks/bitcoin.rs:333-344`). These addresses are publicly computable: anyone who knows the multisig group key can reconstruct `branch_address`/`change_address`/`forward_address`.

`Scanner::scan_transaction` matches outputs purely by `script_pubkey` (`networks/bitcoin/src/wallet/mod.rs:205-211`), and `Bitcoin::get_outputs` tags each match with an `OutputType` based solely on the offset (`processor/src/networks/bitcoin.rs:686-700`). Downstream, `MultisigManager::scanner_event_to_multisig_event` drops every non-`External` output before instruction parsing (`outputs.retain(|output| output.kind() == OutputType::External)` at `processor/src/multisigs/mod.rs:837`). `Scheduler::add_outputs` then pushes any `Branch`/`Change`/`Forwarded` output that doesn't match a pending branch plan directly into `self.utxos` (`processor/src/multisigs/scheduler/utxo.rs:275-295`), where it is spent as ordinary protocol funds.

The result: there is no check — anywhere in the pipeline — that a `Branch`/`Change`/`Forwarded` output was actually created by a protocol transaction. A user who sends BTC to one of these derivable addresses (e.g., mistakenly using the change or branch address, which are structurally indistinguishable P2TR outputs) has their funds swept into the scheduler's UTXO pool. They receive no `sriBTC` mint (no `InInstruction` is ever produced for non-`External` outputs) and no refund (`PlanFromScanning::Refund` is only reachable for `External` outputs carrying a `RefundableInInstruction`). The deposit is permanently lost to the depositor, mirroring — and exceeding — the Derby finding, where funds were merely delayed by one rebalancing period.

### Impact Explanation
An unprivileged external party who pays to any of the deterministic internal addresses loses the full output value permanently. The funds are incorporated into Serai's spendable UTXO set (`self.utxos`) and consumed by future `Plan`s. The depositor has no on-chain recourse: no mint, no refund path, no error. This is "funds received that are not spendable [by the depositor]" caused entirely by public transaction data the party controls — an accepted consequence category.

### Likelihood Explanation
The trigger requires only a standard Bitcoin transaction — the allowed public input. The internal addresses are derivable by anyone from the published group key (all offsets are `hash_to_F(KEY_DST, b"branch"|"change"|"forward")` under a fixed DST), so a mistaken or misinformed deposit is realistic (e.g., a user copying the change/branch address from an explorer instead of the external deposit address), matching the "user accidentally submits" scenario of the source report. Exploitation requires no privileges and no protocol cooperation.

### Recommendation
Distinguish protocol-created outputs from unsolicited ones before absorbing them. For `Branch` outputs, only accept them when `plans`/`queued_plans` contains a matching amount (already partially enforced via `can_use_branch`); unmatched branch outputs should be quarantined or refunded rather than pushed into `self.utxos`. For `Change`/`Forwarded` outputs, cross-check the containing `txid` against `ResolvedDb`/registered `Eventualities` — the closing-step code already demonstrates this pattern (`processor/src/multisigs/mod.rs:529-547`) — and apply it outside `ClosingExisting` as well. Alternatively, treat non-`External` outputs with no matching protocol plan as `External` candidates so the existing refund flow can return them.

### Proof of Concept
1. Obtain the multisig group key `K` (publicly known once a multisig is declared on Serai).
2. Compute `branch_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch")`, incrementing until `K + G*offset` is even, replicating `scanner()` at `processor/src/networks/bitcoin.rs:313-346`.
3. Send BTC from any wallet to `p2tr_script_buf(K + G*branch_offset)`.
4. `get_outputs` returns the output with `kind == OutputType::Branch`; since `plans` has no entry for its amount, `Scheduler::add_outputs` pushes it to `self.utxos`.
5. The depositor's balance appears in no `Batch`, no `InInstructionWithBalance` is emitted, and no refund plan is created; the BTC is spent by Serai in subsequent aggregation/payment transactions while the depositor holds nothing. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
