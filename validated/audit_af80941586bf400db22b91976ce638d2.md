### Title
Withdrawal payout OP_RETURN operator-pubkey commitment is unsigned, allowing anyone to rewrite it via a fee-bumped replacement, mis-attributing or de-attributing the funding operator - (File: `core/src/verifier.rs`)

### Summary
The payout transaction created in `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) only covers input0/output0 under the user's `SinglePlusAnyoneCanPay` signature; the OP_RETURN output carrying the funding operator's x-only pubkey (output index 2) is completely outside the signed message. `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) later trusts whatever transaction is found spending the withdrawal UTXO on-chain (matched purely by outpoint via `get_payout_txs_for_withdrawal_utxos`, `core/src/database/verifier.rs:170-196`) and extracts the operator pk straight from that transaction's OP_RETURN via `parse_op_return_data`/`XOnlyPublicKey::from_slice` (`core/src/verifier.rs:2319-2321`), with no cross-check against the operator that actually funded output0.

### Finding Description
Binding claimed: `operator_xonly_pk` stored in `withdrawals.payout_payer_operator_xonly_pk` for withdrawal `idx` == the x-only pubkey of the operator whose funds actually paid `output0` (the user's payout).

Code path:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds: input0 = withdrawal UTXO (spent with the user's key-path signature), output0 = user payout, output1 = anchor, output2 = OP_RETURN(`operator_xonly_pk`). Only input0 and output0 are protected by the taproot key-spend signature when `sighash_type == SinglePlusAnyoneCanPay` (enforced in `core/src/rpc/parser/operator.rs:174-187` and used in `Operator::withdraw`, `core/src/operator.rs:630-637`).
- `Operator::withdraw` (`core/src/operator.rs:620-689`) funds this tx with `fund_raw_transaction`(`add_inputs: true`, no explicit `replaceable` flag) and broadcasts it.
- Because `SinglePlusAnyoneCanPay` signs only input0's outpoint/amount/scriptPubkey and output0, anyone observing the mempool transaction can construct an alternative transaction reusing the identical signed witness for input0 and identical output0, adding their own fee-paying input(s), and putting **arbitrary bytes** (e.g., the honest operator's pubkey with one bit flipped, or someone else's valid pubkey) in the OP_RETURN output, then get it mined (via RBF fee-bump or a race, since no signer-identity check is enforced for replacement).
- `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) locates the payout transaction purely by whichever tx spends `withdrawal_utxo_txid:vout` in the finalized block (`get_payout_txs_for_withdrawal_utxos`, `core/src/database/verifier.rs:170-196`), then blindly parses that tx's OP_RETURN into `operator_xonly_pk` (lines 2319-2321), storing it (or `None` if parsing fails) via `update_payout_txs_and_payer_operator_xonly_pk`.
- This stored value is later treated as ground truth: `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) returns `true` (malicious) if the pk is `None` or mismatches `kickoff_data.operator_xonly_pk` (lines 1882-1890); `Operator::send_asserts` (`core/src/operator.rs:1275-1295`) errors/aborts if the pk is `None` or mismatches the kickoff operator.

No guard in the reachable path verifies that the OP_RETURN pubkey is itself covered by any signature, nor that it matches the operator who actually funded the extra inputs of the mined transaction. `SECP.verify_schnorr` in `withdraw`/`sign_optimistic_payout` only validates input0/output0, not the OP_RETURN.

### Impact Explanation
If a malicious replacement is mined instead of (or in place of) the honest operator's broadcast payout tx, the DB records either `None` or a wrong `operator_xonly_pk` for that withdrawal. Downstream:
- `is_kickoff_malicious` treats the honest, actually-funding operator's kickoff as malicious (`Ok(true)`), opening a Challenge/Disprove path against them even though they genuinely paid the user out of their own funds.
- `send_asserts` fails outright for the honest operator (`payout_op_xonly_pk_opt.ok_or_eyre` / mismatch check), permanently blocking their reimbursement flow for that withdrawal.

This maps to the Critical categories "an honest operator permanently unable to be reimbursed" and, via the wrongly triggered Challenge/Disprove path, "an honest operator's collateral burned." The attack is repeatable per withdrawal at negligible cost (only a small fee bump) and does not require any privileged role - any general Bitcoin user can watch the mempool/network for payout transactions and race a replacement.

### Likelihood Explanation
Preconditions are minimal: attacker just needs to observe an operator's broadcast payout transaction on the Bitcoin network/mempool (public data) before it confirms, and be able to broadcast a competing transaction reusing the same signed witness with a different OP_RETURN and enough additional fee to win the race/RBF. No verifier, aggregator, or operator role is required, and this fits squarely within the described unprivileged attacker capabilities (broadcast transactions, pay fees, choose UTXO/signature bytes). The `withdraw` funding path does not appear to explicitly disable replaceability or otherwise protect the OP_RETURN output, so the vulnerability is realistically exploitable during the normal window between broadcast and confirmation.

### Recommendation
Bind the OP_RETURN operator-commitment to the same signature that authorizes the spend, e.g. by covering all outputs with a sighash type that commits to the OP_RETURN (such as `Default`/`All` instead of `SinglePlusAnyoneCanPay`), or by having the operator co-sign an additional covenant/output that commits to their own pubkey. Alternatively, have `update_finalized_payouts`/`is_kickoff_malicious` independently verify which operator's wallet actually funded the additional inputs (e.g., by cross-referencing the extra inputs' owning operator) rather than trusting an unauthenticated OP_RETURN.

### Proof of Concept
```rust
// core/src/database/verifier.rs (new test module)
#[tokio::test]
async fn test_op_return_corruption_breaks_operator_attribution() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();

    let real_operator_pk = generate_random_xonly_pk();
    // Flip one bit of a valid xonly pk serialization to produce bytes that either
    // (a) fail XOnlyPublicKey::from_slice, or (b) parse to a different valid key.
    let mut corrupted_bytes = real_operator_pk.serialize();
    corrupted_bytes[31] ^= 0x01;

    let corrupted_pk_opt = bitcoin::XOnlyPublicKey::from_slice(&corrupted_bytes).ok();

    // Simulate update_finalized_payouts storing whatever was parsed from the
    // attacker-replaced OP_RETURN, regardless of the real funding operator.
    // ... set up withdrawal + block + spent utxo as in update_get_payout_txs_from_citrea_withdrawal ...

    db.update_payout_txs_and_payer_operator_xonly_pk(
        Some(&mut dbtx),
        vec![(idx, payout_txid, corrupted_pk_opt, block_hash)],
    ).await.unwrap();

    let stored = db.get_payout_info_from_move_txid(Some(&mut dbtx), move_txid)
        .await.unwrap().unwrap();

    // Assert the binding is broken in both corruption cases:
    assert_ne!(stored.0, Some(real_operator_pk),
        "Stored operator pk must never equal the real funding operator's key after 1-bit corruption");
}
```
This demonstrates that `get_payout_info_from_move_txid` never returns the real funding operator's key once the OP_RETURN bytes are corrupted, for both the "invalid point" and "valid-but-different key" cases, confirming the broken binding traced through `update_finalized_payouts` → `is_kickoff_malicious` / `send_asserts`.
