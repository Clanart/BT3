### Title
Stale `Precisions` decimals corrupt in-flight cross-chain amounts on `hyper-fungible-token` - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`hyper-fungible-token`'s `send` extrinsic and `on_accept` module handler both read the current `Precisions` storage entry to convert amounts between the local asset's decimals and the EVM counterpart's ERC-20 decimals. Because a request dispatched via ISMP sits in flight (consensus proof + challenge period) before delivery, a routine `update_token` call that changes `Precisions` for the same `(asset_id, chain)` pair between dispatch and delivery corrupts the amount decoded for messages already committed with the old decimals assumption — exactly the same "value stored/derived under one decimals assumption becomes stale after decimals change" defect described in the external report.

### Finding Description
`send()` computes the outgoing ERC-20 amount using the `Precisions` value read at call time: [1](#0-0) [2](#0-1) 

`on_accept()` (inbound path) reads the *current* `Precisions` entry for the source chain/asset at delivery time to convert the incoming raw ERC-20 `U256` amount back to the local balance: [3](#0-2) 

`update_token` lets `CreateOrigin` overwrite the `Precisions` entry for an existing `(asset_id, chain)` pair at any time, with no versioning, no reference to in-flight commitments, and no check that outstanding requests still assume the old decimals: [4](#0-3) 

The conversion helper `convert_to_balance` divides the raw `U256` amount by `10^(erc_decimals - local_decimals)`: [5](#0-4) 

Because the amount embedded in an ISMP `PostRequest` is fixed at dispatch time (per the sender's decimals assumption) but is decoded at delivery time using whatever `Precisions` value is currently stored, any change to `Precisions` for that `(asset_id, chain)` pair between dispatch and delivery causes `on_accept` to scale the amount with the wrong `erc_decimals`, producing a mismatched local balance credit — either far larger (fund creation/loss to the pallet's custody) or far smaller (fund loss to the beneficiary) than the amount actually escrowed/burned on the source chain. This mirrors the reported bug pattern exactly: a value computed once under a decimals assumption is later reinterpreted under a changed decimals assumption, with no snapshot or reconciliation.

### Impact Explanation
Because `send` locks/burns the *exact* source-side amount but `on_accept` re-derives the credited amount from a live, mutable `Precisions` lookup, a decimals change touching any request still in flight (which given ISMP's consensus-proof and challenge-period latency can span a meaningful window) causes an amount mismatch of orders of magnitude (e.g., 1e12x for a jump between 6 and 18 decimals). This can result in the pallet's custody escrow being drained beyond what was locked (loss of funds custodied by the pallet) or beneficiaries receiving far less than what was locked/burned on the source chain (fund loss to users) — both are within the "stealing or loss of funds" / "transaction manipulation" impact classes.

### Likelihood Explanation
This requires only a normal, non-malicious `update_token` governance call on either endpoint (an expected maintenance operation, e.g. correcting a configured decimals value or repointing to a new token contract) to overlap with any request already dispatched but not yet delivered — no attacker collusion, no malicious relayer, and no privileged-key compromise is needed for the corruption to occur; the flaw is that the protocol never snapshots or versions the decimals used per in-flight commitment.

### Recommendation
Snapshot the `erc_decimals` (and ideally the full precision context) used at `send()` time into the outgoing message body itself (or into a per-commitment storage entry keyed by the dispatch commitment), and have `on_accept` use that embedded/snapshotted value rather than re-reading the live, mutable `Precisions` map. Alternatively, require `update_token` to only take effect for new dispatches after a delay at least as long as the maximum expected finality/challenge-period latency, and reconcile or block delivery of requests dispatched under a superseded decimals configuration.

### Proof of Concept
1. Governance registers asset `X` for `chain=Evm(97)` with `erc_decimals=18` via `register_token`.
2. User calls `send(asset_id=X, destination=Evm(97), amount=100)`; `on_accept`-side amount is computed as `100 * 10^(18-local_decimals)` and embedded in the `Message`, and the local pallet escrows/burns `100` units. This request is dispatched and awaits proof relay/challenge period.
3. Before the request is delivered/relayed, governance calls `update_token` for the same `(X, Evm(97))` pair, changing `erc_decimals` to `6` (e.g., a legitimate reconfiguration after discovering the real ERC-20's decimals).
4. Symmetric inbound scenario: an EVM-side message dispatched while `Precisions` was `18` arrives at `on_accept` after the update to `6`; `convert_to_balance` now divides by `10^(6 - local_decimals)` instead of `10^(18 - local_decimals)`, inflating the minted/transferred local amount by `10^12` relative to what was actually escrowed on the EVM side — crediting the beneficiary far more than intended and potentially draining the pallet's native-asset custody account (`Pallet::pallet_account()`). pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
