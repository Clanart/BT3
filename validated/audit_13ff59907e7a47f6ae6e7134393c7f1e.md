## Finding: Stale `ContractToAsset` reverse-mapping after re-registering a token in `pallet-hyper-fungible-token`

### Title
Stale `ContractToAsset` entries survive token re-registration, letting a decommissioned/old EVM contract still mint or move funds - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`register_token` writes `TokenContracts` and `ContractToAsset` for every chain in the registration but never removes a pre-existing reverse-mapping entry for that `(chain, asset_id)` pair before overwriting it. This is the same bug class as the reported `_cachedVaults` issue: a per-key config value ("this chain's `token_contract`") is replaced, but the derived index built from the old value (`ContractToAsset[chain][old_contract] = asset_id`) is never invalidated. `update_token`'s `add_chains` branch explicitly performs this cleanup [1](#0-0)  proving the maintainers know the cleanup is required — but `register_token` lacks it entirely [2](#0-1) .

### Finding Description
`register_token` is callable multiple times by `CreateOrigin` for the same `local_id` (there is no check preventing re-registration, unlike `AssetRegistry.addAssets` in the SDK which explicitly forbids redefinition). Each call blindly inserts: [2](#0-1) 

If a token is re-registered for the same `(chain, asset_id)` with a new `token_contract` C2 (e.g., because the old contract C1 was found to be buggy/compromised and operators want to move users to a fixed contract), the pallet writes:
- `TokenContracts[chain][asset_id] = C2` (correctly updated)
- `ContractToAsset[chain][C2] = asset_id` (new entry added)

but `ContractToAsset[chain][C1] = asset_id` from the prior registration is **never removed**. Both C1 and C2 now authorize minting/transferring `asset_id` on this chain.

`on_accept` authenticates purely via this reverse map, keyed by `(source, from)` taken directly from the incoming `PostRequest`: [3](#0-2) 

There is no additional check that `from` still equals the *current* `TokenContracts[source][asset_id]` value — the stale reverse entry alone is sufficient to pass authentication and reach the mint/transfer/mint_into logic [4](#0-3) . `on_timeout`'s refund path has the analogous weakness, keyed on `(dest, to)` [5](#0-4) .

Contrast with `update_token`, whose `add_chains` loop performs exactly the cleanup that's missing from `register_token`: [6](#0-5) 

### Impact Explanation
Because `TokenContracts` and `ContractToAsset` are the sole binding between an EVM contract address and a local Substrate asset, a stale entry means the pallet continues to treat the *old* contract as a legitimate source of mint/transfer instructions for `asset_id` even after operators have moved to a new contract via `register_token`. Any message the old contract dispatches (whoever calls its `send`, e.g. legitimate users who still hold/interact with it, or an attacker exploiting a vulnerability discovered in the retired contract that motivated the migration in the first place) will still be honored: minted to an arbitrary beneficiary or unlocking pallet-custodied native funds, since `on_accept` never re-checks against the currently-configured contract. This is false-state acceptance / unauthorized minting via a binding the operator believed they had revoked — a direct fund-safety impact on the bridge's asset-issuance pallet.

### Likelihood Explanation
Requires only that `CreateOrigin` (the pallet's normal, sanctioned token operator) re-registers the same asset for a chain it had already configured — a realistic maintenance/incident-response operation (e.g., rotating to a patched contract). No relayer, prover, or governance compromise is needed; the vulnerable path is purely local storage state left un-invalidated by an ordinary admin call, exploitable afterward by anyone able to trigger a `PostRequest` from the old contract address on the source chain.

### Recommendation
In `register_token`, before inserting `TokenContracts`/`ContractToAsset` for a `(chain, asset_id)` pair, look up and remove any existing `TokenContracts::get(chain, asset_id)` reverse entry, mirroring the cleanup already implemented in `update_token`'s `add_chains` loop.

### Proof of Concept
1. `CreateOrigin` calls `register_token` for `asset_id = X` with `chains = { Evm(1): { token_contract: C1, decimals: d } }`. Now `TokenContracts[Evm(1)][X] = C1` and `ContractToAsset[Evm(1)][C1] = X`.
2. Later, `CreateOrigin` calls `register_token` again for the same `asset_id = X` with `chains = { Evm(1): { token_contract: C2, decimals: d } }` (e.g., migrating to a fixed/rotated contract). Now `TokenContracts[Evm(1)][X] = C2` and `ContractToAsset[Evm(1)][C2] = X`, but `ContractToAsset[Evm(1)][C1] = X` still exists.
3. Anyone triggers the old contract C1 (still deployed on Evm(1)) to dispatch a `PostRequest` with `source = Evm(1)`, `from = C1`, destined for `PALLET_ID`.
4. `on_accept` looks up `ContractToAsset::get(Evm(1), C1)` and finds `X` (unchanged from step 1) [7](#0-6) , then mints/transfers `asset_id = X` to the attacker-chosen `beneficiary` per the message body, even though C1 is no longer the pallet's configured contract for `X`.
