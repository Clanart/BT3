The key finding: the payout tx signature uses `SinglePlusAnyoneCanPay` sighash, which per BIP341 does NOT commit to outputs other than the one at the same index as the input (output0). This means an attacker can strip output1 (anchor) and output2 (OP_RETURN) from a competing transaction while keeping input0's witness/signature and output0 identical, and the signature remains valid.

### Title
Payout tx's `SinglePlusAnyoneCanPay` signature does not commit to the OP_RETURN output, letting an attacker mine a stripped-output rival tx and strand the honest operator's reimbursement - (File: core/src/operator.rs, core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs)

### Summary
`Operator::withdraw` builds and broadcasts the payout transaction using a user signature whose sighash type is enforced to be `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) . This sighash flag commits only to the output at the same index as the signed input (output0, the user's payout) and to no other outputs, so the anchor output and the operator-identifying OP_RETURN output (added in `create_payout_txhandler`) are never covered by the signature [2](#0-1) . An attacker can therefore rebroadcast a fee-bumped variant of the same transaction (same input0 witness, same output0) that drops the anchor and OP_RETURN outputs entirely, and the Schnorr signature verification in `withdraw` still passes because it was computed the same way [3](#0-2) .

### Finding Description
The broken binding: `operator_xonly_pk` recorded for withdrawal `i` in `withdrawals.payout_payer_operator_xonly_pk` must equal the operator that actually funded output0 of the confirmed payout tx. Instead, `Verifier::update_finalized_payouts` derives this value purely from the confirmed transaction's OP_RETURN, via `get_first_op_return_output` + `parse_op_return_data` [4](#0-3) . Because the payout tx's only signature (`SinglePlusAnyoneCanPay`) never commits to that OP_RETURN output, its presence is not cryptographically bound to the funding operator or to the transaction actually being funded by them.

Exploit flow:
1. Operator A calls `withdraw`, which fetches the input prevout, builds `create_payout_txhandler` (output0 = user payout, output1 = anchor, output2 = OP_RETURN with A's xonly pk), computes the `SinglePlusAnyoneCanPay` sighash over input0 and output0 only, verifies the user's Schnorr signature against that sighash, funds/signs/broadcasts the tx via RBF [5](#0-4) .
2. The tx sits unconfirmed in mempool. An attacker (anyone who can see the mempool and broadcast txs) constructs a new transaction reusing input0 with the identical witness (valid because the sighash doesn't change) and output0 identical to the original, but omitting the anchor and OP_RETURN outputs, adding higher-fee inputs/outputs of their own (allowed by ANYONECANPAY), and gets this variant mined first.
3. `Verifier::update_finalized_payouts` runs `get_first_op_return_output` on the now-confirmed tx, finds none, so `operator_xonly_pk` is stored as `None` [6](#0-5) .
4. `PayoutCheckerTask::run_once` polls `get_first_unhandled_payout_by_operator_xonly_pk(operator_A.xonly_pk)`; since the DB row has `NULL`, this query can never match A, so A never learns it must initiate `handle_finalized_payout`/kickoff for this withdrawal [7](#0-6) .
5. Separately, `Verifier::is_kickoff_malicious` treats a `None` stored operator pk as malicious for any kickoff A eventually sends for this deposit: `let Some(operator_xonly_pk) = operator_xonly_pk_opt else { ... return Ok(true); }` [8](#0-7) .
6. Round progression logic requires every kickoff issued for a round to be finalized before `ready_to_reimburse_tx`; a kickoff that never happens (or is deemed malicious) leads to `kickoff_not_finalized_tx` burning A's collateral, or to a Challenge/Disprove sequence against A's honest kickoff [9](#0-8) .

Existing guards do not catch this: `SECP.verify_schnorr` in `withdraw` only checks the signature against the sighash it was given — it has no way to know the confirmed transaction on-chain diverges from the one it built, because `SinglePlusAnyoneCanPay` was specifically chosen to allow fee-bumping additional inputs/outputs (its doc/error message literally instructs "Ensure the signature uses SinglePlusAnyoneCanPay sighash type"), but the implementation never restricts *which* outputs beyond output0 can be dropped.

### Impact Explanation
An honest operator who genuinely fronted a Citrea withdrawal (spent real BTC to the user) is: (a) never flagged by `PayoutCheckerTask` as having an unhandled payout to reimburse, since `payout_payer_operator_xonly_pk` is `NULL` in the DB, and (b) treated as malicious by `is_kickoff_malicious` if it does manage to kick off through another path, exposing it to Challenge/Disprove and collateral burn via `kickoff_not_finalized_tx`/`Assert`/`Disprove`. This matches the Critical category: "an honest operator permanently unable to be reimbursed" and "an honest operator's collateral burned." The attack is repeatable against any withdrawal and any operator, for the cost of one RBF fee bump.

### Likelihood Explanation
Preconditions: the payout tx must be unconfirmed and RBF-replaceable (default `withdraw` funds it via `fund_raw_transaction`/RBF, so it's mempool-visible before confirmation) [10](#0-9) . The attacker needs only to observe the mempool, reuse the public input0 witness/signature (valid because it doesn't commit to more outputs) and outbid the fee — no privileged access, keys, or collateral required. This is a standard mempool-level attack (child-pays-for-parent style output substitution against ANYONECANPAY signatures), well within scope of "anyone who can broadcast Bitcoin transactions and pay fees."

### Recommendation
Do not rely on an OP_RETURN output that is unsigned by the committing signature. Either (a) change the payout tx's sighash policy so the OP_RETURN output is committed (e.g. require `AllPlusAnyoneCanPay`/`All`, or add the OP_RETURN commitment as part of the input0 script/witness itself rather than as a separate output), or (b) have the operator additionally record its own broadcast payout txid/outpoint in the DB at `withdraw` time (independent of on-chain OP_RETURN parsing) so `update_finalized_payouts` can cross-check the confirmed spender of the withdrawal UTXO against the operator that originally signed/funded it, rather than trusting an unauthenticated OP_RETURN.
