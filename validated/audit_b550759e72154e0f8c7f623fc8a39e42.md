Confirmed: `Kip71GasTarget` uses `noopFormatChecker` — no zero-check — unlike `Kip71BaseFeeDenominator` which explicitly requires `v != 0`. This directly mirrors the reported bug class (insufficient validation of a value later used as a division denominator).

### Title
Missing zero-check on `kip71.gastarget` governance parameter causes division-by-zero panic in Magma base fee calculation - (File: `params/kip71_config.go`)

### Summary
The governance parameter `kip71.gastarget` (`GasTarget`) can be set to `0` because its `FormatChecker` is `noopFormatChecker`, unlike the sibling parameter `Kip71BaseFeeDenominator` which enforces `v != 0`. `GasTarget` is subsequently used as a division denominator inside `NextMagmaBlockBaseFee`, which computes the base fee for every block after the Magma hardfork. If `GasTarget` is `0` and the parent block's gas usage differs from `0`, the function performs `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero denominator, causing a Go runtime panic (`division by zero`) in every node that processes/verifies the block.

### Finding Description
`kaiax/gov/param.go` defines the KIP-71 parameters. `Kip71BaseFeeDenominator` is explicitly guarded against zero: [1](#0-0) 

But `Kip71GasTarget` has no such guard, using `noopFormatChecker` which always returns `true`: [2](#0-1) 

The value flows unchecked into `KIP71Config.GasTarget` via `ParamSet.ToKip71Config()` [3](#0-2) , and is consumed in `NextMagmaBlockBaseFee`, which only special-cases a zero `BaseFeeDenominator` but never checks `GasTarget`: [4](#0-3) 

Specifically, when `parentGasUsed != gasTarget` (true whenever `gasTarget == 0` and any gas is used, or even when `parentGasUsed == 0` triggers the decrease branch with `gasTarget - parentGasUsed = 0` used as dividend, not divisor — the increase branch is the fatal one), the code computes:
```go
y := x.Div(x, new(big.Int).SetUint64(gasTarget))
```
in the "gas used above target" branch, and an equivalent division in the "below target" branch. With `gasTarget = 0`, `big.Int.Div` by zero panics (Go's `math/big` package explicitly panics on division by zero, unlike Solidity's revert — this is more severe because it crashes the node process, not just aborts a transaction).

`NextMagmaBlockBaseFee` is called both when producing a block header (`PrepareHeader`) and when validating any received/gossiped block via `VerifyMagmaHeader`, which is on the hot path of block processing for every full node, including consensus and public RPC nodes.

### Impact Explanation
Because `NextMagmaBlockBaseFee` is invoked during block validation (`VerifyMagmaHeader`) for every block after the Magma hardfork on every full/consensus node, a zero `GasTarget` value would cause every node in the network to panic/crash while validating (or producing) the very next block whose gas usage differs from the target. This is a full network halt / consensus-wide denial of service — every honest node crashes identically since the computation is fork-choice-critical and deterministic, so it isn't even a divergence bug, it's a total-outage bug. This matches the "state divergence between honest nodes" / "acceptance of invalid block" style impact bar, but is arguably worse since it is a crash rather than divergence.

### Likelihood Explanation
Setting `kip71.gastarget` requires a governance vote (single-governance mode: the governing node; ballot mode: validator majority) — not a fully unprivileged transaction sender. However, the prompt's rules explicitly list "governance parameters" as an in-scope reachable category, and the root cause is a pure input-validation gap analogous to the reported issue (an admission-time value later used unguarded as a divisor). Once voted in (which requires only a single transaction/vote from the governing node in single mode — the common Kaia/Kairos configuration), the very next non-target-matching block triggers the panic on every node, so likelihood of triggering *given* the parameter is set is 100%, and setting the parameter itself requires no special code exploit — just a normal governance vote transaction with an out-of-range value that the code fails to reject.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `v == 0`, matching the existing check on `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
},
```
Additionally, as defense-in-depth, `NextMagmaBlockBaseFee` in `params/kip71_config.go` should guard against `gasTarget == 0` the same way it already guards `BaseFeeDenominator == 0` (fallback to a safe non-zero default), so that a bad historical/genesis value cannot crash nodes.

### Proof of Concept
1. Governing node (single mode) casts a governance vote setting `kip71.gastarget = 0` via the normal governance vote transaction/API — `Kip71GasTarget`'s `FormatChecker` (`noopFormatChecker`) accepts this value with no error [2](#0-1) .
2. The vote takes effect at the epoch/voting boundary, and `ParamSet.GasTarget` becomes `0`, flowing into `KIP71Config.GasTarget` via `ToKip71Config()` [3](#0-2) .
3. Any subsequent block whose `GasUsed != 0` (virtually guaranteed) causes `NextMagmaBlockBaseFee` to enter the `parentGasUsed > gasTarget` branch and execute `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0` [5](#0-4) .
4. `math/big.Int.Div` panics with "division by zero" inside every node calling `VerifyMagmaHeader`/`NextMagmaBlockBaseFee` while processing or producing that block, halting the entire network.

	parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)
	if parentGasUsed == gasTarget {
		return makeEvenByFloor(parentBaseFee)

		// shortcut. If parentBaseFee is already reached upperbound, do not calculate.
		if parentBaseFee.Cmp(upperBoundBaseFee) == 0 {
			return makeEvenByFloor(upperBoundBaseFee)
