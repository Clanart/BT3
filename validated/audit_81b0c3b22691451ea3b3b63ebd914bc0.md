### Title
KeychainServer derives its alt-keychain cache key via lossy string concatenation of `kc_user`/`kc_service`, allowing distinct daemon RPC callers to collide onto the same Keychain instance - ([File: chia/daemon/keychain_server.py])

### Summary
`KeychainServer.get_keychain_for_request` partitions keychains by concatenating the `kc_user` and `kc_service` request fields with no separator or escaping: `key = (user or "unnamed") + (service or "")`. This is structurally the same bug class as the Kamaji CVE-2026-62246: a control-plane component derives a shared-resource identifier (there: SQL schema/DB user; here: the cached `Keychain` instance keyed into `_alt_keychains`) via a lossy, non-injective normalization of two independent namespace components, so two distinct (user, service) pairs can normalize to the same identifier and end up sharing the same backing keyring/keystore. [1](#0-0) 

### Finding Description
`get_keychain_for_request` is the daemon-side dispatcher used for every keychain RPC command (`add_key`, `get_key`, `get_keys`, `delete_all_keys`, `set_label`, etc.) coming from local RPC callers (wallet/CLI clients talking to the daemon over the local RPC/keychain proxy): [2](#0-1) 

The cache key that selects (or creates) the `Keychain` instance for a request is built as:
```
key = (user or "unnamed") + (service or "")
```
This concatenation has no delimiter between `user` and `service`, so it is a lossy/non-injective mapping from the pair `(user, service)` to a single string — exactly analogous to Kamaji's `GetDefaultDatastoreSchema()`/`GetDefaultDatastoreUsername()` deriving a shared datastore schema/DB user from a lossy namespace+name normalization. For example:
- caller A: `kc_user="AB"`, `kc_service="C"` → key `"ABC"`
- caller B: `kc_user="A"`, `kc_service="BC"` → key `"ABC"`

Both callers are routed to (and, if the key does not yet exist, both end up creating and then sharing) the exact same `Keychain(user=user, service=service)` object stored in `self._alt_keychains[key]`. Because `Keychain` partitions its underlying keyring storage by these `user`/`service` values, two callers that intended to use *different* keychains (different user/service pairs) can collide onto whichever `Keychain` object happens to be cached first for that colliding key, and subsequently issue key-management operations (`add_key`, `get_key`, `get_keys`, `delete_all_keys`, `set_label`, `delete_key_by_fingerprint`, etc.) against the wrong caller's keychain.

The `kc_user`/`kc_service` values themselves are attacker/caller-supplied strings passed straight from the RPC request dict (`request.get("kc_user", ...)`, `request.get("kc_service", ...)`), so any local RPC caller able to invoke keychain commands controls both components of the identifier and can deliberately construct a colliding pair. [1](#0-0) 

### Impact Explanation
A local process/caller of the daemon's keychain RPC interface (any client using `keychain_proxy`/`KeychainServer` with custom `kc_user`/`kc_service`) can pick a `(kc_user, kc_service)` pair whose concatenation collides with another caller's/service's expected identifier. This breaks the isolation the `user`/`service` partitioning is meant to provide between separate keychains: an attacker-controlled caller can end up reading (`get_keys`, `get_key_for_fingerprint`, `get_all_private_keys`), overwriting (`add_key`/`add_private_key`), relabeling (`set_label`), or destroying (`delete_all_keys`, `delete_key_by_fingerprint`) key material belonging to a different logical keychain namespace that happens to collide under the naive string concatenation. This is a private-key/keychain integrity and confidentiality issue reachable purely through local daemon/keychain RPC calls, matching the in-scope category "daemon/keychain/RPC authorization."

### Likelihood Explanation
Exploitation requires only that a local RPC caller be able to specify `kc_user`/`kc_service` on requests to the daemon's keychain command dispatcher and know or guess the concatenation of another intended namespace's user/service values (no cryptographic secrets involved, just string collision, e.g. `"AB"+"C" == "A"+"BC"`). No network access or privileged position is needed beyond having local RPC access to the daemon, which is the intended usage pattern for these keychain commands. The main uncertainty is how many distinct `kc_user`/`kc_service` values are used in normal deployments and whether any caller other than the default keychain actually supplies non-default values in a given installation — this determines how often a real collision opportunity arises versus being a self-inflicted collision purely at the attacker's discretion.

### Recommendation
Change `get_keychain_for_request` in `chia/daemon/keychain_server.py` to derive the `_alt_keychains` cache key from a collision-free, injective encoding of the `(user, service)` pair — e.g. `key = (user_len, user, service_len, service)` tuple, a JSON/length-prefixed encoding, or hashing `user` and `service` separately before combining (e.g. `hash(user) + b"\x00" + hash(service)`), rather than plain string concatenation. Ensure that no two distinct `(user, service)` pairs can ever map to the same cache key.

### Proof of Concept
1. Start the daemon and connect two local RPC clients using `KeychainProxy` (or send raw `handle_command` payloads directly to `KeychainServer.handle_command`).
2. Client A issues `add_key` with `kc_user="AB"`, `kc_service="C"`, adding a private key `K1`.
3. Client B issues `get_keys` with `kc_user="A"`, `kc_service="BC"`.
4. Because `get_keychain_for_request` computes `key = "AB" + "C" == "A" + "BC" == "ABC"` for both requests, Client B is routed to the same cached `Keychain` object created for Client A and receives `K1` in its response — despite having supplied a different, non-colliding-looking `(user, service)` pair.
```python
@dataclass
class KeychainServer:
    """
    Implements a remote keychain service for clients to perform key operations on
    """

    _default_keychain: Keychain = field(default_factory=Keychain)
    _alt_keychains: dict[str, Keychain] = field(default_factory=dict)

    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```
