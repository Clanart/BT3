### Title
Unauthenticated `associatePublicKey`/`associate` precompile calls allow any third party to force re-association of a validator's direct-cast identity, breaking commission payout and risking an EndBlock chain halt - (File: precompiles/addr/addr.go)

### Summary
The `addr` precompile's `associate` and `associatePubKey` methods let *anyone* submit a target's raw public key (or a signature over a fixed message) to force-create a Sei↔EVM address mapping and migrate the direct-cast account's balance into the pubkey-derived address, without any check on whether the cast address is currently in use as a validator/delegator identity.

### Finding Description
`PrecompileExecutor.associatePublicKey` accepts only a hex-encoded public key with no proof-of-possession signature, derives `evmAddr`/`seiAddr` from it, and calls `associateAddresses` [1](#0-0) , which only checks that the target `seiAddr` isn't *already* associated [2](#0-1) . It performs no check on whether the "cast address" (`sdk.AccAddress(evmAddr[:])`) is currently referenced by staking/distribution state.

`AssociationHelper.AssociateAddresses` then unconditionally rewires the mapping and migrates funds, and — if `LockedCoins` on the cast address is zero — deletes the cast address's account object entirely via `RemoveAccount` [3](#0-2) . `LockedCoins` only reflects vesting locks, not bonded/staked tokens (those live in the bonded-pool module account), so a validator operator address that has been used directly (un-associated, "cast") can have its account object removed by this call while still being referenced by `x/staking`'s validator/delegation records.

The maintainers' own comment in the ante handler acknowledges this exact bug class — "a later `associatePubKey` call can remap, orphaning any staking/distribution state created under the direct-cast identity (which can then halt the chain via the distribution validator-removal hook)" — and mitigated it *only* for EIP-7702 `SetCode` authorities by pre-associating them before EVM execution [4](#0-3) . The general-purpose `associate`/`associatePubKey` precompile entry points have no equivalent guard. Additionally, `distribution`'s hook already has a defensive `canReceiveWithdrawAddr` check specifically because a re-associated address can become unable to receive funds mid-`AfterValidatorRemoved` [5](#0-4) , confirming this is a live class of failure the codebase is still patching around rather than a solved problem.

This maps to the CVE's bug class: an unprivileged party can act *as* another identity's association authority without the affected party's real-time consent or matching authentication — `associatePublicKey` requires no signature at all (unlike `associate`, which at least requires a valid ECDSA signature over a message), so mere knowledge of a public compressed pubkey (routinely exposed on-chain via any prior signed tx) is sufficient to trigger the re-association and downstream account mutation for an arbitrary victim address.

### Impact Explanation
If the cast address targeted has been used as a validator operator/self-delegator or as a delegator whose commission/reward withdraw address is derived by direct byte-cast, an unrelated third party calling `associatePublicKey` (needs only the victim's public key, not their private key) can trigger removal of that account object and remap the EVM↔Sei identity out from under it. Per the acknowledged risk in `preprocess.go`, this can surface later as a panic in `AfterValidatorRemoved`/commission withdrawal, halting block production — a validator-halt-class impact within the report's accepted scope.

### Likelihood Explanation
Requires only a single EVM/CosmWasm-callable precompile transaction with a publicly-obtainable input (a compressed pubkey, not a private key), no special privilege, and no cooperation from the victim. The precondition (a cast address used by staking/distribution before ever being explicitly associated) is a normal, expected operational state for Sei validators/users who haven't yet called `associate` themselves, making the precondition plausible rather than contrived. However, exact triggering of a chain-halting panic depends on timing relative to `EndBlock` hook execution and specific validator/commission state, which I could not fully trace end-to-end (e.g., I did not verify whether `x/staking` keeps a live reference to the deleted `AccountI` object that would nil-panic elsewhere) — this uncertainty is noted.

### Recommendation
Add the same defense used for EIP-7702 authorities to the general `associate`/`associatePubKey` precompile path: reject or pre-associate re-association attempts when the target cast address currently has bonded stake, is a validator operator, or has non-zero `LockedCoins`/staking-related references, before invoking `AssociateAddresses`. Additionally, require `associatePublicKey` to also prove possession of the private key (e.g., a signature) consistent with the `associate` method, rather than accepting a bare public key.

### Proof of Concept
1. Victim `V` uses their Sei-derived-from-EVM cast address `C = sdk.AccAddress(evmAddr[:])` directly as a validator operator/self-delegator without ever calling `associate`.
2. Attacker obtains `V`'s uncompressed/compressed public key (trivially available from any prior transaction signature verification) and calls `IAddr.associatePubKey(pubKeyHex)` on the `addr` precompile at `0x...1004` [6](#0-5) .
3. `associatePublicKey` → `associateAddresses` → `AssociationHelper.AssociateAddresses` executes, migrating `C`'s spendable/wei balance to the pubkey-derived `seiAddr` and calling `RemoveAccount(ctx, C)` since `LockedCoins(C)` is zero (bonded stake isn't counted) [7](#0-6) .
4. On a subsequent unbonding/slashing event triggering `AfterValidatorRemoved` for that validator, the distribution hook's commission-withdraw or outstanding-rewards logic operates against a mapping that no longer matches the account's original state, following the exact failure path the code comments in `preprocess.go` and `hooks.go` describe as chain-halting.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

// associateAuthorizationAuthorities associates every EIP-7702 authorization authority in
// the transaction with its true (pubkey-derived) Sei address, so that a subsequent
// SetCode for the authority does not create a mutable direct-cast mapping. It is
// best-effort: authorities with invalid signatures (which EVM execution would also skip)
// or that are already associated are left untouched, and an association failure skips
// only that authority rather than rejecting the transaction, which go-ethereum would
// still accept.
func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
