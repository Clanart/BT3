### Title
Missing lower-bound validation of signer index allows a remote participant-0 preprocess to panic `sign()` — denial of service - (File: crypto/frost/src/sign.rs)

### Summary
CVE-2023-32252 is a kernel crash caused by using a value without validating it first (null-deref DoS on an attacker-controlled `SMB2_LOGOFF` field). The Serai analog lives in `AlgorithmSignMachine::sign`: the set of co-signers is taken straight from the keys of an attacker-influenced `HashMap<Participant, Preprocess>` and is only checked for *upper* bound (`> n`) and duplicates. A `Participant(0)` entry is never rejected, and is then passed to `ThresholdKeys::view`, whose result is `unwrap()`ed — producing a panic (abort of the signing task) reachable purely from a peer-supplied preprocess.

### Finding Description
`sign` builds `included` from `multisig_params.i()` plus every key in the caller-supplied `preprocesses` map, then sorts it [1](#0-0) . The only validity checks on the participant indexes are:

- `included.len() < t` → error [2](#0-1) 
- `included[included.len() - 1] > n` → error (upper bound only) [3](#0-2) 
- pairwise equality for duplicates [4](#0-3) 

Nothing rejects `Participant(0)`. `Participant` is a tuple wrapper over `u16`, and Serai treats index 0 as invalid — `ThresholdKeys::read` refuses it via `Participant::new(...).ok_or("invalid participant index")` [5](#0-4) , and the verification-share map is populated only for `1 ..= n` [6](#0-5) .

The unvalidated index is then consumed in two dangerous ways:

1. `self.params.keys.view(included.clone()).unwrap()` — if `view` returns `Err`/fails to find a verification share for participant 0 (absent from the `1..=n` map), the `unwrap` panics [7](#0-6) .
2. Even if `view` tolerated it, `validate_map` deliberately skips the *local* index and requires every other `included` entry to be a key of `preprocesses` [8](#0-7) , which a `Participant(0)` key satisfies — so the poisoned set flows into `B.insert`, `B.nonces`, and later `self.view.verification_share(*l)` / `responses[l]` in `complete` [9](#0-8) , each of which indexes collections keyed only by real participants `1..=n`.

The preprocess bytes themselves arrive via `read_preprocess` → `Commitments::read` on unauthenticated-then-authenticated peer data [10](#0-9) , and the participant index framing is exactly the "pointer" the CVE analog fails to validate before dereferencing.

### Impact Explanation
A single malicious co-signer (or any party able to feed a `Participant(0)`-keyed preprocess into the honest node's `sign` call) crashes the signing state machine / host task. In a threshold validator, aborting `sign` mid-session denies the signature — a liveness/availability failure matching the CVE's `A:H` impact. If the panic unwinds across the caller's session bookkeeping, it can also wedge that validator out of subsequent sessions.

### Likelihood Explanation
Triggering requires only that a peer's claimed participant index of `0` reach the `preprocesses` map — plausible wherever participant indexes are deserialized from wire format into the `pub u16` wrapper (the same wire path that `ThresholdKeys::read` already has to defend against with `Participant::new`). No collusion, key material, or privileged position is needed; any participant-slot holder can send the malformed index. Deterministic, single-packet-style trigger once a signing session opens.

### Recommendation
In `sign` (and symmetrically for `shares` in `complete` via `validate_map`), reject any `Participant` equal to `0` before building `included`, e.g. extend the bounds check to `included[0] == 0 → InvalidParticipant`, or make `Participant`'s inner field private so only `Participant::new` (which rejects 0 and `> u16::MAX` provenance) can construct it. Additionally, replace the `.unwrap()` on `keys.view(included)` at `crypto/frost/src/sign.rs:312` with a `FrostError` return so malformed sets can't panic even if another validation gap exists.

### Proof of Concept
```rust
// Assume: honest node has ThresholdKeys with params t=2, n=3, i=1,
// and a PreprocessMachine that already ran preprocess().
let machine: AlgorithmSignMachine<C, A> = /* after preprocess() */;

// Attacker is a peer who supplies a preprocess under participant index 0.
let mut preprocesses: HashMap<Participant, Preprocess<C, A::Addendum>> = HashMap::new();
preprocesses.insert(Participant(0), attacker_preprocess); // index 0 never validated
preprocesses.insert(Participant(2), honest_preprocess);   // satisfy t = 2

// included = [0, 1, 2]; checks pass: len >= t, max == 2 <= n, no dups
// -> keys.view([0,1,2]).unwrap() panics: no verification share exists for
//    participant 0 (map only covers 1..=n, crypto/dkg/src/lib.rs:620-623)
let _ = machine.sign(preprocesses, msg); // panic -> DoS
```

Uncertainty note: I could not re-read `ThresholdKeys::view`'s body in this session to confirm whether it returns `Err` or panics internally on a missing share; either behavior still produces a panic at the `unwrap()` on `crypto/frost/src/sign.rs:312`, so the crash is robust to that detail. The residual question is only whether integrator framing permits a `Participant(0)` key — the struct is constructible outside `Participant::new`, and `sign` performs no zero check, which is precisely the missing validation.
