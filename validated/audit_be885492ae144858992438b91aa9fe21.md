### Title
Division by zero in KIP-71 base fee calculation via unvalidated `kip71.gastarget` governance parameter - (File: `params/kip71_config.go`)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `kc.GasTarget` without checking for zero, while the corresponding governance parameter `Kip71GasTarget` uses a `noopFormatChecker` that accepts any `uint64` value, including `0`. This mirrors the FreeRDP `urbdrc` bug class: a value that reaches a division operation is not validated at the point of acceptance, allowing a division-by-zero panic in a consensus-critical, network-wide path.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` computes the next block's base fee using `gasTarget := kc.GasTarget` as a divisor in both the "gas used above target" and "gas used below target" branches: [1](#0-0) 

Unlike `BaseFeeDenominator`, which has an explicit `if kc.BaseFeeDenominator == 0 { ... fallback to 64 }` guard, `GasTarget` has no such fallback and is used directly as a `big.Int` divisor: [2](#0-1) [3](#0-2) 

The governance parameter definition for `Kip71GasTarget` explicitly uses `noopFormatChecker`, which always returns `true`, whereas the sibling parameter `Kip71BaseFeeDenominator` explicitly rejects zero: [4](#0-3) 

The header-governance vote consistency check (`checkConsistency`) also does not perform any bound/zero check for `gov.Kip71GasTarget`, it is simply grouped with parameters that pass through unconditionally: [5](#0-4) 

Existing tests for vote validation never exercise `GasTarget = 0` as a bad value — only type/format mismatches (string, bool, wrong numeric type) are rejected, confirming `uint64(0)` is accepted by `NewVoteData`/`FormatChecker`: [6](#0-5) 

If `kip71.gastarget` is set to `0` (via a governance vote, or via a misconfigured genesis/chain config `Governance.KIP71.GasTarget`), then for any block where `parentGasUsed != 0` (i.e., `parentGasUsed > gasTarget == 0`), the code executes:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))  // divide by 0
```
`big.Int.Div` panics with "division by zero" when the divisor is zero (Go's `math/big` behavior), just as the FreeRDP `urbdrc` bug caused a division-by-zero crash from unvalidated server-provided values.

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked from consensus-critical header verification (`VerifyMagmaHeader`) as well as from the public `eth_feeHistory` RPC oracle path: [7](#0-6) [8](#0-7) 

Because every full node (and every validator) computes this function identically when validating/preparing the Magma base fee, a zero `GasTarget` causes a synchronous, deterministic panic across all nodes processing the next block or serving `eth_feeHistory`/fee-suggestion RPC calls once any block has non-zero gas usage. This is a chain-halting denial of service that affects the entire network, not just a single node — a severe availability impact matching the CVSS vector's `A:H` component in the reference CVE.

### Likelihood Explanation
Triggering this requires the `kip71.gastarget` parameter to become `0`, which happens either through:
1. A governance vote (`gov.Kip71GasTarget`) that is accepted because `FormatChecker` is a no-op and header-governance consistency checking performs no bound validation for this parameter, or
2. A chain/genesis configuration mistake setting `Governance.KIP71.GasTarget = 0`.

Since governance voting is an intended, reachable path in Kaia's governance module (in scope per this analysis' explicit inclusion of "governance parameters"), and there is no validation anywhere in the vote-acceptance pipeline preventing zero, the likelihood of this configuration being reachable is non-trivial, especially compared to the explicitly-guarded sibling parameter `BaseFeeDenominator`.

### Recommendation
- Add a zero-check to `Kip71GasTarget`'s `FormatChecker` in `kaiax/gov/param.go` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check) to reject a `GasTarget` of zero at vote-acceptance time.
- Additionally, harden `NextMagmaBlockBaseFee` in `params/kip71_config.go` with a defensive zero-check/fallback for `gasTarget`, similar to the existing `BaseFeeDenominator` zero-fallback, to prevent a panic even if an invalid value is otherwise injected (e.g., through direct chain-config misconfiguration).

### Proof of Concept
1. Deploy or configure a Kaia network (or governance-enabled chain) with Magma hardfork active.
2. Submit a governance vote setting `kip71.gastarget = 0` (`gov.Kip71GasTarget`, `uint64(0)`) — this passes `NewVoteData`/`FormatChecker` validation since `noopFormatChecker` accepts any value, and `checkConsistency` performs no range check for this parameter.
3. Once the vote is finalized/enacted (i.e., `ParamSet.GasTarget == 0` for a subsequent block), any block with `parentHeaderGasUsed > 0` will trigger:
   ```go
   testConfig.Governance.KIP71.GasTarget = 0
   testConfig.Governance.KIP71.NextMagmaBlockBaseFee(blockNum, parentBaseFee, /*parentGasUsed=*/ 1)
   ```
   This calls `x.Div(x, new(big.Int).SetUint64(0))` inside `NextMagmaBlockBaseFee`, which panics with `"division by zero"`, crashing header verification (`VerifyMagmaHeader`) on every validating node and the `eth_feeHistory` RPC handler on every full node that processes the block.

	}
	return nil
}
