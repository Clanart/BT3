### Title
Unchecked ERC-20 return-value in Tron `IntentGatewayV2.withdraw()` allows escrow to be marked settled without tokens actually moving - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` replaces the EVM version's `SafeERC20.safeTransfer` with a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the low-level call did not revert (`success`). It never decodes/validates the ABI-encoded `bool` return value that `transfer()` is supposed to return. This mirrors the `LibStoredInitCode.create2WithStoredInitCode()` bug class: a primitive operation can "fail" without reverting (return `false`), the caller only checks the coarse-grained "call succeeded" signal, and downstream bookkeeping (escrow debit, `_filled` commitment marking) is committed as if the real effect happened.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the internal `withdraw()` function (and the `SweepDust` handling in `onAccept`) settles escrowed order funds like this: [1](#0-0) 

```solidity

    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));

            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
```

`token.call(...)` only reverts if the target reverts or has no code. Some ERC-20 implementations (and, notably, many TRC-20/Tron token contracts that predate strict EIP-20 conformance) signal a failed transfer by returning `false` from `transfer()` instead of reverting. In that case:
- `success == true` (the low-level call itself completed normally),
- the actual token balance of `beneficiary` is unchanged (no tokens moved),
- but the code proceeds to debit `_orders[body.commitment][token] -= amount`, sets `_filled[body.commitment] = beneficiary`, and (for `finalize`/non-cross-chain flow elsewhere) emits `EscrowReleased`/`EscrowRefunded`.

This is the exact analog of the referenced bug: `create2` returning `address(0)` on failure without the caller checking it, so the caller's success-path bookkeeping (registering the market, collecting the fee) runs even though the underlying operation did not actually happen. Here the "deployment" is a token transfer instead of a contract deployment, but the broken invariant is identical — a fallible primitive's failure signal is silently discarded, and state is advanced as if it succeeded.

By contrast, the main (non-Tron) EVM implementation in `evm/src/apps/intentsv2/IntentsBase.sol` uses `IERC20(token).safeTransfer(beneficiary, amount)` throughout (`start="408" end="416"` shown in earlier context), which correctly reverts on both call failure and a `false` boolean return via OpenZeppelin's `SafeERC20`. The Tron file imports `SafeERC20`/`IERC20` (`using SafeERC20 for IERC20;`) and does use `safeTransferFrom` for escrow deposits, but for the `withdraw()` payout path and the `SweepDust` payout path (lines ~662-671) it deliberately drops down to raw `.call(...)` without validating the returned boolean, creating an inconsistency between deposit-side and payout-side token-transfer safety in the same contract.

### Impact Explanation
If the token used for an order's input/output is one whose `transfer()` can return `false` on failure instead of reverting (common among legacy/non-standard tokens, and plausible on Tron's TRC-20 ecosystem where the gateway is deployed), a beneficiary calling `cancelOrder`/receiving a `RedeemEscrow`/`RefundEscrow` settlement can have `_filled[commitment]` permanently marked and `_orders[commitment][token]` debited to zero while receiving zero tokens. This is a direct loss of user/solver funds: the escrowed balance is effectively burned (it remains stuck in the gateway contract, unclaimable because `_orders` is already decremented and `_filled` is already set, so no path exists to retry or reclaim). This satisfies the bounty's "stealing or loss of funds" and "false state acceptance" impact classes — the contract accepts an unproven external state (successful transfer) as true from an ambiguous return signal it never inspects.

### Likelihood Explanation
The path is reachable by any unprivileged actor: a user places an order with an ERC-20/TRC-20 token that has non-reverting-`false` transfer semantics, then triggers normal cancellation/settlement flow (`onAccept` → `withdraw`, or `SweepDust`). No malicious relayer, prover, or governance actor is required — only a token whose `transfer()` does not strictly follow EIP-20 revert-on-failure semantics, which is a realistic condition for the diverse token set this gateway is designed to support across chains (the code even explicitly imports `SafeERC20` to defend against this exact class of token elsewhere in the same file, showing the team is aware of non-conforming ERC-20 tokens as a first-class risk).

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()` and the `SweepDust` branch of `onAccept`) with `IERC20(token).safeTransfer(beneficiary, amount)` / `SafeERC20.safeTransfer`, consistent with the deposit-side `safeTransferFrom` usage and with the non-Tron `IntentsBase.sol` implementation. This ensures both call failure and a `false` boolean return revert the transaction before `_orders`/`_filled` state is mutated.

### Proof of Concept
1. Deploy (or use) a TRC-20/ERC-20 token whose `transfer()` returns `false` on failure instead of reverting (e.g., insufficient balance triggers `return false;` rather than a revert) — this is the standard pre-EIP20-hardening token pattern that `SafeERC20` exists to guard against.
2. Place a cross-chain order on the source chain that escrows this token via `IntentGatewayV2.placeOrder`. Confirm `_orders[commitment][token] > 0`.
3. Cause the token's balance backing the gateway to be insufficient at settlement time (e.g., token has an internal freeze/blacklist that makes `transfer` to `beneficiary` fail and return `false` rather than revert — several legacy tokens support recipient blacklisting this way).
4. Trigger settlement (`onAccept` with `RedeemEscrow`/`RefundEscrow`, or the `onGetResponse` cancellation path) so `withdraw()` executes: `token.call(...)` returns `(true, abi.encode(false))`.
5. Observe: `success == true` so no revert occurs; `_orders[commitment][token]` is decremented to 0 and `_filled[commitment]` is set to `beneficiary`, while `beneficiary`'s on-chain token balance is unchanged — the escrowed funds are permanently unrecoverable in the gateway contract. [2](#0-1)
