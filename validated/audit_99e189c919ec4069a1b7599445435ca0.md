## Analysis

The vulnerability is real and confirmed in the code.

`Rule.from_dict` in `plugins/hookify/core/config_loader.py` parses the `action` frontmatter field with an unconditional default and no validation against the only two documented values (`warn`, `block`): [1](#0-0) 

The consuming logic in `RuleEngine.evaluate_rules` (`plugins/hookify/core/rule_engine.py`) then does a strict equality check for `'block'` and treats every other string — including a misspelling like `blocK`, an empty string, or a missing key — as a non-blocking warning: [2](#0-1) 

There is no schema/enum validation of the `action` value anywhere in the plugin — `grep_search` for `validate` in `plugins/hookify/**` returned no results, and `load_rule_file`/`load_rules` in `config_loader.py` only catch I/O and parsing exceptions, not semantic/schema errors: [3](#0-2) 

So a rule author who writes `action: blocK` (typo) or omits `action` entirely on a rule meant to stop destructive commands (e.g. `rm -rf`, `dd`, `mkfs`) gets no error, no warning about the misconfiguration, and the rule silently falls back to the "warn" path — the operation proceeds with only a `systemMessage`, never a `permissionDecision: deny`. Compare with `PreToolUse`/`PostToolUse` blocking behavior which is only emitted when `rule.action == 'block'` exactly: [4](#0-3) 

This affects any autonomous agent (including `code-simplifier`, which explicitly "operates autonomously and proactively" without requiring explicit requests) that relies on hookify rules as a safety net during automated edits: [5](#0-4) 

### Caveat on reachability by an "unprivileged attacker"

Hookify rule files (`.claude/hookify.*.local.md`) are documented as being intended to be git-ignored / local-only config, not something normally checked into a shared repo: "**Rule Files**: Keep rules in `.claude/hookify.*.local.md` - they should be git-ignored." [6](#0-5)  That means the primary attacker path required by the question — "an unprivileged attacker who commits a hookify rule file" into the victim's working tree/repo so it gets loaded — depends on the victim not following that recommendation, or on an unprivileged contributor's PR containing a `.claude/hookify.*.local.md` file being merged unnoticed by a reviewer. This is a plausible but not fully "attacker-controlled reachable from ordinary repository content" path in the strict sense the rules ask for; it's more accurately a fail-open configuration-parsing defect that turns an innocent typo (self-inflicted misconfiguration by the *rule author*, not necessarily an attacker) into a silent security-control downgrade.

Given the loader will silently accept and load a rule with any typo'd/missing `action` value from *any* `.claude/hookify.*.local.md` that ends up in the loaded directory (whether from an attacker-supplied file merged into the repo or from the rule author's own mistake), and there is no fail-closed behavior, no validation error, and no way to detect this at authoring time, this qualifies as a fail-safe-default violation in a security-relevant enforcement path.

### Title
Hookify rule loader silently defaults unknown/misspelled/missing `action` to `warn` instead of failing closed - ([File: plugins/hookify/core/config_loader.py])

### Summary
`Rule.from_dict` in `plugins/hookify/core/config_loader.py` reads the `action` frontmatter field via `frontmatter.get('action', 'warn')` with no validation, and `RuleEngine.evaluate_rules` in `plugins/hookify/core/rule_engine.py` only treats the exact string `'block'` as blocking, routing every other value (including typos like `blocK`, empty strings, or a missing key) into the warn-only path. A rule author intending to block a dangerous command pattern (e.g. `rm -rf`) gets no error and the rule silently degrades to a non-blocking warning, letting the operation execute.

### Finding Description
`load_rule_file` → `Rule.from_dict` parses YAML frontmatter and sets `action=frontmatter.get('action', 'warn')` with no enum/schema check (`plugins/hookify/core/config_loader.py:75-84`). `load_rules`/`load_rule_file` only catch I/O/type/parsing exceptions, not semantic misconfiguration (`plugins/hookify/core/config_loader.py:198-274`). Downstream, `RuleEngine.evaluate_rules` does `if rule.action == 'block': blocking_rules.append(rule) else: warning_rules.append(rule)` (`plugins/hookify/core/rule_engine.py:53-58`), and only the blocking branch emits `permissionDecision: "deny"` for `PreToolUse`/`PostToolUse` or `decision: "block"` for `Stop` events (`plugins/hookify/core/rule_engine.py:60-91`). No component validates that `action` is one of `{warn, block}`; anything else (missing key, misspelling, wrong case) resolves to the warn/allow path with zero diagnostic output to the user.

### Impact Explanation
Any rule intended by its author to block a destructive/dangerous pattern (matching the documented `action: block` examples for `rm -rf`, `dd if=`, `mkfs`, etc.) silently becomes advisory-only if the value is mistyped or omitted. Autonomous agents like `code-simplifier` (`plugins/pr-review-toolkit/agents/code-simplifier.md:74-83`) that operate without explicit user confirmation and rely on hookify as a guardrail during automated edits will proceed with destructive operations, receiving only a `systemMessage` warning instead of being denied — a fail-open violation of the intended "deny means deny" safety control.

### Likelihood Explanation
No special privilege is required to trigger this beyond the ability to have a `.claude/hookify.*.local.md` file with a malformed `action` field present when rules are loaded (via `load_rules` globbing `.claude/hookify.*.local.md`, `plugins/hookify/core/config_loader.py:210-211`). This can happen through a simple authoring typo or through any file of this shape reaching the working directory (e.g., via a merged contribution containing such a file, since these files are only conventionally, not technically, excluded from version control). The failure is fully deterministic and repeatable — there is no randomness, and it will reproduce on every hook invocation.

### Recommendation
In `Rule.from_dict`, validate `action` against an explicit allow-list (`{'warn', 'block'}`); if the value is missing, default explicitly to `'warn'` only when the key is absent, but raise/log a hard error (and skip/refuse to load the rule, or fail closed to `'block'`) when a non-empty but unrecognized value is supplied. Add a `/hookify:validate` style lint step that flags rules with unrecognized `action` values before they take effect.

### Proof of Concept
Unit test in a new `test_config_loader.py`:
1. Construct frontmatter dicts: (a) missing `action` key, (b) `action: blocK`, (c) `action: bloc`, each on a rule with `pattern: rm\s+-rf` and `event: bash`.
2. Call `Rule.from_dict(frontmatter, message)` for each and assert `rule.action` is not silently `'warn'` for case (b)/(c) — i.e., the loader should either raise a `ValueError`/return `None` from `load_rule_file`, or set `action` to a fail-closed value.
3. Additionally, feed the resulting `Rule` into `RuleEngine.evaluate_rules` with `tool_input={"command": "rm -rf /"}` and assert the response contains `hookSpecificOutput.permissionDecision == "deny"` rather than only `systemMessage`, for a rule whose author's evident intent (from rule name/message, e.g. `block-dangerous-rm`) was to block.

```python
def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    except (IOError, OSError, PermissionError) as e:
        print(f"Error: Cannot read {file_path}: {e}", file=sys.stderr)
        return None
    except (ValueError, KeyError, AttributeError, TypeError) as e:
        print(f"Error: Malformed rule file {file_path}: {e}", file=sys.stderr)
        return None
```
