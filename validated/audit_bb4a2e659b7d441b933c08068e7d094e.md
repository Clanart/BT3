## Analog Found

The CVE-2018-5759 bug class (unbounded parser recursion depth causing stack-overflow DoS on crafted input) has a concrete analog in this codebase's outer-puzzle "driver" matching chain, which recursively walks attacker-supplied CLVM puzzle structure with no depth limit.

### Title
Unbounded recursion in outer-puzzle driver matching allows wallet crash via deeply nested curried puzzle - (File: `chia/wallet/outer_puzzles.py`)

### Summary
`match_puzzle()`, and the `match()`/`get_inner_puzzle()`/`get_inner_solution()`/`construct()`/`solve()` methods of each outer-puzzle driver (`CATOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`, `SingletonOuterPuzzle`, `RevocationOuterPuzzle`), recurse into the puzzle's "also" inner layer once per curried wrapper layer, with no maximum-depth check. Because the "also" chain length is dictated entirely by how the puzzle reveal was curried — data that originates from an untrusted coin puzzle (e.g. an offer counterparty's puzzle, or an on-chain NFT/CAT/CR/VC puzzle a wallet is asked to parse) — an attacker can construct a puzzle with thousands of trivial nested layers to blow the Python call stack.

### Finding Description
`match_puzzle()` in [1](#0-0)  iterates `driver_lookup` and calls `driver.match(puzzle)`. Each driver's `match()` implementation, in turn, recursively calls back into `self._match(UnknownPuzzle(known_program=inner_puzzle))`, which is bound to `match_puzzle` itself, e.g.: [2](#0-1) [3](#0-2) [4](#0-3) 

The same unbounded recursive pattern repeats for `get_inner_puzzle()`, `get_inner_solution()`, `construct()`, and `solve()` in each of these drivers — every one recurses through `also()`/`self._get_inner_puzzle(...)`/`self._get_inner_solution(...)` for as many layers as the input puzzle contains: [5](#0-4) 

Each recursion level requires only one additional cheap curry wrapper (`(2 (1 . <mod>) <args>)`) around the previous layer, and `uncurry()` (which is itself iterative per-layer, not the source of the bug) succeeds for each such wrapper, so there is no CLVM-cost limit gating the number of layers a puzzle can carry before it ever reaches these Python-side drivers. This mirrors the MuJS `jsparse.c` flaw: a bug class where nested-expression depth is not tracked/limited before recursively walking the resulting structure, leading to stack exhaustion on crafted input.

This is distinct from the project's own defense against this exact class of bug: `sha256_treehash()` was deliberately written non-recursively "so we don't have to worry about blowing out the python stack" [6](#0-5) , showing the codebase authors are aware of this risk for CLVM tree traversal — but the outer-puzzle driver "also" chain was not given the same treatment.

### Impact Explanation
A wallet or Data Layer client that calls `match_puzzle()` on an attacker-supplied puzzle (e.g., while evaluating an incoming offer, syncing a coin with an unfamiliar CAT/NFT/VC puzzle, or processing an offer counterparty's puzzle during trade settlement) can hit Python's recursion limit and raise `RecursionError`, potentially crashing the process handling that puzzle/offer. This is a spend/offer-triggered transaction-processing halt reachable by a single unprivileged offer counterparty or wallet-sync event — no privileged access is required to construct the malicious puzzle reveal.

### Likelihood Explanation
Constructing a puzzle with thousands of trivial nested curry layers is cheap (each layer is a few bytes of CLVM) and does not require executing expensive CLVM opcodes, so it bypasses cost-based mitigations. The only requirement is that the wallet's puzzle-matching code path (`match_puzzle`, or any outer-puzzle driver's recursive helpers) is invoked on the crafted puzzle, which is a normal part of offer evaluation and NFT/CAT/CR coin-state parsing.

### Recommendation
Add an explicit, enforced maximum recursion/layer-depth (or convert to an iterative loop, consistent with `sha256_treehash`) in `match_puzzle()` and in each outer-puzzle driver's `match()`, `get_inner_puzzle()`, `get_inner_solution()`, `construct()`, and `solve()` implementations in `chia/wallet/outer_puzzles.py`, `chia/wallet/nft_wallet/ownership_outer_puzzle.py`, `chia/wallet/nft_wallet/metadata_outer_puzzle.py`, `chia/wallet/vc_wallet/cr_outer_puzzle.py`, `chia/wallet/cat_wallet/cat_outer_puzzle.py`, and `chia/wallet/nft_wallet/singleton_outer_puzzle.py`, rejecting or truncating puzzles that exceed a sane maximum layer count before recursing further.

### Proof of Concept
Construct a puzzle reveal consisting of N (e.g. 2000+) nested curry-wrapped "ownership"/"CR"/"metadata" layers, each wrapping the next as its inner puzzle (each layer trivially matches one driver's expected curried shape so `match()` recurses into `also`). Present this puzzle as an offer counterparty puzzle reveal or as a coin's puzzle in a wallet sync path, then call `match_puzzle(UnknownPuzzle(known_program=<crafted_puzzle>))`; the resulting `RecursionError` is unhandled and crashes/aborts the wallet's processing of that offer/coin.

    def get_inner_puzzle(
        self, constructor: PuzzleInfo, puzzle_reveal: UnknownPuzzle, solution: Program | None = None
    ) -> Program | None:
        matched, curried_args = match_ownership_layer_puzzle(puzzle_reveal)
        if matched:
            _, _, _, inner_puzzle = curried_args
            also = constructor.also()
            if also is not None:
                deep_inner_puzzle: Program | None = self._get_inner_puzzle(
                    also, UnknownPuzzle(known_program=inner_puzzle), None
                )
                return deep_inner_puzzle
            else:
                return inner_puzzle

    def get_inner_solution(self, constructor: PuzzleInfo, solution: Program) -> Program | None:

        also = constructor.also()
        if also:
            deep_inner_solution: Program | None = self._get_inner_solution(also, my_inner_solution)
