### Title
ProtoJSON parser (Python `json_format.py`) embeds raw untrusted field values in `ParseError` exception messages - ([File: python/google/protobuf/json_format.py])

### Summary
The mapstructure advisory's failed invariant is: type-mismatch decode errors interpolate the raw, attacker-supplied value into the error string, and a consuming application (OpenBao) surfaces that string in logs/API responses, leaking sensitive data. The Protobuf Python ProtoJSON parser has the same failed invariant: when a JSON value has an unexpected type or fails validation, `json_format.py` builds `ParseError` messages by directly interpolating the raw JSON value (`value`, `json`) via `.format()`/string concatenation, not just field names/paths.

### Finding Description
In `_ConvertFieldValuePair`, when a repeated field is not given as a list, the raw value is embedded verbatim in the exception: [1](#0-0) 
and the outer `except ParseError as e` / `except ValueError as e` handlers wrap this into a `Failed to parse {field} field: {e}` message and re-raise it up the call stack, so the raw value propagates all the way to the top-level `ParseError` raised by `Parse()`: [2](#0-1) 

The same pattern occurs for well-known types. `TestStruct`/`Struct.FromJsonObject`-style validation errors interpolate the offending value directly: the test suite documents the resulting message `'Failed to parse value field: Struct must be in a dict which is 1234 at TestStruct.value'`, and similarly for `Timestamp`/`Duration`/`FieldMask`, e.g. `Timestamp JSON value not a string: {u?'foo': 123}`: [3](#0-2) 

The `Any` type-mismatch case shows the same class of leak for dict contents (`KeyError: 'value'` and similar structural echoes) confirming the pattern is systemic across well-known-type validators, not an isolated bug: [4](#0-3) 

The Java `JsonFormat.parseFieldValue` has the analogous construct — when a JSON value's type doesn't match the expected primitive field type, the raw JSON element is concatenated into the exception message: [5](#0-4) 

**Why existing protections do not apply here:** Protobuf's TextFormat printer has an explicit `enablingSafeDebugFormat`/redaction mechanism (`REDACTED_MARKER`, `redact_debug_string_`) that suppresses field *values* in debug output for fields marked sensitive, seen in both Java `TextFormat.java` and C++ `text_format.cc`: [6](#0-5) [7](#0-6) 
This redaction infrastructure exists specifically because Protobuf recognizes that echoing field values (even from trusted/parsed messages) in debug/log output is a security concern. However, this redaction only covers `DebugString()`/`TextFormat` printing of *already-parsed* messages with sensitive-field annotations — it does not cover the **ProtoJSON parse-error path**, where raw incoming JSON scalar/dict values (before they are even accepted into a message) are placed into exception text with no redaction, no field-sensitivity check, and no size/type gating.

### Impact Explanation
Applications that use `google.protobuf.json_format.Parse()` (or Java `JsonFormat.parser().merge(...)`) to decode untrusted client-supplied JSON into protobuf messages — a very common gRPC-gateway / REST-to-protobuf pattern — and that log or return `ParseError`/`InvalidProtocolBufferException` messages to callers (a common practice for user-facing "bad request" diagnostics) will leak the raw content of mistyped fields. If a client sends a password, token, or other sensitive value with an unexpected JSON shape (e.g., a nested object where a string was expected, mirroring the exact mapstructure PoC pattern), the value is echoed back in the error/log, exactly matching CWE-532 (Insertion of Sensitive Information into Log File). This matches the consuming-application exposure assumption used in the OpenBao PoC: the library itself doesn't log, but its error API surfaces attacker-supplied values through a channel (exception message) that applications commonly propagate to logs or HTTP error responses.

### Likelihood Explanation
High likelihood in real deployments: `json_format.Parse` is the standard entry point for consuming ProtoJSON over gRPC-Gateway/Envoy/Connect-style APIs, type-mismatch inputs (wrong JSON shape for a field) are trivially attacker-controlled and require no special privileges, and propagating parser exceptions into logs/HTTP responses on 400-class errors is a routine, "trusted application code" pattern (identical in spirit to the OpenBao example). No crash, memory-safety or resource-exhaustion issue is involved — this is a pure information-disclosure-via-error-message issue, directly analogous to the reported CWE-532.

### Recommendation
- Do not interpolate raw JSON values (`value`, `json`, dict/list contents) into `ParseError` / `InvalidProtocolBufferException` messages in `json_format.py`'s `_ConvertFieldValuePair`, `_ConvertMapFieldValue`, `_ConvertScalarFieldValue`, and the well-known-type parsers in `well_known_types.py`. Replace with just the observed JSON *type name* (e.g., `dict`, `list`, `int`) rather than the value itself.
- Apply the same treatment in Java's `JsonFormat.parseFieldValue` (`"Invalid value: " + json + " for expected type: ..."`).
- Consider extending the existing TextFormat "safe debug format"/redaction concept to the ProtoJSON parser's error path, or at minimum document clearly that `ParseError` messages may contain untrusted input and must not be logged/returned verbatim by callers.

### Proof of Concept
Using the Python bindings in this repository (`python/google/protobuf/json_format.py`), given a proto3 message `TestAllTypes` with a `string` field `optional_string`, sending:
```python
from google.protobuf import json_format
from google.protobuf import struct_pb2

msg = struct_pb2.Struct()
json_format.Parse('{"value": {"secret_token": "my-sensitive-value"}}', ...)  # wrong-typed field
```
reproduces the documented behavior in `json_format_test.py`'s `testInvalidStruct`/`testTimestampInvalidStringValue`, where the raised `ParseError` message textually contains the attacker-supplied nested value (e.g. `Timestamp JSON value not a string: {u'foo': 123}`), confirming the raw payload is embedded in the exception exactly as in the mapstructure/OpenBao case: [8](#0-7)
