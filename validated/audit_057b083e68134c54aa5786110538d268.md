### Title
Front-runnable, unprivileged reward harvesting lets just-in-time depositors capture unclaimed yield accrued to earlier stakers - (File: `wombat/WombatStaking.sol`, `rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool` distributes rewards to stakers by instantaneously stamping the entire incoming reward amount into `rewardPerTokenStored`, weighted by whatever `totalStaked()` happens to be at the moment the reward is provisioned [1](#0-0) . Because the permissionless `harvest()` entrypoint on `WombatStaking` can be called by any wallet at any time to pull pending WOM yield into this pool [2](#0-1) , an ordinary user can deposit immediately before triggering a harvest and receive a slice of yield that accrued to the pool before their own stake existed — the same "future depositor captures reward that began distributing before their deposit" bug class described in the external report, just realized through instantaneous-rather-than-linear vesting.

### Finding Description
`_provisionReward` (called from `queueNewRewards`/`donateRewards` and internally from harvesting) adds the whole new reward batch to `rewardPerTokenStored` in one shot, using the *current* `totalStaked()` as the denominator:
```
rewardInfo.rewardPerTokenStored =
    rewardInfo.rewardPerTokenStored +
    (_amountReward * 10**stakingDecimals()) /
    this.totalStaked();
``` [3](#0-2) 

There is no time-weighted accounting of *when* each staker's balance was present while the underlying yield (WOM emissions from Wombat's `MasterWombat`) was accruing off-chain in the background. `WombatStaking.harvest()` is `external` and gated only by `_onlyActivePool`, which checks pool status, not `msg.sender` [4](#0-3) [2](#0-1) . Any wallet can therefore:

1. Deposit a large stake via `WombatPoolHelper.deposit`/`depositLP`, which stakes into `MasterMagpie` (increasing `totalStaked()`) [5](#0-4) .
2. Immediately call `harvest()` on `WombatStaking`, which pulls the WOM pending rewards that accumulated for the entire pool's LP position on Wombat (accrued over the time before the attacker's deposit) and pushes them into `BaseRewardPool` via `_toMasterWomAndSendReward` → `queueNewRewards`.
3. Because `rewardPerTokenStored` is bumped using the post-deposit `totalStaked()`, the attacker's freshly deposited balance participates in claiming a proportional share of yield that was earned before they staked, diluting the rightful share of long-term stakers.
4. The attacker calls `getReward` to collect their share, then withdraws their principal.

This mirrors the report's root cause exactly: value distribution keyed off a snapshot (`totalStaked()`/vested amount) that does not distinguish stake duration relative to when the underlying reward was earned.

### Impact Explanation
Yield rightfully belonging to stakers who held their position while the WOM emissions accrued is redirected to a just-in-time depositor, i.e., theft of unclaimed yield from existing stakers. This satisfies the accepted impact category "theft ... of unclaimed yield."

### Likelihood Explanation
`harvest()` requires no privilege and no waiting period, and deposit/harvest/claim/withdraw can all be executed by an EOA in quick succession (bounded mainly by however much pending WOM has accrued and gas/slippage costs of entering/exiting the LP). The larger the pending, unharvested WOM balance and the smaller the attacker's relative deposit cost (e.g., using an LP token they already hold via `depositLP`, which has no pool-entry slippage), the more profitable this becomes, making it a realistically exploitable, unprivileged-wallet path.

### Recommendation
Introduce time-weighted or debt-adjusted reward accounting (e.g., checkpoint `rewardPerTokenStored` immediately before any state-changing stake balance change, and/or restrict/rate-limit permissionless harvest calls, or require a minimum holding period before newly deposited stake participates in freshly harvested rewards) so that `totalStaked()` used in `_provisionReward` reflects only balances that were present while the reward accrued.

### Proof of Concept
1. Assume `BaseRewardPool.totalStaked()` (via `MasterMagpie`) is `T`, and Wombat's `MasterWombat` has `R` pending WOM accrued for the pool's LP position that has not yet been harvested.
2. Attacker calls `WombatPoolHelper.depositLP(X)` (or `deposit`), staking `X` receipt tokens; `totalStaked()` becomes `T + X` [6](#0-5) .
3. Attacker (or anyone) calls `WombatStaking.harvest(lpToken)`, which triggers `_toMasterWomAndSendReward`, harvesting `R` WOM and calling `queueNewRewards(R, wom)` on `BaseRewardPool` [2](#0-1) .
4. `_provisionReward` computes `rewardPerTokenStored += R * 10**decimals / (T + X)`, so the attacker's `X` immediately entitles them to `R * X / (T + X)` of `R`, despite `R` having accrued entirely before their deposit [3](#0-2) .
5. Attacker calls `getReward` (via `MasterMagpie`) to claim `R * X / (T + X)` WOM, then withdraws `X` from the pool, netting yield that should have gone to pre-existing stakers.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
```
