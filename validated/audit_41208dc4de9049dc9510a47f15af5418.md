### Title
Missing rate limiting on `auction_submitBid` RPC endpoint allows unmetered bid-validation and target-tx broadcast spam - (File: kaiax/auction/impl/api.go)

### Summary
Kaia's KIP-249 auction module implements per-peer rate limiting for bids received via P2P gossip (`HandleBid`), but the JSON-RPC entry point `auction_submitBid` that any external caller can invoke bypasses this limiter entirely, allowing an unauthenticated caller to flood the node with expensive bid-validation work and RLP-decoded transaction broadcasts without throttling.

### Finding Description
The `auction` module exposes a public JSON-RPC method `auction_submitBid` implemented by `AuctionAPI.SubmitBid`: [1](#0-0) 

This handler (1) RLP-decodes an attacker-supplied raw transaction, (2) calls `api.a.Backend.SendTx(ctx, targetTx)` to broadcast it into the tx pool/network, and (3) calls `bidPool.AddBid(bid)`, which performs full EIP-712 signature verification (`validateBidSigs`) and pool-mutation logic (`insertBid`).

By contrast, the P2P ingestion path `BidPool.HandleBid` explicitly enforces a per-peer token-bucket rate limiter before doing any of this work: [2](#0-1) 

The rate limiter (`bidsPerSecondPerPeer = 300`, `checkRateLimit`) is only invoked from `HandleBid`. `AddBid` — the function called directly by `SubmitBid` — contains no rate-limiting check: [3](#0-2) 

The RPC service itself is registered with no additional protection at the RPC-namespace level; the general RPC server only applies coarse global connection/concurrency limits (`RPCConcurrencyLimit`, `pendingRequestLimit`), not any per-caller/per-endpoint request rate limit: [4](#0-3) 

This mirrors the structure of CVE-2025-47791: a "verification"-style endpoint that performs meaningful server-side work (signature checks, forwarding/broadcasting) reachable without authentication and with no dedicated rate limiting, while an equivalent, better-guarded code path (there: none; here: the P2P path) enforces limits that the endpoint bypasses.

### Impact Explanation
Any RPC caller can invoke `auction_submitBid` at unlimited frequency. Each call forces the node to:
- RLP-decode a transaction and call `SendTx`, injecting it toward the tx pool/broadcast pipeline,
- perform ECDSA/EIP-712 signature recovery twice (`validateBidSigs` verifies both searcher and auctioneer signatures) under `bidPool.auctionInfoMu` and `bidMu` locks.

Because this bypasses the 300 bids/sec/peer P2P throttle, an attacker can drive CPU (signature verification) and lock contention on `auctionInfoMu`/`bidMu` far above what the P2P layer permits, potentially starving legitimate `Auctioneer`-submitted bid processing (`handleBidMsg`) and target-tx propagation, and consuming node resources disproportionate to the cost paid by the caller (RPC calls have no gas/fee cost). This can degrade the CN's block-building/auction subsystem, an availability impact on the auction/gasless settlement path.

### Likelihood Explanation
High: `auction_submitBid` is a documented public API (see `kaiax/auction/README.md`) intended to be called by arbitrary auctioneers/searchers, requires no special privilege, and needs no valid signature/target-tx pairing to trigger the expensive decode/verification path (invalid bids are cheap to construct but still consume decode and signature-recovery cycles before rejection). No wallet funds are required to make the call — the cost asymmetry (near-zero cost to the caller, CPU + lock cost to the node) is comparable to the "no known workaround, unauthenticated abuse" pattern in the CVE.

### Recommendation
Apply the same (or an RPC-appropriate) per-caller rate limit used in `BidPool.HandleBid`/`checkRateLimit` to the `auction_submitBid` RPC path in `AuctionAPI.SubmitBid`, keyed by remote address/connection or by `bid.Sender`, before performing signature validation or calling `SendTx`. Alternatively, route RPC-submitted bids through the same `checkRateLimit` gate that P2P bids use, ensuring parity between the two ingestion paths.

### Proof of Concept
Not independently reproducible without a running node/RPC endpoint; based on static code analysis:
1. Start a CN node with the auction module enabled and RPC HTTP endpoint exposed.
2. Repeatedly call `auction_submitBid` (e.g., thousands of times per second) with syntactically valid but distinct `BidInput` payloads (varying `TargetTxRaw`/signatures so they aren't deduplicated by `ErrBidAlreadyExists`).
3. Observe that, unlike bids received via the P2P `HandleBid` path (capped at `bidsPerSecondPerPeer = 300`), the RPC path in `kaiax/auction/impl/api.go:118-142` performs full transaction decode, `SendTx`, and EIP-712 signature verification per call with no rate limiting, consuming CPU/lock time disproportionate to attacker cost.

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
}

// AddBid adds a bid to the bid pool.
// Required mutex is locked in each function.
func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}

func (bp *BidPool) HandleBid(peerID string, bid *auction.Bid) {
	if atomic.LoadUint32(&bp.running) == 0 || bid == nil {
		return
	}

	// Check rate limit for this peer
	if !bp.checkRateLimit(peerID) {
		logger.Trace("Rate limit exceeded for peer", "peerID", peerID)
		return
	}

	select {
	case bp.bidMsgCh <- bid:
	default:
		logger.Trace("Bid queue is full, dropping bid", "peerID", peerID)
	}
}

// checkRateLimit checks if the peer is within rate limit
func (bp *BidPool) checkRateLimit(peerID string) bool {
	bp.peerRateLimiterMu.Lock()
	defer bp.peerRateLimiterMu.Unlock()

	limiter, exists := bp.peerRateLimiter.Get(peerID)
	if !exists {
		// Create new rate limiter for this peer
		// Use burst equal to the rate limit (we only use rate limit, not the burst)
		limiter = rate.NewLimiter(rate.Limit(bidsPerSecondPerPeer), bidsPerSecondPerPeer)
		bp.peerRateLimiter.Add(peerID, limiter)
	}

	// It'll simply discard the bid if the rate limit is exceeded
	// We don't need to reserve for a bid here because the original bid will be sent from auctioneer through different channel (see #api.SubmitBid)
	return limiter.(*rate.Limiter).Allow()
}
