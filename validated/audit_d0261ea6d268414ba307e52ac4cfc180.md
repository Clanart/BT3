### Title
Scanner reports already-spent outputs as received because spends never invalidate received state - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The bug class in the external report is an authorization/receipt record that is not invalidated when the underlying asset changes state. `Scanner` in `networks/bitcoin/src/wallet/mod.rs` exhibits the same class: `scan_transaction`/`scan_block` only match `output.script_pubkey` against the registered `scripts` map and emit `ReceivedOutput`s, but never inspect `tx.input` to remove outputs that have been spent. An attacker who sends a Bitcoin transaction that both pays to a registered vault script and spends it within the scanned block causes the scanner to report funds as received that are not spendable.

### Finding Description
`Scanner::new`/`register_offset` populate `self.scripts` mapping each watched P2TR `script_pubkey` to its scalar offset (`networks/bitcoin/src/wallet/mod.rs:162-196`). `scan_transaction` iterates only `tx.output`, pushing a `ReceivedOutput` for every match; it never looks at `tx.input` (`mod.rs:199-214`). `scan_block` simply extends that over every transaction in the block, including the coinbase (`mod.rs:221-227`). There is no tracking of the UTXO set, no removal of outpoints that are spent, and no ordering check between the funding transaction and its spend. Bitcoin permits a transaction to spend an output created earlier in the same block, so a single block can contain txA (creates output to the registered script) and txB (spends it), and `scan_block` will still return txA's outpoint as a valid `ReceivedOutput`. The stale record is never deleted — the direct analog of the approval that survives `handleOutgoingRESDL`.

### Impact Explanation
`ReceivedOutput`s are the wallet layer's representation of spendable deposits: `SignableTransaction`/`TransactionMachine` consume them to build spends (`send.rs:273-285`). An output reported as received but already spent is a deposit credited that cannot actually be spent — funds reported received that are not spendable. Depending on downstream handling, the protocol may attempt to sign transactions referencing a nonexistent UTXO (DoS of the signing round) or credit a depositor for value the vault never held.

### Likelihood Explanation
Fully reachable by an unprivileged party with public inputs: the attacker only needs to broadcast ordinary, consensus-valid Bitcoin transactions — a funding tx to the vault's registered script_pubkey followed by a spending tx, orderable in the same block or any later block. The required public input is exactly the class allowed: "Bitcoin transactions they send". No malicious validator, leaked key, or integrator misuse is required; the flaw is that the scanner's model of "received" is append-only with no invalidation path.

### Recommendation
Track spends alongside receipts: when scanning, iterate `tx.input` and remove/flag any `ReceivedOutput` whose `outpoint` appears in a prior or earlier-in-block input, and maintain a persistent spent-set across blocks so re-scanning or re-orgs cannot resurrect spent outputs. At minimum, document that `scan_transaction` results must be filtered through a UTXO lookup before being treated as spendable, and prefer consulting the RPC `gettxout`/UTXO set for each matched outpoint before emitting a `ReceivedOutput`.

### Proof of Concept
```rust
// Setup: scanner for the vault key, registered offset already inserted
let mut scanner = Scanner::new(vault_key).unwrap();
let offset = scanner.register_offset(attacker_offset).unwrap();
let vault_script = p2tr_script_buf(vault_key + (ProjectivePoint::GENERATOR * offset)).unwrap();

// Attacker builds txA paying `vault_script`, and txB spending txA:0 back to
// an attacker-controlled address. Both are mined in the same block
// (Bitcoin allows in-block spends of earlier outputs).
let tx_a = funding_tx_to(vault_script.clone());      // txid_a:0 -> vault_script
let tx_b = spending_tx(OutPoint::new(tx_a.compute_txid(), 0), attacker_addr);

let block = make_block(vec![coinbase, tx_a.clone(), tx_b.clone()]);

let received = scanner.scan_block(&block);
// BUG: outpoint txid_a:0 is reported as received even though tx_b already
// spent it within the same block — the input is never examined.
assert_eq!(received.len(), 1);
assert_eq!(received[0].outpoint(), &OutPoint::new(tx_a.compute_txid(), 0));
assert_eq!(received[0].output().script_pubkey, vault_script);
// `received[0]` will be handed to SignableTransaction as a spendable UTXO;
// any spend built from it is invalid on-chain.
```

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
