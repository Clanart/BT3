Confirmed: `_params.dispatcher` is a single, shared `CallDispatcher` instance (`evm/src/utils/CallDispatcher.sol`) reused across every `placeOrder` call with `predispatch`, and `_execute`'s postdispatch sweep (`IntentsBase.sol:438-485`). This shared, persistent-balance design is the exact analog to `TribeRedeemer`'s "shared balance used as an implicit oracle" flaw.

### Title
Shared `CallDispatcher` balance is swept in full during `placeOrder` predispatch, letting anyone donate dust to a public, known address to inflate another user's escrowed input amount - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`TribeRedeemer` used `IERC20(token).balanceOf(address(this))` as an implicit "is the pool funded" signal, and an attacker could donate tokens to corrupt that signal and cause an early redeemer to receive a wrong (diluted) payout. `IntentGatewayV2.placeOrder`'s predispatch path makes the same class of mistake: it treats the entire current balance of the shared, public `CallDispatcher` contract as "the funds produced by *this* order's predispatch call," and sweeps `balance` (not `requiredAmount`) into escrow for whichever order happens to run next.

### Finding Description
In the predispatch branch of `placeOrder` [1](#0-0) , for each input token the contract:
1. Reads `balance = IERC20(token).balanceOf(dispatcher)` — the *dispatcher's* balance, not something scoped to this transaction.
2. Only requires `balance >= requiredAmount` (`revert InvalidInput()` if not enough) [2](#0-1) .
3. Constructs a sweep call that transfers the **full `balance`**, not `requiredAmount`, from the dispatcher to the gateway [3](#0-2) .
4. Measures `received = balanceOf(gateway)_after - balanceOf(gateway)_before` and sets `order.inputs[i].amount = received` whenever `received <= order.inputs[i].amount` (i.e., not flagged as "dust") [4](#0-3) .
5. This mutated `order.inputs[i].amount` becomes both the EIP-712 commitment input and the actual escrow credited under `_orders[commitment][token]` [5](#0-4) .

`dispatcher` is `_params.dispatcher`, a single `CallDispatcher` instance shared by every order on the gateway (used identically for predispatch here and for postdispatch sweeps in `_execute`) [6](#0-5) . `CallDispatcher` itself is a bare pass-through executor with a public `receive()` and no access control on who can send it tokens [7](#0-6) .

The corrupted value is `order.inputs[i].amount` (and the derived `commitment`/`_orders[commitment][token]` escrow entry): it is computed from the *entire* dispatcher balance rather than the amount actually produced by *this order's own* predispatch call. Any leftover/donated token balance sitting at the dispatcher's address at the moment `placeOrder` runs its sweep gets silently absorbed into whichever order calls `placeOrder` next with a matching input token, exactly as `TribeRedeemer` absorbed a donated balance into whichever user called `redeem` next.

Existing guards do not stop this:
- The `require`/`revert` only checks a lower bound (`balance >= requiredAmount`), never an upper bound or an exact-match against what the predispatch call itself produced.
- The "received > order.inputs[i].amount → dust" branch only protects the case where the *swept* amount ends up bigger than the *original* requested amount; it does not detect or prevent stray/donated balance from being folded into an order whose requested amount is not yet exceeded — it silently overwrites `order.inputs[i].amount = received` as if that were the legitimately produced amount.
- Because `CallDispatcher` is a single shared, unprotected contract instance across all orders (not a fresh, per-order deployment or isolated escrow), any residual balance from a prior aborted/partial predispatch execution, or tokens sent directly by any third party, becomes ambient state that the next `placeOrder` caller's sweep logic treats as trustworthy.

### Impact Explanation
This falls under "logic attacks" / "false state acceptance" / "wrong beneficiary or amount" in the bounty scope: the escrow amount recorded for an order (and thus the commitment a solver is expected to fill against) can silently diverge from what the order's own predispatch call legitimately produced, because it is derived from a balance check on a shared, unprotected contract rather than an amount attributable specifically to the current transaction. This can inflate a user's committed escrow with funds they never intended to escrow (their own predispatch calldata targeted a smaller amount), or cause an order's true funding to be entangled with unrelated stray balances left in `CallDispatcher`, corrupting downstream accounting of `_orders[commitment][token]` used for both fills and refunds.

### Likelihood Explanation
Likelihood is low-to-moderate, similar to the original c4 finding's judged severity: it requires (a) `placeOrder` being called with `predispatch.call.length > 0 && predispatch.assets.length > 0`, and (b) the `CallDispatcher` holding some pre-existing balance of the same token at the moment the sweep executes (e.g., leftover dust from a prior order's predispatch/postdispatch sweep, or tokens sent directly to the publicly known dispatcher address by any address). No relayer, prover, or admin compromise is needed — it is reachable by any unprivileged actor sending tokens to a known, unauthenticated contract address ahead of another user's `placeOrder` call, mirroring the "malicious user sends tokens to make redeem work" primitive from the source report.

### Recommendation
Do not use the dispatcher's absolute balance as the sweep amount. Instead:
- Snapshot the dispatcher's balance **before** transferring predispatch assets and executing the predispatch call, and compute the delta produced strictly by this transaction (`balanceAfterCall - balanceBeforeCall`) as the amount to sweep, rather than reading the raw post-call balance.
- Sweep only up to the delta actually produced by this order's own predispatch execution, and treat any balance that predates the transaction as un-owned (reject the order, or route it to protocol dust rather than crediting it to the caller's escrow).
- Alternatively, make `CallDispatcher` a fresh, disposable instance per `placeOrder` invocation (e.g., via a minimal proxy deployed and self-destructed/cleared within the transaction) so no ambient balance can persist between orders.

### Proof of Concept
1. Attacker sends 1 wei (or any small amount) of `USDC` directly to the known `CallDispatcher` address (`_params.dispatcher`), which has a public `receive()`/accepts arbitrary ERC-20 transfers with no access control.
2. Victim calls `placeOrder` with `predispatch.assets` funding a predispatch call whose Uniswap-style swap produces, say, `999.999999 USDC` (slightly less than intended due to slippage/fees), while `order.inputs[0].amount = 1000 * 1e6`.
3. In the sweep step, `balance = IERC20(usdc).balanceOf(dispatcher)` now equals `999.999999 USDC + attacker's 1 wei`, which still satisfies `balance < requiredAmount` check only marginally — but critically, the **swept and credited amount** is `balance`, i.e., it includes the attacker's donated wei, and in general (with a larger prior stray balance) can inflate the escrow arbitrarily above what the victim's own predispatch call produced.
4. `order.inputs[0].amount` is overwritten to this inflated `received` value, which becomes part of the EIP-712 `commitment` and the amount credited to `_orders[commitment][usdc]`, permanently mixing an unrelated donor's/attacker's funds into the victim's order escrow accounting.                         value: 0,

                ++i;
            }

                }

    /**
     * @dev Receive function to accept ETH transfers

    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
}
