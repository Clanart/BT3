### Title
Attacker-controlled `WWW-Authenticate` header lets a malicious git remote impersonate GitHub Enterprise and trigger sign-in / credential binding to a rogue host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind()` classifies a remote endpoint as `'enterprise'` (i.e., "this is a real GitHub Enterprise host") purely by inspecting the `WWW-Authenticate` header value that Git forwards from the remote server's HTTP response — without ever calling the actual verification routine (`isGitHubHost`) that would otherwise gate that classification. Because the header content is fully attacker-controlled, a malicious or MITM'd git HTTP remote can force GitHub Desktop to treat an arbitrary host as GitHub Enterprise, triggering an unsolicited GitHub sign-in prompt bound to that attacker host and enabling credential replay against it later.

### Finding Description
When Git needs credentials for an HTTPS remote, it invokes Desktop's credential helper, forwarding any `WWW-Authenticate` headers it captured from the server as `wwwauth[...]` credential fields: [1](#0-0) 

```
  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
```

This short-circuit is reached and returned from *before* the genuine verification step further down the function, `isGitHubHost(endpoint)`, ever executes: [2](#0-1) 

Because the `WWW-Authenticate` header is sent by the remote HTTP server (or any proxy/MITM sitting between the user and the remote), an attacker fully controls its content. Any git remote a user clones/fetches/pushes to — legitimately or via a poisoned URL, compromised proxy, or spoofed DNS — can respond to Git's authentication probe with `WWW-Authenticate: Basic realm="GitHub"` and be classified as `'enterprise'` without any actual confirmation that it is a GitHub Enterprise instance.

That classification then feeds directly into `getCredential()`: [3](#0-2) 

If no existing account matches the (attacker's) endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, presenting the user with a "Sign in to GitHub" dialog scoped to the attacker-controlled hostname. Once an account is created/associated for that endpoint (e.g., via PAT entry or OAuth), subsequent credential lookups match purely by origin equality in `findGitHubTrampolineAccount`: [4](#0-3) 

and the stored username/token are merged back into the credential and handed to Git (and thus sent as an `Authorization` header to that same attacker host) for every future operation against that remote.

### Impact Explanation
This breaks the invariant that "a host is only ever treated as an authenticated GitHub/GHE endpoint after Desktop verifies it via `isGitHubHost`/API probing." A malicious remote can:
- Spoof legitimacy to social-engineer the user into a GitHub-branded sign-in flow tied to the attacker's host (unauthorized account binding), and
- Once an account/PAT is associated with that endpoint, have the user's GitHub credentials silently sent to it on every subsequent fetch/push (credential exfiltration), since the account-matching logic only checks URL origin equality, not real GitHub identity.

This fits the "attacker controls ... a git remote/proxy response" primitive and results in "unauthorized OAuth or account binding" / "credential/token exfiltration," both explicitly listed as valid impacts.

### Likelihood Explanation
Any repository a user clones or adds a remote for can trigger this path the moment Git performs HTTPS authentication against that remote — no special privileges, local access, or pre-existing malware are required, only that the user interacts with an attacker-supplied clone URL/remote or that the connection is intercepted (hostile network/proxy). The `WWW-Authenticate` header is entirely under remote-server control, and the vulnerable code path is reached before any legitimate verification runs, so there is no existing guard preventing it.

### Recommendation
Do not treat the `WWW-Authenticate: realm="GitHub"` header as sufficient proof of a GitHub Enterprise host. At minimum, downgrade this to a hint that is only trusted for hosts that also pass the real `isGitHubHost` check (or an equivalent authenticated verification, e.g., requiring TLS + the `/api/v3` probe) before returning `'enterprise'`. Alternatively, only use the header short-circuit to decide whether to *attempt* the API probe, never to bypass it outright.

### Proof of Concept
1. Attacker hosts a git-over-HTTPS server (or sits as a MITM/proxy) at `https://evil.example.com/foo/bar.git`.
2. Victim adds/clones this remote in GitHub Desktop.
3. On the first authenticated Git operation (fetch/push), the attacker's server responds to Git's credential probe with `WWW-Authenticate: Basic realm="GitHub"`.
4. `getEndpointKind()` in `trampoline-credential-helper.ts` returns `'enterprise'` immediately, skipping `isGitHubHost(endpoint)` verification.
5. Since no account exists for `evil.example.com`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com')`, showing the user a "Sign in to GitHub" dialog for the attacker's host.
6. If the user completes sign-in (PAT or OAuth) believing it is a legitimate corporate GitHub Enterprise prompt, the resulting account is bound to `evil.example.com`.
7. On every future Git operation against that same origin, `findGitHubTrampolineAccount` matches by origin and Desktop automatically supplies the stored token to the attacker's server.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
