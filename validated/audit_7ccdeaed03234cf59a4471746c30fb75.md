## Finding: Unbounded recursion in `PuzzleWithRestrictions.from_memo()` allows stack-consumption DoS from a crafted on-chain memo

### Title
Stack Consumption via Unbounded Recursive Memo Parsing in `PuzzleWithRestrictions.from_memo()` - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs custody/pool puzzle structures from an untrusted, attacker-supplied `Program` memo without any recursion-depth limit. A coin's `CREATE_COIN` memo is fully attacker-controlled data placed on-chain by a single spend, and it is later parsed by this function when any node/wallet reconstructs custody structure (e.g. PlotNFT syncing). A maliciously crafted, deeply nested `MofN` memo can drive unbounded Python recursion and crash the parsing process (`RecursionError` / native stack overflow), analogous to the Exiv2 `stringFormat` stack-consumption CVE where crafted input drives unbounded recursive processing to exhaust the call stack.

### Finding Description
`PuzzleWithRestrictions.from_memo()` recurses into itself for every `MofN` member found in the memo, with no cap on nesting depth: [1](#0-0) 

Specifically, when `further_branching_prog` is truthy, the code decodes an `MofNHint` and recurses for every member:
```
puzzle: MIPSComponent = MofN(
    m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
)
```
There is no depth counter, no maximum-nesting check, and no `try/except RecursionError` guard anywhere in this call chain.

This function is reached from real chain-processing code, not just tests. `PlotNFT.get_next_from_coin_spend()` calls it directly on the `memo_blob` taken from a `CREATE_COIN` condition's memo field of an on-chain spend: [2](#0-1) 

Since `memo_blob` is CLVM data chosen entirely by whoever creates the coin (any wallet/pool operator submitting a spend bundle), an attacker can construct a spend whose `CREATE_COIN` memo encodes a deeply nested `(namespace, [nonce, [], 1, (m, [nested_memo, ...])])` structure, with the inner `MofNHint.member_memos` recursively containing another full `PuzzleWithRestrictions` memo, thousands of levels deep. When any process (pool participant, wallet, or plotnft-tracking tooling) later calls `PuzzleWithRestrictions.from_memo()` on this coin's memo to determine plotnft/pool state, it will recurse until the Python interpreter's stack is exhausted.

Unlike the core CLVM execution path, which is Rust-backed and iterative/cost-bounded (e.g. `sha256_treehash` is deliberately implemented iteratively specifically to avoid Python recursion-limit issues — see `chia/types/blockchain_format/tree_hash.py`), this custody/plotnft memo-parsing path is plain recursive Python with no such protection: [3](#0-2) 

### Impact Explanation
A crafted spend memo can crash any process that parses it via `PuzzleWithRestrictions.from_memo()` — most notably `PlotNFT.get_next_from_coin_spend()`, used to track plotnft/pool-singleton lineage. This is a spend-triggered transaction/state-processing halt: a single malicious pool/plotnft coin spend can cause a `RecursionError` (or, depending on Python/C stack limits, a hard interpreter crash) for any party that later needs to walk that plotnft's history, denying service to pool participants and plotnft tooling that rely on this parsing to determine current pool state.

### Likelihood Explanation
Likelihood is Medium: the attacker only needs to construct a coin with a crafted memo — a normal, permission-less spend action — no special privileges required. However, exploitation requires the victim to actually call `from_memo()` on the attacker's data (i.e., that the malicious coin is part of a plotnft/custody chain a wallet or pool tooling chooses to sync), which narrows practical reach compared to core mempool/consensus paths reachable from any spend bundle.

### Recommendation
Add an explicit recursion/nesting depth limit to `PuzzleWithRestrictions.from_memo()` (and `MofNHint.from_program()`), rejecting memos beyond a sane maximum nesting depth before recursing, or convert the recursive descent into an iterative work-stack implementation (mirroring the pattern already used by `sha256_treehash()`). Additionally, bound the total number of `MofN` members/nodes parsed from a single memo to prevent combinatorial blowup.

### Proof of Concept
1. Construct a nested memo program bottom-up in Python:
```python
inner = Program.to((PuzzleWithRestrictions.spec_namespace, [0, [], 0, MemberHint(puzhash=bytes32.zeros, memo=Program.to(0)).to_program()]))
for _ in range(50_000):
    inner = Program.to((PuzzleWithRestrictions.spec_namespace, [0, [], 1, MofNHint(m=1, member_memos=[inner]).to_program()]))
```
2. Place `inner` as the `memo` in a `CREATE_COIN` condition's memo list (`memo_blob`) of a spend bundle submitted by any wallet/pool operator.
3. Once that coin is created and later inspected, any caller invoking `PuzzleWithRestrictions.from_memo(memo_blob.rest())` (e.g. via `PlotNFT.get_next_from_coin_spend()`) will recurse 50,000+ times, raising `RecursionError` or crashing the process due to native stack exhaustion — mirroring the crafted-input stack-consumption pattern of CVE-2017-14861.
