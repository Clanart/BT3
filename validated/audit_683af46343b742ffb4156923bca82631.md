This confirms the analog: the legitimate `pallet-hyperbridge-host-executive` sets `from: PALLET_ID.to_bytes()` (`ModuleId::Pallet(PalletId(*b"hostexec"))`) when dispatching `Withdraw`/`SetHostParam` governance requests [1](#0-0) [2](#0-1) [3](#0-2) , but the EVM-side `HostManager.onAccept()` never checks `request.from` against this expected `PALLET_ID` — it only checks `request.source` (the chain id).

### Title
`HostManager.onAccept()` fails to validate `request.from`, allowing any Hyperbridge-chain module to spoof governance calls - (File: `evm/src/core/HostManager.sol`)

### Summary
This is a structural analog of the Axiom finding: the Axiom verifier checked `msg.sender`/`chainId`/`sender` but omitted a check on `yaru.adapters()` — the specific attester set — letting an attacker-controlled oracle validate forged messages. In `HostManager.onAccept()`, the equivalent “attester/module identity” check is missing: the function verifies only that the ISMP `request.source` chain equals Hyperbridge's state machine id, but never checks that `request.from` equals the trusted governance pallet id (`hostexec`) that is supposed to be the sole originator of `Withdraw`/`SetHostParam` actions.

### Finding Description
`HostManager.onAccept()` is restricted to `msg.sender == host` via the `restrict(_params.host)` modifier, and additionally checks:
```solidity
if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
``` [4](#0-3) 

This only asserts that the request originated from the Hyperbridge relay chain (a `StateMachine` id) — it never checks `request.from`, i.e., which module/pallet on that chain sent the message. On the Substrate side, the ISMP module router dispatches incoming requests to the correct EVM contract based on `to`, but any pallet capable of calling `IsmpDispatcher::dispatch_request` on the Hyperbridge relay chain can set `from` to an arbitrary value, since `DispatchPost.from` is caller-supplied, not enforced by the dispatcher to match a privileged pallet id. The intended authorization design (as seen in `pallet-hyperbridge-host-executive`) relies on `from == PALLET_ID` (`b"hostexec"`) as the security anchor [2](#0-1) , but `HostManager.sol` never validates it, decoding and executing the action based solely on chain-of-origin:
```solidity
OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
if (action == OnAcceptActions.Withdraw) {
    WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
    IHostManager(_params.host).withdraw(withdrawParams);
} else if (action == OnAcceptActions.SetHostParam) {
    HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
    IHostManager(_params.host).updateHostParams(hostParams);
}
``` [5](#0-4) 

Compare this to other `onAccept` implementations in the same codebase that do validate the source module address explicitly (e.g. `_authenticate` in `ExtrinsicIntents.sol`, and `expectedSource`/`request.from` checks in `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol`), showing that per-module `from` verification is the established security pattern that `HostManager` omits [6](#0-5) [7](#0-6) .

### Impact Explanation
If any other pallet on the Hyperbridge relay chain (present now or added in a future runtime upgrade) can call the generic ISMP dispatch primitive with an arbitrary `from` while targeting an EVM `HostManager` contract, it can invoke `IHostManager.withdraw()` (draining protocol fee revenue to an attacker-controlled beneficiary) or `updateHostParams()` (rewriting critical `EvmHost` parameters, e.g. fee token, per-byte fees, or state-machine parameters governing consensus/proof acceptance). This is unauthorized execution/fund loss reachable purely because `HostManager` binds trust to `request.source` (chain-level) instead of `request.from` (module-level), which is the exact class of "checked chain/sender but not the specific attesting identity" bug described in the Axiom report.

### Likelihood Explanation
Exploitability depends on whether any non-privileged, unprivileged-origin pallet on the Hyperbridge relay chain can be induced to dispatch an ISMP POST with `from` set arbitrarily and `dest`/`to` aimed at a target `HostManager`. Based on the code reviewed, `dispatch_request` is a generic dispatcher primitive and `DispatchPost.from` is filled in solely by the calling pallet at its own discretion (as seen in `host-executive`, which sets it to its own hardcoded `PALLET_ID`) — nothing in `HostManager.sol` cross-checks this value. I was not able to fully confirm within this review whether the ISMP router or runtime configuration additionally restricts which pallets/origins may dispatch through this specific primitive (i.e., whether some governance-only origin gate already exists elsewhere in the runtime), so likelihood is assessed as plausible but not fully proven from the EVM-side code alone.

### Recommendation
In `HostManager.onAccept()`, add an explicit check that `request.from` equals the expected governance module id (the `hostexec` pallet id bytes), mirroring the fix pattern from the Axiom report (validating the specific authorized identity, not just the origin chain):
```solidity
bytes memory expectedFrom = hex"..."; // PALLET_ID.to_bytes() for `hostexec`
if (keccak256(request.from) != keccak256(expectedFrom)) revert UnauthorizedAction();
```

### Proof of Concept
Not independently executable from the EVM-only code reviewed — a full PoC would require confirming, on the Substrate runtime side, that a caller can drive `IsmpDispatcher::dispatch_request` with a `DispatchPost{ from: <arbitrary>, to: HostManager, dest: <hyperbridge state machine> }` outside the `hostexec` pallet's controlled call sites. This portion could not be verified within the scope of this review; it is flagged as the key remaining uncertainty for confirming exploitability.
