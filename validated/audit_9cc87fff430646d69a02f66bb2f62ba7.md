### Title
Distribution precompile's `rewards()` query accepts `msg.value` with no non-payable check, permanently stranding sent usei/wei - (File: precompiles/distribution/distribution.go)

### Summary
The `HolographOperator.executeJob` bug is a case where ETH is accepted by a function but the code path that should handle/refund that value never runs, permanently locking the sender's funds in the contract. The Sei distribution precompile has an analogous flaw: its `rewards()` view method is dispatched **without ever inspecting `value`**, unlike every other read/write method in the same precompile, which either calls `pcommon.ValidateNonPayable(value)` (to reject `value`) or `pcommon.HandlePaymentUsei` (to properly account for it). Because Sei's own EVM keeper marks the distribution precompile address as **not** a "payable precompile" (`IsPayablePrecompile`), any `value` sent alongside a `rewards()` call is transferred by the EVM's native value-transfer logic into the precompile's account balance but is never returned to the caller and never converted into a corresponding native `usei` transfer, since `HandlePaymentUsei`/refund logic is only invoked from the mutating (transaction) methods.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute` dispatches on `method.Name`: [1](#0-0) 

Every other view method in this switch (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) receives `value` and calls `p.validateInput(value, args, N)`, which internally calls `pcommon.ValidateNonPayable(value)` to reject any non-zero value: [2](#0-1) [3](#0-2) 

`rewards()`, however, is called as `p.rewards(ctx, method, args)` — `value` is not even passed into the function signature, so there is no way for it to reject or otherwise account for a non-zero `value`: [4](#0-3) 

This is confirmed by the integration-test documentation for this exact precompile, which explicitly calls out this method as the one exception: [5](#0-4) 

Separately, the EVM keeper maintains an explicit allow-list of "payable precompiles" whose transfer events to/from the precompile address are suppressed (bank, staking, gov, wasmd) — the distribution precompile is **not** in this list: [6](#0-5) 

Because the standard EVM `CALL` value-transfer mechanism runs before/independent of the precompile executor logic, any `value` attached to a `rewards()` call is still moved from the caller's account balance into the distribution precompile's address balance at the EVM/state layer, exactly like the underlying `call{value: msg.value}` semantics in the Holograph report. Since (a) `rewards()` never invokes `HandlePaymentUsei` (which is the only mechanism in this precompile that debits/refunds sent value against the real `bank` module) and (b) distribution is not registered as a payable precompile with any sweep/refund path, any usei/wei sent this way has no code path to be recovered by the caller or forwarded to any legitimate destination.

### Impact Explanation
Any externally owned account or contract that calls `rewards(address)` on the distribution precompile (`0x0000000000000000000000000000000000001007`) while attaching non-zero `value` will have that value irrecoverably stranded at the precompile's EVM address. This is a direct, permanent loss of user funds reachable from an ordinary, unprivileged EVM transaction or contract call — no special privileges, validator collusion, or malicious peer behavior required. This matches the "concrete fund loss or permanent freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate to high in practice: `rewards()` is a commonly-used read-only helper for querying delegator rewards, and unlike `distribution.delegate`/`gov.deposit`, which require attaching value by design, there is no reason for a typical caller to intentionally send value to a query method — but naive integrators or wallets that always attach `msg.value` defensively, or that copy patterns from the payable withdraw methods in the same ABI, could easily trigger this without any explicit warning, since the call does not revert. The comment in the integration test README shows the team is aware this exact function is missing the guard other view methods have, which raises confidence this is a genuine, currently-unpatched gap rather than a misunderstanding.

### Recommendation
Add `value` to the `rewards` function signature and call `pcommon.ValidateNonPayable(value)` (or the shared `p.validateInput(value, args, 1)` helper used by every other read method in this file) before executing the query, so that any non-zero `value` attached to a `rewards()` call causes the transaction to revert instead of silently stranding funds — consistent with how `params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, and `communityPool` already behave.

### Proof of Concept
1. Deploy/point a contract or send a raw EVM transaction to the distribution precompile address `0x0000000000000000000000000000000000001007` with:
   - `data` = ABI-encoded call to `rewards(address delegatorAddress)` with a valid, associated delegator address as argument.
   - `value` = any non-zero wei amount (e.g., 1 sei worth of wei).
2. Observe that the call succeeds (does not revert) and returns the expected rewards data, exactly as it would with `value = 0`, confirmed by the dispatch path at `precompiles/distribution/distribution.go` lines 204-205 and `rewards` at lines 543-579, neither of which reference `value`.
3. Check the caller's on-chain usei/wei balance before and after the call: the attached `value` has been debited from the caller but is not present in any bank-module balance associated with the caller, the delegator, or any validator — it is stuck on the EVM precompile address, which has no associated withdrawal or sweep mechanism (distribution is absent from `payablePrecompiles` in `x/evm/keeper/precompile.go`, and unlike the mutating distribution methods, `rewards()` never calls `HandlePaymentUsei`, which is the only refund/accounting path in this precompile).

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
