### Title
Missing zero-address validation on `_for` in staking/deposit paths permanently freezes yield-share accounting - ([File: wombat/WombatPoolHelperV2.sol], [File: rewards/MasterMagpie.sol])

### Summary
Analogous to the Lido `DepositSecurityModule` report (unchecked address before use), several unprivileged, user-reachable deposit paths in the Magpie/Wombat integration accept an attacker/user-supplied `_for` address and forward it into `MasterMagpie`'s share-accounting system without ever validating it is non-zero.

### Finding Description
`WombatPoolHelperV2.depositFor(uint256 _amount, address _for)` pulls tokens from `msg.sender`, deposits them into the Wombat pool, and stakes the resulting receipt tokens into `MasterMagpie` on behalf of an arbitrary `_for` address, with no check that `_for != address(0)`: [1](#0-0) 

That call flows into `MasterMagpie.depositFor`, which is guarded only by `_onlyPoolHelper` (a pool-registration check, not an identity/zero-address check on `_for`), and then into the internal `_deposit` routine that credits `_for`'s balance and increases the pool's total staked supply: [2](#0-1) 

The same unchecked-`_for` pattern exists in `VLMGP.lockFor(uint256 _amount, address _for)` and `mWomSV.lockFor(uint256 _amount, address _for)`, both of which transfer tokens from `msg.sender` and then call `IMasterMagpie(masterMagpie).depositVlMGPFor(_amount, _for)` without validating `_for`: [3](#0-2) [4](#0-3) 

Because `MasterMagpie.updatePool` computes reward-per-share for the whole pool using `lpSupply` (the aggregate staked amount reported by `_calLpSupply`, which is driven by `IBaseRewardPool.totalStaked`) as the denominator: [5](#0-4) 

any deposit credited to `address(0)` permanently inflates this denominator (`totalStaked`/`lpSupply`) with a balance that can never be withdrawn or claimed (nobody controls the zero address), while contributing nothing offsetting to future emission math. This permanently and irreversibly reduces `accMGPPerShare` growth for every other legitimate staker in that same pool, for as long as the protocol runs.

### Impact Explanation
This qualifies as permanent freezing/theft of unclaimed yield for all other stakers of the affected pool: MGP (and, via the `BaseRewardPool`/rewarder wiring, other reward tokens queued against the same `lpSupply`) that would have accrued to legitimate depositors is diluted forever once tokens are staked under `address(0)`. Because `totalStaked` can never decrease (the shares can never be withdrawn), the effect is a permanent, non-recoverable degradation of yield for every other user in the pool — not a self-contained, self-inflicted loss confined to the caller.

### Likelihood Explanation
The path is reachable by any ordinary wallet with no special privileges: `WombatPoolHelperV2.depositFor`, `VLMGP.lockFor`, and `mWomSV.lockFor` are all public/external, unauthenticated beyond `whenNotPaused`/`nonReentrant`, and none of them validate the `_for` parameter. Triggering it only costs the caller the gas and the (small) amount of tokens they choose to deposit for `address(0)`, making it a cheap, repeatable griefing vector against the shared reward pool.

### Recommendation
Add an explicit zero-address check on every externally reachable `_for`/`sender` parameter before it is used to update share accounting, e.g.:
```solidity
if (_for == address(0)) revert InvalidAddress();
```
This should be added in `WombatPoolHelperV2.depositFor`/`depositNative`/analogous helper `depositFor` functions, `MasterMagpie.depositFor`/`depositVlMGPFor`, `VLMGP.lockFor`, and `mWomSV.lockFor`, mirroring the zero-address guards already present in `BaseRewardPool`'s constructor (`NotAllowZeroAddress`): [6](#0-5) 

### Proof of Concept
1. Any wallet calls `WombatPoolHelperV2.depositFor(amount, address(0))` (or `VLMGP.lockFor(amount, address(0))` / `mWomSV.lockFor(amount, address(0))`), supplying its own tokens. [1](#0-0) 
2. `MasterMagpie._deposit`/`depositVlMGPFor` credits `address(0)` and increases the pool's `totalStaked`/`lpSupply` with no corresponding withdrawable claim. [7](#0-6) 
3. On the next `updatePool` call, `accMGPPerShare` is computed as `mgpReward * 1e12 / lpSupply`, where `lpSupply` now permanently includes the un-withdrawable zero-address balance, permanently lowering the reward rate for every other staker in that pool. [8](#0-7)
