### Title
Permissionless `updateEndRemainingAllocation()` allows denominator manipulation in `getBonusAmount`, enabling disproportionate bonus extraction and insolvency - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is a public, unauthenticated function that recomputes `totalEndRemainingAllocation = totalRemainingAllocation` any time after `periodsEndTime[4]`, with no guard preventing repeated overwrites once it has already been set. `claim()` only re-triggers this recompute when `totalEndRemainingAllocation == 0`, but an attacker can call `updateEndRemainingAllocation()` directly between `claim()` calls to shrink the denominator used in `getBonusAmount()`, inflating the bonus paid to whichever claim happens next, at the expense of subsequent legitimate claimers.

### Finding Description
`getBonusAmount()` computes each late claimer's bonus as: [1](#0-0) 
`bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation`.

`totalEndRemainingAllocation` is meant to be a one-time snapshot of `totalRemainingAllocation` taken right after `periodsEndTime[4]`, but the snapshot function has no re-entry guard: [2](#0-1) 

`claim()` only recomputes the snapshot when it is exactly `0`: [3](#0-2) 

Because `updateEndRemainingAllocation()` is `public` and has no access control and no "already finalized" flag, any unprivileged account can call it directly at any point after `periodsEndTime[4]`, independent of `claim()`'s internal guard. Each subsequent claim reduces `totalRemainingAllocation` (line 164, `totalRemainingAllocation -= userAllocation`). By interleaving direct calls to `updateEndRemainingAllocation()` with `claim()` calls (their own or an accomplice's), the attacker can repeatedly shrink the denominator fed into `getBonusAmount()` for subsequent claimants, inflating their `bonusAmount` far beyond their fair pro-rata share of `totalBonus`.

Example: three late claimers (C1, C2, C3), each with `allocation = 100`, and `totalBonus = 300`, with `totalRemainingAllocation = 300` at `periodsEndTime[4]`.
- Intended (no manipulation): first `claim()` sets `totalEndRemainingAllocation = 300` once; each of C1/C2/C3 gets `bonus = 100*300/300 = 100`, totaling exactly `300`.
- Manipulated: attacker calls `updateEndRemainingAllocation()` before C1 claims (`= 300`); C1 claims (bonus 100, `totalRemainingAllocation` drops to 200); attacker calls `updateEndRemainingAllocation()` again (`= 200`); C2 claims (bonus `100*300/200 = 150`, `totalRemainingAllocation` drops to 100); attacker calls it again (`= 100`); C3 claims (bonus `100*300/100 = 300`). Total bonus disbursed = `100+150+300 = 550`, well beyond `totalBonus = 300`.

The only safeguard against over-payment is the balance check `if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();` (line 160), which stops a single overdraft but does not stop cumulative overpayment across multiple claimers: the earlier manipulated claims can drain principal+inflated-bonus disproportionately, leaving the contract without enough balance for legitimate remaining claimants' base allocations (their guaranteed principal, not just the bonus). This is a genuine, unprivileged, permissionless griefing/theft vector because `updateEndRemainingAllocation()` has no `onlyOwner`/`nonReentrant`/finalization check.

### Impact Explanation
This breaks the accounting invariant that the sum of `bonusAmount` paid across all late claimers must never exceed `totalBonus`. By front-running/interleaving calls to the permissionless `updateEndRemainingAllocation()`, an attacker (or an attacker colluding with themselves via multiple claims from accounts they've acquired allocations for) can extract a disproportionately large share of `totalBonus`, and in the worst case drain the airdrop contract's token balance such that later, honest claimants cannot even withdraw their full guaranteed principal allocation. This matches the Immunefi impact class of protocol insolvency / theft of user funds (direct extraction of bonus funds beyond fair share, and permanent freezing of other users' principal once the balance is exhausted).

### Likelihood Explanation
- `updateEndRemainingAllocation()` requires no special role — it is `public` with only a timestamp check (`block.timestamp >= periodsEndTime[4]`).
- No capital is needed beyond gas; the attacker does not need to hold any allocation themselves to call `updateEndRemainingAllocation()`, though they benefit most by controlling (or timing around) one or more `allocations[]` entries to be the "next" claimer after each denominator shrink.
- The attack is fully repeatable in every block after `periodsEndTime[4]` for as long as remaining allocations exist, and simply requires ordering transactions (trivial via mempool front-running or bundling), so feasibility is high.

### Recommendation
Add a one-time finalization guard, e.g. a boolean `bool public endAllocationFinalized` set to `true` the first time `updateEndRemainingAllocation()` successfully sets a non-zero value, and revert/no-op on subsequent calls once finalized. Alternatively, restrict `updateEndRemainingAllocation()` to be called only internally from `claim()` (make it `internal`/`private`) so it cannot be invoked directly and repeatedly by external actors, preserving the intended "set once" snapshot semantics.

### Proof of Concept
Foundry test plan:
1. Deploy `Airdrop` with a `startTime`; register three users (C1, C2, C3) each with `allocations = 100`; warp past all `periodsEndTime[]` so cumulative `percentPerPeriod` = 100%.
2. Seed `totalBonus` to `300` (e.g., via earlier accounts claiming early and forfeiting, or by directly setting via a helper that mimics forfeiture) and ensure `totalRemainingAllocation = 300` at this point (only C1/C2/C3 remain unclaimed), and fund the contract with at least `100*3 + 300 = 600` tokens.
3. Baseline run: call `claim()` from C1, C2, C3 back-to-back with no external `updateEndRemainingAllocation()` calls; assert `bonusSum == totalBonus (300)`.
4. Attack run (fresh deployment/state): before each `claim()` call, have an unprivileged attacker address call `updateEndRemainingAllocation()` directly; record `bonusAmount` returned/paid for each of C1, C2, C3.
5. Assert (invariant violation): `bonusSum (550) > totalBonus (300)`, demonstrating the denominator manipulation inflates aggregate bonus payouts beyond the funded bonus pool, and that the last claimant, or a subsequent unrelated allocation holder, may hit `InsufficientBalance()` on their legitimate principal claim due to the contract balance being drained by the manipulated earlier claims.

    function claim() external {
        if (totalEndRemainingAllocation == 0) {
            updateEndRemainingAllocation();
        }
        uint256 claimableAmount = getClaimableAmount(msg.sender);
        
        if(claimableAmount == 0) revert NothingToClaim();
        if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();

        uint256 userAllocation = allocations[msg.sender];
        allocations[msg.sender] = 0;
        totalRemainingAllocation -= userAllocation;
        if (claimableAmount <= userAllocation) {
            uint256 forfeited = userAllocation - claimableAmount;
            totalBonus += forfeited;
        }
        aidropToken.safeTransfer(msg.sender, claimableAmount);
    }
