### Title
Unbounded Unicode NFKD normalization of attacker-supplied mnemonic strings in `mnemonic_to_seed()` causes daemon-process DoS - (File: `chia/util/keychain.py`)

### Summary
The `add_key`/`add_private_key` daemon RPC commands accept an arbitrary-length `mnemonic_or_pk` string and pass it directly into `Keychain.add_key()`, which for private keys calls `mnemonic_to_seed()` before any length or word-count validation is performed. `mnemonic_to_seed()` runs `unicodedata.normalize("NFKD", mnemonic)` on the entire, unvalidated string. Supplying a very long string containing non-ASCII/combining Unicode code points skips the cheap word-count check and forces the daemon's single asyncio event loop to perform expensive Unicode normalization work, causing a denial of service — the same bug class as CVE-2024-23826 (unbounded-length, Unicode-normalized user input processed expensively before validation).

### Finding Description
`KeychainServer.add_key()` only checks that `mnemonic_or_pk` is present, with no bound on its length, before calling `Keychain.add_key()`: [1](#0-0) 

`Keychain.add_key()` calls `mnemonic_to_seed(mnemonic_or_pk)` unconditionally for private keys, before any format/length validation of the mnemonic occurs: [2](#0-1) 

`mnemonic_to_seed()` only performs the cheap word-count sanity check (`mnemonic_from_short_words`) when the string is pure ASCII. If any character has `ord(c) >= 128` (e.g. combining diacritical marks such as `\u030c`/`\u0301` used in the codebase's own NFKD test fixtures), that check is skipped entirely, and the full, unbounded string is passed straight into `unicodedata.normalize("NFKD", mnemonic)`: [3](#0-2) 

The word-count validation that *would* reject an oversized/invalid mnemonic (`mnemonic_from_short_words`, enforcing 12/15/18/21/24 words) is only reached afterward, inside `bytes_from_mnemonic()`, which is called *after* `mnemonic_to_seed()` has already normalized the whole string: [4](#0-3) 

Because there is no upfront length cap anywhere on the `mnemonic_or_pk` field accepted by the daemon RPC, and because Unicode NFKD normalization cost scales with the number of combining characters/canonical-decomposition steps it must process, a caller can submit a request with a multi-megabyte string composed largely of combining-mark sequences. The daemon processes RPC requests on its single asyncio event loop, so the CPU-bound normalization call blocks all other daemon activity (wallet RPC dispatch, keychain access, other clients) for the duration of the call. This mirrors the original bug class exactly: unauthenticated-format-wise but length-unbounded string flows into a normalization routine known for costly behavior on adversarial inputs, prior to any size/format validation.

By contrast, the keychain's *label* field is defended: it is trimmed and explicitly bounded by `MAX_LABEL_LENGTH` before any processing: [5](#0-4) 
No equivalent bound exists for the mnemonic string consumed by `mnemonic_to_seed`.

### Impact Explanation
A successful call blocks the daemon's event loop, which backs the Chia daemon service used by the wallet RPC/CLI and keychain client (`chia.daemon.keychain_proxy`), producing a synchronous processing halt for the process while the crafted mnemonic is normalized. This denies service to any other RPC clients (wallet, CLI, GUI) waiting on the same daemon process for the duration of the call, matching the "Medium" DoS classification of the original CVE.

### Likelihood Explanation
The `add_key`/`add_private_key` daemon RPC commands are reachable by any client already authorized to talk to the local daemon socket (the same trust boundary as the original wallet-user-facing avatar upload). No additional privilege beyond normal daemon-RPC access is required, and the trigger requires only building a string of repeated Unicode combining characters — no cryptographic knowledge or race condition needed, making exploitation straightforward once RPC access is available.

### Recommendation
Add an explicit upper bound on the length of `mnemonic_or_pk` (and specifically the string passed into `unicodedata.normalize`) before any normalization work is performed in `mnemonic_to_seed()`, and validate word count/character-class constraints prior to calling `unicodedata.normalize`, mirroring the length checks already applied to keychain labels via `MAX_LABEL_LENGTH` in `chia/util/file_keyring.py`. Reject oversized or malformed mnemonic input in `KeychainServer.add_key()`/`Keychain.add_key()` before it reaches `mnemonic_to_seed`.

### Proof of Concept
1. Connect to the local daemon RPC (as an already-authorized keychain/daemon RPC client).
2. Send an `add_private_key` (or `add_key`) command with:
   `mnemonic_or_pk = ("\u030c\u0301" * N)` where `N` is large (e.g., several million repeats), ensuring the string is non-ASCII so `mnemonic_from_short_words` is skipped in `mnemonic_to_seed`.
3. The daemon calls `Keychain.add_key()` → `mnemonic_to_seed()` → `unicodedata.normalize("NFKD", mnemonic)` on the full string before any length/word validation occurs, consuming CPU on the daemon's event loop and delaying/blocking all concurrent RPC processing for the duration of the call.

```python
def mnemonic_from_short_words(mnemonic_str: str) -> str:
    """
    Since the first 4 letters of each word is unique (or the full word, if less than 4 characters), and its common
    practice to only store the first 4 letters of each word in many offline storage solutions, also support looking
    up words by the first 4 characters
    """
    mnemonic: list[str] = mnemonic_str.split(" ")
    if len(mnemonic) not in {12, 15, 18, 21, 24}:
        raise ValueError("Invalid mnemonic length")

    four_char_dict = {word[:4]: word for word in bip39_word_list().splitlines()}
    full_words: list[str] = []
    for word in mnemonic:
        full_word = four_char_dict.get(word[:4])
        if full_word is None:
            raise ValueError(f"{word!r} is not in the mnemonic dictionary; may be misspelled")
        full_words.append(full_word)

    return " ".join(full_words)
```

```python
def mnemonic_to_seed(mnemonic: str) -> bytes:
    """
    Uses BIP39 standard to derive a seed from entropy bytes.
    """
    # If there are only ASCII characters (as typically expected in a seed phrase), we can check if its just shortened
    # 4 letter versions of each word
    if not any(ord(c) >= 128 for c in mnemonic):
        mnemonic = mnemonic_from_short_words(mnemonic)
    salt_str: str = "mnemonic"
    salt = unicodedata.normalize("NFKD", salt_str).encode("utf-8")
    mnemonic_normalized = unicodedata.normalize("NFKD", mnemonic).encode("utf-8")
    seed = pbkdf2_hmac("sha512", mnemonic_normalized, salt, 2048)

    assert len(seed) == 64
    return seed
```
