### Title
CEI violation in `withdraw()` allows escrow double-drain via attacker-supplied malicious input token - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` in the Tron contract deployment pays out escrowed tokens with a raw low-level `.call` **before** debiting the corresponding `_orders[commitment][token]` ledger entry, whereas the equivalent, already-audited mainnet EVM path (`IntentsBase.sol::_withdraw`) was fixed to decrement the escrow ledger *before* making the external transfer. This is the same Checks-Effects-Interactions violation class described in the external report (external call before state update on a balance/ledger variable that is shared across functions).

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` loops over the order's escrowed tokens:

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;   // <-- ledger updated AFTER the external call
``` [1](#0-0) 

The check that is supposed to prevent double-withdrawal only reads the *pre-call* value:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
``` [2](#0-1) 

Because `order.inputs` (the escrowed tokens) are chosen entirely by the order creator when calling `placeOrder`, an attacker can escrow a token contract they fully control alongside a legitimate, valuable token in the same order. When `withdraw()` iterates the `body.tokens` array and reaches the attacker's malicious token, the `token.call(transfer(...))` hands execution to attacker-controlled code *before* `_orders[commitment][token]` for that entry — and every entry not yet reached in the loop (including the legitimate token) — has been debited. This is functionally identical to the CEI-fix example given in the report for `withdraw()`/`liquidate()`, where the guarded state (`_orders`) is written only after the external call returns.

By contrast, the mainnet EVM architecture already fixed this exact pattern in the shared `_withdraw` helper:
```solidity
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
``` [3](#0-2) 
and the accompanying reentrancy test suite explicitly documents that the fix was to move the `_filled`/ledger writes *before* any external call to close a reentrancy window that previously existed in `_fillSameChain`/`withdraw`. [4](#0-3) 

The Tron contract was not brought in line with that fix: its `withdraw()` still performs the external call first for both the per-token loop and the transaction-fee payout (`feeToken.call(...)` before `delete _orders[body.commitment][TRANSACTION_FEES]`), reproducing the pre-fix vulnerability class on a live deployment target. [5](#0-4) 

### Impact Explanation
`_orders[commitment][token]` is the authoritative escrow ledger backing every bridged asset held by the IntentGateway for that order. If the external call to an attacker-controlled token can re-enter before the corresponding decrement, the escrow for that order (including any *other*, legitimate token escrowed in the same order) can be paid out more than once, directly matching the bounty's "stealing or loss of funds" and "double-settlement" categories. The corrupted value is `_orders[body.commitment][token]`, and the existing `if (_orders[...] == 0) revert UnknownOrder()` guard does not stop the path because it is evaluated once per loop iteration against a value that has not yet been decremented for the entry currently being paid out.

### Likelihood Explanation
Exploitability depends on `withdraw()` being reachable from a path an unprivileged solver/filler can trigger with attacker-chosen order composition. Both call sites confirmed by direct code inspection (`onAccept` for `RedeemEscrow`/`RefundEscrow`, and `onGetResponse`) are `onlyHost`-gated, and `EvmHost.dispatchIncoming` correctly records `_requestReceipts`/`_responseReceipts` (replay protection) **before** invoking the app callback, which blocks trivial re-delivery of the same cross-chain message. [6](#0-5) 
A `grep_search` on the Tron file also surfaced a `fillOrder` symbol, suggesting the Tron contract may combine same-chain fill logic and `withdraw()` in a single monolithic contract (unlike the mainnet EVM split into `IntrinsicIntents`/`ExtrinsicIntents`), which would make `withdraw()` reachable from a public, unprivileged entry point the same way `_fillSameChain` reaches `_withdraw` on mainnet. I was not able to read that portion of the file before the tool budget ran out, so **this specific reachability claim is unconfirmed** — it is the key open question determining whether this is directly exploitable by an ordinary user/solver or only by the host/governance-restricted flows already protected by CEI at the `EvmHost` layer.

### Recommendation
Regardless of the exact call-path reachability, bring `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` in line with the fixed `IntentsBase.sol::_withdraw` pattern: decrement `_orders[body.commitment][token]` (and `delete` the `TRANSACTION_FEES` entry) *before* making any external `.call`/`transfer`, for every branch (native, ERC20, and fee token). Additionally, verify and document every public entry point that can reach `withdraw()` in the Tron deployment, and add a reentrancy guard or `_filled`-style short-circuit consistent with the mainnet fix if any unprivileged-caller path exists.

### Proof of Concept
Conceptual PoC (needs confirmation of the exact public entry point into `withdraw()` in the Tron file):
1. Attacker deploys `EvilToken`, an ERC20-like contract whose `transfer()` function, when called by `IntentGatewayV2`, re-enters the gateway.
2. Attacker calls `placeOrder` with `order.inputs = [EvilToken (amount X), USDC (amount Y)]`, escrowing both tokens under a single `commitment`.
3. A solver fills the order (or the order is cancelled/refunded), triggering `withdraw(body, ...)` where `body.tokens = [EvilToken, USDC]`.
4. The loop calls `EvilToken.call(transfer(beneficiary, X))` first; `_orders[commitment][EvilToken]` is not yet decremented, and `_orders[commitment][USDC]` (not yet reached) is also still fully populated.
5. Inside `EvilToken.transfer()`, if `withdraw()` (or the public function that leads to it) can be re-entered, the attacker/malicious contract re-invokes the same withdrawal path for `commitment`, causing `USDC` (and/or `EvilToken`) to be paid out a second time before either decrement from step 4 takes effect, draining escrow beyond what was legitimately owed.             if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }

        }

        if (isRefund) {
