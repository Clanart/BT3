## Title
Discard-Changes Path Resolution Bypasses `resolveWithin` Symlink/Traversal Guard, Enabling File Deletion Outside the Repository - (File: `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore.discardChanges` resolves each file path to discard using raw `Path.resolve`/`Path.join` against `this.repository.path`, instead of the codebase's dedicated `resolveWithin` helper (used elsewhere, e.g. in `app/src/lib/copilot-conflict-context.ts` and `app/src/ui/dispatcher/dispatcher.ts`) which explicitly guards against directory-traversal and symlink-escape attacks via `realpath` comparison.

### Finding Description
The repository already has a hardened path-containment primitive, `resolveWithin`, that normalizes a path, resolves it against a root, and then calls `realpath` on both the root and the resolved path to confirm the *real* (symlink-resolved) location is still inside the root: [1](#0-0) 

This helper is deliberately used in security-sensitive spots that consume repository-relative paths originating from working-directory content, e.g. when building Copilot conflict context (`resolveWithin(workingDirectory, file.path)`): [2](#0-1) 

and when opening a file from an `x-github-client` deep link: [3](#0-2) 

However, `GitStore.discardChanges` — the routine invoked when a user discards changes to a working-directory file — resolves the on-disk path with plain `Path.resolve`/`Path.join` instead: [4](#0-3) 

`file.path` for entries in `WorkingDirectoryFileChange` is derived from `git status` output against a working tree that is fully attacker-controlled content (a cloned/fetched repository). Git's project tree can legitimately contain a symlinked directory as a tracked/untracked entry (a "symlink" blob) whose target points outside the repository (e.g. `../../../../Library/LaunchAgents` or similar). When such a symlink is checked out and the attacker also places an "untracked"/"modified" file underneath that symlinked path, `git status` will report a path like `evil-link/payload` that appears to be repository-relative but, once resolved with plain `Path.resolve`, actually points to a path underneath an attacker-chosen directory outside the repo.

Because `discardChanges` does not call `resolveWithin` (which would call `realpath` and reject anything whose *real* location escapes the repo root — exactly the scenario the project's own `path-test.ts` unit tests exercise for symlinks), the guard is silently absent on this code path: [5](#0-4) 

### Impact Explanation
`this.shell.moveItemToTrash(...)` and, in the permanent-discard fallback, `rm(Path.join(this.repository.path, file.path))` are both invoked with the unvalidated resolved path: [6](#0-5) 

If the resolved path escapes the repository root through a symlink planted by the attacker's repository content, "Discard changes" (a routine, low-friction user action offered directly from the Changes list for any file Desktop reports as modified/untracked) can move-to-trash or permanently delete a file *outside* the repository the user did not intend to touch. This satisfies the "file write/delete outside the repo" impact class from a repository whose content the attacker fully controls (a cloned or fetched repo) with no privileged access or pre-existing malware required.

### Likelihood Explanation
The user only needs to clone/open an attacker-supplied repository and click "Discard changes" on a file that Desktop shows as changed — an ordinary, expected workflow action, not an unnatural or contrived step. The attack requires the attacker to craft a tracked symlink entry that Git will materialize on checkout (supported on macOS/Linux; Windows Git has more restrictive symlink handling by default, so the practical impact is strongest on POSIX platforms, mirroring exactly the platforms covered by the existing symlink test in `path-test.ts`). No admin rights, local access, or existing malware are needed — only that Desktop's own file-status view reports a path underneath the malicious symlink as changed, which requires no unusual manual interaction beyond opening the repo.

### Recommendation
Route `discardChanges`'s path resolution through the existing `resolveWithin` helper (as already done in `copilot-conflict-context.ts` and `dispatcher.ts`) before passing the result to `shell.moveItemToTrash` or `rm`, and skip/reject any file whose resolved real path is `null` (i.e., escapes the repository root):
```ts
const resolved = await resolveWithin(this.repository.path, file.path)
if (resolved === null) {
  // log and skip — do not touch the filesystem outside the repo
  continue
}
await this.shell.moveItemToTrash(resolved)
```
Apply the same fix to the `rm(...)` fallback path.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink entry `evil-link -> ../../../../some/sensitive/dir` and an untracked file `evil-link/decoy.txt` (or a tracked file within it, modified relative to `HEAD`).
2. Victim clones the repository with GitHub Desktop; the symlink is checked out (POSIX).
3. Desktop's Changes list reports `evil-link/decoy.txt` as an untracked/modified file (from `git status`).
4. Victim selects "Discard changes" on that entry (a completely ordinary action).
5. `discardChanges` computes `Path.resolve(repository.path, 'evil-link/decoy.txt')`, which — because the OS resolves the symlink on file-system access even though Node's `Path.resolve` performs no such resolution — actually causes `shell.moveItemToTrash`/`rm` to operate on a file underneath `/some/sensitive/dir`, outside the cloned repository, deleting or trashing content the user never selected nor intended to touch.

Note: I was not able to directly execute or trace the runtime symlink-checkout behavior in this indexed snapshot (limited to static source review), so the exact reachability of a tracked-symlink checkout under Desktop's git configuration (e.g., `core.symlinks` defaults) could not be independently confirmed here and would benefit from a live Devin session to validate end-to-end.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
