### Title
Malformed/decoy conflict-marker text in a tracked file causes Copilot conflict resolution to misidentify hunk boundaries and silently overwrite unrelated content - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`extractConflictHunks()` and `reassembleResolvedFile()` both locate conflict-hunk boundaries purely by regex-scanning a file's raw text for lines that look like `<<<<<<<`, `=======`, `>>>>>>>` (7+ characters at column 0), with no cross-check against git's actual conflict metadata (`git status`/index stage info). An attacker who controls file content merged into the repository (e.g. documentation, a code comment, or a lock file containing an incomplete/decoy marker-like line) can desynchronize this boundary detection from the real conflict produced later by an unrelated merge/rebase/cherry-pick in the same file. Both the prompt-building step and the reassembly step derive the *same* (wrong) span, so the internal hunk-count validation in `validateResolutionPaths()` never catches the corruption — the AI-resolved content silently overwrites a region that includes the user's genuine, un-conflicted edits.

### Finding Description
`extractConflictHunks()` [1](#0-0)  opens a hunk on any line matching `oursMarker` (`/^<{7}(?:\s|$)/`) and then greedily consumes subsequent lines as "ours" content until it sees a `baseMarker` or `separatorMarker` — it never checks whether an *inner* line is itself another `oursMarker`. If it doesn't find a real closing `theirsMarker` before EOF it silently drops that one hunk [2](#0-1) , but if a *later*, genuine conflict's `=======`/`>>>>>>>` markers exist further down in the file, the scanner will latch onto those as the closing markers for the bogus opening line, swallowing the real conflict's own `<<<<<<<`, ours-content, and separator as plain "ours" text of the fake hunk, and the real "theirs" content as the fake hunk's "theirs" text.

`reassembleResolvedFile()` performs the identical column-0 marker scan when splicing the model's output back into the file [3](#0-2) , so it computes the exact same (corrupted) span and replaces everything between the decoy opener and the real closing marker — including the user's real conflicting edits — with a single model-generated blob.

Because both stages agree on the same wrong boundaries, `validateResolutionPaths()` — which only checks that hunk counts per path match between the request and response [4](#0-3)  — has nothing to flag: 1 malformed "hunk" was sent, 1 "hunk" resolution came back, counts match.

This is the same broken-invariant pattern as the Gondi `mergeTranches`/`_loanTermination` bug: an attacker-influenced value (here, decoy marker text embedded in tracked file content) shifts an identifier/boundary (hunk span) that a downstream accounting/reconciliation step (`reassembleResolvedFile`) blindly trusts, with no independent source of truth (e.g. git's own conflict-region metadata) to catch the mismatch.

### Impact Explanation
The reassembled file is written directly to disk and is what the user subsequently stages and commits/pushes via the normal commit flow. If the decoy marker line sits inside a region the model is instructed to "resolve," genuine local (`ours`) changes located between the decoy and the real conflict can be silently dropped or replaced by AI-generated content that the developer never reviewed as a diff against their actual pending changes — a silent corruption of what the user commits, matching the explicitly valid impact category ("silent corruption of what the user commits or pushes").

### Likelihood Explanation
Requires only that: (1) a tracked file in the repository (introduced via a normal commit/PR from any contributor, or a file the attacker gets merged) contains a line starting with 7+ `<` characters not closed by a well-formed marker triple within that block, and (2) a real, unrelated conflict later occurs in the same file during a merge/rebase/cherry-pick where the user opts into the (AI) Copilot conflict-resolution flow. Marker-like lines of this shape are plausible in documentation about git, ASCII banners, changelogs, or generated diff/patch snippets stored verbatim in a repo, making this reachable without unnatural user steps once such a file exists upstream.

### Recommendation
Do not rely solely on freeform regex scanning of raw file text to define hunk boundaries for both context-building and reassembly. Instead, derive hunk boundaries from git's own conflict markers only within properly nested regions (reject/skip an outer marker if an inner, unclosed opening marker is encountered rather than allowing it to consume a later, unrelated closing marker), and add a stronger boundary invariant to `validateResolutionPaths()` (e.g. verify the reconstructed span text matches the original expected hunk delimiters/positions, not just a count) before applying `reassembleResolvedFile()`.

### Proof of Concept
1. Attacker contributes/merges a file, e.g. `docs/git-tips.md`, containing:
```
Example of a conflict marker:
<<<<<<< incomplete-example
some text describing conflicts
```
(no matching `=======`/`>>>>>>>` immediately following — a decoy opener).

2. Later, the victim performs a normal merge/rebase where `docs/git-tips.md` also gets a real, unrelated conflict further down in the same file:
```
<<<<<<< HEAD
victim's real local change
=======
incoming change
>>>>>>> feature
```
3. `extractConflictHunks()` [5](#0-4)  starts at the decoy `<<<<<<< incomplete-example`, consumes everything (including the real `<<<<<<< HEAD` line and victim's real change) as "ours" text until it hits the real `=======`, then consumes the real "incoming change" as "theirs" text and treats the real `>>>>>>> feature` as its closing marker — producing exactly one malformed/misattributed hunk instead of the real one.
4. The Copilot session resolves this single garbled hunk; `reassembleResolvedFile()` [6](#0-5)  splices the model's one resolution over the entire span from the decoy opener through the real closing marker, discarding the victim's real local change along with the decoy text, with `validateResolutionPaths()` seeing matching hunk counts (1 == 1) and raising no error.

Note: I was not able to execute this against a live build (no filesystem/runtime access in this mode), so this PoC is derived from static reading of `extractConflictHunks`, `reassembleResolvedFile`, and `validateResolutionPaths`; a Devin session with repo/runtime access would be needed to confirm behavior end-to-end against the actual Copilot SDK integration.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }
