## Title
Same-chain partial-fill escrow release ignores per-leg allocation when multiple order inputs share a token, allowing over-release and permanent bricking of remaining legs — (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

## Summary
`IntrinsicIntents._fillSameChain` releases escrow from a single, token-keyed bucket (`_orders[commitment][token]`) that is shared across all order legs backed by the same input token. When one output leg becomes fully filled, the code releases the *entire current balance* of that shared bucket instead of the amount proportionally attributable to that leg — the same "aggregate counter used as a per-item invariant" mistake as H-4's `enabledModuleCount`/pagination mismatch, just applied to escrow accounting instead of a module-count guard.

## Finding Description
`_orders` is declared as:
```solidity
mapping(bytes32 => mapping(address => uint256)) public _orders;
``` [1](#0-0) 

Note the key space is `(commitment, token)` only — there is no per-leg/per-index dimension. If an `Order` has two (or more) input entries at different indices that reference the *same* token address (e.g. escrowing 300 USDC to back output leg A and 300 USDC to back output leg B in the same order), both deposits are summed into one bucket, `_orders[commitment][USDC] = 600`, at placement time.

In `_fillSameChain`, when a leg `i` reaches full completion for that leg (`amountFilled == totalRequired`), the escrow released to the solver is computed as:
```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [2](#0-1) 

This reads the **whole remaining balance** of the shared bucket, not the specific allotment for leg `i`. That value then flows into `_withdraw`, which decrements the same shared key and transfers the released amount to the solver who completed only *one* leg:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
``` [3](#0-2) 

Consequences, exactly mirroring the H-4 pattern (an aggregate value substituting for a per-entity invariant, causing divergence between "what should exist" and "what the guard sees"):
- **Over-release / wrong amount to wrong beneficiary**: The solver who fills leg A first receives escrow that was meant to back leg B's output, effectively taking funds earmarked for a different, still-unfulfilled leg.
- **Permanent bricking of the remaining legs**: Once the shared bucket hits zero, any later attempt to fill leg B calls `_withdraw`, which reads `escrowed = _orders[commitment][token] == 0` and reverts with `UnknownOrder()` — line 401 above — for the rest of the order's lifetime. The user who placed the order can also not get a clean refund via `_cancelSameChain`, because that path likewise reads the same shared, already-drained `_orders[commitment][token]` value.
- No malicious relayer, prover, admin, or governance actor is required — this is triggered purely by a normal, permissionless `fillOrder()` call from any solver, which is the intended public entry point documented for same-chain partial fills.

## Impact Explanation
This directly matches the bounty's in-scope impacts: unauthorized extraction of escrowed funds (a solver receives more than their leg entitles them to) and loss/permanent lock of the remainder (the other leg's backing tokens become unwithdrawable — neither fillable by a solver nor refundable to the user). This is a fund-safety defect in the core escrow accounting of `IntentGatewayV2`/`IntrinsicIntents`, not a peer/relayer/prover trust issue.

## Likelihood Explanation
Requires only that a user (or an order builder acting on the user's behalf, e.g. an aggregator building multi-leg orders) construct an `Order` with two or more `inputs[]` entries sharing the same token address, each backing a different `outputs[]` leg — a plausible configuration for "swap token X into two different outputs" style same-chain intents, which the contract's data model (`TokenInfo[] inputs`, `TokenInfo[] outputs`, matched by index) does not forbid. No special privileges are needed to trigger the drain via `fillOrder`.

Note on verification limits: I was not able to inspect `OrderPlacer`/`placeOrder`'s escrow-crediting code in the time available to confirm whether duplicate input token addresses across indices are explicitly rejected at placement. However, the storage layout of `_orders` (keyed only by `(commitment, token)`, with no index component) structurally guarantees that if such an order can be placed, the escrow deposits are aggregated — the fill-side bug described above follows directly from that schema regardless of how placement populates it. This should be confirmed against `OrderPlacer`'s validation logic during triage.

## Recommendation
Track escrow per `(commitment, outputAssetIndex)` (or per `(commitment, inputIndex)`) rather than per `(commitment, token)` alone, or explicitly reject orders whose `inputs[]` contain duplicate token addresses across different indices at `placeOrder()` time. Alternatively, change the full-fill release computation to release only the leg's proportional allocation (`order.inputs[i].amount`, adjusted for any prior partial releases against that specific leg) rather than reading the shared bucket's current total balance.

## Proof of Concept
1. User places a same-chain `Order` with `inputs = [ {token: USDC, amount: 300}, {token: USDC, amount: 300} ]` and `outputs = [ {token: DAI, amount: 100}, {token: WETH, amount: 1} ]` (two legs, same input token backing both). Placement credits `_orders[commitment][USDC] = 600` (aggregated, per the mapping's key space) — see [1](#0-0) .
2. Solver A calls `fillOrder` supplying only enough DAI to fully satisfy leg 0 (`totalRequired` for `outputs[0]`), leaving leg 1 (WETH) unfilled (`solverAmount = 0` for leg 1, so `remaining > 0` ⇒ `isFullyFilled = false`).
3. In the loop, for leg 0, `amountFilled == totalRequired` becomes true, so:
   `escrowedAmount = _orders[commitment][USDC]` = 600 (the full pool), not the 300 attributable to leg 0 — [2](#0-1) .
4. `_withdraw` is called with this 600-unit token entry; it decrements the shared bucket to 0 and transfers all 600 USDC to Solver A — [4](#0-3) .
5. Because `isFullyFilled` is false (leg 1 untouched), `_filled[commitment]` is deleted so the order remains fillable — [5](#0-4) .
6. Solver B later attempts to fill leg 1 (WETH). The corresponding escrow release computation again reads `_orders[commitment][USDC]`, which is now 0. `_withdraw` hits `if (escrowed == 0) revert UnknownOrder();` — [6](#0-5)  — permanently reverting any further fill or cancellation of leg 1's backing funds. Solver A has captured 600 USDC for delivering only leg 0's DAI, and the user's second leg's backing escrow is unrecoverable.
