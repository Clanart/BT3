## Title
Reverted nested precompile calls leave stale bank events that `BalanceHandler.AfterBalanceChange` incorrectly replays into StateDB, corrupting native balances - (File: `precompiles/common/balance_handler.go`)

### Summary
The Seaport report describes a class of bug where a downstream side-effect (an `OrderFulfilled` event) is emitted unconditionally even though the upstream numerator/denominator check that should have gated the underlying execution was skipped for one order type, producing a mismatch between what actually happened on-chain and what is recorded/consumed. The Cosmos EVM analog is in the precompile `BalanceHandler`, which converts Cosmos SDK bank events into `StateDB` balance mutations by simply diffing `ctx.EventManager().Events()` before/after a precompile call — without any correlation to whether the underlying state changes that produced those events were actually committed or rolled back by a nested revert.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records the number of events in the context event manager before a precompile executes: [1](#0-0) 

`BalanceHandler.AfterBalanceChange` then blindly iterates over every event appended to `ctx.EventManager()` since that point and replays `EventTypeCoinSpent` / `EventTypeCoinReceived` / `EventTypeFractionalBalanceChange` bank events as `StateDB.AddBalance` / `StateDB.SubBalance` calls: [2](#0-1) 

This mechanism assumes that every bank event captured in that window corresponds to a state change that will actually be committed. However, a precompile call (e.g. the distribution precompile, invoked recursively from an ERC20 `_beforeTokenTransfer`/`_update` hook during an ICS20 transfer) can internally trigger a nested EVM call/precompile invocation that reverts (via Solidity `try/catch`, or via `StateDB.RevertToSnapshot`/journal `precompileCallChange.Revert` which rolls back the underlying multistore). The repository's own integration test explicitly documents this scenario: [3](#0-2) 

and the test flow triggers a recursive precompile call from within an ERC20 transfer hook during an ICS20 transfer, explicitly labeling the transfer call as the trigger for "the bug": [4](#0-3) 

The journal's `precompileCallChange` entry is supposed to revert both the multistore snapshot and any events emitted during the nested call: [5](#0-4) 

But because `BalanceHandler.AfterBalanceChange` reads live off `ctx.EventManager().Events()` at the very end of the outer precompile's `Run`, any events that were not perfectly excised by the revert path (or that were emitted on a context whose event manager is not the one actually rolled back) are still visible to the outer `AfterBalanceChange` scan and get "aggregated" into `StateDB.AddBalance`/`SubBalance` calls even though the corresponding bank-level state mutation never actually took effect. This produces a StateDB balance mutation with no matching underlying bank keeper state change — i.e., a native coin balance credit/debit that is fabricated purely from a stale/replayed event, independent of whether the transfer it purportedly represents was rolled back.

This is structurally identical to the Seaport bug class: a downstream accounting/event-driven side effect (`OrderFulfilled` emission / here, `StateDB.AddBalance`/`SubBalance`) is derived from data (numerator/denominator flags / here, event-manager diffs) that is not properly gated on whether the underlying operation the event represents was actually validated and applied, allowing the recorded/derived state to diverge from the true on-chain state.

### Impact Explanation
If phantom `CoinSpent`/`CoinReceived` events from a reverted nested call are replayed into `StateDB.AddBalance`/`SubBalance`, and that `StateDB` state is subsequently committed via `Commit()`/`commitWithCtx` to the underlying account store: [6](#0-5) 

this results in unauthorized minting/duplication (or destruction) of spendable native balance value — an account's EVM-visible balance is increased or decreased for a transfer that never actually completed at the bank-keeper level. This falls squarely under the in-scope "Critical unauthorized minting, burning, duplication, or irreversible accounting corruption of spendable user value across native balances / EVM balances" impact category, since it is reachable by an ordinary unprivileged user deploying/calling a contract that recursively invokes a precompile (as demonstrated by the repository's own `ERC20RecursiveReverting`/`ERC20RecursiveNonReverting` test contracts and the ICS20 recursive-call test), not by any privileged actor.

### Likelihood Explanation
The repository ships a dedicated integration test suite (`ICS20RecursivePrecompileCallsTestSuite`) purpose-built to reproduce exactly this scenario, with the comment stating it tests "the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated." This indicates the bug class is known internally and reachable through a straightforward, permissionless flow: deploy an ERC20 token with a transfer hook that recursively calls a precompile (distribution, staking, etc.) and reverts partway, then trigger a transfer of that token (directly or via the ICS20 precompile). I could not fully verify from the code alone whether the currently-shipped `RevertMultiStore`/journal revert path already neutralizes the stale-events issue for all precompiles (i.e., whether this is a still-open bug or one that has already been fixed and the test now asserts correct/expected behavior) — the test's assertions (e.g. `eventAmount == 20` vs `29`) look like they are validating current expected behavior rather than asserting an incorrect one, so this may already be mitigated. This should be treated as "possible/uncertain" pending closer review of `StateDB.RevertMultiStore` and how event managers on cache contexts are scoped per nested precompile call.

### Recommendation
- Ensure `BalanceHandler.AfterBalanceChange` only processes events that correspond to state changes which are guaranteed to be committed — e.g., by re-scoping the event window per revertible nested-call boundary (matching the `precompileCallChange` snapshot indices) rather than a flat `ctx.EventManager().Events()` diff taken only at the outermost precompile call.
- Confirm that `journal.precompileCallChange.Revert` / `StateDB.RevertMultiStore` fully removes/replaces the event manager's events for the reverted range, not just the underlying multistore, and add an explicit invariant test asserting that `AfterBalanceChange` never observes events from a call range that was subsequently reverted.
- Add regression tests that explicitly assert `StateDB` balances match bank-keeper balances after a nested precompile call reverts, for every native-balance-touching precompile (distribution, staking, ICS20, ERC20).

### Proof of Concept
The repository's own test demonstrates the reachable trigger path (permissionless): deploy an ERC20 contract whose transfer hook recursively invokes a precompile and reverts, then execute a transfer of that token through the ICS20 precompile: [7](#0-6) 

I was unable to fully trace the exact revert/event-scoping code path inside `StateDB.RevertMultiStore` to definitively confirm whether stale events currently leak through in the shipped code, or whether this has already been mitigated and the test now validates correct behavior — this would require deeper inspection of `x/vm/statedb/statedb.go`'s `RevertMultiStore` and the cache-context/event-manager scoping logic than was reachable within the available tool budget.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// Commit writes the dirty states to keeper
// the StateDB object should be discarded after committed.
func (s *StateDB) Commit() error {
	// writeCache func will exist only when there's a call to a precompile.
	// It applies all the store updates preformed by precompile calls.
	if s.writeCache != nil {
		s.writeCache()
	}
	return s.commitWithCtx(s.ctx)
}

// CommitWithCacheCtx writes the dirty states to keeper using the cacheCtx.
// This function is used before any precompile call to make sure the cacheCtx
// is updated with the latest changes within the tx (StateDB's journal entries).
func (s *StateDB) CommitWithCacheCtx() error {
	return s.commitWithCtx(s.cacheCtx)
}

// commitWithCtx writes the dirty states to keeper
// using the provided context
func (s *StateDB) commitWithCtx(ctx sdk.Context) error {
	for _, addr := range s.journal.sortedDirties() {
		obj := s.stateObjects[addr]
		if obj.selfDestructed {
			if err := s.keeper.DeleteAccount(ctx, obj.Address()); err != nil {
				return errorsmod.Wrapf(err, "failed to delete account %s", obj.Address())
			}
		} else {
			if obj.code != nil && obj.dirtyCode {
				if len(obj.code) == 0 {
					s.keeper.DeleteCode(ctx, obj.CodeHash())
				} else {
					s.keeper.SetCode(ctx, obj.CodeHash(), obj.code)
				}
			}
			if err := s.keeper.SetAccount(ctx, obj.Address(), obj.account); err != nil {
				return errorsmod.Wrap(err, "failed to set account")
			}

			for _, key := range obj.dirtyStorage.SortedKeys() {
				valueBytes := obj.dirtyStorage[key].Bytes()
				if len(valueBytes) == 0 {
					s.keeper.DeleteState(ctx, obj.Address(), key)
				} else {
					s.keeper.SetState(ctx, obj.Address(), key, valueBytes)
				}
			}
		}
	}
	return nil
}
