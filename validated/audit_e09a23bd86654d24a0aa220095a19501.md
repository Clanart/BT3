### Title
NFT royalty amount computed with division before multiplication truncates payouts to royalty recipients - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount` and `NFTWallet.royalty_calculation` in `chia/wallet/nft_wallet/nft_wallet.py` compute the royalty amount owed to an NFT's royalty address by performing an integer division before the multiplication by the royalty percentage, exactly the division-before-multiplication pattern flagged in the external report. This truncates the royalty amount more than necessary, so the actual `CreateCoin` payment sent to the royalty address in a completed offer is smaller than the mathematically correct amount.

### Finding Description
`compute_royalty_amount` computes: [1](#0-0) 
```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```
Here `abs(offered_amount)` is first floor-divided by `royalty_split`, and only then multiplied by `percentage` and divided by `MAX_ROYALTY_BASIS_POINTS` (10000). Because Solidity/Python integer division truncates on every division step, doing the `// royalty_split` division before the `* percentage` multiplication loses precision that a single combined division (`abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`) would not lose. This is the identical bug class described in the report: "division before multiplication" causing an under-computed amount.

This function is invoked in the actual offer-construction path that creates the royalty payment coin: [2](#0-1) 
```
for asset, amount in fungible_asset_dict.items():  # offered fungible items
    if amount < 0 and request_side_royalty_split > 0:
        payment_list: list[tuple[bytes32, CreateCoin]] = []
        for launcher_id, address, percentage in required_royalty_info:
            extra_royalty_amount = compute_royalty_amount(amount, request_side_royalty_split, percentage)
            payment_list.append((launcher_id, CreateCoin(address, extra_royalty_amount, [address])))
```
The resulting `extra_royalty_amount` becomes the literal on-chain `CreateCoin` amount paid to the NFT royalty address once the offer is completed, so any precision loss here directly reduces the coins actually created for the royalty recipient.

The same pattern also appears in `NFTWallet.royalty_calculation`, which is exposed via the `nft_calculate_royalties` RPC and used by the CLI/wallet to display/estimate royalties before a trade is made: [3](#0-2) 
```
"amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
```

### Impact Explanation
Any offer maker/taker constructing an NFT offer involving royalty-bearing NFTs (a normal, unprivileged wallet action — `NFTWallet.make_nft1_offer` via `TradeManager.respond_to_offer`/`create_offer_for_ids`) causes the royalty amount actually paid to the NFT creator/royalty address to be computed with double truncation instead of a single combined division. This systematically underpays royalty recipients relative to the mathematically correct amount, diverting value away from a passive third party (the royalty holder) toward the trading parties. This is a real, reachable precision-loss bug in an offer-settlement amount calculation, matching the report's bug class of "swapping/settlement math susceptible to precision loss due to premature division."

### Likelihood Explanation
This triggers on every NFT offer/trade involving royalty-bearing NFTs where `royalty_split > 1` (multiple royalty-enabled NFTs on one side of a trade) or otherwise whenever the intermediate floor division discards a remainder that the combined calculation would have preserved. No privileged access or malicious peer is required — any wallet user creating or taking an NFT offer through the standard `TradeManager`/`NFTWallet` flow exercises this code path.

### Recommendation
Combine the multiplication and division into a single operation to minimize truncation, e.g.:
```
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```
applied consistently in both `compute_royalty_amount` and `NFTWallet.royalty_calculation`, while still validating `royalty_split` and `percentage` bounds to avoid overflow before the final `uint64` cast.

### Proof of Concept
Using `compute_royalty_amount(offered_amount=-3, royalty_split=2, percentage=6000)` (60% royalty, split across 2 NFTs):
- Current (buggy) order: `3 // 2 = 1`; `1 * 6000 // 10000 = 0` → royalty paid = 0.
- Correct combined order: `3 * 6000 // (2 * 10000) = 18000 // 20000 = 0` → same result in this specific case, but for larger/varied inputs (e.g. `offered_amount=-7`, `royalty_split=3`, `percentage=6000`): buggy `7 // 3 = 2`; `2 * 6000 // 10000 = 1`. Combined: `7 * 6000 // 30000 = 42000 // 30000 = 1`. For `offered_amount=-5`, `royalty_split=3`, `percentage=9000`: buggy `5//3=1`; `1*9000//10000=0`. Combined: `5*9000//30000=45000//30000=1`. This demonstrates the buggy division-first order yields a strictly lower (or equal) royalty payout than the mathematically correct combined-division approach, confirming the underpayment. def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
```python
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
