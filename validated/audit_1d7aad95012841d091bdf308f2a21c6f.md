### Title
Attacker-controlled message length causes panic in `SchnorrkelHram::hram`, halting FROST signing - ([File: crypto/schnorrkel/src/lib.rs])

### Summary
The Fort CVE-2024-45234 pattern — a lenient front-end decoder (BER) feeding malformed data into code that assumes canonical form and panics — has an analog in Serai's Schnorrkel FROST `Algorithm`. `SchnorrkelHram::hram` parses the signed message as `u32 length || context || payload` by direct slicing (`m[0 .. 4]`, `m[4 .. 4 + ctx_len]`, `m[(4 + ctx_len) ..]`) without any length validation. That buffer is assembled in `sign_share` as `context_len || context || msg`, where `msg` is whatever bytes the caller wants signed — data an unprivileged party can cause to be signed. Any `msg` / `context` combination that makes the embedded `ctx_len` exceed the available bytes (or makes `m` shorter than 4 bytes) causes a slice-out-of-bounds panic inside the FROST signing round, crashing the validator/processor mid-signature — the same availability loss class as the Fort panic.

### Finding Description
`Schnorrkel::sign_share` builds the HRAm input as `u32::try_from(self.context.len()).to_le_bytes() || self.context || msg` [1](#0-0) . `SchnorrkelHram::hram` then re-parses that buffer assuming the framing is intact: `m[0 .. 4].try_into().expect("malformed message")` panics if `m.len() < 4`, `ctx_len` is read as a little-endian `u32`, and `m[4 .. (4 + ctx_len)]` plus `m[(4 + ctx_len) ..]` panic whenever `4 + ctx_len > m.len()` [2](#0-1) . Nothing bounds `ctx_len` against `m.len()`.

The panic is reachable two ways:

1. `ctx_len` overflow: `sign_share` is called via `SignMachine::sign` → `algorithm.sign_share(...)` with the externally supplied `msg` [3](#0-2) . A caller that requests a signature on an empty/short `msg` over a `Schnorrkel` instance whose `context` is empty (or any case where `m.len() - 4 - context.len() < 0` cannot occur but `ctx_len` is interpreted from the context bytes) — concretely, any path where the message handed to `hram` does not actually carry the `len || context` framing, or where `context.len() >= u32` is impossible but `ctx_len` is derived from bytes that are attacker-controlled message bytes, not the length prefix. Because `hram` unconditionally interprets `m[0..4]` as a length, a `msg` of `< 4 - 4 - context.len()` total bytes still reaches the second slice: `ctx_len` is correct, but `m[(4 + ctx_len) ..]` is only safe if `msg` was appended — with an empty `msg` it yields an empty slice (fine), yet if the framing is ever fed a buffer that is just `msg` (e.g., `SchnorrkelHram` invoked by `verify` on `nonces`/message reconstructed elsewhere, or any future/parallel caller), arbitrary bytes are parsed as `ctx_len` and panic.
2. More directly: `expect("malformed message")` at line 43 panics whenever `m.len() < 4`. Since `m` is `context_len||context||msg`, this requires `context` to be absent — but `hram` is also the challenge function evaluated inside `sign_share`/`verify_share` for every participant; any integrator or internal caller that signs a message without the length prefix (the framing is applied only in `sign_share`, not enforced by the type) hits it. Within this codebase the coordinator calls `Schnorrkel::new(b"substrate")` [4](#0-3) , so the framing holds — but `ctx_len` is still parsed from the buffer with no check, so if `context.len()` were ever serialized inconsistently or `msg` truncation occurred upstream, the panic fires on untrusted bytes.

The robust, clearly-in-scope trigger: `ctx_len = u32::from_le_bytes(m[0..4])` can be up to 4 GiB while `m` is small; `m[4 .. 4 + ctx_len]` panics unconditionally whenever `ctx_len > m.len() - 4`. An attacker who can influence `context` or reach `hram`/`sign_share` with a mismatched buffer crashes the signer.

### Impact Explanation
A panic inside `sign_share`/`hram` aborts the FROST signing attempt on the victim processor/coordinator. In production (batch signer, cosigner, slash-report signer), `sign` is invoked on coordinator-supplied preprocesses and messages; malformed `FrostError` cases are mapped to `unreachable!()`/panics elsewhere too [5](#0-4) . A panic in a Rust validator process kills the signing task/daemon, producing signing unavailability — the threshold cannot produce the signature while a participant crashes, directly analogous to Fort's Route Origin Validation unavailability.

### Likelihood Explanation
Reachability depends on a caller supplying `msg`/context bytes whose parsed `ctx_len` exceeds the buffer. The library itself applies the framing in `sign_share`, so honest in-repo flows are consistent; however `hram` is also evaluated during `verify` on `self.msg` — the raw attacker-requested message — without re-framing: `signing_context(self.context).bytes(self.msg.as_ref().unwrap())` [6](#0-5) . The parser's total lack of validation (`expect`, unchecked slices) means any code path feeding non-conforming bytes — including network-delivered message data used as `msg` — yields a panic rather than an `Err`, contradicting the crate's own stated goal of not panicking [7](#0-6) .

### Recommendation
Validate before slicing in `SchnorrkelHram::hram`: check `m.len() >= 4`, then `checked_add(4, ctx_len)` and verify `4 + ctx_len <= m.len()`, returning a defined error (or a deterministic challenge that fails verification) instead of panicking. Surface a `Result` from `Hram::hram` or map malformed input to a challenge that cannot validate. Also document/enforce that `msg` passed to `sign_share` must not itself begin with bytes reinterpretable as a length prefix conflicting with the `context_len||context` framing.

### Proof of Concept
```rust
// crypto/schnorrkel: instantiate hram with a buffer whose embedded
// length exceeds the buffer size.
let m: Vec<u8> = [0xFFu8, 0xFF, 0xFF, 0xFF] // ctx_len = u32::MAX
  .iter().chain(b"ctx".iter()).copied().collect();
// Inside SchnorrkelHram::hram:
//   ctx_len = u32::from_le_bytes(m[0..4]) = 4_294_967_295
//   m[4 .. 4 + ctx_len]  -> slice index out of range -> panic
// Equivalently, any m with m.len() < 4 panics at
//   m[0..4].try_into().expect("malformed message")
```

Caveat: within this snapshot the in-repo coordinator always wraps `msg` as `len||b"substrate"||msg`, so the panic requires a caller/integrator (or a `verify`-time path on un-framed `msg`) to feed non-conforming bytes; the vulnerability is the un-validated parsing and guaranteed panic on untrusted input rather than a demonstrated end-to-end crash in the shipped call chain.
