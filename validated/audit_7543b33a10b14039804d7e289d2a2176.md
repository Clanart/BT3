Investigation into the publish/upgrade/ownership flow surfaces a concrete, locally-provable bug in the object-ownership primitive that `code::publish_package` and the lazy-module-init gate both depend on.

### Title
Unbounded `object::root_owner` traversal lets a self-owning object permanently brick its code object's publish/upgrade path — ("Publish Bomb" via cyclic ownership) - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::root_owner` walks the ownership chain of an object with no cycle or depth bound, unlike the two other ownership-chain walkers in the same module (`owns` and `verify_ungated_and_descendant`), which both enforce `MAXIMUM_OBJECT_NESTING`. `root_owner` is called directly from the code-publishing hot path — `code::publish_package` (to record the "deploy owner" for lazy module init) and `init::assert_may_self_initialize` (the self-init authorization gate) — both of which are protected state-mutation entry points for publish/upgrade. Because `object::transfer` permits an object to be made to own itself (demonstrated by the framework's own `test_cyclic_ownership_transfer_should_fail` test), any object owner can create a self-referential object and thereby make every future `root_owner()` call on that address loop forever, exhausting gas and aborting the transaction.

### Finding Description
`object::root_owner` (lines 742-748 of `object.move`) is:
```
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
``` [1](#0-0) 

Contrast this with `owns` and `verify_ungated_and_descendant`, which explicitly bound their traversal by `MAXIMUM_OBJECT_NESTING` to defend against cyclic ownership graphs: [2](#0-1) [3](#0-2) 

`transfer_raw_inner`/`verify_ungated_and_descendant` allow an object to be transferred to itself when it is the *current owner* of the destination check target (i.e. `object.owner == destination` trivially satisfies the loop with zero iterations), producing a self-owning object. The framework's own test confirms this is achievable on-chain in one step: [4](#0-3) 

Once an object is self-owning, `root_owner()` on that address never terminates because `is_object(obj_owner)` stays true and `obj_owner` never changes.

`root_owner()` is used at two points that sit directly in the protected publish/upgrade write path:
1. `code::publish_package` records the deploy owner on every (re)publish to an object address when lazy module init is enabled: [5](#0-4) 
2. `init::assert_may_self_initialize`, invoked from `init::internal_maybe_initialize`, the native-backed gate every lazily-initializing module calls, also computes `root_owner()`: [6](#0-5) 

Both `object_code_deployment::publish` (initial deploy) and `object_code_deployment::upgrade` route through `code::publish_package_txn` → `code::publish_package`: [7](#0-6) 

So: an object owner deploys a code object, transfers it to itself (`object::transfer(owner, code_object, code_object_address)`), and from that point on:
- Any `code::publish_package` call (upgrade) targeting that object address that has lazy-module-init enabled will loop forever in `root_owner()` and abort on out-of-gas, permanently preventing any future upgrade of that package.
- Any lazily-initializing module hosted at that address will similarly loop forever on `assert_may_self_initialize`, bricking ordinary invocation as well.

This is functionally an unauthorized/uncontrolled **freeze**: it achieves the same practical effect as `code::freeze_code_object` (permanently blocking upgrades) but bypasses that function's explicit owner-authorization and dependency checks entirely, and can be triggered accidentally or maliciously by anyone who controls a transfer into the object (including a griefing transfer to an unsuspecting recipient who then discovers their "upgradeable" package is permanently stuck).

### Impact Explanation
This breaks the code-safety invariant that `code::freeze_code_object` is the sole, gated mechanism for making a package immutable — instead, any address with ungated-transfer control over an object-hosted code package can force a permanent denial-of-upgrade (and denial-of-lazy-init) state without going through that gate. Because Aptos's own audit checklist for `code.move` explicitly lists "the arbitrary upgrade policy should never be used" and "should only be updated by the owner" as Critical invariants, silently forcing a package into a permanently un-upgradable state through an unrelated, unguarded ownership primitive is a real breach of the intended upgrade/freeze authorization model — with high impact for any object code deployment relying on lazy module initialization (a mainnet-relevant, currently-in-repo feature).

### Likelihood Explanation
Triggering the bug requires only:
1. Deploying (or already owning) an object-hosted package (`object_code_deployment::publish`).
2. Calling `object::transfer` (or `transfer_raw`) to set the object's owner to itself — a single permissionless transaction requiring no special privilege beyond normal object ownership, and demonstrated feasible by the framework's own test suite.
3. The `LAZY_MODULE_INITIALIZATION` feature being enabled (it's a live, non-experimental feature flag referenced throughout `code.move`/`init.move`).

No governance or privileged role is required; this is entirely self-inflictable or griefable by transferring a poisoned object to a victim.

### Recommendation
Bound `object::root_owner`'s traversal by `MAXIMUM_OBJECT_NESTING`, consistent with `owns` and `verify_ungated_and_descendant`, and decide/define an explicit, safe fallback behavior (e.g., abort with a clear "cyclic ownership" error, or return the last address reached before the bound) rather than looping unboundedly. Additionally, consider rejecting self-transfers (`to == object`) at the `transfer`/`transfer_raw` level, since a self-owning object is a degenerate state with no legitimate use case and currently only exists as an accepted-by-oversight edge case (caught later, inconsistently, only by callers that happen to bound their loops).

### Proof of Concept
```move
// 1. Deploy an object-hosted package with lazy module init enabled.
object_code_deployment::publish(&owner, metadata, code); // creates object at `object_address`

// 2. Owner (or whoever currently owns the object) makes it self-owning.
let code_object = object::address_to_object<PackageRegistry>(object_address);
object::transfer(&owner, code_object, object_address); // succeeds: owner == destination.owner trivially

// 3. Any subsequent upgrade now hangs / runs out of gas inside code::publish_package,
//    because `object::is_object(addr) => root_owner()` never terminates:
object_code_deployment::upgrade(&owner, new_metadata, new_code, code_object); // OOG / permanently stuck

// 4. Likewise, any module at `object_address` calling `init::internal_maybe_initialize`
//    (lazy self-init) will OOG in `assert_may_self_initialize`, bricking normal use too.
```
This reproduces using only the framework's own demonstrated self-transfer capability [4](#0-3)  combined with the unbounded `root_owner` walk [1](#0-0)  called from the publish path [8](#0-7) .

    public entry fun publish(
        publisher: &signer,
        metadata_serialized: vector<u8>,
        code: vector<vector<u8>>,
    ) {
        let publisher_address = signer::address_of(publisher);
        let object_seed = object_seed(publisher_address);
        let constructor_ref = &object::create_named_object(publisher, object_seed);
        let code_signer = &constructor_ref.generate_signer();
        code::publish_package_txn(code_signer, metadata_serialized, code);

        event::emit(Publish { object_address: signer::address_of(code_signer), });

        move_to(code_signer, ManagingRefs {
            extend_ref: constructor_ref.generate_extend_ref(),
        });
    }

    inline fun object_seed(publisher: address): vector<u8> {
        let sequence_number = account::get_sequence_number(publisher) + 1;
        let seeds = vector[];
        seeds.append(bcs::to_bytes(&OBJECT_CODE_DEPLOYMENT_DOMAIN_SEPARATOR));
        seeds.append(bcs::to_bytes(&sequence_number));
        seeds
    }

    /// Upgrades the existing modules at the `code_object` address with the new modules passed in `code`,
    /// along with the metadata `metadata_serialized`.
    /// Note: If the modules were deployed as immutable when calling `publish`, the upgrade will fail.
    /// Requires the publisher to be the owner of the `code_object`.
    ///
    /// Note: In order to publish a new package to an existing code object,
    /// this `upgrade` function should be called, rather than `publish`.
    public entry fun upgrade(
        publisher: &signer,
        metadata_serialized: vector<u8>,
        code: vector<vector<u8>>,
        code_object: Object<PackageRegistry>,
    ) {
        let publisher_address = signer::address_of(publisher);
        assert!(
            object::is_owner(code_object, publisher_address),
            error::permission_denied(ENOT_CODE_OBJECT_OWNER),
        );

        let code_object_address = code_object.object_address();
        assert!(exists<ManagingRefs>(code_object_address), error::not_found(ECODE_OBJECT_DOES_NOT_EXIST));

        let extend_ref = &borrow_global<ManagingRefs>(code_object_address).extend_ref;
        let code_signer = &extend_ref.generate_signer_for_extending();
        code::publish_package_txn(code_signer, metadata_serialized, code);

        event::emit(Upgrade { object_address: signer::address_of(code_signer), });
    }
