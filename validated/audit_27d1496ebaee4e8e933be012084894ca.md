### Title
Unbounded slippage in `SmartWomConvert._convertFor`'s buyback swap allows sandwiching of `WombatStaking._sendRewards`'s mWOM fee conversion - ([File: wombat/SmartWomConvert.sol])

### Summary
When `WombatStaking._sendRewards` charges an `isMWOM` fee on harvested WOM, it calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`, which internally swaps part of the fee for mWOM via `IWombatRouter.swapExactTokensForTokens(..., amountOutMin = 0, ...)` on `womMWomPool`. Because the router call itself has zero slippage protection and the only post-trade guard enforces merely `convertAmount + amountRec >= _amountIn` (i.e. "not worse than 1:1 minting"), an attacker can sandwich the swap to drive the received mWOM down to just above that floor, capturing the price-improvement spread that the buyback branch was designed to earn for the protocol's reward pool.

### Finding Description
`_sendRewards` is reached from any user's `harvest()`/`depositLP()`/`withdraw()` call path through `_toMasterWomAndSendReward`, and unconditionally triggers the fee conversion whenever a fee entry has `isMWOM == true` and `rewardToken == wom`: [1](#0-0) 

`smartConvert` decides whether to buy mWOM on the open market (buyback) instead of minting 1:1, based on a **spot-price** read of `womMWomPool` with no TWAP/oracle protection: [2](#0-1) [3](#0-2) 

The actual swap is executed with `amountOutMin = 0`, and the only safety check happens *after* the swap, comparing the total result to the full input amount (`_minRec = _amountIn` passed from `smartConvert`): [4](#0-3) 

This check only guarantees `convertAmount + amountRec >= _amountIn`, which reduces to `amountRec >= buybackAmount` — i.e., the swap must not be *worse* than minting 1:1. It does **not** guarantee the swap executes at the fair/undepressed market price. An attacker can:
1. Front-run `harvest()`/`depositLP()` with a large skewed swap on `womMWomPool` to temporarily push the mWOM price up (worsening the WOM→mWOM exchange rate) while staying above the 1:1 floor.
2. Let the victim transaction's `smartConvert` call execute the buyback swap at this manipulated, less favorable price — the call still succeeds (no revert) because it remains ≥1:1, but yields materially less mWOM than the true, unmanipulated market price would have produced.
3. Back-run to reverse their skew swap, capturing the spread between the true market rate and the artificially worsened rate as profit.

The resulting `feeTosend = IMWom(mWom).balanceOf(address(this)) - beforeBalnce` (i.e., the reduced amount) is what actually gets queued to the fee recipient (often a `BaseRewardPool` via `queueNewRewards`): [5](#0-4) 

No existing modifier, reentrancy guard, or reward-index mechanism prevents this — the check only bounds the worst case at "not worse than minting," not "fair execution price," so any spread between the enforced floor and the genuine market price is extractable MEV.

### Impact Explanation
This causes theft of unclaimed protocol yield: the mWOM destined for stakers'/rewarders' reward pool (`feeInfo.to` via `queueNewRewards`) is reduced below what a non-manipulated execution would have produced, and the difference is captured by the attacker instead of accruing to stakers. This matches the Immunefi impact class "theft of unclaimed yield."

### Likelihood Explanation
Preconditions are minimal for an unprivileged attacker: flash-loan capital to move `womMWomPool` skew, and the ability to trigger (or wait for someone else to trigger) `harvest()`/`depositLP()` on any pool where the `isMWOM` fee is active and `smartWomConverter` is set. The buyback branch only activates when `currentRatio() < buybackThreshold` (i.e., mWOM trading at a discount), so the attack is most profitable/likely during periods of natural mWOM discount, but the attacker can also artificially induce that condition via price manipulation to force a buyback that wouldn't otherwise occur. This is repeatable every block that a harvest transaction lands, bounded only by `maxSwapAmount()` (a function of `womAsset` cash/liability imbalance) and pool liquidity/depth for price impact.

### Recommendation
Replace the spot-price check in `currentRatio()`/`smartConvert` with a manipulation-resistant reference (e.g., time-weighted average price, or an oracle), and pass a real minimum-out (computed off the pre-transaction fair quote with a tight tolerance, e.g., via `getAmountOut` queried at call-construction time and enforced with `amountOutMin` on the router call itself) rather than the loose `_amountIn` floor. Consider also capping the swap size/frequency or using a commit-reveal/keeper-only trigger with slippage checks to reduce sandwichability.

### Proof of Concept
Foundry fork test plan:
1. Fork BSC/relevant chain at a block where `womMWomPool` sits below `buybackThreshold` (or manipulate it there).
2. Baseline run: call `harvest()`/`depositLP()` on an active pool with `isMWOM` fee active, record `feeTosend` (mWOM queued to `feeInfo.to`) via `RewardPaidTo`/`queueNewRewards` event, or read `IBaseRewardPool` balance delta.
3. Attack run: reset fork; have an attacker contract flash-loan WOM/mWOM, execute a large swap on `womMWomPool` to skew price against the buyback direction, then call `harvest()` (or wait for the victim's `harvest()` tx), then execute the reverse swap to restore price and realize profit.
4. Assert: (a) attack-run `feeTosend` to `feeInfo.to` < baseline `feeTosend`; (b) attacker's net token balance (post round-trip swaps, minus flash loan fees) is positive, demonstrating extracted MEV came from the fee-conversion swap rather than pure market noise.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
