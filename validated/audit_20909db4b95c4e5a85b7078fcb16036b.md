### Title
Missing participant-index validation causes panic (DoS) when verifying blame proofs - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
Analogous to CVE-2026-37458 (missing input validation in a message handler → DoS), `Decryption::decrypt_with_proof` in `crypto/dkg/pedpop/src/encryption.rs` indexes `self.enc_keys[&decryptor]` without checking that `decryptor` is a registered participant. `enc_keys` only contains entries for the *other* participants registered during `verify_r1` (`Decryption::register` is called per sender's `EncryptionKeyMessage`, never for the local participant). Any `blame` evaluation naming a `recipient` that was never registered — including the verifying machine's own index or any syntactically valid `Participant` — panics on the `HashMap` index, crashing the host instead of returning a `DecryptionError`.

### Finding Description
`BlameMachine::blame` (`crypto/dkg/pedpop/src/lib.rs:623`) forwards attacker-influenced `sender`/`recipient`/`msg`/`proof` to `blame_internal` (`lib.rs:575`), which calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`. Inside `decrypt_with_proof` (`encryption.rs:366`), after the PoP signature check, the code evaluates:

```rust
&[self.enc_keys[&decryptor], *proof.key]
```

(`encryption.rs:388`) as an argument to `dleq.verify`. There is no validation that `decryptor` ∈ `enc_keys`. `enc_keys` is populated only in `Decryption::register` (`encryption.rs:351`), invoked from `SecretShareMachine::verify_r1` (`lib.rs:315`) for each *other* participant's commitment message — the local participant's own index is never inserted (`lib.rs:362-364` skips `l == params.i()` during share generation, and `verify_r1` `continue`s when no message exists for our index). Therefore `decrypt_with_proof` panics whenever `decryptor` equals the verifying party's own `Participant` or any index whose registration is absent.

In the deployment shape (`processor/src/key_gen.rs`, `CoordinatorMessage::VerifyBlame`), the `accuser`/`accused`/`share`/`blame` fields are deserialized from coordinator messages and fed into `EncryptedMessage::read`/`blame` — i.e., a participant can cause a victim validator to evaluate a blame tuple where `recipient` is the victim's own index (or any unregistered index), hitting the panic.

### Impact Explanation
A single crafted blame message causes an unhandled panic in the validator/processor task performing blame arbitration. In Rust services this aborts the signing/key-gen task (or crashes the process if unwinding isn't caught), denying availability of the threshold-signing node — matching the CVE's `A:H` availability-only impact. No secret material is leaked; the panic occurs before any decryption result is produced.

### Likelihood Explanation
Requires an authenticated protocol participant able to submit a blame accusation (matching the CVE's `PR:L`/`AC:L`). The attacker only needs to name an unregistered `recipient` in an otherwise well-formed blame message — the `EncryptedMessage`/`EncryptionKeyProof` bytes need only parse (`read` succeeds on any canonically encoded fields), and the panic triggers during `dleq.verify` argument evaluation. Any syntactically valid `Participant` not present in `enc_keys` suffices.

### Recommendation
Replace the panicking index with a checked lookup in `decrypt_with_proof`:

```rust
let Some(dec_key) = self.enc_keys.get(&decryptor) else {
  Err(DecryptionError::InvalidProof)?
};
```

and use `*dec_key` in the `dleq.verify` statement list. Alternatively, validate `sender`/`recipient` against `params.all_participant_indexes()` in `BlameMachine::blame`/`blame_internal` before calling `decrypt_with_proof`, returning the accuser as faulty for out-of-set recipients. The same pattern should be audited anywhere `enc_keys[...]` or `commitments[...]` is indexed by message-derived participants.

### Proof of Concept
```rust
// Setup: 3-of-3 PedPoP completed normally; `victim_machine` is a BlameMachine
// whose Decryption.enc_keys contains participants {1,2,3} minus its own index i.

// Attacker (participant k != i) builds a blame tuple naming the victim's own index
// as `recipient` (or any Participant not registered in `enc_keys`).
let attacker_share_msg: EncryptedMessage<Ristretto, SecretShare<Scalar>> = /* validly parsed msg */;
let proof: Option<EncryptionKeyProof<Ristretto>> = Some(/* any parsable DLEqProof */);
let sender = Participant::new(attacker_index).unwrap();
let recipient = victim_i; // victim's own index: never present in victim's enc_keys

// On the victim:
let (_machine, _faulty) = victim_machine.blame(sender, recipient, attacker_share_msg, proof);
// PANIC at crypto/dkg/pedpop/src/encryption.rs:388:
//   self.enc_keys[&decryptor]  ->  HashMap index out of bounds / key not found
```

The panic occurs after `msg.pop.verify` passes/fails harmlessly, inside `decrypt_with_proof` when evaluating `&[self.enc_keys[&decryptor], *proof.key]` for `dleq.verify` — no blame determination is returned and the process crashes.

Note: I could not fully confirm within the available context whether `processor`'s `VerifyBlame` path pre-validates `accuser`/`accused` against the participant set before invoking `blame`; if it does, the reachable trigger narrows to `recipient` values that are valid participants but unregistered on the verifier (still including any index the verifier never registered). The panic itself in `decrypt_with_proof` is unconditional for unregistered `decryptor`.
