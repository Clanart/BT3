### Title
Malformed Bitcoin payment amount bypasses the funds check and causes signing of an invalid transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` sums payment amounts and adds the estimated fee using unchecked `u64` arithmetic. A payment near `u64::MAX` wraps the required-funds calculation back to a small value, allowing construction of a transaction whose logical output value greatly exceeds its input value. [1](#0-0) [2](#0-1) 

### Finding Description
The constructor rejects dust payments but does not reject an excessively large payment or use checked addition when computing `payment_sat` and `payment_sat + needed_fee`. With a payment of `u64::MAX`, the addition wraps modulo `2^64`, so the `input_sat < payment_sat + needed_fee` comparison can pass despite the transaction being unspendable and consensus-invalid. [3](#0-2) [4](#0-3) 

The malformed output is retained in `tx_outs`, and the function returns a `SignableTransaction` containing it. `multisig` then verifies only that each prevout's `script_pubkey` corresponds to the threshold key and offset; it does not recalculate affordability or reject an invalid output amount. [5](#0-4) [6](#0-5) [7](#0-6) 

`TransactionSignMachine::sign` subsequently computes a Taproot key-spend sighash over that malformed transaction and produces a FROST signature share for it. [8](#0-7) 

### Impact Explanation
An attacker who can cause a withdrawal/payment request to be signed can make threshold participants sign a transaction that commits to an output amount exceeding the input amount. This is a concrete signature over unintended transaction data; the resulting Bitcoin transaction is invalid and cannot spend the represented funds. [6](#0-5) [8](#0-7) 

The issue can also trip the later fee calculation because `fee()` performs an unchecked `sum(inputs) - sum(outputs)` subtraction. [9](#0-8) 

### Likelihood Explanation
Exploitation requires an attacker-controlled payment amount to reach `SignableTransaction::new` and a signing flow to continue with the returned transaction. Those are public transaction-construction inputs, and no participant preprocess manipulation, validator compromise, leaked key, or invalid curve encoding is needed. [10](#0-9) [7](#0-6) 

### Recommendation
Calculate input, payment, and fee totals with `u128` or checked arithmetic, reject overflow, and explicitly require `input_sat >= payment_sat + needed_fee` before creating any transaction. Also validate each output amount against Bitcoin's consensus money range before signing, and make `fee()` return `Option<u64>` or use `checked_sub` rather than relying on construction-time invariants. [1](#0-0) [4](#0-3)

```rust
#[test]
fn overflowing_payment_bypasses_funds_check() {
  let script = ScriptBuf::new_p2tr_tweaked(
    TweakedPublicKey::dangerous_assume_tweaked(
      XOnlyPublicKey::from_slice(&[2; 32]).unwrap()
    )
  );

  let input = ReceivedOutput {
    offset: Scalar::ZERO,
    output: TxOut {
      value: Amount::from_sat(1_000),
      script_pubkey: script.clone(),
    },
    outpoint: OutPoint::default(),
  };

  // payment_sat + needed_fee wraps below input_sat in release arithmetic.
  let payments = [(script, u64::MAX)];

  let tx = SignableTransaction::new(
    vec![input],
    &payments,
    None,
    None,
    1,
  ).unwrap();

  assert_eq!(tx.transaction().output[0].value.to_sat(), u64::MAX);
}
```

With a threshold `keys` value matching the prevout script, `tx.multisig(&keys)` proceeds to produce per-input `AlgorithmMachine`s, and `sign` signs the Taproot sighash for the malformed transaction. [7](#0-6) [8](#0-7)
