## Analysis

The reported Sudoswap bug class — crediting internal accounting based on the *requested* transfer amount instead of verifying the *actual* balance received — has a direct, unprivileged-wallet-reachable analog in this codebase's reward accounting.

### Title
Unverified token receipt in `_provisionReward()` inflates reward accounting for fee-on-transfer/rebasing reward tokens - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`, `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`donateRewards()` is a public, unprivileged entry point (any wallet can call it, gated only by `isRewardToken[_rewardToken]`, not by `onlyManager`) that funnels into `_provisionReward()`. This function performs `safeTransferFrom(msg.sender, address(this), _amountReward)` and then unconditionally adds the full `_amountReward` (the value supplied by the caller) into `rewardInfo.historicalRewards` and `rewardInfo.rewardPerTokenStored`, with no check that the pool's token balance actually increased by that amount. [1](#0-0) [2](#0-1) 

The same pattern exists in `BaseRewardPoolV2.sol`: [3](#0-2) [4](#0-3) 

And in `mWOMSVBaseRewarder.sol`, which contains the same `donateRewards`/`_provisionReward` structure.

### Finding Description
`_provisionReward()` never checks the reward token's `balanceOf(this)` before and after the `safeTransferFrom` call to confirm that `_amountReward` tokens were actually received — it simply trusts the parameter and mirrors it into on-chain reward-per-share accounting (`rewardPerTokenStored`). This is structurally identical to the Sudoswap `_validateTokenInput()` bug: one code path (`router.pairTransferERC20From`) verifies actual balance delta, while the direct-transfer path does not.

Because `donateRewards()` has no manager/owner restriction — it is callable by any address as long as the token is already an `isRewardToken` — any holder of an already-registered reward token can call it. If that reward token has non-standard transfer semantics (fee-on-transfer, deflationary/rebasing behavior — a known real-world class of tokens exploited in incidents like Qubit Finance), the contract will receive fewer tokens than `_amountReward` but will still credit the full requested amount into `rewardPerTokenStored`.

### Impact Explanation
Since `rewardPerTokenStored` (and therefore every staker's `earned()` calculation) is inflated beyond the tokens actually held by the contract, the sum of all stakers' claimable rewards for that token will exceed the pool's real balance. When stakers call `getReward()`, the `IERC20(rewardToken).safeTransfer(_receiver, reward)` in `getReward()` will eventually fail for some users once the pool is drained below the over-credited total, permanently freezing/insolvency-locking a portion of legitimate stakers' already-accrued yield for that reward token (`rewards/BaseRewardPool.sol` lines 219-240, 297-319). [5](#0-4) 

### Likelihood Explanation
The `donateRewards` path itself requires no privileged role — it is reachable from any unprivileged wallet — but the vulnerability's severity depends on a reward token with non-standard transfer behavior already being registered via the admin-only `queueNewRewards`. This mirrors the same conditional acknowledged by Sudoswap ("pair creators would have to willingly deploy... a non-standard ERC20 token"); likelihood is moderate and depends on the specific reward tokens chosen for pools.

### Recommendation
In `_provisionReward()`, measure `balanceOf(address(this))` before and after the `safeTransferFrom` call and use the actual delta (not the caller-supplied `_amountReward`) when updating `historicalRewards` and `rewardPerTokenStored`, matching the safer `router.pairTransferERC20From()` pattern referenced in the original report.

### Proof of Concept
1. Admin registers `RewardTokenX` (a fee-on-transfer or rebasing token) via `queueNewRewards`, setting `isRewardToken[RewardTokenX] = true`.
2. Any unprivileged wallet calls `donateRewards(1000e18, RewardTokenX)`.
3. `_provisionReward` calls `safeTransferFrom(msg.sender, address(this), 1000e18)`, but due to the token's transfer fee, the pool actually receives e.g. 950e18.
4. `rewardInfo.rewardPerTokenStored` is nonetheless increased using the full `1000e18`, over-crediting all current stakers by 50e18 worth of shares.
5. As stakers redeem via `getReward()`, the pool's real `RewardTokenX` balance is exhausted before all entitled claims are paid, and the last claimants' `safeTransfer` calls revert — their already-accrued rewards become permanently unclaimable. [6](#0-5)

            address rewardToken = rewardTokens[index];
            userRewards[rewardToken][_account] = earned(_account, rewardToken);

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
