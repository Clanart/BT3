### Title
Permanent freezing of native SEI when redeeming WSEI to a contract wallet via `payable(msg.sender).transfer()` - (File: `contracts/src/WSEI.sol`)

### Summary
The canonical Wrapped SEI (WSEI) ERC-20 contract, whose bytecode is embedded in the chain binary and deployable via the `deploy-wsei` CLI/EVM path, unwraps tokens back to native SEI using Solidity's low-level `transfer()`, which forwards only 2300 gas. Any contract-based holder (multisig, smart-contract wallet, or any contract with a non-trivial `receive()`/`fallback()`) that calls `withdraw()` will have the transaction revert, permanently freezing its native SEI inside the WSEI contract.

### Finding Description
`WSEI.withdraw()` burns the caller's wrapped balance and then sends native SEI using `payable(msg.sender).transfer(wad)`: [1](#0-0) 

`transfer()` hard-codes a 2300 gas stipend to the recipient's `receive()`/`fallback()` code. Any contract account (Gnosis Safe-style multisig, proxy wallet, or any contract emitting an event or doing any nontrivial bookkeeping on receipt of ETH/SEI) will run out of gas and revert the whole `withdraw()` call — after `balanceOf[msg.sender]` has already been decremented in the same transaction (the whole tx reverts, so no double-spend, but the caller can never successfully call `withdraw()` again from that same contract address).

This WSEI bytecode is not a throwaway test fixture: it is embedded as a chain artifact and exposed as a first-class deployable contract via `CmdDeployWSEI` in the EVM CLI/tx path, using the exact same bytecode stored at `x/evm/artifacts/wsei/WSEI.bin`: [2](#0-1) [3](#0-2) 

Any EVM contract deployer can deploy this bytecode (or the identical logic bundled in it) and any EVM user can wrap/unwrap SEI through it, exactly mirroring the Renzo `WithdrawQueue.claim()` bug class: a two-step deposit/withdraw ERC20-wrapper pattern where the unwrap step uses `transfer()` instead of `call()`.

### Impact Explanation
Any contract account (smart contract wallet, DeFi vault, multisig, or a DEX router/vault contract) that deposits SEI into WSEI and later attempts `withdraw()` will have its underlying native SEI permanently locked inside the WSEI contract if its own `receive()`/fallback logic costs more than 2300 gas (e.g., emitting an event, updating storage, forwarding through a proxy). This is a direct, irreversible loss/freezing of funds for any smart-contract holder of WSEI, matching the "permanent freezing of funds" impact criterion.

### Likelihood Explanation
Likelihood is high: WSEI is the canonical wrap/unwrap pattern for native SEI in the EVM ecosystem on Sei, deployable by any user via `deploy-wsei`, and widely expected to be integrated by DeFi protocols, vaults, and multisig-controlled treasuries — all of which are contract accounts. As soon as any such contract calls `withdraw()`, the bug triggers deterministically (100% failure rate for that contract), with no special conditions or race required.

### Recommendation
Replace the low-level `transfer()` call in `withdraw()` with a gas-forwarding `call()` plus explicit success check, following the same mitigation Renzo applied:
```solidity
function withdraw(uint wad) public {
    require(balanceOf[msg.sender] >= wad);
    balanceOf[msg.sender] -= wad;
    (bool success, ) = payable(msg.sender).call{value: wad}("");
    require(success, "SEI transfer failed");
    emit Withdrawal(msg.sender, wad);
}
```
Apply the same fix to any other duplicated copies of this contract (`evmrpc/solidity/ERC20.sol`, `evmrpc/tests/solidity/ERC20.sol`) if they are ever exposed as production-deployable artifacts.

### Proof of Concept
1. Deploy a minimal contract wallet `Vault` whose `receive()` writes to storage/emits an event (>2300 gas cost), e.g.:
   ```solidity
   contract Vault {
       event Received(uint amount);
       receive() external payable { emit Received(msg.value); }
   }
   ```
2. From `Vault`, call `WSEI.deposit()` with some SEI value — succeeds, `balanceOf[Vault]` increases.
3. From `Vault`, call `WSEI.withdraw(wad)`.
4. `WSEI.withdraw()` executes `balanceOf[msg.sender] -= wad;` then `payable(msg.sender).transfer(wad)`. The `transfer()` call forwards only 2300 gas to `Vault.receive()`, which needs more gas to emit the event, causing an out-of-gas revert; the whole `withdraw()` transaction reverts.
5. `Vault` can never successfully withdraw its wrapped SEI balance — the funds are permanently stuck in the `WSEI` contract, referencing [1](#0-0) .

package wsei

import (
	"embed"
	"encoding/hex"
	"strings"

	"github.com/ethereum/go-ethereum/accounts/abi"
)

const CurrentVersion uint16 = 1

//go:embed WSEI.abi
//go:embed WSEI.bin
var f embed.FS

var cachedBin []byte
var cachedABI *abi.ABI

func GetABI() []byte {
	bz, err := f.ReadFile("WSEI.abi")
	if err != nil {
		panic("failed to read WSEI contract ABI")
	}
	return bz
}

func GetParsedABI() *abi.ABI {
	if cachedABI != nil {
		return cachedABI
	}
	parsedABI, err := abi.JSON(strings.NewReader(string(GetABI())))
	if err != nil {
		panic(err)
	}
	cachedABI = &parsedABI
	return cachedABI
}

func GetBin() []byte {
	if cachedBin != nil {
		return cachedBin
	}
	code, err := f.ReadFile("WSEI.bin")
	if err != nil {
		panic("failed to read WSEI contract binary")
	}
	bz, err := hex.DecodeString(string(code))
	if err != nil {
		panic("failed to decode WSEI contract binary")
	}
	cachedBin = bz
	return bz
}
