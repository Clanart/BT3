### Title
Bitcoin transaction fee calculation ignores OP_RETURN outputs - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` adds an optional OP_RETURN output to the transaction, but calculates the transaction weight and required fee only from `payments` and the optional change output. The data-carrying output is omitted from `calculate_weight_vbytes`, causing the advertised and enforced fee rate to be lower than the fee rate of the transaction actually signed and broadcast.

### Finding Description
The constructor appends the OP_RETURN output to `tx_outs` before estimating transaction size, but calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` with `payments`, not the complete output list. [1](#0-0)  The same omission occurs in the change-aware estimate, which again passes only `payments` and `Some(&change)`. [2](#0-1) 

`calculate_weight_vbytes` builds the estimation transaction exclusively from the supplied `payments` and optional change output, so the OP_RETURN output's amount field, compact-size length, and up to 80 bytes of script payload are not represented in the returned weight or vbytes. [3](#0-2) 

The result is that `needed_fee` is calculated as `fee_per_vbyte * vbytes_without_data`, while `fee()` later measures the real transaction constructed with the extra output. [4](#0-3)  The minimum-relay check also uses the underestimated `vbytes`, rather than the transaction's real vsize. [5](#0-4) 

### Impact Explanation
An unsigned transaction containing data can be produced and signed with an absolute fee and effective fee rate below the caller's requested `fee_per_vbyte`. With a low requested rate, the signed transaction can also fall below Bitcoin's minimum relay fee even though `SignableTransaction::new` accepted it as satisfying `DEFAULT_MIN_RELAY_TX_FEE`.

The signed transaction itself commits to the real outputs through the Taproot sighashes, so this is not an amount-conservation failure. The practical impact is a validly signed transaction that may not relay or confirm at the intended fee rate, delaying or preventing movement of the selected inputs until a replacement transaction is constructed and signed.

### Likelihood Explanation
Any caller supplying `data` to `SignableTransaction::new` reaches the incorrect calculation. The discrepancy is deterministic and grows with the data length, up to the permitted 80-byte payload. [6](#0-5) 

The issue is most likely to matter when the requested fee is near the minimum relay threshold. At higher fee rates, the transaction remains broadcastable but still pays less than the requested rate. Because Serai's processor currently calls `BSignableTransaction::new` with `None` for data, production signing through that path does not appear to expose this unless another caller supplies data. [7](#0-6) 

### Recommendation
Calculate weight from the actual `tx_outs`, including the OP_RETURN output, or pass an output representation containing payments, data, and change into `calculate_weight_vbytes`. After constructing the final transaction, validate `needed_fee` against `tx.vsize()` and reject or recompute if the actual fee rate is below either the requested rate or the minimum relay rate.

### Proof of Concept
1. Construct a `SignableTransaction` with one spendable input, no payments or change, `data = Some(vec![0; 80])`, and `fee_per_vbyte` chosen so the underestimated fee barely passes the minimum-relay check.
2. `new` creates an OP_RETURN output but estimates weight as if the transaction had no outputs.
3. `needed_fee()` and `fee()` report the same absolute fee, but that fee divided by the final transaction's real `vsize()` is below the requested rate and can be below the minimum relay fee.
4. The resulting transaction is nevertheless eligible for signing because `TransactionMachine` signs the actual serialized transaction. [8](#0-7)
