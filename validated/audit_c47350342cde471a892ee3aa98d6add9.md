Based on my research, the closest structural analog to the seed report's "check silently disabled when the guard variable is at its default/unset value" bug class is in `same-origin-filter.ts`, GitHub Desktop's defense against leaking `Authorization`/`Cookie`/`Authentication` headers across cross-origin redirects.

### Title
Cross-origin credential header leak when redirect-origin tracking is unset - (`app/src/main-process/same-origin-filter.ts`)

### Summary
`installSameOriginFilter` is supposed to strip `Authorization`, `Authentication`, and `Cookie` headers whenever a request is redirected to a different origin than the one it started at. The guard that decides whether to strip headers only fires when the initial origin was actually recorded in the `requestOrigin` map; if that value is `undefined` for any reason, the filter falls back to forwarding the headers unmodified — mirroring the seed report's `manager == address(0)` pattern where a default/unset guard value silently disables the access check instead of denying by default.

### Finding Description
The filter records the origin of the first hop of a request keyed by Electron's `details.id`: [1](#0-0) 

Then on `onBeforeSendHeaders` it decides whether to sanitize headers based solely on whether that recorded origin is present and matches: [2](#0-1) 

The critical line is:
```
if (initialOrigin === undefined || initialOrigin === origin) {
  return { requestHeaders: details.requestHeaders }
}
```
This is structurally identical to the seed's `onlyManager` bug: the intended check is "strip headers unless the origin matches", but it is implemented as "strip headers only if we have a known-different origin", so whenever `initialOrigin` is `undefined` the code fails open and forwards the (potentially credential-bearing) headers to whatever origin the request has been redirected to. `initialOrigin` is left `undefined` whenever the initiating request's protocol is in the `safeProtocols` set (`devtools:`, `file:`, `chrome-extension:`) — those requests are deliberately excluded from being tracked — or in any case where `onBeforeRequest` did not populate the map for that `details.id` before `onBeforeSendHeaders` runs.

### Impact Explanation
If a request that carries GitHub API/enterprise auth headers is routed through a code path where the initial hop is not tracked (e.g., a `file:`-protocol-initiated fetch, or any race/edge-case where `onBeforeRequest` doesn't populate the map before `onBeforeSendHeaders` fires for the same request id), a subsequent redirect to an attacker-controlled origin — such as one returned by a malicious/compromised GHE proxy or API-adjacent endpoint — would receive the full `Authorization`/`Cookie` headers instead of having them stripped. This is exactly the credential-exfiltration scenario the filter's own doc comment says it exists to prevent: [3](#0-2) 

### Likelihood Explanation
I could not fully verify how frequently `initialOrigin` ends up `undefined` for auth-bearing requests in practice. Electron's webRequest API is documented to fire `onBeforeRequest` before `onBeforeSendHeaders` for every hop including redirects, so under normal https-initiated fetches the map should be populated correctly and the bypass path is limited to the explicitly-excluded `safeProtocols` schemes, which are not typically the origin of attacker-controlled, credential-bearing requests. This means the reachable trigger surface for an external, no-privilege attacker (e.g., via a malicious GHE server issuing a redirect) is narrower than the seed's fully-open modifier bug, and I was unable to construct or find in-repo evidence of a concrete end-to-end attacker-triggerable sequence that leaves `initialOrigin` unset for a genuinely credentialed request. This should be treated as a lower-confidence, narrower-scope analog rather than a directly equivalent, fully-proven vulnerability.

### Recommendation
Invert the guard so that the safe/fail-closed behavior is the default: only forward headers unmodified when `initialOrigin` is known **and** equal to the current origin; treat an unset/unknown `initialOrigin` as "different origin" and always sanitize headers in that case. Additionally, reconsider excluding `file:`/`devtools:`/`chrome-extension:` protocols from tracking, since doing so leaves those flows permanently exempt from the cross-origin credential check.

### Proof of Concept
Because reachability from a genuinely credentialed, attacker-controlled request could not be confirmed against the live app flow, a full working PoC cannot be provided with confidence. The code-level demonstration of the flaw is:
1. A request whose initiating hop uses one of the `safeProtocols` (`devtools:`, `file:`, `chrome-extension:`) is never added to `requestOrigin` (`same-origin-filter.ts:47-49`).
2. If that same `details.id` is later observed carrying `Authorization`/`Cookie` headers in `onBeforeSendHeaders` and is redirected to a different origin, the check at line 58 evaluates `initialOrigin === undefined` as `true` and returns the headers unchanged, instead of stripping them, at line 59. [4](#0-3) 

Given the uncertainty flagged above, I'd rate confidence in this being a fully exploitable, in-scope finding as low-to-medium; it is the best structural match I found in the codebase for the seed's "fail-open on unset guard" bug class, but I was not able to conclusively prove an attacker-reachable trigger within the tool access available.

```typescript
import { OrderedWebRequest } from './ordered-webrequest'

/**
 * Installs a web request filter to prevent cross domain leaks of auth headers
 *
 * GitHub Desktop uses the fetch[1] web API for all of our API requests. When fetch
 * is used in a browser and it encounters an http redirect to another origin
 * domain CORS policies will apply to prevent submission of credentials[2].
 *
 * In our case however there's no concept of same-origin (and even if there were
 * it'd be problematic because we'd be making cross-origin request constantly to
 * GitHub.com and GHE instances) so the `credentials: same-origin` setting won't
 * help us.
 *
 * This is normally not a problem until http redirects get involved. When making
 * an authenticated request to an API endpoint which in turn issues a redirect
 * to another domain fetch will happily pass along our token to the second
 * domain and there's no way for us to prevent that from happening[3] using
 * the vanilla fetch API.
 *
 * That's the reason why this filter exists. It will look at all initiated
 * requests and store their origin along with their request ID. The request id
 * will be the same for any subsequent redirect requests but the urls will be
 * changing. Upon each request we will check to see if we've seen the request
 * id before and if so if the origin matches. If the origin doesn't match we'll
 * strip some potentially dangerous headers from the redirect request.
```

```typescript
export function installSameOriginFilter(orderedWebRequest: OrderedWebRequest) {
  // A map between the request ID and the _initial_ request origin
  const requestOrigin = new Map<number, string>()
  const safeProtocols = new Set(['devtools:', 'file:', 'chrome-extension:'])
  const unsafeHeaders = new Set(['authentication', 'authorization', 'cookie'])

  orderedWebRequest.onBeforeRequest.addEventListener(async details => {
    const { protocol, origin } = new URL(details.url)

    // This is called once for the initial request and then once for each
    // "subrequest" thereafter, i.e. a request to https://foo/bar which gets
    // redirected to https://foo/baz will trigger this twice and we only
    // care about capturing the initial request origin
    if (!safeProtocols.has(protocol) && !requestOrigin.has(details.id)) {
      requestOrigin.set(details.id, origin)
    }

    return {}
  })

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const initialOrigin = requestOrigin.get(details.id)
    const { origin } = new URL(details.url)

    if (initialOrigin === undefined || initialOrigin === origin) {
      return { requestHeaders: details.requestHeaders }
    }

    const sanitizedHeaders: Record<string, string> = {}

    for (const [k, v] of Object.entries(details.requestHeaders)) {
      if (!unsafeHeaders.has(k.toLowerCase())) {
        sanitizedHeaders[k] = v
      }
    }

    log.debug(`Sanitizing cross-origin redirect to ${origin}`)
    return { requestHeaders: sanitizedHeaders }
  })
```
