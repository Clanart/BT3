### Title
EVM `deny_list` method restriction is enforced only on the HTTP JSON-RPC transport, fully bypassed via WebSocket - (File: `evmrpc/rpcstack.go`)

### Summary
Operators restrict specific EVM JSON-RPC methods (e.g. expensive `debug_trace*` calls) via `[evm].deny_list` in `app.toml`. This restriction is registered only against the HTTP `rpc.Server` instance and is never applied to the separate `rpc.Server` created for the WebSocket transport. A public client can therefore call any "denied" method simply by connecting over `ws://` instead of `http://`, exactly as the Open WebUI advisory describes bypassing an endpoint restriction by switching the authentication/transport header used to reach the same underlying handler.

### Finding Description
`HTTPServer.EnableRPC` builds an `rpc.Server`, registers the API surface, and then explicitly walks `config.DenyList` to call `srv.RegisterDenyList(method)` for each denied method name: [1](#0-0) 

`HTTPServer.EnableWS` builds a **separate** `rpc.Server` (`srv := rpc.NewServer()`), registers the very same `apis` slice via `RegisterApis`, but never touches `config.DenyList` — there is no deny-list call anywhere in this function: [2](#0-1) 

This is structural, not incidental: `WsConfig` (used by `EnableWS`) has no `DenyList` field at all, while `HTTPConfig` (used by `EnableRPC`) does: [3](#0-2) 

`RegisterDenyList` is called exactly once in the whole codebase, from `EnableRPC` only: [4](#0-3) 

Both `NewEVMHTTPServer` and `NewEVMWebSocketServer` register the identical `apis` list (same `EthNamespace`, `debug`, etc. services) — the method surface reachable is the same on both transports; only the deny-list gate differs: [5](#0-4) [6](#0-5) 

The config documentation confirms `deny_list` is meant to make the EVM RPC "fail fast" for specific methods, with `debug_traceBlockByNumber` given as the canonical example — i.e. methods whose unrestricted execution is expected to be resource-exhausting or otherwise unsafe for the operator's node: [7](#0-6) [8](#0-7) 

This mirrors the reported bug class precisely: the operator's access-control decision (which methods may be invoked) is applied to one entry point into the same backend and is silently skipped on another entry point that reaches identical handler code, because the enforcement point (`RegisterDenyList`) sits outside the shared dispatch logic and one caller of that logic omits it.

### Impact Explanation
Any operator who runs both HTTP and WebSocket JSON-RPC (a common, default-adjacent configuration since both are independently toggled by `http_enabled`/`ws_enabled`) and relies on `deny_list` to block specific methods — most notably heavy `debug_trace*` methods explicitly called out in the docs as the reason this list exists — has that protection completely undermined by any public client simply opening a WebSocket connection instead of an HTTP one. Since `deny_list` exists specifically to prevent otherwise-reachable methods from being invoked because they are considered unsafe/expensive for the node, an unauthenticated public RPC client can use this bypass to invoke a denied trace/debug method and drive the node to resource exhaustion or crash, defeating the operator's explicit safety configuration on a default-configuration RPC node that exposes both transports.

### Likelihood Explanation
High likelihood of exploitability wherever WS is enabled alongside HTTP with a non-empty `deny_list`: no authentication, no special privileges, and no crafted payload beyond choosing a different transport for the exact same JSON-RPC method call are required. The bypass requires no association, no funded account, and no on-chain transaction — a bare WebSocket connection to the public RPC endpoint suffices.

### Recommendation
Apply the configured `deny_list` to the WebSocket `rpc.Server` in `EnableWS` the same way it is applied in `EnableRPC` — add a `DenyList []string` field to `WsConfig`, populate it from `config.DenyList` in `NewEVMWebSocketServer`, and call `srv.RegisterDenyList(method)` for each entry before registering APIs, so deny-list enforcement is centralized and transport-independent (mirroring how `SeiLegacyAllowlist` is documented as being enforced only for one transport, which should also be reviewed for the same class of gap).

### Proof of Concept
1. Configure a node with both `http_enabled = true` and `ws_enabled = true`, and set `deny_list = ["debug_traceBlockByNumber"]` in `[evm]`.
2. Confirm the restriction over HTTP:
```bash
curl -s -X POST http://target:8545 \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"debug_traceBlockByNumber","params":["latest",{}]}'
# -> {"jsonrpc":"2.0","id":1,"error":{"code":-32601,"message":"the method debug_traceBlockByNumber does not exist/is not available"}}
```
3. Send the identical call over the WebSocket endpoint (e.g. `ws://target:8546`) using any WS JSON-RPC client:
```json
{"jsonrpc":"2.0","id":1,"method":"debug_traceBlockByNumber","params":["latest",{}]}
```
The method executes normally and returns a full trace result, confirming the deny-list restriction is bypassed entirely on the WebSocket transport.

// EnableWS turns on JSON-RPC over WebSocket on the server.
func (h *HTTPServer) EnableWS(apis []rpc.API, config WsConfig) error {
	h.mu.Lock()
	defer h.mu.Unlock()

	if h.wsAllowed() {
		return fmt.Errorf("JSON-RPC over WebSocket is already enabled")
	}
	// Create RPC server and handler.
	srv := rpc.NewServer()
	srv.SetBatchLimits(config.batchItemLimit, config.batchResponseSizeLimit)
	readLimit := effectiveMaxRequestBodyBytes(config.readLimit)
	srv.SetReadLimits(readLimit)
	// maxConcurrentRequestBytes is passed through raw; rpc.Server.recomputeWSConcurrentBudget
	// raises it to readLimit when smaller, matching
	// newRequestSizeLimiter's max(budget, maxBody) rule on the HTTP protocol.
	srv.SetWSConcurrentRequestBytes(config.maxConcurrentRequestBytes)
	srv.SetWSAdmissionTimeout(config.wsAdmissionTimeout)
	srv.SetWSAdmissionEventHook(func(reason string) {
		// Hook carries no request context, and the fork's own connCtx is context.Background() too.
		recordWSAdmissionRejected(context.Background(), reason)
	})
	logger.Info("Registering apis for evm websocket")
	if err := RegisterApis(apis, config.Modules, srv); err != nil {
		return err
	}
	h.WsConfig = config
	h.wsHandler.Store(&rpcHandler{
		Handler: NewWSHandlerStack(srv.WebsocketHandler(config.Origins), config.JwtSecret),
		server:  srv,
	})
	return nil
}
