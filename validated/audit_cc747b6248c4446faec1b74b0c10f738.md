### Title
`ReceivedOutput::read` accepts an arbitrary scalar offset without binding it to the output's `script_pubkey`, allowing funds to be reported as received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The analog of the Carapace renewal-bypass is a verification/eligibility check that confirms "the object exists / is well-formed" while omitting a bound on a critical scalar parameter. In Carapace, `verifyBuyerCanRenewProtection` validated pool/NFT identity and timing but ignored `protectionAmount`. In `bitcoin-serai`, `ReceivedOutput::read` deserializes `(offset, output, outpoint)` and only checks syntactic validity (canonical scalar, decodable `TxOut`/`OutPoint`); it never verifies that `offset` is actually the scalar that maps the wallet's scan key to `output.script_pubkey`. The only place that invariant is established is `Scanner::scan_transaction`, which pairs each matched `script_pubkey` with the offset that produces it. Any `ReceivedOutput` entering the wallet via the untrusted `read` path rather than via `scan_transaction` carries an attacker-chosen `offset` that is unchecked against the output it claims to unlock.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` built by `register_offset`, which increments a candidate offset until `p2tr_script_buf(key + G*offset)` yields an even-Y P2TR script and stores `script -> offset`. `scan_transaction` then creates `ReceivedOutput { offset, output, outpoint }` only for outputs whose `script_pubkey` is a key in that map, so `offset` is guaranteed to satisfy `p2tr_script_buf(key + G*offset) == output.script_pubkey`.

`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) reconstructs the same struct from raw bytes:

- `Secp256k1::read_F` ensures only that `offset` is a canonical scalar — not that it is the *correct* scalar.
- `TxOut::consensus_decode` / `OutPoint::consensus_decode` ensure only that the fields parse.

There is no check that `output.script_pubkey == p2tr_script_buf(scanner.key + G*offset)`. A malicious `offset` value points the wallet at a different (or non-existent) derived Taproot key while still naming a real on-chain `outpoint` and `TxOut`. This is precisely the report's bug class: the request's identity fields (`lendingPoolAddress`/`nftLpTokenId` ↔ `output`/`outpoint`) are accepted as authentic while the value parameter (`protectionAmount` ↔ `offset`) is left unconstrained, letting a small/benign-appearing record escalate into a materially different claim.

### Impact Explanation
A party able to supply serialized `ReceivedOutput` bytes to a wallet/processor can cause an output to be recorded as received under an offset that does not open it. When the wallet later derives the spend key (`key + offset*G`, then TapTweak/parity handling), the derived key does not match the output's `script_pubkey`, so the reported funds are not spendable — an explicit accepted impact ("funds reported received that are not spendable"). It can also corrupt accounting: a real outpoint can be claimed under a wrong offset, shadowing or displacing the legitimately scanned record.

### Likelihood Explanation
Reachable wherever `ReceivedOutput` values cross a trust boundary via `read`/`serialize` (e.g., outputs reported between components rather than produced by a local `Scanner`). The bytes are fully attacker-controlled and no cryptographic check rejects a mismatched offset; likelihood is limited only by whether the deployment treats deserialized `ReceivedOutput`s as authenticated, which the code does not document.

### Recommendation
Either (a) have `ReceivedOutput::read` re-derive the expected script — i.e., carry or look up the scan key and require `p2tr_script_buf(key + G*offset) == output.script_pubkey` — or (b) document that deserialized `ReceivedOutput`s must only come from a trusted local `Scanner` and add a `verify(&self, key: &ProjectivePoint) -> bool` method enforcing the offset/script binding before the value is used to build spends.

### Proof of Concept
```rust
// key: the wallet's scan key; output: a real TxOut paying to some P2TR script
// Register a legitimate offset so `output` is "ours" in the honest flow.
let mut scanner = Scanner::new(key).unwrap();
let good_offset = scanner.register_offset(base_offset).unwrap();

// Honest path yields a consistent pair:
// p2tr_script_buf(key + G*good_offset) == output.script_pubkey

// Malicious path: craft bytes directly.
let mut buf = vec![];
let bad_offset = Scalar::ONE; // or any scalar != the offset deriving output.script_pubkey
buf.extend(bad_offset.to_bytes());
buf.extend(serialize(&output));     // real TxOut
buf.extend(serialize(&outpoint));   // real OutPoint

let ro = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// Accepted: offset is canonical, TxOut/OutPoint decode fine.
// But key + ro.offset()*G does not produce output.script_pubkey,
// so `ro` reports received value that cannot be signed for.
```

Caveat: this analog assumes serialized `ReceivedOutput`s are consumed from a less-trusted source than the local `Scanner`; if the codebase only ever round-trips them from `scan_transaction` within a single trust domain, the issue reduces to an undocumented invariant rather than a remotely reachable bug.
