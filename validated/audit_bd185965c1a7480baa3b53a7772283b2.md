### Title
Unbounded recursive parsing of `PuzzleWithRestrictions`/`MofN` custody memos allows a crafted coin memo to crash wallet sync via stack exhaustion - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively re-invokes itself once per `MofN` member found in an untrusted, attacker-supplied CLVM memo, with no depth or size limit. This mirrors the CVE-2026-44028 bug class (unbounded recursion in an untrusted-input parser), except here the untrusted input is a coin's on-chain memo/hint that a wallet parses while processing incoming coin spends (e.g. PlotNFT/pooling singleton sync).

### Finding Description
`PuzzleWithRestrictions.from_memo()` is the parser used to reconstruct an unknown custody puzzle tree from an on-chain memo blob attached to a coin: [1](#0-0) 

When the memo indicates `further_branching` (an `MofN` node), the method builds an `MofNHint` from the program and then calls `PuzzleWithRestrictions.from_memo(memo)` once **per member**, recursively, with no cap on nesting depth: [2](#0-1) 

Because `Program.from_bytes()` parses the CLVM byte-format via the fast Rust/LazyNode path with essentially no depth ceiling other than the CLVM cost limit, an attacker can encode a very deeply nested `MofN` memo structure (each level a `PuzzleWithRestrictions` wrapping another `MofN` with one member) cheaply, then attach it as the memo of a `CreateCoin` output in a spend bundle they submit. Any wallet or PlotNFT-sync client that later decodes that coin's memo — e.g. `PlotNFT.get_next_from_coin_spend()` in `chia/pools/plotnft_drivers.py`, which drives PlotNFT/pooling singleton lineage recognition from coin-spend memos — will call `PuzzleWithRestrictions.from_memo()` on attacker-controlled data and recurse to the crafted depth, hitting the interpreter's recursion limit and raising/propagating an unhandled `RecursionError` from deep within the call stack.

This is directly analogous to the NAR/CLVM-archive-parser class of bug in the CVE: a parser for a nested/tree-shaped serialized format recurses once per nesting level of attacker-controlled data with no depth bound, so the attacker controls the recursion depth and can force the process past its safe stack budget purely through parser recursion, independent of CLVM execution cost limits (the recursion happens in the Python driver code, not the metered CLVM VM).

### Impact Explanation
Because the recursion is unbounded and depth is entirely attacker-controlled via memo nesting, a single malicious spend (or configured PlotNFT/pool state) with a coin memo, once observed and parsed by a wallet performing PlotNFT/pool singleton sync, can raise a `RecursionError` deep inside the parsing/reconstruction logic. Depending on where this exception surfaces (it is not defensively caught around `from_memo` in the driver call chain shown), this can abort in-progress wallet state processing for that peer/sync batch, effectively producing a spend-triggered transaction/state-processing halt for the affected wallet client. Unlike the native-code CVE, CPython's recursion limit check generally converts this into a Python exception rather than true stack-to-heap memory corruption, so the confidentiality/integrity impact described in the CVE (arbitrary code execution) does not translate directly — the practical Chia-side impact is denial-of-service against a wallet's sync/parsing pipeline.

### Likelihood Explanation
Likelihood is moderate: the attacker only needs to construct a CLVM memo program with the expected `(spec_namespace, [nonce, restriction_hints, further_branching=1, (m, [member_memo, ...])])` shape nested to a large depth, associate it with a `CreateCoin` output, and get a victim wallet/PlotNFT client to sync/parse that coin — this requires no special privilege beyond submitting or arranging a normal transaction and does not need to pass mempool CLVM execution limits, since the recursive Python parsing occurs client-side during wallet-level memo interpretation, not during consensus-level CLVM execution.

### Recommendation
Add an explicit maximum recursion/nesting-depth check in `PuzzleWithRestrictions.from_memo()` (and the corresponding `MofNHint.from_program()` path) before recursing into `MofN` members, rejecting memos that exceed a small, fixed depth (e.g. tens of levels) with a clear `ValueError` rather than allowing unbounded Python-level recursion driven by attacker-controlled data. Alternatively, rewrite the parser to be iterative (worklist/stack-based), consistent with how `sha256_treehash` in this codebase was deliberately made non-recursive to avoid the same class of issue.

### Proof of Concept
1. Construct a memo program `M_0 = (spec_namespace, [0, [], 0, (puzhash, memo)])` representing a leaf `UnknownMember`.
2. Iteratively wrap: `M_{i+1} = (spec_namespace, [i, [], 1, (1, [M_i])])`, i.e., an `MofN` with `m=1` and a single member whose memo is `M_i`, repeated for N ≈ Python's recursion limit (or slightly beyond, since `from_memo` calls itself and several helper methods per level).
3. Place `M_N` as the memo of a `CreateCoin` condition output by any coin-spend the attacker submits (e.g., mimicking the `additional_memos`/`CreateCoin.memo_blob` pattern used by `PlotNFT`).
4. When a wallet client later calls `PlotNFT.get_next_from_coin_spend()` / `PuzzleWithRestrictions.from_memo()` on this coin's memo (as exercised by the existing negative tests in `chia/_tests/pools/test_plotnft_v2_drivers.py` and `chia/_tests/clvm/test_custody_architecture.py::test_back_and_forth_hint_parsing`, which already recurse through nested `MofN` memos), the recursive `from_memo` calls exceed the interpreter recursion limit and raise `RecursionError`, aborting parsing of that coin state.

    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):

        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(

        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)
