### Title
Unprivileged callers can force `WombatStaking.convertWOM()` to lock the contract's transient WOM balance into veWOM, freezing protocol funds for the full `lockDays` period - (File: wombat/WombatStaking.sol)

### Summary
`convertWOM(uint256 _amount)` in `wombat/WombatStaking.sol` has no access-control modifier beyond `whenNotPaused`, and it operates on `address(this)`'s own WOM balance rather than `msg.sender`'s tokens. Any unprivileged address can call it directly (bypassing the intended callers `mWOM._lockWom` and `convertAllWom`) to force any WOM sitting in the contract at that moment into a `veWom.mint(_amount, lockDays)` lock, which is only unlockable after the configured `lockDays` cooldown.

### Finding Description
`convertWOM` is defined as: [1](#0-0) 
It carries only the `whenNotPaused` modifier — no `onlyOwner`, `onlyBribeManager`, `_onlyPoolHelper`, or "only mWOM/only self" restriction is applied, unlike sibling functions such as `burnReceiptToken` (`_onlyPoolHelper`) or `vote` (manual `msg.sender != bribeManager` check) in the same file: [2](#0-1) [3](#0-2) 

The intended caller is `mWOM._lockWom`, which forwards WOM to `WombatStaking` and then calls `convertWOM` as part of a controlled flow: [4](#0-3) 
Because `convertWOM` reads `IERC20(wom).balanceOf` implicitly via `IVeWom(veWom).mint`'s internal `transferFrom(address(this), ...)` pull, and does not check `msg.sender`, an attacker can call it directly at any time the contract happens to hold any WOM balance (e.g., un-forwarded harvest/fee amounts sitting in the contract in between internal transfer steps of `_sendRewards`/`_toMasterWomAndSendReward`), forcing that balance into a fresh veWom lock for `lockDays` before the protocol's own logic intended to route it elsewhere (e.g., to `mWom` fee conversion, `feeInfo.to` recipients, or reward pools).

The `whenNotPaused` guard does not restrict caller identity, so it does not mitigate this. There is no reentrancy issue nor token theft from a specific victim — the vulnerability is a lack of caller authorization allowing state-changing manipulation of protocol-owned WOM float timing.

### Impact Explanation
This is a funds-freezing / griefing issue, not fund theft: any WOM balance transiently held by `WombatStaking` can be prematurely locked into veWom by an unprivileged actor, making it inaccessible for `lockDays` (a value settable by the owner, potentially long, e.g. up to Wombat's multi-year max lock) instead of being distributed as intended (fees, rewards, reward-pool funding). This matches the Immunefi impact class of "temporary or permanent freezing of unclaimed yield/protocol funds" since the diverted WOM is locked well beyond 24 hours and the protocol loses control over when/how that balance is used.

### Likelihood Explanation
Feasibility depends entirely on `WombatStaking` transiently holding a nonzero WOM balance when the attacker calls `convertWOM`. This can happen naturally between internal steps of harvest/fee-distribution flows, or an attacker could front-run a legitimate harvest transaction (seeing it in the mempool) and call `convertWOM(balance)` just after WOM lands in the contract but before it is routed onward. No capital is required from the attacker — the call only consumes gas since the function pulls from the contract's own balance, not the caller's. The action is repeatable any time the contract holds unlocked WOM.

### Recommendation
Restrict `convertWOM` to only be callable by trusted internal callers, e.g. add `onlyOwner`/a dedicated `onlyMWom` or `onlyPoolHelper`-style modifier, or make it `internal`/`private` and only expose the flow through `mWOM._lockWom` and an owner-gated `convertAllWom`. At minimum, require `msg.sender == mWom || msg.sender == owner()`.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatStaking` (or use existing fork setup) and configure `wom`, `veWom`, `lockDays`.
2. Simulate a state where the contract holds a nonzero WOM balance (e.g., transfer WOM directly to `WombatStaking` to mimic an in-flight harvest amount, or trigger a partial `harvest`/`_toMasterWomAndSendReward` call up to the point WOM lands in the contract).
3. From an arbitrary unprivileged address (not owner, not mWOM, not bribeManager, not poolHelper), call `wombatStaking.convertWOM(balance)`.
4. Assert the call succeeds (no revert), `IVeWom(veWom).mint` was invoked, and the contract's WOM balance decreased while a veWom lock with `lockDays` cooldown was created — demonstrating that an arbitrary address altered protocol-controlled WOM state and locked funds without holding any privileged role.
5. Assert that no modifier (`onlyOwner`, `onlyBribeManager`, `_onlyPoolHelper`, or equivalent) restricts `convertWOM`'s caller, confirming the missing access control.
