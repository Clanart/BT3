### Title
Identity (zero) encryption key and zero Schnorr PoP accepted as valid in PedPoP `EncryptedMessage` — ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
The PedPoP DKG wraps every per-message encryption key with a Schnorr proof-of-possession so an attacker cannot submit encryption keys whose discrete log they do not know. However, `EncryptedMessage::read` accepts the identity point as `key` (via `Ciphersuite::read_G`, which only enforces canonical encoding and — unlike `Curve::read_G` in `crypto/frost/src/curve/mod.rs:125-131` — performs no identity rejection), and `SchnorrSignature::verify` reduces to `R + c·A − s·G == identity`. Submitting `key = identity` together with the all-zero signature `(R = identity, s = 0)` satisfies that equation for *any* challenge, so the "unproven" zero value is treated as a fully valid proof-of-possession — a direct analog of the zero-default-root fail-open. The forged message passes both the batched PoP check in `Encryption::decrypt` (`crypto/dkg/pedpop/src/encryption.rs:479-485`) and the standalone check in `Decryption::decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:374-379`).

### Finding Description
`SchnorrSignature::batch_statements` returns `[(ONE, R), (challenge, public_key), (-s, G)]` and `verify` accepts iff the multiexp is the identity (`crypto/schnorr/src/lib.rs:88-110`). With `R = identity`, `public_key = identity`, `s = 0`, the sum is `identity + c·identity − 0·G = identity` regardless of the challenge, so no knowledge of any discrete log is demonstrated. `EncryptedMessage::read` (`encryption.rs:171-177`) reads `key` via `C::read_G`, and `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) rejects only non-canonical encodings — the identity encoding is canonical and is returned. Because the PoP challenge binds `key`, `nonce`, `sender`, and `msg` (`encryption.rs:302-324`), an attacker additionally controls the ciphertext `msg`; the ECDH step `ecdh(enc_key, identity) = identity` (`encryption.rs:95-97`) makes the ChaCha20 keystream in `cipher` (`encryption.rs:101-133`) a fixed, publicly computable stream, so the attacker chooses the exact plaintext the victim decrypts.

### Impact Explanation
In `Encryption::decrypt` (used by `KeyMachine::calculate_share`, `crypto/dkg/pedpop/src/lib.rs:476-491`), a forged `EncryptedMessage` passes the batched PoP verification and yields attacker-chosen share bytes; the attacker can thereby inject chosen plaintexts under the guise of an encrypted share without proving key possession — the exact attack the PoP exists to prevent (see the comment at `encryption.rs:83-90` describing message-forgery/blame side-effects). In `decrypt_with_proof` (the blame-adjudication path, `encryption.rs:366-397`), a forged message attributed to an arbitrary `from` participant passes the `InvalidSignature` check, and the DLEq over `[generator, identity]` → `[enc_key_pub, identity]` also verifies trivially, so the "decrypted" attacker-chosen plaintext is accepted as the accused party's message — enabling fabricated evidence in blame proceedings. (I could not fully trace how downstream coordinators consume `BlameMachine`/blame outputs, so the concrete penalty impact is uncertain; the forgery primitive itself is fully verified in the code.)

### Likelihood Explanation
Reachable by any unprivileged DKG participant sending crafted `EncryptedMessage` bytes (the message format is read from the wire via `EncryptedMessage::read`); no collusion, leaked keys, or invalid-curve input is required — only standard encodings of the identity point and a zero scalar. Exploitation of the share path is bounded by the subsequent `share_verification_statements` check against the sender's registered commitments, so the strongest concrete effect is in the blame/forgery path and the bypass of the PoK invariant.

### Recommendation
Reject the identity point in `EncryptedMessage::read` for both `key` and `pop.R` (or have `SchnorrSignature::read`/`verify` reject identity `R`/`public_key` and `s = 0`), mirroring the explicit identity rejection already implemented in `Curve::read_G` (`crypto/frost/src/curve/mod.rs:123-131`). Additionally, check `ecdh` output for identity before keying the cipher, and add regression tests asserting that `(key = identity, R = identity, s = 0)` fails `decrypt`/`decrypt_with_proof`.
