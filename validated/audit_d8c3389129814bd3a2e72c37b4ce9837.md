## Title
Permissionless Bandwidth Purchases Let an Attacker Force-Evict Any App's Paid Bandwidth Subscriptions - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth`'s `push_subscription` enforces a hard cap of `MAX_SUBSCRIPTIONS` (1024) per `(app_chain, app)` key and evicts the oldest entry on overflow — this is exactly the "hard limit on entries" remediation pattern from the external report. However, the cap is keyed by attacker-controllable `(app_chain, app)` values taken from the purchase message body, and the on-chain `purchase()` entrypoint on `BandwidthManager.sol` is fully permissionless. Any unprivileged account can therefore target a victim app's subscription queue directly and force-evict its already-paid-for bandwidth, destroying real value with no privileged access required.

### Finding Description
`pallet-bandwidth::on_accept` credits a purchase to `(msg.chain, msg.app)`, both of which are decoded straight out of the ABI-encoded request body of the purchase message, not derived from `request.source`: [1](#0-0) 

`push_subscription` appends to a `BoundedVec<Subscription, MaxSubscriptions>` capped at 1024 entries; once full, every new push evicts the single oldest entry regardless of its remaining value, and the eviction is unconditional — there is no per-caller quota, no minimum subscription size to trigger eviction, and no protection tying eviction eligibility to relative value: [2](#0-1) 

The purchase path on the EVM side (`BandwidthManager.sol::purchase`) has no access control beyond validating `app`, `chain`, `months` are non-empty/non-zero and that the tier price is non-zero — any address can call it and pay for the cheapest configured tier: [3](#0-2) 

Because `(app_chain, app)` is taken from the attacker-controlled message body rather than tied to the caller's identity, an attacker can:
1. Pick any victim `(app_chain, app)` pair that currently has valuable, unexpired subscriptions queued.
2. Repeatedly call `purchase()` for the cheapest tier, targeting that exact `(app_chain, app)` pair, until the FIFO list reaches the 1024 cap and begins evicting.
3. Continue purchasing to evict the victim's legitimate subscriptions from the front of the queue — regardless of how much bandwidth or money those subscriptions represent — since eviction always removes index `0` (oldest), not lowest-value.

The design doc itself documents the eviction path as expected behavior ("Pushing onto a full list ... evicts the oldest entry"), but the *quota is shared per-app rather than per-payer*, and any address can pay into anyone else's queue, which is the same broken invariant as the referenced report: an unbounded/uncontrolled ability for an unprivileged actor to inject entries into a table that another party's legitimate state depends on, causing that legitimate state to be pushed out.

### Impact Explanation
This directly harms a bandwidth pivot named in the task guidance: "bridged assets, order escrow, refunds, paymaster balances, relayer rewards, and bandwidth balances must move exactly once and only to the rightful beneficiary and amount." Here, a victim app's paid, unexpired bandwidth balance can be destroyed (evicted, not "moved to the rightful beneficiary") by an unrelated, unprivileged party — a genuine loss-of-funds condition, since `remaining_bytes` on the evicted subscription is unrecoverable (`SubscriptionEvicted.lost_bytes` is only an audit event, not a refund).

### Likelihood Explanation
The attack requires no privileged role, relayer, prover, or governance action — only a funded account able to call `BandwidthManager.purchase()` with the cheapest configured tier repeatedly. The economic cost scales with `cheapest_tier_price × (1024 − current_queue_length)`, which bounds but does not eliminate the attack: for apps whose queue is naturally short (most apps, since 1024 is designed as "years of headroom" under normal single-purchase-per-cycle usage) the number of purchases needed to reach the cap and begin evicting is comparatively small, and a well-funded attacker can grief a specific competitor or high-value app cheaply relative to the value being evicted.

### Recommendation
Scope the subscription-eviction quota (or at minimum an eviction-priority policy) to something the payer cannot fully control — e.g., require `request.source` (the authenticated purchasing manager/chain) to match `msg.chain`, or evict by lowest remaining value rather than strict FIFO, or require per-`(app_chain, app)` write access to be restricted to the app itself / its designated sponsor list rather than any purchaser naming an arbitrary target.

### Proof of Concept
1. Victim app `A` on `app_chain = C1` has one active subscription for the $1000/8MB tier with months remaining.
2. Attacker calls `BandwidthManager.purchase(tierOne, chain=C1, app=A, months=1)` repeatedly (paying the $50 tier each time) from any account, with no relationship to app `A` or chain `C1`.
3. Each call dispatches a `PurchaseMessage{chain: C1, app: A, tier: TierOne, months: 1}` to `pallet-bandwidth`, which calls `push_subscription(&C1, &A, TierOne, bytes, duration)`.
4. Once `Allowance::<T>::get(C1, A).len() == MAX_SUBSCRIPTIONS`, the next attacker purchase evicts index `0` — the victim's still-valuable $1000 subscription — emitting `SubscriptionEvicted { lost_bytes: <victim's remaining bytes> }`.
5. The victim's paid bandwidth is permanently lost; the attacker has spent only the marginal cost of filling/overflowing the queue, none of which is refunded to the victim. [4](#0-3)

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
