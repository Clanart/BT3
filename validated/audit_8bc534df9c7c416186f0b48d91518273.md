### Title
Unchecked `uint32`/`uint64` overflow in `compute_assert_height()` can crash spend-bundle admission via crafted relative-timelock conditions - ([File: chia/full_node/mempool_manager.py])

### Summary
`MempoolManager.validate_spend_bundle()` calls `compute_assert_height()` to resolve relative height/seconds timelocks into absolute ones by adding a coin's `confirmed_block_index`/`timestamp` to the spend's `height_relative`/`seconds_relative`/`before_*_relative` values. Each addend is individually valid (each fits in its own `uint32`/`uint64` domain), but the *sum* is re-wrapped with `uint32(...)`/`uint64(...)` without any bounds check first — directly mirroring the reported Panoptic bug where two individually valid tick values are combined into a difference that can exceed the callee's valid domain, triggering an unhandled revert.

### Finding Description
`compute_assert_height()` at `chia/full_node/mempool_manager.py:82-127` does, for every spend in the bundle: [1](#0-0) 

```python
for spend in conds.spends:
    if spend.height_relative is not None:
        h = uint32(removal_coin_records[bytes32(spend.coin_id)].confirmed_block_index + spend.height_relative)
        ret.assert_height = max(ret.assert_height, h)

    if spend.seconds_relative is not None:
        s = uint64(removal_coin_records[bytes32(spend.coin_id)].timestamp + spend.seconds_relative)
        ret.assert_seconds = max(ret.assert_seconds, s)
``` [2](#0-1) 

`spend.height_relative` and `spend.before_height_relative` are themselves `uint32`-typed fields (confirmed by the test helper constructing `SpendConditions` with `uint32(height_relative)`), and `confirmed_block_index` is a `uint32` as well: [3](#0-2) 

Each of the two operands is validated at CLVM-condition level to individually fit in `[0, 2**32-1]` (or `[0, 2**64-1]` for seconds), but their *sum* is not clamped before being fed into the `uint32(...)`/`uint64(...)` constructor. `chia_rs.sized_ints` uint types are strict (they raise on out-of-range construction, unlike Python's unbounded `int`), so a value like `confirmed_block_index = 0xFFFFFFF0` combined with `height_relative = 0xFFFFFFF0` produces a sum far above `2**32-1`, which the `uint32(...)` cast cannot represent and which raises an exception. The analogous case applies to `seconds_relative`/`timestamp` with `uint64`.

This is functionally identical to the Panoptic bug class: two individually-in-range inputs are combined arithmetically and fed into a function whose valid domain is narrower than the sum's possible range, and the failure surfaces as an uncaught exception rather than a graceful rejection code.

`compute_assert_height()` is invoked directly from the mempool admission path, reachable by any unprivileged spend-bundle submitter: [4](#0-3) 

```python
timelocks: TimelockConditions = compute_assert_height(removal_record_dict, conds)

if timelocks.assert_before_height is not None and timelocks.assert_before_height <= timelocks.assert_height:
    return Err.IMPOSSIBLE_HEIGHT_ABSOLUTE_CONSTRAINTS, None, []
```

which is itself called from `MempoolManager.validate_spend_bundle()` → `add_spend_bundle()` → `FullNode.add_transaction()` for every incoming spend bundle (mempool RPC submissions and peer-relayed transactions alike).

### Impact Explanation
If a crafted `SpendBundle` with an `ASSERT_HEIGHT_RELATIVE`, `ASSERT_BEFORE_HEIGHT_RELATIVE`, `ASSERT_SECONDS_RELATIVE`, or `ASSERT_BEFORE_SECONDS_RELATIVE` condition on a coin whose `confirmed_block_index`/`timestamp` is already large (which happens naturally as the chain grows, or trivially for old/deep coins) is submitted with a maximal relative value, the sum overflows the target sized-int type inside `compute_assert_height()`. Because this function has no bounds check or try/except around the `uint32`/`uint64` casts, and I could not confirm (within the available search budget) that `validate_spend_bundle()`/`add_spend_bundle()`/`add_transaction()` wrap this specific call in a catch-all exception handler, a raised overflow exception here risks being an unhandled error during spend-bundle admission — a transaction-processing-halt class issue reachable by any spend-bundle submitter, not just a rejected/failed transaction. Even in the best case where some outer handler swallows the exception, the practical effect is that legitimate transactions using large relative timelocks on old coins are non-deterministically rejected/crash mempool admission instead of receiving a clean `Err` code, which is itself a availability/DoS-relevant divergence from expected graceful-rejection behavior.

### Likelihood Explanation
Reaching this code path requires only:
1. An existing coin with a sufficiently large `confirmed_block_index` (or `timestamp`) — trivially true for any coin, and more easily reached as the chain grows over time or for very old coins.
2. Attaching an `ASSERT_*_RELATIVE`/`ASSERT_BEFORE_*_RELATIVE` condition with a large relative value to that coin's spend.
3. Submitting the resulting spend bundle to any full node's mempool (RPC or P2P).

No privileged access, malicious peer behavior, or race condition is needed — this is directly triggerable by a single unprivileged spend-bundle submitter. The likelihood of triggering the arithmetic overflow itself is high; the residual uncertainty is only whether an outer exception handler currently prevents propagation into an actual node crash/halt versus a milder "rejected transaction" outcome, which I could not fully verify from available context.

### Recommendation
In `compute_assert_height()`, clamp the sum before constructing the sized int, or perform the addition in unbounded Python `int` and saturate/clamp to the type's max value (or explicitly reject with an `Err` code) before re-wrapping with `uint32(...)`/`uint64(...)`:

```python
h = removal_coin_records[bytes32(spend.coin_id)].confirmed_block_index + spend.height_relative
if h > MAX_UINT32:
    # treat as "never satisfiable" / reject condition rather than overflow
    ...
else:
    ret.assert_height = max(ret.assert_height, uint32(h))
```

Apply the equivalent guard to the `seconds_relative`, `before_height_relative`, and `before_seconds_relative` branches. Additionally, audit all other call sites that add a relative offset to a previously-validated absolute value (height/timestamp) across `chia/full_node/mempool_manager.py` and `chia/consensus/block_body_validation.py` for the same unguarded-overflow pattern before re-wrapping with a sized int constructor.

### Proof of Concept
Not independently runnable within this review, but the trigger conditions are directly derivable from the code:
1. Fetch or wait for a coin whose `confirmed_block_index` is `>= 0x80000000` (or `timestamp >= 0x8000000000000000` for the seconds variant) — this occurs naturally for coins confirmed late enough in chain history.
2. Construct a `SpendBundle` spending that coin with a puzzle output condition `(ASSERT_HEIGHT_RELATIVE 0x80000000)` (or the seconds/before-height/before-seconds equivalents) such that `confirmed_block_index + height_relative > 0xFFFFFFFF`.
3. Submit the spend bundle to `FullNode.add_transaction()` (e.g., via the wallet RPC `push_tx` or the P2P `RespondTransaction` message).
4. Observe that `MempoolManager.validate_spend_bundle()` → `compute_assert_height()` computes `confirmed_block_index + spend.height_relative` and passes it to `uint32(...)`, which raises rather than returning a controlled `Err.*` result, in contrast to the graceful `Err.ASSERT_HEIGHT_RELATIVE_FAILED`/`Err.ASSERT_HEIGHT_ABSOLUTE_FAILED` outcomes exercised by the existing `test_condition` overflow test cases (which only cover the Rust-side `check_time_locks` overflow handling with `nowrap=True`, not the Python-side `compute_assert_height` pre-check performed earlier in the admission pipeline).

def compute_assert_height(
    removal_coin_records: dict[bytes32, CoinRecord],
    conds: SpendBundleConditions,
) -> TimelockConditions:
    """
    Computes the most restrictive height- and seconds assertion in the spend bundle.
    Relative heights and times are resolved using the confirmed heights and
    timestamps from the coin records.
    """

    ret = TimelockConditions()
    ret.assert_height = uint32(conds.height_absolute)
    ret.assert_seconds = uint64(conds.seconds_absolute)
    ret.assert_before_height = (
        uint32(conds.before_height_absolute) if conds.before_height_absolute is not None else None
    )
    ret.assert_before_seconds = (
        uint64(conds.before_seconds_absolute) if conds.before_seconds_absolute is not None else None
    )

    for spend in conds.spends:
        if spend.height_relative is not None:
            h = uint32(removal_coin_records[bytes32(spend.coin_id)].confirmed_block_index + spend.height_relative)
            ret.assert_height = max(ret.assert_height, h)

        if spend.seconds_relative is not None:
            s = uint64(removal_coin_records[bytes32(spend.coin_id)].timestamp + spend.seconds_relative)
            ret.assert_seconds = max(ret.assert_seconds, s)

        if spend.before_height_relative is not None:
            h = uint32(
                removal_coin_records[bytes32(spend.coin_id)].confirmed_block_index + spend.before_height_relative
            )
            if ret.assert_before_height is not None:
                ret.assert_before_height = min(ret.assert_before_height, h)
            else:
                ret.assert_before_height = h

        if spend.before_seconds_relative is not None:
            s = uint64(removal_coin_records[bytes32(spend.coin_id)].timestamp + spend.before_seconds_relative)
            if ret.assert_before_seconds is not None:
                ret.assert_before_seconds = min(ret.assert_before_seconds, s)
            else:
                ret.assert_before_seconds = s

    return ret
```
