### Title
Untrusted length prefix in `SchnorrAggregate::read` allows memory-exhaustion DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::<C>::read` in `crypto/schnorr/src/aggregate.rs` trusts a 4-byte little-endian count and then reads that many group elements from the reader, appending each to a `Vec<C::G>`. This is the same bug class as CVE-2024-33781 (MP-SPDZ `octetStream::get_bytes`): a deserialization routine processes an attacker-controlled length with no bound, letting a crafted input drive unbounded work/allocation and cause a denial of service.

### Finding Description
At `crypto/schnorr/src/aggregate.rs:77-88`:

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    #[allow(non_snake_case)]
    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }

    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

Two issues combine here:

1. `len` is a full `u32`, so a single message can claim up to ~4.3 billion `Rs`. The loop pushes one `C::G` per iteration into `Rs` with no cap, so the `Vec` grows linearly with attacker-supplied data with no protocol-level bound (an honest aggregate signature only ever contains a handful of `Rs`).
2. Unlike the bounded readers elsewhere in the tree (e.g., `Commitments::read` in `crypto/dkg/pedpop/src/lib.rs:110-128`, which is capped by `params.t()`, or the `TRANSACTION_SIZE_LIMIT` check in `coordinator/src/tributary/transaction.rs`), `SchnorrAggregate::read` performs no sanity check against an expected signature count before consuming the count.

An unprivileged party can reach this by feeding crafted bytes to `SchnorrAggregate::read` (a public deserialization API in the in-scope `schnorr` crate) — the serialized form is `u32 len || len * G || F`, fully attacker-controlled.

### Impact Explanation
Denial of service. A message claiming ~4 billion nonces forces the host to attempt reading/decoding ~4 billion curve points; every byte of attacker-supplied input that successfully decodes grows `Rs`, enabling heap exhaustion proportional to attacker bandwidth, and `verify` then iterates `keys_and_challenges`-equivalent work over that `Vec`. This mirrors the CVE's DoS-only impact (CVSS 7.5, `A:H`).

### Likelihood Explanation
Any deployment that deserializes `SchnorrAggregate` from network-supplied or otherwise untrusted bytes exposes this path with a single short prefix (`[0xff, 0xff, 0xff, 0xff]`). No special positioning is required beyond the ability to submit a byte blob to a `read`/`verify` entry point.

### Recommendation
Cap the nonce count before the loop: either accept an expected length parameter (the number of aggregated signatures is always known to the caller, as `verify` already requires `self.Rs.len() == keys_and_challenges.len()`), or enforce a hard maximum constant. Pre-size with `Vec::with_capacity(len)` only after the bound check, and reject counts exceeding it with `io::Error::other`.

### Proof of Concept
Conceptual: construct `payload = u32::MAX.to_le_bytes() || <u32::MAX repetitions of a valid C::G encoding> || <valid C::F encoding>` and pass it to `SchnorrAggregate::<C>::read(&mut payload.as_slice())`. Each decoded point is pushed to `Rs`, growing heap usage linearly in attacker-provided input with no bound — matching the CVE-2024-33781 pattern of a trusted length field driving unbounded consumption.

Caveat: I verified `crypto/schnorr/src/aggregate.rs:77-88` directly. Other in-scope readers I inspected (`Commitments::read`, `EncryptedMessage::read`, `SecretShare::read`, `SignData::read` in coordinator) are bounded by `params.t()` or small fixed widths, so `SchnorrAggregate::read` is the strongest reachable analog. Whether `SchnorrAggregate::read` is actually invoked on untrusted bytes by Serai's own processor/coordinator paths was not fully traced; if it is only ever used on already-validated data, the reachable impact drops accordingly.
