### Title
Internal panic stack traces are embedded in the transaction result Log returned to any transaction submitter - (File: sei-cosmos/baseapp/recovery.go)

### Summary
When a Cosmos SDK message handler, ante handler, or OCC-scheduled execution panics for any reason other than out-of-gas, OCC abort, or context cancellation, `newDefaultRecoveryMiddleware` wraps the raw panic value together with the full Go runtime stack trace (`debug.Stack()`) into the error message that becomes the transaction's `Log`/`RawLog` field, which is returned directly in the `CheckTx`/`DeliverTx`/`broadcast_tx_*` RPC response to the client who submitted the transaction.

### Finding Description
`newDefaultRecoveryMiddleware` in `sei-cosmos/baseapp/recovery.go` is the last-resort recovery handler in the `runTx` recovery chain (alongside `newOutOfGasRecoveryMiddleware`, `newOCCAbortRecoveryMiddleware`, and `newContextCancelledRecoveryMiddleware`). For any panic not matched by the more specific handlers, it produces: [1](#0-0) 

```go
handler := func(recoveryObj interface{}) error {
    return sdkerrors.Wrap(
        sdkerrors.ErrPanic, fmt.Sprintf(
            "recovered: %v\nstack:\n%v", recoveryObj, string(debug.Stack()),
        ),
    )
}
```

This is not a log-only artifact — the returned `error` from `processRecovery` becomes the `error` result of `runTx`, which the ABCI layer surfaces as the transaction result's error string (`Log`/`RawLog`). Any client that submits a transaction that trips an unhandled panic anywhere in the message/ante execution path (a malformed message, an edge-case input to a Cosmos module or a Cosmwasm/EVM precompile call, etc.) will receive this full stack trace — including absolute Go source file paths, package names, and goroutine internals of the node — directly in the RPC response body. The equivalent middleware also exists in the legacy ABCI path at `app/legacyabci/recovery.go`: [2](#0-1) 

This mirrors exactly the bug class in the reported advisory (GHSA-9wxj-37p8-49ff / CVE-2020-11883): an unexpected/malformed request triggers an exception whose stack trace (with absolute file paths and module names) is disclosed back to the requester — CWE-200/CWE-209.

By contrast, other recovery paths in the codebase correctly separate "log the stack" from "respond to client": the EVM JSON-RPC HTTP server's `recoverAndLogHandler` logs the stack via `logger.Error(..., "stack", string(debug.Stack()))` but only returns `err.Error()` (no stack) to the caller via `writeError`: [3](#0-2) 

The baseapp `runTx` default recovery middleware does not follow this same separation — it puts the stack directly into the error value that ends up client-visible.

### Impact Explanation
Any unprivileged transaction sender (including EVM contract deployers/callers whose transactions are routed through the same `runTx`/ante pipeline, CosmWasm message senders, tokenfactory/bank message senders, etc.) who can trigger a panic in msg/ante execution receives the node's internal Go stack trace, including absolute file paths and internal package/module names, in the transaction response. This is an information-disclosure vulnerability (CWE-200/CWE-209) that aids further attacks by revealing internal code structure, build paths, and potentially version/module information useful for crafting more targeted exploits against the validator/full-node software — matching the "Medium" severity and impact class of the referenced advisory. It does not by itself cause fund loss, inflation, or chain halt, but it is a genuine reachable information disclosure on a public transaction-submission path.

### Likelihood Explanation
Likelihood is limited by needing to first find/trigger an unhandled panic condition in message or ante-handler execution that isn't already caught by the more specific `OutOfGas`, `OCCAbort`, or context-cancellation middlewares. Such panics are a routine occurrence in large module surfaces (edge cases, nil dereferences, type assertion panics, index-out-of-range, etc.) and historically recur in Cosmos-SDK-based chains, so the reachable trigger set is broad even though a specific panic-inducing input needs to be found per-endpoint.

### Recommendation
Split the panic-recovery behavior so that: (1) the full stack trace is logged server-side only (as already done in the EVM JSON-RPC HTTP handler), and (2) the error value propagated into the transaction's `Log`/`RawLog` field (and any client-facing CheckTx/DeliverTx response) contains only a generic, non-sensitive message (e.g., `"internal error"` plus a wrapped `sdkerrors.ErrPanic` code), without `debug.Stack()` content or the raw panic value's internal details. Apply the same fix to the duplicate handler in `app/legacyabci/recovery.go`.

### Proof of Concept
1. Submit any transaction that causes an unhandled panic somewhere in message execution or the ante chain that isn't an out-of-gas panic, an OCC abort, or a context-cancellation panic (e.g., a module/precompile bug causing a nil pointer dereference or index-out-of-range on adversarial input).
2. Observe the `CheckTx`/`DeliverTx` (or `broadcast_tx_commit`/`broadcast_tx_sync`) RPC response: its `Log`/`RawLog` field contains `"recovered: <panic value>\nstack:\n<full runtime stack trace>"`, exposing absolute file paths and internal Go package/function names from `sei-cosmos/baseapp/recovery.go:113-123`.
