### Title
First-staker-after-empty-pool can seize entire queued reward pot via 1-wei deposit - (`rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool._provisionReward` checks `this.totalStaked() == 0` to decide whether to accumulate rewards into `queuedRewards` or distribute them via `rewardPerTokenStored`. If rewards are queued while the pool is empty and an attacker becomes the sole staker with a dust amount (e.g. 1 wei) before the next `queueNewRewards`/`donateRewards` call, the entire queued balance plus the new reward gets divided by the attacker's dust stake, letting the attacker claim (almost) the whole reward pot.

### Finding Description
`_provisionReward` in `rewards/BaseRewardPool.sol` [1](#0-0)  works as follows:
- If `totalStaked() == 0`, the incoming reward is simply added to `rewardInfo.queuedRewards` and no `rewardPerTokenStored` update happens.
- Once `totalStaked() != 0`, any accumulated `queuedRewards` is combined with the new reward and divided by `totalStaked()` to update `rewardPerTokenStored`.

`totalStaked()` reads the actual staking-token balance held by `MasterMagpie` (`IERC20(stakingToken).balanceOf(operator)`) [2](#0-1) , and `MasterMagpie.deposit`/`_deposit` places no minimum-amount restriction — any `_amount`, including `1` wei, is accepted and simply added to `user.amount`/`user.available` and transferred in [3](#0-2) .

Exploit flow:
1. All existing stakers withdraw from the pool for a given `stakingToken`, so `totalStaked() == 0`.
2. A reward manager calls `queueNewRewards` (a normal, expected periodic action, not a malicious one) while the pool is empty — reward gets fully placed into `rewardInfo.queuedRewards` per the `totalStaked()==0` branch.
3. The attacker (unprivileged EOA) calls `MasterMagpie.deposit(stakingToken, 1)`, becoming the sole staker with `totalStaked() == 1`.
4. On the next `queueNewRewards`/`donateRewards` call (by the manager or even the attacker themselves via the permissionless `donateRewards`), `_provisionReward` computes `rewardPerTokenStored += (queuedRewards + newReward) * 10**decimals / 1`, an enormous per-token value.
5. Attacker's `earned()` = `balanceOf(attacker) * (rewardPerToken - paid) / 10**decimals` = `1 * (queuedRewards+newReward)*10**decimals / 10**decimals` = `queuedRewards + newReward`, i.e. the attacker's dust stake nets essentially the *entire* reward, deprived from the legitimate stakers whose deposits generated the historical `queuedRewards`.
6. Attacker calls `getReward` (via `MasterMagpie`) and withdraws, realizing the theft, then withdraws their 1 wei stake.

No modifier or accounting in `BaseRewardPool` protects against this: `queueNewRewards`/`donateRewards` have no minimum-stake or time-lock requirement, `_provisionReward` naively assumes whoever holds `totalStaked()` at the time of the call deserves the full queued reward, and there's no per-staker proportional carry-forward of `queuedRewards` accrued while they were not staked.

### Impact Explanation
Direct theft of user/protocol funds: legitimate reward tokens intended for distribution to future/returning stakers are instead captured almost entirely by an attacker with a negligible (1 wei) stake, violating reward conservation. This matches Immunefi's "Direct theft of user funds" / "theft of unclaimed yield" impact class.

### Likelihood Explanation
Requires: (a) a period where `totalStaked()==0` for the specific staking-token pool (plausible for smaller/less popular Wombat pools, or transiently for any pool between full-exit and re-entry), (b) a manager/keeper call to `queueNewRewards` during that window (a normal, non-malicious operational event), and (c) the attacker front-running/timing a 1-wei `deposit` before the next reward provisioning call. `donateRewards` is permissionless, so the attacker can even self-trigger the final distribution step once queued rewards exist and they hold the dust stake, removing dependence on manager timing for that last step. No privileged role is required by the attacker; capital cost is negligible (1 wei of staking token plus gas).

### Recommendation
Do not let a zero-totalStaked snapshot allow a later dust-staker to claim historically queued rewards. Options: (1) require a minimum meaningful stake (relative to reward magnitude) before `_provisionReward` distributes accumulated `queuedRewards`, e.g., only flush `queuedRewards` when `totalStaked()` exceeds a sane threshold; (2) track `queuedRewards` per accrual epoch and vest them gradually (e.g., over a streaming window) rather than crediting them instantly and fully to whoever is first to re-stake; (3) disallow reward-affecting state to be based on a single-block `totalStaked()` snapshot — instead require the reward to be distributed pro-rata over time using a rate-based accounting model resistant to point-in-time dust manipulation.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `BaseRewardPool` for a staking token, register a reward token, add a manager.
2. Users A and B deposit `100e18` staking tokens each; manager calls `queueNewRewards(1000e18, rewardToken)`; `rewardPerTokenStored` updates normally; A and B claim/verify normal accrual.
3. A and B fully withdraw so `totalStaked() == 0`.
4. Manager calls `queueNewRewards(500e18, rewardToken)` — assert `rewards[rewardToken].queuedRewards == 500e18` and `rewardPerTokenStored` unchanged.
5. Attacker calls `masterMagpie.deposit(stakingToken, 1)`.
6. Manager (or attacker via `donateRewards`) calls `queueNewRewards(1, rewardToken)` (minimal new reward) — assert `rewardPerTokenStored` jumps to reflect `(500e18+1)*10**decimals`.
7. Attacker calls `getReward` and asserts received reward `~= 500e18`, i.e., nearly all of the reward queued while A and B were the contributing stakers, despite holding only 1 wei stake.
8. Assert A and B, upon any future re-stake, get 0 share of that queued reward — demonstrating the loss/misappropriation.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
```
