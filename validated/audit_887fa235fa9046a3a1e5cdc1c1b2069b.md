### Title
Out-of-range participant index in PedPoP blame handling panics the host - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Like CVE-2016-9802 (a crash reachable by feeding a corrupted input to `btmon`), Serai's PedPoP DKG blame-evaluation path indexes `HashMap`s with attacker-influenced `Participant` values instead of validating them. `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` (`encryption.rs:388`) before any bounds check, and `BlameMachine::blame_internal` evaluates `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`). `enc_keys` and `commitments` only ever contain keys for participants `1..=n` (populated in `Decryption::register` / `AdditionalBlameMachine::new` at `lib.rs:656-660`), so any `sender` or `recipient` index outside that range causes an uncontrolled `HashMap` indexing panic — a crash rather than an `Err`, directly analogous to the buffer over-read crash in the external report.

### Finding Description
`blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-609`) accepts `sender` and `recipient` `Participant` values and an `EncryptedMessage` plus optional `EncryptionKeyProof`, all of which are derived from untrusted accusation data (in the coordinator, an `InvalidDkgShare` transaction carries arbitrary `accuser`/`faulty` `Participant` fields parsed with only a non-zero check at `coordinator/src/tributary/transaction.rs:346-354`). The path:

1. `decrypt_with_proof` (`encryption.rs:366`) verifies `msg.pop` — a Schnorr signature the accuser can produce for any `from`/`sender` bytes, since `pop_challenge` (`encryption.rs:302-324`) only mixes attacker-known public data.
2. If `proof` is `Some`, line 388 builds `&[self.enc_keys[&decryptor], *proof.key]` — `enc_keys` was only populated for `1..=n`, so `recipient` (the `decryptor`) being `0`-checked-but-`>n` or simply absent panics.
3. If the pop verifies and the decrypted share is a canonical scalar, `blame_internal` evaluates `self.commitments[&sender]` (`lib.rs:599`), panicking for any `sender` outside `1..=n`.

Neither call site returns `PedPoPError`; both panic the thread.

### Impact Explanation
An unprivileged participant (or anyone able to submit an accusation carrying `Participant` indexes) can crash the process evaluating blame — in the coordinator this halts DKG/share-blame processing, aborting key generation and potentially stalling the validator set. This is a remote, input-triggered denial of service, matching the CVE's class and severity (Medium, availability-only).

### Likelihood Explanation
High reachability: `blame`/`AdditionalBlameMachine::blame` are `pub` APIs designed to consume accusation messages from counterparties, and `Participant` values arrive from serialized transactions with no `<= n` validation. The only requirement is a syntactically valid `EncryptedMessage` PoP, which is computable entirely from public data (choose `key = k*G`, sign the `pop_challenge` with `k`).

### Recommendation
Replace infallible `HashMap` indexing with checked lookups: in `decrypt_with_proof` use `self.enc_keys.get(&decryptor)` returning `DecryptionError`, and in `blame_internal` use `self.commitments.get(&sender)` returning the accusation as invalid/unattributable rather than panicking. Also validate `sender` and `recipient` against `1..=n` at the top of `blame_internal` before any map access.

### Proof of Concept
```rust
// n = 2 participants, AdditionalBlameMachine built over valid commitments for 1..=2
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 2, commitment_msgs).unwrap();

// Attacker-controlled accusation: recipient index 5 is not a DKG participant
let key_scalar = Zeroizing::new(<Ristretto as Ciphersuite>::random_nonzero_F(&mut OsRng));
let pub_key = <Ristretto as Ciphersuite>::generator() * key_scalar.deref();
let nonce = Zeroizing::new(<Ristretto as Ciphersuite>::random_nonzero_F(&mut OsRng));
let pub_nonce = <Ristretto as Ciphersuite>::generator() * nonce.deref();
// EncryptedMessage with a self-made, validly-verifying PoP over the untrusted `from` index
let msg = EncryptedMessage::<Ristretto, SecretShare<_>> {
  key: pub_key,
  pop: SchnorrSignature::sign(&key_scalar, nonce,
    pop_challenge(context, pub_nonce, pub_key, sender, &share_bytes)),
  msg: Zeroizing::new(SecretShare(share_bytes)),
};

// Panics at crypto/dkg/pedpop/src/encryption.rs:388 — `self.enc_keys[&decryptor]`
// has no entry for recipient = Participant(5)
machine.blame(Participant::new(1).unwrap(), Participant::new(5).unwrap(), msg, Some(proof));
```
Equivalently, `sender = Participant(5)` with a canonical decrypted share panics at `crypto/dkg/pedpop/src/lib.rs:599` on `self.commitments[&sender]`.

Caveat: I did not trace the coordinator's dispatch of `InvalidDkgShare` into `AdditionalBlameMachine::blame` to confirm the transaction `faulty`/`accuser` fields flow in unchecked, so reachability from on-chain data is inferred rather than fully verified; the panic sites themselves (`encryption.rs:388`, `lib.rs:599`) are confirmed in the in-scope `crypto/dkg/pedpop` crate.
