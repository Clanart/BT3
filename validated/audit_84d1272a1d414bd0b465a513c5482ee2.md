### Title
Same-chain fill loop only releases escrow for the first `outputs.length` inputs, permanently locking excess escrowed input tokens once the order is finalized - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` mirrors the reported AuraSpell bug class: a loop/condition that is supposed to fully account for all legs of a multi-asset operation instead only covers a subset, so the "extra" side is silently skipped while the function proceeds to completion and finalizes state as if everything succeeded.

### Finding Description
`_fillSameChain` iterates over `order.output.assets` (`outputsLen = order.output.assets.length`) and, for each output index `i`, computes an escrowed release amount keyed off `order.inputs[i]` — the **same index** `i`: [1](#0-0) [2](#0-1) 

The escrow release array (`escrowedInputs`) is sized to `outputsLen`, not `order.inputs.length`: [3](#0-2) 

If an order has more inputs than outputs (`order.inputs.length > order.output.assets.length`), any input token at an index `>= outputsLen` is never referenced anywhere in the fill loop, so it is never added to `escrowedInputs` and never passed to `_withdraw`: [4](#0-3) 

Once all outputs are filled, `isFullyFilled` is true and `_withdraw` is called with `finalize=true`, which sets `_filled[commitment] = beneficiary` inside `_withdraw`: [5](#0-4) 

Once `_filled[commitment]` is non-zero, the user can no longer cancel the order to reclaim leftover escrow — `_cancelSameChain` is the only other path that returns escrowed input tokens, and it does not check `_filled` status here for the untouched leftover tokens (and in practice, once finalized, this flow is designed as a terminal state). The excess escrowed input token(s) at index `>= outputsLen` remain keyed in `_orders[commitment][token]` in storage with no remaining code path that ever reads or transfers them out, permanently locking those funds in the contract, functionally identical to the AuraSpell bug where `poolAmountOut` from one leg is silently dropped by a check that only accounts for a subset of the legs while the rest of the function proceeds to completion.

This mirrors the reported bug's core invariant break: *a function that is supposed to fully process N legs of a multi-asset structure only processes a subset (bounded by the wrong length/index), and the code proceeds normally without reverting, leaving the user believing the operation completed correctly while part of their value is unaccounted for.*

### Impact Explanation
This causes permanent loss/lock of user escrowed funds for any order where `inputs.length > output.assets.length` gets fully filled — the excess input tokens can never be withdrawn by the user or released to the solver. This falls under "stealing or loss of funds" for the Hyperbridge bounty gate.

### Likelihood Explanation
Likelihood depends entirely on whether `placeOrder` (or any earlier validation layer) enforces `order.inputs.length == order.output.assets.length`. I was unable to locate such a check in the portions of `IntentGatewayV2.sol` / `IntentsBase.sol` I reviewed. If no such check exists, any ordinary user (not a malicious peer/relayer) constructing a legitimate multi-input, fewer-output order (e.g., splitting collateral across two tokens to receive one output token) would trigger this unprivileged, single-transaction fund lock without any attacker collusion required.

### Recommendation
- Add an explicit invariant check in `placeOrder`/order validation requiring `order.inputs.length == order.output.assets.length` for same-chain orders, OR
- Rework `_fillSameChain` to release ALL of `order.inputs` proportionally to total fill progress across the whole order (not indexed 1:1 against `output.assets`), independent of `outputsLen`.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [TokenA: 1000, TokenB: 500]` and `order.output.assets = [TokenC: 900]` (2 inputs, 1 output — no on-chain check observed preventing this).
2. Escrow is recorded for both TokenA and TokenB under the commitment: `_orders[commitment][TokenA] = 1000`, `_orders[commitment][TokenB] = 500`.
3. A solver calls `fillOrder` supplying `solverAmount = 900` for `TokenC` (index 0). The loop in `_fillSameChain` runs for `i = 0` only (`outputsLen = 1`), computing `escrowedAmount` from `order.inputs[0]` (TokenA) only; `escrowedInputs` has length 1.
4. `isFullyFilled = true` → `_withdraw(..., finalize=true)` is called, which sets `_filled[commitment] = solver`, releasing only the TokenA escrow.
5. The 500 TokenB remains in `_orders[commitment][TokenB]` in contract storage forever — no remaining function iterates index 1 for this commitment, and the order is already finalized so `_cancelSameChain`'s authorization/state checks make recovery of that leg unreachable through the normal flow.
