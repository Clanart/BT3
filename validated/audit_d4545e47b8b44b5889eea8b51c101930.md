### Title
Missing pagination on comment-reactions fetch lets non-author reaction flooding suppress the author's "-1" veto in `autoCloseDuplicates`, causing unintended auto-close - ([File: scripts/auto-close-duplicates.ts])

### Summary
`autoCloseDuplicates` fetches the reactions on the bot's duplicate-detection comment with a single, unpaginated GitHub API call and then searches that list for the issue author's `-1` reaction to decide whether to skip auto-closing. Because the request has no `per_page`/pagination handling, GitHub's default page size (30) caps the result, so if enough reactions are added by other (unprivileged) users before the author reacts, the author's actual `-1` reaction can fall outside the fetched page and the veto is silently ignored.

The reactions endpoint is called with no pagination parameters at all: [3](#0-2) 

Compare with `githubRequest`, which is a generic single-shot fetch with no built-in pagination loop: [4](#0-3) 

Elsewhere in the same script, the author explicitly implements pagination loops (for issues) because they are aware the GitHub API paginates results (default page size 30, capped via `per_page`): [5](#0-4) 

...but this pagination discipline was not applied to the reactions (or comments) fetch. GitHub's reactions listing API defaults to 30 items per page and returns items in ascending creation order. Any unprivileged GitHub user can react to a public issue comment (as documented in the operator flow itself — `comment-on-duplicates.sh` tells users to "👎 this comment" to block auto-closure): [6](#0-5) 

Exploit flow: once the bot posts the "Found N possible duplicate issues" comment, an attacker (not the issue author, no special privileges — just ordinary GitHub accounts) reacts to that specific comment with ≥30 reactions (any content values) before the true author gets around to reacting with 👎. When the author's `-1` reaction is eventually added, it becomes the 31st+ reaction and is returned only on page 2+ of the reactions endpoint. Because `autoCloseDuplicates` only fetches page 1 (no `per_page`/pagination), the `reactions` array it evaluates never contains the author's `-1`, so `authorThumbsDown` evaluates to `false` even though the author truly disagreed. This lets `closeIssueAsDuplicate` execute against the author's expressed intent — a real bypass of the "deny means deny" invariant, achievable purely from ordinary/unprivileged GitHub activity (reacting to a public comment), with no need to spoof `user.id` or forge non-enum `content` values (which is correctly not possible, since GitHub restricts reaction `content` to a fixed enum making the "near-miss content string" and "spoofed id" variants in the original question not exploitable).

### Impact Explanation
This is an automation/trust-boundary bypass: an unprivileged third party can force an automated GitHub Action to close another user's issue (state change + `duplicate` label + closing comment) against that user's explicit, GitHub-native objection, purely through public reactions requiring no write access to the repo. This matches an "unauthorized state-changing action via automation flow" / "approval bypass" style impact for the auto-close bot.

### Likelihood Explanation
Feasibility requires only that an attacker control or recruit ≥30 GitHub accounts (or coordinate ≥30 distinct reactors) to react to the bot's comment before the real author posts their veto reaction, and that the author's veto arrive after those 30 have accumulated. This is a real precondition (bulk reactions), but well within reach of a determined unprivileged actor and is fully repeatable — the auto-close job runs on a schedule (3-day window) giving ample time to stage the flood.

### Recommendation
Paginate the reactions request (and the comments request) the same way `allIssues` is paginated — loop with `per_page=100` and `page` until an empty page is returned, aggregating all reactions before evaluating `authorThumbsDown`. Alternatively/additionally, use the issue/comment's aggregated `reactions` totals count field to detect when more pages exist and fail safe (skip auto-close) rather than assume a single page is complete.

### Proof of Concept
Unit test plan for `autoCloseDuplicates`/its reactions-fetch helper:
1. Mock `githubRequest` for the reactions endpoint to return exactly 30 reactions from 30 distinct non-author user IDs (page 1 full), and assert the code makes no follow-up call to fetch page 2.
2. Add the real author's `{user: {id: issue.user.id}, content: "-1"}` as reaction #31 (simulate it living on page 2, which the mock returns only if called with `page=2`).
3. Run the guard logic and assert `authorThumbsDown` evaluates `false` and `closeIssueAsDuplicate` is invoked — demonstrating the false negative.
4. Fix validation: after patching in full pagination, rerun the same mocked sequence (page1 + page2) and assert `authorThumbsDown` is `true` and `closeIssueAsDuplicate` is never invoked, confirming the "deny means deny" invariant holds once pagination is complete.

async function githubRequest<T>(endpoint: string, token: string, method: string = 'GET', body?: any): Promise<T> {
  const response = await fetch(`https://api.github.com${endpoint}`, {
    method,
    headers: {
      Authorization: `Bearer ${token}`,
      Accept: "application/vnd.github.v3+json",
      "User-Agent": "auto-close-duplicates-script",
      ...(body && { "Content-Type": "application/json" }),
    },
    ...(body && { body: JSON.stringify(body) }),
  });

  if (!response.ok) {
    throw new Error(
      `GitHub API request failed: ${response.status} ${response.statusText}`
    );
  }

  return response.json();
}
