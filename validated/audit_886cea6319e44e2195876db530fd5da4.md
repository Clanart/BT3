## Analysis

The external report's bug class is: two mutating entry points share/forget to update a piece of auxiliary state (`stakersVaults`) that a later function depends on to correctly account for the resource, causing desync between the "shares" ledger and the tracking array used for withdrawal/removal.

The closest reachable analog in this Cosmos EVM repository is in the stateful-precompile balance-tracking mechanism (`precompiles/common/balance_handler.go`), which multiple production precompiles (staking, distribution, gov, ics20, erc20, slashing) rely on to reconcile native `x/bank`/`x/precisebank` events with the EVM `StateDB`.

### Title
Shared/stale `BalanceHandler.prevEventsLen` across nested precompile calls desyncs EVM `StateDB` balances from native bank balances - (File: precompiles/common/balance_handler.go, precompiles/common/precompile.go)

### Summary
`BalanceHandler` records `prevEventsLen := len(ctx.EventManager().Events())` in `BeforeBalanceChange`, then in `AfterBalanceChange` re-parses `events[prevEventsLen:]` to translate `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` bank events into `StateDB.AddBalance`/`SubBalance` calls [1](#0-0) . Several production precompiles hold a single `BalanceHandler` obtained via `p.GetBalanceHandler()` on the `Precompile` struct rather than instantiating a fresh handler scoped to each individual precompile invocation [2](#0-1) . When a contract triggers a nested/recursive precompile call within the same EVM transaction (precompile → `CallEVMWithData` → back into the same or another stateful precompile), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, corrupting the window the outer call's `AfterBalanceChange` uses to slice events.

### Finding Description
`RunNativeAction`/`Run` for stateful precompiles wraps native Cosmos SDK keeper calls (bank sends, staking delegate/undelegate, distribution withdraw, IBC transfer, etc.) and afterwards drains the SDK event log to mirror the resulting native balance changes into the EVM `StateDB` via `BeforeBalanceChange`/`AfterBalanceChange` [3](#0-2) . This exact mechanism, and the "shared instance" hazard, is explicitly reproduced and documented by an in-repo regression test:

- `evmd/tests/integration/balance_handler/balance_handler_test.go` — "BalanceHandlerTestSuite tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [4](#0-3) 
- A companion test file explicitly frames this as a bug where "reverted distribution calls leave persistent bank events that are incorrectly aggregated" [5](#0-4) 
- The debug precompile used to reproduce it demonstrates the exact recursive pattern: a Solidity contract calls the precompile, which internally calls `CallEVMWithData` back into the EVM/precompile before returning [6](#0-5) , and its `BeforeBalanceChange`/`AfterBalanceChange` pair operates on a shared `BalanceHandlerFactory`/`BalanceHandler` field exactly like the real bank/staking/distribution/gov/ics20/erc20 precompiles that call `p.GetBalanceHandler()`.

This is structurally identical to the source report's bug class: an auxiliary bookkeeping value (`prevEventsLen`, analogous to `stakersVaults`) is mutated by an "inner" call path without properly scoping/restoring it for the "outer" caller, so the outer caller's accounting step (slicing events to update balances, analogous to `removeVaultFromStaker`) operates on the wrong data window. The result is that `AfterBalanceChange` can re-process events already consumed by the inner call (double counting a `CoinReceived`/`CoinSpent` event, duplicating a credited/debited amount in `StateDB`) or skip events belonging to the outer call (dropping a balance change), producing a divergence between the authoritative native bank ledger and the EVM-visible balance used for all subsequent EVM operations (transfers, gas payment accounting, `eth_getBalance`, contract logic) within that block.

### Impact Explanation
Because `StateDB.AddBalance`/`SubBalance` are driven off a mis-sliced event window, an EVM balance can be credited or debited incorrectly relative to the real `x/bank`/`x/precisebank` state. This is a state-consistency/accounting-corruption issue matching the "Critical unauthorized minting, burning, duplication, or irreversible accounting corruption of spendable user value across ... EVM balances" impact class, since it is reachable purely through ordinary unprivileged contract call flows (a normal contract recursively invoking a stateful precompile — staking, distribution, gov, ics20, erc20/bank precompiles all use this same `BalanceHandler` plumbing).

### Likelihood Explanation
Likelihood is asserted as Low/Medium by the codebase's own author-added regression tests, which indicates the team is aware of and actively investigating this exact scenario, but I could not fully confirm from the available index whether this defect has already been patched in `GetBalanceHandler()`'s current implementation (i.e., whether it now returns a call-scoped handler instead of a shared field) versus the legacy pattern shown in the test precompile (`testutil/testdata/debug/debug.go`, `evmd/tests/testdata/debug/debug.go`). The tests exist specifically to exercise recursive-precompile-call balance desync, but I was not able to retrieve the full body/assertions of `GetBalanceHandler()` in `precompiles/common/precompile.go` or the exact non-test wiring for `distribution.go`, `erc20.go`, `gov.go`, `ics20.go`, `slashing.go`, `staking.go` to confirm whether the shared-instance hazard is still live in the current production code path, or whether these tests currently pass (validating a fix) or fail (documenting an open bug).

### Recommendation
Ensure `BalanceHandler` (and `prevEventsLen`) is allocated fresh per precompile invocation (as the newer `BalanceHandlerFactory.NewBalanceHandler()` pattern in `precompiles/common/precompile.go` does [7](#0-6) ) rather than stored as mutable shared state accessed via `p.GetBalanceHandler()` on the long-lived `Precompile` struct, and add re-entrancy/nesting guards so that a nested precompile call's event-window bookkeeping cannot clobber the enclosing call's bookkeeping.

### Proof of Concept
The existing regression test `TestRecursivePrecompileCallsWithDebugPrecompile` is a ready-made PoC: it deploys `DebugPrecompileCaller.sol`, which recursively calls the debug precompile, and asserts on the resulting event/state counts to detect the `prevEventsLen` desync [8](#0-7) [9](#0-8) . Due to index size limits, I could not retrieve the full production implementations of `GetBalanceHandler()` and each real precompile's Run() wiring; a Devin session with full repository access would be needed to confirm whether this is a currently-exploitable live path in `staking`, `distribution`, `gov`, `ics20`, or `erc20` precompiles versus an already-mitigated legacy pattern only exercised by test-only precompiles.

// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.4;

contract DebugPrecompileCaller {
    address constant debugPrecompile = 0x0000000000000000000000000000000000000799;
    error CallFailed(bytes data);
    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }
        }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));
        if (!result) {
            revert CallFailed(data);
        }
    }
}
