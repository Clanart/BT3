## Title
NFT royalty fee (Allo-style) rounding-down bypass via offer/trade splitting - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
The Chia NFT1 royalty mechanism computes the royalty amount owed to an NFT creator/DID owner using floor (truncating) integer division, exactly like the Allo `feeAmount = (_amount * percentFee) / getFeeDenominator()` pattern. By repeatedly trading (offering/accepting) small enough amounts, the royalty calculation always rounds down to `0`, letting a counterparty transfer the same aggregate value as one large trade while paying no royalty at all.

### Finding Description
The wallet computes the royalty owed on an offer using: [1](#0-0) 

```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```

This is the exact same rounding-down division pattern flagged in the Allo report (`(_amount * percentFee) / getFeeDenominator()`), and the repository's own test suite documents this truncation-to-zero behavior as expected: [2](#0-1)  — a trade of `50` mojos at `1%` (`percentage=100`) yields a royalty of `0`.

This value is fed directly into the on-chain enforcement path: `compute_royalty_amount` is invoked when constructing NFT1 offers, and the resulting `royalty_amount` is embedded in a `CreateCoin` condition that becomes part of the settlement bundle enforced against the NFT's ownership/transfer-program puzzle: [3](#0-2) . The same rounding-down math (`abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS`) is used again in `NFTWallet.royalty_calculation`, the routine used to preview/summarize expected royalties for a trade: [4](#0-3) .

Because the royalty is calculated per-trade (per offer/accept) rather than being tracked cumulatively per NFT/asset pair, a counterparty who wants to acquire (or sell against) a royalty-bearing NFT for a large fungible amount can instead split the transaction into many small offers/accepts, each individually small enough that `trade_price * percentage // MAX_ROYALTY_BASIS_POINTS == 0`. The aggregate value transferred to/from the NFT owner across all the small trades can match what a single large trade would have moved, but the royalty owed to the NFT creator's `royalty_address` is `0` on every leg, in contrast to a single trade of the same aggregate size, which would incur a nonzero enforced royalty payment.

### Impact Explanation
This allows systematic bypass of NFT creator/DID-owner royalties — the core value proposition of Chia's NFT1 royalty enforcement design — by any offer participant. Royalty payments are a fund-movement guarantee baked into the NFT ownership transfer puzzle and asserted via puzzle announcements in the offer settlement flow (`AssertPuzzleAnnouncement` on the royalty payment) [5](#0-4) ; bypassing it via structured dust-sized trades results in unauthorized diversion of value that should have gone to the royalty recipient. This is a concrete instance of "asset identity/royalty fee bypass" impacting offer settlement economics for every royalty-bearing NFT (NFT1).

### Likelihood Explanation
Any wallet user acting as an offer maker or taker can trigger this by constructing multiple small offers instead of one large offer — no special privileges, and it is deterministic (not probabilistic) given fixed integer division. The main friction is transaction/CLVM cost overhead of issuing many small trades, but this is a cost trade-off, not a blocker, and is directly analogous to the Allo report's suggested "repeatedly call fundPool() with small amounts."

### Recommendation
Round the royalty calculation up (ceiling division) instead of down, or enforce a minimum-trade-size threshold below which royalty-bearing trades are rejected, analogous to Solady's `mulDivUp`/ceiling division fix recommended in the source report. For example, change:
```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```
to a ceiling-division formula such as `-(-((abs(offered_amount) // royalty_split) * percentage) // MAX_ROYALTY_BASIS_POINTS)`, ensuring any nonzero trade against a royalty-bearing NFT always yields a nonzero royalty payment (subject to a sane minimum-trade floor to avoid dust-coin creation issues).

### Proof of Concept
1. NFT creator sets `royalty_percentage = 100` (1%) via `create_ownership_layer_puzzle` [6](#0-5) .
2. Instead of one offer trading `50000` mojos for the NFT (which would owe `500` mojos royalty), the buyer performs multiple offers each trading `49` mojos.
3. For each such offer, `compute_royalty_amount(offered_amount=-49, royalty_split=1, percentage=100)` returns `0`, as demonstrated by `test_small_amount_truncates_to_zero` [2](#0-1) , so `make_nft1_offer` skips creating any royalty payment coin entirely: [7](#0-6) .
4. Repeating this over enough small offers, the buyer accumulates the full `50000`-mojo equivalent value transfer to/from the NFT owner while paying `0` total royalty, versus `500` mojos owed in the single-trade case.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```

```python
    did_id: bytes,

    log.debug(
        "Creating ownership layer puzzle with NFT_ID: %s DID_ID: %s Royalty_Percentage: %d P2_puzzle: %s",

        did_id,
```
