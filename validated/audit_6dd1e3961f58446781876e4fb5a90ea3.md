### Title
Copilot conflict-resolution reassembly only checks aggregate hunk *count*, not per-hunk positional correctness, allowing attacker-controlled merge content to silently corrupt committed files - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The reported DeFi bug is a class of "aggregate-check bypass": a system validates a *sum/total* (slippage on total minted shares) but never validates the *individual* components that make up that total, letting an attacker manipulate the composition while satisfying the aggregate check. The same pattern exists in GitHub Desktop's Copilot-assisted merge-conflict resolution feature: `validateResolutionPaths` only verifies that the *number* of hunks returned for a file matches the *number* of conflicts in that file — it never verifies that hunk `j` in the model's response actually corresponds to conflict `j` in the file, or that its content is sane relative to that specific conflict region.

### Finding Description
`validateResolutionPaths` in [1](#0-0)  checks: the returned file paths are all expected, there are no duplicate/missing paths, and for each file `resolution.hunks.length === expectedCount`. It performs no check that each individual hunk's `resolvedContent` is faithful to (or even plausibly derived from) the specific conflict block at that index.

The reassembly step then blindly splices hunks by *order of appearance*, not by any content-based correlation: [2](#0-1) [3](#0-2) 

This is exactly the "sum vs. individual items" flaw from the report: the aggregate invariant (hunk count matches) holds, but nothing constrains which resolved text lands in which conflict slot, nor validates that the content is a safe/faithful merge of that particular hunk. The model's context (and therefore its output) is built from attacker-influenceable data — the "theirs" side of the conflict, PR titles/descriptions, and commit messages from a branch the user is merging/rebasing/cherry-picking, gathered into the system prompt: [4](#0-3) . A crafted incoming branch (conflicting file content, commit messages, or PR description used as context) that influences the LLM into returning hunks in the wrong order, or with subtly altered content for a given index, will still pass `validateResolutionPaths` as long as the total count matches expectations.

The corrupted reassembled content is then written directly to disk and staged with no further diffing/verification against the original conflict boundaries: [5](#0-4) 

### Impact Explanation
If hunk-to-conflict-position mapping is not verified, a maliciously crafted branch/PR (something an attacker fully controls when the victim merges or rebases against it) can cause Desktop to write and stage content the user never reviewed as corresponding to that conflict — e.g., swapping resolutions between two conflicts in the same file, or getting the model to include content the user believes belongs to a different, already-reviewed hunk. Because the write path (`_applyCopilotConflictResolutions`) stages the result via `git add` right before the merge/rebase/cherry-pick commit is finalized, this is a "silent corruption of what the user commits" scenario — the user thinks they're accepting a specific per-hunk resolution shown in the diff viewer, but the actual bytes written can diverge from what was validated, especially in files with multiple conflicts.

### Likelihood Explanation
This requires the victim to actively invoke "Resolve with Copilot" on a conflict against attacker-controlled/attacker-influenced branch content (a normal workflow when merging PRs or third-party branches), and it depends on successfully steering LLM output through prompt injection embedded in commit/PR text or conflicting code — a non-trivial but realistic and previously demonstrated class of attack against LLM-consuming tools. The count-only validation removes what would otherwise be a structural safety net against exactly this kind of manipulation.

### Recommendation
Extend `validateResolutionPaths` / `reassembleResolvedFile` to bind each hunk resolution to its originating conflict by a stable identifier (e.g., include the original `ours`/`theirs`/`base` content or a hash of it in the request/response round-trip) rather than relying purely on array order and a count match. Reject or flag resolutions where a hunk's resolved content bears no plausible relationship to either side of the specific conflict it's meant to replace, and surface a diff-per-hunk comparison so any reordering or mismatch is visibly different from the source conflict before the user confirms and it is staged.

### Proof of Concept
1. Set up a repository where a file has two conflicts (as in the existing test at [6](#0-5) ).
2. Craft the incoming ("theirs") branch's conflicting content/commit message to include a prompt-injection payload designed to make the model swap the order of its two `hunks` entries (or alter hunk 2's content while still returning exactly 2 hunks).
3. `validateResolutionPaths` passes because `resolution.hunks.length === expectedCount` (2 === 2); there is no check that hunk 0 answers conflict 0 and hunk 1 answers conflict 1.
4. `reassembleResolvedFile` splices hunk 0's content into conflict 0's position and hunk 1's into conflict 1's position purely by order [7](#0-6) , so if the model was steered to swap or corrupt one hunk while preserving the total count, the wrong/malicious content is written to the resolved file.
5. `_applyCopilotConflictResolutions` writes this file straight to disk and `git add`s it [8](#0-7) , so the corrupted content is what actually gets committed when the user clicks "Continue Merge".

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
