### Title
PedPoP `Decryption::register` asserts on duplicate encryption-key messages and `decrypt_with_proof` indexes unregistered participants — remote crash of an honest DKG participant - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The libxml2 advisory describes a crash (NULL pointer dereference) triggered by parsing malformed, attacker-controlled schema input. The analog in Serai is a panic reachable purely from untrusted PedPoP DKG messages: `Decryption::register` uses `assert!` to reject a second `EncryptionKeyMessage` for the same participant, and `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` / `BlameMachine::blame_internal` indexes `self.commitments[&sender]`, panicking whenever the named participant was never registered. An unprivileged DKG participant can therefore crash every honest peer's process by sending duplicate or mis-keyed messages.

### Finding Description
`Decryption::register` enforces one-registration-per-participant with a hard `assert!` instead of an error return:

```rust
// crypto/dkg/pedpop/src/encryption.rs:351-362
pub(crate) fn register<M: Message>(
  &mut self,
  participant: Participant,
  msg: EncryptionKeyMessage<C, M>,
) -> M {
  assert!(
    !self.enc_keys.contains_key(&participant),
    "Re-registering encryption key for a participant"
  );
  self.enc_keys.insert(participant, msg.enc_key);
  msg.msg
}
``` [1](#0-0) 

There is no prior deduplication visible in this layer; the asserted invariant depends entirely on the remote participant behaving honestly and on the transport never delivering the same authenticated message twice. Because `EncryptedMessage` / `EncryptionKeyMessage` contents are attacker-controlled (`EncryptionKeyMessage::read` parses `msg` and `enc_key` straight from the wire, `crypto/dkg/pedpop/src/encryption.rs:57-59`), a faulty participant who emits two key messages causes every honest node that registers both to panic in `assert!` rather than returning a blameable error.

Two further unchecked-index panics exist on the blame path, also reachable from attacker-influenced participant indices:

- `self.enc_keys[&decryptor]` in `decrypt_with_proof` panics if the accusation names a `decryptor` that never registered an encryption key (the HashMap index happens while building the DLEq statement, before the proof is checked), [2](#0-1) 
- `self.commitments[&sender]` in `BlameMachine::blame_internal` panics for an unregistered `sender`, [3](#0-2) 
- `self.result.unwrap()` in `BlameMachine::complete` panics if called before a successful result exists. [4](#0-3) 

Like the libxml2 bug, the root cause is missing validation of unexpected-but-representable input on a parse/dispatch path: instead of returning `Err` (or a blame verdict), the code panics.

### Impact Explanation
A single faulty DKG participant crashes every honest participant that processes its second `EncryptionKeyMessage`, aborting the key-generation session and taking down the process (in deployment this is the processor/coordinator node). On the blame path, an accusation crafted with a `sender`/`decryptor` index that is absent from `enc_keys`/`commitments` (e.g., an index that never sent a key message, or beyond the registered set) crashes the honest node that executes `blame`, turning a blame ritual meant to identify the faulty party into a denial of service of the honest one. This maps to the advisory's availability-only impact (C:N/I:N/A:H).

### Likelihood Explanation
Triggering requires only sending malformed-but-parseable protocol messages: two `EncryptionKeyMessage`s for the same `Participant`, or a blame invocation referencing an unregistered index. No collusion, no cryptographic break, and no privileged position is needed — any participant slot (which in a threshold-with-abort DKG is precisely the threat model PedPoP is designed for, since it exists to attribute fault to misbehaving participants) suffices. A library intended to survive malicious DKG members instead panics on the first misbehavior class it encounters, making the crash deterministic rather than probabilistic.

### Recommendation
- Replace `assert!(!self.enc_keys.contains_key(&participant))` in `Decryption::register` with a fallible check that returns an error/blame indication, so duplicate key messages are treated as provable misbehavior rather than a crash.
- Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get()` + error return (blame the party that supplied the bogus index).
- Guard `BlameMachine::complete` (`self.result.unwrap()`) behind an explicit error if the protocol has not finished.
- Audit the rest of `crypto/dkg/pedpop` and `crypto/dkg` for `HashMap` indexing and `unwrap`/`assert` on values derived from remote participants.

### Proof of Concept
Conceptual, against the library API:

```rust
// 1. Honest node runs PedPoPMachine; attacker is Participant j.
// 2. Attacker emits two distinct EncryptionKeyMessage<C, _> values under j
//    (e.g., different inner msg / different enc_key, both parse fine via
//    EncryptionKeyMessage::read).
// 3. Honest node calls Decryption::register(j, msg1)  -> Ok
//    then          Decryption::register(j, msg2)
//    -> assert!(!self.enc_keys.contains_key(&j)) fires -> panic, process aborts.
//
// Variant B (blame path): honest node receives an accusation naming a
// recipient/decryptor Participant index that never sent an EncryptionKeyMessage,
// and calls BlameMachine::blame(sender, decryptor, msg_with_valid_pop, Some(proof)).
// decrypt_with_proof evaluates self.enc_keys[&decryptor] -> panic (indexing a
// missing key) before the DLEq proof is ever checked.
```

`msg_with_valid_pop` is trivially constructible since the PoP is a Schnorr signature over `pop_challenge` signed with a key the attacker generates itself (`crypto/dkg/pedpop/src/encryption.rs:135-168`), so reaching the panicking index only requires the attacker to possess a valid participant slot.
