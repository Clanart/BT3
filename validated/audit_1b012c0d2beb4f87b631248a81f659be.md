### Title
Unbounded per-transaction signature count forces expensive Ecrecover computations before multisig key-count is validated - ([File: blockchain/types/tx_signatures.go])

### Summary
For Kaia-native transaction types (i.e., not legacy and not EIP-2718 Ethereum typed transactions), `TxSignatures.RecoverPubkey` performs a real `crypto.Ecrecover` (secp256k1 native/cgo point-recovery) call for *every* entry in the `TxSignatures` slice, with no upper bound on the number of entries checked before this loop runs. The only place that rejects an excessive signature count (`accountkey.MaxNumKeysForMultiSig = 10`, enforced in `AccountKeyWeightedMultiSig.SigValidationGas`/`Validate`) executes only *after* all signatures have already been recovered.

### Finding Description
`SanityCheckSignatures` (`blockchain/types/tx_signatures.go:179-197`) is invoked at RLP/JSON decode time (`blockchain/types/transaction.go:246`, `:283`). For Kaia-native tx types it falls through to `sigs.ValidateSignature()` (`tx_signatures.go:91-108`), which only performs a cheap range check (`crypto.ValidateSignatureValues`) per entry and does **not** cap the number of signature entries. [1](#0-0) 

Later, during `TxPool.validateTx` (`blockchain/tx_pool.go:797-1021`), the transaction size is checked against `MaxTxDataSize` (line 887) *before* `tx.ValidateSender` is invoked (line 898). However, because RLP encodes small integers extremely compactly (e.g. `V=0, R=1, S=1` needs only ~4 bytes per `TxSignature` entry as a 3-element list), a single transaction bounded by `MaxTxDataSize` can still carry many thousands of syntactically-valid-looking signature triples.

When `tx.ValidateSender` is subsequently called, it eventually reaches `TxSignatures.RecoverPubkey` (`blockchain/types/tx_signatures.go:134-146`), which loops over **all** `t` entries and calls `s.RecoverPubkey` → `recoverPlainPubkey` → the real `crypto.Ecrecover` secp256k1 recovery routine for each one, as long as `R`/`S` pass the cheap `crypto.ValidateSignatureValues` range check (values in `[1, N-1]` satisfy this trivially, e.g. `R=S=1`). [2](#0-1) [3](#0-2) 

Only after all these expensive `Ecrecover` calls complete does `AccountKeyWeightedMultiSig.Validate`/`SigValidationGas` check `len(recoveredKeys) > len(a.Keys)` (bounded by `MaxNumKeysForMultiSig = 10`) and reject the transaction. [4](#0-3) [5](#0-4) 

This mirrors the reported bug class: a structurally cheap, attacker-controlled repeated element (HTTP header fields in the advisory; `TxSignature` entries here) is fully consumed and processed by expensive per-element work (header accumulation into `HTTPHeaders`; here, native secp256k1 point recovery) before any count-based limit is enforced.

### Impact Explanation
An unauthenticated RPC caller can submit a single ~32KB raw transaction (via `kaia_sendRawTransaction` / `SendRawTransaction`, `api/api_kaia_transaction.go:384-390`) crafted with thousands of minimal `TxSignature` triples for a Kaia-native tx type (e.g., `TxTypeValueTransfer`). Each such submission forces the node to perform thousands of native ECDSA point-recovery operations inside `tx.ValidateSender` before ultimately being rejected for exceeding `MaxNumKeysForMultiSig`. Repeated submissions (the tx pool's `known transaction` dedupe can be bypassed by varying nonce/value/gas per submission to get distinct hashes) can be used to consume disproportionate CPU on any public RPC node's tx-pool validation path, degrading availability for other transaction processing — a CPU-exhaustion analog of the header-list amplification described in the report.

### Likelihood Explanation
Reachable directly by any unprivileged RPC caller/tx sender with no special privileges, since it only requires crafting and submitting a raw RLP transaction. It does not require the sender to control a real multisig account; the account-key type check that would reject excess signatures happens only after the costly recovery loop, and does not depend on the `from` account's actual key configuration (`accountkey.MaxNumKeysForMultiSig` bounds any weighted-multisig key list, but the recovery cost is incurred regardless of which key type is ultimately checked).

### Recommendation
Enforce an upper bound on `len(TxSignatures)` (e.g., `accountkey.MaxNumKeysForMultiSig`) as an early, cheap decode/pool-validation check — analogous to `NIOHTTPDecoderLimitConfiguration.maxHeaderFieldCount` — before any `Ecrecover`/`RecoverPubkey` call is performed in `TxSignatures.RecoverPubkey` (`blockchain/types/tx_signatures.go:134`) or in `TxPool.validateTx`/`SanityCheckSignatures`, so that transactions with excessive signature counts are rejected without incurring the cryptographic recovery cost.

### Proof of Concept
Conceptual PoC (not executed):
1. Construct a `TxTypeValueTransfer` (or similar Kaia-native) transaction.
2. Set `TxSignatures` to a slice of, e.g., 5,000–8,000 `{V:0, R:1, S:1}` triples (or other values that pass `crypto.ValidateSignatureValues`'s range check but are not real signatures for the target sighash).
3. RLP-encode the transaction; verify total size stays under `MaxTxDataSize` (32KB) due to the compact RLP encoding of small integers.
4. Submit via `kaia_sendRawTransaction`.
5. Observe: `tx.ValidateSender` → `RecoverTxPubkeys` → `TxSignatures.RecoverPubkey` performs one `crypto.Ecrecover` call per signature entry (thousands of native secp256k1 recoveries) before the transaction is ultimately rejected by `AccountKeyWeightedMultiSig`/legacy-key validation for exceeding the allowed signature/key count. func (t TxSignatures) RecoverPubkey(txhash common.Hash, homestead bool, vfunc func(*big.Int) *big.Int) ([]*ecdsa.PublicKey, error) {
	var err error

	pubkeys := make([]*ecdsa.PublicKey, len(t))
	for i, s := range t {
		pubkeys[i], err = s.RecoverPubkey(txhash, homestead, vfunc)
		if err != nil {
			return nil, err
		}
	}

	return pubkeys, nil

// SanityCheckSignatures validates whether the signature values are valid.
// It checks the signatures from the given TxSignatures.
func SanityCheckSignatures(sigs TxSignatures, txType TxType) bool {
	if len(sigs) == 0 {
		return false
	}

	// Legacy and Eth Typed transactions have only one signature.
	sig := sigs[0]

	if txType.IsEthTypedTransaction() {
		v := byte(sig.V.Uint64())
		return crypto.ValidateSignatureValues(v, sig.R, sig.S, false)
	}

	if txType.IsLegacyTransaction() {
		return validateSignature(sig.V, sig.R, sig.S)
	}

	return sigs.ValidateSignature()
}

func (a *AccountKeyWeightedMultiSig) SigValidationGas(currentBlockNumber uint64, r RoleType, numSigs int) (uint64, error) {
	numKeys := uint64(len(a.Keys))
	if numKeys > MaxNumKeysForMultiSig {
		logger.Warn("validation failed due to the number of keys in the account is larger than the limit.",
			"account", a.String())
		return 0, kerrors.ErrMaxKeysExceedInValidation
	}
	if numKeys == 0 {
		logger.Error("should not happen! numKeys is equal to zero!")
		return 0, kerrors.ErrZeroLength
	}

	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul
	if isIstanbul {
		return uint64(numSigs-1) * params.TxValidationGasPerKey, nil
	}
	return (numKeys - 1) * params.TxValidationGasPerKey, nil
}
