### Title
Copilot conflict-resolution dialog treats a skipped file as "resolved" when its path merely fails to match, allowing conflict markers to be committed silently - (File: `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`)

### Summary
The `CopilotConflictsDialog` gates its "Continue" button on `hasUnresolvedSkippedFiles()`, which iterates over `copilotSkippedFiles` and, for each one, does a linear search (`Array.prototype.find`) over `this.props.workingDirectory.files` to see if the file is still conflicted. If that search comes up empty, the code silently treats the file as "resolved" — the same "not found ⇒ assume success" pattern flagged in the external report, applied here to a path lookup that gates whether a merge/rebase/cherry-pick can be safely continued.

### Finding Description
`isSkippedFileResolved` performs the lookup and short-circuits to `true` when the file is missing from the working-directory list: [1](#0-0) 

The comment even acknowledges the assumption explicitly: "Gone from the working directory... means the file was resolved/staged externally — there is nothing left to gate Continue on, so treat it as resolved." This inference is only valid if the `find` by exact string equality against `skipped.path` is guaranteed to succeed whenever the file is still on disk and conflicted. That assumption breaks any time the path recorded in `ICopilotSkippedFile.path` (produced by the Copilot conflict-resolution pipeline, driven by AI output derived from repository/file content) does not byte-for-byte match the path key used in `WorkingDirectoryStatus.files` (derived from `git status` parsing). This includes normalization mismatches, encoding differences, or any other divergence in how the two paths were captured, and it applies uniformly wherever the same pattern is used to gate whether a file counts as "already handled": [2](#0-1) 

`hasUnresolvedSkippedFiles()` aggregates these results to control the primary submit action: [3](#0-2) [4](#0-3) 

Unlike the analogous helper `isFileResolvedExternally`, which requires the file to actually have `conflictMarkerCount === 0` before it is considered resolved, `isSkippedFileResolved` never checks marker count for the "file not found" branch — it just accepts absence-from-list as proof of resolution.

### Impact Explanation
If the lookup silently fails for a file that is still on disk with live conflict markers, `hasUnresolvedSkippedFiles()` returns `false`, `okButtonDisabled` becomes `false`, and the user is allowed to click "Continue [merge/rebase/cherry-pick]". Continuing calls `applyCopilotConflictResolutions` and then `onContinueAfterConflicts`, which stages and commits based on the working tree contents rather than on the dialog's belief about resolution state — so the conflict-marker-laden file gets committed/pushed as-is. This is exactly the "silent corruption of what the user commits" impact class: the user believes (via the disabled/enabled Continue button and the "No conflicts remaining" label) that every file is clean, but a specific file with unresolved `<<<<<<<`/`=======`/`>>>>>>>` markers ends up in the resulting commit.

### Likelihood Explanation
The trigger requires only that the string used to key `ICopilotSkippedFile.path` diverge from the string used to key `WorkingDirectoryFileChange.path` for the same on-disk file — both of which originate from repository content that a malicious/crafted repo (unusual filenames, paths with non-ASCII or otherwise ambiguous encodings, submodule paths, etc.) can influence. I was not able to fully trace, within the indexed portion of the codebase, the exact code path that produces `ICopilotSkippedFile.path` in `app/src/lib/stores/app-store.ts` versus how `git status` porcelain paths are decoded into `WorkingDirectoryFileChange.path`, so I cannot confirm a concrete byte-level mismatch scenario (e.g., NFC/NFD normalization) is reachable end-to-end; this is a gap in what the current index/tooling let me verify, and a background agent with full repo access would be needed to confirm the exact string-divergence trigger and its exploitability from an attacker-controlled repo.

### Recommendation
Do not treat "not found in the working-directory list" as proof of resolution. Instead:
- Fail closed: if a skipped file cannot be located, keep it counted as unresolved (disable Continue) and surface an explicit warning to the user rather than silently clearing it.
- When looking up files, normalize both path sources (Unicode normalization, path separators) consistently before comparing, and prefer a stable file identity (e.g., inode/git blob path from `git status -z` machine-readable output) rather than string equality.
- Mirror `isFileResolvedExternally`'s stricter check (require `conflictMarkerCount === 0`) for the "file missing" branch as well, or re-run a status/marker check specifically for the skipped path before declaring it resolved.

  private isSkippedFileResolved(path: string): boolean {
    if (this.getSkippedFileChoice(path) !== undefined) {
      return true
    }
    const file = this.props.workingDirectory.files.find(f => f.path === path)
    // Gone from the working directory, or no longer reported as conflicted,
    // means the file was resolved/staged externally - there is nothing left to
    // gate Continue on, so treat it as resolved.
    if (file === undefined || !isConflictedFile(file.status)) {
      return true
    }
    // Still conflicted: resolved only once the markers are removed in an editor.
    return this.isFileResolvedExternally(file)
  }
