Based on the evidence gathered, I found a Desktop analog that fits the required bug class: **an attacker-controlled identity string (a GitHub API object's `name` field) flows unsanitized into a value that becomes part of a locally-authored git commit** — a parallel to the original bug's core flaw ("a value pulled from an external/untrusted context is used verbatim where an identity value is expected, with no validation of its content").

### Title
Unsanitized GitHub profile `name` from co-author autocomplete is embedded verbatim into `Co-Authored-By` commit trailers, allowing an attacker-controlled account to inject content into a victim's commit message - (File: app/src/ui/changes/commit-message.tsx)

### Summary
When a user adds a co-author to a commit via the `@mention` autocomplete or a search, GitHub Desktop takes the co-author's `name` and `email`, both fetched from the GitHub API, and interpolates them directly into a `Co-Authored-By` trailer string with no sanitization of control characters (e.g. newlines).

### Finding Description
The co-author's display name originates from the GitHub API user object [1](#0-0) , and is carried through the mentionable-user pipeline into an autocompletion "hit" [2](#0-1) , and finally converted into a `KnownAuthor` with `name: user.name || user.username` [3](#0-2) .

When the commit is created, that `name`/`email` pair is interpolated directly into a `Co-Authored-By: <name> <<email>>` trailer string with no escaping or newline stripping: [4](#0-3) 

These trailers are then merged into the actual commit message text via `formatCommitMessage`/`mergeTrailers`, which becomes the literal content passed to `git commit`: [5](#0-4) 

At no point is `a.name` (or `a.email`) checked for embedded newlines or trailer-like syntax (e.g. `\n\nSigned-off-by: ...` or additional `Co-Authored-By:` lines) before being spliced into the trailer value and merged into the commit body.

### Impact Explanation
Any GitHub.com user can set an arbitrary public display `name` on their account. Because this is fetched via the API and trusted as plain text throughout the co-author pipeline, an attacker who gets a victim to add them as a co-author (a very common, expected collaborative workflow — e.g. pairing, PR review credit) can craft a `name` value containing embedded newlines and trailer-like text. This can silently corrupt what the victim ultimately commits and pushes: extra trailers (forged `Signed-off-by`, additional bogus `Co-Authored-By` entries, or arbitrary text appended to the commit body) end up embedded in the pushed commit without the victim intending or necessarily noticing, since the UI only shows the co-author as a name/email "chip," not the raw trailer text that will be written to the commit. This matches the "silent corruption of what the user commits or pushes" impact category — the corruption originates from an attacker-controlled GitHub API object (their own profile name), requires no local access, malware, or leaked credentials, and only an ordinary collaborative action (adding a co-author) by the victim.

### Likelihood Explanation
The flow is straightforward and requires only that a victim tag a malicious account as a co-author — a normal, encouraged workflow in Desktop. I was not able to inspect the internals of `mergeTrailers`/`git/interpret-trailers.ts` in this pass to confirm whether `git interpret-trailers` itself would reject or truncate an embedded-newline trailer value (some git trailer parsers fold or reject multi-line trailer values); this is the primary remaining uncertainty and would need to be validated against the actual runtime behavior before treating this as a fully confirmed injection primitive. Absent that confirmation, the certain fact is that no sanitization occurs at the Desktop application layer before the value reaches git's trailer-merging step.

### Recommendation
Sanitize or reject co-author `name`/`email` values that contain newlines or other control characters before constructing `Co-Authored-By` trailer strings in `getCoAuthorTrailers` (`app/src/ui/changes/commit-message.tsx`), and validate the final merged trailer output does not contain unexpected additional trailer lines beyond the ones Desktop explicitly added.

### Proof of Concept
1. Attacker sets their GitHub.com public profile "Name" field to a string containing an embedded newline plus additional trailer-like text, e.g. `Attacker\n\nSigned-off-by: Attacker <attacker@evil.com>`.
2. Victim, in Desktop, opens the commit box and types `@attacker` to add them as a co-author (normal autocomplete flow using `CoAuthorAutocompletionProvider`).
3. Desktop resolves the hit via `authorFromUserHit`, storing `name` verbatim [3](#0-2) .
4. On commit, `getCoAuthorTrailers` builds the trailer value using the raw name [4](#0-3) , which is merged into the commit message text via `formatCommitMessage`/`mergeTrailers` and passed to `git commit`, without the victim seeing or approving the injected extra line(s) before the commit is created and later pushed.

export async function formatCommitMessage(
  repository: Repository,
  context: ICommitContext
) {
  const { summary, description, trailers } = context

  // Git always trim whitespace at the end of commit messages
  // so we concatenate the summary with the description, ensuring
  // that they're separated by two newlines. If we don't have a
  // description or if it consists solely of whitespace that'll
  // all get trimmed away and replaced with a single newline (since
  // all commit messages needs to end with a newline for git
  // interpret-trailers to work)
  const message = `${summary}\n\n${description || ''}\n`.replace(/\s+$/, '\n')

  return trailers !== undefined && trailers.length > 0
    ? mergeTrailers(repository, message, trailers)
    : message
}
