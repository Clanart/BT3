### Title
`RewardMintingAmount` and other governance parameters accepted with `noopFormatChecker`, allowing minting-amount inflation and unsafe pricing parameters without a sanity/range check - (File: kaiax/gov/param.go)

### Summary
The Kaia governance parameter registry (`kaiax/gov/param.go`) defines a `FormatChecker` per parameter that is meant to validate values before they are accepted into consensus (via header-vote governance or the GovParam contract). Several critical, economically sensitive parameters — most notably `RewardMintingAmount` — use `noopFormatChecker`, which always returns `true` regardless of the value, i.e. no upper-bound / sanity check is enforced.

### Finding Description
`kaiax/gov/param.go` defines `Params`, a map of `ParamName -> *Param{Canonicalizer, FormatChecker, ChainConfigValue, DefaultValue}`. Most numeric parameters that end up directly controlling monetary or pricing outcomes use `noopFormatChecker`, e.g.: [1](#0-0) [2](#0-1) [3](#0-2) 

Unlike `IstanbulCommitteeSize` (`v > 0`), `Kip71BaseFeeDenominator` (`v != 0`), or `RewardKip82Ratio`/`RewardRatio` (percentage sums must equal 100), `RewardMintingAmount` has no bound at all — any `*big.Int` value, including an astronomically large one, is accepted by `FormatChecker: noopFormatChecker` at [4](#0-3) .

This is directly analogous to the reported `TimelockController` bug class: a governance-controlled setter accepts a caller-provided numeric value without validating it falls within a sane/expected range, and the value flows straight into a security/economically critical computation.

The `checkConsistency` function in `kaiax/gov/headergov/impl/header.go` only adds extra validation for `GovernanceGoverningNode`, `Kip71LowerBoundBaseFee`, `Kip71UpperBoundBaseFee`, and validator add/remove — `GovernanceUnitPrice` and all `Reward*` parameters (including `RewardMintingAmount`) fall into the default pass-through branch that returns `nil` unconditionally: [5](#0-4) 

Once accepted, `RewardMintingAmount` is used verbatim as the per-block minted amount in every reward-computation path (`getRewardSummary`, `getDeferredRewardSimple`, `getDeferredRewardFullFlex`, `getDeferredRewardFullKore`, `getDeferredRewardFullLegacy`): [6](#0-5) [7](#0-6) [8](#0-7) 

The minted amount is added directly to the proposer/staker/fund balances every block with no cap, so an unchecked value is equivalent to unconditional native-token supply inflation at whatever magnitude the parameter is set to.

### Impact Explanation
If a governance vote (governing node in single mode, or ballot in council mode) sets `governance.reward.mintingamount` to an inappropriately large value — through a simple oversight, misconfiguration, or malicious intent by an authorized-but-compromised governance key — there is no protocol-level circuit breaker preventing it. Every subsequent block would mint that amount to the proposer/reward recipients, causing uncontrolled native token (KAIA) supply inflation with no on-chain sanity check to reject or bound the value, unlike `Kip71LowerBoundBaseFee`/`UpperBoundBaseFee` which at least have relative-consistency checks against each other. This matches the "supply inflation" acceptance criterion.

### Likelihood Explanation
The trigger requires a governance vote to be submitted and accepted (single-mode governing node, or majority in ballot mode) — this is the same "privileged-role-without-bound-check" pattern as the original TimelockController report (an authorized role sets a dangerous unvalidated value). The FormatChecker layer is precisely the intended enforcement point for these sanity checks (as demonstrated by parameters like `Kip71BaseFeeDenominator` and `RewardRatio` that do implement bounds), but `RewardMintingAmount` (and `GovernanceUnitPrice`, `IstanbulEpoch`, `Kip71GasTarget`, `Kip71MaxBlockGasUsedForBaseFee`) were left with `noopFormatChecker`, so the omission is a straightforward gap rather than requiring exotic conditions.

### Recommendation
Add a bounded `FormatChecker` for `RewardMintingAmount` (and ideally the other `noopFormatChecker` numeric params that feed monetary/pricing logic) in `kaiax/gov/param.go`, e.g. enforcing `0 <= value <= MAX_REASONABLE_MINTING_AMOUNT`, mirroring the pattern already used for `RewardMinimumStake` and `RewardStakingRewardThreshold` (`v.Sign() >= 0`) but with an added upper bound informed by expected tokenomics. Additionally consider adding cross-checks in `checkConsistency` (`kaiax/gov/headergov/impl/header.go`) analogous to the `Kip71LowerBoundBaseFee`/`UpperBoundBaseFee` pair, e.g. rejecting minting-amount changes that deviate drastically from the current value without a multi-step/delayed transition.

### Proof of Concept
1. In single-governance mode, the governing node (or in ballot mode, a majority of council members) submits a vote `governance.reward.mintingamount = <arbitrarily large big.Int>`.
2. `NewVoteData` accepts it because `RewardMintingAmount`'s `Canonicalizer` (`bigIntCanonicalizer`) only parses the value into a `*big.Int`, and `FormatChecker: noopFormatChecker` unconditionally returns `true` — see [4](#0-3) .
3. `checkConsistency` in `header.go` treats `gov.RewardMintingAmount` as one of the "no more checks here" cases and returns `nil` — see [5](#0-4) .
4. The vote is accepted into the governance data at the next epoch boundary and becomes the effective `ParamSet.MintingAmount`.
5. From that epoch onward, every block's reward computation (`getDeferredRewardSimple`, `getDeferredRewardFullKore`, etc.) sets `minted := config.MintingAmount` and distributes it to the proposer/validators every block — see [9](#0-8)  — producing unbounded native token supply inflation with no in-protocol rejection mechanism.

func getDeferredRewardSimple(config *reward.RewardConfig, execFee, blobFee *big.Int) (*reward.RewardSpec, error) {
	spec := reward.NewRewardSpec()
	minted := new(big.Int).Set(config.MintingAmount)

	// Non-deferred mode
	if !config.DeferredTxFee {
		var proposer *big.Int
		if config.Rules.IsMagma {
			// In non-deferred mode, no fees to distribute here at the end of block processing.
			// Just distribute the minting reward to the proposer and stop.
			proposer = new(big.Int).Set(minted)
			execFee = big.NewInt(0)
		} else {
			// But Simple policy had a bug where transaction fees were distributed to the proposer here at the end of block processing
			// despite configured to non-deferred mode. To keep the backward compatibility, the buggy behavior retains until Magma.
			proposer = new(big.Int).Add(minted, execFee)
		}
		spec.Minted = new(big.Int).Set(minted)
		// Both exec fees and blob fees are burned during state transition in non-deferred mode,
		// not at finalization. TotalFee/BurntFee are completed by specWithNonDeferredFee (GetBlockReward only).
		spec.TotalFee = execFee // Note that we've set it to 0 for non-deferred + Magma (see above).
		spec.BurntFee = big.NewInt(0)
		spec.Proposer = proposer
		spec.IncRecipient(config.Rewardbase, proposer)
