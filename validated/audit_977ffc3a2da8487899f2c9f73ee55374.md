### Title
Partial-commit staging applies stale, index-based line selections to a freshly re-fetched diff, allowing silent inclusion/exclusion of unreviewed content in a commit - (File: `app/src/lib/git/apply.ts`)

### Summary
The bug-class in the report is "a security-relevant calculation using a value captured before a state change instead of the value that reflects the state after the change" (pre-swap reserves used instead of post-swap reserves). The equivalent invariant in GitHub Desktop is that a partial commit's line selection (an index-based `DiffSelection`, built by the user against one specific diff snapshot) must be evaluated against that *same* diff snapshot when the patch is generated. Instead, the staging path re-fetches a brand-new diff at commit time and blindly re-applies the old, index-based selection to it.

### Finding Description
When a user stages only some lines/hunks of a file, Desktop stores the choice as an index-based `DiffSelection` on the `WorkingDirectoryFileChange` (selection is keyed by absolute line index within the diff hunks the user was looking at, not by line content).

At commit time, `stageFiles()` calls `applyPatchToIndex()` for every partially-selected file: [1](#0-0) 

Inside it, the diff used to build the patch is fetched fresh, independent of whatever diff the user actually reviewed and clicked lines on: [2](#0-1) [3](#0-2) 

`formatPatch()` then decides which lines to include purely by absolute index into *this newly-fetched* diff's hunks, using `file.selection.isSelected(absoluteIndex)`: [4](#0-3) 

If the file on disk changed between the moment the user made the selection (viewing an older diff) and the moment `_commitIncludedChanges` runs `stageFiles`/`applyPatchToIndex`, the hunk layout and line indices shift. The same numeric index that used to point at the line the user explicitly reviewed and selected can now point at a completely different line — including newly-injected attacker content — while the line the user actually intended to stage may fall outside the selection or a different, unintended line gets included.

Desktop is aware this class of problem exists but only partially mitigates it, and only for the *live changes view*, not for the actual staging/commit code path: `updateChangesWorkingDirectoryDiff()` merely prunes selection entries that no longer exist as `isIncludeableLine()`, explicitly noting the remaining risk: [5](#0-4) 

That pruning does not stop the underlying invariant break: it does not re-validate that a *still-selectable* index still corresponds to the same content the user selected, and — critically — it lives in the UI-refresh path, not in `applyPatchToIndex`, which is the code that actually decides what ends up in the commit at staging time.

### Impact Explanation
Since a git commit is exactly what gets pushed to `origin`/GitHub afterward, a shifted-selection bug silently corrupts what the user commits and subsequently pushes — matching the "silent corruption of what the user commits or pushes" category explicitly called out as valid impact. Depending on the shift, this can:
- Cause attacker-injected lines (from a file rewritten by a build tool, formatter, git hook, or other tooling shipped with a cloned/fetched repository) to be committed and pushed under the user's identity without the user ever reviewing or approving them.
- Cause lines the user explicitly intended to exclude (e.g., secrets, debug code) to be committed instead, or vice versa — lines the user wanted staged to be silently dropped.

### Likelihood Explanation
This requires the working file to change on disk in the narrow window between the user reviewing/selecting lines in the diff and the commit actually executing. Plausible triggers that are attacker-controllable via a cloned/fetched repository include file-watchers/build scripts bundled with the project (e.g., linters/formatters running via an npm `postinstall`/`prepare` hook, IDE auto-format-on-save wired to project config, or a `post-checkout`/other git hook shipped in the repo if hooks aren't disabled) that rewrite tracked files shortly after checkout while the user is composing a partial commit. This is a realistic but not trivially-forced timing window, so likelihood is medium rather than high.

### Recommendation
`applyPatchToIndex()` (and `discardChangesFromSelection`) should not re-fetch and blindly reuse the stored `DiffSelection` against a new diff. Instead:
- Persist/verify a content-derived anchor (e.g., a hash of the diff text, or the diff object itself) alongside the selection, and refuse to stage/commit if the freshly-fetched diff doesn't match what the selection was computed against — surfacing a "changes to this file changed since you selected — please re-review" error instead of silently proceeding.
- Alternatively, pass the exact diff object the user last saw (captured with the selection) into `applyPatchToIndex`, generate the patch from it, and let `git apply` fail naturally if the working tree no longer matches that diff (git apply already fails on context mismatch, which would convert silent corruption into a visible failure).

### Proof of Concept
1. Modify a tracked text file with several lines, open it in Desktop's Changes view; the diff shows e.g. hunk at lines 10–15.
2. Select (stage) only line 12 for inclusion in the next commit via the line-level selection UI, leaving the rest of the file's changes unstaged. This creates a `DiffSelection` referencing absolute index N.
3. Before clicking "Commit", have an external process/hook (representing tooling from a cloned/fetched repository, e.g., a project's own auto-formatter or `post-checkout` hook) insert/remove lines earlier in the same hunk range, shifting later lines up/down without necessarily triggering (or being processed by) another full diff refresh in the UI before the click.
4. Click "Commit". `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (now shifted) and calls `formatPatch(file, diff)`, which uses `file.selection.isSelected(absoluteIndex=N)` against the new hunk structure — staging and committing whatever line is now at index N, not the line originally reviewed and approved at step 2.
5. Inspect the resulting commit: it contains content the user never reviewed/approved at the specific line they clicked, demonstrating the silent corruption.

(Note: I was not able to fully trace the exact debounce/refresh timing of `updateChangesWorkingDirectoryDiff` relative to the commit button's enablement in this pass, so the precise reproducibility window/timing constraints should be validated with a live build before treating this as fully confirmed.)
