## Title
Attacker-controlled commit message text is auto-linkified and opened via `shell.openExternal` without confirmation - (`File: app/src/lib/text-token-parser.ts`)

### Summary
The LiFi bug's broken invariant is: an untrusted, attacker-supplied value (a "spender" address) is passed straight into a sensitive sink (`approve`) with no allowlist check. The closest reachable analog in GitHub Desktop is `Tokenizer.scanForHyperlink` in `app/src/lib/text-token-parser.ts`, which scans **commit messages** (fully attacker-controlled content in a cloned/fetched repository) for `http(s)://` substrings and turns them into clickable `LinkButton` targets that are handed directly to `shell.openExternal` in the renderer, and then to Electron's `shell.openExternal` in the main process, with only a scheme-prefix regex as a guard.

### Finding Description
`Tokenizer.scanForHyperlink` accepts any word beginning with `https?://` found inside a commit message and emits it as a `TokenType.Link`: [1](#0-0) 

These tokens are rendered as clickable links (via `LinkButton`, whose `onClick` calls `shell.openExternal(uri)` unconditionally for any `uri` prop it receives): [2](#0-1) 

`shell.openExternal` ultimately reaches the main process IPC handler `open-external`, which does **not** enforce a protocol allowlist — it only logs when the string happens to start with `http`/`https`, but calls `shell.openExternal(path)` regardless of what `path` actually is: [3](#0-2) 

Contrast this with the one place in the codebase where link-following from untrusted content is done safely: `SandboxedMarkdown`'s click interceptor, which is used for PR/issue bodies and validates `a.protocol` against `/^https?:/` before ever calling the click handler: [4](#0-3) 

The tokenizer's own regex (`/^https?:\/\/.+/`) also constrains what gets *classified* as a link, so the practical risk isn't an arbitrary custom-protocol launch via this specific path — it's that a fully attacker-authored commit message (reachable simply by cloning/fetching a hostile repository, or viewing its history in Desktop) can present the user with clickable "hyperlinks" whose destination is entirely attacker-chosen and displayed with no domain/host warning, similar in structure to the reported facets: the destination "address" (URL) is taken as-is from attacker input and fed to a powerful sink (`openExternal`) whose only gate is a superficial prefix check, not a real allowlist of trusted hosts (e.g., `github.com`/the repo's own remote host).

### Impact Explanation
Clicking such a link opens the user's default browser to an arbitrary attacker-chosen HTTPS/HTTP URL from history view, commit summaries, etc. This enables phishing (fake GitHub login pages, credential-harvesting pages that closely mimic github.com), or chaining to browser-based exploits, entirely from content in a repository the user cloned/fetched — no push or write access to the victim's account is required, only that the victim opens/browses the malicious repository in Desktop. This matches the "Valid Impact" criteria of attacker-controlled repository content leading to unwanted external navigation with no unnatural interaction beyond a normal commit-history click.

### Likelihood Explanation
High-likelihood/low-effort for the attacker: any public or shared repository can contain a commit whose message includes an `http(s)://` string; no special git object crafting, hooks, or privileged access is required. The victim only needs to browse commit history in Desktop, which is a routine, expected user action. The severity is bounded (open-in-browser only, not code execution), analogous to the "Medium Risk" framing in the original report ("there shouldn't normally be tokens in the Diamond" ⇔ here, the link's visible/implied trust is inherited from being inside the app UI, not from any real domain check).

### Recommendation
- Do not present raw attacker-controlled URLs from commit messages/PR text as one-click "trusted" launch targets without at least showing the full destination and/or an interstitial confirmation, similar to how browsers warn on suspicious redirects.
- Apply the same host-based validation used elsewhere (e.g., `enterprise-validate-url.ts`'s protocol check, or a host allowlist limited to the repository's own GitHub endpoint or well-known GitHub domains) before auto-linkifying commit-message text, or route these links through the same confirmation path as `SandboxedMarkdown`.
- Harden the main-process `open-external` IPC handler in `app/src/main-process/main.ts` to actually reject/require confirmation for non-`http(s)` schemes rather than only logging.

### Proof of Concept
1. Create a repository and commit with message: `See details at https://github-secur1ty.example.com/login` (an attacker-controlled lookalike domain).
2. Have the victim clone/fetch this repository and open the commit in GitHub Desktop's history view.
3. `Tokenizer.scanForHyperlink` (`app/src/lib/text-token-parser.ts:213-256`) tokenizes the string as a `Link`, rendering it as a clickable element.
4. Victim clicks the rendered link; `LinkButton.onClick` (`app/src/ui/lib/link-button.tsx:76-92`) calls `shell.openExternal(uri)` with the attacker's raw URL, opening it in the system browser via the unrestricted `open-external` IPC handler (`app/src/main-process/main.ts:581-597`) — no host verification occurs anywhere in this path.

  private scanForHyperlink(
    text: string,
    index: number,
    repository?: GitHubRepository
  ): LookupResult | null {
    // to ensure this isn't just the part of some word - if something is
    // found and it's not whitespace, bail out
    const lastItem = this.getLastProcessedChar()
    if (lastItem && !/\s/.test(lastItem)) {
      return null
    }

    const nextIndex = this.scanForEndOfWord(text, index)
    const maybeHyperlink = text.slice(index, nextIndex)
    if (!/^https?:\/\/.+/.test(maybeHyperlink)) {
      return null
    }

    this.flush()
    if (repository && repository.htmlURL) {
      // case-insensitive regex to see if this matches the issue URL template for the current repository
      const compare = repository.htmlURL.toLowerCase()
      if (maybeHyperlink.toLowerCase().startsWith(`${compare}/issues/`)) {
        const issueMatch = /\/issues\/(\d+)/.exec(maybeHyperlink)
        if (issueMatch) {
          const idText = issueMatch[1]
          this._results.push({
            kind: TokenType.Link,
            url: maybeHyperlink,
            text: `#${idText}`,
          })
          return { nextIndex }
        }
      }
    }

    // just render a hyperlink with the full URL
    this._results.push({
      kind: TokenType.Link,
      url: maybeHyperlink,
      text: maybeHyperlink,
    })
    return { nextIndex }
  }

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
