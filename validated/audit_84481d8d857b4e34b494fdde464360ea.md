### Title
Unbounded loop over growing `pools` array in `WombatBribeManager.castVotes`/`claimAllBribes` can DoS voting and bribe distribution - (File: wombat/WombatBribeManager.sol)

### Summary
`WombatBribeManager.castVotes` and `claimAllBribes` both iterate over the full `pools` array with no pagination, mirroring the unbounded-loop DoS pattern described in the referenced report (`BatchRequests.sendWithdrawalRequests`). As more pools are onboarded over time via `addPool`, these permissionless, user-facing functions risk hitting the block gas limit, permanently DoS-ing vote casting and bribe reward distribution for all users.

### Finding Description
`castVotes` is a `public` function (callable by any wallet, not restricted to the owner) that loops over `pools.length` to build vote arrays and then submits votes to `wombatStaking.vote(...)`, followed by forwarding harvested rewards: [1](#0-0) 

Each loop iteration performs a storage read (`poolInfos[pools[i]]`), a call to `getVoteForLp` (which itself makes an external call to `voter.getUserVotes`), and arithmetic — meaning gas cost scales linearly (or worse, given nested external calls) with the number of registered pools: [2](#0-1) 

Similarly, `claimAllBribes` (also `public`, callable by/for any user) iterates over the same `pools` array, making an external call to `voter.infos(lp).bribe` and potentially `getReward` per pool: [3](#0-2) 

The `pools` array only grows via `addPool` (`onlyOwner`) and there is no upper bound enforced on its size: [4](#0-3) 

This is the same bug class as the referenced Yieldy finding: an unbounded `for` loop over an admin-appendable list, reachable from ordinary (unprivileged) callers, whose gas cost grows unboundedly as the protocol's pool set naturally expands over time — not requiring any malicious admin action, just normal operational growth.

### Impact Explanation
If the `pools` array grows large enough (a realistic outcome of normal protocol operation as more Wombat LPs are onboarded), `castVotes` and `claimAllBribes` can exceed the block gas limit and revert unconditionally. Since `castVotes` is the only mechanism to submit/update votes to Wombat's voter and to harvest+forward bribe rewards to pool rewarders, a permanent revert here would:
- Freeze the flow of unclaimed bribe rewards from `WombatStaking`/`voter` into the per-pool `BribeRewardPool` rewarders, since rewards are only forwarded inside `castVotes` via `_forwardRewards`.
- Prevent any vote adjustments from ever being cast to the underlying Wombat voter, freezing the voting mechanism.

This matches the "permanent freezing of unclaimed yield" and "governance voting result manipulation/freeze" impact categories, since bribe rewards accrued in `WombatStaking` would become permanently unreachable by `WombatBribeManager`, and votes could never be re-cast to reflect users' current allocations.

### Likelihood Explanation
Likelihood depends entirely on the number of pools added via `addPool`, which is owner-controlled but represents ordinary, expected protocol growth (adding more Wombat LP pools over time is a normal administrative action, not an attack). Once the pool count is large enough that per-iteration external calls (`getVoteForLp` → `voter.getUserVotes`) push the aggregate gas cost past the block gas limit, the DoS becomes permanent and irreversible without a contract upgrade, since there is no pagination/limit parameter to work around it. This mirrors the original report's acceptance rationale ("acknowledged... only the owner of the contract can add addresses... kept Medium to highlight the importance to be aware of this").

### Recommendation
Add `offset`/`limit` (or explicit `address[] calldata lps`-only, non-full-array) pagination parameters to `castVotes` and `claimAllBribes`, allowing callers to process pools in bounded batches instead of iterating the entire `pools` array in a single transaction. Alternatively, cap the maximum number of pools that can be added via `addPool`, or maintain per-pool independent cast/claim entry points (as already partially exists via `harvestSinglePool`/`claimBribe`) as the primary mechanism, with the all-pools variants clearly gas-bounded or removed.

### Proof of Concept
1. Owner repeatedly calls `addPool(lp, rewarder, name)` to register new Wombat LP pools over time as the protocol's supported pool set grows: [4](#0-3) 
2. Once `pools.length` is large enough that the loop in `castVotes` (each iteration doing external calls via `getVoteForLp`) exceeds the block gas limit, any call to `castVotes(bool)` by any user reverts: [5](#0-4) 
3. Because `_forwardRewards` and vote submission only happen inside `castVotes`, bribe rewards accrued on `WombatStaking`/`voter` can no longer be harvested and forwarded, and votes can never be updated — a permanent freeze of yield and voting functionality.
