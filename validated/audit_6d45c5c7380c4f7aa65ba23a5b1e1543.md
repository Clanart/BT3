### Title
`SignableTransaction::new` excludes the OP_RETURN data output from the weight/fee and standardness calculations - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` charges `fee_per_vbyte` based on a weight estimate computed from only the inputs and payment outputs. When the caller supplies `data`, an OP_RETURN output is pushed into `tx_outs`, but `calculate_weight_vbytes` is invoked with `payments` only — never `tx_outs` — so the data output's bytes are not counted in `vbytes`, `needed_fee`, `fee_with_change`, or the `MAX_STANDARD_TX_WEIGHT` check. The result mirrors the Optimism bug: attacker-controlled `_data`/`data` bytes inflate the real transaction size while escaping the resource-cost bound, so the transaction underpays its fee (potentially below the relay minimum, which is itself checked against the under-counted `vbytes`) and can exceed the standard weight limit.

### Finding Description
In `SignableTransaction::new`:

1. The OP_RETURN output is appended to `tx_outs` before the weight estimate:

```rust
// networks/bitcoin/src/wallet/send.rs:194-204
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data).expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

2. `calculate_weight_vbytes` reconstructs a transaction containing only `inputs` and `payments` (plus optionally `change`) — the OP_RETURN output is never included:

```rust
// networks/bitcoin/src/wallet/send.rs:62-99
fn calculate_weight_vbytes(
  inputs: usize,
  payments: &[(ScriptBuf, u64)],
  change: Option<&ScriptBuf>,
) -> (u64, u64) {
  let mut tx = Transaction {
    ...
    output: payments.iter().map(...).collect(),
  };
  if let Some(change) = change { tx.output.push(...); }
```

3. All downstream accounting uses the under-counted values:
   - `needed_fee = fee_per_vbyte * vbytes` (line 206),
   - the minimum-relay-fee check `(DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (line 211),
   - `fee_with_change` when computing the change amount (lines 225-233),
   - the `weight > MAX_STANDARD_TX_WEIGHT` standardness check (line 241).

An OP_RETURN output carrying the maximum allowed 80 bytes of `data` (checked at line 171) adds roughly 90+ bytes / ~360 weight units (~90 vbytes) that are entirely uncharged and unchecked. Since `fee()` returns `inputs - outputs` and outputs include the zero-value OP_RETURN, the actual fee paid equals the under-estimated `needed_fee`, so the realized fee rate is strictly below `fee_per_vbyte` — and can silently fall below `DEFAULT_MIN_RELAY_TX_FEE` even though the check at line 211 passed, because the check divided the true fee across a smaller `vbytes`.

### Impact Explanation
- **Under-compensated resource use / DoS (the exact analog):** attacker-controlled `data` bytes consume block space and bandwidth without paying the requested fee rate, directly paralleling `_data` inflating `usedGas` while `_gasLimit` stays at the 21000 floor.
- **Unspendable/stuck funds:** a transaction whose true vsize puts it below the minimum relay fee, or above `MAX_STANDARD_TX_WEIGHT` (data pushes the true weight over the limit while `weight` stays under), will not relay or confirm. Inputs selected for it are effectively locked: the Serai wallet/processor builds and signs a transaction the network will never accept, and the spent `ReceivedOutput`s cannot be recovered by the scanner flow as a confirmed payment.
- **Incorrect fee accounting for callers:** `needed_fee()` returns a value that does not achieve `fee_per_vbyte` for the actual signed transaction, and change is credited against a fee that doesn't reflect the real size.

### Likelihood Explanation
`SignableTransaction::new` is public and takes `data: Option<Vec<u8>>` directly; any caller (including downstream processor/scheduler code paths or integrations) that passes a non-empty `data` triggers the undercount deterministically — no racing or special conditions required. The impact scales with data length up to the 80-byte cap. Whether it produces an under-minimum-fee or over-weight transaction depends on how close to the boundary the base transaction already is, but the fee rate is underpaid in every case where `data` is used, making this a Medium-severity accounting flaw.

### Recommendation
Include the OP_RETURN output in the weight estimate. Build the candidate `tx_outs` (or pass `data`/the OP_RETURN script) into `calculate_weight_vbytes` so `vbytes`, `needed_fee`, the relay-fee check, the change computation, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the actual transaction — analogous to the report's `_gasLimit >= 21_000 + _data.length * 16` fix. Concretely, `calculate_weight_vbytes` should accept the full output list (payments + OP_RETURN + optional change) rather than reconstructing outputs from `payments` alone.

### Proof of Concept
```rust
// Conceptual PoC against networks/bitcoin/src/wallet/send.rs

let data = vec![0u8; 80]; // maximum allowed by the TooMuchData check (line 171)

// With data:
let tx_with_data =
  SignableTransaction::new(inputs.clone(), &payments, change.clone(), Some(data), FEE).unwrap();

// Without data:
let tx_no_data =
  SignableTransaction::new(inputs.clone(), &payments, change, None, FEE).unwrap();

// The OP_RETURN output (~92 vbytes: 8-byte amount + ~84-byte script) is absent from the
// weight estimate, so:
assert_eq!(tx_with_data.needed_fee(), tx_no_data.needed_fee());
// Yet the signed transaction with data is ~92 vbytes larger, so its effective fee rate is
// FEE * vbytes_estimated / vbytes_actual < FEE, and it can fall below
// DEFAULT_MIN_RELAY_TX_FEE or exceed MAX_STANDARD_TX_WEIGHT without erroring.
```

Both branches at `send.rs:204` and `send.rs:225-226` call `calculate_weight_vbytes(tx_ins.len(), payments, ...)` — `payments` never contains the OP_RETURN output pushed at `send.rs:194-202`, confirming the omission.
