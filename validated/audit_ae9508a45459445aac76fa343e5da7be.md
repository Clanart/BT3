## Analysis

The DeFi report's broken invariant is: **a value computed and shown to the user at time T1 (expected shares/assets) is not re-validated at execution time T2, allowing an attacker who controls state in between to make the real outcome differ from what the user approved.**

In GitHub Desktop, `RebaseChooseBranchDialog` exhibits the same pattern for rebases, and the branch/remote content is attacker-controllable (a malicious/compromised remote).

### Title
Rebase executes against branch names instead of the previewed commit SHAs, letting a moved base-branch ref silently rebase onto un-reviewed commits - (File: app/src/ui/multi-commit-operation/choose-branch/rebase-choose-branch-dialog.tsx, app/src/lib/git/rebase.ts)

### Summary
When a user opens the "Rebase Current Branch" dialog, Desktop computes a `rebasePreview` (clean/conflicts, `commitsAhead`, `commitsBehind`) from a *snapshot* of `baseBranch.tip.sha` and `targetBranch.tip.sha` via `updateRebasePreview` [1](#0-0) . The user reviews this preview (e.g. "This will update X by applying N commits on top of Y") and clicks "Start rebase", which calls `dispatcher.startRebase(...)` → eventually `rebase(repository, baseBranch, targetBranch, ...)` [2](#0-1) . However the actual git invocation uses branch **names**, not the SHAs that were validated as conflict-free: [3](#0-2) 

`git rebase <baseBranch.name> <targetBranch.name>` resolves `baseBranch.name` to whatever the ref currently points to at execution time, not the `tip.sha` that was used to compute the "clean" preview and commit list shown to the user.

### Finding Description
The only staleness guard in the flow checks whether the *user's selection* changed (`computingRebaseForBranch !== baseBranch.name`) [4](#0-3) , and the merge-preview dialog similarly only checks `selectedBranch.tip.sha !== branch.tip.sha` against local state [5](#0-4) . Neither guard re-verifies that the branch's tip SHA is still the same **at the moment `rebase()`/`git rebase` actually executes**. If a background fetch updates the `origin/base` ref between preview computation and the user clicking "Start rebase" (Desktop performs periodic/background fetches independent of this dialog), `baseBranch.name` in the final `git rebase baseBranch.name targetBranch.name` call will resolve to the new tip — which may contain commits the user never saw, was never shown as "clean", and never approved. The rebase-flow documentation itself calls out that Desktop only warns about remote commits that would be "caught" by a rebase for confirmation-on-force-push purposes, not for detecting that the base branch itself moved before invoking rebase [6](#0-5) .

### Impact Explanation
This is a TOCTOU (time-of-check/time-of-use) gap analogous to the missing `minAmountOut` check: the user approves an outcome computed from a snapshot, but the operation that mutates their repository (`git rebase`) is executed against a live, mutable reference. An attacker who controls the remote (a plausible external attacker per the valid-impact criteria — "a git remote/proxy response") can push new commits to the tracked base branch in the window between preview and execution, causing the user's branch history to be silently rebased on top of attacker-influenced commits, without the "clean/N commits" confirmation the user actually saw. This corrupts what the user ultimately commits/pushes.

### Likelihood Explanation
Medium: it requires an attacker-controlled or compromised remote pushing at a precisely timed moment (or a background fetch racing with the dialog), and Desktop's periodic background fetch behavior makes the timing window realistic but not guaranteed on every rebase. It does not require local access, admin rights, or leaked credentials — only control of the remote content, matching the accepted attacker model.

### Recommendation
Capture and pass through the exact `baseBranch.tip.sha`/`targetBranch.tip.sha` that were validated during preview into the `rebase()` git invocation (e.g. `git rebase <sha> <sha>` or re-verify `getRefOrError`/`getBranchTip` equality immediately before invoking `git rebase`), and abort/re-prompt if the resolved tip differs from the previewed one — mirroring the `minAmountOut`-style "abort if actual result diverges from expected" fix recommended in the original report.

### Proof of Concept
1. User has `feature` branch tracking `origin/main`. User opens "Rebase Current Branch..." and selects `main` as the base.
2. `updateRebasePreview` computes `commitsAhead`/`commitsBehind` from the current `main.tip.sha`, and shows "This will update feature by applying 2 commits on top of main" (clean, no conflicts) [7](#0-6) .
3. Before the user clicks "Start rebase", the attacker (controlling the remote/proxy) pushes new commits to `main`; Desktop's background fetch updates the local `main`/`origin/main` ref.
4. User clicks "Start rebase" — `dispatcher.startRebase` is invoked with the same `Branch` object reference but the real ref `main` now points elsewhere; `rebase()` runs `git rebase main feature`, resolving `main` to the new tip [3](#0-2) .
5. The rebase completes "without error" using commits the user never reviewed in the "clean" preview, and the app reports `RebaseResult.CompletedWithoutError` as if the previewed outcome occurred [8](#0-7) .

export async function updateRebasePreview(
  baseBranch: Branch,
  targetBranch: Branch,
  repository: Repository,
  onUpdate: (rebasePreview: RebasePreview | null) => void

  const computingRebaseForBranch = baseBranch.name

    kind: ComputedAction.Loading,

## Warning about remote commits

If the target branch is tracking a remote branch and the user has enabled the
_Show confirmation dialog before force pushing_ setting, Desktop
will check if any commits exist in the range

This check is important to identify any remote commits that will be caught in
this rebase, because their existence would require rewriting the history on the remote,
