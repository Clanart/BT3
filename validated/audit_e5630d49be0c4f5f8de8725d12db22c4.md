### Title
Symlink-following arbitrary file write/creation via DataLayer delta/full-tree file download (predictable filenames + non-exclusive `open(..., "wb")`) - (File: `chia/data_layer/download_data.py`)

### Summary
Chia's DataLayer downloads delta/full-tree `.dat` files to deterministic, attacker-predictable filesystem paths and writes them using non-exclusive `open(path, "wb")` (or plain `os.path.exists()` guards) instead of atomic, symlink-safe creation (`"xb"`/`O_EXCL`). A local unprivileged user who can write into the shared `server_files_location`/`client_foldername` directory (a realistic condition for shared-cache/multi-tenant DataLayer deployments) can pre-plant a symlink at the exact predictable filename the DataLayer service will later use, causing the service to create or overwrite an arbitrary file elsewhere on the filesystem when it performs a legitimate download/write — the same bug class as CVE-2026-65010 (`Extractor.extract()` symlink-following write).

### Finding Description
Delta/full-tree filenames are fully deterministic, generated from `store_id`, `root_hash`, and `generation` via `get_delta_filename`/`get_full_tree_filename_path` [1](#0-0) , and validated only for format (`is_filename_valid`), not for symlink safety [2](#0-1) . Since `store_id` (the singleton launcher id) and the chain-published root hash/generation sequence are public, any local user sharing the `client_foldername`/`server_files_location` directory (documented as a shared, plugin/mirror-writable, lock-TODO location — see `.cursor/context/data-layer.md` "File-system writes for Merkle blobs, key/value blobs, and `.dat` files have TODOs around locking") can compute the exact future filename and pre-plant a symlink there before the real download happens.

The vulnerable write paths do not check for an existing symlink and use non-exclusive write mode:
- `download_file()` first checks `if target_filename_path.exists(): return True` [3](#0-2) . `Path.exists()` follows symlinks, so a broken symlink (pointing to a not-yet-existing path) evaluates to `False`, allowing the flow to proceed.
- `http_download()` then opens the target path with plain `"wb"` mode and streams downloaded content into it: [4](#0-3) . `open(path, "wb")` follows an existing symlink and writes through it to whatever file the symlink points to, creating it if missing or truncating/overwriting it if present.
- The full-tree file write inside `insert_from_delta_file()` uses the same unguarded pattern: `with open(filename_full_tree, "wb") as writer: ...` [5](#0-4) .
- `DataLayer.fetch_and_validate()` has an equivalent race: `if not os.path.exists(filename_full_tree): with open(filename_full_tree, "wb") as writer: ...` [6](#0-5) . `os.path.exists()` also follows symlinks and returns `False` for broken links, letting `open(..., "wb")` create the linked-to file.
- The S3 plugin's `download()` handler exhibits the same pattern: it computes `target_filename` from a validated-but-attacker-influenceable filename, creates the parent directory, and calls `my_bucket.download_file(filename, str(target_filename))`, which internally opens the destination path directly without symlink checks [7](#0-6) .

By contrast, `write_files_for_root()` uses `mode: Literal["wb", "xb"] = "wb" if overwrite else "xb"` [8](#0-7)  — the `"xb"` (`O_CREAT|O_EXCL`) branch is symlink-safe because `O_EXCL` fails if any directory entry (including a dangling symlink) already exists at that path. This shows the codebase already knows the mitigation pattern but does not apply it consistently to the download/write paths described above.

### Impact Explanation
A local attacker with write access to the shared DataLayer file-serving/client folder can cause the DataLayer service (running as another user or with different privileges, e.g. in a shared hosting/mirror environment) to create or overwrite an arbitrary file at a location the attacker chooses, using content sourced from the legitimate download (delta/full-tree data) but landing at an attacker-chosen path instead of the intended one. This satisfies "unauthorized coin/file-system state divergence" via a spend/RPC-adjacent local action (DataLayer client operation), and matches the High severity profile of the reference CVE (arbitrary file write/overwrite, potential further escalation depending on target file, e.g. config files, other services' data, or cron/systemd unit files reachable by the DataLayer service account).

### Likelihood Explanation
Exploitation requires: (1) local co-location with a running DataLayer service/plugin sharing a writable directory (`server_files_location`/`client_foldername`, or the S3 plugin's `server_files_path`), and (2) ability to predict the exact filename, which is straightforward since `store_id`, root hashes, and generations for actively-syncing stores are observable via wallet/DataLayer RPC or on-chain singleton history. No cryptographic secrets are needed. This is a realistic scenario in shared-cache/multi-tenant DataLayer or S3-plugin deployments, which the module's own documentation flags as an area with locking TODOs.

### Recommendation
- Replace all non-exclusive `open(path, "wb")` writes of downloaded/generated DataLayer files with `O_CREAT|O_EXCL` semantics (mode `"xb"` or `os.open` with `os.O_CREAT | os.O_EXCL | os.O_NOFOLLOW`), matching the existing safe pattern already used in `write_files_for_root()`.
- Before any `exists()`/`os.path.exists()` gate that decides whether to skip a download, explicitly check `path.is_symlink()` and refuse to proceed (or delete the symlink first) rather than trusting the resolved existence check.
- Apply the same fix to `insert_from_delta_file()`'s full-tree write, `DataLayer.fetch_and_validate()`'s full-tree write, and the S3 plugin's `download()`/`upload()` target paths.
- Consider resolving the destination directory once (`os.path.realpath`) and validating the final component is not a symlink prior to any file-system operation performed against attacker-influenceable, predictable filenames.

### Proof of Concept
1. On a host running a DataLayer service configured with `server_files_location` (or an S3 plugin `server_files_path`) shared with an unprivileged local user, the attacker observes the target `store_id` and the next expected root hash/generation (available via public DataLayer/wallet RPC or on-chain singleton history).
2. The attacker computes the exact delta filename via `get_delta_filename(store_id, root_hash, generation, group_by_store)` logic in `chia/data_layer/data_layer_util.py`.
3. The attacker creates a symlink at that computed path pointing to a target file the attacker wants to overwrite/create (e.g. `~/.config/chia/mainnet/config/config.yaml` for the DataLayer service user), before the real generation arrives.
4. When `DataLayer.update_subscription()` → `fetch_and_validate()` → `insert_from_delta_file()` → `download_file()` → `http_download()` runs for that generation, `target_filename_path.exists()` returns `False` (symlink target doesn't exist yet), so `http_download()` opens the symlink path with `"wb"` and writes the downloaded delta content through it, creating/overwriting the attacker-chosen file at the symlink's target location [9](#0-8) [10](#0-9) .

def is_filename_valid(filename: str, group_by_store: bool = False) -> bool:
    if group_by_store:
        if filename.count("/") != 1:
            return False
        filename = filename.replace("/", "-")

    split = filename.split("-")

    try:
        raw_store_id, raw_node_hash, file_type, raw_generation, raw_version, *rest = split
        store_id = bytes32(bytes.fromhex(raw_store_id))
        node_hash = bytes32(bytes.fromhex(raw_node_hash))
        generation = int(raw_generation)
    except ValueError:
        return False

    if len(rest) > 0:
        return False

    # TODO: versions should probably be centrally defined
    if raw_version != "v1.0.dat":
        return False

    if file_type not in {"delta", "full"}:
        return False

    generate_file_func = get_delta_filename if file_type == "delta" else get_full_tree_filename
    reformatted = generate_file_func(
        store_id=store_id, node_hash=node_hash, generation=generation, group_by_store=False
    )

    return reformatted == filename

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
            progress_byte = 0
            progress_percentage = f"{0:.0%}"
            success = False
            try:
                with target_filename_path.open(mode="wb") as f:
                    async for chunk, _ in resp.content.iter_chunks():
                        f.write(chunk)
                        progress_byte += len(chunk)
