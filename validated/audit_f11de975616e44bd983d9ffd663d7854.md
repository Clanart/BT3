### Title
Desktop silently rewrites the `origin` remote URL from an untrustworthy GitHub API `clone_url` field, redirecting future pushes/pulls without user confirmation - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
This mirrors the Super DCA "manager overwrites state without applying/confirming the prior value" bug class: a security-relevant piece of state (the git `origin` remote URL, which determines where the user's commits are pushed and where code is fetched from) is overwritten automatically, based on server-supplied data, with no user confirmation step — unlike the equivalent `upstream` remote flow in the same codebase, which explicitly requires user confirmation via a dialog.

### Finding Description
`updateRemoteUrl` in [1](#0-0)  compares the repository's current `origin` remote against the `clone_url` field of an `IAPIRepository` object fetched from the GitHub API, and — if the protocol matches and the previously cached `cloneURL` still matches the local remote — silently calls `gitStore.setRemoteURL(...)` to rewrite `origin` to the new URL, with **no user prompt at all**: [2](#0-1) 

This is wired into the normal, unprivileged repository-refresh path. `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository(owner, name)` and then immediately feeds the resulting `apiRepo` into `updateRemoteUrl`: [3](#0-2) 

That helper is invoked as part of `_pull` (`withRefreshedGitHubRepository(repository, ...)` wrapping `performPull`), so the remote can be rewritten every time the user pulls — a completely ordinary, unprivileged action that requires no special user awareness that a config value is about to change: [4](#0-3) 

The only "guard" is `urlMatchesRemote`, which merely parses hostname/owner/repo-name structurally and requires matching protocol — it does not pin the hostname to the account's expected GitHub/GHES endpoint, nor does it require the new host to equal the old host: [5](#0-4) 

Contrast this with the `upstream` remote flow in the very same codebase, where an analogous URL change (updating/creating the `upstream` remote to point at a fork's parent) is treated as sensitive enough to require an explicit dialog and user confirmation (`UpstreamAlreadyExists`/`onUpdate`/`onIgnore`): [6](#0-5) [7](#0-6) 

The corrupted value here is the `origin` remote URL stored in `.git/config` — the exact destination Desktop will push to and fetch from on all subsequent operations, applied based on `apiRepo.clone_url`, which is data returned from a GitHub API request (`api.fetchRepository`, `ghRequest('GET', 'repos/{owner}/{name}')`). Nothing downstream re-validates that the new URL still belongs to the account/endpoint the user believes they're working with before the git remote is silently rewritten.

### Impact Explanation
If the value returned for `clone_url` by the API response for a given `owner/name` diverges from what the user expects (e.g., through a compromised/malicious GitHub Enterprise Server the user has added as an account, a repository transfer/rename chain controlled by a party other than the current user, or any tampering of the API response reaching the Desktop client), Desktop will automatically rewrite `origin` to the new URL and continue to use it for all future pulls/pushes with **no notification to the user**. This is a silent corruption of what the user pushes to and fetches from — potentially sending commits (and any git credential negotiation associated with that host) to an unintended remote — while the UI gives the user no indication a change occurred, unlike the parallel `upstream` remote flow that explicitly prompts.

### Likelihood Explanation
The vulnerable code path (`_pull` → `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`) executes on ordinary, frequent, unprivileged user actions (pulling), requiring no special permissions, no local/physical access, and no prior compromise of the user's machine — only that the attacker be able to influence the `IAPIFullRepository`/`IAPIRepository` object returned for the tracked `owner/name` (an explicitly permitted primitive per the task's valid-impact list). The existing guard (`urlMatchesRemote`/protocol check) does not stop this because it only verifies URL *structure* consistency, not that the host is the one the account/user actually trusts.

### Recommendation
Do not silently rewrite `origin` based on API data. At minimum, mirror the `upstream` remote's UX: surface a confirmation dialog (similar to `UpstreamAlreadyExists`) before calling `setRemoteURL` on `origin`, and/or pin the expected hostname to the account's configured endpoint so a differing host can never be silently substituted, regardless of protocol match.

### Proof of Concept
1. User has a repository tracked by Desktop, with `gitHubRepository.cloneURL` cached and `origin` set to a matching URL.
2. On the next `_pull` (a completely normal action), Desktop calls `api.fetchRepository(owner, name)`, obtaining an `IAPIFullRepository` whose `clone_url` differs from the current remote but shares the same URL scheme (e.g., due to a compromised/malicious GHES response or repository takeover).
3. `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:42-44`) sees `protocolsMatch && remoteUrlUnchanged && !urlsMatch` and calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)`.
4. `git remote set-url origin <new_url>` executes silently (`app/src/lib/git/remote.ts:56-64`) — no dialog, no log visible to the user.
5. All subsequent pushes/fetches from that point go to `<new_url>` instead of the URL the user originally configured, with the UI showing no warning that the remote changed.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
