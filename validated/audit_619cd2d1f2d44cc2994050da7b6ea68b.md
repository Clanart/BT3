### Title
FROST single-use preprocess reused across signing sessions sharing a context, enabling nonce reuse and secret-share/key recovery - (File: coordinator/src/tributary/signing_protocol.rs, crypto/frost/src/sign.rs)

### Summary
`SigningProtocol::preprocess_internal` deterministically derives FROST nonces from a cached 32-byte seed stored under `CachedPreprocesses[context]`, and never deletes or rotates the entry. The cache key `context` for `DkgConfirmer` is only `(b"DkgConfirmer", attempt)` — it does not include the validator set, session, or genesis. Any second signing session that reuses the same key and context — a new validator set's DKG attempt with the same attempt number, or a node rebuilt onto an alternate chain history — reproduces identical nonces while the message and participant set differ, leaking the secret key to anyone who observes both published signature shares. This is the direct analog of the reported "single-use token bypass via concurrent/repeated requests": the single-use FROST preprocess is consumed repeatedly because the dedup/check state (`CachedPreprocesses`) never marks it spent.

### Finding Description
In `crypto/frost/src/sign.rs`, `AlgorithmMachine::seeded_preprocess` derives all FROST nonces from a `ChaCha20Rng` seeded by `CachedPreprocess` (lines 121–144), and `AlgorithmSignMachine::from_cache` reconstructs a machine from that seed (lines 268–274). The trait docs explicitly state reuse of a cached preprocess "enables recovery of your private key share" (lines 209–213, 216–219).

In `coordinator/src/tributary/signing_protocol.rs`, `preprocess_internal`:

- Computes the DB key as `self.context.encode()` (line 110), where `context = (b"DkgConfirmer", self.attempt)` (line 275) — no `self.spec.set()`, session, or `spec.genesis()` is bound into it.
- Only writes the seed if `CachedPreprocesses::get` returns `None` (lines 123–134), and **never deletes it after use** — every subsequent `preprocess`, `share`, and `complete` for the same context calls `from_cache` on the identical seed (lines 137–145).

The consumed-share paths are:

- `generated_key_pair` → `DkgConfirmer::share` → `share_internal` → `preprocess_internal` (handle.rs:47–60, signing_protocol.rs:288–310).
- `DkgConfirmed` handling → `DkgConfirmer::complete` → `share_internal` again → `preprocess_internal` (handle.rs:533–535, signing_protocol.rs:312–327).

The file's own header acknowledges the hazard: "it is explicitly unsafe to reuse nonces across signing sessions... Safety is derived from the nonces being context-bound" (lines 25–27). The binding fails because the context omits the validator-set identity. A validator key `self.our_key` persists across validator sets, and `attempt` restarts from 0 for each new set's DKG (`AttemptDb` is keyed per-genesis, but the preprocess cache is not). The first attempt-0 DKG confirmation of set N+1 therefore reuses the exact nonce seed of the attempt-0 confirmation of set N, while `musig(musig_context(set), key, participants)` and `set_keys_message(set, removed, key_pair)` differ — producing two Schnorr signature shares `s = k + c·λ·secret` under the same `k` with different challenges, from which the validator's MuSig secret key is recovered algebraically. Both shares are published on-chain (`Transaction::DkgConfirmed`), so any observer can perform the recovery.

A secondary, same-set reuse path: `complete` internally re-runs `share_internal`, and `share` itself is invoked once per `(attempt, key_pair)` without any "already signed" marker tied to the resulting message — if `generated_key_pair` is ever reached with a different `key_pair` for the same attempt (the DB writes `DkgKeyPair::set`/`KeyToDkgAttempt::set` unconditionally overwrite at handle.rs:54–55), the same nonces sign a different `set_keys_message`.

### Impact Explanation
Reuse of a Schnorr/FROST nonce across two distinct challenges yields the long-lived secret via `secret = (s₁ − s₂) / (c₁λ₁a₁ − c₂λ₂a₂)`. Here the compromised secret is the coordinator validator's MuSig key — the root of trust used to confirm DKG results on-chain via `publish_set_keys`. With it, an attacker can forge future `set_keys` confirmations for validator sets containing that key, i.e., attest to arbitrary threshold keys and thus control/brick the validator set's assets. Severity: High.

### Likelihood Explanation
Triggering requires the same coordinator key to participate in a second signing session under the same `(b"DkgConfirmer", attempt)` context with a different message — which occurs whenever a node rejoins a new validator set (attempt counters reset per genesis, the cache key does not) or rebuilds onto a divergent chain history after a partial-state restore, both anticipated in the code's own comments (lines 38–48 note rebuilds are expected to "re-decide nonces," but the DB-persisted cache makes re-decision impossible without wiping `CachedPreprocesses`). No privileged position is needed to harvest the two published `DkgConfirmed` shares; they are public on-chain data. Medium likelihood.

### Recommendation
- Bind the session identity into the cache context: `context = (b"DkgConfirmer", spec.set(), spec.genesis(), attempt)`, and also bind it into the encryption-key preimage (currently `b"Cached Preprocess Encryption Key" || context`).
- Delete `CachedPreprocesses[context]` in `share_internal` immediately after `from_cache`, so a used seed can never produce a second `sign`, matching the "preprocess MUST only be used once" requirement in `crypto/frost/src/sign.rs:85–87`.
- Before publishing a share, verify on-chain that the commitment derived from the cached seed matches this node's previously published confirmation nonces (the TODO at signing_protocol.rs:50–54).

### Proof of Concept
1. Coordinator key `k` is in validator set S₁; during DKG attempt 0, `preprocess_internal` stores seed `s` under `CachedPreprocesses[(b"DkgConfirmer", 0)]` and the node publishes its confirmation nonce and later its `DkgConfirmed` share `σ₁` for `set_keys_message(S₁, removed₁, kp₁)` (public on tributary).
2. `k` is also in set S₂ (or S₁'s instance is rebuilt onto a divergent history). DKG attempt 0 of S₂ hits `CachedPreprocesses::get(...).unwrap()` at signing_protocol.rs:137 — no new seed is generated — and `from_cache` reproduces identical nonces via `ChaCha20Rng::from_seed(*seed.0)` (frost/src/sign.rs:127–132).
3. The node publishes `σ₂` for `set_keys_message(S₂, removed₂, kp₂)` under the same nonce `k_nonce` but a different challenge `c₂`, MuSig coefficient `a₂`, and participant set.
4. Observer reads `σ₁, σ₂` and the published preprocesses, computes `secret = (σ₁ − σ₂) / (c₁·λ₁·a₁ − c₂·λ₂·a₂)` (all denominators public), recovering the validator's MuSig secret share and enabling forged `set_keys` confirmations.

Note: the trigger (cross-set key reuse / chain rebuild) depends on deployment behavior of the coordinator, and `handle.rs`/`signing_protocol.rs` sit outside the strictly enumerated crate list; the cryptographic root cause — deterministic seed-derived nonces and a cache that is read but never consumed — is in the in-scope `crypto/frost` (`seeded_preprocess`, `from_cache`, `CachedPreprocess` single-use contract).
