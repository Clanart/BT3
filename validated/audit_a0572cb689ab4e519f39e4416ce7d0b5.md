### Title
Instant reward-checkpoint model in `queueNewRewards` lets an attacker sandwich `harvest()` with atomic deposit/withdraw to steal a disproportionate share of freshly harvested WOM/MGP rewards - (File: `rewards/BaseRewardPool.sol`, `wombat/WombatStaking.sol`, `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.harvest()` is a completely unprivileged call into `IWombatStaking.harvest(lpToken)`, which pulls all pending WOM from Master Wombat and immediately calls `IBaseRewardPool.queueNewRewards()`. `BaseRewardPool._provisionReward()` distributes the harvested lump sum as a single instantaneous checkpoint (`rewardPerTokenStored += amount * 1e_dec / totalStaked()`), rather than streaming it over time. Because `totalStaked()` is simply the current `stakingToken.balanceOf(masterMagpie)` at the moment `queueNewRewards` executes, an attacker can inflate `totalStaked()` immediately before the checkpoint and hold that inflated balance only for the instant of the checkpoint, then withdraw, capturing a share of rewards accrued by other stakers over the entire preceding period.

### Finding Description
The reward flow is:
- `WombatPoolHelperV2.depositLP()` → `WombatStaking.depositLP()` → `MasterMagpie.depositFor()` → `_deposit()`, which calls `_harvestBaseRewarder(_stakingToken, _account)` **before** `user.amount` is incremented [1](#0-0) . This call routes into `BaseRewardPool.getReward` (`updateReward` modifier → `_updateFor`), which checkpoints `userRewardPerTokenPaid[_account] = rewardPerToken(_rewardToken)` at the **pre-deposit** value [2](#0-1) .
- `WombatPoolHelperV2.harvest()` → `IWombatStaking.harvest(lpToken)` is callable by any address (`whenNotPaused _onlyActivePool` only checks the pool is registered, not the caller) [3](#0-2) . This triggers `_toMasterWomAndSendReward` → `queueNewRewards` on the rewarder [4](#0-3) .
- `BaseRewardPool.queueNewRewards` → `_provisionReward` updates `rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / totalStaked()` **instantly**, using whatever `totalStaked()` (i.e., `stakingToken.balanceOf(masterMagpie)`) is at that exact call [5](#0-4) . There is no time-weighted accrual (no `rewardRate`/`periodFinish` streaming model as in Synthetix-style `StakingRewards`); the entire lump sum is checkpointed against the instantaneous balance.
- `WombatPoolHelperV2.withdraw()` → `MasterMagpie.withdrawFor()` → `_harvestAndUnstake()` calls `_harvestBaseRewarder` again, which computes `earned = balanceOf(_account) * (rewardPerToken - userRewardPerTokenPaid) / 1e_dec` [6](#0-5) . Because the attacker's `balanceOf` is now large (their fresh deposit) and `rewardPerToken` jumped due to the harvest that occurred while their large balance was in `totalStaked`, they collect a reward share proportional to `theirBalance / totalStakedAtCheckpoint`, despite having staked for effectively zero elapsed time.

This is a classic "flash-stake around reward checkpoint" pattern: since `queueNewRewards` performs a single point-in-time distribution rather than continuous streaming, whoever holds the largest balance exactly when `queueNewRewards` executes captures a disproportionate share of the WOM harvested since the last call, at the expense of honest long-term stakers who were diluted by the attacker's presence during that single checkpoint. There is no cooldown, no minimum holding period, no `nonReentrant` interplay preventing this, and `harvest()` carries no access restriction — any address can trigger it deterministically inside their own atomic transaction, right after depositing.

### Impact Explanation
This results in direct theft of unclaimed yield / user funds: rewards that honest LPs accrued over the elapsed period (proportional to their time-weighted stake) are redirected to the attacker's flash stake, diluting genuine depositors' share of the harvested WOM (and any MGP paid through similar `queueNewRewards`/`queueMGP` checkpoint mechanisms) without the attacker bearing time-weighted exposure. This matches Immunefi's "theft of unclaimed yield" / "direct theft of user funds" impact class.

### Likelihood Explanation
Fully feasible for any unprivileged actor: `depositLP`, `harvest`, and `withdraw` are all public/external and can be called sequentially in one attacker-controlled transaction (single contract call, no cross-block dependency required, though same-block execution maximizes gain since price/AMM slippage on the LP token round-trip is the only capital cost). Capital requirement scales with the amount needed to dominate `totalStaked()` relative to the pending WOM reward size; it is repeatable every time a meaningful amount of WOM accrues and someone (attacker or bot) calls `harvest()`. No special permissions, oracle manipulation, or governance access needed.

### Recommendation
Convert `BaseRewardPool`/related rewarders (`mWOMSVBaseRewarder`, `vlMGPBaseRewarder`) to a time-weighted/streamed reward model (e.g., Synthetix-style `rewardRate` + `periodFinish`, updated continuously via `lastUpdateTime`) instead of an instantaneous `rewardPerTokenStored += amount/totalStaked()` checkpoint. Alternatively, require a minimum staking duration before a deposit is eligible to receive newly queued rewards (checkpoint balances at the start of the epoch, not at call time), or restrict/deprioritize `queueNewRewards` timing to prevent same-block deposit-harvest-withdraw sandwiching (e.g., snapshot `totalStaked`/individual balances prior to the block in which harvest occurs).

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `BaseRewardPool` (WOM rewarder), `WombatStaking`, `WombatPoolHelperV2` with mocked Master Wombat/Wombat Pool that accrues a fixed pending WOM reward over simulated time.
2. Have Honest User A deposit `100` LP at `t=0` and hold for `N` blocks while WOM accrues in Master Wombat.
3. At block `t=N`, Attacker contract in one transaction: `depositLP(9900)` (dominating `totalStaked`) → `harvest()` (triggers `queueNewRewards` with the full accrued WOM against `totalStaked = 10000`) → `withdrawFor` all `9900`.
4. Assert: Attacker's `getReward` payout ≈ `9900/10000` of the harvested WOM despite 0 time-weighted stake, while Honest User A (who staked `100` for the entire `N` blocks) only receives ≈ `100/10000`, violating conservation relative to time-weighted stake share.
5. Compare captured share vs. expected time-weighted share (`stake*duration` integral) to quantify the theft, confirming the reward distribution ignores duration entirely.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
