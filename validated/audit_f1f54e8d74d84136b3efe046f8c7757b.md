Based on my investigation, the OAuth CSRF `state` value is validated on every callback, but the check design still permits a griefing race analogous to the `delegateBySig` nonce race: whichever `code`+`state` pair reaches `resolveOAuthRequest` first "wins" the single-use authorization code, and the loser is left unable to complete sign-in, with no retry path for the legitimate flow.

### Title
Griefer can block a user's GitHub sign-in by racing the OAuth callback deep link - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
`SignInStore.authenticateWithBrowser` opens the system browser to GitHub's `/login/oauth/authorize` endpoint and stores a locally generated CSRF `state` token, then waits for the OS to deliver a `x-github-client://oauth?code=...&state=...` deep link back to the app [1](#0-0) . When the callback arrives, `resolveOAuthRequest` checks that `action.state` matches the stored `state`, and if it matches, immediately redeems the one-time `code` via `requestOAuthToken` [2](#0-1) . GitHub OAuth authorization codes are single-use: whichever request reaches GitHub's token endpoint first consumes the code, and any subsequent redemption attempt with the same code fails.

### Finding Description
The redirect URL containing the live `code` and `state` values is not confidential once it leaves GitHub's redirect and is handed to the OS via the browser: it is fully visible in browser history, address-bar navigation, browser extensions, and any process capable of inspecting the OS "open URL"/protocol-activation event (macOS `open-url`, Windows CLI argument) before Desktop's own handler processes it [3](#0-2) [4](#0-3) . If an attacker (a griefer app, browser extension, or anything else with the ability to read or replay OS-level protocol-activation events on the same machine before Desktop processes it) captures this URL and redeems it against GitHub's token endpoint first — using the exact same technique `requestOAuthToken` uses — the code is invalidated at GitHub. When Desktop's own `resolveOAuthRequest` subsequently calls `requestOAuthToken(endpoint, action.code)` with the same, now-invalidated code, GitHub rejects it, and the flow fails hard: `onAuthError(new Error('Failed retrieving authenticated user'))` [5](#0-4) . There is no retry, no re-request of the authorization code, and no distinguishing between "code already consumed by attacker" and any other network failure — the user is simply told sign-in failed and must restart the entire OAuth flow from scratch.

This mirrors the report's broken invariant exactly: a one-time-use authorization artifact (nonce/signature in the report, OAuth `code` here) can be observed and redeemed out-of-band by an attacker, causing the legitimate holder's otherwise-valid transaction/request to permanently fail because the artifact is already spent. The `state` CSRF check in `resolveOAuthRequest` [6](#0-5)  does not stop this: it verifies the callback matches the expected session, but it does not, and cannot, prevent the underlying `code` from having been consumed by a third party before Desktop's request lands, since `state` and `code` travel together in the same observable URL.

### Impact Explanation
A user attempting to sign in to GitHub.com or a GitHub Enterprise instance from Desktop can be reliably blocked from completing authentication. Since sign-in is a prerequisite for pushing, cloning private repos, or using many Desktop features, this is a meaningful denial-of-service against a specific, non-privileged operation the user initiated themselves, matching the report's "user can be blocked from claiming airdrop" impact class (blocked from completing a legitimate one-time action).

### Likelihood Explanation
Exploitation requires the attacker to observe or intercept the OS-level protocol-activation payload before Desktop's handler consumes it — e.g., another locally-registered handler for the same custom URI scheme, a malicious browser extension with tab/history access, or software monitoring OS `open-url`/CLI-argument events. This is a real, previously documented risk class for custom-URI-scheme OAuth callbacks (as opposed to loopback-redirect OAuth), which is why RFC 8252 recommends loopback interfaces or PKCE-hardened flows over bare custom schemes for native apps. It does not require server-side compromise or credential leakage, only visibility into local URL-open events, which is plausible for other installed software without requiring privileged/admin access.

### Recommendation
Adopt PKCE (RFC 7636) for the OAuth authorization-code exchange so that redeeming the intercepted `code` alone is insufficient without the locally-held `code_verifier`, which never leaves the app. Additionally, treat a `requestOAuthToken` failure distinctly from other errors and surface a specific, actionable "sign-in link already used — please try signing in again" message with an automatic restart of `authenticateWithBrowser`, rather than a terminal failure requiring the user to manually notice and retry.

### Proof of Concept
1. User clicks "Sign in" in Desktop; `authenticateWithBrowser` opens `getOAuthAuthorizationURL(endpoint, csrfToken)` in the system browser [7](#0-6) .
2. User authorizes on GitHub; GitHub redirects the browser to `x-github-client://oauth?code=<CODE>&state=<STATE>`.
3. Before Desktop's `open-url`/protocol-launcher handler processes this URL [3](#0-2) , an attacker process on the same machine that observes this URL (e.g., via a competing scheme handler or history/extension access) sends `POST /login/oauth/access_token` with the same `client_id`/`code`, exactly matching `requestOAuthToken`'s request shape [8](#0-7) , consuming the one-time code at GitHub.
4. Desktop's own handler now runs `resolveOAuthRequest`, `state` matches, so it proceeds to call `requestOAuthToken(endpoint, action.code)` with the already-spent code [9](#0-8) .
5. GitHub rejects the reused code, `requestOAuthToken` returns `null`, and the user sees `onAuthError(new Error('Failed retrieving authenticated user'))` [10](#0-9)  — sign-in fails and must be restarted from step 1.

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
