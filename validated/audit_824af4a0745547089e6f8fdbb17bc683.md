## Analog Found

Confirmed: `ExtendProgram` (the unchecked variant reached via `UpgradeableLoaderInstruction::ExtendProgram`) is dispatched with `check_authority = false` [1](#0-0) , and `common_extend_program` only performs the authority-signer check when `check_authority` is `true` [2](#0-1) . That means anyone can submit a valid `ExtendProgram` instruction for any upgradeable program's `ProgramData` account, supplying only a payer to cover any rent shortfall (which can be `0` if the account already holds sufficient lamports) [3](#0-2) , with `additional_bytes` as small as `1` when `loader_v3_minimum_extend_program_size` is not active [4](#0-3) .

Every successful `ExtendProgram` call unconditionally rewrites `ProgramData.slot = clock_slot` [5](#0-4) , and the guard against a second extend in the same slot checks `clock_slot == slot` and returns `InstructionError::InvalidArgument` ("Program was extended in this block already") [6](#0-5) , exactly as demonstrated in `test_failed_extend_twice_in_same_slot` [7](#0-6) .

### Title
Unprivileged `ExtendProgram` DoS blocks legitimate program-data extension via the one-extend-per-slot guard - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
`common_extend_program` enforces "one extend per slot" by comparing the incoming clock slot to the `ProgramData` account's stored `slot` field [6](#0-5) . This is structurally identical to the reported `FeeDistributor.checkpointToken()` bug: a shared, frequency-limited state field can be updated by an unprivileged/unauthorized caller, which then causes the legitimate caller's subsequent call in the same window to revert.

### Finding Description
The unchecked `ExtendProgram` instruction requires no signature from the program's upgrade authority — `check_authority` is hardcoded to `false` for this instruction path [8](#0-7) . Any transaction sender can target an arbitrary program's `ProgramData` account, supply themselves (or the target account's existing balance) as payer, and request a minimal `additional_bytes` extension. This mutates `ProgramData.slot` to the current slot for every successful call [5](#0-4) . Because the guard rejects any extend attempt when `clock_slot == slot` [9](#0-8) , an attacker who submits (or repeatedly submits, one per slot) a cheap unauthorized `ExtendProgram` transaction against a target program can perpetually keep `ProgramData.slot` pinned to "this slot," causing every subsequent `ExtendProgram`/`ExtendProgramChecked` call from the legitimate upgrade authority in that same slot to fail with `InstructionError::InvalidArgument`.

### Impact Explanation
This blocks the legitimate program-upgrade workflow (`cli/src/program.rs::extend_program_data_if_needed`, used automatically before redeploys to grow `ProgramData` when the new program image is larger) [10](#0-9) . An attacker can force upgrade/redeploy transactions that depend on `ExtendProgram` succeeding first to keep failing, indefinitely delaying legitimate program upgrades for the targeted program — a low-cost, unprivileged availability/griefing primitive against on-chain program maintenance, not requiring any special privilege, leaked key, or trusted role.

### Likelihood Explanation
Likelihood is high for a determined attacker: the instruction is permissionless by design (no signer/authority check), the cost is a single minimal extension (as little as 1 additional byte when the SIMD-0431 minimum-size feature is inactive, or a fixed ~10KiB otherwise) plus transaction fees, and the guard condition (`clock_slot == slot`) is deterministic and easy to keep triggering slot after slot. It does not require front-running a specific victim transaction — it only requires the attacker to have made *any* prior extension in the same slot before the authority's transaction lands, which is a repeatable, standing DoS rather than a one-off race.

### Recommendation
Require the upgrade authority's signature (or otherwise scope the "extend in this slot" bookkeeping per-caller rather than as shared account state) for the unchecked `ExtendProgram` instruction, or decouple the anti-repeat-extend guard from a value that any unauthorized party can mutate. At minimum, only an authorized party (the upgrade authority, or a payer acting on their behalf with authority co-signature) should be able to advance `ProgramData.slot`.

### Proof of Concept
1. Attacker identifies target program `P` with `ProgramData` account `PD` (public info).
2. Attacker submits `extend_program(&P, Some(&attacker_payer), 1)` each slot, needing no signature from `P`'s upgrade authority [1](#0-0) [2](#0-1) .
3. This call succeeds, updates `PD.slot = current_slot` [5](#0-4) .
4. Legitimate upgrade authority submits `ExtendProgramChecked` in the same slot (e.g., as part of an automated redeploy flow) and receives `InstructionError::InvalidArgument` ("Program was extended in this block already"), matching the exact failure path exercised in `test_failed_extend_twice_in_same_slot` [11](#0-10) .
5. Attacker repeats step 2 every slot to sustain the block indefinitely at minimal cost.

async fn extend_program_data_if_needed(
    initial_instructions: &mut Vec<Instruction>,
    rpc_client: &RpcClient,
    commitment: CommitmentConfig,
    fee_payer: &Pubkey,
    program_id: &Pubkey,
    program_len: usize,
) -> Result<(), Box<dyn std::error::Error>> {
    let program_data_address = get_program_data_address(program_id);

    let Some(program_data_account) = rpc_client
        .get_account_with_commitment(&program_data_address, commitment)
        .await?
        .value
    else {
        // Program data has not been allocated yet.
        return Ok(());
    };

    let upgrade_authority_address = match bincode::deserialize(&program_data_account.data) {
        Ok(UpgradeableLoaderState::ProgramData {
            slot: _,
            upgrade_authority_address,
        }) => Ok(upgrade_authority_address),
        _ => Err(format!("Program {program_id} is closed")),
    }?;

    upgrade_authority_address.ok_or_else(|| format!("Program {program_id} is not upgradeable"))?;

    let required_len = UpgradeableLoaderState::size_of_programdata(program_len);
    let max_permitted_data_length = usize::try_from(MAX_PERMITTED_DATA_LENGTH).unwrap();
    if required_len > max_permitted_data_length {
        let max_program_len = max_permitted_data_length
            .saturating_sub(UpgradeableLoaderState::size_of_programdata(0));
        return Err(format!(
            "New program ({program_id}) data account is too big: {required_len}.\nMaximum program \
             size: {max_program_len}.",
        )
        .into());
    }

    let current_len = program_data_account.data.len();
    let additional_bytes = required_len.saturating_sub(current_len);
    if additional_bytes == 0 {
        // Current allocation is sufficient.
        return Ok(());
    }

    let mut additional_bytes =
        u32::try_from(additional_bytes).expect("`u32` is big enough to hold an account size");

    let feature_set = fetch_feature_set(rpc_client).await?;
    let feature_snapshot = feature_set.snapshot();

    if feature_snapshot.loader_v3_minimum_extend_program_size {
        // SIMD-0431: Have to bump `additional_bytes` to satisfy either the
        // minimum size requirement or the remaining headroom to
        // MAX_PERMITTED_DATA_SIZE.
        let headroom =
            u32::try_from(max_permitted_data_length.saturating_sub(current_len)).unwrap();
        additional_bytes = additional_bytes.max(MINIMUM_EXTEND_PROGRAM_BYTES.min(headroom));
    }

    let instruction =
        loader_v3_instruction::extend_program(program_id, Some(fee_payer), additional_bytes);
    initial_instructions.push(instruction);
