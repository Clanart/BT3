This confirms the key fact that undermines the claim: mainnet already enforces `stake_raise_minimum_delegation_to_1_sol` (feature-set/src/lib.rs:1848), meaning each stake delegation requires at least ~1 SOL (`stake_utils::get_minimum_delegation`, `runtime/src/stake_utils.rs:20-27`) plus a rent-exempt reserve, enforced by the on-chain stake program's `create_account_and_delegate_stake`/`delegate_stake` instructions — not merely a CLI-side suggestion. This makes "cheap, unbounded" account creation economically infeasible at any scale that would meaningfully move the needle on `calculate_activated_stake`'s cost, unlike the Cosmos analog where spam-token deposits cost nothing.

Audit Report

## Title
Invalid claim: unbounded stake-delegation scan at epoch boundary is not a viable DoS vector - (`runtime/src/stakes.rs`, `runtime/src/bank.rs`)

## Summary
The claim that `Stakes::calculate_activated_stake` (`runtime/src/stakes.rs:434-478`), invoked from `Bank::compute_new_epoch_caches_and_rewards`/`process_new_epoch` (`runtime/src/bank.rs:1762-1846`), is exploitable by an attacker who "cheaply and repeatedly" mints stake delegations is not supported by the code. Every stake delegation requires locking at least 1 SOL minimum delegation (`stake_raise_minimum_delegation_to_1_sol` feature, `feature-set/src/lib.rs:1847-1850`; enforced via `stake_utils::get_minimum_delegation`, `runtime/src/stake_utils.rs:19-27`) plus a rent-exempt reserve, on top of the on-chain stake program's own `create_account`/`delegate_stake` checks — this is a real, substantial economic cost that scales linearly with the number of accounts an attacker wants to create, unlike the cited Cosmos `GetAllBalances` bug where the attacker-controlled input was free to mint.

## Finding Description
The report accurately describes the code path — `calculate_activated_stake` does perform an unmetered `par_iter().fold()/reduce()` over the full `stake_delegations_vec()` on every epoch boundary, and no `MAX_ALPENGLOW_VOTE_ACCOUNTS`-style cap exists for this set. However, the claim mischaracterizes the cost of inflating this set. Stake account creation is gated by `get_minimum_delegation` (`runtime/src/stake_utils.rs:19-27`), which returns 1 SOL once `stake_raise_minimum_delegation_to_1_sol` is active — a feature that is already listed among historical/inactive features in `feature-set/src/lib.rs`, indicating it is a mature, already-activated mainnet feature, not a future mitigation. To inflate the delegation set by, say, 1,000,000 entries — the same order of magnitude the maintainers' own `runtime/benches/epoch_turnover.rs` benchmark already exercises — an attacker would need to lock on the order of 1,000,000+ SOL (plus rent-exempt reserves per account), which is neither "cheap" nor "repeatable" in the way the report claims. This is fundamentally different from the vote-account case bounded by `MAX_ALPENGLOW_VOTE_ACCOUNTS`, which exists specifically to bound the Alpenglow VAT/rewards snapshot (`RewardEpochDelegatedStakes::set`, `runtime/src/alpenglow_epoch_type.rs:70-75`) rather than as a generic anti-spam measure — vote accounts are also not the correct analog for delegation-count growth since running a vote account has different (also non-trivial) cost properties.

Additionally, tracking the full set of active stake delegations and their activation status is a structural requirement of any Proof-of-Stake protocol; the existing 1,000,000-account benchmark demonstrates the maintainers have already measured and provisioned for this scale, undermining the claim that "nothing prevents that number from growing without bound" as a novel, unaddressed risk.

## Impact Explanation
Not applicable — the described capital requirement (locking capital roughly proportional to $150–300 per stake account created, i.e., 1 SOL minimum delegation plus rent) to grow the delegation set to a size that could meaningfully affect epoch-boundary timing makes this economically infeasible as an "unprivileged, cheap, remote" attack, which is required for the claimed impact category (non-RPC remote exhaustion/degradation).

## Likelihood Explanation
Low. The minimum-delegation requirement (`runtime/src/stake_utils.rs:19-27`, gated by the already-active `stake_raise_minimum_delegation_to_1_sol` feature) is precisely the kind of economic deterrent the report speculates is missing, and it is enforced on-chain by the stake program itself, not just client tooling. The report's core premise — that account creation is "cheap" and costs the attacker "nothing of lasting value" analogous to the Cosmos spam-token case — does not hold here.

## Recommendation
N/A — no code change required based on the claim as submitted. If the maintainers still want defense-in-depth against pathological delegation counts, further investigation of actual mainnet delegation counts vs. benchmark headroom would be needed, but this is not demonstrated to be a live vulnerability.

## Proof of Concept
Not demonstrated. The report itself acknowledges it did not execute the `epoch_turnover` benchmark to measure wall-clock impact, and the economic analysis above shows the premised low-cost, repeatable minting of delegations is not accurate for current mainnet parameters.
