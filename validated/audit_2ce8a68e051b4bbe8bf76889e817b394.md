### Title
Cached FROST seed is never deleted after use, enabling nonce reuse and private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Parse Server bug class is "a secret that must be stripped after a single use is instead retained." In Serai's tributary signing protocol, the FROST `CachedPreprocess` seed — which deterministically derives the signing nonces and from which the private key share can be recovered — is persisted in `CachedPreprocesses` and is read back on every signing attempt for the same context, but is never removed after being consumed.

### Finding Description
`SigningProtocol::preprocess_internal` generates a preprocess seed, XOR-encrypts it with a key derived from the validator's private key, and stores it via `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` [1](#0-0) . On every subsequent call it loads the same seed with `CachedPreprocesses::get` and rebuilds the machine via `AlgorithmSignMachine::from_cache` [2](#0-1) . No deletion occurs anywhere in this flow.

`from_cache` feeds the seed into `ChaCha20Rng` and regenerates the *same* nonces via `Commitments::new` [3](#0-2) . The `SignMachine::from_cache` contract explicitly states: "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" [4](#0-3) . `share_internal` calls `preprocess_internal` for every signing attempt [5](#0-4) , so a second `share_internal` for the same context reuses identical nonces.

A malicious participant controls the preprocess map passed to `machine.sign(preprocesses, msg)` [6](#0-5) . The FROST binding factor rho and the `hash_msg` challenge depend on the preprocess set and message, so two signing sessions sharing the victim's nonces but differing in peer preprocesses or message produce two shares `s = d + e*rho + lambda*x*c` with distinct `(rho, c)`, allowing the attacker to solve for the victim's secret share `x`.

### Impact Explanation
Recovery of a validator's threshold secret share. With enough recovered shares (or combined with other compromises), an attacker can forge signatures on Bitcoin/Substrate transactions, directly enabling theft of bridged funds. This is the exact "secret retained after use" failure class — the seed is a private-key-equivalent and survives across uses instead of being stripped.

### Likelihood Explanation
The DB entry is keyed only by `context`, so any retry, re-attempt, or distinct message sharing a context reuses the seed. An attacker who is a legitimate participant in the signing set can submit a different preprocess set on a second attempt for the same context and observe the victim's two shares, which is fully reachable with public protocol inputs. The encryption of the stored seed protects it at rest but does nothing to prevent its deterministic reuse.

### Recommendation
Delete the `CachedPreprocesses` entry (e.g., a `remove`/`take` on the DB) immediately after decrypting it in `preprocess_internal`, and only re-`set` it when a *new* seed is generated. Alternatively, key the cache by a value that is guaranteed unique per signing session and refuse to serve the same key twice.

### Proof of Concept
1. Participant P triggers signing for context `C` with preprocess set S1 and message m1; victim's `share_internal` decrypts the cached seed, regenerates nonces `(d, e)`, emits share s1. The cache entry remains.
2. P triggers a second signing for the same context `C` with a modified preprocess set S2 (P's own preprocess bytes changed). Victim regenerates identical `(d, e)` but computes a different binding rho and challenge c, emitting share s2.
3. From `s1` and `s2` and the known public preprocess/commitment data, P solves the linear system for the victim's Lagrange-weighted secret share, recovering key material equivalent to the private share — per the documented consequence in `SignMachine::from_cache` [7](#0-6)  and the FROST spec warning on preprocess reuse [8](#0-7) .

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
