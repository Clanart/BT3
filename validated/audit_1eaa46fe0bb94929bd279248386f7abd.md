### Title
Unbounded numeric-string parsing in PHP `GPBUtil::parseDuration`/`Message::mergeFromJsonString` allows quadratic-time CPU DoS via `bccomp`/`bcmul` on attacker-controlled digit strings - (File: `php/src/Google/Protobuf/Internal/GPBUtil.php`)

### Summary
The pure-PHP implementation of protobuf's ProtoJSON parsing passes attacker-controlled numeric strings straight into PHP's `bcmath` functions (`bccomp`, `bcmul`, `bcadd`, `bcsub`) with no length pre-check, mirroring the exact bug class described in the jackson-databind report: a JSON string token containing an arbitrarily long numeric literal is handed to an arbitrary-precision arithmetic routine whose cost is superlinear in digit count, before any bounds/length validation occurs.

### Finding Description
`GPBUtil::parseDuration()` accepts the Duration string value straight from JSON, strips the trailing `s`, and immediately calls `bccomp($number, "315576000001")` and `bccomp($number, "-315576000001")` to range-check it: [1](#0-0) 
There is no upper bound on the length of `$number` before it reaches `bccomp`/`bcmul`. `bccomp` and the other bcmath primitives implement classic schoolbook big-number arithmetic, which is quadratic (or at least superlinear) in the number of decimal digits — the same complexity class as the unguarded `BigInteger`/`BigDecimal` constructors that the jackson-databind advisory flags. A JSON payload such as `{"optionalDuration": "1<millions of digits>s"}` therefore forces `bccomp` to chew through a multi-megabyte digit string before the length/range check can even reject it, exactly analogous to `DatatypeFactory.newDuration(value)` materializing the whole numeric string via `BigInteger(String)`/`BigDecimal(String)` before any check.

The same unguarded pattern also exists in the general int64/uint64 field decode path in `Message.php`, where `bccomp($value, "9223372036854775807")` and `bccomp($value, "18446744073709551615")` are invoked on the raw string value pulled out of JSON with no length cap: [2](#0-1) 
Both call sites reach a value originating from `is_numeric($value)`-checked JSON input, i.e., any string of digits regardless of length passes `is_numeric` in PHP and is accepted for `bccomp`.

By contrast, the C++/upb JSON decoders that back most language bindings do NOT have this issue: they parse duration/int64 strings with a bounded, linear-time custom scanner (`upb_BufToInt64`/`jsondec_buftoint64`, `ParseInt`/`SimpleAtoi` in `src/google/protobuf/json/internal/parser.cc`) rather than an arbitrary-precision library, and Java's `JsonFormat.java` already has an explicit `MAX_NUMERIC_STRING_LENGTH = 1000` guard placed in front of `BigDecimal(String)` specifically to defend against this class of DoS (with an accompanying regression test `testParserRejectOverlyLongNumericStrings`): [3](#0-2) [4](#0-3) 
No equivalent length guard exists in the PHP pure implementation's `GPBUtil::parseDuration`/`parseTimestamp` or `Message::mergeFromJsonString`'s int64/uint64 handling.

### Impact Explanation
An unauthenticated client that can submit ProtoJSON to any consuming application using protobuf's PHP pure-userland runtime (`php/src/...`, not the `php-upb`/`ruby-upb` C extensions, which use bounded integer scanners) can send a small number of bounded-size requests (a few MB each) containing an oversized digit string in a `Duration`/`Timestamp` field or any `int64`/`uint64` field, forcing single-threaded CPU consumption in `bccomp`/`bcmul` before rejection. Given protobuf's pure-PHP implementation is used when the native extension is unavailable, this is a legitimate CPU-exhaustion vector consistent with the CWE-1333/CVE-2026-68497 bug class, though the impact is bounded per-request (no unbounded memory growth) and scoped specifically to the pure-PHP runtime path.

### Likelihood Explanation
High for any deployment relying on the pure-PHP protobuf implementation (no C extension) that exposes ProtoJSON decoding to untrusted input — this is the normal, supported, default-enabled `mergeFromJsonString`/well-known-type parsing path, requiring no special configuration, polymorphic typing, or privileged access, matching the "ordinary client sending bounded ProtoJSON through a supported public parse API" threat model.

### Recommendation
Add an explicit maximum length check on the numeric substring (analogous to Java's `MAX_NUMERIC_STRING_LENGTH`) before it is passed to any `bccomp`/`bcmul`/`bcadd`/`bcsub` call in `GPBUtil::parseDuration`, `GPBUtil::parseTimestamp`, and `Message::mergeFromJsonString`'s int64/uint64 branches — e.g., reject any digit string longer than ~20-30 characters (sufficient for the legal int64/uint64/Duration range) before invoking bcmath functions.
