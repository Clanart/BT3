### Title
OP_RETURN data is excluded from transaction size and fee calculation - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`SignableTransaction::new` adds a caller-controlled `OP_RETURN` output before calculating the transaction’s virtual size, but calls `calculate_weight_vbytes` with only `payments` and the optional change output. The fee is therefore calculated for a transaction smaller than the transaction actually signed and published.

### Finding Description

The function adds an `OP_RETURN` output to `tx_outs` when `data` is supplied, allowing up to 80 bytes of data. It then calculates `vbytes` using `payments`, without representing the `OP_RETURN` output, and derives `needed_fee` from that underestimated size. When a change output is present, the same omission occurs in `vbytes_with_change`, causing the change amount to absorb all funds except the incorrectly small fee. The resulting transaction’s realized fee rate is lower than `fee_per_vbyte`, and the minimum-relay check is also performed against the underestimated virtual size. [1](#0-0) [2](#0-1) 

### Impact Explanation

An unprivileged caller can supply public `data` bytes to `SignableTransaction::new` and cause it to construct a transaction that does not pay the requested fee rate. With a change output, the transaction’s actual fee is fixed to the underestimated `fee_with_change`; for a requested minimum relay-rate transaction, the omitted `OP_RETURN` bytes can reduce the actual rate below Bitcoin’s default relay minimum. The transaction may be rejected from relay or remain unconfirmed even though `needed_fee` reports a compliant value. [3](#0-2) [4](#0-3) 

### Likelihood Explanation

This is reachable whenever transaction creation includes both `data` and `change`. No private key material, malicious validator, or malformed RPC response is required; `data` is an ordinary public constructor argument and is limited only to 80 bytes. Transactions near the minimum relay fee rate are most likely to become non-relayable, while higher requested fee rates still pay less than requested. [5](#0-4) [6](#0-5) 

### Recommendation

Include the `OP_RETURN` output in the transaction template used by `calculate_weight_vbytes`. Preferably calculate weight from the actual `tx_outs` being constructed, including data and change, rather than reconstructing output size from `payments`. Recalculate the minimum-relay threshold and maximum-standard-weight check using that complete output set. [7](#0-6) [8](#0-7) 

### Proof of Concept

```rust
// Conceptual PoC for networks/bitcoin/src/wallet/send.rs

let tx = SignableTransaction::new(
    vec![input],
    &[(payment_script, payment_amount)],
    Some(change_script),
    Some(vec![0xAA; 80]),
    fee_per_vbyte,
)?
.transaction()
.clone();

let actual_vbytes = u64::try_from(bitcoin::policy::get_virtual_tx_size(
    i64::try_from(tx.weight().to_wu()).unwrap(),
    0,
))?;

let actual_fee = input.value() - payment_amount - change_amount(tx);
assert_eq!(actual_fee, tx_needed_fee_reported_by_constructor);

// The OP_RETURN output contributes to actual_vbytes but was not included
// in needed_fee, so this can hold:
assert!(actual_fee < fee_per_vbyte * actual_vbytes);
```

The root cause is that `tx_outs` contains the `OP_RETURN` output, while both `calculate_weight_vbytes` calls only receive `payments` and optional `change`; neither call receives `data` or the already-constructed `tx_outs`. [9](#0-8) [2](#0-1)

    // Expand this a full transaction in order to use the bitcoin library's weight function

      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here

          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };

      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
