## Analog Identified: `pallet-bandwidth` Subscription Eviction Destroys Paid Bandwidth With No Reclaim Path

The Sui Bottle bug's core invariant break is: **a resource the user paid for is destroyed (`destroy_bottle`) without giving the user any way to claim the value still owed to them** (no surplus field, no claim function). The closest Hyperbridge analog is in `pallet-bandwidth`'s FIFO subscription eviction, which destroys unconsumed, already-paid bandwidth with only a log event — no refund, no claim mechanism, and the destruction is reachable by any unprivileged third party who purchases bandwidth for someone else's app.

### Title
Unprivileged FIFO-Eviction Griefing Permanently Destroys a Victim's Prepaid Bandwidth With No Refund Path - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth::push_subscription` appends every successful purchase to a per-`(app_chain, app)` FIFO list capped at `MAX_SUBSCRIPTIONS` (1024) entries. When the cap is hit, the **oldest** entry is silently popped and its `remaining_bytes` are lost forever, with only a `SubscriptionEvicted` event for auditability — no compensating balance, no way for the original payer to reclaim value. Because bandwidth purchases are permissionless and cross-chain-sponsorable (anyone can call `purchase()` on any source chain's `BandwidthManager` and credit an arbitrary `(app_chain, app)` pair), an attacker can flood cheap purchases against a victim app to force-evict a legitimately purchased, unconsumed, larger subscription before it can ever be drained.

### Finding Description
Purchases are recorded via `push_subscription`: [1](#0-0) 

Eviction happens unconditionally by FIFO position — `list.remove(0)` — with no regard to whose subscription is being evicted, whether it originated from the "victim" or the attacker, or whether it has been partially consumed: [2](#0-1) 

Credit is keyed purely by `(app_chain, app)` from the message body, independent of who paid (`paid_from`), which is exactly what makes cross-chain sponsorship possible — and exactly what makes griefing possible, since any payer can credit any app: [3](#0-2) 

The eviction path and its "only happens under pathological repeat-buy behavior" assumption are documented as a benign self-inflicted edge case, not as an attacker-controlled griefing vector: [4](#0-3) 

The gate's own logic confirms drain order matches insertion (FIFO) order, so an app that has purchased ahead of its usage rate keeps older, unconsumed, prepaid entries sitting at the front of the queue — exactly the entries an attacker's flood of new purchases will eventually push past the 1024-slot cap and evict: [5](#0-4) 

There is no analog to the Bottle-fix's "track surplus + claim function" anywhere in `pallet-bandwidth` — `SubscriptionEvicted` only logs `lost_bytes`; the bytes and the value they represent are gone.

### Impact Explanation
This is a direct "loss of funds" primitive matching the required Hyperbridge impact gate: bandwidth balances are bridged, prepaid value tracked on-chain (`Allowance` FIFO list), and the pivot requirement states bandwidth balances "must move exactly once and only to the rightful beneficiary and amount." Here, prepaid bandwidth moves to **nobody** — it is deleted outright by an unprivileged third party's unrelated purchase, with the original payer having no recourse. Any app relying on bandwidth to keep dispatching ISMP messages can be forced back to `GateError::NoAllowance`/`Insufficient` rejection despite having already paid, effectively also enabling a targeted denial-of-service against the victim app's cross-chain messaging.

### Likelihood Explanation
The attack requires only calling the public, permissionless `purchase()` entrypoint on `BandwidthManager` (any chain) 1024+ times targeting the victim's `(app_chain, app)` key — no relayer collusion, no admin/governance action, no malformed proof, and no privileged role is needed. Cost scales with the cheapest configured tier price × 1024, which is bounded and attacker-controlled (they can always choose `TierOne`, the cheapest SKU), making this economically feasible against any specific target the attacker wants to disrupt or whose prepaid balance they want to destroy.

### Recommendation
- Do not evict silently: when the FIFO list is full, reject the purchase (or refund it) rather than destroying another party's unconsumed subscription, or
- Segregate the FIFO/eviction policy by `paid_from` so a purchaser can only evict their own prior subscriptions, never another payer's, and
- At minimum, add a claim/refund path (mirroring the Bottle fix) that credits `lost_bytes` value back to `paid_from` when an eviction occurs, so prepaid value is never simply destroyed.

### Proof of Concept
1. Victim buys a large tier (e.g., `TierFour`, 8 MB) for `app` on `app_chain` via `BandwidthManager.purchase()`; `pallet-bandwidth::on_accept` appends this subscription to `Allowance[app_chain][app]` near the head (oldest) of the FIFO list — see `push_subscription`, [6](#0-5) .
2. Attacker, from any source chain, repeatedly calls `purchase()` targeting the **same** `(app_chain, app)` with the cheapest tier (`TierOne`), 1024 times, each appended via the same `push_subscription` path.
3. On the 1025th append (attacker's), `list.len() == MAX_SUBSCRIPTIONS` triggers `list.remove(0)`, evicting the victim's still-unconsumed `TierFour` subscription (assuming the app has not fully drained it yet) and firing `SubscriptionEvicted { lost_bytes: <victim's remaining bytes> }` — see [7](#0-6) .
4. The victim's paid `lost_bytes` are permanently gone; `Pallet::remaining(app_chain, app)` no longer reflects them, and no function exists anywhere in the pallet to reclaim or refund them.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

### Eviction

### Purchase messages skip the gate

The router uses `Pallet::is_purchase_message(request)` to identify a purchase from a registered manager (`request.source` is managed _and_ `request.from` matches the registered manager address). Purchase messages bypass the gate — otherwise a depleted app couldn't ever recharge.

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
