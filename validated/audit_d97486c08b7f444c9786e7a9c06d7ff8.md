### Title
Attacker-controlled length prefix in `SchnorrAggregate::read` causes unbounded point decompression before signer-count validation - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::<C>::read` trusts a `u32` count prefix embedded in attacker-supplied bytes and performs that many full group-element decompressions (`C::read_G`) before any caller can check whether the claimed aggregate size is sane. This is the same bug class as the OpenClaw webhook advisory: expensive, attacker-driven work is performed on unauthenticated input before the cheap validation that would have rejected it.

### Finding Description
In `crypto/schnorr/src/aggregate.rs:77-88`, `read` reads a 4-byte little-endian length and loops `u32::from_le_bytes(len)` times calling `C::read_G(reader)`, which for `Ristretto`, `Secp256k1`, `Ed25519`, etc. performs a full compressed-point decompression (field inversion / square-root work) per element:

```rust
let mut len = [0; 4];
reader.read_exact(&mut len)?;
let mut Rs = vec![];
for _ in 0 .. u32::from_le_bytes(len) {
  Rs.push(C::read_G(reader)?);
}
Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
```

There is no bound parameter, no early rejection, and the `Vec` grows one element per successful decode, so a crafted buffer causes CPU-heavy decompression work proportional to attacker-controlled input.

The only semantic check on the count happens *after* parsing, in the verifier. `crypto/schnorr/src/aggregate.rs:127-130` (`verify`) and the production caller `Validators::verify_aggregate` in `coordinator/tributary/src/tendermint/mod.rs:207-213` both do `if self.Rs.len() != keys_and_challenges.len() { return false; }` — i.e., the aggregate signature is fully parsed (every `R` decompressed, every scalar reduced) and only then is `signers.len() != aggregate.Rs().len()` checked. The fix would be to validate the count against the expected number of signers *before* decompressing.

Additionally, `verify_aggregate` unwraps `Ristretto::read_G` on each claimed signer key at `mod.rs:225`, but that is on the validator set (trusted-ish); the untrusted surface is the aggregate bytes themselves, which are read in full first.

### Impact Explanation
An unauthenticated party who can get an aggregate-signature byte string to a verifying node (e.g., a commit/block message carrying an aggregate signature on the Tendermint path) can declare up to `u32::MAX` `Rs` and force the node to spend decompression CPU time and `Vec` growth on bytes that would be rejected by a two-integer comparison. Each claimed element costs a full point decompression plus canonicality rejection work in `read_G`/`read_point`, while the legitimate rejection requires only comparing the encoded count against the known signer count — an asymmetric work factor matching CWE-400/CWE-770.

### Likelihood Explanation
The aggregate signature is exactly the unauthenticated ingress object: it is produced by whoever claims a set of signers and is consumed via `SchnorrAggregate::read` before `verify`/`verify_aggregate` can check plausibility. The length-check-then-parse order is inverted relative to the safe pattern; reaching it requires only sending malformed aggregate bytes, no keys, no collusion. Bounded only by outer transport/message size limits, not by anything in the cryptographic layer.

### Recommendation
Pass the expected signer count (or a hard cap) into `SchnorrAggregate::read`, or read the count and reject `len != signers.len()` / `len > MAX` before the decode loop. The signature count is known to every verifier (`signers.len()`), so no legitimate input is affected.

### Proof of Concept
Serialize `[0xFF, 0xFF, 0xFF, 0xFF]` followed by arbitrarily many 32-byte non-canonical or valid point encodings and feed it to `SchnorrAggregate::<Ristretto>::read(&mut bytes.as_slice())`, or submit it as `AggregateSignature` to `Validators::verify_aggregate` (`coordinator/tributary/src/tendermint/mod.rs:201`). The loop at `crypto/schnorr/src/aggregate.rs:83-85` performs up to 4,294,967,295 attempted `read_G` decompressions — bounded only by the input's length — before `verify_aggregate` reaches the `signers.len() != aggregate.Rs().len()` check at `mod.rs:211-213` that would have rejected it for free.
