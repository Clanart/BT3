### Title
NFT metadata-update spend triggers unhandled `KeyError`/`AttributeError` in wallet coin-processing (`prepend_value`) - (File: chia/wallet/nft_wallet/nft_puzzle_utils.py)

### Summary
`prepend_value()` in `chia/wallet/nft_wallet/nft_puzzle_utils.py` blindly indexes `metadata[key]` and calls `.insert()`/list-mutation on it without validating that `key` exists in the metadata dict or that its stored value is actually a mutable list. Because `key` and the accompanying update value are fully attacker-controlled data taken from a coin's spend solution, an NFT sender/counterparty can craft a metadata-update condition (opcode `-24`) whose key is not among the metadata's known/pre-existing keys (or whose existing value is not a list), causing an unhandled `KeyError`/`AttributeError`/`TypeError` when a receiving wallet processes that spend.

### Finding Description
When an NFT coin with a metadata-updater layer is spent, the inner puzzle can emit a magic condition `(-24 ...)` that instructs the wallet to update NFT metadata. This is parsed by `get_metadata_and_phs()`: [1](#0-0) 

which calls `update_metadata()`: [2](#0-1) 

`update_metadata` converts the current on-chain metadata `Program` to a Python dict via `nft_program_to_metadata` (populated only with keys that are actually present in the coin's current metadata, e.g. `b"u"`, `b"h"`, `b"mu"`, etc. depending on what was minted), then calls `prepend_value(key, value, new_metadata)` where `key` comes directly from `uri.first().as_python()` — a value taken straight from the attacker-supplied solution/condition, not validated against the set of keys actually present: [3](#0-2) 

`prepend_value` does `metadata[key]` unconditionally. If `key` is not present in `metadata` (e.g., the NFT was never minted with a `"mu"`/`"lu"` field and the spender submits an update targeting that key, or any arbitrary non-standard key), this raises `KeyError`. Even if the key exists but its value happens not to be a list (e.g. it is `bytes` from `as_python()` for a hash field), `.insert(0, ...)` raises `AttributeError`.

This function is reached from the wallet-sync path whenever any incoming coin spend is recognized as an NFT the local wallet owns: [4](#0-3) 

`coin_added` → `puzzle_solution_received` → `get_metadata_and_phs` → `update_metadata` → `prepend_value` is invoked directly and unconditionally as part of normal wallet state-sync processing for any NFT coin belonging to the wallet, with no `try/except` guarding the metadata-update parsing.

### Impact Explanation
This is the analog of the Exiv2 null-pointer dereference: both are unhandled crashes triggered by processing untrusted, attacker-crafted structured data during a legitimate (non-privileged) operation (Exiv2 printing metadata / Chia wallet syncing an NFT metadata-update spend). Here, an NFT sender, offer counterparty, or anyone who can get a coin spend of an NFT they control (or that is later transferred to the victim) processed by the victim's wallet can supply an `-24` metadata-update condition referencing a key absent from the current metadata (or a non-list value), causing an unhandled exception in `NFTWallet.puzzle_solution_received`. Since this runs inside wallet coin-added/sync notification handling for every relevant coin, an uncaught exception here can repeatedly disrupt processing of that NFT coin/wallet state each time the offending spend is (re-)synced, denying normal wallet operation for the affected NFT wallet — a spend-triggered transaction-processing halt reachable from a single crafted spend.

### Likelihood Explanation
Likelihood is high for triggering: any party who can create/send an NFT coin spend with a metadata-updater inner puzzle solution controls the `key`/`value` fields consumed by `prepend_value` and can trivially choose a key not present in the metadata dict (this requires no special access — just crafting a standard NFT metadata-update spend and getting it accepted into a block, then having a wallet that tracks that NFT sync it).

### Recommendation
In `prepend_value` (and by extension `update_metadata`/`get_metadata_and_phs`), validate that `key in metadata` and that `metadata[key]` is a list before mutating, defaulting to creating a new list entry when absent, and wrap metadata-update processing in `puzzle_solution_received` with error handling that logs and safely skips a malformed/unexpected update instead of propagating an unhandled exception that can repeatedly break wallet coin-sync for the affected NFT.

### Proof of Concept
1. Mint or acquire an NFT with the standard metadata-updater whose current metadata dict only contains a subset of keys (e.g., only `b"u"`/`b"h"`, no `b"mu"`/`b"lu"`).
2. Construct a spend of that NFT coin whose inner puzzle solution emits a condition `(-24 (<updater> (mu . "new value")))` where `"mu"` is not a key already present in the coin's current metadata program (or targets a key whose existing value is not list-shaped).
3. Submit the spend bundle; once included in a block, any wallet tracking that NFT coin will process it via `coin_added` → `puzzle_solution_received` → `get_metadata_and_phs` → `update_metadata` → `prepend_value`, where `metadata[key]` raises `KeyError` (or `.insert` raises `AttributeError`/`TypeError`), producing an unhandled exception during wallet coin-sync processing of that NFT coin.

```python
def nft_program_to_metadata(program: Program) -> dict[bytes, Any]:
    """
    Convert a program to a metadata dict
    :param program: Chialisp program contains the metadata
    :return: Metadata dict
    """
    metadata = {}
    for kv_pair in program.as_iter():
        metadata[kv_pair.first().as_atom()] = kv_pair.rest().as_python()
    return metadata


def prepend_value(key: bytes, value: Program, metadata: dict[bytes, Any]) -> None:
    """
    Prepend a value to a list in the metadata
    :param key: Key of the field
    :param value: Value want to add
    :param metadata: Metadata
    :return:
    """
    if value != Program.to(0):
        if metadata[key] == b"":
            metadata[key] = [value.as_python()]
        else:
            metadata[key].insert(0, value.as_python())
```

```python
def update_metadata(metadata: Program, update_condition: Program) -> Program:
    """
    Apply conditions of metadata updater to the previous metadata
    :param metadata: Previous metadata
    :param update_condition: Update metadata conditions
    :return: Updated metadata
    """
    new_metadata: dict[bytes, Any] = nft_program_to_metadata(metadata)
    uri: Program = update_condition.rest().rest().first()
    prepend_value(uri.first().as_python(), uri.rest(), new_metadata)
    return metadata_to_program(new_metadata)
```

```python
def get_metadata_and_phs(unft: UncurriedNFT, solution: SerializedProgram) -> tuple[Program, bytes32]:
    conditions = unft.p2_puzzle.run(unft.get_innermost_solution(Program.from_serialized(solution)))
    metadata = unft.metadata
    puzhash_for_derivation: bytes32 | None = None
    for condition in conditions.as_iter():
        if condition.list_len() < 2:
            # invalid condition
            continue
        condition_code = condition.first().as_int()
        log.debug("Checking condition code: %r", condition_code)
        if condition_code == -24:
            # metadata update
            metadata = update_metadata(metadata, condition)
            metadata = Program.to(metadata)
```
