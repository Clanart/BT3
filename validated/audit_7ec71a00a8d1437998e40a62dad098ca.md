This confirms my analysis: `is_kickoff_malicious` and `validate_payer_is_operator` only compare `operator_xonly_pk` from the database (which comes straight from the unauthenticated OP_RETURN parsed in `update_finalized_payouts`) against the pubkey of whichever operator sends the kickoff. There is no check anywhere that ties `operator_xonly_pk` to who actually supplied the BTC funding `output_txout.value`.

### Title
Unauthenticated OP_RETURN operator_xonly_pk in payout_tx allows crediting/reimbursement to a party that never funded the payout - (File: core/src/verifier.rs)

### Summary
`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) signs only the withdrawal input and the matching-index user payout output with `user_sig` under `SinglePlusAnyoneCanPay`; the OP_RETURN output carrying `operator_xonly_pk` is never covered by this signature or by any other cryptographic binding to the funds that pay `output_txout.value`. `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) blindly trusts whatever `operator_xonly_pk` is parsed from the first OP_RETURN of the confirmed spending transaction and persists it via `update_payout_txs_and_payer_operator_xonly_pk`, later used by `is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) and `validate_payer_is_operator` (`core/src/operator.rs:1686-1740`) to authorize reimbursement.

### Finding Description
The claimed binding is: `operator_xonly_pk` (parsed from payout_tx OP_RETURN, stored as `withdrawals.payout_payer_operator_xonly_pk`) `==` xonly public key of the party whose BTC actually funded `output_txout.value`.

Tracing the code:
- `operator.withdraw` (`core/src/operator.rs:560-637`) builds `payout_txhandler` via `create_payout_txhandler`, which places `operator_xonly_pk` in a plain OP_RETURN output [1](#0-0) . `user_sig` with `TapSighashType::SinglePlusAnyoneCanPay` is checked against only `sighash = payout_txhandler.calculate_sighash_txin(0, ...)` [2](#0-1) ; `SinglePlusAnyoneCanPay` by BIP-341 semantics commits only to input 0 and the output at the same index (the user payout output) - it does not cover the anchor output, the OP_RETURN output, the number/content of other inputs, or which party funds the shortfall between the tiny withdrawal UTXO and the (typically much larger) payout amount.
- `operator.withdraw` funds the shortfall via `fund_raw_transaction` with `add_inputs: true` [3](#0-2) , adding the broadcaster's own coins. Because the SinglePlusAnyoneCanPay signature does not pin down the rest of the transaction, any party (not just the fronting operator) can construct a *different* transaction reusing the exact same input-0 witness (spending the same withdrawal UTXO, paying the same user output at index 0 - the only two fields the signature actually commits to), while freely choosing their own OP_RETURN `operator_xonly_pk` value and funding the output entirely from their own added input(s), which they sign themselves.
- On confirmation, `update_finalized_payouts` reads whichever transaction actually spent the tracked withdrawal UTXO from `block_cache`, extracts `operator_xonly_pk` via `get_first_op_return_output`/`parse_op_return_data` with zero cross-checks against the funding inputs [4](#0-3) , and persists it unconditionally through `update_payout_txs_and_payer_operator_xonly_pk` [5](#0-4) .
- Later, `is_kickoff_malicious` only checks `operator_xonly_pk != kickoff_data.operator_xonly_pk` [6](#0-5) , and `validate_payer_is_operator` only checks `payer_xonly_pk != self.signer.xonly_public_key` [7](#0-6) . Neither verifies that the named operator's key actually signed/funded any input of the confirmed payout_tx.

Exploit flow: honest operator A broadcasts payout_tx_A (input 0 = withdrawal UTXO with `user_sig`, output 0 = user payout, OP_RETURN = A's pubkey, funded by A's added input). Before payout_tx_A confirms, the attacker (who observes the unconfirmed tx in the mempool/relay - a witness reuse/malleability attack requiring no privileged access) constructs payout_tx_B: same input 0 with the same `user_sig` witness (still valid, since it doesn't cover other fields), same output 0 (required, since sighash SINGLE binds it), attacker's own funding input(s) covering the same output amount, and an OP_RETURN naming an arbitrary 32 bytes (e.g., operator B's real pubkey, or garbage). Attacker broadcasts payout_tx_B with a higher fee to win the race/RBF. If payout_tx_B confirms instead, the DB now records operator B (who paid nothing) as the payer, while A - who genuinely paid - can never pass `is_kickoff_malicious`/`validate_payer_is_operator` for this withdrawal.

### Impact Explanation
Two concrete Critical-tier outcomes, both reachable from the same primitive:
1. Operator A, who genuinely funded `output_txout.value`, is permanently blocked from proving payment and can never be reimbursed for that withdrawal (`is_kickoff_malicious` always flags A's kickoff as malicious since `operator_xonly_pk` in DB ≠ A's pubkey) - "an honest operator permanently unable to be reimbursed."
2. If the attacker (or a colluding operator B) is willing to front the BTC themselves while naming operator B in the OP_RETURN, operator B can later be reimbursed from bridge collateral for a payout it never funded - "an operator reimbursed for a payout it never funded."
This is repeatable per withdrawal/operator and requires no verifier, operator, or aggregator privilege - only the ability to observe/relay Bitcoin transactions and fund a competing spend.

### Likelihood Explanation
Preconditions: a real withdrawal has been fronted (payout_tx broadcast but not yet finalized/deep-confirmed), and the attacker can see the unconfirmed transaction (public mempool data) and win a fee race or RBF replacement before finality-depth confirmations. The attacker must supply BTC equal to `output_txout.value` themselves to keep the required output intact, which is a real cost but is fully recoverable if colluding with the operator named in the OP_RETURN (who then gets reimbursed via bridge collateral, i.e. the attack self-funds). Even without collusion, a griefer only needs enough capital to grief one honest operator per withdrawal, at the cost of donating the payout amount to the withdrawing user (which they were going to receive anyway) - the attacker's cost is the payout amount minus the reimbursement they never get, so it's primarily useful in the colluding-operator variant.

### Recommendation
Bind `operator_xonly_pk` cryptographically to the actual funding of the payout, e.g. require the operator to sign the entire payout_tx (or at minimum the OP_RETURN output and every additional funding input) with a sighash that covers all outputs (e.g. `SIGHASH_ALL` for the operator-added funding input, or include operator_xonly_pk inside data covered by that input's signature), and have verifiers additionally check that the OP_RETURN-named operator's own signature authorizes the specific inputs supplying `output_txout.value`, rather than trusting an arbitrary unauthenticated push.

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
