### Title
Missing-snapshot fallback lets a validator's live commission bypass the one-epoch delay in reward calculation - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The H-07 pattern in the Phi report is: a party who legitimately controls an on-chain "settings" field (the artist) can change it (royalty %) with no restriction, and that change is applied immediately/retroactively to holders who already committed funds under the old terms. The Agave analog is the vote program's commission system: a vote account's authorized withdrawer can freely change `inflation_rewards_commission_bps` via `update_commission_bps` at any time — this is intentional under SIMD‑0249/0291, because protection against surprise commission changes is supposed to be enforced not at the instruction level but later, in reward calculation, by using a one‑epoch‑delayed "snapshot" of the vote account's commission. If that delayed snapshot lookup ever falls through to the *live* vote state instead, the delay guarantee silently disappears and stakers get charged whatever commission the validator set moments earlier, with no opportunity to un-delegate first.

### Finding Description
`update_commission_bps` in `programs/vote/src/vote_state/mod.rs` explicitly removes the epoch-position restriction that the legacy `update_commission` enforces via `is_commission_update_allowed`: [1](#0-0) 

The code comment and test both confirm this is by design: the safety net is supposed to live in the reward calculation path, which is meant to always use a commission value snapshotted from a *prior* epoch instead of the current live value: [2](#0-1) 

That delay logic is implemented in `redeem_delegation_rewards`: [3](#0-2) 

The critical corrupted value is `commission_bps` used to compute the validator's cut of a delegator's rewards. When `delay_commission_updates` is active, the code tries `snapshot_epoch_vote_accounts` first, then falls back to `rewarded_epoch_vote_accounts`, and — critically — if *neither* map contains an entry for `vote_pubkey`, it falls back with `.unwrap_or(vote_state)` to `vote_state`, which is derived from `distribution_epoch_vote_accounts` (i.e., the **current, live** vote account state fetched moments earlier at line 701 of the same function): [4](#0-3) 

In other words, the entire "delay commission updates by one full epoch" guarantee that SIMD‑0249 relies on to justify removing the on-chain timing check is implemented as a *best-effort lookup with a live-state fallback*, not an invariant. Any vote account whose pubkey is absent from both `snapshot_epoch_vote_accounts` and `rewarded_epoch_vote_accounts` — but present in `distribution_epoch_vote_accounts` — will have its commission taken from the value in effect *at reward-distribution time*, which the withdraw authority is free to set arbitrarily (up to the full `u16` bps range, i.e. up to 655.35% before any cap, or simply to the protocol max) via `update_commission_bps`, with zero on-chain rate limiting per `verify_authorized_signer` plus no `is_commission_update_allowed` check: [5](#0-4) 

This exactly mirrors the Phi bug class: a party with narrow, expected privilege over one setting (commission — the Agave equivalent of "royalty fee") can change that setting unrestricted, and — because of a gap in the mechanism meant to protect already-committed counterparties (delegated stakers, the equivalent of NFT holders) — the change takes effect immediately rather than after the intended delay, silently converting a "shielded by design" setting into an "unrestricted" one for a subset of accounts.

### Impact Explanation
If the fallback path is hit for a given vote account in a given epoch, delegators who staked under one commission rate can have their entire epoch's rewards commission calculated using a commission value the validator set at the very last moment (e.g., seconds before rewards distribution), maximizing the commission taken (up to whatever cap `commission_bps` allows) with no opportunity for stakers to withdraw or move their stake first. This is a fund-loss issue for delegators (loss of rewards they were owed) and, unlike the Phi contract (opt-in NFT purchase), delegators cannot practically "undo" an epoch's worth of already-earned stake rewards after the fact.

### Likelihood Explanation
This requires the specific edge case where `distribution_epoch_vote_accounts` contains the vote account (so it participates in reward calculation) but the account is missing from both `snapshot_epoch_vote_accounts` and `rewarded_epoch_vote_accounts` — plausible for vote accounts that only recently became eligible for stake rewards or that were absent from prior-epoch snapshots (e.g., due to restart/recalculation flows using `get_epoch_params_for_recalculation`, which rebuilds `distribution_epoch_vote_accounts` from `epoch_stakes` independently of the snapshot/rewarded caches). I could not fully trace, within the available index, every code path that populates `snapshot_epoch_vote_accounts` and `rewarded_epoch_vote_accounts` to determine precisely how often or under what exact conditions both would be simultaneously absent for an otherwise-rewarded vote account — this is the main open question and would need deeper tracing of `get_cached_vote_accounts` and the snapshot/recalculation call sites in a full checkout of the codebase (the index used here truncates some of that context).

### Recommendation
Treat "vote account missing from both delayed snapshots" as a hard failure/zero-commission-collection case for that epoch (or force the maximum-of legacy/known commission) rather than silently falling back to the live, attacker-controlled commission value. At minimum, add an explicit test that exercises the "vote account absent from `snapshot_epoch_vote_accounts` and `rewarded_epoch_vote_accounts`, but present in `distribution_epoch_vote_accounts`" case in `redeem_delegation_rewards`, and confirm the resulting `commission_bps` cannot reflect a same-epoch modification.

### Proof of Concept
1. A vote account exists and has active stake delegated to it, but due to a restart/recalculation path (`get_epoch_params_for_recalculation`) or another gap in cache population, its pubkey is absent from both `snapshot_epoch_vote_accounts` and `rewarded_epoch_vote_accounts` for the rewarded epoch, while still present in `distribution_epoch_vote_accounts`. [6](#0-5) 
2. The vote account's authorized withdrawer calls `UpdateCommissionBps` right before reward distribution runs, setting `inflation_rewards_commission_bps` to a very high value; this succeeds unconditionally since no timing/rate check exists: [7](#0-6) 
3. During `redeem_delegation_rewards`, because both delayed maps miss the entry, `vote_state_for_commission` resolves via `.unwrap_or(vote_state)` to the just-updated live commission, and every delegator's reward for that epoch is charged using the inflated, last-second commission value instead of the value expected under the "delayed by one epoch" guarantee: [8](#0-7) 

Note: I was unable to conclusively confirm, from the indexed subset of the repository, exactly how frequently/under what production conditions both delayed caches would be simultaneously empty for an actively-staked vote account outside the recalculation path — this would need to be validated against the full `get_cached_vote_accounts` implementation and its callers before treating this as a confirmed exploit rather than a design gap.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
