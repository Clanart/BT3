## Title
Reentrant double-drain of intent escrow via post-transfer state decrement in `withdraw()` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of `IntentGatewayV2` violates checks-effects-interactions in its internal `withdraw()` function: it performs the token/native transfer to `beneficiary` **before** decrementing `_orders[commitment][token]`. Since native-token payouts use a raw `.call{value: amount}("")` and ERC20 payouts use a raw low-level `.call(...)` (not `SafeERC20`), a `beneficiary` that is a contract can re-enter during the transfer and call back into `withdraw`-reachable paths while the escrow accounting still shows the full, un-decremented balance — enabling repeated payouts from the same escrow slot (and, since `_orders` is a shared mapping in one pooled contract, potential drain beyond a single order's own funds if further reentrant calls touch other commitments/logic reachable during the callback).

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` is: [1](#0-0) 

For each token in the withdrawal request, the code:
1. Checks `_orders[body.commitment][token] == 0` (only a non-zero check, not `>= amount`).
2. Immediately performs the external transfer (`beneficiary.call{value: amount}("")` for native token, or a raw `.call(...)` to `IERC20.transfer` for ERC20).
3. **Only after** the transfer does it execute `_orders[body.commitment][token] -= amount;`.

This is the same "read/check, do the risky operation, reset afterward" defect class described in the source report: the balance guard (`_orders[...]`) is not updated before the value-moving operation, so a second call observing the same pre-reset state can pass the same "non-zero" check and trigger a second payout before the first decrement lands. Compare this to the audited main EVM implementation in `evm/src/apps/intentsv2/IntentsBase.sol`, which correctly decrements **before** transferring: [2](#0-1) 

`withdraw()` is reachable from two host-authenticated but externally-influenced entry points:
- `onAccept()` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow`, where `body.beneficiary` comes directly from the decoded cross-chain request body: [3](#0-2) 
- `onGetResponse()` for the cross-chain cancellation/refund flow, again calling `withdraw(body, true)` with `beneficiary` taken from the original order's `order.user`: [4](#0-3) 

Critically, `beneficiary` for a refund is `order.user`, i.e., **whatever address the order's own creator specified when they placed the order**. A user who places an order using a malicious contract address as `order.user` (the standard self-refund/self-fill beneficiary) fully controls what code executes on receipt of funds during `withdraw()`, and thus controls the reentrancy trigger.

### Impact Explanation
Because the escrow decrement (`_orders[body.commitment][token] -= amount`) happens strictly after the external call, a malicious `beneficiary` contract can, inside its `receive()`/fallback (native token case) or inside a callback triggered by a malicious/hooked ERC20 token, re-enter a path that calls `withdraw()` again for the same commitment (or a related one) before the decrement is applied. Each reentrant pass observes `_orders[body.commitment][token] != 0` and pays out `amount` again, resulting in multiple payouts against a single escrowed balance. Since `_orders` is a single shared mapping in one pooled `IntentGatewayV2` contract holding funds for many users' orders, over-withdrawal drains the contract's shared token balance — i.e., funds belonging to other users/orders — constituting direct loss of bridged/escrowed funds. This matches the bounty's "stealing or loss of funds" and "unauthorized transaction/execution" categories.

### Likelihood Explanation
The trigger requires only that the attacker be the order's own creator (an ordinary, unprivileged user) supplying a malicious contract as the refund/fill beneficiary and initiating the standard cancellation/redeem cross-chain flow — no relayer, prover, governance, or leaked-key assumption is needed. The `onAccept`/`onGetResponse` calls are host-authenticated (`onlyHost`), but that only restricts *who calls the gateway*, not *what beneficiary code runs during the transfer* — the beneficiary is attacker-chosen order data carried faithfully through the ISMP message. Likelihood is rated **Medium-High** given the entry point requires driving a legitimate order/cancellation lifecycle through cross-chain messaging (adding some operational complexity/timing), but no privileged actor or malicious infrastructure component.

### Recommendation
Apply checks-effects-interactions consistently in `withdraw()`, matching the already-correct pattern in `evm/src/apps/intentsv2/IntentsBase.sol`:
1. Change the check to `require(_orders[body.commitment][token] >= amount)`.
2. Decrement `_orders[body.commitment][token] -= amount` **before** performing the native/ERC20 transfer.
3. Apply the same fix to the `TRANSACTION_FEES` payout block (`delete _orders[...][TRANSACTION_FEES]` before the transfer, not after).
4. Consider adding a `nonReentrant` guard on `onAccept`/`onGetResponse` as defense in depth, and switch raw `.call(...)` ERC20 transfers to `SafeERC20.safeTransfer`.

### Proof of Concept
1. Attacker places a cross-chain intent order on the source chain, setting `order.user` (and thus the eventual refund `beneficiary`) to `AttackerContract`, an address they control that implements a `receive()`/fallback (for native-token orders) that calls back into the flow that ultimately re-triggers `withdraw()` for the same `commitment` (e.g., by re-invoking the cancellation dispatch/response handling path or another order sharing the token).
2. Attacker lets the order go unfilled past `deadline`, then drives the cross-chain refund path so that, on the destination chain running this `IntentGatewayV2.sol`, `onAccept`/`onGetResponse` eventually calls `withdraw(body, true)` with `beneficiary = AttackerContract` and `token` a native or hook-capable ERC20 asset.
3. During the `beneficiary.call{value: amount}("")` (or the ERC20 transfer's callback, if using a token with transfer hooks), `AttackerContract.receive()` re-enters and triggers another host-authenticated call path that invokes `withdraw()` again for the same `commitment`/`token` before `_orders[body.commitment][token] -= amount` has executed from the first call.
4. The nonzero check `_orders[body.commitment][token] == 0` still passes (unchanged since first read), so a second transfer of `amount` is sent to `AttackerContract`.
5. Only after both external calls return do the two `-= amount` decrements apply, net-underpaying the ledger relative to actual funds paid out — draining more from the shared escrow pool than the original order's amount, at the expense of the contract's other escrowed balances.

Note: full confirmation of exploitability under the Tron/TVM `.call` semantics (e.g., whether a raw ERC20 `.transfer` call actually enables reentrancy for standard non-hook tokens, versus only for native-token/hook-token beneficiaries) would benefit from running the existing `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` harness against this Tron contract variant, which the index did not return the contents of.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
