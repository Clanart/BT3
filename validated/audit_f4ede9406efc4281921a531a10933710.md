### Title
Previous DID owner's recovery/backup configuration is retained on transfer, allowing recovery-based control after ownership change - (File: `chia/wallet/did_wallet/did_wallet.py`)

### Summary
`DIDWallet.transfer_did()` builds the new owner's DID inner puzzle using the *same* `backup_ids` / `num_of_backup_ids_needed` (the DID recovery/backup configuration) that was set by the previous owner, and only clears it when `reset_recovery_list()` determines the list is already empty. There is no check that the incoming/new owner has reviewed or consented to this inherited recovery configuration. This mirrors the reported bug class: a per-identity configuration set by a former owner (`positionConfigs[tokenId]` in the report) is carried forward and remains authoritative after the identity (DID/tokenId) changes hands, without any explicit re-validation tied to current ownership.

### Finding Description
`DIDWallet.transfer_did()` reads `backup_ids = self.did_info.backup_ids` and `backup_required = self.did_info.num_of_backup_ids_needed` from the wallet's *current* (pre-transfer) `DIDInfo`, and directly reuses them to curry the new DID inner puzzle for the recipient: [1](#0-0) 

The only opt-out is `reset_recovery_list()`, which returns `None` (i.e., actually clears the recovery hash) only in narrow cases, and by default just returns the pre-existing hash, preserving the same recovery configuration on the new coin: [2](#0-1) 

The code comment in `get_innerpuz_for_new_innerhash()` explicitly acknowledges this is a known sharp edge that depends on the *seller* remembering to act correctly, not on any enforced check tied to the new owner: "Note: the recovery list will be kept. In a selling case, the seller should clean the recovery list then transfer to the new owner." [3](#0-2) 

The CLI (`chia did transfer`) also defaults to keeping recovery info (`with_recovery_info=not self.reset_recovery`, defaulting to `reset_recovery=False`), so unless the current owner explicitly passes `--reset_recovery`, the transfer silently preserves the old recovery/backup-DID configuration on the DID that is being handed to a new owner: [4](#0-3) 

This is structurally identical to the reported issue: a configuration (`positionConfigs`/here, `backup_ids` + `num_of_backup_ids_needed`) set by the previous controller of an identity (`tokenId`/here, the DID coin) is used by the protocol after the identity changes ownership, without validating that the configuration was authorized by the *current* owner.

### Impact Explanation
If a DID is transferred/sold (e.g., via an offer, or simply sent to a new key) without the previous owner explicitly resetting the recovery list, the previous owner's chosen backup DIDs remain capable of participating in DID recovery for the identity now controlled by the new owner. Depending on how the buyer/new owner uses the DID (NFT ownership, VC "authorized provider" identity, general DID-based authorization), a set of DIDs chosen by the seller retaining recovery authority over an identity the buyer believes they now fully own is a meaningful loss of exclusive control, and can enable the seller (or entities colluding with the seller) to eventually recover/repossess the DID inner-puzzle key control away from the legitimate new owner.

### Likelihood Explanation
This occurs by default on every DID transfer unless the transferring party explicitly passes `--reset_recovery` (CLI) or otherwise clears `backup_ids`/`num_of_backup_ids_needed` before transferring; ordinary usage of `did transfer` or `DIDTransferDID` RPC does not clear it. Since this is default wallet behavior reachable by any DID owner performing a normal transfer/sale, and the buyer has no reliable way to detect stale recovery configuration from the puzzle alone, the likelihood of encountering this in DID trades is high, matching the judge's rationale in the original report that "frontend security checks are unreliable."

### Recommendation
Default `transfer_did()`/`DIDTransferDID` to clear the recovery list (`backup_ids = []`, `num_of_backup_ids_needed = 0`) unless the current owner explicitly opts to preserve it for a trusted transfer, and surface this as an explicit, prominent choice at both the RPC and CLI layers rather than an opt-in `--reset_recovery` flag. Additionally, wallets that receive a DID via transfer should surface the inherited recovery configuration (backup DIDs / verification threshold) to the new owner so they can decide whether to reset it before relying on the DID for authorization purposes.

### Proof of Concept
1. Owner A creates DID `D` with `backup_ids = [X, Y]`, `num_of_backup_ids_needed = 1` (recoverable by X or Y).
2. Owner A sells/transfers `D` to Owner B using `chia did transfer` without `--reset_recovery` (the default), i.e. `DidTransferDidCMD` with `reset_recovery=False`, which maps to `with_recovery_info=True` in `transfer_did()`.
3. `transfer_did()` in `did_wallet.py` reuses `self.did_info.backup_ids` (`[X, Y]`) and `num_of_backup_ids_needed` (`1`) to build `new_did_puzhash` for Owner B's coin.
4. Owner B now treats `D` as exclusively under their control (e.g., using it as DID ownership for NFTs, or as a VC "authorized provider").
5. Owner A (or a party controlling DID `X` or `Y`) can later initiate the DID recovery flow against `D`'s current coin, since the on-chain puzzle still commits to the recovery list `[X, Y]` with threshold `1`, regaining control of `D`'s inner puzzle key away from Owner B without Owner B's consent.

    async def get_innerpuz_for_new_innerhash(self, pubkey: G1Element) -> Program:
        """
        Get the inner puzzle for a new owner
        :param pubkey: Pubkey
        :return: Inner puzzle
        """
        # Note: the recovery list will be kept.
        # In a selling case, the seller should clean the recovery list then transfer to the new owner.

    def reset_recovery_list(self) -> Program | None:
        if self.did_info.current_inner is None:
            return None

        uncurried_args = uncurry_innerpuz(self.did_info.current_inner)
        if uncurried_args is None:
            return None

        _, og_recovery_list_hash, _, _, _ = uncurried_args
        if self.did_info.num_of_backup_ids_needed == 0 and not did_recovery_is_nil(og_recovery_list_hash):
            return None

        if len(self.did_info.backup_ids) > 0:
            return None

        return og_recovery_list_hash
