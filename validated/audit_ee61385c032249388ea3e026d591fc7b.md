### Title
Unauthenticated OP_RETURN operator attribution in `update_finalized_payouts` lets an unprivileged withdrawer front their own payout and frame an honest operator for reimbursement it never funded - (File: `core/src/verifier.rs`)

### Summary
`update_finalized_payouts` credits a payout to whatever operator x-only pubkey appears in the *first* `OP_RETURN` output of any transaction that spends the registered `withdrawal_utxo`, with no cryptographic check that the named operator actually signed, funded, or broadcast that transaction. Because the withdrawer's own `SinglePlusAnyoneCanPay` signature only commits to the withdrawal input and the destination output, the withdrawer (an unprivileged attacker) can complete the payout with their own additional funding inputs and stamp an arbitrary, honest operator's public key into the `OP_RETURN`, causing that operator's own automation (`PayoutCheckerTask`) to later claim on-chain reimbursement it never earned.

### Finding Description
The claimed binding is:
`payout_payer_operator_xonly_pk (DB, set by update_finalized_payouts)` == `xonly_pk of the operator whose own funds actually paid output[0] of the confirmed payout tx`.

Trace:
1. `core/src/rpc/parser/operator.rs::parse_withdrawal_sig_params` enforces the withdrawer's `in_signature` to be `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) . This sighash flag commits **only** to the withdrawal input and the single matching output (`output[0]`); every other input/output of the eventual transaction is unconstrained by the signature.
2. `create_payout_txhandler` (the "canonical" path) builds `output[0]` (payout), `output[1]` (anchor) and `output[2]` (`OP_RETURN` with the *fronting* operator's x-only pubkey), and the fronting operator funds/signs the remaining inputs themselves via `fund_raw_transaction` [2](#0-1) [3](#0-2) .
3. Because the withdrawer already possesses their own valid `SinglePlusAnyoneCanPay` signature (they created it to submit the withdrawal via `WithdrawParams`/`aggregator.withdraw` [4](#0-3) ), nothing on-chain prevents the withdrawer from building their own independent transaction that reuses this signature over the same input/output[0], adds their own funding inputs (signed by themselves, satisfying `output[0]`'s exact committed amount/script), and appends an `OP_RETURN` naming **any** operator's public x-only pubkey (public information).
4. `Verifier::update_finalized_payouts` finds this transaction via `get_payout_txs_for_withdrawal_utxos` (keyed only on which tx spent the recorded `withdrawal_utxo_txid/vout`) [5](#0-4) , extracts the operator pubkey purely from `get_first_op_return_output`'s unsigned/unauthenticated push data [6](#0-5) [7](#0-6) , and writes it into `withdrawals.payout_payer_operator_xonly_pk` with no signature or funding-source check at all.
5. The framed, entirely honest operator's `PayoutCheckerTask` polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` [8](#0-7) [9](#0-8)  and, finding this DB row, automatically calls `handle_finalized_payout`, which allocates a kickoff connector and drives the kickoff → reimburse transaction chain [10](#0-9) , with zero further verification that this specific operator broadcast/funded that payout.
6. `is_kickoff_malicious` (the only later cross-check) merely re-reads the *same* DB-derived `operator_xonly_pk_opt` and compares it to the kickoff's own `kickoff_data.operator_xonly_pk` [11](#0-10)  — it trivially passes because both sides derive from the same attacker-controlled `OP_RETURN`; it never checks who funded the payout tx.

No other guard (`SPV::verify`, `verify_storage_proofs`, `Operator::is_profitable`, DB uniqueness) validates that the credited operator's key/wallet actually produced the payout transaction — attribution is a bare, unsigned `OP_RETURN` push.

### Impact Explanation
The framed operator's own protocol automation will (without any operator action or consent) spend a kickoff connector and eventually receive a `reimburse_tx` payout from their own round collateral for a withdrawal they never funded. This is exactly "an operator reimbursed for a payout it never funded" (Critical). It is fully repeatable: for every withdrawal the attacker initiates, they can choose any currently active operator's public key to frame, draining that operator's collateral/round reimbursement capacity across arbitrarily many deposits/withdrawals, at the attacker's own expense of pre-funding the payout output (which they recoup as the "payout" simply reaches the destination they specified). The blast radius spans every operator whose x-only pubkey is public (all of them, by protocol design) and every withdrawal.

### Likelihood Explanation
No special privilege is required: the attacker only needs to be the withdrawer (calls `withdraw` on the Citrea contract themselves), hold enough BTC to fund `output[0]` at the exact committed amount/script (this is money that ultimately reaches the correct destination, so it is not "wasted" from the attacker's perspective — they are simply choosing who is credited for having paid it), and know any operator's public x-only pubkey (published/discoverable). The attack requires no cooperation from verifiers, operators, or the aggregator, and can be executed purely by broadcasting a self-crafted Bitcoin transaction reusing the withdrawer's own presigned `SinglePlusAnyoneCanPay` signature.

### Recommendation
Do not derive payout attribution solely from unauthenticated `OP_RETURN` content. Require a cryptographic binding between the claimed operator and the payout transaction, e.g.:
- Require the `OP_RETURN` push (or an additional signature covering it) to be signed by the named operator's key, and verify that signature in `update_finalized_payouts`/`is_kickoff_malicious` before attributing payer credit, or
- Bind the operator's identity to one of the transaction's *signed* inputs (e.g., require the operator's funding input, covered by `SIGHASH_ALL`, to be present and attributable to that operator's known UTXO/wallet) rather than to an arbitrary unsigned output.

### Proof of Concept

3. Feed `decoy_tx` into `block_cache` and call `Verifier::update_finalized_payouts`.
4. Assert `db.get_payout_info_from_move_txid(...).0 == Some(operator_B_xonly_pk)` even though operator B never signed/funded any input of `decoy_tx`.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

            .db

        if current_round_index != round_idx {
            // we currently have no free kickoff connectors in the current round, so we need to end round first

                    current_round_index, round_idx, deposit_outpoint
                ).into());
            }
            tracing::info!(
                "Operator: Starting next round to be able to get reimbursement for the payout"

            // start the next round to be able to get reimbursement for the payout
            self.end_round(dbtx).await?;

    /// Returns the withdrawal indexes and their spending txid for the given

    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }
