### Title
Consensus-incentive reward misattribution via batch front-loading — attacker can redirect a legitimate relayer's `$BRIDGE` treasury reward to themselves - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::on_executed` (the `FeeHandler` invoked by `pallet-ismp` after processing a batch of ISMP messages) determines **which relayer to pay** solely from `messages.get(0)` — the first message in the batch — but then pays **every** `StateMachineUpdated` event's reward found anywhere in that batch's `events` to that single relayer. [1](#0-0) 

### Finding Description
`on_executed` is called once per processed batch of `Message`s (a `Vec<MessageWithWeight>`) together with the batch's `events` (which can contain multiple `IsmpEvent::StateMachineUpdated` entries — one per consensus message that advanced a state machine):

```rust
let maybe_relayer_account = messages.get(0).and_then(|first_message| {
    if let Message::Consensus(consensus_msg) = &first_message.message {
        ... recover signer from consensus_msg.signer ...
    } else { None }
});

if let Some(relayer_account) = maybe_relayer_account {
    // collapse ALL StateMachineUpdated events in the whole batch to
    // one highest height per state machine ...
    for (state_machine_id, latest_height) in highest_per_state_machine {
        let _ = Self::process_message(state_machine_height, state_machine_id, relayer_account.clone().into());
    }
}
``` [2](#0-1) 

The relayer identity is bound to only the **first** message's embedded sr25519 signature, but the reward loop iterates over *all* `StateMachineUpdated` events collected from the *entire* batch, regardless of which specific `Message::Consensus` entry (and therefore which signer) actually produced each state-machine's height advance. `pallet_ismp::Pallet::handle_unsigned` accepts an arbitrary `Vec<Message>` from an unsigned/permissionless origin, so any submitter can construct a batch and choose its ordering — the batch submitter is not required to be the signer of any message inside it (the per-message `signer` field is only a sr25519 signature over the payload, not tied to the extrinsic's origin). Consensus proofs/messages are broadcast data (relayers gossip and publish signed consensus messages to get their proofs on-chain), so an attacker can observe a legitimate relayer's already-signed `Message::Consensus` for chain B, then submit their own trivial/cheap signed `Message::Consensus` for chain A as `messages[0]` in a batch alongside the intercepted message for chain B.

Because the reward attribution collapses to `messages[0]`'s signer for every `StateMachineUpdated` event in the batch, the attacker collects the reward for chain B's real (larger) height advance — a reward that was supposed to go to the relayer who actually authenticated and delivered chain B's consensus proof — while only having contributed a minimal/trivial update for chain A themselves.

### Impact Explanation
This directly causes **wrong-beneficiary fund transfer**: `T::Currency::transfer` moves real treasury (`$BRIDGE`) funds from `TreasuryAccount` to the attacker's account instead of the legitimate relayer, and `T::ReputationAsset::mint_into` also mints reputation to the wrong account. [3](#0-2) 

This is a direct loss/misdirection of protocol funds triggered by an unprivileged, permissionless caller assembling a batch from public data — no malicious relayer, prover, or admin collusion is required, only observation of already-broadcast signed messages and control over batch composition via the unsigned extrinsic.

### Likelihood Explanation
The attack requires no special privileges: `handle_unsigned` is designed to be submitted without a signed origin, and consensus messages are inherently public once broadcast (they must reach chain state to have effect). An attacker only needs to front-run/reorder a batch submission so their own signed message is `messages[0]`, then append other relayers' publicly-observable signed consensus messages. Mempool visibility and same-block inclusion make this feasible whenever multiple consensus updates for different state machines are pending simultaneously, which routinely happens with an active relayer network servicing many chains.

### Recommendation
Attribute each `StateMachineUpdated` reward to the relayer who actually signed the specific `Message::Consensus` that produced it, rather than defaulting to `messages[0]`'s signer for the whole batch. Concretely, build a per-state-machine-id map from `Message::Consensus` entries to their recovered signer (matching consensus proof height ranges to the corresponding `StateMachineUpdated` event), and pay/mint per state machine to that message's own recovered relayer instead of a single batch-wide relayer.

### Proof of Concept
1. Relayer B submits `Message::Consensus` (signed by B) advancing state machine `Chain-B` from height 100 → 200; this message becomes publicly visible (mempool/gossip) before finalization.
2. Attacker A crafts their own trivial `Message::Consensus` (signed by A) advancing an unrelated/cheap state machine `Chain-A` by 1 block, and submits a batch `[A's message, B's intercepted message]` via `pallet_ismp::handle_unsigned` (unsigned origin), ensuring A's message is index 0.
3. `pallet-ismp` processes both messages, producing two `StateMachineUpdated` events (`Chain-A`, `Chain-B`) which are passed together to `pallet_consensus_incentives::on_executed`.
4. `on_executed` recovers the relayer from `messages[0]` only (A), then loops over `highest_per_state_machine` for both `Chain-A` and `Chain-B`, calling `process_message(..., relayer_account = A)` for both — paying A the `Chain-B` reward that should have gone to B, per `modules/pallets/consensus-incentives/src/impls.rs:46-75, 112-156`.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
