### Title
Partial-failure handling in staking `CompleteUnbonding` allows a blocked/unassociated recipient to permanently freeze already-mature unbonding funds - ([File: sei-cosmos/x/staking/keeper/delegation.go])

### Summary
The Sei staking module's `CompleteUnbonding` processes an unbonding delegation's mature entries in a loop, paying out each entry to the delegator via the bank keeper as it goes, but it does not defer, roll back, or independently re-queue on a mid-loop failure. This mirrors the reported PufferVault bug class: a multi-step withdrawal process is treated as atomic per-entry but the surrounding accounting/queue bookkeeping is not adjusted when a step fails partway through, producing state that under- or over-tracks the true withdrawal outcome.

### Finding Description
`CompleteUnbonding` iterates over `ubd.Entries`, and for each mature entry calls `k.bankKeeper.UndelegateCoinsFromModuleToAccount(ctx, types.NotBondedPoolName, delegatorAddress, sdk.NewCoins(amt))` [1](#0-0) . If this call fails (e.g. the delegator address is blocked from receiving funds via the bank module's `BlockedAddr`/`CanSendTo` check), the function returns the error immediately without calling `k.SetUnbondingDelegation(ctx, ubd)` to persist the entry removals made so far [2](#0-1) .

Critically, the caller in the staking `EndBlocker` (`BlockValidatorUpdates`) has already permanently dequeued the maturity-time slice via `DequeueAllMatureUBDQueue` before calling `CompleteUnbonding`, and on error it simply does `continue` — it does **not** re-insert the pair into the time-based unbonding queue: [3](#0-2) .

The existing test `TestEndBlockRetainsUnbondingForInvalidRecipient` demonstrates exactly this outcome: after `EndBlocker` runs, the `UnbondingDelegation` record is still present unchanged in the store, but the timeslice queue entry has been deleted (`iterator.Valid()` is false) [4](#0-3) . Because nothing else in the staking module re-inserts a `DVPair` into `UBDQueue` for an already-matured, already-dequeued unbonding delegation, this entry becomes permanently unreachable by the automatic `EndBlocker` completion path — the funds sit in the `NotBondedPool` module account and the delegator's `UnbondingDelegation.Entries` record stays mature forever without any code path that retries the payout.

This is the same bug class as the report: the withdrawal/claim pipeline (mature-queue dequeue → per-entry bank payout → store update) is not treated as an atomic unit, and a failure in one step (the bank transfer) is not reconciled against the step that already succeeded (dequeuing from the time-indexed queue), leading to inaccurate/stuck accounting state, exactly as PufferVault's `claimWithdrawalsFromLido`/`initiateStETHWithdrawalFromEigenLayer` failed to reconcile expected vs. actual withdrawal amounts across multi-step, partially-failing operations.

Additionally, if an unbonding delegation has *multiple* mature entries and the bank transfer fails on a later entry after earlier entries in the same call already succeeded (i.e., delegator received coins for entry 0 but the call fails on entry 1), the local `ubd.RemoveEntry` calls made in-memory for the successful entries are discarded when the function returns early (no `SetUnbondingDelegation` call), yet the underlying bank state changes for those already-succeeded entries are not reverted (Cosmos SDK keeper calls are not automatically rolled back on parent function error return unless the caller uses a cache-wrapped context). This creates a state where the store still reflects the old (unremoved) entries while the delegator has already been paid for some of them — an accounting mismatch that mirrors the report's core complaint about not tracking "actual amounts received versus expected."

### Impact Explanation
This causes **permanent freezing of funds**: the `NotBondedPool` module account continues to hold tokens that were already committed to be released to a delegator whose unbonding matured, but the delegation record is orphaned from the queue that would trigger any retry. There is no user-facing message or keeper method that re-inserts an already-dequeued, already-matured `UnbondingDelegation` back into `UBDQueue`, so the funds are stuck without any programmatic recovery path — meeting the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Reaching a "blocked recipient" condition on a legitimate unbonding delegator address is the main precondition. In the Sei EVM<->Cosmos address-association model, an unprivileged user submits ordinary `MsgUndelegate` transactions; if the resulting delegator address later fails the bank module's send-eligibility check (e.g., because it is or becomes an address the bank module treats as blocked, or SendEnabled restrictions apply at the time of maturity), the described failure occurs automatically at the next `EndBlocker`, with no attacker action required beyond normal undelegation. The existing dedicated regression test in the codebase confirms this exact scenario is already known and reproducible using an EVM-associated Sei address.

### Recommendation
- Make queue removal and payout atomic: only delete the maturity timeslice entry from `UBDQueue` after `CompleteUnbonding` succeeds, or re-insert the `DVPair` back into the queue (e.g., at the next block time) if `CompleteUnbonding` returns an error.
- In `CompleteUnbonding`, track per-entry success and only remove/`SetUnbondingDelegation` for entries that were successfully paid out, continuing to process remaining entries instead of aborting the whole loop on the first error, and log/emit an event for entries that could not be paid so operators can intervene.
- Consider using an isolated (branched) context per entry so a failed transfer for one entry does not leave the overall `ubd` object in a partially-mutated, unpersisted state relative to already-succeeded transfers.

### Proof of Concept
The codebase's own regression test demonstrates the freeze condition: [4](#0-3)  sets up an `UnbondingDelegation` for a delegator address that fails `CanSendTo`, matures it, runs `staking.EndBlocker`, and asserts that (a) the pool balance is unchanged (funds not delivered), (b) the delegator balance is zero (funds not received), (c) the `UnbondingDelegation` record is still present unchanged, and (d) the `UBDQueueIterator` for that maturity time is now empty — proving the record can never be automatically reprocessed by the `EndBlocker` again, permanently freezing the pool's tokens for that delegation.

func TestEndBlockRetainsUnbondingForInvalidRecipient(t *testing.T) {
	_, app, ctx := createTestInput(t)
	maturity := time.Unix(1, 0).UTC()
	ctx = ctx.WithBlockTime(maturity)
	evmAddr := common.HexToAddress("0x3333333333333333333333333333333333333333")
	delegator := sdk.AccAddress(evmAddr[:])
	app.EvmKeeper.SetAddressMapping(ctx, delegator, evmAddr)
	app.EvmKeeper.SetAddressMapping(
		ctx,
		sdk.AccAddress(common.HexToAddress("0x4444444444444444444444444444444444444444").Bytes()),
		evmAddr,
	)
	validator := sdk.ValAddress(seiapp.AddTestAddrsIncremental(app, ctx, 1, sdk.NewInt(10000))[0])
	amount := sdk.NewInt(40)
	bondDenom := app.StakingKeeper.BondDenom(ctx)
	notBondedPool := app.StakingKeeper.GetNotBondedPool(ctx)
	coins := sdk.NewCoins(sdk.NewCoin(bondDenom, amount))

	require.NoError(t, apptesting.FundModuleAccount(
		app.BankKeeper,
		ctx,
		notBondedPool.GetName(),
		coins,
	))

	unbonding := types.NewUnbondingDelegation(delegator, validator, 0, maturity, amount)
	app.StakingKeeper.SetUnbondingDelegation(ctx, unbonding)
	app.StakingKeeper.InsertUBDQueue(ctx, unbonding, maturity)
	require.False(t, app.BankKeeper.CanSendTo(ctx, delegator))

	poolBalanceBefore := app.BankKeeper.GetBalance(ctx, notBondedPool.GetAddress(), bondDenom)
	require.NotPanics(t, func() {
		staking.EndBlocker(ctx, app.StakingKeeper)
	})

	poolBalanceAfter := app.BankKeeper.GetBalance(ctx, notBondedPool.GetAddress(), bondDenom)
	require.Equal(t, poolBalanceBefore, poolBalanceAfter)
	require.True(t, app.BankKeeper.GetBalance(ctx, delegator, bondDenom).IsZero())
	retained, found := app.StakingKeeper.GetUnbondingDelegation(ctx, delegator, validator)
	require.True(t, found)
	require.Equal(t, unbonding, retained)

	iterator := app.StakingKeeper.UBDQueueIterator(ctx, maturity)
	require.False(t, iterator.Valid())
	require.NoError(t, iterator.Close())
}
