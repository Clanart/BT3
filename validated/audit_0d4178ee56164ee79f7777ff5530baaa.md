Based on the code I was able to examine, the strongest local analog to the "missing validation on accounts used in a privileged call" bug class is the complete absence of access control on `CallDispatcher.dispatch()`, which is the shared execution primitive multiple Hyperbridge apps (`IntentGatewayV2`, `HyperFungibleTokenUpgradeable`) rely on to move escrowed value.

### Title
Unauthenticated `CallDispatcher.dispatch()` allows anyone to spend the dispatcher's escrowed balance - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has no caller restriction whatsoever — any address can invoke it and force the contract to execute arbitrary `to.call{value: call.value}(call.data)` using the dispatcher's own held balance. This mirrors the reported class of bug: a function that operates on privileged/escrowed resources (there, `remaining_accounts` fed into `solana_ibc::cpi::set_stake`; here, the dispatcher's own funds fed into an arbitrary external call) without validating who is allowed to trigger it or that the resources belong to the caller.

### Finding Description
`CallDispatcher.sol` is designed to transiently hold funds — it exposes an explicit `receive()` "to accept ETH transfers" [1](#0-0) , and `IntentGatewayV2.placeOrder` actively sends both native tokens and ERC-20 tokens into this shared dispatcher before invoking arbitrary predispatch calldata and then sweeping the dispatcher's balance back out: [2](#0-1) [3](#0-2) 

The sweep itself is performed by calling `dispatch()` again with `transferCalls` that move the *entire* current balance of each token/ETH out of the dispatcher to the gateway [4](#0-3) .

However, `dispatch()` itself performs no `msg.sender` check and no ownership/ordering validation on the `Call[]` it executes — it only checks that `to` is a contract: [5](#0-4) 

Because the dispatcher is a single shared instance (`_params.dispatcher`) referenced by any app configured to use it, and it holds real value between the moment tokens/ETH are transferred in and the moment they are swept back out, any externally owned account can call `dispatcher.dispatch(...)` directly with a `Call[]` that redirects that balance to itself. This is functionally identical to the audited bug: a critical execution primitive consumes externally supplied "accounts"/targets and value without verifying that the invoker is the authorized owner of that state — just as `deposit` trusted unchecked `remaining_accounts` for a CPI that could touch the wrong stake account.

### Impact Explanation
Any native ETH or ERC-20 balance sitting in `CallDispatcher` — whether from `IntentGatewayV2`'s predispatch flow, dust left behind by fee-on-transfer tokens, or direct transfers via its `receive()` — can be drained by an unprivileged attacker with a single unauthenticated call. This is a direct "theft of escrowed/bridged funds" impact matching the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories, since the funds move to an address that was never the rightful beneficiary of that call.

### Likelihood Explanation
No privileged role, relayer, prover, or governance action is required — `dispatch()` is `external` with zero modifiers, so exploitation only requires calling it while the dispatcher holds a non-zero balance. Given `IntentGatewayV2.placeOrder`'s predispatch path routinely moves both native and ERC-20 value through this same shared contract, transient balances are an expected, recurring condition rather than an edge case.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by contracts that are supposed to own the balance at that moment (e.g., an `onlyCaller`/allowlist of registered apps, or make the dispatcher per-order/ephemeral rather than a shared singleton), and avoid leaving swept-in value resident in a permissionless contract even momentarily. At minimum, add the same class of validation the original report requested for `remaining_accounts`: verify the caller and the `Call[]` targets/values against an expected, pre-committed set rather than trusting the balance opportunistically.

### Proof of Concept
1. Observe (or wait for) any transaction that causes native ETH or ERC-20 tokens to sit in the shared `CallDispatcher` instance — e.g., an `IntentGatewayV2.placeOrder` call with `predispatch.assets` set, between the transfer-in step [6](#0-5)  and the sweep-out step [7](#0-6) , or simply send tokens/ETH directly to the dispatcher.
2. As any unprivileged account, call `CallDispatcher.dispatch(encoded)` directly with a `Call[]` whose `to` is the token contract and `data` is `transfer(attacker, balance)` (or, for ETH, a `Call` with `value` equal to the dispatcher's balance and `to` set to the attacker's address).
3. Since `dispatch()` performs no caller check [5](#0-4) , the call succeeds and the attacker receives the dispatcher's balance before the legitimate owner (e.g., `IntentGatewayV2`) can perform its own sweep.

Note: I was not able to fully verify within the available searches whether `_params.dispatcher` is deployed as a single global singleton shared across multiple app instances/chains, or a fresh instance per gateway deployment — this affects how large the exploitable window/balance typically is. If a Devin session with full repo/terminal access is desired to confirm deployment topology and construct a runnable Foundry PoC, that would need to be done separately.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
