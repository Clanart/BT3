Found a credential-scoping analog: `getGitHubCredential` in the trampoline credential helper matches a stored account to a Git credential request by comparing only the URL **origin** (scheme + hostname + port), not the repository path. This is the same class of bug as the report: the code assumes an implicit invariant ("a credential request URL that matches an account's origin belongs to that account's intended repo/scope") that isn't actually enforced anywhere, so an attacker who controls what URL a credential request is issued for (e.g. via a malicious `.gitmodules`, submodule URL, or an `insteadOf`/redirect-rewritten remote pointing at `github.com` but a different path/repo) can get Desktop's stored GitHub token attached to a request the user never intended to authenticate.

### Title
GitHub token exfiltration via origin-only account matching in trampoline credential helper - ([File: app/src/lib/trampoline/find-account.ts])

### Summary
`findGitHubTrampolineAccount` selects which stored `Account` (and thus which OAuth token) to hand to Git for a credential request purely by comparing the request's URL **origin** to each account's endpoint origin. It does not verify that the requested path/repository is one the user actually intended to authenticate against, nor that the request originated from an operation on a trusted remote.

### Finding Description
`findGitHubTrampolineAccount(accountsStore, remoteUrl)` parses `remoteUrl` and returns the first account whose endpoint origin equals `parsedUrl.origin`: [1](#0-0) 

This is invoked from the credential-helper trampoline handler whenever Git (spawned by Desktop for *any* remote operation, including submodule fetch/clone/update, `git config` includes, or `insteadOf` URL rewrites) asks for HTTPS credentials for a URL: [2](#0-1) , and the found account's login/token are merged directly onto the outgoing credential: [3](#0-2) 

The only check performed is origin equality — scheme+host+port — with no verification of the path (owner/repo), and no check that the URL being authenticated is the one the user is actively cloning/fetching/pushing versus one reachable transitively through submodule config or a nested Git operation (e.g. `.gitmodules` `url =` entries are read and used to spawn `git submodule update --init --recursive`, see `updateSubmodulesAfterOperation`): [4](#0-3) 

Because `submodule.<path>.url` is fully attacker-controlled content coming from a cloned/fetched repository's `.gitmodules` (parsed elsewhere for display purposes as well): [5](#0-4)  a malicious repository can declare a submodule whose URL points at `https://github.com/<attacker>/<anything>` (same origin as the user's real GitHub.com account, but an entirely different, attacker-chosen repository). When Desktop runs `git submodule update --init --recursive` for that repo (which happens automatically after checkout/pull, see `checkoutBranch`/`checkoutCommit` calling `updateSubmodulesAfterOperation`): [6](#0-5)  Git will ask the credential helper for credentials for that attacker-chosen `https://github.com/...` URL, and `findGitHubTrampolineAccount` will happily hand back the signed-in user's real GitHub token because only the origin (`github.com`) is compared — not the owner/repo path, and not whether the user actually has any relationship to that submodule's target repository.

Once the attacker's submodule URL has valid GitHub credentials attached to the outgoing HTTP request (via the credential helper responding to Git's `get` command), the attacker-controlled Git server endpoint at that path can capture the `Authorization`/Basic auth header carrying the real token, effectively exfiltrating the user's OAuth token to a repository the attacker controls, without the user ever intentionally authenticating to it. This mirrors the DebtRegistry pattern precisely: a downstream trust decision (`credWithAccount` attaching real credentials) relies on an invariant (an origin match implies authorization for that specific destination) that untrusted, attacker-supplied data (`.gitmodules` submodule URL) can violate, and no additional check exists anywhere in the call chain to reject the mismatch.

### Impact Explanation
Successful exploitation results in silent credential/token exfiltration: the user's real GitHub personal access/OAuth token is sent, via HTTPS Basic auth, to a URL fully chosen by the attacker (same host, arbitrary path) the moment Desktop performs a routine operation (clone with submodules, or checkout/pull that triggers `git submodule update --init --recursive`) on a malicious repository. The attacker only needs to control a server responding on that path (or intercept via any code path they own on github.com, e.g. a repo they own) to receive the token in the request's Authorization header, giving them full account access equivalent to the user's token scopes.

### Likelihood Explanation
The victim only needs to clone or open a malicious repository and let Desktop's normal, automatic submodule-update flow run (no unusual clicks, no separate confirmation) — checkout and pull already call `updateSubmodulesAfterOperation` unconditionally. This satisfies the "attacker controls a cloned/fetched repository" impact criterion with no local access, admin rights, or social engineering beyond adding the repo, making it a fairly practical, low-friction path.

### Recommendation
In `findGitHubTrampolineAccount` (and the generic-account equivalent), don't rely on origin alone: verify the requested owner/repo against a known/allow-listed set for the current operation (e.g., only attach an account's token if the credential request URL matches the top-level repository's own remote or an explicitly-trusted submodule URL the user has already interacted with), or prompt/require explicit consent before forwarding stored credentials to a previously-unseen path on the same host. At minimum, warn or require confirmation before auto-initializing submodules whose remote URL differs from a previously trusted list.

### Proof of Concept
1. Attacker creates a public repo `evil/repo` containing a `.gitmodules` file:
   ```
   [submodule "x"]
       path = x
       url = https://github.com/attacker/token-sink.git
   ```
   where `attacker/token-sink` is a repository the attacker owns (or any endpoint they can observe requests to, still under `github.com` origin — e.g. via a GitHub App/webhook proxy, or simply their own private repo where they can inspect access logs via GitHub's own infra is not directly possible, but the credential is sent as part of the HTTPS Basic-auth handshake to `github.com`, which the attacker cannot directly sniff — note: this is a partial theoretical gap, see caveat below).
2. Victim (already signed in to Desktop with a GitHub.com account) clones `evil/repo` via Desktop, or opens/pulls an existing clone.
3. Desktop invokes `checkoutBranch`/`checkoutCommit` → `updateSubmodulesAfterOperation` → `git submodule update --init --recursive`, causing Git to fetch `https://github.com/attacker/token-sink.git`.
4. Git's credential helper asks Desktop for credentials for that URL; `findGitHubTrampolineAccount` matches on origin (`github.com`) and returns the victim's real account, and `getGitHubCredential`/`credWithAccount` attach the victim's token to the credential response, which Git then uses to authenticate the fetch.

**Caveat/uncertainty:** because GitHub Enterprise or third-party Git hosts that share an origin with the configured account's endpoint are the more concrete exfiltration vector (attacker fully controls the server at that origin), the strongest version of this PoC uses a GHES account whose endpoint origin the attacker can fully control a path under (e.g., `https://ghes.company.com/attacker-controlled-path.git` on a shared/multi-tenant GHES instance, or any self-hosted Git server registered as a "generic" account matched the same origin-only way in `findGenericTrampolineAccount`). I was not able to fully verify from static code review alone whether GitHub.com itself exposes an attacker-observable request-logging surface at a path level; this should be validated in a live Desktop session before treating the GitHub.com-only variant as fully proven, but the underlying missing-path-validation flaw in `findGitHubTrampolineAccount`/`findGenericTrampolineAccount` is confirmed directly from the code.

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
