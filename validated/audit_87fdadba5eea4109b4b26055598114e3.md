## Title
Malicious/redirected git remote can spoof the "GitHub host" identity, silently binding the wrong `endpoint` to an OAuth credential prompt - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
Reducing the Sherlock report to its core primitive: an internal bookkeeping function trusted an **attacker-influenced identifier** (`owner` vs. the real beneficiary `receiver`) instead of validating which entity should actually be credited, silently misdirecting a sensitive resource. The closest reachable analog in GitHub Desktop is in the trampoline git-credential helper, where the "kind" of a git endpoint (`generic` vs `github.com`/`enterprise`) is derived from **server-supplied, attacker-controllable data** (the `WWW-Authenticate` response header forwarded by git) rather than a verified identity, and that inferred kind is then used to auto-populate and launch a GitHub sign-in / OAuth flow bound to the attacker's endpoint.

### Finding Description
When Git needs credentials for an HTTP(S) remote, it invokes Desktop's credential helper (`createCredentialHelperTrampolineHandler`) with fields describing the request (`protocol`, `host`, `path`, and any `wwwauth[]` header lines captured from the server's response) via `parseCredential`. `getEndpointKind` decides how to treat that request: [1](#0-0) 

This block trusts an HTTP response header emitted by whatever server the user's git operation is talking to — which is precisely the "git remote / proxy response" surface the task calls out as attacker-controlled (a malicious repo host, a compromised/malicious proxy, or a spoofable server behind a `http://` remote or an unpinned redirect) — and uses it as a "happy path" to decide the endpoint is a GitHub Enterprise host, without any cryptographic or DNS-level verification that the host really is GitHub-affiliated.

Once `endpointKind !== 'generic'` and no existing account matches that `apiEndpoint`, Desktop calls into the UI to start a sign-in flow: [2](#0-1) 

`promptForGitHubSignIn` then auto-selects the sign-in target based purely on the attacker-influenced `endpoint`'s hostname, and for anything other than literally `github.com` it silently calls `beginEnterpriseSignIn` and forces the sign-in-store's endpoint to the attacker's `origin`: [3](#0-2) 

This mirrors the original bug's shape: the code path that decides "which identity does this credential/action belong to" (`lastRedeemRequestId[owner]` in the Solidity bug; `getEndpointKind`/`apiEndpoint` here) is driven by data that should not be trusted for that purpose (the caller-supplied `owner` argument there; the remote-supplied `WWW-Authenticate` header / URL host here), and the mismatch is not caught by any later check — `AccountsStore` will happily persist a new `Account` keyed by whatever `endpoint`/`origin` the flow was silently bound to (see `getKeyForEndpoint`/`accountEquals`, which key exclusively off `endpoint` string equality): [4](#0-3) [5](#0-4) 

### Impact Explanation
If a user adds/clones from, or is redirected to, a malicious/compromised host while doing ordinary git operations (fetch/pull/push over HTTP), that host can:
1. Force Desktop to believe it is a GitHub/GHE endpoint (via a crafted `WWW-Authenticate: ... realm="GitHub"` response header) even though it isn't, causing an unsolicited sign-in/OAuth popup to appear silently bound to the attacker's `origin`.
2. Because the endpoint used for the OAuth/enterprise sign-in flow (`this.dispatcher.setSignInEndpoint(origin)`) is taken from the credential-helper request rather than a user-typed, explicitly-trusted value, the resulting `Account` gets persisted under an attacker-controlled `endpoint` string. Any later credential lookups keyed by that endpoint (`getKeyForEndpoint`, `findAccountForRemoteURL`, `findGitHubTrampolineAccount`) will now treat that attacker endpoint as a legitimate authenticated GitHub account, and its token would be sent as Basic-Auth credentials (`credWithAccount`) to that same attacker-controlled host on subsequent git operations targeting it — i.e., a token minted for what the user believes is a normal git auth prompt ends up scoped to/exfiltratable by the attacker's host.
3. At minimum this is an unprompted, spoofable trigger of the OAuth/enterprise sign-in UI driven entirely by network response content, which the task's valid-impact criteria (attacker controls a git remote/proxy response, unauthorized OAuth/account binding) directly cover.

### Likelihood Explanation
Reaching this code requires nothing more than the user performing a normal git operation (fetch/clone/push) against a repository whose remote is (or redirects to) a server under attacker control — no local access, no admin rights, no pre-existing malware, no credential leakage, and no unnatural user steps beyond the normal "type credentials"/"sign in" prompt the app already shows during authentication. The `wwwauth[]` fallback path is explicitly documented in the code as a convenience "happy path", suggesting it was not hardened against a hostile server intentionally emitting that header, which raises likelihood further.

### Recommendation
- Do not use the `WWW-Authenticate` header (or any other server-supplied metadata) alone to classify an endpoint as `enterprise`/`github.com`; require either an exact match against a known/user-registered endpoint or a verified `isGitHubHost` probe (already used elsewhere in this same function) before short-circuiting to a GitHub-specific flow.
- In `promptForGitHubSignIn`, do not silently call `setSignInEndpoint`/`beginEnterpriseSignIn` with an endpoint that was not explicitly confirmed by the user; surface the actual host being contacted and require explicit user confirmation before starting any OAuth/enterprise sign-in bound to it.
- Ensure `AccountsStore` account creation from credential-helper-triggered sign-ins is not silently persisted for endpoints that don't match a previously known/trusted GHE URL.

### Proof of Concept
Conceptual PoC (cannot be executed here, but the path is fully traceable in source):
1. Attacker stands up an HTTP git server at `https://evil.example.com/repo.git` (or MITMs/redirects an existing `http://` remote to it).
2. Victim adds this as a remote (or clones it) in GitHub Desktop and performs a fetch/push.
3. When git requests credentials, the attacker's server responds with `WWW-Authenticate: Basic realm="GitHub"` on the 401.
4. `getEndpointKind` (trampoline-credential-helper.ts:153-166) matches the `realm="GitHub"` pattern and returns `'enterprise'` for `evil.example.com` purely from that header, with no verification.
5. Since no account exists for `apiEndpoint` = evil.example.com, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com/...')`.
6. `promptForGitHubSignIn` sees `hostname !== 'github.com'`, calls `beginEnterpriseSignIn(cb)` and `setSignInEndpoint(origin)` with `origin = 'https://evil.example.com'`, launching the GitHub Enterprise sign-in UI bound to the attacker's host without the user ever typing that URL themselves.

I was unable to fully trace how `beginEnterpriseSignIn`/`setSignInEndpoint` interact with the OAuth authorize/token exchange (`sign-in-store.ts`) to confirm whether the final OAuth token exchange itself validates the endpoint against a GitHub-issued client id/secret binding (which could limit real-world exploitability to phishing/UX-confusion rather than genuine GitHub.com token theft) — this would need further review of `app/src/lib/stores/sign-in-store.ts`'s `authenticateWithBrowser`/`requestOAuthToken` and `app-info.ts` client-id scoping before rating this beyond a spoofing/UX-trust issue.

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
