### Title
Unprivileged external sender can forge internal output classification (Branch/Change/Forwarded) by paying to publicly derivable offset script pubkeys - (File: processor/src/networks/bitcoin.rs)

### Summary
`get_outputs` classifies every scanned Bitcoin output solely by which registered offset's `script_pubkey` it matched. The offsets for `OutputType::Branch`, `OutputType::Change`, and `OutputType::Forwarded` are deterministic `hash_to_F(b"Serai Bitcoin Output Offset", label)` scalars over the public multisig group key, so any unprivileged Bitcoin user can compute these internal addresses and send funds to them. This is the analog of CVE-2023-3899: a state-changing "method" (output classification / registration bookkeeping) is reachable by unauthorized parties because no authorization binds a script to its intended use.

### Finding Description
`scanner(key)` in `processor/src/networks/bitcoin.rs` registers three well-known offsets derived via `Secp256k1::hash_to_F(KEY_DST, b"branch" | b"change" | b"forward")`. `KEY_DST` is a public constant and the group key is public, so the tweaked keys `key + G*offset` and their P2TR `script_pubkey`s are computable by anyone. `get_outputs` then scans each block's transactions, looks up the matched offset in `kinds`, and assigns `output.kind` purely from that lookup; only `OutputType::External` outputs receive the `InInstruction` data extracted via `extract_serai_data`.

```rust
let (scanner, _, kinds) = scanner(key);
...
for output in scanner.scan_transaction(tx) {
  let offset_repr = output.offset().to_repr();
  let kind = kinds[offset_repr.as_ref()];   // classification = whoever's script was paid
  let output = Output { kind, presumed_origin: None, output, data: vec![] };
  ...
}
// only External outputs get data attached
if output.kind == OutputType::External { output.data.clone_from(&data); }
```

`Scanner::register_offset`/`scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` confirm the mechanism: `scan_transaction` returns any output whose `script_pubkey` is in `self.scripts`, with no provenance check.

### Impact Explanation
An external attacker can mint `Branch`, `Change`, or `Forwarded`-kind outputs at will:

- Forged `Change`/`Forwarded` outputs enter the processor's UTXO set as protocol-internal outputs, corrupting output accounting and scheduler planning (the scheduler treats these as internal inventory, not user deposits).
- A genuine external deposit deliberately paid to the branch/change script is misclassified: `data` (the Serai `InInstruction`) is never attached, so the deposit is processed under the wrong semantic — funds are reported received under an internal classification rather than as an attributable external payment.
- Because `BRANCH_OFFSET`/`CHANGE_OFFSET`/`FORWARD_OFFSET` are `OnceLock` statics, collisions/incremented offsets from `register_offset` are also fixed; the `kinds` map is keyed by the *final* offset repr, which the attacker can equally well derive.

This is unauthorized manipulation of classification state by an unprivileged party using only public inputs (a Bitcoin transaction they send), matching the "funds reported received under an incorrect classification / misattributed outputs" acceptance criterion.

### Likelihood Explanation
Trivially reachable: no keys, no validator status, no threshold collusion required. The attacker needs only the public group key and the published constants to compute `key + G*hash_to_F(KEY_DST, "change")`, build the P2TR script, and broadcast a standard transaction. Cost is one output's worth of BTC plus fees.

### Recommendation
Authenticate output classification rather than deriving it from the script alone. Options:

- Bind expected internal scripts to context: only accept `Change`-kind outputs from transactions the multisig itself created (check `tx.input` spends a known multisig outpoint); only accept `Forwarded` outputs matching a registered forwarding plan.
- Alternatively, require an `InInstruction`/data payload for any output treated as protocol-significant and drop or quarantine payments to internal scripts that lack matching provenance.
- At minimum, treat unsolicited payments to non-External scripts as a distinct `Unauthorized`/`Dust` kind instead of silently assigning the internal `OutputType`.

### Proof of Concept
1. Observe the multisig group key `K` (public on Serai).
2. Compute `o_change = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change")` (and `"branch"`, `"forward"`), iterating `+1` for odd-parity results exactly as `Scanner::register_offset` does.
3. Build `script = p2tr_script_buf(K + G*o_change)` and broadcast a transaction paying it, optionally embedding an `InInstruction` in an input to mimic a deposit.
4. Every processor's `get_outputs` scans the block, matches `script` in `Scanner.scripts`, looks up `kinds[o_change.to_repr()]`, and emits `Output { kind: OutputType::Change, data: vec![], .. }` — an internally-classified output created entirely by an unauthorized external party.
