### Title
Fee and weight calculated on transaction missing the OP_RETURN output in `SignableTransaction::new` — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output to `tx_outs` when `data` is present, then computes `weight`/`vbytes` via `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds its template transaction only from `payments` — omitting the already-appended `OP_RETURN` output. The same omission occurs in the change branch (`calculate_weight_vbytes(..., Some(&change))` also excludes the `OP_RETURN`). The result is the same bug class as the Ostium report: a metric (`needed_fee`, the `NotEnoughFunds` solvency check, and the `MAX_STANDARD_TX_WEIGHT` policy check) is computed on a pre-modification transaction while the transaction actually committed to and signed includes the extra output.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- `tx_outs` gains the `OP_RETURN` output at lines 194–202.
- At line 204, `(mut weight, vbytes)` is computed from `tx_ins.len()`, `payments`, and `change = None` — the OP_RETURN output is absent.
- `needed_fee = fee_per_vbyte * vbytes` (line 206), the minimum-relay-fee check (line 211), and the `NotEnoughFunds` check `input_sat < payment_sat + needed_fee` (line 215) all use this undercounted `vbytes`.
- The change path (lines 224–234) computes `vbytes_with_change` likewise without the `OP_RETURN` output.
- The standardness check `weight > MAX_STANDARD_TX_WEIGHT` (line 241) uses `weight`, which still excludes the OP_RETURN output.
- The final `SignableTransaction.tx` (lines 245–255) contains `tx_outs` *with* the OP_RETURN output, and `TransactionSignMachine::sign` commits signatures over this full transaction via `taproot_key_spend_signature_hash` with `Prevouts::All`.

`data` is attacker-influenced: `SignableTransaction::new` is invoked from `processor/src/networks/bitcoin.rs`'s `signable_transaction`, where the plan's outputs embed user-supplied instruction data (up to the 80-byte limit checked at line 171). An unprivileged Serai user who causes an output carrying data to be forwarded/refunded reaches this path.

Consequences:
- The transaction's real vsize exceeds the computed `vbytes` by roughly the OP_RETURN output size (~10–90+ vbytes), so the effective fee rate is lower than `fee_per_vbyte`. If `fee_per_vbyte` was chosen at the relay/policy minimum, the signed transaction falls below `DEFAULT_MIN_RELAY_TX_FEE` and is rejected by the network — the scheduler has already consumed the inputs/payments, so the funds stall.
- A transaction whose true weight exceeds `MAX_STANDARD_TX_WEIGHT` can pass the check at line 241 and be produced and signed, yielding a nonstandard transaction that won't relay.
- The `NotEnoughFunds` check can pass while the true required fee would fail it, slightly overpaying or mis-budgeting relative to the declared rate.

### Impact Explanation
Transactions carrying an OP_RETURN data output are signed with an understated fee and may fail propagation (below minimum relay fee or above standard weight). The multisig's scheduler treats the plan as executed once the signed transaction is produced, so payments/branches stall and funds become unconfirmable without manual recovery — a liveness/fund-availability failure driven by attacker-controlled `data` length.

### Likelihood Explanation
Any output carrying instruction data (user-supplied bytes via the Serai instruction flow) triggers the discrepancy whenever `data.is_some()`. The miscalculation is deterministic — not probabilistic — so every such transaction is affected. Exploitation to the worst outcome requires the requested `fee_per_vbyte` to sit near the relay minimum or the transaction to sit near the weight cap, which is a routine rather than exotic condition for a fee-conserving bridge.

### Recommendation
Include the OP_RETURN output in the weight/vbyte template: either pass the fully assembled `tx_outs` (or a `data`-derived output) into `calculate_weight_vbytes`, or add the OP_RETURN script to the `output` list inside `calculate_weight_vbytes` for both the no-change and change computations, so `needed_fee`, the solvency check, and the weight check all reflect the transaction that is actually signed.

### Proof of Concept
```rust
// Conceptual: 1 input, 1 payment, change address, 80-byte data
let data = Some(vec![0xAA; 80]);
let tx = SignableTransaction::new(inputs, &payments, Some(change_script), data.clone(), fee_rate).unwrap();

// Internal vbytes omitted the OP_RETURN output. The signed TX's real vsize is larger:
//   real_vbytes ≈ internal_vbytes + (1 + 1 + 2 + 80) / ~  (OP_RETURN out ≈ +90 WU -> +~22-90 vbytes)
// If fee_rate == DEFAULT_MIN_RELAY_TX_FEE/1000 sat/vb:
//   needed_fee passed line 211, but the final tx's effective rate < min relay fee,
//   so nodes reject it; scheduler already dropped the inputs from its UTXO set.
```
Concretely: construct a `SignableTransaction` with `data` set and `fee_per_vbyte` equal to the minimum relay rate; observe `needed_fee` equals `fee_per_vbyte * vbytes_without_opreturn`, while `tx.weight()` of the produced transaction exceeds the checked `weight`, and `fee() / real_vbytes < fee_per_vbyte`.
