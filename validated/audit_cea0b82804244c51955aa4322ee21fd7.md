### Title
Deserialized `ReceivedOutput` trusts unverified claimed value, enabling deposits/accounting of unspendable "funds" that later invalidate transactions - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The stETH report's bug class is: the system records the *claimed* amount of an asset rather than the *actually received* amount, and later operations built on the recorded amount fail (DoS) because the real balance is lower. In Serai, `ReceivedOutput::read` deserializes an attacker-controlled `TxOut` (value and `script_pubkey`) plus `OutPoint` with no binding to any real on-chain UTXO. `SignableTransaction::new` then treats `input.output.value` as ground truth for the input total, fee amortization, and change computation, and `TransactionSignMachine::sign` commits to those claimed prevout values via `Prevouts::All`. A forged `ReceivedOutput` reporting more satoshis than the real outpoint (or referencing a non-existent/spent outpoint) produces recorded "funds received" that are not spendable: every signature share is generated over a sighash committing to the fake prevout, and the final transaction is either invalid (insufficient real input value) or unconfirmable — permanently stalling any spend that consumes the forged output.

### Finding Description
`ReceivedOutput::read` performs no validation beyond consensus-decoding a `TxOut` and `OutPoint`; the `value` field is whatever bytes the reader supplies: [1](#0-0) 

`SignableTransaction::new` sums `input.output.value.to_sat()` into `input_sat` and only checks `input_sat < payment_sat + needed_fee` — it cannot and does not check that the outpoint exists or actually carries that value: [2](#0-1) 

`multisig` verifies only that `prevouts[i].script_pubkey` matches the offset key — again nothing ties `value` or the outpoint to reality: [3](#0-2) 

`sign` then commits to the entire claimed prevout set via `Prevouts::All(&self.tx.prevouts)` and `taproot_key_spend_signature_hash`, so the fake amount is baked into every input's sighash: [4](#0-3) 

This is the same shape as the stETH issue: an upstream component reports an asset amount (`DepositQueue` records `assets`; here `ReceivedOutput` records `TxOut.value`), downstream logic trusts the recorded figure for all accounting (recorded deposit vs. `input_sat`/fee/change math), and the final settlement step (queue's `TransferLibrary.sendAssets` vs. broadcasting the signed transaction / validating its sighash) fails because the real balance is less than the recorded one.

### Impact Explanation
"Funds reported received that are not spendable": a received output carrying an inflated `value` is treated as real balance by the transaction builder. Any `SignableTransaction` that consumes it will (a) compute payments/change against phantom satoshis and (b) produce Schnorr signature shares over a sighash that commits to prevouts the UTXO set doesn't contain. The completed transaction fails node validation (bad sighash or insufficient input value), so all honest inputs bundled into the same plan are locked behind an unbroadcastable transaction until the plan is rebuilt — a denial of service for withdrawals/redemptions directly analogous to the queue's reverted `sendAssets`.

### Likelihood Explanation
Reachable by an unprivileged party wherever `ReceivedOutput` bytes cross a trust boundary: `ReceivedOutput::read` is an explicitly untrusted deserialization sink, and outputs are routinely serialized/deserialized (e.g., `scanner.ack_block` round-trips them through the DB, and `SignableTransaction::new` consumes `Vec<ReceivedOutput>` from scheduling). An attacker who can inject or corrupt these bytes (malformed scanner data, forged stored output, tampered network message) escalates a 1-field lie (`value`) into a full pipeline DoS. Within safe usage (only scanner-produced outputs), the bug is latent, matching the acknowledged-not-fixed severity posture of the original finding — Medium.

### Recommendation
Bind `ReceivedOutput` to provenance rather than trusting decoded fields: either (a) make `ReceivedOutput::read` only usable for re-serializing scanner-verified outputs and provide a separate checked constructor that verifies the outpoint/value against the chain (or at minimum against a confirmed block's tx output) before the value enters `SignableTransaction::new`; or (b) have the scheduler/`SignableTransaction` re-derive the spendable value from chain data and use the *actual* confirmed amount for `input_sat`, fee amortization, and prevouts — the same "track the real received amount" mitigation proposed for stETH.

### Proof of Concept

// 1. Attacker supplies bytes decoding to a ReceivedOutput whose
//    TxOut.value = 1_000_000 sat while the referenced outpoint is a real
//    deposit of only 600 sat (or a nonexistent outpoint).
let forged_bytes = {
    let mut b = vec![];
    b.extend(Scalar::ZERO.to_bytes());              // offset
    b.extend(serialize(&TxOut {
        value: Amount::from_sat(1_000_000),         // CLAIMED value
        script_pubkey: real_p2tr_script,            // real, matching script
    }));
    b.extend(serialize(&real_outpoint));            // 600-sat or nonexistent UTXO
    b
};
let forged = ReceivedOutput::read(&mut forged_bytes.as_slice()).unwrap();
// read() accepts: no check that outpoint exists or holds 1_000_000 sat.

// 2. Builder trusts the claimed amount.
let stx = SignableTransaction::new(
    vec![forged],
    &[(payment_script, 999_000)],   // affordable only per fake accounting
    None, None, fee_per_vbyte,
).unwrap();                          // NotEnoughFunds NOT raised

// 3. All participants sign; sighash commits to the fake prevout via
//    Prevouts::All. Completed TX fails broadcast (bad prevout amount /
//    missing input) — every honest input in the plan is stalled: DoS.

    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
