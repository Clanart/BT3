### Title
Missing forfeit-percentage enforcement in `mWOMSVBaseRewarder._calExpireForfeit` allows users to bypass early-unlock reward forfeiture - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never applies the `mWomSV.getRewardablePercentWAD()` percentage that is used everywhere else in the protocol to penalize users who have not fully honored their lock/cool-down commitment. Instead it hardcodes `rewardableAmount = _amount`, guaranteeing `forfeitAmount == 0` for every claim, no matter the user's actual lock state.

### Finding Description
`mWOMSVBaseRewarder` is the reward pool paired with `mWomSV` (the mWOM Stability Vault lock token). It computes forfeited rewards for users who claim rewards while not fully vested/locked via `_calExpireForfeit`: [1](#0-0) 

Compare this to the structurally identical sibling contract `vlMGPBaseRewarder`, which correctly queries the locker for the user's rewardable percentage and scales the reward amount by it before computing the forfeit: [2](#0-1) 

The `mWomSV` locker contract itself exposes the exact same `getRewardablePercentWAD` function that computes the proportion of a user's mWomSV balance that is fully locked (vs. in cool-down/expired), intended to gate reward eligibility: [3](#0-2) 

However, `mWOMSVBaseRewarder._calExpireForfeit` never calls `mWOMSV.getRewardablePercentWAD(_account)`. It instead sets `rewardableAmount = _amount` directly, so the `rewardableAmount > _amount` sanity check can never trigger and `forfeitAmount = _amount - rewardableAmount` is always `0`. The dead `_amount/1000` gas-optimization branch further confirms that a genuine forfeit-percentage calculation was intended here but was dropped, an unconstrained-gadget pattern directly analogous to the reported issue where a constraint (`IsZeroGadget::eval`) needed to enforce a real invariant was omitted and replaced by a value that trivially satisfies the following check.

This function is invoked on every reward payout via `_sendReward`, which is reached from `getReward`/`getRewards`, called by `MasterMagpie` (an ordinary wallet action, e.g. `MasterMagpie.claim`/`multiclaim`) on behalf of any mWomSV staker: [4](#0-3) 

### Impact Explanation
Any mWomSV holder who has started `startUnlock` (cool-down) or has an expired unlock slot should have part of their pending mWOMSVBaseRewarder rewards forfeited (redistributed to the pool via `_queueNewRewardsWithoutTransfer`) per the design mirrored in `vlMGPBaseRewarder`/`VLMGP`. Because the enforcement is stubbed out, every user always receives 100% of `earned()` rewards regardless of lock status, and `_queueNewRewardsWithoutTransfer` (the forfeiture-redistribution path) is dead code. This is a direct theft of yield that should have been forfeited and redistributed to still-locked stakers — value is diverted away from honest long-term lockers to users exiting their lock, a permanent, protocol-wide misallocation of unclaimed yield reachable by any ordinary wallet calling the standard claim path.

### Likelihood Explanation
High likelihood: this triggers automatically on every normal reward claim by any mWomSV staker who is in cool-down or has an expired unlock slot — no special privileges, no unusual preconditions, just calling the standard `getReward`/`getRewards` flow through `MasterMagpie`.

### Recommendation
Mirror `vlMGPBaseRewarder._calExpireForfeit` in `mWOMSVBaseRewarder`:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;

    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
        rewardableAmount = _amount;
    }

    return forfeitAmount;
}
```

### Proof of Concept
1. User locks mWOM into `mWomSV`, accruing rewards in `mWOMSVBaseRewarder` over time (`rewardPerTokenStored` increases via `queueNewRewards`).
2. User calls `mWomSV.startUnlock(amount)`, moving their balance into cool-down (per `getRewardablePercentWAD`, this should reduce their "rewardable" share since `fullyInLock` decreases while `userTotalmWomSV` — the denominator — captures the same total, and the cool-down/expired portion is only counted at a discounted rate before `endTime`, or in the fully-expired branch at a time-decayed rate).
3. User (via `MasterMagpie.claim`/`multiclaimFor`) triggers `mWOMSVBaseRewarder.getReward`, which calls `_sendReward` → `_calExpireForfeit(_account, userRewards[...])`.
4. Because `_calExpireForfeit` ignores `mWOMSV.getRewardablePercentWAD(_account)` and sets `rewardableAmount = _amount`, `forfeitAmount` is always `0`, and the user receives their full pending reward via `IERC20(_rewardToken).safeTransfer(_receiver, toSend)` — despite being in/after cool-down, when a real percentage-based forfeiture should have applied and been redistributed via `_queueNewRewardsWithoutTransfer`.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
