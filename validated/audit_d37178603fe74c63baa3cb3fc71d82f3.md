### Title
Git's clone-time protection against malicious repository hooks/config is explicitly disabled and not compensated for - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` set unconditionally, and does not pass an `interceptHooks` option (unlike `pull()`, which explicitly intercepts a list of hooks that could run as part of that operation). This means an attacker-controlled remote repository (the exact “attacker controls a cloned/fetched repository” primitive) is cloned recursively while the app has turned off Git's own clone-time protection and has no fallback hook-interception safety net for this specific operation.

### Finding Description
`clone()` constructs the environment for the clone subprocess like this: [1](#0-0) 

Two things stand out:
1. `GIT_CLONE_PROTECTION_ACTIVE: 'false'` is hard-coded, unconditionally disabling whatever protection this flag gates for every clone Desktop performs, regardless of whether the remote is trusted.
2. `--recursive` is passed to `git clone`, so submodules (which can point to arbitrary, attacker-controlled URLs and paths at clone time) are fetched and checked out as part of the same operation, and the `IGitStringExecutionOptions` object built for the clone (`opts = { env }` / `executionOptionsWithProgress(...)`) never sets `interceptHooks`.

Compare this with `pull()`, which recognizes that a remote-triggered Git operation can run hooks and explicitly proxies/intercepts them: [2](#0-1) 

The hook-interception mechanism that `pull()` relies on is implemented in `withHooksEnv`, which rewrites `core.hooksPath` to a temporary, Desktop-controlled directory containing only proxy stubs, so that hooks present in the repository (which could have been shipped by an attacker via a malicious `.git/hooks` directory, `core.hooksPath` config, or a submodule) are executed through Desktop's mediated proxy instead of directly: [3](#0-2) 

Because `clone()` never supplies `interceptHooks`, this mediation path is skipped entirely for `git clone --recursive`, and because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'`, Git's own equivalent protection for the initial checkout/hook execution during clone (the very moment untrusted repository content, including submodule configuration and hooks, first lands on disk) is also disabled. The net effect is that the one operation most likely to be pointed at fully attacker-controlled content — cloning a URL supplied by the user, a deep link, or `x-github-client://openRepo` style flow — is the one for which both the upstream mitigation and Desktop's own mitigation are turned off.

### Impact Explanation
If the disabled protection and the recursive submodule checkout allow a hook (e.g. a `post-checkout` hook shipped in the repository or a submodule, or one configured via `core.hooksPath` in the cloned config) to execute unmediated, cloning an attacker-controlled or attacker-linked repository can result in arbitrary code execution on the user's machine at the moment of clone — a full renderer/host compromise, not just corrupted state. This satisfies the "attacker controls a cloned/fetched repository ... code execution" impact class described in the task's Valid Impact section.

### Likelihood Explanation
The trigger requires no special user behavior beyond the ordinary "Clone a repository" flow (via URL, `Open in Desktop` deep link, or GitHub API repository object) that GitHub Desktop is designed to handle for arbitrary/attacker-hosted repositories. No local access, admin rights, or pre-existing host compromise is needed — the user only needs to clone a URL they were led to, which is a normal, expected Desktop action. The `--recursive` flag further widens the attack surface to any submodule the attacker's top-level repository references.

### Recommendation
- Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()`, or scope it strictly to cases where Desktop has already applied an equivalent mitigation.
- Pass `interceptHooks` (mirroring `pull()`’s list, extended with `post-checkout` and submodule-related hooks) to the execution options used for `clone()`, so that any hook shipped by the newly cloned repository or its submodules runs through the same mediated proxy used elsewhere in the codebase, per `withHooksEnv`.
- Add regression tests that clone a fixture repository containing a malicious `post-checkout` hook and a submodule with its own hook, asserting the hook is intercepted/blocked exactly as it is for `pull`.

### Proof of Concept
1. Attacker publishes a Git repository whose top-level `.git`-tracked config/submodule definition points at a second repository containing an executable `post-checkout` (or other clone-triggered) hook, relying on `--recursive` submodule checkout.
2. Attacker sends the user a normal clone URL or an `x-github-client://openRepo/...` deep link pointing at this repository.
3. User clicks “Clone” in GitHub Desktop (`clone-repository.tsx` → `dispatcher.clone` → `CloningRepositoriesStore.clone` → `clone()` in `app/src/lib/git/clone.ts`).
4. `clone()` runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` and no hook interception configured.
5. If the disabled protection is Git's mitigation against executing hooks/configuration sourced from the freshly cloned content (as it is for `pull`), the attacker’s hook runs unmediated during the clone, achieving code execution on the user's machine.

Note: I could not find Git upstream documentation for `GIT_CLONE_PROTECTION_ACTIVE` inside this index to confirm precisely which upstream mitigation it toggles; this should be verified directly against the embedded Git version's source/changelog before filing, since the severity of this finding depends on what that flag actually guards.

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
