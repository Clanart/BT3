### Title
Fixed 8000-char truncation of diff text in adversarial self-refute prompt lets attacker-controlled diff padding push high-risk lines out of the refute model's evidence window, causing false-negative security bypass - ([File: plugins/security-guidance/hooks/review_api.py])

### Summary
`build_refute_prompt` truncates the diff shown to the stage-2 adversarial "self-refute" pass to the first 8000 characters via `diff_text[:8000]`, independent of the much larger `DIFF_TOTAL_BYTES`/`DIFF_PER_FILE_BYTES` caps (default 400,000/80,000 bytes) used elsewhere in the pipeline. Because the refute prompt explicitly instructs the model to REFUTE a candidate as "PRE-EXISTING" if its `vulnerableCode` "does NOT appear on any + line in the DIFF block above," an attacker who controls the diff (e.g., a contributor whose changes are reviewed by this pipeline) can pad the diff with enough benign content before the truly dangerous lines to push them past the 8000-character cutoff, causing the refute pass to reliably (not probabilistically) conclude the genuine finding is unverifiable/pre-existing and drop it.

### Finding Description
The two-stage agentic review flow is: Stage 1 (`build_investigate_prompt` / the inline equivalent in `agentic_review`) reads the *full* capped diff (up to `DIFF_TOTAL_BYTES`) and produces `candidates` (list of `{filePath, category, vulnerableCode, ...}`). [1](#0-0) 

Stage 2 (`build_refute_prompt`) is meant to adversarially verify those candidates against the same diff, but it re-slices the diff to only the first 8000 characters: [2](#0-1) 

The refute instructions tell the model to refute (drop) a candidate as "PRE-EXISTING" specifically when its cited code is absent from "any + line in the DIFF block above" — i.e., absent from the truncated 8000-char slice, not the full diff that stage 1 saw. The identical construction (`diff_text[:8000]`) is duplicated in the production `agentic_review` function in `llm.py`, confirming this is the live production code path, not a dead/unused API surface: [3](#0-2) 

An attacker who authors the reviewed diff (e.g., a PR touching many files, or bundling several innocuous file changes with `=== DIFF: {fp} ===` headers ahead of the dangerous change) controls the ordering and size of that diff text. By ensuring enough benign diff content precedes the truly dangerous `+` lines, the attacker can deterministically place the malicious code beyond byte offset 8000 in `diff_text`, while the stage-1 investigate pass (which sees the full, much-larger-capped diff) still correctly identifies it as a candidate. At stage 2, the refute model is handed a diff excerpt that never contains the candidate's cited code, satisfies the "PRE-EXISTING" refutation criterion by the letter of its own instructions, and refutes (drops) a true finding — with `survived` excluding it and no error being raised (the failure mode here isn't the LLM/schema failing open, it's the LLM being handed insufficient/misleading evidence and correctly following its own written rubric to refute).

Existing validation/allowlist checks do not catch this: `cap_diff_for_prompt`/`_cap_files_for_prompt` only bound the diff for the *investigate* stage; they are never consulted or applied to the 8000-char slice used in the refute stage.

### Impact Explanation
This breaks the stated invariant that "truncation must not consistently drop the high-risk lines the user expects to be reviewed." A diff-controlling attacker can reliably force the self-refute filter to silently discard a genuine high/critical severity finding that the investigate stage already surfaced, effectively routing dangerous code around the review/blocking control the security-guidance plugin exists to enforce. This matches the Immunefi "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries" impact category — the net effect is that a security review pipeline reports "no vulnerability" for a diff that objectively contains one.

### Likelihood Explanation
The precondition is trivial and fully within the reach of an unprivileged content author: any diff/commit whose total unified-diff text (including the `=== DIFF: path ===` headers) exceeds 8000 characters before the dangerous `+` lines appear. This is common in ordinary multi-file changes and is easy to engineer deliberately (e.g., touching several large files before the one with the injected vulnerability, since diff ordering follows file iteration order which the attacker's commit controls). The bug is deterministic given diff size/order, not probabilistic, making it highly repeatable.

### Recommendation
Do not use a flat character slice disconnected from the file-aware caps. Options:
- Reuse `cap_diff_for_prompt`'s per-file/total byte caps (already tuned to preserve completeness up to reasonable size) for the refute-stage diff instead of an independent hardcoded `[:8000]`.
- If a smaller refute-stage budget is required for cost/latency, build it by extracting only the diff hunks relevant to each candidate's `filePath`/`vulnerableCode` (i.e., an evidence-focused excerpt per candidate) rather than truncating the concatenated diff from the start.
- At minimum, guarantee that every candidate's cited file/lines are included in whatever diff excerpt is sent to the refute pass before falling back to truncating unrelated file content.

### Proof of Concept
Unit/invariant test in `plugins/security-guidance/hooks/review_api.py` test suite:
1. Construct `diff_files` with several benign files whose combined `=== DIFF: {fp} ===` text exceeds 8000 characters, followed by a final file containing a clearly dangerous `+` line (e.g., `+ os.system(user_input)`).
2. Run `cap_diff_for_prompt` then join into `diff_text` the same way `agentic_review`/production code does.
3. Build a `candidates` list containing one entry whose `vulnerableCode` is exactly the dangerous `+` line.
4. Call `build_refute_prompt(candidates, diff_text)` and assert that the resulting prompt's embedded `diff_text[:8000]` slice does **not** contain the candidate's `vulnerableCode` substring — demonstrating the refute model is handed a prompt in which the "PRE-EXISTING" refutation criterion is trivially satisfied for a genuinely new, dangerous line.
5. Assert this occurs whenever `len(diff_text) > 8000` and the dangerous line's offset is `> 8000`, showing the drop is deterministic/consistent rather than incidental — violating the truncation invariant.

def build_investigate_prompt(
    touched_paths: list[str],
    diff_files: list[tuple[str, str]],
    *,
    context_note: str = "",
) -> str:
    capped, _ = cap_diff_for_prompt(diff_files)
    diff_text = "\n\n".join(
        f"=== DIFF: {fp} ===\n{content}" for fp, content in capped
    )
    return (
        "Review this change for security vulnerabilities.\n\n"
        "Changed files (you may Read these and any other file in the repo):\n"
        + "\n".join(f"  - {p}" for p in touched_paths[:50])
        + context_note
        + "\n\nUnified diff (only + lines are new):\n\n"
        + diff_text
        + extensibility.guidance_block()
        + "\n\nInvestigate per the method in your instructions, then return "
        "the findings list."
    )
```

def build_refute_prompt(candidates: list[dict[str, Any]], diff_text: str) -> str:
    return (
        "You previously flagged these candidate vulnerabilities:\n\n"
        + json.dumps(candidates, indent=2)
        + "\n\nDIFF:\n" + diff_text[:8000]
        + "\n\nNow adversarially try to DISPROVE each one. For each "
        "candidate, FIRST identify the attacker (who controls the "
        "input) and the victim (who is harmed). REFUTE if the only "
        "victim is the attacker themselves on their own machine. KEEP "
        "if the attacker is a legitimate user/tenant but the impact "
        "reaches other users/tenants, shared infra, or server-side "
        "resources.\n\n"
        "DIFF-ANCHOR: candidates are sorted `in_diff` first, then "
        "`off_diff`. Process them in order. `in_diff` candidates "
        "use the standard KEEP/REFUTE bar above. `off_diff` "
        "candidates require STRICTER evidence: you must identify "
        "the specific +/- line in the diff that ENABLES the "
        "off-diff sink (a removed guard, a new caller, a changed "
        "argument feeding it). If you cannot name that enabling "
        "diff line, REFUTE the off_diff candidate. Additionally, "
        "REFUTE any off_diff candidate whose sink is already "
        "covered by a surviving in_diff candidate.\n\n"
        "Then Read the cited file and refute with cited file:line "
        "evidence if ANY of these holds:\n"
        "- PRE-EXISTING: the cited vulnerableCode does NOT appear on "
        "any + line in the DIFF block above — it is unchanged context "
        "in a touched file. The diff did not introduce it.\n"
```
