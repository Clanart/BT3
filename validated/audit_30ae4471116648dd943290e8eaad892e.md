### Title
Payout attribution in `is_kickoff_malicious` trusts an unauthenticated OP_RETURN, letting anyone reimburse an uninvolved operator - (File: `core/src/verifier.rs`)

### Summary
`Verifier::is_kickoff_malicious` (core/src/verifier.rs:1859-1915) attributes a payout to whichever operator's x-only pubkey is written in the payout transaction's OP_RETURN, with no check that this operator actually supplied any funds. Because the withdrawal input is signed with `SinglePlusAnyoneCanPay`, any party holding that signature — including the withdrawing user themselves — can construct and broadcast the payout transaction, self-funding the payout output and naming an uninvolved, honest operator in the OP_RETURN, causing that operator to be reimbursed the full deposit's `bridge_amount` from the move-to-vault UTXO.

### Finding Description
The broken binding is: **`db.get_payout_info_from_move_txid(...).0 (operator_xonly_pk) == the party whose funds actually paid the withdrawal output`**. In reality this field only equals "whatever 32 bytes appear in the payout tx's first OP_RETURN output."

Trace:
1. `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds a payout tx with input = the registered withdrawal UTXO (signed `SinglePlusAnyoneCanPay` by the user, `core/src/rpc/parser/operator.rs:162-187`), output 0 = user payout (both covered by the signature), and an *unsigned* OP_RETURN output carrying an arbitrary operator's x-only pubkey.
2. Because `SinglePlusAnyoneCanPay` only commits to input 0 and output 0, anyone possessing that signature (the withdrawing user obtains it themselves when calling Citrea's `withdraw`, per the threat model) can build their own competing spend of the same withdrawal UTXO: same input/output 0, but self-funded additional inputs and an OP_RETURN naming any currently-registered, uninvolved operator B.
3. Once such a transaction confirms, `update_finalized_payouts` (core/src/verifier.rs:2283-2352) blindly parses the OP_RETURN and writes `payout_payer_operator_xonly_pk = B` into the `withdrawals` table (`core/src/database/verifier.rs:198-251`) — with no verification that B signed or funded anything.
4. Operator B's own automation discovers this row via `get_first_unhandled_payout_by_operator_xonly_pk` (core/src/database/verifier.rs:282-313) and honestly starts a kickoff, believing it fronted the payout.
5. `is_kickoff_malicious` (core/src/verifier.rs:1859-1915) checks only `operator_xonly_pk == kickoff_data.operator_xonly_pk` (both are B, matches) and that the committed blockhash matches the block containing the payout (true, since it is a real block) — it never checks who funded the payout inputs. It returns `false` (non-malicious).
6. Verifiers therefore never send a Challenge (core/src/verifier.rs:1966-2026), so the BitVM assert/disprove path — which is the only place output-amount/funding could plausibly be scrutinized — is never triggered.
7. `create_reimburse_txhandler` (core/src/builder/transaction/operator_reimburse.rs:341-385) then pays B the full `bridge_amount` directly from the deposit's move-to-vault UTXO (pre-signed n-of-n from deposit setup), completing the theft.

No existing guard — `is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, or the presigned tx graph — checks that the OP_RETURN pubkey corresponds to whoever actually funded the payout's non-signature-covered inputs.

### Impact Explanation
An uninvolved, honest operator B is reimbursed `bridge_amount` BTC directly from a deposit's move-to-vault UTXO for a payout it never funded — this drains real bridge collateral to a party who did nothing, and it is fully repeatable for every future withdrawal/deposit and against any registered operator. This matches the Critical category "an operator reimbursed for a payout it never funded" (and equivalently, BTC leaves a move-to-vault UTXO without a matching fronted withdrawal by that operator).

### Likelihood Explanation
The only precondition is that the attacker be the withdrawing user (which the threat model explicitly grants: they can call Citrea's `withdraw`, choose the UTXO, signature and sighash flag). No collusion, key compromise, or majority hashrate is needed. The attacker's own funds temporarily cover the payout output but return to their own chosen output script, so the attack is essentially self-funding (cost ≈ mining fees), and it wins the race outright since the input UTXO's private key belongs to the attacker, giving them exclusive ability to decide which competing spend gets broadcast first.

### Recommendation
Do not attribute payout reimbursement based solely on the payout tx's OP_RETURN bytes. Require cryptographic proof of the claiming operator's involvement — e.g., require the operator to co-sign a designated input of the payout transaction (or otherwise bind the OP_RETURN pubkey to a signature check verified against that same operator's key at `is_kickoff_malicious` time), instead of trusting an unsigned, freely-settable output.

2. As the withdrawing "user"/attacker, build the payout tx directly (bypassing any operator's gRPC), reusing `create_payout_txhandler` but setting `operator_xonly_pk = B.xonly_pk`, fund additional inputs from a wallet the test controls, and broadcast it directly via RPC before operator A's flow can act.
3. Mine to finality and assert `db.get_payout_info_from_move_txid(...).0 == Some(B.xonly_pk)`.
4. Have operator B build/send its Kickoff for this deposit (using `KickoffData { operator_xonly_pk: B, .. }`).
5. Assert `Verifier::is_kickoff_malicious(...)` returns `false` for B's kickoff, and that the subsequent `Reimburse` tx pays `bridge_amount` to B's reimbursement address despite B having contributed zero funds to the payout.
