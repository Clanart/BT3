### Title
MessageSet extension identity carries over across items in the Java Lite array-decoder (`MessageSetSchema.mergeFrom`) - (File: `java/core/src/main/java/com/google/protobuf/MessageSetSchema.java`)

### Summary
In the Lite-runtime array-based decoder for `MessageSet` wire format, the `extension` variable that binds a MessageSet item's `type_id` to its extension descriptor is declared once for the whole message and is not reset when a new `Item` group begins. If a subsequent item's `message` (field 3) tag is encountered before that item's own `type_id` (field 2) tag, the decoder will bind the payload to the **stale extension descriptor left over from a previous item**, rather than treating it as "type not yet known" the way the equivalent C++ (`WireFormat::MessageSetParser`, `ParseMessageSetItemImpl`) and the reflection-based Java (`MessageReflection.mergeMessageSetExtensionFromCodedStream`) implementations do, which explicitly track a per-item `State` (`kNoTag/kHasType/kHasPayload`) reset for every item.

### Finding Description
The external report's invariant is: the entity that consumes/verifies content (a signature) must be bound to the correct identity (its signer), not to state left over from unrelated prior processing. Protobuf's `MessageSet` wire format has a directly analogous binding requirement: the `message` bytes (field 3) of an `Item` group must be parsed as the extension type identified by *that same item's* `type_id` (field 2), not some other item's.

In `MessageSetSchema.mergeFrom` (Lite array decoder):
- `extension` is declared before the outer `while (position < limit)` loop that walks successive `Item` groups [3](#0-2) .
- Within the inner per-item loop, only `typeId` and `rawBytes` are reset to fresh values at the top of each item; `extension` is left as whatever it was from the previous item [4](#0-3) .
- The `MESSAGE_SET_MESSAGE` case checks only `if (extension != null)` to decide whether to eagerly decode the payload directly into `extension.descriptor` via `extensions.setField(extension.descriptor, registers.object1)` [5](#0-4) . It does not verify that `extension` was actually resolved for *this* item's `type_id` (i.e., it doesn't check a "have we seen type_id for this item yet" state, unlike the reflective/C++ implementations).

By contrast:
- The C++ `ParseMessageSetItemTmpl`/`ParseMessageSetItemImpl` explicitly use a `State` enum (`kNoTag, kHasType, kHasPayload, kDone`) that is a **local variable re-declared for every item**, so a message tag seen before a type tag is buffered separately and only resolved once the matching type_id for that same item arrives [6](#0-5) .
- The reflection-based Java `MessageReflection.mergeMessageSetExtensionFromCodedStream` similarly declares `typeId`, `rawBytes`, and `extension` fresh inside the per-item method invocation [7](#0-6) .

So the Lite array-decoder path is the odd one out: it fails to re-bind (or null out) `extension` per item, meaning the "signer" (extension type) of one item's payload can leak into a later item that hasn't yet declared its own type.

### Impact Explanation
If exploitable, an attacker who controls a serialized `MessageSet`-wire-format message (e.g., an extension payload delivered to any application that deserializes attacker-controlled Lite protos with `message_set_wire_format = true` extensions) could craft an item ordering such that a later item's raw bytes get parsed and merged as an instance of an unrelated, previously-resolved extension type, rather than its own declared (or absent) type. This is a type-confusion / integrity failure analogous to signer confusion: content is silently attributed to the wrong "identity" (extension type) due to missing per-item state isolation, potentially corrupting the resulting message contents (fields interpreted under the wrong schema) without any parse error. This does not, by itself, grant memory corruption or code execution — the impact is data-integrity/type-confusion at the application level, consistent with a Medium severity classification comparable to the CVE-2026-7511 analog (binding failure, not memory safety).

### Likelihood Explanation
Exploitability requires: (1) a proto2 message using `option message_set_wire_format = true` with the Lite runtime (`ExtensionSchemaLite`/`GeneratedMessageLite`) parsing path, which is a real, supported configuration; and (2) the attacker being able to submit a bounded, otherwise well-formed length-delimited byte string as the message to a public `parseFrom`/`mergeFrom` API. Because MessageSet is a legacy/uncommon feature primarily used for large extension registries (e.g., some Google-internal protos and a few other users), and this exact ordering bug (message-before-type-id, spanning item boundaries) is a narrow trigger, likelihood is moderate rather than high, but the mechanism is reachable via the public wire-format binary parsing API with no privileged access needed.

### Recommendation
In `MessageSetSchema.mergeFrom` (and any other Lite array-decoder MessageSet paths), reset `extension` (and any related "have I resolved a type for this item yet" state) at the start of every `Item` group, mirroring the explicit per-item `State` machine used in the C++ `ParseMessageSetItemImpl`/`ParseMessageSetItemTmpl` and reflection-based Java `MessageReflection.mergeMessageSetExtensionFromCodedStream`. Concretely, declare `GeneratedMessageLite.GeneratedExtension<?, ?> extension = null;` inside the outer loop body (once per item) rather than once for the whole `mergeFrom` call, and add a differentiation between "no type_id seen yet for this item" and "type_id resolved for this item" so a stray or reordered `MESSAGE_SET_MESSAGE` tag can never be matched to a stale extension descriptor from a prior item.

### Proof of Concept
Concept (not executed — no sandbox/tooling available in this session; recommend verifying with a Devin session that can run the Lite Java runtime):
1. Define a proto2 message `M` with `option message_set_wire_format = true;` and two Lite extensions `ExtA` (number 100, message type `A`) and `ExtB` (number 200, message type `B`), both registered in the generated Lite extension registry.
2. Hand-craft a binary payload representing two `Item` groups:
   - Item 1: `type_id = 100` (`ExtA`), `message = <valid serialized A>` — this resolves `extension = ExtA` inside `MessageSetSchema.mergeFrom`.
   - Item 2: `message = <bytes intended to be parsed as B>` **without a preceding `type_id` tag** (i.e., omit or place the `type_id` tag after the message tag, or omit it entirely so the loop never assigns a new extension for item 2).
3. Because `extension` was never reset when item 2's inner loop starts, the `MESSAGE_SET_MESSAGE` branch's `if (extension != null)` check still finds `ExtA` from item 1, and decodes item 2's bytes as an instance of `A`, storing it via `extensions.setField(ExtA.descriptor, ...)` instead of leaving it as an unknown field or correctly requiring its own type_id.
4. Expected correct behavior (per C++/reflective Java): item 2's payload, lacking its own type_id before the message data completes, should either be buffered as `rawBytes` and only resolved once/if its own type_id arrives, or dropped as unknown — never silently attributed to `ExtA`.
