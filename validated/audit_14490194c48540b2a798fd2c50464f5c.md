Based on my investigation, I found a solid Desktop analog for this bug class. The smart-contract report's core pattern — *a destructive/cleanup operation proceeds and finalizes state even though a dependent sub-operation (the token transfer) can fail silently, leaving the resource in an undocumented, unrevoked state* — maps directly onto how GitHub Desktop tears down an account/OAuth token. [1](#0-0) [2](#0-1) 

### Title
Account removal ("sign out") does not verify OAuth token revocation, silently leaving stolen/leaked tokens valid - (File: app/src/lib/api.ts, app/src/lib/stores/app-store.ts)

### Summary
`AppStore._removeAccount` deletes the account's token from the local OS credential store and then calls `deleteToken(account)` to revoke the OAuth token server-side, but it never checks the result of `deleteToken`, and `deleteToken` itself swallows any network/API failure and just returns `false`. This mirrors the reported contract bug: a "destruction" step (local sign-out) completes unconditionally while the associated resource-disposal step (server-side token revocation) can silently fail, and that failure mode is neither surfaced to the user nor documented.

### Finding Description
`_removeAccount` performs two independent steps with no error propagation between them:

```ts
public async _removeAccount(account: Account) {
  log.info(...)
  await this.accountsStore.removeAccount(account)
  await deleteToken(account)
}
``` [1](#0-0) 

`accountsStore.removeAccount` deletes the token from the OS keychain and drops the account from Desktop's in-memory/persisted list [3](#0-2) . Once this succeeds, Desktop's UI and state consider the account fully "signed out."

`deleteToken` then makes a `DELETE applications/{clientId}/token` call to GitHub to actually revoke the OAuth token server-side. If this request fails for any reason (network blip, proxy interference, rate limiting, GHE endpoint unreachable), the error is caught, logged, and the function simply returns `false`:

```ts
export async function deleteToken(account: Account) {
  try {
    ...
    return response.status === 204
  } catch (e) {
    log.error(`deleteToken: failed with endpoint ${account.endpoint}`, e)
    return false
  }
}
``` [2](#0-1) 

The return value is discarded by every caller of `_removeAccount`, including the path triggered when Desktop itself detects an invalidated/compromised token (`onTokenInvalidated`) [4](#0-3)  and the user-initiated "Log out" flow in Preferences [5](#0-4) . In neither case is the user told whether the remote revocation actually succeeded — Desktop just proceeds as if the account is safely disconnected.

This is precisely the pattern flagged in the original report: the "destruct"-equivalent operation (removing the account from Desktop) is allowed to complete even though the dependent transfer/disposal step (revoking the token at the authority that actually controls it — GitHub) can fail, and that possibility is undocumented and unhandled.

### Impact Explanation
If a user's OAuth token has been exfiltrated (e.g., via a malicious repository hook, compromised extension, or any other credential-leak vector) and the user reacts by removing the account/signing out in Desktop, they will believe access has been cut off. If the revocation call to GitHub fails silently, the attacker's copy of the token remains fully valid and usable against the GitHub API indefinitely — this is unauthorized continued OAuth access that the user has no way to detect from Desktop's UI, since no warning, retry, or error state is ever presented.

### Likelihood Explanation
Any transient network condition, corporate proxy interference, GHE endpoint downtime, or GitHub API rate limiting during the exact moment of sign-out is sufficient to trigger this — no attacker interaction is required to hit the code path, and `deleteToken`'s try/catch guarantees the failure is invisible. Given that token-compromise response is a security-critical action, even infrequent network failures at that moment have outsized consequences.

### Recommendation
Propagate and surface the result of `deleteToken` from `_removeAccount`: if server-side revocation fails, warn the user explicitly that the token may still be valid on GitHub's servers and provide a retry path or a link to manually revoke the OAuth grant. Document this failure mode clearly (similar to the recommendation in the original report) instead of silently discarding it.

### Proof of Concept
1. Sign in to Desktop, note the OAuth token stored by the account.
2. Simulate a leaked token (e.g., copy it out of the OS keychain for testing purposes).
3. Block/interrupt network access to the GitHub API endpoint (or point to an unreachable proxy) at the exact moment of clicking "Log out" in Preferences.
4. Observe: `accountsStore.removeAccount` succeeds (account disappears from Desktop's account list), `deleteToken` throws inside its try/catch and returns `false`, but `_removeAccount` never inspects this value — no error dialog appears.
5. Restore network access and use the previously copied token directly against the GitHub API — it is still valid and accepted, confirming the account was never actually revoked despite Desktop showing a "signed out" state.

export async function deleteToken(account: Account) {
  try {
    const creds = Buffer.from(`${ClientID}:${ClientSecret}`).toString('base64')
    const response = await request(
      account.endpoint,
      null,
      'DELETE',
      `applications/${ClientID}/token`,
      { access_token: account.token },
      { Authorization: `Basic ${creds}` }
    )

    return response.status === 204
  } catch (e) {
    log.error(`deleteToken: failed with endpoint ${account.endpoint}`, e)
    return false
  }
}
