### Title
Unchecked truncation of `*big.Int` staking amounts to `uint64` in `parseCallResult`/`parsePermissionlessCallResult` can silently corrupt staking-reward accounting - (File: kaiax/staking/impl/getter.go)

### Summary
`kaiax/staking/impl/getter.go` reads staking amounts from the AddressBook/AddressBookV2 contracts as `*big.Int` and converts them to `uint64` using `new(big.Int).Div(amounts[i], big.NewInt(params.KAIA)).Uint64()` with no bounds check, exactly the unsafe-narrowing pattern described in the reference finding (`int128(int256(_value))` truncation in FiatDAO's `VotingEscrow`). Go's `big.Int.Uint64()` silently returns the low 64 bits when the value does not fit, rather than erroring, so if the divided KAIA amount exceeds `math.MaxUint64` the stored `StakingAmount`/`CLStakingAmount` value will silently wrap to a smaller (or effectively arbitrary) number.

### Finding Description
`parsePermissionlessCallResult` and `parseCallResult` both perform this truncating conversion: [1](#0-0) [2](#0-1) 

and for CL staking amounts: [3](#0-2) 

These `uint64` values (`StakingInfo.StakingAmounts`, `CLStakingInfo.CLStakingAmount`) are later fed directly into reward-distribution math, e.g. `assignStakingRewards`/`assignStakingRewardsFlex` compare `cn.StakingAmount` against `minStake`/`threshold` and compute `excess := cnTotalStakingAmount - minStake`, which is then multiplied against the reward budget: [4](#0-3) 

and `consolidatedNode.Split` casts `StakingAmount`/`CLStakingAmount` (already-truncated `uint64`) into `int64` for the CN/CL reward split: [5](#0-4) 

This is a chain of unchecked narrowing conversions (`*big.Int` → `uint64` → `int64`) feeding directly into consensus-critical reward-distribution arithmetic, which is the same bug class as the reference report (unsafe cast causing wrong accounting of amounts).

### Impact Explanation
If a staking (or CL staking) contract's on-chain balance, once divided by 1 KAIA (1e18), exceeds `math.MaxUint64` (~1.8e19 KAIA), the truncated `StakingAmounts`/`CLStakingAmount` values used in `getFromState`/reward computation would wrap around, producing an incorrect (and potentially much smaller, or even different-looking) staking amount for that node. Because `GetStakingInfo` results are cached and written into `StakingInfo` used identically by every full node computing `FinalizeState`/`GetDeferredReward` deterministically from the same AddressBook/CLRegistry state, all honest nodes would derive the *same* wrong value — so this would not cause a chain split by itself, but it could misallocate KIP-82 staking rewards (over- or under-paying a validator's reward address) relative to the intended stake-proportional distribution, i.e., concrete reward redistribution/theft between validators.

### Likelihood Explanation
Exploitability requires a single staking (or CL staking) contract to actually hold a balance whose KAIA-denominated amount exceeds ~1.8×10^19 KAIA. Given Kaia's total token supply is orders of magnitude below this (~10 billion KAIA range), this is not reachable under realistic economic conditions on mainnet — mirroring the original finding's outcome, where the sponsor/judge downgraded severity because tokens realistically never approach `2**128`. This report is provided as the closest reachable analog for the "unsafe cast causing broken accounting" bug class in the staking/reward-distribution module, but likelihood of triggering an actual overflow with real KAIA balances is very low absent an unrelated bug that lets an attacker mint/report an artificially huge staking balance.

### Recommendation
Add explicit bounds checks before narrowing `*big.Int` staking amounts (post KAIA-unit division) to `uint64` in `parseCallResult`/`parsePermissionlessCallResult` (and the corresponding CL amount conversion), returning an error (e.g., `staking.ErrAddressBookResult`) if the divided amount does not fit in a `uint64`, instead of silently calling `.Uint64()`. Likewise, harden `consolidatedNode.Split` to avoid raw `int64(uint64Value)` conversions of staking amounts without a fits-check.

### Proof of Concept
Conceptual (not directly triggerable with real KAIA supply):
1. Configure an AddressBook/AddressBookV2 (or CL) staking contract entry whose reported staking balance is `> math.MaxUint64 * 1e18` wei (i.e., > ~1.8×10^19 KAIA).
2. `getFromState` calls `MultiCallStakingInfo`/`MultiCallStakingInfoPermissionless`, returning this large `*big.Int` amount.
3. `parseCallResult`/`parsePermissionlessCallResult` compute `new(big.Int).Div(amount, big.NewInt(params.KAIA)).Uint64()`, silently truncating to the low 64 bits instead of erroring.
4. The wrapped `StakingAmount` is used in `assignStakingRewards`/`Split` for `FinalizeState` reward distribution, producing a reward allocation inconsistent with the node's actual stake. [2](#0-1)

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
