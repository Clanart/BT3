Based on my investigation, the strongest and most well-supported finding is a git argument-injection issue in the branch checkout path reachable from the `x-github-client://openrepo` deep link, distinct from the (well-guarded) OAuth state check and clone-path/filepath traversal protections, which I confirmed are already hardened in this codebase.

### Title
Attacker-controlled branch name from "Open in Desktop" deep link can inject flags into `git checkout` due to misplaced `--` separator - (File: `app/src/lib/git/checkout.ts`)

### Summary
The `x-github-client://openrepo/...&branch=<name>` deep link lets a remote/link-serving attacker supply a branch name that flows, largely unsanitized, into the argument list passed to `git checkout`. The `--` end-of-options marker that is supposed to prevent the branch name from being interpreted as a command-line flag is placed *after* the branch name instead of before it, so an attacker-chosen value starting with `-`/`--` can be parsed by git as an option rather than a ref.

### Finding Description
`parseAppURL` extracts `branch` from a `x-github-client://openrepo/...` URL and only rejects it via `testForInvalidChars`, whose regex blocks control characters and `~^:?*[\|"<>`, `@{`, consecutive/leading/trailing dots, and `.lock`/trailing `/` — but it does **not** reject a leading `-`: [1](#0-0) [2](#0-1) 

This action is dispatched to `openBranchNameFromUrl`, which clones/opens the repository and calls `checkoutLocalBranch(repository, branchName)` with the attacker-supplied string: [3](#0-2) 

The checkout implementation builds the git argument vector as `[branch.name, ...(optional '-b' args), '--']` — i.e. the untrusted `branch.name` is placed **before** the `--` end-of-options marker, so it is not protected from being parsed as a flag: [4](#0-3) [5](#0-4) 

Contrast this with `checkoutPaths` and `checkoutConflictedFile` in the same file, which correctly place `--` immediately before the untrusted path/branch argument: [6](#0-5) 

This mirrors the report's broken invariant: a value that should only ever be treated as inert data (a ref name, analogous to the `owner` address that should only be settable once by a legitimate caller) is instead accepted from an untrusted, attacker-controlled source and used in a security-sensitive position without the guard (`--`) that is supposed to enforce the boundary — the guard exists in the code but is applied on the wrong side.

### Impact Explanation
An attacker who controls a link the victim clicks (or a GitHub Enterprise/API object surfaced through this flow) can force `git checkout` to interpret the "branch" value as a git option instead of a ref (e.g., a flag such as `--orphan`, which takes no argument and contains no characters blocked by `testForInvalidChars`). This can silently change the semantics of the checkout the user believes they triggered (e.g., detaching into an orphan branch), corrupting the repository state the user subsequently commits/pushes from — matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
The path is reachable purely through an unprivileged, attacker-controlled `x-github-client://openrepo/...?branch=...` link — no local access, admin rights, or pre-existing malware is required, and the existing validation (`testForInvalidChars`) gives a false sense of safety while not covering leading-dash values. This is a real, reachable code path (`parseAppURL` → `dispatchURLAction` → `openRepositoryFromUrl`/`openBranchNameFromUrl` → `checkoutLocalBranch` → `checkoutBranch`).

### Recommendation
- In `getBranchCheckoutArgs` (`app/src/lib/git/checkout.ts`), place `--` immediately before `branch.name` (mirroring `checkoutPaths`/`checkoutConflictedFile`), so the branch name can never be parsed as an option.
- Additionally, extend `testForInvalidChars`/`sanitizedRefName` (or add a dedicated check in `parseAppURL`) to reject ref names beginning with `-`, consistent with `git check-ref-format --allow-onelevel` semantics.

### Proof of Concept
1. Attacker hosts a link: `x-github-client://openrepo/https://github.com/attacker/repo?branch=--orphan`
2. Victim clicks the link; Desktop parses it via `parseAppURL`, which accepts `--orphan` as a valid branch name because `testForInvalidChars` does not flag a leading dash.
3. `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` → `checkoutLocalBranch` is invoked with `branchName = '--orphan'`.
4. `checkoutBranch` builds args `['checkout', '--orphan', '--']` (assuming a local `Branch` object is constructed with that name), and git interprets `--orphan` as the checkout flag rather than as a target ref name, silently altering the repository state instead of performing the expected checkout of a ref named `--orphan`.

**Note on confidence**: I was not able to fully trace `checkoutLocalBranch`'s exact implementation (i.e., how the raw string `branchName` is turned into the `Branch` object passed to `checkoutBranch`) within the available tool budget, so the exact resulting git invocation for a *non-existent* remote branch name is not 100% confirmed — this should be verified by a follow-up session before treating the PoC as fully proven end-to-end. The core defect (untrusted, attacker-reachable branch string validated by a filter that permits leading dashes, feeding into `checkout.ts` argument construction where `--` is misplaced relative to the untrusted value) is confirmed directly from the cited source.

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

function getCheckoutArgs(progressCallback?: ProgressCallback) {

async function getBranchCheckoutArgs(branch: Branch) {
  return [
    branch.name,
    ...(branch.type === BranchType.Remote
      ? ['-b', branch.nameWithoutRemote]
      : []),
    '--',
  ]
