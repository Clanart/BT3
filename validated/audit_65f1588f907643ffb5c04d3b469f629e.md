Based on the investigation, the strongest identity-confusion analog in GitHub Desktop is a hostname-parsing mismatch in `remote-parsing.ts` that is structurally identical to the Notional bug: a value (there, a reward token; here, a git remote hostname) that satisfies a naive membership/parsing rule is treated as a trusted item, while the real underlying protocol (there, Curve/Balancer pool trades; here, actual TCP/TLS connection to the URL's authority) resolves to something else entirely.

### Title
Custom git-remote URL parser mis-extracts hostname across authority boundary, enabling host confusion in account/credential matching - (File: app/src/lib/remote-parsing.ts)

### Summary
`parseRemote()` in [1](#0-0)  extracts the "hostname" of an HTTPS remote using a hand-written regex, `^https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)(?:/|\.git/?)?$`, instead of RFC 3986/WHATWG URL authority parsing. The greedy, non-capturing `(?:.+@)?` credentials group is allowed to span a `/`, which real URL authority parsing never permits (the authority section ends at the first `/`, `?`, or `#`). This lets an attacker-controlled remote/deep-link URL smuggle a trusted-looking hostname (e.g. `github.com`) into the parser's output while the actual network host Desktop/git will contact is different.

### Finding Description
For a URL such as `https://evil.example.com/x@github.com/owner/repo`, real URL semantics place the authority at `evil.example.com` (path begins at the first `/`), so any HTTP/git client actually connects to `evil.example.com`. But `parseRemote`'s regex backtracks so that `(?:.+@)?` greedily consumes `evil.example.com/x@`, leaving `github.com` to satisfy the hostname capture group `(.+)`, and `owner`/`repo` as owner/name. The function returns `{ hostname: 'github.com', owner: 'owner', name: 'repo' }` — a hostname that is disconnected from where the connection will actually go.

This parsed (and spoofable) `hostname` field feeds directly into security-relevant matching logic:
- `findAccountForRemoteURL` in [2](#0-1)  compares `parsedURL.hostname` against each stored `Account`'s endpoint hostname to decide **which authenticated account's credentials/token should be associated with this remote**.
- `matchGitHubRepository` in [3](#0-2)  and `urlMatchesRemote`/`urlsMatch` in [4](#0-3)  likewise trust `parseRemote`'s hostname to decide whether a URL "is" a GitHub.com/GHE repository belonging to a signed-in account, and to bind PR/issue/branch deep-link actions (`open-repository-from-url`, see [5](#0-4) ) to an existing repository.

Because `dispatchURLAction` → `openRepositoryFromUrl` in [6](#0-5)  processes attacker-suppliable `x-github-client://openRepo/<url>` deep links, an attacker who gets a user to click such a link can supply a URL whose parsed `hostname` is `github.com` (satisfying `doesRepositoryMatchUrl`/`matchGitHubRepository`) while the actual clone/fetch target (passed to git verbatim as the remote URL) is an attacker-controlled host. This breaks the invariant that "the hostname Desktop uses for account/credential selection equals the hostname git will actually connect to" — the same class of invariant violated in the Notional finding, where "the token being sold" was assumed to be disjoint from "the pool's own tokens."

### Impact Explanation
If account selection or trust decisions keyed off this spoofed hostname are used before the URL reaches git verbatim (e.g., to decide "this is a GitHub.com repo, skip generic-credential prompts" or "use this account's token for API correlation"), a malicious remote/deep-link can present itself as `github.com`/a GHE host known to the user while git itself performs the underlying network operation against an attacker-controlled server named in the actual authority segment. This is a host-confusion primitive that can lead to unintended account binding and, depending on downstream consumers of `parseRemote`, misdirected trust decisions about a remote's authenticity — exactly the "unauthorized OAuth/account binding" impact category.

### Likelihood Explanation
Exploitation only requires the victim to open one crafted URL (a `x-github-client://openRepo/...` deep link, or a remote URL entered/cloned through the Clone dialog which also calls into `parseRepositoryIdentifier`/`parseRemote` per [7](#0-6) ). No local access, prior malware, or leaked credentials are needed — the entire bug is in how Desktop's own regex disagrees with standard URL authority parsing, so any attacker who controls a link the user clicks controls the mismatch.

### Recommendation
Replace the hand-rolled regex hostname extraction in `parseRemote` with `new URL()`/`URL.parse()`-based authority parsing (already used elsewhere in the codebase, e.g. `app/src/lib/api.ts`'s `isGitHubHost`) so that `hostname` can never include characters from the path component, and add a regression test asserting that URLs containing `@` after the first `/` in the path are not mis-parsed as if the `@` were part of the authority section.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

export function urlsMatch(url1: string, url2: string) {
  const firstIdentifier = parseRepositoryIdentifier(url1)
  const secondIdentifier = parseRepositoryIdentifier(url2)

  return (
    firstIdentifier !== null &&
    secondIdentifier !== null &&
    firstIdentifier.hostname === secondIdentifier.hostname &&
    firstIdentifier.owner === secondIdentifier.owner &&
    firstIdentifier.name === secondIdentifier.name
  )
}

    return unknown
  }

  const query = parsedURL.query

  if (actionName === 'oauth') {

    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }

      return unknown

      url: parsedPath,
