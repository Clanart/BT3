### Title
`OP_RETURN` data is excluded from Bitcoin fee and weight accounting, causing underpriced or oversized signed transactions - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output before calculating transaction weight and required fee, but `calculate_weight_vbytes` only receives `payments` and `change`. It never receives `data`, so the mandatory `OP_RETURN` output is omitted from both the fee budget and maximum-standard-weight check. A transaction containing an 80-byte payload can therefore be signed with a fee rate below the configured or minimum relay rate, and potentially remain within the checked weight bound while exceeding the real standard transaction weight.

### Finding Description
The constructor adds `data` as a zero-valued `OP_RETURN` output to `tx_outs` at lines 193–202. It then calculates `vbytes` using only the input count, `payments`, and no change at line 204. The same omission occurs when calculating `weight_with_change` at lines 225–227. The constructed transaction later includes `tx_outs`, including the omitted `OP_RETURN`, at lines 245–251. [1](#0-0) [2](#0-1) 

`calculate_weight_vbytes` constructs a model transaction from only `inputs`, `payments`, and optional `change`; it has no `data` parameter and therefore cannot account for the `OP_RETURN` output. [3](#0-2) 

The undercalculated `vbytes` directly determines `needed_fee`, which is checked against the selected input value at lines 204–221. The final standard-weight check also uses this undercalculated `weight` at lines 241–243. [4](#0-3) [5](#0-4) 

### Impact Explanation
An unprivileged caller able to specify transaction data can cause the wallet to create and sign a transaction that does not actually pay the requested fee rate. For transactions constructed at the minimum relay rate, omitting the `OP_RETURN` output can make the real fee rate fall below Bitcoin's default relay threshold. The transaction may fail propagation or remain unconfirmed, delaying withdrawals and any dependent scheduled transactions. If the omitted output pushes the actual transaction past the standard weight limit while the model remains below it, broadcast can fail entirely after threshold signing has completed.

### Likelihood Explanation
The issue is deterministic whenever `data` is supplied: the code allows up to 80 bytes, appends the output unconditionally, and omits it from every weight calculation. A payload-only transaction or a transaction with tight fee/change margins exposes the discrepancy most reliably. Production processor code currently passes `None` for `data`, which limits exposure in that particular integration path, but `SignableTransaction::new` exposes the reachable parameter publicly and the resulting transaction is signed exactly as constructed. [6](#0-5) 

### Recommendation
Pass the serialized `OP_RETURN` output—or all final outputs—into `calculate_weight_vbytes` rather than reconstructing size from `payments` alone. Preferably, calculate weight and vbytes after constructing the complete `tx_outs`, including `OP_RETURN` and any selected change output, and use that result for `needed_fee`, `NotEnoughFunds`, and `TooLargeTransaction` checks.

### Proof of Concept
1. Call `SignableTransaction::new` with one spendable input, no payments, no change, `Some(vec![0; 80])`, and `fee_per_vbyte = 1`.
2. The code accepts the data because its length is exactly 80 bytes. [7](#0-6) 
3. It appends an `OP_RETURN` transaction output containing the payload. [8](#0-7) 
4. The fee model is invoked with no payments and no change, so the added output contributes zero bytes to `vbytes`. [9](#0-8) 
5. The real serialized transaction nevertheless includes the `OP_RETURN` output. Its actual fee is unchanged while its actual vsize is approximately 90 vbytes larger, placing it below the minimum relay fee even though the constructor accepted it.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
