### Title
Copilot conflict resolution writes reassembled files to disk without re-verifying the combined file is free of conflict markers - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
`parseCopilotConflictResolution` validates that each individual hunk's `resolvedContent` contains no `<<<<<<<`/`=======` conflict markers [1](#0-0) . However, this is a per-hunk check only. The actual artifact that gets written to disk is produced later by `reassembleResolvedFile`/`reassembleResolutions`, which splices the validated hunks back into the original raw file content line-by-line [2](#0-1) [3](#0-2) . Nowhere after reassembly is the *combined* result re-checked to confirm it is now fully free of conflict markers before `_applyCopilotConflictResolutions` calls `writeFile` and stages the file with `git add` [4](#0-3) .

### Finding Description
The invariant that matters for a merge/rebase/cherry-pick to be safe is: the file staged and committed must contain zero residual conflict markers. The codebase enforces a component-level version of this invariant (each hunk's resolved text has no markers) but never re-checks the combined invariant on the reassembled whole file — mirroring the reported class of bug where a per-shard property is checked but the checked property is not re-verified to hold after combination.

Concretely, `reassembleResolvedFile` walks the raw on-disk content and, for well-formed conflict blocks, splices in the hunk resolution; but for a `<<<<<<<` line that isn't followed by both a `=======` separator and a closing `>>>>>>>` before EOF, the code explicitly treats it as "regular content" and copies it through unchanged [5](#0-4) . This is by design for genuinely malformed/stray markers in the original file, but it means: (1) if `hunkIndex` and the actual number of conflict blocks in the file ever diverge (e.g. a race where the on-disk file was concurrently touched, or a hunk ordering mismatch), later hunks get matched against the wrong blocks; and (2) there is no assertion at the end of `reassembleResolvedFile`/`reassembleResolutions` that the produced `resolvedContent` string is free of `<<<<<<<`/`=======`/`>>>>>>>` markers before it becomes the file content that gets committed.

`validateResolutionPaths` only checks that the *count* of hunks per file matches the expected count [6](#0-5)  — it does not validate the reassembled output. The write path in `_applyCopilotConflictResolutions` performs a staleness check (skip if the user already resolved the file externally) [7](#0-6)  but again does not scan `resolution.resolvedContent` for leftover conflict markers before `writeFile` and `git add`.

### Impact Explanation
If reassembly produces a file with residual `<<<<<<<`/`=======`/`>>>>>>>` markers (due to hunk-count mismatch against the actual marker blocks in a file that changed between context-gathering and reassembly, or any other order-desync between `hunks` and marker blocks), Desktop will `git add` and let the user commit/push a file containing raw conflict-marker text as if it were resolved — silently corrupting what the user commits, the exact class of impact called out as valid in this task (silent corruption of what the user commits or pushes). Because the file is staged automatically and the flow's whole selling point is "no manual review needed," a user relying on the Copilot dialog may push broken/nonsensical source (or, in a lock/manifest file, dependency corruption) without noticing.

### Likelihood Explanation
Moderate. This requires either an LLM output/hunk-order edge case or a benign race (file touched between when `rawContent`/marker blocks were captured for the prompt and when reassembly runs against `ctx.rawContent`) to desynchronize hunk index from marker block index. The attacker-controlled surface here is a malicious/compromised remote repository or PR whose diff/file content is crafted to contain many marker-like sequences or edge-case marker formatting, which is inspected by `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` regexes and could be used to influence how many blocks are detected vs. how many hunks the model returns, without the missing whole-file check catching the mismatch.

### Recommendation
After reassembly (in `reassembleResolvedFile` or immediately in `reassembleResolutions`/`_applyCopilotConflictResolutions`), assert the combined `resolvedContent` no longer matches any of `reassemblyOursMarker`, `reassemblySeparatorMarker`, or `reassemblyTheirsMarker` before returning/writing it; throw a `CopilotValidationError` (surfacing a retry) or fall back to skipping the file (leaving it conflicted for manual resolution) rather than staging a file with unresolved markers.

### Proof of Concept
Not independently reproducible from static analysis alone — the exact trigger requires either a Copilot model response with a hunk-count/order mismatch relative to actual marker blocks in `ctx.rawContent`, or a race where the on-disk file changes between context capture and `_applyCopilotConflictResolutions` in a way that shifts marker block boundaries without hitting the "already resolved externally" bail-out at `app/src/lib/stores/app-store.ts:7250-7256`. Because the code path lacks an end-to-end assertion, no test in the repo currently exercises "final combined file still has markers" as a failure mode; this gap itself is direct evidence of the missing invariant check.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
