### Title
`SignableTransaction::new` counts duplicated inputs toward the spendable balance, allowing a transaction whose claimed funds exceed what is actually spendable - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Float Capital `shiftTokens` bug — where each call checked the amount shifted against the user's balance but the cumulative pending shifts were never bounded — `SignableTransaction::new` in `bitcoin-serai` sums the value of every supplied `ReceivedOutput` into `input_sat` without verifying the inputs are distinct outpoints. An attacker can supply the same `ReceivedOutput` (or multiple outpoints that do not correspond to real, distinct UTXOs) repeatedly, inflating the accounted input balance beyond the funds that actually exist, exactly like shifting more tokens than were staked.

### Finding Description
In `SignableTransaction::new`, the input value is computed by unconditionally summing every element of the `inputs` vector:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
```

and each element is turned into a `TxIn` using `input.outpoint` with no uniqueness check against `previous_output`. The solvency check `input_sat < (payment_sat + needed_fee)` therefore validates against an inflated balance if the caller supplies the same `ReceivedOutput` (or two outputs with the same `outpoint`/`output` pair, which can be produced via `ReceivedOutput::read` on attacker-controlled bytes) multiple times. `ReceivedOutput::read` performs no consistency check between `offset`, `output`, and `outpoint`, so arbitrary claimed inputs can be constructed.

Each duplicated input also produces a separate `AlgorithmMachine` in `multisig` (re-keyed by `self.offsets[i]`), so every input index is signed individually with `Prevouts::All`, committing to the duplicated prevout list. The result is a fully FROST-signed transaction that is consensus-invalid — Bitcoin rejects transactions spending the same outpoint twice.

### Impact Explanation
An unprivileged party able to influence the `inputs` passed to `SignableTransaction::new` (e.g., supplying crafted `ReceivedOutput`s) can cause the multisig to produce and sign a transaction whose declared payments exceed the real spendable funds. The signed transaction can never be confirmed: it double-spends an outpoint, making the whole transaction invalid. This wastes the signing session, can permanently jam a payment queue that expects the transaction to confirm, and lets the attacker inflate `needed_fee`/change accounting against phantom balance. It is the same failure mode as the Float bug: per-item checks pass while the aggregate operation exceeds real balance, with the invalidity only surfacing at final execution.

### Likelihood Explanation
Reachability requires an attacker to influence the input list — plausible wherever `ReceivedOutput`s are deserialized (`ReceivedOutput::read` accepts untrusted bytes with no outpoint/output consistency check) or aggregated from external sources before constructing a transaction. Impact is bounded to an invalid, unconfirmable transaction rather than theft, matching the original finding's "no funds could be stolen directly, but the system can be manipulated" assessment; rated Medium.

### Recommendation
Reject duplicate `outpoint`s in `SignableTransaction::new` before summing `input_sat` (e.g., insert each `input.outpoint` into a `HashSet` and error on collision). Additionally consider validating in `ReceivedOutput::read` or at call sites that the `outpoint` is plausible relative to the `output`, and that `offset` correctly derives the `output.script_pubkey` via `p2tr_script_buf(key + GENERATOR * offset)`, so fabricated inputs cannot inflate the balance.

### Proof of Concept
1. Obtain a valid `ReceivedOutput` `o` for key `K` (or forge one via `ReceivedOutput::read` with an arbitrary claimed `output`/`outpoint`).
2. Call `SignableTransaction::new(vec![o.clone(), o], &[(addr, payment)], None, None, fee)` where `o.value() < payment + fee <= 2 * o.value()`.
3. The `NotEnoughFunds` check passes because `input_sat` counts `o` twice; construction and `multisig` signing succeed since `p2tr_script_buf(offset.group_key())` matches the duplicated prevout's script.
4. The resulting signed `Transaction` contains two `TxIn`s with identical `previous_output` and is rejected by the Bitcoin network — payments never execute despite the signature.
