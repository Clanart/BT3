### Title
Stale line-selection indices are silently reapplied to a freshly re-fetched diff during commit, allowing corrupted/mismatched content to be staged and committed - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
The Sherlock report's broken invariant is: a numeric state (`initialMarginInUsdFromBalance`) is mutated based on a *stale* equality check instead of being re-validated against the *current* underlying state, letting a user's accounting drift from reality. The structural analog in GitHub Desktop is a **stale-index reuse** bug in the partial-commit ("stage selected lines") pipeline: the app reviews a diff, records the user's line selection as *positional indices* into that diff, then re-fetches a brand-new diff at commit time and blindly re-applies those same positional indices to it — with zero content/context validation — when generating the patch that gets applied to the git index.

### Finding Description
When a user reviews a file's diff and selects/deselects individual lines, the selection is stored as a `DiffSelection` keyed by absolute line index (`isSelected(absoluteIndex)`), derived from the diff that was rendered at that moment via `getWorkingDirectoryDiff` [1](#0-0) .

Later, `updateChangesWorkingDirectoryDiff` re-fetches the diff (e.g., after any working-directory refresh) and reconciles the *previous* selection against the *new* diff purely by recomputing which line indices are "selectable" — not by matching line content: [2](#0-1) 

When the user commits, `_commitIncludedChanges` passes the currently-selected files (with their index-based selection state) straight into `createCommit` → `stageFiles` → `applyPatchToIndex` [3](#0-2) [4](#0-3) .

Critically, `applyPatchToIndex` does **not** reuse the diff the user actually looked at — it fetches yet another fresh diff of the working directory at staging time: [5](#0-4) 

That freshly-fetched diff is then fed into `formatPatch`, which walks the new diff's hunks and decides what to include based solely on `file.selection.isSelected(absoluteIndex)` — i.e., the *old* positional indices are reused against the *new* hunk/line layout: [6](#0-5) 

The resulting patch is applied with `git apply --cached --unidiff-zero`, which uses zero lines of context, so git performs no sanity check that the hunk actually matches the surrounding content before writing it into the index: [7](#0-6) 

If the working-tree file's content changes between the diff the user reviewed/selected lines on and the diff re-fetched at staging time (line count shifts, insertions, deletions elsewhere in the file), the reused indices will select the wrong lines in the new hunk layout. Because `--unidiff-zero` skips context verification, git will not reject the mismatch — it silently stages whatever text sits at those positions in the new diff. This is exactly the "guard exists but is checked against the wrong/stale value" pattern from the source report (`initialMarginInUsd == initialMarginInUsdFromBalance` checked without accounting for the direction of `amount`): here, the guard is "diff still has the same file ID and file count" (`updateChangesWorkingDirectoryDiff`'s `arrayEquals` check), which says nothing about *content* staying the same, and `applyPatchToIndex` performs no re-validation at all before reusing the selection.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." An attacker who controls content that lands in a user's working tree between diff-render time and commit time (e.g., a cloned/fetched malicious repository containing a symlink that resolves outside the repo to attacker-writable/shared storage, a submodule checkout that mutates a tracked file path, or any concurrent filesystem write triggered by opening the attacker's repository) can cause Desktop to commit lines the user never selected or reviewed, or omit lines the user did select, without any error or warning surfaced in the UI — because `git apply --unidiff-zero` succeeds regardless of context mismatch. This can inject attacker-controlled content into a legitimate commit/push, or silently drop safety-relevant changes the user believed they were committing.

### Likelihood Explanation
The precondition — working-tree content changing between the diff render and the commit-time patch generation — is a normal race window in Desktop's async architecture (diff fetch, selection reconciliation, and staging are all separate async round-trips through `git`). No user error or unnatural steps are required beyond normal usage (view diff → click commit), and the attacker only needs to control repository content (symlink targets, submodule contents, or any file the working tree references) that can change during that window — squarely within the stated valid-impact scope ("attacker controls a cloned/fetched repository"). I was not able to fully verify a concrete, guaranteed trigger for the file mutation within this window using only static analysis (this needs dynamic reproduction, e.g., an automated file-watcher/symlink race harness), which is the main uncertainty in this finding.

### Recommendation
- Have `applyPatchToIndex` reuse the exact diff object the user selected against (already held in `IChangesState.selection.diff`) instead of re-fetching a new diff at staging time, or
- Re-validate that the diff used for staging is byte-identical/hash-identical to the diff the selection was computed against before generating the patch, aborting (and forcing a refresh + re-selection) if it differs, and
- Avoid `--unidiff-zero` (or additionally pass `--recount`/context-bearing hunks) so `git apply` can reject patches that no longer match the surrounding file content instead of silently applying them positionally.

### Proof of Concept
Conceptual reproduction (not fully verified end-to-end in this pass):
1. Attacker delivers a repository containing a working-tree file `secret.txt` that is a symlink to a path shared with another process the attacker also controls (or that a submodule/build step rewrites).
2. Victim opens `secret.txt` diff in Desktop, selects specific lines to include in the commit (`DiffSelection` recorded by index against the diff at time T0).
3. Before the victim clicks "Commit," the attacker-controlled process rewrites the target content underneath the symlink, shifting line counts.
4. Victim clicks commit. `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` re-fetches the diff at time T1 (`getWorkingDirectoryDiff`, `app/src/lib/git/apply.ts:60`) and applies the T0 selection indices via `formatPatch` (`app/src/lib/patch-formatter.ts:143-171`) using `git apply --cached --unidiff-zero` (`app/src/lib/git/apply.ts:52-58`).
5. Because there is no context validation, the patch is applied against the wrong lines of the new content, and the commit silently contains attacker-influenced text that the victim never reviewed or explicitly selected.
