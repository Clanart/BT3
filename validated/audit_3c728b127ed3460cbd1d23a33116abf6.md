## Finding

I found a solid GitHub-Desktop analog of the same "decision made against one state, execution performed against a different, attacker-influenced state" bug class as the Sherlock `RFPSimpleStrategy` report. In that report `proposalBid` is read by the user at registration time but re-read at `_allocate()`/`_distribute()` time without confirming it hasn't changed. In Desktop, the equivalent broken invariant is in the **partial-commit (line-selection) staging path**.

### Title
Line-selection commit staging re-reads the working-directory diff without validating it against the diff the user reviewed, letting attacker-controlled file changes get silently committed - (`app/src/lib/git/apply.ts`)

### Summary
When a user stages only some lines/hunks of a file ("partial commit"), Desktop stores the *position-based* line selection (`DiffSelection`, absolute line indices) against the diff that was rendered in the Changes view. At actual commit time, `applyPatchToIndex` independently re-fetches the working-directory diff from disk and mechanically re-applies the old, position-based selection to this brand-new diff — with no check that the diff is still the one the user reviewed.

### Finding Description
The staging pipeline is:

1. User reviews a diff in the Changes tab (fetched via `getWorkingDirectoryDiff`) and selects specific lines to include, recorded as an absolute-index `DiffSelection` on the `WorkingDirectoryFileChange`. [1](#0-0) 
2. `_commitIncludedChanges` takes the currently cached `workingDirectory.files` (with their stored `selection`) and calls `createCommit`. [2](#0-1) 
3. `createCommit` clears the index and calls `stageFiles`, which for any partially-selected file calls `applyPatchToIndex`. [3](#0-2) [4](#0-3) 
4. `applyPatchToIndex` **independently re-fetches** the diff (`getWorkingDirectoryDiff`) and builds a patch via `formatPatch`, which applies `file.selection.isSelected(absoluteIndex)` to the *newly fetched* hunks: [5](#0-4) [6](#0-5) 

The only place Desktop reconciles a changed on-disk diff with an existing selection is `updateChangesWorkingDirectoryDiff`, which recomputes `selectableLines` and drops selections on lines that "no longer exist" — but this reconciliation only runs opportunistically when a background file-watcher-triggered refresh happens to fire, and it operates on the app's cached diff state, not on the diff that `applyPatchToIndex` will fetch fresh at the moment `git apply --cached` actually runs: [7](#0-6) 

There is no step anywhere in the commit path that re-diffs and compares the file content that was staged against the file content that was displayed/approved for staging. `formatPatch`'s comment even documents the assumption that a stale/invalid selection is "not supported to use this method as a general purpose diff formatter" but nothing enforces that assumption is true at commit time. [8](#0-7) 

### Impact Explanation
If the tracked file's content changes on disk between (a) the last diff the user reviewed/selected lines against and (b) the moment `createCommit` → `applyPatchToIndex` executes, the absolute line indices in the stale `DiffSelection` will be silently reapplied to the new hunk layout. This can cause:
- Attacker-injected lines (inserted above/around the reviewed hunk, shifting line numbers) to be picked up as "selected" and committed even though the user never saw or approved them.
- Or conversely, lines the user intended to include being silently dropped.

Because Desktop then offers to push the resulting commit, this is a direct "silent corruption of what the user commits or pushes" — the malicious content ends up in the user's commit and can propagate to a shared remote under the victim's identity/authorship.

### Likelihood Explanation
This requires the attacker to control code that runs in the context of the victim's clone of a malicious repository and writes to a tracked file during the (short but non-zero) window between diff review/selection and clicking "Commit." A realistic vector matching the task's "attacker controls a cloned/fetched repository" criterion: a malicious repo ships a normal onboarding step (e.g. an npm `postinstall`/dev-watch script, common in JS repos) that spawns a background process which periodically rewrites a tracked file. Running `npm install`/`npm start` on a freshly cloned repo is an ordinary, expected user action — not "unnatural" or requiring local/admin access, malware already present, or leaked credentials. The corruption window is small but the background process can retry indefinitely until it lands inside the race window (e.g., right before `git apply --cached` executes), and Desktop's per-refresh selectable-line reconciliation is a best-effort, timing-dependent mitigation, not a guarantee enforced at staging time.

### Recommendation
Before applying a partial-commit patch in `applyPatchToIndex`, re-diff the file and compare it (e.g., by hashing the hunk content or the full diff text) against the diff the `DiffSelection` was computed from. If they differ, abort staging that file and surface an error/refresh to the user instead of silently reapplying stale, position-based selection indices to new content. This closes the same class of gap the Sherlock finding highlighted: never let a stale approved value be blindly reused against updated state without revalidation.

### Proof of Concept
1. Clone a malicious repository in GitHub Desktop. Its `package.json` `postinstall` script starts a detached background process that watches `src/target.js` and, once per second, checks whether it currently has uncommitted local edits and, if so, inserts an extra line near the top of the file (shifting all following line numbers).
2. Victim runs `npm install` as part of normal setup (natural workflow), starting the background watcher.
3. Victim edits `src/target.js`, opens the Changes tab, and selects only specific lines/hunks to include in the commit (partial commit), leaving other lines unstaged.
4. Between the victim reviewing/selecting lines and clicking "Commit changes," the background watcher fires and inserts its extra line, shifting line numbers in the file.
5. `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (now reflecting the shifted content) and reapplies the victim's old absolute-index selection (`app/src/lib/git/apply.ts` lines 60-81, `app/src/lib/patch-formatter.ts` lines 143-171), silently including the attacker's injected line (or an unintended combination of lines) in the resulting commit without any warning, which the victim may then push.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
