Confirmed: `CLARITY_NAME_REGEX_STRING` allows `^[-+=/*]$` as a standalone valid Clarity name [1](#0-0) , meaning `*` is a **legal, definable** fungible/non-fungible token (or trait/function) name — it is not reserved.

### Title
Wildcard Asset-Name Collision Lets a Malicious Contract Bypass `restrict-assets?`/`as-contract?` Allowances (Authorization Bypass Through User-Controlled Key) - (File: clarity/src/vm/functions/post_conditions.rs)

### Summary
`check_allowances` in the new `restrict-assets?` / `as-contract?` machinery treats any `AssetIdentifier` whose `asset_name` equals the literal string `"*"` as a wildcard that authorizes movement of **every** fungible/non-fungible asset under that contract [2](#0-1) [3](#0-2) . Because `"*"` is also a syntactically valid `ClarityName` (per `CLARITY_NAME_REGEX_STRING`, `^[-+=/*]$` is explicitly permitted) [1](#0-0) , a contract can define/mint a *real* fungible or non-fungible token literally named `*` via `ft-transfer?`/`nft-transfer?`, and any allowance the outer code wrote for that literal token collides with the wildcard-matching logic, and vice versa: an allowance the user intended to scope narrowly (`with-ft .token "*" amount`, meaning "the actual token named `*`") is instead interpreted by `check_allowances` as "any FT in `.token`," silently widening the grant.

### Finding Description
`eval_allowance` lets a Clarity author declare `(with-ft contract-principal asset-name amount)` where `asset-name` is any string that parses as a `ClarityName` — including `"*"` [4](#0-3) . The resulting `Allowance::Ft` is keyed into a `HashMap<AssetIdentifier, Vec<(usize,u128)>>` by the literal `AssetIdentifier{contract_identifier, asset_name}` [5](#0-4) .

When actually validating asset movement, `check_allowances` does two lookups for every FT that moved: an exact match, and a second lookup that manufactures `AssetIdentifier{contract_identifier: asset.contract_identifier.clone(), asset_name: ClarityName::from_literal("*")}` and treats a hit as blanket approval for *that* asset regardless of amount [6](#0-5) . The identical pattern exists for NFTs [7](#0-6) .

Because the code never distinguishes "the developer wrote the wildcard sentinel string" from "the developer is referring to a token whose real name happens to be `*`", these two semantics are conflated. A contract that defines/controls a token named `*` (a name explicitly permitted by the ClarityName grammar) can exploit this in either direction:
- If an `as-contract?`/`restrict-assets?` caller writes `(with-ft 'SP...my-token amount)` intending to scope the allowance to `my-token` only, that does **not** create a collision by itself. But if the *contract itself* (the callee, running inside the protected scope) is malicious and can mint/transfer a token that it names `*` in the same contract namespace referenced by an allowance the caller wrote as `(with-ft 'SP...contract "*" N)` — intending to name an actual asset literally called `*` — the check silently authorizes moving **any** other FT/NFT in that contract past the amount `N`, because the lookup path treats `"*"` as "all assets," not "the asset named asterisk."
- Conversely, a legitimate token issuer who names a real token `*` cannot be protected by a precise, amount-bounded allowance at all: any `with-ft`/`with-nft` targeting that literal token is unconditionally read by `check_allowances` as full unrestricted approval for the whole contract's asset surface, defeating the very post-condition/allowance amount the caller specified in `evaluate_body_with_allowance_check` [8](#0-7) .

This breaks the intended equality "assets moved ≤ amounts explicitly allowed by the caller of `restrict-assets?`/`as-contract?`" — the core invariant `check_allowances` exists to enforce — because a token literally named `*` makes the amount-bound (`if *amount_moved > allowance`) on line 621-624 unreachable for other assets in the same contract; the merge step grants full approval instead of amount-checked approval [9](#0-8) .

### Impact Explanation
This falls under "an asset moving past its post-conditions" (High/Critical per the scope's asset-movement-vs-allowance category): a caller of `as-contract?`/`restrict-assets?` who scopes an allowance to a specific fungible/non-fungible amount can have that scope silently widened to unlimited, for any asset in the targeted contract, if that contract defines or is later upgraded to define an asset literally named `*`. Since Clarity contracts are user-deployable and `*` is a legal `ClarityName`, an attacker fully controls this collision by naming a token `*` in a contract that a victim script protects via `as-contract?`/`restrict-assets?`.

### Likelihood Explanation
Requires the victim to use the new `as-contract?`/`restrict-assets?` allowance primitives (Clarity 4/5+, epoch-gated) against a contract that the attacker authored or can influence the naming of tokens in, and to write an allowance whose asset name happens to collide with the wildcard sentinel, or for the attacker-controlled contract to define a token named `*` under a contract the caller already grants a wildcard-style allowance to. This is a real, deterministic collision, not a probabilistic one — any contract can trivially deploy a fungible/non-fungible token named `*`, since `guarded_string!`/`CLARITY_NAME_REGEX` accepts it [10](#0-9) .

### Recommendation
Reserve `"*"` as an internal-only sentinel that cannot be produced by `ClarityName::try_from` when used as an on-chain asset name for `define-fungible-token`/`define-non-fungible-token`, or — better — represent "wildcard allowance" as a distinct enum variant/flag rather than overloading `AssetIdentifier.asset_name == "*"`, so a real asset literally named `*` can never be conflated with the wildcard-allowance lookup key in `check_allowances`.

### Proof of Concept
1. Attacker deploys `evil.clar` defining `(define-fungible-token * u1000000)` (legal per `CLARITY_NAME_REGEX_STRING`) alongside a normal token `(define-fungible-token payout u1000000)`.
2. A victim contract calls `(as-contract? ((with-ft 'ATTACKER.evil "*" u10)) (contract-call? 'ATTACKER.evil transfer-large-amount-of-payout ...))`, intending to only ever authorize moving up to 10 units of the token actually named `*`.
3. Inside `check_allowances`, the FT-movement check for `payout` looks up the exact `AssetIdentifier{evil, payout}` (no match), then the wildcard key `AssetIdentifier{evil, "*"}` (match, because the caller's allowance used the literal name `*`), merges it in unconditionally, and approves the `payout` transfer with no cap enforced by amount `u10` [11](#0-10) .
4. Result: the victim's amount-scoped allowance for a token named `*` is reinterpreted as an unrestricted allowance for every FT in `evil.clar`, letting `payout` move without being bounded — violating the caller's intended post-condition/allowance equality.

fn evaluate_body_with_allowance_check(
    asset_owner: &PrincipalData,
    allowances: Vec<Allowance>,
    body_exprs: &[SymbolicExpression],
    invoke_ctx: &InvocationContext,
    exec_state: &mut ExecutionState,
    context: &LocalContext,
) -> Result<Value, VmExecutionError> {
    let epoch = *exec_state.epoch();
    exec_state.global_context.begin();

    // Evaluate the body expressions inside a closure so `?` only exits the closure
    let eval_result: Result<Option<Value>, VmExecutionError> =
        (|| -> Result<Option<Value>, VmExecutionError> {
            let mut last_result = None;
            for expr in body_exprs {
                let result =
                    eval(expr, exec_state, invoke_ctx, context)?.clone_with_cost(exec_state)?;
                last_result.replace(result);
            }
            Ok(last_result)
        })();

    // A block-rejecting error raised inside the body must abort the transaction.
    if matches!(&eval_result, Err(err) if err.rejectable()) {
        exec_state.global_context.roll_back()?;
        return Err(eval_result.unwrap_err());
    }

    let asset_maps = exec_state.global_context.get_readonly_asset_map()?;

    // If the allowances are violated:
    // - Rollback the context
    // - Return an error with the index of the violated allowance
    match check_allowances(asset_owner, allowances, asset_maps, epoch) {
        Ok(None) => {}
        Ok(Some(violation_index)) => {
            exec_state.global_context.roll_back()?;
            return Ok(Value::error(Value::UInt(violation_index))?);
        }
        Err(e) => {
            exec_state.global_context.roll_back()?;
            return Err(e);
        }
    }
