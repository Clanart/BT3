## Binding under test

`w.payout_payer_operator_xonly_pk` (the value read by `get_payout_info_from_move_txid` and used by `is_kickoff_malicious`/`PayoutCheckerTask`) is supposed to equal the xonly pubkey of the operator who **economically funded** withdrawal `i`'s output (i.e., who supplied the fee/change inputs of the confirmed payout transaction). I traced whether this binding actually holds.

**Root cause: the user's payout signature never commits to the OP_RETURN output.** [1](#0-0) 

`create_payout_txhandler` builds a 3-output tx (user output0, anchor output1, OP_RETURN output2) with a single input signed via `SpendPath::KeySpend`, and the *only* signature present is the user's `taproot::Signature` with a caller-supplied `sighash_type`. `Operator::withdraw` enforces that this must be `SinglePlusAnyoneCanPay`: [2](#0-1) 

and the sighash for that type is computed with `Prevouts::One` (single input committed, `SIGHASH_SINGLE` commits only to the output at the same index as the input): [3](#0-2) 

This means the operator's own OP_RETURN output (index 2) and anchor (index 1) are **not covered** by any signature the user or operator is required to keep fixed — the only enforced constraint is that whoever completes the transaction keeps input0 and its matching output (index 0) identical. The operator then funds the tx via `fund_raw_transaction`/`sign_raw_transaction_with_wallet` without explicit `replaceable: false`: [4](#0-3) 

so the resulting mempool transaction is standardly RBF-eligible (Core's wallet default `-walletrbf=true` applies when `replaceable: None`). The tx-sender's own RBF code independently confirms and relies on this malleability: it explicitly documents that `SinglePlusAnyoneCanPay` witnesses can be copied verbatim into a *different* funded transaction with different inputs/outputs, and deliberately places change at the *last* index "so that SinglePlusAnyoneCanPay signatures stay valid": [5](#0-4) [6](#0-5) 

This is the mechanism the attacker exploits: it is not a Clementine bug in the sense of broken code, it is inherent to `SIGHASH_SINGLE|ANYONECANPAY` semantics, and Clementine does nothing to bind the OP_RETURN attribution to the actual funder.

**Attribution path with no re-check against the funder:** [7](#0-6) 

`update_finalized_payouts` reads whichever payout tx actually confirms in the synced block, extracts the OP_RETURN via `get_first_op_return_output`/`parse_op_return_data`, and blindly writes that pubkey (or `NULL` if invalid/missing) as `payout_payer_operator_xonly_pk` — with no check on which inputs funded the transaction. [8](#0-7) 

`get_payout_info_from_move_txid` returns exactly this stored value, and [9](#0-8) 

`is_kickoff_malicious` treats any mismatch (including `None`) between this stored value and `kickoff_data.operator_xonly_pk` as malicious, causing a challenge. Likewise: [10](#0-9) 

`PayoutCheckerTask::run_once` looks up unhandled payouts purely `get_first_unhandled_payout_by_operator_xonly_pk`, keyed on this same stored pubkey, with no verification that the calling operator's wallet actually spent funds in that confirmed transaction.

### Title
Payout attribution is decided by a mutable OP_RETURN not covered by the SinglePlusAnyoneCanPay user signature, letting an unprivileged RBF replacement hijack or nullify operator credit for a withdrawal — (File: `core/src/verifier.rs`)

### Summary
The user's payout signature (`SinglePlusAnyoneCanPay`, enforced in `Operator::withdraw`) only commits to input0 and its matching output0; the OP_RETURN output that Clementine later trusts to identify the funding operator is unsigned and freely replaceable via standard RBF. An unprivileged attacker who observes the operator's broadcast (and its S+AP witness) in the mempool can race a higher-fee replacement that reuses input0/output0 but substitutes their own funding inputs and an arbitrary/garbage OP_RETURN, causing `update_finalized_payouts` to persist a false attribution.

### Finding Description
Binding: `w.payout_payer_operator_xonly_pk == xonly_pk(actual funder of output0's economic cost)`. Trace shows this equality is not enforced by any consensus- or protocol-level check: `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) places OP_RETURN as output index 2, unrelated to the S+AP-signed input/output pair at index 0; `Operator::withdraw` verifies only that the *user's* signature is valid over `Prevouts::One` (`core/src/operator.rs:614-637`, `core/src/builder/transaction/txhandler.rs:222-233`), never re-checking after confirmation which party actually paid the fee/change. `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) reads whichever transaction is finally mined and its OP_RETURN, with no cross-check against the fee-paying inputs. `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) and `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) both key exclusively off this single DB column.

Exploit flow: Operator O broadcasts a genuine low-feerate payout tx (input0 = withdrawal UTXO with O's added funding inputs, output2 = OP_RETURN(O)). Before confirmation, attacker crafts a replacement tx keeping input0 and output0 identical (satisfying the still-valid user S+AP signature), but supplies attacker's own additional inputs for fees/change and either omits the OP_RETURN or sets it to garbage/another registered operator Q's pubkey, then broadcasts at a higher feerate. Because O's tx used default wallet RBF settings (`replaceable: None` in `core/src/operator.rs:664-669`), Bitcoin Core's mempool policy permits this eviction/replacement without any signature from O or the attacker over the OP_RETURN. If the attacker's tx confirms, `update_finalized_payouts` attributes the withdrawal either to nobody (`NULL`) or to Q.

Why guards fail: `Verifier::is_deposit_valid`, `SECP.verify_schnorr` (for the user's sig), and `is_kickoff_malicious`'s blockhash-commitment check all operate on data that is orthogonal to this OP_RETURN swap — they check the *user's* consent to the output and the *committed payout blockhash inside the kickoff witness*, not who funded the confirmed transaction. No database uniqueness constraint or presigned-transaction-graph check ties the OP_RETURN to the actual spending wallet.

### Impact Explanation
Two concrete outcomes, both matching listed Critical categories:
- Garbage/absent OP_RETURN: `payout_payer_operator_xonly_pk` becomes `NULL`; `is_kickoff_malicious` treats every subsequent kickoff by O for that deposit as malicious (`core/src/verifier.rs:1882-1885`), permanently blocking O's reimbursement for a withdrawal O never actually got credit for — "an honest operator permanently unable to be reimbursed."
- OP_RETURN naming a different, actually-registered operator Q for that deposit: Q's own `PayoutCheckerTask` will pick up the payout via `get_first_unhandled_payout_by_operator_xonly_pk` and proceed through `handle_finalized_payout`/kickoff/Reimburse, crediting Q with the full deposit `bridge_amount` for a payout Q never funded — "an operator reimbursed for a payout it never funded."
Repeatable across any withdrawal for which the payout tx is not yet confirmed at the moment the attacker observes the S+AP-signed witness in the mempool; the attack is not tied to a specific deposit/operator pair and could be repeated per withdrawal.

### Likelihood Explanation
Requires only: (1) the operator's payout tx sits unconfirmed in the mempool with default RBF-eligible signaling (the default in `core/src/operator.rs:664-669`), and (2) the attacker has enough BTC to fund a higher-fee, fully-value-covering replacement (they must cover the user's output amount plus fee, which can be substantial — up to near the withdrawal amount). No key compromise, no privileged role, no majority hashrate — only public mempool visibility and BTC to spend, matching the stated unprivileged attacker capabilities. Feasible on any network where mempool transactions are visible before confirmation (regtest, testnet, mainnet).

### Recommendation
Require the operator's committed identity to be cryptographically bound to the confirmed payout transaction rather than read from an unauthenticated OP_RETURN: e.g., have the operator co-sign a commitment (via `SIGHASH_ALL` or a dedicated MuSig2/Schnorr signature covering all outputs including the OP_RETURN) so the attribution cannot be altered without invalidating a signature only the true funding operator can produce, and/or cross-check that the payout tx's non-user inputs are spent from the attributed operator's registered wallet before persisting `payout_payer_operator_xonly_pk`.

### Proof of Concept
`cargo test` (regtest, no mainnet/live Citrea) plan:
1. Set up a deposit and withdrawal as in existing e2e harness (`core/src/test/deposit_and_withdraw_e2e.rs`), obtain operator O's signed/funded payout tx `tx_O` (OP_RETURN = O's xonly pk) via `Operator::withdraw`, broadcast with low feerate, don't mine.
2. Craft `tx_attacker`: same input0 (withdrawal UTXO) and output0 (user payout) as `tx_O`, reuse the identical S+AP witness on input0, add attacker-controlled funding input(s)/change, set OP_RETURN to garbage bytes (or another registered operator Q's xonly pk). Broadcast at higher feerate; confirm it replaces `tx_O` in mempool and is the one mined.
3. Run the block sync / `update_finalized_payouts` path, then assert:
   - `db.get_payout_info_from_move_txid(..., move_txid)` returns operator pubkey `None` (or `Q`), **not** `Some(O)`.
   - Simulate a subsequent kickoff by O and call `is_kickoff_malicious`; assert it returns `true` (O permanently flagged malicious for this deposit), demonstrating O can never be reimbursed even though O was the intended fronting operator.

            }

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

        Ok(())
    }
