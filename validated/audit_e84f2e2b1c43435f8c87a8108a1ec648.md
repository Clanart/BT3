### Title
Scanner reports dust outputs as received which can never be spent, causing withdrawal transactions to fail - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` returns any output paying to a registered script regardless of its value. There is no minimum-value check anywhere on the receive path (`ReceivedOutput::read` and `scan_transaction`/`scan_block` accept any `TxOut`). On the spend path, `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` treats every input as fully available liquidity (`input_sat` is the plain sum of input values), even though each Taproot input costs ~57 vbytes of fees to spend. An attacker can send a dust output (e.g. 546–several thousand sats, below the spend cost) to a Serai address; the scanner reports it as received balance, but spending it consumes more in fees than it contributes — the exact "reported received but not spendable" / "withdrawal fails in an unreachable band" shape as the Morpho report, where a borrow needed to satisfy withdrawal fails in the gap between two thresholds.

### Finding Description
- Receive path: `Scanner::scan_transaction` matches only `output.script_pubkey` against registered scripts and pushes a `ReceivedOutput` for any matching `TxOut`, unconditionally of `output.value` (mod.rs:199-214). `scan_block` additionally includes immature coinbase outputs (mod.rs:221-227).
- Spend path: `SignableTransaction::new` sums `inputs.iter().map(|input| input.output.value.to_sat())` into `input_sat` and only checks `input_sat < payment_sat + needed_fee` (send.rs:175, 215-221). `needed_fee` is computed as `fee_per_vbyte * vbytes` where `vbytes` already accounts for each input's ~57-vbyte signature/witness weight — but the *value contribution* of a dust input is less than the marginal fee the input itself adds to `needed_fee`.
- Net effect: a ReceivedOutput of value `v < fee_per_vbyte * ~57` (≈546 sat at ~10 sat/vbyte, far below the processor's `DUST = 10_000`) is counted as balance while being a net negative when included. The transaction construction then either fails with `NotEnoughFunds` even though nominally `input_sat >= payment_sat + needed_fee` was the intent, or (in the processor at `processor/src/networks/bitcoin.rs:458`) returns `Ok(None)` — a failed withdrawal, directly analogous to the failed "hard withdraw" in the Morpho report.

### Impact Explanation
An unprivileged party can send arbitrary dust payments to any registered Serai address (deposit addresses are public). Each such output is permanently reported as received balance yet is economically unspendable: including it can make a withdrawal plan return `None` (stuck withdrawal) or silently burn value. Repeated dusting accumulates zombie balance that the scheduler counts toward plans that can never be constructed.

### Likelihood Explanation
Sending a dust P2TR output to a known address costs only the dust amount plus the attacker's own fee, and requires no privileges — it is a plain Bitcoin transaction to a public address, matching the "Bitcoin transactions they send" reachability class. Whether the output is later included in a `SignableTransaction` depends on the integrator's coin selection, but nothing in the in-scope code filters it out.

### Recommendation
Filter scanned outputs by a minimum spendable value (e.g. drop outputs where `value < fee_estimate * cost_to_spend_input` or a conservative constant like the processor's `DUST`) in `Scanner::scan_transaction`/`scan_block` or when constructing `ReceivedOutput`, and exclude coinbase outputs below maturity. Alternatively, have `SignableTransaction::new` prune inputs whose value is below their marginal spending cost before summing `input_sat`.

### Proof of Concept
1. Obtain a Serai-controlled P2TR script (any `Scanner`-registered script, e.g. the plain `p2tr_script_buf(key)` deposit address).
2. Broadcast a transaction creating a `TxOut` of, e.g., 600 sats to that script.
3. `Scanner::scan_transaction` returns a `ReceivedOutput` with `value() == 600` — reported received.
4. Construct `SignableTransaction::new(vec![dust], &payments, ...)` at a normal fee rate: the input adds ~57 vbytes to `needed_fee` (hundreds to thousands of sats) while contributing only 600 sats. With only such inputs, or when the marginal cost tips `input_sat < payment_sat + needed_fee`, construction fails with `TransactionError::NotEnoughFunds` (send.rs:215-221) and the processor returns `Ok(None)` — the withdrawal fails even though the recorded balance covered the payment.   pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
