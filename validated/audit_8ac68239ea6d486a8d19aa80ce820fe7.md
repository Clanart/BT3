## Finding: Tron `IntentGatewayV2.sol` escrow ledger not reconciled to actual transferred amount for fee-on-transfer / non-standard ERC20 tokens

### Title
Escrow ledger over-credits nominal `order.inputs[i].amount` instead of actual contract balance increase, causing insolvent/duplicable escrow accounting for fee-on-transfer tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2.sol`'s `placeOrder` direct-transfer path calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits the escrow map `_orders[commitment][token]` with `reducedInputs[i].amount`, a value derived from the *requested* amount, not the tokens the contract actually received. [1](#0-0) 

This is exactly the bug class in the external report: ERC20 `transferFrom` does not guarantee the recipient's balance increases by the requested amount (fee-on-transfer, rebasing, or otherwise non-standard tokens), so the contract must diff `balanceOf` before/after and record only the real delta.

### Finding Description
The mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`) already implements this exact mitigation for the equivalent code path: [2](#0-1) 

```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```

and the foundry test suite explicitly validates this invariant for fee-on-transfer tokens: [3](#0-2) 

The Tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol`), however, kept the pre-fix logic in its non-predispatch branch of `placeOrder`: [1](#0-0) 

It performs `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then does `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is computed purely from the user-specified `order.inputs[i].amount` minus the protocol fee bps — never from an actual `balanceOf` delta: [4](#0-3) 

Because `_orders` is a global per-token escrow ledger shared across all orders (not a segregated vault per order), and the contract's real token balance is not reconciled against what is credited, a fee-on-transfer (or any non-1:1 transferring) token causes the ledger to record more tokens than the contract actually custodies. There is no `balanceOf` check anywhere in this branch, confirmed by the absence of any `balanceOf`/`balBefore` usage in this code path.

### Impact Explanation
Every order placed with such a token inflates `_orders[commitment][token]` beyond the contract's real holdings. When escrow is later released via `withdraw()`: [5](#0-4) 

`withdraw()` transfers `body.tokens[i].amount` (sourced from the inflated `_orders` value) directly to the beneficiary via a raw `.call`, with no check that the contract's actual `balanceOf(address(this))` covers the payout. Since the deficit accumulates across all orders that used the deflationary token, the first beneficiaries to redeem drain the real balance in full while later, equally legitimate beneficiaries face reverting/failed transfers — a straightforward fund-loss condition where honest users who funded escrow lose their deposited principal to whichever counterparty settles first. This is a direct "wrong beneficiary/amount" and fund-loss scenario matching the bounty's impact gate (loss of funds, transaction manipulation via unreconciled accounting).

### Likelihood Explanation
This requires no privileged actor, relayer collusion, or malicious peer — any unprivileged user can trigger it simply by using a standard (non-malicious) fee-on-transfer ERC20 token as an order input via the public `placeOrder` entrypoint on Tron. The mainline EVM contract's own test suite demonstrates fee-on-transfer tokens are a realistic and anticipated input class for this exact contract family, and the Tron variant is the live deployed code path for Tron chains, not test-only code.

### Recommendation
Apply the same balance-diff reconciliation used in the mainline `evm/src/apps/IntentGatewayV2.sol` to the Tron `placeOrder` non-predispatch branch: snapshot `IERC20(token).balanceOf(address(this))` before `safeTransferFrom`, and credit `_orders[commitment][token]` with the post-transfer balance delta rather than `reducedInputs[i].amount`. The predispatch branch already computes a `dust`/`balance` check pattern that could be adapted similarly to guarantee escrow bookkeeping never exceeds actual custody.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2.sol`, admin sets `protocolFeeBps = 0` for simplicity.
2. Deploy a 1% fee-on-transfer ERC20 token (as in `FeeOnTransferToken` from the foundry test suite) and mint balances to two users, Alice and Bob.
3. Alice calls `placeOrder` with `order.inputs[0].amount = 1000e18` of the FOT token. Contract actually receives `990e18` (1% fee burned/retained), but `_orders[commitmentA][token]` is credited `1000e18` (no fee-on-transfer test in this fork, so `reducedInputs == order.inputs`).
4. Bob places a similar order with `amount = 1000e18`; contract now holds `1980e18` total but `_orders` records `2000e18` combined across both commitments.
5. Once both orders resolve to `withdraw()` (e.g., via same-chain refund/cancel or fill+redeem path), the first withdrawal pays out the full `1000e18` recorded amount, leaving only `980e18` actual balance for the second beneficiary's recorded `1000e18` entitlement — the second `withdraw()` either reverts (locked funds) or, if multiple tokens are pooled with sufficient balance from other orders, silently pays out from other users' escrowed principal (fund loss/misappropriation).
