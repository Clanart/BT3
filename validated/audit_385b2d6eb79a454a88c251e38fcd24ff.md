### Title
Scanner accepts arbitrarily-small (dust) deposits as spendable received outputs, with no minimum-amount bound — (`networks/bitcoin/src/wallet/mod.rs`)

### Summary
The external report describes `amount0Min`/`amount1Min` hard-coded to zero, so a transaction accepts any output value regardless of how unfavorable it is. The Serai analog lives in `Scanner::scan_transaction`: incoming outputs are matched purely on `script_pubkey`, and **any** `value` — including 1 satoshi — is accepted as a `ReceivedOutput` and reported to the processor as funds received. Below the dust threshold (546 sat in `send.rs`, 10,000 sat in the processor's `Network::DUST`), the credited output costs more in fees to spend than it is worth, and below 546 sat it cannot even be relayed when spent alone. The receive-side "minimum amount" is effectively zero.

### Finding Description
`Scanner::scan_transaction` iterates all outputs and pushes a `ReceivedOutput` whenever `self.scripts.get(&output.script_pubkey)` matches, with no check on `output.value` [1](#0-0) . `ReceivedOutput` likewise stores whatever `TxOut` it is given; `value()` just returns `to_sat()` [2](#0-1) .

The send path is strictly amount-aware, proving the missing bound is asymmetric:

- `DUST = 546` is defined and `SignableTransaction::new` rejects payments below it (`DustPayment`) and refuses to create a change output under it [3](#0-2) [4](#0-3) [5](#0-4) .
- The processor's `get_outputs` calls `scanner.scan_transaction(tx)` directly and wraps every match into an `Output` with no amount filter [6](#0-5) , even though the network declares `DUST = 10_000` precisely because outputs must "be spendable under a 5000 sat/kilo-vbyte fee rate" [7](#0-6) .

So the only minimum-amount enforcement is on the outbound path; inbound crediting has `amountMin = 0`.

### Impact Explanation
Any external party can send a dust output (e.g., 1–545 sat, or any value under the 10,000-sat processor `DUST`) to a Serai branch/external address. `scan_transaction` reports it as a `ReceivedOutput`; `get_outputs` forwards it as received balance. The protocol then either:

- credits value that is economically unspendable — spending it requires paying more in fees than its value, and sub-546-sat outputs cannot be spent alone under standard relay policy (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` triggers `TooLowFee` [8](#0-7) ), so the "received" funds can never be recovered; or
- aggregates the dust input into a real transaction, where it consumes `input_sat` capacity and weight while contributing less than the marginal fee for its own inclusion, silently burning other deposited funds as excess fee.

This is exactly the accepted-impact category: funds reported received that are not spendable. A malicious depositor can also use dust outputs at scale to pollute the input set, inflating transaction weight/fees paid by the protocol.

### Likelihood Explanation
Reachable by any unprivileged party: the deposit addresses (branch/external/forward P2TR script_pubkeys) are public, and crafting a dust-valued output requires nothing beyond a normal Bitcoin transaction. No validator collusion, no malformed encodings — just a minimum-amount check that was never applied on the receive path. Real-world dust spam and accidental sub-dust deposits are common, so both adversarial and incidental triggering are plausible.

### Recommendation
Apply a minimum-value bound when accepting outputs, mirroring the outbound logic:

- In `Scanner::scan_transaction` (or in `Bitcoin::get_outputs`), skip outputs with `output.value.to_sat() < DUST` so sub-dust outputs are never reported as received.
- Alternatively, keep scanning them but classify/route them separately so they are never credited to a depositor's balance and never selected as inputs without a cost model proving `value > marginal_fee` for their inclusion.
- Document the bound so deposits below it are understood to be donations to miners (burnt), consistent with the existing `DustPayment`/change handling in `SignableTransaction::new`.

### Proof of Concept
1. Compute Serai's external address for the active group key: `Address::new(p2tr_script_buf(key)?)` (same construction as `external_address`/`branch_address` [9](#0-8) ).
2. Broadcast a Bitcoin transaction paying `TxOut { value: Amount::from_sat(100), script_pubkey: <that address> }` — a valid, non-dust *transaction* containing a dust output.
3. `scanner.scan_transaction(&tx)` returns `ReceivedOutput { offset: ZERO, output: <100-sat TxOut>, .. }` because only `script_pubkey` is compared [10](#0-9) .
4. `Bitcoin::get_outputs` emits it as a credited `Output` [6](#0-5) ; the depositor is credited 100 sat.
5. Spending it: `SignableTransaction::new(vec![output], &payments, ..)` computes `needed_fee ≥ DEFAULT_MIN_RELAY_TX_FEE * vbytes/1000 > 100` sat, so either `NotEnoughFunds`/net-negative, or it is bundled with other inputs where it contributes less than its ~57-vbyte marginal fee — the credited balance is irrecoverable either way.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
