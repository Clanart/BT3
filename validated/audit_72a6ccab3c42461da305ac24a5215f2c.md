## Analysis Result

### Title
Discarding a single diff line uses an expanded-diff line index against the original (unexpanded) diff, silently discarding the wrong line - (File: app/src/ui/diff/side-by-side-diff.tsx)

### Summary
The reported smart-contract bug is a "unit mismatch across a boundary": a value computed in one numeric space (WAD) is later interpreted/consumed as if it were in a different space (token decimals), without any conversion, silently corrupting the amount that ends up being credited/withdrawn. The GitHub Desktop analog of this pattern is `onContextMenuLine` in the side-by-side diff viewer: it computes a line index that is only valid in the *currently rendered* (potentially hunk-expanded) diff, but passes that raw index through to code that interprets it against the *original, unexpanded* diff's indexing space. Just as the WAD/decimal mismatch silently changed the meaning of a numeric quantity, this index-space mismatch silently changes which line of the file gets discarded, corrupting what the user ends up committing.

### Finding Description
`onContextMenuHunk` (the "discard hunk" path) correctly converts from the displayed diff's index space to the original diff's index space before acting: [1](#0-0) 

It calls `findInteractiveOriginalDiffRange`, which explicitly re-maps the range through `getLineInOriginalDiff` to translate an index in `this.state.diff` (which may be an expanded copy) back into the coordinate system of the pristine diff: [2](#0-1) 

However, `onContextMenuLine` (the "discard single line" path) computes the same `range` via `findInteractiveOriginalDiffRange` purely to build the *label text* (`range.type`), but then invokes the discard action with the **raw, un-mapped** `diffLineNumber` instead of `range.from`/`range.to`: [3](#0-2) 

That raw index is then used directly to build a `DiffSelection` and is applied to `this.props.diff` — the original, unexpanded diff — with an explicit comment acknowledging the index-space distinction exists, but doing nothing to correct for it in this path: [4](#0-3) 

The reason this matters: expanding a hunk (`Expand Up`/`Expand Down`/`Expand Whole File`) inserts new `DiffLine`s into `this.state.diff` and shifts the `unifiedDiffStart`/`unifiedDiffEnd` of all subsequent hunks by `numberOfNewDiffLines`, while `this.props.diff` (the original) keeps its original, smaller indices: [5](#0-4) 

Once any hunk has been expanded, a `diffLineNumber` that correctly identifies a row in `this.state.diff` no longer identifies the same row in `this.props.diff`. `DiffSelection.withRangeSelection`/`isSelected` operate purely on these integer indices with no notion of which diff they belong to: [6](#0-5) [7](#0-6) 

So the selection object built in `onDiscardChanges` marks the wrong absolute index as "selected for discard" relative to `this.props.diff`, and that mis-indexed selection is what actually gets turned into the discard patch (via `formatPatchToDiscardChanges`, which walks `this.props.diff`'s hunks using their own `unifiedDiffStart`): [8](#0-7) 

Existing guards do not stop this: `findInteractiveOriginalDiffRange`/`getLineInOriginalDiff` exist specifically to fix this exact class of bug, and are used correctly one function above (`onContextMenuHunk`) but not in `onContextMenuLine`. There is no validation elsewhere that a selection index actually corresponds to the diff it's being applied against.

### Impact Explanation
The consequence is that "Discard Line" on a single line, performed after any hunk expansion, can silently discard a different line than the one the user right-clicked and confirmed — content the user believed they kept can be reverted, and/or content they meant to discard is left in place. Because the app writes this out via `git apply --reverse` (or equivalent) driven by the corrupted `DiffSelection`, the resulting working-directory content — and ultimately what gets staged/committed — no longer matches user intent. This falls squarely under "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories, and requires no elevated privileges, local access, or leaked credentials — only normal interaction with a diff that a remote/cloned repository caused to be displayed with a hunk expansion.

### Likelihood Explanation
Triggering requires: (1) a file whose diff, once opened, has more than one hunk (or a hunk that supports "Expand Up/Down/Whole File" — common for typical partial-context diffs), (2) the user expanding a hunk (a normal, commonly-used feature for reviewing more context), and (3) then right-clicking an individual line beyond/around the expansion boundary and choosing "Discard Line." This is an entirely ordinary code-review workflow in Desktop, not a contrived or unnatural sequence, so the likelihood of accidental triggering by any user working with multi-hunk files is real, though it depends on interactive discard-line usage after expansion rather than being automatically exploitable by a remote party without any local user action.

### Recommendation
In `onContextMenuLine`, use the already-computed `range.from`/`range.to` (mapped into the original diff's index space via `getLineInOriginalDiff`) when invoking `this.onDiscardChanges(...)`, exactly as `onContextMenuHunk` already does, instead of the raw `diffLineNumber`. More generally, consider making `DiffSelection` indices type-safe/tagged to the diff instance they were computed against (e.g., a branded type or an assertion that the diff passed to `onDiscardChanges` matches the diff the index was derived from), so that a future call site cannot silently mix index spaces the way `onContextMenuLine` currently does.

### Proof of Concept
1. Open a repository in Desktop with a text file whose diff has at least two hunks and enough unchanged content between them to allow expansion (default git diff context of 3 lines is enough once "Expand" is available).
2. In the Changes/diff view, click "Expand Up" or "Expand Down" (or "Expand Whole File") on the first hunk — this mutates `this.state.diff` line/hunk indices but leaves `this.props.diff` (passed down from the file's diff-selection state) unchanged, per `expandTextDiffHunk`'s index-shifting logic (`text-diff-expansion.ts` lines 352-387).
3. Right-click a line that is now displayed after the point where indices diverged (i.e., in a hunk whose `unifiedDiffStart` was shifted by the expansion) and choose "Discard Line."
4. `onContextMenuLine` passes the expanded-diff-relative `diffLineNumber` straight to `onDiscardChanges`, which builds a `DiffSelection` and applies it to `this.props.diff` (`side-by-side-diff.tsx` lines 1446-1473, 1590-1607).
5. Because `this.props.diff`'s hunks have different `unifiedDiffStart` values than `this.state.diff`'s hunks for anything after the expansion point, the selected absolute index resolves to a different line in `this.props.diff`. `formatPatchToDiscardChanges` (`patch-formatter.ts` lines 251-335) then generates a reverse-patch for that different line, discarding content other than what the user selected.

/**
 * For the given row in the diff, determine the range of elements that
 * should be displayed as interactive, as a hunk is not granular enough.
 * The values in the returned range are mapped to lines in the original diff,
 * in case the current diff has been partially expanded.
 */
export function findInteractiveOriginalDiffRange(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
): IDiffRange | null {
  const range = findInteractiveDiffRange(hunks, index)

  if (range === null) {
    return null
  }

  const from = getLineInOriginalDiff(hunks, range.from)
  const to = getLineInOriginalDiff(hunks, range.to)

  if (from === null || to === null) {
    return null
  }

  return {
    ...range,
    from,
    to,
  }
}

/**
 * Utility function to get the line number in the original line from a given
 * line number in the current text diff (which might be expanded).
 */
export function getLineInOriginalDiff(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
) {
  const diffLine = diffLineForIndex(hunks, index)
  if (diffLine === null) {
    return null
  }

  return diffLine.originalLineNumber
}

    const computedSelectionType = this.getSelectionType()
    const to = from + length

    // Nothing for us to do here. This state is when all lines are already

    if (typeMatchesSelection(computedSelectionType, selected)) {
      return this
    }

    if (computedSelectionType === DiffSelectionType.Partial) {
      const newDivergingLines = new Set<number>(this.divergingLines!)

      if (typeMatchesSelection(this.defaultSelectionType, selected)) {
        for (let i = from; i < to; i++) {
          newDivergingLines.delete(i)
        }
      } else {
        for (let i = from; i < to; i++) {
          // Ensure it's selectable
          if (this.isSelectable(i)) {
            newDivergingLines.add(i)
          }
        }
      }

      return new DiffSelection(
        this.defaultSelectionType,
        newDivergingLines.size === 0 ? null : newDivergingLines,
        this.selectableLines
      )

        }
      }

      return new DiffSelection(
        computedSelectionType,
        newDivergingLines,
        this.selectableLines
      )
    }
