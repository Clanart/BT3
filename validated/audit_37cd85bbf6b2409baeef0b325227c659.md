### Title
Diff-hunk expansion desyncs `DiffSelection` line indices, causing silent inclusion/exclusion of unrelated lines when committing - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
`expandTextDiffHunk` (used when a user expands hidden context in the diff viewer) shifts the absolute line indices (`unifiedDiffStart`/`unifiedDiffEnd`) of every hunk that follows the expanded one, but the `DiffSelection` object that tracks which specific lines the user has (de)selected for commit is never remapped to match the new indices. Because the partial-commit patch generator resolves selection purely by absolute index, an expansion performed after a partial selection has been made can make the app commit/discard a line the user never intended to touch, while silently leaving the line the user actually deselected in the diff.

### Finding Description
`DiffSelection` stores the user's "diverging" line choices as a `Set<number>` keyed by an absolute line index (`hunk.unifiedDiffStart + lineIndex`), and `isSelected(lineIndex)` looks values up directly in that set: [1](#0-0) 

That same absolute index is computed identically in the patch generator that actually produces the git patch used to stage/commit or discard changes: [2](#0-1) 

When the user expands a hunk (a normal, one-click UI action available on any diff with hidden context between hunks), `expandTextDiffHunk` inserts new context lines into the expanded hunk and then re-numbers every *following* hunk by shifting its `unifiedDiffStart`/`unifiedDiffEnd` by `numberOfNewDiffLines`: [3](#0-2) 

The calling code in the diff viewer swaps in this re-indexed diff (`this.setState({ diff: updatedDiff })` / `this.setState({ diff: updatedDiff, ... })`) but never touches or remaps the file's `DiffSelection`: [4](#0-3) [5](#0-4) 

The only place selectable/valid indices get reconciled with a changed diff is `withSelectableLines`, and that is invoked from a completely different code path — when the working-directory diff is reloaded from disk/git status, not when a hunk is expanded in the viewer: [6](#0-5) 

So after expansion, absolute index `N` in the old diff and absolute index `N` in the new (post-expansion) diff refer to different physical lines, but `divergingLines` still contains the old value of `N`. This is the exact bug class described in the report: a positional/offset value (`height`/stack slot in the report, `unifiedDiffStart`/absolute line index here) is advanced for one data structure (the hunk array) but not for a dependent one (the selection set) that is indexed the same way, so a read/write that should target one slot silently targets another.

### Impact Explanation
The mismatch directly affects "what the user commits" without any visible indication in the UI: after expanding a hunk, a line that the user had explicitly deselected (e.g., to keep a suspicious or unwanted change out of the commit) can be silently re-selected (included) because the deselection bit now lands on a shifted, unrelated line — and vice versa, a line the user wanted to include can be silently dropped. Since `formatPatch`/`formatPatchToDiscardChanges` use these indices verbatim to build the exact patch applied to the git index/working tree, the corruption flows straight into what gets staged, committed, or discarded, with no re-validation. This matches the "silent corruption of what the user commits or pushes" impact category: content in the repository (number/placement of hunks and the gaps between them, which are attacker-influenced when the user is reviewing a fetched/cloned repository or a hostile PR diff) determines whether/where an "Expand" affordance is offered, and expanding it after a partial review can cause a user to unknowingly commit a change they had rejected.

### Likelihood Explanation
This requires an ordinary, expected user workflow: partially select/deselect lines in a diff, then expand additional context (both are core, commonly used features in the diff viewer, especially for large diffs where reviewers want more context before deciding what to stage). No special privileges, local access, or unnatural steps are needed. The only "attacker" precondition is a repository/diff shape (hunks separated by expandable context) that is entirely ordinary and not something existing guards check for — there is no code anywhere that re-validates or remaps `DiffSelection` state after `expandTextDiffHunk`/`expandWholeTextDiff` run, so the desync is unconditional whenever expansion happens after any partial selection exists.

### Recommendation
When a hunk expansion (`expandTextDiffHunk`, `expandWholeTextDiff`) changes any hunk's `unifiedDiffStart`/`unifiedDiffEnd`, the associated `DiffSelection` must be re-derived/remapped in lock-step: recompute `divergingLines` by translating each existing selected/deselected absolute index by the same `numberOfNewDiffLines` offset applied to the hunk it belongs to (mirroring the shift performed for `followingHunks`), and recompute `selectableLines` from the new hunk layout the same way `updateChangedFiles`/`withSelectableLines` already does for the disk-reload path. This remap should happen atomically together with `setState({ diff: updatedDiff })` in `side-by-side-diff.tsx`, and ideally be covered by a test that partially deselects a line after a hunk that gets expanded, then asserts `formatPatch`/`formatPatchToDiscardChanges` still reflect the user's original per-line choice.

### Proof of Concept
1. Open a file with a diff containing at least two hunks separated by a gap large enough to offer "Expand" (default step is 20 lines): [7](#0-6) .
2. In the second hunk, deselect one added line (e.g. line at absolute index `N`); this stores `N` in `DiffSelection.divergingLines`.
3. Click "Expand" on the first hunk (or "Expand whole file"). `expandTextDiffHunk` inserts new context lines and shifts the second hunk's `unifiedDiffStart`/`unifiedDiffEnd` by `numberOfNewDiffLines`, so the line the user deselected is now at absolute index `N + numberOfNewDiffLines`, while index `N` now refers to a different (newly-inserted or shifted) line.
4. Commit the file. `formatPatch` calls `file.selection.isSelected(absoluteIndex)` with the *new* diff's indices: `absoluteIndex = hunk.unifiedDiffStart + lineIndex` [2](#0-1) . Since `divergingLines` still contains the old value `N`, the originally-deselected line (now at `N + numberOfNewDiffLines`) is treated as selected and gets committed, while whatever line now sits at index `N` is unintentionally excluded — with no warning shown to the user.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
