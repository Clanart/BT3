## Analysis

The auction bug's broken invariant is: a party explicitly given a trust boundary ("bidders are protected until reveal / seller must respect the reserve price") can silently bypass the one guard meant to enforce that boundary (`bid()`'s same-address check), because the guard is trivially defeated (using another address) while the underlying protection it was supposed to provide is not actually restored. The Desktop analog with an equivalent structure — a security guard that git itself uses to stop exactly this class of attack, deliberately disabled by application code — exists in the clone implementation.

### Title
GitHub Desktop disables Git's built-in recursive-clone hook-injection protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), re-enabling CVE-2024-32002-style arbitrary code execution when cloning malicious repositories - (File: `app/src/lib/git/clone.ts`)

### Summary
When GitHub Desktop clones any repository — including via the "Clone repository" dialog, CLI `github clone`, and the `open-repository-from-url`/`openrepo` deep-link handler — it invokes `git clone --recursive` and unconditionally sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE=false`. This variable controls Git's own safety check (added upstream to remediate CVE-2024-32002/GHSA-xx: "arbitrary code execution via crafted repository with symlinked/embedded `.git` in a submodule during recursive clone") that normally aborts a recursive clone when it detects a submodule attempting to write files into the parent repository's `.git` directory (e.g. planting a hook). By explicitly forcing this protection off, Desktop restores the exploitable condition that upstream Git deliberately closed. [1](#0-0) 

### Finding Description
`clone()` builds the execution environment via `envForRemoteOperation(url)` and then overrides it with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` before running `git -c init.defaultBranch=... clone --recursive -- <url> <path>`. [2](#0-1) 

`--recursive` means every submodule referenced by the cloned repository is checked out automatically, without further user confirmation, immediately after the top-level clone completes. Git's fix for the "embedded/symlinked `.git` in submodule" class of vulnerabilities specifically guards this exact recursive-checkout step: it detects a submodule worktree that tries to place an actual `.git` directory (rather than a `gitdir:` pointer file) — or a symlink that resolves outside the intended submodule location — which an attacker can use to have Git write/overwrite files (including hook scripts) into the *superproject's* `.git/hooks` directory during the recursive clone/checkout of the malicious submodule. That write, followed by an automatic Git operation that triggers hooks (`post-checkout`, `pre-commit`, etc. — including operations Desktop itself now runs, see `app/src/lib/hooks/hooks-proxy.ts`/`with-hooks-env.ts`), results in attacker-controlled code execution the moment the user opens or performs any git operation on the freshly cloned repository. [3](#0-2) [4](#0-3) 

By hard-coding `GIT_CLONE_PROTECTION_ACTIVE=false`, Desktop bypasses this guard for every clone it performs, regardless of whether the source is a URL typed by the user, a "Clone repository" GitHub API-listed repo, a `github://` deep link, or the CLI `github clone` command — all of which can point to an attacker-controlled/attacker-forked repository or third-party remote. This is analogous to the auction report's `bid()` same-address check: a control that exists specifically to prevent one actor's tampering is present in the underlying system but is neutralized by the wrapping application, restoring the exact attack the guard was designed to stop.

### Impact Explanation
This is a code-execution primitive triggerable purely by getting a victim to clone a repository they do not control (a public fork, a repo shared via a `x-github-client://openRepo/...` deep link, or a URL pasted into the Clone dialog). No local access, prior malware, or leaked credentials are required — only that the victim clones a URL an attacker chose or authored. Successful exploitation can write arbitrary files into the local `.git/hooks` directory of the clone, executing attacker code on the victim's machine outside of any file the user knowingly interacted with, satisfying the "code execution / file write outside the repo" impact criteria.

### Likelihood Explanation
Every code path that clones a repository in Desktop passes through this function unconditionally (`clone-repository.tsx`, CLI `clone-url` action, and `openBranchNameFromUrl`/`openOrCloneRepository` triggered from the `open-repository-from-url` deep-link handler), so the disabled protection applies universally, with no opt-out or confirmation dialog exposed to the user. [5](#0-4) [6](#0-5) 

The only requirement is that the attacker's repository contains a submodule crafted to exploit the (now unguarded) write-outside-submodule condition — a well-documented, previously-patched-upstream technique, not a novel discovery, making exploitation low-effort for anyone aware of the original CVE.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts` so Git's built-in recursive-clone protection remains active. If the override exists to work around a compatibility issue with a specific submodule layout, gate it behind an explicit, informed user confirmation (with a clear warning about the risk) rather than disabling it unconditionally for all clones, and ensure the bundled/dugite Git version contains the CVE-2024-32002 fixes so the protection is meaningful.

### Proof of Concept
1. Attacker publishes a public GitHub repository containing a submodule entry whose gitlink/worktree is crafted per the CVE-2024-32002 technique (submodule directory containing a real `.git` directory or a symlink causing the recursive checkout to write into the superproject's `.git/hooks`, e.g., placing a `post-checkout` script).
2. Attacker shares the repository via any of Desktop's clone entry points, e.g., a deep link `x-github-client://openRepo/https://github.com/attacker/evil-repo` or simply the clone URL in the "Clone repository" dialog.
3. Victim clicks the link / pastes the URL in Desktop and clones it. `clone()` runs `git ... clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false`, so Git's guard against the malicious submodule write is disabled and the hook file is planted into `.git/hooks` during the recursive submodule checkout. [1](#0-0) 
4. Any subsequent Git operation performed by Desktop or the user in that repository that invokes the corresponding hook (e.g., `post-checkout`, triggered automatically by Desktop's own checkout/branch operations) executes the attacker's script with the victim's privileges.

  ]
