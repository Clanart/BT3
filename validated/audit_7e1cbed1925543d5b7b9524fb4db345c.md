### Title
Silent escrow-release on false ERC20 `transfer()` return in Tron IntentGatewayV2 `withdraw()` — funds finalized as delivered but never sent - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron build of `IntentGatewayV2` diverges from the canonical EVM implementation by replacing OpenZeppelin's `SafeERC20.safeTransfer` with a raw low-level `.call()` that only checks that the call did not revert, never decoding/validating the ABI-encoded boolean the ERC20 standard requires. This is the exact bug class from the external report (unchecked boolean return of a token operation): a token that returns `false` on failure instead of reverting lets escrow-release bookkeeping finalize as successful while the beneficiary receives nothing.

### Finding Description
In the canonical EVM contracts, token payout uses `SafeERC20.safeTransfer`, which reverts on both call failure and a decoded `false` return value: [1](#0-0) [2](#0-1) 

The Tron variant's `withdraw()` function instead uses a raw `.call` with only a "did the call revert" check: [3](#0-2) [4](#0-3) 

The same unchecked pattern is used for governance-triggered dust sweeps: [5](#0-4) 

`token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` returns `success = true` as long as the target contract does not revert — it says nothing about the ABI-decoded return value. A token whose `transfer()` returns `false` on failure (rather than reverting, as the canonical OpenZeppelin ERC20 does) will make `success == true`, so `if (!success) revert TransferFailed();` never fires, and execution proceeds to finalize the withdrawal: [6](#0-5) 

`_filled[body.commitment] = beneficiary;` is set and `_orders[body.commitment][token] -= amount;` is decremented as if the tokens were delivered, even though they never left the contract. Because `_filled`/`_orders` are the sole idempotency/authorization gates for redemption and refund (`RedeemEscrow`/`RefundEscrow` both funnel into this same `withdraw()`), the commitment cannot be retried, and the tokens are permanently stranded in the gateway's actual balance while the accounting says they were already paid out.

### Impact Explanation
Order `inputs`/`output.assets` tokens are attacker-controlled fields supplied at `placeOrder`/fill time — any ERC20 address can be specified, including a token the attacker deploys and controls. An attacker (playing either the order creator or the solver) can use a token contract that returns `false` instead of reverting under attacker-chosen conditions. When the corresponding escrow is redeemed or refunded through `withdraw()`, the contract will:
1. Mark the order as finalized/filled (`_filled[commitment] = beneficiary`), permanently blocking any retry or alternate resolution.
2. Decrement `_orders[commitment][token]` to zero, so the protocol's own bookkeeping no longer reflects any residual claim on the still-held tokens.
3. Leave the actual ERC20 balance sitting in the gateway contract, now unaccounted for by any commitment — a real fund loss/lock for the intended beneficiary, and a balance that is indistinguishable from "protocol dust" once orphaned, making it reachable by the same unchecked-transfer `SweepDust` path to an arbitrary beneficiary.

This satisfies the bounty's "stealing or loss of funds" and "false state acceptance" categories: the withdrawal accounting falsely records a transfer that never executed.

### Likelihood Explanation
This requires no privileged actor, relayer, or prover compromise — only an unprivileged user supplying a custom ERC20 token address as one of the order's escrowed tokens, a pattern the intents protocol explicitly supports (arbitrary `token` fields in `TokenInfo`). Non-reverting-`false` ERC20 implementations are a well-documented real-world pattern (this is precisely the bug class the cited external report targeted), making the trigger condition realistic rather than hypothetical.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` and the `SweepDust` handler) with `SafeERC20.safeTransfer`, matching the pattern already used correctly in `evm/src/apps/intentsv2/IntentsBase.sol`. `SafeERC20` decodes and enforces the boolean return value (or requires the call to revert), preventing bookkeeping from being finalized when no tokens actually moved.

### Proof of Concept
1. Deploy a malicious ERC20 whose `transfer()` returns `false` (without reverting) whenever `to == someSpecificAddress` (or under any attacker-chosen condition), while `transferFrom` behaves normally so escrow funding via `safeTransferFrom` succeeds.
2. Place an order (`placeOrder`) on the Tron `IntentGatewayV2` using this token as an input; escrow is funded normally (goes through `safeTransferFrom`, which is checked correctly).
3. Trigger the redeem or refund path so `withdraw()` is invoked with `token = <malicious token>` and `beneficiary = <attacker-chosen address that triggers false>`.
4. Observe: `token.call(...)` returns `success = true` (no revert) even though the token's internal accounting never moved the balance; `TransferFailed` is not raised; `_filled[commitment]` is set and `_orders[commitment][token]` is decremented to zero.
5. Confirm `IERC20(token).balanceOf(gateway)` still holds the escrowed amount, while `_orders[commitment][token] == 0` and `_filled[commitment] != address(0)` — the order is permanently finalized with no recorded claim on funds that never left the contract.
