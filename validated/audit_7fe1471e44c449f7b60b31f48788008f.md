### Title
Aggregate Schnorr verifier accepts forged signatures with identity nonces - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::read` accepts attacker-controlled nonce commitments without rejecting the identity point, while `SchnorrAggregate::verify` multiplies those points by aggregation weights without any additional validity check. [1](#0-0) [2](#0-1) 

### Finding Description
An aggregate signature consists of `Rs` and `s`. An attacker can set every `R_i` to the group identity and `s` to zero. Verification then reduces to `0 == 0`, regardless of the supplied public keys, messages, or per-signature challenges, because every queued term is either a scalar multiple of identity or a scalar multiple of the generator by zero. [3](#0-2) 

The deserializer imposes only canonical point/scalar encoding checks and does not reject identity `R_i`; canonical encodings can validly represent the identity point. [1](#0-0) [4](#0-3) 

Other Serai code explicitly recognizes that an identity Schnorr nonce is unsafe and rejects it before accepting a signed transaction, but `SchnorrAggregate::read` lacks the equivalent check. [5](#0-4) 

### Impact Explanation
Any caller that accepts serialized aggregate Schnorr signatures through `SchnorrAggregate::read` and then calls `verify` can be given a forged aggregate signature for arbitrary public keys and challenges. This satisfies the forged-signature condition: the attacker does not know any corresponding private keys and does not need any real signer participation. [1](#0-0) [2](#0-1) 

### Likelihood Explanation
The exploit requires only public signature bytes under the attacker’s control. The attacker chooses the serialized signer count, repeats the canonical encoding of the group identity for every `R`, and appends the canonical encoding of scalar zero. No signature oracle, key access, malformed encoding, race, or malicious signer is required. [1](#0-0) 

### Recommendation
Reject identity nonce commitments in `SchnorrAggregate::read` or at the start of `SchnorrAggregate::verify`. Verification should also reject zero `s` unless a protocol-level reason exists to permit it. At minimum, every decoded `R_i` should be checked with `is_identity()` before being used in the multiexponentiation, matching the defensive check applied to single signed transactions. [6](#0-5) [5](#0-4) 

### Proof of Concept
Conceptually, for `n` expected signers:

```rust
use ciphersuite::{group::GroupEncoding, Ciphersuite};
use schnorr::SchnorrAggregate;

fn forged_aggregate<C: Ciphersuite>(n: usize) -> Vec<u8> {
    let mut bytes = (n as u32).to_le_bytes().to_vec();

    for _ in 0..n {
        bytes.extend(C::G::identity().to_bytes().as_ref());
    }

    bytes.extend(C::F::ZERO.to_repr().as_ref());
    bytes
}
```

Decode the result with `SchnorrAggregate::<C>::read`, then invoke `verify(dst, keys_and_challenges)` for any nonempty `keys_and_challenges` of matching length. Every generated term is identity-scaled or zero-scaled, so `multiexp_vartime` returns the identity and verification succeeds. [6](#0-5) [3](#0-2)
