This confirms the mechanism: `HostParams` (including `fee_token`) is updated in-place via `update_host_params`/`set_host_params`, and the accrued `Fees::<T>` balance is a raw `U256` amount with no record of which fee token it was denominated in when accumulated. `withdraw()` reads the *current* `HostParams::<T>::get(dest_chain)` at withdrawal time and disburses that numeric amount in whatever `token` is currently configured.

### Title
Relayer fee balance denominated in stale fee-token loses value/fails on withdrawal after `update_host_params` changes `fee_token` - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
Accrued relayer fees are stored as a bare `U256` amount with no association to the fee token/decimals that were in effect when the fee was accrued. `pallet-host-executive::update_host_params` can change `fee_token` (and implicitly its decimal scale) for a chain at any time. Any relayer balance accumulated before that change is later withdrawn using the *new* token, so the same numeric amount is paid out in a different asset — either draining more value than owed from `HostManager`/the manager contract, or leaving the relayer's payout undersized/reverting on the destination for insufficient balance of the wrong token. This mirrors the GoldCardsFactory issue: a value (fee/price) is locked in an accounting entry at commit time (fee accrual) but settled later using parameters read at a different time (current `HostParams`), and nothing binds the two together.

### Finding Description
`accumulate_fees` (`modules/pallets/relayer/src/accumulate.rs:134-144`) credits `Fees::<T>::mutate(state_machine, beneficiary, |inner| *inner += total_fee)` — a plain balance increment with no token tag. [1](#0-0) 

When the relayer calls `withdraw()` (`modules/pallets/relayer/src/withdrawal.rs:116-159`), the pallet reads `available_amount = Fees::<T>::get(...)` and, for EVM destinations, fetches the *current* `HostParams::<T>::get(withdrawal_data.dest_chain)` to obtain `params.fee_token`, then builds `WithdrawalParams{ beneficiary_address, amount: available_amount.into(), token: params.fee_token }` and dispatches it. [2](#0-1) 

`update_host_params` (`modules/pallets/host-executive/src/lib.rs:182-228`) lets `HostExecutiveOrigin` update the `EvmHostParam` (which includes `fee_token`) for a state machine at any time, overwriting `HostParams::<T>`. [3](#0-2) 

Between the time fees accrue in one fee token (e.g., 6-decimal USDC) and the time the relayer withdraws, governance can legitimately rotate `fee_token` (e.g., to an 18-decimal stablecoin, as the docs for `BandwidthManager` note is a normal operational event: "the host occasionally swaps fee tokens"). The `Fees` storage has no way to express "this amount is denominated in token X" — it is purely numeric. The destination-side `HostManager`/EVM host contract will transfer `amount` units of whatever `token` address is passed, with no cross-check against what token was actually escrowed for that relayer's accrued fee. This is structurally identical to the original bug: `weave_to_burn` was computed from the *current* `goldPrice`/`goldRefund` at melt/mint time rather than the value locked at commit time, causing under- or over-burn.

### Impact Explanation
- If `fee_token` changes to a token with more decimals (or a materially different unit value) after fees accrued, a relayer's withdrawal request can move disproportionately more value out of the destination-chain fee reserve/`HostManager` than what the relayer actually earned — a fund-loss/over-payment from the protocol's escrowed fee reserve.
- If `fee_token` changes to a token with fewer decimals (or higher unit value), the relayer is paid a fraction of what they earned, and since `Fees::<T>::insert(..., U256::zero())` unconditionally zeroes the balance after dispatch regardless of whether the paid-out amount was correct, the shortfall is permanently and silently lost with no path to reclaim it. [4](#0-3) 
- Either direction is an unauthorized/incorrect transfer of value tied to a stored balance that was never re-denominated when its unit of account changed underneath it — a "wrong amount moved to the rightful beneficiary" condition in scope for the bounty (bridged fee funds must move exactly once and in the correct amount).

### Likelihood Explanation
`update_host_params`/`set_host_params` are legitimate, expected operational calls (the docs explicitly describe fee-token rotation as a normal event, e.g. in the `BandwidthManager` "stale balances of an old fee token" note), so this is not a hypothetical or attacker-crafted admin action — it is a routine governance update that any relayer's already-accrued, unwithdrawn balance is exposed to. Any relayer that delays withdrawal (which the protocol explicitly supports — "relays can withdraw their fees at any time") across a fee-token rotation window realizes the mismatch. No malicious peer, relayer, or prover is required; the only precondition is the ordinary sequence "accrue → governance rotates fee token → withdraw," which is a normal part of the system's documented lifecycle.

### Recommendation
Store the fee token (and/or its decimals, or a normalized USD-equivalent value) alongside the accrued `Fees` balance at accrual time, e.g. change `Fees<T>` to key or tuple-store `(token, amount)` rather than a bare `U256`. On withdrawal, dispatch using the token that was recorded at accrual time, not the pallet's live `HostParams`. If governance rotates `fee_token`, provide an explicit migration/conversion step for outstanding balances (analogous to storing `goldPrice`/`goldRefund` in `GoldOrder` per the original report) rather than allowing withdrawal to silently pick up the current configuration.

### Proof of Concept
1. Relayer delivers messages to `EVM-X`; `accumulate_fees` credits `Fees::<T>[EVM-X][relayer] += total_fee` in units implicitly denominated in `HostParams[EVM-X].fee_token = TokenA` (6 decimals).
2. Before the relayer withdraws, `HostExecutiveOrigin` calls `update_host_params(EVM-X, EvmHostParamUpdate{ fee_token: Some(TokenB) })` where `TokenB` has 18 decimals — a routine, non-malicious governance action.
3. Relayer calls `withdraw()`. `available_amount` (numerically unchanged, still scaled for 6-decimal TokenA) is packed into `WithdrawalParams{ amount: available_amount, token: TokenB }` and dispatched to `HostManager` on `EVM-X`.
4. On delivery, `HostManager` transfers `available_amount` units of `TokenB` (18 decimals) to the relayer — a value roughly `10^12` times larger than intended, or, if the rotation went the other direction, a negligible fraction of the true amount owed — while `Fees::<T>` is zeroed out regardless, permanently closing the books on the mismatch.

		/// Update the host params for the provided state machine
		#[pallet::weight(T::DbWeight::get().writes(1))]
		#[pallet::call_index(1)]
		pub fn update_host_params(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			update: HostParamUpdate,
		) -> DispatchResult {
			T::HostExecutiveOrigin::ensure_origin(origin)?;

			let params = HostParams::<T>::get(&state_machine)
				.ok_or_else(|| Error::<T>::UnknownStateMachine)?;

			let (HostParam::EvmHostParam(mut inner), HostParamUpdate::EvmHostParam(update)) =
				(params.clone(), update);
			inner.update(update);

			let body = inner.abi_encode_with_variant().map_err(|_| Error::<T>::DispatchFailed)?;

			let post = DispatchPost {
				dest: state_machine,
				from: PALLET_ID.to_bytes(),
				to: inner.host_manager.0.to_vec(),
				timeout: 0,
				body,
			};

			let updated = HostParam::EvmHostParam(inner);

			let dispatcher = <T as Config>::IsmpHost::default();
			dispatcher
				.dispatch_request(
					DispatchRequest::Post(post),
					FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
				)
				.map_err(|_| Error::<T>::DispatchFailed)?;

			HostParams::<T>::insert(state_machine, updated.clone());

			Self::deposit_event(Event::<T>::HostParamsUpdated {
				state_machine,
				old: params,
				new: updated,
			});

			Ok(())
		}
