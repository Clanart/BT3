Confirmed: `Kip71GasTarget` uses `noopFormatChecker` with no zero-value rejection, unlike `Kip71BaseFeeDenominator` which explicitly enforces `v != 0`.### Title
Missing zero-value validation on `kip71.gastarget` governance parameter causes division-by-zero panic in base fee calculation - ([File: params/kip71_config.go])

### Summary
The `kip71.gastarget` governance parameter is validated with `noopFormatChecker`, which performs no sanity check at all, unlike its sibling parameter `kip71.basefeedenominator` which explicitly rejects zero. If `GasTarget` is set to `0` (via header/contract governance vote, which is an externally reachable, unprivileged-adjustable parameter path once accepted by governance), `KIP71Config.NextMagmaBlockBaseFee()` performs `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`, which causes a `math/big` division-by-zero runtime panic.

### Finding Description
`Kip71GasTarget`'s parameter definition uses `FormatChecker: noopFormatChecker`, i.e., no validation of the value at all: [1](#0-0) 

Compare this to the sibling parameter `Kip71BaseFeeDenominator`, which explicitly guards against zero: [2](#0-1) 

The `BaseFeeDenominator == 0` case is even defensively handled inside `NextMagmaBlockBaseFee` (falls back to 64) as a second layer of protection: [3](#0-2) 

However, `GasTarget` has no equivalent defensive fallback. In `NextMagmaBlockBaseFee`, when `parentGasUsed != gasTarget` (which is guaranteed whenever `gasTarget == 0` and `parentGasUsed > 0`), the function unconditionally divides by `gasTarget`: [4](#0-3) 

and in the decreasing-baseFee branch: [5](#0-4) 

Both branches call `x.Div(x, new(big.Int).SetUint64(gasTarget))` where `gasTarget` is the raw governance value with no floor. `big.Int.Div` panics at runtime when the divisor is zero. This function, `NextMagmaBlockBaseFee`, is invoked on every block after the Magma hard fork during header verification (`VerifyMagmaHeader`) and fee-history/base-fee computation, meaning a value of `0` would deterministically crash block processing on every full node, not just a specific transaction sender.

### Impact Explanation
Setting `kip71.gastarget = 0` through governance (header-vote or contract-governance path, both of which are externally observable/adjustable governance parameters within scope) would cause every node computing the next block's base fee — during block assembly by the proposer and during header verification by all other nodes — to panic. Since this computation happens unconditionally for every Magma-and-later block, this is a network-wide denial-of-service / consensus-halting condition once the parameter takes effect, matching the reported bug class of "unit and length need sanity check" causing DoS through an unguarded division that can degenerate to a divide-by-zero/round-to-zero.

### Likelihood Explanation
This requires a successful governance parameter change setting `kip71.gastarget` to `0`. This is gated behind the governance voting/contract-governance mechanism (not a plain unprivileged transaction), so exploitation requires either malicious/erroneous governance action or an operator mistake (fat-finger a `0`), which is lower likelihood than a fully permissionless attack but is a real, concretely reachable governance-parameter path explicitly in scope ("governance parameters"). There is no validation anywhere in the governance parameter pipeline (`param.go`, `paramset.go`) that would reject this value before it becomes active, unlike the parallel `BaseFeeDenominator` parameter which is explicitly guarded.

### Recommendation
Add a zero-value rejection to `Kip71GasTarget`'s `FormatChecker` in `kaiax/gov/param.go`, mirroring the check already used for `Kip71BaseFeeDenominator` (`v != 0`). As defense-in-depth, also add a fallback/guard inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` analogous to the existing `BaseFeeDenominator == 0` fallback, to prevent a panic even if a zero value is somehow already persisted in an existing chain configuration.

### Proof of Concept
1. Governance parameter `kip71.gastarget` is voted/set to `0` (accepted since `noopFormatChecker` performs no validation): [1](#0-0) 
2. On the next Magma-era block with `parentHeaderGasUsed > 0`, `NextMagmaBlockBaseFee` is invoked (e.g., from `VerifyMagmaHeader` during block validation, or from the block-assembly/fee-history paths): [6](#0-5) 
3. Inside, `parentGasUsed > gasTarget` evaluates true (since `gasTarget == 0` and any nonzero gas usage exceeds it), leading to: [7](#0-6) 
`x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0` triggers a `big.Int` division-by-zero panic, crashing the node process handling this block (both proposer during block assembly and all validating nodes during header verification), halting consensus.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
