## Title
Integer overflow/underflow in `consoleLog.decode` causes an unrecovered panic (node crash) via crafted `console.log` calldata - ([File: blockchain/vm/contracts.go])

### Summary
The `consoleLog` precompile decodes `string`/`bytes` dynamic parameters by converting attacker-controlled 32-byte words directly into Go `int` via `big.Int.Int64()`, then computing slice bounds (`start`, `size`, `start+size+registerSize`) without checking for negative results or arithmetic overflow before slicing. This mirrors the CVE-2017-6839 bug class (integer overflow in a length/offset field during decoding, leading to an out-of-bounds crash) but here manifests as a Go slice-bounds panic instead of a C buffer overflow.

### Finding Description
`consoleLog.decode` handles `StringTy` and `BytesTy` parameters: [1](#0-0) [2](#0-1) 

For both cases:
```go
start := int(big.NewInt(0).SetBytes(params[pos : pos+registerSize]).Int64())
if len(params) < start+registerSize { ... }
size := int(big.NewInt(0).SetBytes(params[start : start+registerSize]).Int64())
if len(params) < start+size+registerSize { ... }
res = append(res, string(params[start+registerSize:start+size+registerSize]))
```
`big.Int.Int64()` is documented to return an undefined/truncated value when the source doesn't fit an `int64` — in practice it returns the low 64 bits reinterpreted as signed, so a crafted 32-byte word (e.g. `0xFFFFFFFFFFFFFFFF...`) yields a **negative** `start` or `size`. The bounds checks (`len(params) < start+registerSize`, `len(params) < start+size+registerSize`) are `int`-arithmetic comparisons that do not catch negative operands or overflow correctly: a large negative `start`/`size` makes the right-hand side negative, so `len(params) < negative` is `false`, and the code proceeds to slice `params[start : ...]` or `params[start+registerSize : start+size+registerSize]` with negative or wrapped-around indices. Slicing a Go slice with an out-of-range (including negative) index causes a runtime panic (`slice bounds out of range`), which is not recovered anywhere in the call chain (`toLogString` → `Run` → EVM interpreter `execute`).

This is invoked from `consoleLog.Run`, which is reachable whenever the `consoleLog` precompile is active in the EVM's precompile map: [3](#0-2) [4](#0-3) 

The precompile is only registered when `evm.Config.UseConsoleLog` is true, i.e. it is an opt-in debug/local feature. I was unable to fully confirm from the index whether any production/public RPC-facing configuration path (e.g. debug/dev-mode node flags in `cmd/utils/flags.go`, `node/cn/config.go`) could enable `UseConsoleLog` on a node that also accepts untrusted public transactions; this needs verification with the full source (see note below).

### Impact Explanation
If `UseConsoleLog` is enabled on a node, a single crafted transaction/call whose EVM code invokes `CALL` (or similar) to the `consoleLog` precompile address with a malicious `string`/`bytes` parameter can trigger an unrecovered Go panic during EVM execution. Unlike normal EVM errors, a panic that escapes the interpreter loop will crash the node process, denying service to that node (and, if replicated across many nodes running with `UseConsoleLog` enabled, a broader availability impact). This matches the CVE's "integer overflow ... causing denial of service (crash)" bug class.

### Likelihood Explanation
Likelihood is conditioned entirely on `UseConsoleLog` being enabled; this flag appears intended for local/development networks per the comment "Hardhat console.log accepts format string ... local networks" in `blockchain/vm/contracts.go:1391-1392`. Because the crash requires the EVM feature flag to be enabled and I could not verify from the indexed code whether this flag is ever set for nodes accepting public/untrusted transactions, likelihood cannot be conclusively assessed as reachable by a fully unprivileged mainnet transaction sender without further investigation of `cmd/utils/flags.go`, `node/cn/config.go`, and any genesis/CLI defaults.

### Recommendation
- In `consoleLog.decode` (blockchain/vm/contracts.go), validate that `start` and `size` are non-negative and within `[0, len(params)]` immediately after converting from `big.Int`, and use unsigned/overflow-safe arithmetic (e.g. `uint64` with explicit overflow checks, similar to `common/math.SafeAdd`) before computing `start+registerSize` and `start+size+registerSize`.
- Reject values where the underlying `big.Int` does not fit in a reasonable bound (e.g., use `IsInt64()` and bound-check against `math.MaxInt32` rather than blindly calling `.Int64()`).
- Recover from panics in precompile `Run` invocations (defense in depth) so that a single malformed precompile call cannot crash the entire node process.
- Confirm and, if necessary, restrict which node configurations can enable `UseConsoleLog` so it can never be active on a node processing public, untrusted transactions.

### Proof of Concept
Deploy/execute a contract that calls the `consoleLog` precompile address (active only if the node has `UseConsoleLog` enabled) with calldata:
```
selector (4 bytes) matching a signature that declares a StringTy or BytesTy parameter
followed by a 32-byte "offset" word = 0xFFFFFFFFFFFFFFFF...FFFF (so that big.Int.Int64() truncation yields a negative `start`)
```
When `consoleLog.decode` computes `start := int(big.NewInt(0).SetBytes(...).Int64())`, `start` becomes negative; the subsequent bounds check `len(params) < start+registerSize` fails to reject it, and the later slice expression `params[start:start+registerSize]` (or the `string`/`bytes` slice with `start+size+registerSize`) panics with "slice bounds out of range", crashing EVM execution unrecovered. (I could not execute this in a live environment; this PoC is derived purely from static analysis of the decode logic shown above.)
