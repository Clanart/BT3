## Title
Divergent conflict-marker scanning between `extractConflictHunks` and `reassembleResolvedFile` allows a malicious repository to desync Copilot resolutions, silently corrupting committed merge results - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's AI-assisted merge-conflict resolution feature extracts conflict hunks from a conflicted file, sends them to Copilot, and then splices the model's per-hunk resolutions back into the original file by re-scanning it for conflict markers. The extraction pass (`extractConflictHunks`) and the reassembly pass (`reassembleResolvedFile`) implement two different, independently-written algorithms for deciding what counts as a well-formed `<<<<<<<`/`=======`/`>>>>>>>` block. When a conflicted file's own content (fully attacker-controlled via a crafted commit on a branch merged/rebased by the victim) contains lines that incidentally match the marker regexes without being real conflict delimiters, the two passes can disagree about hunk boundaries. Because the only integrity check (`validateResolutionPaths`) compares hunk **counts**, not hunk **identity/position**, a resolution meant for one conflict region can be spliced into a different location, or a conflict block can be left with its markers verbatim, all without any error being surfaced to the user.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks the file looking for `oursMarker` (`^<{7}`), and for the "ours" section it stops at the **first** line matching `baseMarker` or `separatorMarker`: [1](#0-0) 
It then collects "theirs" content until the **first** `theirsMarker` match: [2](#0-1) 

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) independently re-scans the same raw content, but with different lookahead semantics: from the `<<<<<<<` line, it scans forward, setting `hasSeparator = true` whenever it passes a `=======`-matching line, and only terminates on the **first** `>>>>>>>`-matching line: [3](#0-2) 
It then consumes the next resolution from `hunkResolutions` **in array order**, regardless of whether the block it just matched is actually the same block `extractConflictHunks` identified as a "hunk": [4](#0-3) 

The corrupted invariant is: *"hunk resolution #N returned by the model corresponds to conflict block #N as counted by both the extraction pass and the reassembly pass."* This holds only when both scanners agree on where blocks start and end. They do not always agree: extraction's "theirs" loop breaks on the first `theirsMarker`-looking line, but so does reassembly's lookahead — the divergence appears when the "ours" content (fully attacker-controlled file content in the conflicting branch, e.g. ASCII art, embedded example diffs, or a script that emits `>>>>>>>`-looking text) contains a line matching `theirsMarker` (`^>{7}(?:\s|$)`) **before** the real `=======` separator has been scanned by that particular algorithm's lookahead loop:

- In `extractConflictHunks`, such an embedded `>>>>>>>`-like line inside the "ours" region is simply pushed as ordinary `oursLines` content, because that loop only checks for `baseMarker`/`separatorMarker`, not `theirsMarker`, while collecting ours-lines. It never breaks early.
- In `reassembleResolvedFile`, the SAME embedded `>>>>>>>`-like line matches `reassemblyTheirsMarker` in the lookahead loop and immediately sets `closingIndex` and **breaks**, before the real `=======` line is ever reached, so `hasSeparator` is still `false`. The well-formedness check (`!hasSeparator || closingIndex === -1`) then fails, and the block is treated as **malformed** — the `<<<<<<<` line is copied through verbatim as plain content, `hunkIndex` is **not** incremented, and scanning resumes one line later (not from the previously-computed real closing marker).

Because `extractConflictHunks` counted this as one legitimate hunk (and sent it to Copilot, which produced a real resolution for it), but `reassembleResolvedFile` does not consume a resolution for it, every subsequent hunk resolution in the array is now off by one relative to the conflict blocks reassembly actually recognizes later in the file. The real conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`) from the "malformed" block, plus all of the ours/base/theirs content including the embedded fake marker text, are written into the final file verbatim, and a later, unrelated conflict block gets the wrong resolved content spliced in.

`validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`) is the only sanity check before write, and it only compares the **count** of hunks the model returned against the count `extractConflictHunks` produced — it has no knowledge of `reassembleResolvedFile`'s independent scan, so it cannot detect this desync: [5](#0-4) 

### Impact Explanation
This causes silent corruption of what the user commits: after "resolving" the conflict with Copilot, the resulting file can (a) still contain literal, unresolved `<<<<<<<`/`=======`/`>>>>>>>` conflict-marker text embedded in code that compiles/parses seemingly fine (especially in comments, strings, or generated fixtures) and (b) contain a completely unrelated hunk's resolved content spliced into the wrong location. The user is given no error, no diff warning beyond the normal review UI, and `validateResolutionPaths` reports success because hunk counts still match. If the user trusts the AI resolution and commits/pushes, broken or semantically wrong code — potentially including silently reintroduced/dropped logic — enters the repository history. This falls squarely in the "silent corruption of what the user commits or pushes" impact category, driven entirely by content in a repository the attacker controls (a branch that, when merged/rebased by the victim, produces the crafted conflict).

### Likelihood Explanation
The trigger requires only that a conflicting branch (fully attacker-controlled, e.g. a PR branch, or any remote branch the victim merges/rebases) contain a line inside the conflicted region that happens to match `^>{7}(?:\s|$)` (seven or more `>` characters followed by whitespace or end-of-line) — an easy string for an attacker to insert intentionally (e.g., in a comment, ASCII banner, embedded diff sample, or minified/generated content) without it needing to be a real git conflict marker. This is triggered purely by opening the repository in Desktop, encountering the conflict, and using the Copilot "resolve conflicts" feature — no elevated privileges, local access, or unusual user action beyond a feature the app markets and surfaces in its UI. The feature is currently in the codebase (`copilot-conflict-resolution.ts`, `copilot-conflict-context.ts`, exercised via `app/src/lib/stores/copilot-store.ts` and the conflict-resolution dialog), so the reachable path exists in shipped code.

### Recommendation
Do not use two independently-implemented marker scanners. `reassembleResolvedFile` should reuse the exact same boundary-detection logic as `extractConflictHunks` (ideally by having `extractConflictHunks` return line-index ranges for each hunk, and have reassembly splice based on those exact ranges) so that the two passes can never disagree about what constitutes a conflict block. Additionally, `validateResolutionPaths` (or a new check performed during reassembly) should assert that the number of conflict blocks recognized by the reassembly scan for a given file also equals `expectedHunkCounts`, and abort/report an error rather than silently writing a mismatched result if the counts diverge at splice time.

### Proof of Concept
1. Create a repository with a file `notes.txt` on `main` containing ordinary text.
2. On a branch `feature`, modify `notes.txt` so that, after a merge/rebase against `main` is attempted, git produces a conflict where the "ours" (or "theirs") region contains a line that itself looks like a conflict marker, e.g.:
   ```
   <<<<<<< HEAD
   Some real content the user wrote
   >>>>>>> this text is NOT a real marker, it's from a script that prints ">>>>>>> done"
   more real content
   =======
   incoming content from feature
   >>>>>>> feature
   ```
3. In `extractConflictHunks`, this is parsed as one hunk: `oursContent = "Some real content the user wrote\n>>>>>>> this text is NOT a real marker...\nmore real content"`, `theirsContent = "incoming content from feature"`. This hunk is sent to Copilot, which returns one `resolvedContent` for it.
4. In `reassembleResolvedFile`, scanning from the `<<<<<<< HEAD` line, the lookahead hits the fake `>>>>>>>` line before ever seeing the real `=======`, so `hasSeparator` is `false` when `closingIndex` is set → the block is deemed malformed, `<<<<<<< HEAD` is copied through verbatim, and `hunkIndex` is not incremented.
5. Scanning continues line-by-line as plain content (no `<<<<<<<` restart), so the real `=======` and `>>>>>>> feature` markers, plus all interleaved content, are also copied through verbatim into the "resolved" file — while the model's one resolution intended for this block is never consumed here, and instead gets attached to whatever the *next* real conflict block in the file is (if any), corrupting it with unrelated resolved content.
6. `validateResolutionPaths` still reports success (hunk count 1 sent, 1 returned), so the corrupted file is presented to the user as fully resolved and ready to commit. [6](#0-5) [7](#0-6)

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
