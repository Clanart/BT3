### Title
Payout Transaction's Operator-Attribution OP_RETURN Is Unauthenticated by the User's SIGHASH_SINGLE|ANYONECANPAY Signature, Allowing Reimbursement Misattribution - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The user's withdrawal signature used to authorize the `payout_tx` is validated with `sighash_type` accepted from the caller and expected to be `SinglePlusAnyoneCanPay` [1](#0-0) . Under `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`, the signature commits only to input 0 and the output at index 0 (the user payout output); it does not commit to output 2, the `OP_RETURN` output carrying the operator's x-only public key that determines who is credited with fronting the withdrawal [2](#0-1) . Anyone who observes the signed input/output (e.g., in the mempool or via any operator that received the withdrawal request) can rebuild an equivalent `payout_tx` with the same signature but a different `operator_xonly_pk` in the OP_RETURN, and get it confirmed first (e.g. by RBF/fee-bump), since nothing else constrains that field.

### Finding Description
`create_payout_txhandler` builds the OP_RETURN output from a caller-supplied `operator_xonly_pk` argument and only applies the key-spend witness to input 0 [2](#0-1) . The `operator.withdraw` function accepts the sighash type embedded in the user-provided `in_signature` and verifies the schnorr signature over `calculate_sighash_txin(0, in_signature.sighash_type)` [1](#0-0) . It only checks that the signature is valid for whichever sighash type is provided — there is no explicit enforcement that `in_signature.sighash_type == SinglePlusAnyoneCanPay`, and even if there were, that sighash mode by definition excludes the OP_RETURN output (index 2) from the signed message.

Downstream, the protocol relies on this OP_RETURN field as the sole on-chain attribution of "who fronted the withdrawal": `update_finalized_payouts` extracts `operator_xonly_pk` from the confirmed payout tx's OP_RETURN and stores it as `payout_payer_operator_xonly_pk` [3](#0-2) , and `is_kickoff_malicious` later compares the OP_RETURN-derived pubkey against the kickoff operator to decide whether a reimbursement kickoff is legitimate [4](#0-3) . The bridge-circuit host similarly binds `deposit_constant` to the OP_RETURN-derived `operator_xonlypk` for the Groth16 proof [5](#0-4) .

Because the OP_RETURN content is unauthenticated by the user's signature, an unprivileged party who learns of a valid signed payout input (broadcast to the network, or obtained by any operator that the withdrawal was routed to via `AggregatorWithdrawalInput.operator_xonly_pks`) can substitute a different `operator_xonly_pk` and get their version mined instead. This breaks the binding "the operator credited (via OP_RETURN + kickoff) versus the party that actually funded the payout output" — the attacker's chosen pubkey (which may not even correspond to a real, provisioned operator, or may belong to a different operator than the one who actually funded/broadcast the tx) is recorded as the payer, while the true operator's rebroadcast attempt is now a conflicting double-spend of the same input.

### Impact Explanation
Per the rules, this matches the Critical impact class "an operator reimbursed for a payout it never funded" / "an honest operator permanently unable to be reimbursed." If a malicious operator (or any party observing the pending signed payout in the mempool) rewrites the OP_RETURN to point to itself before the honest operator's transaction confirms, the honest operator's payout tx is invalidated (same input already spent), yet only the attacker's version — carrying the attacker's `operator_xonly_pk` — gets recorded as `payout_payer_operator_xonly_pk` in `update_finalized_payouts`. The honest operator who actually intended to front the withdrawal is left with no funded, confirmed payout tied to its own key and can never be reimbursed for this withdrawal, while the attacker can subsequently kick off a reimbursement claim using the substituted pubkey without ever having paid a legitimate previously-negotiated fee-bearing withdrawal that the user actually agreed to (the user output itself is unchanged since SIGHASH_SINGLE still covers output 0, but the credited beneficiary of collateral/reimbursement is now attacker-controlled).

### Likelihood Explanation
Exploitability requires only that the signed payout input become visible to a third party before it confirms (mempool visibility, or being one of multiple operators solicited via `AggregatorWithdrawalInput.operator_xonly_pks` when the list is not restricted to one operator) and the ability to fee-bump/rebroadcast a modified transaction with the same signature and input, which is straightforward given `SIGHASH_ANYONECANPAY`. No verifier, aggregator, or operator privilege is needed — any unprivileged observer of the mempool can perform this substitution once a valid signature+input pair is broadcast.

### Recommendation
Bind the operator attribution to the signed message rather than leaving it to an unauthenticated OP_RETURN field. Options: (1) require the user's withdrawal signature to use `SIGHASH_ALL` (or at minimum a sighash mode that commits to all outputs, e.g. drop ANYONECANPAY, or use `SIGHASH_SINGLE|ANYONECANPAY` only when the OP_RETURN commitment is enforced through a separate mechanism); (2) explicitly reject any `in_signature.sighash_type` other than the intended one and additionally have verifiers/aggregator cross-check that the confirmed payout's OP_RETURN pubkey matches the operator that the aggregator/verifier expected to route the withdrawal to before treating that operator as having "fronted" it, rather than trusting the first-seen OP_RETURN bytes unconditionally.

### Proof of Concept
1. Aggregator/verifier-orchestrated withdrawal flow signs a `payout_tx` input with `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` via `operator.withdraw`, targeting output 0 (user payout) and passing `self.signer.xonly_public_key` for the OP_RETURN [6](#0-5) .
2. Operator A funds and broadcasts the resulting transaction (`create_payout_txhandler`, `operator_xonly_pk = A`) [2](#0-1) .
3. Before confirmation, an attacker observes the txin+signature in the mempool, constructs an alternate transaction using `create_payout_txhandler` with the same `input_utxo`, `output_txout`, `user_sig`, but `operator_xonly_pk = B` (attacker-controlled), reusing the same valid signature since it does not cover the OP_RETURN output, and rebroadcasts with a higher fee (RBF).
4. Attacker's transaction confirms instead of Operator A's; `update_finalized_payouts` records `payout_payer_operator_xonly_pk = B` [7](#0-6) .
5. Operator A's original broadcast is now invalid (double-spent input), so A can never get its own kickoff/reimbursement accepted (`is_kickoff_malicious` will reject A's kickoff since `operator_xonly_pk != kickoff_data.operator_xonly_pk`) [8](#0-7) , while B can proceed to claim reimbursement credit it did not legitimately earn through the normal solicited withdrawal flow.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()

fn host_deposit_constant(
    input: &BridgeCircuitInput,
) -> Result<DepositConstant, BridgeCircuitHostParamsError> {
    let first_op_return_output = get_first_op_return_output(&input.payout_spv.transaction)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&input.sp.storage_proof_deposit_txid).map_err(|e| {
            BridgeCircuitHostParamsError::StorageProofDeserializationError(e.to_string())
        })?;

    let round_txid = input.kickoff_tx.input[0]
        .previous_output
        .txid
        .to_byte_array();

    let kickoff_round_vout = input.kickoff_tx.input[0].previous_output.vout;

    let operator_xonlypk: [u8; 32] = parse_op_return_data(&first_op_return_output.script_pubkey)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?
        .try_into()
        .map_err(|_| BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

    Ok(deposit_constant(
        operator_xonlypk,
        input.watchtower_challenge_connector_start_idx,
        &input.all_tweaked_watchtower_pubkeys,
        deposit_value_bytes,
        round_txid,
        kickoff_round_vout,
        input.hcp.genesis_state_hash,
    ))
}
