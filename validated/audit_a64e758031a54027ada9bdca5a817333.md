Confirmed: `Kip71GasTarget` param uses `noopFormatChecker` (no zero-check), unlike `Kip71BaseFeeDenominator` which explicitly requires `v != 0` [1](#0-0) . This is a real, unmitigated division-by-zero path in consensus-critical code.

### Title
Governance-settable `kip71.gastarget` of 0 causes division-by-zero panic in `NextMagmaBlockBaseFee` block base fee calculation - (File: params/kip71_config.go)

### Summary
The KIP-71 dynamic base fee formula divides by `GasTarget` twice, but unlike `BaseFeeDenominator` (which has an explicit zero-guard), `GasTarget` has no such protection and its governance vote validator uses a no-op format checker that accepts any `uint64` including 0.

### Finding Description
`NextMagmaBlockBaseFee` computes the delta by dividing an intermediate value by `gasTarget`: `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` in both the gas-used-above-target and below-target branches [2](#0-1) [3](#0-2) . The code explicitly protects `BaseFeeDenominator` against zero with a fallback comment "To avoid panic, set the fluctuation range small" [4](#0-3) , but no equivalent guard exists for `gasTarget`.

`Kip71GasTarget` is a governance-votable parameter defined with `Canonicalizer: uint64Canonicalizer` and `FormatChecker: noopFormatChecker`, which always returns `true` regardless of value [5](#0-4) [6](#0-5) . By contrast, `Kip71BaseFeeDenominator`'s `FormatChecker` explicitly rejects `v == 0` [7](#0-6) . The `checkConsistency` function in header governance vote validation also does not perform any additional non-zero check for `Kip71GasTarget`, treating it (along with several other KIP-71 params) as passing format checks with no extra consistency rule [8](#0-7) .

If governance votes `kip71.gastarget = 0` and the vote is accepted (passing `NewVoteData`'s canonicalizer/format check and `checkConsistency`), the parameter becomes active in `ChainConfig.Governance.KIP71.GasTarget`. On the next block, `NextMagmaBlockBaseFee` is called both during header verification (`VerifyMagmaHeader`) and block assembly/base fee computation. Since `parentGasUsed` is `min(parentHeaderGasUsed, upperGasLimit)`, when `gasTarget == 0`, `parentGasUsed > gasTarget` is true for any nonzero gas usage, and `x.Div(x, new(big.Int).SetUint64(0))` triggers a Go `big.Int` division-by-zero panic (this is a runtime panic, not a catchable Solidity-style revert).

### Impact Explanation
This is not merely a rejected/reverted transaction, but a Go runtime panic (`div by zero`) inside consensus state-transition code (`VerifyMagmaHeader`/`NextMagmaBlockBaseFee`), which is invoked by every node while validating or assembling every subsequent block. A panic here can crash node processes network-wide (all consensus and endpoint nodes calling this shared code path), effectively producing a chain halt / denial of service once the governance parameter is set — a availability-critical governance/state-transition failure reachable purely through the standard governance voting mechanism (no privileged off-chain access needed beyond the normal governance vote process available to validators/governing node). This qualifies as a valid Medium/High severity acceptance-of-invalid-state issue analogous to the reported unchecked-subtraction/division bug class.

### Likelihood Explanation
Likelihood depends on whether `Kip71GasTarget=0` votes can pass through the full governance vote pipeline (`NewVoteData` canonicalization/format check plus `checkConsistency`) without additional external validation elsewhere (e.g., in a governance contract or additional Go-level guard) that this snippet review could not fully locate. Based on the code reviewed, no such additional guard exists for `GasTarget`, mirroring exactly the missing-validation pattern in the original report (unchecked `epochBegin == epochCreation`).

### Recommendation
Add an explicit non-zero `FormatChecker` for `Kip71GasTarget` analogous to `Kip71BaseFeeDenominator`'s check (`v != 0`), and/or add a defensive zero-check inside `NextMagmaBlockBaseFee` before dividing by `gasTarget`, mirroring the existing `BaseFeeDenominator` zero-fallback pattern.

### Proof of Concept
1. Governance votes to set `kip71.gastarget` to `0`; the vote passes `uint64Canonicalizer` and `noopFormatChecker` [5](#0-4) , and `checkConsistency` applies no extra rule for this key [8](#0-7) .
2. Once the parameter is applied to `ChainConfig.Governance.KIP71.GasTarget = 0`, any subsequent block with `parentHeaderGasUsed > 0` triggers `NextMagmaBlockBaseFee` computing `parentGasUsed > gasTarget` (true) and calling `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0` [2](#0-1) .
3. `big.Int.Div` panics on division by zero, crashing the calling node process during header verification/block assembly.
