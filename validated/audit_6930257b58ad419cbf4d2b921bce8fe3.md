### Title
Unchecked GasTarget=0 governance parameter causes divide-by-zero panic in `KIP71Config.NextMagmaBlockBaseFee` - (File: params/kip71_config.go)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` in `params/kip71_config.go` performs `big.Int` division using the governance-controlled `GasTarget` value as a divisor without checking it is non-zero, while the corresponding governance parameter `Kip71GasTarget` uses a `noopFormatChecker` that accepts any `uint64` value including zero.

### Finding Description
`NextMagmaBlockBaseFee` computes the base fee delta using `gasTarget` (derived from `kc.GasTarget`) as a divisor in both the "gas used above target" and "below target" branches: [2](#0-1) 
`y := x.Div(x, new(big.Int).SetUint64(gasTarget))` — Go's `big.Int.Div` (and `.Mod`) panics with `division by zero` when the divisor is zero, unlike the intentional "avoid panic" guard that exists for `BaseFeeDenominator`: [3](#0-2) 
That guard demonstrates the developers were aware `BaseFeeDenominator == 0` would panic and added an explicit fallback (`baseFeeDenominator = 64`). No equivalent guard exists for `gasTarget`.

Crucially, the governance parameter definition for `Kip71GasTarget` explicitly uses `noopFormatChecker` (i.e., no validation at all), in contrast to `Kip71BaseFeeDenominator`, which has a `FormatChecker` requiring `v != 0`: [1](#0-0) 
This means a governance vote (submitted as a transaction/vote by the governing node, or accepted through the header-vote mechanism) setting `governance.kip71.gastarget = 0` passes format validation and gets applied to the live `KIP71Config` used by every node computing `NextMagmaBlockBaseFee` for each new block header, both during block production and during block/header verification (`VerifyMagmaHeader`) as well as in RPC methods like `eth_feeHistory` (`node/cn/gasprice/feehistory.go`) which also calls `NextMagmaBlockBaseFee`. [4](#0-3) 

Once `GasTarget=0` is active, any block whose `parentGasUsed != 0` (i.e., `parentGasUsed > gasTarget`, since gasTarget=0) will trigger the division-by-zero panic path at line 102, crashing every node computing the next base fee — this is functionally the "roll" analog: an integer division operation reachable through a value fully controlled by an on-chain governance parameter, with insufficient bounds validation, causing a fatal runtime exception (panic) instead of the gracious `INT_MIN`/zero handling exhibited elsewhere in the same file.

### Impact Explanation
A panic in `NextMagmaBlockBaseFee` occurring in the consensus-critical block-processing / header-validation path (and in the public RPC `eth_feeHistory` path) would crash or halt node processes network-wide once such a header is processed, since all Kaia nodes execute identical logic on the same governance state. This constitutes a state-divergence / chain-halt condition — every full node, validator, and public RPC endpoint calling `NextMagmaBlockBaseFee` on the malicious parameter would panic simultaneously, an availability-impacting, network-wide denial of service. This maps to the "Impact = A:H" reachable-crash class described in the external report and satisfies the required "state divergence between honest nodes" / crash escalation bar because the parameter, once accepted, is enforced identically and irrevocably by consensus rules.

### Likelihood Explanation
The likelihood depends on whether the governance parameter change mechanism enforces additional bounds beyond `FormatChecker` (e.g., a governing-node-only permission gate). The vote/parameter path is reachable from a governance proposal transaction; assuming the standard Kaia governance model where a param change is submitted and applied by voting/consensus (accessible to permissioned governing nodes, not arbitrary unprivileged senders), the likelihood is Medium — it requires governance authority to submit the parameter, but no additional value or bounds check prevents `0` from being accepted once submitted.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0`, consistent with `Kip71BaseFeeDenominator`'s treatment, and/or add a defensive zero-check inside `NextMagmaBlockBaseFee` (mirroring the existing `BaseFeeDenominator == 0` fallback) before dividing by `gasTarget`.

### Proof of Concept
1. Submit/accept a governance parameter update setting `governance.kip71.gastarget = 0` (passes because `Kip71GasTarget.FormatChecker = noopFormatChecker`). [5](#0-4) 
2. Once active, any subsequent block with non-zero `GasUsed` (which is essentially all blocks) causes `parentGasUsed > gasTarget` (0), taking the branch at `params/kip71_config.go` line 92. [6](#0-5) 
3. The line `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` executes `big.Int.Div(x, 0)`, panicking with `division by zero`, crashing the node executing `NextMagmaBlockBaseFee` (block processing, header verification, and `eth_feeHistory` RPC calls).
