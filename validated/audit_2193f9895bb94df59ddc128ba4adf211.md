### Title
Stale Line-Selection Indices Are Applied Against a Freshly Re-Fetched Diff During Partial Commit, Silently Corrupting Which Lines Are Staged - ([File: app/src/lib/git/apply.ts])

### Summary
This maps the "amount drift" bug class from the report — a user-authorized intent (swap params / minOut) being reconciled against a *later, possibly-different* actual value using a naive/partial patch instead of a full re-validation — onto GitHub Desktop's line-level partial-commit feature. There, the user's line selection is captured as an index set (`DiffSelection`) against a specific rendered diff snapshot, but when the commit is finally executed, a brand-new diff is fetched from disk and the *old* index set is blindly applied to it.

### Finding Description
When a user makes a partial commit (selecting only some added/removed lines), Desktop tracks the selection as a set of absolute line indices (`divergingLines`) inside `DiffSelection`, computed relative to a specific `ITextDiff` snapshot rendered in the UI: [1](#0-0) 

At commit time, `createCommit()` calls `stageFiles()`, which for any partially-selected file calls `applyPatchToIndex()`: [2](#0-1) [3](#0-2) 

`applyPatchToIndex()` does **not** reuse the diff the user actually reviewed. It re-fetches the working-directory diff fresh from disk (`getWorkingDirectoryDiff`) and immediately formats a patch from it using the file's (potentially stale) `selection`: [4](#0-3) 

`formatPatch()` then walks the *new* diff's hunks and, for each line, calls `file.selection.isSelected(absoluteIndex)` — reusing the old index positions against new hunk content: [5](#0-4) 

Desktop's own code acknowledges that a diff "might have changed dramatically" since it was last rendered, and only prunes indices that no longer exist as *includeable* lines at all — it does **not** verify that a surviving index still refers to the *same logical content*: [6](#0-5) 

This is the direct analog of the reported flaw: instead of fully re-deriving the intended amount/selection against the actual/new data, the code mutates/reuses a stale, partial representation (a fixed index into a document that has shifted), so the "safety" invariant (the app commits exactly the lines the user visually selected) silently breaks when the underlying document changes between selection and execution.

### Impact Explanation
If the tracked file's content on disk changes between when the user visually selects lines in the diff viewer and when `applyPatchToIndex` re-fetches the diff for staging (e.g., due to a checkout-time content rewrite from repository-declared attributes such as an LFS `filter=lfs` smudge/clean pipeline that Desktop auto-installs via `installLFSHooks`, or any other git-attribute-driven working-tree rewrite triggered by a git operation Desktop runs as part of normal repo interaction), the new diff's hunk boundaries and line ordering can shift while the same absolute indices remain "includeable." The stale `DiffSelection` will then mark different, unreviewed lines as selected/deselected, so `git apply --cached` stages content the user never approved — a silent corruption of what gets committed and, subsequently, pushed to a shared remote. Because attacker-controlled repository metadata (`.gitattributes` filter declarations) can influence what content is rewritten on disk during routine git operations, an attacker who controls a cloned/fetched repository can engineer content that shifts diff structure in a way that defeats the user's explicit line-level review, without any local/physical access, elevated privileges, or social engineering step beyond the user opening and normally interacting with the malicious repository.

### Likelihood Explanation
The window between a rendered diff and an executed commit is arbitrary and user-controlled (the user can pause on the Changes view for any length of time before clicking Commit), and Desktop already documents (in its own source comments) that diffs can change "dramatically" between renders. The reuse of raw integer indices, rather than content-anchored selection, means any structural diff change during that window is sufficient to trigger the corruption — no race condition finesse or precise timing is required beyond "some git-attribute-driven rewrite happens before the click." This is a design-level invariant gap rather than a narrow race, making it moderately likely to be reachable in practice with a crafted repository, though it does require the victim to leave a partial selection open across a working-tree-mutating event, which is a normal but not guaranteed workflow.

### Recommendation
Do not reuse pre-existing line-index selections against a diff fetched at a different point in time. `applyPatchToIndex`/`formatPatch` should either (a) re-validate that the diff used to build the patch is byte-identical/content-identical to the diff the selection was computed against (hash/compare hunks, not just re-run `isIncludeableLine`), refusing or re-prompting the user if it has changed, or (b) anchor selections to line *content* (e.g., a stable content hash per hunk line) instead of raw absolute indices, so that structural changes to the diff cannot silently remap a selection onto different content.

### Proof of Concept
1. Clone a malicious repository containing a tracked file `foo.txt` and a `.gitattributes` entry declaring an LFS/clean-smudge style filter for it (Desktop will auto-run `installLFSHooks` for LFS-using repos).
2. In Desktop, modify `foo.txt` locally so several unrelated hunks appear; open the Changes view and use line-level selection to check exactly one specific added line.
3. Before clicking "Commit," trigger a git operation Desktop performs as part of normal use that touches the working tree (e.g., a checkout/pull that re-smudges `foo.txt` via the attacker-defined filter), changing hunk boundaries/line ordering while keeping the same number of includeable lines.
4. Click "Commit." Observe (via `git show <sha>`) that the staged/committed diff does not correspond to the line the user visually selected in step 2, because `applyPatchToIndex` (`app/src/lib/git/apply.ts:60-81`) re-fetched the diff and `formatPatch` (`app/src/lib/patch-formatter.ts:143-171`) applied the old `DiffSelection` indices to the new hunk layout.
