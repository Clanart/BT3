### Title
Unauthorized Invocation of Privileged Internal gRPC Methods via `Noop` Interceptor When `client_verification = false` — (`File: core/src/servers.rs`)

### Summary

`create_grpc_server` in `core/src/servers.rs` installs a `Noop` interceptor (zero authentication) on the operator and verifier gRPC servers whenever `config.client_verification` is `false`. Because the environment-variable parser in `core/src/config/env.rs` silently defaults `client_verification` to `false` when `CLIENT_VERIFICATION` is absent from the environment, any operator or verifier that uses env-based configuration without explicitly setting `CLIENT_VERIFICATION=true` exposes every gRPC method — including privileged internal ones — to unauthenticated callers. The most impactful reachable method is `InternalEndRound`, which, when the `automation` feature is compiled in, unconditionally advances the operator's round state and can exhaust kickoff connectors, permanently locking the operator's collateral UTXO chain.

### Finding Description

**Root cause — `core/src/servers.rs` lines 114–139**

The TCP server path wraps the service in an `InterceptedService` whose interceptor is chosen by a single boolean:

```rust
let service = InterceptedService::new(
    service,
    if config.client_verification {
        OnlyAggregatorAndSelf { aggregator_cert, our_cert: client_cert }
    } else {
        Noop          // ← passes every request unconditionally
    },
);
``` [1](#0-0) 

When `Noop` is active, `core/src/rpc/interceptors.rs`'s `only_aggregator_and_self` function is never called, so neither the mTLS leaf-certificate check nor the `is_internal` guard runs. [2](#0-1) 

**Dangerous default in the env parser — `core/src/config/env.rs` line 182**

```rust
let client_verification =
    read_string_from_env("CLIENT_VERIFICATION").is_ok_and(|s| s == "true" || s == "1");
```

`is_ok_and` evaluates to `false` when the variable is absent, so an operator who omits `CLIENT_VERIFICATION` from their environment silently gets `client_verification = false`. [3](#0-2) 

**Privileged internal methods exposed**

The operator gRPC service exposes `InternalEndRound`, `InternalCreateAssertCommitmentTxs`, `InternalWithdraw`, and `InternalCreateSignedTxs`. These are intended to be callable only by the entity itself (enforced by the `is_internal` path in `OnlyAggregatorAndSelf`): [4](#0-3) 

With `Noop`, none of that logic runs. The proto definitions confirm these methods are live on the operator server: [5](#0-4) 

**`InternalEndRound` implementation (with `automation` feature)**

```rust
async fn internal_end_round(&self, _request: Request<Empty>) -> Result<Response<Empty>, Status> {
    #[cfg(feature = "automation")]
    {
        let mut dbtx = self.operator.db.begin_transaction().await?;
        self.operator.end_round(&mut dbtx).await?;
        dbtx.commit().await...
        Ok(Response::new(Empty {}))
    }
    ...
}
``` [6](#0-5) 

`end_round` advances the operator's round index and broadcasts the round transaction. Calling it repeatedly exhausts the fixed pool of kickoff connectors, after which `handle_finalized_payout` cannot find an unused connector and the operator can no longer process reimbursements. [7](#0-6) 

### Impact Explanation

An attacker who can reach the operator's gRPC TCP port and whose deployment has `client_verification = false` (the silent env-parser default) can:

1. Call `InternalEndRound` repeatedly → exhaust all round kickoff connectors → operator can never claim reimbursement for any future payout → operator collateral UTXOs are permanently locked in the bridge covenant with no recovery path.
2. Call `InternalCreateAssertCommitmentTxs` with a crafted `TransactionRequest` → obtain operator-signed assert transactions for arbitrary deposit/kickoff combinations → use them to submit a fraudulent BitVM assertion on-chain.
3. Call `InternalWithdraw` → force the operator to process a withdrawal the operator has not reviewed, draining the operator's payout liquidity.

The collateral lock and fraudulent assertion paths meet the "permanent lock or slashable exposure of operator collateral / bridge-controlled UTXOs" criterion.

### Likelihood Explanation

- **Trigger condition**: `client_verification = false`. This is the silent default when `CLIENT_VERIFICATION` is absent from the environment. Operators following the `.env.example` set it to `true`, but any env-based deployment that omits the variable is silently vulnerable.
- **Mainnet guard**: `check_mainnet_requirements` rejects `client_verification = false` for `Network::Bitcoin` actors, but only if it is called at startup and only for mainnet. Testnet/regtest deployments and any mainnet deployment where the check is skipped are unprotected.
- **Feature gate**: `InternalEndRound`'s destructive path requires the `automation` feature. `InternalFinalizedPayout` has an additional `!cfg!(test)` guard and is not exploitable in production builds.
- **Network access**: The attacker needs TCP access to the operator's gRPC port. If the port is publicly reachable (common for operators that must accept aggregator connections), no further privilege is required.

### Recommendation

1. **Never use `Noop` for operator/verifier servers.** Internal methods must always enforce the self-cert check regardless of `client_verification`. Either remove the `Noop` branch for operator/verifier server creation, or add a per-method authentication layer inside each `Internal*` handler that checks the peer certificate independently of the interceptor.
2. **Fix the env-parser default.** Change the parser to return an error (not `false`) when `CLIENT_VERIFICATION` is absent, forcing operators to make an explicit choice:
   ```rust
   let client_verification = read_string_from_env_then_parse::<bool>("CLIENT_VERIFICATION")?;
   ```
3. **Extend `check_mainnet_requirements` to all networks**, or at minimum emit a loud warning when `client_verification = false` is detected at startup for any actor type.

### Proof of Concept

**Preconditions**: operator binary compiled with `--features automation`, deployed with env-based config where `CLIENT_VERIFICATION` is unset (defaults to `false`), gRPC port reachable by attacker.

```python
import grpc
# No client certificate — plain TLS channel is sufficient because
# client_verification=false means the server does not request one.
channel = grpc.secure_channel(
    "operator-host:17000",
    grpc.ssl_channel_credentials(root_certificates=open("ca.pem","rb").read()),
)
from clementine_pb2_grpc import ClementineOperatorStub
from clementine_pb2 import Empty
stub = ClementineOperatorStub(channel)

# Exhaust all round kickoff connectors:
for _ in range(100):
    stub.InternalEndRound(Empty())
# Operator can no longer find an unused kickoff connector for any deposit.
# handle_finalized_payout returns RowNotFound; collateral is permanently locked.
```

The attacker sends `InternalEndRound` (gRPC path `/clementine.ClementineOperator/InternalEndRound`) without any client certificate. With `Noop` interceptor active, the request reaches `operator.end_round()` directly. After exhausting the round pool, every subsequent call to `handle_finalized_payout` hits the `ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))` guard at line 860 of `core/src/operator.rs`, permanently blocking reimbursement for all bridged BTC.
