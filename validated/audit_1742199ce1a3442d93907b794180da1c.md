### Title
Unchecked Bitcoin amount arithmetic signs transactions with overflowing outputs - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums attacker-controlled payment amounts and input values with unchecked `u64` arithmetic. In release builds, the total can wrap modulo \(2^{64}\), allowing an invalid transaction whose declared outputs exceed Bitcoin’s maximum supply to pass the insufficient-funds check and proceed to threshold signing. [1](#0-0) [2](#0-1) 

### Finding Description
Payment amounts are public `u64` values, each independently checked only against the 546-satoshi dust threshold. [3](#0-2)  The constructor then computes `input_sat`, `payment_sat`, `payment_sat + needed_fee`, and `payment_sat + fee_with_change` without checked arithmetic. [4](#0-3) [5](#0-4) 

Four payments of `2^62` satoshis each sum to zero after `u64` wraparound in release mode. The transaction still contains four `TxOut`s worth `2^62` satoshis each, but `payment_sat` is treated as zero and the balance test compares only `input_sat` against the fee. [6](#0-5) [7](#0-6)  Because only four outputs are used, the standard-weight check does not reject the transaction before it is converted into a `SignableTransaction`. [8](#0-7) 

### Impact Explanation
The resulting `SignableTransaction` can be converted into per-input FROST machines when each claimed input’s script matches the offset group key. [9](#0-8)  `TransactionSignMachine::sign` then obtains a Taproot key-spend sighash for every input and produces a FROST signature share for it. [10](#0-9)  Participants therefore sign an unintended transaction whose real output total is impossible and whose security-critical balance calculation disagrees with the serialized transaction.

The deserialized-input analogue is also exposed: `ReceivedOutput::read` accepts a consensus-decoded `TxOut` without enforcing Bitcoin’s maximum-money bound before its value enters `input_sat`. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
An unprivileged caller who can influence the payment list used to construct a Bitcoin signing plan can choose amounts satisfying this wraparound. The exploit does not require control of the private key shares, malformed point encodings, a malicious peer implementation, or more than a few payment entries. It does require a release build or another configuration where `u64` addition wraps rather than panics; debug builds will panic on the overflow.

### Recommendation
Use `checked_add` or `checked_sum` for `input_sat`, `payment_sat`, `payment_sat + needed_fee`, `fee_per_vbyte * vbytes`, and `fee_per_vbyte * vbytes_with_change`. Reject any individual payment or `TxOut` amount exceeding Bitcoin’s `MAX_MONEY`, and reject multiplication/addition overflow with `TransactionError::NotEnoughFunds` or a dedicated invalid-amount error before constructing `tx_outs`.

### Proof of Concept
A minimal triggering payment list is four identical payments of `1 << 62` satoshis:

```rust
let huge = 1u64 << 62;
let payments = vec![
    (changeless_script.clone(), huge),
    (changeless_script.clone(), huge),
    (changeless_script.clone(), huge),
    (changeless_script.clone(), huge),
];

// input_sat only has to cover the small computed fee because
// payment_sat wraps to zero in a release build.
let tx = SignableTransaction::new(inputs, &payments, None, None, fee_per_vbyte)?;
```

The serialized transaction contains `4 * 2^62` satoshis of outputs while `payment_sat == 0`, so the check at `send.rs:215` does not reject it. Calling `multisig`, `preprocess`, and `sign` reaches the per-input Taproot signing path for that malformed transaction.
