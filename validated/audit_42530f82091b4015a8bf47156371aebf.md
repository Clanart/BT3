### Title
TokenFactory denom admin can permanently freeze existing holders' balances by setting a `DenomAllowList` that excludes them - ([File: sei-cosmos/x/bank/keeper/send.go])

### Summary
The `UXDController` finding shows that an owner can retroactively remove an asset from a whitelist / remove its backing depository, freezing funds that a user legitimately obtained before the change. Sei-chain's tokenfactory module has an analogous pattern: the (permissionless, self-appointed) creator/admin of a `factory/{creator}/{subdenom}` denom can call `MsgUpdateDenom` at any time to set a `DenomAllowList`, and any address holding that denom which is not on the new list becomes permanently unable to send the tokens it already holds, even if it acquired them before the allow list existed.

### Finding Description
`MsgCreateDenom`/`MsgUpdateDenom` let the denom's admin set an `AllowList` via `SetDenomAllowList`, which is enforced on every subsequent transfer through `IsInDenomAllowList`/`getAllowedAddresses`: [1](#0-0) 

`UpdateDenom` requires only that `msg.Sender` equal the current denom admin (a role obtained simply by calling `MsgCreateDenom`, i.e. reachable by any unprivileged tokenfactory denom creator — no chain governance or validator action needed): [2](#0-1) 

Because `IsInDenomAllowList` is checked purely at send time against the coin's `AllowList`, it has no memory of when a holder acquired the balance. A user can:
1. Receive/hold `factory/{admin}/X` tokens while no allow list exists (any address may hold/send it).
2. The denom admin later calls `MsgUpdateDenom` with an `AllowList` that omits the holder's address.
3. The holder's existing balance in that denom can never again be sent from that address (test `TestSendSenderNotInAllowList` confirms the send is rejected with `"... is not allowed to send funds"`), and the tokens equally cannot be routed to any address not on the allow list. [3](#0-2)  demonstrates exactly this: a sender not present in the allow list is blocked from sending a balance they already hold.

This mirrors the UXD bug class precisely: a centralized party (denom admin) can retroactively restrict access to a whitelist, freezing balances that pre-date the restriction, with no protection for value already held by unprivileged users.

### Impact Explanation
Any tokenfactory denom admin — a role obtainable by any account simply by creating a denom — can permanently lock user funds denominated in that token by excluding their address from a later-set allow list. Because this is enforced unconditionally in `SendCoins`/`IsInDenomAllowList` with no way for the affected holder to appeal, transfer, or burn out (the allow-list gate blocks ordinary sends), this results in permanent freezing of funds for legitimate holders of that tokenfactory denom, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood is centered on token-factory-denom trust assumptions: any user who accepts or is airdropped a `factory/...` denom implicitly trusts that denom's admin not to retroactively allow-list them out. Since creating a denom and later calling `UpdateDenom` requires only a single signed transaction from the admin account (no governance, no validator collusion, no privileged network role), this is straightforward to trigger and is class Medium — the same severity given to the analogous UXD centralization finding — because it depends on the token issuer's action but produces concrete, permanent fund-freezing impact for third-party holders who have no way to opt out in advance.

### Recommendation
- When applying a new/updated `AllowList` via `UpdateDenom`, do not retroactively restrict addresses that already hold a non-zero balance of the denom (e.g., grandfather existing holders, or require they be included automatically).
- Alternatively, provide an unconditional exit path (e.g., allow burning or a time-locked withdrawal) for holders excluded by an allow-list update so a change in the admin's discretion cannot strand funds indefinitely.
- Document/enforce that `AllowList` changes cannot reduce reachability below existing non-zero balance holders without an explicit migration mechanism.

### Proof of Concept
1. Admin `A` creates denom `factory/A/X` with `MsgCreateDenom` (no allow list) and mints/sends some `factory/A/X` to holder `H`. [4](#0-3) 
2. `H` now holds `factory/A/X` freely — no allow list restricts it.
3. `A` calls `MsgUpdateDenom` on `factory/A/X` with `AllowList{Addresses: [A]}` (excluding `H`). This requires only `A`'s signature and passes `validateUpdateDenom`/`SetDenomAllowList`: [5](#0-4) 
4. `H` attempts `MsgSend` of its own `factory/A/X` balance to any address. The transaction fails via `IsInDenomAllowList` because `H` is not in the allow list, exactly as reproduced by `TestSendSenderNotInAllowList`: [3](#0-2) 
5. `H`'s balance is now permanently unspendable — there is no other message type that bypasses the allow-list check for a plain holder to move the funds out.

func (k BaseSendKeeper) SetDenomAllowList(ctx sdk.Context, denom string, allowList types.AllowList) {
	store := ctx.KVStore(k.storeKey)
	denomAllowListStore := prefix.NewStore(store, types.DenomAllowListKey(denom))

	m := k.cdc.MustMarshal(&allowList)
	denomAllowListStore.Set([]byte(denom), m)
}

func (k BaseSendKeeper) GetDenomAllowList(ctx sdk.Context, denom string) types.AllowList {
	store := ctx.KVStore(k.storeKey)
	store = prefix.NewStore(store, types.DenomAllowListKey(denom))

	bz := store.Get([]byte(denom))
	if bz == nil {
		return types.AllowList{}
	}

	var allowList types.AllowList
	k.cdc.MustUnmarshal(bz, &allowList)

	return allowList
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (server msgServer) CreateDenom(goCtx context.Context, msg *types.MsgCreateDenom) (*types.MsgCreateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.Keeper.CreateDenom(ctx, msg.Sender, msg.Subdenom)
	if err != nil {
		return nil, err
	}

	createDenomEvent := sdk.NewEvent(
		types.TypeMsgCreateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeNewTokenDenom, denom),
	)

	if msg.AllowList != nil {
		err = server.validateAllowList(ctx, msg.AllowList)
		if err != nil {
			return nil, err
		}
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		createDenomEvent = createDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		createDenomEvent,
	})

	return &types.MsgCreateDenomResponse{
		NewTokenDenom: denom,
	}, nil
}

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

func (k Keeper) validateUpdateDenom(ctx sdk.Context, msg *types.MsgUpdateDenom) (tokenDenom string, err error) {
	_, _, err = types.DeconstructDenom(msg.GetDenom())
	if err != nil {
		return "", err
	}
	_, found := k.bankKeeper.GetDenomMetaData(ctx, msg.GetDenom())
	if !found {
		return "", types.ErrDenomDoesNotExist.Wrapf("denom: %s", msg.GetDenom())
	}

	err = k.validateAllowList(ctx, msg.AllowList)
	if err != nil {
		return "", err
	}

	return msg.GetDenom(), nil
}
