Let me check how `data` is used in the transaction construction path.### Title
`SignableTransaction` under-estimates transaction vbytes when an OP_RETURN `data` output is present, producing an under-priced or non-relayable transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Zoth incident was a loss caused by an arithmetic error in collateral valuation — a formula that computed a value smaller than the true one. The reachable analog in Serai is in `SignableTransaction::new` / `calculate_weight_vbytes`, where the fee calculation models the transaction using only `payments` (and optionally `change`), while the actual transaction additionally includes an OP_RETURN output carrying up to 80 bytes of attacker-influenced `data`. The measured `vbytes` — and therefore `needed_fee` and the `TooLowFee` minimum-relay check — omit the data output entirely.

### Finding Description
In `SignableTransaction::new`, the `data` argument (up to 80 bytes, checked at send.rs:171) causes an extra `TxOut` to be pushed onto `tx_outs` at send.rs:194-202. However, the weight calculation at send.rs:204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds a model transaction containing only the payment outputs (send.rs:85-93) plus optionally `change` (send.rs:95-99). The OP_RETURN output is never included in the model. The same omission occurs in the change path at send.rs:225-226.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) is computed on a `vbytes` value ~10–91 bytes too small (OP_RETURN output = ~9 bytes overhead + script push of `data`).
2. The `TooLowFee` guard at send.rs:211 validates `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same understated `vbytes`, so a transaction can pass the check while its actual serialized size makes its real fee rate below the minimum relay rate.
3. `fee()` (send.rs:138-141) reports the true fee, but `needed_fee()` — the value consumers use to decide funding sufficiency — understates the requirement. If a change output is created, the change amount inherits the shortfall; if not, the overpayment is absorbed, but when `input_sat == payment_sat + needed_fee` exactly, the real fee rate is what was computed for a smaller transaction.

A caller supplying `data` near the 80-byte maximum obtains the maximal discrepancy (~91 weight-... vbytes ≈ 91 bytes at ~4 WU/byte for a non-witness output, so roughly 91 vbytes shortfall).

### Impact Explanation
- **Undocumented/miscounted fee ("collateral") calculation**: `needed_fee` is asserted to be the fee required to achieve the requested rate (send.rs:129-135), but it systematically undercharges whenever `data` is present — a direct arithmetic miscalculation like the Zoth bug class.
- **Relay failure**: when `fee_per_vbyte` is at/near the minimum relay rate and `data` is large, the produced transaction's actual sat/vbyte falls below `DEFAULT_MIN_RELAY_TX_FEE` despite passing the `TooLowFee` check, so Bitcoin nodes reject it from the mempool — an output/spend that was "computed valid" but cannot propagate. For burn/outbound transfers this can stall funds.
- **Reduced change**: when change is created, the true fee exceeds the accounted fee, silently burning extra satoshis relative to `needed_fee`.

Severity: Medium — concrete, reachable by whoever controls the `data`/`payments`/`fee_per_vbyte` parameters of `SignableTransaction::new` (the processor constructs these for outbound/burn transactions), but the impact is capped at fee mispricing and potential relay failure rather than key compromise.

### Likelihood Explanation
`SignableTransaction::new` is the canonical Bitcoin send path used by the processor (`processor/src/networks/bitcoin.rs` calls it). The bug triggers deterministically on any call with `data: Some(_)` — no race or adversarial peer needed. Exploiting the relay-rejection edge additionally requires a low `fee_per_vbyte` and near-maximal `data`, which depends on integrator/policy values, but the fee miscount itself fires every time.

### Recommendation
Include the OP_RETURN output in the fee model. Either pass the fully-constructed output list (including the data output) into `calculate_weight_vbytes`, or add a `data_len` parameter so the model emits a matching `ScriptBuf::new_op_return` output. Apply the same fix in both call sites (send.rs:204 and send.rs:225-226). Optionally recompute `vbytes` after change insertion and re-check `TooLowFee` against the final `weight`.
