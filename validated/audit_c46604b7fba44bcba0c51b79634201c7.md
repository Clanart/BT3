### Title
Cached FROST preprocess (nonce seed) reused across signing contexts via `CachedPreprocesses` keyed only by `(b"DkgConfirmer", attempt)` - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Cover bug computed rewards from stale cached state instead of fresh values. The Serai analog is in `SigningProtocol::preprocess_internal` (`coordinator/src/tributary/signing_protocol.rs:100-148`): FROST preprocesses are deterministically derived from a cached 32-byte seed stored in `CachedPreprocesses`, keyed solely by `context`. For `DkgConfirmer`, the context is `(b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:275`) — it does not include the validator set, the tributary genesis, or the message being signed. Whenever the same context value recurs while the signed message or participant set differs, `AlgorithmSignMachine::from_cache` regenerates the identical nonces (`crypto/frost/src/sign.rs:121-144`) and produces a second signature share under the same nonce — the classic FROST nonce-reuse/key-share-recovery failure that the code comments themselves warn about (`signing_protocol.rs:104-106`, `sign.rs:85-87`).

### Finding Description
`preprocess_internal` writes `CachedPreprocesses::set(txn, &context, &seed)` once per context and then always loads it back and calls `seeded_preprocess(seed)`, which runs `ChaCha20Rng::from_seed(seed)` → `Commitments::new` → deterministic nonces (`sign.rs:127-133`). Two distinct paths make the cached data stale relative to what is actually signed:

1. **Cross-set context collision.** `DkgConfirmer::signing_protocol` builds `context = (b"DkgConfirmer", self.attempt)` with no `spec.set()`/genesis binding (`signing_protocol.rs:275`). The DB txn passed into `DkgConfirmer::new` is shared — note that unrelated state is disambiguated inside the same txn by explicitly keying on `spec.genesis()` (e.g., `removed_as_of_dkg_attempt(txn, spec.genesis(), attempt)` at `signing_protocol.rs:271`), which shows the transaction/DB outlives a single tributary. On the next validator-set rotation, `attempt` restarts at 0, the same `(b"DkgConfirmer", 0)` context hits the stale cached seed, and identical nonces are used to sign a different `set_keys_message` (which commits to the new `set` and `key_pair`, `signing_protocol.rs:296-300`).

2. **Same-context, different message/set.** `share()` and `complete()` both call `share_internal` → `preprocess_internal`, which deterministically rebuilds the same nonces (`signing_protocol.rs:156`, `321-324`). The signed message is a function of caller-supplied `key_pair` and the `preprocesses` map (which determines `included` and the binding factors, `sign.rs:283-371`). If `share` is ever invoked twice under one attempt with a different `key_pair` or a different signer set — which the API does not prevent — the second share is computed with stale cached nonce data over a different challenge, leaking `d + e·ρ` combinations that allow solving for the secret share, exactly the "share reuse" scenario FROST's binding factors exist to prevent.

### Impact Explanation
Reuse of a FROST nonce across two distinct challenges yields two equations `share_i = d + e·ρ_i·x` (plus offset terms) in the secret share `x`; an observer of the public signature shares/signatures recovers the validator's MuSig/FROST secret share. With `t` compromised shares the tributary threshold key (`Ristretto`/`Schnorrkel`, the Substrate-facing key pair) is fully recoverable, enabling forged `set_keys` confirmations and arbitrary signatures by the validator set. This maps to the accepted impact class "key share recovery / signing of an unintended message." Severity: Critical.

### Likelihood Explanation
The vulnerability triggers on ordinary protocol flow — validator set rotation resets `attempt` while the shared DB retains `CachedPreprocesses` entries, and the stale-seed path is hit automatically since `preprocess_internal` unconditionally prefers the cache (`signing_protocol.rs:123-145`). No malicious validator, collusion, or leaked key is required: any observer of the two broadcast signature shares (which are public protocol messages) can perform the recovery. The only uncertainty is whether the `DbTxn` is strictly per-genesis; the code's own convention of keying other entries by `spec.genesis()` inside the same txn indicates it is not. I was unable to fully trace `handle.rs`/`main.rs` DB scoping before finalizing, so that is the residual assumption.

### Recommendation
Bind the cache key to everything the preprocess must be unique for: include `spec.genesis()`/`set`, the participant set (`removed`), and the message (or key pair) digest in `context`, e.g. `(b"DkgConfirmer", spec.genesis(), attempt, Blake2s256(msg))`. Additionally, delete (`CachedPreprocesses::kill`) the entry once a share has been produced for that context rather than keeping it for the lifetime of the DB, and assert in `share_internal` that the machine was not already consumed for an identical context with different inputs.

### Proof of Concept
```
1. Set N completes DKG confirmation attempt 0.
   - DkgConfirmer::preprocess -> preprocess_internal((b"DkgConfirmer", 0))
   - seed S cached under key (b"DkgConfirmer", 0); nonces (D,E) derived; share over msg_0 = set_keys_message(set_0, removed_0, kp_0).

2. Validator set rotates; new tributary genesis, attempt resets to 0.
   - DkgConfirmer::new(txn, spec_1, attempt = 0) -> same context key.
   - CachedPreprocesses::get(txn, (b"DkgConfirmer", 0)) returns stale S.
   - from_cache regenerates identical (d, e) nonces; node signs
     msg_1 = set_keys_message(set_1, removed_1, kp_1) with same nonces.

3. Attacker collects both public shares/signatures:
   s_0 = d + e·rho_0 + c_0·lambda·x    s_1 = d + e·rho_1 + c_1·lambda·x
   (rho_i, c_i publicly computable from the FROST transcripts, sign.rs:361-379)
   -> two linear equations -> solve for x = secret share.

4. Repeating across t validators yields the full threshold private key.
```

Supporting code: `coordinator/src/tributary/signing_protocol.rs:86-148` (cache keying and reuse), `:274-301` (context without set/message binding), `:312-327` (`complete` re-deriving the same nonces); `crypto/frost/src/sign.rs:121-144` (deterministic `seeded_preprocess`), `:361-379` (rho/challenge transcript enabling the linear solve).
