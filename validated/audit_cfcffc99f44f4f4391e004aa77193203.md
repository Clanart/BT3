## Title
Zero-amount ERC20 transfer not short-circuited in the CW20-wrapper-for-ERC20 contract can permanently strand tokens transferred via `Send`/`SendFrom` for non-standard ERC20s - (File: `example/cosmwasm/cw20/src/contract.rs`)

### Summary
The CW20 wrapper contract that exposes an arbitrary EVM ERC20 token as a CW20 token (embedded as `x/evm/artifacts/erc20/cwerc20.wasm`, built from the `example/cosmwasm/cw20` source) always issues an unconditional `DelegateCallEvm` to the wrapped ERC20's `transfer`/`transferFrom` selector, even when `amount == 0`. Sei explicitly anticipated and hardened this exact bug class in its own Go precompiles (`precompiles/bank/**/bank.go` all short-circuit on `amount.Cmp(utils.Big0) == 0`), but the CW↔EVM `cw20`-wrapper transfer path was never given the same treatment. If the wrapped token is a non-standard ERC20 that reverts on a zero-value `transfer`/`transferFrom` (a known real-world pattern, e.g. LEND), any CW20 `Send`/`SendFrom`/`Transfer`/`TransferFrom` message with `amount = 0` unconditionally reverts, matching the exact bug class described in the GoldLink report (`syncAndAccrue`, `repay`, `borrowAssets`, `executeWithdrawErc20Assets` all missing zero checks before an ERC20 transfer call).

### Finding Description
`transfer()` and `transfer_from()` in `example/cosmwasm/cw20/src/contract.rs` build an EVM delegate-call payload for the wrapped ERC20's `transfer`/`transferFrom` and always append it via `add_message`, with no check on `amount`: [1](#0-0) [2](#0-1) 

These are called unconditionally from `execute_transfer`, `execute_send`, `execute_transfer_from`, and `execute_send_from`: [3](#0-2) [4](#0-3) 

The resulting `EvmMsg::DelegateCallEvm` is sent to `erc_addr`, the arbitrary user-supplied ERC20 token address stored at instantiation (`ERC20_ADDRESS.load`), so the wrapper has no control over the token's implementation: [5](#0-4) 

This is the same root cause pattern as the GoldLink report: several functions ( `syncAndAccrue`, `borrowAssets`, `repay`, `executeWithdrawErc20Assets`) unconditionally forward a possibly-zero amount into an ERC20 transfer call, and some tokens revert on a zero-value transfer, causing unrelated logic bundled in the same transaction/flow to fail.

By contrast, sei-chain's own Go-side bank precompile explicitly guards against this exact scenario for native/pointer sends: [6](#0-5) 

The same short-circuit pattern is duplicated across every legacy precompile version (`v552`, `v555`, `v562`, `v580`, `v600`, `v601`, `v603`, `v605`, `v606`, `v630`, `v640`, `v65`, `v66`, `v67`), demonstrating the team is well aware that zero-amount transfers to externally-controlled token logic must be special-cased — but this awareness was not extended to the CW20-wrapper-for-ERC20 contract, which is precisely the pointer/bridge component that talks to arbitrary, attacker- or third-party-supplied ERC20 tokens.

### Impact Explanation
Any Cosmos-side contract or user that issues a `Send`/`SendFrom` CW20 message with `amount = 0` against a CW20-wrapped ERC20 that reverts on zero transfers will have the entire wasm execution (and any batched sub-messages, e.g. a `Cw20ReceiveMsg` callback into a receiving contract) revert. If this zero-amount transfer is a byproduct of downstream accounting in another CosmWasm contract (e.g., a reward/fee-splitting contract that computes a proportional/leftover transfer that can legitimately be zero, similar to GoldLink's `returnedLoan == 0` liquidation case), that contract's multi-step flow — potentially including fund-moving logic that is bundled in the same message and can't be retried once state elsewhere has advanced — can become permanently stuck for that wrapped ERC20 token whenever the zero-amount case is hit, since the CW20 wrapper itself has no way to be patched to special-case the zero transfer without a contract migration. This matches "permanent freezing of funds" via a bridge/pointer path reachable from any wasm message sender, which is in-scope per the validation rules (CW<->EVM pointers and the wasm bridge).

### Likelihood Explanation
Likelihood depends on whether the wrapped ERC20 belongs to the (documented, real-world) class of tokens that revert on `transfer(_, 0)` — the report explicitly cites LEND on mainnet as a known instance of this behavior. On Sei, any user can deploy an arbitrary ERC20 and register/mint a CW20 wrapper pointer for it via the pointer registration flow, so an attacker or an unwitting integrator can create this condition with a token they choose. Any subsequent CW20-side contract that computes a transfer amount that can legitimately be zero (rounding to zero, full-repayment/zero-remainder cases, dust) will trigger the revert deterministically once that code path is hit — this requires no privileged access, only a standard wasm execute message.

### Recommendation
In `example/cosmwasm/cw20/src/contract.rs`, short-circuit `transfer()` and `transfer_from()` (and by extension `execute_send`/`execute_send_from`) to return successfully without emitting the `DelegateCallEvm` message when `amount.is_zero()`, mirroring the pattern already used in `precompiles/bank/bank.go`'s `send()` (`amount.Cmp(utils.Big0) == 0` → short-circuit and return success). Rebuild and re-embed the corresponding `cwerc20.wasm` artifact used by `x/evm/artifacts/erc20`.

### Proof of Concept
1. Deploy (or use) an ERC20 token on the Sei EVM whose `transfer`/`transferFrom` implementation reverts when `amount == 0` (mirroring LEND's behavior from the original report).
2. Register a CW20 pointer/wrapper for that ERC20 (creating an instance of the `cw20`-wrapper contract with `ERC20_ADDRESS` set to the token).
3. From any account, submit a `MsgExecuteContract` against the CW20 wrapper with `{"transfer": {"recipient": "<addr>", "amount": "0"}}` (or `send`/`transfer_from`/`send_from` with `amount = "0"`).
4. Observe that `transfer()`/`transfer_from()` unconditionally builds and forwards the `DelegateCallEvm` transfer payload regardless of amount, causing the underlying EVM call — and therefore the entire wasm execution — to revert, exactly as in the Foundry PoC from the source report where `deposit(500)` on a zero-interest-accrual path or a zero-value transfer causes the whole transaction to fail.

```rust
fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}
```

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}
