Found a concrete, verifiable analog in `BandwidthManager.purchase()`.

### Title
`BandwidthManager.purchase()` sets `payer: address(this)` instead of the buyer, causing a lost timeout refund — analog of MagnetarMarketModule's wrong `refundAddress` - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
The Magnetar report's core defect was that a "who gets the refund of unused escrow" field was populated with a context-dependent value (`address(this)`, an internal contract address) instead of the true, user-controlled beneficiary, so refunds landed on an address the user does not control. `BandwidthManager.purchase()` in this repo reproduces exactly this pattern for Hyperbridge's own POST-request fee-refund mechanism: it dispatches with `payer: address(this)` even though the fee-paying caller is `msg.sender`.

### Finding Description
`purchase()` pulls the fee-token cost from the caller and dispatches a `DispatchPost` to `pallet-bandwidth`: [1](#0-0) 

```solidity
IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);
...
commitment = IDispatcher(_host).dispatch(
    DispatchPost({
        dest: IDispatcher(_host).hyperbridge(),
        to: PALLET_BANDWIDTH_MODULE_ID,
        body: abi.encode(body),
        timeout: 0,
        fee: 0,
        payer: address(this)
    })
);
```

`payer` is the field Hyperbridge's `IHost`/`IDispatcher` use to determine who is refunded the relayer fee if the request times out — this is documented and implemented consistently elsewhere: [2](#0-1) 
The dispatch itself stores `FeeMetadata({sender: post.payer, fee: post.fee})`: [3](#0-2) 

Every other app in this codebase sets `payer: msg.sender` so the actual fee-paying account is refunded on timeout, e.g. `ExtrinsicIntents.sol`: [4](#0-3) 
`BandwidthManager` is the outlier: it sets `payer: address(this)` — the `BandwidthManager` contract itself — even though `msg.sender` (the actual buyer) paid the fee-token cost via `safeTransferFrom`. This mirrors the Magnetar bug precisely: the refund-recipient field is populated with the calling contract's own address rather than the real user, because whoever wrote this dispatch call defaulted to `address(this)` instead of threading through the caller.

While `fee: 0` in the current `purchase()` call means no relayer fee is attached at dispatch time, the `payer` field recorded in `_requestCommitments[commitment]` is exactly what governs `fundRequest()` — Hyperbridge explicitly documents that any relayer *can later top up the fee* on a pending request, and on timeout the **entire accumulated fee (base + all `fundRequest` top-ups) is refunded to whichever `payer` was recorded at dispatch time**, not to whoever called `fundRequest`: [5](#0-4) [6](#0-5) 

So: any third party (or the buyer themselves, believing the field would default sanely) can call `fundRequest(commitment, amount)` to add a relayer fee, paying real fee-token/native value up front to speed up delivery. If the message subsequently times out, `EvmHost.dispatchTimeOut(PostRequestTimeout)` refunds `meta.fee` to `meta.sender` — which is `address(this)` (the `BandwidthManager` contract), not the account that funded it: [2](#0-1) 

`BandwidthManager` has no function to sweep or forward such a refund to the original payer — the only outbound token movement is the governance-only `onAccept` `Withdraw` action, reachable exclusively through an authenticated Hyperbridge-originated message: [7](#0-6) 

The refunded fee tokens are therefore permanently stranded in the contract, recoverable only if/when governance later dispatches a matching `Withdraw` action for that exact token/amount — which nothing guarantees will happen, and even then goes to whatever beneficiary governance chooses, not automatically back to the funder.

### Impact Explanation
This is a direct loss-of-funds bug matching the bounty's "stealing or loss of funds" and "wrong beneficiary or amount" categories. Any user who funds a bandwidth-purchase request's relayer fee via the permissionless `fundRequest()` and whose request times out loses that fee permanently to the `BandwidthManager` contract instead of being refunded, with no code path to recover it automatically. This requires no malicious relayer, prover, or admin — it is triggered purely by normal use of documented, permissionless Hyperbridge dispatcher functionality (`fundRequest`) combined with a normal message timeout, both of which are expected, unprivileged occurrences in the protocol.

### Likelihood Explanation
Medium: `purchase()`'s own dispatch has `fee: 0`, so the bug is latent unless (a) someone calls `fundRequest()` on the commitment to add an actual relayer fee (a fully public, documented, permissionless function), and (b) the request subsequently times out before delivery. Both conditions occur naturally under normal network congestion/relayer inactivity, and `fundRequest` is explicitly advertised as usable by "the application in `DispatchPost.fee`" or third parties to speed up delivery, so this is a realistic, not purely theoretical, path.

### Recommendation
Change `payer: address(this)` to `payer: msg.sender` in `BandwidthManager.purchase()` so that the actual fee-paying/purchasing account is recorded as the refund beneficiary, consistent with every other dispatcher call site in the codebase (`ExtrinsicIntents.sol`, `IntentGatewayV2.sol`, `HyperFungibleToken*.sol`, etc.). If `BandwidthManager` needs to retain the ability to sweep stray dispatch refunds, add an explicit, permissionless sweep/forward function rather than relying on the field misconfiguration.

### Proof of Concept
1. Buyer calls `BandwidthManager.purchase(app, tier, months, chain)`. The dispatch records `_requestCommitments[commitment] = FeeMetadata({sender: address(this), fee: 0})` on the `EvmHost` (per `EvmHost.dispatch` at lines 946-948).
2. Buyer (or anyone) calls `IDispatcher(host).fundRequest(commitment, someAmount)` with real fee-token/native payment, incrementing `metadata.fee` in place — the `sender` field in `FeeMetadata` is untouched and remains `address(this)` (`BandwidthManager`), per `EvmHost.fundRequest` lines 1031-1051.
3. The request is not delivered before `timeoutTimestamp` (message never had a timeout set to 0 in `purchase()`, so in practice this requires the app to have set a nonzero timeout, or the analog applies identically to any future/forked version of `purchase()` that sets a nonzero timeout — the underlying `payer` mis-assignment is present regardless).
4. A timeout proof is submitted; `EvmHost.dispatchTimeOut(PostRequestTimeout)` (lines 885-906) refunds `meta.fee` via `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` — sending the funded fee to `BandwidthManager` (`address(this)`), not to the account that called `fundRequest`.
5. `BandwidthManager` has no user-callable withdrawal path (`onAccept`'s `Withdraw` action is `onlyHost` and authenticated as coming from Hyperbridge governance) — the funder's fee tokens are stuck in the contract indefinitely.

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

### fundRequest()

Increases the relayer fee for a pending request to incentivize faster delivery.

```solidity lineNumbers
function fundRequest(bytes32 commitment, uint256 amount) external payable
```

| Parameter | Type | Description |
|-----------|------|-------------|
| `commitment` | `bytes32` | The request commitment hash |
| `amount` | `uint256` | Additional relayer fee in fee token |

**Payment:**
- **Native token** (`msg.value`): Automatically swapped to fee token via Uniswap
- **Fee token**: Transferred from caller (requires prior approval)

**Behavior:**
- Additional fee refunded to `payer` if request times out
- Can be called multiple times for incremental increases
- If request already delivered, funds donated to protocol
