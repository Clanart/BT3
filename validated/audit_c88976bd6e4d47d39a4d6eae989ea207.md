### Title
Stale per-path manual conflict resolutions are silently replayed onto unrelated conflicts in a multi-commit rebase - (File: `app/src/lib/git/rebase.ts`, `app/src/lib/stores/updates/changes-state.ts`)

### Summary
This is the same "unresolved-state" bug class as the Paladin finding: a per-key value (`userCurrentBonusRatio`/`durationRatio` there, `ManualConflictResolution` here) is never reset when the context that produced it goes away, so it gets reapplied under different, wrong circumstances. In Desktop, `manualResolutions` is a `Map<filePath, 'ours'|'theirs'>` that is threaded, unmodified, through an entire multi-commit rebase. When a later commit in the same rebase re-conflicts on a path the user already resolved earlier in the same operation, Desktop reuses the old resolution for that path without re-prompting the user or checking that the conflict content is the same one that was originally reviewed.

### Finding Description
`updateConflictState` carries the existing `manualResolutions` `Map` forward unchanged as long as the conflict "kind" doesn't change (`rebase` → `rebase`), independent of which commit (`currentTip`) is currently being replayed: [1](#0-0) 

That same `Map` is forwarded verbatim from one rebase step to the next by the UI layer: [2](#0-1) 

and finally applied in `continueRebase` purely by string-matching the file path, with no check that the conflict being resolved now is the same conflict the user reviewed when they picked "ours"/"theirs": [3](#0-2) 

`stageManualConflictResolution` just runs `git checkout --ours/--theirs -- path` and stages it, blind to content: [4](#0-3) 

The regression tests explicitly confirm this is intentional "preserve resolutions across the same rebase" behavior, but they only validate the *legitimate* case where the SHA state is consistent — nothing in the tests or the implementation checks whether a *later* conflict on the same path is the same conflict: [5](#0-4) 

### Impact Explanation
An attacker who controls the branch being rebased (a fetched PR/remote branch, entirely attacker-authored history) can craft a sequence of commits that:
1. Touch a given file path with a conflict the user will resolve manually (e.g. via "ours"/"theirs") in an early commit.
2. Touch the *same* file path again in a later commit in the same rebase, with completely different/malicious content, producing a fresh conflict.

Because the `manualResolutions` map is keyed only by path and never invalidated between rebase steps, Desktop's `continueRebase` will automatically apply the earlier resolution to the new, unrelated conflict — without showing the user the conflict-resolution UI for it. This silently corrupts what the user commits/pushes: attacker content can be silently staged (if "theirs" was chosen earlier) or the user's own conflicting resolution intent can be silently discarded, without any indication in the UI that a second, different conflict was auto-resolved.

### Likelihood Explanation
This requires a normal, expected Desktop workflow (rebasing a fetched/attacker-authored branch that conflicts more than once on the same path) and no local/admin access, no prior malware, and no social engineering beyond the user performing a routine rebase — squarely in scope. It is somewhat conditional: it requires (a) a rebase with 2+ conflicting commits, and (b) both conflicts touching the same path — a realistic pattern in a hostile, deliberately crafted branch, though not guaranteed on every rebase, which is comparable to the "external circumstances required" reasoning that kept the original Paladin bug at Medium rather than High. I was not able to fully verify, within the available index, whether any downstream code in `app-store.ts` deletes/clears a path's entry from `manualResolutions` immediately after it is applied by `continueRebase` (which would mitigate this); the grep only confirmed 31 references without letting me inspect each call site's logic, so this should be verified before treating the impact as certain.

### Recommendation
Do not key manual resolutions purely by file path across the lifetime of a multi-commit operation. Either:
- Clear the resolution for a path from `manualResolutions` immediately after it is consumed in `continueRebase` (mirroring "set to zero" in the Paladin fix), forcing the user to re-resolve if the same path conflicts again, or
- Bind the resolution to a content identity (e.g. the conflicted blob OIDs for `us`/`them`) rather than just the path, so a stale resolution is never silently replayed against different content.

### Proof of Concept
1. Attacker pushes/hosts a branch with two commits, both modifying `config.json`, each producing a merge conflict with the target branch, but with different malicious payloads in the second commit.
2. Victim rebases their branch onto/with the attacker branch in Desktop; the first conflict on `config.json` is shown, victim manually resolves via "Use theirs".
3. Desktop calls `continueRebase`, which stores `manualResolutions.set('config.json', theirs)` in the `RebaseConflictState` and forwards it via `base-rebase.tsx` (`conflictState.manualResolutions` at `base-rebase.tsx:44`) unchanged to the next step.
4. The rebase advances to the second attacker commit, which again conflicts on `config.json`. Because `updateConflictState` reuses `prevConflictState.manualResolutions` (`changes-state.ts:270-273`), and `continueRebase` matches purely on `file.path === path` (`rebase.ts:449-450`), it silently re-applies "theirs" and stages the attacker's new malicious `config.json` content without ever showing the second conflict to the user.
5. The rebase completes; the victim commits/pushes the malicious content believing all conflicts were manually reviewed.
