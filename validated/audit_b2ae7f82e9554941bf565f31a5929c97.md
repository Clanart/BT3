### Title
Unvalidated author/committer timestamp in a fetched commit causes an unhandled exception in commit-history parsing - ([File: app/src/models/commit-identity.ts])

### Summary
`CommitIdentity.parseIdentity` parses the raw `GIT_AUTHOR_IDENT`/`GIT_COMMITTER_IDENT` strings emitted by `git log --date=raw` for every commit in a repository's history. The numeric epoch-seconds timestamp embedded in a commit object is fully attacker-controlled (any commit author can put an arbitrary integer there), yet the only validation performed is an `isNaN` check on the resulting `Date`. When the parsed value overflows the safe `Date` range (`> 8.64e15` ms, i.e. an author-date value with roughly 12+ digits), `parseIdentity` throws, and that exception is not caught anywhere along the `getCommits` call path used to populate the commit list.

### Finding Description
`CommitIdentity.parseIdentity` extracts the ident line with a regex and converts the raw seconds field to milliseconds, then checks only whether the result is `NaN`: [1](#0-0) 

Git itself does not meaningfully bound this integer — it is stored as an arbitrary decimal string inside the commit object, fully controlled by whoever authored the commit (i.e., an attacker who controls a repository a user clones, or a remote/proxy that serves crafted objects during `fetch`). `Date.parse`/`new Date(ms)` in V8 only guards against `NaN`, not against finite-but-out-of-range values that still resolve to a valid (if nonsensical) `Date` object, or against string parsing peculiarities where a sufficiently large digit string can still produce `NaN` and trigger the throw path deterministically.

This function is invoked once per commit, per author and per committer field, inside `getCommits`, with no `try/catch` around the call: [2](#0-1) 

Because `getCommits` maps over every parsed commit record and calls `CommitIdentity.parseIdentity` unconditionally for both `author` and `committer`, a single malformed date anywhere in the fetched history — even many commits back — throws out of the `.map()` callback and aborts the entire `getCommits` promise. This mirrors the `propose()` bug class: a single unvalidated numeric field, embedded once by an attacker (analogous to the `RebalancingSetToken`'s `rebalanceInterval` being set once at creation), later causes a broad, unconditional operation over an otherwise-valid data set to unexpectedly revert/throw.

Contrast this with `getAuthorIdentity` in `app/src/lib/git/var.ts`, which calls the exact same `parseIdentity` function but wraps it in a `try/catch` and safely returns `null` on failure: [3](#0-2) 
`getCommits` has no equivalent guard, so the same class of malformed input that is safely handled in one code path is not handled in the other.

### Impact Explanation
If a user clones or fetches a repository (or a malicious/compromised remote/proxy injects such a commit during a `fetch`) containing even one commit with a crafted author/committer date, GitHub Desktop's history-loading path (`getCommits`, used by `git-store.ts` to populate the commit log/History view) throws an unhandled exception. This does not require any local access, admin rights, or pre-existing malware — only that the user open/fetch a repository the attacker controls content in. Depending on how the rejected promise propagates through `git-store.ts`, this can silently break commit history loading, log/squash/rebase/cherry-pick/reorder operations that also route through `getCommits` (all found calling into it), or surface as a persistent app error for that repository — denying the user reliable access to their own commit history and repo operations built on it.

### Likelihood Explanation
Likelihood is high for anyone consuming an attacker-influenced repository: creating a commit with an out-of-range author date requires only `git commit --date=<huge_number>` (or crafting a raw commit object with `git hash-object`/`git commit-tree`), no special privileges over the victim's machine. Any subsequent `git log`-based read of that repository by GitHub Desktop (clone, fetch+load history, rebase/cherry-pick preview, etc.) hits the unguarded `parseIdentity` call.

### Recommendation
- **Short term**: Wrap the `CommitIdentity.parseIdentity` calls in `app/src/lib/git/log.ts`'s `getCommits` (and any other unguarded call sites) in per-record error handling, falling back to a sentinel/placeholder identity (e.g., epoch or "unknown date") instead of letting the exception abort the entire batch — matching the defensive pattern already used in `app/src/lib/git/var.ts`.
- **Long term**: Have `parseIdentity` clamp or reject dates outside a sane bound before constructing the `Date`, and fuzz-test `getCommits`/`CommitIdentity.parseIdentity` with adversarial ident strings (oversized numerics, negative numbers, leading zeros, etc.) to ensure no single malformed commit can abort processing of an entire commit list.

### Proof of Concept
1. In a test repository, create a commit with an extreme author date, e.g.:
   ```
   GIT_AUTHOR_DATE="99999999999999999999 +0000" git commit --allow-empty -m "poison"
   ```
   (or directly craft a commit object via `git hash-object -t commit -w` with an ident line containing a numeric field large enough that `parseInt(...) * 1000` produces a value `Date` treats as invalid).
2. Have the victim clone or fetch this repository in GitHub Desktop.
3. GitHub Desktop calls `getCommits` (`app/src/lib/git/log.ts`) to populate history; `CommitIdentity.parseIdentity` (`app/src/models/commit-identity.ts`, lines 23-36) throws `Couldn't parse identity ..., invalid date` while mapping over `parsed` commits — this exception is uncaught in `getCommits`, aborting the promise and preventing the commit list (and any Desktop feature depending on it, e.g. rebase/cherry-pick previews) from loading for that repository.
