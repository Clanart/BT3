### Title
upb `upb_EpsCopyInputStream_ReadStringEphemeral()` can expose stale patch-buffer bytes as string field content before the length-overrun is detected - ([File: upb/wire/eps_copy_input_stream.h])

### Summary
The upb wire decoder's `upb_EpsCopyInputStream_ReadStringEphemeral()` deliberately skips a bounds check "for efficiency" and, when an attacker-supplied length-delimited field size extends past the real end of the input, returns a pointer/length pair that can point into the decoder's internal "patch buffer" containing bytes left over from earlier decoding state rather than any byte the attacker actually sent. This is analogous to the bnxt_re bug: a shared/reused buffer is handed to a consumer based on an attacker-controlled length before the buffer's full extent has been validated or its unwritten region cleared, and only part of the region is guaranteed to correspond to real, checked data.

### Finding Description
`upb/wire/eps_copy_input_stream.h` documents the contract of the ephemeral-string read path used by upb's binary wire decoder when handling `TYPE_STRING`/`TYPE_BYTES` (and other length-delimited) fields: [1](#0-0) 

The comment states verbatim that the function does not verify `size` against the current limit or stream end "for efficiency", and that consequently the returned `upb_StringView` "may contain garbage bytes from the patch buffer" — i.e. leftover, unrelated memory contents from the decoder's internal scratch/slop buffer, not attacker-supplied bytes — and that this "may result in nonsense bytes ending up in the output." The error is only detected afterward, when `upb_EpsCopyInputStream_IsDone()` is checked.

This mirrors the CVE's failed invariant precisely:
- **Attacker-controlled value**: the declared byte-length of a string/bytes field in the wire-format varint length prefix, exactly like the AVID-adjacent offset in bnxt_re's shared page is a controllable index into memory the kernel exposes.
- **Missing check**: the function intentionally omits the size/limit check at the point the buffer region is handed out, deferring validation to a later, separate call (`IsDone()`), just as bnxt_re wrote 4 bytes and left the rest of the page unvalidated/unzeroed before `vm_insert_page()` exposed the full page.
- **Impact**: the caller (a upb decoder frontend, e.g. the fast-table string field decoder) receives a `upb_StringView` whose bytes are not guaranteed to originate from the parsed input — they can be stale bytes from a different, unrelated earlier use of the same patch buffer (potentially containing leftover data from a prior message, prior field, or other library state that occupied that scratch region).

### Impact Explanation
If any consumer of `upb_EpsCopyInputStream_ReadStringEphemeral()` (or the "AlwaysAlias" variant) copies out, logs, or otherwise surfaces the string view content to the application layer before the top-level `IsDone()`/overall-parse-success check is performed and enforced by the caller, an ordinary client sending a bounded, malformed Protobuf binary message with a truncated/over-length string field could cause the server process to briefly hold and potentially propagate bytes it never sent — a heap/stack memory-disclosure primitive structurally identical to the kernel CVE's mmap'd shared-page leak, except mediated through a decoded field value instead of a page mapping.

The severity is bounded by the fact that upb's documented contract requires the overall decode to fail (`upb_Decode`/`ParseFromString` returns an error) once `IsDone()` detects the mismatch, so a fully-conformant caller that only trusts the return value of the top-level parse call and discards the message on failure would not observe the garbage bytes. The real exposure surface is therefore any code path (fast-table decoders in `upb/wire/decode_fast/field_string.c`, or any Any/lazy field/streaming consumer) that reads or forwards the ephemeral view eagerly, before the final decode status is checked — a pattern this checkout's index did not let me fully trace to confirm whether such an early-observation path exists in the shipped fast decoder.

### Likelihood Explanation
Triggering the underrun condition itself is trivial and fully within the attacker's threat model: it requires only sending a bounded ProtoJSON/binary message through the public parse API with a string/bytes field length prefix that claims more bytes than are actually available in the buffer — no privileged access, hostile schema, or malformed MiniTable is needed. What remains unverified (and what would need dynamic confirmation, e.g., inside a Devin session with full repo/tooling access) is whether any in-tree consumer of the ephemeral API observes/propagates the view prior to the final `IsDone()` check, since that determines whether the documented "nonsense bytes" ever reach observable behavior rather than being silently discarded on parse failure.

### Recommendation
- Audit every call site of `upb_EpsCopyInputStream_ReadStringEphemeral()` / `upb_EpsCopyInputStream_ReadStringAlwaysAlias()` (notably `upb/wire/decode_fast/field_string.c`) to confirm none of them copy, log, or otherwise expose the returned `upb_StringView` before the decoder's overall success/`IsDone()` check is enforced.
- If any such early-observation path exists, either move the bounds check before returning the view (accepting the performance cost) or ensure the patch buffer is always zeroed/poisoned between uses so an out-of-bounds read cannot yield contents from an unrelated prior operation.
- Add a regression test that decodes a message whose string field length exceeds the available input and asserts that no bytes beyond the actual input are ever observable through any public or internal API prior to the parse failure being surfaced.

### Proof of Concept
I could not execute a live reproduction in this environment (read-only ask-mode, no code execution). A concrete PoC to be run in a full Devin session:
1. Build a minimal upb-based decoder for a trusted `.proto` schema containing a `string` field.
2. Construct a hand-crafted binary payload whose string field's varint length prefix exceeds the number of bytes actually present in the buffer, calling `upb_Decode` directly against `upb_EpsCopyInputStream_ReadStringEphemeral` (or via the fast-table string decoder) with instrumentation/ASan on the patch buffer to observe whether the returned `upb_StringView.data`/`.size` ever exposes bytes from a previous, unrelated buffer use before the top-level decode returns an error.
3. Confirm whether `upb_Decode`'s return value (or `IsDone()`) is checked/enforced by the fast-path consumer before any use of the view, per the caveat above.

Given the caveat above — that upb's documented contract routes this scenario to an overall decode failure via `IsDone()` — I present this as the strongest structural analog found in this checkout, but flag that confirming actual exploitability (an observable disclosure prior to parse-failure detection) requires further tracing of `decode_fast/field_string.c` and `decode.c` that exceeded the available tool budget in this session.
