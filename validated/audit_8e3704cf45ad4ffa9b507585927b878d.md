### Title
Reward doubling in `incentiveDeposit` bypasses the MGP balance cap enforced in `getRewardAmount` - (File: wombat/ArbWomUp3.sol)

### Summary
`getRewardAmount()` caps `mgpReward` to `IERC20(mgp).balanceOf(address(this))` before returning it, but `incentiveDeposit()` doubles that already-capped value when `_mode == 2`, so the amount subsequently approved and passed to `vlMGP.lockFor()` can exceed the contract's actual MGP balance. The balance check that is supposed to guarantee solvency is performed before the multiplier is applied instead of after, defeating its purpose.

### Finding Description
In `getRewardAmount`, the reward is computed from the user's WOM/mWomSV tier and locked amount, then explicitly clamped: [1](#0-0) 

`incentiveDeposit` calls this clamped value and then, for `_mode == 2`, multiplies it by 2 with no re-check against the contract's MGP balance: [2](#0-1) 

It then approves and locks this post-doubling, unclamped figure: [3](#0-2) 

An unprivileged caller reaches this path simply by calling `incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` with WOM tokens they hold (bought on market), and choosing `_amount`/`_convertRatio` such that `getRewardAmount` returns a value close to (but within) the current MGP balance — e.g., when `mgpReward > mgpleft` so the clamp binds, `getRewardAmount` returns exactly `mgpleft` (the full remaining MGP balance). Doubling that returns `2 * mgpleft`, i.e. twice what the contract owns, which is then passed to `vlMGP.lockFor(rewardToSend, msg.sender)`.

Whether this results in an outright revert (if `vlMGP.lockFor` performs a `transferFrom` for the full amount and the contract cannot cover it) or in the locker crediting the user for more MGP than was ever transferred (if `lockFor` only pulls up to the approved/available amount, or credits based on the passed-in `_amount` argument rather than actually-received tokens) depends on `VLMGP.lockFor`'s implementation, which I was not able to fully inspect (the file content appeared truncated/inaccessible via the index — only its license header was returned). I could not confirm from the available index content whether `lockFor` performs `safeTransferFrom` for the exact `_amount` or relies on some other accounting, so I cannot confirm whether the exploit results in a revert (DoS on mode-2 deposits near the balance cap) or in actual over-crediting of a user's locked balance beyond the MGP the contract holds.

Given this uncertainty and the explicit instruction to not speculate, I am unable to conclusively confirm the "protocol insolvency" impact without seeing `VLMGP.lockFor`'s full implementation. However, the code path described in the question — the balance clamp in `getRewardAmount` being bypassed by the post-clamp doubling in `incentiveDeposit` for `_mode == 2` — is confirmed to exist exactly as described.

### Impact Explanation
If `VLMGP.lockFor` credits the locked amount to the user's vlMGP balance based on the passed argument (rather than strictly limited by actual token transfer success), then a user could obtain a vlMGP lock credit worth up to 2x the contract's real MGP balance, meaning the sum of all locked (claimable/voting) balances would exceed the actual MGP backing them — a real insolvency where later legitimate lockers/withdrawers cannot be made whole. If instead `lockFor` strictly requires `transferFrom` of the full doubled amount, the practical effect is a revert/DoS for any mode-2 call whose reward is clamped by the balance cap, preventing legitimate reward locking rather than causing fund loss. I cannot state with confidence which of these two outcomes occurs without access to the full `VLMGP.lockFor` source.

### Likelihood Explanation
The precondition is straightforward and requires no privileged role: an attacker only needs to hold WOM tokens (which can be bought on the open market) and call `incentiveDeposit` with `_mode == 2` at a point where the contract's MGP balance is low enough that `getRewardAmount`'s clamp binds (`mgpReward > mgpleft`). This is a normal, unprivileged, single-transaction call path with `_convertRatio` and `_amount` fully attacker-controlled, and is repeatable each time the contract's MGP balance is thin relative to computed rewards.

### Recommendation
Apply the mode-2 doubling multiplier before the balance clamp, not after. Concretely, refactor `getRewardAmount` to accept the multiplier (or move the doubling logic inside `getRewardAmount`) so that the `mgpReward > mgpleft ? mgpleft : mgpReward` check is the final step applied to the already-doubled value, e.g.:
```solidity
uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender, _mode == 2);
if (_mode == 2) rewardToSend = rewardToSend * 2;
uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
if (rewardToSend > mgpleft) rewardToSend = mgpleft;
```
Additionally, verify `VLMGP.lockFor`'s behavior to ensure it always requires and performs a real token transfer equal to the locked amount, so that no code path can credit a lock exceeding actual token custody.

6. Repeat with a second unprivileged account attempting to withdraw/claim through `vlMGP` to confirm whether legitimate claims fail due to insufficient backing (insolvency) — this final assertion requires the real `VLMGP.lockFor`/withdrawal implementation, which was not available for inspection in this session.
