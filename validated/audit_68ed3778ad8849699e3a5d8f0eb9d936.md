### Title
Denial of Service via Unhandled UTF-8 Decode Error in Attacker-Controlled DID Metadata During Wallet Sync - ([File: chia/wallet/did_wallet/did_wallet_puzzles.py])

### Summary
This is analogous to the Deno bug class: a remote/attacker-controlled byte string is decoded assuming valid text encoding, without handling the decode-failure case, and the resulting unhandled exception aborts processing. In chia-blockchain, `did_program_to_metadata()` in `chia/wallet/did_wallet/did_wallet_puzzles.py` decodes DID metadata key/value atoms straight from an on-chain puzzle using `str(key, "utf-8")` / `str(val, "utf-8")` with no `try/except`, and this function is invoked automatically during wallet coin-sync whenever a new DID singleton coin is observed.

### Finding Description
`did_program_to_metadata()` converts a CLVM `Program` (the curried DID metadata parameter) into a `dict[str, str]`: [1](#0-0) 

```python
def did_program_to_metadata(program: Program) -> dict[str, str]:
    metadata = {}
    for key, val in program.as_python():
        metadata[str(key, "utf-8")] = str(val, "utf-8")
    return metadata
```

`str(bytes, "utf-8")` (equivalent to `bytes.decode("utf-8")` with strict error handling) raises `UnicodeDecodeError` for any byte sequence that is not valid UTF-8. The metadata `Program` comes directly from the curried arguments of a DID inner puzzle that is fully attacker-controlled — any party can launch/spend a DID singleton with an arbitrary metadata CLVM atom containing invalid UTF-8 bytes (e.g. a lone `0x80`/`0xFF` byte, mirroring the non-ASCII bytes in the Deno advisory).

This function is called from multiple wallet coin-processing paths that run automatically as part of normal wallet sync/receipt of a DID coin, with no exception handling around the call:

- `DIDWallet.create_new_did_wallet_from_coin_spend()` (auto-creates a DID wallet when a new DID coin is first observed): [2](#0-1) 

- `DIDWallet.coin_added()` (invoked by `WalletStateManager` every time a DID coin belonging to the wallet is added, including on ordinary receipt of a DID that was sent to the wallet): [3](#0-2) 

- `WalletStateManager.manual_did_search()` and `WalletStateManager.find_lost_did()`, reachable via the `did_get_info` / `did_find_lost_did` RPC endpoints that a local RPC caller can trigger against any DID coin id on chain: [4](#0-3) [5](#0-4) 

None of these call sites wrap `did_program_to_metadata` in a `try/except`, unlike the adjacent recovery-list parsing in the same functions, which is explicitly wrapped in `try: ... except Exception:` because it is understood to be untrusted, attacker-supplied data: [6](#0-5) 

### Impact Explanation
Any coin creating (or spending to update) a DID singleton with a metadata atom containing non-UTF-8 bytes will cause an unhandled `UnicodeDecodeError` when a victim's wallet observes that coin during normal sync (`_add_coin_state` → `determine_coin_type` → `DIDWallet.identify`/`coin_added`), or when the wallet auto-creates a new DID wallet for a coin sent to it. This is a spend-triggered exception in the wallet's coin-sync/receive pipeline — an attacker only needs to create a DID coin (or send one) to a target wallet's puzzle hash; no privileged access to the victim is required. Depending on whether the exception is caught further up the call stack (not observed in the sync loop shown), this can abort or corrupt the wallet-sync task, resulting in a denial of service against the wallet client (unable to sync/track its coins) — analogous to the Deno process abort from unhandled header decode failure.

### Likelihood Explanation
Likelihood is high for any attacker who can construct a spend bundle: crafting a DID inner puzzle with an invalid-UTF-8 metadata list entry requires no special privileges beyond building/spending a DID singleton, which any wallet user can do. Delivering it to a victim only requires sending a DID (or having the victim query/track a malicious DID via `did_get_info`/`did_find_lost_did`), both of which are standard, low-friction wallet interactions.

### Recommendation
Wrap the decode logic in `did_program_to_metadata()` in a try/except (as is already done for the DID recovery-list parsing in the same file), falling back to a safe placeholder (e.g. skip the malformed key/value or represent it via `errors="replace"`/hex) instead of propagating `UnicodeDecodeError` into the wallet sync and RPC call paths.

### Proof of Concept
1. Attacker builds a DID launcher spend where the DID inner puzzle is curried with a metadata list containing an atom pair whose value (or key) is the raw byte `b"\x80"` (invalid standalone UTF-8 continuation byte) instead of a valid string.
2. Attacker submits the spend bundle to the mempool/network so it confirms on chain (or sends the resulting DID coin to a victim's wallet puzzle hash).
3. Victim wallet's sync pipeline observes the new/updated DID coin via `WalletStateManager._add_coin_state` → `determine_coin_type` → `DIDWallet.identify`/`DIDWallet.coin_added`, which calls `did_wallet_puzzles.did_program_to_metadata(metadata)` on the attacker-supplied `Program`.
4. `str(val, "utf-8")` raises `UnicodeDecodeError`, propagating out of `coin_added`/`create_new_did_wallet_from_coin_spend` unhandled, disrupting the wallet's coin-sync processing for that batch/coin.
