### Title
Point-at-infinity reaches `x()`/`x_only()` and panics — DKG participant cancels the group key to DoS signing - (File: networks/bitcoin/src/crypto.rs)

### Summary
`x()` and `x_only()` in `networks/bitcoin/src/crypto.rs` call `.expect("point at infinity")` / `.expect(...)` on the SEC1 encoding of a `ProjectivePoint`, panicking when the point is the identity. These functions are invoked from `Hram::hram` (BIP-340 challenge) and from key/tweak handling, both of which operate on values derived from commitments supplied by other protocol participants. A DKG participant in PedPoP can choose their verification-share commitments so that the aggregate `group_key` (the sum of all participants' commitment vectors) is the point at infinity, after which any attempt to sign — or even to derive the x-only output key — panics instead of returning an error, mirroring the CVE-2022-34679 class of "unhandled return value → null dereference → denial of service".

### Finding Description
In `networks/bitcoin/src/crypto.rs`:

- `fn x(key: &ProjectivePoint) -> [u8; 32]` does `key.to_encoded_point(true)` then `encoded.x().expect("point at infinity")` — `x()` returns `None` for the identity, so this is an unhandled `Option` that panics.
- `fn x_only(key: &ProjectivePoint)` wraps `x()` with another `expect`.

`x()` is called inside `Hram::hram(R, A, m)` for both `R` (the aggregate bound nonce) and `A` (the group key). `Schnorr::verify` calls `self.0.verify(group_key, nonces, sum)` which internally evaluates `Hram` on `group_key` — this runs inside `AlgorithmSignatureMachine::complete` in `crypto/frost/src/sign.rs:465` on every signing session.

On the input side, `Commitments::read` / `read_preprocess` (`crypto/frost/src/sign.rs:276-281`) accept untrusted point encodings, and the PedPoP DKG accepts each participant's commitment vector without checking that the aggregate group key is non-identity. A participant who observes (or predicts, being last to publish) the other commitment vectors can set their own vector `C_i = -Σ_{j≠i} C_j`, making `group_key = Σ C_j = identity`. PedPoP's per-participant PoK still verifies because it only proves knowledge of the discrete log of their own commitments relative to the basepoint — an additive-cancellation commitment is a perfectly "valid" individual contribution.

Once `group_key` is the identity:
- `x_only(&group_key)` panics immediately wherever the output/external key is derived (e.g., when computing the untweaked x-only key for the wallet).
- Any `sign_share`/`verify`/`verify_share` path that evaluates `Hram::hram(R, &group_key, m)` panics.

The panic is a denial of service: the threshold node crashes or aborts the session rather than returning `FrostError`.

### Impact Explanation
A single DKG participant, using only public commitment messages (which are explicitly in-scope as untrusted bytes fed to `Commitments::read`/PedPoP commitment handling), can force the shared `group_key` to the point at infinity. Every subsequent signing operation — and the key-derivation step that produces the Bitcoin output key — hits the `expect` in `x()`/`x_only()` and panics, permanently denying service for that key. The process must be restarted and the keyset abandoned/rotated.

### Likelihood Explanation
Requires being a participant in the DKG/signing set (a co-signer, reachable with only public protocol messages) and publishing last or computing commitments adaptively. No collusion or leaked secrets are needed; the cancellation is a single additive operation over public values. The probability of an honest session producing an infinity group key or nonce sum is negligible, so this is only exploitable deliberately — consistent with Medium severity (availability only, no key leakage).

### Recommendation
- In `crypto/dkg/pedpop/src/lib.rs` and/or `ThresholdKeys::new` (`crypto/frost/src/lib.rs`), reject a `group_key` that `is_identity()`, and reject per-participant verification shares/commitments that are identity where they are later used as `A` in `Hram`.
- In `networks/bitcoin/src/crypto.rs`, convert `x()`/`x_only()` to return `Option`/`Result` and propagate a `FrostError`/`DLEqError`-style failure instead of panicking, or document and enforce a non-identity precondition checked at deserialization (`read_G` should reject identity encodings).
- In `complete()` (`crypto/frost/src/sign.rs`), validate that `Rs` and `group_key` are non-identity before calling `algorithm.verify`, returning `FrostError::InvalidShare`/`InvalidParticipant` on failure.

### Proof of Concept
1. Run PedPoP with `n` participants. The attacker, publishing last, computes `C_mal = -(C_1 + ... + C_{n-1})` for each generator element of the commitment vector and supplies a valid PoK for `C_mal` (they know the discrete log since they chose it).
2. All PedPoP share-verification checks pass; `ThresholdKeys::new` produces keys with `group_key = identity`.
3. The coordinator/integrator calls `x_only(&group_key)` to derive the external key → panic at `crypto.rs:15`/`22`. Alternatively, initiate a FROST signing session; `AlgorithmSignMachine::sign` succeeds, and `AlgorithmSignatureMachine::complete` calls `Schnorr::verify(group_key, …)` → `Hram::hram(R, A=identity, m)` → `x(A)` → panic at `crypto.rs:15`.

Note: I could not fully confirm within the available iterations whether `read_G` for `Secp256k1`/`dalek-ff-group` rejects identity encodings or whether `ThresholdKeys::new` already asserts a non-identity group key; if either check exists, the PedPoP-cancellation reachability is reduced accordingly and the remaining exposure is the documented `expect` in `x()`/`x_only()`.
