### Title
Length-limit bypass in `bech32_decode` for offer strings enables unbounded-size parsing before validation - (File: `chia/util/bech32m.py`)

### Summary
`chia/util/bech32m.py`'s `bech32_decode()` accepts a `max_length` parameter (default `90`) specifically intended to bound the size of attacker-supplied bech32/bech32m strings before the function does per-character scanning, case checks, charset lookups, and checksum computation [1](#0-0) . `Offer.from_bech32()` in `chia/wallet/trading/offer.py`, however, calls `bech32_decode(offer_bech32, max_length=len(offer_bech32))`, which sets the cap to the exact length of the caller-supplied string, i.e. no cap at all [2](#0-1) .

### Finding Description
`bech32_decode` is explicitly designed with a size limit to prevent unbounded processing of untrusted strings — the same class of defense the `idna` advisory recommends ("enforce the length limit prior to passing... to idna.encode()") [3](#0-2) . All normal address-decoding call sites use the safe default of 90 characters [4](#0-3) [5](#0-4) . The offer-parsing path is the sole call site that defeats this protection by deriving `max_length` from the untrusted input itself, so any caller can submit an arbitrarily large offer string and force full linear-time (and linear-memory) processing — character-class scan, `.lower()`/`.upper()` comparisons, `rfind`, charset membership checks, and `convertbits` — with no upper bound [6](#0-5) . This is reachable from the `take_offer` wallet RPC endpoint, which decodes the caller-supplied `offer` string via `TakeOffer.parsed_offer` → `Offer.from_bech32` [7](#0-6) , and from the CLI's `take_offer` command, which passes raw file/hex content straight to `Offer.from_bech32` [8](#0-7) .

### Impact Explanation
Unlike CLVM execution — which is tightly cost-metered per the mempool/consensus resource-limit model (`MAX_BLOCK_COST_CLVM`, atom/pair density checks) [9](#0-8)  — this parsing path runs entirely in the wallet-RPC Python layer *before* any CLVM cost accounting or spend-bundle validation occurs. A malicious offer string (or a malicious offer-file counterparty) can force the receiving wallet process to spend CPU and memory proportional to an attacker-chosen, effectively unbounded string size purely to decode the bech32 wrapper, independent of what the underlying spend bundle actually costs. This matches the CWE-400/CWE-1333 resource-exhaustion class from the report, though the actual blow-up here is linear-in-input-size (not the quadratic/exponential blow-up idna suffered), so the severity ceiling is lower than the reference CVE.

### Likelihood Explanation
Any wallet RPC caller or offer counterparty who can get a peer's wallet to call `take_offer`/examine an offer (a very common workflow — sharing `.offer` files or offer strings) can trigger this with a single crafted string; no special privileges or prior mempool acceptance are required. The main open question — which I could not verify — is whether an aiohttp-level body-size cap (`max_message_size` = 50MB in `chia/rpc/rpc_server.py`, or `max_request_body_size`) is applied ahead of the wallet RPC endpoint and would already truncate/reject oversized requests before reaching `Offer.from_bech32`. If such a cap is enforced by default for the wallet RPC server (not just Data Layer's, which explicitly configures `rpc_server_max_request_body_size`), the practically exploitable input size — and therefore the real-world impact — would be bounded to whatever that limit allows, which may reduce this from a meaningful DoS to a low-impact inefficiency.

### Recommendation
Change `Offer.from_bech32` to call `bech32_decode(offer_bech32)` using the function's own safe default `max_length`, or pass an explicit, small, protocol-appropriate maximum (sized to the largest legitimate compressed offer), rather than `max_length=len(offer_bech32)`, which nullifies the check entirely. Additionally verify that the wallet RPC server enforces a reasonably small `max_request_body_size`/`max_message_size` independent of this fix, so oversized payloads are rejected before any parsing begins.

### Proof of Concept
1. Construct a syntactically-valid-looking bech32-ish string of very large size (e.g., hundreds of MB) with a valid `hrp` + `1` separator near the end and only charset-valid trailing characters (checksum verification will fail at the end, but only after the full string has been scanned multiple times).
2. Call the wallet RPC `take_offer` endpoint (or CLI `chia wallet take_offer <path_or_hex>`) with this string as the `offer` argument — reaching `TakeOfferCMD.run()` → `take_offer()` → `Offer.from_bech32(offer_hex)` [8](#0-7) , or via RPC `TakeOffer(offer=...)` → `parsed_offer` [7](#0-6) .
3. Observe that `bech32_decode(offer_bech32, max_length=len(offer_bech32))` performs multiple full-string scans (`any()`, `.lower()`, `.upper()`, `rfind`, `all()`, list comprehension, `bech32_polymod`) over the entire attacker-chosen size before failing, consuming CPU/memory proportional to the (unbounded) attacker-supplied length [1](#0-0) , whereas the same code path for ordinary addresses is capped at 90 characters by default [10](#0-9) .

```python
def bech32_decode(bech: str, max_length: int = 90) -> tuple[str | None, list[int] | None]:
    """Validate a Bech32 string, and determine HRP and data."""
    bech = bech.strip()
    if (any(ord(x) < 33 or ord(x) > 126 for x in bech)) or (bech.lower() != bech and bech.upper() != bech):
        return (None, None)
    bech = bech.lower()
    pos = bech.rfind("1")
    if pos < 1 or pos + 7 > len(bech) or len(bech) > max_length:
        return (None, None)
    if not all(x in CHARSET for x in bech[pos + 1 :]):
        return (None, None)
    hrp = bech[:pos]
    data = [CHARSET.find(x) for x in bech[pos + 1 :]]
    if not bech32_verify_checksum(hrp, data):
        return (None, None)
    return hrp, data[:-6]


def convertbits(data: Iterable[int], frombits: int, tobits: int, pad: bool = True) -> list[int]:
    """General power-of-2 base conversion."""
    acc = 0
    bits = 0
    ret = []
    maxv = (1 << tobits) - 1
    max_acc = (1 << (frombits + tobits - 1)) - 1
    for value in data:
        if value < 0 or (value >> frombits):
            raise ValueError("Invalid Value")
        acc = ((acc << frombits) | value) & max_acc
        bits += frombits
        while bits >= tobits:
            bits -= tobits
            ret.append((acc >> bits) & maxv)
    if pad:
        if bits:
            ret.append((acc << (tobits - bits)) & maxv)
    elif bits >= frombits or ((acc << (tobits - bits)) & maxv):
        raise ValueError("Invalid bits")
    return ret
```
