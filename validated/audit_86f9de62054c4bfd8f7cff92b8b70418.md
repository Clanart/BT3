### Title
Type-assertion panic on attacker-controlled CosmWasm query response in the Pointer precompile's `AddCW20`/`AddCW721` handlers - ([File: precompiles/pointer/pointer.go])

### Summary
The `AddCW20`/`AddCW721`/`AddCW1155` handlers of the pointer precompile (and every legacy version of it, e.g. `precompiles/pointer/legacy/v552/pointer.go`, `v555`, `v562`, `v605`, `v66`) query an attacker-deployed CosmWasm contract and then blindly type-assert the JSON response fields to `string` without checking `ok`. A contract deployer can return a non-string (or `null`) value for `name`/`symbol` and force a Go panic when any user registers a pointer for that contract.

### Finding Description
`AddCW20` calls `p.wasmdKeeper.QuerySmart(ctx, cwAddress, []byte("{\"token_info\":{}}"))`, unmarshals the response into a generic `map[string]interface{}`, then does: [1](#0-0) 

```
formattedRes := map[string]interface{}{}
if err := json.Unmarshal(res, &formattedRes); err != nil { ... }
name := formattedRes["name"].(string)
symbol := formattedRes["symbol"].(string)
```

Because a CosmWasm contract's `token_info`/`contract_info` response is entirely under the control of the contract author (any unprivileged wallet can `MsgStoreCode`+`MsgInstantiateContract` a CW20/CW721/CW1155 contract), an attacker can implement a "query" handler that returns e.g. `{"name": null, "symbol": null, ...}` or `{"name": 12345, "symbol": true, ...}`. When `formattedRes["name"]` is `nil` or a non-string type, the assertion `.(string)` panics with `interface conversion: interface {} is nil, not string` (or a mismatched-type panic). This is the exact bug class of CVE-2017-17440: a NULL/absent or malformed field in attacker-supplied structured data reaching an unchecked type coercion causes a crash rather than a graceful error. This pattern repeats identically across `AddCW20`, `AddCW721`, and the CW1155 add-pointer paths, and across every historical precompile version (`v552`, `v555`, `v562`, `v605`, `v66`, and the current `precompiles/pointer/pointer.go`): [2](#0-1) 

### Impact Explanation
This is reachable by any transaction sender: deploy a malicious CW20/CW721 contract, then call the EVM pointer precompile's `addCW20Pointer`/`addCW721Pointer` method against it. Whether this produces only a reverted transaction or a validator crash depends on which call chain invokes `Run`/`Execute` and whether a `recover()` wraps that call. Reviewing the static (non-dynamic-gas) `Precompile.Run` wrapper used by the pointer precompile family, the wrapper only calls `HandlePrecompileError` and converts a returned Go `error` into `vm.ErrExecutionReverted`; it does **not** contain a `defer recover()` around the executor call the way some other precompiles do (e.g. `precompiles/solo/solo.go` and `precompiles/addr/legacy/v66/addr.go` explicitly add `recover()` "to catch gas meter panics"). The pointer precompile's `AddCW20`/`AddCW721` functions have no such recovery. If the panic is not intercepted by a higher-level `recover()` in the tx-execution pipeline (e.g. `DeliverTx`'s runTx recovery, or the giga executor's per-tx `recover()` block seen in `app/app.go`), the failure would only abort that single transaction with an `ErrPanic`/500-style result rather than crash the whole node process — meaning the concretely provable impact is a single-transaction DoS (guaranteed-revert path) at minimum, with node-level impact contingent on whether this path is reached from `eth_call`/other query surfaces that lack the same top-level recovery as `DeliverTx`/giga.

### Likelihood Explanation
High likelihood of triggering the panic: no privileged access is required — deploying a CosmWasm contract and calling the pointer-registration precompile method are both available to any funded account. The trigger condition (return `name`/`symbol` as `null` or a non-string type from `token_info`/`contract_info`) is trivial to implement in a custom CosmWasm contract.

### Recommendation
Replace the unchecked type assertions with checked ones (`name, ok := formattedRes["name"].(string); if !ok { return nil, 0, fmt.Errorf(...) }`) in every `AddCW20`/`AddCW721`/`AddCW1155` implementation across all precompile versions (`precompiles/pointer/pointer.go` and all `precompiles/pointer/legacy/v*/pointer.go`), and add a top-level `recover()` in the pointer precompile's `Execute`/`Run` wrapper (mirroring the pattern already used in `precompiles/solo/solo.go` and `precompiles/addr/legacy/v66/addr.go`) to guarantee any unexpected panic degrades to `vm.ErrExecutionReverted` instead of propagating further.

### Proof of Concept
1. As any account, submit `MsgStoreCode` + `MsgInstantiateContract` for a custom CW20-like contract whose `token_info` query handler returns raw JSON `{"name": null, "symbol": null, "decimals": 0, "total_supply": "0"}`.
2. Call the EVM pointer precompile's `addCW20Pointer(cwAddr)` method (address `0x...1004`/whichever registered address, method per `precompiles/pointer/pointer.go`) with the contract address from step 1.
3. Execution reaches `AddCW20` → `formattedRes["name"].(string)` on a `nil` interface value → Go runtime panic (`interface conversion: interface {} is nil, not string`), aborting the transaction with an internal panic instead of a clean revert (and, depending on the invocation context/lack of `recover()`, potentially surfacing at a level not guarded by tx-level panic recovery).
