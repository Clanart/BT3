### Title
Excess ETH from Uniswap fee-swaps is trapped in `EvmHost` instead of being refunded to the dispatcher - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all convert native token payments into `feeToken` via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`. Standard `UniswapV2Router02.swapETHForExactTokens` refunds any unused ETH (i.e., `msg.value - amountIn`) to its immediate caller — which is `EvmHost` itself, not the original transaction sender/payer. `EvmHost` never forwards that refund on to `_msgSender()`, so any ETH sent in excess of the actual swap cost becomes permanently stuck in the `EvmHost` contract. This is the same bug class as the external report: a cross-chain messaging fee overpayment/refund that should return to the sender is instead misdirected to the bridge contract.

In every one of these paths, when `msg.value > 0`, `EvmHost` calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` directly from its own address. `UniswapV2Router02`'s implementation of `swapETHForExactTokens` computes `amounts[0]` (the ETH actually required), performs the swap, and refunds `msg.value - amounts[0]` to `msg.sender` of that call — which, from the router's perspective, is `EvmHost`, not the account that originated the top-level transaction (`_msgSender()`). None of these three functions capture or forward that refund; there is no post-swap balance check or ETH transfer back to `_msgSender()` anywhere in `EvmHost.sol`'s dispatch/fundRequest logic.

Contrast this with the application layer (`IntentGatewayV2.sol`, `ExtrinsicIntents.sol`), which explicitly tracks `msgValue` and refunds unspent native token to `msg.sender` after calling into the host: [4](#0-3) [5](#0-4) 

Those app-level refunds only cover the gap between the value forwarded by the top-level caller and the amount passed to `dispatch{value: ...}`. They cannot recover the *internal* Uniswap refund that happens once `dispatch()`/`fundRequest()` executes the swap with less-than-exact pricing (spot-price fluctuation, slippage headroom, or an app intentionally over-provisioning ETH to guarantee the swap succeeds) — that ETH lands back on `EvmHost`'s own balance and is never routed anywhere.

### Impact Explanation
Any ETH sent to cover a dispatch/fund-request fee-token swap in excess of the exact amount consumed by the swap is permanently misdirected into `EvmHost`'s balance instead of being returned to the paying account. Over the life of the protocol, this represents a steady, unrecoverable loss of user funds — exactly the same fund-misdirection bug class as the reported LayerZero issue (excess/refundable cross-chain fee ETH ending up with the wrong party, here the bridge contract instead of the payer). There is no visible sweep/withdraw path in `EvmHost.sol` for this stray ETH, so the funds are effectively locked, satisfying the "loss of funds" impact bar.

### Likelihood Explanation
This triggers on ordinary, non-adversarial usage: any application or user calling `dispatch()`/`fundRequest()` with `msg.value` set even slightly above the router's actual required input (a very common pattern to avoid `INSUFFICIENT_INPUT_AMOUNT` reverts from slippage) will lose the difference. No malicious relayer, prover, or governance actor is needed — it is a direct consequence of `EvmHost`'s own fee-swap wiring.

### Recommendation
After each `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the returned `amounts[0]` (actual ETH spent) and refund `msg.value - amounts[0]` to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.sol`/`ExtrinsicIntents.sol` and in `UniV4UniswapV2Wrapper.swapETHForExactTokens` (which correctly forwards its own leftover ETH back to its caller).

### Proof of Concept
1. Caller invokes `EvmHost.dispatch(DispatchPost)` (or `dispatch(DispatchGet)`/`fundRequest`) with `msg.value` intentionally set higher than the current spot price requires for the `post.fee` amount of `feeToken` (e.g., to tolerate slippage between quote time and execution time).
2. `EvmHost` calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`.
3. The Uniswap V2 router uses only `amounts[0] < msg.value` and refunds `msg.value - amounts[0]` ETH to `msg.sender` of the swap call, i.e., to `EvmHost`.
4. `dispatch()`/`fundRequest()` returns without checking `address(this).balance` or transferring anything back to `_msgSender()`.
5. The leftover ETH remains in `EvmHost` permanently; the original caller receives no refund despite having sent the funds for this purpose.
