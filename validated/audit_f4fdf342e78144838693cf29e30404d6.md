The `solana_nonce` crate itself (`Versions::authorize`, `nonce::state::Data`) lives outside this repo as an external dependency, so I can't verify its exact internals here — but the call sites in this repo (`programs/system/src/system_instruction.rs` and the integration tests) are sufficient to confirm the behavior described below.

### Title
Nonce authority reassignment does not advance the durable nonce, allowing stale pre-signed nonce transactions to become valid again - ([File: programs/system/src/system_instruction.rs])

### Summary
`AuthorizeNonceAccount` changes only the `authority` field of a nonce account and never advances the stored `durable_nonce`/blockhash. Because Agave's nonce-transaction validation treats a nonce transaction as valid whenever (a) the transaction's `recent_blockhash` matches the account's stored `durable_nonce`, and (b) the *current* authority is a signer, a transaction that was pre-signed by an authority key at time T remains fully executable at any later time as long as the authority is ever set back to that same key, even if the durable nonce was never advanced in between. This mirrors the external report's core defect: signatures have no monotonic nonce or expiry, so a "stale" pre-signed message can be resurrected and executed whenever the authorized-signer set happens to realign with it, regardless of intervening changes.

### Finding Description
`authorize_nonce_account` only rewrites the authority, leaving `durable_nonce` untouched: [1](#0-0) 

Compare this to `advance_nonce_account`, which is the *only* system instruction that rotates the stored `durable_nonce`: [2](#0-1) 

Runtime-side validation in the SVM only checks that the transaction's `recent_blockhash` equals the stored `durable_nonce` and that the *current* authority is among the signers of the marker instruction — it has no concept of "when" the signature was produced or whether the authority set has changed and changed back since: [3](#0-2) 

The bank-level equivalent performs the same check with no temporal component: [4](#0-3) 

The project's own integration tests confirm this exact state machine: authorizing a new authority does *not* touch the durable nonce hash, and a nonce transaction signed with the *previous* authority is discarded only because the *current* authority no longer matches — not because any nonce/expiry value was consumed: [5](#0-4) 

If the authority is later reassigned back to the original key (a normal, non-durable "blockhash" transaction, unprivileged with respect to the nonce protocol itself — anyone who can get the current authority's signature can do this, including the original authority reasserting control), any previously signed-but-unsubmitted durable-nonce transaction using that authority becomes valid again, because `durable_nonce` was never advanced by the intervening `AuthorizeNonceAccount` calls.

### Impact Explanation
This is the direct analog of the report's "signature saved and used later" scenario: a party holding an old, fully-signed durable-nonce transaction (e.g., a transfer or CPI encoded when authority X was in control) can withhold submission indefinitely. If authority is later reassigned back to X — for entirely legitimate, unrelated reasons — the withheld transaction becomes executable again with its original stale instructions/amounts, without requiring any new signature or awareness from the current stakeholders that a "final" decision was being reopened. Because durable nonces are explicitly designed to support fee-payer-driven, offline-signed transactions with no expiration, this can result in unexpected fund movement or execution of stale intent that no living party currently agrees to, i.e., false acceptance of an outdated authorization.

### Likelihood Explanation
Low to moderate. It requires: (1) an off-chain, unsubmitted, fully-signed nonce transaction to exist, (2) the nonce authority to be changed away and then changed back to the original key without an intervening `AdvanceNonceAccount` call, and (3) the durable nonce blockhash to remain constant throughout. Deliberate multi-step custody/authority hand-offs on durable nonce accounts (common in wallets, escrow, or governance-style tooling built on top of nonce accounts) make this a realistic, if narrow, operational condition — closely paralleling the "controller rejoins the set later" scenario in the original report.

### Recommendation
Treat `AuthorizeNonceAccount` as authority-invalidating for previously signed transactions: either (a) force `AuthorizeNonceAccount` to also rotate/increment the stored `durable_nonce` (similar to `AdvanceNonceAccount`), or (b) bind signed durable-nonce transactions to the specific authority *epoch*/generation at signing time (e.g., store and check a monotonically incrementing authority-generation counter as part of `nonce::state::Data`, analogous to the report's suggested global nonce), so that a stale signature cannot become valid again purely because the authority pubkey happens to match at a later point.

### Proof of Concept
1. Create nonce account N with authority A; initial `durable_nonce = H0`.
2. A signs (but does not submit) transaction `TX1 = [AdvanceNonceAccount(N, A), Transfer(...)]` with `recent_blockhash = H0`.
3. Authority is reassigned: `AuthorizeNonceAccount(N, A, new_authority=B)` — this is a normal blockhash transaction; `durable_nonce` of N remains `H0` (per `authorize_nonce_account`, `programs/system/src/system_instruction.rs:213-249`).
4. At this point, submitting `TX1` fails/is discarded because the current authority is `B`, not `A` (matches the "batch 10" integration test behavior).
5. Later, authority is reassigned back: `AuthorizeNonceAccount(N, B, new_authority=A)`. `durable_nonce` is still `H0`.
6. `TX1`, signed months earlier under step 2, is now submitted. `validate_transaction_nonce` in `svm/src/transaction_processor.rs:833-892` sees `recent_blockhash == durable_nonce (H0)` and `authority == A == current signer`, so it is accepted and executed with its original stale instructions — despite no active party re-signing or re-approving it at submission time.

pub fn advance_nonce_account(
    account: &mut BorrowedInstructionAccount,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Advance nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    let state: Versions = account.get_state()?;
    match state.state() {
        State::Initialized(data) => {
            if !signers.contains(&data.authority) {
                ic_msg!(
                    invoke_context,
                    "Advance nonce account: Account {} must be a signer",
                    data.authority
                );
                return Err(InstructionError::MissingRequiredSignature);
            }
            let next_durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            if data.durable_nonce == next_durable_nonce {
                ic_msg!(
                    invoke_context,
                    "Advance nonce account: nonce can only advance once per slot"
                );
                return Err(SystemError::NonceBlockhashNotExpired.into());
            }

            let new_data = nonce::state::Data::new(
                data.authority,
                next_durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            account.set_state(&Versions::new(State::Initialized(new_data)))
        }

pub(crate) fn authorize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Authorize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }
    match account
        .get_state::<Versions>()?
        .authorize(signers, *nonce_authority)
    {
        Ok(versions) => account.set_state(&versions),
        Err(AuthorizeNonceError::Uninitialized) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
        Err(AuthorizeNonceError::MissingRequiredSignature(account_authority)) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} must sign",
                account_authority
            );
            Err(InstructionError::MissingRequiredSignature)
        }
    }
}
