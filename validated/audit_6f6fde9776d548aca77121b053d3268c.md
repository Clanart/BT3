### Title
`ReceivedOutput` deserialization never binds `offset` to the output's `script_pubkey`, allowing unspendable inputs to be reported as spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` is the wallet's claim that a given `TxOut`/`OutPoint` is spendable by the threshold key plus a scalar `offset`. `ReceivedOutput::read` deserializes all three fields from an untrusted byte stream but never verifies that `offset` actually maps to `output.script_pubkey` — the exact analog of the reported bug class, where an identifier (`recipientId`) is checked for well-formedness but never verified to correspond to the object it references (`recipientAddress`).

### Finding Description
`Scanner` maintains a `HashMap<ScriptBuf, Scalar>` keyed by script to the offset that spends it (`networks/bitcoin/src/wallet/mod.rs:153-156`). `Scanner::scan_transaction` only produces `ReceivedOutput`s where the invariant `p2tr_script_buf(key + G*offset) == output.script_pubkey` holds by construction (`mod.rs:199-214`).

However, `ReceivedOutput::read` (`mod.rs:122-134`) independently parses `offset`, `output`, and `outpoint` with no consistency check:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

Any party that supplies serialized `ReceivedOutput`s to a wallet (a coordinator, indexer, or liquidity provider serving "your deposits") can claim an arbitrary `offset` for an arbitrary output. The wallet's spend path re-keys the threshold keys by `output.offset()` to produce the signing key for that input — an offset that does not correspond to the output's script produces a signature under the wrong key. There is no code path that rechecks `p2tr_script_buf(keys.group_key() + G*offset) == output.script_pubkey` after deserialization.

### Impact Explanation
An attacker-supplied `ReceivedOutput` whose `output` pays to the wallet's registered script but whose `offset` belongs to a different registration (or to no registration) causes the wallet to treat an input as spendable when it is not: the produced transaction input carries a signature under `key + offset*G` that does not match the output's committed key, so the spend is invalid. More broadly, funds can be *reported received* that are not spendable at all — the wallet commits real co-spending inputs and fees to a transaction that can never confirm, or attributes value/ownership incorrectly when the `outpoint` references an output the wallet does not control. This matches the accepted outcome class of "funds reported received that are not spendable" and mirrors the original finding's "funds distributed to an unintended address" (here: a claimed spend path that doesn't correspond to the output).

### Likelihood Explanation
Reachable by an unprivileged party: `ReceivedOutput::read` is explicitly a public deserialization entry point fed by untrusted bytes, and serialized `ReceivedOutput`s are designed to cross trust boundaries (the scanner that detects them and the signer that spends them are distinct roles). Exploitation requires only that the wallet accept an externally-produced `ReceivedOutput` rather than one it scanned itself — a realistic deployment pattern — and causes the wallet to construct invalid or misattributed spends. Impact is bounded to unspendable-input/false-credit semantics rather than direct key compromise, meriting Medium rather than High.

### Recommendation
Bind the identifier to the value at the trust boundary, analogous to the original report's `_recipients[recipientId].recipientAddress == _recipientAddress` check:

- Either make `ReceivedOutput::read` private to scanning (forcing construction only via `Scanner::scan_transaction`), or
- After deserialization, re-derive the script: verify `p2tr_script_buf(expected_spend_key + G*offset) == Some(output.script_pubkey)`, requiring the caller to pass the base spend key or storing it alongside. Since `Scanner` already owns the `scripts` map, an equivalent is `Scanner`-mediated validation: `self.scripts.get(&output.script_pubkey) == Some(&offset)`.

### Proof of Concept
1. Register two offsets `o1`, `o2` via `Scanner::register_offset`, yielding scripts `S1`, `S2` for keys `K + o1·G`, `K + o2·G`.
2. Craft bytes: `offset = o2`, `output = TxOut { value: X, script_pubkey: S1 }`, `outpoint = <real UTXO paying S1>`.
3. Feed to `ReceivedOutput::read` — it succeeds and returns a struct asserting the output is spendable via `o2`.
4. The wallet attempts to spend the input; it signs with the key offset by `o2`, producing a signature valid for `K + o2·G` while the UTXO is committed to `K + o1·G`. The transaction's input fails script/sig validation — the reported-received output is not spendable, and any honest inputs bundled into the same transaction are burned as fee-paying inputs of a rejected transaction.

Uncertainty note: the spending path (`wallet/send.rs`) was not fully read; the impact assumes — per the module's design and the documented `register_offset` semantics — that `ReceivedOutput::offset()` is used to re-key the signing keys per input. Even under the weakest interpretation (the offset only mislabels which registered script an output belongs to), the unverified binding stands as the root cause.
