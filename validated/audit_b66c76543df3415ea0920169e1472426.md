### Title
Scanner::scan_block resolves coinbase outputs outside the spendable-output boundary, reporting immature (unspendable) funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The upstream bug class is a resolver honoring an explicit cross-scope reference (`caProvider.namespace`) that should have been confined to the resource's own namespace. In `bitcoin-serai`, `Scanner::scan_block` has the analogous shape: it is the block-level counterpart of `scan_transaction`, whose job is to report *spendable* outputs received by the group key, yet it iterates `block.txdata` from index 0, resolving matching `script_pubkey`s in the coinbase transaction into `ReceivedOutput`s even though those outputs are consensus-unspendable for `COINBASE_MATURITY` (100) blocks. [1](#0-0) 

### Finding Description
`scan_transaction` reports any output whose `script_pubkey` is registered in `self.scripts`, with no notion of transaction position or maturity. [2](#0-1)  `scan_block` then calls it on every transaction in the block, including `block.txdata[0]` — the coinbase — which is bound by maturity and cannot be spent until 100 confirmations. [3](#0-2)  Like the CAProvider bypass, a lookup that the caller expects to be confined to one scope (ordinary, spendable transaction outputs) silently resolves objects from a different scope (coinbase subsidy outputs) because the boundary is not enforced at the point of resolution. Callers of the *library* get no signal distinguishing the two: `ReceivedOutput` carries only `offset`, `output`, and `outpoint`, none of which encode coinbase/maturity status. [4](#0-3) 

Note that Serai's own processor-side consumer compensates for this by iterating `block.txdata[1 ..]` instead of using `scan_block`. [5](#0-4)  That is remediation at the call site, not in the resolver — the library API still returns the out-of-scope results to any other consumer.

### Impact Explanation
Any returned `ReceivedOutput` is nominally a `SignableTransaction` input candidate. If a consumer (indexer, wallet, scheduler built on `bitcoin-serai`) treats scan results as spendable inputs, an attacker-controlled coinbase output produces:

- Funds reported received that are not spendable: crediting inventory/balance that cannot actually be moved.
- Transactions built over the coinbase outpoint that are consensus-invalid (`bad-txns-premature-spend-of-coinbase`), stalling a signing batch until the input set is rebuilt.

Direct value loss is bounded (the funds do eventually mature, and a coinbase pays the *victim's* key, not the attacker's), consistent with Medium/Low-Medium severity.

### Likelihood Explanation
Reachable by an unprivileged party through a pure public input: any miner can set the coinbase output script to Serai's P2TR script (the external/branch/change/forward addresses are public). On mainnet this requires the attacker to actually win a block, which caps likelihood; on regtest-like deployments or merged-mined/test chains it is trivial. The trigger is precisely the adversary sending a Bitcoin transaction (the coinbase) the scanner resolves — matching the permitted attack surface. The doc comment on `scan_block` does warn that "received outputs must be immediately spendable, a post-processing pass is needed" [6](#0-5) , which reduces this toward a documented-caveat integration hazard; it is reported here because the resolver itself performs no enforcement and the in-repo caller had to work around it.

### Recommendation
Enforce the boundary at resolution time: in `scan_block`, iterate `block.txdata[1 ..]` (skipping the coinbase), or check `tx.is_coinbase()` inside `scan_transaction`'s caller and exclude/mark such outputs. Alternatively, extend `ReceivedOutput` with a maturity flag so downstream consumers can filter without re-parsing block structure. The processor-side workaround in `get_outputs` should remain regardless.

### Proof of Concept
1. Construct a `Scanner` for the group key via `Scanner::new(key)` (registers the P2TR script for offset `Scalar::ZERO`). [7](#0-6) 
2. As miner, build a block whose coinbase transaction (`txdata[0]`) pays `p2tr_script_buf(key)`.
3. Call `scanner.scan_block(&block)`. It returns a `ReceivedOutput` for the coinbase outpoint, indistinguishable in type from a spendable output — despite `Prevouts::All`/sighash signing over it being impossible for 100 blocks. The existing test only exercises `scan_transaction`/`send_and_get_output` on non-coinbase spends and never covers `scan_block`'s coinbase path. [8](#0-7)

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
