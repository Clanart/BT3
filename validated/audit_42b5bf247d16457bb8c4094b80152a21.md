### Title
TOCTOU in `resolveWithin` path-safety check lets a malicious repo cause Copilot conflict-resolution to read a file outside the repository - (File: `app/src/lib/path.ts`, `app/src/lib/copilot-conflict-context.ts`)

### Summary
`resolveWithin()` validates that a path stays inside the repository by resolving symlinks with `realpath()` **once**, then returns the pre-`realpath` path. Consumers such as `buildConflictContext()` re-touch the filesystem at that same path afterwards (`stat`, then `readFile`) without re-validating. Just like the OVER Protocol bug where the sender's existence was checked at one point in time but the transfer executed later against a possibly-changed state, here the "path is inside the repo" check and the actual file read are two separate filesystem operations separated by an await boundary, creating a check-then-use race an attacker who controls the working tree can exploit.

### Finding Description
`_resolveWithin` in `app/src/lib/path.ts` computes the real, symlink-resolved path once: [1](#0-0) 

It returns `resolved` (the *unresolved*, pre-`realpath` joined path), not `realResolved`. The caller in `buildConflictContext()` then performs two more independent filesystem calls on that same `absolutePath` — a `stat` and later a `readFile` — well after the validation completed: [2](#0-1) 

Because git conflict resolution paths originate from files reported as conflicted in a repository the user cloned/merged (an attacker-influenced input via `dispatcher`/`app-store.ts` calling `buildConflictContext`), the attacker can arrange the working tree so that at the moment `resolveWithin` runs, `file.path` resolves to a legitimate in-repo location, and then — between that check and the subsequent `stat`/`readFile` calls — replace an intermediate path component with a symlink pointing outside the repository (e.g. to `~/.ssh/id_rsa`, `~/.netrc`, or `~/Library/Application Support/GitHub Desktop/...`). Since git working-tree entries, hooks, or a concurrently running merge/checkout can legitimately rewrite files on disk, this window is realistically exploitable without any special local access beyond what "cloning/checking out a malicious repository and triggering a merge conflict resolution" already grants the attacker.

### Impact Explanation
If the race succeeds, the resulting file content is read via `readFile(absolutePath, 'utf8')` and folded into the Copilot conflict-resolution prompt, which is subsequently sent to the Copilot SDK/service: [3](#0-2) 

This is a file read outside the repository boundary that the `resolveWithin` guard was specifically designed to prevent, and the leaked content is exfiltrated off-device to an external AI service — matching the "file read outside the repo" / "credential exfiltration" impact class in scope.

### Likelihood Explanation
This requires precise timing (an await gap between the `realpath`-based check and the later `stat`/`readFile`), similar to the "narrow epoch-boundary window" timing constraint in the original report. It is not a trivial one-shot bug, but it is a genuine TOCTOU: the safety invariant ("resolved path is guaranteed to stay inside the repo") is only true at the instant of the check, not at the instant of use, and the two are separated by asynchronous operations that an attacker-controlled repository (via hooks, submodules, or a background git operation) can exploit to swap a path component for a symlink in between.

### Recommendation
Close the window by validating and using the path atomically:
- Open the file with `O_NOFOLLOW` (or use `fs.lstat` immediately before each read to detect a symlink swap) rather than re-stating a path string that was validated earlier.
- Alternatively, perform the `realpath` resolution once and use the **fully resolved real path** (`realResolved`) for every subsequent filesystem operation instead of the original `resolved` path, and re-run the containment check (`realResolved.startsWith(realRoot)`) immediately before both the `stat` and the `readFile` calls, minimizing/eliminating the gap between validation and use.

### Proof of Concept
1. Clone a malicious repository and trigger a merge/rebase/cherry-pick conflict such that `buildConflictContext` in `app/src/lib/stores/app-store.ts` is invoked with a conflicted file path, e.g. `evil/link_target`.
2. At the time `resolveWithin(workingDirectory, 'evil/link_target')` runs, `evil` is a real directory inside the repo, so the check passes and `absolutePath` is returned.
3. Immediately after (via a `post-checkout`/`post-merge` hook that runs asynchronously, or a background process racing the Node event loop), replace `evil` with a symlink pointing to a directory outside the repo (e.g. `~/.ssh`).
4. `buildConflictContext`'s subsequent `stat(absolutePath)` and `readFile(absolutePath, 'utf8')` calls now traverse the attacker-installed symlink and read a file from `~/.ssh`, whose content is embedded into the Copilot prompt and sent off-device.

Note: I was not able to fully verify the exact timing feasibility of the hook-triggered symlink swap (e.g., whether Desktop's own git hook execution model provides a reliable enough window), since that depends on runtime/OS scheduling behavior not fully captured in the indexed source. A Devin session with full repo/test access would be needed to build and run a concrete race-condition PoC to confirm exploitability with high confidence.
