## Analysis

**Core broken invariant from the external report:** a loop that processes multiple independent items (derivative deposits) is not fault-isolated — one item's external-dependent failure (a validation the contract doesn't handle) reverts the entire encompassing call, blocking unrelated, otherwise-valid items bundled in the same transaction.

**Local analog found in `EvmHost.sol`:** the ISMP host's incoming-dispatch functions correctly isolate `IApp` callback failures using a low-level `.call(...)` with an explicit `success` check for the *callback* itself — but the **relayer-fee/refund transfer that runs after a successful callback is NOT isolated**, and these dispatch functions are invoked directly (no try/catch) from the batch-processing loops in `HandlerV2.sol`. [1](#0-0) [2](#0-1) 

Compare this with `dispatchIncoming(PostRequest,...)`, which explicitly documents fault-isolation: *"instead of reverting the entire batch, early return here"* — this pattern is applied to the `onAccept` callback but is absent for the fee-transfer path in the `GetResponse`/timeout variants. [3](#0-2) 

These functions are called directly (not wrapped in try/catch) inside the batch loops of `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` in `HandlerV2.sol`, all of which are **permissionless entry points**: [4](#0-3) [5](#0-4) 

The `payer`/`sender` recipient of the refund is attacker-controlled at request-dispatch time (`DispatchPost.payer`), stored unchecked into `FeeMetadata.sender`: [6](#0-5) 

### Title
Unisolated relayer-fee transfer in `EvmHost.dispatchIncoming(GetResponse)`/`dispatchTimeOut` permanently locks fees and blocks entire batches - (File: `evm/src/core/EvmHost.sol`)

### Summary
`dispatchIncoming(GetResponse, address)`, `dispatchTimeOut(GetRequestTimeout,...)`, and `dispatchTimeOut(PostRequestTimeout,...)` in `EvmHost.sol` correctly isolate the `IApp` callback failure via a raw `.call` + `success` check, but the subsequent `IERC20(feeToken()).safeTransfer(...)` reward/refund is an unprotected direct call. Because `HandlerV2.sol`'s batch loops (`handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) invoke these host functions directly with no try/catch, a single item whose fee-recipient cannot receive the `feeToken` (e.g. blacklisted by a compliance-gated ERC20 like USDC, or a contract without a token hook) causes the *entire* external call, and thus the entire enclosing handler transaction, to revert.

### Finding Description
1. An attacker calls `dispatch(DispatchPost)` and sets `post.payer` to an address that the configured `feeToken` will refuse to receive (e.g., a USDC-blacklisted address, or any ERC20 with transfer hooks/blocklists), with `post.fee > 0`. This value is stored unchecked: `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})`.
2. When the request times out (or, for GET responses, when the relayer address itself becomes fee-token-restricted), a relayer submits a batch (`PostRequestTimeoutMessage`/`GetTimeoutMessage`/`GetResponseMessage`) containing this poisoned item together with other, unrelated legitimate items.
3. `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts`/`handleGetResponses` iterate the batch and call `host.dispatchTimeOut(...)`/`host.dispatchIncoming(...)` directly per item.
4. Inside the host function, after the (isolated) app callback succeeds, `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` executes as a plain external call. If it reverts, that revert propagates up through the un-guarded external call in `HandlerV2`, reverting the whole transaction — including the commitment/receipt deletions and every other item's state changes in the same batch.
5. Unlike the `onAccept`/`onGetResponse`/`onGetTimeout` callback paths (which are wrapped in `.call(...)` and explicitly roll back only their own commitment on failure so they "can be retried"), there is no equivalent fallback for the fee transfer — it can never be isolated, retried in a different form, or skipped, because it is not gated behind a low-level call.

### Impact Explanation
This directly matches the report's core invariant break: one unprivileged, attacker-chosen bad state (an unreceivable fee recipient) makes an entire multi-item batch permanently unprocessable via any relayer, since the same unconditional `safeTransfer` failure recurs on every retry regardless of batching. Consequences:
- The specific request's escrowed protocol fee becomes permanently stuck in the `EvmHost` contract (loss of funds — no path exists to skip or forcibly resolve the transfer).
- If a relayer or the protocol batches multiple pending timeouts/responses together (which `HandlerV2`/`tesseract` batching logic explicitly encourages for gas efficiency), the presence of a single poisoned item blocks delivery/timeout-refund of every other legitimate item in that same call, denying other users' cross-chain settlement/timeout completion.
- This satisfies the bounty's fund-loss and logic-attack criteria (permanent lock of escrowed relayer fees, unauthorized blocking of legitimate settlement) and is not a "generic gas DoS" — it is a deterministic, attacker-plantable, batch-atomicity bug tied directly to fund custody.

### Likelihood Explanation
Reachable by any unprivileged user: `dispatch()` (to set an arbitrary `payer`) and `handlePostRequestTimeouts`/`handleGetRequestTimeouts`/`handleGetResponses` (all documented as permissionless) are public entry points requiring no relayer, prover, or admin collusion. The only external dependency is that `feeToken()` supports a blacklist/pause/hook mechanism capable of rejecting a specific address — a realistic condition for stablecoins like USDC that Hyperbridge is designed to support as `feeToken`.

### Recommendation
Wrap the fee-transfer calls in `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, and `dispatchTimeOut(PostRequestTimeout,...)` in a low-level `.call` (or try/catch) with the same "retryable" fallback pattern already used for the `IApp` callbacks, so a failed fee transfer degrades to a recoverable/claimable state (e.g., credit an internal withdrawable balance) rather than reverting the whole dispatch and blocking unrelated batch items.

### Proof of Concept
1. Deploy/observe `EvmHost` configured with a `feeToken` that supports address blacklisting (e.g., USDC-style token).
2. Attacker calls `IDispatcher(host).dispatch(DispatchPost{... payer: <address blacklisted by feeToken>, fee: X, timeout: small})`.
3. Wait for the request to time out.
4. Any relayer submits `handlePostRequestTimeouts` with a batch containing this timed-out request plus N other unrelated valid timed-out requests.
5. `EvmHost.dispatchTimeOut` succeeds through `onPostRequestTimeout`, then reaches `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)`, which reverts because `meta.sender` is blacklisted.
6. The revert propagates through `HandlerV2.handlePostRequestTimeouts`'s direct call, reverting the entire transaction — none of the N legitimate timeouts get processed, and this repeats for every future batch attempt including this request, permanently locking `X` fee tokens in the host and blocking any batch containing it.     function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
