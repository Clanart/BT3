### Title
Stale-diff-based "Discard Selected Lines" applies a zero-context patch without re-verifying file content, allowing silent corruption of tracked file contents - (`File: app/src/lib/git/apply.ts`)

### Summary
`discardChangesFromSelection` builds a `git apply` patch from a `diff` object that is handed in by the caller (ultimately from React component props / Redux-like store state) rather than re-reading the working directory at execution time, and applies it with `--unidiff-zero` (zero lines of context). This mirrors the report's root cause — an operation is executed against a value that is not re-validated against current ground truth at execution time, with no check that the assumption is still safe.

### Finding Description
`applyPatchToIndex` (used for partial commits) explicitly re-fetches a fresh diff via `getWorkingDirectoryDiff(repository, file)` right before formatting/applying the patch: [1](#0-0) 

In contrast, `discardChangesFromSelection` takes the `diff` as a caller-supplied parameter and uses it directly to build the patch with no re-fetch or re-validation against the current on-disk file: [2](#0-1) 

That `diff` originates from UI state (`Changes` component props) that was computed at some earlier point when the diff was rendered for the user, and is threaded through `onDiscardChanges` → `dispatcher.discardChangesFromSelection` without any freshness check: [3](#0-2) 

The resulting patch is applied with `apply --unidiff-zero --whitespace=nowarn` — i.e., zero context lines: [4](#0-3) 

`formatPatchToDiscardChanges` builds hunks purely from the stale `diff.hunks`/line offsets and the user's line `selection`, with no comparison against the file's live contents: [5](#0-4) 

This is the structural analog of the audited bug: the CVX contract executed a swap using a caller-supplied value (`minOut = 0`) with no check that the actual execution-time state still matched what was assumed safe. Here, Desktop executes a positional patch apply using a caller-supplied, potentially-stale `diff`/line-offset mapping with no check that the working-directory file still matches what was displayed to the user when they made their line selection.

### Impact Explanation
If the tracked file's on-disk content changes between the moment the diff shown to the user was computed and the moment the user confirms "Discard changes" for a line selection (e.g. because a git hook such as `post-checkout`/`post-merge`, a smudge/clean filter, or an external tool/editor autosave rewrites the file in the interim — all of which can be shipped by an attacker-controlled cloned/fetched repository via `.git/hooks` or `.gitattributes` filters), the zero-context patch is applied purely by line offset. Since there is no context to re-anchor against, and no revalidation step confirms the file is unchanged, applying the patch can silently discard/rewrite the wrong lines relative to what the user actually saw and approved, corrupting the working tree without any error or warning to the user. This falls under "silent corruption of what the user commits or pushes," since a corrupted working tree is what subsequently gets staged/committed.

### Likelihood Explanation
Exploitation requires an attacker-controlled repository to introduce a mechanism that mutates a tracked file's content in the background while Desktop already has a diff of that file loaded and the user is mid-selection (a window that is realistically achievable via checkout/merge/fetch-triggered git hooks or clean/smudge filters defined in that same repository, which do not require any user privilege beyond opening/cloning the repo). This is a timing-dependent, no-privilege path consistent with the "attacker controls a cloned/fetched repository" impact category, though it is less deterministic than a pure smart-contract MEV sandwich, since it depends on a hook firing in the relevant window rather than being reliably triggerable every time.

### Recommendation
Re-fetch/re-diff the file's current on-disk state immediately before constructing and applying the discard patch (mirroring what `applyPatchToIndex` already does for partial commits), and abort (surfacing an error to the user) if the live diff/hunks no longer match the `diff` object the user's selection was made against, rather than blindly applying a zero-context, offset-based patch.

### Proof of Concept
1. Clone an attacker-controlled repository containing a `post-checkout` (or equivalent) hook / clean-filter that rewrites a specific tracked file's content shortly after checkout/refresh events.
2. In GitHub Desktop, modify the file, open the Changes view so the diff/hunks are computed and cached in UI state, and select a subset of lines to discard.
3. Trigger a repository event that fires the hook while the discard dialog/selection is still open (e.g. a background refresh, branch operation, or fetch that runs the hook), causing the on-disk file to change.
4. Confirm "Discard changes" for the (now stale) selection; `discardChangesFromSelection` applies the old `diff`'s zero-context patch via `git apply --unidiff-zero` against the file's new content without re-validating it, corrupting the file silently.

Note: I was not able to execute this end-to-end in the sandbox (no filesystem/git execution available here) to empirically confirm `git apply --unidiff-zero`'s exact failure/success behavior against a mismatched file; this should be validated by a Devin session with repo access before treating it as a confirmed exploit rather than a design-level TOCTOU weakness.

```typescript
export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
```

```typescript
export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.newStartLine,
      newCount,
      hunk.header.oldStartLine,
      oldCount
    )
    patch += hunkBuf
  })

  if (patch.length === 0) {
    // The selection resulted in an empty patch.
    return null
  }

  return formatPatchHeader(filePath, filePath) + patch
}
```
