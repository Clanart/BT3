## Title
Stale line-index diff selections are not revalidated against a freshly re-fetched diff before staging, allowing silent corruption of partial commits - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
Desktop's partial-commit ("stage part of a file") feature represents a user's line selection as a set of *absolute line indices* (`DiffSelection`), computed against one snapshot of a file's diff. When the user commits, Desktop re-fetches the diff from disk a second time and reapplies those same absolute indices to the new diff without verifying they still refer to the same content. If the tracked file's content changes between the time the selection was made/refreshed and the time the patch is generated, the indices can silently point at different lines/hunks than the user selected, producing a patch that stages content the user never chose - the same class of bug as the reported Bundler issue, where a caller-controlled quantity ("repay amount"/"line selection") is not re-capped against the actual, current state ("bundler balance"/"current diff") before being consumed downstream.

### Finding Description
Two facts combine to break the invariant "a `DiffSelection`'s line indices are only meaningful relative to the exact diff they were computed from":

1. `DiffSelection` stores only raw integer line indices (`divergingLines: Set<number>`), with no reference back to the diff/content it was computed against. [1](#0-0) 

2. When the store background-refreshes the working directory diff for the currently selected file (e.g. after a filesystem watcher event fires because the file changed on disk), it explicitly does **not** remap or invalidate individual selected indices - it only recomputes the set of `selectableLines` and keeps whatever indices were already marked selected, filtered by that new set. The code comment acknowledges this is a known compromise: [2](#0-1) 

If a previously-selected absolute index still happens to fall on a line that is "includeable" in the new diff (e.g. lines shifted due to an edit elsewhere in the file, or unrelated content changed at that same offset), that index remains "selected" even though it now corresponds to entirely different text than what the user actually clicked.

3. Independently of the UI-cached diff, when the commit is actually created, `stageFiles` calls `applyPatchToIndex` for every partially-selected file, and `applyPatchToIndex` re-fetches the working directory diff **yet again** from disk (a third, independent snapshot), rather than reusing the diff the UI selection was validated against: [3](#0-2) [4](#0-3) 

4. `formatPatch` then walks this brand-new diff's hunks and simply asks `file.selection.isSelected(absoluteIndex)` for each line, with no check that `absoluteIndex` still means what it meant when the user made the selection: [5](#0-4) 

There is no analogue of "cap the amount to the bundler's balance" here - i.e. no step that says "if the diff used to build this selection no longer matches the diff on disk, abort/refresh/reconfirm the selection." The stale index set is trusted and forwarded straight into `git apply --cached`, exactly like the report's `type(uint256).max` amount being forwarded to `AAVE_V3_OPTIMIZER.repay` without being capped to the bundler's actual balance.

### Impact Explanation
If the tracked file's content in the working directory is modified by anything other than the user's explicit edit in the moment between diff-render/selection and clicking "Commit" - for example, by a repository-defined tool that runs automatically on the developer's machine as part of normal onboarding (e.g. a `core.hooksPath`-based, repository-tracked pre-commit/lint-staged hook that reformats staged files, a common and widely adopted pattern), or non-deterministic smudge/filter/LFS content fetched from the (attacker-controlled) origin remote - the final patch built by `formatPatch`/`applyPatchToIndex` can include or exclude the wrong hunks relative to what the user visually reviewed and selected. This is a silent corruption of what the user commits: the user believes they excluded certain lines (e.g. a secret, a debug statement, or unrelated code) from the commit, but the stale index reuse causes different lines to be staged and pushed instead, or vice versa - lines the user intended to include get silently dropped.

### Likelihood Explanation
This requires no local/physical access, no admin rights, and no pre-existing malware: it only requires ordinary developer workflows where tracked-file content can change automatically in response to a checkout/hook/filter that ships as part of a cloned repository's configuration, combined with Desktop's normal filesystem-watcher-driven diff refresh and its independent, unsynchronized diff re-fetch at commit time. The relevant code path (`updateChangesWorkingDirectoryDiff`) already documents that it doesn't fully validate selection state against new diff content, confirming this is a known, reachable gap rather than a hypothetical one.

### Recommendation
Bind a `DiffSelection` (or at least its partial-selection state) to an identifier/hash of the diff it was computed from, and:
- When refreshing the working-directory diff for a selected file, if the underlying diff content has materially changed (not just shifted line counts), clear or fully re-derive the partial selection instead of only filtering by `selectableLines`.
- In `stageFiles`/`applyPatchToIndex`, reuse the exact diff object the selection was validated against (or re-diff and abort/re-prompt the user if it no longer matches) rather than blindly re-fetching a new diff and reapplying old indices to it.

### Proof of Concept
1. Open a repository in Desktop with a modified, tracked file containing several hunks.
2. Select a partial set of lines for the commit (e.g. lines 10-12 selected, rest excluded), as tracked by `DiffSelection.divergingLines`.
3. Before clicking Commit, have some external, repo-defined mechanism (e.g. a `core.hooksPath` pre-commit/format hook configured by the cloned project, or a filesystem watcher-triggered formatter) rewrite the file so that hunk boundaries shift while keeping the total number of "includeable" lines at the previously-selected absolute indices.
4. Desktop's `updateChangesWorkingDirectoryDiff` refreshes `selectableLines` but keeps the old `divergingLines` indices selected (`app/src/lib/stores/app-store.ts:3478-3497`).
5. On commit, `applyPatchToIndex` re-fetches the diff a third time and `formatPatch` builds a patch from `file.selection.isSelected(absoluteIndex)` against this new diff (`app/src/lib/git/apply.ts:60-81`, `app/src/lib/patch-formatter.ts:143-171`), staging/committing different content than what the user visually selected, with no error or warning shown to the user.
