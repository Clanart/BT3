### Title
Unguarded concurrent `git fetch` via `_fetchRefspec` can race with in-progress push/pull operations - ([File: app/src/lib/stores/app-store.ts])

### Summary
Similar to the Napier `requestWithdrawal` bug — where a state-changing calculation failed to account for another operation already in flight — GitHub Desktop's `AppStore._fetchRefspec` performs a network `git fetch` while explicitly and intentionally skipping the app's own "no concurrent network operation" guard, `withPushPullFetch`. This method is reachable when a user views a pull request from a fork, meaning an attacker who controls a fork/PR can cause a git fetch to race against a legitimate, in-progress push or pull on the same working copy.

### Finding Description
All "normal" network operations (`_pull`, `_fetch`, `_fetchRemote`, push) are funneled through `withPushPullFetch`, which sets `isPushPullFetchInProgress` and bails out early if a network operation is already running: [1](#0-0) 

However, `_fetchRefspec` — used to fetch a PR head ref when a user is viewing a pull request from a fork — deliberately does not use this guard. The code comment acknowledges this: [2](#0-1) 

Because this method is not serialized against `isPushPullFetchInProgress`, it can execute a `git fetch` (via `gitStore.fetchRefspec` → `fetchRefspec()` in `app/src/lib/git/fetch.ts`) at the same time as a user-initiated push (`performPush`) or pull (`performPull`), both of which run non-atomic, multi-step git sequences (`pushRepo` → `fetchRemotes` → `fastForwardBranches` → `_refreshRepository`) against the very same repository working directory: [3](#0-2) [4](#0-3) 

This is exactly the pattern in the report: an operation (`_fetchRefspec`) that mutates shared repository state without accounting for another operation (`push`/`pull`) already "pending" — the analog of the pending-withdrawal amount not being deducted before a new withdrawal is calculated. Here, the "shared resource" is the repository's `.git` directory (refs, `FETCH_HEAD`, index, `packed-refs`) instead of an ETH buffer, but the broken invariant is the same: state-changing operations must serialize against pending operations, and one code path explicitly doesn't.

### Impact Explanation
Since git does not guarantee full concurrency safety when index/ref-writing operations run in parallel in the same repository, an attacker who controls a fork (i.e., opens a malicious PR that a victim opens in Desktop, or otherwise causes Desktop to view/preview a PR from their fork) can force `_fetchRefspec` to run at an attacker-chosen moment relative to the victim clicking "Push" or "Pull". This can interleave ref updates and fast-forward operations (`fastForwardBranches` uses `--stdin` with computed `upstreamRef:ref` pairs) with the victim's own push/pull sequence, risking:
- Silent corruption of local branch refs or `FETCH_HEAD` state mid-push/pull.
- The victim's push completing against a ref state that has been mutated by an unrelated, attacker-triggered fetch, causing the wrong commits to be interpreted as "pushed" or a fast-forward to be computed against stale/racy data.

This falls under "silent corruption of what the user commits or pushes," one of the explicitly valid impact classes, and requires no local access, admin rights, or social engineering beyond the normal Desktop workflow of viewing a PR from a fork (which is a first-class, expected, attacker-reachable action in Desktop).

### Likelihood Explanation
The likelihood is constrained by timing: the attacker needs the victim to be actively pushing/pulling while viewing (or Desktop internally re-fetching for) their PR/fork. This is plausible in collaborative workflows where reviewers keep a PR/fork tab open while also syncing their own branches, but it is not deterministically triggerable by the attacker alone — it depends on this race window coinciding with victim-initiated git operations. The comment in the code itself flags this as a known, unresolved risk ("This might require some rework in the future to chain these actions"), which is direct maintainer acknowledgment that the guard is intentionally missing without a compensating protection.

### Recommendation
Route `_fetchRefspec` through the same serialization mechanism as other network operations (`withPushPullFetch`), or introduce a lightweight per-repository mutex/queue so refspec fetches are chained after any in-progress push/pull/fetch completes rather than running concurrently, mirroring the report's recommendation to account for pending operations before performing a state-changing action.

### Proof of Concept
1. Victim opens GitHub Desktop and views a pull request opened from an attacker-controlled fork (this indirectly or directly triggers `_fetchRefspec` for the fork's head ref).
2. At the same time, the victim clicks "Push" (or "Pull") on their current repository, invoking `performPush`/`performPull`, which are protected by `withPushPullFetch`/`isPushPullFetchInProgress`.
3. Because `_fetchRefspec` bypasses this guard, its `git fetch <fork-remote> <refspec>` process executes concurrently with the victim's ongoing push/pull's own git subprocess sequence (`pushRepo` → `fetchRemotes` → `fastForwardBranches`), both operating on the same `.git` directory.
4. Depending on timing, this can result in racing ref/index writes, an inconsistent local ref state observed by `_refreshRepository`, or a push/pull operation completing against a repository state altered mid-flight by the unrelated fetch — without any explicit warning or serialization to the user.   private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

/** Fetch a given refspec from the given remote. */
export async function fetchRefspec(
  repository: Repository,
  remote: IRemote,
  refspec: string
): Promise<void> {
  await git(['fetch', remote.name, refspec], repository.path, 'fetchRefspec', {
    successExitCodes: new Set([0, 128]),
    env: await envForRemoteOperation(remote.url),
  })
}
