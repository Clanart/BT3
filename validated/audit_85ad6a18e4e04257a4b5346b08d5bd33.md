## Analog Found: Unbounded `order.inputs` / `output.assets` array with no cap, used in escrow lock/unlock paths

### Title
Unbounded, attacker-controlled `Order.inputs`/`output.assets` array length can permanently lock escrowed funds in `IntentGatewayV2` - (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core invariant is: an owner-controlled but *unbounded* storage array is iterated in a critical accounting function, so once the array grows past a certain size the function always reverts, and there is no mechanism to shrink it back — the recommended fix was to add a hard cap. `IntentGatewayV2.placeOrder()` has the same structural flaw, except the array length is controlled by an *unprivileged, arbitrary caller* (any user placing an order), not an owner. Neither `placeOrder` in the EVM version [1](#0-0)  nor the Tron variant [2](#0-1)  enforces any maximum on `order.inputs.length` or `order.output.assets.length` — only a non-zero check exists (`if (order.inputs.length == 0) revert InvalidInput();`) [3](#0-2) .

### Finding Description
`placeOrder` escrows tokens by looping over `order.inputs` multiple times (fee calculation, transfer, and escrow crediting) [4](#0-3) , storing one balance entry per input token in `_orders[commitment][token]` [5](#0-4) .

Later, the *only* two paths that can release that escrow — a successful fill (`fillOrder` → `withdraw`) and a cancellation/refund (`cancelOrder` → `withdraw` via `onGetResponse`) — must iterate the exact same-length `body.tokens` array in a single transaction to release/refund each token [6](#0-5) . `fillOrder` explicitly requires `order.inputs.length == order.output.assets.length` before routing to the fill logic [7](#0-6) , meaning both arrays are attacker-supplied at `placeOrder` time and neither is size-capped anywhere in the constructor, `initialize`, or `_validateParams` logic reachable from the search performed.

Because a user calling `placeOrder` fully controls both the number of input tokens and output tokens in their own `Order` struct, they can construct an order with a very large number of distinct token entries (e.g., hundreds of dummy ERC-20 tokens, or repeated distinct addresses up to calldata/array limits). Escrowing the tokens at `placeOrder` time can be done incrementally / is bounded by the user's own gas budget, but unlocking that escrow — via `withdraw()` inside either `fillOrder` or `cancelOrder`/`onGetResponse` — requires iterating the *entire* array (ERC20 `transfer` calls, one per token, each costing tens of thousands of gas) in one atomic transaction. Once the array is large enough that this loop exceeds the destination or source chain's block gas limit, `withdraw()` will always revert, and there is no partial-withdrawal or per-token unlock mechanism, no admin recovery path, and no cap analogous to the "maximum limit" fix applied to `LockedStaking.getRewardsWeight()`.

### Impact Explanation
This directly causes loss/lock of user funds: tokens escrowed via `placeOrder` become permanently unrecoverable once the input/output array is large enough to blow the gas limit in `withdraw()`, since both the fill and refund/cancel code paths funnel through the same unbounded loop. This matches the bounty's accepted impact class ("stealing or loss of funds", "logic attacks") — it is reachable by any unprivileged user acting alone (self-inflicted or, more importantly, weaponizable against solvers: a malicious "victim" order can be crafted so that once a solver commits fill-side output tokens or a source escrow is created, neither the solver's fill nor the user's own cancel/refund can ever complete, permanently freezing the escrowed value on-chain).

### Likelihood Explanation
Likelihood is high: `placeOrder` is a fully public, unprivileged entry point, and nothing prevents supplying dozens to hundreds of `TokenInfo` entries in `order.inputs` and `order.output.assets`. No fee, bond, or size limit gates the array length before escrow commitments are made. The exact number of entries needed to exceed a block gas limit depends on target-chain gas cost per ERC20 transfer/`safeTransferFrom`, but well within calldata limits of a single transaction such thresholds are achievable, especially on L2s with lower per-block gas limits.

### Recommendation
Enforce a `MAX_INPUTS` / `MAX_OUTPUTS` cap in `placeOrder` (mirroring the post-audit fix applied to `LockedStaking`), rejecting orders whose `inputs.length` or `output.assets.length` exceeds a bounded, gas-safe constant. Additionally, consider making `withdraw()` resumable/per-token rather than requiring a single atomic loop over the entire token set, so that even legitimately large orders cannot brick escrow release.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs` containing N (e.g., 300+) distinct dummy ERC-20 token entries and `order.output.assets` with a matching N output entries (satisfying `fillOrder`'s `order.inputs.length == outputsLen` check) [8](#0-7) .
2. `placeOrder` escrows all N tokens, recording N storage entries in `_orders[commitment][token]` [5](#0-4) .
3. A solver attempts `fillOrder`, or the user attempts `cancelOrder`; both eventually call `withdraw(body, ...)` which loops over `body.tokens` (length N) performing an ERC-20/native transfer per iteration [9](#0-8) .
4. With N large enough, the single-transaction gas cost of this loop exceeds the chain's block gas limit; the transaction always reverts (`out of gas`), for both the fill and cancel/refund paths, since both share the identical `withdraw` loop.
5. Escrowed tokens for that commitment remain locked in the contract indefinitely, with no alternate recovery function exposed.

Note: I was not able to locate any `_validateParams` bound, external cap constant, or governance-settable maximum for `inputs.length`/`output.assets.length` in the portions of `IntentGatewayV2.sol` retrieved; if such a bound exists elsewhere in the file outside the indexed/retrieved ranges, it would invalidate this finding — this should be verified directly against the full contract source in a Devin session, since the codebase index used here may not include the complete file.

                ++i;

                tstore(token, 0)

                        value: 0,

            // Reject duplicate input tokens
            if (_orders[commitment][token] != 0) revert InvalidInput();
            _orders[commitment][token] = reducedInputs[i].amount;

            unchecked {
                ++i;
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
