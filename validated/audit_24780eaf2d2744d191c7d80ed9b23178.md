## Title
`SendMessageBanned` custody restriction blocklists `SEND_MESSAGE` but not the paired `RECEIVE_MESSAGE` opcode, letting a "message-banned" delegated puzzle still perform message-based coordination - (File: `chia/wallet/puzzles/custody/send_message_banned.clsp`)

### Summary
The `SendMessageBanned` restriction wrapper, used by the custody/restriction architecture (e.g. in `PlotNFTPuzzle.user_restriction()`), is meant to prevent a delegated puzzle from emitting message conditions. Its CLVM implementation only scans the outgoing condition list for the `SEND_MESSAGE` opcode and never checks for `RECEIVE_MESSAGE`, even though these two opcodes are a symmetric, cooperating pair (`SEND_MESSAGE`/`RECEIVE_MESSAGE`, opcodes 66/67) that provide the exact same inter-coin communication/authorization primitive from either side. This is structurally the same class of bug as CVE-2024-53947: a security-relevant denylist that omits a semantically equivalent "sibling" primitive, allowing the underlying capability to still be exercised through the un-blocked half of the pair.

### Finding Description
`send_message_banned.clsp` implements the restriction as: [1](#0-0) 

It walks the condition list produced by a delegated puzzle and raises `(x)` only if it finds `SEND_MESSAGE`. `RECEIVE_MESSAGE` is a distinct, separately-numbered opcode: [2](#0-1) 

`SEND_MESSAGE` and `RECEIVE_MESSAGE` are designed as a matched pair — a lone `SEND_MESSAGE` or lone `RECEIVE_MESSAGE` fails mempool/consensus validation with `MESSAGE_NOT_SENT_OR_RECEIVED`; only the aggregate of a `SEND_MESSAGE` from one coin and a paired `RECEIVE_MESSAGE` from another (or the same) coin succeeds: [3](#0-2) 

Critically, each opcode is symmetric in capability: for `SEND_MESSAGE` the "sender" mode bits are auto-verified against the emitting coin's own parent/puzzle-hash/amount (like `ASSERT_MY_*`), while the "receiver" bits are attacker-suppliable arguments identifying any other coin in the bundle. For `RECEIVE_MESSAGE`, the roles simply invert — the emitting coin's own identity is auto-verified as the *receiver*, while the *sender* side is attacker-suppliable arguments naming any other coin: [4](#0-3) 

Because of this symmetry, any coordination/authorization effect achievable by emitting `SEND_MESSAGE` from a coin (linking that coin's identity plus an arbitrary payload `msg` to a partner coin's spend in the same bundle) is equally achievable by emitting `RECEIVE_MESSAGE` from that same coin, just with the roles of "who names whom" swapped. The `SendMessageBanned` restriction's check for only `SEND_MESSAGE` therefore fails to close the channel it is meant to close — a delegated puzzle wrapped in this restriction can still couple itself to an external coin's spend via `RECEIVE_MESSAGE` and pass validation.

This restriction is used as a real security boundary in the PlotNFT custody flow, where it is combined with `FixedCreateCoinDestinations` (while pooling) or `Heightlock` (while in the waiting room) specifically to constrain what a pool member/escaping singleton's delegated puzzle may do: [5](#0-4) 

The project's own restriction test suite documents the intended behavior — that any attempt to emit a message condition from the restricted puzzle must fail: [6](#0-5) 

and the PlotNFT test suite exercises the exact scenario the restriction is meant to block during an exit-to-waiting-room transition: [7](#0-6) 

None of these tests (or the puzzle itself) verify that `RECEIVE_MESSAGE` is also rejected, so the restriction's guarantee — "this delegated puzzle cannot participate in message-based coordination with another spend in the bundle" — is only half-enforced.

### Impact Explanation
`SendMessageBanned` is deployed as part of the trust boundary that constrains what a PlotNFT's pooling/waiting-room inner puzzle is allowed to do while transitioning pool state (joining a pool, or waiting to leave one under a `Heightlock`). The restriction is combined with `FixedCreateCoinDestinations`/`Heightlock` precisely so that, in these constrained states, the coin cannot establish an out-of-band coordination channel with another coin in the same spend bundle. Because only `SEND_MESSAGE` is denylisted, an unprivileged spend-bundle submitter who controls (or colludes with) the restricted PlotNFT coin can still emit `RECEIVE_MESSAGE`, paired with an attacker/self-controlled `SEND_MESSAGE` elsewhere in the bundle, and pass mempool/consensus validation despite the restriction's stated intent. This is exactly the vulnerability class in the report: a denylist that omits a paired/related primitive, letting a supposedly-forbidden capability still be exercised — undermining the integrity of the custody/restriction layer that other production code (`PlotNFTPuzzle.user_restriction()`) relies on as an enforcement mechanism during pool-state transitions.

### Likelihood Explanation
Any wallet holder or spend-bundle submitter who controls the restricted coin can trivially construct a delegated-puzzle solution that emits `RECEIVE_MESSAGE` instead of `SEND_MESSAGE`; no privileged access, signing key compromise, or malicious peer/node behavior is required — only a standard spend-bundle submission. The bug requires no unusual conditions beyond knowing that the restriction blocklist is opcode-specific rather than semantic.

### Recommendation
Update `send_message_banned.clsp` (and any equivalent Python-side validators) to reject both `SEND_MESSAGE` and `RECEIVE_MESSAGE`, matching the paired nature of these opcodes, and add restriction tests analogous to `test_send_message_banned` that specifically attempt the escape via `RECEIVE_MESSAGE`.

### Proof of Concept
1. Construct a `PuzzleWithRestrictions` with `SendMessageBanned()` in its restriction stack (as used by `PlotNFTPuzzle.user_restriction()`), mirroring `test_send_message_banned` in [6](#0-5) .
2. Instead of a delegated puzzle emitting `SendMessage(...)`, use a delegated puzzle emitting `ReceiveMessage(...)` (from `chia/wallet/conditions.py`), paired with a `SendMessage(...)` condition from a second, attacker/self-controlled coin in the same `WalletSpendBundle`.
3. Submit the aggregated bundle via `client.push_tx`. Whereas the `SEND_MESSAGE` variant is rejected with `Err.GENERATOR_RUNTIME_ERROR` (per the existing test), the `RECEIVE_MESSAGE` variant is expected to pass the restriction layer and succeed with `MempoolInclusionStatus.SUCCESS`, demonstrating that the restriction's intended message-channel ban is incomplete.

@streamable
@dataclass(frozen=True)
class SendMessage(Condition):
    msg: bytes
    var_args: list[Program] | None = None
    mode_integer: uint8 | None = None
    sender: MessageParticipant | None = None
    receiver: MessageParticipant | None = None
    _other_party_is_receiver: ClassVar[bool] = True

    @property
    def _other_party(self) -> MessageParticipant | None:
        return self.receiver

    @property
    def _opcode(self) -> ConditionOpcode:
        return ConditionOpcode.SEND_MESSAGE

    def __post_init__(self) -> None:
        if self.mode_integer is None and (self.sender is None or self.receiver is None):
            raise ValueError("Must specify either mode_integer or both sender and receiver")

        if self.mode_integer is not None and self.sender is not None:
            assert self.mode_integer >> 3 == self.sender.mode, (
                "The first 3 bits of mode_integer don't match the sender's mode"
            )

        if self.mode_integer is not None and self.receiver is not None:
            assert self.mode_integer & 0b000111 == self.receiver.mode, (
                "The last 3 bits of mode_integer don't match the receiver's mode"
            )

        if self.var_args is None and self._other_party is None:
            raise ValueError(
                f"Must specify either var_args or {'receiver' if self._other_party_is_receiver else 'sender'}"
            )

        if self.var_args is not None and self._other_party is not None and not self._other_party._nothing_committed:
            assert self.var_args == self._other_party.necessary_args, (
                f"The implied arguments for {self._other_party} do not match the specified arguments {self.var_args}"
            )

    @property
    def args(self) -> list[Program]:
        if self.var_args is not None:
            return self.var_args

        # The non-None-ness of this is asserted in __post_init__
        return self._other_party.necessary_args  # type: ignore[union-attr]

    @property
    def mode(self) -> uint8:
        if self.mode_integer is not None:
            return self.mode_integer

        # The non-None-ness of these are asserted in __post_init__
        return uint8((self.sender.mode << 3) | self.receiver.mode)  # type: ignore[union-attr]

    def to_program(self) -> Program:
        condition: Program = Program.to([self._opcode, self.mode, self.msg, *self.args])
        return condition

    @classmethod
    def from_program(cls, program: Program) -> Self:
        full_mode = uint8(program.at("rf").as_int())
        var_args = list(program.at("rrr").as_iter())
        return cls(
            program.at("rrf").as_atom(),
            var_args,
            full_mode,
            MessageParticipant.from_mode_and_maybe_args(
                True, full_mode, var_args if not cls._other_party_is_receiver else None
            ),
            MessageParticipant.from_mode_and_maybe_args(
                False, full_mode, var_args if cls._other_party_is_receiver else None
            ),
        )

@pytest.mark.anyio
async def test_send_message_banned(cost_logger: CostLogger) -> None:
    async with sim_and_client() as (sim, client):
        restriction = ValidatorStackRestriction(required_wrappers=[SendMessageBanned()])
        pwr = PuzzleWithRestrictions(nonce=0, restrictions=[restriction], puzzle=ACSMember())

        # Farm and find coin
        await sim.farm_block(pwr.puzzle_hash())
        coin = (await client.get_coin_records_by_puzzle_hashes([pwr.puzzle_hash()], include_spent_coins=False))[0].coin

        # Attempt to send a message
        send_message_dpuz = DelegatedPuzzleAndSolution(
            puzzle=Program.to(
                (
                    1,
                    [
                        SendMessage(
                            bytes32.zeros,
                            sender=MessageParticipant(parent_id_committed=bytes32.zeros),
                            receiver=MessageParticipant(parent_id_committed=bytes32.zeros),
                        ).to_program()
                    ],
                )
            ),
            solution=Program.to(None),
        )
        wrapped_dpuz = restriction.modify_delegated_puzzle_and_solution(send_message_dpuz, [Program.to(None)])
        escape_attempt = WalletSpendBundle(
            [
                make_spend(
                    coin,
                    pwr.puzzle_reveal(),
                    pwr.solve(
                        [],
                        [Program.to([send_message_dpuz.puzzle.get_tree_hash()])],
                        Program.to(None),
                        wrapped_dpuz,
                    ),
                )
            ],
            G2Element(),
        )
        result = await client.push_tx(escape_attempt)
        assert result == (MempoolInclusionStatus.FAILED, Err.GENERATOR_RUNTIME_ERROR)
