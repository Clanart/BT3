## Finding [1](#0-0) 

### Title
IntentGateway settlement transfers `order.fees` using the *current* `feeToken()` instead of the token actually escrowed at placement, causing wrong-token/wrong-amount transfers or stuck settlements after a host fee-token rotation - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.placeOrder` collects `order.fees` in whatever ERC-20 is currently configured as `EvmHost.feeToken()` at placement time and records only the numeric amount under `_orders[commitment][TRANSACTION_FEES]` — it never records *which token* was collected. At settlement (`IntentsBase._withdraw`, invoked from `RedeemEscrow`/`RefundEscrow` handling and from same-chain cancel/fill paths), the contract re-reads `IDispatcher(host()).feeToken()` **at settlement time** and transfers `fees` units of *that* token to the beneficiary. If the host's `feeToken` is rotated between order placement and settlement, the amount recorded in the old token's units is paid out in the new token, silently mispricing the payout (or reverting/locking the order if the gateway lacks sufficient balance of the new token).

### Finding Description
Fee collection at placement: [1](#0-0) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    ...
    IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    _orders[commitment][TRANSACTION_FEES] = order.fees;
}
```

Only the *amount* is persisted; the token identity is implicit and never re-checked.

Fee payout at settlement: [2](#0-1) 

```solidity
if (finalize) {
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        delete _orders[body.commitment][TRANSACTION_FEES];
        IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
    }
```

`host().feeToken()` is dereferenced fresh here, not the token that was actually pulled from the user at placement. This is structurally identical to the Reality Cards bug: a governance-configurable divisor/parameter (`minRentalDayDivisor` there, `feeToken` here) is baked into a calculation/escrow at one point in time, but a *different* function re-reads the *current* value of that same parameter, producing inconsistent results across the object's lifetime.

The EvmHost's own protection against this class of issue does not cover downstream apps: [3](#0-2) 

```solidity
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
```

This guard only checks the *EvmHost's own* balance of the old fee token, not balances held by `IApp` modules such as `IntentGatewayV2`. Escrowed `TRANSACTION_FEES` sit in the gateway contract, not in the host, so the host's `CannotChangeFeeToken` check is entirely blind to in-flight IntentGateway orders and does not prevent the rotation that breaks them. The gateway itself has no equivalent guard — `setParams`/`ParamsUpdate` governance flow updates `_params` but never revalidates or migrates outstanding `TRANSACTION_FEES` balances against a token change on the host.

### Impact Explanation
Any order with `order.fees > 0` that is still open (unfilled/unsettled) when the Hyperbridge host's `feeToken` is rotated will have its recorded fee amount reinterpreted in a different ERC-20 at redemption:
- If the gateway holds a sufficient balance of the new fee token (e.g., accumulated dust, or another order's escrowed input happens to be denominated in the new token), the beneficiary/filler receives an amount of the wrong token, and the transfer silently succeeds while draining balances that belong to unrelated orders/users.
- If the gateway does not hold enough of the new token, `safeTransfer` reverts, and since this call is inside the same `_withdraw` finalize path used by `RedeemEscrow`/`RefundEscrow`/same-chain fill and cancel, the entire settlement reverts — permanently blocking release of the principal escrow (input tokens) alongside the fee, locking user/solver funds.

This is a fund-loss / fund-lock outcome reachable purely by the ordinary passage of time around a routine, protocol-anticipated operation (fee-token rotation is explicitly documented as expected behavior elsewhere in the codebase), not by any malicious relayer, prover, or compromised key.

### Likelihood Explanation
Fee-token rotation is a normal, supported host operation (the codebase explicitly notes "the host occasionally swaps fee tokens"). Any order with a nonzero `order.fees` that remains open across such a rotation — which can take arbitrarily long for cross-chain orders awaiting solver fill or cancellation — is silently affected. No attacker action is needed at all: the victim is simply an ordinary user/solver whose order happens to straddle the rotation window.

### Recommendation
Record the fee token address alongside the fee amount at placement time (e.g., store `(token, amount)` instead of a bare `uint256` under `TRANSACTION_FEES`), and use that stored token identity — not the live `host().feeToken()` — when paying out fees during `_withdraw`. Alternatively, mirror `EvmHost.CannotChangeFeeToken`'s intent at the gateway level: track the gateway's own committed fee-token liabilities and reject host `feeToken` updates (or require an explicit sweep/migration) while outstanding `TRANSACTION_FEES` balances exist in the old token.

### Proof of Concept
1. Deploy `IntentGatewayV2` bound to an `EvmHost` whose `feeToken()` is Token A.
2. User calls `placeOrder` with `order.fees = 100` (Token A). Gateway pulls 100 Token A from the user; `_orders[commitment][TRANSACTION_FEES] = 100`.
3. Before the order is filled/cancelled, Hyperbridge governance dispatches `updateHostParams` on the host with `feeToken = Token B` (allowed because the *host's* Token A balance is 0 — it never held the escrowed fee, the gateway did).
4. Order settles via `RedeemEscrow`/`RefundEscrow` → `IntentsBase._withdraw` executes `IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, 100)`, i.e., transfers 100 units of Token B (not Token A) if the gateway holds ≥100 Token B from unrelated activity, or reverts (blocking the whole settlement, including the escrowed principal) if it does not.
