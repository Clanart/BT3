### Title
Overwritten `mostRecentSSHCredentials` entry causes wrong SSH credential to survive/被 discarded on auth failure - (File: `app/src/lib/ssh/ssh-credential-storage.ts`)

### Summary
The Behodler bug stems from a single mutable tracking slot (`pendingFlashDecision[targetContract][user]`) being reset to a default value by one action (`burnFlashGovernanceAsset`) instead of being deleted, so a later, unrelated action (`withdrawGovernanceAsset` for a *different* deposit) reads that stale default and incorrectly treats itself as unlocked. The same "single overwritable slot shared across sequential events for one identifier" pattern exists in Desktop's SSH askpass/credential-remember flow: a `Map<string, SSHCredentialEntry>` keyed only by the trampoline `operationGUID` (one git operation), where each new askpass prompt during that same operation overwrites the previous entry rather than tracking prompts independently.

### Finding Description
`mostRecentSSHCredentials` is a `Map` keyed solely by `operationGUID`, which is the trampoline token for the *entire* ongoing git operation, not per SSH-key/prompt: [1](#0-0) 

`setMostRecentSSHCredential`/`setSSHCredential` simply calls `.set(operationGUID, { store, key })`, unconditionally overwriting whatever was previously tracked for that operation: [2](#0-1) 

The askpass handler calls this for *every* passphrase/password prompt it services during one git operation: [3](#0-2) [4](#0-3) 

A single git operation (clone/fetch/push) can legitimately trigger multiple sequential askpass prompts — e.g. SSH tries several keys in turn, or a server/proxy repeatedly rejects and re-prompts ("Permission denied, please try again"). Because SSH's retry behavior is driven by the remote server's responses, a **malicious or misbehaving SSH remote/proxy the user is cloning/fetching from can force multiple sequential prompts within the same trampoline token/operation**. Each prompt the user answers with "remember this" calls `setSSHCredential`, which persists the secret to the OS keychain via `TokenStore.setItem` *and* overwrites the single `mostRecentSSHCredentials` entry for that operation: [5](#0-4) 

If the overall git operation ultimately fails with an SSH authentication error, `withTrampolineEnv`'s catch handler calls `deleteMostRecentSSHCredential(token)` to clean up the *supposedly* bad credential: [6](#0-5) [7](#0-6) 

Because the map holds only the *last-seen* `{store, key}` pair per operation (exactly like Behodler resetting to a single default struct instead of tracking/deleting the correct per-decision entry), this cleanup deletes the wrong entry whenever more than one credential was remembered during the same operation. The credential that actually caused the auth failure (an earlier prompt in the sequence) is never purged from the OS keychain, while a different, possibly valid, later-entered credential is silently discarded instead.

### Impact Explanation
The corrupted value is the single `mostRecentSSHCredentials.get(operationGUID)` slot, which should logically track "the most recently entered-but-unverified credential" but instead only tracks the *last* of potentially several unrelated prompts serviced under one operation token. The practical effect: a bad/expired/malicious-server-influenced passphrase or password remains permanently cached in the OS credential store (`TokenStore`) and will be transparently supplied on all future SSH operations to that key (`getSSHKeyPassphrase`), silently corrupting the user's future authentication attempts without their knowledge — while the credential the user actually wanted forgotten (because it failed) may be the one erroneously deleted. A malicious remote that intentionally sequences multiple key/password prompts can engineer which credential is "protected" from cleanup.

### Likelihood Explanation
This requires an attacker-controlled or misbehaving SSH remote/proxy that the victim is actively cloning, fetching from, or pushing to — it does not require local access, admin rights, or prior compromise, matching the valid-impact criteria (attacker controls a fetched/cloned repository's remote/proxy responses). The multi-prompt sequence (server rejecting one key/credential then re-prompting) is a normal SSH interaction pattern that a hostile server can trigger deliberately, so the precondition is realistic, though it does depend on the user choosing "remember" at more than one prompt within a single operation.

### Recommendation
Key `mostRecentSSHCredentials` (and the corresponding SSH passphrase/password tracking) by both the `operationGUID` and the specific `store`/`key` pair (e.g., use a `Map<string, SSHCredentialEntry[]>` or a compound key), so each prompt's remembered credential is tracked independently and `deleteMostRecentSSHCredential` can purge *all* credentials attempted during a failed operation rather than only the last one.

### Proof of Concept
1. Attacker controls (or man-in-the-middles) an SSH git remote.
2. Victim runs `git fetch`/clone against that remote in Desktop; the malicious server first prompts for key A's passphrase (user enters and checks "remember"), causing `setSSHKeyPassphrase(token, keyA, pass)` → `mostRecentSSHCredentials.set(token, {store, keyA})` and persists `pass` to the OS keychain.
3. Server then rejects and issues a second prompt for key B's passphrase (user enters and checks "remember"), causing `setSSHKeyPassphrase(token, keyB, pass2)` → `mostRecentSSHCredentials.set(token, {store, keyB})`, overwriting the tracked entry for key A.
4. Git ultimately fails with `SSHAuthenticationFailed` for key A's now-known-bad passphrase.
5. `withTrampolineEnv`'s catch handler calls `deleteMostRecentSSHCredential(token)`, which deletes only key B's entry — key A's invalid/attacker-influenced passphrase remains cached in the OS keychain and will be auto-supplied (`getSSHKeyPassphrase`) on all future operations against that key without further user consent. /**
 * Deletes the SSH credential from the TokenStore. Used when the git operation
 * fails to authenticate.
 */
export async function deleteMostRecentSSHCredential(operationGUID: string) {
  const entry = mostRecentSSHCredentials.get(operationGUID)
  if (entry) {
    log.info(
      `SSH auth failed, deleting credential for ${entry.store}:${entry.key}`
    )

    await TokenStore.deleteItem(entry.store, entry.key)
  }
}

async function handleSSHKeyPassphrase(
  operationGUID: string,
  prompt: string
): Promise<string | undefined> {
  const promptRegex = /^Enter passphrase for key '(.+)': $/

  const matches = promptRegex.exec(prompt)
  if (matches === null || matches.length < 2) {
    return undefined
  }

  let keyPath = matches[1]

  // The ssh bundled with Desktop on Windows, for some reason, provides Unix-like
  // paths for the keys (e.g. /c/Users/.../id_rsa). We need to convert them to
  // Windows-like paths (e.g. C:\Users\...\id_rsa).
  if (__WIN32__ && /^\/\w\//.test(keyPath)) {
    const driveLetter = keyPath[1]
    keyPath = keyPath.slice(2)
    keyPath = `${driveLetter}:${keyPath}`
  }

  const storedPassphrase = await getSSHKeyPassphrase(keyPath)
  if (storedPassphrase !== null) {
    // Keep this stored passphrase around in case it's not valid and we need to
    // delete it if the git operation fails to authenticate.
    await setMostRecentSSHKeyPassphrase(operationGUID, keyPath)
    return storedPassphrase
  }

  if (getIsBackgroundTaskEnvironment(operationGUID)) {
    log.debug(
      'handleSSHKeyPassphrase: background task environment, skipping prompt'
    )
    return undefined
  }

  const { secret: passphrase, storeSecret: storePassphrase } =
    await trampolineUIHelper.promptSSHKeyPassphrase(keyPath)

  // If the user wanted us to remember the passphrase, we'll keep it around to
  // store it later if the git operation succeeds.
  // However, when running a git command, it's possible that the user will need
  // to enter the passphrase multiple times if there are failed attempts.
  // Because of that, we need to remove any pending passphrases to be stored
  // when, in one of those multiple attempts, the user chooses NOT to remember
  // the passphrase.
  if (passphrase !== undefined && storePassphrase) {
    setSSHKeyPassphrase(operationGUID, keyPath, passphrase)
  } else {
    removeMostRecentSSHCredential(operationGUID)
  }

  return passphrase ?? ''
}
