### Title
`withdraw()` in IntentGatewayV2 (Tron) checks escrow presence instead of sufficiency, permanently DOS-locking escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Sherlock report's core broken invariant is: a guard checks a *coarse* condition (`recipient.proposalBid > poolAmount`, the aggregate/whole value) instead of the *actual value being moved this call* (`recipient.proposalBid * milestone.amountPercentage / 1e18`), so once the pool balance drops below the coarse threshold, every subsequent payout call reverts — permanent DOS. The same broken-guard shape exists in `IntentGatewayV2.withdraw()`: it checks only that the per-token escrow entry is non-zero, never that the specific `amount` requested by the cross-chain withdrawal message is `<=` the escrowed balance.

### Finding Description
`withdraw()` releases escrow for a `WithdrawalRequest` (used for both `RedeemEscrow`/fill-confirmation and `RefundEscrow`/cancellation paths): [1](#0-0) 

The only pre-condition before transferring `amount` out is:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
```
There is no check that `amount <= _orders[body.commitment][token]`. The transfer executes with the caller-influenced `amount` from the decoded `WithdrawalRequest` body (arriving via `onGetResponse` or an inbound ISMP `PostRequest` from the paired `IntentGatewayV2` instance) before the ledger is decremented:
```solidity
_orders[body.commitment][token] -= amount;
```

At `placeOrder`, the escrow ledger is credited with the **fee-reduced** amount, while the `order` struct used to compute the emitted/committed order data is restored to the **original, pre-fee** input amounts immediately after the commitment hash is taken: [2](#0-1) [3](#0-2) 

Escrow is booked as `reducedInputs[i].amount` (line 457), but the order data available to downstream fill/redeem logic reflects `originalInputs` (pre-fee) amounts once `order.inputs = originalInputs;` restores it. Any code path that derives the `WithdrawalRequest.tokens[i].amount` for a `RedeemEscrow`/`RefundEscrow` message from the original (un-reduced) order amount — rather than from the ledger's fee-reduced escrow value — will produce an `amount` strictly greater than `_orders[commitment][token]`. Because `_orders[...] == 0` only rejects a fully-drained/unknown order and never rejects an over-sized `amount`, the function proceeds to attempt the transfer and then executes the checked (Solidity ≥0.8) subtraction, which reverts on underflow. Since the token transfer and the ledger update are in the same transaction, the whole call reverts and rolls back — but the mismatch is deterministic per order, so **every** future call with the same encoded amount reverts identically.

### Impact Explanation
This is a fund-lock/DOS on the escrow-release path, matching the Impact Gate's "loss of funds" / "logic attacks" category: the escrowed input tokens for the affected order become permanently unredeemable (neither fillable-confirmation payout nor refund can complete), because the guard validates the wrong quantity (non-zero balance) instead of the quantity that matters (sufficiency of `amount` against the ledger). This mirrors exactly the Sherlock M-10 shape: a comparison against the aggregate/whole balance instead of the specific transfer amount, causing recurring reverts once the two diverge.

### Likelihood Explanation
The divergence between the fee-reduced escrow ledger and the original-amount order data is baked into `placeOrder`'s own control flow (temporarily swapping `order.inputs` to compute the commitment, then restoring the original amounts) whenever `protocolFeeBps > 0` for a destination. Any unprivileged user placing an order to a destination with a non-zero protocol fee, followed by the normal fill/redeem or cancel/refund flow, can trigger this path with no malicious relayer, prover, or governance action required — it is intrinsic to standard cross-chain order settlement once fees are non-zero.

### Recommendation
In `withdraw()` (and the equivalent `_withdraw()` in the mainline `IntentsBase.sol`), replace the presence check with a sufficiency check against the exact amount being transferred:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (amount > escrowed) revert InsufficientEscrow();
_orders[body.commitment][token] = escrowed - amount;
```
Additionally, ensure the amount encoded into any `WithdrawalRequest` dispatched cross-chain is derived from the same fee-reduced value that was actually escrowed (`reducedInputs`), not from the restored original `order.inputs`, so the two ledgers never diverge.

### Proof of Concept
1. Deploy `IntentGatewayV2` on source chain S and destination chain D; set `_destinationProtocolFees[keccak256(D)]` (or `_params.protocolFeeBps`) > 0.
2. User calls `placeOrder` on S with `inputAmount = X`. `_orders[commitment][token]` is credited with `X - fee` (reducedInputs), while the order struct emitted/used downstream has `inputs[i].amount = X` (original, restored at line ~374).
3. Order is filled on D; the fill-confirmation `RedeemEscrow` `WithdrawalRequest` is built using the order's (original, pre-fee) input amount `X`, and dispatched back to S via ISMP.
4. On S, `onAccept`/`onGetResponse` decodes the request and calls `withdraw(body, ...)` with `amount = X`.
5. `_orders[body.commitment][token] == 0` is false (it holds `X - fee`), so the guard passes; the transfer of `X` is attempted; `_orders[...] -= X` underflows and reverts (Solidity 0.8 checked arithmetic), reverting the whole transaction.
6. Every retry with the same message produces the identical revert — the user's escrowed `X - fee` tokens are permanently stuck in the contract, unredeemable via either fill or refund.

*Note:* I was not able to fully trace, within the available index, the exact off-chain/on-chain code that constructs the cross-chain `WithdrawalRequest.tokens[i].amount` for the `RedeemEscrow` message on the destination side to confirm with 100% certainty that it uses the restored `originalInputs` value rather than a value re-derived from `reducedInputs`. This is the one open verification step; a Devin session with full repository access (including the paired destination-side fill/withdrawal-request-construction logic) should confirm the exact source of `amount` before treating this as fully proven.
