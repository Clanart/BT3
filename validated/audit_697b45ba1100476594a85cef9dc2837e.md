Confirmed: `_cancelFromSource` builds the destination storage-proof key using `_instance(order.destination)` — the *current* registered gateway address for that state machine — not the gateway address that was actually live when the order was filled. This is the precise analog of the Aave Lens bug: the "handle" (`order.destination`, a stable chain identifier) is used to look up a mutable "profile" (the gateway `address`), and the code never checks that the looked-up instance is the *same* instance the order was actually settled against.

### Title
Stale gateway-instance binding lets an already-filled cross-chain order be refunded again via `cancelOrder` after a `NewDeployment` migration - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2.cancelOrder` → `_cancelFromSource` derives the ISMP `DispatchGet` storage-proof key from `_instance(order.destination)`, the *current* value of `_instances[keccak256(order.destination)]`, rather than from the gateway address that actually processed the fill for that order [1](#0-0) . `_instances` is a simple chain-id-keyed mapping that can be overwritten at any time by a `NewDeployment` request, which the destination gateway accepts for any state machine — new or already registered [2](#0-1) [3](#0-2) .

### Finding Description
`order.destination` is a stable state-machine identifier (analogous to the Lens "handle"); `_instances[keccak256(chain)]` is the mutable "current" gateway contract deployed at that chain (analogous to the Lens "profileId"). `_instance()` performs an existence/lookup check purely on the handle and returns whatever address is *currently* registered [4](#0-3) .

When a solver fills a cross-chain order, `_fillCrossChain` writes `_filled[commitment] = msg.sender` on the destination gateway that is live at fill time, and dispatches a `RedeemEscrow` message so the source-chain escrow is released to the solver [5](#0-4) .

If governance later issues a `NewDeployment` for that same `order.destination` (a normal migration/redeploy — no malicious actor required) before the order's escrow release request is delivered, or simply after any legitimate redeploy, `_instances[keccak256(order.destination)]` is overwritten to the new gateway address [2](#0-1) .

When the user subsequently calls `cancelOrder` → `_cancelFromSource` (available to the order owner any time after `order.deadline`), the GET-request storage key is built with `_instance(order.destination)` — now the *new* gateway address — concatenated with the `_filled` slot hash for the commitment [6](#0-5) . The new gateway contract never processed this order, so its `_filled[commitment]` storage slot is empty. The relayer proves this empty slot, `onGetResponse` sees `values[0].value.length == 0`, and unconditionally calls `_withdraw(...)`, refunding the escrowed input tokens to `order.user` on the source chain [7](#0-6) .

Nothing in this path checks that the gateway instance queried is the one the order was actually filled against — exactly the missing binding in the Lens report (`_profileIdByHandleHash[handle] != profileIds[i]`).

### Impact Explanation
This produces a duplicate settlement / false state acceptance: the solver already delivered output tokens to the user's beneficiary and was credited the input escrow via `RedeemEscrow` at fill time, and the source chain *also* refunds the same escrow to the user via `_cancelFromSource`, because the "unfilled" proof was taken against the wrong (post-migration) instance. Funds are lost by the solver / protocol and the user receives value twice for one order. This falls squarely under "false proof/state acceptance" and "double-claim/double-settlement" in the bounty scope, and requires no relayer/prover misbehavior — the proof itself is entirely legitimate, just scoped to the wrong contract instance.

### Likelihood Explanation
Triggering the bug requires only an ordinary event already supported by the protocol's own design — a `NewDeployment` registration for a state machine that already has orders in flight (e.g., a legitimate gateway upgrade/migration where the address changes, or any subsequent registration overwriting `_instances` for that chain). `_addDeployment`/`onAccept(NewDeployment)` places no restriction preventing re-registration of an already-known state machine. After that, exploitation is a single unprivileged call to `cancelOrder` by the order's own user (or, after `order.deadline`, no cross-chain requirement for a malicious peer) — the standard, expected user flow, with no need for a compromised relayer, prover, or governance actor to act maliciously.

### Recommendation
Bind the fill/cancel storage-proof lookup to the specific gateway instance that was authoritative when the order was placed/filled, not to whatever is "currently" registered for that chain id. Concretely: store the resolved destination gateway address in the order (or a per-commitment record) at placement/fill time, and have `_cancelFromSource` build its storage-proof key from that recorded address rather than a live call to `_instance(order.destination)`; alternatively, version `_instances` (e.g., `_instances[keccak256(chain)][epoch]`) and require the cancel path to prove non-fill against every historical instance that could have processed the order, not only the latest one.

### Proof of Concept
1. Order `O` is placed with `order.destination = ChainB`, where `_instances[keccak256(ChainB)] = GatewayB1`.
2. Solver fills `O` on `GatewayB1`: `_filled[commitment] = solver` is set on `GatewayB1`; `RedeemEscrow` is dispatched, and the source chain (via `onAccept`) releases the input escrow to the solver.
3. Hyperbridge governance issues `NewDeployment{chain: ChainB, gateway: GatewayB2}` (a legitimate redeploy/migration) either before the `RedeemEscrow` message lands or any time afterward; `_instances[keccak256(ChainB)]` is now `GatewayB2` [2](#0-1) .
4. After `order.deadline`, the user calls `cancelOrder(O, options)` with `options.height` past the deadline. `_cancelFromSource` builds the GET key from `_instance(ChainB) == GatewayB2` and `_calculateCommitmentSlotHash(commitment)` [6](#0-5) .
5. `GatewayB2` never processed order `O`, so its storage slot for `_filled[commitment]` is empty. The relayer/state-proof machinery correctly and honestly proves this empty slot (no forged proof involved).
6. `onGetResponse` observes an empty value and calls `_withdraw(body, true, true)`, refunding the source-chain escrow to `order.user` [7](#0-6) .
7. Result: the user has received both the solver's output tokens (step 2) and the refunded input escrow (step 6) for the same order — a duplicate settlement funded by the protocol/solver.

        uint256 outputsLen = order.output.assets.length;

            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }

                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
