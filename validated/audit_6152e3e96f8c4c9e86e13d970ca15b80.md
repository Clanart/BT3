### Title
User-supplied `security-patterns.yaml` regexes bypass the ReDoS heuristic in `_has_redos_structure`, enabling attacker-controlled catastrophic-backtracking DoS of the PostToolUse hook - (File: `plugins/security-guidance/hooks/extensibility.py`)

### Summary
`_validate_pattern` in `plugins/security-guidance/hooks/extensibility.py` gates user-supplied regexes with a purely heuristic catastrophic-backtracking detector, `_has_redos_structure`, that only recognizes two structural shapes (nested quantifiers and alternation-under-repetition with prefix overlap). Regexes causing catastrophic/exponential backtracking through other well-known constructs — e.g. sequences of multiple independently-ambiguous quantified groups — are not detected, so a repo-committed `security-patterns.yaml` can smuggle a ReDoS regex into the merged pattern list evaluated on every `Edit`/`Write` PostToolUse invocation.

### Finding Description
`load_for_session` (`extensibility.py:60-77`) calls `_load_user_patterns(cwd)` which reads `.claude/security-patterns.{yaml,yml,json}` from the current project directory — content that is ordinary, attacker-writable repo content, not an admin/maintainer-only file [1](#0-0) . Each `patterns` entry is passed to `_validate_pattern`, and if a `regex` field is present, it is checked once with `_has_redos_structure(regex)` before being compiled and added to the rule list returned by `user_patterns()` [2](#0-1) .

`_has_redos_structure` is explicitly documented as a heuristic, not a proof [3](#0-2) . It only flags:
1. Nested quantifiers matching `\([^()]*[+*][^()]*\)[+*?]` (e.g. `(a+)*`).
2. Wildcard groups under repetition `(.*)* `.
3. Alternation under repetition where one branch is a literal prefix of another.

It does **not** detect the classic "sequence of ambiguous quantifiers" ReDoS shape, e.g. `(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)b`, or `(a*)+ (a*)+ ...`-style compositions spread across multiple non-nested groups, nor backreference-driven exponential blow-ups where the quantifier is not applied directly to the repeated group's own closing paren (e.g. `(a+)\1+$`-style constructs where the ambiguity comes from combining group content with a following backreference rather than a nested `)[+*]`). Such patterns compile successfully via `re.compile` (no static rejection at compile time in CPython's `re`) and pass `_has_redos_structure` undetected, yet still exhibit exponential worst-case time on crafted non-matching input strings against Python's backtracking `re` engine.

Once accepted, the malicious rule is merged with `SECURITY_PATTERNS` (confirmed by references to both `SECURITY_PATTERNS` and `user_patterns()` in `security_reminder_hook.py`) and evaluated against the content of every `Edit`/`Write` tool call the PostToolUse hook processes for the remainder of the session. No timeout or interpreter-level regex time-budget was found guarding this evaluation path in the files examined.

### Impact Explanation
An attacker who can only add/modify a checked-in file (`.claude/security-patterns.yaml`) — no shell, no admin rights — can cause the `security-guidance` PostToolUse hook to hang or consume excessive CPU on ordinary edits, once a crafted trigger string appears in edited file content. This blocks the hook's enforcement of the built-in `SECURITY_PATTERNS` warnings (and potentially the surrounding hook pipeline) for every subsequent `Edit`/`Write`, i.e. a denial-of-service against the security-review enforcement mechanism itself, without requiring elevated privileges.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs write access to a file the tool already treats as untrusted-but-loaded project configuration (the same trust class as `claude-security-guidance.md`), and the hook loads it automatically via `load_for_session` on every session for that `cwd`. The `_has_redos_structure` heuristic's own documentation ("Not a proof... catches the common shapes") acknowledges it is incomplete, and the specific evasion (sequential ambiguous quantifiers) is a standard, well-documented ReDoS technique distinct from the two shapes it checks for.

### Recommendation
Do not rely solely on static structural heuristics for regexes sourced from repo content. Options: (1) compile and evaluate user-supplied regexes with a hard wall-clock timeout per invocation (e.g. run matching in a subprocess/thread with `signal.alarm` or use the `regex` module's timeout parameter) and drop/disable a rule that exceeds it; (2) restrict user regex syntax to a safe subset (no backreferences, bounded group counts, disallow more than N quantified groups); (3) apply an input-length cap before regex evaluation to bound worst-case backtracking cost regardless of pattern shape.

### Proof of Concept
Fuzz/unit test plan for `plugins/security-guidance/hooks/extensibility.py`:
1. Construct `regex = "(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)(a*)b"` (10 sequential ambiguous groups, no nested quantifier, no overlapping alternation).
2. Assert `_has_redos_structure(regex) is False` (heuristic false negative).
3. Feed the resulting rule through `_validate_pattern({"rule_name": "x", "reminder": "r", "regex": regex}, source="test")` and confirm it returns a non-`None` rule (i.e., accepted).
4. Compile the accepted regex and run `re.search(rule["regex"], "a" * 30)` (a string with many `a`s and no trailing `b`) under a hard timeout (e.g. `signal.alarm(2)` or `multiprocessing` with a 2s join timeout).
5. Assert the search does not return within the timeout, demonstrating exponential blowup on attacker-controlled content that any `Edit`/`Write` hook invocation would trigger once this rule is merged into `user_patterns()`.

    rules: List[Dict[str, Any]] = []
    for label, path in _config_paths(cwd, "security-patterns"):
        # _config_paths returns an extensionless stem (e.g.
        # ".claude/security-patterns" or ".claude/security-patterns.local");
        # try each supported extension.

            candidate = path + ext

            if data is None:
                continue

                rule = _validate_pattern(entry, source=label)
                if rule:
                    rules.append(rule)
            break  # found one extension; don't double-load .yaml AND .json

# Catastrophic backtracking: nested quantifiers, overlapping alternations
# under repetition, and wildcard groups under repetition. Static check, not a
# proof — catches the common shapes that hang the hook on every edit.
_REDOS_SHAPES = [
    re.compile(r"\([^()]*[+*][^()]*\)[+*?]"),  # nested quantifier: (a+)*  (a*b)*
    re.compile(r"\(\.\*[^()]*\)[+*]"),         # wildcard group: (.*)*
]
_ALT_UNDER_REP = re.compile(r"\(([^()]*)\|([^()|]*)(?:\|[^()]*)*\)[+*]")


def _has_redos_structure(regex: str) -> bool:
    """Heuristic catastrophic-backtracking check. Not a proof. Catches:
      - nested quantifiers ((a+)*, (a*b)+)
      - wildcard groups under repetition ((.*)*)
      - alternation under repetition where one branch is a prefix of another
        ((a|aa)*, (ab|a)*) — these overlap and explode on non-matching input.
    Does NOT flag non-overlapping alternation ((a|b)*) which is safe."""
    if any(p.search(regex) for p in _REDOS_SHAPES):
        return True
    for m in _ALT_UNDER_REP.finditer(regex):
        branches = [b for b in m.group(0).strip("()*+").split("|") if b]
        for i, a in enumerate(branches):
            for b in branches[i + 1:]:
                # If one branch is a literal prefix of another, the alternation
                # overlaps and the engine backtracks combinatorially.
                if a.startswith(b) or b.startswith(a):
                    return True
    return False
