### Title
`SignableTransaction::new` omits the OP_RETURN data output from the weight/vbytes used for fee and size-limit calculations - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the USSD bug — where a quantity that should have been excluded (the just-purchased DAI earmarked for other collateral) was included in the collateral balance, corrupting the rebalancing decision — `SignableTransaction::new` computes the transaction's weight and virtual size on a transaction skeleton that omits an output which is actually included in the final transaction. The OP_RETURN `data` output is pushed onto `tx_outs` but is never passed to `calculate_weight_vbytes`, so `needed_fee`, the minimum-relay-fee check, the `NotEnoughFunds` check, the change-amount decision, and the `MAX_STANDARD_TX_WEIGHT` check are all computed against a smaller transaction than the one actually produced.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202`, when `data` is `Some`, an `OP_RETURN` `TxOut` is appended to `tx_outs` — the outputs of the transaction that will actually be signed and broadcast:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
```

However, both weight calculations use `payments` (which does not contain the OP_RETURN output) rather than `tx_outs`:

- Line 204: `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);`
- Line 226: `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`

`calculate_weight_vbytes` (lines 62-99) builds a mock `Transaction` whose `output` list is built solely from `payments` plus an optional change output. The consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change` (line 227) are underestimated by `fee_per_vbyte * op_return_vsize` (up to ~80+ vbytes given the 80-byte data cap at line 171, plus output overhead — roughly 9-13 + 80 bytes).
2. The minimum relay fee check at line 211 uses the underestimated `vbytes`, so a transaction whose *true* feerate falls below `DEFAULT_MIN_RELAY_TX_FEE` can still pass.
3. The change decision at lines 228-233 uses the understated `fee_with_change`, so the change output is slightly larger than it should be — masking the shortfall by paying a lower effective feerate rather than erroring.
4. The `MAX_STANDARD_TX_WEIGHT` check at line 241 is evaluated on `weight` that excludes the data output, so a tx legitimately over the standardness limit can be accepted.

An unprivileged user can supply the `data` payload — the processor wires `Payment`s/OutInstructions carrying user-controlled data into `make_signable_transaction`/`signable_transaction` (`processor/src/networks/bitcoin.rs:818-834`), and burns/transfers carry user-specified OP_RETURN payloads. The result is a threshold-signed transaction paying a lower feerate than the fee policy intended, or exceeding standardness limits.

### Impact Explanation
The network signs and broadcasts transactions with a systematically lower feerate than requested whenever a data output is present. With marginal fee rates this produces transactions that fail relay (below `DEFAULT_MIN_RELAY_TX_FEE` once the true vsize is counted) or linger unconfirmed, delaying/stalling user burns and withdrawals. The weight-check gap additionally allows construction of non-standard transactions that nodes will reject. Funds aren't directly stolen, but network-signed outputs can become stuck, requiring intervention — a Medium-severity availability/integrity issue consistent with the USSD analog (miscounted quantity → wrong funding decision → instability).

### Likelihood Explanation
Triggers deterministically whenever `data.is_some()` — i.e., every Bitcoin transaction carrying an OP_RETURN payload, which is the normal path for Serai InInstructions/burn metadata. No attacker sophistication needed; the undercount is proportional to `fee_per_vbyte` and the data length (up to 80 bytes). Whether it causes a stuck tx depends on how close `fee_per_vbyte` is to relay minimums.

### Recommendation
Pass the actual outputs to `calculate_weight_vbytes` instead of `payments`. Since the OP_RETURN output is already in `tx_outs` before line 204, change `calculate_weight_vbytes` to take `&[TxOut]` (or take `payments` plus `data`), e.g.:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs, None);
```

and inside `calculate_weight_vbytes`, build the mock `tx.output` from the provided `tx_outs` slice (cloning `TxOut`s directly, since value encoding size is fixed). For the change calculation, either build a candidate `tx_outs` including a zero-value change output, or append the change `TxOut` to the slice passed in. Alternatively, include the OP_RETURN output in the mock transaction explicitly when `data.is_some()`.

### Proof of Concept
```rust
// Construct inputs worth `payment + expected_fee`, a payment, change, and 80-byte data.
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
  vec![output], &payments, Some(change_script), Some(data.clone()), fee_per_vbyte,
).unwrap();

// The signed transaction contains the OP_RETURN output...
assert!(tx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));

// ...but needed_fee was computed without it:
let actual_vsize = tx.transaction().vsize() as u64; // includes OP_RETURN (~90+ vbytes extra)
assert!(tx.needed_fee() < actual_vsize * fee_per_vbyte); // feerate below requested

// fee() == needed_fee() still holds (change absorbs the difference),
// so the effective feerate = needed_fee / actual_vsize < fee_per_vbyte,
// and may fall under DEFAULT_MIN_RELAY_TX_FEE despite the check at line 211 passing.
```

Root cause is purely in `networks/bitcoin/src/wallet/send.rs` lines 193-235: `tx_outs` (with OP_RETURN) diverges from the `payments` slice used for both `calculate_weight_vbytes` calls, mirroring the USSD pattern of making a funding decision on a quantity that doesn't match what's actually being transacted.
