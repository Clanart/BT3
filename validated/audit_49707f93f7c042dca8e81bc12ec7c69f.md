### Title
Unauthenticated `InternalSendTx` on Aggregator gRPC Bypasses Role-Based Access Control, Allowing Arbitrary Bitcoin Transaction Broadcast — (File: `core/src/rpc/aggregator.rs`)

---

### Summary

The `ClementineAggregator` gRPC service exposes an `InternalSendTx` endpoint that accepts any raw Bitcoin transaction and queues it for broadcast via the tx-sender. The aggregator server is intentionally configured with a `Noop` interceptor (no client-certificate verification), and `check_mainnet_requirements` explicitly omits the aggregator from the `client_verification` enforcement gate. As a result, any TLS client that can reach the aggregator's gRPC port — without presenting any client certificate — can call `InternalSendTx` and inject arbitrary transactions into the tx-sender broadcast queue.

---

### Finding Description

**Authentication design for Verifier/Operator vs. Aggregator**

Verifier and Operator servers are protected by the `OnlyAggregatorAndSelf` interceptor when `client_verification = true`. The interceptor's `is_internal()` helper classifies any method whose name starts with `"Internal"` as self-only, and all other methods as aggregator-or-self: [1](#0-0) [2](#0-1) 

The aggregator server, however, is always built with `Noop` when `client_verification` is false (the expected production default): [3](#0-2) 

`check_mainnet_requirements` enforces `client_verification` only for `Verifier` and `Operator` actors, explicitly leaving the aggregator unguarded: [4](#0-3) 

The documentation confirms this is the intended posture: *"The aggregator does not enforce client certificates but does use TLS for encryption."* [5](#0-4) 

**The unguarded `InternalSendTx` endpoint**

`InternalSendTx` is declared in the aggregator's proto service and carries the `"Internal"` prefix — the same prefix the interceptor uses to gate self-only access on Verifier/Operator servers: [6](#0-5) 

Its implementation accepts any caller-supplied raw transaction, deserializes it, and inserts it into the tx-sender queue with no metadata, no cancel conditions, and no activation prerequisites: [7](#0-6) 

The `fee_type` field is also fully attacker-controlled. Passing `RBF` instructs the tx-sender to fee-bump the transaction by adding wallet-funded inputs, potentially spending operator wallet UTXOs to subsidize an attacker-crafted transaction.

**Broken invariant**

The `"Internal"` naming convention signals that a method should be restricted to the entity itself. On Verifier and Operator servers this invariant is enforced cryptographically via mTLS leaf-certificate pinning. On the aggregator the same naming convention is used but the enforcement mechanism (`OnlyAggregatorAndSelf`) is never installed, so the invariant is silently broken.

---

### Impact Explanation

An unauthenticated caller with TCP access to the aggregator's gRPC port can:

1. **Broadcast arbitrary pre-signed bridge transactions out of sequence.** If an attacker possesses any pre-signed kickoff, challenge, payout, or reimbursement transaction (e.g., obtained from a prior deposit session or a compromised participant), they can broadcast it at an inopportune time — racing against the honest bridge flow, invalidating pending UTXOs, or triggering premature challenge/disprove windows that expose operator collateral to slashing.

2. **Drain operator wallet via attacker-controlled RBF fee-bumping.** By submitting a transaction with `fee_type = RBF` whose output is attacker-controlled, the tx-sender's fee-bumping loop may add wallet-funded inputs to the replacement transaction, effectively transferring operator wallet funds to the attacker.

3. **Permanently disrupt the tx-sender queue.** Injecting conflicting or double-spending transactions can cancel legitimate bridge transactions tracked in the queue, breaking liveness for deposits, withdrawals, and reimbursements.

---

### Likelihood Explanation

The aggregator gRPC port must be reachable by the backend service, so it is typically exposed on the internal network. Any party with access to that network segment — including a compromised backend, a malicious co-located service, or an attacker who pivots through any other internal host — can reach the endpoint. No client certificate is required; standard TLS is sufficient.

---

### Recommendation

1. **Enforce `client_verification` on the aggregator for `InternalSendTx`.** Either add the aggregator to `check_mainnet_requirements`'s enforcement gate, or introduce a separate interceptor that restricts `InternalSendTx` to a pinned backend certificate.

2. **Validate transaction provenance inside `internal_send_tx`.** Before queuing, verify that the transaction's txid matches a known bridge transaction stored in the database (e.g., cross-reference against `tx_metadata` entries). Reject transactions with no known bridge purpose.

3. **Restrict `fee_type` to `NoFunding` for externally-submitted transactions.** Prevent the tx-sender from adding wallet-funded inputs to caller-supplied transactions.

---

### Proof of Concept

```
# 1. Obtain any valid TLS certificate (no client cert required).
# 2. Connect to the aggregator gRPC port (default: configured host:port).
# 3. Call InternalSendTx with an arbitrary raw Bitcoin transaction hex:

grpcurl -insecure \
  -d '{"raw_tx": {"raw_tx": "<hex-encoded-raw-tx>"}, "fee_type": 1}' \
  <aggregator-host>:<port> \
  clementine.ClementineAggregator/InternalSendTx

# Expected result: HTTP 200 / Empty response.
# The tx-sender will attempt to broadcast the transaction to the Bitcoin network.
# With fee_type=RBF (1), the tx-sender may add wallet-funded inputs to the tx.
```
