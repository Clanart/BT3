### Title
Cached FROST preprocess seed is never deleted from `CachedPreprocesses`, enabling nonce reuse and private share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` writes a deterministic preprocess seed into the `CachedPreprocesses` DB map keyed by `self.context` and reads it back on every invocation, but no code path ever deletes the entry. The modular-frost `from_cache`/`seeded_preprocess` path deterministically regenerates identical nonces from the same seed. If the same context is ever used to produce signature shares over two distinct messages, the reused nonces allow an observer of the public shares/signatures to recover the validator's threshold secret share — the exact "stale map entry remains usable later" class as the Visor `timelockERC721s` finding.

### Finding Description
In `coordinator/src/tributary/signing_protocol.rs`, `preprocess_internal` only generates a fresh preprocess when `CachedPreprocesses::get(txn, &context)` is `None`; otherwise it reuses the stored seed [1](#0-0) . Neither `preprocess_internal` nor `share_internal` (nor any caller) removes the entry after use — there is no `CachedPreprocesses::del`-equivalent call anywhere in the function or its consumers.

On the FROST side, `SignMachine::from_cache` rebuilds the machine via `seeded_preprocess` [2](#0-1) , so the nonces are a deterministic function of the cached 32-byte seed. During `sign`, the effective nonce is `base + rho * actual` where `actual` derives entirely from those seed-derived nonces [3](#0-2) . The spec explicitly states that reuse enables third-party recovery of the private key share and that the cached preprocess "must be deleted so it's never reused" [4](#0-3) .

### Impact Explanation
Two signature shares produced from the same cached seed over messages m₁ ≠ m₂ yield shares `s₁ = d + (b·ρ₁)e + c₁·λ·x` and `s₂ = d + (b·ρ₂)e + c₂·λ·x` with identical `d, e`. Because ρ is a public binding factor and c is a public challenge, the nonce terms are eliminated across the two equations and the participant's secret share `x` (scaled by known Lagrange coefficient λ) is recovered linearly. For a MuSig-assembled key this is recoverable by any unprivileged observer of the public signature shares/signature; recovering one share weakens the threshold and, combined across participants or with a second leak, compromises the validator set key.

### Likelihood Explanation
The map is never cleaned, so any second signing operation under the same `context` reuses the seed. Re-attempts of the same message are safe (identical share), but the DB key is only `context` — it does not commit to the message. Whether a real caller signs two distinct messages under one `context` value could not be fully confirmed within the indexed call graph (the `Encode`-able `C` values supplied by callers were not fully visible); the vulnerability holds wherever context is reused across distinct messages, which the persistent, never-expiring entry makes possible by design.

### Recommendation
Delete the `CachedPreprocesses` entry in the same DB transaction that consumes it (e.g., a `get`-then-`del` inside `preprocess_internal`/`share_internal`), or key the cache by `(context, msg)` so each distinct message derives/requires a fresh seed. Alternatively, bind the message into the seed derivation (e.g., `Blake2s256(seed || msg)`) so reuse of a cached seed under a different message produces independent nonces.

### Proof of Concept
1. Trigger signing under context `ctx` for message `m₁`: `share_internal` stores/loads seed `s`, producing share `σ₁`.
2. Trigger signing under the same `ctx` for message `m₂` (any flow that reaches `preprocess_internal` with identical `C::encode()` output but different `msg`).
3. `CachedPreprocesses::get(txn, &ctx)` returns the stale `s`; `from_cache` → `seeded_preprocess` regenerates identical `nonces`, so the nonce commitments and effective nonces in `sign` repeat.
4. Given `σ₁, σ₂`, solve `σ₁ − σ₂ = (b(ρ₁−ρ₂)e) + (c₁−c₂)λx` — with `d, e` identical across both shares, standard two-nonce-reuse algebra recovers `λx`, hence the secret share `x`.

Note: severity hinges on whether callers ever reuse `context` across distinct messages; if the codebase guarantees unique contexts per message, impact reduces to the documented "delete after use" hygiene gap. That caller-side guarantee was not verifiable from the indexed sources.

Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
