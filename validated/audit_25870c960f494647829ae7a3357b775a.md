### Title
Broken exponent normalization in `normalize-pyth` reverts (or corrupts) every standard-precision Pyth price read - (`File: mainnet/contracts/market/v0-4-market.clar`)

### Summary
`normalize-pyth` in the production market contract implements the Pyth exponent-to-8-decimal conversion incorrectly. Instead of short-circuiting and returning the raw price when no adjustment is needed (`adj == 0`), it wraps that check in `asserts!`, which aborts the entire call with the price value as an error code precisely in the case that should succeed normally. This mirrors the analog bug class ("wrong equation vs. spec" / exponent conversion mismatch) from the reference report, where the implemented arithmetic diverges from the intended normalization logic.

### Finding Description
The correct, working version of this helper exists elsewhere in the same codebase: [1](#0-0) 

```clarity
(define-private (normalize-pyth (price int) (expo int))
  (let ((adj (+ expo 8)))
    (if (is-eq adj 0)
        (to-uint price)
        (if (> adj 0)
            (to-uint (* price (pow 10 adj)))
            (to-uint (/ price (pow 10 (- adj))))))))
```

Here, when `adj` (the exponent adjustment needed to reach 8 decimals) is `0`, the function correctly and directly returns `(to-uint price)`.

The market contract that actually drives borrow/liquidate/health-check pricing implements the same function differently: [2](#0-1) 

```clarity
(define-private (normalize-pyth (p int) (expo int))
  (let ((adj (+ expo 8))
        (inkind? (asserts! (not (is-eq adj 0)) (to-uint p)))
        (res (if (> adj 0)
                (* p (pow 10 adj))
                (/ p (pow 10 (- adj))))))
    (to-uint res)))
```

`(asserts! (not (is-eq adj 0)) (to-uint p))` means: "assert that `adj` is NOT 0; if that assertion fails (i.e., when `adj IS 0`), abort the entire call with `(to-uint p)` as the error value." This is the exact inverse of the intended logic seen in the correct implementation. `adj == expo + 8 == 0` is the *normal* case for Pyth feeds published with `expo = -8` (the standard 8-decimal Pyth precision used throughout this protocol, per `docs/oracle.md`), meaning the most common price reading triggers an abort instead of returning the already-correct value.

This function feeds directly into the market's price-resolution pipeline: [3](#0-2) 

`resolve-pyth` calls `normalize-pyth` to compute `final-price`, which then feeds `price-resolve` → `get-notional-evaluation` / `calculate-asset-notional-value` → `current-ltv` → the health check and liquidation math (`is-healthy`, `calc-liquidation-params`).

### Impact Explanation
Every code path that depends on a Pyth-quoted asset (STX, sBTC, USDC, and their zTokens via `resolve-ztoken`, plus stSTX via `resolve-ststx`) resolves its price through `resolve-pyth` → `normalize-pyth`. Because the standard Pyth exponent for all of these feeds is `-8` (yielding `adj == 0`), the price resolution step aborts on the common case instead of returning the value. Any market operation that requires a fresh price read — `borrow`, `withdraw` (health check), and `liquidate` — reverts, since these operations cannot compute `current-ltv`/`is-healthy` without a resolved price. This blocks legitimate withdrawals and borrow operations and prevents liquidations from executing, i.e., temporary freezing of funds for collateral/borrow positions that require a price-dependent state transition. This lands on the in-scope impact class: **High — temporary freezing of funds**.

### Likelihood Explanation
This is not a conditional edge case — it triggers on the standard/default Pyth exponent (`-8`) used for every price feed integrated by this protocol (STX/USD, BTC/USD, USDC/USD per `mainnet/contracts/utility/v0-1-data.clar` PYTH-STX/PYTH-BTC/PYTH-USDC constants), so it fires on essentially every call that needs a live price, making the likelihood very high/deterministic rather than probabilistic.

### Recommendation
Replace the `asserts!`-based short-circuit in `mainnet/contracts/market/v0-4-market.clar`'s `normalize-pyth` with the same explicit `if (is-eq adj 0) (to-uint p) ...` branching used correctly in `mainnet/contracts/utility/v0-1-data.clar`, so that the zero-adjustment case returns the value instead of aborting.

### Proof of Concept
1. Any Pyth-priced asset publishes a price with `expo = -8` (the standard exponent for STX/USD, BTC/USD, USDC/USD feeds referenced in `mainnet/contracts/utility/v0-1-data.clar`).
2. A user calls `borrow`, `withdraw`, or a liquidator calls `liquidate` on a position involving that asset.
3. Internally, `resolve-pyth` calls `normalize-pyth price -8`, computing `adj = -8 + 8 = 0`.
4. `(asserts! (not (is-eq adj 0)) (to-uint p))` evaluates `(not (is-eq 0 0))` = `(not true)` = `false`, so the assertion fails and the entire transaction aborts with `(to-uint p)` as the error code.
5. The borrow/withdraw/liquidate transaction reverts, even though the price value itself was valid — freezing the ability to act on the position until the code is fixed.
