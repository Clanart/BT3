### Title
Cached FROST preprocess seed keyed only by (label, attempt) — nonce reuse across distinct DKG-confirmation sessions leaks validator key shares - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` persists a deterministic preprocess seed in `CachedPreprocesses` under a context key of `(b"DkgConfirmer", attempt)` — it does **not** include the tributary genesis, validator set, or any session identifier. Because `AttemptDb` counts attempts per genesis, every new validator set's DKG confirmation starts at the same attempt number. A validator participating in two different tributary sets therefore reuses the exact same seed (and hence the same FROST nonces `d, e`) to sign two different `set_keys_message`s with different participant sets. This is the same class as the Revest bug: a missing existence/uniqueness check on state that must be fresh per operation, allowing re-execution over reused secret material.

### Finding Description
In `preprocess_internal`, the cache lookup is:

```rust
if CachedPreprocesses::get(self.txn, &self.context).is_none() { ... generate and store ... }
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
```

with `context = (b"DkgConfirmer", self.attempt)` set in `DkgConfirmer::signing_protocol` (signing_protocol.rs:275). The seed is fed to `ChaCha20Rng::from_seed` in `AlgorithmMachine::seeded_preprocess` (crypto/frost/src/sign.rs:127), which derives `nonces` and `commitments` deterministically (crypto/frost/src/sign.rs:128-133). So identical context ⇒ identical nonces.

The context is missing the tributary `spec.genesis()` / validator `set()`. Attempt counters are scoped per-genesis (`AttemptDb::attempt(txn, genesis, topic)`), so a second DKG session (new genesis, possibly different `removed` set or participant ordering) at the same attempt index produces the identical cache key. The seed encryption key is `"Cached Preprocess Encryption Key" || context || key.to_repr()` — `key` is the validator's static Ristretto key, also unchanged across sets.

`share_internal` then calls `machine.sign(preprocesses, msg)` where `msg = set_keys_message(set, removed, key_pair)` differs across sessions and the MuSig aggregate/`included` set may differ, so the binding factor `rho` and challenge `c` differ while `d, e` repeat.

### Impact Explanation
Each published Schnorr share has the form `s = d + b·e + λ·c·x`. With the same `(d, e)` across two sessions and known `b`, `c`, `λ` (all derivable from the public preprocesses, participant list, and message), an observer holding shares `s1`, `s2` solves a linear system and recovers the validator's effective secret key contribution. The shares and preprocesses are published as tributary data for `Topic::DkgConfirmation`, so an unprivileged party needs only to read public network data — no malicious validator assumption required. This is concrete key-share recovery, matching the "reuse will enable third-party recovery of your private key share" warning in crypto/frost/src/sign.rs:85-86.

### Likelihood Explanation
The collision occurs deterministically whenever the same validator participates in DKG confirmations for two distinct tributary geneses at the same attempt number — the normal case, since every set's first confirmation attempt uses the same index. Unlike the single-set re-execution case defended in the file's header comment (which relies on BFT to keep inputs identical), here the *intended* inputs legitimately differ (different set, message, and participants), so no consensus failure is needed.

### Recommendation
Bind the cache context to the session: `let context = (b"DkgConfirmer", self.spec.genesis(), self.attempt)` (or include `spec.set()`). Alternatively, derive the seed one-shot via `Commitments` randomness keyed by genesis, or mark the cache consumed after `sign` succeeds. This mirrors Revest's fix: check that the per-operation resource was actually minted fresh for *this* session, not a prior one.

### Proof of Concept
1. Validator `V` with static key `k` participates in tributary set A (genesis `g1`) and later set B (genesis `g2`).
2. In set A, `DkgConfirmer::share` runs at `attempt = 0`: context `("DkgConfirmer", 0)`, seed `S` stored, nonces `(d,e)` fixed; `V` publishes share `s1` over `msg1 = set_keys_message(setA, removedA, kpA)`.
3. In set B, `attempt = 0` again: `CachedPreprocesses::get` hits the same key, returns `S`; `seeded_preprocess` regenerates the same `(d,e)` and commitments. `V` publishes `s2` over `msg2 = set_keys_message(setB, removedB, kpB)`.
4. Attacker reads both published preprocesses/shares, computes challenges `c1 ≠ c2`, and solves `s1 − s2 = λ(c1·x1 − c2·x2)` (or the equivalent two-equation system in `d,e`) to recover `V`'s secret share material. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
