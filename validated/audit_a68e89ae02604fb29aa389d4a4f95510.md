### Title
Attacker-supplied `GeneratorProof` map containing the victim's own participant index causes `promote::complete` to panic, DoS-ing key promotion - (File: crypto/dkg/promote/src/lib.rs)

### Summary
Analogous to CVE-2025-30258 — where a crafted certificate lacking a valid subkey binding (backsig) poisons a keyring so signatures from *other* valid keys can no longer be verified — `GeneratorPromotion::complete` accepts an attacker-controlled `HashMap<Participant, GeneratorProof<C1>>` whose shape is only partially validated. It checks the map's *length* (`n - 1`) and that no key exceeds `n`, but never rejects a proof keyed under the *local* participant index `params.i()`. Such a malformed map passes validation and then hits an unconditional `proofs.get(&i).unwrap()`, panicking the verifier.

### Finding Description
In `crypto/dkg/promote/src/lib.rs:120-156`:

```rust
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... }

  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();   // line 146
```

Validation enforces (a) exactly `n - 1` entries and (b) all keys `<= n`. It does **not** enforce that the keys are `1..=n` *excluding* `params.i()`. If the map contains an entry for `params.i()` (the victim's own index — a proof the attacker simply attaches with the wrong key), then `len() == n - 1` still holds while one legitimate participant `i` is absent. The loop skips `params.i()` via `continue`, reaches the missing participant, and `proofs.get(&i).unwrap()` panics at line 146. This is reachable purely from public input bytes: `GeneratorProof` is deserialized via `GeneratorProof::read` (a `read`/verify-reachable type per scope), delivered over the peer channel, and passed straight into `complete`.

The parallel to the CVE is exact: a malformed imported item that is missing a required binding element (there: subkey backsig; here: absence of the self-index exclusion, i.e., a "bad usage flag" in the map) corrupts the verification of *other* participants' proofs — the loop dies before it can verify the legitimately submitted proofs, permanently halting the promotion session for the victim.

### Impact Explanation
`panic!` inside `complete` aborts generator promotion for the affected validator — all `n - 1` other participants' proofs, however valid, are never verified, mirroring the CVE's "verification DoS" where one crafted input disables verification of unrelated keys. Since `unwrap()` panics unwind through caller code that does not catch them, the processor thread/task dies; depending on the caller's panic handling this can crash the key-promotion pipeline or the process. DKG/promotion must then be re-attempted, and an attacker can repeat the input to keep promotion unavailable. This is a liveness (availability) impact on a state transition gated on cryptographic verification, consistent with a Medium severity analog.

### Likelihood Explanation
Any single participant (or anyone able to submit a `GeneratorProof` message into the promotion round) can trigger this deterministically: serialize a valid `GeneratorProof`, insert it into the map under `params.i()` of the victim instead of the sender's own index. No collusion, no invalid curve points, no leaked keys are needed — the map structure itself is the malicious input, identical in spirit to GnuPG accepting a malformed certificate into the keyring.

### Recommendation
Explicitly reject the self-index and enforce key-set equality before iterating:

```rust
if proofs.contains_key(&params.i()) {
  Err(PromotionError::InvalidParticipant { n: params.n(), participant: params.i() })?;
}
// or equivalently: check proofs.keys() == (1..=n).filter(|i| *i != params.i())
```

Then replace `proofs.get(&i).unwrap()` with a fallible lookup (`ok_or(PromotionError::InvalidParticipant { .. })`) so a structurally malformed map yields an error rather than a panic.
