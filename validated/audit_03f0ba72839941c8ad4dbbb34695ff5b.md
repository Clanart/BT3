## Analysis

The Jupyter Notebook CVE's failed invariant is: a "safe" output surface (sanitized HTML) is supposed to be free of characters that let content boundary-cross into an executable context, but one code path fails to apply that sanitization while another does, so downstream consumers who trust "the serializer already made this safe" get bitten.

In Protobuf, the transferable analog is the **HTML/JavaScript-context escaping applied by `MessageToJson`/`protojson`-equivalent public APIs**. Google's own C++, Java, and C# JSON writers deliberately escape `<`, `>`, `&`, `=`, `'`, and paragraph separators `U+2028`/`U+2029` in string field values — not because JSON requires it, but explicitly to prevent script-context injection when the JSON output is embedded into an HTML `<script>` tag (a documented, common server-side templating pattern):

- C++: `MustEscape()` in [1](#0-0)  with a dedicated round-trip test [2](#0-1)  and a purpose-built schema fixture `TestEvilJson` containing a `json_name = "</script>"` field [3](#0-2) .
- Java: `replacementChars` explicitly escaping `<>&='` "to prevent XSS risks" [4](#0-3)  with regression test `testHtmlEscape` [5](#0-4) .
- C#: same `<`/`>` escaping baked into `CommonRepresentations` [6](#0-5) .

However, the **upb native JSON encoder** — the C core used by Ruby's and PHP's protobuf extensions (and embedded verbatim in both) — only implements the JSON-spec-mandated escapes and never escapes `<`, `>`, or the JS paragraph separators: [7](#0-6) 

The identical code is duplicated in `ruby-upb.c` [8](#0-7)  and `php-upb.c` [9](#0-8) .

Python's pure-Python `json_format.py` is likewise unpatched: it delegates only to stdlib `json.dumps` with no extra escaping layer [10](#0-9) , and its own test explicitly documents that `<` and `>` pass through unescaped, unlike the Java/C++ tests for the same characters: [11](#0-10) 

### Title
Inconsistent HTML/JS-context escaping in Protobuf JSON serialization (Ruby/PHP/Python) enables script-injection when trusted-schema JSON output is embedded in HTML — (File: upb/json/encode.c)

### Summary
Protobuf's C++, Java, and C# `ToJson`/`JsonFormat.print` implementations deliberately escape `<`, `>`, `&`, `=`, `'` and JS paragraph separators in string field values as a defense against script injection when the emitted JSON is embedded inside an HTML `<script>` block by a consuming application. The upb-based native JSON encoder (shared by Ruby and PHP bindings) and Python's pure-Python `json_format.py` do not implement this extra escaping, only the JSON-spec-mandated escapes. An attacker-controlled string field value such as `</script><script>alert(1)</script>` passed through a bounded, valid, trusted-schema Protobuf message will be emitted byte-for-byte by these three language bindings' JSON serializers, whereas the same value is safely neutralized by C++/Java/C#.

### Finding Description
`jsonenc_put_escaped_char` in `upb/json/encode.c` handles only `\n`, `\r`, `\t`, `"`, `\f`, `\b`, `\\`, and control bytes `< 0x20`; any other byte, including `<` and `>`, is written verbatim via `jsonenc_putbytes`. This function is the sole string-escaping routine reachable from the public `upb_JsonEncode` entry point used by both Ruby's and PHP's native `to_json`/`serializeToJsonString` message methods (the identical code is vendored into `ruby-upb.c` and `php-upb.c`). Python's `json_format.MessageToJson`/`MessageToDict` builds a plain dict/list tree and hands it to stdlib `json.dumps`, which likewise does not escape `<`/`>`. By contrast, `src/google/protobuf/json/internal/writer.cc`'s `MustEscape` (C++), `JsonFormat.java`'s `replacementChars` (Java, with an explicit "to prevent XSS risks" comment), and `JsonFormatter.cs`'s `CommonRepresentations` (C#) all escape these exact characters for exactly this reason. The upstream C++/Java implementations even ship a dedicated `TestEvilJson` schema and `HtmlEscape`/`testHtmlEscape` regression tests proving this is a recognized, intentionally-hardened security property of the JSON printer surface — a property three other officially supported language bindings do not share.

### Impact Explanation
If a service accepts an ordinary, valid, schema-conformant Protobuf message from an untrusted client and re-serializes a string field to JSON via Ruby, PHP, or Python's `json_format`, and that JSON is subsequently embedded into a server-rendered HTML page inside a `<script>` block (the exact scenario the C++/Java/C# escaping exists to prevent), the missing escaping allows the client-controlled string to break out of the script context and inject arbitrary JavaScript into the page rendered to other users — a stored/reflected XSS whose root cause is a Protobuf API silently failing to provide the same safety guarantee its sibling implementations advertise.

### Likelihood Explanation
High for reachability: any public API caller of `Message#to_json` (Ruby), `serializeToJsonString` (PHP), or `json_format.MessageToJson`/`MessageToDict` (Python) with an attacker-influenced string field triggers this path with no special conditions, recursion, or malformed input required — just a normal string value containing `<`/`>`. The exploitability is entirely dependent on the consuming application's embedding pattern, which is common enough that Google itself hardened C++/Java/C# against it via dedicated regression tests, indicating this is a recognized, realistic deployment pattern rather than a contrived one.

### Recommendation
Port the `MustEscape`/`replacementChars` escaping semantics (escaping `<`, `>`, and preferably the same extended TAG/zero-width/paragraph-separator set for parity) into `upb/json/encode.c`'s `jsonenc_put_escaped_char` so Ruby and PHP inherit the fix automatically, and add the equivalent explicit escaping step to Python's `json_format._Printer` string-serialization path (or document loudly that `MessageToJson` output is not HTML/script-embedding-safe on these bindings and must be additionally escaped by callers).

### Proof of Concept
1. Given trusted proto: `message M { string s = 1; }`.
2. Build `M{s: "</script><script>alert(1)</script>"}` and serialize to binary — a bounded, valid wire payload.
3. Parse it and call:
   - Java `JsonFormat.printer().print(m)` / C++ `MessageToJsonString` → output contains `\u003c/script\u003e...` (safe), matching `testHtmlEscape`/`HtmlEscape` tests.
   - Ruby `m.to_json` / PHP `$m->serializeToJsonString()` → output contains literal `</script><script>alert(1)</script>` verbatim, per `jsonenc_put_escaped_char`'s escape table which has no case for `<`/`>`.
   - Python `json_format.MessageToJson(m)` → output contains literal `<`/`>`, consistent with `testJsonEscapeString`'s expected string `"&\\n<\\"\\r>..."` showing `<`/`>` unescaped.
4. Embedding this Ruby/PHP/Python output inside `<script>var data = {json};</script>` in an HTML response terminates the intended script tag early and executes attacker-supplied JavaScript, whereas the same embedding with C++/Java/C# output remains inert.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}
