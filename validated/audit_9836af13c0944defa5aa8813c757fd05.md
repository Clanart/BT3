## Title
CW721→ERC721 pointer's `transfer_nft` executes an ERC721 transfer without validating the caller owns/is approved for the token - (File: `example/cosmwasm/cw721/src/contract.rs`)

## Summary
This finding is the direct structural analog of the reported `QuestSystem.startQuest()` bug: a privileged/state-mutating action (moving an NFT) is performed using an *implicitly derived* owner instead of validating that the actual message sender (`info.sender`) is authorized to act on the token. In sei-chain, the CosmWasm reference CW721-pointer contract that wraps a native ERC721 as a CW721 token implements `transfer_nft` this way in `transfer_nft()`, called from `execute_transfer_nft`/`execute_send_nft`.

## Finding Description
The pointer contract's transfer logic is: [1](#0-0) 

`transfer_nft` never checks that `info.sender` (the actual CosmWasm message caller) is the NFT owner or an approved operator. Instead, it:
1. Queries the *real* current owner of `token_id` from the underlying ERC721 contract via `querier.erc721_owner(...)`.
2. Builds an ERC721 `transferFrom(owner, recipient, token_id)` payload using that *queried* owner as `from`.
3. Dispatches this payload as a `DelegateCallEvm` message.

This mirrors the audited bug precisely: `startQuest()` in the report never checked that the caller owned the NFT being used as input; it simply used whatever token was referenced. Here, `execute_transfer_nft`/`execute_send_nft` never check that the *caller* owns the token before constructing a transfer instruction that moves it — the "ownership" used in the payload is the token's real owner, not the caller's identity, so any account able to send a `TransferNft`/`SendNft` execute message against this pointer contract for an arbitrary `token_id` can cause a transfer of that NFT to a recipient of their choosing, provided the resulting delegatecall's ERC721-level `msg.sender` check is not itself independently enforced against the real owner.

The related dispatch handling is in: [2](#0-1) 

The `approve`/`approve_all` handlers similarly forward the `spender`/`operator` and rely on the underlying ERC721's `msg.sender` enforcement rather than validating `info.sender` against the queried owner within the CosmWasm contract itself: [3](#0-2) 

## Impact Explanation
If the `DelegateCallEvm` execution context does not propagate an EVM `msg.sender` that the target ERC721's own `_isApprovedOrOwner` check can correctly reject (e.g., if it resolves to the pointer/CW721 contract's own associated EVM address, or otherwise bypasses the real caller's identity), any account able to invoke `TransferNft`/`SendNft` against this pointer for a `token_id` it does not own could force a transfer of someone else's NFT to an arbitrary recipient — a direct, permanent, unauthorized transfer of a user's asset. This is functionally identical in severity to the original report (unauthorized use/loss of another user's NFT).

## Likelihood Explanation
Reachability requires only a CosmWasm `execute` message call against the CW721 pointer contract (or an EVM transaction routed through the `wasmd` precompile to invoke it) with an arbitrary `token_id` not owned by the sender — no special privileges are required, matching the "CosmWasm user" / "pointer user" reachable-surface criteria.

## Recommendation
In `transfer_nft` (and the `approve`/`approve_all` handlers), explicitly validate that `info.sender` equals the token's real owner (or is an approved operator/spender per the underlying ERC721 state) before constructing and dispatching the `DelegateCallEvm` transfer/approve payload, mirroring the `GameHelperLibrary._verifyInputOwnership()` fix applied to `QuestSystem.startQuest()` in the original report.

## Proof of Concept
1. Attacker calls the CW721 pointer contract's `execute` entry point with `ExecuteMsg::TransferNft { recipient: <attacker-controlled-address>, token_id: <victim's token id> }`.
2. `transfer_nft()` queries the real owner of `token_id` (the victim) via `querier.erc721_owner`, and builds an ERC721 `transferFrom(victim, attacker, token_id)` payload — without ever checking that the caller (attacker) is the victim or was approved.
3. The payload is dispatched via `EvmMsg::DelegateCallEvm`; if the resulting EVM `msg.sender` used to authorize the transferFrom does not reflect the real caller/victim's authorization, the transfer succeeds, moving the victim's NFT to the attacker.

Note: I was unable to fully trace the `EvmMsg::DelegateCallEvm` handler (in the `x/evm` module) within the available iterations to conclusively confirm the exact `msg.sender` value used inside the delegatecall, which determines whether the underlying ERC721's `_isApprovedOrOwner` check would ultimately block this specific attack path. This should be verified against the `DelegateCallEvm` message handler and the underlying ERC721 contract's `transferFrom` authorization logic before treating this as a fully confirmed exploit chain.

pub fn execute_approve(
    deps: DepsMut<EvmQueryWrapper>,
    info: MessageInfo,
    spender: String,
    token_id: String,
    approved: bool,
) -> Result<Response<EvmMsg>, ContractError> {
    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let mut payload_spender = spender.clone();
    let mut action = "approve";
    if !approved {
        payload_spender = "".to_string();
        action = "revoke";
    }
    let payload = querier.erc721_approve_payload(payload_spender, token_id.clone())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("action", action)
        .add_attribute("token_id", token_id)
        .add_attribute("sender", info.sender)
        .add_attribute("spender", spender.clone())
        .add_message(msg);

    Ok(res)
}

fn transfer_nft(
    deps: DepsMut<EvmQueryWrapper>,
    info: &MessageInfo,
    recipient: &str,
    token_id: &str,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(recipient)?;

    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let owner = querier.erc721_owner(info.sender.to_string(), erc_addr.to_string(), token_id.to_string())?.owner;
    let payload = querier.erc721_transfer_payload(owner, recipient.to_string(), token_id.to_string())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new().add_message(msg);

    Ok(res)
}
