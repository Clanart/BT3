### Title
Unhandled KeyError in NFT metadata-update parsing when a targeted field is absent — ([File: chia/wallet/nft_wallet/nft_puzzle_utils.py])

### Summary
Wireshark's DNS dissector crashed on a NULL pointer dereference when an SRV record's name field was empty, because the parser assumed the field was always present. The analogous bug class in chia-blockchain is trusting that a parsed on-chain data structure always contains an expected key before indexing into it. `prepend_value()` in `chia/wallet/nft_wallet/nft_puzzle_utils.py` does exactly this when applying an NFT metadata-update condition.

### Finding Description
`update_metadata()` converts an NFT's current on-chain metadata `Program` into a Python dict via `nft_program_to_metadata()`, which only populates whatever keys are actually present in the metadata (`u`, `h`, `mu`, `mh`, `lu`, `lh`, `sn`, `st` — any subset, since NFT minters choose which fields to include). [1](#0-0) 

`prepend_value()` is then called with the key extracted from the update condition inside the spend's solution, and directly indexes into the dict without checking whether the key exists: [2](#0-1) 

`update_metadata()` pulls the target key straight from the attacker-controlled solution program (`uri.first().as_python()`), with no validation that this key was ever present in the NFT's existing metadata: [3](#0-2) 

If an NFT was minted without one of the optional metadata fields (e.g. no `lu`/license-uri, no `mu`/meta-uri), and a subsequent spend includes a metadata-update condition whose target key is that missing field, `metadata[key]` on line 161 raises an uncaught `KeyError`, since the dict produced by `nft_program_to_metadata()` simply never contains that key. This mirrors the original CVE root cause: an assumed-present field (SRV name / metadata key) is dereferenced without checking for absence, leading to a crash while processing untrusted, remotely-supplied data.

### Impact Explanation
Any NFT owner (including an offer counterparty or the current holder of a shared/tracked NFT) can craft a spend containing a metadata-update condition targeting a metadata key that the NFT's current on-chain metadata Program does not include. Any wallet tracking that NFT (owner, DID-linked wallet, or a wallet processing an incoming offer/trade involving that NFT) that processes this spend to update local NFT state will hit the unhandled `KeyError`, which can abort/crash the coin-state processing task for that spend — a spend-triggered transaction-processing halt for wallet clients tracking the affected NFT.

### Likelihood Explanation
The trigger requires only crafting a normal on-chain NFT spend with an update condition whose key is absent from the NFT's current metadata — no special privileges, no consensus changes, and easily reachable by any spend-bundle submitter who controls (or colludes with the owner of) an NFT coin.

### Recommendation
In `prepend_value()`, use `metadata.get(key, b"")` (or `metadata.setdefault(key, b"")`) instead of directly indexing `metadata[key]`, so a metadata-update condition targeting a previously-absent field initializes it gracefully instead of raising `KeyError`. Additionally, wrap `update_metadata()`/`nft_program_to_metadata()` call sites with defensive exception handling wherever untrusted on-chain solutions are parsed, consistent with the defensive `except Exception` pattern already used around similar CLVM-parsing code such as `pool_state_from_extra_data()`. [4](#0-3) 

### Proof of Concept
1. Mint an NFT with `metadata_to_program()` omitting an optional key, e.g. only `("u", [...])` and `("h", ...)`, with no `("lu", ...)` entry — a normal, supported minting configuration.
2. Later spend the NFT's ownership/state layer with a metadata-update condition whose driver targets the `lu` key (the NFT_METADATA_UPDATER puzzle path that invokes `update_metadata()`).
3. Broadcast the spend on-chain.
4. Any wallet tracking this NFT (the owner's wallet, or a counterparty from a prior/pending offer) processes the coin spend through `get_metadata_and_phs()` → `update_metadata()` → `prepend_value()`, hits `metadata[key]` for the missing `lu` key, and raises an unhandled `KeyError`, aborting NFT/coin-state processing for that spend.

**Note on uncertainty:** I could not fully verify within available searches whether this `KeyError` propagates all the way up to crash the wallet's coin-processing task/loop uncaught, or whether an outer `try/except` in `wallet_state_manager.py`'s coin-state handling silently absorbs it (which would reduce this to a lower-severity "state desync" rather than a crash/halt). A full Devin session with broader codebase access would be needed to trace the complete call chain from `NFTWallet`'s coin-state callback through to this function and confirm exception propagation before treating this as a confirmed high-severity finding.

```python
def nft_program_to_metadata(program: Program) -> dict[bytes, Any]:
    """
    Convert a program to a metadata dict
    :param program: Chialisp program contains the metadata
    :return: Metadata dict
    """
    metadata = {}
    for kv_pair in program.as_iter():
        metadata[kv_pair.first().as_atom()] = kv_pair.rest().as_python()
    return metadata
```

```python
def prepend_value(key: bytes, value: Program, metadata: dict[bytes, Any]) -> None:
    """
    Prepend a value to a list in the metadata
    :param key: Key of the field
    :param value: Value want to add
    :param metadata: Metadata
    :return:
    """
    if value != Program.to(0):
        if metadata[key] == b"":
            metadata[key] = [value.as_python()]
        else:
            metadata[key].insert(0, value.as_python())
```
