### Title
Integer overflow in payment/fee summation bypasses the insufficient-funds check, producing an unspendable signed transaction - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` sums attacker-influenced payment amounts and fee products into `u64` with plain `+` and `*` arithmetic. When the accumulated amounts overflow `u64`, the `NotEnoughFunds` guard is evaluated against the wrapped (small) value, so a transaction whose outputs vastly exceed its inputs is constructed and handed to the FROST `TransactionMachine` for signing. This is the same bug class as CVE-2026-66757: arithmetic on externally supplied magnitudes overflows before a bounds/allocation decision, turning a resource-limit check into a no-op.

### Finding Description
The relevant code path: [1](#0-0) [2](#0-1) 

`input_sat` and `payment_sat` are computed with `sum::<u64>()` over untrusted `u64` amounts. Then: [3](#0-2) 

- `needed_fee = fee_per_vbyte * vbytes` can overflow `u64` for large fee rates.
- `input_sat < (payment_sat + needed_fee)` adds two unchecked `u64`s; if `payment_sat + needed_fee` wraps to a value `<= input_sat`, the `NotEnoughFunds` error is skipped even though the true obligation exceeds the inputs.
- The change path repeats the same pattern: `input_sat.checked_sub(payment_sat + fee_with_change)` at line 228 uses `checked_sub` on the outer subtraction but the inner `payment_sat + fee_with_change` can still wrap, yielding an enormous change value that is pushed as a `TxOut` (line 230).

The resulting `SignableTransaction` is consumed by `TransactionMachine::sign`, which produces BIP-340 signature shares over the sighash of this malformed transaction: [4](#0-3) 

Payment amounts flow in from processor payment plans derived from on-chain instructions (`Payment::read`/`ExternalBalance`), i.e. data an unprivileged counterparty can influence by requesting outputs, making this reachable without validator privileges.

### Impact Explanation
Depending on build profile, the overflow either panics (debug / `overflow-checks = on`, a direct denial of service of the signing pipeline — the analog of the GIMP plugin abort) or silently wraps (release), causing the coordinator threshold to produce and finalize signatures for a transaction that can never be broadcast (outputs exceed inputs, or amounts exceed the 21M BTC cap, rejected by `Amount`/consensus). Either way the signing attempt is burned and any larger batch/plan depending on it stalls. It also undermines the `needed_fee`/`fee()` accounting, since `fee()` computes `sum(prevouts) - sum(outputs)` with plain `u64` subtraction which will panic/underflow on the malformed result (lines 138–141).

### Likelihood Explanation
The overflow requires payment amounts summing near `u64::MAX`, which in practice requires either pathological plan data or many large outputs. It is not reachable from a single small public Bitcoin transaction, so practical likelihood is moderate; however the check-bypass is deterministic once triggered, the panic variant requires only `overflow-checks` builds, and the code explicitly bounds `data` to 80 bytes and payments to `>= DUST` — the author clearly intended these bounds to be the safety barrier, and arithmetic overflow silently defeats it.

### Recommendation
- Use `checked_add`/`checked_mul` (or `u128` accumulation) for `input_sat`, `payment_sat`, `payment_sat + needed_fee`, `fee_per_vbyte * vbytes`, and `payment_sat + fee_with_change`, returning `TransactionError::NotEnoughFunds`/`TooLargeTransaction` on overflow.
- Validate each payment amount against a sane upper bound (e.g. `<= MAX_MONEY` = 21M BTC) in addition to the `>= DUST` lower bound.
- Make `fee()` use `checked_sub` so accounting of a malformed transaction cannot panic.

    (script_a, u64::MAX - 1000), // >= DUST, passes the dust check
    (script_b, u64::MAX - 1000), // >= DUST
];
// payment_sat = sum::<u64>() wraps to ~u64::MAX - 2001 (or panics under overflow-checks).
// With release wrapping:
//   payment_sat + needed_fee wraps again to a small value,
//   `input_sat < wrapped` is false -> NotEnoughFunds is skipped.
// In the change path, `payment_sat + fee_with_change` wrapping makes
// `input_sat.checked_sub(wrapped)` return Some(huge), so a change output
// with value > total inputs is pushed.
// The machine then signs sighashes for a transaction no node will accept,
// and `fee()` panics on `sum(inputs) - sum(outputs)` underflow.
