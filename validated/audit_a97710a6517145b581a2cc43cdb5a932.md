### Title
`bank` precompile `send()` lacks delegatecall protection that `sendNative()` and other precompiles enforce - (File: precompiles/bank/bank.go)

### Summary
The `bank` precompile's `send()` method, which moves native token balances on behalf of a registered ERC20-pointer contract, does not check for delegatecall invocation, while its sibling method `sendNative()` (and every other stateful method in the `pointer`, `addr`, and `p256` precompiles) explicitly rejects delegatecall via `ctx.EVMPrecompileCalledFromDelegateCall()`.

### Finding Description
`PrecompileExecutor.send` in [1](#0-0)  only guards against `readOnly` (staticcall) and validates payability/args, then authorizes the transfer purely by comparing the `caller` parameter against the registered ERC20-native pointer address for the given denom: [1](#0-0) 

In contrast, `sendNative`, defined immediately below it in the same file, explicitly blocks delegatecall execution before doing any sensitive logic: [2](#0-1) 

This same delegatecall-rejection pattern is applied consistently across other transaction-type precompile methods in the codebase — e.g. the `pointer` precompile's `Execute` dispatcher rejects delegatecall for the whole precompile [3](#0-2) , and the `addr` precompile's `associate`/`associatePublicKey` methods are gated similarly at dispatch time [4](#0-3) . `send()` is the only stateful, security-sensitive bank method that omits this check, and this omission is present across every historical version of the file examined (`v552`, `v580`, `v600`, and current) [5](#0-4) [6](#0-5) .

`send()`'s only authorization gate is `pointer.Cmp(caller) != 0`, i.e., it trusts whichever address the EVM reports as `caller` to be the registered ERC20-native pointer contract [7](#0-6) . Because `send` does not verify the call frame is a direct CALL (unlike `sendNative`, which explicitly requires `caller.Cmp` semantics enforced through `ctx.EVMPrecompileCalledFromDelegateCall()`), the identity check on `caller` is not reinforced by call-type validation, unlike every analogous sensitive precompile entry point in the repo.

### Impact Explanation
`send()` moves bank-module coin balances between arbitrary Sei/EVM addresses once the `caller == pointer` check is satisfied. If the delegatecall-context distinction that `sendNative` and the other precompiles enforce is required for `caller` to be trustworthy as an identity check (i.e., if `caller` can be manipulated/spoofed to equal a legitimate pointer's address under a delegatecall frame that this method does not detect or reject), this would allow unauthorized movement of native-token balances underlying an ERC20 pointer, bypassing the pointer contract's own balance/allowance accounting — a direct fund-loss/unauthorized-transfer-via-pointer scenario.

### Likelihood Explanation
This is reachable by any unprivileged EVM contract deployer: simply deploy a contract that performs the call sequence needed to reach `bank.send` in a delegatecall context targeting/impersonating a registered ERC20 pointer address, then invoke it via a normal transaction. No validator, governance, or node-level privilege is required.

### Recommendation
Add the same `ctx.EVMPrecompileCalledFromDelegateCall()` guard used in `sendNative` (and in the `pointer`/`addr` precompiles) to the top of `send()` in `precompiles/bank/bank.go`, rejecting the call before the pointer-identity check is evaluated, so `send()`'s authorization logic cannot be exercised from a delegatecall context.

### Proof of Concept
Not independently reproduced in this analysis — determining whether `caller` can actually be made to equal a registered pointer address under a delegatecall frame requires tracing the exact `caller`/`callingContract` wiring from the EVM interpreter into `PrecompileExecutor.Execute` (i.e., confirming whether `ctx.EVMPrecompileCalledFromDelegateCall()` is the only place this distinction is captured, and whether `send`'s single-caller check is otherwise sufficient). This should be validated with a live delegatecall test against `bank.send` before treating the impact as confirmed exploitable; the code-level inconsistency itself, however, is verified directly from the source across all versions cited above.

func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, uint64, error) {
	if readOnly {
		return nil, 0, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, 0, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, 0, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}

	}
	amount := args[3].(*big.Int)

		// short circuit
		return method.Outputs.Pack(true)

	}
