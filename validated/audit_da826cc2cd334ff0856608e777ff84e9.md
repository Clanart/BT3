### Title
Attacker-controlled participant count in `ThresholdKeys::read` causes excessive up-front memory allocation (DoS) - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` trusts an attacker-supplied `n` field (u16) and immediately performs `Vec::with_capacity(usize::from(n))` before a single scalar byte has been validated. An unauthenticated peer can therefore force an allocation of up to ~2 MB of scalar storage per call with only a handful of input bytes, enabling CWE-789 / CAPEC-130 memory-exhaustion denial of service — the same bug class as the Metricbeat advisory (length field used as allocation size without checking what is actually present).

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` parses `t`, `n`, and `i` from the stream, then — when the interpolation byte is `0` (`Interpolation::Constant`) — executes:

```rust
// crypto/dkg/src/lib.rs:604-613
let mut interpolation = [0];
reader.read_exact(&mut interpolation)?;
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
```

`Vec::with_capacity` performs the full heap allocation eagerly. A message of ~10 bytes (4-byte `id_len` + `C::ID` + 6 bytes of `t`/`n`/`i` + 1 interpolation byte with `n = 0xFFFF`) triggers an allocation of `65535 * size_of::<C::F>()` — roughly 2 MB for a 32-byte scalar — before `C::read_F` has even confirmed one scalar exists in the stream. The allocation is not proportional to bytes actually received; it is proportional to a claimed size.

This mirrors the Ethereum-side code that explicitly guards against this exact pattern (`networks/ethereum/src/machine.rs:51-60` reads claimed length in 1 KB chunks precisely because "a valid DoS would be to claim a 4 GB data is present for only 4 bytes"), showing the project acknowledges the bug class but did not apply the mitigation here.

Note the verification-shares loop later in the same function (`crypto/dkg/src/lib.rs:620-623`) uses `HashMap::new()` and inserts per successfully-read point, so it does not share this flaw — only the `Constant` interpolation branch pre-allocates from the untrusted count.

### Impact Explanation
`ThresholdKeys::read` is a listed entry point for untrusted bytes. Each malicious ~10-byte message forces an immediate ~2 MB allocation (amplification ≈ 200,000×). Repeated calls — e.g., an attacker flooding an endpoint or peer message handler that deserializes key material — can exhaust memory and crash the process. The attacker needs no valid shares, no threshold participation, and no authentication; the allocation happens before any validity checks (`ThresholdParams::new` is only invoked at line 626, after allocation and reads).

### Likelihood Explanation
The cap is bounded by u16 (65535 elements), so a single call's damage is ~2 MB rather than unbounded — but the per-message cost to the attacker is ~10 bytes, so sustained requests produce sustained multi-MB allocations churned through the allocator. Any deployment feeding peer-supplied bytes to `ThresholdKeys::read` (e.g., key recovery/resharing flows where a peer transmits serialized `ThresholdKeys`) is reachable. The constraint that limits it to Medium rather than High is the u16 bound.

### Recommendation
Do not size allocations from untrusted length fields. Either:

1. Replace `Vec::with_capacity(usize::from(n))` with `Vec::new()` and let growth track bytes actually consumed, or
2. Cap `n` before allocating (e.g., reject `n` above a protocol maximum — the codebase's own `Participant`/threshold parameters are realistically small), and/or
3. Read scalars first into the vec without pre-reserving, matching the `HashMap::new()` pattern used for `verification_shares` in the same function.

### Proof of Concept
```rust
use std::io;
use frost::{curve::Ristretto, ThresholdKeys};

// Construct minimal bytes: id_len(4) || C::ID || t=1 || n=0xFFFF || i=1 || interpolation=0
fn malicious_bytes() -> Vec<u8> {
    let mut v = vec![];
    v.extend(&(<Ristretto as frost::curve::Ciphersuite>::ID.len() as u32).to_le_bytes());
    v.extend(<Ristretto as frost::curve::Ciphersuite>::ID);
    v.extend(&1u16.to_le_bytes());        // t
    v.extend(&0xFFFFu16.to_le_bytes());   // n = 65535 -> with_capacity(65535) scalars
    v.extend(&1u16.to_le_bytes());        // i
    v.push(0u8);                          // Interpolation::Constant
    v
}

fn main() {
    // ~10+ID bytes of input causes ~2 MB allocation, then errors on EOF
    let _ = ThresholdKeys::<Ristretto>::read(&mut &malicious_bytes()[..]);
    // Loop this call to amplify memory pressure
}
```
