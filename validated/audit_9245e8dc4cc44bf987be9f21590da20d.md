Confirmed: `filepath` in the `x-github-desktop://openRepo?...&filepath=...` deep link is fully attacker-controlled, only checked for non-null and non-absolute in `dispatcher.ts` [1](#0-0) , and is then passed straight to `resolveWithin(repository.path, filepath)` before revealing the resolved path in Finder/Explorer [2](#0-1) .

### Title
Directory-containment check in `resolveWithin` uses substring `startsWith` instead of path-boundary comparison, allowing traversal into sibling directories - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin` (and its `Win32`/`Posix` variants) is Desktop's single security boundary used to guarantee that a path supplied from untrusted sources (deep-link `filepath`, Copilot-generated conflict-resolution paths, etc.) stays inside a given root directory before the app writes a file or reveals it to the OS shell. The final containment check is:

```ts
return realResolved.startsWith(realRoot) ? resolved : null
``` [3](#0-2) 

This is a plain string-prefix test with no trailing path-separator boundary check. `realRoot` and `realResolved` are directory-independent character sequences, so any real path whose *name* merely begins with the same characters as the root directory's name will satisfy the check even though it lives in a completely different, sibling directory.

### Finding Description
`resolveWithin(rootPath, ...pathSegments)` normalizes/resolves the joined path and then compares the `realpath()`-resolved root and target with `String.prototype.startsWith` [4](#0-3) . Because Node's `path.resolve`/`normalize` fully collapses `..` segments before this comparison, an attacker can build a relative path such as `../repo-secrets/leak.txt` that, once joined against a root like `/Users/victim/Documents/GitHub/repo`, normalizes to `/Users/victim/Documents/GitHub/repo-secrets/leak.txt`. `realResolved.startsWith(realRoot)` evaluates `"…/GitHub/repo-secrets/leak.txt".startsWith("…/GitHub/repo")`, which is `true`, even though `repo-secrets` is not a subdirectory of `repo` at all — it is a completely separate, sibling folder that merely shares a name prefix. The check never verifies that the character following `realRoot` in `realResolved` is a path separator (or that the strings are equal), so the "contained in root" invariant the function's own docstring promises ("the resolved path is guaranteed to reside at, or underneath this path") is not actually enforced [5](#0-4) .

This primitive is reachable from network/attacker-controlled input in `openRepositoryFromUrl`, Desktop's handler for the `x-github-desktop://openRepo` deep link: the `filepath` query parameter is parsed with almost no validation (only an absolute-path check) in `parseAppURL` [1](#0-0) , and is fed directly into `resolveWithin(repository.path, filepath)` before the resolved path is handed to `shell.showItemInFolder` [2](#0-1) . A victim who clicks an attacker-supplied "Open in GitHub Desktop" link with a crafted `filepath` (e.g. `../` + a name that shares the target repository directory's prefix) can have Desktop reveal/open a file outside the cloned repository, provided such a sibling path exists on disk (a very common occurrence for repos cloned side-by-side under `~/Documents/GitHub/`, e.g. `myapp` vs `myapp-secrets`, `myapp` vs `myapp.backup`, etc.).

The same `resolveWithin` primitive also gates `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` in the AI conflict-resolution flow [6](#0-5) , so any path drawn from a similarly-prefixed sibling directory bypasses the guard there as well, turning a "read-only" traversal into a write-outside-repo primitive if `resolution.path` can ever contain `..` segments (this path currently derives from git status entries, so exploitability there depends on whether git itself can be tricked into reporting such paths — unconfirmed from available code, but the shared root cause is the same).

### Impact Explanation
The existing unit tests for `resolveWithin` only cover exact traversal-then-symlink-back-into-root cases and never test the sibling-directory-with-shared-prefix scenario [7](#0-6) , confirming the gap is unguarded and untested. Impact is file disclosure/access outside the intended repository boundary via `shell.showItemInFolder` in the deep-link path, and potentially file write outside the repo in the Copilot-resolution path if reachable — both match the "file write or read outside the repo" valid-impact category, driven purely by a link the user clicks, with no local access, admin rights, or malware required.

### Likelihood Explanation
The `filepath` deep-link parameter is attacker-controlled end-to-end and requires only that the victim click a link; success additionally depends on a same-prefixed sibling path existing on the victim's disk, which is common given how developers organize cloned repositories (e.g., `Documents/GitHub/project` next to `Documents/GitHub/project-notes` or `project.bak`). This makes exploitation opportunistic rather than guaranteed, but the underlying containment check is broken regardless of that precondition.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to compare paths on directory boundaries rather than raw substrings, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests covering sibling directories that share a name prefix with the root (both POSIX and Win32 variants), matching the existing `path-test.ts` suite style.

### Proof of Concept
1. Locally, create `~/Documents/GitHub/repo` (a cloned repository) and `~/Documents/GitHub/repo-secrets/leak.txt` (any file outside the repo).
2. Craft a link: `x-github-desktop://openRepo/https://github.com/owner/repo?filepath=..%2Frepo-secrets%2Fleak.txt`.
3. Victim (who has `repo` already cloned/opens it) clicks the link; Desktop parses `filepath` via `parseAppURL` (only rejects absolute paths) [8](#0-7) , then calls `resolveWithin(repository.path, filepath)` [2](#0-1) .
4. `path.resolve`/`normalize` collapse `../repo-secrets/leak.txt` against `.../GitHub/repo` into `.../GitHub/repo-secrets/leak.txt`; `realResolved.startsWith(realRoot)` returns `true` due to the shared `repo` prefix, so `resolveWithin` incorrectly returns the resolved path instead of `null`.
5. `shell.showItemInFolder(resolved)` reveals/opens `leak.txt`, a file entirely outside the intended repository, confirming the containment bypass.

  describe('resolveWithin', () => {
    const root = process.cwd()

    it('fails for paths outside of the root', async () => {
      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {
      assert((await resolveWithin(root, 'foo\0bar')) === null)
    })

    it('succeeds for absolute relative paths as long as they stay within the root', async () => {
      const parent = resolve(root, '..')
      assert.equal(await resolveWithin(parent, root), root)
    })

    if (!__WIN32__) {
