## Analysis

The Rio Vesting Escrow bug: `OZVotingAdaptor` stores an attacker-influenceable `governor` address and later calls into it (`propose`, `castVote`, ...) assuming it implements `IGovernor` correctly, with **no runtime verification that the stored value actually conforms to the expected interface**. The failure is: *a value is bound once, trusted forever, and later dereferenced/dispatched through an interface contract with no re-validation at the call site*.

The closest structural analog in this Protobuf checkout is in the C++ `ExtensionSet`: extensions are stored as a generic `MessageLite*` keyed only by field number, and every accessor (`MessageTypeTraits<Type>::Get`/`Mutable`, `GetMessageByClassData`) blindly `static_cast`s that pointer to the caller's expected `Type` based solely on the field number — the only safety net (`ABSL_DCHECK_TYPE`) is compiled out in release (`NDEBUG`) builds, and the descriptor pool only *warns*, never errors, when two independently-registered extensions collide on the same field number for the same extendee.

### Title
Unchecked `static_cast` of colliding-number extensions to attacker-selected type causes type confusion - (File: `src/google/protobuf/extension_set.h`, `src/google/protobuf/extension_set_heavy.cc`, `src/google/protobuf/descriptor.cc`)

### Summary
`ExtensionSet` stores extension values as an untyped `MessageLite*`/union keyed by field number. `MessageTypeTraits<Type>::Get`/`Mutable` (extension_set.h) and `ExtensionSet::GetMessageByClassData`/`GetMessage` (extension_set.cc / extension_set_heavy.cc) return that stored pointer `static_cast` to whatever `Type` the calling code asks for, on the *assumption* that the field number uniquely and consistently maps to one message type. The only check that this assumption holds (`ABSL_DCHECK_TYPE`) is a debug-only assertion, compiled to nothing in production (`NDEBUG`) builds. Meanwhile `DescriptorBuilder::CrossLinkField` in `descriptor.cc` treats a duplicate/colliding extension number for the same extendee as a **warning**, not an error (explicit `// TODO: Change this to an error.`).

### Finding Description
`extension_set.h` documents the trust assumption explicitly: [1](#0-0) 
and then implements the unguarded cast: [2](#0-1) 

The runtime accessor that backs this only asserts the type via `ABSL_DCHECK_TYPE`, which is a no-op outside debug builds: [3](#0-2) [4](#0-3) 

Crucially, the schema layer does **not** prevent two extensions from different (independently trusted) proto files/libraries linked into the same binary from registering the same field number against the same extendee message — this is only downgraded to a warning: [5](#0-4) 

`upb`'s equivalent code path, by contrast, explicitly detects this and safely falls back to unknown fields rather than performing an unchecked cast, confirming this is a recognized hazard class within the project: [6](#0-5) 

The chain is: (1) two trusted, independently-valid `.proto` schemas each declare an extension on the same extendee message using the same field number (build-time warning only, not rejected); (2) an ordinary client sends a bounded, well-formed serialized message containing that field number populated as extension A's message type; (3) application code compiled against extension B's generated accessor calls `GetExtension(extensionB)`, which reaches `MessageTypeTraits<TypeB>::Get` and performs `static_cast<const TypeB&>(GetMessageByClassData(...))` on an object that was actually constructed/parsed as `TypeA`; (4) in a release build the `ABSL_DCHECK_TYPE` guard is absent, so the mismatched vtable/layout is used directly — precisely the "blindly assumes conformance to the expected interface" failure from the report, just moved from a Solidity governor address to a protobuf extension pointer.

### Impact Explanation
A successful trigger yields a C++ object of one generated message class being addressed through the vtable/field layout of a different, unrelated generated message class. Depending on the layout divergence between the two colliding types this ranges from corrupted field reads/writes (memory corruption within the process) to invalid virtual dispatch, i.e., the same class of "double voting and other unexpected behavior" described in the original report, translated to memory-safety/integrity impact in a native protobuf consumer. This qualifies as High severity because it is a genuine type-confusion primitive reachable purely from bounded, well-formed wire input in production (non-debug) builds, without requiring any privileged access or hostile schema authorship — only two independently-trusted schemas that happen to collide on an extension number, a scenario the descriptor builder explicitly acknowledges but only warns about.

### Likelihood Explanation
Likelihood is bounded by the precondition that the consuming application actually links two extension definitions that collide on field number for the same extendee — a schema-composition hazard, not something a remote client can create from nothing. However, once that (legitimate, non-malicious) precondition exists in a deployed binary, exploitation requires nothing more than an ordinary client sending a normal, bounded message with that field number populated — no malformed data, no huge allocations, no privileged access. The `descriptor.cc` code explicitly flags this as a known, currently-only-warned-about condition (`AddWarning`, with a `TODO` to make it an error), indicating the project itself has not closed this gap.

### Recommendation
- Promote the duplicate/colliding-extension-number check in `DescriptorBuilder::CrossLinkField` (`src/google/protobuf/descriptor.cc`, around lines 7536–7559) from `AddWarning` to `AddError`, refusing to build a pool/binary with colliding extension numbers on the same extendee, closing the root cause at schema-composition time.
- As defense in depth, make the extension type check in `ExtensionSet::GetMessageByClassData`/`GetMessage` (`extension_set.cc`, `extension_set_heavy.cc`) and `MessageTypeTraits<Type>::Get`/`Mutable` (`extension_set.h`) an always-on `ABSL_CHECK` (not `ABSL_DCHECK`) so that a class-data/type mismatch fails safely instead of silently type-confusing in release builds.

### Proof of Concept
1. Define `pkg1.proto`: `message Container { extensions 100 to 101; } extend Container { optional TypeA ext_a = 100; }`
2. Define `pkg2.proto` (independently compiled/trusted): `extend Container { optional TypeB ext_b = 100; }` — same field number 100, different message type, same extendee `Container`.
3. Link both generated libraries into one binary; building the combined descriptor pool only emits a warning (`descriptor.cc` lines 7553–7558), not a build failure.
4. An ordinary client serializes `Container` with field 100 populated as a serialized `TypeA` submessage and sends it through the application's normal `ParseFromString`/`ParseFromArray` entry point.
5. Application code (compiled against `pkg2.proto`) calls `container.GetExtension(pkg2::ext_b)`, which resolves to `MessageTypeTraits<TypeB>::Get`, `static_cast`ing the stored `TypeA` object to `TypeB&` with no runtime check in a release build (`ABSL_DCHECK_TYPE` is a no-op), yielding a type-confused object whose fields/vtable belong to `TypeA` but are accessed as `TypeB`.

const MessageLite& ExtensionSet::GetMessageByClassData(
    Arena* arena, int number, const ClassData* class_data) const {
  const Extension* extension = FindOrNull(number);
  if (extension == nullptr) {
    // Not present.  Return the default value.
    return *class_data->default_instance();
  } else {
    ABSL_DCHECK_TYPE(*extension, OPTIONAL_FIELD, MESSAGE);
    ABSL_DCHECK(!extension->is_lazy);
    return *extension->ptr.message_value;
  }
}
