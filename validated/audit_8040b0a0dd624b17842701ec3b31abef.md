### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub Enterprise trust classification, triggering unsolicited sign-in against an attacker-chosen endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
When Git performs an HTTP operation against a remote and receives a `401` response, Git forwards any `WWW-Authenticate` header values to Desktop's internal credential helper as `wwwauth[]` entries. `getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts` trusts the content of that header at face value: if it contains `realm="GitHub"` it classifies the remote as `'enterprise'` without any verification (the code's own comment calls this a "happy-path" to avoid "having to resort to making a request ourselves"). This is functionally the same broken invariant as the reported `ValidateVoteExtensions` bug: an attacker-supplied value that should only ever influence local formatting/telemetry is instead used, unverified, as authoritative input to a trust/authorization decision.

### Finding Description
`getEndpointKind()` classifies a credential-helper request's target host in this order: `isGist` → `isDotCom` → `isGHE` → **`wwwauth[]` header content** → `findGitHubTrampolineAccount` (existing account match) → `isGitHubHost` (a real network check). [1](#0-0) 

The `wwwauth[]` branch is checked *before* the legitimate `isGitHubHost(endpoint)` API validation and is populated entirely by data returned from the remote server (a value a malicious git server, or a machine-in-the-middle proxy for a plain HTTP/misconfigured remote, fully controls): [2](#0-1) 

`getCredential()` uses this classification to decide whether to invoke `ui.promptForGitHubSignIn(endpoint)` when no existing account matches the endpoint: [3](#0-2) 

`promptForGitHubSignIn` then unconditionally treats any non-`github.com` hostname as a GitHub Enterprise instance and kicks off the enterprise sign-in flow pointed at that attacker-controlled `origin`: [4](#0-3) 

This bypasses the one real verification the app has (`isGitHubHost`, an actual network probe of the endpoint) whenever the header is present, exactly mirroring the report's core flaw: a value the attacker supplies is accepted as ground truth for a security-relevant decision instead of being independently verified.

### Impact Explanation
Simply adding/cloning a remote pointing at an attacker-controlled server (no local access, no admin rights, no prior malware, no phishing link click required) is sufficient: the server just needs to respond to the initial unauthenticated Git HTTP request with `401 WWW-Authenticate: Basic realm="GitHub"`. Desktop will then autonomously classify the host as `'enterprise'` and, if no local account matches, open the "Sign in" popup and start the **GitHub Enterprise OAuth/browser sign-in flow** using the attacker's origin as the enterprise endpoint (`setSignInEndpoint(origin)` / `beginEnterpriseSignIn`). This satisfies the report's allowed impact category of "unauthorized OAuth or account binding" driven purely by a "git remote/proxy response" — the header spoof causes Desktop to bind/attempt binding an account against a server the app has not verified is actually GitHub-compatible, and to present that flow to the user as a routine, Desktop-initiated credential prompt rather than an external link (reducing user suspicion compared to typical phishing).

### Likelihood Explanation
Moderate-to-high. No special positioning is required beyond controlling the git server the victim points a remote at (a common, low-effort attacker capability — malicious/typosquatted clone URLs, compromised self-hosted git servers, or a MITM on an unauthenticated transport). The trigger fires automatically during any ordinary `fetch`/`clone`/`push` against that remote; it requires only sending one HTTP header, no exploitation of git internals.

### Recommendation
Do not trust the `wwwauth[]` `realm=` value as sufficient proof of a GitHub/Enterprise host. Use it only as a *hint* to decide whether to perform the authoritative `isGitHubHost(endpoint)` check (which the code already has, and currently only runs when the header is absent), rather than as a substitute for it.

### Proof of Concept
1. Stand up a minimal HTTPS git-smart-http server at `https://evil.example.com/foo/bar.git` that, on the initial unauthenticated `GET /info/refs?service=git-upload-pack`, replies `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, clone or add a remote pointing at `https://evil.example.com/foo/bar.git` and trigger a fetch.
3. Git invokes Desktop's credential helper with `wwwauth[0]=Basic realm="GitHub"` in the credential protocol payload.
4. `getEndpointKind()` returns `'enterprise'` without ever calling `isGitHubHost`.
5. Since no account exists for `apiEndpoint` derived from `evil.example.com`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com/...')`, which calls `beginEnterpriseSignIn` + `setSignInEndpoint('https://evil.example.com')` and shows the Sign-In popup, initiating an OAuth/browser-based sign-in against the attacker's origin.

I was unable to fully trace what `setEndpoint`/`requestBrowserAuthentication` do beyond opening a browser tab to `origin`+ OAuth path when the origin is attacker-controlled (i.e., whether that origin needs to mimic real GitHub OAuth endpoints to actually capture a token, or whether the flow fails safely at that point) — this would require running the sign-in store code end-to-end, which is out of scope for this static analysis. This affects the exact severity of "credential exfiltration" versus "unwanted sign-in dialog/UX confusion + minor trust-boundary bypass," but the underlying broken invariant (unverified attacker-controlled header driving host trust classification) is confirmed directly from the code.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
