### Title
`bridge_circuit` never verifies the payout transaction's output value/destination, allowing Reimburse to be claimed for any spend of the withdrawal outpoint - (`circuits-lib/src/bridge_circuit/mod.rs`)

### Summary
`bridge_circuit` proves that *some* mined transaction spends the exact withdrawal outpoint `(txid, vout)` registered on Citrea, but never checks the value or script_pubkey of any output of that transaction. Because the withdrawal outpoint is an ordinary Taproot key-spend UTXO whose private key is held by the withdrawer (not locked to any bridge-enforced payout script), any spend of it - including one that pays nothing to the withdrawer - satisfies every assertion in the circuit, letting an operator claim Reimburse for a "payout" it never funded.

### Finding Description
The binding the protocol needs is:
`payout_spv.transaction.output[k].{value, script_pubkey} == (bridge_amount_expected, withdrawer_destination)` for some output `k` of the mined transaction, where `bridge_amount_expected`/`withdrawer_destination` are the values the withdrawer authorized on Citrea/off-chain.

What `bridge_circuit` actually checks (circuits-lib/src/bridge_circuit/mod.rs:162-204) is only: [1](#0-0) [2](#0-1) 

i.e. it verifies SPV inclusion of `payout_spv.transaction` and asserts that `input[payout_input_index].previous_output` equals `(user_wd_txid, vout)` obtained from `verify_storage_proofs` (`circuits-lib/src/bridge_circuit/storage_proof.rs:44-133`), which only checks the storage keys/values for the withdrawal UTXO's txid and vout and the deposit txid: [3](#0-2) 

At no point does `bridge_circuit`, `bridge_circuit_host.rs`, or `structs.rs` read/compare an `output_amount` or `output_script_pubkey` storage key, nor inspect `payout_spv.transaction.output` for value/destination. The circuit's only other constraints (HCP method id, watchtower total-work comparison, light-client L1 block hash match, OP_RETURN operator pubkey for `deposit_constant`) are unrelated to the payout output's content.

Root cause: the withdrawal outpoint `(txid, vout)` registered via Citrea's `withdraw`/`safeWithdraw` (see `core/src/citrea.rs:458-496`, `core/src/operator.rs:588-596`) is a plain Taproot key-spend UTXO owned by the withdrawer (`try_get_taproot_pk`, `SpendPath::KeySpend` in `create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:407-436`). It is not a script that enforces payment; it is merely used by the circuit as an *identifier* for "the transaction that spends this outpoint is the payout." The intended binding between this input and a correct payout output is supposed to come from the withdrawer's own signature over the transaction (documented as `SinglePlusAnyoneCanPay`, `core/src/rpc/clementine.proto:239-253`), but:
1. The proto comment is not an enforced consensus/circuit rule - `bridge_circuit` never checks `sighash_type`, never verifies the withdrawer's Schnorr signature, and never checks which output (if any) corresponds index-wise to the spent input.
2. Because the withdrawer holds the private key, they can (or an operator waiting for them to) spend that outpoint in *any* transaction, at any time, to any destination/amount, entirely outside of `create_payout_txhandler`.

Exploit flow: A withdrawer (or an operator colluding/waiting on them) registers a withdrawal for `(txid, vout)` with `bridge_amount`. Instead of the operator paying `bridge_amount` via `create_payout_txhandler`, any transaction spending `(txid, vout)`—e.g. the withdrawer trivially sweeping their own dust UTXO to themselves, or a minimal-fee self-spend—gets mined. An operator then builds `BridgeCircuitInput`/`BridgeCircuitHostParams` (`bridge-circuit-host/src/structs.rs:170-227`) using that mined transaction as `payout_spv`, computes `payout_input_index` via `get_payout_input_index(wd_txid, ...)`, and generates a valid bridge-circuit proof, since every check in `bridge_circuit` passes: SPV inclusion holds (the tx is really mined), and `input[payout_input_index].previous_output` really does equal `(user_wd_txid, vout)`. Nothing forces the transaction's outputs to actually deliver `bridge_amount` to the withdrawer.

### Impact Explanation
An operator can be reimbursed via the kickoff/BitVM assert graph for a payout it never funded, i.e. BTC held for reimbursement moves without a matching fronted withdrawal — this matches the Critical category "an operator reimbursed for a payout it never funded" / "BTC leaves a move-to-vault UTXO without a matching fronted withdrawal." The blast radius is every deposit/withdrawal pair processed by any operator, since the missing check is in the shared `bridge_circuit` logic used for all Reimburse claims, not tied to a specific operator or deposit.

### Likelihood Explanation
No special privilege is needed beyond being the withdrawer (an unprivileged, permissionless role reachable by calling `withdraw` on the Citrea Bridge contract and choosing the withdrawal UTXO's bytes) or an operator waiting for that UTXO to be spent by its owner for unrelated reasons. The withdrawer controls the private key of their own registered outpoint and can spend it however they like at negligible fee cost. The only extra requirement is that some operator constructs and proves `BridgeCircuitInput` using that transaction as `payout_spv` — which the honest operator would only do if it is dishonest/lazy, but the vulnerability shows the circuit provides no cryptoeconomic disincentive against doing so, since none of the existing guards (`Verifier::is_kickoff_malicious`, `verify_storage_proofs`, `SPV::verify`, watchtower total-work checks) validate payout output content.

### Recommendation
Extend `verify_storage_proofs` / `BridgeCircuitInput` to also read and verify the `output_amount` and `output_script_pubkey` storage keys committed on Citrea for the withdrawal, and add an explicit assertion in `bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs) that some output of `payout_spv.transaction` (ideally the output at a well-defined index, e.g. output 0 as constructed by `create_payout_txhandler`) matches those values exactly, mirroring the `user_wd_txid`/`vout` assertions already present at lines 190-204.

```
// cargo test target: circuits-lib (or bridge-circuit-host) unit/integration test on regtest
// 1. Create a withdrawal outpoint (txid, vout) owned by a test keypair (the "withdrawer").
// 2. Register it as the withdrawal UTXO for a given deposit (mock Citrea storage proof
//    values for storage_proof_utxo/vout referencing (txid, vout)).
// 3. Instead of building the tx via create_payout_txhandler with the correct
//    (bridge_amount, withdrawer_out_script_pubkey), have the withdrawer sign and broadcast
//    a trivial self-spend of (txid, vout) with a dust-value or zero-value-to-withdrawer output,
//    and mine it via regtest bitcoind.
// 4. Construct BridgeCircuitInput/BridgeCircuitHostParams using this mined transaction as
//    payout_spv (get_payout_input_index finds the input spending (txid, vout)).
// 5. Run bridge_circuit(...) (or bridge_circuit_host::prove_bridge_circuit host-side wiring)
//    and assert it does NOT panic / returns Ok, despite the payout transaction's outputs
//    not containing bridge_amount paid to the withdrawer's script_pubkey.
//
// Binding assertions to add and check both sides of:
//   left  = (payout_spv.transaction.output[k].value, .script_pubkey) for the intended payout output k
//   right = (expected_bridge_amount, expected_withdrawer_script_pubkey) from Citrea storage proof
// Before fix: left != right yet bridge_circuit succeeds (no panic).
// After fix: bridge_circuit must panic/return Err when left != right.
```
