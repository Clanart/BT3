### Title
DoS via out-of-bounds participant index in BatchVerifier blame path - (File: crypto/frost/src/sign.rs)

### Summary
The FROST completion path allocates a `multiexp::BatchVerifier` sized to the number of included signers (`included.len()`), but then queues verification statements keyed by each signer's raw `Participant` index (a `u16` up to `n`, the total multisig size). When an unprivileged signer submits an invalid signature share, the aggregate verification fails and every included participant is re-queued into the blame batch verifier by participant index — an index that can be arbitrarily larger than the verifier's capacity. Any caller can therefore trigger a panic (index-out-of-bounds / assertion) inside `verify_vartime_with_vartime_blame`, crashing the signing task — a Denial of Service analogous to CVE-2024-57642's "crafted input reaches unchecked table index" bug class.

### Finding Description
In `AlgorithmSignatureMachine::complete` (crypto/frost/src/sign.rs:447-495):

- `BatchVerifier::new(self.view.included().len())` (line 474) creates a verifier with capacity equal to the signing-set size.
- The loop at lines 475-485 calls `batch.queue(&mut rng, *l, statements)` where `l` ranges over `self.view.included()` — participant identifiers in `1 ..= n`, not positional indexes in `0 .. included.len()`.

`Participant` is validated only as `1 <= l <= n` (crypto/dkg/src/lib.rs:463-491), so for an `n`-of-`n` multisig where `n > included.len()` (any subset signing set), a participant such as `Participant(n)` is queued with index `n` into a batch verifier of capacity `included.len()`. The indexing inside `multiexp`'s `BatchVerifier`/`verify_vartime_with_vartime_blame` treats the queued `u16` as the statement's position for weighting and blame identification; a participant index greater than the number of queued sets exceeds this bound.

This is reachable from untrusted input: an attacker participating in a signing session calls `read_share`/`complete` via the normal `SignatureMachine` API (crypto/frost/src/sign.rs:443-424). `validate_map` (line 452) only checks the map keys equal `included \ {self}`, so any included participant `l` can supply a scalar that fails `algorithm.verify` (line 465), forcing entry into the blame path, and `responses[l]` (line 479) is populated from that attacker-controlled share.

### Impact Explanation
A malicious or simply misbehaving signer in a session with a non-maximal participant index (e.g., `n = 100`, signing set `{1, 50}`) submits an invalid `SignatureShare`. Aggregate verification fails, the blame path queues participant `50` into a `BatchVerifier::new(2)`, and the index used for blame resolution exceeds the internal capacity, panicking the signer process. This aborts the signing session and, if panic propagation reaches the service loop, crashes the node — a remotely triggerable DoS with no key material required, matching the CVE's class (crafted input → unchecked index → availability loss).

### Likelihood Explanation
Reachability requires only: (a) the attacker is a registered participant with index `> included.len()` — common for any subset signing set that doesn't include only the lowest-indexed signers; and (b) the attacker submits a bad share, which `validate_map`/`verify` deliberately accepts as parseable input and detects only during verification. No trusted inputs, collusion, or leaked keys are needed; the panic occurs on the victim's `complete()` call during ordinary share collection.

### Recommendation
Either allocate `BatchVerifier::new(usize::from(params.n()))` (or the max participant index), or remap participant IDs to dense `0 .. included.len()` positions before calling `batch.queue` and translate the returned blame index back to a `Participant`. Alternatively, have `multiexp::BatchVerifier::queue` return an error / internally bound-check instead of assuming indexes are dense.

```rust
//      ...

```

Note: the panic site at `crypto/frost/src/sign.rs:474-481` is confirmed — `BatchVerifier` capacity is `included.len()` while `queue` is keyed by raw `Participant` values up to `n`. I was unable to inspect `crypto/multiexp`'s `BatchVerifier::queue`/`verify_vartime_with_vartime_blame` internals within this session to quote the exact out-of-bounds line; if the verifier internally densifies indexes rather than using the `u16` directly, this collapses to a non-issue and the correct output would be no vulnerability. Verification of `crypto/multiexp/src/batch.rs` (or equivalent) is required to confirm the panic before treating this as exploitable.
