### Title
`rewards()` view method in the distribution precompile accepts payable value with no forwarding or refund path, permanently stranding funds - ([File: precompiles/distribution/distribution.go])

### Summary
The `rewards()` query method on the distribution precompile (address `0x0000000000000000000000000000000000001007`) is the only view-type method in `PrecompileExecutor.Execute` that is dispatched without a non-payable check, unlike every other query method which routes through `p.validateInput` (which calls `pcommon.ValidateNonPayable(value)`). This mirrors the reported `VestingTrustee` bug class: it is possible to transfer more balance than intended to a contract/precompile address, and there is no mechanism inside the codebase to recover it afterward.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute` dispatches methods as follows: [1](#0-0) 

Every other query (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) calls `p.validateInput(value, args, n)`, which enforces `pcommon.ValidateNonPayable(value)`: [2](#0-1) 

But `rewards()` skips this entirely and only validates argument length: [3](#0-2) 

Because `distribution` (0x1007) is registered in `payablePrecompiles`, the EVM keeper suppresses the emitted bank transfer events for calls to this address, but this map only controls event suppression — it does not change whether the underlying EVM value transfer occurs: [4](#0-3) 

The existing test suite explicitly documents this exact gap as a known quirk: `rewards()` is described as "the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)", explaining why no "view rejects value" test exists for it: [5](#0-4) 

Unlike payable state-changing methods such as `delegate()` (staking precompile) or `setWithdrawAddress`, which call `pcommon.HandlePaymentUsei` to properly route the attached value into a Cosmos-side `MsgDelegate` or similar mechanism, `rewards()` performs no such handling — the value is simply left credited to whatever Sei-side account backs the precompile address, with no code path to withdraw or reclaim it. I was not able to fully trace, within the tool budget, the exact low-level point in the EVM's precompile-call dispatch (`pcommon.DynamicGasPrecompile` / `RunAndCalculateGas`) where go-ethereum's native value-transfer semantics interact with `AddBalance`/`SubBalance` for a precompile address, so the precise mechanics of where the credited usei lands could not be fully confirmed from the index; this should be verified directly against `precompiles/common/precompiles.go` and the EVM `Call` path.

### Impact Explanation
This is directly analogous to the reported `VestingTrustee` issue: a caller can transmit `usei` (wei) value to a fixed, always-reachable precompile address via a read-only, permissionless `rewards()` call, and that value is not tracked, refunded, or otherwise recoverable by any code path in the distribution module. This constitutes a permanent freezing of user funds for any account that mistakenly (or is tricked into) attaching value to a `rewards()` call — e.g. wallets/dApps that always attach non-zero `msg.value` defensively, or through delegatecall/proxy composition. Because the amount lost is entirely attacker/caller-controlled and there's no upper bound, this can result in concrete, permanent loss of funds for the caller.

### Likelihood Explanation
The method is a public, unauthenticated view-style call reachable from any EOA or contract via the standard EVM JSON-RPC/precompile call path — no special privileges are required. The bug is a straightforward missing-check inconsistency (every sibling method has the check, this one doesn't), which raises the likelihood that it will eventually be triggered by real integrations (SDKs/wallets that pass along `msg.value` from `payable` wrapper functions) rather than requiring adversarial intent.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` (or route through `p.validateInput`) at the top of `rewards()` in `precompiles/distribution/distribution.go`, consistent with all other query methods in the same file, so that any non-zero `value` attached to a `rewards()` call causes the transaction to revert instead of silently stranding funds.

### Proof of Concept
1. From any EVM account associated with a Sei address, call the distribution precompile at `0x0000000000000000000000000000000000001007` invoking `rewards(address)` with a non-zero `msg.value` (e.g., via `distribution.rewards(delegatorAddr, { value: ethers.parseEther("1") })` as used elsewhere in the test suite: [6](#0-5) ).
2. Because `Execute`'s `RewardsMethod` branch calls `p.rewards(ctx, method, args)` directly without any payable check [7](#0-6) , the call succeeds, returns the rewards data, and the attached value is not returned to the caller nor forwarded to any tracked destination.
3. Attempt to recover the value from the precompile's associated account: unlike `delegate()`, `setWithdrawAddress`, and other payable methods that explicitly call `pcommon.HandlePaymentUsei` to process attached value [8](#0-7) , no such handling exists in `rewards()`, confirming the funds are stranded with no recovery mechanism in the codebase.

func (p PrecompileExecutor) validateInput(value *big.Int, args []interface{}, expectedArgsLength int) error {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return err
	}

	if err := pcommon.ValidateArgsLength(args, expectedArgsLength); err != nil {
		return err
	}

	return nil
}
