## Analysis: Front-running in `bid()` auctions → Kaia `kaiax/auction` bid pool

The Clearpool bug is a classic "last-look sniping" issue: because `bid()` is a plain public entry point with no commit-reveal or finality cutoff, anyone watching the mempool can always resubmit a marginally higher bid right before the auction resolves, denying legitimate bidders. Kaia's KIP-249 auction module (`kaiax/auction`) has a structurally analogous "highest wins, always replaceable" mempool for bids, reachable by any bidder through the public `auction_submitBid` RPC.

### Title
Unbounded last-moment bid replacement in the auction bid pool enables sniping/front-running of auction winners - (File: `kaiax/auction/impl/bid_pool.go`)

### Summary
`BidPool.insertBid` allows any incoming, Auctioneer-signed bid targeting the same `(blockNumber, targetTxHash)` pair to replace the current highest bid as long as it is even marginally larger, with no time-based freeze, commit-reveal, or "take from previous state" cutoff. This mirrors the Clearpool `bid()` front-running class: whoever submits the last, slightly-higher bid before the target transaction is picked up for block building wins, allowing repeated sniping of legitimate bidders' execution/arbitrage rights up until the very last moment the block is assembled.

### Finding Description
Bids reach the pool through the public JSON-RPC method `auction_submitBid`, handled by `AuctionAPI.SubmitBid`, which forwards to `BidPool.AddBid`. [1](#0-0) 

`AddBid` calls `validateBid` and then `insertBid`, which implements the replace-if-higher logic: [2](#0-1) 

There is no mechanism such as a per-block bidding deadline, a minimum time gap before the target block is sealed, or "snapshot the winner as of the previous block" as recommended in the Clearpool report. As long as a new bid strictly exceeds the current one for the same `(blockNumber, targetTxHash)` and passes the generic `validateBid` checks (`blockNumber` range, non-zero bid, size/gas limits, signature checks), it immediately supersedes the prior bid: [3](#0-2) 

Because the winning bid is whatever is present in `bidTargetMap` at the moment the block builder calls `ExtractTxBundles` (which reads `bidTargetMap` for the upcoming block right before bundling), a party who can observe the current highest bid (via bid-pool subscription `SubscribeNewBid`/`newBidFeed`, or via CN-to-CN bid propagation `BroadcastBid`) can always submit one unit more at the last possible instant, exactly the "front-run/back-run the last bidder" pattern described in the report: [4](#0-3) [5](#0-4) 

The README documents this behavior as intended "replace if better" logic without any anti-sniping safeguard: [6](#0-5) 

### Impact Explanation
A bidder who is about to win the right to execute directly after a target transaction (e.g., to capture an arbitrage/backrun opportunity) can be displaced at the last possible moment by a marginally higher bid, exactly as in the Clearpool report. This undermines the fairness/economic value of the auction: legitimate participants cannot reliably secure execution rights, and value that should accrue to earnest bidders (or be captured via true price discovery) can instead be captured by whoever has the fastest last-look bidding infrastructure.

### Likelihood Explanation
Any actor able to obtain an Auctioneer-cosigned bid (a normal step per KIP-249 for a legitimate searcher) and observe pool contents through the standard bid-subscription/propagation channels can perform this at negligible cost — this only requires the public `auction_submitBid` RPC. No node/validator/protocol privilege is required to submit competing bids up to the moment the block is built, making this readily reachable by an ordinary "auction bidder."

### Recommendation
Introduce a bidding cutoff or finality checkpoint analogous to the fix recommended for Clearpool: freeze/lock the winning bid for a target block a fixed number of blocks or a fixed time window before that block is actually built (e.g., only accept the highest bid known as of the previous block, or require bids to be finalized once the block builder starts `ExtractTxBundles`), rather than allowing replacement in `insertBid` until the instant the block is assembled.

### Proof of Concept
1. Searcher A obtains a valid Auctioneer signature and submits a bid via `auction_submitBid` targeting `targetTxHash` for block `N`.
2. Searcher B observes this bid (via `SubscribeNewBid` feed or CN peer propagation) and, holding their own valid Auctioneer signature, submits a bid for the same `(blockNumber=N, targetTxHash)` with `bid = A.bid + 1` just before the worker begins building block `N`.
3. `insertBid` accepts B's bid because `existingBid.Bid.Cmp(bid.Bid) >= 0` is false, replacing A's bid: `kaiax/auction/impl/bid_pool.go:294-309`.
4. When `ExtractTxBundles` runs for block `N`, it reads the now-replaced `bidTargetMap`, and B's bid transaction is bundled instead of A's, giving B the execution rights that A had legitimately raced for.

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)

func (bp *BidPool) validateBid(bid *auction.Bid) error {
	blockNumber := bid.BlockNumber

	bp.bidMu.RLock()

	// Check if the auction tx is already in the pool.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		bp.bidMu.RUnlock()
		return auction.ErrBidAlreadyExists
	}

	// 1. The `bid.Sender` must not be in the winner list of the same block number if the new bid isn't equal to the previous bid.
	if bp.senderHasDifferentWinner(bid) {
		bp.bidMu.RUnlock()
		return auction.ErrBidSenderExists
	}
	bp.bidMu.RUnlock()

	curBlock := bp.Chain.CurrentBlock()
	if curBlock == nil {
		return auction.ErrBlockNotFound
	}

	// 2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
	curNum := curBlock.NumberU64()
	if blockNumber <= curNum || blockNumber > curNum+allowFutureBlock {
		return auction.ErrInvalidBlockNumber
	}

	// 3. The `bid.Bid` must be greater than 0.
	if bid.Bid.Sign() <= 0 {
		return auction.ErrZeroBid
	}

	// 4. The data size must be less than the maximum limit.
	if uint64(len(bid.Data)) > BidTxMaxDataSize {
		return auction.ErrExceedMaxDataSize
	}

	// 5. The gas limit must be less than the maximum limit.
	if bid.CallGasLimit > BidTxMaxCallGasLimit {
		return auction.ErrExceedMaxCallGasLimit
	}

	// 6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.
	if err := bp.validateBidSigs(bid); err != nil {
		return err
	}

	return nil
}

func (a *AuctionModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	bundles := []*builder.Bundle{}
	curBlock := a.Chain.CurrentBlock()
	if curBlock == nil || atomic.LoadUint32(&a.bidPool.running) == 0 {
		return bundles
	}

	miningBlock := curBlock.NumberU64() + 1
	bidTargetMap := a.bidPool.GetTargetTxMap(miningBlock)
	if len(bidTargetMap) == 0 {
		return bundles
	}

	for _, tx := range txs {
		txHash := tx.Hash()
		bid, ok := bidTargetMap[txHash]
		if !ok {
			continue
		}

// If current node is CN, it will send bid to all CN peers without bid.
func (pm *ProtocolManager) BroadcastBid(bid *auction.Bid) {
	if pm.nodetype != common.CONSENSUSNODE {
		return
	}

	cnWithoutBid := pm.peers.CNWithoutBid(bid.Hash())
	for _, peer := range cnWithoutBid {
		if peer.GetVersion() >= kaia66 {
			peer.AsyncSendBid(bid)
		}
	}
}

## Bid pool validation rules

A bid pool is responsible for managing the valid bids from the `Auctioneer`. The bid must satisfy the following rules:

1. The `bid.Sender` must not be in the winner list of the same block number if the new bid doesn't have the same target block and hash as the previous bid.
2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
3. The `bid.Bid` must be greater than 0.
4. The `bid.Data` size must be less than or equal to `BidTxMaxDataSize`.
5. The `bid.CallGasLimit` must be less or equal to `BidTxMaxCallGasLimit`.
6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.

Please note that `Auctioneer` also validates the searcher's bid according to the KIP-249.
