### Title
`client_verification=false` disables mTLS client-cert validation entirely, contradicting its documented guarantee and allowing unauthenticated callers to reach state-changing/signing RPCs - (File: core/src/servers.rs)

### Summary
`BridgeConfig::client_verification` is documented as only restricting *which* certificate (aggregator vs. self) is accepted, explicitly stating "Client certificates are always validated against the CA certificate according to mTLS regardless of this setting." The implementation in `create_grpc_server` does not honor that invariant: when `client_verification` is `false`, the server's `ServerTlsConfig` omits `.client_ca_root(...)` entirely, so the TLS layer stops requesting/validating client certificates at all, and the `OnlyAggregatorAndSelf` interceptor is swapped for `Interceptors::Noop`. This is architecturally analogous to the reported `BridgeRouterHub` bug: a caller-provided/config-driven state (`client_verification=false`, like `adapterId==0`) reaches a sensitive code path (unauthenticated RPC dispatch, like `receiveMessage()`) that the contract's own documentation claims cannot happen.

### Finding Description
In `core/src/servers.rs`, `create_grpc_server` builds the TLS configuration and the auth interceptor from the same `config.client_verification` flag: [1](#0-0) 

- If `client_verification == true`: `client_ca_root(client_ca)` is set (mTLS client-cert requirement enforced) and the `OnlyAggregatorAndSelf` interceptor is installed.
- If `client_verification == false`: `client_ca_root` is **not set at all**, and the interceptor becomes `Interceptors::Noop`, which passes every request through unchanged: [2](#0-1) 

Meanwhile, the doc comment on the config field states the opposite guarantee: [3](#0-2) 

This is a direct mismatch between the documented security invariant (peer certs are *always* validated) and the actual code (peer cert validation is entirely skipped when the flag is false). Any TCP client that can reach the operator/verifier port — without possessing a valid client certificate at all — can then call state-changing and signing gRPC methods that are otherwise gated by the `OnlyAggregatorAndSelf` interceptor, including "Internal*" methods (`InternalHandleKickoff`, `InternalEndRound`, `InternalSendTx`, etc.), reflecting exactly the report's "unauthenticated state-changing/broadcasting call" impact class. This maps to the report's `adapterId==0` bug: a documented invariant ("index must start from 1"/"certs always validated") that the code fails to actually enforce under a reachable configuration/input value, letting an unauthorized caller directly invoke gateway functions meant to be restricted to a specific pre-approved counterparty (`IBridgeAdapter`/aggregator-or-self).

### Impact Explanation
If deployed with `client_verification = false`, any network peer able to reach the verifier/operator gRPC port bypasses the "only aggregator or self" boundary and can invoke internal, state-changing, or signing endpoints directly (e.g., internal round-ending, internal tx sending, kickoff handling) without ever proving possession of an approved client certificate — matching the High-severity "unauthenticated state-changing or broadcasting call" category in scope.

### Likelihood Explanation
Exploitability is contingent entirely on the deployment setting `client_verification = false`. I could not fully confirm within the available context whether this is a value that ships as the default/documented deployment configuration (e.g., in `scripts/docker/configs/testnet4/bridge_config.toml`) or whether it is only intended for exceptional/test setups; the grep for `client_verification` found matches in `core/src/test/data/bridge_config.toml` and `scripts/docker/configs/testnet4/bridge_config.toml`, but I was not able to inspect their actual boolean value before running out of iterations. If `false` is a documented, supported configuration mode for any real deployment (not merely a test fixture), this is squarely in scope; if it is only ever `true` in shipped configs and `false` is purely a test-only convenience, the rules direct rejecting analogs that "depend on a deployment ignoring the documented configuration."

### Recommendation
Make the TLS layer's actual behavior match the documented guarantee: always set `.client_ca_root(client_ca)` on the `ServerTlsConfig` regardless of `client_verification`, so that a valid client certificate signed by the configured CA is always required to complete the TLS handshake. Reserve `client_verification` solely for controlling the additional `OnlyAggregatorAndSelf` identity check (which certificate, not whether any certificate is required). Additionally, update/verify that no shipped deployment config sets `client_verification = false` outside of local/test contexts.

### Proof of Concept
Not independently reproducible from the indexed context alone (would require running the actual server binary with `client_verification=false` and a client connecting with either no client certificate or an arbitrary self-signed one, then calling an `Internal*`-prefixed or otherwise privileged RPC and confirming it succeeds). Conceptually:
1. Deploy an operator/verifier node with `client_verification = false`.
2. Connect a TLS client with no client certificate (or any certificate) — the server's `ServerTlsConfig` accepts it because `client_ca_root` is unset [4](#0-3) .
3. Because `Interceptors::Noop` is installed [5](#0-4) , the request bypasses the `is_internal`/leaf-cert checks in `only_aggregator_and_self` entirely [6](#0-5) .
4. Call any privileged unary RPC (e.g., `InternalEndRound`) directly and observe it executes rather than being rejected with `Status::unauthenticated`.

**Uncertainty note:** I was unable to verify, within the remaining iterations, the exact boolean values of `client_verification` in `core/src/test/data/bridge_config.toml` and `scripts/docker/configs/testnet4/bridge_config.toml`, which determines whether this finding depends on an out-of-scope "deployment ignoring documented configuration" or represents a real, shipped misconfiguration risk. A follow-up read of those files is needed to finalize severity/in-scope determination.

fn is_internal(req: &Request<()>) -> bool {
    // This normally doesn't exist but we add it in the AddMethodMiddleware
    let Some(path) = req.metadata().get("grpc-method") else {
        // No grpc method? this should not happen
        tracing::error!("Missing grpc-method header in request");
        return false;
    };
    path.as_bytes().starts_with(b"Internal")
}
