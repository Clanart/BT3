### Title
Unbounded recursive outer-puzzle matching in wallet driver dispatch can exhaust the Python call stack on an attacker-crafted puzzle reveal - (File: `chia/wallet/outer_puzzles.py`)

### Summary
`chia/wallet/outer_puzzles.py`'s `match_puzzle()` and the corresponding `get_inner_puzzle()`/`get_inner_solution()` dispatchers recursively unwrap nested "outer puzzle" layers (CAT, singleton, metadata, ownership, CR, revocation) by calling each driver's `_match`/`_get_inner_puzzle`/`_get_inner_solution` callback on the next inner puzzle, with no depth limit. Because the "also" chain length is fully determined by how many outer-puzzle layers are curried into an untrusted `puzzle_reveal` Program, a wallet-facing caller (offer counterparty, spend-bundle/coin submitter) can construct a `Program` with an arbitrarily deep nesting of matched puzzle layers to drive this recursion past Python's default recursion limit, raising `RecursionError` and crashing/aborting whatever wallet operation is inspecting the puzzle (offer parsing, coin state sync, asset-id derivation).

### Finding Description
`match_puzzle()` [1](#0-0)  iterates the `driver_lookup` table and returns the first driver whose `match()` succeeds. Each concrete driver's `match()` method recognizes its own curried mod, then immediately calls back into the shared `_match` (which is `match_puzzle` itself) on the extracted inner puzzle to keep unwrapping further layers, for example:

- `CATOuterPuzzle.match()` [2](#0-1) 
- `SingletonOuterPuzzle.match()` [3](#0-2) 
- `MetadataOuterPuzzle.match()` [4](#0-3) 

The same "also"-chained recursion pattern repeats in `get_inner_puzzle()`/`get_inner_solution()` for every driver (e.g. `CATOuterPuzzle.get_inner_puzzle`/`get_inner_solution` [5](#0-4) , `SingletonOuterPuzzle.get_inner_puzzle`/`get_inner_solution` [6](#0-5) ).

None of these `match`/`get_inner_*` functions execute CLVM or check any cost/size budget — they only inspect the curried mod/args tree via `Program.uncurry()`-style helpers, purely in Python. The recursion depth is therefore bounded only by how many outer-puzzle layers the attacker curries into the puzzle reveal Program supplied out-of-band (e.g., inside an offer file, or a puzzle reveal a wallet is asked to interpret for an incoming/offered coin), not by any mempool CLVM cost limit, since this Python-side matching can run before (or independent of) any mempool/cost-gated execution.

A separate but structurally identical recursive parser exists in the custody architecture's memo decoding, `PuzzleWithRestrictions.from_memo()`, which recursively reconstructs `MofN` members from attacker-supplied on-chain memo/hint data [7](#0-6) , and is likewise unbounded in nesting depth.

### Impact Explanation
An unprivileged offer counterparty or coin creator can construct a `Program` puzzle reveal with a deeply nested chain of recognizable outer-puzzle layers (CAT-wrapping-CAT, singleton-wrapping-CAT-wrapping-metadata, etc., or nested `MofN` custody memos) and hand it to a victim wallet through the standard offer/coin-inspection flow. When the wallet calls `match_puzzle()` (or `get_inner_puzzle`/`get_inner_solution`, or `PuzzleWithRestrictions.from_memo()`) to interpret that puzzle/memo, the resulting recursive Python call chain can exceed the interpreter's recursion limit, raising an uncaught `RecursionError`. Depending on where this is triggered (offer inspection, coin-state processing, trade acceptance), this can abort or crash the wallet's processing task for that offer/coin — a spend/offer-triggered transaction-processing halt, matching the bug class in the reference CVE (crafted input causing the receiving process to exit via a stack-overflow-class failure) rather than a memory-safety or asset-forgery bug.

### Likelihood Explanation
Constructing a `Program` with thousands of nested curry layers is cheap (a few bytes per layer) and requires no signature or on-chain fee, since the crafted object only needs to be parsed/matched by wallet-side Python code, not executed by CLVM under cost limits. An attacker only needs to get such a puzzle reveal or memo blob in front of a victim wallet's puzzle-driver or custody-memo parsing path (e.g., via an offer file, a DID/NFT/CAT coin hint, or custody-architecture memo on a coin sent to the victim). This makes the trigger straightforward to reach without any elevated privileges.

### Recommendation
Add an explicit depth limit (and/or convert to an iterative unwrap loop) in `match_puzzle()`, `get_inner_puzzle()`, `get_inner_solution()` in `chia/wallet/outer_puzzles.py` and in each driver's recursive `match`/`get_inner_*` implementation, so that an attacker-controlled nesting depth cannot drive unbounded Python recursion. Apply the same bound to `PuzzleWithRestrictions.from_memo()` in `chia/wallet/puzzles/custody/custody_architecture.py`. Catch and convert any residual `RecursionError` into a normal parsing failure at the boundary where untrusted puzzle reveals/memos are first ingested (offer parsing, coin-state processing) so a single malformed offer/coin cannot abort broader wallet operations.

### Proof of Concept
1. Programmatically build a `Program` puzzle reveal consisting of `N` (e.g., 5,000+) nested CAT/singleton/metadata outer-puzzle curry layers wrapped around a trivial inner puzzle, each layer shaped to satisfy the corresponding `match_*_puzzle()` recognizer in `chia/wallet/cat_wallet/cat_utils.py` / `chia/wallet/puzzles/singleton_top_layer_v1_1.py` / `chia/wallet/nft_wallet/nft_puzzles.py`.
2. Package this puzzle reveal into an offer (or as the puzzle reveal for a coin whose state the victim wallet syncs) and deliver it to a victim wallet.
3. Have the victim wallet call `outer_puzzles.match_puzzle()` (directly, or transitively via offer acceptance / coin-state processing in `chia/wallet/trading/offer.py` or `chia/wallet/wallet_state_manager.py`) on the crafted `UnknownPuzzle`.
4. Observe the recursive `_match` call chain exceed Python's recursion limit and raise `RecursionError`, aborting the wallet's processing of that offer/coin. [1](#0-0)
