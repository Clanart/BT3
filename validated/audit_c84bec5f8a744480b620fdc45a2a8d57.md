### Title
`isApplicationBundle` fails open when Spotlight metadata is empty/not yet indexed, allowing `UNSAFE_openDirectory` to launch a malicious `.app` bundle from a freshly cloned repo - (File: `app/src/lib/is-application-bundle.ts`)

### Summary
`isApplicationBundle` only treats `mdls` failures (a rejected promise) as "assume bundle" (safe default). It does not handle the case where `mdls` succeeds (exit code 0) but returns empty/`(null)` metadata — which happens routinely for files that have not yet been indexed by Spotlight, such as files from a repository that was just cloned. In that case the function returns `false` ("not a bundle"), and the caller in `app/src/ui/main-process-proxy.ts` proceeds to call `UNSAFE_openDirectory`, which invokes `shell.openPath` on the attacker-controlled path.

### Finding Description
`isApplicationBundle` shells out to `mdls -name kMDItemContentType -name kMDItemContentTypeTree <path>` and looks for known bundle content-type identifiers in stdout: [1](#0-0) 

The only safety fallback is the `.catch(err => ... return true)` wrapped around the call in `showFolderContents`: [2](#0-1) 

This catch only fires if the `execFile('mdls', ...)` promise rejects (e.g., binary missing, non-zero exit). It does **not** fire when `mdls` exits successfully but prints `kMDItemContentType = (null)` / `kMDItemContentTypeTree = (null)` — the documented output for a path whose metadata has not yet been indexed by Spotlight (which is common immediately after a `git clone` creates new files on disk, before `mds`/`mdworker` catches up). In that scenario, `stdout` contains no `"com.apple.application-bundle"`/`"com.apple.application"`/`"public.executable"` substrings, so `probableBundleIdentifiers.some(...)` returns `false`, and `isApplicationBundle` incorrectly reports the `.app` directory as "not a bundle."

The call chain from renderer to this sink is: `revealInFileManager`/context-menu action → `shell.showFolderContents` (`app/src/lib/app-shell.ts`, line 51) → `showFolderContents` (`app/src/ui/main-process-proxy.ts`, lines 100–144) → on macOS, `isApplicationBundle(path)` → if `false`, `UNSAFE_openDirectory(path)`, which is explicitly documented as unsafe for unverified paths: [3](#0-2) 

`UNSAFE_openDirectory` sends the `unsafe-open-directory` IPC message to the main process, which ultimately calls `shell.openPath`, and per Electron/macOS semantics `openPath` on a `.app` bundle **launches** the application rather than revealing it in Finder.

### Impact Explanation
If a victim clones/checks out a repository containing an attacker-crafted `Something.app` directory (with `Contents/MacOS/<executable>` and a minimal `Info.plist`), and immediately (before Spotlight indexes the new files) uses Desktop's "Show folder contents" / "Reveal in Finder"-style action on that path, the app bundle can be launched instead of merely revealed, resulting in arbitrary code execution under the victim's account. This matches the intended purpose of `isApplicationBundle`/`UNSAFE_openDirectory`'s safety contract being violated.

### Likelihood Explanation
Exploitability depends on a timing condition: Spotlight must not yet have indexed the bundle at the moment the user triggers the action. This is plausible right after a clone (new files on disk are not immediately indexed), but is not deterministic — it depends on Spotlight indexing speed, whether the volume is indexed at all (e.g., excluded volumes, `mdutil -i off`, network drives, or `.noindex` locations), and the timing of user interaction. On such volumes/situations `mdls` will return empty metadata indefinitely, making exploitation reliable; on typical fast local SSDs with Spotlight enabled, the race window is narrow but the empty-metadata failure mode is a real, reachable code path in `mdls`, not a rare implementation-specific edge case.

### Recommendation
Do not rely purely on presence of positive bundle identifiers in `mdls` output. Treat ambiguous/empty output (e.g., `(null)`) the same as a lookup failure and default to the safe branch (`isApplicationBundle` returning `true`), for example by checking that `stdout` actually contains valid content-type data before concluding it's not a bundle, or by additionally checking the path's extension/structure (e.g., ends with `.app` and contains `Contents/MacOS`) as a defense-in-depth signal, or by forcing a synchronous Spotlight import (`mdimport`) before querying metadata, or falling back to `LSCopyItemAttribute`/os-level bundle detection APIs that don't depend on background indexing state.

### Proof of Concept
1. On macOS, create a directory `Payload.app/Contents/MacOS/evil` with an executable script (or a minimal fake bundle without a full `Info.plist`, which can still cause `mdls` to omit content-type info depending on indexing state).
2. Commit it to a git repository and have the victim `git clone` it onto a volume/session where Spotlight indexing is disabled or lagging (e.g., `mdutil -i off /Volumes/X`, or immediately after clone before indexing completes).
3. In GitHub Desktop, trigger "Show folder contents" (or equivalent reveal action) on `Payload.app`.
4. Because `mdls -name kMDItemContentType -name kMDItemContentTypeTree Payload.app` returns `(null)` for both fields, `isApplicationBundle` returns `false`, and `UNSAFE_openDirectory`/`shell.openPath` launches `Payload.app` instead of revealing it in Finder.
