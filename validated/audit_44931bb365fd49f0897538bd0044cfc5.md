`rewards()` in the distribution precompile accepts value without validation, permanently stranding native funds - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards` query method of the distribution precompile (address `0x0000000000000000000000000000000000001007`) is the only view-style method in that precompile that omits the `pcommon.ValidateNonPayable(value)` check that every other view method in the same file enforces. A caller who mistakenly (or accidentally, e.g. via wallet UI) attaches `msg.value` to a `rewards(address)` call will have that value processed as a normal successful call, with no code path that refunds the payer or otherwise accounts for the sent funds, and no rescue mechanism for the precompile's associated Sei account.

### Finding Description
Every other view method in `precompiles/distribution/distribution.go` (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) calls `p.validateInput(value, args, N)`, which internally invokes `pcommon.ValidateNonPayable(value)` and rejects any call carrying non-zero `value`: [1](#0-0) 

`rewards()`, however, only validates argument length and never checks `value` at all: [2](#0-1) 

The dispatcher confirms `rewards` is routed without any payability gate applied beforehand, unlike e.g. `withdrawValidatorCommission` which explicitly calls `pcommon.ValidateNonPayable(value)` in `Execute`: [3](#0-2) 

This is a known quirk explicitly called out in the integration test suite, which documents that a value-bearing call to `rewards()` "would succeed and strand the funds": [4](#0-3) 

Unlike transaction-type precompile methods that legitimately accept payment (e.g. `gov.deposit`, `bank.sendNative`, `wasmd.execute`), which explicitly call `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` to route the attached `usei`/`wei` into the intended Cosmos-side transfer, `rewards()` performs no such handling: [5](#0-4) [6](#0-5) 

Because the EVM's native `CALL`-with-value semantics debit the caller and credit the precompile's associated address in the underlying `usei`/`wei` StateDB balances (`x/evm/state/balance.go`) before/while the precompile logic runs, and `rewards()` neither rejects the value nor moves it anywhere useful, the sent `usei`/`wei` ends up permanently held at the precompile's mapped Sei address. There is no governance, admin, or user-facing function in the distribution precompile (or elsewhere) that lets that value be withdrawn back out, matching the underlying "no rescue mechanism" pattern in the referenced report.

### Impact Explanation
Any unprivileged EVM caller (regular wallet transaction, contract, or RPC client) who calls `rewards(address)` on the distribution precompile with non-zero `msg.value` permanently loses that value: it is neither refunded to the caller nor forwarded to any legitimate recipient, and there's no rescue path to retrieve it. This is a concrete, fund-loss condition matching the "permanent freezing of funds" acceptance criteria — reachable purely through a single submitted EVM transaction with no special privileges required.

### Likelihood Explanation
Likelihood is non-trivial: the ABI marks other distribution methods `payable`/`nonpayable` per Solidity-side wrapper conventions, and users/dApps interacting through generic multicall or fee-forwarding wrapper patterns, or simply due to fat-fingering a value field in a wallet, could easily attach value to a `rewards` call. The project's own test suite explicitly flags this as an unguarded quirk, indicating the team is aware behavior differs from the rest of the module's view methods, which is a strong signal the omission is unintentional and reachable in production usage.

### Proof of Concept
1. An EVM user calls the distribution precompile at `0x0000000000000000000000000000000000001007` with function selector for `rewards(address)`, passing their own associated Sei address as the argument, and attaches `msg.value = 1 sei` (or any nonzero wei/usei amount).
2. The EVM `CALL` value-transfer semantics debit the caller's `usei`/`wei` balance and credit the precompile's associated Sei address balance.
3. `Execute` routes to `rewards(ctx, method, args)` (`precompiles/distribution/distribution.go:204-205`), which never inspects `value`, executes successfully, and returns the delegation rewards data.
4. The transaction succeeds; the attached value is not refunded to the caller, not applied to any distribution action, and remains stranded on the precompile's associated account with no exposed withdraw/rescue function — permanently lost to the caller.
