The `onAccept` function in `SimplexPaymaster.sol` only authenticates the **source chain**, not the **source module/application**, which is exactly the missing check the invariant calls out.

### Title
Missing source-module (app) authentication in `SimplexPaymaster.onAccept` allows any Hyperbridge-side module to execute governance actions - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`onAccept` is the sole administrative entry point for `SimplexPaymaster` — it processes `UpgradeContract`, `UpdateParams`, `RegisterToken`, `DeactivateToken`, and `WithdrawAssets` requests. It is guarded by `onlyHost` (caller must be the local `EvmHost`) and by a check that `incoming.request.source` equals `IDispatcher(host()).hyperbridge()`. However it never checks `incoming.request.from`, i.e. it never verifies which module/application on the Hyperbridge chain actually dispatched the message. [1](#0-0) 

### Finding Description
The contract's own documentation states the security model explicitly: "every administrative action ... is an `onAccept` request authenticated as originating from Hyperbridge governance and delivered by the local host," implying dual authentication of chain + module. [2](#0-1) 

In practice, `onAccept` only checks:
1. `msg.sender == host()` (via `onlyHost` inherited from `HyperApp`) — guarantees the call came through the local `EvmHost` relay path. [3](#0-2) 
2. `keccak256(incoming.request.source) == keccak256(IDispatcher(host()).hyperbridge())` — guarantees the message originated from the Hyperbridge state machine/chain. [4](#0-3) 

It never checks `incoming.request.from`, which identifies the specific module/pallet on the Hyperbridge chain that dispatched the request. Any permissionless module, pallet, or application living on the Hyperbridge state machine — not just the intended governance module — can dispatch a POST request targeting this paymaster with an attacker-shaped body (`RequestKind` byte + payload). Because the chain check passes (it's still coming "from Hyperbridge"), the module-identity gap lets an unprivileged actor on the Hyperbridge side (e.g. any deployed/permissionless pallet capable of dispatching ISMP messages, or a message crafted to appear from an arbitrary `from` value) trigger:
- `ERC1967Utils.upgradeToAndCall` — arbitrary implementation upgrade,
- `_registerToken` — inject a malicious token/oracle pair,
- `_deactivateToken` — grief legitimate tokens,
- `_withdrawAssets` — drain ERC-20 surplus or the EntryPoint deposit to `treasury` (and if `UpdateParams` can also be abused first to redirect `treasury`, this becomes a direct fund-diversion path).

This matches the reviewed invariant precisely: "cross-chain paymaster governance must authenticate both Hyperbridge as source chain and the intended governing module as source app" — only the first half is enforced.

### Impact Explanation
This directly matches the Critical impact category called out in the question: unauthorized upgrade, token registration, token deactivation, or asset withdrawal, all reachable without any privileged operator involvement, using only unprivileged/legitimate ISMP delivery through the local host from a non-governance module on the source chain.

### Likelihood Explanation
Likelihood is high assuming any module other than the designated governance module can originate a POST request to this destination/module id on Hyperbridge (a permissionless or lower-trust pallet, or a misconfigured relay). This is a structural authorization gap in the contract code itself (missing `from` check), not dependent on relayer compromise or malicious infrastructure, and it is entirely within the EVM contract scope required by the bounty (ignoring malicious peers/relayers).

### Recommendation
Add an explicit, immutable/governance-set `governanceModule` (the expected `from` value on the Hyperbridge chain) and check it in `onAccept`:
```solidity
if (keccak256(incoming.request.from) != keccak256(governanceModule)) revert UnauthorizedCall();
```
in addition to the existing `source` chain check, mirroring the pattern used elsewhere in the codebase for other apps that bind both chain id and module/app identity (e.g., `BandwidthManager.sol`, `HostManager.sol`) — worth confirming those modules perform the `from` check that `SimplexPaymaster` is missing.

### Proof of Concept
1. Deploy `SimplexPaymaster` with `initialize(host_, params_, tokens_, oracles_)`.
2. From the Hyperbridge side, dispatch (through legitimate ISMP relay/host delivery) a POST request whose `dest` module is the `SimplexPaymaster` address, `source` equals the real `hyperbridge()` chain id (so the existing check passes), but `from` is an arbitrary/non-governance module address, with `body = abi.encodePacked(uint8(RequestKind.WithdrawAssets), abi.encode(tokenAddr, amount))`.
3. `HandlerV2.handlePostRequests` delivers this to `EvmHost`, which calls `SimplexPaymaster.onAccept(incoming)` as `msg.sender == host()`.
4. `onAccept` checks only `incoming.request.source`, which matches, and proceeds to execute `_withdrawAssets(tokenAddr, amount)`, sweeping funds to `treasury` — despite the request never having originated from the intended governance module.
5. Because `incoming.request.from` is never validated, this succeeds regardless of which module dispatched it, confirming the missing module-identity check.

Note: I could not fully verify within the indexed code whether the wider ISMP/Handler pipeline enforces any destination-module-to-source-module binding at a layer above `onAccept` (e.g., in `EvmHost` or `Message.sol`) that might mitigate this at a different layer — the `PostRequest`/`IncomingPostRequest` struct definitions were only partially retrievable in this session. If such a binding does not exist elsewhere, this finding stands as described; if it does exist, the finding would need re-scoping to whichever layer is actually deficient. I'd recommend a follow-up read of `sdk/packages/core/contracts/interfaces/IApp.sol` and `evm/src/core/EvmHost.sol`'s request-dispatch validation to close this gap definitively.

```text
    /// @dev Handles governance requests delivered by the local host. The first
    ///      byte of the request body encodes the `RequestKind`; only requests
    ///      originating from Hyperbridge itself are accepted.
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) {
            revert UnauthorizedCall();
        }

        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        bytes calldata payload = incoming.request.body[1:];

        if (kind == RequestKind.UpgradeContract) {
            (address newImpl, bytes memory initData) = abi.decode(payload, (address, bytes));
            ERC1967Utils.upgradeToAndCall(newImpl, initData);
        } else if (kind == RequestKind.UpdateParams) {
            _setParams(abi.decode(payload, (Params)));
        } else if (kind == RequestKind.RegisterToken) {
            (address token, address oracle) = abi.decode(payload, (address, address));
            _registerToken(token, AggregatorV3Interface(oracle));
        } else if (kind == RequestKind.DeactivateToken) {
            _deactivateToken(abi.decode(payload, (address)));
        } else if (kind == RequestKind.WithdrawAssets) {
            (address token, uint256 amount) = abi.decode(payload, (address, uint256));
            _withdrawAssets(token, amount);
        }
    }
```
