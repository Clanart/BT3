### Title
Attacker-controlled `ReceivedOutput::read` bytes forge the offset/output binding, reporting funds as received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` couples a secret scalar `offset` (needed to spend the output under the tweaked Taproot key) with an arbitrary `TxOut` and `OutPoint`. `ReceivedOutput::read` deserializes all three fields from untrusted bytes with no consistency check that `output.script_pubkey` actually equals `p2tr_script_buf(key + G * offset)`. Analogous to a file-overwrite primitive — where attacker bytes replace a critical record — this lets an unprivileged party overwrite the trusted `(offset, output)` binding, causing outputs to be reported as received that can never be spent by the group key.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs:122-134`, `ReceivedOutput::read` reads a `Secp256k1` scalar offset via `Secp256k1::read_F`, then consensus-decodes a `TxOut` and an `OutPoint`, and returns them as a coherent `ReceivedOutput`. The legitimate producer, `Scanner::scan_transaction` (`mod.rs:199-214`), only ever pairs an output with the offset whose registered `script_pubkey` matched (`self.scripts.get(&output.script_pubkey)` at line 205). The deserialization path performs no equivalent check: the offset, the script inside `output`, and the outpoint are accepted as independent attacker-chosen fields.

Because `ReceivedOutput` does not carry the base key, the invariant "the output pays to `key + offset*G`" is only ever enforced on the scan path; on the read path it is silently dropped. A crafted byte stream therefore produces a `ReceivedOutput` that downstream code treats as a spendable input — `offset()` (line 101), `output()`/`value()` (lines 106-118), and `outpoint()` (line 111) are all consumed by the signing flow (`SignableTransaction::new` per the wallet test usage) — while the real key cannot sign for it.

### Impact Explanation
An attacker supplying bytes to `ReceivedOutput::read` can either:
- Pair a real on-chain output paying to some unrelated script with a valid offset, causing the wallet to count unspendable value as an available input (integrity loss: plans/balances computed on phantom funds), or
- Pair a legitimately-owned script with a wrong offset, producing an input the FROST signers cannot actually sign for — transactions built on it fail or, if aggregated with other inputs, misattribute value.

This maps the CVE's "overwrite critical configuration → unauthorized behavior change / DoS" onto Serai: the serialized `ReceivedOutput` record is the configuration-equivalent for which inputs exist and how to spend them, and overwriting its `offset`/`output` binding corrupts that state. Funds are reported received that are not spendable — a concrete accepted impact.

### Likelihood Explanation
Reachable whenever serialized `ReceivedOutput`s transit untrusted storage or messages (the `read`/`serialize` pair exists precisely for persistence/transport, as exercised in `networks/bitcoin/tests/wallet.rs:252`). The attacker needs only write access to those bytes — no key material, no validator collusion. Severity is Medium: integrity loss and signing failure rather than direct key recovery.

### Recommendation
Make `ReceivedOutput` self-validating. Either store and check the base `key` (or the expected `script_pubkey`) inside `ReceivedOutput::read` and verify `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset)`, or bind the offset into the serialized form implicitly (e.g., derive the offset's commitment from the output and reject mismatches). At minimum, document that `read` must only consume bytes produced by a trusted `Scanner`, and add a `verify(key) -> bool` method callers must invoke after deserialization.
