Confirmed: `blockCtx.Transfer = core.Transfer` in [1](#0-0)  means the EVM uses go-ethereum's standard `core.Transfer`, which does a raw `StateDB.SubBalance`/`AddBalance` on the sender/recipient *before* the precompiled contract's `Run` is invoked — completely bypassing the bank keeper. This is the exact mechanical analog of the report: value is force-moved into the target address regardless of whether that address (a precompile) has any logic to accept, forward, or recover it.

Given the codebase's own explicit acknowledgment of this exact class of bug — the ERC20 precompile hard-rejects any `contract.Value() > 0` specifically "because they are not managed by an EOA and will not be possible to recover funds sent to an instance of them" [2](#0-1)  — the same protection is conspicuously absent from the `bank`, `bech32`, `slashing`, `distribution`, `ics20`, and `gov` precompiles, none of which call `contract.Value()` at all (confirmed by `grep`: `contract.Value()` only appears in `erc20.go`, `werc20/tx.go`, and `precompile.go`). Only `erc20`/`werc20` explicitly guard/consume value; `staking`'s `Delegate`/`CreateValidator` consume an explicit `amount` argument rather than `contract.Value()`, so a mismatched or additional `msg.value` sent alongside those calls is also never touched by the staking Go code.

### Title
Native token value sent to non-ERC20 static precompiles (bank, bech32, slashing, distribution, ics20, gov, staking) is silently and permanently locked - (File: x/vm/keeper/state_transition.go, precompiles/bank/bank.go, precompiles/bech32/bech32.go, precompiles/slashing/slashing.go)

### Summary
The EVM's block context uses go-ethereum's stock `core.Transfer` function [1](#0-0)  to move `msg.value`/`call{value:}` directly between `StateDB` accounts before a precompile's `Run` executes. This transfer is a raw `StateDB` balance mutation and is completely independent from the Cosmos SDK `x/bank` keeper. Static precompiles other than `erc20`/`werc20` have no code path that consumes, forwards, or rejects `contract.Value()`; their `Execute`/`Run` implementations never reference it (confirmed absent in `bank.go`, `bech32.go`, `slashing.go`, `distribution.go`, `ics20.go`, `staking.go`). Consequently, any user who calls one of these precompiled contract addresses (e.g. `0x...0804` Bank, `0x...0400` Bech32, `0x...0806` Slashing, `0x...0801` Distribution, `0x...0802` ICS20, `0x...0805` Gov) with non-zero `value` will have that value permanently credited to the precompile's `StateDB` account balance, with no bank-module coins ever having moved and no mechanism in any keeper to sweep, refund, or otherwise account for it.

### Finding Description
`ERC20`'s `Execute` explicitly guards against this exact scenario, calling out that funds sent to a precompile are unrecoverable due to lack of a fallback handler [2](#0-1) . `WERC20`'s `deposit` explicitly reads `contract.Value()` and sends the equivalent bank coin back to the caller via `BankKeeper.SendCoins` to keep StateDB and bank balances synchronized [3](#0-2) . No other static precompile does either of these things:
- `bank.Precompile.Execute`/`Run` never checks or moves `contract.Value()` [4](#0-3) .
- `bech32.Precompile.Run` never checks `contract.Value()` [5](#0-4) .
- `slashing.Precompile.Execute` never checks it [6](#0-5) .
- `distribution.Precompile.Execute` never checks it [7](#0-6) .
- `ics20.Precompile.Execute` never checks it [8](#0-7) .
- `staking.Delegate`/`CreateValidator` take an explicit `amount`/`_value` Solidity parameter rather than reading `contract.Value()`, so it is entirely possible to send `msg.value` that differs from (or is in addition to) the declared amount, and the discrepancy is never reconciled [9](#0-8) .

Because the underlying block-level `Transfer` function is go-ethereum's stock implementation operating purely on `StateDB` balances [1](#0-0) , this value movement happens *before* the precompile's Go code even runs, and it never emits `x/bank` `coin_spent`/`coin_received` events. The `BalanceHandler` mechanism used by `staking`/`ics20` (via `BalanceHandlerFactory`) only reconciles StateDB balances *from* bank events that the precompile's own logic produces [10](#0-9)  — it does nothing to handle or refund a raw `contract.Value()` that was never touched by any bank operation.

### Impact Explanation
Value sent this way becomes a `StateDB` balance at the precompile's fixed hex address (e.g. `0x...0804`). This balance is not backed by real bank-module coins (no `SendCoins`/mint ever occurred), so:
- The tokens are permanently and irrecoverably locked/lost for the sending user — there is no `withdraw`, `receive`, or governance path that can move funds out of a precompile address's StateDB balance back to a spendable bank account, since precompile addresses aren't real accounts with keepers watching them.
- This produces a durable, unauthorized discrepancy between total EVM-visible balances (StateDB, which underlies `eth_getBalance` / `balanceOf` semantics for the native denom) and the actual native coin supply tracked by `x/bank`/`x/precisebank`, i.e. an accounting corruption of the native asset's 1:1 representation invariant between EVM and bank state.

This matches the "Critical permanent freezing/locking, theft, or unauthorized extraction of user funds" and "irreversible accounting corruption ... across native balances, EVM balances" impact classes: user-spendable value is unrecoverably destroyed as a spendable asset while incorrectly still appearing as StateDB balance at an address nobody controls.

### Likelihood Explanation
Trivial and fully unprivileged: any EOA can call any of these static precompile addresses directly with a non-zero `value` field (either through a raw `eth_sendTransaction`/`eth_call` with value, or via a Solidity contract using `.call{value: x}(...)` against the precompile address) using standard tooling (MetaMask, ethers.js, Hardhat). No special permissions, validator collusion, or governance action is required — this is ordinary EVM call flow through the precompile dispatch path already exercised by countless integration tests in the repo (e.g. `tests/integration/precompiles/*`).

### Recommendation
Add the same value-rejection guard used by `erc20.Precompile.Execute` [2](#0-1)  to every static precompile that does not explicitly consume `contract.Value()`: `bank`, `bech32`, `slashing`, `distribution`, `ics20`, `gov`, and non-payable methods of `staking`. Alternatively, implement a common check in `cmn.Precompile.RunNativeAction`/`runNativeAction` (the shared entry point at [11](#0-10) ) that rejects any call carrying `contract.Value() > 0` unless the specific precompile method explicitly opts in and reconciles the transferred value against a real bank operation (as `werc20.Deposit` does).

### Proof of Concept
1. Deploy or use an existing EOA/contract on a Cosmos EVM chain with the default precompile set enabled (addresses per [12](#0-11) ).
2. From the EOA, send a raw EVM transaction to the Bech32 precompile address `0x0000000000000000000000000000000000000400` (or Bank `0x...0804`, Slashing `0x...0806`, etc.) with calldata for a valid read method (e.g. `hexToBech32`) and `value = 1 ether`.
3. The transaction succeeds (since `bech32.Run`/`bank.Run`/etc. never check `contract.Value()`); the EOA's EVM balance decreases by 1 ether, and the precompile address's `StateDB` balance increases by 1 ether.
4. Query `eth_getBalance` for the precompile address — it now shows a non-zero balance.
5. Attempt to recover the funds: there is no `withdraw`, `receive`, `fallback`, or admin/governance function on any of these precompiles, and no keeper holds a reference letting it sweep an arbitrary EVM address's StateDB balance back into `x/bank`. The 1 ether is permanently stranded, and total spendable bank-backed value has effectively decreased by that amount while StateDB shows it as "owned" by an address no one can act as.

**Uncertainty note**: I was not able to directly execute this PoC in the sandbox (no filesystem/terminal access in Ask mode) or trace `core.Transfer`'s exact byte-level semantics from go-ethereum's vendored source within the index, so this analysis relies on the documented `blockCtx.Transfer = core.Transfer` wiring and the absence of any `contract.Value()` handling in the affected precompiles' Go source, cross-validated against ERC20's own explicit guard and comment describing this exact failure mode. A Devin session with full repo/tooling access could confirm this precisely by instrumenting a local devnet and executing the PoC steps above.

// Run executes the precompiled contract bech32 methods defined in the ABI.
func (p Precompile) Run(_ *vm.EVM, contract *vm.Contract, _ bool) (bz []byte, err error) {
	// NOTE: This check avoid panicking when trying to decode the method ID
	if len(contract.Input) < 4 {
		return nil, vm.ErrExecutionReverted
	}

	methodID := contract.Input[:4]
	// NOTE: this function iterates over the method map and returns
	// the method with the given ID
	method, err := p.MethodById(methodID)
	if err != nil {
		return nil, err
	}

	argsBz := contract.Input[4:]
	args, err := method.Inputs.Unpack(argsBz)
	if err != nil {
		return nil, err
	}

	switch method.Name {
	case HexToBech32Method:
		bz, err = p.HexToBech32(method, args)
	case Bech32ToHexMethod:
		bz, err = p.Bech32ToHex(method, args)
	}

	if err != nil {
		return nil, err
	}

	return bz, nil
}

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	initialGas := ctx.GasMeter().GasConsumed()

	defer HandleGasError(ctx, contract, initialGas, &err)()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)

	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	var balanceHandler *BalanceHandler
	if p.BalanceHandlerFactory != nil {
		balanceHandler = p.BalanceHandlerFactory.NewBalanceHandler()
	}

	if balanceHandler != nil {
		balanceHandler.BeforeBalanceChange(ctx)
	}

	bz, err = action(ctx)
	if err != nil {
		return bz, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	if balanceHandler != nil {
		if err := balanceHandler.AfterBalanceChange(ctx, stateDB); err != nil {
			return nil, err
		}
	}

	return bz, nil
}
