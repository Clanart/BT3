Audit Report

## Title
Vote account `pending_delegator_rewards` counter is never decremented after block-reward distribution, permanently inflating the authorized withdrawer's reserved-balance floor - (File: `programs/vote/src/vote_state/mod.rs`)

## Summary
`pending_delegator_rewards` in `VoteStateV4` is incremented on every `DepositDelegatorRewards` instruction via `add_pending_delegator_rewards`, and is used by `withdraw()` as a mandatory reserved-balance floor (lamports below `rent_exempt_minimum + pending_delegator_rewards` cannot be withdrawn, and the account cannot be fully closed while it is nonzero). Each epoch, `calculate_block_reward()` reads this same field to compute and mint delegator rewards from capitalization, but no code path in the codebase ever reduces `pending_delegator_rewards` once that reward has been paid, causing the reserved floor to permanently diverge upward from the actual outstanding obligation.

## Finding Description
The field is mutated additively only in `add_pending_delegator_rewards` (`programs/vote/src/vote_state/handler.rs` L196-209), called from `deposit_delegator_rewards` (`programs/vote/src/vote_state/mod.rs` L936-988) during `DepositDelegatorRewards` processing. Each epoch, `calculate_block_reward()` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs` L173-231) reads `pending_delegator_rewards` from the vote account to compute a delegator's proportional share, capped at the current `pending_delegator_rewards` value, and this reward is minted into stake accounts and capitalization by `store_stake_accounts_in_partition` / `distribute_epoch_rewards_in_partition` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs` L175-224, L336-423). Neither of these distribution functions touches or updates the vote account's stored `pending_delegator_rewards` field — confirmed by the absence of any reference to `pending_delegator_rewards` in `distribution.rs`. Meanwhile, `withdraw()` (`programs/vote/src/vote_state/mod.rs` L1079-1121) treats the full, ever-growing `pending_delegator_rewards` value as a floor that must remain in the vote account, and unconditionally blocks account closure while it is greater than zero. Since the field only grows and is never reduced to reflect rewards already paid out (from minted capitalization, not from the reserved vote-account balance), the reserved floor diverges from the actual outstanding obligation with every deposit/distribution cycle.

## Impact Explanation
This causes a fund-lock condition for the `authorized_withdrawer`: legitimate lamports in the vote account (commission, deposited-but-already-distributed reward residue, or other balance) become permanently unwithdrawable as `pending_delegator_rewards` grows unbounded, and the vote account can never be fully closed while `pending_delegator_rewards > 0`, which per the observed code path never returns to zero. This falls under fund loss/lock within the runtime/accounts/built-in vote program scope, with the exact corrupted value being the `pending_delegator_rewards` field of `VoteStateV4` used as the withdrawal-floor in `withdraw()`.

## Likelihood Explanation
No privileged or adversarial action is required — this occurs under the intended, documented SIMD-0123 flow: repeated `DepositDelegatorRewards` calls plus normal per-epoch reward distribution are sufficient to grow `pending_delegator_rewards` without bound, independent of whether the corresponding reward has already been distributed.

## Recommendation
Add a decrement operation (e.g., `sub_pending_delegator_rewards`) applied to the vote account's `VoteStateV4.pending_delegator_rewards` field whenever its block reward has been included in a partition and successfully distributed in `store_stake_accounts_in_partition` / `distribute_epoch_rewards_in_partition`, so the reserved floor tracks only rewards that remain actually outstanding and unpaid.

## Proof of Concept
1. Enable SIMD-0123/`block_revenue_sharing`; create a V4 vote account with delegated stake.
2. Call `DepositDelegatorRewards` repeatedly to grow `pending_delegator_rewards`, as in the `deposit_delegator_rewards` flow validated in `programs/vote/src/vote_processor.rs` L5120-5140.
3. Advance multiple epochs so `calculate_block_reward` / `store_stake_accounts_in_partition` mint and distribute the corresponding reward to delegators — verify via `pending_delegator_rewards()` that the field is unchanged despite the reward being paid.
4. Attempt `Withdraw` as `authorized_withdrawer` for an amount leaving less than `rent_exempt_minimum + pending_delegator_rewards`; observe `InstructionError::InsufficientFunds`, as in `test_withdraw_with_pending_delegator_rewards`, and note the reserve requirement only grows across epochs, eventually exceeding the account's real available balance.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
