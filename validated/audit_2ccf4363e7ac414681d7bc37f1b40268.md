### Title
Shared `CallDispatcher` used by IntentGatewayV2 has no target whitelist, letting a malicious order drain residual/dust token balances from other orders - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` executes arbitrary `to.call{value}(data)` for any attacker-supplied `Call[]`, with the only check being that `to` has code (`extcodesize > 0`) [1](#0-0) . This is the same missing-whitelist pattern flagged in the external report for `Executor.sol._executeSwaps()`. Unlike LiFi's `SwapperV2`, which restricts callable targets/selectors via a dex allowlist, Hyperbridge's `CallDispatcher` is a single shared contract instance (`_params.dispatcher`) reused across *all* orders processed by `IntentGatewayV2` / `IntentsBase`, and it is explicitly documented to accumulate token/ETH dust between calls.

### Finding Description
`IntentsBase._execute()` dispatches attacker/user-controlled `order.output.call` through the shared dispatcher, then sweeps whatever balance is left on it back to the gateway, emitting `DustCollected` for any leftover amount [2](#0-1) . The same shared dispatcher is used for `order.predispatch.call` in `IntentGatewayV2.sol` [3](#0-2) .

Because `order.output.call` / `order.predispatch.call` are fully attacker-controlled (any unprivileged user can call `placeOrder`/craft the order body) and `CallDispatcher.dispatch()` places no restriction on `to` or `data` beyond "is a contract," a malicious order can encode a call such as `ERC20(token).approve(attacker, type(uint256).max)` issued *from the dispatcher*. This approval persists in the token contract's storage independent of the transaction that set it, since `CallDispatcher` is a single long-lived contract shared by every order that ever routes that token through it. Any dust the dispatcher accumulates for that token from a *different, unrelated* order (explicitly acknowledged by the `DustCollected` event/comment: "any residual token balances left on the dispatcher are swept back... and accounted for as protocol dust") [4](#0-3)  can then be pulled out by the attacker at any later time via a plain `transferFrom(dispatcher, attacker, amount)` call on the token contract, using the standing approval — completely outside of the gateway's control flow.

This is structurally identical to the reported issue: `Executor.sol._executeSwaps()` had no whitelist and could set unlimited allowances that let an attacker steal "leftover tokens in the Executor contract," while `SwapperV2.sol` mitigated this via `dexAllowlist`/`dexFuncSignatureAllowList`. `CallDispatcher.dispatch()` has no analogous allowlist for `to` or the function selector in `data`.

### Impact Explanation
Any dust/residual token balance sitting in the shared `CallDispatcher` (acknowledged by the protocol's own dust-sweep/event logic) can be permanently siphoned by an attacker who merely places one malicious order with a crafted `output.call`/`predispatch.call` containing an `approve()` to themselves, then later calls `transferFrom` directly on the token. This is a direct loss-of-funds primitive reachable by any unprivileged user through the public `placeOrder`/`fillOrder` entrypoints — it does not require a malicious relayer, prover, or admin.

### Likelihood Explanation
The attack requires only: (1) constructing an order whose `output.call`/`predispatch.call` includes an `approve` call routed through the shared dispatcher — fully permitted since `dispatch()` performs no target/selector filtering, and (2) waiting for/triggering dust to accumulate for the targeted token (which the codebase's own comments confirm happens routinely via `DustCollected`). No privileged role, race condition, or malicious infrastructure operator is needed, making this practically exploitable by any address able to call the public order functions.

### Recommendation
- Add a target/selector allowlist to `CallDispatcher.dispatch()` (mirroring `SwapperV2`'s `dexAllowlist`/`dexFuncSignatureAllowList` pattern), or
- Deploy a fresh, single-use `CallDispatcher` (e.g., via `CREATE2`/minimal proxy) per order/fill instead of reusing one shared instance, so no token approval or balance can persist across orders, or
- At minimum, explicitly revoke/reset any approvals granted during `dispatch()` before returning, and ensure the dispatcher never retains a nonzero token balance/approval after a call sequence completes (fail the fill instead of silently emitting `DustCollected`).

### Proof of Concept
1. Attacker calls `placeOrder`/constructs a fill so that `order.output.call` (or `order.predispatch.call`) is `abi.encode([Call({to: USDC, value: 0, data: approve(attacker, type(uint256).max)})])`.
2. `IntentsBase._execute()` (or the `IntentGatewayV2` predispatch path) calls `ICallDispatcher(dispatcher).dispatch(order.output.call)`, which executes `USDC.approve(attacker, max)` from the dispatcher's context — `CallDispatcher.dispatch()` at [1](#0-0)  only checks `extcodesize(USDC) > 0`, allowing this unrestricted call.
3. In a subsequent, unrelated order fill that routes USDC through the same shared `dispatcher`, any USDC dust left un-swept (per the documented dust-collection behavior at [5](#0-4) ) remains on the dispatcher's balance momentarily/persistently.
4. Attacker calls `USDC.transferFrom(dispatcher, attacker, dust_amount)` directly using the standing approval from step 1, draining funds that belonged to other users'/solvers' orders.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
