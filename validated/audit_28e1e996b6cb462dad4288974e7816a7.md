### Title
`ThresholdKeys::read` trusts an attacker-declared participant count to drive unbounded allocation and curve-point deserialization before any validation - ([File: crypto/dkg/src/lib.rs])

### Summary
The referenced Wings bug class is a resource limit that is checked once up front (against a stale/declared value) and then never enforced while the actual work proceeds. The analog in Serai is `ThresholdKeys::<C>::read` in `crypto/dkg/src/lib.rs`. An unprivileged party who can feed bytes to `ThresholdKeys::read` (explicitly an exposed untrusted-input path) controls `n`, a `u16` read directly from the stream. That single declared value is then trusted to size an allocation and to drive `n` scalar reads plus `n` elliptic-curve point decompressions, all before `ThresholdParams::new` performs any consistency validation of `t`, `n`, and `i` at the end of the function.

### Finding Description
In `ThresholdKeys::read`, after the curve-ID check, three `u16`s are read as `(t, n, i)`, and `n` is used unchecked:

```rust
// crypto/dkg/src/lib.rs ~L604-623
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
  ...
};
let secret_share = Zeroizing::new(C::read_F(reader)?);
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
ThresholdKeys::new(
  ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
  ...
)
```

`Vec::with_capacity(usize::from(n))` allocates for up to 65,535 scalars, and then two loops each run `n` iterations of `read_F`/`read_G`. `read_G` performs a full point decompression plus a canonicality re-encoding comparison per iteration (`crypto/ciphersuite/src/lib.rs` L91-100). Only after all of this work is done is `ThresholdParams::new(t, n, i)` invoked — the analog of Wings checking the quota at handle-open and never again: the validity bound is deferred to the very end while the resource consumption is committed up front based purely on attacker-supplied bytes.

Additionally, the `Interpolation::Constant` arm reads `n` coefficients. Constant interpolation of a threshold-`t` secret requires only `t` coefficients, so the count read is also inconsistent with the cryptographic requirement — a declared `n` far larger than `t` inflates the work and the stored polynomial with no structural check at read time.

### Impact Explanation
- **Resource exhaustion (the direct analog):** a single short input (~a dozen header bytes) forces an allocation and up to ~65,535 point decompressions plus ~65,535 scalar reads — a large asymmetric CPU/memory amplification per `ThresholdKeys::read` call, comparable in shape to Wings letting one SFTP write exhaust a shared resource far beyond its declared bound. Repeated submissions amplify this linearly.
- **Validation-after-consumption:** because `ThresholdParams::new` runs only after the reads, every structural rejection (e.g., `t > n`, `i > n`, `i == 0`) is paid for at full cost, so even fully invalid inputs burn maximum resources.
- **Coefficient-count mismatch:** `Interpolation::Constant` reading `n` rather than `t` coefficients means the deserialized structure can carry a polynomial of degree unrelated to the threshold, which downstream key-recovery/share-verification logic may interpret inconsistently (this could not be fully confirmed against `ThresholdKeys::new`/`Interpolation` internals within the available context).

### Likelihood Explanation
Reachability depends on an integrator passing externally supplied bytes to `ThresholdKeys::read` — the prompt scope treats untrusted bytes into this function as reachable. Where it is reachable (e.g., exchanging or recovering key material), a single malicious peer triggers the amplification with trivial bandwidth. The bound is `u16`-capped, so each call is finite (~4 MB of field reads plus decompression cost), making this a Medium-severity availability issue rather than the unbounded exhaustion of the Wings original — the class matches, the magnitude does not.

### Recommendation
- Validate `t`, `n`, `i` via `ThresholdParams::new` (or manual range checks, e.g., `t <= n`, `n <= MAX_PARTICIPANTS` used elsewhere in the protocol) **before** allocating or reading any `n`-proportional data.
- Reject `n` values exceeding the protocol's actual participant bound prior to `Vec::with_capacity` and the read loops.
- For `Interpolation::Constant`, read exactly `t` coefficients, not `n`.

### Proof of Concept
Construct a byte stream for `ThresholdKeys::<C>::read` with: valid `C::ID` length prefix and ID, `t = 1`, `n = 0xFFFF`, `i = 1`, interpolation byte `0x00` (Constant), followed by a truncated payload. The function will allocate a 65,535-element vector and begin consuming scalars/points; regardless of whether the stream completes (CPU/memory spent) or errors on EOF (error after allocation and partial decompression work), the attacker pays only ~15 bytes. In the completing case, `ThresholdParams::new`/`ThresholdKeys::new` validation occurs only after ~131,070 field/group element reads have been performed.
