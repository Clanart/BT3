## Finding

The bug-class from the report (a callback/external transfer call that can conditionally revert and block/corrupt a fee-distribution flow) maps directly onto Cosmos EVM's `x/erc20` "native ERC20" reconversion logic used by the ICS-20 receive/ack/timeout callbacks.

### Title
Reverting native-ERC20 `transfer` call permanently traps escrowed IBC funds in the `erc20` module account - (File: `x/erc20/keeper/msg_server.go`)

### Summary
`ConvertCoinNativeERC20` first moves the user's Cosmos coins into the `erc20` module account (`SendCoinsFromAccountToModule`) and only afterwards calls into the arbitrary, user/registrant-controlled ERC20 contract via `CallEVM("transfer", ...)`, burning the escrowed coins only if that external call succeeds and the balance invariance check passes. [1](#0-0)  If the external `transfer` call reverts, or the post-call balance check (`ErrBalanceInvariance`) fails, the function returns an error but never reverses the prior escrow step, since no `CacheContext`/rollback is used around this sequence.

### Finding Description
This function is invoked from three IBC callback paths that are all reachable by ordinary, unprivileged IBC transfers:
- `OnRecvPacket` (destination-side auto-conversion of a received voucher to its native ERC20 form) [2](#0-1) 
- `OnAcknowledgementPacket` / `OnTimeoutPacket` via `ConvertCoinToERC20FromPacket` (source-side reconversion on failed/timed-out transfers) [3](#0-2) 

The code's own documentation states the expected safety property: "If the ERC20 conversion fails for whatever reason ... the user receives the corresponding bank token from the TokenPair instead." [4](#0-3)  However, the actual implementation contradicts this guarantee: `SendCoinsFromAccountToModule` already ran and is not undone when the subsequent EVM call/invariance check fails, so the coins are not left in nor returned to the user's bank balance — they are stuck in the `erc20` module account. [5](#0-4) [6](#0-5) 

The `ConvertCoinToERC20FromPacket` caller for the ack/timeout path even swallows the error and returns `nil`, masking the fact that funds were trapped rather than restored to the user. [7](#0-6)  In the `OnRecvPacket` path, the failure instead propagates as an `ErrorAcknowledgement`, which additionally causes the **source** chain to refund the original sender — while the escrowed coins remain locked in the destination chain's module account, producing a duplication of spendable value across both chains. [8](#0-7) 

The condition needed to trigger the revert (an unprivileged event) is simply for the registered native-ERC20 contract's `transfer` function to revert when called from the module address — e.g. a pausable/blacklistable token, a token with transfer limits, or any contract logic that can be made to reject a transfer under attacker-influenced conditions (the attacker can register such a token pair or simply pause/blacklist their own already-registered contract, then send/receive an IBC transfer of it).

### Impact Explanation
This is a Critical, unauthorized, permanent freezing (and in the `OnRecvPacket` case, duplication) of user funds: real, escrowed Cosmos-SDK coins become permanently locked in the `erc20` module account with no code path returning or burning them, while in the receive-path scenario the sender is simultaneously refunded on the source chain, meaning the same value now exists both as a refund to the sender and as a stranded balance on the destination chain.

### Likelihood Explanation
Reachable by any unprivileged user performing standard ICS-20 transfers of a native-ERC20 token pair whose ERC20 contract can revert on `transfer` (pausable, blacklistable, allowance-dependent, or governance-toggled tokens are common patterns for native ERC20 tokens registered on Cosmos EVM chains). No relayer or validator collusion is required.

### Recommendation
Wrap the escrow + EVM-transfer + burn sequence in `ConvertCoinNativeERC20` in a `ctx.CacheContext()`/`writeFn` pattern (as already used elsewhere, e.g. `x/ibc/callbacks/keeper/keeper.go`), only committing the escrow and burn if the EVM call and balance invariance check both succeed; otherwise return the coins to the original owner before propagating the error, ensuring the documented "receives the bank token instead" guarantee actually holds.

### Proof of Concept
1. Register a native ERC20 token pair for a contract that the attacker controls and that can be toggled to revert `transfer` calls (e.g., a pausable token, or blacklist the module address post-registration).
2. Perform (or receive) a standard ICS-20 transfer of that token so that `OnRecvPacket`/`OnAcknowledgementPacket` invoke `ConvertCoinNativeERC20`.
3. Before/at the time of conversion, pause/blacklist the contract so the `transfer(moduleAddr → receiver)` call reverts.
4. Observe: the Cosmos coin was already moved via `SendCoinsFromAccountToModule` into the `erc20` module account, but `BurnCoins` never executes; on the receive path an error acknowledgement is returned, triggering a source-chain refund while the destination-side coins remain trapped in the module account — demonstrating permanent fund freezing / value duplication.

// OnAcknowledgementPacket responds to the success or failure of a packet
// acknowledgement written on the receiving chain. If the acknowledgement was a
// success then nothing occurs. If the acknowledgement failed, then the sender
// is refunded and then the IBC Coins are converted to ERC20.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnAcknowledgementPacket
// still succeeds, but the user receives the corresponding bank token from the
// TokenPair instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)
}

// ConvertCoinToERC20FromPacket converts the IBC coin to ERC20 after refunding the sender
// This function is only executed when IBC timeout or an Error ACK happens.
func (k Keeper) ConvertCoinToERC20FromPacket(ctx sdk.Context, data transfertypes.FungibleTokenPacketData) error {
	// Sender is local (source) chain address; accept local bech32 or 0x-hex
	senderBz, err := k.addrCodec.StringToBytes(data.Sender)
	if err != nil {
		return err
	}
	sender := sdk.AccAddress(senderBz)

	pairID := k.GetTokenPairID(ctx, data.Denom)
	pair, found := k.GetTokenPair(ctx, pairID)
	if !found {
		// no-op, token pair is not registered
		return nil
	}

	coin := ibc.GetSentCoin(data.Denom, data.Amount)

	switch {

	// Case 1. if pair is native coin -> no-op
	case pair.IsNativeCoin():
		// no-op, received coin is a  native coin
		return nil

	// Case 2. if pair is native ERC20 -> unescrow
	case pair.IsNativeERC20():
		// use a zero gas config to avoid extra costs for the relayers
		ctx = ctx.
			WithKVGasConfig(storetypes.GasConfig{}).
			WithTransientKVGasConfig(storetypes.GasConfig{})

		params := k.GetParams(ctx)
		if !params.EnableErc20 || !k.IsDenomRegistered(ctx, coin.Denom) {
			// no-op, ERC20s are disabled or the denom is not registered
			return nil
		}

		// assume that all module accounts on Cosmos EVM need to have their tokens in the
		// IBC representation as opposed to ERC20
		senderAcc := k.accountKeeper.GetAccount(ctx, sender)
		if types.IsModuleAccount(senderAcc) {
			return nil
		}

		// Convert from Coin to ERC20
		if err := k.ConvertCoinNativeERC20(ctx, pair, coin.Amount, common.BytesToAddress(sender), sender); err != nil {
			// We want to record only the failed attempt to reconvert the coins during IBC.
			defer func() {
				telemetry.IncrCounter(1, types.ModuleName, "ibc", "error", "total")
			}()
			ctx.EventManager().EmitEvents(
				sdk.Events{
					sdk.NewEvent(
						types.EventTypeFailedConvertERC20,
						sdk.NewAttribute(types.AttributeCoinSourceChannel, pair.Denom),
						sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
						sdk.NewAttribute("error", err.Error()),
					),
				},
			)
			return nil
		}
	}

	return nil
}
