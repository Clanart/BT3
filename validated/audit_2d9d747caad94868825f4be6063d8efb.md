### Title
Cached preprocess reuse across validator sets causes Schnorr nonce reuse and private key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a deterministic FROST/MuSig preprocess seed in `CachedPreprocesses`, keyed only by `context`. For the `DkgConfirmer`, the context is `(b"DkgConfirmer", attempt)` — it does **not** include the tributary spec/genesis, the validator set, or the message. Anal­ogous to CVE-2026-71193 (a uniqueness check scoped to one "pool" while the object is reachable from another pool), the deduplication scope here is too narrow: the same cache key is hit for *different* validator sets, so the identical nonce seed is used to sign different `set_keys_message`s, enabling nonce-reuse recovery of the validator's long-term MuSig secret key.

### Finding Description
`CachedPreprocesses` is defined as `context -> [u8; 32]` (coordinator/src/tributary/signing_protocol.rs:86-89). In `preprocess_internal`, if a cached entry exists for `self.context`, it is decrypted and passed to `AlgorithmSignMachine::from_cache`, which deterministically regenerates the exact same nonces via `seeded_preprocess` → `ChaCha20Rng::from_seed(seed)` → `Commitments::new` (crypto/frost/src/sign.rs:121-144, 268-274). The design intent is reboot safety: re-running the *same* signing session reproduces the *same* preprocess.

However, `DkgConfirmer::signing_protocol` sets `context = (b"DkgConfirmer", self.attempt)` (coordinator/src/tributary/signing_protocol.rs:274-277). Nothing in the key distinguishes *which* tributary spec, validator set (`self.spec.set()`), or genesis this attempt belongs to. A coordinator participates in DKGs for multiple validator sets/networks (each a distinct `TributarySpec`), all beginning at `attempt = 0`. When the second set's DKG confirmation runs, `CachedPreprocesses::get(txn, (b"DkgConfirmer", 0))` returns the seed cached for the first set, so the coordinator signs `set_keys_message(set_B, removed_B, key_pair_B)` — a different message — with the same nonce `k` already used for `set_keys_message(set_A, …)`.

The confirmation shares are public: they are published on the tributary in `Transaction::DkgConfirmed { attempt, confirmation_share, … }` (coordinator/src/tributary/handle.rs:508-516), and the aggregated Schnorrkel signature is published on-chain via `publish_set_keys` (handle.rs:550-559). Any observer seeing two signature shares `s_A = k + c_A·x` and `s_B = k + c_B·x` under the same `R = k·G` computes `x = (s_A − s_B)/(c_A − c_B)` — the validator's private MuSig key share (`self.key`, the validator's long-term secret). The encryption of the cache (`encryption_key` derived from `self.key` + context, signing_protocol.rs:107-114) does not prevent this: it decrypts identically under the same context, so the identical seed is returned.

### Impact Explanation
`self.key` is the validator's long-term Ristretto secret used for `musig(musig_context(set), key, participants)` across all sets it participates in (signing_protocol.rs:117-121). Recovering it lets an attacker impersonate that validator in future MuSig sessions and, if multiple validators hit the collision (which is systematic — every coordinator caches under the same flat context), reconstruct enough shares to forge validator-set signatures such as `set_keys`, i.e., take over key assignment for a Serai network and divert its funds. This is key-share recovery, squarely in scope per the rules.

### Likelihood Explanation
The collision requires only that a coordinator service more than one `TributarySpec` DKG sharing the same backing DB and the same `attempt` number — the normal case of `attempt = 0` for a fresh DKG, and again for every re-attempt number that coincides across two specs. No attacker action is needed to trigger it once two networks run DKGs; a passive observer of two tributaries (or one tributary plus the on-chain `set_keys` signature) performs the recovery. The exploit precondition is the multi-scope reachability the CVE analog describes: the cache is indexed per-context rather than per-(genesis, set, attempt), so an object created in one "pool" silently collides with another. Severity is Critical-class if the shared-DB assumption holds for the coordinator (a single `Db`/`txn` is threaded through all tributary handlers, and `CachedPreprocesses` has no genesis component in its key). If each tributary spec is provisioned a fully separate database, likelihood drops to low/untriggered; that deployment detail is the one element of scope I could not fully confirm from the indexed code.

### Recommendation
Include the domain's full identity in the cache key: `context` should incorporate `self.spec.genesis()` (or `self.spec.set()` and network) alongside the label and attempt, e.g. `(b"DkgConfirmer", spec.genesis(), attempt)`. Alternatively derive the seed as `Hash(context || genesis || attempt || msg-bound salt)` and/or bind the message into the seed so that any change in signed content yields fresh nonces. Defense-in-depth: derive nonces as `H(seed || participant_set || msg)` rather than `ChaCha20Rng::from_seed(seed)` alone, making reuse of a cached entry across any changed domain harmless.

### Proof of Concept
```rust
// Coordinator participates in DKGs for two validator sets (two TributarySpecs,
// e.g. Bitcoin and Ethereum networks), each starting at attempt = 0, sharing `txn`.

// Set A: first call caches the seed under (b"DkgConfirmer", 0) and signs msg_A
let confirmer_a = DkgConfirmer::new(&key, &spec_a, &mut txn, 0).unwrap();
let share_a = confirmer_a.share(preprocesses_a, &key_pair_a).unwrap();
// -> signs set_keys_message(set_A, removed_A, key_pair_A) with nonce k = f(seed)

// Set B: same context key -> CachedPreprocesses::get returns the SAME seed
let confirmer_b = DkgConfirmer::new(&key, &spec_b, &mut txn, 0).unwrap();
let share_b = confirmer_b.share(preprocesses_b, &key_pair_b).unwrap();
// -> signs set_keys_message(set_B, removed_B, key_pair_B) with the SAME nonce k

// Observer of both Transaction::DkgConfirmed publications sees shares
// s_A = k + c_A * x  and  s_B = k + c_B * x, then computes:
//   x = (s_A - s_B) / (c_A - c_B)   // the validator's long-term MuSig secret key
```

Code path: `DkgConfirmer::share` → `share_internal` → `SigningProtocol::share_internal` → `preprocess_internal` (signing_protocol.rs:99-148) → `AlgorithmSignMachine::from_cache` → `seeded_preprocess` (crypto/frost/src/sign.rs:121-144). The `context` at signing_protocol.rs:275 omits `spec.genesis()`/`spec.set()`, and `CachedPreprocesses` (signing_protocol.rs:86-89) is keyed solely by that context.

Note: I could not fully verify from the indexed code whether all `TributarySpec` handlers share one database/txn namespace for `CachedPreprocesses`. If they do not, this specific trigger is unreachable; if they do (the schema has no genesis component, suggesting a shared flat keyspace), the finding stands as described.
