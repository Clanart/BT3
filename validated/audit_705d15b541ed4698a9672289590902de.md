## Title
Payout attribution relies on an unauthenticated `OP_RETURN` field, allowing a false "operator credited" attribution — ([File: core/src/verifier.rs])

### Summary
The Chakra `ERC20Method` bug class is: a field inside a message that is supposed to gate/attribute an operation is decoded but never validated/authenticated, so an unrelated operation gets treated as if it were the validated one. In Clementine, the analogous binding is broken in the payout-attribution logic: the verifier decides *which operator gets credited as the payer of a withdrawal* purely by reading an unsigned `OP_RETURN` output of whatever transaction happens to spend the withdrawal UTXO — that field is never checked against who actually authorized/produced the payout.

### Finding Description
The payout transaction is built by `create_payout_txhandler` with three outputs: the user's payout output (protected by the user's `SinglePlusAnyoneCanPay` Schnorr signature), a CPFP anchor output, and an `OP_RETURN` output carrying the *claimed* operator's x-only public key: [1](#0-0) 

Because the only signed input uses `SIGHASH_SINGLE|ANYONECANPAY` (as documented on the `WithdrawParams` RPC message), the signature covers exactly one input and one output (the user payout). It does **not** cover the `OP_RETURN` output, so anyone who has the user's signature (obtained via the `withdraw`/`InternalWithdraw` RPC flows) can construct and broadcast a valid, fee-bumped variant of the payout transaction with an **arbitrary x-only public key** in the `OP_RETURN` field: [2](#0-1) [3](#0-2) 

When the verifier later processes the block containing this transaction, it derives `payout_payer_operator_xonly_pk` **solely** from parsing that `OP_RETURN` field, with no check that the named operator actually produced, funded, or authorized the transaction: [4](#0-3) 

This attribution is persisted directly into the `withdrawals` table: [5](#0-4) 

The attribution is then trusted downstream to automatically drive the credited operator's reimbursement flow. `PayoutCheckerTask` polls for "unhandled payouts" keyed by the operator's own x-only public key and, once found, automatically starts the kickoff/reimbursement machinery on that operator's behalf: [6](#0-5) 

The only consistency check performed later (`is_kickoff_malicious` / `send_asserts`) merely verifies that the operator sending the kickoff matches the `OP_RETURN` pubkey and that the committed block hash matches — both of which trivially hold for a framed/credited operator once the state machine has already been triggered: [7](#0-6) [8](#0-7) 

None of this validates that the entity named in `OP_RETURN` is the entity that actually broadcast/fronted the payout — the two are only checked for *self-consistency*, never for authenticity, exactly mirroring the missing `ERC20Method` check: a field that should gate/attribute an operation is trusted without validating who produced it.

### Impact Explanation
The binding broken is: `operator credited (OP_RETURN pubkey) == party that actually paid (broadcaster of the completed payout tx)`. Since the `OP_RETURN` is outside the signed portion of the transaction, any party holding the user's `SinglePlusAnyoneCanPay` signature can complete and broadcast the payout transaction naming a different operator as payer. The verifier's `update_finalized_payouts` will then record that named operator as `payout_payer_operator_xonly_pk`, and `PayoutCheckerTask` on the framed operator's node will autonomously drive that operator's kickoff/reimbursement flow for a withdrawal it never funded. Because the downstream consistency checks (`is_kickoff_malicious`) only re-check self-consistency between the (attacker-controlled) `OP_RETURN` and the kickoff that the framed operator is coerced into sending, the flow completes as "legitimate," resulting in an operator being reimbursed for a payout it never funded — one of the explicitly listed Critical impacts.

### Likelihood Explanation
Exploitation requires obtaining a user's withdrawal signature, which is distributed to operators (potentially to all operators, if the aggregator's `Withdraw` call is made with an empty `operator_xonly_pks` list) over the `withdraw`/`InternalWithdraw` gRPC surface, and/or is observable once a completing transaction is broadcast/relayed before confirmation. No verifier, watchtower, operator, or aggregator role compromise is needed — only unauthenticated ability to relay a completed Bitcoin transaction, which is exactly the kind of unprivileged-attacker path this class of finding targets.

### Recommendation
Do not treat the `OP_RETURN` payload as an authenticated attribution of "who paid." Either:
- Require the `OP_RETURN` (or an equivalent commitment identifying the paying operator) to be covered by a signature from that operator (e.g. sign it as part of the payout transaction construction so it cannot be altered without invalidating the tx), or
- Track payer attribution off the unauthenticated on-chain field entirely, e.g. by having the operator's own signed submission (through the aggregator/verifier signing protocol) be the source of truth for who is entitled to reimbursement, with the on-chain `OP_RETURN` used only as a secondary consistency check rather than the sole basis for the DB write in `update_payout_txs_and_payer_operator_xonly_pk`.

### Proof of Concept
1. Obtain the user's `WithdrawParams` (`input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`) — e.g., by receiving it as one of several operators the aggregator forwarded it to, or by observing a payout transaction broadcast/relayed before confirmation.
2. Construct a payout transaction reusing the signed input/output exactly as `create_payout_txhandler` would, but set the `OP_RETURN` output to an arbitrary target operator's x-only public key instead of your own.
3. Broadcast this transaction with sufficient CPFP fee to be the one confirmed for the withdrawal UTXO.
4. Once finalized, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) parses the `OP_RETURN` and records the *target* operator as `payout_payer_operator_xonly_pk` in the `withdrawals` table.
5. The target operator's own `PayoutCheckerTask` (`core/src/task/payout_checker.rs:39-79`) detects this "unhandled payout" for its own key and automatically initiates the kickoff/reimbursement flow for a withdrawal it never funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Checks if the operator who sent the kickoff matches the payout data saved in our db
    /// Payout data in db is updated during citrea sync.
    async fn is_kickoff_malicious(
        &self,
        kickoff_witness: Witness,
        deposit_data: &mut DepositData,
        kickoff_data: KickoffData,
        dbtx: DatabaseTransaction<'_>,
    ) -> Result<bool, BridgeError> {
        let move_txid =
            create_move_to_vault_txhandler(deposit_data, self.config.protocol_paramset())?
                .get_cached_tx()
                .compute_txid();

        let payout_info = self
            .db
            .get_payout_info_from_move_txid(Some(dbtx), move_txid)
            .await?;
        let Some((operator_xonly_pk_opt, payout_blockhash, _, _)) = payout_info else {
            tracing::warn!(
                "No payout info found in db for move txid {move_txid}, assuming malicious"
            );
            return Ok(true);
        };

        let Some(operator_xonly_pk) = operator_xonly_pk_opt else {
            tracing::warn!("No operator xonly pk found in payout tx OP_RETURN, assuming malicious");
            return Ok(true);
        };

        if operator_xonly_pk != kickoff_data.operator_xonly_pk {
            tracing::warn!("Operator xonly pk for the payout does not match with the kickoff_data");
            return Ok(true);
        }

        let wt_derive_path = WinternitzDerivationPath::Kickoff(
            kickoff_data.round_idx,
            kickoff_data.kickoff_idx,
            self.config.protocol_paramset(),
        );
        let commits = extract_winternitz_commits(
            kickoff_witness,
            &[wt_derive_path],
            self.config.protocol_paramset(),
        )?;
        let blockhash_data = commits.first();
        // only last 20 bytes of the blockhash is committed
        let truncated_blockhash = &payout_blockhash[12..];
        if let Some(committed_blockhash) = blockhash_data {
            if committed_blockhash != truncated_blockhash {
                tracing::warn!("Payout blockhash does not match committed hash: committed: {:?}, truncated payout blockhash: {:?}",
                        blockhash_data, truncated_blockhash);
                return Ok(true);
            }
        } else {
            return Err(eyre::eyre!("Couldn't retrieve committed data from witness").into());
        }
        Ok(false)
    }

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
