### Title
Nil-pointer dereference in legacy EVM precompile error handling crashes the node when `evm.StateDB` is not a `*DBImpl` - (File: `precompiles/common/legacy/v610/precompiles.go` and sibling legacy precompile packages)

### Summary
CVE-2017-9239 describes Exiv2 assigning a value pointer to `0x0` when a TIFF structure is malformed, then dereferencing that null pointer during `TiffImageEntry::doWriteImage`, causing a segfault. The analogous root cause in sei-chain is `state.GetDBImpl()`, which returns a `nil *DBImpl` whenever `evm.StateDB` is not a `*state.DBImpl` (or a `*state.HookedStateDB` wrapping one), followed by unconditional use of that nil pointer in the precompile error path.

### Finding Description
`state.GetDBImpl` is a type-assertion helper that returns `nil` for any `vm.StateDB` implementation it doesn't recognize: [1](#0-0) 

Every precompile's `Prepare` correctly guards against this nil case: [2](#0-1) 

However, the sibling error-handling path in the same legacy files calls `state.GetDBImpl(evm.StateDB).SetPrecompileError(err)` with **no nil check at all**: [3](#0-2) 

This exact unguarded pattern is repeated across many legacy precompile packages still present in the repo (used for historical chain-upgrade replay/deterministic execution of old block heights): [4](#0-3) [5](#0-4) [6](#0-5) 

The bug class match to CVE-2017-9239 is precise: when `Prepare` fails because `ctxer == nil` (i.e., `evm.StateDB` is not the expected `*DBImpl` structure — analogous to the malformed TIFF IFD), the returned error triggers the deferred handler, which calls `GetDBImpl` a second time (again returning `nil`) and then invokes `.SetPrecompileError(err)` on that nil pointer. Because `SetPrecompileError` on `*DBImpl` writes to a struct field (`precompileErr`) through the receiver, invoking it on a nil receiver dereferences a null pointer and panics — exactly like Exiv2 dereferencing a null `pValue_`.

This was recognized and fixed in later precompile versions, which now guard the same call site: [7](#0-6) [8](#0-7) 

The presence of the fixed pattern in v614+ confirms the maintainers treated the unguarded v552–v610 pattern as a defect, but the vulnerable legacy code remains in the tree (used for deterministic replay of historical upgrade heights and present in ~20 other legacy precompile files per the "wasmd", "bank", "distribution", "gov", "oracle", "pointer", "pointerview", "staking", "addr", and "json" packages).

### Impact Explanation
A `nil`-pointer method-call panic inside `Run`/`Prepare` on a validator or public RPC node performing an EVM `eth_call`, `eth_estimateGas`, transaction execution, or historical block replay causes an unrecovered Go runtime panic. Depending on where this executes (deliver-tx path vs. isolated goroutine), this can crash the node process, i.e., a crash of a default-configuration node/public RPC endpoint, which is one of the accepted impacts for this analog scan.

### Likelihood Explanation
Reaching this requires the code path where a precompile's `Prepare` observes `evm.StateDB` as something other than `*DBImpl`/`*HookedStateDB(*DBImpl)` — this occurs in specific EVM call contexts (e.g., simulation, tracing, or alternate StateDB wrappers used by RPC handlers) where these legacy versions are still exercised for older block heights. I was not able to fully confirm from the index alone which live call path can still route through a non-`DBImpl` `vm.StateDB` into these specific legacy precompile files (versus the fixed head-of-branch precompile implementation in `precompiles/common/precompiles.go`), since the legacy directories appear tied to historical/replay execution of past chain-upgrade heights. This limits confidence that the vulnerable code is reachable from a fresh, non-historical transaction on the current chain tip, though it remains reachable during full-history sync/replay by any RPC node bootstrapping from genesis.

### Recommendation
Apply the same nil-guard already used in v614+ (`if sdb := state.GetDBImpl(evm.StateDB); sdb != nil { sdb.SetPrecompileError(err) }`) uniformly to all remaining legacy precompile packages (v552, v555, v562, v575, v580, v600, v605, v606, v610, and the corresponding `bank`, `json`, `wasmd`, `pointer`, `pointerview`, `distribution`, `gov`, `oracle`, `staking`, `addr` legacy variants) so historical block replay cannot panic on a malformed/unexpected `StateDB` type.

### Proof of Concept
1. Construct or replay an EVM call into a precompile whose bound version resolves to one of the affected legacy packages (e.g., `precompiles/bank/legacy/v552`), at the corresponding historical chain-upgrade height.
2. Trigger a code path where `evm.StateDB` passed into `vm.EVM` is not a `*state.DBImpl` nor a `*state.HookedStateDB` wrapping one (e.g., a simulation/trace/alternate StateDB implementation feeding into the same precompile dispatch).
3. `Prepare` returns `errors.New("cannot get context from EVM")` because `ctxer == nil`.
4. The deferred error handler executes `state.GetDBImpl(evm.StateDB).SetPrecompileError(err)`; `GetDBImpl` returns `nil` again, and calling `.SetPrecompileError` on the nil `*DBImpl` panics with a nil-pointer dereference, crashing the node/RPC process handling that call.
