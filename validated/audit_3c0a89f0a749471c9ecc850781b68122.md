## Title
Malicious `.gitmodules` submodule URL combined with `protocol.file.allow=always` lets a hostile repository pull arbitrary local files into the working tree - (File: `app/src/lib/git/submodule.ts`)

## Summary
The Cally finding is really about **missing validation of an attacker-influenceable value that is later trusted implicitly**, causing the app to silently create/accept objects it should have rejected. The closest Desktop analog is `updateSubmodulesAfterOperation` in [1](#0-0) , which unconditionally appends `-c protocol.file.allow=always` to `git submodule update --init --recursive` whenever the caller passes `allowFileProtocol: true`, with **no validation of the submodule `url` value that a hostile repository controls via `.gitmodules`**.

## Finding Description
`updateSubmodulesAfterOperation` builds the submodule-update command as: [2](#0-1) 

When `allowFileProtocol` is `true`, Desktop explicitly re-enables the `file` transport for submodules (Git hardened this in 2.38 by defaulting `protocol.file.allow` to `user` specifically because unrestricted `file://`/local-path submodule URLs let a repository author make Git read arbitrary paths on the checkout machine). This flag is threaded from `checkoutBranch`/`checkoutCommit` [3](#0-2)  and is set to `true` from multiple call sites in `app-store.ts` and `dispatcher.ts` as part of ordinary branch-checkout flows (confirmed via grep matches in those files), not just in an explicitly user-confirmed "trust this directory" prompt (that confirmation only exists for locally-added bare/unsafe directories, see `buildRepositoryUnsafeError` in [4](#0-3) ).

Nothing in `listSubmodules` or `updateSubmodulesAfterOperation` validates or restricts the `submodule.<name>.url` value that comes from a cloned/fetched repository's `.gitmodules` file — the same way Cally never checked that `tokenIdOrAmount` was non-zero before trusting it. A repository author fully controls `.gitmodules`, and can set a submodule URL to an absolute or relative local filesystem path (e.g. `../../../../.ssh`, or a Windows `%APPDATA%`-relative path) instead of a real remote. Because Desktop re-enables `protocol.file.allow=always`, `git submodule update --init` will happily "clone" that local path's contents into the submodule directory inside the victim's working tree.

## Impact Explanation
Once the victim's checkout/branch-switch triggers `updateSubmodulesAfterOperation` with `allowFileProtocol: true`, sensitive local content (SSH keys, credential files, other unrelated repos, etc.) that the crafted `url` points at gets copied into the tracked working directory of a repository whose remote is attacker-controlled. If the user later stages/commits/pushes (or even auto-syncs), the exfiltrated material is sent to the attacker's remote — matching the "credential/token exfiltration" and "silent corruption of what the user commits or pushes" categories in the given Valid Impact rubric. This is functionally the same broken-invariant pattern as the Cally report: an attacker supplies a value (`tokenIdOrAmount = 0` there, a submodule `url` here) that the code accepts without checking whether it is a value that should never be trusted, and the unwanted object (worthless vault / exfiltrated local files) is created as a direct, automatic consequence.

## Likelihood Explanation
This requires no elevated privileges or local/physical access by the attacker — the attacker only needs to author a `.gitmodules` entry in a repository the victim clones, forks, or checks out a branch/PR from. I was not able to fully verify inside this session whether *all* the `app-store.ts`/`dispatcher.ts` call sites that pass `allowFileProtocol: true` are reachable purely from normal checkout of an untrusted remote branch/PR (vs. some being gated behind extra confirmation), so likelihood should be validated with a full trace of those 8 call sites before treating this as confirmed-exploitable in production Desktop flows. The mechanism itself (`protocol.file.allow=always` + no submodule URL validation) is present and unguarded in the code shown.

## Recommendation
- Validate/restrict submodule URLs sourced from an untrusted `.gitmodules` before allowing `protocol.file.allow=always`; at minimum, reject `file://`/local-path submodule URLs unless the containing repository itself is already explicitly trusted by the user (reusing the existing "unsafe repository" trust gate shown in `add-existing-repository.tsx`).
- Audit each of the 8 `app-store.ts` and 6 `dispatcher.ts` call sites that pass `allowFileProtocol: true` to confirm they are only reached for repositories the user has already vetted, not for arbitrary cloned/forked/PR-checkout flows.

## Proof of Concept
1. Attacker publishes a repository containing a branch with a `.gitmodules` file:
   ```
   [submodule "loot"]
       path = loot
       url = ../../../../.ssh
   ```
2. Victim uses GitHub Desktop to clone or open the repository and checks out that branch (`checkoutBranch`/`checkoutCommit` → `updateSubmodulesAfterOperation` with `allowFileProtocol: true`).
3. Desktop runs `git -c protocol.file.allow=always submodule update --init --recursive`, which copies the contents of `~/.ssh` (relative to the repo path) into `loot/` inside the tracked working directory.
4. If the victim commits/pushes (or the workflow auto-stages), the private key material is transmitted to the attacker's remote. [5](#0-4) [6](#0-5)

  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await updateSubmodulesAfterOperation(
    repository,

    branch.name,
    allowFileProtocol
  )
