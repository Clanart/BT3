There is no test covering the case where `git describe` fails (e.g., a submodule commit unreachable from any tag/branch ref), which is a very common, attacker-reachable scenario for a submodule pointing at an arbitrary/dangling/detached commit contributed via a malicious repo.

## Title
Silent dropping of submodule entries in `listSubmodules` when `git describe` fails, causing `discardChanges` to trash entire submodule directories instead of a safe git reset/checkout - (File: `app/src/lib/git/submodule.ts`)

### Summary
`listSubmodules` in <cite repo="Kirstentat/desktop--008" path="app/src/lib/git/submodule.ts" start="158,190,192" end="163,190,194" /> parses the output of `git submodule status --` with a regex that hard-requires a trailing parenthesized `git describe` suffix (`\((.+?)\)$`). However, `git describe` can legitimately fail for a submodule commit (e.g. a dangling commit with no reachable tag/branch — trivially producible by an attacker who controls the submodule's pinned commit/ref inside a cloned/fetched repository), in which case `git submodule status` emits the line **without** the parenthesized suffix at all. Such lines silently fail to match `statusRe`, so the submodule is dropped from the returned array with no error and no log.

### Finding Description
The regex used is:
```ts
const statusRe = /^.([^ ]+) (.+) \((.+?)\)$/gm
``` [1](#0-0) 

`git submodule status` only appends `(<describe output>)` when `git describe` succeeds for the submodule's checked-out commit. When the submodule points to a commit with no reachable annotated/lightweight tag or matching ref (a state fully controllable by whoever controls the submodule's content/commit graph in a cloned/fetched repository), the line is emitted as just `<status><sha> <path>` with no trailing parentheses. That line does not match `statusRe`, so `stdout.matchAll(statusRe)` yields nothing for that submodule and it is silently excluded from the returned `submodules` array — with no error, warning, or exit-code signal (the function only special-cases `exitCode === 128`, see [2](#0-1) ).

This function's result is consumed directly in `GitStore.discardChanges` to distinguish submodule paths from ordinary files: [3](#0-2) 

If a submodule is missing from the list, `foundSubmodule` is `false` for that path, and the discard logic falls into the "ordinary file" branch, which calls `this.shell.moveItemToTrash(...)` (or, in the permanent-discard path, `rm(...)`) directly on the submodule's working-tree path: [4](#0-3) 

This is categorically different and more destructive than the code path intended for submodules, which instead calls `resetSubmodulePaths` (a safe `git submodule update --recursive --force`) and excludes the path from `pathsToCheckout`/`pathsToReset` for the parent repo: [5](#0-4) [6](#0-5) 

Because the top-level "Changes" list UI derives submodule status independently, from `git status --porcelain` parsing in `status-parser.ts` (via `mapSubmoduleStatus`), the user still sees the row correctly labeled as a submodule change in the UI. But the separate, decoupled `listSubmodules()` call used specifically inside the discard code path can disagree with what's displayed, because it depends on a fragile regex over `git submodule status` text rather than the same structured status data. This produces exactly the invariant violation named in the question: the parsed state used to decide *how* to discard no longer "exactly reflects" what the UI showed, and a user-initiated discard on that row deletes the entire submodule working directory (moved to trash, or permanently removed via `rm` if the user previously opted out of trash-on-failure prompts) instead of performing the expected, reversible `git submodule update --force` reset.

### Impact Explanation
For a submodule the attacker can arrange (via a crafted/forked/fetched repository containing a submodule reference pointing at a commit unreachable by any tag/ref) to fall into this parsing gap, a user who clicks "Discard changes" on that submodule row in Desktop will have the entire local submodule directory removed from disk (via trash-move or, in the permanent-discard flow, `rm`) rather than having Desktop safely reset the submodule's checked-out commit via `git submodule update --force`. This is silent loss of local work with no confirmation reflecting the true scope of the operation, matching the "High" impact class described (silent loss of local work).

### Likelihood Explanation
Triggering `git describe` failure requires only that the submodule's pinned commit have no tag reachable from it and no matching ref describable by `git describe` — a very common, easily attacker-arranged condition (e.g., committing a submodule pointer to a fresh/dangling/detached commit with no tags). No special git configuration or privileges are needed by the victim; simply cloning/fetching such a repository and later discarding changes to that submodule triggers the bug.

### Recommendation
Do not rely on a brittle single regex requiring the parenthesized `describe` suffix. Either:
1. Use `git submodule status` output line-by-line and make the `(describe)` suffix optional in the regex (e.g. `^.([^ ]+) (.+?)(?: \((.+?)\))?$` per line, processed via a line-split rather than a global multiline regex on the whole buffer), or
2. Use `git submodule--helper list` / `.gitmodules` parsing combined with `git status --porcelain=2` submodule flags (the same data source already used by `status-parser.ts`) so the submodule set used in `discardChanges` is guaranteed consistent with what's rendered in the Changes list.
Additionally, `discardChanges` should treat "path exists in `.gitmodules`" (or otherwise be defensively verified as a submodule via `file.status.submoduleStatus !== undefined`, already available from the regular status parse) as the source of truth for whether to route through `resetSubmodulePaths` instead of trash/`rm`, rather than a second, independently-parsed call to `listSubmodules`.

### Proof of Concept
1. Create a repository with a submodule; inside the submodule, create a commit and ensure no tag/branch describes it (e.g., detach HEAD at a commit with no reachable tags, or delete tags after adding the submodule pointer at that commit) so that `git describe` fails for that submodule's checked-out commit.
2. Run `git submodule status --` manually in the parent repo: confirm the output line for that submodule lacks a trailing `(...)` segment, e.g.: `+1eaabe34fc6f486367a176207420378f587d3b4 foo/submodule` (no parentheses).
3. Call `listSubmodules(repository)` in a unit test (extending `app/test/unit/git/submodule-test.ts`) against this fixture and assert `result.length === 0` even though a submodule exists — demonstrating the dropped entry.
4. Through the UI/`GitStore.discardChanges`, mark the submodule row (shown correctly as a submodule change) for discard; observe that `resetSubmodulePaths` is never invoked for it and instead `shell.moveItemToTrash`/`rm` is called on `foo/submodule`, deleting the entire submodule working directory rather than performing a safe `git submodule update --force`.
