### Title
Unchecked `u64` summation of payment/input amounts lets crafted output amounts bypass the `NotEnoughFunds` check - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` sums attacker-influenced output amounts and input values into plain `u64` variables and compares them with unchecked `+` arithmetic. Overflow wraps the comparison, producing a transaction whose outputs exceed its inputs — analogous to the Pimcore bug where an unvalidated numeric value (a negative counter) breaks business logic.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), amounts come from `payments: &[(ScriptBuf, u64)]` — arbitrary values supplied by whoever requests the transaction (in the protocol these originate from untrusted instruction/withdrawal data). The only per-payment check is a lower bound (`*amount < DUST`, lines 165–169). The sums are computed with plain, wrapping-capable `u64` arithmetic:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();      // line 175
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();                    // line 187
let mut needed_fee = fee_per_vbyte * vbytes;                                              // line 206
if input_sat < (payment_sat + needed_fee) { Err(TransactionError::NotEnoughFunds ...) }     // line 215
```

Two overflows exist:
- `payment_sat` wraps if the payment amounts sum past `u64::MAX` (e.g., two payments of `u64::MAX / 2 + DUST`), making `payment_sat + needed_fee` a small number that passes the `NotEnoughFunds` check.
- `fee_per_vbyte * vbytes` and `payment_sat + needed_fee` can also wrap independently.

The resulting `SignableTransaction` then builds `TxOut`s with `Amount::from_sat(payment.1)` (line 190) whose total exceeds `input_sat`. `fee()` at lines 138–141 computes `sum(inputs) - sum(outputs)` with unchecked subtraction, which panics on underflow, and the serialized transaction is invalid on the Bitcoin network (outputs > inputs), so any inputs it references can never actually be spent through it while the scheduler believed it created them.

### Impact Explanation
A malformed payment request reaches consensus-validated signing of a structurally impossible transaction. Depending on the caller, this either burns inputs into an unspendable/invalid transaction, causes a panic on `fee()`/assertion paths (`assert!((new_outputs + total_fee) <= original_outputs)` in the amortization path), or desynchronizes accounting — "funds reported received/forwarded that are not spendable," matching the accepted-impact criterion. Debug builds panic on overflow; release builds silently wrap.

### Likelihood Explanation
Only reachable if an unprivileged party can control the `u64` payment amounts fed to `SignableTransaction::new`. In the processor flow amounts are constrained by on-chain balances, but the library API itself performs no upper-bound validation and is documented for general use signing externally supplied payment data — the same reachability class as the referenced advisory (untrusted numeric input in a business-logic path). Impact is a logic violation/DoS on the funded wallet, not key compromise, so Medium-to-Low within the accepted classes.

### Recommendation
Use `checked_add`/`saturating_add` when accumulating `payment_sat` and `input_sat`, use `checked_mul` for `fee_per_vbyte * vbytes`, and reject any payment amount or sum exceeding consensus-valid maximums (e.g., `Amount::MAX_MONEY` / 21M BTC) before building `TxOut`s. Make `fee()` use `checked_sub` returning an error instead of panicking.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
let payments = vec![
  (p2tr_script.clone(), u64::MAX / 2 + 1_000),   // each >= DUST, passes check at line 165
