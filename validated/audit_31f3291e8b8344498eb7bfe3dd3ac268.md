### Title
Reward Snapshot Manipulation via Permissionless Harvest - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
The report's bug class — inflating a state variable immediately before a fee/reward snapshot to unfairly capture value, then reversing the inflation — has a direct, unprivileged analog in the reward-distribution accounting used by `BaseRewardPoolV2`, `vlMGPBaseRewarder`, and `mWOMSVBaseRewarder`. Rewards are injected instantly into `rewardPerTokenStored` based on `totalStaked()` at the exact block of `queueNewRewards`/`_provisionReward`, and harvesting that triggers this injection is permissionless. An ordinary wallet can therefore deposit immediately before a harvest-triggered reward injection and withdraw immediately after, capturing a share of yield disproportionate to any real staking duration, at the expense of genuine long-term stakers.

### Finding Description
`_provisionReward` in `BaseRewardPoolV2.sol` updates the global reward accumulator using the staking pool's `totalStaked()` at the moment the function executes: [1](#0-0) 

This is an instantaneous "drop" model rather than a time-streamed model: the entire incoming reward amount is divided by whatever `totalStaked()` happens to be at that single block, and the resulting `rewardPerTokenStored` increment is retroactively earnable by every token balance present at that instant — with no minimum holding period.

Harvesting, which is the trigger for this reward injection via `WombatStaking.harvest` → `_sendRewards`/`queueNewRewards`, is exposed as a permissionless, unprivileged entry point: [2](#0-1) 

An ordinary wallet fully controls both sides of the window: it can call `deposit`/`depositFor` on `MasterMagpie` (via the pool helper's `_deposit`, which calls `IMasterMagpie(masterMagpie).depositFor`) to inflate its share of `totalStaked()` immediately before calling the public `harvest()`, and then call `withdraw` immediately afterward to exit: [3](#0-2) [4](#0-3) 

The identical instantaneous-snapshot pattern (`totalStaked()` used at the exact provisioning block with no time-based averaging) is repeated in the locked-token reward pools: [5](#0-4) [6](#0-5) 

This mirrors the reported bug class precisely: the fee/reward calculation trusts a single-block snapshot of a manipulable balance instead of an average or time-weighted measure over the accrual interval, letting an unprivileged actor extract value that should belong to depositors who were staked throughout the actual reward-accrual period.

### Impact Explanation
An attacker can deposit a large stake immediately before a permissionless `harvest()` call (which they themselves can trigger), instantly earning a proportional share of the newly injected reward via the `rewardPerTokenStored` jump, then withdraw right after. This directly siphons unclaimed yield away from legitimate long-term stakers who accrued the reward through actual time and risk exposure — a theft of unclaimed yield reachable purely through ordinary deposit/withdraw/harvest calls, without any privileged role.

### Likelihood Explanation
Likelihood is high: `harvest()` is public and callable by anyone, deposit/withdraw are ordinary unprivileged operations with no cooldown or minimum staking duration enforced in `_deposit`/`_withdraw`, and the attack requires only capital available atomically within the same transaction sequence (or back-to-back transactions), which any wallet can execute without needing insider knowledge of keeper timing (unlike the original report, timing is even more deterministic here because harvest itself is user-triggerable).

### Recommendation
Replace the instantaneous full-amount reward injection with a time-streamed reward-rate model (e.g., Synthetix-style `rewardRate` over a fixed duration) so that newly queued rewards accrue gradually to `totalStaked()` over time rather than being fully creditable to whichever balance is present at the exact injection block. Alternatively, introduce a minimum staking duration or a snapshot/checkpoint delay before new deposits become eligible for freshly queued rewards in `BaseRewardPoolV2._provisionReward`, `vlMGPBaseRewarder.queueNewRewards`, and `mWOMSVBaseRewarder._provisionReward`.

### Proof of Concept
1. Attacker observes that `WombatPoolHelperV2.harvest()` is publicly callable and will eventually trigger `WombatStaking._sendRewards` → `IBaseRewardPool.queueNewRewards`.
2. Attacker calls `MasterMagpie.deposit`/`depositFor` (via the pool helper) with a large amount of `stakingToken`, inflating `totalStaked()` for the target rewarder just before harvesting.
3. Attacker calls the permissionless `harvest()` [2](#0-1) , causing `_provisionReward` to run with the inflated `totalStaked()`, crediting `rewardPerTokenStored` [7](#0-6) .
4. Because the attacker's balance is already included in `totalStaked()` at this instant, their `_earned` computation captures a proportional share of the newly queued reward despite having staked for effectively zero real time.
5. Attacker calls `withdraw` on the pool helper to exit, retaining the unfairly captured reward share while genuine long-term stakers receive a diluted portion.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
