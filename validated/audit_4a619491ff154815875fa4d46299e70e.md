### Title
BIP-340 `verify` omits the even-Y lift of the group key: signatures are produced against the odd-Y internal key and are invalid on-chain - (File: networks/bitcoin/src/crypto.rs)

### Summary
The analog of the treasure-swap missing K-value check is a missing output-validity check in signature finalization. `Schnorr::verify` (networks/bitcoin/src/crypto.rs) accepts the internally-computed `(R, s)` equation against the raw `group_key` point and only normalizes the parity of `R` (negating `s` when `R` is odd). It never normalizes/checks the parity of the group key `A`. BIP-340 defines verification against `lift_x(A)`, i.e. the even-Y point with the same x-coordinate. When the threshold group's `group_key()` is odd-Y (~50% of keys), the emitted 64-byte signature passes the internal check yet fails every real BIP-340 verifier, so the signed Taproot spend is invalid.

### Finding Description
`Algorithm::verify` delegates to `FrostSchnorr::verify(group_key, nonces, sum)`, which checks `s·G == R + c·group_key` for the `group_key` point **as given**. `Hram::hram` computes `c = H(x(R) || x(A) || m)` — already in the x-only domain — and negates `c` iff `R` is odd (crypto.rs:59-73). `verify` then negates `s` iff `R` is odd and drops `R`'s sign byte (crypto.rs:145-149).

What is missing is the parity normalization of `A`. BIP-340 verification is `s·G == R + c·lift_x(P)` where `lift_x` forces even Y. If `group_key` is odd, the internal equation uses `A` while every on-chain verifier uses `-A`, and `s` is off by `2c·A`-equivalent — the signature is invalid. There is no parity check, no negation of the effective key, and no re-verification under `lift_x` before the signature is committed to the witness in `TransactionSignatureMachine::complete` (send.rs:417-424). `Hram` even documents "If either `R` or `A` is the point at infinity, this will panic" but says nothing about odd `A` (crypto.rs:50-55). This mirrors the swap bug exactly: a state transition is finalized and value is released on the basis of an internal computation whose defining invariant (BIP-340 validity, the analog of the K check) is never verified.

### Impact Explanation
`TransactionMachine` signs every input of `SignableTransaction` (send.rs:373-397), and `complete` writes the produced signatures into the witnesses without any post-check. If the multisig's group key (or an `offset`ed key, `keys.clone().offset(self.offsets[i])` at send.rs:276-281, which can flip parity) is odd-Y, the transaction is signed "successfully" but rejected by Bitcoin consensus. The result is an incorrect verifier formula producing signatures for an unintended key (the odd-Y `A` instead of the on-chain `lift_x(A)`), and funds whose outputs map to a key the network will never accept a spend from — analogous to receiving "all the WETH" against a pool state that was never invariant-checked.

### Likelihood Explanation
Reachability is by construction, not adversary control: an unprivileged depositor causes funds to be sent to `p2tr_script_buf(offset.group_key())` (send.rs:277); whether that x-only committed key corresponds to an even-Y internal point is a coin flip per offset/key. Any odd-Y case yields a universally-invalid signature on `Prevouts::All` commitments. Severity is bounded (locked/unspendable outputs rather than theft), consistent with Medium.

### Recommendation
In `Schnorr::verify`/`sign_share`, normalize the group key to even Y (negate the effective secret/key when `needs_negation(A)`), or assert `needs_negation(&group_key)` is false and have callers offset keys to even parity before constructing the `AlgorithmMachine`. Alternatively, re-verify the emitted `[u8; 64]` under strict BIP-340 (`s·G == R' + c·lift_x(A)` with `R'` even) before returning it.

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }

    fn verify(
      &self,
      group_key: ProjectivePoint,

      sum: Scalar,
    ) -> Option<Self::Signature> {
      self.0.verify(group_key, nonces, sum).map(|mut sig| {

        // Convert to a Bitcoin signature by dropping the byte for the point's sign bit
        sig.serialize()[1 ..].try_into().unwrap()
      })
    }

      let offset = keys.clone().offset(self.offsets[i]);
