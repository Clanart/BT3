Based on this evidence, the `matchGitHubRepository` function derives owner/name purely by parsing the current git remote URL's hostname/owner/name path segments (`app/src/lib/repository-matching.ts:29-46`) — it never re-validates that the resolved API repository is actually the same repository the user originally cloned. This confirms the attack path is real: whoever controls `owner/name` on that GitHub host at query time controls what `apiRepo.clone_url` comes back as, and that gets silently written into the user's `origin` remote via `updateRemoteUrl`.

### Title
Silent, unconfirmed rewrite of a repository's git remote URL from untrusted GitHub API data enables repo-hijack redirection of pushes/fetches - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
GitHub Desktop periodically refreshes each tracked repository's associated GitHub metadata by looking up `owner/name` via the GitHub API and, if it decides the remote URL is "stale," rewrites the local git `origin` remote to the API-reported `clone_url` with **no user confirmation, diff, or warning**. This is structurally the same defect described in ADM-1: a security-relevant value (here, the destination of the user's pushes/fetches, analogous to the "admin" trust anchor) is changed in a single unchecked step based on data supplied by an external, potentially attacker-influenced source, instead of requiring an explicit user-confirmed "push/pull" style transition.

### Finding Description
The refresh flow works as follows:

1. `repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts:4874-4914` resolves `owner`/`name` for the tracked repo via `matchGitHubRepository`, then calls `api.fetchRepository(owner, name)` to get a fresh `apiRepo` object from the GitHub API. [1](#0-0) 

2. `matchGitHubRepository` (`app/src/lib/repository-matching.ts:29-46`) derives `owner`/`name` purely by textually parsing the *current* remote URL — it does not pin to any stable repository ID. If the owner/name pair now resolves to a different underlying repository (e.g. because the original repo was deleted/renamed and the `owner/name` slot was reclaimed, or an Enterprise Server admin/compromised host serves different data for that path), the API will happily return a different `clone_url`. [2](#0-1) 

3. `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:7-45`) then compares the new `apiRepo.clone_url` against the stored `gitHubRepository.cloneURL` and the current remote. If the protocol matches and the current remote still equals the previously-known clone URL, it calls `gitStore.setRemoteURL(...)` **automatically**, with no prompt. [3](#0-2) 

4. `GitStore.setRemoteURL` (`app/src/lib/stores/git-store.ts:1533-1543`) executes `git remote set-url` immediately. [4](#0-3) 

This refresh path is not a rare, user-initiated action — it runs on ordinary background operations: repository selection (`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`), account-change refresh, and adding a repository (`_addRepositories`). [5](#0-4) [6](#0-5) 

The only guard rails are: protocol match, and "remote hasn't been manually changed by the user since the last known API clone URL." Neither of these validates repository *identity* — they only compare URL strings. There is no confirmation dialog analogous to a two-step admin transfer; the change is applied unilaterally the moment new API data disagrees with the last known clone URL.

### Impact Explanation
If an attacker can cause the GitHub API (or a compromised/MITM'd GitHub Enterprise Server) to return an attacker-controlled `clone_url` for the `owner/name` pair a user's repository is associated with, Desktop will silently repoint that user's `origin` remote to the attacker's repository. Subsequent `git push` operations performed through Desktop's UI would then push the user's commits (and, depending on workflow, could expose branch history/credentials-in-history) to the attacker-controlled remote, and subsequent fetches/pulls would merge attacker-supplied history into the user's working repository — a silent corruption of both what the user pushes and what they later build on. This matches the "silent corruption of what the user commits or pushes" and "attacker controls a GitHub API object" categories in the given impact criteria.

### Likelihood Explanation
The refresh path executes automatically and frequently (on repository selection, background fetch/refresh, and account changes) without any special user action beyond normal use of the app. The realistic trigger is repo-name/owner reuse ("repo-jacking"): GitHub allows previously-used owner/name slots to be reclaimed after deletion or a user/org rename, and Enterprise Server deployments add an additional server-compromise/MITM vector where the "GitHub API object" itself is attacker-controlled. No local access, elevated privileges, or unusual user steps are required — only that the app continues periodic background refreshes against a repository whose identity has moved out from under the user.

### Recommendation
Apply the same "two-step" principle recommended in ADM-1: never silently overwrite a security-relevant destination (the git remote) based on a single unauthenticated signal. Concretely:
- Pin repository identity to a stable identifier (e.g. GitHub's numeric repository `id`) rather than the mutable `owner/name` pair, and refuse to auto-update the remote if the API-returned repository `id` differs from the previously stored one.
- When `updateRemoteUrl` detects a real repository-identity change (not just a clone URL protocol/casing difference), surface an explicit confirmation dialog to the user before calling `setRemoteURL`, rather than applying it automatically.

### Proof of Concept
1. User clones `https://github.com/owner/repo` and Desktop stores `gitHubRepository.cloneURL` for that owner/name.
2. The `owner/repo` slot is later reclaimed (owner account renamed/deleted and re-registered, or org repo renamed and slot reused) so that GitHub's API now returns a different repository's `clone_url` for the same `owner/name` path — or, on a compromised/MITM'd GHE instance, the API response for that path is simply forged.
3. On the next background refresh (e.g. user reselects the repository, or the periodic indicator/background fetcher runs), `repositoryWithRefreshedGitHubRepository` fetches the new `apiRepo`, and `updateRemoteUrl` finds `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, and silently calls `gitStore.setRemoteURL(origin, <attacker clone_url>)`.
4. The next time the user pushes via Desktop's UI, their commits go to the attacker's repository instead of the original one, with no warning shown at any point. [7](#0-6)

```typescript
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
```

```typescript
import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
