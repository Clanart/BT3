### Title
Silent git remote hijack via stale-cache trust check in `updateRemoteUrl` - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
GitHub Desktop periodically refreshes the GitHub-side metadata for a repository and, as part of that refresh, will silently rewrite the local `origin` remote URL if it believes the GitHub API's `clone_url` has legitimately changed. The "has it legitimately changed" check relies entirely on comparing the current local remote against a **stale, locally cached** value (`gitHubRepository.cloneURL`) instead of any strong, immutable identifier (e.g., the repository's numeric GitHub ID). This mirrors the reported smart-contract bug class exactly: a decision is made using an out-of-date cached value instead of re-validating against a trustworthy source, allowing an attacker-controlled API object to walk through the guard undetected.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` runs automatically in the background (e.g. on account refresh) and looks up the repository purely by owner login + repo name: [1](#0-0) 

It calls `api.fetchRepository(owner, name)` — not a lookup by the repository's immutable numeric ID — and if a repository object comes back, it hands the fresh `apiRepo` straight to `updateRemoteUrl`: [2](#0-1) 

`updateRemoteUrl` then decides whether to silently run `git remote set-url` based on this logic: [3](#0-2) 

The critical guard is `remoteUrlUnchanged`, which is computed by comparing the **current local remote** to `gitHubRepository.cloneURL` — the value cached in Desktop's local repositories database from the *previous* API fetch, not a freshly re-verified trust anchor: [4](#0-3) 

Because the owner/name pair is not immutable on GitHub (repos can be renamed, deleted, and the freed name/owner slug re-registered — the well-known "repojacking" pattern), an attacker who controls the object returned for `repos/{owner}/{name}` can present a `clone_url` for an entirely different, attacker-owned repository while still satisfying every guard:
- `protocolsMatch` — trivially satisfied by choosing the same URL scheme.
- `remoteUrlUnchanged` — satisfied because it only checks against the old cached `cloneURL`, which still matches the user's untouched local remote.
- `!urlsMatch` — satisfied because the new `clone_url` differs from the current remote.

With all three true, Desktop executes `gitStore.setRemoteURL(...)` and silently rewrites the user's `origin` to the attacker-controlled URL: [5](#0-4) [6](#0-5) 

The existing test suite confirms this is treated as an intentional "keep in sync with renames" feature and only guards against the user having *manually* customized the remote — it never re-validates the API-supplied `clone_url` against anything the user can trust (e.g., the stable numeric repo ID): [7](#0-6) 

### Impact Explanation
This is a silent corruption of what the user pushes and fetches, one of the explicitly valid impacts. Once the remote is redirected, the next `git push` will send commits/history to an attacker-controlled repository (exfiltrating potentially private source code), and the next `git fetch`/`git pull` will silently merge attacker-supplied commits into the user's working tree, with no dialog, warning, or diff review presented to the user. Because the update path is invoked from a background refresh rather than a user-initiated action, the user is not in a position to notice or approve the change before it happens.

### Likelihood Explanation
Likelihood is moderate-to-high in any scenario where a previously-fetched repository's owner/name pair becomes available for someone else to claim (repo deletion/rename, org/user rename, transferred ownership) — a routine and well-documented GitHub occurrence, not a hypothetical GitHub bug. The victim only needs to have previously added such a repository in Desktop (as a remote, fork parent, or clone) and have the app running in the background (account/repo refresh is periodic and automatic), with no other user interaction required.

### Recommendation
Do not trust owner/name lookups or previously cached `clone_url` values as the anchor of trust when deciding to auto-update a remote. Instead:
- Track and compare the GitHub repository's immutable numeric `id` (already available on `IAPIRepository`) between the previously stored `GitHubRepository` and the freshly fetched `apiRepo`, and refuse to auto-update the remote if the IDs differ (this signals owner/name reuse by a different repository entirely).
- Require explicit user confirmation before silently changing `origin`'s URL, at least when the underlying repository ID has changed, rather than performing the `git remote set-url` unattended.

### Proof of Concept
1. Victim clones/adds `github.com/attacker/foo` in GitHub Desktop; Desktop stores `GitHubRepository.cloneURL = https://github.com/attacker/foo.git`, matching the local `origin` remote.
2. Attacker renames `attacker/foo` to `attacker/foo-old`, freeing the `foo` name slot under the same (or another) account they control, then creates a brand-new, unrelated repository at `attacker/foo` (e.g., `https://malicious.example/attacker/foo.git` style content, but hosted at the same slug) — a routine "repojacking" move requiring no privileged access to GitHub or the victim's machine.
3. On its next periodic refresh, Desktop calls `repositoryWithRefreshedGitHubRepository`, which does `api.fetchRepository('attacker', 'foo')`, receiving the *new* repository's API object (same owner/name, different underlying repo, different `clone_url` internals but same displayed slug format).
4. `updateRemoteUrl` computes `remoteUrlUnchanged = true` (local remote still equals old cached `cloneURL`), `protocolsMatch = true`, `urlsMatch = false`, and calls `gitStore.setRemoteURL('origin', <attacker clone_url>)` with no prompt.
5. Victim's next `git push`/`git fetch` interacts with the attacker's repository instead of the original one.

Note: I was not able to fully trace `matchGitHubRepository`'s exact matching keys within the tool-call budget available (only confirmed the owner/name-based `fetchRepository` call in `app-store.ts`); a Devin session with full repository access should verify whether any additional ID-based matching already exists elsewhere in that function before implementing the fix.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

  public async setRemoteURL(name: string, url: string): Promise<boolean> {
    const wasSuccessful =
      (await this.performFailableOperation(() =>
        setRemoteURL(this.repository, name, url)
      )) === true
    await this.loadRemotes()

    this.emitUpdate()
    return wasSuccessful
  }

    const { gitHubRepository, gitStore } = await createRepository(
      t,
      apiRepository
    )
    assert(gitStore.currentRemote !== null)

    const originalUrl = gitStore.currentRemote.url
    const updatedUrl = 'https://github.com/my-user/my-updated-repo'
    const updatedApiRepository = { ...apiRepository, clone_url: updatedUrl }

  })
