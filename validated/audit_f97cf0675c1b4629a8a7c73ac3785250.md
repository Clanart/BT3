### Title
Reentrant `share`/`complete` reuses deterministic FROST nonces across distinct messages, leaking the validator's MuSig secret share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug class in the external report is an *incomplete fix for a reentrancy/state-reuse vulnerability*: protection was nominally added but a re-entrant path still reuses sensitive state. In Serai, `SigningProtocol::preprocess_internal` deterministically re-derives the same FROST nonces from a DB-cached seed on every call for a given `context`, and `share`/`complete` re-invoke `machine.sign` without verifying that the message and preprocess set are identical to what the nonce was committed to. The file's own header acknowledges this check is missing ("we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)").

### Finding Description
`preprocess_internal` stores an encrypted `CachedPreprocess` seed keyed by `context = (b"DkgConfirmer", attempt)` and reloads it on every invocation; it is never deleted or rotated: [1](#0-0) 

`share_internal` calls `preprocess_internal` again and then signs the caller-supplied `msg` and `preprocesses` with those same nonces: [2](#0-1) 

The signed message is `set_keys_message(set, removed, key_pair)`, where `key_pair` is supplied per-call from the processor channel — it is not fixed by BFT-ordered data: [3](#0-2) 

`generated_key_pair` unconditionally overwrites `DkgKeyPair` and calls `share` every time a `GeneratedKeyPair` processor message arrives, with no deduplication guard: [4](#0-3) 

`complete` re-enters `share_internal` a second time, again signing with the cached nonces: [5](#0-4) 

The safety argument in the file header only covers *received* messages being BFT-ordered; it explicitly does not bind the locally-supplied `key_pair`/message to the decided nonces, and flags this as a TODO (incomplete fix): [6](#0-5) 

In FROST, a signature share is `s = d + rho·e·lambda + c·share_secret`. If `share` is invoked twice under the same `context` with different `(key_pair)` — hence a different challenge `c` — or with a different preprocess set (different binding factor `rho`), the same `d`/`e` nonces are used and `(s1 − s2)` linearly reveals the validator's MuSig secret share. `CachedPreprocess` reuse is documented in the codebase as enabling exactly this recovery: [7](#0-6) 

### Impact Explanation
The two confirmation shares are published as `DkgConfirmed` tributary transactions (`confirmation_share` field), i.e., public data. Any observer who obtains two shares computed under the same nonces but different challenges solves a 2x2 linear system and recovers the validator's Ristretto secret share — the root-of-trust key used for the MuSig validator set. That compromises validator identity/signing ability, a full key-share-recovery impact.

### Likelihood Explanation
Trigger requires `share`/`complete` to run twice for the same `(b"DkgConfirmer", attempt)` context with divergent inputs. The divergent input path is `key_pair`: `generated_key_pair` accepts whatever `KeyPair` the processor reports and rewrites `DkgKeyPair` each call, and `complete` reads `DkgKeyPair` at whatever value is current when DkgConfirmed accumulation completes. A duplicated/replayed or regenerated `GeneratedKeyPair` with a different pair (e.g., processor-side retry/rebuild producing a second report for the same attempt) causes a second `set_keys_message` to be signed under identical nonces. There is no guard preventing this; the code relies on an assumed invariant it admits is unchecked. Likelihood is conditional on that channel inconsistency, which keeps this below trivially-exploitable, but the cryptographic consequence is deterministic once reached.

### Recommendation
Bind the decided nonces to the exact `(preprocesses, msg)` they sign:
- Before signing in `share_internal`, store a hash of the serialized preprocess set and `msg` alongside `CachedPreprocesses`; on re-entry, `assert` equality and refuse to sign divergent inputs (implementing the existing TODO at lines 50–54).
- In `generated_key_pair`, reject (or ignore) a second `KeyPair` differing from the stored `DkgKeyPair` for the same attempt instead of overwriting.
- Delete/`zeroize` the cached preprocess after the first successful `share` so re-execution cannot reproduce the nonces.

### Proof of Concept
Conceptual (requires coordinator-level re-invocation, so described rather than executed):
1. Attempt `a` of the DKG confirmation runs; `dkg_confirmation_nonces` publishes commitments `D, E` derived deterministically from the seed stored under `CachedPreprocesses[(b"DkgConfirmer", a)]`.
2. `generated_key_pair` is invoked with `key_pair_A`; `share` computes `s1 = d + rho·e·λ + c(msg_A)·x` where `msg_A = set_keys_message(.., key_pair_A)` and `x` is the validator's MuSig secret share. `s1` is published in a `DkgConfirmed` transaction.
3. A second `GeneratedKeyPair` carrying `key_pair_B ≠ key_pair_A` arrives (processor re-report/retry). `generated_key_pair` overwrites `DkgKeyPair` and calls `share` again; `preprocess_internal` reloads the identical seed → identical `d, e`; `share` computes `s2 = d + rho·e·λ + c(msg_B)·x` and publishes it.
4. Observer computes `x = (s1 − s2) / (c(msg_A) − c(msg_B))` mod curve order (same participant set ⇒ same `rho·e·λ` term cancels), recovering the validator's secret share.

Uncertainty: I could not fully trace every caller that can emit `GeneratedKeyPair` for the same `attempt` (processor reboot/retry semantics), so reachability of the divergent `key_pair` trigger rests on the missing dedup/binding guard rather than a confirmed producer of two distinct pairs; the cryptographic consequence, however, follows directly from the deterministic seed reuse in `seeded_preprocess`/`from_cache`.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
