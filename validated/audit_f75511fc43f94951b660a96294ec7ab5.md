### Title
Reward-per-token snapshot can be front-run via instant deposit/withdraw to steal unclaimed yield - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPoolV2` (and its sibling reward pools `mWOMSVBaseRewarder.sol` / `vlMGPBaseRewarder.sol`) recompute `rewardPerTokenStored` instantaneously and proportionally to whatever `totalStaked()` is at the moment new rewards are provisioned. Because staking/unstaking through `MasterMagpie` is instant and uncooled, and because `donateRewards` is a fully permissionless external function, any ordinary wallet can time a deposit immediately before a reward injection and withdraw immediately after claiming, capturing a disproportionate share of yield that should have accrued to long-term stakers. This mirrors the reported UsdPlus `rebaseAdd/rebaseMul/rebaseSub` front-running issue, where a state variable that instantly re-prices all holders' balances (`_balancePerShare` there, `rewardPerTokenStored` here) can be sandwiched by an unprivileged actor to extract value that belongs to existing participants.

### Finding Description
`_provisionReward` updates the global `rewardPerTokenStored` in a single step using the pool's current `totalStaked()`: [1](#0-0) 

`balanceOf` for reward accounting is read live from `MasterMagpie`'s `stakingInfo`, with no vesting, cooldown, or minimum holding period: [2](#0-1) 

Reward provisioning can be triggered in two ways reachable by, or observable to, an ordinary wallet:
- `queueNewRewards`, restricted to `onlyManager` — but its pending mempool transaction can be front-run by any watcher.
- `donateRewards`, which is **fully permissionless** and callable by any address for any already-registered reward token: [3](#0-2) 

Because `_earned` computes a user's reward purely from the delta between the current `rewardPerToken` and the value stored at their last checkpoint, multiplied by their live `balanceOf`, a wallet that deposits stake in the same block/transaction sequence just before a large reward injection — then immediately calls `getReward`/`getRewards` and withdraws — earns a full pro-rata share of that reward despite having contributed zero economic time-at-risk: [4](#0-3) [5](#0-4) 

This is functionally identical to the reported bug class: a single privileged or permissionless action instantly re-prices a shared accounting variable (`_balancePerShare` in UsdPlus, `rewardPerTokenStored` here), and because deposits/claims/withdrawals are not time-locked or delayed, an unprivileged wallet can sandwich that state transition to capture value that would otherwise accrue to genuine long-term stakers.

### Impact Explanation
Each time this is exploited, the front-runner's share of the freshly injected reward is paid out of the same finite reward pot, permanently reducing the amount left for legitimate stakers who held their position through the actual reward-accrual period — this is a direct theft of unclaimed yield belonging to other users. Because `donateRewards` is public and reward top-ups happen routinely (protocol emissions, bribes, `donateRewards` calls), this can be repeated continuously against every pool built on `BaseRewardPoolV2`/`mWOMSVBaseRewarder`/`vlMGPBaseRewarder`.

### Likelihood Explanation
Likelihood is high in practice: no capital lock-up, no delay, and no fee gates the deposit-claim-withdraw sequence; a bot can watch the mempool for `queueNewRewards`/`donateRewards` calls (or self-trigger via `donateRewards`) and execute the whole front-run/back-run atomically or across adjacent blocks with only gas cost as risk.

### Recommendation
Do not let a single large reward injection be captured within the same block/transaction a stake was created. Options: (1) time-weight reward accrual (e.g., checkpoint balances with a minimum staking duration before they qualify for a given reward epoch), (2) require `donateRewards`/`queueNewRewards` amounts to stream in over time instead of being applied to `rewardPerTokenStored` in one atomic step, or (3) add a short deposit-to-claim/withdraw cooldown in `MasterMagpie` so stake cannot be added and removed within the same block/transaction window as a reward injection.

### Proof of Concept
1. Attacker monitors mempool for a `queueNewRewards(amount, rewardToken)` call from a manager, or calls `donateRewards(amount, rewardToken)` themselves after a large deposit.
2. In the preceding transaction/block, attacker calls `MasterMagpie.depositFor` (or equivalent stake entrypoint) with a large stake amount, becoming a large fraction of `totalStaked()`.
3. The reward-provisioning transaction executes `_provisionReward`, updating `rewardPerTokenStored` for the entire pool based on the now-inflated `totalStaked()` that includes the attacker's fresh stake: [6](#0-5) 
4. Attacker immediately calls `getReward`/`getRewards` to claim their pro-rata share via `_sendReward`: [7](#0-6) 
5. Attacker withdraws their stake from `MasterMagpie`, having held the position for a negligible amount of time, while legitimate long-term stakers now receive a smaller share of the same reward pot.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
