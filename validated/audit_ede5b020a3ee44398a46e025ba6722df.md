### Title
Nil `*big.Int` dereference in `IBCReceivePacketCallback` when the ERC20 token pair contract has no code after callback execution - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
`erc20types.Keeper.BalanceOf` returns `nil` (rather than an error) whenever the underlying EVM call fails or returns un-unpackable data [1](#0-0) . `IBCReceivePacketCallback` calls this function and immediately invokes `.Cmp()` on the result without a nil check, in the same code path that the ICS-20 destination-callback feature exposes to any unprivileged IBC sender/relayer [2](#0-1) .

### Finding Description
The SuperDCA bug pattern is "code assumes an ERC20-like token always behaves like a well-formed ERC20 contract, and blows up when that assumption is violated." The Cosmos EVM analog here is the ICS-20 destination callback path in `x/ibc/callbacks/keeper/keeper.go`.

After executing an attacker-controlled contract call via `CallEVMWithData` (the "dest_callback" calldata supplied by the packet sender) and writing the cached context back with `writeFn()` [3](#0-2) , the code performs a post-condition check to make sure the isolated receiver no longer holds the transferred ERC20 tokens:

```go
receiverTokenBalance := k.erc20Keeper.BalanceOf(ctx, erc20.ABI, tokenPair.GetERC20Contract(), receiverHex)
if receiverTokenBalance.Cmp(big.NewInt(0)) != 0 {
    ...
}
``` [4](#0-3) 

`BalanceOf` calls `CallEVM(... , "balanceOf", account)` and returns `nil` if `CallEVM` errors out, or if `abi.Unpack` fails/produces an empty result set:
```go
func (k Keeper) BalanceOf(ctx sdk.Context, abi abi.ABI, contract, account common.Address) *big.Int {
	res, err := k.evmKeeper.CallEVM(ctx, abi, types.ModuleAddress, contract, false, nil, "balanceOf", account)
	if err != nil {
		return nil
	}
	unpacked, err := abi.Unpack("balanceOf", res.Ret)
	if err != nil || len(unpacked) == 0 {
		return nil
	}
	...
}
``` [1](#0-0) 

`abi.Unpack` will fail this way if the target address has no contract code at the time of the call and thus returns empty return data (the same fundamental class of bug as calling `balanceOf` on `address(0)`/a non-ERC20 address in the SuperDCA report — code that is not a functioning ERC20 no longer behaves like one). This is directly reachable if the ERC20 contract behind the `tokenPair` (a "native ERC20" token pair, registered permissionlessly per `RegisterERC20`) self-destructs during the just-executed callback call, or otherwise reverts/returns malformed data for `balanceOf`. Since the callback contract address and calldata are both attacker-supplied via the packet memo, and `RegisterERC20`/native-ERC20 token-pair registration is permissionless (see governance/permissionless test cases in `tests/integration/x/erc20/test_proposals.go`), an attacker can register their own malicious ERC20 contract as a token pair, initiate an ICS-20 transfer of that token with a destination callback pointing at a contract they control, and have that contract self-destruct the ERC20 token contract during the callback call.

When `BalanceOf` subsequently returns `nil`, `receiverTokenBalance.Cmp(big.NewInt(0))` is invoked on a nil `*big.Int` receiver, which panics (nil pointer dereference) inside `(*big.Int).Cmp`.

### Impact Explanation
This code executes inside `OnRecvPacket` packet processing (via the ibc-go callbacks middleware `ContractKeeper.IBCReceivePacketCallback`), which runs deterministically on every validator during ordinary block/packet processing. A panic here is not scoped to a single malicious actor's transaction sandbox with graceful recovery guaranteed elsewhere in this repository — no `recover()` wrapping was found around this code path (`x/ibc/callbacks/keeper/keeper.go`, verified via repo-wide `recover()` search). If the ibc-go callbacks/transfer middleware or the ABCI message handler does not recover from this panic, all validators processing the same IBC packet would panic identically and deterministically, causing a chain halt / consensus liveness failure triggerable by an ordinary, unprivileged IBC packet relay. Even if some higher-level recovery mechanism exists, at minimum this represents a reliable, unauthenticated remote DoS against block processing for the destination-callback ICS-20 feature, and the underlying broken invariant ("BalanceOf silently returns nil to represent a range of failure conditions, and callers assume non-nil") threatens the Critical chain-halt impact category.

### Likelihood Explanation
Reachability requires: (1) permissionless registration of a native ERC20 token pair with attacker-supplied bytecode (indicated as permissionless-by-default in test cases), (2) initiating a standard ICS-20 transfer with a `dest_callback` memo pointing to an attacker-deployed contract, and (3) that contract executing `selfdestruct` on the paired ERC20 token contract during the callback execution. All of these steps are available to any unprivileged user through ordinary transaction and IBC packet flows — no validator/relayer privilege is required. The likelihood is limited only by whether `selfdestruct` is available/effective in the target EVM version and whether any framework-level panic recovery exists above this call stack, which could not be fully confirmed from the indexed code (no `recover()` was found in the `x/ibc/callbacks` package or its immediate ibc-go integration).

### Recommendation
Check `receiverTokenBalance` for `nil` before calling `.Cmp()`, and treat a `nil` result as an explicit balance-check failure (return an error) rather than assuming success or panicking. More broadly, `x/erc20/keeper/evm.go`'s `BalanceOf` should distinguish "confirmed zero balance" from "could not determine balance" (e.g., by returning `(*big.Int, error)`), and all callers — including `x/ibc/callbacks/keeper/keeper.go` and `x/erc20/keeper/msg_server.go` — should be audited for the same unchecked-nil-dereference pattern.

### Proof of Concept
Not executed against a live node (index-only investigation); the reasoning above is based on static analysis of the reachable code paths:
1. Register a malicious ERC20 contract (with a `selfdestruct`-capable admin/owner function) as a native ERC20 token pair via `MsgRegisterERC20` (permissionless registration path).
2. Send an ICS-20 transfer of that token to this chain with `memo.dest_callback.address` pointing to an attacker-deployed callback contract, and `calldata` that invokes a function on the ERC20 token contract to self-destruct it (contract must be pre-approved appropriately, since `approve` happens before the callback in the same function).
3. During `OnRecvPacket`, `IBCReceivePacketCallback` executes the callback (`CallEVMWithData`), which self-destructs the ERC20 token contract.
4. The subsequent `k.erc20Keeper.BalanceOf(...)` call returns `nil` because the target contract now has no code (`abi.Unpack` fails on empty return data).
5. `receiverTokenBalance.Cmp(big.NewInt(0))` panics with a nil pointer dereference at [5](#0-4) .

// BalanceOf queries an account's balance for a given ERC20 contract
func (k Keeper) BalanceOf(
	ctx sdk.Context,
	abi abi.ABI,
	contract, account common.Address,
) *big.Int {
	res, err := k.evmKeeper.CallEVM(ctx, abi, types.ModuleAddress, contract, false, nil, "balanceOf", account)
	if err != nil {
		return nil
	}

	unpacked, err := abi.Unpack("balanceOf", res.Ret)
	if err != nil || len(unpacked) == 0 {
		return nil
	}

	balance, ok := unpacked[0].(*big.Int)
	if !ok {
		return nil
	}

	return balance
}
