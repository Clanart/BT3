### Title
`verify-package` on-chain code verification never compares actual module bytecode, only self-reported metadata - ([File: aptos-move/cli/src/stored_package.rs])

### Summary
The Aptos CLI's package-verification helper, `CachedPackageMetadata::verify`, is meant to let a user confirm that the bytecode currently published on-chain matches a package they build locally from source. In practice it only diffs the fields of `PackageMetadata` (name, deps, module metadata, manifest, upgrade policy, extension, source digest) between the on-chain registry entry and the locally rebuilt metadata; it never fetches and compares the actual on-chain module bytecode. Since every field being compared (including `source_digest`) is attacker-controlled data submitted by the publisher inside the same `PackageMetadata` object at publish time, a malicious publisher can make the on-chain metadata *look* consistent with a legitimate source tree while the actual published module bytecode is arbitrary/malicious.

### Finding Description
`code::publish_package_txn` / `object_code_deployment::publish` take a serialized `PackageMetadata` and a `code: vector<vector<u8>>` bundle from the caller, with no on-chain guarantee that the `PackageMetadata.source_digest`, `modules[].source`, or `manifest` fields actually correspond to the bytecode in `code`. [1](#0-0) [2](#0-1) 

The only on-chain checks performed against the bundle are module-address-matches-sender, compatibility (for upgrades), duplicate-module checks, and the metadata/attribute validations in `validate_publish_request` (unregistered module/dependency names, resource-group/event attribute shapes). None of these actually recompute or verify that `source_digest` or `ModuleMetadata.source` corresponds to the compiled bytecode being stored. [3](#0-2) [4](#0-3) 

The CLI's `aptos move verify-package` command is the tool users/auditors are expected to rely on to confirm "the on-chain copy matches" a locally built package. [5](#0-4) 

However, `CachedPackageMetadata::verify` only compares `PackageMetadata` struct fields (`name`, `deps`, `modules`, `manifest`, `upgrade_policy`, `extension`, `source_digest`) between the fetched on-chain registry entry (`self_metadata`) and the freshly-built local `package_metadata`. It never calls `CachedPackageRegistry::get_bytecode` to fetch the actual deployed module bytes nor diffs them against the locally compiled bytecode. [6](#0-5) 

The bytecode-fetching capability exists in the same struct (`CachedPackageRegistry::create` with `with_bytecode=true`, `get_bytecode`), but it is used elsewhere (e.g., saving bytecode to disk) rather than in `verify`. [7](#0-6) [8](#0-7) 

Because `source_digest`, module `source`, and `manifest` are all publisher-supplied and unverified against the actual bytecode at publish time (they are just embedded metadata written to `PackageRegistry`), a malicious deployer can:
1. Publish arbitrary/malicious bytecode as `code`.
2. Embed `PackageMetadata` whose `source_digest`/`modules[].source`/`manifest` correspond to a benign, legitimate-looking source tree.
3. Anyone running `aptos move verify-package` against that address, using the legitimate source, will have their locally-rebuilt `PackageMetadata` match the on-chain metadata field-for-field, and `verify()` returns `Ok(())`, falsely certifying that the deployed bytecode matches the shown source.

### Impact Explanation
This breaks the "mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" invariant on the trust boundary that end users/auditors rely on before interacting with a contract (approving spend, depositing funds, granting capabilities, etc.). A contract can be presented as "verified" (source available, hash matches, `verify-package` succeeds) while actually running different, malicious logic, enabling supply-chain-style rug pulls on any protocol whose users trust CLI/API-based source verification. This is a code-safety/trust invariant break on a publish-path tool with direct mainnet relevance (verification of already-published packages), though it does not itself corrupt on-chain state — the false assurance is what enables downstream loss.

### Likelihood Explanation
High likelihood of being reachable: any account can publish a package with completely attacker-chosen `PackageMetadata` fields, since none of them are cross-checked against the compiled bytecode on-chain (only structural/attribute validation is performed). No privileged access or race condition is required — a single publish transaction is sufficient, and the mismatch persists indefinitely until someone bytecode-diffs manually.

### Recommendation
Extend `CachedPackageMetadata::verify` (or callers of it, e.g. `VerifyPackage` command) to fetch each module's actual on-chain bytecode via `get_bytecode`/`get_account_module`, recompile the local source into bytecode using the same compiler/build options, and byte-compare the two, in addition to the existing metadata-field comparisons. Alternatively/also, compute `source_digest` on-chain from the actual `code` bundle rather than trusting the publisher-supplied value, so the digest itself becomes a binding commitment to what was actually stored.

### Proof of Concept
Conceptual PoC (client-side, requires no special on-chain privilege):
1. Build a legitimate-looking Move package `good_pkg` and compute its `PackageMetadata` (source_digest, modules[].source, manifest) via `BuiltPackage::extract_metadata`. [9](#0-8) 
2. Separately compile a malicious package `evil_pkg` with the same module names/signatures (satisfying compatibility) but hostile logic.
3. Publish `evil_pkg`'s bytecode (`code`) together with `good_pkg`'s `PackageMetadata` (source_digest/manifest/module source fields) via `code::publish_package_txn`/`object_code_deployment::publish`; the VM never checks that `code` corresponds to the embedded metadata beyond module-name/attribute checks. [10](#0-9) 
4. A third party runs `aptos move verify-package` against the deployed address using `good_pkg`'s source: `CachedPackageRegistry::create` fetches the on-chain `PackageMetadata` (which is `good_pkg`'s metadata, per step 3), and `CachedPackageMetadata::verify` compares it field-by-field to the locally rebuilt `good_pkg` metadata — all fields match, so `verify()` returns success, even though the actually-executing bytecode is `evil_pkg`. [6](#0-5) 

Note: I could not fully trace every CLI call site of `verify()` (e.g., the exact `VerifyPackage` command wiring in `aptos-move/cli/src/commands.rs`) within the available tool budget; if a bytecode comparison exists elsewhere in that command path that I did not locate, this finding would need to be revised. Based on all located code, no such bytecode comparison exists.

    pub fn verify(&self, package_metadata: &PackageMetadata) -> anyhow::Result<()> {
        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(
                "Dependencies don't match {:?} : {:?}",
                package_metadata.deps,
                self_metadata.deps
            )
        } else if self_metadata.modules != package_metadata.modules {
            bail!(
                "Modules don't match {:?} : {:?}",
                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )
        } else if self_metadata.upgrade_policy != package_metadata.upgrade_policy {
            bail!(
                "Upgrade policy doesn't match {:?} : {:?}",
                package_metadata.upgrade_policy,
                self_metadata.upgrade_policy
            )
        } else if self_metadata.extension != package_metadata.extension {
            bail!(
                "Extensions doesn't match {:?} : {:?}",
                package_metadata.extension,
                self_metadata.extension
            )
        } else if self_metadata.source_digest != package_metadata.source_digest {
            bail!(
                "Source digests doesn't match {:?} : {:?}",
                package_metadata.source_digest,
                self_metadata.source_digest
            )
        }

        Ok(())
    }
