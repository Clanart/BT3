### Title
`translate_signers` invokes `Pubkey::create_program_address` for up to `MAX_SIGNERS` entries without ever charging `create_program_address_units`, underpricing CPI signer-seed verification - ([File: program-runtime/src/cpi.rs])

### Summary
`translate_signers` in `program-runtime/src/cpi.rs` calls `Pubkey::create_program_address` once per `signer_seeds` entry (up to `MAX_SIGNERS = 16`, each with up to `MAX_SEEDS` seeds of up to `MAX_SEED_LEN` bytes) but never calls `invoke_context.compute_meter.consume_checked` for the SHA256-based address-derivation work it performs. This differs from the standalone `SyscallCreateProgramAddress`/`SyscallTryFindProgramAddress` syscalls, which explicitly charge `create_program_address_units` (1500 CU) per call.

### Finding Description
`cpi_common` in `program-runtime/src/cpi.rs` charges a single flat `invoke_units` cost (`DEFAULT_INVOCATION_COST = 946`) at the top of the function: [1](#0-0) 

It then calls `translate_signers`, passing `signers_seeds_addr`/`signers_seeds_len` supplied directly by the attacker's sBPF program: [2](#0-1) 

Inside `translate_signers`, the code bounds the number of signer entries to `MAX_SIGNERS` and the seeds per entry to `MAX_SEEDS`, but for every signer entry it calls `Pubkey::create_program_address(&seeds_bytes, program_id)` with **no compute-meter charge at all** for this hashing operation: [3](#0-2) 

Contrast this with the direct syscalls that perform the identical `Pubkey::create_program_address` operation and correctly charge `create_program_address_units` per invocation (and even per bump-seed retry inside `try_find_program_address`): [4](#0-3) [5](#0-4) 

`Pubkey::create_program_address` performs SHA256 hashing over the concatenation of all seed bytes plus a `"ProgramDerivedAddress"` marker and the target program ID — cost that scales with total seed bytes (up to `MAX_SEEDS * MAX_SEED_LEN` per signer). Because `translate_signers` performs this operation up to `MAX_SIGNERS` (16) times per single CPI call while the CPI's own flat `invoke_units` charge is independent of signer count/seed size, an attacker-controlled program can force the runtime to perform up to 16x the SHA256 hashing work of a single `create_program_address_units`-priced syscall call for the price of one flat, size-independent `invoke_units` charge. The existing compute-meter guards (`consume_checked` calls elsewhere in `cpi_common`/`translate_account_infos` for account bytes and instruction data) do not cover this specific hashing path, so no existing check stops it.

### Impact Explanation
This is a compute-cost underpricing bug: unpriced (or underpriced) CPU-bound work (SHA256 hashing of attacker-controlled seed data, up to `MAX_SIGNERS × MAX_SEEDS × MAX_SEED_LEN` bytes) is performed per invocation of `invoke_signed`-style CPI syscalls without a corresponding compute-unit charge scaled to that work. Repeated across many CPI calls within a single instruction/transaction (bounded by `max_instruction_trace_length` and `compute_unit_limit`), this lets a transaction consume disproportionately more validator CPU time processing PDA derivations than its charged compute units would suggest, falling under Agave's "materially underpriced compute" bounty category rather than memory-safety or privilege-escalation categories.

### Likelihood Explanation
Fully reachable by an unprivileged attacker: any sBPF program can invoke a CPI (e.g., via `invoke_signed`) with a `signer_seeds` array of `MAX_SIGNERS` entries, each with `MAX_SEEDS` seeds of `MAX_SEED_LEN` bytes, entirely under attacker control from instruction data. No special privileges, validator control, or multi-client cooperation are needed, and the path is deterministic and reproducible in a single call.

### Recommendation
In `translate_signers` (`program-runtime/src/cpi.rs`), add a `invoke_context.compute_meter.consume_checked(...)` call for each signer entry prior to or immediately after calling `Pubkey::create_program_address`, mirroring the `create_program_address_units` charge used by `SyscallCreateProgramAddress`/`SyscallTryFindProgramAddress` in `syscalls/src/lib.rs`. The charge should be applied per signer entry (not just once for the whole CPI), consistent with how the direct syscall prices identical work.

### Proof of Concept
Add a unit test in `program-runtime/src/cpi.rs` alongside the existing `test_translate_signers` test:
```rust
#[test]
fn test_translate_signers_unpriced_compute() {
    // Set up invoke_context as in test_translate_signers, but with MAX_SIGNERS
    // distinct signer_seeds entries, each with MAX_SEEDS seeds of MAX_SEED_LEN bytes.
    // Record invoke_context.compute_meter.remaining() before and after calling
    // translate_signers(program_id, vm_addr, MAX_SIGNERS as u64, &invoke_context).
    let before = invoke_context.compute_meter.remaining();
    let signers = translate_signers(&program_id, vm_addr, MAX_SIGNERS as u64, &invoke_context).unwrap();
    let after = invoke_context.compute_meter.remaining();
    let consumed = before - after;

    // Expected assertion demonstrating underpricing: `consumed` should be at least
    // MAX_SIGNERS * create_program_address_units (16 * 1500 = 24000) if properly
    // priced, matching the cost the equivalent number of direct
    // SyscallCreateProgramAddress calls would incur. The bug is confirmed if
    // `consumed` is effectively 0 (no charge at all) instead.
    assert!(
        consumed >= MAX_SIGNERS as u64 * invoke_context.get_execution_cost().create_program_address_units,
        "translate_signers consumed only {} CU for {} signer PDA derivations, expected >= {}",
        consumed, MAX_SIGNERS,
        MAX_SIGNERS as u64 * invoke_context.get_execution_cost().create_program_address_units
    );
}
```
This test currently fails (asserts non-zero/underpriced charge), demonstrating that `translate_signers` performs unpriced SHA256 hashing work proportional to `MAX_SIGNERS × MAX_SEEDS × MAX_SEED_LEN`.
