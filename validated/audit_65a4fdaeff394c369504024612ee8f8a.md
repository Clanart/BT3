### Title
Hunk expansion shifts diff-line array positions without remapping stored line-selection indices, silently flipping which lines get committed - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
The reported smart-contract bug is fundamentally a "broken invariant between a discretely-recorded index/allocation and the true, shifted total" — rounding causes individual `votingPower` values to no longer sum to the total, so a state that should be reachable (unanimous) silently becomes unreachable. The Desktop analog is structurally the same broken-invariant class applied to line-selection bookkeeping: `DiffSelection` records *which lines are selected/deselected* using integer indices computed as `hunk.unifiedDiffStart + arrayIndex` [1](#0-0) . When a user expands a hunk to view more context, `expandTextDiffHunk` inserts new `DiffLine`s **before** the hunk's existing lines (for "expand up") without renumbering the previously-recorded selection state, so old indices now silently point at different lines than the user intended when they made their selection.

### Finding Description
`DiffSelection` is a purely index-based data structure: it stores a `Set<number>` of "diverging" line indices relative to a default (all-selected or all-deselected) state [2](#0-1) . These indices are the *positional* index of a line within the hunk's `lines` array, offset by `hunk.unifiedDiffStart` [1](#0-0) , `app/src/ui/diff/side-by-side-diff.tsx` (`findInteractiveOriginalDiffRange`/`onClickHunk`).

When a hunk is expanded (a normal, unprivileged user action available any time the file's on-disk content is available for diffing), `expandTextDiffHunk` builds `updatedHunkLines` by *prepending* newly-fetched context lines ahead of the hunk's original lines when expanding upward:
```
const updatedHunkLines = isExpandingUp
  ? [newDiffHunkLine, ...newLineDiffs, ...allHunkLinesButFirst]
  : [newDiffHunkLine, ...allHunkLinesButFirst, ...newLineDiffs]
``` [3](#0-2) 

The hunk keeps its original `unifiedDiffStart` [4](#0-3) , so every original line inside that hunk that comes after the header effectively shifts its array position by `numberOfNewDiffLines`. `formatPatch`/`formatPatchToDiscardChanges` (used to build the actual patch that is `git apply`'d to the index/working tree) recompute `absoluteIndex` purely from `hunk.unifiedDiffStart + lineIndex` at patch-generation time [1](#0-0) , so after expansion the *same numeric index* that used to identify one Add/Delete line now identifies a different line (either one of the newly inserted context lines, or another original line that shifted into that slot).

Only hunks *after* the expanded one have their `unifiedDiffStart`/`unifiedDiffEnd` explicitly shifted by `numberOfNewDiffLines` to compensate [5](#0-4) ; the currently-expanded hunk's own line indices are never remapped in the `DiffSelection` object that the UI keeps around in `WorkingDirectoryFileChange.selection`. No code path calls `withSelectableLines`/`withRangeSelection` to renumber the diverging-lines set after an expansion — `expandHunk` in `side-by-side-diff.tsx` only calls `this.setState({ diff: updatedDiff })`, leaving the selection state untouched.

The only guard that exists, `app-store.ts`'s recomputation of `selectableLines` from a *freshly reloaded* diff, only *filters* `divergingLines` to remove entries that are no longer selectable — it does not shift/remap the surviving indices to the lines they were meant to refer to [6](#0-5) , and it only runs on diff reload (e.g. after external file changes), not on hunk expansion, so it does not close the gap.

### Impact Explanation
This is exactly the "silent corruption of what the user commits" impact category. A user who explicitly *deselects* a sensitive addition or deletion line (to keep it out of the commit), and then clicks "Expand Up"/"Expand Whole File" to review more context around it, can end up committing that line anyway (its deselection index now points at a shifted/incorrect slot) — or conversely, a line the user wanted included can silently drop out of the patch. Because the file content that determines hunk boundaries and expansion offsets is the tracked repository content itself (attacker-controlled if the repo/file was cloned or fetched from an untrusted remote), a malicious repository can be crafted so ordinary partial-staging workflows (view diff → deselect line → expand context → commit) reliably desynchronize the selection state and produce a commit whose content differs from what the user reviewed and approved.

### Likelihood Explanation
Hunk expansion ("Expand Up"/"Expand Down"/"Expand Whole File") is a standard, frequently-used, unprivileged UI feature exposed directly in the diff viewer [7](#0-6) . Any repository whose files have hunks close enough together to trigger merges, or where a user wants extra context on a partially-staged change, exercises this exact code path. No admin rights, local access, or social engineering is required — simply opening and reviewing a crafted or ordinary diff and using a built-in feature is sufficient to trigger the divergence.

### Recommendation
When expanding a hunk (or merging adjacent hunks), remap the existing `DiffSelection` diverging-line indices to account for the inserted/shifted line positions before applying the new diff to state — e.g., shift all indices `>= hunk.unifiedDiffStart + insertionPoint` by `numberOfNewDiffLines`, and recompute/replace `selectableLines` accordingly, rather than leaving the `WorkingDirectoryFileChange.selection` untouched after `expandTextDiffHunk`/`expandWholeTextDiff`/hunk-merging. Add regression tests asserting that toggling a line, expanding a hunk, and then generating a patch (`formatPatch`) still reflects the user's original selection for that specific logical line.

### Proof of Concept
1. Open a repository with a modified file containing at least two hunks close enough to be candidates for merging on expansion (or simply expandable), e.g. via `git diff` producing multiple `@@` hunks.
2. In GitHub Desktop's diff view, deselect one specific `+`/`-` line inside a hunk (recorded internally as `divergingLines = { hunk.unifiedDiffStart + N }`).
3. Click "Expand Up" (or "Expand Whole File") on that hunk, which calls `expandTextDiffHunk` — new context lines are spliced in *before* the existing lines of that hunk [3](#0-2) , while `hunk.unifiedDiffStart` is unchanged and the selection object is not updated.
4. Commit only the selected changes. `formatPatch` recomputes `absoluteIndex` from the new (shifted) hunk-lines array and consults the stale `divergingLines` set [8](#0-7) ; the index that used to mark the deselected line now maps to a different array slot, so the previously-deselected line is included in (or a different, previously-included line is excluded from) the resulting patch applied via `git apply`.

Note: I was unable to fully trace whether every UI entry point resets/reconciles the selection immediately after every kind of expansion (e.g., "Expand Whole File" vs. single-hunk expand vs. hunk merges) due to index/context-window limits on this pass; a Devin session with full repo access should verify all call sites of `expandTextDiffHunk`/`expandWholeTextDiff`/`getTextDiffWithBottomDummyHunk` and confirm none of them call any `DiffSelection` remapping function before finalizing this as fully verified across the whole UI.

  private onExpandHunk = (
    hunkIndex: number,
    expansionType: DiffHunkExpansionType

    const { diff } = this.state

    if (hunkIndex === -1 || hunkIndex >= diff.hunks.length) {
      return
    }

    this.setState({ lastExpandedHunk: { hunkIndex, expansionType } })

    const kind = expansionType === DiffHunkExpansionType.Down ? 'down' : 'up'

    this.expandHunk(diff.hunks[hunkIndex], kind)
