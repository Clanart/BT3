### Title
Panic on out-of-range `sender`/`recipient` participant indexes in PedPoP blame evaluation causes denial of service - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The CVE-2017-14406 bug class (untrusted input reaches a dereference that crashes the process) maps onto Serai's PedPoP DKG blame handling: `BlameMachine::blame` / `AdditionalBlameMachine::blame` take attacker-supplied `sender`/`recipient` `Participant` values plus an attacker-supplied `EncryptedMessage`/`EncryptionKeyProof`, and index `HashMap`s with them via `self.enc_keys[&decryptor]` and `self.commitments[&sender]` without range validation, panicking on any nonzero index outside `1..=n`.

### Finding Description
`Participant` is only guaranteed nonzero (`Participant::new`, crypto/dkg/src/lib.rs:29-35); nothing constrains it to `<= n`. `AdditionalBlameMachine::new` registers encryption keys only for participants `1..=n` (crypto/dkg/pedpop/src/lib.rs:656-660), and in the normal `KeyMachine` flow `Decryption::enc_keys` is populated solely from verified round-1 registrations (crypto/dkg/pedpop/src/lib.rs:313-315). `blame()` passes the caller-controlled `sender` and `recipient` straight into `blame_internal` → `Decryption::decrypt_with_proof` (crypto/dkg/pedpop/src/lib.rs:575-632, 674-682). Inside `decrypt_with_proof`, once the attacker-supplied PoP verifies (which the attacker can satisfy trivially by encrypting with a key they generated — `SchnorrSignature::sign` in `encrypt`, crypto/dkg/pedpop/src/encryption.rs:161-165), the code evaluates `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388). A `recipient` such as `Participant(0xffff)` is absent from the map and `HashMap`'s `Index` impl panics. Independently, if a valid `recipient` is used but `sender` is out of range, `self.commitments[&sender]` panics in `blame_internal` (crypto/dkg/pedpop/src/lib.rs:599). `Decryption::register` also asserts on re-registration (crypto/dkg/pedpop/src/encryption.rs:356-359), though that path is guarded by `validate_map`/`MissingParticipant` in `verify_r1` (crypto/dkg/pedpop/src/lib.rs:305-314), whereas the blame path has no equivalent check on the accusation's indexes.

### Impact Explanation
Any party able to submit a blame accusation — which is precisely the untrusted, message-driven input this API exists to evaluate — can crash the evaluating node with a single malformed accusation naming a nonexistent `sender` or `recipient`. Like the reference NULL-deref, this is a remotely triggerable availability loss (panic → process abort under `panic=abort` or unwinding kill of the task), aborting DKG completion and any dependent signing.

### Likelihood Explanation
Blame accusations arrive as public protocol messages (`sender`, `recipient`, `msg`, `proof`). The triggering conditions require no secret: the sender just needs a `Participant` value > `n` and a self-consistent `EncryptedMessage` whose PoP verifies, both of which the attacker fully controls. The `DecryptionError` paths only handle cryptographic failures, not missing map entries, so the panic is reached deterministically.

### Recommendation
In `blame_internal` (and/or `decrypt_with_proof`), validate that `sender` and `recipient` are registered participants before indexing: use `enc_keys.get(&decryptor)`/`commitments.get(&sender)` and return the accusing party (or a dedicated error) on `None` instead of panicking. Reject accusations referencing indexes outside `params.all_participant_indexes()`.

### Proof of Concept
