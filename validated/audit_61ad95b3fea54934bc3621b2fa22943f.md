### Title
Git-argument injection via unsanitized branch name from `x-github-client://` deep link - ([File: app/src/lib/git/checkout.ts])

### Summary
The financial report's broken invariant is: a numeric input (`price_fair`) is trusted to always be positive, so a downstream security check (`margin > minMargin`) silently passes even when it shouldn't. The Desktop analog is structurally identical: a string input (a Git ref/branch name arriving from an attacker-controlled `x-github-client://openRepo/...&branch=...` deep link) is trusted to never begin with `-`, so the argument-separator protection meant to stop option injection is built in a way that never actually protects that value, letting a crafted value be silently reinterpreted as a Git command-line flag instead of a ref name.

### Finding Description
`app/src/lib/git/checkout.ts` builds the `git checkout` argument list like this: [1](#0-0) 

```
async function getBranchCheckoutArgs(branch: Branch) {
  return [
    branch.name,
    ...(branch.type === BranchType.Remote ? ['-b', branch.nameWithoutRemote] : []),
    '--',
  ]
}
```

The resulting command is `git checkout <branch.name> [-b <nameWithoutRemote>] --`. The `--` end-of-options marker is appended **after** the branch name instead of before it, so it provides no protection for `branch.name`/`nameWithoutRemote` — if either value begins with `-`, Git will parse it as an option rather than as a ref, exactly the way the tracer bug let a sign-unchecked `notional_value` slip past `margin > minMargin`.

`branch.name` can originate from an untrusted source: the app-URL handler builds an `IOpenRepositoryFromURLAction` whose `branch` field comes straight from the deep link query string, as declared in [2](#0-1) 
and consumed in `Dispatcher.openBranchNameFromUrl`, which clones/opens the repo and then checks out the attacker-supplied branch name with no further sanitization visible in the dispatcher code: [3](#0-2) 

The only validation applied anywhere in the ref pipeline is the regex in `sanitize-ref-name.ts`: [4](#0-3) 

That regex blocks control characters, space, `~^:?*[\|"<>`, `@{`, `..`, leading/trailing `.`, and `.lock` suffixes — it does **not** reject a leading `-`. So `testForInvalidChars('--orphan=pwned')` returns `false` (i.e., "no invalid chars"), meaning this guard behaves exactly like `margin > minMargin` in the report: it "always passes" for the class of malicious input that actually matters, because the invariant it enforces (Git-safe ref name) doesn't account for leading-dash option-injection payloads.

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openRepo/...&branch=--<option>` link (or an equivalent CLI/protocol invocation) controls `branch.name` end-to-end into a `git checkout` invocation where it lands as the first positional token, unguarded by `--`. This falls squarely into the valid impact category "a link or deep link the user clicks... result[ing] in]... silent corruption of what the user commits or pushes," since Git checkout options such as `-B<name>`/`--orphan=<name>` can force-reset or fabricate branches/refs the user did not intend, silently altering repository state at the moment Desktop tries to "helpfully" open the linked branch.

### Likelihood Explanation
Protocol/deep-link handling in Desktop is a well-known, low-friction attack surface (a single click launches the app with attacker data), and the code path from `parse-app-url.ts` → `Dispatcher.openBranchNameFromUrl` → `checkoutBranch` → `getBranchCheckoutArgs` is a direct, unauthenticated flow with no additional confirmation dialog shown before the checkout in the code reviewed. The only gate is the ref-name regex, which does not consider a leading dash invalid.

### Recommendation
Fix `getBranchCheckoutArgs` (and the analogous `checkoutCommit` argument builder, which appends `commit.sha` with no `--` guard at all) to place `--` immediately **before** the ref/sha argument, e.g. `['checkout', ...(remote ? ['-b', nameWithoutRemote] : []), branch.name, '--']`, and additionally extend `sanitize-ref-name.ts`'s invalid-character set (or add a dedicated check) to reject/neutralize ref names beginning with `-`, mirroring how the tracer report recommended fixing `minMargin()`/notional-value math to explicitly account for the previously-unchecked negative case.

### Proof of Concept
1. Attacker hosts a link: `x-github-client://openRepo/https://github.com/attacker/repo?branch=--orphan%3Dpwned-branch`.
2. Victim (with GitHub Desktop installed and the protocol handler registered) clicks the link.
3. `parse-app-url.ts` parses the action into `{ name: 'open-repository-from-url', url, branch: '--orphan=pwned-branch', pr: null, filepath: null }` — `testForInvalidChars` does not flag the leading `-`.
4. `Dispatcher.openRepositoryFromUrl` → `openBranchNameFromUrl(url, '--orphan=pwned-branch')` clones/opens the repo and calls checkout with this branch name.
5. `getBranchCheckoutArgs` produces `['checkout', '--orphan=pwned-branch', '--']`, which Git interprets as `git checkout --orphan=pwned-branch --`, silently creating/switching to an orphan branch instead of checking out the (nonexistent) ref the user thought they were opening — demonstrating option injection via the unguarded argument ordering.

(Note: I could not locate the exact body of `checkoutLocalBranch` referenced by the dispatcher — only its call sites — so the precise point where `Branch` objects are constructed from the raw `branchName` string could not be fully verified from the indexed code; a Devin session with full repo access would be needed to confirm that no additional sanitization occurs between `openBranchNameFromUrl` and `checkoutBranch`.)

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
