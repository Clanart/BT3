# Title
Unbounded, unpartitioned epoch-boundary stake-reward calculation allows unprivileged stakers to stall block production - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
Solana's partitioned epoch-rewards system was explicitly designed to bound per-block work during reward *distribution*, but the reward *calculation* phase that runs once at every epoch boundary iterates over **all** stake delegations in a single, unpartitioned pass on the block-production critical path. Any unprivileged user can create very cheap stake accounts (rent-exempt reserve plus a delegation as low as 1 lamport, or 1 SOL once `upgrade_bpf_stake_program_to_v5` is active) and delegate them, growing the delegation set without bound. This mirrors the `SurplusGuildMinter`/`ProfitManager.claimRewards()` pattern in the source report: a governance-permissioned but economically unbounded set ("gauges"/"terms") is iterated in full inside a single call with no per-call cap, causing gas/compute blow-up. In Agave, the analogous unbounded set is "stake delegations," and the analogous single unbounded loop is `calculate_stake_rewards_and_commissions`/`calculate_reward_points_partitioned`.

### Finding Description
At every epoch boundary, `Bank::process_new_epoch` calls `compute_new_epoch_caches_and_rewards`, which calls `calculate_rewards` → `calculate_rewards_for_partitioning` → `calculate_validator_rewards`: [1](#0-0) 

`calculate_validator_rewards` runs `calculate_reward_points_partitioned` and then `calculate_stake_rewards_and_commissions`, both of which use `stake_delegations.par_iter()` to process **every** stake delegation in the network in one call: [2](#0-1) [3](#0-2) 

This loop comment explicitly acknowledges an unbounded scale ("For N stake delegations, where N is >1,000,000") and relies purely on rayon parallelism, not an upper bound on N: [4](#0-3) 

By contrast, the *distribution* phase that follows is intentionally chunked across multiple blocks specifically to avoid unbounded per-block work, using `get_reward_distribution_num_blocks` and `partitioned_rewards_stake_account_stores_per_block`: [5](#0-4) 

The calculation phase has no equivalent cap: it computes the entire `PartitionedStakeRewards` array for all delegations synchronously inside `begin_partitioned_rewards`, which runs during `process_new_epoch` for the first slot of every new epoch — i.e., inside normal block execution/validation, not an offline/administrative path.

The corrupted value/broken invariant: the implicit assumption that "the number of stake delegations processed per epoch-boundary block is bounded" is false. The only enforced limit on growing this set is the stake-program's minimum delegation, `get_minimum_delegation`, which is **1 lamport** unless the `upgrade_bpf_stake_program_to_v5` feature is active (in which case it becomes 1 SOL): [6](#0-5) 

Rent-exemption cost per stake account is small and fixed (based on `StakeStateV2::size_of()`), so an unprivileged staker can cheaply mint an arbitrarily large number of delegated stake accounts, unboundedly growing the O(N) work performed by `calculate_stake_rewards_and_commissions`/`calculate_reward_points_partitioned` at every subsequent epoch boundary — exactly analogous to unbounded gauge/term growth driving `ProfitManager.claimRewards()`'s unbounded loop in the source report.

### Impact Explanation
Because this computation occurs inside the bank-creation path for the epoch-boundary slot on every validator (both the leader producing the block and every validator replaying/voting on it), an attacker-inflated delegation count can push per-epoch-boundary computation time far beyond the normal slot budget. Every validator performs the identical (deterministic) computation, so this is not merely a single node's RPC degradation — it is a network-wide slowdown at every epoch boundary that can repeatedly delay or skip the epoch-boundary slot across the cluster, degrading block production availability. This falls into the "non-RPC remote exhaustion/crash" / "consensus halt" impact category defined by scope, since it is triggered by ordinary user stake/delegate transactions, not by a malicious validator, peer, or trusted-plugin assumption.

### Likelihood Explanation
Likelihood is bounded by economics, similar to the original finding's own severity discussion (attacker must pay rent for many accounts). With minimum delegation potentially as low as 1 lamport (pre-`upgrade_bpf_stake_program_to_v5`) or 1 SOL (post-activation), the practical cost to create N delegations is dominated by N × rent-exempt-reserve(`StakeStateV2`), a fixed, modest per-account SOL cost. This is directly analogous to the original C4 finding's accepted medium-severity reasoning: the required scale is uncertain but not proven impossible, the existing safeguard (partitioning) protects only the distribution phase, and the calculation phase has no corresponding limit or fee scaling with delegation count.

### Recommendation
Bound or partition the reward *calculation* phase the same way distribution already is: cap the number of stake delegations processed per epoch-boundary block, or split `calculate_reward_points_partitioned`/`calculate_stake_rewards_and_commissions` across multiple blocks/slots analogous to `get_reward_distribution_num_blocks`. Alternatively, enforce a delegation-count-aware minimum delegation/rent cost that scales the economic cost of growing the delegation set faster than linear, or cap total live stake accounts per staker/network to keep O(N) epoch-boundary work bounded by a known constant.

### Proof of Concept
1. Repeatedly submit `CreateAccount` + `Initialize` + `DelegateStake` (or `create_account_and_delegate_stake`) transactions from many wallets, each funding a stake account with only `rent_exempt_reserve + get_minimum_delegation(...)` lamports (see `stake_utils::get_minimum_delegation`, `runtime/src/stake_utils.rs:20-27`).
2. Accumulate a very large number (e.g., hundreds of thousands to millions) of such minimal delegations before an epoch boundary.
3. At the next epoch boundary, `Bank::process_new_epoch` invokes `compute_new_epoch_caches_and_rewards` → `calculate_rewards_for_partitioning` → `calculate_validator_rewards`, which runs `calculate_reward_points_partitioned` and `calculate_stake_rewards_and_commissions` over the full `stake_delegations_vec()` in one unpartitioned call (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:813-938`, `942-1009`).
4. Measure wall-clock time of this call scaling linearly with the injected delegation count (as already flagged in-code for N > 1,000,000), and observe it runs synchronously inside block production for the epoch-boundary slot (`runtime/src/bank.rs:1841-1846`), unlike the deliberately chunked distribution phase (`runtime/src/bank/partitioned_epoch_rewards/mod.rs:408-428`).

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
