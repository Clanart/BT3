## Title
Unchecked pointer arithmetic in CPI account-data translation can construct an out-of-bounds VM slice - (File: `program-runtime/src/cpi.rs`)

### Summary
`CallerAccount::get_serialized_data` in `program-runtime/src/cpi.rs` performs raw pointer arithmetic (`add(offset)` + `from_raw_parts_mut(..., len)`) to build a mutable byte slice into the VM's input region, analogous to the `LibBytes.sol` `keccak` bug where `add(data, add(32, offset))` was used without validating `offset + length` against the buffer's actual size. Here, only a single byte at `MM_INPUT_START` is bounds-checked via `translate_slice_mut_for_cpi`, and the actual `vm_addr`-derived offset and `len` used to build the final slice are not directly validated against the true size of the mapped input region at that call site.

### Finding Description
The vulnerable code is: [1](#0-0) 

```rust
} else if virtual_address_space_adjustments {
    // Workaround the memory permissions (as these are from the PoV of being inside the VM)
    unsafe {
        let serialization_ptr: &'a mut [u8] = translate_slice_mut_for_cpi::<u8>(
            memory_mapping,
            solana_sbpf::ebpf::MM_INPUT_START,
            1,
            false,
        )?;
        Ok(std::slice::from_raw_parts_mut(
            serialization_ptr
                .as_mut_ptr()
                .add(vm_addr.saturating_sub(solana_sbpf::ebpf::MM_INPUT_START) as usize),
            len,
        ))
    }
}
```

`translate_slice_mut_for_cpi` only validates that **1 byte** at `MM_INPUT_START` is mappable/writable — it does not validate the full range `[vm_addr, vm_addr + len)`. The function then does raw pointer arithmetic (`.add(offset)`) and constructs a slice of `len` bytes via `from_raw_parts_mut`, entirely bypassing `solana_sbpf`'s own region-bounds checking for the actual `[vm_addr, vm_addr+len)` range. This is structurally identical to the reported Solidity bug pattern: computing `pointer + offset` and reading/writing `length` bytes without checking `offset + length <= actual_buffer_length`.

The `len` value passed in ultimately derives from `*ref_to_len_in_vm` (when `syscall_parameter_address_restrictions` is active) or directly from the caller-supplied `AccountInfo::data.len()` / `SolAccountInfo::data_len` (when that feature is inactive) — both of which are values that live in program-controlled VM memory (see call sites at [2](#0-1)  and [3](#0-2) ). While there is a guard `if len > address_space_reserved_for_account { return Err(InvalidRealloc) }` at [4](#0-3) , this guard is only active `if syscall_parameter_address_restrictions` is true, and even when active it bounds `len` only relative to `original_data_len`, not relative to the real host-buffer capacity backing `serialization_ptr`. `vm_addr` itself is separately validated with `check_account_info_pointer` to equal the expected `vm_data_addr` recorded in `SerializedAccountMetadata` at account-info construction time — but that equality check does not re-verify that `vm_addr + len` stays inside the single VM input region referenced by `serialization_ptr`.

### Impact Explanation
If a caller program can influence `vm_addr` or `len` such that `vm_addr.saturating_sub(MM_INPUT_START) + len` exceeds the actual size of the host buffer backing the VM input region, `from_raw_parts_mut` will construct a Rust slice that reads/writes past the end of the allocated buffer. This is a memory-safety violation reachable from unprivileged BPF program code performing a cross-program invocation (`invoke`/`invoke_signed`), and could lead to corruption of adjacent heap memory in the validator process, information disclosure, or a validator crash (denial of service) — all without validator/peer/operator privileges.

### Likelihood Explanation
This code path is only exercised when `virtual_address_space_adjustments` is active and `account_data_direct_mapping` is not, and is additionally constrained by the various pointer-equality (`check_account_info_pointer`) and length-restriction (`syscall_parameter_address_restrictions`) checks elsewhere in `from_account_info`/`from_sol_account_info`. I was **not able to fully verify** whether those surrounding checks (particularly the interaction between `check_account_info_pointer` equality checks and the actual host-buffer size backing the single `MemoryRegion` at `MM_INPUT_START`) are sufficient in all feature-flag combinations to prevent `vm_addr + len` from exceeding the true region size — the analysis required deeper knowledge of `solana_sbpf::memory_region::MemoryRegion` layout for the whole VM input area, which falls partly into the "dependencies/sBPF interpreter" area explicitly out of scope per SECURITY.md. Given the guard only fires under one feature flag and bounds against `original_data_len` (not the real buffer size), and that similar code paths in this same function are exercised by the repository's own tests around invalid account-info pointers and CPI resizing edge cases (e.g., `test_cpi_invalid_account_info_pointers`, `test_update_caller_account_data`), the likelihood is plausible but not conclusively proven from the available code alone.

### Recommendation
Add an explicit bounds check before performing the pointer arithmetic in `CallerAccount::get_serialized_data`'s `virtual_address_space_adjustments` branch, validating that `vm_addr.saturating_sub(MM_INPUT_START).saturating_add(len)` does not exceed the actual size of `serialization_ptr` (i.e., the real host buffer length for the whole input region), returning an error (e.g., `InstructionError::InvalidRealloc` or an access-violation error) otherwise — mirroring the recommended `require(offset + length <= data.length)` fix applied to `LibBytes.sol`. Alternatively, replace the raw `.add()`/`from_raw_parts_mut` construction with a call that goes through `solana_sbpf`'s bounds-checked `map`/`translate_slice`-style API using the *full* `[vm_addr, vm_addr+len)` range instead of `MM_INPUT_START` plus 1 byte.

### Proof of Concept
A definitive PoC requires reproducing the exact `MemoryRegion` layout of the VM input area under `virtual_address_space_adjustments=true`/`account_data_direct_mapping=false` and crafting a `SolAccountInfo`/`AccountInfo` (via CPI) whose `data_addr`/`data_len` (or `ref_to_len_in_vm`) values pass the `check_account_info_pointer` equality check yet whose derived `len` causes `vm_addr - MM_INPUT_START + len` to exceed the real serialized buffer size before the `syscall_parameter_address_restrictions` length guard applies (or in configurations where that flag is inactive). Constructing and validating such a case would require dynamic testing (building this exact CPI scenario with concrete feature-flag combinations, e.g. extending existing tests such as `test_cpi_invalid_account_info_pointers` in `programs/sbf/tests/programs.rs`) rather than static code reading alone, which I was unable to perform in this session.
