### Title
Unhandled panic in `pointer` precompile from unchecked type assertion on CosmWasm query response - (File: precompiles/pointer/pointer.go)

### Summary
The `pointer` precompile's `AddCW20`, `AddCW721`, and `AddCW1155` handlers decode a CosmWasm contract's smart-query JSON response into `map[string]interface{}` and then perform an unchecked type assertion `formattedRes["name"].(string)` / `formattedRes["symbol"].(string)`. If the queried key is absent or not a string, the map lookup yields an untyped `nil` and the single-value assertion panics rather than failing gracefully, analogous to the null-pointer-dereference bug class in ALPINE-CVE-2025-8224 (an unchecked lookup into a data section is dereferenced without validating its presence/type).

### Finding Description
`precompiles/pointer/pointer.go:154-155` (CW20), `:186-187` (CW721), and `:218-219` (CW1155) run: [1](#0-0) 

```go
formattedRes := map[string]interface{}{}
if err := json.Unmarshal(res, &formattedRes); err != nil {
    return nil, 0, err
}
name := formattedRes["name"].(string)
symbol := formattedRes["symbol"].(string)
``` [2](#0-1) [3](#0-2) 

`res` comes from `p.wasmdKeeper.QuerySmartSafe(ctx, cwAddress, []byte("{\"token_info\":{}}"))` (or `contract_info`) — a smart query executed against an arbitrary, attacker-deployed CosmWasm contract. Since the caller fully controls the target contract's code, they control the exact JSON returned by that query, including omitting the `name`/`symbol` fields or returning non-string values (e.g. `null`, a number). A missing key in a Go map returns the zero value for the value type, which for `interface{}` is `nil`; asserting `nil.(string)` (without the two-value `ok` form) panics with `interface conversion: interface {} is nil, not string`.

Tracing the call path up: `DynamicGasPrecompile.RunAndCalculateGas` at `precompiles/common/precompiles.go:156-215` invokes `d.executor.Execute(...)` directly with no `recover()` guarding it — the only `recover()` in that function is inside `chargeDecodeGas`, which only wraps the pre-decode gas-accounting step, not `Execute` itself. [4](#0-3) 

A panic here therefore unwinds out of the precompile call into the EVM interpreter and further up into the Cosmos SDK message handling for the EVM transaction, rather than being converted to a reverted call as intended by the `defer func(){ ... err = vm.ErrExecutionReverted }()` recovery pattern used elsewhere (that defer only catches returned `err`, not a raw Go panic).

### Impact Explanation
Any account can permissionlessly instantiate a CosmWasm contract whose `token_info`/`contract_info` query response omits `name`/`symbol` or returns them as non-strings, then call `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` on precompile `0x100b` targeting that contract. This triggers an uncaught Go panic during EVM message processing. Depending on whether any outer layer (e.g., the Cosmos baseapp's `runTx` recover, or ante handler) ultimately catches the panic, this could at minimum cause the transaction's processing goroutine/deliver-tx path to abort with a panic recovered at a much higher level (potentially causing non-deterministic behavior across validators if any state was mutated before the panic, since only the precompile's own local event manager is protected, not underlying keeper writes already committed via `evm.Create`/`SetCode` prior to the panic point) or, if unrecovered, crash the node process — a validator halt / DoS. This is a Medium-severity availability/correctness issue, not a fund-loss primitive, since it requires the attacker to control the queried CosmWasm contract and doesn't corrupt other accounts' balances directly.

### Likelihood Explanation
Likelihood is high for triggering the panic (any user can deploy a CW20/CW721/CW1155-shaped contract with a manipulated `token_info`/`contract_info` response and call the public pointer precompile), but the ultimate blast radius depends on unverified behavior of Cosmos SDK's outer panic recovery in `runTx`/ante handling, which I could not fully confirm within the available context (I was unable to locate a global panic-to-error recovery wrapping precompile execution specifically, only the local, non-panic-catching `defer` in `precompiles/common/precompiles.go`).

### Recommendation
Replace the unchecked type assertions with the two-value form and treat missing/mistyped fields as a query error instead of allowing a panic, e.g.:
```go
name, ok := formattedRes["name"].(string)
if !ok {
    return nil, 0, fmt.Errorf("cw20 token_info response missing string name field")
}
symbol, ok := formattedRes["symbol"].(string)
if !ok {
    return nil, 0, fmt.Errorf("cw20 token_info response missing string symbol field")
}
```
Apply the same fix to `AddCW721` and `AddCW1155` in `precompiles/pointer/pointer.go`, and audit the legacy versioned copies (`precompiles/pointer/legacy/v552`…`v67`) that contain the identical pattern for consistency, since old code paths can still be reachable depending on the chain's active version routing.

### Proof of Concept
1. Deploy (via `MsgInstantiateContract`, permissionless) a minimal CosmWasm contract whose query handler responds to `{"token_info":{}}` with `{"decimals":0,"total_supply":"0"}` (omitting `name`/`symbol`), or with `{"name":null,"symbol":null,...}`.
2. From any EVM account, call `addCW20Pointer(cwAddr)` on precompile address `0x000000000000000000000000000000000000100b` with `cwAddr` set to the bech32 address of the contract from step 1.
3. Execution reaches `precompiles/pointer/pointer.go:154` (`formattedRes["name"].(string)`), where the type assertion panics because the value is `nil`, since `Execute` is invoked without a panic-recovering wrapper in `precompiles/common/precompiles.go:156-215`.
