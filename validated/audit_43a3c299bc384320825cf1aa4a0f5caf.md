### Title
Stack exhaustion via unbounded recursive layer matching of an untrusted offer's puzzle reveal - ([File: chia/wallet/outer_puzzles.py])

### Summary
`Offer.from_bech32()` / `Offer.from_bytes()` / `TakeOffer.parsed_offer` accept an attacker-supplied offer file/bech32 blob from an untrusted counterparty and immediately call `Offer.from_spend_bundle()`, which runs `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` on every coin spend's raw puzzle reveal. [1](#0-0) [2](#0-1) 

### Finding Description
`match_puzzle()` iterates the registered outer-puzzle drivers (CAT, singleton, metadata, ownership, CR) and, on a match, each driver's `.match()` method recursively calls `self._match(UnknownPuzzle(known_program=inner_puzzle))` on the next inner layer to build up an `also` chain — e.g. `CATOuterPuzzle.match()`, `SingletonOuterPuzzle.match()`, `MetadataOuterPuzzle.match()`, and `OwnershipOuterPuzzle.match()` all end with `next_constructor = self._match(UnknownPuzzle(known_program=inner_puzzle))`. [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Each recursion step first uncurries the puzzle (`UnknownPuzzle.mod`/`.curried_args` calls `uncurry_puzzle()` → CLVM `uncurry()`), which is purely structural — it does not execute the program and is not bounded by any CLVM cost limit. [7](#0-6) [8](#0-7)  Because CLVM curry layers are just nested `(a (q . prog) (c (q . arg) 1))`-style constructs, an attacker constructing an offer can nest an arbitrary number of recognized outer-puzzle layers (e.g. CAT-wrapping repeated thousands of times, or singleton/metadata/ownership layering) without needing to satisfy any real spend semantics, since `match_puzzle` never runs the CLVM program to completion, only inspects its curried shape. The recursion depth in Python is directly proportional to the attacker-chosen nesting depth in the puzzle reveal bytes, exactly analogous to CVE-2019-6291's `expr6` recursing once per input character with no depth cap.

This same unbounded-recursion `match_puzzle` path is also reachable via `Offer._get_offered_coins()` when computing offer summaries, and via any RPC/CLI flow that loads an offer (`TakeOfferCMD`, `get_offer_summary`, `CreateOfferForIDs` responses, `_OfferEndpointResponse.from_json_dict`), all of which are triggered before any signature/cost validation occurs. [9](#0-8) [10](#0-9) 

### Impact Explanation
A crafted offer file/bech32 blob from an untrusted trading counterparty can crash or hang the recipient wallet process (`RecursionError`/native stack overflow) purely by parsing the offer to display its summary or to accept it — before any signature check, cost accounting, or on-chain validation happens. This is a spend-triggered/offer-triggered transaction-processing halt on the wallet side, matching the "Accept" criteria of a spend/offer-triggered processing halt.

### Likelihood Explanation
Medium-to-High: an attacker only needs to construct a valid-looking (or even partially valid) offer whose puzzle reveals are deeply, repeatedly curried with recognized outer-puzzle mod hashes (CAT/singleton/metadata/ownership/CR). No signatures or real coin ownership are required merely to reach `match_puzzle`'s recursive matching in `from_spend_bundle`/`_get_offered_coins`, since those run before consensus validation. The victim only needs to open/inspect (`get_offer_summary`) or attempt to take the offer.

### Recommendation
Bound the recursive layer-matching depth in `match_puzzle`/`OuterPuzzle.match()` (and the corresponding `get_inner_puzzle`/`get_inner_solution`/`construct`/`solve` recursive counterparts) with an explicit maximum nesting count, or convert the layer-walk to an iterative loop with an enforced depth limit, rejecting/treating-as-opaque any puzzle whose outer-layer chain exceeds a sane bound (e.g., the maximum number of real driver layers ever used in production, such as 10–20) before offer parsing/summary generation proceeds.

### Proof of Concept
Not independently executed against a live wallet in this analysis; the mechanism is inferred structurally from source (unbounded mutual recursion in `match_puzzle` driven by attacker-controlled curry nesting depth in an offer's puzzle reveals, with no depth guard found in `chia/wallet/outer_puzzles.py`, `chia/wallet/cat_wallet/cat_outer_puzzle.py`, `chia/wallet/nft_wallet/*_outer_puzzle.py`, or `chia/wallet/puzzles/puzzle_drivers.py`). Conceptually: construct a puzzle reveal that is `CAT_MOD.curry(tail_hash, CAT_MOD.curry(tail_hash2, CAT_MOD.curry(..., inner_puzzle)))` nested N times (N large enough to exceed Python's default recursion limit, e.g. N ≈ 1000–3000), embed it as a coin spend's `puzzle_reveal` in an `Offer`, encode via `Offer.to_bech32()`, and have the victim call `Offer.from_bech32()` (e.g. via `get_offer_summary` RPC or `TakeOfferCMD`) to trigger the recursive `match_puzzle` walk and a `RecursionError`/stack overflow.
