### Title
Identity group keys are accepted and enable universally forged Schnorr signatures - ([File: crypto/schnorr/src/lib.rs])

### Summary
Serai’s Schnorr verifier does not reject an identity public key or identity nonce. When the public key is the identity, the equation `R + cA - sG = 0` reduces to `R = sG`, so `R = identity` and `s = 0` verifies for every challenge and message. [1](#0-0) 

`ThresholdKeys::read` accepts attacker-controlled verification shares through `read_G`, which only enforces canonical point encoding and does not reject the identity. [2](#0-1) [3](#0-2)  `ThresholdKeys::new` likewise derives the group key without checking that the verification shares or resulting group key are non-identity. [4](#0-3) 

### Finding Description
`SchnorrSignature::verify` evaluates:

```text
R + cA - sG = 0
```

where `A` is the public key. [5](#0-4)  If `A` is the identity, then `cA` is always identity. Submitting `R = identity` and `s = 0` therefore satisfies the verifier for every challenge. [6](#0-5) 

This is analogous to accepting `address(0)` as an oracle signer: the verifier accepts a distinguished invalid authority for which anyone can construct a valid response. A one-participant serialized `ThresholdKeys` value with an identity verification share produces an identity group key because the group key is the interpolated sum of the supplied shares. [7](#0-6)  For `t = n = 1`, the interpolation factor is `1`, so the resulting group key is exactly the supplied identity share. [8](#0-7) 

### Impact Explanation
Any application that deserializes or otherwise accepts a `ThresholdKeys` object containing an identity group key can have signatures forged for that key without knowledge of any private key share. The forged signature works for arbitrary messages and challenges, making it a universal signature forgery under the affected identity key.

The same issue also permits other identity-key security failures: FROST’s Schnorr algorithm passes the group key into this verifier without a non-identity check. [9](#0-8) 

### Likelihood Explanation
Exploitation requires an identity public key to be accepted as a configured or deserialized verification key. That can occur through the exposed `ThresholdKeys::read` path because canonical identity encodings are accepted and neither deserialization nor `ThresholdKeys::new` rejects identity shares or an identity aggregate group key. [10](#0-9)  Once accepted, forging signatures is deterministic and requires no private-key material.

### Recommendation
Reject identity points for public keys before signature verification. Specifically:

- In `SchnorrSignature::verify` and `batch_statements` callers, reject `public_key.is_identity()`.
- Reject `R.is_identity()` during `SchnorrSignature::read` or before verification.
- In `ThresholdKeys::new`, reject identity verification shares and reject a resulting identity `group_key`.
- For aggregate verification, reject empty signer sets and identity public keys/nonces.

Defense at the key-construction boundary is preferable, but verification should still reject identity public keys so independently supplied keys cannot bypass the check.

### Proof of Concept
The following invariant demonstrates the forge for any `Ciphersuite` whose encoding accepts the identity point:

```rust
let public_key = C::G::identity();
let challenge = C::F::random(&mut rng); // Any challenge works.

let forged = SchnorrSignature::<C> {
  R: C::G::identity(),
  s: C::F::ZERO,
};

assert!(forged.verify(public_key, challenge));
```

The verifier expands this to:

```text
identity + challenge * identity - 0 * G = identity
```

so it returns `true`. [1](#0-0) 

A serialized `ThresholdKeys` with `t = 1`, `n = 1`, `i = 1`, constant interpolation coefficient `1`, any canonical secret-share scalar, and one identity verification share is accepted by `ThresholdKeys::read`; its derived group key is the identity. [11](#0-10)

  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }

  /// Verify a Schnorr signature for the given key with the specified challenge.
  ///
  /// This challenge must be properly crafted, which means being binding to the public key, nonce,

  /// different keys/messages.
  #[must_use]
  pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
    multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
