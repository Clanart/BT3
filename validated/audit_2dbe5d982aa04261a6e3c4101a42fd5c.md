### Title
Delegated stacking locks (`delegate-stack-stx`/`delegate-stack-extend`/`delegate-stack-increase`) are never recorded in the `AssetMap`, letting a stacking action escape post-condition enforcement - (File: `pox-locking/src/pox_4.rs`)

### Summary
`handle_stack_lockup_pox_v4`, `handle_stack_lockup_extension_pox_v4`, and `handle_stack_lockup_increase_pox_v4` only call `global_context.log_stacking(...)` when `function_name` is exactly `"stack-stx"`, `"stack-extend"`, or `"stack-increase"` — i.e. only for the *direct* stacking entry points. When the same underlying lock is produced via the delegate entry points (`delegate-stack-stx`, `delegate-stack-extend`, `delegate-stack-increase`), the STX lock is still applied to the balance database (`pox_lock_v4`/`pox_lock_extend_v4`/`pox_lock_increase_v4`), but the corresponding `log_stacking` call is skipped, so the amount never enters the transaction's `AssetMap.stacking_map`.

### Finding Description
`check_transaction_postconditions` (`crates/stacks-transactions/src/lib.rs`) enforces stacking post-conditions purely from `asset_map.get_all_stacking()`: [1](#0-0) 
It also gates any "unchecked" fungible/asset movement per the post-condition mode via `asset_map.to_table()`, but the `stacking_map` is intentionally excluded from `to_table()` and enforced only through the dedicated loop above: [2](#0-1) 

The stacking amount is only added to that map when the *direct* function names match: [3](#0-2) [4](#0-3) [5](#0-4) 

In every one of these three handlers, the `pox_lock_v4`/`pox_lock_extend_v4`/`pox_lock_increase_v4` call (which mutates the account's real STX balance/lock state) succeeds unconditionally regardless of whether the call came from `stack-stx` or `delegate-stack-stx` (same for extend/increase), but `log_stacking` — the only mechanism that records the lock in the `AssetMap` used for post-condition checks — is gated behind an `if function_name == "stack-stx" { ... }` (and the analogous checks for extend/increase). The delegate variants fall through that `if` and never call `log_stacking` for the stacker whose funds were actually locked.

This is the same bug class as the referenced Noya finding: a state-mutating operation (locking STX / moving a token) executes, but the bookkeeping structure that downstream authorization logic relies on (`_updateTokenInRegistry` in Noya, `AssetMap.stacking_map` here) is not updated to match, because the "update" call is conditioned on a narrower set of code paths than the set of paths that actually perform the underlying mutation.

### Impact Explanation
Post-condition checks (`Staking` post-conditions and the mode-based "every asset moved must be checked" enforcement in `Deny`/`Originator` mode) are the mechanism by which a signer authorizes exactly what a transaction is allowed to do to their assets, including how much STX may be locked for stacking. Because `delegate-stack-*` calls never populate `AssetMap.stacking_map`, any lock performed through those entry points is invisible to `check_transaction_postconditions`. Concretely, if a principal's own transaction (self-delegated, or calling into a contract that internally invokes `delegate-stack-stx`/`delegate-stack-extend`/`delegate-stack-increase` on that same principal as the stacker) is wrapped in `restrict-assets?`/`as-contract?` with a `with-stacking` allowance, or is submitted in `Deny`/`Originator` mode expecting all stacking actions to be explicitly authorized, the lock silently bypasses that check — the `AssetMap` the check operates on shows no stacking activity at all for the affected principal, even though real STX was locked on-chain. This breaks the "asset movement past its post-conditions" invariant that `check_transaction_postconditions` is meant to guarantee.

### Likelihood Explanation
Reaching this requires the stacker to be reachable as `tx-sender` for a `delegate-stack-*` call in the underlying `.pox-4` contract (e.g., self-delegation, where `delegate-stx`'s `delegated-to` is set to the stacker's own principal, or a contract-mediated call path where the stacker's own transaction indirectly triggers the delegate entry point). This is plausible within the delegation contract logic in `pox-4.clar` (delegate authorization is checked, but nothing in that contract logic prevents `delegated-to` == the delegator), and the Rust-side gap is a straightforward code-path omission (three `if function_name == "..."` conditions each missing their delegate counterpart) rather than a contrived edge case.

### Recommendation
In `pox-locking/src/pox_4.rs`, call `global_context.log_stacking(&stacker, locked_amount)` (and the analogous calls in the extend/increase handlers) for the delegate function names as well as the direct ones, so that every code path that mutates the stacker's locked STX also updates the `AssetMap`. Alternatively, restructure the checks so `log_stacking` is called unconditionally whenever `pox_lock_v4`/`pox_lock_extend_v4`/`pox_lock_increase_v4` return `Ok(_)`, regardless of which of the six function names triggered it, matching how `stx_transfer_consolidated` unconditionally calls `log_stx_transfer` right after `sender_snapshot.transfer_to(...)` succeeds.

### Proof of Concept
1. Stacker `S` calls `delegate-stx` naming itself (`S`) as `delegated-to`.
2. `S` then calls `delegate-stack-stx` for itself as `stacker`, wrapped in `(restrict-assets? tx-sender ((with-stacking u1000)) (try! (contract-call? .pox-4 delegate-stack-stx S amount-ustx pox-addr start-burn-ht lock-period)) true)` where `amount-ustx` exceeds `u1000`.
3. `handle_stack_lockup_pox_v4` is invoked with `function_name == "delegate-stack-stx"`; `pox_lock_v4` locks `amount-ustx` of `S`'s STX.
4. Because `function_name != "stack-stx"`, `global_context.log_stacking(&stacker, locked_amount)` at [6](#0-5)  is skipped.
5. `AssetMap.stacking_map` has no entry for `S`, so the `restrict-assets?` allowance check for `with-stacking u1000` at [1](#0-0)  never triggers, and the full `amount-ustx` gets locked despite the declared `u1000` allowance.
