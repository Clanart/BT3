### Title
OP_RETURN data output omitted from fee/weight calculation, causing underpayment of the intended fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts an optional `data` payload that is appended as a zero-value `OP_RETURN` output to `tx_outs`, but the weight/vbyte estimation in `calculate_weight_vbytes` is invoked only with `payments` (and optionally `change`). The data output is never included in the sized transaction, so `needed_fee = fee_per_vbyte * vbytes` is computed over a transaction that is smaller than the one actually constructed and signed. This is the same bug class as the Buffer report: a fee/amount inversion computed against a formula that omits a term, so the committed value is systematically wrong.

### Finding Description
The data output is pushed to `tx_outs` before the weight is computed: [1](#0-0) 

`calculate_weight_vbytes` builds its sizing transaction from `payments` plus an optional `change` output only — there is no parameter for the `OP_RETURN` output: [2](#0-1) 

Both call sites — the no-change estimate and the `fee_with_change` re-estimate — omit the data output: [3](#0-2) 

Since `data` may be up to 80 bytes (checked at line 171), the real transaction carries an additional output of roughly 34 + 80 ≈ 114 bytes (~110+ vbytes beyond the output slot itself) that was never priced. The same omission affects the `MAX_STANDARD_TX_WEIGHT` check at line 241, which is evaluated against the under-sized `weight`.

### Impact Explanation
The signed transaction's actual fee equals `input_sat - sum(tx_outs)` = `needed_fee`, but the real vsize is larger than `vbytes`, so the effective fee rate is strictly below the requested `fee_per_vbyte`. Consequences:

1. **Below-minimum relay risk**: the `TooLowFee` check compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`. A transaction paying exactly the minimum per the estimate will actually pay less than 1 sat/vbyte once the data output is included, making it non-relayable/non-standard on the Bitcoin network — funds move slowly or stall even though construction "succeeded."
2. **Oversized transaction acceptance**: a transaction whose true weight exceeds `MAX_STANDARD_TX_WEIGHT` can pass the line-241 check because the data output's weight is uncounted.
3. **Systematic underfunding**: any integrator specifying `data` and a target fee rate pays less than intended, degrading confirmation reliability — analogous to the original report where the protocol earns less than the computed fee implies.

### Likelihood Explanation
The bug triggers deterministically whenever `data: Some(..)` is passed to the public `SignableTransaction::new` API in `networks/bitcoin/src/wallet/send.rs` — no race, no adversarial timing required. `data` is untrusted, caller-supplied bytes (the API exists precisely so callers can attach arbitrary `OP_RETURN` payloads), so any external caller of this wallet library path can hit it with public inputs. The severity is bounded because in-repo callers (e.g. `make_signable_transaction` in `processor/src/networks/bitcoin.rs`) currently pass `None` for `data`, limiting exposure to direct users of the wallet API — consistent with a Medium finding.

### Recommendation
Include the data output in the sizing transaction. Either pass the already-built `tx_outs` (or the serialized `OP_RETURN` `ScriptBuf`) into `calculate_weight_vbytes` so its `tx.output` mirrors the final transaction, or compute the `OP_RETURN` output's weight contribution separately and add it to `weight`/`vbytes` before computing `needed_fee`. Apply the same fix at both call sites (lines 204 and 225–226) so the with-change estimate is also correct.

    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
