### Title
Anyone can forge the OP_RETURN payer attribution on a withdrawal payout, causing an operator to be reimbursed for a payout it never funded - ([File: core/src/verifier.rs])

### Summary
The bridge only learns "which operator fronted a withdrawal" by parsing the `OP_RETURN` output of whatever Bitcoin transaction happens to spend the registered withdrawal UTXO, without verifying that the named operator actually signed, funded, or broadcast that transaction. Because the withdrawal UTXO is unlocked with a `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` signature, any unprivileged party who observes that signature can build an alternative payout transaction — funding it themselves — that pins the required input/output but attaches an arbitrary operator's xonly-pubkey in the `OP_RETURN` field. The verifier's bookkeeping then durably attributes that payout to the named operator, letting the operator's own `PayoutCheckerTask` kick off the on-chain reimbursement flow and get paid from the vault for a withdrawal it never fronted.

### Finding Description
Withdrawals are fulfilled by an operator building a payout transaction whose input is the registered withdrawal UTXO and whose `OP_RETURN` output embeds the operator's own xonly-pubkey, alongside the user-signed input/output pair: [1](#0-0) 

The user's signature only covers `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` over that one input and one output, as documented in the proto: [2](#0-1) 

This sighash type is designed to let a fee-payer add arbitrary extra inputs/outputs — that is its purpose for `TxSender`'s RBF/fee-bumping — but it equally allows *anyone* who has seen the signature to construct their own transaction that spends the same withdrawal UTXO, adds their own funding inputs, and injects an arbitrary `OP_RETURN` value, since nothing in the pinned scope constrains the additional outputs' content.

The verifier's chain-scanning logic then trusts whatever `OP_RETURN` value is found in the confirmed spending transaction as ground truth for who paid: [3](#0-2) 

This attribution is persisted via `update_payout_txs_and_payer_operator_xonly_pk` and later consumed by the operator itself to detect its "own" unhandled payouts: [4](#0-3) 

Once picked up, `handle_finalized_payout` allocates a kickoff connector and starts the reimbursement process for that operator: [5](#0-4) 

Reimbursement ultimately spends the vault's move-to-vault deposit output to the operator's own reimbursement address: [6](#0-5) 

The binding that should hold is: `operator credited for reimbursement == operator that actually broadcast/funded the payout transaction`. Because the `OP_RETURN` content is unauthenticated attacker-controlled data on a transaction that need not be built, signed, or funded by the named operator at all, this binding can be broken by any party with (a) knowledge of the user's `SinglePlusAnyoneCanPay` withdrawal signature (which is submitted as public calldata to the Citrea bridge contract when the user registers the withdrawal, as seen in the test helper constructing `safeWithdraw` parameters) and (b) the ability to broadcast a Bitcoin transaction — neither of which requires any verifier/operator/aggregator role or key. [7](#0-6) 

### Impact Explanation
An honest, previously-uninvolved operator can be made to believe it fronted a withdrawal it never funded (funded instead out of the attacker's pocket, or by no one meaningfully at all beyond the attacker paying to complete the withdrawal). Its automation (`PayoutCheckerTask`) will then autonomously spend the operator's own kickoff/round resources and claim the vault's move-to-vault deposit as "reimbursement" for a payout the operator did not pay. This causes the vault to release BTC as reimbursement without a matching cost borne by that operator — a double payment relative to the actual withdrawal outflow, and a value leak from the bridge's custody accounting. This matches the Critical impact criterion "an operator reimbursed for a payout it never funded."

### Likelihood Explanation
The withdrawal signature and parameters are public (submitted as calldata to the Citrea contract as part of the standard withdrawal-registration flow), and constructing an alternative Bitcoin transaction that reuses a `SIGHASH_SINGLE|ANYONECANPAY` signature while adding arbitrary extra inputs/outputs (including a fabricated `OP_RETURN`) is straightforward and requires only wallet access and the ability to broadcast to Bitcoin — no cryptographic keys belonging to any bridge participant, and no privileged gRPC access, since the attack is executed directly on the Bitcoin network rather than through any mTLS-protected RPC.

### Recommendation
Do not trust the `OP_RETURN` value alone as proof of payer identity. The reimbursement/kickoff flow should independently verify that the *specific* payout transaction being credited was actually constructed/signed by the claiming operator (e.g., by checking that the transaction matches a transaction the operator itself generated and recorded before broadcast, or by requiring an operator signature over the full payout transaction — not just the user-pinned input/output — before crediting it in `update_payout_txs_and_payer_operator_xonly_pk`).

### Proof of Concept
1. Observe a user's public withdrawal registration on Citrea (`safeWithdraw` calldata), which includes the `input_signature` (`SinglePlusAnyoneCanPay`), `input_outpoint`, `output_script_pubkey`, and `output_amount`.
2. Before any legitimate operator broadcasts a payout, construct a new Bitcoin transaction that: (a) includes the withdrawal UTXO as an input satisfied by the leaked signature and the pinned output paying the user, (b) adds attacker-funded inputs/outputs to cover fees/amount, and (c) adds an `OP_RETURN` output containing an arbitrary victim operator's xonly-pubkey.
3. Broadcast and get this transaction confirmed.
4. The verifier's `update_finalized_payouts` records the victim operator as the payer for this withdrawal. [8](#0-7) 
5. The victim operator's `PayoutCheckerTask` detects the "unhandled payout" credited to it and autonomously starts the kickoff/reimbursement process, ultimately claiming the vault's deposit funds as reimbursement for a payout it never made. [9](#0-8) 

*Note: I was unable to fully inspect `validate_payer_is_operator` (core/src/operator.rs) within the available context; if that function performs additional cross-checks beyond reading the DB-stored `operator_xonly_pk` column, it might partially mitigate this issue, but since that column's value is itself derived unverified from attacker-controlled `OP_RETURN` data, such a check would not close the gap unless it re-validates against an operator-signed record of the transaction predating broadcast.*

pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
