### Title
Malformed conflict marker desyncs Copilot conflict-hunk count from splice targets, silently leaving live `<<<<<<<`/`>>>>>>>` markers in a "resolved" commit - (File: `app/src/lib/copilot-conflict-context.ts` / `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Copilot AI merge-conflict-resolution feature parses conflict markers twice with two structurally different algorithms that are supposed to agree on hunk boundaries: `extractConflictHunks` (used to build the prompt and to compute the "expected hunk count" for validation) and `reassembleResolvedFile` (used to splice the model's per-hunk resolutions back into the file). Like the StableMath report's two invariant implementations that should-but-don't agree, these two marker scanners diverge on malformed/nested marker sequences, so the hunk count both sides "agree" on does not correspond to the same regions of the file.

### Finding Description
`extractConflictHunks` ( [1](#0-0) ) scans for an ours-marker, then simply collects lines into `oursLines` until it sees a `baseMarker` or `separatorMarker` — it never checks for a stray `theirsMarker` while accumulating ours-content. So a leading, orphaned/malformed hunk (an ours-marker with a theirs-marker but no separator) gets silently swallowed into the *next* real hunk's `oursContent`, and the whole mess is counted and sent to the model as a single hunk.

`reassembleResolvedFile` ( [2](#0-1) ) uses the identical marker regexes ( [3](#0-2) , matching [4](#0-3) ) but a different scanning strategy: its look-ahead loop breaks as soon as it hits *either* a separator *or* a theirs-marker, whichever comes first. For the same orphaned-then-real marker sequence, this causes it to treat the first (orphaned) block as malformed and copy it through **verbatim, markers included**, then correctly identify the *second*, real conflict as the sole valid hunk and splice the model's only hunk resolution into that region instead.

The result: `extractConflictHunks` reports "1 conflict" for the file, `validateResolutionPaths` ( [5](#0-4) ) checks only that the *count* of hunks matches (`resolution.hunks.length !== expectedCount`), and since both algorithms happen to produce "1 hunk" for this file, validation passes — but the hunk the model actually resolved (from the merged/garbled `oursContent`) gets spliced into the wrong physical location, and the orphaned marker block is left untouched, still containing raw `<<<<<<<`/`=======`/`>>>>>>>` text. The app then reports the file as successfully auto-resolved.

Existing guards do not catch this: `validateResolutionPaths` only compares hunk counts and path names — it never re-scans the reassembled output for leftover conflict markers, and `reassembleResolvedFile`'s own malformed-block guard (`!hasSeparator || closingIndex === -1`) only protects that single block; it has no way to detect that its overall hunk segmentation has drifted from `extractConflictHunks`'s segmentation.

### Impact Explanation
This causes silent corruption of what the user commits: the "resolved" file that gets written to disk and is presented to the user as fully merged can still contain live Git conflict markers mixed with model-generated content that was matched against the wrong source region. If the user trusts the "resolved" indicator and commits/pushes without inspecting the diff, broken code (with literal conflict-marker lines, or worse, a chunk of the wrong branch's content) ships into the repository history. This matches the "silent corruption of what the user commits or pushes" impact category — the analog of the invariant-mismatch impact in the original report, where an implicit cross-check (matching hunk counts, matching invariants) passes even though the underlying data used by each side has diverged.

### Likelihood Explanation
Triggering requires only that a merge/rebase/cherry-pick conflict region in a file contains an "orphaned" marker sequence preceding a real one — e.g., a file that already had literal `<<<<<<<`/`>>>>>>>`-looking text (from a previous conflict resolution mistake, example code in docs/tests, or a crafted commit contributed by a collaborator/attacker on a branch the victim later merges) immediately followed by an actual conflict block. This is entirely reachable through normal Desktop usage (merge/rebase with Copilot conflict resolution enabled) and needs no local/admin access, no leaked credentials, and no unnatural steps beyond merging a branch with attacker-influenced content — consistent with the required "attacker controls a cloned/fetched repository" threat model. It is a corner case rather than the common path, so likelihood is moderate, but it's deterministic and reproducible once the marker pattern exists in the merged content.

### Recommendation
Unify hunk segmentation into a single implementation shared by both the prompt-building/validation path and the reassembly path (e.g., have `extractConflictHunks` return hunk boundary offsets that `reassembleResolvedFile` consumes directly, rather than re-deriving boundaries with a separately-written scanner). At minimum, `reassembleResolvedFile`'s look-ahead should also treat an unexpected ours-marker as a boundary/failure condition (mirroring how `extractConflictHunks`'s theirs-collection phase behaves), and `validateResolutionPaths`/the write path should re-scan the final reassembled content for any remaining `<<<<<<<`/`=======`/`>>>>>>>` marker lines and fail the resolution (falling back to manual resolution) rather than reporting success.

### Proof of Concept
Given a conflicted file with the following content (result of a merge where an earlier, already-malformed marker block precedes a genuine conflict):
```
<<<<<<< HEAD
orphan-ours
>>>>>>> feature-orphan
<<<<<<< HEAD
real-ours
=======
real-theirs
>>>>>>> feature
```
1. `buildConflictContext` → `extractConflictHunks` ( [6](#0-5) ) merges lines 0-7 into a single hunk (oursContent = `"orphan-ours\n>>>>>>> feature-orphan\n<<<<<<< HEAD\nreal-ours"`, theirsContent = `"real-theirs"`) and reports **1** hunk for this file to the prompt/validation logic.
2. Copilot returns exactly one `resolvedContent` for "Conflict 1 of 1", which `validateResolutionPaths` accepts because `resolution.hunks.length === expectedCount (1)` ( [7](#0-6) ).
3. `reassembleResolvedFile` ( [8](#0-7) ) instead treats lines 0-2 as malformed and copies them through **unchanged** (still containing `<<<<<<< HEAD` / `>>>>>>> feature-orphan`), then splices the model's one resolution into lines 3-7 (the real conflict).
4. The file written back to disk therefore still contains live, unresolved conflict-marker text from the first block while the app marks the file as auto-resolved by Copilot, which the user can then stage and commit without any warning.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
