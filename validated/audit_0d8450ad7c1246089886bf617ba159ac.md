## Finding: Missing zero-validation on `kip71.gastarget` governance parameter causes divide-by-zero panic in KIP-71 base fee calculation

The Thumbor bug class (user-controlled value flows unchecked into a native division/modulo, causing a crash) has a direct analog in Kaia's KIP-71 dynamic base-fee calculation.

### Title
Unvalidated `GasTarget` governance parameter allows divide-by-zero panic in `KIP71Config.NextMagmaBlockBaseFee`, crashing every node - ([File: params/kip71_config.go])

### Summary
`kip71.gastarget` is a mutable governance parameter that is registered with `noopFormatChecker` (no non-zero check), unlike its sibling parameter `kip71.basefeedenominator`, which explicitly enforces `v != 0`. If `GasTarget` is set to `0` via governance (header vote or contract governance `GovParam.setParam`/`setParamIn`), the next call to `KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` using `big.Int.Div`, which panics on division by zero in Go, crashing the process.

### Finding Description
In `kaiax/gov/param.go`, the parameter table shows the asymmetry directly: [1](#0-0) 

Specifically, `Kip71BaseFeeDenominator` requires `v != 0`, but `Kip71GasTarget` uses `noopFormatChecker`, admitting any `uint64` including `0`: [2](#0-1) 

This `GasTarget` value flows into `KIP71Config.NextMagmaBlockBaseFee`, where it is used as a divisor without a zero-check (unlike `baseFeeDenominator`, which is explicitly special-cased for zero at line 71-76 of the same file): [3](#0-2) 

Concretely, when `parentGasUsed != gasTarget` (the common case), the code executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` (line 102, increasing branch) or the equivalent in the decreasing branch (line 120). With `gasTarget == 0`, `big.Int.Div` panics with "division by zero" — this is Go runtime undefined-behavior-equivalent to the C-extension SIGFPE in the Thumbor report: an externally-controlled divisor reaches a native division operation with no validation.

`NextMagmaBlockBaseFee` is called from multiple hot, consensus-critical, and RPC-facing paths:
- Block header validation, run by every node on every incoming block: `BlockValidator.ValidateHeader` (evidenced by test wiring `pset.GasTarget` directly from `KIP71Config` in `blockchain/block_validator_test.go` lines 213-222).
- Header verification in `KIP71Config.VerifyMagmaHeader`: [4](#0-3) 
- Block/pending-header base fee assembly (mining code paths using the same function).
- Public RPC `eth_feeHistory` computation, which is directly reachable by any public-RPC caller: [5](#0-4) 

Because `GetParamSet` is queried per block (including next-block prediction), once `GasTarget=0` becomes active for block `N+1`, *every* node computing, validating, or answering RPC queries about block `N+1`'s base fee will panic and crash. This is a chain-wide denial-of-service/halt, not merely a local resource issue — it induces a crash-loop across the whole validator/full-node set as soon as the parameter activates, since every node must independently recompute or verify the same base fee.

### Impact Explanation
This is a High severity denial-of-service: once the `GasTarget=0` parameter activates, all full nodes and validators panic while validating the next block's header (`VerifyMagmaHeader`/`ValidateHeader`), while assembling new blocks (proposers), and while answering `eth_feeHistory` RPC calls. This can halt block production/consensus network-wide, matching the "acceptance of an invalid transaction/block" / "state divergence between nodes" and "no block production" impact bar, analogous to the original report's confirmed process-crash DoS via unvalidated divisor.

### Likelihood Explanation
`kip71.gastarget` is documented as a *mutable* governance parameter (`kaiax/gov/README.md`), settable via header-vote governance or KIP-81 contract governance (`GovParam.setParam`/`setParamIn`), both of which are normal (non-malicious-validator, non-p2p-exploit) governance operations explicitly in the allowed-analog scope ("governance parameters"). No format/range check currently prevents `GasTarget=0` from being proposed and activated — the existing test suite in `kaiax/gov/headergov/impl/header_test.go` (line 95) only tests a valid nonzero value and never exercises the zero case, confirming the gap is unguarded in both the header-vote path and (by extension) the identically-structured contract-governance path.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`, which is also divided/compared elsewhere) requiring `v != 0`, mirroring the existing check on `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, defensively guard the division in `KIP71Config.NextMagmaBlockBaseFee` (`params/kip71_config.go`) against `gasTarget == 0`, similar to the existing `baseFeeDenominator == 0` fallback at lines 71-76.

### Proof of Concept
1. Submit a governance vote (or `GovParam.setParam("kip71.gastarget", true, <8-byte zero>, activation)` via contract governance) setting `kip71.gastarget = 0`.
2. Once the parameter activates at block `N`, any node computing block `N+1`'s base fee — via block validation (`ValidateHeader`), block production, or an `eth_feeHistory` RPC call for a block range including `N+1` — calls `NextMagmaBlockBaseFee(parentNumber, parentBaseFee, parentGasUsed)` with `parentGasUsed != 0`.
3. Execution reaches `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, and `math/big.Int.Div` panics, crashing the node process. [6](#0-5)

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
