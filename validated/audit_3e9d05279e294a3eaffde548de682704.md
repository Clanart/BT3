Based on the code evidence gathered, I found a real local analog to the LBTC `burnCommission`-defaults-to-zero bug in `IntentGatewayV2.placeOrder()`.

### Title
Zero-amount / fee-bypassed order inputs are only rejected when a protocol fee is configured, allowing free spam of on-chain intents - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`LBTC.burn()` had no floor on the burnable amount because the `fee` used to gate the operation (`burnCommission`) defaulted to zero, so `amount <= fee` never reverted and attackers could spam the withdrawal pipeline with dust-sized, effectively free requests. `IntentGatewayV2.placeOrder()` has the same structural weakness: the only place that rejects a zero-value order input (`if (originalAmount == 0) revert InvalidInput();`) sits inside the `protocolFeeBps > 0` branch. [1](#0-0) 

### Finding Description
`placeOrder` resolves the applicable fee rate first (`_destinationProtocolFees[destinationHash]`, falling back to `_params.protocolFeeBps`), and only enters the per-input validation/reduction loop — which contains the `originalAmount == 0` check — when that resolved rate is non-zero: [1](#0-0) 

When `protocolFeeBps` is `0` (the deployment default before governance calls `SetTiers`/fee-setter, or for any destination without an override), the `else` branch is taken instead — `reducedInputs = order.inputs;` — with **no per-token amount validation at all**. The only outer guard is `order.inputs.length == 0`, which does not stop individual `TokenInfo.amount` entries from being `0`.

This is functionally identical to the LBTC pattern: a fee-derived state variable defaults to zero, and the only amount floor in the code is conditioned on that fee being non-zero, so when it's zero the floor silently disappears. An unprivileged caller can then call `placeOrder` in a loop with `order.inputs[i].amount = 0` (or with dust-sized amounts under the newly-deployed default `protocolFeeBps = 0`, matching the `PROTOCOL_FEE_BPS` default of `0` seen in the TRON migration script and the `protocolFeeBps: 0` used across the test fixtures), producing a valid commitment, escrow entry, and an `OrderPlaced`/dispatch event on every call at negligible gas cost. [2](#0-1) 

### Impact Explanation
Each spammed order still goes through full escrow bookkeeping (`_orders[commitment][token] = reducedInputs[i].amount;`) and emits the on-chain event that solvers and off-chain relayers must observe and evaluate to decide whether to fill or ignore. Exactly as with the LBTC `UnstakeRequest` flood, this forces solver/relayer infrastructure to process an unbounded stream of essentially free, zero-value intents, degrading indexing/monitoring throughput for legitimate orders and burning relayer/solver gas budgets on evaluation and (for cross-chain orders) subsequent GET/POST dispatches with `options.relayerFee` — a cost the spammer never has to cover since their own escrowed value is zero.

### Likelihood Explanation
This is directly and trivially reachable by any unprivileged EOA calling the public `placeOrder` entrypoint — no relayer, prover, admin, or governance action is required, and it is exploitable precisely in the common state where `protocolFeeBps` has not yet been configured for a chain/destination pair (the default `0` value used at deployment, as shown in the TRON migration script and the zero-fee gateway test fixtures). [3](#0-2) 

### Recommendation
Move the `originalAmount == 0` (and ideally a configurable minimum-amount) check out of the `protocolFeeBps > 0` conditional so it runs unconditionally over every `order.inputs[i]` regardless of whether a protocol fee is currently configured, mirroring the LBTC fix of enforcing a floor independent of whether the fee variable happens to be non-zero.

### Proof of Concept
1. Deploy `IntentGatewayV2` with default params where `protocolFeeBps == 0` and no `_destinationProtocolFees` override is set for the target destination (the state shown in `IntentGatewayV2SameChainTest.sol`'s base fixtures and the TRON migration's `PROTOCOL_FEE_BPS=0` default). [4](#0-3) 
2. Call `placeOrder` in a loop with `Order.inputs = [TokenInfo({token: <any ERC20>, amount: 0})]` and `fees: 0` — the `inputs.length == 0` guard passes (array has one element), the fee branch check (`protocolFeeBps > 0`) is false, so execution goes to the `else` branch with no amount validation. [5](#0-4) 
3. Each call succeeds, records a zero-value escrow entry, and emits an `OrderPlaced` event that solver/relayer tooling must ingest — repeat thousands of times to flood the intent-discovery pipeline at near-zero cost, analogous to the original `burn(scriptPubkey, 1)` spam against Lombard's off-chain unstake processor.
