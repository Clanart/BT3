# Finding: Unchecked ERC-20 return-value in escrow withdrawal ("unsafe transfer") lets loss-tolerant tokens wipe escrow accounting without paying beneficiaries

The reported Solidity issue ("`transfer()` is unsafe, should use `call()` with the return checked") reduces to one broken invariant: **a value-transfer primitive whose failure signal is not actually verified before the ledger is updated as if payment succeeded.** I searched the repo for the concrete local analog of this class in fund-moving code (proof settlement, escrow withdrawal, bandwidth/paymaster payouts) and found a direct match in `IntentGatewayV2.withdraw()`.### Title
Unchecked ERC-20 boolean return in escrow release lets non-reverting ("false-returning") tokens permanently wipe escrow accounting without paying the beneficiary - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's core broken invariant is: *a value-transfer primitive is used without properly validating its success signal before committing the ledger update.* The local analog is in `IntentGatewayV2.withdraw()`, the function that releases escrowed order inputs and transaction fees to a beneficiary on fill, refund, or cancel. For ERC-20 tokens it uses a raw low-level `call` to `IERC20.transfer` and only checks that the *call itself did not revert* — it never decodes/validates the returned `bool` — yet immediately treats the payout as successful and permanently decrements/deletes the escrow accounting. [1](#0-0) 

### Finding Description
`withdraw()` is the single settlement path for all three ways an order resolves: same-chain `cancelOrder`, cross-chain `onAccept` (`RedeemEscrow`/`RefundEscrow`), and `onGetResponse` (cancellation-by-timeout-proof). [2](#0-1) [3](#0-2) 

Inside it, for any escrowed ERC-20 (including the transaction-fee token), the payout is done via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the low-level call reverted or returned normally — it says nothing about the ABI-decoded return value. Per EIP-20, a compliant `transfer()` may legally *return `false`* on failure instead of reverting; several real, non-reverting ERC-20 implementations do exactly this. When such a token is used as an order's input, this call returns `(true, abi.encode(false))`: `success` is `true`, the `if (!success)` guard never fires, and the code proceeds directly to:
```solidity
_orders[body.commitment][token] -= amount;
```
The escrow bookkeeping for `body.commitment`/`token` is wiped even though **no tokens actually moved to `beneficiary`**. The same unchecked pattern is repeated for the transaction-fee redemption a few lines below. [4](#0-3) 

This is exactly the inverse of the correct pattern the contract itself uses on the deposit side, where `SafeERC20`'s `safeTransferFrom`/`safeTransfer` (which decode and require the boolean return, or handle no-return tokens) are used: [5](#0-4) 
So deposits into escrow are protected against non-standard return semantics, but withdrawals out of escrow are not — an inconsistency that mirrors the reported class of bug (unsafe/unverified value-transfer primitive in a fund-moving code path).

Note: the native-ETH branch in the same loop (`beneficiary.call{value: amount}("")`) does not have this specific issue, since there is no analogous "silent false" failure mode for plain value calls; `sent` correctly reflects success. The bug is specific to the ERC-20 branch's failure to validate the ABI return payload.

### Impact Explanation
This directly satisfies the bounty's "stealing or loss of funds" / "wrong beneficiary or amount" criteria on a production bridge escrow contract:
- The order's escrowed tokens remain trapped in `IntentGatewayV2` (the intended beneficiary receives nothing), while `_orders[commitment][token]` is zeroed as if payment succeeded, so the legitimate beneficiary has no further on-chain path to reclaim them (the commitment is already marked filled/refunded and `UnknownOrder` will trip on any retry).
- This is triggerable on the normal, unprivileged happy path — a user or solver simply needs to use (or be assigned, via order composition) a token that returns `false` rather than reverting on transfer failure (e.g., insufficient allowance/edge conditions on certain legacy or non-standard ERC-20s). No malicious relayer, prover, governance actor, or leaked key is required — it is a pure logic/verification-omission bug in the contract's own settlement code.
- It affects the two most security-critical settlement events of the Intents system: `RedeemEscrow` (paying a solver/filler) and `RefundEscrow`/cancellation (returning a user's own escrowed funds).

### Likelihood Explanation
Likelihood is moderate-to-high in production: `IntentGatewayV2` is designed to support arbitrary ERC-20 `TokenInfo.token` inputs supplied by order creators, and nothing in `placeOrder` restricts inputs to a token allowlist. Any deployment or future listing of a non-standard/legacy ERC-20 that returns `false` instead of reverting (a well-known, non-exotic category of tokens) reaching this code path will trigger the silent-failure/fund-loss condition deterministically, every time that token is used for an order's inputs.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the per-token loop and the transaction-fee payout) with `SafeERC20.safeTransfer`, consistent with how deposits already use `safeTransferFrom` elsewhere in the same contract. `SafeERC20` correctly reverts on both a failing low-level call *and* a decoded `false` return value (and tolerates tokens with no return value), closing the silent-failure gap before `_orders[...]` accounting is mutated.

### Proof of Concept
1. Deploy/select an ERC-20 token whose `transfer(to, amount)` returns `false` on failure instead of reverting (a real, known category of non-compliant tokens).
2. Call `placeOrder` escrowing that token as an input, with a same-chain order (source == destination) so cancellation resolves locally.
3. Construct conditions so the token's internal `transfer` call inside `withdraw()` fails (e.g., a blocklist/pausable variant, or an edge-case balance/allowance condition specific to that token's implementation) while still returning `false` rather than reverting.
4. Call `cancelOrder` (or have the corresponding `RedeemEscrow`/`RefundEscrow` cross-chain message delivered) to invoke `withdraw()`.
5. Observe: `token.call(...)` returns `(true, abi.encode(false))` → `success == true` → guard does not fire → `_orders[commitment][token] -= amount` executes → `EscrowRefunded`/`EscrowReleased` is emitted — yet the beneficiary's token balance never increased. The tokens remain stuck in `IntentGatewayV2` with no accounting path left to recover them for that beneficiary.

**Note on confidence/uncertainty:** I was not able to fully trace whether `SweepDust` (governance-only) could later recover these stranded tokens, nor whether any off-chain/allowlist policy in production restricts input tokens to strictly-reverting ERC-20s — that policy detail lives outside the indexed contract code and could not be verified here. The core code-level defect (unchecked ABI return value gating a permanent ledger update) is confirmed directly from the source shown above.
