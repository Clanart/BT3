### Title
`distribution` precompile's `rewards()` view accepts value with no non-payable check, stranding sent usei/wei with no withdraw path - (File: precompiles/distribution/distribution.go)

### Summary
The `distribution` precompile's `Execute` dispatcher calls every other state-changing/query method through a `ValidateNonPayable(value)` guard (or an equivalent `HandlePaymentUseiWei`/`HandlePaymentUsei` refund step), but `RewardsMethod` is dispatched directly to `p.rewards(ctx, method, args)` with no such check and no payment handling.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute` explicitly enforces non-payability or refunds for every other branch, e.g. `WithdrawValidatorCommissionMethod` calls `pcommon.ValidateNonPayable(value)` before proceeding, and value-accepting methods route through `pcommon.HandlePaymentUseiWei`/`HandlePaymentUsei`, which immediately sends the transferred usei/wei back from the precompile's Sei address to the payer before doing the "real" work. [1](#0-0) [2](#0-1) 

But `RewardsMethod` skips this entirely — `return p.rewards(ctx, method, args)` is called with `value` completely ignored, and `rewards()` (a pure query) never calls `HandlePaymentUsei`/`HandlePaymentUseiWei` to refund the caller. This is confirmed by the repo's own precompile integration test comment: "rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)". [3](#0-2) [4](#0-3) 

The precompile itself is backed by a real `sdk.AccAddress` (derived via `GetSeiAddressOrDefault(ctx, p.address)`), and other flows explicitly move the transferred usei/wei out of that address using `bankKeeper.SendCoinsAndWei`/`SendCoins` as part of "refund the payer because the following precompile logic will debit the payments from payer's account". [5](#0-4) 
Since `rewards()` never performs this refund, any usei/wei attached to a `rewards(address)` call is transferred into the precompile's account by the underlying usei/wei StateDB bridge and never sent back — the precompile address has no keeper-level or user-level withdraw path for accidentally received funds (unlike a normal contract, it isn't a bytecode contract a user can add a withdraw function to; it's a fixed hardcoded system address at `0x0000...1007`). [6](#0-5) 

This exact bug class (a payable/receivable entry point with no corresponding way to reclaim value) directly matches the reported `MarginTrading.sol` issue, transposed onto a Sei precompile's dispatch table.

### Impact Explanation
Any unprivileged EVM caller (EOA or contract) invoking `rewards(address)` on the distribution precompile (`0x0000000000000000000000000000000000001007`) with non-zero `msg.value` will have that value permanently stuck at the precompile's associated Sei address, since there is no mechanism (no other precompile method, no governance action visible in this code) to sweep or return it. This is a permanent freezing of user funds — funds loss for the caller and effectively “orphaned” native tokens that never reappear in circulation for any account.

### Likelihood Explanation
Likelihood is low-to-moderate: this requires a caller to mistakenly (or through a buggy integrating contract) attach value to a `staticcall`/`call` to a view-only method. Since Solidity `view`/non-payable ABI wrappers normally block `msg.value`, exploitation would most likely occur through raw low-level calls (e.g. `address(distr).call{value: x}(abi.encodeWithSelector(...))`) or misconfigured integrator contracts that forward value indiscriminately. It's not attacker-profitable (no unauthorized transfer occurs, only self-inflicted stranding of the caller's own funds), but it is trivially reachable by any public-RPC client or CosmWasm/EVM contract that sends value with the call.

### Recommendation
Add the same `pcommon.ValidateNonPayable(value)` guard used by `WithdrawValidatorCommissionMethod` (and all other non-payment methods) to the `RewardsMethod` case in `Execute`, rejecting any non-zero `value` before dispatching to `p.rewards`. Alternatively, if some future design intentionally wants `rewards()` payable, route the value through `pcommon.HandlePaymentUseiWei` so it is immediately refunded to the caller, consistent with every other precompile method.

### Proof of Concept
1. Deploy or use an existing contract with a helper that performs a raw call: `address(0x0000000000000000000000000000000000001007).call{value: 1e18}(abi.encodeWithSignature("rewards(address)", delegatorAddr))`.
2. The call succeeds and returns the expected `Rewards` struct (per `RewardsMethod` dispatch with no payable guard). [2](#0-1) 
3. Query the bank balance of the Sei address mapped to the distribution precompile (`p.address`) — the sent usei/wei now sits there permanently, since no other flow debits/refunds it back to the sender.
