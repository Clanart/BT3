### Title
SignableTransaction computes weight and required fee on a simulated transaction that omits the OP_RETURN data output — (`File: networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` builds a simulated transaction inside `calculate_weight_vbytes` to determine the transaction weight/vbytes, and uses that simulated result as the actual `needed_fee` and for the `TooLargeTransaction` policy check. However the simulation only includes `payments` (and optionally `change`) as outputs — the OP_RETURN output carrying `data`, which was already pushed to `tx_outs`, is omitted. The provisional value is then committed as the real value, exactly mirroring the reported bug class (a simulated quantity computed for one purpose is reused as the real quantity for a downstream state update/fee accounting).

### Finding Description
At `networks/bitcoin/src/wallet/send.rs`, the data output is appended to `tx_outs` (lines ~194-202) **before** the weight is computed:

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ... });
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (lines 62-127) reconstructs a stand-in `Transaction` whose `output` vector is built only from `payments` plus an optional `change` script — it never receives `tx_outs`, so the OP_RETURN output is absent from the simulated transaction. The same omission applies on the change path (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`, line ~225), so `fee_with_change` also ignores the data output's weight.

The resulting `vbytes`/`weight` are then used as if they described the real transaction:
- `needed_fee = fee_per_vbyte * vbytes` (line ~206) — stored and later returned by `needed_fee()`, and used to size the change output (`input_sat - payment_sat - fee_with_change`, line ~228).
- `weight > MAX_STANDARD_TX_WEIGHT` check (line ~241) — the real serialized transaction is heavier than the checked `weight`.
- `TooLowFee` check (line ~211) is evaluated against the understated `vbytes`.

This is the same root cause as the external report: a value derived from a hypothetical/simulated state is stored and consumed as the real value elsewhere, instead of computing the actual value separately.

### Impact Explanation
- The transaction pays `fee_per_vbyte * vbytes(simulated)` as the intended fee while its real vsize is larger by the OP_RETURN output's size (up to 80 bytes payload plus output overhead, ~11-22 vbytes), so the realized fee rate is strictly lower than the requested one. The processor's `prepare_send`/`needed_fee` accounting (which relies on `needed_fee()` and on `fee()` for change calculations) therefore misestimates the actual feerate.
- The `MAX_STANDARD_TX_WEIGHT` gate can be bypassed by the uncounted data output, allowing a transaction to be produced and signed that exceeds standardness limits and will be rejected by relay — the threshold network then signs a transaction that cannot be broadcast.
- The `data` field originates from payment/burn instructions carrying output data (e.g. `OutInstruction` data / OP_RETURN payloads), i.e. transaction data an unprivileged counterparty can cause to be constructed and signed. A user who attaches maximal data lowers the effective feerate of a protocol transaction, degrading confirmation reliability of multisig spends.

### Likelihood Explanation
Any scheduled payment carrying a `data` payload exercises this path; the miscalculation is deterministic whenever `data.is_some()`. The magnitude is bounded by the 80-byte `TooMuchData` cap, so the fee understatement is small per transaction — consistent with Medium severity (incorrect fee/weight accounting, potential relay rejection, no direct key or signature compromise).

### Recommendation
Pass the already-built `tx_outs` (or at least the data output) into `calculate_weight_vbytes` so the simulated transaction matches the real one. Concretely, compute weight/vbytes from `tx_outs` itself:

```rust
fn calculate_weight_vbytes(
  inputs: usize,
  outputs: &[TxOut],
  change: Option<&ScriptBuf>,
) -> (u64, u64)
```

pushing a zero-valued change `TxOut` when simulating the change case, and recompute on the final output set rather than on `payments` alone. Alternatively, compute the weight once from the fully constructed `tx` before returning the `SignableTransaction`, and derive `needed_fee` from that actual weight.

### Proof of Concept
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs):

1. `tx_outs` gains an OP_RETURN `TxOut` (lines ~194-202).
2. `calculate_weight_vbytes` is invoked with `payments`, not `tx_outs` (line ~204); its simulated `Transaction.output` (lines ~85-99) contains only payment outputs (+ optional zero-value change), never the OP_RETURN.
3. `needed_fee` is set from that understated `vbytes` (line ~206) and stored in the returned `SignableTransaction` (line ~254); the change output is sized using `fee_with_change` which suffers the same omission (lines ~225-233).
4. The returned `tx` (lines ~246-251) contains the extra OP_RETURN output, so `self.tx.weight()` exceeds the `weight` used for the `TooLargeTransaction` check and `fee()` reflects a lower effective feerate than `fee_per_vbyte`.

A test asserting `tx.weight()` equality with the simulated weight, or `needed_fee == real_vsize * fee_per_vbyte`, fails whenever `data` is non-empty — e.g. `SignableTransaction::new(inputs, &payments, change, Some(vec![0; 80]), FEE)` yields a real transaction ~90 weight units (~22 vbytes) heavier than the value `needed_fee` was derived from, whereas the existing test at `networks/bitcoin/tests/wallet.rs:269` only passes because it uses `data: None`.

Caveat: I verified this against `send.rs` directly; I did not trace every upstream caller of the `data` parameter within `processor/` to fully enumerate which external instructions populate it, though `prepare_send`/`Plan` payment data is the documented path.
