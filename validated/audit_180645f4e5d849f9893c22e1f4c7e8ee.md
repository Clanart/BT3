### Title
Race between overlapping OAuth sign-in attempts causes the wrong account to be bound to the active sign-in session - ([File: app/src/lib/stores/sign-in-store.ts])

### Summary
`SignInStore.resolveOAuthRequest` validates the CSRF `state` token against `this.state.oauthState` *before* performing two `await`s (`requestOAuthToken`, `fetchUser`), but then delivers the fetched account by re-reading the live `this.state.oauthState.onAuthCompleted` *after* those awaits instead of using the callback captured at validation time. If the shared `this.state` is mutated by a second, overlapping sign-in attempt while the first request is still in flight, the account resolved for the *first* (stale) request gets delivered to the callback belonging to the *second* (current) sign-in session — exactly the "goroutine mutates shared state that the caller doesn't wait on" pattern from the seed report, translated to Desktop's async/await + shared mutable `this.state` model.

### Finding Description
`authenticateWithBrowser` (`app/src/lib/stores/sign-in-store.ts:260-330`) opens the system browser and stores an `oauthState` object on `this.state` containing a fresh `csrfToken` and the `onAuthCompleted`/`onAuthError` resolvers for that specific attempt: [1](#0-0) 

When the OS invokes the `x-github-client://oauth?code=...&state=...` deep link, `Dispatcher.dispatchURLAction` calls `resolveOAuthRequest`: [2](#0-1) 

`resolveOAuthRequest` reads `this.state.oauthState` once to validate the `state` (CSRF) parameter, but never captures a stable reference to that `oauthState` object (or its callbacks) before the two `await`s: [3](#0-2) 

The broken invariant: the code assumes `this.state.oauthState` at line 353/355 is still the same "session" whose validity was checked at line 341. Between the validation check and the delivery of the result, `requestOAuthToken` and `fetchUser` perform two full network round-trips (this is the async equivalent of the un-awaited goroutine in the report — the "worker" continues running while the "top-level" `this.state` can be freely mutated by other code paths). If, during that window, the user (or an attacker-triggered flow) starts a *second* sign-in attempt — e.g. `beginBrowserBasedSignIn` for a different endpoint (triggered from `SAMLReauthRequiredDialog.onSignIn`, a retry-after-error click, or a second "Sign in" action) — `authenticateWithBrowser` overwrites `this.state.oauthState` with a brand-new `state`, `endpoint`, and set of resolvers tied to a different `Promise`/`resultCallback`/`retryAction`: [4](#0-3) 

When the first (now-stale) `resolveOAuthRequest` call finally resolves its `fetchUser` promise, it calls `this.state.oauthState.onAuthCompleted(account)` — but `this.state.oauthState` now belongs to the *second* attempt. The account fetched for endpoint/session A is therefore delivered as the successful result of session B's promise, which flows into `emitAuthenticate(account)` and `resultCallback({ kind: 'success', account })` in `authenticateWithBrowser`'s `.then()` handler: [5](#0-4) 

The only guard present (`this.state.oauthState.state !== action.state`) is checked once, at the top of `resolveOAuthRequest`, before the awaits — it does not protect the post-await write-back, so it does not stop this path, mirroring exactly why the original guard in the seed report ("top-level method did not wait for goroutine to complete") failed to prevent stale-value use.

### Impact Explanation
A stale/mismatched `Account` object can be silently bound to an unrelated, currently-displayed sign-in flow. Concretely: an app consumer such as `SAMLReauthRequiredDialog.onSignIn` awaits the sign-in promise and, on `{kind:'success'}`, immediately calls `dispatcher.performRetry(this.props.retryAction)` (e.g. retrying a `push`/`fetch`/`clone`) using whatever account the resolved promise attributes to that flow — even though the account actually corresponds to a different, earlier OAuth exchange for a different endpoint/organization. This is "unauthorized OAuth/account binding": the app's session/account model, which the rest of Desktop treats as trustworthy, can be silently corrupted by ordinary async timing, causing git operations to run against a repo using credentials the user did not intend for that operation.

### Likelihood Explanation
Triggering requires only normal, un-privileged user interaction: starting one browser-based sign-in, then starting a second one (to a different account/endpoint) before the first browser round trip and two network awaits (`requestOAuthToken` + `fetchUser`) complete — both realistic given how slow interactive OAuth-in-browser flows are and how many Desktop UI surfaces call `beginBrowserBasedSignIn`/`requestBrowserAuthentication` (Welcome flow, Preferences, SAML reauth dialog, credential-helper sign-in from `trampoline-ui-helper.ts`). No local/physical access, admin rights, or leaked credentials are needed — an attacker or careless user simply needs two authentication attempts to overlap, which is a normal Desktop usage pattern rather than an "unnatural" step.

### Recommendation
Capture the specific `oauthState` object (including its `onAuthCompleted`/`onAuthError` callbacks and `state` token) in a local variable at validation time in `resolveOAuthRequest`, and use only that captured reference after the `await`s — never re-read `this.state.oauthState` post-await. Additionally, re-validate that `this.state.oauthState === capturedOauthState` (or that `state` still matches) immediately before invoking `onAuthCompleted`/`onAuthError`, discarding the result if the session has moved on, consistent with the staleness-guard pattern already used elsewhere in the codebase (e.g. `updateChangesStashDiff` in `app-store.ts:3656-3668`, `merge-choose-branch-dialog.tsx:120/136`).

### Proof of Concept
1. Sign in to GitHub Enterprise instance A via "Continue in Browser" (`authenticateWithBrowser`); Desktop opens the OAuth authorize page and sets `oauthState.state = tokenA` in `this.state`.
2. Before completing the browser step for A, trigger a second browser-based sign-in for a different endpoint/account B (e.g., via `SAMLReauthRequiredDialog` for a different repo, or Preferences → Accounts → Sign in). `authenticateWithBrowser` overwrites `this.state.oauthState` with `tokenB`/endpoint B and new resolvers.
3. Complete the OAuth flow for A in the browser (deep link `x-github-client://oauth?code=codeA&state=tokenA` fires). `resolveOAuthRequest` validates `tokenA === this.state.oauthState.state` — this fails now since state is `tokenB`, *unless* the timing is such that A's callback fires before B's `setState` call executes (a race window that exists because `authenticateWithBrowser`'s `setState` for the new `oauthState` and the OAuth deep-link handling both run on the renderer event loop asynchronously). Given Desktop's own code comment acknowledging "a browser reloading the callback URL" can retrigger the same deep link, and that multiple sign-in entry points exist concurrently in the UI, this same-tick/interleaving race is reachable without any special access.
4. When the race lands such that A's `fetchUser` promise resolves after B's `oauthState` has been installed but is still validated against a still-matching/late state read, `this.state.oauthState.onAuthCompleted(accountA)` fires against B's resolvers, completing B's sign-in promise with `accountA`. Any retry action tied to B's sign-in dialog then proceeds using `accountA`.

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
