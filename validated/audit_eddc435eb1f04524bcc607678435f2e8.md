## Analysis

The Notional bug is about a function that accepts a caller-supplied parameter that is supposed to protect the caller's expected outcome, but the parameter is discarded/hardcoded, letting value leak away to someone other than the intended party. The closest concretely provable local analog in Hyperbridge is not a slippage bound at all — it's a swap-wrapper contract that is deployed and documented as a **drop-in `IUniswapV2Router02` implementation** for the intent-gateway's calldata execution flow, but which silently ignores the `to`/recipient argument that callers rely on to route swap output to the correct beneficiary.

### Title
GnosisUniswapV2Interface.swapETHForExactTokens ignores the recipient parameter, diverting order/beneficiary funds to the CallDispatcher - (evm/src/utils/uniswapv2/GnosisUniswapV2Wrapper.sol)

### Summary
`GnosisUniswapV2Interface` is deployed on Gnosis Chain as the canonical `UniswapV2Router02`-compatible address (`UniswapV2 (Gnosis Wrapper)` in the contract-address registry) used by `IntentGatewayV2` predispatch/postdispatch calldata and by `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution flows documented to call `IUniswapV2Router02.swapETHForExactTokens(amountOut, path, recipientAddress, deadline)`. On Gnosis, `swapETHForExactTokens` takes the same four-parameter signature but discards `path` and `recipient` entirely and unconditionally credits the wrapped native asset to `msg.sender` instead of the caller-specified recipient. [1](#0-0) 

### Finding Description
The documented calldata-execution pattern for cross-chain swaps builds a `Call` that targets the router-compatible address with a `recipientAddress` distinct from the calling contract (the `CallDispatcher`), matching real UniswapV2 semantics where the router sends output tokens to the `to` argument regardless of `msg.sender`: [2](#0-1) 

These calls are executed via `CallDispatcher.dispatch()`, so `msg.sender` inside the target contract is always the `CallDispatcher`, not the beneficiary: [3](#0-2) 

On Gnosis Chain, the deployed "router" is not the real Uniswap contract but `GnosisUniswapV2Interface`. Its `swapETHForExactTokens` signature matches `IUniswapV2Router02` exactly (`amountOut, path, address, deadline`) but the last three parameters are unnamed/unused, and the wrapped token is sent to `msg.sender` — i.e., to the `CallDispatcher` — instead of the `recipient` argument the caller supplied: [1](#0-0) 

`CallDispatcher.dispatch()` only validates that the target has code and that the low-level call succeeds; it has no way to verify that the call actually paid the intended beneficiary. `IntentsBase._execute()` (the postdispatch handler) subsequently only sweeps balances of tokens explicitly listed in `order.output.assets` back to the gateway as protocol "dust" — it never reconciles whether the beneficiary was actually paid: [4](#0-3) 

So any order/message that follows the documented pattern — using the router-interface call with a distinct `recipientAddress` — silently misroutes the swap proceeds to the `CallDispatcher`. If the resulting token happens to be one of `order.output.assets`, that balance is swept away as protocol dust (permanent loss of the beneficiary's funds to the protocol treasury); if it is not swept, the funds are stranded in the `CallDispatcher` with no beneficiary-specific recovery path.

### Impact Explanation
This is a direct, unauthorized diversion of user funds during a documented, expected usage flow of the intent-gateway/HFT calldata-execution feature on Gnosis Chain: an unprivileged user or solver who builds an order/message exactly as the official documentation instructs will have the swap output routed away from the intended beneficiary, either being consumed as protocol dust or permanently stranded. This is "loss of funds" / "unauthorized transaction/execution outcome" under the bounty's accepted impact classes — no malicious relayer, prover, or governance actor is required; it's triggered purely by using the documented API on the affected chain.

### Likelihood Explanation
High for any integrator (user, solver, or dApp) on Gnosis Chain following the officially documented calldata pattern for `swapETHForExactTokens`, since the wrapper's function signature is indistinguishable from the real Uniswap V2 router ABI and there is no revert or error signaling the mismatch — the call succeeds, just with the wrong recipient.

### Recommendation
Make `GnosisUniswapV2Interface.swapETHForExactTokens` (and `swapExactTokensForETH`, which is already correct, for consistency) honor the `to` parameter for `swapETHForExactTokens` by transferring the wrapped token to the supplied recipient instead of `msg.sender`, or, if wrap-only behavior to `msg.sender` is intentional, update its ABI/name so it cannot be silently substituted for the real `IUniswapV2Router02` interface in calldata built against the documented pattern. Add a test asserting `recipient != msg.sender` still receives funds correctly.

### Proof of Concept
1. On Gnosis Chain, construct an `Order`/HFT message whose `output.call` (or bridged calldata) contains a `Call` to the registered `UniswapV2 (Gnosis Wrapper)` address, encoding `swapETHForExactTokens(usdcAmountOut, path, recipientAddress, deadline)` with `recipientAddress` set to the end beneficiary — exactly per the documented pattern.
2. `IntentsBase._execute()` dispatches this call through `CallDispatcher.dispatch()`, so `msg.sender` in the wrapper is the `CallDispatcher`.
3. `GnosisUniswapV2Interface.swapETHForExactTokens` ignores `recipientAddress` and transfers the wrapped token to `msg.sender` (the `CallDispatcher`) instead.
4. If the token is listed in `order.output.assets`, `_execute()`'s dust-sweep logic collects the balance from the `CallDispatcher` into the gateway as protocol dust — the beneficiary receives nothing despite the order/message appearing fully executed.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata, address, uint256)
        external
        payable
        returns (uint256[] memory)
    {
        if (amountOut > msg.value) revert MsgValueLessThanExactAmount();

        (bool sent,) = WETH().call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IERC20(WETH()).safeTransfer(msg.sender, msg.value);

        uint256[] memory out = new uint256[](1);
        out[0] = msg.value;
        return out;
    }

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
