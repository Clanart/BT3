### Title
Attacker can dust the vault with uneconomical outputs that `Scanner` reports as received but `SignableTransaction` cannot profitably spend, DoS-ing transaction construction - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Joyn finding where an attacker dusts the royalty vault with `1 wei` so every subsequent token transfer computes a `platformShare` of `0` and reverts, an unprivileged Bitcoin attacker can send arbitrarily small (even 1-satoshi) outputs to the vault's P2TR `script_pubkey`. `Scanner::scan_transaction` returns every output whose `script_pubkey` matches, with no minimum-value or economic-viability filter. These dust outputs are reported as `ReceivedOutput`s — funds received — yet each one costs more in fee weight (~57 vbytes × `fee_per_vbyte`) than it contributes, so including them in `SignableTransaction::new` either inflates `needed_fee` beyond their value or tips the aggregate check into `TransactionError::NotEnoughFunds`, blocking the core send operation until they are manually excluded.

### Finding Description
`Scanner` registers the vault's `p2tr_script_buf` and returns a `ReceivedOutput` for every matching output in a scanned transaction, with no value threshold: [1](#0-0) 

`SignableTransaction::new` then unconditionally consumes all supplied inputs and prices each at ~57 vbytes of fee (`230 WU` per the commentary in `processor/src/networks/bitcoin.rs`), while crediting only `input.output.value` toward `input_sat`: [2](#0-1) 

The only dust check in the wallet is on *outgoing payments* (`*amount < DUST → DustPayment`), never on received inputs: [3](#0-2) 

So a 1-sat input adds ~57·`fee_per_vbyte` to `needed_fee` while adding 1 sat to `input_sat`. At any `fee_per_vbyte ≥ 1`, the input is net-negative; once enough dust accumulates, `input_sat < payment_sat + needed_fee` triggers `NotEnoughFunds`, or the input count pushes `weight > MAX_STANDARD_TX_WEIGHT` → `TooLargeTransaction` (`send.rs:241`), halting the signing machine exactly like the Joyn zero-transfer revert halted token transfers. Both bugs share the same root cause: a permissionless dust deposit is allowed to degrade a per-operation calculation until the core operation fails, with no threshold/gating and no failsafe (the Joyn fix — a `MIN_ROYALTY_AMOUNT`-style threshold — maps directly to a missing `MIN_OUTPUT_VALUE` on scanned inputs).

### Impact Explanation
- **Griefing / liveness:** an attacker can flood the vault address with sub-546-sat (or more generally, below-marginal-fee) outputs. Any consumer that feeds scanned outputs into `SignableTransaction::new` hits `NotEnoughFunds`/`TooLargeTransaction` and cannot construct transactions until dust is manually filtered — the same operational manual-management cost as the Joyn report.
- **Funds reported received that are not spendable:** `scan_transaction` reports dust outputs as `ReceivedOutput`s, yet spending a v-sat input costs ~57·`fee_per_vbyte` sat; for `v < 57·fee_per_vbyte` the output is economically unspendable, so reported balance is not realizable.
- No secret/key material is required — only sending standard Bitcoin transactions to a public address.

### Likelihood Explanation
The attack requires only broadcasting ordinary transactions to the vault's `script_pubkey`, which is publicly derivable from the group key. Cost is bounded by the dust outputs' value (sub-dust amounts are nearly free; even ~546-sat outputs cost little), and deposits persist on-chain permanently, so the attack is lazy like the Joyn bot — no front-running needed. The in-scope wallet crate performs no input-side dust filtering, so reachability does not depend on any caller behavior beyond using scanned outputs as inputs, which is the intended flow (`multisig()` verifies `prevouts[i].script_pubkey` matches the offset key at `send.rs:273-285`).

### Recommendation
Apply the Joyn mitigation pattern: introduce a minimum-input threshold. Concretely:
- In `Scanner::scan_transaction` (or `ReceivedOutput` construction), skip outputs with `output.value.to_sat() < MIN_OUTPUT_VALUE` (e.g., the marginal spend cost `57 * assumed_fee_per_vbyte`, or the `DUST` constant), so dust is never reported as received.
- In `SignableTransaction::new`, additionally reject (or filter) inputs whose value is below their marginal fee contribution, so an unfiltered dust output degrades gracefully instead of erroring the whole transaction.

### Proof of Concept

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
