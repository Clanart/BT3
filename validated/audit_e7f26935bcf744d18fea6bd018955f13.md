### Title
OP_RETURN data output excluded from weight/fee calculation, overpaying change and underpaying the fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the transaction weight and required fee via `calculate_weight_vbytes`, which only models the payment outputs and an optional change output. The OP_RETURN output carrying `data` — pushed into `tx_outs` before the weight is calculated — is never included in the size estimate. When a change output is produced, its value is `input_sat - payment_sat - fee_with_change`, so the omitted OP_RETURN weight directly inflates the change amount: the transaction "refunds" itself sats that should have gone to the fee, and the real fee rate is lower than the `fee_per_vbyte` the caller committed to. This is the same accounting-inconsistency class as the referenced finding: funds are accounted for under one model (no data output) while being spent under another (data output present).

### Finding Description
`calculate_weight_vbytes` builds a dummy `Transaction` whose `output` list is `payments` plus optional `change`; it has no `data` parameter at all. In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` at lines 194-202, then the weight/fee are computed at lines 204 and 225-232 against `payments`/`change` only. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` underestimates the true required fee by roughly `(len(data) + ~11 bytes) * fee_per_vbyte` sats.
- If `change` is `Some`, the change output is `input_sat - payment_sat - fee_with_change`, crediting ~`(data_len * fee_per_vbyte)` extra sats to change while the on-chain fee is `fee_with_change` — a mispriced refund of the remainder, structurally identical to refunding `original_amount - amount_in` after only `amount_in` was actually consumed.
- The `TooLowFee` check at line 211 uses the same underestimated `vbytes`, so a transaction can pass the min-relay-fee check while its actual fee rate is below `DEFAULT_MIN_RELAY_TX_FEE` once the OP_RETURN bytes are counted. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation
The multisig signs a Taproot key-spend committing to all prevout values and all outputs (`Prevouts::All`, `TapSighashType::Default`), so the produced transaction is valid but carries a fee rate lower than requested — potentially below the minimum relay fee, making it unbroadcastable or leaving it stuck indefinitely while the inputs remain locked. The excess sats are diverted into the change output rather than paid as the committed fee. Any caller attaching arbitrary `data` (e.g., instruction data embedded in a refund/forward transaction) can produce a signed transaction whose economics differ from what `fee_per_vbyte` specified — the protocol over-refunds change and underpays miners, and cannot reconcile the discrepancy because `fee()` reports `sum(inputs) - sum(outputs)` which matches the incorrectly computed `needed_fee`.

### Likelihood Explanation
The bug triggers deterministically whenever `data.is_some()` — there is no race or attacker luck involved. Whether the resulting transaction falls below relay minimums depends on `fee_per_vbyte` and the data length; at high fee rates the absolute sats misdirected to change grow linearly with the data payload (up to the 80-byte limit). Reachability requires a caller able to cause a `SignableTransaction` to be built with a `data` payload, which occurs for networks embedding arbitrary instruction data.

### Recommendation
Include the OP_RETURN output in the weight estimate. The simplest fix is to compute `tx_outs` (including the data output and the script_pubkey sizes) before calling `calculate_weight_vbytes`, and pass the full output list — or extend `calculate_weight_vbytes` to accept the optional data length so `vbytes`, `needed_fee`, `fee_with_change`, and the change value all account for it. Alternatively, after building `tx`, recompute the actual vsize and verify `fee() >= fee_per_vbyte * actual_vsize` as a sanity check.

### Proof of Concept
```rust
// Conceptual: one input of 100_000 sats, payment of 50_000, change, 60-byte data,
// fee_per_vbyte = 10.
let data = vec![0u8; 60];
let tx = SignableTransaction::new(
    vec![input],                              // 100_000 sats
    &[(payment_script, 50_000)],
    Some(change_script),
    Some(data),
    10,
).unwrap();

// vbytes is computed WITHOUT the ~71-byte OP_RETURN output.
// fee_with_change is ~710 sats too low; the change output is ~710 sats too high.
// Actual signed tx is ~71 vbytes larger than assumed, so the effective
// fee rate is ~10 * vbytes_estimated / vbytes_actual < 10 sat/vB.
// If fee_per_vbyte was chosen at/near min relay, the real rate can fall below
// DEFAULT_MIN_RELAY_TX_FEE and the signed transaction will not propagate.
```
The existing test `test_data` in `networks/bitcoin/tests/wallet.rs` constructs exactly this configuration (data + change) but never asserts the achieved fee rate against the actual serialized size, which is why the discrepancy is unobserved.
