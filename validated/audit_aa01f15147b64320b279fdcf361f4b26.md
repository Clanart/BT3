## Confirmed Desktop analog

This confirms the analogous broken invariant: `git submodule update --init --recursive` (and equivalently LFS/hooks) is run automatically by Desktop after clone/fetch/pull/checkout [1](#0-0) , using the trampoline credential helper that hands out real account tokens based purely on hostname matching via `findGitHubTrampolineAccount`, which only compares URL `origin` [2](#0-1)  with no check that the URL corresponds to the repository the user actually opened or a remote they configured.

### Title
Attacker-controlled `.gitmodules` URL causes silent credential handoff to unrelated GitHub/GHE repositories via the trampoline credential helper - (File: app/src/lib/trampoline/find-account.ts, app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` runs `git submodule update --init --recursive` automatically after clone/pull/checkout/fetch [3](#0-2) . Submodule URLs come from the untrusted repository's `.gitmodules` file. When git needs credentials for any of these attacker-supplied URLs, it invokes Desktop's credential helper trampoline, which resolves the account to use with `findGitHubTrampolineAccount`, matching solely on URL `origin` (scheme+host) against the user's stored accounts [2](#0-1) . If a match is found, the real account token is attached and handed back to git [4](#0-3) .

### Finding Description
The credential-handling invariant that should hold is: "only supply this user's GitHub/GHE credentials for repositories/URLs the user has explicitly configured as a remote for a repository they opened." Instead, the check is reduced to a hostname equality test [5](#0-4) , exactly mirroring the `buyLoan()` flaw where a caller-supplied identifier (`poolId`) is trusted to authorize an action against someone else's resource without verifying the caller is entitled to that identifier.

Because submodule URLs are read from `.gitmodules`, an attacker who controls a public/cloneable repository can add a submodule (or nested submodule, since `--recursive` is used) pointing to `https://github.com/<any-org>/<any-private-repo>.git` or, for Enterprise users, `https://github.mycompany.com/...`. When the victim clones/pulls/checks out this malicious repository, Desktop:
1. Automatically triggers `git submodule update --init --recursive` [3](#0-2) .
2. Git contacts the attacker-chosen host/path for that submodule and asks Desktop's trampoline for credentials.
3. `getEndpointKind`/`findGitHubTrampolineAccount` only checks that the *host* of that URL matches an account endpoint (`github.com`, or a configured GHE endpoint) — not that the specific repo path was ever authorized or requested by the user [6](#0-5) .
4. Desktop supplies the user's real OAuth token, allowing git to authenticate and fetch content from a private repository the attacker named but the victim never intended to access, entirely from a routine clone operation on an unrelated (possibly public) repository.

Existing guards do not stop this path: there is no verification against the currently-open repository's own registered remotes, no user prompt confirming a *new* host/path is being contacted with stored credentials, and `getGitHubCredential`/`getEndpointKind` treat any GitHub.com/GHE-hostname URL as automatically eligible for the stored token [7](#0-6) .

### Impact Explanation
This lets an attacker who only controls a git repository (no local access, no leaked credentials, no social engineering beyond the victim cloning/pulling a repo — the normal Desktop workflow) cause the victim's real GitHub.com or GitHub Enterprise token to be used to silently fetch and write to disk the contents of a private repository named by the attacker, inside the checkout of the malicious repo. This is unauthorized, silent cross-repository data exfiltration facilitated entirely by Desktop's own automated submodule-update behavior and credential handoff logic — a direct analog of the report's "attacker names someone else's resource identifier and the code trusts it without checking ownership/authorization."

### Likelihood Explanation
Likelihood is Medium: it requires (a) the victim to have a stored account for the targeted host (very common, since most Desktop users are signed in to github.com), (b) the victim to clone/pull/checkout a malicious public repository containing a crafted `.gitmodules`, and (c) the attacker to already know or guess the private repo path they want fetched (they don't get to read the response directly — the fetched content simply lands in the local submodule checkout, which is a real but two-stage exfiltration path requiring an additional step, e.g. a build/postCheckout script in the malicious repo, to actually move that content off the victim's machine).

### Recommendation
Do not authorize the token hand-off purely by hostname. `findGitHubTrampolineAccount`/`getGitHubCredential` should only release stored credentials for submodule/LFS/hook-initiated fetches when the target URL matches (or is scoped to) a remote/path the user has explicitly added to the currently active repository, or the user should be prompted before recursively fetching submodules pointing at previously-unseen repositories, especially cross-organization ones. At minimum, warn/require confirmation before the first automatic `git submodule update --recursive` when new submodule URLs are introduced by a fetch rather than by the user's own commit.

### Proof of Concept
1. Attacker publishes a public repo `evil/repo` with `.gitmodules` containing a submodule pointing to `https://github.com/victim-org/secret-repo.git` (a private repo the victim has access to).
2. Victim (signed in to GitHub.com in Desktop) clones `evil/repo` in GitHub Desktop.
3. Desktop runs `git clone` then automatically calls `updateSubmodulesAfterOperation`, executing `git submodule update --init --recursive` [3](#0-2) .
4. Git requests credentials for `github.com` for the submodule fetch; Desktop's trampoline matches the account by host only [2](#0-1)  and hands back the victim's real token.
5. Git successfully clones `victim-org/secret-repo` into the working directory of `evil/repo`, without any additional prompt, warning, or verification that the victim intended to access that repository.

```typescript
export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
```

```typescript
const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }
```
