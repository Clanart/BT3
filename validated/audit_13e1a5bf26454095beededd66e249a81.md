## Analysis

`escapeGitSpecialCharacters` only escapes `[`, `]`, `!`, `*`, `#`, `?`: [1](#0-0) 

It does not strip or escape newline (`\n`) or carriage-return characters. `appendIgnoreFile` passes the (only partially) escaped path straight into `appendIgnoreRule`: [2](#0-1) 

In `appendIgnoreRule`, for a single string pattern the text is concatenated directly onto the existing (newline-terminated) `.gitignore` contents with no additional sanitization, and for arrays the entries are joined with `\n`: [3](#0-2) 

The path reaching this code comes from the "Ignore file" context-menu action, which passes the raw `WorkingDirectoryFileChange.path` (as produced by the porcelain status parser) straight to the dispatcher: [4](#0-3) [5](#0-4) [6](#0-5) 

GitHub Desktop's status parsing uses `git status --porcelain=2 -z`, i.e. NUL-delimited records, so path fields are passed through raw (unquoted) — meaning a raw embedded `\n` byte in a filename survives intact into `file.path` rather than being C-style escaped the way plain (non `-z`) porcelain output would render it. I was not able to fully re-confirm the exact `status.ts` invocation flags within the remaining tool budget, so this specific claim about `-z` parsing behavior should be independently verified, but it is consistent with the existing status-parser design referenced in `app/src/lib/git/status.ts`.

Given a file whose on-disk name contains a literal newline (e.g. `foo\n*`), because `escapeGitSpecialCharacters` does not neutralize `\n`, the string `foo\n*` is appended as-is to `.gitignore`. Since `formatGitIgnoreContents` guarantees `currentContents` already ends in `\n`, the resulting file becomes:
```
...existing rules...
foo
*
```
i.e., an attacker-controlled extra line (`*`) is silently injected as an independent gitignore rule, distinct from what the user intended ("ignore this one file").

### Title
Newline injection in gitignore entry via unsanitized filename in `appendIgnoreFile` — (File: `app/src/lib/git/gitignore.ts`)

### Summary
`escapeGitSpecialCharacters` (app/src/lib/git/gitignore.ts:103-109) escapes only `[]!*#?` and does not neutralize newline characters. When a repository contains a file whose path embeds a raw `\n` byte, invoking the "Ignore file" context-menu action (`app/src/ui/changes/sidebar.tsx:269-271` → `Dispatcher.appendIgnoreFile` → `appendIgnoreFile`/`appendIgnoreRule` in `app/src/lib/git/gitignore.ts:63-100`) causes the unescaped newline to split the appended text into two separate `.gitignore` lines, letting the part of the filename after the newline become an independent, attacker-chosen ignore rule.

### Finding Description
`appendIgnoreFile` escapes only bracket/glob/negation/comment characters before handing the string to `appendIgnoreRule`, which simply concatenates it onto the (newline-terminated) existing `.gitignore` contents (or `join('\n')`s array entries). Neither function checks for or strips embedded `\n`/`\r` in the input. Because the input originates from a working-directory file path surfaced by git status parsing, an attacker who controls repository content can craft a path containing an embedded newline followed by an arbitrary glob (e.g. `evil\n*`). If such a path ever appears as a file in the user's working tree and the user chooses "Ignore file"/"Ignore folder" on it, the resulting `.gitignore` gains an extra, attacker-chosen line unrelated to the file the user intended to ignore.

### Impact Explanation
A crafted extra rule (e.g. a bare `*`, or a rule targeting specific source files) added to `.gitignore` causes `git status`/commit to silently stop tracking changes to files matching that pattern, without any indication to the user that anything beyond the single selected file was affected. This can result in silent loss of local work being tracked/committed, satisfying the "silent corruption of what the user commits" impact category.

### Likelihood Explanation
Exploitation requires: (1) the attacker's repository/content to place a file with an embedded-newline name in the user's working directory as an untracked (or otherwise "Ignore"-actionable) entry, and (2) the user to explicitly invoke "Ignore file"/"Ignore folder" on that specific entry via the context menu. This is a normal, expected user action (not an unnatural step), but it does depend on the victim noticing and clicking the odd/garbled filename in the Changes list, and depends on the OS/filesystem and git plumbing tolerating an embedded newline in a path end-to-end (tree entry → checkout/creation on disk → status parsing). I could not fully verify within the tool budget whether the app's `git status` invocation (`app/src/lib/git/status.ts`) uses `-z`/NUL-delimited parsing that would let such a raw newline survive unescaped into `WorkingDirectoryFileChange.path`; this should be confirmed against `app/src/lib/status-parser.ts` and the exact `status` command-line flags before treating this as fully proven end-to-end.

### Recommendation
In `escapeGitSpecialCharacters` (or a new pre-filter applied before it in `appendIgnoreFile`), also escape/strip `\n` and `\r` (and reject/normalize any control characters) so a single filename can never inject additional lines into `.gitignore`. Additionally, `appendIgnoreRule` should validate that each pattern is a single line before concatenation, defensively rejecting or escaping any embedded newline regardless of caller.

### Proof of Concept
1. Construct a git tree/commit containing a blob whose path is `evil\n*` (raw newline byte, byte sequence: `e v i l 0x0A *`).
2. Get this path onto disk in the user's working directory as an entry that would appear as untracked/ignorable in GitHub Desktop's Changes list (e.g., via clone/checkout, or by having it appear as `??` in `git status`).
3. In the Desktop UI, right-click that changed-file entry and choose "Ignore file (add to .gitignore)", which calls `sidebar.tsx: onIgnoreFile` → `Dispatcher.appendIgnoreFile` → `gitignore.ts: appendIgnoreFile`/`appendIgnoreRule`.
4. Inspect the resulting `.gitignore`: it will contain two lines — `evil` and `*` — instead of a single escaped entry for the intended filename.
5. Create/modify unrelated tracked files and run `git status --porcelain`; they will now be excluded from status/commit due to the injected `*` rule, demonstrating silent exclusion of legitimate local changes.

export async function appendIgnoreRule(
  repository: Repository,
  patterns: string | string[]
): Promise<void> {
  const text = (await readGitIgnoreAtRoot(repository)) || ''

  const currentContents = await formatGitIgnoreContents(text, repository)

  const newPatternText =
    patterns instanceof Array ? patterns.join('\n') : patterns
  const newText = await formatGitIgnoreContents(
    `${currentContents}${newPatternText}`,
    repository
  )

  await saveGitIgnore(repository, newText)
}

/** Escapes a string from special characters used in a gitignore file */
export function escapeGitSpecialCharacters(pattern: string): string {
  const specialCharacters = /[\[\]!\*\#\?]/g

  return pattern.replaceAll(specialCharacters, match => {
    return '\\' + match
  })
}
