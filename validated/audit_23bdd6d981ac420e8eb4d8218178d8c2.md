Based on the investigation, the codebase already implements substantial hardening for the most obvious analogs of this report (clone path traversal is blocked via `sanitizeCloneName`/`resolveWithin`, submodule updates gate `file://` protocol behind `protocol.file.allow=always`, and OAuth flows validate CSRF `state`). However, one path matches the report's exact broken invariant — an untrusted external input (a clickable deep link) causing the app to silently perform a trusted action (opening/cloning a repository, checking out an attacker-chosen branch, and opening an attacker-chosen file) without any prior "did you mean to do this / confirm the switch" gate, and without any origin check on who invoked it.

### Title
Deep link `x-github-client://openRepo` silently opens/clones attacker-specified repository, branch, and file with no origin check or user confirmation - (File: app/src/lib/parse-app-url.ts)

### Summary
`parseAppURL` parses the `openRepo` deep link action and returns an `IOpenRepositoryFromURLAction` containing an attacker-controlled `url`, `branch`, `pr`, and `filepath`. This is dispatched straight to `dispatchURLAction` / `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts` with no verification of which website or process invoked the protocol handler, and (unlike the OAuth branch, which checks a CSRF `state` token) no confirmation step is interposed before the action is carried out.

### Finding Description
`app/src/main-process/main.ts` registers `x-github-client`, `x-github-desktop-auth`/`x-github-desktop-dev-auth`, and legacy `github-mac`/`github-windows` as OS-level protocol handlers [1](#0-0) . Any webpage, email client, or other app on the system can invoke these via an `<a href="x-github-client://openRepo/...">` link — this is exactly the "attacker controls a...deep link the user clicks" primitive named in the task's Valid Impact list.

When the URL is received (`open-url` on macOS, or parsed out of `argv` on Windows), it is fed directly into `handleAppURL` → `parseAppURL` with no origin or signature check: [2](#0-1) [3](#0-2) .

`parseAppURL` extracts `url`, `branch`, `pr`, and `filepath` straight from the query string with only superficial validation (branch/pr regex checks, `testForInvalidChars`), and no check that the target `url` is even a github.com/GHE host: [4](#0-3) .

The resulting `open-repository-from-url` action is routed by `Dispatcher.dispatchURLAction` to `openRepositoryFromUrl` [5](#0-4)  without any confirmation dialog comparable to the one MetaMask's report asks for. Contrast this with the `oauth` branch of the very same switch statement, which at least validates a CSRF `state` value before proceeding [6](#0-5)  — the `open-repository-from-url` path has no equivalent "is this the chain/session the user expects" check.

This mirrors the MetaMask report's broken invariant precisely: an external, untrusted caller (a dapp in the report, a webpage-triggered protocol handler here) can direct the app to silently perform a state-changing operation (switch chain / open-and-clone a specific repository+branch+file) that the user never explicitly authorized for that specific target, and the app has no notion of "last used repository/remote" to compare against and prompt on divergence — exactly the missing "internal state of the last chain used" + confirmation the report recommends implementing.

### Impact Explanation
While outright directory traversal in the resulting clone path is mitigated by `sanitizeCloneName`/`resolveWithin` [7](#0-6) , the deep link still lets an attacker silently drive the victim's Desktop app to clone an arbitrary remote URL, check out an attacker-chosen branch/PR ref, and open an attacker-chosen `filepath` inside it — all without the app ever asking "do you want to open this repository?" tied to the actual invoking origin. Combined with no host allow-list in `parseAppURL`, this can be used to get a victim to unknowingly clone and open a malicious repository (e.g., one whose `filepath` points at a file crafted to exploit the configured external editor, or simply social-engineer the user once the unexpected repo/file is opened), which the report's underlying class ("no origin check + no user confirmation before exposing state-changing functionality to an untrusted trigger") is meant to prevent.

### Likelihood Explanation
Triggering the flow requires only a single click on a link with the `x-github-client://openRepo/...` scheme, which the OS resolves to GitHub Desktop automatically once the protocol handler is registered — no local access, malware, or leaked credentials are needed, satisfying the "Valid Impact" bar (attacker-controlled link the user clicks). The main blocking factor for real-world impact is that the actual clone/checkout targets a git remote/branch/file, so the payoff depends on what's reachable through those (arbitrary clone URL, branch checkout, and file-open), which is a meaningfully weaker link-based confirmation gap than the fully worked-out MetaMask multi-chain bypass, but the missing-confirmation invariant is the same class of bug.

### Recommendation
Mirror the OAuth handler's CSRF-state pattern for `openRepo`: maintain an internal, signed/opaque token that is only valid for a session initiated from Desktop's own "Open in Desktop" button click-through (similar to how `oauthState.state` is checked in `resolveOAuthRequest`), and require it in the deep link before auto-cloning/opening. Short of that, unconditionally show a confirmation dialog surfacing the resolved remote URL, branch, and file path before performing `openRepositoryFromUrl`, so users can reject unexpected repositories/branches/files the way MetaMask's proposal recommends confirming chain switches.

### Proof of Concept
1. Register/observe that GitHub Desktop has claimed the `x-github-client` protocol (default install behavior) [1](#0-0) .
2. Host a page containing `<a href="x-github-client://openRepo/https://github.com/attacker/evil-repo?branch=main&filepath=payload.txt">Click me</a>`.
3. Victim clicks the link; the OS invokes Desktop, which calls `handleAppURL` → `parseAppURL` → returns `open-repository-from-url` with attacker-supplied `url`/`branch`/`filepath` [8](#0-7) .
4. `Dispatcher.dispatchURLAction` invokes `openRepositoryFromUrl` with no confirmation prompt tied to the click's origin [5](#0-4) , cloning/opening the attacker's chosen repository, branch, and file.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
