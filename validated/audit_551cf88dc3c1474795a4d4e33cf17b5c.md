## Analysis

I found a concrete arithmetic/counting-desync analog to the fee-split bug: `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` matches AI-generated resolutions to conflict-marker blocks purely "by order, not by line number", while `extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` silently **skips malformed conflict-marker blocks** rather than counting them consistently between the two passes. This is the same bug class as the Ramses report: a positional/index-based mapping (`feeProtocol` used as a divisor instead of computing the intended ratio) that silently produces the wrong result when the invariant it depends on (index N always corresponds to slot N) is violated. ### Title
Index-based (not marker-based) splicing of AI conflict resolutions can silently misapply resolved content to the wrong conflict block, corrupting committed code - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
When Copilot resolves merge conflicts, GitHub Desktop extracts each conflict block from the file with `extractConflictHunks`, sends them to the model, and later reassembles the file with `reassembleResolvedFile`, which walks the raw file again and replaces the *i*-th well-formed marker block with `hunkResolutions[i]`. Both passes independently decide, block-by-block, whether a marker sequence counts as "hunk #i". If the two passes ever disagree about which blocks are well-formed conflict blocks, the resolutions array and the marker blocks desynchronize — the model's answer for conflict N gets spliced into the location of a different, unrelated conflict N (or into a location it never analyzed), while `validateResolutionPaths` only checks that the *count* of hunks matches, not their *identity/position*. [3](#0-2) 

### Finding Description
`extractConflictHunks` walks the file and, for each `<<<<<<<` start marker, requires a closing `>>>>>>>` before treating it as a hunk; if none is found it `continue`s and drops that block silently, without emitting an `IConflictHunk` for it. [4](#0-3) 

`reassembleResolvedFile` performs a *separate*, independently-implemented well-formedness check (it requires both a `=======` line AND a `>>>>>>>` line to appear, in that order, before treating a `<<<<<<<` as a real conflict block) using a different scanning algorithm. [5](#0-4) 

These two independent parsers are not guaranteed to agree on every malformed/edge-case input (e.g. multiple `=======` lines inside one block, a `<<<<<<<` block immediately followed by another `<<<<<<<` before any theirs/separator marker, nested/duplicated markers, or a `=======` appearing before any `<<<<<<<` was seen by one parser but treated differently by the other because of how "look-ahead" vs "sequential-collect" differ). An attacker who controls the repository content that gets merged/rebased against (a crafted commit/branch/PR that produces a conflicting file with unusual conflict-marker sequences) fully controls the raw file bytes that both parsers scan. If the count of hunks produced by `extractConflictHunks` (which drives what the model is asked to resolve and what `validateResolutionPaths` checks against) differs in *position* — even while matching in *count* — from what `reassembleResolvedFile` treats as hunk boundaries when splicing, resolution #N from the model gets written into the wrong marker block in the final committed file. `validateResolutionPaths` only enforces `resolution.hunks.length === expectedCount`, not that each hunk corresponds to the same block; there is no guard against this positional mismatch. [6](#0-5) 

This mirrors the Ramses bug precisely: a value (percentage share / hunk index) is used as if it inherently encodes correspondence to the correct counterpart, but the arithmetic/indexing relationship it relies on (division-as-ratio, or "the Nth extracted hunk == the Nth spliced hunk") is not actually guaranteed, and nothing double-checks the result against the original invariant.

### Impact Explanation
The result is silent corruption of what the user commits: content resolved by the AI for one part of a conflicted file (e.g. a security-relevant config value, a dependency version pin, or a code change from a different branch) is spliced into an unrelated conflicted location, or a malformed-but-real conflict block is left with its markers uncounted while a resolution meant for it lands elsewhere. The user then sees a diff that appears "AI-resolved" and may commit and push it without noticing the swap, since the reassembled file has no conflict markers left and looks syntactically plausible. This falls under "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories, and the attacker-controlled input is the conflicted repository content itself (from a git remote/branch the user is merging/rebasing), not anything requiring local/admin access.

### Likelihood Explanation
This requires: (1) the Copilot "resolve conflicts" feature to be used, (2) a maliciously/anomalously formed set of conflict markers to appear in the file being merged (fully attacker-controlled by whoever authored the conflicting branch/commit), and (3) the two independent boundary-detection algorithms in `extractConflictHunks` and `reassembleResolvedFile` to disagree on at least one file. Because the two functions are separately implemented scanners over the same ambiguous marker grammar (nested/duplicate `<<<<<<<`/`=======`/`>>>>>>>` sequences are valid file content, not something Git's own parser fully normalizes before Desktop reads it), such disagreement is plausible for adversarially crafted inputs, though I was not able to execute the code to construct a concrete triggering input in this review — the two implementations were compared by reading, not by running a differential test.

### Recommendation
Replace the "match by order" design with a single shared boundary-detection pass used by both `extractConflictHunks` and `reassembleResolvedFile` (i.e., extract hunks once, keep marker line offsets, and splice using those exact offsets rather than re-scanning the file a second time with a different algorithm). Alternatively, have `extractConflictHunks` return the marker boundaries (start/separator/end line indices) as part of `IConflictHunk`, and have `reassembleResolvedFile` splice using those exact indices instead of independently re-detecting hunk boundaries — eliminating any possibility of positional drift between extraction and reassembly.

### Proof of Concept
Not independently executed/verified — this is a code-review-derived finding based on comparing the two boundary-detection implementations, not a validated exploit. A concrete PoC would need to construct a conflicted file with an edge-case marker sequence (e.g. two consecutive `<<<<<<<` blocks where the first is malformed) and confirm that `extractConflictHunks` and `reassembleResolvedFile` disagree on hunk count/position, then observe that `reassembleResolvedFile(rawContent, hunkResolutions)` under `app/src/lib/copilot-conflict-resolution.ts:549-599` splices resolution N into the wrong block. export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
