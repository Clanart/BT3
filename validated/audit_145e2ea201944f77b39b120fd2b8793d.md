### Title
Panic on point-at-infinity group key reachable via `ThresholdKeys::read` causes node crash (DoS) - (File: networks/bitcoin/src/crypto.rs)

### Summary
The TensorFlow report (CVE-2023-25674) is a null-pointer dereference triggered entirely by attacker-controlled numeric inputs — i.e., a crash/availability bug caused by unchecked degenerate input. The Serai analog is a deterministic panic on the point at infinity inside `x()` / `x_only()` in `networks/bitcoin/src/crypto.rs`, reachable from untrusted bytes fed to `ThresholdKeys::read`: an attacker crafts `ThresholdKeys` whose verification shares are individually valid, non-identity points that sum to the point at infinity, producing an identity group key. Any subsequent use of those keys in the BIP-340 path (`Hram::hram` → `x(R)`/`x(A)`, `tweak_keys`, `p2tr_script_buf`, `x_only`) hits `expect("point at infinity")` and panics, crashing the signer/verifier.

### Finding Description
`crypto.rs` documents the panic explicitly:

```rust
// networks/bitcoin/src/crypto.rs
fn x(key: &ProjectivePoint) -> [u8; 32] {           // L13-16: "Panics on invalid input"
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
pub(crate) fn x_only(key: &ProjectivePoint) -> XOnlyPublicKey {
  XOnlyPublicKey::from_slice(&x(key)).expect("x_only was passed a point which was infinity or odd")
}
```

`Hram::hram` (L59-73) calls `x(R)` and `x(A)` unconditionally, and the doc comments on `Schnorr` (L54, L78-83) admit the code "will panic" if `R` or `A` is the point at infinity, hand-waving it away as "a negligible probability for a well-reasoned caller." That reasoning only holds when the group key comes from an honest DKG. It does not hold when `ThresholdKeys` are deserialized from untrusted bytes via `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), which reads `n` attacker-controlled `verification_shares` and passes them to `ThresholdKeys::new`, which derives `group_key` as the sum of the shares for participants `1..=t`. Shares `(G, -G)` for `t = 2` are each valid non-identity encodings (passing any per-point identity check in `read_G`) yet sum to the identity, yielding an infinity group key. Once a `TransactionMachine`/`AlgorithmMachine` is built over such keys, `Hram::hram` panics during `sign_share`/`verify`, and `tweak_keys`/`p2tr_script_buf`/`x_only` panic even earlier during key setup.

### Impact Explanation
An unprivileged party who can get a node to deserialize `ThresholdKeys` under its control (or trigger verification/signing against a group key of identity) causes a deterministic `expect` panic — a full crash of the signer/verifier thread or process. This is a direct availability analog to the reported NPE: attacker-controlled inputs reach an unchecked panic in cryptographic code handling public data.

### Likelihood Explanation
Triggering requires only crafted, self-consistent serialized `ThresholdKeys` bytes — no collusion, no leaked secrets, no broken transport. Per-point validation does not prevent it, because each verification share is a legitimate curve point; the degenerate condition exists only in their sum, which `ThresholdKeys::read`/`new` does not check. Every Bitcoin signing or verification attempt over the key panics reliably.

### Recommendation
- In `ThresholdKeys::new` (or `ThresholdKeys::read`), reject a `group_key` that is the point at infinity.
- In `x()`/`x_only()`/`Hram::hram`, return `Option`/`io::Error` instead of panicking, and propagate the failure through `Schnorr::verify`/`sign_share`.
- Optionally reject identity `R` when reading/constructing Schnorr signatures (`SchnorrSignature::read`).

### Proof of Concept
```rust
// Attacker crafts ThresholdKeys<Secp256k1> bytes with t=2, n=2 and
// verification_shares[1] = G, verification_shares[2] = -G (both valid
// non-identity SEC1 encodings). Deserialization succeeds:
let keys = ThresholdKeys::<Secp256k1>::read(&mut &crafted_bytes[..]).unwrap();
assert!(bool::from(keys.group_key().is_identity()));

// Any Bitcoin-FROST operation then panics:
// 1) tweak path
let _ = tweak_keys(keys.clone());           // x_only -> x() expect panics
// 2) signing path
let mut machine = AlgorithmMachine::new(Schnorr::new(), keys);
// after preprocess, sign_share -> Hram::hram(R, A=infinity, m) -> x(A) panics
// 3) verification path likewise panics on x(A)
```
Exact panic site: `crypto.rs:15` `expect("point at infinity")` (and L22 for odd/infinity in `x_only`), invoked from `crypto.rs:65-66` (`hram` inputs `x(R)`, `x(A)`) and `wallet/mod.rs:85` (`p2tr_script_buf` → `x_only`).

Note: I could not fully confirm the absence of an identity check on the summed group key inside `ThresholdKeys::new` within the available context; the finding depends on that check being absent (the panic comments in `crypto.rs` strongly imply infinity is only defended against probabilistically, not structurally). If `ThresholdKeys::new` does reject an identity group key, the residual crash surface narrows to identity `R` accepted via signature/preprocess deserialization, which requires verifying `SchnorrSignature::read`/`Preprocess::read` identity handling.
