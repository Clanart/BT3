## Analysis

The reported bug class (fee-on-transfer / deflationary ERC20 tokens breaking accounting that assumes `transferFrom` delivers the full nominal amount) has a direct analog in the Kaia service-chain bridge contracts.

### Root cause

`BridgeTransferERC20.requestERC20Transfer` calls `safeTransferFrom` for the sum of `_value + _feeLimit` and then immediately uses the nominal `_value` (not the actually-received balance delta) for all subsequent fee/burn/event accounting: [1](#0-0) 

That nominal `_value` then flows into `_requestERC20Transfer`, which pays out `_feeLimit`-derived fees via `_payERC20FeeAndRefundChange` and, in mint-burn mode, burns exactly `_value`: [2](#0-1) 

`_payERC20FeeAndRefundChange` also transfers `fee` and `feeRefund` out of the bridge's own balance without ever checking whether the bridge actually received the assumed amount: [3](#0-2) 

Crucially, `_value` is emitted in `RequestValueTransfer` and later replayed 1:1 as the release/mint amount on the counterpart chain via `handleERC20Transfer`, using either mint or a plain `safeTransfer` of the nominal amount: [4](#0-3) 

Token admissibility is gated only by `onlyRegisteredToken`/`onlyUnlockedToken` (owner-controlled allow-list), not by any fee-on-transfer detection or actual-balance-delta accounting: [5](#0-4) 

### Why this is reachable and impactful

Any unprivileged bridge user can call `requestERC20Transfer`/`requestValueTransfer` for a registered ERC20 token whose transfer behavior charges a fee (e.g., USDT-style tokens with a currently-zero-but-switchable fee, or any token the operator later registers that has this behavior). Because the bridge never verifies actual received balance vs. nominal `_value`+`_feeLimit`:
- In non-mint-burn mode, the bridge's real token holdings grow by less than `_value + _feeLimit`, yet it still emits/counts the full nominal `_value` as transferred and pays out the full nominal `fee`/`feeRefund`, silently depleting the bridge's pooled liquidity that backs other users' pending/future releases — a state divergence between the amount actually escrowed and the amount promised to be released on the counterpart chain.
- On the counterpart `handleERC20Transfer` side, the exact nominal `_value` is minted or transferred out, meaning the counterpart chain always assumes full-value delivery regardless of what the source chain bridge actually retained, again causing unbacked value creation/drain over repeated fee-charging transfers.

This matches the report's core defect ("assumption that the amount received matches the amount transferred") and lands squarely on the "unauthorized value movement / fee-delegation and value-transfer abuse" impact category for a system contract reachable via a plain user transaction, not requiring any privileged or malicious-node role.

### Title
Fee-on-transfer ERC20 tokens bypass bridge accounting, allowing liquidity drain/value divergence in `BridgeTransferERC20` - (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary
`BridgeTransferERC20.requestERC20Transfer` and `_payERC20FeeAndRefundChange` use the caller-supplied nominal `_value`/`_feeLimit` for all downstream fee, burn, and cross-chain release accounting instead of measuring the bridge's actual balance delta after `safeTransferFrom`. Any registered ERC20 token that charges a transfer fee (now or via a future fee-switch, e.g. USDT-style tokens) causes the bridge to under-receive tokens while still crediting/emitting and releasing the full nominal amount on the counterpart chain.

### Finding Description
- `requestERC20Transfer` transfers `_value + _feeLimit` via `safeTransferFrom` but never checks the resulting balance change: [1](#0-0) 
- The nominal `_value` and `_feeLimit` propagate unchanged into `_requestERC20Transfer`, which pays fees and (in mint-burn mode) burns the nominal `_value`: [2](#0-1) 
- `_payERC20FeeAndRefundChange` moves `fee`/`feeRefund` out of the bridge assuming they were fully received: [3](#0-2) 
- On the receiving side, `handleERC20Transfer` mints or transfers out the exact nominal `_value` from the request event, with no cross-check against what was actually escrowed on the source chain: [4](#0-3) 
- Token registration only gates by address allow-list, with no validation of transfer-fee behavior: [6](#0-5) 

### Impact Explanation
Repeated use of a fee-on-transfer token drains the bridge's real token reserve relative to the liabilities it has promised to honor on the counterpart chain (either via minted supply or via a fixed pool meant to back future `handleERC20Transfer` releases). This is a concrete, unauthorized value divergence/drain: honest users' funds backing the bridge's liquidity pool can be exhausted by other users' interactions with a fee-charging token, and in mint-burn mode it can also cause `ERC20Burnable(_tokenAddress).burn(_value)` to revert or over-burn relative to what was truly received, breaking bridge solvency invariants.

### Likelihood Explanation
The trigger only requires the bridge owner to have registered an ERC20 token that behaves like USDT (fee currently zero, but toggleable) or any other deflationary/fee-taking token — a plausible administrative choice not excluded by any check in `BridgeTokens.registerToken`. Once registered, any unprivileged user can trigger the mismatch simply by calling `requestERC20Transfer`/`requestValueTransfer`/`onERC20Received`, with no special privileges needed.

### Recommendation
In `BridgeTransferERC20.requestERC20Transfer` (and the `onERC20Received` 1-step path), measure `IERC20(_tokenAddress).balanceOf(address(this))` before and after `safeTransferFrom`, and use the actual received delta — rather than the nominal `_value + _feeLimit` — for all subsequent fee computation, burn amount, and the `RequestValueTransfer` event's `valueOrTokenId`/`fee` fields, mirroring the Curve `FEE_INDEX`-style before/after balance pattern referenced in the original report.

### Proof of Concept
1. Bridge owner registers a fee-on-transfer ERC20 token `T` (fee currently 0%, later enabled to e.g. 1%, as with real-world USDT) via `registerToken`.
2. User Alice approves the bridge for `1000` `T` and calls `requestERC20Transfer(T, Bob, 1000, feeLimit, "")`.
3. Because `T` charges a 1% fee, the bridge actually receives `990` `T`, but `safeTransferFrom`'s success (no revert, since `SafeERC20.safeTransferFrom` doesn't check delivered amount) lets execution proceed with nominal `_value = 1000`.
4. `_payERC20FeeAndRefundChange` sends out `fee`/`feeRefund` computed against the nominal `feeLimit`, and (in mint-burn mode) `ERC20Burnable(T).burn(1000)` is attempted while the bridge holds only `990` of new tokens plus whatever pre-existing balance it has — silently consuming the bridge's other reserves or reverting depending on prior liquidity.
5. `RequestValueTransfer` still emits `1000` as `valueOrTokenId`, so when relayed, `handleERC20Transfer` on the counterpart chain mints/releases `1000` `T`-equivalent to Bob — `10` more than the bridge ever actually retained from Alice's transfer, illustrating the value leak that compounds with repeated use.

```text
    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
