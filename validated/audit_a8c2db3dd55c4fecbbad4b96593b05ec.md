### Title
Deterministic nonce reuse via never-invalidated `CachedPreprocesses` enables FROST secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel CVE fixed a path where a "completed" task was put/freed twice because an early-exit `goto` fell through to common cleanup. The Serai analog is the inverse direction of the same lifecycle bug class: a resource that is documented as single-use (a FROST preprocess/nonce seed) is stored once in the DB and then re-consumed on every invocation of `share_internal`, without any invalidation. `AlgorithmMachine::seeded_preprocess` derives all nonces deterministically from `ChaCha20Rng::from_seed(*seed.0)` (crypto/frost/src/sign.rs:121-144), so any second execution of `share_internal` for the same `self.context` produces a signing machine with identical secret nonces `d, e`, while the binding factors/challenge differ. Two or more shares under the same nonce yield a linear system that recovers the signer's secret share.

### Finding Description
`SigningProtocol::preprocess_internal` writes `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` only when no entry exists, and `share_internal` calls `preprocess_internal` again, which loads the *same* cached seed and reconstructs the machine via `AlgorithmSignMachine::from_cache` (coordinator/src/tributary/signing_protocol.rs:123-145, 156). `from_cache` → `seeded_preprocess` is fully deterministic: `ChaCha20Rng::from_seed(*seed.0)` then `Commitments::new` generates `(d, e)` (crypto/frost/src/sign.rs:127-132). The `SignMachine` contract is explicit: "This cached preprocess MUST only be used once. Reuse of it enables recovery of your private key share" and "the preprocess must be deleted so it's never reused" (crypto/frost/src/sign.rs:209-220). The coordinator layer never deletes, rotates, or marks the cache consumed; the seed persists in `CachedPreprocesses` keyed solely by `self.context` and is re-fetched on every call. Tributary signing protocols are re-attempted (spec/coordinator/Tributary.md:121-128), and `share_internal` is re-entered whenever the coordinator feeds a new preprocess set for the same context; there is no guard equivalent to `AttemptDb`/`CompletedDb` on this path. A peer-driven re-run (e.g., a second `Preprocesses` batch, or a retry where `context` does not incorporate the attempt counter) therefore signs with reused `d, e`.

### Impact Explanation
Each emitted share is `share = d + ρ·e + λ·s·c`. With nonces fixed across k sessions, every additional share adds one linear equation; after ~3 shares with distinct `(ρ, λ, c)` (different participant sets or messages), the system solves for `(d, e, s)`, recovering the validator's threshold secret share. Combined with shares from other compromised sessions or published blame data, this degrades toward group-key material exposure — signing of arbitrary messages / theft of funds secured by the threshold key.

### Likelihood Explanation
Requires `share_internal` to execute more than once for a single `context`. Whether the context object embeds the attempt number could not be fully confirmed (context is generic `C: Encode`); if it does not, ordinary protocol re-attempts or duplicated coordinator delivery of a preprocess set — driven entirely by untrusted `read_preprocess`-parsed bytes — trigger nonce reuse. The explicit MUST-NOT-reuse documentation plus the absence of any consumption marker makes this a real rather than hypothetical exposure; severity rated High conditioned on the context not binding attempts.

### Recommendation
Delete or rotate the `CachedPreprocesses` entry atomically when `share_internal` consumes it (e.g., `remove`/`set` a tombstone per attempt), and include the attempt counter in `self.context` so retries derive fresh seeds — i.e., ensure the "completed" path cannot re-enter the common cleanup/consume path, mirroring the upstream fix.

### Proof of Concept
1. Attacker participates in a signing session for context `X`; coordinator calls `share_internal`, producing share `s1 = d + ρ1·e + λ1·s·c1`.
2. Attacker induces a re-attempt / second preprocess delivery for the same context `X` (new participant set or msg). `preprocess_internal` reloads the identical `CachedPreprocesses` seed; `from_cache` regenerates identical `(d, e)`; a second share `s2 = d + ρ2·e + λ2·s·c2` is broadcast.
3. After three such shares, solve the linear system over `C::F` for `(d, e, s)` → secret share recovered. Determinism is guaranteed by `ChaCha20Rng::from_seed` in `seeded_preprocess` (crypto/frost/src/sign.rs:127) and confirmed by the identical preprocess bytes the machine would emit, observable on the wire.
