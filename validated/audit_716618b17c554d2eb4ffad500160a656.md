## Analog Vulnerability Found

### Title
Commit Summaries Render Unfiltered Unicode Bidirectional Control Characters Outside the Diff View - (File: `app/src/ui/lib/rich-text.tsx`, `app/src/lib/text-token-parser.ts`)

### Summary
GitHub Desktop already recognizes that Unicode bidirectional override characters (Trojan-Source style attacks) in **diff content** are dangerous enough to warrant an explicit user-facing warning banner. However, the exact same class of untrusted, attacker-controlled string — the git **commit summary/message** — is rendered in numerous other UI surfaces (history list, undo-commit panel, expandable commit summary, multi-commit operation progress dialog) through the `RichText`/`Tokenizer` pipeline with no equivalent detection or warning, even though this text originates from a cloned/fetched repository and can be fully attacker-controlled.

### Finding Description
`app/src/lib/diff-parser.ts` defines `HiddenBidiCharsRegex` and computes `hasHiddenBidiChars` for diff hunks: [1](#0-0) 

That flag is consumed only by `DiffContentsWarning`, which shows a dedicated "This diff contains bidirectional Unicode text…" banner: [2](#0-1) 

Commit summaries, by contrast, are rendered through `Tokenizer`/`RichText`, which only classifies text into `Text`, `Emoji`, and `Link` tokens and outputs plain `<span>` elements — with no scan for `\u202A-\u202E` / `\u2066-\u2069` bidi override characters at all: [3](#0-2) [4](#0-3) 

This unfiltered `RichText` rendering path is used to display the raw commit summary/body in at least:
- The commit history list item: [5](#0-4) 
- The expandable commit summary (title and description) shown when a commit is selected: [6](#0-5) 
- The "Undo Commit" panel, which is the confirmation surface a user relies on before reverting the last commit: [7](#0-6) 
- The rebase/cherry-pick/squash/reorder progress dialog, which echoes `currentCommitSummary` while a multi-commit operation is running: [8](#0-7) 

Because React only escapes HTML/markup (not Unicode bidi control characters) when rendering text nodes, a commit message containing `U+202E` (RTL override) or similar characters will visually reorder the displayed characters in all of these locations. There is no equivalent of `HiddenBidiCharsRegex`/`DiffContentsWarning` gating these surfaces, so the existing guard the project built for diffs simply does not cover commit-message rendering.

### Impact Explanation
An attacker who controls a repository the victim clones or fetches (or a branch/PR the victim checks out) can craft a commit message using bidi override characters to make the displayed summary read differently than the underlying bytes — e.g., disguising a destructive or unexpected commit as an innocuous one in the history list, in the "Undo Commit" confirmation, or in the rebase/cherry-pick progress dialog. Since Desktop already treats this exact primitive as a legitimate spoofing risk for diffs (hence the dedicated warning), the same primitive reaching users unguarded through commit summaries is a real, exploitable inconsistency: a user could be misled about what commit they are about to undo, are viewing in history, or are currently rebasing onto, without any indication that hidden reordering characters are present.

### Likelihood Explanation
Commit messages are fully attacker-controlled in any repository the victim clones/fetches — no local access, credentials, or unusual user action is required beyond normal Desktop usage (browsing history, undoing the last commit, or running a rebase/cherry-pick that Desktop's UI displays progress for). This mirrors precisely the “attacker controls a cloned/fetched repository” condition called out as valid impact, and the existence of the diff-specific mitigation demonstrates the project itself considers the underlying primitive (bidi override injection) worth guarding against — it's just inconsistently applied.

### Recommendation
Reuse the existing `HiddenBidiCharsRegex` detection (or an equivalent surface-agnostic check) wherever `RichText`/`Tokenizer` renders untrusted commit summaries/bodies (history list, expandable commit summary, undo-commit, multi-commit-operation progress dialog), and surface the same warning treatment used in `DiffContentsWarning`. Alternatively, strip or visibly escape bidirectional control characters before they reach the `Tokenizer`, so raw untrusted text cannot alter the perceived reading order of the UI.

### Proof of Concept
1. Attacker creates/pushes a commit with summary: `git commit -m "$(printf 'safe fix\u202Etxt.exe')"` (or any payload using `U+202E`/`U+2066-U+2069` to reorder visible characters).
2. Victim clones or fetches this repository in GitHub Desktop.
3. Victim opens History, selects the commit, or hits "Undo Commit" on it, or runs a rebase/cherry-pick that displays this commit in `ProgressDialog`.
4. In each of these surfaces the summary is rendered via `RichText`/`Tokenizer` with no bidi-character detection or warning (unlike the diff view), so the visually-reordered, spoofed text is shown to the user as-is.

```typescript
export enum TokenType {
  /*
   * A token that should be rendered as-is, without any formatting.
   */
  Text,
  /*
   * A token representing an emoji character - should be replaced with an image.
   */
  Emoji,
  /*
   * A token representing a generic link - should be drawn as a hyperlink
   * to launch the browser.
   */
  Link,
}

export type EmojiMatch = {
  readonly kind: TokenType.Emoji
  // The alternate text to display with the image, e.g. ':+1:'
  readonly text: string
  // The path on disk to the image.
  readonly path: string
  // The unicode character of the emoji, if available
  readonly emoji?: string
  // The human description of the emoji, if available
  readonly description?: string
}

export type HyperlinkMatch = {
  readonly kind: TokenType.Link
  // The text to display inside the rendered link, e.g. @shiftkey
  readonly text: string
  // The URL to launch when clicking on the link
  readonly url: string
}

export type PlainText = {
  readonly kind: TokenType.Text
  // The text to render.
  readonly text: string
}

export type TokenResult = PlainText | EmojiMatch | HyperlinkMatch
```

**File:** app/src/ui/lib/rich-text.tsx (L38-79)
```typescript
function getElements(
  emoji: Map<string, Emoji>,
  repository: Repository | undefined,
  renderUrlsAsLinks: boolean | undefined,
  text: string | ReadonlyArray<TokenResult>
) {
  const tokenizer = new Tokenizer(emoji, repository)
  const tokens = typeof text === 'string' ? tokenizer.tokenize(text) : text

  return tokens.map((token, index) => {
    switch (token.kind) {
      case TokenType.Emoji:
        if (token.emoji) {
          return <span key={index}>{token.emoji}</span>
        } else {
          return (
            <img
              key={index}
              alt={token.description ?? token.text}
              className="emoji"
              src={token.path}
            />
          )
        }
      case TokenType.Link:
        if (renderUrlsAsLinks !== false) {
          const title = token.text !== token.url ? token.url : undefined
          return (
            <LinkButton key={index} uri={token.url} title={title}>
              {token.text}
            </LinkButton>
          )
        } else {
          return <span key={index}>{token.text}</span>
        }
      case TokenType.Text:
        return <span key={index}>{token.text}</span>
      default:
        return assertNever(token, `Unknown token type: ${token}`)
    }
  })
}
```
