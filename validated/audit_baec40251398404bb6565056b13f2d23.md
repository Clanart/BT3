Audit Report

## Title
Missing consumed-slot marking on `UnknownSlotLeader` error path allows repeated re-verification of duplicate-shred proofs - (File: gossip/src/duplicate_shred_handler.rs)

## Summary
In `DuplicateShredHandler::handle_shred_data`, once all chunks for a `(slot, pubkey)` entry are received, the buffer entry is drained via `std::mem::take(entry)` before the slot leader is resolved via `slot_leader_at`. If that lookup returns `None`, the function short-circuits with `Err(Error::UnknownSlotLeader(slot))` via the `?` operator, skipping the subsequent `self.consumed.insert(slot, true)` call, and skipping `store_duplicate_slot` (so `blockstore.has_duplicate_shreds_in_slot(slot)` stays `false`). [1](#0-0) 

## Finding Description
`should_consume_slot` gates whether new chunks are accepted for a slot, using the `consumed` map with a fallback to `blockstore.has_duplicate_shreds_in_slot(slot)` only when the slot is absent from the map. [2](#0-1) 

Since the `UnknownSlotLeader` path never calls `store_duplicate_slot` and never inserts `true` into `consumed`, the slot's `consumed` entry stays `false` (or, once inserted as `false` by the `.or_insert_with` fallback, it stays `false` permanently, since nothing subsequently overwrites it). Consequently `should_consume_slot` continues returning `true` for that slot, allowing a re-submitted 3-chunk proof for the same slot to be re-buffered and, once complete, re-run through `duplicate_shred::into_shreds` (wincode deserialization) and `check_shreds` (Ed25519 signature verification) each time. [3](#0-2) 

This matches the described code path exactly: the entry is drained at line 131, `slot_leader_at` is called and its failure is propagated via `?` at line 135, before reaching the `consumed.insert(slot, true)` at line 155.

## Impact Explanation
This is an unprivileged-peer-triggerable repeated CPU cost for cryptographic verification (Ed25519 signature checks and deserialization) with no convergence to a terminal state, matching the "non-RPC remote exhaustion" impact category for gossip-facing code. The exact corrupted/stale value is the `consumed: HashMap<Slot, bool>` entry for the affected slot, which fails to be set to `true` (or is stuck at `false`), and correspondingly the blockstore never records `has_duplicate_shreds_in_slot(slot) == true` for that slot.

## Likelihood Explanation
Exploitability hinges entirely on whether an attacker can pick/produce a `slot` value for which `LeaderScheduleCache::slot_leader_at(slot, None)` reliably returns `None`, while that slot still satisfies `should_consume_slot`'s bounds check (`last_root < slot < last_root + cached_slots_in_epoch`). I attempted to inspect `ledger/src/leader_schedule_cache.rs`'s `slot_leader_at` implementation to determine this but ran out of tool iterations before completing that inspection; this is a genuine gap in verification. Based on general knowledge of Agave's leader schedule caching, `slot_leader_at` typically returns `None` only when the epoch's leader schedule hasn't yet been cached (e.g., slots far enough into a future epoch that the schedule can't be computed from currently rooted state) — a condition that may or may not coexist with the `cached_slots_in_epoch` bound used by `should_consume_slot`. Because I could not conclusively confirm the reachability of this specific `None` condition within the accepted window in the current codebase, likelihood remains unverified but the code defect itself (missing consumed-marking on this error path) is confirmed as present.

## Recommendation
Mark the slot as consumed (or otherwise permanently ineligible for re-buffering) regardless of whether `slot_leader_at` succeeds — e.g., move `self.consumed.insert(slot, true)` before the `slot_leader_at` lookup (once chunks are fully drained), or track "attempted and terminally failed" slots in a separate set so they are not perpetually re-buffered and re-verified.

## Proof of Concept
1. Identify/produce a slot `S` satisfying `last_root < S < last_root + cached_slots_in_epoch` for which `leader_schedule_cache.slot_leader_at(S, None)` returns `None`.
2. Send 3 valid-format chunks (via `duplicate_shred::from_shred`) forming a complete duplicate-shred proof for slot `S`.
3. Observe `handle_shred_data` reassemble the chunks, call `slot_leader_at`, receive `None`, and return `Err(UnknownSlotLeader)` — `self.consumed.insert(slot, true)` at line 155 is never reached, and `blockstore.has_duplicate_shreds_in_slot(S)` remains `false`.
4. Resend the same 3-chunk proof for slot `S`; `should_consume_slot` still returns `true`, so the handler re-buffers and re-verifies (deserialization + signature checks) the proof again.
5. Repeat step 4 to demonstrate unbounded repeated verification cost for slot `S`.

Note: step 1's feasibility (whether such a slot `S` is reachable in steady-state operation) could not be conclusively confirmed within the code inspected in this session; this affects the confirmed likelihood of exploitation but not the presence of the missing-state-update defect itself.

fn should_consume_slot(
    slot: Slot,
    blockstore: &Blockstore,
    consumed: &mut HashMap<Slot, bool>,
) -> bool {
    !*consumed
        .entry(slot)
        .or_insert_with(|| blockstore.has_duplicate_shreds_in_slot(slot))
}
