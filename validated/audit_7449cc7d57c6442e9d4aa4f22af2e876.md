### Title
`Scanner::scan_block` trusts every transaction in a block — including the coinbase — reporting immature outputs as received/spendable - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The OpenClaw bug class is "trusted-prefix fallback": when the strict whitelist (`/etc/shells`) didn't match, a permissive fallback (any executable under `/bin`, `/usr/local/bin`, ...) accepted attacker-influenced input. The structural analog in Serai is `Scanner::scan_block`, which treats "any transaction appearing in a confirmed block" as a trusted source of spendable outputs without checking the transaction's *kind*. The coinbase transaction's outputs are consensus-immature for 100 blocks, yet `scan_block` iterates `block.txdata` from index 0 and emits them as `ReceivedOutput`s indistinguishable from normal payments.

### Finding Description
`scan_block` loops over `block.txdata` in its entirety and delegates to `scan_transaction`, which only matches `output.script_pubkey` against the registered script set. [1](#0-0) [2](#0-1) 

The doc comment acknowledges the coinbase is scanned and says "a post-processing pass is needed" — but `ReceivedOutput` carries no flag distinguishing coinbase outputs, and there is no maturity/height field. The consumer has no way within this API to tell whether an emitted output is spendable now or only after the 100-block coinbase maturity. In the processor's scanning pipeline (`processor/src/multisigs/scanner.rs`), outputs obtained via `network.get_outputs(&block, key)` are emitted as `ScannerEvent::Block { outputs }` once the block reaches `N::CONFIRMATIONS` confirmations — far below coinbase maturity (100) — and are persisted via `save_outputs` and later acked/spendable via `ack_block` with no maturity check anywhere. [3](#0-2) [4](#0-3) 

Just as OpenClaw's fallback executed an attacker-placed binary because it merely lived under a trusted path, `scan_block` credits an attacker-placed output because it merely lives inside a trusted container (a confirmed block), ignoring the coinbase-specific spendability rule.

### Impact Explanation
An output reported as received that is not yet spendable violates the "funds reported received that are not spendable" acceptance criterion. Concretely: any miner (or pool operator — no privileged access to Serai required) can place a P2TR output paying to Serai's external/branch/change/forward address in the coinbase transaction of a block they mine. Once that block passes `N::CONFIRMATIONS`, the processor records the output as a received, spendable input and may select it for a `SignableTransaction`. The resulting spend is consensus-invalid (BIP-34/COINBASE_MATURITY = 100 blocks); the transaction will be rejected by the Bitcoin network, stalling the signing/batch pipeline and causing Serai to have accounted funds it cannot actually move. Repeated poisoned coinbase outputs compound the issue since the scanner explicitly panics on duplicate output IDs but has no maturity filter.

### Likelihood Explanation
Requires an attacker to mine a block containing a coinbase output to a Serai address. On mainnet this costs real hashpower, but mining pools and any solo miner reaching Serai's chain do this routinely; paying to an arbitrary script in a coinbase is trivial. No Serai-side privileges, keys, or collusion are needed — the trigger is purely an on-chain Bitcoin transaction the attacker causes to exist, which is within the allowed reachability model.

### Recommendation
Do not rely on post-hoc filtering of a homogeneous `Vec<ReceivedOutput>`. In `scan_block`, skip `block.txdata[0]` (or more robustly, skip `tx.is_coinbase()`), or return outputs tagged with the containing transaction's coinbase status and required maturity height so callers can exclude them until spendable. The processor's `get_outputs`/scan path should enforce the same rule rather than treating all block transactions uniformly.

### Proof of Concept
```rust
// Conceptual PoC (regtest semantics):
// 1. Build Scanner for the group key K; register offset for branch if desired.
let mut scanner = Scanner::new(key).unwrap();

// 2. Attacker mines a block whose coinbase pays directly to Serai's P2TR script.
//    (Any miner can do this; e.g. generatetoaddress to the Serai address, or a
//     hand-built coinbase.)
let coinbase_script = p2tr_script_buf(key).unwrap();
// block.txdata[0] = coinbase with output { script_pubkey: coinbase_script, value: V }

// 3. After N::CONFIRMATIONS (e.g. 2) but < 100 blocks, scan:
let outputs = scanner.scan_block(&block);
// outputs[0] is a ReceivedOutput with offset ZERO and the coinbase outpoint —
// indistinguishable from a normal deposit.

// 4. Processor emits it via ScannerEvent::Block, persists via save_outputs,
//    ack_block returns it as spendable. Any SignableTransaction built over this
//    input produces a transaction rejected by the network:
//    "bad-txns-premature-spend-of-coinbase".
assert_eq!(outputs[0].outpoint(), &OutPoint::new(block.txdata[0].compute_txid(), 0));
// No field on ReceivedOutput marks this as immature — the caller cannot detect it.
```

Uncertainty note: I could not confirm in the remaining iterations whether `processor/src/networks/bitcoin.rs`'s `get_outputs` filters the coinbase before returning outputs; if it already drops `txdata[0]`, the exposure is limited to direct `scan_block` consumers. The library-level defect stands regardless — `scan_block` silently emits unspendable outputs with no maturity metadata — but the end-to-end severity depends on that call site.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
