### Title
Unauthenticated relayer identity accepted into request/response receipts via `Signature::signer()` — false delivery attribution enables fraudulent reward and fee claims - ([File: modules/pallets/ismp/src/host.rs])

### Summary
`RequestMessage::signer` (and `ResponseMessage::signer`) is documented only as "should ideally be their account identifier" [1](#0-0) , and `ismp::handlers::request::handle` never cryptographically verifies it — it passes `msg.signer` straight into `host.store_request_receipt(&wrapped_req, &msg.signer)` [2](#0-1) . On pallet-ismp, `store_request_receipt` calls `extract_signer`, which, for any `signer` byte blob longer than 32 bytes, SCALE-decodes it as a `crypto_utils::verification::Signature` enum and calls `.signer()` on it — **without ever calling `.verify()`** [3](#0-2) . `Signature::signer()` simply returns the `address`/`public_key` field embedded in the enum variant, with zero relationship to the `signature` field or to any actual cryptographic recovery [4](#0-3) . Anyone can submit `Signature::Evm { address: <arbitrary 20 bytes>, signature: <anything, including all zeros> }` (or the Sr25519/Ed25519 equivalents) as the `signer` field of a `RequestMessage`, and the pallet will store that arbitrary address as the "delivering relayer" in `RequestReceipts[commitment]`.

### Finding Description
This is the direct structural analog of the reported bug: the code performs an operation (`.signer()`) that looks like it authenticates a cryptographic actor, but for a crafted/degenerate input it silently returns attacker-chosen data without ever executing the verification path that would normally reject it — exactly like `0^(p-2) mod p = 0` being accepted as a valid inverse without ever checking `x ≠ 0`.

Downstream, this stored "relayer" identity is treated as authoritative proof of who delivered a message, and is consumed by fund-moving logic in multiple places:
- `pallet-relayer::accumulate::decode_receipt_relayer` decodes the `RequestReceipts` value and, for `bytes.len() > 32`, does the identical trick: `Signature::decode(...).signer()` [5](#0-4) . This value becomes the `address` credited in `accumulate_fee_and_deposit_event`, which increments `Fees[state_machine][address]` [6](#0-5) , later withdrawable via `withdraw_fees`.
- `pallet-relayer::outbound_request::process_outbound_request_delivery_claim` uses the same `decode_receipt_relayer` to compute `delivered_by`, which is then compared against the claimant's `signature.verify(...)` result to gate a treasury payout [7](#0-6) .
- `messaging-incentives::relayer_for` derives the minted-reward recipient from `msg.signer`, but there it *does* call `.verify_and_get_sr25519_pubkey(...)` [8](#0-7)  — showing the codebase knows the correct pattern elsewhere, which makes `extract_signer`'s use of the unverified `.signer()` an inconsistency, not an intentional design choice.

Because `extract_signer` never calls `Signature::verify`, an attacker who is the relayer submitting a `RequestMessage` (a permissionless, unsigned-origin extrinsic path — any account can call the ISMP handler) can set `msg.signer` to a `Signature::Evm { address: <victim_or_self_chosen_address>, signature: [0u8;65] }`. The message-membership state proof is verified normally, so the underlying request delivery is real, but the *identity* attributed to "who delivered it" is completely unauthenticated and attacker-controlled.

### Impact Explanation
This breaks the "one-time receipt handling" / "rightful beneficiary" invariant explicitly called out as in-scope: relayer rewards and accumulated fees must move only to the party that actually performed the delivery. With this bug, any address can be written into `RequestReceipts[commitment]` regardless of who submitted the transaction, so:
- Fee accumulation (`accumulate_fees`) can be attributed to an arbitrary address chosen by whoever submits the request-delivery message, letting an attacker redirect relayer fees to themselves for work they didn't do, or grief a legitimate relayer by stealing their credited fees.
- The `claim_outbound_request_delivery_reward` pipeline uses this receipt value as the ground truth for "who delivered this," directly gating a treasury-funded BRIDGE payout.

This is a real fund-diversion primitive triggerable by an unprivileged actor through a normal, permissionless entrypoint (submitting request messages), not requiring a malicious relayer/prover assumption beyond "submits a message" — which any account can do.

### Likelihood Explanation
High. `RequestMessage.signer: Vec<u8>` is attacker-supplied calldata with no format enforcement beyond SCALE-decodability; `extract_signer` is reached on every normal request-delivery path (`modules/ismp/core/src/handlers/request.rs:112`) with no additional guard. No relayer collusion, governance action, or leaked key is required — only crafting a signer blob whose length exceeds 32 bytes and SCALE-decodes as a valid `Signature` variant.

### Recommendation
`extract_signer` in `modules/pallets/ismp/src/host.rs` must call `Signature::verify(&msg, ...)` (using the same message/commitment the relayer is attesting to) and only take the *verified* recovered signer, mirroring the pattern already used in `messaging-incentives::relayer_for`. Simply decoding the enum and reading its embedded address/public-key field must never be treated as proof of authorship anywhere fee or reward attribution is derived from it — this includes auditing `decode_receipt_relayer` in `modules/pallets/relayer/src/accumulate.rs` for the same issue, since it repeats the identical unverified-`.signer()` pattern on the value that `extract_signer` originally wrote.

### Proof of Concept
1. Any account submits a normal `RequestMessage` (with a valid membership proof for a real, deliverable request) but sets `signer` to the SCALE encoding of `Signature::Evm { address: ATTACKER_ADDR.to_vec(), signature: vec![0u8; 65] }` (65-byte all-zero signature, so `signature.len() == 65` passes the length check but is never cryptographically checked at storage time).
2. `handlers::request::handle` calls `host.store_request_receipt(&req, &msg.signer)` → `extract_signer` sees `signer.len() > 32`, decodes it as `Signature::Evm`, calls `.signer()`, which returns `ATTACKER_ADDR` unconditionally — no `secp256k1_ecdsa_recover` call occurs.
3. `RequestReceipts[commitment] = ATTACKER_ADDR` is persisted despite the all-zero "signature" never being verified.
4. When relayer-fee accumulation or `claim_outbound_request_delivery_reward` later reads this receipt via `decode_receipt_relayer`, `ATTACKER_ADDR` is treated as the address that gets credited fees / must match the reward-claim signature, letting the attacker (or anyone who knows this trick) redirect relayer compensation to an address of their choosing rather than the address that actually delivered the message.

fn extract_signer(signer: &[u8]) -> Result<Vec<u8>, Error> {
	if signer.len() > 32 {
		Signature::decode(&mut signer.as_ref())
			.map(|sig| sig.signer())
			.map_err(|_| Error::SignatureDecodingFailed)
	} else {
		Ok(signer.to_vec())
	}
}
