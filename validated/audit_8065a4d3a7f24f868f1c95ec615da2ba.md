### Title
Duplicate Bitcoin inputs are counted as spendable liquidity, producing invalid transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts duplicate `ReceivedOutput`s without checking their `OutPoint`s for uniqueness. Each duplicate contributes its full value to `input_sat`, so unavailable balance is counted when deciding whether payments and fees are affordable. The resulting transaction then contains the same prevout multiple times and is consensus-invalid. [1](#0-0) 

### Finding Description
`ReceivedOutput` exposes an `outpoint` identifying the UTXO being spent, and `ReceivedOutput::read` accepts that field from serialized input without imposing uniqueness across a later input list. [2](#0-1) 

`SignableTransaction::new` sums every supplied output into `input_sat` and converts every supplied item into a `TxIn` using `input.outpoint`, with no `HashSet`, duplicate check, or rejection path. [1](#0-0) 

Because affordability is checked against this duplicated sum, a single 10,000-satoshi UTXO supplied twice is treated as 20,000 satoshis of available balance. [3](#0-2) 

The transaction is then committed to and signed once per input position, including each duplicate prevout. [4](#0-3) 

Completion places a valid-looking Schnorr witness on every duplicated input and returns the transaction, even though Bitcoin consensus rejects transactions that spend the same outpoint twice. [5](#0-4) 

### Impact Explanation
This mirrors the reported accounting flaw: an unavailable or already-counted resource contributes to the balance used for withdrawal/payment authorization. A crafted input list can therefore cause signers to produce a transaction that can never confirm, delaying payment execution and requiring the plan or signing attempt to be rebuilt. [6](#0-5) 

If this construction is used for withdrawals or batched payments, one duplicated serialized `ReceivedOutput` can prevent all legitimate outputs in the same transaction from being paid. [7](#0-6) 

### Likelihood Explanation
The reachable input is a `Vec<ReceivedOutput>`, and individual entries can originate from serialized bytes through `ReceivedOutput::read`. An attacker who can submit or corrupt an input list only needs to duplicate one entry; no validator key, miner control, or protocol privilege is required. [8](#0-7) 

The likelihood is bounded by where callers source `ReceivedOutput`s: values obtained exclusively from a correctly de-duplicated scanner are not attacker-controlled in this way, but the signing API itself does not enforce that invariant. [9](#0-8) 

### Recommendation
Reject duplicate `OutPoint`s in `SignableTransaction::new` before calculating `input_sat`, and treat duplicate input submission as a dedicated `TransactionError`. [10](#0-9) 

Use checked arithmetic for input and payment totals, and consider enforcing a maximum input count before allocating or constructing `tx_ins`. [11](#0-10)

  // The TX ID and vout of the output to spend.
  outpoint: OutPoint,
}

  /// The offset for this output.
  pub fn offset(&self) -> Scalar {
    self.offset

  pub fn output(&self) -> &TxOut {
    &self.output
  }

  /// The outpoint for this output.
  pub fn outpoint(&self) -> &OutPoint {
    &self.outpoint
  }

  /// The value of this output.
  pub fn value(&self) -> u64 {
    self.output.value.to_sat()
