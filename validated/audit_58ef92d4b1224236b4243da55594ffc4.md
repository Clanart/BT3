## Title
Shared mutable `validatedSender`/`validatedFeePayer` fields on `*Transaction` cause cross-contamination between concurrent validations of fee-delegated transactions - (File: `blockchain/types/transaction.go`)

### Summary
`AsMessageWithAccountKeyPicker`/`ValidateSender`/`ValidateFeePayer` cache the resolved sender and fee payer directly on the shared `*Transaction` object instead of returning them per-call. When the same transaction object is validated concurrently by multiple goroutines (e.g. concurrent block/tx re-execution, tracing, or txpool paths that reuse the same `*types.Transaction` pointer), one goroutine's fee-payer result can be overwritten by another's before it is read back via `tx.ValidatedFeePayer()`. This mirrors CVE-2021-22897's bug class: a value meant to be scoped to a single concurrent operation is instead stored in one shared mutable location, so the last writer "wins" and silently corrupts the result seen by other concurrent callers.

### Finding Description
The `Transaction` struct stores validation results as plain fields (not per-invocation return values): [1](#0-0) 

`ValidateSender` sets `tx.validatedSender`/`tx.validatedFeePayer` guarded only by `tx.mu`, which serializes individual writes but does not make the whole "validate → read" sequence atomic across concurrent goroutines operating on the same tx pointer: [2](#0-1) 

`ValidateFeePayer` similarly conditionally overwrites `tx.validatedFeePayer` based on the current value of `tx.validatedFeePayer`/`tx.validatedSender` at the time of the lock — a value that can have just been written by a *different* concurrent call for a *different* purpose: [3](#0-2) 

`AsMessageWithAccountKeyPicker` composes these two steps and returns the same `*Transaction` object (`tx`) rather than an isolated copy, so the caller's use of `msg.ValidatedFeePayer()` after the call is reading global-to-the-object state that can have been mutated by a concurrent caller in between: [4](#0-3) 

This is a real, already-flagged concurrency hazard: the repo contains a dedicated race test acknowledging that "a fee payer may be inserted wrongly due to concurrent issue" when `AsMessageWithAccountKeyPicker` is invoked from multiple goroutines on the same fee-delegated `*Transaction`: [5](#0-4) 

### Impact Explanation
If a single transaction object is concurrently validated/executed from more than one call path (e.g. speculative execution during consensus replay concurrently with RPC tracing/estimate calls, or any code path that revalidates a pooled/received `*Transaction` pointer from multiple goroutines), the cached `validatedFeePayer` can be corrupted so that:
- The fee-delegated transaction's fee ends up charged to the wrong feePayer/sender account (fee-delegation abuse / unauthorized value movement), or
- Execution proceeds using an incorrect sender/fee-payer identity for gas or state changes, which is a strong precondition for state divergence between nodes that observe different results for the same transaction depending on goroutine scheduling.

Because `blockchain/state_transition.go` and RPC/tracer backends rely on `tx.ValidatedSender()`/`tx.ValidatedFeePayer()` after validation, a wrong cached value silently propagates into consensus-relevant execution results.

### Likelihood Explanation
Exploitation requires two concurrent validations of the *same* `*Transaction` pointer, which the codebase's own test (`TestRaceAsMessageWithAccountPickerForFeePayer`) demonstrates is achievable and does occur in practice under concurrent access patterns already present in the code (e.g. simultaneous tracing/estimateGas and pool/consensus paths touching pooled transactions). No special privileges are needed by the party who submits the fee-delegated transaction; the race is triggered by ordinary concurrent node operations processing that transaction.

### Recommendation
Do not store per-validation results (`validatedSender`, `validatedFeePayer`, `validatedGas`) as mutable fields on the shared `*Transaction` object when the same object can be validated concurrently from multiple call sites. Either:
1. Return validation results as local values from `AsMessageWithAccountKeyPicker`/`ValidateSender`/`ValidateFeePayer` instead of caching on `tx`, or
2. Guarantee (and enforce, e.g. via clone-before-validate) that each concurrently-executing context always operates on its own private `*Transaction` copy rather than sharing one across concurrent validation flows, or
3. Widen the lock scope so that the entire "resolve sender → resolve feePayer → read validated values" sequence is atomic with respect to any other goroutine that could mutate the same fields.

### Proof of Concept
The existing repo test already reproduces the corruption: two goroutines call `tx.AsMessageWithAccountKeyPicker(signer, stateDB, 0)` concurrently on the same fee-delegated transaction and then assert `msg.ValidatedFeePayer() == feePayer.GetAddr()`; under race conditions this assertion can fail because the shared `tx.validatedFeePayer` field was clobbered by the other goroutine's concurrent call. func (tx *Transaction) AsMessageWithAccountKeyPicker(s Signer, picker AccountKeyPicker, currentBlockNumber uint64) (*Transaction, error) {
	intrinsicGas, err := tx.IntrinsicGas(currentBlockNumber)
	if err != nil {
		return nil, err
	}

	gasFrom, err := tx.ValidateSender(s, picker, currentBlockNumber)
	if err != nil {
		return nil, ErrSender(err)
	}

	tx.mu.Lock()
	tx.checkNonce = true
	tx.mu.Unlock()

	gasFeePayer := uint64(0)
	if tx.IsFeeDelegatedTransaction() {
		gasFeePayer, err = tx.ValidateFeePayer(s, picker, currentBlockNumber)
		if err != nil {
			return nil, ErrFeePayer(err)
		}
	}

	sigValidationGas := gasFrom + gasFeePayer
	intrinsicGas = intrinsicGas + sigValidationGas

	tx.mu.Lock()
	tx.validatedGas = &ValidatedGas{IntrinsicGas: intrinsicGas, SigValidateGas: sigValidationGas}
	tx.mu.Unlock()

	return tx, err
}
