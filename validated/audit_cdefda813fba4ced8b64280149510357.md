### Title
Unauthenticated `new_deposit` Floods Verifier `AllSessions`, Evicting Legitimate Nonce Sessions and Permanently Blocking Deposit Finalization — (`core/src/verifier.rs`, `core/src/rpc/aggregator.rs`)

---

### Summary

The Clementine aggregator's `new_deposit` RPC is publicly accessible (no client-certificate enforcement). Each call causes the aggregator to invoke `NonceGen` on every verifier, allocating a `NonceSession` in the verifier's in-memory `AllSessions` store. Because on-chain deposit-outpoint validation only occurs later, inside `deposit_sign`, sessions created for invalid deposits are **never cleaned up**. Once `AllSessions` reaches `MAX_NUM_SESSIONS = 2000`, every new session evicts the oldest one. An attacker who floods `new_deposit` with fake outpoints can continuously evict legitimate sessions, causing every real deposit to fail at `deposit_sign` with "Session not found" and permanently blocking deposit finalization.

---

### Finding Description

**Step 1 – Aggregator is publicly reachable.**
The aggregator server is created without enforcing client certificates:

> "The aggregator does not enforce client certificates but does use TLS for encryption." — `docs/usage.md:203` [1](#0-0) 

When `client_verification = false` (the documented aggregator default), the `Noop` interceptor is installed, so any TLS client can call `new_deposit`.

**Step 2 – `new_deposit` calls `NonceGen` before any on-chain validation.**
Inside `new_deposit`, the aggregator calls `create_nonce_streams` (which invokes `NonceGen` on every verifier) **before** any Bitcoin-chain check of the deposit outpoint: [2](#0-1) 

On-chain validation (`is_deposit_valid`) only runs later, inside the verifier's `deposit_sign`: [3](#0-2) 

**Step 3 – Sessions from failed deposits are never removed.**
`deposit_sign` removes the session from `AllSessions` only inside a spawned task, **after** `is_deposit_valid` has already returned successfully. If `is_deposit_valid` fails (fake outpoint → UTXO not on-chain), the function returns early and the session is never touched: [4](#0-3) 

The session therefore remains in `AllSessions` indefinitely.

**Step 4 – FIFO eviction silently drops legitimate sessions.**
`AllSessions` enforces a hard cap of `MAX_NUM_SESSIONS = 2000`. When the cap is exceeded, `remove_oldest_session` pops the front of the FIFO queue: [5](#0-4) [6](#0-5) 

**Step 5 – Legitimate `deposit_sign` fails.**
When the aggregator later calls `deposit_sign` for a real deposit, the verifier looks up the session by `session_id`. If that session was evicted, the call fails: [7](#0-6) 

The aggregator's `new_deposit` propagates the error, and the deposit cannot be finalized.

---

### Impact Explanation

A user who has already broadcast a Bitcoin transaction to the deposit address (locking real BTC) cannot finalize the deposit. The BTC remains locked in the deposit script until the `user_takes_after` relative timelock (200 blocks ≈ 33 hours on mainnet) expires, at which point the user can reclaim it via the recovery path. During that window the BTC is inaccessible. If the attacker runs the flood continuously, **no deposit can ever be finalized**, permanently breaking bridge liveness and temporarily locking every in-flight deposit's BTC. [8](#0-7) 

---

### Likelihood Explanation

- The aggregator endpoint is publicly reachable (TLS only, no client cert).
- Each `new_deposit` call with a syntactically valid but non-existent outpoint succeeds through `collect_and_distribute_keys` and `NonceGen` before failing at `deposit_sign`.
- The server-side rate limit is `ratelimit_req_count = 1000` per 60 seconds per connection; the attacker can open multiple connections or pipeline requests.
- `MAX_NUM_SESSIONS = 2000` means 2000 fake calls saturate the store.
- Cost to the attacker: negligible (no BTC required, only network traffic). [9](#0-8) 

---

### Recommendation

1. **Validate the deposit outpoint on-chain before calling `NonceGen`.** Move the `is_deposit_valid` (or at minimum the UTXO existence check) into `new_deposit` on the aggregator, before `create_nonce_streams` is invoked.

2. **Clean up orphaned sessions.** If `deposit_sign` fails for any reason, explicitly remove the corresponding session from `AllSessions` (pass `session_id` back to the error path and call `remove_session_with_id`).

3. **Authenticate `new_deposit` callers.** Require a valid deposit proof (e.g., a Bitcoin transaction inclusion proof with sufficient confirmations) before the aggregator initiates the signing pipeline.

4. **Bound session lifetime.** Add a TTL to `NonceSession` entries so that sessions that are never consumed by `deposit_sign` expire automatically.

---

### Proof of Concept

```
# Attacker script (pseudocode)
for i in 1..2001:
    # Construct a syntactically valid but non-existent outpoint
    fake_txid = random_32_bytes()
    fake_vout  = 0

    # Call the publicly accessible aggregator endpoint
    aggregator.new_deposit(
        deposit_outpoint = { txid: fake_txid, vout: fake_vout },
        deposit_data     = BaseDeposit { evm_address: [0u8;20], recovery_taproot_address: any_valid_addr }
    )
    # Each call:
    #   1. Aggregator calls NonceGen on all verifiers → session_i created
    #   2. Aggregator calls deposit_sign → is_deposit_valid fails (UTXO absent)
    #   3. session_i remains in AllSessions, never cleaned up

# After 2000 iterations, AllSessions on every verifier is full.
# Any subsequent legitimate new_deposit call:
#   1. NonceGen creates session_legit → evicts oldest orphaned session (fine so far)
#   2. Attacker immediately fires another fake call → evicts session_legit
#   3. Legitimate deposit_sign: remove_session_with_id(session_legit) → Err("Session not found")
#   4. Deposit fails; user's BTC locked for user_takes_after blocks.

        let session_id = {
            let all_sessions = &mut *self.nonces.lock().await;
            all_sessions.add_new_session_with_random_id(session)?
        };

        Ok((session_id, pub_nonces))
