### Title
Missing user-specified deadline parameter in WombatStaking deposit/withdraw and SmartWomConvert swaps allows stale transaction execution at unfavorable prices - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.deposit`, `WombatStaking.withdraw`, and `SmartWomConvert._convertFor` all pass `block.timestamp` as the `deadline` argument to the underlying Wombat pool/router calls instead of accepting a user-supplied deadline. Because `block.timestamp` is evaluated at the moment of execution (not at the moment of signing), the "deadline" check performed by the downstream Wombat pool/router is always trivially satisfied, regardless of how long the transaction sat unconfirmed in the mempool. ### Finding Description
`WombatStaking.deposit()` forwards `block.timestamp` to `IWombatPool.deposit(...)` as the deadline: [4](#0-3) . Likewise `WombatStaking.withdraw()` forwards `block.timestamp` to `IWombatPool.withdraw(...)`: [5](#0-4) . `SmartWomConvert._convertFor()` also uses `block.timestamp` when calling `IWombatRouter.swapExactTokensForTokens(...)`: [6](#0-5) .

None of `deposit`, `withdraw`, `convert`, or `convertFor` expose a `deadline` parameter that the calling wallet can pre-sign, matching the same root cause described in the referenced report for `safETH.stake()`: the deadline is computed at execution time rather than supplied by the user, so it provides no actual protection against a transaction being held (e.g., by a validator, relay, or simply due to network congestion) and later executed once market conditions have shifted.

The interfaces (`IWombatPool`, `IWombatAssetMock`) are explicitly designed to accept an externally supplied deadline: [7](#0-6) , but `WombatStaking` never exposes this to its own callers, defeating the purpose of the parameter entirely.

### Impact Explanation
A user's `deposit`/`withdraw`/`convert` transaction can be delayed in the mempool (intentionally, via MEV, or unintentionally due to low gas price) and executed at a much later block where pool composition/price has changed. Since the on-chain deadline check always passes (`block.timestamp <= block.timestamp`), the only remaining protection is the static `_minimumLiquidity` / `_minAmount` / `_minRec` slippage bound chosen at signing time, which does not account for the time value of the position. This allows the transaction to be executed at the worst price still satisfying the stale slippage bound, resulting in value extraction from the user (e.g., via sandwiching or unfavorable price movement realized well after the user intended the trade to execute or expire).

### Likelihood Explanation
Any unprivileged wallet calling `WombatStaking.deposit`, `WombatStaking.withdraw`, or `SmartWomConvert.convert`/`convertFor` is affected; no privileged role is required to trigger the condition — it only requires a delayed inclusion of the transaction, which is a common and realistic MEV/mempool scenario.

### Recommendation
Add a user-supplied `deadline` parameter to `WombatStaking.deposit`, `WombatStaking.withdraw`, `SmartWomConvert.convert`, and `SmartWomConvert.convertFor`, require `block.timestamp <= deadline`, and forward that same user-supplied deadline to the downstream `IWombatPool`/`IWombatRouter` calls instead of `block.timestamp`.

### Proof of Concept
1. User A submits `WombatStaking.deposit(lpAddress, amount, minimumLiquidity, for, from)` with a `minimumLiquidity` reflecting current pool pricing.
2. Transaction is delayed (e.g., held by a searcher/validator) for an extended period while pool composition shifts.
3. Transaction is eventually mined; `block.timestamp` at execution is passed as `deadline` to `IWombatPool.deposit`, so the deadline check trivially passes: [4](#0-3) .
4. User A receives `lpReceived` computed from the now-stale, worse pool state, but the transaction still satisfies the old `minimumLiquidity`, resulting in an unexpected loss of value the deadline mechanism was meant to prevent.
