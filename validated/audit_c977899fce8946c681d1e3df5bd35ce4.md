### Title
Cached preprocess seed reused across `share`/`complete` invocations enables nonce reuse and validator key recovery - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary

The coordinator's MuSig-based signing protocol persists a `CachedPreprocess` in the DB keyed only by `(context_tag, attempt)`. Every call to `preprocess_internal`/`share_internal`/`complete` for the same context regenerates the *same* nonces from that seed via `AlgorithmSignMachine::from_cache`. `DkgConfirmer::share` and `DkgConfirmer::complete` each call `share_internal` with attacker-influenced `preprocesses` maps, so the same nonce can be used to sign under two different binding-factor/challenge tuples — the exact nonce-reuse condition the module itself warns leaks the private key share.

### Finding Description

In `coordinator/src/tributary/signing_protocol.rs`, `preprocess_internal` derives a deterministic FROST machine from a stored seed: if `CachedPreprocesses::get(txn, context)` exists, it XOR-decrypts the seed and calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`, which re-executes `seeded_preprocess` → `ChaCha20Rng::from_seed(seed)` → identical nonces (`crypto/frost/src/sign.rs:121-144`, `268-274`).

`DkgConfirmer::share` calls `share_internal(preprocesses, key_pair)`, and `DkgConfirmer::complete` calls `share_internal` *again* with its own `preprocesses` argument (`signing_protocol.rs:288-327`). The module's own header documents the required invariant — the nonce must only be used if "the received nonce commitments (or the message to be signed)" are identical — and then explicitly admits the check is missing: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" (`signing_protocol.rs:34-51`).

If `share` is invoked with one set of peer preprocesses and `complete` (or a re-executed `share` after restart/reorg of provided messages) is invoked with a different set — preprocesses are untrusted bytes fed to `read_preprocess`/`sign` — `machine.sign` computes a different `preprocesses` challenge `c` while using the same nonce `n`. Both published shares satisfy `s_i = n + λ·x·c_i`, so `(s_1 − s_2) = λ·x·(c_1 − c_2)` reveals `x`, the validator's MuSig secret key (its root-of-trust private key, used via `musig(musig_context(...), self.key, ...)`).

### Impact Explanation

An unprivileged participant who can cause the coordinator to run `share`/`complete` over differing preprocess sets (or any divergence in BFT-finalized messages between executions) obtains two signature shares under one reused nonce and algebraically recovers the validator's private key. That key signs Tendermint/Tributary consensus and DKG confirmations, so recovery compromises the validator's entire root-of-trust identity — matching the CVE's class of a missing policy/context check leaking secret data.

### Likelihood Explanation

The cache is keyed only by `(b"DkgConfirmer", attempt)`, so any code path that invokes the protocol twice for one attempt — `share` followed by `complete`, or re-execution after a partial rebuild — deterministically reuses the nonce. The differing-input precondition only requires that the preprocesses map differ between the two calls, which peer-supplied data controls. The authors' own TODO confirms the guarding check is unimplemented.

### Recommendation

Before calling `machine.sign`, verify that the commitments serialized from the regenerated `preprocess` match what was published on-chain for this context, and that the received preprocess set/message is identical to the one originally signed with this nonce; abort (never re-sign) otherwise. Alternatively, delete/invalidate the `CachedPreprocesses` entry once `share` has been produced so `complete` cannot re-derive live nonces.

### Proof of Concept

1. Coordinator runs `DkgConfirmer::new(key, spec, txn, attempt)` and calls `share(preprocesses_A, key_pair)`, publishing share `s_1` computed with nonce `n` derived from cached seed.
2. Same attempt context is used again via `complete(preprocesses_B, key_pair, shares)` where `preprocesses_B ≠ preprocesses_A` (e.g., a different participant set or a maliciously altered preprocess from a peer). `share_internal` regenerates the identical `n` from the unchanged DB seed and signs under a new challenge `c_2`, producing `s_2`.
3. Observer computes `x = (s_1 − s_2) / (λ·(c_1 − c_2))`, recovering the validator's MuSig secret key.
