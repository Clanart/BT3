### Title
`compound()` sweeps entire contract balance of every configured reward token to caller, stealing residual balances left by other users - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` claims rewards for the specific `_lps`/`_rewards` the caller passes in via `multiclaimOnBehalf`, but the settlement loop that converts/locks/transfers rewards to `msg.sender` iterates the entire `rewards` storage array and reads `IERC20(_tokenAddress).balanceOf(address(this))` rather than the amount actually produced by the caller's own claim. Any resting balance of a configured reward token already sitting in the contract (residue from a previous compound, dust from a `SmartWomConvert._convertFor` that doesn't fully consume the transferred-in amount, or any other prior leftover) is settled to the current unrelated caller.

### Finding Description
`compound()` at <cite repo="Annirich/contracts--013" path="rewards/ManualCompound.sol" start="123,139" end="138,159" /> works in two phases:
1. It calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` [1](#0-0) , which pulls into `ManualCompound` only the rewards tied to the pools/tokens the caller specifies and is actually entitled to.
2. It then loops `for (uint256 i; i < rewardTokensLength; i++)` over the entire configured `rewards` array — independent of `_rewards` — and for each configured token computes `receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))`, then converts/locks/transfers that whole balance to `msg.sender` [2](#0-1) .

There is no per-call delta accounting (e.g. snapshotting balance before/after `multiclaimOnBehalf`) — the code trusts that whatever balance of a configured reward token sits in the contract at settlement time was produced by the current caller's claim. That assumption is false whenever the contract is left holding a positive balance of a configured token from a prior transaction, e.g.:
- `SmartWomConvert._convertFor` (the `convertor` used by `ManualCompound`) computes `buybackAmount`/`convertAmount` from the transferred-in amount and can leave rounding dust of `wom`/`mWom` un-swept in some code paths, or a prior `compound()` call could revert/partially process leaving a positive balance of `_tokenAddress` behind.
- Because `compound()` is a shared, permissionless entry point callable by anyone with any `_lps`/`_rewards` combination (including empty/zero-value claims), any address can call `compound()` with a trivial/no-op claim and still trigger the second loop, which sweeps whatever pre-existing balance of a configured reward token is sitting in the contract to `msg.sender`.

This breaks the invariant that settlement in a single `compound()` invocation must be scoped to what that specific caller's claim produced; instead it is scoped to whatever token balances happen to exist for the globally configured `rewards[i].tokenAddress` set, regardless of `compoundableRewards[token]` bookkeeping or which tokens appear in the caller's own `_rewards` argument.

### Impact Explanation
Any balance of a configured reward token resting in `ManualCompound` — which represents unclaimed/undistributed yield or dust belonging to previous users — can be redirected to an unrelated, unprivileged caller by simply invoking `compound()`. Because the mechanism converts/locks/transfers the *entire* current balance (not a delta), this is a direct transfer of other users' funds/yield to the attacker, matching a Critical/theft-of-funds impact class when a meaningful residual balance exists.

### Likelihood Explanation
Exploitability requires only that a positive residual balance of a configured reward token be present in the contract (e.g., dust from conversion rounding, a partially-processed prior compound, or a direct token transfer to the contract by any party). Any unprivileged EOA can then call `compound()` (even with trivial/empty `_lps`/`_rewards` inputs, since `multiclaimOnBehalf` on an empty list is a no-op) and have the second loop sweep that residue to themselves. No special capital or privileged role is needed, and the attack is repeatable each time residue reappears.

### Recommendation
Track reward amounts on a per-call, delta basis instead of by absolute contract balance: snapshot `IERC20(_tokenAddress).balanceOf(address(this))` immediately before calling `multiclaimOnBehalf`, and only settle `balanceAfter - balanceBefore` for each token in the second loop. Alternatively, have `multiclaimOnBehalf`/the claim path report exactly the amounts credited to the caller and use only that value in the settlement/convert/lock calls, ensuring `compoundableRewards[token]` bookkeeping and settlement scope are strictly tied to the current caller's own claim.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `MasterMagpie`, `ManualCompound`, and a mock reward token configured via `addReward`.
2. Have Victim (Alice) call `compound()` normally such that, due to a mocked `IConverter`/`ILocker`/direct transfer path, the contract is left holding a nonzero residual balance of the reward token afterward (e.g. mock the converter to intentionally not consume 100% of `receivedBalance`, or directly `transfer` reward tokens to `ManualCompound` to simulate dust/donation).
3. Record `residualBalance = token.balanceOf(ManualCompound)` > 0.
4. Have Attacker (Bob), who has no claimable rewards and passes empty/zero-value `_lps`/`_rewards` arrays, call `compound([], [], 0, 0, false)`.
5. Assert: `token.balanceOf(Bob)` increased by `residualBalance` (or the token was locked/converted for Bob's benefit), and `token.balanceOf(ManualCompound)` dropped to 0 — demonstrating funds not produced by Bob's own claim were settled to him.
6. Assert Alice's expected claimable/settled amount is unaffected/reduced relative to what she should have received, confirming the residue — which should have remained recoverable/attributable — was misappropriated by an unrelated caller.
