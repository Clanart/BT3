### Title
Deterministic cached preprocess enables nonce reuse across distinct `share`/`complete` invocations, leaking the MuSig secret key share — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The OpenClaw bug class is "guarded policy applied to new sessions, but existing/cached sessions bypass it." Serai's analog lives in `SigningProtocol::preprocess_internal`: the preprocess seed is stored under a fixed context key (`(b"DkgConfirmer", attempt)`) and is *re-derivable* on every call — `CachedPreprocesses::get` is read but never consumed or marked spent. Every call to `preprocess()`, `share()`, or `complete()` rebuilds identical FROST nonces via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed`. The "one seed, one session" policy that `AlgorithmMachine::preprocess(&mut OsRng)` enforces for fresh sessions is bypassed for the existing-session path: the same nonce material signs whatever `share_internal` is invoked with, as many times as it is invoked.

### Finding Description
- `DkgConfirmer::share` accepts attacker-supplied `preprocesses: HashMap<Participant, Vec<u8>>` and `key_pair: &KeyPair` (`coordinator/src/tributary/signing_protocol.rs:304-310`).
- `share_internal` → `SigningProtocol::share_internal` (`:150-181`) re-enters `preprocess_internal` (`:100-148`), which loads the stored 32-byte seed and calls `from_cache` → `seeded_preprocess` (crypto/frost/src/sign.rs:121-144), regenerating the *same* secret nonces `d, e` every time.
- The caller-controlled `preprocesses` map determines the `included` signer set and each participant's commitments (`crypto/frost/src/sign.rs:290-359`), which determines the binding factors `rho`, the Lagrange coefficient `λ_i`, the group nonce `R`, and hence the challenge `c`.
- Each invocation produces `s = d + rho·e + λ_i·x·c_i` where `x` is the FROST/MuSig secret share (`crypto/frost/src/sign.rs:390-398`). With `d, e, x` as three unknowns, three `share` calls under the same `attempt` context with distinct signer sets/preprocess bytes yield three independent equations — `x` is recovered directly.
- `DkgConfirmer::complete` (`:312-327`) unconditionally calls `share_internal` a second time with its own attacker-supplied `preprocesses`, guaranteeing at least a second share equation even in normal operation. Nothing enforces that the preprocess set in `complete` matches the one used in `share`.

### Impact Explanation
An attacker who can cause multiple `share`/`complete` calls for the same DKG attempt with differing preprocess sets recovers the validator's MuSig secret share for the confirmation key — full key-share recovery from public protocol messages, the exact consequence `CachedPreprocess`'s docstring warns about ("Reuse will enable third-party recovery of your private key share", crypto/frost/src/sign.rs:83-92), realized by Serai's own plumbing rather than integrator misuse.

### Likelihood Explanation
The seed persists in `CachedPreprocesses` indefinitely (no deletion after use, :123-145), `share` is callable with arbitrary preprocess maps, and `complete` re-signs by construction. Exploitation needs only that distinct sets of preprocess bytes reach `share`/`complete` for one attempt — precisely the untrusted-bytes → `read_preprocess` route (`:164-167`).

### Recommendation
Bind the cached seed to the exact signer set/preprocess bytes: store a commitment (hash) of the canonicalized `preprocesses` alongside the seed on first use and refuse `share_internal`/`complete` with a mismatched set; or delete/mark the seed spent once a share is emitted and derive crash-recovery determinism from `(context, set)` rather than `context` alone.

### Proof of Concept
1. For attempt `a`, call `DkgConfirmer::share(preprocesses_A, kp)` with set S₁ → share `s₁ = d + ρ₁e + λ₁·x·c₁`.
2. Call `share(preprocesses_B, kp)` (or `complete` with different bytes) with sets S₂, S₃ → `s₂`, `s₃` over the same `d, e`.
3. Solve the 3×3 linear system over `Scalar` for `x`; verify `G·x` equals the participant's verification share.

(Unverified: whether higher-level tributary code limits `share` to one call per attempt — the API itself places no such constraint, and `complete` inherently re-derives a share.)
