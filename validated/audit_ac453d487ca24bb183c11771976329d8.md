## Finding: `SAFER_RESOURCE_GROUPS` retrofit check is bypassed when the old module carries no metadata at all - (File: aptos-move/aptos-vm/src/verifier/resource_groups.rs)

### Summary
`extract_resource_group_metadata_from_module` only walks `old_module.struct_defs()` to populate the `structs` set **inside** the `if let Some(metadata) = get_metadata_from_compiled_code(old_module)` branch. If the previously-published module has no Aptos runtime metadata attached at all, the function returns three empty collections, including an empty `structs` set, instead of the actual struct names. [1](#0-0) 

### Finding Description
`validate_module_and_extract_new_entries` uses the `structs` set returned from `extract_resource_group_metadata_from_module` on the *old* module to detect "retrofitting" — i.e. an upgrade that gives an existing, previously plain struct a new `resource_group`/`resource_group_member` attribute: [2](#0-1) 

The comment at line 171 explicitly assumes `structs` contains "original structs that do not have resource group affiliation" — but this assumption only holds when the old module had *some* metadata blob. If the old module published with zero metadata (no struct attributes whatsoever, which is the normal case for most simple `struct Foo has key {...}` declarations that never use any `#[...]` attribute), `get_metadata_from_compiled_code` returns `None` and the whole struct-name collection is skipped, yielding an empty `BTreeSet`. Consequently, for `group in new_groups.keys() { structs.remove(group) }` and the equivalent for `new_members`, `structs.remove(..)` always returns `false` because the set is empty — regardless of whether that struct name actually existed unrelated to resource groups in the old module. The "Invalid addition of resource_group[_member] attribute" error at lines 178/184 can never fire in this scenario. [3](#0-2) 

This means an unprivileged package owner can:
1. Publish module `M` (v1) with a struct `Foo has key { ... }` and no `#[...]` attributes anywhere in the module (so `get_metadata_from_compiled_code` returns `None`).
2. Publish an upgrade (v2) of the same module with `SAFER_RESOURCE_GROUPS` enabled that adds `#[resource_group_member(group = ...)]` (or `#[resource_group(...)]`) on `Foo`, reclassifying it as a resource-group member/container.
3. The "Invalid addition" guard, whose entire purpose is to prevent exactly this reclassification, never triggers because `structs` was empty coming out of the old module (no metadata to scan) rather than containing `Foo`.

### Impact Explanation
Resource-group membership is not just a metadata label — it changes how the VM constructs and interprets the on-chain `WriteSet`/global storage key for that struct type: group members are packed inside a single `0x...::ResourceGroupContainer` state-slot value rather than being stored at their own flat `StructTag` state key. If `Foo` already had live resources stored at its original flat key before the upgrade, this reclassification changes the storage encoding contract for that type after the upgrade without the compatibility layer objecting, corrupting the relationship between the old (flat) resource storage and the new (grouped) storage semantics for existing state. This is exactly the kind of storage-key layout corruption the `SAFER_RESOURCE_GROUPS` check was introduced to prevent.

### Likelihood Explanation
This requires no special privilege beyond being able to publish and later upgrade one's own module (a normal, permissionless publish flow), and the "no metadata at all" precondition is common — most modules that never use any `#[...]` attribute compile with zero metadata. `SAFER_RESOURCE_GROUPS` must be enabled on the network for the vulnerable code path (the guard it's meant to add) to matter at all; when it is enabled, the gap described above defeats its protection specifically for metadata-less predecessor modules.

### Recommendation
In `extract_resource_group_metadata_from_module`, always collect `structs` from `old_module.struct_defs()` independent of whether `get_metadata_from_compiled_code` returns `Some` or `None` — the struct-name enumeration should not be conditioned on the presence of any metadata blob, only the `groups`/`members` maps should be. This restores the invariant that `structs` always represents all struct names not already known to have a resource-group affiliation.

### Proof of Concept
1. Publish module `0xf00d::M` containing `struct Foo has key { x: u64 }` with no `#[...]` attributes anywhere in the module bundle, so the compiled module has no runtime metadata.
2. With `SAFER_RESOURCE_GROUPS` enabled, publish an upgrade of `0xf00d::M` adding `#[resource_group_member(group = 0xf00d::M::SomeGroup)]` to `Foo` (with a compatible `SomeGroup` container also declared/available).
3. Expect `metadata_validation_err("Invalid addition of resource_group_member attribute")` per the intent of `validate_module_and_extract_new_entries`; observe the publish succeeds instead, because `extract_resource_group_metadata_from_module` returned an empty `structs` set for the metadata-less v1 module at aptos-move/aptos-vm/src/verifier/resource_groups.rs:210-211.

Note: I could not fully verify from static reading alone whether `SAFER_RESOURCE_GROUPS` is currently enabled by default on mainnet, or whether any additional downstream check (outside this file) independently blocks such a reclassification for already-populated resources at the read/write-set construction layer; this should be validated with a live e2e test (mirroring the harness pattern in `aptos-move/e2e-move-tests/src/tests/resource_groups.rs`) before treating the storage-corruption impact as confirmed end-to-end. [4](#0-3)

fn verify_unsafe_resource_group_upgrades() {

    let mut builder = PackageBuilder::new("Package");
    builder.add_source("m.move", source);
    let path = builder.write_to_temp().unwrap();

    assert_success!(result);
