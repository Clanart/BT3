### Title
mWOMSVBaseRewarder._calExpireForfeit never applies mWomSV cooldown forfeiture, allowing unlocking holders to claim 100% of bonus rewards - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` sets `rewardableAmount = _amount` unconditionally and never queries `mWomSV.getRewardablePercentWAD(_account)`, unlike the structurally identical `vlMGPBaseRewarder._calExpireForfeit`, which does call `vlMGP.getRewardablePercentWAD(_account)` to compute a pro-rata forfeiture for accounts in cooldown/unlocking. As a result, any mWomSV holder who has started an unlock can claim their full bonus reward via `getReward`/`_sendReward` with zero forfeiture, and the forfeiture pool that should be redistributed to fully-locked stakers never receives its share.

### Finding Description
`mWOMSVBaseRewarder.getReward(_account, _receiver)` (onlyMasterMagpie, reachable from `MasterMagpie.claim`) calls `_sendReward`, which computes `forfeitAmount = _calExpireForfeit(_account, userRewards[...])` and sends `toSend = userRewards - forfeitAmount` to the user, queuing `forfeitAmount` back into the pool via `_queueNewRewardsWithoutTransfer` [1](#0-0) .

The forfeiture logic itself is broken: `_calExpireForfeit` sets `rewardableAmount = _amount` directly, so `forfeitAmount = _amount - rewardableAmount` is always `0`, and `mWOMSV`/`getRewardablePercentWAD` is never consulted [2](#0-1) .

This contrasts directly with the analogous `vlMGPBaseRewarder._calExpireForfeit`, which correctly computes `rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account)` and applies it to scale down `rewardableAmount` for accounts in cooldown, forfeiting the rest to be redistributed via `_queueNewRewardsWithoutTransfer` [3](#0-2) .

`mWomSV.sol` (in `wombat/mWomSV.sol`) implements cooldown/unlock semantics analogous to `VLMGP.sol`, including a `getRewardablePercentWAD`-style function referenced by grep results, confirming that the concept of pro-rata forfeiture for unlocking holders is a first-class feature of the mWomSV locker that `mWOMSVBaseRewarder` simply fails to invoke. Since `mWOMSVBaseRewarder` implements `ILocker`-based staking accounting (`balanceOf` reads `stakingInfo` from `MasterMagpie`) exactly like `vlMGPBaseRewarder`, there is no structural reason for the omission other than a missing call — this is a copy-paste omission bug, not an intentional design difference.

No existing modifier (`onlyMasterMagpie`, `updateReward`, `nonReentrant`) prevents this, since these only gate caller identity and reward-index bookkeeping, not the forfeiture calculation itself.

### Impact Explanation
This is a theft/permanent loss of unclaimed yield: users who should forfeit a pro-rata share of bonus rewards while in mWomSV cooldown/unlocking instead receive 100% of their accrued bonus rewards, and the forfeiture pool that should be redistributed to fully-locked stakers is left permanently empty of that share. This matches the "theft or permanent freezing of unclaimed yield" impact class, affecting all mWomSV bonus reward pools using `mWOMSVBaseRewarder`.

### Likelihood Explanation
The precondition is simply holding mWomSV and calling the public unlock/cooldown mechanism, then claiming bonus rewards through the normal `MasterMagpie.claim` → `mWOMSVBaseRewarder.getReward` path. No special privileges, capital beyond normal staking, or complex setup are required, and the exploit is repeatable by any holder every time they have pending bonus rewards while in cooldown — making this a systemic issue rather than an edge case.

### Recommendation
Modify `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`: query `mWOMSV.getRewardablePercentWAD(_account)` (add this method to `ILocker`/mWomSV interface as needed) and compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18` before deriving `forfeitAmount`, so that cooldown/unlocking mWomSV holders forfeit their pro-rata share exactly as vlMGP holders do.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `MasterMagpie`, and `mWOMSVBaseRewarder`; register a bonus reward token and fund the pool via `queueNewRewards`.
2. User A and User B each stake equal amounts of mWomSV and accrue equal pending bonus rewards.
3. User A calls `mWomSV.startUnlock(amount)` (or equivalent cooldown-initiating function) to enter cooldown, reducing their `getRewardablePercentWAD` below 1e18.
4. User A calls `MasterMagpie.claim` → `mWOMSVBaseRewarder.getReward`, and asserts `RewardPaid` amount equals 100% of `userRewards` (no forfeiture applied) — i.e., `toSend == userRewards[token][A]` and `forfeitAmount == 0`, despite `mWomSV.getRewardablePercentWAD(A) < 1e18`.
5. Compare against an equivalent scenario using `vlMGPBaseRewarder`/`VLMGP` where a cooling-down user calling `getReward` correctly forfeits a proportional share (`forfeitAmount > 0`), confirming the divergence in behavior.
6. Assert User B (fully locked, no cooldown) never receives the redistributed forfeiture share that should have come from User A's unlock, showing permanent loss of the entitled redistribution.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```
