Based on my investigation, the claim's core factual assertion holds: aside from `add_pending_delegator_rewards` (increment on deposit) and `withdraw()`'s reserve check (read), the only production write-paths I found to `pending_delegator_rewards` are the increment in `deposit_delegator_rewards`, and the field is otherwise read-only in the reward-calculation pipeline (`calculate_block_reward` reads it to compute payouts but the vote account itself is never mutated in `store_stake_accounts_in_partition` / `distribute_epoch_rewards_in_partition` — only stake accounts are credited via `checked_add_lamports`). The only place the field is set to `0` is inside `#[cfg(test)]` test functions in `vote_processor.rs`, which manually stage the "already cleared" scenario rather than exercise real distribution logic.

Audit Report

## Title
`pending_delegator_rewards` is never decremented after block rewards are distributed to stakers, permanently over-reserving vote-account lamports - (File: `programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

## Summary
`deposit_delegator_rewards` increments a vote account's `pending_delegator_rewards` counter on deposit [1](#0-0) , and `withdraw()` gates withdrawable balance and full account closure on the live value of that same field [2](#0-1) . `calculate_block_reward` reads `pending_delegator_rewards` each epoch to pro-rate and pay out `block_reward` to stake accounts [3](#0-2) , but no production code path subtracts the distributed amount back out of the vote account's `pending_delegator_rewards` field.

## Finding Description
The distribution pipeline (`calculate_stake_rewards_and_commissions` → `store_stake_accounts_in_partition` → `distribute_epoch_rewards_in_partition`) only ever credits lamports to stake accounts (`checked_add_lamports` for `block_reward`) [4](#0-3)  and tracks aggregate `block_reward_lamports_distributed` for metrics/capitalization/sysvar bookkeeping [5](#0-4) [6](#0-5) . It never re-reads or writes the vote account's `pending_delegator_rewards` field to decrement it. The only setters of that field in non-test production code are `add_pending_delegator_rewards` (increment) [7](#0-6)  and `pending_delegator_rewards()` getter used purely for reads [8](#0-7) . The only place the field is assigned `0` is inside `#[cfg(test)]` unit tests in `vote_processor.rs` that manually stage the "rewards cleared" scenario rather than exercising real distribution logic [9](#0-8) . `withdraw()`'s reserve check therefore uses a monotonically non-decreasing value as its floor [10](#0-9) , even though the underlying obligation has been discharged via stake-account credits.

I was unable to search every file in the repository within the available tool budget (e.g., `runtime/src/block_component_processor/vote_reward.rs`, which handles a related but distinct block-level reward path, contains no references to `pending_delegator_rewards` or lamport-subtraction logic on vote accounts, but this does not rule out a decrement occurring in some other file not surfaced by search).

## Impact Explanation
If confirmed, this would permanently over-reserve lamports in the vote account: the authorized withdrawer would be denied access to funds already paid out to delegators, and in the `remaining_balance == 0` branch, closing the vote account is unconditionally rejected while `pending_delegator_rewards > 0` [11](#0-10) , which can permanently lock funds. This falls into the "fund loss" category of allowed impacts, contingent on the SIMD-0123/SIMD-0464 block-revenue-sharing feature being active and used.

## Likelihood Explanation
This requires no malicious actor and would trigger under ordinary operation of `deposit_delegator_rewards` plus one or more reward-distribution epochs with `block_revenue_sharing` active. However, this feature is gated behind multiple feature flags (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`) that are not yet globally activated in mainnet production, and my search coverage of the full reward-distribution and vote-program call graph was incomplete — I could not fully rule out a decrement occurring in a file outside the areas searched (e.g., commission/custom-collector distribution logic, or additional vote-program instruction handlers not surfaced by grep/codebase_search).

## Recommendation
After `calculate_block_reward` computes `block_reward` paid from a vote account's `pending_delegator_rewards` pool, decrement that vote account's `pending_delegator_rewards` field by the total amount distributed for that epoch, symmetric to `add_pending_delegator_rewards`. Add an invariant test asserting `pending_delegator_rewards_after == pending_delegator_rewards_before - total_block_reward_distributed_from_this_vote_account` across a full distribution cycle.

## Proof of Concept
1. Call `deposit_delegator_rewards` on a vote account to set `pending_delegator_rewards = X` via `add_pending_delegator_rewards` [12](#0-11) .
2. Enable `block_revenue_sharing`, delegate stake, and let an epoch boundary trigger `calculate_stake_rewards_and_commissions` → `calculate_block_reward`, crediting `block_reward` to the delegator's stake account [13](#0-12) .
3. After `store_stake_accounts_in_partition` completes, read back the vote account's `pending_delegator_rewards` — assert it remains `X`, not `X - block_reward` [5](#0-4) .
4. Call `withdraw()` as the authorized withdrawer and confirm the reserve check still requires leaving `rent_exempt_minimum + X`, denying access to already-distributed funds [10](#0-9) .

        }

        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)

                stake_history,
                new_warmup_cooldown_rate_epoch,
