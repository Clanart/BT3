### Title
Cached FROST preprocess is never deleted and is re-used to produce multiple signature shares under the same nonce - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The CVE-2023-3141 bug class is a stale-state / use-after-free lifecycle flaw: a resource that must be consumed once at removal is instead retained and dereferenced again. Serai's coordinator-side MuSig/FROST signing protocol has the same lifecycle defect in reverse: `preprocess_internal` persists the preprocess seed in `CachedPreprocesses` and re-loads it on every call, so each invocation of `share_internal`/`complete_internal` regenerates the *same* secret nonces and emits a *new* signature share. If two calls for the same `(b"DkgConfirmer", attempt)` context are given different participant preprocess sets (and hence a different aggregate nonce and challenge), the resulting pair of shares leaks the validator's private key share — the exact failure `CachedPreprocess`'s documentation warns about.

### Finding Description
In `SigningProtocol::preprocess_internal`, a fresh `AlgorithmMachine` preprocess is cached as a 32-byte ChaCha seed in the `CachedPreprocesses` DB table keyed only by `context` [1](#0-0) . Every subsequent call loads the same seed, decrypts it, and rebuilds an identical `AlgorithmSignMachine` via `AlgorithmSignMachine::from_cache` [2](#0-1) . The entry is never removed after the preprocess is consumed — there is no `CachedPreprocesses::del` anywhere in the protocol, even though `from_cache` is documented with "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" [3](#0-2) .

`share_internal` calls `preprocess_internal` again and then `machine.sign(preprocesses, msg)` where `preprocesses` is built entirely from caller-supplied bytes via `read_preprocess` [4](#0-3) . `DkgConfirmer::share` and `DkgConfirmer::complete` each independently call `share_internal` — `complete` even re-runs the whole signing step with its own supplied `preprocesses` map [5](#0-4) . Both the signer set and the per-participant preprocesses are attacker-influenced inputs: `threshold_i_map_to_keys_and_musig_i_map` reconstructs the MuSig participant ordering directly from the submitted map keys [6](#0-5) . The file's own header acknowledges nonce reuse occurs if "the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" — which is precisely what the persistent cache enables across `share`/`complete` re-executions [7](#0-6) .

### Impact Explanation
Because `seeded_preprocess` deterministically regenerates the same `nonces` and `commitments` from the cached seed [8](#0-7) , two signing passes that differ in the signer set, a peer's preprocess commitments, or the resulting aggregate nonce produce two shares `z₁ = k + λ·s·c₁` and `z₂ = k + λ·s·c₂` under the same nonce `k`. With MuSig key aggregation `λ` fixed per key, `s = (z₁ − z₂) / (λ·(c₁ − c₂))` recovers the victim validator's MuSig secret share. That share is the root-of-trust validator key used for DKG confirmation on Substrate (`set_keys_message`), so its recovery compromises the validator's signing identity and its ability to securely participate in set-key confirmation.

### Likelihood Explanation
Triggering requires two signing passes under the same `(b"DkgConfirmer", attempt)` context with distinct supplied preprocess sets — e.g., a `share` followed by a `complete` carrying a different preprocess map, or re-execution after the observed preprocess set changed. These inputs arrive as tributary-signed messages, so the practical exposure is bounded to validator-submitted data and BFT ordering assumptions the code explicitly relies on; the author flags a matching check as still TODO ("check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)") [9](#0-8) . The flaw is nevertheless a concrete one-shot-keyed resource being reused, with deterministic key-share recovery as the payoff, warranting High severity.

### Recommendation
Delete (or tombstone) the `CachedPreprocesses` entry the first time a share is emitted for a context, and bind the accepted preprocess set: store a hash of the serialized preprocesses used at first `sign` and refuse to emit a second share under a differing set/message for the same context. Implement the noted TODO of verifying the rebuilt commitments match the on-chain preprocess before publishing shares, so re-execution can never mint a second share under a different aggregate nonce.

### Proof of Concept
1. Under context `("DkgConfirmer", attempt = a)`, call `DkgConfirmer::share(preprocesses_A, key_pair)` — the seed `S` is cached, nonces `k` derived, share `z₁ = k + λ·s·c₁` emitted for signing set/commitments A.
2. Call `DkgConfirmer::complete(preprocesses_B, key_pair, shares)` where `preprocesses_B` differs from `preprocesses_A` in any participant's commitment or the included signer set. `complete` re-invokes `share_internal`, reloads the same undeleted seed `S`, regenerates identical `k`, and emits `z₂ = k + λ·s·c₂` with `c₂ ≠ c₁` (different aggregate nonce/binding).
3. Compute `s = (z₁ − z₂)·(λ·(c₁ − c₂))⁻¹` — the validator's MuSig private key share — using only the two public shares and public challenge data.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
