### Title
Forged `ReceivedOutput` deserialization inflates unspendable Bitcoin inputs - ([File: `networks/bitcoin/src/wallet/mod.rs`])

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without validating that the offset derives the output’s Taproot script or that the output is a genuine scan result for that outpoint. [1](#0-0)  Because `SignableTransaction` trusts the serialized value when calculating available inputs, attacker-supplied bytes can report spendable Bitcoin that is not actually spendable. [2](#0-1) 

### Finding Description
`ReceivedOutput` claims to represent “a spendable output,” but its reader only checks scalar canonicity and Bitcoin consensus encoding. [3](#0-2) [1](#0-0)  Legitimate outputs produced by `Scanner::scan_transaction` bind the offset to the observed script and bind the outpoint to the containing transaction, but that invariant is not represented or checked during deserialization. [4](#0-3) 

`SignableTransaction::new` then trusts the embedded `TxOut` value as available input and uses the embedded `OutPoint` as the transaction input. [2](#0-1)  Although `SignableTransaction::multisig` verifies that the offset produces the claimed script, it does not verify that the outpoint exists or that the claimed amount matches the on-chain output. [5](#0-4) 

### Impact Explanation
An attacker who can supply a serialized `ReceivedOutput` can inflate the amount of a real wallet-controlled output or reference a nonexistent outpoint while retaining a valid wallet-controlled script. [1](#0-0)  The wallet can consequently report funds as available and construct/sign a transaction that Bitcoin consensus will reject, causing funds reported received to be unspendable. [6](#0-5) 

### Likelihood Explanation
This requires callers to deserialize `ReceivedOutput` from an attacker-influenced source rather than only consuming outputs produced directly by `Scanner`. [4](#0-3)  Within that supported input boundary, exploitation only requires modifying the encoded amount or outpoint of an otherwise valid output; no validator privileges, secret material, or malformed scalar encoding is needed. [1](#0-0) 

### Recommendation
Treat `ReceivedOutput::read` as deserialization of untrusted claims rather than proof of spendability. At minimum, validate that `p2tr_script_buf(group_key + G * offset)` equals `output.script_pubkey`; preferably include the expected group key or fingerprint in the serialized context so readers cannot accidentally validate against the wrong wallet. [5](#0-4)  Before spending, independently resolve the `OutPoint` through the Bitcoin node and compare its value and script to the embedded `TxOut`, or avoid serializing `TxOut`/`OutPoint` as trusted facts altogether. [7](#0-6) 

### Proof of Concept
Starting with a legitimate scanned output, changing only the encoded amount leaves the offset, script, and outpoint fields validly encoded:

```rust
// `received` is a genuine Scanner output.
let mut encoded = received.serialize();

// TxOut consensus encoding starts immediately after the 32-byte offset.
// Overwrite its little-endian `u64` amount with a much larger value.
encoded[32 .. 40].copy_from_slice(&u64::MAX.to_le_bytes());

// Parsing succeeds: all three fields are syntactically valid.
let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
assert_eq!(forged.outpoint(), received.outpoint());
assert_eq!(forged.output().script_pubkey, received.output().script_pubkey);
assert!(forged.value() > received.value());
```

The forged object preserves the wallet script, so `multisig`’s offset-to-script check can still pass while `SignableTransaction` credits `u64::MAX` as input and signs a sighash over the false prevout data. [2](#0-1) [5](#0-4) [7](#0-6)
