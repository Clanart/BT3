### Title
`get-asset-price` prices stSTXbtc/zstSTXbtc using the STX feed instead of the BTC feed - ([File: mainnet/contracts/utility/v0-1-data.clar])

### Summary
`v0-1-data.clar` (the `protocol-data` read-only utility contract) computes stSTXbtc and zstSTXbtc valuations using the wrong Pyth price feed constant — `PYTH-STX` instead of `PYTH-BTC` — mirroring the wildcredit `_priceB`/`_priceA` mix-up where one asset's valuation is silently computed with a different asset's price.

### Finding Description
In `get-asset-price`, every other branch correctly pairs an asset with its own oracle feed (e.g. `sBTC` → `PYTH-BTC`, `stSTX` → `PYTH-STX × ratio`). However, the `stSTXbtc` and `zstSTXbtc` branches are commented as "BTC price" but call `get-pyth-price PYTH-STX`: [1](#0-0) 
This is the same class of bug as the referenced H-01: an asset's notional value is computed off a different asset's price feed (here STX's feed used for a BTC-yield-bearing asset), rather than a stale/third-party oracle issue or a DAO misconfiguration — the wrong constant is hardcoded directly in this function's `if/is-eq` chain, which is distinct from the correct per-asset ident wiring used in `v0-4-market.clar`'s `price-resolve`/`resolve-callcode` path where the base price is passed in as a parameter rather than re-looked-up by asset id.

This `get-asset-price` helper feeds `sum-collateral-usd` and `sum-debt-usd`, which in turn compute `coll-usd`, `debt-usd`, `current-ltv`, and `health-factor` / `is-liquidatable` returned by `get-user-position`: [2](#0-1) 

### Impact Explanation
Since BTC and STX prices diverge substantially and independently, any user holding stSTXbtc/zstSTXbtc collateral or debt would have their USD notional, LTV, and `health-factor`/`is-liquidatable` flags misreported by this read-only contract — understating or overstating actual risk depending on relative STX/BTC price movement. I was not able to fully confirm within the available index whether any on-chain enforcement path (borrow/withdraw/liquidate in `v0-4-market.clar`) consumes `v0-1-data.clar`'s output directly, or whether this contract is purely an off-chain/UI convenience read-only helper; `v0-4-market.clar`'s own health-check path (`price-resolve`, `get-notional-evaluation`) appears to resolve prices per-asset via each asset's registered oracle ident rather than through this hardcoded switch, which would mean actual capital-at-risk borrow/liquidation logic is unaffected and this bug is confined to the reporting layer. Given this uncertainty about the consumer of `get-user-position`, I cannot assert the Critical/High impact classes (theft, insolvency, fund-freezing) are directly reachable through this function without further confirmation of downstream callers (e.g., a liquidation bot or UI trusting `is-liquidatable`/`health-factor` to trigger real liquidation transactions).

### Likelihood Explanation
The bug triggers automatically and deterministically whenever `get-user-position` is called for any account holding `stSTXbtc` (`aid u10`) or `zstSTXbtc` (`aid u11`) collateral or debt — no attacker action is required, only asset registration of stSTXbtc/zstSTXbtc which is already present in the mainnet asset list.

### Recommendation
In `mainnet/contracts/utility/v0-1-data.clar`, change the `stSTXbtc` and `zstSTXbtc` branches of `get-asset-price` to call `get-pyth-price PYTH-BTC` instead of `get-pyth-price PYTH-STX`.

### Proof of Concept
1. Register/hold `stSTXbtc` as collateral (`aid u10`).
2. Call `get-user-position` (read-only) for that account.
3. Observe that `sum-collateral-usd` → `get-asset-price aid=u10` returns a value derived from `PYTH-STX` rather than `PYTH-BTC`: [1](#0-0) 
4. Since BTC/STX prices are uncorrelated in magnitude, the reported `total-collateral-usd`, `current-ltv`, and `health-factor` diverge from the true collateral value.
