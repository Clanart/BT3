### Title
Cross-shop session confusion via unscoped `shopify_user_id` lookup in `SessionRepository#load_session` - ([File: lib/shopify_app/session/session_repository.rb])

### Summary
`ShopifyApp::SessionRepository#load_session` and `UserSessionStorage#retrieve_by_shopify_user_id` locate an online (per-user) session record using only the Shopify `shopify_user_id`, discarding the shop-domain component of the session id and never scoping the `find_by` to the requesting shop. This mirrors the reported `market_id_by_symbol` bug class: a lookup key (`symbol` / `shopify_user_id`) that is not guaranteed unique across the full entity space (`market_id` / `shop + user`) is used with a first-match query (`find()` / `find_by`), silently returning a record that may belong to a different shop.

### Finding Description
`SessionRepository.load_session` parses the session id and, for non-offline (user) sessions, keeps only the trailing user-id segment before delegating to storage: [1](#0-0) 

That id is then resolved with a single unscoped `find_by(shopify_user_id: user_id)`: [2](#0-1) 

The `shopify_user_id` column has no uniqueness constraint/validation — only `shopify_domain` presence is validated: [3](#0-2) 

Because a single Shopify staff account (`shopify_user_id`) can be a collaborator/staff member on multiple shops that each install the app, the `User`/session-storage table can legitimately contain multiple rows sharing the same `shopify_user_id` but different `shopify_domain` and `shopify_token`. `find_by` (like the reported `find()`) returns only the first matching row — not necessarily the row belonging to the shop the current request/JWT is scoped to — exactly analogous to `market_id_by_symbol` returning only the first market matching a non-unique symbol.

The JWT-derived session id used to drive this lookup embeds the shop domain (`current_session_id` builds an id combining shop + user), but `load_session`'s `id.split("_").last` strips that shop context away before the storage lookup occurs, so the shop the JWT was issued for is never used to disambiguate which of the duplicate `shopify_user_id` rows should be returned: [4](#0-3) 

### Impact Explanation
If the returned (wrong-shop) record is used to construct the `ShopifyAPI::Auth::Session` (with its `access_token` and `shop`), the app can operate using another shop's stored offline/online access token for a request that was authenticated (via JWT) against a different shop, potentially resulting in cross-shop access-token disclosure or data being served/written against the wrong shop, i.e., cross-shop access confusion.

### Likelihood Explanation
Requires only that the same Shopify user account (a normal staff/collaborator, not an app developer or host operator) install or be granted app access on two or more shops using this gem's generated `User`/`UserSessionStorage`/`UserSessionStorageWithScopes` models — a common, unprivileged multi-shop scenario, not a misconfiguration. No special secrets or developer access are required to trigger the collision; ordinary merchant/staff usage across shops is sufficient to create duplicate `shopify_user_id` rows, and any subsequent JWT-based request resolves via `load_session`'s unscoped lookup.

### Recommendation
Scope the online-session lookup by both `shopify_user_id` and `shopify_domain` instead of `shopify_user_id` alone: change `UserSessionStorage.retrieve_by_shopify_user_id` (and its `_with_scopes` counterpart) to accept/require the shop domain and query `find_by(shopify_user_id: user_id, shopify_domain: domain)`, and update `SessionRepository.load_session` to preserve and pass through the shop-domain portion of the session id (not just the trailing user-id segment) when resolving user sessions.

### Proof of Concept
1. User `U` (`shopify_user_id = 42`) is staff on Shop A and later becomes staff on Shop B; the app is installed/used on both shops, creating two rows in the `users` table: `(shopify_domain: "shop-a.myshopify.com", shopify_user_id: 42, shopify_token: TOKEN_A)` and `(shopify_domain: "shop-b.myshopify.com", shopify_user_id: 42, shopify_token: TOKEN_B)`.
2. A request carrying a valid JWT/id_token issued for Shop A (`sub=42`) hits an `EnsureHasSession`-protected endpoint; `LoginProtection#load_current_session` computes a session id embedding shop+user and calls `SessionRepository.load_session(session_id)`.
3. `load_session` strips the shop portion via `id.split("_").last` and calls `retrieve_user_session_by_shopify_user_id("42")`, which executes `find_by(shopify_user_id: 42)` with no shop filter.
4. Depending on row insertion/ordering, this can return the Shop B row instead of Shop A's, yielding a `ShopifyAPI::Auth::Session` bound to Shop B's `shopify_token` for a request that authenticated against Shop A — a cross-shop session/token mix-up.

Note: I could not execute this in a live environment; the analysis is based on static code review of `session_repository.rb`, `user_session_storage.rb`, and `login_protection.rb`. Confirming exact real-world exploitability (e.g., row ordering guarantees, whether any downstream shop-domain re-validation exists elsewhere in the request pipeline) would require running the app or further tracing all callers of `current_shopify_session`.

        match = id.match(/^offline_(.*)/)
        if match
          domain = match[1]
          ShopifyApp::Logger.debug("Loading session by domain - domain: #{domain}")
          retrieve_shop_session_by_shopify_domain(domain)
        else
          user = id.split("_").last
          ShopifyApp::Logger.debug("Loading session by user_id - user: #{user}")
          retrieve_user_session_by_shopify_user_id(user)
        end
      end
