## #Vulnerability found

### Title
Oversized/long-line conflict diffs are hidden from review by default while the full untruncated content is still written and staged - ([File: app/src/lib/stores/app-store.ts](app/src/lib/stores/app-store.ts))

### Summary
The reported Solidity bug clamps a `value` parameter for display/processing purposes while the actual transfer still uses the real (unclamped) amount, so funds beyond the "limit" are silently lost/exploitable. GitHub Desktop has a structurally identical pattern in its Copilot merge-conflict-resolution feature: diff size/line-length limits (`MaxDiffBufferSize`, `MaxReasonableDiffSize`, `MaxCharactersPerLine`) only gate what is *rendered* to the user for review. They do **not** gate what is actually written to disk and staged for commit. An attacker who controls the conflicting content (a hostile branch/PR/upstream commit the victim merges, rebases onto, or cherry-picks) can make the resolution diff exceed these thresholds so the diff review UI collapses to "too large to display" or is entirely `Unrenderable`, while `_applyCopilotConflictResolutions` still writes and `git add`s the complete, unreviewed content.

### Finding Description
`app/src/lib/git/diff.ts` defines hard/soft caps used purely to decide how a diff is rendered: [1](#0-0) 

`buildDiff` uses these caps to classify a diff as `Unrenderable` (buffer ≥ 70MB) or `LargeText` (buffer ≥ ~4.375MB, or any single line > 5000 characters) — in both cases the diff is not shown by default: [2](#0-1) 

The UI reflects this by hiding the content behind an extra "Show Diff" click, or omitting it entirely: [3](#0-2) 

This exact diff machinery (`getResolutionDiff` → `buildDiff`) backs the read-only diff preview in the Copilot Conflicts "Changes" tab: [4](#0-3) 

However, when the user clicks "Continue Merge", `_applyCopilotConflictResolutions` writes the model's full `resolution.resolvedContent` to disk unconditionally — with no relationship to whether the diff was ever expanded or even renderable — and stages it: [5](#0-4) 

`onContinue` calls this write/stage step and then proceeds to continue the merge/rebase/cherry-pick without requiring that the diff has been reviewed: [6](#0-5) 

The same `getResolutionDiff`/size-cap path is also used for the plain "ours"/"theirs" manual resolution preview, so this isn't specific to Copilot's model output — any conflict side sourced from attacker-controlled content is affected.

### Impact Explanation
The broken invariant: **the value the user is shown (a size/line-capped diff) is not the value that gets committed (the full, uncapped file content)**. An attacker who controls one side of a merge conflict (a malicious branch, PR, or fetched commit) can pad or obfuscate the conflicting hunk — e.g. a single line over 5,000 characters (trivial to craft, e.g. minified/obfuscated code) or a hunk whose accumulated diff exceeds ~4.375MB — to force the review UI into the collapsed "too large to display" / "Unrenderable" state. The victim, following the normal "resolve conflicts → review → Continue Merge" flow, never sees the injected content, yet it is written to their working tree and staged automatically. This is a silent corruption of what the user commits/pushes, matching the report's core impact of "value above the reviewed/limited amount takes effect while the excess is hidden from the actor who is supposed to control it."

### Likelihood Explanation
No local access, privileges, or leaked credentials are needed — only that the victim resolves a merge/rebase/cherry-pick conflict against attacker-influenced content (a fork/PR branch, or any upstream ref the attacker can push a commit to that later gets merged). Crafting a line over `MaxCharactersPerLine` (5000 chars) is a trivial, natural-looking technique (e.g., a long generated/minified line) that developers routinely encounter and would not find suspicious, making the "hidden by default" review gap easy to trigger without any unnatural user steps.

### Recommendation
Do not decouple "what is shown" from "what is applied." Options:
- Require an explicit, logged acknowledgment ("I have reviewed this diff") before allowing `_applyCopilotConflictResolutions` to write content whose diff was `LargeText`/`Unrenderable`.
- Block/flag automatic staging for any file whose resolution diff exceeded `MaxReasonableDiffSize`/`MaxCharactersPerLine`, surfacing a mandatory warning in the Copilot Conflicts dialog rather than silently proceeding on "Continue Merge".
- Ensure the same guarantee applies to manual ours/theirs resolutions, since they share the same diff-capping code path.

### Proof of Concept
1. Attacker pushes a branch/PR containing a file where the "theirs" side of an eventual conflict has a single line > 5000 characters embedding malicious code (or hunk content pushing the overall diff over ~4.375MB).
2. Victim, in GitHub Desktop, merges/rebases/cherry-picks this branch, hits a conflict on that file, and opens the Copilot Conflicts dialog.
3. `getResolutionDiff` computes the diff; `buildDiff` classifies it as `LargeText` (or `Unrenderable` if bigger), so `SeamlessDiffSwitcher` shows "The diff is too large to be displayed by default" with a "Show Diff" button, or nothing at all — the malicious content is not visible.
4. Victim, trusting Copilot's resolution/summary text (or just wanting to unblock the merge), clicks "Continue Merge" without clicking "Show Diff".
5. `_applyCopilotConflictResolutions` writes `resolution.resolvedContent` (the full, attacker-influenced content) to disk via `writeFile` and runs `git add`, staging it for the next commit — with the victim never having seen the actual bytes committed.
