### Title
Silent, Automatic Rewrite of Git Remote URL Based on Unverified GitHub API `clone_url`, Enabling Push/Fetch Hijack After Repository Rename/Transfer/Ownership-Change - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
GitHub Desktop automatically rewrites a repository's local `origin` remote URL whenever it detects that the associated GitHub repository's `clone_url` (from the GitHub API) differs from the locally configured remote, as long as a loose owner/name/hostname match still holds. This happens silently, with no user confirmation, every time a repository is selected or refreshed. Because the matching used to decide "this is still the same remote" (`urlMatchesRemote`) only compares `hostname`, `owner`, and `name` strings — not a stable repository ID — an attacker who can cause the `owner/name` path to resolve to a different, attacker-controlled repository (e.g., via repo rename + name squatting, or ownership transfer of an abandoned name) can get Desktop to silently repoint the victim's local remote to the attacker's repository.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts:4874-4914` is invoked automatically on every repository selection via `_selectRepositoryRefreshTasks` (`app/src/lib/stores/app-store.ts:2257`). It calls `matchGitHubRepository` (`app/src/lib/stores/app-store.ts:4964-4977`), which derives an `owner`/`name` pair purely by parsing the *current* local git remote URL string — it does not use any stable, attacker-resistant repository identifier such as a database ID. [1](#0-0) 

That `owner`/`name` is then used to fetch fresh repository data from the GitHub API (`api.fetchRepository(owner, name)`), and the result is passed into `updateRemoteUrl`: [2](#0-1) 

`updateRemoteUrl` decides whether to silently call `gitStore.setRemoteURL(...)` based on three checks: protocol match, `remoteUrlUnchanged` (a loose comparison via `urlMatchesRemote`, which only checks hostname/owner/name equality, not full string equality or a stable ID), and `!urlsMatch` (the new URL differs from the old): [3](#0-2) 

`urlMatchesRemote`/`urlsMatch` never validate identity beyond `hostname` + `owner` + `name` strings: [4](#0-3) 

The broken invariant: Desktop assumes that "owner/name still parses the same" is sufficient proof that the GitHub API response for that path still refers to the *same* repository the user originally added. This is not true for GitHub — repository names can be freed up by renaming, transferring, or deleting a repository, and then claimed by a different (attacker-controlled) account/repository. When that happens, `api.fetchRepository(owner, name)` returns an entirely different repository's `clone_url`, and Desktop's existing "unchanged" guard (`remoteUrlUnchanged`) still passes because it's comparing against the *stale* GitHub API `cloneURL` cached from the previous refresh, not against ground truth of a persistent repository identity. There is no user prompt, confirmation dialog, or diff shown before `setRemoteURL` overwrites the remote.

### Impact Explanation
If the attacker succeeds in name-squatting a renamed/deleted/transferred repository that a victim has cloned, the victim's local `origin` remote is silently rewritten to point at the attacker's repository the next time they open that repository in Desktop (which happens automatically, not on demand). Consequences:
- Future `git push` operations initiated from Desktop will silently push the victim's commits (potentially containing proprietary/private code) to the attacker's repository.
- Future `fetch`/`pull` will pull attacker-controlled content into the victim's working copy under the guise of the "same" project, which can be leveraged for follow-on supply-chain or code-injection issues.
- This exactly matches "silent corruption of what the user commits or pushes," since the user has no indication their trusted remote destination changed.

### Likelihood Explanation
This requires no local/physical access, no admin rights, and no prior malware — only that the attacker can get GitHub to resolve `owner/name` to a repository they control (classic repo-jacking/name-squatting after a rename or ownership transfer, a well-documented real-world technique). Desktop performs this refresh automatically and repeatedly (on every repository selection, `app/src/lib/stores/app-store.ts:2257`, and via periodic background refresh paths), so no unusual user action is needed beyond normal day-to-day use of the app.

### Recommendation
- Do not silently rewrite `origin` (or any remote) based solely on `owner`/`name`/`hostname` string matching. Require an explicit, stable repository identity check (e.g., GitHub's numeric repository `id`) before treating an API response as "the same repository, just renamed."
- If the numeric ID doesn't match the previously cached `GitHubRepository`, treat this as a *new* association requiring user confirmation, not an automatic rename-follow.
- When an automatic remote URL change is about to occur, surface a non-blocking but visible confirmation/notification to the user before calling `setRemoteURL`, showing old vs. new URL.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
