### Title
Escrow accounting in `IntentGatewayV2.placeOrder` credits requested amount instead of actual received balance for fee-on-transfer/deflationary tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` escrows `reducedInputs[i].amount` (derived purely from the user-supplied `order.inputs[i].amount` minus a protocol fee) after calling `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)`, without ever checking the actual token balance delta. This is the exact bug class from the referenced Gravity `sendToCosmos` finding: for any fee-on-transfer/deflationary ERC20, the gateway credits more escrow than tokens actually received, letting the escrow become insolvent and letting a filler/beneficiary drain tokens belonging to other users' orders.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder`'s non-predispatch escrow path is: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));

        _orders[commitment][token] += reducedInputs[i].amount;

```

`reducedInputs[i].amount` is computed earlier purely from `order.inputs[i].amount * (1 - protocolFeeBps)` — it is never adjusted for the actual amount the contract received via `transferFrom`: [2](#0-1) 

The predispatch branch of the same function has a comment "Store reduced amount (after protocol fees) in escrow" with the identical flaw — it credits `reducedInputs[i].amount` based on requested amounts, while only checking `balance < requiredAmount` for revert purposes, not crediting the actual swept `balance`: [3](#0-2) 

This is the exact same flaw the external report describes for Gravity's `sendToCosmos`: the amount recorded as "locked"/escrowed does not equal the amount actually transferred into custody, because deflationary/fee-on-transfer tokens deliver less than the nominal `amount` passed to `transferFrom`.

By contrast, the actively-fixed EVM version of this exact contract (`evm/src/apps/IntentGatewayV2.sol`) explicitly guards against this by measuring `balanceOf` before and after the transfer and mutating `order.inputs[i].amount` to the actual received value before computing `reducedInputs`/escrow, with an inline comment documenting the exact defect being fixed: [4](#0-3) [5](#0-4) 

This confirms the team is aware of and treats this bug class as security-relevant, but the Tron contract copy at `evm/tron/contracts/apps/IntentGatewayV2.sol` was not updated with the same fix.

### Impact Explanation
On redemption (`withdraw`), the contract pays out exactly `body.tokens[i].amount` — which is populated from the (inflated) escrow figure via `_orders[commitment][token]` — using a raw `token.call` to `transfer`: [6](#0-5) 

Since `_orders[commitment][token]` was credited with `reducedInputs[i].amount` (based on nominal deposit) rather than the actual tokens the contract received, every deposit of a deflationary/fee-on-transfer token creates a shortfall between total escrowed liabilities and the contract's real token balance. Whichever filler/beneficiary withdraws later drains real balance that includes principal deposited by other orders, i.e. direct theft/loss of funds analogous to the Gravity `sendToCosmos` issue, matching the bounty's "stealing or loss of funds" and "false state acceptance" (escrow state does not reflect true custody) categories.

### Likelihood Explanation
Any unprivileged user can call `placeOrder` with an arbitrary ERC20 `token` address as an order input — there is no allow-list enforced in this file for input tokens, so an attacker fully controls the token contract. An attacker can deploy or use any real-world deflationary/fee-on-transfer token (a well-known token category), place multiple orders to accumulate an inflated escrow ledger relative to actual holdings, then withdraw against orders (as filler completing a fill, or via `cancelOrder`/refund path which also uses the same inflated `order.inputs`/escrow value) to extract more tokens than were ever deposited by that specific order, at the expense of the shared token balance backing other users' orders. No relayer, prover, or admin compromise is required — this is a pure public-entrypoint accounting bug.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure `IERC20(token).balanceOf(address(this))` immediately before and after each `safeTransferFrom`, use the delta as the actual received amount, mutate `order.inputs[i].amount` (and derive `reducedInputs`/commitment) from that measured value instead of the caller-supplied nominal amount, for both the direct-transfer branch and the predispatch/dispatcher-sweep branch.

### Proof of Concept
1. Deploy a 1% fee-on-transfer ERC20 (as used in the project's own test, `FeeOnTransferToken`, `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2502-2547`).
2. Call `placeOrder` on `evm/tron/contracts/apps/IntentGatewayV2.sol` with `order.inputs[0].amount = 1000e18` of the FOT token, `protocolFeeBps = 0`.
3. `safeTransferFrom` moves only `990e18` into the gateway (1% burned in transfer), but `_orders[commitment][token]` is credited with `reducedInputs[0].amount = 1000e18` (unreduced, since no protocol fee) — 10e18 more than the gateway actually holds.
4. Repeat step 2 with a second, unrelated order using a normal (non-fee) token to top up the gateway's FOT balance is not even necessary if multiple FOT orders are placed: the ledger `_orders[...]` sums to more than `FOT.balanceOf(gateway)`.
5. On `withdraw`/fill, whichever beneficiary is processed can be paid the full nominal `1000e18` (since `body.tokens[i].amount` — supplied from source-chain order data reproduced by the filler/withdrawer — matches the escrow credit), draining `10e18` of FOT belonging to the shortfall, leaving a later legitimate withdrawer's `transfer` call to fail or receive less than entitled once the pool is exhausted.

Note: I could not execute this PoC in the sandbox (no terminal/build tool access here); the trace above is derived directly from reading the escrow crediting logic against the payout logic in the same file, matching the project's own fee-on-transfer regression tests that validate the *fixed* EVM contract's behavior but do not cover the Tron copy.
