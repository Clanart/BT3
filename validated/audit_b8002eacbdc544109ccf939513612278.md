### Title
Attacker-controlled PR `clone_url` passed unsanitized to `git remote add`/`fetch`, enabling `ext::` transport command execution - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop's pull-request checkout flow takes the `head.repo.clone_url` field verbatim from the GitHub API response for a pull request (attacker-controlled if the PR is opened from a fork the attacker owns) and hands it directly to `git remote add` and subsequently `git fetch`, with no validation that the URL uses an allowed transport (`https`/`ssh`). Git supports remote helper schemes such as `ext::` (and others) that can execute arbitrary local commands when used as a remote URL. Because Desktop never restricts the accepted protocol, opening/checking out a PR whose fork "clone URL" is a malicious `ext::`-style value results in local command execution on the victim's machine.

### Finding Description
`_findPullRequestBranch` resolves the remote to fetch a PR branch from by first checking if any existing remote matches the PR head's clone URL, and if not, creates one directly from the PR data: [1](#0-0) 

`headCloneUrl` originates from the pull request object returned by the GitHub API (`pullRequest.head.repo.clone_url`), which is attacker-controlled data for any pull request opened from a fork — no cryptographic or protocol validation is performed on it before being consumed: [2](#0-1) [3](#0-2) 

`addRemote` forwards this string as-is to the `git` CLI: [4](#0-3) 

and the subsequent fetch (`this._fetchRemote(repository, remote, ...)` inside `_findPullRequestBranch`) invokes `git fetch <remote>`, which will honor whatever transport is configured for that remote, including Git's remote-helper protocol dispatch (e.g., `ext::sh -c '<command>'`, or other externally-invokable helpers).

Searching the codebase for any protocol allow-list (`GIT_ALLOW_PROTOCOL`, `protocol.allow`, `transport.disable`, URL scheme checks against a fixed set of `https`/`ssh`) returned no results — the app never constrains which git transport is permitted for remotes it creates on the user's behalf. By contrast, the codebase does show it is protocol-aware elsewhere (`allowFileProtocol` gating `protocol.file.allow=always` for submodules), demonstrating the team already understands transport-based risk, but this control was never applied to the PR-fork-remote path.

### Impact Explanation
This falls squarely in the "attacker controls a GitHub API object" impact category: an attacker opens a pull request against any repository the victim has cloned in Desktop, sets the fork's `clone_url`-equivalent to a crafted `ext::` (or similar) transport string, and waits for the victim to view/checkout that PR in Desktop (a completely ordinary, un-suspicious workflow). When Desktop calls `addRemote` + fetch with that URL, Git will invoke the attacker-chosen remote helper/command, achieving arbitrary local code execution outside any git sandboxing, under the victim's user account.

### Likelihood Explanation
Checking out a PR from the branch list or from a deep link (`x-github-client://openRepo/...&pr=...`) is a routine, low-friction user action; the victim does not need to trust the fork's content or run any git command manually — Desktop performs `addRemote`/`fetch` automatically as part of `_findPullRequestBranch`/`_checkoutPullRequest`. The only precondition is the attacker being able to open a PR (or otherwise supply a `head.repo.clone_url`) against a repository the victim has locally, which is a very low bar on public repositories.

### Recommendation
- Short term: Before calling `addRemote`/`fetch` with any API- or URL-derived value, validate that the URL's scheme is limited to an explicit allow-list (`https`, `ssh`, `git`) and reject anything else (`ext::`, `fd::`, `file://` unless explicitly intended, etc.), mirroring the existing `allowFileProtocol` pattern used for submodules. Consider also setting `GIT_ALLOW_PROTOCOL=http:https:ssh:git` in the environment used for these operations as defense in depth.
- Long term: Centralize all remote-URL handling (clone, addRemote, submodule update, PR head fetch) through one hardened URL/protocol validator, and add regression tests asserting that `ext::`, `fd::`, and other command-executing transports are rejected before ever reaching `git`.

### Proof of Concept
1. Attacker forks the target repository and opens a pull request; the API-returned PR object's head repo clone URL is influenced/served by data under the attacker's control (e.g., via a GitHub Enterprise instance or Desktop's `openRepositoryFromUrl` deep-link where `pr` and `url` parameters are attacker-supplied, see `parseAppURL`/`openPullRequestFromUrl`).
2. Victim, using GitHub Desktop, opens the PR (via UI list or `x-github-client://openRepo/...?pr=<n>`), invoking `dispatchURLAction` → `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch`.
3. `_findPullRequestBranch` does not find a matching existing remote and calls `addRemote(repository, forkRemoteName, headCloneUrl)` with the malicious `ext::` URL, then fetches from it.
4. Git executes the command embedded in the `ext::` transport string during `fetch`, achieving code execution on the victim's machine — no confirmation dialog, path check, or protocol validation ever intercepts the value.
