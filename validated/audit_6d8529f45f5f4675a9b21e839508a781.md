## Finding

### Title
Escrow over-release via duplicate input-token collision in `_fillSameChain` completion branch - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` computes the escrow amount to release to a filler for a completing output leg by reading the *entire* aggregate escrow balance stored at `_orders[commitment][token]` instead of the proportional amount tied to that specific input/output leg [1](#0-0) . This mirrors the H01 "fragile internal accounting" pattern: the contract tracks funds by an aggregate balance slot (per `commitment`+`token`) rather than per-position/per-leg, and assumes that whatever sits in that slot belongs to the operation currently completing.

### Finding Description
`placeOrder` escrows each `order.inputs[i]` entry into `_orders[commitment][token]`, keyed only by the input token address, with no de-duplication check on input tokens (only *output* tokens are checked for duplicates, via transient-storage guards in `placeOrder`) [2](#0-1) . If an order specifies two (or more) `inputs[]` entries that use the same token address — paired index-for-index with two different `output.assets[]` entries — both inputs' escrowed amounts accumulate into the *same* `_orders[commitment][token]` slot.

In `_fillSameChain`, the loop iterates over `output.assets` by index `i` and, for each leg, looks up the *paired* `order.inputs[i]` by the same index [3](#0-2) . When a leg fully completes (`amountFilled == totalRequired`), instead of computing the proportional escrow for *that specific leg*, the code reads the whole combined balance in the slot:
```
escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
``` [4](#0-3) 

Because that slot may hold escrow contributed by a *different* input index (paired with a different, still partially-filled or unfilled output leg), completing just one leg pays out the combined pot for both legs to the filler via `_withdraw` [5](#0-4) .

### Impact Explanation
An unprivileged filler can construct a fill that fully satisfies one output leg exactly (`solverAmount == totalRequired` for that leg) while providing zero or minimal payment for a second leg mapped to the same input token. The completion branch then releases the *entire* aggregated escrow for that token — including the portion meant to back the still-unfilled leg — to the filler. This results in wrong-amount fund release / loss of user escrow, matching the "stealing or loss of funds" and "transaction manipulation" categories in the bounty scope. The remaining order is left partially filled (or the user's second leg is left unbacked), and the user's cancel path (`_cancelSameChain`) will only find whatever (now drained) balance remains in `_orders[commitment][token]` [6](#0-5) , so the funds cannot be recovered.

### Likelihood Explanation
The path is fully reachable by any unprivileged actor: the order creator (who can freely include duplicate input token addresses, since no duplicate check exists for inputs, unlike outputs) and the filler (who calls the fill entrypoint, a public function, with attacker-chosen `FillOptions`). No relayer, prover, admin, or governance action is required — it is a pure logic flaw in the escrow-release accounting.

### Recommendation
Track and release escrow strictly per-leg (per input/output index pairing) rather than reading the raw aggregate `_orders[commitment][token]` balance on leg completion. Either (a) forbid duplicate token addresses across `order.inputs` (mirroring the existing output-token duplicate guard in `placeOrder`), or (b) maintain a per-index escrow accounting structure so that completing one leg can never consume escrow committed to a different leg sharing the same token.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [{token: T, amount: 100}, {token: T, amount: 50}]` and `order.output.assets = [{token: A, amount: X}, {token: B, amount: Y}]` (two legs, same input token `T`, no dedup check on inputs) — `_orders[commitment][T] = 150` after escrow.
2. A filler calls the same-chain fill path providing `options.outputs = [{token: A, amount: X}, {token: B, amount: 0}]`, i.e., fully satisfying leg 0 and paying nothing for leg 1.
3. In the loop, for `i = 0`, `amountFilled == totalRequired` triggers the completion branch: `escrowedAmount = _orders[commitment][T]` = 150 (the full combined pot from both inputs), not the 100 that was actually meant to back leg 0.
4. `_withdraw` releases the full 150 of token `T` to the filler despite them only having paid for leg 0; the escrow meant to back leg 1 (50) is gone, and the user's `_cancelSameChain` on the still-open leg 1 finds no remaining escrow to refund.

*(Note: the exact internal bookkeeping of `_withdraw` — e.g., whether/how it zeroes or decrements `_orders[commitment][token]` after release — was not fully inspected due to tool-call limits; this does not change the core issue that the amount computed and requested for release at line 118 is the full aggregate slot rather than the leg-specific proportional amount.)*

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
