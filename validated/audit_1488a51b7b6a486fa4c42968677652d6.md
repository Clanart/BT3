## Analysis: Local Analog Found

**Core broken invariant from the external report:** sensitive key material (mnemonic/private key) is persisted in an easily-readable channel (clipboard) that outlives its intended use and can be captured by unrelated processes/scripts, leading to unauthorized use of the underlying authority the key grants.

**Local analog:** the TypeScript SDK's session-key storage persists the raw session **private key** for `IntentGatewayV2` orders in plaintext inside `localStorage`/`indexedDB` in browser environments, keyed only by address/commitment strings, with no encryption at rest. This key is the sole authorization credential for signing the on-chain `SelectSolver` message that determines who is allowed to fill (and thus unlock/route) a user's escrowed order funds.

### Title
Session private key for order fulfillment authorization persisted unencrypted in browser storage - (File: sdk/packages/sdk/src/storage/index.ts)

### Summary
`createSessionKeyStorage` in the SDK stores the raw ephemeral session private key generated for every `IntentGatewayV2` order as plaintext JSON in `localStorage`/`indexedDB` when running in a browser, and reads it back later to sign the `SelectSolver` EIP-712 message that authorizes a solver to fill the order.

### Finding Description
`OrderPlacer.placeOrder` generates a fresh session key per order and immediately persists it via `sessionKeyStorage.setSessionKeyByAddress`, storing `{ privateKey, address, createdAt }` as-is [1](#0-0) , and again after the order is finalized with the commitment attached [2](#0-1) .

`createSessionKeyStorage` writes this object with a bare `JSON.stringify(data)` — no encryption, no passphrase, no expiry enforcement — under predictable key prefixes (`session-key:` / `session-key-address:`) [3](#0-2) . In a browser runtime, `detectEnvironment()` selects `localStorage` (or `indexedDB`) as the backing driver [4](#0-3) , which the browser driver wires directly to `unstorage/drivers/localstorage` / `indexeddb` [5](#0-4) . Both are same-origin-readable by any JavaScript executing on the page (XSS, a compromised dependency, or a malicious/injected script), exactly the class of exposure the external report warns about for clipboard data.

The stolen key is not inert — it is the credential used to produce the on-chain authorization signature. `BidImpl.signSelection` fetches the stored key by address and signs the `SelectSolver` EIP-712 struct `(commitment, solver)` with it [6](#0-5) , using `CryptoUtils.signSolverSelection` [7](#0-6) . On-chain, `IntentGatewayV2._select` recovers the signer from this signature and trusts it as the order's session key holder, storing `keccak256(solver, sessionKey)` in transient storage to gate the subsequent `fillOrder` call [8](#0-7) . `fillOrder` only accepts the caller if it matches this transient authorization [9](#0-8) .

Because the entire on-chain trust anchor for "who may fulfill this order" reduces to possession of this one ECDSA key, and that key sits in plaintext, origin-readable browser storage for the lifetime of the order (not cleared after use, no TTL), any script-level compromise of the dApp origin is sufficient to forge a valid `SelectSolver` authorization for an attacker-chosen solver identity — defeating the entire purpose of `solverSelection` protection described in the docs ("orders are protected from unauthorized fills") [10](#0-9) .

### Impact Explanation
This is "unauthorized transaction/execution" and "transaction manipulation" per the impact gate: an attacker who reads the leaked session private key from browser storage can sign a valid `SelectSolver(commitment, solver)` message naming themselves (or a colluding solver) as the authorized filler, call `select()`, and thereby seize control of a legitimate user's order fulfillment path — bypassing the auction/bid mechanism the protocol relies on for competitive, market-fair fills. This subverts the core guarantee `solverSelection` is designed to provide and lets an unprivileged attacker unilaterally decide the fulfillment terms/beneficiary path of another user's escrowed funds, without requiring a malicious relayer, prover, or node — only a client-side script capable of reading `localStorage`/`indexedDB` for the dApp origin.

### Likelihood Explanation
Likelihood is elevated because: (1) the key is written to persistent storage immediately at order placement and again at finalization, with no expiry/clearing logic anywhere in `createSessionKeyStorage`, so its exposure window spans the full order lifetime, not a single operation; (2) the storage key namespace (`session-key-address:<address>`) is predictable and enumerable by any script with storage access; (3) no additional secret (password, hardware confirmation) gates use of the stored key to produce a valid on-chain signature — `CryptoUtils.signSolverSelection` will happily sign with whatever plaintext key it is given.

### Recommendation
Do not persist the raw session private key in plaintext browser storage. Encrypt it at rest with a key derived from a user-provided passphrase or a WebAuthn/hardware-backed secret, and clear it from storage immediately after the relevant `SelectSolver` signature has been produced and submitted on-chain (mirroring the remediation from the external report: minimize the exposure window and avoid storing sensitive secrets in cleartext). Consider binding session-key usage to a single signature (one-time use) enforced by the storage layer itself, and warn integrators in SDK docs that browser storage drivers are not a secure secret store.

### Proof of Concept
1. User places a cross-chain order through the SDK in a browser dApp; `OrderPlacer.placeOrder` generates a session key and stores `{ privateKey, address, createdAt }` via `setSessionKeyByAddress` into `localStorage` under `hyperbridge/sdk/proof/session-key-address:<address>`.
2. An attacker with any script execution capability on the same origin (e.g., a compromised npm dependency bundled into the dApp, or a stored-XSS payload) runs `localStorage.getItem('hyperbridge/sdk/proof/session-key-address:<address>')` and parses out `privateKey`.
3. Attacker calls `CryptoUtils.signSolverSelection(commitment, attackerSolverAddress, domainSeparator, stolenPrivateKey)` to produce a valid `SelectSolver` signature.
4. Attacker submits `IntentGatewayV2.select({commitment, solver: attackerSolverAddress, signature})` followed by `fillOrder(...)`, becoming the authorized filler for a user's order despite never having been chosen through the legitimate bid/auction flow, exactly because the session key that was supposed to gate this decision was exposed via plaintext client-side storage.

```typescript
			this.solverAddress,
```

```typescript
	static async signSolverSelection(
		commitment: HexString,
		solverAddress: HexString,
		domainSeparator: HexString,
		privateKey: HexString,
	): Promise<HexString | null> {
		const account = privateKeyToAccount(privateKey as Hex)

		const structHash = keccak256(
			encodeAbiParameters(
				[{ type: "bytes32" }, { type: "bytes32" }, { type: "address" }],
				[SELECT_SOLVER_TYPEHASH, commitment, solverAddress],
			),
		)

		const digest = keccak256(concat(["0x1901" as Hex, domainSeparator as Hex, structHash]))
		const signature = await account.sign({ hash: digest })

		return signature as HexString
	}
```

```text
    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }
```
