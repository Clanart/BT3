### Title
Deserialized `ThresholdKeys` accept a zero secret share and identity verification shares, yielding a group key with a publicly known discrete logarithm - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` deserializes a `secret_share` scalar and `n` verification-share points using `C::read_F`/`C::read_G`, which only enforce canonical encodings — never rejecting zero scalars or identity points. `ThresholdKeys::new` then computes `group_key` purely as the interpolation of the attacker-controlled verification shares over participants `1..=t`, with no check that `secret_share != 0`, that `verification_shares[i] == generator * secret_share`, or that the resulting `group_key` is not the identity. An untrusted byte stream can therefore define threshold keys whose group key is the identity element (secret key 0, known to everyone) or any other attacker-chosen point.

### Finding Description
- `Ciphersuite::read_F` (`crypto/ciphersuite/src/lib.rs:74-83`) accepts the zero scalar; `read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) accepts the identity point. Only canonical encoding is enforced.
- `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) reads `t`, `n`, `i`, the interpolation tag (option 0 reads `n` arbitrary `Constant` coefficients via `read_F`), the `secret_share` via `read_F`, and `n` verification shares via `read_G`, then calls `ThresholdKeys::new`.
- `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) validates only the *count* and *index range* of verification shares (`IncorrectAmountOfVerificationShares`, `InvalidParticipant`). It never checks `secret_share.is_zero()`, never rejects identity verification shares, and never verifies share/verification-share consistency. `group_key` is set to `Σ_{i ∈ 1..=t} verification_shares[i] * interpolation_factor(i)` (line 377-378) with no identity check on the result.
- By contrast, the codebase does enforce zero-checks where it considers them security-critical: `Participant::new` rejects index 0 (`crypto/dkg/src/lib.rs:29-35`), `ThresholdParams::new` rejects `t == 0`/`n == 0` (`crypto/dkg/src/lib.rs:167-169`), and `ThresholdKeys::scale` refuses a zero scalar (`crypto/dkg/src/lib.rs:400-403`). The deserialization path simply lacks the analogous checks for the secret material itself.

### Impact Explanation
If the bytes fed to `ThresholdKeys::read` are attacker-influenced (the threat model explicitly covers untrusted bytes passed to `ThresholdKeys::read`), the attacker can set every verification share to the identity and `secret_share` to zero. The resulting `group_key` is the identity element — a public key whose discrete logarithm (0) is universally known. Any Schnorr/FROST verification `s·G == R + c·P` with `P = identity` is satisfiable by anyone with `R = s·G`, so signatures under this group key are trivially forgeable. Equivalently, the attacker can choose verification shares that interpolate to any public key they control, causing the holder of the deserialized keys to produce signatures attributable to an attacker-known key. Downstream consumers that register `group_key()` as a validator key or a deposit address (e.g., Bitcoin/Taproot key derivation in `networks/bitcoin`) would accept funds or signatures on behalf of a key the adversary fully controls — funds are then spendable by anyone, not by the intended holder.

### Likelihood Explanation
Exploitation requires an attacker to control or corrupt the serialized `ThresholdKeys` bytes consumed by a victim — e.g., key material transmitted during recovery/resharing protocols, backups, or peer-distributed key packages. Within a threat model where `ThresholdKeys::read` processes bytes from other participants, this is directly reachable with no privileged access: the attacker only crafts bytes. The necessary fields (`secret_share`, all `n` verification shares) are plain, unauthenticated `read_F`/`read_G` encodings, so construction is deterministic and cheap. Likelihood is moderate: it hinges on an integrator trusting serialized key material rather than locally generated DKG output, which is a plausible usage of the exposed `read`/`serialize` API.

### Recommendation
In `ThresholdKeys::new` (covering both construction and deserialization):
1. Reject `secret_share == 0` (`if bool::from(secret_share.is_zero()) { Err(...) }`), mirroring `scale`'s zero check.
2. Reject identity points in `verification_shares` values and reject an identity or otherwise-degenerate computed `group_key`.
3. Verify consistency `verification_shares[&params.i()] == C::generator() * *secret_share` so the deserialized share provably matches the committed verification shares.
4. For `Interpolation::Constant`, reject all-zero coefficient vectors (or coefficients that make any participant's interpolation factor zero).

Additionally, callers that consume `ThresholdKeys::read` output from untrusted sources should authenticate the serialized blob before use.

### Proof of Concept
```rust
use std::{io, collections::HashMap};
use zeroize::Zeroizing;
use ciphersuite::{Ciphersuite, group::{ff::Field, GroupEncoding}};
use dkg::{ThresholdParams, ThresholdKeys, Participant};

// For any Ciphersuite C (e.g., a dalek-ff-group curve):
fn craft_zero_keys() -> Vec<u8> {
    let mut buf = vec![];
    buf.extend((u32::try_from(C::ID.len()).unwrap()).to_le_bytes());
    buf.extend(C::ID);
    buf.extend(1u16.to_le_bytes()); // t = 1
    buf.extend(1u16.to_le_bytes()); // n = 1
    buf.extend(Participant::new(1).unwrap().to_bytes());
    buf.push(1); // Interpolation::Lagrange
    buf.extend(C::F::ZERO.to_repr().as_ref());            // secret_share = 0
    buf.extend(C::G::identity().to_bytes().as_ref());     // verification_shares[1] = identity
    buf
}

let keys = ThresholdKeys::<C>::read(&mut &craft_zero_keys()[..]).unwrap(); // accepted
assert!(bool::from(keys.group_key().is_identity())); // group key = identity, secret key 0
// Any signature under this group key satisfies s*G == R + c*identity == R,
// i.e., is forgeable by anyone choosing R = s*G.
```
