## Title
Security-review bypass via mis-calculated diff "delta" in `filter_preexisting_from_diff` hides newly-introduced malicious lines from the security-guidance Stop-hook LLM scan - (File: `plugins/security-guidance/hooks/gitutil.py`)

### Summary
The reported bug's root cause is a delta/diff computation that conflates a "before" quantity that should be excluded from the "after" measurement, producing an incorrect result that silently drops value the caller should have seen. The same root cause exists in `filter_preexisting_from_diff()`, which decides which `+` lines in a Write-tool full-file-rewrite diff are "new" (and therefore worth showing the security-review LLM) versus "pre-existing" (converted to context and explicitly excluded from review).

### Finding Description
`filter_preexisting_from_diff` builds `removed_lines` as a **set** of stripped `-` line contents and then treats set *membership* as proof that any `+` line with matching text is "pre-existing": [1](#0-0) 

```
removed_lines = set()
added_lines = []
... 
preexisting_count = sum(1 for l in added_lines if l in removed_lines)
```

and later actually rewrites the diff, converting matching `+` lines into unmarked context lines: [2](#0-1) 

Just like `Swap.sol`'s `originalERC20Balance`/`originalETHBalance` conflating the pre-transaction balance with the post-transaction delta (a scalar quantity bug), this function conflates *existence* of a matching removed line anywhere in the file with a correct 1:1 correspondence between removed and added occurrences. It is a multiset problem solved with set semantics:

- If line `X` was removed once, but two `+` lines with identical stripped text `X` appear (one being a genuine rewrite, one being a brand-new line an attacker or prompt-injected instruction inserted), **both** are converted to context and dropped from the LLM's view, even though only one is legitimately "the same code, reformatted."
- The match is purely textual and file-scoped, not line-position aware, so a newly introduced dangerous line only needs to share exact (whitespace-stripped) text with *any* unrelated line removed elsewhere in the same file's rewrite.

This filtered diff is what gets sent to `analyze_code_security`, whose prompt explicitly instructs the reviewer model to ignore anything that looks pre-existing: [3](#0-2) 

So a line that `filter_preexisting_from_diff` mislabels as context is not merely deprioritized — the review prompt tells the LLM to actively ignore it "even if [it] contains ... hardcoded passwords, SQL injection, or any other vulnerability."

### Impact Explanation
This is a hook-bypass of the `security-guidance` plugin's core protection (`handle_stop_hook`, the final Stop-hook LLM security scan described in `security_reminder_hook.py:1-54`). An unprivileged actor who can influence what Claude writes during a session (e.g. via prompt injection from an untrusted file/tool output, or a compromised skill/MCP tool) can get Claude to perform a full-file `Write` rewrite that introduces a genuinely new dangerous line whose stripped text collides with some other line the rewrite removed elsewhere in the file. That line is converted to context by `filter_preexisting_from_diff` and then explicitly instructed to be ignored by the LLM reviewer, so:
- The Stop-hook's concrete-vulnerability scan (`analyze_code_security`) never sees it.
- No exit-code-2 guidance is produced, so Claude is never nudged to fix or reconsider it.
- The change lands in the user's repo with the plugin having silently "cleared" it.

This defeats the specific trust boundary the plugin exists to enforce — catching vulnerable/malicious code Claude was steered into writing — for the exact class of edits (`Write` full-file rewrites) the docstring calls out as needing this filter.

### Likelihood Explanation
Moderate-to-high. `Write` full-file rewrites are common, and the collision condition is easy to construct deliberately (an attacker/prompt-injector who can see the current file content, which Claude typically reads before rewriting, can choose duplicate text on purpose). It requires no special privilege beyond what an ordinary Claude Code session that reads/writes files already has, and no interaction with git internals beyond the normal diff the Stop hook already computes.

### Recommendation
Replace the set-membership check with position/multiplicity-aware matching, e.g. use a multiset (`collections.Counter`) so each removed occurrence can excuse at most one added occurrence, and additionally require some locality/ordering heuristic (e.g. LCS-based diff of the removed vs added blocks) rather than "any matching stripped text anywhere in the file." At minimum, decrement a `Counter` of `removed_lines` each time a `+` line consumes a match so duplicate new lines are not all excused by a single removed line.

### Proof of Concept
1. Original file contains, among other lines, a benign line whose stripped text is `X = eval(user_input)  # legacy debug`.
2. Claude (steered via prompt injection or a malicious skill instruction reachable in an unprivileged session) is made to fully rewrite the file with the `Write` tool. The rewrite removes that legacy line (so it lands in `removed_lines`) and adds two new lines with the exact same stripped text `X = eval(user_input)  # legacy debug`, one truly a re-add of old dead code and one placed at a new call site that is now reachable with attacker-controlled `user_input`.
3. `filter_preexisting_from_diff` sees both `+` occurrences match an entry in `removed_lines` and converts both to context lines.
4. `analyze_code_security` receives a diff where the new dangerous `eval` call at the new reachable call site is shown only as unmarked context, and per its own prompt instructions in `llm.py:753-758` it is told to ignore any vulnerability found in context lines.
5. The Stop hook exits 0 (no findings), and the newly reachable `eval(user_input)` ships unreviewed. [4](#0-3)
