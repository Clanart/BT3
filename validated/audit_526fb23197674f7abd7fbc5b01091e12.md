## Title
Diff line-selection index reuse across a refreshed diff can silently commit or stage the wrong lines when the underlying file changes between diff load and selection reconciliation - (File: `app/src/lib/stores/app-store.ts`, `app/src/models/diff/diff-selection.ts`)

### Summary
The external report's underlying bug class is: a stateful update formula treats a previously captured value (old weight × old voting power) as if it still matches the *current* state, without accounting for the delta between the two snapshots, producing an incorrect/corrupted result. The GitHub Desktop analog is `_updateChangesWorkingDirectoryDiff` in `app-store.ts`, which reconciles a user's partial line-selection (`DiffSelection`) — captured against an *old* diff — with a *newly reloaded* diff, using bare numeric line indices as the sole identity key, with no validation that the line at that index still represents the same content.

### Finding Description
`DiffSelection` (`app/src/models/diff/diff-selection.ts:53-331`) tracks selected/deselected lines purely as a `Set<number>` of `divergingLines`/`selectableLines` indices — it has "no notion of how many lines exist or what it is that is being selected" (comment at line 310-313). Selection state and content identity are completely decoupled.

When the working-directory diff is reloaded (e.g., after a file changes on disk — which can happen due to background git operations, external file watchers, or content written by another process/tool while Desktop is idle-refreshing), `_refreshRepository`/`updateChangesWorkingDirectoryDiff` re-fetches the diff and then reconciles the old selection against it: [1](#0-0) 

The comment at lines 3480-3485 explicitly acknowledges the weakness: *"The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..."*

`withSelectableLines` (`app/src/models/diff/diff-selection.ts:320-330`) only filters `divergingLines` by whether the **same numeric index** is still `isIncludeableLine()` in the new diff — it never compares the line **content** or **type** at that index between the old and new diff. If the new diff has the same or a larger number of includeable lines at the same absolute offsets (e.g., a hunk shifted, or an interleaving addition/deletion changed which line occupies index N), a previously selected index remains "selected" even though the line it now points to is semantically different content than what the user reviewed and chose to include.

This selection state is later consumed verbatim by `formatPatch` (`app/src/lib/patch-formatter.ts:129-232`) via `file.selection.isSelected(absoluteIndex)` to build the exact patch applied with `git apply --cached` in `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`), and ultimately becomes what gets staged/committed.

Just like the `GaugeController` formula reused `votingPower` without tracking the delta since the last snapshot (causing an incorrect weight), Desktop reuses raw line indices from an old selection snapshot without tracking whether the underlying diff content at that index has changed, causing a mismatch between what the UI visually showed as selected and what is actually staged.

### Impact Explanation
Where the diff refresh races with content changes at the same line offsets (e.g., a large repository with background fetch/checkout activity, submodule updates, or another tool rewriting the file), a user's partial commit selection can silently apply to different lines than they reviewed. This is a "silent corruption of what the user commits" scenario explicitly called out as valid impact: the user believes they excluded/included specific lines, but the actual patch applied to the index reflects stale index positions against new content. Because `formatPatch` throws only on empty patches (line 224-227 of `patch-formatter.ts`), not on semantic mismatch, there is no safety net once indices "line up" numerically.

### Likelihood Explanation
This requires a specific race: the working tree file must change (in a way that yields the same or overlapping includeable-line index positions) between the diff being loaded and the reconciliation step in `_refreshRepository`/`updateChangesWorkingDirectoryDiff`, while the user has an in-flight partial selection. Desktop's own background refresh, fetch-triggered indicator updates (`_refreshRepository` at `app-store.ts:4047-4143`), and status polling create windows where this reconciliation runs automatically without explicit user action, and the code's own comment acknowledges the reconciliation is best-effort rather than content-validated. This is a moderate-likelihood, hard-to-notice correctness bug rather than a trivially exploitable RCE — it degrades the integrity of partial commits under normal (not adversarial-privileged) conditions such as background refreshes racing with disk changes.

### Recommendation
Track selection by stable line content/hash (or an old-diff hunk anchor plus content match) instead of by bare absolute index, so `withSelectableLines`-style reconciliation can detect that a previously selected line's underlying content changed and drop/re-flag the selection instead of silently carrying it over. At minimum, compare line `text`/`type` between old and new diff at each surviving index and invalidate divergence entries when content differs, then surface this to the user (e.g., "selection reset because file changed") rather than transparently re-using indices.

### Proof of Concept
1. Select a file with partial line selection (some lines checked, some unchecked) in the Changes view.
2. While Desktop is displaying that diff, modify the working copy of the file externally (e.g., another process/editor) in a way that inserts/removes lines such that the total count of includeable lines at the previously-selected offsets stays the same (e.g., replace a selected added line with a different added line at the same relative position within the hunk).
3. Trigger `_refreshRepository`/`updateChangesWorkingDirectoryDiff` (this happens automatically on Desktop's periodic background refresh, or on window focus).
4. Observe that `withSelectableLines` keeps the same `divergingLines` indices since they are still includeable, effectively "selecting" the new, different line content.
5. Commit: `formatPatch` builds a patch using `isSelected(absoluteIndex)` against the new diff, staging content the user never reviewed/selected in the UI.

Note: I was not able to fully trace every intermediate git-status/diff refresh trigger path (e.g., exact timing of file-watcher-driven refresh vs. manual refresh) within the available indexed code, so the precise timing window and whether Desktop's UI re-renders the checkbox state before the user commits could not be fully confirmed from local code alone — this would benefit from a live reproduction in a running Desktop session to confirm the UI does not re-warn the user before the stale selection is used in `applyPatchToIndex`.
