In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol`), the escrow amount forwarded to `_withdraw` for a *non-final* partial fill is a freshly **recomputed** proportional value, not the value actually decremented from the persistent `_orders[commitment][token]` state, while `_withdraw` blindly trusts and subtracts whatever amount it is handed. This is the same class of bug as the sUSDz report: a value computed on the fly (vesting/unvested split) diverges from the persisted state variable actually used for later withdrawal/subtraction, and the mismatch surfaces as a broken invariant on that stored balance.

### Title
Same-chain partial-fill escrow release amount is decoupled from the persisted `_orders` balance, allowing solver over-drain or order-bricking underflow - (evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` computes the escrow amount to release for a partial fill as `(order.inputs[i].amount * fillAmount) / totalRequired` — a value derived purely from the order's *declared* input amount and the output fill ratio — instead of reading and proportionally decrementing the actual escrowed balance recorded in `_orders[commitment][token]`. This recomputed value is then handed to `_withdraw`, which does `_orders[commitment][token] = escrowed - amount` using the *live* stored balance. Just like the sUSDz bug where `totalAssets()` computed a value (`pooledUSDz + vestedAmount`) that was never reconciled back into the stored `pooledUSDz` before a later subtraction, here the release `amount` is computed independently of the stored `escrowed` value it will later be subtracted from.

### Finding Description [1](#0-0) 
In the partial-fill branch (`amountFilled != totalRequired`), `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired`. This is a *derived* number based only on order-declared amounts, never cross-checked against `_orders[commitment][token]`, the pallet/contract's single source of truth for how much is actually escrowed for that commitment/token pair. [2](#0-1) 
`_withdraw` then does:
```
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
```
There is no check that `amount <= escrowed`, and no reconciliation logic between the two values, exactly the same absent invariant that caused the sUSDz underflow: a number computed off the "vesting"-equivalent formula (proportional fill math) is subtracted from a separately-tracked stored balance with no guarantee they stay in sync across repeated partial fills, rounding, and multiple input tokens with different escrow ratios (predispatch swaps, protocol-fee deductions applied per input at placement time can make the true escrowed amount diverge from a simple `inputs[i].amount` linear projection).

Because `order.inputs[i].amount` reflects amounts *after* protocol-fee deduction at placement (per the docs: "amounts reflect values after protocol fee deduction"), and multiple partial fills accumulate rounding from integer division (`(order.inputs[i].amount * fillAmount) / totalRequired`), the sum of all partial-fill `escrowedAmount` values released over the life of an order is not guaranteed to equal the actual `_orders[commitment][token]` balance recorded at placement. This can drift in either direction: under-release (permanently stranded escrow dust for that order, which cannot be swept by the user) or in combination with a full-fill branch that instead reads the live storage value directly (`escrowedAmount = _orders[commitment][...]` on the final fill), a fill sequence can be crafted where prior partial-fill under-releases inflate the final fill's `escrowedAmount` beyond what the solver's proportional entitlement should be — the solver captures dust that should have gone proportionally across fillers, or in a degenerate case the running-total accounting error causes `_withdraw`'s `escrowed - amount` subtraction to underflow and revert, permanently bricking the order (Solidity checked-arithmetic revert = the sUSDz "arithmetic underflow or overflow" analog), since no cancellation path recovers from a state where `_orders` is inconsistent with `_partialFills` bookkeeping.

### Impact Explanation
This falls under the accepted "logic attacks" / "transaction manipulation" / "loss of funds" bounty categories: a public, unprivileged `fillOrder` caller (any solver) can, through the ordinary partial-fill mechanic, cause escrow accounting to diverge between the computed release amount and the persisted balance, resulting in either escrowed user funds becoming permanently stuck (can never be fully filled or cancelled because `_orders` balance never reaches zero, or reverts on `escrowed - amount` underflow bricking that specific order's fill/cancel paths) or a solver receiving more escrow than their proportional output entitlement.

### Likelihood Explanation
Requires only ordinary usage of the public, permissionless `fillOrder` same-chain path with more than one partial fill against the same order and output token — no privileged role, relayer, or malicious peer needed. Rounding-driven drift is guaranteed to occur over enough partial fills; a solver can also deliberately choose `solverAmount` values across successive fills to maximize the rounding-derived discrepancy in their favor.

### Recommendation
Do not recompute the escrow-release amount from `order.inputs[i].amount` and the fill ratio. Instead, always derive the release amount from the actual `_orders[commitment][token]` stored balance (e.g., `escrowedAmount = (_orders[commitment][token] * fillAmount) / remaining`, decrementing remaining-based on the *current* stored escrow rather than the order's static declared amount), and reconcile leftover dust to zero on the final fill exactly as is already done for the full-fill branch, so the sum of released amounts across all partial fills is mathematically guaranteed to equal the original escrowed balance with no possibility of underflow or stranded remainder.

### Proof of Concept
Because this requires deploying `IntentGatewayV2`/`IntrinsicIntents` in Foundry with a token that has a protocol-fee deduction and running a multi-partial-fill sequence to demonstrate the rounding/inflation drift (analogous to the two-user, multi-step `testDepositAddYieldAndUnstake2Users` PoC in the source report), a full runnable PoC could not be constructed within this read-only analysis. The vulnerable code path is fully identified above: the divergence between the `escrowedAmount` formula at `IntrinsicIntents.sol:120` and the authoritative `_orders[commitment][token]` state consumed/decremented in `IntentsBase.sol:400-403` is the exact structural analog of the reported sUSDz bug (a derived/computed value never reconciled with the stored balance it is later subtracted against).
