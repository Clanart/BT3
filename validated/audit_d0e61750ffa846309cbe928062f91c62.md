### Title
GitHub credential leak to attacker-controlled host via spoofable `WWW-Authenticate` realm in credential-helper trampoline - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The external bug report's broken invariant is: a verification mechanism trusts an attacker-influenced signal to decide which class of secret to release, and the code path has no independent check to catch a mismatched/forged signal. In Beanstalk this was EIP-712 signature checks that couldn't validate contract-based signers. The Desktop analog is `getEndpointKind()` in `trampoline-credential-helper.ts`, which classifies a Git remote host as `'enterprise'` (a GitHub-Enterprise endpoint entitled to receive the user's stored GitHub token) based partly on the `WWW-Authenticate` response header the *remote server itself* returned.

### Finding Description
When Git needs credentials for an HTTPS remote, it can capture the `WWW-Authenticate` header from the server's 401 response and forward it to Desktop's credential helper as `wwwauth[]` fields. `getEndpointKind()` uses this attacker/server-controlled string to decide the endpoint classification: [1](#0-0) 

If the value contains `realm="GitHub"`, the function returns `'enterprise'`. In `getCredential()`, any non-`'generic'` classification for a host with no already-stored account triggers a GitHub sign-in prompt or credential lookup, and if a byte-for-byte match against known GitHub endpoints fails, this classification governs whether the user's GitHub OAuth token can be attached to the credential response for that arbitrary remote: [2](#0-1) 

Because a malicious or compromised HTTPS remote (or a man-in-the-middle proxy on that connection) fully controls its own HTTP response headers, it can emit `WWW-Authenticate: Basic realm="GitHub"` to make Desktop treat it as an enterprise GitHub host. If the user has an existing account whose credentials get attached via `credWithAccount`, or if the user is prompted and signs in believing it's a legitimate GitHub Enterprise host, the resulting credential (GitHub login + token) is handed back to `git` and sent to that attacker-controlled remote over the same connection that supplied the header.

### Impact Explanation
Existing guards (`isDotCom`, `isGHE`, `findGitHubTrampolineAccount` hostname match) are hostname/config based and would normally classify an unknown domain as `'generic'`. But the `wwwauth[]` branch is evaluated before falling back to the network-based `isGitHubHost(endpoint)` check, allowing a self-declared realm string from the remote itself to short-circuit into the `'enterprise'` classification. This can result in the user's GitHub personal token being exfiltrated to an attacker's server (credential/token exfiltration), matching the valid-impact criteria ("attacker controls ... a git remote/proxy response" resulting in "credential/token exfiltration").

### Likelihood Explanation
Exploitation requires the victim to add or fetch from a remote pointed at an attacker-controlled or MITM'd HTTPS host (e.g., a malicious fork URL, compromised mirror, or captive/corporate proxy performing TLS interception) and for Git to prompt for credentials against that host (e.g., private-looking repo returning 401). This is a plausible, no-privilege scenario reachable purely through normal clone/fetch/push against an untrusted or spoofed remote — no local access, malware, or leaked credentials required.

### Recommendation
Do not trust the `wwwauth[]`/`realm` value alone to elevate trust for credential release. Only use it as a weak hint requiring corroboration with the network round-trip check (`isGitHubHost`) or a strict allow-list of known Enterprise endpoints the user has explicitly configured/signed into, and never auto-attach a stored token to a host that hasn't been previously verified/added as a GitHub account endpoint.

### Proof of Concept
1. Attacker stands up an HTTPS git server at `https://evil.example.com/victim/repo.git` that returns `401` with header `WWW-Authenticate: Basic realm="GitHub"` when Git tries to fetch.
2. Victim clones/fetches this URL in GitHub Desktop (e.g., via a malicious "open in Desktop" link or a typosquatted fork URL).
3. Git invokes the credential-helper trampoline; `parseCredential` extracts the `wwwauth[]` header into `cred`.
4. `getEndpointKind()` matches `realm="GitHub"` and returns `'enterprise'` at [3](#0-2) .
5. `getCredential()` treats this as a GitHub host lacking a stored account, prompts `ui.promptForGitHubSignIn(endpoint)`, or if an existing GitHub-endpoint match happens to apply, attaches the account token via `credWithAccount`.
6. The resulting username/token pair is returned to `git`, which sends it as the `Authorization` header to `https://evil.example.com`, leaking the GitHub token to the attacker.

**Note on completeness:** I could not fully trace whether `findGitHubTrampolineAccount`'s origin comparison (`app/src/lib/trampoline/find-account.ts:20-29`) would prevent attaching an existing stored token unless the attacker's hostname exactly matches a configured account endpoint — that comparison does appear to require an origin match, which reduces (but does not eliminate) impact to the "prompt the user to sign in against a spoofed enterprise host" scenario rather than always leaking an existing token silently. A background Devin session with full repo access would be useful to confirm all downstream branches (especially `ui.promptForGitHubSignIn` behavior and whether the prompted OAuth flow could bind a real token to the attacker domain). /** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
