## Finding

### Title
Argument/option injection into `git remote add` / `git remote set-url` via unsanitized remote URL - (`File: app/src/lib/git/remote.ts`)

### Summary
`addRemote()` and `setRemoteURL()` in `app/src/lib/git/remote.ts` build the git command line as `['remote', 'add', name, url]` / `['remote', 'set-url', name, url]` and pass the caller-supplied `url` as a raw positional argument with **no `--` end-of-options separator**. [1](#0-0) [2](#0-1) 

By contrast, `clone()` in `app/src/lib/git/clone.ts` correctly inserts `--` before the URL/path pair to stop git from parsing them as options: [3](#0-2) 

### Finding Description
`git remote add`/`git remote set-url` accept flags such as `-f`, `-t <branch>`, `-m <branch>`, `--mirror=fetch`, `--mirror=push`, `--tags`, `--no-tags`. Because `addRemote`/`setRemoteURL` never terminate option parsing with `--`, any string beginning with `-` that reaches the `url` parameter is interpreted by git as an option rather than a URL. This breaks the implicit invariant "the value the user/API supplied as a repository URL is stored verbatim as `remote.<name>.url`" — exactly the same class of missing-validation bug as the reported `_xcall()` issue, where an unchecked value (`destChainId`) was allowed to flow into a state-mutating operation without confirming it matched the expected/safe shape.

The reachable, attacker-influenced call site is `AppStore._findPullRequestBranch`, which adds a remote using `headCloneUrl` taken directly from a pull request's `head.repo.clone_url` — a field that originates from a GitHub API response (dotcom or, more importantly, a GitHub Enterprise/third-party endpoint the user has signed into): [4](#0-3) 

This value is populated by `openPullRequestFromUrl` → `_checkoutPullRequest`, which forwards `pullRequest.head.repo.clone_url` unmodified: [5](#0-4) 

Nowhere along this path (`parseAppURL` → `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` → `addRemote`) is the clone URL validated to actually be a well-formed `https://`/`ssh://`/`git@` remote URL (the way `remote-parsing.ts`'s `parseRemote()`/`sanitizeCloneName()` validate URLs on the *clone* path). The manual "Add remote" UI path in `repository-settings.tsx` similarly forwards free-form user text straight into `addRemote`/`setRemoteURL`.

### Impact Explanation
If a value beginning with `-`/`--` reaches `addRemote`/`setRemoteURL` as the "url", the resulting git remote is silently misconfigured rather than pointing at the intended host — e.g. `--mirror=fetch` turns the newly-added fork remote into a mirror remote, which on a subsequent `git fetch` will overwrite/prune refs under `refs/*` instead of only the intended branch. This is a silent corruption of the repository's remote configuration and, transitively, of what gets fetched/pushed, matching the report's accepted impact category ("silent corruption of what the user commits or pushes") without requiring local access, admin rights, or pre-existing malware — the trigger is simply an attacker-controlled GitHub API object (a PR's `head.repo.clone_url`) or attacker-supplied text pasted by the user.

### Likelihood Explanation
For GitHub.com, `clone_url` is server-generated (`https://github.com/<owner>/<repo>.git`) and cannot start with `-`, which limits real-world reachability. The path becomes concretely exploitable when the account is a GitHub Enterprise Server / third-party GitHub-API-compatible endpoint, or if any code path ever surfaces a raw, less-constrained string into `addRemote`/`setRemoteURL` (e.g., the manual "Add remote" repository-settings field). I was not able to fully confirm whether any GHES/compat-endpoint response is validated elsewhere in the stack (e.g. `isGitHubHost`) before reaching `_findPullRequestBranch`, so likelihood for the PR flow specifically is uncertain and should be verified with a live GHES or malicious API proxy; the manual-entry path in `repository-settings.tsx` is trivially reachable by any user pasting a crafted string.

### Recommendation
Add `--` before the URL argument in both `addRemote` and `setRemoteURL` (mirroring `clone.ts`), and/or explicitly reject values that start with `-` before passing them to `git`:
```ts
await git(['remote', 'add', name, '--', url], repository.path, 'addRemote')
await git(['remote', 'set-url', name, '--', url], repository.path, 'setRemoteURL')
```

### Proof of Concept
1. Trigger `_findPullRequestBranch` (or the manual "Add Remote" dialog in Repository Settings) with a URL value of `--mirror=fetch` (obtainable from a malicious/compromised GitHub Enterprise-compatible API endpoint returning this as `head.repo.clone_url`, or by pasting it directly in the Add-Remote UI).
2. Desktop executes `git remote add ghdesktop-fork--mirror=fetch` → wait, actually: `git remote add <forkRemoteName> --mirror=fetch` (per `addRemote`, `app/src/lib/git/remote.ts:29-37`).
3. Git accepts `--mirror=fetch` as a valid flag (no `--` separator present), creating the remote with `remote.<name>.mirror=fetch` and no configured URL.
4. Any later `git fetch` targeting that remote silently mirrors/prunes refs rather than performing the expected scoped branch fetch, corrupting local branch state without user awareness. [6](#0-5) [7](#0-6)

/**
 * List the remotes, sorted alphabetically by `name`, for a repository.
 */
export async function getRemotes(
  repository: Repository
): Promise<ReadonlyArray<IRemote>> {
  const result = await git(['remote', '-v'], repository.path, 'getRemotes', {
    expectedErrors: new Set([GitError.NotAGitRepository]),
  })

  if (result.gitError === GitError.NotAGitRepository) {
    return []
  }

  return [...result.stdout.matchAll(/^(.+)\t(.+)\s\(fetch\)/gm)].map(
    ([, name, url]) => ({ name, url })
  )
}

/** Add a new remote with the given URL. */
export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')

  return { url, name }
}
