### Title
Sed frontmatter-extraction range re-triggers on later `---` pairs in body, letting attacker-controlled body content be smuggled into trusted frontmatter fields - (File: plugins/plugin-dev/skills/plugin-settings/scripts/validate-settings.sh, plugins/ralph-wiggum/hooks/stop-hook.sh, plugins/plugin-dev/skills/plugin-settings/scripts/parse-frontmatter.sh)

### Summary
The frontmatter extraction idiom `sed -n '/^---$/,/^---$/{ /^---$/d; p; }'` is not bound to only the first two `---` delimiters; GNU sed's `/re1/,/re2/` address range automatically re-activates whenever it finds another standalone `---` line after the previous range closes. This means any additional pair of lines that are exactly `---` inside the markdown body gets treated as a second "frontmatter block" and its contents are concatenated into `$FRONTMATTER`/`$FRONTMATTER`-derived variables, contradicting the project's own documentation claim that "the parsing still works because we only match the first two" (`plugins/plugin-dev/skills/plugin-settings/references/parsing-techniques.md:319-336`).

### Finding Description
`validate-settings.sh:55` (and the identical pattern in `parse-frontmatter.sh:37` and the production hook `plugins/ralph-wiggum/hooks/stop-hook.sh:21`) extracts frontmatter with:
```bash
FRONTMATTER=$(sed -n '/^---$/,/^---$/{ /^---$/d; p; }' "$FILE")
``` [1](#0-0) 

For a file with lines exactly:
```
---
a: 1
---
legit body
---
injected: attacker
---
```
sed's range opens at line 1, closes at line 3 (printing `a: 1`), and then — because sed re-scans for a new start match after the range closes — reopens at line 5 and closes at line 7, printing `injected: attacker` as well. The two blocks are concatenated, so `FRONTMATTER` = `"a: 1\ninjected: attacker"`, even though only the first block is the "real" YAML frontmatter. `MARKER_COUNT` (`grep -c '^---$'`) also silently rises to 4 without any check limiting it to exactly 2 [2](#0-1) .

This differs from the sibling `BODY` extraction, which uses `awk '/^---$/{i++; next} i>=2'` and correctly treats everything after the second `---` as body regardless of further `---` occurrences [3](#0-2) . The sed-based frontmatter extractor has no equivalent bound, so it is a genuine parser differential between the two extraction primitives used side-by-side in the same script.

Real-world reachable impact: `plugins/ralph-wiggum/hooks/stop-hook.sh` uses this exact sed pattern to extract `iteration`, `max_iterations`, and `completion_promise` from `.claude/ralph-loop.local.md`, and separately extracts `PROMPT_TEXT` (the body, fed back to Claude every loop iteration) via the awk pattern [4](#0-3) . Because `PROMPT_TEXT`/state-file body is round-tripped every iteration (assistant output can be echoed back into it, and the file itself is rewritten each loop via `sed` in place at line 155), any run where the body/prompt text contains a line that is exactly `---` followed later by another exact `---` line allows attacker/assistant-influenced text in between to be captured into `$FRONTMATTER` and picked up by `grep '^iteration:'`, `grep '^max_iterations:'`, or `grep '^completion_promise:'` at line 22-25. If a duplicate `max_iterations:`/`iteration:` line is injected, the `grep` yields two matches, producing a multi-line value that fails the `^[0-9]+$` numeric-format check at lines 28/39, causing the state file to be treated as "corrupted" and the loop forcibly terminated (`rm "$RALPH_STATE_FILE"; exit 0`) — a controllable denial-of-service against the ralph-loop hook enforcement path. For `strict_mode`/`enabled`-style gating shown in the officially documented hook pattern (`plugins/plugin-dev/skills/plugin-settings/SKILL.md:79-94`), a duplicated field similarly turns an exact-match comparison (`[[ "$STRICT_MODE" == "true" ]]`) into a failing multi-line comparison, silently downgrading a hook from strict to lenient validation even though the real frontmatter said `strict_mode: true` [5](#0-4) .

### Impact Explanation
This is a trust-boundary bypass in hook-gating logic: content from the markdown body (documented as allowed to contain "task descriptions," "prompts fed back to Claude," or assistant-generated text) can be misclassified as frontmatter and alter boolean/numeric fields (`strict_mode`, `enabled`, `iteration`, `max_iterations`, `completion_promise`) that hooks use to decide whether to apply strict validation, whether a plugin is active, or when a loop should stop. Concretely reachable consequences in the shipped `stop-hook.sh` are (a) forced termination of the ralph loop via corrupted-numeric-field detection (denial of automation), and (b) documented hook patterns (`plugin-settings/SKILL.md`) that gate `strict_mode`/`enabled` can be silently flipped to the lenient/disabled path by a duplicated field smuggled through the body, weakening security enforcement that downstream code trusts as validated configuration.

### Likelihood Explanation
Exploitability requires only that the attacker control text that ends up as/inside the markdown body of a `.local.md`-style file (e.g., ralph-loop state file body/prompt content, which is round-tripped every iteration and can include assistant output or fed-back tool output) and can cause two additional literal `---` lines to appear there. Markdown horizontal rules (`---`) are common and could occur in normal LLM output, task text, or file excerpts embedded in the prompt, making accidental triggering plausible and deliberate triggering trivial for anyone who controls the body content. No admin privilege, secrets, or social engineering is required — only normal content that the plugin ecosystem explicitly allows to flow into the body of these files.

### Recommendation
Replace the sed range extraction with a bounded parser that only ever considers the first two `^---$` lines, e.g. using `awk` symmetric to the existing body-extraction logic:
```bash
FRONTMATTER=$(awk '/^---$/{c++; next} c==1' "$FILE")
```
which increments a counter only on exact `---` lines and prints only while exactly one marker has been seen, never restarting after the second marker. Apply this fix uniformly in `validate-settings.sh`, `parse-frontmatter.sh`, `stop-hook.sh`, and update `plugin-settings/SKILL.md` / `parsing-techniques.md` example code (and correct the doc's incorrect claim that the sed pattern "only matches the first two"). Additionally, harden field extraction (`grep '^field:'`) to take only the first match (`head -1`) as defense in depth against duplicate-field smuggling.

### Proof of Concept
Differential unit test (bash):
```bash
cat > /tmp/state.md <<'EOF'
---
strict_mode: true
---
Legit body line.
---
strict_mode: false
---
EOF

FRONTMATTER=$(sed -n '/^---$/,/^---$/{ /^---$/d; p; }' /tmp/state.md)
echo "$FRONTMATTER"
# Actual: "strict_mode: true\nstrict_mode: false"  (BUG: two blocks concatenated)

STRICT_MODE=$(echo "$FRONTMATTER" | grep '^strict_mode:' | sed 's/strict_mode: *//')
[[ "$STRICT_MODE" == "true" ]] && echo "STRICT APPLIED" || echo "STRICT SKIPPED"
# Actual: "STRICT SKIPPED" even though intended real value is strict_mode: true
```
Assertion for a fixed/canonical parser: `FRONTMATTER` should equal only `strict_mode: true` (content strictly between the first two `---` markers), and `STRICT_MODE` should equal `true`, causing "STRICT APPLIED". Extend the same test against `plugins/ralph-wiggum/hooks/stop-hook.sh` by constructing a `.claude/ralph-loop.local.md` whose body contains two extra `---`-delimited lines injecting a duplicate `max_iterations:` value, and assert the hook does not spuriously treat the state file as corrupted/terminate the loop for a well-formed real frontmatter.
