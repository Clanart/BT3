Based on my investigation, the strongest local analog is the **global, mutable `challengePeriod` used to gate already-pending state commitments** in `EvmHost`/`HandlerV2`, on both EVM and Substrate ISMP cores. I could not find a fully unprivileged-attacker-reachable instance of the exact "stale approval counter surviving reconfiguration" pattern — the closest structural analog (`updateHostParams`) is gated by `hostManager` (cross-chain governance) or the pallet's `AdminOrigin`, which the bounty scope explicitly excludes as an attacker primitive. I was not able to verify, within available context, whether any permissionless path lets an attacker itself trigger a challenge-period shrink or a stale-threshold reuse without invoking that governance-gated entrypoint.

### Title
Global mutable `challengePeriod` retroactively re-validates already-pending state commitments - (File: `evm/src/core/HandlerV2.sol`, `evm/src/core/EvmHost.sol`)

### Summary
`HandlerV2.handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` gate execution on `host.challengePeriod()` — the **current, mutable** global parameter — compared against `stateMachineCommitmentUpdateTime(height)`, which is fixed at the time the commitment was stored. This mirrors the reported bug's root cause: a value meant to gate execution (`_approvalCount` vs. current owner set) is checked against a live, reconfigurable parameter instead of the parameter that was in force when the pending item was created.

### Finding Description
When a state commitment is stored via `EvmHost.storeStateMachineCommitment` (called from `HandlerV2.handleConsensus`), only the commitment and its update timestamp are recorded: [1](#0-0) 

Later, every message-processing entrypoint recomputes the elapsed delay against the **current** `challengePeriod`, not the one that was active when that specific height's commitment was stored: [2](#0-1) [3](#0-2) 

`challengePeriod` itself lives in the single mutable `_hostParams` struct, updated wholesale by `updateHostParamsInternal`: [4](#0-3) 

The Substrate ISMP core has the identical structural pattern — `verify_delay_passed` also reads the **current** `challenge_period(id)` value against the stored `update_time`: [5](#0-4) 

Because the challenge period is a single global (per state machine) setting rather than being snapshotted per-commitment, any reduction of `challengePeriod`/`challenge_period` retroactively shortens (or, at `0`, eliminates) the fraud-proof window for *every already-pending* state commitment simultaneously — not just newly created ones. This is structurally identical to the multisig bug: a "reconfiguration" (owner set change / challenge-period change) is applied to *pre-existing pending state* (transactions / state commitments) instead of only affecting future ones, letting stale/pending items be finalized under weaker conditions than what applied when they were created.

### Impact Explanation
If the challenge period is reduced (or set to zero) while state commitments from a byzantine or eclipsed counterparty chain are still within their original challenge window, relayers can immediately submit `PostRequest`/`GetResponse`/timeout messages anchored to those commitments before fishermen had the originally-promised time to submit a fraud proof and veto them via `_vetoes`. Per the protocol's own threat model, this is the exact vector documented for eclipse/long-range attacks — messages based on a forged/byzantine state commitment become actionable, resulting in acceptance of false state and potential unauthorized fund movement across the bridge (`docs/content/protocol/interoperability/consensus-proofs.mdx`, lines 91–143, describes this precisely as what the challenge window is meant to prevent).

### Likelihood Explanation
Reachability requires the `hostManager` (cross-chain governance from Hyperbridge) or, on Substrate, `AdminOrigin`, to call `updateHostParams` / `update_consensus_state` with a smaller `challengePeriod`. This is a privileged/governance action, which the stated bounty gate explicitly excludes ("Discard: ... compromised relayer/prover/operator assumptions ... admin, governance actor"). I could not identify, within the code I reviewed, any unprivileged/permissionless path that lets an attacker independently shrink or bypass the effective challenge period for already-pending commitments — so likelihood as a standalone unprivileged-attacker bug is low/unconfirmed, and this candidate sits at the boundary of the impact gate.

### Recommendation
Snapshot the challenge period at the time each state commitment is stored (alongside `_stateCommitmentsUpdateTime`), and use that snapshotted value — not the live `_hostParams.challengePeriod` — when validating delay elapsed for any message anchored to that height. This ensures a later governance-driven parameter change can only affect future commitments, never retroactively finalize commitments that are still within their originally-promised fraud-proof window. Apply the analogous fix to `challenge_period` lookups in `modules/ismp/core/src/handlers.rs`.

### Proof of Concept
Conceptual (not independently executed):
1. Hyperbridge (via `hostManager`) or Substrate `AdminOrigin` calls `updateHostParams`/`update_consensus_state` reducing `challengePeriod` from, e.g., 30 minutes to 0, while a state commitment `H` submitted 5 minutes ago (under the old 30-minute rule) is still within its original window and potentially fraudulent.
2. A relayer immediately calls `handlePostRequests`/`handleGetResponses` with proof anchored at height `H`; `HandlerV2` computes `delay = 5 minutes`, `challengePeriod = 0`, so `challengePeriod != 0 && challengePeriod > delay` is false — the check passes instantly. [6](#0-5) 
3. The request is dispatched to the destination module before any fisherman could have vetoed commitment `H` under the terms originally promised, defeating the optimistic-bridging safety guarantee described in the protocol docs.

Given the governance-gating caveat above and the explicit exclusion of governance/admin-actor paths in the impact gate, this finding should be treated as a **design-hardening recommendation** rather than a confirmed unprivileged-exploit vulnerability; I did not find a fully unprivileged analog of the reported bug elsewhere in the codebase within the scope I was able to search.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,

	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host

		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
