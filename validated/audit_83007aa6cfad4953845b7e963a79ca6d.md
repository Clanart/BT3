### Title
Scanner reports coinbase (immature) outputs as spendable `ReceivedOutput`s with no API to enforce coinbase maturity - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`Scanner::scan_block` scans every transaction in a block, including `txdata[0]` (the coinbase transaction), and returns matching outputs as ordinary `ReceivedOutput`s. `ReceivedOutput` carries no flag or metadata indicating coinbase provenance, and the crate provides no function to check or filter maturity — the only mitigation is a doc comment telling the caller to re-implement the check or to call `scan_transaction` on `block.txdata[1 ..]` themselves. The security-relevant property (only reporting consensus-spendable outputs) exists as an acknowledged requirement but has no enforcing implementation, mirroring a blacklist modifier whose role can never be assigned.

### Finding Description
`Scanner::scan_block` iterates `block.txdata` in full and delegates to `scan_transaction`, which matches any `output.script_pubkey` present in `self.scripts` and emits a `ReceivedOutput` keyed by `(txid, vout)` [1](#0-0) . The doc comment admits the coinbase "is bound by maturity" and that "a post-processing pass is needed to remove those outputs," yet no such pass, flag, or maturity check exists anywhere in the crate [2](#0-1) . `ReceivedOutput` stores only `offset`, `output`, and `outpoint`, so downstream consumers cannot distinguish a coinbase output from a normal one [3](#0-2) . Even `scan_transaction` alone cannot identify coinbase inputs since it never inspects `tx.input`.

### Impact Explanation
Bitcoin consensus forbids spending coinbase outputs for 100 blocks. Any block reward paid to a Serai-scanned P2TR script is reported as a received, apparently spendable `ReceivedOutput`. If the wallet/signing pipeline consumes it, the resulting spend transaction is consensus-invalid — the funds are reported received but are not spendable, and any batch spend built on the output fails entirely until the poisoning output is manually excluded. A miner (an unprivileged party) can deliberately direct a coinbase payout to a registered offset script to trigger this.

### Likelihood Explanation
Reachable by anyone able to send a Bitcoin transaction paying to a registered script; a coinbase payment requires mining a block, which is costly on mainnet but requires no privileges, keys, or cooperation from Serai. The missing check fires deterministically on every scanned block containing a matching coinbase output.

### Recommendation
Add an explicit maturity check: in `scan_block`, either skip `block.txdata[0]` or mark coinbase-derived `ReceivedOutput`s (e.g., an `is_coinbase`/coinbase-maturity field set during scan) and expose a filter so consumers cannot treat immature outputs as spendable. Do not rely on callers reading the doc comment and re-implementing consensus rules out-of-band.

### Proof of Concept
1. Register a key/offset with `Scanner::new` / `register_offset`, obtaining script `S` [4](#0-3) .
2. Construct (or mine on regtest) a block whose `txdata[0]` coinbase has an output with `script_pubkey = S`.
3. Call `scanner.scan_block(&block)`; the coinbase output is returned as a `ReceivedOutput` indistinguishable from a mature payment [5](#0-4) .
4. Feed the `ReceivedOutput` into the spend path; the produced transaction violates BIP/consensus coinbase-maturity rules and is rejected — funds reported received are not spendable.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
