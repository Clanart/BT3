## Finding: `resolveWithin()` boundary check uses raw `startsWith` without a path-separator guard

The analog to the LinkedList sentinel-equality bug (a boundary comparison that is *technically* satisfied but does not reflect the intended semantic boundary) exists in GitHub Desktop's path-containment guard, `_resolveWithin()`.

### Title
Path-containment check `realResolved.startsWith(realRoot)` allows sibling-directory escape - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` (and its POSIX/Win32 variants) is the app-wide guard used to make sure an attacker/repo-controlled relative path cannot resolve to a location outside a given root directory. The final containment check is a bare string comparison, `realResolved.startsWith(realRoot)`, with no check that the byte immediately following `realRoot` in `realResolved` is a path separator (or that the strings are equal). This is structurally identical to the reported LinkedList bug: an equality/boundary predicate (`isEmpty`, "is this still inside the root") that passes for a value that is only accidentally a string-prefix match, not a semantic match.

### Finding Description [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`realRoot` is the repository path (e.g. `/Users/victim/Documents/GitHub/myrepo`). If the resolved candidate path is a *sibling* directory whose name happens to share `realRoot` as a literal string prefix — e.g. `/Users/victim/Documents/GitHub/myrepo-secrets/token.txt` — `startsWith` returns `true` even though that path is **not** underneath the repository root at all. The function's own doc comment promises the resolved path is "guaranteed to reside at, or underneath" the root [2](#0-1) , which is false for this case.

The unit tests for this function only exercise `..`-traversal-then-return-to-root and symlink-escape cases; there is no test asserting that a same-prefix sibling directory is rejected [3](#0-2) .

### Impact Explanation
`resolveWithin` gates real file-system read/write operations against attacker-influenced relative paths:
- `Dispatcher.openRepositoryFromUrl` resolves a `filepath` supplied via the `x-github-client://openLocalRepo` deep link and calls `shell.showItemInFolder(resolved)` on the result [4](#0-3) .
- `buildConflictContext` resolves conflicted-file paths before reading their content into a prompt sent to Copilot [5](#0-4) .
- `_acceptCopilotConflictResolutions` resolves a conflict-resolution path and then **writes** model-produced content to that path with `writeFile(absolutePath, ...)` [6](#0-5) .

If the containment check is bypassed via the sibling-prefix confusion, these call sites could read or write files outside the intended repository directory — matching the "file write or read outside the repo" and "silent corruption of what the user commits" impact categories.

### Likelihood Explanation
Exploitation requires the resolved candidate to land in a directory whose name is `realRoot`'s name plus a suffix (e.g. `myrepo` vs `myrepo-legacy`), which must already exist on disk as a sibling of the repository. This is a real but narrower precondition than a full path-traversal bypass — it depends on incidental directory naming next to the cloned repository (a plausible layout for users who keep multiple related clones, e.g. `myrepo`, `myrepo-archive`, `myrepo-secrets`, side by side in the same parent folder such as `~/Documents/GitHub`). The `filepath` deep-link vector additionally blocks fully-absolute inputs via `isAbsolute(filepath)` before calling `resolveWithin`, but relative traversal segments (`../myrepo-secrets/...`) are explicitly allowed by design (per the "traverse out, and then back into, the root" test), so the guard's only remaining protection against escaping to a sibling is the flawed `startsWith` check.

### Recommendation
Change the final containment check to require an exact match or a match followed by the platform path separator:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Apply the same fix to the POSIX/Win32 variants, using the corresponding separator for each `options` variant.

### Proof of Concept
1. Repository root: `/Users/victim/Documents/GitHub/myrepo`.
2. A sibling directory exists: `/Users/victim/Documents/GitHub/myrepo-secrets/token.txt`.
3. Call `resolveWithin('/Users/victim/Documents/GitHub/myrepo', '../myrepo-secrets/token.txt')`.
4. `resolved` normalizes/resolves to `/Users/victim/Documents/GitHub/myrepo-secrets/token.txt`; `realRoot` is `/Users/victim/Documents/GitHub/myrepo`.
5. `realResolved.startsWith(realRoot)` evaluates `true` (string prefix match) even though the resolved path is a completely separate directory, so the function returns the out-of-root path instead of `null`. [7](#0-6)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
