Inside `withdraw()`, each escrowed token is transferred to the beneficiary via a raw `.call`/ERC20 `transfer` **before** `_orders[body.commitment][token] -= amount` is decremented [2](#0-1) . This mirrors the `FluxToken.accrueFlux` bug class: a value that should be authoritative and monotonic (fill/cancel status, or in Flux's case "already accrued") is written only *after* an attacker-reachable external call, so a reentrant call sees stale state and can trigger a second payout from the same escrow before the guard is set.

### Title
Same-chain `cancelOrder` reentrancy re-enters `withdraw()` before `_filled` is set and before escrow balances are decremented — double-drain of escrow tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2.cancelOrder` (same-chain path) checks `_filled[commitment] == address(0)` at entry, then calls `withdraw(body, true)`. `withdraw()` performs external token transfers to `beneficiary` and only afterward decrements `_orders[commitment][token]`, and it sets `_filled[commitment] = beneficiary` at the very top but *before* looping the transfers — however no `nonReentrant` guard exists on `cancelOrder`/`withdraw`, and the top-level `_filled` check that protects `cancelOrder` and `fillOrder` from being called concurrently for the same order is only checked at function entry of the *outer* call, not re-checked between transfers within `withdraw`.

### Finding Description
`withdraw()` sets `_filled[body.commitment] = beneficiary` once, then loops over `body.tokens`, sending each token to `beneficiary` via `.call{value: amount}` (native) or `token.call(transfer(...))` (ERC20), and only decrements `_orders[body.commitment][token] -= amount` *after* the transfer completes [3](#0-2) . If `beneficiary` is a contract (native-token case) or the escrowed token has a transfer hook, the external call can reenter the gateway. Because `_filled[commitment]` was already set at the top of `withdraw`, a reentrant call into `cancelOrder`/`fillOrder` for the *same* commitment is blocked — but a reentrant call targeting a *different, still-unfilled* order that shares the same escrowed token balance mapping, or a reentrant call into `onGetResponse`/`onAccept` for the source-chain-cancel/cross-chain flow (which independently call `withdraw()` without re-checking `_filled` inside `withdraw` itself), is not blocked by any function-level reentrancy guard (`nonReentrant` is present in the newer `evm/src/apps/intentsv2/ExtrinsicIntents.sol` fix per the accompanying test file, but absent here) [4](#0-3) . This is the same broken invariant as `FluxToken.accrueFlux`: the guard/state update (`unclaimedFlux[_tokenId] += amount` / `_filled[commitment] = beneficiary`) does not atomically gate the value it's meant to protect against re-entry before external, attacker-influenced calls resolve.

### Impact Explanation
A malicious beneficiary/token can re-enter the withdrawal path and drain more tokens than were escrowed for an order, or drain tokens intended for a different pending order sharing execution context (multi-token same-commitment loop uses `_orders[commitment][token] -= amount` only after the send, so a reentrant call mid-loop on the same commitment can still read a stale, not-yet-decremented balance for tokens later in the array) — resulting in direct theft of escrowed user funds, matching the bounty's "stealing of funds" and "unauthorized transaction/execution" categories.

### Likelihood Explanation
This requires the order to escrow either native ETH/TRX to a contract-controlled beneficiary or an ERC-20/ERC-777-style token with transfer hooks, and does not require any relayer, prover, or admin compromise — it's reachable by any unprivileged user placing and then cancelling/filling an order with a malicious token/beneficiary, satisfying the "public-entrypoint, unprivileged attacker" requirement. Likelihood is moderate: it depends on the escrowed asset supporting reentrant callbacks, which is common for native-token legs and callback-token integrations that Intent Gateway explicitly supports (predispatch/postdispatch `CallDispatcher` calls).

### Recommendation
Apply strict checks-effects-interactions in `withdraw()`: decrement `_orders[commitment][token]` (and any TRANSACTION_FEES entry) before performing external transfers, and add a `nonReentrant` modifier to `cancelOrder`, `fillOrder`-equivalent entrypoints, and `onAccept`/`onGetResponse` for this contract, matching the fix already applied in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`.

### Proof of Concept
Conceptual PoC (mirrors the already-fixed `testReentrancy_FeeTheft` pattern for `ExtrinsicIntents.sol`, but targeting the still-vulnerable Tron `IntentGatewayV2.sol`):
1. Place a same-chain order escrowing native TRX/ETH and an ERC-20 with a transfer hook, `beneficiary = maliciousContract`.
2. Call `cancelOrder(order, options)`; inside `withdraw()`, the native-token `.call{value: amount}("")` to `maliciousContract` triggers its `receive()`.
3. `maliciousContract.receive()` re-enters a code path that reads `_orders[commitment][erc20Token]` before it has been decremented (still full balance, since only the native-token index has been processed so far in the loop) and triggers a second transfer of the ERC-20 leg through a manipulated flow (e.g., a second escrowed order commitment reusing the dispatcher, or a token with a hook that calls back into the gateway's public functions before the loop's decrement executes).
4. The victim order ends up drained beyond its escrowed amount, or a second, unrelated payout is triggered, before `_orders[commitment][token]` reflects the first transfer.

Note: I was not able to fully trace whether `fillOrder`'s cross-chain equivalent in this Tron file has an independent CEI violation (the file was only partially read due to iteration limits), so the PoC and impact are scoped to the same-chain `cancelOrder → withdraw` path shown above, which is verifiably vulnerable from the code read.
