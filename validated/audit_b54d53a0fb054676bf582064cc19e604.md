### Title
Staged index is silently left corrupted when `git diff` fails during Copilot commit-message generation, causing user to commit unintended content - (File: `app/src/lib/git/diff.ts`)

### Summary
`getFilesDiffText()` in [1](#0-0)  temporarily wipes and rebuilds the Git index (`unstageAll` → `stageFiles(files)` → `git diff --staged` → `unstageAll`) purely to compute a diff for AI commit-message generation. Unlike the adjacent `getResolutionDiff()` function in the same file, which wraps its side-effecting work in a `try/finally` to guarantee cleanup of its temp files ( [2](#0-1) ), `getFilesDiffText` performs the restoring `unstageAll(repository)` call as a plain, unguarded statement after the `git()` invocation ( [3](#0-2) ). If the `git diff` process throws instead of resolving, the restoring `unstageAll` is skipped entirely, and the index is left in the intermediate, fully-reset-then-staged-with-`files` state instead of reflecting the user's actual prior staging selections (including any partial/hunk-level selections, which are destroyed by `unstageAll` and never restored as partial selections since `stageFiles` fully stages selected files for the diff).

### Finding Description
The broken invariant is: "the index must be restored to the user's real staging selection after this temporary diff computation, regardless of outcome." The corrupted value is the Git index/staging area (`.git/index`) of the user's repository.

The call chain: `_generateCommitMessage()` in `app-store.ts` invokes `getFilesDiffText(repository, filesSelected, ...)` inside a `try { … } catch (e) { … }` block ( [4](#0-3) ). The `catch` block only surfaces the error to the user via `emitError` and returns `false` — it never calls `unstageAll` or otherwise restores the index ( [5](#0-4) ). So any exception thrown by `getFilesDiffText` propagates without the index ever being restored.

Inside `getFilesDiffText`, the sequence is:
1. `unstageAll(repository)` — destroys the user's existing staging state, including partial/hunk selections.
2. `stageFiles(repository, files)` — fully stages the selected files (partial selections are only preserved transiently for the diff computation, not restored afterward).
3. `git(['diff', ..., '--staged', ...], ..., { successExitCodes: new Set([0]) })` — if this throws (a `GitError` because of an unexpected exit code, or a lower-level process error such as exceeding the child-process output buffer for a large/binary file), execution jumps straight out of the function.
4. `unstageAll(repository)` (line 598) — the compensating cleanup — is never reached if step 3 throws.

Because `successExitCodes` is set to `{0}` only (unlike `getResolutionDiff`'s `{0, 1}`), and because the diffed content is fully attacker-influenced (any file in a cloned/fetched repository that the user selects to commit), a crafted large file, a file that trips a non-`--no-ext-diff`-suppressible git failure, or any condition that makes the underlying `git diff --staged` process exit non-zero or fail to spawn/produce a huge buffer will leave the working index staged in a state the user did not choose and no longer reflects their partial-selection intent.

### Impact Explanation
This meets the "silent corruption of what the user commits or pushes" criterion. After the failure, the UI's "Changes" list is driven by subsequent `git status`, but the actual index content used by any following raw `git commit` (or another Desktop action that trusts current staged state) is now whatever `stageFiles(files)` fully staged, not the user's original partial hunk selections. If the user does not notice and proceeds to commit (relying on Desktop's changes list, which may re-derive selection from status but the underlying index bytes committed may not correspond one-to-one with what the user intended for partially selected files), the resulting commit can include content the user did not consciously choose to stage, or drop the record of a still-pending partial selection. This is a quiet, hard-to-detect corruption of the commit's actual staged content.

### Likelihood Explanation
This is triggered by clicking "Generate Commit Message with Copilot" (a normal, low-friction user action exposed in the commit message UI, see `getGenerateCommitMessageMenuItem` in [6](#0-5) ) on a repository containing attacker-supplied content (a freshly cloned or fetched repo) with files large or unusual enough to cause the `git diff --staged` step to fail. No admin rights, local access, or social engineering beyond normal use of the feature is required — the attacker only needs to control the repository content that ends up staged for diffing.

### Recommendation
Wrap the staging/diff sequence in `getFilesDiffText` in a `try/finally` (mirroring `getResolutionDiff`) so that `unstageAll(repository)` unconditionally executes even when the `git()` call throws, restoring the index before the error propagates:
```
try {
  await unstageAll(repository)
  await stageFiles(repository, files)
  const { stdout } = await git([...], repository.path, 'getFilesDiffText', { successExitCodes, encoding: 'buffer' })
  ...
} finally {
  await unstageAll(repository)
}
```

### Proof of Concept
1. Clone/fetch a malicious repository containing a file crafted to make `git diff --staged` on it exit with a non-zero code (or exceed Desktop's `child_process` buffer, causing the promise from `git()` to reject) — e.g., an oversized or specially-encoded file.
2. In GitHub Desktop, select that file (and possibly other files with partial hunk selections) for commit.
3. Click "Generate Commit Message with Copilot" (`_generateCommitMessage` → `getFilesDiffText`), see [7](#0-6) .
4. The `git diff` step throws; `_generateCommitMessage`'s `catch` swallows it into an error dialog only ( [5](#0-4) ) and the final `unstageAll` in `getFilesDiffText` ( [8](#0-7) ) never runs.
5. Inspect `.git/index` (or run `git status`/`git diff --staged` directly): the index now reflects `stageFiles(filesSelected)`'s full-file staging rather than the user's original (possibly partial) selection, and any other previously-staged files were unstaged by the initial `unstageAll` and never restored.
6. If the user proceeds to commit without noticing, the produced commit's staged content silently diverges from what they intended.

export async function getFilesDiffText(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  commitish?: string
): Promise<string> {
  // Clear the staging area, our diffs reflect the difference between the
  // working directory and the last commit (if any) so our commits should
  // do the same thing.
  await unstageAll(repository)

  await stageFiles(repository, files)

  // `--no-ext-diff` should be provided wherever we invoke `git diff` so that any
  // diff.external program configured by the user is ignored
  const args = [
    'diff',
    '--no-ext-diff',
    '--patch-with-raw',
    '--no-color',
    '--staged',
    ...(commitish ? [commitish] : []),
  ]
  const successExitCodes = new Set([0])

  const { stdout } = await git(args, repository.path, 'getFilesDiffText', {
    successExitCodes,
    encoding: 'buffer',
  })

  await unstageAll(repository)
