### Title
Unhandled `KeyError` in `Offer.to_valid_spend()` on zero-amount requested asset with no matching offered coins crashes offer acceptance - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.to_valid_spend()`, the method that turns an accepted offer into a pushable `WalletSpendBundle`, indexes `all_offered_coins[asset_id]` for every asset in `requested_payments` without checking that the key exists. `get_offered_coins()` only populates a dictionary key for an asset if it heuristically found at least one matching settlement-payment coin `(if coins_for_this_spend != []: offered_coins.setdefault(asset_id, []) ...)`. A malicious offer file can request a zero-amount payment for an asset that has no genuinely offered coins for it, passing the `is_valid()` "enough funds" check while leaving that asset id absent from `all_offered_coins`, causing a `KeyError` when the counterparty (or a wallet UI/RPC caller) tries to accept/complete the offer.

### Finding Description
`Offer.is_valid()` computes `arbitrage()` as `offered_amounts.get(asset_id, 0) - requested_amounts.get(asset_id, 0)` for the union of requested/offered asset ids, and only requires this to be `>= 0` [1](#0-0) [2](#0-1) . If an attacker crafts an offer with a `requested_payments[asset_id]` entry whose `NotarizedPayment.amount == 0`, then `requested_amounts[asset_id] == 0`; if the offer's `_bundle` contains no coin that `_get_offered_coins()` heuristically recognizes as an offered coin for that `asset_id`, `offered_amounts.get(asset_id, 0)` is also `0`, so `arbitrage_dict[asset_id] == 0`, satisfying `is_valid()`.

Crucially, `_get_offered_coins()` only inserts a dictionary entry for `asset_id` when it actually found matching coins: `if coins_for_this_spend != []: offered_coins.setdefault(asset_id, []) ...` [3](#0-2) . When no coins match (as engineered above), the key is simply never created in `get_offered_coins()`'s cached dict.

`to_valid_spend()` then unconditionally does:
```
all_offered_coins: dict[bytes32 | None, list[Coin]] = self.get_offered_coins()
...
for asset_id, payments in self.requested_payments.items():
    offered_coins: list[Coin] = all_offered_coins[asset_id]
``` [4](#0-3) 

Since `asset_id` is absent from `all_offered_coins`, this line raises an unhandled `KeyError`, crashing the code path that processes/accepts the offer — analogous to the libvirt CVE-2017-2635 pattern where handling of an "empty"/missing resource (an empty drive) that was not defensively checked for caused a NULL/undefined-reference crash.

### Impact Explanation
`to_valid_spend()` is invoked from `chia/wallet/trade_manager.py` as part of accepting/responding to an offer [5](#0-4) . An offer file is fully attacker-controlled data that any offer counterparty can send to another wallet user to take. Triggering the `KeyError` denies the victim wallet the ability to process/accept that offer (and can crash the RPC call handling it), which is a wallet-reachable, spend-triggered processing halt — the required "no-additional-privilege" DoS class called out in the validation rules for offers/trades.

### Likelihood Explanation
Likelihood is moderate-to-high: constructing an offer with a zero-amount requested payment for an asset that has no corresponding offered coin does not require any special access — it only requires building a custom `Offer`/`WalletSpendBundle` (bypassing the normal `create_offer_for_ids` helper, which a hostile actor writing their own offer-generation code could easily do) and sending the resulting offer file to a victim. No signature validity or on-chain state is required to reach the crash, since the crash occurs purely in local Python object construction/analysis before any CLVM execution or push to the mempool.

### Recommendation
In `Offer.to_valid_spend()`, guard the lookup with `all_offered_coins.get(asset_id, [])` (or raise a clean, caught `ValueError`) instead of a bare `dict[asset_id]` access, and/or reject offers during `__post_init__`/`is_valid()` that request a non-empty payment list for an asset with zero offered coins (even when the requested amount is 0), so malformed/adversarial offers fail with a handled validation error rather than an unhandled `KeyError`.

### Proof of Concept
Conceptual PoC (not fully executed, given tool constraints — logic verified by static reading of `chia/wallet/trading/offer.py`):
1. Build a `WalletSpendBundle` whose only settlement-style spend does not match any of the offer's `driver_dict`/`OFFER_MOD` heuristics for a chosen `asset_id` (e.g., use an unrelated CAT `asset_id` in `requested_payments` that never appears among the actual settlement payment coins in `_bundle`).
2. Set `requested_payments[asset_id] = [NotarizedPayment(ph, uint64(0), None, nonce=...)]` (amount `0`).
3. Construct `Offer(requested_payments, bundle, driver_dict)`.
4. Call `offer.is_valid()` → returns `True` because `arbitrage()[asset_id] == 0 - 0 == 0`.
5. Call `offer.to_valid_spend(arbitrage_ph)` → raises `KeyError: asset_id` at `all_offered_coins[asset_id]` [6](#0-5) , since `asset_id` was never added by `_get_offered_coins()`.

Note: I was unable to run this scenario against a live wallet due to tool limitations (read-only code search only); the described flow is derived directly from the reachable code paths and dictionary semantics shown above. Confirming exploitability end-to-end (e.g., via `trade_manager.respond_to_offer`) would require executing this PoC in a running Devin session with the actual test harness.

    def arbitrage(self) -> dict[bytes32 | None, int]:
        """
        Returns a dictionary of the type of each asset and amount that is involved in the trade
        With the amount being how much their offered amount within the offer
        exceeds/falls short of their requested amount.
        """
        offered_amounts: dict[bytes32 | None, int] = self.get_offered_amounts()
        requested_amounts: dict[bytes32 | None, int] = self.get_requested_amounts()

        arbitrage_dict: dict[bytes32 | None, int] = {}
        for asset_id in [*requested_amounts.keys(), *offered_amounts.keys()]:
            arbitrage_dict[asset_id] = offered_amounts.get(asset_id, 0) - requested_amounts.get(asset_id, 0)

        return arbitrage_dict
