## Title
Unrestricted, non-reentrant-guarded `CallDispatcher.dispatch()` lets any caller drain tokens/ETH temporarily resident in the shared dispatcher during order fulfillment - ([File: evm/src/utils/CallDispatcher.sol])

## Summary
The Balancer flashloan bug lets anyone call `flashLoan()` and name a trusted contract as `recipient`, so the trusted callback executes on attacker-supplied inputs with no binding to a specific operation the victim actually started. Hyperbridge's `CallDispatcher` reproduces the same broken invariant: it is a shared, singleton "untrusted call executor" used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to hold assets mid-flow and execute arbitrary `Call[]` batches, but `dispatch()` has **no caller restriction whatsoever** and the contract has **no reentrancy guard**, even though it repeatedly custodies real user/order funds between a transfer-in step and a sweep-back step within the same transaction.

## Finding Description
`CallDispatcher.dispatch()` is a bare external function with zero access control: [1](#0-0) 

Any account — not just the apps that are supposed to own the current operation — can call it directly and pass an arbitrary `Call[]` (`to`, `value`, `data`), executed with no notion of "whose operation is this."

This contract is used as a shared per-host instance (`_params.dispatcher`) by multiple apps that transiently move real value onto it and then read back its *entire* balance to sweep it, rather than tracking a per-order amount: [2](#0-1) [3](#0-2) 

Both predispatch and postdispatch flows: (1) push tokens/ETH to the dispatcher, (2) call `ICallDispatcher(dispatcher).dispatch(...)` with the *order's own* attacker/user-controlled `Call[]`, then (3) sweep back `IERC20(token).balanceOf(dispatcher)` / `dispatcher.balance` — the dispatcher's full current balance, not an amount scoped to that specific order.

Because `dispatch()` itself is public and un-gated, and the calls it executes are attacker-controlled (`order.predispatch.call` / `order.output.call` are supplied by whoever created the order), a malicious order's calldata can re-enter `CallDispatcher.dispatch()` directly — bypassing the app entirely — and issue a transfer of "whatever balance the dispatcher currently holds" to itself. Since the SDK/solver flow explicitly supports batching multiple `select()`/`fillOrder()` calls for different orders into a single atomic transaction (documented ERC-7821 batch execution via `SolverAccount`), a second order's output tokens can be resident on the exact same shared `CallDispatcher` instance at the moment a first (malicious) order's calldata runs its `dispatch()` reentry — letting the attacker sweep tokens that belong to a different order/beneficiary the attacker never funded or was authorized to touch.

The corrupted value is `IERC20(token).balanceOf(dispatcher)` (or `dispatcher`'s native ETH balance): it is read and swept as an undifferentiated pool rather than a value bound to a specific order commitment, and `dispatch()` has no check that the caller is the app/order currently entitled to use it. This is the exact structural analog of the flashloan bug: a shared, privileged executor with an unauthenticated entrypoint that any party can invoke with arbitrary inputs, causing it to act on value that does not belong to the caller's own operation.

## Impact Explanation
This meets the bounty's fund-theft/unauthorized-execution bar: an unprivileged attacker can craft an order whose `predispatch.call`/`output.call` reenters `CallDispatcher.dispatch()` to redirect tokens/ETH belonging to a different, concurrently in-flight order to themselves, since the sweep and the dispatch step both operate on the dispatcher's raw balance rather than a per-order-scoped amount, and `dispatch()` enforces no caller/operation binding at all.

## Likelihood Explanation
Exploitability depends on the ability to get two orders' fund-bearing dispatcher calls to be resident in the dispatcher within the same transaction (e.g., via batched `fillOrder`/`placeOrder` calls, which the SDK's `SolverAccount` batching explicitly supports) — this does not require a malicious relayer, prover, or admin, only a user/attacker able to construct an order with malicious `predispatch`/`output` calldata, which the protocol allows by design ("Calldata Execution").

## Recommendation
- Add a caller allowlist (or `msg.sender`-restricted) check to `CallDispatcher.dispatch()` so only the specific app instance/operation currently entitled to it may invoke it.
- Bind each dispatch to the specific order commitment/operation id (transient-storage tag, similar to the report's suggested "verify callback was started by this contract") so a reentrant call cannot act on a different order's funds.
- Replace "sweep full `balanceOf(dispatcher)`" logic with sweeps scoped to the exact amount transferred in for that specific order, and add a reentrancy guard around `dispatch()`.

## Proof of Concept
1. Attacker places Order A with `predispatch.assets` = some token, and `predispatch.call` crafted to call `CallDispatcher.dispatch()` directly (reentrant), targeting `IERC20(token).transfer(attacker, IERC20(token).balanceOf(dispatcher))`.
2. Attacker (as solver or via a batched `SolverAccount` UserOperation) arranges that, in the same transaction, another user's Order B `fillOrder()` has already transferred Order B's output tokens onto the shared `CallDispatcher` (step 1 of `_execute`) before Order A's predispatch runs its reentrant sweep.
3. Order A's `predispatch.call` executes, calling `CallDispatcher.dispatch()` directly and draining the dispatcher's current balance — which at that moment includes Order B's output tokens — to the attacker's address.
4. Order B's own sweep subsequently finds a reduced/zero balance and reverts or under-delivers, while the attacker has extracted Order B's funds via a `dispatch()` call that had no authorization check tying it to Order A's own operation.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
