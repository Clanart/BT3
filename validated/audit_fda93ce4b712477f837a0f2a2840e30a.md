### Title
`DLEqProof::verify` / `MultiDLEqProof::verify` accept zero-length statement lists, letting a "proof of nothing" verify trivially — ([File: crypto/dleq/src/lib.rs])

### Summary
The external report describes a verifier that folds a message hash with a proof list without enforcing a minimum/expected proof length, allowing a truncated proof (which corresponds to an intermediate trie node) to pass verification and enabling replay. The analog in Serai is in the `dleq` crate: `DLEqProof::verify` iterates `generators.iter().zip(points)` to append verification statements to the transcript, but only checks that the two lists have *equal* length — not that the length is nonzero or matches any expected value. With an empty list, the transcript contains only the `domain_separate(b"dleq")` frame, the computed challenge is a fully public, attacker-derivable value, and the proof's `s` scalar is never consumed by any statement. Any attacker can therefore construct a `(c, s)` pair that verifies against zero points — i.e., a truncated proof certifying nothing is accepted.

### Finding Description
In `crypto/dleq/src/lib.rs:160-180`, `DLEqProof::verify` performs:

```rust
if generators.len() != points.len() {
  Err(DLEqError::InvalidProof)?;
}
transcript.domain_separate(b"dleq");
for (generator, point) in generators.iter().zip(points) {
  Self::verify_statement(transcript, *generator, *point, self.c, self.s);
}
if self.c != challenge(transcript) { Err(DLEqError::InvalidProof)?; }
```

When `generators`/`points` are both empty, no `(generator, nonce, point)` tuples are ever appended to the transcript. The expected challenge `challenge(transcript)` is then just `C::hash_to_F` over the bare `"dleq"` domain-separation frame on whatever base transcript the caller supplied — a value the prover can compute locally with no secret. The proof field `s` is completely unconstrained (it only enters via `verify_statement`, which is never invoked). So a deserialized `DLEqProof { c: <computable>, s: <anything> }` returned by `DLEqProof::read` (lib.rs:191-193) is accepted.

`MultiDLEqProof::verify` (lib.rs:264-294) has the same shape: it checks `self.s.len() == generators.len()` and `points.len() == generators.len()`, plus a per-series inner `points.len() != generators.len()` check (lib.rs:270-281), but all of these are satisfied by an outer empty list — and critically, every inner series may also be empty (`generators = [[]]` passes, contributing an empty `zip` body to the transcript under a `discrete_logarithm` label). A "proof" with `s: []` or an `s` vec whose entries are never meaningfully bound verifies with a publicly computable `c`.

This mirrors the Merkle-trie bug exactly: a verification routine whose soundness depends on folding a variable-length statement list into a challenge accepts a degenerate/shortened input because no lower bound on the list length is enforced.

### Impact Explanation
A caller that uses `DLEqProof`/`MultiDLEqProof` as a stand-alone verifier for a dynamically-sized statement set — exactly the documented purpose of `MultiDLEqProof` ("n distinct DLEq proofs") — accepts a forged proof whenever the attacker can influence or truncate the statement lists presented for verification. This produces a forged proof acceptance: `verify` returns `Ok` for a proof that binds no discrete logarithm to any point, equivalent to the shortened Merkle proof validating an intermediate node. In the original report the in-tree consumer was unaffected while the stand-alone library was flawed; the same applies here — `promote`'s `GeneratorProof` supplies fixed-length statements, but the `dleq` library itself offers the broken API to any consumer.

### Likelihood Explanation
Reachability is limited: an attacker must be in a position where the verifier's `generators`/`points` lists (or the number of discrete logs passed to `MultiDLEqProof::read`) are attacker-influenced or empty-by-construction, which the library permits but does not itself arrange. This matches the original finding's profile — the primitive is exposed, downstream callers may or may not trip it — so it is a real but conditional verifier flaw. Medium severity.

### Recommendation
Add explicit non-emptiness (or expected-length) validation in `DLEqProof::verify` — e.g., `if generators.is_empty() { Err(DLEqError::InvalidProofLength)?; }` — and in `MultiDLEqProof::verify` reject both an empty outer list and empty inner series (each `generators[i].is_empty()`), rather than relying solely on the equality checks at lib.rs:166-167 and lib.rs:270-281. Alternatively, document in the NatSpec that the proof's security requires a non-empty, caller-fixed statement set — which is precisely how the upstream Scroll issue was resolved.
