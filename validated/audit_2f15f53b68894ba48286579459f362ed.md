### Title
Commit-message spoofing causes `/clean_gone` to force-delete arbitrary branches and force-remove worktrees - (File: `plugins/commit-commands/commands/clean_gone.md`)

### Summary
The `/clean_gone` slash command identifies "gone" branches by piping `git branch -v` into `grep '\[gone\]'`, but `git branch -v` (single `-v`) never prints upstream tracking status at all — that annotation only appears with `git branch -vv`. Consequently the grep can only ever match on the literal text of the printed line, which is `<flag><branchname> <abbrev-sha> <commit-subject>` — meaning any branch whose HEAD commit's first-line subject happens to contain the literal substring `[gone]` will be treated as a stale/deleted-upstream branch and force-deleted, regardless of its real tracking state.

### Finding Description
Step 3 of `plugins/commit-commands/commands/clean_gone.md` runs: [1](#0-0) 

The pipeline is `git branch -v | grep '\[gone\]' | sed 's/^[+* ]//' | awk '{print $1}' | while read branch; do ... git branch -D "$branch"; done`. Step 1 explicitly uses `git branch -v` (not `-vv`): [2](#0-1) 

`git branch -v` output format is only `<flag><branch> <sha> <commit-subject>` — it contains no `[origin/x: gone]` annotation (that requires `-vv`). This means the `grep '\[gone\]'` filter is not actually inspecting tracking metadata at all; it is substring-matching the entire printed line, which includes the commit subject text. Any local branch whose tip commit's first-line message contains the literal text `[gone]` (e.g., a commit titled `Fix parser: state [gone] handling`) will match the grep unconditionally, independent of whether its upstream remote branch was actually deleted. The `sed`/`awk` chain then extracts the branch name from field 1 of that matched line and the loop calls `git worktree remove --force` (if a worktree exists) followed by `git branch -D "$branch"` — an unconditional force delete/force removal, with no re-verification that the branch's upstream is actually gone.

There is no allowlist, confirmation prompt, or secondary validation step in the command file before the destructive `git branch -D` / `git worktree remove --force` calls — the LLM is instructed to just execute the pipeline as written.

### Impact Explanation
An attacker who can get a commit with a crafted subject line merged/present in the victim's repository (e.g., via a contributed branch, a cherry-picked commit, or a commit authored directly by the user without realizing the significance) can cause `/clean_gone` to force-delete that branch via `git branch -D`, and if a worktree is attached, forcibly remove that worktree via `git worktree remove --force`, causing loss of uncommitted work or unmerged commits. This is an unauthorized destructive filesystem/git action triggered by ordinary repository content (a commit message), fitting the "unauthorized command or file action" / "workspace escape via automation flow" impact category for Claude Code plugin commands.

### Likelihood Explanation
The precondition is narrow but realistic: the victim must run `/clean_gone` in a repository containing a commit whose first-line subject contains the literal string `[gone]` (case-sensitive, bracket-and-word match). This can happen accidentally (a developer's own commit message referencing "state gone" logic) or be deliberately introduced by any contributor whose commits land in the local branch list (feature branches, PR branches checked out locally, etc.) — no special privilege is required to author a commit message. Because the root cause is a fundamentally broken detection mechanism (`-v` vs `-vv`), the false-positive is fully deterministic and repeatable, not probabilistic.

### Recommendation
Rewrite the detection logic to use `git branch -vv` (which does emit the real `[<remote>: gone]` tracking annotation) and anchor the grep to the specific tracking-status column rather than doing an unanchored substring match on the whole line (e.g., match on `: gone\]` at the tracking-info position, not merely `\[gone\]` anywhere in the text). Additionally, prefer `git for-each-ref --format='%(refname:short) %(upstream:track)'` filtered on `gone`, which structurally separates tracking status from the commit subject and cannot be spoofed by commit message content. Add a confirmation/dry-run listing of branches slated for deletion before executing `git branch -D`.

### Proof of Concept
Integration test plan:
1. In a scratch repo, create branch `feature-x` with a single commit whose message is exactly `Fix parser: state [gone] handling`.
2. Do not configure any upstream/remote tracking for `feature-x` (or configure one that is NOT deleted) — its true tracking status is not "gone".
3. Run `git branch -v` and confirm the printed line for `feature-x` contains the literal substring `[gone]` purely from the commit subject.
4. Run the exact pipeline from `clean_gone.md` step 3 against this repo.
5. Assert that `feature-x` is selected by the `grep '\[gone\]'` filter and is force-deleted (`git branch -D feature-x` executes successfully) even though its upstream was never deleted/gone — demonstrating the false-positive destructive branch deletion.
