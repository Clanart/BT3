### Title
Attacker-controlled threshold parameters cause quadratic Lagrange interpolation CPU exhaustion - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts attacker-controlled `t` and `n` values of up to `u16::MAX`, parses `n` verification shares, and then derives the group key using per-participant Lagrange interpolation. With `t = n = 65,535`, a roughly 2 MiB serialized input causes approximately `65,535²` field operations inside `ThresholdKeys::new`, making deserialization consume disproportionate CPU resources. [1](#0-0) 

### Finding Description
The serialized `t`, `n`, and participant index are read directly from attacker-controlled bytes. The implementation then reads `n` verification shares before validating the resulting `ThresholdParams` through `ThresholdKeys::new`. [1](#0-0) 

`ThresholdKeys::new` constructs the list `1..=t` and calls `interpolation_factor` once for every participant. [2](#0-1)  For Lagrange interpolation, each `interpolation_factor` call iterates over every included participant and performs scalar multiplication, subtraction, and an inversion. [3](#0-2) 

Because `t` and `n` are both 16-bit values, a syntactically valid input can set both to `65,535`. The verification-share list contains unique indexes generated directly from `1..=n`, so the parameter validation succeeds when `i` is also within range. [4](#0-3) 

### Impact Explanation
An attacker who can submit serialized `ThresholdKeys` can force a victim to perform billions of scalar field operations from a single input of only about 2 MiB. This is an amplification-style CPU denial of service analogous to nested entity expansion: a small declared structure causes much larger internal computation. [2](#0-1) 

### Likelihood Explanation
`ThresholdKeys::read` is a public deserializer for untrusted encoded key material, and the malicious input is structurally valid: `t <= n`, `i != 0`, `i <= n`, all participant indexes are unique, and all scalar/point encodings can be canonical. [5](#0-4) 

### Recommendation
Bound `t` and `n` to the maximum supported deployment size before parsing variable-length fields. If large threshold sets are required, calculate the first-`t` Lagrange factors in aggregate or with prefix/suffix products rather than recomputing each factor independently, and consider batch scalar multiplication for the verification-share sum. [2](#0-1)

```rust
use std::io::Cursor;

use ciphersuite::{
  Ciphersuite,
  group::{ff::PrimeField, GroupEncoding},
};
use frost::{curve::Secp256k1, ThresholdKeys};

let n = u16::MAX;
let t = n;
let i = n;

let mut input = Vec::new();
input.extend_from_slice(
  &(u32::try_from(Secp256k1::ID.len()).unwrap()).to_le_bytes(),
);
input.extend_from_slice(Secp256k1::ID);

input.extend_from_slice(&t.to_le_bytes());
input.extend_from_slice(&n.to_le_bytes());
input.extend_from_slice(&i.to_le_bytes());

// Lagrange interpolation.
input.push(1);

// A canonical nonzero secret share.
input.extend_from_slice(
  <Secp256k1 as Ciphersuite>::F::ONE.to_repr().as_ref(),
);

// n canonical verification shares.
let share = <Secp256k1 as Ciphersuite>::generator().to_bytes();
for _ in 0..n {
  input.extend_from_slice(share.as_ref());
}

// Enters ThresholdKeys::new and performs O(t^2) interpolation work.
let _keys =
  ThresholdKeys::<Secp256k1>::read(&mut Cursor::new(input)).unwrap();
```

This input uses the maximum representable threshold and participant count accepted by `ThresholdParams::new`, then reaches the quadratic group-key derivation loop. [4](#0-3)
