### Title
Explicit `conditions` frontmatter silently overrides/empties legacy `pattern` scoping, allowing rule authors to evade block rules via `Condition.from_dict` default inference - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`Rule.from_dict` (`plugins/hookify/core/config_loader.py:44-84`) branches on whether the frontmatter contains a `conditions` key at all, not on whether that key yields any usable conditions: [1](#0-0) 

If `conditions` is present but is not a `list` (e.g. a string, dict, or malformed YAML value produced by the plugin's hand-rolled `extract_frontmatter` parser), `isinstance(cond_list, list)` is `False` and `conditions` stays `[]`. Because the legacy fallback is gated on `if simple_pattern and not conditions`, a rule author (or the `/hookify` generation flow) can supply both a `pattern` **and** a malformed/empty `conditions` value; but if `conditions` key is present the legacy `pattern` inference is only skipped when `conditions` ends up truthy. More importantly, `Condition.from_dict` (`plugins/hookify/core/config_loader.py:22-29`) silently defaults any missing sub-fields: [2](#0-1) 

A condition item missing `field` becomes `field=''`, and one missing `pattern` becomes `pattern=''`. Neither `Rule.from_dict` nor `load_rule_file` (`plugins/hookify/core/config_loader.py:244-274`) validates that resulting conditions are well-formed — the custom YAML-lite parser in `extract_frontmatter` (lines 87-195) makes it easy for legitimately-intended frontmatter (e.g. copy-pasted from a README example, or generated by the `/hookify` slash command per `plugins/hookify/commands/hookify.md`) to produce a `conditions` list where an item is missing `field`/`pattern` due to a parsing quirk (e.g. inline `- field: x, operator: y` syntax without trailing `pattern`, or multi-line dict continuation that doesn't recognize indentation correctly).

Once such a malformed `Condition` reaches `RuleEngine._check_condition` (`plugins/hookify/core/rule_engine.py:144-180`), `condition.field == ''` causes `_extract_field('', ...)` to very likely return `None`, and the check short-circuits with `return False` at line 159-160. Since `_rule_matches` requires **all** conditions to match (lines 117-125), a single malformed condition silently makes the entire rule — including `action: block` rules — never match, with no warning surfaced to the operator at runtime (only a print at load-time for outright missing frontmatter, not for malformed condition items).

By contrast, the legacy `pattern:` field path (lines 56-73) always produces a valid, correctly-inferred `field` (`command`/`new_text`/`content`) and a non-empty `pattern`, so it cannot silently degrade to a no-op condition the same way.

### Impact Explanation
This is a reliability/robustness gap in the rule-authoring format rather than an attacker-controlled privilege escalation. A `block` rule intended to stop dangerous commands (e.g. `rm -rf`) can be rendered permanently inert by a subtly malformed `conditions:` frontmatter block, with the hook engine treating it as "no match" rather than raising a visible parse error. If such a malformed rule file is repo-shipped (e.g., committed to `.claude/hookify.*.local.md` by a contributor, or auto-generated by `/hookify` from ambiguous natural-language input) it would silently reintroduce the class of dangerous commands the rule believed it was blocking, without any signal to the user that protection is broken.

However, exploiting this does **not** meet the bar of "unauthorized local command execution that bypasses approval controls" from an *unprivileged attacker with only repo content*. To reach this bug, the attacker needs the rule *itself* to already be malformed — i.e., either (a) they control the `.claude/hookify.*.local.md` file being written to the victim's `.claude` directory (which requires the victim to already trust and merge attacker-authored config into their working tree — not something that flows automatically from ordinary repo/PR/issue content), or (b) they trick `/hookify` generation into emitting bad frontmatter, which is a Claude-authoring-quality issue, not a parser vulnerability that an attacker can directly and reliably steer via untrusted repository content alone. There is no code path shown where hook execution automatically loads or merges arbitrary repository-supplied rule files without the operator explicitly placing them under `.claude/`.

### Likelihood Explanation
Low as a security bypass technique: it requires an existing rule file with subtly malformed `conditions` entries to already exist in the victim's `.claude` directory, which is a config authoring issue rather than an attacker-triggerable "input-drives-behavior" chain. It is more likely to occur accidentally (a benign misconfiguration silently disabling enforcement) than to be intentionally weaponized by an unprivileged attacker who cannot otherwise write files into `.claude/`.

### Recommendation
- In `Rule.from_dict`, validate that each parsed `Condition` has non-empty `field` and `pattern`; reject (raise or skip with an explicit `sys.stderr` warning) rules containing malformed condition entries instead of allowing them to silently degrade to "never matches."
- In `Condition.from_dict`, raise a `ValueError` if `field` or `pattern` is missing/empty rather than defaulting to `''`.
- Add a load-time invariant check in `load_rule_file`: if `action == 'block'` and the resulting rule has zero effective conditions or any invalid condition, refuse to load the rule and print a clear warning, rather than allowing a look-alike no-op block rule.

### Proof of Concept
Unit test to add to `plugins/hookify` test suite:
```python
from hookify.core.config_loader import Rule

frontmatter = {
    "name": "block-dangerous-rm",
    "enabled": True,
    "event": "bash",
    "action": "block",
    "conditions": [
        {"operator": "regex_match", "pattern": "rm\\s+-rf"}  # missing 'field'
    ],
}
rule = Rule.from_dict(frontmatter, "blocked")
assert rule.conditions[0].field == ""  # invalid condition accepted silently

from hookify.core.rule_engine import RuleEngine
engine = RuleEngine()
input_data = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /"},
}
result = engine.evaluate_rules([rule], input_data)
assert result == {}  # expected: block, actual: rule silently never matches
```
This demonstrates that a `block` rule with a malformed `conditions` entry is accepted without error at load time and never fires at evaluation time, evading the intended enforcement — confirming the finding but showing it is a config-robustness defect requiring pre-existing control over the rule file's content rather than a directly attacker-reachable privilege escalation from ordinary repo content alone. class Condition:
    """A single condition for matching."""
    field: str  # "command", "new_text", "old_text", "file_path", etc.
    operator: str  # "regex_match", "contains", "equals", etc.
    pattern: str  # Pattern to match

    @classmethod
    def from_dict(cls, data: Dict[str, Any]) -> 'Condition':
        """Create Condition from dict."""
        return cls(
            field=data.get('field', ''),
            operator=data.get('operator', 'regex_match'),
            pattern=data.get('pattern', '')
        )


@dataclass
class Rule:
    """A hookify rule."""
    name: str
    enabled: bool
    event: str  # "bash", "file", "stop", "all", etc.
    pattern: Optional[str] = None  # Simple pattern (legacy)
    conditions: List[Condition] = field(default_factory=list)
    action: str = "warn"  # "warn" or "block" (future)
    tool_matcher: Optional[str] = None  # Override tool matching
    message: str = ""  # Message body from markdown

    @classmethod
    def from_dict(cls, frontmatter: Dict[str, Any], message: str) -> 'Rule':
        """Create Rule from frontmatter dict and message body."""
        # Handle both simple pattern and complex conditions
        conditions = []

        # New style: explicit conditions list
        if 'conditions' in frontmatter:
            cond_list = frontmatter['conditions']
            if isinstance(cond_list, list):
                conditions = [Condition.from_dict(c) for c in cond_list]

        # Legacy style: simple pattern field
        simple_pattern = frontmatter.get('pattern')
        if simple_pattern and not conditions:
            # Convert simple pattern to condition
            # Infer field from event
            event = frontmatter.get('event', 'all')
            if event == 'bash':
                field = 'command'
            elif event == 'file':
                field = 'new_text'
            else:
                field = 'content'

            conditions = [Condition(
                field=field,
                operator='regex_match',
                pattern=simple_pattern
            )]

        return cls(
            name=frontmatter.get('name', 'unnamed'),
            enabled=frontmatter.get('enabled', True),
            event=frontmatter.get('event', 'all'),
            pattern=simple_pattern,
            conditions=conditions,
            action=frontmatter.get('action', 'warn'),
            tool_matcher=frontmatter.get('tool_matcher'),
            message=message.strip()
        )
