### Title
Automatic, unconfirmed remote-URL rewrite trusts unauthenticated GitHub API `clone_url` field, allowing silent redirection of a repository's push/fetch target - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically refreshes the "GitHub repository" metadata associated with a local clone and, if the API's reported `clone_url` no longer matches the current `origin` remote, **silently rewrites the local `.git/config` remote URL** to the value returned by the API — with no user confirmation and no validation that the new URL points to a trusted host. This mirrors the audited invariant break in `FathomProxyWalletOwner`: a value that is critical to correct operation (the "address" the client will subsequently talk to) is accepted and acted upon without a way to verify it is still the legitimate target, and the consumer (git push/fetch) has no independent guard against the swap.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts:4904-4907`, which runs automatically (e.g. on account refresh/sign-in-state change, see `refreshSelectedRepositoryAfterAccountChange`, `app-store.ts:4921-4933`) and calls `api.fetchRepository(owner, name)` against the account's configured endpoint: [1](#0-0) 

The result is passed straight into: [2](#0-1) 

The only checks performed before rewriting the remote are: (1) the *protocol* (http/https/ssh-scp form) hasn't changed, and (2) the user hasn't manually edited the remote away from the last-known `cloneURL`: [3](#0-2) 

Critically, there is **no check that the new `clone_url`'s hostname matches the account's endpoint hostname** (the same hostname validation that `findAccountForRemoteURL` and `matchGitHubRepository` perform elsewhere, e.g. `app/src/lib/repository-matching.ts:34-42`, is absent here). Once the three conditions above are satisfied, `gitStore.setRemoteURL` is called unconditionally, which shells out to git and rewrites `origin` on disk: [4](#0-3) 

The broken invariant: the local git remote — the address that the user's `git push`/`git fetch`/`git pull` will use — is treated as a mutable cache of whatever `clone_url` the configured API endpoint last returned, and the app auto-heals it to match, without re-validating that the returned host is the same trusted host the repository is actually associated with. This is the same class of bug as the reported issue: an address that governs where the client talks to is silently overwritten by data from an untrusted/potentially-compromised source, with no migration/consent mechanism, and downstream consumers (git operations) have no way to detect the corruption.

### Impact Explanation
If the account's endpoint (particularly relevant for GitHub Enterprise Server accounts, or any environment where the API traffic path can be influenced — a compromised/malicious proxy sitting in front of the configured endpoint, or a compromised GHES instance) returns an attacker-chosen `clone_url`, Desktop will rewrite the user's `origin` remote to that attacker-controlled host without any dialog, warning, or opt-in. Because `urlMatchesRemote`'s owner/name/hostname parsing is only used to *decide whether to rewrite*, not to constrain *what* it can be rewritten to, the new value can be any URL with a matching protocol scheme. Subsequent `git push`/`git fetch` performed by the user (via Desktop or the CLI, since the change is persisted to `.git/config`) will silently talk to the attacker's server — this is exactly the "silent corruption of what the user commits or pushes" impact called out as in-scope.

### Likelihood Explanation
This runs automatically in the background any time the app refreshes GitHub-repository association (account refresh, sign-in state change, app focus, etc.) — it requires no explicit user action beyond having the repository open with Desktop signed in to the affected account. The attacker precondition is control over the API/proxy response path for the configured endpoint, which is explicitly listed as an acceptable attacker capability in this task's valid-impact criteria ("a git remote/proxy response"). No local/physical access, admin rights, or pre-existing host compromise of the victim's machine is required.

### Recommendation
Before calling `gitStore.setRemoteURL`, validate that the new `clone_url`'s hostname matches the expected trusted host for the associated `GitHubRepository`/account endpoint (the same hostname check already used in `matchGitHubRepository`/`findAccountForRemoteURL`). If the hostname differs, do not silently rewrite the remote — instead surface an explicit, user-confirmed prompt (a "migration" step, analogous to the audit's recommendation), since a hostname change on a `clone_url` for the same owner/repo is not an expected legitimate rename scenario.

### Proof of Concept
1. User signs into a GitHub Enterprise Server account in Desktop and has a repository cloned with `origin` pointing at `https://ghes.corp.example/owner/repo.git`, matching `gitHubRepository.cloneURL`.
2. An attacker who can influence responses on the path to the configured GHES API endpoint (compromised/malicious proxy, or compromised GHES instance) returns, for `GET repos/owner/repo`, a body with `"clone_url": "https://ghes-evil.example/owner/repo.git"` (same owner/name/protocol, different host).
3. Desktop triggers `repositoryWithRefreshedGitHubRepository` (e.g. via `refreshSelectedRepositoryAfterAccountChange`, on focus/account refresh) → `api.fetchRepository` returns the poisoned object → `updateRemoteUrl` computes `protocolsMatch = true`, `remoteUrlUnchanged = true`, `urlsMatch = false`.
4. `gitStore.setRemoteURL('origin', 'https://ghes-evil.example/owner/repo.git')` is executed silently, rewriting `.git/config` with no prompt.
5. The next time the user pushes or fetches (via Desktop or `git` CLI), traffic and any credentials issued for that operation are sent to `ghes-evil.example` instead of the legitimate server.

Note: I was unable to fully verify, within available tool iterations, how Desktop's credential helper scopes which credentials are offered to a rewritten remote host (i.e., whether it would also hand out a token to the attacker host during this flow) — this would strengthen the impact (credential exfiltration) if confirmed, but the remote-URL corruption itself is independently verified from the cited code paths.

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
