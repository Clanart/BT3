## Title
Attacker-controlled `WWW-Authenticate` realm header lets a malicious remote force GitHub Desktop into an "Enterprise sign-in" flow scoped to the attacker's endpoint, enabling credential/token exfiltration - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

## Summary
`getEndpointKind()` in `trampoline-credential-helper.ts` is supposed to decide, for a Git credential request, whether the remote is GitHub.com, GitHub Enterprise, or a generic (non-GitHub) host, so it knows whether it's safe to hand over the user's stored GitHub token or whether it should treat the host as untrusted/generic. Just like `Seer.sol` computing two prices (a safe Chainlink value and a manipulable Uniswap TWAP value) and blindly using the manipulable one, this function has both an authoritative check (`isGitHubHost`, an actual server round-trip) and a cheap heuristic derived directly from attacker-controlled data (the `WWW-Authenticate` header text that Git forwards from the remote's HTTP response). The heuristic is trusted first and short-circuits the authoritative check.

## Finding Description
`getEndpointKind` classifies a credential endpoint using several checks, in order: [1](#0-0) 

For URLs that aren't `github.com`/`.ghe.com`, it falls back to inspecting `wwwauth[...]` entries in the credential map — data that git populates directly from the HTTP `WWW-Authenticate` response header sent by the remote server: [2](#0-1) 

If the header contains `realm="GitHub"`, the function immediately returns `'enterprise'` — without ever calling the actual verification function `isGitHubHost(endpoint)`, which performs a real network check and is only reached later as a fallback: [3](#0-2) 

This is the same broken invariant as the `Seer.sol` bug: two signals are available (a strong, verifiable one — `isGitHubHost` — and a weak, attacker-influenceable one — the `WWW-Authenticate` header), and the code uses the weak signal and skips the strong one whenever the weak one is favorable to the classification. Any HTTP(S) git remote or a man-in-the-middle/corporate proxy sitting in front of a git remote can freely set `WWW-Authenticate: Basic realm="GitHub"` on a 401 response for any hostname, since this header is not authenticated in any way and is not tied to TLS certificate identity or a genuine GitHub-only response signature.

Once `getEndpointKind` returns `'enterprise'` for an attacker's host, `getCredential` treats this as a "GitHub-like" endpoint: [4](#0-3) 

If the user has no account already registered for that exact endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, passing the **attacker's own endpoint URL** as the sign-in target: [5](#0-4) 

Since the attacker's hostname is not `github.com`, this routes the user into the Enterprise sign-in flow (`beginEnterpriseSignIn` + `setSignInEndpoint(origin)`), where `origin` is derived from the attacker's malicious remote URL. This causes GitHub Desktop's real sign-in UI (which the user trusts) to initiate an OAuth/basic-auth handshake **against the attacker-controlled host** instead of a genuine GitHub Enterprise Server, because Desktop believed (from the spoofed header) that the host was a GitHub instance.

## Impact Explanation
This directly matches the "unauthorized OAuth ... or credential/token exfiltration" category from an attacker-controlled git remote/proxy response. A user cloning or fetching from a malicious/compromised HTTP git remote (or one sitting behind a hostile corporate/public proxy) can be silently redirected into signing in to what they believe is a legitimate GitHub Enterprise instance, but is actually the attacker's endpoint. Depending on the enterprise sign-in flow's fallback (basic auth challenge / device flow relay), this can result in the user's GitHub Enterprise username/password or session token being sent to the attacker's server, i.e., credential exfiltration triggered purely by fetching from a hostile remote — no prior compromise, admin rights, or unusual user action required beyond a normal `fetch`/`clone`/`push`.

## Likelihood Explanation
Medium-to-High: the `WWW-Authenticate` header is fully attacker-controlled (any HTTP server the user's git operations touch can set it), the check happens unconditionally for any non-dotcom/non-ghe.com endpoint before the authoritative `isGitHubHost` verification is attempted, and no special network position beyond controlling/proxying the git remote's HTTP response is required. The realm string `"GitHub"` is trivial to guess since it is the exact literal checked in the code.

## Recommendation
Do not let the unauthenticated `WWW-Authenticate` realm header short-circuit classification. Always perform the authoritative `isGitHubHost(endpoint)` check (or otherwise cryptographically/API-verify the host) before trusting a host as "enterprise", or at minimum require both signals to agree in the same way the report recommends returning/using both price sources instead of blindly trusting the more "convenient" one. If the header-based heuristic is kept as a performance optimization, treat a positive match only as a hint to prioritize calling `isGitHubHost`, not as a substitute for it, and never invoke `promptForGitHubSignIn`/`setSignInEndpoint` against an endpoint that hasn't been verified.

## Proof of Concept
1. Attacker sets up an HTTP git remote (or a MITM/corporate proxy in front of one) at `https://evil.example.com/attacker/repo.git`.
2. Victim adds this as a remote (e.g., via a shared link or a forked/renamed repository) and runs `git fetch`/`git push` from within GitHub Desktop.
3. Git performs the HTTP request; the attacker's server responds `401 Unauthorized` with header `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this to Desktop's credential helper trampoline as a `wwwauth[...]` credential field.
5. `getEndpointKind` sees `realm="GitHub"` and returns `'enterprise'` for `evil.example.com`, skipping the real `isGitHubHost` verification (`app/src/lib/trampoline/trampoline-credential-helper.ts:158-165` vs the unreached fallback at `167-178`).
6. Since no account exists for `evil.example.com`, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com/...')`, which invokes `beginEnterpriseSignIn` and `setSignInEndpoint(origin)` with the attacker's origin (`app/src/lib/trampoline/trampoline-ui-helper.ts:80-99`).
7. The victim, seeing Desktop's native "Sign in to GitHub Enterprise" dialog, enters credentials or completes an OAuth/basic-auth flow that is actually directed at the attacker's server.

Note: I was not able to trace the exact downstream basic-auth/OAuth exchange implementation invoked by `beginEnterpriseSignIn`/`SignInStore` within the indexed content (only test files and high-level call sites were available), so the precise mechanism by which credentials reach the attacker (basic auth vs. OAuth device flow relay) could not be fully confirmed from the available index. A Devin session with full repository access would be needed to trace `SignInStore`/`AuthenticationForm` to confirm exactly what is transmitted to the attacker endpoint during this flow.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
