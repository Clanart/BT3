### Title
`CallDispatcher.dispatch` is a fully public, unauthenticated function that can drain any funds temporarily held on the shared dispatcher during `IntentGatewayV2` predispatch/postdispatch flows - (File: evm/src/utils/CallDispatcher.sol)

### Summary
This is the exact analog of the reported bug class: a critical, fund-moving function (`dispatch`) is `public`/`external` with **no access control whatsoever**, mirroring `RescuableV1.rescue` and `BlacklistableV1.blacklist`. `CallDispatcher` is the shared executor `IntentGatewayV2` uses for predispatch/postdispatch calldata, and it holds tokens/ETH transiently while a `placeOrder`/`fillOrder` transaction is in progress.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an arbitrary `Call[]` and executes each call with attacker-controlled `to`, `value`, and `data`, using the dispatcher's own balance for `value`: [1](#0-0) 

There is no `restrict`, `onlyHost`, `onlyOwner`, or any caller check — unlike every other privileged mutator in the codebase (`EvmHost.setFrozenState`, `EvmHost.setConsensusState`, `HostManager.setIsmpHost`, etc.) which use a `restrict(caller)` modifier: [2](#0-1) 

`IntentGatewayV2.placeOrder` uses this same dispatcher instance (`_params.dispatcher`) as a temporary custodian: it sends predispatch assets (ETH or ERC-20) to the dispatcher, then calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, and only afterward calls `dispatch` again to sweep tokens back to the gateway: [3](#0-2) 

Because `dispatch` is callable by anyone, the window between the first transfer of user assets to the dispatcher and the final sweep-back call is a race: any address can front-run/interleave a call to `CallDispatcher.dispatch` that sends the dispatcher's current native/ERC-20 balance to an attacker-controlled address before the legitimate sweep-back executes, since the dispatcher's `receive()` and its balance are globally accessible and the function is fully unauthenticated. Even outside of exact transaction ordering, the dispatcher is a **shared, single instance** referenced by `_params.dispatcher` across all orders/gateway calls (per `docs/content/developers/evm/intent-gateway/overview.mdx:85-99`), so any residual balance left on it (dust, an in-flight predispatch/postdispatch amount) is stealable by any external account calling `dispatch` directly with a `Call{to: attacker, value: dispatcher.balance, data: ""}` or an ERC-20 `transfer` to itself.

### Impact Explanation
This falls squarely within scope: "stealing or loss of funds" and "unauthorized transaction or execution." User-escrowed order inputs (ERC-20 and native ETH) transiently held by `CallDispatcher` during `placeOrder`'s predispatch phase can be redirected to an arbitrary address by anyone, with no relayer, prover, or admin compromise required — a bare EOA calling `CallDispatcher.dispatch()` directly is sufficient.

### Likelihood Explanation
Likelihood is high on any chain where `IntentGatewayV2` predispatch/postdispatch is used with a shared, non-ephemeral `CallDispatcher`: the attack requires only observing a pending `placeOrder`/`fillOrder` transaction (public mempool) and front-running with a plain call to the public `dispatch` function, or simply calling `dispatch` opportunistically whenever the dispatcher holds a non-zero balance between the transfer-in and sweep-back steps in the same transaction is not race-vulnerable, but any balance left standing between transactions (e.g., partial predispatch failures, leftover dust, or reentrant call ordering across multiple orders sharing one dispatcher) is exploitable at will since the function is public and stateless with respect to caller identity.

### Recommendation
Restrict `CallDispatcher.dispatch` to authorized callers only, mirroring the recommendation in the original report: make the raw execution logic internal, and expose it only through a function gated to the specific `IntentGatewayV2`/`HyperFungibleToken` instances that are supposed to use it (e.g., an `onlyAuthorizedCaller` modifier set at construction, or make each order/session use an ephemeral, single-use dispatcher/clone rather than one shared singleton). At minimum, add `restrict(msg.sender == authorizedCaller)` before executing any `Call[]`.

### Proof of Concept
1. Deploy/observe the shared `CallDispatcher` address referenced by `IntentGatewayV2._params.dispatcher`.
2. Monitor for any transaction that sends assets to this dispatcher address (native ETH via `dispatcher.call{value: amount}("")` or ERC-20 `transferFrom(msg.sender, dispatcher, amount)`) as part of `placeOrder`'s predispatch step: [4](#0-3) .
3. Before the gateway's own sweep-back `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` call executes (or in any block where the dispatcher holds residual balance), call `CallDispatcher.dispatch(abi.encode([Call({to: attacker, value: dispatcher.balance, data: ""})]))` directly as an unrelated EOA — this succeeds because `dispatch` has no caller restriction: [1](#0-0) .
4. The attacker receives the escrowed order-input funds instead of the `IntentGatewayV2` gateway, breaking the intended custody invariant that predispatch assets always land back in the gateway for escrow.

Note: I was unable to fully verify from the index whether each `IntentGatewayV2` deployment uses a freshly-deployed, single-use `CallDispatcher` per order (which would eliminate cross-order residue) versus one long-lived shared instance referenced by `_params.dispatcher` set via governance `setParams`/`UpdateParams`. The documentation and `Params.dispatcher` field strongly suggest a single persistent address is configured and reused across all orders, but confirming the exact deployment topology would require a full Devin session with access to the deployment scripts and `Params` initialization values.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
