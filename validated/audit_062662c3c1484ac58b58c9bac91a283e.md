Audit Report

## Title
Missing proof-length binding lets a malicious repair peer forge a `FecSetRoot` block-id-repair response by substituting an internal double-Merkle node for a leaf - (File: `core/src/repair/serve_repair.rs`)

## Summary
The `verify_response` match arm for `BlockIdRepairType::FecSetRoot` in `core/src/repair/serve_repair.rs` only checks that `fec_set_proof` is non-empty, unlike the sibling `ParentAndFecSetCount` arm which explicitly computes the expected proof length from `fec_set_count` via `merkle_tree::get_proof_size` and rejects any mismatch. Because the double-Merkle tree's "leaves" (FEC-set roots) are hashed into the tree using the exact same `join_nodes` construction and `MERKLE_HASH_PREFIX_NODE` prefix as internal nodes (no separate leaf-domain prefix is applied before `MerkleTree::try_new_with_len` ingests them), an internal node of the double-Merkle tree is byte-for-byte indistinguishable from a leaf. `get_merkle_root`'s fold loop has no notion of expected tree depth — it simply folds until the running index reaches 0 — so a proof one entry shorter than correct, with an internal node substituted in place of the true leaf, still verifies successfully.

## Finding Description
`join_nodes` in `ledger/src/shred/merkle_tree.rs` (lines 106-111) always uses `MERKLE_HASH_PREFIX_NODE` regardless of whether it is combining two leaves or two internal nodes. FEC-set roots are pushed into the double-Merkle tree verbatim (`Blockstore` computes `merkle_tree_leaves` from prior `join_nodes` outputs and feeds them straight into `MerkleTree::try_new_with_len` without any leaf-prefix rehash), so a leaf value and an internal node value share an identical hash format. `get_merkle_root` (lines 115-132) folds the proof entries against the claimed leaf node, tracking only the halved index, and accepts once `index == 0` — it never validates that the proof length matches the expected tree depth for the given leaf index. `verify_merkle_proof` (lines 136-152) simply delegates to `get_merkle_root` and compares the final hash to the expected root, again with no depth check.

In `core/src/repair/serve_repair.rs`, the `ParentAndFecSetCount` branch (lines 300-311) explicitly guards against this by deriving `proof_size` from `fec_set_count` via `get_proof_size` and rejecting a proof whose length doesn't match. The `FecSetRoot` branch (lines 327-353) omits this check entirely, only requiring `fec_set_proof` is non-empty before calling `verify_merkle_proof`. This allows an attacker to substitute an internal node `N = join(L_i, L_{i+1})` for the true leaf `L_i`, and supply a proof that is one entry shorter (omitting the sibling that `N` already encodes). The fold in `get_merkle_root` still reconstructs the real root and returns `Ok`, so `verify_response` returns `true` despite `fec_set_root` not being the true FEC-set root.

## Impact Explanation
This falls under the "false execution/rooting/acceptance" class in the repair path: a victim node that requests `BlockIdRepairType::FecSetRoot` from an untrusted repair-serving peer can be made to accept a forged `fec_set_root` value that is not the true Merkle root of the FEC set's shreds, backed only by public, real hashes the attacker can derive from the already-broadcast shreds for that slot. The victim then issues `ShredRepairType::ShredForBlockId` requests keyed on the poisoned root (per `block_id_repair_service.rs`), and every legitimate per-shred proof will subsequently fail against it, stalling/degrading that node's ability to repair the affected FEC set/slot. This is a non-RPC, low-cost remote degradation of the victim's repair progress, consistent with allowed impact categories for repair/shred code.

## Likelihood Explanation
The attack requires a single crafted repair-response packet from any peer selected to answer a `FecSetRoot` repair request under Agave's decentralized/untrusted repair-source model — no privileged access, no hash collision search, and no brute force: the substituted internal node is a real, publicly derivable value from already-broadcast shred data for the slot. The `debug_assert_eq!` on `fec_set_index` alignment provides no protection in release builds. This makes the exploit reliably and repeatably triggerable by any unprivileged network participant capable of responding to repair requests.

## Recommendation
In the `FecSetRoot` verification branch of `verify_response`, enforce a proof length matching the expected double-Merkle depth for the given leaf index — e.g., require the verifier to know (or have cached from a prior `ParentAndFecSetCount` exchange) the `fec_set_count` for the `block_id` in question, and reject any `fec_set_proof` whose length isn't exactly `get_proof_size(fec_set_count + 1) * SIZE_OF_MERKLE_PROOF_ENTRY`. Alternatively/additionally, hash FEC-set roots into the double-Merkle tree with a leaf-specific domain prefix distinct from `MERKLE_HASH_PREFIX_NODE` so that no internal node byte-string can ever validate as a leaf regardless of proof length.

## Proof of Concept
1. For a slot with `fec_set_count = 4`, the double-Merkle tree has leaves `L0..L3` (FEC-set roots) plus a trailing `PInfo` leaf; internal nodes are `N01 = join(L0, L1)`, `N23 = join(L2, L3)`, `M = join(N01, N23)`, `P' = join(PInfo, PInfo)`, `root = join(M, P')` — all publicly derivable from broadcast shreds.
2. Victim sends `BlockIdRepairType::FecSetRoot { fec_set_index: 0, block_id: root }`.
3. Malicious peer replies with `FecSetRoot { fec_set_root: N01, fec_set_proof: [N23, P'] }` (2 entries instead of the correct 3-entry proof `[L1, N23, P']`).
4. `verify_response` → `verify_merkle_proof(N01, 0, [N23, P'], root)` folds: `join(N01, N23) = M`, then `join(M, P') = root`; index reaches 0 → verification succeeds even though `N01` is not the real FEC-set-0 root.
5. The victim proceeds to issue `ShredForBlockId` repair requests using the poisoned `N01`, and legitimate per-shred proofs fail against it, stalling repair for that FEC set — reproducible as a Rust unit test asserting `serve_repair::BlockIdRepairType::FecSetRoot::verify_response` returns `true` for this crafted short proof. // Obtains parent's hash by joining two sibling nodes in merkle tree.
```rust
fn join_nodes<S: AsRef<[u8]>, T: AsRef<[u8]>>(node: S, other: T) -> Hash {
    let node = &node.as_ref()[..SIZE_OF_MERKLE_PROOF_ENTRY];
    let other = &other.as_ref()[..SIZE_OF_MERKLE_PROOF_ENTRY];
    hashv(&[MERKLE_HASH_PREFIX_NODE, node, other])
}

// Recovers root of the merkle tree from a leaf node
// at the given index and the respective proof.
pub fn get_merkle_root<'a, I>(index: usize, node: Hash, proof: I) -> Result<Hash, Error>
where
    I: IntoIterator<Item = &'a MerkleProofEntry>,
{
    let (index, root) = proof
        .into_iter()
        .fold((index, node), |(index, node), other| {
            let parent = if index % 2 == 0 {
                join_nodes(node, other)
            } else {
                join_nodes(other, node)
            };
            (index >> 1, parent)
        });
    (index == 0)
        .then_some(root)
        .ok_or(Error::InvalidMerkleProof)
}
```

```rust
pub fn verify_merkle_proof(
    node: Hash,
    index: usize,
    proof: &[u8],
    expected_root: Hash,
) -> Result<(), Error> {
    let proof = proof
        .chunks(SIZE_OF_MERKLE_PROOF_ENTRY)
        .map(<&MerkleProofEntry>::try_from)
        .map(|entry| entry.map_err(|_| Error::InvalidMerkleProof))
        .collect::<Result<Vec<_>, Error>>()?;
    let merkle_root = get_merkle_root(index, node, proof)?;

    (merkle_root == expected_root)
        .then_some(())
        .ok_or(Error::InvalidMerkleProof)
}
```
