### Title
CPI account/instruction data byte-cost rounds down to zero for small buffers, underpricing compute during Cross-Program Invocation - (File: program-runtime/src/cpi.rs)

### Summary
Several compute-cost calculations in the CPI (Cross-Program Invocation) path divide a buffer length by `cpi_bytes_per_unit` and charge the truncated result directly, with **no floor/minimum charge**. When the translated length is smaller than `cpi_bytes_per_unit`, integer division rounds the cost down to `0`, so that portion of the CPI's compute cost is never billed. This mirrors the reported `RubiconMarket.buy()` bug where `amount * feeBPS / 100_000` rounds down to `0` for small trade amounts, causing the fee to be silently skipped.

### Finding Description
In `program-runtime/src/cpi.rs`, the byte-based CPI translation costs are computed as a bare `checked_div` with no minimum:

- `CallerAccount::from_account_info` (account data length cost): `(data.len() as u64).checked_div(cpi_bytes_per_unit).unwrap_or(u64::MAX)` [1](#0-0) 
- `CallerAccount::from_sol_account_info` (account data length cost): `account_info.data_len.checked_div(cpi_bytes_per_unit).unwrap_or(u64::MAX)` [2](#0-1) 
- `translate_instruction_rust` (instruction data + account-meta cost): `(data.len() as u64).checked_div(cpi_bytes_per_unit)` and `(account_metas.len() * size_of::<AccountMeta>()).checked_div(cpi_bytes_per_unit)` [3](#0-2) 
- `translate_instruction_c` (same, C ABI variant) [4](#0-3) 
- `translate_account_infos` (account-info array cost): `(account_infos_bytes as u64).checked_div(cpi_bytes_per_unit).unwrap_or(u64::MAX)` [5](#0-4) 

In each case, whenever the byte length is less than `cpi_bytes_per_unit`, `checked_div` truncates to `0`, and `consume_checked(0)` charges nothing for that component.

This contrasts with the analogous cost helper in `syscalls/src/mem_ops.rs`, which explicitly guards against this rounding-to-zero behavior by taking the `max` with a base cost:
```
let cost = compute_cost.mem_op_base_cost.max(
    n.checked_div(compute_cost.cpi_bytes_per_unit).unwrap_or(u64::MAX),
);
``` [6](#0-5) 

The CPI-path costs in `cpi.rs` lack this floor, so the byte-length component of the cost can legitimately be zero, unlike memcpy/memset/memcmp/memmove, or `SyscallGetEpochStake`, which always include a `mem_op_base_cost`/`syscall_base_cost` floor alongside the divided cost [7](#0-6) .

### Impact Explanation
`cpi_common` (the entry point invoked by every `invoke`/`invoke_signed` syscall from a BPF program) does charge a flat `invoke_units` cost per CPI call [8](#0-7) , so this is not a "free CPI" bug — it's an under-billing of the byte-proportional components of CPI cost. An unprivileged, non-privileged BPF program can perform many CPI calls, each passing account data / instruction data / account-info arrays whose length is below `cpi_bytes_per_unit`, and for each such call the byte-length compute charge for that buffer is `0` instead of the intended fractional charge. Repeated across thousands of small CPIs, this results in the program consuming real host-side CPU work (translation/mapping) for a compute-unit price cheaper than intended, i.e. materially underpriced compute for the CPI translation work, one of the explicitly accepted impact classes.

### Likelihood Explanation
This is directly and trivially reachable by any unprivileged BPF program via `invoke`/`invoke_signed` — no special permissions, precompiles, or validator role required. Small account data (e.g., 0–31 bytes, depending on `cpi_bytes_per_unit`), small instruction data, or a small number of `AccountMeta`/`AccountInfo` entries per CPI call are extremely common in real on-chain programs and trivially triggerable by an attacker who intentionally issues many CPI calls with sub-threshold-sized buffers.

### Recommendation
Apply the same "floor" pattern used in `syscalls/src/mem_ops.rs` to all CPI byte-cost calculations in `program-runtime/src/cpi.rs`: instead of billing the raw `checked_div` result, take the `max()` of the divided cost and an appropriate minimum/base cost (or, at minimum, round the division up via `div_ceil` so that any non-zero length always yields a non-zero charge). This should be applied consistently to:
- `CallerAccount::from_account_info` / `from_sol_account_info` data-length cost,
- `translate_instruction_rust` / `translate_instruction_c` data + account-meta cost,
- `translate_account_infos` account-info-array cost.

### Proof of Concept
Conceptual trace (no PoC executed; based on static code reading):
1. A BPF program issues `invoke()` with an inner `Instruction` whose `data` is, e.g., 8 bytes, and a single `AccountInfo` with `data.len()` also below `cpi_bytes_per_unit`.
2. `translate_instruction_rust` computes `total_cu_translation_cost` from `data.len() / cpi_bytes_per_unit` and `account_metas.len() * size_of::<AccountMeta>() / cpi_bytes_per_unit` — both round to `0` for small enough `data`/`account_metas` [9](#0-8) .
3. `CallerAccount::from_account_info` further computes the account-data-length cost as `data.len() / cpi_bytes_per_unit`, which again rounds to `0` for small account data [1](#0-0) .
4. Only the flat `invoke_units` cost from `cpi_common` is charged; the byte-proportional components are billed as `0` instead of a fractional-but-positive amount, for every such CPI call.

Because I was unable to execute a live test harness in this session, the exact value of `cpi_bytes_per_unit` (and thus the exact byte-length threshold at which rounding-to-zero occurs) was not fully confirmed — this should be verified against `program-runtime/src/execution_budget.rs` / `compute-budget/src/compute_budget.rs` defaults before finalizing severity, but the structural rounding-to-zero bug itself is confirmed by direct code inspection.
