## Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo` allows attacker-crafted coin memos to crash Chia clients (`chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs a custody structure from an on-chain coin memo, and for `MofN` branches it recurses once per member with no bound on nesting depth. This mirrors the reported Tezos issue where a proxy-contract executor tracked call-stack depth but never enforced a limit before descending into another "transaction data" layer — here, `from_memo` tracks nothing at all and blindly recurses into `MofNHint.member_memos` for every member.

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses the CHIP-0043 custody memo format. When the parsed structure indicates further branching (`further_branching_prog != Program.to(None)`), it builds an `MofN` puzzle by recursively calling `PuzzleWithRestrictions.from_memo(memo)` for every member memo: [1](#0-0) 

There is no check on recursion depth, member count nesting, or overall memo size/shape before creating each new recursive "layer," analogous to `handler.execute_call` in the Tezos report noting call-stack depth but never enforcing it.

This function is reached from production coin-spend processing in the plotnft/pool-participant flow, where an untrusted `CREATE_COIN` memo blob attached to a singleton spend is parsed to reconstruct pool state: [2](#0-1) 

Because `memo_blob` originates from a `CoinSpend`'s `CREATE_COIN` condition — content fully controlled by whoever creates that coin (e.g., a malicious/adversarial plotnft peer, or any spend that a wallet subsequently has to interpret) — an attacker can construct a `MofNHint` whose `member_memos` list recursively nests many `PuzzleWithRestrictions` memos, driving Python's call stack to its recursion limit and raising an uncaught `RecursionError` inside `from_memo`. The test suite explicitly demonstrates recursive `MofN` reconstruction is a first-class supported (and expected) shape: [3](#0-2) 

Unlike the CLVM tree-hash and DataLayer code paths in this same codebase — which were deliberately made iterative or bounded specifically to avoid Python recursion-limit crashes on attacker/large input — [4](#0-3) [5](#0-4) 

`PuzzleWithRestrictions.from_memo` has no equivalent guard.

### Impact Explanation
An uncaught `RecursionError` raised while parsing a coin's memo during `PlotNFT.get_next_from_coin_spend` propagates up through pool/plotnft sync processing. This is a spend-triggered halt in transaction/state processing for any node or wallet attempting to interpret the malicious plotnft coin's history — a denial-of-service against pool-participant/plotnft clients rather than direct fund loss, but it can stall wallet sync or pool-state reconstruction for affected participants until the code is patched or the offending spend is otherwise avoided.

### Likelihood Explanation
Likelihood is limited by the fact that the affected code path is confined to the plotnft/pool driver's memo reconstruction, and any single coin spend can only carry one `CREATE_COIN` memo — the attacker needs to build a naturally-shaped MofN memo tree deep enough to exhaust Python's default recursion limit (~1000 frames), which is plausible given CLVM programs and memos have no comparable depth ceiling and the recursive parsing multiplies stack frames roughly per MofN nesting level (`from_memo` → `MofNHint.from_program` → per-member `from_memo`).

### Recommendation
Add an explicit depth counter/limit parameter to `PuzzleWithRestrictions.from_memo()` (and its recursive `MofN` member reconstruction) analogous to the fix referenced in the report — reject memos whose nesting exceeds a sane bound before recursing further, and/or convert the recursive descent into an iterative stack-based traversal (as already done for `sha256_treehash`) so a crafted deep memo cannot exhaust the interpreter's call stack.

### Proof of Concept
Construct a `CREATE_COIN` memo blob whose payload is a `PuzzleWithRestrictions.memo()` encoding an `MofN` puzzle where each level's single member is itself another deeply-nested `MofN`-wrapped `PuzzleWithRestrictions`, nested to a depth exceeding Python's recursion limit (e.g. 2000+ levels), following the exact shape exercised by `test_back_and_forth_hint_parsing`'s nested `MofN(... members=[PuzzleWithRestrictions(..., puzzle=MofN(...))])` construction. Feed the resulting memo through `PlotNFTPuzzle.get_next_from_coin_spend()` (or any code path that calls `PuzzleWithRestrictions.from_memo` on attacker-supplied memo data); observe an uncaught `RecursionError` rather than a graceful `GetNextPlotNFTError`.
