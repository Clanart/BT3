### Title
`Backend.GetBlockContext` swallows the `GetVMBlockContext` error and returns a zero-value `vm.BlockContext`, corrupting public `debug_traceBlock*` tracing results instead of failing - ([File: evmrpc/simulate.go])

### Summary
`x/evm/keeper.Keeper.GetVMBlockContext` (and its Giga-executor counterpart) can return a non-nil `error` (e.g. from `GetFeeCollectorAddress` or `ctx.BlockHeader().Time.MarshalBinary()`) together with a `nil *vm.BlockContext`. Every other caller of `GetVMBlockContext` in the codebase propagates that error to its own caller. `Backend.GetBlockContext`, used by the parallel and sequential `debug_traceBlock*` RPC paths, instead discards the error and returns a zero-value `vm.BlockContext{}` with a `nil` error, exactly mirroring the kernel bug class of "ignore the failure signal from a state getter and keep using its (invalid) result."

### Finding Description
`GetVMBlockContext` returns `(*vm.BlockContext, error)` and is documented (by every other call site) as fallible: [1](#0-0) 

Every legitimate caller checks the error and bails out, e.g.: [2](#0-1) [3](#0-2) [4](#0-3) 

However, `Backend.GetBlockContext`, which is the block-context supplier for the public `debug_traceBlock*` JSON-RPC surface, does the opposite: it checks the error only to *discard* it and return a zero-value struct with a `nil` error, telling every downstream caller that block-context construction succeeded: [5](#0-4) 

This function is invoked, per transaction, from both the parallel and sequential debug trace paths without any additional validation of the returned context: [6](#0-5) 

Because callers treat `err == nil` as "the context is valid," the zero-value `vm.BlockContext{}` — with `GetHash == nil`, `CanTransfer == nil`, `Transfer == nil`, `GasLimit == nil` (all function fields nil) — flows straight into `vm.NewEVM(blockCtx, ...)` and is used to execute the traced/replayed transaction. Any EVM opcode that invokes these nil function fields (`BLOCKHASH` calling `BlockContext.GetHash`, a value transfer calling `BlockContext.Transfer`, or gas-limit lookups) will nil-pointer-dereference and panic inside the go-ethereum EVM interpreter, mirroring the kernel's "unchecked getter result dereferenced" defect class.

### Impact Explanation
`debug_traceBlock`, `debug_traceBlockByNumber`, and `debug_traceBlockByHash` are default-enabled JSON-RPC methods reachable by any public RPC client on a default-configuration Sei full/archive node. `GetVMBlockContext` fails whenever `GetFeeCollectorAddress` or `ctx.BlockHeader().Time.MarshalBinary()` errors for the historical block/state being traced (e.g. gap in fee-collector account state at an old height, or store read failures during a non-live/pruned or racy state lookup). When that happens here, instead of the RPC call returning a clean error, the corrupted zero-value block context is handed to the EVM and executing any transaction that touches `BLOCKHASH`, native transfers, or block gas-limit logic will crash the RPC-serving goroutine with a nil-pointer dereference — a crash of a default-configuration RPC node, matching the required-impact bar (rather than merely returning wrong data).

### Likelihood Explanation
Reaching this path only requires calling `debug_traceBlockByNumber`/`debug_traceBlockByHash` (or the parallel variant) against a block whose underlying `GetVMBlockContext` computation fails — no privileged access, malicious validator, or consensus-level condition is needed, only a public RPC request against a block/height where the fee-collector lookup or header-time marshal produces an error. Since `debug_trace*` endpoints are commonly enabled on public/archive nodes and this exact function is on the hot path for every traced tx, the trigger condition is plausible whenever the underlying keeper call legitimately errors (which several other call sites in the same file explicitly guard against, confirming the failure mode is expected/handled elsewhere).

### Recommendation
In `Backend.GetBlockContext` (`evmrpc/simulate.go:943-949`), propagate the error instead of discarding it: return `vm.BlockContext{}, err` when `GetVMBlockContext` fails, matching every other call site in the same file (e.g. `StateAtTransaction`). Add a regression test asserting that a `GetVMBlockContext` failure surfaces as an RPC error from `debug_traceBlock*` rather than a zero-value context being used to build the EVM.

### Proof of Concept
1. Configure or trigger a state/height where `k.GetFeeCollectorAddress(ctx)` or `ctx.BlockHeader().Time.MarshalBinary()` returns a non-nil error for the block being traced (both are reachable failure paths already handled defensively elsewhere in `x/evm/keeper/keeper.go`).
2. Send `debug_traceBlockByNumber` (or `debug_traceBlock`) for that block via the public JSON-RPC endpoint.
3. `Backend.GetBlockContext` swallows the error and returns `vm.BlockContext{}, nil`.
4. `profiledTraceBlockParallel`/`profiledTraceBlockSequential` proceed to build `vm.NewEVM(blockCtx, ...)` with the zero-value context and execute the block's transactions.
5. Any transaction using `BLOCKHASH`, a native value transfer, or gas-limit-dependent opcode dereferences the nil `GetHash`/`Transfer`/`GasLimit` function fields inside `vm.BlockContext`, panicking the RPC-serving goroutine — a crash of the default-configuration RPC node.
