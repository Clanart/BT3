### Title
`ThresholdKeys::read` accepts arbitrary `Interpolation::Constant` coefficients, letting attacker-supplied key bytes silently redefine the group key and interpolation - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary

The bug class in the external report is "a public entry point accepts caller-supplied parameters that are supposed to match a derivable, canonical value, but nothing checks them, so the operation executes against arbitrary values." In Serai, the analogous surface is `ThresholdKeys::read` / `ThresholdKeys::new` in `crypto/dkg/src/lib.rs`. `Interpolation::Constant(c)` coefficients are only legitimate when they equal the MuSig binding factors deterministically derived from the key set via `binding_factor::<C>(transcript, i)` in `crypto/dkg/musig/src/lib.rs`. The deserializer reads `n` unchecked field elements straight from untrusted bytes and `ThresholdKeys::new` verifies only that `t == n`, never that the constants match the canonical derivation. The result is a `ThresholdKeys` whose `group_key()` — and every subsequent `view()`/`sign()` share weight — is computed under an attacker-chosen linear combination.

### Finding Description

`ThresholdKeys::read` deserializes the interpolation variant tag from the stream and, on `0`, reads `n` raw scalars via `C::read_F(reader)` with no semantic validation [1](#0-0) . `ThresholdKeys::new` then computes `group_key` as the interpolated sum of the first `t` verification shares using whatever coefficients were supplied [2](#0-1) , and for `Constant` only enforces `params.t() == params.n()` [3](#0-2) .

The legitimate source of `Constant` coefficients is the MuSig DKG, where each coefficient is `hash_to_F(b"dkg-musig", context || n || keys || i)` — a value fully determined by the public key set [4](#0-3) . Nothing on the read path re-derives or compares against these binding factors. Similarly, `view()` applies the same unvalidated coefficients as multiplicative weights to both the secret share and the verification shares [5](#0-4) , and FROST signing then consumes this view [6](#0-5) .

This mirrors the Lambo report exactly: just as `rebalance(directionMask, amountIn, amountOut)` executes with arbitrary amounts rather than the values `previewRebalance()` would have produced, `ThresholdKeys` operations execute with arbitrary interpolation coefficients rather than the binding factors the key set commits to.

### Impact Explanation

An unprivileged party who can supply serialized `ThresholdKeys` bytes (an in-scope untrusted-bytes sink) can craft `Constant` coefficients so that `group_key()` evaluates to an arbitrary point in the span of the provided verification shares. Consequences:

- The node reports/derives a group public key that does not correspond to any consistent secret sharing. Any funds or protocol state bound to that `group_key()` are unredeemable — "funds reported received that are not spendable."
- Because `view()` scales `secret_share` and `verification_shares` by the same bogus factors and the offset is added to `included[0]` [7](#0-6) , every FROST signing session under these keys signs for a group key unrelated to the real MuSig aggregate, and per-share blame verification (`verify_share` / `BatchVerifier` in `complete()`) is performed against verification shares weighted by attacker-chosen constants [8](#0-7)  — shares can simultaneously verify and sum to a signature for the wrong key, or honest shares can be blamed.

### Likelihood Explanation

Reachability requires only that an integration deserialize `ThresholdKeys` from bytes influenced by an external party (backup/restore, peer-provided key material, recovery flows). No malicious validator, collusion, or key leakage is needed — the attacker supplies only public-input bytes. The misweighted coefficients produce deterministic, attacker-selected group keys, analogous to the PoC where arbitrary `amountIn/amountOut` deterministically unbalance the pool. Severity is bounded by whether the deployment ever loads keys from untrusted sources; where it does, the impact is Medium–High.

### Recommendation

On the `Constant` path, validate the coefficients instead of trusting them:

- Have `ThresholdKeys::new` (or `read`, when a MuSig context is available) recompute the binding factors via `binding_factor::<C>(binding_factor_transcript::<C>(context, n, verification_share_keys), i)` and reject mismatches — the direct analog of checking `directionMask ∈ {0, 1<<255}` and `amountIn/amountOut == previewRebalance()`.
- Alternatively, serialize only the interpolation *type* tag plus the MuSig `context`, and derive the coefficient vector locally, removing attacker control over the weights entirely.

### Proof of Concept

Conceptual PoC (Rust, against `crypto/dkg`):

```rust
// Build legitimate-looking MuSig-style keys with n = t
let n = 3u16;
let shares: Vec<F> = (0..n).map(|_| F::random(rng)).collect();
let vshares: HashMap<Participant, G> = (1..=n)
    .map(|i| (Participant::new(i).unwrap(), G::generator() * shares[i - 1]))
    .collect();

// Attacker crafts serialized bytes: interpolation tag 0 + n arbitrary scalars.
// Instead of the real binding factors b_i = H(context||n||keys||i), submit
// e.g. c = [0, 1, 0], isolating verification share 2.
let evil_coeffs = vec![F::ZERO, F::ONE, F::ZERO];
// ... write t=n=3, i=1, tag=0, evil_coeffs, secret_share, vshares ...

let keys = ThresholdKeys::<C>::read(&mut evil_bytes).unwrap(); // succeeds: only t==n is checked
// keys.group_key() == vshares[2] * 1  (arbitrary attacker-selected point),
// NOT musig_key(context, keys) — deposits to this key are unspendable
// since no party's secret_share interpolates to it under the real binding factors.
```

The check that should exist, at `crypto/dkg/src/lib.rs:367-374`, validates nothing beyond `t == n`, while the deserializer at `crypto/dkg/src/lib.rs:604-616` accepts the coefficients verbatim — matching the "no check that parameters are legit" root cause in the report.
