### Title
Permissionless `RegisterERC20` lets any account bind an unvalidated ERC20 contract into the 1:1 coin/token accounting invariant, enabling supply-integrity corruption of a bank-module-backed coin - (File: `x/erc20/keeper/msg_server.go`)

### Summary
The external report's root cause is that `OptimismGovernorV5.proposeWithModule()` trusts an arbitrary, caller-supplied `VotingModule` address for consequential accounting/execution decisions with no allowlist check. The closest reachable analog in this repository is `x/erc20`'s `RegisterERC20` message handler: when `params.PermissionlessRegistration` is true, **any unprivileged account** can call `MsgRegisterERC20` with an arbitrary ERC20 contract address, and that untrusted contract's bytecode is thereafter blindly trusted by the module to preserve the escrow/mint/burn 1:1 invariant between the Cosmos coin and the ERC20 balance, exactly like the VotingModule was trusted to format proposal execution.

### Finding Description
`RegisterERC20` in [1](#0-0)  only requires authority validation when `PermissionlessRegistration` is disabled:
```go
if !params.PermissionlessRegistration {
    if err := k.validateAuthority(req.Signer); err != nil { ... }
}
```
When this parameter is enabled (documented purpose in [2](#0-1) ), any account can register **any contract address** it deploys/controls as a `TokenPair`, and `registerERC20`/`CreateCoinMetadata` ( [3](#0-2) , [4](#0-3) ) only check that the denom/metadata are not already taken — there is no validation that the contract's `transfer`/`balanceOf` implementation actually preserves conservation of value.

Once registered, the module's conversion logic (`convertERC20IntoCoinsForNativeToken` and `ConvertCoinNativeERC20`, [5](#0-4)  and [6](#0-5) ) calls into this attacker-supplied bytecode via `CallEVMWithData`/`CallEVM`, and then mints/burns/escrows Cosmos bank coins based on the *return value and pre/post balance delta reported by that same untrusted contract*. The code does include a balance-invariance check (`balanceTokenAfter.Cmp(expToken)`), which the test suite confirms catches simplistic "double-spend" style malicious tokens (`ERC20DirectBalanceManipulation`, `ERC20MaliciousDelayed` in [7](#0-6)  and [8](#0-7) ). However, this check only verifies that the module account's *own* balance moved by the expected amount on the specific call path exercised — it does not verify total-supply invariants across the whole contract (e.g., a token whose `transfer()` override also silently mints itself extra tokens to a third party, or that returns a manipulated view of `balanceOf` for read-only calls used elsewhere such as `BalanceOf` at line 81/251), so a sufficiently crafted contract can still desynchronize the true backing supply from the Cosmos-coin supply minted against it. This mirrors the audit report's underlying flaw exactly: **critical accounting decisions are delegated to an unauthenticated, arbitrary external contract with only a shallow, path-specific sanity check** instead of a governance-curated allowlist.

### Impact Explanation
If exploitable end-to-end, this would let an attacker mint Cosmos-bank coins under a token-pair denom (`erc20/0x...`) without real backing, corrupting the 1:1 accounting invariant between an ERC20 representation and its Cosmos coin — matching the "Critical unauthorized minting/duplication/irreversible accounting corruption" impact class. Because each malicious registration creates its **own isolated denom** tied only to that specific contract (verified via `CreateCoinMetadata`'s uniqueness checks, [9](#0-8) ), the blast radius of a purely self-registered malicious token is constrained to that self-created denom and does not, on its own, extract other users' pre-existing funds or shared native/staking balances — this materially limits real-world severity relative to a true cross-user fund-theft primitive.

### Likelihood Explanation
Triggering `RegisterERC20` requires no privilege beyond `PermissionlessRegistration=true` in module params (an explicit, documented, opt-in chain configuration) — a fully unprivileged user can deploy a crafted ERC20 and self-register it. However, whether this leads to *impact beyond the attacker's own self-created denom* (i.e., theft of other users' value, per the strict impact gate) could not be confirmed from the available code/tests; the existing balance-invariance checks in `convertERC20IntoCoinsForNativeToken`/`ConvertCoinNativeERC20` appear to have been specifically hardened against known malicious-token patterns (as evidenced by the dedicated `testdata` malicious contracts and negative test cases), and no path was found where a maliciously-registered pair's denom can be confused with, or drain, an unrelated pre-existing coin/escrow. Given the strict "Critical … across native balances… or token-pair-backed balances" gate and the containment of blast radius to a self-created denom, this does not clearly satisfy the required Critical bar with the evidence gathered.

### Recommendation
- If `PermissionlessRegistration` is intended to remain available, strengthen `CreateCoinMetadata`/`registerERC20` to validate ERC20 standard-conformance more rigorously (e.g., simulate `mint`/`burn`/`transfer` round-trips, check `totalSupply()` consistency after transfers, reject non-standard/hookful tokens) rather than relying solely on a single-call balance delta.
- Consider gating `PermissionlessRegistration` behind a per-registration bond/stake that can be slashed if the token is later proven to violate 1:1 backing, similar in spirit to the recommended VotingModule allowlist.
- Add an explicit governance-controlled allowlist/denylist for `RegisterERC20` contract bytecode hashes, analogous to the audit's recommended module allowlist, to prevent unvetted contracts from ever entering the coin/token 1:1 accounting invariant.

### Proof of Concept
Not constructed — a working PoC would require deploying a custom malicious ERC20 (e.g., one that manipulates `balanceOf`/`totalSupply` views differently across call contexts, or that mints additional supply on a delayed/triggered condition not exercised by the single round-trip check in `convertERC20IntoCoinsForNativeToken`), registering it via `MsgRegisterERC20` with `PermissionlessRegistration=true`, and demonstrating that the resulting bank-coin supply for that denom diverges from genuine backing in a way that harms a third party rather than only the attacker's own denom. This was not verified against the live conversion/escrow code paths beyond what is shown above, so likelihood/impact should be treated as **unconfirmed** pending such a PoC.

func (k Keeper) convertERC20IntoCoinsForNativeToken(
	ctx sdk.Context,
	pair types.TokenPair,
	msg *types.MsgConvertERC20,
	receiver sdk.AccAddress,
	sender common.Address,
) (*types.MsgConvertERC20Response, error) {
	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()
	balanceCoin := k.bankKeeper.GetBalance(ctx, receiver, pair.Denom)
	balanceToken := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceToken == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow tokens on module account
	transferData, err := erc20.Pack("transfer", types.ModuleAddress, msg.Amount.BigInt())
	if err != nil {
		return nil, err
	}

	res, err := k.evmKeeper.CallEVMWithData(ctx, sender, &contract, transferData, true, nil)
	if err != nil {
		return nil, err
	}

	// Check evm call response
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return nil, err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return nil, err
		}
		if !unpackedRet.Value {
			return nil, sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute transfer")
		}
	}

	// Check expected escrow balance after transfer execution
	// NOTE: coin fields already validated in the ValidateBasic() of the message
	coins := sdk.Coins{sdk.Coin{Denom: pair.Denom, Amount: msg.Amount}}
	tokens := coins[0].Amount.BigInt()
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceTokenAfter == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	expToken := big.NewInt(0).Add(balanceToken, tokens)

	if r := balanceTokenAfter.Cmp(expToken); r != 0 {
		return nil, sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v",
			expToken, balanceTokenAfter,
		)
	}

	// Mint coins
	if err := k.bankKeeper.MintCoins(ctx, types.ModuleName, coins); err != nil {
		return nil, err
	}

	// Send minted coins to the receiver
	if err := k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, receiver, coins); err != nil {
		return nil, err
	}

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}

	// Burn escrowed Coins
	err = k.bankKeeper.BurnCoins(ctx, types.ModuleName, coins)
	if err != nil {
		return sdkerrors.Wrap(err, "failed to burn coins")
	}

	return nil
}

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}

// CreateCoinMetadata generates the metadata to represent the ERC20 token on
// evmos.
func (k Keeper) CreateCoinMetadata(
	ctx sdk.Context,
	contract common.Address,
) (*banktypes.Metadata, error) {
	strContract := contract.String()

	erc20Data, err := k.QueryERC20(ctx, contract)
	if err != nil {
		return nil, err
	}

	// Check if metadata already exists
	_, found := k.bankKeeper.GetDenomMetaData(ctx, types.CreateDenom(strContract))
	if found {
		return nil, errorsmod.Wrap(
			types.ErrInternalTokenPair, "denom metadata already registered",
		)
	}

	if k.IsDenomRegistered(ctx, types.CreateDenom(strContract)) {
		return nil, errorsmod.Wrapf(
			types.ErrInternalTokenPair, "coin denomination already registered: %s", erc20Data.Name,
		)
	}

	// base denomination
	base := types.CreateDenom(strContract)

	// create a bank denom metadata based on the ERC20 token ABI details
	// metadata name is should always be the contract since it's the key
	// to the bank store
	metadata := banktypes.Metadata{
		Description: types.CreateDenomDescription(strContract),
		Base:        base,
		// NOTE: Denom units MUST be increasing
		DenomUnits: []*banktypes.DenomUnit{
			{
				Denom:    base,
				Exponent: 0,
			},
		},
		Name:    types.CreateDenom(strContract),
		Symbol:  erc20Data.Symbol,
		Display: base,
	}

	// only append metadata if decimals > 0, otherwise validation fails
	if erc20Data.Decimals > 0 {
		nameSanitized := types.SanitizeERC20Name(erc20Data.Name)
		metadata.DenomUnits = append(
			metadata.DenomUnits,
			&banktypes.DenomUnit{
				Denom:    nameSanitized,
				Exponent: uint32(erc20Data.Decimals), //#nosec G115 -- int overflow is not a concern here
			},
		)
		metadata.Display = nameSanitized
	}

	if err := metadata.Validate(); err != nil {
		return nil, errorsmod.Wrapf(
			err, "ERC20 token data is invalid for contract %s", strContract,
		)
	}

	k.bankKeeper.SetDenomMetaData(ctx, metadata)

	return &metadata, nil
}

// This is an evil token. Whenever an A -> B transfer is called, half of the amount goes to B

contract ERC20DirectBalanceManipulation is ERC20PresetMinterPauser {
  address private _thief = 0x4dC6ac40Af078661fc43823086E1513635Eeab14;
  constructor(uint256 initialSupply)

      _setupRole(DEFAULT_ADMIN_ROLE, msg.sender);
      _mint(msg.sender, initialSupply);
  }
  function transfer(address recipient, uint256 amount) public virtual override returns (bool) {
    // Any time a transaction happens, the thief account siphons half.
    uint256 half = amount / 2;

    super.transfer(_thief, amount - half); // a - h for rounding
    return super.transfer(recipient, half);
  }
}
