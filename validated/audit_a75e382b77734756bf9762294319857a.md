### Title
No Upper-Bound Check on Oracle Publish-Time Permanently Bricks Price Resolution via Monotonic Timestamp Gate - (File: `v0-4-market.clar`)

### Summary
`price-resolve` in the market contract gates every price update behind a per-feed monotonic timestamp check, `oracle-timestamp-fresh`, that only rejects timestamps that are *too old*, never timestamps that are *too far in the future*. Any anomalously-future `publish-time` accepted once gets permanently written to the `last-update` map, and every subsequent (correct, present-time) update for that feed is instantly rejected as "not newer," exactly mirroring the reported Keystore `rootHash` bug class: a bad value committed once, with no recovery mechanism, bricks all further updates/validations for that entity.

### Finding Description
`oracle-timestamp-fresh` computes staleness as: [1](#0-0) 
```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```
If the incoming `ts` (the oracle's `publish-time`) is greater than the current `stacks-block-time`, `delta` is forced to `u0`, so the staleness bound (`<= delta max-staleness`) is trivially satisfied regardless of how far in the future `ts` is. `price-resolve` then commits that inflated timestamp as the new baseline: [2](#0-1) 
```
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((...)
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        ...)
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```
Once `last-update` for `{type, ident}` is set to a future value `prev`, every subsequent legitimate call with the real, present-time `ts` fails `(>= ts prev)`, so `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for that feed until real wall-clock time surpasses the erroneously stored future value. There is no admin/DAO function found in the market contract to reset or overwrite the `last-update` map entry for a feed — the same "no recovery mechanism" gap called out in the original Keystore report for a bricked `rootHash`.

Because `price-resolve` is the single choke point used both for direct price lookups (`get-asset-value`) and batched lookups feeding health checks (`calculate-asset-notional-value`, `is-healthy`), the failure is not confined to one call path — any operation needing that asset's price (borrow, repay, add/remove collateral, liquidation) fails outright once the feed is "bricked."

### Impact Explanation
This lands on **temporary freezing of funds**: while the affected feed's stored `last-update` exceeds real time, all deposits, withdrawals, borrows, repayments, and liquidations that require pricing that asset (as collateral or debt) revert with `ERR-ORACLE-INVARIANT`. Positions using that asset cannot be liquidated even if they become undercollateralized, and users cannot manage their positions, for the duration the bogus future timestamp remains ahead of chain time. Depending on how far in the future the bad timestamp lands, the freeze duration is bounded only by that gap, but the contract has no way to shorten it once set.

### Likelihood Explanation
Triggering requires a single price update accepted by the market with `publish-time` set ahead of `stacks-block-time` (e.g. a Pyth publisher/network clock skew, or any anomalous but signature-valid update, since Pyth's own `pyth-storage-v4.write-batch-entry` only enforces a lower staleness bound, not an upper future bound). Given the market's own gating logic actively rewards a future timestamp with `delta = u0` (bypassing the staleness check entirely) and then persists it as the new floor, this is a design defect in Zest's own oracle-timestamp validation code, not merely "bad third-party data" — the code should have rejected forward-dated timestamps outright rather than silently zeroing their delta.

### Recommendation
- In `oracle-timestamp-fresh`, reject timestamps greater than `stacks-block-time` (or bound the allowed forward drift to a small tolerance) instead of setting `delta` to `u0`.
- Add a DAO-governed recovery/reset path for the `last-update` map per `{type, ident}` so an erroneously-advanced timestamp can be corrected without waiting for real time to catch up.

### Proof of Concept
1. A price update for feed `F` is submitted through `resolve-pyth`/`resolve-dia` with `publish-time = T_future`, where `T_future > stacks-block-time`.
2. `price-resolve` calls `oracle-timestamp-fresh(T_future, last-update-time, max-staleness)`; since `T_future > stacks-block-time`, `delta = u0`, satisfying `<= delta max-staleness`; `T_future >= last-update-time` also holds, so the check passes.
3. `map-set last-update {type,ident} T_future` commits the future timestamp.
4. Any later legitimate call with real `publish-time = T_now < T_future` fails `(>= ts prev)` inside `oracle-timestamp-fresh`, causing `price-resolve` to `asserts!` into `ERR-ORACLE-INVARIANT` for every subsequent operation touching feed `F`, until chain time passes `T_future`.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
