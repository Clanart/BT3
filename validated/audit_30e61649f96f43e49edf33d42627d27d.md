### Title
Payout OP_RETURN operator attribution is not covered by the user's `SinglePlusAnyoneCanPay` signature, allowing an uninvolved attacker to reassign withdrawal credit to any operator - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The payout transaction's user signature is required to use `SighashType::SinglePlusAnyoneCanPay`, which under BIP-341/342 rules commits only to input 0 and the output at the same index (output 0). It does not commit to the anchor output or the OP_RETURN output that encodes the fronting operator's x-only pubkey. Since `update_finalized_payouts` derives operator credit purely from whichever OP_RETURN happens to be in the transaction that first confirms spending the `withdrawal_utxo`, an attacker who obtains the user's signature (leaked once any operator broadcasts/relays its candidate payout tx, or handed off-chain) can rebuild a transaction with an arbitrary OP_RETURN naming any operator B, get it mined first, and cause B to be credited for a withdrawal B never funded.

### Finding Description
Binding claimed: `withdrawals.payout_payer_operator_xonly_pk` (set by `update_finalized_payouts`) must equal the x-only pubkey of the operator that actually fronted `bridge_amount` liquidity to the user for withdrawal index `i`, i.e. the operator whose wallet output 0 of the payout tx was funded from.

Trace:
- `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds a payout tx with output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN(operator_xonly_pk), and signs input 0 with `set_p2tr_key_spend_witness(&user_sig, 0)`. [1](#0-0) 
- `Operator::withdraw` verifies the user signature against `calculate_sighash_txin(0, in_signature.sighash_type)` and explicitly documents/relies on `SinglePlusAnyoneCanPay`: "Ensure the signature uses SinglePlusAnyoneCanPay sighash type." [2](#0-1) 
- `SIGHASH_SINGLE|ANYONECANPAY` semantics (standard Bitcoin taproot rules) commit only to input 0 (amount+script+sequence) and output 0 (value+script). The anchor output and the OP_RETURN output (index 2, holding the credited operator's xonly pk) are **not** covered by the signature, nor are any additional inputs added later (e.g. via `fund_raw_transaction`). [3](#0-2) 
- After confirmation, `update_finalized_payouts` reads whatever transaction actually spent the withdrawal UTXO in the finalized block, extracts the first OP_RETURN output, parses it as an xonly pubkey, and stores it as `payout_payer_operator_xonly_pk` with no cross-check against which operator's capital funded output 0. [4](#0-3) 
- `PayoutCheckerTask::run_once` for operator B polls `get_first_unhandled_payout_by_operator_xonly_pk` filtered by B's own key and, upon finding a match, calls `handle_finalized_payout`, marks the payout handled, and proceeds to the kickoff/reimbursement flow — crediting B. [5](#0-4) 
- `is_kickoff_malicious` (core/src/verifier.rs:1859-1915) only checks that the OP_RETURN-derived operator key equals the kickoff's claimed operator key and that the committed block hash matches; it performs no independent verification that the credited operator actually supplied the payout capital. [6](#0-5) 

Exploit flow: the user signs input 0/output 0 with `SinglePlusAnyoneCanPay` and hands the signature to an operator (or it becomes visible once any operator broadcasts its candidate payout tx to the Bitcoin mempool). An attacker with no privileges takes that signature, reuses the identical input 0 (same outpoint/witness) and output 0 (same value/script, required to keep the SIGHASH_SINGLE commitment valid), but substitutes their own choice of OP_RETURN naming operator B, adds their own fee-paying input(s)/change output (uncommitted, since ANYONECANPAY), and gets this transaction confirmed before the operator-funded version. `update_finalized_payouts` then attributes withdrawal `i` to B, and B's own `PayoutCheckerTask` (or any operator's, at the attacker's choice) proceeds to treat the withdrawal as fronted by B, triggering B's kickoff/reimbursement path even though B put up no capital — the value backing output 0 is entirely the user's own withdrawal UTXO value, not any operator's.

No existing guard rejects this: `SECP.verify_schnorr` only checks input 0/output 0 integrity (which is preserved), `is_kickoff_malicious` only checks self-consistency between the OP_RETURN and the kickoff-claimed operator, and `update_finalized_payouts` performs no fronting-capital verification at all.

### Impact Explanation
This is a Critical finding matching "an operator reimbursed for a payout it never funded." Operator B (who may not even be aware of withdrawal `i`) gets its `PayoutCheckerTask` to mark the withdrawal as its own fronted payout, driving it through `handle_finalized_payout` → kickoff → reimbursement from the round/collateral vault, while B never actually paid the user. This is repeatable per withdrawal and per attacker choice of arbitrary operator, and the blast radius spans every withdrawal whose payout tx signature (embedding `SinglePlusAnyoneCanPay`) becomes visible before confirmation.

### Likelihood Explanation
Preconditions: the user must sign with `SinglePlusAnyoneCanPay` (which the codebase's own error message frames as the expected/required sighash type for this flow), and the attacker must observe the signature — trivially possible once any operator broadcasts the candidate payout tx to the Bitcoin P2P network/mempool (witness data is public) or if the signature is otherwise leaked off-chain. The attacker only pays ordinary Bitcoin transaction fees to build a competing/faster-confirming transaction, no special privileges, keys, or collateral are needed. Feasibility is high in any deployment where payout txs are broadcast via mempool before confirmation, which is the normal operator flow (`fund_raw_transaction` + `send_raw_transaction`).

### Recommendation
Bind the OP_RETURN operator attribution (and any other outputs beyond output 0) into the user's committed signature, e.g. by switching to `SIGHASH_ALL` (or `SIGHASH_ALL|SIGHASH_ANYONECANPAY` if additional operator-added inputs are still required) so the OP_RETURN output cannot be substituted without invalidating the signature. Alternatively, require an operator-specific authenticator (e.g., a second, operator-committed signature/covenant) binding the OP_RETURN to the specific operator prior to acceptance in `update_finalized_payouts`, rather than trusting whatever OP_RETURN happens to appear in the first confirming spend.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;
