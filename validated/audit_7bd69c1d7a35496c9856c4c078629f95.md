### Title
`SignableTransaction::new` fee/weight check omits the OP_RETURN data output, underpaying the declared fee rate — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The report's bug class is a bound check evaluated against a partial amount while an additional, unaccounted component is added afterward (the TWAB supply-limit check ignoring `yieldFeeBalance`). In Serai, `SignableTransaction::new` computes the transaction weight/vbytes — and therefore `needed_fee`, the `TooLowFee` relay check, the `NotEnoughFunds` check, and the `TooLargeTransaction` check — from `tx_ins` and `payments` only, *after* an OP_RETURN `data` output of up to 80 bytes has already been appended to `tx_outs` but is not fed into the size estimator.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` pushes the OP_RETURN output onto `tx_outs` at lines 193-202, then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204, which builds the mock transaction solely from `payments` (`send.rs:85-94`). The `data` output never participates in `weight`, `vbytes`, `needed_fee`, the minimum-relay-fee check (`send.rs:211`), the `input_sat < payment_sat + needed_fee` solvency check (`send.rs:215`), or the `MAX_STANDARD_TX_WEIGHT` check (`send.rs:241`). The same omission applies to the change-aware recalculation at `send.rs:225-226`.

Concretely, every transaction carrying `data` pays `fee_per_vbyte * vbytes_without_data` while its real vsize is ~89+ bytes larger (8-byte value + up to 80-byte script push). The declared `needed_fee()`/`fee()` is therefore systematically below what the requested fee rate requires.

### Impact Explanation
- The `TooLowFee` guard is evaluated on understated vbytes, so a transaction can be constructed whose *effective* fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`. Such a transaction will not relay or confirm — the multisig produces a transaction that burns its signing session yet cannot be published, stalling/locking the inputs it spends (analogous to the report's permanently unclaimable `yieldFeeBalance`).
- `NotEnoughFunds` can pass while `input_sat` is actually insufficient once the true fee is considered, and the change-creation threshold is likewise computed against an understated fee.
- Even when the TX relays, the paid fee rate is silently up to `fee_per_vbyte * ~89` sats below the caller's request, degrading confirmation guarantees for a threshold-coordinated transaction that cannot be trivially re-signed/RBF'd.

### Likelihood Explanation
Any caller of the public `SignableTransaction::new` API that supplies `data` (up to 80 bytes, the documented and tested maximum at `tests/wallet.rs:185-191`) triggers the underestimation deterministically. Reaching an outright non-relayable transaction additionally requires `fee_per_vbyte` near the relay minimum, which the API permits.

### Recommendation
Include the `data` output in the size estimate: build the mock transaction's output list from the fully-assembled `tx_outs` (payments + OP_RETURN), e.g. change `calculate_weight_vbytes` to accept the constructed `Vec<TxOut>` (or push `TxOut { value: Amount::ZERO, script_pubkey: <OP_RETURN script> }` into the mock) before computing `weight`/`vbytes`, and do the same for the change-aware recalculation.

### Proof of Concept
