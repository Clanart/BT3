Based on my investigation, I found a legitimate analog in the Python pure-Python decoder implementation.

### Title
Global mutable recursion-limit state shared across concurrent Python message parses - ([File: python/google/protobuf/internal/decoder.py])

### Summary
The Python pure-Python decoder (`python_message.py`'s `_InternalParse`, backed by `decoder.py`) enforces a recursion-depth check against a **module-level global variable** `_recursion_limit`, which can be mutated at any time via the public function `decoder.SetRecursionLimit()`. Because this limit is stored in process-global state rather than being scoped to the individual `CodedInputStream`/parse call (as the C++ implementation correctly does), a call to `SetRecursionLimit()` from one thread affects the recursion-depth enforcement seen by every other concurrently-running parse operation in the process — mirroring the exact bug class in CVE-2021-22897, where a single static variable holding a per-session TLS setting was clobbered by concurrent transfers. [1](#0-0) 

### Finding Description
The invariant that fails to hold is: *a recursion/depth-limit protection configured for one parse operation must not leak into or be overwritten by a concurrently executing, unrelated parse operation*. In the C++ implementation, `CodedInputStream::recursion_limit_` and `recursion_budget_` are **per-instance** fields on the `CodedInputStream` object, so each concurrent parse gets its own independent, correctly-scoped limit. [2](#0-1) 

The Python pure-Python fallback backend, however, defines:
```python
DEFAULT_RECURSION_LIMIT = 100
_recursion_limit = DEFAULT_RECURSION_LIMIT

def SetRecursionLimit(new_limit):
  global _recursion_limit
  _recursion_limit = new_limit
``` [1](#0-0) 

This single module-global is consulted by every decode call in the interpreter, regardless of which `Message`, thread, or logical "session" is doing the parsing. Any caller (library code, application code, or a test harness) invoking `decoder.SetRecursionLimit()` — for example to raise the limit temporarily to accept a deeply-nested but trusted message — changes the effective depth enforcement for **all other concurrently executing parses** in the same process, including ones parsing attacker-supplied bytes that were relying on the original (lower) limit for protection. This is architecturally identical to curl's bug: a single "static"/global variable intended to configure one operation ends up controlling all concurrent operations, and "the last one that sets" the value wins for everyone.

### Impact Explanation
Where an application sets a low recursion limit specifically to bound attacker-controlled binary protobuf input (a defense-in-depth stack-overflow/DoS mitigation), a second, unrelated code path in the same process that calls `SetRecursionLimit()` with a higher value (e.g., to parse large, trusted internal messages) will silently and globally raise the limit for every other concurrent parse, including the one processing untrusted input. This weakens or defeats the recursion-depth protection for other in-flight parses without any indication to the caller — an "exposure of data/protection to the wrong session," in the same spirit as curl's CVE, though the concrete exploitable effect here is a bypassed depth-limit guard rather than a leaked cipher/credential. It does not itself grant memory corruption; the impact is a silent security-control weakening across sessions, consistent with a Medium-severity finding.

### Likelihood Explanation
This requires: (1) the pure-Python decoder backend to be in use (as opposed to the C++/upb-accelerated backends, which use per-instance state as shown in `coded_stream.h`), and (2) some code path in the process to call `decoder.SetRecursionLimit()` concurrently with another parse relying on the default/lower limit. This is a plausible but not universal deployment: `SetRecursionLimit` is a real, documented, callable API (referenced/tested in `python/google/protobuf/internal/message_test.py`), so multi-tenant or multi-purpose Python processes that adjust this setting per use-case are exposed. It is less likely in single-purpose processes that never call `SetRecursionLimit`, or when running on the C++/upb backend where this global does not exist.

### Recommendation
Scope the recursion limit to the parse call/stack (e.g., pass it explicitly through `_InternalParse`/decoder calls or store it on a per-parse context object) rather than a shared module-level global, matching the per-instance design already used in the C++ `CodedInputStream`. At minimum, document that `SetRecursionLimit` is process-global and unsafe to call from multi-threaded or multi-tenant code paths that parse untrusted input concurrently with adjustable limits.

### Proof of Concept
A concrete runnable reproduction was not executed in this session (no execution environment available here); the finding is based on static code inspection of the `global _recursion_limit` pattern in `decoder.py` contrasted with the per-instance `recursion_limit_`/`recursion_budget_` fields in `coded_stream.h`. To confirm exploitability, a background Devin session with code execution should run two threads in the Python pure-Python protobuf backend: Thread A repeatedly calls `google.protobuf.internal.decoder.SetRecursionLimit(100000)` while Thread B concurrently calls `MyMessage().MergeFromString(deeply_nested_payload)` with a payload whose nesting depth exceeds the intended default limit (100) but is below the value Thread A set; verify whether Thread B's parse — which did not itself request a higher limit — unexpectedly succeeds due to Thread A's concurrent global mutation, and compare against the equivalent scenario using the C++/upb backend (`api_implementation`) where each `CodedInputStream` has its own limit and no cross-thread interference should occur.
