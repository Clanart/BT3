### Title
Single-value `interested_puzzle_hashes` mapping silently overwrites earlier wallet registrations, causing coins to be attributed to the wrong wallet - (File: `chia/wallet/wallet_interested_store.py`)

### Summary
`WalletInterestedStore` persists `puzzle_hash -> wallet_id` as a **single-value** mapping (`puzzle_hash` is the SQL `PRIMARY KEY`), even though `WalletStateManager.add_interested_puzzle_hashes()` explicitly documents that more than one wallet can become interested in the same puzzle hash. When a second registration occurs for a puzzle hash that is already tracked, the previous `wallet_id` is silently discarded (`INSERT OR REPLACE`), which is structurally identical to the reported `tokenIdsToPoolIds` bug: a mapping that should support many-to-one relationships is implemented as a last-write-wins single value, and callers (`get_wallet_identifier_for_puzzle_hash`, `_add_coin_state`) rely on it to route incoming coins to the correct wallet.

### Finding Description
`WalletInterestedStore` creates the table as: [1](#0-0) 

and writes to it with `INSERT OR REPLACE`, which overwrites any prior `wallet_id` for a given `puzzle_hash`: [2](#0-1) 

`WalletStateManager.add_interested_puzzle_hashes()` explicitly calls out this exact class of defect in a code comment — the in-memory `interested_coin_cache` keeps *all* interested `wallet_id`s per puzzle hash, but the persistent `interested_store` keeps only the last one written: [3](#0-2) 

This mapping is read back by `get_wallet_identifier_for_puzzle_hash()`, which is the fallback path used during coin-state processing (`_add_coin_state`) to decide which wallet a newly seen coin belongs to when the puzzle hash isn't already a known derived puzzle hash: [4](#0-3) [5](#0-4) 

`add_interested_puzzle_hashes()` is invoked from singleton-lifecycle code such as `PoolWallet` (p2-singleton puzzle hash tracking) and the Data Layer / plot-NFT wallets, all of which are driven by on-chain singleton spends that an unprivileged wallet user (or offer/trade counterparty triggering singleton transitions) can produce. If two different local wallet objects (e.g., two `PoolWallet`s tracking distinct singletons that happen to route through, or become interested in, the same `p2_singleton_puzzle_hash`/inner puzzle hash) register interest in the same puzzle hash, the second `add_interested_puzzle_hash()` call overwrites the first wallet's `wallet_id` entry in the persistent store, exactly mirroring the `tokenIdsToPoolIds` overwrite in the Solidity report where a single key incorrectly stores only one owner.

### Impact Explanation
Because coin-to-wallet attribution can fall through to this overwritten mapping, a coin that should be recognized and processed by the first wallet can instead be silently associated with (or fail to be associated with) the wrong wallet identifier once the entry is clobbered. This is directly analogous to `Sleeves.adminSyncPools()`/`Sleeves._withdrawWithProofBatch()` misbehaving from `tokenIdsToPoolIds` overwrites: state that legitimately needs a many-to-one (or many-to-many) relationship is collapsed to one-to-one, and the resulting misrouting/lost association can leave the affected wallet's coin unrecognized by its owning wallet logic (never confirmed, spend/absorb logic skipped), which functionally strands funds in wallet state until manual intervention/resync.

### Likelihood Explanation
Likelihood is lower than the original Solidity finding because puzzle hashes are normally unique per singleton/derivation path, so a genuine collision requires a specific singleton/pool/DL flow where the same puzzle hash is legitimately registered as "interesting" by two different wallet objects (the codebase's own TODO comment confirms the maintainers are aware this scenario is possible and unhandled). It is reachable purely through normal wallet-driven singleton operations (pool join/leave, plot NFT creation, DL launcher tracking) without any privileged or malicious-peer capability, but it depends on triggering a specific overlap condition rather than being trivially exploitable on every use.

### Recommendation
Change `interested_puzzle_hashes` from a `puzzle_hash -> single wallet_id` primary-key table to a many-to-many structure (e.g., composite primary key on `(puzzle_hash, wallet_id)`, or a boolean/junction table as recommended in the original report), so that `add_interested_puzzle_hash()` adds an association without evicting existing ones, and `get_interested_puzzle_hash_wallet_id()`/`get_wallet_identifier_for_puzzle_hash()` are updated to return/consider all associated wallets consistently with what `interested_coin_cache` already does in memory.

### Proof of Concept
Not independently reproduced with a live wallet sync scenario (this is a static-analysis analog derived from the code and its own acknowledging TODO comment); a concrete PoC would require driving two `PoolWallet`/`DataLayerWallet` instances to register interest in the same puzzle hash and observing that `WalletInterestedStore.get_interested_puzzle_hash_wallet_id()` returns only the most recently registered `wallet_id`, verified against the table definition and `INSERT OR REPLACE` semantics cited above.

```python
    async def get_wallet_identifier_for_puzzle_hash(self, puzzle_hash: bytes32) -> WalletIdentifier | None:
        wallet_identifier = await self.puzzle_store.get_wallet_identifier_for_puzzle_hash(puzzle_hash)
        if wallet_identifier is not None:
            return wallet_identifier

        interested_wallet_id = await self.interested_store.get_interested_puzzle_hash_wallet_id(puzzle_hash=puzzle_hash)
        if interested_wallet_id is not None:
            wallet_id = uint32(interested_wallet_id)
            if wallet_id not in self.wallets.keys():
                self.log.warning(f"Do not have wallet {wallet_id} for puzzle_hash {puzzle_hash}")
                return None
            return WalletIdentifier(uint32(wallet_id), self.wallets[uint32(wallet_id)].type())
        return None
```

```python
    async def add_interested_puzzle_hashes(self, puzzle_hashes: list[bytes32], wallet_ids: list[int]) -> None:
        # TODO: It's unclear if the intended use for this is that each puzzle hash should store all
        # the elements of wallet_ids. It only stores one wallet_id per puzzle hash in the interested_store
        # but the coin_cache keeps all wallet_ids for each puzzle hash
        for puzzle_hash in puzzle_hashes:
            if puzzle_hash in self.interested_coin_cache:
                wallet_ids_to_add = list({w for w in wallet_ids if w not in self.interested_coin_cache[puzzle_hash]})
                self.interested_coin_cache[puzzle_hash].extend(wallet_ids_to_add)
            else:
                self.interested_coin_cache[puzzle_hash] = list(set(wallet_ids))
        for puzzle_hash, wallet_id in zip(puzzle_hashes, wallet_ids):
            await self.interested_store.add_interested_puzzle_hash(puzzle_hash, wallet_id)
        if len(puzzle_hashes) > 0:
            await self.wallet_node.new_peak_queue.subscribe_to_puzzle_hashes(puzzle_hashes)
```
