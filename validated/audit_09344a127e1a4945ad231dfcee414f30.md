### Title
Bitcoin deposits can inherit instructions from unrelated later transactions - ([File: processor/src/networks/bitcoin.rs])

### Summary
`Bitcoin::get_outputs` accumulates all scanned outputs for a block in `outputs`, then runs the metadata-population step whenever that block-level vector is non-empty, rather than only when the current transaction produced outputs. As a result, every later transaction in the block can overwrite the `data` and `presumed_origin` of earlier deposits. An unprivileged attacker can place a transaction containing their own OP_RETURN-encoded `Shorthand::Transfer` after a victim's deposit in the same block and cause the victim's deposit to mint funds to the attacker. [1](#0-0) 

### Finding Description
For each non-coinbase transaction, `get_outputs` scans it and appends matching outputs to the shared `outputs` vector. The subsequent `if outputs.is_empty()` check tests whether **any** output has been collected so far, not whether the current transaction produced one. [2](#0-1) 

Once at least one output has been collected, the function derives `presumed_origin` from `tx.input[0]` of the *current* transaction, extracts Serai data from that transaction, and assigns both values to every accumulated output. This assignment is not scoped to outputs created by that transaction and is repeated for every later transaction, so the last transaction in a matching block controls the metadata for all previously scanned deposits. [3](#0-2) 

For `OutputType::External`, `instruction_from_output` decodes `output.data()` as a `Shorthand`, converts it to `RefundableInInstruction`, associates it with the scanned output's balance, and emits an `InInstructionWithBalance`. [4](#0-3)  Those instructions are pushed into the batch produced from the scanned block. [5](#0-4)  A `Transfer` instruction mints the incoming balance to the supplied Serai address. [6](#0-5) 

### Impact Explanation
A deposit can be processed with an instruction belonging to an unrelated transaction. If the injected transaction encodes `Shorthand::Transfer` to an attacker-controlled Serai address, Serai treats the victim's Bitcoin output as funding that instruction and mints the corresponding sriBTC balance to the attacker. If the injected data is malformed, the overwritten `presumed_origin` can instead direct a refund to an attacker-selected source address derived from the attacker's transaction input. [7](#0-6) [8](#0-7) 

This is a concrete loss of bridged value: the vault receives the victim's BTC while the corresponding Serai-side balance or refund destination is assigned to the attacker. [9](#0-8) [6](#0-5) 

### Likelihood Explanation
The required public action is ordinary Bitcoin transaction inclusion: a victim sends a deposit to the recognized external P2TR script, and an attacker places another transaction carrying attacker-controlled OP_RETURN data later in the same block. The malicious transaction does not need to send funds to Serai because the metadata path executes whenever `outputs` already contains an earlier deposit. [10](#0-9) 

The attacker must obtain ordering after the victim transaction, but can monitor the public mempool, prepare the instruction transaction in advance, and use a higher fee or miner coordination to seek placement in the same block. The condition is therefore externally reachable and does not require control of validators, the Bitcoin node, private keys, or malformed curve encodings. [11](#0-10) [12](#0-11) 

### Recommendation
Track metadata on a per-transaction basis. For each `tx`, store the outputs produced by `scanner.scan_transaction(tx)` in a separate `tx_outputs` vector; if that vector is empty, continue before deriving the origin or extracting data. Populate only `tx_outputs`, then extend the block-level result vector afterward. [1](#0-0) 

Also associate the instruction data with the transaction ID or derive the data only from the same transaction that created each output. Add a regression test with two transactions in one block where only the first pays Serai and the second contains an OP_RETURN instruction, asserting the first output retains empty/original metadata. [10](#0-9) 

### Proof of Concept
1. Victim broadcasts transaction `tx_v`, containing output `vout0` to Serai's external P2TR script and no Serai instruction.
2. Attacker broadcasts transaction `tx_a`, containing an OP_RETURN payload encoding `Shorthand::Raw(RefundableInInstruction { origin: None, instruction: InInstruction::Transfer(attacker_serai_address) })`.
3. Both transactions are included in one block with `tx_v` before `tx_a`.
4. During `tx_v`, `scan_transaction` appends the victim output and initializes it with the victim transaction's origin and empty data. [13](#0-12) 
5. During `tx_a`, `outputs` is still non-empty even though `tx_a` created no Serai output, so the code recomputes metadata from `tx_a` and loops over every accumulated output. [14](#0-13) 
6. The victim's `OutputType::External` output now carries the attacker's serialized instruction. `instruction_from_output` decodes it and emits the attacker's `Transfer` with the victim's deposit amount, causing the corresponding Serai balance to be minted to the attacker. [12](#0-11) [6](#0-5)
