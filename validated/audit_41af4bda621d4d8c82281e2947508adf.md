### Title
Fee-on-transfer ERC20 tokens cause bridge collateral under-accounting in `requestERC20Transfer` — ([File: contracts/service_chain/bridge/BridgeTransferERC20.sol])

### Summary
`BridgeTransferERC20.requestERC20Transfer` pulls `_value + _feeLimit` from the caller via `safeTransferFrom` and then emits `RequestValueTransfer` carrying the nominal `_value` (not the amount actually received by the bridge). If the registered `_tokenAddress` is a fee-on-transfer ERC20, the bridge's actual token balance increase is less than `_value + _feeLimit`, yet the counterpart chain's operators will mint/unlock the full nominal `_value` to the recipient based on the emitted event. This is the same root-cause pattern as the referenced Y2K report: crediting a nominal transferred amount instead of the actually-received balance delta.

### Finding Description
In `_requestERC20Transfer`/`requestERC20Transfer` [1](#0-0) , the bridge does:
1. `IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))`
2. `_requestERC20Transfer(...)` which computes/pays fee via `_payERC20FeeAndRefundChange`, optionally burns `_value` if `modeMintBurn`, and emits `RequestValueTransfer(..., _value, ..., fee, ...)` [2](#0-1) .

None of this code checks the token's actual balance delta before/after the `safeTransferFrom` call; it simply assumes the full `_value + _feeLimit` was received. For a fee-on-transfer token, the bridge's real balance increase is strictly less than what is assumed. On the non-mint-burn (lock/unlock) side, `handleERC20Transfer` later sends out the full nominal `_value` via `safeTransfer` to satisfy the counterpart request [3](#0-2) . Because deposits under-collateralize the bridge relative to the nominal amounts credited via emitted events (which off-chain operators/counterpart bridge act upon to mint or release funds), the bridge's real token reserve is progressively depleted below what's needed to honor all outstanding value-transfer requests.

### Impact Explanation
This is a value-accounting break reachable by any unprivileged transaction sender who calls `requestERC20Transfer` (or `onERC20Received`) with a fee-on-transfer token that has been registered on the bridge. Over repeated deposits, the bridge's real balance falls behind the sum of nominal values it has committed to honor on the counterpart chain, so later legitimate withdrawal/handle requests can fail or be under-collateralized — a Medium-severity insolvency/accounting-drift issue analogous to the referenced report, since it results in a mismatch between recorded value transferred and value actually held/movable, potentially stealing value from users who settle later.

### Likelihood Explanation
Likelihood depends on whether a fee-on-transfer ERC20 token is registered via `registerToken` on this bridge (`onlyRegisteredToken` gate) [4](#0-3) . This is the service-chain (child-chain) bridge used for custom token bridging between Kaia's parent and child (service) chains, so it depends on chain operators registering arbitrary ERC20 tokens; if any registered token later becomes (or is) fee-on-transfer, any ordinary user transaction triggers the accounting drift — no special privileges are required to trigger the bug once such a token is registered.

### Recommendation
Measure the actual balance delta (`asset.balanceOf(address(this))` before/after `safeTransferFrom`) in `requestERC20Transfer`/`onERC20Received` and use that measured amount — not the nominal `_value + _feeLimit` — for fee calculation, burning, and the `RequestValueTransfer` event's `valueOrTokenId` field, so the counterpart chain only credits what was actually received.

### Proof of Concept
Not independently reproducible from the indexed contents alone: this repository's bridge test suite (`contracts/test/Bridge/bridge.test.ts`) only exercises standard (non fee-on-transfer) ERC20 tokens, and I could not find a fee-on-transfer test token or scenario in the codebase to confirm whether operators are expected/allowed to register such tokens in practice. This is a limitation to flag explicitly — the finding is grounded in the exact code (`safeTransferFrom` amount assumed intact) but the operational likelihood of a fee-on-transfer token actually being registered on this bridge could not be verified further with the available tools.

    function _requestERC20Transfer(
        address _tokenAddress,
        address _from,
        address _to,
        uint256 _value,
        uint256 _feeLimit,
        bytes memory _extraData
    )
        internal
        onlyRegisteredToken(_tokenAddress)
        onlyUnlockedToken(_tokenAddress)
    {
        require(isRunning, "stopped bridge");
        require(_value > 0, "zero ERC20 token amount");

        uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);

        if (modeMintBurn) {
            ERC20Burnable(_tokenAddress).burn(_value);
        }

        emit RequestValueTransfer(
            TokenType.ERC20,
            _from,
            _to,
            _tokenAddress,
            _value,
            requestNonce,
            fee,
            _extraData
        );
        requestNonce++;
    }
