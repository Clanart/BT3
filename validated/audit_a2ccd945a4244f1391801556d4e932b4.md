## Title
Attacker-controlled file content with a decoy `>>>>>>>` (or `=======`) line desynchronizes Copilot conflict-hunk boundary detection, silently corrupting/leaving unreviewed conflict-marker text in the committed file - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Sherlock finding's root cause is that a computed value (`rewardAmount`) is split into parts *before* the configuration that governs one of those parts (`escrowPool`) is validated, so a part of the value silently disappears with no error raised. The same "split first, validate later — but validate the wrong thing" shape exists in GitHub Desktop's Copilot merge-conflict resolver: the file is split into "hunks" at parse time (`extractConflictHunks`) and spliced back together at write time (`reassembleResolvedFile`), and the only cross-check between the two (`validateResolutionPaths`) only compares hunk *counts*, never hunk *boundaries*. An attacker who controls content that ends up on either side of a real merge conflict (a branch/PR the victim later merges) can craft a decoy line that both parsers agree on positionally but that truncates the real conflict block, leaving literal git conflict-marker text spliced into the final file that gets written to disk and `git add`-ed without any diff review.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) locates the closing marker for a hunk with a simple regex scan that stops at the *first* line matching the "theirs" marker regex: [1](#0-0) 

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`), which independently re-parses the same raw file content to splice the model's resolved text back in, uses the same "first match wins" logic to find the closing marker: [2](#0-1) 

Because git always writes well-formed markers, the only way to make this ambiguous is via **attacker-supplied file content that itself contains a line matching `/^>{7}(?:\s|$)/` or `/^={7}$/`** positioned inside what will become one side of a real future conflict (e.g. a markdown blockquote line of exactly seven `>` characters, or a heading underline of exactly seven `=` characters — both plausible, naturally occurring text). When such a file later genuinely conflicts:

- Both `extractConflictHunks` and `reassembleResolvedFile` independently stop at the *decoy* marker line, not the real one, and they agree on this wrong boundary (since they use equivalent regexes). This means the hunk *count* stays correct, so `validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`), which only checks `resolution.hunks.length !== expectedCount`, does not catch anything: [3](#0-2) 
- The content between the decoy line and the *real* closing `>>>>>>>` marker (including the real marker line itself) is treated by both functions as ordinary, non-conflicted file content and is copied through verbatim into the final reassembled file.
- `_applyCopilotConflictResolutions` in `app/src/lib/stores/app-store.ts` then writes this content straight to disk and stages it with no intervening full-file diff review by the user: [4](#0-3) 

The result: a literal, un-negotiated fragment of conflict-marker text (and the corresponding cut-off resolution) ends up in the file that gets `git add`-ed — silently corrupting what the user commits, exactly analogous to how the escrow bug silently drops `escrowedRewardAmount` because the split happens before the config that decides where that portion goes is checked.

### Impact Explanation
This causes silent corruption of the working tree / index content that the user is about to commit and push, without any error, warning, or diff shown for the discrepancy — matching the "silent corruption of what the user commits or pushes" impact criterion. A committed file containing a stray literal `>>>>>>> branch-name` (or truncated content) can break builds, leak the losing side's code unexpectedly, or reintroduce content the model was never actually asked to reconcile.

### Likelihood Explanation
This requires no local/physical access, no prior malware, no leaked credentials, and no unnatural user steps: the attacker only needs to contribute ordinary-looking text (a blockquote, a markdown heading underline, changelog formatting, or similar) to a branch/PR that a victim will merge, rebase, or cherry-pick with Copilot conflict resolution enabled. Because the trigger text is plausible/naturally occurring (7-character `>` or `=` sequences are common in markdown/git-log style content), an attacker does not need to inject anything obviously suspicious.

### Recommendation
Make `reassembleResolvedFile` and `extractConflictHunks` share a single hunk-boundary-detection implementation, and have `validateResolutionPaths` (or a new check) verify that the number of hunk boundaries reassembly detects at splice time still matches what was sent to the model — not just that the model's returned count matches the *extraction*-time count. Alternatively, tag each parsed hunk with a stable identifier/checksum of its exact marker positions and verify that identifier at splice time so a boundary mismatch fails loudly instead of silently truncating content.

### Proof of Concept
1. Attacker pushes a branch/PR that adds a file containing a line of exactly seven `>` characters (e.g., as part of markdown blockquote nesting) inside a section of code that legitimately diverges from `main`.
2. Victim merges/rebases and hits a real conflict on that file; Copilot conflict resolution is invoked.
3. `extractConflictHunks` (`copilot-conflict-context.ts:228-237`) stops at the attacker's decoy `>>>>>>>`-looking line rather than the real closing marker, and hands the model a truncated "theirs" hunk.
4. `reassembleResolvedFile` (`copilot-conflict-resolution.ts:559-582`) independently stops at the same decoy line when splicing the model's resolution back in.
5. `validateResolutionPaths` only checks hunk count (still 1), so no error is raised.
6. `_applyCopilotConflictResolutions` writes the reassembled file — which now contains the model's (truncated) resolution followed by leftover literal conflict-marker text — to disk and runs `git add` on it, all without a full-file diff review.
