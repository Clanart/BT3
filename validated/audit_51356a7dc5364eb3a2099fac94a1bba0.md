## Title
Shared `CallDispatcher` balance swept via raw `balanceOf()` in `placeOrder` predispatch path causes fund loss / cross-order misattribution - (File: `evm/src/apps/IntentGatewayV2.sol`)

## Summary
The external report's core defect is using an unaccounted, shared, raw token balance (`balanceOf(address(this))`) — rather than an internally tracked per-depositor value — as the basis for distributing/crediting funds, letting unrelated deposits corrupt accounting and permanently strand value. `IntentGatewayV2.placeOrder`'s predispatch flow reproduces this exact pattern against the shared `CallDispatcher` contract.

## Finding Description
In the predispatch branch of `placeOrder`, user assets are sent to the shared `dispatcher` contract, an arbitrary call is executed on it, and then the gateway sweeps funds back by reading the dispatcher's **raw total balance**, not a value scoped to what this specific order's predispatch call produced: [1](#0-0) 

Specifically:
- `uint256 balance = IERC20(token).balanceOf(dispatcher);` reads the dispatcher's entire current balance for the token.
- `transferCalls[i]` is built to sweep that *entire* balance (`balance`), not `requiredAmount`, back to the gateway: `abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)`.
- `received` is then computed as the gateway's balance delta, and used to set `order.inputs[i].amount` (capped at the originally required amount) with any excess emitted only as `DustCollected` and left sitting, untracked, in the gateway: [2](#0-1) 

The `dispatcher` (`_params.dispatcher`) is a single, shared, publicly-known contract used by every order that includes predispatch calldata (per its own doc comment: "e.g., unwrapping LP tokens"). Because the sweep is driven by `balanceOf(dispatcher)` instead of a value derived strictly from this order's own predispatch execution, any token left behind in the dispatcher — from:
- a prior order's predispatch call producing byproduct/slippage tokens not declared in that order's `order.inputs` (so never swept by that order),
- fee-on-transfer or rounding residue from an unrelated predispatch swap, or
- a third party directly transferring tokens to the publicly-known `dispatcher` address —

gets silently absorbed into the *next* unrelated order's sweep and is either (a) misattributed as that order's own "dust" (benefiting no one, just stuck in the gateway with no escrow entry), or (b) in principle inflates `received` for the new order without any linkage back to the original depositor who produced it. The original depositor whose leftover was swept away has no way to reclaim it — it's not tracked per-order, only a generic event is emitted.

This is structurally identical to the JPEG'd `LPFarming` defect: a value that should be tracked internally per-depositor (`totalLPSupply` in the original bug) is instead read as a live, shared `balanceOf()`, so unrelated inflows/outflows corrupt the accounting used to credit/settle funds for a specific party.

## Impact Explanation
Funds belonging to a legitimate order-placer can become permanently stuck/unaccounted at the `IntentGatewayV2` contract whenever their predispatch call (an arbitrary, dispatcher-executed call such as an LP-unwrap or swap) produces token amounts beyond what they declared in `order.inputs`, or whenever residue from token behavior (fee-on-transfer, slippage, rounding) is left in the shared dispatcher. This satisfies the bounty's "loss of funds" / "logic attack" criteria: value that should be attributable and recoverable by the depositor is instead swept, uncredited, and stranded — matching the "part of rewards locked forever" impact class from the seed report. No relayer, prover, admin, or governance actor is required; the corrupting condition is producible by any ordinary user of `placeOrder` (via normal predispatch execution) or even a bystander donating tokens to the well-known `dispatcher` address.

## Likelihood Explanation
Moderate-to-high. Because `dispatcher` is a single shared, publicly known contract address reused across *all* predispatch-enabled orders, any predispatch call whose output doesn't exactly match the declared `order.inputs` set (a very plausible occurrence with real-world swaps/unwraps subject to slippage or multi-token outputs) leaves residue that the very next unrelated predispatch order will sweep via the uncontrolled `balanceOf(dispatcher)` read. No adversarial coordination or privileged access is needed — it is a direct consequence of normal usage plus the balance-based sweep design.

## Recommendation
Do not size the sweep or the "received" computation off `IERC20(token).balanceOf(dispatcher)`. Instead:
- Have the `CallDispatcher` explicitly report (or transfer) only the amount actually produced for the *current* call's declared assets, or
- Track dispatcher outflows per-order using an internally maintained accounting value (analogous to `totalLPSupply` in the referenced fix) rather than a live balance query, and
- Reconcile/refund any genuine surplus back to the depositor whose predispatch produced it, instead of emitting it as ownerless `DustCollected` credited to whichever order happens to sweep next.

## Proof of Concept
1. User A calls `placeOrder` with `predispatch.call` that unwraps an LP token into `TokenX` + `TokenY`, but `order.inputs` only declares `TokenX` (a legitimate, common case where a predispatch produces an ancillary/byproduct token not part of the order).
2. During Phase 1 (`evm/src/apps/IntentGatewayV2.sol:227-258`), only `TokenX`'s full dispatcher balance is swept via the `transferCalls` sweep; the `TokenY` byproduct is never referenced in `order.inputs`, so it is left sitting in `dispatcher`.
3. User B later calls `placeOrder` with a predispatch that also touches `TokenY`, declaring it in `order.inputs`. When Phase 1 executes for User B, `uint256 balance = IERC20(TokenY).balanceOf(dispatcher);` reads **User A's stranded TokenY plus User B's own predispatch output**, and the full amount is swept to the gateway.
4. `received` for User B's `TokenY` input is `balancesBefore` delta including User A's leftover; if it exceeds `order.inputs[i].amount`, the excess is emitted as `DustCollected` and stays in the gateway contract, permanently unrecoverable by User A, with no on-chain record tying it back to User A's original order commitment.
