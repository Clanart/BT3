## Title
Stale index-based partial diff selection is silently reapplied to a changed file after a status refresh, corrupting what gets committed - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
GitHub Desktop tracks a user's partial line/hunk selection for a working-directory file (`DiffSelection`) purely by numeric **line indices**, and re-attaches that selection to the "same" file across refreshes using only the file's `id`, which is derived from `status.kind + path` (and never from file content). If the file's on-disk content/diff shape changes between the time the user made a partial selection and the time the commit is created (e.g., because of a background `git status`/diff refresh racing with an external content change to the working tree), the old line-index selection is blindly reapplied to the new diff. This is structurally the same class of bug as the Ramses `secondsPerLiquidityPeriodStartX128` issue: a reference/offset ("start", here "selected line indices") is computed against one version of the underlying data and is never invalidated/recomputed when the underlying data is swapped out from under it, so subsequent accounting (there: SPL; here: which lines get committed) silently uses stale coordinates against new data.

### Finding Description
`updateChangedFiles` merges new `git status` results with the previous working-directory state by matching files solely on `file.id`: [1](#0-0) 

If a file with the same `id` still exists, its **old** `DiffSelection` (which encodes selected/deselected line indices from the previous diff) is reattached verbatim via `file.withSelection(existingFile.selection)`, with no comparison of the actual diff content between old and new state.

`id` is computed only from status kind and path, never from content: [2](#0-1) 

Later, when the diff is (re-)loaded for the selected file, `updateChangesWorkingDirectoryDiff` only trims the reused selection down to lines that are still "selectable" in the new diff — it does not remap or invalidate the selection based on whether the new diff's line *content* at those indices matches what the user originally selected: [3](#0-2) 

The code comment even acknowledges this limitation explicitly, admitting the fix is incomplete: [4](#0-3) 

`DiffSelection.isSelected`/`withRangeSelection`/`withSelectableLines` operate strictly on integer line indices, with no notion of the underlying line's content or hash: [5](#0-4) [6](#0-5) 

Because the guard is purely "does a selectable line still exist at index N", a hunk shift (lines added/removed above the previously selected hunk due to any process touching the working tree — a hook, a slow async status/diff pipeline racing a checkout/merge, or content rewritten by a filter/tool while Desktop is mid-refresh) causes index `N` to now refer to different content. The stale `divergingLines` set (still keyed by index) is kept, so the selection silently applies to the wrong lines of the new diff. `_commitIncludedChanges` then commits based on exactly this stale, reused selection object without any additional content-based validation: [7](#0-6) 

This is the direct analog of the audited contract bug: `secondsPerLiquidityPeriodStartX128` ("start") is recorded once and reused as a reference point for later accounting, but is never invalidated/recomputed when the underlying tick/outside data is reset — leading to silently wrong results that pass existing sanity checks. Here, the "start" is the set of selected line indices, and the underlying data that can shift without invalidating it is the diff's line layout.

### Impact Explanation
If exploitable, the result is silent corruption of what a user commits: lines the user believed were excluded (e.g., secrets, debug code, unrelated changes) could be included, or lines they believed were included could be silently dropped — without any error or warning, directly matching the "silent corruption of what the user commits or pushes" impact category. Since Desktop pushes on the user's behalf, this could also propagate unintended content to a remote.

### Likelihood Explanation
This requires a race between Desktop's asynchronous status/diff refresh pipeline (`_loadStatus` → `updateChangedFiles` → `updateChangesWorkingDirectoryDiff`) and a content change to the working tree of a tracked file that shifts line numbers, while the user has an existing partial selection on that file. This is a timing-dependent condition rather than a simple, always-reproducible one-shot, and I could not fully verify from static code inspection alone (without running Desktop) exactly how tight this race window is in practice, or whether any other code path (not found in this pass) revalidates selection against diff content before commit. This uncertainty should be resolved by dynamic testing/fuzzing of the Changes-list partial-selection + refresh + commit flow, similar to the "requires heavy testing/fuzzing" caveat in the original report.

### Recommendation
Do not key preserved partial selections purely on file `id` (kind+path) and line index. Instead, either (a) invalidate/reset the partial selection whenever the underlying diff for that file has structurally changed (e.g., compare hunk boundaries/line content hashes, not just "is line N still includeable"), or (b) attempt a content-aware remap of selected lines (matching by line content/context rather than raw index) similar to a three-way merge, falling back to clearing the selection when remapping is ambiguous. At minimum, before creating a commit, re-validate that the currently loaded diff for each partially-selected file matches the diff that was current when the selection was made.

### Proof of Concept
Conceptual reproduction (exact timing must be validated with instrumentation/fuzzing, consistent with the original report's own recommendation):
1. Open a repository in Desktop with a tracked file `foo.txt` containing multiple hunks of changes.
2. In the Changes view, partially select only specific lines within one hunk (e.g., lines 10-12) via `withRangeSelection`.
3. While Desktop's async status refresh is in flight (e.g., triggered by any background poll, another Desktop operation, or an external process/hook touching `foo.txt`), have the working-tree content of `foo.txt` change such that lines are inserted/removed above the selected hunk, shifting subsequent line indices, while the file's `AppFileStatusKind` and path remain identical (so `id` is unchanged).
4. `updateChangedFiles` reattaches the old `DiffSelection` (indices 10-12) to the new file object because `id` matched.
5. `updateChangesWorkingDirectoryDiff` only trims to lines still selectable at those indices in the new diff — the old indices may now overlap with unrelated new content.
6. Trigger `_commitIncludedChanges`; the commit is created from `file.selection` at the stale indices, silently including/excluding unintended content relative to the user's actual intent.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
