### Title
Unchecked `u32` Subtraction in `calculate_new_difficulty` Silently Wraps on Timestamp Underflow, Producing Inverted Difficulty Adjustment — (`circuits-lib/src/header_chain/mod.rs`)

---

### Summary

`calculate_new_difficulty` computes the epoch timespan with a plain `u32` subtraction: `last_timestamp - epoch_start_time`. If the last block's timestamp is less than the epoch-start timestamp — which is valid under Bitcoin's MTP rule — this underflows. In Rust release mode (standard for RISC Zero zkVM guest builds), the underflow wraps silently to a value near `u32::MAX`, which is then clamped to `EXPECTED_EPOCH_TIMESPAN * 4`. This produces a difficulty that is **4× easier** than the current difficulty — the exact opposite of what Bitcoin Core computes (which uses signed arithmetic and clamps to `EXPECTED_EPOCH_TIMESPAN / 4`, making difficulty **4× harder**). The corrupted `current_target_bits` is stored in `ChainState` and used to validate all subsequent blocks, enabling acceptance of an invalid header-chain proof.

---

### Finding Description

In `circuits-lib/src/header_chain/mod.rs`, `calculate_new_difficulty` is called at every epoch boundary (every 2016 blocks): [1](#0-0) 

The critical line is:

```rust
let mut actual_timespan = last_timestamp - epoch_start_time; // plain u32 subtraction
``` [2](#0-1) 

Bitcoin's MTP rule only requires that a block's timestamp exceeds the median of the previous 11 blocks — it does not require strict monotonicity. Over a 2016-block epoch it is theoretically valid for the last block's timestamp to be less than the first block's timestamp. When this occurs:

1. `last_timestamp - epoch_start_time` underflows as `u32`
2. In Rust release mode the result wraps to approximately `u32::MAX - (epoch_start_time - last_timestamp)`
3. This wrapped value exceeds `EXPECTED_EPOCH_TIMESPAN * 4`, so it is clamped to the maximum
4. The new target is computed as `current_target × 4` — a **4× easier** difficulty

Bitcoin Core uses `int64_t` for this calculation. A negative timespan is clamped to `EXPECTED_EPOCH_TIMESPAN / 4`, producing a **4× harder** difficulty — the exact opposite result.

The corrupted `current_target_bits` is then stored in `ChainState` and used to validate all subsequent blocks in the next epoch via the `bits` field check in `apply_block_headers`: [3](#0-2) 

The circuit will accept blocks with the wrong (4× easier) difficulty and reject blocks with the correct (4× harder) difficulty.

---

### Impact Explanation

The header chain circuit is the root of trust for all bridge operations. An incorrect difficulty target stored in `ChainState` causes the circuit to validate subsequent block headers against the wrong target. A chain built with the wrong (easier) difficulty would pass circuit verification while the canonical Bitcoin chain (with the correct harder difficulty) would be rejected. This enables acceptance of an invalid header-chain proof, directly affecting deposit finalization and withdrawal/challenge outcomes — matching the allowed impact of **"Acceptance of a forged or otherwise invalid header-chain proof that changes deposit, withdrawal, or challenge outcomes."**

---

### Likelihood Explanation

The trigger requires a real Bitcoin epoch where the last block's timestamp is less than the epoch-start timestamp. Bitcoin's MTP rule permits timestamps to go backwards by up to a few hours over short windows. Over 2016 blocks (~2 weeks) this is extremely rare on mainnet but is more plausible on testnet4 or signet (where block times and timestamp rules are less constrained). The bug is latent in production code and activates automatically without any attacker action if such an epoch occurs.

---

### Recommendation

Replace the plain subtraction with signed arithmetic, matching Bitcoin Core's behavior:

```rust
// Cast to i64 (matches Bitcoin Core's signed arithmetic)
let actual_timespan_signed = (last_timestamp as i64) - (epoch_start_time as i64);
let mut actual_timespan: u32 = if actual_timespan_signed < 0 {
    0 // will be clamped up to EXPECTED_EPOCH_TIMESPAN / 4
} else {
    actual_timespan_signed as u32
};
```

Alternatively, use `saturating_sub` which clamps to 0 on underflow (then the existing lower-bound clamp raises it to `EXPECTED_EPOCH_TIMESPAN / 4`):

```rust
let mut actual_timespan = last_timestamp.saturating_sub(epoch_start_time);
```

Either approach ensures a negative timespan is clamped to the minimum, matching Bitcoin Core's consensus behavior.

---

### Proof of Concept

1. Construct a 2016-block epoch where `block[2015].time < block[0].time` (valid under MTP — each block only needs to exceed the median of the previous 11 blocks).
2. Feed this epoch to `apply_block_headers`. At block 2015, `calculate_new_difficulty(epoch_start_time=block[0].time, last_timestamp=block[2015].time, ...)` is called.
3. `last_timestamp - epoch_start_time` underflows, wrapping to ~`u32::MAX`.
4. The clamping sets `actual_timespan = EXPECTED_EPOCH_TIMESPAN * 4`.
5. The new target is 4× the current target (4× easier difficulty).
6. `self.current_target_bits` is set to this wrong value and committed into `ChainState`.
7. The next epoch's blocks are validated against the wrong (easier) difficulty.
8. A chain built with this easier difficulty passes circuit verification; the canonical chain (with harder difficulty) does not.

fn calculate_new_difficulty(
    epoch_start_time: u32,
    last_timestamp: u32,
    current_target: u32,
) -> [u8; 32] {
    let mut actual_timespan = last_timestamp - epoch_start_time;
    if actual_timespan < EXPECTED_EPOCH_TIMESPAN / 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN / 4;
    } else if actual_timespan > EXPECTED_EPOCH_TIMESPAN * 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN * 4;
    }

    let current_target_bytes = bits_to_target(current_target);
    let mut new_target = U256::from_be_bytes(current_target_bytes)
        .wrapping_mul(&U256::from(actual_timespan))
        .wrapping_div(&U256::from(EXPECTED_EPOCH_TIMESPAN));

    if new_target > NETWORK_CONSTANTS.max_target {
        new_target = NETWORK_CONSTANTS.max_target;
    }
    new_target.to_be_bytes()
}
