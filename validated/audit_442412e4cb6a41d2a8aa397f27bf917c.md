## Finding

The specific proof‑of‑concept URL quoted in the question — `https://github.com/evil@github.com/owner/repo.git` — does **not** actually trigger a mismatch. Tracing the regex `^https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)(?:/|\.git/?)?$` [1](#0-0)  against that string, the greedy `(?:.+@)?` backtracks to the only `@` in the string, consuming `github.com/evil@`, leaving `github.com/owner/repo.git` for `(.+)/([^/]+)/([^/]+?)`. The regex engine then backtracks `(.+)` to the correct slash boundary and extracts `hostname="github.com"`, `owner="owner"`, `name="repo"` — which is exactly the authority a real HTTP client would connect to. So that particular example is not a valid PoC.

However, the underlying flaw the question is pointing at is real, just demonstrated with a different crafted URL. Because `(?:.+@)?` is unanchored across `/` boundaries, an `@` that appears *inside the URL path* (after the true authority component) can be mistaken for a userinfo separator, causing the regex to skip the real host and pick a fake one out of the path.

Example: `https://evil.com/x@github.com/owner/repo`
- Real URL semantics (RFC 3986): authority terminates at the first `/` after `//`, so the actual connection host is `evil.com`; `x@github.com/owner/repo` is just path.
- `parseRemote` regex: `(?:.+@)?` greedily matches `evil.com/x@` (the only `@` in the string), leaving `github.com/owner/repo`, from which `(.+)` extracts `hostname="github.com"`, `owner="owner"`, `name="repo"`.

So `parseRemote` returns `hostname="github.com"` — a value that will match the user's real, authenticated GitHub.com `Account` in `findAccountForRemoteURL` [2](#0-1)  and in `matchGitHubRepository` [3](#0-2)  — while the actual network connection for that remote is to `evil.com`.

### Title
Ambiguous `parseRemote` HTTPS regex extracts a hostname that does not match the actual connection authority - (`app/src/lib/remote-parsing.ts`)

### Summary
`parseRemote`'s HTTPS regex uses an unanchored `(?:.+@)?` that can consume text across `/` boundaries, letting an `@` embedded later in the URL path be mistaken for the userinfo separator of the real authority. This lets a crafted remote URL make `parseRemote` report a `hostname` (e.g. `github.com`) that differs from the actual host the HTTP/git client connects to (e.g. `evil.com`).

### Finding Description
The regex `^https?://(?:.+@)?(.+)/([^/]+)/([^/]+?)(?:/|\.git/?)?$` [4](#0-3)  does not restrict the optional user-info group to the authority segment (text before the first `/` after `//`). For a URL such as `https://evil.com/x@github.com/owner/repo`, RFC 3986 authority parsing yields host `evil.com`, but the regex's greedy backtracking treats `evil.com/x@` as the "user@" prefix and extracts `hostname="github.com"` from what is actually a path segment.

### Impact Explanation
The mismatched `hostname` is consumed by `findAccountForRemoteURL` [2](#0-1)  and `matchGitHubRepository` [5](#0-4) , both of which compare `parsedRemote.hostname` against configured account endpoints to decide which `Account` "owns" a remote. A crafted repository remote can therefore be associated in the Desktop UI/model with the user's real `github.com` account even though the URL's true authority is an attacker-controlled host. I was not able to verify within this session whether the actual git fetch/push credential flow (the git credential helper / askpass path) re-derives the host independently from the real URL (which would limit this to a UI/model-level mis-association) or whether it relies on the Desktop-computed `GitHubRepository`/`Account` association for supplying stored tokens — that distinction determines whether this is a UI‑only corruption of account/endpoint attribution or an actual OAuth-token/credential exposure to the wrong host. This should be confirmed by tracing how the account returned by `findAccountForRemoteURL` feeds into the actual git network authentication path.

### Likelihood Explanation
Exploitation requires the attacker to control the *remote URL string* itself (e.g. a `.git/config` `url =` value in a repository the victim opens, or a value passed through the clone dialog / deep link) — all of which are within the stated unprivileged threat model (repository content, links/deep links). No local access or credentials are required, only that the victim opens/adds the crafted remote in Desktop.

### Recommendation
Rewrite the HTTPS regex (or, better, use the platform `URL` parser) so the optional userinfo group cannot cross a `/` boundary, e.g. restrict it to `^https?://(?:[^/@]+@)?([^/]+)/([^/]+)/([^/]+?)(?:/|\.git/?)?$`, and add a regression test asserting that URLs containing `@` after the first `/` (i.e., in the path) are either rejected or parsed with the correct authority-derived hostname.

### Proof of Concept
```ts
import { parseRemote } from '../../src/lib/remote-parsing'

// Real authority per RFC 3986 is "evil.com"; "x@github.com" is path, not userinfo.
const url = 'https://evil.com/x@github.com/owner/repo'
console.log(parseRemote(url))
// => { protocol: 'https', hostname: 'github.com', owner: 'owner', name: 'repo' }
// but the actual HTTP/git connection for this URL goes to host "evil.com".
```
Note: the exact URL given in the original submitted question (`https://github.com/evil@github.com/owner/repo.git`) does **not** reproduce the bug — tracing the regex shows it correctly yields `hostname="github.com"`, matching the real authority. The reproducible mismatch requires placing the extra `@` after the *first* slash, as in the PoC above.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
