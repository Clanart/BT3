Unbounded ReceivedOutput flooding via attacker-controlled transaction outputs lacking dust/limit checks - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to CVE-2026-56324 — where a rate limit keyed on a user-controlled `device_id` was bypassed by rotating the identifier, flooding the `channel_devices` table — `Scanner::scan_transaction` performs an unbounded, unfiltered match over every output of every attacker-supplied transaction and appends a `ReceivedOutput` for each one whose `script_pubkey` is watched. A Bitcoin transaction is uniquely identified by its txid (the analog of `device_id`): an unprivileged attacker can mint an arbitrary number of distinct transactions, each carrying up to the max-standard-output-quantity of outputs paying to Serai's deposit script, and each output is unconditionally recorded as a spendable `ReceivedOutput` regardless of value, count, or duplication.

### Finding Description
`Scanner` stores watched `script_pubkey -> offset` pairs in `scripts` and `scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for every match (`networks/bitcoin/src/wallet/mod.rs:199-214`):

```rust
// networks/bitcoin/src/wallet/mod.rs:199
pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for (vout, output) in tx.output.iter().enumerate() {
    let Ok(vout) = u32::try_from(vout) else { break };
    if let Some(offset) = self.scripts.get(&output.script_pubkey) {
      res.push(ReceivedOutput { ... });
    }
  }
  res
}
```

There is:
- no minimum-value check on `output.value` — outputs at or below the `DUST` constant (`send.rs:32`, 546 sats) are recorded identically to spendable outputs;
- no cap on the number of matched outputs per transaction or per block (`scan_block` at `mod.rs:221` extends this to every tx in a block);
- no deduplication keyed on `OutPoint` — the same logical deposit can be replayed across arbitrarily many txids.

Each returned `ReceivedOutput` carries only `offset`, `TxOut`, and `OutPoint` (`mod.rs:90-97`), so downstream consumers cannot distinguish a dust flood output from a legitimate deposit. In `SignableTransaction::new` (`send.rs:150-256`), every supplied input contributes to `input_sat` and requires one `AlgorithmMachine`/signature share per input (`send.rs:273-285`, `send.rs:378-397`). An input whose value is less than the marginal vbyte cost of spending it (a Taproot input adds ~58 vbytes) is net-negative: including it in `payments + needed_fee` accounting drains funds rather than adding them, and omitting it means the recorded "received" balance can never be spent.

### Impact Explanation
- **Resource exhaustion**: the set of `ReceivedOutput`s grows unboundedly with attacker-funded transactions, mirroring the `channel_devices` table exhaustion in the reference report.
- **Funds reported received that are not spendable**: dust-level outputs are indistinguishable from real deposits, inflating the perceived balance while being economically or logically unspendable (`NotEnoughFunds` at `send.rs:215` or silent fee drain).
- **Signing amplification**: consolidating a flooded output set forces one FROST signing operation per input, turning cheap attacker outputs into expensive threshold-signing work.

### Likelihood Explanation
Any party able to broadcast a standard Bitcoin transaction can craft outputs paying to the watched `script_pubkey` (it is publicly derivable from the group key). The only cost is the dust value itself (~546 sats/output), making sustained flooding cheap. Rotating txids provides unlimited distinct "identifiers" per the analog.

### Recommendation
Enforce a minimum-value floor in `Scanner::scan_transaction`/`scan_block` (reject or quarantine outputs `<= DUST` plus the marginal input-spend fee), cap the number of matched outputs recorded per transaction/block, and deduplicate/track already-recorded `OutPoint`s so replayed transactions cannot re-insert entries.

### Proof of Concept

// An attacker builds a tx with N outputs paying to the watched script:
let mut tx = Transaction { version: Version(2), lock_time: LockTime::ZERO,

  }).collect(),
};
// scan_transaction returns N ReceivedOutputs — unbounded growth,
