### Title
`pallet-hyper-fungible-token` calldata-authorization signature omits source chain, contract identity, and transfer amount, enabling replay/hijack of a beneficiary's signed call - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`on_accept` in the HFT ISMP module lets any incoming bridge transfer carry an optional `SubstrateCalldata{signature, runtime_call}` that is dispatched under the beneficiary's own account origin once the signature is checked. The signed payload is only `(nonce, runtime_call)` — it does not bind the source chain, the specific bridge contract/module, the request/commitment, or the transferred amount, mirroring the `NodeRegistry.registerNodeFor` defect of signing data without `registryID`/contract-address binding.

### Finding Description
`on_accept` at [1](#0-0)  decodes `SubstrateCalldata` from the bridged message's `data` field and, when a `signature` is present, verifies it as `(nonce, runtime_call)` where `nonce = frame_system::Pallet::<T>::account_nonce(beneficiary)`: [2](#0-1) 

The verified call is then dispatched as `RawOrigin::Signed(beneficiary)` and the account nonce is incremented only after successful dispatch: [3](#0-2) 

The signed digest `(nonce, runtime_call).encode()` contains no reference to:
- the source `StateMachine`/contract (`source`, `from`) that originated the transfer,
- the transferred `amount` or `local_asset_id`,
- any per-request commitment/nonce unique to this specific ISMP message,
- this destination chain's own identity (module id / genesis / chain id).

The `data`/`SubstrateCalldata` bytes travel inside the public `Message` ABI payload of the cross-chain `PostRequest`, so once a beneficiary uses a signature once, the raw `(signature, runtime_call)` bytes are visible to anyone (via source-chain events or the Hyperbridge relay). Anyone can independently initiate a brand-new cross-chain transfer to the same `beneficiary` — the `send` extrinsic is a normal signed call reachable by any account, and the resulting `Message.data` is attacker-controlled — and simply copy in the previously-observed `signature`/`runtime_call` bytes. Because the only replay guard is the beneficiary's shared `frame_system` nonce (a chain-wide counter also advanced by the beneficiary's ordinary extrinsics), and because the signature never commits to which deposit/contract/amount it is supposed to be paired with, an attacker who wins the race to have their forged transfer processed while the nonce still matches can force dispatch of the beneficiary's authorized call bound to an entirely different (attacker-chosen) transfer/asset/amount, or cause it to execute twice for what was meant to authorize a single transfer.

This is the direct analog of the reported `NodeRegistry` bug: a signed authorization message lacking a domain/registry-style binding (here: source chain id, module identity, commitment) that can be resubmitted through an unprivileged, unrelated entry point (`send`) that anyone can call.

### Impact Explanation
A successful replay lets an unprivileged attacker cause the beneficiary's authorized `runtime_call` to be dispatched under `RawOrigin::Signed(beneficiary)` in a context the beneficiary never approved (paired with attacker-chosen amount/asset/source), i.e., unauthorized execution under someone else's identity — matching the bounty's "unauthorized transaction or execution" / "logic attacks" / "replay" categories. If the beneficiary's authorized call moves funds (e.g., a `transfer` or `approve`-style dispatchable), this becomes direct fund loss/misdirection for the beneficiary.

### Likelihood Explanation
Reachability requires no privileged role: any account can call `send` on the source chain's HFT contract, targeting any beneficiary with attacker-supplied `data`. The main constraint is that the beneficiary's on-chain nonce must still equal the nonce embedded in the previously observed signature, which realistically holds for inactive/fresh beneficiary accounts (nonce still 0) or for signatures replayed before the original message is delivered. This is a genuine binding-omission bug in the local codebase rather than a hypothetical relayer/prover assumption.

### Recommendation
Bind the signed payload to the specific bridge event: include the source `StateMachine`, the source contract/module id (`from`), the destination pallet's own module id, and either the exact `commitment`/request nonce or the transferred `amount`/`local_asset_id` in the signed digest, e.g. `keccak256((nonce, source, from, amount, runtime_call).encode())`. Additionally consider tracking a dedicated per-beneficiary calldata nonce (separate from `frame_system` account nonce) so ordinary user activity cannot desynchronize the check, and reject calldata execution once a request's commitment has already been consumed.

### Proof of Concept
1. Beneficiary `B` (fresh account, nonce = 0) initiates a legitimate cross-chain transfer from chain A to chain D via the HFT bridge, attaching `SubstrateCalldata { signature: sig_over(0, call), runtime_call: call }` intended to run alongside that specific deposit.
2. Before (or as) this message is delivered, an unrelated attacker `M` observes `(sig, call)` in the public `Message.data` bytes (from chain A's contract event / the ISMP payload).
3. `M` calls `send` on chain A's (or any other configured chain's) HFT contract, setting `to = B`, `amount` = an attacker-chosen value, and `data = SubstrateCalldata { signature: sig, runtime_call: call }` (byte-for-byte reused).
4. If `M`'s message reaches `on_accept` on chain D while `B`'s nonce is still 0, verification at [4](#0-3)  succeeds (the signature check does not reference `source`, `from`, or `amount`), and `call` is dispatched as `RawOrigin::Signed(B)` paired with `M`'s attacker-chosen deposit instead of `B`'s original one — or dispatched a second time if `B`'s legitimate message has not yet advanced the nonce.

Note: I was unable to find any existing test in `modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs` covering cross-message/cross-source replay of the calldata signature, which suggests this scenario is not currently guarded against or tested — a background Devin session with repository access could confirm this by inspecting the full test file contents, which the index did not return in full.
