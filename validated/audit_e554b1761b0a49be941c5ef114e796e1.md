### Title
Payout `OP_RETURN` operator attribution is unauthenticated under `SinglePlusAnyoneCanPay` — attacker can rewrite the fronting operator's identity - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs)

### Summary
`create_payout_txhandler` builds the `payout_tx` with the user's Schnorr signature restricted to `TapSighashType::SinglePlusAnyoneCanPay`, which under BIP341 only commits to input 0 (via ANYONECANPAY) and output 0 (via SIGHASH_SINGLE). The anchor output and the `OP_RETURN` output carrying `operator_xonly_pk` (added at core/src/builder/transaction/operator_reimburse.rs:418,432) are outside the signed message. `Verifier::update_finalized_payouts` (core/src/verifier.rs:2312-2342) blindly trusts whatever `operator_xonly_pk` is found in the first `OP_RETURN` of the confirmed `payout_tx`, with no check that the party who supplied that pubkey is the one who actually funded output 0.

### Finding Description
Binding claimed: `withdrawals.payout_payer_operator_xonly_pk == xonly_pk(party who funded output[0] of the confirmed payout_tx)`.

Trace:
- `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds outputs `[user_payout, anchor, OP_RETURN(operator_xonly_pk)]` and signs only input 0 with the user's key via `set_p2tr_key_spend_witness`.
- The sighash type is enforced to be `SinglePlusAnyoneCanPay` in `parse_withdrawal_sig_params` (core/src/rpc/parser/operator.rs:182-187) and in `Operator::withdraw` (core/src/operator.rs:630-637), confirmed by the taproot sighash encoder (circuits-lib/src/bridge_circuit/mod.rs:801-844): when `anyone_can_pay` is true, only input 0's prevout/value/script/sequence are hashed, and `sha_outputs` (covering all outputs) is only included for sighash types other than `None`/`Single`. Thus, for `SinglePlusAnyoneCanPay`, no output-set-wide commitment is made, and only the output at index 0 is committed (BIP341 SIGHASH_SINGLE rule).
- Because outputs 1 (anchor) and 2 (`OP_RETURN` operator pubkey) are unsigned, and additional funding inputs can be freely appended by AnyoneCanPay, any party who reconstructs a transaction with the same input 0 witness and the same output 0 can freely choose the `OP_RETURN` payload — including inserting an arbitrary xonly pubkey unrelated to who actually supplies the extra funding inputs that pay for output 0.
- `Verifier::update_finalized_payouts` (core/src/verifier.rs:2312-2342) reads the confirmed `payout_tx`, calls `get_first_op_return_output`/`parse_op_return_data` (circuits-lib/src/bridge_circuit/mod.rs:609-617, 688-692) and writes whatever pubkey is parsed into `payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk`, with no cross-check against which UTXOs/signatures actually funded output 0.
- No existing guard (`SECP.verify_schnorr` only verifies the user's own S+AP signature over input 0/output 0, not the OP_RETURN; `is_deposit_valid`/`is_profitable` run only inside the honest operator's own `withdraw()` call path, not in the verifier's block-scanning `update_finalized_payouts`) closes this gap.

### Impact Explanation
Once `withdrawal_utxo` W is spent by any transaction satisfying the S+AP signature, the recorded `payout_payer_operator_xonly_pk` can name any xonly pubkey the broadcaster chooses, independent of who actually paid for output 0. Consequences per the described categories:
- If the attacker (or a colluding/self-controlled key) writes their own pubkey while providing the actual funding, this simply reproduces the intended "operator race" mechanic (not novel).
- If the attacker writes a victim operator's pubkey while personally funding output 0, the victim operator becomes eligible for `Reimburse` via `validate_payer_is_operator`/`handle_finalized_payout` for a payout it never funded (an operator credited for a payout it did not front).
- If honest operator O had already begun fronting W and the attacker's competing transaction confirms first with a different/invalid `OP_RETURN`, W is irreversibly spent and O can never be reimbursed for that withdrawal (permanent inability to be reimbursed), and if the `OP_RETURN` is malformed/omitted, no operator can pass attribution at all, risking the associated `MoveToVault` UTXO becoming unclaimable.

I was not able to fully trace `validate_payer_is_operator`/`handle_finalized_payout` (their implementations were not retrieved within the tool budget) to confirm definitively whether a `None`/mismatched `payout_payer_operator_xonly_pk` permanently freezes the corresponding vault UTXO or whether some other reconciliation exists; this remains unverified and should be checked before treating the "frozen vault UTXO" sub-claim as certain.

### Likelihood Explanation
This requires the attacker to reconstruct output 0 exactly (same script_pubkey/value, since it's part of the SIGHASH_SINGLE commitment) and to supply, from their own funds, essentially the full value paid out in output 0 (the withdrawal input UTXO W is typically a low-value/dust marker UTXO, not the funding source — confirmed by test helper `generate_withdrawal_utxo`, core/src/test/common/setup_utils.rs:480-497, using a 550-sat dust UTXO). This makes the attack capital-intensive (cost ≈ the withdrawal amount being fronted), not a cheap griefing vector — this substantially limits practical incentive/likelihood, since the attacker gains no direct BTC profit and instead spends real capital either to gift a third party or to burn/freeze value, at a roughly 1:1 cost-to-damage ratio. It is repeatable across any withdrawal where the honest operator has not yet gotten their competing payout_tx confirmed, i.e., it is a mempool front-running window, not something exploitable after confirmation.

### Recommendation
Bind the `OP_RETURN` operator attribution into what the user actually signs, or otherwise cryptographically prove that the party named in `OP_RETURN` supplied the payout funds — e.g., require the payout transaction's non-withdrawal-UTXO input(s) to be spendable only by (or signed by) the same xonly pubkey placed in the `OP_RETURN`, and have `Verifier::update_finalized_payouts` validate that binding on-chain (checking that the additional funding input(s)' scriptPubkey/witness correspond to `operator_xonly_pk`) before writing `payout_payer_operator_xonly_pk`, rather than trusting the raw `OP_RETURN` bytes unconditionally.
