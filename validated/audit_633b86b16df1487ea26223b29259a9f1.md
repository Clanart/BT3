### Title
Stale cached FROST preprocess (nonce seed) survives across `share()`/`complete()` re-executions without binding the signing set — nonce reuse enables secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The external report concerns authorization state (`_limitPositions[tokenId]`/operator approval) persisting unchanged across an ownership transfer, so a stale grant remains usable under new conditions the new owner never consented to. The analog in Serai is the `CachedPreprocesses` table in `SigningProtocolDb`: a FROST nonce seed is persisted under a context key `(b"DkgConfirmer", attempt)` and is *not* reset or bound to the data it is later used to sign — the participant set (`serialized_preprocesses` / `included`) and the exact `msg`. `DkgConfirmer::share` and `DkgConfirmer::complete` each invoke `share_internal`, which re-derives a signing machine from the *same* cached seed and calls `machine.sign(preprocesses, msg)`. If the signing set or message at `complete()` differs from what was used at `share()`, the same private nonces `(d, e)` are spent twice under different binding factors/challenges — a classic FROST nonce-reuse secret-share leak.

### Finding Description
`preprocess_internal` writes a deterministic RNG seed to `CachedPreprocesses` keyed only by `self.context` (for `DkgConfirmer`, `(b"DkgConfirmer", attempt)`), and reuses it whenever a machine is reconstructed: [1](#0-0) 

`share_internal` then rebuilds the machine from that fixed seed and calls `sign(preprocesses, msg)` with whatever preprocesses/message are supplied at call time: [2](#0-1) 

Crucially, `DkgConfirmer::share` and `DkgConfirmer::complete` each perform a full `share_internal` (i.e., `sign`) execution: [3](#0-2) 

Inside `AlgorithmSignMachine::sign`, the binding factors `rho` and the Lagrange coefficients `lambda` are computed over `included` (the set of participants derived from the `preprocesses` map) and over the committed nonces/message: [4](#0-3) 

The nonce seed itself is regenerated *only* if the DB entry is absent; nothing incorporates the signing set or `msg` into the cache key or invalidates the seed after a `sign` call. `DkgConfirmer::new` snapshots `removed` via `removed_as_of_dkg_attempt`, and `preprocesses` come from the accumulated `ConfirmationNonces` map — neither is part of `context`.

The file's own safety argument acknowledges exactly this hazard — nonce reuse occurs "if the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" — but relies purely on BFT-finalized data being identical at both invocations, and even flags an unimplemented consistency check: [5](#0-4) 

### Impact Explanation
FROST share structure is `z_i = d_i + (e_i * rho_i) + (lambda_i * s_i * c)`. If the same `(d_i, e_i)` is signed with under two executions where `included`, `rho_i`, `lambda_i`, or `c` differ (e.g., `complete()` runs with a superset/different set of participant preprocesses than `share()`, or a different `key_pair`/`removed` message), an observer of the two published shares obtains two linear equations in the unknowns `s_i` (secret share) and `d_i + e_i*rho` — enabling recovery of the validator's private signing key share. Since these are the validators' long-lived keys used as the root of trust for confirming DKG results on-chain (Schnorrkel signatures accepted by Substrate), recovery of a threshold's worth of shares — or even degrading the scheme toward forgery — compromises the validator-set confirmation signature. This is a "key share recovery" impact, the highest-severity class listed.

### Likelihood Explanation
Reachability hinges on whether `share()` and `complete()` can legitimately observe different preprocess sets or messages under the same `(b"DkgConfirmer", attempt)` context. The preprocesses map is accumulated on-chain (`ConfirmationNonces`, `DataDb`) and is passed wholesale into `share_internal`; `complete()` re-executes `share_internal` unconditionally. Between the two calls, additional validators' preprocesses can be finalized, changing `included`, all `rho` values, and the interpolation coefficients — while the local nonce stays fixed. A validator who controls when their preprocess lands (any validator is an unprivileged signer relative to the key being leaked; no collusion or node compromise is required) can time submission so that `share()` and `complete()` run over different sets. The author's own comments concede the safety argument is incomplete ("TODO: check the commitments generated from the decided nonces are in fact its commitments on-chain"; "we also need to review how we're handling Processor preprocesses"). I was unable to fully trace the `handle.rs` accumulation flow to confirm under exactly which conditions `share` vs `complete` see divergent maps, so the exploitability rating depends on that ordering; the cryptographic flaw (nonce reuse on set/message change, uncorrected by the cache key) is unambiguous. Likelihood: Medium-conditional; severity if triggered: High (threshold key share disclosure).

### Recommendation
Bind the signing context into the cached-preprocess key the way the report recommends resetting state on change: key `CachedPreprocesses` by `context` plus a commitment to the message (`msg`) and the sorted `included` participant set, or delete `CachedPreprocesses[context]` the first time `share_internal` performs `sign` so `complete()` cannot silently re-sign under a changed set. Complementarily, implement the in-file TODO: before publishing a share, verify the commitments derived from the decided nonces equal the preprocess this validator actually published on-chain, and abort if the incoming preprocess set/message differs from the one the nonce was first used with.

### Proof of Concept
Conceptual trace (validator V, attempt `a`):
1. `DkgConfirmer::preprocess`/`share` executes `preprocess_internal`; DB stores seed `S` under `(b"DkgConfirmer", a)`; `share_internal` builds a machine with nonces `(d_V, e_V)` from `ChaCha20Rng(S)` and signs over set `I₁`, producing share `z_V^(1) = d_V + e_V·rho₁ + λ_V¹·s_V·c₁`.
2. Additional preprocesses finalize; `DkgConfirmer::complete` re-enters `share_internal`. The cache hit returns the same `S`, so `(d_V, e_V)` are identical, but `included = I₂ ≠ I₁` (or `msg` differs via `key_pair`/`removed`), yielding `z_V^(2) = d_V + e_V·rho₂ + λ_V²·s_V·c₂`.
3. With `rho₁, rho₂, λ_V¹, λ_V², c₁, c₂` all publicly computable, the two shares give two equations in `s_V` and the nonce term; solving yields `s_V = (Δz − Δ(d + e·rho)) / Δ(λ·c)` — recovering V's secret share from public on-chain data.

  3) Sign and publish the signature share.

  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
