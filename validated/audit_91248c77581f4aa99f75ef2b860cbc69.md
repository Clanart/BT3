### Title
Race condition on `knownTxs` map in gasless `PreAddTx` — write performed under a read lock - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
`GaslessModule.PreAddTx` acquires `g.knownTxsMu.RLock()` (a *read* lock) and then calls `g.knownTxs.add(tx, TxStatusQueue)`, which mutates the shared, non-thread-safe `knownTxs` map in place. This is the same bug class as the NEAR `ChunkEndorsementTracker` race (#11452): a shared mutable tracking structure is updated by a code path that does not hold an exclusive lock, so concurrent callers can race on the same map.

### Finding Description
`knownTxs` is a plain `map[common.Hash]*knownTx` (not `sync.Map`), guarded in every other method (`IsReady`, `PreReset`, `PostReset`) by `g.knownTxsMu.Lock()` (write lock): [1](#0-0) [2](#0-1) [3](#0-2) 

However `PreAddTx` — which runs on the tx-submission path for every incoming transaction — takes only `RLock()`, and then calls `g.knownTxs.add(...)`, a mutating operation that does `k[tx.Hash()] = &knownTx{...}` on the map and also updates package-level metric gauges: [4](#0-3) [5](#0-4) 

Since `RLock()` allows multiple goroutines to hold the lock concurrently, two or more transactions arriving at (nearly) the same time and both being classified as bundle txs (`g.IsBundleTx(tx)`) can enter `PreAddTx` simultaneously and both execute `g.knownTxs.add(...)` at the same time — an unsynchronized concurrent write (and read, via `numQueue()`/`get()`) to a Go map. This is undefined behavior in Go and can panic ("concurrent map writes") or silently corrupt the map (lost inserts, inconsistent `numQueue()`/`numExecutable()` counts used later by `IsReady`/pool admission bookkeeping).

### Impact Explanation
A corrupted or inconsistent `knownTxs` map affects:
- Gasless bundle-tx admission limits (`GetMaxBundleTxsInQueue` / `GetMaxBundleTxsInPending`) enforced via `numQueue()`/`numExecutable()`, which are read without synchronization guarantees if the map itself is corrupted.
- Availability: a concurrent map write panic in `PreAddTx` (invoked on every tx submission via the tx pool's `PreAddTx` hook) can crash the node process handling transaction ingestion, which is a liveness/DoS impact reachable by any unprivileged public sender submitting gasless-looking transactions concurrently.
- Potential inconsistency between what the tracker believes is queued/pending vs. actual pool state, undermining the gasless bundle admission control that is meant to bound resource usage and to correctly track lend/repay bundle state (KIP-247 gasless flow).

This does not appear to allow direct fund theft, but a crash/panic caused by an ordinary unprivileged transaction sender submitting transactions is a legitimate, concretely reachable Medium-severity issue since it can be triggered without any special privilege.

### Likelihood Explanation
`PreAddTx` is called for every transaction entering the pool, and multiple RPC callers/goroutines can submit transactions to `AddRemote(s)`/`AddLocal` concurrently. I confirmed the read-vs-write lock mismatch directly in the code, but I was unable to fully trace, within available tool budget, whether `blockchain/tx_pool.go` serializes `PreAddTx` invocations under `pool.mu`/`pool.txMu` before calling into module hooks (the pattern used elsewhere in the tx pool such as `pendingUnlocked`/`queueUnlocked`, guarded by `pool.mu` + `pool.txMu`). If the outer `TxPool` machinery already serializes all module hook calls (`PreAddTx`, `IsReady`, `PreReset`, `PostReset`) under `pool.mu.Lock()`, then this particular race would be mitigated at a higher layer, but the `RLock()` inside `PreAddTx` itself is still a latent/defense-in-depth bug: it is semantically wrong (a mutation guarded by a read lock) and would become an active concurrency bug the moment `PreAddTx` is called without the pool-level lock (e.g., from a validation/queue path or a future refactor), exactly the kind of hidden invariant violation the NEAR fix targeted.

### Recommendation
- Change `PreAddTx` to acquire `g.knownTxsMu.Lock()` (write lock) instead of `RLock()`, matching the locking discipline used in `IsReady`, `PreReset`, and `PostReset`.
- Audit all call sites of `knownTxs` methods to ensure read-only methods (`get`, `has`, `numQueue`, `numPending`, `numExecutable`, `getTimeOfOldestKnownTx`) are only ever called under `RLock`, and any method that can mutate (`add`, `addKnownTx`, `delete`) is only ever called under a full `Lock`.
- Add a `go test -race` regression test that concurrently calls `PreAddTx` with multiple bundle-classified transactions to catch this class of bug in CI, similar in spirit to `tests/race_test.go`'s `TestRaceBetweenTxpoolAddAndCommitNewWork` already present in this repo.

### Proof of Concept
1. Configure a gasless module (`GaslessConfig.MaxBundleTxsInQueue` > 1) and register it on a `TxPool` as in `kaiax/gasless/impl/tx_pool_test.go`.
2. From N goroutines, concurrently call `pool.AddRemote(bundleTx_i)` (or directly `g.PreAddTx(bundleTx_i, false)`) for N distinct gasless approve/swap transactions from different senders, so each is classified `IsBundleTx == true` and reaches the `g.knownTxs.add(tx, TxStatusQueue)` call inside the `RLock()`-protected section simultaneously.
3. Run with `go test -race`: the Go race detector flags the concurrent map write in `knownTxs.add` (`kaiax/gasless/impl/tx_counter.go:53`), and without `-race`, repeated runs can trigger a `fatal error: concurrent map writes` panic or produce a `knownTxs` map with missing/duplicate entries, corrupting the bundle-tx admission counters. func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

type knownTxs map[common.Hash]*knownTx

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}
