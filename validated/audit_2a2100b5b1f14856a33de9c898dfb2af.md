### Title
Unbounded recursive parsing of attacker-controlled `PuzzleWithRestrictions` memo causes Python stack overflow / wallet DoS - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
The reported Expat CVE is a C stack overflow caused by unbounded recursive parsing of a deeply nested, attacker-supplied structure. The closest reachable analog in this codebase is `PuzzleWithRestrictions.from_memo()`, which recursively parses a CLVM `Program` memo with no depth limit. Because this memo is sourced from a `CREATE_COIN` condition's hint/memo field — data fully controlled by whoever creates the coin — a wallet that processes such a coin (e.g. via the PlotNFT/pool-singleton sync path) can be driven into unbounded Python recursion.

### Finding Description
`PuzzleWithRestrictions.from_memo()` recursively reconstructs a custody structure from a CLVM program: [1](#0-0) 

When the memo encodes an `MofN` component (`further_branching` is true), the function recurses once per member via a list comprehension, and each member's memo can itself encode another `MofN`, allowing arbitrarily deep nesting: [2](#0-1) 

There is no maximum-depth check, and no bound on `len(m_of_n_hint.member_memos)` combined with nesting depth versus CLVM cost — the memo is just a `Program` (an s-expression) that can be crafted to nest thousands of `MofN` layers cheaply, since constructing the memo bytes is far cheaper than the recursive Python call this induces at parse time.

This function is invoked when the wallet reconstructs pool/plotnft state from an on-chain coin spend's memo, treating it as untrusted input from any coin creator: [3](#0-2) 

That code path is reached from `get_next_from_coin_spend`, which is used by wallet sync logic to interpret arbitrary singleton coin spends that look like PlotNFT/pool singletons, meaning any spend that creates a coin with a crafted `memo_blob` mimicking this shape can trigger the recursive parse.

This mirrors the CVE's bug class exactly: a parser with a handler that recurses once per level of an attacker-supplied nested definition, with no recursion-depth cap, leading to stack exhaustion.

### Impact Explanation
Python's default recursion limit (typically ~1000) combined with unbounded `from_memo` recursion means a sufficiently deep memo triggers a `RecursionError` (or, in pathological cases with C-extension frames involved via `Program`/CLVM object attribute access, a genuine C stack overflow crashing the process) in the wallet process parsing the coin state. Since this runs inside wallet sync/state-reconstruction logic, a single malicious coin (creatable by any unprivileged spend-bundle submitter) can crash or hang the victim wallet's parsing loop whenever that wallet observes the coin — a spend-triggered transaction-processing halt affecting wallet availability. This is a Denial-of-Service on the wallet's ability to process further state, which the task's Validate criteria explicitly accepts ("a spend-triggered transaction-processing halt").

### Likelihood Explanation
Likelihood is high for wallets that actively track pool/plotnft or custody-based coins: any address controlled by an attacker can create a coin whose `CREATE_COIN` memo encodes a deeply nested `MofN` hint tree; no signature or special privilege is needed to construct and broadcast such a spend, only that some victim wallet later processes/syncs the coin. Whether every default wallet configuration processes memos this way for arbitrary incoming coins (versus only when the coin is already recognized as a PlotNFT wallet) was not fully confirmed in the available context; the `plotnft_wallet.py` call sites were not resolved from the codebase index within available time. This is worth Devin verifying with full repo access before treating it as a confirmed high-severity issue.

### Recommendation
Add an explicit recursion/nesting depth limit (and/or an iterative parser using an explicit stack, similar to the existing `sha256_treehash` pattern in `chia/types/blockchain_format/tree_hash.py`) to `PuzzleWithRestrictions.from_memo()`. Reject memos whose `MofN` nesting exceeds a small sane bound (e.g., matching realistic custody configurations) before recursing, and validate `member_memos` length against a maximum member count.

### Proof of Concept
Conceptual PoC (not executed):
1. Construct a `Program` memo of the form `("CHIP-0043", [0, [], 1, [1, [<memo>, ...]]])` where the `MofN` hint recursively nests another such memo as its single member, to depth N (e.g., N = 5000).
2. Attach this memo as the `memo_blob` on a `CREATE_COIN` condition of a spend bundle creating a singleton-shaped coin that a victim wallet will attempt to interpret via `PlotNFT.get_next_from_coin_spend` (or any code path invoking `PuzzleWithRestrictions.from_memo`).
3. Submit the spend bundle to the mempool; once included and observed by the victim wallet during sync, `from_memo` recurses N times reconstructing the `MofN` tree, exhausting the Python call stack and raising `RecursionError`/crashing the wallet sync task. [1](#0-0) [3](#0-2)
