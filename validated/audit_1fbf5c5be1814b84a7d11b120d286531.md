### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` allows stack-overflow DoS when parsing untrusted on-chain `MofN` custody memos - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a custody/`MIPSComponent` tree from an arbitrary CLVM `Program` memo taken from a coin's `CREATE_COIN` memo field. When the memo indicates a nested `MofN` structure, the method recurses into itself once per member, with no depth limit. An attacker who controls a spend's `CREATE_COIN` memo (e.g. a pool/plotnft counterparty, or any spend a wallet later syncs) can nest `MofN` hints arbitrarily deep, exhausting the Python call stack and crashing/raising an uncaught `RecursionError` in the parsing client.

### Finding Description
`from_memo()` is a `classmethod` that parses a `Program` memo without validating structural depth: [1](#0-0) 

Specifically, when `further_branching_prog` is truthy, the code does:
```
m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
puzzle: MIPSComponent = MofN(
    m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
)
```
Each `member_memo` can itself encode a further `MofN` hint, and this call recurses into `PuzzleWithRestrictions.from_memo()` again for every nested member with no maximum-depth or iteration-count check. There is no CLVM cost accounting or Python recursion-guard at this parsing layer — it operates purely on a decoded `Program` tree taken directly from chain data.

This is directly reachable from a genuinely untrusted/attacker-supplied artifact: the `memo_blob` of a `CREATE_COIN` condition inside a spend bundle/coin spend. One concrete call site is plotnft/pool syncing: [2](#0-1) 

Here, `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` is invoked directly on the memo of a coin created by any spend the plotnft/pool wallet observes while syncing plotnft/pool state — an operation driven by chain data that a spend-bundle submitter fully controls (the memo argument of `CREATE_COIN`). Nothing in the mempool/consensus layer constrains the logical nesting depth of an arbitrary `Program` memo tree beyond overall CLVM cost/size limits, which are far larger than what is needed to exceed Python's default recursion limit (~1000 frames) with a single, cheap, deeply right-nested list.

This closely matches the bug class in the reference CVE: `CIccBasicStructFactory::CreateStruct()` recursively parses an untrusted, self-describing structure with unconstrained nesting, causing native/interpreter stack exhaustion. `PuzzleWithRestrictions.from_memo()` is the Chia analog: a factory-style recursive parser reconstructing a nested `MofN`/`PuzzleWithRestrictions` object graph directly from attacker-controlled serialized data, with unbounded recursion depth.

### Impact Explanation
An attacker can construct a coin (e.g. in a plotnft/pool related spend, or any custody-architecture-memoized coin) whose `CREATE_COIN` memo encodes deeply nested `MofN` hints. When a wallet or plotnft/pool client later parses this memo via `from_memo()` while syncing state for that coin, it triggers a Python `RecursionError`. Because this call is not guarded by a try/except for `RecursionError` (only `ValueError` is caught by the caller in `plotnft_drivers.py`), the exception propagates and can crash or halt the wallet's/pool-client's coin-sync / transaction-processing flow, denying that wallet's ability to process subsequent state for the affected puzzle path. This is a reachable, spend-triggered processing-halt condition consistent with the "Medium" severity of the source CVE (uncontrolled recursion / stack exhaustion causing crash), not a privilege-escalation or funds-theft bug.

### Likelihood Explanation
Likelihood is moderate-to-high for any code path that calls `PuzzleWithRestrictions.from_memo()` on chain-observed memos, since:
- The memo content is fully attacker-controlled (it is written by whoever creates the coin with that `CREATE_COIN` condition).
- No cost/size gate exists at this parsing layer beyond generic CLVM condition-count/cost limits, which are not remotely tight enough to prevent reaching Python recursion limits with a cheap, deeply nested list structure.
- The known call site (`chia/pools/plotnft_drivers.py`) is exercised during normal pool/plotnft wallet sync of externally-created coins.

### Recommendation
Add an explicit maximum nesting-depth check (or convert `PuzzleWithRestrictions.from_memo()` / the `MofN` branch to an iterative, stack-based parser) before recursing into nested `MofN` member memos, rejecting memos that exceed a sane depth (e.g. matching whatever depth the custody puzzles chialisp itself supports). Also wrap/guard the recursive parse so a `RecursionError` is converted into a handled `ValueError` (as with other malformed-memo cases) rather than propagating and crashing the caller.

### Proof of Concept
Conceptually (cannot execute code in this environment, but the path is direct from the source above):
1. Construct a `MofNHint` whose `member_memos` list contains one `PuzzleWithRestrictions` memo, itself encoding another `MofN` hint, nested N times (N > ~1000, well within CLVM program size/cost budgets for a simple list-of-one-element repeated structure).
2. Serialize this as the `memo` of a `CREATE_COIN` condition in a spend bundle, and get that coin created (e.g. via a plotnft-related singleton spend or any custody-architecture coin the target wallet will later sync).
3. When the victim wallet/pool client processes that coin via `PlotNFT.get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())`, the recursive parsing in `from_memo()` exceeds Python's stack/recursion limit, raising an unhandled `RecursionError` that is not caught by the `except ValueError` clause, crashing/halting the client's coin-processing.
