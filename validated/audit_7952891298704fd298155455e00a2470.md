## Summary

The seed report's core broken invariant is: **an external call is made before per-account/per-share accounting is finalized, and the finalization logic does not re-verify that the state it is about to write is still consistent** — allowing the same escrowed value to be paid out and only "corrected" afterward, when it's already too late.

The closest, directly provable local analog is in the Tron fork of the Intent Gateway, `evm/tron/contracts/apps/IntentGatewayV2.sol`. Its `withdraw()` function reintroduces the exact Checks-Effects-Interactions violation that the mainline EVM `IntentsBase._withdraw` was hardened against (as documented by the project's own `IntrinsicIntentsReentrancyTest.sol` regression suite), and it additionally omits the “already filled” guard that the sibling `cancelOrder()` function relies on.

### Title
Escrow accounting decremented *after* the token transfer in `IntentGatewayV2.withdraw()` (Tron fork) — CEI regression vs. the hardened mainline contract - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Finding Description
In the mainline, hardened implementation, `IntentsBase._withdraw` decrements escrow **before** making the external transfer: [1](#0-0) 

The Tron fork's `withdraw()` does the opposite — it performs the external call/transfer first and only decrements `_orders[commitment][token]` afterward: [2](#0-1) 

The per-iteration guard is also weak: it only checks `_orders[body.commitment][token] == 0` (existence), never that the escrowed balance is *sufficient* for `amount`, mirroring the seed report's flawed `revoke()` logic that "assumes missing shares were consumed" rather than validating the actual balance before finalizing.

In addition, unlike `cancelOrder()` — which explicitly guards against double-processing with `if (_filled[commitment] != address(0)) revert Filled();` — `withdraw()` itself never checks whether `_filled[body.commitment]` was already set before unconditionally overwriting it and re-running the escrow payout loop: [3](#0-2) 

`withdraw()` is reached from `onAccept` (RedeemEscrow / RefundEscrow) and `onGetResponse`: [4](#0-3) [5](#0-4) 

This is the exact structural pattern the seed report exploited in `CollateralTracker`: an unsafe external call precedes the accounting write, and the accounting write itself doesn't independently re-validate correctness — it just trusts the pre-call state.

### Impact Explanation
If the corrupted value (`_orders[commitment][token]`) can be read twice before it is decremented — via any code path that reaches `withdraw()` a second time for the same commitment before the first call's decrement executes — an attacker-controlled beneficiary (attacker fully controls `order.user`/`beneficiary` since they create their own order) can receive the same escrowed token/ETH allocation more than once, draining `CollateralTracker`-equivalent escrow (the `IntentGatewayV2` vault balance) beyond what was actually deposited for that order. This is a direct "stealing or loss of funds" / "duplicate/double-settlement" outcome as required by the bounty scope.

### Likelihood Explanation
Exploitability strictly depends on whether the Host's message-delivery layer (`onlyHost`-gated `onAccept`/`onGetResponse`) permits a second, still-unreceipted message for the same commitment to be processed while the first `withdraw()` call is still inside its external-call/decrement window (e.g., a RedeemEscrow and a RefundEscrow message both outstanding for the same commitment, or a callback-driven re-entry into the permissionless handler mid-transfer). I was not able to fully trace the Host's per-message receipt timing for POST message delivery within the remaining investigation budget to confirm or rule out this window with certainty — the code evidence for the CEI-order defect and missing double-processing guard inside `withdraw()` itself is solid, but end-to-end unprivileged exploitability through the Host dispatch path is not fully verified here.

### Recommendation
- In `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`, decrement `_orders[body.commitment][token]` **before** performing the native/ERC-20 transfer, matching the CEI pattern already applied in `IntentsBase._withdraw`.
- Add an explicit `if (_filled[body.commitment] != address(0)) revert Filled();` guard at the top of `withdraw()` itself (not only in `cancelOrder`), so it cannot be invoked twice for the same commitment regardless of which caller path reaches it.
- Change the per-token check from `== 0` (existence) to `< amount` (sufficiency) to prevent any payout that exceeds the actual escrowed balance.

### Proof of Concept
Concrete PoC requires confirming the exact receipt-timing of the Host's POST-message dispatch path (whether `_requestReceipts`/equivalent is set before or after invoking `onAccept`) to demonstrate the double-invocation window; that verification was not completed in this session. The structural defect itself (transfer-before-decrement, missing `_filled` guard in `withdraw`) is directly reproducible by inspecting `evm/tron/contracts/apps/IntentGatewayV2.sol:682-721` against `evm/src/apps/intentsv2/IntentsBase.sol:390-425`, and a Foundry test analogous to `IntrinsicIntentsReentrancyTest.sol` (armed malicious beneficiary reentering during the native-token leg of `withdraw`) is the natural next step to confirm end-to-end exploitability.
