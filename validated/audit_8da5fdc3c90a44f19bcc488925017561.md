Based on my investigation, I found a genuine structural analog of the "double-vote" bug class in Hyperbridge's ISMP request-handling pipeline, not a copy of the governance bug itself.

### Title
Non-atomic `on_accept` retry after receipt deletion allows re-application of partial module state changes on request resubmission - (File: `modules/ismp/core/src/handlers/request.rs`)

### Summary
The double-vote report's core defect is that the same underlying value (Alice's stake) gets counted a second time because a state transition (delegation) happens between two "counting" events without invalidating the first count. Hyperbridge's inbound POST-request handler has the same shape of flaw: a module's `on_accept` callback can mutate pallet storage, then fail later in the same call; the handler's failure-recovery path erases the very guard (`request_receipt`) that is supposed to prevent the request from being processed twice, and the outer extrinsic still returns `Ok`, so nothing rolls the partial mutation back. A resubmission of the identical, already-verified request can then re-run `on_accept` and re-apply whatever it already committed.

### Finding Description
In `handle()`: [1](#0-0) 

the flow per request is:
1. `store_request_receipt` marks the request as "being processed" **before** the callback runs.
2. `cb.on_accept(request.clone())` (the destination module, e.g. pallet-bandwidth, TokenGateway, Intents-Coprocessor, etc.) executes.
3. If `on_accept` returns `Err`, `host.delete_request_receipt` deletes that guard "so it can be timed out."

The comment at lines 103-107 explicitly acknowledges the receipt is the only defense against double-invocation within a batch, but only re-checks it *before* the callback — it does nothing to undo storage writes a callback already made before it returned `Err`.

Crucially, the outer function always returns `Ok(MessageResult::Request { events: result, weight })` regardless of whether individual per-request results are `Err`: [2](#0-1) 

Because the top-level dispatchable call succeeds, Substrate's automatic transactional-storage rollback (which only reverts state when the *outer* call returns an `Err`) never triggers. Any storage mutation a module made **before** it hit its failing step is permanently committed, while the receipt that would block reprocessing is deleted — leaving the request fully replayable.

This is architecturally identical to the double-vote bug's invariant break: a value is "counted" (module state mutated) at time T1, then a later event (the receipt deletion) removes the record that should prevent counting it again, and a second, entirely legitimate-looking submission (a relayer resubmitting the same proof/request, well within the request's validity/challenge window) re-triggers the counting a second time.

I verified this is a systemic gap in the router-level guard rather than a per-module bug: no `#[transactional]` / `with_storage_layer` wrapper exists around the `cb.on_accept()` call site, and the only occurrence of "transactional" in the whole codebase is unrelated to this call path. [3](#0-2) 

I checked `pallet-bandwidth`'s `on_accept` specifically, since it is the clearest "credit a balance" module in this repo: [4](#0-3) 
There, every fallible step (`ok_or_else`, `try_from`) happens *before* the only storage mutation, `push_subscription` (which is infallible). So this particular module is safe today, but only by ordering coincidence, not by any protocol-level guarantee — any module callback (present or future) that performs a storage write and *then* has a later fallible step (e.g., a forward-dispatch, a second external call, a cross-module lookup after crediting) inherits this exposure through the shared handler.

### Impact Explanation
If any registered ISMP module's `on_accept` mutates protocol state (mints tokens, credits an allowance, marks an order filled, releases escrow) before a later step that can fail, the described replay path yields a duplicate application of that mutation for a single, once-delivered cross-chain message — i.e., double-crediting, double-minting, or double-settlement without any second corresponding burn/lock/payment on the source chain. This falls squarely under "stealing or loss of funds" / "replay/double-claim/double-settlement" / "false proof/state acceptance," since the second execution is accepted as valid state transition despite the underlying cross-chain event having occurred only once.

### Likelihood Explanation
The trigger does not require a malicious relayer, prover, or admin — only that the identical, already-membership-proven request be resubmitted (a normal retry a relayer would naturally do after an apparent partial failure, or that any unprivileged submitter of the unsigned/permissionless `handle_messages`-style extrinsic could deliberately repeat). The precondition (a module whose `on_accept` writes state before a later fallible branch) is plausible for any module beyond the one audited here (`pallet-bandwidth`), especially ones with multi-step effects (mint-then-forward, credit-then-notify, escrow-then-external-call).

### Recommendation
Wrap each per-request `cb.on_accept(...)` invocation in an explicit transactional storage layer (e.g. `frame_support::storage::with_storage_layer`) so that any storage mutation the module performs is rolled back atomically whenever the callback ultimately returns `Err`, before the receipt is deleted. This restores the invariant "one receipt insertion = at most one committed state effect," removing the need to reason about ordering-of-fallible-steps inside each module implementation.

### Proof of Concept
1. Register (hypothetically, or via any future module) an ISMP module whose `on_accept` performs a storage credit/mint as its first effect and a later fallible operation (e.g., a nested dispatch) as a subsequent step.
2. Relayer submits a valid `RequestMessage` batch containing one such request; membership proof passes, `store_request_receipt` records it, `on_accept` credits the balance, then fails on the later step.
3. Handler catches the `Err`, calls `host.delete_request_receipt`, and the outer `handle()` still returns `Ok(..)`, so the extrinsic succeeds and the credit already applied is retained.
4. The relayer (or anyone) resubmits the exact same `RequestMessage` (still valid — membership proof against the same finalized state, no request-level nonce reuse check beyond the deleted receipt).
5. `host.request_receipt(&wrapped_req).is_none()` now (it was deleted), so the duplicate check at line 108 passes, `on_accept` runs again, crediting the balance a second time for what was a single source-chain event. [5](#0-4) [6](#0-5)

	let result = msg
		.requests
		.into_iter()
		.map(|request| {
			let wrapped_req = Request::Post(request.clone());
			let mut lambda = || {
				let cb = router.module_for_id(request.to.clone())?;
				// Re-check the receipt right before dispatch. The up-front pass above
				// runs before any callback executes; a prior request's on_accept in
				// this same batch could have stored a receipt for this request
				// (directly or by re-entering the handler), and we must not invoke
				// on_accept a second time.
				if host.request_receipt(&wrapped_req).is_some() {
					Err(Error::DuplicateRequest { meta: wrapped_req.clone().into() })?
				}
				// Store request receipt to prevent reentrancy attack
				let signer = host.store_request_receipt(&wrapped_req, &msg.signer)?;
				let res = cb.on_accept(request.clone()).map(|weight| {
					total_weights.saturating_accrue(weight);

					let commitment = hash_request::<H>(&wrapped_req);
					Event::PostRequestHandled(RequestResponseHandled {
						commitment,
						relayer: signer,
					})
				});
				// Delete receipt if module callback failed so it can be timed out
				if res.is_err() {
					host.delete_request_receipt(&wrapped_req)?;
				}
				Ok(res)
			};

			let res = lambda().and_then(|res| res);
			res
		})
		.collect::<Vec<_>>();

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
