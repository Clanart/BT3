### Title
Missing binding/authorization on PedPoP registration encryption key allows a participant to claim another's `enc_key`, leaking victims' secret shares - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
Analogous to the BigBlueButton report (a write operation accepted without verifying the submitter is authorized for the claimed identity), `Decryption::register` / `Encryption::register` accepts an `EncryptionKeyMessage` containing an arbitrary `enc_key` with no proof that the claimed participant owns its discrete logarithm. The Schnorr PoK in `generate_coefficients` covers only the commitments (`cached_msg`), never the encryption key. A malicious participant can register a victim's encryption public key as their own, causing all honest parties to encrypt that participant's secret shares to a key the *victim* owns — but since the ciphertext shares are transported on a channel the attacker-defined registry governs, anyone holding the key's secret (or the victim, or any observer of a subsequent blame proof) can decrypt shares intended for the attacker-indexed slot, collapsing threshold security.

### Finding Description
In `KeyGenMachine::generate_coefficients`, the proof-of-knowledge is computed as `challenge(context, i, nonce, cached_msg)` where `cached_msg` is built only from the coefficient commitments (`crypto/dkg/pedpop/src/lib.rs:163-184`). The broadcast message wraps those commitments together with `enc_pub_key` via `Encryption::registration` (`encryption.rs:448-450`), but the `enc_key` field is not covered by the signature.

On receipt, `SecretShareMachine::verify_r1` calls `self.encryption.register(l, msg)` (`lib.rs:315`), which stores `msg.enc_key` as participant `l`'s encryption key with no proof-of-possession and no uniqueness check. The batch verification (`lib.rs:323-334`) only verifies the PoK over the commitments, not over `enc_key`. Later, `Encryption::encrypt` (`encryption.rs:460-467`) encrypts each secret share to `self.decryption.enc_keys[&participant]` — the unauthenticated, attacker-substitutable key.

Contrast with the per-message key, which *does* carry a PoP bound to sender and message (`encryption.rs:91`, `302-324`) precisely because the authors recognized the "claim another's key" attack class — yet the long-lived registration key that actually decrypts shares has no such binding.

### Impact Explanation
A malicious participant Eve registers Alice's `enc_pub_key` (public data) as Eve's own. Every honest party encrypts the share intended for index `Eve` under Alice's key (`encrypt`, `encryption.rs:154`). Where DKG messages are relayed/broadcast (e.g., posted to a shared medium, as in Serai's coordinator usage), Alice — an unprivileged party — can compute `ecdh(alice_enc_key_priv, msg.key)` and decrypt Eve's share (`cipher`, `encryption.rs:101-133`). Alice thereby accumulates additional shares; combined with her own and any legitimately-obtainable set reaching `t` distinct evaluations of the summed polynomial, the full group private key is recoverable — i.e., key share recovery / total threshold collapse from public inputs only. Even absent disclosure of the shares' channel, Eve can selectively cause shares-to-Eve to be decryptable by Alice, and the mis-binding is invisible to `verify_r1` and to `calculate_share` blame attribution.

### Likelihood Explanation
The attack requires only one malicious DKG participant submitting a crafted `EncryptionKeyMessage` — exactly the "viewer injects data under an unauthorized identity" class of the reference CVE. All inputs (`enc_key`, commitments, PoK) are attacker-controlled bytes to `read`/`register`. No collusion, leaked keys, or broken transport is needed beyond observability of the share ciphertexts, which the protocol's blame design already assumes may be published (`spec/cryptography/Distributed Key Generation.md:19-35`).

### Recommendation
Bind the encryption key into the authenticated registration: extend `cached_msg`/the PoK `challenge` to include `enc_key.to_bytes()` in `generate_coefficients` and `verify_r1`, so the Schnorr signature authorizes the `(participant, commitments, enc_key)` tuple. Additionally, have `Decryption::register` reject duplicate `enc_key` values across participants.

### Proof of Concept
1. Alice and Eve run `KeyGenMachine::generate_coefficients`; Alice broadcasts `{Commitments_A, enc_key_A}`.
2. Eve broadcasts `{Commitments_E, enc_key: enc_key_A}` with a valid PoK over `Commitments_E` — `verify_r1` accepts it because the challenge never references `enc_key` (`lib.rs:328`).
3. Every honest party `p` calls `encrypt(rng, Eve, share_p(Eve))` → ECDH key `enc_key_A * k` (`encryption.rs:154`), so the ciphertext is readable by Alice.
4. Alice reads the relayed `EncryptedMessage` for Eve, computes `ecdh(enc_key_priv_A, msg.key)`, runs `cipher` (`encryption.rs:101-133`), and recovers `share_p(Eve)` for every `p`, plus Eve's self-share derivable from the public commitments — yielding enough evaluations of the Pedersen-sum polynomial to reconstruct the group secret.
