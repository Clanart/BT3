### Title
MuSig key aggregation accepts the identity point as a participant public key, allowing the corresponding signer slot to be bypassed by anyone - (File: crypto/dkg/musig/src/lib.rs)

### Summary
`check_keys` (the "constructor-level" input validation for the MuSig n-of-n DKG, analogous to the missing zero-address checks in the external report) validates that the key list is non-empty, fits in `u16`, and contains no byte-identical duplicates — but it never rejects the group identity element. `Ciphersuite::read_G` also accepts identity; only `Curve::read_G` (used by the FROST signing layer) explicitly rejects it, showing the codebase recognizes identity rejection as necessary. A participant who registers the identity point as their public key produces a `ThresholdKeys` with `secret_share = 0`, whose signature share is publicly computable — collapsing the declared n-of-n policy to (n-1)-of-n for the remaining signers without the identity participant's involvement.

### Finding Description
In `check_keys` (crypto/dkg/musig/src/lib.rs:46-63), each key is only checked for byte-uniqueness via `set.insert(bytes)`; there is no `key.is_identity()` check. `musig` then locates the caller's key via `keys.iter().position(|key| *key == our_pub_key)` where `our_pub_key = generator() * private_key` — a private key of `0` yields `our_pub_key = identity`, which is present if the attacker registered identity (crypto/dkg/musig/src/lib.rs:121-124). `musig_key_multiexp` computes the group key as `Σ binding_factor_i · keys_i`, so the identity key contributes nothing (crypto/dkg/musig/src/lib.rs:93-96). `ThresholdKeys::new` (crypto/dkg/src/lib.rs:347-391) checks share count and participant ranges but never verifies `secret_share * generator() == verification_shares[i]`, so a zero share paired with an identity verification share is accepted. During FROST signing, `Interpolation::Constant` multiplies the share by the public binding factor: `b_i · 0 = 0`, and the interpolated verification share is `b_i · identity = identity` (crypto/dkg/src/lib.rs:228). The resulting signature share `d + ρe + c·0` verifies against nonce commitments alone — i.e., it is computable by anyone who observes the preprocess. Contrast: `Curve::read_G` rejects identity at crypto/frost/src/curve/mod.rs:125-131, but `check_keys` never invokes an equivalent check, and `Ciphersuite::read_G` at crypto/ciphersuite/src/lib.rs:91-101 accepts identity.

### Impact Explanation
The MuSig construction is documented as "n-of-n" (crypto/dkg/musig/src/lib.rs:115). With an identity participant, that signer's interpolation-weighted secret share is 0 and their signature share reduces to the publicly-bound nonce term, so the remaining n-1 participants can produce valid signatures under the group key with no secret held by — and no cooperation from — the identity slot. This is a threshold-policy bypass / unintended-signature condition: the declared signer set is not actually required. The group key itself silently excludes the rogue entry, so the misconfiguration is invisible in `group_key()`.

### Likelihood Explanation
Requires one participant in a MuSig aggregation to submit the identity encoding (a canonical, well-formed point that passes all existing checks). The keys list is externally supplied peer data — no collusion, leaked secrets, or trusted-party failure is needed. Exploitation is deterministic once the malformed key is accepted, since `musig(context, Zeroizing::new(F::ZERO), keys)` always succeeds when identity is in the list.

### Recommendation
In `check_keys` (crypto/dkg/musig/src/lib.rs:46), reject `key.is_identity()` for every element of `keys`, returning a new `MusigError` variant. Additionally, consider a defense-in-depth check in `ThresholdKeys::new` that `secret_share` is non-zero and `C::generator() * secret_share == verification_shares[&params.i()]`, which would catch inconsistent share/share-commitment pairs regardless of the calling DKG.

### Proof of Concept
```rust
use zeroize::Zeroizing;
use rand_core::OsRng;
use dkg_musig::{musig, musig_key};
use ciphersuite::{group::Group, Ciphersuite};
use dkg::Participant;
// e.g. Ristretto/dalek-ff-group as C

// Honest participant key
let honest_priv = Zeroizing::new(<C as Ciphersuite>::F::random(&mut OsRng));
let honest_pub = C::generator() * *honest_priv;

// Malformed slot: identity public key, accepted by check_keys
let keys = vec![honest_pub, C::G::identity()];

// Succeeds: no identity rejection in check_keys
let group_key = musig_key::<C>(context, &keys).unwrap();
// group_key == binding_factor(1) * honest_pub; the identity term contributes 0

// The identity holder runs musig with private_key = 0 and is accepted,
// because keys.position(identity) is found and ThresholdKeys::new does not
// check share == generator() * secret_share
let attacker_keys =
  musig::<C>(context, Zeroizing::new(C::F::ZERO), &keys).unwrap();
assert_eq!(*attacker_keys.original_secret_share(), C::F::ZERO);
```
During signing, this participant's `view.secret_share()` is `b_i * 0 = 0` and `view.verification_share(i)` is `identity`, so their `SignatureShare` `s = d + ρe` verifies with no secret — any observer of the preprocess can supply it, letting the other n-1 signers complete signatures unilaterally.

Note on uncertainty: whether downstream consumers ever call `musig`/`musig_key` with peer-supplied key lists containing an untrusted identity encoding is an integrator-level question; the cryptographic flaw — missing identity validation in the aggregation input check — is present in the in-scope code itself.
