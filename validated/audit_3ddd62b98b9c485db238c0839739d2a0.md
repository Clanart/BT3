### Title
Non-injective outpoint→withdrawal binding lets one payout satisfy two withdrawal intents - (File: core/src/database/verifier.rs, core/src/operator.rs)

### Summary
`get_reimbursement_txs` decides whether an operator is owed a reimbursement for a deposit by looking up `payout_payer_operator_xonly_pk`/`payout_tx_blockhash`/`kickoff_txid` for that deposit's `withdrawals` row via `validate_payer_is_operator` / `get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id`. Those columns are populated by `get_payout_txs_for_withdrawal_utxos`, which matches a spent Bitcoin UTXO to a withdrawal solely by `(withdrawal_utxo_txid, withdrawal_utxo_vout)` equality rather than by the Citrea withdrawal index. Since the withdrawal UTXO bytes registered on Citrea are fully attacker-chosen, an unprivileged withdrawer can register the identical outpoint for two different withdrawal/deposit indices, causing a single real payout transaction to be recorded as having paid both withdrawals.

### Finding Description
The binding the system relies on is: `spending_txid(outpoint O) ⇒ exactly one withdrawal idx`, i.e. the map `(txid, vout) -> idx` must be injective. In practice this map is attacker-controlled, because Citrea's `withdrawalUTXOs[idx]` is set directly from the bytes the withdrawer submits to `withdraw()`, with no requirement that the registered UTXO be unique across indices.

`get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) implements the reverse lookup for a spent Bitcoin block:
```
SELECT w.idx, bsu.spending_txid
FROM withdrawals w
JOIN bitcoin_syncer_spent_utxos bsu
   ON bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout
WHERE bsu.block_id = $1
``` [1](#0-0) 

This is called from `update_finalized_payouts` in `core/src/verifier.rs`, which for every `(idx, payout_txid)` returned writes the same `payout_txid`, `operator_xonly_pk` (parsed from the payout tx's OP_RETURN) and `block_hash` into every matching row via `update_payout_txs_and_payer_operator_xonly_pk`: [2](#0-1) 

If an attacker registers the same withdrawal UTXO `O` for two different Citrea withdrawal indices (e.g. two of the attacker's own deposits A and B, each redeemable at its paired index, per the same-index deposit/withdrawal storage layout confirmed in `verify_storage_proofs`, `circuits-lib/src/bridge_circuit/storage_proof.rs:44-133`), then when an operator legitimately services withdrawal A by spending `O` in a payout tx, the JOIN above returns **both** idx A and idx B rows for that single spend. Both rows get stamped with the servicing operator's xonly pubkey and the payout's block hash/txid.

`get_reimbursement_txs` (`core/src/operator.rs:2098-2150`) for deposit B then calls `validate_payer_is_operator`, which reads exactly these forged columns via `get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id` (`core/src/database/verifier.rs:315-346`), and will find that the operator "paid" B - even though the operator's payout transaction never funded B's withdrawer. `get_reimbursement_txs` will then proceed to walk the round/kickoff/reimburse transaction sequence for deposit B as if it were legitimately serviced.

Why guards fail: the on-chain bridge circuit (`circuits-lib/src/bridge_circuit/mod.rs`) checks storage proofs per `storage_proof.index`, confirming `withdrawalUTXOs[index] == O` and that `O` was spent by the payout SPV transaction - both of which are literally true for B as well, because the attacker genuinely registered `O` at index B on Citrea. Nothing in `verify_storage_proofs`, `SPV::verify`, or the payout OP_RETURN check constrains the withdrawal UTXO to be unique across indices, so the circuit itself would accept a claim built from this identity collision. `Verifier::is_deposit_valid`/`is_kickoff_malicious` do not check for duplicate withdrawal UTXOs across different deposits either.

### Impact Explanation
An operator that serviced one real withdrawal (A) gets automatically credited by the verifier's block-scan (`update_finalized_payouts`) as having also serviced a second withdrawal (B), enabling it to walk the round/kickoff/reimburse flow via `get_reimbursement_txs` and claim collateral reimbursement for deposit B without ever having funded B's withdrawer. This matches "an operator reimbursed for a payout it never funded" (Critical). It also means the honest withdrawer of B can never be properly serviced/tracked, since B's `withdrawals` row is already marked as paid by an unrelated payout — an honest party (the true payer, or the withdrawer expecting funds for B) is left in an inconsistent state. The attack is repeatable across any pair of deposits/withdrawal indices the attacker controls (attacker only needs to own two deposits and duplicate a UTXO registration across them), and does not require attacker access to any protocol key, verifier, or Citrea privilege beyond calling `withdraw()` twice with the same bytes.

### Likelihood Explanation
Preconditions: attacker needs two deposits into the bridge (self-funded, standard cost = 2× bridge amount in BTC plus fees) and the ability to call Citrea's `withdraw()` twice, registering identical `(txId, outputId)` bytes for both. Per the audit's stated attacker capabilities, this registration is fully attacker-controlled. No majority hashrate, key compromise, or verifier/operator collusion is required — an honest, unwitting operator services withdrawal A normally and is automatically implicated by the verifier's own bookkeeping in "having serviced" B. The attack is mechanical and repeatable for every additional colliding pair the attacker is willing to fund.

### Recommendation
Change the identity used to correlate a spent Bitcoin UTXO to a withdrawal to be the Citrea `idx` itself rather than `(withdrawal_utxo_txid, withdrawal_utxo_vout)`. Concretely, when recording a spend against `bitcoin_syncer_spent_utxos`, also record which `idx` the spend was expected to satisfy (the `idx` used when the operator called `withdraw`/`InternalWithdraw`/optimistic-payout for that specific outpoint), and have `get_payout_txs_for_withdrawal_utxos` join/filter on that recorded idx rather than raw outpoint equality. Additionally, enforce (at minimum at the DB layer, and ideally reflected in the bridge-circuit's storage-proof check) that a given withdrawal UTXO can only be attributed to a single withdrawal index; reject/flag any deposit or withdrawal record where `withdrawal_utxo_txid/vout` collides with an existing row before marking it paid.

            .get_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), index)
            .await

        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;
