### Title
`rewards()` in the distribution precompile is the only query missing the non-payable `value` check, silently stranding sent funds - (File: `precompiles/distribution/distribution.go`)

### Summary
The distribution precompile at `0x0000000000000000000000000000000000001007` enforces a non-payable guard (`pcommon.ValidateNonPayable`, invoked through `p.validateInput`) on every view/query method — `params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, and `communityPool` — but `rewards()` is dispatched directly without this check.

### Finding Description
In `Execute`, all query methods pass `value` into their handler and each handler calls `p.validateInput(value, args, N)` which internally calls `pcommon.ValidateNonPayable(value)` before doing any work [1](#0-0) . However, `RewardsMethod` is routed to `p.rewards(ctx, method, args)` without ever receiving or checking `value` [2](#0-1) , and the `rewards` function itself never references `value` at all [3](#0-2) . Because the EVM already deducted `msg.value` from the caller's balance and credited it to the precompile address as part of the CALL semantics before the precompile logic runs, any wei/usei sent alongside a `rewards()` call is not rejected, not credited to any account's spendable balance in a meaningful accounting sense inside the precompile's business logic, and not returned to the caller. This is confirmed by an explicit code comment in the integration test suite: `integration_test/precompile_tests/precompiles/distribution.spec.ts` states "rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)" [4](#0-3) . This mirrors the reported bug class of a contract/interface inconsistently handling native-value acceptance versus its siblings, except here the asymmetry causes actual value to be accepted and stranded rather than rejected.

### Impact Explanation
Any EOA or contract that calls `rewards(address)` on the distribution precompile with a non-zero `value` field will have that usei/wei permanently stuck at the precompile address (`0x1007`) with no code path to withdraw or reclaim it, since the precompile is a native Go-implemented contract with no logic to track or refund incidental payments. This is a direct, irreversible loss of user funds triggered by a single externally-submitted EVM transaction — no privileged access, governance, or validator collusion required. Because the precompile's other seven view methods diligently reject value, a wallet or integrator relying on ABI-declared "payable"/non-payable consistency, or a naive integration copying a value-forwarding call pattern used elsewhere in the contract, could trigger permanent fund loss without any explicit error signal.

### Likelihood Explanation
Likelihood is moderate: the precompile ABI does not prevent sending value to `rewards()`, and unlike every sibling query it produces no revert to warn the caller. Any transaction sender or contract composing calls to the distribution precompile (e.g., a batching/aggregator contract that forwards `msg.value` uniformly across a set of calls, or a script that mistakenly reuses call parameters from a payable withdraw method) can trigger the loss with a single call.

### Recommendation
Add the same non-payable guard used by the other seven distribution view methods to `rewards()`: extend `p.validateInput(value, args, 1)` (or an equivalent `pcommon.ValidateNonPayable(value)` call) before executing `p.rewards`, and thread `value` into the `rewards` function signature and dispatch call so it can validate accordingly, consistent with the current dispatch in `Execute` at `precompiles/distribution/distribution.go` line 204-205 [5](#0-4) .

### Proof of Concept
1. Associate a Sei address with an EVM address and ensure it has a positive delegation reward balance.
2. Construct an EVM transaction calling `rewards(address)` on `0x0000000000000000000000000000000000001007`, setting `value` to a non-zero amount of wei (or usei-equivalent, e.g. `10**12` wei).
3. Submit the transaction: it succeeds and returns the caller's reward data, exactly as the integration test comment describes, and the caller's balance is reduced by the supplied `value`.
4. Observe that the sent value is not returned, not credited to any spendable balance the caller can access, and there is no method on the distribution precompile to reclaim funds sent to it — the funds are permanently stranded.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
