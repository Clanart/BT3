## Title
Missing timestamp/freshness validation in App Proxy HMAC verification allows indefinite replay of signed proxy requests - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
The Chainlink oracle bug is a case of an incomplete validity check: the code verifies one property of the returned data (freshness via `TIMEOUT`) but omits another mandatory bound (`minAnswer`/`maxAnswer`), letting a technically "valid" but semantically stale/wrong value be trusted. `ShopifyApp::AppProxyVerification#query_string_valid?` has the same class of flaw: it verifies that the HMAC `signature` matches the query parameters, but it never checks the `timestamp` parameter that Shopify includes in every signed app-proxy request. As a result, a signature that is cryptographically valid is accepted no matter how old the request is.

### Finding Description
`query_string_valid?` extracts the `signature` param, recomputes the HMAC over the remaining sorted params, and does a `secure_compare`. It never inspects `query_hash["timestamp"]`: [1](#0-0) 

`verify_proxy_request` (the `before_action`) relies solely on this method to gate access to any controller including this concern: [2](#0-1) 

Because the `timestamp` value is part of the signed payload but is never compared against `Time.now`, a full app-proxy URL (query string + signature) that was ever valid remains valid forever. Any anonymous party who observes such a URL (via browser history, shared links, server logs, Referer headers, proxy/CDN logs, browser extensions, etc.) can replay it against the app's app-proxy endpoint at any point in the future and it will be treated as an authentic, freshly-signed Shopify request.

This mirrors the reported oracle issue precisely: a partial/insufficient bound check (`secondsSince > TIMEOUT` only, no min/max price check) lets stale-but-syntactically-valid data be accepted as trustworthy.

### Impact Explanation
An attacker who captures one valid app-proxy request URL can replay it indefinitely to `verify_proxy_request`-protected controller actions as if it were a fresh request from Shopify, without needing the shared secret. Depending on what the app does in the app-proxy endpoint (return shop-specific data, execute a state-changing action tied to the `shop` param in the query, issue a response consumed by the storefront), this can lead to unauthorized data disclosure or replay-driven state changes scoped to whatever shop/session the original captured URL referenced.

### Likelihood Explanation
Exploitation requires only that an anonymous party obtain one previously-issued app-proxy URL (no secret knowledge, no valid session, no privileged access needed) — satisfied by the "unprivileged analog" requirement. App-proxy request URLs are exposed in browser address bars/history and to any intermediary (analytics scripts, CDNs, logs) that see the storefront request, making leakage plausible.

### Recommendation
Add an explicit timestamp bound check inside `query_string_valid?` (or `verify_proxy_request`), rejecting requests whose `timestamp` is older than a small tolerance window (e.g. a few minutes), similar to how `WebhookVerification`/OAuth callback flows should validate freshness:
```ruby
def query_string_valid?(query_string)
  query_hash = Rack::Utils.parse_query(query_string)

  signature = query_hash.delete("signature")
  return false if signature.nil?

  timestamp = query_hash["timestamp"]
  return false if timestamp.nil? || (Time.now.to_i - timestamp.to_i).abs > MAX_ALLOWED_TIMESTAMP_SKEW

  ActiveSupport::SecurityUtils.secure_compare(
    calculated_signature(query_hash),
    signature,
  )
end
```

### Proof of Concept
1. Capture any historically valid app-proxy URL for an app that includes `ShopifyApp::AppProxyVerification`, e.g.:
   `GET /apps/my-app?shop=some-shop.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid-hmac>`
2. Wait an arbitrary amount of time (days/months later).
3. Replay the exact same request. `query_string_valid?` recomputes the same HMAC over the same params and it matches, so `verify_proxy_request` allows the request through — confirmed by the existing test asserting only signature correctness, with no timestamp-based test present: [3](#0-2)
