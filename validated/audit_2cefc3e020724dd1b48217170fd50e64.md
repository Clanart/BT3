Payout tx's self-declared OP_RETURN operator_xonly_pk is trusted with no signature/funding check, letting a party who never funded a withdrawal get an operator credited (and reimbursed) for it - (File: core/src/verifier.rs, core/src/database/verifier.rs, core/src/task/payout_checker.rs)

### Summary
`update_finalized_payouts` attributes a withdrawal's payout to whichever `operator_xonly_pk` appears in the payout transaction's OP_RETURN, with no verification that this operator's signature or funds appear anywhere in the transaction's inputs. Because the withdrawer's `SinglePlusAnyoneCanPay` signature only commits to the withdrawal input and the payout output, anyone (an unprivileged attacker who is also the withdrawer) can add their own funding input, name an arbitrary honest operator's public key in the OP_RETURN, and broadcast the transaction directly — bypassing the operator's `withdraw` gRPC entirely.

### Finding Description
The intended binding is: `withdrawals.payout_payer_operator_xonly_pk == the operator whose funds actually paid the withdrawer`.

The code path:
- `core/src/verifier.rs:2283-2354` (`update_finalized_payouts`) finds the payout tx purely via `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`), which just looks up whatever transaction spent the registered `withdrawal_utxo_txid`/`vout` (from `bitcoin_syncer_spent_utxos`) — no input/signature check at all.
- It then calls `get_first_op_return_output(&circuit_payout_tx)` → `parse_op_return_data(...)` → `XOnlyPublicKey::from_slice(bytes)` (`core/src/verifier.rs:2312-2321`) and stores whatever key is found via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`).
- The withdrawer's signature is only over `SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:174-187`, `core/src/operator.rs:614-637`), which lets any party add extra funding inputs and any OP_RETURN after the withdrawer signs — the withdrawer never signs or commits to the OP_RETURN content or to who funds the tx.
- This attacker-controlled attribution is then trusted downstream with no re-verification:
  - `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only compares the stored `operator_xonly_pk` to the kickoff sender's key — a match causes verifiers to *not* challenge.
  - `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:31-113`) queries `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and automatically calls `handle_finalized_payout` — the honest operator's own automation self-triggers a kickoff for a payout it never made, purely because its own key was named by an attacker.
- `handle_finalized_payout` (`core/src/operator.rs:839-885`) then consumes a real kickoff connector and proceeds toward `create_reimburse_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:318-385`), which spends the shared `MoveToVault` UTXO (N-of-N controlled bridge reserve) to the operator's reimbursement address.

Root cause: nothing in `bridge_circuit`/`update_finalized_payouts`/`is_kickoff_malicious` ties `operator_xonly_pk` to a Schnorr signature or a spent input actually controlled by that operator. The OP_RETURN is pure self-declared metadata, and it is trusted as if it were an authenticated claim.

### Impact Explanation
An attacker who is also the withdrawer can: (1) deposit and register a withdrawal for themselves, (2) construct and directly broadcast the payout transaction (bypassing every operator), funding the large output entirely from their own extra input, while (3) placing a named honest operator's public `operator_xonly_pk` in the OP_RETURN. The honest operator's own automation will then detect this as "its" unhandled payout and initiate a kickoff and eventual `Reimburse` transaction, which spends real bridge value out of the shared `MoveToVault` UTXO to the operator — reimbursing an operator for a payout it never funded. This matches the Critical impact category "an operator reimbursed for a payout it never funded," draining shared bridge reserve funds (contributed by all depositors, not just the attacker) to whichever operator's key the attacker chooses to name, or consuming that operator's limited kickoff connectors/round slots as a griefing vector. It is repeatable across every deposit/withdrawal index and every registered operator, since the attribution mechanism has no per-tx authentication.

### Likelihood Explanation
Preconditions are minimal: the attacker must be able to deposit and register a withdrawal for themselves (standard unprivileged actions on Citrea), obtain their own `SinglePlusAnyoneCanPay` signature (already required for anyone withdrawing), and know any operator's public `operator_xonly_pk` (this is public information distributed to depositors/aggregator for operator selection). No verifier, operator, or security-council privilege, key compromise, or hashrate is required. The attacker pays normal Bitcoin fees and the deposit/withdrawal amount (their own funds moving to their own withdrawal address), so the attack cost is low relative to the amount that can be drained from the shared vault via the framed operator's reimbursement. This is fully reproducible on regtest with `feature = "automation"` enabled for the framed operator.

### Recommendation
Do not trust the OP_RETURN operator_xonly_pk as proof of funding. Require the payout transaction's additional funding input(s) to be signed/spendable by the claimed operator's key (or otherwise cryptographically bind the OP_RETURN commitment to a signature made by that operator over the specific payout tx), and verify this binding in `update_finalized_payouts`/`is_kickoff_malicious` before crediiting an operator or allowing an uncontested kickoff. Alternatively, require operators to co-sign or pre-commit to payouts they intend to claim (e.g., via a Winternitz/Schnorr commitment collected before broadcasting), and reject/challenge any kickoff whose payout tx cannot be tied to the claiming operator's actual signed input.

pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {

            return Some(data.as_bytes());
        }
    }
