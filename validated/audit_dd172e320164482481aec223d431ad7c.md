## Finding: Same-chain fills strand escrowed input tokens when `inputs.length != outputs.length`, allowing the order creator to double-dip via `_cancelSameChain`

### Title
Mismatched input/output array lengths in same-chain intent fills leave escrow un-released, letting the user reclaim solver-owed funds after fill - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`_fillSameChain` builds the list of escrow releases by iterating over **output** assets and indexing into `order.inputs[i]` at the same index [1](#0-0) . `placeOrder` never enforces that `order.inputs.length == order.output.assets.length` — only that `order.inputs.length != 0` is checked at placement. When a user places an order with more input tokens than output tokens, a full fill only ever releases the first `outputsLen` input entries to the solver; any input tokens beyond that index are never included in the `WithdrawalRequest` passed to `_withdraw`, so their `_orders[commitment][token]` balance is never decremented. Yet `_fillSameChain` still marks the order fully filled (`isFullyFilled = true`, `_filled[commitment] = msg.sender`) and emits `OrderFilled`. The mirrored cross-chain path, `_fillCrossChain`, does not have this asymmetry — it always forwards the **entire** `order.inputs` array in the `RedeemEscrow` message [2](#0-1) , so solvers are always paid in full there. This is the same class of bug as the reported H-07: one settlement path (`openShort`) omits an accounting update that its mirror path performs correctly.

### Finding Description
1. `placeOrder` escrows all of `order.inputs` with no constraint tying array length to `order.output.assets` (only `order.inputs.length == 0` is rejected).
2. `_fillSameChain` sizes `escrowedInputs`/`outputFills` to `outputsLen = order.output.assets.length` and, for each output index `i`, releases `order.inputs[i]` [1](#0-0) .
3. If `order.inputs.length > outputsLen`, indices `outputsLen..inputs.length-1` are never touched by this loop, so their `_orders[commitment][token]` balances remain non-zero after the order is marked filled.
4. `_cancelSameChain` has no check on `_filled[commitment]` at all — it only verifies `order.user == msg.sender`, correct chain, and that at least one input still has non-zero escrow (`hasEscrow`) [3](#0-2) . Since the untouched input tokens still show non-zero escrow, `hasEscrow` is true even after the order has been fully filled by a solver.
5. `_withdraw` (shared by both fill and cancel) only reverts on `escrowed == 0` per-token [4](#0-3)  — it has no independent check that the order hasn't already been finalized, relying entirely on callers to gate that. `_cancelSameChain` does not perform such a gate.

The net effect: the order creator can call `fillOrder` logic path with mismatched input/output counts, receive their outputs from the solver, and then call `cancelOrder` (same-chain path) to reclaim the leftover, un-released input escrow that rightfully belonged to the solver.

### Impact Explanation
This is a direct loss/theft of solver funds: the solver transfers output tokens to the beneficiary in good faith expecting the full escrowed input in return, but a subset of the input tokens is never paid out and is later reclaimed by the user who placed the order. This matches the "stealing or loss of funds" and "logic attacks" categories in the bounty scope, is reachable by any unprivileged user simply by crafting an order with unequal input/output array lengths, and requires no malicious relayer, prover, or admin action.

### Likelihood Explanation
Likelihood is high for any user willing to construct such an order — there's no validation anywhere in `placeOrder`, `_fillSameChain`, or `_cancelSameChain` preventing this array-length mismatch or gating cancellation on fill status. It requires only a single attacker-controlled account acting as the order creator; the solver is the victim and needs no compromise.

### Recommendation
- Enforce `order.inputs.length == order.output.assets.length` (or an explicit, validated input-to-output allocation mapping) at `placeOrder` time so `_fillSameChain`'s index-based release logic cannot silently skip escrow entries.
- Independently, gate `_cancelSameChain` (and any other cancellation/refund path) on `_filled[commitment] == address(0)`, mirroring the finalize-state checks already implicit in `_fillCrossChain`/`onAccept`, so a filled order can never be cancelled regardless of residual escrow bookkeeping.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [TokenA: 100, TokenB: 50]` and `order.output.assets = [TokenC: 10]` (2 inputs, 1 output) — accepted since only `inputs.length == 0` is checked.
2. Solver calls the same-chain fill path with `options.outputs = [TokenC: 10]`. In `_fillSameChain`, `outputsLen = 1`, so the loop only processes `i = 0`, releasing only `order.inputs[0]` (TokenA) to the solver via `_withdraw`. `order.inputs[1]` (TokenB, 50) is never included in `escrowedInputs`, so `_orders[commitment][TokenB]` stays at 50.
3. Because `isFullyFilled = true` (outputsLen fully satisfied), `_filled[commitment] = solver` is set and `OrderFilled` is emitted [5](#0-4) .
4. User (order.user) now calls `_cancelSameChain(order, commitment)`. The check only verifies `order.user == msg.sender`, correct source chain, and `hasEscrow` (true, since TokenB still has 50 escrowed) [3](#0-2) . No `_filled` check blocks this.
5. `_withdraw` refunds the remaining 50 TokenB to `order.user`, even though the solver already delivered TokenC output tokens and the order was already marked filled. The user ends up with both the solver's output tokens and the stranded input, at the solver's expense.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
