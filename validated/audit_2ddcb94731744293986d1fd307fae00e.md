### Title
Unhandled AssertionError (null/None-check crash) when processing a malicious offer's CREATE_COIN conditions - (File: chia/wallet/util/compute_hints.py)

### Summary
`compute_spend_hints_and_additions()` blindly asserts that the puzzle-hash argument of a `CREATE_COIN` condition is a CLVM atom. When the puzzle-hash argument is instead a pair (list), `.atom` evaluates to `None` and the subsequent `assert rf is not None` raises an uncaught `AssertionError`. This function is invoked, without any exception handling, from `TradeManager.calculate_tx_records_for_offer()` while processing an offer's spend bundle — a code path directly reachable by any offer counterparty sending a crafted offer file/bech32 blob to be accepted.

### Finding Description
`compute_spend_hints_and_additions` iterates over the conditions produced by running each coin spend's puzzle reveal against its solution: [1](#0-0) 

```
if op != ConditionOpcode.CREATE_COIN.value:
    continue
cost += ConditionCost.CREATE_COIN.value

rf = condition.at("rf").atom
assert rf is not None
```

For any coin spend whose puzzle emits a `(51 <puzzle_hash> <amount> ...)` condition where `<puzzle_hash>` is a cons pair rather than an atom, `condition.at("rf").atom` returns `None`, and the `assert` fails, raising `AssertionError` (equivalent to a null-pointer dereference guard failing without a graceful fallback).

This function is called, unguarded, from `TradeManager.calculate_tx_records_for_offer()`: [2](#0-1) 

```
async def calculate_tx_records_for_offer(self, offer: Offer, validate: bool) -> list[TransactionRecord]:
    if validate:
        final_spend_bundle: WalletSpendBundle = offer.to_valid_spend()
        hint_dict: dict[bytes32, bytes32] = {}
        additions_dict: dict[bytes32, Coin] = {}
        for hinted_coins, _ in (
            compute_spend_hints_and_additions(spend) for spend in final_spend_bundle.coin_spends
        ):
```

Unlike `Offer.__post_init__`, which wraps the equivalent call in a broad `try/except`, this call site has **no exception handling** whatsoever: [3](#0-2) 

`calculate_tx_records_for_offer(complete_offer, True)` is invoked directly from `respond_to_offer()`, the routine the wallet runs when a user accepts/takes an offer received from a counterparty: [4](#0-3) 

Because the coin spends inside the offer's `WalletSpendBundle` belong to the offer *maker* and are fully signed/controlled by them (their own coins, their own puzzle logic), the maker can embed arbitrary CLVM in the puzzle reveal for their offered coins. Nothing prevents that puzzle from outputting a `CREATE_COIN` condition whose puzzle-hash argument is a pair instead of an atom — this is invalid by consensus rules, but `calculate_tx_records_for_offer` runs this analysis client-side, *before* any consensus/mempool validation occurs, purely to compute display/tx-record data for the taker's wallet.

### Impact Explanation
A malicious offer counterparty can craft an offer file (bech32 blob) that, when a victim wallet attempts to accept it via `respond_to_offer` (the standard "take offer" flow used by CLI/RPC/GUI), raises an unhandled `AssertionError` deep inside wallet processing. This halts the offer-acceptance transaction-processing flow for that wallet call with no graceful error handling, denying the victim the ability to accept that (or potentially similarly-shaped) offers and disrupting normal wallet transaction processing — a spend-triggered processing halt reachable by an unprivileged offer counterparty, matching the reachable "offer settlement" and "wallet state" impact categories in scope.

### Likelihood Explanation
High likelihood of triggerability: constructing a CLVM puzzle that outputs a `CREATE_COIN` condition with a non-atom (pair) puzzle-hash argument is trivial with custom Chialisp, and requires no special privileges — only the ability to author an offer using one's own coins and share the resulting offer file/bech32 string with a victim, which is the normal offer workflow.

### Recommendation
Replace the bare `assert rf is not None` in `compute_spend_hints_and_additions` with an explicit, caught error path (e.g., raise a `ValidationError`/skip the malformed condition) and ensure all call sites that process untrusted offer data (including `calculate_tx_records_for_offer`) wrap calls to this function in the same defensive `try/except` pattern already used in `Offer.__post_init__`, so malformed conditions degrade gracefully instead of crashing the caller.

### Proof of Concept
1. Attacker crafts a custom Chialisp puzzle for a coin they own that, when run, outputs `(51 (c 1 1) 1000)` — i.e., a `CREATE_COIN` condition (opcode 51) whose puzzle-hash argument is the pair `(1 . 1)` instead of a 32-byte atom.
2. Attacker builds a normal `Offer` object using this coin/puzzle as the offered asset and serializes it to a bech32 offer string, sending it to the victim.
3. Victim calls the standard "take offer" flow (`TradeManager.respond_to_offer`), which internally calls `calculate_tx_records_for_offer(complete_offer, True)`.
4. This calls `compute_spend_hints_and_additions()` on the attacker's coin spend; `condition.at("rf").atom` returns `None` for the pair argument, and `assert rf is not None` raises an unhandled `AssertionError`, aborting offer acceptance processing for the victim's wallet call.
