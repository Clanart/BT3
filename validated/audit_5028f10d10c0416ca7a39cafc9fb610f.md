### Title
Governance deposit refunds are permanently frozen for depositors whose Sei address becomes EVM-unreceivable, with no recipient-override recovery path - ([File: sei-cosmos/x/gov/keeper/deposit.go])

### Summary
`RefundDeposits` in the gov module pays deposit refunds back to the exact depositor address recorded on the deposit, with no ability to redirect the payout to an alternate recipient. If that address later fails the bank module's `CanSendTo` recipient check (enforced via `EvmKeeper.CanAddressReceive`, registered as a `RecipientChecker`), the refund is retained indefinitely inside the gov module account instead of being paid out, and the code explicitly states recovery requires a chain migration. This mirrors the reported bug class: a payout mechanism that hardcodes the original depositor as recipient becomes permanently unable to deliver funds once that depositor becomes "blacklisted" (here, EVM-unreceivable) — exactly analogous to a `vaultCurrency` blacklisting a staking user with no way to redirect `withdrawRewards()`.

### Finding Description
`BaseSendKeeper.CanSendTo` walks a list of `RecipientChecker`s registered by other modules: [1](#0-0) . In `app.go`, the EVM keeper's `CanAddressReceive` is registered as exactly such a checker: [2](#0-1) .

A Sei address that has not been explicitly associated with an EVM public key (a "cast" address, derived deterministically from an EVM address) can later become unreceivable once the underlying EVM address is associated to a *different* Sei address (e.g., via `associatePubKey`/an `Associate` transaction). This exact mechanic is demonstrated and explicitly documented in the distribution module's own regression tests: [3](#0-2) [4](#0-3) 

The gov module's `RefundDeposits` uses this exact `CanSendTo` gate but, unlike the distribution module (which falls back to routing unpayable commission to the community pool, see `canReceiveWithdrawAddr` and `AfterValidatorRemoved`), simply skips the payout and leaves the deposit record (and the backing coins) sitting in the module account indefinitely: [5](#0-4) 

The distribution module's own analogous logic and comment confirms the intent to guard against exactly this failure mode elsewhere: [6](#0-5) 

Unlike distribution's `AfterValidatorRemoved`, which routes unpayable funds to the community pool so they remain usable by governance, the gov module's `RefundDeposits` has no such fallback — the funds sit inert with no on-chain path to recovery besides an explicit state migration, per the function's own comment.

### Impact Explanation
Any unprivileged account can:
1. Submit a governance proposal deposit from a cast (unassociated) Sei address it controls.
2. Trigger the underlying EVM address to be (re-)associated with a different Sei address (a normal, permissionless `Associate`/`associatePubKey` operation), which causes `CanAddressReceive`/`CanSendTo` to return `false` for that cast address going forward.
3. Have the proposal reach a terminal state that triggers `RefundDeposits` (e.g., proposal rejected, fails to reach quorum, or is vetoed) — the deposit for that address is silently retained, deleting nothing, and the funds become permanently unrecoverable through any user-facing path. Recovery requires an operator-initiated chain state migration, which is not something the depositor can trigger or expect. This is a genuine permanent freezing of user funds (their governance deposit), matching the "fund loss/permanent freezing" impact bar. It affects only the specific depositor whose address became unreceivable, not the whole module, but is nonetheless a concrete, permanent, unrecoverable-without-migration loss for that user.

### Likelihood Explanation
This is easily reachable with two ordinary, permissionless transactions from the same account: (1) `MsgDeposit` from a cast address, and (2) any transaction/`Associate` action that causes the underlying EVM address to be mapped to a different Sei address. No validator, governance, or operator privilege is required, and cast addresses (used by any wallet before an explicit association step) are a normal, expected user state on Sei. The condition is deterministic and reproducible, not reliant on race conditions or third-party behavior.

### Recommendation
Apply the same pattern already used in `x/distribution` (`canReceiveWithdrawAddr` / `AfterValidatorRemoved`'s community-pool fallback) to `RefundDeposits`: when a depositor fails `CanSendTo`/`BlockedAddr`, route the stuck deposit to the community pool (or an equivalent recoverable destination) instead of leaving it permanently un-refundable and dependent on a manual migration, and/or allow depositors to designate an alternate payout address analogous to `SetWithdrawAddr` in distribution.

### Proof of Concept
1. Create account A; do not send an `Associate` transaction for A yet, so A's Sei address is a byte-cast of an EVM address `E` (`sdk.AccAddress(E[:])`).
2. From A, submit `MsgDeposit` on a governance proposal.
3. Cause `E` to be re-associated to a different Sei address, e.g. call `EvmKeeper.SetAddressMapping`/perform an `associatePubKey` flow that maps `E` to account B (mirrors `TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator`'s setup at [7](#0-6) ). After this, `app.BankKeeper.CanSendTo(ctx, A)` returns `false`.
4. Let the proposal reach a terminal, non-deposit-forfeiting outcome so `RefundDeposits` runs.
5. Observe that A's deposit is neither paid out nor removed: `store.Delete` is skipped and the coins remain in the `gov` module account per the guard in [8](#0-7) , with no subsequent way for A to reclaim the funds absent a migration.

```go
func (k BaseSendKeeper) CanSendTo(ctx sdk.Context, recipient sdk.AccAddress) bool {
	for _, rc := range *k.recipientCheckers {
		if !rc(ctx, recipient) {
			return false
		}
	}
	return true
}
```

```go
// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
}
```

```go
func (k Keeper) canReceiveWithdrawAddr(ctx sdk.Context, withdrawAddr sdk.AccAddress) bool {
	// BlockedAddr mirrors the gate SendCoinsFromModuleToAccount actually enforces:
	// beyond the module-account blocklist it also rejects dynamically-derived
	// addresses such as the EVM coinbase addresses (an "evm_coinbase"-prefixed
	// address), which CanSendTo does not catch. Consulting it here keeps this
	// predicate in lockstep with the send, so AfterValidatorRemoved never concludes
	// an address is receivable and then panics on the resulting bank error.
	return !k.blockedAddrs[withdrawAddr.String()] &&
		!k.bankKeeper.BlockedAddr(withdrawAddr) &&
		k.bankKeeper.CanSendTo(ctx, withdrawAddr)
}
```
