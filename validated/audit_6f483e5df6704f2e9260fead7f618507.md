### Title
Order-Based (Not Content-Verified) Splicing of AI Conflict Resolutions Can Corrupt Committed Code - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The Sherlock report's core flaw is that a value computed under one set of assumptions (token precision) is fed into a downstream function that assumes a different, incompatible precision, with no cross-check — silently corrupting the computed price. The GitHub Desktop analog is in the Copilot merge-conflict-resolution pipeline: `reassembleResolvedFile` splices AI-generated per-hunk resolutions into the on-disk conflicted file **purely by positional order**, with no verification that hunk *N* as counted at splice time corresponds to hunk *N* as counted when the prompt/context was built. A conflicting file whose "ours"/"theirs" content merely *contains* text resembling conflict markers (attacker-controlled content coming from a merged/rebased/cherry-picked branch) can desynchronize that count, causing a resolution meant for one conflict to be written into a different one — silently corrupting what the user commits.

### Finding Description
`reassembleResolvedFile` re-scans the raw on-disk file for marker lines using its own local regexes: [1](#0-0) 

It walks the file, and for every line matching `^<{7}(?:\s|$)` looks ahead for a `=======` separator and `>>>>>>>` closer; when found it advances past the whole block and splices in `hunkResolutions[hunkIndex]`, incrementing `hunkIndex` — explicitly "matched by order, not by line number": [2](#0-1) [3](#0-2) 

This function is called from `reassembleResolutions`, which pulls `ctx.rawContent` from `IFileConflictContext` (built earlier, when hunks are extracted to construct the "Conflict 1 of N" prompt sent to the model) and splices the model's `raw.hunks` array into it: [4](#0-3) 

The only integrity check performed before reassembly is `validateResolutionPaths`, which verifies the **count** of hunks returned by the model matches the **count** originally extracted per file — it does not verify that each hunk's marker boundaries line up positionally between the two independent counting passes: [5](#0-4) 

The vulnerability is the same broken invariant as the Balancer bug: two code paths are assumed to operate on values with the same "precision" (here, the same enumeration/ordering of conflict-marker blocks) but nothing enforces that assumption. If the marker-line regex used by `reassembleResolvedFile` (`^<{7}(?:\s|$)`, `^={7}$`, `^>{7}(?:\s|$)`) disagrees — even in one file, even by one block — with whatever logic produced the hunk list used to build the prompt (in `copilot-conflict-context.ts`, not fully inspectable within tool limits), `hunkIndex` drifts. From that point on, every subsequent resolved block is spliced into the *wrong* conflict location in the file that ends up written to disk and committed.

### Impact Explanation
Because the on-disk conflicted file's content comes directly from the two sides of a real git merge/rebase/cherry-pick — i.e., from a fetched/cloned remote branch that an attacker (any contributor whose branch is merged) fully controls — an attacker can craft a hunk's "ours" or "theirs" content containing a line that satisfies `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` without actually being a git conflict marker block (e.g. code, a string literal, or documentation that legitimately contains 7-`<`/7-`=`/7-`>` lines). This desynchronizes the hunk index used for splicing from the hunk index the model was told about, so a resolution intended for conflict *K* gets written into conflict *K±1*. The result is silent corruption of the file the user reviews and commits/pushes — potentially reinstating vulnerable code, dropping a security fix that the other side had, or inserting content the user never intended, all without any error or warning, since counts still match and no exception is raised.

### Likelihood Explanation
This requires no local access, no admin rights, and no prior compromise — only that the user (a) uses the AI conflict-resolution feature and (b) is resolving a conflict against a branch/PR whose content was authored by someone else (the normal collaborative case). The attacker only needs to shape ordinary file content in their branch/PR, which is a completely realistic, low-effort trigger. The bug is deterministic given a crafted file, not probabilistic.

### Recommendation
- Do not rely on positional/order matching between two independently derived hunk counts. `reassembleResolvedFile` should use the *exact same* marker-parsing routine (ideally the identical function/regex) that originally built `IFileConflictContext.hunks`, so both the prompt-construction and the splice-back operate on an identical enumeration of conflict blocks.
- After reassembly, re-parse the resulting resolved region and structurally diff it against the corresponding `IFileConflictContext` hunk (ours/theirs/base) to confirm the spliced content targets the expected block, failing closed (falling back to manual resolution) on any mismatch.
- Treat any residual `<<<<<<<`/`=======`/`>>>>>>>`-looking line inside a hunk's "ours"/"theirs"/context content as a validation failure rather than allowing it to silently participate in marker-block detection during reassembly.

### Proof of Concept
1. Create a repository with a file `f.ts` where branch A and branch B modify overlapping lines such that a normal 2-way merge produces two conflict blocks.
2. In branch B's content for the *first* conflict (either the "ours" or "theirs" side), embed a crafted string/comment containing three lines:
   ```
   <<<<<<< fake
   =======
   >>>>>>> fake
   ```
   This is valid file content (e.g., inside a multi-line string, markdown code fence, or comment) and is not itself a real git conflict — it is one side's actual textual content that git leaves untouched in the merged file.
3. Trigger a real merge/rebase between A and B so the file has 2 genuine conflict blocks, with the crafted marker-like text sitting inside the first block's "ours"/"theirs" region.
4. Run the Copilot conflict resolution feature. Assume `copilot-conflict-context.ts`'s hunk-extraction counts 2 conflicts (using the real conflict boundaries) and prompts the model with "Conflict 1 of 2" / "Conflict 2 of 2", producing `hunks = [resolution1, resolution2]`.
5. `reassembleResolvedFile` re-scans `rawContent` line-by-line with its local regexes and, upon reaching the embedded fake `<<<<<<< fake` line inside the first real conflict's own content, treats it as a spurious extra "conflict start," finds the fake `=======`/`>>>>>>> fake` immediately after, and splices `hunkResolutions[0]` there instead of at the real first conflict marker further down — shifting all subsequent hunk indices.
6. The file written to disk (and then committed) contains `resolution1`'s content in the wrong location and effectively drops or misplaces the intended resolution for the real first conflict, all while `validateResolutionPaths` reports a matching hunk count and no error surfaces to the user.

(Note: I could not fully inspect `app/src/lib/copilot-conflict-context.ts`'s hunk-extraction regex within the available tool budget to confirm it uses a stricter/different pattern than `reassembleResolvedFile`'s regexes; this should be verified directly against that file to confirm the exact drift condition, though the splicing-by-order design itself is confirmed and is the root cause regardless of the precise extraction regex.)

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }

 * Reassemble a fully resolved file by splicing per-hunk resolutions into

 *
 * Walks the original file line-by-line. Non-conflicted lines are copied

 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
