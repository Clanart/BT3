The analog vulnerability exists in Hyperbridge's `challengePeriod` mechanism, which mirrors the exact broken invariant in the Timelock report: a security-critical waiting-period value is hardcoded to zero, and the code additionally treats zero as "disabled" rather than "immediate," fully bypassing the fraud-proof challenge window designed to protect state commitment finality.

### Title
Challenge period hardcoded to zero disables the fraud-proof waiting window, allowing immediate acceptance of requests/responses/timeouts on unchallenged state commitments - (File: evm/script/DeployIsmp.s.sol / evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2.sol` is supposed to enforce a challenge/delay period between when a state machine commitment is stored (via consensus proof) and when that commitment can be used to process incoming POST requests, GET responses, or timeouts. The deployment script `DeployIsmp.s.sol` hardcodes `challengePeriod: 0` in `HostParams` for both mainnet and testnet deployments [1](#0-0) , and `HandlerV2.sol`'s guard explicitly special-cases zero as "no delay required" rather than "delay of zero seconds": `if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();` [2](#0-1) . This is functionally identical to the reported Timelock bug: a parameter meant to enforce a mandatory waiting period is unconditionally set to zero, silently disabling the protection.

### Finding Description
The challenge period exists to give watchers time to dispute a freshly-submitted consensus/state proof before it is relied upon to process cross-chain requests, responses, and timeouts. `HandlerV2.handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` all compute `delay = block.timestamp - host.stateMachineCommitmentUpdateTime(...)` and then only revert if `challengePeriod != 0 && challengePeriod > delay` [3](#0-2) [4](#0-3) .

The same "zero means bypass" semantics exist on the Substrate/Rust side in `verify_delay_passed`: `Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)` [5](#0-4) .

Critically, `updateHostParamsInternal` in `EvmHost.sol` validates several `HostParams` fields (handler code/interface, consensus client code/interface, non-empty `hyperbridge` id, non-empty `stateMachines`, and `unStakingPeriod >= 1 days`) but performs **no minimum-value check on `challengePeriod`** before storing it [6](#0-5) . So unlike `unStakingPeriod`, which is guarded against being set too low, `challengePeriod` can be, and in the actual deployment script is, hardcoded to `0` with no validation and no config override path [7](#0-6) .

### Impact Explanation
With `challengePeriod == 0`, the delay check in `HandlerV2` is compiled out at runtime — any relayer can submit a consensus proof and, in the same or a subsequent transaction, immediately submit `PostRequestMessage`/`GetResponseMessage`/timeout messages referencing the just-stored, unchallenged state commitment. This removes the fraud-proof window that is supposed to protect against a malicious or buggy consensus client momentarily accepting an invalid state root, enabling false state/proof acceptance to be acted upon (fund-moving dispatches via `host.dispatchIncoming`/`host.dispatchTimeOut`) before anyone has the opportunity to freeze the host or dispute the commitment. This matches the "false proof/state acceptance" and "unauthorized execution" impact categories in the bounty scope.

### Likelihood Explanation
This is not a theoretical misconfiguration — it is the value baked into the actual deployment script used for both mainnet and testnet host deployments [1](#0-0) , and it is also the value used across the test fixtures (`BaseTest.sol`, `HandlerV2Test.sol`, Rust EVM harness) [8](#0-7) , indicating the zero-delay configuration is the default, unexamined state of the system rather than an edge case. No code path enforces a nonzero minimum, so the flaw is live from the moment of deployment and requires no privileged or malicious actor to trigger — it is a default-open condition on the public request/response/timeout handling entrypoints.

### Recommendation
Enforce a minimum nonzero `challengePeriod` in `updateHostParamsInternal` (analogous to the existing `unStakingPeriod` check), and remove the `challengePeriod != 0` bypass branch in `HandlerV2.sol`'s delay checks (and the analogous `delay_period.as_secs() == 0` bypass in `handlers.rs`) so that a zero value is treated as "zero-second delay is invalid" rather than "no delay enforced." Update `DeployIsmp.s.sol` to source `challengePeriod` from configuration with a safe non-zero default for both mainnet and testnet deployments.

### Proof of Concept
1. Deploy `EvmHost` using `DeployIsmp.s.sol`, which sets `challengePeriod: 0` [1](#0-0) .
2. Submit a consensus proof via `HandlerV2.handleConsensus`, causing `storeStateMachineCommitment` to record a new `StateCommitment` with `_consensusUpdateTimestamp = block.timestamp` (i.e., `delay == 0` immediately after).
3. In the very same block, call `HandlerV2.handlePostRequests` (or `handleGetResponses`/timeout variants) with a valid merkle proof against that fresh commitment.
4. The check `if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();` evaluates `challengePeriod != 0` as `false`, skipping the revert entirely regardless of how small `delay` is [2](#0-1) .
5. The request/response/timeout is dispatched immediately, with zero opportunity for challenge/dispute of the underlying state commitment — confirming the fraud-proof window is fully disabled by the hardcoded zero value, exactly mirroring the Timelock's `delay = 0` bypass.

        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());

            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
