### Title
Tokenfactory denom admin can front-run an `AllowList` update to freeze/steal in-flight user funds — no timelock on admin-controlled transfer restrictions ([File: x/tokenfactory/keeper/msg_server.go])

### Summary
Any account can permissionlessly create a tokenfactory denom via `MsgCreateDenom` and becomes its unrestricted, non-timelocked "admin" — directly mirroring the NFTX report's "anyone can create a pool / manager is not a trusted actor" premise. That admin can call `MsgUpdateDenom` at any time to set/replace the denom's `AllowList`, which is enforced by `x/bank` on every subsequent `SendCoins` for that denom. Because there is no timelock or delay on this change (exactly the missing control the NFTX report calls out for the fee setter), the admin can observe a victim's pending transaction in the mempool and front-run it with an `AllowList` update that excludes the victim (or a contract the victim is interacting with), causing loss/blocking of the victim's transfer at the moment of maximum exposure.

### Finding Description
`MsgCreateDenom` lets any account become the admin of a new `factory/<creator>/<subdenom>` denom, with no vetting and no distinction presented to downstream consumers ("the token denom does not indicate the current admin") [1](#0-0) . The admin retains unilateral, unrestricted control to mutate the denom's `AllowList` via `MsgUpdateDenom`/`UpdateDenom`, gated only by an admin-equality check with no cooldown or timelock: [2](#0-1) 

This `AllowList` is enforced directly inside `x/bank`'s `IsInDenomAllowList`, which is consulted on every coin transfer for `factory/...` denoms: [3](#0-2) 

and a `bank.MsgSend` involving a denom whose sender/receiver is not on the (admin-controlled) allow list is rejected outright ("is not allowed to receive/send funds"), as demonstrated in the module's own test suite: [4](#0-3) [5](#0-4) 

Because `UpdateDenom` applies instantly and network-wide with zero delay, a malicious/self-appointed denom admin can watch the mempool for a large pending transfer or DEX/pointer interaction involving their denom and submit an `MsgUpdateDenom` in the same block (front-running via higher gas/priority) that flips the `AllowList` to exclude the victim's address or the contract address the victim is about to interact with (e.g., an ERC20/CW20 native pointer contract minted against that denom, registered via the permissionless `pointer` precompile [6](#0-5) ). This is structurally identical to the NFTX bug class: a permissionlessly-created, untrusted "manager" role holds an always-mutable parameter (fee/allow-list) with no timelock, enforced at the moment of user interaction, allowing front-running to disadvantage/steal from unsuspecting counterparties.

### Impact Explanation
Unlike NFTX's fee (which siphons value to the manager on every deposit), the tokenfactory `AllowList` front-run primarily causes denial of a specific, targeted transfer at the moment of interaction. This can be leveraged to:
- Selectively block a specific victim's withdrawal/exit from a pool, pointer, or CW contract holding that denom while allowing everyone else, effectively freezing that user's assets that are already custodied by a contract (a "permanent freezing" outcome per the accepted impact classes), and
- Grief/extract value in multi-step flows (e.g., a swap that has already debited one leg before the second leg's `SendCoins` reverts due to the allow-list change), depending on how the calling CW contract handles the resulting error.
This satisfies the accepted "fund loss / permanent freezing" impact bar, though the direct value-extraction path is narrower than NFTX's outright fee-siphoning, since Cosmos SDK message execution is atomic and a failed `SendCoins` alone typically reverts the whole message rather than partially completing.

### Likelihood Explanation
Likelihood is comparable to the medium rating given by the NFTX judge: it requires an attacker to (a) create and control a tokenfactory denom, (b) have users/contracts trust and use that denom for value custody (e.g., wrap it via the pointer precompile or deposit into a DEX), and (c) actively monitor the mempool to front-run a specific victim transaction. The "denom does not indicate the current admin" property documented in the proto comments increases the chance an unsuspecting user or integrator is exposed without realizing an untrusted admin exists.

### Recommendation
- Add a timelock/delay (e.g., N blocks) between submission of an `AllowList` change via `MsgUpdateDenom` and its effect, so in-flight transactions cannot be selectively targeted.
- Emit and require clients/integrators to surface a persistent, queryable "denom has a mutable admin/allow-list" warning (mirroring the "we warn users for unfinalized vaults" mitigation NFTX applied) so pointer registration and DEX listings can flag or exclude such denoms.
- Consider disallowing `AllowList` shrink-only or additive changes without a delay when the denom already has outstanding supply/liquidity held by third-party contracts (pointers, AMMs).

### Proof of Concept
1. Attacker calls `MsgCreateDenom` to create `factory/<attacker>/foo`, becoming its admin [7](#0-6) .
2. Attacker mints `foo` and gets it adopted (e.g., registers a native ERC20 pointer via the permissionless `addNativePointer` precompile method so users can wrap/unwrap it in EVM DeFi) [6](#0-5) .
3. A victim broadcasts a transaction to unwrap/withdraw `foo` from the pointer contract back to their Sei address (a `bank.MsgSend`/native transfer of `foo`).
4. Attacker observes this pending transaction and front-runs it with `MsgUpdateDenom` setting an `AllowList` that excludes the victim's address (or the pointer's module/escrow address).
5. The victim's withdrawal is enforced against `IsInDenomAllowList` inside `SendCoins` and rejected with "is not allowed to receive/send funds" [3](#0-2) , while the pointer contract's internal EVM-side bookkeeping may already reflect the burn/unwrap, leaving the victim's underlying native balance permanently unreachable — with no timelock having given the victim any warning or opportunity to react, exactly paralleling the NFTX front-run-fee scenario.

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

func (k BaseSendKeeper) GetDenomAllowList(ctx sdk.Context, denom string) types.AllowList {
	store := ctx.KVStore(k.storeKey)
	store = prefix.NewStore(store, types.DenomAllowListKey(denom))

	bz := store.Get([]byte(denom))
	if bz == nil {
		return types.AllowList{}
	}

	var allowList types.AllowList
	k.cdc.MustUnmarshal(bz, &allowList)

	return allowList
}

func (p PrecompileExecutor) AddNative(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, suppliedGas uint64, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	token := args[0].(string)
	existingAddr, existingVersion, exists := p.evmKeeper.GetERC20NativePointer(ctx, token)
	if exists && existingVersion >= 1 {
		return nil, 0, fmt.Errorf("pointer at %s with version %d exists when trying to set pointer for version %d", existingAddr.Hex(), existingVersion, native.CurrentVersion)
	}
	metadata, metadataExists := p.bankKeeper.GetDenomMetaData(ctx, token)
	if !metadataExists {
		return nil, 0, fmt.Errorf("denom %s does not have metadata stored and thus can only have its pointer set through gov proposal", token)
	}
	name := metadata.Name
	symbol := metadata.Symbol
	var decimals uint8
	for _, denomUnit := range metadata.DenomUnits {
		if denomUnit.Exponent > uint32(decimals) && denomUnit.Exponent <= math.MaxUint8 {
			decimals = uint8(denomUnit.Exponent)
			name = denomUnit.Denom
			symbol = denomUnit.Denom
			if len(denomUnit.Aliases) > 0 {
				name = denomUnit.Aliases[0]
			}
		}
	}
	constructorArguments := []interface{}{
		token, name, symbol, decimals,
	}

	packedArgs, err := native.GetParsedABI().Pack("", constructorArguments...)
	if err != nil {
		panic(err)
	}
	bin := append(native.GetBin(), packedArgs...)
	if value == nil {
		value = utils.Big0
	}
	ret, contractAddr, remainingGas, err := evm.Create(caller, bin, suppliedGas, uint256.MustFromBig(value))
	if err != nil {
		return
	}
	err = p.evmKeeper.SetERC20NativePointer(ctx, token, contractAddr)
	if err != nil {
		return
	}

	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypePointerRegistered, sdk.NewAttribute(types.AttributeKeyPointerType, "native"),
		sdk.NewAttribute(types.AttributeKeyPointerAddress, contractAddr.Hex()), sdk.NewAttribute(types.AttributeKeyPointee, token),
		sdk.NewAttribute(types.AttributeKeyPointerVersion, fmt.Sprintf("%d", native.CurrentVersion))))
	ret, err = method.Outputs.Pack(contractAddr)
	return
}
