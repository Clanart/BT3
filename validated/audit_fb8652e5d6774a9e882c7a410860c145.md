### Title
ThresholdKeys Deserialization Accepts Identity (Zero) Verification Shares and Zero Scalars, Allowing a Group Key Whose Discrete Log the Attacker Controls - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` and `ThresholdKeys::new` validate participant indexes (`<= n`), the share count, and `t <= n`, but never validate the *values* of the deserialized points and scalars. Verification shares are parsed with `Ciphersuite::read_G`, which only enforces canonical/non-torsioned encodings and explicitly does **not** reject the identity point — unlike `Curve::read_G` in `crypto/frost/src/curve/mod.rs:125`, which rejects identity precisely because zero points are dangerous in threshold protocols. Likewise, `secret_share` and `Interpolation::Constant` coefficients are parsed with `read_F` with no zero check.

### Finding Description
The zero-address bug class maps directly onto zero/identity group elements and zero scalars fed through deserialization:

- `ThresholdKeys::read` (crypto/dkg/src/lib.rs:620-623) inserts `Ciphersuite::read_G` output into `verification_shares` with no identity check.
- `ThresholdKeys::new` (crypto/dkg/src/lib.rs:361-378) only checks `participant <= n` and count, then computes `group_key` as `sum(verification_shares[i] * interpolation_factor(i))` over participants `1..=t`. It never verifies `verification_shares[i] == generator * secret_share_i` nor that the resulting `group_key` is non-identity.
- `read_F` accepts zero scalars, so `secret_share` and `Constant` interpolation coefficients may be zero.

An attacker who supplies serialized `ThresholdKeys` bytes can therefore install a key set where every `verification_shares[i] = G * a_i` and `secret_share = a_i` for attacker-known scalars — yielding a group key whose discrete log the attacker alone knows — or identity shares collapsing `group_key` toward the identity/offset. Nothing in `new` rejects this; `debug_assert_eq` only exists in the dealer.

### Impact Explanation
`ThresholdKeys` is the root object for all FROST signing (`AlgorithmMachine::new(algorithm, keys)`), `view()`, `scale()`, and `offset()`. A party loading attacker-controlled serialized keys ends up "participating" in a threshold signature for a group key the attacker fully controls (unilateral forgery of any message under that key — the threshold security property is silently void), or a degenerate/identity group key producing signatures for a key no honest coalition intended. `view()`/`complete()` integrity checks only confirm internal consistency of the crafted shares, which the attacker controls end-to-end, so they pass.

### Likelihood Explanation
Requires feeding crafted bytes to `ThresholdKeys::read` — a listed untrusted-byte entry point. Once loaded, no subsequent check distinguishes attacker-consistent shares from a real DKG output, so exploitation is deterministic. The `complete()` signature check does not help because the attacker fabricated a self-consistent share set.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349), reject identity points in `verification_shares` (`point.is_identity()` → error), reject a zero `secret_share`, reject zero `Constant` interpolation coefficients, and reject an identity computed `group_key`. In `ThresholdKeys::read`, use the identity-rejecting point reader (as `Curve::read_G` does at crypto/frost/src/curve/mod.rs:125-131) rather than `Ciphersuite::read_G`.

### Proof of Concept
```rust
// t = n = 2, attacker-known scalars a1, a2 with Interpolation::Constant([1, 1])
let a = <Ristretto as Ciphersuite>::F::random(&mut OsRng);
let mut buf = vec![];
// curve ID header
buf.extend((Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(2u16.to_le_bytes()); // t
buf.extend(2u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes()); // i
buf.push(0);                    // Interpolation::Constant
buf.extend(Ristretto::F::ONE.to_repr());   // c[0]
buf.extend(Ristretto::F::ONE.to_repr());   // c[1]
buf.extend(a.to_repr());                   // secret_share = a (attacker known)
for _ in 0 .. 2 {
  buf.extend((Ristretto::generator() * a).to_bytes()); // attacker-controlled shares
}
let keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice()).unwrap();
// keys.group_key() == G * 2a; attacker knows 2a and can forge any signature.
// Using identity points for verification_shares likewise yields group_key == identity
// (before scalar/offset) without error.
```

The analogous checks that should revert — identity `verification_shares`, zero `secret_share`, zero `Constant` coefficients — all pass today because `ThresholdKeys::new` validates only participant indexes and counts.
