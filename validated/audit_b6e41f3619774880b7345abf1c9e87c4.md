### Title
ReceivedOutput deserialization performs no consistency validation, allowing fabricated outputs to be reported as received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Chainlink report where a price is accepted after only a `price > 0` check, `ReceivedOutput::read` accepts untrusted bytes after only checking that they decode. There is no verification that the claimed `offset` actually derives the output's `script_pubkey` from the wallet key, nor that the `outpoint` (txid, vout) actually resolves to the claimed `TxOut` on-chain. A `ReceivedOutput` produced by `Scanner::scan_transaction` is trustworthy because the scanner constructs it from real transaction data; a deserialized one is not, yet both are indistinguishable downstream.

### Finding Description
`ReceivedOutput` bundles three independent claims:

- `offset`: the scalar that turns the wallet's group key into the key that can spend this output [1](#0-0) 
- `output`: the `TxOut` (value + script_pubkey) claimed to be received
- `outpoint`: the claimed location of that output

The legitimate constructor, `Scanner::scan_transaction`, guarantees consistency: it only creates a `ReceivedOutput` when `output.script_pubkey` is in the `scripts` map (i.e., `script_pubkey == p2tr(key + offset*G)`), and the outpoint/TxOut pair is taken verbatim from the scanned transaction [2](#0-1) .

`ReceivedOutput::read` performs none of these checks. It reads an arbitrary scalar via `Secp256k1::read_F` and decodes an arbitrary `TxOut` and `OutPoint` via consensus decode, then returns the triple as a valid `ReceivedOutput` [3](#0-2) . Like the oracle consumer that only rejects `price <= 0`, the only "validation" is that the bytes parse:

- No check that `p2tr_script_buf(key + offset*G) == output.script_pubkey` — the offset may bear no relation to the output, making the output unspendable while it is counted as wallet funds.
- No check that the outpoint's transaction contains `output` at `vout` — the (outpoint, TxOut) binding is never verified, so a real outpoint can be paired with a fabricated value or script.
- No sanity checks on the decoded TxOut at all (e.g., value range beyond what consensus decode permits, dust, or script form).

Because `Offset`/key-derivation semantics matter here — `register_offset` explicitly warns that an offset not securely generated "may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script" [4](#0-3)  — an attacker-supplied offset with a matching attacker-crafted script_pubkey could also direct the wallet to track outputs spendable by someone else's script path.

### Impact Explanation
Funds reported received that are not spendable. Any component that consumes serialized `ReceivedOutput`s (e.g., a scanner reporting to a coordinator over an untrusted channel, or persisted wallet state restored from a tampered source) will treat attacker-fabricated outputs as wallet funds. Consequences:

- Inflated reported balance: an outpoint pointing at an unrelated output paired with a high-value TxOut is counted at face value via `value()` [5](#0-4) .
- Unspendable inputs selected for signing: the wallet will attempt to spend outputs whose script_pubkey does not match `key + offset*G`, or whose outpoints do not exist / are already spent, producing invalid transactions and potential fee burn in constructed spends.
- Wrong-key spend attempts: a mismatched offset yields signatures under the wrong tweaked key, so even a real output cannot be spent.

This mirrors the oracle finding's impact: insufficiently validated external data poisons a downstream financial judgment (account liquidity there, spendable-balance/input-selection here).

### Likelihood Explanation
Medium. Exploitation requires an unprivileged party to supply bytes to `ReceivedOutput::read` — a reachable path per the deserialization surface (any transport or storage of scanner results outside a trusted boundary). No cryptographic break, threshold collusion, or validator misbehavior is needed; only the ability to write the serialized blob. The missing checks are entirely absent from the code rather than bypassable, so success is deterministic once the path is reached.

### Recommendation
Bind the three fields on deserialization, or make fabrication impossible by construction:

1. Store/check the wallet key with the `Scanner` and, on `read`, verify `p2tr_script_buf(key + GENERATOR * offset) == Some(output.script_pubkey)`; reject otherwise.
2. Do not serialize the `TxOut` separately from the outpoint's authority — either re-fetch the output from the chain by outpoint after deserialization (trusting the RPC-verified UTXO rather than the blob), or include a proof/hash commitment binding `output` to the transaction committed by `outpoint.txid`.
3. Alternatively, narrow the serialized form: persist only `(offset, outpoint)` and always reconstruct `output` from the verified chain data, keeping `ReceivedOutput` construction private to `Scanner`.

### Proof of Concept
Conceptual, against `ReceivedOutput::read`:

```rust
// Attacker-controlled bytes fed to ReceivedOutput::read:
let mut buf = vec![];
buf.extend(Scalar::ZERO.to_bytes());                 // offset = 0
// TxOut: arbitrary value and a script_pubkey NOT equal to p2tr(group_key)
let fake = TxOut { value: Amount::from_sat(21_000_000_0000_0000u64.min(u64::MAX)),
                   script_pubkey: ScriptBuf::new_p2tr_tweaked(attacker_tweaked_key) };
buf.extend(serialize(&fake));
// Outpoint: any txid/vout the attacker chooses (need not exist or match `fake`)
buf.extend(serialize(&OutPoint::new(Txid::all_zeros(), 0)));

let out = ReceivedOutput::read(&mut &buf[..]).unwrap(); // accepted
assert_eq!(out.value(), /* fabricated value */);        // counted as received
// The wallet cannot spend it: offset 0 doesn't produce fake.script_pubkey,
// and the outpoint doesn't resolve to `fake`.
```

`read` succeeds with no error despite all three fields being mutually inconsistent — the analog of accepting a stale/incomplete `latestRoundData` answer after only a positivity check.

Caveat: I did not fully trace every caller of `ReceivedOutput::read` across the workspace, so the exact transport that exposes the untrusted-bytes path is asserted from the listed reachable surface rather than traced end-to-end.

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
