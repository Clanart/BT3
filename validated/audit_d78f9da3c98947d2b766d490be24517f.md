### Title
Unprivileged wallets can bypass the Ankr 1-year lock by calling `MasterMagpie.withdraw` directly - (File: `rewards/MasterMagpie.sol`, `wombat/AnkrBNBPoolHelper.sol`)

### Summary
`AnkrBNBPoolHelper` implements a vesting-like restriction (`unlockTime` / `lockedAmount`) intended to prevent Ankr-exploit-compensation recipients from withdrawing their staked position before a fixed unlock date. That check, however, only exists inside `AnkrBNBPoolHelper.withdraw()` — it is never enforced by `MasterMagpie`, the contract that actually custodies the user's staked `stakingToken` balance. Because `MasterMagpie.withdraw()` is a plain, permissionless function callable by any wallet for its own balance, a locked user can withdraw the same amount straight from `MasterMagpie`, completely skipping the lock check, exactly mirroring the reported "migration bypasses vesting" bug class (a privileged exit path exists that never re-checks the lock/vesting state enforced elsewhere).

### Finding Description
`AnkrBNBPoolHelper.batchDepositLPFor` deposits LP-derived `stakingToken` into `MasterMagpie` on behalf of compensation recipients and records the locked portion in `lockedAmount[_for[i]]`: [1](#0-0) 

The lock is only enforced in this helper's own `withdraw()` function, which checks `lockedAmount[msg.sender] > rest` (the remaining staked balance) against `unlockTime`: [2](#0-1) 

However, the actual custody of the staked `stakingToken` balance lives in `MasterMagpie`, and `MasterMagpie` exposes an unrestricted, user-callable `withdraw` function that any wallet can call for its own `UserInfo.amount`: [3](#0-2) 

`_onlyPoolHelper` restrictions only gate the `*For` variants (`depositFor`/`withdrawFor`), not the plain `withdraw`/`deposit` entry points: [4](#0-3) 

Since `MasterMagpie` has no knowledge of `AnkrBNBPoolHelper.lockedAmount` or `unlockTime`, a compensation recipient can simply call `MasterMagpie.withdraw(stakingToken, amount)` directly instead of going through `AnkrBNBPoolHelper.withdraw()`. This returns the raw, freely transferable `stakingToken` (the Wombat LP receipt token minted by `WombatStaking`) to the caller's wallet with no lock check whatsoever, entirely bypassing the intended one-year lock — analogous to the reported bug where `migrate()` let users move tokens to a new contract without honoring vesting restrictions enforced elsewhere in the same protocol.

### Impact Explanation
The `unlockTime`/`lockedAmount` mechanism exists specifically to guarantee that Ankr-exploit compensation funds remain locked for a fixed period. Because the enforcement lives only in a wrapper contract and not in the underlying custodian (`MasterMagpie`), any ordinary wallet holding a locked position can trivially unlock and freely transfer/sell its full staked balance before `unlockTime`, defeating the compensation scheme's core security guarantee. This is a direct bypass of an economic lock, resulting in early extraction of funds that were supposed to remain restricted — an unprivileged-wallet-reachable violation of the protocol's stated fund-locking guarantee.

### Likelihood Explanation
The path requires only a normal transaction from a wallet that already has a locked position (i.e., was included via `batchDepositLPFor`) calling the standard, non-privileged `MasterMagpie.withdraw` function — no admin, governance, or external protocol interaction is required. This is trivially and reliably exploitable by any affected user.

### Recommendation
Enforce the lock check (`unlockTime` / `lockedAmount`) at the `MasterMagpie` level (e.g., a generic lock/vesting registry checked inside `_withdraw`), or restrict withdrawal of the Ankr-compensation `stakingToken` so it can only be withdrawn through `AnkrBNBPoolHelper.withdraw()` (for example by having `MasterMagpie` consult the pool helper before allowing direct withdrawals for that specific staking token).

### Proof of Concept
1. `ankrOperator` calls `AnkrBNBPoolHelper.batchDepositLPFor(...)`, which sets `lockedAmount[user] += amount` and stakes `amount` of `stakingToken` for `user` via `MasterMagpie.depositFor(stakingToken, amount, user)`.
2. Before `unlockTime`, `user` calls `MasterMagpie.withdraw(stakingToken, amount)` directly (no restriction other than `whenNotPaused`/`nonReentrant`).
3. `MasterMagpie` transfers `amount` of the raw `stakingToken` (Wombat LP receipt token) to `user`'s wallet, since `_withdraw` never consults `AnkrBNBPoolHelper.lockedAmount`/`unlockTime`.
4. `user` now holds a freely transferable ERC20 receipt token representing the "locked" value and can transfer/sell it immediately, fully bypassing the intended one-year lock enforced only in `AnkrBNBPoolHelper.withdraw()`.

        if (msg.sender != ankrOperator) revert NotAllowed();
        if (_for.length != _ratios.length) revert LengthMisMatch();
        
        uint256 totalRatio=0;
        for(uint256 i=0; i<_ratios.length; ++i){
            totalRatio+=_ratios[i];
        }
        if(totalRatio != DENOMINATOR) revert NotAllowed();

        uint256 beforeDeposit = IERC20(stakingToken).balanceOf(address(this));
        IWombatStaking(wombatStaking).depositLP(lpToken, _lpAmount, msg.sender);
        uint256 lpAmount = IERC20(stakingToken).balanceOf(address(this)) - beforeDeposit;

        IERC20(stakingToken).safeApprove(masterMagpie, lpAmount);

        for (uint256 i = 0; i < _for.length; i++) {
            uint256 amount = lpAmount * _ratios[i] / DENOMINATOR;
            lockedAmount[_for[i]] += amount;
            IMasterMagpie(masterMagpie).depositFor(stakingToken, amount, _for[i]);
            emit NewBatchDeposit(_for[i], amount);
        }
    }
