### Title
Default-permissive duplicate-key handling in ProtoJSON parser causes value-confusion between validated and parsed field values - ([File: src/google/protobuf/json/internal/parser.cc])

### Summary
The external report's failed invariant is: a JSON payload is inspected/displayed in one form, then re-parsed, and a JSON parser's silent handling of duplicate keys (keeping one value while discarding another) causes the value actually used by the application to differ from the value that was validated/shown, letting an attacker smuggle a different effective value past inspection. Protobuf's C++ ProtoJSON parser (`google::protobuf::json`) has the same class of behavior for singular, non-oneof fields: duplicate JSON keys are accepted by default and resolved by silent last-value-wins, rather than rejected, because `allow_legacy_nonconformant_behavior` defaults to `true` in the public API.

### Finding Description
`ParseOptions::allow_legacy_nonconformant_behavior` defaults to `true` in the public header, even though the comment states strict conformance ("recommended for new code... expected to eventually become the default") is the safer setting: [1](#0-0) 

In `ParseField`, when a field name is seen a second time, the code tracks `SeenState` and only rejects the duplicate if it is part of a `oneof`, or if it is a plain repeat of a singular field name **and** `allow_legacy_nonconformant_behavior` is false: [2](#0-1) 

Because the default is `true`, an ordinary (non-oneof) singular field that appears twice in a ProtoJSON document is *not* rejected: the second occurrence simply overwrites the first (no clear needed for scalars; message/repeated fields are cleared only on first sight and re-populated on the duplicate occurrence): [3](#0-2) 

This is also acknowledged for `null`-valued duplicates, where the implementation explicitly documents that duplicate-key checking is skipped even under strict mode for the `null` special case (bug `b/519557203`): [4](#0-3) 

The project's own conformance test suite confirms this is a known non-conformance for both the C++ and upb backends — `FieldNameDuplicate` and its casing variants are marked as accepted failures rather than fixed defects: [5](#0-4) [6](#0-5) 

In contrast, the pure-Python `json_format.Parse` API always rejects duplicate keys unconditionally via `_DuplicateChecker`, with no opt-out: [7](#0-6) 

This produces a genuine cross-implementation parser differential: the same attacker-controlled ProtoJSON bytes containing a duplicated field name will be **rejected** by Python's `json_format.Parse` but **silently accepted with last-value-wins** by the C++ `json::JsonStringToMessage`/`JsonToBinaryString` APIs under their default options. Any system that uses one implementation to validate/log/display a ProtoJSON payload (e.g., a security review, audit log, or gateway built on the Python or strict-mode C++ path) and a different implementation (default C++ ProtoJSON, which most callers use since they don't override `ParseOptions`) to actually act on the message will validate one value while acting on another — exactly the invariant violated in the original report ("what is shown/validated differs from what is actually parsed").

### Impact Explanation
Impact is bounded to the consuming application's trust model: if any component that receives attacker-controlled ProtoJSON relies on the *first* occurrence of a field for authorization/validation while the actual protobuf message construction (via the default-permissive C++ parser) uses the *last* occurrence, an attacker can smuggle a materially different value (e.g., a different `user_id`, `amount`, or `chain_id`-equivalent field) past validation while having a different value take effect — an integrity/authorization-bypass class issue analogous to HTTP request smuggling via duplicate headers. This is Medium severity: it requires a consuming application to have this specific pattern of "validate-then-reparse" or "dual-parser" design, and does not itself grant memory corruption or code execution.

### Likelihood Explanation
Likelihood is real but not universal: the vulnerable condition (default `allow_legacy_nonconformant_behavior=true`) is the out-of-the-box behavior of `google::protobuf::json::JsonStringToMessage`/`BinaryToJsonString` for any caller who does not explicitly set `ParseOptions.allow_legacy_nonconformant_behavior = false`, which the project's own comments say is "recommended for new code" but is not enforced. Any bounded, valid ProtoJSON payload with a duplicated key for a non-oneof field reliably triggers last-wins overwrite; conformance tests confirm this is deterministic, known, and untracked as an active defect (accepted into the failure list rather than fixed).

### Recommendation
- Change the default of `ParseOptions::allow_legacy_nonconformant_behavior` to `false` for `JsonStringToMessage`/`JsonToBinaryStream`, or at minimum, always reject duplicate keys for non-repeated, non-oneof fields regardless of the legacy flag (mirroring what is already unconditionally done for oneof fields).
- Extend duplicate-key rejection to the `null`-valued case referenced in `b/519557203` instead of special-casing it out of the check.
- Document explicitly, in the public `json.h` header (not just in a `TODO`), that consuming applications performing validation on ProtoJSON prior to message construction must not assume first-occurrence semantics under default settings.

### Proof of Concept
Using the C++ `google::protobuf::json` public API with default `ParseOptions` (`allow_legacy_nonconformant_behavior` left at its default `true`), parse the following bounded ProtoJSON into a message with a singular string field `name`:
```json
{"name": "safe-value", "name": "attacker-value"}
```
Per `ParseField`'s `SeenState` logic (`parser.cc:1256-1267`), this succeeds (`absl::OkStatus()`), and the resulting message has `name == "attacker-value"`. The exact same bytes passed to `google.protobuf.json_format.Parse` in Python raise `ParseError: Failed to load JSON: duplicate key name.` (`json_format.py:432-438`), demonstrating the cross-implementation value/validation divergence for identical attacker-controlled input.

```python
def _DuplicateChecker(js):
  result = {}
  for name, value in js:
    if name in result:
      raise ParseError('Failed to load JSON: duplicate key {0}.'.format(name))
    result[name] = value
  return result
```
