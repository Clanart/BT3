### Title
Interest rate/fee-reserve parameter changes are applied retroactively over the full elapsed time window, skewing the on-chain liquidity/debt index preview used for zToken and debt pricing - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Each vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) computes its "next" liquidity/debt index by re-deriving the interest rate and liquidity rate from the *current* live parameters (`points-ir`, `fee-reserve`) and applying them across the *entire* elapsed `time-delta` since `last-update`, instead of using the rate that was actually in effect during that period.

### Finding Description
`next-index` and `next-liquidity-index` recompute `interest-rate` (from the live `points-ir` curve) and `calc-liquidity-rate` (from the live `fee-reserve`) and then multiply that freshly-recomputed rate by the *full* `time-delta` since `last-update`: [1](#0-0) 

```
(define-private (next-index)
  ... 
        (let (
            (rate (interest-rate))
            (time-delta (- stacks-block-time (var-get last-update)))
            ...
          (calc-index-next idx multiplier)))))

(define-private (next-liquidity-index)
  ...
        (let (
            (rate (interest-rate))
            (liquidity-rate (calc-liquidity-rate rate (utilization) (var-get fee-reserve)))
            (time-delta (- stacks-block-time (var-get last-update)))
            ...
          (calc-index-next lidx multiplier)))))
```

`interest-rate` reads the live `points-ir` variable, and `calc-liquidity-rate` reads the live `fee-reserve` variable: [2](#0-1) [3](#0-2) 

If governance/admin updates the interest-rate curve (`points-ir`) or the protocol fee (`fee-reserve`) via the DAO-controlled setter, any subsequent call to `next-index`/`next-liquidity-index` (either during a real accrual on `deposit`/`withdraw`/`borrow`, or via a read-only preview getter that other contracts rely on for pricing) applies the *new* rate retroactively across the whole `time-delta` since the last real accrual, rather than only from the moment of the parameter change forward. This is exactly the bug class described in the external report: the getter re-derives the rate live instead of using the cached rate that was actually accrued for the pre-change portion of the elapsed period.

This index feeding function is the same one used by `get-vault-liquidity-index`/`get-vault-borrow-index` in the price utility contract, which is used by `get-asset-price` to price zTokens (via liquidity index) and outstanding debt (via borrow index) for USD-value/health calculations: [4](#0-3) [5](#0-4) 

### Impact Explanation
Because `get-asset-price` for zTokens multiplies the underlying price by this live-recomputed liquidity index, and debt USD value is computed from the live-recomputed borrow index, a parameter change (rate curve or fee-reserve) that has not yet been "settled" by a real accrual transaction will cause the pricing/health-check path to apply the new rate over the entire un-accrued window instead of just the post-change portion. Depending on the direction of the parameter change, this either inflates collateral valuation (zToken price too high, letting a position appear healthier or under-collateralized borrowing succeed) or deflates/inflates debt valuation, skewing the health verdict used for borrow/liquidation decisions. This lands on the in-scope "temporary freezing of funds" / mispriced-liquidation class, matching the original report's High severity classification for the same root cause (recomputing the rate live instead of caching it).

### Likelihood Explanation
Requires a legitimate (non-compromised) governance parameter update to `points-ir` or `fee-reserve` followed by any read of the price/health path before the next state-changing accrual occurs on that vault — a normal, expected sequence of operations rather than an attack requiring privileged access, making it Medium likelihood as in the original report.

### Recommendation
Cache the rate that was actually in effect at `last-update` (or split accrual at the exact block/timestamp a parameter changes) instead of re-deriving `interest-rate`/`calc-liquidity-rate` from live `points-ir`/`fee-reserve` values when computing `next-index`/`next-liquidity-index` for time spans that predate the parameter change.

### Proof of Concept
1. At `t0`, vault has `fee-reserve = 1000` bps and accrues normally; `last-update = t0`.
2. At `t1 = t0 + 1 hour`, governance calls the fee-reserve setter to change `fee-reserve` to `2000` bps (no accrual transaction is triggered by the setter itself).
3. At `t2 = t1 + 1 minute`, a user (or off-chain caller) queries pricing/health via `v0-1-data.clar`'s `get-asset-price`/`get-vault-liquidity-index`, which calls `next-liquidity-index`. This recomputes `calc-liquidity-rate` using the *new* `fee-reserve = 2000` bps but applies it over the full `time-delta = t2 - t0` (1 hour + 1 minute), even though `fee-reserve` was `1000` bps for the first hour.
4. The returned liquidity index (and thus zToken price) diverges from what would have accrued with the correct time-weighted rate, skewing collateral valuation used in downstream health/liquidation checks.
