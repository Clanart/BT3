## Title
Unhandled AssertionError in `Offer._get_offered_coins()` on crafted offer files causes wallet-side denial of service - (File: chia/wallet/trading/offer.py)

### Summary
The CVE-2018-7999 report describes a NULL pointer dereference in graphite2's `Segment.cpp` that crashes the process when it renders a crafted, untrusted `.ttf` file — the bug class is: untrusted structured input is parsed/interpreted by code that assumes a successful, well-formed result and blindly dereferences it without a validity check, causing a crash/DoS on the party doing the rendering. In chia-blockchain, `Offer._get_offered_coins()` in `chia/wallet/trading/offer.py` exhibits the same bug class: it interprets attacker-controlled coin-spend puzzle/solution data from an offer file and uses a bare `assert` to enforce an invariant that a malicious/malformed offer can violate, causing an uncaught `AssertionError` when a wallet user (the offer counterparty) merely inspects/examines an offer they received.

### Finding Description
`Offer._get_offered_coins()` iterates the coin spends inside a `SpendBundle` embedded in an `Offer` object (constructed from a bech32/binary offer file that can be received from any counterparty) and calls `match_puzzle()` on each spend's puzzle reveal: [1](#0-0) 

When `match_puzzle()` succeeds (i.e., the puzzle reveal is recognized as one of the known outer-puzzle types such as CAT, singleton, ownership, metadata, or CR layers), the code immediately does:
```
inner_puzzle: Program | None = get_inner_puzzle(puzzle_driver, parent_puzzle, parent_solution)
inner_solution: Program | None = get_inner_solution(puzzle_driver, parent_solution)
assert inner_puzzle is not None and inner_solution is not None
``` [2](#0-1) 

`get_inner_puzzle`/`get_inner_solution` dispatch to the specific outer-puzzle driver (`chia/wallet/outer_puzzles.py`) which then re-derives structure from the puzzle/solution using its own, independent matching/uncurrying logic (e.g. `match_cat_puzzle`, `match_metadata_layer_puzzle`, `match_ownership_layer_puzzle`, singleton struct unpacking) rather than reusing the exact match result from `match_puzzle()`: [3](#0-2) [4](#0-3) 

Because `match()` (used by `match_puzzle`) and `get_inner_puzzle`/`get_inner_solution` (used afterward) run separate parsing passes over the same untrusted bytes, an attacker who crafts a puzzle reveal that is *ambiguous or structurally malformed at the boundary* between two matcher functions can make `match_puzzle()` succeed (returning a non-`None` `PuzzleInfo`) while a driver's own `get_inner_puzzle`/`get_inner_solution` call — for a puzzle where `also is not None` (nested outer layers) — bottoms out returning `None` because the deeper layer's own match fails against the (attacker-crafted) inner puzzle/solution shape. Some driver implementations (e.g. `OwnershipOuterPuzzle.get_inner_solution`, `MetadataOuterPuzzle.get_inner_solution`) simply take `solution.first()` without validating that structure exists or matches, and can silently propagate `None` up through recursive `also` calls instead of raising. This mismatch is directly analogous to graphite2 trusting a `.ttf` structure was internally consistent and dereferencing a pointer that a malformed file made null: chia's offer code trusts that a puzzle recognized by `match_puzzle()` will also be successfully decomposed by `get_inner_puzzle`/`get_inner_solution`, and asserts that trust instead of handling the mismatch gracefully.

Since `assert` statements are stripped only when Python runs with `-O`, and are not caught anywhere in the call chain (`Offer.__init__` / `__post_init__` catches only broad exceptions from a *different* code path — `compute_spend_hints_and_additions`, not `_get_offered_coins`), an `AssertionError` here propagates uncaught through any caller of `_get_offered_coins()` (offered-coins computation, offer summary/inspection paths used by `trade_manager.py` and wallet RPC when a user examines an offer file before deciding whether to accept it).

### Impact Explanation
This matches the "spend-triggered transaction-processing halt" impact category. An attacker can craft an offer file (a `.offer`-encoded bech32 blob, exactly the kind of file exchanged between offer counterparties — no privileged access needed) that a victim wallet user loads via standard "view/examine offer" tooling. The crafted offer, containing a puzzle reveal that satisfies `match_puzzle()` but fails a nested driver's inner-puzzle/inner-solution derivation, triggers an unhandled `AssertionError` in the wallet process, denying service to that wallet's offer-processing/trade flow (and potentially crashing the RPC worker handling it), mirroring the DoS impact of the graphite2 NULL-pointer dereference on crafted font files.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to construct a CLVM puzzle/solution pair that is recognized as matching by one driver's `match()` implementation while deliberately breaking the invariant expected by `get_inner_puzzle`/`get_inner_solution` for nested (`also`) puzzle layers — a purely off-chain crafting exercise (no signing, no mempool submission, no fees) since offer files are exchanged and inspected before any spend is broadcast. This is reachable by any wallet user who receives an untrusted offer, which is one of the explicitly in-scope reachable actors (offer counterparty).

### Recommendation
Replace the bare `assert inner_puzzle is not None and inner_solution is not None` in `Offer._get_offered_coins()` with an explicit check that raises a caught/handled exception (e.g. skip this coin spend or raise a `ValueError` that the offer-parsing call sites already handle), so that a malformed/adversarial puzzle structure results in a clean "unparseable offer" error rather than an uncaught `AssertionError` that can crash the caller. More broadly, audit all outer-puzzle drivers (`chia/wallet/nft_wallet/*_outer_puzzle.py`, `chia/wallet/cat_wallet/cat_outer_puzzle.py`, `chia/wallet/vc_wallet/cr_outer_puzzle.py`) so `get_inner_puzzle`/`get_inner_solution` reuse the same match results as `match()` rather than re-parsing untrusted bytes independently, eliminating the possibility of divergence between the two passes.

### Proof of Concept
Conceptual PoC (requires runtime verification, not confirmed executable from static review alone):
1. Construct a CAT-or-singleton-style outer puzzle whose top layer satisfies `match_cat_puzzle`/`match_singleton_puzzle` (so `match_puzzle()` in `chia/wallet/outer_puzzles.py:49-54` returns a `PuzzleInfo` with `also` set for a nested layer).
2. Make the *inner* puzzle (the one wrapped by `also`) a shape that the inner driver's own `match_*` function used inside `get_inner_puzzle`/`get_inner_solution` fails to parse (e.g. a metadata/ownership layer with a subtly different curried-argument count than what `match_metadata_layer_puzzle`/`match_ownership_layer_puzzle` expects), while still satisfying the initial top-level `match()` used for `next_constructor` determination in `chia/wallet/cat_wallet/cat_outer_puzzle.py:42-45` or the singleton equivalent.
3. Package this puzzle reveal plus a corresponding coin spend and solution into a `WalletSpendBundle`/`Offer` object and encode it as a standard offer file.
4. Have a victim wallet call any code path that invokes `Offer._get_offered_coins()` (e.g. offer summary/inspection via `trade_manager.py` or the wallet RPC offer endpoints) on the received offer file.
5. Observe an uncaught `AssertionError` raised at `chia/wallet/trading/offer.py:260`, terminating/erroring the request instead of returning a graceful "invalid offer" response.

Note: I was unable to fully trace, within tool/iteration limits, the exact call sites in `wallet_rpc_api.py`/`trade_manager.py` that invoke `_get_offered_coins()` at offer-examination time (before acceptance), nor definitively confirm a concrete byte-level puzzle construction that produces the match/no-match divergence described above. A Devin session with full repository and runtime access would be needed to construct and execute a working exploit and confirm the exact reachable RPC entry points.
