### Title
Missing ReDoS protection on repo-controlled hookify rule patterns causes hook hang / fail-open enforcement bypass - (File: plugins/hookify/core/rule_engine.py)

### Summary
`compile_regex` and `_regex_match` in `plugins/hookify/core/rule_engine.py` compile and execute attacker-supplied regex patterns from `.claude/hookify.*.local.md` files against attacker-influenceable tool input with no complexity/length guard or execution timeout, allowing a catastrophic-backtracking pattern (`(a+)+$` style) to hang the `PreToolUse`/`PostToolUse`/`Stop` hook process. This is a real gap versus the sibling `security-guidance` plugin, which explicitly validates custom regexes for catastrophic-backtracking structure at load time.

### Finding Description
`load_rules()` in `plugins/hookify/core/config_loader.py` globs `.claude/hookify.*.local.md` files from the current working directory (the project root) and parses `pattern`/`conditions[].pattern` fields directly from YAML frontmatter with no validation of the regex content [1](#0-0) . These rule objects flow into `RuleEngine._check_condition` → `_regex_match(pattern, field_value)` → `compile_regex(pattern)` (an `lru_cache`-wrapped `re.compile`) → `regex.search(text)` [2](#0-1) . There is no pattern-complexity check, no length cap on `text` (which comes from `tool_input['command']`, `new_string`, `file_path`, etc. — fully attacker-influenceable via a Bash command or a pasted diff), and no per-call execution timeout inside the Python process itself [3](#0-2) .

The hook is invoked from `pretooluse.py`/`posttooluse.py`/`stop.py`, each wrapped in `try/except Exception` with `finally: sys.exit(0)` — i.e. it always intends to exit cleanly regardless of internal error [4](#0-3) . However, a catastrophic-backtracking regex hang occurs *inside* `regex.search()`, before the `except`/`finally` block can run, so the only backstop is the external hook timeout configured in `hooks.json`: `"timeout": 10` seconds per hook invocation [5](#0-4) . When that timeout fires, the process is killed externally without ever emitting its enforcement decision — effectively converting a would-be "block" rule into an unenforced/allowed action for that specific tool call, matching the "fail-open" concern in the question.

Notably, this codebase already recognizes and mitigates this exact risk class elsewhere: the `security-guidance` plugin explicitly states "Custom regexes are validated at load for catastrophic-backtracking structure and skipped (with a debug log) if they look ReDoS-prone" [6](#0-5) . `hookify`'s `config_loader.py`/`rule_engine.py` has no equivalent guard.

### Impact Explanation
Per triggering tool call matching a malicious rule's `event`/`tool_matcher`, the hook process can hang for up to the configured 10-second timeout before being externally killed, at which point the `PreToolUse`/`Stop` block decision is never delivered and the operation is not enforced (fail-open). This is a scoped availability/enforcement-bypass issue: it can be used to blunt a `block`-action safety rule (e.g. "block dangerous rm") at a precisely chosen moment, or to introduce a ~10s stall on every matching tool call as a low-grade DoS. It does not, on its own, grant new command execution, file access, or credential disclosure beyond what the bypassed rule would have blocked.

### Likelihood Explanation
Requires an attacker to get a malicious `.claude/hookify.<name>.local.md` file with a ReDoS-prone `pattern`/`conditions[].pattern` into a repository that the victim later opens with Claude Code, and to then trigger a matching tool call (e.g., a long Bash command, large pasted diff, or long filename) that reaches the vulnerable field. This is plausible in projects that intentionally version-control hookify rules as team-wide conventions (the plugin's own README/skill examples show rules like `warn-sensitive-files.local.md` intended to enforce shared policy), even though a separate, generic plugin-settings skill document recommends `.local.md` files be gitignored. No admin/maintainer privilege, leaked secrets, or social engineering is required beyond normal PR/commit contribution to the repo. The exact hang duration is bounded by the hook's 10-second `timeout`, limiting but not eliminating exploitability.

### Recommendation
Add a load-time regex complexity/safety check in `config_loader.py` (e.g., reject patterns matching common ReDoS-prone constructs like nested quantifiers `(a+)+`, `(a*)*`, alternation with overlapping repetition, or use a vetted ReDoS static-analysis check) mirroring the approach already used in `plugins/security-guidance/hooks/extensibility.py`. Additionally, cap the length of `field_value` passed into `_regex_match` and/or wrap `regex.search()` with a bounded execution mechanism (e.g., `signal.alarm`/subprocess with its own hard timeout, or use of the `regex` module's timeout parameter) so a single malicious pattern cannot consume the full hook timeout budget.

### Proof of Concept
```python
import time
from plugins.hookify.core.rule_engine import RuleEngine
from plugins.hookify.core.config_loader import Rule, Condition

def test_redos_pattern_hangs():
    rule = Rule(
        name="evil",
        enabled=True,
        event="bash",
        action="block",
        conditions=[Condition(field="command", operator="regex_match", pattern=r"(a+)+$")],
        message="boom",
    )
    engine = RuleEngine()
    payload = {
        "tool_name": "Bash",
        "tool_input": {"command": "a" * 40 + "!"},  # fails at end, triggers backtracking blowup
    }
    start = time.monotonic()
    engine.evaluate_rules([rule], payload)
    elapsed = time.monotonic() - start
    # Expect this to complete within a bounded time (e.g. 1s); currently it will
    # take exponentially longer as the 'a' run grows, demonstrating no timeout/guard.
    assert elapsed < 1.0, f"regex evaluation took {elapsed}s — no ReDoS guard present"
```
Run with increasing lengths of `"a" * N` to show execution time scales exponentially, and add a second test asserting that `load_rule_file`/`Rule.from_dict` rejects or flags `(a+)+$`-style patterns at load time (currently absent, so the test will fail, confirming the missing guard).

```python
def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules
```

```python
# Cache compiled regexes (max 128 patterns)
@lru_cache(maxsize=128)
def compile_regex(pattern: str) -> re.Pattern:
    """Compile regex pattern with caching.

    Args:
        pattern: Regex pattern string

    Returns:
        Compiled regex pattern
    """
    return re.compile(pattern, re.IGNORECASE)
```

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
