### Title
`ReceivedOutput::read` accepts a spending offset inconsistent with the output's `script_pubkey`, reporting funds as received that are not spendable - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
Analogous to `liquidateVaultsForToken()` invoking the swapper without ever delivering the sell tokens (so the swapper's balance check reverts and the funds are unusable), `ReceivedOutput::read` deserializes a claimed spend-offset together with a `TxOut`/`OutPoint` without ever verifying that `key + offset·G` actually produces the output's `script_pubkey`. The output is treated as spendable, yet no key under that claimed offset can sign for it.

### Finding Description
`ReceivedOutput` pairs `offset` (the scalar added to the group key to obtain the spending key) with the raw `TxOut` and `OutPoint`. `read` performs only syntactic decoding — `Secp256k1::read_F`, `TxOut::consensus_decode`, `OutPoint::consensus_decode` — and returns `Ok` for any combination [1](#0-0) . The only place consistency is enforced is inside `Scanner`, which builds `ReceivedOutput`s from its own `scripts` map [2](#0-1) . Anything arriving through `read` (e.g., `Output::read` in the processor, which wraps `ReceivedOutput::read`) bypasses that construction [3](#0-2) .

The inconsistency then propagates:

- `Output::key()` recovers the purported group key as `scriptKey − offset·G`, so a forged offset silently re-attributes the output to a completely different key [4](#0-3) .
- When a spend is attempted, `SignableTransaction::multisig` computes `keys.offset(offset)` and requires `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey`; a mismatched offset makes this return `None`, aborting the spend [5](#0-4) .

### Impact Explanation
A `ReceivedOutput` obtained from untrusted bytes claims a balance and a spending key that do not correspond. Downstream code records it as a received output belonging to key `K' = scriptKey − offset·G`, schedules it into plans, and only discovers at multisig construction time that no valid signature can be produced — the equivalent of the swapper's `InsufficientBalance` revert. Funds reported as received are permanently unspendable under the reported key, and the misattribution can wedge plans built on the output (signing for the input fails, so the whole transaction cannot be completed).

### Likelihood Explanation
Any path feeding attacker-controlled bytes into `ReceivedOutput::read`/`Output::read` reaches this with a trivial serialization: pick a real UTXO paying to the victim's script, attach an arbitrary scalar as `offset`. No key knowledge is needed — unlike `Scanner::register_offset`, there is no parity or membership check, so even `offset = 0` against an offset-registered script, or a random scalar, is accepted. The exploit requires only malformed input bytes, not any cryptographic capability.

### Recommendation
Either validate at `read` time (requires the group key, so likely a `read_for(key)` variant checking `p2tr_script_buf(key + G·offset) == output.script_pubkey`), or reject `ReceivedOutput`s constructed outside `Scanner` and treat deserialization as untrusted by re-deriving the script before use. At minimum, `Output::key()` should not be relied on to attribute ownership for deserialized outputs whose offset was never checked against the script.

### Proof of Concept
```rust
// networks/bitcoin: a UTXO paying to K + a·G is claimed under offset b
let real = scanner.scan_transaction(&tx)[0].clone(); // offset = a, script = p2tr(K + a·G)
let forged_offset = Scalar::random(&mut OsRng);        // b != a

let mut bytes = vec![];
bytes.extend(forged_offset.to_bytes());                // read_F
bytes.extend(bitcoin::consensus::encode::serialize(real.output()));
bytes.extend(bitcoin::consensus::encode::serialize(real.outpoint()));

let ro = ReceivedOutput::read(&mut bytes.as_slice()).unwrap(); // accepted, no consistency check

// processor::Output::key() => (K + a·G) - b·G = wrong key, misattributes the funds
// SignableTransaction::new(vec![ro], ...) then multisig(&keys) returns None:
// p2tr_script_buf(K + b·G) != script_pubkey -> spend impossible
```
Funds are reported received and attributed to `K + (a−b)·G`, yet no key can sign for the input — the direct analog of the swapper being invoked without ever receiving the sell tokens.
