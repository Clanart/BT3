Based on the code evidence, here is the closest structural analog to the Solidity bug: **a security invariant established by one initialization/setup step gets silently undone by a later step in the same chain**, because Desktop's request-filter pipeline is order-dependent and each filter operates independently without knowledge of what earlier filters already enforced.

### Title
Authorization token can be re-attached to a redirected request after the same-origin protection strips it, due to filter ordering in the `OrderedWebRequest` pipeline - (File: `app/src/main-process/authenticated-image-filter.ts`)

### Summary
`app/src/main-process/main.ts` wires up three independent `onBeforeSendHeaders` filters, in this fixed order: `installSameOriginFilter`, then `installAliveOriginFilter`, then `installAuthenticatedImageFilter`. [1](#0-0) 
`OrderedWebRequest` runs all registered `onBeforeSendHeaders` listeners for a request **sequentially in insertion order**, feeding the output of one into the next. [2](#0-1) 

### Finding Description
`installSameOriginFilter` exists specifically to strip `authorization`/`authentication`/`cookie` headers whenever a request's origin changes across a redirect, because plain `fetch` will otherwise happily forward credentials cross-origin. [3](#0-2) 

`installAuthenticatedImageFilter`, however, is registered *after* that filter and makes its decision purely from the **current** `details.url`'s origin and pathname — it has no concept of the request's original origin or of redirects at all: [4](#0-3) 

Because it runs last in the chain, it reintroduces an `Authorization: token …` header on the very same request/redirect hop that `installSameOriginFilter` just sanitized. The two filters were clearly designed to cooperate (one strips credentials on origin change, the other adds credentials for a known set of origins) but neither is aware of the other, and the initialization order in `main.ts` means the credential-adding step always has the final say. This is the same class of defect as the Solidity report: a step meant to be a *sub-step of a protected chain* (`onlyInitializing`) is instead treated as independently authoritative (`initializer`), so the guarantee the earlier step was supposed to provide for the whole chain is not preserved.

### Impact Explanation
If a GHES/private-asset URL that Desktop treats as authenticated (an enterprise avatar path or a `.../assets/...` repo-asset path controlled by attacker-supplied repository/PR/comment content rendered in the app) is served with a redirect, `installAuthenticatedImageFilter` re-evaluates the redirected URL on its own and will attach the enterprise/GitHub API token if the redirected URL's origin happens to be one Desktop already holds a token for and the path matches its regexes, regardless of what the same-origin filter just decided for that hop. This defeats the explicit design intent documented in `same-origin-filter.ts` — that authorization data must never survive an origin change unless a filter has actually verified it's safe to do so — and does so specifically for the credential type (API tokens) that the app treats as most sensitive.

### Likelihood Explanation
The attacker primitive matches the accepted scope: attacker controls content rendered by Desktop (a repository asset / avatar URL embedded in a PR, issue, or commit rendered by the app) and can therefore control what URL/redirect chain the app's image loader will hit. No local access, admin rights, or prior compromise is needed — only that the app fetch a URL whose path matches `isEnterpriseAvatarPath`/`isGitHubRepoAssetPath` and that gets redirected.

### Recommendation
Make `installAuthenticatedImageFilter` redirect-aware in the same way `installSameOriginFilter` is (track the initiating request's origin by `details.id`) and only add the `Authorization` header when the current origin equals the request's original origin, or run token-attachment logic before the same-origin filter so the origin-sanitization step is always the last and authoritative word for a given request/redirect chain.

### Proof of Concept
1. User has an account token for `https://ghes.example.com` (private repo asset support enabled).
2. Attacker-controlled content in a repo/PR rendered by Desktop references an image URL of the form `https://ghes.example.com/owner/repo/assets/<id>/<guid>` that the GHES server (or attacker-controlled proxy in front of it) responds to with an HTTP redirect to another URL matching `isGitHubRepoAssetPath`/`isEnterpriseAvatarPath` on a different origin Desktop also holds a token for.
3. `installSameOriginFilter` strips any pre-existing auth headers for that hop as designed, but `installAuthenticatedImageFilter`, running afterward and unaware of the redirect/original origin, independently re-attaches the `Authorization` header for the new destination based solely on the current URL, exposing the token to the redirected destination instead of only the intended origin.

export function installSameOriginFilter(orderedWebRequest: OrderedWebRequest) {
  // A map between the request ID and the _initial_ request origin
  const requestOrigin = new Map<number, string>()
  const safeProtocols = new Set(['devtools:', 'file:', 'chrome-extension:'])
  const unsafeHeaders = new Set(['authentication', 'authorization', 'cookie'])

  orderedWebRequest.onBeforeRequest.addEventListener(async details => {
    const { protocol, origin } = new URL(details.url)

    // This is called once for the initial request and then once for each
    // "subrequest" thereafter, i.e. a request to https://foo/bar which gets
    // redirected to https://foo/baz will trigger this twice and we only
    // care about capturing the initial request origin
    if (!safeProtocols.has(protocol) && !requestOrigin.has(details.id)) {
      requestOrigin.set(details.id, origin)
    }

    return {}
  })

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const initialOrigin = requestOrigin.get(details.id)
    const { origin } = new URL(details.url)

    if (initialOrigin === undefined || initialOrigin === origin) {
      return { requestHeaders: details.requestHeaders }
    }

    const sanitizedHeaders: Record<string, string> = {}

    for (const [k, v] of Object.entries(details.requestHeaders)) {
      if (!unsafeHeaders.has(k.toLowerCase())) {
        sanitizedHeaders[k] = v
      }
    }

    log.debug(`Sanitizing cross-origin redirect to ${origin}`)
    return { requestHeaders: sanitizedHeaders }
  })
