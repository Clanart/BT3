### Title
Out-of-range `Participant` in a blame accusation panics via unguarded `HashMap` indexing in PedPoP blame handling - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` (and the shared `blame_internal` helper) take attacker-influenced `sender` and `recipient` `Participant` indexes and use them to directly index `self.commitments` and `self.decryption.enc_keys`. `Participant` only enforces "non-zero u16" — there is no check that `sender`/`recipient` are within `1 ..= n` of the DKG that produced `commitments`/`enc_keys`. Passing an index greater than `n` (or, for `AdditionalBlameMachine`, any index not among the registered participants) panics on `HashMap` indexing instead of returning an error, crashing the calling process. This is the Serai analog of CVE-2025-65563: a missing-element validation gap reachable from an untrusted accusation message that turns a "who is faulty?" lookup into a panic.

### Finding Description
`Participant` is a newtype over `u16` whose only invariant is non-zero (`Participant::new` rejects only 0, e.g. `crypto/dkg/src/lib.rs:600` and `coordinator/src/tributary/transaction.rs:346-354` show untrusted bytes becoming `Participant`s with no upper bound).

`blame_internal` indexes `self.commitments[&sender]` without a membership check: [1](#0-0) 

`decrypt_with_proof` (reached from `blame_internal` before the `commitments` index when a proof is attached) indexes `self.enc_keys[&decryptor]`, where `enc_keys` is only populated for participants `1 ..= n` via `register`: [2](#0-1) [3](#0-2) 

`AdditionalBlameMachine::new` explicitly builds `commitments`/`enc_keys` with exactly `1 ..= n` keys, so any `sender`/`decryptor` index `> n` (or an index absent because `commitment_msgs` keyed by attacker-declared indexes differ) is a guaranteed panic: [4](#0-3) 

The `blame` APIs return `(AdditionalBlameMachine, Participant)` / `Participant` — there is no `Result`, so the panic cannot even be handled as an error: [5](#0-4) 

Compare with the rest of the codebase, which does bound-check externally-sourced indexes (`ThresholdParams::new` rejects `i > n`, `crypto/dkg/src/lib.rs:166-179`; `ThresholdKeys::view` rejects `included.last() > n`, `crypto/dkg/src/lib.rs:487-491`). The blame path simply never performs the equivalent check.

### Impact Explanation
Any process driving PedPoP blame adjudication — e.g., a processor evaluating `InvalidDkgShare`-style accusations whose `accuser`/`faulty` fields are deserialized from untrusted bytes as unbounded `Participant`s — can be crashed by an accusation naming a `sender` or `recipient` index `> n`. A panic during blame processing aborts the node/daemon, halting DKG fault resolution and any dependent signing work. Repeatable by any party able to submit an accusation message: pure availability loss (High/Medium depending on how blame accusations are sourced).

### Likelihood Explanation
`blame` takes four attacker-influenced arguments (`sender`, `recipient`, `msg`, `proof`) and no bound check exists anywhere along `blame → blame_internal → decrypt_with_proof → enc_keys[&decryptor]` or `blame_internal → commitments[&sender]`. The only thing required is a `Participant` value outside the registered set, which the `Participant` type itself permits (it is only guaranteed non-zero). No valid proof, signature, or share is needed to reach the panic — in `blame_internal`, an attached `proof` routes through `decrypt_with_proof` which panics on `enc_keys[&decryptor]` before any proof verification completes, and even without a proof a bogus `sender` panics on `commitments[&sender]`. The one mitigating assumption is that the caller must invoke `blame` with attacker-controlled indexes; the library documents the `msg` as needing authentication, but places no documented requirement on `sender`/`recipient` bounds.

### Recommendation
Bound-check `sender` and `recipient` before indexing: return the accuser/`recipient` as faulty (or a dedicated error) when either index is not present in `commitments`/`enc_keys`. Concretely, in `blame_internal` replace `self.commitments[&sender]` with `self.commitments.get(&sender)` returning `recipient` (a malformed accusation) on `None`, and in `Decryption::decrypt_with_proof` replace `self.enc_keys[&decryptor]` with `get(&decryptor).ok_or(DecryptionError::InvalidProof)?`. Making `blame`/`blame_internal` return `Result<_, PedPoPError>` for out-of-set indexes would be cleaner still.

### Proof of Concept
```rust
// After an honest n-participant PedPoP run, construct a blame evaluator:
let mut blame_eval = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs)
    .unwrap();

// commitments/enc_keys now contain exactly Participants 1..=n.
// An accusation message carries an attacker-chosen "faulty" index:
let bogus_sender = Participant::new(n + 1).unwrap(); // valid Participant (nonzero)
let honest_recipient = Participant::new(1).unwrap();

// Path A: without a proof -> panic on `self.commitments[&sender]`
//   (crypto/dkg/pedpop/src/lib.rs ~line 599)
blame_eval.blame(bogus_sender, honest_recipient, captured_msg, None);

// Path B: with any proof -> panic on `self.enc_keys[&decryptor]` inside
//   decrypt_with_proof (crypto/dkg/pedpop/src/encryption.rs ~line 388)
//   when `recipient` is out of range instead.
let bogus_recipient = Participant::new(u16::MAX).unwrap();
blame_eval.blame(Participant::new(1).unwrap(), bogus_recipient, captured_msg, Some(proof));
```

Both paths panic with `HashMap` index-out-of-bounds (key not present) rather than returning an error or attributing blame, mirroring the CVE's missing-IE → nil-deref panic.

  pub(crate) fn decrypt_with_proof<E: Encryptable>(
    &self,
    from: Participant,
    decryptor: Participant,
    mut msg: EncryptedMessage<C, E>,
    // There's no encryption key proof if the accusation is of an invalid signature
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Result<Zeroizing<E>, DecryptionError> {
    if !msg.pop.verify(
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    ) {
      Err(DecryptionError::InvalidSignature)?;
    }

    if let Some(proof) = proof {
      // Verify this is the decryption key for this message
      proof
        .dleq
        .verify(
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &[self.enc_keys[&decryptor], *proof.key],
        )
        .map_err(|_| DecryptionError::InvalidProof)?;

      cipher::<C>(self.context, &proof.key).apply_keystream(msg.msg.as_mut().as_mut());
      Ok(msg.msg)
    } else {
      Err(DecryptionError::InvalidProof)
    }
  }
