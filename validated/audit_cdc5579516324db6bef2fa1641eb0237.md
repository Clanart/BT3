### Title
Shared CallDispatcher balance conflation lets predispatch orders steal residual/dust token balances from unrelated orders - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder`'s predispatch path measures a user's "received" input amount as the *full* token balance swept out of the shared, gateway-wide `CallDispatcher` contract, not as the delta attributable to that specific order's transferred/produced tokens. Because `_params.dispatcher` is one singleton address reused by every order, any token balance a prior order's predispatch calldata leaves stranded on the dispatcher (a token not enumerated in that prior order's own `inputs` array, so never swept for it) sits there until a later, unrelated order that lists that token as an input sweeps the dispatcher's whole balance and folds it into its own `received` computation.

### Finding Description
In `placeOrder`, when `order.predispatch.call.length > 0`, tokens are pushed to `dispatcher`, arbitrary calldata is executed via `ICallDispatcher(dispatcher).dispatch(...)`, and then for each of the *current* order's `inputs` the code builds a sweep call that transfers the dispatcher's **total** balance (`IERC20(token).balanceOf(dispatcher)` / `dispatcher.balance`) back to the gateway: [3](#0-2) 

`received` is then computed as the delta on the *gateway's* own balance before/after the sweep, and is used directly as the order's escrowed `amount` when it doesn't exceed the requested amount: [2](#0-1) 

This mirrors the Neptune Mutual "conflated staking pool reward balance" defect: a shared/aggregate contract's raw token balance is used as a stand-in for a specific account's (here, a specific order's) entitlement, so any balance belonging to — or stranded by — a different context bleeds into the current one's accounting.

The concrete corrupted value is `order.inputs[i].amount` (and therefore `_orders[commitment][token]`, the escrow ledger written a few lines later): it is set from `IERC20(token).balanceOf(dispatcher)` at sweep time instead of from an amount provably contributed by the current order's `msg.sender`/predispatch execution. `dispatcher` is a single contract shared by all orders, so its balance is not partitioned per order — nothing prevents residue from Order A (a token that Order A's predispatch calldata produced/received but that is not part of Order A's own `inputs` list, so Order A's sweep loop never touches it and it is left on the dispatcher) from being scooped up by Order B's sweep if Order B lists that token as an input. Order B's `received` — and hence its escrowed `amount` — is inflated by tokens that were never actually contributed by Order B's own placer, letting an attacker fund (or over-fund) their own order's escrow with someone else's leftover tokens, or systematically harvest dust that the protocol's own accounting (`DustCollected`) was designed to capture for itself. Existing guards do not stop this: there is no per-order scoping of the dispatcher, no "expected balance before this order touched the dispatcher" baseline, and the `nonReentrant` guard on `placeOrder` only prevents reentrancy within a single call — it does nothing to prevent balance carry-over between two separate, sequential `placeOrder` transactions that both use the same shared dispatcher.

### Impact Explanation
An unprivileged user can place an order whose `predispatch.call` intentionally produces or leaves a token balance on the shared dispatcher that is *not* declared in that order's `inputs` (so it's never swept back for that order and is never counted as dust for that order either, since dust accounting only triggers when the token *is* one of the current order's declared inputs). A subsequent order — placed by the same or a different account — that lists that residual token as an input then absorbs it as legitimate "received" funds, and the escrow ledger (`_orders[commitment][token]`) is inflated accordingly. This lets an attacker fund escrow with tokens they never actually contributed to that order, subsequently withdrawing/canceling that order to redeem those tokens to themselves — a fund-diversion/loss primitive matching the bounty's "logic attacks" / "wrong beneficiary or amount" category, since value that should have been dust swept to the protocol treasury (or belonged to whatever party actually paid for it) is instead captured by an unrelated order's escrow.

### Likelihood Explanation
The attacker needs no privileged role, relayer, or prover — only the ability to call the public `placeOrder` entrypoint twice with crafted `predispatch.call` payloads (predispatch execution is fully attacker-controlled arbitrary calldata via `CallDispatcher`). The precondition is that the gateway is configured with `predispatch` enabled and a nonzero `_params.dispatcher`, which the codebase explicitly documents as a supported "swap-then-escrow" feature. Reliability depends on being able to leave a predictable residual balance and on no other order interleaving to consume it first, which is a timing consideration but not a blocker for a determined attacker (e.g., back-to-back transactions in the same block, or targeting low-traffic token pairs).

### Recommendation
Do not use the shared dispatcher's raw `balanceOf`/`.balance` as the basis for an order's `received` amount. Either (a) deploy an ephemeral, single-use dispatcher per order (e.g., a minimal proxy created and destroyed within the `placeOrder` call), or (b) snapshot the dispatcher's balance for every token type immediately before pushing this order's predispatch assets and treat only the incremental delta attributable to this order's own predispatch transfer as sweep-eligible, sweeping and accounting for any additional residual token types explicitly as protocol dust rather than allowing them to silently roll over into whichever order's `inputs` array happens to touch that token next.

### Proof of Concept
1. Governance configures `_params.dispatcher` = a shared `CallDispatcher` and predispatch is enabled.
2. Attacker calls `placeOrder` (Order A) with `predispatch.assets = [WETH: X]`, `predispatch.call` = a swap that converts WETH into DAI but only lists `WETH` (not `DAI`) in `order.inputs`; the swap leaves `Y` DAI stranded on the shared `dispatcher` because Order A's sweep loop only sweeps tokens present in `order.inputs` (WETH), never touching the DAI produced as a side effect. [4](#0-3) 
3. Attacker immediately calls `placeOrder` (Order B) with `order.inputs = [DAI: Y]` and a trivial/no-op `predispatch.call` that touches the dispatcher (or simply relies on `predispatch.assets` being empty while `predispatch.call.length > 0` to still route through the sweep path). Order B's sweep step reads `IERC20(DAI).balanceOf(dispatcher)` — which now includes the `Y` DAI stranded by Order A — and transfers it all to the gateway, setting `order.inputs[i].amount = received = Y` even though Order B's own caller contributed nothing. [5](#0-4) 
4. `_orders[commitmentB][DAI] += Y` is recorded as legitimate escrow for Order B. [6](#0-5) 
5. Attacker cancels Order B (same-chain) and redeems the `Y` DAI escrow to themselves via `_withdraw`, having paid nothing for it. [7](#0-6) 

Note: I was not able to fully trace every predispatch/`CallDispatcher` code path (e.g., exact `ICallDispatcher` implementation and whether it enforces any additional balance isolation) within the available indexed context, so the exact feasibility of leaving an unswept residual (step 2) should be independently verified against the live `CallDispatcher.sol` contract before treating this as fully confirmed exploitable.
