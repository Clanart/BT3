Based on the analog search, the strongest match to the "trusting unverified/attacker-supplied data for a security-critical decision" pattern from the `.latestRoundData()` report is in the trampoline credential helper's host-classification logic, not a price-cache issue (Desktop has no oracle). The relevant broken invariant is: **Desktop decides whether to treat a remote git host as a trusted GitHub/Enterprise host based on a header value that the remote server itself supplies**, then uses that decision to trigger an interactive sign-in / OAuth flow bound to the attacker's chosen endpoint.

### Title
Attacker-controlled `WWW-Authenticate` realm header spoofs GitHub Enterprise trust classification and triggers OAuth sign-in bound to an attacker endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind()` classifies an unknown git remote as `'enterprise'` (i.e. "this is a legitimate GitHub Enterprise host, worth signing in to") purely because the HTTP response Git captured from that remote contained a `WWW-Authenticate` header whose realm string equals `"GitHub"`. Since this header is emitted by the remote server (or an interposing proxy) that the user is fetching/pushing/cloning against, an attacker who controls that remote fully controls Desktop's trust classification for their own host, with no cryptographic or out-of-band verification involved.

### Finding Description
When Git needs credentials for a remote, it invokes Desktop's credential trampoline, which calls `getCredential()` → `getEndpointKind()`: [1](#0-0) 

The classification walks through `isGist`, `isDotCom`, `isGHE` (hostname pattern checks that an attacker cannot spoof without controlling DNS for `github.com`/`*.ghe.com`), but then falls through to inspecting `wwwauth[...]` credential fields that Git forwards verbatim from the server's HTTP response: [2](#0-1) 

If the value contains `realm="GitHub"`, the host is unconditionally classified as `'enterprise'` — a fully trusted GitHub Enterprise Server. This value is attacker-supplied: any git server (or a MITM proxy sitting between Desktop and the real remote) can emit `WWW-Authenticate: Basic realm="GitHub"` on an HTTP 401 response and be classified as `'enterprise'`, bypassing the only other verification path (`isGitHubHost(endpoint)`, an actual network probe) entirely.

Once classified `'enterprise'`, back in `getCredential()`: [3](#0-2) 

if no existing stored account matches that origin, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, which begins a real Enterprise sign-in flow, sets the sign-in endpoint to the attacker's own origin, and shows a native "Sign in" popup — all triggered transparently by a routine `git fetch`/`clone`/`push`, not by any unusual user action: [4](#0-3) 

That sign-in flow then performs the actual OAuth handshake against a URL derived from the attacker-controlled endpoint: [5](#0-4) 

`shell.openExternal(getOAuthAuthorizationURL(endpoint, csrfToken))` opens the user's browser to whatever authorize URL is derived from the attacker's endpoint. If the attacker implements a plausible OAuth authorize/callback surface, the resulting `Account` (with real, functioning `login`/`token` fields returned by the attacker's own OAuth callback) is persisted into `AccountsStore`, permanently bound to the attacker's chosen endpoint origin.

### Impact Explanation
This is an **unauthorized OAuth/account binding** vulnerability caused by an attacker-controlled git remote/proxy response (identical attacker capability class to the M-02 report's "attacker controls the data source used for a security decision"). Consequences:
- A spoofed, natively-triggered "Sign in to GitHub Enterprise" dialog appears during ordinary git operations against a malicious or MITM'd remote, with no unnatural user steps — the user is simply doing a normal fetch/clone/push.
- Successful completion binds a persistent `Account` for the attacker's endpoint into Desktop's trusted account store; `findGitHubTrampolineAccount` matches purely on origin equality (`app/src/lib/trampoline/find-account.ts:20-29`), so this endpoint will subsequently receive automatic credential-helper handling for that origin, forgoing further prompts to the user.
- No cryptographic verification (TLS pinning, known-endpoint allowlist, or reachable server capability check via `isGitHubHost`) gates the `'enterprise'` classification when the header path is taken — the network-probe fallback (`isGitHubHost`) is only reached if no `wwwauth[...]` header is present, so an attacker can simply always include the header to skip it.

### Likelihood Explanation
Moderate-to-high: any attacker who can stand up a git-over-HTTPS server (or MITM proxy on an untrusted network) that the victim clones/fetches/pushes to can trivially add a `WWW-Authenticate: Basic realm="GitHub"` response header — this requires no special privileges over the victim's machine, no leaked credentials, and no social engineering beyond the victim performing a routine git operation against a repository/remote they were told to add (a common onboarding action, e.g. "clone this repo").

### Recommendation
Do not derive host trust classification from a header value the remote itself controls. Require classification to rely only on: (1) exact matches against endpoints the user has explicitly configured/signed into, or (2) the authenticated network probe (`isGitHubHost`) — and even then, require explicit user confirmation before initiating an OAuth sign-in flow bound to a previously-unknown endpoint, clearly surfacing the destination hostname/origin so the user can detect endpoint spoofing before completing sign-in.

### Proof of Concept
1. Attacker sets up an HTTPS git server at `https://attacker.example.com/repo.git` (or a MITM proxy in front of any HTTP git remote).
2. Server is configured to respond to unauthenticated requests with `WWW-Authenticate: Basic realm="GitHub"`.
3. Victim runs `git clone https://attacker.example.com/repo.git` inside GitHub Desktop (or adds it as a remote and fetches/pushes).
4. Git invokes Desktop's credential trampoline; `getEndpointKind()` sees the `wwwauth[...]=...realm="GitHub"...` field and returns `'enterprise'`: [6](#0-5) 
5. `getCredential()` finds no matching account for `attacker.example.com` and calls `ui.promptForGitHubSignIn('https://attacker.example.com')`, which opens a legitimate-looking "Sign in to GitHub Enterprise" dialog and begins an OAuth flow rooted at that origin: [7](#0-6) 
6. If the attacker's server answers the OAuth handshake, the resulting account is stored and bound to `attacker.example.com` in `AccountsStore`, and the victim believes they've signed into a legitimate Enterprise host.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
