### Title
Cached coordinator preprocess reuse can leak validator signing keys - (File: `coordinator/src/tributary/signing_protocol.rs`)

### Summary
`SigningProtocol::preprocess_internal` caches a deterministic FROST preprocess seed in `CachedPreprocesses`, decrypts it, and reconstructs an `AlgorithmSignMachine` with `AlgorithmSignMachine::from_cache`, but never deletes or rotates the cached seed after signing. Any repeated `share_internal` call for the same `context` therefore reuses the same nonce material.

### Finding Description
The coordinator-side signing protocol caches the preprocess seed for each context and derives encryption material from `context` plus the validator's private key. On the first call, it creates a fresh `AlgorithmSignMachine`, stores `machine.cache()` under `self.context`, then rebuilds the machine from that same seed on every subsequent call. There is no removal, tombstone, or attempt counter in the cache key before reuse. This contradicts the FROST API contract stating a cached preprocess must only be used once because reuse enables recovery of the private key share. [1](#0-0) [2](#0-1) 

The reused seed deterministically recreates the same FROST nonce pair and published commitments through `ChaCha20Rng::from_seed` and `Commitments::new`. [3](#0-2)  `share_internal` then signs attacker-influenced `serialized_preprocesses` and `msg` using that machine. [4](#0-3) 

### Impact Explanation
Two accepted signing rounds sharing the same context but differing in either the participant preprocess set or message produce two Schnorr shares using the same private nonce:

```text
s1 = d + rho1 * e + c1 * x
s2 = d + rho2 * e + c2 * x
```

Because `rho` is publicly derived from the group key, message hash, and committed preprocess transcript, and `d`, `e` are reused, the shares expose linear relations sufficient to recover the signing share. For the normal single-generator Schnorr algorithm, if the peer preprocesses and message are unchanged except for participant binding variations that alter `rho`, the equations can be solved for `d`, `e`, and then the private share `x`. [5](#0-4) 

The file's own threat analysis recognizes that signing again over distinct received nonce commitments or messages would cause nonce reuse, but relies on BFT/rebuild assumptions and explicitly leaves processor-side handling as a TODO. The cache implementation does not enforce that safety invariant locally. [6](#0-5) 

### Likelihood Explanation
The vulnerable behavior is directly in production coordinator code: the cache is keyed only by `self.context`, so a repeated signing attempt under the same context reconstructs identical nonce material. [7](#0-6) 

Reachability is conditional on the coordinator invoking `share_internal` more than once for one `context` with a changed preprocess map or message. The surrounding comments say this should be prevented by BFT finality, but also identify logical flaws, message overwrite bugs, or inconsistent preprocess handling as ways the assumption can fail. This means the cryptographic layer has a catastrophic consequence for a state-machine mistake instead of enforcing single-use semantics itself. [8](#0-7) 

### Recommendation
Make cached preprocesses single-use:

- Delete `CachedPreprocesses[self.context]` immediately when the machine is reconstructed for signing, before any fallible parsing or signing can return early.
- Include an attempt/nonce-generation identifier in the cache key if retries are meant to be safe.
- If the cache is absent or already consumed, fail closed rather than deterministically regenerating and reusing the same seed.
- Add a regression test that calls `share_internal` twice for the same context and verifies the second call cannot reuse the same preprocess commitments.

### Proof of Concept
A focused unit test can demonstrate the invariant violation without needing a live adversary:

1. Create a `SigningProtocol` with a fixed `context`.
2. Invoke `share_internal` once and record the serialized preprocess/commitments and resulting share.
3. Invoke `share_internal` again with a different `serialized_preprocesses` map or `msg`.
4. Observe that `CachedPreprocesses::get(self.txn, &self.context)` still returns the same encrypted seed because `preprocess_internal` never deletes it.
5. `AlgorithmSignMachine::from_cache` reconstructs identical nonce commitments from the same seed, proving nonce reuse across distinct signing sessions. [9](#0-8) [3](#0-2)
