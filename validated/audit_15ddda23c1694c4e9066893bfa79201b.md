## Analysis

The root cause is confirmed in the code. `ShopifyApp::WebhookVerification#verify_request` computes the HMAC only over `request.raw_post`: [1](#0-0) 

and `PayloadVerification#hmac_valid?` compares the signature against `Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data))` where `data` is that same raw body — nothing else is folded into the signed bytes: [2](#0-1) 

The route that receives all webhooks is a single catch-all: `namespace :webhooks do post "(:type)" => :receive end`, where `:type` is a decorative path segment. [3](#0-2) 

`WebhooksController#receive` doesn't even read the route's `:type` param — it forwards the raw headers (including `X-Shopify-Topic`) straight into `ShopifyAPI::Webhooks::Registry.process`, which is the actual dispatcher deciding which handler/job class runs, based purely on the (unsigned) topic header: [4](#0-3) 

So: `verify_request` only gates on whether the *body bytes* were HMAC-signed by a known secret; it says nothing about which topic that body was signed for. Job-class selection is entirely delegated to the (external, not-repo-owned) `ShopifyAPI::Webhooks::Registry`, driven by the `X-Shopify-Topic` header value, which is never part of the signed data. This matches exactly the mechanism described in the question: a replayed `(body, hmac)` pair with a forged `X-Shopify-Topic` header will pass `hmac_valid?` unchanged and get routed to whichever job class is mapped to the forged topic (e.g. `webhook_job_klass_name` in `ShopifyApp::WebhooksManager`). [5](#0-4) 

Note also that `shop_domain` (used by many generated job templates as the tenant key) is likewise read straight from `HTTP_X_SHOPIFY_SHOP_DOMAIN` and is also outside the signed bytes: [6](#0-5) 

— meaning both topic *and* the shop attribution used by dispatched jobs are attacker-controllable metadata riding along on a signature that only covers the body.

This is consistent with the design of Shopify's actual webhook protocol (HMAC signs body only; topic/shop are separate headers), so it is not a coding defect unique to this gem so much as an inherent property of how signature verification and routing are wired together here — no additional binding check (e.g., verifying the topic against a per-topic secret, or against the registered job's expected schema) exists anywhere in this call chain.

### Title
Webhook HMAC verification binds only to the request body, not the `X-Shopify-Topic`/`X-Shopify-Shop-Domain` headers, allowing replay of a valid signed webhook under forged topic/shop metadata - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::PayloadVerification#hmac_valid?` validates only `request.raw_post` against the app secret, never the `X-Shopify-Topic` or `X-Shopify-Shop-Domain` headers. Because the single catch-all webhooks route dispatches jobs purely based on the (unsigned) topic header via `ShopifyAPI::Webhooks::Registry.process`, a previously-observed valid `(body, hmac)` pair can be replayed with a different topic (and/or shop domain) header, and `verify_request` will accept it and the wrong job will be enqueued with attacker-influenced metadata.

### Finding Description
`verify_request` calls `hmac_valid?(request.raw_post)`, comparing the header HMAC to a digest computed over the raw body only. Topic/shop headers are read separately and are not part of the signed data. The engine route is a single generic `post "(:type)" => :receive"`, and `WebhooksController#receive` ignores the route param entirely, forwarding raw headers into `ShopifyAPI::Webhooks::Registry.process`, which selects the handler class by the `X-Shopify-Topic` header value. Consequently, once verification passes (because the body+hmac pair is valid for *some* topic), the job dispatched is determined solely by an attacker-controlled header, decoupled from the check that "authenticated" the request.

### Impact Explanation
This falls under "forged webhook requests" (explicitly a recognized impact class). Concretely, an attacker who can produce or replay one valid `(raw body, hmac)` pair for a topic can cause the app to invoke a different job (e.g. a mandatory privacy job like `shop/redact`, or any other registered handler) with mismatched/attacker-shaped payload data, and since `shop_domain` is likewise unsigned, potentially misattribute the event to an arbitrary shop identifier consumed by the downstream job.

### Likelihood Explanation
Exploitability strictly requires the attacker to first possess a valid `(body, hmac)` pair — this can only come from a genuine Shopify-signed delivery. The vulnerable code path itself (topic/shop not bound to signature, single generic route dispatching by header) is unconditionally present and requires no additional misconfiguration. The remaining precondition (obtaining a legitimate signed payload to replay) is outside this repo's control and depends on how/where the specific host app is able to observe raw deliveries.

### Recommendation
Bind the topic (and ideally shop domain) into the trust decision instead of relying on the body-only HMAC: verify that the resolved handler/job for the `X-Shopify-Topic` header matches the topic the webhook was actually registered for at that route/path (use the `:type` route segment to look up the expected topic and reject mismatches), and/or include topic/shop in an application-level integrity check before dispatch (e.g., cross-check against `ShopifyApp.configuration.webhooks` topic-to-path mapping) rather than trusting the header verbatim for routing.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
