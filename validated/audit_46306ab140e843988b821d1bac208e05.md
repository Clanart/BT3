### Title
Hard-coded UTF-8 decoding of raw diff buffers silently corrupts partially-staged/committed content for non-UTF-8 files - (File: app/src/lib/git/diff.ts)

### Summary
GitHub Desktop's diff pipeline unconditionally decodes the raw `Buffer` returned by `git diff`/`git log --patch` as UTF-8, even though it explicitly acknowledges this is an assumption that may not hold. This decoded (and potentially already-corrupted) string is what backs the line-by-line diff model used for partial staging (`git add -p`-style UI). When a user selects individual lines to stage/discard, `formatPatch`/`formatPatchToDiscardChanges` rebuild a patch from that same lossy string and feed it to `git apply --cached`, so the bytes that end up staged/committed can differ from the bytes actually present in the tracked file/working tree — silently.

### Finding Description
`diffFromRawDiffOutput` in `app/src/lib/git/diff.ts` does: [1](#0-0) 
```

  // for now we just assume the diff is UTF-8, but given we have the raw buffer
  // we can try and convert this into other encodings in the future
  const result = output.toString('utf-8')
  ...
```
The comment itself documents the assumption — directly analogous to the Compound oracle assuming a fixed `18`-decimal scale for exchange rates that are actually scaled by underlying-token decimals. Here, the "scale/format" being assumed is the text encoding of arbitrary, attacker-influenced file content pulled straight from a git object (blob) via `git diff`/`git log --patch`, invoked with `encoding: 'buffer'`: [2](#0-1) 

`Buffer.prototype.toString('utf-8')` in Node.js does not throw on invalid byte sequences — it silently substitutes the Unicode replacement character (U+FFFD) for any byte sequence that isn't valid UTF-8. This means any file whose content is not valid UTF-8 (e.g., legacy Latin-1/Shift-JIS/GBK text files, or any file with a byte sequence that merely happens to be invalid UTF-8) gets mangled at the moment the diff buffer is decoded, well before it's parsed by `DiffParser.parse`.

That mangled text becomes the authoritative representation used by:
- `DiffHunk`/`DiffLine.text`, driving the UI and the per-line selection model.
- `formatPatch()` in `app/src/lib/patch-formatter.ts`, which reconstructs a unified diff purely out of `line.text` values: [3](#0-2) 
- `applyPatchToIndex()` in `app/src/lib/git/apply.ts`, which pipes that reconstructed patch as `stdin` to `git apply --cached`: [4](#0-3) 

`git apply` writes the patch text (with any U+FFFD substitutions now baked in as new UTF-8 bytes, `EF BF BD`) directly into the git index/blob. There is no re-validation step that compares the resulting staged/committed blob against the original working-directory bytes for lines that were "context" or "modified" adjacent to the corrupted bytes.

No existing guard mitigates this:
- `isValidBuffer`/`isBufferTooLarge` gate on size, not encoding validity.
- `hasHiddenBidiChars` detection only flags a specific bidi-override Unicode range; it does nothing for encoding corruption.
- The parser (`app/src/lib/diff-parser.ts`) operates purely on the already-decoded JS string and has no visibility into the original bytes, so it cannot detect or reject corrupted input.
- Full-file staging (`updateIndex`, the non-partial path in `app/src/lib/git/update-index.ts`) is safe because it never round-trips through this decode — it uses `git add`, staging exact working-tree bytes. Only the **partial-selection path** (`applyPatchToIndex` → `formatPatch`) is affected, so the bug is invisible in the common case and only manifests when a user does line-level (or hunk-level) selective staging/discarding on a non-UTF-8 file.

### Impact Explanation
This causes silent corruption of what the user commits/pushes — one of the explicitly valid impact categories. A user working with legacy-encoded text files (common in localization files, older codebases, CSVs from external tools, Windows-authored files with codepage-specific bytes, etc.) who uses Desktop's partial-line staging or "discard selected lines" feature can have unrelated, unselected/unmodified byte sequences replaced with `U+FFFD` in the committed blob, without any warning, dialog, or diff indication that data loss occurred. Because the replacement happens during decode (before the parser even runs), the corruption is baked into every hunk that touches a non-ASCII byte region of the file, not just the lines the user intentionally changed — meaning even "kept" context/deleted-turned-context lines are permanently rewritten with mojibake when the patch is applied.

This is not a crash or DoS; it is a data-integrity issue that persists in the git history once committed and pushed, matching the report's core theme (mis-scaled/mis-decoded external data producing "incorrect" values that get trusted downstream).

### Likelihood Explanation
The attacker primitive fits the allowed model: the affected data (file content) can be attacker-controlled (a cloned/fetched repository containing non-UTF-8-encoded tracked files), and no admin rights, local access, or social engineering beyond normal repository cloning/fetching is required. Triggering requires only that the user perform ordinary partial staging or discard-changes actions on such a file inside Desktop — an unprompted but entirely natural workflow (this is one of Desktop's signature features, not an unusual step). Likelihood is moderate: it requires a text file that is not valid UTF-8 and a partial-selection action, both plausible in real repositories (e.g. repos with mixed legacy encodings, or repos deliberately crafted with invalid-UTF-8 byte sequences to test/exploit this specific behavior).

### Recommendation
- Detect decode failures instead of silently substituting replacement characters: use a strict decoder (e.g. Node's `TextDecoder('utf-8', { fatal: true })`) on the raw diff buffer, and if decoding fails, fall back to treating the file as binary/unrenderable for partial-selection purposes (mirroring how binary diffs already disable partial staging in `apply.ts`).
- Alternatively, preserve the raw buffer alongside the decoded string and have `formatPatch`/`applyPatchToIndex` operate on byte offsets rather than decoded JS string content, so unaffected bytes are never round-tripped through a lossy decode.
- At minimum, surface a warning in the UI when a diff contains characters indicating potential encoding loss (U+FFFD) and disable/guard the partial-staging and discard-changes actions for such files, similar to the existing binary-file guard in `applyPatchToIndex`.

### Proof of Concept
1. Create a file `latin1.txt` containing a byte sequence that is valid Latin-1 but invalid UTF-8, e.g. bytes `48 65 6C 6C 6F 20 A9 20 57 6F 72 6C 64` (`Hello © World` encoded in Latin-1, where `0xA9` alone is an invalid UTF-8 continuation byte in this position). Commit it to a repository.
2. Modify one line elsewhere in the file and open the repository in Desktop; view the diff — the line containing byte `0xA9` will render with `U+FFFD` in place of the original byte because `getWorkingDirectoryDiff`/`diffFromRawDiffOutput` decoded the raw buffer as UTF-8 (`app/src/lib/git/diff.ts:788-796`).
3. In the Changes view, select only the unrelated modified line for staging (leave the `0xA9`-containing line unselected/context). Desktop calls `formatPatch` (`app/src/lib/patch-formatter.ts:129-232`) which emits the context line using the already-corrupted `line.text`, then `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-83`) pipes this patch to `git apply --cached`.
4. Inspect the staged blob (`git show :latin1.txt`): the previously untouched line now contains the UTF-8 encoding of `U+FFFD` (`EF BF BD`) instead of the original `0xA9` byte — confirming the staged/committed content silently diverges from the working-directory file, purely as a side effect of the hard-coded UTF-8 decoding assumption.
