### Title
Unverified-PoP blame proofs leak the ECDH key for attacker-chosen `msg.key`, decrypting other participants' shares sent to the victim - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the CouchDB design-document issue — where attacker-supplied content causes a victim's own function to disclose the victim's credentials/session — PedPoP's secret-share decryption produces a publishable `EncryptionKeyProof` containing `ecdh(victim_enc_key, msg.key)` **before** the attacker-controlled proof-of-possession (`pop`) on `msg.key` is ever verified. `msg.key` is an arbitrary point supplied by the sender. By copying the `key` field of another sender's `EncryptedMessage` addressed to the victim and attaching a garbage ciphertext/PoP, a malicious participant forces the victim's `calculate_share` to return `PedPoPError::InvalidShare { blame: Some(proof) }` — a proof the victim is expected to publish — which reveals the shared key that decrypts the honest third party's share to that victim.

### Finding Description
`Encryption::decrypt` (encryption.rs:469-501) queues the per-message Schnorr PoP into a `BatchVerifier` (line 479-485) but **immediately** computes and returns `EncryptionKeyProof { key: ecdh(enc_key, msg.key), dleq: ... }` (lines 487-499). The PoP is only verified later inside `batch.verify_with_vartime_blame()` in `KeyMachine::calculate_share` (lib.rs:493).

In `calculate_share` (lib.rs:476-499), the deserialized share check at lines 479-482 early-returns `InvalidShare { blame: Some(blame) }` *before* `batch.verify_with_vartime_blame()` is reached:

```rust
let (mut share_bytes, blame) =
  self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);
```

The code comments acknowledge this exact hazard class: the PoP exists specifically so that "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X... Bob would then use this to create a blame argument against Eve... they'd reveal bX, revealing Alice's message to Bob" (encryption.rs:84-90). The mitigation is correct in `Decryption::decrypt_with_proof` (which checks `msg.pop.verify` synchronously at line 374-379 before applying the cipher), but it is bypassed on the primary decryption path: the blame proof — whose `key` is `enc_key_victim * msg.key` — is materialized and returned even when the PoP is forged, because PoP verification is deferred to a batch that is never executed when the ciphertext fails `from_repr`.

The DLEq in `EncryptionKeyProof` binds `proof.key` to `msg.key` and to the victim's registered encryption key (`decrypt_with_proof` lines 381-390), so once the victim's blame is published, `AdditionalBlameMachine::blame` lets **any** party — including non-participants via `AdditionalBlameMachine::new` (lib.rs:649-662) — decrypt the *other* sender's `EncryptedMessage` that legitimately used that `msg.key`, obtaining the plaintext secret share.

### Impact Explanation
Each secret share `s_j(i)` sent to participant `i` is confidential; the security of the Pedersen DKG depends on share privacy. A malicious participant Eve can, per DKG run, select any one honest sender's share `s_j(i)` addressed to any victim `i`, cause the victim to emit a blame proof, and have that share publicly decrypted via `blame`/`AdditionalBlameMachine`. Eve can repeat this across DKG sessions/attempts (new `context`, new `msg.key`s but a fresh injection each time), accumulating public shares. Since blame proofs are designed to be publicly verifiable, the leaked plaintext is available to arbitrary observers — a unilateral disclosure of DKG secret material that the victim's own code produces, matching the CVE-2023-45725 pattern of a victim function leaking credentials to an attacker via attacker-crafted input.

### Likelihood Explanation
The attacker needs only to be a DKG participant (or to submit through the coordinator's blame-handling path) sending a single crafted `EncryptedMessage` whose `key` field copies the victim-addressed target message's `key`, with ciphertext that fails `C::F::from_repr` (overwhelmingly likely for random bytes, and trivially forceable) and any `pop` value. No timing, no collusion, and no control over other participants is required; the early-`?` return on `from_repr` deterministically emits the proof before PoP verification.

### Recommendation
Do not emit `EncryptionKeyProof` until the PoP on `msg.key` has been verified for this specific message. Concretely: synchronously verify `msg.pop` inside `Encryption::decrypt` (as `decrypt_with_proof` already does) before computing `ecdh`/`DLEqProof::prove`, or at minimum gate the `blame` value in `calculate_share` so a proof is only attached after the PoP batch for `BatchId::Decryption(l)` has passed — e.g., verify the PoP batch first, then attempt `from_repr`, then verify the share statements. Additionally consider binding `msg.key` to `from` in the cipher transcript so cross-sender key copying is rejected regardless of blame timing.

### Proof of Concept
1. Honest Alice sends victim Bob `EncryptedMessage` `M` with `key = K` encrypting scalar share `s_A(B)` (lib.rs:369).
2. Malicious participant Eve, as her share message to Bob, sends `M' = EncryptedMessage { key: K, pop: <invalid signature>, msg: <bytes that deserialize to a non-canonical scalar> }`.
3. Bob runs `calculate_share`. `encryption.decrypt` queues `M'.pop` for batch verification but returns `(garbage_bytes, blame)` where `blame.key = enc_key_Bob * K` with a valid DLEq (encryption.rs:487-499).
4. `C::F::from_repr(garbage_bytes)` fails → `PedPoPError::InvalidShare { participant: Eve, blame: Some(blame) }` is returned (lib.rs:480-482) before `batch.verify_with_vartime_blame()` ever checks the forged PoP.
5. Bob publishes `blame` per the protocol (cf. `CoordinatorMessage::VerifyBlame` handling in processor/src/key_gen.rs:504-549).
6. Anyone calls `AdditionalBlameMachine::new(context, n, commitment_msgs).blame(Eve, Bob, M', Some(blame))`: the DLEq verifies, `cipher(context, blame.key)` decrypts `M'`, and the same `blame.key` also decrypts Alice's `M` — revealing `s_A(B)` publicly.
