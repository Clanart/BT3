## Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw()` permanently marks escrow settled without verifying token delivery, causing loss of solver/user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` settles escrow by calling ERC20 `transfer` via a raw low-level `.call()` and only checking that the call did not revert (`success`), never inspecting the ABI-decoded boolean return value. Any ERC20 that returns `false` on failure instead of reverting (a widely-deployed, non-fully-EIP20-compliant but common token behavior, e.g. some deflationary/paused/blacklist-gated tokens) will make `withdraw()` treat the transfer as successful while no tokens actually moved. Because `_orders[...]` accounting and `_filled[commitment]` are already decremented/marked before this unchecked call returns, the escrow is irreversibly marked settled and the beneficiary never receives funds. This mirrors the root cause of the referenced report — an on-chain invariant is enforced by *assuming* an external contract behaves according to an unverified interface contract (draft EIP-4524 compliance in the original; implicit "returns true on success" ERC20 semantics here) without actually validating it, and the composability/fund-safety guarantee silently breaks for any conforming-but-different implementation.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is the single settlement path for all three ISMP-triggered flows: `RedeemEscrow`, `RefundEscrow` (via `onAccept`, lines 620-626), and cancellation refunds (via `onGetResponse`, lines 729-734): [1](#0-0) 

For every escrowed token it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the external call reverted — it says nothing about the ABI-decoded `bool` that `transfer()` is supposed to return. Tokens that follow the letter of ERC20 but return `false` instead of reverting on failure (rather than throwing) will cause `success == true` even though no value was transferred. The same unchecked pattern is repeated for the fee-token payout at line 711 and for the `SweepDust` handler at line 665.

Crucially, the state mutations that make this settlement irreversible happen around the unchecked call:
- `_filled[body.commitment] = beneficiary;` is set unconditionally at the top of `withdraw()` (line 684), before any transfer is attempted.
- `_orders[body.commitment][token] -= amount;` (line 701) permanently reduces the escrow ledger regardless of whether the transfer actually delivered value.
- `EscrowReleased`/`EscrowRefunded` is emitted (lines 716-720) as if settlement succeeded.

Once these run, the request receipt is also durably stored by `EvmHost.dispatchIncoming` because `onAccept` returned without reverting (`success == true` at the low-level `.call()` level in the host itself — see `EvmHost.sol` lines 794-818, where the receipt is only deleted if the app call reverts). Since `withdraw()` does not revert, the ISMP receipt is permanently persisted, the original cross-chain request can never be retried, and the corresponding source-chain escrow entry is gone with no possibility of a timeout-based refund. The end state is: the input tokens were correctly escrowed and debited from the ledger, but the beneficiary's `transfer()` silently no-oped, and the accounting has no path left to correct or reclaim it.

This is architecturally the same class of bug as the HolographERC20 finding: a fund-moving primitive is gated on an assumption about an external contract's interface behavior (there, mandatory EIP-4524 support; here, mandatory "returns true or reverts" ERC20 semantics) that is not universally true across real-world token implementations, and the contract does not defensively validate it — it just trusts a shallow signal (`success` boolean from the raw call) as proof that value moved.

Note: the mainline EVM `IntentGatewayV2.sol` and `IntentsBase.sol` use OpenZeppelin's `SafeERC20.safeTransfer`, which correctly decodes and checks the boolean return value (or absence thereof) — the Tron variant is the one path that reintroduces the unchecked pattern.

### Impact Explanation
This falls squarely within the bounty's "stealing or loss of funds" and "false proof/state acceptance" categories. The escrowed input tokens (belonging to a user, on a refund, or to a solver, on a fill settlement) become permanently unrecoverable: the internal ledger (`_orders`) is decremented and the commitment is marked `_filled`/receipted as though the payout occurred, yet the beneficiary's balance never changes. There is no retry, no timeout path, and no admin recovery mechanism visible in this contract for a partially-settled/no-op transfer — the funds are effectively locked/lost in the gateway contract while the protocol's own bookkeeping asserts the transaction is closed.

### Likelihood Explanation
The path is triggered by the entirely standard flow of a solver filling an order or a user cancelling one for any token pair where the input token is a non-throwing-on-failure ERC20 implementation. No malicious relayer, prover, or governance actor is required — an ordinary user or solver interacting with any listed token that returns `false` (e.g. due to being paused, blacklisted for one of the parties, or hitting some transfer-limit condition) at the moment of settlement triggers this unconditionally. Because `IntentGatewayV2` is meant to support arbitrary ERC20 tokens across chains (as advertised for intent-based swaps), the set of qualifying tokens is realistically broad, and the failure mode requires no attacker cooperation beyond normal usage — it is a systemic data-integrity gap in the settlement code path itself.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` at lines 697/711, and the `SweepDust` handler at line 665) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used in the non-Tron `IntentGatewayV2.sol`/`IntentsBase.sol`. This decodes and validates the boolean return value in addition to checking for reverts, ensuring `_orders`/`_filled` state is only finalized when a transfer has genuinely succeeded (or reverting the whole settlement so the ISMP receipt is rolled back and the request can be retried/timed out).

### Proof of Concept
1. Register/escrow an order whose input (or output, for the fee-token path) is an ERC20 token `T` that implements `transfer()` to return `false` on failure without reverting (a valid, real-world pattern for many deployed tokens, e.g. transfers blocked by a blacklist/pause flag rather than a `require`).
2. A solver fills the cross-chain order; `_fillCrossChain`/settlement dispatches a `RedeemEscrow` message back to the source chain.
3. On the source chain, `IsmpHost.dispatchIncoming` invokes `IntentGatewayV2.onAccept()`, which calls `withdraw()`.
4. At the moment of settlement, token `T` is configured (or becomes, e.g., due to a blacklist toggle) such that `transfer(beneficiary, amount)` returns `false`.
5. `token.call(...)` still returns `success == true` (the call itself did not revert), so `withdraw()` proceeds: `_orders[commitment][T] -= amount` executes, `_filled[commitment] = beneficiary` is set, `EscrowReleased` is emitted, and `onAccept` returns normally.
6. `EvmHost` persists the request receipt (no revert occurred), permanently precluding replay or timeout-based recovery.
7. Result: the beneficiary's balance of `T` is unchanged, but the protocol considers the escrow fully and permanently settled — the tokens are stuck in the `IntentGatewayV2` contract with no code path to reclaim them. [2](#0-1)
