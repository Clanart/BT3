### Title
Challenge-period bypass via zero-default `stateMachineCommitmentUpdateTime` in `HandlerV2` message handlers - (File: evm/src/core/HandlerV2.sol)

### Summary
The EVM `HandlerV2` gates every incoming ISMP request/response/timeout on a challenge period that must elapse since the state machine commitment for the proof height was recorded. This is computed as `block.timestamp - host.stateMachineCommitmentUpdateTime(height)`. Because Solidity mappings default unset entries to `0`, any height whose update-time entry was never separately populated collapses `delay` to `block.timestamp`, which trivially satisfies `challengePeriod > delay == false`, silently bypassing the challenge-period check — exactly the same "unset sentinel treated as a passed gate" defect as the reference `GroupcoinFactory` bug (`commitLaunch[tokenId] == 0` bypassing the launch gate).

### Finding Description
In `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`, the pattern repeats: [1](#0-0) 

```solidity
uint256 timestamp = block.timestamp;
uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
uint256 challengePeriod = host.challengePeriod();
if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
```

The gate is only effective if `stateMachineCommitmentUpdateTime(height)` is guaranteed non-zero for every height that also has a valid `stateMachineCommitment(height).overlayRoot`/`stateRoot`. The same subtraction-against-a-possibly-zero-default appears in all four handlers: [2](#0-1) [3](#0-2) [4](#0-3) 

Critically, the order of checks in each function computes the challenge-period delay **before** validating that the state commitment for that height actually exists (`if (root == bytes32(0)) revert StateCommitmentNotFound();` comes afterward), so any height whose update-time bookkeeping diverges from its commitment bookkeeping produces a computed delay of essentially `block.timestamp`, defeating the intended waiting period rather than reverting.

This mirrors the report's root cause precisely: a two-step invariant (`commitLaunch[tokenId]` must be explicitly set before the gated action succeeds) is checked with a comparison (`<=`) that is also satisfied by the default zero value, so "never configured" is silently treated as "condition satisfied."

The Substrate/pallet-ismp equivalent, `verify_delay_passed`, is NOT vulnerable to this because it uses `OptionQuery`-backed storage and propagates an error (`?`) rather than defaulting to zero: [5](#0-4) 

This asymmetry between the Rust host (fails closed on missing update time) and the presumed Solidity host getter (fails open, defaults to `0`) is the crux of the issue.

### Impact Explanation
If exploitable, this would let a relayer/attacker submit a `PostRequestMessage`, `GetResponseMessage`, or timeout message referencing a `StateMachineHeight` whose commitment exists but whose update-time entry is zero/unset, causing the challenge period to be bypassed entirely. This directly maps to the bounty's "false proof/state acceptance" and "logic attacks" categories: requests could be dispatched to destination modules, and timeouts could be honored, before the intended fraud/challenge window has elapsed, undermining the core cross-chain security assumption that state commitments are only trusted after the challenge period.

### Likelihood Explanation
This requires a concrete code path in `EvmHost.sol` where a height's `stateMachineCommitment` is written without its paired `stateMachineCommitmentUpdateTime` also being written in the same state transition. I was not able to confirm or rule this out from the files retrieved in this session — the `EvmHost.sol` `storeStateMachineCommitment`/`stateMachineCommitmentUpdateTime` implementations were not returned in enough detail. The separation into two independently-named getters (mirroring the pallet's separate `BoundedStateCommitments` and `BoundedStateMachineUpdateTime` storage maps, which are two distinct `StorageDoubleMap`s) makes an un-paired write architecturally plausible, but is not proven from the evidence gathered.

### Recommendation
Regardless of whether a concrete divergent write path exists today, harden the check to fail closed on the sentinel value, exactly as recommended in the reference report:
```solidity
uint256 updateTime = host.stateMachineCommitmentUpdateTime(request.proof.height);
if (updateTime == 0) revert StateCommitmentNotFound();
uint256 delay = timestamp - updateTime;
```
Apply this to all four call sites in `HandlerV2.sol` (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`), and audit `EvmHost.sol` to confirm `storeStateMachineCommitment` and the update-time write are always performed atomically for a given height.

### Proof of Concept
Full exploitation requires confirming a code path in `EvmHost.sol` that stores a `StateCommitment` for a height without also setting `stateMachineCommitmentUpdateTime` for that same height (e.g., via a helper/admin function or a re-entrant/alternate write path distinct from `handleConsensus`'s `storeStateMachineCommitment` call in `HandlerV2.sol`, lines 156-164). I could not retrieve that implementation in this session to build a concrete unit test; a Devin session with full repo access should inspect `evm/src/core/EvmHost.sol` for the `storeStateMachineCommitment` and `stateMachineCommitmentUpdateTime`/setter functions to confirm or rule out an un-paired write path, then write a Foundry test analogous to the reference PoC (deploy host, drive a state commitment write via the divergent path, then call `handlePostRequests` for that height and observe `ChallengePeriodNotElapsed` failing to revert).

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
