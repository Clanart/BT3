### Title
Scanner reports economically unspendable dust inputs, letting an attacker burn wallet value as fees — (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
The yAxis finding is a "value silently consumed with no lower bound" bug: the strategy swaps/mints at whatever price the mempool dictates, so a frontrunner extracts the difference. The Serai analog is in the Bitcoin wallet: `Scanner::scan_transaction` accepts any output paying to a watched `script_pubkey` regardless of value, and `SignableTransaction::new` then spends those outputs as inputs without checking that each input is worth more than the fee it costs to spend. An unprivileged attacker can send dust-valued P2TR outputs to a watched address; every such output is reported as received funds, yet spending it costs more in transaction fee than it contributes — the excess is burned to miners exactly as the yAxis slippage was burned to a frontrunner.

### Finding Description
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs:199-214` matches only on `output.script_pubkey`:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
```

There is no minimum-value check. A `ReceivedOutput` carrying e.g. the P2TR dust-limit minimum is indistinguishable from a real deposit.

`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs:150-256` enforces `DUST` on payments (line ~181 in tests shows `TransactionError::DustPayment` for a sub-dust payment) and on the change output (`value >= DUST` at line 229), but performs no analogous viability check on `inputs`: every `ReceivedOutput` passed in is added as a `TxIn` and signed over with `Prevouts::All` / `TapSighashType::Default` (lines 373-390). Each Taproot key-spend input adds ~57.5 vbytes of weight, so each injected dust input forces the signature to commit to paying `~57.5 * fee_per_vbyte` extra fee while contributing only ~330 sats or less of value. At any non-trivial fee rate the input is net-negative, and because `fee() = sum(inputs) - sum(outputs)` (line 139), the deficit is silently absorbed into the fee — the wallet's "harvest" is frontrun by the dust sender.

### Impact Explanation
An attacker can create arbitrary numbers of dust outputs to a victim's watched address (their only cost is the dust value itself plus their own cheap fan-out transaction). Any later spend constructed from `Scanner` results either (a) bleeds wallet value into miner fees with no bound or alert — the direct analog of unbounded slippage — or (b) if the caller tries to exclude the dust inputs, permanently strands the reported "received" funds. Since `scan_transaction` reports them, downstream accounting credits value that is economically unspendable.

### Likelihood Explanation
Fully attacker-reachable with public inputs: sending a Bitcoin transaction to a known P2TR script requires no privilege. The wallet key/script is public on-chain, so any watched address can be dusted at will. Loss per input is bounded (fee-rate dependent), but the attack is cheap to repeat and the misreporting is guaranteed.

### Recommendation
Apply the same dust bound to inputs that is already applied to payments and change: filter or mark `ReceivedOutput`s whose `value()` is below a spendable threshold (input weight × fee rate), either in `Scanner::scan_transaction` or in `SignableTransaction::new` (return an error or skip inputs that are net-negative), so injected dust is never credited nor consumed.

### Proof of Concept
1. Victim runs `Scanner::new(key)` (mod.rs:162).
2. Attacker broadcasts a transaction with an output `TxOut { value: 330 sats, script_pubkey: p2tr_script_buf(key) }`.
3. `scan_transaction` returns a `ReceivedOutput` for it (mod.rs:205-211).
4. Caller builds `SignableTransaction::new(vec![dust_output, ...], payments, change, None, fee_per_vbyte)`; no input-value check rejects it, and the signed transaction commits ~57.5 vB × fee rate of extra fee against only 330 sats of input. For `fee_per_vbyte > ~6`, the input is net-negative and the difference is paid to miners.

Caveat: I could not exhaustively verify whether `SignableTransaction::new` filters dust inputs in the lines 157-186 region beyond what was returned; the code shown and the test table (send.rs tests 157-206) indicate `DustPayment` applies only to payments, and `value >= DUST` only to change — no input-side check is present in the indexed code.
