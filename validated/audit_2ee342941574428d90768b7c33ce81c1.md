### Title
Non-monotonic `mWomSV.getUserTotalLocked` baseline in `calDoubledCounted` allows repeated MGP tier-reward extraction via lock/unlock cycling - (File: wombat/ArbWomUp3.sol)

### Summary
`getRewardAmount`/`calDoubledCounted` compute the "already rewarded" portion of a user's tiered MGP bonus using the *current* live balance from `mWomSV.getUserTotalLocked(_account)` instead of a monotonic historical high-water mark of WOM ever converted/rewarded. Because a user can freely reduce this live balance via `mWomSV.startUnlock`/`unlock` (both permissionless, no special role, only a cooldown wait), they can cycle their mWomSV position down and back up to re-claim the same tier bracket's MGP reward multiple times.

### Finding Description
`incentiveDeposit` computes the bonus in `_mode == 2` (lock) path as: [1](#0-0) 
`accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)` is the new hypothetical total, and `calDoubledCounted(_account)` subtracts the tier value already attributable to the account's *current* locked balance: [2](#0-1) 

Both calls read `mWomSV.getUserTotalLocked(_account)`, which is a live, mutable quantity: [3](#0-2) 

This value decreases whenever the user starts/completes an unlock via `startUnlock` and `unlock`, both externally callable by the position owner with no privileged role, only subject to `coolDownInSecs`: [4](#0-3) [5](#0-4) 

Exploit flow:
1. Attacker calls `incentiveDeposit` (mode 2) with amount that pushes `mWomSV` locked balance from 0 up through several tiers to `L` (e.g., 2000). Reward paid = `f(2000) - f(0) = f(2000)` and MGP is locked for the attacker via `vlMGP.lockFor`.
2. Attacker calls `mWomSV.startUnlock` then, after the cooldown, `mWomSV.unlock`, withdrawing most of the position back to raw mWOM, dropping `getUserTotalLocked` down to a low value `c` (e.g., 100). This mWom is returned to the attacker's own wallet — capital is not burned.
3. Attacker re-locks that same (or new) mWom back up near `L` again (either directly via `mWomSV.lock`/`lockFor`, or by calling `incentiveDeposit` again). `calDoubledCounted(_account)` now only subtracts `f(c)` (based on the now-low current balance) instead of `f(L)` (the true amount already rewarded), so the reward for the bracket `[c, L]` — which was already paid in step 1 — is paid again.
4. Steps 2-3 can be repeated (bounded only by the unlock cooldown) to keep re-extracting the same tier bracket's reward against the same underlying value, draining the `mgp` balance held by `ArbWomUp3` (only capped by `mgpleft = IERC20(mgp).balanceOf(address(this))`, see line 127-128) rather than by any real new WOM conversion.

The contract even contains an unused `bracketRewarded` mapping (`// not in use`) suggesting a monotonic reward-tracking mechanism was intended but never wired in, confirming `calDoubledCounted`'s reliance on the mutable live balance is the root cause rather than intentional design. [6](#0-5) 

Neither `nonReentrant` on `incentiveDeposit` nor any modifier on `mWomSV` prevents this, since the exploit is executed across multiple separate, sequential transactions, not via reentrancy. [7](#0-6) 

### Impact Explanation
This breaks the intended "one-time tier reward per WOM value locked" conservation invariant and lets an attacker repeatedly drain the finite `mgp` token balance held by `ArbWomUp3` for the airdrop/incentive program, which is subsequently locked into `vlMGP` on the attacker's behalf via `vlMGP.lockFor`. This is a direct theft of the protocol's unclaimed MGP incentive reward pool — an Immunefi "theft of unclaimed yield" / protocol insolvency class impact, since honest depositors' promised proportional rewards get front-run/drained by the repeat-claiming attacker.

### Likelihood Explanation
Preconditions are modest: the attacker only needs enough WOM/mWom capital to initially cross one or more reward tiers, plus the patience to wait out `coolDownInSecs` between unlock cycles (no special role required, `startUnlock`/`unlock`/`lock`/`lockFor` on `mWomSV` and `incentiveDeposit` on `ArbWomUp3` are all public/external). Since the position's raw mWom is returned to the attacker on unlock, the same capital can be recycled indefinitely, making the exploit fully repeatable and highly likely to be discovered/executed if the reward pool is materially funded.

### Recommendation
Track a per-account monotonic high-water mark of "WOM value ever rewarded" (e.g., re-enable/rework the unused `bracketRewarded` mapping) and update it only to increase inside `incentiveDeposit`, rather than deriving the already-rewarded portion from the live, decreasable `mWomSV.getUserTotalLocked`. `calDoubledCounted` should subtract based on this stored cumulative value, not on the current mutable lock balance.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `MasterMagpie`, `vlMGP`, mock WOM/mWom/MGP tokens, and `smartWomConvert`. Configure `rewardTier`/`rewardMultiplier` with at least two tiers (e.g., `[0, 1000]`, multipliers `[100, 500]`). Fund `ArbWomUp3` with a large MGP balance.
2. Attacker calls `incentiveDeposit(2000e18, ratio, false, 2)`. Assert `mWomSV.getUserTotalLocked(attacker) ≈ L` and record `reward1 = vlMGP` amount locked for attacker (via emitted `VLMGPRewarded`/`vlMGP.lockFor` mock).
3. Attacker calls `mWomSV.startUnlock(L - c)` for some small `c` (e.g., 100e18), warp `block.timestamp` past `coolDownInSecs`, then `mWomSV.unlock(slotIndex)`. Assert `mWomSV.getUserTotalLocked(attacker) == c`.
4. Attacker re-locks mWom back toward `L` (directly via `mWomSV.lockFor` or via a fresh `incentiveDeposit` call sized to restore the locked balance to ~`L`). Record `reward2`.
5. Assert `reward1 + reward2 > getRewardAmount` computed once for a single continuous deposit of the same total WOM (i.e., `f(L) - f(0)`), proving double payment for the `[c, L]` bracket, and assert cumulative MGP locked via `vlMGP.lockFor` for the attacker exceeds the single-shot tier entitlement for the total WOM ever actually converted.

    function calDoubledCounted(address _account) public view returns (uint256) {
        uint256 accuIn1 = mWomSV.getUserTotalLocked(_account);
        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accuIn1 > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;

        rewardAmount += (accuIn1 - rewardTier[i - 1]) * rewardMultiplier[i - 1];
        return rewardAmount / DENOMINATOR;
