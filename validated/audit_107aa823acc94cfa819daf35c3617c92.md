Based on my research, I found a concrete analog: `app/src/lib/parse-app-url.ts` validates the `branch` parameter of the `openRepo` deep-link action against a character allowlist, but the sibling `filepath` parameter — which is also attacker-controlled via a deep link — receives no such validation before being forwarded into the app's action pipeline.

### Title
Unsanitized `filepath` parameter from `openRepo` deep links enables path traversal outside the cloned repository - (File: app/src/lib/parse-app-url.ts)

### Summary
GitHub Desktop registers custom URL protocols (`x-github-client://`, `github-mac://`, `github-windows://`, etc.) that are handled by `parseAppURL()` [1](#0-0) . For the `openrepo` action, the parser extracts `pr`, `branch`, and `filepath` from the query string. The `pr` value is checked against `/^\d+$/` and the `branch` value is checked against `testForInvalidChars()` before being accepted [2](#0-1) , but `filepath` is passed through completely unvalidated into the resulting `IOpenRepositoryFromURLAction` [3](#0-2) , which is documented as "the file to open after cloning the repository." This is directly analogous to the original report's broken invariant: a value that should be scoped/attributable to a trusted context (the cloned repo's own file tree) is instead fully attacker-controlled and consumed downstream without a matching guard, just as `_msgSender()` let the `trustedForwarder` substitute an arbitrary "trusted" sender.

### Finding Description
The `openRepo` deep-link handler is reachable by any attacker who can get a victim to click a link — a normal web page, email, or an attacker-controlled `openrepo` link containing a malicious repository URL — through `app.on('open-url', ...)` on macOS and the `--protocol-launcher` argument path on Windows, both of which funnel into `handleAppURL()` → `parseAppURL()` in `app/src/main-process/main.ts` [4](#0-3) [5](#0-4) . Once parsed, the resulting `IOpenRepositoryFromURLAction`, including the raw `filepath` field, is dispatched to the renderer via `window.sendURLAction(action)`. Six references to `filepath` exist in `app/src/ui/dispatcher/dispatcher.ts`, indicating it is consumed later in the open/clone flow to open a specific file post-clone, but unlike `branch` there is no character/traversal check performed on it before it leaves `parse-app-url.ts`.

### Impact Explanation
If the `filepath` value is joined with the cloned repository's working directory path without normalization/containment checks at the eventual file-open sink, a crafted value such as `..%2F..%2F..%2F.ssh%2Fid_rsa` or an absolute path could cause Desktop to open, and potentially read, a file outside the intended repository boundary — matching the "read/write outside the repo" impact class from the bug bounty scope. Because the trigger is a single clicked deep link and the app already treats `openRepo` actions as sufficiently trusted to auto-clone/open repositories, the missing guard on `filepath` breaks the same invariant class as the original report (an externally supplied value silently overriding an implicitly trusted parameter).

### Likelihood Explanation
Likelihood is moderate: the code path is reachable purely through URL protocol registration and requires no local access, admin rights, or pre-existing compromise — only a user clicking a link, which is within the accepted attacker model. I could not fully confirm within my available tool calls the exact file-system API used downstream in `dispatcher.ts` to consume `filepath` (e.g., whether it is joined with `path.join` and passed to `shell.openPath`/`fs` without `path.resolve`/containment checks), so the practical exploitability (versus e.g. an existing implicit sanitization at the sink) is not fully verified from the indexed code alone.

### Recommendation
Apply the same allowlist/validation used for `branch` (`testForInvalidChars`, or a stricter check disallowing `..`, absolute paths, and drive letters) to the `filepath` parameter in `parseAppURL()` before constructing `IOpenRepositoryFromURLAction`, and additionally enforce path containment (e.g., `path.resolve` + prefix check against the repository root) at the point where `filepath` is ultimately used to open a file in `dispatcher.ts`.

### Proof of Concept
1. Register/observe that GitHub Desktop handles `x-github-client://openRepo/...` and `github-mac://openRepo/...` URLs via `app.on('open-url', ...)` [5](#0-4) .
2. Craft a link: `x-github-client://openRepo/https://github.com/attacker/repo?filepath=..%2F..%2F..%2F.ssh%2Fid_rsa`.
3. `parseAppURL` accepts this because only `branch` and `pr` are validated [6](#0-5) ; `filepath` is returned as-is.
4. The victim clicks the link, Desktop clones `attacker/repo` and (per the documented intent of `filepath`) attempts to open the resulting path post-clone; if the downstream consumer in `dispatcher.ts` does not re-validate/contain the path, the traversal sequence resolves outside the cloned repository directory.

Note: step 4's exact outcome depends on file-open logic in `app/src/ui/dispatcher/dispatcher.ts` that I was unable to fully inspect before running out of tool iterations; confirming the precise sink behavior would require further review of that file's `filepath` consumers.

```typescript
export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  // we require something resembling a URL first
  // - bail out if it's not defined
  // - bail out if you only have `/`
  const pathName = parsedURL.pathname
  if (!pathName || pathName.length <= 1) {
    return unknown
  }
```

```typescript
function handleAppURL(url: string) {
  log.info('Processing protocol url')
  const action = parseAppURL(url)
  onDidLoad(window => {
    // This manual focus call _shouldn't_ be necessary, but is for Chrome on
    // macOS. See https://github.com/desktop/desktop/issues/973.
    window.focus()
    window.sendURLAction(action)
  })
}
```
