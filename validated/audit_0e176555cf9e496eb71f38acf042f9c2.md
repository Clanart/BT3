### Title
Path-prefix boundary bypass in `resolveWithin` allows deep-link `filepath` to reveal files outside the repository - (File: app/src/lib/path.ts)

### Summary
`resolveWithin` (used to guard several attacker-reachable path operations, including the `x-github-client://openRepo` deep-link file handler) validates containment with `realResolved.startsWith(realRoot)` and no separator boundary check, so a sibling directory whose name has the repository directory name as a string prefix bypasses the containment check.

### Finding Description
The core containment invariant lives in `_resolveWithin`: [2](#0-1) 

`realResolved.startsWith(realRoot)` treats `realRoot` as a raw string prefix instead of a path component. If `realRoot` is `/Users/victim/Documents/GitHub/my-repo` and a sibling folder `/Users/victim/Documents/GitHub/my-repo-secrets` (or any other directory whose name extends `my-repo` as a string, e.g. `my-repo2`, `my-repository`) exists — a very common situation for developers who clone multiple related repositories side-by-side, or fork/rename variants into the same parent folder — then a resolved path such as `/Users/victim/Documents/GitHub/my-repo-secrets/ssh-keys/id_rsa` passes the `startsWith` check even though it is not inside `my-repo` at all. The existing unit tests only cover `..`/`../..` and symlink-escape cases; they never test the prefix-collision boundary case, confirming the gap is unguarded. [3](#0-2) 

This function is reused as the single security boundary for multiple attacker-reachable code paths:

1. Deep link handling: `dispatcher.ts`'s `openRepositoryFromUrl` takes the `filepath` query parameter straight from a `x-github-client://openRepo/...&filepath=...` URL (parsed with no sanitization other than rejecting absolute paths) and passes it to `resolveWithin(repository.path, filepath)` before calling `shell.showItemInFolder(resolved)`: [4](#0-3) [1](#0-0) 

2. Copilot merge-conflict file read/write flows also depend on `resolveWithin` for their "no path traversal" guarantee: [5](#0-4) [6](#0-5) 

Because the check is a raw string prefix comparison rather than a component-boundary comparison (e.g. `realResolved === realRoot || realResolved.startsWith(realRoot + sep)`), any of these call sites can be tricked into treating a path outside the intended root as "safe" whenever a same-prefixed sibling path exists on disk.

### Impact Explanation
The deep-link path (`openRepositoryFromUrl`) is the strongest reachable primitive because it requires only that the victim click an attacker-supplied `x-github-client://openRepo/...` link — matching the "link/deep link the user clicks" impact category. If the victim's local clone directory has any sibling whose name is prefixed by the target repo's folder name (a routine occurrence for forked/renamed repos cloned into the same parent directory), the attacker can construct a `filepath` value that resolves into that sibling and have Desktop call `shell.showItemInFolder()` on a file outside the intended repository — a "file read outside the repo" boundary violation of exactly the kind excluded impacts explicitly allow. The Copilot conflict-resolution write path is more constrained since `file.path`/`resolution.path` values are derived from repository-tracked filenames (git itself restricts `..` components in tracked paths), making the deep-link vector the most directly exploitable one.

### Likelihood Explanation
Moderate. It requires (a) a victim clicking a crafted deep link (a normal, low-friction lure for GitHub Desktop users, since `x-github-client://` links are a documented, expected interaction pattern) and (b) the existence of a sibling directory whose name is a superstring of the target repository's folder name — a condition that is common but not universal, and which the attacker cannot directly control, only guess or rely on typical developer folder layouts (e.g., `repo`/`repo-fork`, `app`/`app-old`, `desktop`/`desktop-021` style naming as seen even in this very repo's naming convention).

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to enforce a real path-boundary comparison instead of a raw string prefix check, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests covering sibling-directory-with-shared-prefix scenarios (both POSIX and Windows separators) alongside the existing `..`/symlink tests in `app/test/unit/path-test.ts`.

### Proof of Concept
1. Victim has GitHub Desktop cloned repos at:
   - `/Users/victim/Documents/GitHub/my-repo` (currently open in Desktop)
   - `/Users/victim/Documents/GitHub/my-repo-private` (contains sensitive files)
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/owner/my-repo?filepath=../my-repo-private/secret.txt`
3. `parseAppURL` extracts `filepath = "../my-repo-private/secret.txt"` unchanged [1](#0-0) .
4. `openRepositoryFromUrl` passes it to `resolveWithin(repository.path, filepath)` [7](#0-6) ; the resolved absolute path lands in `my-repo-private`, but because `"/Users/victim/Documents/GitHub/my-repo-private".startsWith("/Users/victim/Documents/GitHub/my-repo")` is `true`, `_resolveWithin` incorrectly returns it as valid [2](#0-1) .
5. `shell.showItemInFolder(resolved)` reveals `secret.txt` from the sibling repository in the victim's file explorer, disclosing its existence/location outside the intended repository boundary.
