### Title
`multiclaimFor` allows a third party to force a victim's default-pool MGP rewards into a locked vlMGP position - (File: rewards/MasterMagpie.sol)

### Summary
`multiclaimFor(address[] _stakingTokens, address[][] _rewardTokens, address _account)` is a permissionless external function that lets any caller trigger claim processing for an arbitrary `_account` [1](#0-0) . In `_multiClaim`, MGP rewards accrued from "default" pools (non-vlMGP, non-mWOM pools) are routed to `_sendVlMGPFor(_user, _receiver, defaultPoolAmount)`, which calls `vlmgp.lockFor(_amount, _account)` instead of transferring liquid MGP to the account, so the victim's rewards end up locked in vlMGP without their consent [2](#0-1) [3](#0-2) .

### Finding Description
`multiclaimFor` calls `_multiClaim(_stakingTokens, _account, _account, _rewardTokens)`, setting both `_user` and `_receiver` to the attacker-supplied `_account` [1](#0-0) . Inside `_multiClaim`, for each staking token the pending MGP (`claimableMgp`) is computed and bucketed based on token type: vlMGP-staking-token rewards go to `vlMGPPoolAmount`, MPGRewardPool tokens go to `mWOmPoolAmount`, and everything else accumulates into `defaultPoolAmount` [4](#0-3) . The `defaultPoolAmount` branch unconditionally calls `_sendVlMGPFor(_user, _receiver, defaultPoolAmount)`, which approves and calls `vlmgp.lockFor(_amount, _account)`, locking the MGP for the victim rather than transferring liquid MGP to them [2](#0-1) [3](#0-2) . Because `multiclaimFor` has no access control (`_account` is not restricted to `msg.sender`, unlike `multiclaimOnBehalf` which requires `_onlyCompounder`) [5](#0-4) , any unprivileged attacker can call it against a victim `_account` at any time their default-pool `rewardDebt` shows unclaimed MGP, forcing that MGP into a cooldown/penalty-bearing vlMGP lock instead of leaving it as a liquid, freely claimable reward. The reward-debt accounting itself (`user.rewardDebt = (user.amount * accMGPPerShare) / 1e12`) is correctly reconciled after the claim [6](#0-5) ; the issue is not an accounting desync but that the routing logic in `_multiClaim`/`_sendVlMGPFor` always sends default-pool rewards to a lock rather than a transfer, and this can be triggered by anyone against anyone.

### Impact Explanation
This forces a victim's liquid MGP reward entitlement into vlMGP, which by design has an unbonding/cooldown period and can carry an early-withdrawal penalty. The victim loses immediate access/liquidity to MGP they were entitled to claim freely, matching "High - Temporary freezing of funds for at least 24 hours" (or longer, depending on vlMGP's lock/cooldown duration) as an unwanted, third-party-imposed lock.

### Likelihood Explanation
The attack requires no special privileges or capital: the attacker only needs to call `multiclaimFor` with the victim's address, staking-token list, and reward-token arrays — all publicly known/derivable — whenever the victim has any unclaimed default-pool MGP reward. Since `_multiClaim` recomputes `claimableMgp` from on-chain state (`user.amount`, `pool.accMGPPerShare`, `user.rewardDebt`, `unClaimedMgp`) at call time, this is trivially repeatable, and the "mempool sandwich of a large deposit" scenario described in the prompt further amplifies the forced-locked amount but is not required for the base exploit to work.

### Recommendation
Restrict `multiclaimFor` so that MGP rewards routed through `_sendVlMGPFor` can only be forced into vlMGP when `msg.sender == _account` (self-claim), or split the function so that a third party calling on behalf of `_account` can only trigger claims for base rewarders/liquid-transfer paths (`_sendMGP`), not the vlMGP-locking path, unless the account has explicitly opted in (e.g., via an approval mapping) to allow others to lock MGP on their behalf.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, `MGP`, `vlMGP`, and a default-pool staking token/pool (non-vlMGP, non-MPGRewardPool).
2. Victim deposits into the default pool via `deposit`, accrues MGP rewards over time (`updatePool` increases `accMGPPerShare`).
3. Confirm victim's pending/claimable MGP via `_calMGPReward`-style view is > 0 and victim holds no vlMGP lock yet.
4. From an unrelated attacker EOA (no roles granted), call `multiclaimFor([stakingToken], [[]], victim)`.
5. Assert: (a) victim's MGP balance did NOT increase (no liquid transfer occurred), (b) `vlmgp.lockFor` was invoked for the victim and the victim's locked vlMGP balance increased by the claimable amount, (c) `userInfo[stakingToken][victim].rewardDebt` now equals `user.amount * accMGPPerShare / 1e12` (reconciled, proving the vulnerability is not an accounting bug but the forced-lock behavior itself), (d) attempting to withdraw that vlMGP amount as liquid MGP before the vlMGP cooldown/lock period elapses reverts or incurs a penalty, demonstrating the funds are frozen/penalized for ≥24 hours despite the attacker holding no special role.
