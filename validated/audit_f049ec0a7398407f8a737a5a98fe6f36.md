### Title
Line-selection index reuse against a re-fetched diff can silently stage content the user never selected - (File: `app/src/lib/git/apply.ts`)

### Summary
`applyPatchToIndex` regenerates a brand-new diff of the working-tree file immediately before building the commit patch, but the line selection it applies (`file.selection`) was computed by the user against a *previously rendered, cached* diff. The selection is a purely positional/index-based structure with no content binding, so if the on-disk file changes between the moment the user reviews and selects lines and the moment the patch is generated, the wrong lines get included in the commit without any warning to the user.

### Finding Description
When a user makes a partial commit, GitHub Desktop shows a diff (fetched once and cached in `changesState.selection.diff`, see `updateChangedFiles` in `app/src/lib/stores/updates/changes-state.ts:90-95`) and lets the user pick individual lines via `DiffSelection`, which stores selections as line indices (`app/src/models/diff/diff-selection.ts`).

At commit time, `stageFiles` (`app/src/lib/git/update-index.ts:163-168`) calls `applyPatchToIndex` for every file with a partial selection. Crucially, `applyPatchToIndex` does **not** reuse the diff the user actually looked at — it re-fetches a fresh one: [1](#0-0) 

That freshly generated diff is then handed to `formatPatch`, which walks each hunk and decides inclusion purely by numeric position: [2](#0-1) 

`absoluteIndex` is derived from `hunk.unifiedDiffStart + lineIndex` of the *new* diff, while `file.selection.isSelected(absoluteIndex)` reflects choices the user made while looking at the *old* diff. There is no verification that the line content, hunk boundaries, or total line count at that index are unchanged between the two diffs — the code comment in `app-store.ts` even acknowledges this is a known soft spot for a different code path ("The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines"), but that reconciliation is only applied to the *rendered* diff shown in the UI, not to the diff actually used to build the patch in `applyPatchToIndex`.

This is the structural analog of the reported issue: an amount/selector computed against one state (`supplyFactor` / a rendered diff) is applied unchecked against a different, more current state (the recalculated `amountNormalized` / the freshly fetched diff), with no re-synchronization or invalidation check before the value is committed to persistent state (`_normalizedBalances` / the git index).

### Impact Explanation
If the tracked file's content changes on disk between diff-render time and staging time (e.g., due to a Git operation triggered in the background such as an auto-fetch-driven checkout, a smudge/clean filter, a `core.autocrlf` conversion, or any external process altering the file while Desktop's changes view is open), the absolute line indices in the new diff no longer correspond to the lines the user selected. `formatPatch` will still stage/commit whatever text now occupies those index positions. This can silently commit and push content the user did not review or intend to include — a direct "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Requires no elevated privileges: it only requires that the working-tree file be mutated between the render of the diff panel and the click of "Commit," which is plausible in normal usage (background auto-refresh, another tool/editor autosaving, a clean/smudge filter defined in a cloned repository's `.gitattributes`, or a slow user reviewing a diff while a build/watch process is running). Because Desktop performs many implicit background Git/status operations, the window for this race is not negligible, though it does depend on external content mutation rather than attacker code execution inside Desktop itself — I could not find a guard in `applyPatchToIndex` or `formatPatch` that detects or rejects a diff/selection mismatch before applying the patch, so likelihood is assessed as best-effort/plausible rather than confirmed with certainty from local code alone (I could not fully trace whether `getWorkingDirectoryDiff` result is diffed against `state.selection.diff` anywhere else in the commit path).

### Recommendation
Before calling `formatPatch`/`applyPatchToIndex`, re-validate that the diff obtained in `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) is content-identical to the diff the selection was made against (e.g., compare hunk headers/line text, or a hash of the diff) — and if it differs, abort the partial-commit path and force the UI to refresh the diff/selection (similar to the reconciliation already done for the rendered diff in `app-store.ts`) rather than silently applying stale index-based selections to new diff content.

### Proof of Concept
1. Open a repository in GitHub Desktop and modify a tracked file so it produces a multi-hunk diff.
2. Open the Changes view, select the file, and manually deselect specific lines in one hunk (partial selection) — this uses the diff currently cached in `changesState.selection.diff`.
3. Before clicking "Commit," trigger a background modification of the same file's content that changes some line text (but keeps overall line indices in the same hunk range) — e.g., run a `.gitattributes` clean/smudge filter, or have an external process/editor autosave a change to that exact hunk region.
4. Click "Commit" — `applyPatchToIndex` calls `getWorkingDirectoryDiff` (`app/src/lib/git/apply.ts:60`) and obtains the new diff, then `formatPatch` applies the previously computed `DiffSelection` indices against the new hunk content (`app/src/lib/patch-formatter.ts:143-157`).
5. Inspect the resulting commit: the staged content reflects the newly written lines at the previously-selected indices rather than the content the user actually reviewed and approved, confirming the silent-corruption path.
