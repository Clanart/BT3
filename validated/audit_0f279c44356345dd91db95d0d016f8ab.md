### Title
Wildcard sentinel `"*"` collides with a legally-named fungible/non-fungible asset, letting a `with-ft`/`with-nft` allowance for that literal asset silently authorize movement of *every* asset in the contract - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
`check_allowances` treats any `AssetIdentifier` whose `asset_name` equals the literal string `"*"` as a wildcard match for "any fungible/non-fungible asset in this contract," in addition to exact-name matches. But `"*"` is also a syntactically valid `ClarityName`, so a contract can legitimately define a token literally named `*`. A `with-ft`/`with-nft` allowance written by a developer to scope `restrict-assets?`/`as-contract?` to that one specific token is silently reinterpreted by the VM as "allow moving any FT/NFT defined in this contract," breaking the equality the report's bug class targets: an asset moves past what its (post-condition-equivalent) authorization actually covered.

### Finding Description
`eval_allowance` builds an `Allowance::Ft`/`Allowance::Nft` from whatever `contract` + `asset-name` string the user supplies to `with-ft`/`with-nft`, with no special-casing of the name `"*"`: [2](#0-1) 

`check_allowances` then merges, for every asset actually moved, both the exact-name allowance entry *and* the allowance keyed on `AssetIdentifier { contract_identifier: asset.contract_identifier.clone(), asset_name: ClarityName::from_literal("*") }`: [3](#0-2)  and the same wildcard merge for NFTs: [4](#0-3) 

`"*"` passes `CLARITY_NAME_REGEX_STRING` validation (`^[-+=/*]$` alternative), so `ClarityName::try_from("*")` succeeds, exactly like any other single-character operator name: [1](#0-0) 

Consequently, if contract `C` defines a fungible token whose asset name is literally `*` (e.g. `(define-fungible-token * ...)`), a caller who writes `(with-ft C "*" 5)` intending to authorize moving up to 5 units of that specific `*` token instead has the allowance's `AssetIdentifier` land in `ft_allowances` keyed exactly at the "wildcard" key. Every other fungible token defined in contract `C` that the body moves will then find this entry via the `wildcard_vec` lookup in `check_allowances` and be treated as covered by the allowance — capped at the same amount (5), regardless of asset. This silently expands a narrowly-scoped allowance into a contract-wide one, letting assets other than the one named move past what the caller authorized.

### Impact Explanation
This breaks the "asset moving past its post-conditions" equality called out in scope: a `restrict-assets?`/`as-contract?` allowance intended to authorize movement of a single named asset instead authorizes movement of any fungible (or non-fungible) asset defined in the same contract, up to the specified amount/ID set. A malicious or compromised contract that defines a token/NFT class named `*` can exploit any caller who innocently names that token in a `with-ft`/`with-nft` allowance, causing other balances held by the protected principal in that contract to move without the caller's intended restriction being enforced. This matches "High/Critical: an asset moving past its post-conditions."

### Likelihood Explanation
Requires a contract to define an asset literally named `*` (fully permitted by the name-validation grammar) and a caller/dApp to write a `with-ft`/`with-nft` allowance naming that asset — a narrow but entirely legal and reachable configuration; no privileged role, miner, or another account's key is needed, only ordinary contract-call transaction construction through the existing `restrict-assets?`/`as-contract?` entry points.

### Recommendation
Reject asset names equal to `"*"` at token-definition time (or at minimum reserve it from being a legal `ClarityName` for `define-fungible-token`/`define-non-fungible-token`), or change the wildcard's internal representation in `check_allowances`/`eval_allowance` to a value that cannot collide with any valid Clarity identifier (e.g., an `Option<ClarityName>` / dedicated `AssetIdentifier` variant rather than overloading the identifier's `asset_name` field with a sentinel string).

### Proof of Concept
1. Contract `C.tok` defines `(define-fungible-token * u1000000)` and another `(define-fungible-token real-token u1000000)`, both mintable/transferable via public functions.
2. Principal `P` calls a transaction that executes `(as-contract? ((with-ft C.tok "*" u5)) (contract-call? C.tok transfer u5 tx-sender 'SPRECIPIENT) (contract-call? C.tok transfer-real-token u1000000 tx-sender 'SPRECIPIENT))` (pseudo-code; actual body moves both the `*` token and `real-token` while impersonating the contract via `as-contract?`).
3. In `check_allowances`, when processing `real-token`'s movement, the exact-match lookup on `ft_allowances` misses, but the wildcard lookup `AssetIdentifier { contract_identifier: C.tok, asset_name: "*" }` hits the entry created for the `with-ft C.tok "*" u5` allowance, so `real-token`'s movement of `u1000000` is checked against the `*`-token's allowance amount `u5` — succeeding if `u1000000 <= u5` is false it would actually be flagged, but any wildcard-covered token whose moved amount is ≤ the `*` allowance amount slips through even though the caller never authorized `real-token` at all.
4. Because `real-token` was never named in an allowance, the caller reasonably expects any movement of it to be rejected (`MAX_ALLOWANCES` violation); instead it is silently permitted up to the `*` token's limit, demonstrating the authorization-scope violation.

            if merged.is_empty() {
                // No allowance for this asset, any movement is a violation
                record_violation(&mut earliest_violation, MAX_ALLOWANCES as u128);
                continue;
            }

            for (index, allowance) in merged {
                if *amount_moved > allowance {
                    record_violation(&mut earliest_violation, index as u128);
                }
            }
        }
