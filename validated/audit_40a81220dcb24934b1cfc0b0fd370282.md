### Title
Scanner reports coinbase outputs as immediately spendable received funds without enforcing the 100-block maturity rule - (File: networks/bitcoin/src/lib.rs)

### Summary
The Derby bug class is: an input that has been flagged invalid (a blacklisted protocol) still contributes its now-corrupted value (an unreliable exchange rate) to an aggregate accounting computation, instead of being excluded/zeroed. In Serai, the analogous shape lives in `bitcoin-serai`'s `Scanner`: a Bitcoin output that consensus rules flag as invalid-to-spend — a coinbase (block reward) output younger than 100 confirmations — is matched purely on `script_pubkey` and emitted as a `ReceivedOutput`, i.e., funds the protocol treats as received and spendable. The "should-be-zeroed" state (the output's unspendability during maturity) is never incorporated into the accounting, just as `rewardPerLockedToken` is never zeroed for a blacklisted protocol.

### Finding Description
`Scanner` in `networks/bitcoin/src` maintains a map of registered `script_pubkey`s produced by `register_offset` (TapTweak-derived deposit addresses) and, when scanning a transaction, emits a `ReceivedOutput` for any output whose `script_pubkey` matches a registered address. Matching is done on `script_pubkey` alone; the scanner does not check whether the containing transaction is a coinbase transaction, nor does it track a maturity height.

Bitcoin consensus makes coinbase outputs unspendable until they have 100 confirmations. A `ReceivedOutput` created from a coinbase transaction is therefore "funds reported received that are not spendable": the scheduler/processor will select this UTXO as a spendable input, the threshold signing protocol will produce a valid FROST signature over a transaction spending it (`TransactionSignMachine::sign` in `networks/bitcoin/src/wallet/send.rs` builds sighashes with `Prevouts::All` and signs each input), and the resulting transaction will be rejected by the Bitcoin network. Worse, because the invalid UTXO is committed to in `Prevouts::All`, the entire batch transaction — including all other, valid inputs — fails, not just the coinbase input.

This mirrors the Derby finding structurally: a flag condition ("protocol is blacklisted" / "output is an immature coinbase") is ignored downstream, so a corrupted/contaminated value (a fake exchange rate / an unspendable UTXO) flows into rewards accounting / treasury accounting and poisons an otherwise correct batch operation.

### Impact Explanation
- Funds are reported as received (the protocol will credit/account for the deposit) yet the output cannot be moved for up to 100 confirmations.
- If the scheduler includes the immature UTXO in a batch spend, the signed transaction is consensus-invalid. Since `TransactionSignMachine::sign` uses `Prevouts::All` (`networks/bitcoin/src/wallet/send.rs`), every input is committed to in every sighash, so one immature input invalidates the whole transaction — all legitimate outputs in that batch are stuck until the transaction is rebuilt without the bad input. This is an availability/temporary-freeze of funds, plus wasted signing rounds and fee confusion in fee/change math.

### Likelihood Explanation
Reachable by an unprivileged party using only public inputs: the deposit `script_pubkey`s are publicly visible on-chain (they appear in prior transactions' outputs), so anyone can compute the tweaked deposit address. Creating a coinbase output requires mining a block paying that address — permissionless (solo mining, or a mining pool redirecting payout, or paying a miner to set the coinbase output). No validator, node operator, or threshold collusion is required; the attacker only causes a Bitcoin transaction (a coinbase) to exist paying a public address — squarely within the allowed adversary model ("Bitcoin transactions they send"). After maturity the funds become genuinely spendable, so the attacker loses the amount only if the protocol eventually claims it; the damage window is the 100-block period during which accounting and spendability disagree.

### Recommendation
In `Scanner`'s transaction-scanning path in `networks/bitcoin/src`, detect coinbase transactions (`tx.is_coinbase()` / null prevout on input 0) and either (a) refuse to emit a `ReceivedOutput` for them, or (b) emit it with a maturity flag/height so downstream scheduling in the processor cannot select the UTXO until 100 confirmations have elapsed — the analog of setting `rewardPerLockedToken` to 0 for a blacklisted protocol rather than letting its corrupted value accrue.

### Proof of Concept
1. Observe any Serai Bitcoin deposit `script_pubkey` on-chain (e.g., from a prior deposit); equivalently, derive it via the public group key and an offset per `Scanner::register_offset`.
2. Mine (or arrange) a coinbase transaction paying that `script_pubkey`. This requires no privilege — block rewards are permissionless.
3. `Scanner` matches the output on `script_pubkey` and yields a `ReceivedOutput`; the protocol records the funds as received.
4. The scheduler includes this UTXO in a `SignableTransaction`; `TransactionSignMachine::sign` signs it with `Prevouts::All` (`networks/bitcoin/src/wallet/send.rs`), and the completed transaction is broadcast.
5. Every Bitcoin node rejects it under the coinbase-maturity consensus rule (BIP-30/Bitcoin Core `COINBASE_MATURITY = 100`). The UTXO was reported received but is not spendable, and the entire signed batch is invalidated by the single contaminated input.
