### Title
Payments/deposits to the multisig's own internal offset addresses are absorbed as protocol-internal outputs instead of being credited — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the `PSP22Wrapper::deposit_for(self)` bug, Serai's Bitcoin wallet derives multiple "internal" addresses (external/base, branch, change, forward) from a single group key via `Scanner::register_offset`, and `Scanner::scan_transaction` reports any payment to any registered script as a spendable `ReceivedOutput` carrying that internal offset. There is no validation anywhere in the in-scope path preventing an unprivileged user from sending funds to the multisig's own internal addresses (change/branch/forward), nor preventing a payment destination from equaling the multisig's own scripts. Such outputs are indistinguishable from genuine protocol-internal outputs and are spent as internal funds (`SignableTransaction::multisig` applies `keys.offset(offset)` for whatever offset the scanner returned), so a depositor's coins sent to an internal address are absorbed by the multisig without ever being credited — the analog of tokens becoming "stuck" in the wrapper.

### Finding Description
`Scanner::new` registers the base P2TR script under `Scalar::ZERO`, and `register_offset` inserts each derived script (`key + G*offset`) into the same `scripts` map [1](#0-0) [2](#0-1) . `scan_transaction` then returns a `ReceivedOutput { offset, ... }` for every output whose `script_pubkey` is in the map, with no notion of whether the sender intended a deposit or whether the address is a protocol-internal one [3](#0-2) . All offset addresses are publicly derivable from the published group key, so any external party can send Bitcoin to the branch/change/forward addresses.

Downstream, `SignableTransaction::multisig` accepts any scanned `ReceivedOutput` and produces a signing machine for `keys.clone().offset(self.offsets[i])` as long as the prevout script matches [4](#0-3) . Funds received at an internal offset address are therefore fully spendable by the multisig yet were never an external deposit; they are treated exactly like the multisig's own change/branch/forwarded outputs.

Additionally, `SignableTransaction::new` performs no check that a `payments` entry or the `change` script differs from the multisig's own registered scripts (or is even a valid spendable script for `change`) — payments may target the multisig's own addresses [5](#0-4) [6](#0-5) .

### Impact Explanation
A user who (maliciously or by mistake — e.g., copying the change/forward address instead of the deposit address) sends BTC to an internal offset address produces a `ReceivedOutput` that the system spends as its own internal output. The sender is not credited a deposit, while the coins are absorbed into the multisig's spendable pool — permanently unrecoverable for the depositor, mirroring the report's `underlying_balance - total_supply = 0` accounting gap where self-directed tokens become trapped. A user-specified withdrawal destination equal to the multisig's own address similarly produces a "self-payment" that is re-scanned as a new received output, corrupting deposit accounting.

### Likelihood Explanation
The internal addresses are deterministic functions of the public group key (`hash_to_F(KEY_DST, ...)`-derived offsets over `G`), so they are computable by anyone. Reaching the bug requires only an ordinary Bitcoin transaction the unprivileged party sends — squarely within the reachable-inputs model. Severity is Medium: it requires the user to target an internal address rather than the canonical deposit address, but results in permanent loss/misattribution of funds.

### Recommendation
- When constructing `ReceivedOutput`s, distinguish outputs paying the base/external script from outputs paying internal offsets, and reject or specially handle externally-originated transactions paying internal (change/branch/forward) scripts — treat them as deposits to the base key or refuse to classify them as internal outputs.
- In `SignableTransaction::new`, validate that no `payments` script and no `change` script equals a script the multisig itself scans for, and that `change` is a P2TR script controlled by the multisig — the direct analog of checking `account != wrapper`.

### Proof of Concept
1. Obtain the multisig group key `K`. Compute the internal change script `C = p2tr_script_buf(K + G*hash_to_F("Serai Bitcoin Output Offset", b"change"))` (incrementing the offset until the point is even, exactly as `register_offset` does) [7](#0-6) .
2. Broadcast a normal Bitcoin transaction paying `C` an amount above dust.
3. `scan_transaction` returns `ReceivedOutput { offset: change_offset, ... }` [8](#0-7) . It is classified and spent as an internal Change output via `keys.offset(change_offset)` [9](#0-8) , never credited to the sender — the funds are absorbed into the multisig with no attribution, and are unrecoverable for the depositor.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
