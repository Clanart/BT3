### Title
`WombatBribeManager.addPool` re-adding an existing `_lp` with a new rewarder permanently bricks pre-existing voters' `unvote()` path and orphans their `totalVoteInVlmgp`/vote weight - (File: `wombat/WombatBribeManager.sol`)

### Summary
`addPool(_lp, _rewarder, _name)` unconditionally overwrites `poolInfos[_lp]` with a fresh `Pool` struct (`totalVoteInVlmgp: 0`, new `rewarder`), without checking whether `_lp` already had an active pool with existing votes. Any user (attacker or legitimate voter, not just an attacker) who voted for `_lp` before the swap has a non-zero `userVotedForPoolInVlmgp[user][_lp]`, but the underlying `Pool.totalVoteInVlmgp` is reset to `0` and the vote record staked in the *old* rewarder is never migrated, causing `unvote()` to revert permanently and freezing the user's vlMGP vote weight and stranding accrued rewards in the old rewarder.

### Finding Description
`vote()` stakes into `poolInfos[_lp].rewarder` at call time [1](#0-0) . If the owner later calls `addPool(_lp, newRewarder, name)` for the same `_lp` (e.g. migrating rewarder contracts), the entire `Pool` struct is replaced: `totalVoteInVlmgp` is reset to `0` and `rewarder` is switched to `newRewarder`, while `pools.push(_lp)` unconditionally appends `_lp` again (duplicate entry), and pre-existing `userVotedForPoolInVlmgp[user][_lp]` balances are left untouched from the old vote [2](#0-1) .

When a pre-existing voter then calls `unvote(_lp)`:
```
pool.totalVoteInVlmgp -= uint256(currentVote);           // 0 - X underflows -> revert
...
IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(currentVote), true); // now points to newRewarder
``` [3](#0-2) 

Because `pool.totalVoteInVlmgp` was reset to `0` while `currentVote = X > 0`, the subtraction underflows and reverts under Solidity 0.8 checked arithmetic before even reaching the rewarder call. Even in a scenario where `totalVoteInVlmgp` were non-zero (e.g., other later votes raised it above `X`), the subsequent call would hit `newRewarder.withdrawFor(user, X, true)`, and since `BribeRewardPool` tracks per-contract `_balances`/`totalSupply` independently [4](#0-3) , the new rewarder has `_balances[user] == 0`, so `_balances[_for] - _amount` and `totalSupply - _amount` both underflow and revert.

In either branch, `unvote(_lp)` permanently reverts for that user going forward (there is no way to correct `userVotedForPoolInVlmgp` or restage the stake in the new rewarder via any public/external function), which also keeps `userTotalVotedInVlmgp[user]` inflated forever, reducing their `getUserVotable` headroom for future votes [5](#0-4) . The stake recorded in the old rewarder also becomes unreachable, since only the manager (as `onlyOperator`) can call `withdrawFor`/`getReward` on rewarders, and the manager no longer references the old rewarder for that `_lp` [6](#0-5) .

No existing modifier or check (e.g., `nonReentrant`, activity checks, or balance reconciliation) prevents this; `addPool` has no guard against re-adding an already-populated `_lp`.

### Impact Explanation
This causes permanent freezing of the affected user's vlMGP vote weight (cannot unvote or reallocate it) and effectively strands reward accrual tied to the old rewarder, since the manager can no longer route reward-claim calls to it for that pool. This matches the "permanent freezing of funds / unclaimed yield ≥24h" impact class. The freeze is not attacker-limited — it affects any user who voted before an owner-triggered `addPool` re-registration of the same LP, which is realistic if the owner migrates a rewarder without first pausing votes or explicitly settling outstanding balances.

### Likelihood Explanation
The precondition only requires a normal, unprivileged `vote()` call (using tokens/vlMGP the caller already holds) landing in the same block or shortly before a normal admin `addPool` re-registration of the same `_lp` — no special privilege, flash loan, or reentrancy is needed, and it is trivially repeatable by observing pending owner transactions/mempool. The owner action itself is a legitimate/expected operational action (rewarder migration), not malicious admin behavior; the bug is that `addPool` provides no safe migration path for existing votes.

### Recommendation
In `addPool`, check whether `poolInfos[_lp]` already exists (e.g., `poolInfos[_lp].poolAddress != address(0)`) and either revert to force explicit removal/migration first, or implement a proper migration path that transfers each existing voter's `_balances` from the old rewarder to the new rewarder (or forces `unvote` before the swap) before overwriting `totalVoteInVlmgp` and `rewarder`. Also avoid unconditionally `pools.push(_lp)` for an `_lp` that is already present, to prevent duplicate entries.

### Proof of Concept
Foundry test outline:
1. Deploy `WombatBribeManager`, two `BribeRewardPool` instances (`rewarderA`, `rewarderB`) for the same LP, with manager set as `operator`.
2. Owner calls `addPool(lp, rewarderA, "poolA")`.
3. User locks vlMGP and calls `vote([lp], [X])` → assert `rewarderA.balanceOf(user) == X`, `userVotedForPoolInVlmgp[user][lp] == X`, `poolInfos[lp].totalVoteInVlmgp == X`.
4. Owner calls `addPool(lp, rewarderB, "poolA-v2")` (simulating rewarder migration) → assert `poolInfos[lp].totalVoteInVlmgp == 0`, `poolInfos[lp].rewarder == rewarderB`.
5. User calls `unvote(lp)` → assert the call reverts (arithmetic underflow) — i.e., `unvote()` neither recovers the vote weight nor the position in `rewarderA`.
6. Assert `userTotalVotedInVlmgp[user]` remains at `X` indefinitely with no available function to reset it, and `rewarderA.balanceOf(user)` remains `X` with no operator-callable path to withdraw/claim on `rewarderA` for that user via the manager.
