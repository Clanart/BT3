### Title
Premature integer division in `compute_royalty_amount` truncates NFT royalty payments in offers - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount` computes the royalty owed to an NFT creator by dividing before multiplying, causing avoidable truncation identical to the reported `interestFor` bug class (division before multiplication in a fee/interest calculation).

### Finding Description
`compute_royalty_amount` calculates the royalty as: [1](#0-0) 

```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```

The intermediate `abs(offered_amount) // royalty_split` performs an integer division first, truncating before the multiplication by `percentage`, and the code divides a second time by `MAX_ROYALTY_BASIS_POINTS` (10000) afterward. Mathematically the correct order to minimize truncation is `(abs(offered_amount) * percentage) // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`. Whenever `royalty_split > 1` and `offered_amount` is not an exact multiple of `royalty_split`, the current ordering discards fractional remainder before the multiplication step ever sees it, producing a smaller royalty than the mathematically correct amount — precisely the same class of bug identified in the external report (`rate * duration / 365 days` then `* amount / decimals`).

This function is invoked from `NFTWallet.make_nft1_offer`, which is reached whenever a wallet user creates an offer involving royalty-enabled NFTs on the requested side (multiple such NFTs increase `royalty_split`): [2](#0-1) 

A related but distinct helper, `NFTWallet.royalty_calculation` (used by the `nft_calculate_royalties` RPC to *display estimated* royalty summaries) has the same division-before-multiplication pattern: [3](#0-2) 

### Impact Explanation
The impact is confined to the wallet's own bookkeeping/off-chain computation of how much royalty to attach to a payment when constructing an offer — it does not corrupt consensus-level coin-set validation, forge asset identity, or allow unauthorized on-chain fund movement, because the actual amount paid is whatever CreateCoin the wallet emits in the spend bundle; there is no other party enforcing a specific correct royalty value on-chain beyond what this code computes and what the offer's own puzzle conditions require. The result is under-payment of the NFT creator's royalty by up to a few basis points/mojos, only in the edge case of splitting royalties across multiple simultaneously-offered royalty-enabled NFTs. This is a real but narrow value-loss bug (creator receives slightly less than owed), not a consensus divergence, invalid-block, or theft-of-signed-funds vulnerability. Given the strict scope of this exercise (concrete unsigned/unauthorized coin movement, supply inflation, forged identity, offer settlement theft, coin-set divergence, invalid spend/block acceptance, reward redirection, or transaction-processing halt), this finding does not clearly rise to a validated High/Critical/Medium per the required "Validate" criteria — it is a self-inflicted, wallet-side undercalculation affecting only the offering party's own outgoing royalty payment, not counterparty theft or protocol-level invariant violation.

### Likelihood Explanation
Would trigger any time a wallet user builds an offer with more than one royalty-enabled NFT split across the same fungible-asset payment (`royalty_split > 1`) and the resulting division has a nonzero remainder — a plausible but not default single-NFT-offer scenario.

### Recommendation
Reorder the arithmetic to multiply before dividing, consistent with the cited report's recommendation:
```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```
Apply the same reordering to `NFTWallet.royalty_calculation`'s inline computation at chia/wallet/nft_wallet/nft_wallet.py:853.

### Proof of Concept
Using `compute_royalty_amount(offered_amount=-1_000_000, royalty_split=3, percentage=500)`:
- Current code: `1_000_000 // 3 = 333333`, `333333 * 500 = 166,666,500`, `// 10000 = 16666`.
- Correct order: `1_000_000 * 500 = 500,000,000`, `// (3*10000=30000) = 16666`.

In this particular example both orders coincide, but with values where `abs(offered_amount) // royalty_split` truncates a larger remainder (e.g. `offered_amount=-1_000_001, royalty_split=3, percentage=9999`), the two orders diverge: current code computes `333333 * 9999 // 10000 = 333299`, whereas multiply-first computes `1_000_001*9999 // 30000 = 333300` — an off-by-one (or more, for larger inputs) underpayment of royalty mojos, confirmed by the existing test suite's tolerance for this behavior in `test_royalty_split_across_multiple_nfts` (chia/_tests/wallet/nft_wallet/test_nft_royalty.py:24-26) which only checks a case with no remainder.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
