### Title
Excess native-token payment sent to `EvmHost.dispatch()` / `fundRequest()` is refunded to the Host contract instead of the payer, permanently stranding ETH - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native-token payment and swap it for `feeToken` via `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)` [1](#0-0) . The configured "router" is not the real Uniswap V2 router but one of the project's own wrapper contracts (e.g. `UniV3UniswapV2Wrapper`), and its `swapETHForExactTokens` refunds any unspent ETH to `msg.sender` of that call [2](#0-1) . Because `EvmHost` itself is the caller of the wrapper (not the end user), any ETH the user over-sent to `dispatch()`/`fundRequest()` beyond what is needed to buy `post.fee`/`amount` worth of `feeToken` is refunded back into `EvmHost`, not to the original payer (`_msgSender()`). This is exactly the same broken invariant as the reported bug: ETH accumulates inside a bridge/exchange contract's own balance with no accounting entry and no path to the rightful owner.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`:
```solidity
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

The same pattern recurs in `dispatch(DispatchGet)` and `fundRequest()` [3](#0-2) [4](#0-3) .

`swapETHForExactTokens` is only guaranteed to spend up to `msg.value`; any unspent portion is refunded. In the wrapper implementation used for the actual swap, the refund destination is hard-coded to `msg.sender`:
```solidity
if (spent < msg.value) {
    uint256 refund = msg.value - spent;
    IWETH(weth).withdraw(refund);
    (bool success,) = msg.sender.call{value: refund}("");
    if (!success) revert RefundFailed();
}
``` [5](#0-4) 

Since `EvmHost` is the contract that calls `swapETHForExactTokens{value: msg.value}(...)`, `msg.sender` from the wrapper's perspective is `EvmHost`, not the account that originally called `dispatch()`/`fundRequest()` on `EvmHost`. The refunded ETH therefore lands back in `EvmHost`'s own balance, silently, with no event, no ledger entry crediting the true payer, and no code path in the reviewed `EvmHost.dispatch`/`fundRequest`/`dispatchTimeOut`/`dispatchGetResponse` functions that forwards it onward. This mirrors the reported class of bug precisely: value legitimately entering a bridge contract's balance becomes permanently disconnected from any withdrawal mechanism that could return it to its owner.

By contrast, `IntentGatewayV2.fillOrder` — which performs a structurally identical native→feeToken swap — explicitly refunds any unspent `msgValue` back to `msg.sender` after the swap:
```solidity
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
``` [6](#0-5) 

`EvmHost.dispatch`/`fundRequest` have no equivalent refund-to-caller step; they trust the swap call's own internal refund routing, which points at the wrong recipient.

### Impact Explanation
Any user who overestimates the ETH needed to cover `post.fee`/`get.fee`/`amount` (a very likely scenario given `dispatch()` and `fundRequest()` accept `msg.value` broadly and the docs explicitly warn fee estimation via `quote()` is imprecise and sandwich-prone off-chain) will have the excess ETH silently diverted into `EvmHost`'s own balance rather than refunded to them. This is a direct, unauthorized loss of user funds through the core dispatch/fee-payment path — the same "permanently frozen ETH revenue/funds" invariant break as the InfinityExchange report, now affecting end users of a live bridge rather than only the protocol's fee wallet.

### Likelihood Explanation
This does not require a malicious peer, relayer, or governance actor — any ordinary caller of `dispatch()` or `fundRequest()` who supplies `msg.value` greater than what the swap consumes triggers the misrouted refund unconditionally. It happens on every over-funded native-token dispatch, on both POST and GET paths and on `fundRequest`, making it a systemic, not edge-case, issue given fee estimation is inherently imprecise per the documented `quote()` caveat. I was not able to fully confirm, within available tool budget, whether `EvmHost.sol` contains a separate governance-only sweep/rescue function elsewhere in the file that could recover this stranded ETH after the fact (the file is large and only partially reviewed) — if no such recovery path exists, the funds are permanently locked exactly as in the referenced report; if one does exist, the impact is reduced to "trapped until manual admin intervention" rather than permanent loss. This should be verified directly against the full `EvmHost.sol` source before finalizing severity.

### Recommendation
- In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the actual amount spent by the swap and refund any leftover ETH directly to `_msgSender()` (the true payer), the same way `IntentGatewayV2.fillOrder` does, instead of relying on the swap's own refund-to-caller semantics.
- Alternatively/additionally, add an owner-gated sweep function on `EvmHost` that can forward its native-token balance to a designated treasury/beneficiary, so ETH that does land in the contract (from this or any other path) is not unrecoverable.
- Audit all other `swapETHForExactTokens`/`swapExactTokensForETH` call sites in the wrapper contracts (`UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper`, `GnosisUniswapV2Wrapper`) for the same "refund goes to intermediate caller, not end user" pattern.

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost)` with `msg.value = X` ETH, intending to cover `post.fee` worth of `feeToken`.
2. `EvmHost` calls `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` on the configured wrapper router [7](#0-6) .
3. The wrapper only needs `spent < X` ETH to acquire `post.fee` tokens; it refunds `X - spent` to `msg.sender`, which is `EvmHost`, not the user [5](#0-4) .
4. `EvmHost.dispatch()` proceeds to emit `PostRequestEvent` and returns; it never checks or forwards the refunded ETH now sitting in its own balance.
5. The user has lost `X - spent` ETH with no function in the reviewed `EvmHost` dispatch/fund paths to reclaim it, reproducing the "accumulated ETH cannot be retrieved" invariant break from the source report.
