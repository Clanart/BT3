### Title
Stale oracle price passes freshness check when publish-time is ahead of `stacks-block-time` - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The staleness gate that protects every price-dependent operation — including liquidation's health/LTV computation — silently disables itself whenever an oracle's reported timestamp is greater than the current `stacks-block-time`. In that branch the elapsed-time delta is hardcoded to `u0`, so the `<= delta max-staleness` check always passes regardless of how old the underlying price data actually is. This can let a genuinely stale price be accepted as "fresh," producing a wrong health verdict during liquidation and allowing bad debt to accrue — the exact outcome the client says it wants to avoid at all times.

### Finding Description
`oracle-timestamp-fresh` is the sole staleness gate used by `price-resolve`, which underlies every collateral/debt valuation used in `liquidate`, `borrow`, `collateral-remove`, etc.: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

When the oracle-reported publish time `ts` is greater than the block's `stacks-block-time` (e.g. due to normal clock/block-production lag between the oracle publisher's wall-clock and Stacks block time, or a stale cached price whose feed timestamp still lags but happens to exceed a delayed block time), the code takes the `u0` branch instead of computing the real elapsed delta. `u0 <= max-staleness` is always true, so the "how old is this price" check is fully bypassed. Only the monotonicity check `(>= ts prev)` still applies, but that only rejects timestamps older than the previously recorded one — it says nothing about whether the price is actually within `max-staleness` of "now."

This gate is invoked directly inside `price-resolve`, which is used to compute `debt-price` / `coll-price` in `liquidate`: [2](#0-1) 

and those prices flow straight into `current-ltv`, `calc-liquidation-params`, `process-debt-asset`, and `process-collateral-asset` in `liquidate`: [3](#0-2) [4](#0-3) 

If a stale price is accepted because the timestamp comparison branch masked the true delta, `current-ltv`, `debt-actual-usd`, and `coll-price` are all computed off wrong data, producing a wrong health verdict for the position being liquidated.

### Impact Explanation
- If the stale price overstates collateral value (or understates debt value), a position that is actually undercollateralized will be judged healthy (`ERR-HEALTHY` reverting real liquidations), letting the borrower keep an underwater position open — directly causing the bad debt the client explicitly does not want.
- If the stale price understates collateral value (or overstates debt value), a healthy position can be wrongly liquidated, seizing collateral and paying the liquidator a bonus (`liq-penalty`) it should not have received — a form of fund loss to the position owner and unwarranted profit to the liquidator.
- Because this same `price-resolve`/`oracle-timestamp-fresh` path is shared by `borrow`, `collateral-remove`, and every other user-facing valuation, the same defect can also let users borrow against or withdraw against a stale price, again risking insolvency.

This lands in the Critical impact bucket (protocol insolvency via bad debt / theft during wrongful liquidation).

### Likelihood Explanation
The triggering condition — an oracle-reported publish timestamp exceeding the current `stacks-block-time` — does not require a malicious or compromised oracle. Stacks block timestamps can lag real time (e.g., during slow block production, chain congestion, or Nakamoto fast blocks), while Pyth/DIA publish times track real-world clocks; whenever `ts > stacks-block-time` occurs for any reason, the staleness check is nullified for that call. This is a systemic, code-level defect in the gating condition itself, not a claim about bad data from the oracle provider — the code's own comparison logic is the root cause of the bypass.

### Recommendation
Remove the branch that zeroes the delta. If timestamps can legitimately be ahead of `stacks-block-time`, treat that case explicitly (e.g., either reject as invalid/require `ts <= stacks-block-time`, or compute an absolute-value delta) instead of always mapping it to "0 seconds old":

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (>= ts prev)
    (<= ts stacks-block-time)                 ;; disallow "future" timestamps outright, or
    (<= (- stacks-block-time ts) max-staleness)))
```

### Proof of Concept
1. Configure an asset with `max-staleness` = 120s.
2. Have the oracle report a price with `publish-time = T`, where `T` happens to be greater than the current block's `stacks-block-time` (achievable whenever Stacks block time is lagging behind the oracle's wall-clock feed, which is expected/observable behavior rather than an oracle attack).
3. `oracle-timestamp-fresh` computes `delta = u0` and returns `true` for freshness regardless of how stale the underlying price actually is relative to real elapsed time.
4. `price-resolve` accepts the price and returns it for use in `liquidate`'s `current-ltv`/`debt-actual-usd`/`coll-price` computation, producing a liquidation health verdict based on out-of-date data — either blocking a legitimate liquidation (accruing bad debt) or executing an illegitimate one (unwarranted collateral seizure).

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
