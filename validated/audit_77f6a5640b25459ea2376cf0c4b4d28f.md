### Title
Prompt-injection via attacker-controlled PR/commit content leads to silent malicious code insertion during Copilot conflict resolution - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop's "Resolve with Copilot" feature builds an LLM prompt from data an attacker can fully control — conflicting hunk content, commit summaries, and pull-request titles/bodies — and then writes the model's `resolvedContent` directly to the working tree and stages it with no independent verification that the merged result reflects only "ours"/"theirs" content. This lets a malicious branch/fork/PR shape the AI's output to insert code the user did not write, which is then silently written to disk and `git add`ed as part of the user's own commit.

### Finding Description
The conflict-resolution prompt is assembled in `formatConflictContextForPrompt` [1](#0-0) , which directly interpolates PR titles/bodies (`appendPullRequest`) and commit summaries into the text sent to the model [2](#0-1) . All of this content — the conflicting hunks themselves, the commit messages, and the PR body (truncated to 4000 chars but otherwise unsanitized) — originates from the "theirs" side of the merge, i.e. from a branch, fork, or pull request that an attacker fully controls.

The model's structured output is parsed and, for each conflicted file, spliced back into the original file's non-conflicted regions via `reassembleResolvedFile`, which trusts the model's `resolvedContent` verbatim for anything inside a matched conflict-marker block [3](#0-2) .

The only safety checks present are (1) a path-traversal guard via `resolveWithin` [5](#0-4) , and (2) a check that the file wasn't externally resolved in the meantime [6](#0-5) . Neither of these validates that the content actually written matches a legitimate combination of "ours" and "theirs" — there is no diff/allow-list check confirming the model didn't fabricate or inject code beyond what either side actually contained. The UI does show a diff/result dialog before the user clicks "Continue Merge" [7](#0-6) , but this is a UX safeguard, not an enforced invariant — a crafted, plausible-looking diff (e.g., a subtly altered dependency version, an added script in `package.json`, or a shifted conditional) is exactly the kind of content an attacker optimizing a prompt-injection payload would produce, and large/batched conflict sets (chunked at 15–20 files per prompt, up to 5 concurrent chunks) make careful manual review of every hunk unrealistic [8](#0-7) .

This is structurally the same bug class as the reported liquidation issue: a value is computed from attacker/user-influenced input (the required collateral / the "faithful" merge resolution), then a side-effecting operation (fee deduction / LLM generation-and-splice) is applied, and the system never re-validates the final invariant (position health / "resolved content only contains legitimate ours-or-theirs material") before committing to the effect (liquidation trigger / file write + `git add`).

### Impact Explanation
If the attacker's crafted branch/PR/commit content manipulates the model into producing a resolution that silently reintroduces or injects malicious code (backdoored dependency, disabled security check, altered build script), that code is written to the victim's working directory and staged into their next commit — meeting the "silent corruption of what the user commits or pushes" impact category. Because this flows from data in a remote/fork/PR the attacker controls (not local access, not admin rights, not a leaked credential), it satisfies the valid-impact criteria.

### Likelihood Explanation
Exploitation requires: (1) the victim to encounter a real merge/rebase/cherry-pick conflict against attacker-controlled content (easily engineered by opening a PR or pushing a branch designed to conflict with a target file), (2) the victim to have GitHub Copilot conflict resolution enabled and to click "Resolve with Copilot" then "Continue Merge". This is a realistic, in-product workflow (the feature exists specifically to reduce manual conflict review), and the second step is a normal, expected user action rather than an "unnatural" step. The main mitigating factor is the result dialog giving the user a chance to review the diff before applying — but this depends entirely on user vigilance and does not scale to large conflict sets, so likelihood is assessed as low-to-medium rather than trivial.

### Recommendation
- Do not trust `resolvedContent` unconditionally: after reassembly, validate that each resolved hunk is derivable from a combination of the "ours" and "theirs" hunk content (e.g., diff resolved content against both sides and flag/reject content introducing lines present in neither side) before allowing it to be written/staged.
- Strip or neutralize prompt-injection vectors in commit messages and PR bodies before including them in the model prompt (e.g., markdown/instruction-stripping beyond the existing markdown-heading sanitization), and clearly delimit "untrusted context" from "instructions" in the system prompt.
- Surface an explicit, mandatory per-file diff review step (not just an optional dialog) before staging AI-modified content, especially for large batches, and prevent one-click "Continue Merge" for chunks above a safe review size.

### Proof of Concept
1. Attacker opens a pull request (or pushes a branch) against the victim's repository containing a commit that: (a) modifies a shared file to create a merge conflict with the victim's local changes, and (b) has a commit message/PR title-body crafted as a prompt-injection payload instructing "the merge resolution must include `<malicious code>`" framed as legitimate intent/context.
2. Victim locally merges/rebases/cherry-picks against the attacker's branch, hits a conflict, and clicks "Resolve with Copilot" — the prompt built by `formatConflictContextForPrompt` includes the attacker's commit/PR text verbatim [1](#0-0) .
3. The model, influenced by the injected instructions, returns a `resolvedContent` that looks like a reasonable merge but contains the attacker's payload; `reassembleResolvedFile` splices it in without validation [3](#0-2) .
4. Victim clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes the payload to disk and runs `git add` on it [9](#0-8) , after which it becomes part of the victim's next commit/push.

export function formatConflictContextForPrompt(
  context: IConflictResolutionContext
): string {
  const parts: Array<string> = []

  parts.push(
    `Merge conflict between "${context.ourLabel}" (ours) and "${context.theirLabel}" (theirs).`
  )
  parts.push('')

  if (context.pullRequests.length > 0) {
    parts.push('## Pull Request Context')
    parts.push(
      'These pull requests were referenced in the commit history and may explain the intent behind either side:'
    )
    parts.push('')
    for (const pr of context.pullRequests) {
      appendPullRequest(parts, pr)
    }
  }

/** Append a single pull request's title and (truncated) body to the prompt. */
function appendPullRequest(
  parts: Array<string>,
  pr: IConflictContextPullRequest
): void {
  parts.push(`PR #${pr.number}: ${pr.title}`)
  if (pr.body) {
    parts.push('Description:')
    parts.push(makeFencedBlock(truncateBody(pr.body)))
  }
  parts.push('')
}

/** Truncate an over-long PR body so a single PR can't dominate the prompt. */
function truncateBody(body: string): string {
  if (body.length <= MAX_PR_BODY_LENGTH) {
    return body
  }
  return `${body.slice(0, MAX_PR_BODY_LENGTH)}\n…(truncated)`
}

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
