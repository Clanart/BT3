### Title
Main renderer window loads with no Content-Security-Policy and Node integration enabled, turning any renderer script injection into full Node.js code execution - (File: app/src/main-process/app-window.ts)

### Summary
GitHub Desktop's main `BrowserWindow` is created with `nodeIntegration: true` and `contextIsolation: false`, and the HTML document it loads (`app/static/index.html`) declares no Content-Security-Policy, nor is one injected via the `onHeadersReceived` web-request pipeline. [1](#0-0) [2](#0-1) 

### Finding Description
The extension report flags a partially restrictive CSP (`object-src 'self'`, missing `default-src`) as a way of limiting the blast radius of any script injection. GitHub Desktop's equivalent surface — the renderer that displays repository-derived content (commit messages, PR titles/bodies rendered as markdown, diffs, branch names, avatar URLs, etc.) — has no CSP fallback at all, and the window hosting it runs with full Node.js integration (`nodeIntegration: true`, `contextIsolation: false`). This is a broken invariant: even where individual rendering paths are sandboxed (e.g. `SandboxedMarkdown` renders untrusted markdown into a separate `data:` iframe without Node access [3](#0-2) ), the top-level document that hosts the whole application has no CSP fallback to restrict `script-src`/`object-src`/`base-uri` if any other unsandboxed code path in the renderer allows attacker-influenced HTML/JS to execute. Because the window process itself has Node integration, a script-injection bug anywhere in the un-sandboxed renderer (outside the markdown iframe) — for example a future/undiscovered path that renders repository- or GitHub-API-controlled strings without going through `SandboxedMarkdown`/`DOMPurify` — would run with full access to `require('fs')`, `child_process`, etc., not just DOM/cookie access as in a browser extension. The `web-contents-created` handler in `main.ts` only prevents new-window creation and top-level navigation; it does not add any CSP or otherwise restrict script execution in the existing frame. [4](#0-3)  None of the three installed `onHeadersReceived`/`onBeforeSendHeaders` filters (`installSameOriginFilter`, `installAliveOriginFilter`, `installAuthenticatedImageFilter`) set a CSP header. [5](#0-4) [6](#0-5)  The `CrashWindow` used for uncaught-exception reporting has the identical misconfiguration. [7](#0-6) 

### Impact Explanation
Whereas the original report's impact is bounded to browser-extension-style script execution (DOM/cookie/session access within the extension's own storage partition), the Desktop analog's impact is code execution on the user's machine with the privileges of the desktop app process, because `nodeIntegration: true` exposes Node APIs directly to any script that executes in that window. A single missed sanitization point for attacker-controlled repository/API content (commit metadata, PR/issue content, remote URLs, etc., which are all attacker-controlled inputs per the valid-impact scope) would not just be contained by browser sandboxing/CSP — there is no CSP fallback (`default-src`) to fall back on, and the Node bridge means the payload can read/write arbitrary files or execute processes outside the repo.

### Likelihood Explanation
Likelihood is moderate: existing mitigations (`SandboxedMarkdown` + `DOMPurify` for rendered markdown, `will-navigate`/`setWindowOpenHandler` blocking cross-origin navigation) reduce the number of realistic injection points today. However, the complete absence of a CSP safety net means any single overlooked or future rendering path that inserts untrusted HTML/JS into the main window (rather than the isolated iframe) has an unmitigated path to Node-level code execution, unlike a browser/extension context where a CSP would still block script execution even after an injection succeeds.

### Recommendation
Add a strict `Content-Security-Policy` (at minimum `default-src 'none'`, explicit `script-src`, `object-src 'none'`, `base-uri 'none'`) either as a `<meta>` tag in `app/static/index.html` or via an `onHeadersReceived` filter registered alongside `installSameOriginFilter`/`installAliveOriginFilter` in `app/src/main-process/main.ts`. Independently and more importantly, migrate `app-window.ts` and `crash-window.ts` off `nodeIntegration: true`/`contextIsolation: false` toward `contextIsolation: true` with a `preload` script and `contextBridge`, per Electron's security guidance, so that a CSP failure or injection bug does not directly yield Node.js code execution.

### Proof of Concept
Not independently reproducible from static code alone: exploitation requires locating an existing (or introduced) rendering path in the un-sandboxed renderer that inserts attacker-controlled repository/API string content as live HTML/script rather than routing it through `SandboxedMarkdown`. The code evidence establishes the missing CSP and the `nodeIntegration: true` configuration as a standing structural weakness [1](#0-0) , but I could not find (nor could I rule out) a concrete un-sandboxed injection sink within the indexed portion of the codebase — this would need a full-repo review (e.g., via a Devin session) of every renderer component that displays repository/GitHub-API-sourced strings to confirm whether such a sink currently exists.

export function installSameOriginFilter(orderedWebRequest: OrderedWebRequest) {
  // A map between the request ID and the _initial_ request origin
  const requestOrigin = new Map<number, string>()
  const safeProtocols = new Set(['devtools:', 'file:', 'chrome-extension:'])
  const unsafeHeaders = new Set(['authentication', 'authorization', 'cookie'])

  orderedWebRequest.onBeforeRequest.addEventListener(async details => {
    const { protocol, origin } = new URL(details.url)

    // This is called once for the initial request and then once for each
    // "subrequest" thereafter, i.e. a request to https://foo/bar which gets
    // redirected to https://foo/baz will trigger this twice and we only
    // care about capturing the initial request origin
    if (!safeProtocols.has(protocol) && !requestOrigin.has(details.id)) {
      requestOrigin.set(details.id, origin)
    }

    return {}
  })
```

export function installAliveOriginFilter(orderedWebRequest: OrderedWebRequest) {
  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const { protocol, host } = new URL(details.url)

    // Here we're only interested in WebSockets
    if (protocol !== 'wss:') {
      return {}
    }

    // Alive URLs are supposed to be prefixed by "alive" and then the hostname
    if (
      !/^alive\.github\.com$/.test(host) &&
      !/^alive\.(.*)\.ghe\.com$/.test(host)
    ) {
      return {}
    }

    // We will just replace the `alive` prefix (which indicates the service)
    // with `desktop`.
    return {
      requestHeaders: {
        ...details.requestHeaders,
        Origin: `https://${host.replace('alive.', 'desktop.')}`,
      },
    }
  })
```
