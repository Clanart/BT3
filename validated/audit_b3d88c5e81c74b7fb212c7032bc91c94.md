Based on the investigation, I found a concrete analog in the deep-link URL parser that mirrors the "missing validation on an attacker-influenced value that later flows into a sensitive path-building operation" pattern from the ETH refund report.

### Title
Unsanitized `filepath` parameter from `x-github-client://openRepo` deep link enables path traversal outside the cloned repository - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL()` parses the `openRepo` deep-link action and validates the `branch` and `pr` query parameters against strict formats, but performs **no validation whatsoever** on the `filepath` query parameter before returning it as part of `IOpenRepositoryFromURLAction`.

### Finding Description
In `parseAppURL`, `branch` is checked with `testForInvalidChars(branch)` and `pr` is checked against `/^\d+$/`, but `filepath` is taken directly from the query string and returned unchanged: [1](#0-0) 

This is the exact analog of the Curves bug: a value that is trusted to be "safe" for a downstream operation (there, `msg.value`; here, `filepath`) is validated for one property (payment sufficiency / branch and pr format) but not for the property that actually matters for safety (refund of excess / path confinement to the repository).

Elsewhere in the codebase, relative file paths coming from repository state are joined with the repository's root directory and passed to file-opening sinks without a `path.resolve`/containment check, e.g.: [2](#0-1) [3](#0-2) [4](#0-3) 

These call sites assume the incoming `path` is a benign relative path derived from git status, not an attacker-supplied string from a URL. The `filepath` value from `IOpenRepositoryFromURLAction` is defined specifically to be used this way — "the file to open after cloning the repository": [5](#0-4) 

Because `filepath` is not checked with `testForInvalidChars` or any traversal guard (e.g. rejecting `..` segments or absolute paths), a value like `../../../../Users/victim/.ssh/id_rsa` or an absolute path would pass through unchanged into any `Path.join(repository.path, filepath)` call in the post-clone "open file" flow, and then into `shell.openExternal(\`file://${fullPath}\`)`.

**Verification gap:** I was not able to fully trace, within the tool budget, the exact call site in `app-store.ts`/`dispatcher.ts` that consumes `IOpenRepositoryFromURLAction.filepath` after a clone completes (searches showed 6 references to `filepath` in `app/src/ui/dispatcher/dispatcher.ts` but I could not read that section's content before running out of iterations). This should be confirmed directly in the repository before treating this as a fully proven end-to-end exploit chain.

### Impact Explanation
If the unsanitized `filepath` does reach a `Path.join(repository.path, filepath)` + `shell.openExternal`/external-editor-launch sink, a crafted `x-github-client://openRepo/<url>?filepath=../../...` link — delivered via a webpage, email, or the GitHub "Open in Desktop" button — could cause Desktop to open an arbitrary file on the victim's filesystem outside the cloned repository once the user clicks the link and Desktop finishes cloning. This matches the "attacker controls... a link or deep link the user clicks" + "file read outside the repo" impact category.

### Likelihood Explanation
Requires only that the victim click a deep link (a normal, expected Desktop interaction pattern — this is literally how "Open in Desktop" works from github.com), with no other local access or credentials needed. Likelihood of exploitation depends entirely on confirming the unverified sink noted above.

### Recommendation
Sanitize `filepath` in `parseAppURL` the same way `branch` is sanitized: reject values containing `..` path segments, null bytes, or absolute path indicators, and reject the action entirely (return `unknown`) if `testForInvalidChars`-style validation fails. Additionally, wherever `filepath` is later joined with `repository.path`, resolve the final path and verify it remains within `repository.path` before opening it.

### Proof of Concept
1. Attacker crafts: `x-github-client://openRepo/https://github.com/some/public-repo?filepath=..%2F..%2F..%2F..%2FUsers%2Fvictim%2F.ssh%2Fid_rsa`
2. Victim clicks the link (e.g., embedded in a webpage or "Open in Desktop" button pointing at attacker-controlled query params).
3. `parseAppURL` returns `{ name: 'open-repository-from-url', url, branch: null, pr: null, filepath: '../../../../Users/victim/.ssh/id_rsa' }` unchanged, per [6](#0-5) .
4. Desktop clones the repo, then (per the intended post-clone behavior documented on the `filepath` field) attempts to open the file at that path relative to the repo root — if joined naively, this resolves outside the repository and could trigger `shell.openExternal` on a sensitive file.

import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
