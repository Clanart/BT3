### Title
PedPoP `EncryptedMessage` accepts identity ECDH key, making secret shares decryptable by any observer - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG encrypts each secret share with a per-message ECDH key carried in `EncryptedMessage.key`. `EncryptedMessage::read` parses that key with `Ciphersuite::read_G`, which validates canonicity but does **not** reject the identity point — unlike `frost::Curve::read_G`, which explicitly errors on identity. A participant can therefore submit `key = identity` with a trivially satisfiable proof-of-possession, causing the recipient's ECDH to evaluate to a publicly known point. Any third party who observes the wire bytes can recompute the ChaCha20 key and recover the secret share in the clear.

### Finding Description
`EncryptedMessage::read` deserializes `key` and `pop` via `C::read_G`/`SchnorrSignature::read`, both of which route to `Ciphersuite::read_G` — a canonical-encoding check only, with no `is_identity` rejection. [1](#0-0) [2](#0-1) 

Contrast with `frost::Curve::read_G`, which was deliberately hardened to reject identity — PedPoP never got the equivalent check. [3](#0-2) 

Decryption computes `ecdh(enc_key_priv, msg.key)` and feeds the shared point's encoding into `cipher()`. [4](#0-3) [5](#0-4)  When `msg.key` is identity, the ECDH output is `enc_priv * identity = identity`, so the ChaCha20 key is `H(transcript(context, identity.to_bytes()))` — fully computable by anyone who knows the public `context`, since `identity.to_bytes()` is a fixed encoding and the IV is the static `b"DKG IV v0.2\0"`. [6](#0-5) 

The PoP gate does not stop this: `pop.verify(msg.key, pop_challenge(...))` checks `R + c·key − s·G == 0`. With `key = identity`, the sender picks any `s` and sets `R = s·G` (or `R = identity, s = 0`, since `SchnorrSignature::read` also accepts an identity `R` via `Ciphersuite::read_G`), and the equation holds for every `c`. [7](#0-6) [8](#0-7) 

The message is otherwise fully valid — the recipient decrypts "successfully" under the degenerate key, the share parses as a canonical scalar, and `share_verification_statements` pass because the sender embeds a genuine share. The malicious sender is indistinguishable from an honest one. [9](#0-8) 

### Impact Explanation
PedPoP shares are transmitted over authenticated but **not confidential** channels — the whole point of the ECDH+ChaCha20 layer is confidentiality of shares, per the spec. [10](#0-9)  An eavesdropper (or any relay/coordinator that sees the authenticated ciphertexts, e.g. `CoordinatorMessage::Shares` routing in the processor) who sees all `n` malicious-keyed `EncryptedMessage`s addressed to victim `i` can decrypt every `f_j(i)` and recover `i`'s full secret share `Σ f_j(i)`. Repeating across `t` victims — the attacker just sets `key = identity` on every outgoing share message — yields `t` secret shares, i.e. complete recovery of the threshold group's private key. This is key share recovery from public/wire data, the exact impact class the analog requires.

### Likelihood Explanation
The attacker is a single PedPoP participant (a role explicitly in scope — PedPoP ECDH/PoP handling is listed as an in-scope attack surface). The attack requires no threshold of colluders, no special network position beyond observing the authenticated channel the encryption layer exists to protect, and is fully deterministic — no probabilistic failure. Detection is impossible at the victim: all proofs verify and the delivered share is correct. Even absent a passive eavesdropper, in the Serai deployment the coordinator relays share ciphertexts (`CoordinatorMessage::Shares`), so any party with read access to coordinator messages — not just validators — can recover shares. [11](#0-10) 

### Recommendation
Reject the identity point in PedPoP deserialization, matching the hardening already applied in FROST. Concretely: after `C::read_G` in `EncryptedMessage::read` (encryption.rs:173), in `EncryptionKeyMessage`/`Commitments` reads (`Commitments::read`, lib.rs:115-127, and wherever `enc_key` is parsed), add `if point.is_identity().into() { Err(io::Error::other("identity point")) }`. Additionally reject `identity` for `SchnorrSignature.R` in `pop` at read time, or validate `key.is_identity()` before `register`/`decrypt`. The deeper fix is making `Ciphersuite::read_G` itself identity-rejecting for these protocol types, but per-callsite checks in pedpop suffice.

### Proof of Concept
Conceptual, using the library's own types:

```rust
// Malicious PedPoP participant `from` builds EncryptedMessage to victim:
let identity = C::G::identity();
let ciphertext: SecretShare<C::F> = /* honest share XOR keystream derived from ecdh = identity */;
let msg = EncryptedMessage {
  key: identity,                                  // accepted: C::read_G has no identity check
  pop: SchnorrSignature { R: C::generator() * s, s },  // verify: sG + c·identity − sG = 0
  msg: ciphertext,
};
// ciphertext = share_repr XOR ChaCha20(H("DKG Encryption v0.2" || context || identity_bytes), "DKG IV v0.2\0")
```

Victim path (`Encryption::decrypt`, encryption.rs:469-501):
1. `EncryptedMessage::read` succeeds — `key=identity` is canonical.
2. `pop.batch_verify` passes for the crafted `(R=sG, s)` since `c·identity` vanishes.
3. `ecdh(enc_key_priv, identity) = identity` → `cipher(context, identity)` decrypts to the valid share → `calculate_share` returns `Ok`, victim completes the DKG normally.

Eavesdropper path: reads the wire bytes, computes `cipher(context, identity)` independently (no private input needed), XORs the keystream against `msg.msg`, recovers the sender's share `f_from(victim)` in the clear. With the attacker sending `key=identity` to every participant and anyone observing all routed ciphertexts, `t` victim shares are recovered and `recover_key` reconstructs the group secret. [12](#0-11)

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
  }

**File:** spec/cryptography/Distributed Key Generation.md (L9-17)
```markdown
### Encryption

In order to protect the secret shares during communication, the `dkg` library
establishes a public key for encryption at the start of a given protocol.
Every encrypted message (such as the secret shares) then includes a per-message
encryption key. These two keys are used in an Elliptic-curve Diffie-Hellman
handshake to derive a shared key. This shared key is then hashed to obtain a key
and IV for use in a ChaCha20 stream cipher instance, which is xor'd against a
message to encrypt it.
```
