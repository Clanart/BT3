### Title
Independent, unmarker-anchored re-scan in `reassembleResolvedFile` can splice AI hunk resolutions into the wrong location, silently corrupting committed content - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The reported bug class is a **dual-accounting mismatch**: one code path tracks a per-entry quantity (a user's actual weight) while a second, independent path later removes/consumes an aggregate using a *different, re-derived* quantity (the pool average), with no cross-check that the two agree. The result is silent state corruption that a third party can exploit.

The closest analog in this codebase is in the Copilot merge-conflict resolution pipeline: the number/identity of "conflicts" a file has is computed twice, by two different mechanisms, and the results are only partially cross-validated. `reassembleResolvedFile` independently re-scans the raw file text for conflict-marker lines and splices the model's hunk resolutions into the file **by sequential order of markers found in this second scan**, not by the same hunk identities that were extracted and sent to the model.

### Finding Description
`reassembleResolvedFile` walks the raw on-disk file content and detects "conflict blocks" purely with regex matching against lines that look like `<<<<<<<`, `=======`, `>>>>>>>`: [1](#0-0) 

It then treats every such detected block, in the order encountered, as one entry to consume from `hunkResolutions` via a simple incrementing `hunkIndex`: [2](#0-1) 

This is a *second, independent* accounting of "how many conflicts this file has," separate from whatever mechanism originally parsed the file into `IFileConflictContext.hunks` (the structure used to build the prompt sent to the model and to number "Conflict 1 of N" for it). The only cross-check between the two counts is `validateResolutionPaths`, which compares the *model's returned* hunk count against `expectedFiles` hunk counts — it never re-parses `rawContent` itself, so it cannot detect a mismatch between the original hunk-extraction and `reassembleResolvedFile`'s own regex-based rescan: [3](#0-2) 

If the file being merged (content fully controlled by whoever authored the commits in the cloned/fetched repository — i.e., an attacker who can craft one side of a merge) contains any line elsewhere in the file that incidentally matches the ours/separator/theirs marker patterns — for example literal example text like `<<<<<<< HEAD` inside a README, changelog, code comment, or string literal describing git conflict markers — `reassembleResolvedFile`'s scanner can count a different number of "blocks" than the model was actually told about. Because splicing is done strictly by **positional order** (`hunkIndex`) rather than by matching against the original hunk identity/location, a single miscounted block anywhere in the file shifts every subsequent splice point, and the model's hunk resolutions get written into the wrong locations in the reassembled file — exactly the same "match by aggregate/derived count instead of the tracked identity" flaw as the `pool.cumulative`/`pool.AverageMagnitude` bug in the report.

The function's own doc comment acknowledges the ordering assumption without any identity check: "matched by order, not by line number" — it never says "matched against the original parsed hunks," confirming there is no cross-reference back to the authoritative hunk list used to build the prompt. [4](#0-3) 

### Impact Explanation
If the re-scan and the original parse disagree on hunk count/position, `reassembleResolvedFile` will splice AI-generated "resolved" content into the wrong offsets of the file — potentially overwriting non-conflicted code, or leaving actual conflict markers or model output in the wrong place. Since Desktop writes this reassembled content directly to disk as the resolution and the user then stages/commits it, this is a path to **silent corruption of what the user commits**, driven entirely by content in a fetched/cloned repository (a side of the merge) that the attacker controls. It requires no elevated privileges, no malware, and no unusual user action beyond running the (standard, sanctioned) AI conflict-resolution feature on a repository containing attacker-authored files.

### Likelihood Explanation
This requires: (1) a genuine merge/rebase/cherry-pick conflict exists in a file, (2) that same file (in either "ours" or "theirs" content, or in adjacent non-conflicted lines) also contains text matching the 7-character `<`/`=`/`>` marker patterns that isn't a real, currently-open conflict block. This is a plausible, not far-fetched, scenario for files such as documentation about Git, CI/config templates, or test fixtures that intentionally contain example conflict-marker text — content fully within an attacker's control when they author a branch that will later be merged by the victim. I was not able to fully verify, within the available tool budget, whether the original hunk-extraction logic in `app/src/lib/copilot-conflict-context.ts` uses exactly the same marker-detection algorithm as `reassembleResolvedFile` (which would eliminate the mismatch) — this should be confirmed by a maintainer/agent with full file access, since the index only exposed partial contents of that file.

### Recommendation
Do not re-derive hunk positions independently in `reassembleResolvedFile`. Instead, splice using the same hunk boundary offsets/identities that were computed once during the original conflict parse (the same data used to build the "Conflict N of M" prompt and populate `IFileConflictContext.hunks`), and pass those exact boundaries through to reassembly rather than re-scanning raw text with a second, potentially-divergent detector. Add a hard assertion that the number of marker blocks found during reassembly equals the number of hunks in the original `IFileConflictContext` for that file, and fail closed (skip the file, surface it to the user for manual resolution) rather than silently proceeding on a mismatch.

### Proof of Concept
1. Create a repo with a file (e.g. `docs/git-conflicts.md`) whose content includes literal example lines that match the marker regexes, e.g.:
   ```
   <<<<<<< HEAD
   example ours text
   =======
   example theirs text
   >>>>>>> feature
   ```
   placed in a section of the file that is **not** part of an actual merge conflict (i.e., identical on both branches).
2. In the same file, introduce a real, single-hunk merge conflict elsewhere (both branches modify the same line differently).
3. Merge the two branches in Desktop and invoke Copilot conflict resolution. The context builder reports 1 real conflict to the model and the model returns 1 hunk resolution.
4. `reassembleResolvedFile`'s regex scan detects the literal example block as an extra "conflict" ahead of (or after) the real one, shifting `hunkIndex` so the model's single resolution is spliced at the wrong location (the literal example block) while the real conflict is left with unresolved markers or is overwritten incorrectly.
5. Confirm the written file has resolved/garbled content in the wrong place relative to the real conflict, and that the app has no check that would have caught this mismatch before writing to disk (per `validateResolutionPaths`, which only checks the model-returned count against the *originally parsed* count — not against `reassembleResolvedFile`'s own rescan).

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved

      // must have a ======= separator and a >>>>>>> closing marker.
