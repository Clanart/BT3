### Title
Missing Forfeit Calculation in `_calExpireForfeit` Lets Users Claim 100% of Rewards Without the Intended Cooldown Penalty - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never queries the user's actual "rewardable percent" from the locker before computing the forfeit, unlike the parallel `vlMGPBaseRewarder._calExpireForfeit` implementation. As a result the forfeit penalty that is supposed to apply to users who have started/are in cooldown on their mWomSV lock is always zero, and users always receive their full accrued reward instead of the reduced, penalty-adjusted amount.

### Finding Description
In `vlMGPBaseRewarder.sol`, the forfeit is derived from the locker's live "rewardable percent," which accounts for whether/how much of a user's lock is in cooldown: [1](#0-0) 

The equivalent function in `mWOMSVBaseRewarder.sol` (the reward pool used for `mWomSV` lock slots and forfeits, which is explicitly in scope) sets `rewardableAmount` directly to `_amount` instead of consulting `mWomSV.getRewardablePercentWAD(_account)`: [2](#0-1) 

Because `rewardableAmount` is hard-set equal to `_amount`, the line `uint256 forfeitAmount = _amount - rewardableAmount;` always evaluates to `0`, regardless of the user's actual lock/cooldown status. This is the same class of bug as the reported `StakingVault` issue — a calculation that is supposed to be derived from a computed, state-dependent value instead uses an unmodified/default value, silently short-circuiting the intended penalty logic.

This function is directly reachable by any unprivileged wallet through the standard reward-claim path: [3](#0-2) 

### Impact Explanation
The forfeit mechanism exists to penalize users who claim rewards while their `mWomSV` lock is in cooldown/not fully vested, redistributing the forfeited portion back to the reward pool for other honest stakers (`_queueNewRewardsWithoutTransfer`). Because `forfeitAmount` is always `0`, every user — including those who should be penalized — receives 100% of their accrued reward. This is a direct theft of unclaimed yield that should have been forfeited and redistributed to the remaining `mWomSV` stakers; it is trivially triggerable by any ordinary wallet simply by claiming rewards through `getReward`/`getRewards` on this rewarder while in a state that should incur a forfeit.

### Likelihood Explanation
High likelihood — no special conditions, privileges, or race are required. Every call to claim mWomSV-based rewards through this rewarder is affected, and the incorrect behavior is deterministic (not proc-based), so the bug fires on every claim rather than only in edge cases.

### Recommendation
Mirror the `vlMGPBaseRewarder` pattern: query the actual rewardable percentage from the locker before computing `rewardableAmount`, e.g.:
```solidity
uint256 rewardablePercentWAD = mWomSV.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
```
instead of `uint256 rewardableAmount = _amount;`.

### Proof of Concept
1. User locks tokens in `mWomSV` and starts an unlock/cooldown on part of their position (partial `startUnlock`), which should reduce their `getRewardablePercentWAD` below 100%.
2. Rewards accrue to the user in `mWOMSVBaseRewarder` via normal reward distribution.
3. User calls the reward-claim path (`getReward`/`getRewards`), which internally calls `_sendReward` → `_calExpireForfeit`: [4](#0-3) 
4. Because `_calExpireForfeit` sets `rewardableAmount = _amount` unconditionally (never calling `mWomSV.getRewardablePercentWAD`), `forfeitAmount` computes to `0` even though the user's percent is below 100%.
5. The user receives their full reward (`toSend = userRewards - 0`), bypassing the forfeit that other stakers were relying on to be redistributed via `_queueNewRewardsWithoutTransfer`, resulting in a permanent loss of yield for the remaining honest `mWomSV` stakers.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```
