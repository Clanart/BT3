### Title
PedPoP issues blame proof revealing the ECDH shared key before verifying the message's proof-of-possession, letting a participant co-opt another's encryption key to decrypt their share - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
Analogous to the ActiveMQ issue (unvalidated input is consumed — beans instantiated — before the configuration is checked), `KeyMachine::calculate_share` consumes an attacker's `EncryptedMessage` by performing ECDH decryption and minting a blame proof (`EncryptionKeyProof` containing the shared ECDH key) **before** the message's Schnorr proof-of-possession is ever verified. The PoP exists precisely to stop reuse of another participant's per-message encryption key, but the early `from_repr` error path returns the blame proof while the PoP check sits unexecuted inside the deferred batch verifier. A malicious participant can copy an observed victim's `key` field, submit a garbage ciphertext under it, and receive a blame proof that decrypts the victim's real encrypted share.

### Finding Description
In `calculate_share`, each share is processed by `Encryption::decrypt`, which (a) queues `msg.pop.batch_verify(...)` into a `BatchVerifier`, then (b) immediately computes `ecdh(enc_key, msg.key)`, applies the ChaCha20 keystream, and returns an `EncryptionKeyProof { key: ecdh_result, dleq }` — i.e., a public disclosure of the ECDH shared point for `msg.key` [1](#0-0) .

Back in `calculate_share`, if the decrypted bytes are not a canonical scalar, the function returns `Err(InvalidShare { participant: l, blame: Some(blame) })` immediately — the blame proof is emitted **without ever running `batch.verify_with_vartime_blame()`**, so the PoP was never checked [2](#0-1) .

The PoP's sole purpose is documented in the code: without it, "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X… [the blame] would reveal bX, revealing Alice's message to Bob" [3](#0-2) . The early error path reintroduces exactly this attack, because the PoP failure would only be detected at `batch.verify_with_vartime_blame()` (mapped to `BatchId::Decryption`), which is unreachable once `from_repr` fails first [4](#0-3) .

The DLEq inside `EncryptionKeyProof` proves `key = enc_key_bob * msg.key` against Bob's registered `enc_pub_key`, so the published proof is a universally usable decryption key for any ciphertext encrypted under `msg.key` toward Bob [5](#0-4) .

### Impact Explanation
Eve participates in the DKG, observes Alice's `EncryptedMessage` to Bob (broadcast on the authenticated channel), and copies its `key` point `X` into her own share message to Bob with an invalid PoP and arbitrary ciphertext. Bob's `decrypt` computes `bX` (ECDH of Bob's encryption key with `X`), decrypts to non-scalar garbage, and `calculate_share` returns `InvalidShare { participant: Eve, blame: Some(EncryptionKeyProof { key: bX, dleq }) }` — which Bob publishes as a blame proof. Anyone can now use `bX` to decrypt Alice's real encrypted share to Bob via `cipher(context, bX)`, recovering a DKG secret share that was intended to be known only to Bob. This breaks DKG share confidentiality: Eve learns extra polynomial evaluations, reducing the effective secrecy of the generated threshold key (and permanently, since blame proofs are public).

### Likelihood Explanation
Fully reachable by a single unprivileged DKG participant sending one crafted `EncryptedMessage` (read via `EncryptedMessage::read` in `processor/src/key_gen.rs`). No collusion needed. The only requirement is that the decrypted bytes fail `C::F::from_repr`, which holds with high probability for random garbage on fields like ristretto255/secp256k1 (and Eve can brute-force the ciphertext offline until decryption would fail, since she cannot predict the keystream — but any non-canonical result suffices, and she can also simply send an oversized/invalid encoding or rely on the ~high fraction of non-canonical 32-byte strings). Additionally, if decryption yields a *valid* scalar, the share-verification batch check still fails later and leaks the blame proof in the `BatchId::Share` arm — the PoP batch statement and share statement are verified together, so a PoP failure would be attributed as `Decryption` → `blame: None` — meaning the leak specifically requires the `from_repr` early-return path, which Eve can force by also making the share fail its Feldman verification or by choosing ciphertext length/content that decodes to a non-canonical scalar.

### Recommendation
Verify `msg.pop` synchronously inside `Encryption::decrypt` (or at least gate blame-proof issuance on it) before computing/returning `EncryptionKeyProof`. Concretely: run `msg.pop.verify(msg.key, pop_challenge(...))` and return a distinct "invalid signature, no blame" error before the keystream/ECDH result is packaged as a publishable proof; or ensure `calculate_share` executes `batch.verify_with_vartime_blame()` for the `Decryption` statements *before* any `InvalidShare` error carrying `Some(blame)` is returned.
