## Analysis

The Lybra bug is a broken-invariant pattern: a permission check is *performed* but its result is never used to gate execution (`checkOnlyRole(...)` is called but not wrapped in `require`). Searching GitHub Desktop for the analogous pattern — "a security check is computed but not used to block the action" — the clearest match is the `open-external` IPC handler in the main process.

### Title
`open-external` IPC handler computes a protocol check but never enforces it before calling `shell.openExternal` - (File: `app/src/main-process/main.ts`)

### Summary
The main process IPC handler for `open-external` inspects the target URL's scheme (`http://`/`https://`) but only uses that check to decide whether to write a log line — the check's boolean result is discarded and `shell.openExternal(path)` is invoked unconditionally on whatever string the renderer supplies. [1](#0-0) 

### Finding Description
`open-external` is declared as a renderer-invokable channel in `RequestResponseChannels['open-external']`, taking an arbitrary `path: string`. [2](#0-1) 

Its main-process implementation only uses `pathLowerCase.startsWith('http://')`/`'https://'` to decide whether to `log.info`; it never returns early or rejects when the scheme check fails, and then calls `shell.openExternal(path)` with the raw, unvalidated string: [1](#0-0) 

This is architecturally identical to the reported Solidity bug: a guard expression is evaluated (`checkOnlyRole(...)` / `pathLowerCase.startsWith(...)`) but its result is never used to `require`/gate the sensitive call, so the sensitive operation (`transferOwnership`-equivalent access-restricted call / `shell.openExternal`) always executes regardless of the check's outcome.

Some renderer call sites *do* self-impose a scheme allow-list before invoking this pathway — e.g. the sandboxed markdown link interceptor only forwards `https:` links to `onMarkdownLinkClicked`: [3](#0-2) 

But `LinkButton` — used throughout the UI, including for API-supplied URLs (PR/check-run `html_url` fields, notification links, etc.) — forwards `this.props.uri` straight to `shell.openExternal` with no scheme validation at all: [4](#0-3) 

and `Dispatcher.openInBrowser` / `AppStore._openInBrowser` likewise pass the URL straight through to `shell.openExternal`: [5](#0-4) [6](#0-5) 

Because enforcement is inconsistently pushed to individual call sites rather than centralized in the IPC boundary (the one place that actually has a scheme check computed), any renderer code path or GitHub API-sourced field (check-run `details_url`/`html_url`, PR comment/notification links surfaced via `LinkButton`, etc.) that reaches `openInBrowser`/`open-external` without its own allow-list bypasses protection entirely — the decorative check in `main.ts` gives a false sense that the channel is scheme-restricted when it is not.

### Impact Explanation
If an attacker-controlled string (e.g., a GitHub Checks API `details_url`, a webhook-originated notification link, or any other API object rendered via `LinkButton`) reaches this channel with a non-`http(s)` scheme, `shell.openExternal` will launch it via the OS shell/handler resolution unconditionally. Electron's `shell.openExternal` has a history of being abused with custom URI schemes (e.g. `file:`, platform search/protocol handlers) to achieve unexpected local file access or process launches on the victim's machine — impact classes explicitly listed as valid (code execution / file access outside repo scope) if such a scheme reaches an unguarded `shell.openExternal` call.

### Likelihood Explanation
Medium: the check exists precisely where it would need to be enforced, indicating the pattern was recognized by developers but not correctly wired (analogous to `checkOnlyRole` being called but not `require`d). Exploitation requires an attacker-influenced URL string to reach this handler through one of the many unguarded call sites (`LinkButton`, notification/check-run rendering) rather than the one path that does self-validate (`sandboxed-markdown`'s link interceptor). Full confirmation of a specific attacker-controlled data source (e.g., whether `ci-check-run-popover.tsx` passes a raw, unvalidated `details_url` from the Checks API into `openInBrowser`) requires further code-path tracing beyond what indexed search results conclusively showed.

### Recommendation
Move the scheme allow-list enforcement into the `open-external` IPC handler itself (and correspondingly into `AppStore._openInBrowser`), rejecting/short-circuiting on any non-`http:`/`https:` scheme instead of only using the check for logging:

```ts
ipcMain.handle('open-external', async (_, path: string) => {
  const isHttp = /^https?:\/\//i.test(path)
  if (!isHttp) {
    log.warn(`Refusing to open non-http(s) url: ${path}`)
    return false
  }
  try {
    await shell.openExternal(path)
    return true
  } catch (e) {
    log.error(`Call to openExternal failed: '${e}'`, e)
    return false
  }
})
```

### Proof of Concept
1. Locate any renderer surface using `LinkButton` (or `dispatcher.openInBrowser`) whose `uri`/`url` value originates from a GitHub API field that a repository/PR/workflow author controls (e.g., a check run's `details_url`, or a PR comment link surfaced outside the `sandboxed-markdown` iframe's protocol filter).
2. Set that field to a non-`http(s)` URI (e.g., a custom/registered protocol handler string or a `file:` URL).
3. Have the victim click the resulting link inside Desktop.
4. `LinkButton.onClick` → `shell.openExternal(uri)` is invoked directly (renderer-side `app-shell` wrapper) or via `dispatcher.openInBrowser(url)` → IPC `open-external`, whose handler in `app/src/main-process/main.ts:581-597` never rejects based on scheme — the `startsWith('http')` check only affects a log line — so the non-http(s) URI is passed unconditionally to `shell.openExternal`.
