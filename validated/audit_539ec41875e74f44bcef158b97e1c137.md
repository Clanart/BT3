### Title
JIT (front-run) locking of MGP via `VLMGP.lockFor` lets an attacker steal a disproportionate share of forfeited MGP queued through `vlMGPBaseRewarder.queueMGP` - (File: `rewards/vlMGPBaseRewarder.sol`, `VLMGP.sol`)

### Summary
`vlMGPBaseRewarder.queueMGP` folds a victim's forfeited MGP into `rewardPerTokenStored` by dividing it by the *current* `totalStaked()` (i.e., `vlMGP.totalSupply()`) at the moment the transaction executes, with no time-weighting, checkpointing, or minimum holding period. Because `VLMGP.lockFor` immediately increases the caller's `balanceOf`/`totalStaked()` with no cooldown to start earning, an attacker can front-run a forfeiting transaction with a large `lockFor`, capture a share of the newly-added forfeit reward proportional to their inflated balance, then immediately call `getReward` and unwind their position.

### Finding Description
`queueMGP` computes `forfeitAmount` for the victim account and, if positive, calls `_queueNewRewardsWithoutTransfer(forfeitAmount, MGP)`: [1](#0-0) 

`_queueNewRewardsWithoutTransfer` distributes the forfeited amount to `rewardPerTokenStored` using the current `totalStaked()`, exactly like a normal reward: [2](#0-1) 

`totalStaked()` reads `vlMGP.totalSupply()` live, and a user's `balanceOf` in the rewarder reads live `MasterMagpie.stakingInfo`, both without any snapshot or time-weighting mechanism: [3](#0-2) 

`VLMGP.lockFor` lets anyone lock MGP "for" any address (including themselves) with only `whenNotPaused`/`nonReentrant` guards — no cooldown, no minimum holding period before the deposited balance counts toward `totalSupply()`/`balanceOf()`: [4](#0-3) 

The reward accrual formula (`_earned`) only depends on the delta between the current `rewardPerToken` and the user's last-paid snapshot multiplied by their *current* balance — it has no concept of "how long you've held that balance": [5](#0-4) 

Exploit flow:
1. Attacker observes a pending transaction that will route MGP through `queueMGP` with a large `forfeitAmount` (a whale being penalized on an expired/forced-unlock cooldown flow).
2. Attacker front-runs with `VLMGP.lockFor(bigAmount, attacker)` (or `lock`), instantly inflating both their `balanceOf` and the pool's `totalStaked()`.
3. Victim's transaction executes, calling `queueMGP`, which folds `forfeitAmount` into `rewardPerTokenStored` based on the now-inflated `totalStaked()`.
4. Attacker back-runs with `getReward`, claiming a share of the forfeited MGP proportional to their JIT-inflated balance, despite having held that balance for zero economically meaningful time.
5. Attacker can then unwind (start unlock / exit) shortly after, since there's no time lock tying rewards to staking duration.

None of the existing guards (`nonReentrant`, `onlyManager`, `updateReward`) prevent this because they only protect against reentrancy and access control, not against JIT balance manipulation around a discrete, batched reward-injection event. The reward accounting model itself (linear `rewardPerTokenStored` accrual keyed to instantaneous balance) is what enables the front-run.

### Impact Explanation
This is theft of other lockers' unclaimed yield: a locker who has held vlMGP for a long time and is entitled to a share of a whale's forfeited MGP has that share diluted/stolen by a JIT depositor who contributed zero time-weighted stake. This matches the "theft of unclaimed yield" impact class described in the prompt's scope.

### Likelihood Explanation
- Requires the attacker to hold/acquire enough MGP to instantly lock a large amount right before a forfeiting transaction is executed (capital-intensive but feasible, especially with flash-loanable MGP or if MGP liquidity allows large temporary acquisition).
- Requires mempool visibility of the victim's forfeiting transaction (standard front-running assumption, achievable on public mempools).
- Fully repeatable any time a large forfeiture event is queued through `queueMGP`.
- No privileged role needed — `lockFor`, `getReward`, and unlock functions are all public/external and open to any EOA.

### Recommendation
Introduce time-weighting or a minimum holding/eligibility period before newly locked balance counts toward reward-per-token accrual — e.g., checkpoint balances used for reward distribution based on stake as of the start of the current reward epoch, or require a minimum lock duration (analogous to a "reward eligibility delay") before a user's balance is counted in `totalStaked()` for `_queueNewRewardsWithoutTransfer`/`queueNewRewards`. Alternatively, batch/vest forfeited amounts linearly over time (as many reward-streaming designs do) rather than instantaneously updating `rewardPerTokenStored` in a single block, which removes the atomic-frontrun window entirely.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder` with MGP as both staking-adjacent asset and reward token, per existing test fixtures.
2. Seed two honest lockers (Alice, Bob) with locked vlMGP positions established well before the test's forfeiting event, and let their positions age.
3. Simulate the "victim forfeiture" path: set up a large locked balance for `Victim`, put it in cooldown, and trigger the path that results in `queueMGP(_amount, Victim, receiver)` being called by an authorized `manager`, producing a large `forfeitAmount` via `_calExpireForfeit`.
4. **Baseline run:** call `queueMGP` directly (no attacker involvement) and record Alice's and Bob's claimable share via `getReward` after the forfeit is folded in.
5. **Attack run:** reset state to before step 3; have `Attacker` call `VLMGP.lockFor(bigAmount, attacker)` immediately before the `queueMGP` call in the same block; then call `queueMGP`; then have `Attacker` call `getReward` immediately.
6. Assert: `Attacker`'s captured forfeit share in the attack run is strictly greater than zero and disproportionate relative to Alice's/Bob's share compared to the baseline run — quantify by comparing `(attacker's claimed forfeit-derived MGP) / forfeitAmount` vs `attacker's contribution to totalStaked() over time` (near zero prior to front-run).
7. Assert Alice's and Bob's claimable rewards decreased in the attack run relative to baseline, holding the total forfeited amount constant, demonstrating dilution/theft of their yield.

```text
    function queueMGP(uint256 _amount, address _account, address _receiver) override external onlyManager nonReentrant returns (bool) {
        IERC20(vlMGP.MGP()).safeTransferFrom(msg.sender, address(this), _amount);
        
        uint256 forfeitAmount = _calExpireForfeit(_account, _amount);
        uint256 rewardableAmount = _amount - forfeitAmount;
        
        if (forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()));

        if (rewardableAmount > 0) {
            IERC20(vlMGP.MGP()).safeTransfer(_receiver, rewardableAmount);
            emit MGPHarvested(_account, rewardableAmount, forfeitAmount);
        }

        return true;
    }
```

```text
    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**vlMGPDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }
```
