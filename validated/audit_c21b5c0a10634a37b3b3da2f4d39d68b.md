Based on my research, I found the strongest analog in GitHub Desktop's **deep-link URL parser**, `parseAppURL` in `app/src/lib/parse-app-url.ts`. This directly matches the requested attacker surface ("a link or deep link the user clicks") and mirrors the report's broken-invariant pattern: some fields of an externally-controlled input are validated/sanitized before being trusted, while a sibling field carrying the same trust level is not, creating an inconsistent internal invariant that downstream code may rely on.

### Title
Deep-link `filepath` parameter is not validated like `branch`/`pr`, allowing an unsanitized value into repository-open flow - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL()` handles the `x-github-client://openrepo/...` deep link (also `github-mac://`/`github-windows://` legacy protocols), which is fully attacker-controlled content since it originates from a link a user clicks. For the `openrepo` action, the `pr` and `branch` query parameters are explicitly validated (`pr` must match `/^\d+$/`, `branch` is checked with `testForInvalidChars`), but the `filepath` parameter is read via `getQueryStringValue` and passed straight into the resulting `IOpenRepositoryFromURLAction` with **no validation whatsoever**. [1](#0-0) 

### Finding Description
The broken invariant is analogous to the `USDMPegRecovery` bug: the code assumes all fields of the parsed action are equally "safe" once the action object is constructed and dispatched (just like the contract assumed `totalLiquidity`/`userLiquidity` accounting always matched real, spendable balance). Here, `branch` and `pr` go through explicit format checks before being trusted, but `filepath` — a value later presumably used to open/reveal a file inside the just-opened repository — bypasses this check entirely: [2](#0-1) 

The action is then dispatched via `dispatchURLAction` → `openRepositoryFromUrl`: [3](#0-2) 

I was **not able to fully trace, within the remaining tool budget, the exact downstream consumer of `filepath`** (e.g., whether it is joined with the repository path via `path.join`/`Path.resolve` and passed to `shell.openPath`, an editor launcher, or similar). This is the critical missing link needed to state definitively whether a value like `filepath=../../../../etc/passwd` or an absolute path would result in a file read/open outside the cloned repository. The test suite only confirms parsing accepts arbitrary `filepath` strings without normalization or traversal checks: [4](#0-3) 

### Impact Explanation
If the downstream consumer of `filepath` joins it with the repository root and opens/reveals it in the file system or an external editor without checking that the resolved path stays inside the repository, a crafted deep link (`x-github-client://openrepo/<url>?filepath=..%2F..%2F..%2Fetc%2Fpasswd`) clicked by a victim could cause Desktop to open or reveal an arbitrary file outside the repo boundary — matching the allowed impact category "file write or read outside the repo" triggered by "a link or deep link the user clicks." This would be unprivileged, require no local access, and only a single click.

### Likelihood Explanation
Medium-low, pending confirmation of the sink. The asymmetry in validation (`branch`/`pr` sanitized, `filepath` not) is a concrete code smell suggesting this field was overlooked, similar to how the audited contract's `withdraw()` overlooked that `provide()` could deplete the balance backing its internal accounting. However, without confirming the exact function that consumes `IOpenRepositoryFromURLAction.filepath`, I cannot assert with certainty that a path-traversal sink exists — Desktop may only use `filepath` for cosmetic purposes (e.g., pre-selecting a file in the diff view) which would reduce the impact significantly.

### Recommendation
- Trace and inspect the consumer of `IOpenRepositoryFromURLAction.filepath` (likely in `app-store.ts` or a "open pull request file" flow) to confirm whether it's used in any filesystem path construction.
- Apply the same `testForInvalidChars`-style validation (or explicit path-traversal rejection / `path.normalize` + boundary check against the repository root) to `filepath` as is already done for `branch`.

### Proof of Concept
Not fully constructable without confirming the sink. The parser itself, however, demonstrably accepts unvalidated values:
```
x-github-client://openrepo/https://github.com/owner/repo?filepath=..%2F..%2F..%2F..%2Fetc%2Fpasswd
```
`parseAppURL` returns this filepath unmodified in the resulting action per `app/src/lib/parse-app-url.ts:98-124`, whereas an equivalent malformed `branch` value would be rejected by `testForInvalidChars` at line 114.

**Caveat**: Because I could not verify the exact downstream file-handling code for `filepath` within the available investigation budget, this should be treated as a **lead requiring confirmation**, not a fully proven vulnerability. If a Devin session/code review confirms `filepath` is never used to construct a filesystem path (e.g., only used for UI display or grep-matching an already-known list of repo files), this finding should be downgraded or dismissed.

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
