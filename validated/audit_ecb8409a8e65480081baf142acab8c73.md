### Title
Fail-open exception handling in `hookify` PreToolUse/PostToolUse/Stop hook executors silently drops `block`/`deny` rule enforcement on any parsing or evaluation error - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The `hookify` plugin implements a user-configurable guard rail system: `.claude/hookify.*.local.md` rule files define `block` rules that are supposed to deny dangerous `Bash`/`Write`/`Edit`/`MultiEdit` tool calls via `hookSpecificOutput.permissionDecision: "deny"` [1](#0-0) . This mirrors the two-layer gas-check structure in the Optimism report: an outer harness (Claude Code's PreToolUse dispatcher) treats the hook's exit code / JSON output as the authoritative enforcement decision, while the actual enforcement logic (`load_rules` + `RuleEngine.evaluate_rules`) is a separate inner computation that can fail. Just as `L1CrossDomainMessenger.relayMessage` used `revert` instead of `return false` and thereby discarded the failure record that should have preserved the withdrawal's replayability, `pretooluse.py` wraps the entire rule-loading/evaluation step in a bare `except Exception` that discards the failure and always falls back to an implicit *allow*, then unconditionally `sys.exit(0)`s in a `finally` block [2](#0-1) .

### Finding Description
`pretooluse.py` is the executable registered for Claude Code's `PreToolUse` event across every Bash/Edit/Write/MultiEdit call [3](#0-2) . Its `main()` function:

1. Loads all enabled `.claude/hookify.*.local.md` rule files via `load_rules()` [4](#0-3) .
2. Evaluates them with `RuleEngine.evaluate_rules()`, which is the only code path that can return `permissionDecision: "deny"` for a matched `block` rule [1](#0-0) .
3. Wraps steps 1–2 in `try/except Exception`, and on *any* exception, replaces the result with `{"systemMessage": f"Hookify error: {str(e)}"}` — an object with no `hookSpecificOutput.permissionDecision` at all [5](#0-4) .
4. Always calls `sys.exit(0)` in `finally`, explicitly documented as "ALWAYS exit 0 - never block operations due to hook errors" [6](#0-5) .

Because Claude Code treats "no `permissionDecision`" + exit code 0 as *no opinion → allow*, any exception inside the rule pipeline silently converts what should be a `deny` decision into an allow. `load_rule_file()`'s hand-rolled YAML/markdown frontmatter parser (`extract_frontmatter`) is a plausible, reachable source of such exceptions: it manually splits on `---`, tracks indentation state, and mutates dict/list buffers with string slicing [7](#0-6) ; malformed but syntactically-plausible rule content (e.g., inconsistent indentation combined with a `conditions:` list, or a rule value that triggers a `TypeError`/`AttributeError` when `Rule.from_dict` or `RuleEngine._check_condition` operate on unexpected types) can raise at multiple points. Although `load_rules()`/`load_rule_file()` already catch several exception classes and safely skip the *file* (still allowing other rules to load) [8](#0-7) , `RuleEngine.evaluate_rules()` itself has no internal exception handling around the per-rule loop, so any error inside `_rule_matches` → `_check_condition` → `_extract_field` (e.g., a `.startswith()`/`.endswith()` call in `_check_condition` on a non-string field, since `_extract_field` can return non-`str` values from `tool_input`) propagates up to `pretooluse.py`'s outer `except Exception`, at which point *every* rule's decision for that tool call — including matched `block` rules — is discarded and replaced with a bare allow. This is the same shape as the Optimism bug: the inner enforcement layer's failure is swallowed by a broad catch-all instead of being surfaced as a denial, and the outer layer (the CC permission dispatcher / OptimismPortal analog) has already committed to treating the hook's exit-0 as final.

### Impact Explanation
A `hookify` `block` rule (e.g., "block writes to `.env`", "block `rm -rf`") is a user-configured guardrail against destructive or credential-exposing tool calls. If the rule engine throws for any input that reaches a matching rule (crafted or malformed `tool_input`, or a rule authored with unusual `conditions:` values), the guard is defeated for that specific call with zero signal to the user beyond a possibly ignorable `systemMessage` — the tool call proceeds exactly as if no rule existed. This is an unprivileged-user-relevant command-approval bypass: the model (or an attacker steering the model via prompt injection) can execute a Bash command or file write that the user explicitly configured to be blocked, defeating the last line of defense hookify provides.

### Likelihood Explanation
Moderate. It requires either (a) a rule author writing a syntactically valid-looking but structurally unusual `.local.md` rule (quite plausible given the hand-rolled frontmatter parser and the `/hookify` command that lets the model auto-generate these files), or (b) a `tool_input` shape that causes `_check_condition`'s string methods to receive a non-string. Both are within normal usage of the advertised feature and don't require any external attacker capability beyond normal model/tool-call variability — the trust boundary crossed is "model output vs. user-declared deny policy," matching the analog's unprivileged-user scope.

### Recommendation
- Wrap the per-rule evaluation loop in `RuleEngine.evaluate_rules()` (and each `_check_condition`/`_extract_field` call) in narrow try/except blocks that skip only the offending rule (mirroring the existing per-file handling in `config_loader.load_rules()`), so one bad rule/input cannot blank out decisions from all other rules.
- In `pretooluse.py`/`posttooluse.py`/`stop.py`/`userpromptsubmit.py`, do not collapse an unexpected exception into an implicit allow. At minimum, fail closed for `PreToolUse` (emit `permissionDecision: "ask"` rather than silently allowing) when the rule pipeline cannot be evaluated, and always surface the exception to the user/transcript rather than only a swallowable `systemMessage`.
- Add regression tests that intentionally raise inside `_check_condition`/`_extract_field` with a matching `block` rule present, and assert the hook does not fall back to allow.

### Proof of Concept
1. Create `.claude/hookify.block-env.local.md`:
   ```markdown
   ---
   name: block-env-writes
   enabled: true
   event: file
   action: block
   conditions:
     - field: file_path
       operator: ends_with
       pattern: .env
   ---
   Blocked: writes to .env files are forbidden.
   ```
2. Have Claude Code (or a prompt-injected instruction) issue a `Write` tool call whose `tool_input.file_path` is not a `str` (e.g., a non-string JSON value smuggled through a tool-input mutation, or a downstream integration that passes `file_path` as `None`/a list) — `_extract_field` returns non-`str`, and `_check_condition`'s `field_value.endswith(pattern)` raises `AttributeError` [9](#0-8) .
3. `pretooluse.py`'s outer `except Exception` catches this, discards the `block` decision, prints only `{"systemMessage": "Hookify error: ..."}`, and `sys.exit(0)` — the `.env` write proceeds despite the configured `block` rule. [10](#0-9)

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```

```python
def extract_frontmatter(content: str) -> tuple[Dict[str, Any], str]:
    """Extract YAML frontmatter and message body from markdown.

    Returns (frontmatter_dict, message_body).

    Supports multi-line dictionary items in lists by preserving indentation.
    """
    if not content.startswith('---'):
        return {}, content

    # Split on --- markers
    parts = content.split('---', 2)
    if len(parts) < 3:
        return {}, content

    frontmatter_text = parts[1]
    message = parts[2].strip()

    # Simple YAML parser that handles indented list items
    frontmatter = {}
    lines = frontmatter_text.split('\n')

    current_key = None
    current_list = []
    current_dict = {}
    in_list = False
    in_dict_item = False

    for line in lines:
        # Skip empty lines and comments
        stripped = line.strip()
        if not stripped or stripped.startswith('#'):
            continue

        # Check indentation level
        indent = len(line) - len(line.lstrip())

        # Top-level key (no indentation or minimal)
        if indent == 0 and ':' in line and not line.strip().startswith('-'):
            # Save previous list/dict if any
            if in_list and current_key:
                if in_dict_item and current_dict:
                    current_list.append(current_dict)
                    current_dict = {}
                frontmatter[current_key] = current_list
                in_list = False
                in_dict_item = False
                current_list = []

            key, value = line.split(':', 1)
            key = key.strip()
            value = value.strip()

            if not value:
                # Empty value - list or nested structure follows
                current_key = key
                in_list = True
                current_list = []
            else:
                # Simple key-value pair
                value = value.strip('"').strip("'")
                if value.lower() == 'true':
                    value = True
                elif value.lower() == 'false':
                    value = False
                frontmatter[key] = value

        # List item (starts with -)
        elif stripped.startswith('-') and in_list:
            # Save previous dict item if any
            if in_dict_item and current_dict:
                current_list.append(current_dict)
                current_dict = {}

            item_text = stripped[1:].strip()

            # Check if this is an inline dict (key: value on same line)
            if ':' in item_text and ',' in item_text:
                # Inline comma-separated dict: "- field: command, operator: regex_match"
                item_dict = {}
                for part in item_text.split(','):
                    if ':' in part:
                        k, v = part.split(':', 1)
                        item_dict[k.strip()] = v.strip().strip('"').strip("'")
                current_list.append(item_dict)
                in_dict_item = False
            elif ':' in item_text:
                # Start of multi-line dict item: "- field: command"
                in_dict_item = True
                k, v = item_text.split(':', 1)
                current_dict = {k.strip(): v.strip().strip('"').strip("'")}
            else:
                # Simple list item
                current_list.append(item_text.strip('"').strip("'"))
                in_dict_item = False

        # Continuation of dict item (indented under list item)
        elif indent > 2 and in_dict_item and ':' in line:
            # This is a field of the current dict item
            k, v = stripped.split(':', 1)
            current_dict[k.strip()] = v.strip().strip('"').strip("'")

    # Save final list/dict if any
    if in_list and current_key:
        if in_dict_item and current_dict:
            current_list.append(current_dict)
        frontmatter[current_key] = current_list

    return frontmatter, message
```
