## Title
Case-Insensitive Bech32 Collision Bypasses Pointer-Registry Duplicate-Detection in `x/evm/keeper/pointer.go`

### Summary
The `btcutil/bech32` decoder used by sei-cosmos (`sei-cosmos/types/bech32/bech32.go` `DecodeAndConvert`, wrapping `bech32.Decode`) accepts bech32 strings that are entirely lowercase *or* entirely uppercase and decodes both to the identical underlying address bytes, per the BIP-173/bech32 spec. [1](#0-0)  The EVM keeper's pointer registry, however, keys its forward and reverse pointer records by the **raw, unnormalized address string** rather than the canonical decoded address, e.g. `PointerERC20CW20Key(cw20Address)` in `x/evm/types/keys.go` appends `[]byte(cw20Address)` directly to the key. [2](#0-1)  This is the same bug class as the node-tar advisory: a "reservation"/duplicate-detection layer normalizes/compares using the wrong equivalence relation relative to what the underlying decoder treats as identical.

### Finding Description
`SetERC20CW20PointerWithVersion`, `SetERC721CW721PointerWithVersion`, and `SetERC20NativePointerWithVersion` first call `cwAddressIsPointer`/existence checks, then persist under a key built purely from the caller-supplied string:

```go
func (k *Keeper) SetERC20CW20PointerWithVersion(ctx sdk.Context, cw20Address string, addr common.Address, version uint16) error {
	if k.cwAddressIsPointer(ctx, cw20Address) {
		return ErrorPointerToPointerNotAllowed
	}
	err := k.setPointerInfo(ctx, types.PointerERC20CW20Key(cw20Address), addr[:], version)
	...
	return k.setPointerInfo(ctx, types.PointerReverseRegistryKey(addr), []byte(cw20Address), version)
}
``` [3](#0-2) 

The precompile entry point (`AddCW20`, used by `precompiles/pointer`) accepts the CW address as a free-form string argument and only decodes it via `sdk.AccAddressFromBech32` to validate it and perform the `wasmdKeeper.QuerySmart` call — the *decoded, canonical* address is never used as the storage key; the original string is: [4](#0-3) 

```go
cwAddr := args[0].(string)
existingAddr, existingVersion, exists := p.evmKeeper.GetERC20CW20Pointer(ctx, cwAddr)
...
cwAddress, err := sdk.AccAddressFromBech32(cwAddr)   // canonical decode, used only for the wasm query
...
err = p.evmKeeper.SetERC20CW20Pointer(ctx, cwAddr, contractAddr)   // stores keyed by the RAW string cwAddr
```

`GetERC20CW20Pointer` performs an exact byte-for-byte lookup on `PointerERC20CW20Key(cw20Address)`, i.e. `[]byte(cw20Address)` appended to a fixed prefix — a pure string comparison with no case normalization: [5](#0-4) 

Since bech32 decoding is case-insensitive (accepting all-lowercase or all-uppercase encodings of the same data, per the spec implemented by `github.com/cosmos/btcutil/bech32`), two textually different strings — e.g. `sei1abc...xyz` and `SEI1ABC...XYZ` — decode to the exact same `sdk.AccAddress` / underlying CW contract, and both pass `sdk.AccAddressFromBech32` validation and the same `wasmdKeeper.QuerySmart` target. But because the pointer-registry key is derived from the literal string rather than the canonical decoded bytes, the duplicate check `GetERC20CW20Pointer(ctx, cwAddr)` will **not** find an existing pointer registered under the differently-cased spelling of the same address.

### Impact Explanation
An attacker (any unprivileged EVM caller, since `AddCW20`/`AddCW721` on the pointer precompile are public, unauthenticated transactions) can:
1. Call `addCw20("sei1abc...xyz")` to register pointer contract P1 for CW20 contract C.
2. Call `addCw20("SEI1ABC...XYZ")` (the case-flipped, still bech32-valid spelling of the identical address C) — the existence check misses the previous registration, so a **second** pointer contract P2 is deployed and registered for the *same* underlying CW20 contract C, under a distinct reverse-registry entry (`PointerReverseRegistryKey(P1) -> "sei1abc...xyz"`, `PointerReverseRegistryKey(P2) -> "SEI1ABC...XYZ"`).

This breaks the pointer registry's fundamental invariant of a unique ERC20↔CW20 mapping per underlying token. Multiple canonical ERC20 "views" of the same CW20 balance can now exist simultaneously, each independently trusted by downstream tooling/consumers that query `GetPointerInfo`/`Pointee`. Because CW20/ERC20 pointer contracts are used across the bridge to represent CW-native balances as ERC20 tokens for EVM consumers, having two independently-deployed and independently-trusted pointer contracts for the same CW20 balance can be leveraged to construct spoofed/duplicate token views, confusing indexers, DEX integrations, and any EVM contract that identifies "the" ERC20 wrapper for a CW20 asset via `getERC20CW20Pointer`/pointerview lookups, undermining the invariant that the pointer→pointee relationship is 1:1 and enabling downstream fund-accounting confusion for integrators relying on that uniqueness.

### Likelihood Explanation
Reachable directly from a single, unprivileged EVM transaction calling the public `pointer` precompile's `addCW20`/`addCW721`/`addERC20Native` methods — no special privileges, validator collusion, or off-chain component required. The only requirement is supplying a bech32 address string in a different (but still spec-valid) letter case than a previous registration, which is trivial and deterministic (not a race condition/timing-dependent race like the original node-tar bug, but the exact same root cause: a normalization mismatch between the "reservation"/duplicate-check layer and the actual underlying equivalence class of the resource).

### Recommendation
Normalize the address key before use in `PointerERC20CW20Key`, `PointerERC721CW721Key`, `PointerERC1155CW1155Key`, `PointerERC20NativeKey`, and the reverse-registry pointee string, by decoding through `sdk.AccAddressFromBech32` and re-encoding with `.String()` (canonical lowercase bech32) — or otherwise storing/comparing the raw decoded address bytes — before computing any pointer-registry key or performing existence checks, so that all bech32-equivalent spellings of an address map to a single canonical registry entry.

### Proof of Concept
1. Deploy/identify a CW20 contract with bech32 address `sei1abc...` (lower-case).
2. Compute the case-flipped bech32-valid equivalent (`SEI1ABC...`, uppercase) — bech32 requires the whole string to be one case, and both decode to the same underlying bytes.
3. Call `pointer.addCw20("sei1abc...")` via the EVM pointer precompile — succeeds, deploys pointer contract P1, `GetERC20CW20Pointer(ctx,"sei1abc...")` now returns P1.
4. Call `pointer.addCw20("SEI1ABC...")` — the existence check `GetERC20CW20Pointer(ctx,"SEI1ABC...")` misses P1 (different byte-string key), so the call succeeds again, deploying a second pointer contract P2 for the identical underlying CW20 contract.
5. Observe two independent, live ERC20 pointer contracts (P1, P2) both proxying the same CW20 balance, confirmed via `x/evm/keeper/pointer.go`'s `GetERC20CW20Pointer`/`GetCW20Pointee` returning inconsistent results depending on which string casing is queried.

// DecodeAndConvert decodes a bech32 encoded string and converts to base64 encoded bytes.
func DecodeAndConvert(bech string) (string, []byte, error) {
	hrp, data, err := bech32.Decode(bech, 1023)
	if err != nil {
		return "", nil, fmt.Errorf("decoding bech32 failed: %w", err)
	}

	converted, err := bech32.ConvertBits(data, 5, 8, false)
	if err != nil {
		return "", nil, fmt.Errorf("decoding bech32 failed: %w", err)
	}

	return hrp, converted, nil
```

	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err

		return nil, 0, err
	}

		return nil, 0, err

		return nil, 0, err
