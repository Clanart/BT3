## Title
Recursive precompile calls share a single `BalanceHandler` instance, causing `prevEventsLen` to be overwritten and desynchronizing bank-module balances from EVM `StateDB` balances - (File: `precompiles/common/precompile.go` / `testutil/testdata/debug/debug.go`)

### Summary
The Gravity.sol report asks for an emergency brake to stop an in-progress exploit before funds move. The applicable native analog in this repo is not a missing "pause" switch, but a state-consistency bug that a Devin test already reproduces and flags by name: recursive/nested precompile calls that reuse a single `BalanceHandler`, so its `prevEventsLen` bookkeeping gets clobbered and bank-module coin-spent/coin-received events get mis-attributed (or lost) between the Cosmos bank keeper and the EVM `StateDB` balance view. Unlike Gravity.sol, there is no pause mechanism gating this precompile call flow, so once triggered within one atomic EVM transaction it cannot be interrupted.

### Finding Description
Each stateful precompile execution records the current length of `ctx.EventManager().Events()` via `BalanceHandler.BeforeBalanceChange`, then after the native action, replays only the events appended since that recorded index (`events[bh.prevEventsLen:]`) to apply `AddBalance`/`SubBalance` on the `StateDB` [1](#0-0) . This design assumes a linear, non-overlapping precompile call life-cycle.

Some precompiles (e.g. the debug/test precompile mirrored by production-pattern precompiles that hold a single `BalanceHandler` on the struct via `GetBalanceHandler()`) keep that handler on the receiver rather than creating a fresh one per call [2](#0-1) . When a contract makes a nested/recursive call back into the same precompile before the outer call's `AfterBalanceChange` runs, `BeforeBalanceChange` is invoked again and overwrites `bh.prevEventsLen` with the inner call's starting index. When the inner call returns and processes `AfterBalanceChange`, and then the outer call resumes and calls `AfterBalanceChange` again, the event window computed from the now-stale/overwritten `prevEventsLen` no longer corresponds to the correct slice of bank events for that call frame - leading to double-processing, skipped events, or events attributed to the wrong balance window.

The integration test explicitly built to demonstrate this describes it as: "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB" [3](#0-2) . The test drives this via a `callback` contract that recursively re-enters the debug precompile [4](#0-3) .

Note: the general-purpose `Precompile.runNativeAction` (used by ERC20/ICS20/staking precompiles) allocates a *new* `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()` [5](#0-4) , which mitigates this specific sharing issue for those precompiles. I could not fully verify, within the available index, whether any production (non-test) precompile stores its `BalanceHandler` as a persistent struct field the way the debug precompile does, or whether nested calls into the *same* generic precompile instance (which is a long-lived Go object registered once, not per-tx) could still race on `BalanceHandlerFactory`/other shared state across concurrent/nested invocations within one EVM call stack. This would need to be confirmed by inspecting all registered stateful precompiles (`erc20`, `staking`, `distribution`, `ics20`, `bech32`, `bank`, `gov`, etc.) for any handler or counter stored on the precompile struct itself rather than created fresh per `Run`/`RunNativeAction` invocation.

### Impact Explanation
If a production precompile does hold shared/reentrant-unsafe state (as the debug precompile pattern shows is possible), an unprivileged EVM contract could trigger a StateDB balance view that diverges from the actual bank-module ledger within a single transaction. Since `StateDB.AddBalance`/`SubBalance` for the native EVM balance are what get committed back via `Commit()`/`commitWithCtx` [6](#0-5) , a persistent divergence between bank balances and EVM balances is an accounting-corruption class bug matching the "irreversible accounting corruption of spendable user value across native balances / EVM balances" impact category.

### Likelihood Explanation
Likelihood for the exact scenario demonstrated (debug/test precompile) is high and reproducible today via the referenced test, but the debug precompile is explicitly test-only and not part of production surface (`Package debug defines test utilities that are meant for debugging the chain, and *not* for use in production.`) [7](#0-6) . I was not able to confirm an equivalent reentrancy-unsafe shared-state pattern in a production precompile (erc20/ics20/staking/etc.) within the available index/tool budget — the generic `RunNativeAction` path allocates a fresh handler per invocation, which appears to close this specific vector for those precompiles.

### Recommendation
Recommend that a background engineer:
1. Audit every registered stateful precompile (erc20, ics20, staking, distribution, bank, gov, bech32, and any others) to confirm each call path allocates a fresh `BalanceHandler` per invocation (as `runNativeAction` does), and none store a `BalanceHandler` (or any per-call cursor like `prevEventsLen`) as a field on the long-lived precompile struct.
2. If any production precompile is found to reuse a handler across nested/recursive calls, refactor to always construct the handler locally within the call (matching the `RunNativeAction` pattern), or make `AddPrecompileFn`'s snapshot/event-window handling stack-aware (e.g., pass event window explicitly through the call rather than storing it as mutable receiver state).
3. Add/extend the existing `balance_handler_test.go` reentrancy test to run against all production precompiles that support nested EVM calls, not just the debug precompile, to guard against regressions.

### Proof of Concept
The reproduction already exists in the repo: `evmd/tests/integration/balance_handler/balance_handler_test.go` deploys a caller contract that recursively calls back into the debug precompile (`callback(0)`), and asserts on event counts to demonstrate that `prevEventsLen` state is shared/overwritten across recursive invocations [8](#0-7) . Extending this harness to a bank-affecting production precompile (if one is found to share handler state) would demonstrate concrete balance desync rather than only an event-count anomaly.

// Commit writes the dirty states to keeper
// the StateDB object should be discarded after committed.
func (s *StateDB) Commit() error {
	// writeCache func will exist only when there's a call to a precompile.
	// It applies all the store updates preformed by precompile calls.
	if s.writeCache != nil {
		s.writeCache()
	}
	return s.commitWithCtx(s.ctx)
}

// CommitWithCacheCtx writes the dirty states to keeper using the cacheCtx.
// This function is used before any precompile call to make sure the cacheCtx
// is updated with the latest changes within the tx (StateDB's journal entries).
func (s *StateDB) CommitWithCacheCtx() error {
	return s.commitWithCtx(s.cacheCtx)
}

// commitWithCtx writes the dirty states to keeper
// using the provided context
func (s *StateDB) commitWithCtx(ctx sdk.Context) error {
	for _, addr := range s.journal.sortedDirties() {
		obj := s.stateObjects[addr]
		if obj.selfDestructed {
			if err := s.keeper.DeleteAccount(ctx, obj.Address()); err != nil {
				return errorsmod.Wrapf(err, "failed to delete account %s", obj.Address())
			}
		} else {
			if obj.code != nil && obj.dirtyCode {
				if len(obj.code) == 0 {
					s.keeper.DeleteCode(ctx, obj.CodeHash())
				} else {
					s.keeper.SetCode(ctx, obj.CodeHash(), obj.code)
				}
			}
			if err := s.keeper.SetAccount(ctx, obj.Address(), obj.account); err != nil {
				return errorsmod.Wrap(err, "failed to set account")
			}

			for _, key := range obj.dirtyStorage.SortedKeys() {
				valueBytes := obj.dirtyStorage[key].Bytes()
				if len(valueBytes) == 0 {
					s.keeper.DeleteState(ctx, obj.Address(), key)
				} else {
					s.keeper.SetState(ctx, obj.Address(), key, valueBytes)
				}
			}
		}
	}
	return nil
}
