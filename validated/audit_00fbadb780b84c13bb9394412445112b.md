### Title
Outbound-request delivery rewards are permanently frozen when a stale timeout proof races real delivery - ([File: modules/ismp/core/src/handlers/timeout.rs])

### Summary

### Finding Description
`process_outbound_request_delivery_claim` (the reward-claim entrypoint for relayers that deliver hyperbridge-originated requests) is gated on the request's commitment still being present in local storage: [1](#0-0) 

That commitment is removed by the generic ISMP timeout handler, which accepts a **non-membership proof anchored at any previously-finalized state height** for the destination, not necessarily the latest one: [2](#0-1) [3](#0-2) 

Timeout handling is explicitly permissionless ("Access: Permissionless" per the EVM handler docs, and the substrate `handle_timeouts` path has no origin check either), and once the module callback succeeds the commitment is unconditionally deleted: [4](#0-3) 

Because Hyperbridge retains state commitments for multiple historical heights (each `StateMachineUpdate` is stored independently and only needs its own challenge period to elapse), it is possible to submit a timeout with a non-membership proof for an *older* finalized height — one that predates the block where the relayer's delivery actually landed on the destination — even though a *newer* height already proves the request was delivered (`RequestReceipts[commitment]` is set). The handler only checks non-membership at the height supplied in the proof; it never checks whether a later, already-committed height shows the request as delivered.

For ordinary user-funded requests this race is harmless: `on_timeout`/`on_request_timeout` simply refunds the payer's fee, and the relayer who actually delivered still gets nothing extra either way. But hyperbridge-originated system requests (host-executive, intents-coprocessor, token-governor, relayer withdrawal) dispatch with `FeeMetadata { payer: 0, fee: 0 }` (per `docs/outbound-request-incentivization.md`), and their delivery reward is paid out later, keyed strictly by commitment presence in `RequestCommitments`. If the commitment is deleted by a stale-but-valid timeout before the relayer submits `claim_outbound_request_delivery_reward`, the claim path hits `OutboundRequestNotKnown` and can never succeed again — even though the relayer genuinely delivered the request and the destination's `RequestReceipts[commitment]` proves it.

This mirrors the Alchemix bug precisely: a legitimate, unclaimed entitlement (ALCX yield / bridge relayer reward) becomes permanently unclaimable the moment the underlying record it depends on (the veALCX lock / the `RequestCommitments` entry) is destroyed (burn / timeout-delete) through a code path that does not first settle or protect the pending claim.

### Impact Explanation
Permanent freezing of relayer rewards for a valid, already-completed delivery. The relayer performed the real off-chain work (delivering the hyperbridge-originated request) but is permanently denied payment from the treasury with no recovery path, since `OutboundRequestsClaimed`/`OutboundRequestDeliveryReward` lookups both depend on the now-deleted `RequestCommitments` entry and the pallet has no path to re-derive or reward against a commitment it no longer recognizes.

### Likelihood Explanation
No privileged actor, malicious relayer, or leaked key is required. Any unprivileged account can call the permissionless timeout handler with a non-membership proof anchored at an older, already-challenge-period-elapsed height — a proof that is honestly valid for that height, simply stale relative to the delivery that has since happened at a later height. This can occur naturally under network delay (a timeout submission racing a delivery submission) or can be deliberately triggered by anyone who watches for hyperbridge-originated dispatches near their timeout window and submits an older-height non-membership proof before the delivery claim is processed.

### Recommendation
Before deleting a request's commitment in `handle::<H>` (`modules/ismp/core/src/handlers/timeout.rs`), check whether a state commitment at a height *later* than `timeout_proof.height` (but still known to the host) already proves delivery (i.e. a `RequestReceipts` membership at any committed height ≥ the timeout proof height for the destination). If such a later height exists, reject the timeout with a "delivery already observed" error instead of deleting the commitment. Alternatively, for `pallet-relayer`'s outbound-request reward path, decouple the reward eligibility check from `RequestCommitments` presence and instead key it off an immutable append-only log of dispatched hyperbridge-originated commitments (write-once, never deleted by timeout processing), so a legitimate delivery reward is never invalidated by unrelated timeout housekeeping.

### Proof of Concept
1. Host-executive (or intents-coprocessor / token-governor) dispatches a hyperbridge-originated `PostRequest` with a timeout window; `RequestCommitments[commitment]` is created.
2. A relayer delivers the request to the destination at height `H_deliver`; `RequestReceipts[commitment]` is now set on the destination, and a `StateMachineUpdate` for the destination at height `H_deliver` is later relayed to and committed on Hyperbridge.
3. Before the relayer submits `claim_outbound_request_delivery_reward`, anyone submits `TimeoutMessage::Post` with a non-membership proof anchored at an older height `H_old < H_deliver` for which Hyperbridge already stores a state commitment and whose challenge period has elapsed (`modules/ismp/core/src/handlers/timeout.rs:49-55,84-88`). At `H_old` the request had genuinely not yet been delivered, so the non-membership proof verifies.
4. `handle` deletes `RequestCommitments[commitment]` (`modules/ismp/core/src/handlers/timeout.rs:106-123`).
5. The relayer now calls `claim_outbound_request_delivery_reward` with the real `RequestReceipts[commitment]` proof from `H_deliver`; `process_outbound_request_delivery_claim` fails at the `RequestCommitments::<T>::get(commitment).is_some()` check with `OutboundRequestNotKnown` (`modules/pallets/relayer/src/outbound_request.rs:133-136`), and the reward can never be claimed again.
