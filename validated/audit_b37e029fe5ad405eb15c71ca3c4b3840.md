### Title
`recover_key` validates recovered secrets only against attacker-supplied group keys, enabling impersonation of the recovered key - (File: crypto/dkg/recovery/src/lib.rs)

### Summary
The Contrast advisory (GHSA-vqv5-385r-2hf8) is a missing-authentication bug: a recovering coordinator accepts a secret seed from the recovering party without binding it to a previously committed public value, so an attacker-supplied seed "passes validation" and yields an attacker-known key. Serai's `recover_key` in `dkg-recovery` has the same shape: when reconstructing a shared secret from a set of deserialized `ThresholdKeys`, every value it cross-checks (parameters, `group_key`, `verification_shares`, `secret_share`) comes from the same untrusted input, and `ThresholdKeys::read`/`ThresholdKeys::new` never verify that the secret share is consistent with the participant's verification share or that the group key matches any externally trusted commitment.

### Finding Description
`recover_key` collects the included participants, checks only intra-input consistency (same `t`/`n`/`group_key`/`scalar`/`offset` across all provided `ThresholdKeys`), sums the interpolated secret shares via `ThresholdKeys::view`, and finally checks `C::generator() * res == first_keys.group_key()` — where `first_keys.group_key()` is itself derived from the attacker-supplied `verification_shares` (`ThresholdKeys::new` computes `group_key` as `sum(verification_shares[i] * interpolation_factor(i))` for `i in 1..=t`). [1](#0-0) [2](#0-1) 

The deserialization path `ThresholdKeys::read` reads `t`, `n`, `i`, the interpolation variant (including a fully attacker-chosen `Constant` coefficient vector of length `n`), the raw `secret_share` via `C::read_F`, and all `n` `verification_shares` via `C::read_G`, then constructs the keys without ever checking `C::generator() * secret_share == verification_shares[params.i()]`. [3](#0-2) 

Consequently, an attacker who can feed `ThresholdKeys::read`/`recover_key` untrusted bytes can fabricate a `ThresholdKeys` set with a `secret_share` they chose, verification shares `G * s_i` they generated, and a `group_key` derived from those shares. All of `recover_key`'s checks pass — including the final `G * res == group_key` — while the "recovered" secret is fully known to the attacker. This is exactly the Contrast bug class: validation is circular and self-referential; nothing binds the recovered secret to a group key established by a legitimate prior DKG.

### Impact Explanation
If `recover_key` (or signing with `ThresholdKeys` material obtained from an untrusted source) is used in a recovery/migration flow — e.g., a node operator restoring keys from a backup or coordinator-supplied blob — the caller is led to believe the recovered key is the legitimate threshold secret because `recover_key` returns `Ok`. The actual result is an attacker-known secret, enabling the attacker to forge signatures for any downstream operation that trusts the recovered key as the group's secret (key rotation proofs, ownership attestations, or funds migrated to a key derived from it). This is a High-severity key-recovery/impersonation analog: the secret reconstructed is controlled by the party supplying the shares, not the original group.

### Likelihood Explanation
The attack requires the `ThresholdKeys` bytes consumed by recovery to originate from an unprivileged party rather than exclusively from local, integrity-protected storage. `ThresholdKeys::read` is a public deserialization API over arbitrary `io::Read` streams, and `recover_key` is a public function accepting a slice of such keys with no provenance or trusted-anchor parameter. Wherever a recovery workflow accepts key material contributed by the recovering party (the scenario the upstream advisory describes), the path is reachable. Within Serai's own processor, keys are normally loaded from local DB, which lowers practical reachability — hence Medium–High rather than Critical.

### Recommendation
- In `ThresholdKeys::new` (and therefore `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]`, rejecting shares inconsistent with their public commitment. [4](#0-3) 
- In `recover_key`, require an externally supplied expected `group_key` (or expected `verification_shares`) and compare the reconstructed key's public key against it, rather than comparing against `first_keys.group_key()` taken from the same input. Document that consistency checks are not authentication. [5](#0-4)

pub fn recover_key<C: Ciphersuite>(
  keys: &[ThresholdKeys<C>],
) -> Result<Zeroizing<C::F>, RecoveryError> {
  let included = keys.iter().map(|keys| keys.params().i()).collect::<Vec<_>>();

  let keys_len = keys.len();
  let mut keys = keys.iter();
  let first_keys = keys.next().ok_or(RecoveryError::NoKeysProvided)?;
  {
    let t = first_keys.params().t();
    if keys_len < usize::from(t) {
      Err(RecoveryError::NotEnoughKeysProvided { required: t, provided: keys_len })?;
    }
  }
  {
    let first_params = (
      first_keys.params().t(),
      first_keys.params().n(),
      first_keys.group_key(),
      first_keys.current_scalar(),
      first_keys.current_offset(),
    );
    for keys in keys.clone() {
      let params = (
        keys.params().t(),
        keys.params().n(),
        keys.group_key(),
        keys.current_scalar(),
        keys.current_offset(),
      );
      if params != first_params {
        Err(RecoveryError::InconsistentParameters)?;
      }
    }
  }

  let mut res: Zeroizing<_> =
    first_keys.view(included.clone()).map_err(RecoveryError::DkgError)?.secret_share().clone();
  for keys in keys {
    *res.deref_mut() +=
      keys.view(included.clone()).map_err(RecoveryError::DkgError)?.secret_share().deref();
  }

  if (C::generator() * res.deref()) != first_keys.group_key() {
    Err(RecoveryError::Failure)?;
  }

  Ok(res)
