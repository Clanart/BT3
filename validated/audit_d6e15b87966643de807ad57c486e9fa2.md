### Title
Cached FROST preprocess reused across signing sessions sharing a context, enabling key share recovery - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
`SigningProtocol::preprocess_internal` deterministically derives a FROST preprocess (and hence the signing nonces `d, e`) from a seed stored under `CachedPreprocesses`, keyed only by `self.context`. The cache entry is read, decrypted, and passed to `AlgorithmSignMachine::from_cache`, but is never deleted, consumed, or bound to a specific signing session or message. Any second call to `share_internal` for the same context silently regenerates the identical preprocess/nonces and produces a signature share under a *different* binding factor `rho` and/or challenge `c`. Two shares produced from the same nonce seed under different `rho`/`c` yield a linear system that recovers the participant's secret key share. The external bug class (a message/operation that does not limit where it can be executed, CWE-693) maps directly: the cached preprocess is an unconstrained replayable cryptographic message. [1](#0-0) 

### Finding Description
In `preprocess_internal`, if `CachedPreprocesses::get(self.txn, &self.context)` is `None`, a fresh preprocess is generated, its 32-byte seed is XOR-masked with a key derived from `b"Cached Preprocess Encryption Key" || context || key`, and stored under the context key. On every subsequent call, the same stored seed is decrypted and expanded via `from_cache` → `seeded_preprocess`, producing byte-identical commitments and identical secret nonces `d, e`.

The seed is stored under `context` alone — there is no binding to `participants`, `msg`, or any per-session nonce, and nothing removes the entry after use. `share_internal` then calls `machine.sign(preprocesses, msg)` where the effective nonce is `d + rho * e`, with `rho` derived from the `FROST_rho` transcript over `group_key`, `hash_msg(msg)`, and the `preprocesses` challenge. [2](#0-1) [3](#0-2) 

If two `share_internal` executions occur under the same `context` — e.g., a retried signing attempt with a different declared signer set, or two transactions scheduled under the same context value — the same `d, e` are reused while `rho` and the Schnorrkel challenge `c` differ. Given shares `s1 = d + rho1·e + λ·c1·x` and `s2 = d + rho2·e + λ·c2·x`, an observer solves for `e = (s1 − s2 − λx(c1 − c2))/(rho1 − rho2)`… more directly: with the same public preprocess commitments, the two shares give `s1 − s2 = e·(rho1 − rho2) + λ·x·(c1 − c2)`; combined with the share-verification relation `s·G = R_share + c·Y_i`, `e` and then the secret share `x` are recoverable. In practice any two shares under the same nonce seed with different `(rho, c)` give `x = (s − r)/(λ·c)` once `r = d + rho·e` is solved.

### Impact Explanation
Recovery of a threshold participant's secret key share `x_i`. Combined with a threshold-1 set of cooperating or compromised preprocess transcripts, or used against the validator's Tributary signing key (Ristretto/Schnorrkel), this degrades to full key-share extraction from publicly broadcast signature shares — the exact "key share recovery" impact class. The spec itself acknowledges the severity: "Reusing preprocesses would enable a third-party to recover your private key share." [4](#0-3) 

### Likelihood Explanation
Requires two `share_internal` invocations resolving to the same `context` value. The code provides no defense-in-depth: no consume-on-use, no session/message binding, and a deterministic `from_cache` expansion, so the safety of the scheme rests entirely on every scheduler context being globally unique for all time — a property nothing in this file enforces. Because the bug is a missing protection mechanism rather than an actively triggered path, and exploitation only needs the shares broadcast on the authenticated channel, this is a High-severity latent failure: any context collision (retry after blame/round failure, scheduler bug, or two plans sharing a context encoding) immediately exposes the share.

Uncertain: whether the current scheduler actually emits duplicate contexts for distinct sign operations was not fully verified in this review; the vulnerability is the missing single-use enforcement itself, which turns any such collision into key compromise rather than an honest-mistake failure.

### Recommendation
- Delete or tombstone the `CachedPreprocesses` entry in `share_internal`/`preprocess_internal` immediately after reading, so a second sign under the same context generates a fresh seed (or fails loudly).
- Include the signing-session identifier (participants set and/or message hash) in the cache key or in the encryption-key preimage so stale seeds cannot be replayed into a different session.
- Track a "consumed" flag on `AlgorithmSignMachine`/`CachedPreprocess` so `from_cache` cannot be invoked twice on one seed. [5](#0-4) 

### Proof of Concept
1. Scheduler calls `share_internal(participants_A, preprocesses_A, msg1)` for context `C`. The seed under `CachedPreprocesses[C]` is decrypted and expanded → nonces `(d, e)`, commitments `(D, E)`.
2. A second call `share_internal(participants_B, preprocesses_B, msg2)` for the same `C` (retry, or a second scheduled item with a colliding context) re-reads the same seed → identical `(d, e)` and identical broadcast preprocess.
3. The participant's emitted shares are `s1 = d + ρ1·e + λ1·c1·x` and `s2 = d + ρ2·e + λ2·c2·x`, where `ρi` come from the `FROST_rho` transcript (different message/signing set) and `ci` from `SchnorrkelHram`.
4. `s1 − s2 = e·(ρ1 − ρ2) + λ·x·(c1 − c2)`. Using the public verification relation to eliminate `x` (or across three reused shares), solve for `e`, then `d`, then `x = (s1 − d − ρ1·e)/(λ1·c1)` — recovering the secret share from data already broadcast publicly.
