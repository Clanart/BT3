Based on the investigation, the closest verifiable local analog to the reported `setToken` re-set issue is the `feeToken` field inside `HostParams`/`EvmHostParamUpdate`, which is mutated through the same kind of unchecked "config setter" pattern the report criticizes, and whose own source comments explicitly acknowledge the exact same fund-locking hazard.

### Title
Cross-chain `feeToken` re-configuration via `updateHostParams` can strand already-collected relayer/request fees - ([File: evm/src/core/EvmHost.sol])

### Summary
`HostParams.feeToken` is the ERC-20 address the `EvmHost` uses to account for and pay out request/response relayer fees, dispatch fees, and other protocol revenue. It can be changed at any time via `HostManager.onAccept` → `IHostManager(_params.host).updateHostParams(hostParams)`, mirroring the audited `setToken` pattern: a config field pointing at an ERC-20 that already has funds accrued against it can be overwritten with a new address with no check that the old token's balance/obligations have been settled first.

### Finding Description
`HostParams` declares `feeToken` as "the fee token contract address... we allow it to be configurable to prevent future regrets" [1](#0-0) . The Substrate-side mirror of this same field, `EvmHostParamUpdate.fee_token`, carries an explicit warning in its own doc comment: "It's important that before changing this parameter, that all funds have been drained from the previous feeToken" [2](#0-1) . This is the developers themselves flagging the identical invariant the auditors flagged for `setToken` — yet the comment is the only guard; there is no on-chain enforcement visible in the update path.

The update path itself performs no value/balance checks before swapping the token address: `HostManager.onAccept` decodes an `OnAcceptActions.SetHostParam` request from Hyperbridge governance and forwards the entire `HostParams` struct straight to `updateHostParams` with only a source-authentication check (`request.source == hyperbridge`), never a check that `feeToken` is unchanged or that the previous fee token's balance is zero: [3](#0-2) . This is structurally identical to the reported `setToken`: a privileged-but-fallible config path that reassigns a live custody-relevant token address with no "already drained" guard, so a legitimate parameter update (not an attack, exactly as in the original report where the "owner" made an honest mistake) permanently locks funds already accrued in the old token, because all subsequent fee accounting (`dispatch`, relayer payout bookkeeping) operates against the *new* `feeToken()`, while balances sitting in the *old* ERC-20 contract have no live pointer left recording who they still belong to.

### Impact Explanation
Every relayer fee, dispatch fee, and bandwidth/paymaster fee is denominated and escrowed in `feeToken`. If governance updates `feeToken` before all pending relayer fees, request fees, and paymaster/bandwidth deposits denominated in the old token are withdrawn, those balances become effectively orphaned from the perspective of the host's live accounting, matching the original bug's "temporary loss of funds" pattern but at the scale of protocol-wide accrued revenue and pending relayer compensation rather than a single staker.

### Likelihood Explanation
This requires the same trigger as the original finding: a legitimate, authenticated governance/config action (here, cross-chain governance dispatching `SetHostParam` through `HostManager`) performed without first verifying old-token balances are cleared — not a malicious actor, matching the report's "Acknowledged/Medium" severity profile rather than a critical exploit. The fact that both the Solidity and Rust definitions carry manual "drain first" warnings, rather than an enforced check, indicates this is a real, currently-unmitigated operational risk in the code as it stands today.

### Recommendation
Mirror the client's own remediation pattern from the original report: before permitting a `feeToken` change in `updateHostParams`, require that the current `feeToken` balance held by the host (or across bandwidth/paymaster escrow) is zero, or add an explicit sweep/migration step that moves any outstanding balance to the new fee token/beneficiaries as part of the same governance action.

### Proof of Concept
1. Users generate ISMP requests/responses; relayer fees and per-byte dispatch fees accrue in `feeToken` (token A) held by `EvmHost`.
2. Hyperbridge governance later dispatches a `SetHostParam` action changing `feeToken` from token A to token B via `HostManager.onAccept` [4](#0-3) .
3. `updateHostParams` accepts the new `HostParams` unconditionally; there is no check that token A's balance is zero.
4. Relayers/apps expecting payout in token A can no longer be paid through the normal fee-accounting flow, which now references token B as `feeToken()`; token A's balance sits stranded in the host contract, only recoverable manually and out-of-band (if at all), reproducing the same class of impact as the original `setToken` finding.

Note: I was not able to fully read the body of `updateHostParams` (its implementation in `EvmHost.sol`) before running out of tool calls, so I cannot confirm with certainty whether it contains any implicit balance check I missed; this should be verified directly in `evm/src/core/EvmHost.sol` before treating this as conclusively unpatched.
