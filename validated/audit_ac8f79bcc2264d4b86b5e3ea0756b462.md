### Title
App Proxy request signature verification has no timestamp freshness check, enabling unlimited replay of a captured signed request - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` validates only that the HMAC `signature` query parameter matches the other query parameters; it never checks that the `timestamp` parameter is recent. As a result, any previously captured, validly-signed app-proxy request URL remains valid forever and can be replayed against the endpoint an unlimited number of times by anyone who obtains it, exactly analogous to `GaugeController::distributeRewards` being callable repeatedly with no time-based gating.

### Finding Description
`verify_proxy_request` calls `query_string_valid?`, which recomputes the HMAC signature over all query parameters except `signature` and compares it to the supplied `signature` using `ActiveSupport::SecurityUtils.secure_compare`: [1](#0-0) 

Nothing in this method (or anywhere else in the module) inspects the `timestamp` parameter that Shopify includes in every app-proxy request, nor rejects requests whose `timestamp` is stale. The signature is a deterministic HMAC over the query string using the app's shared secret, so it will validate successfully no matter how old the `timestamp` value is — as proven by the project's own test suite, which asserts that a request with `timestamp=1466106083` (year 2016) still produces a valid signature and passes verification: [2](#0-1) [3](#0-2) 

Because app-proxy endpoints are public, unauthenticated HTTP endpoints reached directly by anonymous browser requests forwarded through Shopify's storefront proxy (that's the entire point of the app proxy feature), any signed URL that is exposed once — via browser history, server access logs, a shared/cached link, a Referer header leak, browser extensions, or a network intermediary — can be captured and replayed against the app indefinitely with no way for the app to detect or reject the replay. This mirrors the report's root cause: a state-changing/reward-triggering action is reachable repeatedly with no temporal check preventing repeated invocation of the same otherwise-legitimate request.

### Impact Explanation
Any app-proxy controller that relies solely on `ShopifyApp::AppProxyVerification` for authorization (as documented and generated by `rails g shopify_app:app_proxy_controller`) inherits this weakness. If such a controller performs any state-changing or resource-consuming action (e.g., recording a vote/review, redeeming a discount, incrementing a counter, sending a notification, granting a one-time benefit), an attacker who captures a single valid signed request URL can replay it as many times as desired, producing the same class of "excessive repeated distribution/action" harm described in the original report. This is a design gap in the shared verification concern itself, not merely a misuse by app developers, since the module's only documented guarantee is signature validity, and no companion mechanism (nonce store, timestamp window check) is provided.

### Likelihood Explanation
Exploitation requires an attacker to obtain one previously-issued valid signed app-proxy URL (which is not secret and is routinely embedded in page content, logs, or shared/forwarded links since it's delivered over the storefront to any visitor), after which replay is trivial and unauthenticated. This is realistically likely wherever an app proxy performs any per-request effect, and the codebase's own tests demonstrate acceptance of decade-old timestamps, confirming there is no time-boxing at all.

### Recommendation
Add a freshness check on the `timestamp` query parameter in `query_string_valid?` (or `verify_proxy_request`), rejecting requests whose timestamp is outside an acceptable window (e.g., a few minutes), similar to standard replay-protection practice:
```ruby
def verify_proxy_request
  head(:forbidden) unless query_string_valid?(request.query_string) && timestamp_fresh?(request.query_string)
end

def timestamp_fresh?(query_string)
  ts = Rack::Utils.parse_query(query_string)["timestamp"].to_i
  (Time.now.to_i - ts).abs <= ShopifyApp.configuration.app_proxy_timestamp_tolerance # e.g. 300 seconds
end
```
This closes the replay window while preserving existing signature verification behavior.

### Proof of Concept
Using the existing test helper `query_string_valid?` in `test/shopify_app/controller_concerns/app_proxy_verification_test.rb`, the query string:
```
shop=some-random-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=f5cd7233558b1c50102a6f33c0b63ad1e1072a2fc126cb58d4500f75223cefcd
```
(a signature generated with `timestamp=1466106083`, i.e. June 2016) is accepted as valid by `query_string_valid?` and by the controller action (`assert_response :ok`) even though the timestamp is many years old, demonstrating that any captured valid app-proxy URL can be replayed at any future time with no rejection: [3](#0-2)

      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
