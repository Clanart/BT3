## Analysis

The external report's core broken invariant: a completion/finalization gate reads a **raw `balanceOf(address(this))`** and requires it to be exactly zero before allowing a state transition to proceed. Because anyone can transfer a token directly to the contract without going through the tracked accounting path, an unprivileged attacker can permanently keep that balance non-zero and block the gated action forever.

The same pattern exists in `EvmHost.updateHostParamsInternal()`.

### Title
Permanent denial-of-service on fee-token migration via dust-donation griefing of `balanceOf(address(this))` check - (File: `evm/src/core/EvmHost.sol`)

### Summary
`updateHostParamsInternal()` gates any change of the protocol `feeToken` on the `EvmHost` contract's own balance of the *old* fee token being exactly zero. Since ERC-20 `transfer()` is unrestricted, any unprivileged actor can send 1 wei of the old fee token to the `EvmHost` contract at any time, permanently keeping that balance non-zero and blocking cross-chain governance from ever migrating the fee token again.

### Finding Description
`updateHostParamsInternal` is invoked by `updateHostParams`, restricted to `_hostParams.hostManager` (cross-chain governance) via the `restrict` modifier [1](#0-0) . Inside it, when governance attempts to change `feeToken` to a different address, the function requires the contract's current balance of the *old* fee token to be zero:

```solidity
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
``` [2](#0-1) 

This is the exact analog of `LogarithmVault._isWithdrawRequestExecuted()` checking `utilizedAssets() == 0` where `utilizedAssets` includes `IERC20(asset()).balanceOf(address(this))` — a raw balance that any address can inflate via a direct ERC-20 transfer, with no way for the contract to distinguish "protocol-owned" balance from "griefed dust." No unprivileged permission, relayer, prover, or admin key is needed for the attacker — a plain `IERC20(oldFeeToken).transfer(evmHostAddress, 1)` call, callable by literally anyone, suffices. Once sent, the balance can never return to exactly zero on demand (the contract only spends fee-token balance opportunistically through `withdraw()`, `restrict(_hostParams.hostManager)` [3](#0-2) , and normal ISMP fee flows, none of which are guaranteed to zero it out at the moment governance wants to migrate).

### Impact Explanation
This blocks a legitimate, governance-authorized `updateHostParams` fee-token migration indefinitely: cross-chain governance can never successfully switch `feeToken` on that `EvmHost` deployment once an attacker has donated dust of the old fee token, because the check `balance != 0` will keep reverting with `CannotChangeFeeToken()`. This is a logic attack that permanently disables a host-management execution path with a single unprivileged transaction and no ongoing cost beyond 1 wei of the token, matching the accepted impact class "logic attacks" / "unauthorized... transaction manipulation" against host-management execution called out in the bounty scope.

### Likelihood Explanation
Trivial and cheap to trigger: any address can call `transfer(evmHostAddress, 1)` on the current fee token at any time, with no special timing, no relayer/prover collusion, and no admin/governance compromise required. The attack is a pure griefing/front-running-independent action — it can be executed proactively, well before any governance proposal to change `feeToken` exists, making it a low-cost, always-available denial-of-service against future fee-token migrations.

### Recommendation
Do not gate the fee-token change on a raw `balanceOf(address(this)) == 0` check. Instead, either (a) drop the check entirely and let leftover dust of the old fee token remain sweepable via the existing `withdraw()` function after migration, or (b) track fee-token balance via internal accounting (a ledger incremented/decremented on protocol-controlled deposits and withdrawals) rather than trusting the externally-manipulable ERC-20 `balanceOf`.

### Proof of Concept
1. Attacker observes `EvmHost.feeToken()` returns token `F`.
2. Attacker calls `F.transfer(evmHostAddress, 1)` — no permissions needed, standard ERC-20 call.
3. `EvmHost`'s balance of `F` is now `1` (or more) and can never be forced back to `0` by governance alone.
4. Cross-chain governance later dispatches an `updateHostParams` message trying to change `feeToken` from `F` to a new token `G`.
5. `updateHostParamsInternal` computes `balance = IERC20(F).balanceOf(address(this))`, which is non-zero, and reverts with `CannotChangeFeeToken()` [2](#0-1) , permanently blocking the fee-token migration for that host.
