### Title
Decimal-scaling uses `saturating_sub` in the wrong direction, silently skipping down-scaling and inflating cross-chain amounts — ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`hyper-fungible-token`'s decimal-conversion helpers `convert_to_erc20` and `convert_to_balance` compute the scaling exponent with `erc_decimals.saturating_sub(local_decimals)` (and its inverse), which silently clamps to `0` whenever the subtraction would be negative, instead of applying scaling in the opposite direction. This is the exact same bug class as the reported `MixOracle::getThePrice()` issue: using the wrong scaling variable/direction produces an inflated or deflated value whenever the two decimal precisions differ in the "wrong" order.

### Finding Description
`convert_to_erc20` is used in the public `send()` extrinsic to convert a locally-denominated balance into the amount encoded in the outgoing ISMP `Message` that will be interpreted by the destination chain's ERC20 contract: [1](#0-0) 

```
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

This only up-scales correctly when `erc_decimals > local_decimals`. If the local asset's decimals are *greater* than the destination ERC20's configured `Precisions` decimals (a legitimate, admin-configurable case — e.g. a locally 18-decimal `pallet-assets` token bridged to a 6-decimal ERC20 representation), `erc_decimals.saturating_sub(local_decimals)` clamps to `0`. The function then multiplies by `10^0 = 1`, i.e. performs **no down-scaling at all**, instead of dividing by `10^(local_decimals - erc_decimals)` as correctness requires.

This is invoked directly from the unprivileged, signed `send()` extrinsic: [2](#0-1) 

The symmetric bug exists in `convert_to_balance`, used by `on_accept` (crediting incoming transfers) and `on_timeout` (refunding failed transfers): [3](#0-2) [4](#0-3) [5](#0-4) 

There, if `erc_decimals < local_decimals`, the exponent again clamps to `0`, so the received/refunded amount is under-scaled by `10^(local_decimals - erc_decimals)` (the value is left in remote-chain units instead of being multiplied up to local-chain units), causing beneficiaries to receive far fewer tokens than escrowed/minted on the other side.

The destination-side EVM contracts (`HyperFungibleToken`/`WrappedHyperFungibleToken`) trust the `amount` field encoded in the `Message` and mint/release exactly that value with no independent decimal cross-check, so an inflated `erc20_amount` from `send()` becomes a real, unauthorized excess mint/release on the destination chain.

### Impact Explanation
When `local_decimals > erc_decimals` for a registered asset (an admin-supported, documented configuration — see `Precisions`/`update_token`), any unprivileged user calling `send()` gets an amount encoded on the destination chain that is `10^(local_decimals - erc_decimals)` times larger than intended, while only the correct (small) local amount was escrowed/burned. This directly produces unauthorized excess minting/release of destination-chain funds — a fund-creation/loss primitive, not merely a display bug, matching the bounty's "unauthorized transaction/execution" and "false state acceptance" criteria. The reverse direction (`erc_decimals < local_decimals` on `on_accept`/`on_timeout`) causes recipients/refunded senders to be under-credited, i.e. fund loss/lock for legitimate users.

### Likelihood Explanation
The trigger condition is purely a decimal-configuration mismatch that is explicitly supported by the pallet's design (`Precisions` is a per-asset, per-chain `u8` map, and the pallet's own docs cite differing decimals like 10-decimal DOT vs 18-decimal DOT as the intended use case). Any asset registered with local decimals higher than the configured remote `erc_decimals` (or vice-versa for the receive path) triggers the bug on every single transfer, with no attacker privilege beyond calling the public `send()` extrinsic.

### Recommendation
Replace the one-sided `saturating_sub` scaling with a direction-aware calculation that multiplies when `erc_decimals > local_decimals` and divides when `erc_decimals < local_decimals` (mirroring the fix pattern in the source report — use the correct decimals difference and correct operation, not a value that silently becomes `0`), in both `convert_to_erc20` and `convert_to_balance`.

### Proof of Concept
1. Admin registers asset `X` with `NativeAssets::<T>` and `local_decimals = 18` (via `pallet-assets`), and sets `Precisions::<T>::insert(X, dest_chain, 6)` (erc_decimals = 6).
2. User calls `send()` with `amount = 1_000_000_000_000_000_000` (1 token, 18 decimals) — the pallet burns/escrows exactly 1 token locally.
3. `convert_to_erc20(1e18, 6, 18)` computes `erc_decimals.saturating_sub(local_decimals) = 6.saturating_sub(18) = 0`, so `erc20_amount = 1e18 * 10^0 = 1e18`.
4. The destination `Message.amount = 1e18` is delivered to the destination ERC20 contract, which mints/releases `1e18` raw units of a 6-decimal token — i.e., `1,000,000,000,000` tokens instead of `1`, a 10^12x inflation, for the cost of escrowing a single token on the source chain.
