Based on the evidence gathered, the strongest local analog to the CCTP `mintRecipient` blacklist deadlock is the IntentGateway escrow-release path, where the beneficiary address is baked immutably into a cross-chain settlement message with no mechanism to redirect it if that address becomes unable to receive the escrowed token.

### Title
Immutable beneficiary binding in Intent Gateway cross-chain escrow settlement permanently locks funds if the token transfer to that beneficiary cannot succeed - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`RedeemEscrow`/`RefundEscrow` cross-chain messages hard-code a `beneficiary` (the filler on redeem, or `order.user` on refund) at the time the message is constructed on the destination/source chain, and `_withdraw()` performs a direct `safeTransfer` to that fixed address with no fallback, no update path, and no alternate claim mechanism.

### Finding Description
`_cancelFromDest` and the fill-settlement path construct a `WithdrawalRequest` whose `beneficiary` field is fixed and dispatched as part of the cross-chain POST body: [1](#0-0) 

When the message lands on the settlement chain, `onAccept` authenticates the source module and unconditionally calls `_withdraw`, which transfers escrowed tokens directly to `beneficiary` via `safeTransfer`: [2](#0-1) 

This mirrors the CCTP `mintRecipient` problem exactly: once the order is placed, `order.user` (and by extension every downstream refund/redeem beneficiary derived from it) is permanently fixed inside the hashed `Order` commitment used for authentication. There is no `replaceMessage`-style function, no governance recovery action, and no alternate withdrawal path if the token transfer to that address reverts (e.g., an ERC20 with an issuer-controlled blacklist, a paused/frozen account, or any token whose `transfer` can revert for a specific address). Because `_withdraw` performs the state update (`_filled[commitment] = beneficiary`) and the token transfer in the same atomic call, a reverting transfer reverts the whole `onAccept`, meaning the cross-chain message can never be successfully processed — the escrow is stuck in the gateway forever with no code path to redirect it to a different, receivable address.

### Impact Explanation
If `order.user` (source-chain refund beneficiary) or the solver/filler (destination-chain redeem beneficiary) becomes unable to receive the specific escrowed token — through issuer blacklisting, a `Pausable`/`Freezable` token implementation, or any transfer-reverting condition — the escrowed principal is permanently locked in the `IntentGatewayV2`/`IntentsBase` contract. Neither the user nor governance has any mechanism to redirect the beneficiary or recover the funds, since the beneficiary is embedded in the signed/hashed order and in the dispatched `WithdrawalRequest` body. This is a direct, unrecoverable loss of user funds analogous to the CCTP `mintRecipient` scenario.

### Likelihood Explanation
This requires no malicious relayer, prover, or admin — it is purely a function of the immutable design: any user whose chosen input/output token later restricts their address (a routine occurrence for USDC/USDT-class assets, which are explicitly supported as `TokenInfo`/escrow assets) will hit this permanently once an order is in flight, with no way for anyone (not even the user) to change the destination address after `placeOrder`/`fillOrder` has committed the order hash.

### Recommendation
Add a governance- or user-gated path to update the `beneficiary` of an unsettled `WithdrawalRequest` (analogous to CCTP's `replaceMessage`), or separate the escrow finalization (`_filled` marking) from the token transfer so that a failed transfer leaves funds claimable by a re-specified address instead of reverting the entire settlement and leaving the order un-processable indefinitely.

### Proof of Concept
1. Alice places a cross-chain order with `order.user = Alice` and USDC as the input token, escrowing 10,000 USDC on the source chain (`IntentGatewayV2.placeOrder`).
2. While the order is unfilled, Alice's address becomes blacklisted by Circle for an unrelated reason (dusted with tainted funds, as in the original report).
3. Alice (or a relayer after the deadline) calls `cancelOrder` from the destination chain; `_cancelFromDest` dispatches a `RefundEscrow` `WithdrawalRequest{beneficiary: order.user}` back to the source chain.
4. On the source chain, `onAccept` → `_withdraw` attempts `IERC20(usdc).safeTransfer(Alice, 10000e6)`, which reverts because Alice is blacklisted.
5. The entire `onAccept` transaction reverts; the message can never be successfully processed since `beneficiary` cannot be changed, and the escrowed 10,000 USDC remains permanently locked in the `IntentGatewayV2` contract. [3](#0-2) [4](#0-3)
