### Title
Unvalidated participant index in PedPoP blame decryption causes panic (DoS) via HashMap indexing - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary

The PedPoP blame-resolution path (`Decryption::decrypt_with_proof`, reached via `BlameMachine::blame` / `AdditionalBlameMachine::blame`) indexes the registered encryption-key map with an attacker-chosen participant index (`self.enc_keys[&decryptor]`) instead of returning an error. An unprivileged accuser can supply a `decryptor`/`accused` index for which no encryption key was ever registered, causing a panic — the direct analog of the reported invalid-dereference crash in FAAD2's `sbrDecodeSingleFramePS`.

### Finding Description

`Decryption` stores per-participant ECDH public keys in `enc_keys: HashMap<Participant, C::G>`, populated by `register` (crypto/dkg/pedpop/src/encryption.rs:351-362). In `decrypt_with_proof`, once the accuser-supplied `EncryptedMessage`'s Schnorr PoP verifies, the code constructs the DLEq verification inputs by directly indexing the map: [1](#0-0) 

`self.enc_keys[&decryptor]` uses `HashMap`'s `Index` impl, which panics on a missing key. `decryptor` (the `recipient` parameter of `blame`/`blame_internal`, crypto/dkg/pedpop/src/lib.rs:575-609) is attacker-controlled: it is the `accused` field of the blame accusation. Neither `blame` nor `decrypt_with_proof` checks that `decryptor` was ever registered via `register`/`Encryption::encrypt`, and `register` itself asserts non-duplication rather than completeness — a participant that never submitted its `EncryptionKeyMessage` simply has no entry.

A second, related panic exists in `Encryption::encrypt` (`self.decryption.enc_keys[&participant]`, crypto/dkg/pedpop/src/encryption.rs:466) and in `blame_internal`'s `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:599), where `sender` is likewise attacker-supplied and unvalidated against the commitments map — though reaching the latter requires a fully valid decryption proof.

All inputs needed to trigger the panic are public/attacker-controlled bytes: `sender`, `recipient`, the `EncryptedMessage` (readable via `EncryptedMessage::read`, crypto/dkg/pedpop/src/encryption.rs:171-177), and an optional `EncryptionKeyProof` (readable via `EncryptionKeyProof::read`, crypto/dkg/pedpop/src/encryption.rs:267-269) whose contents need not even verify, since the map indexing occurs while *constructing* the DLEq verify arguments, before the proof is evaluated.

### Impact Explanation

A single crafted blame accusation crashes the node executing the blame-resolution state machine. Since blame adjudication determines slashing and is triggered precisely when the DKG is under attack, this is a reliable denial of service against every honest validator processing the accusation — matching the CVE class (invalid input → crash → DoS, CVSS 5.5 Medium).

### Likelihood Explanation

The accuser controls `accused`/`recipient` and only needs to produce a `EncryptedMessage` with a self-consistent Schnorr PoP (trivial — they generate the ephemeral key themselves) plus any parseable `EncryptionKeyProof`. Any participant index absent from the registered `enc_keys` map — e.g., a valid `Participant` that never delivered its commitment message, or in paths that don't bound-check the index — triggers the panic. No threshold cooperation or key knowledge is required.

### Recommendation

Replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`, and similarly validate `sender`/`recipient` membership in `blame`/`blame_internal` (`self.commitments.get(&sender)`, `enc_keys.get(&participant)` in `Encryption::encrypt`) returning `PedPoPError`/`DecryptionError` instead of panicking on untrusted participant indexes.
