## Analysis

The AlephZeroAMM report's underlying pattern is: **one code path enforces a security invariant on a shared resource, while a sibling code path that manipulates the same class of resource omits the check**, letting an attacker-influenced value reach a sensitive operation unguarded. The Desktop analog of this pattern is path-containment enforcement (`resolveWithin`) around repository-relative file paths that originate from git-tracked content.

The codebase has a dedicated helper, `resolveWithin`, built specifically to stop symlink-based directory traversal [1](#0-0) , and it is wired into some newer file-touching flows such as `openRepositoryFromUrl` [2](#0-1)  and the Copilot conflict-resolution writer [3](#0-2) . There is even a regression test proving the project is aware that a tracked symlink can be used to escape the repository root [4](#0-3) .

However, the much older and far more commonly used **Discard Changes** flow does not use this guard at all — it resolves the working-directory path with plain `Path.resolve` and hands the result straight to the OS trash API: [5](#0-4) 

### Title
Discard Changes trashes files outside the repository via a tracked symlink (missing `resolveWithin` containment check) - (File: app/src/lib/stores/git-store.ts)

### Summary
`GitStore.discardChanges` builds the path to hand to `shell.moveItemToTrash` with `Path.resolve(this.repository.path, file.path)`, where `file.path` comes from `git status` output for the working directory [6](#0-5) . Unlike `openRepositoryFromUrl` and the Copilot conflict resolver, this path is never passed through `resolveWithin`, which is the only helper in the codebase that dereferences symlinks and verifies the result stays under the repository root.

### Finding Description
A cloned/fetched repository can contain a tracked symlink (git versions symlinks as blobs and materializes them as real filesystem symlinks on checkout) whose target points outside the working directory, e.g. `link -> ../../.ssh`. Once such a repo is checked out and a file inside that symlinked location is created/modified (by a build step, a hook, or any tool running in the working tree), `git status` reports a working-directory change such as `link/authorized_keys`. This string becomes `file.path` on a `WorkingDirectoryFileChange`.

When the user selects "Discard Changes" for that entry, `discardChanges` computes:
```
Path.resolve(this.repository.path, 'link/authorized_keys')
```
`Path.resolve` performs purely lexical resolution — it does not dereference the `link` symlink — so the resulting path is lexically `<repo>/link/authorized_keys`. That string is passed unchecked to `shell.moveItemToTrash` [7](#0-6) , which ultimately invokes the OS-level trash/move operation. The OS *does* resolve the symlink component when performing the actual filesystem operation, so the real target outside the repository (e.g. `~/.ssh/authorized_keys`) is the file that actually gets moved/deleted.

This is the exact traversal primitive that `resolveWithin` was written to close, as proven by the project's own test `fails for paths that use a symlink to traverse outside of the root` [4](#0-3) ; the guard simply isn't applied on this call site.

### Impact Explanation
A malicious/compromised repository can cause GitHub Desktop, in response to the ordinary "Discard Changes" action, to delete or move an arbitrary file outside the repository that the OS user has access to (SSH keys, other project files, credential files, etc.), via `Path.resolve`/`moveItemToTrash` on an unvalidated repo-relative path. This fits the "file write/read outside the repo" impact category from an attacker-controlled cloned repository.

### Likelihood Explanation
Requires the victim to clone/open a malicious repository and click "Discard Changes" on a file whose path traverses a tracked symlink — no unusual or "unnatural" steps beyond the repository containing a crafted symlink and the victim performing routine discard actions on working-directory changes, which is one of the most common Desktop operations.

### Recommendation
Route `file.path` (and `file.status.oldPath` for renames/copies) through `resolveWithin(this.repository.path, file.path)` before calling `shell.moveItemToTrash` / `rm` in `GitStore.discardChanges`, mirroring the containment check already used in `dispatcher.ts`'s `openRepositoryFromUrl` and `copilot-conflict-context.ts`; skip/report the file if it resolves outside the repository root.

### Proof of Concept
1. Create a repository containing a tracked symlink `evil -> ../../../..` (or any path escaping the eventual clone location) and commit it.
2. Have the victim clone this repository with Desktop.
3. Arrange for a file to appear as a working-directory change under `evil/...` (e.g., via a build script executed in the repo, or another commit that later modifies a file whose git-reported path traverses `evil/`).
4. In Desktop's Changes list, select that file and choose "Discard Changes."
5. `discardChanges` resolves the path lexically to `<repo>/evil/...`, and the OS-level trash call follows the symlink, deleting/moving the real target file outside the repository — confirmed unguarded by the code at `app/src/lib/stores/git-store.ts:1561-1563`, in contrast to the guarded call at `app/src/ui/dispatcher/dispatcher.ts:1963`.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
