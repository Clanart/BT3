## Title
Sending value to the `rewards()` view method of the distribution precompile permanently strands SEI/wei funds - ([File: precompiles/distribution/distribution.go])

## Summary
The distribution precompile at address `0x0000000000000000000000000000000000001007` exposes a `rewards(address)` query method that, unlike every other method on the same precompile, is dispatched without a `pcommon.ValidateNonPayable(value)` guard. A caller can invoke `rewards()` while attaching `msg.value`, and that value is never forwarded, refunded, or otherwise accounted for by the executor, permanently stranding the sent funds — directly analogous to the reported "unclaimed reward funds stuck forever" bug class (fund loss with no recovery path).

## Finding Description
In `precompiles/distribution/distribution.go`, the `Execute` dispatcher explicitly calls `pcommon.ValidateNonPayable(value)` before running state-mutating or even other query methods (e.g. `WithdrawValidatorCommissionMethod`), but the `RewardsMethod` case skips this check entirely: [1](#0-0) 

The `rewards()` handler itself only reads `DelegationTotalRewards` from the distribution keeper and packs the response; it never inspects, forwards, or reverts on the `value` parameter that was passed into `Execute`: [2](#0-1) 

This same missing check exists identically across every legacy snapshot of the precompile (`v65`, `v66`, `v67`, `v580`, `v605`, `v606`, `v610`, `v614`, `v620`, `v630`, `v640`), confirming it is a long-standing, reproducible pattern rather than a one-off typo: [3](#0-2) 

A test comment in the integration suite explicitly documents this as a known quirk, stating that `rewards()` is "the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)," and that the test suite deliberately skips the "view rejects value" assertion for this method: [4](#0-3) 

Under the standard EVM `CALL` semantics that sei-chain's EVM module implements, value attached to a call is credited to the callee's balance before the callee code (or precompile) executes. For a precompile address, that balance is tracked via the `StateDB` bridge, which maps EVM balance changes to `usei`/`wei` bank credits on the associated Sei address of the precompile address itself: [5](#0-4) 

Because the precompile's own executor code never moves or refunds that credited value (there is no corresponding `SubBalance`/transfer-out call in `rewards()`), the funds become permanently associated with the distribution precompile's address — an address with no private key and no user-facing withdrawal path, since the precompile only exposes the fixed method set in its ABI (none of which sweeps stray balance back to a caller).

## Impact Explanation
Any unprivileged EVM caller (a contract or externally-owned account) who mistakenly or intentionally sends `msg.value` while calling `rewards(address)` on the distribution precompile permanently loses that value — it becomes unreachable/unrecoverable by any subsequent transaction, since there is no emergency-withdraw or sweep function exposed by the precompile for balance that lands on its own address. This matches the "permanent freezing of funds" impact class validated by the audit rules (concrete, permanent loss reachable from a single transaction against a public precompile).

## Likelihood Explanation
Likelihood is low-to-moderate: exploitation requires a user or an integrating contract to intentionally or accidentally attach `value` to a `rewards()` call, which is unusual for a read-only "view" function, but nothing in the ABI or precompile framework prevents it (unlike all sibling methods, which explicitly reject non-zero value). Any wallet/dApp/contract that blindly forwards `msg.value` on generic precompile calls, or a user who fat-fingers a value field while querying rewards through a generic contract interaction UI, would trigger the loss.

## Recommendation
Add the same `pcommon.ValidateNonPayable(value)` check used by every other case in `Execute` to the `RewardsMethod` branch (in `precompiles/distribution/distribution.go` and all legacy versions still reachable in state-transition replay), so that a value-bearing call to `rewards()` reverts instead of silently stranding funds. As a defense-in-depth measure, consider adding a generic check at the `Precompile.Run`/`RunAndCalculateGas` layer in `precompiles/common/precompiles.go` that rejects unexpected value for any method not explicitly marked payable, so future new precompile methods cannot reintroduce this class of bug.

## Proof of Concept
1. From any EVM account, call the distribution precompile at `0x0000000000000000000000000000000000001007` with:
   - `data` = ABI-encoded `rewards(address)` selector + a delegator address argument
   - `value` = some non-zero amount of SEI (e.g. 1 SEI)
2. Observe that the call succeeds and returns the queried rewards data (per `precompiles/distribution/distribution.go:543-578`, no error is raised for the attached value).
3. Query the balance of the precompile's associated Sei address afterward — the attached value has been credited there via the `AddBalance` StateDB path (`x/evm/state/balance.go:64-95`) with no corresponding withdrawal mechanism in the precompile's method set, making it permanently unrecoverable.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
