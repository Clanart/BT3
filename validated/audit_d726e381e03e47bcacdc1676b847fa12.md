### Title
Re-callable `updateEndRemainingAllocation()` allows attacker to manipulate the bonus-share denominator and steal a disproportionate share of `totalBonus` from other allocatees - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is `public`, has no "already-set" guard, and simply overwrites `totalEndRemainingAllocation = totalRemainingAllocation` any time `block.timestamp >= periodsEndTime[4]`. Because `totalRemainingAllocation` shrinks with every `claim()` while `totalBonus` is **never decremented** when bonus is paid, an attacker can call `updateEndRemainingAllocation()` (directly, or implicitly via their own `claim()`) at a strategically chosen moment — after other users have already claimed but before their own claim — to shrink the denominator used in `getBonusAmount()` and capture a disproportionately large (potentially near-total) share of the fixed `totalBonus` pool.

### Finding Description
Relevant code, `rewards/Airdrop.sol`: [1](#0-0) [2](#0-1) 

Root cause:
- `totalBonus` accumulates forfeitures from early claimers but is **never reduced** when bonus is actually paid out in `claim()` (there is no `totalBonus -= bonusAmount`).
- `getBonusAmount(user) = userAllocation * totalBonus / totalEndRemainingAllocation`. This formula only conserves funds correctly if `totalEndRemainingAllocation` is a *single, immutable snapshot* taken once, right when period 4 starts, equal to the sum of allocations of all users who haven't claimed yet at that exact instant.
- `claim()` only auto-triggers `updateEndRemainingAllocation()` the first time (`if (totalEndRemainingAllocation == 0)`), which would normally freeze this snapshot. However, `updateEndRemainingAllocation()` itself is `public` and unconditionally overwrites `totalEndRemainingAllocation` again whenever called and the time condition holds — there is no check preventing re-snapshotting.
- Since `totalRemainingAllocation` is decremented on every `claim()` (regardless of period), any address can call `updateEndRemainingAllocation()` again *after* some users have already claimed, shrinking `totalEndRemainingAllocation` to reflect only the allocation of users who haven't claimed yet (which may be just the attacker).
- The attacker's own `getBonusAmount()` uses whatever `totalEndRemainingAllocation` value is current at the moment of their `claim()`. By waiting (or ordering their transaction) until after other legitimate claimers have already been paid under a larger denominator, and then forcing/letting a re-snapshot with a much smaller denominator right before their own `claim()`, the attacker inflates `userAllocation / totalEndRemainingAllocation` toward 1, receiving up to nearly the entire (still non-decremented) `totalBonus` pool for themselves — on top of what earlier legitimate claimers already received from the same pool.
- Net effect: the sum of bonus tokens paid across all users exceeds the intended `totalBonus`, directly diverting tokens away from what should accrue proportionally to other allocatees, and can push the contract toward the `InsufficientBalance` check, causing later legitimate claimers to be unable to claim (temporary/permanent freezing of their entitled tokens) or the airdrop balance to be drained beyond the fair-share design.

This is fully reachable by an unprivileged attacker: they only need a registered allocation (a normal user status) and the ability to submit `claim()`/`updateEndRemainingAllocation()` transactions with chosen gas price/timing — no admin or special role is required. No existing modifier (`onlyOwner`, `nonReentrant`, etc.) guards `updateEndRemainingAllocation()`, and `claim()`'s zero-check does not stop external, out-of-band re-triggering of the snapshot.

### Impact Explanation
Direct theft of bonus tokens that should accrue proportionally to other allocatees, and potential protocol insolvency for the `aidropToken` balance backing the airdrop, causing legitimate later claimers to be unable to claim their earned (base + bonus) allocation. This matches Immunefi's "Direct theft of user funds" / "Protocol insolvency" impact classes.

### Likelihood Explanation
Highly feasible: the attack requires no capital beyond having a registered allocation (which any airdrop recipient already has), no privileged role, and only ordinary transaction timing/gas-price control to sequence `updateEndRemainingAllocation()`/`claim()` relative to other users' pending claims around `periodsEndTime[4]`. It is repeatable by any registered allocatee and does not depend on governance, oracle, or upgrade paths.

### Recommendation
- Decrement `totalBonus` by the paid `bonusAmount` inside `claim()` when it is distributed, so the pool cannot be paid out more than once.
- Make the snapshot in `updateEndRemainingAllocation()` idempotent/one-time (e.g., guard with `if (totalEndRemainingAllocation != 0) return;` or restrict it to internal use only, called exactly once at the first post-period-4 interaction), so the denominator used for all `getBonusAmount()` calculations is a single fixed value equal to the sum of allocations outstanding at `periodsEndTime[4]`.

### Proof of Concept
Foundry test plan:
1. Deploy `Airdrop` with `startTime = block.timestamp + 1`, register allocations for `userA`, `userB`, `attacker` (e.g., equal amounts), fund the contract with `aidropToken`.
2. Warp to `periodsEndTime[0..3]` and have `userA` and `userB` claim partially at an earlier period to build up `totalBonus` via forfeiture (`claim()` before period 4 forfeits remaining allocation into `totalBonus`).
3. Warp to `periodsEndTime[4]`.
4. **Ordering A (no manipulation):** `attacker` calls `claim()` first (triggers `updateEndRemainingAllocation()` once, snapshotting `totalEndRemainingAllocation` to include all still-unclaimed allocations including `userC`'s); record `attacker`'s `bonusAmount`.
5. **Ordering B (manipulated):** Reset state; have all other remaining allocatees (`userC`, etc.) `claim()` first (their claims use the pre-existing snapshot or trigger the first snapshot); then `attacker` calls `updateEndRemainingAllocation()` directly again, re-snapshotting `totalEndRemainingAllocation` to a much smaller value (only attacker's own remaining allocation); then `attacker.claim()`.
6. Assert `attacker`'s payout in Ordering B is significantly larger than in Ordering A, and that `sum(bonusAmount paid to all claimers)` in Ordering B exceeds the original `totalBonus` recorded before any claims — demonstrating conservation is broken and the attacker can choose the more profitable ordering.

        public
        view
        returns (uint256 bonusAmount)
    {
        bonusAmount = 0;
        uint256 userAllocation = allocations[_user];
        if (
            block.timestamp >= periodsEndTime[4] &&
            totalEndRemainingAllocation != 0
        ) {
            bonusAmount =
                ((userAllocation * 10**9) * totalBonus) /
                totalEndRemainingAllocation /
                10**9;
        }
    }

    /// @notice This will store the ending remaining amount for the bonus.
    function updateEndRemainingAllocation() public {
        if (block.timestamp >= periodsEndTime[4]) {
            totalEndRemainingAllocation = totalRemainingAllocation;
        }
    }

    /// @notice Claim MGP and forfeit remaining allocation
    function claim() external {
        if (totalEndRemainingAllocation == 0) {
            updateEndRemainingAllocation();
        }
        uint256 claimableAmount = getClaimableAmount(msg.sender);
        
        if(claimableAmount == 0) revert NothingToClaim();
        if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();

        uint256 userAllocation = allocations[msg.sender];
        allocations[msg.sender] = 0;
        totalRemainingAllocation -= userAllocation;
        if (claimableAmount <= userAllocation) {
            uint256 forfeited = userAllocation - claimableAmount;
            totalBonus += forfeited;
        }
        aidropToken.safeTransfer(msg.sender, claimableAmount);
    }
