### Title
`GetBalance()` panics when a vesting account's locked balance exceeds its raw bank balance, crashing EVM state reads - (File: `x/evm/keeper/balance.go`)

### Summary
The Sei EVM StateDB balance lookup computes an account's spendable usei by unconditionally subtracting `LockedCoins` from the raw bank balance, exactly like the reported `MainVault.deposit()` bug subtracts `reservedFunds` from `getVaultBalance()` without guarding against the reserved amount exceeding the balance. When a vesting account delegates its unvested (locked) tokens — an ordinary, permissionless `MsgDelegate` — its on-chain bank balance drops below the amount still reported as "locked" by the vesting schedule, producing a negative intermediate value that later triggers a hard `panic("balance overflow")` in the EVM balance path.

### Finding Description
`x/evm/keeper.Keeper.GetBalance` computes: [1](#0-0) 

```go
allUsei := k.BankKeeper().GetBalance(ctx, addr, denom).Amount
lockedUsei := k.BankKeeper().LockedCoins(ctx, addr).AmountOf(denom)
usei := allUsei.Sub(lockedUsei)
```

`LockedCoins` for a vesting account is derived purely from the vesting schedule and current block time, independent of the account's current spendable balance: [2](#0-1) 

The Cosmos SDK by design allows vesting accounts to delegate their locked (unvested) tokens to validators via an ordinary `MsgDelegate` — this moves the tokens out of the account's bank balance into the bonded pool while the vesting schedule (and thus `LockedCoins()`) is unaffected until it matures. As a result, `allUsei` (raw balance) can legitimately fall below `lockedUsei` (locked amount) for a normal, single-transaction user action, with no validator misbehavior or slashing required.

The generic `spendableCoins` helper elsewhere in the bank keeper is written defensively to handle exactly this case with `SafeSub`, returning an empty `Coins` set instead of a negative value: [3](#0-2) 

But `x/evm/keeper.GetBalance` uses a plain, unchecked `Sub`, so the negative case is not handled there. The negative `*big.Int` returned then flows into the EVM StateDB's `GetBalance`, which converts it with `uint256.FromBig` and panics on overflow: [4](#0-3) 

A negative `big.Int` cannot be represented as an unsigned `uint256`, so `uint256.FromBig` reports overflow, and the code unconditionally panics.

The same unguarded subtraction pattern is duplicated in the `giga` EVM path: [5](#0-4) 
while that codepath at least contains explicit negative-balance error handling downstream (`errStateBalanceUnderflow`) in `giga/evmonly/state_db.go`, showing the underflow case is a recognized-but-unfixed possibility for the base `x/evm` path.

This `GetBalance` is the same function used to serve the public `eth_getBalance` JSON-RPC method and to source EVM StateDB balances for every EVM transaction touching the affected address (senders, recipients, and precompile callers), meaning any public RPC client or EVM transaction interacting with an affected vesting-derived EVM address can trigger the panic.

### Impact Explanation
A panic in `DBImpl.GetBalance` is hit any time the EVM state layer needs the balance of an address whose underlying Sei account is a vesting account that has delegated its locked stake. This includes:
- Any EVM transaction where that address is the `msg.sender` or a transfer recipient (ante-handler/StateDB balance checks).
- The public `eth_getBalance` RPC call for that address, reachable from any unauthenticated client.

Depending on where the panic surfaces, this either fails all EVM transactions/queries touching the affected address (denial of service against a specific account, effectively "freezing" its ability to transact/be queried through the EVM) or, if hit outside a `recover()`-wrapped code path (e.g. inside RPC handling), can crash the RPC server goroutine of a default-configuration node.

### Likelihood Explanation
The precondition is fully reachable by an unprivileged user: create/hold a vesting account (a standard, common account type), associate it to an EVM address, and delegate the locked/unvested tokens via a normal `MsgDelegate`. No validator misbehavior, slashing, or governance action is required. Once locked balance exceeds raw balance, every subsequent EVM balance lookup for that address panics.

### Recommendation
Use a safe subtraction in `x/evm/keeper.GetBalance` (mirroring `spendableCoins`'s `SafeSub` pattern), clamping to zero when `lockedUsei > allUsei` instead of allowing a negative value to propagate into `uint256.FromBig`:
```go
usei, hasNeg := allUsei.SafeSub(lockedUsei)
if hasNeg {
    usei = sdk.ZeroInt()
}
```
Apply the same fix to `giga/deps/xevm/keeper/balance.go`.

### Proof of Concept
1. Create a vesting account and associate it with an EVM address.
2. Submit `MsgDelegate` from that account to delegate all (or most) of its balance, including the still-locked/unvested portion, to a validator — this is a standard vesting-account capability.
3. Now `BankKeeper().GetBalance(ctx, addr, denom)` (raw balance) is near zero while `BankKeeper().LockedCoins(ctx, addr)` still reflects the full unvested schedule amount.
4. Call `eth_getBalance` for the associated EVM address, or send/receive any EVM transaction touching it.
5. `x/evm/keeper.GetBalance` computes `allUsei.Sub(lockedUsei)` → negative `sdk.Int` → negative `big.Int`.
6. `x/evm/state.DBImpl.GetBalance` calls `uint256.FromBig` on the negative value, `overflow == true`, and `panic("balance overflow")` fires.

// LockedCoins returns all the coins that are not spendable (i.e. locked) for an
// account by address. For standard accounts, the result will always be no coins.
// For vesting accounts, LockedCoins is delegated to the concrete vesting account
// type.
func (k BaseViewKeeper) LockedCoins(ctx sdk.Context, addr sdk.AccAddress) sdk.Coins {
	acc := k.ak.GetAccount(ctx, addr)
	if acc != nil {
		vacc, ok := acc.(vestexported.VestingAccount)
		if ok {
			return vacc.LockedCoins(ctx.BlockTime())
		}
	}

	return sdk.NewCoins()
}

func (k BaseViewKeeper) spendableCoins(ctx sdk.Context, addr sdk.AccAddress) (spendable, total sdk.Coins) {
	total = k.GetAllBalances(ctx, addr)
	locked := k.LockedCoins(ctx, addr)

	spendable, hasNeg := total.SafeSub(locked)
	if hasNeg {
		spendable = sdk.NewCoins()
		return
	}

	return
}

func (s *DBImpl) GetBalance(evmAddr common.Address) *uint256.Int {
	s.k.PrepareReplayedAddr(s.ctx, evmAddr)
	// Hook for mock balances (no-op in production builds)
	s.ensureMinimumBalance(evmAddr)
	seiAddr := s.getSeiAddress(evmAddr)
	res, overflow := uint256.FromBig(s.k.GetBalance(s.ctx, seiAddr))
	if overflow {
		panic("balance overflow")
	}
	if res == nil {
		return uint256.NewInt(0)
	}
	return res
}
