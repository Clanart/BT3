## Analysis

The report's bug class — profit/reward distribution being computed against an instantaneous share balance that can be inflated by a front-running deposit — has a direct, reachable analog in the Wombat integration's reward pipeline.

### Title
Reward distribution in `BaseRewardPool`/`WombatStaking` can be front-run via permissionless `harvest()`/`deposit()` calls to steal pending WOM yield from existing stakers - (File: `wombat/WombatStaking.sol`, `rewards/BaseRewardPool.sol`)

### Summary
`WombatStaking::harvest` is a fully permissionless external function [1](#0-0) . Calling it (or performing any deposit/withdraw, which internally calls the same path) invokes `_toMasterWomAndSendReward`, which harvests pending WOM from MasterWombat and pushes it into the pool's `BaseRewardPool` via `queueNewRewards` [2](#0-1) . `BaseRewardPool::_provisionReward` then updates `rewardPerTokenStored` using the *current* `totalStaked()` at that exact moment [3](#0-2) . Because deposits into the pool via `WombatPoolHelper::deposit`/`depositLP`/`depositNative` are unrestricted and immediately increase the staker's `MasterMagpie` balance (and thus `totalStaked()`) [4](#0-3) , an attacker can watch WOM emissions accrue (visible via the public `pendingWom()` view) [5](#0-4) , deposit a large stake immediately before calling/triggering `harvest()`, and capture a disproportionate share of rewards that accrued while they were not actually staked — exactly the same “buy shares right before profit distribution” pattern described in the external report.

### Finding Description
`BaseRewardPool` distributes rewards using the classic `rewardPerTokenStored += amount * 1e_decimals / totalStaked()` accounting model [6](#0-5) . This model assumes reward injections cannot be timed by an outside party relative to stake changes. However:

1. `WombatStaking::harvest(_lpToken)` has no caller restriction beyond the target pool being active [1](#0-0) , so any wallet can trigger the WOM harvest and reward queueing at a time of their choosing.
2. `WombatPoolHelper::deposit`, `depositLP`, and `depositNative` are unauthenticated and immediately mint/stake the staking token into `MasterMagpie` on behalf of `msg.sender` [7](#0-6) , which is what `BaseRewardPool::totalStaked()` reads from (`IMasterMagpie(operator).stakingInfo`) [8](#0-7) .
3. Because `_provisionReward` snapshots `totalStaked()` synchronously when `queueNewRewards` executes, a wallet that inflates its stake in the block/transaction immediately preceding a harvest captures a share of rewards proportional to its newly added balance, even though that balance was not staked during the period in which the WOM emissions accrued.

This is the same class of vulnerability as the "sendProfit front-run" report: profit/reward accounting has no vesting or time-weighting mechanism, so entry timing relative to a public, permissionless reward-triggering call determines reward capture rather than actual staking duration.

### Impact Explanation
Existing long-term LPs/stakers in a Wombat pool routed through `WombatStaking`/`WombatPoolHelper` see their proportional share of harvested WOM (and any bonus reward tokens) diluted whenever an attacker times a large deposit immediately before a `harvest()` call (self-triggered or naturally occurring via another user's deposit/withdraw). This constitutes theft of unclaimed yield from existing stakers, transferring it to an opportunistic depositor who held no meaningful economic exposure to the pool during the emission period.

### Likelihood Explanation
`harvest()` requires no privilege and no cost beyond gas, and `pendingWom()` is a public view enabling attackers to detect a profitable amount of accrued, unharvested WOM rewards. Any wallet with capital sufficient to acquire a large share of the pool's LP token (which can be flash-loaned or briefly held) can execute this every time meaningful pending rewards accumulate, making this practically exploitable and repeatable, similar to the acknowledged risk in the original report.

### Recommendation
Introduce a stake-duration or time-weighted mechanism before newly staked balances become eligible for freshly queued rewards — e.g., a checkpoint/vesting delay analogous to the recommended "membership delay" in the original report, or snapshot `totalStaked()`/eligible balances prior to the block in which `queueNewRewards` is invoked rather than using the instantaneous balance.

### Proof of Concept
1. Attacker calls `WombatPoolHelper.pendingWom()` and observes a large amount of unharvested WOM pending for a pool.
2. Attacker calls `WombatPoolHelper.deposit(largeAmount, minLiquidity)`, which stakes a large receipt-token balance into `MasterMagpie` via `WombatStaking.deposit` → `_stake` [9](#0-8) .
3. Attacker (or anyone) calls `WombatStaking.harvest(lpToken)`, which calls `_toMasterWomAndSendReward` → `queueNewRewards` on `BaseRewardPool`, computing `rewardPerTokenStored` using `totalStaked()` that now includes the attacker's freshly added, disproportionately large balance [2](#0-1) .
4. Attacker calls `WombatPoolHelper.withdraw` to unwind their position shortly after, having captured a share of WOM rewards proportional to their brief large stake rather than their actual time-weighted contribution, at the expense of long-term stakers.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
