### Title
Fork PR `clone_url` from GitHub API is trusted unvalidated as a git remote target in `_findPullRequestBranch` - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The reported bug's broken invariant is: *a value that should be derived/verified internally (`debtOut`) is instead accepted verbatim from an attacker-influenced input (`sendParam.amountLD`) and used to drive a privileged, irreversible action (cross-chain minting).* The same shape of bug exists in GitHub Desktop's "checkout PR from fork" flow: the `headCloneUrl` value, which comes straight from a GitHub API pull-request payload that the **PR author (an attacker) fully controls** (their fork's `clone_url`), is passed unvalidated into `addRemote()` → `git remote add <name> <url>`, and is then fetched.

### Finding Description
`_findPullRequestBranch` in [1](#0-0)  takes `headCloneUrl` (originating from `pullRequest.head.repo.clone_url`, an attacker-supplied fork URL surfaced through the GitHub API/PR object, see `openPullRequestFromUrl` at [2](#0-1) ) and, if no existing remote matches it, calls: [3](#0-2) 

This flows straight into `addRemote`, which shells out to git with the raw URL as a positional argument and no `--` separator or scheme allow-list check: [4](#0-3) 

Nowhere in this path is `headCloneUrl` validated against `parseRemote()`'s known URL shapes (`https://`, `git@host:`, `ssh://`, etc. — defined in [5](#0-4) ) before being handed to `git remote add` and subsequently fetched via `this._fetchRemote(repository, remote, ...)` at [6](#0-5) . Compare this to the clone path, which *does* have a dedicated defensive check (`isClonePathSensitive`) guarding against traversal from attacker-controlled URLs: [7](#0-6)  — no equivalent allow-list/validation exists for the remote-URL value used in the PR-checkout path.

This mirrors the report's exact class: the app has an internal source of truth for a "safe" value (the parsed/normalized remote URL shape used everywhere else, e.g. `parseRemote`), but instead of enforcing that shape, it trusts the attacker-influenced raw string end-to-end for a privileged operation (spawning a git subprocess with that string as an argument).

### Impact Explanation
If `git remote add`/`git fetch` can be made to interpret the attacker-controlled `clone_url` string as something other than a plain remote URL (e.g., a leading `-`/`--` causing argument-injection into the git CLI, or a non-`https`/`ssh` transport scheme such as `ext::`), this could result in unintended local command execution or SSRF-like requests to attacker-chosen protocol handlers, entirely triggered by the victim clicking "Open in Desktop" / viewing a PR from a fork — no local access, credentials, or unusual steps beyond normal PR-review usage required. This is a case of "attacker controls a GitHub API object" leading to potentially unauthorized code execution, consistent with the valid-impact categories for this exercise.

### Likelihood Explanation
I could **not** confirm within the available tool budget whether `envForRemoteOperation()` (imported in both `clone.ts` and `remote.ts`) sets `GIT_PROTOCOL_FROM_USER=0` or an equivalent `GIT_ALLOW_PROTOCOL` allow-list before these git invocations — if it does, the practical exploitability of the "unsafe protocol" variant would be significantly reduced or eliminated, leaving mainly the argument-injection variant (URL string beginning with `-`) as the residual concern. I was unable to read `app/src/lib/git/environment.ts` before the session ended, so this analysis should be treated as a strong structural lead requiring that file's confirmation, not a fully proven exploit chain.

### Recommendation
- Validate `headCloneUrl` (and any other API-sourced clone URL) against `parseRemote()`'s known schemes before calling `addRemote`, rejecting anything that doesn't match an expected `https://`/`ssh://`/`git@host:` shape.
- Reject/escape URL values beginning with `-` before passing them as positional git CLI arguments, or insert a `--` separator in the `git remote add`/`git remote set-url` argument arrays (as is already good practice for `clone`'s `args.push('--', url, path)` in [8](#0-7) , but is missing from `remote.ts`'s `addRemote`/`setRemoteURL`).
- Confirm and, if missing, enforce `GIT_PROTOCOL_FROM_USER=0`/`GIT_ALLOW_PROTOCOL` restrictions uniformly across every git invocation that consumes an externally-sourced URL (clone, remote add, remote set-url, fetch).

### Proof of Concept
Not independently verified end-to-end due to the unresolved `environment.ts` question noted above. Conceptually: an attacker forks a public repo, sets their fork's remote/clone URL to a crafted value (e.g., starting with `-` or using a non-standard transport), and gets the victim to open a PR link from that fork via Desktop's "Open in Desktop"/PR-checkout flow (`openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` → `addRemote`). Full confirmation requires tracing `envForRemoteOperation()` and testing actual git CLI argument-parsing behavior for `git remote add <name> <maliciously-crafted-url>`.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
