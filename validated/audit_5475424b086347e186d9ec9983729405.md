Confirmed: this is a valid analog. The user's withdrawal signature uses `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0)  which, per BIP-341/342 semantics and the manual sighash computation, covers only the txin at index 0 and the output at the *same index* (`SIGHASH_SINGLE`) — the OP_RETURN output that attributes the payout to a specific operator sits at a different output index and is excluded from the digest [2](#0-1) . This means the user's signature does not bind the operator-attribution output at all.

### Title
Unsigned OP_RETURN in `payout_tx` lets anyone rewrite operator attribution before confirmation - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The `payout_tx` created by `create_payout_txhandler` embeds the fronting operator's xonly public key in an OP_RETURN output that is used later to attribute reimbursement credit to that operator [3](#0-2) . The only cryptographic signature present on this transaction is the user's `SinglePlusAnyoneCanPay` signature over input 0 [4](#0-3) , which under `SIGHASH_SINGLE|ANYONECANPAY` semantics commits only to the same-indexed output (the user payout output), not the OP_RETURN output carrying the operator attribution. Anyone observing the unconfirmed/unbroadcast `payout_tx` (e.g. in the mempool, or if it is shared for RBF fee-bumping) can therefore substitute a different `operator_xonly_pk` into the OP_RETURN output and rebroadcast a variant transaction that still validly spends the same user-signed input and pays the user the same amount, but attributes the reimbursement credit to an attacker-chosen operator instead of the party who actually fronted the withdrawal.

### Finding Description
`create_payout_txhandler` builds three outputs: the user payout output, an anchor output, and an OP_RETURN output containing `operator_xonly_pk.serialize()` [5](#0-4) . The transaction's only witness is `set_p2tr_key_spend_witness(&user_sig, 0)` on input 0, and this signature is required to have sighash type `SinglePlusAnyoneCanPay` [6](#0-5) .

Verifiers later parse this exact OP_RETURN to determine which operator is credited for the payout: `update_finalized_payouts` extracts `operator_xonly_pk` from the first OP_RETURN output of the on-chain payout tx and persists it via `update_payout_txs_and_payer_operator_xonly_pk` [7](#0-6) . This value is the sole binding between "who actually paid the withdrawal" and "who is authorized to claim reimbursement": `validate_payer_is_operator` requires `payer_xonly_pk == self.signer.xonly_public_key` before returning kickoff/reimbursement data [8](#0-7) , and `send_asserts` rejects mismatches between the recorded payer pubkey and the kickoff's operator pubkey [9](#0-8) .

Because `SIGHASH_SINGLE|ANYONECANPAY` only commits to the input and the co-indexed output (index 0, the user's payout), the OP_RETURN output (a later output index) is excluded from the signed digest, matching the manual sighash serialization logic that skips `sha_outputs` for `TapSighashType::Single`/`None` [2](#0-1) . Consequently the OP_RETURN payload is fully malleable by any party with access to the unconfirmed transaction (network-level mempool visibility, RBF resubmission via `fund_raw_transaction`/`send_raw_transaction` [10](#0-9) , or a competing bump) without invalidating the witness.

This is the same bug class as the Gondi `mergeTranches` finding: a permissionless mutation of an identifier/attribute (there, `loanId`; here, the operator-attribution OP_RETURN) that the downstream accounting logic treats as authoritative but which is not actually bound by any authorization check — breaking the equality "operator credited == party that paid."

### Impact Explanation
If exploited, an attacker who never fronted any BTC to the user can get the reimbursement pipeline to record them as the payer (`payout_payer_operator_xonly_pk`), then follow the normal kickoff/assert/reimburse flow to claim reimbursement from the pool of collateral/round outputs meant for the honest operator that actually paid. This is a misattributed reimbursement — Critical impact per the "operator reimbursed for a payout it never funded" class, and correspondingly the honest operator who did front the withdrawal would find the payout already marked as handled by a different (attacker) `operator_xonly_pk`, potentially leaving them permanently unable to be reimbursed.

### Likelihood Explanation
Requires only mempool visibility or knowledge of the pending payout transaction (e.g., relayed for RBF fee-bumping by the fee bumper/tx-sender), a passive/unprivileged network position, no operator, verifier, or key compromise. Given `SinglePlusAnyoneCanPay` is explicitly documented and enforced as the required sighash type [11](#0-10) , the malleability is a structural, always-present property of every payout transaction, not a misconfiguration.

### Recommendation
Bind the operator attribution cryptographically to the same signed data as the user payout, e.g., by using `SIGHASH_ALL|ANYONECANPAY` (or otherwise covering all outputs) for the user's payout signature, or by moving operator identity out of a mutable OP_RETURN into something covered by the operator's own signature/witness that verifiers additionally check on-chain before crediting reimbursement.

### Proof of Concept
1. Operator A fronts a withdrawal by calling `withdraw`, constructing `payout_tx` via `create_payout_txhandler(input_utxo, output_txout, A_xonly_pk, user_sig, network)` and broadcasting/funding it through `fund_raw_transaction`/RBF [12](#0-11) .
2. Before the transaction confirms, an attacker observes it in the mempool (or receives it via RBF propagation) and constructs a variant transaction reusing the same signed input 0 witness (valid under `SinglePlusAnyoneCanPay`, same user output at index 0) but swapping the OP_RETURN output to contain `attacker_xonly_pk` instead of `A_xonly_pk`.
3. The attacker's variant confirms first (via higher fee/RBF race). `update_finalized_payouts` parses the confirmed tx's OP_RETURN and records `attacker_xonly_pk` as `payout_payer_operator_xonly_pk` for that withdrawal index [13](#0-12) .
4. The attacker (impersonating an operator entity, or if actually running an operator node) now passes `validate_payer_is_operator` and `send_asserts`'s payer-match check, and can pursue the kickoff/reimburse flow to claim the reimbursement that should have gone to the operator who actually paid the user.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
