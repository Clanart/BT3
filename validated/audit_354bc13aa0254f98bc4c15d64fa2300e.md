### Title
Governance-settable `KIP71.GasTarget = 0` causes a division-by-zero panic in `NextMagmaBlockBaseFee`, halting all nodes - ([File: params/kip71_config.go])

### Summary
Analogous to the Notional issue where a zero-value edge case (`totalfCash == 0`) is not treated before it is used as a divisor, `KIP71Config.NextMagmaBlockBaseFee` in `params/kip71_config.go` divides by the `GasTarget` governance parameter without any check for `GasTarget == 0`, even though the governance parameter definition (`Kip71GasTarget` in `kaiax/gov/param.go`) uses `noopFormatChecker` and thus accepts any `uint64` value, including `0`.

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee for the KIP‑71 dynamic base-fee mechanism: [1](#0-0) 

When `parentGasUsed > gasTarget`, the delta is computed as:
```
gasUsedDelta := parentGasUsed - gasTarget
x := parentBaseFee * gasUsedDelta
y := x.Div(x, gasTarget)          // divide by gasTarget
```
and symmetrically in the decreasing branch. The only early-return guard is `if parentGasUsed == gasTarget`, which only protects the case `gasTarget == parentGasUsed == 0`. As soon as any transaction in the previous block consumed gas (`parentGasUsed > 0`) while `gasTarget == 0`, execution falls into the `parentGasUsed > gasTarget` branch and calls `big.Int.Div(x, 0)`, which is a Go run-time panic (unlike `BaseFeeDenominator`, which is defensively defaulted to `64` when zero at line 71-76, `GasTarget` has no such fallback).

The governance parameter that supplies this value is registered with no zero-rejection check: [2](#0-1) 

Compare this to the sibling parameter `Kip71BaseFeeDenominator`, which explicitly rejects zero (`v != 0`): [3](#0-2) 

This asymmetry shows the zero-value edge case for `GasTarget` was not treated, exactly mirroring the reported bug class where zero utilization (a legitimate/reachable state) was not special-cased before being used as a divisor.

`NextMagmaBlockBaseFee`/`VerifyMagmaHeader` is invoked from core, unconditionally-executed consensus paths, including block validation and block building: [4](#0-3) [5](#0-4) 

### Impact Explanation
Once a governance vote sets `kip71.gastarget` to `0` (a value the format checker does not reject) and the parameter becomes active, every subsequent block whose parent used any gas at all will trigger a `Div`-by-zero panic in `NextMagmaBlockBaseFee`. Because this function is called from block validation (`block_validator.go`), block assembly (`work/worker.go`, `chain_makers.go`), and the tx pool/gas price oracle, the panic crashes the consensus/execution path on every full node and validator that processes or builds the affected block. This causes a chain-wide halt: all honest nodes attempting to validate or produce the next block panic identically, which is a severe availability/consensus-halting impact analogous in class (unhandled zero-value input to a required division) to the migration-blocking bug in the reported issue, but with a stronger blast radius (crashes live consensus rather than blocking a one-time migration).

### Likelihood Explanation
Likelihood depends on governance being able to set `GasTarget = 0`. The `Kip71GasTarget` parameter uses `noopFormatChecker`, i.e., no validation prevents this value from being accepted by the governance module and written into `ChainConfig.Governance.KIP71.GasTarget`. Any governance proposal/vote mechanism that can change KIP‑71 parameters (the normal governance-parameter update flow explicitly listed as in-scope) can set this value, whether by misconfiguration or malicious intent from a governing entity. Once set and active, the divide-by-zero triggers deterministically on the very next block with nonzero gas usage — essentially guaranteed in practice.

### Recommendation
- Add a zero check to `Kip71GasTarget`'s `FormatChecker` in `kaiax/gov/param.go`, matching the pattern already used for `Kip71BaseFeeDenominator` (`v != 0`).
- Defensively guard `NextMagmaBlockBaseFee` in `params/kip71_config.go` against `gasTarget == 0` (e.g., treat it like `BaseFeeDenominator`'s zero fallback, or explicitly return a safe value/error) so a zero value can never reach `big.Int.Div` as the divisor.

### Proof of Concept
1. Via governance, set `kip71.gastarget` (mapped to `ChainConfig.Governance.KIP71.GasTarget`) to `0`. The `Kip71GasTarget` `FormatChecker` (`noopFormatChecker`) accepts this value without error.
2. Once this parameter set becomes active at the relevant block, mine/produce a block that uses any nonzero amount of gas (trivial — any normal transaction).
3. When the following block's base fee is computed via `NextMagmaBlockBaseFee(parentNumber, parentBaseFee, parentGasUsed)` with `parentGasUsed > 0` and `gasTarget == 0`:
   - `parentGasUsed == gasTarget` is false (since `parentGasUsed > 0`), so the early return is skipped.
   - Execution enters the `parentGasUsed > gasTarget` branch, computing `gasUsedDelta = parentGasUsed - 0 = parentGasUsed`, then `y := x.Div(x, new(big.Int).SetUint64(0))`.
   - `big.Int.Div` panics with a division-by-zero run-time error.
4. This panic occurs identically in every node that calls `VerifyMagmaHeader`/`NextMagmaBlockBaseFee` while validating or building this block (block validator, worker/miner, tx pool, gas price oracle), crashing block processing across the network.
