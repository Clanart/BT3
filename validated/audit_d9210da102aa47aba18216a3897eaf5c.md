## Analysis

The core broken invariant in the external report is: **a threshold/majority calculation is derived from a self-reported set of "voter" contributions without ensuring each contribution corresponds to a *distinct* authorized signer.** The proposer controls what gets aggregated, so the participation count can be inflated without genuine independent participation.

The closest local analog is in the BEEFY consensus verifier, which computes a "supermajority" purely from the *length* of a caller-supplied signature array, and never checks that the array's `authority index` entries are unique before treating that length as the participation count. [1](#0-0) 

### Title
BEEFY consensus verifier accepts duplicated signature entries as distinct participants, letting a single authority's signature forge supermajority - (File: `modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
`verify_mmr_update_proof` derives the BEEFY supermajority check from `mmr.signed_commitment.signatures.len()` and then builds `authority_indices`/`authority_leaves` directly from that same, caller-supplied array with no uniqueness check on `sig.index`. The identical pattern exists in the Solidity twin, `EcdsaBeefy.verifyMmrUpdateProof`.

### Finding Description
`signatures_length` is taken directly from the untrusted `ConsensusMessage` and passed to `check_participation_threshold` before any cryptographic binding is verified: [1](#0-0) 

The loop that follows recovers an address per signature and pushes `(index, leaf)` pairs into `authority_indices`/`authority_leaves` with no `dedup`/`BTreeSet` check on `sig.index` (contrast with the BSC verifier, which explicitly guards against a related "phantom bits" inflation vector at [2](#0-1) , showing the project is aware of this exact bug class but did not apply the same fix here): [3](#0-2) 

Because the merkle multi-proof only asserts "the leaf at index i equals H(authority_i)" for each supplied index, submitting the *same* `(index, signature)` pair `k` times is internally consistent — the same index always maps to the same leaf hash, so the multi-proof verifies without contradiction. The verifier therefore reaches `SuperMajorityRequired`'s pass condition and `InvalidAuthoritiesProof`'s pass condition using only **one real signature repeated `⌈2/3·N⌉` times**, rather than genuine signatures from `⌈2/3·N⌉` distinct authorities. `bls::verify`/`ECDSA.recover` only checks that *a* valid signature exists for *that* message from *that* one key — it does not independently enforce distinctness of contributors either.

The exact corrupted value is `signatures_length` (Rust) / `sigLen` (Solidity): it is used as a proxy for "number of distinct authorities who attested," but it is actually just "number of array entries the caller chose to submit," which the caller fully controls.

### Impact Explanation
This directly maps to the required impact "false proof/state acceptance": an attacker with exactly one authority's valid BEEFY signature (e.g., one compromised/malicious validator key, or any signature already publicly gossiped for a legitimate but different context) can craft a `ConsensusMessage`/`RelayChainProof` that the light client accepts as if signed by a 2/3+1 supermajority of the authority set. This collapses BEEFY's core BFT safety assumption (`f < n/3`) down to `f = 1`, allowing a single malicious/compromised authority to push an attacker-chosen MMR root, and subsequently forge finalized parachain state commitments (`verifyParachainHeaderProof`/`verify_parachain_headers`) that downstream ISMP request/response and asset-settlement paths treat as trusted remote state. This is the same class of consequence flagged in the source report — "the state machine may accept invalid blocks" — but here it manifests as fabricated cross-chain state used to unlock funds or approve fraudulent messages.

### Likelihood Explanation
Submission of consensus proofs to a light client is a public, permissionless entrypoint (any relayer/user may submit a `ConsensusMessage`). No privileged role, governance action, or majority collusion is required — only possession of a single valid signature over *some* commitment payload that the attacker can wrap into a crafted proof with duplicated entries. This is a config-independent code path exercised on every consensus update, making it a realistic, low-cost attack once a single authority key is available to the attacker (compromise, key leak, or a validator acting alone), which is a materially weaker bar than the intended 2/3+1 collusion assumption.

### Recommendation
Before computing `signatures_length`/`sigLen` and before building `authority_indices`, deduplicate signatures by recovered authority address (or by `sig.index`) — e.g., collect into a `BTreeSet`/mapping and reject the proof (`Error::DuplicateAuthority`) if `deduped.len() != signatures.len()`. Apply the same fix symmetrically in `EcdsaBeefy.sol`'s `verifyMmrUpdateProof`. This mirrors the fix already applied for the BSC bit-set-overflow case and enforces that the participation count reflects distinct authorities, not array length.

### Proof of Concept
1. Obtain (or compromise) one valid BEEFY authority signature `sig_0` over a legitimate `Commitment` (recoverable address `A_0`, index `i_0`), from any current or next authority set.
2. Build `MmrProof.signed_commitment.signatures = [sig_0; k]` where `k = ceil(2 * authority_set.len / 3)` (all identical entries, same `index: i_0`).
3. Submit this `ConsensusMessage` to `verify_consensus`.
   - `signatures_length == k` satisfies `check_participation_threshold(k, authority_set.len)`.
   - The loop recovers `A_0` `k` times, producing `k` identical `(i_0, hash(A_0))` leaves/indices.
   - `merkle_proof.verify(authority_set.keyset_commitment, &[i_0,...,i_0], &[leaf_0,...,leaf_0], authority_set.len)` succeeds because there is no contradiction — the leaf at `i_0` is asserted the same way every time.
4. The verifier proceeds to `verify_mmr_leaf` and accepts the attacker-controlled MMR root as finalized, using only one real signer instead of a genuine supermajority.

(Note: step 3's merkle-verification behavior against literally-duplicated indices is inferred from the absence of any dedup logic in the surrounding Rust/Solidity code — I was not able to inspect the underlying `MerkleProof`/`MerkleMultiProof` library implementation itself to confirm it does not independently reject repeated indices. If that library does enforce index uniqueness internally, this specific PoC would fail at that step and the finding would be moot; this residual uncertainty should be validated against the `rs_merkle`/`solidity-merkle-trees` library semantics before treating this as confirmed-exploitable.)

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}
