### Title
Unrestricted NFT Ownership (DID) Assignment on Eve Coin Mint - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`NFTWallet.generate_new_nft` mints the eve singleton coin for a new NFT with its ownership-layer `current_owner` field left empty, explicitly documenting that "the eve coin DID can be set to whatever" and that "wallets should always ignore DID value for eve coins as they can be set to any DID without approval." This mirrors the reported bug class: a value that should represent verified/authorized ownership (an owner assignment) can be set unilaterally by the transaction's own signer with no cryptographic proof or consent from the claimed owner, analogous to `OTLMFactory.deploy` letting `msg.sender` become the unrestricted owner of a newly deployed contract. [1](#0-0) 

### Finding Description
When minting a DID-linked ("provenant") NFT, `generate_new_nft` creates the ownership layer for the eve coin with an empty current owner and only sets the intended `did_id` on the *next* spend via `new_owner=did_id` in `generate_signed_transaction`, alongside `did_inner_hash` obtained through `get_did_approval_info`. [2](#0-1) [3](#0-2) 

The `-10` ("change owner") condition set in the eve-spend solution is the mechanism that assigns the `owner_did` field seen by every wallet that later syncs this NFT via `identify()`/`get_new_owner_did()`. Critically, this DID value is asserted purely via a magic condition inside the *minter's own* delegated puzzle — there is no signature, announcement, or on-chain proof from the DID singleton itself that it approved being linked as the owner at mint time. `get_did_approval_info` is only used to obtain a `did_inner_hash` to make the *next* DID spend possible, not to prove the DID authorized this specific NFT's ownership claim. [4](#0-3) 

Any wallet/RPC caller building the mint transaction fully controls the `did_id` parameter passed to `generate_new_nft` / `create_new_nft_wallet`; nothing in the puzzle or wallet code cryptographically verifies that the DID owner consented to or co-signed this specific mint. This is functionally the same defect as the external report: assignment of an "ownership" attribute happens unconditionally based on the caller's say-so (`msg.sender`/`did_id` parameter), not on authorization from the party actually being assigned as owner.

### Impact Explanation
Because the `owner_did` recorded on-chain for an NFT is trusted by `NFTWallet.identify()` to route/attribute the NFT to a specific DID-owned wallet, and is exposed via RPC (`coin.owner_did`) to marketplaces, DID-based access control, or royalty/attribution logic, an attacker can mint NFTs that falsely claim ownership by an arbitrary DID they do not control. Consumers of the `owner_did` field (front-ends, DID-gated NFT collections, minter-attribution systems) that treat this field as proof of an authorized relationship between the DID and the NFT can be misled — enabling impersonation of a DID's collection, spoofed provenance, or bypass of DID-based authorization checks that rely on `owner_did` alone. [5](#0-4) 

### Likelihood Explanation
This is trivially reachable by any wallet user or RPC caller: it only requires calling the existing `create_new_nft_wallet` / `generate_new_nft` mint flow with an arbitrary `did_id` value; no special privileges, malicious peer, or network-layer behavior is needed — it is a standard, unprivileged wallet action reachable from the RPC/CLI mint path. [6](#0-5) 

### Recommendation
Require an on-chain proof of DID consent at NFT mint/ownership-assignment time (e.g., an assertion tied to a coin/puzzle announcement created by the actual DID singleton spend, verified before the eve or ownership-layer spend is accepted), rather than trusting a caller-supplied `did_id`/`-10` condition with no counter-signature or announcement from that DID. At minimum, wallet and RPC consumers must not treat `owner_did` as an authorization signal without independently verifying the DID's own spend history/consent.

### Proof of Concept
1. Call `create_new_nft_wallet` / mint via `generate_new_nft` with `did_id` set to any arbitrary DID's launcher ID that the caller does not control (no signature or cooperation from that DID's wallet required).
2. The eve coin is created with an empty ownership current_owner, then the very next spend the same caller controls sets `new_owner=did_id` via the `-10` condition — entirely signed by the minter's own key, never touching the target DID's key. [7](#0-6) 
3. Any node/wallet syncing this NFT calls `identify()`, which reads `owner_did` straight off the puzzle without any proof that the DID approved being linked, and attributes/displays the NFT as owned by that DID. [8](#0-7) 

Note: the in-code comment at lines 503-505 explicitly acknowledges this exact risk ("eve coin DID can be set to whatever... can be set to any DID without approval"), confirming the root cause is a known, unresolved gap rather than a misreading of intended behavior. [9](#0-8)

def get_new_owner_did(unft: UncurriedNFT, solution: Program) -> Literal[b""] | bytes32 | None:
    conditions = unft.p2_puzzle.run(unft.get_innermost_solution(solution))
    new_did_id: Literal[b""] | bytes32 | None = None
    for condition in conditions.as_iter():
        if condition.first().as_int() == -10:
            # this is the change owner magic condition
            atom = condition.at("rf").as_atom()
            if atom == b"":
                new_did_id = b""
            else:
                new_did_id = bytes32(atom)
    return new_did_id
