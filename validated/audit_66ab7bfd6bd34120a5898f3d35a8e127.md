### Title
Attacker-controlled OP_RETURN `data` is excluded from fee and weight accounting, producing an underpriced / oversize transaction the protocol still signs - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` accepts a caller-supplied `data: Option<Vec<u8>>` which is appended as an OP_RETURN output to `tx_outs` (lines 194-202), but the size/fee estimation is performed with `Self::calculate_weight_vbytes(tx_ins.len(), payments, ...)` (lines 204, 225-226), which only expands `payments` and `change` into a dummy transaction — the OP_RETURN output is never included. Every downstream decision (`needed_fee`, `TooLowFee`, `NotEnoughFunds`, change derivation, `MAX_STANDARD_TX_WEIGHT`) is therefore computed against a transaction up to ~90 bytes smaller than the one that is actually built and threshold-signed in `TransactionSignMachine::sign` (lines 373-397). This is the same bug class as C-02: a user-influenced size parameter is decoupled from the fee the protocol actually commits to — except here the measured size under-counts while the constructed transaction grows, so the committed fee rate silently diverges from the requested `fee_per_vbyte`. [1](#0-0) [2](#0-1) 

### Finding Description
In `SignableTransaction::new`:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds a fresh `Transaction` containing only `payments` and `change` (lines 85-99); the OP_RETURN output pushed into `tx_outs` is absent from it. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` under-prices the real transaction by `fee_per_vbyte * (~11 + data.len())` (up to ~91 bytes of output data → roughly +91 vbytes at full weight since script bytes are non-witness).
2. The `TooLowFee` minimum-relay check (line 211) validates the *estimated* vbytes, not the real one, so a transaction whose true fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` is accepted.
3. `NotEnoughFunds` (line 215) is checked against the understated `needed_fee`; inputs may be committed that cannot actually fund the true required fee.
4. The change-amount branch (lines 224-235) recomputes with `calculate_weight_vbytes(..., Some(&change))`, again excluding the OP_RETURN, so `fee_with_change` is equally understated.
5. The `TooLargeTransaction` check (line 241) uses `weight` that omits the data output, permitting a transaction whose real weight exceeds `MAX_STANDARD_TX_WEIGHT` to be constructed.

The resulting `SignableTransaction` is then fed to `TransactionSignMachine::sign`, which computes `taproot_key_spend_signature_hash` over the *real* (larger) transaction — i.e., the threshold group signs and broadcasts a transaction whose economics were validated against a different, smaller transaction. [3](#0-2) 

### Impact Explanation
- The signed transaction's effective fee rate is strictly lower than the `fee_per_vbyte` the caller requested and checked — in the worst case below the relay minimum, so the network will not propagate/confirm it while the protocol treats the inputs as spent, burning a signing round and leaving the plan's funds in limbo (funds committed to a transaction that is not relayable).
- When a change output exists, the unpriced bytes do not reduce the fee (it is fixed at `needed_fee`); instead the discrepancy is invisible until broadcast, at which point fee-bumping is impossible for a fixed `Prevouts::All`/`TapSighashType::Default` threshold-signed transaction.
- Weight-accounting bypass means a `data`-bearing transaction can cross `MAX_STANDARD_TX_WEIGHT` undetected, producing a consensus-valid but non-standard transaction that nodes reject — again, signed funds that cannot confirm.
Severity: Medium (integrity/availability of protocol funds via fee misaccounting on an attacker-influenced input; no direct theft, but reliably reachable whenever `data` is supplied).

### Likelihood Explanation
Any caller able to populate `data` (up to the 80-byte `TooMuchData` bound at line 171) triggers the discrepancy deterministically — it is structural, not probabilistic. Whether an unprivileged party controls `data` depends on the integrator (the processor currently passes `None`), but as a library primitive `SignableTransaction::new` exposes the vulnerable path publicly, and the miscalculation applies to 100% of invocations with `data.is_some()`, scaling with `data.len()`. [4](#0-3) 

### Recommendation
Include the OP_RETURN output in the weight/vbytes estimation — e.g., pass the fully-built `tx_outs` (or an explicit `data` parameter) into `calculate_weight_vbytes`, or build the dummy estimation transaction from the same `tx_outs` vector used for the real transaction, so `needed_fee`, `TooLowFee`, `NotEnoughFunds`, change derivation, and `MAX_STANDARD_TX_WEIGHT` are all evaluated against the transaction that will actually be signed. Alternatively, recompute `vbytes` from `tx.weight()` after assembling the final `Transaction`.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs semantics, conceptual PoC
let data = vec![0u8; 80]; // maximal permitted OP_RETURN payload
let tx = SignableTransaction::new(
    vec![input],                       // ReceivedOutput covering payments + needed_fee exactly
    &[(payment_script, DUST)],
    None,                              // no change: leftover becomes fee
    Some(data.clone()),
    fee_per_vbyte,
).unwrap();

// needed_fee was computed from a dummy TX with only the payment output.
// The real TX additionally carries an ~91-byte OP_RETURN output.
let estimated_vbytes = tx.needed_fee() / fee_per_vbyte;
let actual_vbytes = tx.transaction().vsize() as u64; // includes OP_RETURN
assert!(actual_vbytes > estimated_vbytes);           // under-priced by ~91 * fee_per_vbyte

// With fee_per_vbyte chosen so needed_fee barely passes the TooLowFee check,
// the true feerate falls below DEFAULT_MIN_RELAY_TX_FEE:
let effective_rate = tx.fee() as f64 / actual_vbytes as f64;
assert!(effective_rate < fee_per_vbyte as f64);      // protocol signs an underpriced TX
```

The divergence holds identically in the change branch (`fee_with_change` at lines 225-232 also omits the data output) and in the weight cap check (line 241).
