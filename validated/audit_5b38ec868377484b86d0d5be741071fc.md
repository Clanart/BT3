## Title
Unauthenticated wallet crash via non-UTF-8 VCProofs key/value data during Verified-Credential proof parsing - (File: `chia/wallet/vc_wallet/vc_store.py`)

### Summary
`VCProofs.from_program()` parses proof key/value data that originates from a Verified Credential (VC) coin's CLVM program and blindly calls `bytes.decode("utf-8")` on both the key and value atoms with no error handling. Any counterparty who can cause a VC-related coin/spend to be processed by a wallet (offer counterparty, VC issuer, or any spend the wallet's VC-wallet logic uncurries) can supply non-UTF-8 bytes in these atom positions, raising an unhandled `UnicodeDecodeError` and crashing the wallet's processing path — directly analogous to the Mattermost mobile crash where an untyped/uncastable attachment field crashed the client when rendered.

### Finding Description
`VCProofs.from_program()` in `chia/wallet/vc_wallet/vc_store.py` recursively walks a `Program` (CLVM tree) that represents proof data attached to a Verified Credential coin, and when it reaches a leaf pair it does: [1](#0-0) 
```
elif first.atom is not None and rest.atom is not None:
    return VCProofs({first.atom.decode("utf-8"): rest.atom.decode("utf-8")})
```
There is no `try/except` around either `.decode("utf-8")` call. The `Program` being parsed is derived from wallet-visible coin data (VC lineage/coin spends processed by the VC wallet subsystem), which is attacker-influenced content: any party able to construct a coin spend that the victim's wallet interprets as VC-related proof data controls the exact atom bytes fed into this decode call. Supplying an atom containing an invalid UTF-8 byte sequence (e.g., a lone continuation byte such as `0x80`) causes `bytes.decode("utf-8")` to raise `UnicodeDecodeError`, an uncaught exception that propagates out of `from_program` and aborts whatever wallet operation (sync processing, RPC call inspecting the VC, etc.) invoked it.

This mirrors the reported bug class exactly: a field that is assumed to be safely castable/decodable to a string, but is attacker-supplied binary data, crashes the client when it is parsed/displayed, with no server-side or on-chain validation gating the content beforehand.

### Impact Explanation
A successful trigger halts wallet processing of the malicious VC data with an unhandled exception. Depending on the call site (sync loop iterating over incoming coin states, or an RPC/CLI call inspecting VC proofs), this results in a targeted denial of service against the victim wallet process — a spend-triggered transaction-processing halt, which is one of the explicitly accepted impact categories. It does not enable fund theft or consensus divergence by itself, keeping severity at the Medium tier (comparable to the CVSS 6.5 rating of the original report), since a full node/consensus is not affected — only the wallet client handling VC data.

### Likelihood Explanation
Likelihood is meaningful but bounded: an attacker needs a way to get a VC coin whose proof program is parsed by the victim's wallet (e.g., as a VC issuer/counterparty legitimately interacting with a VC feature, or through a maliciously crafted VC that ends up in the wallet's sync path). No signature/authorization bypass is required — the content of the proof atoms is fully attacker-controlled at construction time, and no length/encoding validation exists anywhere upstream of the `.decode("utf-8")` calls.

### Recommendation
Wrap both `.decode("utf-8")` calls in `VCProofs.from_program()` in a `try/except UnicodeDecodeError`, either rejecting the malformed VC proof by raising the existing `ValueError("Malformatted VCProofs program")` or by falling back to a safe non-crashing decode (e.g., `errors="replace"` or storing raw bytes) so that malformed VC proof content cannot propagate an unhandled exception into wallet-processing/RPC code paths.

### Proof of Concept
1. Construct (or have a counterparty construct) a VC coin/spend such that its proof `Program` contains, at a leaf pair, an atom that is not valid UTF-8 — e.g., a single `0x80` byte — for either the key or value position.
2. Cause the victim wallet to process this VC (e.g., via a legitimate VC-issuance/transfer interaction that the wallet's VC-wallet logic later uncurries into `VCProofs.from_program()`), or invoke the RPC/CLI path that inspects the VC's proofs.
3. Observe `VCProofs.from_program()` raise `UnicodeDecodeError: 'utf-8' codec can't decode byte 0x80 ...`, which is unhandled at this call site and propagates upward, aborting the processing/RPC call. [1](#0-0)

    @staticmethod
    def from_program(prog: Program) -> VCProofs:
        first: Program = prog.at("f")

        if first.atom is None and rest.atom is None:
            final_dict: dict[str, str] = {}
