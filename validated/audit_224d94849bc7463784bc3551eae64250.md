## Title
Path‑containment check in `_resolveWithin` compares raw prefixes without a path‑separator boundary, allowing a sibling directory (e.g. `repo-evil`) to be treated as inside `repo` - (File: `app/src/lib/path.ts`)

### Summary
The containment check in `_resolveWithin` uses `realResolved.startsWith(realRoot)` with no boundary character check after the prefix. Any directory whose name starts with the exact characters of `realRoot` (e.g. `repo-evil` next to `repo`) satisfies the check even though it is a completely different, sibling directory tree.

### Finding Description
`resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` are the app's sanctioned "keep this path inside the repo" primitive. The core logic is: [1](#0-0) 

`resolve()` first joins `rootPath` with the (already normalized) relative segments, which can legitimately walk outside the root via `..` before the final `realResolved.startsWith(realRoot)` check is meant to reject it. The problem is that `startsWith` is a pure string-prefix test: it does not verify that the character immediately following `realRoot` in `realResolved` is a path separator (or that the strings are exactly equal). Consequently:

- `realRoot = '/Users/x/repo'`
- `realResolved = '/Users/x/repo-evil/secret'`

`realResolved.startsWith(realRoot)` evaluates to `true`, so the function returns the fully resolved (attacker-influenced) path as "safe," even though `/Users/x/repo-evil` is a sibling directory, not a subdirectory of `/Users/x/repo`.

Note this bug requires the sibling path (`repo-evil/secret` in the PoC) to actually exist on disk for `realpath()` to succeed at line 69 — if it doesn't exist, `realpath` throws and the caller sees an error rather than a false "safe" result. So exploitation depends on a naming coincidence between the user's repository directory and another directory that already exists alongside it (a scenario that is plausible in ordinary multi-repo workspaces where users clone repos with related prefixed names, e.g. `app` / `app-electron`, `repo` / `repo2`, `project` / `project-backup`).

The function is used to keep file reads from a cloned repository's working directory or a git object bounded to the repo tree, notably in `buildConflictContext`, which resolves repository-relative conflict file paths and feeds their raw content to the Copilot conflict-resolution prompt: [2](#0-1) 

### Impact Explanation
If the naming-coincidence precondition is met, `resolveWithin` returns a path pointing outside the intended repository as if it were validated/safe. Downstream consumers such as `buildConflictContext` will then `stat`/`readFile` that out-of-repo file and include its contents in a prompt sent to a networked model, resulting in local file disclosure/exfiltration of data the user never intended to expose, i.e. a file read outside the repo boundary this function is supposed to enforce.

### Likelihood Explanation
Exploitation is not fully attacker-controlled: it requires (a) an attacker-influenced relative path segment traversing to a sibling directory, and (b) that a real directory with a name that is a strict superstring-prefix match of the repository's directory name already exists next to it on the victim's filesystem, containing a real file at the traversed sub-path. This is a plausible but not universally guaranteed condition (common in workspaces with multiple similarly-prefixed repo clones), so likelihood is moderate rather than high — it is not reliably attacker-triggerable against an arbitrary victim without knowledge of their local directory layout.

### Recommendation
Fix the boundary check to require an exact match or that the next character after the root is the platform path separator, e.g.:
```ts
const rootWithSep = realRoot.endsWith(sep) ? realRoot : realRoot + sep
return realResolved === realRoot || realResolved.startsWith(rootWithSep) ? resolved : null
```
Add a regression test mirroring the reported PoC (`/tmp/root` vs `/tmp/root-evil/file`) alongside the existing symlink-traversal tests in `app/test/unit/path-test.ts`.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import { mkdir, writeFile, rm } from 'fs/promises'
import { join } from 'path'

// mkdir -p /tmp/root /tmp/root-evil && echo secret > /tmp/root-evil/file
await mkdir('/tmp/root', { recursive: true })
await mkdir('/tmp/root-evil', { recursive: true })
await writeFile('/tmp/root-evil/file', 'secret')

const result = await resolveWithin('/tmp/root', '../root-evil/file')
console.log(result) // -> '/tmp/root-evil/file' instead of null
```
This demonstrates that `_resolveWithin`'s containment check (`app/src/lib/path.ts` line 71) incorrectly returns the out-of-root path instead of `null`.
