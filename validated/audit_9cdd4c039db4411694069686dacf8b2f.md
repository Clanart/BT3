### Title
Unauthenticated DKG encryption key enables MITM substitution and secret share recovery - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
In PedPoP, each participant broadcasts an `EncryptionKeyMessage { msg: Commitments, enc_key }`. The Schnorr proof-of-knowledge authenticates only the Feldman commitments (`cached_msg`); the `enc_key` field — the ECDH public key every other participant will encrypt secret shares to — is not covered by any signature or proof bound to the sender. An attacker able to inject/modify bytes on the wire at the first (registration) round can replace `enc_key` with a key they control, exactly mirroring CVE-2021-23214's "injection at connection establishment despite certificate authentication."

### Finding Description
The PoK challenge binds `context`, `participant`, `nonce`, and `commitments` — but not `enc_key`: [1](#0-0) 

`Commitments::read`/`write` only serialize the t commitment points plus the Schnorr signature; `enc_key` rides alongside in `EncryptionKeyMessage` unauthenticated: [2](#0-1) 

On registration, the peer-supplied `enc_key` is stored verbatim with no proof of possession and no inclusion in the verified transcript: [3](#0-2) 

Then `generate_secret_shares` encrypts each victim's Pedersen share via `ecdh(per_message_key, registered_enc_key)`: [4](#0-3) [5](#0-4) 

The per-message PoP (`pop_challenge`) binds `sender`/`key`/`msg`, but it is produced by the *sender* of the encrypted share — it cannot detect that the recipient's registered `enc_key` was swapped. The code itself notes "the per-message keys have no root of trust other than their existence in the assumed-to-exist external authenticated channel" — yet unlike the `msg` field, `enc_key` also lacks any internal authentication, so even a channel that authenticates the Commitments PoK leaves this field injectable.

### Impact Explanation
An attacker substituting participant *i*'s `enc_key` with their own scalar's public key causes every other participant's `encrypt(rng, i, share)` to produce ciphertexts decryptable by the attacker. The attacker recovers all shares directed at *i* in plaintext, learning victim polynomial evaluations — i.e., remote recovery of threshold secret-share material with no valid share needed from *i*'s side. Under FROST this is threshold key-share theft, enabling eventual forgery if enough shares are harvested across a malicious-coordinator or repeated-DKG scenario. Even a single stolen share is secret material the protocol intends to protect.

### Likelihood Explanation
Requires the ability to tamper with the broadcast `EncryptionKeyMessage` bytes in transit — precisely the MITM-during-handshake position the CVE describes. The attack is undetectable: the PoK still verifies (it doesn't cover `enc_key`), all shares remain valid Feldman shares (they're honestly computed, just encrypted to the wrong key), and no blame event is ever triggered since decryption by the true recipient simply yields a valid-looking share failure only if the attacker also fails to relay — a passive attacker who also forwards a re-encrypted share to the real key stays fully invisible.

### Recommendation
Bind `enc_key` into the authenticated portion of the message: either (a) append `enc_key.to_bytes()` to `cached_msg` inside `Commitments` so it is covered by the PoK challenge in `challenge()`, or (b) require a Schnorr PoP over `enc_key` transcripted with `context` and `participant`, verified in `verify_r1`/`Decryption::register` before insertion into `enc_keys`.

### Proof of Concept
1. Victim *i* runs `KeyGenMachine::generate_coefficients`, producing `EncryptionKeyMessage { msg: Commitments{...sig}, enc_key: iG }`.
2. MITM reads the serialized message, replaces `enc_key` with `aG` (attacker scalar `a`), forwards it. `Commitments::read` and the PoK batch verify still succeed since `cached_msg` and `sig` are untouched.
3. Every participant `j` calls `self.encryption.encrypt(rng, i, share_j(i))`, computing `ecdh(k_j, aG) = a·k_j·G` and storing `key = k_j·G` publicly in the `EncryptedMessage`.
4. Attacker computes `k_j·a·G = a·(k_jG)` from the public per-message key, derives the ChaCha20 cipher via `cipher(context, ecdh)`, and decrypts each `SecretShare` — recovering every share addressed to *i*, i.e., `f_j(i)` for all `j`, without detection.

impl<C: Ciphersuite> ReadWrite for Commitments<C> {
  fn read<R: Read>(reader: &mut R, params: ThresholdParams) -> io::Result<Self> {
    let mut commitments = Vec::with_capacity(params.t().into());
    let mut cached_msg = vec![];

    #[allow(non_snake_case)]
    let mut read_G = || -> io::Result<C::G> {
      let mut buf = <C::G as GroupEncoding>::Repr::default();
      reader.read_exact(buf.as_mut())?;
      let point = C::read_G(&mut buf.as_ref())?;
      cached_msg.extend(buf.as_ref());
      Ok(point)
    };

    for _ in 0 .. params.t() {
      commitments.push(read_G()?);
    }

    Ok(Commitments { commitments, cached_msg, sig: SchnorrSignature::read(reader)? })
  }

  fn write<W: Write>(&self, writer: &mut W) -> io::Result<()> {
    writer.write_all(&self.cached_msg)?;
    self.sig.write(writer)
  }
