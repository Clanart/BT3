### Title
CW20-wraps-ERC20 pointer contract does not verify the boolean return value of the underlying ERC20 `transfer`/`transferFrom` call, allowing silent transfer failures with no on-chain error (File: `example/cosmwasm/cw20/src/contract.rs`)

### Summary
The CosmWasm CW20 pointer contract that wraps a native EVM ERC20 token (deployed via `registerPointerForERC20` and driven by `x/evm` pointer precompiles) forwards `transfer`/`transfer_from` CW20 messages to the underlying ERC20 contract using an `EvmMsg::DelegateCallEvm` message, but never inspects the ABI-encoded `bool` return value of the ERC20 `transfer`/`transferFrom` call. It only relies on whether the EVM call itself succeeds (does not revert). Any ERC20 token that is not fully ERC20-compliant and returns `false` on a failed transfer (instead of reverting), such as the well-known BADGER-style tokens referenced in the original report, will cause the CW20 pointer to report a successful transfer while no tokens actually moved.

### Finding Description
The pointer's `transfer` and `transfer_from` handlers build the ERC20 call payload and dispatch it as a `DelegateCallEvm` submessage without checking its return data: [1](#0-0) [2](#0-1) 

`DelegateCallEVM` is a thin binding that is encoded and dispatched as a Cosmos `sdk.Msg` by `evmwasm.EncodeDelegateCallEVM`; it exposes only `To`/`Data` and carries no mechanism for the caller to observe or assert on the callee's ABI-encoded boolean result: [3](#0-2) [4](#0-3) 

Because the message handler for `DelegateCallEvm` only fails the CosmWasm message when the EVM sub-call reverts, an ERC20 implementation that returns `false` on failure (rather than reverting) will let the CW20 message succeed even though the transfer never happened. This is directly observable in the test suite for this exact pointer direction, where a transfer to an unassociated address neither reverts nor updates the balance, silently no-op'ing the transfer: [5](#0-4) 

This is the same bug class as the referenced report: return values of `transfer`/`transferFrom` are not checked to be `true`, so a non-compliant ERC20 causes silent failure instead of an explicit revert. Note this is distinct from the ERC20-wraps-CW20 direction (`contracts/src/CW20ERC20Pointer.sol`), whose `_execute` requires `success` from the WASM precompile delegatecall and correctly reverts on CW20-level failures (e.g. "should fail transfer() if sender has insufficient balance" reverts with "CosmWasm execute failed").

### Impact Explanation
Any unprivileged CosmWasm user who owns a CW20 pointer for a non-fully-compliant ERC20 token can submit a `transfer`/`transfer_from` CW20 message. If the underlying token returns `false` on failure conditions, the CW20 message will report success (emit `action: transfer` attributes) while balances do not change. Downstream integrators (DEXes, vaults, multi-hop CW20 flows) that trust the success of this message without independently re-verifying balances can proceed as if funds moved, leading to accounting desync, double-crediting, or fund loss in composed contracts that rely on the pointer's reported success.

### Likelihood Explanation
Likelihood depends on a specific non-ERC20-compliant token (returning `false` instead of reverting) being wrapped by a CW20 pointer, which is plausible since pointer creation for ERC20 tokens is permissionless (`registerPointerForERC20`) and any EVM-deployed token, compliant or not, can be pointed. Given Sei's design goal of interop with arbitrary EVM tokens, encountering a non-compliant token via `AddCW20`/pointer registration is a realistic occurrence rather than a contrived edge case.

### Recommendation
When constructing the `DelegateCallEvm` payload for ERC20 `transfer`/`transferFrom` in `example/cosmwasm/cw20/src/contract.rs`, do not treat EVM call success alone as sufficient. Either:
- Decode the returned ABI `bool` after the delegatecall and revert the CosmWasm message if it is `false`, or
- Use a `staticcall`-based pre/post balance check pattern (compare `balanceOf` before and after) to assert the actual transfer occurred, similar to OpenZeppelin's `SafeERC20` semantics, before allowing the `Response` to be considered successful.

### Proof of Concept
1. Deploy a non-ERC20-compliant token on the EVM side whose `transfer`/`transferFrom` returns `false` on failure (e.g., insufficient balance) instead of reverting, mirroring the BADGER token behavior described in the report.
2. Register a CW20 pointer for that ERC20 token via `registerPointerForERC20` (permissionless), as done in `contracts/test/CW20toERC20PointerTest.js`.
3. As an unprivileged CosmWasm caller, invoke `transfer`/`transfer_from` on the CW20 pointer with an amount/target that triggers the token's `false`-return failure path (e.g., an address association edge case as shown in the existing test at lines 118-128, or an amount exceeding balance where the token returns `false` instead of reverting).
4. Observe: the CW20 message returns success (no revert), yet `balanceOf` for sender/recipient is unchanged, confirming the transfer silently failed while being reported as successful.

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}
