### Title
`SignableTransaction::new` computes weight/vbytes and `needed_fee` against the payment set only, excluding the OP_RETURN `data` output that is actually included in the transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to `MarketUtils#getNextTotalBorrowing` — which applied the new factor to the new total while the cost should have been evaluated against the prior amount — `SignableTransaction::new` computes the transaction's weight, virtual size, `needed_fee`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check against a transaction reconstructed from `payments` only. The OP_RETURN `data` output is pushed into `tx_outs` at `send.rs:194-202` *before* the weight is measured, yet `calculate_weight_vbytes` (line 204 and again at lines 225-226) rebuilds a synthetic `Transaction` whose `output` list is derived exclusively from `payments` (plus optionally `change`) — see lines 85-99. The `data` output is never counted.

### Finding Description
`calculate_weight_vbytes(inputs, payments, change)` constructs a dummy transaction containing only the payment outputs (and optionally a change output) and returns `tx.weight()`/`get_virtual_tx_size` for it. In `SignableTransaction::new`, when `data` is `Some`, a `TxOut` with `ScriptBuf::new_op_return(...)` of up to ~83 bytes is pushed to `tx_outs` at line 195, but the subsequent fee/weight computation at line 204 passes `payments` — not `tx_outs` — so the OP_RETURN output contributes nothing to `weight`, `vbytes`, `needed_fee`, the `TooLowFee` minimum-relay comparison (line 211), or the `TooLargeTransaction` check (line 241). The same omission applies to the `fee_with_change`/`weight_with_change` recomputation at lines 225-226.

The result: the declared `needed_fee = fee_per_vbyte * vbytes` is calculated on a smaller virtual size than the real transaction. Since the actual fee paid is `sum(inputs) - sum(outputs) = needed_fee` (change is computed as `input_sat - payment_sat - fee_with_change`, line 228), the final broadcast transaction has a lower effective sat/vbyte rate than the caller-specified `fee_per_vbyte`, and can fall below `DEFAULT_MIN_RELAY_TX_FEE` despite the guard at line 211 passing.

### Impact Explanation
A `SignableTransaction` created with `data` underpays relative to the requested fee rate. If `fee_per_vbyte` is near the relay minimum, the real transaction's effective rate can fall below `DEFAULT_MIN_RELAY_TX_FEE`, producing a transaction that full nodes will not relay — payments become stuck/unconfirmable even though all sanity checks passed. Additionally, the `TooLargeTransaction` check is bypassed for the data output's weight, permitting a transaction that exceeds `MAX_STANDARD_TX_WEIGHT` to be constructed (bounded in practice by the 80-byte data cap, so this second effect is marginal).

### Likelihood Explanation
The bug triggers deterministically whenever `SignableTransaction::new` is called with `data: Some(_)` and a `fee_per_vbyte` low enough that omitting ~20 vbytes of OP_RETURN weight drops the effective fee below the relay floor, or simply whenever an exact fee rate matters. `data` is a public, caller-supplied parameter of the wallet API (`networks/bitcoin/src/wallet/send.rs:154`), so any unprivileged caller constructing a data-carrying transaction reaches it. The in-tree processor (`processor/src/networks/bitcoin.rs:446-452`) currently passes `None` for `data`, so trigger likelihood within the shipped processor is low, but the library API itself is reachable and silently produces the miscounted fee.

### Recommendation
Compute weight/vbytes over the actual output set that will appear in the transaction. Either pass `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes`, or move the OP_RETURN push to after the measurement and separately account for its weight (`data.len() + ~11` serialized bytes times the non-witness multiplier). Apply the same corrected output list to both the no-change and with-change calculations at `send.rs:204` and `send.rs:225-226`, so `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the real transaction.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs (simplified trace)
// Line 194-202: OP_RETURN output added to tx_outs
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...) });
}

// Line 204: weight computed WITHOUT tx_outs / data
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
// calculate_weight_vbytes (lines 85-99) builds tx.output only from `payments`
// -> data output's weight is never counted

let mut needed_fee = fee_per_vbyte * vbytes;      // underestimated
if needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000 { /* passes */ }

// Line 224-235: change path repeats the same omission
let fee_with_change = fee_per_vbyte * vbytes_with_change; // still no data output
let change_value = input_sat - payment_sat - fee_with_change;
// Actual fee paid == needed_fee, but real tx is larger -> effective sat/vB < fee_per_vbyte
```
Concretely: choose `fee_per_vbyte = 1`, `data = vec![0; 80]` (≈+83 weight units ≈ +21 vbytes), and size inputs so `needed_fee` computed on the payments-only vbytes is exactly `vbytes` sat. The resulting signed transaction's real vsize is `vbytes + ~21`, so its effective rate is ~`vbytes / (vbytes + 21)` sat/vB < 1 sat/vB = the relay minimum — a non-relayable transaction that the constructor accepted.
