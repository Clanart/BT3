### Title
Unbounded recursive decoding of nested `AccountKeyRoleBased` containers allows CPU-amplification DoS via `TxTypeAccountUpdate`/`TxTypeAccountCreation` transactions - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively RLP-decodes each element of a role-based account key without any check on the *type* or *nesting depth* of the sub-keys before decoding them. The type-validity rule that forbids a composite key (role-based/nested) from containing another composite key (`IsCompositeType()` check) is only enforced in `CheckInstallable`/`CheckUpdatable`, which run *after* the entire nested structure has already been fully parsed. This mirrors the CVE-2019-3559 root cause: a container of "unknown"/disallowed-typed elements is not rejected until after the expensive parse has already happened, letting a small, cheaply-constructed message force disproportionate CPU work on the receiving node.

### Finding Description
`AccountKeySerializer.DecodeRLP` decodes a key type tag and then dispatches via `NewAccountKey(keyType)` to construct the concrete key, immediately calling `s.Decode(serializer.key)`: [1](#0-0) 

If the type is `AccountKeyTypeRoleBased`, this reaches `AccountKeyRoleBased.DecodeRLP`, which decodes an arbitrary-length `[][]byte` and, for **every element**, performs an independent, fresh `rlp.DecodeBytes` call into a new `AccountKeySerializer` — which can again resolve to `AccountKeyTypeRoleBased`, recursing: [2](#0-1) 

No bound is enforced at decode time on:
- the number of elements per role-based array (the `RoleLast`/length limit is only checked in `CheckInstallable`/`CheckUpdatable`), and
- whether a nested key is itself a composite type (the `IsCompositeType()` rejection is likewise only checked in `CheckInstallable`), see: [3](#0-2) 

This means a crafted `AccountUpdate`/`AccountCreation`/`FeeDelegatedAccountUpdate*` transaction whose `KeyData` encodes deeply/broadly nested `AccountKeyRoleBased` values will be **fully recursively RLP-decoded** — including all descendant `rlp.DecodeBytes` calls, `NewAccountKey` allocations, and interface dispatch — before the "nested composite type is not allowed" rule is ever checked. The decode path is reached by `TxInternalDataAccountCreation.fromSerializable` (and equivalent fromSerializable methods for AccountUpdate variants), which is invoked whenever such a transaction is decoded off the wire (public RPC `eth_sendRawTransaction`, p2p tx broadcast, or block/body decoding): [4](#0-3) 

Because each `[][]byte` element can independently repeat the same nested `AccountKeyRoleBased` pattern, an attacker can amplify decode cost combinatorially with nesting depth/width while the top-level transaction payload remains cheap to construct and cheap in terms of the outer RLP list size — exactly the amplification pattern the CVE-2019-3559 report describes ("short messages...take a long time to parse").

### Impact Explanation
Any unprivileged transaction sender or public-RPC caller can submit a single `AccountUpdate`/`AccountCreation`/fee-delegated variant transaction with a maliciously nested `AccountKeyRoleBased` `KeyData` blob. Every node that decodes this transaction (mempool admission, p2p propagation, or block validation) pays the full recursive-decode cost before any validity check (`CheckInstallable`) can reject it. Submitting many such transactions (or one inside a block) can consume disproportionate CPU across the network's nodes relative to transmitted bytes, degrading transaction processing/block validation — a network-wide denial-of-service risk consistent with High severity.

### Likelihood Explanation
The path is reachable from a single, unprivileged, unsigned-verification-required transaction — no consensus/validator/peer privilege is needed; only that the transaction be well-formed enough to pass basic RLP syntax and (for full block inclusion) a valid signature over an attacker's own key. Constructing nested `AccountKeyRoleBased` values is a purely mechanical RLP-encoding exercise fully within an external actor's control, making exploitation straightforward once the size/depth needed for meaningful CPU amplification is empirically determined.

### Recommendation
Enforce the composite-type and length constraints **during** `DecodeRLP` rather than only in `CheckInstallable`/`CheckUpdatable` — i.e., in `AccountKeyRoleBased.DecodeRLP`, reject decoding of any sub-key whose type is itself `AccountKeyTypeRoleBased` (or otherwise `IsCompositeType()`), and reject arrays longer than `RoleLast`, before recursively decoding further. Consider similarly bounding `AccountKeyWeightedMultiSig` key counts at decode time against `MaxNumKeysForMultiSig` rather than only at `CheckInstallable`/`SigValidationGas` time.

### Proof of Concept
Construct a `TxTypeAccountUpdate` (or `TxTypeAccountCreation`) transaction whose `KeyData` is an `AccountKeySerializer`-encoded `AccountKeyRoleBased` value where one or more of its RLP-encoded sub-key byte slices are themselves valid encodings of `AccountKeyRoleBased` (type tag `AccountKeyTypeRoleBased`) containing further nested `AccountKeyRoleBased` sub-keys, repeated to the desired depth/width (e.g., using `accountkey.NewAccountKeySerializerWithAccountKey` and `rlp.EncodeToBytes` recursively as done in `tests/kaia_test.go`'s `TestWronglyEncodedAccountKey`, but nesting `AccountKeyRoleBased` inside itself instead of a malformed byte string). Submitting this transaction (or decoding it via `rlp.DecodeBytes` on the receiving side, e.g. as exercised in `TestWronglyEncodedAccountKey`) triggers full recursive decoding in `AccountKeyRoleBased.DecodeRLP` before any `CheckInstallable` nested-composite rejection occurs, demonstrating the amplification path: [5](#0-4)

```go
func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
```

```go
func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
```
