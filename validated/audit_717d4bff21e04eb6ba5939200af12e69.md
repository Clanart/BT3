### Title
Out-of-range `recipient`/`sender` in blame evaluation panics via unchecked `HashMap` indexing, enabling unauthenticated denial of service - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`AdditionalBlameMachine::blame` / `BlameMachine::blame` accept externally-supplied `sender` and `recipient` `Participant` values and pass them into `Decryption::decrypt_with_proof` and `blame_internal`, which index `self.enc_keys[&decryptor]` and `self.commitments[&sender]` without validating the indexes against the registered set. Any `Participant` value in `1 ..= u16::MAX` is constructible, while only participants `1 ..= n` were registered. A `Participant > n` causes a `HashMap` index panic, crashing the caller. This mirrors CVE-2020-0556's class: insufficient validation of externally supplied identifiers lets an unauthenticated party trigger denial of service (and abort the protocol's accountability mechanism) via adjacent access.

### Finding Description
`AdditionalBlameMachine::new` registers encryption keys and commitments only for `i in 1 ..= n`:

`crypto/dkg/pedpop/src/lib.rs` (lines 655-661):
```rust
let mut encryption = Decryption::new(context);
for i in 1 ..= n {
  let i = Participant::new(i).unwrap();
  let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
  commitments.insert(i, encryption.register(i, msg).commitments);
}
```

`blame` then forwards caller-controlled `sender` and `recipient` into `blame_internal` (lines 674-682), which calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` (line 582).

Inside `decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs` lines 366-390), after the PoP check, the DLEq verification indexes the encryption-key map directly:

```rust
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],
  )
```

`std::collections::HashMap`'s `Index` impl panics on a missing key, so `decrypt_with_proof` panics whenever `decryptor` (the attacker-supplied `recipient`) is not a registered participant. Similarly, in `blame_internal` (`lib.rs` lines 595-604), `self.commitments[&sender]` panics if `sender` was not in `1 ..= n`. `Participant::new` accepts any nonzero `u16` (`crypto/dkg/src/lib.rs` lines 29-35), so values like `Participant::new(n + 1)` or `u16::MAX` are trivially constructible from public input.

Note the panic occurs even earlier than one might assume: `decrypt_with_proof` checks `msg.pop` first (lines 374-379), which returns `InvalidSignature` → `sender` for a *forged* message — but a real, correctly-formed message (e.g., a replayed or legitimately-obtained `EncryptedMessage` whose PoP verifies under `sender`) reaches the `enc_keys[&decryptor]` index with no bounds check. Even simpler, `blame_internal` is also reachable with `proof: Some(...)` paths that index `enc_keys` before any share validation.

### Impact Explanation
Blame evaluation is the protocol's accountability path: it runs when a participant reports a fault. An adjacent party who can submit or relay a blame accusation (the API explicitly exists so machines and even non-participants can evaluate blame — `AdditionalBlameMachine::new` documents it "capable of evaluating Blame regardless of if the caller was a member") can crash the evaluating process by naming `recipient` or `sender` outside `1 ..= n`. This is a denial of service on the node evaluating the accusation and can indefinitely stall the DKG abort/blame flow, exactly the "denial of service via adjacent access" consequence of the reference advisory.

### Likelihood Explanation
Triggering requires only supplying a blame tuple `(sender, recipient, msg, proof)` where `recipient > n` (panics at `enc_keys[&decryptor]` when `proof` is `Some`) or `sender > n` with a PoP-valid `msg` (panics at `commitments[&sender]`). No secret material, valid proof forgery, or protocol participation is needed to choose the `Participant` indexes; `Participant::new` is a public const constructor. The only mitigation is callers pre-validating indexes, which the API does not document as required (contrast `AdditionalBlameMachine::new`, which does document its commitment-validity precondition).

### Recommendation
Replace unchecked indexing with fallible lookups in `Decryption::decrypt_with_proof` and `blame_internal`:
- `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`
- `self.commitments.get(&sender)` guarded, returning a defined fault result or a new `PedPoPError` variant for out-of-range participants.
Alternatively, validate `sender`/`recipient` against `1 ..= n` at the top of `BlameMachine::blame`/`AdditionalBlameMachine::blame` and return an error/fault result rather than panicking.

### Proof of Concept
```rust
// Assume n = 3 participants completed round 1; commitment_msgs collected.
let machine = AdditionalBlameMachine::<Ristretto>::new(CONTEXT, 3, commitment_msgs).unwrap();

// Attacker submits an accusation naming a non-existent recipient.
// Participant::new only rejects 0; 9 > n = 3 is accepted.
let bogus_recipient = Participant::new(9).unwrap();

// Any msg whose PoP verifies for `sender` reaches decrypt_with_proof;
// with proof = Some(...), enc_keys[&bogus_recipient] is indexed -> panic.
machine.blame(ONE, bogus_recipient, msg, Some(proof)); // thread panics on HashMap index
```
