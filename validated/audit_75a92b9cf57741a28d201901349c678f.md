### Title
Copilot conflict-resolution write path hardcodes UTF-8, silently corrupting non-UTF-8 files that get committed - ([File: app/src/lib/stores/app-store.ts])

### Summary
`IncentivizedERC20` hardcodes an assumption (18 decimals) that is only valid for a subset of inputs, silently corrupting derived values for tokens that don't match the assumption. The same broken-invariant pattern exists in GitHub Desktop's Copilot merge-conflict resolution pipeline: the code reads conflicted file content, base content, and blob content as `'utf8'`/`'utf-8'` unconditionally, and later writes the AI-reassembled resolution back to disk with `'utf8'` encoding, with no check of the file's actual encoding.

### Finding Description
The conflict-resolution flow performs three hardcoded-UTF-8 operations on attacker-influenced repository content:

1. `getResolutionDiff` reads the working-tree file with conflict markers as UTF-8: [1](#0-0) 

2. It also decodes the "theirs"/"ours" git blob via `toString('utf-8')`: [2](#0-1) 

3. `reassembleResolvedFile` operates purely on JS strings, splicing model-provided resolved sections into the original content that was already utf8-decoded: [3](#0-2) 

4. Finally, `_applyCopilotConflictResolutions` writes the reassembled content back to the working directory unconditionally as `'utf8'` and then stages it with `git add`: [4](#0-3) 

Node's `Buffer.toString('utf8')` / `fs.readFile(..., 'utf8')` do not throw on invalid byte sequences for non-UTF-8 encodings (e.g. Shift-JIS, UTF-16LE, Windows-1252/Latin-1, GBK) — it silently substitutes malformed sequences with the U+FFFD replacement character. None of the read paths (`readFile`, `getBlobContents().toString('utf-8')`) detect or preserve the original encoding, and the corrupted string is passed to the AI model and reassembled/spliced with `reassembleResolvedFile`, which also just treats the file as UTF-8 text. The final `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` re-encodes the mangled string back as UTF-8 bytes, replacing the original file content on disk. There is no encoding-detection guard, no binary/non-UTF-8 warning, and no round-trip verification anywhere in this path.

### Impact Explanation
A cloned/fetched repository the user does not control (e.g. a legacy codebase with Shift-JIS/Latin-1-encoded source files, a common real-world scenario for internationalized or older projects) that develops a merge/rebase/cherry-pick conflict on such a file will have that file corrupted the moment the user invokes "Resolve with Copilot" and clicks "Continue Merge." The corruption is silent: no error is raised, the file is staged via `git add` and becomes part of the commit/push, permanently replacing bytes that cannot be recovered from the working tree (only from git history, if the user notices at all). This matches "silent corruption of what the user commits or pushes" — the attacker's control surface is simply the encoding of files inside the repository content the victim clones, and no other special privilege is required.

### Likelihood Explanation
The trigger requires only: (1) a repository containing a non-UTF-8 encoded file, (2) a normal git conflict during merge/rebase/cherry-pick touching that file, and (3) the user using the built-in "Resolve with Copilot" feature, which is a standard, in-product workflow gated only by having a valid account for `enableCopilotConflictResolution()`/`getAccountForCopilotConflictResolution` — no unnatural steps, no admin rights, no local malware. Non-UTF-8 source files are common enough (localized strings, legacy Windows-1252 files, Shift-JIS Japanese codebases) that this is a realistic occurrence, though it's scoped to users who opt into the newer Copilot conflict-resolution feature.

### Recommendation
Do not hardcode UTF-8 across the read/reassemble/write pipeline:
- Detect or preserve the original file encoding when reading conflicted files/blobs (or read as `Buffer` and only decode for model consumption, keeping the raw buffer as the fallback baseline).
- Before writing resolved content back with `writeFile(..., 'utf8')`, verify the file's original encoding was in fact UTF-8 (or explicitly ASCII-compatible), and refuse/skip Copilot auto-resolution for files whose content cannot be losslessly round-tripped through UTF-8 decode/encode — falling back to manual conflict resolution instead.
- At minimum, warn the user when a file is detected as non-UTF-8 before offering AI-based resolution for it, similar to how `parseLineEndingsWarning` surfaces line-ending changes.

### Proof of Concept
1. Create a repository containing `legacy.txt` encoded in Shift-JIS (or another non-UTF-8 encoding) with distinguishing multi-byte characters.
2. Create two branches that both modify `legacy.txt`, producing a merge conflict.
3. In Desktop, trigger the merge and click "Resolve with Copilot."
4. Observe that `getResolutionDiff`/`reassembleResolvedFile` decode the byte sequences as UTF-8 (`app/src/lib/git/diff.ts:460-463`, `app/src/lib/copilot-conflict-resolution.ts:549-599`), producing replacement characters (`U+FFFD`) or mis-decoded text wherever multi-byte Shift-JIS sequences don't form valid UTF-8.
5. Click "Continue Merge" — `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7258`) writes the mangled string back as UTF-8 bytes, replacing the original Shift-JIS-encoded content, and stages it with `git add`.
6. Commit and push: the corrupted, non-reversible byte content is now part of the permanent git history.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
