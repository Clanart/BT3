Based on my research, the closest structural analog to the reported bug class is a validation gap in the deep-link ("Open in Desktop") branch-name handling path, not a duplicate-distribution/state-monotonicity issue (Desktop has no equivalent "admin distributes twice" state machine). The underlying pattern that matches the report — an attacker-influenced parameter that is consumed by a privileged, state-changing operation without validation strong enough to prevent it from changing the *meaning* of the operation — shows up here.

### Title
Insufficient validation of deep-link `branch` parameter permits git argument/flag injection - (File: `app/src/lib/sanitize-ref-name.ts`)

### Summary
GitHub Desktop's custom protocol handler (`x-github-client://openRepo/...`) accepts a `branch` query parameter that is fully attacker-controlled via a link the victim clicks. The only validation applied is `testForInvalidChars`, whose regex blocks control characters, spaces, and a handful of git-ref-illegal symbols, but does **not** reject values beginning with `-`/`--`. That branch string is later passed as a positional git command argument, creating the same class of defect as the audited report: a state-changing operation trusts an externally supplied value without sufficiently validating it before it reaches a sensitive execution path.

### Finding Description
`parseAppURL` in [1](#0-0)  extracts `branch` from the URL query string and only rejects it if `testForInvalidChars(branch)` returns true. That function is defined in [2](#0-1) , using a regex that excludes hyphens, parentheses, `$`, `;`, and `=` from the "invalid" set — so a value like `--upload-pack=...` passes validation untouched.

The resulting `IOpenRepositoryFromURLAction.branch` flows through `dispatcher.ts`'s `openRepositoryFromUrl` → `openBranchNameFromUrl`, which calls `this.checkoutLocalBranch(repository, branchName)` after cloning/fetching the attacker-referenced repository [3](#0-2) . This mirrors the report's root cause: a function that mutates repository/application state (`checkoutLocalBranch`) consumes an argument (`branchName`) that came from an untrusted, attacker-influenced source without a validation check strong enough to prevent it from being reinterpreted as something other than a plain identifier — analogous to `distributeDividends`'s `date` argument not being checked against prior state before being used to drive state mutation.

### Impact Explanation
If the underlying git invocation for checkout (`app/src/lib/git/checkout.ts`) builds its argument list as `['checkout', branchName, ...]` without a `--` separator before positional arguments (a pattern I was not able to fully confirm within my remaining tool budget — see Likelihood/Uncertainty below), a crafted `branch` value beginning with `-` could be interpreted by git as an option rather than a ref name, enabling argument injection against the git checkout/branch subcommand. Depending on the exact flags reachable this could range from silently checking out an unintended ref (corruption of what the user later commits/pushes) up to more severe outcomes if a dangerous flag (e.g., one accepting a command hook path or template directory) is reachable through this code path.

### Likelihood Explanation
Medium-to-uncertain. The attacker primitive (a link the victim clicks, per the accepted impact scope) is confirmed and requires no local access, admin rights, or prior compromise — parity with the report's "unprivileged/no state validation" theme. However, I was unable to verify, within my remaining tool calls, whether `app/src/lib/git/checkout.ts` / `app/src/lib/git/branch.ts` construct their `git` argument arrays with a `--` separator (which is the standard mitigation and may already be present, in which case this specific path is not exploitable). This is the key open question that determines whether the finding is a confirmed vulnerability or merely a latent/defense-in-depth gap in input validation.

### Recommendation
- Reject or strip leading `-`/`--` sequences in `sanitizedRefName`/`testForInvalidChars` (mirrors the report's short-term fix of validating the untrusted input before it reaches a state-mutating function).
- Audit `app/src/lib/git/checkout.ts` and `app/src/lib/git/branch.ts` to confirm a `--` argument separator is used before all user/ref-derived positional arguments passed to `git`.
- As with the audited report's long-term recommendation, document which deep-link/API-derived fields are "trusted" vs "untrusted" and enforce consistent allow-list validation (e.g., strict git ref-name grammar, disallowing leading dashes) at the single point where `parseAppURL` accepts external input.

### Proof of Concept
1. Attacker crafts a link: `x-github-client://openRepo/https://github.com/attacker/repo?branch=--upload-pack%3Dtouch%2520%2Ftmp%2Fpwned`
2. Victim clicks the link; `parseAppURL` accepts it because `--upload-pack=touch%20/tmp/pwned` contains no character in `testForInvalidChars`'s blocklist [4](#0-3) .
3. `openBranchNameFromUrl` clones/fetches the repo and calls `checkoutLocalBranch(repository, branchName)` with the unsanitized value [5](#0-4) .
4. **Unverified step:** if the git command builder does not insert `--` before the ref argument, git may parse `branchName` as an option rather than a ref, altering checkout behavior. I could not confirm this final step's implementation before running out of tool calls, so this PoC step remains a hypothesis based on the validation gap I did confirm, not a fully demonstrated exploit chain. // See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
