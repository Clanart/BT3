### Title
Scanner credits unspendable/dust outputs because matched parameters (script only) are validated while the value and spendability are not - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in the report is "variable parameters accepted and accounted without integrity checks" — the contract records `amount`/`asset`/`receiver` from unvalidated calldata, inflating recorded deposits and bypassing fees. The Serai analog lives in the Bitcoin wallet's `Scanner`: `scan_transaction`/`scan_block` match an incoming output solely by `script_pubkey` membership in the registered script set, and immediately construct a `ReceivedOutput` carrying whatever `value` the attacker chose. No check is performed that the output is economically spendable (above dust) or otherwise usable. An unprivileged party can send dust-valued outputs to a registered deposit script (external, branch, change, or forward address) and have them reported as received funds.

### Finding Description
`Scanner::scan_transaction` iterates all transaction outputs, looks up `self.scripts.get(&output.script_pubkey)`, and on a match pushes a `ReceivedOutput { offset, output, outpoint }` without inspecting `output.value` or any other field. [1](#0-0)  `scan_block` applies this to every transaction including the coinbase. [2](#0-1)  The only validations in the crate of "does this output correspond to a usable key" happen later: `SignableTransaction::multisig` verifies `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` per input, which detects offset/script mismatches but says nothing about value. [3](#0-2)  The crate defines `DUST = 546` for payments, yet never applies it to received outputs. [4](#0-3)  A 1-sat (or otherwise uneconomical/nonstandard-relayable) output paying to a registered script is therefore credited exactly like a real deposit.

This mirrors the report precisely: a subset of attacker-controlled parameters (`script_pubkey` — the analog of the whitelisted `lendingContract` selector/`asset`) is validated, while the other variable parameters (`value`, outpoint, number of outputs) are folded into the accounting (`Vec<ReceivedOutput>` treated as spendable balance) unchecked.

### Impact Explanation
- Balance inflation / fee erosion: each dust output becomes an input candidate. To spend it, the protocol must pay a per-input fee share (~68+ vbytes for a key-path input) far exceeding its value, so "funds reported received" are not spendable — they are net-negative. An attacker can flood a registered deposit script with dust, causing the wallet to report deposits that either can never be economically consolidated or force the protocol to subsidize their consolidation out of fee budget — the same "protocol absorbs a cost the depositor never paid" shape as fee bypassing.
- Accounting discrepancy: downstream consumers receiving `Vec<ReceivedOutput>` (e.g., crediting user balances by `value()`) cannot distinguish griefing dust from genuine deposits, since the interface exposes `value()` as authoritative. [5](#0-4) 

### Likelihood Explanation
Trivially reachable: any unprivileged party can craft a Bitcoin transaction paying dust to a known/registered P2TR script (deposit addresses are public). No collusion, no key knowledge, and no protocol-internal access is required — the sink is literally "a Bitcoin transaction they send." The only mitigating factor is that downstream consumers may apply their own dust threshold (the out-of-scope processor does check `N::DUST`), but the in-scope `Scanner` itself performs none.

### Recommendation
Apply a minimum-value/spendability filter inside `Scanner::scan_transaction` (and document it), e.g., reject outputs with `value < DUST` or a configurable spendability threshold, so credited `ReceivedOutput`s are guaranteed economically spendable. This is the analog of the report's recommendation to validate all non-static arguments rather than relying on partial matching rules.

### Proof of Concept
1. A `Scanner` is created for an even group key `K` (`Scanner::new`), registering the script `p2tr_script_buf(K)`. [6](#0-5) 
2. Attacker broadcasts a transaction with output `TxOut { value: 1 sat, script_pubkey: p2tr_script_buf(K) }`.
3. `scanner.scan_transaction(&tx)` returns `ReceivedOutput { offset: 0, output: <1-sat TxOut>, outpoint }` — reported as a received deposit despite being unspendable at any fee rate.
4. Including it via `SignableTransaction::new` consumes `input_sat` of 1 sat while adding a full input's weight, so the fee attributable to that input exceeds its value; alternatively the output is simply never spendable and the reported balance is permanently inflated.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
