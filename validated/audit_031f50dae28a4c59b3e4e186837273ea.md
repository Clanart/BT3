### Title
Stale line-selection indices from a whitespace-hidden diff get silently reapplied to a different diff at commit time, corrupting partial commits - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop lets a user hide whitespace-only changes in the Changes view (`hideWhitespaceInChangesDiff`). The line-selection object the user builds while reviewing a diff (`DiffSelection`) stores selected/deselected line positions as *absolute indices into that specific diff's hunk layout*. At commit time, `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff with `getWorkingDirectoryDiff(repository, file)` and no whitespace option, i.e. always `hideWhitespaceInDiff = false`, producing a **different hunk/line layout** than the one the selection indices were computed against whenever the user had "Hide Whitespace Changes" enabled. `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) then blindly calls `file.selection.isSelected(absoluteIndex)` against this new, differently-indexed diff with no recomputation or validation that indices still refer to the same lines — mirroring the audited `Vault.withdraw` bug where a value computed against one state (`_shares`) was reused against a different actual state (`_diff`) without recomputing it.

### Finding Description
- The Changes view loads a diff and, if "Hide Whitespace Changes" is on, computes a diff whose hunks omit/collapse whitespace-only hunks (`getWorkingDirectoryDiff(repository, file, hideWhitespaceInDiff)` in `app/src/lib/git/diff.ts:342-401`, driven by `this.hideWhitespaceInChangesDiff` in `app/src/lib/stores/app-store.ts`, `updateChangesWorkingDirectoryDiff`, `app/src/lib/stores/app-store.ts:3444-3448`). [1](#0-0) 
- The user selects/deselects individual lines using `DiffSelection.withLineSelection`/`withRangeSelection`, which store the choice keyed by the **absolute line index of the diff currently loaded** (`app/src/models/diff/diff-selection.ts:205-231`, `isSelected` at lines 121-136). [2](#0-1) 
- When the user commits, `_commitIncludedChanges` passes the working-directory files (carrying this selection object) straight to `createCommit` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/stores/app-store.ts:3680-3699`, `app/src/lib/git/commit.ts:15-31`, `app/src/lib/git/update-index.ts:163-168`). [3](#0-2) 
- `applyPatchToIndex` re-fetches the diff independently, without the whitespace-hiding option used by the UI: `const diff = await getWorkingDirectoryDiff(repository, file)` (`app/src/lib/git/apply.ts:60`), always defaulting `hideWhitespaceInDiff` to `false`. [4](#0-3) 
- `formatPatch` then walks this freshly fetched (and structurally different) diff and checks `file.selection.isSelected(absoluteIndex)` per line to decide inclusion in the patch (`app/src/lib/patch-formatter.ts:143-171`), with no step that reconciles or recomputes the selection against the new hunk boundaries — there is no equivalent of the recommended "recompute the actual value from current state" fix from the audit report. [5](#0-4) 
- The only place selection is reconciled against a changed diff is `updateChangesWorkingDirectoryDiff`, and it is limited to fixing lines that no longer exist / are no longer includable in the *same* (whitespace-hidden) diff — it never re-derives selection against the un-hidden diff that will actually be used to build the commit patch (`app/src/lib/stores/app-store.ts:3478-3497`). [6](#0-5) 

Because whitespace-only hunks are collapsed/removed under "hide whitespace" but reappear as real, separately-indexed hunks in the full diff, the same absolute index number can point at a semantically different line (or a line belonging to an adjacent, unrelated change) once `applyPatchToIndex` recomputes the diff. This lets a specially crafted file — content authored by whoever controls the cloned/fetched repository, where whitespace-only edits are interleaved tightly with real content changes — cause the user's partial-commit selection to include lines the user never intended to stage, or drop lines the user did intend to stage, without any error or warning.

### Impact Explanation
This is a silent corruption of what the user commits/pushes: content the user did not visually approve for staging can be included in (or excluded from) a commit while the app reports success, matching the exact impact class called out in the report (index/shares mismatch → wrong output despite success). Because commits are later pushed, this can propagate unintended or attacker-influenced content into the remote history without any visible error to the user.

### Likelihood Explanation
The bug is deterministic, not a timing race, whenever "Hide Whitespace Changes" is enabled and the diff contains a mix of whitespace-only and substantive hunks close together — a condition trivially engineered by whoever authors the tracked file content in a cloned/fetched repository (e.g., inconsistent indentation mixed with a small, easy-to-miss content change). The user only needs to do the ordinary, in-app supported action of toggling "Hide Whitespace Changes" and making a partial (line-level) commit selection, both of which are first-class, expected Desktop workflows — no unnatural steps, elevated privileges, or local compromise required.

### Recommendation
- Do not let `applyPatchToIndex`/`stageFiles` fetch a diff independently of the one the selection was built against. Either persist the exact diff (or a stable line-identity mapping, e.g. old/new line numbers rather than positional index) alongside `WorkingDirectoryFileChange.selection`, or force `applyPatchToIndex` to request the diff with the same `hideWhitespaceInDiff` setting the selection was computed with, and recompute/validate the selection against that diff before formatting the patch.
- Prefer selection keyed by stable `(oldLineNumber, newLineNumber)` pairs instead of `unifiedDiffStart`-relative absolute indices, so that a differently-hunked diff cannot silently reinterpret a previously selected index as a different line.
- As a defense-in-depth check, before applying the patch, verify that the total number of includable lines addressed by the stored selection is consistent with the newly fetched diff's includable-line count/content hash, and refuse to stage/commit (surfacing an error) if a mismatch is detected — analogous to the report's recommendation to recompute shares rather than reuse a stale value.

### Proof of Concept
1. Create a repository with a tracked file containing a hunk that mixes whitespace-only changes and one substantive content change in the same region (e.g., a line that only changes trailing whitespace immediately followed by a line with an actual content edit).
2. In Desktop, enable "Hide Whitespace Changes" in the Changes view. The rendered diff will collapse/omit whitespace-only lines, shifting the `unifiedDiffStart`/absolute line indices of subsequent hunks.
3. Partially select only the intended content-change line using the collapsed diff (building a `DiffSelection` whose diverging line indices are relative to the collapsed hunk layout).
4. Click Commit. `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` runs `getWorkingDirectoryDiff` again with `hideWhitespaceInDiff` defaulted to `false` (`app/src/lib/git/apply.ts:60`), yielding the full (non-collapsed) diff with different line indices for the same hunk.
5. `formatPatch` evaluates `file.selection.isSelected(absoluteIndex)` against this new indexing (`app/src/lib/patch-formatter.ts:157`), selecting/deselecting different underlying lines than the ones the user visually chose in step 3.
6. Inspect the resulting commit: it contains a line set that does not match what was highlighted as "selected" in the UI, silently corrupting the partial commit — with no error surfaced to the user.

Note: I was not able to execute this PoC in a live Desktop instance from this environment; the analysis above is based on static tracing of the exact functions/line ranges cited. If a fuller runtime verification is desired (reproducing the exact hunk-index divergence with a concrete whitespace/content-mixed fixture), that would require running Desktop's test harness (`app/test/unit/patch-formatter-test.ts`) with a new whitespace-hiding scenario, which I could not do from static code search alone.
