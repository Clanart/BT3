### Title
Racy `dl_track_new` / `dl_stop_tracking` RPCs allow stale DataLayer singleton records to leak, evading the launcher-dedup guard - (File: chia/data_layer/data_layer_wallet.py)

### Summary
`DataLayerWallet.track_new_launcher_id`/`_track_new_launcher_id` and `stop_tracking_singleton` mutate the same `dl_store` state (`launcher` rows and `singleton_records`) but neither RPC handler acquires `wallet_state_manager.lock` before calling them, unlike other DL/wallet-mutating endpoints in the same file.

### Finding Description
`_track_new_launcher_id` first checks `get_launcher(launcher_id)` to decide whether the launcher was "already processed", then performs network I/O (`get_launcher_coin_state`, `fetch_coin_spend_for_coin_state`), and only afterward writes `add_singleton_record`/`add_launcher` and registers interested puzzle hashes/coin IDs [1](#0-0) . `stop_tracking_singleton` concurrently deletes `singleton_records` and the `launcher` row for the same `launcher_id` [2](#0-1) . The two RPC entry points that trigger these paths, `dl_track_new` and `dl_stop_tracking`, are dispatched with no locking whatsoever [3](#0-2) , in contrast to `create_new_dl`/`dl_update_root` which wrap their mutations in `async with self.service.wallet_state_manager.lock` [4](#0-3) .

Because `_track_new_launcher_id`'s existence check (`get_launcher(...) is not None` at line 222) happens before the awaited network round-trip, an interleaved `stop_tracking_singleton` call that deletes the launcher row in between leaves the tracking coroutine to proceed on stale state: it can re-insert a `singleton_record`/`launcher` row for a launcher that the operator/DataLayer service just intentionally stopped tracking, or it can race the other direction and leave `dl_store` with a `singleton_record` whose `launcher` row was deleted mid-write, reproducing the exact bug class from the CVE: two toggling operations (`track` vs `stop_tracking`) sharing the same tracking structure with no mutual exclusion, so entries get written into slots the other path is concurrently tearing down.

### Impact Explanation
This does not directly move funds, but it corrupts `DataLayerWallet`/`dl_store`'s bookkeeping of owned/tracked singletons, which downstream drives `get_owned_singletons()`, offer creation for DataLayer proofs, and mirror/root update spends. A stale or duplicated `singleton_record`/`launcher` entry can cause `create_update_state_spend` or offer-settlement code to act on the wrong lineage tip, and in the DataLayer offer flow this determines what root gets asserted/spent. Given the restricted scope (local RPC caller only, no direct fund-forging path proven), this is best characterized as a Medium-severity local wallet-state-corruption issue rather than a High-severity unauthorized coin movement — I could not trace a concrete unsigned-spend or asset-forgery outcome from this race within the available context.

### Likelihood Explanation
Triggering requires two RPC calls (`dl_track_new` and `dl_stop_tracking` for the same `launcher_id`) issued concurrently by the local DataLayer service/RPC caller. This is a locally-reachable RPC race (DataLayer service is expected to call these back-to-back during subscribe/unsubscribe cycles per `chia/_tests/core/data_layer/test_data_rpc.py:4306-4372`), so likelihood is plausible under normal operational conditions (e.g., rapid subscribe/unsubscribe or resync racing a manual stop-tracking call), though it needs specific timing to land inside the unlocked window.

### Recommendation
Wrap `dl_track_new` and `dl_stop_tracking` (and any other `dl_store`-mutating DL RPCs that currently lack it) in `async with self.service.wallet_state_manager.lock`, matching the pattern already used by `create_new_dl` and `dl_update_root`, so that tracking and untracking of the same launcher ID are mutually exclusive.

### Proof of Concept
Not independently reproduced in this analysis — the finding is based on static code-path review of `chia/wallet/wallet_rpc_api.py:3130-3148` and `chia/data_layer/data_layer_wallet.py:214-294` and `:872-874`, showing the absence of the lock present on neighboring endpoints; I was unable to execute a live concurrency test to confirm the exact corrupted end-state within this session.

    async def dl_track_new(self, request: DLTrackNew) -> Empty:
        """Initialize the DataLayer Wallet (only one can exist)"""
        if self.service.wallet_state_manager is None:
            raise ValueError("The wallet service is not currently initialized")

        await (await self.service.wallet_state_manager.get_dl_wallet(create_if_not_found=True)).track_new_launcher_id(
            request.launcher_id
        )

        return Empty()

    async def dl_stop_tracking(self, request: DLStopTracking) -> Empty:
        """Initialize the DataLayer Wallet (only one can exist)"""
        if self.service.wallet_state_manager is None:
            raise ValueError("The wallet service is not currently initialized")

        dl_wallet = await self.service.wallet_state_manager.get_dl_wallet()
        await dl_wallet.stop_tracking_singleton(request.launcher_id)
        return Empty()
