## Analysis

The Sherlock finding's core issue is: a value (price) is read from state at execution time that differs from the value the user reviewed when deciding to act, with no mechanism to verify the state hasn't changed and no way to bound acceptable deviation. The closest structural analog in GitHub Desktop is the partial-commit ("select lines to stage") flow, where the user's line selection is computed against one diff snapshot, but the actual patch applied to the index is generated from a second, independently-fetched diff snapshot taken later — with no check that the two match.

### Title
Partial commit staging re-diffs the working tree at apply-time and blindly replays the user's stale line-selection indices, silently staging/committing unreviewed content - ([File: app/src/lib/git/apply.ts])

### Summary
When a user stages only some lines of a modified file, Desktop stores line selection as absolute indices into a specific diff object that was rendered to the user. When the commit is actually executed, `stageFiles` → `applyPatchToIndex` re-runs `git diff` against the *current* working tree to build a fresh diff, then reuses the old selection object (by index, not content) to build the patch via `formatPatch`. If the tracked file's content on disk changes between the moment the user reviewed/selected lines and the moment "Commit" is processed, the committed patch is derived from content the user never saw.

### Finding Description
The staging pipeline is:

1. UI renders a diff and lets the user pick lines: `getWorkingDirectoryDiff` is called once to produce hunks, and the user's choices are recorded as absolute line indices in a `DiffSelection` attached to the `WorkingDirectoryFileChange`. [1](#0-0) 
2. The app does try to reconcile stale selections against a newer diff, but only inside `updateChangesWorkingDirectoryDiff`, which is triggered by status refreshes (e.g., file-watcher events) and is explicitly documented as best-effort: "The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines." [2](#0-1) 
3. When the user clicks Commit, `_commitIncludedChanges` reads whatever `WorkingDirectoryFileChange[]` objects currently sit in the cached `changesState.workingDirectory.files` — with no fresh `getStatus`/diff-equality check — and passes them straight into `createCommit`. [3](#0-2) 
4. `createCommit` unstages everything and calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex`. [4](#0-3) [5](#0-4) 
5. `applyPatchToIndex` independently re-fetches the diff from disk *at this moment* (a second, separate `git diff` invocation, unrelated to whatever diff object the UI had cached) and then calls `formatPatch(file, diff)` using the **old** `file.selection` object against this **new** diff's line indices. [6](#0-5) 
6. `formatPatch` decides what to include purely via `file.selection.isSelected(absoluteIndex)` against the hunks of whatever diff was passed in — it has no way to know that diff is not the one the indices were computed against. [7](#0-6) 
7. The resulting patch is applied with `git apply --cached --unidiff-zero`, i.e., zero-context patch application directly against the index. [8](#0-7) 

There is no code path that aborts, warns, or re-validates selection integrity between step 3 and step 5. The only staleness guard that exists (`updateChangesWorkingDirectoryDiff`) is asynchronous, best-effort, and not on the commit critical path — it depends on a status refresh having already landed by the time the user presses commit.

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits bug class. If the working tree file changes between the time the user reviews a diff and selects lines and the time the commit actually executes (the commit path itself performs multiple sequential git invocations — `unstageAll`, `stageFiles` for normal files, then `applyPatchToIndex` per partially selected file — introducing a real window), the final commit can:
- include lines the user explicitly deselected (and never reviewed), or
- exclude lines the user explicitly selected, or
- in edge cases, fail to construct a coherent patch (index corruption/aborted commit).

Because the attacker's/external actor's write to the tracked file only needs to land within this window (which can be widened by anything that keeps the app busy — hook execution, large repos, background fetches, or the user simply taking time between reviewing a large diff and pressing commit), a repository that ships a build tool, watch-mode dev server, editor plugin, or any auto-run tooling that rewrites tracked files can cause Desktop users to commit/push content they never reviewed, without any error or warning surfaced by the app.

### Likelihood Explanation
Moderate-to-low but realistic: it requires something to modify a tracked file on disk in the small window between the last diff render and the commit's internal `applyPatchToIndex` re-diff. This is plausible in ordinary developer workflows (auto-formatters/linters running via editor-on-save, file watchers, generated files, npm/yarn scripts) bundled by a malicious/compromised repository, without requiring any privileged access, malware, or unusual user action beyond normal "open repo in Desktop + edit/format + commit."

### Recommendation
- In `_commitIncludedChanges`/`createCommit`, capture (or re-verify) a content hash/diff fingerprint for each partially-selected file at selection time, and re-validate it immediately before `applyPatchToIndex` executes; abort or re-prompt the user if it has changed.
- In `applyPatchToIndex`, avoid re-fetching a brand-new diff independent from the one the selection indices were derived from — thread the originally-rendered diff (or its hash) through, and fail loudly if it no longer matches the current working tree state, rather than silently reusing stale indices against new hunk content.

### Proof of Concept
1. Open a repository in Desktop and modify `file.txt`, producing a 2-hunk diff.
2. In the Changes view, select only hunk 1 for commit (deselect hunk 2), matching the flow exercised in the existing partial-commit unit tests. [9](#0-8) 
3. Before Desktop's commit pipeline reaches `applyPatchToIndex`, have an external process (e.g., a `postinstall`/watch script shipped in the repo, or an editor auto-format-on-save triggered by opening the file) rewrite `file.txt` so the line/hunk layout shifts (e.g., inserts lines above hunk 1, shifting what indices correspond to).
4. Click Commit. `applyPatchToIndex` re-runs `getWorkingDirectoryDiff` against the now-modified file and calls `formatPatch` using the original `DiffSelection` indices computed against the pre-modification diff.
5. Inspect the resulting commit with `git show`: the staged/committed hunk no longer corresponds to the lines the user visually selected in step 2 — content the user never saw or approved is now part of the commit (or the intended content is missing), with no error or warning from Desktop.
