Based on my investigation, I found a strong, verifiable analog. The core broken invariant in the DeFi report — "a value is computed at time T1, an attacker-influenced action happens, then the code proceeds at T2 using a payment/loss decision derived from the T1 value without re-validating it against the changed state" — maps directly onto how GitHub Desktop's **discard-selection** flow trusts a caller-supplied, stale `diff` object when generating a destructive patch.

### Title
Stale-diff trust in `discardChangesFromSelection` allows silent corruption/loss of working-directory content on refresh race - ([File: app/src/lib/git/apply.ts])

### Summary
`discardChangesFromSelection()` in [1](#0-0)  builds a reverse-apply patch purely from a `diff` object and `DiffSelection` line indices that are handed to it by the caller, without ever re-fetching or validating the diff against the current on-disk content immediately before applying it. `DiffSelection.isSelected()` only knows about integer line offsets (`absoluteIndex`), not content [2](#0-1) , so `formatPatchToDiscardChanges()` blindly maps those offsets onto whatever hunk lines exist in the passed-in `diff` [3](#0-2) .

### Finding Description
The UI/dispatcher path that leads here explicitly documents the staleness risk but does nothing to close it:
- `SideBySideDiffRow`'s discard handler comments that it passes "the original diff (from props) instead of the (potentially) expanded one" [4](#0-3) .
- `Changes.onDiscardChanges` forwards that same `diff`/`selection` pair straight to the dispatcher, optionally through a confirmation dialog [5](#0-4) , and the confirmation dialog (`DiscardSelection`) stores the diff in component state and only invokes the discard once the user clicks the button — an interval during which the file can change on disk [6](#0-5) .
- `_discardChangesFromSelection` in `AppStore` and `GitStore.discardChangesFromSelection` pass the diff through unchanged all the way to `git apply` [7](#0-6) [8](#0-7) .
- `discardChangesFromSelection()` itself never calls `getWorkingDirectoryDiff` again; it trusts the caller's diff completely [1](#0-0) .

Separately, Desktop's own live-diff-refresh logic (`updateChangesWorkingDirectoryDiff`) proves that the working-directory diff for a selected file *is* expected to change asynchronously and that stale selection state must be revalidated — it explicitly recomputes `selectableLines` after a new diff load and notes "the diff might have changed dramatically since last we loaded it" [9](#0-8) . This safeguard exists for the *committing* selection UI, but **no equivalent revalidation exists on the discard path** before `git apply` is invoked with the stale patch.

This is structurally identical to the report's flaw: the CreditFacade computed `totalValue` before an attacker-controlled action (`_multicall`) altered state, then used the stale value to decide the outcome (loss vs. payment) without re-checking. Here, Desktop computes a `diff`/line-selection before a race window (dialog confirmation delay, or an attacker/tool-driven change to the file such as a `git-lfs` smudge/clean rewrite, an editor autosave, or another concurrent Desktop-triggered git operation touching the same working tree), then applies a reverse patch built from the stale hunk offsets without re-checking that the file's content still matches — `git apply` will happily apply a positional patch to content it no longer describes if line counts/context still loosely align, or fail in a way that leaves partial changes.

### Impact Explanation
If the on-disk content shifts between diff-load time and the moment `discardChangesFromSelection` calls `git apply`, the reverse patch is built from `absoluteIndex` positions in a diff that no longer matches the file. Because `git apply --unidiff-zero --whitespace=nowarn` is used (zero-context, non-strict), the patch can succeed against unrelated lines, silently discarding or reintroducing content the user never selected — this is precisely the "silent corruption of what the user commits" impact category. In the worst case the user loses new, valuable working-directory edits with no explicit signal that a different region of the file was affected, since `git apply` applying "successfully" gives no on-screen diff-of-diff confirmation.

### Likelihood Explanation
The confirmation-dialog window (`DiscardSelection`) is an explicit, common user-facing delay where file content can change — the code comment on `side-by-side-diff.tsx` line 1604 acknowledges the diff can already be stale ("the (potentially) expanded one") even before the dialog is shown. Any file-system-level change during that window (auto-formatting tools, git-lfs smudge/clean triggered by an attribute change from a fetched branch, editor autosave) reaches this exact code path without any additional guard. However, I could not verify from the indexed code whether `git apply`'s own context validation would reject most such stale patches outright (which would reduce likelihood to failure/DoS rather than silent corruption) — that requires exercising the exact hunk/line-count interactions in `git apply`, which is not observable from static review alone.

### Recommendation
Before invoking `git apply` in `discardChangesFromSelection`, re-fetch the current working-directory diff for the file and verify that the hashes/line content backing the caller-supplied `selection` still match the fresh diff (similar to the `selectableLines` revalidation already performed for the commit-selection path in `app-store.ts`). If they don't match, abort and force the UI to reload the diff and selection before allowing a discard, rather than trusting the positional patch built from a potentially stale diff object.

### Proof of Concept
1. Modify a tracked file and open it in the Changes view so Desktop loads its diff and the user selects several lines to discard.
2. Trigger the "Confirm Discard Changes" dialog (default setting).
3. While the dialog is open (or in the same tick before submit resolves), have an external process/tool modify the same file on disk (e.g., an editor autosave, or a `.gitattributes`-driven filter such as `git-lfs` smudge/clean triggered by another Desktop git operation touching the same file) so its line offsets shift but git still sees it as "Modified".
4. Click "Discard Changes." `DiscardSelection.discard` sends the original (stale) `this.props.diff`/`this.props.selection` straight to `dispatcher.discardChangesFromSelection` [6](#0-5) , which flows unchanged into `git apply` [1](#0-0) .
5. Inspect the file afterward: because `--unidiff-zero --whitespace=nowarn` is used, the reverse-patch is applied against stale positional offsets, producing content different from what the user intended to keep — silently reverting or destroying edits the user never selected for discard.

**Caveat**: I was not able to execute `git apply` locally to confirm the exact failure/silent-success behavior for a given magnitude of drift, and the index does not include a runnable environment for empirical confirmation; the analysis above is based on static code-path tracing showing the missing revalidation, matching the report's TOCTOU bug class exactly.

export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })
