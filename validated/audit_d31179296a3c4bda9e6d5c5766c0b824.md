### Title
Unrestricted-scheme `shell.openExternal` on attacker-controlled GitHub API URLs enables non-http(s) protocol handler invocation - (File: app/src/ui/lib/link-button.tsx)

### Summary
Multiple UI surfaces (`LinkButton`, `AppStore._openInBrowser`, and the `open-external` IPC handler) pass URLs originating from GitHub API objects (PR comments, reviews, check runs) directly to Electron's `shell.openExternal` without validating the URL scheme is `http:`/`https:`.

### Finding Description
The `receive()`-less-contract bug pattern here is: the code has exactly one intended "safe" entry gate for opening links, but a second, unguarded path exists that bypasses it. `app/src/ui/lib/sandboxed-markdown.tsx` correctly gates markdown-embedded links with `/^https?:/.test(a.protocol)` before invoking `onMarkdownLinkClicked` [1](#0-0) . However, `LinkButton.onClick` calls `shell.openExternal(uri)` unconditionally for any `uri` prop, with no such check [2](#0-1) . `LinkButton` is fed `comment.html_url`, a field taken verbatim from the GitHub API's `IAPIComment` object, in `pull-request-comment.tsx` [3](#0-2) . The same unguarded pattern exists in the main-process `open-external` handler, where the `http/https` prefix check only controls a `log.info` call and does not prevent `shell.openExternal(path)` from running on any other scheme [4](#0-3) , and in `AppStore._openInBrowser`, which has no validation at all [5](#0-4) .

Because `html_url` and similar fields on PR comments, reviews, and check-run objects are populated by the GitHub API (or GitHub Enterprise, which a user can point Desktop at), an attacker able to influence PR metadata — e.g., a malicious collaborator, a compromised/malicious Enterprise API endpoint, or a check-run app — can supply a non-`https` URL. Electron's `shell.openExternal` on Windows dispatches to arbitrary registered URL protocol handlers, some of which are known to accept dangerous parameters (e.g., `search-ms:`, custom app URI schemes with command-injection-capable arguments), providing execution outside the sandboxed renderer.

### Impact Explanation
If a crafted URL reaches `shell.openExternal` via an unguarded path such as `LinkButton`, it can invoke arbitrary installed protocol handlers on the user's OS with attacker-chosen parameters. Depending on the OS and installed handlers, this can range from launching unexpected local applications to code execution or credential prompts, satisfying "code execution ... outside the repo" from an attacker-controlled GitHub API object.

### Likelihood Explanation
Medium: it requires the user to click a link in Desktop's PR-comment/review/check dialogs, and the attacker needs to control PR/comment metadata returned by the API (achievable by any commenter on a public repo, or by a malicious Enterprise server). No local access, malware, or leaked credentials are required — this matches the "link the user clicks" / "GitHub API object" valid-impact categories.

### Recommendation
Enforce `https:`/`http:` scheme validation (matching the check already used in `sandboxed-markdown.tsx`'s `setupLinkInterceptor`) at the single choke point before any call reaches `shell.openExternal` — ideally inside the `open-external` IPC handler in `app/src/main-process/main.ts`, so all call sites (`LinkButton`, `AppStore._openInBrowser`, etc.) are protected uniformly rather than relying on each caller to sanitize independently.

### Proof of Concept
1. As a GitHub collaborator (or via a malicious/compromised GHE instance), post a PR review comment whose `html_url` (or equivalent API field) is not an `https://` URL but instead a Windows-registered protocol URI with malicious parameters (e.g. `search-ms:query=...&crumb=location:\\attacker-share`).
2. The victim opens the PR comment/review dialog in GitHub Desktop, which renders `LinkButton uri={comment.html_url}` at `app/src/ui/notifications/pull-request-comment.tsx:128`.
3. The victim clicks "Open in Browser."
4. `LinkButton.onClick` calls `shell.openExternal(uri)` unconditionally at `app/src/ui/lib/link-button.tsx:85`, invoking the attacker-chosen protocol handler with attacker-controlled arguments instead of a browser navigation.

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
