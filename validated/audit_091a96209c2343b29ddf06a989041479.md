### Title
Conflict-marker parser can be defeated by attacker-supplied lines that mimic markers, corrupting AI-assisted merge-conflict resolution and the file that gets committed - ([File: app/src/lib/copilot-conflict-context.ts])

### Summary
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` parses Git's conflict-marker text by doing a simple, unescaped linear scan for the next line that matches `oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker`. It implicitly assumes that the *first* line matching one of these fixed regexes after a given marker is always the *structurally correct* boundary of the conflict hunk. That assumption breaks the moment the content on either side of the conflict (which is attacker-controlled, e.g. a branch from a fork the victim merges/rebases/cherry-picks) contains a line that happens to match one of these regexes as ordinary text (seven `<`, `|`, `=`, or `>` characters, optionally followed by whitespace). This is exactly the same bug class as the Sherlock finding: a boundary/last-element calculation that is correct for the "regular" case but silently wrong for "irregular" input, and nothing downstream detects or guards against the mismatch.

### Finding Description [1](#0-0) 

`extractConflictHunks` walks the file line-by-line:
- After the `<<<<<<<` marker it collects "ours" lines until the first `|||||||` or `=======`.
- It then collects "theirs" lines until the first `>>>>>>>`. [2](#0-1) 

Nothing in this loop verifies that the encountered marker line actually belongs to *this* hunk (e.g. by checking a matching branch label, marker count, or re-validating against the real merge output). If the "theirs" side (fully attacker controlled content coming from a merged/fetched branch) contains a line that is exactly `>>>>>>>` (optionally with trailing text/space) as legitimate file content — plausible in changelogs, blockquoted diffs, ASCII banners, or simply crafted adversarially — the scan stops there:
- `theirsLines` is truncated before the real end of the attacker's content.
- `hunkEnd` is set to the *fake* marker's line index.
- The real closing `>>>>>>> branch-name` marker that Git actually wrote is left further down in `lines`, but the outer `while` loop only looks for a *new* `<<<<<<<` to start the next hunk, so that leftover real marker line (and any of the attacker's remaining content up to it) is never recognized as part of the conflict region — it just falls through as ordinary "context" text.

This corrupted `oursContent`/`theirsContent`/`hunkEnd` is what gets:
1. Sent to the Copilot model as the definitive "ours"/"theirs" content for the hunk (`formatConflictContextForPrompt`, [3](#0-2) ), so the model resolves a conflict based on truncated/misattributed content.
2. Used as the hunk boundary (`markerStart`…`hunkEnd`) for splicing the model's resolution back into `rawContent` to produce the file that is written to disk, per the documented intent of `rawContent`: “Used after the model responds to reassemble the resolved file by splicing per-hunk resolutions into the original content.” [4](#0-3) 

Because the splice range is computed from the same broken boundary, the reconstructed file can end up containing left-over, never-reviewed attacker content (including the genuine trailing marker text) that was excluded from both the AI's input and the region actually replaced.

### Impact Explanation
An attacker who only controls a branch/fork that the victim fetches and merges (no local access, no credentials, no social engineering beyond "please merge my PR/branch") can shape ordinary-looking file content to desynchronize the conflict-hunk parser from Git's real marker structure. The consequence is that:
- The AI-assisted resolution is computed from content that does not match what Git actually produced, and
- The file ultimately spliced back to disk after resolution can silently retain attacker content (or stray marker text) that the user never saw or approved in the resolution UI.

Since this is the exact mechanism producing the file that gets `git add`/committed/pushed after conflict resolution, this is a silent corruption of what the user commits, matching the accepted impact category.

### Likelihood Explanation
Requires only that the victim merge, rebase, or cherry-pick a branch/PR containing crafted content and then use the Copilot-assisted conflict resolution feature on the resulting conflicts. No unusual UI steps beyond the normal merge-conflict-resolution flow are needed, and the marker regexes (`^<{7}`, `^\|{7}`, `^={7}`, `^>{7}`) are narrow enough to be reliably reproduced by an attacker crafting file content, and even accidentally triggerable by legitimate content containing 7-character runs of these symbols (e.g. Markdown separators, ASCII art, changelogs).

### Recommendation
Do not rely on "next line matching the marker regex" as ground truth for hunk boundaries. Instead:
- Derive hunk boundaries from a single pass that pairs markers strictly in the expected `<<<<<<<` → (`|||||||`) → `=======` → `>>>>>>>` sequence while validating the *marker character count/consistency* Git actually used for that merge (Git supports variable marker length via `merge.conflictStyle`/`--marker-size`), rejecting or re-scanning if a run-length mismatch is detected.
- Alternatively, obtain the authoritative hunk boundaries from `git`'s own machinery (e.g. `git merge-file`/`ls-files -u` blobs diffed against the working tree) rather than re-parsing raw marker text with regexes, since Git already knows exactly where each marker belongs.
- When splicing the model's resolution back into `rawContent`, re-validate that the byte range being replaced still starts/ends with the exact marker lines originally detected, and abort (falling back to manual resolution) if the file changed shape between extraction and splice or if any ambiguity in marker attribution was detected during parsing.

### Proof of Concept
1. Attacker opens a PR/branch where a file (e.g. `NOTES.md`) is modified to include this literal line as legitimate content: `>>>>>>>` (7 `>` characters).
2. Victim's own branch modifies a *different* line in the same file, guaranteeing a real merge conflict when merging the attacker's branch.
3. Victim merges the attacker's branch; Git writes standard conflict markers, e.g.:
   ```
   <<<<<<< HEAD
   victim's line
   =======
   attacker's line 1
   >>>>>>>
   attacker's real trailing line
   >>>>>>> feature/attacker-branch
   ```
   (the middle `>>>>>>>` here is attacker's own file content, not a real Git marker; the last `>>>>>>> feature/attacker-branch` is the real one Git generated.)
4. Victim opens the Copilot conflict-resolution dialog. `extractConflictHunks` stops "theirs" collection at the fake `>>>>>>>` line, setting `hunkEnd` there. `theirsContent` sent to the model is `attacker's line 1` only — "attacker's real trailing line" and the real closing marker are excluded from the hunk and effectively invisible to both the reviewer and the model.
5. After the model returns a resolution and it is spliced back using the computed (wrong) `markerStart`/`hunkEnd` range, "attacker's real trailing line" (never reviewed, never sent to the model) remains verbatim in the resulting file, which the victim then commits/pushes without ever having seen it flagged as part of the conflict.

 * an enormous single line to the model.
