## Finding

### Title
Copilot conflict reassembly misidentifies conflict-block boundaries when hunk content contains marker-like text, silently corrupting the committed file - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot-assisted merge/rebase conflict resolution splices AI-generated per-hunk resolutions back into the original file using `reassembleResolvedFile`, which locates conflict-marker boundaries with simple line-pattern regexes and *positional* (ordinal) matching rather than verifying the located boundaries are the genuine conflict delimiters. When the conflicting region of a file (the "ours"/"theirs" text between the real `<<<<<<<` and `>>>>>>>` markers) itself contains a line that matches the closing-marker pattern (`^>{7}(?:\s|$)`), the boundary-detection loop stops at that look-alike line instead of the real terminator, mis-splicing the model's resolution and leaving genuine conflict content corrupted or partially replaced — all without any error surfaced to the user, who then commits and pushes the corrupted result.

### Finding Description
`reassembleResolvedFile` walks the raw on-disk file line by line, using three regexes to find conflict blocks: [1](#0-0) 

For each `<<<<<<<` line it finds, it looks ahead for a `=======` and then the *first* line matching `>{7}` to treat as the closing marker: [2](#0-1) 

Critically, the search takes the **first** line matching `reassemblyTheirsMarker` as `closingIndex` and breaks immediately — it does not verify this line is actually the terminator of the specific conflict block versus a coincidental marker-like line embedded in the "ours" or "theirs" content itself (e.g., a documentation file, YAML/markdown/tutorial content, or CI config that legitimately contains a line of 7+ `>` characters). If such a line appears between the real `<<<<<<<` and the real `=======`, the loop concludes `hasSeparator === false` (since it broke before ever reaching the true separator) and takes the "malformed marker" branch, copying only the opening `<<<<<<<` line through as plain content and resuming the scan from `i++`. From that point on:
- The genuine `=======` and `>>>>>>>` lines of the real conflict are no longer recognized as markers (they don't match `reassemblyOursMarker`), so they are copied through verbatim into the "resolved" file as leftover raw conflict-marker text.
- The `hunkIndex` counter used to pick which model-provided resolution (`hunkResolutions[hunkIndex]`) gets spliced into the *next* real conflict block is now off — it was never incremented for the corrupted block, so the model's resolution intended for conflict N gets applied to conflict N+1 (or is dropped/duplicated), because matching is deliberately done "by order, not by line number": [3](#0-2) [4](#0-3) 

The upstream validation step, `parseCopilotConflictResolution`, only rejects a hunk's `resolvedContent` if it contains *both* an ours-marker pattern **and** a separator pattern together in the same string: [5](#0-4) 
This check operates on the model's *output*, not on the *original raw file content* being reassembled, so it does nothing to prevent the raw-content mis-boundary condition described above. Likewise `validateResolutionPaths` only checks that the *count* of hunks returned by the model matches the *count* of hunks the context-gathering step originally parsed out of the file — it does not, and cannot, detect that `reassembleResolvedFile`'s independent line-scanning logic will misidentify a boundary at reassembly time: [6](#0-5) 

### Impact Explanation
This breaks the invariant "the file the user reviews and commits is either the model's intended resolution or clearly still marked as conflicted." Instead, the reassembled file can contain a mix of stray raw `=======`/`>>>>>>>` marker lines, misplaced hunk resolutions (right content, wrong location), or dropped/duplicated code — silently, since no error is thrown and the dialog reports success. Because Desktop writes this file to disk and the user then stages/commits/pushes it as the merge/rebase resolution, this matches the "silent corruption of what the user commits or pushes" impact class directly. In the worst case, security-relevant code from one side of the merge could be silently dropped or displaced into the wrong function, entirely unreviewed since the diff the user sees is presented as an already-resolved, marker-free file.

### Likelihood Explanation
The trigger only requires that a conflicted file's changed region contain, anywhere in its text, a line of 7+ consecutive `>` characters (optionally followed by whitespace) — e.g., in a markdown/doc file describing Git conflict syntax, a changelog quoting a conflict example, a diff/patch fixture, an ASCII-art banner, or a template with a `>>>>>>>` delimiter convention. Such content is common in real repositories (docs about Git itself, CI/tutorial fixtures, generated diff snippets) and is entirely attacker-controlled: an attacker who can get a PR/branch merged or fetched into the user's repository controls the exact text that ends up on one side of a future conflict. The user only needs to invoke the built-in "Resolve with Copilot" feature on a conflict touching that file — a normal, expected user action, not an unnatural step. No local access, elevated privileges, or pre-existing compromise is required.

### Recommendation
- Make marker detection in `reassembleResolvedFile` robust against embedded look-alike lines: require the closing `>>>>>>>` search to stop at the *first* `=======` only if no intervening `<<<<<<<`/`>>>>>>>` was already consumed, or better, reuse the exact same conflict-block indices computed during context gathering (`copilot-conflict-context.ts`) instead of re-deriving them independently at reassembly time, so both stages agree on identical byte/line offsets.
- After reassembly, re-scan the output for any remaining lines matching the conflict-marker regexes and treat their presence as a hard failure (surface an error / fall back to manual resolution) rather than silently shipping a file with leftover or misapplied conflict content.
- Add a post-reassembly sanity check that the number of consumed real conflict blocks equals `hunkResolutions.length` exactly, and abort the automatic write if not.

### Proof of Concept
1. Create a repository where two branches modify the same file such that the conflicting region includes a line with 7+ `>` characters as literal content, e.g.:
```
<<<<<<< HEAD
some real code
Example of a conflict marker: >>>>>>>>>> (documentation text)
=======
their real code
>>>>>>> branch
```
2. Trigger a merge/rebase in Desktop that produces this conflict, then invoke Desktop's Copilot conflict-resolution feature.
3. The model returns a well-formed `resolvedContent` for this single hunk (containing neither a genuine ours-marker+separator pair, so it passes `parseCopilotConflictResolution`'s check at `app/src/lib/copilot-conflict-resolution.ts:444-448`).
4. In `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:560-591`), the inner lookahead loop encounters the literal `>>>>>>>>>>` line before the real `=======`/`>>>>>>> branch` lines, sets `closingIndex` to that line, and — having set `hasSeparator = false` — takes the malformed-marker branch, copying only the `<<<<<<<` line through and resuming the outer scan mid-conflict.
5. The genuine `=======` and `>>>>>>> branch` lines are then copied through verbatim as plain text into the "resolved" file, and the model's actual resolution is spliced at the wrong position (or dropped), producing a corrupted file that Desktop presents as fully resolved and that the user commits/pushes without any warning.
