### Title
`multiclaimSpec`/`multiclaimFor` silently no-op reward payouts for pools using legacy `BaseRewardPool.getRewards` while still updating MGP accounting - ([File: rewards/MasterMagpie.sol], [File: rewards/BaseRewardPool.sol])

### Summary
`MasterMagpie._claimBaseRewarder` calls `rewarder.getRewards(_account, _receiver, _rewardTokens)` whenever a caller supplies a non-empty `_rewardTokens` array via `multiclaimSpec`/`multiclaimFor`. For pools whose `PoolInfo.rewarder` is the legacy `BaseRewardPool` (not `BaseRewardPoolV2`), `getRewards` has an empty function body, so the call is a silent no-op that transfers nothing and updates no reward-per-token state, while the surrounding MGP-reward bookkeeping in `_multiClaim` still executes unconditionally.

### Finding Description
`_claimBaseRewarder` branches on `_rewardTokens.length`: [1](#0-0) 

When `_rewardTokens.length > 0`, it calls `rewarder.getRewards(...)`. In `BaseRewardPool.sol` (the legacy/V1 implementation), that function is declared but has an empty body — no `onlyMasterMagpie` check even runs any logic, no `_sendReward`, no `userRewards` reset, no event: [2](#0-1) 

Compare this to the correctly implemented `BaseRewardPoolV2.getRewards`, which is gated by `onlyMasterMagpie`/`updateRewards` and actually calls `_sendReward` for each requested token: [3](#0-2) 

Crucially, `_multiClaim` in `MasterMagpie.sol` updates `unClaimedMgp` and `user.rewardDebt` (MGP-side accounting) unconditionally, before invoking `_claimBaseRewarder`, and does not check the return value or any success signal from the rewarder call: [4](#0-3) 

Because `IBaseRewardPool.getRewards` (V1) has no revert path and simply does nothing, an unprivileged caller invoking `multiclaimSpec`/`multiclaimFor` with a real, non-empty `_rewardTokens` array against a pool backed by the legacy `BaseRewardPool` will:
1. Have their MGP portion of rewards processed and paid normally (unaffected).
2. Have their bonus/base-rewarder tokens silently skipped — no transfer, no state update, no revert, no event.
3. Believe the claim succeeded (transaction returns success) while `userRewards`/`rewardPerToken` state for that account remains untouched, since the no-op body never runs `_updateFor`/`updateReward`.

The only working path for recovering the bonus reward is calling `getReward` (no `s`, no token filter) via `multiclaim(_stakingTokens)` (empty `_rewardTokens[]` triggers the `else` branch in `_claimBaseRewarder`, which calls `rewarder.getReward(_account, _receiver)` — the fully implemented function in V1). Until the user (or anyone) makes that different call, the reward is inaccessible through the "specify tokens" entrypoints.

### Impact Explanation
This matches "funds frozen for at least 24 hours" under the Immunefi impact classes: legitimate bonus-reward tokens accrued in a legacy `BaseRewardPool`-backed pool cannot be retrieved via `multiclaimSpec`/`multiclaimFor` even though the call succeeds and the user reasonably assumes the reward was paid. Recovery is possible only via a different, non-obvious call path (`multiclaim`/`getReward` with an empty reward-token array), and only if the user or integrators are aware of this discrepancy — otherwise the funds remain claimable-but-unclaimed indefinitely from the perspective of anyone relying on the "spec" entrypoints.

### Likelihood Explanation
No special privilege is required — any staker of a pool whose `rewarder` is the legacy `BaseRewardPool` can trigger this simply by calling `multiclaimSpec`/`multiclaimFor` with a non-empty reward-token list, which is a completely normal, expected usage pattern documented by the function's own purpose ("Claims for each of the pools with specified rewards to claim for each pool"). No capital or complex setup is needed; the bug reproduces every time this entrypoint is used against a V1-rewarder pool.

Note: I could not fully confirm from the indexed code whether any currently-active production pool still has its `PoolInfo.rewarder` pointed at the legacy `BaseRewardPool` contract as opposed to `BaseRewardPoolV2` (deployment/wiring logic in `WombatStaking.sol`/pool-helper contracts references `BaseRewardPool` but the exact current pool configuration wasn't fully traceable within available tool budget). If such a pool exists or is re-introduced (e.g., via a future pool registration reusing the legacy contract), this bug is fully live.

### Recommendation
Remove or properly implement `BaseRewardPool.getRewards` to match `BaseRewardPoolV2.getRewards` (apply `onlyMasterMagpie`, `updateRewards`, and actually iterate `_rewardTokens` to call `_sendReward`), or have `_claimBaseRewarder` revert/fallback safely when the rewarder does not support token-specific claims (e.g., via an interface capability check or by deprecating/migrating all pools off the legacy `BaseRewardPool` before exposing `multiclaimSpec`/`multiclaimFor`).

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, a staking token, and a legacy `BaseRewardPool` (not V2) as `pool.rewarder` for that staking token; register the pool.
2. Fund the `BaseRewardPool` with a bonus reward token via `queueNewRewards` and have an attacker stake into the pool so `earned(attacker, bonusToken) > 0`.
3. Call `masterMagpie.multiclaimSpec([stakingToken], [[bonusToken]])` from the attacker.
4. Assert: (a) the call does not revert, (b) `IERC20(bonusToken).balanceOf(attacker)` is unchanged before/after, (c) `BaseRewardPool.earned(attacker, bonusToken)` is unchanged (proving no internal accounting reset occurred), while (d) any MGP-side `unClaimedMgp`/`rewardDebt` state was updated as if the claim succeeded.
5. Contrast by calling `masterMagpie.multiclaim([stakingToken])` (empty reward-token array) and show the bonus token is now correctly transferred via the `getReward` path, confirming the specific-token entrypoint is broken while the full-claim entrypoint works.

    function _claimBaseRewarder(address _stakingToken, address _account, address _receiver, address[] memory _rewardTokens) internal {
        IBaseRewardPool rewarder = IBaseRewardPool(tokenToPoolInfo[_stakingToken].rewarder);
        if (address(rewarder) != address(0)) {
            if (_rewardTokens.length > 0)
                rewarder.getRewards(_account, _receiver, _rewardTokens);
            else
                // if not specifiying any reward token, just claim them all
                rewarder.getReward(_account, _receiver);
        }
    }
