### Title
`ThresholdKeys::read` accepts attacker-inconsistent verification shares: `group_key` binds only participants 1..=t, letting shares t+1..=n be set arbitrarily — ([File: crypto/dkg/src/lib.rs])

### Summary
The intended construction boundaries for `ThresholdKeys` — PedPoP (`KeyMachine::calculate_share` verifies every share against committed polynomials), MuSig (`musig` derives verification shares from the bound key list), and `dealer::key_gen` — all guarantee a fixed relationship between the secret share, the per-participant verification shares, and the group key. The deserialization path `ThresholdKeys::read` bypasses all of these checks: it accepts raw bytes for `secret_share` and every entry of `verification_shares`, then calls `ThresholdKeys::new`, which computes `group_key` only from participants `1..=t` and never checks that `secret_share` corresponds to `verification_shares[i]` nor that shares `t+1..=n` are consistent with the key. The result is used verbatim by `view()`/`sign`, exactly mirroring the AzuraCast bug class: a weaker-guarded input path writes fields verbatim that the privileged path would have validated.

### Finding Description
`ThresholdKeys::new` at `crypto/dkg/src/lib.rs:376-378` computes:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

Only verification shares for participants `1..=t` contribute to `group_key`. `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) reads `n` verification shares and an arbitrary `secret_share` from the wire and passes them to `new` with no check that:

1. `C::generator() * secret_share == verification_shares[i]` (the node's own share is never validated — PedPoP checks this via `share_verification_statements`/`exponential` at `crypto/dkg/pedpop/src/lib.rs:490,518`), and
2. shares `t+1..=n` lie on the polynomial implied by shares `1..=t` (no binding at all exists in `new`).

`view()` (`crypto/dkg/src/lib.rs:463-533`) then interpolates `verification_shares` for whatever `included` set is used and exposes the attacker-controlled points as the basis for `verify_share` in `crypto/frost/src/algorithm.rs:219-230` and the offset-injection at line 521 (`verification_shares[included[0]] += G*offset`).

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (a listed reachable API) obtains a `ThresholdKeys` whose declared `group_key` never commits to the verification shares of participants `t+1..=n`, and whose `secret_share` need not match `verification_shares[i]`. Consequences:

- **Forged share acceptance for participants t+1..=n:** since `verification_shares[l]` for `l > t` is attacker-chosen and unconstrained by `group_key`, the share-verification statements in `verify_share` can be satisfied for shares unrelated to the group key — a forged-proof condition the DKG boundary (`calculate_share`'s `BatchVerifier`) exists to prevent.
- **Unspendable funds / inconsistent key registration:** a `group_key` derived only from shares `1..=t` can be registered while the shares `t+1..=n` needed by larger signing sets were never bound to it, so any signing set including such participants produces shares that cannot reconstruct a signature under the registered key — deposits to that key are unspendable.
- **Signing under unintended key material:** an inconsistent `secret_share` (not matching `verification_shares[i]`) is used verbatim by `view()` to sign, producing shares blamed on the honest participant index `i`.

### Likelihood Explanation
Reachability is limited to call sites that deserialize `ThresholdKeys` from bytes an attacker can influence (backup/restore, key transport, or DB contents writable through a lower-privileged path — the direct analog of the AzuraCast profile-edit endpoint). Within the crypto crates the flaw is unconditional: `read` performs no consistency validation beyond parameter bounds and canonical encodings. When reachable, exploitation needs only crafted scalar/point encodings — trivially constructible.

### Recommendation
In `ThresholdKeys::new` (or at least in `ThresholdKeys::read`), enforce the invariants the DKG guarantees:

- Verify `C::generator() * *secret_share == verification_shares[&params.i()]`.
- Verify shares `t+1..=n` are consistent with the group key — e.g., for `Interpolation::Lagrange`, check each `verification_shares[l]` (`l > t`) equals the evaluation of the polynomial implied by shares `1..=t` at `l` (i.e., `Σ_j verification_shares[j] * lagrange_factor(j, l, {1..=t})`), or store/verify a commitment to the full share vector.
- For `Interpolation::Constant`, similarly bind all shares to `group_key` via the supplied coefficients.

### Proof of Concept
For `Ristretto` with `t = 1, n = 3, i = 2`:

```rust
// Crafted bytes: C::ID, t=1, n=3, i=2, Lagrange (1), secret_share = arbitrary s,
// verification_shares = [G*x, G*s, G*y] with arbitrary y
let keys = ThresholdKeys::<Ristretto>::read(&mut crafted.as_ref()).unwrap();

// group_key = verification_shares[1] * λ_1({1}) = G*x — shares[2] and shares[3]
// never contributed. read() succeeded even though share[3] = G*y is inconsistent
// with any polynomial having group key G*x.
assert_eq!(keys.group_key(), Ristretto::generator() * x);
```

`new` accepts because `verification_shares.len() == n` and all indices `<= n`; the absence of any per-share or secret-share consistency check is the bypass. A signing set `{1,2,3}` then verifies participant 3's shares against the attacker-chosen `G*y`, and `included[0] == 1` receives the offset at `view()` line 518-521 — all under a `group_key` that never committed to `y`.
