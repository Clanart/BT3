## Title
Git's built-in submodule clone protection (`GIT_CLONE_PROTECTION_ACTIVE`) is explicitly disabled during recursive clones, re-enabling CVE-2024-32002-class RCE from a malicious repository - (File: `app/src/lib/git/clone.ts`)

### Summary
Desktop's `clone()` function performs `git clone --recursive` but explicitly sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` on the child process [1](#0-0) . This variable is Git's own internal safety guard (added upstream as part of the fix for CVE-2024-32002) that detects and blocks malicious submodule layouts — e.g. a submodule whose worktree/gitdir path collides with the parent `.git` directory on case-insensitive or Unicode-normalizing filesystems — which can otherwise be abused to write files into the `.git` directory (including hooks) and achieve arbitrary code execution during `clone --recursive`/`checkout --recurse-submodules`. By forcing this flag to `'false'`, Desktop disables the very protection Git ships specifically to stop this attack, for every recursive clone it performs.

### Finding Description
The broken invariant is: "Git's clone-time defenses against attacker-crafted submodule configurations are active whenever Desktop clones a repository recursively." That invariant is violated because Desktop unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment passed to `git clone --recursive` [1](#0-0) .

The attacker primitive here is a malicious/attacker-controlled repository (or any repository the user is fetching from a compromised or untrusted remote) containing a submodule configuration crafted to collide with the parent repository's `.git` directory (case-insensitive path collision or similar). Git's own recursive-clone protection is designed to detect and refuse such configurations, but Desktop disables that check before invoking the clone.

The same recursive-submodule code path (`updateSubmodulesAfterOperation`) is also invoked after every `checkout` and `pull` with `git submodule update --init --recursive` [2](#0-1) , meaning that a malicious submodule reference introduced into a branch a user checks out or a commit they pull can trigger the same unguarded recursive submodule initialization, without any separate opt-in.

Desktop does have some hardening nearby — `isClonePathSensitive` blocks cloning into sensitive destination directories [3](#0-2) , and `allowFileProtocol`/`protocol.file.allow` gates whether `file://` submodules are permitted [4](#0-3)  — but neither of these guards addresses the specific submodule-path-collision class that `GIT_CLONE_PROTECTION_ACTIVE` exists to stop. None of the existing checks re-validate submodule paths for case-insensitive/Unicode collisions with the parent `.git` directory.

### Impact Explanation
If exploitable against the underlying dugite/git version bundled with Desktop, this allows an attacker who controls a repository URL (a malicious public repo, a compromised remote, or a repo linked to the user) to achieve arbitrary code execution on the victim's machine the moment Desktop clones (or checks out a branch that pulls in) that repository — because the file-write-outside-worktree protection is deliberately turned off. This meets the "code execution" and "file write outside the repo" impact bar for GitHub Desktop.

### Likelihood Explanation
The trigger requires nothing beyond the normal, expected user action of cloning a repository or checking out/pulling a branch in Desktop — no local access, no admin rights, and no unusual steps. The disabling of the protection is unconditional and hardcoded, not something a user could enable or disable, so any user cloning an attacker-supplied URL is affected. Likelihood is bounded only by whether the installed git/dugite version is otherwise still vulnerable to the underlying submodule-collision issue that `GIT_CLONE_PROTECTION_ACTIVE` guards against, and by git's other independent defenses that may still partially mitigate the same class of bug.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` [5](#0-4)  and let Git's default (enabled) protection apply. If the override was added to work around a legitimate false positive (e.g., recursive clone re-invocation), scope the override narrowly (e.g., only for Desktop's own re-entrant internal invocations) rather than disabling it for every recursive clone from an arbitrary, potentially untrusted URL. Apply the same review to `updateSubmodulesAfterOperation`'s recursive submodule update path, since it performs the same recursive initialization for `checkout`/`pull`.

### Proof of Concept
1. Attacker publishes a repository containing a submodule whose configured path is crafted to collide with `.git` on a case-insensitive or Unicode-normalizing filesystem (the layout historically fixed by CVE-2024-32002 protections).
2. Victim uses GitHub Desktop's "Clone repository" feature with the attacker's URL, invoking `clone()` in `app/src/lib/git/clone.ts`.
3. Desktop spawns `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment [1](#0-0) , disabling Git's own defense against the crafted submodule layout.
4. If the bundled git/dugite is otherwise susceptible to the underlying collision bug, the recursive submodule clone writes attacker-controlled content into the parent `.git` directory (e.g., hooks), leading to code execution on subsequent git operations.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
