## Title
`check_chained_block_id` silently skips SIMD-0340 chained-Merkle-root verification when the parent slot's last shred is unavailable, allowing an unverified parent block ID to be accepted - (`File: ledger/src/blockstore_processor.rs`)

## Summary
The Linea report's core defect is: data loaded from storage to seed a validation check is not checked for "empty/absent," so the absence of prior data is silently treated as trivially valid rather than as an error, letting corrupted/out-of-order state pass validation. The Agave analog is `check_chained_block_id`, which loads the parent slot's last shred Merkle root from `Blockstore` to validate the child's `chained_merkle_root` (SIMD-0340 block-ID chaining), but treats a missing/incomplete parent record as automatic `Pass` instead of a validation failure.

## Finding Description
`check_chained_block_id` fetches the expected parent block ID from the child's first shred, then attempts to fetch the *actual* parent block ID via `blockstore.get_last_shred_merkle_root(parent_slot)`: [1](#0-0) 

```rust
pub fn check_chained_block_id(...) -> ChainedBlockIdCheck {
    ...
    let Ok(expected_parent_block_id) = blockstore.get_parent_chained_block_id(slot) else {
        return ChainedBlockIdCheck::Unavailable;
    };
    match blockstore.get_last_shred_merkle_root(parent_slot).expect(...) {
        Some(parent_block_id) => {
            if expected_parent_block_id != parent_block_id {
                ...
                ChainedBlockIdCheck::Mismatch
            } else {
                ChainedBlockIdCheck::Pass
            }
        }
        None => {
            warn!("{parent_slot} is missing from our blockstore, likely the snapshot slot. Skipping chained block id verification");
            ChainedBlockIdCheck::Pass
        }
    }
}
```

`get_last_shred_merkle_root` returns `Ok(None)` whenever the parent `SlotMeta` is absent or its `last_index` field is not yet set (i.e., the parent block is not "complete" in the blockstore's view): [2](#0-1) 

The comment in the `None` branch assumes this can "likely" only happen for the snapshot bootstrap slot, and therefore returns `ChainedBlockIdCheck::Pass` — the same code path as a *successful* cryptographic match — rather than `Unavailable`/failure. This mirrors the LineaRollup bug precisely: a loaded value that is empty/absent is not validated as an error condition; it is instead interpreted as an implicit "OK," bypassing the very check meant to enforce correct chaining (SIMD-0340 chained Merkle root / block ID).

The blockstore's `SlotMeta.last_index` for a given slot can become unset/`None` again after having previously been set, through the ledger cleanup and purge paths that rewrite `SlotMeta` for non-purged descendant slots into `SlotMeta::new_orphan`, which resets meta fields including completion markers: [3](#0-2) 

Additionally, routine automatic cleanup (`BlockstoreCleanupService`) purges old slots based on shred-count thresholds, and `cleanup_chaining_for_nonpurged_slots` is only invoked when `purge_slots_cleanup_chaining` (not the default `purge_slots` used by the auto-cleanup path) is called; either way, a parent slot legitimately can end up without a resolvable `last_index`/last shred even outside of the "snapshot slot" scenario the comment assumes, because retained `SlotMeta::new_orphan` records and racing purges/pruning can leave a `None` for `last_index` on a still-referenced parent.

## Impact Explanation
If the check is bypassed (returns `Pass` via the `None` branch) for a parent slot that is *not* actually the pristine snapshot boundary, `ChainedBlockIdCheck::Pass` is treated identically by callers in `core/src/replay_stage.rs` to a real cryptographic confirmation that the child's declared parent block ID matches the parent's actual last-FEC-set Merkle root. This defeats the purpose of SIMD-0340, which is to cryptographically bind child slots to a specific parent block content (the parent's last shred's Merkle root), preventing chain-splitting / duplicate-block attacks where a leader or Byzantine peer could produce two different "last blocks" for the same parent slot. Silently treating "we don't have the data" as "verified" allows a forged or mismatched chaining relationship to be accepted as valid during replay, which can cause a validator to accept/vote on a block chained to an unverifiable or different parent state — a false-execution/false-acceptance style consensus defect rather than a simple crash.

## Likelihood Explanation
The `None` branch requires the parent's `last_index`/last shred to be unset in the local blockstore at the moment of replay for a non-genesis, non-snapshot-boundary slot. This is not attacker-controlled directly (it depends on the node's own ledger cleanup/pruning state), so it is not a remotely triggerable "malicious peer" bug, but it is a state a single unprivileged validator's own blockstore can reach during normal cleanup/pruning combined with lag/rebuild scenarios, making the assumption "likely the snapshot slot" incorrect in general. This is best characterized as a latent correctness gap rather than a high-frequency exploit; confidence that it is remotely triggerable by an attacker is limited by the available code (I could not trace all call sites/timing invariants in `core/src/replay_stage.rs` that might already guarantee the parent block is always complete before this check runs, due to iteration/tool-call limits).

## Recommendation
Do not conflate "parent data unavailable" with "chaining verified." `get_last_shred_merkle_root` returning `None` should map to `ChainedBlockIdCheck::Unavailable` (or a distinct `Unknown` state that callers treat conservatively, e.g., delaying replay/vote until the parent's last shred can be confirmed) except in the explicitly identifiable genesis/snapshot-root case, which should be checked structurally (e.g., comparing `parent_slot` to the bank's snapshot root slot) rather than inferred from the absence of data.

pub fn check_chained_block_id(
    blockstore: &Blockstore,

    let slot = bank.slot();

        return ChainedBlockIdCheck::Inactive;

        return ChainedBlockIdCheck::Unavailable;

        .get_last_shred_merkle_root(parent_slot)

                     {parent_block_id}"

                ChainedBlockIdCheck::Mismatch

                ChainedBlockIdCheck::Pass
            }
        }

            warn!(

                 chained block id verification",
            );

        }
    }
}

    /// Retrieves the merkle root of the last data shred in the given slot,
    /// which serves as the slot's block ID for chained merkle root validation
    /// in child slots (SIMD-0340).
    ///
    /// Returns `Ok(None)`` if the block is not complete
    pub fn get_last_shred_merkle_root(&self, slot: Slot) -> Result<Option<Hash>> {
        let Some(meta) = self.meta(slot)? else {
            return Ok(None);
        };
        let Some(last_index) = meta.last_index else {
            return Ok(None);
        };
        let shred_bytes = self
            .get_data_shred(slot, last_index)?
            .ok_or(BlockstoreError::MissingShred(slot, last_index))?;
        shred::layout::get_merkle_root(&shred_bytes)
            .map(Option::Some)
            .ok_or(BlockstoreError::MissingMerkleRoot(slot, last_index))
    }
