### Title
Cross-function signature replay between `accumulate()` beneficiary-redirect and `withdraw()` due to shared nonce and identical hash preimage - ([File: modules/pallets/relayer/src/accumulate.rs] / [File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
The relayer-fee pallet uses one shared `Nonce<T>` counter (keyed by `(address, state_machine)`) for two unrelated signed actions: `Pallet::withdraw` (dispatches an actual cross-chain fee payout) and the beneficiary-redirect check inside `Pallet::accumulate`. Both build their signed digest with the identical structure `keccak256((nonce, state_machine/dest_chain, beneficiary).encode())` via `withdrawal::message()` and `accumulate::beneficiary_message()`. Because these two call paths are permissionless/unsigned extrinsics that only validate the signature and consume the shared nonce, a signature produced for one purpose can be submitted through the other entrypoint, letting an unrelated caller force a relayer's pending fee-accumulation flow to fail or force an early/forced withdrawal dispatch that the relayer did not intend at that time.

### Finding Description
`withdrawal.rs::message()` computes:
```
keccak256(&(nonce, dest_chain, beneficiary).encode())
``` [1](#0-0) 

`accumulate.rs::beneficiary_message()` computes:
```
keccak256(&(nonce, state_machine, beneficiary).encode())
``` [2](#0-1) 

`StateMachine` and `dest_chain`/`state_machine` are the same type, so both digests are byte-for-byte identical for the same `(nonce, chain, beneficiary)` triple. Both consumers read and increment the *same* storage item, `Nonce::<T>::get(address, state_machine)` / `Nonce::<T>::try_mutate(...)`:
- `withdraw()` reads/increments `Nonce::<T>` for `(address, dest_chain)` before dispatching the payout. [3](#0-2) 
- `accumulate()`'s beneficiary-redirect branch reads/increments `Nonce::<T>` for `(delivery_address, state_machine)` using the exact same map. [4](#0-3) 

Neither function scopes its signature purpose (e.g. via a domain separator/tag distinguishing "withdrawal" from "beneficiary-redirect"), and both extrinsics are permissionless (unsigned, callable by anyone who has the signature bytes, since these are relayer off-chain-signed payloads submitted by any account). This mirrors the GMX report's core broken invariant: a value/parameter (there, the `uiFeeReceiver`; here, the shared `nonce` + signed digest) that one code path assumes is exclusively bound to its own execution context is actually shared with a second, independently-triggerable code path, letting an outside party consume/corrupt that shared value ahead of the intended caller and force the legitimate flow into a failure/stuck state.

Concretely:
1. A relayer signs a beneficiary-redirect message intended only for `accumulate()` at nonce `N` for `(state_machine, beneficiary)`. This signature must be published (typically embedded in the `WithdrawalProof.beneficiary_details` of a to-be-submitted, permissionless `accumulate` extrinsic, visible in the mempool before inclusion).
2. Any third party extracts `(address, signature, dest_chain=state_machine, beneficiary)` from the pending transaction and submits it to `withdraw()` first via `WithdrawalInputData`. Because the digest format is identical and the current `Nonce` value is still `N`, `withdraw()`'s signature check succeeds, `Nonce` is bumped to `N+1`, `Fees` for `address` is zeroed, and a real cross-chain payout dispatch is fired using whatever `available_amount` currently sits in `Fees::<T>` (which may be smaller than what the relayer's pending `accumulate()` batch was about to add). [5](#0-4) 
3. When the relayer's original `accumulate()` transaction lands, `Nonce::<T>::get(&delivery_address, state_machine)` is now `N+1`, so the recomputed `beneficiary_message(N+1, ...)` no longer matches the signature computed for `N`, and `signature.verify()` fails with `InvalidSignature`, aborting the whole `accumulate()` call before any commitment is marked `claimed` or fee credited. [6](#0-5) 

The result: the relayer's intended fee-accumulation transaction is forced to fail and must be resigned/resubmitted, while an unrelated third party has forced an unplanned withdrawal dispatch for the relayer at a time and amount not chosen by the relayer. This is directly analogous to the GMX report's pattern where a parameter/field a victim assumed was private to their own flow is silently shared/exploitable through a sibling code path, forcing the victim's operation into an unusable/stuck state until manual recovery (resigning and resubmitting).

### Impact Explanation
This breaks the "one-time, purpose-bound signature" invariant required by the bounty's replay/double-claim/false-acceptance category: a signature meant to authorize a beneficiary redirect in `accumulate()` is valid and consumable through the unrelated `withdraw()` extrinsic (and vice versa, since the reverse ordering — a withdrawal-intent signature reused in `accumulate()` — collides identically). It allows any unprivileged observer of a pending relayer signature to:
- Force premature/duplicate consumption of the relayer's nonce, causing genuine `accumulate()`/`withdraw()` submissions to revert with `InvalidSignature`.
- Trigger an unauthorized dispatch of the relayer's currently accumulated fee balance to the signed beneficiary at a time chosen by the attacker rather than the relayer, and zero out `Fees::<T>` before the relayer's own batch is processed — a transaction-manipulation/unauthorized-execution effect on relayer reward accounting.

While the beneficiary address itself remains bound in the signed digest (limiting outright fund theft to a different beneficiary), the confusion still constitutes unauthorized execution of a state-changing, fund-moving dispatch (`IsmpDispatcher::dispatch_request` cross-chain payout) triggered by a party other than the relayer, at the wrong time, and it reliably grief-blocks the sibling extrinsic — a direct functional analog of the "GMXVault stuck in Deposit_Failed" scenario, since operators must re-sign and resubmit to recover.

### Likelihood Explanation
Both `accumulate` and `withdraw` are dispatched as unsigned/permissionless extrinsics that only validate the embedded ECDSA/Sr25519/Ed25519 signature — no `ensure_signed`/origin check ties the caller identity to the relayer. Any relayer-signed message that becomes visible before finalization (mempool, gossiped calldata, or shared beneficiary redirect data) can be front-run by any address able to submit an extrinsic, which is a low bar. The exploit requires no relayer, prover, or admin collusion and no malformed proof — only reading publicly broadcast signed data and front-running it into the sibling function.

### Recommendation
Add an explicit domain separator/purpose tag to the signed payload in both `withdrawal::message()` and `accumulate::beneficiary_message()` (e.g. prefix with a distinct constant such as `b"HYPERBRIDGE_WITHDRAW"` vs `b"HYPERBRIDGE_BENEFICIARY_REDIRECT"`) so that a signature valid for one purpose can never be replayed through the other entrypoint, even though they currently share the same `(nonce, state_machine, beneficiary)` tuple and storage-backed nonce. Additionally, consider using independent nonce counters/namespaces per purpose so that consuming one does not desynchronize the other's expected digest.

### Proof of Concept
1. Relayer `R` (address `A`) constructs a beneficiary-redirect proof for `accumulate()`: signs `msg = keccak256((N, SM, B).encode())` with their key, where `N = Nonce::<T>::get(A, SM)`, and submits a pending `accumulate` extrinsic with `beneficiary_details = Some((B, sig))`.
2. Before that transaction is included, attacker `X` observes `(A, SM, B, sig)` from the mempool/broadcast data and calls `Pallet::withdraw` with:
   ```
   WithdrawalInputData {
       signature: sig,        // same signature bytes
       dest_chain: SM,        // matches the state_machine used above
       beneficiary: Some(B),  // matches the beneficiary encoded in msg
   }
   ```
3. `withdraw()` recomputes `message(N, SM, Some(B))`, which equals the same digest `R` signed, so `signature.verify(&msg, None)` succeeds even though `X` is calling on `R`'s behalf without `R`'s prior consent for a withdrawal at this specific moment.
4. `Nonce::<T>::get(A, SM)` is bumped to `N+1`, `Fees::<T>` for `A` is zeroed, and a cross-chain withdrawal dispatch for `available_amount` at time-of-call is fired to beneficiary `B`.
5. `R`'s original `accumulate` transaction later executes; `Nonce::<T>::get(A, SM)` is now `N+1`, so `beneficiary_message(N+1, SM, B)` no longer matches `sig` (signed for `N`), and `signature.verify()` fails with `Error::<T>::InvalidSignature`, aborting the entire `accumulate()` call and leaving the batch's `RequestCommitments` unclaimed until `R` resigns and resubmits.

Note: full exploit confirmation (e.g., exact mempool-visibility assumptions for unsigned extrinsics in this specific Substrate runtime, and whether `beneficiary_details` are ever transmitted out-of-band rather than via a submitted transaction) could not be independently verified from static code alone; a Devin session with node/test access would be needed to reproduce the front-running timing end-to-end.

pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
