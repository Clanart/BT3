## Title
Asymmetric decimal-scaling bug in `convert_to_balance`/`convert_to_erc20` mints or credits wildly wrong token amounts when the local asset has more decimals than its ERC20 counterpart - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `hyper-fungible-token` pallet's decimal-conversion helpers, `convert_to_balance` and `convert_to_erc20`, use `erc_decimals.saturating_sub(local_decimals)` to compute a scaling exponent instead of using the true signed difference. Whenever the local Substrate asset has **more** decimals than its registered ERC20 precision on a given remote chain, `saturating_sub` silently clamps to `0`, so the function applies **no scaling at all** where scaling in the opposite direction was required. This causes both the outbound `send` path and the inbound `on_accept`/`on_timeout` paths to compute amounts that are off by a power-of-ten factor, either minting far more tokens on the destination chain than were escrowed, or crediting far fewer tokens than were actually sent.

### Finding Description
`convert_to_erc20` (used by `send` to build the outbound ISMP message) and `convert_to_balance` (used by `on_accept`/`on_timeout` to credit/refund) both compute the scaling factor the same way: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions assume `erc_decimals >= local_decimals` and only ever scale in one direction (divide in `convert_to_balance`, multiply in `convert_to_erc20`). When `local_decimals > erc_decimals`, the correct scaling factor should invert (multiply in `convert_to_balance`, divide in `convert_to_erc20`), but `u8::saturating_sub` returns `0` instead of underflowing, so `10^0 = 1` is used — i.e., **no scaling is performed** — silently producing a wrong magnitude rather than erroring out.

This is the exact bug-class from the external report: reward/amount math computed with the wrong decimal exponent, silently truncating or inflating the transferred amount instead of failing loudly.

**Outbound impact (`send`)** — escrows `params.amount` in local-asset units, then computes the ERC20 amount for the outbound message: [2](#0-1) 

If `decimals` (local) > `erc_decimals` (remote), `convert_to_erc20` returns `amount` unscaled, which the destination chain's `HyperFungibleToken`/`WrappedHyperFungibleToken` contract will mint/unlock at face value in the *lower*-decimal ERC20 token — i.e., `10^(local_decimals - erc_decimals)` times too many tokens are unlocked/minted on the destination relative to what was actually escrowed on the source chain.

**Inbound impact (`on_accept`/`on_timeout`)** — the reverse case: if the incoming message's `erc_decimals` < the local asset's `decimals`, `convert_to_balance` divides by `10^0 = 1` instead of multiplying up, so the beneficiary is minted/transferred `10^(local_decimals - erc_decimals)` times too few tokens: [3](#0-2) [4](#0-3) 

The `Precisions` storage that supplies `erc_decimals` is governance-set per `(asset_id, chain)` and is independent from the local asset's decimals (which come from `T::Decimals::get()` for the native asset or from the `pallet_assets` metadata for other assets) — nothing in the code enforces `erc_decimals >= local_decimals`, so this asymmetric-scaling condition is a reachable configuration, not a hypothetical one.

### Impact Explanation
This directly matches the bounty's "stealing or loss of funds" and "transaction manipulation / logic attacks" categories:
- On the outbound leg, a legitimate user calling `send()` with a tiny amount of a high-decimal local asset can cause the destination `HyperFungibleToken` contract to unlock/mint a vastly larger ERC20 amount than what was escrowed, draining the bridge's custody on the destination chain — pure fund creation from nothing.
- On the inbound/refund leg, legitimate cross-chain transfers or timeout refunds silently under-credit the beneficiary by orders of magnitude, causing permanent fund loss for users with no error surfaced (the conversion function doesn't fail — it just produces a wrong number).

### Likelihood Explanation
No malicious relayer, prover, or governance actor is required — any unprivileged user triggers the bug simply by calling the public `send` extrinsic once a registered asset/chain pair exists where local decimals and ERC20 decimals differ in this direction. The only precondition is a `Precisions` entry where `erc_decimals < local_decimals` for some `(asset_id, chain)`, which is a normal, plausible governance configuration (e.g., a native asset configured with 18 local decimals bridging against a remote representation registered with fewer decimals), not an adversarial one.

### Recommendation
Replace the `saturating_sub`-based scaling with an explicit signed comparison that scales in the correct direction regardless of which side has more decimals, and reject (rather than silently no-op) any case that would otherwise lose precision without an intentional design decision, e.g.:
```rust
if erc_decimals >= local_decimals {
    value / 10^(erc_decimals - local_decimals)     // scale down
} else {
    value * 10^(local_decimals - erc_decimals)     // scale up
}
```
mirrored symmetrically in `convert_to_erc20`. Add unit tests covering both directions of the decimal difference (not just the case currently tested, `erc=18, local=10`).

### Proof of Concept
1. Governance registers a local asset `X` with `local_decimals = 18` (e.g., via `pallet-assets`) and sets `Precisions::<T>::insert(X, StateMachine::Evm(dest), 6)` (ERC20 representation with 6 decimals, e.g. USDC-style) on some destination chain.
2. A user calls `HyperFungibleToken::send` with `amount = 1_000_000_000_000` (i.e., `1e-6` of the local asset in 18-decimal terms — a negligible amount actually escrowed).
3. `erc20_amount = convert_to_erc20(1_000_000_000_000, erc_decimals=6, local_decimals=18)`. Since `6u8.saturating_sub(18) == 0`, the result is `1_000_000_000_000 * 10^0 = 1_000_000_000_000`, unscaled.
4. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract interprets this value in its 6-decimal token — i.e., `1_000_000` full tokens are minted/unlocked, for an escrow of only `0.000001` local-asset units. The correct value should have been `1_000_000_000_000 / 10^12 = 1` (i.e., `0.000001` tokens in 6-decimal terms), a factor of `10^12` discrepancy.
5. Symmetrically, reversing the roles (erc_decimals=18, local_decimals=6 on the receiving side) via `on_accept`/`on_timeout` under-credits the beneficiary by the same `10^12` factor when the misconfiguration runs the other way.
