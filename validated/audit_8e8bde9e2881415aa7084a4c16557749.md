### Title
Untyped raw-byte message signing reuses the wallet's spend-authorizing synthetic key for AGG_SIG-style payloads, enabling phishing-driven fund theft - (File: chia/wallet/wallet_rpc_api.py, chia/wallet/util/signing.py)

### Summary
The RPCs `sign_message_by_address` / `sign_message_by_id` sign attacker- or caller-supplied "messages" using the exact same synthetic secret key that is used to authorize coin spends (`AGG_SIG_ME`/`AGG_SIG_UNSAFE`), and — when `safe_mode=False` — sign the raw bytes with no domain separation/prefix at all, unlike the default CHIP-0002 mode.

### Finding Description
`sign_message_by_address` and `sign_message_by_id` in [1](#0-0)  derive `synthetic_secret_key` via `main_wallet.convert_secret_key_to_synthetic(...)`, which calls `calculate_synthetic_secret_key(secret_key, DEFAULT_HIDDEN_PUZZLE_HASH)` [2](#0-1) . This is the identical synthetic key used to sign real coin spends for the standard `p2_delegated_puzzle_or_hidden_puzzle` puzzle, as documented in that module and exercised by `sign_transaction`/`WalletSigner` [3](#0-2) [4](#0-3) .

The message that actually gets signed depends on `SigningMode`, defined in `sign_message`: for `CHIP_0002`/`CHIP_0002_HEX_INPUT` the payload is domain-separated via `Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash()`, but for `BLS_MESSAGE_AUGMENTATION_UTF8_INPUT` / `BLS_MESSAGE_AUGMENTATION_HEX_INPUT` the raw UTF-8 bytes or raw hex-decoded bytes are signed directly with no prefix, no coin binding, and no chain/application binding [5](#0-4) . These non-CHIP-0002 modes are selectable by any RPC/CLI caller via the `safe_mode` flag on `SignMessageByAddress`/`SignMessageByID` (default `True`, but overridable to `False`) [6](#0-5) , as exercised in tests that explicitly pass `safe_mode=False` and `is_hex=True` to get `AugSchemeMPL.verify(pubkey, hexstr_to_bytes(message), signature)` [7](#0-6) .

Separately, the consensus-layer AGG_SIG domain separation only guards against confusion *among* the AGG_SIG_* condition variants: `pkm_pairs_for_conditions_dict` explicitly rejects an `AGG_SIG_UNSAFE` message if it ends with any of the `AGG_SIG_*_ADDITIONAL_DATA` suffixes [8](#0-7) , but this check has no knowledge of, and provides no protection against, the wallet-RPC message-signing domain (`CHIP_0002_SIGN_MESSAGE_PREFIX`) or arbitrary raw-byte messages signed via `BLS_MESSAGE_AUGMENTATION_*_INPUT` modes. `AGG_SIG_UNSAFE` itself is defined to accept an arbitrary attacker-supplied message atom paired with a pubkey [9](#0-8)  — there is no forced binding to the specific coin being spent, which is precisely why `AGG_SIG_UNSAFE` requires callers to avoid message collisions with other signing domains.

This creates a signature-reuse-across-functions attack analogous to the reported Rigor "untyped data signing" issue: a malicious dApp/site/local RPC caller can request the user's wallet to "sign a message" (an innocuous-looking action, e.g. via `SignMessageByAddress`/`SignMessageByID` with `safe_mode=False`, `is_hex=True`), while actually asking for a signature over raw bytes chosen by the attacker to exactly match the `AGG_SIG_UNSAFE` message required by a coin puzzle the attacker controls (e.g. a coin pre-funded by the victim, or a puzzle that releases attacker-favorable conditions once that exact signature is supplied). Because the signing key is the real spend-authorizing synthetic key and the raw-byte mode adds zero domain separation, the resulting `G2Element` signature is a valid `AGG_SIG_UNSAFE` witness that can be dropped straight into a spend bundle.

### Impact Explanation
An attacker who can get a victim to invoke wallet message-signing with `safe_mode=False` (via a malicious dApp, script, or any local RPC/CLI-integrated tool) can obtain a signature from the victim's real spend-authorizing key over attacker-chosen bytes, and reuse it to satisfy an `AGG_SIG_UNSAFE` condition in a coin spend the attacker controls — enabling unauthorized/forged spend authorization without the victim ever intending to sign a transaction. This is a concrete "unsigned/unauthorized coin movement" vector consistent with the report's class 3/4 (function/domain confusion and DApp phishing reuse of a generically-formatted signature).

### Likelihood Explanation
Requires social engineering (tricking the user/local caller into invoking `sign_message_by_address`/`sign_message_by_id` with `safe_mode=False` for attacker-chosen content) and requires the attacker to construct/fund a puzzle whose `AGG_SIG_UNSAFE` message matches the signed bytes exactly — a non-trivial but fully attacker-controlled setup since the attacker writes the puzzle. `safe_mode=True` (the default, using CHIP-0002 hashing) is not vulnerable in the same direct way, so exploitation is limited to flows/wallets/integrations that explicitly disable safe mode.

### Recommendation
- Never sign raw, unprefixed bytes with the same key used for consensus spend authorization. Route `BLS_MESSAGE_AUGMENTATION_UTF8_INPUT`/`BLS_MESSAGE_AUGMENTATION_HEX_INPUT` message signing through a dedicated, non-spend-authorizing key, or always apply CHIP-0002-style domain separation regardless of `safe_mode`.
- Consider removing/deprecating the `safe_mode=False` raw-signing modes from `sign_message`, or require explicit strong warnings and out-of-band confirmation showing exactly what will be signed and that the signature could authorize spends.
- Extend the AGG_SIG domain-separation check in `pkm_pairs_for_conditions_dict`/message construction to also cover the CHIP-0002 message-signing prefix domain so that wallet-level message signatures can never validate as consensus `AGG_SIG_UNSAFE` conditions.

### Proof of Concept
1. Attacker crafts a coin puzzle that contains a condition `(AGG_SIG_UNSAFE <victim_synthetic_pubkey> <M>)` together with a condition paying out to the attacker, where `<M>` is a specific byte string chosen by the attacker.
2. Attacker gets the victim's coin/funds locked into (or otherwise controlling) such a puzzle (e.g., via a "test my dApp" or "verify ownership" flow that first requests a deposit, then requests message-signing).
3. Attacker's dApp calls the victim's wallet RPC `sign_message_by_address`/`sign_message_by_id` with `is_hex=True, safe_mode=False`, requesting the victim to sign message `M` under the guise of "login"/"verification" [1](#0-0) .
4. The wallet signs `M` directly with the coin's real synthetic secret key (no prefix) via `sign_message` in `BLS_MESSAGE_AUGMENTATION_HEX_INPUT` mode [5](#0-4) , returning `signature`.
5. Attacker submits a `SpendBundle` spending the pre-set-up coin with solution containing `(AGG_SIG_UNSAFE <victim_synthetic_pubkey> <M>)` and the returned `signature`; consensus validation accepts it because `pkm_pairs_for_conditions_dict` only rejects messages ending in the AGG_SIG_* domain suffixes, not CHIP-0002/raw message-signing content [8](#0-7) , resulting in unauthorized fund movement.

def calculate_synthetic_secret_key(secret_key: PrivateKey, hidden_puzzle_hash: bytes32) -> PrivateKey:
    secret_exponent = int.from_bytes(bytes(secret_key), "big")
    public_key = secret_key.get_g1()
    synthetic_offset = calculate_synthetic_offset(public_key, hidden_puzzle_hash)
    synthetic_secret_exponent = (secret_exponent + synthetic_offset) % GROUP_ORDER
    blob = synthetic_secret_exponent.to_bytes(32, "big")
    synthetic_secret_key = PrivateKey.from_bytes(blob)
    return synthetic_secret_key

def sign_message(secret_key: PrivateKey, message: str, mode: SigningMode) -> SignMessageResponse:
    public_key = secret_key.get_g1()
    if mode == SigningMode.CHIP_0002_HEX_INPUT:
        hex_message: bytes = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, bytes.fromhex(message))).get_tree_hash()
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_UTF8_INPUT:
        hex_message = bytes(message, "utf-8")
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT:
        hex_message = bytes.fromhex(message)
    else:
        hex_message = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash()
    return SignMessageResponse(
        pubkey=public_key,
        signature=AugSchemeMPL.sign(secret_key, hex_message),
    )

class AggSigUnsafe(Condition):
    pubkey: G1Element
    msg: bytes

    def to_program(self) -> Program:
        condition: Program = Program.to([ConditionOpcode.AGG_SIG_UNSAFE, self.pubkey.to_bytes(), self.msg])
        return condition

    @classmethod
    def from_program(cls, program: Program) -> AggSigUnsafe:
        return cls(
            G1Element.from_bytes(program.at("rf").as_atom()),
            program.at("rrf").as_atom(),
        )
