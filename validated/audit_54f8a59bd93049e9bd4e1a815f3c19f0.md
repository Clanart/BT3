### Title
Webhook `shop_domain` is derived from an unauthenticated header while HMAC verification only covers the request body, allowing shop-identity spoofing on replayed webhooks - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` verifies webhook authenticity by HMAC-signing only the raw request body, but it exposes a separate `shop_domain` helper that simply reads the `X-Shopify-Shop-Domain` HTTP header without any cryptographic binding to that signature. Any code path that uses this `shop_domain` value to attribute a webhook to a shop (the documented and generator-provided usage pattern) inherits the same class of bug described in the report: the "initiator" (here, the originating shop) is never validated as part of the trust decision, only the payload's raw bytes are.

### Finding Description
`verify_request` in `lib/shopify_app/controller_concerns/webhook_verification.rb` calls `hmac_valid?(request.raw_post)`, which is implemented in `lib/shopify_app/controller_concerns/payload_verification.rb`: [1](#0-0) 

The HMAC is computed strictly over `data` (`request.raw_post`). The `shop_domain` accessor, defined in the same concern that performs this verification, is completely independent of that signature: [2](#0-1) 

The gem's own documentation instructs developers to build custom webhook controllers exactly this way — verifying with the concern, then trusting `shop_domain` to route work to the correct shop: [3](#0-2) 

Because `X-Shopify-Shop-Domain` is not part of the signed material, an attacker who legitimately controls their own shop (an "unrelated merchant") can:
1. Install the app on their own shop and receive a legitimately HMAC-signed webhook request from Shopify (a valid `(body, hmac)` pair for their own domain).
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `hmac_valid?` still returns true because the body and secret are unchanged — verification never inspects the header at all — yet the handler processes the request believing it originated from the victim shop.

This is the same root cause pattern as the reported issue: a security-relevant "who is the initiator/account" field (there, `deposit.account`; here, `shop_domain`) is not included in — or cross-checked against — the value that was actually authenticated (there, callback contract validation; here, the HMAC digest).

### Impact Explanation
Any app that follows the documented custom-controller pattern (or the generator-produced job templates that key off `shop_domain`, e.g. `lib/generators/shopify_app/add_webhook/templates/webhook_job.rb.tt` which does `Shop.find_by(shopify_domain: shop_domain)` then acts `with_shopify_session`) can be tricked into executing shop-scoped business logic (webhook processing, data mutation, session-scoped API calls) attributed to a shop the attacker does not control, using a signature the attacker validly obtained for their own shop. This is a cross-shop confusion / spoofing issue that could lead to incorrect authorization decisions or state changes scoped to another merchant's shop.

### Likelihood Explanation
Exploitation only requires an attacker to be a legitimate (even free/trial) merchant of the app to obtain one genuinely signed webhook body, then replay it with a modified header — no secret leakage or privileged access is required, and the vulnerable pattern is the one the gem's own docs recommend for anyone who doesn't use the built-in `WebhooksController`/`Registry` flow.

### Recommendation
Bind the shop identity to the verified signature: either include the `X-Shopify-Shop-Domain` (or a recomputed value derived from the verified payload/topic) inside the HMAC-covered data, or, at minimum, require that any consumer of `shop_domain` re-derive/validate it against an installed-shop record's stored secret/session rather than trusting the header value on its own once HMAC validity is confirmed. Document this requirement clearly in `docs/shopify_app/webhooks.md` and reinforce it in `PayloadVerification`/`WebhookVerification`.

### Proof of Concept
1. Install the target app as Shop A (attacker-controlled), triggering some webhook (e.g. `carts/update`). Capture the resulting POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Send a new POST request to the same webhook endpoint with the identical body `B` and header `H`, but replace `X-Shopify-Shop-Domain` with Shop B's (victim) domain.
3. `verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb`) calls `hmac_valid?(B)`, which succeeds because `B` and `H` are unmodified.
4. The custom controller/job (as documented) reads `shop_domain` from the header — now Shop B — and processes the webhook as if it were sent by Shop B, even though Shop B never sent it.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
