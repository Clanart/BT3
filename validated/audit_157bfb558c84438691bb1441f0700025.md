### Title
Missing Arbitrum L2 Sequencer-Uptime Check in `SimplexPaymaster._getOraclePrice` Allows Stale/Frozen Chainlink Prices to Be Trusted, Draining Treasury Funds - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` is deployed on Arbitrum One (`SimplexPaymaster: 0x7281Bccb4f0BCE44F3B8542d1fC5e51c2F5fC08C`, [1](#0-0) ), and prices every gas payment through `_getOraclePrice`, which reads Chainlink `latestRoundData()` and only reverts on non-positive answers or on absolute staleness against `maxOracleAge` ( [2](#0-1) ). It never verifies that the Arbitrum sequencer is up, unlike the Chainlink-recommended L2 sequencer-uptime-feed pattern that the external report specifically calls out.

### Finding Description
Chainlink's own guidance for L2s (including Arbitrum) is that consumers must additionally check a sequencer-uptime aggregator and enforce a grace period after the sequencer comes back online, because during an outage the underlying price feeds simply freeze at their last `updatedAt` value — they don't necessarily revert, and they don't necessarily become "stale" by the naive `block.timestamp - updatedAt > maxOracleAge` metric if the outage duration is shorter than the configured `maxOracleAge` window.

`SimplexPaymaster` sets `maxOracleAge` to a wide buffer — the deploy script defaults it to `90_000` seconds (25 hours) specifically to tolerate the 24h heartbeat of some stablecoin feeds ( [3](#0-2) ), and the contract caps it at `MAX_ORACLE_AGE = 7 days` ( [4](#0-3) ). Any Arbitrum sequencer outage shorter than this window — which realistically covers essentially all historical Arbitrum sequencer incidents — passes the staleness check with a fully "fresh-looking" price that is in fact frozen and disconnected from the real market.

`_tokenPrice` uses `_getOraclePrice` for both `nativeOracle` and the per-token `tokenOracle` to compute the gas-to-token exchange rate charged to users ( [5](#0-4) ), and this price is what `_fetchDetails` returns to `PaymasterERC20` as the authoritative `tokenPrice` used to charge the UserOp sender ( [6](#0-5) ).

### Impact Explanation
During (or immediately after) an Arbitrum sequencer outage, `nativeUsd`/`tokenUsd` can be frozen at pre-outage levels while the real ETH/USD or token/USD price has since moved. Since transactions do resume being processed once the sequencer restarts (and Arbitrum sequencer downtime has historically been in the range of minutes to a few hours, well under the 25h/7d windows this paymaster tolerates), an attacker can submit UserOps as soon as the sequencer resumes, paying gas in stablecoins at the stale exchange rate. If native asset price rose during the outage, the attacker underpays for gas relative to its true USD cost, extracting value from the paymaster's markup/treasury (`MAX_MARKUP_BPS` surplus is meant to cover exactly this spread, and normally protects the treasury ( [7](#0-6) ) — with a frozen stale price the markup no longer reflects reality). Because `_registerToken`/`swapAndDeposit` also rely on the same `_getOraclePrice` for slippage protection ( [8](#0-7) ), a frozen price also lets a governance-triggered `swapAndDeposit` execute against a stale `amountOutMin` bound, worsening the exploitable window on that path too. This is a direct, no-privilege loss-of-funds vector against the paymaster's treasury/surplus, matching the "stealing or loss of funds" bounty class.

### Likelihood Explanation
Any unprivileged actor watching for Arbitrum sequencer status (a fully public, well-monitored piece of infrastructure) can time UserOps to land exactly when the sequencer resumes after an outage, before Chainlink oracles catch up to the post-outage market price. No relayer/prover/admin compromise, no malicious peer, and no governance is required — this is purely a self-serve public entrypoint (`_validatePaymasterUserOp` / `_fetchDetails`) exploited by a normal user submitting a UserOp with the paymaster's `paymasterData`.

### Recommendation
Follow Chainlink's documented pattern for L2 consumers: read the sequencer-uptime feed (e.g. `0xFdB631F5EE196F0ed6FAa767959853A9F217697D` on Arbitrum One) via `latestRoundData()`, revert if `answer == 1` (sequencer down), and additionally enforce a grace period (e.g. Chainlink's recommended 3600s) after `startedAt` before trusting any price feed again. This check should be added inside `_getOraclePrice` in `evm/src/utils/SimplexPaymaster.sol` so it protects every caller (`_tokenPrice`, `swapAndDeposit`, `getTokenPrice`, `estimateTokenCost`) uniformly.

### Proof of Concept
1. Arbitrum sequencer goes down for e.g. 2 hours. Chainlink `nativeOracle`/`tokenOracle` `updatedAt` freezes at the last pre-outage round.
2. Off-chain, ETH/USD price moves up materially during the outage (public information, e.g. tracked via other chains/CEXs).
3. Sequencer resumes; `block.timestamp - updatedAt` is still well under `maxOracleAge` (e.g. 25h default), so `_getOraclePrice` returns the stale (lower) ETH/USD price without reverting.
4. Attacker immediately submits a UserOp with `SimplexPaymaster` paymasterData (mode `0x01`/APPROVE, pre-approved USDC), consuming gas at the stale, cheaper `tokenPrice` computed by `_fetchDetails`/`_tokenPrice`.
5. The paymaster undercharges the attacker in USDC relative to the real-time ETH cost of the gas it spent, and the deficit is absorbed by the treasury/protocol surplus rather than the user — repeatable for every UserOp submitted in the stale window.

    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
