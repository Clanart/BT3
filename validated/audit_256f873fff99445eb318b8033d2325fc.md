### Title
Unvalidated serialized output offsets allow forged Bitcoin receive records - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an untrusted scalar offset, `TxOut`, and `OutPoint` without checking that the output script is derived from the wallet key plus that offset, or that the outpoint was actually scanned. Because `Scanner::scan_transaction` is the component that establishes this association, deserializing attacker-controlled bytes can fabricate a received output that later proves unspendable.

### Finding Description
A `ReceivedOutput` consists of an offset, Bitcoin output, and outpoint. [1](#0-0) 

The deserializer reads a canonical scalar, then consensus-decodes the output and outpoint directly from caller-controlled bytes. [2](#0-1) [3](#0-2) 

No expected wallet key is supplied to `ReceivedOutput::read`, so it cannot verify `output.script_pubkey == p2tr_script_buf(wallet_key + G * offset)`. It also does not verify the claimed `OutPoint` against blockchain data.

By contrast, `Scanner::scan_transaction` only creates `ReceivedOutput` after matching the transaction output script against the scanner's registered script-to-offset map. [4](#0-3) 

This creates a trust-boundary mismatch: bytes produced through the authenticated scanning path carry a proven key/script/outpoint relationship, while `ReceivedOutput::read` allows an unprivileged party to claim that relationship arbitrarily.

### Impact Explanation
A forged `ReceivedOutput` can report funds as received even though the referenced outpoint does not exist, the output belongs to another script, or the supplied offset does not derive the output's key. Transaction construction consumes `input.offset` and `input.outpoint` as authoritative spend metadata. [5](#0-4) 

If the offset does not match the key embedded in `script_pubkey`, threshold signing produces a signature for a different key and cannot spend the output. If the outpoint is fictitious, the transaction is invalid regardless of the signature. This results in false balance/reporting and funds that appear spendable but are not, matching the concrete failure mode of received funds that cannot actually be spent.

### Likelihood Explanation
The issue is reachable wherever untrusted or externally supplied serialized `ReceivedOutput` bytes are accepted, including restored wallet state, imported scan results, or messages containing serialized outputs. The vulnerability does not require a malicious validator, private-key access, malformed curve encodings, or modification of trusted scanner state: the attacker only supplies bytes to `ReceivedOutput::read`.

Likelihood is deployment-dependent because callers that only deserialize records generated locally by `Scanner::scan_transaction` and stored over authenticated storage are not exposed. The lack of cryptographic binding in the format nevertheless makes accidental cross-context or attacker-controlled deserialization unsafe.

### Recommendation
Do not expose a context-free `ReceivedOutput::read` for untrusted data. Provide a scanner-bound decoding API such as `Scanner::read_output` which:

1. Reads the claimed offset, output, and outpoint.
2. Recomputes `p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset))`.
3. Rejects the record unless the computed script equals `output.script_pubkey`.
4. Confirms the outpoint was observed by the scanner or an authenticated blockchain source before marking it spendable.

Additionally, tag serialized records with the wallet key or a scanner-instance identifier to prevent records from being replayed into a different wallet context.

### Proof of Concept
```rust
use bitcoin::{
  consensus::encode::Encodable,
  Amount, OutPoint, ScriptBuf, TxOut,
};
use k256::Scalar;
use bitcoin_serai::wallet::ReceivedOutput;

let mut bytes = vec![];

// Claim a zero derivation offset.
bytes.extend(Scalar::ZERO.to_bytes());

// Attach an arbitrary output not derived from the victim wallet's key.
TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_op_return([]),
}
.consensus_encode(&mut bytes)
.unwrap();

// Claim an arbitrary outpoint.
OutPoint::default().consensus_encode(&mut bytes).unwrap();

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.offset(), Scalar::ZERO);
assert_eq!(forged.value(), 100_000);
```

`ReceivedOutput::read` succeeds despite the output and outpoint having no demonstrated relationship to the victim scanner. The forged record can then be treated as spendable input metadata even though the claimed offset does not authorize spending the arbitrary script.
