### Title
Cached FROST preprocess seed reused across distinct messages for the same signing context causes nonce reuse and secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` derives FROST nonces deterministically from a per-`context` cached seed (`CachedPreprocesses`), and `share_internal` regenerates the same machine — and thus the same nonces — every time it is invoked for a given context. Analogous to the reported bug where an accounting variable was left uninitialized so downstream logic reused a stale state, here the cached nonce seed is not re-keyed to the message being signed: if two distinct messages are ever signed under the same `context`, the same nonce pair is committed to different challenges, leaking the validator's private key share.

### Finding Description
In `preprocess_internal`, the seed for the signing machine's ChaCha20 RNG is stored under `self.context` alone:

```rust
// coordinator/src/tributary/signing_protocol.rs
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  let (machine, _) =
    AlgorithmMachine::new(algorithm.clone(), keys.clone()).preprocess(&mut OsRng);
  ... cache.0[b] ^= encryption_key ...
  CachedPreprocesses::set(self.txn, &self.context, &cache.0);
}
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
...
let (machine, preprocess) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

`share_internal` then calls `self.preprocess_internal(participants).0`, so every share call for a given `context` rebuilds an `AlgorithmSignMachine` from the same seed. Because `seeded_preprocess` derives nonces via `ChaCha20Rng::from_seed(*seed.0)` (crypto/frost/src/sign.rs:127-141), identical nonces and commitments are produced. `sign()` computes `share = k_i + c * share_i` where `c` binds `msg` via `rho_transcript.append_message(b"message", C::hash_msg(msg))` (sign.rs:362-379). Two shares `s1 = k + c1*x`, `s2 = k + c2*x` over the same nonce yield `x = (s1 - s2)/(c1 - c2)`.

The trigger is a context collision across distinct messages: `ExpectedBatchDb::set` overwrites the stored instruction hash keyed by `(network, batch.id)` (coordinator/src/db.rs:98-108), and the signable-ID flow in `main.rs` publishes `Transaction::SubstrateSign`/`Transaction::Sign` keyed by the recognized ID. If a batch or plan is re-executed under the same ID/context with different instructions (retry, overwrite, or reorg-driven replay), the same context re-signs a different message with identical nonces.

### Impact Explanation
Any observer of the two broadcast `SignatureShare`s (all signing-set participants and the coordinator) can algebraically recover the signer's MuSig/tributary secret key share `self.key`. For the n-of-n substrate-signing MuSig (`musig(musig_context(...), self.key.clone(), participants)`), one recovered private key collapses unforgeability for that validator's signer, enabling forged tributary signatures and corrupted consensus attribution.

### Likelihood Explanation
Medium: exploitation requires the same `context` to be signed over two distinct `msg` values. The cache is deliberately keyed only on `context` with no binding to `msg`, and no check compares the message against a stored value before reusing the seed. Whether the coordinator ever re-signs a context with different data depends on DB overwrite paths (e.g., `ExpectedBatchDb::set` overwriting per `(network, id)`) and retry semantics not fully visible in the excerpted code, but the cryptographic precondition — deterministic nonce derivation from a message-independent seed — is confirmed in `seeded_preprocess`.

### Recommendation
Bind the cached-preprocess key to the message being signed (e.g., key `CachedPreprocesses` by `(context, hash(msg))`, or mix `C::hash_msg(msg)` into the encryption-key/seed derivation), and reject any `share_internal` call whose `msg` differs from the first message recorded for that context. Alternatively, generate a fresh random seed per sign invocation and persist the whole `AlgorithmSignMachine` state rather than a message-agnostic seed.

### Proof of Concept
1. Validator stores seed `S` under context `X` via `preprocess_internal`, emitting preprocess commitments `(D, E)` derived from `ChaCha20Rng::from_seed(S)`.
2. `share_internal` is called for `msg1` under context `X`: produces `share1 = d + b*e·ρ + c1·λ_i·x_i` and publishes it.
3. A second signing flow (batch re-executed under the same ID, or `ExpectedBatchDb` overwrite) invokes `share_internal` for `msg2 ≠ msg1` under context `X`. `CachedPreprocesses::get` returns `S`, regenerating identical nonces `(d, e)`.
4. `share2` uses identical nonce combination but challenge `c2` (since `rho_transcript` binds `C::hash_msg(msg)`), giving `x_i = (share1 - share2)/(c1 - c2)·λ_i⁻¹`.
5. The recovered share reveals `self.key` (the Ristretto secret), since for the tributary MuSig the secret share is the raw private key.
