## Title
Reward misattribution in `pallet-consensus-incentives` — all state-machine rewards paid to the signer of the first message in a batch - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::on_executed` collapses a whole batch of ISMP `StateMachineUpdated` events into a `BTreeMap<StateMachineId, u64>` of highest heights, then pays the block-span reward for *every* state machine in that map to a single relayer account — the signer recovered from `messages.get(0)` only. [1](#0-0) 

### Finding Description
The parameter used to compute *who gets paid* (`messages[0]`'s signer) is decoupled from the parameter used to compute *how much is paid* (the full set of `StateMachineUpdated` events in the batch, deduplicated per `state_machine_id`) — mirroring the CurveFi bug class where one derived quantity (`xs`) is computed from a different, inconsistent source than the other (`ys`), causing systematically wrong outputs.

Concretely:
- `relayer_account` is derived once, from the signature on `messages[0]` only, via `Signature::decode(...).verify_and_get_sr25519_pubkey(...)`. [2](#0-1) 
- The reward loop then iterates over **every distinct `state_machine_id`** touched by `StateMachineUpdated` events in the whole batch (not just the one tied to `messages[0]`), and calls `process_message(..., relayer_account.clone())` for each of them. [3](#0-2) 
- `process_message`/`calculate_reward` compute the reward purely from `StateMachinesCostPerBlock` and the height delta since `LastRewardedHeight`, with no check that the paid-out relayer is the one who actually delivered the proof for that particular state machine. [4](#0-3) 

If a batch of ISMP messages processed in a single `on_executed` call contains more than one `Message::Consensus` entry for different source chains (a normal batching pattern for relayers submitting multiple chain updates together), only the identity of the *first* message in the vector is credited, while the reward amount is computed and paid for **all** state machines whose commitment advanced in that batch. Whoever controls message ordering when constructing the batch (i.e., whoever assembles/submits the `Vec<Message>` that becomes `messages` and `events`) can place a cheaply-signed message of their own first, then include additional valid consensus proofs (which are public data, not privileged) for other chains, and collect the entire batch's reward under their own account — regardless of who actually produced the proofs for those other chains.

### Impact Explanation
This is a direct fund-diversion bug in a live reward-payout path: `T::Currency::transfer` moves real balance from the treasury account to `relayer_account`, and `T::ReputationAsset::mint_into` also credits that single account. [5](#0-4) 
An unprivileged party can redirect protocol-funded relayer rewards for state machines they did not deliver proofs for to their own account, at the expense of the actual relayer(s) — "wrong beneficiary" fund loss, squarely inside the bounty's accepted impact set (stealing/loss of funds, logic attacks). The `LastRewardedHeight` watermark still advances correctly (so there's no double-payment across blocks), but the *within-batch* attribution is broken every time a batch mixes consensus updates for more than one state machine.

### Likelihood Explanation
The comment in the code shows the author already fixed one variant of this bug (multiple `StateMachineUpdated` events for the *same* state machine no longer double-pay), but explicitly left the single-relayer-per-batch assumption in place for *different* state machines in the same batch — the fix only addresses the amount-side aggregation, not the beneficiary-side attribution. [6](#0-5) 
Exploitability depends on how the `messages`/`events` batch fed to `FeeHandler::on_executed` is assembled (I was not able to fully trace, within the remaining tool budget, whether a single unprivileged extrinsic submitter fully controls the ordering/composition of that batch, or whether pallet-ismp only ever batches messages from one already-authenticated relayer per call). This is the main open question that would need to be confirmed by reading `modules/pallets/ismp/src/impls.rs` and `modules/pallets/ismp/src/fee_handler.rs`, which I located but did not have remaining iterations to read in full.

### Recommendation
Track and use a per-`state_machine_id` relayer identity instead of a single batch-wide `relayer_account`: derive the signer from the specific `Message::Consensus` entry that produced each `StateMachineUpdated` event (matching consensus messages to the state machines they advanced), and pay each relayer only for the state machines their own proof actually advanced.

### Proof of Concept
Not independently executable within this investigation — the exploit requires constructing a batch (`Vec<MessageWithWeight>` plus corresponding `Vec<IsmpEvent>`) containing more than one `Message::Consensus` for distinct `StateMachineId`s, with `messages[0]` signed by the attacker and later entries being valid-but-not-attacker-authored consensus proofs, then invoking `FeeHandler::on_executed`. Confirming a full PoC would require tracing `modules/pallets/ismp/src/impls.rs` / `modules/pallets/ismp/src/fee_handler.rs` to verify how `messages` and `events` are populated per call and whether an unprivileged caller controls their contents — this could not be completed before the iteration budget ran out.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}
