## Analysis

The reported bug class is: **a threshold parameter that gates value distribution has no upper bound, so setting it too high causes funds/rewards to become effectively undistributed/redirected instead of reaching their intended recipients.**

The closest reachable analog in Kaia is the governance parameter `reward.stakingrewardthreshold` (`gov.RewardStakingRewardThreshold`), which gates the Flex reward scheme's per-validator staking-reward eligibility, exactly like `wethConversionThreshold` gated fee-compounding eligibility.

### Root cause

`RewardStakingRewardThreshold`'s `FormatChecker` only checks that the value is non-negative — there is no upper bound and no cross-validation against `MinimumStake`: [1](#0-0) 

Compare this to `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, which *do* get a `checkConsistency` cross-check against each other before being accepted into a vote: [2](#0-1) 

`RewardStakingRewardThreshold` (along with `RewardMinimumStake`, `RewardRatio`, etc.) is only subject to format checks with no consistency check, per `checkConsistency`'s catch-all case: [3](#0-2) 

The threshold is then consumed directly in `assignStakingRewardsFlex`, where any validator whose stake does not exceed `threshold` is excluded from the "excess-stake" pool used to distribute the staker reward budget: [4](#0-3) 

The test suite explicitly demonstrates the consequence when the threshold is set above all validators' stakes: **all staker rewards are redirected to the block proposer instead of being distributed to stakers** ("flex, all below threshold, no staking reward" — `Stakers: big.NewInt(0)`, with the entire staker budget added into `Proposer`): [5](#0-4) 

### Title
Unbounded `reward.stakingrewardthreshold` governance parameter can redirect all staker rewards to the proposer - (File: kaiax/gov/param.go, kaiax/reward/impl/getter.go)

### Summary
The `reward.stakingrewardthreshold` governance parameter used by the Flex reward distribution scheme (`reward.useflexreward = true`) has no upper bound validation. Its `FormatChecker` only requires the value to be non-negative, and `checkConsistency` performs no cross-check against `reward.minimumstake` or realistic staking amounts, unlike the analogous KIP-71 base-fee bounds which are mutually validated.

### Finding Description
`Params[RewardStakingRewardThreshold].FormatChecker` accepts any `*big.Int` with `Sign() >= 0`, with no maximum value enforced (`kaiax/gov/param.go` lines 497-515). Governance votes for this parameter go through `headerGovModule.checkConsistency`, but `RewardStakingRewardThreshold` falls into the generic case that performs no further validation, unlike `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` which are checked against each other (`kaiax/gov/headergov/impl/header.go` lines 188-219).

The threshold is consumed in `assignStakingRewardsFlex` (`kaiax/reward/impl/getter.go` lines 421-483), where a validator's excess stake is only counted if `amount > threshold`. If governance sets the threshold above every validator's actual stake (e.g. a value far exceeding realistic total network stake), `totalExcessInt` becomes `0` for all validators, and the entire staker reward budget is folded back into the proposer's reward as a "remainder" rather than being distributed to stakers, as confirmed by the "flex, all below threshold, no staking reward" test case.

### Impact Explanation
This causes systematic reward misallocation: the staker-reward portion of every block's minting reward is diverted entirely to the block proposer instead of being distributed proportionally among staking validators, for as long as the malicious/misconfigured threshold value remains active. This is a concrete reward redirection affecting the protocol's token economy and validator incentives network-wide, not merely a stuck/idle-funds inconvenience — the funds are actively redirected to the proposer address every block.

### Likelihood Explanation
Requires a governance vote to set `reward.stakingrewardthreshold` to an unreasonably large value. Voting itself requires reaching the governing/validator vote path, but there is no on-chain safeguard preventing the parameter from being set to an absurd or attacker-favorable value once a vote is cast and accepted, since neither `FormatChecker` nor `checkConsistency` enforces any reasonable upper limit (unlike KIP-71 bounds, which mutually constrain each other).

### Recommendation
Add an upper-bound `FormatChecker` for `RewardStakingRewardThreshold`, and/or add a `checkConsistency` rule requiring `StakingRewardThreshold` to remain within a sane range relative to `RewardMinimumStake` and realistic total staking supply, mirroring the mutual bound checks already implemented for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`.

### Proof of Concept
1. Submit/accept a governance vote setting `reward.stakingrewardthreshold` to a value larger than the sum of all validators' realistic stake (e.g. `MaxUint256` or any value exceeding total possible stake).
2. `FormatChecker` and `checkConsistency` both accept the value since only non-negativity is enforced.
3. In `assignStakingRewardsFlex`, no validator's `amount > threshold` holds, so `totalExcessInt == 0` and `alloc` is empty; the full `budget` remains in `remaining` and is added to the proposer's reward instead of stakers, as demonstrated by the existing unit test at `kaiax/reward/impl/getter_test.go` lines 1082-1100 ("flex, all below threshold, no staking reward").

// assignStakingRewardsFlex assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}
