### Title
ECDH shared decryption key exposed via `Debug` impl on `EncryptionKeyProof` - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`EncryptionKeyProof` derives `Debug`, and one of its fields — `key: Zeroizing<C::G>` — is the ECDH shared point that is the sole secret input to the stream cipher protecting DKG share messages. Any debug/trace logging, error formatting, or panic message that prints an `EncryptionKeyProof` writes the shared decryption key to log output, where parties with log access (admins, aggregators, crash reporters) can use it to decrypt a threshold secret share. This mirrors the reported class: authentication secrets written to accessible logs.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `EncryptionKeyProof` is defined as:

```rust
#[derive(Clone, PartialEq, Eq, Debug, Zeroize)]
pub struct EncryptionKeyProof<C: Ciphersuite> {
  key: Zeroizing<C::G>,
  dleq: DLEqProof<C::G>,
}
``` [1](#0-0) 

`key` is not a public value. It is the ECDH result `ecdh(private, public) = public * private` (`fn ecdh` at lines 95–97), and `fn cipher` derives the ChaCha20 key solely from this shared point plus the public `context` (lines 101–133). Knowledge of `key` is therefore exactly equivalent to knowledge of the message encryption key.

The proof is created inside `Encryption::decrypt`, which computes `let key = ecdh::<C>(&self.enc_key, msg.key)` and returns it inside the `EncryptionKeyProof` (lines 487–499). The proof's purpose is blame: it is handed to other parties/protocol layers so they can call `Decryption::decrypt_with_proof`, which uses `proof.key` directly in `cipher::<C>(...).apply_keystream(...)` to recover the plaintext share (lines 381–393).

The contrast with the sibling type shows this was not considered: `Encryption<C>` has a hand-written `fmt::Debug` that deliberately omits `enc_key` via `finish_non_exhaustive`, printing only `context`, `i`, `enc_pub_key`, and `decryption` (lines 410–419). `EncryptionKeyProof` was given a derived `Debug` that prints its secret field in full. `Zeroizing` forwards `Debug` transparently, so `key` formats as the full elliptic-curve point encoding.

Note on threat model: the proof is intentionally disclosed during blame resolution, so leaking it to the *blame participants* is by design. The vulnerability is the accidental disclosure channel — a `{:?}`/`{proof:?}` in a log macro, a `Debug`-formatted error propagated into logs, or a `dbg!`/`expect`/`assert` failure printing the struct — which exposes the key to *anyone with log access*, not just the intended decryptor, and persists it. An unprivileged DKG participant can force proofs to be generated (and thus logged) by sending a malformed `EncryptedMessage` that fails `msg.pop` verification or share validation, triggering the blame path at scale.

### Impact Explanation
Whoever reads the log obtains `key`, computes `cipher(context, &key)` — `context` is the public session/context value — and decrypts the corresponding `EncryptedMessage` ciphertext, which carries a PedPop/FROST secret share. A single leaked key decrypts one targeted share; if an attacker can force or observe blame proofs for `t` shares of a `t-of-n` threshold key, they can reconstruct the group secret or key shares. This is direct secret-material exposure via the logging channel, matching the report's class.

### Likelihood Explanation
Medium. Exploitation requires (a) a code path that `Debug`-formats the proof into logs/errors — plausible given `Message` types in the same file are bound by `fmt::Debug` (line 40) and error/reporting paths in the processor format such structures — and (b) an adversary who can trigger blame generation by submitting malformed messages, plus access to the logs (operator, log pipeline, crash reports). The flaw itself is unconditional: the secret is unconditionally included in the `Debug` output.

### Recommendation
Implement `fmt::Debug` manually for `EncryptionKeyProof` that prints only the `dleq` field (or a redacted marker) and calls `finish_non_exhaustive`, mirroring the `Encryption<C>` impl at `crypto/dkg/pedpop/src/encryption.rs:410`. Also consider removing `Debug` from the `sealed::Message` bound or auditing every `Debug`-printing use of blame structures upstream. `Zeroize` should continue to cover `key`.
