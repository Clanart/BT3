### Title
Deterministic FROST nonce reuse across `share`/`complete` invocations allows recovery of a validator's MuSig secret share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a FROST `CachedPreprocess` seed in the DB keyed only on `context` and deterministically re-derives the *same* nonces on every call (`AlgorithmSignMachine::from_cache` → `seeded_preprocess`). `share_internal` is invoked once by `share()` and **again** by `complete()` (which re-runs `share_internal`), and `share()` may additionally be called for multiple `key_pair`s under the same `(b"DkgConfirmer", attempt)` context. If any two of these invocations observe a different `msg` or a different `preprocesses` map, the validator emits multiple Schnorr shares of the form `s_i = d + e·ρ_i + c_i·λ·x` over the same nonce seed. Since `ρ_i` (binding factor) and `c_i` (challenge) are publicly computable, three such shares form a solvable linear system in `{d, e, x}`, yielding the validator's root MuSig secret share.

### Finding Description
- `preprocess_internal` loads or creates a 32-byte seed under `CachedPreprocesses[context]` and reconstructs the sign machine with `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` (coordinator/src/tributary/signing_protocol.rs:123-145). `from_cache` calls `seeded_preprocess`, so the nonce scalars `(base, actual)` are a deterministic function of the seed.
- `share_internal` rebuilds that machine and calls `machine.sign(preprocesses, msg)` (lines 150-180). Inside `sign` (crypto/frost/src/sign.rs:283-411), the effective nonce is `base + actual·ρ`, where `ρ` is derived from a transcript binding `group_key`, `hash_msg(msg)`, and the hash of all preprocesses (lines 361-371). Different `msg` or different preprocess sets ⇒ different `ρ`, but the *same underlying* `(base, actual)` pair.
- Two distinct call sites reuse the same context: `DkgConfirmer::share` (line 304) and `DkgConfirmer::complete` (line 312), the latter calling `share_internal` a second time with the `preprocesses`/`key_pair` carried by the final block data. Any divergence between the preprocess map/message seen at `share` time and at `complete` time — or a second `share` for a distinct `key_pair` under the same attempt — produces a second share over the same nonce seed.
- The file's own safety argument (lines 34-54) is that BFT ordering guarantees identical bytes and explicitly leaves verification that "the commitments generated from the decided nonces are in fact its commitments on-chain" as a `TODO` (line 51), i.e., the guard preventing divergence does not exist. Shares are broadcast publicly, so the published `s_i` values plus the public preprocesses/`msg` give any observer the equations `s_i = d + e·ρ_i + c_i·λ_i·x`. With three distinct `ρ`/`c` tuples, `x` (the validator's MuSig private key, `self.key`) is recovered algebraically.

### Impact Explanation
Recovery of `self.key` — the validator's root Ristretto secret used to confirm DKG results via MuSig — lets an attacker forge that validator's `set_keys` confirmation signatures and any other signatures produced with the same validator key, equating to remote compromise of a consensus participant's signing identity and the ability to push attacker-chosen threshold key confirmations on-chain.

### Likelihood Explanation
The trigger is not exotic: `share()` and `complete()` are separate entry points that independently re-execute `share_internal`, and `share()` itself is parameterized by caller-supplied `preprocesses` and `key_pair`. A single inconsistent `key_pair` confirmation or a differing preprocess map reaching `complete` (e.g., mempool-observed vs. block-committed data) creates distinct `ρ`s under one seed. The code already acknowledges this is possible via "a logical flaw" or rebuild paths and leaves the defensive check unimplemented, so the invariant is enforced by assumption rather than code.

### Recommendation
Never reuse a cached preprocess seed across calls that can observe different inputs. Options: key `CachedPreprocesses` by the full hash of `(participants, msg, preprocesses)` and refuse to sign if a different input set is presented for the same context; burn the cached entry after first `sign` and regenerate; or implement the noted TODO — before publishing a share, verify the nonce commitments in the received set match the commitments derived from the cached seed.

### Proof of Concept
1. Context `C = (b"DkgConfirmer", attempt)`. `preprocess_internal` stores seed `S` once; every machine built from `S` has identical `(d, e)` nonce scalars.
2. Invocation 1 (`share` or `complete`): inputs `(P_1, msg_1)` → `ρ_1`, `c_1`, share `s_1 = d + e·ρ_1 + c_1·λ·x` (published).
3. Invocations 2 and 3 with `(P_2, msg_2)`, `(P_3, msg_3)` — e.g., `share`/`complete` seeing different preprocess maps or different `key_pair`s — yield `s_2, s_3` with `ρ_2,ρ_3,c_2,c_3`.
4. Solve the 3×3 linear system over the Ristretto scalar field for `(d, e, λ·x)`; divide by the known Lagrange coefficient `λ` (participant indexes are public) to obtain `x`, the validator's MuSig secret share. Verification: `x·G` equals the validator's public key in `spec.validators()`.

I could not fully trace whether `share()` is invoked for multiple `key_pair`s within one attempt in this codebase version, nor confirm the exact divergence of `complete`'s preprocess map versus `share`'s; the finding rests on the code-visible reuse of a deterministic nonce seed across independently-parameterized `share_internal` calls combined with the explicitly unimplemented consistency check (TODO at line 51).
