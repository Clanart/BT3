## Analysis

The onERC721Received analog is: an entrypoint that mutates protocol state is reachable by any caller, without any check that the caller is the intended party. Searching Clementine's RPC layer for the equivalent "the caller reaching a signing or state-changing method versus the party it is meant for" binding surfaces the aggregator's authentication model.

Clementine authenticates verifier/operator gRPC servers via an mTLS interceptor that restricts `Internal*`-prefixed methods to the entity's own certificate [1](#0-0) [2](#0-1) . But the project's own documentation states this protection does not apply to the aggregator: "The aggregator does not enforce client certificates but does use TLS for encryption" [3](#0-2) , and `create_aggregator_grpc_server` merely warns when `client_verification` is enabled rather than forcing it [4](#0-3) . When `client_verification` is false, the interceptor becomes `Noop`, so the `is_internal()` gate that would otherwise restrict `Internal*` methods to self is never evaluated [5](#0-4) [6](#0-5) .

The aggregator exposes `InternalSendTx`, an `Internal`-prefixed, state-changing/broadcasting RPC meant only for the aggregator's own internal callers [7](#0-6) . Its handler takes an arbitrary caller-supplied raw transaction and fee type and inserts it directly into the tx-sender's send/fee-bump queue [8](#0-7) . The tx-sender's RBF/CPFP logic funds and signs transactions using the bridge's own operational Bitcoin wallet (`fund_raw_transaction`, `sign_raw_transaction_with_wallet`) before broadcasting [9](#0-8) .

### Title
Unauthenticated `InternalSendTx` call on the aggregator lets any network caller force the bridge wallet to fund and broadcast arbitrary transactions - ([File: core/src/rpc/aggregator.rs])

### Summary
The aggregator gRPC service intentionally runs without client-certificate enforcement, per the documented deployment model. This means the `InternalSendTx` RPC — an `Internal`-prefixed method that is supposed to be reachable only by the aggregator itself — is reachable by any unauthenticated network client, exactly mirroring the `onERC721Received` analog where a callback meant for a restricted party is open to anyone.

### Finding Description
Verifier/operator servers restrict `Internal*` RPCs to the entity's own certificate via `only_aggregator_and_self` [10](#0-9) . The aggregator, however, is documented and configured to skip this enforcement [3](#0-2) , so its interceptor resolves to `Noop` and no cert-based restriction is applied to any of its RPCs, including `InternalSendTx` [6](#0-5) .

`internal_send_tx` accepts an arbitrary, fully attacker-controlled `raw_tx` plus `fee_type`, and unconditionally queues it via `TxSenderClient::insert_try_to_send`, with no check that the caller is the aggregator's own automation task or that the transaction is bridge-related [8](#0-7) . The tx-sender then funds/signs/broadcasts this transaction using the bridge's shared Bitcoin wallet when RBF/CPFP fee types are requested [9](#0-8) .

The binding broken: "a caller reaching a signing or state-changing method versus the party it is meant for." Before the attacker's request: only the aggregator's own automation tasks can invoke `Internal*` methods (as intended and as enforced on verifier/operator). After: any network peer can invoke the aggregator's `InternalSendTx`, an equality that should hold (`caller == aggregator-self`) is broken.

### Impact Explanation
This is an unauthenticated state-changing/broadcasting call reaching a method meant only for the entity itself. An attacker can repeatedly submit arbitrary transactions to be funded (via CPFP) and broadcast through the bridge's own operational wallet, causing the bridge's Bitcoin funds to be spent paying fees for transactions unrelated to bridge operation, and polluting the tx-sender's send/fee-bump queue and database state that legitimate bridge transactions rely on.

### Likelihood Explanation
High — any party with network access to the aggregator's gRPC endpoint (which, per the documented and configured deployment model, requires no client certificate) can call this RPC directly with no further preconditions.

### Recommendation
Enforce the same `is_internal` / self-certificate restriction on the aggregator's own gRPC server that is already applied to verifier and operator servers, regardless of the `client_verification` toggle used for public-facing methods — i.e., always require the aggregator's own identity for any `Internal*`-prefixed RPC, even when general client verification is disabled for the aggregator's public methods.

### Proof of Concept
1. Deploy the aggregator per documented configuration (`client_verification` disabled / no client cert enforcement, as `docs/usage.md` describes).
2. From any unauthenticated network client, open a gRPC/TLS connection to the aggregator without presenting an aggregator or self client certificate.
3. Call `InternalSendTx` with an arbitrary attacker-supplied `raw_tx` and `fee_type = Rbf`/`Cpfp` [8](#0-7) .
4. Observe the aggregator's tx-sender fund/sign/broadcast the submitted transaction using the bridge's own wallet [9](#0-8) , confirming the internal-only method was reached without any authorization check.

```rust
#[allow(clippy::result_large_err)]
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
```

```rust
pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
```

```rust
    async fn internal_send_tx(

        request: Request<clementine::SendTxRequest>,

            Err(Status::unimplemented("Automation is not enabled"))

        #[cfg(feature = "automation")]
        {
            let send_tx_req = request.into_inner();
            let fee_type = send_tx_req.fee_type();
            let signed_tx: bitcoin::Transaction = send_tx_req
                .raw_tx
                .ok_or(Status::invalid_argument("Missing raw_tx"))?
                .try_into()?;
            tracing::warn!(
                "Internal send tx rpc called with feetype: {:?}, tx hex: {}",
                fee_type,
                bitcoin::consensus::encode::serialize_hex(&signed_tx)
            );

            let mut dbtx = self.db.begin_transaction().await?;
            self.tx_sender
                .insert_try_to_send(
                    &mut dbtx,
                    None,
                    &signed_tx,
                    fee_type.try_into()?,
                    None,
                    &[],
                    &[],
                    &[],
                    &[],
                )
                .await
                .map_to_status()?;
            dbtx.commit()
                .await
                .map_err(|e| Status::internal(format!("Failed to commit db transaction: {e}")))?;
            Ok(Response::new(Empty {}))
        }
    }
```
