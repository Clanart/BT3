### Title
Arbitrary `address` field in permissionless `handle_unsigned`/`handle_get_requests` allows minting reputation rewards to any attacker-chosen account - (File: modules/pallets/state-coprocessor/src/impls.rs)

### Summary
`handle_get_requests` mints `pallet_messaging_incentives::ReputationAsset` directly to the `address` field taken verbatim from the caller-supplied `GetRequestsWithProof` message, with no binding to the transaction submitter or the entity that actually delivered the proofs.

### Finding Description
The only extrinsic that reaches `handle_get_requests` is `handle_unsigned`, which is dispatched via `ensure_none(origin)` — i.e. it is an unsigned transaction with no authenticated caller at all: [1](#0-0) 

Validity for the unsigned transaction pool is determined only by `validate_state_machine`/proof checks inside `handle_get_requests` itself, and the "provides" tag used for mempool dedup is derived from the request hashes, not from `address`: [2](#0-1) 

Inside `handle_get_requests`, after verifying the source/response state proofs (which certify that the *requests and their state values* are authentic — they say nothing about *who* submitted this particular transaction), the pallet computes `total_bytes` and mints reputation straight to the attacker-controlled `address`: [3](#0-2) 

The `GetRequestsWithProof` struct itself defines `address` as a plain caller-supplied `Vec<u8>` with a comment saying it is "the relayer's raw 32-byte public key as supplied by the coprocessor" — but nothing in the extrinsic path enforces that this bytes32 corresponds to the actual submitter, signer, or any account that performed relay/proof-fetching work: [4](#0-3) 

Because the call is unsigned (`ensure_none`), there is no `T::AccountId` derived from a signature to compare against `address`, and the code never performs such a comparison. State proofs are public, non-secret data — any node that observes/derives the source/response proofs for a `GetRequestsWithProof` batch (including a party who simply copies a batch already broadcast in the transaction pool, changing only the `address` field, since `address` is not part of the proof-verification or dedup logic) can resubmit it naming an arbitrary account.

### Impact Explanation
This breaks the reward/reputation accounting invariant: reputation/bandwidth-consumption tokens minted per delivered byte must go to the account that did the relaying/proof-fetching work, not to an arbitrary caller-chosen address. An attacker can mint `ReputationAsset` balance to any account for free by simply relaying (or replaying) valid `GetRequestsWithProof` batches and naming a different beneficiary than whoever actually incurred the work/cost, inflating rewards without doing the corresponding service. Given `ReputationAsset`/`MintPerByte` in `pallet_messaging_incentives` exists specifically to reward genuine relaying, this allows economic value (minted tokens) to be diverted to an uninvolved beneficiary — a wrong-beneficiary/reward-accounting violation, matching the bounty's "broken timeout/refund/reward accounting" and "wrong beneficiary" impact categories.

### Likelihood Explanation
The path is fully unauthenticated (`ensure_none`) and requires only a valid, otherwise-unremarkable `GetRequestsWithProof` batch — the state/source proofs are the only cryptographic gate, and they are independent of `address`. Any party capable of observing or constructing a valid proof batch (including simply changing the `address` field of a batch already visible in the mempool or emitted via events, before the honest relayer's copy is included, subject to the block being produced only once due to `dedup_requests`/receipt checks) can redirect the mint. This is a low-effort, repeatable attack pattern once a party can produce or intercept a single valid batch.

### Recommendation
Bind the reputation mint target to a cryptographically-verified identity rather than an arbitrary field in the payload:
- If the intent is to reward the actual transaction submitter, require the call to be signed and mint to `ensure_signed(origin)`'s account instead of the caller-chosen `address` field, or
- If unsigned submission must be preserved (e.g., for off-chain worker relayers), require `address` to be authenticated via a signature over the batch (e.g., the relayer signs the batch/commitment with the key corresponding to `address`, and `validate_unsigned`/`handle_get_requests` verifies that signature) before minting.
Additionally, ensure `address` participates in the `validate_unsigned` `provides` tag (or an equivalent commitment) so that proof-batch replay with a different `address` cannot bypass the existing dedup protection.

### Proof of Concept
1. Observe (or construct) a valid `GetRequestsWithProof` batch `M` with correct `source`/`response` proofs, e.g. one submitted to the transaction pool by an honest relayer with `address = X`.
2. As attacker, construct `M' = M` but with `address = Y` (an account the attacker controls, uninvolved in fetching/relaying the proofs).
3. Submit `M'` via `handle_unsigned` (unsigned transaction, `ensure_none` origin — no signature/identity check ties `Y` to the submission).
4. `handle_get_requests` verifies the (unchanged, still-valid) source/response proofs, computes `total_bytes`, and calls `ReputationAsset::mint_into(&Y, amount)`.
5. Assert: `Y`'s `ReputationAsset` balance increased by `amount` despite `Y` performing no proof-fetching or relaying work, and no check rejected the mismatch between the payload's `address` and any authenticated submitter identity (none exists, since the call is unsigned).
