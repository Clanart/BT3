## Verdict: Valid finding (design flaw with real, if narrow, security-relevant impact)

### Title
Untracked-file/staged-delete path collision in `buildStatusMap` silently discards a staged deletion, causing GitHub Desktop to commit file content the user intended to delete - ([File: app/src/lib/git/status.ts])

### Summary
`buildStatusMap` builds the `Map<string, WorkingDirectoryFileChange>` that becomes the working directory's change list and, ultimately, the exact list of files that `createCommit` re-stages before committing. When a path has both a staged deletion (tracked entry) and a freshly recreated untracked file at the identical path, the reducer explicitly deletes the prior map entry for that key and replaces it with the untracked ("new file") entry: [1](#0-0) 

Because `Map` keys on `entry.path`, only one `WorkingDirectoryFileChange` can ever exist per path, so the staged-delete record is unconditionally overwritten rather than merged or flagged.

### Finding Description
`getStatus` reduces the porcelain-v2 entries into `files` via `buildStatusMap`, and this exact map (through `WorkingDirectoryStatus.fromFiles`) is what populates the visible Changes list: [2](#0-1) 

Git itself, when a path is staged for deletion (removed from the index) and a new, un-added file appears on disk at the same path, reports two separate status records for that path: one ordinary "index=Deleted" record and one `??` untracked record. `buildStatusMap`'s comment ("we should ensure that we only draw one entry ... remove it if found") shows this collapsing behavior is intentional, but it always favors the untracked record and completely discards the staged-delete `WorkingDirectoryFileChange`, with default selection `DiffSelectionType.All`: [3](#0-2) 

The consequence surfaces at commit time. `createCommit` always clears the index first and re-stages *only* the files passed in (which come from this same collapsed map), so whatever `AppFileStatusKind` survived the collision is what actually gets applied to the index: [4](#0-3) 

Since the surviving entry is typed as a new/untracked file rather than a deletion, `stageFiles` adds the recreated file's *current* working-tree content to the index instead of recording the deletion. The commit therefore keeps/updates the file rather than deleting it, silently reversing the user's earlier `git rm`/staged-delete action, with the Changes list showing only "New file: path" and no indication that a conflicting deletion was ever staged.

### Impact Explanation
This is a "silent corruption of what the user commits" case: the user explicitly staged removal of a file, but the resulting commit keeps the file (with whatever content happens to be on disk at that path) without any warning or diff cue distinguishing this from an ordinary new-file addition. In a supply-chain-relevant scenario, a repository-provided build script, watcher, linter/formatter hook, or `postcheckout`/`prepare-commit-msg` style automation bundled in the untrusted repository could recreate a file at a path the user just deleted (e.g., a generated artifact, lockfile, or config the user is trying to purge) between the deletion staging step and the commit action, causing Desktop to re-add attacker-influenced content into history under the guise of "New file" while masking the fact the deletion never happened.

### Likelihood Explanation
Likelihood is low-to-moderate. It requires a specific interleaving: (1) user stages a delete for path P, (2) something (an npm/yarn/hook script from the untrusted repo, an editor autosave, a build watcher) recreates an untracked file at path P before the user commits, and (3) the user commits with the default "select all" selection without noticing the Changes list shows "New file" instead of "Deleted" for P. This is plausible in real workflows involving generated/build files but is not attacker-triggerable purely on clone/fetch without some local process re-creating the file - it depends on repo-provided automation actually running in the user's environment during the relevant window.

### Recommendation
`buildStatusMap` should not collapse the two records into one another silently. Either:
- Key the map by `path` **and** kind so both the staged-deletion and untracked-new entries can coexist and be surfaced distinctly to the user, or
- When a collision is detected, synthesize a single `Renamed`/`Modified`-style change that accurately reflects "delete overwritten by new content" so the Changes list and diff view make the conflict visible, or at minimum
- Preserve/prioritize the staged-delete status and surface a warning banner rather than silently defaulting to the untracked file when both exist for the same path.

### Proof of Concept
```
git init repo && cd repo
echo "original" > file.txt
git add file.txt && git commit -m "init"

# Stage a deletion
git rm --cached file.txt   # file.txt removed from index (staged delete), still on disk is now gone via rm - use `rm file.txt` if needed
rm -f file.txt

# Simulate a repo-provided script recreating the file after the user staged the delete
echo "attacker content" > file.txt   # untracked file at same path

# Open in GitHub Desktop: Changes list shows only "New file: file.txt" (via buildStatusMap collision)
# Select All (default) -> Commit
git show HEAD:file.txt   # shows "attacker content" - the deletion was never committed
```
Instrumenting `buildStatusMap` (app/src/lib/git/status.ts:320-326) with a log statement confirms the staged-delete `WorkingDirectoryFileChange` is deleted from the map and replaced by the untracked entry, and `createCommit`'s `unstageAll` + `stageFiles` (app/src/lib/git/commit.ts:26-31) confirms only the surviving untracked entry is staged for the final commit.
