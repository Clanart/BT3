Based on the evidence gathered, the strongest local analog is the token-agnostic relayer fee ledger in `pallet-ismp-relayer`.

### Title
Relayer `Fees` ledger stores a bare `U256` amount with no token binding, so a fee-token change lets accrued balances be paid out in the wrong token/value - ([File: modules/pallets/relayer/src/lib.rs])

### Summary
`pallet-ismp-relayer` accumulates relayer rewards into `Fees<T>: StorageDoubleMap<StateMachine, Vec<u8>, U256>` [1](#0-0) . The stored value is a raw amount with no record of which ERC20 (`fee_token`) it was denominated in at accumulation time. When a relayer later withdraws, `Pallet::withdraw` reads the *current* `fee_token` from `HostParams::<T>::get(dest_chain)` and instructs the destination `HostManager` to pay out `available_amount` of *that* token [2](#0-1) . This is structurally the same defect as the reported Treasury bug: value is tracked as an undifferentiated balance while the "currency" it's paid out in is resolved separately and later, so a change to that currency silently reinterprets old balances.

### Finding Description
Fee accumulation (`Pallet::accumulate` / `accumulate.rs`) increments `Fees::<T>::try_mutate(state_machine, address, ...)` with `total_fee`, a `U256` with no token identifier attached [3](#0-2) . This fee amount is proven from the source chain's `RequestCommitments`/`FeeMetadata`, which was denominated in whatever `feeToken` the source `EvmHost` had configured at dispatch time.

At withdrawal time, the EVM payout path builds `WithdrawalParams { beneficiary_address, amount: available_amount, token: params.fee_token }`, where `params.fee_token` comes from `HostParams::<T>::get(withdrawal_data.dest_chain)` — i.e., the *host executive pallet's current record* of that chain's fee token, not the token that was actually in effect when the fee was earned [2](#0-1) .

On the EVM side, `EvmHost.withdraw()` and `HostManager` payouts blindly transfer `params.token` for `params.amount`, with only a guard that blocks changing `feeToken` while the *host's own balance* of the old token is non-zero [4](#0-3) . That guard checks the host contract's ERC20 balance, not the separate, off-chain-tracked `Fees<T>` ledger on Hyperbridge (a different chain's storage). So:

1. Governance can legitimately update `feeToken` on `EvmHost` as long as the host's balance of the old token happens to be zero at that moment (e.g., because outstanding revenue was already swept via `withdraw()`).
2. Relayers with an *already-accrued but unwithdrawn* `Fees<T>` balance denominated in the old token now have that same numeric `U256` amount reinterpreted and paid out in the new `fee_token` on the next `withdraw_fees` call.
3. Because ERC20 tokens differ in decimals and value, the relayer either receives a windfall (if the new token is worth more per unit or has fewer decimals) or is shortchanged (opposite case) — the exact "withdraw a token different than deposited" defect from the seed report, applied to a fee ledger instead of a treasury.

### Impact Explanation
This breaks the invariant that bridged/accrued value must move exactly once and only in the correct amount to the correct beneficiary. A token/decimals mismatch between accrual and withdrawal directly causes fund loss (relayer underpaid, difference stranded/unaccounted) or a false-value credit (relayer overpaid from the `HostManager`'s general balance, effectively stealing value earned by other relayers or funded by other fee payers) — this is loss/theft of bridge funds, not just a bookkeeping annoyance.

### Likelihood Explanation
Triggering requires the EVM host's `feeToken` to be changed via the normal cross-chain governance `updateHostParams` flow while there exist accrued-but-unwithdrawn entries in `Fees<T>` for that destination chain — a realistic operational sequence (e.g., migrating stablecoins) rather than an attacker-controlled exploit. No malicious relayer, prover, or admin is required beyond a routine, otherwise-authorized fee-token migration; the bug is the *absence* of a check tying `Fees<T>` balances to a token identifier, not misuse of privilege.

### Recommendation
- Extend `Fees<T>` (and the accumulate/withdraw code paths) to store the fee token address alongside the amount, e.g. `StorageDoubleMap<StateMachine, Vec<u8>, (H160, U256)>`, keyed or additionally indexed by the token that was active at accumulation time.
- On `withdraw`, use the token stored with the balance rather than re-reading `HostParams`'s current `fee_token`.
- When governance changes `feeToken` on `EvmHost`/`HostParams`, require settlement (or migration) of all outstanding `Fees<T>` balances denominated in the old token before the change is permitted, mirroring the existing `CannotChangeFeeToken` host-balance check but scoped to the Hyperbridge-side ledger.

### Proof of Concept
Conceptual sequence (cannot be executed without a full test harness, but derivable from cited code):
1. Relayer delivers messages priced in `feeToken = TokenA`; `Pallet::accumulate` credits `Fees::<T>::get(Evm(1), relayer) = 1000` (`accumulate.rs:134-147`).
2. Governance sweeps `EvmHost`'s `TokenA` balance to zero via `EvmHost.withdraw()` (`EvmHost.sol:651-660`), then calls `updateHostParams` setting `feeToken = TokenB`; the guard at `EvmHost.sol:617-621` only checks the host's own `TokenA` balance (now zero) and passes.
3. Relayer calls `withdraw_fees`; `withdrawal.rs:144-158` builds `WithdrawalParams{ amount: 1000, token: TokenB }` using the *now-current* `fee_token`.
4. `HostManager`/`EvmHost` transfers `1000` units of `TokenB` to the relayer even though the fee was earned in `TokenA` units — a value mismatch identical in kind to the seed report's DAI/USDC confusion.
