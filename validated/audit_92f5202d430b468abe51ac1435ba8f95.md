### Title
Debug-mode JSON parser logging leaks unredacted sensitive field values via `PROTOBUF_DEBUG` / `ABSL_DLOG` - (File: `src/google/protobuf/json/internal/parser.cc`)

### Summary
The external report describes `snyk-broker` logging private keys in plaintext when its logging level is set to `DEBUG` (CWE-532, information exposure through log files). The analogous Protobuf behavior is in the JSON parsing entry points `JsonStreamToMessage` and `JsonToBinaryStream`, which, when the library is built with the opt-in flag `PROTOBUF_ENABLE_DEBUG_LOGGING_MAY_LEAK_PII`, unconditionally log the full raw input payload and the full decoded message contents via `ABSL_DLOG(INFO)`, without applying the field-level `debug_redact` protection that Protobuf's own `DebugString()`/`TextFormat` redaction mechanism is designed to provide.

### Finding Description
`JsonStreamToMessage` and `JsonToBinaryStream` gate extra logging behind the compile-time flag `PROTOBUF_DEBUG` (derived from `PROTOBUF_ENABLE_DEBUG_LOGGING_MAY_LEAK_PII` in `src/google/protobuf/port_def.inc:705-710`): [1](#0-0) 

When enabled, `JsonStreamToMessage` logs the client-supplied JSON payload and the fully parsed message's `DebugString()`: [2](#0-1) 

`JsonToBinaryStream` similarly buffers and logs both the raw input hex-escaped bytes and the resulting serialized binary output: [3](#0-2) [4](#0-3) 

Protobuf has a schema-driven redaction mechanism specifically intended to keep sensitive field values (e.g., credentials, tokens, keys) out of debug output: the `debug_redact` field option, documented as "Indicate that the field value should not be printed out when using debug formats, e.g. when the field contains sensitive credentials": [5](#0-4) 

That redaction, however, is only applied by `TextFormat::Printer` when `redact_debug_string_` is explicitly set (e.g., via `DebugFormat`/`TextFormat::Printer::SetRedactDebugString`): [6](#0-5) 

The default `Message::DebugString()` used inside `JsonStreamToMessage`'s `ABSL_DLOG` call does not enable this redaction flag, so any field annotated `debug_redact = true` — the exact mechanism designed to prevent leaking "sensitive credentials" — is printed in full in the debug log, alongside the entire raw request payload. This mirrors the Snyk Broker flaw: a debug/verbose logging mode that bypasses the application's own safeguard against exposing secrets.

### Impact Explanation
If a consuming application builds Protobuf with `PROTOBUF_ENABLE_DEBUG_LOGGING_MAY_LEAK_PII` (the macro name itself acknowledges the risk) and processes attacker- or user-supplied JSON containing fields marked `debug_redact` (a common pattern for tokens/credentials embedded in protobuf-modeled requests, e.g. OAuth tokens, API keys, passwords), those values are written verbatim to logs at DEBUG/INFO log level, including the complete raw and decoded payload. This is an information exposure of sensitive data through logs, matching CWE-532, and is a direct functional analog of the Snyk Broker advisory although scoped to Protobuf's JSON codec logging path rather than an RPC private key. Confidentiality impact is High if such logs are less protected than the RPC channel itself.

### Likelihood Explanation
Exploitability requires the consuming application to have compiled Protobuf with the non-default flag `PROTOBUF_ENABLE_DEBUG_LOGGING_MAY_LEAK_PII` and to have log verbosity set to allow `ABSL_DLOG(INFO)` output (also requires a non-`NDEBUG`-suppressed `DLOG` build in most Abseil logging configurations). This is not the default state, which lowers likelihood relative to the original CVE (where DEBUG level alone was sufficient with no separate compile flag). However, once that debug configuration is enabled — which operators may do temporarily for troubleshooting production issues, exactly the scenario in the original advisory — every JSON parse request from an ordinary client causes full-payload and full-message logging, with no per-field redaction despite the schema declaring `debug_redact` for sensitive fields.

### Recommendation
- In `JsonStreamToMessage` (`src/google/protobuf/json/internal/parser.cc:1389-1392`) and `JsonToBinaryStream` (`:1414-1453`), use a redaction-aware debug string (e.g., `DebugFormat::singleLine()`/`multiline()` equivalent in C++, or `TextFormat::Printer` with `SetRedactDebugString(true)` and `SetReportSensitiveFields`) instead of the raw `Message::DebugString()` when producing `ABSL_DLOG` output.
- Consider redacting or omitting the raw input payload log (`absl::CHexEscape(copy)`) entirely, or gate it separately from the decoded-message log so that raw bytes containing secrets aren't dumped even when message-level redaction is applied.
- Document prominently in `port_def.inc`/build docs that `PROTOBUF_ENABLE_DEBUG_LOGGING_MAY_LEAK_PII` bypasses `debug_redact` field protections, since that is not obvious from the flag's current usage.

### Proof of Concept
Conceptual reproduction (cannot be executed in this read-only environment):
1. Define a `.proto` schema with a message field, e.g. `string api_key = 1 [debug_redact = true];`.
2. Build Protobuf/the application with `-DPROTOBUF_ENABLE_DEBUG_LOGGING_MAY_LEAK_PII` and a non-`NDEBUG` build so `ABSL_DLOG` emits.
3. Send a bounded JSON payload `{"apiKey": "SECRET_VALUE_1234"}` through the public `JsonStringToMessage`/`JsonStreamToMessage` API.
4. Observe the `ABSL_DLOG(INFO) << "json2/output: " << message->DebugString();` line in `src/google/protobuf/json/internal/parser.cc:1391` printing `api_key: "SECRET_VALUE_1234"` unredacted, and the `ABSL_DLOG(INFO) << "json2/input: ..."` line printing the raw hex-escaped request bytes containing the same secret — despite the schema explicitly marking the field `debug_redact = true` to prevent exactly this exposure.
