### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers quadratic `O(t²)` Lagrange interpolation work, hanging the caller - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `n` (u16) from the input byte stream and then calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for each of participants `1..=t`. Under Lagrange interpolation each factor computation loops over all `t` included participants, making `ThresholdKeys::new` `O(t²)` in scalar multiplications/additions. A short serialized blob (under ~4 MiB) with `t = n = 65535` forces ~4.3×10⁹ field operations plus 65535 point operations, effectively hanging the thread that deserializes the keys — a complete DoS analogous to CVE-2018-3062's "crafted packet → hang/crash" class.

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), `t` and `n` are read directly from the untrusted reader (lines 591-602) with only `ThresholdParams::new`'s bounds (`t <= n`, `i <= n`, nonzero — `crypto/dkg/src/lib.rs:166-179`). Then `ThresholdKeys::new` is invoked (lines 625-631), which computes:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```
(`crypto/dkg/src/lib.rs:376-378`)

For `Interpolation::Lagrange`, `interpolation_factor` iterates over every member of `included`, performing a scalar multiply and subtraction per member (`crypto/dkg/src/lib.rs:229-247`). Since `included` here is `1..=t`, total work is `t` factor computations × `t` iterations each = `O(t²)`. With `t = n = 65535` (both are u16, so this is fully encodable), that is ~4.3 billion field multiplications — hours of single-threaded CPU time — plus 65535 `read_G` decodings.

The only input cost to the attacker is `n` scalar encodings for `Interpolation::Constant`'s coefficient vector is not even needed — choosing the `Lagrange` tag (byte `1`) requires just `n` verification-share points (~2 MiB for 32-byte encodings) plus one secret share. `read_F`/`read_G` perform canonicality checks but no work bounding.

### Impact Explanation
Any code path that calls `ThresholdKeys::read` on bytes influenced by an untrusted party (key-share recovery/backup blobs, resync messages, threshold-key payloads relayed through the network) can be made to spin for effectively unbounded time inside `ThresholdKeys::new`. Per the scan rules, `ThresholdKeys::read` is an explicitly listed untrusted-bytes sink. The result is a complete availability loss of the calling component — directly matching the CVE class (low-privileged remote input → hang or repeatable crash), with no cryptographic assumption or malicious-validator requirement: only the byte stream itself is attacker-controlled.

### Likelihood Explanation
`n` is a raw u16; a value of 65535 is trivially constructible. The required payload is roughly `4 + 6 + 1 + 32 + n·32` bytes ≈ 2.1 MiB — small. No malformed encodings are needed: every point can be the canonical generator encoding, so all `read_G` calls succeed and execution always reaches the quadratic loop. Triggering requires only that the attacker can cause the target to deserialize a `ThresholdKeys` blob they supply, which is the stated reachable-input model.

### Recommendation
Bound `t`/`n` before performing interpolation work:
- Enforce a protocol-level maximum (e.g., the existing `MAX_KEY_SHARES_PER_SET`-style bound used elsewhere) inside `ThresholdKeys::read` before calling `ThresholdKeys::new`, rejecting `n` above the real deployment maximum.
- Alternatively/al additionally, precompute Lagrange denominators in `O(t)` (product-tree / prefix-product approach) inside `interpolation_factor` callers rather than per-participant `O(t)` loops.

### Proof of Concept
```rust
use std::io;
use frost::{curve::Secp256k1, ThresholdKeys};
use ciphersuite::{group::GroupEncoding, Ciphersuite};

fn malicious_blob() -> Vec<u8> {
    let mut buf = vec![];
    // Curve ID
    buf.extend((Secp256k1::ID.len() as u32).to_le_bytes());
    buf.extend(Secp256k1::ID);
    // t = 65535, n = 65535, i = 1
    buf.extend(65535u16.to_le_bytes());
    buf.extend(65535u16.to_le_bytes());
    buf.extend(1u16.to_le_bytes());
    // Interpolation::Lagrange
    buf.push(1);
    // secret_share: any canonical scalar, e.g. 1
    buf.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr());
    // n verification shares: reuse the generator encoding
    let g = Secp256k1::generator().to_bytes();
    for _ in 0 .. 65535u16 {
        buf.extend(g.as_ref());
    }
    buf
}

#[test]
fn dos() {
    let blob = malicious_blob(); // ~2.1 MiB
    // Hangs: ThresholdKeys::new evaluates 65535 interpolation factors,
    // each scanning 65535 participants => ~4.3e9 field ops
    let _ = ThresholdKeys::<Secp256k1>::read(&mut blob.as_slice());
}
```

Root cause chain: `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) → unbounded `t`, `n` → `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:376-378`) → `Interpolation::Lagrange::interpolation_factor` (`crypto/dkg/src/lib.rs:229-247`) executed per participant → `O(t²)` hang reachable purely from untrusted serialized bytes.
