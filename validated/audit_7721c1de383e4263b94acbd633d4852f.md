Based on my investigation, I found a genuine analog to the http-signature header-forgery bug class in the Kaia auction (KIP-249) module's EIP-712 bid signing scheme.

### Title
Auction bid `MaxGasPrice` field excluded from EIP-712 struct hash under default/legacy version, allowing post-signature tampering without invalidating the searcher signature - (File: kaiax/auction/eip712.go)

### Summary
The `Bid.GetHashTypedData` function in `kaiax/auction/eip712.go` computes two different EIP-712 struct-hash encodings depending on the configured `auctionEntryPointVersion`. Similar to the `http-signature` bug where header *values* were signed but header *names* were not (allowing values to be relabeled without breaking the signature), the Kaia auction bid signs a subset of `BidData` fields whose composition changes silently based on version, so a field (`MaxGasPrice`) present in the signed `BidData` object can be entirely absent from the cryptographic commitment depending on which code path is taken.

### Finding Description
`Bid.EncodeData()` (the default/"v2.1" path) does not include `MaxGasPrice` in the encoded struct: [1](#0-0) 

Only the `bidV3` wrapper's `EncodeData()` includes `MaxGasPrice`: [2](#0-1) 

`GetHashTypedData` selects which struct hash to use based on a `version` string, and explicitly falls back to the v2 (no-`MaxGasPrice`) hash for anything that isn't the exact `AuctionVersionV3` string, including unrecognized values: [3](#0-2) 

The `BidPool.validateBidSigs` function verifies `SearcherSig` against this same version-dependent digest, using the node's currently configured `auctionEntryPointVersion` (read from on-chain `SystemRegistry`/`AuctionEntryPoint` state per the module's README), not a value chosen or committed to by the searcher within the signed payload itself: [4](#0-3) 

Because `BidData.MaxGasPrice` is a regular field of the struct (carried alongside the signature, with `omitempty` JSON tag) but is not cryptographically bound to `SearcherSig` whenever the entry point is on version 2 (or any non-"0.0.2" version string), any party that can modify the `Bid` before it reaches `validateBid`/`insertBid` — e.g., the `Auctioneer` relay that receives the searcher's signed bid, re-signs it, and forwards it to the CN — can change `MaxGasPrice` without invalidating `SearcherSig`. This is structurally identical to the `http-signature` flaw: content is signed, but the binding of which *fields* are covered by the signature is not guaranteed to match what the signer believed they signed, letting a data field be forged/altered post-signature. [5](#0-4) 

### Impact Explanation
If downstream bid/tx-building logic (`kaiax/auction/impl/execution.go`, `blockchain/system/auction.go`) uses `bid.MaxGasPrice` to cap or determine the gas price used when constructing/executing the winning bid's transaction, tampering with this field after the searcher's signature is produced changes the economic terms of the auction settlement without the searcher's authorization — i.e., "auction settlement theft" as explicitly listed in the accepted impact categories. I was unable to fully trace the exact consumption site of `MaxGasPrice` in `execution.go`/`auction.go` within the remaining investigation budget, so the precise financial blast radius (e.g., whether it directly changes the gas price charged to the searcher, or only a display/cap value) is not fully confirmed and should be verified.

### Likelihood Explanation
The `Auctioneer` is a required intermediary in the bid flow (it always re-signs `SearcherSig` to produce `AuctioneerSig`), giving it a natural position to modify the `BidData` object before submission, matching the "privileged network position" role in the original CVE. No cryptographic break is needed — only a version mismatch (any entry-point version other than exactly `"0.0.2"`) causes the field to fall outside signature coverage, which is the module's current default behavior.

### Recommendation
Include all economically significant `BidData` fields (in particular `MaxGasPrice`) in the EIP-712 struct hash unconditionally, regardless of `auctionEntryPointVersion`, or reject/ignore `MaxGasPrice` entirely when using the version whose struct hash does not cover it, so that no field can influence bid execution without being covered by `SearcherSig`.

### Proof of Concept
1. Node/contract is configured with `auctionEntryPointVersion` != `AuctionVersionV3` (i.e., default "v2.1" path, which is the fallback for any unrecognized version string per `kaiax/auction/eip712.go:144-147`).
2. Searcher signs a `Bid` with `MaxGasPrice = X` using `GetHashTypedData`, which invokes `EncodeEIP712(b)` (default `EncodeData`) that omits `MaxGasPrice` from the struct hash (`kaiax/auction/eip712.go:75-86`).
3. Auctioneer (or any party handling the bid before pool insertion) changes `bid.MaxGasPrice` to `Y` and forwards the bid.
4. `BidPool.validateBidSigs` recomputes the same version-2 digest (still excluding `MaxGasPrice`) and successfully validates `SearcherSig` against the unmodified fields (`kaiax/auction/impl/bid_pool.go:397-419`), accepting the tampered bid with `MaxGasPrice = Y` as validly signed by the searcher.

// GetHashTypedData returns the EIP-712 digest for the bid.
// version must match the on-chain AUCTION_VERSION of the entry-point contract
// the bid targets; "0.0.2" selects the v3.0 struct typehash (with maxGasPrice),
// any other value falls back to the v2.1 typehash.
func (b *Bid) GetHashTypedData(chainId *big.Int, verifyingContract common.Address, version string) []byte {
	if chainId == nil {
		return nil
	}

	domain := EIP712Domain{
		EIP712DomainTypeHash: eip712TypeHash,
		NameHash:             auctionNameHash,
		VersionHash:          crypto.Keccak256Hash([]byte(version)),
		ChainId:              chainId,
		VerifyingContract:    verifyingContract,
	}

	domainSeparator := EncodeEIP712(domain)

	var structHash []byte
	if version == AuctionVersionV3 {
		structHash = EncodeEIP712(bidV3{b})
	} else if version == AuctionVersionV2 {
		structHash = EncodeEIP712(b)
	} else {
		// Unknown version: default to v2.1 typehash.
		structHash = EncodeEIP712(b)
	}

	return crypto.Keccak256([]byte{0x19, 0x01}, domainSeparator, structHash)
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
