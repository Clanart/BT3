### Title
SignableTransaction::new calculates the required fee without the OP_RETURN output, underpaying the fee and overstating change - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` accepts an optional `data` payload and appends an `OP_RETURN` output to the transaction, but computes `needed_fee` (and the change amount) from a vbyte estimate that only covers the inputs and `payments` — the OP_RETURN output is excluded from `calculate_weight_vbytes`. The result mirrors the LiFi bug class: the value committed to cover the operation's cost (inputs − payments − fee) does not actually cover the true cost of the produced transaction, so the effective fee rate is lower than `fee_per_vbyte`, and any change output is credited with satoshis that should have gone to the fee.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is pushed to `tx_outs` before the weight calculation:

```rust
// lines 194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

// line 204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (lines 62-127) builds the estimation transaction from `inputs` and `payments` only; `tx_outs` — which already contains the OP_RETURN output — is never consulted. Both `needed_fee = fee_per_vbyte * vbytes` (line 206) and the `fee_with_change` path (lines 225-233) therefore omit the ~9-91 byte OP_RETURN output. When a change output is produced, `value = input_sat - (payment_sat + fee_with_change)` (line 228) inflates the change by the fee attributable to the data output.

A similar miscount applies to weight: `weight` used for the `MAX_STANDARD_TX_WEIGHT` check (line 241) excludes the data output when `change` is `None`.

### Impact Explanation
- The transaction pays a fee rate strictly below the caller-requested `fee_per_vbyte` whenever `data` is supplied (by up to ~91 vbytes worth of fee). At low fee rates this can drop the effective feerate below relay/policy thresholds, so the signed transaction is delayed or never propagates — funds are committed in a transaction that fails to confirm at the requested rate.
- When `change` is specified, the change output receives satoshis that were meant to cover the fee for the data output, silently skewing accounting for callers who reconcile `needed_fee()`/`fee()` against outputs.
- A data-carrying transaction that sits just under the weight limit can exceed `MAX_STANDARD_TX_WEIGHT` once the OP_RETURN output is accounted for, producing a non-standard (unrelayable) transaction the builder believed was valid.

### Likelihood Explanation
Any caller of `SignableTransaction::new` (e.g. `processor/src/networks/bitcoin.rs::make_signable_transaction` passes `None` today, but the wallet API is public and intended for integrators) that supplies `data` deterministically triggers the undercount. The miscount is proportional to the data length, and the 80-byte cap maximally bounds it — it is always wrong when used, not an edge case.

### Recommendation
Include the OP_RETURN output in the fee estimation: pass the data output (or its serialized length) into `calculate_weight_vbytes`, or compute `vbytes`/`weight` after building the full `tx_outs` vector, for both the no-change and with-change estimates. Additionally, perform the `MAX_STANDARD_TX_WEIGHT` check against a weight that includes the data output.
