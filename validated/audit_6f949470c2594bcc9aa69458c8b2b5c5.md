## Title
Webhook HMAC verification does not bind the `shop_domain` header, enabling cross-shop webhook forgery replay - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

## Summary
The Astaria bug is a signature-verification flaw where a cryptographic proof binds only *some* of the data relevant to its use (leaving out `strategy.vault`), so the exact same signed payload can be replayed in a different context that the signer never intended. The `shopify_app` analog is structurally identical: `ShopifyApp::WebhookVerification` validates a webhook's authenticity by HMAC-signing only the raw request body, while the shop identity (`X-Shopify-Shop-Domain` header) used by application code to attribute the webhook to a specific merchant is never part of the signed material.

## Finding Description
`WebhookVerification#verify_request` computes validity purely from `request.raw_post`: [1](#0-0) 

and `shopify_hmac`/`hmac_valid?` in `PayloadVerification` HMAC-sign only that same `data` (the raw body) against the app's shared secret: [2](#0-1) 

Crucially, `shop_domain` is read directly from an HTTP header with **no cryptographic binding** to the HMAC that was just verified: [3](#0-2) 

The gem's own documented, recommended pattern for custom webhook controllers explicitly forwards this unauthenticated `shop_domain` value into background jobs that key data by shop: [4](#0-3) 

This is exactly analogous to the Astaria root cause: the "signature" (HMAC) is valid over a subset of the semantically relevant data (body only), while a security-relevant field used downstream (`shop`/vault-equivalent) is excluded from what's signed, letting one legitimately-signed payload be reused/relabeled in a different context (a different shop) that the original issuer (Shopify, on behalf of the merchant whose store generated the event) never authorized for that context.

## Impact Explanation
Any merchant can install the app on their own store (unprivileged action) and thereby legitimately receive Shopify webhooks—complete with a valid `X-Shopify-Hmac-Sha256` signature computed by Shopify using the app's shared secret—for events on their own shop (e.g., `orders/create`, `customers/redact`). Because the HMAC covers only the body and not the shop identity header, the attacker can replay that captured body+signature to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `hmac_valid?` still succeeds since it only checks the body against the secret, and the controller/job layer will process the forged event as if it originated from the victim shop, since `shop_domain` is trusted for attributing the webhook. Depending on the job wired to the topic, this enables cross-shop data injection (fake order/customer records attributed to a shop the attacker doesn't own) or triggering of shop-scoped side effects (e.g., mandatory privacy webhooks like `shop/redact`, `customers/redact`) against an arbitrary victim shop.

## Likelihood Explanation
Exploitation requires only an attacker-controlled shop installation (which any user of the app can obtain) plus the ability to send an ordinary POST request with a spoofed header to the app's public webhook endpoint—no privileged access, no secret leakage, and no dependency-only code path. This is directly reachable from an anonymous/merchant-controlled HTTP client.

## Recommendation
Bind the shop identity into the HMAC verification (e.g., re-derive/validate shop from the payload itself where Shopify includes it, or require the HMAC to also cover the `X-Shopify-Shop-Domain` header/topic), and/or cross-check the `shop_domain` header against a shop the caller is actually associated with (e.g., verify the shop has an active session/webhook subscription for that topic) before trusting it in downstream job dispatch. Following Shopify's own webhook verification model where the signed digest is tied to the specific delivery (body) and the shop is only trusted after HMAC success against that shop's/app's known configuration, apps should not treat the shop header as authoritative without further correlation.

## Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (normal merchant flow).
2. Attacker triggers a webhook event on their own shop (e.g., updates a customer to fire `customers/update`), and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends to the app's webhook endpoint — this HMAC is valid because it's computed by Shopify using the app's real secret over that body.
3. Attacker replays the identical body and HMAC header to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)` [5](#0-4)  which succeeds because the body is unchanged and matches the previously-issued HMAC.
5. The controller (per the documented pattern) reads `shop_domain` from the (attacker-controlled) header [3](#0-2)  and enqueues the job scoped to `victim-shop.myshopify.com` with attacker-chosen webhook body content, achieving cross-shop webhook forgery.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
