Based on my investigation, the strongest verifiable local analog to the Stargate "hardcoded-router-check-could-revert-and-strand-funds" pattern is the **one-time, unrecoverable `host` address binding** used by Hyperbridge's app modules (`BandwidthManager`, `HostManager`, `SimplexPaymaster`), combined with the confirmed EVM host delivery semantics that silently and permanently drop a callback whenever it reverts.

### Title
Immutable one-shot `host` binding in governance-gated apps permanently strands escrowed and treasury funds if `EvmHost` is ever redeployed - (File: `evm/src/apps/BandwidthManager.sol`, `evm/src/core/HostManager.sol`, `evm/src/utils/SimplexPaymaster.sol`)

### Summary
Several core Hyperbridge apps (`BandwidthManager`, `HostManager`, `SimplexPaymaster`) hardcode the local `EvmHost` address into a single storage slot that can only ever be set once, and gate their entire recovery/withdrawal logic behind `onlyHost`/`restrict(host)`. If the configured host is ever redeployed for any reason (upgrade, migration, incident response), every legitimate `onAccept` governance message — including `Withdraw`/`WithdrawAssets` and `UpgradeContract` — will permanently fail the address check and be silently and irreversibly dropped by `EvmHost.dispatchIncoming`, exactly mirroring the Stargate `sgReceive` router-address `require` that could strand funds on redeployment.

### Finding Description
`BandwidthManager.setHost` can be called exactly once: [1](#0-0) 
and every subsequent inbound message is gated by `onlyHost`, which compares `msg.sender` to this immutable `_host`: [2](#0-1) 

`HostManager` has the identical pattern — `setIsmpHost` is a one-shot setter that zeroes the admin afterward, and `onAccept` (the only path through which `Withdraw`/`SetHostParam` governance actions reach the chain) is restricted to `_params.host`: [3](#0-2) 

`SimplexPaymaster` follows the same design: `_hostAddr` is set once in `initialize()` and `onAccept` — the only path for `WithdrawAssets`, `UpgradeContract`, `RegisterToken`, etc. — is gated by `onlyHost`: [4](#0-3) 
Notably, `SimplexPaymaster._authorizeWithdraw` unconditionally reverts, meaning `_withdrawAssets` is reachable *only* through this single `onAccept` gate: [5](#0-4) 

Critically, I confirmed that `EvmHost.dispatchIncoming(PostRequest)` treats a reverting `onAccept` call as a routine, silent failure — it deletes the request receipt "so it can be retried" and returns without reverting the batch: [6](#0-5) 
If the underlying cause of the revert (a stale `host`/`_hostAddr` value) never changes, this "retry" path never succeeds — the message is retried indefinitely and fails indefinitely, precisely the Stargate failure mode where a `require` against a stale trusted address perpetually reverts the receiving callback.

### Impact Explanation
Once the bound host address goes stale, these contracts lose their *only* administrative recovery mechanism:
- `BandwidthManager`'s fee-token proceeds pulled into the contract via `purchase()` (`IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount)`) become permanently unwithdrawable, since `Withdraw` can only arrive via the broken `onAccept`. [7](#0-6) 
- `HostManager`'s revenue-withdrawal and `SetHostParam` paths (the only way to migrate `EvmHost` parameters, including `hostManager` itself) become permanently unreachable, since they too depend on `onAccept` from the same stale host.
- `SimplexPaymaster`'s accrued markup surplus and EntryPoint deposit become permanently stuck, and the contract can never be upgraded to fix the problem, because `UpgradeContract` is also gated by the same broken `onlyHost` check.

This matches the bounty's "loss of funds" and "unauthorized/blocked execution" categories: value legitimately owned by the protocol/treasury becomes permanently inaccessible with no fallback path, not because of a malicious actor, but because of a structural single point of failure identical in shape to the Stargate report.

### Likelihood Explanation
As with the original Stargate report, it is difficult to estimate how likely an `EvmHost` redeployment is; Hyperbridge's own `HostManager.updateHostParams` shows that host-side parameters (consensus client, handler, fee token, etc.) are explicitly designed to be migrated over time via governance, and the `EvmHost` implementation itself sits behind proxies in some deployments. Any operational reason to redeploy or migrate the host contract (rather than merely updating its params) would trigger this failure mode across every app module that hardcodes it. The likelihood is therefore comparable to the original finding: non-trivial but not attacker-controlled.

### Recommendation
- Add a governance-only "re-point host" escape hatch to `BandwidthManager`, `HostManager`, and `SimplexPaymaster` that does not depend on the same `onAccept`/`onlyHost` gate being functional (e.g., a timelocked admin function, or a fallback owner-controlled path once a grace period elapses without successful host confirmation).
- Alternatively, avoid the "settable exactly once" pattern and instead allow the current host to authorize its own succession (an EvmHost-initiated address migration message) so the app never needs an independent, unrecoverable trust anchor.
- At minimum, add monitoring/alerting for `EvmHost` redeployment intentions before they occur, matching the "monitor and redeploy if necessary" mitigation suggested in the original Stargate report.

### Proof of Concept
1. Deploy `BandwidthManager`, call `setHost(hostA)`.
2. Users call `purchase()` repeatedly, accumulating fee-token balance inside `BandwidthManager`.
3. `EvmHost` is redeployed to `hostB` for any operational reason (upgrade, consensus-client migration requiring a new host, etc.).
4. Hyperbridge governance dispatches a `Withdraw` message targeting `BandwidthManager`; it is delivered by `hostB`.
5. `onAccept`'s `onlyHost` check compares `msg.sender` (`hostB`) against `_host` (`hostA`) and reverts.
6. `EvmHost.dispatchIncoming` (on `hostB`) catches the failure, deletes the receipt "so it can be retried," and returns — the message is retried on every future delivery attempt but always fails identically, since `_host` can never be changed (`setHost` reverts once already set).
7. All fee-token proceeds held in `BandwidthManager` are now permanently unrecoverable.

Note: this analysis is based on statically reading the cited contracts; I was not able to execute the Foundry test suite to dynamically confirm the exact revert/retry behavior end-to-end, so I recommend a background Devin session verify this with `evm/tests/foundry/HostManagerTest.sol` / `BandwidthManagerTest.t.sol` before treating it as fully confirmed.

    /// @dev Handles governance requests delivered by the local host. The first
    ///      byte of the request body encodes the `RequestKind`; only requests
    ///      originating from Hyperbridge itself are accepted.
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) {
            revert UnauthorizedCall();
        }

        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        bytes calldata payload = incoming.request.body[1:];

        if (kind == RequestKind.UpgradeContract) {
            (address newImpl, bytes memory initData) = abi.decode(payload, (address, bytes));
            ERC1967Utils.upgradeToAndCall(newImpl, initData);
        } else if (kind == RequestKind.UpdateParams) {
            _setParams(abi.decode(payload, (Params)));
        } else if (kind == RequestKind.RegisterToken) {
            (address token, address oracle) = abi.decode(payload, (address, address));
            _registerToken(token, AggregatorV3Interface(oracle));
        } else if (kind == RequestKind.DeactivateToken) {
            _deactivateToken(abi.decode(payload, (address)));
        } else if (kind == RequestKind.WithdrawAssets) {
            (address token, uint256 amount) = abi.decode(payload, (address, uint256));
            _withdrawAssets(token, amount);

    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
