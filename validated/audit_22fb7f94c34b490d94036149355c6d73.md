Audit Report

## Title
Unauthenticated, unbounded `getProgramAccounts` full-account-table scan lacks a byte-size guard when secondary indexes are disabled - ([File: rpc/src/rpc.rs])

## Summary
`getProgramAccounts` is a public, unauthenticated JSON-RPC method that, when the `AccountIndex::ProgramId` secondary index is not configured (the default), scans and collects the entirety of a program's owned accounts into an unbounded in-memory `Vec` with no byte-size ceiling, pagination, or rate limiting, unlike the indexed path which enforces `scan_results_limit_bytes`.

## Finding Description
`AccountsScanImpl::get_program_accounts` in `rpc/src/rpc.rs` accepts an arbitrary `program_id_str` from any unauthenticated network client via the `get_program_accounts` handler at [1](#0-0) . This flows into `JsonRpcRequestProcessor::get_filtered_program_accounts`, which branches on whether `AccountIndex::ProgramId` is configured for the queried key: the indexed branch calls `get_filtered_indexed_accounts`, which enforces `self.config.scan_results_limit_bytes`, while the non-indexed branch explicitly comments "this path does not need to provide a mb limit because we only want to support secondary indexes" and calls `bank.get_filtered_program_accounts` with no byte limit [2](#0-1) .

`Bank::get_filtered_program_accounts` forwards directly to `Accounts::load_by_program_with_filter`, which uses `ScanConfig::default()` and pushes every matching account into an unbounded `collector: Vec<KeyedAccountSharedData>` with no abort mechanism [3](#0-2) . In contrast, the indexed path `load_by_index_key_with_filter` wires in `accumulate_and_check_scan_result_size` and `maybe_abort_scan`, which aborts the scan once `byte_limit_for_scan` is exceeded [4](#0-3) . This size-check machinery is never invoked from `load_by_program`/`load_by_program_with_filter`.

Additionally, the `scan_results_limit_bytes` config value is derived from the `accounts_index_scan_results_limit_mb` CLI flag, which has no `default_value` set, so it defaults to `None`, meaning this guard is entirely optional even on the indexed path unless explicitly configured by the operator [5](#0-4) .

Because most validators query programs like the SPL Token program, System program, or other widely-used programs owning many accounts, an unauthenticated client can send a single `getProgramAccounts` request against such a program, forcing the node to load and clone every owned account's full data into heap memory with no rate limit, byte cap, or authentication gate on this path.

## Impact Explanation
A single unauthenticated RPC client issuing `getProgramAccounts` against a large program with no `AccountIndex::ProgramId` configured (the common default) can force unbounded heap allocation and CPU-bound account cloning/serialization on the JSON-RPC node's `Vec<KeyedAccountSharedData>` collector. Repeated or concurrent requests of this kind can degrade or crash a single RPC-serving node, matching the "single-client low-rate RPC crash/degradation" impact class.

## Likelihood Explanation
High. No privileged credentials, stake, or special network position are required; any JSON-RPC client can invoke `getProgramAccounts` with a popular `program_id` string as the sole parameter. Disabling the secondary index is the default validator configuration, and even when enabled, the byte-limit guard defaults to unset (`None`) unless the operator explicitly passes `--accounts-index-scan-results-limit-mb`, making the unguarded path commonly reachable in practice.

## Recommendation
Wire the existing byte-limit/abort machinery (`ScanConfig::recreate_with_abort`, `accumulate_and_check_scan_result_size`, `maybe_abort_scan`) into `load_by_program`/`load_by_program_with_filter` and the `Bank::get_filtered_program_accounts` non-indexed call path, applying `self.config.scan_results_limit_bytes` regardless of whether a secondary index is configured. Consider giving `accounts_index_scan_results_limit_mb`/`scan_results_limit_bytes` a sane non-`None` default, and/or imposing a hard server-side account-count/byte cap plus per-IP request-rate limiting for `getProgramAccounts`.

## Proof of Concept
1. Run a validator with `--full-rpc-api` and without `--account-index program-id` (default) and without `--accounts-index-scan-results-limit-mb`.
2. Send `{"jsonrpc":"2.0","id":1,"method":"getProgramAccounts","params":["TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA"]}` from any unauthenticated client.
3. The request enters the non-indexed branch of `get_filtered_program_accounts` at [6](#0-5) , which calls `bank.get_filtered_program_accounts` → `Accounts::load_by_program_with_filter` → unbounded `collector` growth, with no `maybe_abort_scan` check as exists in the indexed path [7](#0-6) .
4. A unit test analogous to `test_get_filtered_indexed_accounts_limit_exceeded` (which demonstrates the indexed path aborts on limit) can be added for the non-indexed `load_by_program_with_filter`/`get_filtered_program_accounts` path to show no equivalent abort occurs regardless of `byte_limit_for_scan`.

    fn calc_scan_result_size(account: &AccountSharedData) -> usize {
        account.data().len()
            + std::mem::size_of::<AccountSharedData>()
            + std::mem::size_of::<Pubkey>()
    }

    /// Accumulate size of (pubkey + account) into sum.
    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }
