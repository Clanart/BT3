### Title
Duplicate inputs are double-counted yet produce a consensus-invalid transaction, permanently locking the consumed UTXOs - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` accepts an arbitrary `Vec<ReceivedOutput>` and never validates that no two entries share the same `OutPoint`. Analogous to the Tally bug where the same value could be supplied through two channels (`msg.value` and a WETH pull) because the `require` failed to enforce mutual exclusivity, here the same coin can be supplied twice through the `inputs` channel. The builder counts its value twice toward `input_sat` while emitting the duplicated `TxIn` into the signed transaction, which Bitcoin consensus rejects (duplicate inputs are invalid). The FROST signature shares are still generated and the protocol treats the inputs as consumed, but the resulting transaction can never confirm, so those UTXOs become unspendable within the protocol's bookkeeping.

### Finding Description
In `SignableTransaction::new`, the spendable balance is computed by summing every provided input:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
``` [1](#0-0) 

Each input is then mapped to a `TxIn` with no uniqueness check on `previous_output`:

```rust
.map(|input| TxIn {
  previous_output: input.outpoint,
  ...
})
``` [2](#0-1) 

Because `input_sat` counts a duplicated `ReceivedOutput` twice, the `NotEnoughFunds` check, the change calculation (`input_sat.checked_sub(payment_sat + fee_with_change)`), and the change output value are all computed against funds that do not exist. The resulting `Transaction` contains the same input twice, which Bitcoin consensus rules (and `bitcoin::consensus` validation) reject. Downstream, `multisig()` creates one FROST `AlgorithmMachine` per tx input and `TransactionSignMachine::sign` commits `Prevouts::All(&self.tx.prevouts)` — the duplicated prevout included — so signers produce valid shares for an unbroadcastable transaction. [3](#0-2) [4](#0-3) [5](#0-4) 

### Impact Explanation
Like the Tally finding (caller mistakenly pays through two channels and loses funds), a caller/aggregator passing the same `ReceivedOutput` twice gets a signed transaction that can never be mined. In the processor flow (`make_signable_transaction` → `signable_transaction` → `Eventuality`), the plan's inputs are consumed and an `Eventuality` bound to `signable.txid()` is registered, yet `confirm_completion` can never observe the txid on-chain. The affected UTXOs are therefore reported as spent/in-flight while remaining unspendable — a permanent fund-lock for those coins, matching the "funds reported received/spent that are not spendable" impact class. Severity: Medium.

### Likelihood Explanation
Reachable by any caller supplying transaction data to the `SignableTransaction`/`sign` API — no special privileges needed. It requires mistakenly (or maliciously, via untrusted input lists assembled from scan results) passing the same outpoint twice, a plausible data-format mistake when merging `ReceivedOutput`s from multiple scans or blocks, exactly the class of mistaken-input bug in the reference report. The bitcoin crate does not prevent construction of transactions with duplicate inputs, and no upstream code deduplicates.

### Recommendation
Add an explicit uniqueness check in `SignableTransaction::new`, analogous to enforcing mutual exclusivity in the Tally fix:

```rust
// in SignableTransaction::new, after the NoInputs check
{
  let mut seen = std::collections::HashSet::with_capacity(inputs.len());
  for input in &inputs {
    if !seen.insert(input.outpoint) {
      Err(TransactionError::DuplicateInput)?;
    }
  }
}
```

This rejects the mistaken input at construction time, before any FROST shares or protocol bookkeeping are produced.

### Proof of Concept
```rust
// networks/bitcoin/tests/ analog — concept
let output = send_and_get_output(&rpc, &scanner, key).await; // one real UTXO, value V

// Mistakenly pass the same ReceivedOutput twice
let inputs = vec![output.clone(), output.clone()];

// input_sat = 2*V, so a payment of 1.5*V passes the NotEnoughFunds check
// even though only V real funds exist, and change is computed against 2*V.
let tx = SignableTransaction::new(
  inputs, &[(addr(), (3 * output.value()) / 2)], Some(change_addr), None, FEE,
).unwrap(); // succeeds — should have been rejected

// The produced transaction lists the same OutPoint in tx.input[0] and tx.input[1].
let signed = sign(&keys, &tx);
// rpc.send_raw_transaction(&signed) -> rejected by Bitcoin consensus:
// duplicate inputs ("bad-txns-inputs-duplicate") → can never confirm.
// The plan's eventuality (txid) is unfulfillable; the input is locked in
// protocol bookkeeping despite never being spent on-chain.
```

Notes/uncertainty: this rests on Bitcoin's duplicate-input consensus rule (not re-verifiable in-repo) and on the processor treating inputs as consumed once a `SignableTransaction` is produced; the strongest reachable, in-scope expression of the bug class is this input-deduplication gap in `networks/bitcoin/src/wallet/send.rs`.
