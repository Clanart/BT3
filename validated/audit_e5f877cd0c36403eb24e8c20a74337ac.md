## Analog Identified

### Title
Silent deletion of conflict content when Copilot's hunk count diverges from the file's actual conflict-marker count during merge/rebase reassembly - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
The Sherlock finding is about two different code paths computing the "value" of the same conceptual object (a pending withdrawal) using inconsistent methods, with no cross-check between them, so the number ultimately used to decide liquidation can silently diverge from reality. GitHub Desktop's Copilot-assisted merge-conflict resolution feature has a structurally identical flaw: conflict "hunks" are counted and extracted by one function when building the AI prompt, and independently re-counted by a *different* function when splicing the AI's answer back into the file. Nothing validates that these two counts agree, and when they don't, extra conflict blocks are silently deleted rather than erroring out — corrupting the file that ultimately gets `git add`-ed and committed.

### Finding Description
`extractConflictHunks` (app/src/lib/copilot-conflict-context.ts:179-279) parses the on-disk conflicted file once to build the list of hunks sent to the Copilot model, using its own marker regexes (`oursMarker`, `baseMarker`, `separatorMarker`, `theirsMarker`) and its own malformed-hunk handling (a trailing `<<<<<<<` with no closing marker is dropped entirely via `continue`, not surfaced as a marker). [1](#0-0) 

Later, after the model responds, `reassembleResolvedFile` (app/src/lib/copilot-conflict-resolution.ts:549-599) re-parses the *same* raw file content from scratch, but with an entirely separate, independently maintained set of marker regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`) and its own definition of what counts as a "well-formed" conflict block. [2](#0-1) 

Critically, the splice step matches the model's per-hunk resolutions to detected marker blocks purely **by order**, with no validation that the count of blocks found here equals the count of hunks the model was told about (or that they correspond to the same physical block): [3](#0-2) 

If `reassembleResolvedFile` detects more conflict blocks than the model returned resolutions for (`hunkIndex >= hunkResolutions.length`), the bounds check silently skips inserting *any* replacement content for that block — the conflict markers and both sides' content are simply dropped from the reassembled file, with no error, no warning, and no fallback to the original content: [4](#0-3) 

This directly mirrors the Sherlock bug class: two independent implementations computing "the same thing" (which regions of the file are conflicts) can diverge, and the code that acts on the result (here, writing the final committed content) trusts one of them without reconciling against the other — exactly like the vaults valuing the same withdrawal request differently depending on which code path computed it.

The reassembled content is then written straight to disk and staged without further validation: [5](#0-4) 

and committed via the normal merge/rebase/cherry-pick continuation flow (`createMergeCommit` / `continueRebase`), which assumes conflicts are already resolved and does not re-check content correctness. [6](#0-5) 

### Impact Explanation
A crafted repository/branch (the "theirs" side an attacker controls, e.g. a malicious PR the victim merges locally) can include conflicting file content engineered so that `extractConflictHunks`'s marker parsing and `reassembleResolvedFile`'s independent marker parsing disagree on hunk boundaries or count (e.g. via malformed/nested marker-like sequences that one parser treats as a valid hunk and drops via `continue` while the other still counts a block, or vice versa). The result is silent deletion of arbitrary code sections from the merged file, which then gets staged and included in the merge commit the user pushes — this is "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories. No local/physical access, admin rights, or prior malware is required; the attacker only needs their content to end up on one side of a merge/rebase the victim performs.

### Likelihood Explanation
This requires the user to have opted into "Resolve with Copilot" for the conflict and to not scrutinize every file's diff in the result dialog before clicking "Continue Merge" — a plausible workflow for larger merges where users trust the AI summary. The comment in the code itself acknowledges the fragility ("matched by order, not by line number"), and the two marker-parsing implementations are maintained in different files with no shared logic or cross-check, making silent divergence a genuine (not merely theoretical) risk as the parsers evolve independently. I was not able to fully diff the exact regex definitions of `oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker` against `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` beyond what's cited above (their full pattern source wasn't retrieved), so I cannot certify a specific concrete input that triggers divergence — but the absence of any hunk-count reconciliation, combined with confirmed silent-deletion behavior on overflow, is a directly verified structural bug regardless of the exact trigger input.

### Recommendation
Have `reassembleResolvedFile` consume the same `IConflictHunk[]` structure that `extractConflictHunks` already produced (rather than re-parsing raw text with a second, independent parser), or at minimum assert `hunkResolutions.length === detectedBlockCount` and throw/skip-with-warning (falling back to leaving the original conflicted content untouched, requiring manual resolution) instead of silently deleting content when the counts diverge.

### Proof of Concept
Not independently executable from static review alone — reproducing it requires constructing a merge conflict whose raw text causes `extractConflictHunks` and `reassembleResolvedFile`'s independent marker scans to disagree on hunk boundaries/count, then walking through `_startCopilotConflictResolution` → `_applyCopilotConflictResolutions` → `createMergeCommit` to confirm the resulting commit is missing content. The silent-deletion code path itself is directly demonstrated by the cited `reassembleResolvedFile` bounds check, which unconditionally omits replacement content for any block index at or beyond `hunkResolutions.length`. /**
```typescript
 * Creates a commit to finish an in-progress merge
 * assumes that all conflicts have already been resolved
 * *Warning:* Does _not_ clear staged files before it commits!
 *
 * @param repository repository to execute merge in
 * @param files files to commit
 */
export async function createMergeCommit(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  manualResolutions: ReadonlyMap<string, ManualConflictResolution> = new Map()
): Promise<string> {
  // apply manual conflict resolutions
  for (const [path, resolution] of manualResolutions) {
    const file = files.find(f => f.path === path)
    if (file !== undefined) {
      await stageManualConflictResolution(repository, file, resolution)
    } else {
      log.error(
        `couldn't find file ${path} even though there's a manual resolution for it`
      )
    }
  }
```
