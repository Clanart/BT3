### Title
Rewardable-percent calculation incorrectly forfeits rewards on already-matured/unlocked capital in `getRewardablePercentWAD` - ([File: wombat/mWomSV.sol])

### Summary
`mWomSV.getRewardablePercentWAD()` (and the structurally identical `VLMGP.getRewardablePercentWAD()`) computes the fraction of a user's locked position that is "rewardable" for the purpose of forfeiting bonus rewards in `vlMGPBaseRewarder._calExpireForfeit`. For unlock slots whose cool-down period has already fully elapsed, the function keeps decaying the contribution of that already-matured amount as more time passes, instead of treating it as either fully rewardable or a fixed known value. This mirrors the Sherlock M-4 pattern of a ratio calculation that keeps penalizing capital that should no longer be counted as a liability/negative factor once it has effectively "settled." [1](#0-0) 

### Finding Description
`getRewardablePercentWAD` builds `percent` as follows:
- Base contribution from actively-locked (non-cooldown) tokens: `fullyInLock * 1e18 / userTotalmWomSV`. [2](#0-1) 
- For each unlock slot still in cool down (`block.timestamp <= endTime`), it adds the slot's full pro-rata share: `amountInCoolDown * 1e18 / userTotalmWomSV`. [3](#0-2) 
- For each unlock slot that has **already matured** (`block.timestamp > endTime`, i.e. the tokens are fully unlocked and withdrawable), it adds a decaying term:
```
percent += amountInCoolDown * 1e18 * (endTime - startTime) / userTotalmWomSV / (timeNow - startTime);
``` [4](#0-3) 

As `timeNow` grows past `endTime`, the denominator `(timeNow - startTime)` keeps increasing while the numerator stays fixed, so this term monotonically shrinks toward zero the longer the user waits (for any reason) before calling `unlock()`. This means capital that is fully matured and effectively free (analogous to the "unlocked" capital in the Sherlock report) is treated progressively worse over time rather than being excluded from the penalty entirely or valued at its full, static, already-earned share.

This computed `percent` (`rewardablePercentWAD`) is consumed directly by `vlMGPBaseRewarder._calExpireForfeit`, which computes `forfeitAmount = _amount - (_amount * rewardablePercentWAD / 1e18)`, and that forfeited amount is not returned to the user — it is diverted back into the reward pool for other stakers via `_queueNewRewardsWithoutTransfer`. [5](#0-4) [6](#0-5) 

This is directly analogous to the referenced bug class: a ratio (leverage ratio / rewardable percent) fails to stop counting an amount once it has moved from an "encumbered" state into a "free/settled" state, and instead keeps penalizing the user unboundedly based on that stale accounting, causing an economically nonsensical and increasingly severe outcome the longer the position sits in its matured state — exactly as the original report showed the leverage ratio getting worse the longer capital stayed locked, when it should have improved once the position was effectively resolved.

### Impact Explanation
Any ordinary user who locks mWOM/MGP, starts an unlock (`startUnlock`), and does not immediately call `unlock()` after the cool-down period ends (a completely normal and expected user behavior — there is no obligation or incentive documented to claim instantly) will see the `rewardablePercentWAD` for that matured portion decay toward zero over time. The next time they claim rewards via `MasterMagpie`/`vlMGPBaseRewarder.getReward`/`getRewards`, an increasing (approaching 100%) fraction of the reward tied to that already-vested balance is force-forfeited and permanently redirected to other users, with no way for the affected user to recover it. This is a permanent loss of unclaimed yield for the user, driven purely by an accounting flaw, not by any wrongdoing or a deliberate exit decision.

### Likelihood Explanation
This requires no privileged role and no adversarial action — it is triggered by completely standard user behavior (lock → start unlock → wait past cool-down → later claim rewards, which is common since users are not required to call `unlock()` the instant the cool-down ends). The longer the delay, the larger the unintended forfeiture, so likelihood of at least some users being affected, and the severity growing over time, is high.

### Recommendation
Once an unlock slot's cool-down period has elapsed (`block.timestamp > endTime`), the corresponding `amountInCoolDown` should either be treated as fully rewardable (percent contribution = `amountInCoolDown * 1e18 / userTotalmWomSV`, same as the still-in-cool-down case) or excluded from the penalty calculation entirely, rather than being scaled by a shrinking `(endTime - startTime) / (timeNow - startTime)` factor that causes indefinite decay. The forfeiture logic should not continue to punish a user for capital that has already fully matured.

### Proof of Concept
1. User calls `mWomSV.lock(amount)` to lock mWOM.
2. User calls `startUnlock(amount)`, creating an unlock slot with `startTime = t0`, `endTime = t0 + coolDownInSecs`. [7](#0-6) 
3. Time passes well beyond `endTime` (e.g. user is simply not actively monitoring the position; there is no requirement to call `unlock()` immediately).
4. User calls a reward claim path through `MasterMagpie` → `vlMGPBaseRewarder.getReward`/`getRewards`, which calls `_calExpireForfeit` → `vlMGP.getRewardablePercentWAD(_account)`. [8](#0-7) 
5. Because `timeNow - startTime` has grown large, the slot's contribution to `percent` is now near zero, so `_calExpireForfeit` returns a `forfeitAmount` close to the full pending reward tied to that balance, which is transferred away from the user via `_queueNewRewardsWithoutTransfer` instead of being paid out. [9](#0-8) 
6. The user permanently loses reward tokens they had already earned, purely as a function of how long they waited to call `unlock()` after their tokens had already matured — with no adversarial actor involved.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
