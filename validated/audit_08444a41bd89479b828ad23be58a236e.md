### Title
OP_RETURN `data` output excluded from weight/fee calculation, producing transactions with a lower feerate than requested that can fail relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the referenced bug (a value that must be accounted for is treated as zero, causing downstream failure), `SignableTransaction::new` pushes an OP_RETURN output into `tx_outs` when `data` is specified, but computes the transaction weight, vbytes, `needed_fee`, the minimum-relay-fee check, and the max-standard-weight check using only `payments` and the optional `change` output. The `data` output's ~13–93 bytes are silently omitted from every size/fee calculation.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before any size calculation:

```rust
// networks/bitcoin/src/wallet/send.rs:194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
```

However, both calls to `calculate_weight_vbytes` pass `payments` — not `tx_outs`:

```rust
// networks/bitcoin/src/wallet/send.rs:204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
// :226
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
```

Inside `calculate_weight_vbytes`, the dummy transaction's `output` vec is built exclusively from `payments` plus the optional change output; the OP_RETURN output never contributes to `weight` or `vbytes`. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` is computed on a vsize up to ~93 bytes smaller than the real transaction (8-byte amount + compact-size length + `OP_RETURN <push>` of up to 80 bytes of data).
2. The `TooLowFee` check (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) uses the underestimated `vbytes`.
3. The `MAX_STANDARD_TX_WEIGHT` check uses the underestimated `weight`.

The actual fee paid is `input_sat - sum(tx_outs)` (see `fee()`), which still equals roughly `needed_fee`, but it is spread over a transaction ~93 vbytes larger than assumed. The *effective* feerate is therefore `needed_fee / (vbytes + ~93)` — strictly below the caller-specified `fee_per_vbyte`, and when `fee_per_vbyte` is at or near the minimum relay rate, below `DEFAULT_MIN_RELAY_TX_FEE` entirely.

### Impact Explanation
The bug is reachable via `data`, a caller-controlled input to the public constructor `SignableTransaction::new`, which flows through `multisig` → `TransactionMachine::sign` where the threshold group signs the BIP-341 sighash of the real (larger) transaction. The resulting signed transaction can be rejected by Bitcoin Core relay policy for paying less than the minimum feerate, or silently confirm far slower than the requested rate. Unlike the change-output case (where `fee_with_change` is recomputed with the change output included), the data path never re-accounts for the added output. In the worst case, a threshold wallet funds and signs a transaction that cannot be broadcast — an "attempts to spend will fail" outcome matching the report's class: a component that should contribute to a required value is treated as zero.

### Likelihood Explanation
Any transaction constructed with non-empty `data` (up to 80 bytes is permitted by the `TooMuchData` check) and a `fee_per_vbyte` within ~`fee_per_vbyte * 93 / vbytes` of the minimum relay fee produces an under-minimum-feerate transaction. For typical single-input P2TR spends (~150–250 vbytes), even moderate `fee_per_vbyte` values yield an effective rate several percent below requested, and near-minimum rates fall below relay policy outright. The bug triggers deterministically whenever `data` is used — no adversarial timing or collusion required — but impact is limited to the transaction builder's own funds being temporarily unspendable rather than theft or forgery.

### Recommendation
Include the OP_RETURN output in the size accounting by constructing the candidate output list (payments + OP_RETURN + optional change) before calling `calculate_weight_vbytes`, or add an explicit `extra_output_bytes` parameter. Concretely, in `SignableTransaction::new`, build a `Vec<(ScriptBuf, u64)>` (or pass `&tx_outs` directly) containing payments plus the `Amount::ZERO` OP_RETURN output, and use it in both `calculate_weight_vbytes` calls so `needed_fee`, `TooLowFee`, and `TooLargeTransaction` reflect the real transaction.

### Proof of Concept
```rust
// Conceptual: one P2TR input of 10_000 sats, one payment of 8_000 sats,
// no change, 80 bytes of OP_RETURN data, fee_per_vbyte = 1 (min relay rate).
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
    vec![received_output_10k],
    &[(payment_script, 8_000)],
    None,
    Some(data),
    1, // fee_per_vbyte == minimum relay rate
).unwrap();

// vbytes used internally ≈ size without the ~93-byte OP_RETURN output.
// needed_fee ≈ vbytes, passing the TooLowFee check.
// Real serialized tx is ~93 bytes larger, so actual feerate < 1 sat/vB.
// assert!(tx.fee() as f64 / real_vsize(&tx) < 1.0); // falls below DEFAULT_MIN_RELAY_TX_FEE
// Broadcasting the signed transaction is rejected by Bitcoin Core policy.
```

One caveat I could not fully verify within scope: whether the caller of `SignableTransaction::new` counts as an "unprivileged party" in Serai's deployment, or is always the integrator itself. The arithmetic defect in `send.rs` is unambiguous either way; the reachability classification depends on who supplies `data`.
