### Title
Unchecked `fee_per_vbyte * vbytes` and `payment_sat + fee` arithmetic can wrap, producing a transaction whose outputs exceed its inputs - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` mirrors the sch_sfq bug class: a user-influenced numeric parameter (`fee_per_vbyte`, and the payment amounts) is used directly in `u64` multiplication and addition with no range/overflow check. In release builds these operations wrap, so the computed `needed_fee` and the funds check can collapse to small values, letting `SignableTransaction` be constructed (and then threshold-signed by `TransactionMachine`) with outputs whose total exceeds the true input sum — an invalid, unspendable transaction paying out funds that do not exist.

### Finding Description
Three unchecked arithmetic sites:

1. `let mut needed_fee = fee_per_vbyte * vbytes;` — `fee_per_vbyte` is a caller-supplied `u64` (line 206). With a large `fee_per_vbyte` (e.g. `u64::MAX / vbytes + 1`), the product wraps to a small value, exactly like `ctl->perturb_period * HZ` overflowing in the kernel report.
2. `if input_sat < (payment_sat + needed_fee)` — `payment_sat` is itself an unchecked `sum::<u64>()` of all payment amounts (line 187), and the addition with `needed_fee` is unchecked (line 215). Both can wrap to make the `NotEnoughFunds` check pass when the true required amount far exceeds `input_sat`.
3. `input_sat.checked_sub(payment_sat + fee_with_change)` — the inner `payment_sat + fee_with_change` can overflow *before* `checked_sub` runs (line 228), so the subtraction sees a wrapped-small right-hand side and yields a `value` near `input_sat`, which is then emitted as a change `TxOut` (line 230) far larger than the funds actually remaining.

The result is a `SignableTransaction` whose `tx.output` totals more than `sum(prevouts)`. `multisig()` then builds a FROST `AlgorithmMachine` per input and the group signs the sighashes of this malformed transaction.

### Impact Explanation
The threshold group is driven to sign a Bitcoin transaction that is consensus-invalid (outputs > inputs) or that pays a wildly wrong fee/change. In Serai, batch payment plans and fee rates are derived from data processed by the signers; an unprivileged party who can influence payment amounts or the fee-rate field in the plan data reaches this path via `SignableTransaction::new` → `TransactionMachine` → FROST signing. Outputs include "funds reported received that are not spendable" (an oversized change/payment output that can never confirm) and signing of an unintended transaction, both in the accepted impact set.

### Likelihood Explanation
Requires the wrapped values to align: `fee_per_vbyte` near `u64::MAX/vbytes`, or payment amounts summing past `u64::MAX` (needs many large payments or amounts near the limit — each payment is only checked `>= DUST` at line 166, with no upper bound). The panic-vs-wrap behavior depends on build profile (`debug_assertions`/overflow checks); under the standard release profile used for production, wrapping occurs silently. Conditional reachability keeps this at Medium.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`: `fee_per_vbyte.checked_mul(vbytes)`, `checked_add`/`checked_sum` for `payment_sat`, `input_sat`, and `payment_sat + fee_with_change`, returning a `TransactionError` on overflow — the same fix shape as the kernel's `perturb_period` range check. Also bound `fee_per_vbyte` to a sane maximum at parse time.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs, release build (wrapping arithmetic)
// One input of 100_000 sats, one dust-valid payment, malicious fee rate.
let inputs = vec![received_output_with_value(100_000)];
let payments = &[(script, 546u64)];
let fee_per_vbyte = u64::MAX / 200; // vbytes ~ 100-200 for 1-in/1-out

// needed_fee = fee_per_vbyte * vbytes wraps to a small number,
// passing the TooLowFee and NotEnoughFunds checks.
let tx = SignableTransaction::new(inputs, payments, Some(change_script), None, fee_per_vbyte);
// With change: input_sat.checked_sub(payment_sat + fee_with_change) sees a
// wrapped sum, so `value` ≈ 100_000 even though the real fee should consume
// far more than the input — or the requested fee silently becomes ~0.
// tx.fee() then reports inputs - outputs which no longer matches needed_fee.
```
Equivalently, craft `payments` whose `u64` sum overflows so `payment_sat` wraps below `input_sat`, while the emitted `TxOut`s carry the true large amounts, making `sum(outputs) > sum(inputs)`.
