## Title
Copilot conflict-resolution applies stale in-memory file state instead of re-checking live git status, allowing an attacker-controlled merge conflict to silently overwrite the user's own conflict resolution - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes AI-generated resolution content to disk and stages it for commit, but the safety check that is supposed to prevent clobbering the user's own edits is evaluated against a cached, potentially stale `repositoryStateCache` snapshot rather than the actual file contents on disk at write time.

### Finding Description
The function fetches a single `state` snapshot at the top and never refreshes it before performing file writes: [1](#0-0) 

For every non-delete/modify conflict it looks up `onDiskFile` from that same stale snapshot and uses it as the sole guard against overwriting a resolution the user already made externally: [2](#0-1) 

The comment at line 7241-7246 explicitly documents the intended invariant — "if the user resolved this file externally... git status will report it with no remaining conflict markers... skip and let their resolution stand" — but the code never calls `getStatus`/`loadStatus` again immediately before the `writeFile` to confirm that invariant against the live working directory. It only trusts `state.changesState.workingDirectory.files`, which is populated by periodic/async status refreshes elsewhere in the store (e.g. `_loadStatus`), not guaranteed to be current at the moment of writing. This is structurally identical to the `TokenMigration` bug: a precondition ("both contracts paused" / "file resolution is still live") is documented but not actually enforced at the point where the mutating action occurs, relying instead on a cached belief about state.

Additionally, `resolution.resolvedContent` and `resolution.path` originate from an AI resolution generated from conflict hunks extracted directly from repository content that can come from an attacker-controlled remote branch/PR (`buildConflictContext` reads raw file content containing conflict markers) [3](#0-2) . An attacker who crafts a merge conflict (e.g. via a malicious branch merged/rebased by the victim) controls the conflicting hunk content that seeds the model's resolution, and thus indirectly influences what gets written back via `writeFile` and staged with `git add`.

### Impact Explanation
If the working-directory status changes between when the Copilot resolution stage was computed and when the user clicks "Continue Merge" (a real possibility given `loadStatus` is invoked asynchronously and not re-run inline here), the guard can pass on stale data and `writeFile` will overwrite content the user had just resolved themselves, then stage it with `git add`. Combined with attacker-influenced conflict content feeding the AI-generated `resolvedContent`, this can result in silent corruption of what the user actually commits — content different from what the user reviewed/intended ends up staged and committed without an explicit fresh confirmation.

### Likelihood Explanation
The precondition check exists but is provably decoupled from the actual write operation (no interleaved fresh `getStatus` call), so the TOCTOU window is real and matches the exact failure pattern from the report (documented invariant not enforced at the enforcement point). However, exploitation depends on timing between async status refresh and the user's click, and it is not confirmed from the available code whether a guaranteed-fresh status call happens in an intermediate layer (e.g., in the dispatcher or UI before invoking this store method) — that could not be fully verified from local code alone.

### Recommendation
Before writing each file in `_applyCopilotConflictResolutions`, re-run `getStatus`/`gitStore.loadStatus()` (or otherwise re-read live status for the specific paths) immediately prior to the `writeFile` call, and abort/skip if the on-disk conflict state has changed since the resolutions were generated, rather than relying on the previously cached `repositoryStateCache` snapshot.

### Proof of Concept
Not independently executable from static analysis alone. Conceptually: (1) attacker's branch is merged, producing conflicts whose markers are crafted to steer the Copilot resolution; (2) Copilot generates `resolutions` based on the initial status snapshot; (3) before the user clicks "Continue Merge", the working-directory status changes (e.g., user manually resolves the file, or another async status refresh fires) but the store's cached `state.changesState.workingDirectory.files` used inside `_applyCopilotConflictResolutions` is not re-fetched; (4) `writeFile` overwrites the user's manual resolution with the (attacker-influenced) `resolution.resolvedContent`, which is then staged via `git add` and can be committed unnoticed. Full confirmation of the async timing window would require dynamic testing, which is outside the scope of static code review — this should be validated by a Devin session with runtime access to the repo.
