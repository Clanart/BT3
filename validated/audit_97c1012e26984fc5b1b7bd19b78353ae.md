### Untrusted `ThresholdKeys` deserialization can force large attacker-controlled allocations - ([File: crypto/dkg/src/lib.rs:574](blackvul/serai--022/crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `n` parameter and immediately uses it to allocate/read `n` scalars and `n` group elements before `ThresholdParams::new` is called. A short malicious byte stream can therefore force allocation and parsing work proportional to a 16-bit participant count, rather than rejecting invalid or oversized parameter sets up front.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from untrusted input. If the interpolation tag requests `Interpolation::Constant`, it creates `Vec::with_capacity(usize::from(n))` and reads `n` field elements. It then independently reads `n` verification-share group elements into a `HashMap`. Only after this work does it call `ThresholdParams::new(t, n, i)` and `ThresholdKeys::new` [1](#0-0) .

Because `n` is encoded as `u16`, a malformed serialized key can request up to 65,535 scalar reads and 65,535 point reads. The reader is explicitly exposed as an untrusted-input API in scope through `ThresholdKeys::read`.

### Impact Explanation
The external report's relevant bug class is an availability failure caused by excessive work on attacker-controlled input. Here, unauthenticated bytes supplied to `ThresholdKeys::read` cause bounded but substantial CPU and memory work before semantic validation. Repeated malformed reads can consume resources across deserialization, field decoding, and elliptic-curve point decoding. This is a denial-of-service condition, but not signature forgery, key recovery, or incorrect verification.

The strongest concrete impact is resource exhaustion during input handling. The allocation is capped by `u16::MAX`, so this is a medium-impact DoS analog rather than an unbounded allocation vulnerability.

### Likelihood Explanation
An attacker can reach this path whenever serialized `ThresholdKeys` are accepted from an untrusted party. No private state is needed: the `n` field and interpolation tag are public input bytes. The attacker does not need the payload to deserialize successfully; merely providing enough bytes, or causing repeated reads to be attempted, forces the parser to perform work based on the attacker-selected `n`.

However, the attacker cannot make the allocation truly unbounded because `n` is limited to `u16::MAX`. The issue is also mitigated where callers constrain total message size.

### Recommendation
Validate `t`, `n`, and `i` with `ThresholdParams::new` before allocating vectors or reading variable-count fields. Reject `n` values above protocol-specific participant limits, avoid `Vec::with_capacity` based directly on untrusted lengths, and require the serialized size to be consistent with the advertised count before decoding.

### Proof of Concept
Conceptually, submit a serialized `ThresholdKeys` payload containing:

1. The expected curve-ID length and curve ID.
2. `t = 1`, `n = 0xffff`, and a valid nonzero `i`.
3. Interpolation tag `0` for `Interpolation::Constant`.
4. Enough trailing bytes to sustain scalar/point decoding attempts.

`ThresholdKeys::read` will allocate for 65,535 coefficients at lines 607-612 and then attempt to populate 65,535 verification shares at lines 620-623 before constructing `ThresholdParams` at line 626. Repeating this input performs repeated attacker-directed allocation and decoding work.
