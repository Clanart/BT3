### Title
Spoofed `WWW-Authenticate: realm="GitHub"` header from a malicious git remote triggers an unauthenticated GitHub Enterprise sign-in/OAuth flow bound to an attacker-controlled host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`OmoRouter.approve()`'s broken invariant is that an unprivileged caller can drive a privileged action (granting spend approval) using data/inputs it fully controls, with the router blindly trusting the caller. The GitHub Desktop analog is `getEndpointKind()` in the trampoline credential helper: it classifies an arbitrary git remote as a trusted "GitHub Enterprise" host based solely on a `WWW-Authenticate` header value that the remote HTTP server itself returns during a normal `git fetch`/`clone`. That classification then drives Desktop's real sign-in/OAuth UI against the attacker's own host.

### Finding Description
When git needs credentials for a remote, it invokes Desktop's credential helper trampoline with any captured `WWW-Authenticate` header, forwarded as `wwwauth[...]` fields [1](#0-0) . `getEndpointKind()` trusts this attacker-supplied header as a "happy path" to decide the remote is GitHub-compatible: [2](#0-1) 

If the classification comes back `'enterprise'` and no existing account matches that host, `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)` [3](#0-2) .

`promptForGitHubSignIn` takes the attacker-controlled `endpoint`'s origin verbatim and feeds it into the real Enterprise sign-in flow: [4](#0-3) 

`beginEnterpriseSignIn`/`setSignInEndpoint` eventually leads to `authenticateWithBrowser()`, which opens the system browser at a URL built directly from that origin, embedding the bundled OAuth `client_id`: [5](#0-4) [6](#0-5) 

Because the "authorization" endpoint is entirely attacker-controlled (it's just `origin + /login/oauth/authorize`), the attacker can serve any page there — e.g., a convincing phishing form — and complete the loop by redirecting to Desktop's `x-github-client://oauth` handler with a `code`/`state` pair. Desktop then POSTs to the attacker's own `/login/oauth/access_token` and `/user` endpoints and treats whatever is returned as a legitimate authenticated `Account`: [7](#0-6) [8](#0-7) 

No guard verifies that the host issuing the `WWW-Authenticate: realm="GitHub"` header is actually a real GitHub Enterprise Server (e.g., by probing `/api/v3/meta` or checking a version header) before Desktop escalates a routine credential lookup into its trusted native "Sign in to GitHub Enterprise" UI and OAuth flow. The CSRF `state` value (`crypto.randomUUID()`) only protects against a mismatched callback session [9](#0-8) ; it does nothing to validate the *origin* the flow is bound to, which is fully attacker-supplied.

### Impact Explanation
An attacker who controls (or has compromised/MITM'd) any git HTTP remote that the victim clones or fetches from can, purely by returning a crafted response header, cause GitHub Desktop to pop its own trusted sign-in dialog and drive the user through what looks like a legitimate GitHub Enterprise OAuth sign-in — except every endpoint in that flow (`/login/oauth/authorize`, `/login/oauth/access_token`, `/user`) is served by the attacker. This can be used to phish real credentials (if the attacker's authorize page prompts for username/password directly) or to get the victim to "sign in" and have Desktop bind/store an attacker-fabricated `Account` under that host. This matches the accepted impact class: attacker-controlled repository/remote response leading to unauthorized OAuth/account-binding UI abuse, without any local access, admin rights, or unnatural user steps beyond a normal `fetch`/`clone` plus the habitual "sign in" click users are trained to make.

### Likelihood Explanation
Likelihood is medium: it requires the victim to have a remote configured to (or be tricked into adding) an attacker-controlled/compromised HTTP git server, then perform a normal `fetch`/`clone`/`push`. This is a realistic scenario for open-source contributors adding forks/mirrors, corporate proxies, or compromised self-hosted git servers, and requires no special git configuration beyond git's default behavior of forwarding `WWW-Authenticate` headers to the credential helper.

### Recommendation
Do not trust the `wwwauth[...]` `realm="GitHub"` heuristic on its own to classify a host as GitHub-compatible before triggering the interactive sign-in/OAuth UI. At minimum:
- Require an independent server-side check (e.g., existing `isGitHubHost`/enterprise metadata probe) before falling back to the header heuristic, rather than treating the header as sufficient by itself.
- When falling back to `promptForGitHubSignIn` for a previously-unknown host, surface the raw hostname prominently and require explicit user confirmation that they intend to add this specific host as a GitHub Enterprise account, distinct from the normal in-app "Add Enterprise account" flow.
- Consider not auto-triggering the full browser-based OAuth flow purely from a credential-helper callback originating from git subprocess I/O tied to an arbitrary, previously untrusted remote.

### Proof of Concept
1. Attacker stands up an HTTP git server (or MITMs one) at `https://evil.example.com/repo.git`.
2. Victim runs `git clone https://evil.example.com/repo.git` (or adds it as a remote and fetches) inside GitHub Desktop.
3. When git requests credentials for the host, the server responds with `WWW-Authenticate: Basic realm="GitHub"`.
4. `getEndpointKind()` returns `'enterprise'` for `evil.example.com` [2](#0-1) .
5. Since no account exists for `evil.example.com`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com')` [3](#0-2) , which shows Desktop's native "Sign in to GitHub Enterprise" dialog bound to that origin [10](#0-9) .
6. Clicking "Sign in using your browser" opens `https://evil.example.com/login/oauth/authorize?client_id=...&state=...` in the system browser [5](#0-4)  — a page entirely controlled by the attacker, who can present a credential-harvesting form or immediately redirect to `x-github-client://oauth?code=X&state=<echoed-state>`.
7. Desktop's `resolveOAuthRequest` accepts the callback (state matches because it was echoed back) and calls `requestOAuthToken`/`fetchUser` against `evil.example.com`, completing a "successful" sign-in bound to the attacker's host [7](#0-6) .

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)

        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })

export function getOAuthAuthorizationURL(

  const urlBase = getHTMLURL(endpoint)

  return new window.URL(

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
