## Finding: Unbounded Recursion in `AccountKeyRoleBased.DecodeRLP` Enables Stack-Overflow DoS via a Single Transaction

### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` account keys causes stack-overflow crash - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
Elasticsearch's GHSA-5xm9-x7x4-4j5x describes a stack overflow caused by unbounded recursive parsing of nested `GeometryCollection` WKT objects. Kaia has a structurally identical bug class: `AccountKeyRoleBased.DecodeRLP` recursively decodes each contained key by calling `rlp.DecodeBytes` on nested byte blobs, and if a nested key is itself typed `AccountKeyTypeRoleBased`, the decoder recurses into itself again with no depth limit. This is reachable from a single `TxTypeAccountUpdate` / `TxTypeFeeDelegatedAccountUpdate` transaction submitted by any unprivileged sender.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes an outer list of byte blobs, and for each blob recursively decodes an `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads a key type and then calls `s.Decode(serializer.key)`, which — if the type is `AccountKeyTypeRoleBased` — re-enters `AccountKeyRoleBased.DecodeRLP`: [2](#0-1) 

This recursive decode path is invoked directly while decoding a transaction's `Key` field, e.g. in `TxInternalDataFeeDelegatedAccountUpdate.DecodeRLP` and `TxInternalDataAccountUpdate.UnmarshalJSON`, both of which call `rlp.DecodeBytes` on the raw key bytes as soon as the transaction is parsed from the wire (RPC submission, p2p propagation, or txpool ingestion) — *before* any semantic validation runs: [3](#0-2) [4](#0-3) 

The only guard against nested `RoleBased` keys, `CheckInstallable`/`CheckUpdatable`'s `IsCompositeType()` check, executes only **after** the entire nested structure has already been fully RLP-decoded — the check happens too late to prevent the recursive decode itself: [5](#0-4) 

A dedicated test confirms nesting is rejected only at the *semantic* validation stage (`kerrors.ErrNestedCompositeType`), not at decode time: [6](#0-5) 

Because RLP is very size-efficient, an attacker can encode thousands of nesting levels of `AccountKeyRoleBased` (each level only a few bytes) within a transaction well under normal size limits, causing the recursive `DecodeRLP`/`Decode` call chain to exhaust the goroutine stack. Go's stack-overflow due to unbounded recursion is a fatal, unrecoverable runtime error (it cannot be caught by `recover()`), crashing the entire node process.

### Impact Explanation
Any node that decodes this malicious `TxTypeAccountUpdate`/`TxTypeFeeDelegatedAccountUpdate` transaction — via `eth_sendRawTransaction`, p2p transaction propagation, or transaction-pool ingestion — will crash with an unrecoverable stack overflow. Since this transaction is validated and decoded identically by all full nodes, an attacker submitting it to the network can crash multiple/all validating and RPC nodes simultaneously, resulting in an availability-impacting, network-wide denial of service — matching the severity profile of the original Elasticsearch report (CVSS `C:N/I:N/A:H`).

### Likelihood Explanation
Likelihood is high: the attack requires only constructing and submitting/broadcasting a single RLP-encoded transaction, requires no special privileges, no fee-delegation counterparty, and no wait for block inclusion — decoding alone (which happens on every node that receives or relays the transaction) triggers the crash.

### Recommendation
Add an explicit recursion/nesting-depth limit inside `AccountKeyRoleBased.DecodeRLP` (and the corresponding `UnmarshalJSON` path) that rejects a nested `AccountKeyTypeRoleBased` (or otherwise excessively deep) key immediately at decode time, before recursing further — mirroring the `isNested` check already present in `checkAccountKeyZeroValues` in `api/api_kaia.go`, but enforced unconditionally at the RLP/JSON decode layer rather than only in semantic validation performed after decoding completes.

### Proof of Concept
1. Construct an `AccountKeySerializer` for `AccountKeyTypeRoleBased` whose single element is itself a fully RLP-encoded `AccountKeySerializer` of type `AccountKeyTypeRoleBased`, and repeat this nesting programmatically N times (e.g., N = 100,000), wrapping the innermost key with a trivial `AccountKeyNil`/`AccountKeyLegacy`.
2. Embed the resulting deeply-nested byte blob as the `Key` field of a `TxTypeAccountUpdate` (or `TxTypeFeeDelegatedAccountUpdate`) transaction, sign it, and RLP-encode the full transaction.
3. Submit the transaction via `eth_sendRawTransaction` to a Kaia node, or feed it directly into `blockchain.TxPool.AddRemote`.
4. Observe that decoding (`Transaction.DecodeRLP` → `TxInternalDataFeeDelegatedAccountUpdate.DecodeRLP` → `accountkey.AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recursing N times) exhausts the goroutine stack and crashes the node process with a fatal, unrecoverable stack overflow, before `CheckInstallable`'s nested-type check is ever reached.

```go
func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
```

```go
func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
```
