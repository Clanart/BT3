### Title
Cached DKG-confirmation preprocess reused across validator sets: context omits genesis/session, enabling nonce reuse and validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug is a NULL dereference caused by one path (`sk_psock_stop_verdict`) clearing a saved callback while a concurrent path (`sk_psock_verdict_data_ready`) still uses it — a stale/cleared-state reuse under concurrency. The Serai analog is `SigningProtocol::preprocess_internal`, which persists a deterministic FROST preprocess seed in a shared database keyed by a `context` that is under-scoped. For `DkgConfirmer`, the context is `(b"DkgConfirmer", attempt)` — it does not include the tributary `genesis`, `ExternalValidatorSet`, or session. Since the coordinator shares one DB across all networks/tributaries, a validator participating in two validator sets that run a DKG confirmation with the same `attempt` reuses the same 32-byte `ChaCha20Rng` seed, regenerating identical FROST nonces to sign different `set_keys_message` payloads — textbook nonce reuse.

### Finding Description
`preprocess_internal` lazily creates a preprocess, XOR-encrypts its `CachedPreprocess` seed, and stores it under `CachedPreprocesses::set(self.txn, &self.context, ...)`; every subsequent call for the same context reloads the identical seed and reconstructs identical nonces via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` [1](#0-0) . The safety comment explicitly states nonce reuse safety derives from "the nonces being context-bound" [2](#0-1) , yet `DkgConfirmer::signing_protocol` builds `context = (b"DkgConfirmer", self.attempt)` with no binding to `spec.genesis()` or the validator set [3](#0-2) . All other data accumulated by the block handler is correctly keyed by `genesis` (e.g., `DataDb::get(self.txn, genesis, ...)`, `ConfirmationNonces::set(self.txn, genesis, attempt, ...)`) [4](#0-3) [5](#0-4) , making the omission in `CachedPreprocesses` anomalous. `share` then signs `set_keys_message(&self.spec.set(), removed, key_pair)`, a message that differs per set [6](#0-5) .

### Impact Explanation
Two DKG confirmations under the same `attempt` but different sets produce two Schnorr signature shares `s = d + b·e + c·λ·secret` over identical nonces `d, e` (seed-derived via `ChaCha20Rng::from_seed(*seed.0)` in `seeded_preprocess`) with different binding factors/challenges and different messages. An observer of the two public `DkgConfirmed` shares can solve for the signer's secret contribution, recovering the validator's static Ristretto key — the root-of-trust key used for tributary signing and `SignCompleted` attestations — enabling signature forgery. This is a private-key-recovery class impact (High/Critical), not merely DoS. The FROST spec's own warning applies: "Reusing preprocesses would enable a third-party to recover your private key share" [7](#0-6) .

### Likelihood Explanation
Requires the same coordinator key to be a validator in two distinct validator sets whose DKGs reach the same `attempt` number — common for multi-network validators (attempt numbering starts at 0 for every DKG and is per-topic per-genesis). No malicious validator, collusion, or BFT failure is needed; the collision is deterministic once two sets share an attempt index. Reachability caveat: the recovered secret is the share within the MuSig aggregation; if `musig()` derandomizes the effective secret share per participant set, full recovery may additionally require solving across the differing aggregation coefficients — the nonce reuse itself is unconditional.

### Recommendation
Include `self.spec.genesis()` (and/or `spec.set().session`) in the `SigningProtocol` context — e.g., `context = (b"DkgConfirmer", spec.genesis(), attempt)` — so `CachedPreprocesses` is namespaced per set, matching the `genesis`-keyed pattern used by `DataDb`, `ConfirmationNonces`, and `DkgKeyPair`. The encryption-key preimage already mixes `self.context.encode()`, so fixing the context propagates correctly to the encryption key as well [8](#0-7) .

### Proof of Concept
1. Validator `V` (key `k`) is a member of sets for networks A and B, each with its own `TributarySpec` (`genesis_A ≠ genesis_B`) sharing the coordinator's `raw_db`.
2. Both sets initiate DKG attempt `0`. Each calls `dkg_confirmation_nonces(k, spec, txn, 0)`, which constructs `DkgConfirmer` with `context = (b"DkgConfirmer", 0)` for both.
3. First call stores `CachedPreprocesses[(b"DkgConfirmer", 0)] = enc(seed)`; the second call's `CachedPreprocesses::get` returns it, skipping generation [9](#0-8) .
4. Both `share()` calls invoke `machine.sign(preprocesses, set_keys_message(...))` with identical nonces but distinct messages/participant sets, publishing two shares on the two public tributaries.
5. Any observer collects both `DkgConfirmed` shares and solves the two linear equations for the reused nonce and secret share, recovering `V`'s key material.
