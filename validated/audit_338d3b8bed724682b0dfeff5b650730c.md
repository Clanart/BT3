### Title
Unbounded attacker-controlled workload in `SchnorrAggregate::read`/`verify` enables asymmetric CPU/memory exhaustion - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The MadeYouReset class — an attacker repeatedly forcing the server to perform expensive work while evading the protocol's stated concurrency limit — maps onto Serai's aggregate Schnorr verification path. `SchnorrAggregate::read` trusts a 4-byte length prefix with no bound, and `SchnorrAggregate::verify` performs hashing and multiexponentiation work linear in that attacker-declared count, with no analog of `SETTINGS_MAX_CONCURRENT_STREAMS` anywhere on the path.

### Finding Description
`SchnorrAggregate::<C>::read` reads a little-endian `u32` count and loops `C::read_G` for each element, with no cap on the count and no pre-check that enough bytes remain:

```rust
// crypto/schnorr/src/aggregate.rs:77-88
let mut len = [0; 4];
reader.read_exact(&mut len)?;
let mut Rs = vec![];
for _ in 0 .. u32::from_le_bytes(len) {
  Rs.push(C::read_G(reader)?);
}
```

Each `read_G` performs full point decompression (field inversion / square-root recovery — hundreds of field operations) per ~32 attacker-controlled bytes. Because the reader is typically a network buffer or stream, an attacker can stream R encodings continuously; every byte received is converted into a `C::G` and retained in `Rs`.

The subsequent `verify` then does per-element transcript hashing (`weight(&mut digest)` per signature), builds `Vec::with_capacity(2 * keys_and_challenges.len() + 1)`, and runs `multiexp_vartime` over the entire list (`crypto/schnorr/src/aggregate.rs:127-145`). There is no maximum-signature bound anywhere: unlike `Transaction::read` in the coordinator, which checks `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT`, or `Call::read` in `networks/ethereum/src/machine.rs`, which explicitly chunks reads to bound the DoS ("A valid DoS would be to claim a 4 GB data is present for only 4 bytes"), `SchnorrAggregate` has no limit at all.

Like MadeYouReset, the design-level accounting check that should bound concurrent work (a cap on aggregated signatures) is simply absent, so a single unprivileged party can drive unbounded work per connection. Since FROST's `complete` in `crypto/frost/src/sign.rs:462-494` already treats the happy path as cheap and pushes failures into an O(n log n) `blame_vartime` binary search (`crypto/multiexp/src/batch.rs:108-123`), any integrator batch-verifying attacker-supplied aggregates additionally pays a super-linear blame scan when the batch fails.

### Impact Explanation
- **Memory exhaustion**: `Rs` grows without bound during `read`; a sustained stream of valid point encodings forces linear heap growth until OOM. On the `verify` side, `pairs` doubles the footprint again.
- **CPU exhaustion**: each 32-byte group element costs a full decompression, then a transcript hash and multiexponentiation terms in `verify` — roughly two orders of magnitude more CPU per byte than the attacker spends transmitting.
- **Amplified blame cost**: a single invalid statement in a large batch triggers `blame_vartime`, which performs ~log2(n) additional multiexps over the whole statement set — the attacker converts one cheap forgery into repeated full-batch scans.
- No secret material is required and no signature needs to be valid; the cost is incurred before any signature is checked.

### Likelihood Explanation
Reachable wherever `SchnorrAggregate::read`/`verify` (or a wrapper) is fed bytes/keys-and-challenges from an untrusted counterparty — exactly the threat model the type is designed for (aggregated signatures from multiple signers). The attacker needs no key share, no valid signature, and no protocol role; this satisfies the "unprivileged party with public inputs" requirement. Exploitation is trivial: emit a large `u32` length followed by a continuous stream of canonical point encodings. The only mitigating factor is that exploitation requires an integrator that aggregates externally supplied signatures over an unbounded channel — purely a deployment question, not a code barrier.

### Recommendation
- Add an explicit maximum aggregate size (e.g., a `MAX_AGGREGATE_SIGNATURES` constant or a parameter on `read`/`verify`), and reject `len` values exceeding it before looping, mirroring the `TRANSACTION_SIZE_LIMIT` pattern used in `Transaction::read`.
- Read R encodings incrementally against the remaining input length (fail fast when `len` implies more bytes than can be present), similar to the 1 KB chunked read in `networks/ethereum/src/machine.rs`.
- Consider capping `BatchVerifier` sizes or making `blame_vartime` bounded so a single invalid statement in a large attacker-sized batch cannot force repeated full multiexps.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use schnorr::aggregate::SchnorrAggregate;
use dalek_ff_group::Ed25519;

// Attacker bytes: u32::MAX count followed by a stream of valid point encodings.
let mut buf = u32::MAX.to_le_bytes().to_vec();
// Generator encoding appended repeatedly; attacker streams this indefinitely.
let g = Ed25519::generator().to_bytes();
for _ in 0 .. 1_000_000 {
    buf.extend_from_slice(g.as_ref());
}

// 4-byte prefix declares ~4.3 billion Rs; read allocates/deserializes unboundedly.
let agg = SchnorrAggregate::<Ed25519>::read(&mut Cursor::new(&buf)).unwrap();
// agg.Rs now holds 1M decompressed points for ~32 MB of input;
// verify() then hashes + multiexps over all of them, and on failure runs
// blame_vartime with O(n log n) extra multiexps.
```
Under a streaming reader (e.g., a socket-backed `Read`), the declared count never needs to be backed by actual bytes — the loop only terminates at EOF, so memory grows with whatever the attacker sends, with no protocol-level limit analogous to the HTTP/2 concurrent-streams counter MadeYouReset defeats.
