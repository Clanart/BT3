### Title
Outputs below the dust threshold sent to a Serai Bitcoin address are silently discarded, permanently stranding the funds - (File: processor/src/multisigs/scanner.rs)

### Summary
The external report describes funds accepted by a contract but never credited or refundable (ETH sent alongside an ERC-20 deposit becomes stuck). The analogous shape in Serai's Bitcoin processor: when a block is scanned, `get_outputs`/`scan_transaction` return every output paying to a registered multisig script, but the scanner's main loop silently drops any output whose value is below `N::DUST` (546 sats). A user who funds a branch/forward/deposit address with an amount under that threshold has the funds land on a key the multisig controls, yet the output is never emitted as a `ScannerEvent::Block` output, never credited, and never scheduled to be spent — it is stranded exactly like the un-refunded `msg.value` in the original report. [1](#0-0) [2](#0-1) 

### Finding Description
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` returns a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script (base key, Branch, Change, Forwarded offsets), regardless of value. [3](#0-2)  The processor scanner loop then filters: `if output.balance().amount.0 >= N::DUST { outputs.push(output); }` — sub-dust outputs are dropped before being emitted, before being recorded in `ram_outputs`/`seen`, and before any eventuality handling. [1](#0-0)  There is no error, no event, and no later rescan: the scan cursor advances past the block, so the output is permanently invisible to the protocol even though it is spendable by the threshold key (`Scanner`/`SignableTransaction` would happily spend it if it were ever handed in — `SignableTransaction::new` only rejects dust *payments*, not dust inputs). [4](#0-3) 

### Impact Explanation
Any BTC amount below 546 sats sent to a Serai deposit, branch, change, or forward address is received on-chain but never credited to the sender and never entered into the multisig's spendable output set. The funds sit at a key the threshold group controls but which no protocol flow will ever sign for — economically equivalent to ETH stuck in the bounty contract: accepted value with no recovery path. An attacker can also deliberately grief by dust-funding an address; the sender's funds are burned from the protocol's perspective.

### Likelihood Explanation
Reachable by any unprivileged party who sends a Bitcoin transaction to a Serai-registered address with a value under the dust constant — a plausible accident for small test deposits, change-amount errors, or fee-miscalculated transactions. No malicious validator, leaked key, or integrator misuse is required; the drop is deterministic and silent.

### Recommendation
Either reject/flag sub-dust outputs explicitly (emit an event so the deposit can be handled or refunded via an out-of-band spend), or accumulate them in `ram_outputs`/`seen` so they are at least tracked and can be batched as inputs later. At minimum, document that sub-dust deposits are unrecoverable. Analogously to the original fix, the scan path should not silently accept-then-ignore value it cannot credit.

### Proof of Concept
1. `scanner(key)` registers External/Branch/Change/Forwarded scripts for a multisig key. [5](#0-4) 
2. A user broadcasts a TX paying 500 sats to the branch address (`p2tr_script_buf(key + G*BRANCH_OFFSET)`).
3. `scan_transaction` returns the `ReceivedOutput`; `get_outputs` wraps it as an `Output`. [6](#0-5) 
4. In the scan loop, `output.balance().amount.0 (500) >= N::DUST (546)` is false, so the output is never pushed, never emitted in `ScannerEvent::Block`, and never inserted into `ram_outputs`/`seen`. [1](#0-0) 
5. The block is marked scanned; the 500 sats are permanently uncredited though controlled by the multisig key.
