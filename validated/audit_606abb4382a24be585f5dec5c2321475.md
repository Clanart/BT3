### Title
FROST secret key share and signature share left unwiped on attacker-triggered `complete` error paths - (File: crypto/frost/src/sign.rs)

### Summary
The advisory's bug class is secret material surviving in memory after an attacker-triggerable early return. In Serai's FROST implementation, `AlgorithmSignatureMachine` holds the adjusted secret share (`view.secret_share`, via `ThresholdView`) and our signature share (`share: C::F`). The struct has no `#[derive(Zeroize)]` and no `Drop` impl, and none of these fields are wrapped in `Zeroizing` at this level, so when `SignatureMachine::complete` errors out — a path fully controlled by a counterparty feeding bytes through `read_share` — the key-share material is dropped in place on the heap, recoverable until reuse/GC.

### Finding Description
`AlgorithmSignatureMachine` (crypto/frost/src/sign.rs:431) is declared with only `#[allow(non_snake_case)]` — unlike `Params` and `AlgorithmSignMachine`, which at least carry `#[derive(Zeroize)]` (lines 50, 245). It stores:

- `params: Params<C, A>` — contains `keys: ThresholdKeys<C>`
- `view: ThresholdView<C>` — contains the secret share used to produce `share` in `sign_share` (sign.rs:398)
- `share: C::F` — our produced signature share (sign.rs:436)

`complete` (sign.rs:447) reaches `Err` returns driven entirely by remote-supplied bytes:

1. `read_share` (sign.rs:443-445) parses `C::read_F(reader)?` — arbitrary untrusted scalar bytes.
2. `validate_map(&shares, ...)` (sign.rs:452) errors on an attacker-chosen `Participant` key set.
3. `self.params.algorithm.verify_share(...)` returning `Err` produces `Err(FrostError::InvalidShare(*l))?` (sign.rs:476-484).
4. A failing batch verification produces `Err(FrostError::InvalidShare(l))?` (sign.rs:487-489).

On each path, `self` is consumed and dropped. Because `AlgorithmSignatureMachine` neither derives `Zeroize`/`ZeroizeOnDrop` nor wraps `view`/`share` in `Zeroizing`, the key-share scalar and signature share remain in heap memory. Note that even the `#[derive(Zeroize)]` on `AlgorithmSignMachine` only implements `fn zeroize(&mut self)` — it does not install a `Drop` impl — so intermediate plaintext such as the `responses` map entries (`sum`, `responses.insert(params.i(), self.share)`, sign.rs:454-460) is likewise never wiped on the `InvalidShare` early return.

This matches the report's class exactly: the API-success path is fine, but error returns triggered by malformed remote input abandon secret material on the heap. It is also the same class as the prior Serai-relevant advisory the report cites (GHSA-8h84-fhqq-q58v, key zeroization).

### Impact Explanation
`view.secret_share` is the long-lived FROST secret key share; `self.share` is a per-signature share `s_i = nonce_i + λ_i·sk_i·c`. An attacker with memory-read capability (core dump, swap, heap scraping, crash artifact) who deliberately submits an invalid share to force `complete` to error leaves the secret share resident in freed-but-unwiped heap. Recovery of `secret_share` (plus its public verification share) degrades the threshold scheme — combined with `t-1` other compromised shares it yields the group key — and recovery of a `share` for a session whose nonce handling is elsewhere compromised enables share-recovery attacks the codebase explicitly warns about (sign.rs:85-87, 211-213). This is secret leakage, satisfying the Medium bar.

### Likelihood Explanation
Reachability is high: `read_share` + `complete` are the public API for collecting counterparties' signature shares, and an unprivileged participant can supply a scalar that fails `verify_share` or batch verification, or simply a malformed encoding that deserializes fine but verifies false — all without any privilege beyond participating in a signing session. Exploitation additionally requires a memory-disclosure primitive, which is inherent to this bug class (identical assumption to the referenced advisory, rated High there); severity here is lower because a single FROST share alone does not recover the group key, so Medium is appropriate.

### Recommendation
Derive `Zeroize`/`ZeroizeOnDrop` on `AlgorithmSignatureMachine` (or wrap `view`'s share and `share` in `Zeroizing<C::F>`), and add a `Drop` impl (or `ZeroizeOnDrop`) to `Params` and `AlgorithmSignMachine` so that `ThresholdKeys`/`CachedPreprocess` are wiped even though `#[derive(Zeroize)]` alone does not run on drop. Wipe `responses`/`sum` before the `InvalidShare` returns in `complete`. Ensure the wipe is idempotent and runs on every `Err` path, mirroring the report's `defer caMgr.Wipe()` fix.

### Proof of Concept
Conceptual: two parties run FROST. The signer completes `preprocess`/`sign` normally. The counterparty sends a signature share encoding a scalar that deserializes via `C::read_F` (sign.rs:444) but fails `verify_share` (sign.rs:476) or batch blame (sign.rs:487). `complete` returns `Err(FrostError::InvalidShare(l))`; the consumed `AlgorithmSignatureMachine` is dropped without zeroization, leaving `view.secret_share` and `share` bytes in the heap allocation formerly backing the struct and the `responses` `HashMap` — recoverable from a core dump or heap scan, exactly as in the referenced advisory.
