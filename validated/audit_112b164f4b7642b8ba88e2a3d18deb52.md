### Title
Unauthenticated OP_RETURN payer attribution lets anyone credit a real operator with a payout it never funded - (File: core/src/verifier.rs, core/src/task/payout_checker.rs)

### Summary
`create_payout_txhandler` puts the fronting operator's xonly_pk in an OP_RETURN output that is neither signed by that operator nor covered by the withdrawing user's `SinglePlusAnyoneCanPay` signature. `update_finalized_payouts` blindly trusts this OP_RETURN to set `payout_payer_operator_xonly_pk`, and `PayoutCheckerTask::run_once` for the named operator's own node unconditionally calls `handle_finalized_payout` to build and broadcast a Kickoff→Reimburse chain, paying that operator from the shared move-to-vault UTXO for a payout it never actually funded.

### Finding Description
The claimed binding is: `payout_payer_operator_xonly_pk` stored for withdrawal `i` (used by `get_first_unhandled_payout_by_operator_xonly_pk` and `handle_finalized_payout` to authorize a Reimburse for operator X) must equal the operator whose own BTC funded `output0` of the confirmed payout transaction for `i`.

Tracing the code shows this binding is never enforced:

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds input0 = withdrawal UTXO (KeySpend, signed only by the user with `SinglePlusAnyoneCanPay`), output0 = user payout, output1 = anchor, output2 = OP_RETURN(`operator_xonly_pk`). The signature check in `withdraw`/`sign_optimistic_payout` (`core/src/operator.rs:630-637`) via `calculate_sighash_txin(0, SinglePlusAnyoneCanPay)` only covers input0 and output0 — the OP_RETURN output is **not covered by any signature at all**.
- The actual full withdrawal amount is not carried by the tiny "dust" withdrawal UTXO (550 sats, see `generate_withdrawal_utxo` in `core/src/test/common/setup_utils.rs:480-497`); the transaction is funded with extra inputs added by whoever broadcasts it (`fund_raw_transaction(... add_inputs: true ...)` in `core/src/operator.rs:652-674`). There is no on-chain or off-chain check that the extra funding inputs belong to the operator named in the OP_RETURN.
- `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) parses the OP_RETURN of whatever transaction happens to spend the registered withdrawal UTXO and stores that xonly_pk as `payout_payer_operator_xonly_pk`, with no check that the named operator's key appears anywhere else in the transaction (no signature, no matching input ownership, no attestation).
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) for operator X's own process polls `get_first_unhandled_payout_by_operator_xonly_pk(X)` (`core/src/database/verifier.rs:282-313`), which returns any withdrawal whose stored `payout_payer_operator_xonly_pk` equals X, and unconditionally calls `self.operator.handle_finalized_payout(...)`.
- `handle_finalized_payout` (`core/src/operator.rs:839-964`) consumes X's own unused/signed kickoff connector and drives the Kickoff→Reimburse flow that ultimately spends `move_txhandler.get_spendable_output(UtxoVout::DepositInMove)` (`core/src/builder/transaction/operator_reimburse.rs:341-385`) — i.e., pays X from the shared N-of-N vault — with no verification that X (or anyone acting for X) broadcast or otherwise authorized the specific payout transaction being credited.

Exploit flow: an attacker who is simply the withdrawing user (unprivileged; can call `withdraw` gRPC and hold their own withdrawal UTXO/signature) constructs the payout transaction themselves off the official flow: input0 = withdrawal UTXO + user's `SinglePlusAnyoneCanPay` signature (which they legitimately hold, since they are the user), output0 = their own payout address/amount, and any number of additional self-funded inputs to cover the shortfall between the dust input and the full withdrawal amount, plus an OP_RETURN naming operator X's public xonly_pk (a real, configured operator who never received this specific withdrawal, never signed off, and never funded it). The attacker broadcasts this transaction directly to Bitcoin, racing any operator front. Once it confirms and reaches finality, verifier nodes' `update_finalized_payouts` records X as the payer. X's own `PayoutCheckerTask` (running automatically on X's node) then proceeds to build and send Kickoff/Reimburse transactions, ultimately spending the move-to-vault UTXO to reimburse X — for a payout X never funded.

None of the listed guards catch this: `SECP.verify_schnorr` only checks the user's signature over input0/output0 (not the OP_RETURN or extra inputs); `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only checks that the kickoff's `operator_xonly_pk` matches the DB's `payout_payer_operator_xonly_pk` — which is exactly the attacker-controlled value being validated against itself, so it always matches; there is no DB uniqueness constraint or cross-check tying the credited operator to actual fund provenance.

### Impact Explanation
An attacker can cause a real, uninvolved operator to have BTC paid to them out of the shared move-to-vault UTXO for a withdrawal that operator never fronted with their own capital — this is squarely "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" (Critical). Because the framed operator's automation (`PayoutCheckerTask`) acts automatically and irreversibly (queues Kickoff and eventually Reimburse transactions), the vault loses `bridge_amount` (minus fees) per exploited withdrawal, credited to an operator who did not spend anything themselves. This is repeatable per withdrawal and per operator — any withdrawal index can be targeted at any currently-configured operator's xonly_pk (which is public via `GetParams`/operator config), so the blast radius spans all deposits/operators using the standard (non-optimistic) payout path.

### Likelihood Explanation
Preconditions are minimal and match the standard unprivileged capability set: the attacker only needs to be a withdrawing user with a valid Citrea withdrawal registration and the corresponding withdrawal UTXO/signature, both of which they legitimately control by definition of initiating their own withdrawal. No verifier, operator, or aggregator collusion is required. The attacker's cost is simply the BTC they must supply as the "difference" input to complete their own payout (which they would pay in any case to get their own withdrawal paid out) plus normal transaction fees — there is no extra cost associated with picking an arbitrary victim operator's key for the OP_RETURN. The only skill required is assembling a raw Bitcoin transaction with a custom OP_RETURN, well within "choose the bytes of ... an OP_RETURN" as stated in the threat model. This is repeatable for every withdrawal a user can create.

### Recommendation
Require operator authentication for the fronting attribution instead of an unsigned OP_RETURN: e.g., have the credited operator co-sign the payout transaction (covering the OP_RETURN output) with their own key, or require the extra funding inputs to be provably owned/controlled by the operator being credited and check this at `update_finalized_payouts`/`handle_finalized_payout` time. At minimum, `is_kickoff_malicious`/`handle_finalized_payout` should independently verify that the credited operator authorized this specific spend (e.g., by checking a database record created only when that operator's own `withdraw` RPC handler broadcast the transaction) rather than trusting the unauthenticated OP_RETURN bytes taken directly from the chain.
