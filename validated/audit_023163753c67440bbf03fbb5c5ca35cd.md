### Title
upb JSON encoder omits HTML-unsafe character escaping (`<`, `>`, `&`, `=`, `'`) used by Ruby/PHP bindings, unlike C++/Java/C# ProtoJSON encoders - ([File: upb/json/encode.c])

### Summary
The C++ (`src/google/protobuf/json/internal/writer.cc`), Java (`java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`), and C# (`csharp/src/Google.Protobuf/JsonFormatter.cs`) ProtoJSON string encoders all deliberately escape `<`, `>` (and, in Java's case, also `&`, `=`, `'`) as `\uXXXX` sequences in addition to the characters mandated by the JSON spec, explicitly to prevent the output from being unsafe when embedded in HTML/`<script>` contexts. The upb-based encoder shared by the PHP and Ruby (and other upb-consuming) bindings, `jsonenc_put_escaped_char` in `upb/json/encode.c` (duplicated in `ruby/ext/google/protobuf_c/ruby-upb.c` and `php/ext/google/protobuf/php-upb.c`), only escapes the JSON-spec-required characters (`\n`, `\r`, `\t`, `"`, `\f`, `\b`, `\\`, and control chars `<0x20`) and passes `<`, `>`, `&`, `=`, `'` straight through unescaped.

### Finding Description
This is a cross-implementation escaping inconsistency directly analogous to the alf.io issue: text controlled by an upstream, semi-trusted actor (an event admin able to set customizable strings) is serialized into JSON that is later embedded into an HTML page/script context, and because the specific characters needed to break out of that context (`<`, `>`) are not escaped, the JSON payload is not safe for embedding verbatim in HTML/JS, even though it is syntactically valid JSON.

Evidence in this repo:
- C++ writer explicitly escapes `<`/`>` "to prevent security bugs in JavaScript": [1](#0-0) 
- Java's `JsonFormat` printer explicitly escapes `<>&='` "to prevent XSS risks" and has a regression test (`testHtmlEscape`, referencing bug b/73832901) verifying `</script>` becomes `\u003c/script\u003e`: [2](#0-1) [3](#0-2) 
- C#'s `JsonFormatter` similarly escapes `<`/`>` "for HTML security": [4](#0-3) 
- The core C++ `internal/writer.cc` `HtmlEscape` unit test proves `</script>` in a string value is rendered as `\u003c/script\u003e`: [5](#0-4) 
- By contrast, the upb encoder's escape table has no case for `<`, `>`, `&`, `=`, or `'`; those bytes fall to the `default` branch and, since they are >= 0x20, are written through unmodified: [6](#0-5) 
- The exact same function body is compiled into the Ruby native extension: [7](#0-6) 
- And into the PHP native extension: [8](#0-7) 
- PHP's pure-PHP fallback encoder (`GPBJsonWire.php`) has the same gap — its `jsonNiceEscape`/`isJsonEscaped` only cover RFC 4627-mandated characters, not `<`/`>`: [9](#0-8) 

So for the same logical operation (`MessageToJson`/`JsonEncode` on a message with a string field containing `</script>`), C++, Java, and C# produce `\u003c/script\u003e` while the upb-backed encoder (used transitively by PHP and Ruby's native protobuf extensions) produces the literal `</script>` unescaped.

### Impact Explanation
If application code (analogous to alf.io) embeds the upb/PHP/Ruby-generated protobuf JSON string directly into an HTML page inside a `<script>` block (a documented/common pattern for "preloaded JSON data"), a value containing `</script><script>...` supplied by a semi-trusted actor (e.g., an admin-configurable text field, similar to alf.io's customizable UI text) can terminate the enclosing script tag and inject arbitrary markup/script, exactly as in the alf.io CVE. This is a confidentiality/integrity-impacting output-encoding gap in a supported public serialization API (ProtoJSON `MessageToJson`), not a parsing memory-safety bug, matching the CVSS profile of the original report (`AV:N/AC:L/PR:H/UI:N/C:N/I:H/A:H` — requires the attacker to control input that reaches the encoder, and impact is realized only when the consuming application embeds the JSON unsafely, similar to alf.io's own caveat that CSP mitigates script execution).

### Likelihood Explanation
Medium. Exploitability requires: (1) attacker-influenced string content reaching a message field, (2) that message being serialized via the upb-backed JSON encoder (PHP/Ruby native protobuf), and (3) the consuming application embedding the resulting JSON text inline in HTML/`<script>` without an additional HTML-context-aware escaping layer or CSP — the same precondition alf.io itself had. Protobuf's JSON encoders are documented as JSON encoders, not HTML-safe encoders, so this is a defense-in-depth inconsistency rather than a guaranteed-exploitable primitive in isolation, but the C++/Java/C# implementations already treat it as a hardening requirement worth explicit code and regression tests, showing Google's own protobuf maintainers consider this an actionable security property that PHP/Ruby lack.

### Recommendation
Update `jsonenc_put_escaped_char` in `upb/json/encode.c` (and the generated copies in `ruby-upb.c` / `php-upb.c`) to additionally `\u00XX`-escape `<`, `>` (and ideally `&`, `=`, `'` for parity with Java) the same way `src/google/protobuf/json/internal/writer.cc` and `JsonFormat.java` do, then regenerate the upb amalgamation used by the Ruby and PHP native extensions. Add a regression test mirroring `JsonFormatTest.testHtmlEscape` / `JsonTest.HtmlEscape` for the upb JSON encoder to lock in the behavior.

### Proof of Concept
1. Using the Ruby (or PHP) native protobuf extension, build a message with a string field set to `"</script><script>alert(1)</script>"`.
2. Call the message's `to_json` (Ruby) / `serializeToJsonString` (PHP), which route through `jsonenc_string` → `jsonenc_stringbody` → `jsonenc_put_escaped_char` in `ruby-upb.c`/`php-upb.c`.
3. Observe the output JSON contains the literal, unescaped `</script><script>alert(1)</script>` substring (verified by code inspection of the escape table at [6](#0-5) , which has no case for `<`/`>`).
4. Compare against the C++/Java/C# encoders on the identical input, which per [5](#0-4)  and [3](#0-2)  produce `\u003c/script\u003e...` instead — demonstrating the cross-language inconsistency and the missing HTML-context safety escaping in the upb backend.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

    // Used for escaping control chars in strings.
    private static $k_control_char_limit = 0x20;

    private static function jsonNiceEscape($c)
    {
      switch ($c) {
          case '"':  return "\\\"";
          case '\\': return "\\\\";
          case '/': return "\\/";
          case '\b': return "\\b";
          case '\f': return "\\f";
          case '\n': return "\\n";
          case '\r': return "\\r";
          case '\t': return "\\t";
          default:   return NULL;
      }
    }

    private static function isJsonEscaped($c)
    {
        // See RFC 4627.
        return $c < chr($k_control_char_limit) || $c === "\"" || $c === "\\";
    }
