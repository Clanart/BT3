### Title
Copilot conflict-resolution "continue merge" writes AI-generated content using a stale working-directory snapshot, silently overwriting conflicting content that changed after the check - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The reported Balancer bug is a **stale-state execution** bug: `onJoinPool` computes `amountLP` from pool reserves that can have moved between transaction submission and inclusion, and the protocol offers no way for the caller to bound acceptable execution conditions, so the caller's committed value can silently diverge from what they intended when they signed the transaction. The closest Desktop analog is `AppStore._applyCopilotConflictResolutions`, which decides whether it is safe to overwrite a conflicted file using a **single status snapshot taken at the start of the function**, then performs the actual `writeFile` after several `await` points, without re-checking the file's live state immediately before overwriting it — the same "decide-then-act-later-on-stale-data" shape as the LP mint calculation.

### Finding Description
When the user clicks "Continue Merge" in the Copilot conflicts dialog, `_applyCopilotConflictResolutions` is invoked: [1](#0-0) 

For each Copilot-proposed resolution, the function looks up the file's conflict status from a `state` object captured once at the top of the function call, and only overwrites the file if that snapshot shows no remaining unresolved conflict markers: [2](#0-1) 

The comment directly acknowledges the invariant being protected — "If the user resolved this file externally ... while the result dialog was open ... Overwriting it with Copilot's stored content would silently clobber their work" — but the guard only compares against `state.changesState.workingDirectory.files`, i.e. the last background status refresh, not the file's actual on-disk content evaluated immediately before the `writeFile` call. The loop also `await`s `resolveWithin` per file and performs the write only after several asynchronous steps, all using the same pre-fetched `state` object rather than re-querying git status right before the mutating write.

This mirrors the Cron/Balancer flaw precisely: a value is computed/validated against one snapshot of state (pool reserves / working-directory status) and then executed later against a potentially different real state (post-swap reserves / post-edit file contents), with no re-verification ("slippage check") at the moment of the state-mutating action.

### Impact Explanation
If the working-directory status cache is stale relative to disk at the moment `_applyCopilotConflictResolutions` runs (e.g., because the background status refresh has not yet completed, or the conflict was altered by another concurrent git operation triggered during the merge/rebase/cherry-pick flow attached to a remote the user just fetched from), Desktop will overwrite the file with the AI-generated `resolution.resolvedContent` even though the true current file state no longer matches what was used to decide "safe to overwrite." Because this write happens right before `git add`, the corrupted content becomes exactly what gets staged and committed — a silent corruption of what the user commits, without any user-visible confirmation of the final content actually written.

### Likelihood Explanation
This requires a specific timing window between the status snapshot capture and the `writeFile`/`git add` calls, and depends on background status refresh latency, which is not something Desktop's UI signals to the user. It does not require local/physical access, admin rights, or leaked credentials — only a merge/rebase/cherry-pick against attacker-influenced remote content that produces conflicts routed through the Copilot resolution flow. However, the window is narrow and the existing guard reduces (without eliminating) the practical likelihood, so this should be treated as a moderate-likelihood, state-consistency defect rather than a trivially reproducible one.

### Recommendation
Re-fetch and re-check the file's live conflict/status state immediately before each `writeFile` call in `_applyCopilotConflictResolutions`, rather than relying solely on the `state` object captured at function entry. This is the direct analog of the report's recommendation to let callers bound execution against the freshest state (slippage tolerance) instead of trusting a stale precondition check.

### Proof of Concept
1. Start a merge/rebase that produces file conflicts against a branch fetched from a remote.
2. Trigger Copilot conflict resolution; while the result dialog is open and before status refresh completes, modify the conflicted file externally so it appears (per a lagging status cache) as still-conflicted, then quickly resolve/save it manually.
3. Click "Continue Merge" before the app's cached `workingDirectory.files` status updates to reflect the manual resolution.
4. `_applyCopilotConflictResolutions` reads the stale cached status, treats the file as still conflicted, and overwrites the user's freshly resolved content with `resolution.resolvedContent`, then stages it via `git add` — corrupting the commit silently. [3](#0-2)
