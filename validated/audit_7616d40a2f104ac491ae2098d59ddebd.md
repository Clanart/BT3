## Title
GetResponse values are silently re-ordered relative to the requesting app's `keys` array, breaking the documented positional contract - (File: `modules/ismp/core/src/handlers/response.rs`)

### Summary
The ISMP response handler builds each `GetResponse.values` array from a `BTreeMap<Vec<u8>, Option<Vec<u8>>>` returned by `verify_state_proof`, iterating it in **lexicographic key order** rather than in the order the requesting application originally supplied in `GetRequest.keys`. The protocol's own documentation and shipped example applications explicitly promise that "values are provided in the same order as requested keys" and consume `response.values[i]` positionally without checking `values[i].key` against `keys[i]`.

### Finding Description
`handlers/response.rs::handle` constructs the response like this: [1](#0-0) 

`state_machine.verify_state_proof` returns a `BTreeMap<Vec<u8>, Option<Vec<u8>>>` on every implementation (EVM, Substrate-EVM, Tendermint-EVM, Substrate, Pharos): [2](#0-1) [3](#0-2) 

A `BTreeMap`'s `.into_iter()` always yields entries sorted by key bytes — it does **not** preserve insertion/request order. When an app supplies multiple keys (a documented, supported use case: "Reading Multiple Slots"), the resulting `values` array is silently reordered relative to `request.keys` if the raw key bytes don't happen to already sort ascending.

The exact same reordering happens on the Hyperbridge-chain path that builds `GetResponse`s destined for EVM chains via the state-coprocessor pallet, which is committed into the MMR and later proven to `HandlerV2.handleGetResponses` on EVM: [4](#0-3) 

The protocol's own documentation guarantees positional correspondence and even instructs integrators to rely on it without per-item key checks: [5](#0-4) [6](#0-5) 

The shipped reference implementations follow that guidance and index `values[i]` directly, and the "Reading Multiple Slots" example explicitly builds a multi-key `DispatchGet` with arbitrary caller-supplied slot ordering and no re-matching logic: [7](#0-6) [8](#0-7) 

No guard anywhere in `handle` (nor in `verify_state_proof` on any state machine) re-sorts `values` back into `request.keys` order, and no shipped `onGetResponse` implementation validates `values[i].key == request.keys[i]` before consuming `values[i].value`.

### Impact Explanation
This is a real, permissionless logic bug that breaks the "one value per requested key, in the order requested" invariant the protocol advertises. Any application built to the documented/expected pattern — including multi-slot price readers, oracle aggregators, or intent-settlement logic that fetches multiple remote storage values (e.g., reserve0/reserve1-style pairs, or multiple balances used to compute a payout) — will misattribute values to the wrong logical key whenever the raw key bytes for a request don't already sort in the caller's intended order. Because the mis-ordering is a function of the deterministic key bytes (not of any malicious relayer or prover action — the honest protocol code path itself does the resorting), a normal unprivileged caller triggering a multi-key GET can, deterministically, cause the destination `IsmpModule`/`IApp` to compute a wrong amount, wrong price, or wrong beneficiary decision from swapped storage values. This lands squarely in the "transaction manipulation / logic attack causing wrong beneficiary or amount" bucket the bounty targets, since it corrupts values consumed by on-chain settlement logic without requiring any protocol-security assumption to be broken.

### Likelihood Explanation
High for any app that (a) uses multi-key `GetRequest`s and (b) follows the documented/reference pattern of indexing `values[i]` positionally, which is exactly what the SDK ships as example code (`HyperGet.sol`, "Reading Multiple Slots"). No attacker privilege is required — an ordinary user dispatching a multi-key GET (or an app doing so on a user's behalf) is sufficient to trigger the mismatch; the bug is deterministic based on the raw key byte ordering versus the caller's intended semantic ordering.

### Recommendation
In `handlers/response.rs::handle` (and the analogous construction in `modules/pallets/state-coprocessor/src/impls.rs`), rebuild `values` by iterating the *original* `request.keys` vector and looking up each key in the returned map, instead of iterating the map directly:
```rust
let value_map = state_machine.verify_state_proof(host, keys.clone(), state.state_root, &proof)?;
let values: Vec<StorageValue> = keys
    .into_iter()
    .map(|key| {
        let value = value_map.get(&key).cloned().flatten();
        StorageValue { key, value }
    })
    .collect();
```
This restores the order guarantee that the documentation promises and that reference `IApp` implementations rely on.

### Proof of Concept
1. An app dispatches a `GetRequest` with `keys = [key_B, key_A]` where `key_B`'s raw bytes are lexicographically greater than `key_A`'s (e.g., via the documented "Reading Multiple Slots" pattern, `MultipleSlotReader.readMultipleSlots(contract, [slotB, slotA], ...)`).
2. On the destination, `verify_state_proof` internally builds/returns a `BTreeMap` keyed by raw bytes, so it necessarily produces `{key_A: value_A, key_B: value_B}` in that map's iteration order (sorted ascending), regardless of the caller's `[key_B, key_A]` request order.
3. `handlers/response.rs` (or `state-coprocessor/impls.rs` for the EVM path) does `.into_iter().map(|(key,value)| StorageValue{key,value}).collect()`, producing `values = [StorageValue{key_A, value_A}, StorageValue{key_B, value_B}]`.
4. The source-chain app's `onGetResponse` callback (following the documented and reference pattern) reads `values[0]` expecting it to correspond to `keys[0] = key_B`, but it actually receives `value_A`.
5. If the app uses `values[0]`/`values[1]` to compute a payout, price ratio, or settlement amount (e.g., reserve0/reserve1 style calculation), the swapped values yield an incorrect result — deterministically reproducible by any caller who orders their `keys` array non-ascending, with no relayer, prover, or admin collusion required.

	fn verify_state_proof(
		&self,
		_host: &dyn IsmpHost,
		keys: Vec<Vec<u8>>,
		root: H256,
		proof: &Proof,
	) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
		let ismp_host_address = EvmHosts::<T>::get(&proof.height.id.state_id)
			.ok_or(SubstrateEvmError::IsmpContractNotFound)?;

		let proof: SubstrateEvmProof =
			Decode::decode(&mut &proof.proof[..]).map_err(SubstrateEvmError::ProofDecodeError)?;

		let state_root = root;

		let keys_len = keys.len();
		let mut contract_keys: BTreeMap<H160, Vec<Vec<u8>>> = BTreeMap::new();
		for key in keys {
			let address = if key.len() == 52 {
				H160::from_slice(&key[..20])
			} else if key.len() == 32 {
				ismp_host_address
			} else {
				return Err(SubstrateEvmError::InvalidKeyLength(key.len()).into());
			};
			contract_keys.entry(address).or_default().push(key);
		}

		let mut result_map = BTreeMap::new();

		for (address, keys) in contract_keys {
			let contract_info_key = contract_info_key(address);
			let trie_id = fetch_trie_id_from_main_proof::<H>(
				&proof.main_proof,
				state_root,
				&contract_info_key,
			)?;

			let child_root =
				fetch_child_root_from_main_proof::<H>(&proof.main_proof, state_root, &trie_id)?;

			let storage_proof = proof
				.storage_proof
				.get(address.as_bytes())
				.ok_or(SubstrateEvmError::StorageProofMissing(address.as_bytes().to_vec()))?;

			let storage_keys: Vec<Vec<u8>> = keys
				.iter()
				.map(|k| {
					let slot = if k.len() == 52 { &k[20..] } else { &k[..] };
					blake2_256(slot).to_vec()
				})
				.collect();

			let values = verify_child_trie_values::<H>(child_root, storage_proof, storage_keys)?;

			for (key, value) in keys.into_iter().zip(values.into_iter()) {
				result_map.insert(key, value);
			}
		}

		if result_map.len() != keys_len {
			return Err(SubstrateEvmError::MismatchedValuesAndKeys.into());
		}

		Ok(result_map)
	}

	fn verify_state_proof(
		&self,
		_host: &dyn IsmpHost,
		keys: Vec<Vec<u8>>,
		root: H256,
		proof: &Proof,
	) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
		// The trie root is supplied by the caller, bound to the calling context, so a relayer
		// cannot steer verification at the wrong trie.
		let StateMachineProof { hasher, storage_proof } =
			codec::Decode::decode(&mut &*proof.proof)
				.map_err(SubstrateStateMachineError::ProofDecodeError)?;
		let data = match hasher {
			HashAlgorithm::Keccak => {
				let db = StorageProof::new(storage_proof).into_memory_db::<Keccak256>();
				let trie = TrieDBBuilder::<LayoutV0<Keccak256>>::new(&db, &root).build();
				keys.into_iter()
					.map(|key| {
						let value = trie
							.get(&key)
							.map_err(|e| SubstrateStateMachineError::TrieError(format!("{e:?}")))?;
						Ok::<_, SubstrateStateMachineError>((key, value))
					})
					.collect::<Result<BTreeMap<_, _>, _>>()?
			},
			HashAlgorithm::Blake2 => {
				let db = StorageProof::new(storage_proof).into_memory_db::<BlakeTwo256>();
				let trie = TrieDBBuilder::<LayoutV0<BlakeTwo256>>::new(&db, &root).build();
				keys.into_iter()
					.map(|key| {
						let value = trie
							.get(&key)
							.map_err(|e| SubstrateStateMachineError::TrieError(format!("{e:?}")))?;
						Ok::<_, SubstrateStateMachineError>((key, value))
					})
					.collect::<Result<BTreeMap<_, _>, _>>()?
			},
		};

		Ok(data)
	}

function readMultipleSlots(
    address contract_,
    bytes32[] memory slots,
    uint256 height,
    bytes memory dest
) public payable returns (bytes32) {
    // Construct keys for multiple slots
    bytes[] memory keys = new bytes[](slots.length);
    for (uint256 i = 0; i < slots.length; i++) {
        keys[i] = bytes.concat(bytes20(contract_), slots[i]);
    }
    
    DispatchGet memory getRequest = DispatchGet({
        dest: dest,
        height: height,
        keys: keys,
        timeout: 0,
        fee: msg.value,
        context: abi.encode(contract_, slots)
    });
    
    return IDispatcher(_host).dispatch{value: msg.value}(getRequest);
}
