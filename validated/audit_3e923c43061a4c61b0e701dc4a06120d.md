## Finding: Desktop silently rewrites a repository's git remote URL from an untrusted GitHub API response

### Title
Desktop silently overwrites the local git remote URL based on an untrusted GitHub API `clone_url` field, redirecting future pushes/fetches - (`File: app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Sherlock report is a "stale mapping" bug class: a value (`userCode`) that should be kept in sync with a related value (`codeOwner`) is not updated when the owning relationship changes. The closest security-relevant analog in this GitHub Desktop codebase is the inverse failure mode of the same class: a *local, trusted* value (the git `remote.origin.url` git-config entry) is automatically overwritten based on a value taken from a *remote, less-trusted* source (the GitHub API's `clone_url` field for the repo's associated `GitHubRepository`) with insufficient verification that the update is legitimate.

### Finding Description
`updateRemoteUrl` in [1](#0-0)  compares the locally configured remote URL against `apiRepo.clone_url` returned from the GitHub API and, if the protocol matches and the previously known clone URL matched the current remote ("the user hasn't manually changed it"), calls `gitStore.setRemoteURL(...)` to silently rewrite the remote — with no user confirmation: [2](#0-1) 

This is invoked from `repositoryWithRefreshedGitHubRepository`, which runs during routine repository-refresh flows (e.g. `withRefreshedGitHubRepository`, used before push/pull operations when there's no cached account association): [3](#0-2)  and [4](#0-3) 

The repository lookup itself, `api.fetchRepository(owner, name)`, is driven by `owner`/`name` strings resolved via `matchGitHubRepository`, which only checks that the remote's hostname matches a signed-in account's endpoint — it performs no verification that the *content* of the API response (particularly `clone_url`) is the same repository the user originally cloned: [5](#0-4) 

The `git-store.ts` `setRemoteURL` method applies the change directly via `git remote set-url` with no dialog, confirmation prompt, or diff shown to the user: [6](#0-5)  and [7](#0-6) 

The only guards in place are:
1. `urlsMatch` must be false (i.e., the API-reported URL differs from the current remote).
2. `remoteUrlUnchanged` — the *previously cached* `GitHubRepository.cloneURL` must equal the current remote (so the user hasn't manually edited it).
3. `protocolsMatch` — old and new URL must use the same protocol scheme.

None of these checks validate that the new `clone_url` genuinely refers to the same underlying repository (e.g., by repository ID) — they only compare URL string structure. A GitHub Enterprise Server instance, a compromised/malicious API endpoint, or a man-in-the-middle on a non-TLS-pinned connection that returns a crafted `apiRepo.clone_url` (same protocol, different host/owner/name) will cause Desktop to silently repoint the user's `origin` (or upstream) remote.

### Impact Explanation
Once the remote URL is silently repointed, all subsequent `git push`/`git fetch` operations target the attacker-controlled destination without any user awareness. This matches the "silent corruption of what the user commits or pushes" impact class: a user believing they are pushing to their legitimate repository would instead push commits (potentially including proprietary source, secrets, or credentials embedded via git credential helpers negotiated for the new host) to an attacker-controlled server. If the new host is used for HTTPS auth, this can also cause the credential-helper flow to present the account's stored token or credentials to the attacker's host.

### Likelihood Explanation
This path only triggers under the `remoteUrlUnchanged` condition, i.e. when the user has not manually retargeted the remote — meaning it is generally exercised passively during normal background refresh. It requires an attacker who can influence the API response for the repository referenced by an already-signed-in account's endpoint (e.g., a rogue/compromised GitHub Enterprise Server, or a network position capable of tampering with API responses for that endpoint). It does not require the user to click any link or take any unusual action, since it fires from routine repository-refresh calls performed automatically by the app.

### Recommendation
- Do not auto-rewrite `remote.origin.url` (or upstream) purely from API `clone_url` string comparison; require the change to be explicitly confirmed by the user, or restrict automatic updates to cases verified via a stable repository ID rather than string URL matching.
- When accepting `clone_url`/`html_url` from the API to drive local git configuration changes, validate that the underlying repository ID (`apiRepo.id`) matches the previously stored `GitHubRepository.dbID`/API id, not just hostname/owner/name text.
- Surface the remote change to the user before applying it (similar to other destructive/consequential git operations in Desktop).

### Proof of Concept
1. User has an account signed into a GitHub Enterprise Server endpoint `https://ghe.example.com`, with a local repository whose `origin` remote is `https://ghe.example.com/acme/app.git`, matching the cached `GitHubRepository.cloneURL`.
2. Attacker gains the ability to influence API responses for that endpoint (e.g. compromised/malicious GHES instance, or a MITM position for that host) and, when Desktop calls `api.fetchRepository('acme', 'app')` during a routine refresh (`repositoryWithRefreshedGitHubRepository`), returns a repository object with `clone_url: 'https://ghe.example.com/attacker/app.git'` (same host/protocol, different owner).
3. `updateRemoteUrl` ( [8](#0-7) ) finds `urlsMatch === false`, `remoteUrlUnchanged === true` (matches cached clone URL), and `protocolsMatch === true`, so it calls `gitStore.setRemoteURL('origin', 'https://ghe.example.com/attacker/app.git')`.
4. The user's next `git push` sends commits to `attacker/app.git` with no dialog or warning shown, confirmed by the existing test asserting the URL is silently changed: [9](#0-8) .

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export async function setRemoteURL(
  repository: Repository,
