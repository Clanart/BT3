### Title
Deep-link `branch` parameter bypasses ref validation and enables git argv/option injection via leading-dash ref names - (File: app/src/lib/sanitize-ref-name.ts, app/src/lib/git/checkout.ts)

### Summary
`testForInvalidChars`, used at `app/src/lib/parse-app-url.ts:114` to gate the `branch` query parameter of an `x-github-client://openrepo` deep link, only rejects control characters, spaces, `~^:?*[\|"<>`, `@{`, consecutive/leading/trailing dots, `.lock` suffix, and trailing `/`. It does not reject values beginning with `-`. [1](#0-0) 

Compare this to `sanitizedRefName` (used elsewhere to *sanitize* a proposed branch name, not to validate a deep-link one), which explicitly strips leading `-`/`+` characters after applying the same regex: [2](#0-1) 

`testForInvalidChars` has no equivalent leading-dash stripping/rejection, so a `branch` value such as `--upload-pack=/tmp/evil.sh` passes validation in `parseAppURL` unchanged: [3](#0-2) 

This value flows to `Dispatcher.openBranchNameFromUrl`, which calls `checkoutLocalBranch(repository, branchName)` with the raw, attacker-controlled string: [4](#0-3) 

Separately, `getBranchCheckoutArgs` in `app/src/lib/git/checkout.ts` builds the `git checkout` argv by placing the branch name *before* the `--` end-of-options marker, not after it: [5](#0-4) 

```
const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]
// => ['checkout', branch.name, '--']   (for a local branch)
await git(args, repository.path, 'checkoutBranch', opts)
```

For the `--` terminator to protect against option-like ref names, it must precede the ref (`git checkout -- <ref>`), not follow it. As implemented, `git checkout <ref> --` lets git's argument parser interpret a leading-dash `<ref>` as an option before it ever reaches the trailing `--`.

### Finding Description
The `branch` parameter of an `x-github-client://openrepo?...&branch=...` deep link is validated only by `testForInvalidChars`, which does not reject leading-dash values. This value is passed as-is into the checkout pipeline. The `checkout` argv builder appends `--` after the branch name rather than before it, so the dash-prefixed string is positionally eligible to be parsed as a `git checkout` option rather than a ref/pathspec.

### Impact Explanation
If git's `checkout` subcommand accepts (or misparses) an option that can be abused this way, this could allow an attacker who gets a victim to click a crafted `x-github-client://openrepo` link to influence the arguments passed to a locally spawned `git` process, potentially resulting in unexpected file writes/reads or process behavior outside normal repository scope — all without prior local access, matching the "unprivileged, clicked deep link" scope of this program.

### Likelihood Explanation
Exploitability is dependent on unverified facts I could not fully confirm in this pass:
- Whether `git checkout` actually accepts an `--upload-pack=...`-style option (that flag is normally associated with `fetch`/`clone`/`ls-remote`, not `checkout`), or whether some other checkout-supported option (e.g. `--to`, `-b`, `--orphan`, `--conflict=`) could be substituted for a similar effect.
- The exact body of the `checkoutLocalBranch` dispatcher method that turns the raw `branchName` string into the `Branch` object consumed by `checkoutBranch` — I could only confirm the call site at `app/src/ui/dispatcher/dispatcher.ts:1993`, not its full implementation, so I cannot state with certainty whether it performs any additional validation/lookup (e.g., requiring the branch to already exist from a fetched remote) before invoking `checkoutBranch`.

Because of these open questions, I can confirm the validation gap and the argv-ordering weakness as facts in the code, but cannot fully confirm end-to-end weaponizability into code execution/file write without further testing of git's actual behavior for `checkout` with these flags and without seeing the complete `checkoutLocalBranch` implementation.

### Recommendation
- Update `testForInvalidChars` (or add a companion check used specifically for deep-link input) to reject ref names beginning with `-`, mirroring the stripping logic already present in `sanitizedRefName`.
- Fix `getBranchCheckoutArgs` in `app/src/lib/git/checkout.ts` to place `--` immediately before the branch name/pathspec arguments rather than after them, so it functions as an actual end-of-options guard: `['checkout', '--', branch.name]` (adjusting for the `-b` remote-tracking case accordingly).
