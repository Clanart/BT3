### Title
Panic on missing `enc_keys` entry in `Decryption::decrypt_with_proof` causes DoS when victim blames a faulty share sender - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` without checking membership. `enc_keys` is populated by `Decryption::register`, which is only invoked for *other* participants' `EncryptionKeyMessage`s during `verify_r1` — the local participant `params.i()` is never registered. When an honest participant calls `BlameMachine::blame`/`blame_internal` with `recipient == params.i()` (the natural case: "participant X sent me an invalid share"), the HashMap index panics, aborting the process instead of returning the faulty `Participant`. A malicious DKG participant can deterministically trigger this by sending the victim an invalid `EncryptedMessage<SecretShare>`, mirroring CVE-2025-52292's crafted-input → crash → DoS class.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `decrypt_with_proof` verifies a DLEq proof binding the message key to the decryptor's registered public encryption key:

```rust
&[self.enc_keys[&decryptor], *proof.key],
```

`enc_keys` is a `HashMap<Participant, C::G>`; indexing a `HashMap` with a missing key panics. Registration happens in `Decryption::register` (encryption.rs:351-362), which is only called from `SecretShareMachine::verify_r1` (lib.rs:315) for entries in `commitment_msgs` — a map that `validate_map` guarantees excludes the local participant. `AdditionalBlameMachine::new` similarly only registers the `n` commitment senders. There is no path that inserts `params.i()` (for `BlameMachine`) or any arbitrary `recipient` into `enc_keys`.

The blame path in `BlameMachine::blame_internal` (lib.rs:575-609) passes the caller-supplied `recipient` straight through to `decrypt_with_proof`. When `recipient` is the local participant (the expected usage for "I received a bad share") or any participant index not present in `enc_keys`, the lookup panics.

### Impact Explanation
An unprivileged DKG participant who sends a malformed/invalid `EncryptedMessage<SecretShare>` to a victim causes the victim's node to panic (process abort / thread unwind) when it attempts to adjudicate blame, rather than cleanly identifying the malicious sender. This converts a gracefully handled protocol fault into a crash, preventing the DKG from completing and preventing blame attribution — a remotely triggerable denial of service via attacker-supplied bytes fed into `EncryptedMessage::read` → `calculate_share` → `blame`.

### Likelihood Explanation
The trigger is fully deterministic: it does not depend on rare values, only on `decrypt_with_proof` being reached with `Some(proof)` and a `decryptor` absent from `enc_keys`. Sending any invalid share (which `calculate_share` already surfaces as `InvalidShare { participant, blame }`, prompting blame evaluation) suffices. The only mitigation is the integrator never invoking `blame` with `recipient == i`, which contradicts the API's documented purpose.

### Recommendation
Replace `self.enc_keys[&decryptor]` with a `get` + error return (e.g., `DecryptionError::InvalidProof`), and register the local participant's own `enc_pub_key` in `Decryption::new`/`Encryption::new` so self-recipient blame resolves correctly. Also consider a `get` on `self.commitments[&sender]` in `blame_internal` (lib.rs:599), which has the same unchecked-indexing pattern.

### Proof of Concept
1. Run PedPoP with `n >= 2`, victim participant `i`.
2. Malicious participant `l` completes `generate_secret_shares` but sends victim `i` an `EncryptedMessage<SecretShare>` whose decrypted share fails verification (or any fault prompting blame).
3. Victim calls `calculate_share` → gets `PedPoPError::InvalidShare` and later calls `BlameMachine::blame(sender=l, recipient=i, msg, proof)` (or `AdditionalBlameMachine::blame` with a `recipient` not in `enc_keys`).
4. `blame_internal` → `decrypt_with_proof` → `self.enc_keys[&i]` panics (`HashMap` index on absent key), crashing instead of returning `l` as faulty. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    recipient: Participant,

      Err(DecryptionError::InvalidSignature) => return sender,

      Err(DecryptionError::InvalidProof) => return recipient,
