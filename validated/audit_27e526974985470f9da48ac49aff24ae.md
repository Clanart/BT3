### Title
Attacker-controlled `Participant` keys in the promotion proofs map cause a panic (denial of service) in `GeneratorPromotion::complete` — (File: crypto/dkg/promote/src/lib.rs)

### Summary
Analogous to prototype pollution — where an attacker supplies keys of their choosing that are inserted into/looked up from an object — `GeneratorPromotion::complete` consumes a `HashMap<Participant, GeneratorProof<C1>>` whose keys are fully attacker-controlled. The validation only rejects keys `> n` and checks `proofs.len() == n - 1`; it never rejects the victim's own participant index `params.i()`. A key equal to `params.i()` therefore "pollutes" the map: it counts toward the required `n - 1` entries while being unusable, because the completion loop skips `i == params.i()` and then unconditionally `unwrap()`s `proofs.get(&i)` for every other participant.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` performs only two checks on the untrusted `proofs` map:

- `proofs.len() != params.n() - 1` is rejected (line 125), and
- each key must satisfy `u16::from(i) <= params.n()` (lines 132-136).

Unlike `frost::validate_map` (`crypto/frost/src/lib.rs:50-73`), there is no check that the map does **not** contain the local participant's own index, and no check that every required participant `1..=n` (minus `params.i()`) is present. The loop then does:

```rust
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();   // panics if participant i omitted
```

A malicious peer (or a network adversary relaying promotion messages) can submit a proofs map of exactly `n - 1` entries that contains a spurious entry keyed at `params.i()` — a key the honest protocol would never produce for us — while omitting some legitimate participant `j`. Both validation checks pass, then `proofs.get(&j).unwrap()` panics, aborting key promotion.

Contrast with `PedPoP`'s `SecretShareMachine::verify_r1` and `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:305-309`, `:468-472`), which correctly call `validate_map` to enforce that peer-supplied maps contain exactly the expected participants and never our own index. `promote` re-implements this validation by hand and gets it wrong.

### Impact Explanation
Denial of service: an unprivileged participant (or anyone able to deliver/relay `GeneratorProof` messages to a victim running `GeneratorPromotion::complete`) can deterministically panic the victim's promotion, preventing migration of threshold keys to the new generator. Since the panic occurs after proof verification begins, it cannot be distinguished from an honest failure path without code changes; retrying with the same malicious input panics again. This mirrors the DoS impact claimed in CVE-2024-38983, mapped onto Serai's real shape (attacker-named map keys with missing reserved-key validation). No secret material is leaked and no invalid `ThresholdKeys<C2>` is produced — the code aborts rather than constructing bad keys — so the impact is availability only (Medium).

### Likelihood Explanation
Reachable with public inputs: `complete(&self, proofs: &HashMap<Participant, GeneratorProof<C1>>)` takes the proof map directly, and `GeneratorProof::read` (lines 72-77) deserializes attacker bytes. Any peer who can send a promotion proof keyed as the victim's own `Participant` index (plus `n - 2` valid-looking entries, which can even be garbage since the panic precedes most `verify` calls) triggers it. Requirements: the victim runs generator promotion and accepts a proof map containing a foreign entry under `params.i()`.

### Recommendation
Replace the manual validation in `GeneratorPromotion::complete` with `frost::validate_map(&proofs, &params.all_participant_indexes().collect::<Vec<_>>(), params.i())` (or equivalent logic), which rejects maps containing the caller's own index (`DuplicatedParticipant`) and maps missing any required participant (`MissingParticipant`). Alternatively, explicitly error on `proofs.contains_key(&params.i())` and replace `proofs.get(&i).unwrap()` with a checked lookup returning `PromotionError::IncorrectAmountOfParticipants`/`InvalidParticipant`.

### Proof of Concept
```rust
// Victim has ThresholdParams with n = 3, i = Participant(2).
// Attacker supplies a proofs map of exactly n - 1 = 2 entries:
//   key = Participant(2)  // the victim's own index — invalid, never sent honestly
//   key = Participant(1)  // any entry; contents never reach verification for key 2
// Participant(3)'s proof is omitted.

let mut proofs = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof_1);
proofs.insert(Participant::new(2).unwrap(), attacker_proof_2); // victim's own index

// Validation passes: proofs.len() == n - 1 == 2, all keys <= n == 3.
// Loop: i = 1 -> verify proof_1 (may pass); i = 2 -> skipped (i == params.i());
//       i = 3 -> proofs.get(&Participant(3)).unwrap() -> PANIC
promotion.complete(&proofs);
```

Root cause confirmed at `crypto/dkg/promote/src/lib.rs:125-146`: key validation omits the `params.i()` exclusion and the subsequent `proofs.get(&i).unwrap()` assumes full coverage that the length check does not guarantee.

Caveat: I did not verify whether a higher-level caller pre-filters the proofs map; the finding stands on `complete`'s own contract as a public API accepting untrusted per-participant data, per the reachable-API criteria.
