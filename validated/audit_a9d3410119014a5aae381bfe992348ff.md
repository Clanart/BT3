### Title
Unsigned `MaxGasPrice` field in `auction_submitBid` allows mass-assignment-style tampering of KIP-249 bids without invalidating the Searcher/Auctioneer signatures - ([File: kaiax/auction/impl/api.go])

### Summary
The `auction_submitBid` RPC endpoint accepts a `BidInput` JSON object and maps it directly into the internal `auction.BidData` struct via `ToBid()` with no field-level whitelist tied to what is actually covered by the cryptographic signatures. In particular, the `MaxGasPrice` field is copied from client input into `BidData.MaxGasPrice` unconditionally, but when the bid pool validates signatures under the (default/legacy) `AuctionVersionV2` EIP-712 typehash, `MaxGasPrice` is not part of the signed struct at all. This is the same root-cause pattern as the FlowiseAI advisory: attacker/relay-controlled fields are merged into a server-trusted object while validation only covers a subset of fields, letting the value diverge from what was actually authorized (signed) by the responsible party (the searcher/auctioneer).

### Finding Description
`BidInput` in `kaiax/auction/impl/api.go` is decoded straight from the RPC caller's JSON: [1](#0-0) 

`ToBid()` merges every field, including `MaxGasPrice`, into the `auction.Bid`/`BidData` that is fed into `bidPool.AddBid`: [2](#0-1) 

Signature validation (`bp.validateBidSigs` → `Bid.ValidateSearcherSig`) recomputes the EIP-712 digest via `GetHashTypedData`, and the digest content depends on `auctionEntryPointVersion`: [3](#0-2) 

The V2 typehash (`auctionType`) and its `EncodeData()` implementation deliberately omit `MaxGasPrice` from the signed payload — only the V3 typehash (`auctionTypeV3`/`bidV3.EncodeData`) commits to it: [4](#0-3) [5](#0-4) [6](#0-5) 

Because `ValidateSearcherSig` only checks that `recoveredSender == b.Sender` against a digest that (under V2) excludes `MaxGasPrice`, a value for `MaxGasPrice` supplied via the RPC call is accepted and persisted into the bid object without being authenticated by the searcher's signature at all in the V2 code path: [7](#0-6) 

The bid-pool admission checks (`validateBid`) never independently re-verify `MaxGasPrice` against anything — they check sender/winner conflicts, block-number window, positive bid amount, data size, call-gas-limit, and signatures, but not `MaxGasPrice` consistency with the signed struct for V2 bids: [8](#0-7) 

The unauthenticated `MaxGasPrice` then flows unchanged into the on-chain calldata builder `EncodeAuctionCallData`, which — for V3-labeled entry points — packs `bid.MaxGasPrice` directly into the `AuctionTx` struct sent on-chain: [9](#0-8) 

Because the RPC-facing struct is shared for both versions and the caller controls both `BidInput.MaxGasPrice` and the mapping into `BidData`, an unprivileged caller of the (non-public, but reachable) `auction_submitBid` API can submit a bid whose `MaxGasPrice` differs from what the searcher actually signed (when the network is on the V2 entry point, or if any client mistakenly resolves the wrong version), while the signature verification (`ValidateSearcherSig`/`ValidateAuctioneerSig`) still passes.

### Impact Explanation
`MaxGasPrice` is meant to cap the gas price the searcher/auctioneer authorized for the bid execution (per KIP-249 v3). If it can be set/mutated by the RPC caller independent of what the searcher actually signed (in the V2 signature scope), a relayer or malicious intermediary submitting `auction_submitBid` on behalf of a searcher could inflate or otherwise alter the effective gas-price ceiling used when the winning bid transaction is built and executed on-chain via `GetBidTxGenerator`/`EncodeAuctionCallData`, without invalidating the searcher's or auctioneer's signature. This breaks the integrity guarantee that "the signed bid fields are what gets executed," analogous to the FlowiseAI issue where fields outside the intended write-scope were silently accepted and persisted despite lacking authorization, resulting in unauthorized value/behavior mutation of a resource (the bid) that a different party (the node) then trusts and executes with system-contract-mediated fund movement (bid deposit / gas payment).

### Likelihood Explanation
The `auction_submitBid` API is invoked over JSON-RPC by whoever controls a `SearcherSig`/`AuctioneerSig` pair (or a relay operating between them); it does not require validator/node compromise, only submission of a crafted RPC payload with a `MaxGasPrice` value that differs from the value embedded in the actual EIP-712 payload the searcher signed under V2. Because the vulnerability requires the specific combination of the V2 (non-`MaxGasPrice`-covered) typehash being in use while a `MaxGasPrice` value is still populated and forwarded downstream, the exploitability depends on operational conditions (which auction contract version is active) that I could not fully confirm from static code alone — I did not find code that positively forbids setting `MaxGasPrice` while `auctionEntryPointVersion == AuctionVersionV2`, but I also did not find a live execution path where a V2-signed bid with a populated `MaxGasPrice` produces an observably different on-chain outcome, since `EncodeAuctionCallData` gates `MaxGasPrice` packing behind `version == AuctionVersionV3`.

### Recommendation
Enforce a whitelist in `ToBid()`/`BidInput` that zeroes/rejects `MaxGasPrice` whenever the active `auctionEntryPointVersion` is not `AuctionVersionV3`, and add an explicit check in `validateBid`/`validateBidSigs` that a non-nil `MaxGasPrice` is rejected unless the corresponding version's typehash (which commits to it) was used to produce a valid `SearcherSig`. More generally, avoid a direct field-by-field copy from client-supplied RPC structs into internally trusted structs without an explicit list of "signature-covered" vs. "server-derived" fields, mirroring the same DTO-whitelisting fix recommended for the FlowiseAI chatflow-update endpoint.

### Proof of Concept
1. Assume the current on-chain `AuctionEntryPoint` reports `AUCTION_VERSION() == "0.0.1"` (V2), so `bp.auctionEntryPointVersion == auction.AuctionVersionV2`.
2. A searcher signs a valid V2 EIP-712 bid (fields per `auctionType`, which excludes `maxGasPrice`) producing `SearcherSig`.
3. An intermediary (or the searcher's own faulty client) submits `auction_submitBid` with the same `sender/to/nonce/bid/callGasLimit/data/searcherSig/auctioneerSig` but adds an arbitrary `maxGasPrice` value not agreed to when the bid was signed.
4. `ToBid()` copies this attacker-chosen `MaxGasPrice` into `BidData.MaxGasPrice`.
5. `ValidateSearcherSig` recomputes the V2 digest (`GetHashTypedData(..., AuctionVersionV2)`), which does not include `MaxGasPrice` in `EncodeData()`, so the signature still validates successfully despite the tampered field.
6. The bid, containing the unauthenticated `MaxGasPrice`, is accepted into the bid pool (`AddBid`) and stored for later inclusion via `GetBidTxGenerator`, demonstrating that a value never actually endorsed by the searcher's signature was accepted and persisted by the node — mirroring the FlowiseAI pattern of accepting/persisting server- or signature-controlled fields supplied by an unauthorized party.

// GetHashTypedData returns the EIP-712 digest for the bid.
// version must match the on-chain AUCTION_VERSION of the entry-point contract
// the bid targets; "0.0.2" selects the v3.0 struct typehash (with maxGasPrice),
// any other value falls back to the v2.1 typehash.
func (b *Bid) GetHashTypedData(chainId *big.Int, verifyingContract common.Address, version string) []byte {
	if chainId == nil {
		return nil
	}

	domain := EIP712Domain{
		EIP712DomainTypeHash: eip712TypeHash,
		NameHash:             auctionNameHash,
		VersionHash:          crypto.Keccak256Hash([]byte(version)),
		ChainId:              chainId,
		VerifyingContract:    verifyingContract,
	}

	domainSeparator := EncodeEIP712(domain)

	var structHash []byte
	if version == AuctionVersionV3 {
		structHash = EncodeEIP712(bidV3{b})
	} else if version == AuctionVersionV2 {
		structHash = EncodeEIP712(b)
	} else {
		// Unknown version: default to v2.1 typehash.
		structHash = EncodeEIP712(b)
	}

	return crypto.Keccak256([]byte{0x19, 0x01}, domainSeparator, structHash)
}

func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

func (bp *BidPool) validateBid(bid *auction.Bid) error {
	blockNumber := bid.BlockNumber

	bp.bidMu.RLock()

	// Check if the auction tx is already in the pool.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		bp.bidMu.RUnlock()
		return auction.ErrBidAlreadyExists
	}

	// 1. The `bid.Sender` must not be in the winner list of the same block number if the new bid isn't equal to the previous bid.
	if bp.senderHasDifferentWinner(bid) {
		bp.bidMu.RUnlock()
		return auction.ErrBidSenderExists
	}
	bp.bidMu.RUnlock()

	curBlock := bp.Chain.CurrentBlock()
	if curBlock == nil {
		return auction.ErrBlockNotFound
	}

	// 2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
	curNum := curBlock.NumberU64()
	if blockNumber <= curNum || blockNumber > curNum+allowFutureBlock {
		return auction.ErrInvalidBlockNumber
	}

	// 3. The `bid.Bid` must be greater than 0.
	if bid.Bid.Sign() <= 0 {
		return auction.ErrZeroBid
	}

	// 4. The data size must be less than the maximum limit.
	if uint64(len(bid.Data)) > BidTxMaxDataSize {
		return auction.ErrExceedMaxDataSize
	}

	// 5. The gas limit must be less than the maximum limit.
	if bid.CallGasLimit > BidTxMaxCallGasLimit {
		return auction.ErrExceedMaxCallGasLimit
	}

	// 6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.
	if err := bp.validateBidSigs(bid); err != nil {
		return err
	}

	return nil
}
