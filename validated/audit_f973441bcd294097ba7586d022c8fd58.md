### Title
Deterministically reused FROST nonces across distinct signing sets/messages in `DkgConfirmer` allow secret key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to a lender committing the borrower's collateral without consent, an unprivileged participant can cause a validator's already-published nonce commitment to be "paid" into additional signing sessions it never intended to fund. `SigningProtocol::preprocess_internal` caches a single preprocess seed per `context = (b"DkgConfirmer", attempt)` and `share_internal` re-derives the same nonces from that cache on every call, signing whatever `msg`/`preprocesses` the caller supplies. Because `Preprocess` carries no session/attempt binding (the `rho` transcript binds only `group_key`, `hash_msg(msg)`, and the preprocesses challenge), supplying a different signer set or a different `key_pair` under the same attempt produces a second signature share over the same nonces — classic FROST nonce reuse enabling third-party recovery of the victim's secret share.

### Finding Description
- `SigningProtocol::preprocess_internal` stores an (XOR-"encrypted") `CachedPreprocess` seed keyed only by `self.context` (`coordinator/src/tributary/signing_protocol.rs:123-145`). Every subsequent call for the same context returns the identical seed, so `from_cache` → `seeded_preprocess` regenerates identical nonces and commitments (`crypto/frost/src/sign.rs:121-144,268-274`).
- `DkgConfirmer` fixes `context = (b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:274-277`) but `share`/`share_internal` accept a caller-supplied `preprocesses` map and `key_pair`, and the signed `msg` is `set_keys_message(set, removed, key_pair)` (`signing_protocol.rs:288-301`). Peer-supplied preprocess bytes enter via `read_preprocess` (`signing_protocol.rs:160-168`).
- The FROST binding transcript commits to `group_key`, `hash_msg(msg)`, and the preprocessed-commitments challenge — nothing binds the session/attempt/context to the preprocess itself (`crypto/frost/src/sign.rs:361-379`). Hence any variation in the included signer set (different `preprocesses` keys → different `included` → different `rho` binding factors and challenge `c`) or in `key_pair` (different `msg`) yields a *different* challenge while the victim's nonces `d, e` are unchanged.

### Impact Explanation
Two shares `s₁ = d + ρ₁e + λkc₁` and `s₂ = d + ρ₂e + λkc₂` over the same nonces with known `ρ`, `c`, and public commitment to `k` allow recovery of the victim's secret key share `k` (the exact failure the `CachedPreprocess` docs warn of: "Reusing preprocesses would enable a third-party to recover your private key share", `spec/cryptography/FROST.md:51-55`). Recovery of `t` shares — or even one — degrades/breaks the MuSig threshold over validator set keys (`dkg_musig::musig`, `signing_protocol.rs:118-121`).

### Likelihood Explanation
Any DKG participant can publish arbitrary preprocess bytes and can cause `share`/`complete` to be evaluated multiple times per attempt — e.g., by emitting preprocesses for different claimed signer sets, or when more than one `key_pair`/share set circulates for the same attempt. Each evaluation regenerates identical victim nonces while the challenge varies with the signer set or `key_pair`. This is reachable purely through public preprocess/share messages fed to `read_preprocess`/`sign`; no key material or privileged role is required. Caveat: exploitation requires the victim's `share` path to be invoked more than once per attempt with a differing challenge; the message-driven dispatch in `handle.rs` makes `share`/`complete` re-callable, though I did not fully trace every guard limiting distinct `key_pair`s per attempt.

### Recommendation
Bind the cached preprocess seed to everything that can vary in a session: key the `CachedPreprocesses` DB entry by `(context, msg/signer-set digest)` or generate a fresh seed whenever `share_internal` is invoked with a `preprocesses`/`key_pair` combination not seen before, and refuse to produce a second share once a share has been emitted for that context. Alternatively, transcript the `attempt`/session ID into the preprocess addendum so cross-session replay is cryptographically impossible.

### Proof of Concept
1. Attacker (any set participant) collects victim V's preprocess for attempt `a` — `P_V` is deterministic because `CachedPreprocesses[(b"DkgConfirmer", a)]` is fixed (`signing_protocol.rs:123-147`).
2. Attacker submits signer set S₁ (participants incl. V) to V; V calls `share_internal(S₁, kp)` → emits share `s₁` with nonces `(d, e)` under challenge `c₁ = H(ρ₁(S₁), msg₁)`.
3. Attacker submits a different signer set S₂ ≠ S₁ (or a different valid `key_pair`, changing `set_keys_message`) for the same attempt; `preprocess_internal` returns the same seed → same `(d, e)` → V emits `s₂` under `c₂`.
4. With `R = D + ρE` known on-chain and `λ` computable, solve `s₁ − s₂ = λk(c₁ − c₂) + e(ρ₁ − ρ₂)`-style linear system (standard two-share nonce-reuse) to recover V's secret share.
