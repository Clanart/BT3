## Analysis

The external report's core broken invariant is: **a low-level `call` can report `success == true` while the actual desired side-effect (a real value transfer) never happened**, and calling code that only checks the boolean `success` flag without validating that the effect actually occurred will silently proceed as if funds moved.

The exact same broken invariant exists in the Tron variant of `IntentGatewayV2.sol`, but in an even more directly exploitable form than the AVAX-existence case in the original report: instead of missing an `extcodesize` check on native transfers, the code performs a **raw low-level call to an ERC20 `transfer()` and only checks that the call did not revert — it never decodes/validates the returned `bool`**.

### Where it happens

`withdraw()` — releases escrowed order-input tokens to the filler/beneficiary after a fill or refund: [1](#0-0) 

`onAccept` / `SweepDust` handling — sweeps dust tokens to a beneficiary: [2](#0-1) 

Fee redemption in the same `withdraw()` function: [3](#0-2) 

In all three spots, the pattern is:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This only reverts if the call itself reverts. Any ERC20 whose `transfer()` **returns `false` on failure instead of reverting** (a widely-known non-standard-but-common pattern, e.g. legacy tokens, tokens with transfer restrictions, paused/blacklist tokens) will make `success == true` even though zero tokens were moved — exactly the "low-level call succeeds while the real operation silently failed" class from the report.

Critically, right before this call, the escrow accounting is already decremented/marked settled and cannot be re-triggered: [4](#0-3) 

`_filled[body.commitment] = beneficiary;` is set and `_orders[body.commitment][token] -= amount;` runs unconditionally on the (falsely) "successful" call, permanently closing out the escrow record. If the token transfer silently no-ops, the tokens remain stuck in the `IntentGatewayV2` contract with no accounting path left to claim them — the escrow is marked redeemed/refunded, `_filled` is set (blocking any retry, including the timeout/refund path via `onGetResponse`), yet the beneficiary received nothing.

Note the same file imports and uses `SafeERC20` (`using SafeERC20 for IERC20;`) for other flows, but deliberately bypasses it here in favor of raw `.call(...)` — the EVM (non-Tron) counterparts of `IntentsBase.sol` use `IERC20(token).safeTransfer(beneficiary, amount)` which *does* check the returned boolean. The Tron variant lost that protection.

### Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw`/`SweepDust` allows silent transfer failure with escrow already marked settled - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2` contract redeems escrowed order tokens and sweeps dust using raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`, checking only that the low-level call did not revert. Non-standard ERC20 tokens that return `false` on failure (instead of reverting) will cause the escrow/fee/dust bookkeeping to be finalized (`_filled` set, `_orders[...] -= amount` applied, `EscrowReleased`/`EscrowRefunded` emitted) while the beneficiary actually receives zero tokens.

### Finding Description
`withdraw()` iterates `body.tokens`, decrements `_orders[commitment][token]`, and performs `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`, reverting only `if (!success)`. Because Solidity's low-level `call` returns `success = true` whenever the callee does not revert — regardless of what boolean value it returns in the response data — any ERC20 that signals failure via a `false` return value (rather than reverting) will pass this check even though no tokens moved. [1](#0-0) 

Immediately after, `_filled[body.commitment] = beneficiary` was already set at function entry and the escrow map is decremented — there is no rollback and no remaining path to re-attempt or reclaim the funds for that commitment, since `_filled` being non-zero blocks the corresponding timeout/refund GET-response check (`onGetResponse` reverts with `Filled()` if `_filled` is set). [5](#0-4) 

The same unguarded pattern is repeated for transaction-fee payout and for `SweepDust`. [3](#0-2) [2](#0-1) 

### Impact Explanation
This falls squarely within "stealing or loss of funds" / "false state acceptance" for the bridge's escrow custody logic: legitimately escrowed tokens (posted by an order creator/filler as part of intent settlement) can become permanently locked in `IntentGatewayV2` while the on-chain ledger (`_orders`, `_filled`) records the escrow as already released/refunded. No malicious relayer, prover, or admin is required — an ordinary user picks (or is forced to accept, since intent input/output tokens are order-defined) a token whose `transfer()` follows the return-`false`-on-failure convention (a real-world category of ERC20s, common on token-restricted/paused states), and any transient transfer failure (e.g., a pause, blacklist hit, insufficient allowance/edge case in the token's own logic) converts into an irreversible loss of the escrowed funds instead of a revert-and-retry.

### Likelihood Explanation
Likelihood is moderate: it requires a token used in the order's `inputs`/dust list to implement the non-reverting-`false`-return failure convention and to actually hit a failure condition at redemption time (e.g., beneficiary blacklisted, token paused, contract-level restriction). This is a known, common real-world ERC20 behavior class (not a "malicious token" prerequisite in the excluded sense — many mainstream tokens on some networks behave this way), and the trigger path (`withdraw`, reached via `onAccept`'s `RedeemEscrow`/`RefundEscrow`, or via `SweepDust`) is on the unauthenticated-execution-adjacent but core settlement hot path of the gateway.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported and used elsewhere in the codebase (and in the non-Tron `IntentsBase.sol`), so that both call-revert failures and `false`-return failures cause the whole transaction — including the escrow/fee bookkeeping mutation — to revert atomically.

### Proof of Concept
1. An order creator escrows `TokenX` (a token whose `transfer()` returns `false` on failure rather than reverting, e.g. becomes paused/blacklists an address) as `order.inputs`.
2. A filler completes the fill; later `withdraw()` is invoked (via `RedeemEscrow`) to release `TokenX` to the filler's beneficiary address.
3. If `TokenX.transfer(beneficiary, amount)` returns `false` at that moment (e.g. beneficiary is momentarily blacklisted, or the token is paused), the raw `.call` still returns `success = true`.
4. `withdraw()` proceeds: `_filled[commitment]` is set, `_orders[commitment][token] -= amount` executes, `EscrowReleased` is emitted — but the beneficiary's `TokenX` balance never increased.
5. Because `_filled[commitment]` is now non-zero, any later `onGetResponse` cancellation/timeout check reverts with `Filled()`, and there is no other function to re-attempt the transfer for that commitment — the tokens remain permanently stuck in `IntentGatewayV2` with the ledger showing them as already paid out. [6](#0-5)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
