### Title
OP_RETURN outputs are excluded from Bitcoin fee and weight accounting - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an attacker-controlled `OP_RETURN` output to `tx_outs` before calculating the transaction weight and required fee, but `calculate_weight_vbytes` only receives `payments` and the optional change script. The serialized output set used for accounting is therefore stale and omits the data output entirely. [1](#0-0) 

### Finding Description
`SignableTransaction::new` accepts up to 80 bytes of caller-provided `data` and appends a zero-value `OP_RETURN` output to the transaction output list. [2](#0-1) 

The subsequent fee calculation calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, where `payments` excludes the `OP_RETURN` output already inserted into `tx_outs`. [3](#0-2) 

`calculate_weight_vbytes` builds its model transaction solely from `payments`, plus an optional change output, so the `data` output contributes nothing to either `weight` or `vbytes`. [4](#0-3) 

When change is present, the same stale `payments` list is used again to calculate `fee_with_change`, and the resulting change output is then appended to the already-expanded `tx_outs`. [5](#0-4) 

The final transaction commits to `tx_outs`, including the omitted `OP_RETURN`, while `needed_fee` and the standard-weight check were calculated from the earlier, incomplete output list. [6](#0-5) 

### Impact Explanation
An unprivileged caller who can cause transaction data to be signed can make the threshold wallet sign a transaction whose effective fee rate is lower than the `fee_per_vbyte` supplied to the builder. With an 80-byte payload, the omitted output is approximately 91 serialized bytes, so the actual transaction can underpay the intended fee by roughly that many satoshis when change is used. [7](#0-6) 

The minimum-relay-fee check uses the same undersized `vbytes`, so a transaction expected to satisfy Bitcoin's default relay policy can instead fall below it. The maximum-standard-weight check also omits the data output and can accept a transaction that exceeds the checked bound after the output is included. [8](#0-7) 

Because the later signing path sighashes the final transaction and all prevouts, the result is a validly signed but economically inconsistent transaction: the fee and change values commit to an output layout that was not the layout used to calculate them. This can prevent relay/confirmation and leave the selected funds unavailable until a replacement transaction is coordinated. [9](#0-8) 

### Likelihood Explanation
The trigger is reachable through the public `SignableTransaction::new` API by supplying non-empty `data` together with a change address. No invalid curve points, malformed encodings, compromised peers, or leaked key material are required. [10](#0-9) 

The discrepancy is deterministic whenever `data` is non-empty because the output is added before fee calculation but deliberately absent from every `calculate_weight_vbytes` model. [11](#0-10) 

### Recommendation
Calculate weight and fee from the actual `tx_outs` list after all outputs—payments, `OP_RETURN`, and potential change—are represented. At minimum, pass a representation of the `OP_RETURN` script into `calculate_weight_vbytes`, and include it both in the initial fee calculation and the change-aware recalculation. The final `MAX_STANDARD_TX_WEIGHT` check should likewise use the complete transaction rather than the stale payment-only model. [12](#0-11) 

### Proof of Concept
1. Obtain a spendable `ReceivedOutput`, for example by scanning a transaction with `Scanner::scan_transaction`.
2. Call:

```rust
let tx = SignableTransaction::new(
  vec![received_output],
  &[],
  Some(change_script),
  Some(vec![0xaa; 80]),
  1, // one satoshi per vbyte
)?;
```

3. The constructor accepts the 80-byte payload and pushes an `OP_RETURN` output before calculating the fee. [2](#0-1) 
4. With no payments, `calculate_weight_vbytes` models either no outputs or only the change output; it never sees the `OP_RETURN` output. [13](#0-12) 
5. The returned transaction's `fee()` equals the fee calculated for the smaller transaction, while `transaction().vsize()` includes the additional serialized `OP_RETURN` output. Consequently, `fee() < transaction().vsize() as u64` at a requested rate of 1 sat/vbyte. [14](#0-13)

    let mut tx = Transaction {

      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here

          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),

      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }

    let weight = tx.weight();
