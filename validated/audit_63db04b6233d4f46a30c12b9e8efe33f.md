### Title
Scanner registers arbitrarily-small outputs as spendable, forcing fee-bleeding spends - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` records every transaction output whose `script_pubkey` matches a registered script as a spendable `ReceivedOutput`, with no minimum value check. The only dust floor in the wallet code is applied to *outgoing* payments inside `SignableTransaction::new` (`send.rs:165-169`); nothing bounds the value of *incoming* outputs. An unprivileged sender can split a deposit into many outputs each just above Bitcoin's relay dust limit, each of which is reported as received funds yet costs more in signature/witness weight to spend than it is worth.

### Finding Description
The bug class from the reference report is "a per-operation bound that an attacker defeats by splitting into many operations." In Serai's Bitcoin layer, the analog lives in the receive path:

- `scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for every output whose script matches `self.scripts`, checking only `vout` overflow — never `output.value` (`mod.rs:199-214`).
- `scan_block` extends this to every transaction in the block, including the coinbase (`mod.rs:221-227`).
- The `DUST = 546` constant and its enforcement exist only in `SignableTransaction::new` for *payments Serai constructs* (`send.rs:32`, `send.rs:165-169`). No equivalent floor is applied to outputs Serai accepts.

Each `ReceivedOutput` becomes a `TxIn` in a later `SignableTransaction`, costing roughly 57 vbytes of weight (36-byte outpoint + sequence + ~66 WU of discounted witness signature, per the accounting in `send.rs:71-83`). At any relay-acceptable fee rate, spending an output worth e.g. 600 sats costs more in fee than the output contributes — yet `needed_fee`/`fee()` accounting in `send.rs:206-235` treats `input_sat` as fully available toward payments. The sender only pays once for creating cheap outputs; the signer pays the spend-side fee for every registered input, and this repeats across unbounded transactions per block.

### Impact Explanation
Funds are reported as received that are effectively unspendable: the protocol credits/aggregates outputs whose spend cost exceeds their value, and must either burn fees consolidating them or let them accumulate. Because the attacker controls output count and granularity with ordinary public Bitcoin transactions, they can amplify a small deposit into an arbitrarily large number of fee-consuming inputs, with the loss bounded only by what they choose to spend. This is a griefing/economic drain reachable entirely from public inputs.

### Likelihood Explanation
Any external party can send a Bitcoin transaction to Serai's scanned script(s) (the plain tweaked key script is always registered in `Scanner::new`, `mod.rs:162-166`). Crafting N dust-adjacent outputs in one transaction is a standard, cheap on-chain operation. No validator collusion, key material, or privileged access is required.

### Recommendation
Enforce a minimum-accepted-value floor on the receive path mirroring the send path: either filter outputs below a `DUST`-style threshold inside `scan_transaction`/`scan_block`, or expose the value check on `ReceivedOutput` so callers cannot treat sub-economic outputs as spendable balance. The floor should exceed the marginal signature weight cost of spending the input (the ~57 vbytes computed in `calculate_weight_vbytes`), not merely Bitcoin's relay dust limit.

### Proof of Concept
```rust
// Any external sender constructs one transaction paying the Serai key's
// P2TR script_pubkey with many outputs just above relay dust:
let script = p2tr_script_buf(serai_key).unwrap();
let tx = Transaction {
    /* 1 input funding N outputs */
    output: (0..N)
        .map(|_| TxOut { value: Amount::from_sat(600), script_pubkey: script.clone() })
        .collect(),
    ..
};

// Scanner reports all N as received, spendable outputs:
let received = Scanner::new(serai_key).unwrap().scan_transaction(&tx);
assert_eq!(received.len(), N);          // each value() == 600 sats

// Each ReceivedOutput later becomes a TxIn costing ~57 vbytes to spend.
// At >= ~11 sat/vbyte the fee to spend one input (>= 627 sats) exceeds the
// 600 sats it contributes, yet SignableTransaction::new sums input_sat as
// fully available (send.rs:175) and emits change/payments on that basis.
```
