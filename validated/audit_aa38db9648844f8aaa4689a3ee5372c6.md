### Title
Public, repeatable `updateEndRemainingAllocation()` re-snapshots the bonus denominator, allowing bonus over-distribution and fund insolvency - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is `public`, has no access control, and no internal guard preventing it from being called more than once [1](#0-0) . The only "already-set" guard lives outside the function, in `claim()`'s `if (totalEndRemainingAllocation == 0)` check [2](#0-1) , so any unprivileged caller can invoke the function directly at any later time after `periodsEndTime[4]` to overwrite the bonus denominator with a smaller, decayed `totalRemainingAllocation`.

### Finding Description
`totalBonus` accumulates forfeited allocation from users who claim early (before all 5 periods have elapsed) [3](#0-2) . After `periodsEndTime[4]`, this pot is meant to be split pro-rata among the remaining (not-yet-claimed) allocatees, using `bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation` [4](#0-3) . For this formula to conserve `totalBonus` exactly across all remaining claimants, `totalEndRemainingAllocation` must be fixed **once**, at the moment `periodsEndTime[4]` is crossed, to the sum of allocations of users who have not yet claimed.

However, `totalRemainingAllocation` is decremented on every `claim()` call, including for post-period-4 claimants (`totalRemainingAllocation -= userAllocation` at [5](#0-4) ). Since `updateEndRemainingAllocation()` has no one-shot guard and no access control, any address can call it again later, after some remaining users have already claimed, causing `totalEndRemainingAllocation` to be overwritten with a smaller value (the shrinking `totalRemainingAllocation`). Because `totalBonus` is never decremented after being used in a payout, every subsequent claimant now computes `userAllocation * totalBonus / (smaller totalEndRemainingAllocation)`, which yields a larger bonus per remaining unit of allocation than originally intended. The sum of bonus payouts across all claimants then exceeds the original `totalBonus` pot, and because that pot is paid out of the shared `aidropToken` balance that also backs everyone's principal, later legitimate claimants can find the contract's balance insufficient, tripping `InsufficientBalance()` at [6](#0-5)  and being unable to claim their own principal — a fund-insolvency/theft scenario benefiting whoever claims right after the re-snapshot at the expense of remaining, honest claimants.

### Impact Explanation
This breaks the airdrop's core invariant that `totalBonus` is a bounded pot split proportionally without exceeding total contract holdings. An attacker (any allocatee, or a third party colluding/timing a call) can call `updateEndRemainingAllocation()` after watching several remaining allocatees claim, shrinking the denominator and inflating their own and subsequent claimants' bonus shares, ultimately causing insolvency such that the last claimants cannot retrieve their rightful principal — direct theft/freezing of user funds.

### Likelihood Explanation
No privileged role or capital is required — the function is `public`, callable by any EOA, with the only precondition being `block.timestamp >= periodsEndTime[4]`, which is guaranteed to become true. The attack is simply a well-timed transaction (or several) calling `updateEndRemainingAllocation()` after observing other claims, and can be repeated indefinitely since there is no one-shot flag inside the function itself.

### Recommendation
Add an internal one-shot guard directly in `updateEndRemainingAllocation()` (e.g., `require(totalEndRemainingAllocation == 0)` before the assignment, or a dedicated boolean flag), so the snapshot can only ever be taken once regardless of whether it is invoked via `claim()` or called directly by an outside party. Optionally also restrict the function with access control if only a single canonical snapshot moment is desired.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `Airdrop` with a `startTime`; register several users with equal allocations (e.g., 3 users, 100 tokens each); fund the contract with 300 tokens.
2. Warp past `periodsEndTime[1]` (early period) and have User A `claim()` early to generate a `totalBonus` forfeiture (some portion of A's 100 tokens is forfeited into `totalBonus`).
3. Warp past `periodsEndTime[4]`. Have User B call `claim()`, which internally calls `updateEndRemainingAllocation()` since `totalEndRemainingAllocation == 0`, snapshotting `totalEndRemainingAllocation` to the current `totalRemainingAllocation` (allocations of B and C only, since A already claimed).
4. Assert User B's `bonusAmount` matches `B.allocation * totalBonus / totalEndRemainingAllocation_snapshot1`.
5. Before User C claims, have an unprivileged third-party attacker directly call `updateEndRemainingAllocation()` again. Since `totalRemainingAllocation` shrank after B's claim, assert `totalEndRemainingAllocation` is now overwritten to a smaller value (`totalEndRemainingAllocation_snapshot2 < totalEndRemainingAllocation_snapshot1`).
6. Have User C `claim()` and assert C's `bonusAmount` is computed against the smaller `totalEndRemainingAllocation_snapshot2`, making C's bonus larger than the fair pro-rata share intended by the original pot.
7. Assert the sum of `bonusAmount` paid to B and C exceeds `totalBonus` (violating conservation), and/or assert the contract's final `aidropToken.balanceOf(address(this))` goes negative/insufficient relative to any remaining unclaimed principal, causing a legitimate claim to revert with `InsufficientBalance()`.
