### Title
Fee estimation omits the OP_RETURN data output, so the signed transaction pays less than the target/minimum feerate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes `needed_fee` — the value used for the minimum-relay check, the `NotEnoughFunds` check, and the change deduction — via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which reconstructs the transaction weight using only `payments`. The actual signed transaction in `tx_outs` additionally contains the OP_RETURN `data` output, which is never included in the weight/vbytes estimate. The accounting value (`needed_fee`) and the actual transaction disagree about what was deducted — the same bug class as the report, where a returned/subtracted amount silently excludes a fee-relevant component.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- `tx_outs` gains an OP_RETURN output when `data` is `Some` (send.rs:194-202).
- `calculate_weight_vbytes` is then called with `payments` — not `tx_outs` — in both fee computations (send.rs:204 and send.rs:225-227). The reconstructed `Transaction` used for `tx.weight()` therefore lacks the OP_RETURN output entirely.
- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206, 227) and the minimum-relay-floor check (send.rs:211) both use the underestimated `vbytes`.
- When `change` is `Some`, the change output value is computed as `input_sat - payment_sat - fee_with_change` (send.rs:228), so the real transaction's total output set = `payments + OP_RETURN(0) + change`, and its actual fee is exactly `fee_with_change` — charged against a transaction that is larger than the one measured.

Because `Prevouts::All` binds prevout values but nothing re-checks the real serialized size, the produced `SignableTransaction` (and its `needed_fee()`/`fee()` getters, send.rs:133-141) reports a fee computed for a smaller transaction than what is signed.

### Impact Explanation
A transaction constructed with `data` set and `fee_per_vbyte` at (or near) the minimum relay boundary passes the `TooLowFee` check while its true feerate is below `DEFAULT_MIN_RELAY_TX_FEE` — the OP_RETURN output adds roughly `9 + data.len()` bytes (up to ~89 vbytes for the 80-byte cap) that were never priced. Such a transaction will be rejected as non-standard by Bitcoin Core mempools, so a perfectly validly signed multisig transaction cannot propagate, stalling the funds it carries. It is a concrete "accounting amount excludes a fee" divergence: the amount reported/used for deduction (`needed_fee`) does not include the cost of the `data` output even though `data` is part of the signed bytes.

### Likelihood Explanation
Any `SignableTransaction::new` caller that supplies `data` triggers it; callers providing `data` plus `change` get a deterministic underpayment of `fee_per_vbyte * (vbytes_with_data - vbytes)` and a smaller-than-intended effective feerate on every such transaction. Whether an unprivileged party controls `data`/`fee_per_vbyte` depends on the integrating caller (out of scope here), but within the crate the defect is unconditional whenever `data.is_some()` — no race or adversary timing is required.

### Recommendation
Compute the weight/vbytes over the actual output set: pass `tx_outs` (or append the OP_RETURN `TxOut` inside `calculate_weight_vbytes`) to both call sites at send.rs:204 and send.rs:226 so `needed_fee`, the minimum-relay check, the `NotEnoughFunds` check, and the change deduction all price the transaction that will actually be signed. Optionally assert `self.fee() >= needed_fee` against the final `tx` weight before returning.
