### Title
Single Reward-Token Transfer Failure in `BaseRewardPool.getReward`/`BaseRewardPoolV2.getReward` Permanently Blocks Claiming of All Other Accrued Reward Tokens - ([File: rewards/BaseRewardPool.sol / rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPool.getReward` and `BaseRewardPoolV2.getReward` iterate over every registered reward token for a staking pool and, for each one with a nonzero pending balance, call `IERC20(rewardToken).safeTransfer(...)` directly inside the loop with no isolation (no try/catch, no per-token accounting rollback). If the transfer for a single reward token reverts, the entire loop reverts, and the user is unable to claim any of the other reward tokens accrued in the same pool, even though those transfers would have succeeded. This mirrors the "claimRemovedTokens" bug class: one bad transfer in a loop blocks access to otherwise-claimable funds for that user.

### Finding Description
`getReward` computes `userRewards[rewardToken][_account]` for every token in `rewardTokens` via the `updateReward`/`updateRewards` modifier, then loops and unconditionally calls `safeTransfer` for each token with `reward > 0`: [1](#0-0) 
The `BaseRewardPoolV2` variant has the identical pattern, delegating to `_sendReward`: [2](#0-1) [3](#0-2) 

Because `rewardPerTokenStored` is updated via integer division in `_provisionReward` (`(_amountReward * 10**decimals) / totalStaked()`), truncation dust accumulates over the pool's lifetime. This can leave the contract's actual on-chain balance of a given reward token marginally short of the sum of all users' computed `earned()`/`userRewards` entitlements for that token. When the shortfall manifests for the *last* claimant(s) of that specific token, `IERC20(rewardToken).safeTransfer` reverts due to insufficient balance. Since this transfer sits inside the same loop as all other (fully-funded) reward tokens for the pool, and effects for a token are zeroed only in the same iteration as its transfer (not committed if the transaction reverts), the whole `getReward` call reverts — blocking the user from claiming any of the pool's reward tokens, not just the shortfall one.

This is invoked from `MasterMagpie._claimBaseRewarder`, called within `_multiClaim`, which batches claims across multiple staking-token pools in a single transaction: [4](#0-3) [5](#0-4) 
Since `_claimBaseRewarder` is called with no try/catch inside the `for` loop over `_stakingTokens`, a stuck reward token in any single pool's rewarder causes the entire `multiclaimSpec`/`multiclaimFor` transaction to revert — freezing the user's accrued MGP and every other pool's reward tokens included in that same call as well.

### Impact Explanation
An ordinary staking user's own already-accrued (unclaimed) yield across multiple reward tokens/pools becomes permanently unclaimable once a shortfall condition is hit for any single reward token, because retrying `getReward`/`multiclaimFor` deterministically reproduces the same revert (the underlying shortfall is never resolved by the failed call, and normal reward flow does not top up the specific deficient token). This satisfies the "permanent freezing of unclaimed yield" impact bar.

### Likelihood Explanation
Truncation dust from repeated `_provisionReward` calls is a normal, expected byproduct of the reward-per-token accounting design and requires no privileged or malicious action — it accumulates naturally as pools receive many small reward deposits over time relative to `totalStaked()`. Any staking pool with several bonus reward tokens and an active reward-donation cadence is exposed, making the bug reachable purely through ordinary user/manager interactions with the reward pools over time.

### Recommendation
Wrap each reward token's transfer inside `getReward`/`getRewards`/`_sendReward` in a try/catch (or use a low-level `call` with success check) so that a failure on one reward token does not block payout of the others; skip/queue the failed token's amount (re-crediting it to `userRewards`) rather than reverting the whole loop. Additionally, cap each transfer at `min(computedReward, IERC20(rewardToken).balanceOf(address(this)))` similar to the `MultiRewarderPerSec.onReward` pattern already used elsewhere in the codebase, so dust shortfalls degrade gracefully instead of reverting.

### Proof of Concept
1. A `BaseRewardPool` is set up with reward tokens `A` and `B`; multiple users stake and claim over time, accruing rounding dust each time `_provisionReward` divides `_amountReward * 10**decimals / totalStaked()`.
2. Eventually, for token `A`, the sum of all users' `earned()` values exceeds the pool's real `A` balance by a few wei due to truncation.
3. A user calls `multiclaimFor`/`getReward` including this pool. `userRewards[A][user]` is computed (nonzero) and `userRewards[B][user]` is also nonzero and fully backed.
4. The loop reaches token `A`, calls `safeTransfer`, which reverts (`ERC20: transfer amount exceeds balance`).
5. The revert propagates through `getReward` → `_claimBaseRewarder` → `_multiClaim`, reverting the whole transaction, so the user also fails to receive their fully-funded token `B` reward and any other pools' rewards included in the same `multiclaimFor` call — with no way to work around it since the same computation repeats on retry.

            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier
            if (reward > 0) {
                userRewards[rewardToken][_account] = 0;
                IERC20(rewardToken).safeTransfer(_receiver, reward);

            }
        }

        return true;
    }

    function _claimBaseRewarder(address _stakingToken, address _account, address _receiver, address[] memory _rewardTokens) internal {
        IBaseRewardPool rewarder = IBaseRewardPool(tokenToPoolInfo[_stakingToken].rewarder);
        if (address(rewarder) != address(0)) {
            if (_rewardTokens.length > 0)
                rewarder.getRewards(_account, _receiver, _rewardTokens);
            else
                // if not specifiying any reward token, just claim them all
                rewarder.getReward(_account, _receiver);
        }
    }
