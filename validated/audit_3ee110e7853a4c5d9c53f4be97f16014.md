Based on my research, I found a strong structural analog to the original bug: **GitHub Desktop uses `Array.prototype.find()` to resolve a locally-tracked repository from an attacker-controlled deep-link URL, using a non-unique matching criterion (GitHub HTML/parent URL), which can silently select the wrong local repository.**

### Title
Deep-link repository resolution uses short-circuiting `find()` on a non-unique URL match, causing wrong local repository to be silently opened/acted upon - (File: `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The `x-github-client://openRepo/<url>` protocol handler (and its legacy `github-mac://`/`github-windows://` aliases) is Desktop's implementation of "Open in Desktop"/PR/branch deep links — fully attacker-controlled content that a user clicks. `openRepositoryFromUrl` resolves the target local `Repository` by matching the URL against the user's tracked repositories via `Array.prototype.find`, which — exactly like the reported `market_id_by_symbol` bug — is short-circuiting and returns only the first repository whose GitHub `htmlURL` (or fork `parent.htmlURL`) matches the incoming URL, even though nothing in the data model guarantees this match is unique.

### Finding Description
`openOrCloneRepository` looks up an existing repository purely by URL match: [1](#0-0) 

The match predicate `doesRepositoryMatchUrl` treats a repository as matching if either its own GitHub URL *or its fork parent's URL* equals the requested URL: [2](#0-1) 

This is invoked from `openRepositoryFromUrl`, which is the entry point for the `open-repository-from-url` action parsed straight out of the incoming deep-link URL, including an optional `pr` or `branch` parameter that triggers PR/branch checkout in whichever repository is matched: [3](#0-2) 

The URL and query parameters originate entirely from the protocol URL, which is parsed with no server-side or identity verification: [4](#0-3) 

and is delivered to the app via the OS-level `open-url`/protocol-launcher handlers, i.e., anything the user clicks (a webpage link, email, chat message) can trigger it: [5](#0-4) 

Because `find()` stops at the first match, if a user has **more than one locally-tracked repository whose GitHub URL matches the link's URL** — e.g., they have both a fork and its upstream parent tracked (parent URL match), or two separate clones associated with the same GitHub repository (common after a repo rename/transfer, or a repo added twice under different local paths) — the deep link will silently resolve to whichever one happens to appear first in `state.repositories`, not necessarily the repository the link (or the user) intended. There is no uniqueness constraint enforced anywhere in the repositories store analogous to the original report's suggested "unique identifier" fix (`market_id`), so this ambiguity is unresolved by design.

### Impact Explanation
When combined with the `branch` or `pr` query parameters, this can cause Desktop to silently switch branches or check out a pull request in a repository the user did not intend, based solely on a crafted link. Since `doesRepositoryMatchUrl` matches on the *parent* URL too, an attacker-controlled link referencing an upstream project's URL can resolve to the user's **fork** repository instead of the upstream one the link nominally points at, and drive a branch/PR checkout there — silently changing the working tree/HEAD of a repository the user subsequently commits/pushes from, without any explicit confirmation that repository identity matches the link's target. This satisfies the "silent corruption of what the user commits/pushes" impact category via an attacker-controlled link, requiring no local access, malware, or leaked credentials.

### Likelihood Explanation
Exploitability depends on the victim having multiple locally-tracked repositories that legitimately share a GitHub URL relationship (fork + parent is a very common Desktop workflow), and on the victim clicking a crafted deep link — both are realistic, low-friction preconditions for a Desktop user. The `find()`/first-match short-circuit itself is not conditional on anything else; it fires deterministically whenever more than one tracked repository matches.

### Recommendation
Replace the `find()`-based, URL-based repository match with an unambiguous identifier for resolution (e.g., require the link to disambiguate origin vs. parent explicitly, or present the user with a picker/confirmation dialog whenever more than one local repository matches the URL, analogous to the recommended fix of using `market_id` instead of `symbol`). At minimum, `doesRepositoryMatchUrl`/`openOrCloneRepository` should collect *all* matches and require explicit user confirmation before performing branch/PR checkout when the match is ambiguous.

### Proof of Concept
1. User forks `https://github.com/upstream/project` to `https://github.com/user/project` and clones both the fork and the upstream repo locally in Desktop (a common workflow — the fork's `gitHubRepository.parent.htmlURL` is set to the upstream URL).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/upstream/project?branch=malicious-branch`.
3. Victim clicks it. `parseAppURL` parses it into an `open-repository-from-url` action, and `openRepositoryFromUrl` → `openBranchNameFromUrl`/`openOrCloneRepository` resolves the target repository via `repositories.find(r => this.doesRepositoryMatchUrl(r, url))`.
4. Because the victim's **fork** repository's `parent.htmlURL` equals the upstream URL, `doesRepositoryMatchUrl` returns `true` for the fork if it happens to be earlier in `state.repositories` than the actual upstream clone (or if the upstream clone isn't tracked at all), causing Desktop to check out `malicious-branch` in the fork instead of (or in addition to) the intended upstream repository — with no dialog indicating which local repository was actually selected.

Note: I was not able to directly inspect `openPullRequestFromUrl`/`openBranchNameFromUrl` bodies or `urlsMatch`'s exact normalization logic in this session (tool budget exhausted), so the precise downstream checkout mechanics should be verified against `app/src/ui/dispatcher/dispatcher.ts` in a follow-up session before treating this as fully confirmed.

  private doesRepositoryMatchUrl(
    repo: Repository | CloningRepository,
    url: string
  ): repo is RepositoryWithGitHubRepository {
    if (repo instanceof Repository && isRepositoryWithGitHubRepository(repo)) {
      const originRepoUrl = repo.gitHubRepository.htmlURL
      const upstreamRepoUrl = repo.gitHubRepository.parent?.htmlURL ?? null

      if (originRepoUrl !== null && urlsMatch(originRepoUrl, url)) {
        return true
      }

      if (upstreamRepoUrl !== null && urlsMatch(upstreamRepoUrl, url)) {
        return true
      }
    }

    return false
  }

      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    }

  private async openOrCloneRepository(url: string): Promise<Repository | null> {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const existingRepository = repositories.find(r =>
      this.doesRepositoryMatchUrl(r, url)
    )

    if (existingRepository) {
      return await this.selectRepository(existingRepository)
    }
