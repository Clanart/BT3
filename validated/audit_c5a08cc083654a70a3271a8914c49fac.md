### Title
`ReceivedOutput::read` deserializes an unverified offset↔script binding, letting untrusted bytes report funds that cannot be spent — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Yieldblox exploit was not a cryptographic break — an oracle adapter faithfully passed through an attacker-supplied value (the poisoned USTRY price) without checking that the reported value corresponded to reality. The analog in `bitcoin-serai` is `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`), which deserializes a claimed key `offset`, a `TxOut`, and an `OutPoint` from untrusted bytes without verifying the one binding that makes a `ReceivedOutput` meaningful: that `p2tr_script_buf(key + G * offset) == output.script_pubkey`. That binding is only ever established inside `Scanner::scan_transaction` at scan time (`wallet/mod.rs:205-211`) and re-checked at signing time inside `SignableTransaction::multisig` (`send.rs:273-282`) — never at deserialization time, where the untrusted claim is first admitted.

### Finding Description
`ReceivedOutput` is the structure `bitcoin-serai` uses to represent "funds belonging to the threshold key that we can later spend." Its security depends on the triple `(offset, output, outpoint)` being internally consistent: the `script_pubkey` in `output` must equal `p2tr_script_buf(group_key + G·offset)` for `offset` to yield a spendable key.

`Scanner::scan_transaction` constructs `ReceivedOutput`s where this holds by construction (`wallet/mod.rs:205-211`). However, `ReceivedOutput::read` is also a public deserialization API that accepts arbitrary bytes:

- `wallet/mod.rs:122-134` reads `offset` via `Secp256k1::read_F`, then consensus-decodes an attacker-chosen `TxOut` and `OutPoint`, and returns them as a valid `ReceivedOutput` — no relationship check between `offset` and `output.script_pubkey` is performed anywhere in `read`.
- The only downstream check is in `SignableTransaction::multisig` (`send.rs:276-279`), which returns `None` if the offset doesn't re-derive the script. This means the invalid claim propagates through `SignableTransaction::new` first, where `input.output.value` is summed into `input_sat` (`send.rs:175`) and used for fee/change/balance accounting on the claimed — not real — value.

Like the oracle adapter that "returned the latest price and passed the full inflation straight through," `read` returns the claimed offset/output pair straight through, and every consumer between `read` and `multisig` sees a `ReceivedOutput` asserting received value with no validated spendability.

### Impact Explanation
An attacker who can feed bytes into `ReceivedOutput::read` (serialized `ReceivedOutput`s are exchanged/relayed between protocol components via `serialize`/`read`) can fabricate a `ReceivedOutput` claiming an arbitrary `TxOut` value and a controlled offset. Consequences:

- `SignableTransaction::new` treats the claimed `output.value` as spendable input value (`send.rs:175`), inflating the apparent balance and emitting change/fee amounts computed against phantom funds.
- If the claimed `script_pubkey` does not match the offset, `multisig` returns `None` — the "funds" were reported and accounted as received but are not spendable (accepted impact class).
- If the claimed `script_pubkey` is a legitimately registered offset script but the `outpoint`/`value` do not correspond to a real UTXO of that value, the BIP-341 sighash in `Prevouts::All` (`send.rs:373-386`) commits to the declared amounts; the resulting signatures will not validate on chain, producing multisig-signed transactions that burn a real `OutPoint` reference or stall signing sessions.

Severity: Medium. The signing-time check in `multisig` bounds the worst case (no direct theft of the threshold key's funds), but the unvalidated deserialization admits fabricated received-funds claims that drive incorrect balance accounting and invalid/signature-wasting transactions.

### Likelihood Explanation
Reachable by an unprivileged party: `ReceivedOutput::read` is listed among the deserialization sinks for untrusted bytes, and `serialize`/`read` round-trips are the mechanism by which outputs move between components. The attacker needs no key material — only the ability to supply bytes to `read`. Exploitation requires a consumer that trusts the returned `output.value`/`offset` before `multisig` re-validates; the scan path itself (`scan_transaction`) is safe, but `read` exposes the unchecked path explicitly for external data.

### Recommendation
Either remove the public `read` path or make `ReceivedOutput` validate-on-read. Since `read` lacks access to the group key, the minimal fix is to store/verify the binding at construction: change `read` into a method on `Scanner` (which holds `key` and the registered `scripts` map), so that deserialization re-derives `p2tr_script_buf(key + G·offset)` and rejects bytes whose `script_pubkey` isn't a registered script for that offset — the same check `multisig` performs at `send.rs:277`, moved to the trust boundary where the untrusted bytes enter. Alternatively, add a `ReceivedOutput::verify(&self, key) -> bool` and require consumers to call it immediately after `read`.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ReceivedOutput::read:
// offset = arbitrary scalar, output = TxOut { value: u64::MAX >> 10, script_pubkey: <attacker script> }
let mut bytes = vec![];
bytes.extend(Scalar::ONE.to_bytes());                    // claimed offset
bytes.extend(serialize(&TxOut {                          // claimed output
    value: Amount::from_sat(50_000_000),                 // 0.5 BTC phantom value
    script_pubkey: ScriptBuf::new_p2tr_tweaked(
        TweakedPublicKey::dangerous_assume_tweaked(attacker_xonly),
    ),
}));
bytes.extend(serialize(&OutPoint::new(real_txid, 0)));   // claimed outpoint

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// forged.value() == 50_000_000, forged.offset() == Scalar::ONE
// No error raised: the offset/script binding is never checked here.
// SignableTransaction::new(vec![forged], ...) will treat 50M sats as input value
// (send.rs:175); only multisig() at send.rs:277 notices — after accounting
// has already consumed the fabricated claim.
```

Uncertainty note: whether a concrete processor path calls `ReceivedOutput::read` on peer-supplied bytes could not be fully confirmed within scope (`processor/` is out of scope and the index showed only test usage at `networks/bitcoin/tests/wallet.rs:73`). The vulnerability stands at the `networks/bitcoin/src` API boundary: `read` admits claims `scan_transaction` would never produce, and the validation that protects signing (`multisig`) runs only after the fabricated value has already driven `SignableTransaction` accounting.
