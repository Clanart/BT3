### Title
`Scanner::scan_block` reports immature coinbase outputs as immediately spendable - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_block` scans `block.txdata[0]` along with every ordinary transaction, converts matching coinbase outputs into `ReceivedOutput`s, and does not expose enough maturity metadata for downstream transaction construction to reject them before Bitcoin's 100-block maturity period. [1](#0-0) [2](#0-1) 

### Finding Description
`ReceivedOutput` is documented as “a spendable output,” but contains only an offset, `TxOut`, and `OutPoint`, with no transaction type, block height, or maturity marker. [2](#0-1) 

`scan_transaction` blindly returns every matching output as spendable and `scan_block` invokes it on every element of `block.txdata`, including the coinbase transaction at index zero. [3](#0-2) [4](#0-3) 

`SignableTransaction::new` then accepts each supplied `ReceivedOutput`, places its `outpoint` into a transaction input, and includes its nominal value in the available-input total without any maturity validation. [5](#0-4) 

### Impact Explanation
A miner can direct a new coinbase reward to a scanner-registered script, causing the wallet to report a confirmed-looking balance which cannot legally be spent until it reaches maturity. [6](#0-5) 

If that result is passed to `SignableTransaction::new`, the protocol constructs and signs a transaction spending an immature outpoint, which the Bitcoin network will reject; repeated processing can also overstate immediately available funds and stall the intended payment flow. [5](#0-4) 

### Likelihood Explanation
The triggering transaction is public chain data under an unprivileged miner's control, and no malformed encoding, trusted peer behavior, leaked key, or malformed cryptographic object is required. [4](#0-3) 

The function documentation mentions that a post-processing pass is required for immediate spendability, but the returned type still represents the object as spendable and provides no maturity field that would let ordinary consumers enforce that requirement after serialization. [7](#0-6) [8](#0-7) 

### Recommendation
Exclude `block.txdata[0]` from `scan_block`, or extend `ReceivedOutput` with maturity metadata and make `SignableTransaction::new` reject inputs which are not mature. [4](#0-3) [9](#0-8) 

### Proof of Concept

```rust
// A miner creates a block whose coinbase pays `scanner_script`.
let outputs = scanner.scan_block(&block);

// `scan_transaction` matches the coinbase output solely by `script_pubkey`.
assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].outpoint().vout, paying_vout);

// The wallet treats this as immediately available input value.
let tx = SignableTransaction::new(
    vec![outputs[0].clone()],
    &payments,
    change,
    None,
    fee_per_vbyte,
)?;

// FROST signs a transaction which Bitcoin rejects for spending an
// immature coinbase outpoint.
let machine = tx.multisig(&threshold_keys).unwrap();
```

This path requires no exploit primitives beyond a coinbase transaction paying the monitored script, because the only membership test performed is a `script_pubkey` lookup and no transaction-index or maturity check occurs before input construction. [10](#0-9) [11](#0-10)

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
