Audit Report

## Title
Single unprivileged WebSocket client can exhaust the entire global RPC PubSub subscription pool, denying subscription service to all other clients - (File: `rpc/src/rpc_subscription_tracker.rs`)

## Summary
`SubscriptionControl::subscribe` in `rpc/src/rpc_subscription_tracker.rs` enforces only a single global cap (`max_active_subscriptions`, default `1_000_000`) via `SubscriberCountGuard::try_reserve`, with no per-connection, per-IP, or per-client quota anywhere in the pubsub stack. A single unprivileged WebSocket client can issue enough distinct `accountSubscribe`/`programSubscribe`/`logsSubscribe` requests over one connection to consume the entire global subscription budget, denying the RPC PubSub service to all other legitimate clients on that node.

## Finding Description
`rpc/src/rpc_pubsub_service.rs`'s `handle_connection` (lines 349-427) accepts any TCP client and repeatedly calls `json_rpc_handler.handle_request` for each JSON-RPC message on the connection, without any per-connection request counting, subscription counting, or throttling logic [1](#0-0) . Each subscribe call routes to `RpcSolPubSubImpl::subscribe`, which calls `SubscriptionControl::subscribe` in `rpc/src/rpc_subscription_tracker.rs` [2](#0-1) .

The reservation is performed by `SubscriberCountGuard::try_reserve`, which checks and increments a single shared `AtomicUsize` bounded only by `max_active_subscriptions` — no dimension of the check is tied to the connection, socket address, or client identity [3](#0-2) . The comment directly above `subscribe` explicitly documents that "duplicate subscribes to the same params each consume their own slot," confirming that a connection cannot be capped by relying on `SubscriptionParams` deduplication [4](#0-3) .

The default global cap is `1_000_000`, explicitly documented as shared "across all connections" [5](#0-4) . A search of the RPC pubsub source for any rate-limiting, quota, or semaphore-based per-connection mechanism returns no matches, confirming there is no existing guard against this. Because `SubscriptionParams` includes the account pubkey/filter as part of the hash key, a client trivially avoids dedup by varying the pubkey on each `accountSubscribe` call, causing each call to allocate its own `SubscriberCountGuard` and consume one slot of the shared pool, exactly as demonstrated by the existing unit test documenting that duplicate params each consume separate subscriber slots [6](#0-5) .

Once the shared counter reaches `max_active_subscriptions`, every other client's subscribe attempts fail via `Error::TooManySubscriptions`, which `RpcSolPubSubImpl::subscribe` maps to a generic `InternalError` ("Node subscription limit reached") [7](#0-6) , denying the PubSub service to all other legitimate clients.

## Impact Explanation
This is an RPC-service-degradation/denial condition reachable by a single unprivileged WebSocket client at low per-request cost, requiring no special access, no malicious peer/validator assumption, and no trusted plugin. It disables the subscription-notification capability of the node for all other consumers, matching the "single-client low-rate RPC crash/degradation" and "non-RPC remote exhaustion" categories of valid impact for this scope.

## Likelihood Explanation
The exploit path only requires opening one WebSocket connection to the public RPC PubSub port and sending a loop of ordinary, publicly documented `accountSubscribe` (or `programSubscribe`/`logsSubscribe`) requests with varied parameters to avoid dedup. No authentication, elevated privilege, or timing/race condition is required; the shared counter fills deterministically and monotonically as each request succeeds, and no code path anywhere in `handle_connection`, `RpcSolPubSubImpl`, or `SubscriptionControl` bounds how much of that counter a single connection may claim.

## Recommendation
Add a per-connection (and/or per-IP) subscription quota, smaller than and independent of the global `max_active_subscriptions` cap, enforced either inside `SubscriptionControl::subscribe` (by threading a per-connection counter/handle through the call) or in `handle_connection`/`RpcSolPubSubImpl` (by tracking and capping the size of `current_subscriptions` per connection before delegating to the global reservation). Additionally consider rate-limiting subscribe requests per connection to slow slot-exhaustion attempts.

## Proof of Concept
1. Run an `agave-validator` with default `--rpc-pubsub-max-active-subscriptions` (1,000,000).
2. From a single unauthenticated WebSocket client connected to the pubsub port, loop sending `accountSubscribe` requests, each with a freshly generated random `Pubkey` (to avoid `SubscriptionParams` dedup in `rpc/src/rpc_subscription_tracker.rs`), until the client accumulates a very large share of/ up to the configured cap.
3. From a second, independent client, attempt any subscribe call (e.g., `slotSubscribe`); once the global pool is exhausted it fails with `TooManySubscriptions` → `InternalError` ("Node subscription limit reached"), demonstrating denial of the PubSub subscription service to legitimate clients caused solely by one client's unthrottled subscription flood.

async fn handle_connection(
    socket: TcpStream,
    subscription_control: SubscriptionControl,
    config: PubSubConfig,
    mut tripwire: Tripwire,
) -> Result<(), Error> {
    let mut server = Server::new(socket.compat());
    let request = server.receive_request().await?;
    let accept = server::Response::Accept {
        key: request.key(),
        protocol: None,
    };
    server.send_response(&accept).await?;
    let mut builder = server.into_builder();
    builder.set_max_message_size(4_096);
    builder.set_max_frame_size(4_096);
    let (mut sender, mut receiver) = builder.finish();

    let mut broadcast_receiver = subscription_control.broadcast_receiver();
    let mut data = Vec::new();
    let current_subscriptions = Arc::new(DashMap::new());

    let mut json_rpc_handler = IoHandler::new();
    let rpc_impl = RpcSolPubSubImpl::new(
        config,
        subscription_control,
        Arc::clone(&current_subscriptions),
    );
    json_rpc_handler.extend_with(rpc_impl.to_delegate());
    let broadcast_handler = BroadcastHandler::new(current_subscriptions);
    loop {
        // Extra block for dropping `receive_future`.
        {
            // soketto is not cancel safe, so we have to introduce an inner loop to poll
            // `receive_data` to completion.
            let receive_future = receiver.receive_data(&mut data);
            pin!(receive_future);
            loop {
                select! {
                    biased; // See [prioritization] note below.

                    // [prioritization]
                    // This block must come FIRST in the `select!` macro. This prioritizes
                    // processing received messages over sending messages. This ensures the timely
                    // processing of new subscriptions and time-sensitive opcodes like `PING`.
                    result = &mut receive_future => match result {
                        Ok(_) => break,
                        Err(soketto::connection::Error::Closed) => return Ok(()),
                        Err(err) => return Err(err.into()),
                    },
                    result = broadcast_receiver.recv() => {

                        // In both possible error cases (closed or lagged) we disconnect the client.
                        if let Some(json) = broadcast_handler.handle(result?)? {
                            sender.send_text(&*json).await?;
                        }
                    },
                    _ = &mut tripwire => {
                        warn!("disconnecting websocket client: shutting down");
                        return Ok(())
                    },

                }
            }
        }
        let Ok(data_str) = str::from_utf8(&data) else {
            // Old implementation just closes the connection, so we preserve that behavior
            // for now. It would be more correct to respond with an error.
            break;
        };

        if let Some(response) = json_rpc_handler.handle_request(data_str).await {
            sender.send_text(&response).await?;
        }
        data.clear();
    }

    Ok(())
}

// RAII guard for one subscriber slot. The slot is reserved atomically against
// the configured cap by `try_reserve` (returns `None` if the cap is reached)
// and released on drop. Intentionally not `Clone`: each holder must go through
// `try_reserve` so duplicates cannot bypass the cap.
struct SubscriberCountGuard(Arc<SubscriptionControlInner>);

impl SubscriberCountGuard {
    fn try_reserve(control: &Arc<SubscriptionControlInner>) -> Option<Self> {
        let max = control.max_active_subscriptions;
        control
            .subscriber_count
            .fetch_update(Ordering::Relaxed, Ordering::Relaxed, |current| {
                (current < max).then_some(current + 1)
            })
            .ok()?;
        Some(Self(Arc::clone(control)))
    }
}

    fn duplicate_params_consume_separate_subscriber_slots() {
        // Cap of 1 must reject a second subscriber even when params match an
        // existing subscription (GHSA: duplicate-params cap bypass).
        let (sender, _receiver) = bounded(1024);
        let (broadcast_sender, _broadcast_receiver) = broadcast::channel(42);
        let control = SubscriptionControl::new(1, sender, broadcast_sender);

        let token1 = control.subscribe(SubscriptionParams::Slot).unwrap();
        assert_eq!(control.total(), 1);
        assert_eq!(control.subscriber_total(), 1);

        assert!(matches!(
            control.subscribe(SubscriptionParams::Slot),
            Err(Error::TooManySubscriptions)
        ));
        assert_eq!(control.subscriber_total(), 1);

        drop(token1);
        // After the only holder drops, a fresh subscriber should fit again.
        let token2 = control.subscribe(SubscriptionParams::Slot).unwrap();
        assert_eq!(control.subscriber_total(), 1);
        drop(token2);
        assert_eq!(control.subscriber_total(), 0);
    }
