### Title
Unbounded aggregate length causes memory exhaustion during deserialization - ([File: crypto/schnorr/src/aggregate.rs])

### Summary
`SchnorrAggregate::read` trusts an attacker-controlled 32-bit count and repeatedly reads and stores group elements without imposing an aggregate-size limit, allowing an input stream to consume unbounded memory and CPU. [1](#0-0) 

### Finding Description
The function reads four bytes, interprets them as `u32::from_le_bytes(len)`, and loops exactly that many times while pushing each decoded `C::G` into `Rs`. [2](#0-1)  There is no maximum count, expected-size check, or relationship to a caller-provided participant/signature count before allocation and decoding occur. [3](#0-2)  Because `C::read_G` performs canonical point decoding for every supplied element, the input also causes CPU work proportional to the declared count. [4](#0-3) 

### Impact Explanation
An unprivileged input producer can keep a stream supplying valid point encodings and force the deserializer to accumulate up to `u32::MAX` group elements. [2](#0-1)  On 64-bit systems this permits memory growth well beyond the serialized input processed at any particular time, eventually exhausting available memory or causing the process to be terminated. [5](#0-4)  The denial of service occurs before any signature validity needs to be established. [1](#0-0) 

### Likelihood Explanation
The only initial attacker-controlled field is the four-byte count, and no authentication or proof verification is required before the loop executes. [2](#0-1)  A stream such as a network reader can continuously provide the same canonical secp256k1 generator encoding while allocation continues. [6](#0-5)  This is exploitable wherever untrusted aggregate-signature bytes are passed to `SchnorrAggregate::read`. [7](#0-6) 

### Recommendation
Add an explicit, protocol-appropriate maximum aggregate length before iterating, and reject counts greater than that bound. [8](#0-7)  Prefer passing the expected signature count into `read`, reserving at most that amount, and erroring when the encoded length differs. [3](#0-2) 

### Proof of Concept
```rust
use std::io::{self, Read};

use frost::curve::Secp256k1;
use schnorr::aggregate::SchnorrAggregate;

struct EndlessGenerator {
  offset: usize,
}

impl Read for EndlessGenerator {
  fn read(&mut self, out: &mut [u8]) -> io::Result<usize> {
    const GENERATOR: [u8; 33] = [
      0x02, 0x79, 0xbe, 0x66, 0x7e, 0xf9, 0xdc, 0xbb,
      0xac, 0x55, 0xa0, 0x62, 0x95, 0xce, 0x87, 0x0b,
      0x07, 0x02, 0x9b, 0xfc, 0xdb, 0x2d, 0xce, 0x28,
      0xd9, 0x59, 0xf2, 0x81, 0x5b, 0x16, 0xf8, 0x17,
      0x98,
    ];

    for byte in out {
      *byte = GENERATOR[self.offset];
      self.offset = (self.offset + 1) % GENERATOR.len();
    }
    Ok(out.len())
  }
}

let count = u32::MAX.to_le_bytes();
let mut reader = count.as_slice().chain(EndlessGenerator { offset: 0 });

// Never terminates successfully on an endless stream: Rs grows until OOM.
let _ = SchnorrAggregate::<Secp256k1>::read(&mut reader);
```

This supplies a maximal length followed by an unending sequence of canonical compressed secp256k1 generator encodings, causing `Rs` to grow without a protocol bound. [9](#0-8)
