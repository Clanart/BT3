### Title
Data race on `CMessage::composite_fields` lazy-initialized map in `GetFieldValue`/`SetCompositeField` (Python pyext) - ([File: python/google/protobuf/pyext/message.cc])

### Summary
EVerest's CVE-2026-26074 describes a `std::map<std::queue>` data race caused by a lock mismatch: a shared map is read/mutated from one thread (network CSMS event) while another thread (physical EVSE fault) concurrently mutates it without a consistent lock discipline, corrupting the map. The transferable invariant is: *a mutable container shared across threads must be protected by a single, consistently-held lock for both its lazy-initialization and its read/insert operations.*

In this protobuf checkout, `CMessage::composite_fields` (a `LazyUniquePtr<PyWeakValueMap>`) is exactly such a shared, lazily-initialized map. `GetFieldValue` reads it via `composite_fields.TryGet()` and later lazily creates/populates it via `SetCompositeField` → `composite_fields.Get()->TrySet(...)`, with no mutex protecting the check-then-act sequence across threads that access the same `CMessage` object concurrently [1](#0-0) . This is the same class of bug as EVerest's: concurrent lazy-init + insert/lookup on a shared map without synchronization.

### Finding Description
`GetFieldValue(CMessage* self, const FieldDescriptor* field_descriptor)` first checks whether `self->composite_fields` has already been lazily allocated and looks up the field in it: [1](#0-0) 

If not found, it builds a new container object and stores it back into the map via `SetCompositeField`, which itself calls `.Get()` (lazily allocating the map if needed) followed by `TrySet`: [2](#0-1) [3](#0-2) 

The `LazyUniquePtr` type backing `composite_fields` is defined in `lazy_unique_ptr.h` and provides `TryGet()`/`Get()` accessors, but the "lazy" allocation itself is a classic check-then-act pattern (`if (!ptr) ptr = new T()`) that is unsafe when two threads call `Get()`/`TrySet()` on the same `CMessage` concurrently without an external lock. Nothing in `GetFieldValue`, `SetCompositeField`, or `SetSubmessage` (which similarly touches `child_submessages`) acquires a mutex around the read-then-lazily-allocate-then-insert sequence [4](#0-3) .

This is not merely theoretical: the repository's own regression test explicitly documents and reproduces this exact race: [5](#0-4) 

The comment states plainly: *"This access triggers GetFieldValue and lazy initialization of the composite_fields map in CMessage,"* and the test uses a `threading.Barrier` to force ten threads to hit `GetFieldValue` concurrently on the same shared `msg` object — precisely mirroring the EVerest pattern of two independent event sources (there: network + physical fault; here: two threads calling a public API) mutating a shared map without a consistent lock. The same file also documents companion races: `testConcurrentGetOptionsRace`, `testConcurrentGetAndRegisterMessageClassDataRace`, `testConcurrentLazyUnpackAndRead`, and `testConcurrentRepeatedCompositeSubscript` — all against unsynchronized lazy-initialized shared state reached through ordinary public accessors [6](#0-5) .

### Impact Explanation
A consuming application that shares a single parsed `Message` object across threads (a common and supported pattern — messages are documented as safe for concurrent read-only access) and has two threads independently access different message fields for the first time can race on the underlying weak-value map used to cache field wrapper objects. Under ThreadSanitizer this manifests as the same class of finding as the EVerest report: a data race on map internals during concurrent lazy population, with potential for map corruption (lost/duplicate entries, use-after-free of a container object if two threads simultaneously build and insert competing wrapper objects for the same field), analogous to the `std::map<std::queue>` corruption in the external report. Confidentiality/integrity impact is bounded to process-local memory corruption reachable via ordinary API use (`msg.optional_nested_message` accessed concurrently after a normal `ParseFromString`) rather than a directly attacker-controlled wire-format defect — the trigger is concurrent *host application* access pattern, not a malicious payload per field/tag/length as in typical parser CVEs.

### Likelihood Explanation
Reachability requires only that the consuming application share one parsed `Message` object across multiple threads and read different not-yet-materialized composite fields concurrently — no malicious schema or malformed payload is needed, only the standard behavior of accessing a message's submessage/repeated/map fields for the first time from more than one thread. This is a realistic and even common Python multi-threaded usage pattern (e.g., worker threads inspecting different fields of a message received from a shared queue), which is exactly why the project's own `thread_safe_test.py` maintains a dedicated reproduction (`testConcurrentGetFieldValueRace`) with a synchronization barrier to reliably force the race window [7](#0-6) .

### Recommendation
Protect the composite-fields (and child-submessages) lazy-initialize/read/insert sequence in `GetFieldValue`/`SetCompositeField`/`SetSubmessage`/`RemoveFromParentCache` with a consistent per-`CMessage` (or per-map) lock — matching the approach already used elsewhere in the codebase for `MapFieldBase::ReflectionPayload` (`absl::Mutex& mutex()` guarding `SyncMapWithRepeatedField`/`SyncRepeatedFieldWithMap` under double-checked locking) [8](#0-7) . Since this code targets CPython's free-threaded (`Py_GIL_DISABLED`) builds where the GIL no longer serializes these accesses, the fix should reuse the existing `FreeThreadingMutex`/`PyUpb_Mutex` pattern already present in the tree for analogous cases [9](#0-8)  to guard `LazyUniquePtr::Get()` and the subsequent map mutation as one atomic critical section, rather than leaving the check-then-act split across `TryGet()`/`Get()`/`TrySet()` calls.

### Proof of Concept
The existing in-tree test is a direct, minimal reproduction using only public API surface (message construction + field access from multiple threads); no modification of the test is required to demonstrate the race: [5](#0-4) 
Running this test under a free-threaded CPython build with ThreadSanitizer enabled on the C++ extension reproduces concurrent unsynchronized access to `self->composite_fields` inside `GetFieldValue`/`SetCompositeField` [10](#0-9) , mirroring the "concurrent access (data race) to a shared map" pattern described in the EVerest advisory. I was not able to execute this test in this environment to capture a live TSAN trace; the analysis above is based on static reading of `message.cc`, `message.h`, and the test file's own explicit documentation of the race, which should be treated as the strongest available evidence in this checkout.

PyObject* GetFieldValue(CMessage* self,
                        const FieldDescriptor* field_descriptor) {
  if (CMessage::CompositeFieldsMap* fields = self->composite_fields.TryGet();
      fields != nullptr) {
    if (PyObject* value = fields->Get(field_descriptor, nullptr)) {
      return value;
    }
  }

  const Descriptor* message_descriptor =
      (reinterpret_cast<CMessageClass*>(Py_TYPE(self)))->message_descriptor;
  // We might've run into a descriptor pool mismatch.
  // In that case, we can update the field descriptor directly in the case
  // of a direct match.
  if (message_descriptor != self->message->GetDescriptor()) {
    if (message_descriptor->full_name() ==
        self->message->GetDescriptor()->full_name()) {
      message_descriptor = self->message->GetDescriptor();
      field_descriptor =
          message_descriptor->FindFieldByName(field_descriptor->name());
    }
  }

  if (self->message->GetDescriptor() != field_descriptor->containing_type()) {
    PyErr_Format(PyExc_TypeError,
                 "descriptor to field '%s' doesn't apply to '%s' object",
                 std::string(field_descriptor->full_name()).c_str(),
                 Py_TYPE(self)->tp_name);
    return nullptr;
  }

  if (!field_descriptor->is_repeated() &&
      field_descriptor->cpp_type() != FieldDescriptor::CPPTYPE_MESSAGE) {
    return InternalGetScalar(self->message, field_descriptor);
  }

  ContainerBase* py_container = nullptr;
  if (field_descriptor->is_map()) {
    const Descriptor* entry_type = field_descriptor->message_type();
    const FieldDescriptor* value_type = entry_type->map_value();
    if (value_type->cpp_type() == FieldDescriptor::CPPTYPE_MESSAGE) {
      CMessageClass* value_class = message_factory::GetMessageClass(
          GetFactoryForMessage(self), value_type->message_type());
      if (value_class == nullptr) {
        return nullptr;
      }
      py_container =
          NewMessageMapContainer(self, field_descriptor, value_class);
    } else {
      py_container = NewScalarMapContainer(self, field_descriptor);
    }
  } else if (field_descriptor->is_repeated()) {
    if (field_descriptor->cpp_type() == FieldDescriptor::CPPTYPE_MESSAGE) {
      CMessageClass* message_class = message_factory::GetMessageClass(
          GetFactoryForMessage(self), field_descriptor->message_type());
      if (message_class == nullptr) {
        return nullptr;
      }
      py_container = repeated_composite_container::NewContainer(
          self, field_descriptor, message_class);
    } else {
      py_container =
          repeated_scalar_container::NewContainer(self, field_descriptor);
    }
  } else if (field_descriptor->cpp_type() == FieldDescriptor::CPPTYPE_MESSAGE) {
    py_container = InternalGetSubMessage(self, field_descriptor);
  } else {
    PyErr_SetString(PyExc_SystemError, "Should never happen");
  }

  if (py_container == nullptr) {
    return nullptr;
  }
  PyObject* value = py_container->AsPyObject();
  SetCompositeField(self, field_descriptor, value);
  return value;

      barrier.wait()

      _ = msg.optional_nested_message

    for _ in range(100):
      threads = []
      msg = unittest_proto3_pb2.TestAllTypes()

      for _ in range(10):

        threads.append(thread)
        thread.start()
