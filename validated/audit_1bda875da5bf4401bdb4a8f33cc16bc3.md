### Title
Unauthenticated `OutputType` classification lets any Bitcoin sender spoof Branch/Forwarded outputs and hijack balance-keyed scheduler state - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the GOAT `createVote()` bug — where a security-critical value (`aEthValue`) was derived from ambient, attacker-influenceable state (`balanceOf(address(this))`) instead of an authenticated parameter — `Scanner::scan_transaction` derives an output's semantic `OutputType` (`External`, `Branch`, `Change`, `Forwarded`) solely from `script_pubkey` membership in `self.scripts`. These scripts are deterministic functions of the public group key (`p2tr_script_buf(key + G*offset)` with fixed `hash_to_F(KEY_DST, b"branch"|"change"|"forward")` offsets), so any unprivileged party can compute them and send a Bitcoin transaction that the scanner classifies as an internal `Branch`, `Change`, or `Forwarded` output. Downstream logic then consumes that spoofed output against state keyed only on the amount (`can_use_branch`/`plans.get_mut(&amount)`, `ForwardedOutputDb::take_forwarded_output(txn, output.balance())`), which the attacker fully controls.

### Finding Description
`Scanner::scan_transaction` pushes a `ReceivedOutput` for any output whose `script_pubkey` is in the `scripts` map, returning the registered offset. In `Bitcoin::get_outputs` (`processor/src/networks/bitcoin.rs:686-700`), the kind is recovered via `kinds[offset_repr_ref]` — purely attacker-selectable by choosing which derived script to pay. The offsets are surjective, not authenticated: `register_offset` only guarantees internal uniqueness of scripts, not that outputs to them were honestly created. The downstream trust is explicit in `processor/src/networks/mod.rs:67-75`, which states a `Branch` output may be "from S[0], or Eve ... has sent us a forged TX which is ... equally as usable". However, the equivalence assumption breaks because:

1. `filter_outputs_due_to_closing` (`processor/src/multisigs/mod.rs:485-526`) treats any `Branch`-kind output whose `balance()` passes `scheduler.can_use_branch` as confirmation of a scheduled plan, popping the queued payments and executing them with the attacker's output as input (`utxo.rs:276-291` matches plans purely on `amount`).
2. `scanner_event_to_multisig_event` (`processor/src/multisigs/mod.rs:824-833`) calls `ForwardedOutputDb::take_forwarded_output(txn, output.balance())` — binding a pending `InInstruction` to any `Forwarded`-kind output of matching amount, regardless of origin.
3. The `Change` branch (`mod.rs:527-548`) explicitly "lets slip in" payments to the change address co-located in a transaction with an honest change output.

Unlike GOAT — where the attacker could recover funds via `earningWithdraw` — the spoofed output here does become real spendable multisig funds, so the direct "free revert" shape doesn't transfer. The transferable analog is the unauthenticated ambient-value trust: the protocol attributes protocol-internal semantics (`Branch` = my scheduled plan completed; `Forwarded` = this InInstruction was delivered) to data an unprivileged sender fabricated.

### Impact Explanation
An attacker who observes a pending forward (predictable amount, known forward address) can race a payment to the `Forwarded` script with an equal amount, causing `take_forwarded_output` to bind the stored `InInstruction` to their output — the instruction is then reported as delivered against the attacker's transaction rather than the actual forward. Similarly, during rotation (`ClosingExisting`), a spoofed `Branch` output of the exact queued amount is treated as plan confirmation, triggering execution of queued payments using attacker-supplied inputs, corrupting the deterministic schedule assumption (`S[i]` chaining described in `mod.rs:53-75`). These produce incorrect internal state transitions — instructions marked resolved and plans consumed on the basis of unauthenticated inputs.

### Likelihood Explanation
Reachable by any unprivileged Bitcoin user constructing an ordinary transaction (the allowed "Bitcoin transactions they send" input class). Requirements: knowing the group key (public) and guessing/matching a pending plan or forward amount (amounts are deterministic sums of known payments). No timing precision beyond landing in the same or next block is needed. Likelihood is gated by needing a pending matching-amount plan/instruction, hence Medium rather than High.

### Recommendation
Do not trust `script_pubkey`/`amount` alone as proof of internal provenance. For `Branch` outputs, bind the scanned output's `OutPoint` to the expected plan TXID (the txid is deterministically computable before signing, as `SignableTransaction::txid()` exists) rather than matching on `balance()` alone. For `Forwarded` outputs, key `ForwardedOutputDb` on the outpoint or the exact expected script-plus-amount-plus-TXID, not just `balance()`. Where perfect binding isn't possible (privacy-coin chains justify the current design for Monero), gate the amount-keyed matching paths to networks that genuinely need it and document the Bitcoin-specific exposure.

### Proof of Concept
1. Obtain the multisig group key `K` (public). Compute the forward script `p2tr_script_buf(K + G * hash_to_F("Serai Bitcoin Output Offset", "forward"))` per `scanner()` in `processor/src/networks/bitcoin.rs:314-347` and `p2tr_script_buf` in `networks/bitcoin/src/wallet/mod.rs:80-86`.
2. When an `InInstruction` is pending (its forwarded amount `A` is deterministic), broadcast a transaction paying exactly `A` to the forward script, in the same or an earlier block than the honest forward.
3. `scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) emits a `ReceivedOutput`; `get_outputs` labels it `OutputType::Forwarded`; `scanner_event_to_multisig_event` consumes `ForwardedOutputDb::take_forwarded_output(txn, A)` and pushes the stored instruction as resolved — bound to the attacker's tx, not the real forward.
4. Branch variant: during `RotationStep::ClosingExisting`, send `amount` equal to a queued plan's expected branch amount to the branch script; `can_use_branch` (`processor/src/multisigs/scheduler/utxo.rs:193-196`) returns true, the plan is consumed and `execute`d with the attacker's UTXO as the input.

Caveat: the impact manifestations (scheduler/instruction DB) live in `processor/`, which is outside the listed in-scope directories; the root cause — provenance-free classification of untrusted chain data into internal `OutputType`s — is in-scope in `networks/bitcoin/src/wallet/mod.rs`. If the scope restriction is interpreted to exclude findings whose impact is realized in `processor/`, this should be downgraded accordingly.
