### Title
Auction bid `MaxGasPrice` term can be forged/altered without invalidating existing signatures under KIP-249 v2 typehash - (File: kaiax/auction/eip712.go)

### Summary
In the `kaiax/auction` module (KIP-249 implementation), a searcher's bid (`Bid`/`BidData`) contains an optional `MaxGasPrice` field, but the EIP-712 struct hash used for the "v2.1" (`AuctionVersionV2 = "0.0.1"`) auction-entry-point typehash does not include `MaxGasPrice` in the signed data. Combined with the fact that the auctioneer's signature is computed only over the searcher's signature bytes (not over the bid fields), any caller that has observed a valid `(searcherSig, auctioneerSig)` pair for a given bid can resubmit that bid via the permissionless `auction_submitBid` RPC / p2p `HandleBid` path with an arbitrary `MaxGasPrice` value while both signatures still validate successfully. This mirrors the Cooler "roll loan with arbitrary terms" bug class: a party can unilaterally alter agreed transaction terms after the fact, and the protocol still accepts them as validly authorized.

### Finding Description
The KIP-249 typehashes are defined as: [1](#0-0) 

The base (v2.1) `EncodeData()` implementation for `Bid` only encodes `TargetTxHash, BlockNumber, Sender, To, Nonce, Bid, CallGasLimit, Data` — it omits `MaxGasPrice` entirely: [2](#0-1) 

Only the `bidV3` wrapper (selected when the on-chain entry point reports `AUCTION_VERSION == "0.0.2"`) includes `maxGasPrice` in the signed struct: [3](#0-2) 

`GetHashTypedData` picks the struct hash purely based on the `version` string, falling back to the v2.1 (no-maxGasPrice) hash for any unrecognized version: [4](#0-3) 

The `BidData` struct nonetheless carries a `MaxGasPrice` field that is present on the wire (RLP-encoded and part of the JSON bid payload) even when it's not part of the signed digest: [5](#0-4) 

Critically, the auctioneer's signature does not commit to the bid contents either — it is computed over the raw bytes of the searcher's signature, not over the bid struct itself: [6](#0-5) 

Bid admission in the bid pool (reachable from any bidder/relay via the permissionless `auction_submitBid` API or p2p bid propagation) validates only block-number range, non-zero bid amount, size/gas limits, and the two signatures — it never independently binds `MaxGasPrice` to anything cryptographically committed by the searcher when the entry point is on v2.1: [7](#0-6) 

Because the searcher's EIP-712 signature (`ValidateSearcherSig`) is checked against a digest that excludes `MaxGasPrice` for v2.1 entry points, and the auctioneer's signature (`ValidateAuctioneerSig`) is checked only against the searcher's signature bytes (not the bid fields), an attacker who has captured one valid signed bid can replay it with a modified `MaxGasPrice`, and both signature checks will still pass. This is functionally identical to the Cooler pattern where a counterparty can unilaterally rewrite loan terms (interest/duration/LTV) post-agreement while the underlying "roll" mechanism still treats the modified terms as authorized.

### Impact Explanation
`MaxGasPrice` is intended to cap/gate gas-price-related payment terms for the winning bid transaction (the field exists specifically to protect a party from being charged based on unauthorized gas price values; it's referenced downstream in `blockchain/system/auction.go` and `kaiax/auction/impl/api.go`, which this investigation could not fully trace to completion). If it can be forged independent of the searcher's actual authorization, a malicious bidder, relay, or anyone able to intercept/observe the bid (submitted over the public `auction_submitBid` RPC or gossiped over p2p) can:
- Resubmit the bid with an inflated or deflated `MaxGasPrice` that the original searcher never agreed to, altering the economic terms of gas payment/refund for the auction settlement.
- Potentially manipulate which bid wins or how gas is charged/refunded for the winning bid transaction, since the bid pool logic does not re-derive an independently-committed `MaxGasPrice`.

This constitutes unauthorized alteration of agreed transaction terms and possible fee/gas abuse in the auction settlement path — directly matching the "concrete... fee or fee-delegation abuse... auction settlement theft" acceptance criteria.

### Likelihood Explanation
Likelihood is high on any deployment where the `AuctionEntryPoint` contract reports `AUCTION_VERSION` other than `"0.0.2"` (i.e., any v2.1/legacy entry point, or any unrecognized version string, which falls back to the v2.1 typehash per `GetHashTypedData`). No special privilege is required — the bid tampering is reachable purely by observing/replaying a signed bid through the standard `auction_submitBid` RPC endpoint or the bid-pool's p2p `HandleBid` path.

### Recommendation
- Always include `MaxGasPrice` (defaulting to zero when unset) in the EIP-712 struct hash for every auction version, so the searcher's signature commits to it regardless of entry-point version.
- Have the auctioneer's signature commit to the full bid struct hash (or at minimum a hash including all bid fields) rather than solely to the searcher's raw signature bytes, preventing any field from being altered post-signature without invalidating the auctioneer's attestation as well.
- Reject bids where `MaxGasPrice` is present but not part of the verified digest for the resolved auction version.

### Proof of Concept
1. Deploy/observe an `AuctionEntryPoint` reporting `AUCTION_VERSION() == "0.0.1"` (or any version not equal to `"0.0.2"`), so `updateAuctionInfo`/`GetHashTypedData` resolve to the `auctionType` (v2.1) hash that excludes `maxGasPrice`.
2. Searcher signs and submits a legitimate bid with `MaxGasPrice = X` via `auction_submitBid`; the signed digest (per `Bid.EncodeData()`, `kaiax/auction/eip712.go:75-86`) does not include `X`.
3. Auctioneer validates and co-signs, producing `AuctioneerSig = sign(hashEthSignedMessage(SearcherSig))` (`kaiax/auction/bid.go:52-55`) — again not covering `MaxGasPrice`.
4. An attacker observing this `(SearcherSig, AuctioneerSig)` pair constructs a new `Bid` object identical in every signed field but with `MaxGasPrice = Y` (arbitrary), reusing the same `SearcherSig` and `AuctioneerSig`.
5. Submit this modified bid via `auction_submitBid` (or p2p `HandleBid`); `bp.validateBidSigs` (`kaiax/auction/impl/bid_pool.go:397-419`) calls `ValidateSearcherSig` and `ValidateAuctioneerSig`, both of which pass because neither digest depends on `MaxGasPrice`.
6. The bid pool accepts and processes the bid with the attacker-chosen `MaxGasPrice`, achieving unauthorized modification of bid terms without the searcher's consent.

Note: full confirmation of the downstream consumption of `MaxGasPrice` (e.g., in `blockchain/system/auction.go` / `kaiax/auction/impl/api.go`) to precisely quantify financial impact could not be completed within this investigation; the structural signature-exclusion flaw itself is confirmed directly from the cited source.

// GetHashTypedData returns the EIP-712 digest for the bid.
// version must match the on-chain AUCTION_VERSION of the entry-point contract
// the bid targets; "0.0.2" selects the v3.0 struct typehash (with maxGasPrice),
// any other value falls back to the v2.1 typehash.
func (b *Bid) GetHashTypedData(chainId *big.Int, verifyingContract common.Address, version string) []byte {
	if chainId == nil {
		return nil
	}

	domain := EIP712Domain{
		EIP712DomainTypeHash: eip712TypeHash,
		NameHash:             auctionNameHash,
		VersionHash:          crypto.Keccak256Hash([]byte(version)),
		ChainId:              chainId,
		VerifyingContract:    verifyingContract,
	}

	domainSeparator := EncodeEIP712(domain)

	var structHash []byte
	if version == AuctionVersionV3 {
		structHash = EncodeEIP712(bidV3{b})
	} else if version == AuctionVersionV2 {
		structHash = EncodeEIP712(b)
	} else {
		// Unknown version: default to v2.1 typehash.
		structHash = EncodeEIP712(b)
	}

	return crypto.Keccak256([]byte{0x19, 0x01}, domainSeparator, structHash)
}

func (bp *BidPool) validateBid(bid *auction.Bid) error {
	blockNumber := bid.BlockNumber

	bp.bidMu.RLock()

	// Check if the auction tx is already in the pool.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		bp.bidMu.RUnlock()
		return auction.ErrBidAlreadyExists
	}

	// 1. The `bid.Sender` must not be in the winner list of the same block number if the new bid isn't equal to the previous bid.
	if bp.senderHasDifferentWinner(bid) {
		bp.bidMu.RUnlock()
		return auction.ErrBidSenderExists
	}
	bp.bidMu.RUnlock()

	curBlock := bp.Chain.CurrentBlock()
	if curBlock == nil {
		return auction.ErrBlockNotFound
	}

	// 2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
	curNum := curBlock.NumberU64()
	if blockNumber <= curNum || blockNumber > curNum+allowFutureBlock {
		return auction.ErrInvalidBlockNumber
	}

	// 3. The `bid.Bid` must be greater than 0.
	if bid.Bid.Sign() <= 0 {
		return auction.ErrZeroBid
	}

	// 4. The data size must be less than the maximum limit.
	if uint64(len(bid.Data)) > BidTxMaxDataSize {
		return auction.ErrExceedMaxDataSize
	}

	// 5. The gas limit must be less than the maximum limit.
	if bid.CallGasLimit > BidTxMaxCallGasLimit {
		return auction.ErrExceedMaxCallGasLimit
	}

	// 6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.
	if err := bp.validateBidSigs(bid); err != nil {
		return err
	}

	return nil
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
