### Title
Unchecked payment-sum overflow bypasses the funds check, producing an invalid transaction and a panicking `fee()` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` verifies affordability with `if input_sat < (payment_sat + needed_fee)`, where `payment_sat` is the raw `u64` sum of attacker-influenced payment amounts. Each payment is only checked to be `>= DUST`; nothing bounds their sum or the `payment_sat + needed_fee` addition. In a release build the addition wraps, bypassing the `NotEnoughFunds` check; the resulting `SignableTransaction` has `sum(outputs) > sum(inputs)`, and `fee()` later performs a raw subtraction that underflows/panics. This is the same bug class as the Merit Circle finding: an unenforced ordering/monotonicity-style invariant (`sum(outputs) <= sum(inputs)`) leading to unchecked-arithmetic failure.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- Line 165-169: each payment amount is checked only against `DUST`; there is no per-payment or aggregate upper bound.
- Line 187: `payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>()` — the sum itself can overflow `u64` (panic in debug, wrap in release).
- Line 215: `if input_sat < (payment_sat + needed_fee)` — `payment_sat + needed_fee` can wrap to a small value, defeating the check even when `payment_sat` legitimately fits.
- Line 139-141: `fee()` computes `sum(prevouts) - sum(outputs)` with a plain `-`, so once an over-spending `SignableTransaction` exists, calling `fee()` underflows.

```rust
// send.rs:215
if input_sat < (payment_sat + needed_fee) {
  Err(TransactionError::NotEnoughFunds { ... })?;
}
// send.rs:139-141
self.prevouts.iter().map(|prevout| prevout.value.to_sat()).sum::<u64>() -
  self.tx.output.iter().map(|prevout| prevout.value.to_sat()).sum::<u64>()
```

`payments` are ultimately driven by user-supplied burn/out-instruction amounts, so an unprivileged party can craft payment amounts (e.g., two payments near `u64::MAX / 2`, each `>= DUST = 546`) that overflow the aggregate check.

### Impact Explanation
Either a panic/DoS (debug build, or via the underflowing `fee()` / overflowing `sum`) halting transaction construction, or — in release — a `SignableTransaction` authorizing `outputs > inputs`. The multisig would then be asked to sign a transaction that can never be valid on-chain; `fee()` reports a wrapped garbage value, and the associated inputs/plan are stuck, constituting funds that cannot be spent as intended.

### Likelihood Explanation
Triggerable purely by choosing large payment amounts in the instructions that feed `SignableTransaction::new`; no privileged position is required. Each individual amount passes the `DUST` bound, and only the *aggregate* is unchecked.

### Recommendation
Use checked arithmetic throughout: accumulate `payment_sat` with `checked_add`/`try_fold`, and replace `input_sat < payment_sat + needed_fee` with `payment_sat.checked_add(needed_fee).map_or(true, |t| input_sat < t)`. Make `fee()` use `checked_sub` and return an error/`Option` rather than underflowing.

### Proof of Concept
```rust
let payments = [
  (any_script.clone(), u64::MAX / 2 + 1), // >= DUST
  (any_script.clone(), u64::MAX / 2 + 1), // >= DUST
];
// payment_sat + needed_fee wraps in release -> NotEnoughFunds check bypassed
let tx = SignableTransaction::new(vec![small_input], &payments, None, None, fee_per_vbyte)?;
// tx.fee() underflows; tx is invalid (outputs > inputs)
```

Note: I verified the arithmetic paths in `send.rs` directly; the debug-vs-release behavior of the overflow was inferred from standard Rust semantics rather than from build-flag configuration in the repo.
