### Title
Denial of service via duplicate participant indexes causing a zero denominator in Lagrange interpolation - (File: crypto/dkg/src/lib.rs)

### Summary
The source report is a division-by-zero DoS: `share` is computed as a quotient whose denominator (`totalSupplyYsCvgHistories[cycleClaimed]`) can be zero, reverting the call. Serai's in-scope analog is the Lagrange coefficient routine in the DKG/FROST stack: `lagrange` (defined in `crypto/dkg/src/lib.rs`) computes a product denominator over pairwise differences of participant indexes `(l - i)` and then calls `.invert().unwrap()` on that field element. If the `indexes`/`included` set passed by the caller contains a duplicate index, the denominator product is zero, the field inversion returns `None`, and `.unwrap()` panics — crashing the signing/verifying process.



### Finding Description
`lagrange` in `crypto/dkg/src/lib.rs` evaluates:

- `numerator *= F::from(l)` for every `l != i`
- `denominator *= F::from(l - i)` (negated when `l < i`)
- returns `numerator * denominator.invert().unwrap()`

The denominator is zero iff two indexes in the set are equal (`l - i == 0` once `i` iterates to the duplicate). This function is reached from every threshold operation that consumes an `included: &[u16]` participant list: `ThresholdKeys::new` / `ThresholdView` construction and FROST `sign` / `verify` / `complete` paths in `crypto/frost/src/sign.rs` and `crypto/frost/src/algorithm.rs` compute Lagrange coefficients over the signer-provided inclusion set. The indexes are attacker-influenced public inputs — in PedPoP/FROST signing flows, the inclusion set enumerates which peers participate, and a participant index list containing a duplicate (e.g., `[1, 2, 2]`) reaches `lagrange` without a prior strict-distinctness check. The only validation performed is a zero/bounds sanity (`i != 0`, `i <= n`); duplicates are not rejected before the inversion.



### Impact Explanation
A malformed inclusion set containing a duplicate index turns `denominator.invert().unwrap()` into an unconditional panic. Any verifier or signer that processes a share/proof/signature whose participant list embeds a duplicate index crashes. This is a denial of service against the node processing the message — matching the source report's class (unrecoverable failure on a division-by-zero path) — and affects every code path that aggregates or verifies threshold material: DKG share verification, `ThresholdView::sign`/`verify`, and key aggregation that interpolates `group_key` from `verification_shares` over participants `1..=t`. No secret material is required; the trigger is purely the public index list.

### Likelihood Explanation
Reaching the panic requires only that an inclusion/participant index list with a duplicate element be fed to a Lagrange evaluation. Participant index sets originate from remote coordinators/peers in the DKG and signing protocols; a single malicious or malfunctioning peer (or a crafted signing request where the `included` set is derived from attacker-controlled signatory enumeration) can supply `[a, ..., a]`. Because the check that would catch this (strict sortedness / pairwise distinctness of `included`) is absent at the `lagrange` boundary, the panic is deterministic whenever such input arrives. This is a crash-only (liveness) bug, hence Medium rather than High: no key, share, or forgery results, but the affected process aborts mid-protocol, which in a threshold network can stall signing rounds and force restart/recovery.

### Recommendation
Enforce strictness on the index set before interpolation, mirroring the report's `require(denominator > 0)` remediation:

- In `crypto/dkg/src/lib.rs` `lagrange`, return `Option<F>` / `Result` and propagate failure instead of `.unwrap()` on `invert()`, or debug/release-assert `denominator != 0` with a graceful error.
- In the callers that accept `included: &[u16]` (`ThresholdKeys::new`, `ThresholdView`/`sign`/`verify` in `crypto/frost`), validate that indexes are strictly increasing (or dedup-and-compare length) and reject duplicates, zero, and `> n` values before any interpolation — e.g., `included.windows(2).all(|w| w[0] < w[1])`.

### Proof of Concept
Conceptually, in the crate context (`C: Ciphersuite`):

```rust
// indexes containing a duplicate -> denominator contains factor (2 - 2) = 0
let dup_indexes = [1u16, 2, 2];
let _ = lagrange::<C::F>(1, &dup_indexes); // panics at denominator.invert().unwrap()
```

Equivalently at the protocol layer, construct a `ThresholdView`/signing session whose `included` list is `[1, 2, 2]` (with `t = 2`, `n >= 2`); the first Lagrange coefficient evaluation for `i = 1` multiplies the denominator by `F::from(2 - 2) = 0`, making the whole product zero, and `.invert().unwrap()` panics, aborting the signing process.
