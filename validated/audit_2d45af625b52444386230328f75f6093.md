Based on the investigation, I found a structurally similar issue in `sei-chain`'s block-gas admission check, which mirrors the Rubicon `ReserveRatio` pattern: a security invariant (total gas consumed by a proposed block must stay within `ConsensusParams.Block.MaxGas`) is enforced using a value that is *not* the actual outcome of execution, and is never re-validated against the real, post-execution outcome.

### Title
Block gas-limit admission relies on an unverified, self-reported `GasEstimate` instead of enforcing the real `MaxGas` bound - (File: app/app.go)

### Summary
`app.checkTotalBlockGas` (used during `ProcessProposal`) is the invariant that is supposed to guarantee `(sum of GasUsed in a block) <= ConsensusParams.Block.MaxGas`, exactly as required by the ABCI spec cited in the repo's own documentation. For EVM transactions it substitutes `decodedTx.GetGasEstimate()` for `gasWanted` whenever the estimate is `>= MinGasEVMTx` and `<= gasWanted`, and never reconciles this pre-execution number against the transaction's actual `GasUsed` once the block is executed. [1](#0-0) 

### Finding Description
`checkTotalBlockGas` accumulates two counters while iterating proposed transactions: `totalGasWanted` (bounded by `MaxGasWanted`) and `totalGas` (bounded by `MaxGas`). For an EVM transaction, instead of always using the transaction's declared gas limit (`etx.Gas()`), the function prefers the tx's `GasEstimate` field for the `MaxGas` accounting whenever it looks "plausible" (`>= MinGasEVMTx && <= gasWanted`): [2](#0-1) 

This `GasEstimate` is a field carried on the Cosmos `sdk.Tx`/`GasInfo` envelope (`GasEstimate uint64` in `GasInfo`) that is attached when the transaction is built/submitted, not computed by consensus-verified execution of that specific transaction at proposal time. [3](#0-2) 

The ante pipeline itself treats this field as an untrusted hint, only using it if it's `>= MinGasEVMTx`, and otherwise falling back to the full gas-meter limit — evidence that it is not independently verified against the transaction's actual gas cost before being trusted elsewhere in the system: [4](#0-3) 

Because `checkTotalBlockGas` is only invoked as a proposal-time gate (`ProcessProposal`), a block whose EVM transactions declare a low `GasEstimate` (just above `MinGasEVMTx`) while carrying a large `GasLimit`/`gasWanted` and executing gas-heavy logic can pass the `MaxGas` check using the deflated estimate sum, yet during `FinalizeBlock` the transactions can consume real EVM gas far closer to their declared `gasWanted` — the invariant that was checked before proposal is never re-validated against the real `GasUsed` after execution, exactly matching the Rubicon `enforceReserveRatio` pattern of "check once before, never re-check after the state-changing operation actually runs."

The ABCI spec excerpt embedded in the repo makes explicit that the application (not Tendermint) is responsible for guaranteeing `(sum of GasUsed in a block) <= MaxGas`: [5](#0-4) 

### Impact Explanation
If the true per-block gas budget (`MaxGas`) can be circumvented by supplying a favorable (low) `GasEstimate` while the transaction's actual EVM execution burns a much larger amount of real gas (up to `gasWanted`), validators can be made to accept and execute blocks whose real computational cost exceeds the configured `MaxGas` safety bound. This directly threatens the guarantee that block execution time stays bounded, and can push block processing time beyond the intended interval (the rules explicitly list "block delay beyond 2.5 seconds" as an accepted impact), since the entire purpose of `MaxGas` is to cap per-block EVM execution cost/time deterministically across all validators.

### Likelihood Explanation
The attack path only requires an unprivileged EVM transaction sender: submit an ordinary signed EVM transaction (reachable via public RPC / the normal transaction submission path) with a `gasWanted`/`GasLimit` large enough to run expensive EVM logic, while the accompanying `GasEstimate` value on the outer Cosmos envelope is deflated to just above `MinGasEVMTx` (21000). Multiple such transactions, or a proposer including many of them, can accumulate real execution cost far beyond what `checkTotalBlockGas` accounted for at proposal time, with no code path found that re-validates `totalGas` against the block's actual `GasUsed` sum after `FinalizeBlock`.

### Recommendation
Do not trust a self-reported `GasEstimate` for the hard `MaxGas` admission check. Either (a) always account EVM transactions by their declared `gasWanted`/`GasLimit` for `MaxGas` purposes (matching the `MaxGasWanted` treatment), or (b) if an estimate-based fast path is kept for efficiency, add a post-execution reconciliation in `FinalizeBlock`/`EndBlock` that verifies cumulative real `GasUsed` for the block does not exceed `MaxGas`, and reject/fail the block (or the offending transactions) if it does — mirroring the Rubicon fix of re-checking the invariant after the state-changing operation completes, not only before it.

### Proof of Concept
Not independently executed; based on static analysis of `app.checkTotalBlockGas` and `x/evm/ante/gas.go`, illustrated by the existing repository test `TestCheckTotalBlockGas_GasEstimatePreferredOverGasWanted`, which itself demonstrates that three transactions each declaring `gasWanted=100_000` but `gasEstimate=21_000` are admitted under a `MaxGas=80_000` budget (which would reject them if `gasWanted` were used), showing the estimate-substitution logic that allows real potential gas usage to exceed the enforced cap: [6](#0-5) 

**Note on completeness:** I was not able to fully trace, within the available tool budget, the exact code path in `evmrpc/send.go` / mempool ingestion that originally sets/derives the `GasEstimate` field for a submitted raw transaction (i.e., whether it is computed via local `eth_estimateGas` simulation by the receiving node, and whether any node-local sanity check exists that would catch a mismatched estimate before it reaches `ProcessProposal`). This should be verified in a follow-up (e.g., via a Devin session with full repo access) before treating this as conclusively exploitable end-to-end.

```go
// checkTotalBlockGas checks that the block gas limit is not exceeded by our best estimate of
// the total gas by the txs in the block. The gas of a tx is either the gas estimate if it's an EVM tx,
// or the gas wanted if it's a Cosmos tx. typedTxs must align with proposal order (nil = decode failure).
func (app *App) checkTotalBlockGas(ctx sdk.Context, typedTxs []sdk.Tx) (_result bool) {
	defer func() {
		if r := recover(); r != nil {
			logger.Error("panic recovered in checkTotalBlockGas", "panic", r)
			_result = false
		}
	}()

	var totalGas, totalGasWanted uint64
	for _, decodedTx := range typedTxs {
		if decodedTx == nil {
			return false
		}

		isEVM, evmErr := evmante.IsEVMMessage(decodedTx)

		// EVM classification failed (e.g. multi-msg containing an EVM message); such a tx won't be
		// processed and so contributes no gas to the block.
		if evmErr != nil {
			continue
		}

		var gasWanted uint64
		if isEVM {
			msg := evmtypes.MustGetEVMTransactionMessage(decodedTx)
			if msg.IsAssociateTx() {
				continue
			}
			etx, _ := msg.AsTransaction()
			gasWanted = etx.Gas()
		} else {
			feeTx, ok := decodedTx.(sdk.FeeTx)
			if !ok {
				// Non-fee tx won't be processed and thus won't consume gas. Skipping.
				continue
			}
			gasWanted = feeTx.GetGas()
		}

		// Overflow guards: gasWanted must fit in int64, and adding it to either accumulator
		// must not wrap uint64.
		if int64(gasWanted) < 0 || //nolint:gosec
			totalGasWanted > math.MaxUint64-gasWanted ||
			totalGas > math.MaxUint64-gasWanted {
			return false
		}

		totalGasWanted += gasWanted

		// Prefer the gas estimate when it's a valid EVM estimate (>= MinGasEVMTx) and not
		// inflated above gasWanted; otherwise charge full gasWanted.
		if est := decodedTx.GetGasEstimate(); est >= MinGasEVMTx && est <= gasWanted {
			totalGas += est
		} else {
			totalGas += gasWanted
		}
```

```go
// Called at the end of the ante chain to set gas limit and gas used estimate properly
func (gl GasDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	msg := evmtypes.MustGetEVMTransactionMessage(tx)
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return ctx, err
	}

	txGas := txData.GetGas()
	if txGas > math.MaxInt64 {
		return ctx, errors.New("tx gas exceeds max")
	}
	adjustedGasLimit := gl.evmKeeper.GetPriorityNormalizer(ctx).MulInt64(int64(txGas)) //nolint:gosec
	gasMeter := sdk.NewGasMeterWithMultiplier(ctx, adjustedGasLimit.TruncateInt().Uint64())
	ctx = ctx.WithGasMeter(gasMeter)
	if tx.GetGasEstimate() >= MinGasEVMTx {
		ctx = ctx.WithGasEstimate(tx.GetGasEstimate())
	} else {
		ctx = ctx.WithGasEstimate(gasMeter.Limit())
	}
	return next(ctx, tx, simulate)
```

```markdown
In Tendermint, the [ConsensusParams.Block.MaxGas](#consensus-parameters) limits the amount of
total gas that can be used by all transactions in a block.
The default value is `-1`, which means the block gas limit is not enforced, or that the concept of
gas is meaningless.

Responses contain a `GasWanted` and `GasUsed` field. The former is the maximum
amount of gas the sender of a transaction is willing to use, and the latter is how much it actually
used. Applications should enforce that `GasUsed <= GasWanted` &mdash; i.e. transaction execution
or validation should fail before it can use more resources than it requested.

When `MaxGas > -1`, Tendermint enforces the following rules:

* `GasWanted <= MaxGas` for every transaction in the mempool
* `(sum of GasWanted in a block) <= MaxGas` when proposing a block

If `MaxGas == -1`, no rules about gas are enforced.

In v0.35.x and earlier versions, Tendermint does not enforce anything about Gas in consensus,
only in the mempool.
This means it does not guarantee that committed blocks satisfy these rules.
It is the application's responsibility to return non-zero response codes when gas limits are exceeded
when executing the transactions of a block.
Since the introduction of `PrepareProposal` and `ProcessProposal` in v.0.36.x, it is now possible
for the Application to enforce that all blocks proposed (and voted for) in consensus &mdash; and thus all
blocks decided &mdash; respect the `MaxGas` limits described above.

Since the Application should enforce that `GasUsed <= GasWanted` when executing a transaction, and
it can use `PrepareProposal` and `ProcessProposal` to enforce that `(sum of GasWanted in a block) <= MaxGas`
in all proposed or prevoted blocks,
we have:

* `(sum of GasUsed in a block) <= MaxGas` for every block
```
