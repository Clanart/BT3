### Title
Attacker-controlled `WWW-Authenticate` header spoofs a non-GitHub host as "GitHub Enterprise", triggering unauthorized OAuth account binding and credential exfiltration - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
Bug class from the report: a value that Desktop treats as "safe/authoritative" is actually attacker-influenced (there, a rounded-down swap amount driving `safeApprove`; here, a raw `WWW-Authenticate` HTTP header echoed by Git into the credential-helper protocol). In both cases the code trusts derived/external data without validating it against the real invariant, causing an unsafe downstream state transition. In Desktop, `getEndpointKind()` classifies an arbitrary remote as a GitHub Enterprise host purely by substring-matching a `wwwauth[]` field that comes straight from the server's HTTP response, and that classification drives whether GitHub Desktop prompts the user to sign in and later hands out stored GitHub tokens to that host.

### Finding Description
When Git performs an HTTP(S) operation against a remote and receives a `401` with a `WWW-Authenticate` header, it forwards that header verbatim to the configured credential helper as `wwwauth[]=...` fields [1](#0-0) . GitHub Desktop's trampoline credential helper uses this attacker-controlled value as a "happy path" to decide whether a host is GitHub: [2](#0-1) 

Any HTTP server the app talks to via a git remote (or a machine-in-the-middle/malicious proxy for that remote) can freely set `WWW-Authenticate: Basic realm="GitHub"` and get classified as `'enterprise'` — there is no TLS/cert binding, no call to `isGitHubHost()`, and no relation to the actual endpoint at all; it's a pure string match on server-supplied data.

That classification feeds `getCredential()`: [3](#0-2) 

If no existing account matches the spoofed endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, which opens the real GitHub/Enterprise sign-in dialog and, for non-`github.com` hosts, calls `dispatcher.beginEnterpriseSignIn` + `setSignInEndpoint(origin)` using the attacker's origin as the enterprise endpoint: [4](#0-3) 

If the user completes this flow (which looks like a normal "sign in to continue" prompt triggered by a legitimate-looking clone/fetch), a new `Account` is created and persisted with `endpoint` set to the attacker's host. From then on, every future git operation against that same origin will be matched by `findGitHubTrampolineAccount()` (which matches purely on URL origin equality) and will hand the account's OAuth token straight to that host via `getGitHubCredential()`: [5](#0-4) [6](#0-5) 

The Balancer bug and this one share the same root cause: a downstream security decision (allowance re-use / credential trust) is derived from a value the attacker fully controls (rounded swap amount / HTTP response header) instead of an independently verified invariant, and no cleanup/verification step exists to catch the mismatch.

### Impact Explanation
This matches the listed valid impact "unauthorized OAuth or account binding" and "credential/token exfiltration": a malicious or compromised git host/proxy can get a GitHub Desktop user to bind a new "Enterprise" account to an attacker-controlled origin, and can subsequently receive that account's GitHub token on every future git operation targeting the same origin (and, since `findGitHubTrampolineAccount` only checks origin equality, potentially any path under that origin). This is a credential leak driven purely by server-returned data during a normal clone/fetch/push, not by any local access or pre-existing compromise.

### Likelihood Explanation
The trigger requires only that the attacker control (or MITM) the HTTP server backing a git remote the user adds/clones/fetches from — well within the described threat model ("attacker controls...a git remote/proxy response"). No unnatural user action is required beyond completing what looks like a normal GitHub sign-in prompt that Desktop itself initiated. The `isGitHubHost()` network-verification path exists in the code but is only reached if there's no `wwwauth[]` match, so the substring shortcut fully bypasses the more careful check.

### Recommendation
Do not use the `wwwauth[]` realm string as a trust signal for classifying a host as GitHub/Enterprise. At minimum, treat it only as a hint to short-circuit to calling `isGitHubHost()` (i.e., always verify via the authenticated `/meta`-style discovery request or an already-known account) rather than returning `'enterprise'` directly. Additionally, before binding a new account, verify that the sign-in endpoint actually matches a discoverable GitHub API surface (as `isGitHubHost()` already does) rather than trusting client-observable protocol metadata that any HTTP server can emit.

### Proof of Concept
1. Attacker sets up an HTTP git server (or MITMs a plain-HTTP git remote) at `http://evil.example.com/repo.git`.
2. Victim adds/clones this remote in GitHub Desktop.
3. On authentication challenge, the server responds `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this as `wwwauth[]=...realm="GitHub"...` to Desktop's credential helper stdin.
5. `getEndpointKind()` returns `'enterprise'` for `evil.example.com` purely from the substring match [7](#0-6) .
6. `getCredential()` finds no matching account and calls `ui.promptForGitHubSignIn('http://evil.example.com/...')`, opening the enterprise sign-in dialog bound to that origin [8](#0-7) .
7. Victim signs in (PAT or browser OAuth) believing it's a legitimate prompt from a clone action; an `Account` is stored with `endpoint = http://evil.example.com`.
8. Any subsequent git operation to that origin now matches via `findGitHubTrampolineAccount` and Desktop supplies the stored token as the git credential, sending it to the attacker's server.

Note: I was not able to independently verify additional caller-side safeguards (e.g., any endpoint allow-list enforced elsewhere in `AccountsStore.addAccount` or `SignInStore`) beyond what's shown here; a full audit of `sign-in-store.ts`'s account-persistence path is recommended to confirm no other check blocks binding accounts to arbitrary HTTP origins.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
