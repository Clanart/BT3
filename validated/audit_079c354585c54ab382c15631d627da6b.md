### Title
Attacker-controlled participant count causes oversized allocation during threshold-key deserialization - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts the serialized `n` participant count and immediately allocates an interpolation-coefficient vector with `n` elements when the interpolation tag selects `Interpolation::Constant`. A very small untrusted input can therefore request a 65,535-element allocation before the supplied bytes are otherwise validated.

### Finding Description
The deserializer reads `t`, `n`, and `i` directly from attacker-controlled bytes. [1](#0-0)  If the next byte is `0`, it executes `Vec::with_capacity(usize::from(n))` before validating `ThresholdParams` or determining whether the input actually contains the corresponding scalar data. [2](#0-1)  Since `n` is a `u16`, a two-byte value can request capacity for as many as 65,535 field elements. [3](#0-2) 

The parameter checks that reject zero parameters, `t > n`, or `i > n` occur only after this allocation and subsequent parsing work. [4](#0-3)  Thus, even a malformed or truncated payload can trigger the allocation and then fail while reading the first scalar.

### Impact Explanation
An unprivileged party that can submit bytes to `ThresholdKeys::read` can force repeated large allocations using only a small request for each call. This is uncontrolled resource consumption: the allocation size is derived from a serialized count rather than an external protocol bound or the actual payload size.

Although each request is bounded by the `u16` representation, the amplification is substantial because a handful of bytes can allocate a vector with 65,535 elements. Repeated calls can create allocator pressure and degrade availability of the process handling the untrusted keys.

### Likelihood Explanation
The input format gives the attacker direct control of `n`, and choosing `t = 1`, `n = 65535`, `i = 1`, and constant interpolation reaches the vulnerable allocation path. `ThresholdParams::new` would accept those values if reached because `i` is a non-zero participant and does not exceed `n`. [5](#0-4)  No malformed scalar or point payload is needed to cause the allocation.

### Recommendation
Validate `t`, `n`, and `i` with `ThresholdParams::new` before allocating or parsing variable-sized structures. Also impose a protocol-defined maximum participant count where one exists, and avoid `Vec::with_capacity(n)` for attacker-controlled `n`; incrementally parse the required elements instead.

### Proof of Concept
```rust
// crypto/dkg/src/lib.rs deserialization format.
// Requires a valid C::ID for the instantiated ciphersuite.

let mut input = Vec::new();

// Curve identifier length and identifier.
input.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
input.extend(C::ID);

// t = 1, n = 65535, i = 1.
input.extend(1u16.to_le_bytes());
input.extend(u16::MAX.to_le_bytes());
input.extend(1u16.to_le_bytes());

// Select Interpolation::Constant, then provide no scalar bytes.
input.push(0);

// This allocates Vec::with_capacity(65535) before failing on C::read_F.
assert!(ThresholdKeys::<C>::read(&mut input.as_slice()).is_err());
```
