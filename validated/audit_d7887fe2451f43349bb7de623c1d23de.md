## Title
Partial-commit line selection is applied against a re-fetched diff, letting working-tree content changed after review get silently committed - (File: `app/src/lib/git/apply.ts`, `app/src/lib/git/update-index.ts`)

### Summary
GitHub Desktop lets a user select individual lines/hunks of a file to include in a commit ("partial commit"). The line selection (`DiffSelection`) is a set of *line indices* computed against the diff that was rendered in the UI at selection time. When the commit actually runs, `stageFiles` calls `applyPatchToIndex` for every partially-selected file, and that function re-invokes `getWorkingDirectoryDiff` to fetch a brand-new diff of the file, then applies the user's old line-index selection to this newly-fetched diff via `formatPatch`. [1](#0-0) [2](#0-1) 

This mirrors the reported bug class: state (the patch to be applied/committed) is derived from data (a fresh diff) that is different from — and generated after — the state the user actually reviewed and approved (the old diff/selection), instead of consistently using one converted/validated snapshot. In the original Solidity report the storage got updated from data produced during an intermediate conversion step rather than the values validated at the top of `_redeem`; here the commit's patch content is derived from a diff fetched at apply-time rather than the diff the selection indices were computed against.

### Finding Description
1. The user opens a file's diff in the Changes view; `_changeFileSelection`/diff rendering calls `getWorkingDirectoryDiff` and the UI displays hunks/lines with indices. [3](#0-2) 
2. The user selects a subset of lines to include (`DiffSelection.withRangeSelection`), which stores selection state purely as absolute line indices into that diff — it has no cryptographic or content binding to the diff it was created from. [4](#0-3) 
3. When the user clicks "Commit", `_commitIncludedChanges` passes the selected `WorkingDirectoryFileChange` objects (which carry only the stale `DiffSelection`, not the diff itself) straight into `createCommit`. [5](#0-4) 
4. `createCommit` → `stageFiles` → for any file with a partial selection, `applyPatchToIndex` is invoked, which calls `getWorkingDirectoryDiff` again — re-running `git diff` against the *current* on-disk content of the file — and then builds a patch (`formatPatch`) by testing `file.selection.isSelected(absoluteIndex)` against this newly fetched diff's line indices. [6](#0-5) [7](#0-6) 

If the file's on-disk content changes between the moment the user reviewed/selected lines and the moment the commit executes — e.g., a Git `clean`/`smudge` filter defined in a cloned repository's `.gitattributes` (attacker-controlled, since `.gitattributes` and `.git/config` filter definitions come from the fetched/cloned repository or a hostile checkout), a build tool, a background formatter, or another process writing to the working tree — the hunk boundaries and line numbering of the newly fetched diff can differ from the diff the indices were originally computed against. `formatPatch` will then select/deselect lines that do **not** correspond to what the user actually saw and approved, because it blindly maps old absolute indices onto a different hunk layout.

None of the "before/after" staleness guards used elsewhere in the store (e.g., `updateChangesWorkingDirectoryDiff`, `updateChangesStashDiff`, which explicitly re-check `stateAfterLoad` against `stateBeforeLoad` before writing) are applied to the commit path — `_commitIncludedChanges` does not re-verify that the diff used to build the patch matches the diff the selection was made against. [8](#0-7) [9](#0-8) 

### Impact Explanation
This is a "silent corruption of what the user commits/pushes" scenario, an explicitly valid impact class: content the user never reviewed (added by an attacker-controlled clean/smudge filter, or lines shifted by any tree modification between diff-render and commit) can be silently included in a commit that the user believes only contains the lines they selected. Because commits are then typically pushed, this can smuggle attacker-influenced content into a pushed history/branch without any visible warning, undermining the "review before commit" trust model that partial-commit selection exists to provide.

### Likelihood Explanation
The attacker needs to control content of a cloned/fetched repository (e.g. `.gitattributes` + filter config, or any mechanism that mutates tracked files after checkout but before the user commits) — this fits the allowed "attacker controls a cloned/fetched repository" primitive. The race window is real: partial-commit UI flows in Desktop routinely have measurable gaps between diff render (`getWorkingDirectoryDiff`) and commit-time re-diff (`applyPatchToIndex`'s inner `getWorkingDirectoryDiff` call), since committing is a distinct user action performed after reviewing/selecting lines, and Desktop does not lock the working tree or re-validate the diff for staleness in that path.

### Recommendation
`applyPatchToIndex`/`stageFiles` should not silently re-fetch a new diff for partial selections at commit time. Instead:
- Retain and reuse the exact diff object the selection was computed against (or a content hash/version) through the entire commit path, from `_changeFileSelection`/`updateChangesWorkingDirectoryDiff` down to `applyPatchToIndex`.
- Before applying the patch, verify the file's current content/hash still matches what was diffed; if not, abort the commit for that file and force the user to re-review, mirroring the "stateBeforeLoad"/"stateAfterLoad" staleness pattern already used elsewhere in `app-store.ts`.

### Proof of Concept
Conceptual PoC (requires validating locally, since this analysis is based on static code reading rather than a running repro):
1. Clone/checkout a malicious repository containing a `.gitattributes` rule with a `clean` filter script that appends/reorders lines in a tracked file whenever `git diff`/`git add` reads it.
2. In Desktop, open the file, view its diff, and select only specific lines/hunks for a partial commit.
3. Trigger the commit. `stageFiles` invokes `applyPatchToIndex`, which re-runs `getWorkingDirectoryDiff` — this second `git diff` invocation re-triggers the clean filter, altering hunk layout/line numbers relative to what the user reviewed.
4. `formatPatch` maps the user's old absolute-index selection onto the new hunk layout, potentially including filter-injected or shifted content that was never shown to or approved by the user in the resulting commit.

Because I could not execute Desktop interactively in this environment, step 3/4 behavior (exact patch mis-mapping) is based on static analysis of `applyPatchToIndex`, `formatPatch`, and `DiffSelection.isSelected` rather than an observed runtime repro; a background Devin session with terminal/Electron access would be needed to confirm the exact patch divergence with a concrete `.gitattributes` filter payload.
