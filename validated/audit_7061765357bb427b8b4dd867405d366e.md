Based on the investigation, the strongest analog in this codebase to the "untrusted external object corrupts a trust boundary and blocks/exfiltrates user assets" bug class is the re-enablement of Git's `file://` submodule transport during automatic submodule initialization.

### Title
Automatic submodule initialization re-enables `file://` transport, allowing a malicious repository to exfiltrate local files into the user's working tree - (File: `app/src/lib/git/submodule.ts`)

### Summary
Modern Git disables the `file://` transport for submodule clones by default (a hardening added upstream after CVE-2022-39253, which allowed malicious repositories to smuggle a victim's local files into a cloned repo via a `.gitmodules` entry pointing at a `file://` path). GitHub Desktop's submodule-update helper explicitly re-enables this transport via `-c protocol.file.allow=always` whenever `allowFileProtocol` is `true`, and this flag is not derived from any validation of the submodule's actual origin.

### Finding Description
`updateSubmodulesAfterOperation` builds its `git submodule update --init --recursive` invocation with `protocol.file.allow=always` injected whenever the caller passes `allowFileProtocol: true`: [1](#0-0) 

This function is invoked from both `checkoutBranch` and `checkoutCommit`, which each accept an `allowFileProtocol` parameter (default `false`) and forward it unchanged to the submodule step: [2](#0-1) [3](#0-2) 

The project's own test suite demonstrates the intended production use case — automatically initializing a previously-uninitialized submodule discovered on branch checkout — by calling `checkoutBranch(..., true)`: [4](#0-3) 

The broken invariant: once `allowFileProtocol` is `true`, Git will honor *any* submodule URL scheme committed to `.gitmodules` by the (attacker-controlled) upstream repository, including `file:///Users/<user>/.ssh` or other sensitive local paths. Git's local-clone codepath for `file://` performs the equivalent of a local checkout of that path's contents into the submodule directory inside the user's repository working tree — content that did not come from the remote at all, but from the local filesystem. This is the same accounting-mismatch pattern described in the report: the system trusts an external, attacker-supplied declaration (a token address in the ERC-20 report; a submodule URL here) without verifying it behaves within expected bounds, and the consequence surfaces later as corrupted/leaked state that the user unknowingly commits and pushes.

### Impact Explanation
If this flag is ever exercised on a path that processes a repository not fully trusted by the user (e.g., automatically initializing a submodule discovered while checking out a branch from a cloned/forked/PR-sourced repository), a malicious `.gitmodules` entry can direct Git to copy arbitrary local file-system content (SSH keys, config files, other repositories) into the working directory. Because this happens as ordinary submodule content, GitHub Desktop's UI will present it as new/changed files like any other checkout, and an unsuspecting user could stage, commit, and push it — resulting in credential/secret exfiltration to whatever remote the repository points at. This matches the accepted impact categories: "attacker controls a cloned/fetched repository ... and the result is ... credential/token exfiltration ... or silent corruption of what the user commits or pushes."

### Likelihood Explanation
The regular interactive branch-switch path (`checkoutIgnoringChanges` and friends in `app-store.ts`) calls `checkoutBranch` without an explicit `allowFileProtocol` argument, so it defaults to `false` — safe. However, the codebase clearly has a supported flow (validated by its own test) that passes `true` for the case of initializing a submodule discovered on checkout. I was not able to fully trace, within the tool-call budget available, every production call site in `app-store.ts` that determines when `true` is passed versus relying on the safe default, so I cannot confirm with certainty that an untrusted/attacker-supplied repository can reach the `true` branch without any additional gating (e.g., a prior explicit user confirmation). This is the key open question a deeper audit of `app-store.ts`'s checkout/submodule-initialization logic would need to resolve.

### Recommendation
1. Never pass `allowFileProtocol: true` for submodules whose parent repository was cloned/fetched from a remote (as opposed to a fully local, developer-trusted repository). At minimum, restrict this to repositories where the submodule URL's origin matches the parent's remote host, or require explicit user confirmation before allowing `file://` submodule fetches.
2. Validate `.gitmodules` submodule URLs and reject non-network schemes (`file://`, `ext::`, etc.) by default, consistent with Git's own default posture post-CVE-2022-39253.
3. Add regression tests asserting that submodule initialization triggered by checking out branches from a cloned/remote repository never re-enables `protocol.file.allow`.

### Proof of Concept
1. Attacker publishes a public repository containing a branch whose `.gitmodules` declares a submodule with `url = file:///Users/victim/.ssh` (or an OS-appropriate sensitive path).
2. Victim clones or opens this repository in GitHub Desktop and switches to that branch, triggering the app's submodule-initialization logic for the newly-discovered, uninitialized submodule.
3. If that code path (mirrored by the test in `app/test/unit/git/checkout-test.ts:150-189`) invokes `checkoutBranch(..., true)`, `updateSubmodulesAfterOperation` executes `git -c protocol.file.allow=always submodule update --init --recursive`, causing Git to copy the contents of `/Users/victim/.ssh` into the repository's working directory as the submodule.
4. The victim, seeing new files in the working directory, commits and pushes, exfiltrating their SSH keys to the attacker's remote.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
