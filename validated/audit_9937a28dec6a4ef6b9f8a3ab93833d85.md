### Title
`Scanner::register_offset` increments into another party's offset, so their deposits are attributed to the wrong scalar - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to `enlistInRollover()` writing a stale/wrong queue index so one user's update lands on another user's entry, `Scanner` keys deposit attribution solely by `script_pubkey` while `register_offset` silently slides a requested offset forward (`offset += Scalar::ONE`) until the tweaked key has even Y. Two distinct requested offsets can therefore resolve to the same script, and whichever registration runs first claims the script→offset mapping; every later deposit to that script is reported as a `ReceivedOutput` carrying the *first* registrant's offset.

### Finding Description
`Scanner` stores `scripts: HashMap<ScriptBuf, Scalar>` (`mod.rs:155`). `register_offset` loops, incrementing `offset` until `p2tr_script_buf(key + G*offset)` is `Some` (even-Y Taproot key), then inserts `script -> offset` unless the script is already present, in which case it returns `None` (`mod.rs:180-196`). `scan_transaction` attributes any output whose `script_pubkey` is in the map to the stored `offset` (`mod.rs:205-211`).

Because the increment is internal, the *requested* offset and the *recorded* offset differ whenever the requested point is odd. An attacker who knows the victim's deterministic offset derivation can choose a requested offset `o` such that `key + G*o`, `key + G*(o+1)`, … are odd until exactly the victim's offset `v = o + k` produces an even key. Registering `o` first stores `script_v -> v` under the attacker's registration. When the victim later registers `v`, `register_offset` returns `None` (script already present). Meanwhile any output the victim already published to the address derived from `v` is scanned and reported as `ReceivedOutput { offset: v, .. }` — a slot the attacker claimed first. This mirrors the report: the index (script key) is written/looked-up in a way that binds one party's entry to another party's slot.

### Impact Explanation
Deposit attribution is wrong-party: outputs are reported with an offset that belongs to a different logical registration. In the Serai flow, the offset identifies which Serai address a deposit belongs to, so a victim deposit can be credited under a key/registration an attacker occupied first, or the victim's registration can be permanently refused (`None`) while funds sent to the derived script still scan — funds reported received under an offset the depositor did not register. That satisfies "funds reported received that are not spendable" by the intended party and is reachable with purely public inputs: the attacker only needs the (public, deterministic) offset-derivation function and to send/register first.

### Likelihood Explanation
Requires the attacker to front-run the victim's `register_offset` call and to compute a request offset whose odd-Y chain lands on the victim's offset — feasible since parity is ~50% per step and the derivation is public. The window is the ordering of registrations, which the attacker can influence in any registration scheme that processes requests in received order.

### Recommendation
Make `register_offset` collision-safe for the recorded value: derive the script from the offset actually assigned, but additionally reject (or key accounting by) the *requested* offset — e.g., store `requested_offset -> used_offset` and have `scan_transaction` report the requested offset, or document/enforce that callers must verify the returned offset equals the intended one before publishing a deposit address, so a deposit is never published to a script that a prior registration can claim.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs semantics
let mut scanner = Scanner::new(key).unwrap();

// Victim's deterministic offset v (publicly derivable).
// Attacker picks o < v such that key + G*o ... key + G*(v-1) are odd-Y
// and key + G*v is even-Y.
assert_eq!(scanner.register_offset(o), Some(v)); // claims script_v -> v

// Victim's own registration is refused:
assert_eq!(scanner.register_offset(v), None);

// Victim already deposited to the address derived from v:
let outputs = scanner.scan_transaction(&victim_deposit_tx);
// outputs[0].offset() == v — attributed to the slot the attacker claimed,
// not to a registration the victim controls.
```

Caveat: whether mis-attribution translates into mis-crediting of user accounts depends on the out-of-scope processor's use of `ReceivedOutput::offset()`; within the in-scope code the demonstrated defect is that script attribution binds to the wrong registration entry, which is the direct analog of the report's wrong-index queue corruption.
