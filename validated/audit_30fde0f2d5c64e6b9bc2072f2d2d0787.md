### Title
Direct token transfers to `MasterMagpie` inflate `BaseRewardPool.totalStaked()`, permanently diluting/freezing reward distribution - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`)

### Summary
`BaseRewardPool`/`BaseRewardPoolV2` compute the reward-distribution denominator `totalStaked()` from the **real** ERC20 balance of the staking token held by `MasterMagpie` (the `operator`), while individual staker balances (`balanceOf(_account)`) are derived from `MasterMagpie`'s **internal** `stakingInfo` accounting. Any unprivileged wallet can directly transfer the staking token to the `MasterMagpie` contract, inflating the real balance without updating any user's internal stake record, exactly mirroring the root cause described in the external report (real-balance source used for one side of a calculation, internal tracking used for the other).

### Finding Description
`totalStaked()` in `BaseRewardPool` and `BaseRewardPoolV2` is defined as: [1](#0-0) 
which reads the raw ERC20 balance of the staking token held by `operator` (`MasterMagpie`), not a sum of internally tracked user stakes.

Meanwhile, individual balances used in reward accounting are sourced purely from `MasterMagpie`'s internal bookkeeping: [2](#0-1) 

When new rewards are queued (via `queueNewRewards` or the permissionless `donateRewards`), the reward-per-token accumulator is computed by dividing the incoming reward amount by `totalStaked()`: [3](#0-2) 

The identical pattern exists in `BaseRewardPoolV2`: [4](#0-3) 

Since `stakingToken` is a standard ERC20 (e.g. a Wombat receipt token or LP token), any unprivileged wallet can call `IERC20(stakingToken).transfer(masterMagpieAddress, amount)` directly, bypassing `MasterMagpie.deposit()`/`depositFor()` entirely. This increases `IERC20(stakingToken).balanceOf(operator)` — and therefore `totalStaked()` — without incrementing any user's `stakingInfo` record. The sum of all individually tracked staker balances (`Σ balanceOf(account)`) then becomes permanently smaller than `totalStaked()`.

From that point forward, every subsequent `queueNewRewards`/`donateRewards` call divides the incoming reward amount by the inflated `totalStaked()`, producing a `rewardPerTokenStored` increment that is smaller than it should be. Because `earned()`/`_earned()` compute user rewards strictly as `balanceOf(account) * rewardPerTokenStored / 10**decimals`, the sum of rewards claimable by all real stakers is permanently less than the reward amount actually transferred into the pool — the shortfall remains stuck in the contract with no mechanism to reclaim or redistribute it (no sweep/rescue function exists that would return this excess to depositors or the protocol).

### Impact Explanation
This is a direct analog to the reported bug class: a discrepancy between "real" token balance and "internally tracked" balance feeding two different sides of the same accounting formula, causing systemic miscalculation. Here, it results in a permanent, irrecoverable freezing of a portion of every future reward distribution to that pool's stakers — the excess reward tokens sit in the contract balance but are never included in any staker's claimable `rewardPerTokenStored` delta. This satisfies the "permanent freezing of unclaimed yield" impact bar.

### Likelihood Explanation
Likelihood is Medium: the action (a plain ERC20 `transfer` to the `MasterMagpie` contract address) requires no privilege and no cooperation from any protocol actor, and it can be triggered accidentally (e.g., a user mistakenly sending staking tokens to the wrong address, which is common) or done deliberately by any wallet holding the staking token. Every reward-queuing event afterward compounds the dilution.

### Recommendation
Track `totalStaked()` via an internal accumulator maintained by `MasterMagpie`'s `deposit`/`withdraw` flows (i.e., sum of `stakingInfo` balances) instead of relying on the raw ERC20 balance of the operator contract, so that the denominator used in `_provisionReward` always matches the sum of balances used in `earned()`/`_earned()`. Alternatively, add a mechanism to sweep/redirect any non-accounted staking-token balance so it cannot silently distort reward math.

### Proof of Concept
1. Users A and B each deposit into a Wombat pool through the relevant `PoolHelper`, causing `MasterMagpie.depositFor()` to record their stakes in `stakingInfo`, matching `BaseRewardPool.totalStaked()` (= `IERC20(stakingToken).balanceOf(masterMagpie)`).
2. An unprivileged wallet C calls `IERC20(stakingToken).transfer(masterMagpie, X)` directly (not through `deposit`), increasing `balanceOf(operator)` by `X` while `stakingInfo` for C is never created/updated.
3. A manager calls `BaseRewardPool.queueNewRewards(rewardAmount, rewardToken)` (or anyone calls the permissionless `donateRewards`). `_provisionReward` divides `rewardAmount` by the now-inflated `totalStaked()` [5](#0-4) , producing a smaller `rewardPerTokenStored` increment than if the denominator only reflected A+B's real stakes.
4. Sum of `earned(A) + earned(B)` for this distribution is strictly less than `rewardAmount`; the delta remains stuck in the `BaseRewardPool` contract with no path to recovery, permanently freezing that portion of the distributed reward.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
