## Title
Stale Object-Cache Entry Aliasing via Non-Atomic Secondary-Key Lookup - ([File: ruby/lib/google/protobuf/internal/object_cache.rb])

## Summary
The `axios-cache-interceptor` bug caches HTTP responses keyed only on URL and ignores the server's `Vary: Authorization` directive, so distinct request contexts collapse into one cache entry and a response computed for one auth context is returned for another. The transferable invariant is: *a cache/lookup structure must key strictly on the true identity of the underlying resource; if the key can be reused for a different underlying object before the cache is invalidated, a stale value will be served to an unrelated context.* In this Ruby protobuf backend, `Google::Protobuf::Internal::ObjectCache::LegacyObjectCache#try_add` ( [1](#0-0) ) uses a raw C pointer value as the cache key for the Ruby wrapper object of a upb C object, exactly analogous to using only the URL as a cache key while ignoring the differentiator (the Authorization header) that actually determines identity.

## Finding Description
`ObjectCache` is used throughout the Ruby FFI backend to avoid creating two different Ruby wrapper objects for the same upb C object address, e.g. `Google::Protobuf::OBJECT_CACHE.try_add @descriptor_pool.address, self` in `ruby/lib/google/protobuf/ffi/descriptor_pool.rb` and analogous call-sites for `Message`/`RepeatedField`/`MapField` wrappers (`ruby/lib/google/protobuf/ffi/message.rb`, `ruby/lib/google/protobuf/ffi/object_cache.rb`).

`LegacyObjectCache#try_add` (used automatically on JRuby / 64-bit-Windows where `interpreter_supports_non_finalized_keys_in_weak_map?` is false or `SIZEOF_LONG < SIZEOF_VALUE`, see `ruby/lib/google/protobuf/ffi/object_cache.rb:15-25`) is: [2](#0-1) 

The key invariant that must hold is: the raw pointer/address used as `key` must uniquely and durably identify the underlying upb object for as long as any Ruby wrapper referencing it is alive. But native heap/arena memory is routinely freed and reused by the allocator. When a upb `Message`/`Arena` is freed, nothing in this cache proactively invalidates the `@secondary_map[key]` entry that maps the old address to a `secondary_key` object; cleanup relies entirely on GC eventually collecting the `secondary_key` from the `ObjectSpace::WeakMap` (`@map`) and later `purge` sweeping `@secondary_map`. The `try_add` fast path is:
```ruby
if secondary_key = @secondary_map[key]
  if old_value = @map[secondary_key]
    return old_value
  end
end
```
If a *new*, unrelated upb object is allocated at the same address as a previously-freed one (a common allocator behavior, especially with upb's own arena/pool block-reuse machinery — see `upb_Arena_AllocPool`/`upb_Arena_FreePool`, `upb/mem/arena.h:130-160` — and its power-of-2 free-pool for repeated-field/array/message-sized blocks), and the stale `secondary_key`'s Ruby wrapper object has not yet been garbage-collected (GC is non-deterministic and lazy), `try_add` will return the **old** cached Ruby wrapper object for the **new** underlying C data. This is structurally identical to the axios cache poisoning: the "key" (URL / pointer address) is treated as a durable identity, but the actual identity-bearing dimension (the specific live allocation / the `Authorization` header) is not checked, so a value computed for context A is served for context B.

## Impact Explanation
If exploited, a Ruby application that repeatedly parses many independent, attacker-supplied protobuf messages (a typical server pattern: parse request N, free it, parse request N+1) could, under pointer-reuse conditions, receive a wrapper object that still reflects the *previous* message's contents/fields instead of the new message just parsed. This is a data-integrity/information-disclosure hazard: one client's parsed data (or portions of it) could be observed through, or attributed to, a different, unrelated parse operation happening later in the same process — mirroring the cross-user data leakage described in the CVE. It does not provide code execution or memory corruption by itself, but it can defeat per-request isolation assumptions in server code that trusts each `Message.new`/parse call to reflect only its own input.

## Likelihood Explanation
This requires the specific timing race of (a) a upb object being freed and its address recycled by a subsequent allocation, and (b) the corresponding Ruby wrapper not yet reclaimed by GC when the `try_add`/`get` fast path executes — a genuinely rare, GC-timing-dependent condition, and it is limited to the `LegacyObjectCache` code path (JRuby, or platforms where `long` is narrower than a pointer, e.g. 64-bit Windows), not the default `ObjectCache`/`WeakMap` path used on CRuby elsewhere. This lowers likelihood substantially relative to the original Medium-severity npm advisory, which triggers deterministically on every request with a differing `Authorization` header.

## Recommendation
- In `LegacyObjectCache`/`ObjectCache`, do not trust a bare pointer address as a durable identity key across allocation lifetimes; tie cache entries to allocation generation (e.g., invalidate/remove the `@secondary_map` entry synchronously when the underlying native object is explicitly freed, rather than relying solely on GC-driven `purge`).
- Consider eagerly deleting the `secondary_map[key]` entry at the point the native wrapper's finalizer runs (already tracked via `ObjectSpace::WeakMap`), instead of only opportunistically purging based on a size-based heuristic.
- Audit other call sites for the same fast-path pattern (`try_add`, `get`) to ensure staleness cannot be observed before a `purge`.

## Proof of Concept
A full reproduction requires forcing address reuse and controlling GC timing, which is outside what can be demonstrated as a deterministic unit test; this is inherently a race-dependent condition rather than a guaranteed-reproducible corruption. Conceptually:
```ruby
# Repro sketch (JRuby / LegacyObjectCache code path)
cache = Google::Protobuf::Internal::ObjectCache::LegacyObjectCache.new
addr = 0x1000  # address of first native object
cache.try_add(addr, wrapper_for_msg_A)   # msg_A freed shortly after
# ... native allocator frees msg_A's block and reuses `addr` for msg_B ...
cache.try_add(addr, wrapper_for_msg_B)   # if wrapper_for_msg_A hasn't been GC'd yet,
                                          # this returns wrapper_for_msg_A instead of registering wrapper_for_msg_B
```
No assertions were executed against the live codebase for this report; the finding is based on static reading of `ruby/lib/google/protobuf/internal/object_cache.rb` and the upb arena/pool-reuse allocator code (`upb/mem/arena.h`), and should be validated with a targeted stress test (repeated alloc/free cycles under forced GC delay) before treating it as confirmed exploitable.

```ruby
      class LegacyObjectCache
        def initialize
          @secondary_map = {}
          @map = ObjectSpace::WeakMap.new
          @mutex = Mutex.new
        end

        def get(key)
          value = if secondary_key = @secondary_map[key]
            @map[secondary_key]
          else
            @mutex.synchronize do
              @map[(@secondary_map[key] ||= Object.new)]
            end
          end

          # GC if we could remove at least 2000 entries or 20% of the table size
          # (whichever is greater).  Since the cost of the GC pass is O(N), we
          # want to make sure that we condition this on overall table size, to
          # avoid O(N^2) CPU costs.
          cutoff = (@secondary_map.size * 0.2).ceil
          cutoff = 2_000 if cutoff < 2_000
          if (@secondary_map.size - @map.size) > cutoff
            purge
          end

          value
        end

        def try_add(key, value)
          if secondary_key = @secondary_map[key]
            if old_value = @map[secondary_key]
              return old_value
            end
          end

          @mutex.synchronize do
            secondary_key ||= (@secondary_map[key] ||= Object.new)
            @map[secondary_key] ||= value
          end
        end
```
