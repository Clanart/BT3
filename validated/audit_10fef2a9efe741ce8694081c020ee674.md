## Title
Whitespace-hidden diff line indices are silently reused against the full diff when staging a partial commit, corrupting committed content - (File: `app/src/lib/git/apply.ts`)

## Summary
This is a structural analog of the Suzaku bug: the reward function fetched a **current** list (asset classes) but applied it to compute values for a **historical** epoch, and the array/keys silently didn't line up, causing a division by zero. In GitHub Desktop, `applyPatchToIndex` fetches a **freshly-computed, full diff** at staging time and blindly applies **line-selection indices that were computed against a different diff representation** (the whitespace-hidden diff shown in the Changes view). Nothing revalidates that the indices still refer to the same lines, so the wrong lines can be included or excluded from the patch that is `git apply --cached`'d into the index — a silent corruption of what the user commits.

## Finding Description
The user's line selection (`DiffSelection`) is a set of **absolute line indices** computed relative to a specific rendered diff's hunks (`hunk.unifiedDiffStart + lineIndex`), as seen in `formatPatch`: [1](#0-0) 

That diff is produced by `getWorkingDirectoryDiff`, which optionally hides whitespace-only changes via `hideWhitespaceInChangesDiff` when rendering the Changes view — this alters hunk boundaries, line counts, and therefore the absolute index of every line, compared to the full (non-hidden) diff of the same file.

When the user commits, `stageFiles` calls `applyPatchToIndex` for any partially-selected file: [2](#0-1) 

`applyPatchToIndex` re-fetches the diff **without** the whitespace-hidden option (i.e. the full diff), then formats a patch using `file.selection`, which was computed against whatever diff was last rendered (potentially the whitespace-hidden one): [3](#0-2) 

`DiffSelection.isSelected(lineIndex)` performs no validation that the index still corresponds to the same underlying line/content — it's a pure set-membership/default-selection check: [4](#0-3) 

Desktop's own code acknowledges this exact class of hazard, but only patches it at **display-refresh** time, not at **staging/commit** time: [5](#0-4) 

That guard recomputes `selectableLines` from a newly-loaded diff and drops now-invalid selections — but it only runs when the Changes view reloads a diff for on-screen display (e.g., on file selection change or `git status` refresh). It is never invoked from `applyPatchToIndex`/`stageFiles`/`createCommit`, so the actual patch-building path has no equivalent revalidation between "the diff structure the selection was computed against" and "the diff structure the patch is generated from."

This is structurally identical to the Suzaku bug: a set of indices/keys (selectableLines/asset classes) computed for one state (whitespace-hidden diff / current asset list) is reused against a different, freshly-fetched state (full diff / historical epoch) without any consistency check, and the existing partial guard (Suzaku's — division-by-zero check missing; Desktop's — `updateChangesWorkingDirectoryDiff`'s selectable-line reconciliation) does not cover the actual execution path where the mismatch is exploited (`_calculateOperatorShare` / `applyPatchToIndex`).

## Impact Explanation
If the diff used to build the git patch has a different line/hunk layout than the diff the user's selection indices were computed against, `formatPatch` will include/exclude the wrong lines relative to what the user intended and reviewed. Because `git apply --cached` operates on context matching within the hunk, this can either:
- fail loudly (safe, if content around the hunk no longer matches), or
- succeed with the wrong lines staged/omitted — a **silent corruption of what the user commits**, which is explicitly called out as a valid impact category (data the user believes they reviewed and selected ends up different from what is actually recorded in the commit, with no error surfaced).

This can also affect discard-changes flows via `formatPatchToDiscardChanges`, which shares the identical hunk/line-index pattern: [6](#0-5) 

## Likelihood Explanation
Toggling "Hide Whitespace Changes" is a documented, user-facing setting (`hideWhitespaceInChangesDiff`) that is common on files reformatted by linters/formatters — exactly the kind of file an attacker-controlled or externally-modified repository (via a fetched/pulled branch, a pre-commit formatter, or a `.gitattributes`-driven filter) is likely to contain: mixed whitespace-only and semantic changes in the same hunk region. A user reviewing such a diff with whitespace hidden, then making a partial line selection and committing, exercises this exact code path without any unusual or "unnatural" steps — it is a normal Desktop workflow (view diff with whitespace hidden → select lines → commit). No local/admin access or prior compromise is required, and it triggers automatically as part of ordinary partial-commit usage.

## Recommendation
- Before calling `formatPatch`/`applyPatchToIndex`, either fetch the diff using the **same** `hideWhitespaceInChangesDiff` setting that was used to compute the current `file.selection`, or re-derive/revalidate the selection against the diff actually used to build the patch (mirroring the `selectableLines` reconciliation already done in `updateChangesWorkingDirectoryDiff`, but applied at staging time as well).
- Alternatively, store selections keyed by stable line content/hash rather than purely positional indices, so a structural diff mismatch is detected instead of silently mapped to different lines.
- Add an integrity check that aborts (rather than silently proceeds) if the diff's hunk layout used for `formatPatch` differs from the one the selection was validated against.

## Proof of Concept
1. Create a file with a hunk containing a whitespace-only change adjacent to a real code change (e.g., trailing whitespace removed on line A, and a semantic edit on line B in the same hunk).
2. In Desktop, enable "Hide Whitespace Changes" for the Changes diff view. Observe the hunk collapses/shifts because the whitespace-only line is hidden.
3. Select only line B (the semantic change) via its absolute index in the whitespace-hidden rendering.
4. Commit the file (triggering `createCommit` → `stageFiles` → `applyPatchToIndex`, which fetches the diff **without** hiding whitespace).
5. Because `applyPatchToIndex`'s freshly-fetched full diff has different hunk indices (the whitespace-only line is now present and shifts positions), `file.selection.isSelected(absoluteIndex)` in `formatPatch` maps to a different line than the one the user selected — either committing the whitespace change instead of/along with the intended change, or omitting the intended change, with no error surfaced to the user.

Note: I was unable to execute this end-to-end in a live Desktop instance to confirm whether `git apply --cached` throws or silently succeeds for every hunk-shift permutation; the code-level mismatch (full diff fetched at staging time vs. selection computed against a possibly whitespace-hidden diff, with no revalidation) is verified directly in `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, and `app/src/models/diff/diff-selection.ts`.
