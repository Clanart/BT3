### Title
Unrefunded ETH overpayment is permanently locked in `EvmHost` on every native-fee dispatch/fund call - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and swap it for an exact amount of fee token via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. Unlike `IntentGatewayV2`/`IntrinsicIntents`, which explicitly refund any unspent native token back to the caller after a swap or partial fill, none of these `EvmHost` functions refund the excess ETH that the router returns when `msg.value` exceeds the exact input required for `fee`. That excess is refunded by the router to the caller of `swapETHForExactTokens`, which is `EvmHost` itself, and `EvmHost` never forwards it on to the end user. [1](#0-0) [2](#0-1) 

Compare with `IntentGatewayV2`, which does implement this refund correctly for the analogous ETH-legged flows: [3](#0-2) [4](#0-3) 

### Finding Description
`UniswapV2Router02.swapETHForExactTokens` computes the exact ETH input required to produce `amountOut` tokens (`fee`), and if `msg.value` supplied to the router call is greater than that computed input, the router refunds the difference to `msg.sender` of the router call. In `EvmHost.dispatch()` / `fundRequest()`, the entity calling the router is `EvmHost` itself (`address(this)` is also the token recipient), so:

- Router receives `msg.value` (forwarded 1:1 from the original caller's `dispatch{value: X}(...)` call).
- Router computes `amounts[0] <= X` needed for the exact fee.
- Router sends `X - amounts[0]` back to `EvmHost`'s balance (not to the original user).
- `EvmHost` has no code path in `dispatch()`/`fundRequest()` that forwards this refunded remainder back to `_msgSender()`.

Since the exact price of the fee token in ETH terms fluctuates with each block, any caller who does not send the *exact* wei amount (which is unknowable in advance without doing an on-chain quote in the same block, and even then is racy) will overpay and have the difference silently absorbed into the `EvmHost` contract's own balance, with no accounting or event recording it as anything (unlike `IntentGatewayV2`'s `DustCollected` event) and no permissionless path shown for the original payer to reclaim it.

This is the structural analog to the reported bug class: the swap-payment code path here has no user-controlled "amountOutMin/refund" guarantee, causing an unprivileged caller's own funds to move to the wrong beneficiary (the protocol contract) with no on-chain accounting or recovery, for the ordinary, expected use case of paying request fees in native token.

### Impact Explanation
This falls under "stealing or loss of funds" from the bounty's required impact gate: any regular user calling `dispatch()` or `fundRequest()` with native token to pay Hyperbridge dispatch fees permanently loses the ETH overpayment above the exact quoted price, with the difference accruing, uncredited, into `EvmHost`'s own balance. This happens on the unprivileged, primary user entrypoint for paying protocol fees, not through any malicious relayer/prover/admin action, and requires no special conditions beyond normal usage (sending a safety buffer above the exact quote, which is standard practice to avoid `EXCESSIVE_INPUT_AMOUNT` reverts from price movement between quote and execution).

### Likelihood Explanation
High likelihood in practice: because `swapETHForExactTokens` reverts if `msg.value` is insufficient at execution time (`EXCESSIVE_INPUT_AMOUNT`/underflow), any caller wanting their `dispatch()`/`fundRequest()` transaction to reliably succeed under normal price movement between quoting and mining must send more ETH than the exact quoted amount. Every such over-provisioned call permanently forfeits the difference — this is not an edge case requiring an attacker, it is the expected operating mode for any integrator paying with native token.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture `address(this).balance` before/after the swap (or use the router's returned `amounts[0]`) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder` and `IntrinsicIntents._fillSameChain`.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch{value: 1 ether}(DispatchPost{... fee: X, ...})` where the exact ETH cost for `X` fee tokens at execution-time price is `0.9 ether` (buffer sent to survive price movement/slippage during mining).
2. Inside `dispatch()`, `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: 1 ether}(X, path, address(this), block.timestamp)` executes: the router pulls `0.9 ether` worth of WETH, delivers `X` fee tokens to `EvmHost`, and refunds `0.1 ether` back to `msg.sender` of the router call — which is `EvmHost`, not the user.
3. `dispatch()` proceeds to build/emit the `PostRequest` and returns; there is no subsequent line refunding the `0.1 ether` back to `_msgSender()`.
4. The user has permanently lost `0.1 ether` with no on-chain record distinguishing it from ordinary protocol balance, and no user-facing function to reclaim it. [1](#0-0)
