## Analysis

I looked for the closest Desktop analog to the report's core pattern: **a per-user choice is saved into state, but the code path that actually performs the consequential action never reads that saved state**, so the choice is silently discarded.

The closest exact match is GitHub Desktop's manual conflict resolution ("ours"/"theirs" for binary or added-in-both conflicts).

- The user's choice is stored in `changesState.conflictState.manualResolutions` via `_updateManualConflictResolution` [1](#0-0) .
- That map is only ever consumed by `createMergeCommit`, `continueRebase`, and `continueCherryPick`, all of which explicitly call `stageManualConflictResolution` for each entry in `manualResolutions` before staging the rest of the files [2](#0-1) .
- However, the dialog the user actually sees when trying to commit conflicted files from the normal "Changes" pane — `CommitConflictsWarning` — does **not** go through `createMergeCommit`. Its `onSubmit` calls `dispatcher.commitIncludedChanges(repository, context)` directly [3](#0-2) .
- That dispatches to `_commitIncludedChanges`, which calls `createCommit(repository, message, selectedFiles, {...})` [4](#0-3)  — and `createCommit` has **no `manualResolutions` parameter at all**; it unconditionally calls `stageFiles(repository, files)` (plain `git add`) on every selected file, including conflicted ones [5](#0-4) .

This is structurally identical to the report: `manualResolutions` (analogous to `userBoosts`) is written by one function and consulted by only a subset of consumers (`createMergeCommit`, analogous to `removeBoostDelegation`), while the path the user most naturally exercises (the ordinary Commit button / conflict warning dialog) ignores it entirely (analogous to `_calculateBoost` ignoring delegations).

### Title
Manual Conflict Resolution Choice Is Ignored When Committing Through the Standard Commit Button, Silently Committing the Wrong File Content - (File: `app/src/lib/git/commit.ts`)

### Summary
When a repository has a binary or "added-in-both" conflict, Desktop lets the user pick "ours" or "theirs" via a dropdown, which is stored only in in-memory state (`conflictState.manualResolutions`). If the user commits that choice through the ordinary Commit button (which routes through `CommitConflictsWarning` → `commitIncludedChanges` → `createCommit`), the stored resolution is never read or applied — `createCommit` simply runs `git add` on whatever bytes currently sit in the working tree for that path, then commits.

### Finding Description
`stageManualConflictResolution` is the function responsible for actually materializing a user's ours/theirs choice: for "both added"/binary conflicts it calls `checkoutConflictedFile` to write the chosen side's blob to disk before staging [6](#0-5) . This function is invoked only from `createMergeCommit` [7](#0-6) , `continueCherryPick` [8](#0-7) , and equivalent rebase code.

The generic `createCommit` used for every ordinary commit has no concept of `manualResolutions` whatsoever and just stages the files as-is [5](#0-4) . The `CommitConflictsWarning` dialog — the UI surface explicitly built to let a user "commit these conflicted files" — calls `dispatcher.commitIncludedChanges`, i.e. the generic path, not `finishConflictedMerge`/`createMergeCommit` [3](#0-2) . `_commitIncludedChanges` never reads `state.changesState.conflictState.manualResolutions` before calling `createCommit` [9](#0-8) .

So the "ours"/"theirs" decision recorded in state is exactly like the delegated boost in the report: saved, displayed, and even shown as "resolved" in the UI, but never consulted by the code path that performs the actual write/commit.

### Impact Explanation
For a repo the user cloned or is merging (attacker controls the two conflicting branches/blobs — e.g. a malicious remote branch merged by the user), a "both added"/binary conflict lets the attacker's content and the user's own content race for which one lands in the commit. Since `createCommit`'s `stageFiles` just adds whatever git currently has staged/on-disk for that path (typically one arbitrary side of the conflict, not necessarily the one the user selected), the user can select "theirs" (attacker's malicious binary/script) intending to review and possibly reject it, but actually commit and push it — or conversely believe they discarded the attacker's file while it's the one that gets committed. This is silent corruption of what the user commits/pushes, satisfying the required impact class.

### Likelihood Explanation
This triggers on an ordinary workflow: merge or cherry-pick a branch that contains a binary/added-in-both conflict, use the resolution dropdown, then click "Commit" from the normal Changes pane (which surfaces `CommitConflictsWarning` when conflicted files are selected) rather than going through the "Continue Merge"/multi-commit-operation flow. No local access, admin rights, or social engineering is required beyond the attacker controlling the conflicting branch content, which is the normal untrusted-remote-branch threat model for Desktop.

### Recommendation
Have `_commitIncludedChanges` read `state.changesState.conflictState?.manualResolutions` and pass it through to a staging routine that calls `stageManualConflictResolution` for any conflicted path with a stored resolution (mirroring `createMergeCommit`), instead of calling the manualResolutions-unaware `createCommit`/`stageFiles` for those paths. Alternatively, route `CommitConflictsWarning`'s submit handler through the same `finishConflictedMerge`-style commit function used by the dedicated conflict-resolution flows.

### Proof of Concept
1. Attacker pushes/offers a branch that, when merged, produces an "added-in-both" or binary-file conflict with the user's file.
2. User merges that branch in Desktop; conflict dialog/dropdown appears; user selects "theirs" (or "ours") for the conflicted binary file — this only updates `conflictState.manualResolutions` in memory [1](#0-0) .
3. Instead of clicking "Continue merge" in the conflicts flow, the user goes to the Changes pane and clicks "Commit N Files," triggering `CommitConflictsWarning`.
4. User clicks "Yes, Commit Files," which calls `commitIncludedChanges` → `_commitIncludedChanges` → `createCommit` [3](#0-2) [5](#0-4) .
5. `createCommit` runs `stageFiles` (git add) on the conflicted path exactly as it exists on disk/index, ignoring the "theirs"/"ours" selection — the file committed does not match what the user selected in the dropdown, with no error or warning about the mismatch.

  public _updateManualConflictResolution(
    repository: Repository,
    path: string,
    manualResolution: ManualConflictResolution | null
  ) {
    this.repositoryStateCache.updateChangesState(repository, state => {
      const { conflictState } = state

      if (conflictState === null) {
        // not currently in a conflict, whatever
        return { conflictState }
      }

      const updatedManualResolutions = new Map(conflictState.manualResolutions)

      if (manualResolution !== null) {
        updatedManualResolutions.set(path, manualResolution)
      } else {
        updatedManualResolutions.delete(path)
      }

      return {
        conflictState: {
          ...conflictState,
          manualResolutions: updatedManualResolutions,
        },
      }
    })
