### Title
Bank precompile `sendNative` bypasses `SendEnabled`/blocklist/allow-list circuit breakers - (File: precompiles/bank/bank.go)

### Summary
The Cosmos `x/bank` module exposes admin-controlled circuit breakers — `SendEnabled` (a per-denom / default "pause" switch, analogous to the `Pausable` mechanism the external report recommends), `BlockedAddr`, and `IsInDenomAllowList` — which are enforced on the standard `MsgSend`/`MsgMultiSend` transfer paths. The EVM `bank` precompile's `sendNative` method (and its wei-transfer counterpart `SendCoinsAndWei`) is a second fund-transfer path that never calls any of these checks, so an unprivileged EVM caller can move `usei`/wei even while the chain operators have "paused" transfers of that denom or blocked/restricted specific addresses.

### Finding Description
The standard bank send flow enforces the pause/allow-list/blocklist guards before moving funds: [1](#0-0) 

These guards are backed by the `SendEnabled` param (the chain's coin-transfer "pause" switch): [2](#0-1) [3](#0-2) 

However, the EVM `bank` precompile's `sendNative` function — reachable by any EVM caller sending value to address `0x1001` — moves funds by calling `bankKeeper.SendCoinsAndWei` directly, completely independent of the `msgServer.Send` path: [4](#0-3) 

`SendCoinsAndWei` itself performs no `IsSendEnabledCoins`, `BlockedAddr`, or `IsInDenomAllowList` checks — it only debits/credits wei balances and, for the usei remainder, calls the low-level `SendCoinsWithoutAccCreation`: [5](#0-4) 

By contrast, the precompile's `send` (ERC20-pointer) method does route through `bankMsgServer.Send`, which does perform the enable/allow-list/blocklist checks: [6](#0-5) 

This inconsistency means the chain's designated "pause"/access-control switches for coin transfers (`SendEnabled=false`, `BlockedAddr`, `DenomAllowList`) can be silently bypassed by simply using the EVM `sendNative` entry point instead of a Cosmos `MsgSend`. This pattern is repeated across every legacy precompile version examined (v552 through v67 and the current `bank.go`), so it is not a one-off omission but a structural gap in the precompile's design across the codebase's version history.

### Impact Explanation
If operators disable transfers of `usei` (or any denom wired to a native EVM pointer/wei path) via the `SendEnabled` parameter — the exact "pause" mechanism intended to stop fund movement during an incident, mirroring the recommendation in the external report — or place an address on the `BlockedAddr` list, or restrict a denom via `DenomAllowList`, any unprivileged EVM transaction sender can still move `usei`/wei balances by calling `sendNative` on the bank precompile. This directly undermines the chain's only administrative circuit breaker for halting fund transfers during a security incident, allowing unauthorized transfers to continue and defeating incident-response pausing, satisfying the "unauthorized transfer via precompile" and "fund loss/abuse of circuit breaker" impact classes.

### Likelihood Explanation
High. The path requires only a standard EVM transaction (a value-bearing call to the bank precompile address `0x0000000000000000000000000000000000001001` invoking `sendNative`), which is fully reachable by any unprivileged EVM account, with no special permissions needed. The bypass is deterministic and does not depend on race conditions or validator behavior — it triggers on every call as soon as an operator relies on `SendEnabled=false`, `BlockedAddr`, or the allow-list to restrict transfers.

### Recommendation
Add the same guard checks (`IsSendEnabledCoins`, `BlockedAddr`, `IsInDenomAllowList`) to the bank precompile's `sendNative` path (and any other path invoking `SendCoinsAndWei`/`AddWei`/`SubWei` directly for user-initiated transfers), or move these checks into `SendCoinsAndWei` itself so that all fund-transfer entry points — Cosmos messages and EVM precompile calls alike — respect the chain-level pause and access-control mechanisms uniformly.

### Proof of Concept
1. Governance/admin sets `SendEnabled` to `false` for `usei` (or leaves `DefaultSendEnabled=false`) to pause transfers chain-wide, e.g. in response to a detected exploit.
2. An unprivileged user submits a normal `MsgSend` — it is correctly rejected with `ErrSendDisabled` per [7](#0-6) .
3. The same user instead sends an EVM transaction with non-zero `value` calling `sendNative(toNativeAddress)` on the bank precompile (`0x...1001`) as defined in [8](#0-7) .
4. The precompile's `sendNative` executes `bankKeeper.SendCoinsAndWei` unconditionally — see [4](#0-3)  — moving the funds successfully despite the chain-wide pause, demonstrating the bypass.
