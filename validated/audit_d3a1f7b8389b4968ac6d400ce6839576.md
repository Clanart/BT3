### Title
Escrow ledger accounting breaks pooled-balance solvency for deflationary/fee-on-transfer input tokens, causing order-dependent fund loss on withdrawal - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2` correctly measures the *actual received* amount when a fee-on-transfer/deflationary token is escrowed at `placeOrder` time (confirmed by the dedicated test suite in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`), but the release path, `_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol`, does the opposite: it trusts the static ledger value and calls a fixed-amount `safeTransfer`/native `.call` without verifying what the beneficiary actually received or reconciling the ledger against the contract's real token balance. Because all orders denominated in the same ERC-20 share one pooled contract balance while each order's entitlement is tracked as an independent number in `_orders[commitment][token]`, any token whose balance mechanics can diverge from a naive "amount in == amount out" ledger (deflationary/rebasing/fee-on-transfer tokens, which are explicitly tested as supported inputs) can leave the pool under-collateralized. Whichever order is settled last against that token can revert or be shorted, exactly mirroring the "Alice loses more than Eve" unfairness in the seed report — the loss falls on the participant who settles last, not the one who is at fault.

### Finding Description
In `evm/src/apps/intentsv2/IntentsBase.sol` the escrow bookkeeping and release logic are: [1](#0-0) [2](#0-1) 

`_withdraw` (used for `RedeemEscrow` fills, `RefundEscrow` cancellations, and the same-chain fill path via `evm/tron/contracts/apps/IntentGatewayV2.sol`'s equivalent `withdraw`) decrements `_orders[body.commitment][token]` by the recorded `amount` and then transfers exactly `amount` out, with no post-transfer balance check: [3](#0-2) 

By contrast, the *deposit* side is careful to use the actual balance-delta for deflationary tokens, as proven by the test suite: [4](#0-3) 

This asymmetry is the root cause. `_orders` is a per-commitment ledger, but the underlying ERC-20 balance backing all outstanding commitments for a given token is one shared pool inside the gateway contract. The ledger's sum-of-entries invariant (`sum(_orders[*][token]) == token.balanceOf(gateway)`) is only guaranteed to hold at the moment each order is placed (because placement uses the balance-diff pattern). Nothing re-verifies or corrects this invariant at withdrawal time. Any token whose transfer-out behavior, total-supply mechanics, or balance accounting can cause the contract's real balance to fall below what the ledger believes it holds (deflationary tokens that tax every transfer including outbound ones, rebasing tokens whose balances shrink independent of transfers, or tokens with elastic supply) will silently desynchronize the ledger from reality. Because withdrawals are processed one order at a time, whichever order is redeemed first drains its full recorded `amount` from the shared pool while the pool's real balance may already be lower than the sum of remaining ledger entries — the last order(s) to settle inherit the shortfall, either reverting (fund lock) or, if the token's `transfer` silently returns fewer tokens without reverting, having the beneficiary receive less than their recorded/expected entitlement while `_orders` is nonetheless zeroed out as if they were paid in full.

This is structurally identical to the reported "rebase logic" bug: multiple parties who deposited the same recorded amount into a shared, fungible pool end up with different real payouts purely as a function of settlement order, because the accounting layer treats a shared pool as if each entry were independently backed.

### Impact Explanation
This falls under "stealing or loss of funds" and "logic attacks" in the impact gate. It is reachable by any unprivileged solver/user who places, fills, or cancels orders using a deflationary/rebasing/fee-on-transfer ERC-20 as the order's `input` token — no malicious relayer, prover, or governance actor is required. Consequences:
- Users/solvers who settle later against the same token pool can have their withdrawal transaction revert (`TransferFailed`/insufficient balance), permanently locking their escrowed funds since `_orders[commitment][token]` for their commitment remains non-zero but the pool can never be topped back up.
- If the token's `transfer` does not revert on a shortfall (some deflationary tokens simply deliver less without reverting), the ledger is decremented and the order marked filled/refunded (`_filled[commitment]` set) even though the beneficiary received less than the amount recorded in the on-chain accounting and in `OrderFilled`/`EscrowReleased`/`EscrowRefunded` events — a silent, unrecoverable loss of funds with no path to reclaim the difference.

### Likelihood Explanation
Likelihood is limited to gateways/chains where such a token is configured as a valid `Order.inputs[]` token. The gateway explicitly documents and tests support for fee-on-transfer tokens as inputs (see the `FEE-ON-TRANSFER TOKEN TESTS` section referenced above), which shows this is an anticipated, not merely theoretical, class of token to be used with the intent gateway — the tests only validate the deposit-side balance-diff correctness and never validate multi-order pool solvency at withdrawal time. Any deployment that allows permissionless input-token selection (which appears to be the default, since `placeOrder` accepts an arbitrary `TokenInfo.token` address) is exposed the moment two or more concurrent orders share such a token.

### Recommendation
Apply the same actual-balance-diff discipline used in `placeOrder` to the withdrawal path in `_withdraw`/`withdraw`: measure `token.balanceOf(address(this))` before and after each outbound transfer and treat the delta — not the static `amount` — as authoritative for what has left the pool and what the beneficiary received. Additionally, consider tracking and reconciling escrow on a per-token pooled basis (e.g., a global `token -> totalEscrowed` invariant checked against `balanceOf(this)` on every state-changing entry point) so that a shortfall is detected and fails safely/proportionally rather than being silently absorbed by whichever order settles last. At minimum, refuse to finalize a withdrawal (`_filled`/ledger zeroing) if the beneficiary's received amount is less than the recorded escrow amount for a token, and surface the shortfall instead of writing over it — eliminating the order-dependent unfairness described in the seed report.

### Proof of Concept
1. Deploy `IntentGatewayV2` with a deflationary/rebasing ERC-20 `D` registered as a valid input/output token (the same class of token as `FeeOnTransferToken` used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`, but one whose fee/rebase also applies on transfers **out** of the gateway, or whose balance can shrink independent of transfers).
2. Alice, Bob, and Eve each call `placeOrder` depositing `N` of `D`. Each order's escrow, per the balance-diff logic, is recorded correctly as the amount actually received by the gateway at that time (as validated in `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`).
3. Let the token's rebase/deflation mechanism reduce the gateway's real `D` balance further (or let a subsequent transfer-out tax further compound), so that `token.balanceOf(gateway) < sum(_orders[*][D])`.
4. Sequentially trigger `RedeemEscrow`/`RefundEscrow`/`fillOrder` withdrawals for Alice, then Bob, then Eve via `_withdraw`/`withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:390-410`, `evm/tron/contracts/apps/IntentGatewayV2.sol:682-705`).
5. Alice's withdrawal succeeds in full (pool still solvent at that point). By the time Eve withdraws, the pool balance is insufficient for the full recorded `amount`; Eve's transaction either reverts (locking her funds indefinitely since her ledger entry is never cleared) or — for tokens that short-deliver instead of reverting — Eve receives less than her recorded entitlement while the contract still marks her order `_filled` and zeroes her escrow, permanently losing the difference. Alice, Bob, and Eve deposited identical amounts, but withdrawal order alone determines who bears the loss.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
