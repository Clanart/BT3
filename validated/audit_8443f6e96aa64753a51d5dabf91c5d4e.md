### Title
Missing zero-address check on ERC20 precompile `transfer`/`transferFrom` permanently locks user funds - (File: `precompiles/erc20/tx.go`)

### Summary
The `DepositSecurityModule.addGuardian` bug is a missing `address != address(0)` check that lets an invalid/uncontrollable address be accepted as valid state. The same bug class exists in the Cosmos EVM `x/erc20` ERC20 precompile: the `to` recipient address passed to `Transfer`/`TransferFrom` is never checked against the zero address before the underlying bank `Send` message is executed, unlike the OpenZeppelin ERC20 reference implementation bundled in this same repo, which explicitly reverts with `ERC20: transfer to the zero address` / `ERC20InvalidReceiver(address(0))`.

### Finding Description
`Precompile.Transfer` and `Precompile.TransferFrom` in [1](#0-0)  parse the caller-supplied `to` address via `ParseTransferArgs`/`ParseTransferFromArgs` and pass it straight into the shared `transfer` helper with no zero-address validation: [2](#0-1) 

The helper builds a `banktypes.NewMsgSend(from.Bytes(), to.Bytes(), coins)` and executes it via `msgSrv.Send(ctx, msg)` unconditionally. `to.Bytes()` for `common.Address{}` (the zero address) produces a 20-byte all-zero `sdk.AccAddress`, which is a structurally valid Cosmos address (correct length) and is not a registered module/blocked account, so the bank `Send` message succeeds and moves the coins there.

This directly contradicts the pattern the repo itself documents/implements as the safe behavior for ERC20-like transfers — every Solidity ERC20 reference in the repo (`contracts/solidity/precompiles/erc20/testdata/ERC20NoMetadata.sol`, `tests/evm-tools-compatibility/hardhat/Flattened.sol`) explicitly reverts transfers/mints/burns to `address(0)`: [3](#0-2) 

No such guard exists in the Go precompile implementation that Cosmos-side ERC20 token pairs actually execute against.

By contrast, other precompiles in the same codebase do perform this exact zero-address check on their address inputs (e.g. `setAllowance`/`Approve` in the ERC20 keeper, and staking `NewMsgDelegate`/`NewMsgRedelegate`/`NewMsgEditValidator`): [4](#0-3) [5](#0-4) 

This inconsistency confirms the `transfer`/`transferFrom` path is the one instance missing the guard.

### Impact Explanation
Any unprivileged EVM caller can invoke the ERC20 precompile's `transfer(address(0), amount)` or `transferFrom(owner, address(0), amount)` for any registered token pair (native coin, IBC voucher, or native ERC20-backed coin). The bank `Send` succeeds, moving the coin balance to the zero-derived `sdk.AccAddress`, for which no private key or module authority exists. This is an irreversible, unauthorized extraction/loss of user (or, if invoked via `transferFrom`, third-party owner) spendable value with no way to recover the funds — matching the "Critical permanent freezing/locking/theft of user funds" impact category. It can be repeated for any amount the caller controls or has allowance over, and applies uniformly across all token pairs routed through this shared precompile code path.

### Likelihood Explanation
High likelihood: the precondition is only that the caller has a balance (or an allowance) for a registered token pair and calls a public, unprivileged precompile method with a trivially craftable zero address argument. No governance, validator, or relayer privilege is required, and the flow is part of the ordinary transaction/contract execution surface (JSON-RPC → EVM call → precompile `Run`/`Execute` → `Transfer`/`TransferFrom`).

### Recommendation
Add an explicit zero-address check for `to` (and defensively for `from`) in `precompiles/erc20/tx.go`'s `transfer` function before constructing/executing the bank `MsgSend`, mirroring the pattern already used in `x/erc20/keeper/allowance.go` and the staking precompile's message constructors, e.g.:
```go
if to == (common.Address{}) {
    return nil, errors.New("ERC20: transfer to the zero address")
}
```
Apply the same check to any other precompile paths (e.g. werc20) that ultimately construct bank `Send` messages from EVM-supplied addresses.

### Proof of Concept
1. Register/obtain a token pair (native coin, IBC voucher, or native ERC20) exposed at its ERC20 precompile address.
2. As any account holding a balance of that token pair's denom, call the precompile's `transfer` method with `to = address(0)` and a nonzero `amount` (or, as a third party with an allowance, call `transferFrom(owner, address(0), amount)`).
3. Observe that `Precompile.Transfer`/`TransferFrom` in `precompiles/erc20/tx.go` executes `banktypes.NewMsgSend(from.Bytes(), common.Address{}.Bytes(), coins)` via `msgSrv.Send` without error, and the `Transfer` event is emitted with `to = 0x000...000`.
4. Query the bank balance of the zero-derived `sdk.AccAddress` — it now holds the transferred coins, which are permanently unspendable since no corresponding private key exists.

Note: I was unable to execute this against a running node/test harness in this session (read-only code search only), so the exact runtime error strings and whether any additional SDK-level `BlockedAddr` check intercepts this specific derived address in this app's `evmd/app.go` bank keeper configuration could not be fully confirmed; a Devin session with the ability to build/run the integration test suite (e.g. extending `tests/integration/precompiles/erc20/test_tx.go`) should verify end-to-end before treating this as certain.

	contract *vm.Contract,
	stateDB vm.StateDB,
	method *abi.Method,
	args []interface{},
) ([]byte, error) {
	from := contract.Caller()
	to, amount, err := ParseTransferArgs(args)
	if err != nil {
		return nil, err
	}

	return p.transfer(ctx, contract, stateDB, method, from, to, amount)
