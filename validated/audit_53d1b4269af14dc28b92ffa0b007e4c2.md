### Title
Future-dated oracle timestamp permanently poisons the per-feed monotonic `last-update` map, causing all subsequent legitimate price resolutions for that feed to revert forever - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`oracle-timestamp-fresh` treats any oracle timestamp greater than the current `stacks-block-time` as automatically "fresh" (`delta = u0`), and `price-resolve` unconditionally advances the per-feed `last-update` map to that future timestamp. Because the same function also enforces a strictly monotonic constraint (`>= ts prev`), once a future-dated timestamp is accepted and stored, every subsequent — correctly timestamped — price update for that feed will have `ts < prev` and be rejected forever, permanently bricking price resolution for the affected asset.

### Finding Description
`price-resolve` in `mainnet/contracts/market/v0-4-market.clar` computes freshness via: [4](#0-3) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

When the oracle-reported publish timestamp `ts` is ahead of the local `stacks-block-time` (a routine occurrence given Pyth's near-real-time publishing cadence versus Stacks block cadence, or a benign clock/latency skew from the price source), `delta` is forced to `u0`, which trivially satisfies `<= max-staleness` for any asset. The price is accepted as "fresh" regardless of how far in the future `ts` is.

Immediately after this check, `price-resolve` persists that future timestamp as the new floor for the feed: [5](#0-4) 

```clarity
    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```

`last-update` is keyed per `{type, ident}` (per price feed) and is read as `prev` on every subsequent call via `oracle-last-update key`. Since the monotonicity clause requires `(>= ts prev)`, once `prev` has been inflated to a future value, every later legitimate oracle update — whose `ts` is normal, non-future, and therefore less than the inflated `prev` — fails the `(>= ts prev)` check and `price-resolve` returns `ERR-ORACLE-INVARIANT` (or, via callers, `ERR-DISABLED-COLLATERAL-PRICE-FAILED`) permanently, with no way to reset `last-update` for that feed.

### Impact Explanation
Any function whose control flow depends on resolving that asset's price is bricked for as long as the poisoned `last-update` entry stands:
- `borrow` reverts because `get-notional-evaluation`/`price-resolve` for the debt or collateral asset fails before health checks can complete. [6](#0-5) 
- `collateral-remove` reverts for any account with debt, or for disabled-collateral withdrawal paths, since both call `price-resolve`/`get-notional-evaluation`. [1](#0-0) 
- `liquidate` reverts because it also depends on `get-notional-evaluation` for the affected asset, meaning positions using the poisoned feed as collateral or debt can no longer be liquidated even while becoming insolvent.

This lands on **temporary freezing of funds** (borrowers cannot withdraw collateral or repay/borrow against the affected asset, and liquidators cannot act on positions using it) and can escalate toward **protocol insolvency** if the frozen asset's positions become undercollateralized while liquidation is blocked, since there is no governance/DAO or user-level function to reset the poisoned `last-update` entry for a single feed — the market contract exposes no "clear stale monotonic timestamp" mechanism, mirroring the referenced report's core defect: a required internal state transition (a fresh, accepted timestamp) can become permanently unreachable, locking user funds with no escape hatch.

### Likelihood Explanation
No malicious actor action is strictly required to trigger the future-timestamp branch: Pyth publish times are generated off-chain at seconds-level granularity nearly in real time, while `stacks-block-time` reflects the timestamp of the last mined Stacks block; brief periods where a genuine Pyth `publish-time` exceeds the current `stacks-block-time` are plausible during normal operation (e.g., block production lag, oracle publishing jitter). The bug is in the protocol's own handling of this ordinary condition — not corrupted third-party data — since a correctly-signed, non-manipulated price with a timestamp merely ahead of the local block clock is enough to permanently write an inflated floor into `last-update`.

### Recommendation
Do not let a future-dated `ts` bypass staleness AND simultaneously become the new monotonic floor. Options:
- Reject timestamps that are ahead of `stacks-block-time` beyond a small tolerance instead of silently clamping `delta` to `0`.
- Cap the value written into `last-update` at `stacks-block-time` rather than at the raw (potentially future) `ts`.
- Add a DAO-gated recovery function to reset/lower a specific feed's `last-update` entry, so an inflated value does not permanently brick that asset's price resolution.

### Proof of Concept
1. A Pyth update for feed `F` (asset `USDC`, say) arrives with `publish-time = T_future`, where `T_future > stacks-block-time` by even a few seconds, due to ordinary publish/block latency skew.
2. `oracle-timestamp-fresh(T_future, prev, max-staleness)` computes `delta = 0` (since `T_future > stacks-block-time`), so `delta <= max-staleness` passes trivially, and `T_future >= prev` also passes (prev being some earlier, legitimate value). The price is accepted.
3. `price-resolve` executes `(if (> timestamp last-update-time) (map-set last-update key timestamp) false)`, storing `last-update[F] = T_future`.
4. On the next legitimate Pyth update for feed `F` with a normal `publish-time = T_normal` (where `T_normal < T_future` because no clock skew this time), `oracle-timestamp-fresh(T_normal, T_future, max-staleness)` fails the `(>= ts prev)` clause since `T_normal < T_future`.
5. `price-resolve` now returns `ERR-ORACLE-INVARIANT` for every future call referencing feed `F`, and this failure propagates to `borrow`, `collateral-remove` (debt/disabled-collateral paths), and `liquidate` for asset `USDC`, permanently blocking those operations for that asset with no recovery path in the contract.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
