### Title
Unchecked u64 overflow accepts consensus-invalid Bitcoin payments - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/blackvul/serai--010/blob/master/networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` sums attacker-controlled payment amounts with `sum::<u64>()` and then compares the wrapped result against available inputs. An overflowing set of payment outputs can therefore bypass the `NotEnoughFunds` check and produce a transaction whose outputs exceed its inputs. The resulting transaction can still be passed to the FROST transaction-signing machines, while `fee()` can subsequently underflow/panic or the network can reject the signed transaction.

### Finding Description
The constructor reads each supplied payment amount into `TxOut` and calculates `payment_sat` using an unchecked `u64` sum. In release builds, overflowing amounts wrap modulo `2^64`; in debug builds, they panic. The funds check then uses the wrapped total and unchecked `payment_sat + needed_fee` arithmetic, so an attacker can specify multiple individually non-dust outputs whose mathematical total exceeds `u64::MAX` but whose wrapped total appears affordable. [1](#0-0) [2](#0-1) 

No later validation checks that the actual serialized output values are economically valid or that their total remains below the input total. The malformed transaction is returned as a valid `SignableTransaction`. [3](#0-2) 

`multisig` then creates one FROST algorithm machine per input after matching the prevout script against the offset key, and `TransactionSignMachine::sign` signs each corresponding Taproot sighash. [4](#0-3) [5](#0-4) 

### Impact Explanation
An unprivileged party that can cause a particular payment vector to be constructed can cause threshold participants to sign a consensus-invalid Bitcoin transaction. The same overflow can also produce a denial of service: debug builds panic during `sum`, while release builds create a transaction for which `fee()` subtracts a larger output sum from a smaller input sum and underflows. [6](#0-5) 

This is a signing-integrity failure because the API promises to reject insufficiently funded transactions, yet produces signing machines for a transaction that cannot be spent or relayed under Bitcoin consensus rules.

### Likelihood Explanation
The trigger only requires public transaction-construction data: one valid `ReceivedOutput` and two attacker-controlled payment amounts whose sum wraps to a small value. `ReceivedOutput` is explicitly deserializable from untrusted bytes through `ReceivedOutput::read`. [7](#0-6) 

Exploitation does not require key compromise, validator collusion, or malicious internals. It does require the integrating protocol to accept attacker-influenced payment outputs before requesting signatures, which is the reachable Bitcoin wallet boundary.

### Recommendation
Use checked arithmetic throughout transaction construction:

- Accumulate inputs and payments with `checked_add` or `u128`.
- Calculate `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`.
- Calculate `fee_per_vbyte * vbytes` with `checked_mul`.
- Reject individual outputs above Bitcoin’s maximum money range.
- Calculate `fee()` with `checked_sub` and return an error instead of panicking.
- Add regression tests for output totals that wrap `u64::MAX`.

### Proof of Concept
```rust
// Conceptual test inside networks/bitcoin/src/wallet.

let input_sats = 100_000;
let inputs = vec![valid_received_output_with_value(input_sats)];

// Both payments independently satisfy `amount >= DUST`.
// Their true total exceeds u64::MAX, but `sum::<u64>()` wraps to 1_499.
let payments = vec![
    (script_pubkey.clone(), u64::MAX - 500),
    (script_pubkey, 2_000),
];

let tx = SignableTransaction::new(
    inputs,
    &payments,
    None,
    None,
    1,
).unwrap();

// The constructed transaction attempts to spend ~u64::MAX + 1_499 sats
// from only 100_000 sats.
assert!(tx.transaction().output[0].value.to_sat() > input_sats);

// With matching keys for the input's offset/script, this remains usable:
// let machine = tx.multisig(&keys).unwrap();
// let (sign_machine, _preprocess) = machine.preprocess(&mut OsRng);
//
// Calling fee() underflows because output_sum > input_sum.
let _ = tx.fee();
```

In a checked build, the payment accumulation itself can panic before `unwrap`; in an unchecked release build, construction succeeds even though the true payment total is not fundable.
