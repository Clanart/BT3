## Analog Identified: Pure-Python `MergeFromString`/`ParseFromString` can raise exceptions outside its documented contract

### Title
Pure-Python decoder's exception-safety contract can be violated by malformed field data, causing unhandled exceptions instead of `DecodeError` - (File: `python/google/protobuf/internal/decoder.py`, `python/google/protobuf/internal/python_message.py`)

### Summary
The GHSA-4g63-c64m-25w9 report describes `SignatureChecker.isValidSignatureNow`, a function explicitly documented as "not expected to revert," reverting anyway because of an incorrect assumption baked into how it decodes returned bytes (`abi.decode`), for input from an untrusted, non-conforming counterpart. The Protobuf analog is the pure-Python message implementation's `MergeFromString`/`ParseFromString`, which is documented and contractually expected to convert all parsing failures on attacker-controlled bytes into a single, catchable `message.DecodeError`, but only actually catches a fixed, hard-coded set of exception types.

### Finding Description
The pure-Python decoder module states its exception contract explicitly: [1](#0-0) 

`_AddMergeFromStringMethod` implements this contract by wrapping `_InternalParse` and catching only `IndexError`, `TypeError`, and `struct.error`, converting them to `message.DecodeError`: [2](#0-1) 

This mirrors the `SignatureChecker` bug pattern exactly: the caller assumes a bounded, closed set of failure modes for attacker-controlled, non-conforming binary input, and builds an exception-catching contract around that assumption. In `SignatureChecker`, the assumption was that `abi.decode` on a length-prefixed return value either succeeds or reverts in a way the caller controls; in reality malformed return data from a non-EIP-1271-conforming contract could still cause `abi.decode` to revert unexpectedly outside the intended try/catch boundary. In `MergeFromString`, the assumption is that decoders/value-transformers invoked while parsing attacker-controlled bytes only ever raise `IndexError` (truncation) or `struct.error` (fixed-width unpack failure) — but decoding helpers in `decoder.py` are not restricted to only those exception types. For instance, `_VarintDecoder`'s streaming code path explicitly raises a bare `ValueError`, a type not in the caught set: [3](#0-2) 

Field-value decoding (e.g., string/UTF-8 validation, enum range checks, and similar in the surrounding decoder factories not shown here) is the kind of value-transform logic historically prone to raising exception types like `UnicodeDecodeError` outside the (`IndexError`, `TypeError`, `struct.error`) net. Because `field_decoder` functions returned by `_SimpleDecoder`/`_ModifiedDecoder`/`EnumDecoder` are called directly inside `InternalParse` (itself called from the try/except block in `MergeFromString`), any decoder that raises something other than the three caught types will propagate straight out of `MergeFromString`/`ParseFromString` to the caller as an uncaught, undocumented exception, rather than the promised `DecodeError`.

### Impact Explanation
Any Python application that calls `Message.ParseFromString()`/`MergeFromString()` on attacker-supplied binary Protobuf bytes and is written to expect only `google.protobuf.message.DecodeError` (per the documented contract) can be caused to raise an unexpected, uncaught exception type instead. Applications that catch `DecodeError` specifically to reject malformed input gracefully (a very common pattern for public parse APIs) would instead see the exception escape their handler, potentially causing an unhandled-exception crash, differing error-handling paths, or (depending on the surrounding framework) an unintended fail-open/fail-closed behavior change. This is a direct violation of a documented parsing invariant, matching the "not expected to revert but does" bug class, though the impact is scoped to applications that rely on this specific pure-Python fallback path (the C++-backed extension implementation follows a different, ptr/ctx-based parsing path and is not subject to this specific Python exception-typing issue).

### Likelihood Explanation
Likelihood is bounded by two factors: (1) the pure-Python message implementation is a fallback/alternate backend rather than the default C++-accelerated implementation in most production deployments, and (2) I could not fully confirm within the available exploration budget the exact exception types raised by the string/enum field decoders further down in `decoder.py` for malformed UTF-8 or out-of-range data, since the file view was cut off before reaching those decoder factories. The `_VarintDecoder`'s `ValueError` path is confirmed but only reachable via its `BytesIO`-based streaming mode (`pos is None`), which is not the mode used by `MergeFromString`'s memoryview-based call into `_InternalParse`; whether an analogous uncaught-exception path is reachable purely through the memoryview/`pos`-based call chain used by `MergeFromString` was not fully verified in this pass. This should be treated as the strongest observed structural analog to the reported bug class, but confirmation of a concrete, reachable input that triggers an uncaught non-(`IndexError`/`struct.error`/`TypeError`) exception through `MergeFromString` specifically would require reading the remainder of `decoder.py` (string/enum/message-set decoders) and running an actual parse, which was not completed here.

### Recommendation
Audit all decoder factories in `python/google/protobuf/internal/decoder.py` for any exception type raised on attacker-controlled input that is not `IndexError`, `struct.error`, or an existing `_DecodeError`, and either (a) normalize all such raises to `_DecodeError`, or (b) broaden the `except` clause in `MergeFromString` in `python/google/protobuf/internal/python_message.py` to catch the full, audited set of exception types that decoders can legitimately raise on malformed data, consistent with the documented contract at the top of `decoder.py`.

### Proof of Concept
Not executed/confirmed in this pass — a concrete minimal reproduction would require constructing a crafted binary Protobuf payload that reaches a decoder path other than fixed-width `struct.unpack` or the caught `IndexError`/`TypeError` cases (e.g., invalid UTF-8 bytes in a `string` field, if the string decoder indeed does a raw `.decode('utf-8')` without catching `UnicodeDecodeError`) and calling `SomeMessage().MergeFromString(payload)` from the pure-Python implementation (`PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python`), observing whether `UnicodeDecodeError` (or similar) escapes instead of `google.protobuf.message.DecodeError`. This step was not completed due to exploration limits, so this finding should be treated as a plausible, structurally well-supported analog rather than a fully confirmed exploit.

    serialized = memoryview(serialized)
