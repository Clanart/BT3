### Title
Deprecated `.transfer()` with fixed 2300-gas stipend used to return native SEI in `WSEI.withdraw` - (File: contracts/src/WSEI.sol)

### Summary
`WSEI.sol`, sei-chain's canonical Wrapped Sei (WSEI) contract — compiled and embedded as production artifacts under `x/evm/artifacts/wsei/` and deployable via the `deploy-wsei` CLI command — uses the deprecated `payable(msg.sender).transfer(wad)` call to return unwrapped native SEI to the caller in `withdraw()`.

### Finding Description
The `withdraw` function debits the caller's internal WSEI balance and then attempts to send back the equivalent amount of native SEI using Solidity's `.transfer()`: [1](#0-0) 
`.transfer()` forwards a hard-coded 2300 gas stipend to the recipient. If `msg.sender` is a smart contract (e.g. a multisig, smart-contract wallet, proxy, or any contract whose `receive`/`fallback` performs storage writes, external calls, or other gas-intensive logic), the forwarded stipend can be insufficient, causing the native-SEI transfer to revert and the entire `withdraw` transaction to fail. Any unprivileged EVM account can trigger this simply by depositing to WSEI from a contract with a nontrivial receive function and then calling `withdraw`.

### Impact Explanation
Because `balanceOf[msg.sender]` is decremented before the `.transfer()` call, a permanently reverting `withdraw()` for a contract-based holder means that holder's WSEI can never be redeemed for native SEI through this path — the wrapped balance is stuck (WSEI is minted 1:1 against locked native SEI, so this is a freezing-of-funds condition for any smart-contract account whose fallback needs more than 2300 gas, which is common for modern smart-contract wallets/proxies that perform basic accounting on receipt). This matches the Medium-severity fund-freezing impact class validated by the rules (permanent freezing for affected callers), since the affected wallet has no alternative in-protocol path to redeem the same funds through this contract.

### Likelihood Explanation
Likelihood is moderate-to-high: any contract wallet whose `receive`/`fallback` consumes more than 2300 gas (a widespread and increasingly common pattern, e.g., Gnosis Safe modules, ERC-4337 smart accounts, or any contract emitting an event or writing storage on receipt) will hit this immediately and deterministically on every `withdraw` call, with no special privileges or race conditions required — only a normal EVM transaction from that contract.

### Recommendation
Replace the fixed-stipend `.transfer()` call in `WSEI.withdraw` (and mirror the fix in the identical pattern in `evmrpc/solidity/ERC20.sol`) with a low-level `call` that forwards all available gas and checks the boolean result:
```solidity
(bool success, ) = msg.sender.call{value: wad}("");
require(success, "WSEI: ETH_TRANSFER_FAILED");
```
This follows the same safe pattern already used elsewhere in the codebase, e.g. `TransferHelper.safeTransferETH` in `integration_test/load_generator/contracts/uniswapv2/libraries/TransferHelper.sol`.

### Proof of Concept
1. Deploy a simple contract `Holder` whose `receive() external payable` performs an `SSTORE` (e.g., increments a counter), consuming more than 2300 gas.
2. From `Holder`, call `WSEI.deposit{value: 1 ether}()`. `balanceOf[Holder]` becomes `1 ether`.
3. Call `WSEI.withdraw(1 ether)` from `Holder`. The internal call chain executes `payable(msg.sender).transfer(wad)`; because the 2300 gas stipend is insufficient for `Holder.receive()` to complete its `SSTORE`, the low-level call reverts, `.transfer()` bubbles up the revert, and the entire `withdraw` transaction fails, even though `balanceOf[Holder]` was already decremented in the same execution — leaving `Holder`'s SEI permanently locked in the WSEI contract with no alternative redemption path in this contract.
