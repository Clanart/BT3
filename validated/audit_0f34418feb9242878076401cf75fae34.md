### Title
SimplexPaymaster mispriced gas when a Chainlink feed hits its `minAnswer`/`maxAnswer` circuit breaker, allowing gas to be paid with worthless tokens — ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster._getOraclePrice()` validates a Chainlink `latestRoundData()` result only for non-positive answers and staleness. It never checks the returned `answer` against the aggregator's own `minAnswer`/`maxAnswer` circuit-breaker bounds. This is the exact bug class from the referenced Blueberry report (M-16): when the underlying asset's price crashes past the aggregator's floor, the feed keeps returning the frozen floor price instead of the real price, and the consumer values the asset at the stale floor. In `SimplexPaymaster` this directly and quantifiably mis-prices the ERC-20 gas token relative to native gas, letting any UserOp sender pay for gas with a token that is worth far less than the paymaster charges it as, draining real value (ETH in the EntryPoint deposit / ERC-20 surplus) from the paymaster/treasury. [1](#0-0) 

### Finding Description
`_getOraclePrice()` is the sole gate on both the `token/USD` and `native/USD` Chainlink feeds used to compute the ERC-20 gas price: [2](#0-1) 

It only reverts on `answer <= 0` (`InvalidOraclePrice`) or on staleness beyond `maxOracleAge` (`StaleOraclePrice`). Chainlink aggregators, however, additionally enforce a `minAnswer`/`maxAnswer` circuit breaker inside the aggregator itself: if the true price falls below `minAnswer` (or exceeds `maxAnswer`), `latestRoundData()` continues to report a fresh, positive, recently-updated `answer` that is pinned at the floor/ceiling rather than reality. Neither the `answer <= 0` check nor the staleness check catches this — the round is legitimately "fresh" and positive; it is simply wrong.

This value feeds directly into `_tokenPrice()`: [3](#0-2) 

`tokenPrice = (nativeUsd * 10^tokenDecimals * (10000+markupBps)) / (tokenUsd * 10000)` — the amount of the registered ERC-20 token charged per wei of gas. `_fetchDetails()` reads this price on every UserOp validation for any registered/active token (permissionless — any account can submit a UserOp using the paymaster), and `PaymasterERC20` uses it to compute `erc20Cost = weiCost * tokenPrice / 1e18`, pulled from the sender via `transferFrom`/permit: [4](#0-3) 

If a registered token's real market value crashes below its feed's `minAnswer` floor (e.g. a stablecoin depeg, or any registered token undergoing a LUNA-style collapse), `tokenUsd` stays frozen at the floor (higher than the token's real value). Since `tokenPrice` is inversely proportional to `tokenUsd`, an inflated `tokenUsd` makes `tokenPrice` too low — i.e., the paymaster charges fewer token units per wei of gas than the token is actually worth. Any UserOp sender can then pay gas fees in the crashed token at the stale floor valuation while the paymaster's EntryPoint deposit is drained for real ETH, and the residual token balance held by the contract is worth a fraction of what governance's `swapAndDeposit()`/`_withdrawAssets()` accounting assumes.

Existing guards do not stop this path:
- `answer <= 0` — the floor/ceiling value is still positive.
- staleness (`updatedAt`) — the aggregator still updates the round timestamp even while pinned at the floor, so the price looks "fresh".
- `TokenNotRegistered`/`TokenNotActive` — only checks whether the token is currently listed, not whether its price is trustworthy.
- Governance can `DeactivateToken`, but nothing on-chain detects the min/max-pinned condition automatically; it requires an operator noticing off-chain, by which point loss has already occurred, and there is no reentrant/replayable defense in the contract itself.

The same unguarded pattern also affects `swapAndDeposit()`'s `amountOutMin` derivation, which reuses `_getOraclePrice()` for both oracles: [5](#0-4) 

A pinned `tokenUsd` here computes a wrong (too high or too low) `expectedWei`/`amountOutMin`, but that call is `treasury`-gated, so the primary unprivileged attack surface is the permissionless `_fetchDetails()`/`_validatePaymasterUserOp()` gas-pricing path.

### Impact Explanation
This is a direct loss-of-funds vector against the paymaster's own reserves (EntryPoint ETH deposit and ERC-20 float), reachable by any unprivileged UserOp sender using a registered token whose Chainlink feed has hit its circuit breaker — no malicious relayer, prover, or governance actor is required. Repeated exploitation (many UserOps paid with the crashed/pinned token) can drain the paymaster's EntryPoint deposit of real native gas value while the contract accrues an ERC-20 balance worth far less than the ETH it paid out, matching the bounty's "stealing or loss of funds" / "logic attacks" impact classes.

### Likelihood Explanation
Likelihood is bounded by the precondition that a *registered* token's underlying Chainlink feed must actually hit its `minAnswer`/`maxAnswer` bound — a real, historically observed event for Chainlink feeds (e.g. LUNA, and periodic stablecoin depegs approaching feed floors). Once that precondition holds, exploitation requires nothing more than submitting ordinary UserOps through the paymaster with the affected token, which is the paymaster's normal, permissionless intended use — comparable to the accepted-as-Medium severity of the original Blueberry finding.

### Recommendation
In `_getOraclePrice()`, additionally fetch and enforce the aggregator's configured `minAnswer`/`maxAnswer` bounds (e.g. via the aggregator's `aggregator()`/`phaseAggregators` accessor or a governance-configured bound per token), and revert (e.g. a new `OraclePriceOutOfBounds` error) when the reported `answer` is at or near those bounds. As a defense-in-depth measure independent of feed internals, also consider cross-checking `tokenUsd`/`nativeUsd` against a secondary source (TWAP, secondary oracle) before trusting a single Chainlink round for pricing, and/or capping the maximum single-UserOp token exposure so a mispriced feed cannot drain more than a bounded amount before governance can react.

### Proof of Concept
1. Governance registers token `T` with a Chainlink `token/USD` feed via `RegisterToken` (`onAccept` → `_registerToken`), per [6](#0-5) .
2. `T`'s market price crashes far below the feed's configured `minAnswer` (e.g. a depeg/LUNA-style event). The aggregator's internal circuit breaker keeps `latestRoundData()` returning `answer == minAnswer` with a current `updatedAt`.
3. `_getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals)` returns the stale floor price; `answer > 0` and `updatedAt` is fresh, so both existing checks pass, per [2](#0-1) .
4. An attacker submits UserOps using `T` as the gas token (mode `0x00`/`0x01` in `paymasterData`). `_fetchDetails()` computes `tokenPrice` using the inflated `tokenUsd`, undercharging `T` relative to its real (crashed) value, per [7](#0-6)  and [3](#0-2) .
5. `PaymasterERC20` pulls the undercharged `T` amount from the attacker and the EntryPoint deducts the real gas cost in ETH from the paymaster's deposit. Repeating across many UserOps drains real ETH value from the paymaster while it accumulates a near-worthless `T` balance — a quantifiable, unauthorized loss of paymaster funds with no privileged actor involved.

Existing test coverage (`testStaleOracleReverts`, `testNonPositiveOraclePriceReverts` in `evm/tests/foundry/SimplexPaymasterTest.t.sol`) confirms only the staleness and non-positive cases are guarded, per [8](#0-7) ; no test exercises a min/max-pinned aggregator, confirming the gap.

```text
    /// @dev Returns the token to charge and its price relative to native gas.
    ///
    ///      PaymasterERC20 computes `erc20Cost = weiCost * tokenPrice / 1e18`,
    ///      so tokenPrice must be token base units per wei, scaled by 1e18:
    ///        tokenPrice = (nativeUsd * 10^tokenDecimals) / tokenUsd
    ///      e.g. BNB at $600, USDC at $1 with 6 decimals: 0.001 BNB (1e15 wei)
    ///      should cost 0.60 USDC (600000 units), giving tokenPrice = 6e8, which
    ///      is exactly (600e8 * 1e6) / 1e8. Markup is applied on top.
    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }
```

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
