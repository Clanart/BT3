### Title
Missing zero-check on `Kip71GasTarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: params/kip71_config.go)

### Summary
`params.KIP71Config.NextMagmaBlockBaseFee` uses `GasTarget` as a divisor when computing the next base fee, but the governance parameter validation for `Kip71GasTarget` does not reject a value of `0`, unlike the sibling parameter `Kip71BaseFeeDenominator` which explicitly does. A governance vote setting `governance.kip71.gastarget` to `0` will be accepted by parameter validation and, once activated, cause every node computing the next block's base fee to panic on integer division by zero.

### Finding Description
`NextMagmaBlockBaseFee` divides by `gasTarget` in both the "gas used above target" and "gas used below target" branches: [1](#0-0) [2](#0-1) 

`gasTarget := kc.GasTarget` comes directly from governance configuration with no fallback for zero (unlike `BaseFeeDenominator`, which has an explicit `if kc.BaseFeeDenominator == 0 { ... set to 64 }` fallback): [3](#0-2) 

The governance parameter registry validates `Kip71BaseFeeDenominator` with a `FormatChecker` that rejects zero: [4](#0-3) 

But `Kip71GasTarget` uses `noopFormatChecker`, which performs no validation at all and therefore accepts `0`: [5](#0-4) 

The accepted value flows unchanged into `ParamSet.GasTarget` and then into `KIP71Config.GasTarget` via `ToKip71Config`: [6](#0-5) [7](#0-6) 

Since `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)` will almost certainly be non-zero for any block that processes transactions, and `gasTarget == 0` makes `parentGasUsed > gasTarget` true, the code proceeds to `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor, which panics (`big.Int.Div` panics on division by zero) rather than returning a graceful error.

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked during header validation/computation for every block after the Magma hard fork on every full/consensus node (`VerifyMagmaHeader` and block-building code paths depend on it). A single governance vote that (accidentally or maliciously, via legitimate governing-node voting power) sets `governance.kip71.gastarget = 0` will, once the vote is finalized/epoch-activated, cause every node in the network to panic while validating or building the next block whose gas usage is nonzero. This halts block production/validation network-wide — a consensus-liveness/state-transition failure across all honest nodes, which is a Medium-severity availability/state-transition defect analogous to the reported division-by-zero bug class (an unchecked governance-facing numeric parameter used unguarded as a divisor).

### Likelihood Explanation
Likelihood depends on a governance vote being cast/approved with `GasTarget = 0`. This requires governing-council voting privilege rather than an arbitrary unprivileged transaction, but the underlying code defect — accepting a value that is provably unsafe as configured — is a genuine validation gap: the codebase's own author pattern (seen with `Kip71BaseFeeDenominator`'s explicit non-zero `FormatChecker`) shows the zero case was considered for one parameter but omitted for the structurally identical divisor parameter `GasTarget`. This is a straightforward oversight/inconsistency bug, not a hypothetical attack requiring insider network compromise beyond governance participation, which is an in-scope category ("governance parameters") per the reachable-surface rules.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0` (mirroring `Kip71BaseFeeDenominator`), and/or add a defensive zero-check with a safe fallback (as already done for `BaseFeeDenominator`) inside `KIP71Config.NextMagmaBlockBaseFee` in `params/kip71_config.go` before using `gasTarget` as a divisor.

### Proof of Concept
1. Submit/approve a governance vote setting `governance.kip71.gastarget = 0`. `PartialParamSet.Add` accepts it because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` (always returns true).
2. Once the new parameter set activates at the next epoch, `ParamSet.ToKip71Config()` produces a `KIP71Config{GasTarget: 0, ...}`.
3. On the next block whose `parentHeaderGasUsed > 0` (essentially any block with transactions), `NextMagmaBlockBaseFee` computes `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)` (nonzero), sees `parentGasUsed > gasTarget (0)`, and executes `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, which panics.
4. Every node calling `VerifyMagmaHeader`/`NextMagmaBlockBaseFee` for header validation or block building panics, halting block processing network-wide.
