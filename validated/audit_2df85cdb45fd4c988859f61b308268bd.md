## Local Analog Found

### Title
Relayer fee ledger is zeroed optimistically before destination payout is confirmed, permanently losing rewards on destination-side failure - (File: modules/pallets/relayer/src/withdrawal.rs)

### Summary
The external report's broken invariant is: a locally-tracked accounting value (`currentSupply`) is mutated (or fails to be mutated) without being tied to the real, verifiable state it represents, so the bookkeeping value and the actual resource permanently diverge and funds/units become unrecoverable. The same pattern exists in `pallet-relayer`'s fee withdrawal flow: the `Fees` ledger is zeroed on Hyperbridge as soon as an outbound withdrawal message is *dispatched*, not when the destination chain has actually *paid out* the funds.

### Finding Description
`Pallet::withdraw` in [1](#0-0)  reads the relayer's accrued balance via `Fees::<T>::get(...)`, dispatches a fire-and-forget ISMP POST (`timeout: 0`, meaning the request never expires) instructing the destination's `HostManager`/`EvmHost` to disburse `available_amount`, and then immediately sets `Fees::<T>::insert(dest_chain, address, U256::zero())` — before there is any proof that the destination chain executed the payout.

On the EVM side, `HostManager.onAccept` unconditionally forwards to `IHostManager(_params.host).withdraw(withdrawParams)` [2](#0-1) . If that destination-side transfer reverts — insufficient fee-token balance held by the `EvmHost` contract, a stale/misconfigured `HostParams.fee_token`, or any other execution failure — the request is simply never successfully delivered. Because the withdrawal dispatch uses `timeout: 0`, there is no timeout callback path on `pallet-relayer` that could re-credit `Fees`; the pallet has no `on_timeout`/failure handler for `WithdrawRelayerFees`/`WithdrawalParams` at all (confirmed absent via search of the relayer pallet). The source-side ledger (`Fees`) has already been zeroed unconditionally as part of the same extrinsic that dispatched the message, so the relayer's claim to that balance is destroyed regardless of whether the destination chain ever actually pays.

This mirrors the SWSupplyManager bug precisely: a tracked balance (`currentSupply`/`Fees`) is decremented/zeroed based on an action (`burn`/`dispatch_request`) whose real-world effect (tokens actually gone/reward actually paid) is not verified or tied back to the ledger update, and there is no safety check preventing the ledger from reaching a state that no longer matches reality, with no path to recover.

### Impact Explanation
If the destination-side `HostManager`/`EvmHost` cannot pay out (e.g., insufficient balance accumulated there, wrong fee token configured, or any other permanent revert condition), the relayer's earned reward is lost permanently: `Fees` is already zero on Hyperbridge, so the relayer cannot re-request the withdrawal, and there is no re-credit mechanism. This is a direct "loss of funds" case for the relayer-rewards accounting model, which the bounty scope explicitly protects ("relayer rewards... must move exactly once and only to the rightful beneficiary and amount") — here the funds move zero times but the ledger records them as moved.

### Likelihood Explanation
This does not require a malicious actor, relayer, or admin — it triggers under ordinary operation any time the destination `HostManager`/`EvmHost` fee-token balance is insufficient relative to accumulated `Fees` claims (e.g., multiple relayers withdrawing concurrently against a slowly-replenished balance, or a misconfigured `fee_token`/`host_manager` address in `HostParams`). Because `timeout: 0` removes any timeout-driven remediation, the failure mode is silent and has no automated recovery.

### Recommendation
Do not zero `Fees` until the destination payout is confirmed. Either (a) hold the withdrawal in a "pending" sub-ledger and only clear `Fees` once a delivery/receipt proof is observed (mirroring the receipt-based idempotency pattern already used in `OutboundRequestDeliveryClaim`/`OutboundConsensusDeliveryClaim`), or (b) give the dispatch a real timeout and implement an `on_timeout` handler that re-credits `Fees::<T>::insert(dest_chain, address, available_amount)` so a failed/undelivered withdrawal is reversible.

### Proof of Concept
1. Relayer accrues `Fees[dest_chain][relayer] = X` via normal `accumulate_fees` flow.
2. `EvmHost` on `dest_chain` currently holds `< X` in the configured fee token (e.g., because governance hasn't topped it up, or other relayers already drained it via concurrent withdrawals).
3. Relayer calls `withdraw()`: `available_amount = X` is read, the outbound `WithdrawalParams` POST is dispatched with `timeout: 0`, and `Fees::<T>::insert(dest_chain, relayer, 0)` executes in the same extrinsic [3](#0-2) .
4. Delivery reaches `HostManager.onAccept` → `EvmHost.withdraw()`, which reverts due to insufficient balance [4](#0-3) .
5. The relayer's `Fees` entry on Hyperbridge is now `0`; no on-chain path exists to reclaim `X`, and no timeout ever fires to restore it.

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
