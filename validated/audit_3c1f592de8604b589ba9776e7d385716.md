### Title
Unbounded re-snapshotting of `totalEndRemainingAllocation` + non-decrementing `totalBonus` allows bonus-pool over-extraction - ([File: rewards/Airdrop.sol])

### Summary
`Airdrop.updateEndRemainingAllocation()` is a public, unguarded function that can be called repeatedly by anyone after `periodsEndTime[4]`, each time overwriting `totalEndRemainingAllocation` with the *current* `totalRemainingAllocation` rather than a one-time immutable snapshot. Combined with the fact that `totalBonus` is only ever incremented (never decremented when bonus is actually paid out in `getBonusAmount`), a claimant can shrink the bonus-share denominator right before their own `claim()` call, causing cumulative bonus payouts across claimants to exceed the actual `totalBonus` pool that was funded by forfeitures.

### Finding Description
In `rewards/Airdrop.sol`: [1](#0-0) 

`updateEndRemainingAllocation()` has no guard preventing re-execution once `totalEndRemainingAllocation` is already non-zero — it simply re-assigns it to `totalRemainingAllocation` every time it's called after period 4. `claim()` only auto-invokes it once (`if (totalEndRemainingAllocation == 0)`): [2](#0-1) 

Since every `claim()` (whether early or late) unconditionally reduces `totalRemainingAllocation -= userAllocation` (line 164), each successive post-period-4 claim shrinks `totalRemainingAllocation`. If a subsequent claimant (or anyone) calls `updateEndRemainingAllocation()` again *after* other late-claimers have already claimed, the denominator used in `getBonusAmount` shrinks to reflect only the remaining unclaimed allocations, while the numerator `totalBonus` (line 138-141) stays exactly the same fixed value it was before any of that pool was paid out — because `totalBonus` is never decremented in `claim()` when bonus is actually disbursed (only incremented via `forfeited`, lines 165-168).

This means: (1) claimant D claims post-period-4 first, receives `bonus_D = D_alloc/1100*totalBonus`; `totalRemainingAllocation` drops to just `C_alloc`. (2) Attacker/claimant C (or an accomplice) calls `updateEndRemainingAllocation()` again, resetting `totalEndRemainingAllocation` to `C_alloc` alone. (3) C claims and receives `bonus_C = C_alloc/C_alloc*totalBonus = totalBonus` — i.e., the *entire* original bonus pool a second time. The sum `bonus_D + bonus_C` now exceeds the single `totalBonus` pool that was actually funded by forfeitures, breaking the conservation invariant. No existing modifier (no `nonReentrant`, no "already snapshotted" flag) prevents this re-snapshot.

### Impact Explanation
This directly causes protocol insolvency / theft of other users' unclaimed principal: aggregate bonus payouts can exceed the `totalBonus` actually accumulated from forfeitures, so the contract pays out more `aidropToken` than was ever forfeited — funds that can only come from other users' still-unclaimed allocation principal held in the same balance. Later legitimate claimants may then hit `InsufficientBalance` (line 160) and have their funds permanently frozen/undercollateralized, or an attacker positioned to claim near-last can extract a disproportionately large, non-pro-rata share of the bonus pool. This matches "direct theft of user funds" / "protocol insolvency" / "funds frozen ≥24h" impact classes.

### Likelihood Explanation
Fully reachable by an unprivileged EOA: `updateEndRemainingAllocation()` and `claim()` are both public/external with no access control, no reentrancy guard on the ordering, and no requirement to have any special allocation size. It requires no flash loan, no admin/owner rights — only (a) waiting until after `periodsEndTime[4]`, (b) observing that at least one other late-claimer has already reduced `totalRemainingAllocation`, and (c) calling `updateEndRemainingAllocation()` immediately before one's own `claim()`. This is trivially repeatable by any of the remaining late claimants and does not require collusion, since each successive claimant benefits from calling this refresh right before claiming.

### Recommendation
Make `totalEndRemainingAllocation` a true one-time snapshot: add a boolean/timestamp guard so it can only be set once (e.g., `require(totalEndRemainingAllocation == 0)` inside `updateEndRemainingAllocation()`, mirroring the check already done in `claim()`), and/or decrement `totalBonus` by the exact `bonusAmount` paid out inside `claim()` so the pool is conserved regardless of snapshot timing.

### Proof of Concept
Foundry test outline:
1. Deploy `Airdrop` with `startTime = now + 1`; `register([A,B,C,D],[1000,1000,100,1000])`.
2. Warp to `periodsEndTime[0]`; `A.claim()` and `B.claim()` (10% each, forfeiting 900 each) → `totalBonus = 1800`, `totalRemainingAllocation = 1100` (C+D).
3. Warp to `periodsEndTime[4]`.
4. `D.claim()` → triggers first `updateEndRemainingAllocation()` (`totalEndRemainingAllocation = 1100`); D receives `1000 + 1000/1100*1800 ≈ 2636`. `totalRemainingAllocation` now `100` (C only).
5. Call `updateEndRemainingAllocation()` again (callable by anyone, e.g. C) → `totalEndRemainingAllocation` reset to `100`.
6. `C.claim()` → `bonusAmount = 100/100*1800 = 1800`; C receives `100 + 1800 = 1900`.
7. Assert `bonus_D (1636) + bonus_C (1800) = 3436 > totalBonus (1800)`, and assert total tokens paid out (`100+100+2636+1900 = 4736`) exceeds total registered allocations (`3100`) by `1636`, proving the conservation invariant is broken and demonstrating fund extraction beyond deposited/forfeited amounts.

```text
    function claim() external {
        if (totalEndRemainingAllocation == 0) {
            updateEndRemainingAllocation();
        }
        uint256 claimableAmount = getClaimableAmount(msg.sender);
        
        if(claimableAmount == 0) revert NothingToClaim();
        if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();

        uint256 userAllocation = allocations[msg.sender];
        allocations[msg.sender] = 0;
        totalRemainingAllocation -= userAllocation;
        if (claimableAmount <= userAllocation) {
            uint256 forfeited = userAllocation - claimableAmount;
            totalBonus += forfeited;
        }
        aidropToken.safeTransfer(msg.sender, claimableAmount);
    }
```
