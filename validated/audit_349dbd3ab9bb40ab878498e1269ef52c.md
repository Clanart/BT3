### Title
`Scanner::scan_block` reports coinbase (immature) outputs as received funds which cannot be spent for 100 blocks - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
CVE-2019-19234's bug class is "a blocked/disabled state is not considered, so an excluded principal can still be impersonated/used." The analog in `bitcoin-serai` is `Scanner::scan_block`, which iterates `block.txdata` in full — including `txdata[0]`, the coinbase transaction — and emits `ReceivedOutput`s for it. Coinbase outputs are consensus-unspendable for 100 blocks (COINBASE_MATURITY). The function does not consider this "blocked" state of the output, so it reports funds as received that are not actually spendable.

### Finding Description
`Scanner::scan_transaction` maps any output whose `script_pubkey` matches a registered script to a `ReceivedOutput` with the output's real `OutPoint` and value (networks/bitcoin/src/wallet/mod.rs lines 199-214). `scan_block` simply calls it for every transaction in the block including index 0, the coinbase (lines 221-227).

Any miner — an unprivileged party — can craft a coinbase transaction paying to a Serai multisig address (the plain `p2tr_script_buf(key)` script is registered by `Scanner::new`, or any registered offset). `scan_block` then returns a `ReceivedOutput` for an outpoint that no transaction may legally spend until 100 confirmations pass.

Contrast with the production integration: `Bitcoin::get_outputs` explicitly skips `block.txdata[0]` with the comment "Skip the coinbase transaction which is burdened by maturity" (processor/src/networks/bitcoin.rs line 691). That means `scan_block`, the in-scope public API, retains a state-check omission that downstream consumers must silently know about; the doc comment on `scan_block` says "a post-processing pass is needed," which documents rather than fixes the missing check — the API itself accepts and reports an unusable output.

### Impact Explanation
Any caller that scans blocks via `scan_block` (rather than `scan_transaction` over `txdata[1..]`) and feeds the results into scheduling/wallet logic will treat miner-generated coinbase outputs to a multisig as received, immediately-spendable funds. This enables reporting of funds received that are not spendable (a stated acceptance criterion), and could cause attempted spends that are consensus-invalid, triggering signing rounds for transactions that can never confirm, or accounting crediting funds that fail at broadcast.

### Likelihood Explanation
Requires a Bitcoin miner to include an output paying a Serai-registered script in a coinbase — fully within reach of an unprivileged party willing to mine a block (on regtest trivially; on mainnet costly but permissionless). The bug is deterministic once triggered: `scan_block` unconditionally includes `txdata[0]`.

### Recommendation
Skip `block.txdata[0]` inside `Scanner::scan_block` itself, matching the behavior already implemented in `Bitcoin::get_outputs`, rather than relying on callers to post-process. Alternatively, annotate `ReceivedOutput` with a maturity flag so consumers can distinguish coinbase outputs.

### Proof of Concept

// Construct a regtest block whose coinbase pays to a registered Serai script:
// p2tr_script_buf(key) is registered by Scanner::new at networks/bitcoin/src/wallet/mod.rs:164
let scanner = Scanner::new(key).unwrap();
let block = mine_block_with_coinbase_paying(p2tr_script_buf(key).unwrap());
let outputs = scanner.scan_block(&block);
// outputs contains a ReceivedOutput for (coinbase_txid, vout) even though the
// outpoint is unspendable for 100 blocks; scan_transaction(&block.txdata[0])
// produces the same result, as demonstrated by the test asserting
