### Title
Cross-shop session/data destruction via unauthenticated `X-Shopify-Shop-Domain` header trusted by webhook jobs - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#shop_domain` and the generated webhook controller (`webhook_controller.rb.tt`) derive the target shop solely from the unauthenticated `X-Shopify-Shop-Domain` request header, while HMAC verification only covers the raw request body. Since Shopify webhook HMACs are computed with a single app-wide client secret (not a per-shop secret), any actor who can obtain one genuinely-signed webhook (e.g., by installing the app on their own store) can replay that exact body+HMAC pair with a forged `X-Shopify-Shop-Domain` header pointing at an arbitrary victim shop, causing the generated job (`AppUninstalledJob`, `ShopRedactJob`, `CustomersRedactJob`, etc.) to act against the victim's `Shop` record instead of the attacker's own.

### Finding Description
`verify_request` in `lib/shopify_app/controller_concerns/webhook_verification.rb` calls `hmac_valid?(request.raw_post)`, defined in `lib/shopify_app/controller_concerns/payload_verification.rb`, which computes `OpenSSL::HMAC.digest(digest, secret, data)` over the raw body using `ShopifyApp.configuration.secret` (and optionally `old_secret`) and compares it via `secure_compare` against the `X-Shopify-Hmac-Sha256` header. [1](#0-0) [2](#0-1) 

The HMAC digest input is only the raw body — it never includes `X-Shopify-Shop-Domain` or any other header. Immediately after HMAC validation succeeds, `shop_domain` reads directly from the unauthenticated header: [3](#0-2) 

This value flows unchecked into the generated controller and job templates. The declarative-webhook controller template passes `webhook_request.shop` (also header-derived) straight into `perform_later`: [4](#0-3) 

The mandatory privacy/uninstall job templates then use that value to look up and mutate a `Shop` record with no additional binding to the payload's actual origin: [5](#0-4) [6](#0-5) 

Because the app's webhook HMAC secret (`config.secret`/`config.old_secret`) is shared across all shops that install the app rather than shop-specific, a merchant who legitimately installs the app on their own store receives real, correctly-HMAC-signed webhooks (e.g., `app/uninstalled` upon uninstalling their own app). That attacker can capture the raw body + valid HMAC header pair and replay it to the app's webhook endpoint while substituting an arbitrary victim's domain in `X-Shopify-Shop-Domain`. `verify_request` still passes because the HMAC only certifies the body content, not the header. The resulting job is then enqueued with `shop_domain: victim.myshopify.com`, causing `AppUninstalledJob` to `shop.destroy` the victim's `Shop` record, or `ShopRedactJob`/`CustomersRedactJob` to run `shop.with_shopify_session` scoped to the victim — none of which are actually gated on any check that the payload actually originated for that shop.

### Impact Explanation
This allows a merchant controlling an unrelated shop (unprivileged attacker per the rules) to trigger destructive, tenant-mutating actions against a victim shop they do not control — e.g., destruction of the victim's stored `Shop`/session record via `AppUninstalledJob#perform`, effectively deauthorizing/uninstalling state for the victim inside the host app, or triggering shop-redaction workflows against the wrong tenant. This is a cross-tenant/session-confusion and denial-of-service impact class (forged webhook accepted as authentic for an arbitrary victim tenant), matching Shopify's "broken authentication/tenant isolation via forged webhook" impact category.

### Likelihood Explanation
Feasible and repeatable: the only precondition is possessing one genuinely-signed webhook body+HMAC pair, which any developer/merchant obtains automatically and repeatedly during ordinary app installs/uninstalls on their own store (a normal, unprivileged action). No secret leakage or victim cooperation is required — only replay of a captured legitimate request with a modified header, which any HTTP client can do.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or any other header) as the tenant identity for webhook-driven actions. Bind the resolved shop to data actually covered by the HMAC/verified payload (e.g., the `shop_id`/`shop_domain` embedded in the JSON body issued by Shopify for topics that include it, or validate the header value against a shop-specific webhook secret/registration record instead of the shared app secret) before using it to look up or mutate any `Shop` record.

### Proof of Concept
```ruby
test "forged shop-domain header on a validly-HMAC-signed webhook targets the wrong shop" do
  body = "{}"
  hmac = Base64.strict_encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyApp.configuration.secret, body)
  )

  post "/webhooks/app_uninstalled",
    params: body,
    headers: {
      "X-Shopify-Hmac-Sha256" => hmac,
      "X-Shopify-Shop-Domain" => "victim.myshopify.com", # attacker-forged, unrelated to signer
      "X-Shopify-Topic" => "app/uninstalled",
    }

  assert_response :no_content
  perform_enqueued_jobs
  # Fails: AppUninstalledJob destroys victim's Shop even though the HMAC
  # only proves the *body*, not that the payload concerns "victim".
  assert_nil Shop.find_by(shopify_domain: "victim.myshopify.com")
end

      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
