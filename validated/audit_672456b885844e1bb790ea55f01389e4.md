## Title
Unauthenticated leakage of encrypted emergency-stop transactions via `internal_get_emergency_stop_tx` when `client_verification` is disabled - (`core/src/rpc/aggregator.rs`)

## Summary
`ClementineAggregator::internal_get_emergency_stop_tx` is protected only by the `Internal` prefix convention enforced in `only_aggregator_and_self`, which checks that the caller's TLS leaf certificate matches the aggregator's own certificate. When the aggregator's gRPC server is configured with `client_verification = false`, `create_grpc_server` installs `Interceptors::Noop` instead, which performs no certificate check at all, so any unauthenticated caller reaching the port can invoke the "Internal" RPC directly.

## Finding Description
The binding the question implies is: `caller_authority(request to internal_get_emergency_stop_tx) == aggregator/security-council-authorized-reveal-flow`. This binding is enforced entirely by the `is_internal` + leaf-certificate check inside `only_aggregator_and_self` in `core/src/rpc/interceptors.rs` (lines 12-20, 62-69), not by any check inside `internal_get_emergency_stop_tx` itself (`core/src/rpc/aggregator.rs:1938-1971`), which unconditionally calls `self.db.get_emergency_stop_txs(None, txids)` (`core/src/database/aggregator.rs:33-61`) and returns whatever encrypted blobs exist for the requested `move_txid`s.

The enforcement point is selected in `create_grpc_server` (`core/src/servers.rs:106-138`): if `config.client_verification` is `true`, the server installs `OnlyAggregatorAndSelf{...}`; if `false`, it installs `Interceptors::Noop`, which is `Ok(req)` unconditionally (`core/src/rpc/interceptors.rs:9-10, 30`) — no certificate, no caller-identity check, no distinction between "Internal"-prefixed methods and any other method. Because `internal_get_emergency_stop_tx` has no independent authorization check of its own, when `client_verification` is `false` the "Internal" prefix convention provides zero protection, and the RPC is reachable by any client that can open a gRPC connection to the port and knows (or brute-forces/observes) a `move_txid`.

Exploit flow: attacker performs (or observes) any deposit's move-to-vault transaction becoming known (move_txids are public once broadcast on Bitcoin, or discoverable through withdrawal flows), then sends `GetEmergencyStopTxRequest{txids: [move_txid]}` to the aggregator's public port. `get_emergency_stop_txs` returns the row inserted by `verify_and_save_emergency_stop_sigs` (`core/src/rpc/aggregator.rs:916-922`) for any deposit that has completed the emergency-stop-signing step, regardless of whether the caller was ever a party to that deposit. This is a premature-disclosure issue only in the specific deployment configuration where `client_verification` is disabled.

## Impact Explanation
The disclosed data is the encrypted emergency-stop transaction blob (encrypted with `emergency_stop_encryption_public_key`, per `core/src/rpc/aggregator.rs:907-914`) plus its associated `move_txid`. This is ciphertext, not the plaintext emergency-stop transaction or any signature/secret usable to spend or move funds — decryption requires the security council's private key, which the attacker does not hold. No BTC moves, no reimbursement is misdirected, and no collateral is burned as a direct consequence of this leak alone. The concrete harm is metadata/commitment disclosure: an attacker learns which `move_txid`s already have an emergency-stop tx staged, and can collect ciphertexts ahead of the council's intended reveal timing, which the question's severity taxonomy (High: "premature disclosure of a protocol commitment") targets. Repeatable across every deposit for which `verify_and_save_emergency_stop_sigs` has run.

## Likelihood Explanation
This finding is entirely conditional on deployment configuration: it is exploitable **only** when the operator sets `client_verification = false` in `BridgeConfig` (`core/src/servers.rs:106-138`). In the default/intended production configuration (`client_verification = true`), `OnlyAggregatorAndSelf` is installed and the leaf-certificate check in `only_aggregator_and_self` correctly rejects any caller other than the aggregator's own client certificate for "Internal"-prefixed methods, per `core/src/rpc/interceptors.rs:62-69`. The attacker needs no BTC cost — just network reachability to the aggregator's gRPC port and any known/guessed `move_txid`, both trivially available to an unprivileged depositor.

## Recommendation
Do not rely solely on the `Internal` naming convention plus a TLS-only interceptor for authorization of `internal_get_emergency_stop_tx`. Add an explicit authorization check inside the RPC handler itself (e.g., verify the request originates from the aggregator's own process/self-call context, independent of `client_verification` configuration), so that disabling TLS client verification cannot silently strip protection from "Internal" endpoints. Alternatively, make `internal_get_emergency_stop_tx` refuse to serve requests entirely when `client_verification` is disabled, or gate it behind a separate always-authenticated channel (e.g., loopback/unix-socket only).

Test plan:
1. Build a `BridgeConfig` with `client_verification = false` and start the aggregator gRPC server via `create_grpc_server`/`create_aggregator_grpc_server` (or the Unix-socket test helper), confirming `Interceptors::Noop` is installed per `core/src/servers.rs:106-138`.
2. Perform a real `new_deposit` flow that reaches `verify_and_save_emergency_stop_sigs` (`core/src/rpc/aggregator.rs:850-925`), which calls `insert_signed_emergency_stop_tx_if_not_exists` to persist a row keyed by `move_to_vault_txid`.
3. From a fresh, unauthenticated tonic client (no client certificate presented, or a certificate belonging to neither the aggregator nor "self"), call `internal_get_emergency_stop_tx(GetEmergencyStopTxRequest{txids: [move_txid]})`.
4. Assert the RPC succeeds (no `Status::unauthenticated`) and `response.encrypted_emergency_stop_txs` is non-empty and matches the ciphertext stored via `get_emergency_stop_txs` — i.e., binding `caller_authority == aggregator/self` did not hold, yet disclosure occurred.
5. As a control, repeat with `client_verification = true` and confirm the same call is rejected with `Status::unauthenticated("Unauthorized call to internal method (not self)")` from `core/src/rpc/interceptors.rs:66-69`, demonstrating the vulnerability is specific to the `client_verification = false` configuration.     #[tracing::instrument(skip(self), err(level = tracing::Level::ERROR))]
```rust
    async fn internal_get_emergency_stop_tx(
        &self,
        request: Request<clementine::GetEmergencyStopTxRequest>,
    ) -> Result<Response<clementine::GetEmergencyStopTxResponse>, Status> {
        tracing::warn!("Get emergency stop tx rpc called");
        let inner_request = request.into_inner();
        let txids: Vec<Txid> = inner_request
            .txids
            .into_iter()
            .map(|txid| {
                Txid::from_slice(&txid.txid).map_err(|e| {
                    tonic::Status::invalid_argument(format!("Failed to parse txid: {e}"))
                })
            })
            .collect::<Result<Vec<_>, _>>()?;
        tracing::warn!(
            "Parsed get emergency stop tx rpc params, move txids: {:?}",
            txids
                .iter()
                .map(|txid| txid.to_string())
                .collect::<Vec<_>>()
        );

        let emergency_stop_txs = self.db.get_emergency_stop_txs(None, txids).await?;

        let (txids, encrypted_emergency_stop_txs): (Vec<Txid>, Vec<Vec<u8>>) =
            emergency_stop_txs.into_iter().unzip();

        Ok(Response::new(clementine::GetEmergencyStopTxResponse {
            txids: txids.into_iter().map(|txid| txid.into()).collect(),
            encrypted_emergency_stop_txs,
        }))
    }
```

```rust
    pub async fn get_emergency_stop_txs(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        move_txids: Vec<Txid>,
    ) -> Result<Vec<(Txid, Vec<u8>)>, BridgeError> {
        if move_txids.is_empty() {
            return Ok(Vec::new());
        }

        let mut query_builder = QueryBuilder::new(
            "SELECT move_txid, emergency_stop_tx FROM emergency_stop_sigs WHERE move_txid IN (",
        );

        let mut separated = query_builder.separated(", ");
        for txid in &move_txids {
            separated.push_bind(TxidDB(*txid));
        }
        query_builder.push(")");

        let query = query_builder.build_query_as::<(TxidDB, Vec<u8>)>();

        let results: Vec<(TxidDB, Vec<u8>)> =
            execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        Ok(results
            .into_iter()
            .map(|(txid, tx_data)| Ok((txid.0, tx_data)))
            .collect::<Result<_, eyre::Report>>()?)
    }
```
