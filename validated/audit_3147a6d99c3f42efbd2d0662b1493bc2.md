### Title
`SignableTransaction::new` hardcodes `lock_time` and `sequence`, giving users no way to bound transaction validity or enable replacement - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The reported bug class is a freshness/finality parameter that should be caller-controlled being silently hardcoded, so a delayed execution happens under stale conditions. In Serai's Bitcoin wallet, `SignableTransaction::new` accepts `inputs`, `payments`, `change`, `data`, and `fee_per_vbyte` from the caller, but unconditionally hardcodes `lock_time: LockTime::ZERO` and `sequence: Sequence::MAX` on every input, with no API to override either. `sequence: Sequence::MAX` additionally signals RBF-disabled for every input, so a broadcast transaction cannot be fee-bumped or replaced by the signer.

### Finding Description
The transaction template is built entirely inside `SignableTransaction::new`. Inputs are constructed with a fixed final sequence:

```rust
// networks/bitcoin/src/wallet/send.rs
sequence: Sequence::MAX,
```

and the resulting `Transaction` is sealed with a fixed zero lock time:

```rust
tx: Transaction {
  version: Version(2),
  lock_time: LockTime::ZERO,
  input: tx_ins,
  output: tx_outs,
},
```

`LockTime::ZERO` means the transaction is valid from the moment it exists until its inputs are spent — there is no expiration. `Sequence::MAX` (0xFFFFFFFF) disables BIP-125 opt-in replace-by-fee on every input and makes any nonzero `lock_time` moot anyway. Neither value is exposed as a parameter to `new`, nor is any setter provided on `SignableTransaction` before it is passed to `TransactionMachine`/`TransactionSignMachine`, which signs `taproot_key_spend_signature_hash` digests committing to exactly this fixed `lock_time`/`sequence` choice.

This mirrors the UniV3Swap finding directly: the caller controls the economic terms (payments, fee rate) but has no control over the temporal validity of the signed artifact. The threshold-signed transaction is valid at `block.timestamp` now and equally valid arbitrarily far in the future.

### Impact Explanation
Two concrete consequences follow from the hardcoded values:

1. **No validity bound (analogous to a missing deadline).** A threshold signature produced for a `SignableTransaction` remains valid indefinitely. If signing or broadcast is delayed — e.g., the coordinator retries signing attempts or the completion rebroadcast task republishes — the transaction can be mined at a much later time under conditions (fee market, payment intent, counterparties) the participants no longer agree to. The users have no mechanism to say "this payment is only valid within window X," exactly the exposure the original report describes where a stale request executes at a dramatically changed price.

2. **RBF disabled.** Because every input uses `Sequence::MAX`, the signed transaction explicitly opts out of BIP-125 replacement. During network congestion — the precise scenario cited in the original report — the transaction can sit unconfirmed at its fixed `fee_per_vbyte` and the signer set cannot replace it with a higher-fee version without producing a conflicting transaction that relays reject. The user is stuck: they cannot cancel (the signature never expires) and cannot accelerate (RBF is off). All funds committed in the inputs are locked behind whichever of the two signed variants confirms first, with the stale-priced one remaining a standing threat.

Impact is bounded to fund timeliness/finality rather than direct theft, consistent with the Medium severity of the source finding.

### Likelihood Explanation
Any threshold-signed Bitcoin payment passes through this code path, so every transaction produced by the wallet inherits the behavior. Congestion-delayed confirmation and delayed signing attempts are routine events, not adversary-only conditions. No attacker is required — though any party holding a signed-but-unbroadcast completion (e.g., a rebroadcast path or a stored `SignedBatch` artifact) can choose to publish it at an arbitrarily later, stale point.

### Recommendation
Expose `lock_time` (and/or a relative `sequence`/`Sequence::ENABLE_RBF_NO_LOCKTIME` choice) as caller-supplied parameters to `SignableTransaction::new`, validate them (e.g., reject `lock_time` in the far past; if a lock time is set, require `sequence < MAX`), and default `sequence` to an RBF-signaling value so signed transactions remain replaceable during congestion. Document that the resulting `Transaction`'s fields are committed to by the threshold signature via `Prevouts::All` sighash.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, &[(payment_script, amount)], Some(change), None, fee_per_vbyte)`.
2. Inspect the returned `SignableTransaction::transaction()`: `tx.lock_time == LockTime::ZERO` and every `tx.input[i].sequence == Sequence::MAX`, regardless of caller intent — no API exists to change them.
3. Run `multisig(keys)` → `preprocess` → `sign` → `complete` to produce a fully signed `Transaction`.
4. Broadcast it at a low fee during congestion: because all sequences are `MAX`, nodes reject any replacement (no BIP-125 signaling); because `lock_time` is zero, the signed transaction remains immediately and perpetually valid, so a held copy can be broadcast and mined at any future time under stale terms.
