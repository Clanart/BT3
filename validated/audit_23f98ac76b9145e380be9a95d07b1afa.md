### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s - (networks/bitcoin/src/wallet/mod.rs)

### Summary
The analog of "contract accepts Ether deposits that then get stuck" in Serai's Bitcoin code is that `Scanner::scan_block` scans `block.txdata[0]` — the coinbase transaction — and returns any matching outputs as ordinary `ReceivedOutput`s. Coinbase outputs are bound by Bitcoin's 100-block maturity rule, so these are funds "deposited" to the multisig that are reported as received yet cannot be spent. This matches the validate criterion "funds reported received that are not spendable".

### Finding Description
`Scanner::scan_transaction` iterates all outputs of a transaction and pushes a `ReceivedOutput` for every `script_pubkey` matching a registered script, with no distinction for coinbase transactions [1](#0-0) . `scan_block` then calls `scan_transaction` over *every* transaction in `block.txdata`, including `txdata[0]` (the coinbase) [2](#0-1) . The doc comment acknowledges the issue — "This will also scan the coinbase transaction which is bound by maturity" — but the function still returns those outputs by default, indistinguishable from spendable ones.

The bug is reachable from public inputs: any miner (or any party able to construct a block paying to the multisig's P2TR script, e.g. via a mining pool payout or a `generatetoaddress`-style flow) can cause a coinbase output to pay to a script the scanner tracks. The downstream consumer treats every `ReceivedOutput` uniformly — `ReceivedOutput` carries only `offset`, `output`, and `outpoint`, with no maturity flag [3](#0-2) . If such an output is fed to `SignableTransaction::new` and signed, the resulting transaction spends an immature coinbase and is rejected by the Bitcoin network; worse, the wallet's accounting has already recorded the funds as received.

Notably, the in-scope crate's own test asserts this behavior: `assert_eq!(outputs, scanner.scan_transaction(&block.txdata[0]))` confirms the coinbase is scanned identically to normal transactions [4](#0-3) . The processor happens to work around this by skipping `block.txdata[1 ..]`'s complement — i.e. it iterates `block.txdata[1 ..]` — but `scan_block` itself remains the public API whose default behavior is unsafe [5](#0-4) .

### Impact Explanation
Outputs reported as received are not spendable for 100 confirmations. Any consumer relying on `scan_block` (rather than manually slicing `txdata[1 ..]`) will schedule spends on immature coinbase outputs, producing consensus-invalid transactions and incorrect balance accounting — the exact "stuck deposit" shape of the reference report, where mistakenly deposited funds require special handling to avoid being treated as available.

### Likelihood Explanation
Requires a coinbase output paying to a tracked script. On mainnet this means a miner/pool directs a payout to the multisig address — plausible for a bridge address that pools may intentionally or accidentally pay to. The failure is silent at scan time and only manifests when the output is spent.

### Recommendation
`scan_block` should skip `block.txdata[0]` by default (matching what the processor already does manually in `get_outputs`), or `ReceivedOutput` should carry an `is_coinbase`/maturity flag so callers can filter. At minimum, `scan_transaction` could take an `is_coinbase: bool` parameter so the coinbase case cannot be silently merged with spendable outputs.

### Proof of Concept
```rust
// Regtest: mine a block paying to the scanner's key
let mut scanner = Scanner::new(key).unwrap();
// coinbase pays to p2tr_script_buf(key) -- e.g. generatetoaddress
let block: Block = /* fetch mined block */;

let outputs = scanner.scan_block(&block);
// outputs[0] is the coinbase output to our script.
// It is returned identically to a normal output:
assert_eq!(outputs[0].outpoint(), &OutPoint::new(block.txdata[0].compute_txid(), 0));

// Feeding it into SignableTransaction::new produces a TX that is
// consensus-invalid for 100 blocks (bad-txns-premature-spend-of-coinbase),
// yet the wallet already counted the value as received.
let tx = SignableTransaction::new(
  vec![outputs[0].clone()], &payments, change, None, fee,
).unwrap(); // signs an unspendable input
```
The existing test at `networks/bitcoin/tests/wallet.rs:65-69` already demonstrates the coinbase output is returned by both `scan_block` and `scan_transaction(&block.txdata[0])` with no marker distinguishing it.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
