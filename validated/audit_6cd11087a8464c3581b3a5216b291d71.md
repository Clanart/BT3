## Title
`LinkButton` opens externally-sourced GitHub repository URLs via `shell.openExternal` with no protocol allow-list, unlike other link surfaces in the app - (File: `app/src/ui/lib/link-button.tsx`)

### Summary
GitHub Desktop enforces an `http(s)`-only allow-list before invoking `shell.openExternal` on links rendered inside the sandboxed markdown viewer, but the same check is missing from `LinkButton`, the component used to render links built from GitHub API repository metadata (`htmlURL`) throughout the rest of the app (repo rules, fork dialogs, rich-text commit/issue links). This mirrors the reported bug class: a security check ("only open http/https") exists on one code path but is silently skipped on another path that handles the same class of attacker-influenced data, letting a malicious value bypass validation and reach a dangerous sink.

### Finding Description
`SandboxedMarkdown.setupLinkInterceptor` explicitly validates the link protocol before allowing navigation: [1](#0-0) 

By contrast, `LinkButton.onClick` — the generic link component used across the renderer — hands the `uri` prop straight to `shell.openExternal` with no scheme check whatsoever: [2](#0-1) 

The IPC handler in the main process that ultimately backs `shell.openExternal` also does not gate on protocol; it only logs when the URL happens to be `http(s)`, but calls `shell.openExternal(path)` for any string: [3](#0-2) 

`LinkButton` is fed URLs built from `GitHubRepository.htmlURL`, a value copied verbatim from the GitHub/GHE API's `html_url` field with no protocol validation at ingestion time: [4](#0-3) 

That unvalidated `htmlURL` is then interpolated into links rendered via `LinkButton` in multiple surfaces, e.g. repo rulesets and fork-creation errors: [5](#0-4) [6](#0-5) 

It is also the basis for issue/PR "shorthand" links produced by the commit-message tokenizer (`#123` links), which construct `${repository.htmlURL}/issues/${id}` and render through `RichText` → `LinkButton`: [7](#0-6) [8](#0-7) 

The broken invariant: "only open http(s) URLs via the OS shell" is enforced in the sandboxed-markdown click interceptor but not in the much more widely used `LinkButton`/`shell.openExternal` sink, nor in the data-ingestion step that stores `htmlURL` from the API response. An account connected to a malicious or compromised GitHub Enterprise Server (or an attacker able to tamper with API responses for a repository the user has added, e.g. via a compromising the GHE instance or session) can set `html_url` to an arbitrary non-`https` value. Desktop persists it unmodified and later opens it via `shell.openExternal` when the user clicks any of these repo/issue/PR links.

### Impact Explanation
`shell.openExternal` with an attacker-controlled non-`http(s)` URI can invoke arbitrary OS-registered URL protocol handlers (custom app URI schemes, `file:`, etc.), a well-documented Electron/OS attack surface for triggering unintended application behavior, credential prompts, or code execution in vulnerable third-party handlers — all with a single click on what looks like a normal "View ruleset"/"View on GitHub"/`#123` issue link inside Desktop. This falls squarely within the requested impact class: attacker controls a GitHub API object (repository metadata from a connected/malicious endpoint) and the result is potentially code execution or unauthorized action outside the repo, triggered by a link the user clicks.

### Likelihood Explanation
Exploitation requires the user to have added/authenticated to a repository whose GitHub API responses are attacker-influenced (malicious or compromised GitHub Enterprise Server, or a MITM position on that connection) — no local access, malware, or leaked credentials are needed. Since `htmlURL` is stored and reused across many UI surfaces (`repo-ruleset-link.tsx`, `repo-rulesets-for-branch-link.tsx`, `create-fork-dialog.tsx`, `rich-text.tsx`/`text-token-parser.ts`), there are many natural, low-suspicion click targets, increasing the odds a user triggers it during normal use.

### Recommendation
Enforce the same protocol allow-list used in `SandboxedMarkdown.setupLinkInterceptor` (`/^https?:/`) inside `LinkButton.onClick` before calling `shell.openExternal`, and/or validate `html_url`/`clone_url` to be `https:` (mirroring `enterprise-validate-url.ts`'s `validateURL`) when ingesting API repository data in `repositories-store.ts`. Consider also tightening the main-process `open-external` IPC handler to reject non-`http(s)` schemes by default.

### Proof of Concept
1. Connect Desktop to a malicious/compromised GitHub Enterprise Server (or intercept the API response for a repository already added).
2. Have the server return `html_url: "some-installed-app-protocol://malicious-args"` for that repository.
3. `repositories-store.ts` persists this value as `GitHubRepository.htmlURL` unchanged.
4. Any UI element using that repo's link (e.g. "View ruleset" in `RepoRulesetLink`, the fork-error "creating the fork manually on GitHub" link in `CreateForkDialog`, or an auto-linked `#123` issue reference in a commit message rendered by `RichText`) renders a `LinkButton` with `uri` set to the attacker's scheme.
5. User clicks the link; `LinkButton.onClick` calls `shell.openExternal(uri)` with no scheme check, and Electron/OS invokes whatever handler is registered for that protocol — unlike the `SandboxedMarkdown` markdown-comment path, which would have rejected the same URL.
