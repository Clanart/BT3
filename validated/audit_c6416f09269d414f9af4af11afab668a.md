### Title
Uncontrolled recursion in `PuzzleWithRestrictions.from_memo` via attacker-controlled `MofN` memo nesting - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a `MofN` custody structure by recursing once per nesting level found in an on-chain `CREATE_COIN` memo. The recursion depth is fully controlled by the coin creator (an unprivileged spend-bundle submitter) and is not bounded anywhere in this code path, unlike the CVE-2026-0990 pattern where `xmlCatalogXMLResolveURI` recurses without a depth limit on attacker-supplied catalog structure.

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses a `Program` memo and, when the "further branching" flag is set, builds a `MofN` node whose members are produced by recursively calling `PuzzleWithRestrictions.from_memo()` for each member memo: [1](#0-0) 

Nothing in this function enforces a maximum nesting depth, a maximum member count, or an iterative/stack-based traversal (contrast with `sha256_treehash`, which the codebase deliberately implemented non-recursively specifically to avoid "blowing out the python stack"): [2](#0-1) 

This `from_memo()` path is reachable from consensus data: `PlotNFT.get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` directly on the memo attached to a `CREATE_COIN` condition produced by an arbitrary coin spend when trying to recognize an unknown PlotNFT inner puzzle: [3](#0-2) 

Because a `CREATE_COIN` memo is just an arbitrary CLVM atom/list chosen by whoever creates the coin (any spend-bundle submitter can set memos on coins they create), an attacker can craft a coin memo that encodes a `MofN` hint nested tens of thousands of levels deep. When wallet code walks the singleton lineage and calls `PlotNFT.get_next_from_coin_spend()` on that spend to sync PlotNFT/pool state, `from_memo()`'s recursive descent will exhaust the Python call stack, raising an uncaught `RecursionError`.

### Impact Explanation
A crafted, deeply-nested memo on a coin created inside a normal spend bundle can trigger unbounded Python recursion in wallet code that processes singleton/PlotNFT lineage. This is a spend-triggered processing halt: a wallet (or any code path that calls `PlotNFT.get_next_from_coin_spend()` while syncing coin history, e.g. plotnft wallet sync) that encounters this coin can crash with a `RecursionError`, since no `RecursionError`/`ValueError`-to-`RecursionError` handling exists in this path (`get_next_from_coin_spend()` only catches `ValueError` around the `from_memo()` call, not `RecursionError`): [4](#0-3) 
This matches the "spend-triggered transaction-processing halt" acceptance criterion — a single malicious/crafted coin (creatable by any spend-bundle submitter) can deny service to wallet processing that reaches this recognition code.

### Likelihood Explanation
Likelihood is moderate: any spend-bundle submitter can create a coin with an arbitrary memo, and no cost/CLVM constraint bounds memo nesting depth (memos are plain CLVM data, not executed, so mempool CLVM cost limits do not bound Python-side parsing recursion once the memo is read off-chain by wallet code). The attack requires the crafted coin to actually be processed by `PlotNFT.get_next_from_coin_spend()` — i.e., a target wallet syncing a PlotNFT/pooling singleton lineage that includes the malicious coin as a create-coin memo needing "unknown inner puzzle" recognition. This is a real, wallet-reachable but somewhat narrower trigger than a fully generic mempool-wide DoS, since it requires the victim wallet to walk to that specific coin spend during singleton history sync.

### Recommendation
- Rewrite `PuzzleWithRestrictions.from_memo()` (and its `MofN` member expansion) to use an iterative, explicit-stack traversal instead of Python recursion, following the pattern already used by `sha256_treehash()`.
- Add an explicit maximum nesting-depth / maximum total-node limit when parsing `MofNHint` member memos, rejecting (raising `ValueError`) memos that exceed the limit rather than recursing further.
- In `PlotNFT.get_next_from_coin_spend()`, treat any parsing failure (including a bounded/py `RecursionError` if not eliminated) as an "Invalid memoization of PlotNFT" `GetNextPlotNFTError`, the same way `ValueError` is already handled, so a malformed/hostile memo cannot crash the wallet process.

### Proof of Concept
1. Construct a `CREATE_COIN` condition whose memo is a nested `Program` value shaped as `(CHIP-0043, [nonce, [], 1, (m, [<deeply nested member memo>, ...])])`, where the innermost `MofNHint` again has `further_branching=1` and nests another `MofN` member, repeated to a depth of tens of thousands of levels (well beyond Python's default recursion limit, e.g. ~10,000+).
2. Include a coin spend in a normal, otherwise-valid spend bundle that creates a coin with this deeply nested memo attached via `CreateCoin(...,memo_blob=...)`, following the shape validated by existing tests such as `test_plotnft_errors` which directly constructs `CreateCoin(... memo_blob=Program.to((bytes32.zeros, (PuzzleWithRestrictions.spec_namespace, [...]))))`: [5](#0-4) 
3. Submit the spend bundle; the coin is created on-chain as part of a PlotNFT/pool singleton lineage (or crafted to look like one to the recognizing wallet).
4. When a wallet later calls `PlotNFT.get_next_from_coin_spend()` on this coin's spend to recognize/sync the PlotNFT state (via `plotnft_wallet.py`), `PuzzleWithRestrictions.from_memo()` recurses once per nesting level, exceeding the Python stack and raising an uncaught `RecursionError`, halting that wallet processing path.

    @classmethod
    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
            puzzle=puzzle,
            additional_memos=additional_memos,
        )
