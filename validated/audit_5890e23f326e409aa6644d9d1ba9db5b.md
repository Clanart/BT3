## Analysis

The ERC-4626 report's core issue is a **broken invariant between two independently-computed values** (share price assumed 1:1 vs. attacker-manipulated actual balance) that lets an attacker cause silent, unrecoverable loss for a second party who trusts the first computation. The closest structural analog in GitHub Desktop is in the Copilot merge-conflict resolution pipeline, where the file offsets the AI model resolves against (produced by one parser) and the offsets the app later splices resolved content into (produced by an independent, weaker parser) are not guaranteed to agree, and the mismatch is driven by attacker-controlled file content that arrives via a normal merge/rebase/cherry-pick from a fetched/cloned repository.

### Title
Naive conflict-marker regex scan in `reassembleResolvedFile` lets attacker-controlled file content desynchronize hunk positions, silently corrupting merged code before commit - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` walks a post-merge file on disk line-by-line and treats any line matching `^<{7}` followed later by a `^={7}` line and a `^>{7}` line as a real conflict block, splicing in the model's per-hunk resolution "matched by order, not by line number." [1](#0-0)  This walk is completely independent of whatever conflict-hunk parser built the `hunks` array that was actually sent to the model as context (in `copilot-conflict-context.ts`). If a file that is part of a genuine merge conflict also contains attacker-supplied lines that incidentally match the 7-character marker regexes (e.g. text documenting conflict-marker syntax, a fixture/test string, or deliberately crafted lines), the two parsers can disagree on how many "conflicts" exist and where they start/end.

### Finding Description
The reassembly function's own doc comment acknowledges the ordering assumption is load-bearing: hunk resolutions are matched "by order, not by line number," and any malformed-looking marker sequence is just "copied through as regular content" rather than validated against the count of hunks the model was actually asked to resolve. [2](#0-1)  The only defense elsewhere in the pipeline is `validateResolutionPaths`, which checks that the *number* of resolved hunks returned by the model equals the *expected* hunk count computed from the original context-gathering parse — but that check compares the model's hunk count to the same context object, not to what `reassembleResolvedFile` will independently discover while re-scanning the raw file with its own regex. [3](#0-2) 

Because the attacker fully controls the content of a branch that gets merged, rebased, or cherry-picked into the victim's working tree (a git remote/fetched-repo scenario), the attacker can shape the "ours" or "theirs" side of a real, legitimate conflict to itself contain extra sequences that pass the loose `^<{7}`, `^={7}`, `^>{7}` regexes. This does not require any special git trickery — it's just ordinary file content that happens to look like conflict markers (fenced examples of git syntax are common in READMEs/docs/fixtures, and this very codebase's own test suite stores literal marker text as string data, showing how organically this pattern occurs). When `reassembleResolvedFile` re-walks the file, it can:
- count more or fewer "conflict blocks" than the model saw when producing `hunks`, shifting `hunkIndex` for every subsequent real conflict in the file, so a later hunk's resolution is spliced into the wrong location, and
- swallow attacker-supplied non-conflict text as if it were a resolvable conflict region, silently deleting or replacing it with model output the user never reviewed against that specific text.

### Impact Explanation
The corrupted value is the file content that becomes the final `IFileResolution.resolvedContent`, which is what the app subsequently writes to disk and stages/commits on behalf of the user via the write path that consumes `reassembleResolutions`. [4](#0-3)  Because the user's review UX is the AI-resolved diff (which already "looks reasonable" since it's a plausible merge), a misalignment silently changes what actually gets committed and pushed relative to what the user believes they approved — matching the report's required impact class of "silent corruption of what the user commits or pushes," without any local access, admin rights, or social engineering beyond the normal act of merging a branch that contains attacker-authored files.

### Likelihood Explanation
This requires the victim to (a) have Copilot conflict resolution enabled, and (b) merge/rebase/cherry-pick a branch whose content — entirely attacker-controlled — includes lines that coincidentally or deliberately resemble conflict markers alongside a genuine conflict in the same file. This is a plausible but non-trivial precondition (the attacker needs a conflicting change to land in the same file, and needs their content to survive as "ours"/"theirs" text in the post-conflict file), so likelihood is best assessed as low-to-medium; I was not able to fully verify from the index how strict the marker-detection regex is in `copilot-conflict-context.ts` (I could only confirm via grep that it uses a similarly-shaped pattern, not the exact stringency/labels it requires), which limits certainty about how easy it is to desynchronize the two parsers in practice.

### Recommendation
Make `reassembleResolvedFile` consume the same structured hunk boundaries (e.g., byte/line offsets) that were computed once by the authoritative conflict parser used to build `IFileConflictContext.hunks`, rather than independently re-deriving boundaries via a second, looser regex scan of the raw file. At minimum, assert that the number of conflict blocks discovered during reassembly exactly matches `hunks.length` from the original context object (not just the model's returned count) and fail closed (surface the file as a Copilot-skipped file for manual resolution) rather than silently proceeding on a mismatch.

### Proof of Concept
Not independently executed against a live Desktop build (no filesystem/terminal access in this session), but the vulnerable path can be demonstrated statically:
1. Attacker pushes branch `evil` with a file `notes.md` containing a legitimate paragraph plus a documentation block that itself contains literal lines `<<<<<<< example`, `=======`, `>>>>>>> example` (illustrating git conflict syntax to readers).
2. Victim merges `main` into a branch touching the same real content in `notes.md`, producing one genuine conflict region plus the pre-existing literal marker lines now sitting in the "theirs" or "ours" side of that real conflict.
3. `copilot-conflict-context.ts`'s parser (built for real conflicts) reports 1 real hunk to the model; the model returns 1 resolution.
4. `reassembleResolvedFile` re-scans the raw file and, because of the extra literal marker-like lines, detects 2 candidate blocks per the code path at [5](#0-4) , consuming the single available resolution against the wrong block and passing the real conflict through unresolved or vice versa — producing a final file that neither matches the model's intended output nor leaves the real conflict properly resolved, yet is written and offered for commit without any error surfaced to the user.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
