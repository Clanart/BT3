Confirmed: `filepath` comes directly and unrestricted from the `x-github-client://openrepo?...&filepath=...` deep link query string with no sanitization beyond being passed to `resolveWithin` [1](#0-0) , and `dispatcher.ts` only additionally rejects absolute paths before calling `resolveWithin(repository.path, filepath)` and then reveals the resolved path via `shell.showItemInFolder` [2](#0-1) .

### Title
Boundary check in `resolveWithin()` uses unanchored `startsWith`, allowing path traversal to sibling directories via deep-link `filepath` - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is GitHub Desktop's shared guard against path traversal/symlink escapes, used to validate a `filepath` argument taken from an attacker-controlled `x-github-client://openrepo` deep link before it is passed to `shell.showItemInFolder()`. The final containment check compares the resolved real path against the repository's real root using a plain string `startsWith()`, without requiring a path-separator boundary after the root. This is the same class of bug as the audited `_compareMinMax()` off-by-one: the comparison is supposed to enforce "is contained within X" but its boundary condition is wrong, so values that are outside X but share X as a string prefix pass the check.

### Finding Description
`_resolveWithin()` computes the real, symlink-resolved root and target paths and then does:

```javascript
return realResolved.startsWith(realRoot) ? resolved : null
``` [3](#0-2) 

`path.resolve()` lexically collapses `..` segments, so a `pathSegments` value containing enough `..` can legitimately move the resolved path to a filesystem sibling of `rootPath` (e.g. root `/Users/alice/Projects/MyRepo` + `../MyRepo-secrets/config.json` → `/Users/alice/Projects/MyRepo-secrets/config.json`). Because `MyRepo-secrets` textually starts with `MyRepo`, `realResolved.startsWith(realRoot)` returns `true` even though the resolved path is a completely different, unrelated directory outside the repository. The correct boundary check would require `realResolved === realRoot || realResolved.startsWith(realRoot + sep)`, exactly analogous to the reported fix of turning `>`/`<` into `>=`/`<=` to correctly include the boundary — here the missing element is enforcement of the separator boundary rather than a bare string prefix.

The existing tests only cover exact parent/child escapes and symlink escapes to unrelated absolute roots [4](#0-3) ; they do not cover the sibling-directory-with-shared-prefix case, so this bypass is not caught by the test suite.

### Impact Explanation
This check is the sole guard used before `shell.showItemInFolder(resolved)` reveals a filesystem location to the OS shell/Finder/Explorer from an attacker-supplied `filepath` in a clickable deep link:

```javascript
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
}
``` [5](#0-4) 

If a victim has (or the attacker can predict/name) a directory next to a cloned repository whose name shares the repository directory name as a prefix, a malicious `x-github-client://openrepo/...&filepath=../SiblingDirWithSharedPrefix/secret-file` link, when clicked, bypasses the "must stay within the repo" guarantee and causes Desktop to reveal/open a file outside the repository in the OS file manager — a read/disclosure outside the intended repo boundary, matching the "file read outside the repo" impact class from a link the user clicks. The same `resolveWithin()` primitive is also reused for the Copilot merge-conflict file reader [6](#0-5) , so any future or existing caller relying on this containment guarantee inherits the same weakness.

### Likelihood Explanation
The `filepath` value is fully attacker-controlled and reaches `resolveWithin` with essentially no prior sanitization: `parseAppURL()` only validates `pr` and `branch` formats, not `filepath` [7](#0-6) , and `dispatcher.ts` only rejects absolute paths, not `..` traversal segments [8](#0-7) . Exploitation requires the victim to click a crafted link while having (or the attacker guessing) a suitably-named sibling directory, which is a plausible but non-trivial precondition — this keeps likelihood moderate rather than trivial, similar to how the oracle bug required an actual price-crash event to manifest.

### Recommendation
Change the containment check in `_resolveWithin()` to require an exact path-separator boundary, e.g.:
```javascript
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests for sibling directories whose names share the root directory name as a string prefix (with and without symlinks) to `app/test/unit/path-test.ts`.

### Proof of Concept
1. Attacker hosts a link: `x-github-client://openrepo/owner/MyRepo?filepath=..%2FMyRepo-secrets%2Fsecret.txt` (URL-encoded `../MyRepo-secrets/secret.txt`).
2. Victim has previously cloned `MyRepo` to `/Users/victim/Projects/MyRepo`, and (independently) has a directory `/Users/victim/Projects/MyRepo-secrets` containing sensitive files.
3. Victim clicks the link; GitHub Desktop routes it to `openRepositoryFromUrl`, which calls `resolveWithin('/Users/victim/Projects/MyRepo', '../MyRepo-secrets/secret.txt')`.
4. `resolve()` yields `/Users/victim/Projects/MyRepo-secrets/secret.txt`; `realResolved.startsWith(realRoot)` is `true` because `'/Users/victim/Projects/MyRepo-secrets/secret.txt'.startsWith('/Users/victim/Projects/MyRepo')` is `true` in plain string comparison.
5. `shell.showItemInFolder()` opens the OS file manager at `secret.txt`, outside the repository directory that the guard was meant to enforce.
