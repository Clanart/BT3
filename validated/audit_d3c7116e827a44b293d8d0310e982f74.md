## Title
Destination-side order cancellation uses raw `block.number` instead of the chain-aware `_blockNumber()`, permanently breaking the permissionless-cancel gate on Arbitrum - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The external report shows that on Arbitrum, `block.number` returns a stale, L1-synced value rather than the true L2 block height, so any on-chain logic that compares `block.number` against a deadline denominated in L2 blocks is broken. Hyperbridge's own `IntentGatewayV2` codebase is aware of exactly this problem and introduced `_blockNumber()` (using the ArbSys precompile) specifically because `order.deadline` is denominated in the L2 block heights that Hyperbridge tracks for each state machine. However, this fix was not applied consistently: `_cancelFromDest`, the function that gates the "anyone can cancel after expiry" path for destination-side cross-chain cancellation, still compares `order.deadline` against raw `block.number`.

### Finding Description
`IntentsBase._blockNumber()` exists precisely to correct for Arbitrum's stale `block.number` opcode: [1](#0-0) 

`IntentGatewayV2.fillOrder` correctly uses this chain-aware helper to check order expiry: [2](#0-1) 

But the destination-side cancellation authorization check in `_cancelFromDest` uses the raw, unadjusted `block.number` instead, as documented verbatim in the project's own docs quoting the contract: [3](#0-2) 

Because `order.deadline` is denominated in the *L2*-tracked block height (per the `_blockNumber()` doc comment) while Arbitrum's `block.number` opcode returns the approximate, far smaller, slower-incrementing *L1*-synced height, the comparison `order.deadline >= block.number` in `_cancelFromDest` will, for any realistic order deadline, essentially always evaluate to `true`. This means the `Unauthorized()` guard for non-owner callers never relaxes — the intended "public may cancel after deadline" branch is unreachable on Arbitrum destination deployments, while the exact same deadline value is treated correctly (i.e., as expired) by `fillOrder` via `_blockNumber()`.

This is a direct local analog of the seed bug: a time/height-based access-control gate that silently breaks because the wrong block-number primitive is used on an L2 whose `block.number` opcode does not track true chain height.

### Impact Explanation
The mismatch corrupts the authorization boundary in `_cancelFromDest`: the check meant to open a permissionless cancel/refund path once an order is expired never does so on Arbitrum, because it measures expiry with the wrong clock (`block.number` instead of `_blockNumber()`/ArbSys). This is exactly the class of "logic attack against an authorization gate caused by an unreliable block-number primitive" called out in the Hyperbridge pivots (`request/response/timeout paths ... must bind ... one-time receipt handling`, and generally that cross-chain state transitions must not be reachable/blockable through mismatched height semantics). Concretely: the destination-side `RefundEscrow` dispatch that finalizes cancellation and unlocks the user's source-chain escrow can be triggered by `order.user` only, indefinitely, regardless of how expired the order truly is per the deadline unit that `fillOrder` itself enforces — the two enforcement points for the same `order.deadline` value diverge on the same contract.

### Likelihood Explanation
This is triggerable with completely standard, unprivileged inputs — any order placed with a cross-chain destination on Arbitrum whose deadline has passed will exhibit this divergence deterministically, with no reliance on a malicious relayer, prover, or admin. It requires no race condition or front-running; it is a static, provable inconsistency between two functions in the same file/contract family that both read `order.deadline` but use different block-number sources.

### Recommendation
Replace the raw `block.number` comparison in `_cancelFromDest` with `_blockNumber()`, matching the chain-aware value already used in `fillOrder`, so that the deadline is evaluated consistently (in L2-tracked height units) across every function that gates behavior on `order.deadline`.

### Proof of Concept
1. Deploy `IntentGatewayV2` as the destination gateway on Arbitrum One (`block.chainid == 42161`).
2. `placeOrder` a cross-chain order with `destination` = Arbitrum, and `deadline` set relative to the ArbSys L2 block height (as the SDK/contract intends, per `_blockNumber()`'s doc comment).
3. Time passes; Arbitrum's L2 height (via `arbBlockNumber()`) surpasses `order.deadline`, so `fillOrder` on this same contract now reverts with `Expired()` — the order is, by design, expired.
4. A third party (not `order.user`) calls `cancelOrder` → `_cancelFromDest`. Because Arbitrum's L1-synced `block.number` is numerically far below the L2-denominated `order.deadline` (Arbitrum's L2 height counter is on the order of hundreds of millions vs. Ethereum L1's tens of millions), `order.deadline >= block.number` remains `true`, so the function reverts `Unauthorized()` even though the order is genuinely expired.
5. This demonstrates the divergence: `fillOrder` treats the order as expired (via `_blockNumber()`), while `_cancelFromDest` treats it as not-yet-expired (via raw `block.number`), permanently keeping the permissionless-cancel branch closed on Arbitrum destination deployments.

    /**
     * @dev Returns the current block number of the host chain. Order deadlines are
     * denominated in the block heights Hyperbridge tracks for each state machine —
     * for Arbitrum chains that is the L2 block number, but the `block.number` opcode
     * there returns the approximate L1 block number, so the ArbSys precompile is
     * queried instead. The chain id check keeps the bytecode identical across all
     * chains, preserving the deterministic CREATE2 deployment addresses.
     * @return The chain-appropriate current block number.
     */
    function _blockNumber() internal view returns (uint256) {
        if (block.chainid == ARBITRUM_ONE || block.chainid == ARBITRUM_NOVA || block.chainid == ARBITRUM_SEPOLIA) {
            return IArbSys(ARB_SYS).arbBlockNumber();
        }
        return block.number;
    }
