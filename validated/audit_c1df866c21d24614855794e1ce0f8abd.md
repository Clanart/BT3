### Title
Silent, unattended git remote URL rewrite driven by attacker-influenced GitHub API `clone_url` - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
GitHub Desktop periodically calls the GitHub API to refresh metadata for every open repository, even ones not currently selected, as part of its background fetch/indicator-refresh cycle. If the API's reported `clone_url` for a repository differs from what Desktop last recorded (e.g. because the repository was renamed or transferred), Desktop will automatically rewrite the local `origin` remote's URL to match the API-reported value — with no user prompt, confirmation dialog, or visible notification. Since the trigger condition depends entirely on data returned by the GitHub API for a repository slot the user has already linked locally, and repository ownership/location can change server-side (rename, transfer, or re-creation after deletion) outside the user's awareness, this gives a path for silently repointing a user's push/fetch destination.

### Finding Description
`updateRemoteUrl` is called from `repositoryWithRefreshedGitHubRepository`, which is exercised unattended by both `BackgroundFetcher` (every ~30–60 minutes per repo) and `RepositoryIndicatorUpdater` (every ~15 minutes, for all *non-selected* repos) — i.e., without the user ever interacting with the repo: [1](#0-0) 

The rewrite logic itself: [4](#0-3) 

The guard conditions are: (1) the URL protocol (http vs ssh-style) must match between old and new, (2) the *previously recorded* `gitHubRepository.cloneURL` must still match the current git remote (i.e. user hasn't manually pointed `origin` elsewhere), and (3) the new API `clone_url` differs from what's currently configured. None of these guards validate that the *new* target is actually the repository the user originally intended to interact with — they only check "did the user manually diverge" and "does the protocol still match." The actual authority for what `origin` should point to is delegated entirely to whatever the GitHub API returns for the `owner/name` pair matched from the existing remote URL, via `matchGitHubRepository`: [5](#0-4) 

Because GitHub repository identity for API lookups is resolved by owner/name text parsed from the existing remote URL, and repository transfers/renames/deletions+recreation change what `owner/name` resolves to server-side, an attacker who can influence what repository sits at that owner/name slot (e.g., by being granted/gaining control of the repo, or via a rename race after the original repo is deleted/transferred) can cause Desktop's background task to silently repoint the victim's local `origin` remote to a URL the attacker controls — all without any git operation being initiated by the user and without any dialog being shown.

### Impact Explanation
If `origin` is silently rewritten to point at an attacker-influenced remote, the next ordinary `git push`/`git fetch`/`git pull` the user performs from Desktop's UI (which they believe targets their original repository) instead targets the new remote. This can result in:
- The user unknowingly pushing commits/branches (potentially containing proprietary code) to a repository the attacker controls.
- The user fetching/merging attacker-controlled history into their local repository under the belief it originated from the trusted upstream, i.e., silent corruption of what the user commits or pushes.
- If credential helpers/tokens are scoped broadly, this could also result in credentials being sent to a host serving the same hostname/owner/name (SSH remotes are excluded from validation by design here, but HTTPS same-host rewrites are the primary path).

This matches the "silent corruption of what the user commits or pushes" impact category, since it happens transparently to a normal git operation the user actually intends to run.

### Likelihood Explanation
Likelihood is constrained by needing the attacker to control what the GitHub API returns for the `owner/name` slot bound to an already-cloned repository (e.g., through a repo rename/transfer scenario, or squatting a freed repository name/owner) and by the requirement that the local remote hasn't been manually changed by the user. This is a background, no-interaction, no-confirmation code path — the user does nothing to trigger it besides having Desktop open with the repository added, which happens routinely. There is no rate limiting on the trust decision itself (only on fetch cadence), and no confirmation UI anywhere in the call chain (`updateRemoteUrl` → `gitStore.setRemoteURL` → `git remote set-url`) as shown in [6](#0-5) .

### Recommendation
Do not silently rewrite `origin` based on background API refreshes. At minimum:
- Never auto-update the remote URL during unattended/background refresh cycles (`BackgroundFetcher`, `RepositoryIndicatorUpdater`); only offer the update as a prompt when the user is actively viewing/interacting with the repository.
- Surface an explicit confirmation dialog showing old vs. new URL before calling `setRemoteURL`, similar to other repository-identity-changing actions in the app.
- Additionally validate repository identity continuity (e.g., using the GitHub repository's immutable numeric ID rather than owner/name text) before trusting a `clone_url` change, so that a name/owner slot being reused server-side doesn't get silently treated as "the same repository, just moved."

### Proof of Concept
1. User A clones `https://github.com/org/project` into GitHub Desktop; Desktop records `gitHubRepository.cloneURL = https://github.com/org/project`.
2. The `project` repository under `org` is later deleted (or transferred away) and an attacker manages to create/control a new repository at the same `org/project` slot (or a transfer occurs to an attacker-controlled account with the same name, a known GitHub race/squatting scenario).
3. On its next unattended background cycle (`BackgroundFetcher` fetch or `RepositoryIndicatorUpdater` refresh — both running without any user action), Desktop calls `api.fetchRepository(owner, name)` in `repositoryWithRefreshedGitHubRepository` and receives the attacker's repository's `clone_url`.
4. Since `remoteUrlUnchanged` is true (user never touched `origin`) and `protocolsMatch` is true (both `https`), `updateRemoteUrl` calls `gitStore.setRemoteURL('origin', <attacker clone_url>)`, silently rewriting the user's `origin` remote — no dialog, no log visible to the user in the UI.
5. The user later clicks "Push" in Desktop believing they're pushing to `org/project`; the push instead goes to the attacker-controlled repository behind the same displayed name.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
