### Title
Unchecked `int` Overflow in C# `CalculateSize()`/`ByteArray` Allocation Path Causes Serialization-Size/Buffer-Length Mismatch - (File: `csharp/src/Google.Protobuf/MessageExtensions.cs`, `csharp/src/Google.Protobuf/Collections/RepeatedField.cs`, generated `*.pb.cs` `CalculateSize()`)

### Summary
The Babylon advisory's failed invariant is: an attacker-controlled accumulation into a fixed-width integer is summed without an overflow check, and the wrapped/incorrect result is trusted downstream, causing a crash (there, a chain-halting panic). The transferable Protobuf analog is the C# runtime's generated `CalculateSize()` methods and `RepeatedField<T>.CalculateSize()` / `MapField<K,V>.CalculateSize()`, which accumulate field byte-sizes into a plain `int size` using ordinary (unchecked, by C# default) `+=` arithmetic [1](#0-0) . Unlike the C++ backend, which accumulates in `size_t` and explicitly documents/relies on later `> INT_MAX` checks before serialization [2](#0-1) , the C# path has no equivalent guard: `ToByteArray()` calls `message.CalculateSize()` directly to allocate a buffer and then writes into it, trusting the (possibly overflowed) `int` result [3](#0-2) .

### Finding Description
`RepeatedField<T>.CalculateSize(FieldCodec<T> codec)` sums per-element sizes into a local `int size` with plain `+=`, and the packed-data-size helper `CalculatePackedDataSize` does the same into `int tmp` [4](#0-3) . All generated message `CalculateSize()` methods across every `.pb.cs` file follow the identical unchecked pattern, summing tag-plus-payload sizes for every field, including repeated/map fields, into `int size` [5](#0-4) .

In C#, arithmetic on `int` is unchecked by default (no `checked` context is used anywhere in this arithmetic — confirmed by grep showing `checked(...)` only appears in test files and unrelated `ByteString`/`CodedOutputStream` code, never in `CalculateSize`/`RepeatedField`/generated message code). This means if the accumulated byte-size for a message's fields (e.g., very many packed/repeated elements or several large `bytes`/`string` fields) exceeds `int.MaxValue` (2,147,483,647), the sum silently wraps around to a small or negative number instead of throwing.

This computed (and now wrong) size is then used directly to allocate the output buffer:
```
byte[] result = new byte[message.CalculateSize()];
CodedOutputStream output = new CodedOutputStream(result);
message.WriteTo(output);
output.CheckNoSpaceLeft();
``` [3](#0-2) 

If `CalculateSize()` wraps to a small or negative value, `new byte[...]` either throws `OverflowException`/`NegativeArraySizeException`-equivalent, or (worse) allocates an undersized buffer while `WriteTo` still attempts to write the full (correct, larger) payload into it — an out-of-bounds/buffer-overrun condition detected only reactively by `CheckNoSpaceLeft()` throwing after the fact, i.e., after the write already occurred into memory the buffer doesn't own. The same unguarded accumulation is used by `WriteDelimitedTo` and `WriteLengthPrefixedTo`, which write `message.CalculateSize()` as a length prefix on the wire without any bounds validation [6](#0-5) .

This directly parallels the Babylon flaw: an attacker supplies bounded-looking input (a message with enough repeated elements/large byte fields) that causes an internal `int` summation invariant ("total serialized size fits in int and correctly reflects what will be written") to silently fail, and the corrupted value is trusted by calling code without a defensive check.

### Impact Explanation
Where this is reachable (an application deserializing/holding attacker-influenced Protobuf messages and later calling `ToByteArray()`, `WriteDelimitedTo()`, or `WriteLengthPrefixedTo()` on them, e.g., proxies, re-encoders, and RPC gateways), a wrapped/incorrect size leads to either an unhandled exception (denial of service, analogous to the chain-halting panic in the report) or, in the worst case, a serialization buffer-overrun/memory-corruption scenario. This is a High-severity class of bug matching the report's CWE-190 (Integer Overflow) / CWE-770 (Allocation of Resources Without Limits) pairing, though the concrete consequence here is corruption/crash in the serialization path rather than a consensus/chain-halt.

### Likelihood Explanation
Reaching `int.MaxValue` bytes (~2 GiB) of accumulated field sizes within a single in-memory C# message is a large but not impossible payload for services that accept large or many repeated/packed numeric fields, large `bytes`/`string` fields, or deeply populated maps without independent size limits — the C# implementation itself does not enforce a message size ceiling analogous to Java's/C++'s stream-level `CodedInputStream` size limits when constructing messages that are then re-serialized. However, this requires a specific application pattern (build/merge a message from attacker-controlled repeated data, then serialize it), so likelihood is Medium rather than trivially exploitable on every parse call.

### Recommendation
Add explicit overflow checks in `RepeatedField<T>.CalculateSize()` / `CalculatePackedDataSize()` and in all generated `CalculateSize()` accumulations (or centralize accumulation in a checked/`long`-based helper that throws `InvalidProtocolBufferException`/`OverflowException` before returning a corrupted `int`), mirroring the C++ approach of computing in a wider type and validating against `int.MaxValue` before it is used to allocate buffers or emit length prefixes in `MessageExtensions.ToByteArray`/`WriteDelimitedTo`/`WriteLengthPrefixedTo`.

### Proof of Concept

Expected (if unpatched): `CalculateSize()` returns a wrapped-around `int`, causing `new byte[message.CalculateSize()]` to allocate an incorrectly sized buffer, followed by an out-of-bounds write during `message.WriteTo(output)` or a late-surfacing exception via `output.CheckNoSpaceLeft()`.
