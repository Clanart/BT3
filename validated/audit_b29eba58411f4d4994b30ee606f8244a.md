### Title
Unauthenticated blame accusation with an out-of-range participant index panics the PedPoP `BlameMachine`, aborting the DKG node - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
JLSEC-2026-891 describes a denial of service where ImageMagick crashes due to improper use of `open()` on attacker-influenced input. The analogous Serai bug is an unprivileged-party-reachable panic: `BlameMachine::blame` / `AdditionalBlameMachine::blame` pass the caller-supplied `sender` and `recipient` `Participant` indexes directly into `HashMap` indexing (`self.enc_keys[&decryptor]` and `self.commitments[&sender]`) without validating them against `1..=n`. Any participant (or even a third party evaluating blame via `AdditionalBlameMachine`) can submit a blame accusation referencing an unregistered participant index, causing an indexing panic that crashes the process handling blame.

### Finding Description
`BlameMachine::blame` (crypto/dkg/pedpop/src/lib.rs:623) forwards the accusation to `blame_internal` (lib.rs:575), which calls `Decryption::decrypt_with_proof` (encryption.rs:366). Inside `decrypt_with_proof`, if the embedded Schnorr proof of possession verifies, the provided `EncryptionKeyProof` is checked against `self.enc_keys[&decryptor]` (encryption.rs:388). `enc_keys` is only populated via `Decryption::register` for participants `1..=n` other than ourselves; there is no entry for our own index `i` nor for any index `> n`. `Participant` is an arbitrary non-zero `u16`, so `recipient` can be our own index or any index up to 65535. A missing key makes `self.enc_keys[&decryptor]` panic.

The same class of panic exists on the sender side at `self.commitments[&sender]` in `blame_internal` (lib.rs:599) and in `calculate_share` at `self.commitments[&l]` (lib.rs:490), though the latter is protected by `validate_map`. The blame path has no such validation.

To reach the `enc_keys` panic, an attacker only needs:
1. A `Participant` index for `recipient` that is not a registered key holder (e.g., the victim's own index `i`, or any value `> n`).
2. An `EncryptedMessage` whose `pop` Schnorr signature verifies over `msg.key` — the attacker can generate this themselves with `SchnorrSignature::sign` since they know the ephemeral key (the PoP binds `context`, `key`, `sender`, and `msg`, all of which the attacker controls).
3. Any `EncryptionKeyProof` value to make `proof` be `Some`.

### Impact Explanation
Processing a blame accusation is part of the normal DKG abort/blame flow and, per the API docs, is meant to be callable by non-participants ("capable of evaluating Blame regardless of if the caller was a member in the DKG protocol", lib.rs:639). A single crafted accusation crashes the task/process running `blame`, denying service to every node that evaluates accusations. Since blame evaluation is exactly what happens after a failed key generation, an attacker who disrupts a DKG can also crash every honest party attempting to attribute fault — preventing blame attribution entirely. This matches the report's class: improper handling of an "open"-equivalent lookup on attacker-influenced input yielding a crash (DoS, availability-only, no secret leakage) — Medium severity.

### Likelihood Explanation
Any party able to submit a blame accusation (a DKG participant, or anyone relaying accusations to `AdditionalBlameMachine`) triggers this with trivial effort: they choose the `recipient` field freely and generate a self-consistent `EncryptedMessage`/`EncryptionKeyProof` pair. No threshold collusion, no leaked keys, and no invalid-curve tricks are required — only a `Participant` index outside the registered set and a validly signed PoP.

### Recommendation
- In `Decryption::decrypt_with_proof`, replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor)` and return `DecryptionError::InvalidProof` (or a dedicated `UnknownParticipant` error) on `None`.
- In `blame_internal`, look up `self.commitments.get(&sender)`/`get(&recipient)` and treat unknown indexes as the accuser being faulty rather than panicking.
- Validate `sender`/`recipient` against `params.all_participant_indexes()` at the top of `BlameMachine::blame` and `AdditionalBlameMachine::blame`.

### Proof of Concept
```rust
// Inside a DKG that already ran: victim holds a BlameMachine (or an
// observer constructs AdditionalBlameMachine with the n commitment msgs).

// Attacker (any participant, or the accuser) builds a self-consistent message:
let key = Zeroizing::new(C::random_nonzero_F(&mut rng));
let pub_key = C::generator() * key.deref();
let nonce = Zeroizing::new(C::random_nonzero_F(&mut rng));
let pub_nonce = C::generator() * nonce.deref();
let msg = EncryptedMessage::<C, SecretShare<C::F>> {
  // fields as produced by encrypt(): valid PoP over attacker-chosen bytes
  key: pub_key,
  pop: SchnorrSignature::sign(&key, nonce,
        pop_challenge::<C>(context, pub_nonce, pub_key, attacker, &share_bytes)),
  msg: share_bytes,
};

// Craft a syntactically valid EncryptionKeyProof (any DLEq; it just needs proof = Some(..))
let proof = Some(attacker_dleq_proof);

// Accuse with recipient = an index never registered in `enc_keys`
// (e.g. the victim's own index i, or Participant::new(n + 1).unwrap()):
let bogus_recipient = Participant::new(u16::from(n) + 1).unwrap();

// This panics at encryption.rs:388 on `self.enc_keys[&decryptor]`
// (indexing a missing HashMap key) -> process abort / DoS.
let (_, faulty) = blame_machine.blame(attacker, bogus_recipient, msg, proof);
```

Note: `decrypt_with_proof` first verifies the PoP (encryption.rs:374), which passes because the attacker knows the ephemeral key. It then reaches `self.enc_keys[&decryptor]` (encryption.rs:388) and panics since `bogus_recipient` was never registered via `Decryption::register` (encryption.rs:351-362). The equivalent panic on `self.commitments[&sender]` at lib.rs:599 is reachable the same way when `sender` is out of range.
