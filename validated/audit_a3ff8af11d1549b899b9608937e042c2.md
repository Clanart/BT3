### Title
Uncontrolled heap allocation from untrusted `n` field in `ThresholdKeys::read` — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` reads a 16-bit participant count `n` directly from the byte stream and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector, before validating `n` against `t`/`i` or confirming the reader actually contains `n` scalars. This is the same bug class as CVE-2026-52759: an attacker-chosen count field drives a heap allocation with no check that the input supplies the claimed elements. [1](#0-0) 

### Finding Description
`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574`) parses: a curve ID, then `t`, `n`, `i` as raw `u16`s, then a 1-byte interpolation tag. For tag `0` (`Interpolation::Constant`), it executes `Vec::with_capacity(usize::from(n))` and then loops `n` times calling `C::read_F(reader)`.

Two properties make this an uncontrolled allocation:

1. The allocation happens **before** `ThresholdParams::new(t, n, i)` is invoked (line 626), so a `ThresholdParams` that would be rejected (`n = 65535` with `t = 1`, `i` arbitrary) still triggers the `with_capacity` allocation of up to `65535 × size_of::<C::F>()` (~2 MiB for 32-byte fields, ~4.5 MiB for ed448-sized fields).
2. The allocation happens **before** any bytes backing the elements are confirmed present. A ~15-byte input (`id_len || id || t || n=0xFFFF || i || 0x00`) causes the multi-MiB allocation; the subsequent `read_F` immediately fails on EOF, but the allocation and zeroing work have already occurred. Repeating this on a decoding endpoint (e.g., a coordinator/processor deserializing received `ThresholdKeys`, or any service calling `ThresholdKeys::read` on peer-supplied bytes) yields a memory-bandwidth/allocation amplification DoS of roughly 10⁵× input size per call.

The same pattern, weaker, exists for `verification_shares` (line 621): `1 ..= n` `HashMap` inserts driven by `n`, though that loop is bounded by actual `read_G` input. The `Vec::with_capacity` is the pure allocation primitive since it does not depend on input content at all.

For comparison, the Serai codebase already acknowledges this bug class: `Call::read` in `networks/ethereum/src/machine.rs:51-60` explicitly chunks a u32-prefixed read "to only read data actually present (with a max DoS of 1 KB)", showing the intended defensive pattern that `ThresholdKeys::read` lacks.

### Impact Explanation
An unprivileged party who can cause a node to deserialize `ThresholdKeys` bytes (or any wrapper invoking `ThresholdKeys::read`) can force a ~2–4.5 MiB heap allocation plus memset per ~15 input bytes, with no authentication, no valid signature, and no complete payload required — the allocation precedes the EOF failure. Sustained requests cause allocator churn, memory-pressure stalls, and can contribute to OOM termination of the process, denying service to the threshold-signing/DKG pipeline. This maps to a denial-of-service (availability) impact matching the referenced advisory's VA:H profile.

### Likelihood Explanation
Reachability requires an endpoint that feeds untrusted bytes to `ThresholdKeys::read`; the API is public and documented for key-material deserialization, and Serai services persist/reload keys and exchange protocol messages over peer channels. The attacker needs no keys, no signature validity, and no cooperation — only the ability to submit malformed bytes. The cost asymmetry (bytes-in vs. bytes-allocated) is large, and the attack is trivially scriptable. Residual uncertainty: the exact in-repo call site that routes unauthenticated network bytes into `ThresholdKeys::read` was not pinned down, so the attack surface depends on integrator usage of this public deserialization API.

### Recommendation
Validate ordering and cap the allocation:

- Move the `ThresholdParams::new(t, n, i)` construction/validation **before** any allocation sized by `n` (before line 604), so `t > n` or invalid `i` rejects the input before `with_capacity` runs.
- Replace `Vec::with_capacity(n)` with `Vec::new()` + `push` in the `read_F` loop so memory grows only as real bytes are consumed (the chunked-read approach used in `Call::read`), or enforce a hard `n <= MAX_PARTICIPANTS` bound consistent with the protocol's real participant limits before allocating.
- Apply the same audit to the `verification_shares` loop (cap `n` before iterating) and to other count-prefixed `read` paths exposed on untrusted input.

### Proof of Concept
Conceptually, feed `ThresholdKeys::read` a buffer structured as:

```
u32 LE len(C::ID) || C::ID          // valid curve ID so the ID check passes
u16 LE t = 1                        // minimal t
u16 LE n = 0xFFFF                   // attacker-controlled count
u16 LE i = 1                        // valid nonzero participant
u8     interpolation = 0            // Interpolation::Constant -> Vec::with_capacity(65535)
u8     ... C::F::Repr for share     // minimal trailing bytes; EOF follows
```

Expected behavior: `ThresholdKeys::read` performs a ~2 MiB `Vec::with_capacity` allocation (line 608) and then fails with an I/O error at `C::read_F`/`read_exact` — but only after the allocation work completes. Repeating the call in a loop from a single connection demonstrates the allocation amplification without ever presenting a valid or complete key blob. Note: whether `ThresholdParams::new` would have rejected the parameters is irrelevant, because it is only evaluated at line 626, after the allocation.

Severity note: the per-call allocation is capped at ~`u16::MAX` elements (unlike the unbounded `ncmds` in the advisory), so the analog is a bounded-but-large amplification; it satisfies the concrete "uncontrolled memory allocation from an untrusted count, allocated before input validation/EOF confirmation" root cause, and is assessed as Medium under the provided rubric.
