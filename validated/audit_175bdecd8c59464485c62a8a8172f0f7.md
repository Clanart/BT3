### Title
Webhook shop-domain spoofing via HMAC that only signs the body, not the shop identity — cross-shop data/job injection ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates a webhook request solely by checking that `request.raw_post` HMAC-matches the shared app secret [1](#0-0)  and the HMAC itself is computed only over the raw body using the app-wide secret [2](#0-1) . The shop identity used for all downstream processing, `shop_domain`, is read directly from an unsigned request header (`HTTP_X_SHOPIFY_SHOP_DOMAIN`) that is not covered by the HMAC at all [3](#0-2) . This is structurally the same class of bug as the reported issue: the entity that is "authenticated"/paid for (the body's HMAC, tied only to the shared secret) is decoupled from the entity that state/actions get attributed to (the shop domain used to dispatch shop-scoped jobs).

### Finding Description
`hmac_valid?` computes `OpenSSL::HMAC.digest(digest, secret, data)` where `data` is `request.raw_post`, and compares it (constant time) against the `X-Shopify-Hmac-Sha256` header [2](#0-1) . This proves only that "someone who knows `ShopifyApp.configuration.secret` produced this exact body" — it says nothing about which shop the body is "for." The `shop_domain` used by the default `WebhooksController`/generated job controllers to scope all subsequent business logic (`shop_domain: webhook_request.shop` / `SomeJob.perform_later(shop_domain: shop_domain, ...)`) comes straight from the unsigned `HTTP_X_SHOPIFY_SHOP_DOMAIN` header [4](#0-3)  and the documented custom-controller pattern reinforces the same unverified binding [5](#0-4) .

Since the app secret is shared across every installed shop (it is a single, app-level secret, not per-shop), any merchant who has installed the app can:
1. Trigger a real business event in their own store (e.g. a cart/order update) to receive a genuinely, validly-signed webhook `(body, X-Shopify-Hmac-Sha256)` pair from Shopify.
2. Replay that exact `(body, hmac)` pair to the app's webhook endpoint while swapping only the `X-Shopify-Shop-Domain` header to point at a victim shop.
3. Because the HMAC check only validates `body + secret`, it still passes, and the request is treated as an authentic webhook "from" the victim shop.

The controller then enqueues shop-scoped background jobs (e.g. `CartsUpdateJob.perform_later(shop_domain: "victim.myshopify.com", webhook: attacker_controlled_body)`), letting the attacker inject data attributed to a shop they do not control.

### Impact Explanation
This allows any authenticated-but-unrelated merchant (an "unrelated-merchant" actor per scope) to forge webhook events that the application processes as belonging to a different, victim shop, since verification never binds the signed body to the claimed shop identity. Depending on what the app's webhook job handlers do with `shop_domain` (e.g., updating merchant-facing records, triggering notifications, altering per-shop settings/state), this is a cross-shop data/state confusion vector rooted directly in `shopify_app`'s webhook verification design.

### Likelihood Explanation
Exploitation only requires: (a) installing the app as any ordinary merchant to obtain one legitimately signed webhook body/HMAC pair, and (b) a single unauthenticated POST replay with a modified header — no secret leakage, credential theft, or privileged access is needed. This is directly reachable from an external HTTP request to the public webhook endpoint.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` as an identity claim based solely on body-HMAC validity. Cross-check the shop domain against the app's own list of currently-installed/authorized shops (e.g., verify a `ShopifyApp::SessionRepository` record exists for that domain) before dispatching shop-scoped jobs, and/or include the shop domain in the data that is integrity-checked (e.g., validate it against fields present in the parsed webhook body when available) rather than relying on an unauthenticated header value in `ShopifyApp::WebhookVerification#shop_domain` [3](#0-2) .

### Proof of Concept
1. Install the target app on shop A (attacker-controlled) and perform an action that triggers a registered webhook topic (e.g., `carts/update`).
2. Capture the resulting webhook POST request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since HMAC is only a function of `B` and the shared secret).
3. Replay POST to `/webhooks/carts_update` (or whichever path is configured) with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `WebhookVerification#verify_request` / `hmac_valid?` passes because it only checks `B` against `H` and the shared secret [2](#0-1) .
5. The generated job is enqueued with `shop_domain: "victim-shop.myshopify.com"` and attacker-controlled `webhook` body [4](#0-3) , causing the app to process attacker data as if it originated from the victim shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
