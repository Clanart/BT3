### DKG blame verification transposes sender and recipient, allowing false blame of an honest participant - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

`AdditionalBlameMachine::blame` expects the accused share **sender** first and accusing **recipient** second. The verification path instead treats the accuser as the sender and the accused as the intended decryptor. An on-chain accusation therefore validates a share traveling in the opposite direction and reaches the wrong conclusion.

### Finding Description

The PedPoP `blame` API is defined as `(sender, recipient)`, where the encrypted share must be authenticated as coming from `sender` to `recipient` [1](#0-0) .

`decrypt_with_proof` verifies the per-message proof of possession against `from`, then verifies the supplied ECDH proof against the registered encryption key of `decryptor` [2](#0-1) . This means transposing the two participants changes both checks.

The DKG records shares by `(from, to)` [3](#0-2) . However, when handling an `InvalidDkgShare`, it fetches `(accuser, faulty)` rather than `(faulty, accuser)` and passes them in that order to blame verification [4](#0-3) . The processor then calls `blame(accuser, accused, ...)` for both DKGs [5](#0-4) .

Consequently, the checked share is the message **from the accuser to the accused**, not the accused-to-accuser message being challenged. Its PoP verifies because the code uses the actual sender (`accuser`) as `from`, but the accuser-supplied ECDH proof is checked against the accused’s encryption key rather than the accuser’s key. That fails with `InvalidProof`, and `blame_internal` returns the recipient—now the accused party [6](#0-5) . The processor maps that result back to the accused participant [7](#0-6) .

### Impact Explanation

A participant can submit an `InvalidDkgShare` accusation against another participant while supplying either no proof or a proof for the wrong directional share. Verification dereferences a valid stored share in the accuser-to-accused direction, then deterministically blames the accused because the ECDH proof does not match the accused encryption key. This can incorrectly identify an honest validator as faulty and trigger DKG failure/slashing despite no invalid share being proven.

### Likelihood Explanation

The accusation path is directly reachable by a participating validator who can publish `InvalidDkgShare`. The coordinator only verifies that the accuser belongs to the submitting signer and that a `(accuser, faulty)` share exists; it does not ensure `faulty` is a valid participant range member or that the lookup uses the claimed sender-to-recipient direction [8](#0-7) . Since every sender normally has a share for every other participant, this condition is generally satisfiable.

### Recommendation

Use consistent `(sender, recipient)` ordering throughout blame handling:

- Fetch `DkgShare` as `(faulty, accuser)`, matching `(from, to)`.
- Call `AdditionalBlameMachine::blame(faulty, accuser, ...)`.
- Explicitly verify both `accuser` and `faulty` are valid participating participants, distinct, and mapped to the correct stored message direction.
- Add a regression test proving a false accusation against an honest sender returns the accuser, not the accused.

### Proof of Concept

Given participant `A` accusing participant `B`:

1. `DkgShares` stores normal encrypted shares under `(B, A)` and `(A, B)` [9](#0-8) .
2. `A` publishes `InvalidDkgShare { accuser: A, faulty: B, blame: proof_for_A_to_B_or_none }`.
3. The handler fetches `(A, B)` and sends `accuser=A`, `accused=B` to verification [10](#0-9) .
4. `decrypt_with_proof` verifies the PoP for sender `A`, then checks the proof against `B`’s encryption key, returning `InvalidProof` [11](#0-10) .
5. `blame_internal` maps `InvalidProof` to the recipient argument `B`, so the processor returns `Blame { participant: B }` even though `B`’s actual share to `A` was never checked [12](#0-11) .
