### Title
`isTrackedByLFS` uses an unanchored regex that matches the queried filename itself, allowing a crafted file path to force `filesNotTrackedByLFS` to falsely report a large/binary file as LFS-tracked - (File: `app/src/lib/git/lfs.ts`)

### Summary
`isTrackedByLFS` runs `git check-attr filter <path>` for a single path and decides "tracked" by testing the *entire raw stdout* against `/: filter: lfs/` with no anchoring and no parsing of the actual attribute value returned by `check-attr`. Because `git check-attr` echoes the queried path back verbatim as the first field of its output line, a path whose own bytes happen to contain the substring `: filter: lfs` will match the regex even though the real attribute value reported by git is `unspecified`. This lets a hostile repository (a file with a crafted name) cause Desktop to believe a file is LFS-tracked when it is not.

### Finding Description [1](#0-0) 

`isTrackedByLFS` invokes `git check-attr filter <path>` and simply does:
```
const lfsFilterRegex = /: filter: lfs/
const match = lfsFilterRegex.exec(stdout)
return match !== null
```
`git check-attr` output format is `<path>: <attribute>: <value>`, where `<path>` is exactly the queried path echoed back. The code assumes the only place `: filter: lfs` can appear is in the trailing `<attribute>: <value>` portion, but the regex is unanchored (no `^`/`$`/line-boundary assertions) and is tested against the *whole stdout string*, including the leading `<path>` field. If the queried path itself contains the literal characters `: filter: lfs` (or the code is fed a path with an embedded newline that manufactures a synthetic second "line"), the match succeeds regardless of the real attribute value returned by git.

`filesNotTrackedByLFS` calls `isTrackedByLFS` once per file, in a loop, and trusts the returned boolean to build the list of files not covered by LFS: [2](#0-1) 

So for a path like `malicious: filter: lfs.bin`, `git check-attr filter "malicious: filter: lfs.bin"` (assuming no `.gitattributes` LFS rule) would print something like:
```
malicious: filter: lfs.bin: filter: unspecified
```
The regex `/: filter: lfs/` matches the substring embedded in the echoed path (`malicious: filter: lfs`) even though the real attribute value is `unspecified`. `isTrackedByLFS` returns `true`, and `filesNotTrackedByLFS` omits this file from its result even though it is *not* actually tracked by Git LFS.

Regarding the newline variant proposed in the question: git's path-quoting (`quote_path`) unconditionally C-quotes control characters such as `\n` in `check-attr` output (this is independent of `core.quotepath`, which only governs non-ASCII), so an embedded raw newline byte in the path would typically appear as the two characters `\` and `n` in stdout rather than a real line break. That specific newline-injection mechanic is therefore not the most reliable trigger. However, the underlying defect the question is pointing at — an unanchored regex tested against the whole stdout blob rather than against the parsed attribute value for the actual path — is real and exploitable via a much simpler vector: a filename that simply contains the literal substring `: filter: lfs`, with no newline required.

### Impact Explanation
The affected function is only used from the "changes" sidebar to decide whether to warn the user before committing large files that are not covered by Git LFS. If a repository contains a maliciously named file that spoofs a "tracked" result, Desktop will skip the "some files are too large / not tracked by LFS" warning for that file and commit/push it as a normal blob instead of prompting the user to set up LFS tracking. This is a silent-corruption-of-what-the-user-commits issue: the user's expectation (a warning + option to LFS-track large files) is defeated by attacker-controlled repository content (a crafted file name), and the large/binary file ends up embedded directly in the Git history/pack instead of as an LFS pointer, with the resulting downsides (bloated repo, exceeding size limits when pushing to GitHub, potential broken clones or rejected pushes) landing on the user later without an explicit signal at commit time.

### Likelihood Explanation
Exploitation only requires the victim to clone/check out a repository containing a file with an adversary-chosen name (colon and the string `filter: lfs` are legal in file names on Linux/macOS; colon is disallowed on Windows, limiting the attack to non-Windows users of Desktop), then use the normal commit flow after adding/modifying such a file. No unusual user action, elevated privileges, or social engineering beyond "clone this repo" is required, making this a low-effort, high-plausibility path for a determined attacker targeting non-Windows Desktop users.

### Recommendation
- In `isTrackedByLFS`, do not test the regex against the raw, unparsed stdout. Parse `check-attr` output per its documented format (one `<path>: <attribute>: <value>` line, with `path` quoted when it contains special characters) and compare only the `<value>` field for the requested attribute, or anchor the match to the end of line (e.g. `/: filter: lfs$/m`) after confirming the path portion is correctly consumed/unquoted.
- Alternatively, invoke `git check-attr -z --stdin filter` and feed paths via NUL-terminated stdin, then parse the NUL-delimited `path\0attribute\0value\0` records, which removes ambiguity from embedded colons/newlines in filenames entirely.

### Proof of Concept
1. Create a repository containing a file literally named:
   ```
   malicious: filter: lfs.bin
   ```
   with no `.gitattributes` LFS rule for it (or any rule that would make git report `unspecified`).
2. Clone this repository in GitHub Desktop, add the file to the working directory changes.
3. Call `filesNotTrackedByLFS(repository, ['malicious: filter: lfs.bin', 'other-large-file.bin'])`.
4. Observe that `isTrackedByLFS` runs `git check-attr filter "malicious: filter: lfs.bin"`, whose stdout contains the substring `: filter: lfs` embedded in the echoed path, causing `/: filter: lfs/.exec(stdout)` to return non-null.
5. `filesNotTrackedByLFS` therefore omits `malicious: filter: lfs.bin` from the "not tracked" list, even though `git check-attr`'s actual reported value for the `filter` attribute is `unspecified` — diffing the returned array against ground truth (querying `.gitattributes` state independently) shows the mismatch.

```typescript
export async function isTrackedByLFS(
  repository: Repository,
  path: string
): Promise<boolean> {
  const { stdout } = await git(
    ['check-attr', 'filter', path],
    repository.path,
    'checkAttrForLFS'
  )

  // "git check-attr -a" will output every filter it can find in .gitattributes
  // and it looks like this:
  //
  // README.md: diff: lfs
  // README.md: merge: lfs
  // README.md: text: unset
  // README.md: filter: lfs
  //
  // To verify git-lfs this test will just focus on that last row, "filter",
  // and the value associated with it. If nothing is found in .gitattributes
  // the output will look like this
  //
  // README.md: filter: unspecified

  const lfsFilterRegex = /: filter: lfs/

  const match = lfsFilterRegex.exec(stdout)

  return match !== null
}
```

```typescript
export async function filesNotTrackedByLFS(
  repository: Repository,
  filePaths: ReadonlyArray<string>
): Promise<ReadonlyArray<string>> {
  const filesNotTrackedByGitLFS = new Array<string>()

  for (const file of filePaths) {
    const isTracked = await isTrackedByLFS(repository, file)

    if (!isTracked) {
      filesNotTrackedByGitLFS.push(file)
    }
  }

  return filesNotTrackedByGitLFS
}
```
