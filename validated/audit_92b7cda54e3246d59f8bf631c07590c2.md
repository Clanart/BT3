### Title
Unchecked `u64` Overflow in Payment Sum Bypasses `NotEnoughFunds` Check in `SignableTransaction::new` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums attacker-influenced payment amounts with plain `u64` arithmetic (`payments.iter().map(|payment| payment.1).sum::<u64>()`, line 187) and compares it against inputs with `input_sat < (payment_sat + needed_fee)` (line 215). Neither the sum nor the addition is checked, so a crafted payment set can wrap `payment_sat` to a small value, bypassing the insufficient-funds guard and producing a `SignableTransaction` the FROST `TransactionMachine` will sign — a transaction whose declared outputs exceed its inputs.

### Finding Description
The arithmetic on funds in `SignableTransaction::new` uses unchecked operators throughout:

- `input_sat` at `networks/bitcoin/src/wallet/send.rs:175` sums `input.output.value.to_sat()` with a plain `.sum::<u64>()` over `ReceivedOutput`s that can be supplied via `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122`).
- `payment_sat` at `send.rs:187` sums caller/payment-supplied `u64` amounts; each amount is only checked to be `>= DUST` (line 166).
- `input_sat < (payment_sat + needed_fee)` at `send.rs:215` adds `payment_sat + needed_fee` unchecked.
- The change computation at `send.rs:228` uses `input_sat.checked_sub(payment_sat + fee_with_change)` — the inner `payment_sat + fee_with_change` addition is itself unchecked.
- `fee()` at `send.rs:138-140` subtracts `sum(outputs)` from `sum(inputs)` with a plain `-`, which panics (debug) or wraps (release) if the earlier checks were bypassed via wraparound.

An unprivileged party who can cause a transaction to be built/signed with chosen `payments` (withdrawal-style flows feed attacker amounts into `payments`) can specify a few payments of ~`u64::MAX/3` each — all `>= DUST`, so they pass the per-payment check — making `payment_sat` wrap to a small value. The `NotEnoughFunds` guard then passes even though the encoded `TxOut` values astronomically exceed `input_sat`. The resulting `SignableTransaction` is fed to `TransactionSignMachine::sign` (line 355), which produces a valid BIP-340 threshold signature over a transaction spending more than it holds — consensus-invalid and unintended by the signer policy. In release builds `fee()` additionally wraps; in debug builds it panics.

### Impact Explanation
The threshold signs a transaction the `NotEnoughFunds` policy was designed to reject: outputs exceeding inputs. Because output amounts are committed via `Prevouts::All`/`SighashCache` (line 375-386), the signature is valid for that exact malformed transaction. The node either wastes the signing session on a non-broadcastable transaction or, with moderately-sized wrapping, produces bookkeeping (`needed_fee`, `fee()`) that is silently wrong. This is a real overflow-driven check bypass on the fund-accounting path, the same class as the external report (unchecked `balance + amount`), mapped to Serai's shape where the "balance" is `input_sat`/`payment_sat`.

### Likelihood Explanation
Reachable whenever attacker-influenced payment amounts reach `SignableTransaction::new`, which is the only transaction-construction entry point and is explicitly in scope. Triggering needs only 2-3 large `u64` amounts — well under `MAX_STANDARD_TX_WEIGHT` — so no exotic conditions are required. Severity is bounded because the forged output amounts are consensus-invalid (each exceeds 21M BTC), so direct theft is not achievable; the realistic impact is a policy-check bypass producing a signed invalid transaction and potential panic in `fee()`. Medium.

### Recommendation
Use `checked_add`/`saturating_add` (or `Amount` arithmetic, which saturates and validates `MAX_MONEY`) when computing `input_sat`, `payment_sat`, and `payment_sat + needed_fee` / `payment_sat + fee_with_change`, and reject on overflow before the `NotEnoughFunds` comparison. Additionally validate each payment against `Amount::MAX_MONEY` so consensus-invalid outputs are rejected at construction.
