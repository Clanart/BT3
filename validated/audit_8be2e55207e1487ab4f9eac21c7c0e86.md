### Title
EIP-712 Domain Lacks `chain_id` and `verifying_contract` — Aggregator Verification Signatures Are Cross-Network and Cross-Deployment Replayable - (File: `core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

The `CLEMENTINE_EIP712_DOMAIN` used to sign and verify aggregator authorization signatures for both the optimistic-payout and operator-withdrawal flows omits `chain_id` and `verifying_contract`. Because the domain separator does not bind to a specific network or bridge deployment, a valid `verification_signature` produced for one Clementine instance is cryptographically valid on every other instance that shares the same aggregator key.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

The domain contains only `name` and `version`. The EIP-712 specification defines `chain_id` and `verifying_contract` precisely to prevent cross-chain and cross-contract replay. Neither is present here, even though both values are available in `BridgeConfig`:

```rust
pub citrea_chain_id: u32,          // e.g. 5655
pub bridge_contract_address: String, // e.g. "3100000000000000000000000000000000000002"
``` [2](#0-1) 

The two message structs — `OptimisticPayoutMessage` (used by verifiers in `sign_optimistic_payout`) and `OperatorWithdrawalMessage` (used by operators in `withdraw`) — have **identical field layouts**:

```rust
struct OptimisticPayoutMessage {
    uint32 withdrawal_id; bytes input_signature; bytes32 input_outpoint_txid;
    uint32 input_outpoint_vout; bytes output_script_pubkey; uint64 output_amount;
}
struct OperatorWithdrawalMessage  { /* identical fields */ }
``` [3](#0-2) 

The proto comment acknowledges the cross-type risk and claims the different struct names prevent it:

> "This message contains same data as the one in Optimistic Payout signature, but with a **different message name**, so that the same signature can't be used for both optimistic payout and normal withdrawal." [4](#0-3) 

The struct-name-based separation does work (EIP-712 type hash includes the struct name). However, the domain itself carries no network or contract binding, so the same signature is valid on any Clementine deployment that uses the same aggregator key.

The signature is verified in two places:

**Verifier** (`sign_optimistic_payout`):
```rust
if let Some(address_in_config) = self.config.aggregator_verification_address {
    let address_from_sig =
        recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>(...)?;
    if address_from_sig != address_in_config { return Err(...); }
}
``` [5](#0-4) 

**Operator** (`withdraw`):
```rust
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    let address_from_sig =
        recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>(...)?;
    if address_from_sig != address_in_config { return Err(...); }
}
``` [6](#0-5) 

Both checks are also **gated on `aggregator_verification_address` being `Some`** — if the operator or verifier is deployed without this config value, the entire check is skipped and any caller can trigger a withdrawal without any aggregator authorization. [7](#0-6) 

---

### Impact Explanation

If the same aggregator key is used across multiple Clementine deployments (e.g., mainnet and a staging/testnet instance, or two bridge instances on the same chain), an attacker who observes a valid `verification_signature` from one deployment can replay it on another. The replayed signature passes `recover_address_from_ecdsa_signature` because the domain separator is identical across all deployments.

The attacker must also supply withdrawal params (`withdrawal_id`, `input_outpoint`, `output_script_pubkey`, `output_amount`) that match a valid deposit in the target deployment's database. Because Bitcoin UTXOs are globally unique, cross-network replay is practically infeasible. Cross-deployment replay on the same Bitcoin network (e.g., two bridge instances) is the realistic threat: if the same UTXO appears in both deployments (e.g., during a migration), a signature from the staging deployment authorizes a withdrawal on production, causing unauthorized movement of bridged BTC from the vault.

---

### Likelihood Explanation

Likelihood is **low-to-medium**. It requires the same aggregator key across deployments and overlapping withdrawal params. However, the code deficiency is unconditional — every deployment is affected — and the missing domain fields are a straightforward omission of standard EIP-712 hardening that the protocol already partially implements (it uses EIP-712 specifically to prevent cross-type replay).

---

### Recommendation

Include `chain_id` and `verifying_contract` in `CLEMENTINE_EIP712_DOMAIN`. Since the domain is currently a `static`, it must be constructed at runtime using the values from `BridgeConfig`:

```rust
fn build_eip712_domain(chain_id: u64, contract_addr: Address) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
        verifying_contract: contract_addr,
    }
}
```

Pass this domain into `recover_address_from_ecdsa_signature` instead of the global static. This binds every signature to a specific Citrea chain ID and bridge contract address, making cross-deployment and cross-network replay cryptographically impossible.

Additionally, consider making `aggregator_verification_address` a required field rather than `Option` so that the check cannot be silently disabled by omitting the config value.

---

### Proof of Concept

1. Deploy two Clementine instances (A and B) on different Citrea networks (or two bridge contracts on the same network) sharing the same aggregator key.
2. On instance A, obtain a valid `verification_signature` for `OptimisticPayoutMessage` with params `(withdrawal_id=X, input_outpoint=Y, ...)`.
3. Submit the same params and the same `verification_signature` to instance B's `optimistic_payout` RPC.
4. `recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>` computes `eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)` — the domain is identical on both instances — and recovers the same aggregator address.
5. The check `address_from_sig != address_in_config` passes, and instance B's verifiers proceed to sign the optimistic payout, spending the vault UTXO on instance B without a fresh aggregator authorization for that deployment. [8](#0-7) [9](#0-8)

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
