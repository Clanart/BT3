### Title
Wasmd Precompile DELEGATECALL Pointer-Scope Check Uses Type-Blind OR Logic, Allowing Cross-Contract Authorization Bypass - (File: precompiles/wasmd/wasmd.go)

### Summary
The wasmd precompile's `execute()` function enforces a "is this calling contract actually the registered pointer of this CW contract" scope check only when it is reached via `DELEGATECALL` (`ctx.EVMPrecompileCalledFromDelegateCall()`), analogous to the OpenCloud/Reva bug where a scope check exists but can be satisfied against the wrong resource. The check queries three *independent* pointer-registration keyspaces (ERC20↔CW20, ERC721↔CW721, ERC1155↔CW1155) for the same `contractAddrStr` and passes if **any one** of them matches `callingContract`, regardless of which asset type that match came from. [1](#0-0) 

### Finding Description
`execute()` derives the acting Sei identity from `caller` (which DELEGATECALL preserves as the original tx sender/EOA), while `callingContract` is the immediate contract in the call frame (normally the CW20/CW721/CW1155 pointer contract). To stop an arbitrary contract from delegatecalling into wasmd and forging a "pointer" relationship it doesn't actually have, the code checks:

```go
if ctx.EVMPrecompileCalledFromDelegateCall() {
    erc20pointer, _, erc20exists := p.evmKeeper.GetERC20CW20Pointer(ctx, contractAddrStr)
    erc721pointer, _, erc721exists := p.evmKeeper.GetERC721CW721Pointer(ctx, contractAddrStr)
    erc1155pointer, _, erc1155exists := p.evmKeeper.GetERC1155CW1155Pointer(ctx, contractAddrStr)
    if (!erc20exists || erc20pointer.Cmp(callingContract) != 0) &&
       (!erc721exists || erc721pointer.Cmp(callingContract) != 0) &&
       (!erc1155exists || erc1155pointer.Cmp(callingContract) != 0) {
        return nil, 0, fmt.Errorf("%s is not a pointer of %s", callingContract.Hex(), contractAddrStr)
    }
}
``` [1](#0-0) 

The three pointer maps are stored under distinct keys (`PointerERC20CW20Key`, `PointerERC721CW721Key`, `PointerERC1155CW1155Key`) that only prevent a target address from being registered if the target itself is *already a pointer* (`cwAddressIsPointer`), not from being registered under a *different* pointee-type mapping than it actually is: [2](#0-1) 

Because the guard condition is a disjunction ("pass if this callingContract matches the ERC20 pointer for X, OR the ERC721 pointer for X, OR the ERC1155 pointer for X"), the check does not verify that the *matching* record corresponds to the actual asset type of `contractAddrStr`. If any wasm address can be registered under more than one of these three pointer keyspaces (e.g., an attacker registers themselves as the "ERC721 pointer" of a wasm contract address that is really a CW20 token, since registration does not appear to validate that the target contract implements the corresponding CW interface before writing the mapping), the OR check is satisfied by the attacker-controlled pointer contract even though it has no legitimate relationship to that contract as an ERC20/CW20 pointer.

Once the check passes, `senderAddr` is resolved from the delegatecall-preserved `caller` (the real end user), and `p.wasmdKeeper.Execute(ctx, contractAddr, senderAddr, msg, coins)` runs an attacker-chosen `ExecuteMsg` against the target CW contract as that user: [3](#0-2) 

### Impact Explanation
If pointer registration does not strictly enforce a 1:1, type-exclusive relationship between a CW contract address and the pointer keyspace it can be registered under, an attacker can register their own malicious EVM contract as a spurious "pointer" (of a mismatched asset type) for a high-value CW20/CW721/CW1155 contract. Any victim who interacts with the attacker's contract via delegatecall (or is otherwise induced to route a call through it) has their real Sei identity impersonated to execute arbitrary wasm `ExecuteMsg`s (e.g. transfers) against the targeted contract, resulting in unauthorized transfer of funds/assets — direct fund loss for the victim.

### Likelihood Explanation
Pointer registration through `precompiles/pointer` is permissionless and reachable by any EVM caller/contract deployer; the wasmd `execute()` path is reachable by any transaction that gets delegatecalled through a "pointer"-like contract. The exploit requires only (1) successfully registering a mismatched-type pointer for a target CW contract, and (2) getting the victim (or the victim's approved contract) to delegatecall through the attacker's registered contract. I was not able to fully confirm from the available index whether `AddCW20Pointer`/`AddCW721Pointer`/`AddCW1155Pointer` in `precompiles/pointer/pointer.go` validate that the target wasm contract actually implements the claimed CW interface before calling `SetERC*CW*Pointer` — this is the key open question that determines exploitability, and it should be verified directly against `precompiles/pointer/pointer.go` and `x/evm/keeper/pointer.go`'s `cwAddressIsPointer` guard.

### Recommendation
- In `precompiles/wasmd/wasmd.go` `execute()`/`executeBatch()`, require that the matching pointer record's type corresponds to the actual CW contract type being targeted (e.g., verify via `wasmdViewKeeper` that the contract implements the matched interface), rather than accepting any one of the three OR-ed lookups.
- In `x/evm/keeper/pointer.go`, enforce that a given `cwAddress` can only ever be registered under exactly one of the ERC20/ERC721/ERC1155 pointer keyspaces, and validate the target contract's actual type at registration time in the pointer precompile before calling `Set*Pointer`.

### Proof of Concept
1. Attacker calls the pointer precompile to register their own EVM contract `AttackerPointer` as the CW721 (or CW1155) pointer for `contractAddrStr = X`, where `X` is actually a well-known CW20 stablecoin contract (assuming registration does not verify `X` implements CW721/CW1155) — via `SetERC721CW721Pointer`/`SetERC1155CW1155Pointer` [4](#0-3) .
2. Victim (or a contract holding victim approvals) is induced to interact with `AttackerPointer`, which internally issues a `DELEGATECALL` to the wasmd precompile with `contractAddrStr = X` and an attacker-chosen CW20 `ExecuteMsg` (e.g. `transfer`).
3. In `execute()`, `ctx.EVMPrecompileCalledFromDelegateCall()` is true; `GetERC721CW721Pointer(ctx, X)` returns `AttackerPointer`, matching `callingContract`, so the guard passes even though `AttackerPointer` has no legitimate ERC20/CW20 relationship to `X` [1](#0-0) .
4. `senderAddr` resolves to the victim's Sei address (preserved through delegatecall as `caller`), and `p.wasmdKeeper.Execute` runs the attacker's CW20 transfer message as the victim, moving the victim's tokens to the attacker [3](#0-2) .

// ERC20 -> CW20
func (k *Keeper) SetERC20CW20Pointer(ctx sdk.Context, cw20Address string, addr common.Address) error {
	return k.SetERC20CW20PointerWithVersion(ctx, cw20Address, addr, cw20.CurrentVersion(ctx))
}

// ERC20 -> CW20
func (k *Keeper) SetERC20CW20PointerWithVersion(ctx sdk.Context, cw20Address string, addr common.Address, version uint16) error {
	if k.cwAddressIsPointer(ctx, cw20Address) {
		return ErrorPointerToPointerNotAllowed
	}
	err := k.setPointerInfo(ctx, types.PointerERC20CW20Key(cw20Address), addr[:], version)
	if err != nil {
		return err
	}
	return k.setPointerInfo(ctx, types.PointerReverseRegistryKey(addr), []byte(cw20Address), version)
}

// ERC20 -> CW20
func (k *Keeper) GetERC20CW20Pointer(ctx sdk.Context, cw20Address string) (addr common.Address, version uint16, exists bool) {
	addrBz, version, exists := k.GetPointerInfo(ctx, types.PointerERC20CW20Key(cw20Address), cw20.CurrentVersion(ctx))
	if exists {
		addr = common.BytesToAddress(addrBz)
	}
	return
}

// ERC20 -> CW20
func (k *Keeper) DeleteERC20CW20Pointer(ctx sdk.Context, cw20Address string, version uint16) {
	addr, _, exists := k.GetERC20CW20Pointer(ctx, cw20Address)
	if exists {
		k.deletePointerInfo(ctx, types.PointerERC20CW20Key(cw20Address), version)
		k.deletePointerInfo(ctx, types.PointerReverseRegistryKey(addr), version)
	}
}
