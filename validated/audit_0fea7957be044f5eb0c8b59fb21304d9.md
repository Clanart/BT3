### Title
Untrusted repository submodule with `file://` URL can be auto-checked-out when `allowFileProtocol` is enabled, allowing arbitrary local path disclosure - ([File: app/src/lib/git/checkout.ts], [File: app/src/lib/git/submodule.ts])

### Summary
`checkoutBranch()` / `checkoutCommit()` accept an `allowFileProtocol` flag that is forwarded to `updateSubmodulesAfterOperation()`, which, when `true`, appends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation. Git normally blocks `file://` submodule URLs by default (`protocol.file.allow=user`) precisely because a repository controlled by an attacker can point a submodule at an arbitrary local filesystem path and have it "cloned" into the working tree, exposing local file contents. If any caller path lets Desktop pass `allowFileProtocol = true` while operating on content that ultimately originates from a cloned/fetched (attacker-controlled) repository, the safety check Git provides is deliberately disabled by Desktop itself.

### Finding Description
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` builds the submodule-update args as: [1](#0-0) 
When `allowFileProtocol` is `true`, the command is run with `-c protocol.file.allow=always`, overriding Git's built-in protection (`protocol.file.allow=user`, which normally refuses `file://` submodule URLs unless the operation is a genuinely local, user-initiated clone). `checkoutBranch` and `checkoutCommit` both expose this same boolean and default it to `false`, but explicitly thread it through as a parameter that callers can set to `true`: [2](#0-1) [3](#0-2) 

The broken invariant is the same class as the seed report: code trusts an interface/flag to behave safely ("approve() always returns/reverts correctly" in the Solidity case) without accounting for the fact that the underlying object it operates on — here, a `.gitmodules` entry — is attacker-controlled content coming from a cloned repository, a fetched branch, or a GitHub API-driven checkout (e.g. PR checkout, `x-github-client://` deep link flows that call `checkoutBranch`/`checkoutCommit`). If any code path threads `allowFileProtocol = true` down to a checkout of a branch/commit whose tree contains a `.gitmodules` file with a `url = file:///etc/passwd` (or any local path such as `~/.ssh`), Git will "clone" that local directory/file into the submodule path inside the repository's working tree, effectively copying local file contents into a location the user did not choose and did not review — silently corrupting the user's working directory with the contents of unrelated, potentially sensitive local files, and creating a foothold for further exfiltration if the user subsequently commits/pushes that content.

The existing guardrails in the codebase (`resolveWithin`, `sanitizeCloneName`, `isClonePathSensitive`) protect against path-traversal when deriving a *clone destination*, but they do nothing to stop a *submodule URL* using the `file://` scheme once `protocol.file.allow=always` has been set for the `git submodule update` invocation — that check happens entirely inside Git's own protocol allow-list, which Desktop is explicitly overriding.

### Impact Explanation
If reachable from a checkout/branch-switch triggered on attacker-supplied content (a cloned malicious repo, a branch fetched from a remote, or a PR/deep-link driven checkout), this allows reading and exposing arbitrary local files/directories the Desktop process can access, by having Git copy them into the repository's working directory as a "submodule." This matches the report's valid-impact categories: file read outside the intended repo scope originating from an attacker-controlled git object, with the potential for a subsequent silent corruption of what the user commits/pushes (since the newly materialized submodule contents look like ordinary tracked/untracked files).

### Likelihood Explanation
This is contingent on whether any caller in the codebase currently passes `allowFileProtocol: true` for a checkout that is *not* purely local/user-initiated (e.g., a PR checkout coming from a fork, or a branch checkout following a fetch of an untrusted remote). Grep results confirmed the flag exists and is plumbed only through `checkout.ts` and `submodule.ts`; I was not able to fully enumerate every call site of `checkoutBranch`/`checkoutCommit` across the app in the remaining iterations to confirm a concrete untrusted-triggering call site with `allowFileProtocol = true` — this is a gap in my verification. The default value is `false`, which is safe; the risk exists only where a caller opts in for content whose provenance is remote/untrusted.

### Recommendation
- Restrict `allowFileProtocol = true` to strictly local, first-party, and pre-vetted operations (e.g., re-checking-out a submodule the user just added locally themselves), never to branches/commits/PRs obtained from a remote or third-party fork.
- Prefer never overriding `protocol.file.allow`; if local submodules are a legitimate use case, validate the submodule URL against an explicit allow-list (e.g., only paths under the same repository's already-known local directories) rather than blanket-enabling `file://` for the whole `submodule update --init --recursive` invocation.
- Add a regression test that checks out an untrusted branch containing a `.gitmodules` entry with a `file://` URL pointing outside the repo and asserts the update is rejected unless the checkout is verified to be a purely local operation.

### Proof of Concept
1. Attacker creates a public repo with `.gitmodules` containing:
   ```
   [submodule "leak"]
       path = leak
       url = file:///Users/victim/.ssh
   ```
2. Victim clones/fetches this repo in GitHub Desktop and checks out the branch/commit containing that `.gitmodules` file via a code path that calls `checkoutBranch`/`checkoutCommit` with `allowFileProtocol: true`.
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, which copies the contents of `/Users/victim/.ssh` into `leak/` inside the repository's working directory.
4. The victim's SSH keys are now materialized as ordinary/untracked files inside the repo, visible in the Changes list, and could be accidentally committed and pushed.

Note: I could not confirm, within the available tool budget, an actual call site in the Desktop UI/dispatcher layer that sets `allowFileProtocol: true` for a checkout originating from untrusted/remote content — this would need to be verified (e.g., by searching `checkoutBranch(`/`checkoutCommit(` call sites across `app/src/ui` and `app/src/lib/stores`) before treating this as a confirmed, exploitable end-to-end path rather than a latent dangerous primitive.

```typescript
export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
```
