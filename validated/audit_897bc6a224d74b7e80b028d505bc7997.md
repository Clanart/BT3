### Title
Shared `BalanceHandler` instance in `Precompile.Run` desyncs EVM StateDB balances from bank-module truth during recursive/nested precompile calls - (File: `precompiles/common/precompile.go`, `precompiles/common/balance_handler.go`)

### Summary
The DYAD report's root cause is that a value-moving side channel (`liquidate`→`move`) does not update the same bookkeeping variable (`idToBlockOfLastDeposit`) that the primary transfer path (`deposit`/`withdraw`) updates, letting an attacker use multiple "accounts" to desynchronize protective state from actual value movement. The Cosmos EVM analog is the `BalanceHandler` used by every stateful precompile (staking, distribution, gov, slashing, ics20, erc20, werc20) to reconcile native bank-keeper balance changes back into the EVM `StateDB`. This mechanism relies on a single mutable `prevEventsLen` marker, and the repository itself contains a dedicated regression test (`evmd/tests/integration/balance_handler/balance_handler_test.go`) explicitly documenting: "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [1](#0-0) 

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `prevEventsLen = len(ctx.EventManager().Events())` before a precompile method executes, and `AfterBalanceChange` replays only the bank/precisebank events that occurred at index `>= prevEventsLen` to update the EVM `StateDB` via `AddBalance`/`SubBalance`. [2](#0-1) 

If a single `BalanceHandler` instance (rather than one freshly allocated per precompile invocation) is reused across a nested/recursive call chain — e.g., a contract that calls a precompile, which re-enters the same precompile or another precompile before the first `AfterBalanceChange` runs — the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` to a later index. When the outer call's `AfterBalanceChange` subsequently executes, it will only replay events starting from this now-advanced `prevEventsLen`, silently skipping the bank events generated by the outer call's own balance-affecting operation. The result is that the bank keeper (source of truth for native/coin balances) correctly reflects the transfer/mint/burn, but the EVM `StateDB` (used for all subsequent EVM-visible balance reads, gas refund calculations, and any downstream contract logic in the same transaction) does not, producing a permanent divergence between the two balance representations for the remainder of that transaction and any state committed from it.

The framework code (`precompiles/common/precompile.go`, `runNativeAction`) allocates a **new** `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()`, which is the safe pattern used by the newer `RunNativeAction` path: [3](#0-2) . However, the debug/test precompile at `testutil/testdata/debug/debug.go` demonstrates the alternate, vulnerable pattern of calling `p.GetBalanceHandler()` — a shared handler stored on the `Precompile` struct — showing that this pattern exists and is reachable in the precompile framework: [4](#0-3) . The dedicated `BalanceHandlerTestSuite` was written specifically to exercise recursive precompile calls through this shared-instance mechanism and assert on event counts, confirming this is a recognized, non-hypothetical hazard in the precompile execution model rather than an academic concern. [5](#0-4) 

This is structurally identical to the DYAD bug: two independent state-mutation code paths (bank keeper's authoritative ledger vs. EVM `StateDB`'s cached balance) are supposed to stay synchronized via a bookkeeping variable (`idToBlockOfLastDeposit` / `prevEventsLen`), but a nested/nonstandard invocation ordering (self-liquidation via a second account / recursive precompile re-entry) causes the bookkeeping variable to be overwritten before the synchronization step runs, silently breaking the invariant without reverting the transaction.

### Impact Explanation
If a production precompile (staking, distribution, gov, slashing, erc20, ics20, werc20) is invoked in a way that triggers nested/recursive precompile calls sharing one `BalanceHandler` (e.g., an ERC20 hook, callback, or contract-to-contract call pattern that re-enters a precompile before the outer call completes), the EVM-side balance for an account can be understated or overstated relative to the actual bank-module balance. Because subsequent EVM operations in the same or later transactions (transfers, `balanceOf` reads via precompiles that source from bank, gas/value checks in `ante/evm/07_can_transfer.go`) trust `StateDB` balances for EVM natives and can trust bank balances for ERC20/precompile views, a sustained desync directly corresponds to "irreversible accounting corruption of spendable user value across native balances / EVM balances" — an attacker could construct a call sequence where the EVM-visible balance is inflated relative to real backing funds, then spend/transfer based on the inflated EVM balance, effectively duplicating spendable value.

### Likelihood Explanation
Likelihood is uncertain without deeper verification: I was not able to fully confirm, within the available iterations, whether any of the six production precompiles (staking, distribution, gov, slashing, erc20, ics20) actually call `p.GetBalanceHandler()` (shared-instance, vulnerable pattern) versus exclusively going through `RunNativeAction`/`BalanceHandlerFactory.NewBalanceHandler()` (per-call, safe pattern) for every method, or whether the framework fully forecloses recursive re-entry into the same precompile call frame before `AfterBalanceChange` runs. The presence of a purpose-built regression test suite for exactly this scenario, and the existence of the vulnerable shared-handler pattern in the debug precompile, indicates the underlying mechanism is fragile and has been treated as a known bug class by the developers, but I could not verify from the retrieved code whether the currently shipped production precompiles are exposed to it or whether the test suite proves the bug is fixed (the test may exist to confirm correct behavior post-fix, or to reproduce the still-open bug — the file's own docstring says it "demonstrates" the bug, suggesting the issue may still be reproducible along a specific call path).

### Recommendation
1. Verify that every stateful precompile (`staking.go`, `distribution.go`, `gov.go`, `slashing.go`, `erc20.go`, `ics20.go`, `werc20`) obtains its `BalanceHandler` via a fresh `BalanceHandlerFactory.NewBalanceHandler()` per top-level `Run` invocation, never via a shared/cached instance field (`p.GetBalanceHandler()`), and remove or gate the shared-instance code path (as currently exercised only by the test-only debug precompile).
2. Make `BalanceHandler` re-entrancy-safe: instead of a single `prevEventsLen int`, use a stack/counter of checkpoints, or bind the handler lifetime strictly to a single call frame that cannot be reused by nested calls (e.g., allocate and pass explicitly through the call context rather than storing on the `Precompile` struct).
3. Add an invariant check after each `AfterBalanceChange` that reconciles `StateDB` balance for touched addresses against `bankKeeper.GetBalance` and reverts/panics on mismatch, to fail closed rather than silently diverge.
4. Extend `BalanceHandlerTestSuite`-style tests to cover recursive calls across the actual production precompiles (not just the debug precompile) to close the coverage gap.

### Proof of Concept
A concrete PoC could not be fully constructed within the available investigation because it requires confirming a real production precompile call path that (a) triggers a nested/recursive precompile invocation before the outer call's `AfterBalanceChange` executes, and (b) uses the shared-`BalanceHandler` code path rather than the per-call `RunNativeAction` path. The existing repository test `TestRecursivePrecompileCallsWithDebugPrecompile` in `evmd/tests/integration/balance_handler/balance_handler_test.go` demonstrates the mechanics (a caller contract triggering 10 nested `debug_precompile` events) and would need to be adapted to a production precompile (e.g., a token contract whose `_beforeTokenTransfer`/`_afterTokenTransfer` hook calls back into the `staking` or `distribution` precompile, similar to the pattern already present in `contracts/solidity/ERC20RecursiveNonRevertingPrecompileCall.sol`) to prove balance divergence on a real, spendable asset. [6](#0-5)

// It records the current number of events in the context to later process balance changes

	bh.prevEventsLen = len(ctx.EventManager().Events())
