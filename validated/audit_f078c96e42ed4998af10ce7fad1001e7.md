## Title
Git's clone-time RCE protection is explicitly disabled during recursive clones of attacker-controlled URLs - (`File: app/src/lib/git/clone.ts`)

### Summary
`clone()` in [1](#0-0)  builds the environment for every `git clone` invocation by explicitly setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and always passing `--recursive`, while the destination URL is fully attacker/user-controlled input (any URL entered in the "Clone repository" dialog, a `x-github-client://openrepo` deep link, or a repo picked from the GitHub API). This unconditionally turns off Git's own clone-time safety check that exists specifically to stop malicious repositories from executing code or writing files outside the intended checkout during a recursive clone.

### Finding Description
Modern Git ships a built-in protection (the mechanism behind fixes for the class of vulnerabilities exemplified by CVE-2024-32002, where a crafted repository with case-confusable or symlinked nested `.git`/submodule directories can, during `clone --recursive`, cause Git to write into or execute hooks from a directory outside the intended worktree) that is active by default for local/remote clones. This is exactly the "existing guard" that should stop a malicious repository from breaking out of the intended destination during a recursive clone.

Desktop's `clone()` function does the opposite of relying on that guard — it forces the safety check off for every clone: [2](#0-1) 

The `url` and `path` arguments originate from user-facing, attacker-influenceable surfaces: the URL/clone dialog, CLI `--cli-clone` argument, and the `x-github-client://openrepo` deep link handled by [3](#0-2) , which is dispatched via [4](#0-3) . None of these paths validate that the *target repository content* is safe — they only validate the destination *path* (`isClonePathSensitive`, at [5](#0-4) ), which defends against a different attack (path traversal to sensitive local directories), not against a malicious remote crafting a repo whose nested submodules/symlinked `.git` entries are designed to be exploited when Git's own protection is disabled.

Because the clone always runs `--recursive` and always disables `GIT_CLONE_PROTECTION_ACTIVE`, an attacker who controls the cloned repository (fully in-scope per this task's "Valid Impact" — "the attacker controls a cloned/fetched repository") can craft nested submodules exploiting the exact class of bug this protection exists to prevent.

### Impact Explanation
If the disabled protection is what stands between a crafted repository and out-of-worktree file writes/hook execution during `--recursive` clone, then disabling it for every single clone performed by Desktop reintroduces that RCE/arbitrary-file-write class of bug for any user who clones an attacker-supplied URL — including via a deep link the user merely clicks, satisfying the "code execution, file write ... outside the repo" impact bucket explicitly called out as valid.

### Likelihood Explanation
Every clone Desktop performs takes this code path unconditionally — there is no opt-out or user-configurable safe mode, and `--recursive` combined with the protection override is applied regardless of whether the URL is a trusted GitHub.com repo the user searched for, or an arbitrary third-party/enterprise URL pasted into the clone dialog or clicked via a deep link. The disabling is unconditional and always paired with `--recursive`, maximizing exposure with no additional user action beyond initiating a normal clone.

### Recommendation
Do not unconditionally set `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Leave Git's built-in clone protection enabled by default for `clone()`; if it must be disabled for a specific known-safe scenario (e.g., cloning the user's own already-trusted repositories), gate it behind an explicit, narrowly-scoped condition rather than applying it to every clone of an arbitrary, potentially attacker-supplied URL.

### Proof of Concept
1. Attacker hosts a malicious Git repository containing a submodule/`.git` layout crafted to exploit the disabled clone-time protection under `--recursive` (the general shape of the CVE-2024-32002 class of issue).
2. Attacker distributes the repository URL either as a normal clone URL or as an `x-github-client://openrepo/<attacker-url>` deep link.
3. Victim clones it in Desktop through the normal "Clone repository" flow or by clicking the link, invoking [6](#0-5) .
4. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` and `--recursive` is always passed, Git's own guard against the malicious nested-submodule layout never triggers, allowing the crafted repository to write/execute outside the intended clone directory.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
