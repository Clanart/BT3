Live-balance double-count correction in `getRewardAmount`/`calDoubledCounted` lets a user re-earn already-paid MGP tiers via `mWomSV.startUnlock` - (File: wombat/ArbWomUp3.sol)

### Summary
`incentiveDeposit(uint256 _amount, uint256 _convertRatio, bool _bullMode, uint256 _mode)` computes the "already rewarded" amount via `calDoubledCounted()`, which reads the user's *current* `mWomSV.getUserTotalLocked(_account)` instead of a stored, monotonic record of past rewards. Because `getUserTotalLocked` in `wombat/mWomSV.sol` immediately drops the moment a user calls `startUnlock` (moving mWom into the cooldown queue, without waiting for the cooldown to elapse), a user can shrink this figure at will and then re-trigger `incentiveDeposit` in lock mode (`_mode == 2`) to claim MGP for a tier bracket that was already paid out in a previous call.

### Finding Description
`getRewardAmount` (wombat/ArbWomUp3.sol:107-129) computes, for lock mode:
```
uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
... // cumulative reward over rewardTier[] up to `accumulated`
mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
```
`calDoubledCounted` (lines 131-144) recomputes the cumulative reward that corresponds to the user's *current* `mWomSV.getUserTotalLocked(_account)`, intending to subtract out the reward already paid for the previously-locked balance so only the incremental portion is newly rewarded.

The flaw: `getUserTotalLocked` (wombat/mWomSV.sol:113-117) is `_amountInMasterMagpie - getUserAmountInCoolDown(_user)`, and `startUnlock` (wombat/mWomSV.sol:247-277) immediately increases `getUserAmountInCoolDown` (via `userUnlockings[...].amountInCoolDown`) as soon as it's called — there is no waiting for `coolDownInSecs` to elapse before this value affects `getUserTotalLocked`. This means a user can:
1. Call `incentiveDeposit(..., _mode == 2)` once, locking `L` mWom and receiving the full MGP reward for reaching tier bracket containing `L` (this reward is correctly recorded as paid at the time, but nothing is stored — only the resulting locked balance `L` implicitly "represents" that payment).
2. Call `mWomSV.startUnlock(L - ε)` directly (an unprivileged, no-permission call on `mWomSV`), instantly reducing `getUserTotalLocked(account)` to `ε` while the bulk of the tokens sit in the cooldown queue (still owned by the user, recoverable after cooldown via `unlock`).
3. Call `incentiveDeposit` again with a modest additional `_amount` such that `accumulated = _amount + ε` lands back at or above `L`. `calDoubledCounted(account)` now only subtracts the reward for the tiny `ε` locked balance (a fraction of what was actually already paid), so `mgpReward` is computed as almost the *entire* cumulative reward for reaching `L` again — effectively double-paying the same tier bracket.
4. After the cooldown period elapses, the user calls `mWomSV.unlock()` to fully recover the original `L - ε` mWom tokens back to their own wallet — tokens they never permanently committed, on top of the freshly re-minted MGP reward.

No modifier (`nonReentrant`, `whenNotPaused`) or accounting check in `ArbWomUp3` prevents this, because the exploit does not require reentrancy or a single atomic transaction — it only requires two independent, unprivileged transactions (an `incentiveDeposit` call and a `mWomSV.startUnlock` call) separated by ordinary block time. The referenced "sandwich around the wom/mWom Wombat pool" is not actually necessary for this specific bug — the root cause is entirely within `calDoubledCounted`'s use of a live, user-lowerable balance as its "already rewarded" record; the `bracketRewarded` mapping that could have stored this monotonically is explicitly declared but marked `// not in use` (wombat/ArbWomUp3.sol:47).

### Impact Explanation
This allows an attacker to repeatedly re-claim MGP incentive rewards for the same locked-mWom tier bracket by cycling `startUnlock`/relock, draining the `mgp` token balance held by `ArbWomUp3` (capped only by `IERC20(mgp).balanceOf(address(this))`, wombat/ArbWomUp3.sol:127-128) far beyond what legitimate depositors were entitled to. This matches "Critical - Direct theft of user funds" since the MGP incentive pool is drained by an unprivileged actor exploiting the double-count logic, at the expense of the protocol's incentive reserves and other genuine participants who will find the reward pool exhausted.

### Likelihood Explanation
- Fully reachable by any unprivileged EOA; requires only holding WOM tokens to deposit and calling public functions on `ArbWomUp3` and `mWomSV`.
- No special capital beyond the WOM needed for the top-up deposit (`ε`-sized delta) is required per cycle; the bulk of the locked balance is always recoverable after cooldown.
- Repeatable: the attacker can perform this "unlock-relock" cycle every `coolDownInSecs` (or with multiple unlock slots up to `maxSlot` in parallel), draining MGP incentives repeatedly.
- The only "precondition" is that `rewardTier`/`rewardMultiplier` be configured (via `setMultiplier`, an owner-only setup action expected to happen normally) and that the contract holds an MGP reward balance to be drained — both are the ordinary operating state of this contract.

### Recommendation
Replace the live-balance-based `calDoubledCounted()` with a monotonically increasing, per-user stored record of MGP (or reward-equivalent-locked) amount already rewarded — e.g., actually use the existing but unused `bracketRewarded` mapping, incrementing it by the exact `mgpReward` granted (or by the tier-bracket amount consumed) on every `incentiveDeposit` call, and basing future incremental-reward calculations on that stored value rather than re-reading `mWomSV.getUserTotalLocked(_account)`. Additionally, consider snapshotting the locked balance immediately before this specific deposit (rather than the live value which can change via unrelated `mWomSV` calls) so that reward accounting can never regress.

### Proof of Concept
Foundry fork test plan:
1. Deploy/fork `ArbWomUp3`, `mWomSV`, `MasterMagpie`, `wom`/`mWom` tokens, and `smartWomConvert`. Configure `rewardTier = [0, 1000e18, 3000e18]`, `rewardMultiplier = [100, 300]` (bps-style multipliers), fund `ArbWomUp3` with a large `mgp` balance via `adminWithdrawReward`-reverse (owner mint/transfer).
2. Attacker account `A` calls `incentiveDeposit(1000e18, ratio, false, 2)`; record `mgpBalanceAfter1 = IERC20(mgp).balanceOf(A_vlMGP_lock)` and `lockedAfter1 = mWomSV.getUserTotalLocked(A)` (~1000e18).
3. `A` calls `mWomSV.startUnlock(999e18)` directly. Assert `mWomSV.getUserTotalLocked(A)` immediately drops to `~1e18` (no cooldown wait required for this read).
4. `A` calls `incentiveDeposit(999e18, ratio, false, 2)` again. Assert `getRewardAmount`/`calDoubledCounted` yields a `mgpReward` close to the full first-time reward (i.e., `mgpBalanceAfter2 - mgpBalanceAfter1 ≈ mgpBalanceAfter1`), rather than a near-zero incremental reward, demonstrating the tier bracket `[0,1000e18]` was rewarded twice.
5. Advance time past `coolDownInSecs`; `A` calls `mWomSV.unlock(slotIndex)` to recover the original `999e18` mWom back to their wallet.
6. Assert final state: `A` has received MGP reward for cumulative locked amount `~1999e18` (two tiers' worth) while never having more than `~1000e18` mWom permanently committed at any settled time, and the contract's `mgp` reserve has been depleted by roughly double the amount a single, honest 1000e18 depositor would have received — confirming the invariant break and fund drain.
