### Title
Unbounded quadratic Lagrange interpolation in `ThresholdKeys::new`/`ThresholdKeys::read` enables CPU denial of service via crafted serialized keys - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `n`/`t` (each up to `u16::MAX` = 65535) and then `ThresholdKeys::new` computes the group key by calling `interpolation_factor` for every participant `1..=t`. Under `Interpolation::Lagrange`, each `interpolation_factor` call is O(`included.len()`), so construction is O(t²) field multiplications — up to ~4.3×10⁹ multiplications for `t = 65535` — plus `n` point decompressions. This is the Serai analog of CVE-2018-16875: no bound on per-verification (here, per-deserialization) work for pathological inputs.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` directly from the input stream, then reads `n` scalars/points and calls `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:574-632`). `ThresholdKeys::new` computes `group_key` as the sum over participants `1..=t` of `verification_shares[i] * interpolation_factor(i, &t)` (`crypto/dkg/src/lib.rs:376-378`). `interpolation_factor` for `Interpolation::Lagrange` iterates the entire `included` vector performing field multiplications (`crypto/dkg/src/lib.rs:229-246`). Since `ThresholdParams::new` only enforces `t <= n <= u16::MAX` (`crypto/dkg/src/lib.rs:166-179`), a small serialized blob (< ~100 bytes of header) claiming `t = n = 65535` forces ~t² ≈ 4.3 billion field operations during group-key derivation, and any subsequent `view(included)` repeats quadratic interpolation per included participant (`crypto/dkg/src/lib.rs:500-507`).

### Impact Explanation
An unprivileged party who can supply bytes to `ThresholdKeys::read` (or otherwise induce a node to deserialize/construct `ThresholdKeys` with adversarial `t`/`n`) can pin a CPU core for an extended period with a tiny input — a classic asymmetric CPU DoS identical in class to the Go `crypto/x509` chain-verification issue: the amount of work performed per input is unbounded relative to input size.

### Likelihood Explanation
Reachability depends on the integrator feeding untrusted bytes into `ThresholdKeys::read` or `ThresholdKeys::new`; within this codebase, DKG outputs flow between participants via the pedpop/musig machines, and any deployment that persists or relays serialized threshold keys from untrusted sources exposes the path. The work amplification (~4×10⁹ ops from <1KB input) makes even occasional hits impactful.

### Recommendation
- Reject or cap `t`/`n` in `ThresholdKeys::read`/`ThresholdParams::new` to a protocol-meaningful maximum (e.g., `MAX_KEY_SHARES_PER_SET` used elsewhere in the codebase) before allocating/iterating.
- Compute the group key for `Interpolation::Constant` directly (sum of `binding_factor * share`) and avoid per-participant O(n) Lagrange evaluation where a linear-time aggregate suffices; at minimum, precompute denominator inverses via batch inversion.
