## Analysis

This repository contains an exact structural analog of the `BurnUnlock` bug, but on the **receiving side of an IBC transfer for a `NativeERC20` token pair**, in `x/erc20/keeper/ibc_callbacks.go` `OnRecvPacket` combined with `ConvertCoinNativeERC20` in `x/erc20/keeper/msg_server.go`.

### Title
Native-ERC20 IBC receive can return an error acknowledgement after an irreversible bank-coin state mutation, causing duplicated token value across chains - (`x/erc20/keeper/ibc_callbacks.go`, `x/erc20/keeper/msg_server.go`)

### Summary
When an IBC packet delivers a coin backed by a chain-native ERC20 token pair, the base ICS20 transfer application first unescrows/mints the coin to the recipient and returns a *success* acknowledgement. The `x/erc20` IBC middleware then attempts an automatic conversion of that coin back into the ERC20 representation via `ConvertCoinNativeERC20`. If this secondary conversion step fails (e.g. the EVM `transfer` call reverts because the module account's escrowed ERC20 balance/contract state doesn't match expectations), the middleware overwrites the already-successful acknowledgement with an **error acknowledgement**. Because IBC-go only branches/reverts state when the message handler returns a Go `error` — not when the acknowledgement content is `Error` — all state mutations made up to that point (the original mint/unescrow, plus the partial escrow-to-module-account transfer performed inside `ConvertCoinNativeERC20`) are committed. The counterparty chain then processes the error ack and refunds the original sender. The net effect: value is created on both chains — the sender is refunded on the source chain, while on the destination chain the coin remains stuck (escrowed to `types.ModuleName`) without ever being burned back or attributed to anyone, having already been drained from the ICS20 escrow (or freshly credited) irreversibly.

### Finding Description
`IBCMiddleware.OnRecvPacket` [1](#0-0)  first invokes the wrapped ICS20 transfer module (which performs the mint/unescrow to the recipient), and only if that succeeds (`ack.Success()`), calls `im.keeper.OnRecvPacket`.

Inside `Keeper.OnRecvPacket` [2](#0-1) , for the `pair.IsNativeERC20()` case, it calls `ConvertCoinNativeERC20`, and **replaces the already-successful ack with a brand-new error acknowledgement** if that call fails:
```go
if err := k.ConvertCoinNativeERC20(ctx, pair, coin.Amount, common.BytesToAddress(recipient.Bytes()), recipient); err != nil {
    return channeltypes.NewErrorAcknowledgement(err)
}
```

`ConvertCoinNativeERC20` itself performs a sequence of non-atomic, non-cached state mutations [3](#0-2) : it first escrows the bank coin from the recipient into the erc20 `ModuleAccount` (`SendCoinsFromAccountToModule`), and only afterward calls the EVM `transfer` to unescrow the ERC20 token to the recipient. If that EVM call fails, the function returns an error, but the earlier `SendCoinsFromAccountToModule` call is **not rolled back** — there is no `ctx.CacheContext()`/`writeFn()` pattern used here (unlike the pattern seen in `x/ibc/callbacks/keeper/keeper.go`, which does correctly use cache contexts for its EVM calls). 

Crucially, per IBC-go / Cosmos SDK semantics, returning an acknowledgement object with `Error` content is not the same as the packet-receiving message handler (`MsgRecvPacket`) returning a Go `error`. The message handler still returns success, so the whole branched state for that transaction — including the original mint/unescrow by the base ICS20 app and the partial escrow performed by `ConvertCoinNativeERC20` — is committed to the store. Only the acknowledgement payload written back to the source chain reflects failure.

This mirrors the `BurnUnlock` root cause exactly: an irreversible state change ("burn on source" in the original report; here, "coin is unescrowed to recipient and then re-escrowed to the module account" on the destination chain) is performed *before* confirming that the corresponding step ("unlock on destination"; here, "ERC20 unescrow" via EVM call) actually succeeds, and the failure signal (error ack) subsequently drives a *refund* on the other chain that assumes nothing happened on this chain.

### Impact Explanation
The consequence is duplicated/unbacked token value:
- The **source chain**, upon receiving the error acknowledgement, executes its standard refund path (`OnAcknowledgementPacket` → `ConvertCoinToERC20FromPacket` [4](#0-3) ), returning the original sender's tokens as if the transfer never succeeded.
- The **destination chain** has already unescrowed/minted the coin to the recipient (via the base ICS20 app, which succeeded) and then moved it into the `types.ModuleName` module account during the failed `ConvertCoinNativeERC20` call, where it is stranded — neither returned to the recipient, nor burned, nor reconciled with the ICS20 escrow account.

This satisfies the "Critical unauthorized minting/duplication/irreversible accounting corruption of spendable user value across ... IBC escrows" impact class: total circulating value across the two chains increases by the transferred amount every time this failure path is hit, and funds become permanently stuck/unattributed in the erc20 module account on the destination chain.

### Likelihood Explanation
Unprivileged trigger: this is reachable by an ordinary user submitting `MsgTransfer` for a coin registered as a chain-native ERC20 token pair, combined with any condition that causes `ConvertCoinNativeERC20`'s EVM `transfer` call to fail on the receiving chain (e.g., the module account's escrowed ERC20 balance for that token has been depleted/mismatched, the ERC20 contract has non-standard behavior, or has been paused/selfdestructed — all realistically reachable states given ERC20 registration is permissionless per `RegisterERC20` [5](#0-4) ). No relayer or validator misbehavior is required — an honest relayer simply delivers the packet and relays the resulting ack.

### Recommendation
Wrap the entire `OnRecvPacket` conversion logic (mint/unescrow by the base ICS20 app + `ConvertCoinNativeERC20`) in a `ctx.CacheContext()`/`writeFn()` pattern, only committing state if the whole sequence — including the ERC20 conversion — succeeds; otherwise return the error acknowledgement with the underlying store changes discarded, letting the recipient simply keep the bank-coin representation (per the documented, but not implemented, fallback behavior "the user receives the corresponding bank token instead").

### Proof of Concept
1. Register a native ERC20 token pair on chain B via `MsgRegisterERC20`.
2. From chain B, convert some ERC20 to the coin representation and send it to chain A via `MsgTransfer` (escrows chain B's ERC20 in `types.ModuleAddress`, and the coin is escrowed in the ICS20 escrow account on B when later transferred out and back, or minted as voucher on A).
3. From chain A, send the coin back to chain B via IBC (`MsgTransfer` with the corresponding voucher denom / native denom).
4. Ensure that, at the time chain B processes `OnRecvPacket`, `k.evmKeeper.CallEVM(..., "transfer", ...)` inside `ConvertCoinNativeERC20` fails (e.g., have another concurrent packet or `ConvertCoinNativeERC20`/`ConvertCoin` invocation drain the module's escrowed ERC20 balance for that contract first, or interact with an ERC20 contract that reverts under certain conditions).
5. Observe: chain B's `OnRecvPacket` returns an error acknowledgement even though the underlying ICS20 unescrow/mint already succeeded and the coin was moved into `types.ModuleName` by `ConvertCoinNativeERC20`'s `SendCoinsFromAccountToModule` call.
6. Chain A processes the error ack and refunds the original sender in full.
7. Verify on chain B: the coin is now held by the `x/erc20` module account (`authtypes.NewModuleAddress(types.ModuleName)`), not attributed to the recipient, and not returned to the ICS20 escrow account — while chain A's sender balance has also been restored, demonstrating value duplication.

func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

		ctx.EventManager().EmitEvent(
			sdk.NewEvent(
				types.EventTypeRegisterERC20,
				sdk.NewAttribute(types.AttributeKeyCosmosCoin, pair.Denom),
				sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
			),
		)
	}

	return &types.MsgRegisterERC20Response{}, nil
}
