### Title
Missing generator-promotion proof causes a panic (DoS) instead of an error - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates only the *count* and *upper bound* of the supplied proof map, then unconditionally indexes it with `proofs.get(&i).unwrap()`. If any participant `j != i` fails to supply a `GeneratorProof` — which any unprivileged protocol peer can arrange by simply not sending one — the function panics rather than returning a `PromotionError`, crashing the caller.

### Finding Description
In `crypto/dkg/promote/src/lib.rs:120-156`, `complete` performs two checks on the peer-supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

```rust
if proofs.len() != (usize::from(params.n()) - 1) { ... IncorrectAmountOfParticipants ... }
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... InvalidParticipant ... }
}
```

It then iterates `for i in 1 ..= params.n()`, skips its own index, and does `let proof = proofs.get(&i).unwrap();` (line 146). The validation never establishes that every participant `1..=n` (other than `self.params.i()`) is actually present in the map. It checks cardinality (`n - 1` entries) and that no key exceeds `n`, but a map of `n - 1` distinct keys drawn from `1..=n` can still be missing a required participant — for example, `{1..=n} \ {j}` where `j` is the participant who withheld their proof (that set legitimately contains `i` since a peer's message is indexed under their own ID).

When `j`'s proof is absent, `proofs.get(&j)` returns `None` and `.unwrap()` panics. This is reachable entirely through public protocol inputs: the `proofs` map is populated from `GeneratorProof` messages sent by other participants (deserializable via `GeneratorProof::read`, as exercised in `crypto/dkg/promote/src/tests.rs:90`), and a peer withholding their message — or a mis-sequenced delivery — produces a map missing exactly that key.

### Impact Explanation
Analogous to CVE-2018-2839 (unauthorized ability to cause a hang/crash → complete DoS), a single remote participant can crash the local key-promotion routine. In a deployment where promotion runs inside the validator/processor process (which treats panics as fatal), one non-responsive or malicious-indexed peer aborts the promotion for the whole set — an availability failure requiring no privileges, keys, or collusion. The error enum `PromotionError` already has variants for invalid/missing conditions, so the panic is an unchecked-invariant bug, not intended behavior.

### Likelihood Explanation
Any participant in the `n`-of-`n` promotion can trigger it by omitting their proof (or by the caller constructing the map from received messages where one sender is silent/faulty). No cryptographic work is needed; likelihood is high whenever the protocol is exposed to peers that can drop or withhold messages, which is precisely the threat model for distributed key ceremonies.

### Recommendation
Replace the `unwrap()` with a membership check that returns `PromotionError::MissingParticipant`/`IncorrectAmountOfParticipants` for any `i in 1..=n, i != params.i()` absent from `proofs`, e.g. iterate `proofs.keys()` to confirm the set equals `all_participant_indexes() minus i`, or use `proofs.get(&i).ok_or(PromotionError::MissingParticipant(i))?`.

### Proof of Concept
Setup: generate `n` `ThresholdKeys<C1>` shares (as in `crypto/dkg/promote/src/tests.rs`), build `GeneratorPromotion::promote` for participant `i`, then call `complete` with a `proofs` map containing `n - 1` entries keyed `{1..=n} \ {j}` for some `j != i` — i.e., every peer's proof except `j`'s (which may be filled with a valid `GeneratorProof` from another index or even a syntactically valid read of a real proof). The length check `proofs.len() == n - 1` passes, all keys satisfy `u16::from(k) <= n`, and execution reaches `proofs.get(&j).unwrap()` at `crypto/dkg/promote/src/lib.rs:146`, panicking instead of returning an error.

Caveat: this analysis assumes the caller populates the `proofs` map directly from received peer messages keyed by sender index (the natural integration, mirroring `crypto/dkg/pedpop` usage). If the integrator pre-validates the participant set before calling `complete`, the panic is unreachable; the library itself does not enforce that invariant.
