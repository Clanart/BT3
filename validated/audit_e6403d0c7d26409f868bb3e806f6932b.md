## Title
Explicit override of Git's built-in recursive-clone RCE protection (`GIT_CLONE_PROTECTION_ACTIVE`) - (File: `app/src/lib/git/clone.ts`)

## Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for `git clone --recursive` and unconditionally forces `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into that environment before invoking git. `GIT_CLONE_PROTECTION_ACTIVE` is the guard Git itself introduced (as part of the fix for CVE‑2024‑32002, the recursive-clone submodule RCE) to detect and refuse the exploit condition (a malicious repository/submodule whose on-disk layout, via case-insensitive filesystems or crafted symlinked `.git`-like paths, tricks Git into executing hooks from an untrusted location during a nested/recursive clone). By explicitly setting this variable to `'false'` for every `--recursive` clone Desktop performs, the application is forcing Git's own internal safety check off, regardless of the Git version's default.

## Finding Description
`clone()` always passes `--recursive` and constructs:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
``` [1](#0-0) 

`envForRemoteOperation` only sets authentication and proxy variables — it never touches `GIT_CLONE_PROTECTION_ACTIVE` — so the `false` value is added purely by Desktop's own code, not inherited from any upstream default. [2](#0-1) 

The broken invariant here mirrors the report's pattern: a security-relevant boolean/threshold check is set to the wrong value, silently disabling the intended protection while leaving surrounding code (the sensitive-path destination check in the same file) looking like the developer was actively hardening clone security. The `isClonePathSensitive()` guard added just above this block only protects the *local destination* path (`~/.ssh`, `~/.gnupg`, etc.) — it does nothing to protect against the recursive-submodule-clone RCE that `GIT_CLONE_PROTECTION_ACTIVE` exists to stop. [3](#0-2) 

An attacker who controls the content of a repository (the exact threat model in scope — "attacker controls a cloned/fetched repository") can craft a submodule/gitlink layout that, on a case-insensitive or symlink-capable filesystem, causes Git to write/execute hooks or configuration outside the intended repository boundary when Desktop performs `git clone --recursive` on it. Git's own upstream fix relies on `GIT_CLONE_PROTECTION_ACTIVE` being left at its default (enabled) so that Git can detect this specific attack pattern during the nested clone and abort. Desktop's `clone.ts` unconditionally overrides it to disabled for every recursive clone, removing that specific backstop.

## Impact Explanation
If Git's `GIT_CLONE_PROTECTION_ACTIVE` mechanism is the guard for the CVE‑2024‑32002 class of recursive-clone submodule attacks, forcing it off reintroduces the RCE/arbitrary-file-write conditions that upstream Git patched for, specifically for every clone Desktop performs (since `clone()` is the single code path used and always requests `--recursive`). This matches the "Valid Impact" criteria: the attacker only needs to control a repository that the victim clones through Desktop (no local access, no malware, no social engineering beyond "clone this URL/repo" which is core Desktop functionality), and the potential outcome is code execution or file writes outside the intended repository directory.

## Likelihood Explanation
Likelihood is high in terms of trigger conditions (every single clone in Desktop goes through this function and always sets the flag to `'false'`), but the practical exploitability depends on whether the installed Git binary still honors `GIT_CLONE_PROTECTION_ACTIVE` as the CVE-2024-32002 protection mechanism and whether the target filesystem is case-insensitive or otherwise vulnerable to the underlying gitlink/symlink trick. I was not able to verify from this codebase alone (no vendored Git source is indexed here) the exact semantics Git assigns to this variable in the bundled `dugite`/Git version, so I cannot fully confirm this is the *same* variable/guard as the upstream CVE fix versus some other custom flag Desktop itself defines. This should be verified against the actual `dugite`-bundled Git version's source/changelog before treating this as confirmed-exploitable.

## Recommendation
- Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()`, or verify precisely why it was added (e.g., a compatibility workaround) and restrict disabling to only the narrow scenario that requires it, and only after confirming that scenario is not itself attacker-triggerable via `url`.
- Add a regression test asserting that `GIT_CLONE_PROTECTION_ACTIVE` is not set (or is explicitly left enabled) when invoking `git clone --recursive` from Desktop.
- If the flag must be disabled for legitimate reasons, gate it so it is never disabled for network/remote clones of untrusted URLs, and document the exact upstream Git protection being bypassed and why it's safe to bypass in Desktop's flow.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
```
