### Title
Reward-pool "harvest sandwich" enables risk-free reward dilution in BaseRewardPool / mWOMSVBaseRewarder / vlMGPBaseRewarder - (File: `contracts--014/rewards/BaseRewardPool.sol`, `contracts--014/rewards/BaseRewardPoolV2.sol`, `contracts--014/wombat/WombatStaking.sol`)

### Summary
`BaseRewardPool._provisionReward` (and its equivalents in `BaseRewardPoolV2.sol`, `mWOMSVBaseRewarder.sol`, `vlMGPBaseRewarder.sol`) immediately bumps `rewardPerTokenStored` by dividing the newly arrived reward amount over the *current* `totalStaked()` at the moment the reward is queued. [1](#0-0)  Because `WombatStaking.harvest()` is a permissionless, unrestricted entrypoint (`_onlyActivePool` only checks the pool is active, not who calls it) that triggers `_toMasterWomAndSendReward`, which ultimately calls `queueNewRewards`/`_provisionReward`, any wallet can watch for pending Wombat rewards, deposit into the corresponding pool right before triggering (or being front-run by) a harvest, and withdraw immediately after — capturing a slice of rewards that accrued while it had no stake, diluting long-term stakers. [2](#0-1) [3](#0-2) 

### Finding Description
Standard MasterChef-style pools (e.g. `MasterMagpie`) accrue rewards linearly over time via `mgpPerSec` multiplied by elapsed seconds, so a deposit right before an `updatePool` call earns essentially nothing extra since `multiplier` is tiny. [4](#0-3)  However, `BaseRewardPool`/`BaseRewardPoolV2`/`mWOMSVBaseRewarder`/`vlMGPBaseRewarder` use a *lump-sum donation* model: whenever `queueNewRewards` (manager-only, called by `WombatStaking`) or `donateRewards` (public) is invoked, the entire `_amountReward` is instantly divided by `totalStaked()` at that exact block and added to `rewardPerTokenStored`, with no time-weighting whatsoever. [5](#0-4) 

This mirrors the referenced Citadel bug exactly: in `CitadelMinter.mintAndDistribute`, a lump sum of new tokens was minted and distributed to *current* share holders, inflating share price instantly and letting a depositor who entered right before the mint withdraw immediately after for profit. Here, the analogous "mint and distribute" event is any call that funnels newly-harvested Wombat rewards (WOM, bonus tokens) into the reward pool via `queueNewRewards`. This happens routinely: `WombatStaking.deposit`, `withdraw`, and `harvest` all call `_toMasterWomAndSendReward`, which harvests from Wombat's `MasterWombat` and forwards the harvested amount to the reward pool. [6](#0-5)  `harvest(_lpToken)` in particular is callable by literally any address once a pool is active, with no cooldown, no minimum holding period, and no per-block/per-tx restriction, making the sandwich trivially executable in a single transaction (deposit → trigger harvest → withdraw) or via a two-transaction MEV bundle. [7](#0-6) 

Concretely:
1. Attacker observes a large pending WOM reward on Wombat's `MasterWombat` for pool `_lpToken`.
2. Attacker calls `WombatPoolHelper.deposit`/`WombatStaking.deposit` (or `depositLP`) for a large `_amount`, which stakes receipt tokens in `MasterMagpie` and increases `totalStaked()` in the corresponding `BaseRewardPool`.
3. Attacker (or anyone) calls `harvest(_lpToken)`, which pulls the large pending WOM reward and calls `queueNewRewards`, instantly minting `rewardPerTokenStored` proportional to `_amountReward / totalStaked()` — where `totalStaked()` now includes the attacker's fresh, unearned stake.
4. Attacker immediately calls `withdraw`, claiming their proportional share of `rewardPerTokenStored` even though they were staked for a single block.

Because the attacker's deposit inflates the denominator at exactly the moment the numerator (reward) is added, and the attacker's own capital receives back a share of that same reward, other genuine long-term stakers receive a diluted share of the harvest they alone contributed to earning (via TVL over time).

### Impact Explanation
This results in permanent, uncompensated loss of yield for legitimate long-term LPs/stakers in the affected `BaseRewardPool`/`BaseRewardPoolV2`/`mWOMSVBaseRewarder` instances: a portion of every harvested Wombat reward batch is siphoned to opportunistic single-block depositors, which is a direct theft of unclaimed yield from existing users, matching the finding's "theft of unclaimed yield" impact category.

### Likelihood Explanation
Likelihood is high relative to the original Citadel case because there is no 21-day vesting lock here — the attacker's capital is exposed for a single block/transaction rather than 21 days, removing the price-risk factor that led the original judges to downgrade severity. `harvest()` is fully permissionless and can be called by the attacker themselves in the same transaction as their deposit and withdrawal, making this executable atomically with zero directional market exposure, unlike the Citadel case which required flashbots and multi-day exposure. [2](#0-1) 

### Recommendation
Replace the lump-sum `rewardPerTokenStored` bump in `_provisionReward` with a time-weighted/streaming distribution (e.g., a `periodFinish`/`rewardRate` model as in Synthetix `StakingRewards`, or requiring rewards to vest over a duration) so newly-added stake cannot immediately capture freshly harvested rewards. Alternatively, enforce a minimum staking duration before a deposit is eligible to earn from any reward `queueNewRewards` call, or snapshot `totalStaked()` prior to the block in which the reward was queued.

### Proof of Concept
1. `BaseRewardPoolV2` pool has `totalStaked() = 1000e18`, `rewardPerTokenStored = 0`.
2. Attacker calls `deposit` (via `WombatPoolHelperV2`) for `9000e18` receipt tokens, bringing `totalStaked()` to `10000e18`. This happens inside `WombatStaking.deposit`, which itself first calls `_toMasterWomAndSendReward(_lpAddress, lpReceived, true)` — but if the attacker's transaction is placed immediately before a large pending-reward harvest (or the deposit's own internal harvest triggers a smaller donation while a much larger external harvest follows in the same block via `WombatStaking.harvest`), the attacker's stake is present when the big `queueNewRewards(50000e18, WOM)` call executes.
3. `_provisionReward` executes: `rewardInfo.rewardPerTokenStored += (50000e18 * 10**decimals) / 10000e18` — attacker now owns 90% of `totalStaked()` and is entitled to 90% of the just-added `50000e18` WOM, i.e., `45000e18`, despite having contributed only one block of exposure. [8](#0-7) 
4. Attacker immediately calls `withdraw` via `WombatPoolHelperV2.withdraw`, which calls `_unstake` → `MasterMagpie.withdrawFor` → `_harvestBaseRewarder`, realizing the `45000e18` WOM reward, then withdraws the underlying principal from Wombat. [9](#0-8) 
5. Net effect: attacker earned reward proportional to capital with zero time-at-risk, at the expense of the original `1000e18` long-term stakers who now only share the remaining `5000e18`.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```

```text
    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }
```
