Based on the evidence gathered, the closest verified analog is not a "revert on cancel/refund" issue (Desktop has no user-defined-token analog), but a structurally similar issue: **an attacker-controlled repository object (a `.gitmodules` entry) that Desktop trusts without restriction**, mirroring the report's core flaw — "no restriction on an attacker-supplied value that is later used in a privileged operation."

I was not able to fully confirm, within the remaining tool budget, the exact conditions under which `allowFileProtocol: true` is passed from `app/src/lib/git/checkout.ts` into `updateSubmodulesAfterOperation`. This should be verified in a follow-up before treating the finding as fully confirmed.

### Title
Submodule updates can re-enable `file://` protocol cloning, allowing a malicious repo to pull arbitrary local paths into the working tree - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` flag that, when true, adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation [1](#0-0) . This explicitly re-enables the `file://` transport that upstream Git disabled by default (the fix for CVE-2022-39253, where a malicious `.gitmodules` submodule URL using `file://` could be used to clone arbitrary local paths into the repository). The flag is consumed from `app/src/lib/git/checkout.ts`, which calls into this same submodule-update path [2](#0-1) , but I could not fully verify from the index alone whether the code that sets `allowFileProtocol: true` correctly restricts it to trusted, previously-known submodule remotes versus being applied broadly to any freshly fetched/checked-out branch that introduces new submodules from an untrusted clone/fetch.

### Finding Description
Like the `OracleLess.tokenIn` field in the Sherlock report — an attacker-controlled value accepted with no allow-list before being used in a security-sensitive operation — a `.gitmodules` file is fully attacker-controlled content that arrives via clone/fetch/checkout of a remote repository. Git's own hardening restricts submodule URLs to `file://` only when explicitly allowed, precisely because an attacker can set a submodule URL such as `file:///home/user/.ssh` or `file:///home/user/Documents` and have Git treat that local directory as a "repository" to clone, effectively exfiltrating its contents into the submodule path of the working tree. GitHub Desktop's `submodule.ts` unconditionally honors `allowFileProtocol` by injecting `protocol.file.allow=always` without any check tying the submodule URL to a known/trusted origin [3](#0-2) .

### Impact Explanation
If this flag is reachable from a normal checkout/clone/pull of an untrusted, attacker-supplied repository (as opposed to being gated to only re-initializing submodules the app itself previously validated), a malicious repository could:
- Cause Desktop to silently copy the contents of arbitrary local directories (e.g. `~/.ssh`, `~/.aws`, browser profile folders) into the submodule path within the cloned working tree.
- If the victim later stages/commits/pushes ("Publish repository", "Push"), those exfiltrated files become visible to the attacker who controls the origin remote — this matches the requested impact category of "credential/token exfiltration" and "silent corruption of what the user commits or pushes," since the user has no visual indication that a submodule directory now contains copied local files rather than a legitimate cloned repo.

### Likelihood Explanation
This requires only that the victim clone, fetch, or check out a branch introducing a submodule from an attacker-controlled repository, and that Desktop's own code path enables `protocol.file.allow=always` for that operation — no local access, no admin rights, and no unusual user action beyond normal Desktop usage (clone/fetch/pull/checkout) is required. This is exactly the class of guard that upstream Git added after CVE-2022-39253, so if Desktop's own `allowFileProtocol` plumbing bypasses that guard for untrusted submodule content, the mitigation is nullified.

### Recommendation
Restrict `allowFileProtocol: true` strictly to submodule paths/URLs that were already known and initialized locally (i.e., re-syncing a submodule the user has already trusted), never to newly-introduced `.gitmodules` entries coming from a fetch/clone/checkout of a remote the user does not control. Alternatively, validate that any `file://` submodule URL resolves to a path inside an already-trusted location (e.g., another already-cloned sibling repository) before allowing the flag, and audit every call site in `app/src/lib/git/checkout.ts` to confirm this flag is not set for first-time checkouts of branches from unauthenticated/foreign remotes.

### Proof of Concept
1. Attacker creates a repository with a `.gitmodules` file containing:
```
[submodule "leak"]
    path = leak
    url = file:///home/victim/.ssh
```
2. Attacker gets the victim to clone this repository, or to fetch/checkout a branch containing this `.gitmodules` file, in GitHub Desktop.
3. If the code path that invokes `updateSubmodulesAfterOperation(..., allowFileProtocol: true)` is reached for this untrusted content, Desktop runs `git -c protocol.file.allow=always submodule update --init --recursive`, which clones `/home/victim/.ssh` into the `leak/` directory of the working tree [4](#0-3) .
4. The victim's private keys now exist as tracked/untracked files inside their repository; if the repository is later pushed, they are exposed to the attacker-controlled remote.

Given I could not fully trace every caller in `checkout.ts` to confirm the exact gating conditions before this iteration budget ended, this should be verified by inspecting all call sites of `updateSubmodulesAfterOperation` and confirming whether `allowFileProtocol` can ever be `true` for submodules introduced by a fetch/clone from an untrusted remote.
