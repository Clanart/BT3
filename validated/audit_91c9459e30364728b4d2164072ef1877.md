### Title
ProtoJSON parser embeds raw attacker-controlled field values into `ParseError` exception messages, bypassing `debug_redact` protections and exposing sensitive data to application logs - ([File: python/google/protobuf/json_format.py])

### Summary
CVE-2023-5182 describes subiquity logging sensitive data (hashed passwords) because a diagnostic/debug code path emitted attacker/user-controlled content into logs without applying the sanitization that other paths applied. The invariant that failed: values considered sensitive should never reach an unredacted log/diagnostic channel. The Protobuf analog is in the pure-Python ProtoJSON parser (`python/google/protobuf/json_format.py`): several error paths interpolate the raw JSON value (the literal field content submitted by the client) directly into `ParseError` message text, with no `debug_redact` check, unlike the parallel `TextFormat`/`DebugString()` machinery which explicitly redacts fields marked `debug_redact = true`.

### Finding Description
Protobuf has a dedicated mechanism to prevent sensitive proto field values from leaking into human-readable/debug output: `FieldOptions.debug_redact`, enforced in C++ via `TextFormat::Printer::TryRedactFieldValue` and `GetRedactionState` (`src/google/protobuf/text_format.cc:3265-3305`), and in Java via `FieldDescriptor.getRedactionState()`/`DebugFormat` (`java/core/src/main/java/com/google/protobuf/TextFormat.java:668-676`, `DebugFormatTest.java:87-122`). `Message::DebugString()`/`StringifyMessage` turn redaction on by default (`src/google/protobuf/text_format.cc:118-148`, `SetRedactDebugString(true)`).

However, `_Parser._ConvertFieldValuePair`, `_ConvertScalarFieldValue`, `_ConvertMapFieldValue`, `_ConvertValueMessage`, and `_ConvertListOrTupleValueMessage` in `python/google/protobuf/json_format.py` build `ParseError` strings by directly formatting the untransformed JSON `value` the client sent:
- `'Map field {0} must be in a dict which is {1} at {2}'.format(field.name, value, path)` [1](#0-0) 
- `'Value {0} has unexpected type {1} at {2}'.format(value, type(value), path)` [2](#0-1) 
- `'ListValue must be in [] which is {0} at {1}'.format(value, path)` and `'Struct must be in a dict which is {0} at {1}'.format(value, path)` [3](#0-2) 
- `'repeated field {0} must be in [] which is {1} at {2}'.format(name, value, path)` [4](#0-3) 
- Enum conversion errors include the raw string value: `'Invalid enum value {0} for enum type {1}'.format(value, field.enum_type.full_name)` [5](#0-4) 

None of these paths consult `field.GetOptions().debug_redact` before embedding `value` (the attacker-supplied content, which can be a password/credential field sent with the wrong JSON type or an invalid enum string) into the exception text. Consuming applications commonly log unhandled/handled exceptions (`logging.exception(e)`, `str(e)`) as part of standard error handling — this is exactly the "log an error message that inadvertently contains sensitive content" pattern in CVE-2023-5182, just triggered through a Protobuf JSON-parsing API instead of subiquity's installer logging.

By contrast, C++/Java TextFormat parsing errors only ever include field *names* and structural context, never the raw value (e.g., `"Non-repeated field \"c\" is specified multiple times."`, `"Invalid field value: ..."` from `_SkipFieldValue`), and the `PrintAny` warning logs only the `type_url`, never message content [6](#0-5) . The ProtoJSON path is the outlier that surfaces raw payload content.

### Impact Explanation
If an application's message schema marks a field `debug_redact = true` (the documented mechanism for marking "sensitive credentials", per `FieldOptions.debug_redact`'s own doc comment: "e.g. when the field contains sensitive credentials" [7](#0-6) ), sending a malformed value for that field (wrong JSON type, or a bad enum string, or a non-list where a list is expected) causes the raw value to be embedded verbatim in the `ParseError` message. Any downstream logging of that exception (a very common pattern for RPC/gateway error handling) discloses the sensitive value in cleartext logs, defeating the purpose of `debug_redact`. This mirrors the CVE's confidentiality impact (`C:H`) with no integrity/availability impact, and requires no special privilege beyond calling the public `json_format.Parse`/`MessageToJson`-adjacent parse API with attacker-controlled JSON.

### Likelihood Explanation
High likelihood of reachability: any application exposing a JSON ingestion endpoint that calls `google.protobuf.json_format.Parse()` on client-supplied JSON, with fields marked `debug_redact` (or fields that are simply otherwise sensitive), will trigger this whenever the client sends a structurally invalid but otherwise well-formed JSON payload for that field (e.g., sending a string where an int is expected, or a string that isn't a valid enum value) — this requires no privileged access, only normal client interaction with the exposed parse API.

### Recommendation
Modify `json_format.py`'s error-construction paths (`_ConvertFieldValuePair`, `_ConvertScalarFieldValue`, `_ConvertMapFieldValue`, `_ConvertValueMessage`, `_ConvertListOrTupleValueMessage`, enum handling in `_ConvertScalarFieldValue`) to consult `field.GetOptions().debug_redact` before including the raw `value` in `ParseError` text, replacing it with a redaction placeholder (mirroring `kFieldValueReplacement = "[REDACTED]"` used by `TextFormat::Printer::TryRedactFieldValue`) when the field is annotated sensitive. At minimum, avoid embedding raw scalar/collection payloads in exception messages for any field, and document that `ParseError` text may contain field content so integrators know not to log it unredacted.

### Proof of Concept
Given a proto schema with a `debug_redact`-annotated `string password` field of enum type `PasswordEnum` (or simply an int32 field), a client sends:
```json
{"password": "not-a-valid-enum-value"}
```
Calling `json_format.Parse(json_str, MyMessage())` raises:
```
ParseError: Invalid enum value not-a-valid-enum-value for enum type mypkg.PasswordEnum at MyMessage.password.
```
The exception's `str(e)` — which a typical `except ParseError as e: logging.error(e)` handler will log — contains the raw client-submitted value verbatim, regardless of the field's `debug_redact` annotation, unlike `DebugString()`/`TextFormat` output for the same message which would print `[REDACTED]`. This was traced through `_ConvertScalarFieldValue` at [5](#0-4)  and the wrapping re-raise at [8](#0-7) .
