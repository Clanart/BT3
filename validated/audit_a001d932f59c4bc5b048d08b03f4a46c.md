I found a concrete analog: `reassembleResolvedFile` splices per-hunk model resolutions back into a file purely by **positional order**, with no validation that the number of hunks the model returned matches the number of conflict blocks actually present in the on-disk file. An attacker who controls a merged/fetched branch (i.e. controls the conflicting content) can shape the conflict markers so that Copilot's per-hunk resolution array and the on-disk block count diverge, causing the wrong resolved text to be spliced into the wrong location — silently corrupting what the user commits.

### Title
Order-based (not identity-based) hunk splicing in Copilot conflict reassembly allows attacker-controlled conflict markers to silently corrupt the committed file - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
`reassembleResolvedFile` walks the raw on-disk file and, for every conflict block it recognizes (`<<<<<<<` … `=======` … `>>>>>>>`), pops the next entry off `hunkResolutions[hunkIndex]` and splices it in, incrementing `hunkIndex` regardless of whether that resolution was actually meant for that block. [1](#0-0) 
The array of hunk resolutions comes from the model's JSON response, validated only for shape (`resolvedContent` is a string, no leftover markers) — never for count or identity against the source hunks. [2](#0-1) 

### Finding Description
The invariant the reassembly logic silently assumes is: *"the Nth conflict block found by the second-pass scanner in `reassembleResolvedFile` corresponds exactly to the Nth hunk resolution returned by the model, which in turn corresponds to the Nth hunk extracted by `extractConflictHunks` when building the prompt."* Nothing in the code enforces this three-way correspondence.

- `extractConflictHunks` (used to build the prompt sent to Copilot) and the marker-matching logic inside `reassembleResolvedFile` are two independently written scanners over the same regexes (`oursMarker`/`reassemblyOursMarker`, `separatorMarker`/`reassemblySeparatorMarker`, `theirsMarker`/`reassemblyTheirsMarker`). [3](#0-2) [4](#0-3) 
- `extractConflictHunks` silently *drops* any hunk whose closing `>>>>>>>` marker is never found (`if (hunkEnd === -1) { continue }`), while `reassembleResolvedFile` treats the same malformed block as "not a conflict" and copies it through verbatim. [5](#0-4) [6](#0-5) 
  These two behaviors are similar but not provably identical for all inputs (e.g. diff3 `|||||||` handling, nested/stray marker sequences, marker lines with trailing whitespace variants). Because an attacker fully controls the file content that produces these markers (any branch/PR the user merges, rebases, or cherry-picks), they can construct a conflicted file where the two scanners disagree on hunk count or boundaries.
- Reassembly matches resolutions to blocks **by array position only** — there is no hunk identifier, checksum, or content anchor tying `hunkResolutions[i]` back to a specific marker block in the raw file. [7](#0-6) 
- If the model returns fewer hunks than blocks found during reassembly (e.g. because the model — following the untrusted, attacker-authored surrounding code/comments — decided to merge two prompted hunks into one answer, or a scanner-count mismatch shifts the index), later legitimate blocks are silently spliced with the *wrong* resolved content, or dropped entirely with no resolution appended (`if (hunkIndex < hunkResolutions.length)` — if false, the block is simply deleted from the output with nothing to replace it). [8](#0-7) 
- The final result of this reassembly is written straight to disk and `git add`-ed without further diffing against the original conflict content or user review of the exact byte-for-byte change: [9](#0-8) 

No existing guard stops this path: `parseCopilotConflictResolution` only checks that `resolvedContent` is a string and doesn't still contain marker text; it never checks that `hunks.length` for a file matches the number of hunks originally extracted for that file. [10](#0-9) 

### Impact Explanation
This lets an attacker who controls the content of a merged/rebased/cherry-picked branch (a fully unprivileged, remote-content-only primitive — no local access, no credentials, no social engineering beyond "the user merges this branch or opens this PR through normal Desktop workflows") cause Desktop's AI-assisted conflict resolution feature to silently commit content the user did not intend — either dropping a legitimate resolved hunk (data loss committed to the user's history) or splicing an unrelated hunk's resolution into the wrong location in the file, without any diff/marker discrepancy visible to the user beyond what the dialog already shows as "resolved." This matches the "silent corruption of what the user commits or pushes" impact category exactly, structurally analogous to the ZCToken report's core defect: two code paths that are supposed to describe the same underlying unit/structure (decimals vs. genesis-value decimals; extracted hunks vs. reassembled hunks) diverge, and the mismatch is invisible until the wrongly-scaled/misplaced value is used downstream.

### Likelihood Explanation
Likelihood is moderate: it requires the model's response to actually diverge in hunk count/order from the raw file (whether via a crafted adversarial marker sequence or a model quirk when reasoning about attacker-supplied comments/context), and it only manifests within the Copilot conflict-resolution flow, which is opt-in and requires the user to click "Continue Merge." However, this is a purely content-driven trigger — no local access or privileged state is needed — and conflict markers are naturally attacker-influenced content in any merge scenario, making the crafted-input precondition realistic (e.g. a malicious PR branch or a diff3 corner case).

### Recommendation
Do not rely on positional matching alone. Either (a) have the model echo back a stable per-hunk identifier (e.g. an index or content hash computed from `extractConflictHunks`) and validate at reassembly time that the returned hunk list length and identifiers exactly match the hunks re-extracted from the *current* on-disk `rawContent`, aborting/falling back to manual resolution on any mismatch; or (b) unify the extraction and reassembly marker-scanning logic into a single shared parser so that both stages provably agree on hunk boundaries and malformed-marker handling for every input, and add an explicit check that `hunkIndex === hunkResolutions.length` at the end of `reassembleResolvedFile`, treating any surplus/deficit as a hard validation error rather than silently truncating.

### Proof of Concept
1. Craft a repository branch whose merge produces a conflicted file containing a conflict block with subtly malformed/adjacent markers designed to be parsed as N blocks by `extractConflictHunks` but N±1 blocks by the marker-matching loop in `reassembleResolvedFile` (e.g. abusing the differing malformed-marker handling shown above, or nested marker-like lines inside one side's content).
2. The user opens this branch in Desktop and triggers Copilot conflict resolution; the model is prompted with N hunks (per `formatConflictContextForPrompt`) and returns N resolutions in order. [11](#0-10) 
3. `reassembleResolvedFile` walks the same raw content but finds N±1 well-formed blocks by its own scanner, so `hunkResolutions[hunkIndex]` is misapplied to the wrong block (or exhausted early, silently deleting the last conflict block's content). [7](#0-6) 
4. The user clicks "Continue Merge," `_applyCopilotConflictResolutions` writes this corrupted content straight to disk and stages it, without further review. [9](#0-8) 

Note: I was not able to fully verify the two marker-scanning implementations against every edge case (nested/nested-adjacent markers, nested diff3 sequences, nested nested-comment marker lines) purely from index search; a background Devin session with full repository/test access would be needed to construct and confirm a concrete divergent input for the PoC.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
