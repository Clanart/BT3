### Title
`pair.Enabled` governance pause is bypassed in IBC timeout/error-ack ERC20 reconversion path - ([File: x/erc20/keeper/ibc_callbacks.go])

### Summary
The `ToggleConversion` governance action pauses conversion for a specific `TokenPair` by setting `pair.Enabled = false` [1](#0-0) . This flag is correctly enforced on the primary conversion entry points (`MintingEnabled`, used by `ConvertCoin`/`ConvertERC20`, and in `OnRecvPacket`) but is never checked in `ConvertCoinToERC20FromPacket`, which is reached from `OnTimeoutPacket` and `OnAcknowledgementPacket` (error-ack) and which calls the same underlying `ConvertCoinNativeERC20` state-mutating function directly.

### Finding Description
`MintingEnabled` is the gatekeeper used by the two user-facing message handlers (`ConvertCoin`, `ConvertERC20`) and explicitly checks `!pair.Enabled` before allowing conversion: [2](#0-1) 

`OnRecvPacket` also honors the same pause flag for inbound IBC coins destined to become ERC20: [3](#0-2) 

However, `ConvertCoinToERC20FromPacket` — invoked when an outbound ICS20 transfer of a native-ERC20-backed coin times out or receives an error acknowledgement — fetches the `TokenPair` directly via `k.GetTokenPair` and only checks `params.EnableErc20` (the *global* switch) and `IsDenomRegistered`, never the per-pair `pair.Enabled` flag, before calling `k.ConvertCoinNativeERC20`: [4](#0-3) 

`ConvertCoinNativeERC20` itself performs no `pair.Enabled` check either — it trusts callers to have already gated on it: [5](#0-4) 

This is structurally the same bug class as the reported EigenLayer analog: a privileged/pause-guarded state-mutating action (`_deregisterOperator` / `ConvertCoinNativeERC20`) is protected by a check on one entry point (`deregisterOperator`'s modifier / `MintingEnabled`'s `pair.Enabled` check) but is reachable through a second, unrelated entry point (`registerOperatorWithChurn` / IBC timeout-callback path) that calls the internal function directly and omits the pause check.

### Impact Explanation
`ToggleConversion` (governance) is the chain's only mechanism to halt conversion for a specific ERC20 token pair — e.g., in response to a discovered vulnerability, malicious/broken behavior, or fee-on-transfer/inflationary bug in the underlying ERC20 contract, or to freeze a compromised token pair. An unprivileged user can trigger the bypass without any special privilege: initiate (or have in-flight) an ICS20 transfer of the disabled pair's native-ERC20-backed coin, then let the packet time out or get an error-ack (achievable simply by choosing a channel/timeout that will not complete, or by relayer-independent timeout expiry). When that happens, `OnTimeoutPacket`/`OnAcknowledgementPacket` calls `ConvertCoinToERC20FromPacket`, which unescrows the erc20-backed coin from the module account and calls the ERC20 contract's `transfer` to move real ERC20 tokens to the user — completely ignoring the fact that governance disabled this pair. This directly corrupts the accounting/security guarantee that a disabled pair cannot mint/move ERC20 value, and can be used to convert coins to ERC20 out of an intentionally frozen/paused pair, defeating the governance-level fund-freeze/incident-response control and re-exposing user funds to whatever vulnerability caused the pause. This matches the "Critical unauthorized minting/duplication/irreversible accounting corruption" and "Critical permanent freezing/theft/unauthorized extraction of ... token-pair-backed balances" impact classes, since the disable flag is the chain's designated safety control for token-pair-backed balances and this path silently defeats it.

### Likelihood Explanation
Likelihood is moderate-to-high: any unprivileged user holding the disabled pair's Cosmos-coin representation can send an ICS20 transfer of it and force (or wait for) a timeout/error ack — both are ordinary, permissionless IBC transaction flows requiring no relayer cooperation (a timeout naturally occurs if the counterparty channel/receiver rejects or the packet simply is not relayed within the timeout window, which the sender fully controls when constructing the `MsgTransfer`). No validator or governance collusion is needed.

### Recommendation
Add the same `pair.Enabled` check that gates `MintingEnabled`/`OnRecvPacket` into `ConvertCoinToERC20FromPacket` before calling `ConvertCoinNativeERC20`, e.g.:
```go
case pair.IsNativeERC20():
    if !pair.Enabled {
        return nil // conversion paused for this pair; leave user with the bank coin
    }
    ...
```
Alternatively, move the `pair.Enabled` check into `ConvertCoinNativeERC20` itself so that the invariant is enforced at the single shared choke point rather than at every caller, eliminating the possibility of a bypass through any future or existing alternate entry point.

### Proof of Concept
1. Governance registers a native ERC20 token pair `P` (`OWNER_MODULE`, `IsNativeERC20() == true`) and it is `Enabled = true`.
2. A user holds native coin `P.Denom` (obtained via `ConvertERC20`) and constructs an ICS20 `MsgTransfer` sending `P.Denom` to a counterparty chain, with a short/guaranteed-to-expire timeout (or targeting a channel/receiver that returns an error ack).
3. Governance calls `MsgToggleConversion` on `P`, setting `pair.Enabled = false`, intending to fully halt conversions for `P` (e.g., due to a discovered bug in `P`'s ERC20 contract).
4. The user's transfer times out (or errors), invoking `OnTimeoutPacket`/`OnAcknowledgementPacket` → `ConvertCoinToERC20FromPacket` (x/erc20/keeper/ibc_callbacks.go:186-257).
5. `ConvertCoinToERC20FromPacket` checks only `params.EnableErc20` and `IsDenomRegistered`, not `pair.Enabled`, and proceeds to call `ConvertCoinNativeERC20`, which burns the escrowed `P.Denom` coin and calls the ERC20 contract's `transfer` to send the corresponding ERC20 tokens back to the user.
6. Despite `pair.Enabled == false`, the user has successfully converted native coin into ERC20 tokens, bypassing the governance pause — identical in structure to the reported `registerOperatorWithChurn` bypassing the `PAUSED_DEREGISTER_OPERATOR` pause via a direct call to `_deregisterOperator`.

// ToggleConversion toggles conversion for a given token pair
func (k Keeper) toggleConversion(
	ctx sdk.Context,
	token string,
) (types.TokenPair, error) {
	id := k.GetTokenPairID(ctx, token)
	if len(id) == 0 {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered by id", token,
		)
	}

	pair, found := k.GetTokenPair(ctx, id)
	if !found {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered", token,
		)
	}

	pair.Enabled = !pair.Enabled
	k.SetTokenPair(ctx, pair)
	return pair, nil

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}
