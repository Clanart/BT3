### Title
Unvalidated `sender`/`recipient` participant indexes cause out-of-map indexing panic in `BlameMachine::blame_internal` - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The CVE class is an out-of-bounds access on attacker-controlled data that leads to a crash (MediaInfo `Synched_Test` OOB read). The Serai analog is in `crypto/dkg/pedpop`: `BlameMachine::blame_internal` (and the wrappers `BlameMachine::blame` and `AdditionalBlameMachine::blame`) indexes `self.commitments` with a caller/network-supplied `Participant` via `&self.commitments[&sender]`. `Participant` only encodes "non-zero u16" — any value `> n` is accepted by `Participant::new` — so a `sender` outside the 1..=n participant set hits a `HashMap` index (`[]`) which panics instead of returning an error.

### Finding Description
`Participant::new` accepts any non-zero `u16`; validity relative to a specific set (`i <= n`) is only enforced inside `ThresholdParams::new`/`validate_map`. In `BlameMachine::blame_internal`, the accused `sender` is used as an unchecked `HashMap` key:

```rust
// crypto/dkg/pedpop/src/lib.rs:596-600
if !bool::from(
  multiexp_vartime(&share_verification_statements::<C>(
    recipient,
    &self.commitments[&sender],   // panics if sender is not in the map
    ...
```

`self.commitments` is populated for exactly the participant indexes `1..=n` (in `calculate_share` via `verify_r1`, or in `AdditionalBlameMachine::new` which inserts keys `Participant::new(i)` for `i in 1..=n`). There is no `validate_map`-style check that `sender`/`recipient` are members of the set before indexing. The same unchecked pattern exists in `calculate_share` at line 490 (`&self.commitments[&l]`), but there `l` is constrained to validated map keys; in `blame_internal` the `sender`/`recipient` arguments are entirely attacker-influenced protocol inputs (e.g., parsed from an accusation message as arbitrary non-zero `u16` values).

Additionally, `msg` and `proof` passed to `decrypt_with_proof` are deserialized via `EncryptedMessage::read`/`EncryptionKeyProof::read`, which safely reject malformed bytes — but the panic occurs purely from the attacker-chosen `Participant` argument, not from byte length.

### Impact Explanation
Any party able to trigger a blame evaluation (the intended public flow for reporting a faulty DKG share) can supply `sender` (or a `sender`/`recipient` pair) with a participant index `> n` or otherwise absent from `commitments`. The `HashMap` `Index` impl panics on a missing key, aborting the calling thread. In a node/coordinator context where blame proofs from peers are evaluated, this is a remotely triggerable crash — the same availability impact (CVSS A:H / Medium profile) as the reference CVE, which was rated Medium for an OOB read crash from a crafted file. While Rust turns the OOB into a panic rather than a memory disclosure, the denial-of-service impact is identical, and the panic handler in Serai binaries (e.g., the Ethereum relayer's `panic → exit(1)` hook) makes thread panics process-fatal.

### Likelihood Explanation
Triggering requires only that a blame/accusation flow is reachable with attacker-supplied participant indexes — a normal protocol surface (accusations are inherently adversarial inputs). No cryptographic break, timing, or collusion is needed; the input just needs `Participant::new(x)` to succeed while `x` is not a member of the DKG set. Cost is trivial; probability of reaching the path depends on integrators wiring peer-supplied accuser/faulty fields into `blame`, which is the documented purpose of the API.

### Recommendation
Validate membership before indexing in `blame_internal` and in `AdditionalBlameMachine::blame`:
- Reject `sender`/`recipient` not present in `self.commitments` (e.g., `let Some(sender_commitments) = self.commitments.get(&sender) else { return sender }` or a dedicated error), rather than using `[]` indexing.
- Consider returning a `Result`/`PedPoPError` variant for out-of-range participants so callers can distinguish malformed accusations from valid blame.

### Proof of Concept
Conceptual (Rust, `no_run` sketch):

```rust
// After a legitimate DKG produces BlameMachine for n participants, or via
// AdditionalBlameMachine::new(context, n, commitment_msgs):
let attacker = Participant::new(n + 1).unwrap(); // valid non-zero u16, not in set
let msg = /* any EncryptedMessage<C, SecretShare<C::F>> that decrypts with a
             structurally valid share so execution reaches line 599 */;
machine.blame(sender: attacker, recipient: honest_i, msg, proof);
// -> thread panics at `self.commitments[&sender]` (HashMap index of absent key)
```

Even simpler, `blame_internal` also dereferences nothing else before the panic, so any path that reaches line 596-599 with an out-of-set `sender` crashes the evaluator. The root cause is the unchecked `&self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599`, reachable through the public `BlameMachine::blame` (`lib.rs:623`) and `AdditionalBlameMachine::blame` (`lib.rs:674`) APIs.
