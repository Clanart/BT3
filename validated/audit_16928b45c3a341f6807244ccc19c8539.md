Audit Report

## Title
Partitioned stake rewards are permanently burned if a staker withdraws their stake account between reward calculation and reward distribution - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

## Summary
Stake rewards are computed once at the epoch boundary into an immutable `PartitionedStakeRewards` list, but crediting happens later across several subsequent blocks via `distribute_partitioned_epoch_rewards`. If the staker performs an ordinary, unprivileged `Withdraw` that empties the stake account in that gap, `StakesCache::check_and_store` removes the stake delegation entirely (zero-lamport accounts are purged from the cache), causing `build_updated_stake_reward` to return `AccountNotFound` and the already-computed reward to be unconditionally burned instead of paid.

## Finding Description
Reward calculation produces `PartitionedStakeReward` entries with a positive `stake_reward` for stake pubkeys active during the rewarded epoch [1](#0-0) . Distribution is spread over multiple subsequent blocks, not atomic with calculation [2](#0-1) . At the actual distribution step, each pubkey is looked up in the *current* `StakesCache`, not a calculation-time snapshot [3](#0-2) , and a missing entry unconditionally burns the reward [4](#0-3) .

Critically, `StakesCache::check_and_store` explicitly removes a stake pubkey's delegation from the cache the moment its account balance reaches zero lamports: [5](#0-4) . This confirms the exploit mechanism: an ordinary `Withdraw` instruction that empties a stake account causes the pubkey to vanish from `StakesCache` before its turn in the distribution partition arrives.

The code's own comment in `store_stake_accounts_in_partition` acknowledges reliance on "stake-program restrictions" preventing this, but no such restriction (e.g., an `EpochRewardStatus`/pending-distribution check) exists anywhere in the stake program — confirmed by the absence of any `EpochRewardStatus` reference under `programs/stake*` [6](#0-5) .

## Impact Explanation
This is a fund-loss / permanent-freezing-of-yield issue in the `runtime`/`accounts` scope: a reward already computed and reserved (part of `all_stake_rewards`, backed by lamports in the `EpochRewards` sysvar/bank capitalization) is silently and permanently added to `stake_reward_lamports_burned` rather than delivered, with only an `error!` log and no recovery path [7](#0-6) .

## Likelihood Explanation
An ordinary unprivileged staker using only standard, permissionless `Deactivate`/`Withdraw` stake instructions can time full account closure to land within the distribution window (bounded by `get_reward_distribution_num_blocks`, up to 10% of `slots_per_epoch`) after that account's reward was computed but before its partition is processed. No malicious validator, RPC, or privileged access is required, only precise but achievable timing.

## Recommendation
Either have the stake program refuse full account closure while a distribution is outstanding for that pubkey, or have `build_updated_stake_reward` redirect the reward lamports (e.g., to the withdrawal destination or a reconstituted minimal account) instead of unconditionally burning them on `AccountNotFound`, analogous to the vote program's `withdraw` blocking closure while `pending_delegator_rewards > 0`.

## Proof of Concept
1. Delegate and let a stake account earn credits through epoch `N`.
2. At the epoch `N+1` calculation block, a `PartitionedStakeReward` with `stake_reward > 0` is computed for this pubkey.
3. Before this pubkey's partition is reached in the distribution phase, submit `Deactivate` (if not already cooling down) then `Withdraw` for the full balance, removing the pubkey from `StakesCache`.
4. When `store_stake_accounts_in_partition` reaches this pubkey, `build_updated_stake_reward` returns `Err(DistributionError::AccountNotFound)`, and the reward is added to `stake_reward_lamports_burned` instead of being paid.

            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.

                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,

                "epoch-rewards-status-update",
