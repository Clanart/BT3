## Analysis

The report's core invariant: **a boolean "success" from a raw low-level token call must not be trusted as proof that value actually moved** — non-standard/malicious ERC20s can return `false` (or no data at all is fine, but returning `false` without reverting is the failure mode) while the call itself doesn't revert. `SafeERC20` exists specifically to check both call-success and the encoded return value.

I found a direct, exploitable local analog in the Tron variant of the intent-settlement escrow release path.

### Title
Escrow withdraw/sweep accepts failed ERC20 transfers as successful due to unchecked return value - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` handler in `onAccept()` release escrowed funds using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the low-level call did not revert, never inspecting the returned boolean. Every other transfer path in the same codebase (main EVM `IntentGatewayV2.sol`, `IntentsBase.sol`, `ExtrinsicIntents.sol`, `WrappedHyperFungibleToken*.sol`) consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which decodes and enforces a `true` return. The Tron contract is the outlier.

### Finding Description
In `withdraw()`: [1](#0-0) 

and in the `SweepDust` branch of `onAccept()`: [2](#0-1) 

Both use `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check `success` (whether the call reverted), not the ABI-decoded boolean return value. If a TRC20/ERC20 token used as an order `input` returns `false` on a failed `transfer` instead of reverting (a common non-compliant behavior explicitly called out by the SafeERC20 pattern), the contract treats the transfer as successful. Immediately after, `_orders[body.commitment][token] -= amount;` decrements the internal escrow accounting even though the token balance never left the contract. The order is also marked filled/refunded (`_filled[body.commitment] = beneficiary`) and the corresponding `EscrowReleased`/`EscrowRefunded` event fires.

This exactly mirrors the report's bug class: `token.transfer`/raw calls used where `safeTransfer`/`safeTransferFrom` should enforce the actual success of value movement — the same root cause flagged for `TokenStaking.sol` and `BondedECDSAKeep.sol` in the external report.

Compare with the main EVM contract's equivalent logic in `IntentsBase._withdraw`, which correctly uses `safeTransfer`: [3](#0-2) 

### Impact Explanation
An order creator picks the escrow `input` token when creating an order (a normal, unprivileged action). If that token is non-compliant (returns `false` instead of reverting on transfer failure — e.g., due to a paused state, blacklist, or insufficient contract balance at redemption time), the escrow bookkeeping (`_orders[commitment][token]`) desynchronizes from the actual token balance held by the `IntentGatewayV2` contract: the contract believes funds were paid out and reduces/deletes accounting state, while the tokens remain locked inside the contract. This causes silent fund loss/lock for the intended beneficiary (solver or refund recipient) without any revert, and corrupts the escrow ledger that other legitimate orders rely on for correct accounting — a direct violation of the "funds must move exactly once and only to the rightful beneficiary and amount" pivot for bridge custody/intent settlement.

### Likelihood Explanation
Reachable without any privileged, relayer, or prover assumption: the only precondition is that the escrowed input token is a non-standard ERC20/TRC20 that can return `false` on failure without reverting — a real and known class of tokens (this is precisely why SafeERC20 exists and why the rest of the codebase uses it consistently). The withdraw path itself is invoked through the legitimate cross-chain `RedeemEscrow`/`RefundEscrow` flow (`onAccept`/`onGetResponse`, both gated by `onlyHost` and `authenticate`), so no malicious relayer or forged proof is needed — it triggers on ordinary settlement of an order that used such a token.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, consistent with every other transfer site in the codebase (`IntentsBase.sol`, main-EVM `IntentGatewayV2.sol`, `WrappedHyperFungibleToken*.sol`). This ensures both call-success and the ABI-decoded return value are enforced before mutating `_orders` accounting or marking the order as filled/refunded.

### Proof of Concept
1. An order creator posts an order on the Tron chain whose escrowed input token is a non-standard TRC20 contract `EvilToken` that returns `false` (rather than reverting) from `transfer()` when, e.g., the recipient is blacklisted or the contract's internal balance check fails, while still logging an event or doing nothing.
2. Order is filled normally on the destination chain; a legitimate `RedeemEscrow`/`RefundEscrow` POST request or GET-response-based cancellation eventually calls `withdraw()` on the Tron `IntentGatewayV2`.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, false-encoded-data)` — `success` is `true` since the callee did not revert.
4. The `!success` check passes, so `_orders[body.commitment][token] -= amount` executes and `_filled[body.commitment]` is set — the order is marked settled and the event emitted — despite `beneficiary` never receiving the tokens.
5. Tokens remain stuck in `IntentGatewayV2` under an escrow slot that is now decremented/deleted, permanently unrecoverable by the beneficiary through the normal withdraw path, while the internal accounting no longer reflects the actual on-chain token balance held by the contract.
