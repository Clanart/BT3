### Title
Stop-hook / commit-review finding dedup keyed on `(filePath, category)` instead of exact vulnerable code lets a new dangerous change be silently swallowed - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
`handle_stop_hook` (and `handle_commit_review_posttooluse`/push-sweep) dedup newly-found LLM vulnerabilities against `previous_findings` using `_dedup_against_state`/`_finding_keys`, which reduces each finding to the tuple `(filePath, category)` and drops any new finding whose key was already recorded, regardless of whether the actual vulnerable code differs. Because an attacker fully controls file paths and can cause the classifier to assign the same `category` string to two unrelated dangerous patterns in the same file (e.g., two different command-injection sites both categorized as `"Command Injection"`), a genuinely new dangerous change in the same file can be suppressed as a "duplicate" once the same `(path, category)` pair has previously fired — no warning, no `exit(2)`, no rewake.

### Finding Description
`_finding_keys` at `plugins/security-guidance/hooks/llm.py:680-682` computes `{(f.get("filePath",""), f.get("category",""))}` for a findings list, deliberately excluding `vulnerableCode`. `_dedup_against_state` (`llm.py:685-707`) uses this coarse key to filter the *race-delta* set. Separately, and more importantly, `handle_stop_hook`'s `_record_fire` closure (`security_reminder_hook.py:1896-1911`) persists `previous_findings` keyed the same way — `seen = {(f.get("filePath",""), f.get("category",""))}` — explicitly to prevent "the same finding accumulate[ing] as new each fire" because `vulnerableCode` diff-context lines drift. The comment at lines 1901-1903 acknowledges this is an intentional simplification for the *same* finding across LLM re-runs, but it does not distinguish a legitimately fixed-then-reintroduced or a wholly *different* vulnerability in the same file that happens to be assigned the same category by the classifier.

Once a `(filePath, category)` pair is written into `state["previous_findings"]` by any prior Stop/commit/push review fire, subsequent fires (`_dedup_against_state` at `security_reminder_hook.py:1874-1880`, and the equivalent path in `handle_push_sweep_posttooluse` at `1625-1627`) will drop any new LLM finding sharing that key from the `vulns` list, sending it into the `n_deduped and not vulns` branch (`_skip(35, ...)`), which exits 0 with no stderr guidance and no `exit(2)` — i.e., **no warning, no rewake** for a real new dangerous change. The only exception carved out is content that was in the `prompted` set passed to the LLM this turn (a legitimate "fix incomplete" re-flag); anything with a matching key that the LLM was never prompted about (e.g., because it's a *different* line/vulnerability in the same file under the same category) is treated as noise from a "concurrent hook race" and silently dropped.

Attacker-controlled surface: normal edits and `git commit`/`git push` diff content are exactly what feeds `analyze_code_security`'s `vulns` output, and file paths/category labels are attacker-influenced (the attacker chooses what file to edit and what kind of vulnerability pattern to introduce, and the LLM's category taxonomy is coarse, e.g. `"Command Injection"`, `"Path Traversal"`, `"Hardcoded Secret"`). This lets an attacker (or a compromised/malicious task the agent executes) first introduce a low-severity or decoy issue in `foo.py` that gets flagged and recorded as `(foo.py, "Command Injection")` in `previous_findings`, then later (same session, within `PREVIOUS_FINDINGS_TTL_SEC` = 3600s default) introduce an actually dangerous, unrelated command-injection change in the same file — which shares the same `(filePath, category)` key and is dropped by `_dedup_against_state` across Stop, commit-review, and push-sweep, defeating the "must stay reviewable across retries/amends/pushes" invariant.

### Impact Explanation
This breaks the plugin's core guarantee that dangerous edits/commands remain reviewable and blockable: a real, new vulnerability can be introduced and pushed without the Stop-hook `exit(2)` block, the commit-review `asyncRewake`, or the push-sweep rewake ever firing, because the dedup key collision makes the review pipeline believe the finding was already surfaced. Since these hooks are the mechanism gating whether Claude is forced to stop and address a security finding (i.e., the closest thing to an "approval" control in this plugin), silently dropping a genuinely new dangerous finding is a bypass of that control, potentially allowing an unreviewed dangerous command/pattern to reach a commit/push undetected. However, this is a *detection/warning suppression* bypass within the security-guidance plugin's own advisory LLM-review layer — it does not directly grant unauthorized command execution by itself; it removes a defense-in-depth signal that would otherwise prompt Claude/the user to reconsider or block the change.

### Likelihood Explanation
Feasible with only normal edit/commit access (which the threat model grants). It requires: (1) the LLM security reviewer to assign the same `category` string to two distinct findings in the same file — plausible given the coarse, LLM-generated category taxonomy — and (2) both findings to occur within the same session and within the `PREVIOUS_FINDINGS_TTL_SEC` window (1 hour by default). This is a real, but not trivially deterministic, condition: it depends on the categorization behavior of the Haiku-based classifier (`analyze_code_security` in `llm.py`), which is not fully attacker-controlled but is influenced by the code patterns the attacker introduces (they can craft both changes to look like the "same category" of issue).

### Recommendation
Change the dedup key used for persisted `previous_findings` and `_finding_keys` to include a stable content fingerprint (e.g., a hash of the normalized vulnerable code snippet or the diff hunk) in addition to `(filePath, category)`, rather than relying on category alone. At minimum, only suppress a new finding when it is a near-exact match (e.g., same line range / near-identical `vulnerableCode` after normalizing whitespace) to the previously recorded one, not merely the same `(filePath, category)` pair — this preserves the "fix didn't work" re-flag behavior while preventing unrelated new vulnerabilities in the same file/category from being swallowed.

### Proof of Concept
Integration test plan (pytest style, mirroring existing test patterns for `handle_stop_hook`):
1. Monkeypatch `analyze_code_security` (or the underlying LLM call) to return, on the **first** Stop-hook fire, a single vuln: `{"filePath": "app.py", "category": "Command Injection", "vulnerableCode": "os.system(user_a)"}`.
2. Run `handle_stop_hook` once; assert it exits with code 2 and the finding is written to `state["previous_findings"]` as `{"filePath": "app.py", "category": "Command Injection", ...}`.
3. Simulate a second, unrelated dangerous edit to `app.py` (different line, different injected command) and monkeypatch `analyze_code_security` to return a **new** vuln: `{"filePath": "app.py", "category": "Command Injection", "vulnerableCode": "subprocess.call(user_b, shell=True)"}` — a genuinely different vulnerability sharing the same `(filePath, category)` key.
4. Run `handle_stop_hook` again (simulating a subsequent turn/fire, `previous_findings` not yet expired, and this finding not in `prompted`/previous_findings snapshot).
5. Assert that `_dedup_against_state` drops this second, distinct finding (`vulns` becomes empty), the hook takes the `_skip(35, ...)` path, exits 0 with no stderr output, and no `exit(2)`/rewake occurs — demonstrating that a new dangerous command-injection change in the same file is never surfaced to the user/model because it collides on `(filePath, category)` with an earlier, unrelated finding.
