### Title
Stale `ContractToAsset` reverse-mapping lets a decommissioned/old EVM contract retain permanent minting authority after `register_token` re-registration - (File: modules/pallets/hyper-fungible-token/src/lib.rs)

### Summary
`pallet_hyper_fungible_token::register_token` can be called more than once for the same `asset_id`. When it is used to re-point a chain's token contract (e.g., after a contract migration/redeploy) instead of `update_token`, it overwrites `TokenContracts` and inserts a new `ContractToAsset` entry for the new contract, but never removes the old `ContractToAsset` entry for the previously configured contract address on that chain.

### Finding Description
`register_token` inserts blindly, with no check for a prior contract already registered on the same `(chain, asset_id)` pair: [5](#0-4) 

Compare this to `update_token`, which explicitly looks up and deletes the previous `ContractToAsset` entry before inserting the new one: [6](#0-5) 

Because `register_token` skips this cleanup step, if it is invoked a second time for an asset that is already registered — pointing the same chain at a new contract address — the storage state becomes:
- `TokenContracts(chain, asset_id) = new_contract` (correctly updated, single value)
- `ContractToAsset(chain, new_contract) = asset_id` (correctly inserted)
- `ContractToAsset(chain, old_contract) = asset_id` (never removed — now stale, but still authoritative)

`on_accept` and `on_timeout` in `module.rs` use `ContractToAsset` as the **sole** authentication check for whether an incoming ISMP message legitimately represents asset `asset_id` — there is no cross-check against `TokenContracts` to confirm the message came from the currently-configured contract: [7](#0-6) 

This is directly analogous to the HydraDX oracle bug: one storage location (`TokenContracts`, like the Omnipool's own state) is fully updated/overwritten during a "re-add"/reconfiguration operation, while a second, semantically-dependent storage location (`ContractToAsset`, like the EMA Oracle) retains stale data from before the reconfiguration and continues to be trusted for authorization decisions.

### Impact Explanation
Any EVM contract address that was ever registered as a token contract for an asset — even after being superseded by a newer contract via `register_token` — permanently retains the ability to mint/release that asset's balance on the substrate side, as long as it can still dispatch a `Send` ISMP `PostRequest` with `from == old_contract`. This breaks the "exactly-once, rightful beneficiary" custody invariant: two independent EVM addresses now have module-identity authority to mint the same wrapped/native asset, so total issuance is no longer bound to a single canonical bridge contract's escrow. If the old contract is upgradeable, was compromised, was left with unexpected authority/escrow logic, or its EVM address is later redeployed/taken over, this becomes a direct path to unauthorized minting (unbacked token creation) of the affected asset — matching the bounty's "unauthorized transaction or execution" / "false state acceptance" categories.

### Likelihood Explanation
`register_token`'s origin is gated by `CreateOrigin` (governance/root) [8](#0-7) , so the initial trigger (re-registering an already-registered asset instead of using `update_token`) requires a privileged operator action — a realistic operational mistake during contract migrations rather than a purely permissionless exploit. However, once that state exists, exploitation of the stale binding (sending the forged/legitimate `Send` message from the old contract) requires no privilege at all — any party controlling that old contract, including its original deployer/owner after the fact, or anyone who can trigger execution on it, can exercise the leftover authority indefinitely. This mirrors the judge's medium-severity reasoning in the source report: the root cause is an admin-adjacent operational action, but the resulting stale-state window enables value leakage without further privileged involvement.

### Recommendation
In `register_token`, before inserting a new `TokenContracts`/`ContractToAsset` pair for a given `(chain, asset_id)`, look up and remove any existing `ContractToAsset` entry for the old contract address on that chain, mirroring the cleanup already done in `update_token`:
```rust
if let Some(old_contract) = TokenContracts::<T>::get(chain, registration.local_id.clone()) {
    ContractToAsset::<T>::remove(chain, old_contract);
}
```
Additionally, consider making `register_token` idempotent-safe by either rejecting re-registration of an already-known `asset_id` (forcing operators to use `update_token` for migrations) or applying the same add/remove semantics as `update_token` uniformly.

### Proof of Concept
1. Governance calls `register_token` for `asset_id = X` with `chains = { Evm(1): contract = 0xOLD }`. Storage: `TokenContracts(Evm(1), X) = 0xOLD`, `ContractToAsset(Evm(1), 0xOLD) = X`.
2. A relayer/user bridges tokens using `0xOLD`; this is normal usage — `on_accept` mints/credits `X` correctly.
3. The contract for `X` on `Evm(1)` is redeployed at `0xNEW` (e.g., bug fix). Governance calls `register_token` again for the same `asset_id = X` with `chains = { Evm(1): contract = 0xNEW }` instead of using `update_token`.
4. Storage now has: `TokenContracts(Evm(1), X) = 0xNEW`, `ContractToAsset(Evm(1), 0xNEW) = X`, **and** the untouched stale entry `ContractToAsset(Evm(1), 0xOLD) = X`.
5. Anyone able to trigger a `Send` message from `0xOLD` (the old contract is not required to be destroyed and may still be callable) dispatches a `PostRequest` with `from = 0xOLD`, `to = PALLET_ID`.
6. `on_accept` looks up `ContractToAsset::<T>::get(Evm(1), 0xOLD)`, finds it still resolves to `X`, and mints/releases `X` to the attacker-chosen beneficiary — even though `0xOLD` is no longer the recognized contract in `TokenContracts` and was believed decommissioned. [7](#0-6)

		/// Registers a new token with per-chain contract configuration
		#[pallet::call_index(1)]
		#[pallet::weight(T::WeightInfo::register_token(registration.chains.len() as u32))]
		pub fn register_token(
			origin: OriginFor<T>,
			registration: TokenRegistration<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if registration.local_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					registration.local_id.clone(),
				)
			};

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}

			Self::deposit_event(Event::<T>::TokenRegistered {
				asset_id: registration.local_id,
				native: registration.native,
				chains,
			});
			Ok(())
		}
