### Title
`depositFor` in `WombatPoolHelperV2` hardcodes `_minimumLiquidity` to `0`, disabling slippage protection and enabling sandwich attacks on deposits - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.deposit()` correctly forwards a caller-supplied `_minimumLiquidity` value that is ultimately passed to the underlying Wombat pool's `deposit()` function to bound slippage. However, the sibling entry point `depositFor()` hardcodes this value to `0`, completely removing slippage protection for any deposit routed through it. This makes deposits made via `depositFor` fully exposed to sandwich/MEV attacks, matching the bug class described in the external report (missing minimum-liquidity check on liquidity provisioning).

### Finding Description
`WombatPoolHelperV2.deposit()` takes a `_minimumLiquidity` parameter from the caller and forwards it down to `WombatStaking.deposit()`, which in turn passes it into `IWombatPool(poolInfo.depositTarget).deposit(...)` as the pool's own slippage guard: [1](#0-0) 

`depositFor`, however, is a separate unprivileged, externally callable function that lets any caller deposit `depositToken` on behalf of an arbitrary `_for` address, but it always calls `_deposit(_amount, 0, _for, address(this))`, i.e. it hardcodes the minimum liquidity to `0`: [2](#0-1) 

That `0` propagates unchanged through `WombatStaking.deposit()`'s `_minimumLiquidity` parameter into the real Wombat pool's `deposit()` call, which is the exact function that enforces the minimum-liquidity/slippage check on-chain: [3](#0-2) [4](#0-3) 

Because the check is effectively disabled (`minimumLiquidity = 0`), any deposit made through `depositFor` will succeed no matter how unfavorable the resulting LP/liability conversion rate is, exactly the missing-minimum-liquidity condition flagged in the referenced Vader report as enabling sandwich attacks.

### Impact Explanation
An MEV searcher monitoring the mempool can front-run a `depositFor` call by skewing the underlying Wombat pool's cash/liability ratio (e.g., swapping heavily against the target asset), let the victim's zero-slippage deposit mint an unfavorable (low) amount of LP/receipt tokens at the skewed rate, then back-run to restore the pool and capture the difference. Because `depositFor` is reachable by any ordinary wallet with no way for the depositing user to bound the acceptable liquidity received, this results in a direct, deterministic loss of user funds (fewer receipt/LP tokens minted than the fair-market amount) with no recourse — a concrete theft-of-funds outcome as opposed to a hypothetical.

### Likelihood Explanation
`depositFor` is a normal, unrestricted external function with no access control (any EOA/contract can call it), and the vulnerable path is triggered on every single call. Sandwiching capability is standard for MEV searchers on public mempools, making exploitation highly likely for any non-trivial deposit size, consistent with the referenced Vader finding's medium/high likelihood rating.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (mirroring `deposit`) and forward the caller-supplied value instead of hardcoding `0`, so the underlying Wombat pool's minimum-liquidity check can meaningfully protect the depositor from adverse price movement between transaction submission and execution.

### Proof of Concept
1. Attacker observes a pending `depositFor(_amount, _for)` transaction targeting `WombatPoolHelperV2`.
2. Attacker front-runs by swapping a large amount against the target asset in the underlying Wombat pool, skewing its cash/liability ratio unfavorably.
3. The victim's `depositFor` call proceeds to `WombatStaking.deposit()` → `IWombatPool.deposit(..., _minimumLiquidity = 0, ...)`, which succeeds despite the unfavorable rate because the minimum-liquidity guard is `0`. [2](#0-1) 
4. Attacker back-runs by reversing the swap, restoring the pool and capturing the value extracted from the victim's under-minted LP/receipt tokens.
