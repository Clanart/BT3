### Title
Unanchored regex match on `anchor.href` in `IssueLinkFilter` allows spoofed issue/PR links to attacker-controlled origins - (File: `app/src/lib/markdown-filters/issue-link-filter.ts`)

### Summary
`issueUrl()` builds a `RegExp` from the repository's GitHub host but never anchors it to the start of the string, and `isGitHubIssuePullDiscussionLink` calls `.test(anchor.href)` on the *whole href* instead of comparing `new URL(anchor.href).origin` against `getHTMLURL(repository.endpoint)`'s origin. As a result, a URL such as `https://evil.com/https://github.com/owner/repo/issues/1` — whose real origin is `evil.com` — still satisfies the regex because the trusted host string appears later in the path.

### Finding Description
`issueUrl` builds the pattern as `escapeRegExp(gitHubURL) + '/' + owner/repo + '/' + (issues|pull|discussions) + '/' + number` with no leading `^` anchor: [1](#0-0) 

`isGitHubIssuePullDiscussionLink` runs a series of substring `.test()` checks and finally relies on this unanchored regex against `anchor.href` directly, rather than validating the URL's origin: [2](#0-1) 

Because the regex has no `^`/`origin`-boundary anchor, any href that merely *contains* the trusted GitHub host + `/owner/repo/issues/N` as a substring will pass, even if that substring is embedded inside the path of a completely different origin (e.g., `https://evil.com/https://github.com/owner/repo/issues/1`). The upstream `createFilterTreeWalker` only additionally requires that `el.href === el.innerText`, which is naturally true for markdown auto-linked bare URLs (marked will auto-link a raw URL string, setting both `href` and displayed text to that same string): [3](#0-2) 

When the check passes, `filter()` rewrites the *visible text* of the anchor to a short reference like `#1`, while leaving the `href` attribute (the actual navigation target) untouched: [4](#0-3) 

This is rendered inside the sandboxed markdown iframe, whose click interceptor forwards any `http(s)` anchor's `href` to `onMarkdownLinkClicked` without any origin verification of its own: [5](#0-4) 

Consumers of `onMarkdownLinkClicked` (issue/PR comment views, release notes, copilot-conflicts dialog, etc.) then call `dispatcher.openInBrowser(url)` or `shell.openExternal(url)` directly on that href: [6](#0-5) [7](#0-6) 

Net effect: a comment/issue/PR body (attacker-controlled content) containing the raw URL `https://evil.com/https://github.com/owner/repo/issues/1` is displayed with the innocuous, trust-implying label `#1`, matching the exact visual style GitHub Desktop uses for legitimate, verified issue links to the current repository — while the actual link target is an arbitrary attacker-controlled origin.

### Impact Explanation
This is a link-spoofing/UI-deception issue, not a same-origin-bypass that itself achieves code execution. The filter never changes `href`; it only changes the *displayed text*, and Desktop's link interceptor already forwards arbitrary `http(s)` hrefs to `openExternal`/`openInBrowser` regardless of what `IssueLinkFilter` decides — clicking any auto-linked URL in a rendered comment already opens an external browser. The vulnerability's practical effect is that the attacker can make a malicious URL *look like* a trusted, same-repository issue reference (`#1`) instead of a visibly foreign URL, increasing the chance a user clicks it (e.g., for a phishing page mimicking GitHub sign-in). This could plausibly contribute to credential phishing, but it requires the user to click through to an external phishing site and enter credentials there — no in-app credential exfiltration, code execution, or sandbox/IPC escape results directly from this bug.

### Likelihood Explanation
Requires only that the attacker controls markdown content (issue/PR/commit comment body) rendered in Desktop and that the auto-linked raw URL matches the crafted nested-host pattern; no special user privileges or local access are needed. However, exploitation still depends on a user clicking the disguised link and then being fooled into taking further action (e.g., entering credentials) — an additional user-interaction step beyond passive viewing.

### Recommendation
Anchor the regex to the start of the string and, more robustly, parse `anchor.href` with `new URL()` and compare `.origin` (and optionally `.host`) strictly against `new URL(getHTMLURL(repository.endpoint)).origin` before treating the link as a trusted issue/PR/discussion reference, rather than relying on unanchored substring matching of the href.

### Proof of Concept
1. In a repository's issue/PR/commit comment body, insert the raw text: `https://evil.com/https://github.com/owner/repo/issues/1` (where `owner/repo` matches the current repository).
2. Marked auto-links this into `<a href="https://evil.com/https://github.com/owner/repo/issues/1">https://evil.com/https://github.com/owner/repo/issues/1</a>`, satisfying `el.href === el.innerText`.
3. `isGitHubIssuePullDiscussionLink` runs: the substring `issue` is present, it's not a pull-request-tab path, it doesn't end in a dotted extension, and `issueUrl(repository).test(anchor.href)` returns `true` because the unanchored regex matches the embedded `https://github.com/owner/repo/issues/1` segment.
4. `filter()` replaces the displayed text with `#1`, so the rendered comment shows `#1` while the underlying `href` still points to `https://evil.com/...`.
5. Clicking the rendered `#1` link in the sandboxed markdown view triggers `setupLinkInterceptor` → `onMarkdownLinkClicked(a.href)` → `shell.openExternal`/`dispatcher.openInBrowser` with the attacker's URL, opening `evil.com` in the system browser despite the trusted-looking label.

export function issueUrl(repository: GitHubRepository): RegExp {
  const gitHubURL = getHTMLURL(repository.endpoint)
  return new RegExp(
    escapeRegExp(gitHubURL) +
      '/' +
      /** A regexp that searches for the owner/name pattern in issue href */
      /(?<nameWithOwner>\w+(?:-\w+)*\/[.\w-]+)/.source +
      '/' +
      /(?:issues|pull|discussions)/.source +
      '/' +
      /** A regexp that searches for the number and #anchor of an issue reference */
      /(?<refNumber>\d+)(?<anchor>#[\w-]+)?\b/.source
  )
}

  private isGitHubIssuePullDiscussionLink(anchor: HTMLAnchorElement) {
    const isIssuePullOrDiscussion = /(issue|pull|discussion)/.test(anchor.href)
    if (!isIssuePullOrDiscussion) {
      return false
    }

    const isPullRequestTab = /\d+\/(files|commits|conflicts|checks)/.test(
      anchor.href
    )
    if (isPullRequestTab) {
      return false
    }

    const isURlCustomFormat = /\.[a-z]+\z/.test(anchor.href)
    if (isURlCustomFormat) {
      return false
    }

    return issueUrl(this.repository).test(anchor.href)
  }

  public async filter(node: Node): Promise<ReadonlyArray<Node> | null> {
    const { textContent: text } = node
    if (!isElement(node, 'a') || text === null) {
      return null
    }

    const match = text.match(issueUrl(this.repository))
    if (match === null || match.groups === undefined) {
      return null
    }

    const { refNumber, anchor } = match.groups
    const newNode = node.cloneNode(true)
    newNode.textContent = this.getConsistentIssueReferenceText(
      refNumber,
      anchor
    )

    return [newNode]
  }
