### Title
Unbounded, unevictable `commitLookup` cache in `GitStore` allows a malicious repository history to exhaust renderer memory - (File: app/src/lib/stores/git-store.ts)

### Summary
`GitStore.commitLookup` is a plain `Map<string, Commit>` that is populated every time commits are loaded from a repository's history (via `loadCommitBatch`, `loadLocalCommits`, `reconcileHistory`, and tag-change reconciliation) and is never bounded or evicted for the lifetime of the `GitStore` instance. [1](#0-0) 
This mirrors the broken invariant in the libp2p report: attacker-supplied data (there, signed peer records; here, commit objects from a repository the attacker controls) is accepted and stored in memory with no cleanup path, unlike sibling caches in the same codebase that explicitly bound themselves (`AheadBehindStore` and `CommitStatusStore` both use `QuickLRU` with a `maxSize` specifically "to ensure the cache won't grow unbounded"). [2](#0-1) [3](#0-2) 

### Finding Description
When a user browses history (scrolling in the History/Compare tab) or Desktop reconciles tags/history after a fetch/pull, `getCommits` reads commit data with `git log` and returns `Commit` objects whose `summary` and `body` fields are each capped at 100 KiB per commit (`subarray(0, 100 * 1024)`), but there is no cap on the *number* of distinct commits that can be cached. [4](#0-3) 

Every batch loaded via `loadCommitBatch` (paged by `CommitBatchSize = 100`) and `loadLocalCommits` is passed to `storeCommits`, which populates `commitLookup` keyed by SHA. [5](#0-4) [6](#0-5) 
This map lives inside the `GitStore`, which itself is cached per-repository (keyed by `repository.hash`) in `GitStoreCache` and is only removed when the repository is explicitly removed from Desktop, not on tab switches or history scroll-back. [7](#0-6) 

A malicious/compromised remote can therefore serve a repository with an extremely large number of commits, each with a near-maximal (100 KiB) commit message/body (git places essentially no server-side limit on this). As the History/Compare view lazily paginates through history — which is normal, expected UI usage triggered by scrolling (`onScroll` → `loadNextCommitBatch` → `gitStore.loadCommitBatch`) — every loaded commit is permanently retained in `commitLookup` with no LRU eviction, no size cap, and no expiry, unlike the `AheadBehindStore`/`CommitStatusStore` caches that were deliberately designed with `QuickLRU` for this exact reason. [8](#0-7) [9](#0-8) 

### Impact Explanation
Sustained memory growth in the renderer process from repository data that the user does not otherwise inspect can degrade or crash the Desktop app (renderer OOM), matching the "silent, time-delayed OOM" impact class of the source report. Because `commitLookup` is retained for the app session and only cleared when the repository entry is removed, a large/malicious repository can accumulate large amounts of committed message text in memory purely through normal history scrolling that a user would reasonably perform while reviewing a cloned/fetched repo.

### Likelihood Explanation
Moderate. Exploitation requires (a) the victim to clone or add a repository under attacker influence and (b) the victim to scroll through a large portion of its commit history (a natural, expected interaction, not an "unnatural" step). The 100 KiB per-field truncation limits worst-case single-commit size but does not limit total commit count, so the attack scales with history length rather than requiring any exotic trigger. No admin rights, local access, or prior compromise are needed — only a hostile git remote and normal Desktop usage against it.

### Recommendation
Bound `commitLookup` the same way `AheadBehindStore.cache` and `CommitStatusStore.cache` are bounded — e.g., replace the plain `Map` with a `QuickLRU<string, Commit>` with a fixed `maxSize`, or otherwise evict entries once the associated history/compare state SHAs are no longer displayed/referenced.

### Proof of Concept
1. Create/host a git repository with a very large number of commits (e.g. hundreds of thousands), each with a commit message body close to the 100 KiB truncation limit (achievable with `git commit --allow-empty -m "$(python3 -c 'print("A"*100000)')"` repeated in a loop, or scripted via `git fast-import`).
2. Have the victim clone or add this repository in GitHub Desktop.
3. Open the History tab and scroll continuously to the bottom of history (or trigger `Compare`/tag-reconciliation flows that call `loadCommitBatch`/`loadLocalCommits` repeatedly).
4. Observe `commitLookup` in `GitStore` grow without bound as new batches are loaded — no entries are ever evicted, unlike the bounded `AheadBehindStore`/`CommitStatusStore` caches — leading to steadily increasing renderer memory usage that can culminate in an out-of-memory crash.

  public async loadCommitBatch(commitish: string, skip: number) {
    if (this.requestsInFight.has(LoadingHistoryRequestKey)) {
      return null
    }

    const requestKey = `history/compare/${commitish}/skip/${skip}`
    if (this.requestsInFight.has(requestKey)) {
      return null
    }

    this.requestsInFight.add(requestKey)

    const commits = await this.performFailableOperation(() =>
      getCommits(this.repository, commitish, CommitBatchSize, skip)
    )

    this.requestsInFight.delete(requestKey)
    if (!commits) {
      return null
    }

    this.storeCommits(commits)
    return commits.map(c => c.sha)
  }

  public async loadLocalCommits(
    branch: Branch | null,
    skip?: number
  ): Promise<string[] | null> {
    if (branch === null) {
      this._localCommitSHAs = []
      return null
    }

    let localCommits: ReadonlyArray<Commit> | undefined
    if (branch.upstream) {
      const range = revRange(branch.upstream, branch.name)
      localCommits = await this.performFailableOperation(() =>
        getCommits(this.repository, range, CommitBatchSize, skip)
      )
    } else {
      localCommits = await this.performFailableOperation(() =>
        getCommits(this.repository, 'HEAD', CommitBatchSize, skip, [
          '--not',
          '--remotes',
        ])
      )
    }

    if (!localCommits) {
      return null
    }

    this.storeCommits(localCommits)

    let newCommitSHAs: string[]

    if (skip !== undefined) {
      // perform a soft ammend to the list of local commits
      const previousSHAs = new Set(this._localCommitSHAs)
      newCommitSHAs = localCommits
        .map(c => c.sha)
        .filter(sha => !previousSHAs.has(sha))
      this._localCommitSHAs = [...this._localCommitSHAs, ...newCommitSHAs]
    } else {
      // reset the local commits since its a page reset
      newCommitSHAs = localCommits.map(c => c.sha)
      this._localCommitSHAs = Array.from(newCommitSHAs)
    }

    this.emitUpdate()

    return newCommitSHAs
  }

  public async _loadNextCommitBatch(repository: Repository): Promise<void> {
    const gitStore = this.gitStoreCache.get(repository)

    const state = this.repositoryStateCache.get(repository)
    const { formState } = state.compareState
    if (formState.kind === HistoryTabMode.History) {
      const commits = state.compareState.commitSHAs

      const tip = state.branchesState.tip

      let newCommits: string[] | null = null

      // Prioritize pulling from the local commits if the last one we pulled is local
      if (
        commits.length > 0 &&
        tip.kind === TipState.Valid &&
        gitStore.localCommitSHAs.includes(commits[commits.length - 1])
      ) {
        newCommits = await gitStore.loadLocalCommits(tip.branch, commits.length)
      }

      if (!newCommits || newCommits.length === 0) {
        newCommits = await gitStore.loadCommitBatch('HEAD', commits.length)
      }

      if (!newCommits) {
        return
      }

      this.repositoryStateCache.updateCompareState(repository, () => ({
        commitSHAs: commits.concat(newCommits),
      }))
      this.emitUpdate()
    }
