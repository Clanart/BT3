### Title
`SignableTransaction`/`multisig` trusts the value in a deserialized `ReceivedOutput`, letting recorded obligations exceed the actual UTXO amount — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The M-14 bug class is "the system mints/records a claim on assets exceeding what was actually credited" — `wfCash` minted shares against the pre-fee deposit while Notional credited only the post-fee amount. The Serai analog lives in the Bitcoin wallet: `SignableTransaction::new` computes `input_sat` purely from `ReceivedOutput.output.value` (deserialized, attacker-controllable bytes via `ReceivedOutput::read`), and `multisig()` only verifies that the *script_pubkey* of each prevout matches the offset-derived key — it never checks that `value` equals the real on-chain UTXO amount. An inflated `value` inflates `input_sat`, so the wallet signs a transaction whose declared input value exceeds the actual input — the same "claims exceed assets" mismatch.

### Finding Description
`ReceivedOutput::read` (mod.rs:122-134) accepts arbitrary `offset`, `TxOut` (including `value`), and `outpoint` with no validation. `SignableTransaction::new` sums `input.output.value` into `input_sat` (send.rs:175) and only checks `input_sat >= payment_sat + needed_fee` (send.rs:215). If `input_sat` is inflated, the change branch computes `value = input_sat - (payment_sat + fee_with_change)` (send.rs:228) and creates a change output for funds that don't exist — the exact analog of minting `fCashAmount` while only `deposit - fee` was credited.

When signing, `multisig` (send.rs:273-285) verifies `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — script equality only, no value check. `TransactionSignMachine::sign` then commits the fraudulent `prevouts` into each `taproot_key_spend_signature_hash` via `Prevouts::All(&self.tx.prevouts)` (send.rs:375-390). Since BIP-341 commits the sighash to each input's amount, the resulting signature is valid for the *claimed* value but invalid for the real UTXO. The signed transaction cannot be broadcast/mined; the plan's payments and change are committed on-chain accounting-wise yet the inputs can't cover them.

### Impact Explanation
The wallet produces a signed transaction pledging obligations (payments + change) greater than real spendable funds — directly mirroring the insolvency mismatch where issued `wfCash` exceeded the vault's prime-cash balance. On-chain the signature is invalid (sighash binds the inflated amount), so the transaction can never confirm: any scheduler/plan that consumed those outputs and emitted obligations against them is stuck, and the "funds reported received" are not spendable — matching the accepted impact category "funds reported received that are not spendable."

### Likelihood Explanation
Reachable only by feeding crafted bytes to `ReceivedOutput::read` (an explicitly permitted untrusted-input surface). No timing or collusion needed, but it requires a path where an unprivileged party supplies serialized `ReceivedOutput`s rather than the scanner producing them, and it yields stuck funds / invalid signatures rather than key recovery — consistent with Medium.

### Recommendation
In `SignableTransaction::multisig` (send.rs:273-285), in addition to checking `script_pubkey`, verify the claimed prevout value — e.g., require the caller to confirm each `prevouts[i]` against the confirmed transaction's actual `TxOut` (or store verified values at scan time and mark `ReceivedOutput`s as trusted/untrusted). Alternatively, have `ReceivedOutput::read` produce a distinct "unverified" type that `multisig` refuses to sign for.

### Proof of Concept
1. Take a real scanned `ReceivedOutput` for a UTXO worth `V` sats. Deserialize a modified copy via `ReceivedOutput::read` where `output.value` is `V + D` (e.g., double).
2. `SignableTransaction::new` sees `input_sat = V + D`; with `change = Some(addr)`, it creates a change output of `(V + D) - payments - fee`, minting a claim on `D` phantom sats — the fee-on-transfer mismatch analog.
3. `multisig()` passes because only `script_pubkey` is checked (send.rs:277).
4. `sign`/`complete` produce signatures committing to `V + D` in the taproot sighash; nodes reject the transaction since the real prevout value is `V`. The change and payments are scheduled against assets that do not exist, and the inputs become unspendable under this plan.
