### Title
Hookify PreToolUse enforcement fails open on any parser/engine exception, allowing a crafted rule file to silently disable all `block`/`deny` rules - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The Solidity report describes a privileged, security-critical operation (`_cleanupLoan` liquidation flow) that hands control to an untrusted callback (`onERC721Received`), and the untrusted party crafts that callback to fail, causing the enforcement action (liquidation) to be aborted entirely rather than degrading safely. The closest analog reachable in this repo is the `hookify` plugin's `PreToolUse` enforcement hook, which is Claude Code's mechanism for blocking dangerous tool calls (e.g., destructive `Bash` commands). Its top-level design explicitly swallows *any* exception raised while loading or evaluating rules and always exits `0` (allow), rather than failing closed. A crafted or corrupted rule file — which is workspace/repo-controlled, i.e. attacker-influenceable content similar in spirit to the untrusted "owner" contract in the Solidity bug — can drive `load_rules`/`RuleEngine.evaluate_rules` into raising, which the hook interprets as "allow the operation," silently disabling all `block` rules (e.g. `block-destructive-ops`) for that and potentially every subsequent invocation.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` is registered as Claude Code's `PreToolUse` hook for the hookify plugin. It reads `.claude/hookify.*.local.md` rule files, evaluates them against the current tool call, and is meant to return a permission decision (`allow`/`ask`/`deny`) that Claude Code enforces before running the tool [1](#0-0) .

The `main()` function wraps rule loading and evaluation in a `try/except Exception` block. On *any* exception — including malformed YAML frontmatter, a bad regex `pattern`, or any parsing bug in `load_rules`/`RuleEngine.evaluate_rules` — it prints only a `systemMessage` and does not emit any `permissionDecision`, and then unconditionally calls `sys.exit(0)` in the `finally` block: [2](#0-1) 

This is explicitly documented in the code comment as intentional: "ALWAYS exit 0 - never block operations due to hook errors" [3](#0-2) . Because a `PreToolUse` hook that exits 0 without a `permissionDecision` is treated as "no opinion" (i.e., allow-through) by Claude Code's hook contract, any rule that would have blocked a dangerous operation — such as the documented `block-destructive-ops` rule matching `rm -rf`, `dd if=`, `mkfs`, etc. — is silently skipped whenever the rule file fails to parse or the engine throws, exactly as shown in the plugin's own README example [4](#0-3) .

This mirrors the reported bug class structurally:
- Privileged/protective action = `PreToolUse` block enforcement (analogous to `_cleanupLoan`'s liquidation transfer).
- Untrusted/attacker-influenced input = the `.claude/hookify.*.local.md` rule file content and the tool-call input being matched (analogous to the borrower-controlled `onERC721Received`).
- Failure mode = an engine exception causes the enforcement path to abort, and the fallback behavior (fail-open / allow) is exactly the outcome the protective mechanism was supposed to prevent — just as the reverting `onERC721Received` callback prevented liquidation from ever completing.

### Impact Explanation
If a workspace's rule files (which can originate from a shared/cloned repository, or be manipulated by a lower-privileged collaborator with edit access to `.claude/`) contain content that trips an unhandled exception in `config_loader.load_rules` or `RuleEngine.evaluate_rules` (e.g., unusual frontmatter, invalid regex causing `re.error`, or any parsing edge case not defensively handled inside those modules), every `PreToolUse` block/deny rule configured via hookify is silently bypassed for that invocation. Since hookify's stated purpose is to block destructive Bash commands and warn about unsafe file edits, this converts hookify's declared safety guarantee into a no-op precisely when the input is anomalous — which is also the condition most likely to correlate with an actual attack or unsafe command being crafted to exploit that same parsing weakness. The impact is a security-control bypass (unauthorized command/file-operation execution proceeds unblocked) rather than data loss by itself, but it directly undermines the "hook bypass" trust boundary the plugin is meant to enforce.

### Likelihood Explanation
Likelihood is moderate to low-confidence without full visibility into `config_loader.py` and `rule_engine.py` (their contents could not be retrieved in this session, see caveat below), but the fail-open contract is confirmed directly from `pretooluse.py`'s own code and comments, which unconditionally treat *any* exception, including ones triggered by attacker/workspace-supplied rule-file content or unusual tool-call input, as "allow." Given that rule files are markdown+YAML+regex parsed from disk and matched against free-form tool inputs (attacker-controllable strings, e.g. a crafted Bash command or file path), the surface for triggering a parse/match exception is realistic, and the plugin authors clearly anticipated hitting exceptions often enough to hard-code a blanket catch-all around the entire evaluation path.

### Recommendation
Change the fail-open default to fail-closed for `block`/`deny`-configured rules: if rule loading or evaluation raises, either (a) return a hookSpecificOutput of `"ask"` so the user is prompted rather than silently allowed, or (b) at minimum, distinguish "no rules configured for this event" (safe to allow) from "rules exist but evaluation errored" (should not silently allow). Additionally, harden `config_loader.load_rules` and `RuleEngine.evaluate_rules` to catch and report file-level and rule-level errors individually (skip only the malformed rule, not all rules), so a single bad or adversarial rule file cannot disable every other valid rule in the same evaluation pass.

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
