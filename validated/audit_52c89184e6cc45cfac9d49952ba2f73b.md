## Title
Non-atomic ERC20 post-conversion after successful ICS20 unescrow enables cross-chain fund duplication - (File: `x/erc20/keeper/ibc_callbacks.go`)

### Summary
This is the Cosmos EVM analog of the CCIP "price update mechanism can break" report: a cross-chain flow performs an irreversible state-changing action first, then executes a secondary step that can fail for ordinary, non-malicious reasons, and the failure is surfaced only as an acknowledgement value rather than by rolling back the already-committed state. In the CCIP case this caused DoS; here the same failure-handling gap produces a stronger impact — duplicated spendable value across two chains.

### Finding Description
The ERC-20 IBC middleware wraps the core ICS-20 transfer module: `im.Module.OnRecvPacket` (core transfer) runs first and, for the "native ERC20 returning home" case, unescrows real bank-denominated tokens to the receiver. Only *after* that unescrow succeeds does `Keeper.OnRecvPacket` attempt to convert/mint the ERC-20 representation for the receiver: [1](#0-0) 

If `MintingEnabled` or `ConvertCoinNativeERC20` fails for any ordinary reason (e.g. `SendEnabled=false` for the denom, a minting restriction, a reverting/self-destructed ERC20 contract as explicitly called out in the code's own doc comment), the function returns `channeltypes.NewErrorAcknowledgement(err)` — but the unescrow performed a moment earlier by the core transfer module is **not rolled back**: [2](#0-1) 

The outer middleware wiring simply forwards whatever acknowledgement the inner layer produces: [3](#0-2) 

Since `sdk.Msg` handling in the SDK/IBC core only decides *what acknowledgement bytes to relay*, not whether to discard the state mutations already performed during `OnRecvPacket`, an `ErrorAcknowledgement` returned after a successful unescrow still leaves the escrow released and the funds resident (as bank coins) at the receiver/isolated address on the destination chain. The relayer nonetheless delivers this `ErrorAcknowledgement` back to the source chain, where standard ICS-20 `OnAcknowledgementPacket` logic refunds/mints back the sender's original amount because the ack indicates failure.

This exact "trapped-but-not-reverted" behavior is confirmed by the repository's own middleware test, which asserts that when the ERC-20 conversion step fails (`SendEnabled=false`), the escrow is **not** restored and the bank tokens instead land at an isolated address recoverable only by the original sender: [4](#0-3) [5](#0-4) 

Combined with standard ICS-20 refund-on-error-ack semantics on the counterparty chain, the destination chain retains real value (the isolated/trapped bank balance) while the source chain refunds the same value to the sender — a double-credit of the transferred amount across the two chains.

### Impact Explanation
This breaks the fundamental cross-chain 1:1 accounting invariant between escrowed value and circulating representations: the same transferred amount becomes simultaneously spendable on the destination chain (as a trapped/recoverable bank balance belonging to the sender/receiver) and refunded on the source chain. This is unauthorized duplication of spendable user value across IBC escrows/ERC20 representations, matching the Critical impact gate for "unauthorized minting, burning, duplication ... of spendable user value across native balances, EVM balances, ERC20 representations, IBC escrows."

### Likelihood Explanation
No malicious actor is required. Any ordinary, honest-operation condition that causes the post-unescrow ERC20 conversion step to fail — a temporarily disabled `SendEnabled` flag, a minting/pair restriction, or (per the code's own documentation) a self-destructed or reverting ERC20 contract — triggers this path. This mirrors the CCIP report's finding that ordinary usage (e.g., price deviation checks) can trip an unhandled-failure path without any adversary, making this readily reachable in production operation.

### Recommendation
Make the unescrow/mint and the ERC-20 post-conversion atomic: perform the ERC-20 conversion attempt inside a `CacheContext` alongside (or before) the core transfer's state mutation, and only commit both together if the entire flow succeeds; otherwise return an `ErrorAcknowledgement` with all destination-side state (including the unescrow) rolled back so it matches the semantics assumed by the source chain's refund-on-error-ack logic. Alternatively, never return an `ErrorAcknowledgement` once the underlying transfer has already committed value — treat post-processing failures as no-ops that leave the recipient holding the bank-denominated coin (which the code's own top-level doc comment claims is the intended behavior) rather than signaling failure upstream.

### Proof of Concept
1. Register a native ERC20 token pair and send it out from chain A to chain B (funds now escrowed on A).
2. Disable `SendEnabled` for that denom on chain A (or otherwise cause `MintingEnabled`/`ConvertCoinNativeERC20` to fail, e.g. a reverting destination contract).
3. Relay the return packet from B to A with a `dest_callback` memo. Core `transfer.OnRecvPacket` succeeds and unescrows the coin to the isolated receiver address, as shown in the middleware test at [6](#0-5) .
4. `Keeper.OnRecvPacket`'s native-ERC20 branch then fails the conversion and returns `channeltypes.NewErrorAcknowledgement(err)`, per [7](#0-6) .
5. Confirm on chain A that the escrow account balance is not restored (funds remain outside escrow, held at the isolated address) — as validated by the test comment "not send them back to escrow."
6. The relayer delivers this `ErrorAcknowledgement` to chain B, where the standard ICS-20 acknowledgement handler refunds the original sender.
7. Result: chain A holds the real released value (recoverable later by the sender/receiver) while chain B has refunded the same amount to the sender — duplicated spendable value across chains.

// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnAcknowledgementPacket
// still succeeds, but the user receives the corresponding bank token from the
// TokenPair instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
