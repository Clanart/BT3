### Title
Fee/weight accounting omits the OP_RETURN output, underpaying the real transaction fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` adds an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` to `tx_outs`, yet calculates `weight`/`vbytes`/`needed_fee` only over `payments`, which excludes the data output. The resulting transaction is larger than accounted for, so `needed_fee` understates the fee required for the requested `fee_per_vbyte`, the minimum-relay-fee check is evaluated against too-small a vsize, and the change output is over-credited while the actual fee is under-paid.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed into `tx_outs` before the weight calculation, but `calculate_weight_vbytes` is only passed `payments`: [1](#0-0) 

`calculate_weight_vbytes` builds the sizing transaction exclusively from `payments` plus an optional change output — there is no parameter for the data output, so its ~9–90+ vbytes (OP_RETURN opcode + pushdata + up to 80 bytes payload, plus the fixed `TxOut` fields) are never counted: [2](#0-1) 

The same omission propagates to the change branch, where `fee_with_change` is computed from `payments` and the change script only: [3](#0-2) 

This is the same bug class as the report: a counter ("supply" / "vbytes accounting") is not updated to reflect value that was moved into the structure, so a subsequent computation (`supply_before + _value` / `fee_per_vbyte * vbytes`) is applied on a stale base. The "merge"-equivalent is that `data` is committed into `tx_outs` but never "removed" from — i.e., added to — the weight accounting. Additionally, the check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` uses the understated `vbytes`, so a transaction can pass the min-fee gate while the actual serialized transaction underpays the relay minimum: [4](#0-3) 

### Impact Explanation
The signed transaction's actual vsize exceeds the accounted `vbytes`, so the effective fee rate is strictly below the requested `fee_per_vbyte`. Consequences:

- With a large `data` payload and a marginal `fee_per_vbyte`, the real fee rate can fall below `DEFAULT_MIN_RELAY_TX_FEE`, making the fully-signed transaction non-relayable — inputs referenced by `tx_ins`/`prevouts` become unspendable through this construction path for that attempt.
- When change is present, `input_sat - payment_sat - fee_with_change` credits the change output with sats that the real fee should have consumed, i.e., `tx.fee()` (computed from actual outputs) < `needed_fee()`, contradicting the documented invariant that the transaction achieves the specified fee rate.
- `needed_fee()` is exposed to callers (used in tests and presumably processor fee accounting), so downstream accounting records a fee lower than the rate the signer intended.

### Likelihood Explanation
An unprivileged caller controls `data: Option<Vec<u8>>` entirely (any `Some(vec)` up to 80 bytes triggers it) and `fee_per_vbyte`. Any transaction carrying data — a supported, tested feature (`test_data`) — deterministically underpays relative to the requested rate. Whether it drops below relay minimum depends on payload size and fee rate, but the accounting error occurs on every data-bearing transaction.

### Recommendation
Include the data output in the sizing calculation. Either pass the already-constructed `tx_outs` (or a synthesized OP_RETURN `TxOut`) into `calculate_weight_vbytes`, or add the OP_RETURN output inside `calculate_weight_vbytes` alongside the change output in both the no-change and change branches, so `weight`, `vbytes`, `needed_fee`, and the minimum-relay check reflect the actual transaction.

### Proof of Concept
```rust
// SignableTransaction::new(vec![input], &[], Some(change), Some(vec![0u8; 80]), FEE)
// tx_outs gets 2 outputs: OP_RETURN(80 bytes) + change
// calculate_weight_vbytes is called with payments=&[] and Some(change)
//  -> sized tx has 1 output; actual tx has 2, ~100+ extra serialized bytes unpriced
let tx = SignableTransaction::new(inputs, &payments, change, Some(data), fee_per_vbyte)?;
let actual_vsize = tx.transaction().vsize() as u64;
assert!(tx.needed_fee() < fee_per_vbyte * actual_vsize); // real rate < requested rate
```
With `fee_per_vbyte` equal to the relay minimum and an 80-byte payload, the effective fee rate on the serialized transaction falls below `DEFAULT_MIN_RELAY_TX_FEE`, so the signed transaction is rejected by standard Bitcoin relay despite passing the internal `TooLowFee` check.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
