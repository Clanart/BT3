### Title
OP_RETURN data output is excluded from the transaction weight/vbytes estimate, undercharging the fee and potentially producing an unrelayable transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds the fee estimate by calling `calculate_weight_vbytes(inputs, payments, change)`, which reconstructs a template transaction containing only the payment outputs (and optionally change). The `data: Option<Vec<u8>>` OP_RETURN output — which can be up to 80 bytes plus overhead — is pushed onto the real `tx_outs` but is never included in the template used for `weight`, `vbytes`, `needed_fee`, or the `MAX_STANDARD_TX_WEIGHT` check. The resulting transaction therefore pays `fee_per_vbyte * vbytes` for a transaction whose actual vsize is larger, i.e., it underpays relative to the requested fee rate. [1](#0-0) [2](#0-1) 

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` at lines 194–202, but the weight/vbytes are computed at line 204 from `payments` (and the change-only recomputation at lines 225–226) — neither template includes the data output. `calculate_weight_vbytes` (lines 62–127) builds its template `Transaction` solely from `payments` plus an optional change output. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` undervalues the true fee for the requested rate whenever `data` is `Some`.
- The `TooLowFee` guard at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same underestimated `vbytes`. A caller passing the minimum-acceptable `fee_per_vbyte` together with `data` produces a transaction whose *actual* fee rate falls below the minimum relay fee, so Bitcoin nodes will reject it.
- `fee()` (lines 138–141) computes `sum(prevouts) - sum(outputs)`, so the discrepancy is not self-correcting — the tx simply pays less sat/vbyte than intended.

This is the same class as the Linea report (fees computed against an incorrect/unknown gas measure, leaking or stranding value), mapped onto Serai's shape: the fee formula is wrong for a caller-controlled input (the `data` field fed to `SignableTransaction::new`).

### Impact Explanation
A transaction constructed with a 1–80 byte `data` payload pays less sat/vbyte than the caller requested. At marginal fee rates the transaction falls below the minimum relay fee and is rejected/stuck (no confirmation, inputs effectively frozen until re-signed). At higher rates, the transaction silently confirms slower than intended. All leftover value beyond `payments + needed_fee` is already directed to the fee when no change is given, so the intended fee is the caller's only protection — and it is computed against the wrong size. Impact is a denial-of-confirmation / degraded-fee condition reachable with only public inputs; no keys or signatures are forged. Medium/low-severity magnitude but a concrete incorrect verifier-style formula.

### Likelihood Explanation
Any caller of `SignableTransaction::new` with `data: Some(_)` hits the undercount deterministically; the miscount grows with data length (up to ~84 vbytes of unaccounted weight vs. the 80-byte limit). Whether the transaction is actually rejected depends on how close the requested `fee_per_vbyte` is to the relay minimum — callers using exactly the minimum rate are reliably affected.

### Recommendation
Include the OP_RETURN output in the weight template: either pass a synthetic `(ScriptBuf::new_op_return(...), 0)` entry into `calculate_weight_vbytes`, or refactor so the fee/size estimates are computed from the fully assembled `tx_outs` list (payments + data + change) rather than a partial reconstruction. Re-run `TooLowFee` and `MAX_STANDARD_TX_WEIGHT` checks against that complete transaction.
