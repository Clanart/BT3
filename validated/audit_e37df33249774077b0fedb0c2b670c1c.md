## Analysis

The external report's core broken invariant: **a payable entrypoint calculates a required payment, accepts `msg.value >= required`, but never computes or returns the excess to the payer** — causing silent fund loss for any user who overpays.

Hyperbridge's own `IntentGatewayV2`/`ExtrinsicIntents` contracts explicitly guard against this pattern — they capture the Uniswap swap's return value and refund unspent `msg.value` to `msg.sender` at the end of `placeOrder`/`fillOrder`: [1](#0-0) 

But the **core `EvmHost` dispatch entrypoints that every ISMP application relies on for cross-chain messaging do not implement this refund at all**.

### Title
Excess native `msg.value` sent to `EvmHost.dispatch()`/`fundRequest()` is silently trapped, never refunded to the caller — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native ETH via `msg.value` and swap it for the exact fee-token amount needed using Uniswap V2's `swapETHForExactTokens`. None of these three functions capture the `amounts` array returned by the swap, and none compute or refund any leftover native ETH to `_msgSender()`.

### Finding Description
In each of these functions: [2](#0-1) [3](#0-2) [4](#0-3) 

`swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is called with the full `msg.value`, but only `fee` worth of tokens is actually required. A standard `IUniswapV2Router02.swapETHForExactTokens` implementation refunds any unused ETH to the caller of the swap — but the caller here is `EvmHost` itself (it calls the router directly, not via `delegatecall`), so the refund lands back in `EvmHost`'s own balance, not in the account that originally sent the transaction. `EvmHost` never reads the swap's return value, never tracks this leftover ETH, and has no logic anywhere in `dispatch`/`fundRequest` to forward it back to `_msgSender()`.

This is the exact bug class from the external report (`safeMint` overpayment not refunded), reproduced at the protocol's most heavily used payable entrypoint — every dispatching app/user that pays fees in native token through `IDispatcher.dispatch{value: ...}()` is exposed. It is not a peer/relayer/admin-dependent bug; it is directly triggerable by any unprivileged EOA or contract calling `dispatch()`/`fundRequest()` with `msg.value` even marginally above the amount consumed by the swap (which is common since callers must estimate the required native amount off-chain against a volatile AMM price, and the SDK's own fee-estimation docs acknowledge slippage on native-token payments).

### Impact Explanation
Any user who over-provisions `msg.value` for a native-token-funded `dispatch()`/`fundRequest()` call permanently loses the difference — it becomes permanently locked in `EvmHost` with no accounting of whose it was and no admin-facing refund path (unlike `_requestCommitments`/`FeeMetadata`, which only tracks the deliberate relayer fee, not incidental ETH overpayment). This matches the required impact category "stealing or loss of funds" — funds are lost with no recovery mechanism, on the core bridging contract rather than a peripheral app contract, affecting every EVM deployment of `EvmHost`.

### Likelihood Explanation
High. Native-token fee payment is a documented, encouraged path (`docs/content/developers/evm/messaging/post-requests.mdx` explicitly recommends it for "one-off transactions, user-facing apps" and warns of AMM slippage), meaning overpayment by a normal, safety-margin-adding integrator or end user is an expected occurrence, not an edge case. No malicious actor, relayer, or governance participant is required — the caller triggers the loss against themselves simply by using the documented native-payment flow with any safety buffer.

### Recommendation
Capture the `amounts` array returned from `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, compute `msg.value - amounts[0]`, and refund the difference to `_msgSender()` via a low-level `call` at the end of each function (mirroring the pattern already implemented in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `evm/src/apps/IntentGatewayV2.sol`), reverting on refund failure.

### Proof of Concept
1. Caller estimates the fee-token cost of a `DispatchPost` at `post.fee = 100` fee-token units and, to be safe against AMM slippage, sends `msg.value = 1 ether` to `EvmHost.dispatch{value: 1 ether}(post)`. [5](#0-4) 
2. `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), ...)` only spends, say, `0.02 ether` of the `1 ether` to acquire exactly `post.fee` fee tokens; the router refunds the remaining `0.98 ether` — but to `EvmHost` (the caller of the swap), not to the original transaction sender.
3. `dispatch()` proceeds to build the commitment, store `FeeMetadata{sender: post.payer, fee: post.fee}`, and emit `PostRequestEvent`, never inspecting the swap's return value. [6](#0-5) 
4. The `0.98 ether` overpayment remains in `EvmHost`'s balance permanently; the caller has no function to reclaim it, and it is indistinguishable from other protocol ETH once accumulated — a direct, unrecoverable loss of user funds.
