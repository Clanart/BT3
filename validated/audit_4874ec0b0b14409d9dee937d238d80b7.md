### Title
`GaslessSwapRouter.updateCommissionRate` has no upper-bound validation, allowing owner front-running to divert user's gasless-swap output - ([File: contracts/bindings/kip247/GaslessSwapRouter.go])

### Summary
`GaslessSwapRouter` (KIP-247 gasless-swap system contract) exposes an owner-only `updateCommissionRate(uint256 _commissionRate)` function [1](#0-0) . Unlike the analogous `PublicDelegation` contract, which enforces a hard cap via `MAX_COMMISSION_RATE` [2](#0-1) , no `MAX_COMMISSION_RATE`-style constant or bound check exists anywhere for `GaslessSwapRouter`'s commission rate in the indexed codebase. This mirrors the reported `PumpV1.setFeeRate` bug class: an admin/owner-controlled fee parameter with no upper bound that can be updated at any time, including right before a pending settlement transaction (`swapForGas`) is mined.

### Finding Description
`GaslessSwapRouter` implements the on-chain side of KIP-247 gasless transactions: a user swaps ERC-20 tokens for KAIA via `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` to repay the block proposer who fronted their gas [3](#0-2) . The contract emits `SwappedForGas(proposer, amountRepaid, user, finalUserAmount, commission)` [4](#0-3) , confirming that a `commission` cut is taken out of the swap proceeds before the `finalUserAmount` is delivered to the user.

The commission rate is mutable via the owner-only `updateCommissionRate` transactor, which emits `CommissionRateUpdated(oldRate, newRate)` [5](#0-4) . No bound check (e.g., `require(_commissionRate <= X)`) is discoverable in the codebase for this setter — no `MAX_COMMISSION_RATE`-equivalent constant is exposed in the ABI/bindings for `GaslessSwapRouter`, contrasting with `PublicDelegation.MAX_COMMISSION_RATE()` which is explicitly bound-checked [2](#0-1) .

The off-chain `kaiax/gasless` module's pre-inclusion validation (`checkBalanceForSwap`) only verifies `minAmountOut >= amountRepay` and that `amountIn >= gsr.getAmountIn(token, minAmountOut)` at the current on-chain exchange rate [6](#0-5) . This check is evaluated against the router's live state at validation/inclusion time; it does not lock in or otherwise protect the eventual `finalUserAmount` against a commission-rate change that lands in the same or an earlier block, before `swapForGas` executes. Because `updateCommissionRate` is an ordinary, non-timelocked owner transaction, a malicious or compromised owner can observe a pending `swapForGas` transaction (via the public mempool/tx pool) and front-run it with an `updateCommissionRate` call setting the rate to a very high value (up to 100%), causing the user's `finalUserAmount` to be reduced to near zero for that swap, while `amountRepay` to the proposer is still deducted as before.

### Impact Explanation
High. If the commission rate is raised to (or near) 100% immediately before a pending `swapForGas` transaction executes, the user pays away their input tokens (and the gas they borrowed is still repaid to the proposer) but receives little to no KAIA output — effectively the commission recipient (owner) can extract almost the entire swap proceeds from unsuspecting gasless-transaction users, analogous to the reported `PumpV1.setFeeRate` issue where an unbounded fee rate lets the admin capture the recipient's expected proceeds.

### Likelihood Explanation
Low-to-Medium. This requires control of, or compromise of, the `GaslessSwapRouter` owner key, and the ability to observe pending `swapForGas` transactions and land a front-running `updateCommissionRate` transaction before them — same precondition (malicious/compromised privileged party) as in the original report. This is reachable purely through normal transaction submission (owner tx + user's public `swapForGas` tx), without requiring any node/validator/network-level compromise.

### Recommendation
Add an upper bound (e.g., a `MAX_COMMISSION_RATE` constant, similar to `PublicDelegation.MAX_COMMISSION_RATE`) enforced inside `updateCommissionRate`, and/or introduce a time-delayed/queued parameter change (e.g., only effective after N blocks) so pending `swapForGas` transactions cannot be front-run by an instantaneous commission-rate change. Additionally, consider having `swapForGas` accept a caller-supplied maximum acceptable commission rate (analogous to `minAmountOut` slippage protection) so that unexpected owner-side rate changes cause the transaction to revert instead of silently reducing the user's payout.

### Proof of Concept
Note: this analysis is based only on the generated Go bindings/ABI for `GaslessSwapRouter` and the `kaiax/gasless` off-chain module; the actual `GaslessSwapRouter.sol` source file was not found in the indexed codebase, so the exact arithmetic order of the commission deduction inside `swapForGas` (i.e., whether it is taken before or after the `minAmountOut` check) could not be directly confirmed from source and is inferred from the `SwappedForGas` event fields and the off-chain module's validation logic. Conceptual PoC:
1. User A submits `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` to the public transaction pool, expecting `finalUserAmount ≈ amountOut - amountRepay - commission(currentRate)`.
2. Owner observes this pending transaction and submits `updateCommissionRate(1e18)` (or the maximum representable rate) with higher priority/gas so it lands first.
3. `swapForGas` executes using the new, elevated commission rate; `amountRepay` is still paid to the proposer, but `finalUserAmount` delivered to User A is drastically reduced, diverting the difference to the commission recipient — matching the `SwappedForGas` event's `commission` field spiking relative to `finalUserAmount`.
