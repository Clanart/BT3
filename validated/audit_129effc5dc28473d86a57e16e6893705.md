### Title
Missing `chain_id` and `verifying_contract` in EIP-712 Domain Allows Cross-Deployment Replay of Withdrawal Authorization Signatures — (File: `core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

The `CLEMENTINE_EIP712_DOMAIN` used to authenticate withdrawal and optimistic-payout authorization signatures omits both `chain_id` and `verifying_contract`. A valid aggregator-signed authorization for one Clementine deployment is therefore cryptographically indistinguishable from one for any other deployment that shares the same aggregator key, enabling cross-deployment and cross-network replay of the gating signature that controls whether an operator will front a withdrawal.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

EIP-712 requires `chain_id` to scope a signature to a specific EVM chain and `verifying_contract` to scope it to a specific contract instance. Both fields are absent here.

This domain is used in `recover_address_from_ecdsa_signature` to reconstruct the signer address from the `verification_signature` field of `WithdrawParamsWithSig` and `OptimisticWithdrawParams`:

```rust
let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);
let address = signature.recover_address_from_prehash(&eip712_hash)…;
``` [2](#0-1) 

The recovered address is then compared to `aggregator_verification_address` in the operator's config:

```rust
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    …
    if address_from_sig != address_in_config {
        return Err(BridgeError::InvalidECDSAVerificationSignature)…;
    }
}
``` [3](#0-2) 

The signed payload covers `withdrawal_id`, `input_signature`, `input_outpoint_txid`, `input_outpoint_vout`, `output_script_pubkey`, and `output_amount`: [4](#0-3) 

Because the domain carries no `chain_id`, the same signature is valid on every EVM chain (Citrea testnet4 chain-id 5115, Citrea mainnet, any future fork). Because it carries no `verifying_contract`, the same signature is valid against every Clementine operator deployment that uses the same aggregator key, regardless of which Citrea bridge contract address they point to. Both values are already present in the codebase: `citrea_chain_id` is in `BridgeConfig` and `BRIDGE_CONTRACT_ADDRESS` is a well-known constant.

---

### Impact Explanation

The `verification_signature` is the sole cryptographic gate that prevents an unauthorized party from directing an operator to front a withdrawal. If a valid signature obtained from one deployment (e.g., testnet4) can be replayed on another (e.g., mainnet, or a second bridge instance on the same network), the authorization invariant is broken.

Concrete scenario: the aggregator signs a withdrawal authorization for a testnet4 withdrawal. An attacker captures that signature. If Citrea undergoes a hard fork, or if a second Clementine bridge instance is deployed on the same Bitcoin network with the same aggregator key, the attacker replays the captured signature to the mainnet/second-instance operator. The operator's signature check passes. The operator then proceeds to check the Citrea bridge contract for the withdrawal — but on a fork both chains share the same state at the fork point, so the withdrawal entry exists on both. The operator fronts the withdrawal on the unintended chain, spending real BTC collateral for a reimbursement path that may not exist or may be contested.

The impact is bounded by the fact that the signed message includes a Bitcoin `input_outpoint` (txid + vout), which is network-specific in practice (mainnet and testnet4 UTXOs never collide). This makes cross-network replay practically infeasible under normal conditions. However, in a fork scenario the UTXO set is identical at the fork point, making replay directly feasible. For same-network cross-deployment replay, the attacker needs the same UTXO registered in both bridge contracts, which is contrived but not impossible if the same deposit UTXO is processed by two bridge instances.

---

### Likelihood Explanation

- The `aggregator_verification_address` check is **optional** (guarded by `if let Some(...)`), so deployments that omit it are unaffected.
- Exploiting cross-network replay requires a Citrea fork or a future mainnet deployment that reuses the same aggregator key and has overlapping state — a realistic but not everyday condition.
- Same-network cross-deployment replay requires two bridge instances sharing an aggregator key and a common UTXO registration, which is operationally unlikely but not impossible.
- The Citrea chain-id (`5115` for testnet4) and bridge contract address are both available in the config and could trivially be added to the domain.

Overall likelihood: **Low-Medium** under current deployment conditions; elevated to **Medium** if a Citrea fork occurs or multiple bridge instances share an aggregator key.

---

### Recommendation

Add `chain_id` and `verifying_contract` to `CLEMENTINE_EIP712_DOMAIN`. Both values are already available in `BridgeConfig`:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
    chain_id: <citrea_chain_id from config>,
    verifying_contract: <bridge_contract_address from config>,
};
```

Because the domain is currently a `static`, it must be converted to a runtime-constructed value (or a `lazy_static`/`OnceLock`) that reads `citrea_chain_id` and `bridge_contract_address` from `BridgeConfig` at startup. All callers of `recover_address_from_ecdsa_signature` and `sign_withdrawal_verification_signature` must pass the domain as a parameter rather than using the global static.

---

### Proof of Concept

1. Deploy two Clementine instances (A and B) on the same Bitcoin network, both configured with the same `aggregator_verification_address` key.
2. On instance A, the aggregator signs a `WithdrawParamsWithSig` for withdrawal `id=0`, UTXO `txid:vout`, amount `X`, destination `D`.
3. Register the same UTXO in instance B's Citrea bridge contract (or wait for a fork where both contracts share state).
4. Send the captured `WithdrawParamsWithSig` (with the same `verification_signature`) to instance B's operator RPC.
5. Instance B's operator calls `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` with the same domain — the recovered address matches `aggregator_verification_address` because the domain is identical.
6. Instance B's operator proceeds to front the withdrawal, spending BTC collateral on a reimbursement path that was only authorized for instance A.
