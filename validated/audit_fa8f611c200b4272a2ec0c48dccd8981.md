### Title
BIP-340 Schnorr output negates only `s` for odd-Y `R` and never accounts for group-key parity, producing invalid/unspendable signatures ~50% of the time - (File: networks/bitcoin/src/crypto.rs)

### Summary
The bug class of the external report is a hidden path that emits sensitive/incorrect material while appearing to function normally. The analog in Serai's in-scope code is the Bitcoin BIP-340 wrapper around the FROST Schnorr algorithm in `networks/bitcoin/src/crypto.rs`. Its `verify` assembles the aggregate signature `(R, sum)` where `sum = r_agg + e·x_agg`, then applies a single corrective transformation — `s = conditional_select(sum, -sum, needs_negation(sig.R))` — before serializing to a 64-byte BIP-340 signature. It performs no handling of the x-only group key's parity.

### Finding Description
In `crypto/frost/src/algorithm.rs`, `sign_share` computes the challenge `c = H::hram(nonce_sums[0][0], group_key, msg)` and each share as `d_i + c·x_i`, so the aggregate satisfies `sum·G = R + c·P` for the full (un-normalized) points `R` and `P`. BIP-340 verification, however, is defined entirely over x-only points: it checks `s·G == lift_x(R.x) + e·lift_x(P.x)`, where `lift_x` always yields the even-Y representative.

`Schnorr::verify` at `networks/bitcoin/src/crypto.rs:139-150` does:

```rust
self.0.verify(group_key, nonces, sum).map(|mut sig| {
  sig.s = <_>::conditional_select(&sum, &-sum, needs_negation(&sig.R));
  sig.serialize()[1 ..].try_into().unwrap()
})
```

Negating the whole scalar `sum` flips the sign of *both* terms: `-sum·G = (-R) + e·(-P)`. This is only the correct BIP-340 equation when the group key `P` is *also* odd-Y (i.e. `lift_x(P.x) = -P`). The four cases:

| `R` parity | `P` parity | emitted `s` | `s·G` vs `R' + e·P'` | result |
|---|---|---|---|---|
| even | even | `s` | `R + e·P` | valid |
| odd | odd | `-s` | `(-R) + e·(-P)` | valid |
| even | odd | `s` | `R + e·P` vs `R - e·P` | **invalid** |
| odd | even | `-s` | `-R - e·P` vs `-R + e·P` | **invalid** |

Nothing negates the secret shares (or the signers' nonce shares) when `lift_x(P.x) = -P`. The correct construction requires the key-parity mismatch to be absorbed by negating the `e·x_i` contribution (equivalently signing against `-P`), and the `R` parity by negating each nonce share — not by post-hoc negation of the aggregate `s`. As written, validity depends on the parities coincidentally matching, which holds only ~50% of the time.

### Impact Explanation
Roughly half of all threshold-signing sessions produce a signature that fails BIP-340 verification on-chain. For a Taproot/tweaked output controlled by the multisig, a spend whose sighash yields mismatched parities results in an invalid witness: the funds are reported/signable by the protocol but the transaction cannot actually broadcast — an instance of "funds reported received/signed that are not spendable" per the validation criteria, plus a liveness/DoS on the signing pipeline.

### Likelihood Explanation
Reachable by an unprivileged party through public inputs: the parity of `R` depends on the aggregated nonce commitments and on the message (any transaction/sighash an external party causes to be signed); the parity of `P` is fixed per group key, so a multisig whose group key is odd-Y fails on ~50% of messages, and an even-Y key fails the other ~50%. Either way, a substantial fraction of signing rounds emit invalid signatures with no error surfaced — `verify` returns `Some(sig)` unconditionally once the internal Schnorr check on the un-normalized equation passes.

### Recommendation
Handle both parity adjustments inside the algorithm: when `needs_negation(group_key)` (i.e. `lift_x(P.x) != P`), treat the effective secret as `-x` during share computation (or fold the negation into `hram`/share assembly), and when `needs_negation(R)`, negate each signer's nonce share before aggregation rather than negating the final `sum`. At minimum, `verify` must condition `s`-negation on `needs_negation(R) XOR needs_negation(group_key)` — equivalently emit `s` adjusted so that `s·G = lift_x(R.x) + e·lift_x(P.x)`.

### Proof of Concept
1. Build a `ThresholdKeys<Secp256k1>` set whose group key `P = sum·G` has odd Y (trivially satisfiable — ~50% of keys; no tweak needed).
2. Run `AlgorithmMachine<Secp256k1, Schnorr>` with `Schnorr::new()` over any message `m` such that the aggregated `R = nonce_sums[0][0]` has even Y (again ~50% of preprocess sets).
3. `verify` returns `Some(sig)` with `s = sum` unchanged. BIP-340 verification computes `e = H(R.x || P.x || m)` and checks `s·G == lift_x(R.x) + e·lift_x(P.x) = R - e·P`, but `s·G = R + e·P`. The signature fails verification despite `verify` having accepted it — an invalid witness for the output, directly confirming the missing key-parity negation at `networks/bitcoin/src/crypto.rs:145-149`.
