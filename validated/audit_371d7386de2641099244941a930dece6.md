### Title
Attacker can flood the Serai Bitcoin key with uneconomical dust outputs which are reported as received yet cannot be profitably or safely spent - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`Scanner::scan_transaction` / `scan_block` return every transaction output whose `script_pubkey` matches a registered script, with no minimum-value filter (`networks/bitcoin/src/wallet/mod.rs:199-227`). `SignableTransaction::new` then accepts the `Vec<ReceivedOutput>` it is given verbatim: it enforces `DUST` (546 sats) only on *payments*, never on *inputs* (`send.rs:165-169`), and unconditionally fails once total weight exceeds `MAX_STANDARD_TX_WEIGHT` (`send.rs:241-243`). Anyone can send tiny P2TR outputs to the Serai multisig's scan key (the zero-offset script registered in `Scanner::new`, `mod.rs:163-166`) at negligible cost, inflating the UTXO set that must later be swept.

### Finding Description
Analogous to the Teller issue (an unprivileged party grows an attacker-controlled set that a later, mandatory iteration must traverse), any external party can grow the set of `ReceivedOutput`s matched by `Scanner` simply by broadcasting Bitcoin transactions paying to the Serai key's script. No access control exists — this is a public blockchain. Each received output becomes a mandatory `TxIn` when it is spent (`send.rs:177-185`), adds ~58 vbytes of weight, requires its own FROST preprocess/sign/complete in `TransactionMachine` (`send.rs:275-395`), and is committed to via `Prevouts::All` (`send.rs:375`). There is no check anywhere in-scope that an input's value exceeds the marginal fee needed to spend it, nor a bound on input count; once enough dust accumulates, a sweeping transaction either exceeds the standardness weight limit and fails with `TooLargeTransaction`, or must pay fees exceeding the inputs' value.

### Impact Explanation
Dust-valued outputs are reported as received funds yet are effectively unspendable: spending a sub-546-sat output costs more in fees than its value at moderate fee rates, so the wallet either loses value by including it or the output is stranded permanently. At scale, an attacker inflating the UTXO set forces every consolidation transaction toward `MAX_STANDARD_TX_WEIGHT`, multiplying the number of signing sessions and fees needed to recover funds — a griefing vector where trapped/inaccessible value is created for a few hundred sats per output.

### Likelihood Explanation
The attacker needs only to send Bitcoin transactions to a publicly known address — no protocol privilege, validator status, or malformed input is required. Cost is the per-output dust amount plus miner fees, exactly the "extremely low cost attack" profile of the original finding. Whether the scheduler does input selection mitigates the weight-limit branch, but the uneconomical-input branch is unavoidable within this crate since `SignableTransaction::new` performs no input-value check.

### Recommendation
Filter out or quarantine outputs below a profitability threshold in `Scanner`/`ReceivedOutput` handling (e.g. value < cost to spend at a reference fee rate), and/or enforce a maximum input count and a per-input value check in `SignableTransaction::new` so the caller is forced to perform economical coin selection rather than silently accepting loss-making inputs.

### Proof of Concept
1. Take the Serai multisig key `K`; `Scanner::new(K)` registers `p2tr_script_buf(K)` (`mod.rs:163-166`).
2. Broadcast N transactions paying 330–545 sats to that script. `scan_block` returns N `ReceivedOutput`s (`mod.rs:221-227`).
3. Any `SignableTransaction::new` call including them either (a) burns fee > value for each input, or (b) with enough inputs returns `TooLargeTransaction` (`send.rs:241-243`), while the outputs remain recorded as received.
