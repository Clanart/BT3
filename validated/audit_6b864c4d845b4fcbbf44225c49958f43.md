The go-ethereum fix (PR #31407) sanitized an attacker/config-influenced numeric period before multiplying it by `time.Second` to build a `time.Duration`, because the multiplication could silently overflow Go's `int64`-backed `time.Duration`. The protobuf codebase has the same class of bug in the C++ Duration well-known-type utility: `google::protobuf::util::TimeUtil::DurationToNanoseconds` multiplies a value taken directly from a parsed (and JSON-parser-validated) `Duration` message by a fixed nanosecond scale, and the documented valid range of `Duration.seconds` is large enough to overflow `int64` when multiplied.

### Title
Signed integer overflow in `TimeUtil::DurationToNanoseconds` for in-range `Duration` values - (File: `src/google/protobuf/util/time_util.cc`)

### Summary
`google::protobuf::util::TimeUtil::DurationToNanoseconds()` computes `duration.seconds() * kNanosPerSecond + duration.nanos()` without any overflow check. `kDurationMaxSeconds` is `315576000000` [1](#0-0) , which is a value the JSON parser (`ParseDuration`) and every other language binding explicitly accepts as valid (`kMaxSeconds = 3652500 * 86400 == 315576000000`) [2](#0-1) . Multiplying this maximum valid value by `kNanosPerSecond` (1e9) produces `315576000000000000000`, which is roughly 34x larger than `INT64_MAX` (~9.22e18), causing signed integer overflow (undefined behavior in C++) [3](#0-2) .

### Finding Description
An attacker who can only send a bounded, well-formed ProtoJSON payload through the public `json_util`/`JsonStringToMessage` parsing API can populate a `google.protobuf.Duration` field with `seconds` at or near `315576000000` (e.g. `"optionalDuration": "315576000000s"`), which the JSON parser accepts as valid because it is exactly at the documented boundary `kMaxSeconds` [2](#0-1)  and also matches the conformance-suite's `DurationMaxValue` test [4](#0-3) .

Once such a message is in memory, any consuming application code that calls the public utility `TimeUtil::DurationToNanoseconds(duration)` [5](#0-4)  triggers:
```cpp
int64_t TimeUtil::DurationToNanoseconds(const Duration& duration) {
  ABSL_DCHECK(IsDurationValid(duration))
      << "Duration is outside of the valid range";
  return duration.seconds() * kNanosPerSecond + duration.nanos();
}
``` [3](#0-2) 

`IsDurationValid()` only checks that `seconds`/`nanos` are within `[kDurationMinSeconds, kDurationMaxSeconds]`/`[-999999999, 999999999]` and sign-consistent [6](#0-5)  — it does **not** check whether `seconds * kNanosPerSecond` fits in `int64_t`. The `ABSL_DCHECK` is a debug-only assertion; it compiles to a no-op in release/`NDEBUG` builds, so in production the multiplication silently overflows.

This mirrors exactly the invariant broken in the go-ethereum bug: a bounded, schema/spec-valid numeric value (the beacon period, here the Duration's `seconds`) is multiplied by a fixed scale factor (`time.Second`, here `kNanosPerSecond`) to build a duration-like integer, and the code fails to sanitize/bound-check the multiplication itself, only the input's nominal range.

The library's own header comment implicitly acknowledges this: "It's undefined behavior if the input duration is not valid or **the result exceeds the range of int64**." [7](#0-6)  — but this UB is reachable with a maximally-valid, spec-conforming `Duration`, not just an "invalid" one, because `315576000000 * 1e9` inherently exceeds `int64` regardless of validity.

Note that `DurationToMilliseconds`/`DurationToMicroseconds` do not overflow at the same boundary (`315576000000 * 1e3` and `* 1e6` both fit in `int64`), and the existing unit test explicitly exercises and asserts correctness only for those two conversions at the boundary, explicitly labeling them "Test overflow issue" [8](#0-7)  — but there is no equivalent test for `DurationToNanoseconds` at the maximum boundary, confirming the nanosecond-scale overflow path is untested and unguarded.

### Impact Explanation
Signed integer overflow is undefined behavior in C++; in practice this typically wraps to an implementation-defined (often garbage/negative) value. Any application logic that uses the (attacker-influenced) result of `DurationToNanoseconds` — e.g., for computing timeouts, deadlines, rate-limit windows, or scheduling sleeps/wakeups from a client-supplied `Duration` — would silently receive an incorrect, potentially negative or wildly wrong nanosecond value. Depending on how that value is consumed downstream, this can translate into logic/integrity failures such as premature/never-expiring timeouts, incorrect scheduling, or (analogous to the go-ethereum case) busy-loops/hangs if the corrupted value feeds a sleep/wait primitive.

### Likelihood Explanation
High likelihood of reachability: the boundary value `315576000000` is not an edge case requiring parser bypass — it is the documented maximum and is explicitly accepted by the JSON parser and conformance suite as a *valid* Duration. Any application that (a) accepts `Duration` via ProtoJSON from an external/untrusted client and (b) calls the standard `TimeUtil::DurationToNanoseconds` helper on it is exposed, with no additional attacker sophistication required beyond sending one JSON string field near the maximum.

### Recommendation
Add an explicit overflow check (or use `absl::int128`/saturating arithmetic, similar to the multiplication/division operators in this same file which already use `absl::uint128` to avoid overflow, e.g. `operator*=(Duration&, int64_t)` [9](#0-8) ) in `DurationToNanoseconds` (and any other conversion whose scale factor can overflow for legitimately in-range `Duration` values), returning an error/clamped result instead of silently invoking UB. Also promote the `ABSL_DCHECK` to a checked runtime validation (or perform the overflow check unconditionally) so release builds do not silently proceed with corrupted results.

### Proof of Concept
1. Trusted schema: any message with a `google.protobuf.Duration` field, e.g. `optional_duration`.
2. Attacker-controlled bounded ProtoJSON payload sent to the public parse API:
   ```json
   {"optionalDuration": "315576000000s"}
   ```
   This is accepted as valid by `ParseDuration` because `315576000000 <= kMaxSeconds` [2](#0-1) , matching the `DurationMaxValue` conformance test [4](#0-3) .
3. Application code (a plausible consuming pattern) calls:
   ```cpp
   int64_t ns = google::protobuf::util::TimeUtil::DurationToNanoseconds(msg.optional_duration());
   ```
4. Inside, `duration.seconds() * kNanosPerSecond` computes `315576000000 * 1000000000 = 315576000000000000000`, which exceeds `INT64_MAX` (9223372036854775807) by roughly 34x, producing signed integer overflow (UB) in the release build (where `ABSL_DCHECK` is compiled out) [3](#0-2) .

I did not execute this PoC in a sandbox; the overflow arithmetic is derived directly from the documented constants (`kDurationMaxSeconds = 315576000000` and `kNanosPerSecond = 1000000000`) and `int64_t` limits shown in the cited source.
