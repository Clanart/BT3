### Title
Bridge Circuit Accepts Operator Payout When Total Work Equals Watchtower's Max Work — (`File: circuits-lib/src/bridge_circuit/mod.rs`)

### Summary

The `bridge_circuit` function uses a strict less-than comparison (`<`) to guard against a watchtower's work exceeding the operator's work. When the operator's 128-bit `total_work` equals the watchtower's `max_total_work`, the circuit does **not** panic and the operator's payout is accepted. The protocol invariant — stated explicitly in both the inline documentation and the design doc — requires the operator to have **strictly greater** work than any valid watchtower challenger.

### Finding Description

In `circuits-lib/src/bridge_circuit/mod.rs`, after computing `max_total_work` from all valid watchtower Groth16 proofs, the circuit checks:

```rust
// If total work is less than the max total work of watchtowers, panic
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [1](#0-0) 

`TotalWork` is a newtype over `[u8; 16]` with a derived `PartialOrd`, giving correct big-endian lexicographic (i.e., numerical) ordering:

```rust
#[derive(Debug, Clone, Copy, PartialEq, PartialOrd, Eq, BorshDeserialize, BorshSerialize)]
pub struct TotalWork(pub [u8; 16]);
``` [2](#0-1) 

Both the operator's `total_work` and the watchtower's `max_total_work` are the **lower 128 bits** of the full 256-bit accumulated work:

- Operator side: `input.hcp.chain_state.total_work[16..32]` (bytes 16–31 of the 32-byte big-endian value)
- Watchtower side: `work_conversion` in the work-only circuit truncates to the lower 128 bits via `let (_, work): (U128, U128) = work.into()` [3](#0-2) [4](#0-3) 

The design documentation and the function's own doc-comment both state the required invariant as **strictly greater**:

> "Asserts that the Operator's `total_work` from their HCP is **greater than** the `max_total_work` from the Watchtowers." [5](#0-4) 

> "If `max_total_work` given by watchtowers is **greater than** `hcp.chain_state.total_work`." [6](#0-5) 

The boundary case `total_work == max_total_work` is silently accepted.

### Impact Explanation

When a watchtower submits a valid work-only Groth16 proof whose 128-bit total work equals the operator's 128-bit total work, the circuit does not panic. The operator's payout transaction is accepted by the bridge circuit even though the watchtower has demonstrated an equally-weighted competing chain. Under the protocol's canonical-chain rule, equal work means neither chain is definitively canonical; the operator has not proven their chain dominates. An operator on a fork whose lower-128-bit work collides with the canonical chain's value can therefore claim a payout for a withdrawal that was never legitimately settled on the canonical chain, resulting in loss of bridged BTC.

### Likelihood Explanation

For Bitcoin mainnet today, total accumulated work is approximately 2^95, well within 128 bits, so the upper 128 bits of the 256-bit work field are all zero. This means the 128-bit truncation is lossless and two genuinely different chains would need to accumulate exactly the same total work — essentially impossible in practice. On a regtest or controlled test network, however, an operator can mine blocks to engineer an exact 128-bit work collision. The likelihood is therefore **very low** on mainnet but **feasible** in test/staging environments, and the invariant is unconditionally broken at the code level regardless of network.

### Recommendation

Change the comparison from strict less-than to less-than-or-equal, so that equal work also causes the circuit to panic:

```rust
// Operator must have STRICTLY MORE work than the best watchtower challenger
if total_work <= max_total_work {
    panic!(
        "Insufficient total work: operator {total_work:?} must exceed watchtower max {max_total_work:?}",
    );
}
``` [1](#0-0) 

This aligns the code with the documented invariant and eliminates the boundary-equality bypass.

### Proof of Concept

1. On regtest, mine two chains A (operator) and B (watchtower) from the same genesis such that both accumulate exactly the same number of blocks with the same difficulty target. Their 128-bit total work values will be identical.
2. Operator constructs a `BridgeCircuitInput` with HCP over chain A (containing a payout tx) and a `WatchtowerInput` carrying a valid work-only Groth16 proof over chain B with the same `total_work`.
3. `total_work_and_watchtower_flags` returns `TotalWork(X)` for the watchtower.
4. The operator's `total_work` is also `TotalWork(X)`.
5. The check `if total_work < max_total_work` evaluates to `X < X` → `false` → no panic.
6. The circuit completes successfully and commits a `journal_hash`, allowing the operator to claim the payout on a chain the watchtower has equally challenged. [7](#0-6)
