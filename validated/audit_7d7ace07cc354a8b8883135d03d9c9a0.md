Based on my investigation, I found `clear_pending_roots` in `chia/data_layer/data_layer_rpc_api.py` lacks the ownership check present in `batch_insert`.## Title
Missing store-ownership check in `clear_pending_roots` allows a Data Layer client to delete another store's pending root/data - (File: `chia/data_layer/data_layer_rpc_api.py`)

### Summary
`chia/data_layer/data_layer.py`'s `batch_insert()` explicitly re-validates that a `store_id` is owned by the local DataLayer wallet before mutating anything: `"check before any DL changes that this singleton is currently owned by this wallet"` [1](#0-0) . The `clear_pending_roots` RPC endpoint, by contrast, performs no such check — it takes a caller-supplied `store_id` and deletes the pending root directly.

### Finding Description
`DataLayerRpcApi.clear_pending_roots` simply forwards the request to `DataStore.clear_pending_roots(store_id=...)` with no ownership/ACL verification: [2](#0-1) .

`DataStore.clear_pending_roots` then unconditionally deletes any `PENDING`/`PENDING_BATCH` root row for the given `store_id`: [3](#0-2) .

This is inconsistent with the rest of the mutation surface. `batch_insert()` — the primary mutation entry point reachable via `/insert`, `/delete_key`, `/batch_update`, and `/multistore_batch_update` — fetches `get_owned_stores()` and raises `ValueError` if the `store_id` is not owned by the local DL wallet before allowing any change: [4](#0-3) . Likewise `DataLayerWallet.delete_mirror()` requires a derivation record for the mirror's parent puzzle hash, i.e. proof of key ownership, before it will spend/delete a mirror coin: [5](#0-4) .

`clear_pending_roots` has no analogous guard. Any caller who can reach the Data Layer RPC (a "Data Layer client" per the threat model) can pass an arbitrary `store_id` — including a store this DL service is only *subscribing to* / mirroring, not one it owns — and cause the service to delete that store's in-progress `PENDING`/`PENDING_BATCH` root row. Per the module's own invariant notes, "Root status drives publication state: `COMMITTED` is local confirmed/canonical, `PENDING` is ready/submitted for chain publication, and `PENDING_BATCH` is an open local batch not yet publishable" [6](#0-5) , and "Only one pending root is expected; multiple pending roots are an error" [6](#0-5) . Deleting the wrong store's pending row silently discards uncommitted batch work for a store the caller does not own, and is functionally analogous to the memos advisory's core defect: an endpoint that mutates/deletes another party's resource because it trusts a caller-supplied identifier without checking ownership.

### Impact Explanation
An unauthorized `clear_pending_roots` call can wipe a pending (unsubmitted) batch update or an already-submitted-but-unconfirmed root for a store the caller does not own, causing loss of uncommitted local data/state and requiring the legitimate owner to redo batch work. This maps to the "coin-set divergence between honest nodes" / local state corruption category insofar as it desynchronizes the local `DataStore` from what the actual store owner intended to publish, though it does not directly enable forged asset identity or unauthorized coin movement on-chain (the on-chain singleton state itself is unaffected; only the local pending-batch bookkeeping is deleted).

### Likelihood Explanation
The Data Layer RPC is intended to be operator/local-only, similar to other Chia service RPCs, so exploitation requires a caller who can reach the `/clear_pending_roots` route. Within that trust boundary, the omission is trivial to trigger: it requires only a single RPC call with an arbitrary `store_id` hex string, no signature, and no coordination with mempool/consensus.

### Recommendation
Add the same ownership check used by `batch_insert()` to `clear_pending_roots` before deleting a pending root — i.e., verify `store_id` is present in `self.get_owned_stores()` (or, if intentionally allowed for non-owned/subscribed stores, scope the change to only stores in a state the operator is authorized to reset) and raise if not, mirroring: [1](#0-0) 

### Proof of Concept
1. Run a DataLayer service subscribed to (but not owning) `store_id = S` belonging to another party, alongside an owned store the operator does control.
2. Have the remote store `S` in a state with a `PENDING`/`PENDING_BATCH` root (e.g. it just performed a batch update it hasn't yet confirmed).
3. Call the RPC directly: `await data_rpc_api.clear_pending_roots({"store_id": S.hex()})`, as exercised (without any ownership assertion) in the existing test `test_clear_pending_roots` [7](#0-6) .
4. Observe the pending root row for `S` is deleted (`pending_root = await data_store.get_pending_root(store_id=S)` becomes `None`), even though the caller does not control the launcher singleton for `S`, contrasting with `batch_insert`'s owner check that would reject a mutation request for the same non-owned `S`.

    async def clear_pending_roots(self, store_id: bytes32) -> Root | None:
        async with self.db_wrapper.writer() as writer:
            pending_root = await self.get_pending_root(store_id=store_id)

            if pending_root is not None:
                await writer.execute(
                    "DELETE FROM root WHERE tree_id == :tree_id AND status IN (:pending_status, :pending_batch_status)",
                    {
                        "tree_id": store_id,
                        "pending_status": Status.PENDING.value,
                        "pending_batch_status": Status.PENDING_BATCH.value,
                    },
                )

        return pending_root
