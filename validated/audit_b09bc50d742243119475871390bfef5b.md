## Analysis

The seed report's broken invariant is: *a value checked at one point in time (price) is used to authorize an action at a later point in time (settlement), and the attacker can shift that value in the gap.* The closest structural analog in GitHub Desktop is in the **partial-commit staging pipeline**, where the *line-selection state* the user builds against one diff snapshot is later re-applied, by absolute line index, against a **freshly re-fetched diff** of the same file taken at commit time — with no check that the two diffs still describe the same hunk layout.

### Title
Stale line-index diff selection allows silent corruption of partially-staged commits - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user selects individual lines/hunks of a modified file to include in a commit ("partial commit"), GitHub Desktop stores the selection as a set of **absolute line indices** into the diff that was on screen at selection time. When the commit is actually created, `applyPatchToIndex` does **not** reuse that diff — it fetches a brand-new diff of the file from disk and reapplies the old index-based selection against it [1](#0-0) . If the file's hunk layout has shifted since the selection was made (fewer/more lines earlier in the file), the same numeric indices now point at different, semantically unrelated lines, and `formatPatch` will silently build a syntactically valid patch that includes/excludes the wrong content [2](#0-1) .

### Finding Description
`formatPatch` decides whether a diff line is committed purely via `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` computed against **whatever diff object is passed in** [3](#0-2) . `applyPatchToIndex` always supplies a **freshly fetched** diff (`getWorkingDirectoryDiff`) rather than the diff the UI used when the user made their selections [4](#0-3) .

The only place selection state is reconciled against diff changes is `updateChangesWorkingDirectoryDiff`, and it only prunes indices that no longer exist — it does not detect that the *meaning* of surviving indices has shifted, and it only runs for the single file currently displayed in the Changes view, not for every file about to be staged [5](#0-4) . `stageFiles` then applies every partially-selected file's `applyPatchToIndex` sequentially, each doing its own independent, un-synchronized diff refetch [6](#0-5) .

Because `git apply --cached` validates the patch against the *current* index/working tree and the freshly-fetched diff is always self-consistent with the current file, the applied patch **always succeeds** — there is no error or warning when the index-to-line mapping has silently drifted. The result is a commit that includes lines the user never selected, or omits lines they did select, with no indication to the user.

### Impact Explanation
This is "silent corruption of what the user commits or pushes" — an explicitly in-scope impact. A user who carefully reviews a diff and selects only specific lines for a commit (a core, security-relevant Desktop workflow — e.g., splitting a fix from unrelated debug code, or deliberately excluding a secret/credential line from a commit) can end up pushing a commit whose actual content differs from what they reviewed and approved, without any error being surfaced. Depending on what shifted into the selection, this can leak content the user intentionally excluded (e.g., a credential or debug statement) or drop content they meant to include.

### Likelihood Explanation
The race window is the entire span between "user makes a line selection in the Changes view" and "user clicks Commit," which in practice can be seconds to minutes. Any process that touches the same file in that window — an editor autosave, a linter/formatter-on-save, a file watcher (webpack/nodemon), or content generated by a build step defined inside the cloned repository itself — shifts hunk boundaries and triggers the bug without any special local privileges, malware, or unusual user action; this is normal developer tooling operating on content that originates from the repository the attacker controls. No existing guard (context-line diffing, hash comparisons of the pre-selection diff, or a "diff changed, please re-review" prompt) exists to catch this at the exact moment of staging.

### Recommendation
Before calling `applyPatchToIndex`, compare the diff that produced the current `DiffSelection` against the freshly fetched diff (e.g. via the existing `textDiffEquals`/`isSameDiff` helpers already used in `seamless-diff-switcher.tsx` [7](#0-6) ). If the two differ, abort the partial-commit apply for that file and force the user to re-review the current diff and re-establish their selection instead of silently reapplying stale indices to new content.

### Proof of Concept
1. Open a modified file in GitHub Desktop's Changes view and select only a specific added line (e.g., line 40 of a 60-line hunk) for commit, leaving everything else unselected.
2. Before clicking "Commit", have any file watcher/build tool that is part of the repository's normal tooling (or simply another editor) insert or remove lines earlier in the same file, shifting subsequent line numbers.
3. Click "Commit". `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches the new diff and `formatPatch` reapplies the old absolute-index selection (`app/src/lib/patch-formatter.ts:143-157`) against it.
4. `git apply --cached` succeeds silently. Inspect the resulting commit: it includes a different line than the one the user selected in the UI, with no warning shown.
