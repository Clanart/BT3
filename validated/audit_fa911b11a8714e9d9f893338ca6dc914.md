### Title
`ThresholdKeys::read` accepts a serialized key file whose secret share is inconsistent with the verification shares, letting a file-writing attacker substitute key material they fully know - (File: crypto/dkg/src/lib.rs)

### Summary
The analog of CVE-2020-18185 (arbitrary control via modification of a trusted configuration file) in Serai is the threshold-key "configuration file": `ThresholdKeys::serialize`/`ThresholdKeys::write` produce the persisted form of a node's DKG output, and `ThresholdKeys::read` reconstructs it. An unprivileged party who can feed crafted bytes to `ThresholdKeys::read` obtains a `ThresholdKeys` whose `secret_share` is an attacker-chosen scalar while the group key and other participants' verification shares remain those of the real group, because `ThresholdKeys::new` never checks `secret_share * G == verification_shares[i]`. The node then signs FROST shares with a secret the attacker knows, under the group's real key.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, `i`, the interpolation method, `secret_share`, and `n` verification shares from raw bytes, then calls `ThresholdKeys::new` [1](#0-0) . `ThresholdKeys::new` validates only structural properties: share count equals `n`, participant indexes are `<= n`, and constant interpolation requires `t == n` [2](#0-1) . It then derives `group_key` by interpolating only the verification shares of participants `1..=t` [3](#0-2)  — the `secret_share` is never related to `verification_shares[i]`, and `i` is not required to be `<= t`.

Two distinct injections follow:

1. **Known-share injection**: set `i` to any participant index, `verification_shares[i] = G * s'` for an attacker-chosen `s'`, keep all other verification shares (and hence the structure) attacker-controlled but self-consistent. The node signs every FROST share with `s'` — a secret the attacker knows — so every signature share and its implied contribution to aggregate signatures is computable by the attacker. Choosing `i > t` additionally lets the attacker preserve the victim's `group_key()` (computed from shares `1..=t`), so the node believes it is signing for the legitimate group key while using a share the attacker selected.
2. **Index/role reassignment**: rewrite `i` to a different participant index while leaving `secret_share` as participant `i_original`'s share. `view()` only checks `i ∈ included` and duplicate/sortedness of `included` [4](#0-3) , so the node interpolates and signs under an index whose verification share doesn't match its secret — or, combined with a rewritten `verification_shares[i]`, produces valid-looking shares for an attacker-shaped key set.

In FROST signing, `view()` interpolates `secret_share` and scales `verification_shares` for the included set without ever binding the two [5](#0-4) , and `sign` uses `view.secret_share()` directly. Nothing downstream detects that the persisted share doesn't match the persisted verification share, since both came from the same tampered file.

### Impact Explanation
The node's key file is the analog of PluXml's `config.php`: a trusted persisted configuration whose modification grants the writer control over the application's privileged operation — here, threshold signing rather than PHP execution. Concretely:

- The attacker dictates the scalar the victim uses as its FROST secret share. If the attacker sets `secret_share` to a known value, they can compute the victim's signature share for any `(preprocess set, message)` and, combined with the verification-share manipulation, produce threshold-valid signatures under a group key the attacker shaped — i.e., signing of unintended messages under what the node believes is the group key.
- Equivalently, the attacker can set the entire polynomial image (`verification_shares` for `1..=t`) so `group_key()` becomes a key whose discrete log the attacker knows, redirecting any subsequent signing and any funds/outputs attributed to `group_key()` to attacker control.

### Likelihood Explanation
`ThresholdKeys::read` is explicitly in scope as a sink for untrusted bytes. The attack requires only a write to the serialized key material — exactly the "modify the configuration file" primitive of the reference CVE — not a colluding validator, leaked key, or broken BFT assumption. The missing check is unconditional: `ThresholdKeys::new` performs no `G * secret_share == verification_shares[i]` consistency proof, so any tampered file that is internally self-consistent is accepted.

### Recommendation
In `ThresholdKeys::new`, after validating parameters, verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. This binds the secret share to the committed verification share, making a tampered file either detectable or requiring knowledge of a real share's discrete log. Optionally bind a hash/MAC of the key file to the DKG transcript so silent substitution is also detectable across restarts.

### Proof of Concept
```rust
// Attacker writes a key file for the victim with a share they know.
// C = Ristretto (or any in-scope ciphersuite), n = 3, t = 2.

let mut buf = vec![];
// curve ID
buf.extend((Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID);
// t = 2, n = 3, i = 3  (i > t keeps group_key derived from shares 1..=2)
buf.extend(2u16.to_le_bytes());
buf.extend(3u16.to_le_bytes());
buf.extend(3u16.to_le_bytes()); // Participant i = 3
// Interpolation::Lagrange
buf.push(1);

// Attacker-chosen secret share
let s_evil = Scalar::from(0xdeadbeefu64);
buf.extend(s_evil.to_repr().as_ref());

// verification shares: attacker-known polynomial evaluated at 1,2,3,
// e.g. f(x) = s_evil-ish; simplest: all = G * s_evil is NOT needed —
// attacker uses any polynomial whose f(3) = s_evil.
// Simplest consistent choice: constant polynomial f(x) = s_evil
for _ in 1 ..= 3 {
    buf.extend((Ed25519point::generator() * s_evil).to_bytes().as_ref());
}

let keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice()).unwrap();
// Accepted: no check that G * secret_share == verification_shares[i] fails
// (here it happens to hold, but nothing enforced it — the attacker also
// could have set verification_shares[3] = G * s_evil while shares 1..=2
// encode the REAL group's key image, keeping group_key() = real group key
// while secret_share = s_evil).

// Victim now calls keys.view(included).secret_share() == interpolated s_evil,
// and frost SignMachine signs with a scalar the attacker fully knows.
```

The critical line missing from `ThresholdKeys::new` is a check equivalent to `assert_eq!(C::generator() * secret_share.deref(), verification_shares[&params.i()])`; without it, deserialized "configuration" directly controls the signing secret.
