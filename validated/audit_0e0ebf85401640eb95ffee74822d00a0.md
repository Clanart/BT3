### Title
Bridge Circuit Accepts Equal-Work Operator Proof, Violating Strict-Greater-Than Invariant — (`File: circuits-lib/src/bridge_circuit/mod.rs`)

### Summary

The `bridge_circuit` function in `circuits-lib/src/bridge_circuit/mod.rs` uses a strict `<` comparison to check whether the operator's total work exceeds the maximum watchtower work. When both values are equal (a tie), the circuit does **not** panic and the operator's proof is accepted. The protocol specification and module documentation both require the operator's work to be **strictly greater than** the watchtower's maximum work. This is a direct analog of the external `OneVsOneExactPrice` bug: the tie case is silently absorbed into the "operator wins" branch instead of being rejected.

---

### Finding Description

In `circuits-lib/src/bridge_circuit/mod.rs`, the work comparison is:

```rust
// If total work is less than the max total work of watchtowers, panic
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [1](#0-0) 

The condition only panics (rejects the proof) when `total_work < max_total_work`. When `total_work == max_total_work`, the `if` branch is not taken and the circuit continues to completion, producing a valid journal commitment.

The protocol specification in `docs/bridge-circuit.md` explicitly states:

> "Asserts that the Operator's `total_work` from their HCP is **greater than** the `max_total_work` from the Watchtowers." [2](#0-1) 

The module-level docstring for `bridge_circuit` also states:

> "ensures that an operator's claimed Bitcoin chain state is valid and that it has **more** cumulative proof-of-work than any challenging watchtower." [3](#0-2) 

The `TotalWork` type is a 16-byte (`[u8; 16]`) value derived from the lower 16 bytes of the HCP's 32-byte `total_work` field:

```rust
let total_work: TotalWork = input.hcp.chain_state.total_work[16..32]
    .try_into()
    .expect("Cannot fail");
``` [4](#0-3) 

The watchtower's `max_total_work` is also a 16-byte value (`work_u128`) extracted from the OP_RETURN data of the watchtower challenge transaction and verified via Groth16: [5](#0-4) 

Both values are 128-bit truncations of the full 256-bit cumulative work. The `TotalWork` struct derives `PartialOrd` from `[u8; 16]`, so the comparison is lexicographic over the 16 bytes.

---

### Impact Explanation

The bridge circuit is the ZK proof an operator submits (via RISC Zero) when challenged. A valid circuit output (committed `journal_hash`) is the prerequisite for the operator to survive a BitVM2 challenge and collect their reimbursement for a payout transaction. If the circuit accepts an operator whose chain has only **equal** work to the canonical chain proven by a watchtower, the operator is not definitively on the canonical chain — they could be on a fork chain of equal weight. Their payout transaction may exist only on that fork, meaning the withdrawal they fronted was never finalized on the canonical Bitcoin chain. Accepting such a proof allows a fraudulent withdrawal to be treated as valid, resulting in loss of bridged BTC from the bridge's collateral pool.

---

### Likelihood Explanation

For the tie to occur, the lower 128 bits of the operator's HCP cumulative work must exactly equal the 128-bit `work_u128` committed by a watchtower's valid Work-Only Proof. In production Bitcoin, this requires two chains to have identical lower-128-bit cumulative work — extremely unlikely to occur naturally. However:

1. The protocol's security model must not rely on probabilistic arguments; the invariant is stated as strict inequality and the code violates it.
2. The 128-bit truncation (bytes 16–32 of the 32-byte work field) makes collisions more feasible than a full 256-bit comparison, particularly in low-difficulty environments (regtest, signet, testnet4) where the bridge is also deployed.
3. An adversarial operator with significant hash power could engineer an exact tie by mining a fork chain to match the canonical chain's lower-128-bit work precisely.

---

### Recommendation

Change the comparison from strict `<` to `<=` so that equal work is also rejected:

```rust
// Operator must have STRICTLY MORE work than any watchtower
if total_work <= max_total_work {
    panic!(
        "Insufficient total work: operator work {total_work:?} must be strictly greater than max watchtower work {max_total_work:?}",
    );
}
``` [1](#0-0) 

This aligns the code with the documented invariant and eliminates the tie-case bypass.

---

### Proof of Concept

1. A watchtower observes a kickoff and generates a valid Work-Only Proof (WOP) for the canonical chain with `work_u128 = W` (16 bytes). It submits the watchtower challenge transaction on-chain with the Groth16 proof and `W` in the OP_RETURN.

2. A malicious operator is on a fork chain whose lower-128-bit cumulative work also equals `W`. The operator generates an HCP for their fork chain such that `hcp.chain_state.total_work[16..32] == W`.

3. The operator calls `bridge_circuit`. At line 156, `total_work == max_total_work`, so `total_work < max_total_work` is `false`. The circuit does **not** panic.

4. The circuit proceeds through SPV, LCP, and storage proof verification using the fork chain's data, producing a valid `journal_hash`.

5. The operator uses this valid ZK proof to survive the BitVM2 challenge, claiming their payout on the fork chain is legitimate. The bridge pays out collateral for a withdrawal that was never finalized on the canonical Bitcoin chain. [6](#0-5) [7](#0-6) [8](#0-7)

pub fn total_work_and_watchtower_flags(
    circuit_input: &BridgeCircuitInput,
    work_only_image_id: &[u8; 32],
) -> (TotalWork, ChallengeSendingWatchtowers) {
    let watchtower_challenge_set = verify_watchtower_challenges(circuit_input);

    let mut valid_watchtower_challenge_commitments: Vec<WatchTowerChallengeTxCommitment> = vec![];

    for outputs in watchtower_challenge_set.challenge_outputs {
        let compressed_g16_proof: [u8; 128];
        let total_work: [u8; 16];

        match outputs.as_slice() {
            // Single OP_RETURN output with 144 bytes
            [op_return_output, ..] if op_return_output.script_pubkey.is_op_return() => {
                // If the first output is OP_RETURN, we expect a single output with 144 bytes
                let Some(Ok(whole_output)) = parse_op_return_data(&op_return_output.script_pubkey)
                    .map(TryInto::<[u8; 144]>::try_into)
                else {
                    continue;
                };
                compressed_g16_proof = whole_output[0..128]
                    .try_into()
                    .expect("Cannot fail: slicing 128 bytes from 144-byte array");
                total_work = whole_output[128..144]
                    .try_into()
                    .expect("Cannot fail: slicing 16 bytes from 144-byte array");
            }
            // Otherwise, we expect three outputs:
            // 1. [out1, out2, out3] where out1 and out2 are P2TR outputs
            //    and out3 is an OP_RETURN output with 80 bytes
            [out1, out2, out3, ..]
                if out1.script_pubkey.is_p2tr()
                    && out2.script_pubkey.is_p2tr()
                    && out3.script_pubkey.is_op_return() =>
            {
                let first_output: [u8; 32] = out1.script_pubkey.to_bytes()[2..]
                    .try_into()
                    .expect("Cannot fail: slicing 32 bytes from P2TR output");
                let second_output: [u8; 32] = out2.script_pubkey.to_bytes()[2..]
                    .try_into()
                    .expect("Cannot fail: slicing 32 bytes from P2TR output");

                let Some(Ok(third_output)) =
                    parse_op_return_data(&out3.script_pubkey).map(TryInto::<[u8; 80]>::try_into)
                else {
                    continue;
                };

                compressed_g16_proof =
                    [&first_output[..], &second_output[..], &third_output[0..64]]
                        .concat()
                        .try_into()
                        .expect("Cannot fail: concatenating and converting to 128-byte array");

                // Borsh deserialization of the final 16 bytes is functionally redundant in this context,
                // as it does not alter the byte content. It is retained here for consistency and defensive safety.
                total_work = borsh::from_slice(&third_output[64..])
                    .expect("Cannot fail: deserializing 16 bytes from 16-byte slice");
            }
            _ => continue,
        }

        let commitment = WatchTowerChallengeTxCommitment {
            compressed_g16_proof,
            total_work,
        };

        valid_watchtower_challenge_commitments.push(commitment);
    }

    valid_watchtower_challenge_commitments.sort_by(|a, b| b.total_work.cmp(&a.total_work));

    let mut total_work_result = [0u8; 16];

    for commitment in valid_watchtower_challenge_commitments {
        if convert_to_groth16_and_verify(
            &commitment.compressed_g16_proof,
            commitment.total_work,
            work_only_image_id,
            circuit_input.hcp.genesis_state_hash,
        ) {
            total_work_result = commitment.total_work;
            break;
        }
    }

    (
        TotalWork(total_work_result),
        ChallengeSendingWatchtowers(watchtower_challenge_set.challenge_senders),
    )
}
