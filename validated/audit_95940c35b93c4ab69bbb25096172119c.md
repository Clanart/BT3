### Title
Unbounded gas/return-data forwarded to attacker-controlled `IApp` callbacks in `EvmHost` request/response/timeout dispatch enables batch griefing - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming`/`dispatchTimeOut` deliver POST requests, GET responses and timeouts to destination applications using a bare `.call()` with no gas stipend and no bound on returned data, exactly the pattern flagged as a gas-griefing risk in the external report for `ModuleManager`/`HookManager`. Unlike modules/hooks (admin-installed), the destination `IApp` here is **attacker-controlled by design** — anyone can register any contract as the `to`/`from` address of a cross-chain message — turning the same low-level-call griefing primitive into an unprivileged, permissionless DoS on message batches.

### Finding Description
`dispatchIncoming(PostRequest ...)`, `dispatchIncoming(GetResponse ...)`, and both `dispatchTimeOut` overloads all invoke the destination application via an unmetered low-level `.call`: [1](#0-0) [2](#0-1) [3](#0-2) 

None of these calls pass an explicit gas value or cap the returned data, so the callee receives ~63/64 of all remaining gas (EIP-150) and can force unbounded memory-expansion via oversized return data — the same primitive described in the external report against `disable()`.

Critically, applications implementing `IApp`/`HyperApp` are **not privileged actors**: any address can be the `to` field of an incoming POST request or the registered app receiving a response/timeout, and the destination contract's bytecode is entirely attacker-controlled (see `HyperApp.onAccept`/`onPostRequestTimeout` being freely overridable by any integrator, and `IApp` callbacks documented as callable on arbitrary destination contracts): [4](#0-3) 

Message delivery to the host is batched by the relayer infrastructure (`HandlerV2.batchCall`), which is documented as atomic — if any inner call reverts (including via out-of-gas), the entire batch transaction reverts: [5](#0-4) 

Combined with `dispatchIncoming`'s unmetered forwarding, a malicious `to` contract deployed by an attacker can consume nearly all remaining gas inside `onAccept`, `onGetResponse`, or `onPostRequestTimeout`, causing the surrounding `handlePostRequests`/`handleGetResponses`/timeout-processing call (and therefore the whole atomic batch it is a part of) to run out of gas and revert — reverting delivery of every other legitimate, unrelated request/response/timeout bundled in the same batch by the relayer.

### Impact Explanation
This is a logic/transaction-manipulation vector on the production request/response/timeout dispatch path: an unprivileged attacker who simply deploys a malicious `IApp`-conforming contract and gets a message routed to it can repeatedly force reverts of relayer batches, delaying settlement, refunds, and proof acceptance for unrelated users' legitimate cross-chain messages bundled in the same transaction. Because `_requestReceipts`/`_requestCommitments` are only mutated on success/explicit failure paths inside `dispatchIncoming`/`dispatchTimeOut` (not on OOG revert of the whole batch), repeated griefing can stall processing of legitimate requests/timeouts, effectively a fund-availability and settlement-delay issue rather than a simple gas cost, since relayers must resubmit smaller batches or drop the malicious message entirely, at their own expense.

### Likelihood Explanation
Moderate. It requires no privileged role, no relayer/prover compromise, and no malformed proof — only deploying an ordinary contract and getting a cross-chain message routed to it as `to`, which is exactly the intended, permissionless use case for `IApp`/`HyperApp`. The main constraint is the relayer's batching strategy (batch size, per-message vs per-batch submission), which determines the blast radius, but the underlying host-level unmetered `.call()` is present in all delivery paths regardless of batching.

### Recommendation
Mirror the fix already applied for `ModuleManager`/`HookManager`: cap the gas forwarded to `IApp` callbacks with an explicit gas amount (not `gasleft()`), and bound/ignore returned data using a safe-call pattern (e.g. `ExcessivelySafeCall`) in `dispatchIncoming` and both `dispatchTimeOut` overloads in `EvmHost.sol`. Additionally, consider isolating each message's delivery in its own gas-bounded sub-context inside `HandlerV2` batch processing so a single malicious destination cannot revert the entire atomic batch.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp.onAccept` that, on invocation, loops until gas runs low (or returns an extremely large `bytes` payload) before returning normally or reverting.
2. Attacker (or anyone) dispatches a POST request whose `to` field is `EvilApp`'s address on the destination chain.
3. A relayer batches this request together with several legitimate, unrelated requests/timeouts via `HandlerV2.batchCall`.
4. When `EvmHost.dispatchIncoming` reaches `EvilApp`'s `onAccept`, the callee consumes ~63/64 of remaining gas (or forces large memory expansion via return data), causing the enclosing call to run out of gas and the atomic batch transaction to revert, per [1](#0-0) .
5. All unrelated legitimate messages bundled in that batch fail to be delivered/settled, and the relayer must retry, giving the attacker a free, repeatable griefing lever over other users' cross-chain settlement.
