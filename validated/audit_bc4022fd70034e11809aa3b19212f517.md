### Title
Duplicate `withdrawal_utxo` OutPoint across two withdrawal indices lets one Bitcoin payout tx be counted as fronting two vaults - (`core/src/database/verifier.rs`)

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` correlates a spent Bitcoin outpoint to a payout purely by `(txid, vout)` equality against the `withdrawals` table, with no additional binding to the specific `move_to_vault_txid`/deposit for that index, and the `withdrawals` schema has no uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`. An attacker who can freely choose the withdrawal UTXO bytes on two separate `withdraw()` calls (backing two different deposits) can register the same outpoint for both, causing a single Bitcoin spend of that outpoint to be recorded as the payout for both withdrawal indices.

### Finding Description
The binding that must hold is: **number of Bitcoin vault UTXOs spent by the payout transaction (1) == number of move-to-vault deposits reimbursed for it (1)**.

- `withdrawals` table stores `idx` (PK), `move_to_vault_txid`, `withdrawal_utxo_txid`, `withdrawal_utxo_vout`, `payout_txid`, etc., with **no unique/exclusion constraint** on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` [1](#0-0) .
- `Database::update_withdrawal_utxo_from_citrea_withdrawal` writes whatever `withdrawal_utxo` OutPoint bytes were reported for a given `citrea_idx`, with no check that this OutPoint is not already used by another `idx` [2](#0-1) .
- `Database::get_payout_txs_for_withdrawal_utxos` joins `bitcoin_syncer_spent_utxos` to `withdrawals` **solely** on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`, returning `(idx, spending_txid)` pairs for every matching row - if two `idx` rows share the same `(txid, vout)`, both are returned for the single spend [3](#0-2) .
- `Database::update_payout_txs_and_payer_operator_xonly_pk` then unconditionally sets `payout_txid`/`payout_payer_operator_xonly_pk`/`payout_tx_blockhash` on every row whose `idx` matches, i.e., on both idx i and idx j [4](#0-3) .
- `PayoutCheckerTask::run_once` picks up "first unhandled payout" rows one at a time and, for each, independently resolves `deposit_data` from `move_to_vault_txid` and calls `Operator::handle_finalized_payout`, which drives the reimbursement flow (kickoff, LCP fetch, `end_round`, marking handled) [5](#0-4) . Since both rows independently satisfy "payout_txid is set, not yet handled," the task will process deposit A's row and, on a subsequent poll, deposit B's row, triggering `handle_finalized_payout` twice for a single real Bitcoin payment.

Per the rules, the attacker is explicitly permitted to "choose the bytes of a withdrawal UTXO" when calling `withdraw()`. Nothing in the traced path re-validates, at payout-detection time, that the spent outpoint is uniquely bound to the specific deposit/idx being credited - the correlation is purely by outpoint bytes, which are attacker-controlled and can collide across two distinct deposits' withdrawal registrations.

### Impact Explanation
If exploited, one Bitcoin payout transaction (funding one user's withdrawal once) results in two `move_to_vault` deposits (A and B) being marked reimbursed, so the corresponding operator can claim reimbursement collateral/rounds for both, or the bridge's accounting treats both vault UTXOs as legitimately spent for a single funded payout. This is a "BTC leaves TWO move-to-vault UTXOs for a payout that fronted a user once" scenario, matching the Critical impact category (operator reimbursed for a payout it never separately funded / broken 1:1 vault-to-payout binding). The blast radius scales with however many withdrawal indices an attacker can register with colliding outpoints, across any deposits/operators.

### Likelihood Explanation
Preconditions: the attacker needs to (1) make two deposits (or reuse existing ones) so two `move_to_vault_txid`s exist, and (2) call `withdraw()` twice on the Citrea bridge contract, supplying the same withdrawal UTXO outpoint bytes for both registrations - both explicitly listed as attacker-controlled actions in the rules. No verifier/operator/aggregator privilege is required. Feasibility of the Citrea-contract side accepting a duplicate outpoint across two different withdraw calls is not confirmed from this repo's code (the contract itself is out of scope), but assuming the question's premise (both registrations succeed and reach the verifier's DB via `update_withdrawal_utxo_from_citrea_withdrawal`), the clementine-side correlation logic traced above does not add any additional disambiguation and would process both.

### Recommendation
Add a uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the `withdrawals` table (or reject registration of an outpoint already used by another `idx`), and additionally disambiguate `get_payout_txs_for_withdrawal_utxos`/the payout-marking logic so a single spent outpoint can satisfy at most one withdrawal `idx` - e.g., using an idempotency check that atomically claims the spend for the first matching idx and excludes others, or by re-validating the payout transaction's outputs against each idx's specific recipient script/amount before crediting `handle_finalized_payout`.

### Proof of Concept
`cargo test` plan (non-mainnet, mocked `CitreaClientT`):
1. Create two deposits A and B, each with a valid `move_to_vault_txid`.
2. Register withdrawal idx=i for A and idx=j for B via the mocked Citrea client, both reporting the identical `OutPoint` bytes, causing `update_withdrawal_utxo_from_citrea_withdrawal` to store the same `(withdrawal_utxo_txid, withdrawal_utxo_vout)` for both rows.
3. Have one operator broadcast a single Bitcoin payout transaction spending that shared outpoint.
4. Run the block-processing/bitcoin-syncer path so `bitcoin_syncer_spent_utxos` records the spend, then call `Database::get_payout_txs_for_withdrawal_utxos` for that block and assert it returns two entries `(i, spending_txid)` and `(j, spending_txid)` - **binding-broken side**: 2 idx entries for 1 spent outpoint (expected: 1).
5. Call `update_payout_txs_and_payer_operator_xonly_pk` with both entries and assert both rows in `withdrawals` now have `payout_txid` set.
6. Run `PayoutCheckerTask::run_once` twice (once per unhandled row) and assert `Operator::handle_finalized_payout` is invoked exactly twice - once for deposit A's outpoint and once for deposit B's - proving one payout tx drove two reimbursement flows instead of one.

    /// Returns the withdrawal indexes and their spending txid for the given
    /// block id.
    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }

    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;

        dbtx.commit().await?;

        Ok(true)
    }
