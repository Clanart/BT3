### Title
Unbounded recursive puzzle-layer matching in outer-puzzle drivers allows attacker-controlled stack-overflow denial of service - (File: `chia/wallet/outer_puzzles.py`, `chia/wallet/cat_wallet/cat_outer_puzzle.py`, `chia/wallet/nft_wallet/ownership_outer_puzzle.py`, `chia/wallet/nft_wallet/metadata_outer_puzzle.py`, `chia/wallet/vc_wallet/cr_outer_puzzle.py`)

### Summary
The CVE describes libopenmpt's `Snd_fx.cpp` crashing (OOB read / DoS) when parsing a file with many nested pattern loops because the loop-nesting depth was not bounded before recursive/iterative processing. The structural analog in this codebase is the outer-puzzle "driver" matching chain used by the wallet to interpret a coin's puzzle reveal (CAT, singleton, metadata, ownership, credential-restricted layers). Each driver's `match()`/`get_inner_puzzle()`/`get_inner_solution()` recursively calls back into `match_puzzle()`/`self._match(...)`/`self._get_inner_puzzle(...)` for the "inner" puzzle one layer at a time, with no limit on how many layers may be nested, and `PuzzleInfo.also()`/`check_type()` similarly chain unbounded.

### Finding Description
`match_puzzle()` in [1](#0-0)  iterates over `driver_lookup` and calls `driver.match(puzzle)`. Each driver's `match` (e.g. `CATOuterPuzzle.match`) unconditionally recurses into its inner puzzle via `self._match(UnknownPuzzle(known_program=inner_puzzle))` when the inner puzzle also matches the same or another driver: [2](#0-1) . The existing test suite explicitly demonstrates that CAT puzzles can be nested arbitrarily (`construct_cat_puzzle(CAT_MOD, tail, cat_puzzle)` wrapped again), and `match_puzzle` correctly walks each nested layer via `.also()`: [3](#0-2) .

The same unbounded recursive pattern exists in `OwnershipOuterPuzzle.match`/`get_inner_puzzle` [4](#0-3) , `MetadataOuterPuzzle.match`/`get_inner_puzzle` [5](#0-4) , `SingletonOuterPuzzle.get_inner_puzzle` [6](#0-5) , and `CROuterPuzzle.get_inner_puzzle` [7](#0-6) . All of these are pure Python recursion with no depth cap, unlike `sha256_treehash`, which was deliberately made iterative specifically to avoid "blowing out the python stack" on deeply nested CLVM structures [8](#0-7) . `PuzzleInfo.also()`/`check_type()` also recurse without bound, driven entirely by attacker-supplied `info` dict nesting [9](#0-8) .

Because CLVM puzzle-reveal construction only costs CLVM execution units and byte-size to *build*, an attacker can cheaply construct a coin puzzle with thousands of nested CAT/ownership/metadata/CR layers (e.g. `CAT(tail, CAT(tail, CAT(tail, ...ACS...)))`), analogous to IT/MO3's deeply nested pattern loops. When this coin is offered in a trade or otherwise surfaces in a spend bundle that a wallet inspects, the wallet calls `match_puzzle()` to determine the asset driver, or `get_inner_puzzle()`/`get_inner_solution()` while processing the offer, recursing once per nesting layer. Python's default recursion limit (~1000) is reachable well within the CLVM cost budget, so a crafted offer/spend can trigger a `RecursionError` deep in wallet processing.

### Impact Explanation
A malicious offer counterparty or spend-bundle submitter can craft a puzzle reveal with sufficiently many nested outer-puzzle layers to trigger unbounded Python recursion in wallet-side puzzle interpretation (`Offer` parsing, NFT/CAT/VC coin-state processing that calls `match_puzzle`/`get_inner_puzzle`). This can crash or hang the recursion path in the wallet process (RPC handler or background sync task), denying service to the wallet user attempting to inspect/accept the offer or process the coin — a spend-triggered transaction-processing halt, matching the CVE's DoS bug class. It does not, by itself, appear to enable unauthorized coin movement or supply inflation.

### Likelihood Explanation
Medium. Exploitation only requires crafting a puzzle (not necessarily spendable/valid) with deeply nested driver-matchable outer layers and getting it in front of a victim wallet (e.g., via an offer file, a coin hint, or coin state sync) — no privileged access or valid signature is required to *construct* the puzzle reveal, only to have the victim's wallet attempt to interpret it.

### Recommendation
Add an explicit recursion/nesting-depth limit to `match_puzzle`, `PuzzleInfo.also()/check_type()`, and each `OuterPuzzle.match/get_inner_puzzle/get_inner_solution` implementation (mirroring the iterative, non-recursive design already used in `sha256_treehash` and the `RecursionDepthExceededError` guard used in the Data Layer merkle-tree loader), raising a clear error instead of allowing unbounded Python-stack recursion driven by attacker-supplied puzzle structure.

### Proof of Concept
Conceptually (not verified against a running instance, since I only have static code access):
1. Build a base inner puzzle `ACS = Program.to(1)`.
2. Repeatedly wrap it N times (N large enough to approach Python's recursion limit, e.g. 2000+) using `construct_cat_puzzle(CAT_MOD, tail, prev_puzzle)` as shown in the existing `test_cat_outer_puzzle` test's `double_cat_puzzle` pattern, but applied N times instead of once.
3. Wrap the resulting puzzle reveal in a coin used in an `Offer`/spend bundle, or a coin whose puzzle reveal is presented to `match_puzzle`/`get_inner_puzzle`.
4. Have a victim wallet call `Offer.from_bytes(...)`/inspect the offer, which invokes `match_puzzle()` → recursive `driver.match()` chain N levels deep, or `get_inner_puzzle()` similarly, raising `RecursionError` and aborting/crashing the wallet's processing path.

**Note on verification**: I was not able to execute this PoC or trace the full call graph from `Offer.__post_init__`/RPC entry points down into `match_puzzle`/`get_inner_puzzle` due to tool/iteration limits — the citations above establish the unbounded-recursion pattern and its invocation sites, but the exact victim-reachable entry point (e.g., specific RPC or sync callback that calls `match_puzzle` on an untrusted, attacker-supplied puzzle reveal) should be confirmed with a live Devin session that can run the test suite and trace call sites end-to-end.

            if self.also() is None:
                return True
            else:
                return False
        elif self.type() == types[0]:
            types.pop(0)

                return self.also().check_type(types)  # type: ignore
            else:
                return self.check_type(types)
