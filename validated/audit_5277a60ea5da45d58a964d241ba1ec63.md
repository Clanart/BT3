## Analysis

Looking at `verify_mmr_update_proof` in `modules/consensus/beefy/verifier/src/lib.rs`, the participation check and the merkle membership check are two independent steps that are never cross-checked against each other for authority uniqueness: [1](#0-0) [2](#0-1) 

`signatures_length` is simply `mmr.signed_commitment.signatures.len()` — a raw count of entries in an attacker/relayer-supplied array — with no requirement that `sig.index` values be distinct. `authority_indices`/`authority_leaves` are built by iterating that same array without deduplication, then passed straight into `rs_merkle::MerkleProof::verify`. There is no `.sort()`/`.dedup()` step, and no comparison between "number of raw signatures" and "number of unique authority indices actually proven."

`check_participation_threshold` itself is a pure count comparison with no concept of identity: [3](#0-2) 

The identical pattern (`sigLen = relayProof.signedCommitment.votes.length` fed straight into `checkParticipationThreshold`) exists in the Solidity `EcdsaBeefy.sol` contract as well: [4](#0-3) 

This is notable because sibling consensus verifiers in the same codebase explicitly guard against exactly this class of bug — padding a participation count without actually growing the set of distinct signers:
- The BSC verifier explicitly rejects bits set beyond the validator count to prevent inflating `count_ones()`: [5](#0-4) 
- The sync-committee verifier has the same anti-padding guard with an explicit comment about attackers padding `count_ones()`: [6](#0-5) 
- The pharos verifier explicitly detects and rejects duplicate participant keys, with a dedicated test `test_duplicate_participant_keys_rejected`: [7](#0-6) 

None of these three "assume distinct participants" pitfalls are guarded against in the BEEFY verifier's index/signature counting path, and I found no test in `modules/consensus/beefy/verifier/src/test.rs` exercising duplicate `authority_indices` (the existing test `rejects_sub_supermajority_from_named_authority_set` only checks a genuinely too-small signature count, not a padded/duplicated one).

## Key uncertainty

Whether this is actually exploitable end-to-end hinges on how the external `rs_merkle` crate's `MerkleProof::verify` treats duplicate `(index, leaf_hash)` pairs supplied in the `leaf_indices`/`leaf_hashes` arguments:
- If `rs_merkle` internally collapses indices via a map keyed by position (common in multi-proof implementations), then re-submitting the same authority's `(index, signature)` twice would be structurally accepted by the merkle check with no additional proof data required — meaning the real vulnerability is fully live: an attacker (unprivileged relayer submitting the consensus proof extrinsic) could take real signatures from a minority of authorities and duplicate entries to inflate `signatures_length` past the 2/3+1 threshold while only ⌈N/3⌉+1 or fewer distinct authorities actually signed.
- If instead `rs_merkle` builds proof layers by strict positional pairing (as the project's own documented multiproof algorithm in `docs/content/protocol/cryptography/merkle-trees/binary.mdx` implies — pairing sorted `(k_index, node)` entries two at a time), a duplicate index would corrupt the sibling pairing and cause root reconstruction to fail, blocking the attack at the merkle-verification step.

I could not inspect the vendored/actual `rs_merkle` crate source in this repo (it's an external dependency pulled via `Cargo.toml`, not present in the indexed codebase), so I cannot confirm with certainty which behavior applies. This should be resolved by writing and running a concrete unit test (duplicating a `SignatureWithAuthorityIndex` entry for a real proof-generation flow in `test.rs`) to observe whether `merkle_proof.verify(...)` accepts or rejects the padded index list.

## Conclusion

Regardless of the `rs_merkle` internals, the code as written has a real design gap: `check_participation_threshold` is evaluated against the raw signature array length rather than a deduplicated/unique-authority-index count, unlike the analogous checks in the BSC, sync-committee, and Pharos verifiers in the same codebase. This is a legitimate finding worth escalating for confirmation via a concrete PoC test against the real `rs_merkle::MerkleProof::verify`, since if duplicate indices do pass merkle verification, this directly allows a minority of real signers to forge acceptance of a fabricated BEEFY consensus update (wrong MMR root / wrong next authority set), corrupting the trusted `ConsensusState` that all downstream parachain header and cross-chain message proofs rely on.

### Title
Supermajority Threshold Bypass via Duplicate Authority Signatures/Indices in BEEFY Verifier - (File: modules/consensus/beefy/verifier/src/lib.rs)

### Summary
`verify_mmr_update_proof` computes `signatures_length` as the raw length of the attacker-controlled `signed_commitment.signatures` array and checks it against `check_participation_threshold`, without ever verifying that the `sig.index` values (and thus the underlying authorities) are unique. Unlike the BSC, sync-committee, and Pharos verifiers in the same codebase — which all explicitly guard against inflating a participation count via padding/duplication — this code path has no such guard.

### Finding Description
`signatures_length = mmr.signed_commitment.signatures.len()` and `authority_indices`/`authority_leaves` are both derived by iterating the same unvalidated array ( [1](#0-0) , [2](#0-1) ). There is no deduplication of `authority_indices` and no check that the count of unique indices meets the 2/3+1 threshold — only the raw count of supplied signature entries is checked. The Solidity `EcdsaBeefy.sol` verifier has the identical pattern ( [4](#0-3) ).

### Impact Explanation
If the underlying merkle multi-proof verification accepts repeated `(index, leaf_hash)` entries for the same authority (which is plausible for common multiproof implementations that key proof layers by position), a minority of real BEEFY authorities below the true 2/3+1 supermajority could get their consensus update accepted as valid by duplicating their own signature/index entries. This would let an attacker force acceptance of a fabricated MMR root and/or `beefy_next_authority_set`, corrupting `ConsensusState` and everything downstream (parachain header proofs, ISMP state commitments), which the review scope identifies as capable of unlocking bridged assets against a fabricated state commitment.

### Likelihood Explanation
Requires collusion of only `authority_set.len/3 + 1` (roughly a minority) real signers rather than a genuine supermajority, and the attack is mounted purely through the unprivileged consensus-proof submission path (relayer/prover extrinsic), consistent with the review's "unprivileged input" requirement. Exploitability is contingent on the exact duplicate-index behavior of the `rs_merkle` crate, which needs to be confirmed with a concrete test.

### Recommendation
In `verify_mmr_update_proof` (and the equivalent Solidity `verifyMmrUpdateProof`), deduplicate `authority_indices` (e.g., collect into a `BTreeSet`/sorted-and-deduped `Vec`) before computing the threshold, and compute `signatures_length`/`sigLen` from the deduplicated set rather than the raw array length. Mirror the explicit anti-padding pattern already used in the BSC and sync-committee verifiers, and add a `rejects_duplicate_authority_indices` test analogous to Pharos's `test_duplicate_participant_keys_rejected`.

### Proof of Concept
1. Take `authority_set.len = 7` (threshold = `(2*7)/3+1 = 5`).
2. Obtain valid signatures from only 3 real, distinct authorities (below the 5 needed for supermajority).
3. Build `mmr.signed_commitment.signatures` with each of the 3 real `SignatureWithAuthorityIndex` entries duplicated once (6 total entries, same `index`/`signature` bytes repeated), and reuse the honestly-generated `authority_proof` for the 3 real indices.
4. Call `verify_mmr_update_proof`: `signatures_length = 6 >= 5` passes `check_participation_threshold`; if `merkle_proof.verify` accepts the duplicated `authority_indices`/`authority_leaves` pairs against the original 3-authority proof, the fabricated update is accepted despite only 3/7 authorities (not a real supermajority) having actually signed.
5. Confirming step 4's merkle-acceptance behavior requires executing this against the real `rs_merkle` dependency, which I could not do in this read-only review — recommend adding this exact test to `modules/consensus/beefy/verifier/src/test.rs` to confirm or rule out exploitability.
