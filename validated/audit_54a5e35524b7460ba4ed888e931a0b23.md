### Title
`ThresholdKeys::read`/`ThresholdKeys::new` accept attacker-controlled threshold and never bind `secret_share` to `verification_shares[i]`, yielding keys whose group key is fully attacker-known - (File: crypto/dkg/src/lib.rs)

### Summary
The Bouncy Castle report (CVE-2016-1000343) is a "weak key from default parameters" bug: an uninitialized key generator silently produced a 1024-bit (weak) private key. The Serai analog lives in the `dkg` crate's threshold-key deserialization. `ThresholdKeys::read` consumes attacker-controlled bytes for `t`, `n`, the interpolation method, `secret_share`, and all `verification_shares`, then calls `ThresholdKeys::new`, which derives `group_key` purely from `verification_shares[1..=t]` and the interpolation factors. Two defects combine: (1) the threshold `t` is whatever the bytes claim — `t = 1` is accepted — and (2) the holder's `secret_share` is never checked against `verification_shares[i]`. An attacker who feeds crafted bytes to `ThresholdKeys::read` produces a structurally valid `ThresholdKeys` whose group key has a discrete logarithm known to the attacker.

### Finding Description
In `crypto/dkg/src/lib.rs:574-631`, `ThresholdKeys::read` parses `t`, `n`, `i`, the interpolation discriminant, `secret_share`, and `n` verification shares from the reader, then constructs keys via `ThresholdKeys::new`. `ThresholdKeys::new` (lines 349-391) validates only that `verification_shares.len() == n`, that each index `<= n`, and `t <= n` via `ThresholdParams::new` (lines 166-179). It then computes the group key as the interpolation of `verification_shares[1..=t]` (lines 376-378). Nowhere is `secret_share` verified to satisfy `C::generator() * secret_share == verification_shares[i]`, and no minimum/expected threshold is enforced — the caller's actual intended `t` is taken from the untrusted blob itself.

Concrete malicious encodings:
- `t = 1`: `group_key = verification_shares[1]` (interpolation factor is 1 for a singleton set). The attacker sets `verification_shares[1] = G * x` for known `x` and `secret_share = x`. `ThresholdKeys::new` succeeds and produces keys whose group private key `x` the attacker holds.
- Any `t`: the attacker picks arbitrary verification shares whose interpolated sum is `G * x`; the group key is still attacker-known.
- `secret_share` inconsistent with `verification_shares[i]`: signing with the resulting `ThresholdView` (lines 463-533) will interpolate a secret share that does not correspond to the published group key, producing `SignatureShare`s that fail `algorithm.verify` and then fail `verify_share` blame resolution in `crypto/frost/src/sign.rs:465-480` — silent liveliness failure attributed to other participants.

### Impact Explanation
Any component that loads `ThresholdKeys` from untrusted or externally-routed bytes (the prompt's threat model explicitly admits untrusted bytes to `ThresholdKeys::read`) will accept a key materialization whose group key is attacker-controlled. Consequences:

- Funds/outputs attributed to `group_key()` are spendable by the attacker, not by the intended threshold set — the exact "weak/known private key" outcome of CVE-2016-1000343, mapped from "weak key size" to "degenerate attacker-chosen threshold + unbound verification shares".
- A mismatched `secret_share`/`verification_shares[i]` pair causes every signing session to fail verification with blame that cannot correctly identify a malicious peer, since the victim's own key material is corrupt — persistent DoS indistinguishable from peer faults.

### Likelihood Explanation
Reachability is limited to integrations that deserialize `ThresholdKeys` from bytes an unprivileged party can influence (imports, backups, peer-delivered key material, storage an attacker can write). Where reachable, the attack is deterministic: no computation, no collusion, and no protocol interaction is required — a single crafted byte string is accepted by `ThresholdKeys::read`. The condition is environment-dependent, hence Medium-to-High rather than unconditional.

### Recommendation
- In `ThresholdKeys::new` (and therefore `read`), verify the holder's share consistency: assert `C::generator() * secret_share == verification_shares[&params.i()]` (adjusted for Lagrange interpolation at index `i` over the declared full set, or reject if a canonical check isn't defined for the interpolation mode).
- Reject `t = 1` for multi-participant materialized keys, or require callers to pass the expected `ThresholdParams` to `ThresholdKeys::read` (as `Commitments::read`/`EncryptedMessage::read` already do with `params` in `crypto/dkg/pedpop/src/lib.rs:110` and `crypto/dkg/pedpop/src/encryption.rs:171`) instead of trusting the serialized `t`, `n`, `i`.
