### Title
Partial-commit patch is re-diffed from disk without revalidating against the diff the user actually reviewed, allowing a repo-controlled write between review and commit to silently corrupt what gets committed - (File: `app/src/lib/git/apply.ts`)

### Summary
The reported Primitive Protocol bug's broken invariant is: a state check (expiry/pause) is enforced at one control point (mint/exercise) but not re-enforced at a later point (transfer), so a stale/invalid object keeps moving through the system to a party who trusted an earlier check. The GitHub Desktop analog is a TOCTOU gap in the partial-commit ("stage selected lines") pipeline: the line-based selection a user approves against one diff snapshot is applied, unchecked, to a *different, freshly re-fetched* diff of the same file when the patch is actually built and staged.

### Finding Description
When a user stages only some lines/hunks of a file, Desktop stores a `DiffSelection` keyed by absolute line index against the diff that was rendered in the Changes view (`app/src/lib/stores/app-store.ts`, `updateChangesWorkingDirectoryDiff`, `~L3404-3513`). This function even acknowledges the underlying fragility in its own comment: "The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines" [1](#0-0) .

When the user clicks Commit, `_commitIncludedChanges` takes the files/selection currently in `repositoryStateCache` and calls `createCommit` [2](#0-1) , which in turn calls `stageFiles` for partially-selected files [3](#0-2) .

For every partially-selected file, `stageFiles` calls `applyPatchToIndex`, which does **not** use the diff the user reviewed. Instead it independently re-fetches a brand-new diff straight from the working directory right before building the patch: [4](#0-3) 

`formatPatch` then walks the *freshly fetched* diff's hunks and, for each line, tests `file.selection.isSelected(absoluteIndex)` — reusing the **old** line-index-based selection object against the **new** diff's line layout [5](#0-4) . There is no comparison of hunk headers, line content, or file hash between the diff that produced the selection and the diff that is actually patched.

If the working tree file is modified by anything running inside the repo's environment between the moment Desktop last computed the diff shown to the user and the moment `applyPatchToIndex` re-diffs it (a race window that spans UI interaction time — typically seconds), the absolute-index selection silently maps onto unrelated lines of the new content. `formatPatch`'s only self-check is `if (!patch.length) throw ...` [6](#0-5)  — it does not detect a mismatched-but-nonempty patch.

### Impact Explanation
This lets a hostile repository silently corrupt what a user commits without the user's on-screen selection ever being wrong at the time they reviewed it. A cloned/fetched repository can ship tooling that runs automatically while the repo is open in Desktop (a `.vscode` auto-task, an npm `postinstall`/watch script the user already has running, a build step wired to file-save, or any other process the attacker seeds into the repo) that rewrites a tracked file's content shortly after the user opens the diff and selects lines to stage but before they press Commit. Because Desktop re-diffs the file from disk at staging time instead of validating against the reviewed diff, the resulting commit can include content the user never saw or approved (e.g., injecting a backdoor line into a hunk the user thought they excluded, or dropping a security-relevant line the user thought they included) — a direct instance of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
The window is real but requires: (1) the user to use partial/line-level staging (a supported, common Desktop feature) and (2) something in the environment (which the attacker's cloned repo can arrange to auto-run) to mutate the exact file between diff-render and click-commit. This is plausible for automated build/format/lint-on-save tools that many repos configure and that a user may already be running while reviewing a diff. The maintainers' own comment on the closely related read-side validation ("we should be more clever about validating that partial selection state is still valid... but for now we'll settle on just updating the selectable lines") indicates this exact class of staleness was already recognized as incompletely handled, which supports plausibility though I could not find a CVE/advisory confirming exploitation, and could not verify from the index whether any additional guard exists elsewhere (e.g., a hash/hunk comparison) that isn't visible in the excerpted files.

### Recommendation
Before building the patch in `applyPatchToIndex`, compare the freshly fetched diff against the diff the selection was computed from (e.g., via hunk header/content hashes, or by re-deriving the selection from `withSelectableLines` immediately prior to staging and failing/re-prompting instead of silently proceeding if the diff changed). At minimum, detect when the newly fetched diff's hunks differ from what produced the selection and abort the commit with a user-facing warning rather than applying a best-effort but potentially mismatched patch.

### Proof of Concept
Not independently executed; based on static code-flow analysis of `app/src/lib/git/apply.ts` (`applyPatchToIndex`, re-diff call), `app/src/lib/patch-formatter.ts` (`formatPatch`, index-based selection application), `app/src/lib/git/commit.ts` (`createCommit`/`stageFiles` call order), and `app/src/lib/stores/app-store.ts` (`updateChangesWorkingDirectoryDiff`, `_commitIncludedChanges`). Conceptual repro: clone a hostile repo containing an auto-run watcher script; modify a tracked file in the diff view, select only some lines to stage, let the watcher rewrite the file before clicking Commit, and observe that the committed patch reflects the new file content mapped through the old line-index selection rather than the content actually reviewed.
