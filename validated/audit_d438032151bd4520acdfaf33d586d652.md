### Title
UTF-8 validation is silently skipped for Cord-backed string fields parsed via the `MpString` fallback path in `TcParser` - (File: `src/google/protobuf/generated_message_tctable_lite.cc`)

### Summary
The Y2K `Carousel` bug boils down to one invariant: "the same mutation must be validated the same way regardless of which code path executes it." The direct-deposit path calculates and enforces a fee; the late/queued-deposit path performs the identical mutation (`_mintShares`) but skips the check entirely because it is a different, less-travelled code path. The Protobuf analog with the same shape is `TcParser::MpVerifyUtf8`: the primary (`absl::string_view`/`ArenaStringPtr`) code path enforces UTF-8 structural validity when the field's `xform_val` is `kTvUtf8`, but the `absl::Cord` overload used for `ctype=CORD`-backed string fields performs **no validation at all** — it unconditionally returns `true` regardless of `xform_val`, relying only on a debug-only `ABSL_DCHECK_EQ(xform_val, 0)` that is compiled out in release (NDEBUG) builds.

### Finding Description
`TcParser::MpString` (the "mini"/fallback parser used when a field isn't handled by the fast, tag-width-specialized table entries — e.g. `oneof` members, fields hit via the generic `MiniParse`/fallback dispatch, or reflection-driven table generation) dispatches string-typed fields to one of three storage representations: `ArenaStringPtr`, `MicroString`, or `Cord`, then calls `MpVerifyUtf8` on the parsed value before accepting it: [1](#0-0) 

For the `string_view`/`ArenaStringPtr` and `MicroString` branches, `MpVerifyUtf8` genuinely checks `utf8_range::IsStructurallyValid` when `xform_val == kTvUtf8`: [2](#0-1) 

But the `absl::Cord` overload — invoked for `kRepCord` fields — never performs the check; it just `switch`es on `xform_val` and returns `true` in the `default` branch, backed only by a debug assertion that `xform_val` is `0`: [3](#0-2) 

The table-driven parser's own internal documentation shows that `Uc` (a **U**TF-8-strictly-verified string field with **c**ord storage) is a documented, expected combination in the type-card naming scheme (`U` = "utf8 string, strictly verified"; the `c`/`i` suffix indicates cord/inlined storage): [4](#0-3) 

That means the fast-table code path is expected to support (and presumably correctly validates) a UTF-8-checked, Cord-backed string field. The fallback `MpString`/`MpVerifyUtf8` path, however, was implemented as if `xform_val` for Cord fields is always `0` — i.e., never `kTvUtf8` — and therefore never wires up the actual `utf8_range::IsStructurallyValid` call for the Cord case. If a `Cord`-backed string field is ever routed through `MpString` (e.g. because it's a `oneof` member — `MpString` explicitly handles `card == field_layout::kFcOneof` via `ChangeOneof` — or because the field entry falls back to `MiniParse` for any other reason), the field is accepted with **no UTF-8 verification whatsoever**, silently violating the "supported public parse API" contract that proto3 string fields (and edition-configured UTF8-validated fields) are guaranteed to be valid UTF-8 once parsing succeeds.

This is structurally identical to the Sherlock finding: the "primary" processing path (`_deposit` with `_id != 0`, or here, `MpVerifyUtf8(absl::string_view...)`) enforces a security invariant that the "secondary/fallback" path (`mintDepositInQueue`, or here, `MpVerifyUtf8(absl::Cord...)`) omits, even though both paths ultimately commit the same trusted-schema-declared field.

### Impact Explanation
Downstream consumers of a generated protobuf message routinely rely on the documented guarantee that a `string` field (as opposed to `bytes`) contains structurally valid UTF-8 once `ParseFrom*` succeeds — this is exactly the guarantee the conformance suite enforces for `RejectInvalidUtf8` tests. Applications frequently use this guarantee as a boundary condition before feeding the value to systems that assume valid UTF-8 (log sinks, JSON/text re-serialization, other language runtimes, filesystem or shell operations that mis-handle invalid byte sequences). Silently accepting a value with malformed UTF-8 into a nominally-validated `string` field can therefore cause downstream data-integrity problems, inconsistent round-tripping (a message that "parses" but cannot be safely re-serialized/re-interpreted the same way in every runtime), or security-relevant assumptions being violated in consuming applications. This is a data-integrity/parsing-consistency bug, not a memory-safety bug and not a resource-exhaustion issue, matching the exclusion criteria in the prompt.

### Likelihood Explanation
The exact reachability of `kTvUtf8` for a `Cord`-backed field through the `MpString`/`MiniParse` route (rather than the fast-table path) depends on codegen details (specifically, whether the field-generator ever emits a `Uc`-class `type_card` and routes it to `MpVerifyUtf8` rather than to a dedicated fast/table-driven Cord+UTF8 parser). I could confirm from the source comments that `Uc` is a documented combination in the type-card naming scheme and that `oneof`-typed Cord fields are explicitly routed through `MpString` regardless of fast-table availability (oneofs always require the `ChangeOneof` bookkeeping done in `MpString`). I was not able to fully trace the exact codegen path that assigns `xform_val` for cord-backed oneof/extension string fields within the time available, so there is residual uncertainty about whether `kTvUtf8` is ever actually emitted for a Cord field in current generated code, or whether it is dead code protected upstream by other invariants. This should be verified with a concrete `.proto` schema (`ctype = CORD` on a `oneof` string member in a UTF8-validated edition/proto3 message) compiled and parsed with an invalid-UTF8 payload.

### Recommendation
1. Confirm (or refute) that `MpVerifyUtf8(const absl::Cord&, ...)` is reachable with `xform_val == kTvUtf8` for a Cord-backed `oneof` (or other fallback-routed) string field, by generating a minimal proto3/editions schema with `ctype=CORD` on a `oneof` string member and parsing an invalid-UTF8 payload for that field.
2. If reachable, implement the missing `utf8_range::IsStructurallyValid` check inside the `kTvUtf8` case of the `Cord` overload of `MpVerifyUtf8`, mirroring the `string_view` overload, and add conformance/unit tests analogous to the existing `RejectInvalidUtf8` conformance cases specifically targeting Cord-backed, `oneof`/fallback-routed string fields.
3. Replace the debug-only `ABSL_DCHECK_EQ(xform_val, 0)` with either a real validation branch or, if the combination is genuinely impossible by construction, a `static_assert`/build-time guarantee rather than a runtime-elided debug check, so that a future codegen change cannot silently reintroduce this exact fast-path/fallback-path validation asymmetry (the same "keep behavior consistent across all entry points" fix recommended for the original Carousel bug).

### Proof of Concept
I could not execute a compiled reproduction within this environment (no build/test tools were available in this session). The concrete reproduction to run would be:
1. Define a proto2/proto3/editions message with a `oneof` member of type `string` with option `ctype = CORD` (and, for editions, `features.utf8_validation = VERIFY`).
2. Serialize a payload where that oneof field's bytes are set to an invalid UTF-8 sequence (e.g. `\xFF`), using an untyped/raw byte writer (bypassing the setter-side validation that only applies to trusted in-process construction).
3. Call the public `ParseFrom(...)` API on the generated message type with this payload and assert whether parsing succeeds. If it succeeds and the byte content is retained verbatim (not rejected as in the `string_view`-backed analogue), this confirms the bypass in `MpVerifyUtf8(const absl::Cord&, ...)` at `generated_message_tctable_lite.cc:2516-2524`.

Given the reasoning-effort and no-tool-execution constraints of this session, this proof of concept is described but not run; running it in a Devin session with full build tooling is recommended to confirm exploitability before treating this as a confirmed, fixable defect.
