## Confirmed Analog Found

The `nominator_pool` slashing report reduces to this invariant break: **a contract credits its internal accounting ledger with a nominal/requested amount instead of the amount it actually received/holds, so the ledger can promise more than the contract's real balance.** In Hyperbridge, `evm/tron/contracts/apps/IntentGatewayV2.sol` (the Tron deployment of the Intent Gateway) reproduces this exact bug, while the canonical EVM contract at `evm/src/apps/IntentGatewayV2.sol` was explicitly hardened against it.

### Title
Escrow Ledger Trusts Requested Input Amount Instead of Actual Received Balance on Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` on the Tron variant of `IntentGatewayV2` credits `_orders[commitment][token]` with the user-declared `order.inputs[i].amount` (minus protocol fee) right after calling `safeTransferFrom`, without ever checking how many tokens the contract actually received.

### Finding Description
In `placeOrder`, the direct (non-predispatch) escrow path does: [1](#0-0) 
```
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
```
`reducedInputs[i].amount` is derived directly from `order.inputs[i].amount` (the caller-supplied value), never from a measured balance delta: [2](#0-1) 

For any TRC-20/ERC-20 token that takes a fee or reflection on transfer (fee-on-transfer, rebasing, deflationary tokens — common on Tron), the gateway's real token balance after `safeTransferFrom` is strictly less than `order.inputs[i].amount`. The `_orders` ledger is nonetheless credited with the full requested amount, so the sum of all `_orders[...]` entries can exceed the gateway's actual token balance.

The canonical EVM contract, `evm/src/apps/IntentGatewayV2.sol`, was fixed to avoid exactly this: it snapshots the balance before transfer and mutates `order.inputs[i].amount` to the measured delta before computing the commitment and crediting escrow — explicitly documented as a fee-on-transfer fix and covered by dedicated tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, etc.): [3](#0-2) [4](#0-3) 

The Tron contract, which is a full independent copy of the app logic (not a thin wrapper), never received this fix — the direct-path escrow crediting at lines 444-462 still uses the unverified requested amount, exactly like `financial.fc` trusting the nominal `deposit_amount` instead of what `nominator_proxy` actually forwards after slashing.

### Impact Explanation
Once even one order is placed with a token that skims a transfer fee, the gateway's on-chain `_orders` ledger overstates real holdings for that token by the skimmed amount. `withdraw()` pays out from `_orders` balances on fill/cancel/refund without any global solvency check against the token's actual `balanceOf(this)`: [5](#0-4) 
As more such orders accumulate, later legitimate withdrawals for *other, unrelated* users/tokens sharing the same token balance will fail or, in a worse ordering, an attacker can front-run/queue withdrawals to be among the first to redeem while the last redeemer(s) find the contract's real balance insufficient — a direct "loss of funds" / accounting-insolvency condition matching the bounty's fund-loss category, without needing a malicious relayer, prover, or admin.

### Likelihood Explanation
Any unprivileged user can trigger this by placing an order with a fee-on-transfer or deflationary TRC-20 as the input token — no relayer, governance, or cross-chain proof is required; the discrepancy is created purely by the token's own `transfer`/`transferFrom` semantics interacting with the gateway's unchecked accounting on `placeOrder`. Fee-on-transfer and reflection tokens are common on Tron/BSC-style ecosystems, which is precisely the class of token the maintainers already anticipated and fixed for the EVM contract, confirming this is a realistic, foreseeable condition rather than a contrived edge case.

### Recommendation
Mirror the fix already applied to `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before each `safeTransferFrom`, compute the actually-received delta, use that delta (not the caller-declared `amount`) both for the commitment hash and for the `_orders[commitment][token]` credit, and emit `DustCollected`/revert appropriately if it diverges from the requested amount. Apply the equivalent fix to the predispatch escrow path in the Tron contract as well.

### Proof of Concept
1. Deploy a TRC-20 token with a 1% transfer fee (as in `FeeOnTransferToken` from `evm/tests/foundry/IntentGatewayV2Test.sol`).
2. User calls `placeOrder` on the Tron `IntentGatewayV2` with `inputs[0].amount = 1000e18` of this token, having approved 1000e18.
3. `safeTransferFrom` moves only 990e18 into the gateway (1% fee burned/redirected), but `_orders[commitment][token]` is set to `reducedInputs[0].amount` derived from the full 1000e18 (minus protocol fee if any) — i.e., the ledger claims ~990e18+ more than the gateway actually holds relative to what later orders using the same token expect.
4. Repeat with additional orders using the same fee-on-transfer token; the sum of `_orders[...]` entries for that token now exceeds `IERC20(token).balanceOf(gateway)`.
5. When solvers fill/cancel these orders and `withdraw()` attempts to pay out the full ledgered amounts, the last redeemer's `token.call(transfer(...))` reverts or drains balance intended for a different order/commitment, producing fund loss/lock for legitimate participants — confirmable by comparing to the passing EVM-side test `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, which the Tron contract has no equivalent guard for.
