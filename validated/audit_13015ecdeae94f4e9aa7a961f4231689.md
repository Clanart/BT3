### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes amplified heap allocation before parameter validation, enabling memory exhaustion - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
Analogous to CVE-2017-12432 (untrusted image dimensions driving a huge allocation in `ReadPCXImage`), `ThresholdKeys::read` trusts an attacker-supplied participant count `n` to size an allocation, and performs that allocation before `ThresholdParams::new` validates the parameters. A handful of untrusted bytes therefore triggers a multi-megabyte heap allocation.

### Finding Description
`ThresholdKeys::read` deserializes `t`, `n`, and `i` as raw `u16`s from the reader [1](#0-0) . It then reads the interpolation variant byte, and for `Interpolation::Constant` executes `Vec::with_capacity(usize::from(n))` where `n` is the attacker-controlled `u16` [2](#0-1) . Only afterward is `ThresholdParams::new(t, n, i)` invoked to validate the parameters [3](#0-2) .

With `n = u16::MAX` (65535), each call reserves `65535 * size_of::<C::F>()` bytes — roughly 2 MiB for a 32-byte scalar — triggered by ~10 bytes of input. The subsequent `for _ in 0 .. n` loop fails fast on a short input, but the capacity reservation in `with_capacity` is a real allocation that has already occurred. Additionally, the `verification_shares` loop iterates `1 ..= n` reading a group element per participant [4](#0-3) , and a fully populated input (≈2 MiB) is then stored into a `HashMap` again sized by attacker `n`.

By contrast, nearby code demonstrates awareness of this bug class: `Transaction::read` bounds `commitments_len * each_commitments_len` against `TRANSACTION_SIZE_LIMIT` before allocating [5](#0-4) , and the libp2p codec rejects oversized lengths before `vec![0; len]` [6](#0-5) . `ThresholdKeys::read` has no equivalent bound or validation-first ordering.

### Impact Explanation
Any component deserializing `ThresholdKeys` from attacker-influenced bytes (key material propagated over tributary/p2p messages, processor DB entries, or cosigner flows that call `ThresholdKeys::read`) can be forced to allocate ~2 MiB per call — an amplification of ~10⁵× over input size. Repeated calls in parallel or in a loop exhaust process memory, crashing the node/library. This is a pure unprivileged-remote DoS against availability, matching the CVE's CVSS profile (A:H, no C/I impact).

### Likelihood Explanation
Reachability requires that an unprivileged party can feed bytes into `ThresholdKeys::read` — this function is explicitly in-scope as an untrusted-bytes sink. The trigger is trivial: 10 bytes (`id_len`, `id`, `t`, `n=0xFFFF`, `i`, `interpolation=0`). The amplification is bounded at ~2 MiB per call (rather than unbounded as in PCX), and the backing allocation is freed on error, so the DoS requires sustained or concurrent invocations. This keeps severity at Medium rather than High.

### Recommendation
Validate `t`, `n`, and `i` via `ThresholdParams::new` **before** any count-driven allocation, and avoid speculative `with_capacity` on untrusted counts — either grow the `Vec` incrementally while reading (as `SchnorrAggregate::read` does at `crypto/schnorr/src/aggregate.rs:82-85`, keeping allocation proportional to bytes actually present) or enforce a protocol-level maximum `n` prior to the allocation.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;

// Build a minimal serialization claiming n = 65535 with Constant interpolation,
// but containing no actual scalar/point data.
fn malicious_bytes<C: Ciphersuite>() -> Vec<u8> {
    let mut buf = vec![];
    // curve ID
    buf.extend((u32::try_from(C::ID.len()).unwrap()).to_le_bytes());
    buf.extend(C::ID);
    // t = 1, n = 65535, i = 1
    buf.extend(1u16.to_le_bytes());
    buf.extend(u16::MAX.to_le_bytes());
    buf.extend(1u16.to_le_bytes());
    // Interpolation::Constant => Vec::with_capacity(65535) fires here,
    // before ThresholdParams::new ever runs.
    buf.push(0u8);
    buf
}
```
Each invocation of `ThresholdKeys::<C>::read(&mut malicious_bytes::<C>().as_slice())` reserves ~2 MiB of heap (`65535 * size_of::<C::F>`) at `crypto/dkg/src/lib.rs:608` while consuming only ~10 bytes, before failing inside the read loop — permitting repeated-call memory exhaustion of the deserializing process.
