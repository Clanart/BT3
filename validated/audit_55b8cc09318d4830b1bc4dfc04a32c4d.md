### Title
Lost-Update Race in `AccountsStore.refresh()` Resurrects Removed/Stale Accounts - (File: `app/src/lib/stores/accounts-store.ts`)

### Summary
`AccountsStore` mirrors the exact anti-pattern described in the report: an in-memory global (`this.accounts`, analogous to the contract's `balance`) is read implicitly, mutated only *after* an external asynchronous call resolves, and then unconditionally overwritten without re-checking whether the global changed while the call was in flight. `addAccount` and `removeAccount` mutate `this.accounts` synchronously (no interleaving window), but `refresh()` snapshots-via-map, awaits a network call per account (`fetchUser`, which hits `account.endpoint` — an attacker/Enterprise-server-controlled URL), and then does a blind `this.accounts = await Promise.all(...)`, clobbering whatever `addAccount`/`removeAccount` wrote during the await. [1](#0-0) 

### Finding Description
`refresh()` builds its update from the *pre-await* array reference:
```
public async refresh(): Promise<void> {
    this.accounts = await Promise.all(
      this.accounts.map(acc => this.tryUpdateAccount(acc))
    )
    this.save()
    this.emitUpdate(this.accounts)
}
``` [2](#0-1) 

Each element's promise resolves via `tryUpdateAccount` → `updatedAccount` → `fetchUser(account.endpoint, account.token)`, an HTTP request to an endpoint that, for GitHub Enterprise accounts, is a server the account owner (potentially an attacker running a malicious/compromised GHE instance) controls. [3](#0-2) [4](#0-3) 

Meanwhile `removeAccount` deletes the OS-keychain secret and then filters the shared `this.accounts` array synchronously (read-then-write with no `await` in between, so no interleaving is possible *within* that call):
```
public async removeAccount(account: Account): Promise<void> {
    await this.loadingPromise
    await this.secureStore.deleteItem(getKeyForAccount(account), account.login)
    this.accounts = this.accounts.filter(a => !(a.endpoint === account.endpoint && a.id === account.id))
    this.save()
}
``` [5](#0-4) 

The bug is the *inter*-call race: if `refresh()`'s `Promise.all` is still in flight (waiting on a slow/attacker-delayed `fetchUser` response) when `removeAccount` runs and deletes the account from `this.accounts`, the later-resolving `refresh()` write overwrites `this.accounts` with its pre-removal snapshot — silently reinstating the removed `Account` object (which still carries its previously-loaded `.token` in memory) into the live account list, and persisting it back to disk via `this.save()`. This is structurally identical to the `StakingBase._withdraw` bug: a local variable computed from a stale read of a shared global, finalized by an external call, unconditionally overwrites concurrent legitimate updates to that same global made through a different entry point (`unstake(B)` / `removeAccount`) during the window opened by the external call (`transfer` / `fetchUser`).

There is no reentrancy guard, no versioning/CAS check, and no "did anything change while I was awaiting" verification before the final assignment in `refresh()` — unlike the defensive `stateBeforeLoad`/`stateAfterLoad` comparisons seen elsewhere in the codebase (e.g. `app-store.ts`'s `updateChangesWorkingDirectoryDiff`), which this code path lacks entirely. [6](#0-5) 

### Impact Explanation
An account the user explicitly removed (e.g., because its GHE server was found malicious, its token was compromised, or the user wanted to revoke it) can be silently resurrected into the live, in-memory `accounts` array with a still-populated `.token` field, even though the underlying OS keychain entry was deleted. Any code path that reads `AccountsStore.getAll()`/the emitted account list (dispatcher, git operations selecting credentials, API calls) would continue to treat the account as valid, effectively continuing to authenticate as/trust an account the user believed was revoked. The corrupted list is also persisted to disk via `save()`, making the resurrection durable across restarts (tokens are stripped by `save()`, but the account identity/metadata is not). This matches "silent corruption of what the user commits/pushes"-class impact via corruption of trusted-identity state, since GitHub Desktop derives commit author identity and remote authentication from the account list.

### Likelihood Explanation
`refresh()` is invoked periodically/on user action while accounts include GitHub Enterprise entries whose `endpoint` is attacker-influenced infrastructure; the attacker (a malicious or compromised GHE server operator) can simply delay the HTTP response to `fetchUser` to arbitrarily widen the race window, making the race trivial to win without any special client-side timing skill. The user only needs to perform an unprivileged, natural action (remove/sign out of the account) while a background refresh happens to be outstanding — no local access, malware, or leaked credentials required. The main uncertainty is the exact caller/scheduling of `refresh()` (I located only one call site in `app-store.ts` but could not fully confirm its periodicity/triggers within the available tool budget), which affects how frequently the race window naturally occurs versus needing user-visible delay.

### Recommendation
1. In `refresh()`, don't blindly overwrite `this.accounts`; instead merge results by identity (`endpoint`+`id`) into whatever `this.accounts` currently is at completion time, and drop/ignore entries for accounts that no longer exist in the current `this.accounts` (i.e., were removed during the await).
2. Alternatively, serialize all mutating operations (`addAccount`, `removeAccount`, `refresh`) through a single-flight queue/mutex keyed on the store instance, so a `refresh()` in flight cannot race with a concurrent `removeAccount`/`addAccount`.
3. Add a "state changed under us" guard: capture a version counter incremented on every `this.accounts` mutation; before committing `refresh()`'s result, verify the counter hasn't changed and otherwise recompute/merge instead of overwrite.

### Proof of Concept
1. Add a GitHub Enterprise account whose endpoint is attacker-controlled (or a compromised GHE instance).
2. Trigger `AccountsStore.refresh()` (e.g., via the app's periodic account refresh call in `app-store.ts`) while the malicious GHE server intentionally stalls its response to the `GET /user` (`fetchUser`) request used by `updatedAccount`. [4](#0-3) 
3. While the `fetchUser` request is stalled (i.e., `refresh()`'s `Promise.all` hasn't resolved yet), the user removes that account from GitHub Desktop, invoking `removeAccount`, which deletes the token from the OS keychain and filters `this.accounts`. [5](#0-4) 
4. The attacker's server finally responds; `refresh()`'s `await Promise.all(...)` resolves with the pre-removal snapshot (still containing the removed account with its in-memory `.token`), and `this.accounts = <that array>` overwrites the post-removal state, followed by `this.save()` persisting it. [2](#0-1) 
5. Observe that `AccountsStore.getAll()` / emitted state again returns the "removed" account as active, despite its keychain secret having been deleted — a silent, attacker-timable corruption of the trusted-account state analogous to the stale-balance overwrite in `StakingBase._withdraw`.
