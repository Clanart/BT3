### Title
OP_RETURN data output excluded from weight/vsize calculation underpays the fee, causing the signed transaction to fail relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts a caller-supplied `data` payload which is appended as an OP_RETURN output, but `calculate_weight_vbytes` is only ever invoked with `payments` and `change` — the data output's weight is never counted. The result mirrors the Optimism `l2Gas` underpayment bug class: a parameter supplied at transaction construction causes the produced transaction to carry a fee below the intended rate, potentially below the minimum relay fee, so the transaction the threshold signature was produced for cannot propagate and the payment never completes.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- Lines 193–202: the OP_RETURN output (up to 80 bytes of caller data) is pushed onto `tx_outs`.
- Line 204: `(mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — only `payments` are modeled; the already-created `tx_outs` (including the OP_RETURN output) is ignored.
- Lines 224–235: the change-aware recalculation `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` likewise omits the data output.
- `calculate_weight_vbytes` (lines 62–127) builds a dummy `Transaction` solely from the `payments`/`change` arguments, so the OP_RETURN output is absent from both `weight` and `vbytes`.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change` (line 227) are computed against a vsize that excludes the data output (~90+ extra bytes for an 80-byte push). The actual fee paid (`sum(inputs) - sum(outputs)`, line 138–141) therefore corresponds to a lower effective sat/vbyte rate than `fee_per_vbyte`.
2. The `TooLowFee` guard (line 211) checks `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes`, again using the underestimated vbytes. A transaction whose *actual* fee rate falls under the relay minimum passes validation.
3. The `MAX_STANDARD_TX_WEIGHT` check (line 241) uses `weight` that excludes the data output, so a transaction may pass the check while actually exceeding standardness limits (marginal, ~90 WU·4 bytes for max-size data).

### Impact Explanation
When `data` is supplied, the threshold multisig signs a transaction whose real fee rate is strictly below the requested `fee_per_vbyte`, and possibly below `DEFAULT_MIN_RELAY_TX_FEE` (1 sat/vbyte boundary). Such a transaction will be rejected by `sendrawtransaction`/never relayed, exactly like a bridged deposit with underpaid L2 gas: the signature is produced for a transaction that cannot execute, the payment is never delivered, and the inputs remain locked to a plan/eventuality (`Eventuality(signable.txid())` in `processor/src/networks/bitcoin.rs:830`) that can never complete on chain. The fee discrepancy also silently reduces the change amount accuracy relative to the intended rate.

### Likelihood Explanation
The bug triggers deterministically whenever `data` is `Some` — no adversarial timing or collusion is needed. `data` is a public constructor input (`data: Option<Vec<u8>>`, up to 80 bytes allowed by line 171), and any caller attaching an OP_RETURN (metadata, commitment schemes) hits it. The fee shortfall is proportional to the data size; at the maximum 80 bytes the vsize is underestimated by roughly 88–92 vbytes, enough to drop below the relay minimum when `fee_per_vbyte` is at or near 1.

### Recommendation
Include the OP_RETURN output in the weight/vsize model: either pass the finalized `tx_outs` (or an explicit `data: Option<&[u8]>` parameter) into `calculate_weight_vbytes`, or construct the dummy transaction from `tx_outs` directly. Apply the same inclusion to both the no-change and with-change fee calculations and to the `MAX_STANDARD_TX_WEIGHT` check. Additionally, compute the minimum-relay check against the post-signing estimated vsize of the actual output set.

Concretely: `vbytes` at line 204 counts `inputs + payments` only; the pushed `tx_outs` OP_RETURN (line 195) adds ~92 real vbytes the fee never pays for, and the `TooLowFee` check at line 211 validates the under-estimated size, so construction succeeds while relay fails.
