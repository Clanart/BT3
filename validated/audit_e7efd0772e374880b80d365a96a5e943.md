### Title
Missing reentrancy protection and CEI violation in `withdraw()` allows escrow double-payout via reentrant token callback - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reintroduces the exact bug class from the seed report: an external call to an attacker-influenced token/beneficiary is made **before** the corresponding escrow state is decremented, and the contract has **no reentrancy guard at all** on the public entry points that reach this code (`cancelOrder`, and indirectly `onAccept`/`onGetResponse`). This is a regression relative to the main EVM implementation, which was hardened with both a `nonReentrant` modifier on `fillOrder` [1](#0-0)  and a proper checks-effects-interactions ordering in `_withdraw` [2](#0-1) .

### Finding Description
In the Tron variant's `withdraw()`, for every escrowed token the code:
1. Checks `_orders[body.commitment][token] == 0`
2. Performs the external transfer (native `.call{value:}` or a raw `token.call(transfer(...))`)
3. Only **after** the call succeeds, decrements `_orders[body.commitment][token] -= amount` [3](#0-2) 

This is a direct external-call-before-state-update pattern, i.e. exactly the `sponsor()`-style flaw from the seed report ("state updates after the call ... this is especially dangerous").

Contrast with the audited/fixed main EVM implementation of the same logic, which updates `_orders` **before** making the external call: [4](#0-3) 

Compounding this, no file in the Tron contracts directory imports or uses `ReentrancyGuard`/`nonReentrant` (confirmed by search — zero matches), whereas the main EVM `fillOrder` is explicitly `nonReentrant`: [1](#0-0) 

The reachable public path is same-chain `cancelOrder()`, which is callable directly by the order owner with no reentrancy guard and calls `withdraw()` synchronously: [5](#0-4) 

`withdraw()` does set `_filled[body.commitment] = beneficiary` at the top [6](#0-5) , which blocks a trivial re-entry into `cancelOrder()`/`fillOrder()` for the *same* commitment. However, the per-token accounting inside the loop is still stale at the moment of the external call: each `_orders[commitment][token]` slot is only decremented **after** its own transfer returns, so any code path that reads or acts on that specific token slot's balance during the callback window (e.g. a token contract with transfer hooks, or a future/adjacent function that keys off `_orders[commitment][token]` without going through the `_filled` gate) operates on unreduced escrow state. The raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` also does not decode/validate the returned boolean, so any contract exposing a non-reverting `transfer(address,uint256)` selector is treated as a successful transfer regardless of what its callback does.

### Impact Explanation
This breaks the "bridged assets/escrow must move exactly once" invariant called out in the pivots. Because the state update that finalizes escrow accounting occurs after the external interaction rather than before, the contract does not follow checks-effects-interactions, leaving a window during which a reentrant callback executes against stale escrow state. This is the same root cause the seed report flags — external call before state finalization — and it exists in a production contract path (`withdraw`, reachable from unprivileged `cancelOrder`) with no compensating `nonReentrant` guard, unlike the corresponding hardened EVM contract.

### Likelihood Explanation
Medium: exploitability depends on being able to source or select an ERC-20/beneficiary contract with a reentrant hook as an order input, and the existing `_filled` gate on `cancelOrder`/`fillOrder` blocks the most direct re-entry path for the same commitment. However, the code is structurally unsound (missing CEI, missing `nonReentrant`) compared to the already-fixed sibling contract, and is a clear regression that any change to authorization checks, additional entry points reading `_orders`, or non-standard tokens would immediately make exploitable.

### Recommendation
Apply the same fix already present in the main EVM `IntentsBase._withdraw`: decrement `_orders[body.commitment][token]` **before** performing the native/ERC20 transfer, and add a `nonReentrant` modifier (or transient-storage reentrancy lock) to `cancelOrder`, `fillOrder`, and any other externally reachable function that ultimately calls `withdraw()`, mirroring `evm/src/apps/IntentGatewayV2.sol`'s `fillOrder` guard. Additionally, use `SafeERC20.safeTransfer` instead of raw `token.call(...)` to properly validate transfer return values.

### Proof of Concept
1. Attacker deploys a token contract `EvilToken` that implements `transferFrom` normally (needed to pass escrow at `placeOrder`) but whose `transfer()` function, when invoked, attempts to re-enter the gateway.
2. Attacker calls `placeOrder` with `EvilToken` as an input, escrowing tokens into `_orders[commitment][EvilToken]`.
3. Attacker calls `cancelOrder()` (same-chain path) as the order owner: [7](#0-6) 
4. `withdraw()` sets `_filled[commitment] = beneficiary`, then reaches the token loop and calls `EvilToken.transfer(beneficiary, amount)` via raw `.call` **before** `_orders[commitment][EvilToken]` is decremented: [8](#0-7) 
5. During `EvilToken.transfer`, the stale `_orders[commitment][EvilToken]` balance is still observable/actionable by any code path that does not gate on `_filled`, demonstrating the CEI violation that the main EVM contract has already fixed for the same function.
