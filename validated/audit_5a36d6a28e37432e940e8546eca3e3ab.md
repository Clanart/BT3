## Analysis

The report's root cause — a signature/authentication check that validates payload integrity but does not bind the *destination* to the signed data, permitting a validly-signed message to be replayed against a different target — has a direct analog in `shopify_app`'s webhook verification flow.

### Title
Webhook HMAC verification does not bind the `shop_domain` header to the signed payload, enabling cross-shop webhook replay - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only validates that the `X-Shopify-Hmac-Sha256` header matches an HMAC of the raw request body, computed with the app's shared secret. The `X-Shopify-Shop-Domain` header, which is used downstream to select which shop record/tenant the webhook belongs to, is never included in the HMAC computation and is not itself authenticated.

### Finding Description
`verify_request` computes validity solely from `request.raw_post`: [1](#0-0) 

and `hmac_valid?` in the shared `PayloadVerification` concern signs only the body `data` with the app-wide `ShopifyApp.configuration.secret` (or `old_secret`) — there is no shop-specific key or shop-binding value mixed into the HMAC input: [2](#0-1) 

`shop_domain` is read directly and unauthenticated from a header: [3](#0-2) 

Because the HMAC secret is the same across all shops installing the app (it's the app's client secret, not a per-shop secret), any attacker who installs the app on their own shop can trigger a real webhook (e.g. `app/uninstalled`), capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair — which is a *valid* signature — and replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header. `verify_request` will still accept it because the header is not covered by the signature.

Downstream, generated jobs act on the attacker-chosen `shop_domain` value taken from this unauthenticated header, e.g. the uninstall job destroys whatever `Shop` record matches it: [4](#0-3) 

and the generic webhook job template performs the same shop lookup/scoping pattern: [5](#0-4) 

The `WebhooksController#receive` action forwards `request.headers` (including the attacker-controlled shop-domain header) unmodified to the registry for dispatch: [6](#0-5) 

This mirrors the external report's root cause precisely: a cryptographically valid signature over data (`ExecuteArgs`/webhook body) is accepted without the destination context (`destinationDomain`/`shop_domain`) being cryptographically bound to that signature, so the same valid signed artifact can be "replayed" against a different destination/tenant.

### Impact Explanation
An attacker who is a legitimate (even free/dev) merchant installer of the app can forge a webhook request that the app will accept as authentic for **any other shop domain** of their choosing, because the shop-domain claim is not authenticated. Depending on the job wired to a given webhook topic, this enables cross-shop/cross-tenant state changes using attacker-supplied but Shopify-signature-valid payloads — for example, the generated `AppUninstalledJob` would `destroy` an arbitrary victim `Shop` record (deleting their stored access token / installation state), a denial-of-service/data-loss condition against a shop the attacker does not control. Other custom webhook jobs (e.g. inventory/order sync jobs) that trust `shop_domain` to select the tenant database scope would be similarly exposed to cross-tenant data corruption.

### Likelihood Explanation
Exploitability requires only: (1) the ability to install the target app on any shop (including a free development store) to obtain one valid `(body, HMAC)` pair, and (2) sending a single forged HTTP POST to the app's public webhook endpoint with a substituted `X-Shopify-Shop-Domain` header. No secrets need to be leaked, and no privileged relationship to the victim shop is required, so this is reachable by any anonymous/unrelated merchant.

### Recommendation
Bind the shop context into the authenticated payload rather than trusting the `X-Shopify-Shop-Domain` header independently. In practice: after `hmac_valid?` succeeds, cross-check that the `shop_domain` extracted from the header matches shop identifying information contained within the verified webhook body itself (Shopify webhook payloads for most topics include the shop's ID or domain in the JSON body); reject the request if it doesn't match. Alternatively, use `ShopifyAPI::Webhooks::Request`'s own shop-verification helpers (if they perform such consistency checks) rather than trusting the raw header, and ensure any custom `WebhooksController`/job code cannot process a webhook whose header-declared shop conflicts with the signed body's shop reference.

### Proof of Concept
1. Attacker installs the target app on their own development shop `attacker.myshopify.com`.
2. Attacker uninstalls the app (or triggers any other subscribed webhook topic), causing Shopify to POST a legitimately-signed webhook to the app's `/webhooks` endpoint with headers `X-Shopify-Hmac-Sha256: <valid_hmac>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker intercepts/records this exact `raw_body` and `X-Shopify-Hmac-Sha256` value (both are attacker-visible since it's their own shop's webhook, or they can trivially reconstruct a body triggering the desired job).
4. Attacker sends a new POST request directly to the app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `WebhookVerification#verify_request` → `hmac_valid?(request.raw_post)` succeeds because it never inspects the shop-domain header, per [7](#0-6) .
6. The webhook is processed and the corresponding job (e.g. `AppUninstalledJob`) executes `Shop.find_by(shopify_domain: "victim-shop.myshopify.com").destroy`, per [8](#0-7) , deleting the victim shop's stored session/access token without their consent.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
