### Title
Attacker-controlled FROST preprocess forces point-at-infinity nonce, panicking `x()`/`x_only()` in the Bitcoin BIP-340 HRAm — denial of service during signing - ([File: networks/bitcoin/src/crypto.rs])

### Summary
The analog of the FFmpeg NULL-deref (untrusted input reaches a dereference of an absent value) is a reachable Rust panic on untrusted input. In `networks/bitcoin/src/crypto.rs`, `x()` calls `.expect("point at infinity")` on a `ProjectivePoint` it assumes is non-infinity [1](#0-0) , and `x_only()` unwraps the same assumption [2](#0-1) . `Hram::hram` calls `x(R)` on the aggregate nonce point supplied by the caller [3](#0-2) .

### Finding Description
The doc comment on `Schnorr` admits the panic surface: "This may panic if called with nonces/a group key which are the point at infinity" [4](#0-3) . The nonce `R` passed to `hram` is computed in `BindingFactor::nonces` / `bound` as `D + rho*E` per participant, where `D` and `E` are commitment points deserialized from the peer's preprocess message via `Commitments::read` → `NonceCommitments::read` → `GeneratorCommitments::read` [5](#0-4) [6](#0-5) . `read_G` accepts any canonically encoded curve point — importantly, a malicious signer can choose `D` and `E` as arbitrary non-identity points satisfying `D = -rho_l * E`, because `rho_l` is a public value derived from the `FROST_rho` transcript over `group_key`, `hash_msg(msg)`, and the hash of all transcribed preprocesses [7](#0-6) . A participant who sends their preprocess last (or who colludes with the message/coordinator ordering) computes all other participants' contributions, derives `rho` for their own index, and submits `E = g`, `D = -rho_l * g`. Their bound nonce commitment is then `D + rho_l*E = identity`. When `B.nonces()` aggregates commitments, or when `verify_share`'s statements / `verify`'s `R` become infinity, `hram` invokes `x(&infinity)` and the process panics on `.expect("point at infinity")` inside `sign_share` (each participant's `sign` call) or inside `complete`/`algorithm.verify` [8](#0-7) [9](#0-8) . None of the deserialization (`Commitments::read`), `sign` validation (`validate_map`, index checks), or `process_addendum` rejects a preprocess whose bound commitment sums to infinity — the identity check only exists implicitly as this `expect`.

### Impact Explanation
A single malicious signing participant, using only their broadcast preprocess bytes (fully public input channel), reliably panics the `sign`/`complete` path of every honest participant in a Bitcoin FROST session — permanent denial of service of the signing protocol, matching the CVE class (medium-severity availability impact via crafted input). It also produces an unhandled-abort channel: since `panic!` unwinds past `FrostError`, an integrator wrapping signing in `catch_unwind`-less async code aborts the whole task.

### Likelihood Explanation
Requires only that the attacker be a threshold participant able to order or adaptively choose their preprocess after learning the other preprocesses (or the message), which is standard in FROST deployments where the coordinator collects preprocesses before broadcasting. The rho transcript is deterministic and fully computable by the attacker, so `D = -rho*E` is trivial to construct.

### Recommendation
In `Hram::hram` (and `x`/`x_only`), return a graceful failure or define behavior for the point at infinity (e.g., hash a canonical 32-byte placeholder) rather than `expect`. Additionally, in `BindingFactor::bound`/`nonces` or `Commitments::read`, reject bound nonces/commitment sums equal to the identity with `FrostError::InvalidCommitments` instead of letting them flow into HRAm.

### Proof of Concept
Conceptual, against `crypto/frost` + `networks/bitcoin` `Schnorr`:

1. Honest signers broadcast `Preprocess` messages; attacker `l` waits, collects all commitments and `msg`.
2. Attacker builds the rho transcript (`FROST_rho` with `group_key`, `C::hash_msg(msg)`, `hash_commitments(preprocesses_challenge)`) locally and computes their binding factor `rho_l` exactly as `BindingFactor::calculate_binding_factors` does [10](#0-9) .
3. Attacker publishes preprocess with `E = C::G::generator()`, `D = -(rho_l) * C::G::generator()` for each generator slot — both validly encoded non-identity points, passing `Commitments::read` [11](#0-10) .
4. Every honest signer calls `SignMachine::sign` → `B.nonces`/`bound` produces identity for the attacker's nonce contribution (and the aggregate `R` can likewise be forced to infinity by spanning multiple generator slots) → `IetfSchnorr`/`Hram::hram` calls `x(&ProjectivePoint::IDENTITY)` → `expect("point at infinity")` panics [1](#0-0) .

Caveat: whether the panic fires inside `sign_share` (each signer's `sign`) or only inside `verify`/`complete` depends on where `hram` is invoked relative to the identity point, but in both cases the panic is reachable purely from attacker-controlled preprocess bytes.

  fn complete(
    self,
    mut shares: HashMap<Participant, SignatureShare<C>>,
  ) -> Result<A::Signature, FrostError> {
    let params = self.params.multisig_params();
    validate_map(&shares, self.view.included(), params.i())?;

    let mut responses = HashMap::new();
    responses.insert(params.i(), self.share);
    let mut sum = self.share;
    for (l, share) in shares.drain() {
      responses.insert(l, share.0);
      sum += share.0;
    }

    // Perform signature validation instead of individual share validation
    // For the success route, which should be much more frequent, this should be faster
    // It also acts as an integrity check of this library's signing function
    if let Some(sig) = self.params.algorithm.verify(self.view.group_key(), &self.Rs, sum) {
      return Ok(sig);
    }

    // We could remove blame_entropy by taking in an RNG here
    // Considering we don't need any RNG for a valid signature, and we only use the RNG here for
    // performance reasons, it doesn't feel worthwhile to include as an argument to every
    // implementor of the trait
    let mut rng = ChaCha20Rng::from_seed(self.blame_entropy);
    let mut batch = BatchVerifier::new(self.view.included().len());
    for l in self.view.included() {
      if let Ok(statements) = self.params.algorithm.verify_share(
        self.view.verification_share(*l),
        &self.B.bound(*l),
        responses[l],
      ) {
        batch.queue(&mut rng, *l, statements);
      } else {
        Err(FrostError::InvalidShare(*l))?;
      }
    }

    if let Err(l) = batch.verify_vartime_with_vartime_blame() {
      Err(FrostError::InvalidShare(l))?;
    }

    // If everyone has a valid share, and there were enough participants, this should've worked
    // The only known way to cause this, for valid parameters/algorithms, is to deserialize a
    // semantically invalid FrostKeys
    Err(FrostError::InternalError("everyone had a valid share yet the signature was still invalid"))
  }
