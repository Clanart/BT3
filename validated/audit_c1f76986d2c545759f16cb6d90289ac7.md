## Analysis

The Cozy Finance report describes a structural pattern: a safety check meant to protect against a bad admin action instead creates a **permanent lockout** because the guard condition (utilization ≤ 100%) can only be *pushed further away* by external/market forces, and the owner has no path to satisfy it without the very update being blocked.

The closest local analog in Hyperbridge is the `CannotChangeFeeToken` invariant in `updateHostParamsInternal`, guarding `EvmHost.updateHostParams`: [1](#0-0) 

```solidity
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
```

Unlike the Cozy bug, the deadlock condition here (`balance != 0`) is not merely a self-inflicted market state — it is a public, unprivileged, and freely repeatable state that anyone can set by sending 1 wei of the old fee token to the `EvmHost` contract, since the contract has no gate on receiving ERC-20 transfers (`receive()` only guards native ETH, and there is no `onlyOwner`/allowlist on inbound ERC-20 transfers): [2](#0-1) 

`withdraw()` — the only way to zero the old-token balance — is itself gated to `hostManager` (cross-chain governance only): [3](#0-2) 

Because governance's fee-token migration is a two-step, cross-chain flow (`withdraw` to sweep, then a separate `updateHostParams` dispatched via `HostManager.onAccept`), an unprivileged attacker can grief the sequence indefinitely: after governance sweeps the old token to zero, the attacker re-donates a trivial amount of the old fee token before the `updateHostParams` message lands, re-triggering `CannotChangeFeeToken` and blocking the migration again.

### Title
Fee-token migration is permanently griefable by an unprivileged donation of the old fee token - (File: `evm/src/core/EvmHost.sol`)

### Summary
`updateHostParamsInternal` refuses any `HostParams` update that changes `feeToken` whenever the `EvmHost` contract's balance of the *old* fee token is non-zero. Since any address can transfer the old fee token into the host with an ordinary ERC-20 `transfer` (no access control on inbound transfers), an attacker can perpetually re-arm this guard immediately after governance's `withdraw()` sweep and before the follow-up `updateHostParams()` governance message lands, permanently blocking the protocol from migrating off a compromised, depegged, or otherwise undesirable fee token.

### Finding Description
`EvmHost.updateHostParams` is restricted to `hostManager` (cross-chain governance), and internally calls `updateHostParamsInternal`: [4](#0-3) [1](#0-0) 

The invariant is intended to stop governance from stranding held funds by switching away from a token while a balance remains. But nothing prevents a third party from *creating* that balance. Any account can call `IERC20(oldFeeToken).transfer(hostAddress, 1)` at will — this requires no permission and costs only gas plus a negligible token amount (or even a token the attacker mints/controls if the "old" fee token is attacker-influenced in an edge case, though the baseline case only needs 1 wei of the legitimate current fee token).

Migrating the fee token is a two-transaction governance flow:
1. `HostManager.onAccept` → `withdraw()` (sweeps the old token to zero) — restricted to `hostManager`/governance.
2. A later cross-chain governance message → `updateHostParams()` with the new `feeToken`. [5](#0-4) 

Between step 1 and step 2 there is an unavoidable window (cross-chain message delivery time), during which an attacker who is watching the mempool/chain for the `withdraw` sweep can immediately re-fund the host with a trivial amount of the old fee token, re-arming `CannotChangeFeeToken` before the migration message arrives. This can be repeated indefinitely, at the attacker's discretion, for as long as they are willing to keep re-donating dust.

### Impact Explanation
This is a logic attack on a privileged host-management function: an unprivileged actor can indefinitely deny Hyperbridge governance the ability to change `feeToken` on an `EvmHost`. If the currently configured fee token becomes compromised, depegged, or exploited (e.g., a fee-on-transfer bug, an oracle manipulation vector, or a rebasing/inflation bug is discovered in the token contract), governance's only mitigation — migrating to a new, sound fee token — can be permanently blocked by this griefing vector, prolonging exposure and increasing the risk of fund loss from continuing to accrue/hold value in the compromised token. It also blocks routine token migrations (e.g., planned stablecoin upgrades), degrading protocol operability with no way to route around it short of a contract upgrade.

### Likelihood Explanation
Likelihood is high once an attacker is motivated: the griefing action is a single unrestricted `transfer()` call costing gas plus 1 unit of the fee token, requires no privileged role, no compromised keys, and no race against block production beyond simple mempool monitoring of the `withdraw` transaction. The attack is fully repeatable and cheap relative to the value it can indefinitely hold hostage.

### Recommendation
Do not gate the fee-token change on the *current* on-chain balance being exactly zero. Instead:
- Have `withdraw()`/`updateHostParams()` be combined into a single atomic governance action that sweeps and switches in one transaction (removing the vulnerable window), or
- Replace the strict `balance != 0` check with a governance-supplied explicit acknowledgment/override (similar to Cozy's "manual override" fix) so a small unsweepable dust balance from a griefer cannot block migration, or
- Track and sweep balances internally rather than relying on `IERC20.balanceOf`, so unsolicited inbound transfers cannot influence the invariant.

### Proof of Concept
1. Governance dispatches a `withdraw` request via `HostManager.onAccept` to sweep the old `feeToken` balance from `EvmHost` to zero, as a precondition for switching `feeToken` in a subsequent `updateHostParams` call.
2. An attacker observes the `withdraw` transaction/receipt (or simply front-runs proactively) and calls `oldFeeToken.transfer(evmHostAddress, 1)` — no permission required.
3. When the governance-dispatched `updateHostParams(params)` with `params.feeToken != oldFeeToken` is finally delivered by a relayer and executed, `updateHostParamsInternal` reads `IERC20(oldFeeToken).balanceOf(address(this)) != 0` and reverts with `CannotChangeFeeToken`, exactly as exercised in the existing test: [6](#0-5) 

4. The attacker repeats step 2 after every subsequent governance attempt, indefinitely blocking the fee-token migration.

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
