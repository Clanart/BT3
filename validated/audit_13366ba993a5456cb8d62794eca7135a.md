## Title
Escrow decrement performed *after* external token transfer in `withdraw()` allows reentrant double-redemption of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron build of `IntentGatewayV2` mirrors the reported Aave bug class — a state-accounting update ordered after the balance-affecting action, so a stale value is read/left available for reuse. `onAccept` → `withdraw()` transfers escrowed tokens to the beneficiary **before** decrementing `_orders[commitment][token]`, and the entry function carries no reentrancy guard.

### Finding Description
`onAccept` dispatches `RedeemEscrow`/`RefundEscrow` requests straight into `withdraw()`: [1](#0-0) 

`withdraw()` itself performs the external call/transfer for each token **before** subtracting the amount from the escrow ledger: [2](#0-1) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");   // external call FIRST
    ...
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); // external call FIRST
    ...
}
_orders[body.commitment][token] -= amount;   // stale accounting mutated AFTER the payout
```

This is the exact analog of the reported bug: the report showed `updateInterestRates` (a stateful calculation) running before `burn` (the balance mutation) so the rate calculation read stale debt. Here the escrow-balance check (`_orders[commitment][token] == 0`) and the debit both happen using a value that is still non-decremented at the moment the external call executes — i.e., the "commitment/state" is stale for the duration of the external call. Because native-token transfers use a raw low-level `.call{value:}` and ERC-20 transfers use a raw `.call` (not `safeTransfer`, and no `nonReentrant` modifier on `onAccept`/`withdraw`), a beneficiary contract (or a malicious/callback-capable ERC-20) can re-enter `onAccept`/`withdraw` for the *same commitment* while `_orders[commitment][token]` still reflects the pre-payout amount, and redeem the same escrow entry multiple times before the decrement is applied.

Compare this to the "correct" pattern used in the primary EVM `IntentsBase._withdraw`, which decrements the escrow slot **before** making the transfer: [3](#0-2) 

The Tron variant inverted this ordering, reintroducing the stale-state window the main EVM implementation deliberately avoids.

### Impact Explanation
This is a real fund-loss / double-settlement primitive on custodied bridge escrow: a beneficiary (attacker-controlled receiving contract, or a token with transfer hooks) that receives the `RedeemEscrow`/`RefundEscrow` payout can re-enter and drain the same escrowed amount more than once from the gateway's token/native balance, directly stealing bridged funds meant for other orders or the protocol. This matches the bounty's explicit inclusion of "stealing or loss of funds" and "replay/double-claim/double-settlement," and requires no relayer, prover, or admin compromise — only a normal `onAccept` call authenticated as coming from the paired gateway/host (the standard cross-chain path), with the beneficiary being attacker-controlled.

### Likelihood Explanation
The call path is reachable through the standard message flow (a legitimately delivered `RedeemEscrow`/`RefundEscrow` POST triggers `onAccept` → `withdraw`), requiring only that the order's beneficiary/solver address point at an attacker-controlled contract — something fully within an ordinary unprivileged user's control when placing/filling orders. No malicious relayer or governance action is needed. `onAccept` has no reentrancy guard, and native transfers/ERC-20 transfers both use unguarded low-level `.call`.

### Recommendation
Reorder `withdraw()` to update `_orders[body.commitment][token] -= amount` (and the fees/`_filled` bookkeeping) **before** performing any external call or token transfer, matching the pattern already used in `IntentsBase._withdraw`. Additionally add a reentrancy guard to `onAccept`/`withdraw` and switch raw `.call` ERC-20 transfers to `SafeERC20.safeTransfer`.

### Proof of Concept
1. Attacker places/fills an order (or is named beneficiary) with `beneficiary` set to an attacker-controlled contract implementing a `receive()`/ERC-777-style hook, or uses an ERC-20 token with a transfer callback.
2. A `RedeemEscrow` (or `RefundEscrow`) request for `commitment` is delivered and processed by `onAccept`, which calls `withdraw(body, ...)`.
3. Inside `withdraw`, the native `.call{value: amount}` (or ERC-20 `.call(transfer(...))`) triggers the attacker's callback **before** `_orders[body.commitment][token] -= amount` executes.
4. From the callback, the attacker re-enters `onAccept`/`withdraw` for the same `commitment`/`token`: since `_orders[body.commitment][token]` has not yet been decremented, the `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` check still passes, and the beneficiary receives another full payout of `amount`.
5. Repeat until the contract's actual token/native balance for that asset is drained, exceeding what was legitimately escrowed for the order — a double (or N-fold) settlement of the same escrow entry.

Note: I could not find an explicit `nonReentrant` modifier anywhere in this file within the excerpts retrieved, and the main-EVM sibling contract's equivalent function performs the decrement-before-transfer correctly, reinforcing that this is a local regression in the Tron variant rather than an intentional/duplicated safe design; a live Devin session with full repo access should verify there is no guard elsewhere in the inheritance chain (e.g., `HyperApp`) that might mitigate this before treating it as fully confirmed.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
