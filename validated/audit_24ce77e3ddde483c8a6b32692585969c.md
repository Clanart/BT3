### Title
Legacy `EnsureInstalled` derives `current_shopify_domain`/`installed_shop_session` from unauthenticated `params[:shop]`, enabling cross-shop session confusion when the new embedded auth strategy is disabled - ([File: app/controllers/concerns/shopify_app/ensure_installed.rb])

### Summary
When `ShopifyApp.configuration.use_new_embedded_auth_strategy?` is `false` (the legacy/default-off path), `EnsureInstalled#current_shopify_domain` sanitizes and returns `params[:shop]` with no cryptographic verification, and `installed_shop_session` uses that value to fetch the *stored offline session* for whatever shop name the attacker supplies via `SessionRepository.retrieve_shop_session_by_shopify_domain`. No HMAC, ID-token, or cookie check is performed inside `EnsureInstalled` itself before this session object is exposed to `check_shop_known` (`@shop`) and to any controller action that reads `installed_shop_session`/`current_shopify_domain`.

### Finding Description
`current_shopify_domain` (lines 29-38) reads `params[:shop]`, runs it only through `ShopifyApp::Utils.sanitize_shop_domain` (format validation, not authentication), and memoizes it as `@shopify_domain`. `installed_shop_session` (lines 40-42) passes that attacker-controlled domain directly to `SessionRepository.retrieve_shop_session_by_shopify_domain`, returning the previously-stored offline (or online) session — including its access token — for *any* shop name that has ever completed OAuth with the app, regardless of who is making the current request.

In the legacy flow (`before_action :check_shop_known` / `:validate_non_embedded_session`, lines 24-25, 50-59, 73-82), the only gate against an attacker naming a different shop is `validate_non_embedded_session`, which fires a live `GET /admin/shop.json` call using the (attacker-selected) session and redirects to login only on a `401`. This check validates that the *stored token for that shop* still works — it does not validate that the *current requester* is that shop. It contains no HMAC verification, no session-token/JWT check, and no `ActiveSupport::SecurityUtils.secure_compare` of any signed value; it is purely "is params[:shop] well-formed and does that shop have a currently-valid token on file." A controller/action that then reads `@shop` (set in `check_shop_known`) or calls `installed_shop_session`/`current_shopify_domain` again to make further API calls is operating on the victim shop's session and token merely because the attacker supplied `?shop=victim-shop.myshopify.com`.

By contrast, when the new embedded auth strategy is enabled, `EnsureInstalled` includes `ShopifyApp::TokenExchange`, whose `current_shopify_domain` override (`authenticated_shopify_domain_from_token`) derives the shop from a verified ID token (`current_shopify_session&.shop || jwt_shopify_domain`), and `reject_mismatched_requested_shopify_domain` explicitly rejects (`head(:unauthorized)`) any mismatch between the requested `shop` param and the authenticated domain. That protection is absent in the legacy path that the base `EnsureInstalled#current_shopify_domain`/`#installed_shop_session` methods implement. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Impact Explanation
An unprivileged merchant/attacker who knows or guesses a victim shop's `myshopify.com` domain (these are often guessable/enumerable business names, not secrets) can, on any controller including only `EnsureInstalled` in the legacy configuration, cause `installed_shop_session`/`@shop`/`current_shopify_domain` to resolve to the victim shop's stored session and access token. If the action performs any API call using that session (a documented, plausible pattern — `validate_non_embedded_session` itself does exactly this), the attacker's request is served with the victim's Admin API token — a cross-shop/tenant session confusion and unauthorized data access, matching Shopify's "Authentication Bypass"/"Broken Access Control" impact class. It does not, however, exfiltrate the token to the attacker's browser directly (the token stays server-side); the practical exploitation is bounded by what the app's action does with the resolved session/domain.

### Likelihood Explanation
Exploitability depends on: (1) the host app running with `use_new_embedded_auth_strategy?` disabled (the pre-token-exchange, legacy default for many existing installs), (2) the victim shop already having installed the app (a session exists in `SessionRepository`), and (3) a controller action using `EnsureInstalled` alone that reads/uses `@shop`/`installed_shop_session`/`current_shopify_domain` for authorization or API calls beyond the built-in `validate_non_embedded_session` shop-token check. Condition 3 is an omission a developer could easily make since `EnsureInstalled`'s only documented purpose is "ensure installed," not "authenticate the current caller," and the concern's public API (`installed_shop_session`, `current_shopify_domain`) invites exactly this usage. This is a design gap in a widely-reused gem concern rather than a one-off misconfiguration, making it moderately likely to surface in real apps still on the legacy strategy.

### Recommendation
Do not treat `params[:shop]` as authenticated context. In the legacy (non-token-exchange) `EnsureInstalled` path, require verification equivalent to `TokenExchange#reject_mismatched_requested_shopify_domain` — i.e., only allow `installed_shop_session`/`current_shopify_domain` to resolve a shop that is also proven by a signed ID token, HMAC, or an existing verified session cookie, and reject/redirect on mismatch instead of silently trusting the raw param. At minimum, add documentation and a runtime guard so `EnsureInstalled`-only controllers cannot be used for actions that make authenticated API calls without such verification, and encourage migration to `use_new_embedded_auth_strategy?` / `TokenExchange`, which already implements this check.

### Proof of Concept
```ruby
# test/controllers/concerns/ensure_installed_domain_spoof_test.rb
class EnsureInstalledDomainSpoofTest < ActionController::TestCase
  class FakeController < ActionController::Base
    include ShopifyApp::EnsureInstalled
  end

  test "installed_shop_session resolves to whatever shop param is supplied, with no auth check" do
    victim_session = ShopifyAPI::Auth::Session.new(id: "offline_victim-shop.myshopify.com",
                                                     shop: "victim-shop.myshopify.com",
                                                     access_token: "victim-token")
    ShopifyApp::SessionRepository.store_shop_session(victim_session)

    controller = FakeController.new
    controller.params = ActionController::Parameters.new(shop: "victim-shop.myshopify.com")

    # No JWT, no HMAC, no cookie, no proof of being victim-shop's client.
    assert_equal "victim-shop.myshopify.com", controller.current_shopify_domain
    assert_equal victim_session, controller.installed_shop_session
    assert_equal "victim-token", controller.installed_shop_session.access_token
  end
end
```
This demonstrates that `current_shopify_domain`/`installed_shop_session` return a real, previously-installed shop's session/token based solely on an attacker-supplied `params[:shop]`, with zero token-verification step inside `EnsureInstalled` (legacy path), confirming the attacker-capability boundary described in the question.

      if params[:shop].blank?

      url = URI(ShopifyApp.configuration.login_url)

      url.query = URI.encode_www_form(
        shop: params[:shop],
        host: params[:host],
        return_to: request.fullpath,
      )

    end

    def validate_non_embedded_session
      return if loaded_directly_from_admin?

      client = ShopifyAPI::Clients::Rest::Admin.new(session: installed_shop_session)
      client.get(path: "shop")
    rescue ShopifyAPI::Errors::HttpResponseError => error
      ShopifyApp::Logger.info("Shop offline session no longer valid. Redirecting to OAuth install")
      redirect_to(shop_login) if error.code == 401
      raise error if error.code != 401
    end

    def current_shopify_domain
      authenticated_shopify_domain_from_token
    rescue *INVALID_SHOPIFY_ID_TOKEN_ERRORS => e
      respond_to_invalid_shopify_id_token(e)
    end

    private

    def authenticated_shopify_domain_from_token
      current_shopify_session&.shop || jwt_shopify_domain
    end

    def reject_mismatched_requested_shopify_domain
      requested_domain = requested_shopify_domain
      return false if requested_domain.blank?

      authenticated_domain = authenticated_shopify_domain_from_token
      return false if authenticated_domain.blank? || authenticated_domain == requested_domain

      ShopifyApp::Logger.debug("Shop context validation failed")
      head(:unauthorized)
      true
    end
