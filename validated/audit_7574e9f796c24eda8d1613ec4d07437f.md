### Title
Missing-key indexing panic in `Decryption::decrypt_with_proof` allows unauthenticated node crash via crafted blame participant - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2026-34271 (low-privileged, network-reachable input causing a complete hang/crash of the server), `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with the `[]` operator, which panics when the supplied `decryptor` participant index has no registered encryption key. An unprivileged party who can cause a blame/accusation flow to be evaluated with a `decryptor` index that was never registered (including the local participant's own index, whose encryption key is never inserted into `enc_keys`) triggers an unconditional panic — a repeatable, remotely triggerable crash of the DKG participant.

### Finding Description
`Encryption::new` creates `Decryption { enc_keys: HashMap::new() }`, and the only insertion path is `Decryption::register`, which is invoked from `SecretShareMachine::verify_r1` once per *other* participant's `EncryptionKeyMessage` (`crypto/dkg/pedpop/src/lib.rs:315`). The local participant's own index `self.params.i()` is never inserted — `verify_r1` skips it (`let Some(msg) = commitment_msgs.remove(&l) else { continue }` and the map intentionally omits `ours` per `validate_map`).

In `decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:366-397`), after the Schnorr PoP check passes, the code does:

```rust
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],
)
```

`HashMap`'s `Index` impl panics on absent keys. Nothing in `decrypt_with_proof` validates that `decryptor` is a participant distinct from the local party or present in `enc_keys`. The `decryptor` value originates from the caller's blame context — i.e., the accuser/faulty participant indexes carried in blame data that an external party supplies (e.g., the `InvalidDkgShare` path, which deserializes attacker-chosen `Participant` values and routes them to the blame machine that calls `decrypt_with_proof`).

Two reachable panic cases:
1. `decryptor == self.params.i()` — never inserted into `enc_keys`, always panics.
2. `decryptor` = any participant index whose `EncryptionKeyMessage` was not registered (e.g., a participant omitted from the commitments round, or a garbage index if the caller doesn't range-check before calling).

Because the PoP signature check happens *before* the indexing, the attacker must provide a message with a valid `pop` under `msg.key` — but they can trivially generate this themselves: choose any scalar `key`, form `msg.key = key * G`, and produce a valid `SchnorrSignature` for `pop_challenge(context, R, msg.key, from, msg_bytes)` since `from` and `msg` are attacker-controlled. So the panic is reachable with fully attacker-generated public inputs.

### Impact Explanation
A single crafted blame/accusation message deterministically panics the target's DKG/blame evaluation. This is a "frequently repeatable crash" — the same class of complete-DoS impact as the reference CVE (CVSS 6.5, availability-only). A crashing validator/processor cannot complete the DKG or signing sessions it participates in; repeated submissions abort it every time it processes the malicious blame data, effectively knocking the honest participant out of the threshold set and potentially halting dependent signing work.

### Likelihood Explanation
High. The attacker needs only to trigger the blame-decryption path with a `decryptor` index absent from `enc_keys` — most simply the victim's own participant index. All inputs are public/attacker-controlled bytes (participant indexes, encrypted-message bytes, PoP signature). No threshold collusion, leaked keys, or broken-BFT assumptions are needed. The panic is deterministic, not probabilistic.

### Recommendation
Replace `self.enc_keys[&decryptor]` with a checked lookup:

```rust
let Some(enc_key) = self.enc_keys.get(&decryptor) else {
  Err(DecryptionError::InvalidProof)?
};
```

and additionally reject `decryptor == i` at the `BlameMachine`/caller layer with a typed error rather than an indexing panic. All participant indexes derived from deserialized blame transactions should be validated against `params.all_participant_indexes()` before reaching `decrypt_with_proof`.

### Proof of Concept
Conceptual trigger (assuming the `BlameMachine` blame API forwards a caller-supplied `accuser`/`decryptor` participant to `Decryption::decrypt_with_proof`):

```rust
// Victim completed calculate_share; enc_keys contains every participant
// EXCEPT victim's own index i_v.

// Attacker constructs a syntactically valid EncryptedMessage:
let key = Zeroizing::new(C::random_nonzero_F(rng));
let pub_key = C::generator() * key.deref();
let nonce = Zeroizing::new(C::random_nonzero_F(rng));
let msg_bytes = SecretShare(C::F::random(rng).to_repr());
let pop = SchnorrSignature::sign(
  &key, nonce,
  pop_challenge::<C>(context, C::generator() * nonce.deref(), pub_key, from, msg_bytes.as_ref()),
);
let forged_msg = EncryptedMessage { key: pub_key, pop, msg: msg_bytes };
let proof = EncryptionKeyProof { key: ecdh-anything, dleq: any_proof };

// Trigger blame evaluation naming the VICTIM's own index as decryptor.
// enc_keys[i_v] was never inserted (register() is only called for l != i_v),
// so `self.enc_keys[&decryptor]` panics before the DLEq is even checked.
decryption.decrypt_with_proof(accuser, i_v /* == decryptor == victim's own index */, forged_msg, Some(proof));
// => thread panic: "key not found" — repeatable node crash.
```

Even when the DLEq proof would ultimately fail, the `enc_keys[&decryptor]` indexing occurs while *building the argument list* to `dleq.verify`, so the panic precedes any verification failure and cannot be caught as a `DecryptionError`.

Note on scope/confidence: the indexing panic in `decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:388`) is verified directly in the in-scope crate. The exact call chain from the coordinator's blame transaction handler into `BlameMachine`/`decrypt_with_proof` was not fully traced within the available context; the finding assumes the blame API exposes the `decryptor`/`accuser` participant index from deserialized blame data, which is consistent with the `InvalidDkgShare` transaction carrying attacker-supplied `Participant` values.
