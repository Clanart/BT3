## Analysis

The core broken invariant in the seed report is: **a state update meant to prevent re-use of a slot happens on a copy/deferred basis instead of before the effect it's supposed to guard**, so the guard can be bypassed and the same value gets processed more than once.

Reasoning through Hyperbridge's own escrow-settlement code, I found a direct structural analog: the canonical `_withdraw` implementation follows checks-effects-interactions (decrement the escrow **before** the external token transfer), but a parallel/ported implementation of the exact same logic reverses that order, transferring tokens **before** decrementing the escrow accounting.

### Title
Escrow decrement performed after external token transfer in `IntentGatewayV2.withdraw` (Tron port) breaks checks-effects-interactions, enabling double-withdrawal via a malicious escrowed token - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentsBase._withdraw` (the audited/canonical implementation) decrements `_orders[commitment][token]` before performing the external transfer: [1](#0-0) 

The Tron contracts directory contains a separately-maintained copy of the same intents settlement logic, `IntentGatewayV2.withdraw`, where the ordering is reversed — the external `token.call(...transfer...)` executes first, and `_orders[body.commitment][token] -= amount;` only runs afterward: [2](#0-1) 

This is the same class of bug as the seed report: a critical accounting mutation (`delete`/decrement of escrowed-value state) that should gate re-entry is deferred until *after* an external, attacker-influenceable call, instead of before it.

### Finding Description
`withdraw(body, isRefund)` is invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` message kinds and from `onGetResponse`: [3](#0-2) [4](#0-3) 

Inside the token loop, for each entry in `body.tokens` (which is `order.inputs`, fully attacker-controlled at `placeOrder` time), the contract only checks that `_orders[body.commitment][token] != 0` (not that it covers `amount`), then performs the external transfer, and only afterward subtracts `amount`: [5](#0-4) 

Because `token` is an address the order creator fully controls (it is whatever ERC-20 the user chose to escrow as an input at `placeOrder`), an attacker can escrow a self-deployed token whose `transfer()` implementation executes arbitrary code before returning. At the moment that code runs, `_orders[body.commitment][token]` still holds its pre-decrement (non-zero) value, so any re-entrant path back into `withdraw` for the same commitment/token would pass the `!= 0` guard again and receive a second payout before the first decrement is ever applied — the exact "guard mutated too late to be effective" pattern from the seed report, just with `-=` in place of `delete`.

### Impact Explanation
If reachable, this allows draining escrowed input tokens beyond what was actually deposited for an order — i.e., theft/loss of bridged funds and double-settlement of the same escrow commitment, which is squarely within the bounty's "stealing or loss of funds" / "replay/double-claim/double-settlement" categories. The canonical EVM path (`IntentsBase._withdraw`) already codifies the correct ordering, confirming the Hyperbridge team is aware this ordering matters for safety — the Tron port simply does not follow it.

### Likelihood Explanation
The attacker only needs to be the creator of their own order (an unprivileged, permissionless action — anyone can call `placeOrder`) and choose a token they control as one of the order's inputs; no relayer, prover, or admin compromise is required. The remaining constraint is finding a re-entry path back into `withdraw` for the same commitment from within the malicious token's `transfer` call (e.g., via any reachable code path that re-triggers `onAccept`/`onGetResponse` processing for the same in-flight message, or any other function that ultimately calls `withdraw` again for the same `body.commitment`/`token` pair before the decrement lands). Given `onAccept`/`onGetResponse` are `onlyHost`-gated, exploitability depends on whether the host/relayer message-processing flow can be induced to reprocess the same commitment while the first invocation's external call is still on the stack (e.g., cross-function reentrancy into another public entrypoint that reads/writes `_orders` for the same commitment, or nested dispatch/callback flows). This needs to be confirmed against the concrete Tron `Host`/dispatch implementation, but the vulnerable ordering itself is unambiguous and already deviates from the fixed reference implementation.

### Recommendation
Mirror `IntentsBase._withdraw`'s ordering in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`: decrement `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` entry) **before** performing any external `token.call`/native transfer, so the escrow-accounting guard is effective against any re-entrant call rather than being satisfiable on the same, stale value twice.

### Proof of Concept
```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        // VULNERABLE: external call happens while _orders[...] is still non-zero
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();

        // Effect applied only AFTER the external call returns
        _orders[body.commitment][token] -= amount;
        unchecked { ++i; }
    }
    ...
}
```
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer()` re-enters the bridge's message-processing path for the same order commitment/token before returning.
2. Attacker calls `placeOrder` escrowing `EvilToken` as an input.
3. On fill/redeem, `withdraw` is invoked; during `EvilToken.transfer()`, the attacker's reentrant call reaches `withdraw` again for the same `body.commitment`/`token` — `_orders[commitment][token]` is still non-zero (not yet decremented), so the `UnknownOrder` guard does not fire and a second transfer is issued.
4. `_orders[commitment][token]` is only decremented once per completed loop iteration return, so the escrow accounting under-counts the actual amount paid out, resulting in more tokens leaving the gateway than were ever escrowed for that commitment.
