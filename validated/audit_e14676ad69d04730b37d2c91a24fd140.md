### Title
Silent ERC-20 `transfer` failure permanently burns escrowed funds in `IntentGatewayV2.withdraw()` (Tron) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron build of `IntentGatewayV2` settles escrowed intent funds using a raw low-level `.call` to the ERC-20 `transfer` selector and only checks the outer call's `success` boolean, never decoding/validating the ERC-20 return data. Any ERC-20 token that follows the standard's non-reverting failure mode (returning `false` instead of reverting on insufficient balance/blacklist/etc.) will report `success = true` even though no tokens moved, while the contract still decrements escrow accounting and marks the commitment as filled — permanently locking the beneficiary's funds inside the gateway with no remaining path to recover them.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is the internal settlement routine invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` and from `onGetResponse` for refund-via-timeout flows: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
```

The ERC-20 branch only checks that the low-level `.call` did not revert (`success`). It never inspects the ABI-encoded return payload to confirm the token actually returned `true`. Per ERC-20, `transfer` is permitted to return `false` on failure instead of reverting (e.g. some legacy/rebasing/pausable/blacklist tokens, or fee-on-transfer tokens that silently move less than requested). In that case:
- `success` from the low-level call is `true` (the callee executed without reverting),
- `TransferFailed()` is never raised,
- `_orders[body.commitment][token] -= amount` still executes, zeroing/reducing the escrow entry,
- `_filled[body.commitment] = beneficiary` is set unconditionally at the top of the function.

The same unchecked pattern recurs for the fee-token payout and for `SweepDust` in the same file: [2](#0-1) [3](#0-2) 

Once `withdraw()` returns, there is no other entry point that lets the beneficiary retry: `RedeemEscrow`/`RefundEscrow` are one-shot dispatches from the source chain, and `onGetResponse` (timeout-refund path) is gated by `Filled()` — a subsequent GET-response refund attempt against the same commitment will read the request as already processed and revert, since `_filled[body.commitment]` is already set: [4](#0-3) 

This mirrors the seed report's core broken invariant exactly: state that represents "assets delivered" advances even though the ERC-20 transfer silently returned `false`, and there is no recovery path once that happens — the tokens remain custodied by the gateway contract but the internal accounting says they were already paid out.

By contrast, the mainline EVM `IntentGatewayV2`/`IntentsBase` path correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, which reverts on both call failure and a `false` return value: [5](#0-4) 

The Tron contract does not reuse this base and reimplements the raw, unchecked pattern instead.

### Impact Explanation
This is a direct loss/lock of bridged user funds without any privileged, malicious-peer, or front-running precondition: an unprivileged solver/user simply needs the order's input or output token to be a standard (non-malicious) ERC-20 that can legitimately return `false` on transfer failure (paused, blacklisted recipient, insufficient contract balance due to fee-on-transfer dust, etc.). When that happens during `RedeemEscrow`/`RefundEscrow` settlement, the beneficiary's escrowed tokens are permanently stuck in the `IntentGatewayV2` contract: `_orders[...]` accounting is decremented as if paid, `_filled[...]` marks the commitment as resolved, and no further withdrawal or refund call can be issued for that commitment. Funds are unretrievable — squarely within the bounty's "stealing or loss of funds" / "false state acceptance leading to fund loss" category.

### Likelihood Explanation
The trigger condition — a token whose `transfer` can return `false` instead of reverting — is common among production ERC-20s (this is explicitly a compliant, standard behavior per EIP-20, as cited in the seed report: BAT, cUSDC, EURS, ZRX, etc.). No attacker collusion, malicious relayer, or governance action is required; the vulnerable code path (`withdraw()`) executes automatically as part of normal cross-chain escrow settlement whenever a `RedeemEscrow`/`RefundEscrow` request is delivered. Any order using such a token as input/output on the Tron deployment reaches this code unconditionally.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern throughout `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`'s token loop, the fee-token payout, and `SweepDust` in `onAccept`) with OpenZeppelin's `SafeERC20.safeTransfer`, which both propagates call-level reverts and enforces that a non-reverting `false` return also reverts. Additionally, consider deferring `_filled[body.commitment] = beneficiary` and the `_orders[...] -= amount` decrement until after all transfers in the loop have succeeded, so a failure partway through the token list cannot leave the commitment marked as filled while some legs never paid out.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an order whose input/output token is an ERC-20 that returns `false` on a failed transfer instead of reverting (e.g. a token that pauses transfers to a specific address, or one whose balance is insufficient due to prior fee-on-transfer deduction leaving the gateway short of `amount`).
2. Have the source chain dispatch a `RedeemEscrow` (or `RefundEscrow`) request for a commitment whose escrowed token balance in the gateway is intentionally short by some `dust` amount (achievable via a fee-on-transfer token, or simply a token that returns `false` when `balanceOf(gateway) < amount`).
3. `onAccept` invokes `withdraw(body, ...)`. The `token.call(...)` succeeds (`success == true`) because the token contract returns `false` rather than reverting.
4. Observe: `TransferFailed()` is not raised, `_orders[body.commitment][token]` is decremented to zero, `_filled[body.commitment]` is set to the beneficiary, and no tokens were actually received by the beneficiary.
5. Any later call to redeem/refund the same commitment (via `RedeemEscrow`, `RefundEscrow`, or the GET-response timeout path) is rejected because `_filled[body.commitment]` is already non-zero / `Filled()` check trips — the tokens remain trapped in the gateway contract permanently.
