### Title
Future-dated oracle timestamp permanently poisons the per-feed monotonic staleness gate, freezing price resolution - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The market contract's oracle freshness check silently disables the staleness bound whenever the reported price timestamp is greater than the current block time, and permanently records that inflated value as the new floor for all future updates to the same feed. This mirrors the Optimism dispute-game bug: a value that must be monotonically increasing (there, the game UUID/root claim; here, the per-feed `last-update` timestamp) can be poisoned by an out-of-order/oversized value, after which the legitimate value can never be accepted again because it can no longer satisfy the monotonic ordering constraint.

### Finding Description
`oracle-timestamp-fresh` computes the staleness delta as follows: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

When the oracle-reported timestamp `ts` is greater than `stacks-block-time` (the current block's timestamp), `delta` is forced to `u0`, which trivially satisfies `<= delta max-staleness` no matter how far in the future `ts` actually is. This means the per-asset `max-staleness` bound configured in the asset registry [2](#0-1)  is not enforced at all for any timestamp ahead of the current block — there is no upper-bound check.

`price-resolve` then uses this gate to decide whether to accept the price and to advance the feed's monotonic floor: [3](#0-2) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((...)
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        ...)
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

Once a price update for a given `{type, ident}` feed is accepted with a timestamp that is (even slightly) ahead of the current block's `stacks-block-time`, the map `last-update` is set to that value. From then on, `oracle-timestamp-fresh` requires every subsequent price for that feed to satisfy `(>= ts prev)`, i.e. `ts >= last-update-time`. If the poisoned `last-update-time` sits materially ahead of subsequent legitimate, real-time publish timestamps, no correctly-timed price update can ever pass the monotonic check again — `price-resolve` (and therefore `price-multi-resolve`, which every market operation depends on for collateral/debt valuation and health checks) reverts with `ERR-ORACLE-INVARIANT` for that feed going forward. This is the same failure mode as the referenced report: a monotonic ordering requirement that, once advanced past the honest value, can never again admit the honest value, deadlocking the update path for that state.

The trigger does not require a compromised oracle network: `stacks-block-time` reflects the Stacks block's own timestamp, while Pyth/DIA publish timestamps track real-world (off-chain) clock progression, which can and normally does run ahead of block timestamps between blocks. Any relayed Pyth/DIA update whose `publish-time` happens to be ahead of the current block's timestamp — a routine occurrence, not an attack requiring bad oracle data — is treated by this code as automatically "fresh" and is written into the monotonic floor unconditionally.

### Impact Explanation
Once the per-feed `last-update` value is poisoned into the future, `price-resolve`/`price-multi-resolve` for the affected feed (and every asset built on it via `resolve-callcode`, e.g. `zSTX`, `zsBTC`, `zstSTX`, `zUSDC`, `zUSDH`, `zstSTXbtc` all derive from a base feed) reverts on every subsequent call. Since price resolution feeds directly into health checks, collateral valuation, borrowing, withdrawal, and liquidation logic in `v0-4-market.clar`, this blocks all operations that require pricing that asset — a temporary freezing of user funds (deposits/collateral become unusable for borrow/withdraw/liquidation) until the feed's real-world publish time eventually overtakes the poisoned floor (which could take an arbitrarily long time depending on how far ahead the poisoning timestamp was), or until a privileged reconfiguration occurs. This lands on the in-scope "temporary freezing of funds" impact category.

### Likelihood Explanation
Likelihood is elevated compared to the original Optimism report because no adversarial third party or capital lock-up is required — it can occur from ordinary clock/timestamp skew between the off-chain oracle publish cadence and Stacks block production, and is reachable by any account calling normal market functions that trigger `price-resolve`/`price-multi-resolve`. An attacker could also intentionally front-run the update path once they notice a relay's price timestamp is ahead of the current block, to lock out the feed on purpose.

### Recommendation
Add a genuine upper-bound (future-timestamp) check in `oracle-timestamp-fresh` instead of silently zeroing the delta when `ts > stacks-block-time` — reject timestamps that are unreasonably ahead of `stacks-block-time` (e.g., bound the positive skew the same way the negative skew is bounded by `max-staleness`), so the monotonic floor cannot be advanced by an out-of-range future value.

### Proof of Concept
1. A relayed Pyth/DIA price update for feed `{type, ident}` arrives with `publish-time = T_future`, where `T_future` is even one second greater than the current block's `stacks-block-time`.
2. `oracle-timestamp-fresh(T_future, prev, max-staleness)` computes `delta = 0` (because `T_future > stacks-block-time`), so the staleness check trivially passes regardless of `max-staleness`.
3. `price-resolve` accepts the price and executes `(map-set last-update key T_future)`.
4. All later legitimate updates for that feed carry real-time publish timestamps `ts_real < T_future` (since real-world clock has not yet caught up to the poisoned value, or simply because subsequent normal ticks are smaller than the anomalous spike).
5. `oracle-timestamp-fresh(ts_real, T_future, max-staleness)` now fails the `(>= ts prev)` check for every subsequent call, so `price-resolve`/`price-multi-resolve` reverts with `ERR-ORACLE-INVARIANT` for that asset until (if ever) a real-world timestamp exceeds `T_future`.
