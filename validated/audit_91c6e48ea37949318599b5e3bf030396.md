## Title
Malicious escrow input token permanently locks solver payout and legitimate escrowed assets - (evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
The `IntentGatewayV2` intent-settlement flow (`IntentsBase.sol`, `ExtrinsicIntents.sol`) escrows arbitrary user-supplied `TokenInfo[]` (`order.inputs`) on the source chain and releases them to a solver via `_withdraw()` once a `RedeemEscrow` message arrives from the destination chain. `_withdraw()` iterates over every escrowed token and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each one in a single all-or-nothing loop. Because an order creator fully controls the token addresses placed into `order.inputs`, a malicious order creator can include one attacker-controlled ERC20 whose `transfer` deterministically reverts. Once a solver has honestly delivered the real output assets on the destination chain and the `RedeemEscrow` settlement message arrives, `_withdraw()` reverts on the poisoned token — and since the ISMP host retries failed `onAccept` calls indefinitely with the exact same fixed input, the failure is not transient: it locks **every** escrowed token for that order (legitimate ones included), not just the malicious one, forever. This is a direct structural analog of the Putty `exercise()`/`withdraw()` honeypot-token bug: an attacker-controlled asset embedded in a settlement payload blocks release of the entire bundle, including the counterparty's rightful assets.

### Finding Description
`placeOrder` accepts arbitrary `TokenInfo[] inputs` from the order creator and escrows them under `_orders[commitment][token]` with no token allowlist. On a successful cross-chain fill, the destination gateway dispatches a `RedeemEscrow` message back to the source chain; `onAccept()` authenticates the message and calls `_withdraw()`: [1](#0-0) 

Every token in `body.tokens` is transferred in the same loop, with no per-token isolation, no try/catch, and no partial-success bookkeeping: [2](#0-1) 

The call chain is invoked from `onAccept`: [3](#0-2) 

which is itself dispatched by `EvmHost.dispatchIncoming`, which only offers *retry*, not isolation, on failure: [4](#0-3) 

Since the malicious token's revert condition is deterministic and attacker-controlled (e.g. `if (msg.sender == intentGateway) revert;`), retrying the exact same `onAccept` call forever cannot succeed — it is not a transient failure that self-heals, it is a permanent block. The same `_withdraw()` function is also the terminal step for `RefundEscrow` (cancellation) and for the storage-proof-verified `onGetResponse` cancel path, so the same poisoned-token trick blocks refunds too: [5](#0-4) 

The identical pattern exists in the Tron variant of the gateway: [6](#0-5) 

### Impact Explanation
A solver who honestly delivers real output assets to the beneficiary on the destination chain — an action that is itself irreversible once done — can be denied their earned escrowed-input compensation indefinitely if the order creator embedded one malicious token among otherwise legitimate `order.inputs`. Because the loop is all-or-nothing, this also permanently locks the *legitimate* escrowed tokens in the same order (they cannot be separated from the poisoned one), causing real fund loss/lock for the solver and freezing otherwise-good assets in the contract. This maps directly to the bounty's "stealing or loss of funds" / "logic attacks" impact classes: an unprivileged party (the order creator) fully controls a value that gates fund release for another unprivileged party (the solver), with no admin, relayer, or prover collusion required.

### Likelihood Explanation
Likelihood is high: placing an order with a malicious ERC20 in `inputs` requires no special privilege — any user can deploy a trivial reverting token and reference it in `placeOrder`. A solver evaluating an order sees only the token address and amount fields; nothing in the on-chain flow validates that `order.inputs` tokens are well-behaved, and the deterministic revert can be toggled by the attacker (e.g., only revert once they see the order is unprofitable to let stand, exactly as in the Putty writeup) to selectively grief solvers.

### Recommendation
Make `_withdraw()` resilient to individual token failures — e.g., wrap each transfer in a low-level call and skip/queue failed tokens for later claim/sweep rather than reverting the entire batch, or require solvers/relayers to pre-validate token behavior (e.g., a dry-run `transfer(0)` probe or an allowlist of vetted tokens) before escrow is accepted. At minimum, decouple `finalize` bookkeeping (marking the order filled, paying fees) from per-token transfer success so a single poisoned token cannot block release of the rest of the bundle or the order's finalization state.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer()` always reverts (or reverts conditionally based on `msg.sender`/timestamp/attacker-toggled flag).
2. Attacker calls `placeOrder()` with `order.inputs = [ {token: EvilToken, amount: X}, {token: USDC, amount: Y} ]`, escrowing both tokens under the order's commitment.
3. A solver observes the order, fills it honestly on the destination chain by delivering the requested `outputs` to the beneficiary, per `fillOrder()`.
4. The destination gateway dispatches `RedeemEscrow` back to the source chain; `onAccept()` calls `_withdraw()` at `IntentsBase.sol:390`.
5. The loop reaches `EvilToken.safeTransfer(solver, X)` and reverts. The entire `_withdraw()` call reverts, so the legitimate `USDC` amount `Y` is also not released to the solver.
6. `EvmHost.dispatchIncoming` catches the failure and deletes the receipt so the message "can be retried" — but resubmitting `onAccept` with the same fixed `WithdrawalRequest` hits the same deterministic revert every time. The solver's earned `USDC` payout, and the attacker's own escrowed `EvilToken`, remain locked in the gateway indefinitely, while the solver has already irreversibly delivered value on the destination chain.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        address destination = _bytesToAddress(request.to);

        }

            // so that it can be retried

            return;
