## Analysis

The core broken invariant in the external report is: **a scaling formula silently drops the "wrong-direction" decimal adjustment, producing a mismatched token amount between escrowed/burned input and minted/released output.** The exact analog exists in the `hyper-fungible-token` pallet's decimal-scaling helpers.

### The bug [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
	let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions use `u8::saturating_sub`, which clamps to `0` whenever `erc_decimals < local_decimals`. In that case the scaling exponent silently becomes `0` (i.e., `10^0 = 1`) instead of the correct **division** by `10^(local_decimals - erc_decimals)` (for `convert_to_erc20`) or correct **multiplication** (for `convert_to_balance`). This is functionally identical to the Halborn-flagged EntangleDex bug: a formula that assumes one decimal relationship and breaks silently — no revert, no bounds check — when the real relationship is inverted.

### Where it's exploitable

`send()` calls `convert_to_erc20(amount, erc_decimals, decimals)` where `decimals` is the local asset's precision (from `Assets::decimals` or `T::Decimals`) and `erc_decimals` is the destination chain's configured precision (`Precisions` storage, set by `register_token`/`update_token`): [2](#0-1) 

If a token is registered where the destination EVM contract's decimals are lower than the local asset's decimals (e.g. local pallet-assets token with 18 decimals bridging to a 6-decimal EVM representation — a completely ordinary, non-malicious configuration), the exponent computation becomes `erc_decimals.saturating_sub(decimals) = 0`, so `erc20_amount = amount` **unscaled**, instead of `amount / 10^12`. The dispatched cross-chain message carries an amount inflated by `10^(local_decimals - erc_decimals)` relative to what was actually escrowed/burned locally.

The counterpart `on_accept` path has the same flaw in the opposite direction via `convert_to_balance`, using the identical `erc_decimals.saturating_sub(decimals)` pattern: [3](#0-2) 

### Why existing tests miss it

Every existing test exercises only the "safe" direction (`erc_decimals=18 > local_decimals=10`), where `saturating_sub` behaves correctly: [4](#0-3) 

No test registers a token with `erc_decimals < local_decimals`, so the silent clamp-to-zero path is entirely unverified.

### Impact

An unprivileged user calling `send()` for a token registered with `erc_decimals < local_decimals` (a routine, admin-approved token configuration, not an attacker-controlled one) causes the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract to mint or release an amount inflated by `10^(local_decimals - erc_decimals)` relative to the amount actually escrowed or burned on the source chain — a direct false-amount fund creation across the bridge, matching the bounty's "unauthorized transaction... wrong beneficiary or amount" and "false proof/state acceptance" criteria (the destination trusts the message's `amount` field verbatim once source/module authentication passes).

### Title
Decimal-scaling exponent silently clamps to zero when destination decimals are lower than source decimals, causing wildly inflated cross-chain mint/release amounts — (`modules/pallets/hyper-fungible-token/src/impls.rs`)

### Recommendation
Replace the `saturating_sub` exponent computation with an explicit signed comparison that divides when `erc_decimals < local_decimals` and multiplies when `erc_decimals > local_decimals`, mirroring the correct bidirectional logic already used elsewhere in the codebase (e.g. `VWAPOracle._normalizeAmount`, `evm/src/utils/VWAPOracle.sol:240-248`, and the BandwidthManager's `PriceNotRepresentable` guard). Add test coverage for the `erc_decimals < local_decimals` configuration on both `send` and `on_accept`/`on_timeout` paths.
