### Title
Unchecked `payment_sat + needed_fee` overflow bypasses the `NotEnoughFunds` guard, producing a signed transaction paying more than its inputs - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` guards affordability with `if input_sat < (payment_sat + needed_fee)`, but the addition is performed on `u64` without an overflow check — the same bug class as the external report, where a product is bounds-checked against a wide type's max yet the resulting arithmetic can still wrap. If `payment_sat + needed_fee` exceeds `u64::MAX` it wraps to a small value, the guard passes, and a transaction is constructed and put through FROST signing whose outputs exceed its inputs.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `payment_sat` is an unchecked `sum::<u64>()` over caller-supplied payment amounts (each only required to be `>= DUST`), and `needed_fee = fee_per_vbyte * vbytes` is an unchecked `u64` multiplication [1](#0-0) [2](#0-1) . The solvency check then adds them in `u64` [3](#0-2) . In release builds this wraps: with `payment_sat = u64::MAX - 100` and `needed_fee = 1000`, the sum wraps to ~899, so `input_sat < wrapped` is false even though the payment vastly exceeds the inputs. The wrapped sum is then embedded in `tx_outs` as real `Amount::from_sat` output values [4](#0-3) , and the resulting `SignableTransaction` flows into `TransactionSignMachine::sign`, which has every threshold participant sign the per-input Taproot sighashes [5](#0-4) . Additionally, `fee()` computes `sum(inputs) - sum(outputs)` with plain subtraction, which panics on the underflow this bug makes reachable [6](#0-5) .

This mirrors the report exactly: the guard reasons about the wide-type bound (does the sum fit under `input_sat`) while the arithmetic itself is evaluated in the same wrapping width it was meant to police — analogous to checking `timeBucket <= type(uint256).max / timeCoefficient` and then truncating the product into `int256`.

### Impact Explanation
The check is the only thing standing between the payment list and a fully-signed transaction. Its bypass means the threshold signing machine emits valid BIP-340 signature shares/completed signatures for a transaction that consensus-invalidly pays out more than its inputs contain — the group signs a message the guard was designed to forbid. The transaction will be rejected by the network, so the practical impact is a wasted/mis-signed transaction and an availability loss for that batch (plus a reachable panic in `fee()`), rather than direct theft — hence Medium rather than High. Note that the change path already uses `checked_sub` [7](#0-6) , so this can't mint a change output; the flaw is confined to the solvency guard and the multiplications feeding it.

### Likelihood Explanation
Reachability requires caller-controlled `payments`/`fee_per_vbyte` values large enough to overflow `u64` — i.e., a payment amount near `u64::MAX` must reach `SignableTransaction::new` without an upstream balance check. Since all in-scope validation here is dust-only, any integrator or coordinator path that forwards user-requested withdrawal amounts without first bounding them against actual holdings exposes this. That upstream validation is out of scope to confirm, which caps confidence and severity.

### Recommendation
Use checked arithmetic for all value accounting in `SignableTransaction::new`: `let required = payment_sat.checked_add(needed_fee).ok_or(NotEnoughFunds{..})?`, `fee_per_vbyte.checked_mul(vbytes)`, and `checked_sum` for `input_sat`/`payment_sat`. Make `fee()` return via `checked_sub` as well.
