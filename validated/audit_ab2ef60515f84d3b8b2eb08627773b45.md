### Title
Fee-on-transfer ERC20 tokens break `BridgeTransferERC20.requestERC20Transfer` accounting, allowing reserve draining / stuck funds on the counterpart chain - (File: contracts/service_chain/bridge/BridgeTransferERC20.sol)

### Summary
`BridgeTransferERC20.requestERC20Transfer()` pulls `_value + _feeLimit` tokens via `safeTransferFrom` and then emits `RequestValueTransfer` with the caller-declared `_value` as the amount to be credited on the counterpart chain, without ever checking how many tokens the bridge contract actually received. For fee-on-transfer (deflationary) ERC20 tokens, the bridge's actual balance increase is less than the declared `_value`, but the full declared `_value` is what gets minted/unlocked to the recipient on the other chain via `handleERC20Transfer`. This is the same root-cause bug class as the reported `DonationVotingMerkleDistributionVaultStrategy::claim` issue: crediting a caller-supplied amount instead of the actually-received (balance-diff) amount.

### Finding Description
`requestERC20Transfer` is a public, unprivileged, user-reachable function: [1](#0-0) 

It performs:
```
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [2](#0-1) 

`_requestERC20Transfer` then emits `RequestValueTransfer` carrying the caller-supplied `_value` (not the actual balance delta), and, in mint-burn mode, burns `_value` tokens from the bridge's own balance: [3](#0-2) 

There is no `balanceOf(address(this))` before/after check anywhere in this flow — the contract simply trusts that `safeTransferFrom` moved exactly `_value + _feeLimit` tokens into the bridge. If `_tokenAddress` charges a transfer fee (deducts a percentage on each transfer), the bridge's real token balance increase is smaller than `_value + _feeLimit`, yet the emitted `_value` (the full, undiscounted amount) is what relayers/operators use to call `handleERC20Transfer` on the counterpart chain: [4](#0-3) 

On the destination side, `handleERC20Transfer` either mints `_value` new tokens (mint-burn mode) or `safeTransfer`s `_value` out of the bridge's locked reserve (lock-unlock mode) — both driven purely by the event's declared `_value`, with no cross-check against what was actually deposited on the source chain.

### Impact Explanation
- **Lock-and-unlock mode**: Each request under-collateralizes the bridge by the fee-on-transfer deduction, while the counterpart chain unlocks/releases the full declared `_value`. Repeated use drains the bridge's token reserve faster than it is topped up, so eventually honest users' legitimate `handleERC20Transfer` calls fail for lack of funds (denial of funds for later depositors/recipients), or an attacker can intentionally use such a token to accelerate reserve depletion, effectively extracting more value than they contributed.
- **Mint-and-burn mode**: `ERC20Burnable(_tokenAddress).burn(_value)` in `_requestERC20Transfer` attempts to burn the full declared `_value` from the bridge's balance, but the bridge only received a discounted amount; if the discount is large enough, the requisite burn amount may not even be available, causing reverts (denial of service) or, in cases of repeated smaller transfers preceding a burn, other latent accounting inconsistencies.
- Either way this is an unauthorized/incorrect value-movement bug rooted in trusting a caller-declared transfer amount instead of the actually-received balance delta — the same defect class validated in the external report, now reachable by any unprivileged user calling the public `requestERC20Transfer` function with a fee-on-transfer token registered on the bridge.

### Likelihood Explanation
Exploitability depends on an ERC20 token with transfer fees being registered on the bridge (`onlyRegisteredToken`). Bridge operators control token registration (`onlyOperators`/governance-like process elsewhere in the contract), so likelihood is contingent on such a token being allowed. However, unlike the audited Gitcoin contract, this bridge code offers no protective mechanism at all (no balance-before/after check, no fee-on-transfer rejection), so once such a token is registered, exploitation requires nothing more than a single ordinary transaction from any user — no special privilege is needed to trigger the mismatch.

### Recommendation
In `requestERC20Transfer`/`_requestERC20Transfer`, measure `IERC20(_tokenAddress).balanceOf(address(this))` before and after `safeTransferFrom`, and use the actual received delta (minus fee) as the value encoded in `RequestValueTransfer` and used for burning, rather than trusting the caller-supplied `_value`. Alternatively, explicitly disallow fee-on-transfer/deflationary tokens from being registered via `registerToken`/`onlyRegisteredToken`.

### Proof of Concept
1. Bridge operator registers a fee-on-transfer ERC20 token `T` (e.g., 2% fee on transfer) via the token registration path guarded by `onlyRegisteredToken`.
2. User calls `requestERC20Transfer(T, to, value=100, feeLimit=0, extraData)`.
3. `safeTransferFrom(msg.sender, address(this), 100)` executes, but due to the 2% fee, the bridge's actual balance only increases by 98 tokens.
4. `_requestERC20Transfer` emits `RequestValueTransfer(..., _value=100, ...)` — the full, undiscounted amount — see [5](#0-4) .
5. A relayer/operator on the counterpart chain calls `handleERC20Transfer(..., _value=100, ...)`, which either mints 100 new tokens to `to` (mint-burn mode) or transfers 100 tokens out of the bridge's reserve to `to` (lock-unlock mode) — see [6](#0-5) .
6. Repeating this process systematically over-credits the destination chain by 2% per transfer relative to what was actually deposited on the source chain, draining the bridge's reserve (lock-unlock mode) or creating a burn shortfall (mint-burn mode).

    function _requestERC20Transfer(
        address _tokenAddress,
        address _from,
        address _to,
        uint256 _value,
        uint256 _feeLimit,
        bytes memory _extraData
    )
        internal
        onlyRegisteredToken(_tokenAddress)
        onlyUnlockedToken(_tokenAddress)
    {
        require(isRunning, "stopped bridge");
        require(_value > 0, "zero ERC20 token amount");

        uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);

        if (modeMintBurn) {
            ERC20Burnable(_tokenAddress).burn(_value);
        }

        emit RequestValueTransfer(
            TokenType.ERC20,
            _from,
            _to,
            _tokenAddress,
            _value,
            requestNonce,
            fee,
            _extraData
        );
        requestNonce++;
    }
