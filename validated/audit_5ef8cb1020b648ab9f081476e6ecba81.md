### Title
Attacker inflates `getUserTier` via unrelated direct `mWomSV.lockFor` calls to extract disproportionate MGP reward in `ArbWomUp3.getRewardAmount`'s non-lock branch - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.getRewardAmount`'s `!_lock` branch computes `mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR`, where `getUserTier` reads `mWomSV.getUserTotalLocked(_account)` [3](#0-2) . Since `mWomSV.lockFor` is a public, unrestricted function [1](#0-0) , an attacker can lock a large amount of mWOM into mWomSV directly (unrelated to any actual WOM conversion through ArbWomUp3) to reach the top reward tier, then call `incentiveDeposit` with `_mode` 1 or 3 (the `!_lock` path) and a tiny `_amountToConvert`, collecting `topTierMultiplier * tinyAmount` MGP — disproportionate to the real economic activity performed in that call.

### Finding Description
`getRewardAmount`'s `!_lock` branch (`_mode` 1 or 3) has no bookkeeping to offset previously-rewarded tier gains: unlike the `_lock == true` branch which subtracts `calDoubledCounted(_account)` (computed from the same `mWomSV.getUserTotalLocked` value) to avoid double-rewarding a user's existing locked stack, the `!_lock` branch simply multiplies the *entire* `_amountToConvert` of the current call by whatever tier multiplier the user's `mWomSV` balance currently qualifies for [4](#0-3) . There is no `userWOMDeposited`/`claimedReward`-style tracking for this path (unlike the equivalent logic in `ArbWomUp.sol`/`ArbWomUp2.sol` which track cumulative deposits marginally via `userWOMDeposited` and `claimedReward`) [5](#0-4) .

Exploit flow:
1. Attacker acquires/holds mWOM tokens (obtainable permissionlessly via `mWOM.deposit`/`convert`, which mints mWOM 1:1 for WOM deposited) [6](#0-5) .
2. Attacker calls `mWomSV.lockFor(largeAmount, attacker)` directly — a completely public function with only `whenNotPaused nonReentrant` guards, callable by anyone for any beneficiary [1](#0-0) . This inflates `mWomSV.getUserTotalLocked(attacker)` and thus `ArbWomUp3.getUserTier(attacker)` to the top tier, entirely bypassing ArbWomUp3's `_deposit` mode-2 path.
3. Attacker calls `ArbWomUp3.incentiveDeposit(_amount = small, _convertRatio, false, _mode = 1)` (or `_mode = 3`). Inside, `getRewardAmount` hits the `!_lock` branch and returns `small * rewardMultiplier[topTier] / DENOMINATOR`, i.e., a reward computed at the top-tier rate applied to the entire (tiny) `_amount`, with zero deduction for the fact that the attacker's tier was built from unrelated mWomSV holdings [7](#0-6) .
4. Because there is no accounting to prevent re-earning the same tier-based multiplier repeatedly, the attacker can repeat step 3 many times with small `_amount`s, each time draining `rewardMultiplier[topTier] * _amount / DENOMINATOR` MGP from the contract's balance, bounded only by `mgpleft = IERC20(mgp).balanceOf(address(this))` [8](#0-7) .

Existing checks that fail to stop this: `whenNotPaused`/`nonReentrant` on `incentiveDeposit` do not prevent repeated legitimate calls; `calDoubledCounted` is only invoked in the `_lock == true` branch and does not apply to `_mode` 1/3 calls; `getUserTier` trusts `mWomSV.getUserTotalLocked` unconditionally with no requirement that the locked balance originated from this specific contract's conversion flow.

### Impact Explanation
This is a direct, repeatable drain of the ArbWomUp3 contract's MGP reward reserve (locked into vlMGP on the attacker's behalf via `vlMGP.lockFor`) [9](#0-8) , disproportionate to any genuine WOM-to-mWOM/mWomSV conversion activity. This matches the Immunefi impact class of "theft of unclaimed yield/reward funds" and can lead to depletion of the incentive pool intended for legitimate converters, and this is a violation of the Conservation invariant referenced in the question — reward extracted is not bounded by the actual `_amountToConvert` processed in the triggering transaction.

### Likelihood Explanation
The only precondition is holding/acquiring mWOM tokens (obtainable permissionlessly and cheaply via `mWOM.deposit`) and calling two unrestricted public functions (`mWomSV.lockFor` then `ArbWomUp3.incentiveDeposit`). No privileged role, oracle manipulation, or governance is required. The attack is fully repeatable while the contract holds MGP balance, and the capital used to reach the top tier is not consumed (it remains locked in mWomSV, recoverable later after the cooldown period via `startUnlock`/`unlock`), making this a low-cost, highly repeatable exploit for any unprivileged EOA.

### Recommendation
For the `!_lock` branch of `getRewardAmount`, do not apply the full-amount multiplier based on a snapshot of unrelated `mWomSV` balance. Instead, track marginal WOM actually converted per user through ArbWomUp3 (as done in `ArbWomUp`/`ArbWomUp2` via `userWOMDeposited`/`claimedReward`), and compute rewards incrementally against tier boundaries crossed by the user's *ArbWomUp3-tracked* cumulative conversions, not an externally-manipulable `mWomSV` balance. Alternatively, restrict `mWomSV.lockFor`'s `_for` parameter usage or require that tier-qualifying balances originate only from deposits routed through ArbWomUp3's own accounting.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `MasterMagpie`, `mWOM`, `vlMGP`, `ArbWomUp3`, and wire them per production config; set `rewardTier`/`rewardMultiplier` with a large gap between tier 0 and top tier (e.g., tier 0 multiplier = 100 (1%), top tier multiplier = 10000 (100%)); fund `ArbWomUp3` with MGP.
2. As attacker EOA, acquire mWOM via `mWOM.deposit(largeWomAmount)` (or however mWOM is obtained), then call `mWomSV.lockFor(largeMWomAmount, attacker)` directly (not via ArbWomUp3) to push `mWomSV.getUserTotalLocked(attacker)` above the top tier threshold.
3. Assert `ArbWomUp3.getUserTier(attacker) == topTierIndex`.
4. Call `ArbWomUp3.incentiveDeposit(smallAmount, _convertRatio, false, 1)` and record MGP reward locked into vlMGP for attacker.
5. Assert `reward == smallAmount * rewardMultiplier[topTierIndex] / DENOMINATOR`, and assert this exceeds `smallAmount * rewardMultiplier[0] / DENOMINATOR` (the reward an honest first-time converter with no external tier manipulation would receive) — demonstrating reward is bounded by an unrelated, externally-manipulable balance rather than by `smallAmount`'s genuine conversion history.
6. Repeat step 4 multiple times with fresh small amounts and assert cumulative MGP extracted grows unbounded (limited only by contract MGP balance), confirming no per-account deduction/tracking exists for this path.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
