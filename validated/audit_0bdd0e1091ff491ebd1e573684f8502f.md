## Title
Delayed-field identifier mapping is determined by struct name only, not by module address - (File: `third_party/move/move-vm/runtime/src/storage/ty_layout_converter.rs`)

### Summary
`LayoutConverter::get_delayed_field_kind_if_delayed_field_optimization_enabled` classifies a struct as a delayed field (aggregator/snapshot/derived-string) purely based on the textual module name and struct name, without verifying that the struct's module is actually published at the reserved framework address (`0x1`).

### Finding Description
When delayed-field optimization is enabled, the layout converter resolves the kind of a struct via: [1](#0-0) 

`self.get_struct_name(idx)` resolves an `Arc<StructIdentifier>` from the `StructNameIndex`, and `struct_name.module()` / `struct_name.name()` are passed to `IdentifierMappingKind::from_ident`. Only the identifier strings (module name, struct name) are consulted here — the `AccountAddress` component of the struct's owning `ModuleId` is never checked in this call. Since Move allows any address to publish a module using any (unreserved) name — including a module literally named `aggregator_v2` containing a struct `Aggregator` — an unprivileged package publisher can create a struct whose `(module_name, struct_name)` textually collides with the markers recognized by `IdentifierMappingKind::from_ident`, even though it lives at a different, attacker-controlled address than the genuine `0x1::aggregator_v2::Aggregator` type.

This is consistent with how the resulting kind is later consumed for value conversion, e.g. `TryFromMoveValue for DelayedFieldValue`, which matches purely on `(IdentifierMappingKind, MoveTypeLayout)` pairs without any address check: [2](#0-1) 

If the attacker-owned struct's field layout is compatible with the expected shape (e.g. a lone `u64`/`u128` field), the layout construction pass would mark `contains_delayed_fields = true` for it, causing the same identifier-mapping/materialization machinery used for genuine aggregators (in the block-executor's value-exchange logic) to treat ordinary user data as a delayed-field payload.

### Impact Explanation
Resources of the attacker's colliding struct type would be routed through the delayed-field native substitution/materialization path instead of plain BCS (de)serialization. This could cause:
- Incorrect classification of ordinary resource data as delayed-field content, feeding attacker-controlled raw integers into the delayed-field versioned-value table as if they were legitimate aggregator/snapshot values.
- Divergence between the layout used for gas charging/storage representation and what the type actually is, since delayed fields receive specialized handling throughout the execution/storage pipeline (e.g. `aptos-move/block-executor/src/view.rs`, `aptos-move/block-executor/src/value_exchange.rs`).
- Potential confusion or invariant violations in code that assumes "delayed field kind ⇒ struct is `0x1`'s aggregator/snapshot type," since that assumption is not actually enforced at the classification site.

I was not able to fully trace, within the available tool budget, every downstream consumer to confirm whether some other layer (e.g. native function registration gating, or a stricter check elsewhere in the block-executor) fully neutralizes this at runtime before any observable effect occurs. The code shown at the cited call site itself performs no address check, which is the concrete defect being reported.

### Likelihood Explanation
Any unprivileged account can publish a module with an arbitrary name (subject to normal identifier rules) and define a struct with a chosen field layout, so triggering the name collision requires no special privilege — only publishing a module at the attacker's own address with the colliding module/struct names and a compatible field layout (single `u64`/`u128`, or matching the derived-string struct layout).

### Recommendation
`IdentifierMappingKind::from_ident`/`get_delayed_field_kind_if_delayed_field_optimization_enabled` should additionally verify that the module's address equals the genuine framework address (`0x1`, or whatever the canonical aggregator/snapshot module address is) before returning a non-`None` kind, so name-only collisions from unprivileged addresses cannot be classified as delayed fields.

### Proof of Concept
1. Publish an unprivileged module at address `0xCAFE` named `aggregator_v2` containing `struct Aggregator has store, drop { value: u64 }` (or matching whatever shape is required by `is_derived_string_struct_layout`/the U64/U128 match arms).
2. Store a resource containing this struct and enable delayed-field optimization.
3. Call `LayoutConverter::type_to_type_layout_with_delayed_fields` (or the annotated variant) on this type and observe that `get_delayed_field_kind_if_delayed_field_optimization_enabled` returns `Some(IdentifierMappingKind::Aggregator)` for the attacker's struct, i.e. `contains_delayed_fields == true`, despite the module being owned by `0xCAFE`, not `0x1`.
4. Assert the correct behavior instead: the returned kind should be `None` unless `struct_name`'s owning module address equals the canonical framework address.

    fn get_delayed_field_kind_if_delayed_field_optimization_enabled(
        &self,
        idx: &StructNameIndex,
    ) -> PartialVMResult<Option<IdentifierMappingKind>> {
        if !self.vm_config().delayed_field_optimization_enabled {
            return Ok(None);
        }
        let struct_name = self.get_struct_name(idx)?;
        Ok(IdentifierMappingKind::from_ident(
            struct_name.module(),
            struct_name.name(),
        ))
    }
