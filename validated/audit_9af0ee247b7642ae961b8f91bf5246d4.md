### Title
ERC721 bridge mint path uses `_mint()` instead of `_safeMint()`, allowing bridged NFTs to be minted to non-ERC721-aware recipients and permanently lost - (File: contracts/service_chain/bridge/BridgeTransferERC721.sol)

### Summary
The service-chain ERC721 bridge's mint-and-burn mode mints bridged NFTs on the destination chain via `ERC721MetadataMintable.mintWithTokenURI()`, which internally calls the unsafe `ERC721._mint()` rather than `_safeMint()`. Because the destination `_to` address is fully attacker/user-controlled from the public `requestERC721Transfer()` entrypoint on the source chain, a bridge user can specify a `_to` address that is a contract incapable of handling ERC721 tokens, causing the minted NFT to become permanently stuck/unrecoverable on the destination chain.

### Finding Description
`requestERC721Transfer()` is a `public` function callable by any unprivileged transaction sender, and it forwards an arbitrary `_to` address chosen by the caller to the destination chain: [1](#0-0) 

On the destination chain, bridge operators relay the request via `handleERC721Transfer()`. When `modeMintBurn` is enabled, the contract mints the NFT to `_to` using `ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI)`: [2](#0-1) 

`mintWithTokenURI()` itself calls the internal `_mint()`: [3](#0-2) 

And the base `ERC721._mint()` implementation performs no receiver-capability check — it does not invoke `onERC721Received` or otherwise verify the recipient can handle ERC721 tokens, unlike `_safeMint()`/`safeTransferFrom()` which do call `_checkOnERC721Received`: [4](#0-3) [5](#0-4) 

Because the entire code path from the unprivileged `requestERC721Transfer()` call to the eventual `_mint()` on the destination chain is reachable purely by a standard bridge user request (the `_to` value flows unmodified through `RequestValueTransferEncoded` and `handleERC721Transfer`), any bridge user can trigger a mint to a contract address that does not implement `onERC721Received`, or is otherwise incapable of transferring/using ERC721 tokens.

### Impact Explanation
If `_to` is a smart-contract address that cannot handle ERC721 tokens (no ERC721 transfer/approval logic, or it reverts on unexpected token receipt), the bridged NFT is minted directly into that contract with no safety check. The token becomes irrecoverably locked at that address — there is no recovery path once minted (unlike a `safeTransferFrom` which would revert atomically, allowing the request to fail safely). This results in permanent, unrecoverable loss of the NFT value for the destination-chain state, which is a concrete asset-loss impact consistent with a Medium-severity finding.

### Likelihood Explanation
Likelihood is moderate to high: `requestERC721Transfer()` is a fully public function with no access control on the `_to` parameter, so any user (or a mistaken/careless caller) transferring an NFT cross-chain can supply an incompatible contract address, either by accident or via a crafted contract intended to look benign. Because the bridge processes handle-side minting automatically once operators vote through the transfer, there's no independent recipient-capability check to prevent this outcome.

### Recommendation
Replace `_mint()` with `_safeMint()` (or equivalently call `_checkOnERC721Received` before finalizing the mint) in the ERC721 mint path used by the bridge, specifically in `ERC721MetadataMintable.mintWithTokenURI()` (and `ERC721Mintable.mint()`), so that `handleERC721Transfer()` in `BridgeTransferERC721.sol` reverts safely instead of permanently locking the token when `_to` cannot handle ERC721 tokens.

### Proof of Concept
1. Deploy/attach an ERC721 token via the bridge in mint-and-burn mode (`modeMintBurn = true`) with `ServiceChainNFT`/`ERC721MetadataMintable` as underlying token contract.
2. As any unprivileged user, call `requestERC721Transfer(tokenAddress, to, tokenId, extraData)` on the source-chain bridge where `to` is set to a contract address that has no `onERC721Received` handling and no way to move ERC721 tokens out (e.g., a minimal contract with no ERC721 logic at all). [6](#0-5) 
3. Bridge operators call `handleERC721Transfer()` on the destination chain, which invokes `mintWithTokenURI(to, tokenId, tokenURI)` → `_mint(to, tokenId)`. [2](#0-1) 
4. The mint succeeds unconditionally (no receiver check), and the NFT is now owned by the contract address `to` with no built-in mechanism to move it out, permanently losing the asset.

    /**
     * @dev Internal function to mint a new token.
     * Reverts if the given token ID already exists.
     * @param to The address that will own the minted token
     * @param tokenId uint256 ID of the token to be minted
     */
    function _mint(address to, uint256 tokenId) internal {
        require(to != address(0), "ERC721: mint to the zero address");
        require(!_exists(tokenId), "ERC721: token already minted");

        _tokenOwner[tokenId] = to;
        _ownedTokensCount[to].increment();

        emit Transfer(address(0), to, tokenId);
    }
