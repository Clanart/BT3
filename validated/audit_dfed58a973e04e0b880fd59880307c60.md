### Title
JSON parser skips duplicate-key/oneof "already seen" enforcement for `null` values, allowing an ambiguous duplicate/oneof-conflicting field to be silently accepted - ([File: src/google/protobuf/json/internal/parser.cc])

### Summary
The C++ ProtoJSON parser (`google::protobuf::json::JsonStringToMessage`, implemented in `ParseField()`) validates duplicate JSON keys and oneof-exclusivity using a "seen" bookkeeping check (`Traits::RecordAsSeen`), but this check is skipped whenever the *first* occurrence of a field/oneof-member's value is JSON `null`. This produces exactly the same class of flaw as the reported ModSecurity issue: a normalization/short-circuit step (treating `null` as a no-op) happens *before* the security-relevant structural check (uniqueness/oneof-exclusivity enforcement) that is otherwise applied uniformly to every other value type — so the same ambiguous input is accepted here but would be rejected by the spec-conformant path, or by any other consumer of the same message that assumes duplicate/oneof-conflict rejection as an invariant.

### Finding Description
`ParseField()` in `src/google/protobuf/json/internal/parser.cc` processes each JSON member as follows: [1](#0-0) 

1. If the upcoming value is JSON `null` and the field is not `google.protobuf.Value`/`NullValue`, the code eagerly `return`s/no-ops the field **before** calling `Traits::RecordAsSeen`.
2. Only for non-null values does the code call `Traits::RecordAsSeen(*field, msg)`, which returns `SeenState::kOneofAlreadySeen` / `kFieldAlreadySeen` and is the sole gate that rejects duplicate keys or conflicting oneof members: [2](#0-1) 

The code itself documents this as a known spec-deviation, referencing an internal bug (b/519557203): [3](#0-2) 

This is the direct analog of the ModSecurity flaw: ModSecurity's URL decoder ran *before* the path/query split, so the WAF's security decision (built on the undecoded/whichever-order view) diverged from the backend's actual interpretation of the same bytes. Here, the JSON parser's "null short-circuits without touching seen-state" step runs *before* the duplicate-key/oneof-exclusivity check, so the parser's acceptance decision for a payload with a `null` first-occurrence diverges from what the same parser (and the documented spec) would do for a non-null first-occurrence, and from what any other JSON consumer assuming strict oneof/duplicate-key enforcement would do.

### Impact Explanation
An attacker who controls a bounded ProtoJSON payload passed to the public `JsonStringToMessage` parsing API can construct a message where a oneof (or any field) has two entries — the first `null`, the second a real value — and have it accepted, even though the wire/JSON spec and the parser's own (non-null) code path would reject it as "already been set...as part of a oneof" (note: the oneof check at line 1261 is unconditional, not gated on `allow_legacy_nonconformant_behavior`). This is a parsing-invariant break rather than memory corruption: applications or intermediary validators that rely on ProtoJSON's duplicate/oneof-uniqueness rejection as a security boundary (e.g., to guarantee a field was set exactly once, or to reject ambiguous/duplicate-key payloads as a defense against JSON key-confusion between two different consumers of the same bytes) can be bypassed by simply null-guarding the first occurrence. This is a logic/consistency vulnerability, not RCE; severity is bounded by how much downstream logic depends on this invariant.

### Likelihood Explanation
High reachability: any caller of the standard C++ ProtoJSON parsing entry point on attacker-controlled JSON hits this code path with no special configuration required (the `null`-skip is unconditional; only the *non-null* duplicate-key legacy toggle is configurable). Constructing the trigger requires only ordinary JSON with a `null` value for one member of a oneof (or a repeated/duplicate key) followed by a real value for a conflicting key — no privileged access, malicious schema, or memory corruption needed.

### Recommendation
Move the `Traits::RecordAsSeen(*field, msg)` call (and its `kOneofAlreadySeen`/`kFieldAlreadySeen` enforcement) ahead of the `null`-short-circuit branch so that "seen" bookkeeping and oneof-exclusivity/duplicate-key rejection are applied uniformly regardless of whether the value is `null`, matching the behavior for non-null values and closing the gap tracked as b/519557203.

### Proof of Concept
Given a proto3 message:
```proto
message M {
  oneof o {
    int32 a = 1;
    int32 b = 2;
  }
}
```
Parsing the following JSON via `google::protobuf::json::JsonStringToMessage`:
```json
{ "a": null, "b": 5 }
```
is accepted and yields `b = 5` set, because the `null` value for `a` bypasses `RecordAsSeen`, so no oneof-conflict is ever recorded before `b` is processed.

Contrast with:
```json
{ "a": 0, "b": 5 }
```
which is rejected with `"'b' has already been set (either directly or as part of a oneof)"` because both `a` and `b` pass through `RecordAsSeen` (line 1256) and the unconditional `kOneofAlreadySeen` check (line 1261) fires.   // Any `null` values eagerly no-op, except for exactly the special cases of
  // google.protobuf.Value message and google.protobuf.NullValue enum.
  // Note that spec behavior is that we should do duplicate key checking in the
  // case of a null value, but this implementation currently does not
  // (b/519557203).
  if (lex.Peek(JsonLexer::kNull)) {
    MessageType type = ClassifyMessage(Traits::FieldTypeName(*field));
    if (type != MessageType::kValue && type != MessageType::kNull) {
      return lex.Expect("null");
    }
  }

  SeenState seen = Traits::RecordAsSeen(*field, msg);

  // Legacy nonconformant behavior only enforces duplicate key checking for
  // fields within the same oneof, otherwise enforce duplicate keys for all
  // fields.
  if (seen == SeenState::kOneofAlreadySeen ||
      (seen == SeenState::kFieldAlreadySeen &&
       !lex.options().allow_legacy_nonconformant_behavior)) {
    return lex.Invalid(absl::StrFormat(
        "'%s' has already been set (either directly or as part of a oneof)",
        name));
  }
