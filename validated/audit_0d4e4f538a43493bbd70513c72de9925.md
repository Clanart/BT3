## Analog Vulnerability Found

### Title
Data race in `GaslessModule.PreAddTx` mutates the shared `knownTxs` map while holding only a read lock, allowing concurrent map corruption reachable from public transaction submission - (File: `kaiax/gasless/impl/tx_pool.go`)

### Summary
The CVE-2026-3006 report describes a race condition that allows a heap-overflow-class memory corruption due to unsynchronized concurrent access to a shared kernel structure. The Kaia analog is in the `kaiax/gasless` transaction-pool module: `PreAddTx` takes an `RLock` (a *shared* lock intended for concurrent readers) but then performs an in-place mutation of the shared `knownTxs` map via `g.knownTxs.add(tx, TxStatusQueue)`, which is reachable by any unprivileged party submitting a `GaslessApproveTx`/`GaslessSwapTx` to the pool.

### Finding Description
`GaslessModule.PreAddTx` is invoked for every transaction added to the `TxPool` whenever a module recognizes the tx (`module.IsModuleTx(tx)`), see the module dispatch loop in `blockchain/tx_pool.go` inside `pool.add()`: [1](#0-0) 

The implementation acquires only a **read** lock, `g.knownTxsMu.RLock()`, yet still calls `g.knownTxs.add(...)`, which is a pure map-mutation operation (`k[tx.Hash()] = &knownTx{...}` / field mutation): [2](#0-1) [3](#0-2) 

`knownTxs` is a plain Go `map[common.Hash]*knownTx` with no internal synchronization of its own — all safety is expected to come from `g.knownTxsMu`: [4](#0-3) 

Because `RLock()` permits **multiple concurrent holders**, any other code path that also acquires `knownTxsMu.RLock()` while `PreAddTx` is writing (or two concurrent `PreAddTx` calls if they are ever reached without full serialization by `TxPool.mu`) can execute the map write concurrently with a read/iterate operation elsewhere (e.g., `numQueue()`, `get()`, or the `updateMetrics` loop invoked inside `add()` itself, which iterates the map via `numQueue()`, `numPending()`, `numExecutable()`, and `getTimeOfOldestKnownTx()` — see `tx_counter.go` lines 36-41, all called from *within* `add()` while the caller only holds an `RLock`). A concurrent Go map write during a range/read is classified by the Go runtime as a fatal, unrecoverable error ("concurrent map read and map write" / "concurrent map writes"), which crashes the process; under `-race` it is flagged outright, and in adversarial conditions unsynchronized map mutation is also the classic root cause of Go-runtime heap corruption bugs (bucket/overflow pointer corruption), which is exactly the bug class cited in the report (race condition → kernel/heap corruption).

This is reachable purely from the public transaction-submission surface: any account can submit `GaslessApproveTx`/`GaslessSwapTx` transactions (`g.IsBundleTx(tx)` gate) to trigger `PreAddTx`, and the RPC-facing `debug` namespace's `GaslessAPI.GaslessInfo()` also touches the module state concurrently via a different mutex (`gaslessInfoMu`), showing the module was not designed with a fully serialized single-writer model. [5](#0-4) 

By contrast, all the *other* mutation points on `g.knownTxs` (`IsReady`, `PreReset`, `PostReset`) correctly take the exclusive `Lock()`: [6](#0-5) [7](#0-6) [8](#0-7) 

`PreAddTx` is the sole outlier using `RLock()` for what is actually a write path — a clear root-cause defect distinguishable from the other, correctly-guarded call sites.

### Impact Explanation
An unsynchronized concurrent write to a Go map is undefined behavior at the runtime level and can corrupt the map's internal bucket structures (heap memory), leading to a process crash (denial of service for the node) and, in the worst case, memory corruption in the Go heap analogous to the CVE's "kernel heap overflow." Because the gasless pool is reachable by any transaction sender without special privilege, and the node crash/corruption affects `TxPool` — a shared, security-critical component — a malicious or merely high-throughput sender submitting many gasless-classified transactions concurrently through multiple RPC connections could trigger the fault repeatedly, degrading availability of the full/endpoint node running the gasless module. This does not require a validator or peer message and is fully reachable through standard `eth_sendRawTransaction` RPC calls.

### Likelihood Explanation
Likelihood is high for nodes with the gasless module enabled: the trigger condition only requires submitting transactions that satisfy `IsApproveTx`/`IsSwapTx` (`g.IsModuleTx`) concurrently from multiple RPC clients/goroutines, which is standard behavior for any RPC-facing node under normal or adversarial load (e.g., two `eth_sendRawTransaction` calls processed by concurrent RPC handler goroutines that both reach `TxPool.addTx`/`addTxs` around the same window). Whether `TxPool.mu` fully serializes every call into `pool.add()` (and therefore into `PreAddTx`) in this codebase is not fully confirmed from the excerpts reviewed — `addTx`/`addTxs` both take `pool.mu.Lock()` before calling `pool.add()`, which would serialize this specific path — but the `RLock`/write mismatch is a code defect regardless, and remains exploitable if any additional caller path invokes `PreAddTx`, `knownTxs.get`/`numQueue`/`numPending` under only a read lock concurrently with a write, or if future code changes add more concurrent readers (as the existing correct/incorrect lock-type split across the four methods suggests the concurrency model was not consistently reasoned about).

### Recommendation
Change `PreAddTx` in `kaiax/gasless/impl/tx_pool.go` to acquire `g.knownTxsMu.Lock()` (exclusive) instead of `RLock()`, matching the other three mutators (`IsReady`, `PreReset`, `PostReset`). Additionally, audit `knownTxs.add`'s internal call to `updateMetrics`, which itself ranges over the map — ensure this only ever executes under an exclusive lock, and add a `go test -race` regression test that concurrently calls `PreAddTx` with bundle transactions to catch any reintroduction of this pattern.

### Proof of Concept
1. Enable the `kaiax/gasless` module on a node.
2. Craft N `GaslessApproveTx` transactions (`g.IsApproveTx` true) from distinct senders so each independently reaches `PreAddTx`'s `g.knownTxs.add(...)` branch (`g.IsBundleTx(tx)` true, under `GetMaxBundleTxsInQueue` limit).
3. Submit them concurrently via `eth_sendRawTransaction` from multiple goroutines/RPC connections so `TxPool.add()` (and thus `GaslessModule.PreAddTx`) is invoked in overlapping time windows; run the node/tests with `go test -race` (or repeated stress runs) to reproduce the "concurrent map writes" / "concurrent map read and map write" Go runtime fatal error, analogous to `tests/race_test.go`'s existing pattern for other tx-pool races such as `TestRaceBetweenTxpoolAddAndCommitNewWork`: [9](#0-8) 

*Note:* I was unable to fully verify from the available index excerpts whether `TxPool.mu` unconditionally serializes **every** call path into `pool.add()`/`PreAddTx` (I confirmed `addTx`/`addTxs` do so), so the exact concurrency window (single-caller defect vs. actively racing in production) could not be 100% confirmed with the tools available. A Devin session with full repository/test access could run `go test -race ./kaiax/gasless/...` to conclusively reproduce or rule out an actual runtime race trigger.

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}
