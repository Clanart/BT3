## Title
Silent, unconfirmed rewrite of the `origin` remote URL from GitHub API data — single-step trust transfer with no user confirmation - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The reported issue is a generic "single-step transfer of a trust-critical value" bug class: a security-sensitive pointer (ownership/role, or here — the git remote URL that determines where a repository's data flows) is changed in one unconfirmed step instead of requiring an explicit, user-verified action. GitHub Desktop has a direct analog: `updateRemoteUrl()` silently executes `git remote set-url` on the `origin` remote whenever it observes that the GitHub API's `clone_url` for the matched repository differs from what's configured locally, with no dialog, confirmation, or "are you sure" step — unlike the equivalent manual flow in Repository Settings, which is an explicit, user-initiated action.

### Finding Description
`updateRemoteUrl()` compares the locally configured `origin` remote against the `clone_url` returned by the GitHub API for the same owner/name and, if the protocol matches and the previously cached `GitHubRepository.cloneURL` still matches the current remote, it calls `gitStore.setRemoteURL()` unconditionally and without any user interaction: [1](#0-0) 

This function is invoked automatically during routine, non-interactive repository refresh: [2](#0-1) 

`gitStore.setRemoteURL()` calls straight into `git remote set-url` with no gate: [3](#0-2) [4](#0-3) 

By contrast, the same value can be changed by the user through the Repository Settings UI, which is an explicit, one-at-a-time user action requiring the user to type a new URL and click Save: [5](#0-4) [6](#0-5) 

The broken invariant: the origin remote — the value that determines what content the user's future `git push`/`git fetch`/`git pull` operations exchange, and what host the credential helper hands the user's token to — is a "role/destination" value exactly analogous to the ownership/role fields in the report. It is changed automatically based on data returned by an external, only loosely-verified source (the GitHub API response for the matched `owner/name`), in a single unconfirmed step, with the only guard being a same-protocol / previously-matched-URL heuristic in `urlMatchesRemote()` — not a user confirmation: [7](#0-6) 

If the repository the user has cloned changes its `clone_url` on the GitHub side (e.g., a rename/transfer performed by a compromised or malicious account holder, or a malicious/compromised GitHub Enterprise Server the user is authenticated against returning a crafted `clone_url` for the endpoint), Desktop will re-point the user's local `origin` remote to that new destination the next time it performs a background refresh — with zero user awareness, let alone a two-step confirm.

### Impact Explanation
Once `origin` is silently repointed, every subsequent `git push` sends the user's work (and, over HTTPS, their credentials via the trampoline credential helper) to the new destination, and every `git fetch`/`pull` retrieves history from a destination the user never approved. This can result in credential exposure to an unintended host and can cause the user's future commits to be silently redirected away from the repository they believe they're working with — corrupting what the user thinks they are pushing to/pulling from, one of the explicitly valid impact categories.

### Likelihood Explanation
Low/Medium: it requires the attacker to control the `clone_url` reported by the GitHub API for a repository the victim has already cloned (e.g., via account/repo compromise, a rename-and-reclaim of the old owner/name, or a malicious/compromised Enterprise Server endpoint), and it only fires while the previous cached `cloneURL` still matches the existing remote (`remoteUrlUnchanged`) and the protocol is unchanged. This mirrors the report's own likelihood framing: the trigger condition is narrow but the resulting single-step, no-confirmation transfer is what turns a plausible external event into unrecoverable, silent state change.

### Recommendation
Apply the same "two-step" principle the report recommends for ownership transfers: instead of calling `gitStore.setRemoteURL()` automatically inside `updateRemoteUrl()`, surface a confirmation prompt/banner to the user showing the old and new URLs and require an explicit accept before rewriting `origin`, mirroring how manual edits already work in Repository Settings. At minimum, log/notify and require opt-in before mutating a value that affects push/fetch destinations and credential routing.

### Proof of Concept
1. Victim clones `https://github.com/acme/widgets` in Desktop; Desktop stores `GitHubRepository.cloneURL = https://github.com/acme/widgets`.
2. The `acme` account (compromised, or renamed/reclaimed) causes `GET /repos/acme/widgets` to return a different `clone_url` (e.g., pointing to `attacker/widgets-fork`) while keeping the same owner/name path Desktop uses for lookup.
3. On the next periodic `repositoryWithRefreshedGitHubRepository` refresh cycle (`app/src/lib/stores/app-store.ts:4874-4907`), `updateRemoteUrl()` sees `protocolsMatch && remoteUrlUnchanged && !urlsMatch` and calls `gitStore.setRemoteURL('origin', attackerUrl)` with no prompt (`app/src/lib/stores/updates/update-remote-url.ts:42-44`).
4. The victim's next `git push`/`git fetch` silently targets the attacker-controlled remote.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
