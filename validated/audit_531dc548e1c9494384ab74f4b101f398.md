## Title
Stale diff/line-selection is silently reapplied at commit time without content revalidation, allowing corrupted commits/discards - (File: `app/src/lib/git/apply.ts`)

## Summary
The Tigris `_checkDelay()` bug is fundamentally a **TOCTOU/consistency break**: a value validated at one point in time (a price) is paired with a different value that was also "valid" at commit time, and nothing checks that the two are mutually consistent before the state-changing action executes. The GitHub Desktop analog is in the partial-commit ("stage selected lines") pipeline: the user's line selection is captured against one diff snapshot, but the code that actually builds the git patch re-fetches a brand-new diff at execution time and blindly reapplies the old line-index selection to it, with no check that the two diffs are the same content.

## Finding Description
When a user partially selects lines in the Changes view, the UI stores a `DiffSelection` (a set of line **indices**, not content hashes) alongside the `WorkingDirectoryFileChange` [1](#0-0) . When the user commits, `createCommit` calls `stageFiles`, which for any partially-selected file calls `applyPatchToIndex` [2](#0-1) [3](#0-2) .

`applyPatchToIndex` does **not** use the diff object the user actually reviewed. Instead it calls `getWorkingDirectoryDiff` again, fresh, right before building the patch: [4](#0-3) 

The freshly-fetched diff is then fed into `formatPatch`, which walks the new diff's hunks and decides what to keep purely by `file.selection.isSelected(absoluteIndex)` — i.e., by line index from the *old* diff: [5](#0-4) 

There is no check anywhere in this path that the newly fetched diff's hunks/line count/content match what the user actually selected against. The renderer does have a partial mitigation, but it only prunes indices from a *newly displayed* diff so the UI doesn't show a stale selection — it does not run again right before the commit, and does not stop `applyPatchToIndex` from independently re-fetching yet another diff at commit time: [6](#0-5) 

The same unguarded re-fetch-and-reapply-by-index pattern exists for the destructive "Discard changes" flow: `discardChangesFromSelection` takes a `diff` parameter and blindly formats/applies a patch from it with no requirement that it is the current on-disk diff [7](#0-6) .

**Corrupted value:** the mapping between "line index N in the diff the user saw and clicked to select" and "line index N in the diff actually used to build the git patch." Nothing enforces these are the same diff.

**Why existing guards don't stop this:** `updateChangesWorkingDirectoryDiff` only reconciles selectable line sets when the UI happens to reload the diff for display purposes; it never re-runs synchronously immediately before `createCommit`/`stageFiles` executes, and `applyPatchToIndex` itself performs its own independent, unguarded `getWorkingDirectoryDiff` call with no cross-check against the diff the selection was made from.

## Impact Explanation
If the tracked file's on-disk content changes between the moment the user reviews/selects lines in the Changes view and the moment they click Commit (e.g., a background formatter, editor auto-save, build/watch task, or any other process that rewrites the file — plausible in developer workflows on a freshly cloned malicious repository that ships such tooling), `formatPatch` will apply the user's old line-index selections to new hunk content. This can silently stage and commit (or discard) lines the user never reviewed or intended — a direct "silent corruption of what the user commits" scenario, potentially reintroducing or hiding attacker-authored content in a commit the user believes matches what they reviewed and approved.

## Likelihood Explanation
Medium: it requires a timing window between diff display/selection and clicking Commit during which the working-tree file content changes without the user re-reviewing the diff. This window is entirely plausible in real developer environments (auto-formatters, linters-on-save, watch/build scripts commonly shipped in repositories) and does not require local/admin access, leaked credentials, or unnatural user steps — normal "review diff, then commit" usage is sufficient.

## Recommendation
Before applying the patch in `applyPatchToIndex`/`discardChangesFromSelection`, revalidate that the newly fetched diff is structurally identical (same hunks/line count/content) to the diff the selection was computed against, and abort/re-prompt the user if it has changed, rather than silently re-mapping indices onto new content. Consider keying selections by content hash of hunks rather than raw line index, or caching and reusing the exact diff object shown to the user for both `stageFiles` and `discardChangesFromSelection`.

## Proof of Concept
1. Clone a repository and modify a tracked file so it has several hunks.
2. In GitHub Desktop, open the Changes view, view the diff, and select only specific lines/hunks for commit (partial selection).
3. Before clicking "Commit", have a background process append/insert new lines into the same file (simulating an auto-formatter, watch task, or any writer), changing hunk boundaries/line numbers without the user reopening the diff.
4. Click "Commit". Trace shows `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetching the diff via `getWorkingDirectoryDiff` and `formatPatch` (`app/src/lib/patch-formatter.ts:143-161`) applying the old selection's line indices to the new hunks — producing a committed patch that does not match either the diff originally reviewed by the user or the file's true current state, without any warning.
