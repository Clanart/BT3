### Title
Cached FROST preprocess seed is persisted and reused deterministically, enabling secret-share recovery on repeated signing for the same context - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug class is "an entry is freed/consumed but left in a container, then used (freed) again". Serai's analog: `CachedPreprocesses` stores the FROST preprocess seed keyed by `context`, and `preprocess_internal` regenerates identical nonces from that seed every time it runs, without ever clearing the entry. Any second signing pass under the same context reuses the same nonce material — the exact "stale entry reused after it should have been invalidated" pattern.

### Finding Description
`SigningProtocol::preprocess_internal` writes the `CachedPreprocess` seed to the DB the first time a context is seen, then loads it with `CachedPreprocesses::get` on every subsequent call; there is no `CachedPreprocesses::del`/`remove`/`take` anywhere in the codebase. [1](#0-0) 

`AlgorithmSignMachine::from_cache` calls `seeded_preprocess`, which seeds `ChaCha20Rng` with the cached seed — making all nonces and the preprocess commitments fully deterministic functions of `(seed, keys)`. [2](#0-1) 

`share_internal` calls `preprocess_internal` again to rebuild the sign machine before calling `sign`, so every share produced under a given context uses the same `d`, `e` nonces. [3](#0-2) 

For `DkgConfirmer`, the context is `(b"DkgConfirmer", attempt)`, so all share-generation within an attempt reuses one nonce set. Both `share` and `complete` route through `share_internal`, and `complete` invokes it a second time. [4](#0-3) 

A FROST share has the form `s = d + rho·e + c·λ·x`. The binding factor `rho` is computed from the transcripted participant/preprocess set, and `c` commits to the message (`set_keys_message`, which includes the `KeyPair` being confirmed and the removed set). [5](#0-4) 

### Impact Explanation
If two (or more) share-producing invocations occur under the same attempt with attacker-influenced inputs differing in either the preprocess set (changing `rho`) or the `KeyPair`/message (changing `c`), the repeated `d`, `e` turn the shares into a linear system. With two shares differing only in `c` (same preprocesses, different `key_pair`), `x = (s1 − s2) / ((c1 − c2)·λ)` directly — full recovery of the validator's MuSig secret share, which the code itself warns about: "Reusing preprocesses would enable a third-party to recover your private key share." [6](#0-5)  Recovery of `t` shares yields the threshold secret and total key compromise.

### Likelihood Explanation
The DKG confirmation preprocess and shares are untrusted tributary data; `share(preprocesses, key_pair)` accepts both the participant preprocess map and the `KeyPair` from externally supplied messages, so a participant can influence `rho` and `c`. [7](#0-6)  Whether two distinct `(preprocesses, key_pair)` combinations reach `share`/`complete` under the same attempt depends on tributary data-handling in `coordinator/src/tributary/handle.rs`, which I could not fully verify in the available iterations; if only one unique combination is ever signed per attempt, the second deterministic use in `complete` is benign because it reproduces the identical share. The seeded-reuse hazard is unconditional in the code, however — nothing in `preprocess_internal` enforces the documented single-use contract.

### Recommendation
Delete the `CachedPreprocesses` entry (or atomically rotate it) after the first share is produced for a context — mirroring the kernel fix's "set the slot to NULL after freeing". Concretely: after `share_internal` consumes the seed, call `CachedPreprocesses::del(txn, &context)` so a later call generates a fresh seed, or have `preprocess_internal` `take` the entry and only fall back to it if a matching prior output is proven identical (same participants, same message). Also bind the consumed context into any retry/attempt path so retries cannot resurrect the same seed.

### Proof of Concept
1. During a `Topic::DkgConfirmation` round for attempt `a`, an honest validator stores a seed under `CachedPreprocesses[(b"DkgConfirmer", a)]`.
2. A participant causes `DkgConfirmer::share(preprocesses_A, key_pair_1)` to run, publishing share `s1 = d + rho_A·e + c_1·λ·x`.
3. The same participant supplies `key_pair_2 ≠ key_pair_1` (or a differing preprocess set `preprocesses_B`, changing `rho`) under the same attempt, triggering a second `share_internal` call that reloads the identical seed and emits `s2` with the same `d`, `e`.
4. With `s1`, `s2` and the publicly known `rho`, `c_1`, `c_2`, `λ`, solve for `d`, `e`, `x` — with equal preprocess sets, `x = (s1 − s2)·((c_1 − c_2)·λ)⁻¹`.
5. Repeating across `t` validators recovers the full threshold secret key.
