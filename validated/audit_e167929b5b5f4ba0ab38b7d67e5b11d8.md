### Title
`ReceivedOutput::read` accepts attacker-controlled output/offset/outpoint tuples with no consistency check, letting forged bytes fabricate unspendable "received" outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes a firewall accepting TCP packets for connections that are not in the expected (ESTABLISHED) state — input accepted without validating that it is consistent with the state it claims to represent. The Serai analog is `ReceivedOutput::read` in `bitcoin-serai`: it deserializes three independent fields (`offset`, `output: TxOut`, `outpoint`) from untrusted bytes and returns a `ReceivedOutput` that the wallet layer then treats as a spendable output owned by the scanner's key — without ever checking that the `output.script_pubkey` actually corresponds to `key + offset * G`, or that the outpoint/output pairing is coherent. The only place this binding is established is `Scanner::scan_transaction`, which looks up `output.script_pubkey` in the registered scripts table; `ReceivedOutput::read` bypasses that check entirely.

### Finding Description
`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) reads a `Secp256k1` scalar as the spend `offset`, then a consensus-decoded `TxOut`, then an `OutPoint`, and constructs `ReceivedOutput { offset, output, outpoint }` directly. There is no verification that:

1. `output.script_pubkey == p2tr_script_buf(key + offset * G)` — the actual invariant `Scanner::register_offset`/`scan_transaction` maintain (mod.rs:185-211). `scan_transaction` only produces a `ReceivedOutput` after `self.scripts.get(&output.script_pubkey)` succeeds; deserialization skips this.
2. The `offset` is even-parity-consistent the way `register_offset` enforces (it increments `offset` until the derived tweaked key has even Y; mod.rs:180-196). A deserialized odd-parity offset produces a tweaked key whose x-only BIP-340 encoding does not match any standard spend path this signer would produce.
3. The `output.value`/`outpoint` correspond to anything real — they are simply trusted.

Downstream, `ReceivedOutput` is consumed as a guaranteed-spendable output: `offset()` is used to re-derive the signing key (`self.keys.offset(offset)` style usage when building the spend transaction), `outpoint()` populates the transaction input, and `value()` feeds fee/change/dust math. A forged `ReceivedOutput` where the offset does not match the script_pubkey yields a Schnorr signature under the wrong key — the input is unspendable on-chain — yet the wallet believes it holds those funds and will deduct them, compute change from them, and produce an invalid transaction.

### Impact Explanation
An attacker who can feed bytes to `ReceivedOutput::read` (the deserializer is an explicit in-scope untrusted-bytes sink) can cause the wallet to report funds as received that are not spendable: a crafted `TxOut` with an arbitrary `script_pubkey` plus a fabricated `OutPoint` is accepted as owned by the key. Consequences include crediting deposits that never occurred, constructing funding transactions referencing non-existent or unspendable inputs (burning real fees/change outputs into an invalid transaction), and corrupting balance/fee accounting. This is a fabrication of wallet state from public inputs, matching the "wrong-state acceptance" class of the CVE.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ReceivedOutput::read`, e.g., received outputs relayed between processors, loaded from an untrusted store, or supplied by a peer — the constructor gives callers a structurally valid object indistinguishable from a scanner-produced one. No signature or secret knowledge is needed to forge it. Exploitation does not produce a forged *valid* signature (the offset mismatch prevents spending), which caps severity below Critical/High, but false crediting of funds and invalid-spend construction are concrete and attacker-driven.

### Recommendation
Bind the deserialized fields to the key/offset invariant. Options:

- Add the owning `ProjectivePoint` (or the `Scanner`) to a `ReceivedOutput::read`/`verify` path and assert `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset).unwrap()` plus the even-parity condition enforced by `register_offset`.
- Alternatively, make `ReceivedOutput` fields private (they already are) and make deserialization fallible by requiring it to pass through `Scanner::scan`-style validation — i.e., deserialize as `(OutPoint, TxOut)` and require a scanner lookup to recover the offset rather than trusting the serialized one.
- At minimum, document that `ReceivedOutput::read` output must be re-validated against `Scanner` before use, and reject outputs whose `script_pubkey` is not in the registered set.

### Proof of Concept
```rust
// Conceptual: attacker bytes -> ReceivedOutput::read
// key = scanner key (public, x-only P2TR)
let attacker_offset = Scalar::ONE;            // not the registered offset
let fake_out = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: ScriptBuf::new_p2tr_tweaked(some_other_key), // not key + offset*G
};
let fake_outpoint = OutPoint::new(Txid::all_zeros(), 0);      // non-existent UTXO

let mut bytes = vec![];
bytes.extend(attacker_offset.to_bytes());
bytes.extend(serialize(&fake_out));
bytes.extend(serialize(&fake_outpoint));

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// forged.value() == 1_000_000 reported as owned by the wallet key;
// any spend built from `forged.offset()` produces an invalid BIP-340 signature
// under the fake_out script_pubkey, so the funds are unspendable.
```

Supporting references: the trust assumptions live at `Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214, which is the only path that actually checks `scripts.get(&output.script_pubkey)`), `register_offset` parity handling (mod.rs:180-196), and the field-free construction in `ReceivedOutput::read` (mod.rs:122-134).

Note on scope confidence: I verified the read path performs no offset↔script binding and that `scan_transaction` is the only place enforcing it. I did not trace every consumer of `ReceivedOutput` (e.g., `send.rs` internals) to confirm exactly where `offset()` is applied to keys, so the precise downstream failure (invalid tx vs. credited balance) depends on integrator usage — the invariant break itself is confirmed.
