### Title
Malicious ERC20 token registered via `RegisterERC20` can grant hidden allowances during escrow transfer, enabling theft of the module's escrowed token backing - (File: `x/erc20/keeper/msg_server.go`)

### Summary
`x/erc20`'s `RegisterERC20` msg server lets a caller register an arbitrary "UniswapV3-like" style ERC20 contract as a token pair, similar to the `UNCX_ProofOfReservesV2_UniV3` pattern of accepting an arbitrary user-supplied contract. The module then trusts that contract's `transfer()` semantics during `ConvertERC20`/`ConvertCoin`, validating only balance deltas, not allowance state changes. The codebase's own test fixture `ERC20MaliciousDelayed` demonstrates that a token can secretly grant a huge `allowance()` to an attacker-controlled address on every `transfer()` call while preserving correct balances - and this scenario is asserted to **pass** in `tests/integration/x/erc20/test_msg_server.go` (`"pass - delayed malicious contract"`).

### Finding Description
`RegisterERC20` in [1](#0-0)  registers any hex address as an ERC20 token pair (gated by `PermissionlessRegistration`/`IsERC20Enabled` params, which are governance-controlled but do not vet contract bytecode/behavior).

When a user calls `ConvertERC20` to escrow their ERC20 tokens into the module account and mint native coin 1:1, `convertERC20IntoCoinsForNativeToken` executes the token's `transfer(ModuleAddress, amount)` via `CallEVMWithData`, then only checks that the module's **balance** increased by the expected amount: [2](#0-1) 

Similarly, `ConvertCoinNativeERC20` unescrows tokens via `transfer(receiver, amount)` from the module account and checks only the receiver's balance delta: [3](#0-2) 

Neither path checks whether the token's `transfer()` implementation mutated `allowance()` state as a side effect. The repository's own malicious test contract shows this is exploitable: on every `transfer()` call, it silently grants an unlimited allowance to a hardcoded "thief" address, while leaving balances correct (so the balance-invariance check passes): [4](#0-3) 

The integration test suite explicitly documents this as passing (i.e., accepted by the module) rather than rejected: [5](#0-4) 

An attacker who deploys their own version of such a token (with the "thief" address set to an address they control instead of the hardcoded one in the test fixture), registers it via `RegisterERC20`, and calls `ConvertERC20` to escrow tokens into `types.ModuleAddress`, causes the token's `transfer()` to grant the attacker-controlled address an allowance over the **module account's** balance of that ERC20 contract. The attacker can then call `transferFrom` directly on the malicious ERC20 contract (bypassing the erc20 module entirely) to drain the module's escrowed token balance to any address of their choosing.

### Impact Explanation
Draining the module's escrowed ERC20 balance breaks the 1:1 backing invariant between the native/IBC-transferable Cosmos coin denom (minted via `MintCoins` in `convertERC20IntoCoinsForNativeToken`) and the actual ERC20 tokens held in escrow. After the drain:
- The native coin denom remains in circulation (held by the original converter and any subsequent recipients, including across IBC), but the underlying ERC20 collateral is gone.
- Later holders attempting `ConvertCoin` back to the ERC20 token will find insufficient escrowed balance, and/or the attacker has already extracted the tokens directly.

This matches the "Critical permanent freezing/theft/unauthorized extraction of ... token-pair-backed balances" allowed-impact category: the module-held collateral backing a registered token pair can be stolen by an unprivileged user who registers and interacts with their own crafted ERC20 contract, corrupting the accounting between the Cosmos coin and its ERC20 backing.

### Likelihood Explanation
Likelihood is high given a self-registering (or governance-approved) malicious token: `RegisterERC20` does not vet contract bytecode, and the module's own test suite already contains a working proof-of-concept malicious contract (`ERC20MaliciousDelayed`) whose exact behavior triggers exactly the gap described (balance-only invariant checks, no allowance guard). No special privileges are required beyond registering the token pair, which - depending on `params.PermissionlessRegistration` - may itself be permissionless, or reachable via a routine governance-approved listing (a normal, expected registration flow, not a privileged/malicious-governance assumption).

### Recommendation
- After any `transfer()`/`transferFrom()` call made by the erc20 module on a native ERC20 contract, verify that no unexpected `allowance()` was granted from the module account (or from the affected addresses) to any third party, or explicitly reset/zero any allowances the module account did not itself set.
- Alternatively (and more robustly, mirroring the audited fix pattern of whitelisting position managers), require ERC20 tokens registered via `RegisterERC20` to conform to a stricter bytecode/behavioral check (e.g., disallow registration of tokens with non-standard bytecode, or add a governance-curated allow-list for tokens that back convertible native coins) so that only vetted, well-behaved ERC20 implementations can be paired 1:1 with mintable native coin denoms.
- At minimum, immediately after escrowing tokens into `types.ModuleAddress`, explicitly call `approve(anyone, 0)`-style resets are impractical generically; instead, detect `Approval` events emitted during the module's own `transfer` calls in the returned `res.Logs` (similar to `validateTransferEventExists`) and reject the conversion if an `Approval` event naming a spender other than expected values (e.g., zero) is found.

### Proof of Concept
1. Attacker deploys a malicious ERC20 contract implementing OpenZeppelin `ERC20` where `transfer()` is overridden to call `_approve(address(this) /* i.e. the transfer's `to` param, here the module */, attackerAddr, type(uint256).max)` before performing the real transfer - directly analogous to `ERC20MaliciousDelayed.transfer()` in [6](#0-5)  but with `_thief` set to the attacker's own address.
2. Attacker calls `MsgRegisterERC20` to register this contract as a token pair (permissionless registration, or via a routine governance vote as with any legitimate token listing) - see registration path in [7](#0-6) .
3. Attacker mints tokens to themselves on the malicious contract, then submits `MsgConvertERC20` to escrow tokens to `types.ModuleAddress` and mint native coin. This call succeeds and passes the balance-invariance check as shown in [8](#0-7) , while secretly granting the attacker's address an allowance over the module account's token balance.
4. Attacker calls `transferFrom(ModuleAddress, attackerAddr, moduleBalance)` directly on the malicious ERC20 contract (outside the erc20 module, using the granted allowance) to drain all module-held collateral for that token pair, while the previously-minted native coin remains circulating and redeemable claims against now-nonexistent collateral.

```go
// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

		ctx.EventManager().EmitEvent(
			sdk.NewEvent(
				types.EventTypeRegisterERC20,
				sdk.NewAttribute(types.AttributeKeyCosmosCoin, pair.Denom),
				sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
			),
		)
	}

	return &types.MsgRegisterERC20Response{}, nil
}
```

```text
pragma solidity ^0.8.0;

import "@openzeppelin/contracts/token/ERC20/presets/ERC20PresetMinterPauser.sol";

// This is an evil token. Whenever an A -> B transfer is called,
// a predefined C is given a massive allowance on B.
contract ERC20MaliciousDelayed is ERC20PresetMinterPauser {
  address private _thief = 0x4dC6ac40Af078661fc43823086E1513635Eeab14;
  uint256 private _bigNum = 1000000000000000000; // ~uint256(0)
  constructor(uint256 initialSupply)
    ERC20PresetMinterPauser("ERC20MaliciousDelayed", "ERC20MALICIOUSDELAYED") {
      _setupRole(DEFAULT_ADMIN_ROLE, msg.sender);
      _mint(msg.sender, initialSupply);

  }
  function transfer(address recipient, uint256 amount) public virtual override returns (bool) {
    // Any time a transaction happens, the thief account is granted allowance in secret.
    // Still emits an Approve!
    super._approve(recipient, _thief, _bigNum);
    return super.transfer(recipient, amount);
  }
}
```
