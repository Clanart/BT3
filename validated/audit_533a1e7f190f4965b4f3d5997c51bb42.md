This confirms it: `Kip71BaseFeeDenominator` explicitly requires `v != 0` in its `FormatChecker`, but `Kip71GasTarget` uses `noopFormatChecker`, which performs no validation at all, allowing `GasTarget` to be voted to `0`. `GasTarget` is used as a divisor in `NextMagmaBlockBaseFee` without any zero-guard (unlike `BaseFeeDenominator`, which has an explicit `if kc.BaseFeeDenominator == 0` fallback "to avoid panic"). No such guard exists for `GasTarget`.

### Title
Missing zero-value validation on KIP-71 `GasTarget` governance parameter causes division-by-zero panic in base fee calculation - (File: `kaiax/gov/param.go`, `params/kip71_config.go`)

### Summary
The `Kip71GasTarget` governance parameter uses `noopFormatChecker` [1](#0-0)  which performs no validation, unlike its sibling parameter `Kip71BaseFeeDenominator`, which explicitly rejects zero via `return ok && v != 0` [2](#0-1) . `GasTarget` is used as an unguarded divisor in `NextMagmaBlockBaseFee`, the KIP-71 dynamic base fee computation that runs on every block after the Magma hardfork.

### Finding Description
`NextMagmaBlockBaseFee` computes the base fee delta using `gasTarget` as a divisor in both the "gas used above target" and "gas used below target" branches: [3](#0-2) [4](#0-3) 

The code explicitly guards against `BaseFeeDenominator == 0` ("To avoid panic, set the fluctuation range small") [5](#0-4) , but performs no equivalent guard for `gasTarget`. The only case that avoids the division is when `parentGasUsed == gasTarget` [6](#0-5) ; whenever gas usage in a block differs from a `gasTarget` of `0` (i.e., any block with `GasUsed > 0`), execution proceeds to `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, which panics (`big.Int.Div` panics on division by zero).

`GasTarget` can be set to `0` through the standard KIP-81 governance voting flow: a validator submits `headergov.NewVoteData(..., gov.Kip71GasTarget, uint64(0))`, which passes `NewVoteData`/`VerifyVote` because `checkConsistency` explicitly treats `Kip71GasTarget` as a parameter with "no more checks" beyond `NewVoteData`'s format check [7](#0-6) , and the format checker itself is a no-op. It can also be set via contract governance (`GovParam` contract `setParamIn`), which reuses the same `Params` map and thus the same unchecked `FormatChecker` [8](#0-7) .

### Impact Explanation
Once `GasTarget = 0` becomes effective at an epoch boundary, every subsequent block whose gas usage is nonzero triggers `NextMagmaBlockBaseFee`, which is called both when verifying headers (`VerifyMagmaHeader`) and when assembling new blocks. A division by zero causes a Go runtime panic on all full nodes and validators processing blocks after the parameter takes effect — this is a chain-halting, network-wide denial of service, not a resource-only bug, since it prevents further block production/verification across all honest nodes simultaneously (a "State transition and gas/burn accounting" / "block assembly" defect per the in-scope categories).

### Likelihood Explanation
Governance parameter changes require a validator (or GC) vote/contract call, so this is not exploitable by an arbitrary unprivileged sender, but it is reachable through the standard, unprivileged-from-the-protocol's-perspective KIP-81 parameter update mechanism with zero additional validation — a single malformed vote (accidental or malicious) for `kip71.gastarget = 0` is sufficient to trigger the panic across the network at the next epoch boundary. The complete absence of a format check (contrasted with the deliberate `!= 0` check on the adjacent `BaseFeeDenominator` parameter) indicates this is an oversight rather than an intentional allowance.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally for `Kip71MaxBlockGasUsedForBaseFee`, which is also used without a zero-check) that rejects `0`, mirroring the existing `Kip71BaseFeeDenominator` check:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
},
```
As defense in depth, also add an explicit zero-guard directly in `NextMagmaBlockBaseFee` (as already done for `BaseFeeDenominator`) so that a `0` value arriving through any other path (e.g., genesis chain config or future code paths) cannot cause a panic.

### Proof of Concept
1. A validator submits a governance vote `headergov.NewVoteData(validatorAddr, "kip71.gastarget", uint64(0))` — this passes `NewVoteData` and `VerifyVote`/`checkConsistency` since `Kip71GasTarget`'s format checker is a no-op [7](#0-6) .
2. At the next epoch boundary the vote becomes part of `header.Governance` and the parameter set effective from that block has `GasTarget = 0`.
3. On the next block after the change where `parentHeaderGasUsed != 0` (virtually any real block with transactions), `NextMagmaBlockBaseFee` enters the `parentGasUsed > gasTarget` branch and executes `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0` [3](#0-2) , causing a runtime panic in every node computing or verifying that block's base fee, halting the chain.
