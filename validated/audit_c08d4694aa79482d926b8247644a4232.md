### Title
PedPoP encrypted-share PoP is not bound to the recipient, allowing replay of an honestly-formed message to a different participant who will then produce valid blame against the honest sender - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the report's "a required parameter was never bound during initialization, so the default/ambient value is silently used", the per-message proof-of-possession in PedPoP's `EncryptedMessage` binds the context, sender, ephemeral key, and ciphertext — but never the *recipient*. `pop_challenge` (encryption.rs:302-324) takes `context, nonce, key, sender, msg` with no recipient field, and `Encryption::encrypt`/`decrypt` (encryption.rs:460-501) likewise never mix the recipient's identity or encryption key into the PoP transcript. As a result, an `EncryptedMessage<C, SecretShare<C::F>>` that sender `l` legitimately formed for recipient `A` is a fully "validly signed" message when presented as a message from `l` to any other participant `B`.

### Finding Description
- `EncryptedMessage` consists of `key` (ephemeral `x·G`), `pop` (Schnorr signature), and `msg` (ChaCha20 ciphertext under `ecdh(recipient_enc_key, x·G)`) (encryption.rs:80-93, 95-133).
- `pop_challenge` is invoked in `decrypt` as `pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg...)` — `from` is the *sender*; the receiver's `Participant` index and `enc_pub_key` appear nowhere in the transcript (encryption.rs:484, 302-324).
- An unprivileged party that observes the authenticated-channel message `l → A` can deliver the identical bytes as `l → B`. `B`'s `KeyMachine::calculate_share` decrypts with `B`'s ECDH key, obtaining a garbage scalar. Two outcomes, both harmful to the honest sender:
  - If the garbage fails `C::F::from_repr`, or parses but fails `share_verification_statements`, `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` is returned with a *valid* `EncryptionKeyProof` (pedpop/src/lib.rs:476-499).
  - `BlameMachine::blame_internal` then verifies the (correctly derived) ECDH key and the invalid share, and returns `sender` as the faulty party (pedpop/src/lib.rs:582-608).
- The honest sender `l` — whose only "fault" was sending a correct message to `A` — is thereby cryptographically blamed as faulty for `B`, which in the wider protocol maps to removal/slashing of an honest validator and abort of the DKG attempt.

### Impact Explanation
A third party (or the malicious recipient `B` themselves) can manufacture a blame statement that deterministically convicts an honest DKG participant, using only bytes the sender publicly broadcast. This is an incorrect-attribution primitive: it produces a forged-incrimination proof accepted by `BlameMachine`/`AdditionalBlameMachine`, forcing DKG abort and wrongful punishment of `l`. It also lets `B` selectively trigger blame to leak nothing of their own while griefing a chosen honest party. Severity: Medium (protocol abort / wrongful blame, no key recovery).

### Likelihood Explanation
Reachable by any party able to relay/copy the sender's authenticated ciphertext bytes to a different recipient's `calculate_share` input — including the malicious recipient themselves, who needs no cooperation. No key material, collusion, or BFT assumptions are required. It does require the integrator to route per-recipient messages based on untrusted delivery rather than a recipient field the ciphertext/PoP commits to — exactly the gap the missing binding creates.

### Recommendation
Bind the recipient into the PoP and/or cipher transcript: e.g., extend `pop_challenge` with `transcript.append_message(b"recipient", recipient.to_bytes())` and pass the target `Participant` through `encrypt`/`decrypt`, or domain-separate `cipher`/`encryption_key_transcript` per `(sender, recipient)` pair. Then a message replayed across recipients fails the PoP batch check, which the code already treats as `blame: None` (self-explanatory sender fault only when the message was actually addressed to the verifier — i.e., it cannot convict an honest party).

### Proof of Concept
1. Run PedPoP with `n ≥ 2`. Honest sender `l` calls `encryption.encrypt(rng, A, share_for_A)`, producing `m = EncryptedMessage { key: x·G, pop, msg }`.
2. Attacker (or `B`) feeds `m` to `B`'s `KeyMachine::calculate_share` in the `shares` map under key `l`.
3. `B` decrypts `m` with `ecdh(B_enc_key, x·G)` ≠ the intended cipher key → garbage `share_bytes`.
4. The PoP verifies, because `pop_challenge` contains no recipient binding — so `B` obtains `blame = Some(EncryptionKeyProof { key: ecdh(B_enc_key, x·G), dleq })`.
5. `BlameMachine::blame(l, B, m, Some(blame))` verifies the DLEq (correct ECDH derivation) and the invalid share, returning `sender = l` as faulty — an honest party is convicted with a valid proof.
