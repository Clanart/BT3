## Finding: Repository sidebar renders unsanitized Unicode (homoglyph/bidi-control) repository names, enabling visual spoofing between distinct local repositories

### Summary

`HighlightText` in `app/src/ui/lib/highlight-text.tsx` renders the raw `text` prop character-by-character with no filtering, normalization, or Unicode-confusable/bidi handling. It is used by `RepositoryListItem` to render `repository.name` (or `alias`) in the sidebar. For repositories without an associated `GitHubRepository`, `Repository.name` is derived directly from `Path.basename(path)` [1](#0-0) [2](#0-1) , and that path is in turn derived from `sanitizeCloneName()`, which only strips path-traversal segments and a trailing `.git` — it does **not** strip Unicode bidi-control characters (`U+202A`-`U+202E`, `U+2066`-`U+2069`) or filter homoglyph characters [3](#0-2) . The rendering path passes this string straight to `HighlightText`, which just emits `<span>`/`<mark>` text nodes [4](#0-3) [5](#0-4) .

### Finding Description

Two different clone URLs/directory names can be crafted so that, after Desktop applies `sanitizeCloneName`, they resolve to distinct local paths whose basenames are visually indistinguishable (e.g. using a Cyrillic "а" (U+0430) versus Latin "a", or embedding bidi-override characters such as U+202E to reorder rendered glyphs). Because the codebase already has a dedicated `HiddenBidiCharsRegex` used to warn about hidden bidi characters in diff content [6](#0-5) , the project is aware of this general class of attack for diffs, but the same protection is not applied to repository display names.

The sidebar's only existing disambiguation mechanism is exact string equality between display titles (`allNames`/`groupNames` maps), used to decide whether to prepend an owner prefix [7](#0-6) . Since homoglyph strings are different code points, this check does not fire, and the spoofed entry displays with no distinguishing prefix. The item's underlying path is only revealed on hover-triggered tooltip [8](#0-7) , which the user has no reason to check if the two names appear equal at a glance.

Note that this only applies to repositories without `GitHubRepository` metadata (local-only / not GitHub-hosted), because GitHub.com repository names are restricted server-side and would not contain confusable Unicode; the `gitHubRepository.name` path is not affected [2](#0-1) .

### Impact Explanation

If a user is induced to clone or add two repositories whose local directory basenames render identically in the sidebar (one trusted, one attacker-controlled), the user can select the wrong entry when intending to push/commit, silently sending content to the attacker's remote instead of the trusted one. This matches "silent corruption of what the user commits or pushes."

### Likelihood Explanation

Exploitation requires the victim to first clone/add the attacker's lookalike repository (a URL or repo the attacker controls, in scope per the review's "attacker controls a cloned/fetched repository"), and to already have (or subsequently add) a trusted repository with a similar name. This is a real but constrained scenario — it doesn't grant code execution, file access outside the repo, or credential exfiltration; it is a UI/spoofing issue whose exploitation depends on the user's own selection behavior rather than an automatic action, and the existing tooltip does show the real path on hover.

### Recommendation

- Apply a Unicode-confusable/bidi sanitization step (reusing or extending `HiddenBidiCharsRegex`) to repository names/paths before display, or strip/escape bidi-control characters in `HighlightText`/`Repository.name` derivation.
- Extend `sanitizeCloneName` to reject or normalize bidi-control characters, similar to the traversal-segment handling already present [3](#0-2) .
- Consider Unicode-normalization-aware duplicate detection (not just exact string equality) for the sidebar's `needsDisambiguation` logic [7](#0-6) , and always show full path/owner context for local (non-GitHub) repositories.

### Proof of Concept

1. Craft two clone URLs, e.g. `https://github.com/owner/admin-repo.git` (trusted) and `https://evil.example.com/owner/аdmin-repo.git` (Cyrillic "а", U+0430) or one embedding a bidi-override character before the visible name.
2. Clone both into Desktop; `sanitizeCloneName` produces directory basenames that are byte-different but visually identical [3](#0-2) .
3. Observe the sidebar: both entries render via `HighlightText` with no visual distinction and no disambiguation prefix, since `needsDisambiguation` compares exact strings [7](#0-6) .
4. Select the visually-matching entry expecting the trusted repo; commit/push instead targets the attacker's remote.

This is a legitimate, but moderate-severity UI-spoofing gap rather than a high-impact exploit (no code execution, sandbox escape, or credential exfiltration is achieved) — it should be reported as a lower-severity spoofing/hardening issue rather than a critical vulnerability.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
