### Title
Independent, inconsistent conflict-marker parsers in Copilot conflict resolution let a crafted repository desync hunk counts, causing silent code loss/corruption when Desktop stages the "resolved" file - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
Desktop's AI-assisted merge-conflict resolver extracts conflict hunks from a file with one hand-rolled parser (`extractConflictHunks`) to build the prompt sent to Copilot, and later splices Copilot's per-hunk answers back into the file on disk with a *second, independently written* parser (`reassembleResolvedFile`). The two parsers use different rules for what counts as a well-formed conflict block. `validateResolutionPaths` only compares hunk *counts*, not actual positions, so if a file is crafted so the two parsers disagree, the count check can still pass while the splice targets the wrong marker blocks. The result is written straight to disk and `git add`'ed with no diff review, so incorrect/lost hunks are silently staged for commit.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks the file once. When it starts consuming an "ours" block and never finds a matching `>>>>>>>` before EOF, it simply `continue`s the outer loop — but by then `i` has already been advanced to `lines.length` while scanning for the missing markers, so **the rest of the file is never scanned again** and any well-formed conflicts that come after the malformed block are silently dropped from the hunk list: [1](#0-0) 

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`), which runs later against the *same raw file content*, uses a different malformed-block rule: for every `<<<<<<<` it independently looks ahead for a separator/closer; on failure it treats **only that one line** as regular content and resumes scanning line-by-line for the next marker, rather than abandoning the rest of the file: [2](#0-1) 

Because these two hand-written state machines can disagree on where a "conflict block" ends (e.g. a file that legitimately contains marker-like text — documentation about git conflicts, a lockfile, or generated content that includes `<<<<<<<`/`=======`/`>>>>>>>`-shaped lines — interleaved with a genuine unresolved conflict), `extractConflictHunks` can report fewer hunks for a file than `reassembleResolvedFile` will actually find and splice into.

`validateResolutionPaths` only enforces that the *count* of hunks Copilot returned matches `f.hunks.length` from the context builder's parse — it never re-validates against the raw file's actual marker positions: [3](#0-2) 

So Copilot answers with N-1 resolutions (matching what the prompt showed it), the count check passes, but `reassembleResolvedFile` finds N real conflict blocks in the file on disk. Every block after the desync point is spliced with the wrong resolution, and the final block — with `hunkIndex >= hunkResolutions.length` — is dropped with nothing spliced in (its `<<<<<<<...>>>>>>>` content is simply deleted): [4](#0-3) 

This corrupted content is then written to disk and staged directly, without further diff verification, when the user clicks "Continue Merge": [5](#0-4) 

This is the structural analog of the reported bug: a value (here, the "hunk index"/count) computed by one code path is trusted and matched against a value computed by an inconsistent second code path (analogous to using asset decimals where share decimals were meant), producing a silently wrong result that is then persisted.

### Impact Explanation
An attacker who controls content merged into the user's repository (a malicious/compromised branch, a crafted file in a dependency repo, or any content the victim merges/rebases/cherry-picks against) can cause GitHub Desktop's Copilot conflict resolution to silently delete or misapply code in the committed result — without the user's explicit intent, and without any tool showing that a whole hunk was dropped. Because the final write path goes straight to `writeFile` + `git add`, this is "silent corruption of what the user commits and pushes," one of the explicitly valid impact classes.

### Likelihood Explanation
Requires: (1) the user to have Copilot conflict resolution enabled/available and use "Continue Merge" with Copilot's suggestions, and (2) a conflicted file whose content contains marker-shaped lines that are ambiguous enough to make the two independent parsers disagree on hunk boundaries (e.g. minified/generated files, files about git tooling, or lock files with repeated `=======`-like separators). This is a real, reachable condition — no privileged access or local/physical presence is needed, only that the victim merges a repository/branch the attacker influences. The two-parser inconsistency is a genuine implementation defect (duplicated, non-shared marker-scanning logic with different error-handling branches), which is inherently fragile and easy to trigger with adversarial file content.

### Recommendation
- Use a single, shared conflict-marker parser for both context extraction (`extractConflictHunks`) and reassembly (`reassembleResolvedFile`), so hunk boundaries can never diverge between the two phases.
- Instead of matching resolutions to conflict blocks "by order," have the reassembler re-derive hunk boundaries from the same data structure used to build the prompt (e.g. store byte/line offsets in `IConflictHunk` and splice by offset, not by re-scanning the raw file).
- Add a hard assertion/validation error (not a silent fallback) if the number of conflict blocks discovered during reassembly doesn't exactly match the number of hunk resolutions available, aborting the write instead of dropping content.
- Surface a diff/preview of the AI-modified file before staging/committing so any content loss is visible to the user prior to `git add`.

### Proof of Concept
1. Set up a merge that produces a conflicted file (`example.md`) containing:
   - A real conflict block: `<<<<<<< HEAD` / `real ours` / `=======` / `real theirs` / `>>>>>>> feature`
   - Followed later by content engineered so `extractConflictHunks`'s inner "collect theirs" loop consumes to EOF without finding a `>>>>>>>` (e.g. an unmatched `<<<<<<<`-looking line inside documentation text with no closing marker anywhere after it), causing the malformed-hunk `continue` at `app/src/lib/copilot-conflict-context.ts:240-242` to terminate hunk extraction early even though the file could still contain further real conflicts below.
2. Because `extractConflictHunks` stops scanning, `buildConflictContext`/`f.hunks.length` reports fewer hunks than actually exist for the file if additional genuine conflicts exist after the malformed section.
3. Copilot responds with resolutions matching the (undercounted) prompt; `validateResolutionPaths` passes because counts match.
4. `reassembleResolvedFile`, re-scanning the same raw content with its own laxer rules (`app/src/lib/copilot-conflict-resolution.ts:559-596`), locates a different set/number of `<<<<<<<...>>>>>>>` blocks and splices the too-short `hunkResolutions` array positionally, dropping the last conflict's content entirely (`hunkIndex < hunkResolutions.length` check fails at line 585) and/or misapplying earlier resolutions to the wrong blocks.
5. `_applyCopilotConflictResolutions` writes this corrupted file to disk and stages it via `git add` (`app/src/lib/stores/app-store.ts:7258-7268`) with no diff shown, so the user's next commit/push silently contains lost or swapped code.

Note: I was not able to execute this end-to-end (no test harness access in this environment), so the exact minimal file content that reliably desynchronizes the two parsers should be validated empirically by a background agent using the existing unit tests in `app/test/unit/copilot-conflict-resolution-test.ts` as a starting harness.

  const expectedHunkCounts = new Map(

  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []

    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }

      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
