### Title
Reward misattribution: `on_executed` pays only the first message's signer for all state-machine height advances in a batch - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::on_executed` recovers the relayer/signer only from `messages[0]`, then iterates over *all* `StateMachineUpdated` events in the executed batch (collapsed per state machine to the highest height) and pays the full block-span reward for every one of them to that single recovered signer. Because `pallet_ismp::handle_unsigned` is a permissionless unsigned extrinsic that executes an arbitrary `Vec<Message>` batch supplied by the caller, and because each `ConsensusMessage`'s proof/state advance is public, independently verifiable data (proofs are "freely provided" and re-submittable by anyone), an attacker can assemble a batch consisting of their own trivially-cheap signed consensus message first, followed by other already-valid consensus messages/updates for unrelated state machines, and collect the entire treasury payout for all of them.

### Finding Description
`on_executed` in [1](#0-0)  derives `maybe_relayer_account` exclusively from `messages.get(0)`. It then walks the full `events: Vec<IsmpEvent>` produced by executing the whole batch, and for every distinct `state_machine_id` that advanced, computes `calculate_reward` using the watermark logic in [2](#0-1)  and pays it to that one signer via `process_message` in [3](#0-2) .

`handle_unsigned` is a permissionless, unsigned entrypoint that executes an arbitrary caller-supplied `Vec<Message>` in one transactional call: [4](#0-3) . There is no requirement that all messages in a batch share the same signer, nor that the batch contain only one consensus message. Documentation confirms consensus proofs are public and freely re-submittable by anyone: [5](#0-4) , and rewards are meant to go to "the account recovered from the proof submitter's signature" per-update: [6](#0-5) .

The broken invariant: reward attribution is supposed to be per-message (whoever actually delivered/signed each specific consensus update should be paid for that update's block-span), but the code only checks who signed `messages[0]` and then pays that account for the cumulative height-advance of *every* state machine touched anywhere in the batch. An attacker constructs a batch where element 0 is their own signed (possibly trivial, single-block) consensus message for chain A, and elements 1..N are other already-broadcast, valid consensus messages for chains B, C, D (which anyone can resubmit since proofs are public data, not secrets). All of it executes successfully (since each message is independently valid), producing `StateMachineUpdated` events for A, B, C, D — but the attacker, as `messages[0]`'s signer, collects the treasury reward for the full block-span of B, C, D as well, even though they did not construct or discover those proofs themselves and other relayers who did submit them separately would be racing for nothing or duplicating gas cost. The `LastRewardedHeight` watermark prevents double-payment for the *same* height range once claimed, but does not stop the attacker from being the one who claims it by riding on other messages in the same batch.

Existing guards do not stop this because: (1) `handle_unsigned` has no per-message signer/relayer segregation — it batches for gas efficiency; (2) `on_executed`'s relayer identification logic assumes (incorrectly) that a batch's first message signer represents all consensus deliveries in that batch; (3) `LastRewardedHeight` only prevents replay of the *same* range across separate calls, it does not prevent a single call's misattribution across state machines.

### Impact Explanation
This directly translates to "stealing... of funds" from the `TreasuryAccount`: [7](#0-6) . An attacker who submits a batch containing one throwaway consensus update they signed, plus copies of other pending/valid consensus proofs for other state machines, is paid for block-spans they did not perform the (potentially costly, e.g., BEEFY/SP1 proving) work for, at the expense of the treasury and of the legitimate relayers who generated those other proofs. Reputation minting (`T::ReputationAsset::mint_into`) is likewise misattributed, corrupting the collator-selection input described in [8](#0-7) .

### Likelihood Explanation
High feasibility for an unprivileged actor: `handle_unsigned` is explicitly permissionless and free (unsigned, no fee) per [9](#0-8) ; consensus proofs for other chains are public/republishable, so no malicious peer or leaked key is required — the attacker only needs to observe already-broadcast valid consensus messages (e.g., from the mempool or a previous block) and repackage them behind their own signed message in a single batch before the legitimate relayer's separately submitted transaction lands, or simply whenever they can assemble a batch before others' updates get executed to be "first" in a batch that advances multiple chains.

### Recommendation
Attribute and pay rewards per consensus message, not per batch: iterate `messages`, and for each `Message::Consensus` entry independently recover its own `signer`, correlate it to the specific `StateMachineUpdated` event(s) actually caused by that individual message (not the batch-wide highest height), and pay/mint per (message, state_machine) pair. If per-message-to-event correlation isn't tracked today, add it (e.g., by having message execution surface which event(s) correspond to which message index) so `on_executed` can no longer default to `messages[0]` for the entire batch.

### Proof of Concept
1. Relayer R2 observes a valid, already-broadcast BEEFY consensus proof `M_B` (for chain B) that another relayer R1 is about to submit (or has submitted but not yet finalized/rewarded); proofs are public data.
2. R2 crafts `M_A`, a cheap consensus message for a chain they control/can trivially advance (or reuses any small valid consensus update for chain A that they can sign as submitter), and submits `handle_unsigned([M_A, M_B])` as a single unsigned extrinsic, signed with R2's key on `M_A`.
3. `Pallet::execute` processes both messages; both are valid so both apply, producing `StateMachineUpdated` events for chain A and chain B: [10](#0-9) .
4. `on_executed` fires with `messages[0] = M_A` (signed by R2) and `events` containing both updates: [11](#0-10) .
5. `highest_per_state_machine` collapses to {A: heightA, B: heightB}; `process_message` is invoked twice, both times crediting **R2** (from `messages[0]`'s signature) — including the full block-span reward for chain B's advance, which R2 did not independently discover/prove.
6. R1's legitimate, separately-submitted consensus update for chain B (same or lower height) either fails as stale or, if it lands, cannot re-claim the same block-span due to the `LastRewardedHeight` watermark already having advanced — R1 is paid nothing for the work despite doing the actual proof generation.

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}

# Pallet Relayer

The Hyperbridge protocol is uniquely enabled by cryptographic proofs which certify the integrity of cross-chain transactions. These proofs can be generated by anyone, as they are freely provided by its connected chains. However, the Hyperbridge protocol provides a mechanism to incentivize the generation and submission of these proofs. This is where relayers come in.

Relayers are responsible for collecting and transmitting proofs of cross-chain messages across connected chains. In return, relayers are rewarded with the associated transaction fees that were provided by users and applications. The `pallet-ismp-relayer` module is responsible for tracking the accrued fees and distributing them to the relayers. The module permits relays to withdraw their fees at any time, the module works in conjunction with the [`pallet-host-executive`](/developers/explore/nexus/host-executive) to perform fee withdrawals on the destination chain.

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
