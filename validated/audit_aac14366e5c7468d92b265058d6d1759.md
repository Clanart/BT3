### Title
Webhook `shop_domain` header is trusted for tenant identity despite not being covered by HMAC, enabling cross-shop confusion via webhook replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#shop_domain` returns the raw, unauthenticated `X-Shopify-Shop-Domain` request header, while `hmac_valid?` (in `PayloadVerification`) only signs `request.raw_post`. The library's own documentation and generator templates instruct developers to pass this header value directly to background jobs as the tenant identifier, so an attacker who can obtain any validly-HMAC'd webhook body for the app (e.g., because they legitimately run their own shop using the app) can replay that body with a rewritten shop-domain header and have it accepted as coming from a different shop.

### Finding Description
`hmac_valid?` computes `OpenSSL::HMAC.digest(digest, secret, data)` where `data = request.raw_post`, and compares it via `ActiveSupport::SecurityUtils.secure_compare` against the `X-Shopify-Hmac-Sha256` header. [1](#0-0)  The digest input never includes any request headers, so `X-Shopify-Shop-Domain` is not covered by the signature. `WebhookVerification#shop_domain` simply reads that header as-is: `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]`. [2](#0-1) 

`verify_request` only checks HMAC validity of the body and never cross-checks the shop-domain header against anything derived from the verified payload. [3](#0-2) 

Crucially, the app's webhook signing secret (`ShopifyApp.configuration.secret`) is a single, app-wide secret shared across every shop that installs the app — it is not shop-specific. [4](#0-3)  This means any legitimate installer of the app (an unprivileged "merchant controlling an unrelated shop", per the allowed threat model) will receive genuine, validly-HMAC'd webhook deliveries for their own shop's events. They can capture such a payload+HMAC pair and POST it directly to the app's public webhook endpoint again, this time supplying a forged `X-Shopify-Shop-Domain` header naming a victim shop. Because the HMAC only covers the body, and the secret is shared across all tenants, this replayed request passes `verify_request` unchanged.

The library's own documented usage pattern for `shop_domain` directly propagates this unverified value as the tenant key to background jobs:
```ruby
SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
``` [5](#0-4)  and the shipped generator job templates use it directly for session/tenant lookup, e.g. `Shop.find_by(shopify_domain: shop_domain)` in the uninstall and privacy-webhook job templates. [6](#0-5) [7](#0-6)  None of these paths independently verify that the claimed shop domain matches the actual origin of the HMAC-signed payload.

### Impact Explanation
A forged webhook can cause a job to act on the wrong tenant: e.g., `AppUninstalledJob`/`ShopRedactJob` destroying or redacting a shop record for a shop the attacker doesn't control, or any custom `perform_later(shop_domain: ...)` consumer performing shop-scoped database writes/API calls against victim shop B's session/data while the payload actually originated as shop A's event. This is a cross-shop data/session confusion issue delivered via a forged/replayed webhook, matching Shopify's "Cross-tenant data access / forged request" impact class.

### Likelihood Explanation
Feasibility depends on the attacker being able to legitimately install the app on a shop they control (allowed under "merchant controlling an unrelated shop") and observe a genuine webhook delivery for that shop — which is trivial since the app-wide secret is shared and every installer receives real signed webhooks. The endpoint is public (`POST` to `shopify_app.webhooks_path`), no additional authentication is required beyond the HMAC check, and the exploit is fully repeatable since HMAC validity is independent of the header. The main precondition explicitly stated by the question — that a downstream job trusts the `shop_domain` header value directly for shop/session lookup — matches the documented and generated default usage in this repo.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` as trusted tenant identity on its own. Either (a) bind webhook delivery to a per-shop verifiable value (e.g., cross-check against a shop-specific secret/session, or validate the domain is one the app has an active session/webhook registration for) before dispatching jobs, or (b) have `WebhookVerification` reject requests where the shop domain cannot be corroborated against verified state, and update docs/generator templates to add this cross-check before calling `Shop.find_by(shopify_domain: shop_domain)`.

### Proof of Concept
```ruby
test "HMAC validity does not bind shop_domain header to the payload" do
  # Attacker legitimately installs the app on shop-a and captures a real, validly
  # HMAC'd webhook delivery for shop-a (body + X-Shopify-Hmac-Sha256).
  body = { id: 123 }.to_json
  secret = ShopifyApp.configuration.secret
  valid_hmac = Base64.strict_encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
  )

  # Replay same body+HMAC but claim it's from shop-b (victim) via the header.
  post shopify_app.webhooks_path("orders_update"),
       params: body,
       headers: {
         "X-Shopify-Hmac-Sha256" => valid_hmac,
         "X-Shopify-Shop-Domain" => "victim-shop-b.myshopify.com",
       }

  assert_response :ok # or :no_content — verify_request accepts it
  # Assert downstream job was enqueued with shop_domain: "victim-shop-b.myshopify.com"
  # even though the signed body was originally shop-a's event.
end
```
This demonstrates that `hmac_valid?` passing does not imply the `shop_domain` header is trustworthy, confirming jobs relying on `WebhookVerification#shop_domain` for tenant binding must independently verify the shop against verified payload/session state.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)
