### Title
Unsanitized JSON key interpolation into jq filter strings enables jq expression injection and environment-variable disclosure - (File: `plugins/plugin-dev/skills/hook-development/scripts/validate-hook-schema.sh`)

### Summary
`validate-hook-schema.sh` builds every jq filter by directly splicing the untrusted `$event` (and derived `$i`/`$j`) values into a double-quoted jq program string (e.g. `".\"$event\"[$i].matcher // empty"`), without escaping quotes or jq metacharacters. A crafted key in a JSON object (`hooks.json`) that a victim validates (e.g. while auditing a third-party plugin via `plugin-validator` agent, which explicitly calls this script per `plugins/plugin-dev/agents/plugin-validator.md:107-108`) can break out of the intended `."key"` field-access expression and inject arbitrary jq syntax, including accessing `$ENV` (the process environment).

### Finding Description
The event key is derived from `jq -r 'keys[]' "$HOOKS_FILE"` [1](#0-0)  and is fully attacker-controlled since it is simply a top-level key of the JSON file being validated. That value is then interpolated, unescaped, into a jq filter argument at multiple sites: `hook_count` [2](#0-1) , `matcher` [3](#0-2) , `hooks` [4](#0-3) , `hook_array_count` [5](#0-4) , `hook_type` [6](#0-5) , `command` [7](#0-6) , `prompt` [8](#0-7) , and `timeout` [9](#0-8) . Since a JSON key can legitimately contain a literal `"`, an attacker key such as `foo"|$ENV.HOME|"bar` (crafted without whitespace to avoid unquoted word-splitting in `for event in $(...)` at line 43/65) inserts a real double quote into the jq program text, terminating the intended `."foo"` access and appending arbitrary jq operators (e.g. `|$ENV.HOME`), whose result is then captured into the shell variable and can be echoed back in the `❌`/`⚠️` diagnostic lines.

The claim that the *same* injected key defeats all seven sites uniformly is not fully supported by the code, however: each site appends a different jq suffix (`| length`, `.matcher // empty`, `.hooks[$j].type // empty`, etc.), and jq enforces runtime types strictly, so a payload tuned to succeed at one site (e.g. returning a string from `$ENV`) will typically cause a jq type error at a differently-shaped site (e.g. indexing that string with `[$j]`). Combined with `set -euo pipefail` [10](#0-9) , a jq failure at any one call site aborts the whole script immediately, which naturally caps how many of the seven sites can be triggered by one single crafted key in one run — contrary to the premise that all sites are simultaneously and uniformly exploitable by the same payload.

### Impact Explanation
Where reachable, this is a jq expression-injection bug, not arbitrary file read: jq's injected filter can access `$ENV` (the validating process's environment variables) and `input_filename`, so the disclosed information is limited to whatever secrets happen to be present in the environment of whoever runs `validate-hook-schema.sh` against the crafted `hooks.json` (e.g. during plugin review/vetting flows). This matches a scoped "secret disclosure" impact, but is bounded by (a) requiring the victim to actually run this specific dev-utility script against attacker-authored content, and (b) the practical difficulty of one payload cleanly compromising more than one or two of the seven call sites before the script errors out under `set -e`.

### Likelihood Explanation
Precondition: the victim must run `validate-hook-schema.sh` on an attacker-authored `hooks.json`, which is a documented step in `plugins/plugin-dev/agents/plugin-validator.md` when auditing third-party plugins. Crafting a working payload requires avoiding whitespace (due to unquoted `for event in $(...)` word-splitting) and satisfying jq's grammar/type rules for at least the first reached call site — feasible for a single site, but not guaranteed to be uniformly repeatable across all seven sites as the question frames it.

### Recommendation
Never splice untrusted JSON keys/values into jq program text. Use `jq --arg key "$event" '.[$key]...'` (or `--argjson`) to pass all untrusted values as bound jq variables instead of string-interpolating them into the filter, at every one of the cited call sites (lines 66, 70, 78, 86, 89, 105, 117, 131). Also quote the `for event in $(jq -r 'keys[]' ...)` iteration properly (e.g. iterate with `readarray`/`jq -c` and NUL-delimited output) to avoid IFS word-splitting on untrusted keys.

### Proof of Concept
Differential fuzz/unit test:
1. Generate a `hooks.json` with a single crafted top-level key, e.g. `{"a\"|$ENV.HOME|\"b": [...]}` (no whitespace).
2. Run `validate-hook-schema.sh` against it and capture stdout/stderr and exit code.
3. Assert (currently failing): the printed output for the `hook_count` computation at line 66 does not equal the real array length, and/or contains the value of `$HOME` — demonstrating jq filter injection at that site.
4. Repeat by shifting the injection payload to target each of the other six call sites (70, 78, 86, 89, 105, 117, 131) individually with tailored payloads matching each site's trailing filter shape, and assert each one independently leaks `$ENV` content or throws a jq type error under `set -e` (documenting that the script aborts rather than continuing to leak across all sites in one run).
5. Fix validation: after switching to `--arg`, repeat the same crafted-key fuzz corpus and assert no jq filter ever executes injected operators (output must reflect only the literal string value of the key/field, with an exit code that only fails on genuine schema errors).
