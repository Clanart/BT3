## Analysis

The reported bug class is deterministic-input–triggered **stack overflow via unbounded JSON nesting depth** during JSON decoding. Sei-chain has a directly analogous, transaction-reachable sink in the **`json` precompile** at `0x0000000000000000000000000000000000001003`.

### Root cause

Every method of `precompiles/json/json.go` (`extractAsBytes`, `extractAsBytesList`, `ExtractAsUint256`, `extractAsBytesFromArray`) takes attacker-controlled `bz := args[0].([]byte)` — raw bytes supplied as calldata by any EVM contract caller — and feeds it directly into `gjson.Unmarshal` (which in this file is Go's standard `encoding/json`, aliased `gjson "encoding/json"`): [1](#0-0) [2](#0-1) 

Gas for these calls is metered only linearly by *byte length* of the payload, not by nesting depth: [3](#0-2) 

Go's `encoding/json` decoder recurses once per nested `{`/`[` with no built-in depth cap; a deeply nested payload (e.g. `"["*N + "]"*N`) is cheap in bytes (2 bytes per nesting level) but expands the call stack by one frame per level. Because Go cannot recover from a real stack-overflow (`fatal error: stack overflow` is not a `panic` and bypasses `recover()`), a sufficiently deep payload crashes the entire node process, not just the transaction/goroutine.

The same unguarded pattern (`gjson.Unmarshal` on raw calldata bytes with no depth check) is repeated across every legacy version of this precompile: `precompiles/json/legacy/v552/json.go`, `v555`, `v562`, `v605`, `v606`, `v610`, `v614`, `v620`, `v630`, `v640`, `v65`, `v66`, `v67`.

### Reachability / gas budget

An EVM transaction's gas limit is only bounded by the consensus `Block.MaxGas` (e.g. `35,000,000` in the Autobahn deployment config), and there is explicitly **no block-level gas limit enforced by the EVM module beyond the per-tx limit**: [4](#0-3) 

At `GasCostPerByte = 100`, a single transaction with a max gas budget in the tens of millions can afford calldata large enough (hundreds of thousands of bytes) to encode a JSON nesting depth far beyond what triggers a Go stack overflow — all from a single, ordinary contract call to the JSON precompile, executed deterministically by **every full node/validator processing the block**.

### Title
Unbounded JSON nesting depth in the `json` precompile causes a stack-overflow crash of every node executing the block - (File: `precompiles/json/json.go`)

### Summary
The `json` precompile (address `0x...1003`) decodes attacker-controlled calldata bytes with Go's `encoding/json` via `gjson.Unmarshal`, without any limit on JSON nesting depth. This mirrors the Tink-cc `JsonKeysetReader` DoS class (CVE-2024-4420): a valid-but-deeply-nested JSON input drives the recursive decoder into a stack overflow. Unlike an ordinary panic, Go stack overflows are unrecoverable (`fatal error`), crashing the entire node process handling the transaction.

### Finding Description
`extractAsBytes`, `extractAsBytesList`, `ExtractAsUint256`, and `extractAsBytesFromArray` in `precompiles/json/json.go` all call `gjson.Unmarshal(bz, &decoded)` on the caller-supplied `bz` bytes before any depth or structural validation occurs [5](#0-4) . Gas metering charges only `GasCostPerByte * len(payload)` [6](#0-5) , so an attacker pays for bytes, not for the recursion depth those bytes create. A payload consisting of thousands of nested `[` characters costs only a few bytes per nesting level, letting an attacker cheaply reach recursion depths that exhaust the goroutine stack. Since every validator/full node deterministically re-executes the same EVM transaction during block processing, the crash is not confined to a single node — it can halt the whole network if the transaction is included in a block.

### Impact Explanation
A crash triggered inside transaction execution (as opposed to only in an RPC-only code path) affects every node that processes the block, i.e. validators and full nodes alike, causing a validator halt / consensus-wide outage — the strongest impact tier in the ruleset ("validator halt", "block delay beyond 2.5 seconds", "crash of default-configuration RPC nodes").

### Likelihood Explanation
Any account (unprivileged EOA or contract) can call the JSON precompile directly with arbitrary calldata; no special privileges, prior state, or governance action is required. The only cost is standard EVM gas for calldata and the linear `GasCostPerByte` charge, both of which are affordable at the deployed block gas limits observed in this repo (tens of millions of gas).

### Recommendation
Enforce a maximum JSON nesting depth (and/or use a depth-limited decoder, or `json.Decoder` with a custom depth-tracking wrapper) before/while unmarshalling attacker-supplied bytes in all `json` precompile implementations (current and every `precompiles/json/legacy/*` version). Reject payloads whose nesting exceeds a small bound (e.g., a few dozen levels) prior to calling `gjson.Unmarshal`, and charge gas proportional to worst-case decode cost (depth × bytes) rather than bytes alone.

### Proof of Concept
1. Deploy or use any contract able to make a `staticcall`/`call` to `0x0000000000000000000000000000000000001003` with method `extractAsBytesFromArray` (or any of the other three methods).
2. Craft calldata whose `bz` argument is `strings.Repeat("[", N) + strings.Repeat("]", N)` for N large enough to exceed Go's default goroutine stack limit (experimentally on the order of 10^5–10^6 depending on frame size), staying within the tx's affordable gas budget at `GasCostPerByte = 100`/byte.
3. Submit the transaction. During `PrecompileExecutor.Execute` → `extractAsBytesFromArray` → `gjson.Unmarshal(bz, &decoded)`, the recursive JSON decoder exhausts the stack, producing an unrecoverable `fatal error: stack overflow` that terminates the node process on every validator/full node executing that block.
