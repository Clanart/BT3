### Title
FROST nonce seed cached indefinitely and deterministically regenerated for every `sign` under a context, enabling private key share recovery via nonce reuse across retry/parallel `share` invocations — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

`SigningProtocol::preprocess_internal` persists the FROST preprocess seed in the `CachedPreprocesses` DB table keyed only by `context`, and `share_internal` rebuilds the signing machine from that same cached seed on every invocation. Nothing ever deletes the cache entry, and both `share()` and `complete()` independently call `share_internal` → `preprocess_internal` → `machine.sign(...)`. Any second `sign` under the same context with a different preprocess set or message reuses the identical secret nonces, which for Schnorr/FROST yields immediate algebraic recovery of the validator's private key share from the two published shares — a fully offline computation, directly analogous to serving verifier/KDF material to unauthorized readers.

### Finding Description

At `coordinator/src/tributary/signing_protocol.rs:123-145`, `preprocess_internal` does:

- `if CachedPreprocesses::get(self.txn, &self.context).is_none()` → generate preprocess, store `machine.cache()` XOR-masked with `Blake2s256("Cached Preprocess Encryption Key" || context || key)` (lines 123-135).
- Then unconditionally reload the same seed and call `AlgorithmSignMachine::from_cache(...)` (lines 137-145).

There is no `CachedPreprocesses::del`/`kill` anywhere — grep confirms the table is only `get`/`set` in this file. The FROST contract being violated is explicit in `crypto/frost/src/sign.rs:209-219`: "This cached preprocess MUST only be used once... After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share."

The reuse path is structural, not hypothetical:

- `DkgConfirmer::share` calls `share_internal` (line 309), which calls `preprocess_internal` (line 156) and then `machine.sign(preprocesses, msg)` (line 170).
- `DkgConfirmer::complete` calls `share_internal` **again** (line 322) to rebuild the machine, then `complete_internal`. That is a second `sign` consuming a machine rebuilt from the same seed.
- `share_internal` returns `Err(Participant)` on `FrostError::InvalidPreprocess(p) | InvalidShare(p)` (lines 177) rather than aborting the context, so a retry of `share` with a corrected/different `preprocesses` map is a designed path — and each retry re-signs with the same nonces.
- The preprocess map is attacker-influenced: `serialized_preprocesses` comes from other validators' messages and is fed to `machine.read_preprocess` (lines 162-168). The map keys are re-derived per call via `threshold_i_map_to_keys_and_musig_i_map`, so a validator who submits a malformed preprocess first (forcing `Err(p)`) and a valid one later causes two `sign` executions over different binding sets with identical nonces.

The file's own header (lines 25-54) acknowledges the hazard and defers safety to a BFT argument, while explicitly noting the check that "the commitments generated from the decided nonces are in fact its commitments on-chain" is an unimplemented **TODO** — i.e., the guard that would make reuse impossible is absent. Reuse does not require broken BFT: it only requires two executions of `share_internal` with non-identical preprocess sets or messages, which the error/retry shape permits.

### Impact Explanation

Two FROST/MuSig signature shares produced with the same nonce but different binding factors (`rho`) or challenges leak the signer's secret share linearly: `z1 - z2 = (c1·λ - c2·λ')·x_i` (plus nonce cancellation), solvable for `x_i` offline. Since this signs `set_keys_message` confirming the DKG result on Substrate (`KeyPair` for the set), recovery of a validator's MuSig key share undermines the root-of-trust signature that gates key confirmation. The attacker needs only public inputs — preprocess bytes they send — and passively observed shares; all recovery math is off-chain, mirroring the report's "unthrottled offline cracking" shape.

### Likelihood Explanation

Reachability requires a second `sign` under one context with a differing message or signing set. The code itself creates the second `sign` in `complete` and exposes an error/retry surface (`Err(Participant)` returns) that invites re-invocation; a malicious validator controls part of the preprocess map. Exploitation needs the re-executed `sign` to actually differ in commitments/message — plausible via retry after `InvalidPreprocess`, or a `removed`/`attempt` boundary where the participant set changed while `context` (`(b"DkgConfirmer", attempt)`) did not. Medium-high confidence in the reuse primitive; exploitation depends on coordinator retry behavior outside this file, which I could not fully trace within the indexed context.

### Recommendation

- Delete the `CachedPreprocesses` entry (or mark it spent) inside `share_internal`/`preprocess_internal` before returning the machine, enforcing the FROST `cache()`/`from_cache` single-use contract at the DB layer rather than by convention.
- Refuse to rebuild a `SignMachine` from a consumed cache: after `sign` succeeds or fails, overwrite the entry with a tombstone so any later `share`/`complete` under the same context errors instead of re-signing.
- Implement the acknowledged TODO: verify on-chain that the preprocess commitments being signed over match this validator's previously published commitments before emitting a share.

### Proof of Concept

Conceptual, code-derived (no runtime harness available in index):

1. Coordinator runs `DkgConfirmer::share(preprocesses_A, kp)` for attempt `a`. `preprocess_internal` stores seed `s` under context `("DkgConfirmer", a)`, `from_cache(s)` regenerates nonce commitments `D_i, E_i`, and `sign` emits share `z1 = d + e·ρ_A + c_A·λ_A·x_i`.
2. Attacker (a validator) caused step 1 to use a distinct signing set — e.g., first submitted an invalid preprocess (`Err(InvalidPreprocess)`) then valid, or `complete()` re-executes with `preprocesses_B ≠ preprocesses_A`.
3. Second `sign` with same `s` produces `z2 = d + e·ρ_B + c_B·λ_B·x_i` — identical nonce scalars `d, e` since `CachedPreprocess` determinism makes `from_cache` regenerate the same nonces (spec/FROST.md:45-62: "the entire preprocess can be derived from the RNG seed").
4. Offline: `x_i = ((z1 - z2) - e·(ρ_A - ρ_B)) / (c_A·λ_A - c_B·λ_B)`, recovering the validator's Ristretto private key share with no further interaction.
