### Title
BIP-340 signature produced over the un-negated group key when the group key has odd Y — invalid signatures / unspendable funds — (File: networks/bitcoin/src/crypto.rs)

### Summary
The Aave bug class is "a dependent value is consumed *before* the required state update is applied" (`updateInterestRates` called after the liquidity-changing `burn`). The same class appears in Serai's Bitcoin FROST algorithm: BIP-340 requires the signing key to be the even-Y lift of the x-only key, i.e. the secret must be effectively negated when the group key `A` has odd Y. In `Schnorr::sign_share` the raw (un-updated) secret share is consumed to produce `s = c·a + r`, and `verify` only corrects for the parity of the nonce point `R`, never for the parity of the group key `A`. The parity correction for the key is never applied before the secret is used.

### Finding Description
`Hram::hram` (networks/bitcoin/src/crypto.rs:59-73) computes the BIP-340 challenge over `x(R)` and `x(A)` and correctly negates `c` when `R` has odd Y (line 72), and `verify` (crypto.rs:145-149) negates `s` when `R` is odd. However, BIP-340 also mandates signing with the secret corresponding to the *even-Y* representative of the x-only public key. In `crypto/frost/src/algorithm.rs:201-211`, `sign_share` computes `SchnorrSignature::<C>::sign(params.secret_share(), nonce, c)`, which yields `s = c·a + r` (crypto/schnorr/src/lib.rs:79-83). When `A` has odd Y, a BIP-340 verifier checks `s·G == R_even + c·A_even` where `A_even = -A`, i.e. it expects `s = r ± c·(-a)`. Serai emits `s = r + c·a`, which fails verification. For a threshold wallet whose (possibly TapTweak-offset) group key lands on odd Y — which occurs for ~50% of keys — every signature produced is invalid on-chain.

### Impact Explanation
Any Bitcoin output controlled by a group key with odd Y cannot be spent via this signing path: the threshold protocol completes, `verify` returns a 64-byte signature that looks well-formed, and the transaction is then rejected by the network. Funds become unspendable through this code path until a corrected signer is used, and any unprivileged party can cause a message (e.g. a spend they request) to be "signed" into an invalid signature. Medium-to-High severity correctness flaw in signing math.

### Likelihood Explanation
The parity of the (tweaked) group key is effectively a coin flip per key generation/tweak, so roughly half of all threshold Bitcoin keys hit this condition. No adversarial input is required to trigger it; any signature request against an odd-Y key deterministically produces an invalid signature. (Caveat: I did not inspect the wallet code that applies TapTweak offsets; if an external layer normalizes key parity before FROST sees it, the trigger requires that normalization to be absent or ineffective — the FROST algorithm itself contains no such correction.)

### Recommendation
Apply the BIP-340 key-parity update *before* consuming the secret, analogously to the nonce fix: in `sign_share` (or via the `ThresholdView`/`Hram` plumbing), detect `needs_negation(&params.group_key())` and negate the secret share / sign `r - c·a` when the group key is odd. Equivalently, the challenge-side trick already used for `R` could be extended so the contribution `c·a` is flipped together with the `s`-negation path in `verify`. Ensure `verify_share` reconstructs statements consistent with the negated-key equation.
