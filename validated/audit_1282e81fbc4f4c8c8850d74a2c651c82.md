### Title
Swallowed conversion error in `ConvertCoinToERC20FromPacket` permanently strands escrowed native coins in the `x/erc20` module account on IBC ack-error/timeout - ([File: x/erc20/keeper/ibc_callbacks.go])

### Summary
`ConvertCoinToERC20FromPacket` (invoked from `OnAcknowledgementPacket` on an error ack and unconditionally from `OnTimeoutPacket`) calls `k.ConvertCoinNativeERC20` to auto-convert refunded IBC coins back into their native-ERC20 representation. If that conversion fails partway through, the error is caught, an event is emitted, and `nil` is returned instead of propagating the error [1](#0-0) . Because the failure is swallowed at this layer rather than allowed to bubble up and abort the enclosing IBC packet-processing transaction, any state mutation performed by `ConvertCoinNativeERC20` before the failure point is committed rather than rolled back.

### Finding Description
`ConvertCoinNativeERC20` performs, in order: (1) escrow the sender's native coins into the `x/erc20` module account via `SendCoinsFromAccountToModule`, (2) call the ERC20 contract's `transfer` to unescrow/deliver ERC20 tokens to the receiver, (3) verify the balance delta, (4) burn the escrowed coins [2](#0-1) . Step (1) is a real, committed state mutation before step (2) is attempted.

If step (2), (3), or the `BurnCoins` step fails for any reason (self-destructed/broken ERC20 contract, reverted `transfer`, balance-invariance mismatch, EVM call error, etc.), `ConvertCoinNativeERC20` returns a non-nil error. Its caller, `ConvertCoinToERC20FromPacket`, catches this error, emits a `types.EventTypeFailedConvertERC20` event and telemetry counter, and then explicitly `return nil` [1](#0-0) . The doc-comment even states the intended behavior is "the user receives the corresponding bank token from the TokenPair instead" [3](#0-2)  — but this is only true if the coins were never escrowed. Since the escrow step already succeeded and committed before the failure, returning `nil` here does **not** undo that escrow. There is no `ctx.CacheContext()`/`branchService` wrapping around the `ConvertCoinNativeERC20` call in this IBC callback path to make the escrow-then-mint sequence atomic (unlike, e.g., the direct `MsgConvertCoin`/`MsgConvertERC20` flows, where the whole SDK message handler failing reverts the entire transaction). Because `OnAcknowledgementPacket`/`OnTimeoutPacket` swallow the error and return `nil`, the outer IBC packet-handling transaction is treated as fully successful and commits, permanently leaving the user's coins locked in the module account with no ERC20 tokens minted to compensate.

This is the direct structural analog of the M-09 pattern: one code path (successful branch / Uniswap-liquidity-found branch) is asymmetric with another path that should have equivalent handling but instead short-circuits and discards useful/necessary information — here, the "recoverable failure" branch discards the fact that funds were already moved, silently accepting an inconsistent intermediate state as final.

### Impact Explanation
This breaks the core IBC-refund invariant: on an IBC send failure (error-ack or timeout), the user is supposed to be made whole by receiving back either the native coin or its ERC20 equivalent. Instead, the user's native coin balance is debited (escrowed into the `x/erc20` module account) while the ERC20 mint/unescrow that was supposed to compensate them never happens, and no error is surfaced to trigger a rollback. This is a permanent freezing/loss of user funds — an unprivileged user who owns a `TokenPair`-registered native-ERC20 asset and whose outbound IBC transfer times out or is nacked can have their refunded coins captured by the module account irrecoverably, satisfying the Critical impact bar for "permanent freezing, locking, theft, or unauthorized extraction of user funds... escrowed assets."

### Likelihood Explanation
Triggering requires only causing `ConvertCoinNativeERC20`'s EVM leg to fail after the bank escrow step, e.g., by having the native-ERC20 contract behave adversarially (revert on `transfer`, return `false`, or emit an unexpected `Approval` event that breaks invariance checks) or by having a receiver/token-pair state such that the follow-up `MintingEnabled`/EVM call reverts. Since `TokenPair` registration for ERC20 contracts is permissionless (`RegisterERC20`) [4](#0-3) , an attacker can register their own malicious ERC20 contract as a native-ERC20 pair, then send an IBC transfer of that pair's coin and force the destination/timeout condition, guaranteeing the vulnerable code path executes with a contract they fully control to force the desired mid-flow failure. This makes the bug practically reachable by an unprivileged user without relying on validator or relayer misbehavior.

### Recommendation
Do not swallow the error from `ConvertCoinNativeERC20` inside `ConvertCoinToERC20FromPacket`. Either:
1. Execute `ConvertCoinNativeERC20` within an isolated `ctx.CacheContext()` (or equivalent branch mechanism) and only write its changes back to the parent context if it succeeds, discarding the branch (including the escrow) on failure so the user's coin balance is unaffected; or
2. Reorder `ConvertCoinNativeERC20` so the ERC20 transfer/verification happens before the bank escrow/mint step is committed, ensuring failure occurs before any state mutation; or
3. If the intended design is "best-effort" reconversion, at minimum guarantee that failure paths cannot leave coins in the module account without a corresponding ERC20 credit — e.g., refund the escrowed coins back to the sender before returning `nil` on failure.

### Proof of Concept
1. Attacker permissionlessly registers a malicious ERC20 contract as a `TokenPair` via `MsgRegisterERC20` (`registerERC20`) [5](#0-4) , with a `transfer` function that reverts (or returns `false`) whenever called from the erc20 module address.
2. Attacker holds native coins of this pair's denom and initiates an IBC transfer of that denom to another chain, then forces the packet to fail (e.g., time it out, or coordinate on the receiving chain to nack).
3. On the sending chain, the IBC transfer module refunds the coin to the attacker's account, then invokes `OnTimeoutPacket` → `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20` [6](#0-5) .
4. `SendCoinsFromAccountToModule` escrows the coin from attacker to the `x/erc20` module account (committed) [7](#0-6) ; the subsequent `CallEVM(... "transfer" ...)` reverts due to the malicious contract, causing `ConvertCoinNativeERC20` to return an error.
5. `ConvertCoinToERC20FromPacket` catches this error, emits a failure event, and `return nil` [1](#0-0) , so the enclosing transaction commits successfully — the attacker's coins remain stuck in the `x/erc20` module account with neither the original coin nor the ERC20 token in their wallet.

*Note: I was not able to fully verify from the indexed excerpts whether some other layer above `OnTimeoutPacket`/`OnAcknowledgementPacket` (e.g., IBC core packet processing, or a `CacheContext` wrapper in `x/ibc/callbacks/keeper/keeper.go`) independently branches/reverts state per-callback; the grep hit in that file could not be inspected in this session due to iteration limits. If such a wrapper exists and reverts only the erc20-module's own state changes on error while still returning success to IBC core, the impact would be unchanged (coins still stuck); if it fully aborts the whole transaction on any non-nil return from these hooks, the swallowed `nil` here is precisely what defeats that safety net. Confirming the exact call chain in `x/ibc/callbacks/keeper/keeper.go` would strengthen this finding and is recommended as a follow-up with full repository access.*

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)
}

// ConvertCoinToERC20FromPacket converts the IBC coin to ERC20 after refunding the sender
// This function is only executed when IBC timeout or an Error ACK happens.
func (k Keeper) ConvertCoinToERC20FromPacket(ctx sdk.Context, data transfertypes.FungibleTokenPacketData) error {
	// Sender is local (source) chain address; accept local bech32 or 0x-hex
	senderBz, err := k.addrCodec.StringToBytes(data.Sender)
	if err != nil {
		return err
	}
	sender := sdk.AccAddress(senderBz)

	pairID := k.GetTokenPairID(ctx, data.Denom)
	pair, found := k.GetTokenPair(ctx, pairID)
	if !found {
		// no-op, token pair is not registered
		return nil
	}

	coin := ibc.GetSentCoin(data.Denom, data.Amount)

	switch {

	// Case 1. if pair is native coin -> no-op
	case pair.IsNativeCoin():
		// no-op, received coin is a  native coin
		return nil

	// Case 2. if pair is native ERC20 -> unescrow
	case pair.IsNativeERC20():
		// use a zero gas config to avoid extra costs for the relayers
		ctx = ctx.
			WithKVGasConfig(storetypes.GasConfig{}).
			WithTransientKVGasConfig(storetypes.GasConfig{})

		params := k.GetParams(ctx)
		if !params.EnableErc20 || !k.IsDenomRegistered(ctx, coin.Denom) {
			// no-op, ERC20s are disabled or the denom is not registered
			return nil
		}

		// assume that all module accounts on Cosmos EVM need to have their tokens in the
		// IBC representation as opposed to ERC20
		senderAcc := k.accountKeeper.GetAccount(ctx, sender)
		if types.IsModuleAccount(senderAcc) {
			return nil
		}

		// Convert from Coin to ERC20
		if err := k.ConvertCoinNativeERC20(ctx, pair, coin.Amount, common.BytesToAddress(sender), sender); err != nil {
			// We want to record only the failed attempt to reconvert the coins during IBC.
			defer func() {
				telemetry.IncrCounter(1, types.ModuleName, "ibc", "error", "total")
			}()
			ctx.EventManager().EmitEvents(
				sdk.Events{
					sdk.NewEvent(
						types.EventTypeFailedConvertERC20,
						sdk.NewAttribute(types.AttributeCoinSourceChannel, pair.Denom),
						sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
						sdk.NewAttribute("error", err.Error()),
					),
				},
			)
			return nil
		}

// ConvertCoinNativeERC20 handles the coin conversion for a native ERC20 token
// pair:
//   - escrow Coins on module account
//   - unescrow Tokens that have been previously escrowed with ConvertERC20 and send to receiver
//   - burn escrowed Coins
//   - check if token balance increased by amount
//   - check for unexpected `Approval` event in logs
func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}

	// Burn escrowed Coins
	err = k.bankKeeper.BurnCoins(ctx, types.ModuleName, coins)
	if err != nil {
		return sdkerrors.Wrap(err, "failed to burn coins")
	}

	return nil
}

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

		ctx.EventManager().EmitEvent(
			sdk.NewEvent(
				types.EventTypeRegisterERC20,
				sdk.NewAttribute(types.AttributeKeyCosmosCoin, pair.Denom),
				sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
			),
		)
	}

	return &types.MsgRegisterERC20Response{}, nil
}

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
