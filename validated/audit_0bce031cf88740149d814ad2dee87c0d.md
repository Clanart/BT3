### Title
Missing `chain_id` in `CLEMENTINE_EIP712_DOMAIN` Enables Cross-Network Replay of Aggregator Withdrawal Authorization Signatures - (`core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

The `CLEMENTINE_EIP712_DOMAIN` used to authenticate aggregator-signed withdrawal authorization messages (`OptimisticPayoutMessage` and `OperatorWithdrawalMessage`) is defined without a `chain_id`, `verifying_contract`, or `salt`. This means the EIP-712 domain separator is identical across every Citrea network deployment. A valid aggregator signature produced for one Citrea network can be replayed verbatim on any other Citrea network where the same aggregator key is in use and the same withdrawal parameters are present, bypassing the authorization gate that guards optimistic payout signing and operator withdrawal execution.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is declared as a static constant:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

No `chain_id`, `verifying_contract`, or `salt` field is present. The EIP-712 domain separator is therefore:

```
keccak256(typeHash || keccak256("ClementineVerification") || keccak256("1"))
```

This value is a compile-time constant that is identical on every Citrea network (regtest, testnet4, mainnet). The full EIP-712 signing hash fed to `recover_address_from_prehash` is:

```
keccak256(0x1901 || CLEMENTINE_EIP712_DOMAIN_SEPARATOR || struct_hash(message))
``` [2](#0-1) 

Because the domain separator carries no network identity, any signature over the same `(withdrawal_id, input_signature, input_outpoint_txid, input_outpoint_vout, output_script_pubkey, output_amount)` tuple is accepted on every Citrea deployment that shares the same aggregator key.

This domain is consumed in two production paths:

1. **Verifier optimistic-payout signing** (`sign_optimistic_payout` in `core/src/verifier.rs`): the verifier checks the recovered address against `config.aggregator_verification_address` before contributing its MuSig2 partial signature to the N-of-N optimistic payout transaction that spends the bridge vault UTXO. [3](#0-2) 

2. **Operator withdrawal execution** (`withdraw` RPC in `core/src/rpc/operator.rs`): the operator checks the recovered address before executing the payout transaction. [4](#0-3) 

---

### Impact Explanation

If the same aggregator ECDSA key is used across two Citrea deployments (e.g., testnet4 and regtest, both of which use `citrea_chain_id = 5655` per the shipped configuration), and the same `(withdrawal_id, input_outpoint, output_script_pubkey, output_amount)` tuple is present on both networks, a signature produced for one network is accepted on the other without any additional check. [5](#0-4) [6](#0-5) 

A successful replay on the verifier path causes every participating verifier to contribute a partial MuSig2 signature, completing the N-of-N optimistic payout signature and spending the bridge vault UTXO for a withdrawal the aggregator never explicitly authorized on that network. On the operator path it causes the operator to execute a payout transaction from their own funds, triggering a reimbursement claim against the bridge vault.

The attack is bounded by the requirement that `input_outpoint` (a Bitcoin UTXO) must be registered as a valid withdrawal on the target network. Because mainnet and testnet4 are distinct Bitcoin networks their UTXOs cannot overlap, which limits cross-network replay to deployments that share the same underlying Bitcoin network. The testnet4/regtest pair (same `citrea_chain_id = 5655`, potentially same aggregator key) is the most immediately reachable scenario.

---

### Likelihood Explanation

- Clementine is explicitly designed for multi-network deployment (regtest, testnet4, mainnet).
- The shipped default and testnet4 configs both set `citrea_chain_id = 5655`, making the domain separator byte-for-byte identical between those two environments.
- The `aggregator_verification_address` field is `Option<Address>` and is silently skipped when `None`, meaning deployments that omit it receive no protection at all from this mechanism. [7](#0-6) 

---

### Recommendation

Bind the EIP-712 domain to the Citrea chain ID at construction time instead of using a static constant:

```rust
pub fn clementine_eip712_domain(citrea_chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: citrea_chain_id,
    }
}
```

Pass `config.citrea_chain_id as u64` wherever `CLEMENTINE_EIP712_DOMAIN` is currently used in `recover_address_from_ecdsa_signature`, `sign_optimistic_payout`, and the operator `withdraw` RPC. This ensures a signature produced for one Citrea chain ID is cryptographically invalid on any other.

Additionally, make `aggregator_verification_address` a required field rather than `Option` so that the authorization gate cannot be silently disabled by omitting the config key.

---

### Proof of Concept

1. Clementine is deployed on testnet4 Bitcoin + Citrea testnet4 (`citrea_chain_id = 5655`) and on regtest Bitcoin + Citrea regtest (`citrea_chain_id = 5655`). The same aggregator ECDSA key is used for both.
2. A user makes a deposit on regtest. The bridge registers `withdrawal_id = 0` with `input_outpoint = T` and `output_amount = A`.
3. The aggregator signs an `OptimisticPayoutMessage` for `(withdrawal_id=0, input_outpoint=T, output_script_pubkey=S, output_amount=A)` on regtest. The EIP-712 hash is `H = keccak256(0x1901 || D || struct_hash)` where `D` is the chain-ID-free domain separator.
4. The same `(withdrawal_id=0, input_outpoint=T, output_script_pubkey=S, output_amount=A)` tuple exists on testnet4 (same sequential counter, same UTXO registered by the bridge contract).
5. The attacker submits the regtest signature to the testnet4 verifier's `optimistic_payout_sign` RPC. Because `CLEMENTINE_EIP712_DOMAIN` is identical on both networks, `recover_address_from_prehash` returns the same aggregator address. [8](#0-7) 

6. The verifier's address check passes (`address_from_sig == address_in_config`), and it contributes its partial MuSig2 signature to the optimistic payout transaction on testnet4, spending the bridge vault UTXO without the aggregator having explicitly authorized that action on testnet4.

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
