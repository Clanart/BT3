## Finding

### Title
Stale manual conflict resolutions are silently carried over into unrelated rebase/merge operations, corrupting committed content - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState` in [1](#0-0)  reuses the previous conflict's `manualResolutions` map whenever `prevConflictState !== null`, without verifying that the new conflict state actually belongs to the same rebase/merge session. The only check that detects "this is actually a different operation" (branch-name/tip comparison in `performEffectsForRebaseStateChange` / `performEffectsForMergeStateChange`) is used exclusively to increment a telemetry counter, not to gate reuse of the stale resolutions map — structurally identical to the Sherlock bug where a counter reaching a boundary condition was checked but the derived cumulative value was still carried forward unconditionally.

### Finding Description
`getConflictState` builds a new `ConflictState` (merge/rebase/cherry-pick) purely from on-disk git status flags (`REBASE_HEAD`, `MERGE_HEAD`, etc.) but is handed whatever `manualResolutions` map was computed by the caller: [2](#0-1) 

`updateConflictState` computes that map like this: [3](#0-2) 

The only place that distinguishes "same operation continuing" from "a new, unrelated operation of the same kind started" is `performEffectsForRebaseStateChange`, which compares `targetBranch`/tip and, if they differ, concludes the previous rebase "must have been aborted" — but this conclusion is used only for a stats increment, never to reset `manualResolutions`: [4](#0-3) [5](#0-4) 

Because both the old and new state have `kind === 'rebase'` (or `'merge'`), the `isRebaseConflictState`/`isMergeConflictState` branch is taken regardless of whether the underlying operation is actually the same one, and the stale `manualResolutions` map from the previous, unrelated conflict is returned as-is in the new `ConflictState`.

This resolutions map is not cosmetic — it is later consumed to decide what actually gets staged and committed. `continueRebase` iterates it and stages the chosen side for each path without re-confirming the choice is still valid for the current conflict: [6](#0-5) 

### Impact Explanation
If a user aborts (or a rebase/merge is otherwise superseded — e.g. after a `git pull --rebase` is interrupted by a subsequent fetch that changes the target ref, or the user manually resolved conflicts, aborted, and started a new rebase/merge against a different branch/tip) while having recorded manual resolutions for file paths, and a *new* rebase/merge of the same kind later conflicts on a file with the *same path*, Desktop will silently reuse the old "ours"/"theirs" choice for that path in the new operation. The user never made that choice for the new operation's actual content, yet the UI will show the file as already resolved, and `continueRebase`/commit will silently stage and commit the stale side. This is a silent corruption of what the user commits/pushes: the committed/pushed content can differ from what the user actually intended or reviewed, with no warning presented (the conflicts dialog only re-renders based on `getResolvedFiles`/`getConflictedFiles`, which trust the persisted `manualResolutions` map as ground truth: [7](#0-6) ).

Because the trigger is purely git status transitions (REBASE_HEAD/MERGE_HEAD presence, branch/tip values) driven by repository content, an attacker who controls a remote (e.g., force-pushing/rewriting the ref being rebased onto between the user's fetch attempts, or crafting commit history so the same file paths repeatedly conflict) can increase the likelihood that a user's earlier conflict choice on a given path gets silently reapplied to different, attacker-influenced content in a later, unrelated rebase against that same path.

### Likelihood Explanation
This requires a specific but realistic sequence: an in-progress merge/rebase gets superseded by another of the same kind without going through a `conflictState === null` transition (or with the resolutions surviving the intermediate transition since the map is always inherited from `prevConflictState`), and both operations conflict on the same file path. Multi-commit-operation "pull with rebase", repeated rebase attempts against a moving remote branch, or `Amend`/`Continue`/`Abort` cycles on the same file are common enough real-world flows that this is not a purely theoretical edge case, though it is less immediately obvious than a single-request exploit.

### Recommendation
`updateConflictState` should only carry forward `manualResolutions` when the new conflict state is confirmed to be a continuation of the exact same operation instance (e.g., same `targetBranch` **and** same `originalBranchTip`/`baseBranchTip` for rebase, same `currentBranch` **and** same starting tip for merge), not merely the same `kind`. When `performEffectsForRebaseStateChange`/`performEffectsForMergeStateChange` detect the branch/tip changed (i.e., what they currently interpret as "aborted"), `updateConflictState` should discard the stale resolutions map and start the new conflict state with an empty one, exactly the same way it already does when `prevConflictState === null`.

### Proof of Concept
1. Start a rebase of `feature` onto `origin/main` (target `origin/main`, tip `T1`). Conflict occurs on `config.yml`; user manually resolves it by choosing "ours" — `conflictState.manualResolutions = { 'config.yml' -> ours }`.
2. Abort the rebase (or let it be effectively superseded, e.g. user checks out a different starting point and starts a new rebase of `feature` onto `origin/develop`, tip `T2`, different `targetBranch`).
3. A new rebase begins; git status again reports `REBASE_HEAD` present with `targetBranch = 'origin/develop'`. `updateConflictState` sees `prevConflictState.kind === 'rebase'` and `newConflictState.kind === 'rebase'`, so it takes the `isRebaseConflictState` branch; `performEffectsForRebaseStateChange` notices `targetBranch` changed and increments `rebaseAbortedAfterConflictsCount`, but the returned `ConflictState` still carries `manualResolutions = { 'config.yml' -> ours }` from step 1.
4. This second rebase also conflicts on `config.yml` (different content, since it's against `origin/develop`). Desktop's UI immediately shows `config.yml` as resolved (no user action taken this session) because `getResolvedFiles`/`getConflictedFiles` trust the stale map.
5. User clicks "Continue rebase" → `continueRebase` stages `config.yml` using the old "ours" resolution against the new conflict's actual content, and commits it — silently committing/pushing content the user never reviewed or chose for this operation. [8](#0-7) [9](#0-8)

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

function performEffectsForRebaseStateChange(
  prevConflictState: RebaseConflictState | null,
  newConflictState: RebaseConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
) {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.targetBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.targetBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the rebase must have been aborted
  if (branchNameChanged) {
    statsStore.increment('rebaseAbortedAfterConflictsCount')
    return
  }

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  if (
    (prevConflictState == null || isRebaseConflictState(prevConflictState)) &&
    (newConflictState == null || isRebaseConflictState(newConflictState))
  ) {
    performEffectsForRebaseStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  // Otherwise we transitioned from a merge conflict to a rebase conflict or
  // vice versa, and we should avoid any side effects here

  return newConflictState
}

/** Filter working directory changes for resolved files  */
export function getResolvedFiles(
  status: WorkingDirectoryStatus,
  manualResolutions: Map<string, ManualConflictResolution>
) {
  return status.files.filter(
    f =>
      isConflictedFileStatus(f.status) &&
      !hasUnresolvedConflicts(f.status, manualResolutions.get(f.path))
  )
}

/** Filter working directory changes for conflicted files  */
export function getConflictedFiles(
  status: WorkingDirectoryStatus,
  manualResolutions: Map<string, ManualConflictResolution>
) {
  return status.files.filter(
    f =>
      isConflictedFileStatus(f.status) &&
      hasUnresolvedConflicts(f.status, manualResolutions.get(f.path))
  )
}
