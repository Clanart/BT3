### Title
Deterministic cached FROST preprocess is re-signed across multiple `sign()` calls in the same context, enabling nonce reuse and validator key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The libvips CVE is a NULL-pointer dereference caused by a race between a failed lazy load and worker threads — i.e., a presumed-initialized resource being used again under conditions the loader never re-validated. The Serai analog lives in `SigningProtocol::preprocess_internal` (`coordinator/src/tributary/signing_protocol.rs:100-148`): the FROST preprocess seed is cached in the DB keyed only by `context` and is *reused* on every call, never invalidated after use. `share_internal` calls `preprocess_internal` to rebuild a fresh `AlgorithmSignMachine` from that same seed and then calls `machine.sign(preprocesses, msg)` — so `sign()` is executed multiple times over identical deterministic nonces (`CachedPreprocess` → `ChaCha20Rng::from_seed` → `Commitments::new` in `crypto/frost/src/sign.rs:121-144`).

### Finding Description
- `CachedPreprocesses` is keyed solely by `self.context` (for `DkgConfirmer`, `(b"DkgConfirmer", attempt)`, `signing_protocol.rs:275`). Once set at `signing_protocol.rs:134`, it is never deleted or rotated within that attempt.
- `share_internal` (`signing_protocol.rs:150-181`) rebuilds the machine via `AlgorithmSignMachine::from_cache`, which re-derives the same nonces from the same seed (`crypto/frost/src/sign.rs:127-141`, `268-274`).
- `DkgConfirmer::complete` (`signing_protocol.rs:312-327`) calls `share_internal` *again* — a second `sign()` over the same nonces — using whatever `preprocesses` map is supplied at completion time, which is built from a possibly different participant subset via `threshold_i_map_to_keys_and_musig_i_map` (`signing_protocol.rs:208-250`).
- In FROST, a share is `s_i = d_i + b_i·e_i + λ_i·σ_i·c` where `b_i` is the binding factor derived from the preprocess set. If `share()` and `complete()` (or two `share()`-equivalent invocations) sign with the same `(d_i, e_i)` but different `b_i`/participant sets, `s1 − s2 = e_i(b1 − b2)` recovers `e_i`, then `d_i`, then `σ_i = (s − d_i − b_i e_i)/(λ_i c)` recovers the validator's MuSig secret share — the root-of-trust key.
- The file's own header (`signing_protocol.rs:25-54`) acknowledges exactly this hazard ("it is explicitly unsafe to reuse nonces... would have to be distinct and sign would have to be called again") and relies on BFT ordering plus full rebuilds for safety — while noting the on-chain-commitment consistency check is still a TODO (line 51). Re-execution after a partial rebuild, or a logically distinct second accumulation for the same attempt, bypasses that assumption.

### Impact Explanation
Reuse of deterministic nonces under two different binding-factor/message combinations yields the validator's Ristretto secret share, compromising the MuSig root key used to confirm DKG results on Substrate — full key-share recovery from publicly broadcast signature shares. High/Critical severity.

### Likelihood Explanation
Requires `sign()` to run twice under the same `context` with distinct `preprocesses`/`msg` inputs. `share` and `complete` already call `share_internal` separately; whether their inputs can diverge (different accumulated participant subsets, or re-execution after restart where the DB persists but message ordering differs) is the remaining condition — I did not fully confirm the `handle.rs` call sites before the iteration limit. The documented TODO and the reliance on unverified invariants suggest the path is not adequately defended.

### Recommendation
Consume (delete) `CachedPreprocesses` entries on first use of `sign()`, and/or bind the cached entry to a hash of the preprocess set and message, refusing to sign if they differ. Implement the documented TODO of verifying on-chain preprocess commitments match the presumed preprocess before publishing shares.

### Proof of Concept
Conceptual: trigger `DkgConfirmer::share` and then `DkgConfirmer::complete` (or a restarted `share`) within one `attempt` such that the preprocess maps differ by at least one participant. Observe the two published `[u8; 32]` shares; compute `e = (s1 − s2)/(b1 − b2)`, `d = s1 − b1·e − λ·σ·c` rearranged to solve `σ`, recovering the validator's MuSig private share.   As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from
  the nonces being context-bound under a BFT protocol. The flow is as follows:

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
