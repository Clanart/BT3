### Title
Payout OP_RETURN operator-attribution byte is unsigned under `SinglePlusAnyoneCanPay`, allowing a replace-by-fee substitution that mis-credits reimbursement to an uninvolved operator - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` signs only input 0 with a user signature using `TapSighashType::SinglePlusAnyoneCanPay`, which cryptographically commits only to input 0 and the output at the same index (output 0, the user payout). Output 2 (the OP_RETURN carrying the fronting operator's xonly pubkey) and any additional funding inputs are completely unsigned, so anyone who observes the broadcast RBF-enabled payout transaction can replace it with a variant that keeps output 0 identical (satisfying the signature) but substitutes an arbitrary OP_RETURN value, causing `update_finalized_payouts` to attribute the withdrawal to a party who never funded it.

### Finding Description
The broken binding: `withdrawals.payout_payer_operator_xonly_pk` (as set in `update_finalized_payouts`) SHOULD equal "the xonly_pk of the operator whose own BTC funded output 0 of the confirmed payout tx." Before the exploit these are equal by construction (the operator that calls `withdraw` embeds its own key). After the exploit they diverge: the DB records an arbitrary attacker-chosen key while the real spender of the extra funding inputs is someone else.

Code path:
- `create_payout_txhandler` builds output 0 (user payout, sighash-committed), output 1 (anchor), output 2 (OP_RETURN with `operator_xonly_pk`, not commited by the signature) and signs only input 0 with `SpendPath::KeySpend` [1](#0-0) .
- `calculate_pubkey_spend_sighash` shows that for `SinglePlusAnyoneCanPay` (and the other `*PlusAnyoneCanPay` variants) only the single relevant prevout is committed (`Prevouts::One`), meaning all other inputs/outputs are unconstrained by the signature [2](#0-1) .
- `Operator::withdraw` verifies the schnorr signature against this sighash and then funds/broadcasts the tx via `fund_raw_transaction`, i.e. RBF-eligible [3](#0-2) [4](#0-3) .
- The tx-sender queue explicitly routes `TransactionType::Payout` through `FeePayingType::RBF` [5](#0-4) , confirming the broadcast payout tx is replaceable in the mempool by a higher-fee competing spend of the same input 0.
- `update_finalized_payouts` (run by every verifier/operator syncing Citrea/Bitcoin state) attributes the payout purely by parsing the OP_RETURN of whichever transaction actually confirms, with no check tying it to who funded the extra inputs [6](#0-5) , and writes it via `update_payout_txs_and_payer_operator_xonly_pk` [7](#0-6) .
- `get_first_unhandled_payout_by_operator_xonly_pk` and `PayoutCheckerTask` then let the operator named in the (attacker-controlled) OP_RETURN autonomously pick up and kick off reimbursement for this idx [8](#0-7) [9](#0-8) .
- `is_kickoff_malicious` only checks self-consistency between the OP_RETURN-derived operator and the kickoff's declared operator — it does not check who actually funded the payout tx's non-committed inputs — so it cannot detect the substitution [10](#0-9) .
- The true fronting operator's own broadcast (same input 0, its own OP_RETURN) is now a conflicting double-spend and is orphaned/rejected once the substituted transaction confirms; `validate_payer_is_operator` will subsequently reject that operator forever for this `deposit_id` because the DB's payer key no longer matches its own key [11](#0-10) .

Exploit flow: attacker observes operator A's broadcast payout tx (mempool, RBF-enabled), copies input 0's witness/signature unchanged, keeps output 0 byte-identical (mandatory, since it's sighash-committed), adds its own funding input(s) sufficient to cover output 0's value plus a higher fee, and replaces output 2's OP_RETURN with victim operator B's xonly_pk (read from `OperatorParams`/deposit registry). Broadcasts with a higher fee so it wins the RBF race and confirms before A's transaction. `update_finalized_payouts` then durably attributes the payout to B.

### Impact Explanation
Two Critical-tier consequences occur simultaneously and match the listed severity categories:
- Operator B is credited (via `payout_payer_operator_xonly_pk` and `get_first_unhandled_payout_by_operator_xonly_pk`) as the fronting operator for a withdrawal it never funded, and B's automation (`PayoutCheckerTask`) will autonomously drive `handle_finalized_payout`/kickoff to claim reimbursement it did not earn — "an operator reimbursed for a payout it never funded."
- Operator A, who actually attempted to front the withdrawal (or whose tx was displaced), is permanently blocked from `validate_payer_is_operator` success for that `deposit_id`, since the DB payer key will never again equal A's key for that idx — "an honest operator permanently unable to be reimbursed."

This is repeatable for every future withdrawal any operator fronts via `Operator::withdraw`, since the root cause is structural (sighash scope does not cover the OP_RETURN attribution byte or extra inputs) and not tied to a specific deposit or operator set.

### Likelihood Explanation
The attacker needs no privileged role: only the ability to observe the public Bitcoin mempool, hold Bitcoin funds sufficient to cover the payout output amount plus a competitive fee, and craft a standard taproot key-spend transaction with a substituted OP_RETURN — all explicitly within the stated unprivileged attacker capabilities (broadcast transactions, choose scripts/OP_RETURN/witness, pay fees). No verifier, operator, or aggregator compromise, no majority hashrate, and no TLS interception are needed; this is a pure mempool replacement using a signature the protocol itself designed to be malleable outside output 0. The requirement to front the full withdrawal amount is a cost, but it does not need to come from the attacker's own capital gain motive — it is sufficient griefing capital to permanently corrupt one operator's reimbursement path and gift funds to an arbitrary uninvolved operator, which is a real integrity violation regardless of the attacker's own profit.

### Recommendation
Bind the operator attribution cryptographically to the signature scope. Options:
- Require the withdrawer's signature to use a sighash type that commits to all outputs (e.g. `Default`/`All`) so the OP_RETURN (and ideally the full output set) cannot be altered without invalidating the user's signature, and/or
- Require the fronting operator itself to co-sign (or additionally commit via a covenant/output) the OP_RETURN payload, so attribution cannot be substituted by any third party who merely reuses input 0's witness.
- As a defense in depth, when marking a payout's attribution in `update_finalized_payouts`, cross check that the additional payout tx inputs are consistent with the claimed operator (e.g., trace funding back to a known operator wallet) rather than trusting the OP_RETURN bytes alone.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
