## Finding: Stale diff cache reused across working-directory refreshes based on file ID equality, not content identity

### Title
Stale diff cache reused after external file content change due to ID-only comparison - (File: app/src/lib/stores/updates/changes-state.ts)

### Summary
`updateChangedFiles` in `app/src/lib/stores/updates/changes-state.ts` decides whether to keep a previously-loaded diff (`state.selection.diff`) when a fresh `git status` result comes in. It does this purely by comparing the *file ID* (effectively the path) of the currently selected file before and after the refresh — it never checks whether the underlying file content/blob actually changed: [1](#0-0) 

This mirrors the structural pattern in the seed report: a value (`bank.totalLend` there, a cached diff here) is only invalidated on some state-transition paths but not all of them, so it can persist as stale/incorrect after an event that should have refreshed it.

### Finding Description
GitHub Desktop periodically re-runs `git status` in the background (and after fetch/pull/checkout) and merges the result into `IChangesState` via `updateChangedFiles`. When the same file remains the sole selection across two consecutive status refreshes, the function reuses `state.selection.diff` as-is: [2](#0-1) 

The comparison key is `WorkingDirectoryFileChange.id`, which is derived from the file path, not from any content hash, mtime, or git object ID. If the file's on-disk contents change between two status polls (e.g., a build tool, git hook, or any process writing to a tracked file in the repository while Desktop has that file selected in the Changes view with a partial line selection), the diff shown to the user is not recomputed — the UI keeps rendering the old hunks/lines while the new working-tree content is different from what's displayed.

Since GitHub Desktop supports partial/line-level staging (`DiffSelectionType.Partial`, `WorkingDirectoryFileChange.selection`), and `createCommit`/`stageFiles` apply the patch built from the (stale) diff's line selection via `applyPatchToIndex`: [3](#0-2) 

a user who reviews the (stale, cached) diff and commits "the selected lines" can end up committing content that does not match what they visually reviewed, because the actual working tree content moved on while only the cached hunk offsets/line text are shown.

### Impact Explanation
This falls into "silent corruption of what the user commits or pushes": the user visually approves a diff, but the committed patch can diverge from the currently-reviewed content because the cache invalidation only checks file identity (path), never content identity. In a supply-chain-adjacent scenario (e.g., a compromised pre-commit/post-checkout hook, a build step, or any tool that rewrites a tracked file while Desktop's background status poller is running), this could let a maliciously-timed content change slip into a commit under a diff the user never actually reviewed.

### Likelihood Explanation
This requires a specific race: a file must be selected with an existing diff, and its content must change on disk between two status refreshes while Desktop retains the same selection. GitHub Desktop does run background status polling and refreshes after various git operations, so the window is real but narrow, and it depends on some external process modifying repository files concurrently with Desktop's UI session — I could not find and did not have iterations remaining to confirm the exact polling interval or whether there's an additional safeguard elsewhere (e.g., in the render path) that revalidates the diff against current file stats before staging. This is a caveat I could not fully rule out given the remaining budget.

### Recommendation
Invalidate the cached diff whenever the file's content-identifying attributes change, not just when its ID/path is stable — e.g., compare `WorkingDirectoryFileChange` size/mtime or the underlying git status metadata (`status.kind`, blob OID if available) in addition to `id` in `updateChangedFiles`, and force `diff: null` whenever any such attribute differs between `existingFile` and the new `file` in the merge loop, in addition to the current `selectedFileIDs` equality check.

### Proof of Concept
1. Open a repository in GitHub Desktop and modify a tracked file so it produces a multi-hunk diff; select a subset of lines.
2. While the diff pane is showing the cached hunks (Desktop's background status poller/`refreshChangesSection` will re-run periodically), have an external process (e.g., a script, editor autosave, or a git hook) rewrite the same file's content at the same path within the polling interval.
3. Observe that `updateChangedFiles` keeps `state.selection.diff` because `selectedFileIDs[0]` (the path) is unchanged — the UI does not refresh the diff.
4. Commit the "selected lines" via the Changes pane; inspect the resulting commit with `git show` and compare to the actual working-tree content — verify the staged/committed content reflects offsets computed against the old diff’s line numbers rather than the file’s current content, demonstrating the review the user performed does not correspond to what was actually recorded in the commit.

  // Collect all the currently available file ids into a set to avoid O(N)
  // lookups using .find on the mergedFiles array.
  const mergedFileIds = new Set(mergedFiles.map(x => x.id))

  // The file selection could have changed if the previously selected files
  // are no longer selectable (they were discarded or committed) but if they
  // were not changed we can reuse the diff. Note, however that we only render
  // a diff when a single file is selected. If the previous selection was
  // a single file with the same id as the current selection we can keep the
  // diff we had, if not we'll clear it.
  const workingDirectory = WorkingDirectoryStatus.fromFiles(mergedFiles)

  const selectionKind = state.selection.kind
  if (state.selection.kind === ChangesSelectionKind.WorkingDirectory) {
    // The previously selected files might not be available in the working
    // directory any more due to having been committed or discarded so we'll
    // do a pass over and filter out any selected files that aren't available.
    let selectedFileIDs = state.selection.selectedFileIDs.filter(id =>
      mergedFileIds.has(id)
    )

    // Select the first file if we don't have anything selected and we
    // have something to select.
    if (selectedFileIDs.length === 0 && mergedFiles.length > 0) {
      selectedFileIDs = [mergedFiles[0].id]
    }

    const diff =
      selectedFileIDs.length === 1 &&
      state.selection.selectedFileIDs.length === 1 &&
      state.selection.selectedFileIDs[0] === selectedFileIDs[0]
        ? state.selection.diff
        : null

    return {
      workingDirectory,
      selection: {
        kind: ChangesSelectionKind.WorkingDirectory,
        selectedFileIDs,
        diff,
      },
    }
