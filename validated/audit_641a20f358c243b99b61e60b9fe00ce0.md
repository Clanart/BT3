### Title
Duplicate column lookup in `onLineNumberCheckedChanged` silently drops selection updates on modified diff lines, corrupting what gets staged/committed - (File: `app/src/ui/diff/side-by-side-diff.tsx`)

### Summary
When a user checks/unchecks the inclusion checkbox for a "Modified" row in the side-by-side diff view, GitHub Desktop is supposed to update the selection state for **both** the deleted ("before") line and the added ("after") line that make up that modified-row pairing. Instead, the handler queries the same column twice, so only one of the two paired lines is ever toggled. This can cause the generated partial-commit patch to contain a deletion without its corresponding addition (or vice versa), silently corrupting the file content that actually gets committed relative to what the UI shows as selected.

### Finding Description
`onLineNumberCheckedChanged` is the callback invoked when a user (un)checks a line-selection checkbox in the diff view: [1](#0-0) 

```
private onLineNumberCheckedChanged = (
    row: number,
    column: DiffColumn,
    isSelected: boolean
  ) => {
    ...
    const lineBefore = this.getDiffLineNumber(row, column)
    const lineAfter = this.getDiffLineNumber(row, column)

    if (lineBefore !== null) {
      selection = selection.withLineSelection(lineBefore, isSelected)
    }

    if (lineAfter !== null) {
      selection = selection.withLineSelection(lineAfter, isSelected)
    }

    this.props.onIncludeChanged(selection)
  }
```

Both `lineBefore` and `lineAfter` are computed by calling `this.getDiffLineNumber(row, column)` with the **identical** `column` argument. This delegates to `getDiffRowLineNumber`, which explicitly distinguishes between the before/after line numbers for a `Modified` row: [2](#0-1) 

```
private getDiffRowLineNumber(row: SimplifiedDiffRow, column: DiffColumn) {
    if (row.type === DiffRowType.Added || row.type === DiffRowType.Deleted) {
      return row.data.diffLineNumber
    }

    if (row.type === DiffRowType.Modified) {
      return column === DiffColumn.After
        ? row.afterData.diffLineNumber
        : row.beforeData.diffLineNumber
    }

    return null
  }
```

Because the intent is clearly to resolve both the "before" line number and the "after" line number for a `Modified` row (a row that visually represents a deleted line and its replacement added line side by side), the code should call `getDiffLineNumber(row, DiffColumn.Before)` and `getDiffLineNumber(row, DiffColumn.After)` respectively. As written, `lineBefore` and `lineAfter` are always equal, so the second `withLineSelection` call is a no-op on the line index already updated by the first. The paired line on the other side of the `Modified` row is never toggled.

This directly affects `formatPatch`, which builds the partial commit patch strictly from `file.selection.isSelected(absoluteIndex)` per diff line: [3](#0-2) 

If a user believes they have selected/deselected an entire "modified line" pair via the checkbox but only one side's selection state actually changed, the resulting patch can:
- Include an addition without deleting the corresponding old content (leaving duplicate/stale content), or
- Include a deletion without its intended replacement (silently removing content the user believed was being replaced, not deleted).

This is analogous to the fractional-vault bug's core defect: a computation that is supposed to jointly resolve two paired values (fraction share vs. contribution share) instead collapses to a single value due to a subtle implementation slip, causing a state (selection/committed content) that silently diverges from what the "protocol"/UI promised the user.

### Impact Explanation
This causes **silent corruption of what the user commits**, one of the explicitly valid impact categories in the task instructions. A user reviewing and toggling a modified line pair in the side-by-side diff view can end up staging a patch whose actual line content differs from their intent — without any error or warning — because the checkbox interaction updates only one of the two paired diff lines. Repeated use across a session could result in unintended/incomplete changes being pushed, which is a genuine correctness/security-relevant defect for a version control client whose entire trust model rests on accurately reflecting to the user what will be committed.

### Likelihood Explanation
The bug triggers on ordinary, unprivileged user interaction — no attacker-controlled repository/API object is strictly required, since the flaw is purely in Desktop's own UI selection logic when handling any diff that produces a `Modified` row in side-by-side view (i.e., an adjacent deletion+addition pair in a hunk). Any user editing files with `Modified`-type rows and using the per-line checkbox to select a subset for commit can hit this path. Because it requires no crafted repository content beyond a normal modified line, and no special privileges, likelihood of occurrence during routine use is high, though the user may not immediately notice the mismatch since the UI still visually shows a checked/unchecked state consistent with `isSelected` reads that use the same (buggy) column resolution path elsewhere — meaning the UI checkbox rendering and the underlying committed patch can silently diverge.

### Recommendation
Fix `onLineNumberCheckedChanged` to resolve the before and after line numbers independently:
```
const lineBefore = this.getDiffLineNumber(row, DiffColumn.Before)
const lineAfter = this.getDiffLineNumber(row, DiffColumn.After)
```
Add a regression test exercising a `Modified` row checkbox toggle that asserts both the underlying deleted line and added line indices are updated in the resulting `DiffSelection`, and that `formatPatch` produces the expected paired add/delete lines.

### Proof of Concept
1. Open a repository in Desktop and modify a single line in a tracked text file (produces a `Modified` row — one deleted line beside one added line — in side-by-side diff view).
2. In the Changes view, toggle the per-line checkbox for that modified row to include only that change in the commit.
3. Instrument/log `getDiffLineNumber(row, column)` calls inside `onLineNumberCheckedChanged`, or inspect the resulting `DiffSelection` object: observe that `lineBefore === lineAfter`, i.e., only one of the paired before/after diff-line indices was toggled.
4. Call `formatPatch(file, diff)` with this selection state and observe the emitted hunk: the deleted ("before") line and added ("after") line are not both included/excluded together as intended, producing a patch whose net content differs from what the checkbox UI implied to the user.
