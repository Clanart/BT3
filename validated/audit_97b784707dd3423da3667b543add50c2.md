## Analysis

The external report's core broken invariant: a Chainlink consumer treats a price as "fresh" purely by comparing `block.timestamp` against `updatedAt`, without confirming the L2 sequencer was actually live and posting rounds during that window — letting attackers exploit a stale/frozen price the instant the sequencer resumes.

The local analog is `SimplexPaymaster._getOraclePrice()` in `evm/src/utils/SimplexPaymaster.sol`, which performs exactly the vulnerable pattern and is deployed on Arbitrum-class chains.

### Title
Missing Chainlink L2 sequencer-uptime check in `SimplexPaymaster._getOraclePrice()` allows underpriced gas token draining on Arbitrum-class deployments - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payment using two Chainlink `AggregatorV3Interface.latestRoundData()` feeds (`nativeOracle` and `cfg.tokenOracle`), guarding only `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge`, as seen in `_getOraclePrice()` at [1](#0-0) . There is no check of an L2 sequencer-uptime feed (e.g., Chainlink's `L2SequencerUptimeFeed`), which is the exact bug class from the external report. This contract is explicitly designed for multi-chain deployment (`DeploySimplexPaymaster.s.sol` reads a `NATIVE_ORACLE` address per target chain) [2](#0-1) , and the indexer's own Chainlink feed registry lists Arbitrum Mainnet/Sepolia price feeds [3](#0-2) , confirming Arbitrum is a supported/expected deployment target for this codebase's oracle-consuming contracts.

### Finding Description
On Arbitrum, when the sequencer goes offline, no new L2 blocks (and thus no new transactions, including Chainlink price pushes relayed via L2) are produced. When the sequencer comes back online, it can batch-process a backlog of transactions with `block.timestamp` values that land close together, or the last on-chain round from before the outage can still fall within `maxOracleAge` even though the off-chain market price moved substantially during the outage window. `_getOraclePrice()` only checks:
```solidity
if (answer <= 0) revert InvalidOraclePrice(...);
if (block.timestamp - updatedAt > maxOracleAge) revert StaleOraclePrice(...);
``` [4](#0-3) 
Neither check detects "the round is stale relative to sequencer downtime" — the canonical failure mode the Chainlink L2 docs warn about. `_tokenPrice()` feeds this same unguarded price directly into the amount of ERC-20 charged for gas [5](#0-4) , and `_fetchDetails()`/`_validatePaymasterUserOp()` use it, unauthenticated by any caller-side permission, to determine exactly how much of the sender's token is pulled per UserOp [6](#0-5) . Any unprivileged account can submit an ERC-4337 UserOp the instant the sequencer resumes, using the stale/mispriced `tokenPrice` to pay far less ERC-20 than the true dollar cost of the native gas the paymaster fronts via its EntryPoint deposit.

### Impact Explanation
Each exploited UserOp lets the sender pay under-market ERC-20 while the paymaster's EntryPoint deposit is drained for the real gas cost — a direct, repeatable loss of protocol funds (the treasury-owned EntryPoint deposit and accrued surplus) with no privileged actor, malicious relayer, or governance compromise required. This matches the bounty's "stealing or loss of funds" and "transaction/logic manipulation via false price acceptance" categories.

### Likelihood Explanation
Exploitability is bounded by real Arbitrum sequencer outages, which do occur periodically, and by the size of the price move during downtime relative to `maxOracleAge`. It is a public, unprivileged entrypoint attack (any address can call `validate`/submit UserOps through the EntryPoint) requiring no relayer or admin compromise — moderate likelihood, contingent on an external, non-adversarial event (sequencer downtime) rather than any malicious peer assumption, so it satisfies the "unprivileged attacker" requirement of the gate.

### Recommendation
Add an Arbitrum/L2 sequencer-uptime feed check (per Chainlink's documented pattern) to `_getOraclePrice()`: revert if the sequencer feed reports `answer != 0` (down) or if `block.timestamp - startedAt` is within a grace period after the sequencer came back up, in addition to the existing staleness and positivity checks.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum with `nativeOracle`/token oracles and `maxOracleAge` per `DeploySimplexPaymaster.s.sol`.
2. Simulate sequencer downtime (no new Chainlink rounds pushed) while off-chain ETH/USD price rises sharply.
3. When sequencer resumes, the last round's `updatedAt` may still satisfy `block.timestamp - updatedAt <= maxOracleAge` per `_getOraclePrice()` at [4](#0-3) .
4. Attacker immediately submits a UserOp using `_fetchDetails()` pricing derived from this stale round, paying ERC-20 at the pre-outage (lower) native price while the paymaster fronts gas at the true post-outage cost, draining the EntryPoint deposit disproportionately versus ERC-20 collected — repeatable until oracles catch up.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
