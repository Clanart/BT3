### Title
Quadratic Lagrange interpolation in `ThresholdKeys::read` enables deserialization denial of service - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes attacker-controlled `t`, `n`, and interpolation-method bytes and immediately calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for every participant `1..=t`. With `Interpolation::Lagrange`, each `interpolation_factor` call is O(t), making `read` O(t²) — an unprivileged party supplying `t = n = 65535` forces ~4.3 billion field multiplications plus a scalar inversion during a single `read`.

### Finding Description
The bug class of CVE-2023-32636 is "validation performed at deserialization time is algorithmically expensive on crafted input" — Serai has the same shape. `ThresholdKeys::read` reads `t`, `n`, `i` from the byte stream with no size bound beyond `u16`, then for `Interpolation::Lagrange` (tag byte `1`) calls `ThresholdKeys::new`, which computes `group_key` by summing `verification_shares[i] * interpolation_factor(*i, &t)` for all `t` participants [1](#0-0) [2](#0-1) . `interpolation_factor` in the `Lagrange` arm iterates over the entire `included` slice performing field multiplications per element [3](#0-2) . Unlike `Interpolation::Constant`, `Lagrange` imposes no `t == n` restriction and no cap, so a fully attacker-controlled serialized blob forces `t` × O(t) = O(t²) field arithmetic — ~4.3 × 10⁹ multiplications at the `u16` maximum — inside a function that returns `io::Result`, i.e., expected to be cheap input validation [4](#0-3) . The same quadratic pattern recurs in `ThresholdView::view`/`verification_share` interpolation, but `read` is the unprivileged entry point listed for untrusted bytes.

### Impact Explanation
A single small (~2 MB) malicious payload stalls any thread that deserializes untrusted `ThresholdKeys` (e.g., key-share recovery, `networks/bitcoin`/`recovery` paths feeding `ThresholdKeys::read`) for minutes of CPU time per message. Repeated messages amplify this into sustained CPU exhaustion of validators/processors handling untrusted input — availability loss with no cryptographic break, matching the DoS impact of the reference CVE.

### Likelihood Explanation
Reachable whenever serialized `ThresholdKeys` originate from an untrusted or recoverable source (`crypto/dkg/recovery`, reshare flows) rather than self-generated output. The attacker needs no keys, no collusion, and no protocol role — only the ability to hand bytes to `ThresholdKeys::read`. Cost asymmetry is extreme: a few megabytes of input buys billions of field operations.

### Recommendation
Bound `t`/`n` at read time to a protocol-realistic maximum (e.g., `MAX_KEY_SHARES_PER_SET`) before calling `ThresholdKeys::new`, or precompute the Lagrange basis product denominators so `group_key` derivation is O(t·log t) or O(t) instead of O(t²). At minimum, defer interpolation to first use so `read` remains linear in input size.

### Proof of Concept
Conceptual: serialize a `ThresholdKeys` blob with curve ID matching, `t = n = 65535`, `i = 1`, interpolation tag `1` (Lagrange), any canonical `secret_share`, and 65535 canonical non-identity `verification_shares`. `ThresholdKeys::read` on this blob executes `ThresholdKeys::new`, which evaluates `interpolation_factor` (O(t) inner loop) for each of `t` participants — ~4.3 × 10⁹ field multiplications — before returning. Compare with interpolation tag `0` (Constant), where each factor is a single index lookup (`c[i - 1]`) and the same input completes in linear time, demonstrating the quadratic blowup is inherent to the Lagrange path.
