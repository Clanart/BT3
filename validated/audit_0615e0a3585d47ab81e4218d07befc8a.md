### Title
OP_RETURN data is omitted from transaction weight and fee calculations, producing underpriced signed transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends a caller-controlled `OP_RETURN` output to `tx_outs`, but both calls to `calculate_weight_vbytes` pass only `payments` and `change`. The data output is therefore absent from the estimated weight, virtual size, required fee, minimum-relay-fee check, and maximum-standard-weight check. [1](#0-0) [2](#0-1) 

### Finding Description
`calculate_weight_vbytes` reconstructs the transaction from `inputs`, `payments`, and an optional `change` output, then returns its weight and virtual size. [3](#0-2)  The function has no parameter for `data`, even though `SignableTransaction::new` accepts up to 80 bytes and unconditionally adds them as an `OP_RETURN` output before calculating the fee. [4](#0-3) 

This creates an asymmetric reserve calculation analogous to the reported bug: the required-resource bound is derived from only some components of the final object. The final transaction can contain a payment output, a change output, and an `OP_RETURN` output, while `needed_fee` is priced only for the payment and change forms. [5](#0-4)  The final `MAX_STANDARD_TX_WEIGHT` check likewise evaluates the underestimated `weight`, not the weight of `tx` after adding the `OP_RETURN`. [6](#0-5) 

The resulting `SignableTransaction` is signed over its actual contents, including the `OP_RETURN`, because the sighash cache is constructed from `self.tx.tx`. [7](#0-6) 

### Impact Explanation
An unprivileged caller that can supply transaction data can cause the threshold wallet to produce a validly signed transaction whose actual fee is lower than the requested `fee_per_vbyte`. With tightly selected inputs and no change output, the actual fee can be exactly `needed_fee`; once the unpriced `OP_RETURN` output is included in the actual vsize, the effective feerate falls below the requested rate and can fall below Bitcoin Core's minimum relay feerate. [8](#0-7) [9](#0-8) 

The signed transaction may therefore be rejected during relay or remain unconfirmed, making the selected UTXOs unavailable until the invalid/stuck attempt is abandoned or replaced. This affects the core Bitcoin send path exposed through `SignableTransaction::new` and ultimately signs a transaction different in size and required fee from the one that was priced. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
The trigger requires only the supported `data: Option<Vec<u8>>` argument. Payloads of up to 80 bytes are explicitly permitted by `SignableTransaction::new`, so no malformed input, malicious validator, leaked key, or protocol violation is needed. [12](#0-11) [13](#0-12) 

Any nonempty `OP_RETURN` output increases the transaction's base size by its serialized output amount, script length, script bytes, and output-count encoding. Because base bytes are not discounted, the unaccounted virtual size can approach the size of the serialized 80-byte data output. The discrepancy is deterministic, not probabilistic. [14](#0-13) [15](#0-14) 

### Recommendation
Include the serialized `OP_RETURN` output in every call to `calculate_weight_vbytes`, both with and without change. A direct fix is to build the complete output vector before sizing and pass it to `calculate_weight_vbytes`, rather than passing only `payments`. Ensure that:

- `needed_fee` is calculated from the final transaction vsize;
- the minimum relay fee check uses that complete vsize;
- the change decision subtracts the fee required by the transaction containing both change and data;
- `MAX_STANDARD_TX_WEIGHT` is checked against the actual `tx.weight()` after all outputs are appended. [16](#0-15) 

### Proof of Concept
The following test demonstrates that `needed_fee` is calculated for the transaction without the `OP_RETURN` output, while `transaction()` contains it:

```rust

fn op_return_is_not_included_in_fee_size() {
  let (_, key) = keys();
  let rpc = /* regtest RPC */;
  let scanner = Scanner::new(key).unwrap();
  let input = /* spendable ReceivedOutput */;
  let payment = (p2tr_script_buf(key).unwrap(), 1_000);

  // Choose fee_per_vbyte = 1 so needed_fee equals the underestimated vsize.
  let fee_per_vbyte = 1;
  let tx = SignableTransaction::new(
    vec![input],
    &[payment],
    None,
    Some(vec![0xaa; 80]),
    fee_per_vbyte,
  )
  .unwrap();

  let actual_vbytes = u64::try_from(tx.transaction().vsize()).unwrap();

  // Fails: needed_fee was calculated from a transaction that did not contain
  // the 80-byte OP_RETURN output.
  assert!(tx.needed_fee() >= actual_vbytes * fee_per_vbyte);
}
```

The root cause is visible without executing the test: `tx_outs` receives the `OP_RETURN` at lines 193–202, but the sizing calls at lines 204 and 225–226 receive only `payments`, not `tx_outs` or `data`. [17](#0-16) [18](#0-17)
