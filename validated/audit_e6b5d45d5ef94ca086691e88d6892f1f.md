## Title
Stale index-based diff line selection can silently include/exclude the wrong content when the working directory changes between diff display and patch generation - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop tracks a user's partial-commit line selection (`DiffSelection`) as a set of **absolute line indices** into a previously-loaded diff, not as a reference to actual line content. When the working directory changes between the time the diff is rendered/selected and the time the commit patch is generated, Desktop re-fetches a fresh diff but re-applies the old, index-based selection against it. The code's own comments acknowledge this is not properly reconciled. This mirrors the reported Portals bug class: one derived state (`selection`) is updated/reused independently of the primary state it depends on (`diff` content), letting the two drift out of sync.

### Finding Description
Partial-commit selection is stored as line-index sets in `DiffSelection` (`app/src/models/diff/diff-selection.ts`), and is refreshed only by pruning indices that no longer exist, not by verifying that retained indices still refer to the same underlying content: [1](#0-0) 

The comment at these lines explicitly states the limitation: "The diff might have changed dramatically since last we loaded it... but for now we'll settle on just updating the selectable lines such that any previously selected line which now no longer exists or has been turned into a context line isn't still selected." Any selected index that is still "includeable" in the new diff is kept selected, even if the actual text at that index has changed.

Separately, at actual commit/staging time, `applyPatchToIndex` re-fetches the diff **again**, independent of whatever diff the UI last showed the user, and applies the (already possibly stale) `file.selection` against it: [2](#0-1) 

`formatPatch` then decides what to include purely by `file.selection.isSelected(absoluteIndex)` against the freshly fetched diff's line indices: [3](#0-2) 

If the file content on disk changes between the moment the user visually reviews/checks lines in the Changes view and the moment `_commitIncludedChanges` triggers staging, the index-to-content mapping shifts. `_commitIncludedChanges` itself does not re-diff or re-validate selection against current content before staging — it simply filters files by selection type and hands them to `stageFiles`/`applyPatchToIndex`: [4](#0-3) 

This is the same broken-invariant pattern as the Portals report: `stakedBalance`/`availableToWithdraw` (analogous to the freshly-reloaded diff content) get updated, while `maxStakeDebt`/`portalEnergy` (analogous to the cached line-index selection) are not recomputed in lockstep, letting a state that should be derived from the same source drift independently.

### Impact Explanation
If an attacker can influence working-directory content changes that happen concurrently with a user's review-then-commit workflow (e.g. via a malicious repository containing a `smudge`/`clean` filter, a `post-checkout`/`post-merge` hook, an LFS pointer resolution, or a background process triggered by content the attacker controls in a cloned/fetched repository), the lines a user visually selected for inclusion can silently diverge from the lines actually staged and committed. This is a "silent corruption of what the user commits" scenario — the user believes they excluded certain content (e.g. secrets, malicious code, or unwanted changes) but Desktop stages different lines than what was shown, or vice versa.

### Likelihood Explanation
This requires a narrow timing window (working tree modified between diff render and commit) and a mechanism for the attacker's repository to trigger such modifications (hooks, filters, or other repository-controlled automation) without additional user action beyond normal clone/fetch/commit usage. It does not require admin rights, local access, or leaked credentials — only that the user clones/opens a malicious repository and performs the ordinary partial-commit workflow. Likelihood is lower than a fully deterministic exploit because it depends on a race between working-tree mutation and commit action, but the code path exists exactly as described with an acknowledged and unaddressed gap.

### Recommendation
- Re-validate `DiffSelection` against actual line content hashes (not just index/position) whenever the diff is reloaded, invalidating (rather than blindly retaining) any selection whose underlying line content has changed.
- In `_commitIncludedChanges`, re-fetch and re-diff each selected file's content immediately before staging and compare it against the diff that was last shown to the user; abort or re-prompt if content has changed since selection was made.
- Ensure `applyPatchToIndex` and `formatPatch` operate against the same diff snapshot that produced the currently-active `DiffSelection`, rather than independently re-fetching a diff that could differ from what the selection was computed against.

### Proof of Concept
1. Clone a malicious repository containing a `smudge` filter or `post-checkout` hook that, after a short delay, rewrites a tracked file's content (attacker-controlled, triggered automatically on checkout/fetch without extra user action).
2. In Desktop, modify the file further and open the Changes view; Desktop loads a diff and the user selects specific lines for inclusion via `DiffSelection`.
3. Before the user clicks Commit, the attacker's hook/filter fires and rewrites the file's content on disk, shifting line positions but keeping the same number of "includeable" lines (so `updateChangesWorkingDirectoryDiff`'s prune-only guard, `app/src/lib/stores/app-store.ts:3478-3497`, does not clear the stale selection).
4. The user clicks Commit. `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`) and applies the old index-based `selection` to it via `formatPatch` (`app/src/lib/patch-formatter.ts:157`), staging different content than what the user last visually reviewed and approved.
