### Title
`donateRewards`/`_provisionReward` accounting breaks with fee-on-transfer reward tokens, permanently freezing part of stakers' claimable rewards - (File: rewards/BaseRewardPool.sol, rewards/BaseRewardPoolV2.sol)

### Summary
`_provisionReward` (invoked by the unpermissioned `donateRewards` entrypoint, and also by `queueNewRewards`) increases `rewardInfo.rewardPerTokenStored` and `rewardInfo.historicalRewards` using the caller-supplied `_amountReward` value, while pulling the tokens with `safeTransferFrom(msg.sender, address(this), _amountReward)`. If the reward token charges a transfer fee, the pool receives less than `_amountReward`, but the accounting still credits users as if the full amount arrived, over-crediting `rewardPerTokenStored` relative to the actual token balance held by the contract.

### Finding Description
`_provisionReward` in `BaseRewardPool.sol` (and identically in `BaseRewardPoolV2.sol`) does:
```solidity
IERC20(_rewardToken).safeTransferFrom(msg.sender, address(this), _amountReward);
...
rewardInfo.rewardPerTokenStored = rewardInfo.rewardPerTokenStored +
    (_amountReward * 10**stakingDecimals()) / this.totalStaked();
``` [5](#0-4) 

It never checks the pre/post balance delta of the reward token, so it assumes the pool received exactly `_amountReward`. This is exactly the bug class described in the referenced PoolTogether `TwabRewards` report: reward-per-share/reward-per-epoch accounting is based on the nominal transferred amount, not the actually-received balance.

Critically, `donateRewards` is reachable by any ordinary, unprivileged wallet — it has no `onlyManager` or `onlyOwner` modifier, unlike `queueNewRewards`:
```solidity
function donateRewards(uint256 _amountReward, address _rewardToken) external {
    if (!isRewardToken[_rewardToken])
        revert MustBeRewardToken();
    _provisionReward(_amountReward, _rewardToken);
}
``` [6](#0-5) 

Any account is free to call `donateRewards` for any already-registered `_rewardToken` (e.g. MGP, WOM, WOM-bribe tokens registered via `queueNewRewards`/`vote()` in `WombatStaking.sol`). If the registered reward token is (or later becomes) a fee-on-transfer / deflationary token, every `donateRewards`/`queueNewRewards` call inflates `rewardPerTokenStored` beyond what the pool actually holds. `mWOMSVBaseRewarder.sol` has the identical unguarded `donateRewards` + `_provisionReward` pattern as well.

### Impact Explanation
Because `rewardPerTokenStored` (and thus each user's `earned()`/`userRewards`) is computed from the nominal donated amount rather than the real balance received, the sum of all users' claimable rewards can exceed the reward token balance actually held by the contract. When users call `getReward`, `BaseRewardPool.sol`'s `IERC20(rewardToken).safeTransfer(_receiver, reward)` will eventually fail for balance-insufficient tokens, or earlier claimants will drain the real balance leaving later claimants permanently unable to claim their accrued/entitled rewards — a permanent freeze of unclaimed yield for at least a subset of stakers, with no recovery mechanism in the contract.

### Likelihood Explanation
This requires only that a reward token registered on a `BaseRewardPool`/`BaseRewardPoolV2` be fee-on-transfer, or that a caller repeatedly calls the completely permissionless `donateRewards` with mismatched actual-vs-declared transfer amounts (any fee/rebasing/deflationary ERC20). No privileged role is needed to trigger the shortfall — a single unprivileged wallet holding such a token can call `donateRewards` directly.

### Recommendation
In `_provisionReward`, measure the actual amount received instead of trusting the `_amountReward` parameter:
```solidity
uint256 before = IERC20(_rewardToken).balanceOf(address(this));
IERC20(_rewardToken).safeTransferFrom(msg.sender, address(this), _amountReward);
uint256 received = IERC20(_rewardToken).balanceOf(address(this)) - before;
// use `received` for historicalRewards / rewardPerTokenStored math
```
Apply the same fix to `BaseRewardPool.sol`, `BaseRewardPoolV2.sol`, and `mWOMSVBaseRewarder.sol`.

### Proof of Concept
1. Owner/manager registers a fee-on-transfer ERC20 `FeeToken` as a reward token on a `BaseRewardPool` (via `queueNewRewards`, which pushes it into `isRewardToken`) [7](#0-6) .
2. Any unprivileged wallet holding `FeeToken` calls `donateRewards(1000e18, FeeToken)`. Say `FeeToken` charges a 5% fee, so the pool only receives 950e18 tokens, yet `_provisionReward` credits `rewardPerTokenStored` based on the full 1000e18 [5](#0-4) .
3. Over multiple donations, cumulative `rewardPerTokenStored` overstates the real `FeeToken` balance held by the pool by the cumulative fee amount.
4. Stakers who call `getReward` early drain the real balance; later stakers' `getReward` calls revert or return zero due to insufficient balance, permanently losing their accrued rewards with no way to recover them.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
