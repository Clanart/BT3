### Title
Third-party replay of a signed EIP-7702 authorization tuple lets anyone consume a victim's account nonce, front-running and DoS'ing the victim's own pending transactions - (File: `blockchain/state_transition.go`)

### Summary
Kaia's EIP-7702 (`TxTypeEthereumSetCode`) implementation lets **any** transaction sender embed a `SetCodeAuthorization` tuple signed by a third-party "authority" inside their own `AuthList`, and the state transition applies it — including incrementing the authority's account nonce — as long as the authorization's `nonce` field still matches the authority's current on-chain nonce. This mirrors the symmio-core `chargeFundingRate` bug class: a party that is not the nonce owner can cheaply force a nonce bump on someone else's account, invalidating that account's own pending/queued operations that were signed against the old nonce.

### Finding Description
`applyAuthorization` validates and applies each authorization tuple in `msg.AuthList()` independently of who submitted the outer transaction: [1](#0-0) [2](#0-1) 

The only checks performed are chain ID, nonce-overflow, signature validity, code/delegation state, and `have := st.state.GetNonce(authority); have != auth.Nonce`. Critically, there is no requirement that `msg.ValidatedSender()` (the tx submitter/fee payer) be the authority, nor any binding of the authorization to the specific outer transaction that the authority intended it to accompany. This is invoked unconditionally for every `TxTypeEthereumSetCode` transaction on the network: [3](#0-2) 

`AccountStorage`-analog protection at the tx-pool layer (`validateAuth`/`checkDelegationLimit`) only limits how many *mempool-resident* transactions may reference the same authority; it does nothing once the authorizing tuple is embedded in someone else's transaction that gets mined directly: [4](#0-3) [5](#0-4) 

Consequently, any address that obtains a validly signed `SetCodeAuthorization{ChainID, Address, Nonce}` for victim account `V` (e.g. leaked from a wallet UI, a griefed dApp flow, mem-pool sniffing of a pending SetCodeTx from `V` itself, or any other legitimate distribution channel for the authorization) can wrap it in an unrelated `TxTypeEthereumSetCode` transaction of its own — paying its own gas, using an arbitrary unrelated `to`/`data` — and get it mined ahead of `V`'s own transaction that uses the same nonce. `state.IncNonce(authority)` is executed as a side effect: [6](#0-5) 

This bumps `V`'s nonce and (unless `Address` is the zero address) installs a delegation to `auth.Address`, exactly analogous to `chargeFundingRate` bumping `partyANonces[partyA]` for the price of gas alone.

### Impact Explanation
Once `V`'s nonce is advanced by the attacker's transaction:
- Any of `V`'s own pending transactions (fee-delegated or not) signed with the old nonce become stale and fail with `ErrNonceTooLow` in `preCheck`, exactly the mechanism the state transition uses for ordinary nonce checks: [7](#0-6) 
- Because the attacker fully controls the timing (they can watch the mempool for `V`'s intended SetCodeTx/authorization and front-run it), this is a griefing/DoS primitive: `V`'s legitimately signed transaction is denied inclusion and must be re-signed with the new nonce, at `V`'s expense/inconvenience, and repeatedly if the attacker keeps re-triggering it (as long as they keep obtaining/replaying valid authorization tuples for `V`).
- Additionally, since `applyAuthorization` installs `auth.Address` as `V`'s delegation target, a malicious relayer can force `V`'s account into a state (or force-clear an intended delegation) at a time the attacker chooses rather than when `V` intended, which can be leveraged to disrupt time-sensitive flows built on account delegation.

This matches the accepted Sherlock M-5 pattern: a non-owning party can cheaply and repeatedly manipulate a victim's nonce state to block the victim's legitimate signed operations.

### Likelihood Explanation
The precondition — possession of a validly signed authorization tuple for the target nonce — is the main constraint, but this is not unusual: authorizations are commonly distributed off-chain (to relayers/sponsors, by design of EIP-7702) before being bundled on-chain, and any leak, resend, or malicious relayer scenario exposes this. Because the attack costs only ordinary transaction gas and requires no special privilege (any public-RPC submitter can do it), and the mempool-level `checkDelegationLimit`/`validateAuth` protections do not prevent a single directly-mined transaction from applying a foreign authorization, likelihood is Medium — comparable to the semi-trusted-but-adversarial-role likelihood accepted for the original PartyB medium finding.

### Recommendation
- Require that authorizations applied within a `TxTypeEthereumSetCode` transaction either originate from `msg.ValidatedSender()` itself, or be scoped/bound to a specific outer transaction (e.g., include a hash/commitment of the accompanying call in what the authority signs), so a third party cannot unilaterally replay a authority's authorization outside the transaction it was intended for.
- Alternatively, enforce a mempool/state-transition level "consume once, only via the transaction the authority actually broadcast/co-signed" model, and reject authorizations whose outer transaction was not authorized by the authority (e.g., via an authority-provided allow-list of relayers, or a nonce-window/commit-reveal scheme).
- At minimum, extend the tx-pool's `checkDelegationLimit`/`validateAuth` invariant ("at most one in-flight tx per authority") to also gate direct inclusion, and surface a way for `V` to detect and cancel a stale nonce quickly (already partially possible via `TxTypeFeeDelegatedCancel`, but that requires `V`'s own action after the griefing has already occurred).

### Proof of Concept
1. Authority `V` signs `SetCodeAuthorization{ChainID: chainId, Address: someAddr, Nonce: N}` intending to co-submit it with their own `TxTypeEthereumSetCode` transaction (nonce `N`) at a later time; the tuple is exposed (e.g. observed in `V`'s own broadcast pending tx, or leaked via any off-chain sharing channel for sponsored transactions).
2. Attacker `A` (unrelated to `V`) crafts its own `TxTypeEthereumSetCode` transaction with `to = A`'s own contract/arbitrary address, `AuthList = [that SetCodeAuthorization]`, signed by `A`, and submits it with higher gas price to front-run `V`'s original transaction.
3. On execution, `applyAuthorization` verifies `GetNonce(V) == N` (still true) and calls `state.IncNonce(V)` and `state.SetCodeToEOA(V, delegation(someAddr))`, as shown in: [2](#0-1) 
4. `V`'s nonce is now `N+1`. `V`'s original pending transaction (nonce `N`) subsequently fails `preCheck`'s nonce check with `ErrNonceTooLow`: [8](#0-7) 
5. `V` must detect the failure and re-sign a new transaction with nonce `N+1`, and the attacker can repeat this whenever a new valid authorization for `V` becomes available, at minimal and repeatable cost to the attacker.

func (st *StateTransition) validateAuthorization(auth *types.SetCodeAuthorization) (authority common.Address, err error) {
	// Verify chain ID is 0 or equal to current chain ID.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(st.evm.ChainConfig().ChainID) != 0 {
		return authority, ErrAuthorizationWrongChainID
	}
	// Limit nonce to 2^64-1 per EIP-2681.
	if auth.Nonce+1 < auth.Nonce {
		return authority, ErrAuthorizationNonceOverflow
	}
	// Validate signature values and recover authority.
	authority, err = auth.Authority()
	if err != nil {
		return authority, fmt.Errorf("%w: %v", ErrAuthorizationInvalidSignature, err)
	}
	// Check the authority account
	//  1) doesn't have code or has existing delegation
	//  2) matches the auth's nonce
	//
	// Note it is added to the access list even if the authorization is invalid.
	st.state.AddAddressToAccessList(authority)
	code := st.state.GetCode(authority)
	if _, ok := types.ParseDelegation(code); len(code) != 0 && !ok {
		return authority, ErrAuthorizationDestinationHasCode
	}
	if have := st.state.GetNonce(authority); have != auth.Nonce {
		return authority, ErrAuthorizationNonceMismatch
	}
	return authority, nil
}

func (st *StateTransition) applyAuthorization(auth *types.SetCodeAuthorization, rules params.Rules) (err error) {
	authority, err := st.validateAuthorization(auth)
	if err != nil {
		return err
	}

	// If the account already exists in state, refund the new account cost
	// charged in the initrinsic calculation.
	if st.state.Exist(authority) {
		// If the account is not AccountKeyTypeLegacy, setcode is not allowed.
		accountKeyType := st.state.GetKey(authority).Type()
		if !accountKeyType.IsLegacyAccountKey() {
			return fmt.Errorf("%w: %v", ErrAuthorizationNotAllowAccountKeyType, accountKeyType)
		}
		st.state.AddRefund(params.CallNewAccountGas - params.TxAuthTupleGas)
	}

	// Update nonce and account code.
	st.state.IncNonce(authority)
	delegation := types.AddressToDelegation(auth.Address)
	if common.EmptyAddress(auth.Address) {
		// Delegation to zero address means clear.
		st.state.SetCodeToEOA(authority, []byte{}, rules)
		return nil
	}

	// Otherwise install delegation to auth.Address.
	// We treat EOA and SCA as separate objects and therefore need to use
	// distinct methods.
	st.state.SetCodeToEOA(authority, delegation, rules)

	return nil
}

func (pool *TxPool) checkDelegationLimit(tx *types.Transaction) error {
	from, _ := types.Sender(pool.signer, tx) // validated

	// Short circuit if the sender has neither delegation nor pending delegation.
	if pool.currentState.GetCodeHash(from) == types.EmptyCodeHash && !pool.all.hasAuth(from) {
		return nil
	}
	pending := pool.pending[from]
	if pending == nil {
		// Transaction with gapped nonce is not supported for delegated accounts
		if pool.getPendingNonce(from) != tx.Nonce() {
			return ErrOutOfOrderTxFromDelegated
		}
		return nil
	}
	// Transaction replacement is supported
	if pending.Contains(tx.Nonce()) {
		return nil
	}
	return ErrInflightTxLimitReached
}

// validateAuth verifies that the transaction complies with code authorization
// restrictions brought by SetCode transaction type.
func (pool *TxPool) validateAuth(tx *types.Transaction) error {
	// Allow at most one in-flight tx for delegated accounts or those with a
	// pending authorization.
	if err := pool.checkDelegationLimit(tx); err != nil {
		return err
	}

	// For symmetry, allow at most one in-flight tx for any authority with a
	// pending transaction.
	for _, auth := range tx.SetCodeAuthorities() {
		var count int
		if pending := pool.pending[auth]; pending != nil {
			count += pending.Len()
		}
		if queue := pool.queue[auth]; queue != nil {
			count += queue.Len()
		}
		// Replace the existing in-flight transaction for delegated accounts
		// are still supported
		if count > 1 {
			return ErrAuthorityReserved
		}
	}
	return nil
}
