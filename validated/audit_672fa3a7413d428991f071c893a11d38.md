## Analysis

The external report's core pattern: an amount is partially consumed/transferred out, but the code that follows doesn't update its tracked "remaining balance" variable — so the contract either double-spends against a stale balance (revert / accounting corruption) or, in the inverse case, forgets to disburse the leftover it never subtracted.

The Tron deployment of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) has exactly this class of bug in `placeOrder()`. Compare it against the maintained EVM version.

**Reference (correct) implementation** — `evm/src/apps/IntentGatewayV2.sol`: [1](#0-0) 

Here, after the ETH→feeToken swap, `amounts[0]` (the actual ETH the router consumed) is subtracted from the tracked `msgValue`, and any leftover `msgValue` is explicitly refunded to `msg.sender`.

**Tron implementation (missing both steps)** — `evm/tron/contracts/apps/IntentGatewayV2.sol`: [2](#0-1) 

In this version:
1. `swapETHForExactTokens{value: msgValue}(order.fees, ...)` is called with the *entire remaining* `msgValue`, but the returned `amounts` array is discarded — `msgValue` is never decremented by the ETH actually spent.
2. There is no refund step at all after the fee block — the function goes straight to `emit OrderPlaced(...)` and returns.

Uniswap V2's `swapETHForExactTokens` only consumes as much ETH as needed to produce the exact `order.fees` output and refunds the difference (`msg.value - amounts[0]`) back to the caller — i.e., back to the `IntentGatewayV2` contract itself, not to the user. Since the contract never tracks or forwards that ETH to `msg.sender`, it is permanently stranded in the contract's balance. Any native-token input remainder that would otherwise be refunded (as the EVM version does) is likewise never returned on this code path.

### Title
Unrefunded / Unaccounted Native-ETH Surplus Permanently Locked in `placeOrder()` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder()` in the Tron contract swaps `msgValue` native ETH for the fee token via `swapETHForExactTokens`, but never decrements `msgValue` by the amount actually spent (`amounts[0]`) and never refunds the leftover to the user, unlike the audited EVM `IntentGatewayV2.sol` which does both. Excess native ETH sent with an order is silently stranded in the contract.

### Finding Description
`placeOrder()` accepts `msg.value` and tracks the unspent remainder in a local `msgValue` variable as it escrows inputs and predispatch assets. When `order.fees > 0` and the caller pays with native tokens, the function calls `IUniswapV2Router02.swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)`. This router call only spends `amounts[0] <= msgValue` ETH and refunds `msgValue - amounts[0]` to the caller of the router — which is the `IntentGatewayV2` contract, not the end user. The upstream, audited EVM version captures this by doing `msgValue -= amounts[0];` and later executing an explicit refund of any residual `msgValue` to `msg.sender`. The Tron contract's `placeOrder()` omits both: it neither decrements `msgValue` after the swap nor performs any final refund, so the corrected value (the true unspent native balance) is simply dropped — the same "amount transferred/consumed out-of-band but never subtracted from the value used downstream" defect described in the seed report, just manifesting as silently abandoned funds instead of an under-collateralized swap revert.

### Impact Explanation
Any user who overestimates the native ETH needed for `order.fees` (a very likely scenario since the exact router price is unknown at call time and users must supply headroom) permanently loses the surplus — it is locked inside the `IntentGatewayV2` contract with no code path that returns it to them. This is a direct, unprivileged loss of user funds triggered purely through the normal `placeOrder()` entrypoint, matching the "loss of funds" impact category.

### Likelihood Explanation
Every same-chain or cross-chain order placed on this deployment with `order.fees > 0` paid in native token and any `msg.value` beyond the exact router-quoted cost triggers this loss deterministically — there is no attacker-controlled or adversarial condition required, just normal usage with imprecise fee estimation (the common case, since off-chain estimators cannot know the router's exact quote at execution time).

### Recommendation
Mirror the EVM `IntentGatewayV2.sol` fix in the Tron contract: capture the router's returned `amounts` array, decrement `msgValue -= amounts[0]` after the fee swap, and add a final `if (msgValue > 0) { (bool sent,) = msg.sender.call{value: msgValue}(""); if (!sent) revert InsufficientNativeToken(); }` before emitting `OrderPlaced`.

### Proof of Concept
1. User calls `placeOrder{value: 5 ether}(order, graffiti)` where `order.fees = X` (payable in native ETH) and the input tokens are ERC-20 (no native input consumed), so `msgValue` starts at `5 ether`.
2. `order.fees > 0` and `msgValue > 0`, so `swapETHForExactTokens{value: 5 ether}(X, path, address(this), deadline)` executes; the router only needs, say, `0.01 ether` to produce `X` fee tokens, and refunds `4.99 ether` back to `address(intentGateway)` (the caller of the router).
3. Function falls through directly to `emit OrderPlaced(...)` — `4.99 ether` remains in the contract's balance, uncredited to any order, unretrievable by the user (only sweepable by Hyperbridge governance via `SweepDust`, to an arbitrary beneficiary, not the original payer).
4. Compare against `evm/src/apps/IntentGatewayV2.sol` lines 353-368, which would correctly refund the `4.99 ether` to `msg.sender`. [3](#0-2) [4](#0-3)
