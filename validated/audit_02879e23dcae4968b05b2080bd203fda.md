### Title
`SignableTransaction::new` performs unchecked `u64` additions on input/payment sums, letting the "insufficient funds" check be bypassed by overflow so a transaction can commit outputs exceeding its inputs — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The reported Notional bug is a missing directional guard: `_finalize` enforced that a cash change could not push an account further into debt only on one path, so an already-negative balance could be made more negative. The Serai analog lives in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`, which is supposed to enforce "a transaction can never spend more than its inputs" but implements the guard with unchecked `u64` arithmetic. Both `payment_sat + needed_fee` (line 215) and `payment_sat + fee_with_change` (line 228) can overflow and wrap, defeating the `NotEnoughFunds` check — the exact analogue of allowing a balance to go further negative because the guard only handled the non-overflowing case.

### Finding Description
`SignableTransaction::new` computes totals with plain `u64` operations:

- `input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>()` — `send.rs:175`
- `payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>()` — `send.rs:187`
- `if input_sat < (payment_sat + needed_fee) { NotEnoughFunds }` — `send.rs:215`
- `if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change)` — `send.rs:228`

None of the additions are `checked_add`. The payment amounts come from the caller's `payments` slice, and the input values come from `ReceivedOutput`, which is deserializable from untrusted bytes via `ReceivedOutput::read` (`wallet/mod.rs:122-134`): `TxOut::consensus_decode` accepts any 64-bit value with no 21M-supply or plausibility bound, and `offset` is read via `Secp256k1::read_F`.

With crafted values (e.g., two payments of `u64::MAX/2 + 1` each, or one payment of `u64::MAX`), `payment_sat + needed_fee` wraps to a small value, the `input_sat < ...` comparison passes, and `new` returns `Ok` with `tx_outs` whose summed value vastly exceeds the real inputs. The wrapped sum then also feeds `input_sat.checked_sub(payment_sat + fee_with_change)`, which can yield `Some(huge)` and push a change `TxOut` with an absurd value (`send.rs:228-234`).

The resulting `SignableTransaction` is passed to `TransactionSignMachine::sign`, which computes Taproot sighashes over `Prevouts::All` (`send.rs:373-390`) and produces FROST signature shares for it. `SignableTransaction::fee()` (`send.rs:138-141`) also subtracts output sums from input sums with unchecked subtraction, so any fee accounting on this object underflows/panics.

### Impact Explanation
The invariant "a transaction cannot output more than its inputs" (the wallet-layer equivalent of "cannot push an account further into debt") is violated by arithmetic wraparound. Concretely:

1. The produced transaction is consensus-invalid (outputs > inputs), so any signatures generated for it are wasted and the plan it implements can never settle — the funds the scheduler believes are being moved are not moved.
2. The change-output math can emit a `TxOut` whose value bears no relation to real funds, corrupting downstream fee/change accounting (`fee()` underflow panic).
3. Because input values are attacker-influenced through `ReceivedOutput::read`, an unprivileged party feeding crafted output bytes into the wallet path can trigger the wrap without any privilege.

### Likelihood Explanation
Requires supply of inputs/payment amounts whose `u64` sums overflow — feasible whenever `ReceivedOutput` bytes or payment amounts originate from an untrusted source rather than the internal scanner (whose outputs mirror real chain values). Real on-chain UTXOs can't carry such values, so exploitation depends on the `read`/`from-bytes` path being reachable; severity is therefore Medium: accounting corruption and signing of an invalid transaction, but no direct key or signature compromise.

### Recommendation
Use `checked_add`/`checked_sum` for `input_sat`, `payment_sat`, `payment_sat + needed_fee`, and `payment_sat + fee_with_change`, returning `TransactionError::NotEnoughFunds` on overflow. Optionally sanity-bound each input `value` and each payment amount before summation, and make `fee()` use `checked_sub` to surface malformed transactions instead of panicking.

### Proof of Concept
```rust
// networks/bitcoin context; constructs a SignableTransaction whose
// outputs exceed inputs yet passes the NotEnoughFunds check.
let huge_input = ReceivedOutput {
    offset: Scalar::ZERO,
    output: TxOut {
        value: Amount::from_sat(u64::MAX - 1000), // attacker-supplied via ReceivedOutput::read
        script_pubkey: p2tr_script_buf(key).unwrap(),
    },
    outpoint: some_outpoint,
};
// Two payments whose sum wraps around u64
let payments = vec![
    (addr(), u64::MAX / 2 + 1),
    (addr(), u64::MAX / 2 + 1),
];
// payment_sat wraps to ~2; input_sat < payment_sat + needed_fee is false,
// so NotEnoughFunds is NOT returned even though outputs >> real spendable funds.
let res = SignableTransaction::new(vec![huge_input], &payments, None, None, FEE);
assert!(res.is_ok()); // guard bypassed; resulting tx is consensus-invalid
```
