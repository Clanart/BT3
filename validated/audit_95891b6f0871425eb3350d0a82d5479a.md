### Title
Unbounded aggregate-signature count in `SchnorrAggregate::read`/`verify` enables memory and CPU exhaustion from untrusted input - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` trusts a 32-bit count from the wire and loops `C::read_G` up to ~4.3 billion times with no maximum; `verify` then allocates `Vec::with_capacity(2*n + 1)` and runs a variable-time multiexponentiation over that unbounded set. This is the same bug class as CVE-2026-62963: a bounded length check (or none at all) applied to a wire field while the decoded/expanded object is consumed without an output cap.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`:

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }
    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
``` [1](#0-0) 

Two amplification properties make this worse than a plain proportional read:

1. Each 32-byte `R` element triggers `C::read_G`, which performs full point decoding/decompression and validity checks (for dalek-ff-group curves, subgroup/torsion-safe decompression costing orders of magnitude more CPU than the 32 input bytes). A modest stream of attacker bytes therefore generates large CPU work, analogous to a small compressed frame expanding to large decompressed work.

2. `verify` amplifies again: it preallocates `Vec::with_capacity((2 * keys_and_challenges.len()) + 1)` and calls `multiexp_vartime` over `2n+1` scalar-point pairs derived from the attacker-influenced `Rs`: [2](#0-1) 

There is no `MAX_AGGREGATE_LEN`, no comparison of `len` against remaining input, and no cap anywhere in `read`. Compare with sibling code that does bound allocations against a transaction-size limit (e.g., `DkgCommitments` checks `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT`); `SchnorrAggregate::read` has no equivalent guard.

### Impact Explanation
Any caller that passes untrusted bytes to `SchnorrAggregate::read` and then `verify` — e.g., deserializing an aggregate signature supplied by an external party for batch verification — lets an unauthenticated attacker cause:

- Allocation and growth of `Rs` up to the full input stream size, with each element expanded into an in-memory group element plus `C::read_G` decompression cost per 32 bytes.
- A second allocation of `2n+1` `(F, G)` pairs in `verify` and a `multiexp_vartime` over an arbitrarily large input — CPU and memory exhaustion proportional to attacker-supplied data with a large constant multiplier, matching the Medium-severity DoS class of the referenced advisory.

### Likelihood Explanation
Reachability requires an in-scope caller to feed untrusted bytes into `SchnorrAggregate::read`/`verify`. Within the audited crates the deserialization itself is public and unsanitized; any signing/verification path that accepts a serialized `SchnorrAggregate` from a non-trusted party (message data a party causes to be verified) reaches this code. The likelihood caveat: I could not fully confirm every in-scope production call site of `SchnorrAggregate::read` during this review, so the concrete exposure depends on the integrator path that deserializes aggregate signatures — but the vulnerable primitive is present and uncapped.

### Recommendation
- Cap the declared count before reading: `if len > MAX_AGGREGATE_SIGS { return Err(..) }` where `MAX_AGGREGATE_SIGS` reflects a protocol bound (e.g., number of validators).
- Reject `len` values inconsistent with the remaining input length (require `len` such that `len * C::G::Repr::LEN` fits the buffered/announced message size).
- In `verify`, bound `keys_and_challenges.len()` and `Rs.len()` before the `Vec::with_capacity` and `multiexp_vartime`.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to SchnorrAggregate::read
let mut bytes = vec![];
// Claim u32::MAX aggregate members
bytes.extend_from_slice(&u32::MAX.to_le_bytes());
// Followed by as many 32-byte "points" as desired; every 32 bytes costs a
// full C::read_G decompression/validation, and a successful read leaves an
// unbounded Vec<C::G> that verify() doubles into a multiexp input.
bytes.extend(std::iter::repeat([0u8; 32]).take(10_000_000).flatten());

let agg = SchnorrAggregate::<Ristretto>::read(&mut &bytes[..]).unwrap();
// verify() allocates Vec::with_capacity(2n+1) and runs multiexp_vartime
// over attacker-controlled size — CPU/memory exhaustion.
let _ = agg.verify(b"dst", &keys_and_challenges);
```
