## Analysis

The zAuction bug is about a reference update (`zauction` address) taking effect immediately, with no validation, allowing state to diverge and creating an unsafe transition between two "versions" of the trusted target. The closest GitHub Desktop analog is the automatic, unconfirmed rewrite of a repository's `git` remote URL driven directly by data returned from the GitHub API (an object fully controlled by whatever server answers the request — dotcom, a GHES instance, or an enterprise proxy sitting in front of it).

### How the update happens

`repositoryWithRefreshedGitHubRepository` runs on routine repository refresh and calls the GitHub API to re-fetch the associated repository, then unconditionally calls `updateRemoteUrl` with whatever `apiRepo` is returned: [1](#0-0) 

`updateRemoteUrl` decides to silently call `gitStore.setRemoteURL(...)` based only on: protocol-family match (https/https or ssh/ssh) and "the user hasn't hand-edited the remote away from what was last cached from the API": [2](#0-1) 

Crucially, `urlMatchesRemote`, which decides whether the URLs are already "the same" and therefore whether an update is needed, only compares hostname/owner/name of the two parsed URLs against each other — it never pins the new URL's hostname to the account's own trusted endpoint (`account.endpoint` / `getHTMLURL(account.endpoint)`): [3](#0-2) 

So if the API response's `clone_url` names a different hostname than the current remote (e.g. `https://evil.example/owner/repo.git`), `urlsMatch` becomes `false`, `protocolsMatch` is still `true` (both `https:`), `remoteUrlUnchanged` is `true` for the common case of an untouched, desktop-managed remote, and the code path proceeds to call `setRemoteURL`, rewriting the local `origin` (or default remote) to the attacker-chosen host with no host allow-list check and no user confirmation: [4](#0-3) 

### Title
Unvalidated remote-URL rewrite from GitHub API repository data allows silent push/fetch redirection - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` rewrites a repository's local git remote URL automatically, based solely on the `clone_url` field of a `GitHubRepository`/`IAPIRepository` object obtained from the configured GitHub endpoint, without ever confirming that the new URL's hostname belongs to that same trusted endpoint. Any GitHub API response (from GitHub.com, a GHES instance, or anything answering as one) that supplies a different-hostname `clone_url` for the same owner/repo pair causes Desktop to silently repoint the user's git remote to an attacker-controlled host on the very next repository refresh.

### Finding Description
`repositoryWithRefreshedGitHubRepository` (invoked during normal repository refresh flows) fetches the repository via `API.fromAccount(account).fetchRepository(owner, name)` and immediately hands the result to `updateRemoteUrl` for the tracked repository's default remote: [5](#0-4) 

`updateRemoteUrl`'s only gates are:
1. `protocolsMatch` — both old and new URL use the same protocol family (or both are SSH-style with no explicit scheme).
2. `remoteUrlUnchanged` — the *current* remote URL still matches the *previously cached* `GitHubRepository.cloneURL` (true for any repository the user hasn't manually re-pointed).
3. `!urlsMatch` — the new `clone_url` differs from the current remote.

None of these validate that the new `clone_url`'s hostname corresponds to the account's own endpoint (`account.endpoint`/`getHTMLURL(account.endpoint)`), which is exactly the check `matchGitHubRepository` uses elsewhere to bind a remote to an account. `urlMatchesRemote`, reused here to compute `urlsMatch`, deliberately just compares the two URLs to each other, not either of them to a trusted allow-list: [6](#0-5) 

Consequently, whichever server answers `fetchRepository` fully controls the destination the app will start pushing to and fetching from, with no user-visible prompt — analogous to `zAuctionAccountant.SetZauction` applying an admin-supplied address update immediately and without re-validating the new target, letting stale/parallel state (old vs. new remote target) diverge silently.

### Impact Explanation
If a malicious or compromised GitHub Enterprise Server (or any endpoint the app is configured to trust, including a compromised network intermediary answering as that endpoint) returns a repository object whose `clone_url` points at an attacker-controlled host, Desktop will silently reconfigure the user's `origin` remote to that host on the next background refresh. Subsequent `git push` operations (`performPush` uses `state.remote`/`branch.upstreamRemoteName`, sourced from the rewritten remote) send the user's code to the attacker's server, and subsequent fetches/pulls bring in attacker-supplied history the user may believe is legitimate upstream content — this is "silent corruption of what the user commits or pushes" as defined in scope, achieved purely via a GitHub API object under attacker control.

### Likelihood Explanation
The refresh path (`repositoryWithRefreshedGitHubRepository`) runs routinely as part of normal repository refresh, not behind any special user action, so exploitation requires no unusual user steps beyond having Desktop open with the repository tracked — the trigger is purely server-side response content. The main precondition is control over (or the ability to tamper with) the API response for a `fetchRepository` call to the configured endpoint, which is plausible for a compromised/malicious GHES instance or an on-path actor able to answer as that endpoint; this matches the allowed "a git remote/proxy response" / "a GitHub API object" attacker model.

### Recommendation
When automatically updating a remote URL from GitHub API data, additionally verify that the new `clone_url`'s hostname matches the hostname of the account's own configured endpoint (as `matchGitHubRepository` already does when initially associating a remote with an account) before calling `setRemoteURL`. If the hostname differs, treat it as a repository transfer/migration event requiring explicit user confirmation rather than a silent update, consistent with the report's recommendation to avoid keeping two divergent trusted targets active without an explicit, validated transition.

### Proof of Concept
1. Add a repository in Desktop whose `origin` remote and cached `GitHubRepository.cloneURL` both point at `https://github.example.com/owner/repo.git` (a GHES endpoint the user is signed into).
2. Compromise or spoof a response from that endpoint's `fetchRepository` API call (`GET /repos/owner/repo`) such that `clone_url` is `https://evil.example.com/owner/repo.git` (same protocol family, different hostname).
3. Wait for/trigger a repository refresh (e.g. switching repositories or focusing the app), invoking `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`.
4. Observe that `protocolsMatch` is `true`, `remoteUrlUnchanged` is `true` (remote hasn't been hand-edited), and `urlsMatch` is `false` (different hostname), so `gitStore.setRemoteURL('origin', 'https://evil.example.com/owner/repo.git')` executes with no prompt.
5. Confirm via `git remote -v` in the repository that `origin` now points at `evil.example.com`, and that a subsequent push in Desktop targets that host.

  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // clone url retrieved from the GitHub API previously

    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

  public async setRemoteURL(name: string, url: string): Promise<boolean> {
    const wasSuccessful =
      (await this.performFailableOperation(() =>
        setRemoteURL(this.repository, name, url)
      )) === true
    await this.loadRemotes()

    this.emitUpdate()
    return wasSuccessful
  }
