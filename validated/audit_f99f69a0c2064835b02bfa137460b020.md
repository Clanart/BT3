## Analysis

The external report's core broken invariant is: **native-ETH payment paths were bolted onto ERC-20 transfer logic without properly capturing/returning the correct value flow, causing funds sent as native ETH to be mishandled** (either lost or unable to reach their destination). The strongest local analog in Hyperbridge is in the fee-swap path of `EvmHost.dispatch()`, which is used by every app contract (`HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken(Upgradeable)`) to pay relayer fees in native ETH.

### Title
Excess native ETH sent to `EvmHost.dispatch()` for fee-swap is permanently stranded, not refunded to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` swap the caller's entire `msg.value` for an *exact* amount of fee token (`post.fee`/`get.fee`) via `swapETHForExactTokens`, with the swap's `to` parameter set to `address(this)` (the `EvmHost` contract itself). Any ETH left over after the exact-output swap is refunded by the Uniswap V2 router to `msg.sender` of the swap call — which is `EvmHost`, not the original app/user. `EvmHost.dispatch()` never forwards this refund back to the caller. ### Finding Description

`swapETHForExactTokens` sends `msg.value` ETH to the router but only consumes the amount needed to buy exactly `post.fee` of `feeToken()`; the router refunds the unspent ETH to its `msg.sender`. Because `EvmHost` itself calls the router, that refund lands in `EvmHost`'s own balance, not in the calling contract's balance. `EvmHost.dispatch()` contains no logic to capture this refund and forward it to `_msgSender()` (the app contract) or the end user.

Callers such as `WrappedHyperFungibleTokenUpgradeable.send()`, `HyperFungibleToken.send()`, `HyperFungibleTokenUpgradeable.send()`, and `WrappedHyperFungibleToken.send()` forward their *entire remaining* `msg.value` into this call with no subsequent refund step of their own:

There is no way for the caller (or the underlying user) to know the exact ETH price of `post.fee` at the moment the swap executes on-chain — the AMM price can move between when a user calls `quote()`/estimates the fee off-chain and when their transaction is mined, so any conservative buffer or slippage protection a caller sends is unrecoverable. This is exactly the class of bug flagged in the external report: value paths for native ETH are handled asymmetrically from the ERC-20 path, and the code fails to explicitly return unspent native value to its rightful owner.

By contrast, `IntentGatewayV2.placeOrder()` performs the identical swap *itself* (`to: address(this)` = the gateway, not the host) and explicitly tracks and refunds any unspent `msgValue` to `msg.sender` at the end of the function, proving the codebase is aware refunds are required — but this discipline was not applied inside `EvmHost.dispatch()`/`dispatch(DispatchGet)`. [3](#0-2) [4](#0-3) 

### Impact Explanation
Any unprivileged user who calls `send()` on `WrappedHyperFungibleTokenUpgradeable`, `HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, or `WrappedHyperFungibleToken` (or any other `IApp` that calls `IDispatcher.dispatch{value: X}` and forwards more ETH than the exact swap requires) permanently loses the difference between the ETH sent and the ETH actually consumed by the exact-output swap. The stranded ETH accumulates in `EvmHost` with no accounting, no event, and no function visible in the excerpted code to return it to the depositor — it is effectively silently expropriated from ordinary users on every native-fee bridge transfer. This matches the bounty's "stealing or loss of funds" impact category, is triggered purely through the intended, documented "pay fees in native ETH" flow, and requires no malicious relayer, prover, or admin.

### Likelihood Explanation
High. This occurs on every ordinary `send()` call that pays fees in native ETH whenever the AMM price at execution time is even slightly better than the price used to size `msg.value` (which is unavoidable given normal price movement and the fact that users must send some ETH ahead of execution). It requires no attacker action — it fires on completely benign, expected usage of the bridge's public token-transfer entrypoints.

### Recommendation
In `EvmHost.dispatch(DispatchPost)` and `dispatch(DispatchGet)`, capture the ETH balance before/after the swap (or check `address(this).balance` delta) and refund any leftover native ETH back to `_msgSender()` (the calling contract), mirroring the refund pattern already used in `IntentGatewayV2.placeOrder()`. Alternatively, require callers to pass an exact/quoted amount and revert on overpayment, or expose a native-ETH sweep/refund accessor keyed to `_msgSender()`.

### Proof of Concept
1. A user calls `WrappedHyperFungibleTokenUpgradeable.send{value: params.amount + X}(params)` where `X` is an ETH buffer intended to cover the relayer fee (`post.fee`), sized using an off-chain `quote()` estimate.
2. `send()` wraps `params.amount` into WETH and forwards `msgValue = X` to `IDispatcher(_host).dispatch{value: X}(request)`. [5](#0-4) 
3. Inside `EvmHost.dispatch()`, `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` is called; suppose only `Y < X` ETH is needed to buy `post.fee` of `feeToken()` at the current pool price. [1](#0-0) 
4. The router refunds `X - Y` ETH to `msg.sender` of the swap call, i.e., to `EvmHost`. `EvmHost.dispatch()` never forwards this amount anywhere; it silently increases `EvmHost`'s native balance.
5. The user's transaction completes successfully (fee paid, message dispatched), but `X - Y` ETH is unrecoverable by the user — no refund event, no accounting slot, no callable function shown to reclaim it.
