### Title
Unvalidated type assertion on attacker-controlled CosmWasm query response fields crashes EVM tx processing — (File: precompiles/pointer/pointer.go)

### Summary
The `pointer` precompile's `AddCW20`, `AddCW721`, and `AddCW1155` handlers query an arbitrary, caller-specified CosmWasm contract (`token_info`/`contract_info`) and then directly type-assert the returned JSON fields `name`/`symbol` to `string` without checking the "ok" form of the assertion, mirroring the CVE-2024-49860 root cause of trusting an externally-returned value's type without validation.

### Finding Description
`AddCW20` calls `p.wasmdKeeper.QuerySmartSafe(ctx, cwAddress, []byte("{\"token_info\":{}}"))` against `cwAddr`, an address fully controlled by the caller (any EVM transaction sender), then unmarshals the response into `map[string]interface{}{}` and performs: [1](#0-0) 
`name := formattedRes["name"].(string)` and `symbol := formattedRes["symbol"].(string)` are single-value type assertions. If the target contract's `token_info`/`contract_info` query response omits the `name`/`symbol` keys, or returns them as a non-string JSON type (number, bool, object, array, null), `formattedRes["name"]` will be `nil` or a non-string `interface{}`, and the assertion panics ("interface conversion: interface {} is nil, not string" or "... is float64, not string").

The same unchecked pattern repeats in `AddCW721` [2](#0-1)  and `AddCW1155` [3](#0-2) , and is present across all versioned legacy copies of this precompile (`precompiles/pointer/legacy/v552` through `v640`), matching the `formattedRes[...]` grep hits found in those files.

This is directly analogous to the ACPI `_STR` bug class: a subsystem trusts that an externally-produced object (there, an ACPI `_STR` return value; here, a CosmWasm contract's query JSON response) has a specific type, and dereferences/casts it without validating the type first, leading to invalid access (there, memory access; here, a Go runtime panic).

Because `cwAddr` is any CosmWasm contract address supplied by the transaction sender, a malicious or malformed CW20/CW721/CW1155 contract (which the same attacker can deploy via `MsgInstantiateContract`) can return a `token_info`/`contract_info` response with a non-string or missing `name`/`symbol` field, e.g. `{"name": 123, "symbol": null, ...}`, and then call `addCW20Pointer(cwAddr)` (or the CW721/CW1155 equivalents) through the EVM pointer precompile at `0x000000000000000000000000000000000000100b`.

### Impact Explanation
A Go type-assertion panic inside `PrecompileExecutor.Execute` propagates up through the precompile `Run` call during EVM message execution. Unless caught by a `recover()` somewhere in the EVM execution/ante pipeline, this panic will crash the node process handling the transaction (in `DeliverTx`/`CheckTx` and, more importantly, in `eth_estimateGas`/`eth_call`-style JSON-RPC handling paths on any node, including public RPC nodes), because any account can trigger it with a single transaction after deploying a trivial malicious wasm contract. If it is caught by a top-level recover and converted into a panic-error (as is common in Cosmos SDK `runTx`), the impact reduces to a failed transaction rather than a crash — I was not able to fully verify whether such a top-level recover wraps precompile execution specifically (I found only test-file and `x/evm/keeper/msg_server.go` recover references, but did not have iterations left to inspect that recover's exact scope). If the panic is NOT contained (e.g., during `eth_call`/`eth_estimateGas` served synchronously by a public RPC node), this is a low-cost crash of default-configuration RPC nodes, satisfying the report's "crash of default-configuration RPC nodes" impact bar.

### Likelihood Explanation
High reachability: any account can deploy a CosmWasm contract whose `token_info`/`contract_info` query handler returns a JSON object without the `name`/`symbol` string fields (or with them typed incorrectly), and then invoke `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` on the `pointer` precompile via a normal EVM transaction. No special privileges, governance, or validator collusion is required — it is a single, cheap, self-contained transaction from an unprivileged EVM/CosmWasm user.

### Recommendation
Replace all unchecked type assertions on `formattedRes["name"]`/`formattedRes["symbol"]` in `AddCW20`, `AddCW721`, and `AddCW1155` (and their versioned legacy copies) with the two-value form (`name, ok := formattedRes["name"].(string)`) and return a descriptive error (rather than panicking) when the field is absent or of the wrong type, analogous to validating the `_STR` return type in the referenced kernel fix before use.

### Proof of Concept
1. Deploy a CosmWasm contract whose `token_info` query handler returns `{"name": 123, "symbol": null, "decimals": 6, "total_supply": "0"}` (an invalid but syntactically valid CW20 `TokenInfoResponse` payload).
2. From an EVM account, call the `pointer` precompile at `0x000000000000000000000000000000000000100b` method `addCW20Pointer(cwAddr)` with `cwAddr` set to the malicious contract's bech32 address.
3. Execution reaches: [4](#0-3) 
4. `formattedRes["name"].(string)` panics with an interface-conversion error because the value is `float64`, not `string` (and `formattedRes["symbol"].(string)` would panic on `nil`).
5. Observe whether the panic is caught by any surrounding recover; if uncaught in the RPC/tx-processing path, the node process serving that request crashes.

*(Note: I could not fully confirm within available iterations whether a top-level `recover()` in `x/evm/keeper/msg_server.go` or elsewhere in the ante/EVM pipeline catches this specific panic before it reaches process level — this should be verified directly in a live/test environment before treating the crash impact as certain rather than a caught-panic/tx-revert.)*
