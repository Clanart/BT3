Based on the investigation, I found a genuine local analog, but it also revealed that the codebase's protected pattern (atomic ERC1967Proxy init) is *not* used everywhere — the core `EvmHost` deployment uses the exact vulnerable two-step pattern the external report warns about.

### Title
`EvmHost.initialize()` deployed as a separate transaction after construction, enabling front-run hijack of host params - (File: `evm/script/DeployIsmp.s.sol`, `evm/src/core/EvmHost.sol`)

### Summary
`DeployIsmp.s.sol` deploys `EvmHost` via a bare constructor call and only afterward calls `host.initialize(params)` in a second, separate statement/transaction, exactly the deploy-then-initialize split flagged in the external `EnsoWalletFactory` report. [1](#0-0) 
This contrasts with the atomic pattern already used elsewhere in this same repo for `IntentGatewayV2` and `SimplexPaymaster`, where `initialize` is baked into the `ERC1967Proxy` constructor call so init data is bound to the deployment transaction itself. [2](#0-1) [3](#0-2) 

### Finding Description
`EvmHost` (or `TestnetHost`) is deployed with `new EvmHost{salt: salt}(admin)`, then `host.initialize(params)` is invoked as a distinct call. [4](#0-3) 
`HostParams` sets critical bridge-trust parameters — `consensusClient`, `hostManager`, `handler`, `challengePeriod`, `hyperbridge` (the trusted coprocessor identity), and `feeToken` — every one of which underpins consensus-proof validation, request/response dispatch, and fee custody for the entire bridge. [5](#0-4) 
If `initialize` has no `onlyAdmin`/deployer-bound gating (the same class of defect the external report calls out for `EnsoWalletFactory.initialize()`), any address that observes the pending/mined constructor transaction can front-run the second `initialize` call and supply attacker-controlled values for `consensusClient` or `hyperbridge`, letting a forged consensus client or forged coprocessor source pass the host's own trust checks — i.e., false remote state and message-origin authenticity would be compromised at the root.

Whether this is actually exploitable depends on `EvmHost.initialize()`'s access control, which the available index snippets did not show; that part is unverified with the tools available (the file may not be fully indexed, or the guard may exist but wasn't returned by search). Given the index size limits noted, a Devin session with full file access is needed to confirm whether `initialize()` is unguarded or restricted to `msg.sender == admin`/deployer.

### Impact Explanation
If `EvmHost.initialize()` lacks a strict caller/one-shot binding to the deployment transaction, an attacker front-running it could seed the host with a malicious `consensusClient` (breaking state-commitment trust for every subsequent proof verification) or a spoofed `hyperbridge` identity (breaking module/source authentication for all cross-chain requests), enabling false proof/state acceptance and unauthorized cross-chain execution across the entire deployed bridge instance — a critical, protocol-wide compromise rather than a single-contract issue.

### Likelihood Explanation
Exploitation requires only observing a public deployment transaction and submitting a second transaction before the legitimate `initialize` call lands — no relayer, prover, or governance compromise needed, matching the "public entrypoint, unprivileged attacker" requirement. Likelihood is contingent entirely on the (unverified) access-control state of `EvmHost.initialize()`; if it is properly restricted (e.g., `onlyAdmin`), this reduces to a non-issue, same as how `IntentGatewayV2`/`SimplexPaymaster` mitigate it via atomic CREATE2+initData rather than caller checks.

### Recommendation
Confirm and, if needed, harden `EvmHost.initialize()` (and `TestnetHost`) to either (a) restrict the call to the immutable `admin` set in the constructor, or (b) refactor the deployment to bind initialization atomically to construction/proxy-creation the same way `IntentGatewayV2` and `SimplexPaymaster` already do via `ERC1967Proxy(implementation, initData)`, so no window exists between deployment and parameter-setting.

### Proof of Concept
1. Attacker monitors mempool/mined blocks for `new EvmHost{salt}(admin)` from `DeployIsmp.s.sol`'s deployment flow. [6](#0-5) 
2. Before the legitimate `host.initialize(params)` transaction confirms, attacker submits their own `initialize(HostParams({consensusClient: attackerConsensusClient, hyperbridge: attackerId, ...}))` call against the same freshly-deployed `EvmHost` address (deterministic via CREATE2, so the attacker can predict and prepare this call before deployment even completes).
3. If `initialize()` is not restricted to `admin`, the attacker's parameters are accepted, and the legitimate call from `DeployIsmp.s.sol` line 134 either reverts (if `initialize` is single-shot) or is itself front-run, leaving the host trusting an attacker-supplied consensus client/coprocessor identity.
4. This needs to be confirmed against the actual `EvmHost.initialize()` implementation, which was not available in the indexed snippets — recommend a full-repo Devin session to inspect `evm/src/core/EvmHost.sol`'s `initialize` function body directly.
