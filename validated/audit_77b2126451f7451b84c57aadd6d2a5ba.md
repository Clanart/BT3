### Title
Rule loader binds to `os.getcwd()` instead of the trusted project root, allowing cwd-drift to load attacker-controlled `.claude/hookify.*.local.md` rules - (File: plugins/hookify/core/config_loader.py)

### Summary
`load_rules` resolves its rule-file glob with a bare relative path `os.path.join('.claude', 'hookify.*.local.md')` passed to `glob.glob`, which is always resolved against the process's current working directory rather than any fixed, validated project root. Since every hookify hook (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) calls `load_rules()` with no path argument, whatever directory the hook process happens to be running in at invocation time determines which `.claude/` rules get loaded and enforced for the session.

### Finding Description
`load_rules` in [1](#0-0)  builds its search pattern purely from a relative path and calls `glob.glob(pattern)` with no `root_dir` argument and no reference to a known-good project root (e.g. `CLAUDE_PROJECT_DIR`), unlike `CLAUDE_PLUGIN_ROOT`, which is explicitly consumed elsewhere to anchor plugin import paths, e.g. in [2](#0-1) . The hook entry points then call `load_rules(event=event)` with no override of the directory, as seen in [3](#0-2)  and [4](#0-3) .

Because the resolved rule set feeds directly into `RuleEngine.evaluate_rules`, which drives warn/block enforcement for every Bash/Edit/Write/MultiEdit tool call, whichever `.claude/hookify.*.local.md` files happen to be reachable relative to `os.getcwd()` at hook-invocation time become the enforcement policy for the entire session — with no check that this directory is the same one the user opened Claude Code in.

### Impact Explanation
If the working directory used to launch the hook subprocess drifts away from the trusted project root — e.g., a CI step or wrapper script `cd`s into a nested submodule/subrepo checkout before the hook fires, or a monorepo has multiple `.claude` directories at different nesting levels — an attacker who can place files at that alternate location can inject `hookify.*.local.md` rules that silently downgrade `action: block` rules to `warn`, or plant additional `warn`/`block` rules with attacker-chosen regex/messages that get rendered as `systemMessage` back to the model/user. This is a workspace/session-binding violation: rule enforcement is not scoped to the approved project root, only to ambient process state.

### Likelihood Explanation
Exploitability depends entirely on an operator, wrapper script, or CI pipeline invoking the hook with a `cwd` different from the intended project root (e.g., after a `cd` into a submodule). Standard interactive Claude Code usage keeps `cwd` equal to the opened project directory, so this is not exploitable purely from repository content alone; it requires an automation/CI misconfiguration or an attacker-controlled build step that changes directory before hook invocation. Given that scope, likelihood is low-to-moderate and tied to non-standard invocation environments rather than default usage.

### Recommendation
Anchor `load_rules` to a validated project root instead of `os.getcwd()`: prefer `CLAUDE_PROJECT_DIR` (already used elsewhere in the plugin for `CLAUDE_PLUGIN_ROOT`) if Claude Code exposes an equivalent for the workspace root, or accept an explicit `project_root` parameter threaded from the hook's input payload, and use `glob.glob(pattern, root_dir=project_root)` (or `os.path.join(project_root, ...)`) so rule discovery cannot be influenced by transient cwd state.

### Proof of Concept
Integration test plan:
1. Create two directories, `trusted_project/.claude/hookify.a.local.md` (benign rule) and `other_dir/.claude/hookify.evil.local.md` (rule with `action: block` and attacker message).
2. Call `load_rules()` with `os.chdir('trusted_project')` and assert only `hookify.a.local.md` rule is returned.
3. Call `load_rules()` again after `os.chdir('other_dir')` (simulating cwd drift) and assert the evil rule from `other_dir/.claude` is now loaded and would be enforced — demonstrating the loader is bound to `os.getcwd()` rather than a fixed trusted project root, i.e. `load_rules()` returns different, non-project-scoped rule sets purely based on ambient process cwd rather than the actual opened workspace.
