## Title
Partial-commit line selection is re-applied to a freshly re-read diff, allowing a changed file to silently corrupt what gets staged/committed - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages a *partial* selection of lines in a file (some added/removed lines checked, others not), GitHub Desktop stores that selection purely as a set of **line indices** (`DiffSelection`), computed against the diff that was rendered in the UI at selection time. When the commit is actually created, `applyPatchToIndex` re-fetches the diff from disk a second time and re-applies the *old* index-based selection to this *new* diff, rather than reusing the diff the user actually reviewed. [1](#0-0) 

### Finding Description
The root cause mirrors the reported bug class exactly: a piece of state (here, the user's line-level selection, computed against diff version A) is later combined with a *different*, re-fetched version of the underlying data (diff version B) without re-validating that the indices still correspond to the same content.

`formatPatch` builds the patch purely by indexing into `diff.hunks` and checking `file.selection.isSelected(absoluteIndex)`: [2](#0-1) 

`applyPatchToIndex` is the call site that performs the unsafe combination — it fetches a brand-new diff from disk and hands it, together with the pre-existing `file.selection`, to `formatPatch`: [1](#0-0) 

The codebase itself acknowledges that diffs can change out from under a stale selection. In `updateChangesWorkingDirectoryDiff`, when the UI re-loads a diff, the comment explicitly states: [3](#0-2) 

That reconciliation logic only prunes indices that no longer exist or became context lines — it runs when the *UI* reloads a diff. It does **not** run again at commit time inside `applyPatchToIndex`/`stageFiles`, which independently re-reads the file from disk via `getWorkingDirectoryDiff` and blindly reuses whatever `DiffSelection` is attached to the `WorkingDirectoryFileChange` passed into `_commitIncludedChanges`: [4](#0-3) 

If the tracked file's content changes between when the diff was rendered/selected in the UI and the moment `createCommit` → `stageFiles` → `applyPatchToIndex` executes (e.g., due to a background status refresh, an external process, or content written back by another git operation running concurrently), the hunk boundaries and absolute line indices can shift. `file.selection.isSelected(absoluteIndex)` then answers against the *wrong* lines of the *new* diff, so `formatPatch` can include lines the user never selected, or drop lines the user did select — with no warning to the user and no re-validation of selection line ranges against the newly fetched diff's actual line content.

### Impact Explanation
This directly matches the report's "silent corruption of what the user commits or pushes" impact category: a bondholder-equivalent invariant here is "the bytes staged for commit == the bytes the user visually selected." Because the staged patch is built from indices resolved against a diff the user never saw, a user could unknowingly commit and push content different from what they reviewed and approved in the Changes view — e.g., partially reverting a security fix, re-including a line the user explicitly deselected, or committing content injected by a concurrently running process, without any diff-mismatch error being surfaced.

### Likelihood Explanation
Requires a timing window between diff render/selection and commit execution during which the working-tree file content changes — plausible via GitHub Desktop's own periodic background repository refresh (`_refreshRepository`) racing with user-driven partial staging/commit, or any other process (editor autosave, external tool, git hook) touching the file. No local/admin access or leaked credentials are needed; the only requirement is a file whose content is not static during the selection→commit window, which the app's own background refresh cycle can itself trigger.

### Recommendation
Before calling `formatPatch` inside `applyPatchToIndex`, re-validate (or re-derive) the selection against the freshly fetched diff — e.g., reuse the same "prune/rebuild selectable lines" logic already implemented in `updateChangesWorkingDirectoryDiff` — and fail/abort the partial-stage operation (rather than silently proceeding) if the diff has changed materially since the selection was made, surfacing this to the user instead of silently applying stale indices to new content.

### Proof of Concept
1. Open a repository in GitHub Desktop with a tracked file containing several lines.
2. In the Changes view, select a subset of added/removed lines for a partial commit (leaving the rest unselected).
3. Before clicking "Commit", have another process (or a concurrent Desktop background refresh combined with an external edit) modify the same file so the diff hunks/line offsets shift.
4. Click "Commit" — `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` fetches the diff fresh via `getWorkingDirectoryDiff` (`app/src/lib/git/apply.ts:60`) and applies the old `file.selection` indices to it via `formatPatch` (`app/src/lib/patch-formatter.ts:129-157`).
5. Inspect the resulting commit: it can include/exclude lines the user never intended, differing from what was displayed and selected in the UI at selection time.
