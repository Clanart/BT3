### Title
Unclaimed reward tokens sitting in `ManualCompound` can be swept and stolen by any caller of `compound()` - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` determines the amount of each reward token to process by reading the contract's total `balanceOf(address(this))` instead of tracking the amount actually claimed by the calling user in that transaction. Any ERC20 balance sitting in the contract - whether from rounding dust, a partially-processed prior interaction, or tokens sent to the contract outside of a user's own claim - is swept in full to whichever address calls `compound()` next.

### Finding Description
`compound()` first claims a caller-selected set of rewards via `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)`, which transfers the claimed reward tokens into the `ManualCompound` contract itself. [1](#0-0) 

For non-compoundable rewards explicitly listed in the caller's `_rewards` array, the function reads `IERC20(_rewards[i][j]).balanceOf(address(this))` and forwards the *entire* balance to `msg.sender`: [2](#0-1) 

For every globally-registered compoundable reward token, the function again reads `receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))` — the whole contract balance for that token, not the amount just claimed on the caller's behalf — and routes it to a converter/locker/helper or transfers it directly to `msg.sender`: [3](#0-2) 

This mirrors the root cause of the referenced H-01 finding: the contract computes the payout by inspecting its own token balance rather than the amount attributable to the specific caller/action, so any leftover balance in the contract (e.g., rounding dust left behind by a prior `convertFor`/`lockFor`/`depositFor` call, or tokens transferred into the contract by any third party) is not segregated per user and gets fully swept to whoever calls `compound()` next — even with an empty `_lps`/`_rewards` array that claims nothing new.

### Impact Explanation
Any unprivileged wallet can call `compound()` and receive reward tokens (WOM/mWOM/MGP/etc.) that were never claimed by them, as long as some balance of a tracked reward token is present in the `ManualCompound` contract at call time. This is a direct theft of other users' unclaimed yield/reward tokens, satisfying the "theft of unclaimed yield" / "direct theft of user funds" impact bar.

### Likelihood Explanation
The attack requires no special privileges — any address can call the external `compound()` function at any time, including with empty `_lps`/`_rewards` arrays. Because payouts for the compoundable-token loop are calculated purely from `balanceOf(address(this))`, the presence of any leftover balance (dust from `_convertFor`/`lockFor`/`depositFor` rounding, or accidental/incidental transfers into the contract) is a realistic, low-effort trigger, making exploitation straightforward for an attacker who simply monitors the `ManualCompound` contract's token balances and front-runs/calls right after such a balance appears.

### Recommendation
Track and process only the amount of each reward token actually received/claimed within the current `compound()` invocation (e.g., by measuring the balance delta immediately before and after `multiclaimOnBehalf`, per token, rather than using the absolute `balanceOf(address(this))`), and refund/sweep any truly unattributable leftover balance to a protocol-controlled address instead of to the arbitrary caller.

### Proof of Concept
1. Assume, due to a rounding remainder from a previous `compound()` call's `IConverter.convertFor` (which computes `obtainedmWomAmount = convertAmount + amountRec` and may leave a few wei of the reward token in `ManualCompound` because `receivedBalance` used for `safeApprove`/`convertFor` does not perfectly net to zero after downstream rounding), or from an unrelated direct transfer, a nonzero balance of a compoundable reward token (say WOM) sits in `rewards/ManualCompound.sol`.
2. Attacker (unprivileged wallet) calls `compound(_lps = [], _rewards = [[]], _convertRatio, _minRec = 0, _lockMgp = false)`.
3. `multiclaimOnBehalf([], [], msg.sender)` claims nothing new for the attacker, so the first loop does nothing (`_lps.length == 0`). [1](#0-0) 
4. The second loop iterates over the globally registered `rewards` array and computes `receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))`, which now returns the leftover WOM balance belonging to previous, unrelated users.
5. Since `receivedBalance > 0`, the WOM is routed via `IConverter(_convertor).convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2)` (or `safeTransfer` if no convertor is set) with `msg.sender` = the attacker, transferring the leftover tokens to the attacker despite them having claimed nothing. [4](#0-3)

        uint256 rewardTokensLength = rewards.length;        
        IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender);
        // send none compoundable reward back to caller
        for(uint256 i; i < _lps.length; i++) {
            uint256 rewardLength = _rewards[i].length;
            if (rewardLength > 0) {
                for (uint j; j < rewardLength; j++) {
                    if (!compoundableRewards[_rewards[i][j]]) {
                        uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
                        if (rewardBalance > 0)
                            IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
                    }
                }
            }
        }
