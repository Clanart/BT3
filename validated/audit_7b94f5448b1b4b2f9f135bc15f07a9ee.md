## Analysis

The report's broken invariant is: **a fixed-format assumption (18-decimal base token) is applied to data that can arrive in a different, attacker/environment-controlled format (6-decimal USDC/USDT), producing a silently wrong calculated value that downstream logic trusts.**

The Desktop analog is the hard-coded UTF-8 decoding of raw git diff output in `diffFromRawDiffOutput`, which is later trusted verbatim when reconstructing the patch that is actually applied to the git index for partial commits.

### Title
Hard-coded UTF-8 decoding of diff output can silently corrupt partially-staged commit content - (File: `app/src/lib/git/diff.ts`)

### Summary
`diffFromRawDiffOutput` always decodes the raw `Buffer` returned by `git diff`/`git log --patch` as UTF-8, regardless of the actual encoding of the file(s) being diffed, and explicitly documents this as a known simplification. [1](#0-0) 

### Finding Description
`getWorkingDirectoryDiff` and `getCommitDiff` invoke `git` with `encoding: 'buffer'` and hand the raw `Buffer` to `diffFromRawDiffOutput`, which converts it to a JS string via `output.toString('utf-8')` with a comment acknowledging "for now we just assume the diff is UTF-8, but given we have the raw buffer we can try and convert this into other encodings in the future". [2](#0-1) [3](#0-2) 

`Buffer.toString('utf-8')` never throws on invalid byte sequences; it silently substitutes the Unicode replacement character (U+FFFD) or otherwise mis-decodes multi-byte sequences that are valid in other encodings (UTF-16, Shift-JIS, GBK, Latin-1 with high bytes, etc.). The resulting string is fed into `DiffParser.parse`, which slices it into `DiffLine.text` values purely by scanning for `\n`/prefix characters. [4](#0-3) 

Those `DiffLine.text` strings are exactly what the UI renders for line-by-line selection, and — critically — exactly what `formatPatch`/`formatPatchToDiscardChanges` re-emit verbatim to build a new unified-diff patch that is piped to `git apply --cached` in `applyPatchToIndex`. [5](#0-4) [6](#0-5) 

Because the decode step already lost or altered byte-level fidelity, the reconstructed patch text no longer matches the original bytes on disk. `git apply` will then either apply a corrupted hunk (writing mangled bytes into the index/commit) or fail outright depending on how badly the byte/char alignment was disturbed — there is no re-validation against the original raw bytes anywhere in this path. This exactly mirrors the report's core defect: a component assumes one fixed representation (UTF-8, analogous to 18-decimals) for a value that can legitimately arrive in another representation (a non-UTF-8 encoding, analogous to 6-decimal USDC/USDT), and that unchecked assumption propagates into a value that is later trusted as authoritative (the applied patch / minted `amountOut`).

### Impact Explanation
When a user performs **line-level (partial) staging** on a file whose on-disk bytes are not valid UTF-8 (a common case: files encoded as UTF-16, Shift-JIS, GBK, or containing legacy Latin-1 content, which routinely appear in real-world repositories, especially ones containing non-English text or files authored on Windows), the patch built from the mis-decoded `DiffLine.text` can differ from the user's actual working-directory bytes. This is a **silent corruption of what the user commits**: the file staged/committed may contain replacement characters, truncated/duplicated content, or bytes that don't match what was on disk or what was rendered as "selected" in the UI, without any error or warning. This satisfies the "silent corruption of what the user commits or pushes" impact category, and requires no local/admin access — it's triggered by ordinary use of the app's core diff/stage/commit workflow on a repository containing non-UTF-8 text files, something an attacker publishing a shared repository with such files can force upon any collaborator who partially stages hunks in it.

### Likelihood Explanation
Full-file staging (`git add`) bypasses this bug since it uses the file as-is, but Desktop's signature UX feature — line-by-line/hunk selection for commits — always routes through `getWorkingDirectoryDiff` → `diffFromRawDiffOutput` → `formatPatch` → `applyPatchToIndex`, so any repository with non-ASCII, non-UTF-8-encoded tracked files hits this path routinely. The comment in the code itself acknowledges the assumption is known and unaddressed, and there is no encoding detection or fallback (e.g., using `git diff`'s own encoding negotiation or `core.quotepath`/`i18n.commitEncoding` awareness) anywhere in this pipeline.

### Recommendation
Do not unconditionally decode the raw diff buffer as UTF-8. Detect or respect the file's actual encoding (e.g., via `.gitattributes` `working-tree-encoding`, BOM sniffing, or git's own `i18n`/`core.quotepath` settings) before converting to a string for parsing, or — safer — perform partial-patch application using byte offsets against the original buffer rather than round-tripping through a lossy string decode/re-encode, so a partial commit's applied bytes always match the working-directory bytes the user actually selected.

### Proof of Concept
1. Create a repository containing a tracked text file saved in a non-UTF-8 encoding (e.g., UTF-16LE, or Shift-JIS) that includes byte sequences which are invalid/ambiguous as UTF-8.
2. Modify a line in that file and open Desktop's changes view; select only some of the hunks/lines for commit (partial staging).
3. Observe that `diffFromRawDiffOutput` (`app/src/lib/git/diff.ts:788-796`) decodes the git diff buffer as UTF-8, producing `DiffLine.text` values that no longer correspond byte-for-byte to the on-disk content wherever multi-byte sequences were misinterpreted.
4. Commit the partial selection; `formatPatch` (`app/src/lib/patch-formatter.ts:143-206`) reassembles the patch from these already-corrupted `DiffLine.text` strings and `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-82`) applies it via `git apply --cached`.
5. Inspect the resulting commit blob: it differs from the actual working-directory file content the user intended to stage, despite the UI never surfacing any warning.

/**
 * Render the diff for a file within the repository working directory. The file will be
 * compared against HEAD if it's tracked, if not it'll be compared to an empty file meaning
 * that all content in the file will be treated as additions.
 */
export async function getWorkingDirectoryDiff(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  hideWhitespaceInDiff: boolean = false
): Promise<IDiff> {
  // `--no-ext-diff` should be provided wherever we invoke `git diff` so that any
  // diff.external program configured by the user is ignored
  const args = [
    'diff',
    ...(hideWhitespaceInDiff ? ['-w'] : []),
    '--no-ext-diff',
    '--patch-with-raw',
    '-z',
    '--no-color',
  ]
  const successExitCodes = new Set([0])
  const isSubmodule = file.status.submoduleStatus !== undefined

  // For added submodules, we'll use the "default" parameters, which are able
  // to output the submodule commit.
  if (
    !isSubmodule &&
    (file.status.kind === AppFileStatusKind.New ||
      file.status.kind === AppFileStatusKind.Untracked)
  ) {
    // `git diff --no-index` seems to emulate the exit codes from `diff` irrespective of
    // whether you set --exit-code
    //
    // this is the behavior:
    // - 0 if no changes found
    // - 1 if changes found
    // -   and error otherwise
    //
    // citation in source:
    // https://github.com/git/git/blob/1f66975deb8402131fbf7c14330d0c7cdebaeaa2/diff-no-index.c#L300
    successExitCodes.add(1)
    args.push('--no-index', '--', '/dev/null', file.path)
  } else if (file.status.kind === AppFileStatusKind.Renamed) {
    // NB: Technically this is incorrect, the best kind of incorrect.
    // In order to show exactly what will end up in the commit we should
    // perform a diff between the new file and the old file as it appears
    // in HEAD. By diffing against the index we won't show any changes
    // already staged to the renamed file which differs from our other diffs.
    // The closest I got to that was running hash-object and then using
    // git diff <blob> <blob> but that seems a bit excessive.
    args.push('--', ensureRelativePath(file.path))
  } else {
    args.push('HEAD', '--', ensureRelativePath(file.path))
  }

  const { stdout, stderr } = await git(
    args,
    repository.path,
    'getWorkingDirectoryDiff',
    { successExitCodes, encoding: 'buffer' }
  )
  const lineEndingsChange = parseLineEndingsWarning(stderr)

  return buildDiff(stdout, repository, file, 'HEAD', 'HEAD', lineEndingsChange)
}

  // for now we just assume the diff is UTF-8, but given we have the raw buffer

  private nextLine(): boolean {
    this.ls = this.le + 1

    // We've reached the end of the diff
    if (this.ls >= this.text.length) {
      return false
    }

    this.le = this.text.indexOf('\n', this.ls)

    // If we can't find the next newline character we'll put our
    // end pointer at the end of the diff string
    if (this.le === -1) {
      this.le = this.text.length
    }

    // We've succeeded if there's anything to read in between the
    // start and the end
    return this.ls !== this.le
  }

  /**
   * Advances to the next line and returns it as a substring
   * of the raw diff text. Returns null if end of diff was
   * reached.
   */
  private readLine(): string | null {
    return this.nextLine() ? this.text.substring(this.ls, this.le) : null
  }

          oldCount++
        }

        // partial patch. If the user has elected not to commit a particular

          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++

          assertNever(line.type, `Unsupported line type ${line.type}`)
